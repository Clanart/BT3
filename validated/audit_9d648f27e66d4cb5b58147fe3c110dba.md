### Title
Webhook shop attribution is unauthenticated, allowing cross-shop data injection via HMAC replay - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only the raw request body against the shared secret via HMAC, but the `shop_domain` value used everywhere downstream to attribute the webhook to a specific shop is read from an unsigned HTTP header and is never bound to that signature. This is the same bug class as the CoWSwapClone report: a signature check that only covers part of the message data (here, the body) while a separate, security-relevant field (here, the shop identity) is trusted unchecked, letting an attacker who can obtain any one validly-signed message reuse it to affect a different party's context.

### Finding Description
`hmac_valid?` computes the HMAC over `request.raw_post` only: [1](#0-0) 

`WebhookVerification#verify_request` gates the endpoint solely on this body HMAC: [2](#0-1) 

The `shop_domain` helper, which the docs and generators instruct developers to use for dispatching per-shop background jobs, reads directly from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, which is completely outside the HMAC computation: [3](#0-2) 

The gem's own documentation instructs developers to build custom webhook controllers on exactly this pattern — passing the unauthenticated `shop_domain` straight into a background job: [4](#0-3) 

The generator templates for both declarative and manually-registered webhooks follow the same pattern, forwarding the header-derived shop value into the job without any binding to the signed payload: [5](#0-4) 

Because the secret used for HMAC is the app's single client secret (shared across every shop that installs the app, per `ShopifyApp.configuration.secret`), any shop that legitimately installs the app can receive a validly HMAC-signed webhook body for itself. An attacker (an "unrelated merchant" from the perspective of a target victim shop) can capture that valid `(body, HMAC)` pair from their own store's webhook delivery and resend it to the app's webhook endpoint while replacing only the `X-Shopify-Shop-Domain` header with the victim shop's domain. `hmac_valid?` still passes because it never inspects the header, and the resulting job is queued/executed with `shop_domain` set to the victim shop, even though the payload content originated from, and was authored by, the attacker's own shop.

### Impact Explanation
This lets an attacker who controls one shop feed attacker-chosen webhook payload data into another shop's processing pipeline (e.g. triggering `orders/create`, `products/update`, or other per-shop jobs under the victim's `shop_domain`), which is a cross-shop data-integrity/access violation analogous to the surplus-misdirection issue in the original report: a value/attribution field that should be authenticated by the signature is instead accepted from an untrusted source.

### Likelihood Explanation
Requires the attacker to operate/install the app on a shop they control (low barrier — any merchant can install a public app) and to intercept/replay one legitimate webhook delivery while modifying an HTTP header, which is straightforward for anyone who can send arbitrary HTTP requests to the app's public webhook endpoint. No secret leakage or privileged access is needed.

### Recommendation
Bind the shop identity into the authenticated payload rather than trusting the `X-Shopify-Shop-Domain` header on its own — e.g., derive the shop exclusively from the verified webhook body's `myshopify_domain`/equivalent field (as Shopify's official webhook payloads include this), or include the header value in the HMAC computation and reject the request in `verify_request`/`hmac_valid?` if it doesn't match. `shop_domain` in `lib/shopify_app/controller_concerns/webhook_verification.rb` should not be exposed as an independently-trustworthy value separate from the signature check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook (e.g. `orders/create`) from Shopify, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify with the app's shared secret over `B`).
2. Attacker sends `POST /webhooks/orders_create` (or the app's custom endpoint using `ShopifyApp::WebhookVerification`) to the target app with body `B`, header `X-Shopify-Hmac-Sha256: H`, but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `hmac_valid?(request.raw_post)` succeeds because it only checks `B` against `H` and the shared secret [1](#0-0) .
4. The app dispatches the job using `shop_domain` = `victim-shop.myshopify.com` (per the documented pattern) even though the payload `B` was generated for/by the attacker's own shop, injecting attacker-influenced data into the victim shop's processing context.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
