### Title
`presumed_origin` and in-instruction data are bound to scanned outputs positionally — the payer controls which input/output is treated as the "origin" - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
The Footium report's bug class — an off-chain/intended identifier bound to an entity purely by ordering, with the mapping under the caller's control — exists in Serai's Bitcoin output scanning. `Bitcoin::get_outputs` derives each received `Output`'s `presumed_origin` from `tx.input[0]` and applies the transaction's extracted Serai `data` to every `OutputType::External` output in the same transaction. An unprivileged Bitcoin sender fully controls input and output ordering, so the identity bound to a deposit is whatever they choose to place first — never verified on-chain.

### Finding Description
In `get_outputs`, after `scanner.scan_transaction(tx)` collects all outputs paying a multisig key, the processor computes a single `presumed_origin` for the entire transaction by taking the *first* input's prevout script: [1](#0-0) 

The code itself acknowledges the guesswork: "This may identify the P2WSH output *embedding the InInstruction* as the origin". Then one shared `data` blob from `Self::extract_serai_data(tx)` and that single `presumed_origin` are stamped onto *every* scanned output in the tx: [2](#0-1) 

Nothing binds `tx.input[0]` to the depositor. In any transaction paying a Serai address — including PayJoin/coinjoin-style transactions or any multi-input spend — the party constructing the tx (or a cooperating counterparty) picks which input occupies index 0, hence which address Serai records as the origin. Likewise, a single embedded `InInstruction` is attributed to all external outputs of the tx regardless of which output it was intended for; the correspondence between `tx.output[i]` and the instruction is positional only.

### Impact Explanation
`presumed_origin` is recorded on the `Output` (`Output { kind, presumed_origin, output, data }`) and propagated via `ScannerEvent::Block`/Batch handling for downstream attribution — e.g., refund/origin resolution for deposits. Because the binding is caller-chosen:

- A depositor can make Serai attribute a deposit to an arbitrary origin address they do not control (by placing an input whose prevout has that script first — trivially achievable in any jointly-constructed or batched transaction where the initiator orders inputs).
- One `InInstruction` (e.g., a swap/refund instruction naming a destination/refund address) is applied to every external output in the tx. A sender can attach multiple Serai-payable outputs to one instruction, causing all of them to be processed under a single intended binding — funds end up accounted under an instruction/origin the on-chain data never actually tied them to.

This mirrors the Footium issue exactly: the mapping between the claimed identifier (`presumed_origin`/instruction) and the asset (the output) is enforced nowhere on-chain and is malleable via ordering by an unprivileged party.

### Likelihood Explanation
Any Bitcoin user sending funds to a Serai multisig address reaches this code; input ordering and the presence of multiple Serai-bound outputs are entirely under their control. No validator cooperation, broken BFT, or leaked keys are required. Exploitability of *consequence* depends on how downstream instruction execution consumes `presumed_origin`/`data` (e.g., refund routing); the misattribution primitive itself is unconditional. I could not fully trace all consumers of `presumed_origin` within the indexed scope, so the ceiling of impact (e.g., whether refunds are sent to it) is not fully verified — that residual uncertainty is why this is reported at Medium rather than higher.

### Recommendation
Do not infer a single origin for all outputs of a transaction positionally. Options:

1. Require the origin/instruction to be cryptographically bound per-output — e.g., derive the deposit identity from the output's own data (the `InInstruction` embedded in an OP_RETURN that explicitly commits to the vout it applies to), not from `tx.input[0]`.
2. If an input-based origin is retained, document it as a heuristic only, and never use `presumed_origin` for refund routing or fund attribution; require explicit refund addresses inside the instruction.
3. Reject or handle separately transactions with multiple inputs whose prevout scripts differ, or transactions containing more than one `OutputType::External` output with a single instruction, instead of silently replicating the binding.

### Proof of Concept
In `get_outputs` (`processor/src/networks/bitcoin.rs:686-740`):

```rust
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { /* collect outputs */ }
  if outputs.is_empty() { continue; }
  let presumed_origin = {
    let input = &tx.input[0];                      // caller-chosen index
    ... rpc.get_transaction(prev txid) ...
    Address::new(spent_output.script_pubkey)       // first input's prevout script
  };
  let data = Self::extract_serai_data(tx);          // one blob for the whole tx
  for output in &mut outputs {
    if output.kind == OutputType::External { output.data.clone_from(&data); }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

Attack scenario:

1. Attacker constructs a Bitcoin transaction with inputs `[A, B]`, where input `A` spends a prevout paying to address `V` (e.g., a PayJoin/coinjoin input contributed by, or referencing, another party's script — or any script the attacker wants Serai to believe is the payer).
2. The transaction pays Serai's external (key) address with output(s), and embeds an `InInstruction` (refund/swap data) in an OP_RETURN.
3. `get_outputs` records `presumed_origin = V` for all scanned outputs, and attaches the same `data` to each external output — attributing the deposit and instruction to an origin chosen purely by input ordering, exactly as `generationIds` were bound to `playerId` purely by mint order in the Footium report.
