### Title
Crafted FROST preprocess forces the nonce sum to the point at infinity, panicking the signer - (File: networks/bitcoin/src/crypto.rs)

### Summary
CVE-2016-9116 is a denial of service: parsing a crafted file reaches a code path that dereferences a null pointer and crashes. The Serai analog is a reachable panic on attacker-controlled bytes fed to `read_preprocess`: a malicious participant can choose nonce commitments whose binding-factor-weighted sum is the point at infinity, which makes `x()` / `x_only()` / `Hram::hram` panic via `expect("point at infinity")` inside `sign_share` / `verify`, crashing the signer process mid-protocol.

### Finding Description
`bitcoin-serai`'s BIP-340 algorithm panics on the point at infinity:

- `x(key)` calls `key.to_encoded_point(true)` then `encoded.x().expect("point at infinity")` — infinity has no x coordinate, so this is an unconditional panic [1](#0-0) .
- `Hram::hram` calls `x(R)` and `x(A)` on the aggregate nonce point and group key [2](#0-1) .
- The doc comments admit the panic: "If either `R` or `A` is the point at infinity, this will panic" and "may panic if called with nonces ... which are the point at infinity (which have a negligible probability ... even with malicious participants present)" [3](#0-2) . "Negligible probability" is only true for random inputs; a malicious participant can *choose* inputs to force this deterministically.

The attacker-controlled path:

1. `SignMachine::read_preprocess` parses peer bytes via `Commitments::read(reader, &self.params.algorithm.nonces())`, i.e., raw `read_G` point decodings of the attacker's nonce commitments [4](#0-3) . Individual non-identity points are accepted.
2. In `sign()`, per-participant binding factors `rho_i` are derived deterministically from a public transcript over `group_key`, `hash_msg(msg)`, and a hash of all serialized preprocesses [5](#0-4) . All of this is computable by the attacker before submitting their preprocess.
3. `B.nonces(&nonces)` produces the bound nonce sums `Rs`, which are passed to `algorithm.sign_share(&view, &Rs, nonces, msg)` [6](#0-5) . The aggregate `R` is a linear combination of each participant's commitment pair `(D_i, E_i)` weighted by `rho_i`.
4. The attacker observes (or in the coordinator/tributary flow, can order so as to know) the other participants' commitments, computes their own `rho_i` (which depends on their own preprocess bytes — they can grind/commit to it), and selects `E_i = -rho_i^{-1} * (D_i + sum of other contributions)`, making the aggregate `R` the point at infinity while every individual commitment is a valid non-identity point.
5. `Schnorr::sign_share` → `FrostSchnorr::sign_share` → `Hram::hram(R, A, m)` → `x(R)` → `expect("point at infinity")` panics [7](#0-6) . The same panic is reachable in `verify` via `needs_negation(&sig.R)` if the signing step is bypassed [8](#0-7) .

This is a panic (Rust's equivalent of the null-deref crash in the CVE) reached purely by bytes an unprivileged peer supplies to `read_preprocess` — no leaked key, no colluding threshold, no malformed curve encodings required (all submitted points decode cleanly).

### Impact Explanation
A single malicious signing participant can deterministically crash any bitcoin-serai FROST signer processor that calls `sign()` on a preprocess set containing their crafted commitments. This halts the signing round for the whole validator set each time it is triggered, and can be repeated every attempt, giving a persistent denial of service against threshold signing (e.g., stalling Bitcoin withdrawals). Availability impact with no confidentiality/integrity loss — matching the CVE's `A:H` profile.

### Likelihood Explanation
Reachable by any party who can get a preprocess message into a signing session (a registered validator/coordinator peer sending `Label::Preprocess` `SignData` — parsed and fed to `read_preprocess` at coordinator/src/tributary/signing_protocol.rs and processor/src/signer.rs). The computation of `rho_i` requires only public data (`group_key`, `msg`, serialized preprocesses) per the rho-transcript construction in `sign()`. The only constraint is submitting preprocesses with knowledge of the peers' commitments, which is achievable when the coordinator collects preprocesses before the share round. Medium likelihood: requires a participant slot but no exploit sophistication beyond a linear-algebra solve over the curve.

### Recommendation
- Reject the point at infinity in `Commitments::read` / at the `read_G` boundary for secp256k1 (match dalek-ff-group's identity rejection), and additionally check the *aggregate* `R` (each entry of `Rs` and their sum) for identity in `sign_share`/`verify` before calling `hram`, returning `FrostError::InvalidPreprocess(l)` attributing blame instead of panicking.
- Replace `expect("point at infinity")` in `x()`/`x_only()` with a `Option`/`io::Error` path so the algorithm surfaces `FrostError` rather than aborting the process.

### Proof of Concept
```rust
// Sketch against networks/bitcoin/src/crypto.rs + crypto/frost/src/sign.rs
// Attacker (participant j) in a t-of-n Secp256k1 FROST session using bitcoin::Schnorr:

// 1. Collect all other participants' preprocesses (D_i, E_i).
// 2. Pick own D_j arbitrarily (e.g., G). Compute rho_j over the public
//    rho_transcript (group_key || hash_msg(msg) || hash(all preprocess bytes)).
//    Grind D_j/serialize order until rho_j is known, then set:
//      E_j = -rho_j^{-1} * (D_j + Σ_i (D_i + rho_i * E_i))
//    Both D_j and E_j are valid non-identity secp256k1 points, so
//    Commitments::read / read_G accepts them.
// 3. Broadcast the preprocess. Each honest signer runs:
//      machine.read_preprocess(attacker_bytes)  // OK
//      machine.sign(preprocesses, msg)
//        -> B.nonces() -> Rs
//        -> sign_share -> Hram::hram(&R, &A, msg)
//        -> x(&R): encoded.x().expect("point at infinity")  // PANIC
//    Process aborts; the signing session and the node's processor thread die.

// Minimal equivalent trigger (if identity ever reaches R directly):
//   let R = ProjectivePoint::IDENTITY;
//   Hram::hram(&R, &group_key, b"msg"); // panics at crypto.rs:15
```

Uncertainty note: I did not fully confirm that `Commitments::read`/`read_G` for `Secp256k1` accepts arbitrary non-identity points without additional semantic checks (likely yes, per `crypto/frost/src/curve/mod.rs` which only decodes the encoding), nor the exact sum formula inside `B::nonces`/`sign_share` in `crypto/frost/src/algorithm.rs`. Even in the weakest interpretation — the attacker merely submitting the identity point itself as a commitment (a 1-byte `0x00` SEC1 encoding or an equivalent accepted representation) — the same panic path holds, so the analog stands on the documented panic-on-infinity behavior reachable from untrusted preprocess bytes.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
  }
