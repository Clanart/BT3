### Title
`ReceivedOutput::read` records an untrusted offset and `TxOut` without validating the pair — deserialized outputs claim spendable value the group key cannot spend (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
Analogous to D3Maker recording a maker-supplied token decimal instead of querying the token contract, `ReceivedOutput::read` deserializes a scalar `offset` and a `TxOut` straight from attacker-controlled bytes and records them as a spendable output without any check that `p2tr(group_key + G*offset) == output.script_pubkey` or that the output exists on chain. The recorded pair is later trusted by `SignableTransaction::new` for input-value accounting, fee math, and as the `Prevouts::All` commitment signed by every FROST participant.

### Finding Description
`Scanner::scan_transaction` only ever produces `ReceivedOutput`s whose `offset` was derived from `register_offset` and whose `output` came from a real transaction output matching a registered `script_pubkey` (`wallet/mod.rs:199-214`). The `read` constructor bypasses both invariants: it reads `offset` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` (including its `value`) and `OutPoint`, and returns them with no binding to the scanner's key or script map (`wallet/mod.rs:122-133`).

The value enters `input_sat` at `send.rs:175`, the offset enters `self.offsets` at `send.rs:176`, and the fabricated `TxOut` enters `self.prevouts` at `send.rs:253`. At signing time each input's prevout (with the attacker-chosen `value`) is committed via `Prevouts::All` into `taproot_key_spend_signature_hash` (`send.rs:375-390`), so all threshold participants sign a sighash committing to amounts the UTXO set may not contain.

`SignableTransaction::multisig` does check `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` (`send.rs:277`), but this is a partial, downstream check: it only binds the offset to the script, never the script/value/outpoint to an actual chain output, and it fails closed by returning `None` rather than at the deserialization boundary where the malformed object should be rejected.

### Impact Explanation
An unprivileged party able to feed bytes to `ReceivedOutput::read` can cause the wallet/coordinator to treat a fabricated UTXO (arbitrary `outpoint`, arbitrary `value`, arbitrary `script_pubkey`/offset pairing) as a spendable input. Consequences: (a) funds accounted as received/spendable in `input_sat` and `needed_fee` math that are not spendable, burning a full FROST signing round and producing a transaction that is invalid on-chain (sighash commits to fake prevout amounts under `Prevouts::All`), or (b) when the offset/script pairing is inconsistent, the late `multisig` check silently returns `None`, wedging the spend. This is the Serai analogue of "wrong decimal → wrong amount": a parameter that should be derived (offset from the scanner, value/script from the chain) is recorded verbatim from input.

### Likelihood Explanation
Requires a peer/queue path delivering serialized `ReceivedOutput`s to a signer — the same trust level as share/preprocess bytes, which the threat model already treats as untrusted. Unlike the decimal bug it requires no privileged role; it needs only the ability to supply bytes to `read`. Impact is capped at Medium: it cannot forge a valid Bitcoin signature (sighash binds prevouts), but it reliably produces unspendable inputs, invalid signed transactions, and failed signing rounds.

### Recommendation
Do not trust the deserialized `offset`/`TxOut` pair. Either remove `ReceivedOutput::read` for untrusted input, or re-verify at read/consumption time that the output exists on chain (matching the outpoint's real `TxOut`) and that `p2tr_script_buf(key + G*offset)` equals `output.script_pubkey` — i.e., derive the binding from the authoritative source (the scanner/chain), exactly as the DODO fix derives decimals from the token contract rather than from maker input.
