### Title
Future-timestamped Pyth price accepted as "fresh" bypasses staleness gating - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`oracle-timestamp-fresh` is the gate used in `price-resolve` to decide whether a resolved oracle price is usable for collateral/debt valuation. It computes a staleness `delta` between the current block time and the feed's `publish-time`. When the feed's reported timestamp `ts` is in the future relative to `stacks-block-time`, the function sets `delta` to `u0` rather than treating this as invalid, so the freshness check `(<= delta max-staleness)` always passes for future timestamps, regardless of how far in the future they are.

### Finding Description
`price-resolve` calls `resolve-price-feed` to fetch a Pyth/DIA price and its `publish-time`, then gates acceptance with:
```clarity
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
          ERR-ORACLE-INVARIANT)
``` [2](#0-1) 

`oracle-timestamp-fresh` is supposed to reject stale prices (delta too large) and enforce monotonicity (`ts >= prev`, i.e., the per-feed timestamp must not go backwards). However, for the "future" branch it silently substitutes `delta = 0`, treating a future-dated publish-time as maximally fresh instead of rejecting it. It only enforces monotonicity (`>= prev`) for that branch, not a staleness/plausibility bound. This means any price entry with a `publish-time` set arbitrarily far in the future — whether from a misbehaving/compromised relay path, clock skew, or crafted Pyth VAA payload accepted by `pyth-storage-v4` — will always satisfy the freshness assertion and be accepted by the market as the current price, updating `last-update` in the process (`(if (> timestamp last-update-time) (map-set last-update key timestamp) false)`). [3](#0-2) 

This mirrors the report's root cause exactly: a temporal bound check ("don't accept values belonging to the future") is missing on one branch, letting an attacker-influenced or stale/incorrect value pass validation that should have failed, and it also poisons `last-update` so subsequent legitimate but earlier-timestamped updates can be rejected as not "newer".

### Impact Explanation
Because the accepted price feeds directly into `price-multi-resolve`/collateral and debt valuation, an unchecked future-timestamped price of arbitrary staleness bypasses the protocol's staleness gating for that asset's oracle path, corrupting the health/valuation computation used for borrow/liquidation decisions. This falls under theft of unclaimed yield or temporary freezing of funds depending on which direction the mispriced value skews borrowing/liquidation, since it directly manipulates the price feed used for collateral and debt accounting.

### Likelihood Explanation
Triggering this requires only a Pyth (or DIA) price update whose `publish-time` is greater than the current `stacks-block-time` to reach `resolve-pyth`/`resolve-dia` and then `price-resolve`; no privileged access or DAO action is needed — it can be exercised through the standard price-update path whenever a feed timestamp exceeds the local block clock.

### Recommendation
Reject timestamps that are in the future outright (e.g., `(asserts! (<= ts stacks-block-time) ...)`) instead of clamping `delta` to `u0`, so future-dated publish-times fail the staleness/freshness check like any other invalid timestamp.

### Proof of Concept
1. A Pyth price update is stored in `pyth-storage-v4` (or relayed via DIA) with `publish-time` set to a value greater than the current `stacks-block-time` (e.g., due to clock skew, malformed VAA, or any path that lets a future timestamp reach storage).
2. `resolve-pyth`/`resolve-dia` returns `{ value, timestamp }` with this future `timestamp`. [4](#0-3) 
3. `price-resolve` calls `oracle-timestamp-fresh(timestamp, last-update-time, max-staleness)`. Since `timestamp > stacks-block-time`, `delta` becomes `u0`, so `(<= delta max-staleness)` is trivially true, and (assuming `timestamp >= last-update-time`) the whole check passes. [5](#0-4) 
4. The market accepts `final-price` as valid and sets `last-update` to the future timestamp, which is then used for collateral/debt valuation in subsequent borrow/liquidation calculations.
