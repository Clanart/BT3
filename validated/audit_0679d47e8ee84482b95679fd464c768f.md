## Title
Bank precompile `send()` bypasses `SendEnabled`/`AllowList` restrictions in legacy versions - (File: `precompiles/bank/legacy/v552/bank.go`, `v555/bank.go`, `v562/bank.go`)

## Summary
Multiple legacy versions of the Cosmos `bank` precompile's `send` method call `p.bankKeeper.SendCoins(...)` directly, completely skipping the `IsSendEnabledCoins` and `IsInDenomAllowList` checks that the canonical `x/bank` `MsgSend` handler enforces. This is structurally the same bug class as the phpMyFAQ advisory: an authorization/state check ("send enabled" / "allow-listed") that is correctly enforced on one code path is silently missing on a second, still-reachable code path.

## Finding Description
`sei-cosmos/x/bank/keeper/msg_server.go`'s `Send` handler enforces both restrictions before moving funds: [1](#0-0) 

`IsSendEnabledCoins`/`IsInDenomAllowList` gate transfers of `SendEnabled=false` denoms and tokenfactory denoms with a configured allow-list: [2](#0-1) [3](#0-2) 

However, the legacy `bank` precompile `send()` implementations (reachable by any EVM caller that is the registered ERC20-native pointer for a denom) call `p.bankKeeper.SendCoins` directly instead of going through `MsgSend`/`bankMsgServer.Send`, so neither check is applied: [4](#0-3) [5](#0-4) [6](#0-5) 

By contrast, later legacy revisions (`v601`, `v605`, `v606`, `v630`, `v65`, `v66`, `v67`) were fixed to route through `p.bankMsgServer.Send(...)`, which does apply `IsSendEnabledCoins` and `IsInDenomAllowList`: [7](#0-6) 

This shows the checks were deliberately added at the `MsgSend` boundary but a set of still-present legacy precompile code paths were never patched to enforce them — mirroring the phpMyFAQ pattern of a state-gating check (`inactive`/`SendEnabled`/`AllowList`) enforced on the primary path but forgotten on a secondary path.

## Impact Explanation
Any denom (including a tokenfactory denom) that has been configured with `DefaultSendEnabled=false`, a per-denom `SendEnabled=false` override, or a restrictive `AllowList` (used by tokenfactory issuers to control who may hold/transfer their asset) can still be transferred by calling the affected legacy `bank` precompile `send` method through its registered ERC20-native pointer contract. This is an unauthorized transfer via a precompile that circumvents issuer/governance-configured transfer restrictions, matching the "unauthorized transfer via precompile" impact category.

## Likelihood Explanation
Reachability depends on whether these specific legacy precompile module versions (`v552`, `v555`, `v562`) are still wired up and dispatched for live pointer contracts on the current chain (Sei's pointer/precompile versioning system keeps older bytecode-pinned pointer contracts working against pinned precompile logic after upgrades, as evidenced by the pointer-version-compatibility tests in `contracts/test/ERC20toCW20PointerTest-backup.js` and the `DisableWasmTest.js` guarantee that "existing pointers still work" after parameter changes). I could not fully confirm from the index whether the current version-dispatch wiring still routes any live pointer to these specific legacy files versus only to the patched `v601+`/current `precompiles/bank/bank.go`, or whether any tokenfactory denom relevant to a legacy pointer currently has `SendEnabled=false` or a restrictive `AllowList` set. If the legacy versions are still reachable for any live ERC20-native pointer, exploitation only requires a single EVM `send` call from that pointer contract — no privileged capability is needed.

## Recommendation
- Confirm which precompile module versions are actually dispatched to live pointer contracts, and if `v552`/`v555`/`v562` (or any other version still calling `bankKeeper.SendCoins` directly) are reachable, patch them to route through `bankMsgServer.Send` (or explicitly call `IsSendEnabledCoins` and `IsInDenomAllowList` before calling `SendCoins`), consistent with `v601`+.
- Audit all precompiles that call `bankKeeper.SendCoins`/`AddCoins`/`SubUnlockedCoins` directly (bypassing `MsgSend`) to ensure `SendEnabled` and `AllowList` checks are applied uniformly across every fund-movement code path, not just the primary `MsgSend` transaction type.

## Proof of Concept
1. As the tokenfactory admin, create a denom `factory/{admin}/restricted` and set `SendEnabled=false` for it (or set a `DenomAllowList` excluding an attacker address) via governance/`x/bank` params or `MsgSetDenomMetadata`/allow-list message.
2. Register (or use an already-deployed) ERC20-native pointer for that denom, which becomes the only `caller` permitted by the precompile's pointer check.
3. From the pointer contract, invoke the bank precompile's `send(from, to, denom, amount)` method for `factory/{admin}/restricted`.
4. Observe that if the pointer resolves to one of the vulnerable legacy precompile implementations (`v552`, `v555`, `v562`), the transfer succeeds despite `SendEnabled=false`/the address not being in the `AllowList`, because `p.bankKeeper.SendCoins` is called with no gating checks, unlike the equivalent `MsgSend` path in `sei-cosmos/x/bank/keeper/msg_server.go` which would reject it with `ErrSendDisabled` or `ErrUnauthorized`.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

// IsSendEnabledCoins checks the coins provide and returns an ErrSendDisabled if
// any of the coins are not configured for sending.  Returns nil if sending is enabled
// for all provided coin
func (k BaseSendKeeper) IsSendEnabledCoins(ctx sdk.Context, coins ...sdk.Coin) error {
	for _, coin := range coins {
		if !k.IsSendEnabledCoin(ctx, coin) {
			return sdkerrors.Wrapf(types.ErrSendDisabled, "%s transfers are currently disabled", coin.Denom)
		}
	}
	return nil
}

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}

func (p Precompile) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	// TODO: it's possible to extend evm module's balance to handle non-usei tokens as well
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}
