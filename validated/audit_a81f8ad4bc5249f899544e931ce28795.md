### Title
ReceivedOutput deserialization trusts an unbound scalar `offset` as the identifier for which key can spend the output - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to GHSA-8m3c-c723-h4p4 (a mutable identifier used for authorization decisions), `ReceivedOutput` uses a free-floating scalar `offset` as the identity of the spending key: the spendable key is implicitly `scanner.key + G * offset`. `ReceivedOutput::read` accepts `offset` directly from untrusted bytes without checking that it is consistent with `output.script_pubkey`, so a malformed `ReceivedOutput` can claim an output is spendable by an offset key that does not actually lock the output.

### Finding Description
`Scanner::scan_transaction` attributes an output by looking up `output.script_pubkey` in `scripts: HashMap<ScriptBuf, Scalar>` and returns the registered `offset` as the identifier of the derived key (`networks/bitcoin/src/wallet/mod.rs:199-214`). That pairing is internally consistent. However `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) reconstructs `offset` from raw bytes via `Secp256k1::read_F` and stores it alongside an arbitrary `TxOut` and `OutPoint`, with no recomputation of `p2tr_script_buf(key + GENERATOR * offset)` against the embedded `script_pubkey`. The offset is also intrinsically mutable — `register_offset` increments a requested offset until the resulting key is even (`wallet/mod.rs:180-196`), making offset bytes non-canonical identifiers that must not be trusted as-is.

### Impact Explanation
Any consumer feeding untrusted bytes to `ReceivedOutput::read` gets an output whose claimed spending key (`key + G*offset`) may differ from the key actually committed by `output.script_pubkey`. The result is funds reported received/attributed to an offset key that are not spendable under it (the script locks to a different tweaked point), or misattribution of ownership between registered subkeys. Spending code that derives the tweak from `offset()` will produce signatures for the wrong key.

### Likelihood Explanation
`ReceivedOutput::read` is an explicitly listed untrusted-bytes entry point and the type is a plain serialized record (offset || TxOut || OutPoint), so any peer-supplied or replayed serialized output controls the identifier. Exploitation only requires flipping/replacing the 32-byte offset field; no signing capability is needed. Impact is bounded to misattribution/unspendable-reporting rather than key recovery, hence medium.

### Recommendation
Make the offset non-authoritative: either (a) re-derive the expected `script_pubkey` from `key + GENERATOR * offset` in `ReceivedOutput::read`/a validating constructor and reject mismatches, or (b) store the canonical script_pubkey-derived mapping and verify `Scanner`-produced offsets only from the trusted `scripts` map, never from deserialized bytes. Document that `offset` is mutable (surjective under `register_offset`) and must never serve as a standalone identifier.

### Proof of Concept
```rust
// Given a Scanner for `key` and a legitimate ReceivedOutput O for offset `o`,
// an attacker crafts bytes: offset' (arbitrary) || O.output || O.outpoint.
let mut bytes = Vec::new();
bytes.extend(offset_prime.to_repr().as_ref());        // attacker-chosen scalar
bytes.extend(serialize(&legit_output));               // script locks to key + o·G
bytes.extend(serialize(&legit_outpoint));
let forged = ReceivedOutput::read::<&[u8]>(&mut bytes.as_slice()).unwrap();
// forged.offset() == offset_prime, so consumers treat it as spendable by
// key + offset_prime·G, while script_pubkey actually locks key + o·G.
// No consistency check exists in ReceivedOutput::read (wallet/mod.rs:122-134).
```
