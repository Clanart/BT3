Based on my investigation, I found a genuine analog: an unhandled `assert` (Python "CHECK-fail" equivalent) in offer parsing that fires on attacker-controlled input from an offer counterparty, rather than returning a graceful validation error.

### Title
Unhandled `AssertionError` (CHECK-fail) in `Offer.__post_init__` on malicious offer file with duplicate coin spends - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.__post_init__` builds an additions cache by iterating over `self._bundle.coin_spends` and asserting each `Coin` is unique with a bare `assert cs.coin not in adds` [1](#0-0) . This is a hard Python assertion, not a `ValidationError`/`Err` return, so a spend bundle crafted with two `CoinSpend` entries referencing the exact same `Coin` (identical `parent_coin_info`, `puzzle_hash`, `amount`) will raise an uncaught `AssertionError` instead of being rejected cleanly — the same bug class as the TensorFlow `CHECK_LT` report: an internal invariant check aborts processing on malformed/untrusted input rather than surfacing a handled error.

### Finding Description
`Offer` objects are constructed directly from untrusted, attacker-supplied bytes via `Offer.from_bytes` → `WalletSpendBundle.from_bytes` → `Offer.from_spend_bundle` [2](#0-1) , and via `Offer.from_bech32` → `try_offer_decompression` → `from_bytes` [3](#0-2) . Both paths run `__post_init__`, which contains the unguarded assertion at line 168:
```
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
``` [1](#0-0) 

This is directly reachable by an offer counterparty who hands a wallet user (or a Data Layer client) a `.offer` file / bech32 string. Any code path that parses an offer before the wallet's normal admission checks run will hit this: the wallet RPC `check_offer_validity` endpoint calls `Offer.from_bech32(request.offer)` unconditionally [4](#0-3) ; the `take_offer` RPC request type eagerly parses the offer via a cached property, `TakeOffer.parsed_offer` → `Offer.from_bech32(self.offer)` [5](#0-4) ; and the CLI `take_offer` command similarly calls `Offer.from_bech32(offer_hex)` on the raw file/string before any RPC round-trip [6](#0-5) .

By contrast, the mempool's own `validate_spend_bundle` catches the equivalent duplicate-coin condition and returns `Err.DOUBLE_SPEND` cleanly (confirmed by `test_double_spend_prevalidation` / `test_duplicate_removals`), showing the intended behavior is a handled error, not a crash [7](#0-6) . The offer-parsing path lacks this protection.

### Impact Explanation
This is a denial-of-service against wallet/RPC/CLI processing of a single crafted offer, not a network-wide or consensus-level break — no unauthorized coin movement, no supply inflation, and no coin-set divergence results. The assertion aborts the specific `Offer` construction call with an unhandled `AssertionError` rather than a `ValueError`/`ValidationError`, which is exactly the "hard-abort instead of clean error" pattern the CVE describes; whether this crashes only the RPC call (if wrapped by a generic exception handler) or a longer-running CLI/daemon process could not be fully confirmed from static inspection alone, since I did not locate an explicit `except AssertionError` handler around these call sites in the reviewed code. This uncertainty should be verified by exercising the RPC server's global exception handling behavior directly.

### Likelihood Explanation
High: any offer counterparty can trivially construct a `SpendBundle` with two `CoinSpend`s that reference byte-identical `Coin` objects (same parent id/puzzle hash/amount) — no signature validity or CLVM execution is required to reach `__post_init__`, since the assertion fires during object construction before any cryptographic or consensus check.

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__` with an explicit check that raises `ValueError`/`ValidationError` (consistent with the existing `Bundle has duplicate requested payments` handling a few lines above at line 155) so malformed/malicious offers are rejected gracefully instead of raising an uncaught `AssertionError`.

### Proof of Concept
1. Construct a `Coin` object `C` (arbitrary parent id, puzzle hash, amount).
2. Build a `WalletSpendBundle` with two `CoinSpend` entries both spending the identical `Coin` `C` (can use trivial/garbage puzzle reveal and solution — no valid signature or CLVM execution is needed since the assertion fires before those are used).
3. Serialize this bundle the way an `Offer` is serialized (`Offer.__bytes__` writes `bytes(self.to_spend_bundle())` — an attacker can construct the same byte layout directly) and bech32m-encode it as an offer file.
4. Have the victim run `chia wallet take_offer <path_or_hex>` or call the `check_offer_validity` / `take_offer` RPC endpoint with this string.
5. Observe `Offer.from_bech32` → `Offer.__post_init__` raises `AssertionError` on `assert cs.coin not in adds` instead of returning a handled validation error.
