Confirmed: `CallDispatcher.dispatch(bytes)` is a completely unpermissioned, singleton, persistent contract shared by every `IntentGatewayV2.placeOrder`/`fillOrder` call that uses predispatch/postdispatch execution — it has no access control (`external`, no `msg.sender` check) and no self-destruct/ephemeral pattern, so any balance sitting on it at any time carries over between unrelated orders and unrelated callers.

### Title
Predispatch/postdispatch escrow sweep uses raw `balanceOf(dispatcher)` instead of a delta, letting anyone donate tokens to the shared `CallDispatcher` and have them silently captured into the next unrelated order's escrow — (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` (and the analogous cross-chain fill path) mirrors the GVault `convertToShares`/`_totalAssets` bug class: it computes an "actual received" accounting value from a live `balanceOf()` read on a shared contract rather than from a value that is provably attributable to the current transaction/caller. In the predispatch sweep, the amount escrowed for `order.inputs[i]` is derived from `IERC20(token).balanceOf(dispatcher)` — the dispatcher's *total* balance — not the balance delta produced by that specific predispatch call.

### Finding Description
In `placeOrder`'s predispatch branch: [1](#0-0) 
```solidity
ICallDispatcher(dispatcher).dispatch(order.predispatch.call);

// Build sweep calls and snapshot gateway balances before the sweep.
...
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token, value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
```
The sweep transfers **the dispatcher's entire balance** of `token`, not the amount produced by the just-executed predispatch call. `CallDispatcher` itself is a bare, unauthenticated, persistent singleton (`evm/src/utils/CallDispatcher.sol`): `dispatch()` has no caller restriction, no reentrancy guard, and the contract never zeroes or isolates balances per call. Any ERC-20 (or native ETH, via its `receive()`) can be sent directly to the dispatcher address by anyone, at any time, completely outside of a `placeOrder` transaction.

Because the gateway measures "received" as the dispatcher's full balance swept back (`received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]`, at lines 261-268), any tokens already sitting in the dispatcher before a legitimate user's predispatch call executes get folded into that user's order — inflating `order.inputs[i].amount`, which flows directly into the fee-reduced amount, the `commitment` hash, and the `_orders[commitment][token]` escrow credit: [2](#0-1) 

This is the same broken invariant as the GVault report: a value used for critical accounting (`_totalAssets` there, "actual received input" here) is read via `balanceOf()` on an address that is influenceable by unrelated third-party transfers, instead of being derived from a value scoped strictly to the current logical operation.

### Impact Explanation
An attacker who directly `transfer()`s tokens to the `CallDispatcher` address can have those donated funds swept into *someone else's* (or their own, if they self-fill same-chain) order escrow the next time any user places an order with a predispatch call using that token. This:
- Inflates escrowed input amounts beyond what the order's user actually paid, meaning tokens that never belonged to that order's economics get committed into `_orders[commitment][token]` and are later paid out to whichever solver fills the order (`withdraw()`/`_fillSameChain`) — a wrong-beneficiary / unauthorized-transfer of donated value.
- If the attacker times their own `placeOrder` (with a minimal/no-op predispatch call) right after donating, they can capture stray or maliciously pre-seeded dispatcher balances into their own escrow essentially for free, then fill/settle to extract value — a fund-diversion primitive matching the bounty's "stealing or loss of funds" / "transaction manipulation" categories.
- Because the dispatcher is shared across **all** orders and chains using predispatch, this also creates cross-order interference: a normal user's predispatch swap leaving any residual dust in the dispatcher (which the code assumes gets fully swept) can be intercepted by a subsequent unrelated order that races to sweep first, front-running the intended sweep within the same block/mempool.

This is an unprivileged, no-relayer/no-prover/no-admin path reachable purely by an ordinary ERC-20 `transfer` plus a normal `placeOrder` call.

### Likelihood Explanation
Medium-High. `CallDispatcher` is a public, address-known, singleton contract with `receive()` and an unauthenticated `dispatch()`; anyone can send it tokens/ETH at any time with a plain transfer — no special permissions or malicious peer/relayer/prover involvement required. Exploitation only additionally requires calling the already-public `placeOrder` with a predispatch order, which is a standard use path documented for swap-then-escrow flows.

### Recommendation
Do not sweep `balanceOf(dispatcher)`. Track and sweep only the **delta** produced by the specific predispatch call, e.g. snapshot `balanceOf(dispatcher)` immediately before `ICallDispatcher.dispatch(...)` executes and sweep only `balanceAfter - balanceBefore` (mirroring the pattern already correctly used for `address(this)` in the same function, at lines 261-268). Alternatively, deploy an ephemeral (per-order) `CallDispatcher` instance via `CREATE2`/minimal-proxy that is destroyed or can be proven to start at zero balance, so no state can carry over between unrelated orders. Add regression tests that pre-fund the dispatcher with an attacker-controlled donation before a legitimate `placeOrder` call and assert the resulting escrow equals only the amount produced by that order's own predispatch execution.

### Proof of Concept
1. Attacker calls `usdc.transfer(address(callDispatcher), 1_000e6)` directly — no gateway interaction, no approval, works because `CallDispatcher` has no owner/whitelist and `evm/src/utils/CallDispatcher.sol` `dispatch()` is unauthenticated with no balance isolation.
2. A victim (or the attacker themself) calls `placeOrder(order, graffiti)` with `order.predispatch.assets` containing USDC and a trivial no-op/self-contained predispatch call that produces, say, `10e6` USDC of real output at the dispatcher.
3. Inside `placeOrder`, the sweep computes `balance = IERC20(usdc).balanceOf(dispatcher)` = `1_010e6` (10 real + 1000 donated) instead of `10e6`, and transfers the whole amount back to the gateway.
4. `order.inputs[i].amount` is set to `received = 1_010e6` (line 274), which is then fee-reduced and committed into `_orders[commitment][usdc]` (lines 300-343) — escrowing 100x more USDC than the order's user actually contributed.
5. When a solver fills the order and the escrow is released via `withdraw()`, the solver (or the attacker if they are also the filler in a same-chain order) receives the donated `1000 USDC` that was never part of any legitimate order economics — verified against the existing fee-on-transfer test pattern at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2281-2308`, which already demonstrates the gateway trusts `balanceOf`-derived "actual received" values as authoritative for escrow and commitment computation.
