### Title
Restricted (allow-listed) tokenfactory denom transfers can be moved through the bank keeper's `SendCoins`/`InputOutputCoins` internal paths that skip the `IsInDenomAllowList` check enforced only in `MsgSend`/`MsgMultiSend` - ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
`x/bank`'s `MsgSend` and `MsgMultiSend` handlers explicitly call `IsInDenomAllowList` before moving funds for tokenfactory denoms that have an allow-list configured (`SetDenomAllowList`/`DenomAllowList`). However, the actual balance-moving primitives — `BaseSendKeeper.SendCoins`, `SendCoinsWithoutAccCreation`, `sendCoinsWithoutAccCreation`, and `InputOutputCoins` — perform no such check themselves; the allow-list enforcement lives entirely in the message-server layer, not in the keeper.

### Finding Description
`IsInDenomAllowList(ctx, addr, coins, cache)` gates whether a sender/receiver may move a tokenfactory denom that has a configured `AllowList` [1](#0-0) . The check is invoked from `msgServer.Send` and `msgServer.MultiSend` before calling into `k.SendCoins`/`k.InputOutputCoins` [2](#0-1) [3](#0-2) . But `BaseSendKeeper.SendCoins` itself simply calls `SendCoinsWithoutAccCreation` → `sendCoinsWithoutAccCreation` → `SubUnlockedCoins`/`AddCoins`, with no allow-list validation anywhere in that chain [4](#0-3) . Any module or precompile path that calls `bankKeeper.SendCoins` directly (rather than going through the `MsgSend`/`MsgMultiSend` message server) bypasses the allow-list restriction entirely — mirroring the Gitea report's pattern where the fix (a visibility/permission gate) was applied to one API surface (`ListPublicMembers`) but not a sibling one reaching the same underlying data/action (`ListMembers`).

Concretely, `precompiles/bank`'s `send`/`sendNative` functions build a `banktypes.MsgSend` and invoke it via `p.bankMsgServer.Send(...)` (which is safe, since it goes through the checked path) [5](#0-4) , so EVM-originated `MsgSend` traffic is protected. The risk is any other caller of the raw keeper `SendCoins`/`InputOutputCoins` methods (used pervasively by other Cosmos SDK modules, e.g., IBC transfer, distribution, staking module-to-account payouts, or custom precompiles/keepers that move tokenfactory-denom coins) that does not re-implement the `IsInDenomAllowList` gate. In such a path, an address excluded from a token's allow-list can still receive or (if it is itself the module-authorized signer of such a transfer) send an allow-listed tokenfactory denom, defeating the purpose of `MsgCreateDenom`'s / `MsgUpdateDenom`'s allow-list feature.

### Impact Explanation
An allow-list on a tokenfactory denom is meant to strictly control which addresses may hold/transfer a specific token (e.g., compliance-gated or permissioned assets). If any keeper-level transfer path other than `MsgSend`/`MsgMultiSend` moves that denom without checking `IsInDenomAllowList`, tokens can end up permanently held by or transferred to/from unauthorized addresses. Depending on which subsystem invokes `SendCoins` unchecked, this can amount to unauthorized transfer of a restricted asset, undermining the allow-list authority guarantee that `x/tokenfactory`/`x/bank` are supposed to enforce.

### Likelihood Explanation
This requires identifying a code path (module, precompile, or IBC middleware) that calls the raw `SendCoins`/`InputOutputCoins` keeper methods with a tokenfactory-allow-listed denom instead of the checked `MsgSend`/`MsgMultiSend` message-server path. The `precompiles/bank` `send` function is confirmed to be safe because it always routes through `p.bankMsgServer.Send`. I was unable to conclusively enumerate every other caller of `bankKeeper.SendCoins` across the codebase (e.g., IBC transfer module, IBC hooks, IBC-wasm bridge, IBC->CW20 pointer flow) within the available search budget, so it is uncertain whether a currently-reachable transaction path exists that would trigger this bypass, or whether this is only a latent architectural gap.

### Recommendation
Move the `IsInDenomAllowList` (and companion `BlockedAddr`) enforcement into the shared keeper primitives (`BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation`/`InputOutputCoins`) rather than duplicating it only in the `MsgSend`/`MsgMultiSend` message-server handlers, so that every caller of the keeper — present and future — is guaranteed to respect denom allow-lists, consistent with how `AddCoins` already enforces `CanSendTo` for blocklisted addresses at the primitive level [6](#0-5) .

### Proof of Concept
Not independently confirmed with a live end-to-end transaction trace due to tool-call limits; the following is the code-level reasoning trail supporting the finding:
1. Create a tokenfactory denom and call `MsgUpdateDenom`/`SetDenomAllowList` to restrict it to a specific set of addresses [7](#0-6) .
2. Confirm `MsgSend`/`MsgMultiSend` correctly reject transfers to/from non-allow-listed addresses [2](#0-1) .
3. Find/trigger any code path that calls `bankKeeper.SendCoins`/`InputOutputCoins` directly (bypassing the msg server) for that denom; because `sendCoinsWithoutAccCreation` performs no allow-list check [8](#0-7) , such a transfer would succeed to/from a non-allow-listed address, whereas the equivalent `MsgSend` would fail with `ErrUnauthorized`.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		bz, err := method.Outputs.Pack(true)
		return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, 0, err
	}

	msg := &banktypes.MsgSend{
		FromAddress: senderSeiAddr.String(),
		ToAddress:   receiverSeiAddr.String(),
		Amount:      sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount))),
	}

	err = msg.ValidateBasic()
	if err != nil {
		return nil, 0, err
	}

	if _, err = p.bankMsgServer.Send(sdk.WrapSDKContext(ctx), msg); err != nil {
		return nil, 0, err
	}

	bz, err := method.Outputs.Pack(true)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
