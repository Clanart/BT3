### Title
Trailer-boundary disagreement between Desktop's own regex parser and `git interpret-trailers` allows attacker-controlled commit bodies to smuggle/hide `Co-Authored-By` data across "Undo Commit" - ([File: app/src/lib/stores/git-store.ts])

### Summary
GitHub Desktop uses two independent parsers on the same untrusted commit-message text when restoring the commit editor state after "Undo Commit": (1) `git interpret-trailers --parse`, the ground-truth parser, and (2) a homegrown JS regex/`indexOf`-based re-parser (`coAuthorRe` + `parseSingleUnfoldedTrailer`). These two parsers do not enforce identical rules for what constitutes a trailer boundary, mirroring the class of bug in CVE-2021-22959 where two HTTP parsers disagreed about where a header name ends and its value begins.

### Finding Description
`loadCommitAndCoAuthors` in [1](#0-0)  gets trailers twice from the same commit message:
1. `parseTrailers` → shells out to `git interpret-trailers --parse`, the authoritative parser [2](#0-1) .
2. It then calls `mergeTrailers(..., unfold=true)` to get an "unfolded" body and walks the lines itself with a hand-written regex `coAuthorRe = /^co-authored-by(.)\s(.*)/i` and `parseSingleUnfoldedTrailer`, which locates the separator with a bare `line.indexOf(separator)` check (`ix > 0`) rather than git's own token-validation rules [3](#0-2) [4](#0-3) .

Desktop then reconciles the two views only by comparing `trailer.value` strings (not the full line, not the token strictly) between what its own regex found and what git's parser returned [5](#0-4) . This is a classic "two parsers, one input, ambiguous boundary" situation: because the value equality check is the only cross-check, an attacker-crafted commit body containing a line that git's official trailer parser accepts as a trailer, but that also collides on `value` with an unrelated line the local regex captures (or vice-versa — a well-formed trailer that git accepts but whose separator character isn't in the locally-fetched `separators` string, or a look-alike line the regex accepts that git's parser does not consider part of the trailer block), causes Desktop's JS-side view of "what's a trailer" to diverge from git's own semantics.

The result of the divergence is directly observable and actionable: `newBody` is computed by `lines.splice()`-ing out only the lines the *local* regex matched [6](#0-5) , not the lines that git's parser considered trailers. If the two disagree about which line is a trailer, the restored commit `description` (`newBody`) presented in the commit-message editor can silently retain or drop content compared to what git actually recorded/would record as a trailer, and `newAuthors`/`coAuthors` are populated from `GitAuthor.parse(t.value)` without further validation of the token that produced it [7](#0-6) .

### Impact Explanation
This is a parser-disagreement/smuggling-class bug rather than direct RCE. The concrete consequence within Desktop's actual attack surface (attacker controls a commit that lands in the user's history, e.g., via merge/cherry-pick/pull of a malicious branch, and the user later hits "Undo Commit") is:
- Corruption of what the user believes they are about to re-commit: `newBody`/`description` populated into the commit editor may silently include or exclude attacker-crafted lines depending on which parser "won," i.e. silent corruption of what the user commits next, matching the "silent corruption of what the user commits or pushes" impact category.
- Spurious/incorrect `Co-Authored-By` attribution surfaced in the UI (`newAuthors`), which is a trust/attribution integrity issue but not by itself a code-execution or credential-exfiltration primitive.

I was not able to fully verify, within the available tooling, the exact git-internal trailer grammar (e.g. whether `git interpret-trailers` accepts leading whitespace before the separator, or trailing token characters after `co-authored-by` that the local regex's single-wildcard-character separator would also accept) to construct a concrete divergent example line. This would need to be validated empirically with `git interpret-trailers --parse` against several crafted lines to build a reliable PoC.

### Likelihood Explanation
Likelihood is moderate-to-low:
- Requires the attacker's commit to become `HEAD` locally (via merge, cherry-pick, or direct push to a branch the user later undoes) — not "any cloned repo" automatically triggers this, it only runs on `Undo Commit`.
- The security-relevant blast radius is limited to commit-message editor content and co-author display, not filesystem or process boundaries, since `git`'s subprocess itself is the source of truth for the actual repository trailer data — Desktop's re-parse only affects what's shown/re-composed in the UI before the user re-commits.

### Recommendation
- Do not attempt to re-derive trailer boundaries with a hand-rolled regex/`indexOf` parser once `git interpret-trailers --parse` has already produced authoritative results; instead have git emit line-position or index metadata (or drive removal from the *unfolded* output using the same tokens git returned) so there is a single source of truth for boundary detection.
- If a second, local pass is unavoidable, match on the full `token:value` line (not just `value`) against git's canonical trailer list before splicing lines out of the body, and validate that the JS-side separator match (`coAuthorRe`) enforces the same token-character constraints (`trailer.separators`, key-format rules) that git's own trailer.c enforces, rather than accepting any single non-whitespace character as a valid separator.

### Proof of Concept
Not able to produce a concrete, empirically-verified divergent commit-message line within this investigation (would require running `git interpret-trailers --parse` locally against crafted trailer-like lines, e.g. lines with a space before the separator character, unusual separator characters, or characters between "Co-Authored-By" and the separator, and comparing against the output of `parseSingleUnfoldedTrailer`/`coAuthorRe` in [8](#0-7) ). This should be validated with a Devin session that can run `git interpret-trailers` directly before treating this as a fully confirmed, exploitable finding.

export function parseSingleUnfoldedTrailer(
  line: string,
  separators: string
): ITrailer | null {
  for (const separator of separators) {
    const ix = line.indexOf(separator)
    if (ix > 0) {
      return {
        token: line.substring(0, ix).trim(),
        value: line.substring(ix + 1).trim(),
      }
    }
  }

  return null
}

export async function parseTrailers(
  repository: Repository,
  commitMessage: string
): Promise<ReadonlyArray<ITrailer>> {
  const result = await git(
    ['interpret-trailers', '--parse'],
    repository.path,
    'parseTrailers',
    {
      stdin: commitMessage,
    }
  )

  const trailers = result.stdout

  if (trailers.length === 0) {
    return []
  }

  const separators = await getTrailerSeparatorCharacters(repository)
  return parseRawUnfoldedTrailers(result.stdout, separators)
}

export class GitAuthor {
  public static parse(nameAddr: string): GitAuthor | null {

  }

  public constructor(
