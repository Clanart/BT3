Based on my investigation, I found a concrete local analog to the CollectionShutdown pattern in the IntentGatewayV2 escrow-release logic.

### Title
`_withdraw()` finalizes an order and locks the `_filled` mapping without verifying all escrowed input tokens were drained, permanently stranding any un-swept escrow - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The bug-class in the source report is: a batch/array-driven "sale/settlement" operation is provided a caller-supplied list of items to process, the operation finalizes state as if it were exhaustive, but any eligible item not in that list is permanently orphaned because finalization blocks all future recovery paths. `IntentsBase::_withdraw()` reproduces this exact pattern for cross-chain intent orders: it sets `_filled[commitment]` (the sole gate that permits any future fill/refund/cancel) based on a `finalize` flag, while draining only the tokens present in the caller/message-supplied `body.tokens` array rather than deriving the drain set from the order's full escrowed token set.

### Finding Description
`_withdraw()` accepts a `WithdrawalRequest memory body` whose `tokens` array is constructed elsewhere (in `_fillCrossChain`/`onAccept` handling of `RedeemEscrow`/`RefundEscrow` messages) from `order.inputs` at commitment time [1](#0-0) . When `finalize` is true, it unconditionally sets `_filled[body.commitment] = beneficiary` before or independent of whether every token bucket held in `_orders[commitment][token]` was actually iterated and zeroed [2](#0-1) .

`_filled[commitment] != address(0)` is the single check that gates every subsequent path — `fillOrder`, `cancelOrder`, and the cross-chain `_cancelFromSource`/`_cancelFromDest` routes all revert with `Filled()` once this is set [3](#0-2) [4](#0-3) . There is no reconciliation step anywhere in `_withdraw()` that walks the full set of tokens that were actually escrowed for `commitment` (i.e., the original `order.inputs` array recorded at `placeOrder` time in `_orders[commitment][token]`, at line 338 of `IntentGatewayV2.sol`) and asserts each has been reduced to zero before flipping `_filled`. If the `body.tokens` array passed into `_withdraw` ever diverges from the full escrowed set — e.g., a token amount of `0` is skipped via `continue` at line 398, or a message body is constructed with an incomplete token list — the escrow balance in `_orders[commitment][token]` for the omitted token remains non-zero forever, because once `_filled` is non-zero, no code path in the gateway (`fillOrder`, `cancelOrder`, `_cancelSameChain`, `_cancelFromSource`, `_cancelFromDest`) can ever call `_withdraw` again for that commitment. This exactly mirrors `CollectionShutdown::execute()`: a caller-controlled/message-controlled array of "items to settle" that does not verify it covers everything currently locked/escrowed under that key, followed by an irreversible finalization flag.

This is structurally the same class of gap even though the specific triggering vector (constructing a mismatched `WithdrawalRequest.tokens` for a given `commitment`) is not fully provable from the EVM contract code alone; the cross-chain message body (`RedeemEscrow`/`RefundEscrow`) is decoded in `onAccept` and I was not able to fully trace every call site that builds `body.tokens` to confirm it is always kept byte-for-byte identical to the original `order.inputs` set recorded at `placeOrder`.

### Impact Explanation
If any escrowed token for an order is left un-drained when `_filled` is finalized, the user's or solver's tokens become permanently locked in the `IntentGatewayV2` contract with no function able to retrieve them — `_orders[commitment][token]` remains non-zero but unreachable because every entry point checks `_filled[commitment] != address(0)` first and reverts. This is a direct, irrecoverable loss of user/solver funds, matching the "loss/lock of funds" impact class in the bounty gate.

### Likelihood Explanation
This requires a real divergence between the escrowed-token set and the `WithdrawalRequest.tokens` array supplied to `_withdraw()` at finalize time. I could not conclusively demonstrate from the available EVM sources that this divergence is reachable by an unprivileged party through the public `fillOrder`/`onAccept` flow (the `order.inputs`/`options.outputs` length checks in `fillOrder` line 439-440 constrain the same-chain and simple cross-chain paths). The likelihood is therefore uncertain without a full trace of `_fillCrossChain` and the ISMP `onAccept` decode path for `RedeemEscrow`/`RefundEscrow` payloads, which was not fully covered by the indexed code.

### Recommendation
In `_withdraw()`, before setting `_filled[body.commitment]`, assert that the sum of tokens released in `body.tokens` accounts for the entire non-zero balance recorded for that commitment (e.g., iterate the original `order.inputs` token set, or track a per-commitment token registry, and require every entry to be zeroed) so that finalization can never occur while residual escrow remains.

### Proof of Concept
Not constructed — a working PoC would require tracing the exact construction of `WithdrawalRequest.tokens` inside `_fillCrossChain`/`onAccept` to prove a caller-reachable path produces a `body.tokens` array smaller than the full escrowed set for a commitment. This step could not be completed within the available context/index limits.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
