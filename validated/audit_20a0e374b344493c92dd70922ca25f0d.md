### Title
Discard-selection patch is applied against a stale, zero-context diff snapshot, allowing silent corruption of the working file - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The Mantra report's broken invariant is: an operation that transfers value to the user (`withdraw_liquidity`) is executed using state computed at a point in time earlier than execution, with no check that the outcome still matches what the user expects. The closest unprivileged analog in GitHub Desktop is the "discard selected changes" flow: the UI computes a patch from a `ITextDiff` snapshot taken when the Changes list was last refreshed, and later applies that patch via `git apply --unidiff-zero` with **zero lines of context**. Anything that changes the file on disk between the diff snapshot and the click of "Discard Changes" (an editor autosave, a build tool, a background format-on-save, a git hook, another process writing to the working tree) is not detected, and the destructive patch is applied blindly against the new content.

### Finding Description
`discardChangesFromSelection` in `app/src/lib/git/apply.ts` builds a reverse patch from a diff object and a line-selection captured earlier in the UI, then applies it directly: [1](#0-0) 

The patch itself is generated with `formatPatchToDiscardChanges`, which writes hunk headers using the **original hunk's line numbers** (`hunk.header.oldStartLine` / `hunk.header.newStartLine`) taken from the stale diff, not from a fresh read of the file: [2](#0-1) 

Critically, the apply arguments used are: [3](#0-2) 
`--unidiff-zero` means the hunks carry **no context lines**, so `git apply` has nothing to fuzzy-match against — it trusts the line offsets in the patch header verbatim. Compare with `applyPatchToIndex`, which uses the same flag when staging a partial commit: [4](#0-3) 

Because the diff/selection pair the UI holds is a snapshot, and there is no verification step (e.g., re-diffing the file or checking a content hash/mtime immediately before invoking `git apply`) that the working file is unchanged since the diff was captured, a file modified out-of-band between "select lines to discard" and "confirm discard" will have the reverse-patch hunks applied at the wrong offsets. With zero context, `git apply` either fails outright (best case) or — more dangerously — succeeds by inserting/removing lines at the position given by the stale line numbers, silently corrupting content the user did not intend to touch, with no rollback and (depending on `moveToTrash`) no way to recover the original file content, as seen in the broader `discardChanges` flow in `git-store.ts`: [5](#0-4) 

The confirmation dialog that gates this destructive action shows only the file path, never re-confirms the diff content, and offers no way to cap or validate the amount of change about to be discarded — the same missing "acceptable outcome" bound the C4 report flags for `withdraw_liquidity`: [6](#0-5) 

### Impact Explanation
This is a "silent corruption of what the user commits" scenario per the impact scope: a user who intends to discard a specific, reviewed set of lines can end up with unrelated lines in the file altered or deleted because the patch is positional and context-free, and was computed against content that is no longer current. Since Desktop treats a repository's working tree as attacker-influenceable (any tool, hook, or process that writes into the working directory between diff-read and discard-click), this satisfies the "attacker controls... a cloned/fetched repository" trigger condition when the corrupting write originates from repo tooling (e.g., a `post-checkout`/`post-merge` hook, a linter/formatter run automatically on save, or a file watcher triggered by a fetched/cloned repo's build config) that races with the user's discard action.

### Likelihood Explanation
Moderate-to-low but plausible: it requires a window between the diff snapshot displayed to the user and the discard confirmation during which the file's content changes without a full status refresh reconciling the stale diff object. Desktop does not appear to re-validate the diff/selection against current file content or hash before calling `git apply`, so the guard that would normally stop this (Desktop's own working-directory status polling) is not synchronously tied to the discard action.

### Recommendation
Before applying a discard/partial-commit patch, re-read the file (or at minimum verify a content hash/mtime captured with the diff) and abort with a user-facing error if it no longer matches the diff used to build the patch — analogous to Uniswap's `amountOutMin` check, this gives the user (or the app) a hard "expected vs. actual" guard instead of blindly trusting a stale positional patch. Alternatively, retain some diff context (avoid `--unidiff-zero` for discard operations) so `git apply` can reject/fuzzy-detect mismatches instead of applying at raw offsets.

### Proof of Concept
1. Open a file with local changes in Desktop's Changes view; note the diff/hunks rendered are the `ITextDiff` object held in component state.
2. Select a subset of lines and open "Discard Selection" (`discard-selection-dialog.tsx`), but do not yet confirm.
3. While the dialog is open, externally modify the same region of the file (e.g., an editor auto-format or a background script appends/removes lines near the same hunk), without Desktop's UI re-diffing (status refresh cycles are not synchronous with the dialog).
4. Click "Discard Changes." `discardChangesFromSelection` (`app/src/lib/git/apply.ts:102-120`) builds the patch from the now-stale `diff`/`selection` via `formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts:251-335`) and applies it with `git apply --unidiff-zero` against the *current* file.
5. Because the patch hunk headers reference the old line numbers and there is no context to validate against, the reverse-patch is applied at those offsets in the changed file, corrupting content outside of what the user selected to discard (or, at best, aborts with a patch-apply failure the user cannot easily diagnose).

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
