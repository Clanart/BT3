## Title
Automatic, unprompted fast-forwarding of *all* tracked local branches on every fetch silently rewrites branches other than the checked-out one, allowing a malicious/compromised remote to corrupt what a user later commits or pushes — (`File: app/src/lib/stores/app-store.ts`, `app/src/lib/git/fetch.ts`)

### Summary
Every time GitHub Desktop performs a fetch — including the fully automatic, unattended hourly background fetch — it calls `fastForwardBranches()`, which silently moves the ref of **every local branch that has an upstream configured** (except the currently checked-out one) to match whatever the remote reports, with no diff, no confirmation, and no user awareness. This is the exact same class of bug as the EigenPod report: a state-mutating operation that is effectively permissionless/unprompted and executes on attacker-influenceable input (here, the remote's ref advertisement) before the user has any chance to review or gate it.

### Finding Description
`performFetch()` unconditionally calls `this.fastForwardBranches(repository)` after every fetch: [1](#0-0) 

That private helper collects every local branch that differs from its upstream (excluding only the current branch) and fast-forwards them all: [2](#0-1) 

`getBranchesDifferingFromUpstream()` explicitly scopes to *all* `refs/heads` with a configured upstream, only excluding the checked-out branch: [3](#0-2) 

`fastForwardBranches()` in the git layer then executes `git fetch . --stdin` with the collected ref pairs, moving every one of those local refs to the corresponding remote-tracking ref in one shot, with no per-branch confirmation: [4](#0-3) 

Crucially, this same code path runs from the **fully automatic background fetcher**, which requires zero user interaction and runs roughly every hour for as long as the app/repo is open: [5](#0-4) [6](#0-5) 

The only safety property enforced is that the update must be a genuine fast-forward (`--show-forced-updates` is used to reject rewrites), but git does not verify authorship, provenance, or integrity of the *content* of a fast-forward — an attacker who controls the remote server (or a MITM/proxy sitting in front of it) can trivially author new commits whose parent is the client's currently-known tip, making any malicious payload "just" a fast-forward from the client's perspective.

### Impact Explanation
Because the update happens for every tracked branch — not just the one the user is actively working on — a user can be unaware that a branch they haven't looked at in days/weeks has been silently rewritten to point at attacker-supplied commits. If the user later:
- switches to that branch and builds on top of it, or
- merges/rebases it into another branch, or
- pushes it (fast-forward push requires no `--force`, so the corrupted content goes out silently),

then attacker-controlled commits are propagated as if they were the user's own work, satisfying the "silent corruption of what the user commits or pushes" impact category. There is no diff, banner, or confirmation shown anywhere in this path that would let the user notice the ref moved to unexpected content before it's baked into their next commit/push.

### Likelihood Explanation
The prerequisite is that the attacker controls (or can MITM/proxy) a git remote the victim's repository is configured to fetch from — this is exactly the "git remote/proxy response" attacker model allowed by this exercise. No local access, no leaked credentials, and no unusual user action are required: the vulnerable code runs automatically on the existing hourly background fetch (`BackgroundFetcher`) as well as on every manual fetch/pull, so the attacker only needs to wait for the routine timer.

### Recommendation
- Restrict automatic (background/unattended) fast-forwarding to the currently checked-out branch, or make it fully opt-in/configurable.
- For any non-active branch fast-forward performed silently, surface a visible notification/diff summary so the user can review what changed before building on or pushing that branch.
- Consider gating fast-forward of non-active branches behind the same "local changes would be overwritten"-style confirmation UX already used elsewhere in the app (see `localChangesOverwrittenHandler`) rather than performing it unconditionally in the background.

### Proof of Concept
1. Victim has a repository with `origin` remote and two local branches: `main` (checked out) and `feature` (not checked out), both tracking `origin`.
2. Attacker controls (or MITMs) the `origin` git server.
3. On the server, attacker crafts a new commit on `feature` whose parent is the SHA the victim's `feature` currently points to (trivially known since it's a normal git ref), embedding a backdoor (e.g. a modified build script or CI config).
4. Victim's Desktop app performs its routine hourly background fetch of `origin` (`BackgroundFetcher.performAndScheduleFetch` → `performFetch` → `fastForwardBranches`), which silently fast-forwards local `feature` to the attacker's commit — with no prompt, diff, or notification since `feature` isn't the checked-out branch.
5. Days later, the victim checks out `feature`, adds a commit, and pushes — propagating the attacker's backdoor commit into the shared/upstream history under the victim's push, without the victim ever having reviewed it.

export async function fastForwardBranches(
  repository: Repository,
  branches: ReadonlyArray<ITrackingBranch>
): Promise<void> {
  if (branches.length === 0) {
    return
  }

  const refPairs = branches.map(branch => `${branch.upstreamRef}:${branch.ref}`)

  await git(
    [
      'fetch',
      '.',
      // Make sure we don't try to update branches that can't be fast-forwarded
      // even if the user disabled this via the git config option
      // `fetch.showForcedUpdates`
      '--show-forced-updates',
      // Prevent `git fetch` from touching the `FETCH_HEAD`
      '--no-write-fetch-head',
      // Take branch refs from stdin to circumvent shell max line length
      // limitations (mainly on Windows)
      '--stdin',
    ],
    repository.path,
    'fastForwardBranches',
    {
      // Fetch exits with an exit code of 1 if one or more refs failed to update
      // which is what we expect will happen
      successExitCodes: new Set([0, 1]),
      env: {
        // This will make sure the reflog entries are correct after
        // fast-forwarding the branches.
        GIT_REFLOG_ACTION: 'pull',
      },
      stdin: refPairs.join('\n'),
    }
  )
}
