### Title
TextFormat parser logs attacker-controlled field values in cleartext by default - (File: `src/google/protobuf/text_format.cc`)

### Summary
When `TextFormat::Parser` (and the equivalent Java/Python/C++ text-format parsers) encounters an unknown field, an invalid enum value, or a malformed token, it embeds the raw, attacker-supplied text directly into the error/warning message. If the caller has not registered an `io::ErrorCollector` (which is the documented default), this message is unconditionally written through `ABSL_LOG(ERROR)`/`ABSL_LOG_EVERY_POW_2(WARNING)`, i.e. into the process's ordinary logging pipeline rather than being confined to an in-memory collector the caller controls. Any secret or sensitive value that a client places in that "invalid" or "unknown" field is echoed verbatim into the application's logs.

### Finding Description
`TextFormat::Parser::ReportError`/`ReportWarning` delegate to the free function `ReportErrorImpl` in `src/google/protobuf/text_format.cc`: [1](#0-0) 

When `error_collector_` is `nullptr` — the documented default ("Set to NULL (the default) to discard error messages" / "errors will be printed to stderr") — the message text is written via `ABSL_LOG(ERROR)`: [2](#0-1) 

Several call sites build that message by directly concatenating attacker-controlled token/value text, not just structural metadata (field names/positions):

- Unknown enum textual/numeric value is embedded verbatim: `absl::StrCat("Unknown enumeration value of \"", value, "\" for field \"", field->name(), "\".")` [3](#0-2) 
- Raw unparsed token text is embedded when a field value can't be classified: `absl::StrCat("Cannot skip field value, unexpected token: ", text)` and `absl::StrCat("Invalid float number: ", text)` [4](#0-3) 

The same pattern is reproduced independently in the Java and Python bindings, confirming it is a systemic behavior of the TextFormat implementation rather than one C++-specific bug:
- Java: `throw tokenizer.parseException("Invalid field value: " + tokenizer.currentToken);` [5](#0-4) 
- Python: `raise ParseError('Invalid field value: ' + tokenizer.token)` [6](#0-5) 

The upstream unit tests explicitly document and lock in the "print errors to stderr via glog/absl log" default behavior: [7](#0-6) . Nothing sanitizes, truncates, or redacts the token/value text before it is placed in the log line — the only "safety" mechanism (registering a custom `ErrorCollector`) is opt-in and off by default.

### Impact Explanation
An application that accepts TextFormat-serialized protobuf input from a client (e.g., a debug/import endpoint, a config-reload RPC, or any code path that calls `TextFormat::ParseFromString`/`MergeFromString` without configuring `RecordErrorsTo`) will have any string an attacker places in a malformed/unknown field or an invalid enum value written into the process log at ERROR/WARNING severity. If a client submits a request containing sensitive data (tokens, credentials, PII copied from a legitimate field into a bogus one, or simply mistyped identifiers that happen to contain secrets) inside a field the parser rejects, that data is persisted into log files/log aggregation systems that may have broader read access than the original request — the same class of exposure described in the NeuVector CVE-2025-46808 report (CWE-532, sensitive data inserted into logs by default without an opt-out).

### Likelihood Explanation
Reaching this code path only requires supplying a syntactically-parseable-but-schema-invalid TextFormat payload (an unrecognized field name, an out-of-range/invalid enum literal, or a malformed value token) to any caller of the public `TextFormat::Parse*`/`MergeFrom*` APIs that has not installed an `ErrorCollector` — which is the out-of-the-box default for every language binding. No special privileges are required; a normal client triggering a parse error is sufficient. Because logging is enabled by default and there is no size/length cap or redaction on the embedded token, likelihood of triggering is high for any TextFormat-accepting endpoint.

### Recommendation
- Do not interpolate raw, unbounded attacker-controlled token/value text into `ABSL_LOG`/logger messages by default; log only structural identifiers (field number/name, line/column) unless a caller explicitly opts in to verbose diagnostics.
- Truncate/redact the offending token before inclusion, or require callers to explicitly opt in via a flag (rather than opting out via `ErrorCollector`) before raw content is logged.
- Apply the same fix consistently to the Java (`TextFormat.java`), Python (`text_format.py`), and any other language-binding parsers, since each reimplements the same verbatim-echo behavior.
- Update documentation to make clear that default TextFormat parse-error behavior writes to the process log (via absl logging, which may be captured to persistent files), not merely "stderr," so consuming applications are aware of the exposure and can register an `ErrorCollector` when parsing untrusted input.

### Proof of Concept
1. Using an application that calls `TextFormat::ParseFromString(input, &message)` (default parser, no `RecordErrorsTo` configured) on client-supplied TextFormat data.
2. Send input such as: `secret_lookalike_field: "SUPER-SECRET-TOKEN-VALUE"` where `secret_lookalike_field` is not a valid field on the target message, or `status: "SUPER-SECRET-TOKEN-VALUE"` where `status` is an enum field and the literal is not a defined enum value.
3. Parsing fails as expected, but `ReportErrorImpl` (`src/google/protobuf/text_format.cc:342-357`) executes `ABSL_LOG(ERROR) << "Error parsing text-format " ... << message`, where `message` contains `Unknown enumeration value of "SUPER-SECRET-TOKEN-VALUE" for field "status".` — reproducing exactly the pattern validated by the existing test `TextFormatParserTest.PrintErrorsToStderr` (`src/google/protobuf/text_format_unittest.cc:2712-2726`), confirming the attacker-supplied string is written to the process's log stream by default.

void ReportErrorImpl(int line, int col, absl::string_view message,
                     const Descriptor* root_message_type,
                     io::ErrorCollector* error_collector) {
  if (error_collector == nullptr) {
    if (line >= 0) {
      ABSL_LOG(ERROR) << "Error parsing text-format "
                      << root_message_type->full_name() << ": " << (line + 1)
                      << ":" << (col + 1) << ": " << message;
    } else {
      ABSL_LOG(ERROR) << "Error parsing text-format "
                      << root_message_type->full_name() << ": " << message;
    }
  } else {
    error_collector->RecordError(line, col, message);
  }
}
