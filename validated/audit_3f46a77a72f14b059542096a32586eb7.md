## Analysis

The externally reported bug's core pattern is: **a semi-trusted external call return value is used, unverified, to drive a security-critical decision**, letting the attacker who controls that external response corrupt protocol state. Searching the Desktop codebase for the same *class* of bug (trusting attacker-controlled data coming back from a git/remote interaction to make a security decision) surfaces a real analog in the credential-helper trampoline.

### Title
Malicious git remote can force Desktop into a GitHub/Enterprise sign-in flow scoped to an attacker-controlled host via a spoofed `WWW-Authenticate` header - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git performs an HTTPS operation (clone/fetch/push) against a remote, Git forwards any `WWW-Authenticate` response header it receives from that remote to Desktop's credential helper as `wwwauth[N]` fields. `getEndpointKind()` trusts the *content* of that header — fully controlled by the remote server — to decide whether the host being talked to should be treated as a GitHub Enterprise host, without any independent verification (e.g. an actual API probe) in that branch.

### Finding Description
In `getEndpointKind`, before falling back to `isGitHubHost()` (an actual network check), the code takes a shortcut: [1](#0-0) 

This is described in the code itself as trusting the header "as a happy-path... without having to resort to making a request ourselves." The header value comes verbatim from the HTTP response of the git remote — i.e., from an attacker who controls the remote/proxy the user is cloning from or fetching/pushing to.

If `getEndpointKind` returns `'enterprise'` (attacker sends `WWW-Authenticate: Basic realm="GitHub"`), `getCredential` — finding no existing account bound to that host — invokes: [2](#0-1) 

`promptForGitHubSignIn(endpoint)` then takes the `endpoint` value (which is the attacker's own remote URL, `getCredentialUrl(cred)`) and uses its `origin` to drive a full Enterprise sign-in flow: [3](#0-2) 

`dispatcher.setSignInEndpoint(origin)` ultimately calls `SignInStore._setEndpoint`, whose validation only checks URL syntax and protocol, not that the host is an actual, verified GitHub Enterprise instance: [4](#0-3) 

The net effect: a purely attacker-controlled HTTP response header (something any malicious/compromised git server or MITM proxy can send back during a routine `git fetch`/`clone`/`push`) causes Desktop to autonomously pop a "Sign in to GitHub" dialog whose target endpoint is the attacker's own host — with the user having taken no action beyond a normal repository operation. If the user (believing this is a legitimate GitHub Enterprise prompt triggered by Desktop) enters credentials or completes basic-auth style sign-in, those credentials/PAT are sent to the attacker-controlled `origin`, not to any real GitHub service.

This mirrors the report's broken invariant exactly: a return value from an untrusted external actor (there: swap return; here: HTTP `WWW-Authenticate` header) is trusted to gate a high-value action (there: slippage bypass to steal funds; here: sign-in-flow redirection to steal credentials) instead of being independently verified.

### Impact Explanation
A malicious or compromised git host (or a MITM/proxy sitting between the user and a legitimate host, e.g., over a corporate proxy or compromised network) can trigger Desktop to open an OAuth/Enterprise sign-in dialog whose destination endpoint is fully attacker-chosen. Users who complete sign-in believing it's a legitimate re-authentication prompt would leak GitHub credentials or personal access tokens to the attacker's server. This is a credential-exfiltration / unauthorized-account-binding primitive triggered purely by cloning or interacting with a hostile remote — satisfying the "attacker controls...a git remote/proxy response...credential/token exfiltration, unauthorized OAuth" criterion.

### Likelihood Explanation
Any public git server the victim is willing to clone/fetch from (a common, low-friction action in Desktop) can serve this header on an HTTP 401/`WWW-Authenticate` response during the credential-negotiation phase of a git HTTPS operation. No admin rights, local access, or prior compromise is needed — only that the user perform a normal clone/fetch/push against an attacker-controlled or attacker-intercepted remote.

### Recommendation
Do not use the `wwwauth[N]` `realm="GitHub"` heuristic to short-circuit into the "enterprise" credential path (which triggers a scoped sign-in-flow) without also verifying the host via `isGitHubHost()` (an authenticated API probe) as is already done in the non-heuristic fallback path. At minimum, the sign-in dialog triggered via `promptForGitHubSignIn` should clearly and unambiguously surface that the account/endpoint being signed into originates from an unverified remote-supplied value, and any credential entry flow reachable this way should be re-validated against the real endpoint before being trusted/stored.

### Proof of Concept
1. Attacker stands up a git-over-HTTPS server (or a MITM proxy) that the victim will clone/fetch from, e.g. `https://evil.example.com/foo.git`.
2. On an unauthenticated request, the server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim runs `git clone https://evil.example.com/foo.git` (or fetch/push) through Desktop.
4. Git forwards the header to Desktop's credential helper via the trampoline (`command.stdin` containing `wwwauth[0]=Basic realm="GitHub"`).
5. `getEndpointKind` returns `'enterprise'` for `evil.example.com` — see [1](#0-0) .
6. `getCredential` finds no existing account bound to `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com')` — see [5](#0-4) .
7. `promptForGitHubSignIn` starts an Enterprise sign-in flow scoped to `https://evil.example.com` — see [6](#0-5) .
8. If the victim completes the sign-in dialog (basic auth or OAuth-style flow) believing this is a genuine GitHub prompt, the entered credentials/tokens are sent directly to the attacker's server.

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
