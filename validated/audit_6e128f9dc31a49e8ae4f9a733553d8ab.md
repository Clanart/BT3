### Title
OP_RETURN data is excluded from Bitcoin fee and weight accounting - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` appends caller-supplied `data` as an `OP_RETURN` output, but calculates the transaction’s vsize, required fee, and maximum-weight status using only `payments` and optional `change`. An 80-byte data payload can therefore add roughly 90 serialized bytes without increasing `needed_fee`, causing the signed transaction to have a lower feerate than requested and potentially fall below Bitcoin’s minimum relay feerate. [1](#0-0) 

### Finding Description
The constructor builds `tx_outs` from the payments and then appends a zero-valued `OP_RETURN` output when `data` is supplied. [2](#0-1) 

However, `calculate_weight_vbytes` receives only `tx_ins.len()`, `payments`, and `None`; the already-created `tx_outs` and `data` output are not represented in the weight calculation. [3](#0-2) 

The helper reconstructs a transaction containing only payment outputs and an optional change output, so its returned weight and vbytes omit the `OP_RETURN` output entirely. [4](#0-3) 

`needed_fee` and the minimum-relay-fee check are based on that underestimated vsize. [5](#0-4) 

When change is present, the code recalculates size using `payments` and the change script, again omitting `data`; the change amount is then set to consume everything except this underestimated fee. [6](#0-5) 

Finally, the transaction actually committed for signing contains `tx_outs`, including the unaccounted `OP_RETURN` output. [7](#0-6) 

### Impact Explanation
A caller can supply up to 80 bytes of transaction data, which is enough to add a complete `OP_RETURN` output while fee accounting remains based on the smaller transaction without that output. [8](#0-7) 

With a change output, the extra output size does not become part of the fee; instead, change consumes all remaining value after the incorrectly small fee. The resulting signed transaction therefore pays less than `fee_per_vbyte` for its actual vsize. [6](#0-5) 

At a boundary feerate, the underestimated size can make `fee_per_vbyte` pass the constructor’s minimum-relay check while the actual transaction’s feerate is below the relay minimum. This can cause the fully signed spend to be rejected or remain unconfirmed, delaying use of the selected inputs. [5](#0-4) 

The same omission also affects the maximum-standard-weight check because `weight` is copied from a transaction that lacks the data output. [9](#0-8) 

### Likelihood Explanation
The only attacker-controlled prerequisite is causing a transaction to be created with nonempty `data`, which is a public constructor argument and explicitly documented as producing an `OP_RETURN` output. [10](#0-9) 

The discrepancy is deterministic rather than probabilistic: any nonempty `data` output is excluded from both the no-change and with-change size calculations. [1](#0-0) [11](#0-10) 

The strongest exploit requires a change output so the input remainder cannot accidentally compensate for the omitted fee. That is a normal supported transaction configuration. [6](#0-5) 

### Recommendation
Calculate weight and vbytes over the same output set that will be signed, including the `OP_RETURN` output. A robust structure would:

1. Build the payment and data outputs first.
2. Calculate the no-change fee using those outputs.
3. If change is possible, calculate a second fee using those outputs plus a placeholder change output.
4. Apply the minimum-relay and maximum-weight checks to the final transaction shape.
5. Optionally assert before returning that `fee() >= fee_per_vbyte * actual_vsize` once the final transaction exists.

The change calculation should keep the change amount variable while including the change output’s script size, as it does now, but must also include the data output. [12](#0-11) 

### Proof of Concept
1. Create a valid `ReceivedOutput`.
2. Call `SignableTransaction::new` with:
   - that output as the sole input;
   - one ordinary payment above `DUST`;
   - `Some(change_script)`;
   - `Some(vec![0; 80])`;
   - `fee_per_vbyte` equal to the minimum effective rate.
3. Select the input amount as `payment + estimated_fee_with_change + DUST`, forcing creation of a dust-valued change output.
4. The constructor accepts because its minimum-fee check uses vbytes calculated without the 80-byte `OP_RETURN` output. [13](#0-12) 
5. The returned transaction nevertheless contains payments, the `OP_RETURN` output, and change. [7](#0-6) 
6. The change amount is `input - payment - underestimated_fee`, so the actual fee remains the underestimated value while the real transaction is larger. Its actual feerate is therefore below the requested/minimum rate. [6](#0-5) 
7. Signing commits to this complete transaction via Taproot sighashes and completion places signatures in every input witness, producing a validly signed but underpriced transaction. [14](#0-13) [15](#0-14)

    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
