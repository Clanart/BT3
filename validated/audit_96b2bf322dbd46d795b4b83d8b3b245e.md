### Title
Coinbase outputs are reported as spendable before maturity - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching outputs as `ReceivedOutput`s. `ReceivedOutput` is defined as “a spendable output” and carries no maturity/spendability flag, so a coinbase output paying a tracked Taproot script is reported exactly like an immediately spendable UTXO even though Bitcoin consensus prevents spending it for 100 blocks.

### Finding Description
The vulnerable path is:

1. An attacker controls or obtains a Bitcoin block’s coinbase transaction.
2. The attacker creates a coinbase output whose `script_pubkey` equals a script tracked by `Scanner`.
3. `Scanner::scan_block` iterates over all `block.txdata`, including `block.txdata[0]`, and calls `scan_transaction` on each transaction.
4. `scan_transaction` matches only `output.script_pubkey` against `self.scripts` and constructs a `ReceivedOutput`.
5. The returned object can be passed to `SignableTransaction::new`, which uses the supplied `outpoint` and `TxOut` as inputs without checking coinbase maturity.

`Scanner::scan_block` explicitly includes the coinbase transaction at `networks/bitcoin/src/wallet/mod.rs:216-227`, while `scan_transaction` converts matching outputs directly into `ReceivedOutput` at `networks/bitcoin/src/wallet/mod.rs:198-213`. `ReceivedOutput` is documented as “A spendable output” at `networks/bitcoin/src/wallet/mod.rs:88-97`, but coinbase outputs are not spendable until maturity.

### Impact Explanation
This is analogous to counting trapped collateral as available collateral: the scanner reports value that cannot actually be spent yet. A caller treating `scan_block` results as available UTXOs can overstate immediately spendable funds and construct/sign transactions that consensus will reject.

The issue is bounded by Bitcoin’s 100-block coinbase maturity and does not permanently lock the funds. It can nevertheless cause incorrect accounting, failed withdrawals, delayed execution, or repeated construction of invalid transactions.

### Likelihood Explanation
A miner, mining pool, or party able to influence coinbase payouts can direct a coinbase output to a tracked Serai/Bitcoin address. A normal transaction sender cannot create a coinbase, so exploitation requires block-production influence rather than arbitrary transaction submission alone.

### Recommendation
Do not return coinbase outputs from `Scanner::scan_block` as ordinary `ReceivedOutput`s. Skip `block.txdata[0]`, or extend the returned type/API to carry confirmation/maturity state and prevent `SignableTransaction::new` from accepting immature coinbase outputs. If delayed availability is required, expose a separate immature-output result rather than representing it as “a spendable output.”

### Proof of Concept
```rust
// Conceptual PoC for networks/bitcoin/src/wallet/mod.rs

let scanner = Scanner::new(tracked_key).unwrap();
let tracked_script = p2tr_script_buf(tracked_key).unwrap();

let coinbase = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![TxIn {
    previous_output: OutPoint::null(),
    script_sig: coinbase_script,
    sequence: Sequence::MAX,
    witness: Witness::default(),
  }],
  output: vec![TxOut {
    value: Amount::from_sat(50_000_000_000),
    script_pubkey: tracked_script,
  }],
  ..Default::default()
};

let block = Block {
  header,
  txdata: vec![coinbase],
};

let outputs = scanner.scan_block(&block);
assert_eq!(outputs.len(), 1);

// The output is returned as spendable even though Bitcoin consensus
// prevents spending this coinbase outpoint for 100 blocks.
let spend = SignableTransaction::new(
  outputs,
  &payments,
  change,
  None,
  fee_per_vbyte,
);
```
