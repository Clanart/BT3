## Title
Unauthenticated operator attribution in payout transaction OP_RETURN enables payout-hijacking / mis-attributed reimbursement - (`core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The payout transaction that fronts a Citrea withdrawal embeds the fronting operator's x-only pubkey in a plain (unsigned-by-the-user) `OP_RETURN` output, while the user's authorization only covers the withdrawal input and the user's own payout output via `SinglePlusAnyoneCanPay` sighash. This is the same bug class as Illuminate's M-11: a value that is trusted later for a custody decision (which party is credited/reimbursed) is not actually bound to the value that was really moved/paid, so an unprivileged party can rewrite the "who paid" attribution.

### Finding Description
`create_payout_txhandler` builds the payout tx with three outputs: the user's payout, an anchor, and an `OP_RETURN` carrying the fronting operator's x-only pubkey: [1](#0-0) 

The only witness placed on the transaction is the **user's** signature on input 0 (the withdrawal UTXO), and per the protobuf docs this is a `SinglePlusAnyoneCanPay` (`SIGHASH_SINGLE|ANYONECANPAY`) signature: [2](#0-1) 

By BIP341 semantics, `SIGHASH_SINGLE|ANYONECANPAY` commits **only** to input[0] and the output at the *same index* (output[0], the user payout). It does **not** commit to output[1] (anchor) or output[2] (`OP_RETURN` operator pubkey). The operator's own signature only appears on the *additional funding inputs* it adds via `fund_raw_transaction`, and it is that signer (whoever funds/signs those inputs) who fully controls the final `OP_RETURN` content: [3](#0-2) [4](#0-3) 

Downstream, the verifier's block scanner blindly trusts whatever x-only pubkey is found in the payout tx's `OP_RETURN` as "the payer operator," with no check that this party is the one who actually supplied the payout value: [5](#0-4) 

That attribution is what later gates reimbursement eligibility: an operator can send asserts/kickoff for a deposit only if the DB's recorded `payout_op_xonly_pk` equals its own kickoff `operator_xonly_pk` — a check that is satisfied purely by string/key equality, independent of who actually funded the payout tx: [6](#0-5) 

The same unauthenticated value is later fed into the bridge circuit as part of the `deposit_constant` that is proven in the BitVM/ZK path, so the false attribution propagates all the way into the reimbursement-eligibility proof: [7](#0-6) 

**Binding broken:** `operator_credited_from_OP_RETURN == operator_who_actually_funded_the_payout` — this equality is assumed everywhere downstream (`update_finalized_payouts`, `send_asserts`, `deposit_constant`) but is never enforced at the point the payout tx is finalized, because the field that encodes it is not covered by the only signature (the user's) that is checked when the tx is accepted.

### Impact Explanation
Because `SinglePlusAnyoneCanPay` leaves outputs[1..] fully malleable to whoever finishes funding/broadcasting the transaction, any unprivileged party who observes an honest operator's broadcasted-but-unconfirmed payout tx in the mempool can:
1. Extract the user's witness for input 0 (valid for the withdrawal UTXO and the user's payout output only).
2. Construct a competing transaction reusing that input/witness and output[0], but substituting arbitrary content in the anchor and, critically, the `OP_RETURN` (e.g., a different operator's x-only pubkey), while funding the transaction from their own wallet.
3. Get this competing transaction confirmed instead (via fee bump/RBF race), which the network accepts as a valid double-spend replacement of the honest operator's version.

Consequences:
- The honest operator who actually intended to front the withdrawal never gets it confirmed under its own pubkey and can become permanently unable to claim reimbursement for that withdrawal (its `handle_finalized_payout`/`validate_payer_is_operator` path will fail because the recorded payer no longer matches it).
- A different (potentially colluding or simply attacker-chosen) operator's x-only pubkey ends up recorded as `payout_payer_operator_xonly_pk`, and that operator becomes eligible to claim the `Reimburse` transaction against the deposit's `move_to_vault` UTXO, even though it never funded the payout — i.e., "an operator reimbursed for a payout it never funded."
- Alternatively, the attacker can wipe/garble the `OP_RETURN` so `operator_xonly_pk` parses to `None`, which the code interprets as "optimistic payout," causing the payout-checker task to silently skip normal reimbursement processing for a payout that was actually fronted by a specific operator, permanently freezing that operator out of reimbursement.

This satisfies the required Critical impact categories: an operator reimbursed for a payout it never funded, or an honest operator permanently unable to be reimbursed.

### Likelihood Explanation
No privileged role, key, or off-chain trust is required — only the ability to observe the Bitcoin P2P mempool (any full node) and to fund a competing transaction with higher fee/priority than the honest operator's broadcast. The withdrawal UTXO/output amount/script are fixed by the user's signature, so the attacker doesn't even need to know anything more than what any mempool-watching node already sees once the honest operator broadcasts. This is a standard SIGHASH_SINGLE|ANYONECANPAY malleability pattern, well understood and practically exploitable by any network participant with basic fee-bumping capability.

### Recommendation
Bind the operator attribution to something the user's signature (or another cryptographically enforced mechanism) actually commits to, e.g.:
- Require the user to sign with `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY`) so all outputs, including the `OP_RETURN`, are committed and cannot be altered post-broadcast, or
- Have the aggregator/verifier pre-commit (and separately verify) the intended operator pubkey for a given withdrawal before accepting the payout tx as valid for a specific operator, instead of trusting whatever pubkey ends up on-chain in the `OP_RETURN` at confirmation time, or
- Require the funding inputs' signer to independently attest (e.g., via a nonce or additional covenant) that it is the same party embedded in the `OP_RETURN`, preventing a third party from funding the tx with someone else's identity in the output.

### Proof of Concept
1. Operator A calls `withdraw`/`internal_withdraw` (`core/src/operator.rs:560-674`), builds the payout tx via `create_payout_txhandler` with `OP_RETURN` = A's xonly pubkey, funds it with its own wallet inputs (SIGHASH_ALL on those inputs), and broadcasts it.
2. An unprivileged watcher extracts the witness for input 0 (the withdrawal UTXO) from the mempool transaction; per `SinglePlusAnyoneCanPay`, this witness is valid for any transaction reusing input 0 and output 0 unchanged.
3. The watcher builds tx' with the same input 0 + output 0 (user payout unchanged, so the user's signature check in `withdraw` at `core/src/operator.rs:630-637` would have accepted it) but a different anchor output and `OP_RETURN` (e.g., operator B's xonly pubkey), funding it from its own wallet.
4. Watcher broadcasts tx' with a higher fee; it confirms instead of Operator A's tx, double-spending the withdrawal UTXO.
5. `update_finalized_payouts` (`core/src/verifier.rs:2298-2350`) scans the confirmed block, parses the `OP_RETURN` of tx', and records `payout_payer_operator_xonly_pk = B` — even though B never funded anything.
6. Operator B (or nobody, if pubkey is garbage) is now the party whose `handle_finalized_payout`/`send_asserts` path (`core/src/operator.rs:839-885`, `1275-1295`) is unblocked to claim the `Reimburse` transaction against the deposit's vault UTXO, while Operator A — who actually tried to front the withdrawal — is permanently excluded from reimbursement for that deposit.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
