### Title
Attacker can deposit uneconomical dust outputs to the vault, forcing the shared UTXO pool to burn more in spend fees than the deposited value - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report describes a rebate-pool donation attack: an unprivileged party injects cheap "contribution" units into a shared pool such that the distribution formula pays out more (or retains less for the protocol) than the real economic value added. The analog in Serai is the Bitcoin scanner/transaction-builder path: `Scanner::scan_transaction` accepts every output paying to a registered `script_pubkey` with no minimum-value check, and `SignableTransaction::new` treats every `ReceivedOutput` as a worthwhile input, charging per-input weight to the shared pool's fee budget. An attacker can therefore "donate" dust outputs whose spend cost exceeds their face value, draining the vault's aggregate funds to miners while the deposit is still credited at full value.

### Finding Description
`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) iterates all transaction outputs and emits a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script. There is no value threshold — a 546-sat (or even 1-sat, nonstandard aside) output is reported identically to a large deposit.

```rust
// networks/bitcoin/src/wallet/mod.rs
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout) });
}
```

On the spend side, `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) enforces the `DUST` (546 sat) minimum only on `payments` and `change` (lines 165-169, 228-234). Inputs are never checked for economic viability: every supplied `ReceivedOutput` is turned into a `TxIn` (lines 177-185) and adds ~57 vbytes (`230 wu / 4`, per the comment in `processor/src/networks/bitcoin.rs:606-636`) to `needed_fee = fee_per_vbyte * vbytes` (line 206). The actual fee paid is `sum(inputs) - sum(outputs)` (`fee()`, lines 138-141), so the marginal cost of each input is borne by the pool's aggregate balance, not by the depositor.

The crate's own commentary acknowledges the real cost model: Bitcoin requires "each output's value [to] exceed the fee of the TX spending it at 3000 sat/kilo-vbyte", and Serai sets a 10,000-sat internal `DUST` precisely so outputs are "actually worth our time" (`processor/src/networks/bitcoin.rs:622-636`). Yet `scan_transaction` registers outputs below that threshold (anything ≥ 546 sats that relays), and nothing in `ReceivedOutput::read` / `SignableTransaction::new` filters them out. Since every input must be signed with a per-input FROST offset and included in an aggregation/spend transaction, each sub-threshold output consumes more satoshis in fee than it contributes.

### Impact Explanation
An unprivileged party sends N small outputs to a Serai vault/branch address. Each is scanned as a valid `ReceivedOutput` and later swept. At a fee rate of `f` sats/vbyte, each input costs ~`57·f` sats to spend; for `f ≥ 10` that exceeds the 546-sat minimum relayable output. The vault's net balance decreases by `57·f − v` per dust input — value that exits the shared pool to miners. If the deposit is credited toward the attacker (minted sriBTC / a `Shorthand::transfer` instruction), the attacker converts `v` sats on-chain into `v` sats of credited balance while the protocol additionally eats the spend cost — a direct net-positive donation-for-drain analog of the Cobb-Douglas query-fee spoof: the attacker inflates their "contribution" count and the protocol-retained share of the pool shrinks (`remaining` decreases, per the report's formula). Repeated at scale this is a persistent bleed of vault funds.

### Likelihood Explanation
Fully unprivileged: sending Bitcoin transactions to a known P2TR script requires no role, stake, or threshold participation. `Scanner` matches on `script_pubkey` alone, so any output to the vault address (or a registered offset/branch script) qualifies. The only prerequisites are that fee rates are high enough that `input_cost > output_value` — the common case for outputs in the 546–several-thousand sat range — and that the wallet sweeps all scanned UTXOs, which the scheduler does by design (it "always want[s] to aggregate our UTXOs into a single UTXO"). Cost to the attacker is bounded (their own spend tx fee plus the dust values); profit/drain per input is small but repeatable and scales with mempool fee volatility.

### Recommendation
Enforce a minimum economic value at intake and at spend time:

- In `Scanner::scan_transaction` (or the layer consuming `ReceivedOutput`s), ignore outputs below a `MIN_INPUT_VALUE` computed from a conservative fee rate (e.g., the `10_000`-sat `DUST` rationale already documented for spendability), so unprofitable outputs are never treated as spendable funds.
- In `SignableTransaction::new`, skip or reject inputs whose `output.value` is below `fee_per_vbyte * INPUT_VBYTES` (~`57 * fee_per_vbyte`), so a dust output can never be bundled into a fee-paying transaction.
- If such outputs must eventually be recovered, only spend them when the prevailing fee rate makes them net-positive, rather than aggregating unconditionally.
