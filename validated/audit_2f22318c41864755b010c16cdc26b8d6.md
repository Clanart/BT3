### Title
`internal_withdraw` RPC bypasses the aggregator-authentication check enforced by `withdraw` - (File: `core/src/rpc/operator.rs`)

### Summary
The operator's gRPC service exposes two distinct methods that trigger the exact same privileged action — building, signing and broadcasting a payout transaction via `Operator::withdraw`: `withdraw` and `internal_withdraw`. Only `withdraw` performs the ECDSA verification-signature check that confirms the request actually originated from the aggregator; `internal_withdraw` calls into the identical state-changing/broadcasting logic without any such check, so the authorization boundary the protocol relies on ("the caller reaching a state-changing method versus the party it is meant for") is not uniformly enforced across the two entry points.

### Finding Description
`ClementineOperator::withdraw` parses `WithdrawParamsWithSig`, and—when `self.operator.config.aggregator_verification_address` is configured—requires a `verification_signature` recovered via `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` to match that configured address before calling `self.operator.withdraw(...)`: [1](#0-0) 

`ClementineOperator::internal_withdraw`, however, parses the same kind of withdrawal parameters (`WithdrawParams`, without any signature wrapper) and calls straight into `self.operator.withdraw(...)` with no verification-address/verification-signature gate at all: [2](#0-1) 

Both paths converge on `Operator::withdraw`, which checks the Citrea withdrawal state, profitability, and builds/broadcasts the payout transaction: [3](#0-2) 

Because `internal_withdraw` is a separate RPC on the same `ClementineOperator` gRPC service (defined alongside `withdraw` in the proto and generated client/server code), any client that can reach the operator's gRPC endpoint can invoke it directly and skip the authentication step that `withdraw` enforces — even in deployments where `aggregator_verification_address` is configured specifically to restrict who may trigger a payout. [4](#0-3) 

### Impact Explanation
This breaks the intended binding: *the party authorized to trigger a payout broadcast (the aggregator, verified via ECDSA signature) = the caller who actually invokes the state-changing/broadcasting RPC*. Via `internal_withdraw`, an unauthenticated/unauthorized caller can reach the same state-changing and transaction-broadcasting code path (`Operator::withdraw`) that is otherwise gated behind aggregator verification in `withdraw`. This matches the High-severity class of "an unauthenticated state-changing or broadcasting call."

### Likelihood Explanation
Any actor with network access to the operator's gRPC port and knowledge of a valid Citrea withdrawal index/outpoint/signature (which is inherently public/user-supplied information carried in the withdrawal flow) can call `internal_withdraw` directly, since it requires no operator-role credential beyond gRPC reachability.

### Recommendation
Apply the same `aggregator_verification_address` / `verification_signature` check that `withdraw` performs to `internal_withdraw` (or remove `internal_withdraw` as a public RPC and restrict it to trusted/local callers only), so both entry points into `Operator::withdraw` enforce identical authorization.

### Proof of Concept
1. Deploy an operator with `aggregator_verification_address` configured (intending only the aggregator to trigger payouts).
2. As an arbitrary client with the required withdrawal parameters (`withdrawal_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`), call the operator's `internal_withdraw` RPC directly instead of `withdraw`.
3. Observe that `internal_withdraw` (`core/src/rpc/operator.rs:168-190`) performs no verification-signature check and proceeds straight to `self.operator.withdraw(...)`, producing and broadcasting a signed payout transaction — bypassing the authorization gate present in `withdraw` (`core/src/rpc/operator.rs:209-239`).
