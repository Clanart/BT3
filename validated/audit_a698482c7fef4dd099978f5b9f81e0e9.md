Based on my research, I found a concrete, code-supported analog. The invariant that's broken in `MarinateV2.migrateToken()` is "an entity outside the trust boundary can trigger a privileged fund-moving operation without validation." The GitHub Desktop analog is: **an entity outside the trust boundary (a GitHub API object returned for a pull request) can inject data into a raw `git remote add` invocation that lacks the `--` end-of-options separator, allowing option/argument injection instead of a validated URL.**

### Title
Missing `--` end-of-options guard in `addRemote()` allows git argument injection via attacker-influenced pull-request `clone_url` - (File: `app/src/lib/git/remote.ts`)

### Summary
`addRemote()` builds the git command as `['remote', 'add', name, url]` with no `--` separator before the positional arguments. [1](#0-0) 
This function is called with `headCloneUrl`, a string taken directly from a `PullRequest`/GitHub API object (`pullRequest.head.repo.clone_url` or `pullRequest.head.gitHubRepository.cloneURL`), inside `_findPullRequestBranch` in `app-store.ts`. [2](#0-1)  The reachable entry points into this code path include the `x-github-client://openRepo/...?pr=NNN` deep link handler, which resolves a PR via `appStore.fetchPullRequest(url, pr)` and feeds the resulting `head.repo.clone_url` straight into `_checkoutPullRequest`. [3](#0-2) 

### Finding Description
`git remote add <name> <url>` is invoked without a `--` before the positional arguments in `addRemote`: [1](#0-0) 
Compare this to `clone.ts`, where the same class of URL is explicitly protected with `args.push('--', url, path)` precisely to stop a crafted URL from being parsed as a flag: [4](#0-3) 
That mitigation is absent in `remote.ts`. If `url` (or `name`) begins with `-`, git will interpret it as an option rather than a literal remote URL/name, enabling classic git argument-injection primitives (e.g., forcing unexpected git behavior via injected flags on `remote add`, and by extension on any subsequent `fetch`/`pull` against that remote).

The `url` value that reaches `addRemote` here (`headCloneUrl`) originates from a `PullRequest` object populated from the GitHub API's PR JSON (`head.repo.clone_url`), which is exactly the kind of "attacker controls a GitHub API object" primitive named in the Valid Impact criteria. The deep-link handler (`x-github-client://openRepo/<url>?pr=<n>`) resolves this by calling `appStore.fetchPullRequest(url, pr)` with the `url` taken from the clicked link itself: [5](#0-4) 

### Impact Explanation
If a crafted `clone_url`/repo-owner value beginning with `-` reaches `addRemote`, git argument injection on `remote add` is possible without any explicit `--` guard, which is the same class of vulnerability the maintainers proactively fixed in `clone.ts` and `remote-parsing.ts`'s `sanitizeCloneName` (both hardened against path/argument-injection payloads). An unguarded `git remote add` invocation could be leveraged to smuggle unexpected git options in, potentially affecting how the remote is fetched from afterward, silently altering what gets fetched/merged into the user's working tree — matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This is **not fully confirmed** as exploitable end-to-end from local code alone, and I want to be explicit about the uncertainty: on real github.com, repository owner/name segments (which compose `clone_url`) are constrained by GitHub's own naming rules and cannot start with `-`, which would block trivial exploitation against genuine github.com/GHE-authenticated flows. The open question I could not fully resolve given tool-call limits is whether `fetchPullRequest(url, pr)` validates that the deep-link-supplied `url` corresponds to an already-authenticated, known endpoint before querying it as an API host — if it does not, an attacker-controlled server masquerading as a PR API endpoint could return arbitrary JSON (including a `clone_url` starting with `-`), fully controlling the string that reaches the unguarded `addRemote` call. I was unable to verify `fetchPullRequest`'s endpoint validation logic in `api.ts` before running out of iterations, so this should be checked directly before treating the issue as confirmed high-likelihood.

### Recommendation
Add the same `--` end-of-options guard used in `clone.ts` to `addRemote()` and any other raw `git remote ...` invocations that take externally-sourced strings (`app/src/lib/git/remote.ts`), e.g. `git(['remote', 'add', '--', name, url], ...)`. Additionally, verify (and if missing, add) validation in `fetchPullRequest`/deep-link handling that the `url` parameter used to resolve PR data is restricted to a currently signed-in account's known API endpoint, rather than an arbitrary attacker-supplied host, before that host's JSON response is trusted to populate `clone_url`.
