### Title
Data Layer `take_offer` commits a pending local root before the wallet spend is confirmed, with no rollback if the wallet RPC call fails - ([File: chia/data_layer/data_layer.py])

### Summary
Chia's Data Layer offer flow mirrors the multi-step "local state update → external commit → possible failure with no rollback" pattern described in the report. `DataLayer.take_offer()` first runs `process_offered_stores()` inside a `data_store.transaction()` that writes a new `PENDING` root (via `batch_insert()` → `insert_batch()`), then, **outside** that transaction, calls `self.wallet_rpc.take_offer(...)` to actually submit the spend bundle on-chain. If the wallet RPC call throws (network error, wallet rejection, RPC exception) after the local pending root has already been committed, the local `data_store` is left with a `PENDING` root that has no corresponding on-chain transaction, and there is no code path that clears or rolls back that pending root.

### Finding Description
`DataLayer.take_offer()`: [1](#0-0) 
computes proofs and a solver **inside** `async with self.data_store.transaction():`, which internally calls `process_offered_stores()` → `batch_insert()`, which persists a new pending root via `insert_batch()`: [2](#0-1) 

Once that `async with` block exits (transaction committed), the code explicitly acknowledges the risk in a comment and then calls the wallet RPC outside the DB transaction: [3](#0-2) 

The comment itself documents the intentional tradeoff ("Excluding wallet from transaction since failures in the wallet may occur after the transaction is submitted to the chain. If we roll back data we may lose published data.") — but this only covers the case where the wallet spend *is* submitted. It does not address the case where `wallet_rpc.take_offer()` raises before ever submitting anything (e.g., RPC connection failure, wallet-side validation exception, `push=True` submission failure). In that scenario:
- The local data store already has a new `Root` row for `store_id` in `Status.PENDING` state (`insert_batch`).
- No spend was ever created or broadcast.
- Nothing in `take_offer()` catches the exception from `wallet_rpc.take_offer` to call `data_store.clear_pending_roots()` (that cleanup only exists in the `cancel_offer()` non-secure path): [4](#0-3) 

The `get_pending_root`/duplicate-pending-root guard in `batch_insert()` means any subsequent legitimate `take_offer`/`make_offer`/`batch_insert` call for the same `store_id` will now fail with `"Already have a pending root waiting for confirmation."`: [5](#0-4) 
until the operator manually intervenes, effectively locking that store's ability to make further updates/offers.

### Impact Explanation
This is a Medium-severity availability/state-consistency issue reachable by an ordinary Data Layer client (offer taker) performing a normal `take_offer` RPC call. A transient wallet RPC failure (not attacker-controlled, but reachable via normal error conditions such as a disconnected wallet, insufficient funds discovered late, or any exception raised inside `wallet_rpc.take_offer`) leaves the local `data_store` with an orphaned `PENDING` root that was never actually published on-chain. This blocks all further legitimate root updates/offers for that store (`batch_insert` raises) until manual cleanup, matching the report's core concern: "state updates being irreversible... left in an inconsistent state" and "funds/state locked."

### Likelihood Explanation
Likelihood is moderate: it requires only a call failure in `wallet_rpc.take_offer` after `process_offered_stores` has already committed — no malicious peer or attacker action is needed, just a normal error path (RPC/network hiccup, wallet busy, insufficient balance surfaced at submission time). Data Layer offer-taking is a routine operation for any Data Layer client, so exposure is realistic, though the specific failure window (post-DB-commit, pre-wallet-submission exception) is narrower than a fully attacker-controlled trigger.

### Recommendation
Wrap the `wallet_rpc.take_offer()` call in a try/except and, on failure, call `await self.data_store.clear_pending_roots(store_id=store_id)` for every store touched by `process_offered_stores(offer_stores=taker)` before re-raising, so a failed wallet submission does not leave orphaned pending roots. The same care should be applied to `make_offer()`, which also commits `process_offered_stores` state before calling `wallet_rpc.create_offer_for_ids`.

### Proof of Concept
1. Call `DataLayer.take_offer(offer_bytes, taker, maker, fee)` with a valid `taker` `OfferStore` whose inclusions produce a non-empty changelist.
2. Inside the `async with self.data_store.transaction()` block, `process_offered_stores` runs `batch_insert`, which commits a new `PENDING` root for `store_id` via `insert_batch`.
3. Simulate/force `self.wallet_rpc.take_offer(...)` to raise (e.g., wallet RPC connection drop, or a wallet-side exception during signing/broadcast) — this is outside the DB transaction so the pending root write is already committed and unaffected by any DB rollback.
4. Observe: `data_store` still has the `PENDING` root for `store_id`; `take_offer()` propagates the exception with no cleanup.
5. Call `DataLayer.batch_insert` or `DataLayer.take_offer`/`make_offer` again for the same `store_id` — it raises `Exception("Already have a pending root waiting for confirmation.")` from `chia/data_layer/data_layer.py:400-401`, confirming the store is now stuck until an operator manually clears the pending root (e.g., via the non-secure `cancel_offer` cleanup path, which does not apply here since no trade was ever recorded).

    async def cancel_offer(self, trade_id: bytes32, secure: bool, fee: uint64) -> None:
        store_ids: list[bytes32] = []

        if not secure:
            trade_record = (
                await self.wallet_rpc.get_offer(GetOffer(trade_id=trade_id, file_contents=True))
            ).trade_record
            trading_offer = TradingOffer.from_bytes(trade_record.offer)
            summary = await DataLayerWallet.get_offer_summary(offer=trading_offer)
            store_ids = [offered.launcher_id for offered in summary.offered]

        await self.wallet_rpc.cancel_offer(
            CancelOffer(trade_id=trade_id, secure=secure, fee=fee, push=True),
            # TODO: probably shouldn't be default but due to peculiarities in the RPC, we're using a stop gap.
            # This is not a change in behavior, the default was already implicit.
            tx_config=DEFAULT_TX_CONFIG,
        )

        if not secure:
            for store_id in store_ids:
                await self.data_store.clear_pending_roots(store_id=store_id)
