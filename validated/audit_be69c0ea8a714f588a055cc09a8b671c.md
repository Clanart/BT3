## Title
Cross-chain token mint/transfer executes before optional-calldata verification, so a signature failure keeps the request unprocessed and lets a request be replayed to mint/drain funds repeatedly — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

## Summary
`pallet-hyper-fungible-token`'s `on_accept` mints or transfers the bridged amount to the beneficiary **before** it verifies the optional calldata signature. If the calldata signature check fails, the handler returns `Err`, which — per Hyperbridge's own documented ISMP semantics — means the request receipt is never persisted and the request can be resubmitted (replayed) with the same membership proof. Each replay repeats the mint/transfer step before hitting the same deterministic signature failure, letting an unprivileged party mint unbounded tokens or drain the pallet's native-asset escrow account from a single source-chain deposit.

## Finding Description
`IsmpModule::on_accept` for the token pallet does the following, in this order:

1. Mint (for wrapped/non-native assets) or transfer from the pallet's escrow account (for the native asset) the bridged `amount` to `beneficiary`: [1](#0-0) 

2. Only afterward does it decode and verify optional calldata attached to the message, including verifying an attacker-suppliable signature: [2](#0-1) 

If the supplied signature fails verification, the code does `Err(HftError::SignatureVerificationFailed)?`, which propagates out of `on_accept` as `Err`, i.e. the function returns without ever reaching the `Ok(...)` at the end: [3](#0-2) 

The protocol's own documentation states the consequence of an `on_accept` that doesn't return `Ok`:

> "if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying its internal state to prevent partial state changes..." [4](#0-3) 

`pallet-hyper-fungible-token` violates exactly the invariant this warning calls out: it mutates state (mints/transfers funds) *before* the step that can fail (signature verification), rather than after all validation. Because `call_data` and its embedded signature are attacker-controlled fields inside the cross-chain `Message` body (documented as SCALE-encoded `SubstrateCalldata` with signature and runtime call, verified "against the beneficiary's account nonce and the runtime call before dispatch"): [5](#0-4) 

an attacker can craft a message whose calldata signature is deterministically invalid (e.g. garbage bytes, or a signature over the wrong key) so that verification fails on every delivery attempt, not just once. Since no receipt is ever written, the same `RequestMessage` + membership proof can be resubmitted through the standard ISMP `handle()` entrypoint indefinitely — this is a normal, permissionless relayer action, not a compromised-relayer or malicious-node assumption.

## Impact Explanation
Each successful replay re-executes step 1 (mint/transfer) before failing again at step 2:
- For a **non-native (wrapped) asset**, `Assets::mint_into` is invoked again on every replay, minting new tokens against a single source-chain lock/burn — unbounded token inflation.
- For the **native asset**, `NativeCurrency::transfer` moves funds out of the pallet's shared escrow account (`pallet_account()`) to the attacker-chosen beneficiary on every replay — this drains balances that back *other users'* legitimate deposits, i.e. direct theft of bridged funds.

This is a direct "stealing or loss of funds" / "double-claim" class vulnerability matching the required impact gate, reachable by any unprivileged user who can call the token contract's `send()` with calldata, with no relayer or prover collusion required.

## Likelihood Explanation
High. The attacker only needs to:
1. Call `send()` with `call_data` containing a syntactically valid but cryptographically invalid `SubstrateCalldata` (any signature bytes that don't verify against the derived key).
2. Wait for (or self-submit as) delivery of the resulting `PostRequest` to the destination chain.
3. Resubmit the same `RequestMessage`/proof as many times as desired, since the failed `on_accept` never wrote a receipt.

No special privileges, no dependency on a malicious relayer, and no reliance on governance/admin misconfiguration are required — only the documented, standard ISMP replay behavior for non-`Ok` module responses.

## Recommendation
Reorder `on_accept` so all validation that can fail — including calldata decode and signature verification — happens *before* any balance-affecting mutation (mint/transfer). Only after all checks pass should the beneficiary receive funds and the optional runtime call be dispatched. If calldata execution itself must be allowed to fail independently of the transfer (e.g., to support "deliver funds even if calldata fails" semantics), that failure must be caught and turned into an `Ok` return (so the receipt is persisted and replay is blocked), with the calldata failure surfaced only via an event, not a propagated `Err`.

## Proof of Concept
1. On the source EVM chain, attacker calls `HyperFungibleToken.send(...)` (or the pallet's own `send`) specifying:
   - `amount = X` (escrowed/burned once on source).
   - `call_data` = SCALE-encoded `SubstrateCalldata { signature: Some(<invalid random 64 bytes>), runtime_call: <anything> }`.
2. A relayer (can be the attacker) delivers the resulting `PostRequest` to the destination chain via the standard ISMP `handle()` request-message path.
3. `Pallet::on_accept` executes: mints/transfers `X` to `beneficiary` (`modules/pallets/hyper-fungible-token/src/module.rs:93-117`), then reaches signature verification, which fails deterministically because the signature bytes are garbage (`module.rs:138-151`), returning `Err`.
4. Per the documented ISMP semantics (`docs/content/protocol/ismp/requests.mdx:102-113`), no receipt is written for this request.
5. Attacker resubmits the identical `RequestMessage` + proof any number of times; each time step 3 repeats, minting/transferring `X` again to `beneficiary` — net effect: `N × X` credited to the beneficiary from a single `X` locked/burned on the source chain.

The request `handle` is used to notify onchain `IsmpModule`s of new requests to be processed. A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
</Callout>

## Calldata Execution

The `call_data` field in `SendParams` allows executing arbitrary runtime calls on the destination substrate chain after the tokens are transferred. The calldata is SCALE-encoded as:

```rust lineNumbers
pub struct SubstrateCalldata {
    /// Optional SCALE-encoded MultiSignature of (account_nonce, runtime_call)
    pub signature: Option<Vec<u8>>,
    /// SCALE-encoded runtime call to execute
    pub runtime_call: Vec<u8>,
}
```

If a signature is provided, it is verified against the beneficiary's account nonce and the runtime call before dispatch. Supported signature types: Ed25519, Sr25519, ECDSA. The account nonce is incremented after dispatch to prevent replay.

If no signature is provided, the origin is derived from the sender address in the cross-chain message.
```
