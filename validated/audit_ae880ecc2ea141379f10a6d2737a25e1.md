### Title
SSRF via unvalidated Data Layer mirror URLs dialed by any subscriber's node - (File: chia/data_layer/download_data.py)

### Summary
`DataLayerWallet.create_new_mirror()` lets any wallet holder attach an arbitrary URL to any Data Layer `store_id` on-chain for a trivial mojo cost, with no ownership check on the `launcher_id` and no validation of the URL. Any peer's Data Layer service that is tracking/subscribed to that store id will unconditionally read that URL back through `update_subscriptions_from_wallet` and later dial it via plain `aiohttp` GET requests in `http_download`, with no host allow/deny-list, no blocking of loopback/link-local/RFC1918/cloud-metadata addresses, and no redirect protection.

### Finding Description
The mirror-creation path in `chia/data_layer/data_layer_wallet.py:687-703` builds a standard coin spend whose puzzle is `create_mirror_puzzle()` and whose memo list is `[launcher_id, *urls]`, with zero validation of either field: [1](#0-0) 

This is exposed at the wallet RPC layer via `dl_new_mirror` (`chia/wallet/wallet_rpc_api.py:3255-3274`), and the Data Layer RPC `add_mirror` only checks that the URL list isn't empty: [2](#0-1) 

The mirror coin's memos are decoded on-chain from any coin spend matching `create_mirror_puzzle().get_tree_hash()`, without checking that the caller owns `launcher_id`: [3](#0-2) 

Any full node/wallet running the Data Layer service that already tracks (subscribes to) that `launcher_id` will observe the mirror coin and persist the raw URL strings via `coin_added`: [4](#0-3) 

`DataLayer.update_subscriptions_from_wallet` then copies these attacker-chosen URLs into local server tracking with no filtering: [5](#0-4) 

`fetch_and_validate` subsequently selects one of these server URLs and attempts to download from it via `insert_from_delta_file` → `download_file` → `http_download`: [6](#0-5) [7](#0-6) 

The `session.get(server_info.url + "/" + filename, ...)` call in `http_download` dials whatever URL was stored — including `http://127.0.0.1:<port>/...` or `http://169.254.169.254/latest/meta-data/...` — with no scheme restriction, no DNS/IP allow-list, and no protection against redirect-based bypass. A source-wide review of `chia/data_layer` shows no host/IP validation anywhere in this chain (unlike the `enforce_https` mainnet check applied to pool URLs in `chia/farmer/farmer.py:685-688`, Data Layer mirror URLs have no such guard at all).

### Impact Explanation
Any wallet holder — no special permission beyond paying the mirror amount + fee — can force every other node that syncs a given Data Layer store to issue outbound HTTP requests to attacker-chosen internal/loopback/link-local/cloud-metadata addresses. The response content is fed into `insert_from_delta_file`/`data_store.insert_into_data_store_from_file` (rejected on validation mismatch), so this is blind SSRF: it provides a status/timing oracle for internal network reconnaissance and can reach cloud metadata endpoints or internal-only management interfaces reachable from the Data Layer host, matching the same bug class (CWE-918) as the referenced Unleash advisory. This satisfies the "coin-set divergence" bar loosely (different nodes probing/being probed) but more directly is a concrete SSRF impact reachable purely from a spend-bundle-created coin, without requiring a malicious peer, node, or operator action beyond normal store subscription.

### Likelihood Explanation
Likelihood is Medium: creating the malicious mirror coin requires only a standard wallet transaction (any user, any store id, no ownership check), but exploitation additionally requires a victim node to already be subscribed to/tracking that specific `launcher_id`. This is a normal, expected Data Layer usage pattern (subscribing to remote/foreign stores to sync their data, e.g. via offers referencing a store), so the precondition is readily satisfiable by an attacker who first gets a victim interested in a store (their own store, or one shared via a Data Layer offer) and then attaches a malicious mirror to it.

### Recommendation
Validate mirror URLs server-side before persisting them via `coin_added`/`update_subscriptions_from_wallet`, and again immediately before dialing in `http_download`/`download_file`: restrict to `http`/`https` schemes, resolve the hostname and reject loopback/link-local/private/metadata address ranges (with DNS-rebinding-safe pinned-IP connection), and disable or constrain redirects. Consider applying the same mainnet HTTPS-only style restriction used for pool URLs (`chia/farmer/farmer.py:685-688`) plus an explicit private-network deny-list, and optionally require store ownership before a mirror can be attached to a `launcher_id`, or make outbound-mirror-fetching opt-in per subscription with an explicit operator allow-list.

### Proof of Concept
1. Attacker wallet A creates a Data Layer store (or targets any store id known to be tracked by victim node V), then calls `dl_new_mirror` (`chia/wallet/wallet_rpc_api.py:3255`) / CLI `chia data add_mirror -i <store_id> -u http://169.254.169.254/latest/meta-data/iam/security-credentials/ -a 1 --fee <fee>` to publish an internal-target URL as a mirror for that `launcher_id`.
2. The resulting coin spend is broadcast and confirmed like any normal transaction; no consensus rule inspects the mirror coin's memo contents.
3. Victim node V, already tracking that `launcher_id` (e.g., subscribed to sync the store), picks up the new mirror coin in `DataLayerWallet.coin_added` (`chia/data_layer/data_layer_wallet.py:775-799`) and stores the URL via `dl_store.add_mirror`.
4. On V's next Data Layer sync cycle, `update_subscriptions_from_wallet` (`chia/data_layer/data_layer.py:979-985`) and `fetch_and_validate`/`download_file`/`http_download` (`chia/data_layer/data_layer.py:642-666`, `chia/data_layer/download_data.py:110-169,298-323`) cause V's Data Layer process to issue an HTTP GET to `http://169.254.169.254/latest/meta-data/iam/security-credentials/<filename>` (or any RFC1918/loopback host), from inside V's network — demonstrating SSRF triggered purely by an on-chain, wallet-submitted coin spend.

```python
def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
```
