**Reasoning:**

The scenario correctly observes that `verify_parachain_headers_with_grandpa_finality_proof` can accept a proof with an empty `parachain_headers` map (nothing to iterate in the `for (hash, proof) in parachain_headers` loop), returning an empty `verified_parachain_headers` while the relay-level `consensus_state.latest_height`/authorities still advance via `verify_grandpa_finality_proof`. [1](#0-0) 

However, this does not create the described exploit path because parachain header freshness/ordering is enforced downstream in the ISMP consensus handler on a **per-`StateMachineId` basis** (i.e., per relay+para_id pair), independent of the relay chain's own `latest_height`: [2](#0-1) 

Specifically, for each intermediate state (per-parachain `StateMachineId`), the handler fetches `previous_latest_height = host.latest_commitment_height(id)` at accept-time and skips any commitment whose height is not strictly greater (`if previous_latest_height > commitment_height.height { continue; }`), then also skips duplicates. This ordering check is keyed on the parachain's own previously-stored latest height, not on the relay's `consensus_state.latest_height`. Submitting a relay-only proof with empty `parachain_headers` never touches this per-parachain `LatestStateMachineHeight` value (there's nothing to insert), so a subsequent "stale" parachain header submission (with a lower `header.number()` than what was already recorded for that para id) would still be rejected by this exact guard — regardless of how far the relay chain's `consensus_state` has advanced in between. `store_latest_commitment_height` and `latest_commitment_height` are both keyed by `StateMachineId` (which embeds `para_id`), confirming the independence from relay-level height: [3](#0-2) 

The BEEFY equivalent path shows the same pattern of skipping entirely when there are no verified parachains, without corrupting or bypassing any per-parachain height tracking: [4](#0-3) 

Thus the "freshness not pinned to consensus_state.latest_height" premise doesn't matter — freshness is pinned to the parachain's own last-accepted height per `StateMachineId`, which is exactly the invariant needed to reject stale/out-of-order parachain state commitments. There is no path by which advancing the relay-only consensus state enables acceptance of a stale prior parachain header afterward.
