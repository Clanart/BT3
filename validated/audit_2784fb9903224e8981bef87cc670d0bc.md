## Analysis Result [1](#0-0) 

### Title
GitHub Desktop explicitly disables Git's recursive-clone hook-execution protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for every `git clone --recursive` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` alongside the recursive submodule flag. [2](#0-1) 
This environment variable is Git's internal safety switch that keeps Git from running repository-controlled hooks (e.g. via nested/embedded `.git` directories or crafted submodules) while a recursive clone is still populating the working tree — the exact class of bug that `GIT_CLONE_PROTECTION_ACTIVE`/related clone-time hardening was introduced for after the 2024 recursive-clone hook-execution advisories. By force-disabling it, Desktop removes Git's own guard for every clone the user performs from the app, while its own hook interception layer (`withHooksEnv`) is never engaged for `clone()` at all, since `clone()` does not pass `interceptHooks` in its options. [3](#0-2) [4](#0-3) 

### Finding Description
Desktop's hook safety model is built around `withHooksEnv`, which intercepts a known allowlist of hooks (`interceptHooks`) and proxies their execution through a sandboxed process so output can be captured and failures can be surfaced/ignored by the user. [5](#0-4) 
This is used for `commit`, `pull`, etc., but `clone()` bypasses this mechanism entirely — it neither sets `interceptHooks` nor routes through `withHooksEnv`; it just runs `git(['clone', '--recursive', ...], __dirname, 'clone', opts)` with an environment that actively turns off Git's own recursive-clone protection. [6](#0-5) 

The invariant being broken is: "content coming from an attacker-controlled remote must not be able to execute code on the victim's machine purely as a side effect of cloning it." A malicious repository (top-level repo or, more likely, a submodule referenced by it) can embed a crafted `.git` directory / hook configuration that Git's `GIT_CLONE_PROTECTION_ACTIVE` guard is specifically designed to neutralize during `--recursive` clone. Because Desktop explicitly forces this guard off for every single clone operation it performs, and does not compensate with its own `interceptHooks`/hooks-proxy for `clone`, any protection that upstream Git relies on this variable for is not present in Desktop's clone path.

### Impact Explanation
If exploited, this allows arbitrary code execution on the victim's machine triggered solely by cloning an attacker-hosted repository through the normal Desktop UI ("Clone Repository", "Open in Desktop" deep link, or `x-github-client://openRepo` URL handling that leads to `openOrCloneRepository`). [7](#0-6) 
This satisfies the report's valid-impact bar: the attacker only controls the cloned repository, and the outcome is code execution on the user's machine — no local/physical access, no prior malware, and no unnatural user steps beyond the ordinary "clone this repo" action that Desktop is designed to support.

### Likelihood Explanation
Every `clone()` call in the app goes through this same code path and always sets `GIT_CLONE_PROTECTION_ACTIVE=false` and `--recursive` unconditionally — it is not conditioned on trust, source, or any prior confirmation. [8](#0-7) [9](#0-8) 
The clone-path sensitivity check in the same file only protects against writing the clone destination itself into sensitive filesystem locations; it does nothing to validate or restrict what the cloned repository (or its submodules) can execute once written. [10](#0-9) 

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` so Git's built-in recursive-clone protection remains active, and/or route the clone operation through the same `interceptHooks`/`withHooksEnv` sandboxing used for `commit`/`pull` so any hook invocation triggered during a recursive clone is captured and gated, rather than left to run unprotected.

### Proof of Concept
1. Attacker hosts a repository containing a submodule reference crafted to place hook content that Git's clone-time hook protection is meant to block from auto-executing during `--recursive` clone population.
2. Victim uses GitHub Desktop's "Clone repository" dialog (or a "Open in Desktop"/PR-checkout deep link that funnels into `openOrCloneRepository` → `clone()`). [7](#0-6) 
3. `clone()` executes `git -c init.defaultBranch=... clone --recursive ... -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment. [11](#0-10) 
4. Because Desktop's own hook interception (`withHooksEnv`) is not applied to this operation and Git's own runtime guard is disabled via the environment variable, no layer prevents the attacker-supplied hook content from being written and eligible to run as part of populating the recursive clone.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
