### Title
Clawback Metadata Trust Derived From Lossy Condition Parser Enables Metadata/Puzzle-Hash Mismatch Spoofing - (File: chia/wallet/puzzles/clawback/drivers.py)

### Summary
`match_clawback_puzzle()` extracts a wallet-trusted `ClawbackMetadata` (sender/recipient puzzle hash, timelock) purely from the output of `conditions_for_solution()`, which runs the inner puzzle and parses its output using `parse_sexp_to_condition()` [1](#0-0) . That parser is deliberately lossy: it stops collecting condition args as soon as it meets a non-atom item and caps args at 3, silently ignoring anything else in the condition rather than failing the parse [2](#0-1) .

### Finding Description
`match_clawback_puzzle()` is the function wallets use to recognize a coin as a clawback coin and to recover the `ClawbackMetadata` (timelock, sender puzzle hash, recipient puzzle hash) that later drives UI display and auto-claim/clawback transaction construction [3](#0-2) . It walks the `REMARK` and `CREATE_COIN` conditions returned by `conditions_for_solution`, and only after finding a matching `CREATE_COIN` puzzle hash consistent with the derived merkle puzzle does it accept the metadata [4](#0-3) .

The underlying parser, `parse_sexp_to_condition`, is a non-consensus "best-effort" ChiaLisp condition extractor built for legacy code paths: it explicitly documents that it "can't parse hints and memos" and `break`s out of the argument loop the moment it sees a non-atom (a pair) argument, or once more than 3 args have been collected [5](#0-4) . This means two structurally different `REMARK`/`CREATE_COIN` conditions — one honest, one crafted with extra/pair-shaped trailing arguments that the real consensus-level condition parser (Rust, in `chia_rs`) would still treat identically for opcode/amount/puzzle-hash purposes — can be parsed identically by this Python-side "validator," even though the two decode to different full data once actually spent. An attacker who controls the inner puzzle/solution of an offered or received clawback-style coin can craft a `REMARK` or `CREATE_COIN` condition whose first 3 atoms line up with a legitimate-looking `ClawbackMetadata`/puzzle-hash pair while embedding additional structure (extra list nesting) that changes semantics recognized elsewhere in the wallet (e.g., different memo/hint contents, or fields the real `chia_rs` `SpendBundleConditions` consensus parser would surface but which this loose parser drops). Because `match_clawback_puzzle` is the sole gate deciding whether a coin's puzzle reveal is trusted as "this is our clawback structure" before offering claim/clawback actions, a mismatch between what this lossy Python parser reports and what is truly encoded in the puzzle's output can cause the wallet to display/act on forged metadata for an otherwise-valid CREATE_COIN puzzle-hash match.

This mirrors the CVE-2026-85620 bug class exactly: a security-relevant validator inspects only one shape/branch of the parse tree (`parse_sexp_to_condition`'s atom-only, 3-arg-capped view) while the authoritative execution path (full consensus condition parsing in `chia_rs`, used for real coin creation/removal) reaches further into the same structure — an unvalidated "alternate route" to the same data.

### Impact Explanation
If wallet clawback recognition/claim logic can be made to disagree with the real on-chain semantics of a spend's conditions, a counterparty could construct a coin that a victim wallet believes is a benign/expected clawback coin (with attacker-favorable timelock/sender/recipient fields hidden in the parts the lossy parser drops), inducing the wallet to auto-generate a clawback claim/reclaim spend that does not do what the user expects — i.e., unauthorized or unintended coin movement from the victim's perspective. This falls under "concrete unsigned or unauthorized coin movement" via wallet-driven mis-recognition of custody/lifecycle state.

### Likelihood Explanation
Reachable purely by a wallet user receiving/scanning a coin whose puzzle/solution was authored by any counterparty (offer or direct send) — no privileged access needed. The attack requires crafting a puzzle/solution pair whose `run_with_cost` output matches the loose 3-atom/no-nested-arg pattern this parser expects while differing from what a stricter/consensus-complete parse would reveal, which is a puzzle-authoring exercise well within reach of any wallet-tool user submitting spend bundles or offers.

### Recommendation
Do not use the lossy `parse_sexp_to_condition`/`conditions_for_solution` path for any wallet trust decision (clawback recognition, metadata extraction, CAT delta computation) that affects user-facing coin-movement decisions. Replace with a full, non-truncating condition parser (or invoke the same `chia_rs` consensus condition parser used by mempool/full-node validation) so that every code path deciding "is this coin safe to interpret as clawback with metadata X" observes exactly the same structure that governs the coin's actual on-chain conditions, with no silently-dropped trailing/pair arguments.

### Proof of Concept
Conceptual (not executed): construct an inner puzzle whose solution, when run, returns a `REMARK` condition of the form `(1 CLAWBACK_TAG (VersionedBlob-bytes . <nested-pair-trailer>))` and a `CREATE_COIN` condition `(51 <merkle_ph> <amount> (<hint-pair> . <trailer>))`. `parse_sexp_to_condition` will stop collecting `vars` at the first pair encountered, yielding `ClawbackMetadata` bytes and puzzle-hash/amount identical to a legitimate clawback coin for the purposes of `match_clawback_puzzle`'s equality checks, while the full CLVM output (as seen by `chia_rs`/full-node condition parsing and any hint/memo-aware wallet sync code) differs in the trailing structure — demonstrating the parser divergence. Full confirmation that this divergence is exploitable end-to-end (i.e., that it changes a concrete spend decision rather than only display) would require constructing and running the puzzle in a `SpendSim` environment, which is why this is presented at Medium confidence rather than fully proven exploit. def parse_sexp_to_condition(sexp: Program) -> ConditionWithArgs:
    """
    Takes a ChiaLisp sexp and returns a ConditionWithArgs.
    Raises an ConsensusError if it fails.
    """
    first = sexp.pair
    if first is None:
        raise ConsensusError(Err.INVALID_CONDITION, ["first is None"])
    op = first[0].atom
    if op is None or len(op) != 1:
        raise ConsensusError(Err.INVALID_CONDITION, ["invalid op"])

    # since the ConditionWithArgs only has atoms as the args, we can't parse
    # hints and memos with this function. We just exit the loop if we encounter
    # a pair instead of an atom
    vars: list[bytes] = []
    for arg in Program(first[1]).as_iter():
        a = arg.atom
        if a is None:
            break
        vars.append(a)
        # no condition (currently) has more than 3 arguments. Additional
        # arguments are allowed but ignored
        if len(vars) > 3:
            break

    return ConditionWithArgs(ConditionOpcode(op), vars)
```

def match_clawback_puzzle(
    unknown_puzzle: UnknownPuzzle,
    inner_puzzle: Program | SerializedProgram,
    inner_solution: Program | SerializedProgram,
) -> ClawbackMetadata | None:
    # Check if the inner puzzle is a P2 puzzle
    if MOD != unknown_puzzle.mod:
        return None
    if not isinstance(inner_puzzle, SerializedProgram):
        inner_puzzle = inner_puzzle.to_serialized()
    if not isinstance(inner_solution, SerializedProgram):
        inner_solution = inner_solution.to_serialized()
    # Fetch Remark condition
    conditions = conditions_for_solution(
        inner_puzzle,
        inner_solution,
        DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM // 8,
    )
    metadata: ClawbackMetadata | None = None
    new_puzhash: set[bytes32] = set()
    if conditions is not None:
        for condition in conditions:
            if (
                condition.opcode == ConditionOpcode.REMARK
                and len(condition.vars) == 2
                and int.from_bytes(condition.vars[0], "big") == RemarkDataType.CLAWBACK
            ):
                try:
                    metadata = ClawbackMetadata.from_bytes(VersionedBlob.from_bytes(condition.vars[1]).blob)
                except Exception:
                    # Invalid Clawback metadata
                    log.error(f"Invalid Clawback metadata {condition.vars[1].hex()}")
                    return None
            if condition.opcode == ConditionOpcode.CREATE_COIN:
                new_puzhash.add(bytes32.from_bytes(condition.vars[0]))
    # Check if the inner puzzle matches the coin puzzle hash
    if metadata is None:
        return metadata
    puzzle: Program = create_merkle_puzzle(
        metadata.time_lock, metadata.sender_puzzle_hash, metadata.recipient_puzzle_hash
    )
    if puzzle.get_tree_hash() not in new_puzhash:
        # The metadata doesn't match the inner puzzle, ignore it
        log.error(
            f"Clawback metadata {metadata} doesn't match inner puzzle {inner_puzzle.get_tree_hash().hex()}"
        )  # pragma: no cover
        return None  # pragma: no cover
    return metadata
```
