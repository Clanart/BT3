### Title
Missing mutual exclusion around unknown-field promotion mutates shared `upb_Message` state without synchronization - ([File: upb/message/promote.c])

### Summary
The upb core runtime's `upb_Message_GetOrPromoteExtension()` mutates a message's internal `aux_data` array (deleting unknown-field entries and inserting a new extension entry) with no built-in locking. The upb project's own code acknowledges this is an unresolved concurrency hazard ("Temporary locking api for cross-language concurrency issue around extension api that uses lazy promotion... Will be replaced by a core runtime solution in the future"), but that locking hook (`hpb::internal::upb_extension_locker_global`) is a no-op unless a language binding explicitly wires it up, and the Python/Ruby/PHP `upb`-based extension-dictionary code paths (e.g. `python/extension_dict.c`) do not use it at all.

### Finding Description
The sctp bug's failed invariant was: two entry points (`sctp_udp_sock_start`/`sctp_udp_sock_stop`) mutate shared global state without a lock, so concurrent invocations race and one thread dereferences state freed/nulled by the other.

The transferable analog in this checkout is `upb_Message_GetOrPromoteExtension` in `upb/message/promote.c:118-215`. When called on a message that has an extension field represented only as unknown/non-canonical data, it:
1. Iterates the message's unknown-field list (`upb_Message_NextUnknown2`),
2. Parses/decodes matching entries into a message (`upb_MiniTable_ParseUnknownMessage`),
3. Calls `_upb_Message_GetOrCreateExtension` to insert a new tagged entry into `msg`'s `upb_Message_Internal.aux_data` array,
4. Then repeatedly calls `upb_Message_DeleteUnknown2` to remove the now-promoted unknown entries from the same `aux_data` array [1](#0-0) .

`aux_data` is a single grow-able array (`upb_Message_Internal{ size; capacity; aux_data[]; }`) owned by the message, reallocated in place via `_upb_Message_ReserveSlot`/realloc-style helpers [2](#0-1) . Nothing in `upb_Message_GetOrPromoteExtension` or `_upb_Message_Getext`/`_upb_Message_GetOrCreateExtension` takes any lock — the function is a plain, non-atomic read-modify-write sequence on shared per-message storage [3](#0-2) .

upb's own maintainers recognize this exact hazard: `hpb/internal/message_lock.h` states this API is used for cross-language "extension api that uses lazy promotion from unknown data to `upb_MiniTableExtension`" and explicitly calls the locking mechanism a temporary stop-gap "to be replaced by a core runtime solution in the future" [4](#0-3) . The locker is a global function pointer that defaults to null (no locking) unless a binding registers one [5](#0-4) ; it is only wired up for the hpb/C++ hybrid path and its own tests demonstrate the race is real by requiring an explicit locker to avoid corruption under concurrent access [6](#0-5) . The upb-based Python extension access path (`python/extension_dict.c`, `PyUpb_ExtensionDict_Subscript` → `PyUpb_Message_GetFieldValue`) does not call into any such locker before touching the shared message's aux_data array [7](#0-6) .

### Impact Explanation
If two threads concurrently access an extension field on the same parsed message object — a normal usage pattern for a message shared across worker threads after being produced once by a public `Parse`/`ParseFromString` call — both can enter `upb_Message_GetOrPromoteExtension` and race on the same `aux_data` array: concurrent `_upb_Message_GetOrCreateExtension` insertions and `upb_Message_DeleteUnknown2` deletions on the same backing array can corrupt the `size`/`capacity`/`aux_data` bookkeeping, leading to out-of-bounds reads/writes, use of stale/reallocated pointers, or a crash (the same class of "one thread frees/mutates what another is dereferencing" failure as the sctp bug's GPF). This is High-severity to the extent the race is reachable through ordinary API usage without any privileged access, malicious schema, or adversarial input beyond an unknown/extension field being present.

### Likelihood Explanation
Likelihood is Medium: the race requires two threads to call extension-accessing APIs (`GetOrPromoteExtension`/`HasExtensionOrUnknown`/related) concurrently on the *same* message instance while that message still has the relevant data in unknown/non-canonical-extension form (i.e., before/while it's being promoted). This is a realistic pattern in multi-threaded server code that parses a message once and then reads extension fields concurrently from multiple worker threads, but it does not happen on every parse — only when promotion is triggered concurrently, and only in language bindings that do not opt into the locking mechanism (the default state for most bindings, per the code above).

### Recommendation
Add mutual exclusion (or a lock-free CAS-based scheme like `python/free_threading/lazy_ptr.c` already uses elsewhere in this codebase) directly inside `upb_Message_GetOrPromoteExtension`/`_upb_Message_GetOrCreateExtension`/`upb_Message_DeleteUnknown2` in the core upb runtime, rather than relying on an opt-in, per-binding locker hook that most language bindings never register. This matches the upb team's own stated TODO to move from the "temporary" `hpb` locking hack to "a core runtime solution."

namespace hpb::internal {

std::atomic<UpbExtensionLocker> upb_extension_locker_global;

/**
 * MessageLock(msg) acquires lock on msg when constructed and releases it when
 * destroyed.
 */
class MessageLock {
 public:
  explicit MessageLock(const upb_Message* msg) : msg_(msg) {
    UpbExtensionLocker locker =
        upb_extension_locker_global.load(std::memory_order_acquire);
    unlocker_ = (locker != nullptr) ? locker(msg) : nullptr;
  }
  MessageLock(const MessageLock&) = delete;
  void operator=(const MessageLock&) = delete;
  ~MessageLock() {
    if (unlocker_ != nullptr) {
      unlocker_(msg_);
    }
  }

 private:
  const upb_Message* msg_;
  UpbExtensionUnlocker unlocker_;
};
