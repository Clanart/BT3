Confirmed: `IntentGatewayV2` on Tron imports `SafeERC20` and uses `using SafeERC20 for IERC20;` for the *escrow-in* path (`safeTransferFrom`), but the *escrow-out* path (`withdraw()` and the `SweepDust` handler in `onAccept()`) deliberately bypasses `SafeERC20.safeTransfer` and instead does a raw low-level `.call()` that only checks the outer call didn't revert — it never decodes/validates the ERC20 boolean return value.

### Title
Escrow release trusts a bare `.call()` success flag instead of validating ERC20 return data, allowing false settlement with worthless "input" tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` releases escrowed order-input tokens to a beneficiary (a solver on `RedeemEscrow`, or the depositor on `RefundEscrow`/refund) using: [1](#0-0) 
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```
This is functionally the same defect class as the referenced `_transferNFTs()` bug: the code treats "the external call did not revert" as proof that value was actually transferred. A contract can implement `transfer()` to simply return `true` (or return nothing, or execute empty logic) without moving any balance, and this check will pass. Compare this to `placeOrder`'s deposit path, which correctly uses `IERC20(token).safeTransferFrom(...)` via OpenZeppelin's `SafeERC20`, which decodes and enforces the boolean return value.

### Finding Description
`order.inputs[].token` is fully attacker/user-controlled data set at `placeOrder()` time on the source chain. A user can register an arbitrary "input token" address pointing to a contract they deploy that:
- Accepts `transferFrom` calls (used at deposit, via `safeTransferFrom`) and returns `true` without holding/moving real backing value, or backing them with worthless self-minted supply.
- Implements `transfer(address,uint256)` to always return `true` (or simply not revert) regardless of actual balance movement.

Because the deposit step uses `safeTransferFrom`, the attacker's contract only needs to "succeed" per ERC20 semantics for its own token — it does not need to be a real, valuable asset. `_orders[commitment][token]` is credited purely from internal bookkeeping (`reducedInputs[i].amount`) with no external verification that the token has real market value.

A solver observes the order, fills it on the destination chain by delivering **real** output tokens to the beneficiary (`_fillSameChain` / cross-chain fill path in `IntrinsicIntents.sol` / `ExtrinsicIntents.sol`), and then triggers the `RedeemEscrow` flow that eventually calls `withdraw()` on the source chain to pay the solver back from escrow. `withdraw()` calls `token.call(...)` for the (worthless) malicious token; the call "succeeds" (no revert) even though no value is transferred, so:
- `_orders[commitment][token] -= amount` proceeds normally (accounting is decremented as if payment was made).
- `_filled[body.commitment] = beneficiary` is recorded, and `EscrowReleased` is emitted.
- The function does not revert, so the solver's real, valuable delivery on the destination chain is never compensated — funds are lost to the solver while the malicious order-placer pays nothing real.

This mirrors the audited pattern precisely: a settlement primitive ("transfer the escrowed asset") appears to succeed and the protocol state moves forward (escrow marked released/filled) even though the actual value movement never occurred, because only the outer call's revert status is checked instead of the actual transfer outcome.

### Impact Explanation
This falls squarely within the bounty's covered impacts: loss of funds (solver performs real work/delivers real value and receives nothing back) and false/incorrect settlement state acceptance (escrow marked as released/filled without real payment). It is reachable by any unprivileged user simply placing a `placeOrder()` call with a malicious token address — no relayer, prover, or admin compromise is required. Any solver naively filling arbitrary orders without off-chain verifying that `order.inputs[].token` is a legitimate, liquid ERC20 is exposed.

### Likelihood Explanation
Likelihood is limited by the fact that a rational solver would typically verify the escrowed input token's legitimacy/liquidity before filling (since solvers already bear pricing risk). However, this defense is off-chain and not enforced by the contract; the contract itself provides zero on-chain guarantee that the escrowed token's `transfer()` return value reflects a genuine balance movement. Given automated/bot-driven solver infrastructure (as referenced in the SDK filler/strategy code), a malicious order engineered to look like a normal small-value swap request could realistically slip past unsophisticated fillers, and the Tron contract's inconsistent transfer-validation style (raw `.call` for payout vs `SafeERC20` for deposit) is itself evidence this wasn't an intentional, reviewed trust decision.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and in the `SweepDust` handler in `onAccept()` with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this same contract (`safeTransferFrom` in `placeOrder`/`fillOrder`). `SafeERC20` correctly decodes returndata and reverts when a token returns `false` or has non-standard return semantics, closing the false-success gap without needing balance-diffing, consistent with the referenced report's recommended mitigation ("revert if the transfer did not actually succeed").

### Proof of Concept
1. Attacker deploys `EvilToken` implementing minimal ERC20 interface: `transferFrom` returns `true` and updates only an internal ledger with no real backing liquidity; `transfer` always returns `true` and does nothing (or silently no-ops).
2. Attacker calls `placeOrder` with `order.inputs[0].token = address(EvilToken)`, `amount = X`, and legitimate-looking `order.output` (e.g., requesting USDC on destination chain) to entice a solver.
3. `placeOrder`'s `safeTransferFrom(msg.sender, address(this), X)` succeeds trivially since `EvilToken.transferFrom` returns `true`; `_orders[commitment][EvilToken] = X` is credited. [2](#0-1) 
4. A solver, seeing the order, calls `fillOrder`/cross-chain equivalent and delivers real USDC to the beneficiary on the destination chain.
5. Solver triggers `RedeemEscrow`; on the source chain `onAccept()` routes to `withdraw(body, false)`. [3](#0-2) 
6. Inside `withdraw()`, `EvilToken.call(transfer(solver, X))` returns `success = true` with no real balance change; the check `if (!success) revert TransferFailed();` passes, `_orders[commitment][EvilToken] -= X` executes, and `EscrowReleased` is emitted — the solver receives nothing of value for the real USDC it paid out on the destination chain. [4](#0-3)
