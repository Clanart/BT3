### Title
Rebasing/yield-bearing input tokens break IntentGatewayV2's per-order escrow ledger, causing under-collateralized settlement or permanently stuck balances - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` credits each order a **fixed integer amount** in the `_orders[commitment][token]` ledger, computed once at deposit time via a `balanceOf` delta [1](#0-0) . This ledger is a set of independent claims against a single **shared, fungible** `IERC20(token).balanceOf(address(this))` pool for that token — many orders' escrow entries draw from the same physical balance. Settlement (`withdraw`, per the documented flow) later pays out exactly the recorded ledger amount to the solver/user, not a live-recomputed share of the pool. If the escrowed token's balance can move independently of transfers — as with any rebasing or auto-compounding token (e.g. `stETH`-style assets) — the actual pooled balance drifts away from the sum of outstanding ledger claims, exactly the invariant break described in the seed report for Cork's `Psm`/`Vault`.

### Finding Description
`placeOrder` protects against fee-on-transfer tokens by measuring the *actual* amount received via balance deltas [2](#0-1) , and stores that fixed number, further reduced by the protocol fee, into `_orders[commitment][token]` [3](#0-2) . This static per-commitment ledger entry is the sole state Hyperbridge uses to settle an order later (documented: "Transfers each escrowed input token to the solver" during `withdraw()`, per `docs/content/developers/evm/intent-gateway/overview.mdx:52-57`).

Crucially, `_orders` is a **mapping of many independent commitments to the same token's shared contract balance** — there is no per-token reserve segregation or balance re-synchronization at settlement time. This is structurally identical to Cork's `Balances` struct tracking `Ra`/`Pa` via state variables while the underlying rebasing token's real balance diverges silently.

For a rebasing input token:
- **Negative rebase / yield-bearing token whose share value can drop** (or simply a token where `balanceOf` doesn't stay pinned 1:1 to what was deposited): the sum of all live `_orders[...][token]` ledger entries can exceed the actual `balanceOf(address(this))`. Whichever order settles last will find the contract short of funds — its `safeTransfer` either reverts (locking the order, since the commitment can never satisfy its recorded amount) or, if a smaller safe-transfer path exists, pays less than recorded.
- **Positive rebase**: surplus balance accrues in the contract with no ledger entry tracking it, silently becoming unclaimable "dust" outside of any of the existing order accounting — the same "stuck yield accrual" impact the seed report describes for Cork.

Neither case requires a malicious relayer, prover, or admin: it is a direct consequence of an unprivileged user placing an order with a rebasing token as `order.inputs[i].token`, and the multi-tenant nature of the escrow pool doing the rest.

### Impact Explanation
This is a genuine fund-loss/lock path reachable through the normal, permissionless `placeOrder` → `fillOrder`/`cancelOrder` → `withdraw` flow, not a peer/relayer/admin trust assumption:
- Later-settling order owners/solvers can be left unable to redeem their full escrowed principal because the shared pool has fewer tokens than the sum of outstanding ledger claims (loss of funds / logic attack on the escrow invariant).
- Positive-rebase surplus becomes permanently stuck in the contract, unaccounted for by any order and unrecoverable through the intended user-facing settlement path (loss/lock of funds).

### Likelihood Explanation
Likelihood is contingent on governance/integrators listing a rebasing or yield-accruing token as an intent input asset (no whitelist enforcement visible in `placeOrder`), which is plausible given the protocol's broader multi-token intent design and precedent (the seed bug shows this exact "we support any token via balance deltas" assumption failing for rebasing assets in another protocol). No attacker action beyond normal order placement/settlement is required once such a token is in use.

### Recommendation
- Disallow rebasing/yield-mutating tokens as intent inputs, or explicitly document them as unsupported (mirroring the seed report's accepted mitigation for Cork).
- If support is desired, re-measure `IERC20(token).balanceOf(address(this))` against the sum of outstanding `_orders[...][token]` claims at withdrawal time, and either pro-rate payouts to the live balance or sweep/redistribute rebase surplus through an explicit accounted mechanism rather than leaving it as unmodeled "dust."

### Proof of Concept
1. Governance lists a rebasing ERC-20 (`balanceOf` can decrease without a corresponding `transfer`) as a valid `order.inputs[i].token` on `IntentGatewayV2`.
2. User A places `orderA` with 1,000 tokens; `_orders[commitmentA][token] = 1000` per `placeOrder`'s balance-delta bookkeeping [2](#0-1) .
3. User B places `orderB` with 1,000 tokens; `_orders[commitmentB][token] = 1000`. Contract's real `balanceOf` = 2,000.
4. A negative rebase reduces the token's `balanceOf(address(this))` to 1,500, while both ledger entries still read 1,000 each (total claims = 2,000 > 1,500 actual).
5. `orderA` settles first via the documented `withdraw()` path and receives its full recorded 1,000 tokens, leaving only 500 in the contract.
6. `orderB`'s settlement (`withdraw()`/refund) attempts to pay out its recorded 1,000 tokens but only 500 remain — the transfer reverts or under-pays, permanently stranding User B's principal, with no attacker, relayer, or admin misbehavior involved.

Note: I could not directly inspect the `withdraw()`/`onAccept()` function bodies within tool-call limits to confirm the exact transfer statement (e.g., whether it is a bare `safeTransfer(token, _orders[commitment][token])`); this is inferred from the documented settlement description and the confirmed `placeOrder` ledger mechanics [3](#0-2) . A background agent with full file access should verify the exact settlement code path before remediation.
