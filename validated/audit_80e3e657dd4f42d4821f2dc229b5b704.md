## Analysis

The Sherlock bug's core pattern: a value computed from **stale positional/temporal state** (the old `listing.created` timestamp) is combined with a **freshly recomputed** quantity (`getListingTaxRequired`) without invalidating the stale reference point, producing an incorrect result that silently harms the user.

GitHub Desktop has a structurally identical pattern in its partial-commit ("stage individual lines") pipeline: a user's line selection is captured as **line-index positions** against a diff that was loaded at selection time, but the actual patch applied to the index at commit time is built from a **freshly re-fetched diff**, with the stale indices re-applied without validating they still map to the same content.### Title
Partial-commit line selection is applied against a freshly-refetched diff, allowing silent inclusion/exclusion of unintended lines in a commit - (File: app/src/lib/git/apply.ts)

### Summary
When a user stages only some lines of a modified file ("partial commit"), Desktop stores the selection as a set of **line indices** (`DiffSelection`) computed against the diff that was displayed at selection time. At commit time, `applyPatchToIndex` does not reuse that diff — it re-fetches a brand-new diff from disk (`getWorkingDirectoryDiff`) and then applies the *old* index-based selection to the *new* diff via `formatPatch`, with no check that the line positions still correspond to the same content. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the Flayer `Listings.sol` bug class exactly: a stale reference computed at one point in time (`listing.created` / here, the diff snapshot and its line offsets) is combined with a value recomputed later (full-duration tax / here, a freshly re-fetched diff) without invalidating or realigning the stale part, producing a silently wrong result.

The flow:
1. User opens a file diff; Desktop loads `diff` and builds `selection.selectableLines` from `diff.hunks[...].unifiedDiffStart + index`. [3](#0-2) 
2. User selects specific lines (adds/deletes) by absolute index — this selection is stored on the `WorkingDirectoryFileChange` object independent of diff content.
3. If the working tree changes on disk between diff-load and commit — e.g., a Git hook (`post-checkout`, `post-merge`), a file watcher/build tool, a `smudge`/`clean` filter, or another background process rewriting the file — the byte/line offsets of subsequent hunks shift.
4. `_commitIncludedChanges` grabs the currently selected files straight from state and calls `createCommit` → `stageFiles` → `applyPatchToIndex`, which re-fetches the diff at that moment (`app/src/lib/git/apply.ts:60`) rather than the diff the user actually looked at. [4](#0-3) [5](#0-4) 
5. `formatPatch` walks the **new** diff's hunks/lines but decides inclusion using `file.selection.isSelected(absoluteIndex)` — an index computed from the **old** diff. [6](#0-5) 

The only place Desktop attempts to reconcile stale line selections against a new diff is `updateChangesWorkingDirectoryDiff`, which explicitly acknowledges the risk ("The diff might have changed dramatically since last we loaded it... we'll settle on just updating the selectable lines") but this reconciliation is asynchronous, debounced by a background status refresh, and is not consulted by `applyPatchToIndex`/`formatPatch` at actual commit time. [7](#0-6) 

Because `DiffSelection` is purely index-based (no content/hash binding), there is no guard preventing a shifted diff from being interpreted with the wrong selection. [8](#0-7) 

### Impact Explanation
This is a silent corruption of what the user commits: lines the user intended to exclude (e.g., a secret, a debug flag, or an unrelated change) can be silently included, or lines they intended to include can be silently dropped, because the positional mapping used to build the patch no longer matches the content the user actually reviewed. Since this affects the exact content written into the Git history and potentially pushed, it satisfies the "silent corruption of what the user commits or pushes" impact class. An attacker who controls repository tooling that runs against the working tree between diff display and commit (hooks, filters, build watchers triggered by a cloned/fetched repo's own configuration) can reliably shift line offsets to manipulate what ends up staged.

### Likelihood Explanation
Requires a specific timing window: file content on disk must change between when the diff/selection is established and when the user clicks Commit, without Desktop's async reconciliation pass completing first. This is plausible in real workflows (auto-formatters, git hooks defined in the cloned repo, slow background refresh cycles) but is a race condition rather than a deterministic trigger, so likelihood is moderate rather than high.

### Recommendation
Do not re-fetch a fresh diff at commit time and blindly reapply stored line indices. Either:
- Persist and reuse the exact diff object that produced the current `DiffSelection` all the way through to `applyPatchToIndex`, rejecting/re-validating the commit if the file's diff has changed since selection, or
- Bind `DiffSelection` to a content fingerprint (e.g., hash of the diff/hunks) and force reselection/re-render when the fingerprint changes, applying the same "selectable lines" reconciliation currently done in `updateChangesWorkingDirectoryDiff` immediately before `formatPatch` is invoked in `apply.ts`.

### Proof of Concept
1. Clone/open a repository containing a `post-checkout` or file-watch/build hook that rewrites a tracked file's content on any working-tree touch (this is legitimate repo configuration an attacker can ship).
2. Modify the file so it produces multiple hunks; open it in Desktop's Changes view, causing a diff to load and `selectableLines` to be computed for the current line positions.
3. Select only specific "safe" lines (e.g., lines 10–12) for partial staging.
4. Before clicking Commit, let the hook/background process alter the file so that new content shifts subsequent hunks (e.g., adds lines above the target region) — Desktop's UI may still display the stale selection highlight if the async reconciliation in `updateChangesWorkingDirectoryDiff` hasn't run yet.
5. Click Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches a fresh diff and applies the old absolute-index selection via `formatPatch`, so the committed patch corresponds to different lines than what the user selected/reviewed, silently including or excluding unintended content in the created commit.
