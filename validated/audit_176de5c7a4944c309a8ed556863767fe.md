Important finding first: in the current (non-legacy) `precompiles/wasmd/wasmd.go`, `ExecuteBatchMethod` is disabled and returns `ErrExecuteBatchDisabled` [1](#0-0) . The batch-loop code with the described lack-of-guard shape only remains reachable through the numerous `precompiles/wasmd/legacy/*` executors (`v552` … `v67`), which are kept for historical block-height replay/tracing per the precompile versioning scheme described in `x/evm/AGENTS.md` [2](#0-1) . ### Title
Potential out-of-order/interleaved execution of `wasmd` `execute_batch` CW sub-messages due to missing reentrancy guard around EVM↔CW round-trips - (File: precompiles/wasmd/legacy/{v552…v67}/wasmd.go)

### Summary
The legacy `wasmd` precompile executors implement `executeBatch`, which iterates over a caller-supplied array of `ExecuteMsg{ContractAddress, Msg, Coins}` and calls `p.wasmdKeeper.Execute` sequentially in a plain Go `for` loop, with no reentrancy guard [3](#0-2) . Because a CW contract invoked as one of these sub-messages can itself issue a `MsgInternalEVMCall` back into the EVM (the "EVM↔CW" round-trip explicitly permitted via `ctx.EVMEntryViaWasmdPrecompile()`), the same precompile address can be re-entered before the outer loop finishes, letting attacker-controlled batch items interleave with, or fully nest inside, other in-flight batches. This is structurally the same bug class as TRST-M-2: an ordered array of "actions" is executed by a loop with no guard against reentry from a callback triggered mid-loop.

### Finding Description
`executeBatch` type-asserts the batch array and loops through it twice: once to sum coin values for `value` validation, and once to actually call `p.wasmdKeeper.Execute(ctx, contractAddr, senderAddr, msg, coins)` for each item [4](#0-3) . There is no lock/flag set before entering this loop and cleared after it, unlike the `nonReentrant` pattern shown in the repo's own Solidity test fixtures (`FixtureReentrancyGuard`) [5](#0-4) .

The `Execute`/`Run` entrypoints for `wasmd` guard against delegatecall/staticcall misuse and against a bare `CW->EVM->CW` pattern (`if method.Name != QueryMethod && !ctx.IsEVM() { ... "sei does not support CW->EVM->CW call pattern" }`) [6](#0-5) , but nothing prevents an `EVM -> wasmd.executeBatch -> CW contract -> EVM (CallEVM) -> wasmd.executeBatch` round-trip. `CallEVM` (invoked when a CW contract calls back into the EVM) explicitly allows this: it only rejects re-entry when `ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile()`, i.e. it *permits* the case where the EVM context was entered via the wasmd precompile [7](#0-6) . A CosmWasm contract can call back into the EVM through `MsgInternalEVMCall`, as documented in the WASM integration section of the EVM module's design notes [8](#0-7) .

Combining these facts: a batch item at index `i` can trigger a CW contract that turns around and calls the `wasmd` precompile (`execute` or `execute_batch`) again — with a fresh, nested set of messages — before the outer loop advances to index `i+1`. This is exactly the pattern flagged in the external report ("[1,[1,2,3],2,3]" instead of "[1,2,3]"): a caller/keeper (here, any attacker-deployed CW contract referenced in the batch) can force nested/interleaved execution of ordered sub-actions.

### Impact Explanation
The impact is analogous to, but weaker than, the original TRST-M-2 finding because the wasmd precompile itself does not carry cross-call financial state comparable to a DCA "last-swap-timestamp" invariant — each `executeBatch`/`execute` call independently validates its own `value`/`coins` sum against the current call's `msg.value`, so there is no direct double-spend of the *precompile's own* accounting shown here. The concrete, exploitable damage instead depends on invariants held by user-deployed CosmWasm contracts that assume a batch of their own actions runs atomically/sequentially without being interrupted by a nested call — e.g., a strategy/vault-style CW contract that performs a swap in one message and records `block.time` of the last swap in a following message (the same DCA pattern in the original report), where reentry could let the same "next" step run multiple times before the record-keeping step executes, bypassing intended cooldown/ordering guarantees and potentially draining held balances faster than intended. Because this depends on the invariants of externally deployed CW/EVM contract pairs rather than on core protocol accounting, I could not confirm a guaranteed, protocol-level fund-loss/freezing/inflation outcome purely from the sei-chain code inspected; it is a credible fund-loss vector for badly-designed downstream contracts, not a certain drain of chain-level funds.

### Likelihood Explanation
Reachability requires: (1) the legacy `executeBatch` precompile path being reachable for live transactions (only confirmed for historical/legacy block heights via the precompile versioning scheme, not confirmed for current-height transactions since the current `precompiles/wasmd/wasmd.go` disables `execute_batch` outright [1](#0-0) ), and (2) a CW contract in the batch that issues a `MsgInternalEVMCall` back to the wasmd precompile. Both are within the reach of a normal EOA/contract deployer (no special privileges needed) if the legacy path is indeed callable, but I was unable to fully verify from the index whether legacy executors can be invoked for new transactions or are restricted to trace-replay of already-finalized historical blocks — this materially affects likelihood and should be verified against the precompile-versioning dispatch code before treating this as exploitable on current chain state.

### Recommendation
Add an explicit reentrancy guard around `wasmd`'s `execute`/`execute_batch` handling (e.g., a per-context flag set on entry and checked/cleared on exit, similar to `ctx.EVMEntryViaWasmdPrecompile`) that rejects nested `wasmd` precompile calls originating from a CW callback while an outer `wasmd.execute`/`execute_batch` invocation is still in progress, rather than only guarding against delegatecall/staticcall and the bare `CW->EVM->CW` shape.

### Proof of Concept
Conceptual PoC (could not be fully validated end-to-end given the "current dispatch disables execute_batch" caveat above):
1. Deploy CW contract `A` whose `execute` handler, when called with a specific message, issues `MsgInternalEVMCall` targeting the `wasmd` precompile address with a new `execute`/`execute_batch` payload.
2. From an EOA, call the `wasmd` precompile's `execute_batch([ {A, triggerMsg}, {B, secondMsg} ])` (on a chain height/path where the legacy `executeBatch` in [4](#0-3)  is reachable).
3. While processing item 0 (`A`), the nested `MsgInternalEVMCall` re-enters the `wasmd` precompile per the round-trip allowance in `CallEVM` [7](#0-6) , executing an attacker-chosen inner batch before the outer loop proceeds to item 1 (`B`).
4. Observe that a CW contract relying on strict, uninterrupted sequential execution of its own batch (e.g., a swap-then-timestamp-update pattern) has its invariant violated because of the interleaved nested call.

func (p PrecompileExecutor) executeBatch(ctx sdk.Context, method *abi.Method, caller common.Address, callingContract common.Address, args []interface{}, value *big.Int, readOnly bool, hooks *tracing.Hooks, evm *vm.EVM) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()
	if readOnly {
		rerr = errors.New("cannot call execute from staticcall")
		return
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	executeMsgs := args[0].([]struct {
		ContractAddress string `json:"contractAddress"`
		Msg             []byte `json:"msg"`
		Coins           []byte `json:"coins"`
	})

	responses := make([][]byte, 0, len(executeMsgs))

	// validate coins add up to value
	validateValue := big.NewInt(0)
	for i := 0; i < len(executeMsgs); i++ {
		executeMsg := ExecuteMsg(executeMsgs[i])
		coinsBz := executeMsg.Coins
		coins := sdk.NewCoins()
		if err := json.Unmarshal(coinsBz, &coins); err != nil {
			rerr = err
			return
		}
		messageAmount := coins.AmountOf(sdk.MustGetBaseDenom()).Mul(state.SdkUseiToSweiMultiplier).BigInt()
		validateValue.Add(validateValue, messageAmount)
	}
	// if validateValue is greater than zero, then value must be provided, and they must be equal
	if (value == nil && validateValue.Sign() == 1) || (value != nil && validateValue.Cmp(value) != 0) {
		rerr = errors.New("sum of coin amounts must equal value specified")
		return
	}
	// Copy to avoid modifying the original value
	var valueCopy *big.Int
	if value != nil {
		valueCopy = new(big.Int).Set(value)
	} else {
		valueCopy = value
	}
	for i := 0; i < len(executeMsgs); i++ {
		executeMsg := ExecuteMsg(executeMsgs[i])

		// type assertion will always succeed because it's already validated in p.Prepare call in Run()
		contractAddrStr := executeMsg.ContractAddress
		if ctx.EVMPrecompileCalledFromDelegateCall() {
			erc20pointer, _, erc20exists := p.evmKeeper.GetERC20CW20Pointer(ctx, contractAddrStr)
			erc721pointer, _, erc721exists := p.evmKeeper.GetERC721CW721Pointer(ctx, contractAddrStr)
			erc1155pointer, _, erc1155exists := p.evmKeeper.GetERC1155CW1155Pointer(ctx, contractAddrStr)
			if (!erc20exists || erc20pointer.Cmp(callingContract) != 0) && (!erc721exists || erc721pointer.Cmp(callingContract) != 0) && (!erc1155exists || erc1155pointer.Cmp(callingContract) != 0) {
				return nil, 0, fmt.Errorf("%s is not a pointer of %s", callingContract.Hex(), contractAddrStr)
			}
		}

		contractAddr, err := sdk.AccAddressFromBech32(contractAddrStr)
		if err != nil {
			rerr = err
			return
		}
		senderAddr, senderAssociated := p.evmKeeper.GetSeiAddress(ctx, caller)
		if !senderAssociated {
			rerr = types.NewAssociationMissingErr(caller.Hex())
			return
		}
		msg := executeMsg.Msg
		coinsBz := executeMsg.Coins
		coins := sdk.NewCoins()
		if err := json.Unmarshal(coinsBz, &coins); err != nil {
			rerr = err
			return
		}
		useiAmt := coins.AmountOf(sdk.MustGetBaseDenom())
		if valueCopy != nil && !useiAmt.IsZero() {
			// process coin amount from the value provided
			useiAmtAsWei := useiAmt.Mul(state.SdkUseiToSweiMultiplier).BigInt()
			coin, err := pcommon.HandlePaymentUsei(ctx, p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address), senderAddr, useiAmtAsWei, p.bankKeeper, p.evmKeeper, hooks, evm.GetDepth())
			if err != nil {
				rerr = err
				return
			}
			valueCopy.Sub(valueCopy, useiAmtAsWei)
			if valueCopy.Sign() == -1 {
				rerr = errors.New("insufficient value provided for payment")
				return
			}
			// sanity check coin amounts match
			if !coin.Amount.Equal(useiAmt) {
				rerr = errors.New("mismatch between coins and payment value")
				return
			}
		}
		// Run basic validation, can also just expose validateLabel and validate validateWasmCode in sei-wasmd
		msgExecute := wasmtypes.MsgExecuteContract{
			Sender:   senderAddr.String(),
			Contract: contractAddr.String(),
			Msg:      msg,
			Funds:    coins,
		}
		if err := msgExecute.ValidateBasic(); err != nil {
			rerr = err
			return
		}

		res, err := p.wasmdKeeper.Execute(ctx, contractAddr, senderAddr, msg, coins)
		if err != nil {
			rerr = err
			return
		}
		responses = append(responses, res)
