### Title
OP_RETURN `data` output omitted from fee/weight calculation, producing transactions whose real fee rate is below the requested and minimum relay rates - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is a fee parameter effectively never applied, so the intended fee is never charged. In Serai's Bitcoin wallet, `SignableTransaction::new` computes the transaction weight and `needed_fee` from `payments` only, even though an attacker/caller-supplied `data` payload creates an extra OP_RETURN output that is serialized into the final transaction. The fee actually paid (`sum(inputs) - sum(outputs)`) is therefore sized for a transaction that never includes the data output, and the minimum-relay-fee check (`TooLowFee`) is performed against the under-estimated `vbytes`. The result is a signed transaction whose true fee rate is strictly lower than `fee_per_vbyte` and potentially below `DEFAULT_MIN_RELAY_TX_FEE`.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight calculation, but the weight calculation is invoked with `payments`, not `tx_outs`: [1](#0-0) . `calculate_weight_vbytes` builds a mock transaction whose outputs are exactly the `payments` (plus an optional change output), so the up-to-80-byte `PushBytesBuf` OP_RETURN output is never weighed: [2](#0-1) . The minimum relay fee check then compares `needed_fee` against the under-estimated `vbytes`: [3](#0-2) . Because the OP_RETURN output carries `value: Amount::ZERO`, the real fee `input_sat - sum(outputs)` equals the under-charged `needed_fee` while the serialized transaction is larger than estimated: [4](#0-3) . Even the change-amount calculation uses `fee_with_change`, which is likewise computed from `payments` without the data output: [5](#0-4) .

### Impact Explanation
A transaction constructed with a `data` payload pays a fee rate below the caller-specified `fee_per_vbyte`. With an 80-byte OP_RETURN (~83+ serialized bytes ≈ 83+ weight units ≈ 21+ vbytes plus output overhead), the effective fee rate can drop below `DEFAULT_MIN_RELAY_TX_FEE` (1000 sat/kvB) even when `fee_per_vbyte` was chosen to satisfy it, because the `TooLowFee` check runs against the smaller, incorrect `vbytes`. Such a transaction is rejected by standard Bitcoin node mempool policy (`sendrawtransaction` fails with "min relay fee not met"), so a threshold-signed spend cannot confirm or even be broadcast — funds are not spendable through the produced transaction. This is a Medium-severity availability/correctness flaw: an incorrect fee formula reachable purely through a public input (`data`), analogous to the original report where a never-assigned fee parameter meant the intended fee was never charged.

### Likelihood Explanation
The `data` argument is a public input to `SignableTransaction::new` (`data: Option<Vec<u8>>`, up to 80 bytes) on the in-scope `networks/bitcoin` wallet code. Any caller supplying `data` triggers the under-charge on every such transaction; the miscalculation is deterministic, not probabilistic. In the bundled processor, `make_signable_transaction` currently passes `None` for data ( [6](#0-5) ), so the defective path is only exercised by other consumers of the wallet API, which lowers practical likelihood within this repo's own call graph.

### Recommendation
Pass the full output set — payments plus the OP_RETURN output — into `calculate_weight_vbytes` so `vbytes` reflects the real transaction size. Concretely, build the `tx_outs` vector (including the data output) first and derive weight/vbytes from it, or add an explicit `data_len`/`output` parameter to `calculate_weight_vbytes`. The same correction must apply to `vbytes_with_change` so change subtraction also uses the true fee. Add a test asserting that `SignableTransaction` with `Some(data)` pays `fee_per_vbyte * actual_vsize` of the final transaction.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte = 1` (1 sat/vB ≈ the minimum relay rate).
2. The returned `needed_fee` equals `1 * vbytes` where `vbytes` was computed without the ~110-byte OP_RETURN-containing output region; the `TooLowFee` check against `(1000 * vbytes)/1000` passes because it uses the same under-estimated `vbytes` ( [7](#0-6) ).
3. The constructed `Transaction` includes the zero-value OP_RETURN `TxOut` in `tx.output` ( [8](#0-7) ), so its real `vsize()` exceeds the estimate by the serialized OP_RETURN output size.
4. Real fee rate = `fee() / tx.vsize()` < 1 sat/vB < `DEFAULT_MIN_RELAY_TX_FEE`; a Bitcoin Core node rejects it via `sendrawtransaction` ("min relay fee not met"), producing an unbroadcastable, unconfirmable spend even though `SignableTransaction::new` returned `Ok`.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
