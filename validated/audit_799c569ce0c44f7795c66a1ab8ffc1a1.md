### Title
Partial-fill escrow release rounds to zero, letting a lopsided order drain a filler's real payment for zero input tokens - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrowed input tokens released to a partial-fill solver as `(order.inputs[i].amount * fillAmount) / totalRequired`, with no check that the result is non-zero, while the solver's real payment (`beneficiaryTotal = fillAmount + beneficiaryShare`) is transferred unconditionally in full. When an order's input/output ratio is set so that `order.inputs[i].amount * fillAmount < totalRequired`, the division truncates to 0: the solver pays real value to `beneficiary` but is escrowed **zero** input tokens in return. This is the same broken invariant as the reported `SharesManager._mintShares` bug — a value-transfer function that can silently mint/allocate zero of the "shares" side while still debiting the full "deposit" side, with no `> 0` guard.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:66-124`), for each output leg: [1](#0-0) 
computes `fillAmount` (bounded by `remaining`), then unconditionally transfers `beneficiaryTotal = fillAmount + beneficiaryShare` from the solver to the beneficiary: [2](#0-1) 

The proportional escrow released back to the solver is then computed only for the non-final-fill branch as: [3](#0-2) 

`escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` uses integer division with no minimum-output check (`escrowedAmount > 0`). If the order creator sets `order.inputs[i].amount` small relative to `totalRequired` (e.g. `order.inputs[i].amount = 1`, `totalRequired = 1e18`), then for any `fillAmount < totalRequired` (i.e., any non-completing partial fill), `escrowedAmount` truncates to `0`. The solver has already paid `beneficiaryTotal` (real output-token value) via `safeTransferFrom`/native transfer at line 107/104, but receives `escrowedInputs[i].amount = 0` in the resulting `WithdrawalRequest` passed to `_withdraw`.

This exactly mirrors the external report's core defect: `shares = (underlyingAssetValue * totalSupply) / oldTotalAssetBalance` can round to zero while the depositor's `underlyingAssetValue` is still pulled in full, and the report's fix — "add a validation check enforcing `sharesToMint > 0`" — is precisely the guard missing here for `escrowedAmount`.

Unlike the reported ERC-4626 case, this does not need front-running: the order creator fully controls both `order.inputs[i].amount` and `order.output.assets[i].amount` at `placeOrder` time (the fee-adjusted, final escrowed amount is committed into the hash before any solver ever sees the order), so the "attacker determines the share price" scenario from the report — the most profitable variant — is directly available to any unprivileged order creator here, with `attackerShares` (the escrow numerator) fully controlled just like in the report.

The existing mitigation visible in the test suite (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1543-1657`, "ROUNDING DUST IN PARTIAL FILLS") only fixes the case where the *final* fill that completes the order receives the full remaining escrow balance (`amountFilled == totalRequired` branch, line 117-118 of `IntrinsicIntents.sol`). It does not address every non-final partial fill rounding to exactly zero — that dust isn't "released later to the last solver" in this scenario, it's a complete, single-fill zero-payout for whichever solver happens to make a partial (non-completing) fill on such a lopsided order.

### Impact Explanation
A solver that partially fills such a lopsided order transfers real, non-zero value (`beneficiaryTotal` of the output token, or ETH) to `beneficiary` and receives `0` escrowed input tokens back — an unconditional, uncompensated loss of funds for the filler, extracted by the order's creator. This matches the bounty's "stealing or loss of funds" and "transaction manipulation" categories: an unprivileged, malicious order-creator can craft an order specifically to bait/trap solvers (or a naive/automated filler, e.g. a solver bot that fills conservatively in small chunks) into a fill that transfers value to the beneficiary for zero consideration. The severity depends on adoption by automated solvers that partially fill without first simulating the escrow release, but the on-chain state transition itself unconditionally allows a zero-value payout for a non-zero payment with no revert, no minimum-amount guard, and no way for the victim to recover the lost value afterward (the input tokens sit escrowed for the order but credited to nobody's fill share for the amount lost to truncation).

### Likelihood Explanation
High for orders deliberately crafted with an extreme input/output ratio (e.g., `inputs[i].amount = 1` unit). No relayer, prover, admin, or malicious peer is required — only `placeOrder` (called by any user) and a subsequent `fillOrder` from an unsuspecting solver performing a non-completing partial fill. Solvers that fill orders piecemeal (multiple small fills, common for order books/liquidity management) are naturally exposed. Solvers that always fill orders completely in one transaction are not exposed, so real-world likelihood scales with how much partial-fill activity the deployed solver ecosystem actually performs.

### Recommendation
Add an explicit non-zero check on the computed escrow release in the non-final branch of `_fillSameChain`:
```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
if (escrowedAmount == 0) revert PartialFillTooSmall();
```
or better, use a rounding scheme (round up, or cap `fillAmount` to the minimum value that yields a non-zero escrow) so a solver's payment is never accepted when it cannot be matched to any escrowed input. This mirrors the report's own recommendation: "Consider adding a validation check enforcing that `sharesToMint > 0`."

### Proof of Concept
1. User calls `placeOrder` with:
   - `order.inputs[0] = { token: USDC, amount: 1 }` (1 unit, e.g. 1 wei of USDC)
   - `order.output.assets[0] = { token: DAI, amount: 1e18 }` (`totalRequired = 1e18`)
2. Order is placed on-chain (no protocol fee complicates this — set `protocolFeeBps = 0` for simplicity), escrow of `1` unit of USDC is held in `_orders[commitment][USDC]`.
3. Solver calls `fillOrder` with `options.outputs[0].amount = 5e17` (a 50% partial fill):
   - `fillAmount = 5e17` (≤ `remaining = 1e18`)
   - `beneficiaryTotal = 5e17` DAI transferred from solver to beneficiary (real payment).
   - `amountFilled = 5e17 != totalRequired (1e18)` → non-final branch:
     `escrowedAmount = (1 * 5e17) / 1e18 = 0` (integer division truncates).
   - Solver's `escrowedInputs[0].amount = 0` is passed to `_withdraw`; solver receives `0` USDC.
4. Result: solver paid `5e17` DAI and received `0` USDC — total loss of the payment, with no revert and no recovery path.

Note: I was unable to fully verify `_withdraw`'s exact bookkeeping of `_orders[commitment][token]` decrement (the `evm/src/apps/intentsv2/IntentsBase.sol` implementation body was not retrieved in full within the available tool budget), so the precise fate of the "un-escrowed" 1 wei of USDC (whether it remains locked forever, or is later handed to whichever fill completes the order) is not confirmed — but the core defect (real payment for a computed-zero release with no guard) is confirmed directly in `IntrinsicIntents.sol` and does not depend on that detail.
