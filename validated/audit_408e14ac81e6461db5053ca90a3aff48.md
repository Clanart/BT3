### Title
`ThresholdKeys::read` accepts identity verification shares via `Ciphersuite::read_G`, bypassing the identity ban enforced by `Curve::read_G` — (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2019-3839 is a "sandbox escape via paths missed by a prior restriction" bug: dangerous operators remained reachable through entry points not covered by the original fix. The Serai analog is the split between two point-deserialization paths. `frost::Curve::read_G` was hardened to reject the identity point, but `ThresholdKeys::read` deserializes untrusted verification shares with `Ciphersuite::read_G`, which only enforces canonicality — identity points are accepted. `ThresholdKeys::new` additionally never verifies that `generator() * secret_share` equals the claimed verification share, so fully attacker-crafted key material is accepted.

### Finding Description
The FROST curve layer explicitly bans the identity point when reading group elements: [1](#0-0) 

However, `ThresholdKeys::read` — an in-scope sink for untrusted bytes — reads all `n` verification shares via `<C as Ciphersuite>::read_G`, which performs only a canonical-encoding round-trip check and permits the identity element: [2](#0-1) [3](#0-2) 

`ThresholdKeys::new` then validates only the *count* and *index range* of the shares, and computes `group_key` from the shares of participants `1..=t` — it never rejects identity shares and never checks that `C::generator() * secret_share == verification_shares[&params.i()]`: [4](#0-3) 

Just as ghostscript operators stayed reachable from places the -dSAFER fix didn't cover, the identity-group-element value — explicitly banned on the FROST read path — remains reachable through the `ThresholdKeys` deserialization path.

### Impact Explanation
An attacker who can supply serialized `ThresholdKeys` bytes (the prompt's listed sink) produces keys where:
- All `t` leading verification shares are identity ⇒ `group_key` (pre-scalar) is identity. `view()` interpolates these shares and adds `offset * generator()` only to `included[0]`'s share, so the effective group key is attacker-controlled (identity, or `offset * G` for a chosen offset). Any FROST signature produced is then a signature under a key whose discrete log the attacker knows (0 or `offset`) — i.e., the group "threshold" key is a single-party attacker key.
- The secret share need not be consistent with `verification_shares[i]`, so `recovery::recover_key`'s final `generator() * res == group_key` check is also satisfiable with attacker-known values.

Concretely this yields signatures that verify under an attacker-controlled group key where a threshold of honest shares was presumed, and, for consumers that derive an external address/key from `group_key()` (e.g., bitcoin-serai wallet paths), "funds received" at a key no real threshold quorum controls.

### Likelihood Explanation
Requires an attacker to feed crafted bytes to `ThresholdKeys::read` — i.e., control over the stored/transmitted key blob rather than just protocol messages. Serai's real flow generates keys via PedPoP/musig locally, so this is a defense-in-depth gap rather than a remote exploit in the honest-coordinator model; hence Medium, not High. The missing checks (`is_identity` on read shares, `G * secret_share == verification_shares[i]`) are cheap and consistent with checks already present elsewhere in the codebase.

### Recommendation
- In `ThresholdKeys::read` (or `ThresholdKeys::new`), reject any verification share where `share.is_identity()` is true.
- In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and error otherwise.
- Optionally reject `group_key` identity after combination.

### Proof of Concept
```rust
// For any Curve C (e.g., Ristretto). Build a ThresholdKeys blob where every
// verification share is the identity point — Ciphersuite::read_G accepts it,
// even though frost::Curve::read_G would reject it.
let t: u16 = 2; let n: u16 = 3; let i: u16 = 1;
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(i.to_le_bytes());
buf.push(1); // Interpolation::Lagrange
let secret = C::F::ONE; // arbitrary attacker-chosen share
buf.extend(secret.to_repr().as_ref());
for _ in 1 ..= n {
  buf.extend(C::G::identity().to_bytes().as_ref()); // identity shares
}
let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap(); // succeeds
assert!(bool::from(keys.group_key().is_identity())); // group key = identity

// Signing under `keys` yields FROST signatures valid for public key = identity,
// whose discrete log (0) the attacker knows — a "threshold" key one party
// fully controls. Curve::read_G would have rejected these bytes.
```

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
