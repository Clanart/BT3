### Title
DkgConfirmer re-signs with a cached deterministic nonce across `share()` and `complete()`, enabling nonce reuse when caller-supplied inputs differ - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The fake-vault bug class — a function trusting a caller-supplied entity without binding it to the state established in a prior call — maps onto `SigningProtocol`'s deterministic preprocess cache. `DkgConfirmer::share()` and `DkgConfirmer::complete()` each independently call `share_internal`, which rebuilds the signing machine from `CachedPreprocesses` keyed only by `(b"DkgConfirmer", attempt)`. Both the `preprocesses` map and the `key_pair` (which determines the signed message) are per-call caller-supplied arguments, yet the nonce seed is fixed per attempt. Any divergence between the inputs of the two calls — or repeated `complete()` calls with differing inputs — produces two FROST signature shares generated under identical nonces `d, e` but different binding factors/challenges, leaking linear relations that recover the validator's secret key.

### Finding Description
`preprocess_internal` caches a 32-byte seed under `self.context = (b"DkgConfirmer", attempt)` and reconstructs the machine via `AlgorithmSignMachine::from_cache`, which deterministically regenerates the same nonces through `seeded_preprocess` (`ChaCha20Rng::from_seed(seed)` feeding `Commitments::new`) every time it is invoked (`crypto/frost/src/sign.rs:121-144`). `share()` calls `share_internal(preprocesses, key_pair)` once to emit a share, and `complete()` calls `share_internal(preprocesses, key_pair)` *again* to rebuild the machine before aggregating (`signing_protocol.rs:288-327`). The message signed is `set_keys_message(&spec.set(), &removed, key_pair)`, so `key_pair` — taken as an argument on each call — directly controls the signed message, and `preprocesses` controls the participant binding factors `rho`. The module's own header acknowledges the danger: "it is explicitly unsafe to reuse nonces across signing sessions... In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" (`signing_protocol.rs:25-35`). `complete()` is precisely such a second `sign` call, and nothing enforces that its `preprocesses`/`key_pair` equal those used in the preceding `share()` — the "fake vault" analog, where a substitute argument is fed to a stateful operation that assumed continuity.

### Impact Explanation
Each signature share has the form `s_j = d + rho_j·e + lambda·(a·s)·c_j`, where `d, e` are the reused nonces, `rho_j`/`c_j` are public values derived from the (attacker-influenced) preprocess set and message, and `s` is the coordinator validator's private key — the root of trust for confirming DKG results on-chain. Every distinct `(msg, preprocesses)` pair signed under the same cached seed yields one linear equation in the three unknowns `d, e, s`. Three such signings (e.g., `share()` plus two `complete()` invocations, or `complete()` calls with differing tributary-supplied `key_pair`s within one attempt) fully determine `s`, allowing an attacker to recover a validator key and forge DKG confirmations — a critical secret-leakage impact.

### Likelihood Explanation
Reachability requires that a caller submit DKG-confirmation transactions causing `share`/`complete` to execute with divergent `key_pair` or preprocess arguments inside one attempt/context. The code relies entirely on BFT ordering to prevent this ("a logical flaw... letting new messages overwrite prior messages" is listed as the only trigger), and provides no in-code guard — there is no storage of the signed message or preprocess hash alongside `CachedPreprocesses` to assert continuity. Because `complete` unconditionally re-runs `sign`, any path where `complete` sees data different from `share` triggers reuse with no additional preconditions; this is at least Medium likelihood, arguable High given confirmation data originates from external transactions.

### Recommendation
When caching the preprocess under `CachedPreprocesses`, also persist a commitment to the exact `sign` inputs (hash of the canonicalized `preprocesses` map and `msg`). On any subsequent `share_internal` for the same context, require the inputs to hash identically; otherwise refuse to sign. Alternatively, have `complete()` reuse the `AlgorithmSignatureMachine` returned by the earlier `share()` call rather than re-deriving and re-signing, so the nonce is consumed exactly once per attempt.

### Proof of Concept
1. Within one `attempt`, trigger `DkgConfirmer::share(preprocesses_A, key_pair_1)`. This caches seed `S` under `(b"DkgConfirmer", attempt)` and emits share `s_1 = d + rho_1·e + lambda·a·s·c_1`.
2. Trigger `DkgConfirmer::complete(preprocesses_A, key_pair_2, shares)` with `key_pair_2 != key_pair_1`. `complete` calls `share_internal` again; `from_cache` regenerates identical `d, e` from `S`, but `msg` differs, so `rho_2`/`c_2` differ → second equation `s_2`.
3. A third signing (another `complete` with `key_pair_3`, or a distinct `preprocesses` set, which also changes `rho`) yields a third equation; solving the 3×3 linear system over the scalar field recovers the validator's private key `s`.

Uncertainty note: whether the tributary layer permits multiple confirmation transactions with distinct `KeyPair`s/`preprocess` sets inside a single attempt was not fully verified within the indexed code; the vulnerability stands on the library-level invariant violation regardless, since `complete()` performing a fresh `sign` under the cached seed is only safe if that upstream invariant holds — an assumption the code itself flags as unenforced (the on-chain preprocess-consistency check is marked `TODO` at `signing_protocol.rs:50-54`).
