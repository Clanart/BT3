### Title
Native-token fee payment in `EvmHost.dispatch()` traps user's excess ETH refund instead of returning it to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept native token payment for relayer fees and internally swap the full `msg.value` for an exact amount of `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens`. Because AMM price can move between quote and execution, callers must supply `msg.value` with slippage headroom — exactly the same "unpredictable exact-output swap" pattern flagged in the external report. Uniswap V2's `swapETHForExactTokens` refunds any unused ETH to `msg.sender` of the router call, but the router's `msg.sender` here is `EvmHost` itself (since `EvmHost` calls the router with `{value: msg.value}`), not the original user. `EvmHost` never forwards that refund back to the original caller, so any ETH provided beyond the exact swap requirement is permanently retained by the contract.

### Finding Description
In `evm/src/core/EvmHost.sol`:
```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
}
``` [1](#0-0) 

The identical pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 

`swapETHForExactTokens` computes `amounts[0]` (actual ETH consumed) internally and, per Uniswap V2 semantics, refunds `msg.value - amounts[0]` to whichever address called the router — here that is `address(this)` (the `EvmHost` contract), because `EvmHost` is the direct caller of the router. Neither `dispatch()` function checks `address(this).balance` after the swap or forwards any residual ETH back to `_msgSender()`. Every other place in the codebase that handles native-token overpayment explicitly refunds the caller (e.g., `IntentGatewayV2`/`IntrinsicIntents._fillSameChain` refunds unspent `msgValue` to `msg.sender` at the end of the function: `(bool sent,) = msg.sender.call{value: msgValue}("")`), confirming this refund step is expected and simply missing from `EvmHost.dispatch()`. [3](#0-2) 

Since users must overprovision `msg.value` to survive price movement between fee estimation and execution (the same exact-output/slippage exposure as the `MAX_SLIPPAGE` report), the guaranteed refund of that buffer is silently absorbed by the protocol contract instead of returning to the payer.

### Impact Explanation
Any unprivileged user who dispatches a POST or GET request with native ETH and provides even a modest slippage/gas-price buffer over the exact fee requirement permanently loses that excess ETH — it accumulates in `EvmHost` with no on-chain accounting tying it back to the original payer. This is a direct, unprivileged loss-of-funds bug reachable through the primary, most commonly used public entrypoints of the bridge (`dispatch`), not a griefing or gas-DoS issue.

### Likelihood Explanation
High. This triggers on ordinary usage — any caller sending `msg.value` greater than the exact amount the AMM ultimately consumes (which is the norm, since callers cannot predict the exact execution price of `swapETHForExactTokens` in advance and must pad `msg.value`) loses the difference on every single dispatch call. No malicious relayer, prover, or governance actor is required.

### Recommendation
After the `swapETHForExactTokens` call, forward any leftover native balance attributable to this call back to `_msgSender()` (e.g., record `address(this).balance` before/after the swap, or use `amounts[0]` returned by the router, and refund `msg.value - amounts[0]` to `_msgSender()`), mirroring the refund pattern already used in `IntentGatewayV2`/`IntrinsicIntents`.

### Proof of Concept
1. Deploy `EvmHost` with a Uniswap V2 router and fee token as normal.
2. Call `dispatch(DispatchPost{ fee: F, ... })` sending `msg.value = M` where `M > amounts[0]` needed to acquire `F` fee tokens (a realistic scenario since the caller must estimate `M` ahead of execution and add slippage buffer, exactly as flagged in the original slippage report).
3. Observe: `swapETHForExactTokens` consumes `amounts[0] <= M` ETH and refunds `M - amounts[0]` ETH to `address(this)` (the `EvmHost` contract) rather than to the caller.
4. Check the caller's ETH balance before and after the transaction: the caller is short exactly `M - amounts[0]` ETH with no corresponding on-chain refund event or path to reclaim it; `address(EvmHost).balance` increases by that amount instead.
