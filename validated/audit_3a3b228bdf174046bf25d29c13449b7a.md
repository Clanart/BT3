It's in the Tron-specific fork of the intents contract, where escrow accounting is credited from the *declared* input amount rather than the *actual* token balance received — the same "trust the field, not the derived/verified reality" flaw as the reported vault bug.## Title
Fee-on-transfer / non-standard ERC-20 inputs let escrow accounting exceed real custody, draining other orders' redemptions — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` credits the `_orders[commitment][token]` escrow ledger with a value derived from the **user-declared** input amount, never checking how many tokens the contract actually received. This is the same broken invariant as the reported `vault_gkhan_account` bug: the program trusts a caller-supplied value/identity (declared amount / owner+mint fields) instead of verifying it against the real, deterministically-checkable state (actual balance received / canonical account derivation). Any order placed with a fee-on-transfer, rebasing, or otherwise lossy ERC-20 as input inflates the shared escrow ledger beyond the contract's real token balance for that asset, letting a later, unrelated legitimate order's redemption fail or be paid out of another user's deposited funds.

### Finding Description
In `placeOrder` (non-predispatch branch), the Tron contract does: [1](#0-0) 

`IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` is called, but the amount credited to the escrow ledger, `_orders[commitment][token] += reducedInputs[i].amount`, is computed from `order.inputs[i].amount` (the caller-declared amount, reduced only by the protocol fee percentage) computed earlier at: [2](#0-1) 

There is no balance-before/after check, so if `token` deducts a transfer fee (fee-on-transfer, deflationary/rebasing token, or any ERC-20 whose `transferFrom` delivers less than requested), the gateway's real `balanceOf(this)` increases by less than the amount credited to `_orders`.

Compare this to the canonical/fixed EVM implementation, which explicitly measures the real balance delta and only computes fees/commitment/escrow from what was actually received: [3](#0-2) [4](#0-3) 

This confirms the Tron contract is a divergent, unpatched copy that reintroduces exactly the class of bug the main contract was hardened against (see the `testPlaceOrder_FeeOnTransferToken*` tests that exist only for the main version, e.g. `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2401-2434`, asserting "Escrow should equal actual received amount" — an invariant the Tron contract does not enforce).

Because `_orders` is a shared per-`(commitment, token)` pool backed by the gateway's single aggregate token balance (not a per-order-derived/isolated custody account — mirroring the missing PDA/ATA derivation in the original report), inflating one order's escrow entry beyond its real backing silently erodes the pool that every other order for the same token relies on. `withdraw`/`_withdraw` later pays out strictly from `_orders[commitment][token]` bookkeeping and the aggregate `IERC20.transfer`, so whichever order redeems first drains real tokens that were nominally credited to a different, honest order: [5](#0-4) 

### Impact Explanation
An attacker places an order using a fee-on-transfer/rebasing ERC-20 as the input token (their own deployed token or an existing one that shares the same token address other users also use as an input). The contract credits `_orders[commitment][token]` with the full declared (minus protocol fee) amount while actually holding less. When a fill/redeem or cancel/refund is later processed for *any* order sharing that token, the pool no longer has enough real balance to cover all outstanding escrow entries — the last party to redeem for that token either has their transfer fail (fund lock / DoS on `withdraw`, directly analogous to Alice's failed `complete_vest`) or, depending on ordering, an attacker's inflated entry is paid out first using tokens that were actually deposited by another honest order. This is unauthorized value extraction / loss-of-funds through pure accounting manipulation, requiring no relayer, prover, or admin compromise.

### Likelihood Explanation
Any unprivileged user can call `placeOrder` with an arbitrary ERC-20 token address as input — the contract performs no allow-listing of input tokens and no post-transfer balance verification in this code path, so the attack is trivially reachable by a single `placeOrder` call with a crafted or existing fee-on-transfer token.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after `safeTransferFrom` (and after the predispatch dispatcher sweep), mutate `order.inputs[i].amount` to the actual received amount, and derive `reducedInputs`/the commitment/escrow credit from that verified value rather than the caller-declared amount. Apply the identical fix to the Tron contract's predispatch branch, which currently sizes `dust`/escrow off `requiredAmount` rather than a verified transferred amount as well.

### Proof of Concept
1. Deploy or reuse a fee-on-transfer ERC-20 `T` (1% fee on transfer) that is also used as an input token by other legitimate orders.
2. Attacker calls `placeOrder` with `inputs = [{token: T, amount: 1000}]`; `reducedInputs[0].amount` is computed as `1000 - protocolFee` at `evm/tron/contracts/apps/IntentGatewayV2.sol:356-364`.
3. `safeTransferFrom(msg.sender, address(this), 1000)` at line 453 actually delivers only `990` `T` to the gateway (1% fee burned/redirected), but `_orders[commitment][T] += reducedInputs[0].amount` at line 457 credits based on `1000`-derived value — a `~10` token deficit versus real custody.
4. Repeat/scale across multiple orders using `T`; the aggregate deficit across `_orders[*][T]` versus `IERC20(T).balanceOf(gateway)` grows.
5. When an honest, unrelated order using `T` as input attempts `withdraw` (via `RedeemEscrow`/`RefundEscrow` in `onAccept`), `IERC20(token).transfer` may fail from insufficient real balance, or an earlier redemption may consume real balance that was supposed to back the honest order — reproducing the "Alice's `complete_vest` fails because Bob drained the shared vault" scenario from the original report.
