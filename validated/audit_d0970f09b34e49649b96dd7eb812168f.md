## Finding [1](#0-0) 

### Title
Stale line-selection indices applied to a freshly re-fetched diff during partial commit silently stages unintended content — (File: `app/src/lib/git/apply.ts`)

### Summary
`WorkingDirectoryFileChange.selection` (a `DiffSelection` bitmask keyed purely by absolute line index) is computed by the renderer against the diff that was displayed to the user at some point in time. When the user commits, `applyPatchToIndex` does **not** reuse that diff; it re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and then blindly applies the old index-based selection to the new diff's line indices via `formatPatch`. If the working tree changes between the moment the user made their line selection and the moment `createCommit` actually runs `applyPatchToIndex`, the indices no longer refer to the same logical lines, so the wrong lines are silently staged/committed — an analog of the reported bug class ("stale state computed against an old reference point applied unchanged to a new reference point/boundary").

### Finding Description
The commit pipeline is:

`_commitIncludedChanges` (app-store.ts) → `createCommit` (app/src/lib/git/commit.ts) → `stageFiles` (app/src/lib/git/update-index.ts) → `applyPatchToIndex` (app/src/lib/git/apply.ts).

`applyPatchToIndex` independently re-fetches the diff: [2](#0-1) 
and immediately builds the patch from it using the file's *existing* `selection` object: [3](#0-2) 

`formatPatch` decides whether to include each line solely by `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` in the *newly fetched* diff — there is no verification that the line at that index is the same line the user actually selected.

The app is aware selection indices can go stale, but the only mitigation implemented lives in the UI refresh path, not in the commit path: [4](#0-3) 
This "prune selectable lines" logic runs when `updateChangesWorkingDirectoryDiff` re-renders the Changes view, but it only trims the `selectableLines` set held in UI state — it does not run again inside `applyPatchToIndex`, which fetches its own independent diff at commit time. Consequently, any working-tree mutation that happens after the last UI diff refresh but before the user clicks "Commit" (e.g. a build tool, dev-server hot-reload, file watcher, or `.gitattributes` clean/smudge filter shipped by a cloned/fetched repository that mutates a tracked file) shifts line offsets in the fresh diff without the app noticing, and the stale index bitmask is applied verbatim.

### Impact Explanation
Because `formatPatch` treats unselected `Add` lines as if they never existed and unselected `Delete` lines as if they never happened (app/src/lib/patch-formatter.ts:171-201), an index-misalignment doesn't just fail loudly — it silently produces a *different, valid* patch. A user who explicitly deselected a specific line (e.g. to exclude a malicious backdoor line injected by tooling in the cloned repository) can have that exact line committed anyway if line offsets shifted, or conversely have legitimate content dropped from the commit. This is "silent corruption of what the user commits" — the same failure class as the reported `_massUpdatePools` bug, where a previously-valid computed value is reused unmodified across a state boundary that has since moved.

### Likelihood Explanation
This requires no local/admin access or leaked credentials. The attacker-controlled ingredient is simply a cloned/fetched repository whose typical dev workflow (build watcher, LFS smudge filter, generated file, autoformatter run via a task the README instructs the user to start) mutates a tracked file's content between the time GitHub Desktop's Changes pane last fetched a diff and the time the user presses Commit — a normal, expected part of using such a repo, not an "unnatural" user step. Desktop does not poll/refresh the diff continuously, so this window is realistically wide.

### Recommendation
Before applying `file.selection` to a freshly fetched diff in `applyPatchToIndex`, revalidate that the diff hasn't changed since the selection was made (e.g. compare against the diff hash/line content the selection was derived from, not just line indices), or re-fetch the diff and recompute/clamp the selection exactly as `updateChangesWorkingDirectoryDiff` does for `selectableLines`, and abort/re-prompt the commit if the underlying diff shape changed instead of silently applying a positional bitmask to different content.

### Proof of Concept
1. Clone a malicious repository that ships a background process (e.g. `npm run watch`) which appends/reorders lines in a tracked file at short intervals — instructed as a normal part of the project's dev workflow.
2. In GitHub Desktop, open the file's diff, deselect one specific line the user does not want to commit (e.g. a line the attacker wants included, disguised as noise).
3. Let the tracked file mutate (line shifted by the watcher) without the Changes pane's diff being re-fetched (no repository refresh trigger occurs in this window).
4. Click Commit. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a new diff; `formatPatch` (`app/src/lib/patch-formatter.ts:143-161`) applies the stale `isSelected(absoluteIndex)` bitmask to the new line positions.
5. Inspect the resulting commit: the originally deselected line is included (or a selected line is dropped), even though the Desktop UI showed the user's intended selection.
