### Title
`git diff -z` output is naively split on NUL bytes, letting a crafted file hide changes from Desktop's diff review - ([File: app/src/lib/git/diff.ts])

### Summary
`diffFromRawDiffOutput` converts the entire raw `git diff --patch-with-raw -z` output buffer to a UTF‑8 string and splits it on the NUL character (`\0`), then feeds only the *last* fragment (`pieces.at(-1)`) to `DiffParser.parse`. [1](#0-0) 
This assumes NUL only ever appears as the `-z` raw-format path separator preceding the patch body. That assumption does not hold for arbitrary file content: Git's binary-detection heuristic only inspects a bounded prefix of a blob, so a text-like file that contains a raw NUL byte later in its content can still be diffed as text (not flagged `Binary files ... differ`) while embedding a stray `\0` inside an added/removed line.

### Finding Description
`getWorkingDirectoryDiff` (and the analogous commit-diff path) runs `git diff ... --patch-with-raw -z ...` and hands the resulting `Buffer` to `diffFromRawDiffOutput`. [2](#0-1) 
Inside that helper, `output.toString('utf-8').split('\0')` blindly splits on every NUL in the *entire* output, including any NUL that happens to occur inside the diff hunk body itself (not just the intended raw-format separator before the patch). Only the final split fragment is parsed:
```
const pieces = result.split('\0')
const parser = new DiffParser()
return parser.parse(forceUnwrap(`Invalid diff output`, pieces.at(-1)))
``` [3](#0-2) 

If an attacker-controlled repository (cloned or fetched) contains a file whose content is textual enough to bypass Git's binary check yet contains an embedded NUL byte positioned after the actual diff hunks the attacker wants hidden, the split discards everything before that NUL — including the `diff --git`, `+++`/`---`, and hunk header lines. `DiffParser.parse` then fails to find a `+++` line via `parseDiffHeader()` and falls into the documented "empty diff" branch, returning `hunks: []` and no error: [4](#0-3) [5](#0-4) 

Crucially, this parsed diff is only used for *review/partial-staging* purposes. When a user chooses "select all" for the file (the common case), staging goes through `stageFiles`, which for fully-selected files just runs `git add`/`update-index` directly on the path — it never consults the parsed diff at all: [6](#0-5) 
So the *displayed* diff (empty, or truncated to only the content after the NUL) can diverge completely from the *actual* content that gets staged and committed by `createCommit`: [7](#0-6) 

This mirrors the reported bug class exactly: a crafted "order" (here, a file diff) presents itself as empty/benign to the reviewer, while the underlying operation (staging/committing the full real file) proceeds and includes content the user never saw or approved.

### Impact Explanation
This allows an attacker who controls a repository the victim clones or pulls from (or a compromised remote/proxy serving fetch responses) to smuggle content into a file such that GitHub Desktop's diff viewer shows no changes (or a truncated diff) for that file, while the real content is fully staged/committed when the user reviews an (apparently empty) file and commits "select all." This is a silent corruption of what the user believes they are committing/pushing — satisfying the "silent corruption of what the user commits or pushes" impact category. Depending on the payload (e.g., a build script, CI config, or source file), this could also lead to downstream code execution once the corrupted commit is pushed and consumed by build/CI systems.

### Likelihood Explanation
Exploitation requires the attacker to craft a file that (a) is not flagged binary by Git's binary-detection heuristic (achievable by keeping the scanned prefix free of NUL/control bytes) and (b) contains a NUL byte positioned to swallow the hunks the attacker wants concealed. This is a data-crafting exercise fully within the attacker's control when they author the malicious repository/commit; no local access, elevated privileges, or social engineering beyond a normal clone/fetch is required. However, it depends on the specific placement of the NUL byte and on `-z` raw output framing behaving as assumed, and I was not able to trace every caller of `diffFromRawDiffOutput` (e.g., whether `getCommitDiff` uses an identical code path) within the available index, so the exact set of affected views (working-directory diff vs. commit history diff) should be confirmed with a live repro.

### Recommendation
Do not indiscriminately split the whole raw output buffer on `\0`. Instead, parse the `-z` raw-format prefix using a bounded/structured approach (e.g., split only the known raw-format header portion, or locate the exact boundary via the diff header's own line markers, or avoid `-z` when parsing patch bodies and instead correlate file paths through a separate `--name-status -z` invocation). Additionally, treat any NUL byte found within already-identified hunk bodies as a hard error (fail-closed) rather than silently falling back to an "empty diff," since Desktop currently treats "no header found" as a valid, empty result.

### Proof of Concept
1. Attacker creates a repository containing `payload.txt` whose first several KB are plain ASCII (so Git's binary heuristic classifies it as text), followed later in the file by a single `\0` byte, followed by malicious/sensitive content, e.g.:
   ```
   ...8000+ bytes of innocuous ascii text...
   \x00
   MALICIOUS_PAYLOAD_LINE
   ```
2. Victim clones the repository and modifies `payload.txt` (e.g., appends a line at the very end, after the payload), then opens Desktop.
3. Desktop runs `git diff --patch-with-raw -z` for the working-directory change; `diffFromRawDiffOutput` splits the buffer on `\0` and keeps only `pieces.at(-1)`, dropping the `diff --git`/hunk-header lines that precede the injected NUL. `DiffParser.parse` cannot find the header and returns `hunks: []` (empty diff), matching the existing "empty diff" fallback path. [1](#0-0) [5](#0-4) 
4. The victim, seeing no diff for `payload.txt` (or believing it unchanged), still selects "select all" and commits. `stageFiles` stages the full file content via `git add` regardless of the (broken) parsed diff, and `createCommit` commits it — including the attacker's hidden payload segment that was never rendered for review. [6](#0-5) [7](#0-6)

export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}

function diffFromRawDiffOutput(output: Buffer): IRawDiff {
  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')

  const pieces = result.split('\0')
  const parser = new DiffParser()
  return parser.parse(forceUnwrap(`Invalid diff output`, pieces.at(-1)))
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

export async function createCommit(
  repository: Repository,
  message: string,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  options?: {
    amend?: boolean
    noVerify?: boolean
    signOff?: boolean
    allowEmpty?: boolean
  } & HookCallbackOptions
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  const args = ['-F', '-']

  if (options?.amend) {
    args.push('--amend')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  if (options?.signOff) {
    args.push('--signoff')
  }

  if (options?.allowEmpty) {
    args.push('--allow-empty')
  }

  const result = await git(
    ['commit', ...args],
    repository.path,
    'createCommit',
    {
      stdin: message,
      // https://git-scm.com/docs/githooks/2.46.1
      interceptHooks: [
        'pre-commit',
        'prepare-commit-msg',
        'commit-msg',
        'post-commit',
        ...(options?.amend ? ['post-rewrite'] : []),
        'pre-auto-gc',
      ],
      onHookProgress: options?.onHookProgress,
      onHookFailure: options?.onHookFailure,
      onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
    }
  )
  return parseCommitSHA(result)
}
