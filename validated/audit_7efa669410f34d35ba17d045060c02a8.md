### Title
`ThresholdKeys::read`/`new` accepts attacker-chosen verification shares with no secret-share binding or identity rejection, yielding a group key whose discrete log the attacker knows — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The reported bug class is "an authority that is expected to be an external signer can be an account whose private key is known to the adversary." In Serai, the analog is a verification share (i.e., a public key that is supposed to correspond to a share of a distributed secret no single party knows) being replaced by a point with a publicly known or attacker-known discrete log. `ThresholdKeys::read` deserializes `n` verification shares via `C::read_G`, and `ThresholdKeys::new` accepts them with only two checks — the count equals `n` (`crypto/dkg/src/lib.rs:355-360`) and each index `<= n` (`crypto/dkg/src/lib.rs:361-365`). There is no rejection of the identity point (unlike `Curve::read_G` which rejects identity at `crypto/frost/src/curve/mod.rs:125-131`), and no check that `C::generator() * secret_share == verification_shares[params.i()]` or that any share is non-trivial. The group key is then computed as the Lagrange combination of shares `1..=t` (`crypto/dkg/src/lib.rs:376-378`), so whoever controls those `t` points controls the group key's discrete log.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads `t`, `n`, `i`, the interpolation mode, a `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new`. The only validations are:

```rust
// crypto/dkg/src/lib.rs:355-378
if verification_shares.len() != usize::from(params.n()) { ... }
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() { ... }
}
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

A crafted byte stream can set `verification_shares[1..=t]` to `G*k_j` for attacker-chosen scalars `k_j` (or to the identity, since `Ciphersuite::read_G` at `crypto/ciphersuite/src/lib.rs:91-101` does not reject identity — it is FROST's `Curve::read_G` wrapper that adds that check, and `ThresholdKeys::read` calls `<C as Ciphersuite>::read_G` at line 622). The resulting `group_key` equals `G * Σ λ_j k_j`, a key whose discrete log is fully known to the attacker. Any `secret_share` value passes; the code never verifies it is consistent with `verification_shares[i]`. By contrast, `dkg_dealer::key_gen` asserts consistency (`debug_assert_eq!(keys.group_key(), group_key)`, `crypto/dkg/dealer/src/lib.rs:64`), and `musig()` at least rejects duplicates via `check_keys` (`crypto/dkg/musig/src/lib.rs:54-60`) — the raw `ThresholdKeys` deserialization path performs no equivalent "is this really a share key" check.

### Impact Explanation
The whole security model of FROST signing (`crypto/frost`) rests on `group_key` being a key whose discrete log is shared among `t`-of-`n` parties and known to no one. If attacker-supplied bytes are fed to `ThresholdKeys::read`, the node imports a key set whose group key is effectively a single-party key held by the attacker. The attacker can then produce valid Schnorr signatures for that group key alone (satisfying `SchnorrSignature::verify`, `crypto/schnorr/src/lib.rs:88-110`), i.e., sign any message/spend any funds addressed to the reported group key, while the honest holder believes it is threshold-protected. This mirrors the report exactly: an "authority"/key whose private key is known is substituted where a distributed (unknowable) key is expected, enabling unauthorized signing and fund transfer. Shares `t+1..=n` are additionally unconstrained since `group_key` only sums `1..=t`.

### Likelihood Explanation
Reachability is conditional: `ThresholdKeys::read` consumes serialized bytes (e.g., key material imported from storage or an external source). The threat model here explicitly includes untrusted bytes passed to `ThresholdKeys::read`. When such a path is exercised, exploitation is deterministic — no probabilistic or multi-party conditions are required; a single crafted serialization sets a fully attacker-known group key. The missing checks (identity rejection, `G*secret_share == verification_shares[i]`) are absent unconditionally in the code as written. Where key bytes are strictly locally generated and never attacker-influenced, the issue is latent rather than live.

### Recommendation
In `ThresholdKeys::new` (and consequently `read`):
- Reject identity points in `verification_shares` (or use the identity-rejecting read).
- Verify `C::generator() * secret_share == verification_shares[&params.i()]`, failing with a `DkgError` on mismatch — this binds the claimed share to the claimed public key, analogous to requiring the authority to be a real signer.
- Optionally sanity-check that `group_key` is non-identity.

### Proof of Concept
```rust
use std::collections::HashMap;
use zeroize::Zeroizing;
use ciphersuite::{group::ff::Field, Ciphersuite};
use dalek_ff_group::Ristretto as C;
use dkg::{ThresholdParams, ThresholdKeys, Interpolation, Participant};

let t = 2u16; let n = 3u16;
// Attacker picks discrete logs for the first t verification shares
let k1 = <C as Ciphersuite>::F::random(&mut rand_core::OsRng);
let k2 = <C as Ciphersuite>::F::random(&mut rand_core::OsRng);
let mut verification_shares = HashMap::new();
verification_shares.insert(Participant::new(1).unwrap(), C::generator() * k1);
verification_shares.insert(Participant::new(2).unwrap(), C::generator() * k2);
// Share 3 is never used in group_key computation; anything works, incl. identity
verification_shares.insert(Participant::new(3).unwrap(), C::G::identity());

// Any secret_share is accepted; consistency with verification_shares[i] is never checked
let keys = ThresholdKeys::<C>::new(
  ThresholdParams::new(t, n, Participant::new(1).unwrap()).unwrap(),
  Interpolation::Lagrange,
  Zeroizing::new(<C as Ciphersuite>::F::random(&mut rand_core::OsRng)),
  verification_shares,
).unwrap();

// group_key = lambda_1*k1*G + lambda_2*k2*G -> attacker knows its discrete log
let group_key = keys.group_key();
// Attacker can now Schnorr-sign as `group_key` with no threshold participation,
// and spend any funds credited to it.
```

Confidence note: the missing validation is confirmed in the code; the practical severity depends on whether a deployment feeds adversary-controlled bytes into `ThresholdKeys::read`, which is within the stated threat model but not something I could verify end-to-end in the caller layer within this scan.
