### Title
Path-containment check `resolveWithin()` uses prefix `startsWith()` without separator, allowing escape to sibling directories via deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
`app/src/lib/path.ts` exposes `resolveWithin()`/`_resolveWithin()`, the app's central guard for "is this path still inside the repository root". The final containment check is a plain string `startsWith()` comparison between the resolved real path and the real root path, with no requirement that a path separator follow the root. This is the same class of bug as the reported Go `Root()` off-by-one: a boundary comparison that is too permissive at exactly the edge case that matters (here, the boundary between "inside root" and "sibling of root that merely shares a prefix"), so input that should be rejected is instead accepted.

### Finding Description
`_resolveWithin()` in `app/src/lib/path.ts`: [1](#0-0) 
resolves `rootPath` + attacker-influenced `pathSegments` to `resolved`, then compares real paths with:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
`String.prototype.startsWith` performs a raw character-prefix comparison, not a path-boundary comparison. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and an attacker-supplied relative path causes resolution to land in a sibling directory `/Users/victim/Documents/GitHub/repo-secrets/secret.txt`, the latter string still starts with the former string (no trailing separator is appended to `realRoot` before the comparison), so the function incorrectly reports the path as "contained" and returns it instead of `null`.

This directly mirrors the audited report's invariant break: the Go `Root()` function rejected an input at the exact boundary value it should have accepted (`==` vs `>`), causing valid input rejection; here the JS `resolveWithin()` accepts an input at the exact boundary value it should reject (prefix match without a separator), causing invalid/out-of-root paths to be treated as valid. Both are "off-by-one" boundary-condition validation failures in a security-relevant containment/limit check.

The function is the sole containment guard used when GitHub Desktop processes the `filepath` parameter of the `x-github-client://openrepo` deep link: [2](#0-1) 
```
if (filepath !== null) {
  if (isAbsolute(filepath)) { ... return }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } else { ... }
}
```
`filepath` originates from `parseAppURL()`'s `open-repository-from-url` action, which is populated straight from the deep link's query string with no path-traversal-specific sanitization: `getQueryStringValue(query, 'filepath')`. [3](#0-2) 

The only other guard is `isAbsolute(filepath)`, which blocks absolute paths but does nothing to stop `../`-style traversal that lands in a sibling folder sharing a name prefix with the target repository — exactly the case `resolveWithin`'s `startsWith` check fails to catch.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openrepo/<repo-url>?filepath=...` link can cause Desktop to resolve and act on a path outside the intended repository, as long as the victim has (or can be induced to have, e.g. via a previous "Clone Again" with a predictable/similar directory name) a directory adjacent to the repo whose name is prefixed by the repo's directory name (e.g. `repo` vs `repo-secrets`, `repo` vs `repo.bak`, `repo` vs `repository`). This satisfies the report's required attacker primitive: "a link or deep link the user clicks." The concrete effect implemented today is `shell.showItemInFolder(resolved)` — revealing/selecting an arbitrary file outside the repository in the OS file manager, which can expose the existence and location of sensitive files (credentials, config, other repos) and, depending on OS file manager behavior on "reveal", assist deeper disclosure. Because `resolveWithin` is a shared, general-purpose primitive (also referenced from `app-store.ts` and `copilot-conflict-context.ts`), any future or existing caller that uses it to gate a file *read* or *write* inside a "trusted root" (rather than just reveal-in-folder) would inherit the same boundary flaw and could be escalated to file read/write outside the repository.

### Likelihood Explanation
Moderate. Exploitation requires: (1) the victim clicking a malicious `x-github-client://` link (a normal, low-friction step already supported and expected in Desktop's OAuth/open-repo flow — not "unnatural"), and (2) the existence of a sibling directory whose name is a superstring of the repository's directory name. Condition (2) is common in practice (e.g., `.bak`, `-old`, `-secrets`, `2`, numbered clone suffixes Desktop itself creates when a folder already exists) and does not require local/physical access, admin rights, or prior malware — only ordinary use of the filesystem, satisfying the "Valid Impact" bar (attacker controls a link the user clicks; no leaked credentials or social engineering beyond the click itself).

### Recommendation
- **Short term:** In `_resolveWithin()` (`app/src/lib/path.ts`), fix the boundary check to require a path separator (or exact equality) after the shared prefix, e.g.:
  ```
  return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ```
  (using the appropriate `sep` for the `options` module, i.e. `Path.posix.sep`/`Path.win32.sep`).
- **Long term:** Add unit tests specifically for the sibling-directory-prefix case (e.g. root `/a/repo`, target `/a/repo-evil/file`) to `app/test/unit/path-test.ts`, matching the same rigor already applied there to symlink-traversal cases. Audit all other `startsWith`-based containment/prefix checks in the codebase (e.g. `isClonePathSensitive` in `app/src/lib/git/clone.ts`, which does correctly append `Path.sep` — use it as the reference implementation) for the same missing-separator pattern.

### Proof of Concept
1. Victim has GitHub Desktop with a repository cloned at `/Users/victim/Documents/GitHub/repo`, and, separately, a sensitive directory `/Users/victim/Documents/GitHub/repo-secrets/secret.txt` (or any directory literally prefixed by `repo`).
2. Attacker sends the victim a link:
   `x-github-client://openrepo/https://github.com/owner/repo?filepath=..%2Frepo-secrets%2Fsecret.txt`
3. Victim clicks the link; Desktop routes it through `parseAppURL` → `openRepositoryFromUrl` in `dispatcher.ts`.
4. `filepath = "../repo-secrets/secret.txt"` is not absolute, so it passes the `isAbsolute` check.
5. `resolveWithin(repository.path, filepath)` resolves to `/Users/victim/Documents/GitHub/repo-secrets/secret.txt`. `realResolved.startsWith(realRoot)` evaluates `"/Users/victim/Documents/GitHub/repo-secrets/secret.txt".startsWith("/Users/victim/Documents/GitHub/repo")` → `true`.
6. Desktop calls `shell.showItemInFolder("/Users/victim/Documents/GitHub/repo-secrets/secret.txt")`, revealing a file entirely outside the cloned repository, even though the containment check was supposed to prevent exactly this. [4](#0-3) [5](#0-4) [6](#0-5)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
