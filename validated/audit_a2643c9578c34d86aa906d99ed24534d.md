### Title
Cached FROST preprocess produces deterministic, reusable nonces enabling ROS-style secret-share recovery — (File: crypto/frost/src/sign.rs)

### Summary
`AlgorithmSignMachine::from_cache` reconstructs a signing machine from a stored `CachedPreprocess` seed (`crypto/frost/src/sign.rs:268-274`, via `AlgorithmMachine::new(...).seeded_preprocess(cache)`). The nonce pair `(d, e)` is derived deterministically from that seed, so every machine rebuilt from the same cache commits to identical nonce commitments `(D, E)` and, critically, uses identical raw nonces when producing a signature share in `sign()` (`crypto/frost/src/sign.rs:386-398`). A co-signer who can cause an honest participant to emit shares for the same cached preprocess across multiple signing attempts — each with a different participant set, message, or co-signer preprocesses — can solve a small linear system and recover the victim's secret share.

### Finding Description
In `sign()`, the effective nonce of participant `i` is `base + rho_i * actual`, where `rho_i` is the binding factor derived per-participant from the `rho_transcript` (`crypto/frost/src/sign.rs:361-371`, `crypto/frost/src/nonce.rs:161-191`). The emitted share has the form:

```
s = d + rho * e + lambda * c * x
```

where `d, e` are the raw nonces, `lambda` the interpolation factor for `i` in `included`, `c` the Schnorr challenge, and `x` the (interpolated/scaled/offset) secret share. `rho`, `lambda`, `c`, and `s` are all computable by a co-signer; `d`, `e`, `x` are unknown.

Because `from_cache` regenerates the *same* `d, e` from the cached seed, every signing session driven from that cache yields one linear equation in the same three unknowns `d, e, x`. Three sessions with distinct `rho`/`lambda`/`c` triples (different co-signer preprocesses, different `included` sets, or different messages) give three independent equations, recovering `x` — the victim's secret key share — exactly the classic ROS attack the binding factors are meant to prevent *within* one session but which caching reintroduces *across* sessions.

### Impact Explanation
Recovery of an honest participant's secret share `x` is key-share recovery — one of the explicitly accepted impacts. Combined with shares obtained elsewhere (or with `t-1` compromised slots in a `t`-of-`n` setup), it contributes to reconstruction of the group private key and forgery of arbitrary threshold signatures, including Bitcoin spends (`TransactionSignMachine` wraps this machinery in `networks/bitcoin/src/wallet/send.rs:373-397`).

### Likelihood Explanation
The caching API exists specifically so preprocesses survive across attempts: `cache()`/`from_cache()` are public trait methods (`crypto/frost/src/sign.rs:264-274`), and `share_internal`-style flows regenerate the machine from the same stored cache on every invocation — including *retries after a failed round*, where co-signers can vary the signing set or their preprocesses. Nothing in `sign()` or `from_cache` enforces one-time use of a cached seed; the doc on `TransactionSignMachine` even acknowledges cached preprocesses are dangerous enough that Bitcoin disables them (`send.rs:333-349`), confirming the hazard is real for every other algorithm built on `AlgorithmSignMachine`. An attacker only needs to be a counterparty in the signing protocol — public-input reachable.

### Recommendation
Bind the cached seed to exactly one completed `sign`: either (a) mix a monotonically-increasing attempt counter or the full `rho_transcript`/`included` set and message hash into nonce derivation so retries cannot reproduce `(d, e)` under attacker-chosen binding factors, or (b) invalidate/rotate the cache entry after the first `sign` call (burn-after-use), or (c) derive nonces as `H(seed || secret_share || rho_transcript_commitment)` so different sessions produce different effective nonces even with identical seed material.

### Proof of Concept
1. Honest participant `i` runs `preprocess()` once and stores `CachedPreprocess` (nonce seed). Attacker `j` (co-signer) receives commitments `(D, E)`.
2. Attempt 1: attacker supplies preprocess set `P1` and message `m1`; honest side calls `from_cache(alg, keys, cache).sign(preprocesses_P1, m1)` → emits share `s1 = d + rho1*e + λ1*c1*x`.
3. Attempts 2 and 3 (e.g., after engineered round failures or new sessions under the same context): attacker varies the participant set / preprocesses / message, obtaining `s2`, `s3` with independently computed `rho2, λ2, c2` and `rho3, λ3, c3` — same `(D, E)` commitments confirm identical `d, e`.
4. Solve the 3×3 linear system over the scalar field for `(d, e, x)`. `x` is the honest participant's secret share — verify against `x*G == verification_share(i)` (after interpolation/scalar adjustments), which is public. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  pub(crate) fn calculate_binding_factors<T: Clone + Transcript>(&mut self, transcript: &T) {
    for (l, binding) in &mut self.0 {
      let mut transcript = transcript.clone();
      transcript.append_message(b"participant", C::F::from(u64::from(u16::from(*l))).to_repr());
      // It *should* be perfectly fine to reuse a binding factor for multiple nonces
      // This generates a binding factor per nonce just to ensure it never comes up as a question
      binding.binding_factors = Some(
        (0 .. binding.commitments.nonces.len())
          .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
          .collect(),
      );
    }
  }

  pub(crate) fn binding_factors(&self, i: Participant) -> &[C::F] {
    self.0[&i].binding_factors.as_ref().unwrap()
  }

  // Get the bound nonces for a specific party
  pub(crate) fn bound(&self, l: Participant) -> Vec<Vec<C::G>> {
    let mut res = vec![];
    for (i, (nonce, rho)) in
      self.0[&l].commitments.nonces.iter().zip(self.binding_factors(l).iter()).enumerate()
    {
      res.push(vec![]);
      for generator in &nonce.generators {
        res[i].push(generator.0[0] + (generator.0[1] * rho));
      }
    }
    res
  }
