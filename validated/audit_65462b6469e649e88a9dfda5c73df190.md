### Title
Path-containment check in `resolveWithin` uses raw prefix `startsWith` without a separator boundary, allowing sibling-directory escape via the `x-github-client://openRepo` deep-link `filepath` parameter - (File: `app/src/lib/path.ts`)

### Summary
The Franklin Templeton bug's broken invariant is: a function is supposed to enforce a hard guarantee (shares must be burned / a boundary must be enforced) but a coding error makes the guarantee silently not hold, and the caller has no way to detect this. The same class of bug exists in GitHub Desktop's path-confinement helper `resolveWithin`, which is relied on to guarantee that an attacker-influenced relative path cannot resolve outside of a trusted root directory. The final containment check uses a raw string prefix comparison instead of a path-boundary-aware comparison, so a sibling directory whose name happens to share the root directory name as a prefix (e.g. `repo` vs `repo-evil` or `repoTools`) is incorrectly treated as "inside" the root.

### Finding Description
`resolveWithin` is the security boundary used across Desktop to keep attacker-controlled relative paths confined to a trusted directory. Its final check is: [1](#0-0) 

```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character comparison with no path-separator boundary check. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and a sibling directory `/Users/victim/Documents/GitHub/repo-secret` (or `repoTools`, `repository2`, etc.) exists on disk, then a resolved path such as `/Users/victim/Documents/GitHub/repo-secret/.git/config` will pass the `startsWith` check even though it is not actually underneath `repo`. This is the well-known "path-prefix without trailing separator" bug class.

This helper is exercised with attacker-controlled input via the `x-github-client://openRepo` deep link. `parseAppURL` extracts an unsanitized `filepath` query-string value directly from the URL with no path validation beyond rejecting absolute paths: [2](#0-1) 

That `filepath` flows into `Dispatcher.openRepositoryFromUrl`, which checks only for an absolute path and otherwise trusts `resolveWithin` to enforce containment: [3](#0-2) 

```
if (filepath !== null) {
  if (isAbsolute(filepath)) {
    log.error(`Refusing to open absolute path: ${filepath}`)
    return
  }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } else {
    log.error(...)
  }
}
```

An attacker who gets a victim to click a crafted `x-github-client://openRepo/<repo-url>?filepath=../<sibling-name-prefix-match>/...` link can cause Desktop to resolve and reveal (via `shell.showItemInFolder`) a path in a sibling repository/folder whose name shares the root directory's name as a prefix — a scenario made more plausible because Desktop clones repositories under a common parent folder (e.g. `~/Documents/GitHub/`), where many differently named repos with shared name prefixes routinely coexist (`repo`, `repo2`, `repo-fork`, `repository`, etc.).

The same helper is also relied upon in `copilot-conflict-context.ts` to keep AI-assisted merge-conflict file reads confined to the working directory before sending file contents to the Copilot API: [4](#0-3) 

A bypass there would mean file contents from a sibling directory (which could include another checked-out repository, `.git/config`, or unrelated files) get read and forwarded to an external API — an out-of-repo read plus potential data exfiltration.

### Impact Explanation
This falls squarely under "file write or read outside the repo" and, via the Copilot path, potential exfiltration of file contents to an external service. Both call sites treat `resolveWithin`'s non-null result as a hard security guarantee ("resolved path is confined to root"), exactly mirroring the original report's pattern where a downstream consumer (the settlement code) trusted an upstream function to have enforced an invariant it did not actually enforce.

### Likelihood Explanation
Exploitation requires: (1) the victim already has multiple repositories/folders cloned under a common parent directory with prefix-overlapping names (a very common Desktop usage pattern, since Desktop's default clone path groups all repos in one folder), and (2) the victim clicks an attacker-supplied `x-github-client://openRepo` deep link (a natural, low-friction attack vector — such links are meant to be clicked from web pages, exactly the class of unprompted-but-natural user action that's in scope). No local access, malware, or leaked credentials are required. The existing guards (`isAbsolute(filepath)` check and `resolveWithin`'s realpath/normalize logic) do not stop this path because the vulnerability lies in the final `startsWith` comparison itself, not in something those guards address.

### Recommendation
Change the final containment check in `_resolveWithin` (`app/src/lib/path.ts`) to a boundary-aware comparison, e.g.:
```
return (
  realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
) ? resolved : null
```
using the appropriate separator for the `options` module in use (`Path`, `Path.posix`, or `Path.win32`), and add regression tests covering sibling directories whose names share the root as a string prefix (not just symlink-traversal cases, which are already tested).

### Proof of Concept
1. Victim has GitHub Desktop with two cloned folders under the same parent directory, e.g. `~/Documents/GitHub/project` and `~/Documents/GitHub/project-internal` (the latter containing sensitive files).
2. Attacker hosts a link: `x-github-client://openRepo/https://github.com/owner/project?branch=main&filepath=..%2Fproject-internal%2F.git%2Fconfig`
3. Victim clicks the link. Desktop resolves `filepath` against `repository.path` = `.../project` via `resolveWithin`.
4. `realResolved` = `.../project-internal/.git/config`; `realRoot` = `.../project`. `realResolved.startsWith(realRoot)` evaluates `true` because `"project-internal/..."` starts with the string `"project"`.
5. The check passes, and `shell.showItemInFolder` reveals the file from the sibling repository — demonstrating a read/reveal outside the intended repository root, bypassing the intended containment guarantee. (I could not run this end-to-end in a live Electron environment from this analysis; verification of `shell.showItemInFolder`'s exact behavior with such a path should be done in a live Devin session, but the `startsWith`-without-separator flaw in `_resolveWithin` is confirmed directly from source at `app/src/lib/path.ts:66-71`.)
