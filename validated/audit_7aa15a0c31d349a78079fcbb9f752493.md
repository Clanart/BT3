## Analysis Result

I traced the "state resets before the dependent value is finalized" bug class into GitHub Desktop's multi-commit conflict handling (rebase/cherry-pick/merge), where `manualResolutions` is a `Map<string, ManualConflictResolution>` keyed only by file `path`, and this map is carried forward across sequential per-commit conflict stops without being cleared when the operation advances to the next commit.

### Title
Manual conflict resolutions are silently carried over between successive commits in a multi-commit rebase/cherry-pick, causing wrong content to be committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` preserves the entire `manualResolutions` map from the previous conflict state whenever a new conflict is detected, keyed solely by file path, with no check that the new conflict is for the *same* logical hunk/commit step as when the resolution was recorded. [1](#0-0) 

### Finding Description
During an interactive rebase or cherry-pick of multiple commits, each commit that touches a conflicting file causes git to stop and expose a fresh conflict. Desktop's `getConflictState`/`updateConflictState` re-derive the conflict state from `IStatusResult` after each git operation, but they always seed the new state with the *previous* `manualResolutions` map: [2](#0-1) 

The only signal used to decide whether a rebase is "continuing" vs. "moved on" is `currentTip`/`targetBranch` change detection in `performEffectsForRebaseStateChange`, which is used purely for **statistics** (`rebaseAbortedAfterConflictsCount`) — it does not clear or re-key `manualResolutions` when the tip changes because a new commit in the sequence has started conflicting: [3](#0-2) 

A dedicated unit test explicitly documents that resolutions are "preserved" even when the rebase advances to a new tip while remaining conflicted (i.e., moving from one commit's conflict directly into the next commit's conflict on the same rebase): [4](#0-3) 

Once a path is present in `manualResolutions`, the UI treats it as resolved via `hasUnresolvedConflicts`/`getConflictedFiles`, which only look up the resolution by `path`, not by which commit or content produced the conflict: [5](#0-4) [6](#0-5) 

When the user clicks "Continue", `continueRebase`/`continueCherryPick` apply the stale `manualResolutions` entry directly via `stageManualConflictResolution`, without re-validating that it corresponds to the conflict markers currently in the working tree for that path: [7](#0-6) [8](#0-7) 

### Impact Explanation
If an attacker crafts a repository (or a series of commits fetched/pulled by the victim) such that the same file path conflicts on two or more consecutive commits during a rebase/cherry-pick, and the correct resolution differs between those two conflicts (e.g., "ours" is correct for commit N but "theirs"/manual edit is required for commit N+1), Desktop's UI will show the second conflict as already resolved (because the path key exists in `manualResolutions`) and silently stage/apply the resolution left over from the first conflict. This results in **silent corruption of what the user commits**: the wrong side of a conflict (potentially attacker-controlled content) is committed and later pushed without the user ever reviewing or approving it for that specific commit — directly matching the "silent corruption of what the user commits or pushes" impact criterion, since the attacker only needs to control the fetched/cloned repository history, not the local machine.

### Likelihood Explanation
Requires the victim to run a multi-commit rebase or cherry-pick (a normal Desktop workflow) against a maliciously crafted branch/commit sequence where the same file conflicts across at least two adjacent commits — no unusual local access, credentials, or social engineering beyond the attacker supplying the repository/branch content is needed. Moderate likelihood: it depends on the victim doing an interactive rebase/cherry-pick across a range containing the crafted commits, which is a supported and common Desktop feature, and the effect (stale `manualResolutions` entries by path) is deterministic per the code paths and unit test shown above.

### Recommendation
Scope `manualResolutions` per conflict "occurrence" instead of by bare path — e.g., include the current `currentTip`/`CHERRY_PICK_HEAD` commit sha (or the conflicted blob hashes) in the resolution key, or explicitly clear `manualResolutions` for paths whenever `currentTip` changes while still conflicted (i.e., whenever the rebase/cherry-pick advances to a new commit in `performEffectsForRebaseStateChange`). Also add a check that re-validates any pre-populated `manualResolutions` entry against the current conflict markers for that path before treating the file as resolved in `getConflictedFiles`/`continueRebase`/`continueCherryPick`.

### Proof of Concept
1. Attacker prepares a branch with commit A (modifies `config.json` introducing conflict-prone content) and commit B (also modifies `config.json`, requiring an opposite resolution to be safe).
2. Victim starts an interactive rebase/cherry-pick spanning A and B onto their branch in Desktop.
3. Commit A conflicts on `config.json`; user manually resolves via UI, setting `manualResolutions.set('config.json', ManualConflictResolution.theirs)` through `_updateManualConflictResolution`. [9](#0-8) 
4. User clicks Continue; rebase advances, `currentTip` changes, but `updateConflictState` re-seeds the new conflict state (for commit B, also touching `config.json`) with the same `manualResolutions` map still containing `'config.json' -> theirs`.
5. Desktop's conflicts dialog shows `config.json` as already resolved for commit B's conflict (per `getConflictedFiles`), so the user is never prompted to look at it, and `continueRebase` calls `stageManualConflictResolution` with the stale/incorrect resolution, silently committing the wrong (attacker-favorable) content.

**Uncertainty**: I was not able to fully trace every UI-level gating check (e.g., whether `ConflictsDialog` or `base-multi-commit-operation.tsx` performs any additional path+content re-validation beyond what's shown) due to index size limits on some files; a Devin session with full repository access could confirm whether any UI code path re-derives conflict markers per path before allowing "Continue" to be clicked, which would affect the precise severity of this analog.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

  return status.files.filter(

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

    this.updateMultiCommitOperationStateAfterManualResolution(repository)

    this.emitUpdate()
  }
