Based on my analysis, I found a concrete analog in `is_atom_canonical()` / `is_clvm_canonical()` in `chia/full_node/mempool_manager.py`, which is invoked directly on every spend bundle submitted to the mempool via `validate_spend_bundle()`.

### Title
Unbounded/out-of-range offset read in CLVM canonical-encoding checker can crash mempool validation on attacker-controlled spend bundle - (File: chia/full_node/mempool_manager.py)

### Summary
`is_clvm_canonical()` and its helper `is_atom_canonical()` walk a raw CLVM byte buffer using a manually tracked `offset`, exactly the offset-driven parsing pattern that caused CVE-2018-14341 in Wireshark's DICOM dissector. Both functions read `clvm_buffer[offset]` and increment `offset` based on attacker-controlled length-prefix bytes with no explicit bounds check before each read [1](#0-0) . Any submitted `SpendBundle` reaches this code on every coin spend during mempool admission [2](#0-1) .

### Finding Description
`is_clvm_canonical()` loops with `while True`, reading `b = clvm_buffer[offset]` and, for atoms, delegating to `is_atom_canonical(clvm_buffer, offset)` [3](#0-2) . `is_atom_canonical()` decodes a variable-length (0–5 extra byte) length prefix by repeatedly indexing `clvm_buffer[offset]` inside a `for i in range(prefix_len)` loop, again with no bounds check against `len(clvm_buffer)` [4](#0-3) . If a submitter crafts a puzzle reveal or solution whose final bytes declare a multi-byte length prefix (e.g. `0xFC`–`0xFD`, requiring 5 extra bytes) but the buffer ends before those bytes exist, `clvm_buffer[offset]` raises an unhandled `IndexError` inside `validate_spend_bundle()`. Unlike the CVE's true infinite loop, this is the Python-safe failure mode of the same missing-bounds-check class: reading past the buffer end because the length/offset arithmetic is trusted from attacker input without validating `offset < len(clvm_buffer)` before every dereference.

This code path is reached from `MempoolManager.validate_spend_bundle()`, called for every coin spend in every submitted `SpendBundle` before signature/cost checks, i.e. by any unprivileged spend-bundle submitter [5](#0-4) .

### Impact Explanation
An unhandled `IndexError` raised deep inside `validate_spend_bundle()` is not a `ConsensusError`/`Err` return value that the mempool machinery is designed to catch and convert into a rejected-bundle response; if uncaught by any outer handler, it can propagate and abort mempool processing for that call, representing a spend-triggered transaction-processing halt (a crafted, cheaply constructed spend bundle can disrupt full-node mempool validation availability). This matches the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Crafting a puzzle reveal or solution with a truncated multi-byte atom length prefix at the very end of the buffer is trivial and requires no special privileges — it only requires being able to submit a `SpendBundle` (or offer / wallet-generated spend containing a malformed sub-blob) to a full node's mempool. No signature validity is required to trigger the crash since `is_clvm_canonical()` runs before/alongside admission checks on raw bytes. The exact reachability without the full test harness/exception-handling stack trace could not be fully confirmed in this review — it's possible outer callers (e.g. `add_spend_bundle`) wrap this call in a broad `try/except`, which would downgrade impact from a crash to a benign single-bundle rejection. This should be verified by directly testing a truncated-prefix buffer against `validate_spend_bundle()`.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (raise/return a well-defined `False`/error instead of indexing past the buffer), and similarly guard the `b = clvm_buffer[offset]` read at the top of the `is_clvm_canonical()` loop. Ensure any exception from this function is caught in `validate_spend_bundle()`/`add_spend_bundle()` and converted to a normal `Err.INVALID_COIN_SOLUTION`-style rejection rather than propagating.

### Proof of Concept
1. Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) bytes end with a byte in the `0xFC`–`0xFD` range (6-byte prefix encoding, needing 5 more bytes) but provide fewer trailing bytes than required, e.g. `solution_hex = "fc"` (single byte, but the encoding claims 5 additional length bytes follow).
2. Submit a `SpendBundle` containing this `CoinSpend` via the standard mempool submission path (`push_tx`/`add_spend_bundle`).
3. Observe that `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))` [6](#0-5) , which calls `is_atom_canonical()`, which indexes `clvm_buffer[offset]` beyond the buffer's length inside the `for i in range(prefix_len)` loop [7](#0-6) , raising an unhandled `IndexError` rather than a graceful `Err` rejection.

Existing project tests (`chia/_tests/core/mempool/test_mempool_manager.py::test_mempool_requires_canonical_clvm`) exercise non-canonical prefixes like `"c00101"` but only within valid buffer lengths [8](#0-7) ; they do not cover the truncated-buffer/out-of-range case described here, which should be added to confirm actual runtime behavior.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
