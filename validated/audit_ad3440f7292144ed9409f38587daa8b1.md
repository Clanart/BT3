### Title
Fee-on-transfer staking tokens cause over-crediting of user balances in `MasterMagpie`, leading to protocol insolvency - (File: `rewards/MasterMagpie.sol`)

### Summary
`MasterMagpie._deposit` credits a user's `user.amount` / `user.available` with the full nominal `_amount` parameter before performing `safeTransferFrom`, without verifying the amount actually received by the contract. If a registered `stakingToken` deducts a fee on transfer, the contract will always receive less than `_amount`, but the user's accounted shares (and therefore withdrawal entitlement) will be inflated.

### Finding Description
In the deposit path, the contract updates state using the caller-supplied `_amount` and only afterwards calls `safeTransferFrom`, with no before/after balance check: [1](#0-0) 

Contrast this with `WombatStaking.deposit`, which correctly measures actual LP received via a before/after balance diff before minting receipt tokens: [2](#0-1) 

`MasterMagpie` has no equivalent balance-diff safeguard. Both `deposit`/`depositFor` (callable directly by any wallet or by an authorized pool helper on a user's behalf) route through `_deposit`: [3](#0-2) 

On withdraw, the full `_amount` is transferred back out regardless of what was actually deposited: [4](#0-3) 

If any pool's `stakingToken` deducts a transfer fee, every depositor is credited more shares (`user.amount`, `user.available`, and the pool's implicit `lpSupply` used for reward-per-share math via `_calLpSupply`) than the token balance actually held by the contract. Early withdrawers can fully redeem their inflated `_amount`, which drains the contract of real tokens faster than deposits replenish it, and the last depositors are unable to withdraw their credited balance because the contract literally does not hold enough of the underlying token — a direct, unprivileged-wallet-reachable insolvency/fund-freezing bug, identical in root cause to the original prePO Collateral.sol finding (crediting the pre-fee nominal amount instead of the actually-received amount).

### Impact Explanation
This causes permanent inability for some legitimate depositors to withdraw their full credited stake (protocol insolvency for that pool), since the sum of `user.amount` values across all depositors of a fee-on-transfer staking token will exceed the actual token balance held by `MasterMagpie`. This is triggerable by ordinary user deposit/withdraw transactions with no admin or governance action required, satisfying the "protocol insolvency" / "permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood depends on whether a pool is ever configured with a fee-on-transfer `stakingToken`. Pool registration itself is a privileged/admin action, but exploitation of the bug requires no privileged action at all — any ordinary depositor interacting with such a pool via `deposit`/`depositFor` triggers the miscounting, exactly mirroring the external report's scenario where an ordinary fee-on-transfer token is simply used as the accounted asset.

### Recommendation
In `MasterMagpie._deposit`, measure the actual amount received via a before/after balance check on `pool.stakingToken` (as already done in `WombatStaking.deposit`) and use that measured amount for `user.amount`, `user.available`, and reward-debt accounting instead of trusting the caller-supplied `_amount`.

### Proof of Concept
1. Assume a pool is registered in `MasterMagpie` with a `stakingToken` that charges a 1% fee on transfer.
2. User A calls `MasterMagpie.deposit(stakingToken, 100e18)`. `_deposit` sets `user.amount = 100e18` and `user.available = 100e18` at [5](#0-4) , then calls `safeTransferFrom`, which due to the fee only delivers 99e18 tokens to the contract.
3. User A calls `withdraw(stakingToken, 100e18)`, which passes the `available` check (`user.available == 100e18`) and transfers out the full 100e18 via `safeTransfer` at [6](#0-5) , exceeding the 99e18 actually held for that user's deposit.
4. Repeated across depositors, the pool's real token balance is depleted faster than credited balances decrease, leaving later depositors unable to withdraw their full recorded `user.amount`.
