### Title
DataLayer multi-store root publication permanently freezes unrelated stores when one launcher fails mid-batch - ([File: chia/data_layer/data_layer.py])

### Summary
`DataLayer.multistore_batch_update()` and `DataLayer.submit_all_pending_roots()` mark the local pending root of *every* store in a batch as `Status.PENDING` before making a single aggregated wallet RPC call (`dl_update_multiple`) that actually pushes the spends on-chain. If that aggregated wallet call fails because just one launcher ID in the batch is unspendable, the exception aborts the whole publish with zero on-chain effect, but the local `PENDING` markers already committed for the other, unrelated, healthy stores are never rolled back. Those stores are then permanently unable to accept new batch updates or submissions, exactly mirroring the reported Vault pattern where a single bad queued request caused the whole settlement to revert and freeze future processing for everyone else.

### Finding Description
`multistore_batch_update()` first inserts local changes for every store id and sets their pending root `status` to `Status.PENDING` (when `submit_on_chain=True`): [1](#0-0) 

`submit_all_pending_roots()` follows the identical pattern: it iterates every currently `PENDING_BATCH` root across all stores, flips each one's status to `Status.PENDING` via `change_root_status()`, and only afterwards issues one aggregated `dl_update_multiple` wallet RPC call for all of them: [2](#0-1) 

On the wallet side, `dl_update_multiple` iterates the supplied `launcher_root_pairs` and calls `wallet.create_update_state_spend()` for each launcher inside one `action_scope`: [3](#0-2) 

`create_update_state_spend()` (via `get_spendable_singleton_info()`) raises a `ValueError` if a given launcher id is not tracked, not yet confirmed, or missing lineage information: [4](#0-3) 

Because `new_wallet_action_scope()` only pushes staged transactions to the mempool *after* the caller's `async with` block completes without raising, a mid-loop exception in `dl_update_multiple` aborts the entire action scope and **no spend is ever pushed on-chain**: [5](#0-4) 

However, the local `DataStore` root-status mutations performed earlier in `multistore_batch_update()`/`submit_all_pending_roots()` are committed in separate, already-finished SQLite transactions and are not undone when the later wallet RPC call fails. Any store now sitting at `Status.PENDING` locally, with the wallet singleton never having advanced (because the spend was never pushed), is stuck: `batch_insert()` explicitly refuses to accept new changes for that store while a `PENDING` root exists, and `submit_pending_root()` refuses re-submission the same way: [6](#0-5) [7](#0-6) 

`_update_confirmation_status()` is the only mechanism that can clear a stale `PENDING` root, but it only promotes/clears state once the wallet's singleton `generation` actually advances to match — which never happens here because the spend never reached the chain: [8](#0-7) 

### Impact Explanation
A single unspendable/untracked launcher id included in a `multistore_batch_update` or swept up by `submit_all_pending_roots` (e.g., a store id typo, a store the caller doesn't actually own, or one whose singleton state is transiently unconfirmed due to a race with another concurrent update) causes the entire aggregated on-chain publish to fail. All other, legitimate stores that were included in that same batch call are left with local roots incorrectly marked `PENDING` even though nothing was ever broadcast. From that point on, every future `batch_update`, `multistore_batch_update`, and `submit_pending_root` call against those stores is rejected with "Already have a pending root waiting for confirmation" / "Pending root is already submitted," permanently blocking further DataLayer state publication for those stores until an operator manually intervenes (there is no visible RPC path to force-clear a stuck `PENDING` root that never reached chain). This is a spend/RPC-triggered halt of the DataLayer's transaction-processing pipeline for otherwise-healthy stores, directly analogous to the Vault bug where one bad queued withdrawal froze settlement for all other users.

### Likelihood Explanation
This is reachable by any local Data Layer RPC caller batching multiple stores in one `multistore_batch_update`/`submit_all_pending_roots` call — a normal, expected DataLayer usage pattern for multi-store owners. No special privileges beyond normal DataLayer RPC access are required, and the triggering condition (one store not confirmed/tracked/spendable while others are healthy) is an easy, even accidental, occurrence (e.g., racing a store's confirmation, or including a store id not currently owned).

### Recommendation
Do not mark a store's local pending root as `PENDING` (nor set `PENDING_BATCH` state as unrecoverable) until the aggregated wallet publish call has actually succeeded. Either: (1) validate all launcher ids' spendability up front before mutating any local root status, aborting the whole batch atomically if any fail; or (2) wrap the local root-status mutation and the wallet RPC publish call in a single rollback-capable transaction so a failed publish reverts every store's status back to its pre-batch state; or (3) add a recovery/reset RPC that lets a `PENDING` root whose wallet spend never got confirmed/pushed be safely reverted to `PENDING_BATCH`/cleared.

### Proof of Concept
1. Create three DataLayer stores, `A`, `B`, `C`, all owned and confirmed.
2. Stop tracking or otherwise make `B`'s singleton unconfirmed/untracked (e.g., interleave with `dl_stop_tracking` or race a concurrent `create_update_state_spend` against `B` so its singleton is mid-spend and `get_spendable_singleton_info` will raise "is currently pending").
3. Call `multistore_batch_update` (or `submit_all_pending_roots` after separately batching `A`, `B`, `C`) with changelists for `A`, `B`, and `C` together, `submit_on_chain=True`.
   - `data_layer.py`'s loop first calls `batch_insert()` for `A`, `B`, `C`, setting all three local pending roots to `Status.PENDING`.
   - It then calls the aggregated `wallet_rpc.dl_update_multiple()` with all three launcher/root pairs.
   - Inside `dl_update_multiple`, the wallet's loop calls `create_update_state_spend()` for `A` (succeeds, staged), then for `B` — which raises `ValueError` because `B`'s singleton is not confirmed/spendable.
   - The exception propagates out of the `async with new_action_scope(...)` block before the `yield` point's follow-up push code runs, so **nothing is pushed to the mempool** for `A`, `B`, or `C`.
4. Observe: `A` and `C` (perfectly healthy stores) are left with local `Status.PENDING` roots, even though no spend was ever broadcast.
5. Attempt `batch_update` or `submit_pending_root` for `A` or `C` — both fail permanently with "Already have a pending root waiting for confirmation." / "Pending root is already submitted.", and `_update_confirmation_status()` never clears this because the wallet singleton generation for `A`/`C` never advances (no spend was ever confirmed).

    async def multistore_batch_update(
        self,
        store_updates: list[dict[str, Any]],
        fee: uint64,
        submit_on_chain: bool = True,
    ) -> list[TransactionRecord]:
        store_ids: set[bytes32] = set()
        for update in store_updates:
            store_id = update["store_id"]
            changelist = update["changelist"]

            if store_id in store_ids:
                raise Exception(f"Store id {store_id.hex()} must appear in a single update")
            store_ids.add(store_id)

            status = Status.PENDING if submit_on_chain else Status.PENDING_BATCH
            await self.batch_insert(store_id=store_id, changelist=changelist, status=status)

        if submit_on_chain:
            updates: list[LauncherRootPair] = []
            for store_id in store_ids:
                await self._update_confirmation_status(store_id=store_id)
                root_hash = await self._get_publishable_root_hash(store_id=store_id)
                updates.append(LauncherRootPair(launcher_id=store_id, new_root=root_hash))
            response = await self.wallet_rpc.dl_update_multiple(
                DLUpdateMultiple(updates=DLUpdateMultipleUpdates(launcher_root_pairs=updates), fee=fee),
                DEFAULT_TX_CONFIG,
            )
            return response.transactions
        else:
            return []

    async def _update_confirmation_status(self, store_id: bytes32) -> None:
        async with self.data_store.transaction():
            try:
                root = await self.data_store.get_tree_root(store_id=store_id)
            except Exception:
                root = None
            singleton_record = (
                await self.wallet_rpc.dl_latest_singleton(DLLatestSingleton(launcher_id=store_id, only_confirmed=True))
            ).singleton
            if singleton_record is None:
                return
            if root is None:
                pending_root = await self.data_store.get_pending_root(store_id=store_id)
                if pending_root is not None and pending_root.status == Status.PENDING:
                    if pending_root.generation == 0 and pending_root.node_hash is None:
                        await self.data_store.change_root_status(pending_root, Status.COMMITTED)
                        await self.data_store.clear_pending_roots(store_id=store_id)
                        return
                    else:
                        root = None
            if root is None:
                self.log.info(f"Don't have pending root for {store_id}.")
                return
            if root.generation == singleton_record.generation:
                return
            if root.generation > singleton_record.generation:
                self.log.info(
                    f"Local root ahead of chain root: {root.generation} {singleton_record.generation}. "
                    "Maybe we're doing a batch update."
                )
                return
            wallet_history = (
                await self.wallet_rpc.dl_history(
                    DLHistory(
                        launcher_id=store_id,
                        min_generation=uint32(root.generation + 1),
                        max_generation=singleton_record.generation,
                    )
                )
            ).history
            new_hashes = [record.root for record in reversed(wallet_history)]
            root_hash = self.none_bytes if root.node_hash is None else root.node_hash
            generation_shift = 0
            while len(new_hashes) > 0 and new_hashes[0] == root_hash:
                generation_shift += 1
                new_hashes.pop(0)
            if generation_shift > 0:
                await self.data_store.clear_pending_roots(store_id=store_id)
                await self.data_store.shift_root_generations(store_id=store_id, shift_size=generation_shift)
            else:
                expected_root_hash = None if new_hashes[0] == self.none_bytes else new_hashes[0]
                pending_root = await self.data_store.get_pending_root(store_id=store_id)
                if (
                    pending_root is not None
                    and pending_root.generation == root.generation + 1
                    and pending_root.node_hash == expected_root_hash
                    and pending_root.status == Status.PENDING
                ):
                    await self.data_store.change_root_status(pending_root, Status.COMMITTED)
            await self.data_store.clear_pending_roots(store_id=store_id)

    async def dl_update_multiple(
        self,
        request: DLUpdateMultiple,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLUpdateMultipleResponse:
        """Update multiple singletons with new merkle roots"""
        if self.service.wallet_state_manager is None:
            raise RuntimeError("not initialized")

        wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            # TODO: This method should optionally link the singletons with announcements.
            #       Otherwise spends are vulnerable to signature subtraction.
            # TODO: This method should natively support spending many and attaching one fee
            fee_per_launcher = uint64(request.fee // len(request.updates.launcher_root_pairs))
            for launcher_root_pair in request.updates.launcher_root_pairs:

                    launcher_root_pair.launcher_id,
                    launcher_root_pair.new_root,
                    action_scope,
                    fee=fee_per_launcher,
                    extra_conditions=extra_conditions,
                )

            # tx_endpoint will take care of default values here
            return DLUpdateMultipleResponse(unsigned_transactions=[], transactions=[])

    async def get_spendable_singleton_info(self, launcher_id: bytes32) -> tuple[SingletonRecord, LineageProof]:
        # First, let's make sure this is a singleton that we track and that we can spend
        singleton_record: SingletonRecord | None = await self.get_latest_singleton(launcher_id)
        if singleton_record is None:
            raise ValueError(f"Singleton with launcher ID {launcher_id} is not tracked by DL Wallet")

        # Next, the singleton should be confirmed or else we shouldn't be ready to spend it
        if not singleton_record.confirmed:
            raise ValueError(f"Singleton with launcher ID {launcher_id} is currently pending")

        # Next, let's verify we have all of the relevant coin information
        if singleton_record.lineage_proof.parent_name is None or singleton_record.lineage_proof.amount is None:
            raise ValueError(f"Singleton with launcher ID {launcher_id} has insufficient information to spend")

async def new_wallet_action_scope(
    wallet_state_manager: WalletStateManager,

        puzzle_for_pk = wallet_state_manager.main_wallet.puzzle_for_pk
