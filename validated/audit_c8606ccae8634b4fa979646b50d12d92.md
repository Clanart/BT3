### Title
Panic on out-of-range `Participant` in `Decryption::decrypt_with_proof` crashes blame adjudication - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The MySQL charset DoS class maps onto Serai as a panic reachable by feeding an attacker-controlled participant index and attacker-crafted bytes into the PedPoP blame path. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with no bounds check. `AdditionalBlameMachine::new` only populates `enc_keys` for `1 ..= n`, so any `Participant` index greater than `n` causes an unconditional `HashMap` index panic, killing the calling thread/process. The `accuser`/`accused` indexes in a blame accusation are deserialized from raw `u16`s (`Participant::new(u16::from_le_bytes(...))` in `coordinator/src/tributary/transaction.rs:348`), which accepts any nonzero value, including `> n`. ### Finding Description
`AdditionalBlameMachine::new(context, n, commitment_msgs)` builds `Decryption` with `enc_keys` containing only participants `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs:656-659`). `blame(sender, recipient, msg, proof)` → `blame_internal` → `decrypt_with_proof(from, decryptor, msg, proof)` (`encryption.rs:366-397`). Inside `decrypt_with_proof`:

1. `msg.pop.verify(...)` is checked — the PoP is a Schnorr signature under the ephemeral `msg.key`, bound to the claimed `from` index via `pop_challenge`. An attacker can satisfy this trivially by generating `msg` themselves with any `from` index.
2. If `proof.is_some()`, `self.enc_keys[&decryptor]` is evaluated as an argument to `dleq.verify` before any validity check on the proof itself (`encryption.rs:388`). If `decryptor` was never registered (index `> n`, or `0` excluded by `Participant::new`), this panics.

A panic here aborts the thread evaluating blame. In the processor flow (`processor/src/key_gen.rs:504-549`), `VerifyBlame { accuser, accused, share, blame }` calls `.blame(accuser, accused, substrate_share, substrate_blame)` on an `AdditionalBlameMachine` built only from participants `1..=n`. The `InvalidDkgShare` transaction reader (`coordinator/src/tributary/transaction.rs:341-353`) parses `accuser` and `faulty` as arbitrary nonzero `u16`s with no `<= n` bound at deserialization; the share bytes and blame proof are read via `EncryptedMessage::read`/`EncryptionKeyProof::read` — all untrusted inputs. An out-of-range index in the position used as `decryptor` panics on `enc_keys[&decryptor]`. The same panic exists at `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`), though reaching it additionally requires a valid DLEq proof.

Note: I could not fully verify whether the coordinator validates `accuser`/`faulty <= n` before the transaction reaches `VerifyBlame`; if such a bound exists upstream, the panic remains reachable through the public `AdditionalBlameMachine::blame` API, which accepts unchecked `Participant`s, but in-protocol reachability would depend on that gap. [4](#0-3) [5](#0-4) 

### Impact Explanation
Analogous to the CVE's "hang or frequently repeatable crash (complete DoS)": a single malformed blame accusation causes a deterministic panic in every processor/validator that evaluates it, denying availability of the blame-adjudication path (and the host process if panics are not caught). Since `InvalidDkgShare` is meant to slash faulty DKG participants, crashing on it also lets a malicious DKG participant evade adjudication. Impact is availability only; no secret leakage. [6](#0-5) 

### Likelihood Explanation
Reachability requires only attacker-chosen bytes: a nonzero `u16` participant index `> n`, a self-generated `EncryptedMessage` whose PoP is valid for that index (free to construct — the signer knows the ephemeral key), and any parseable `EncryptionKeyProof` (its validity is never checked before the panic). No valid DKG share, no collusion, and no threshold of participants is needed — matching the CVE's low-complexity, high-privilege-free crash profile (the original requires a privileged session; here the only "privilege" is ability to submit a blame transaction). Caveat: likelihood is reduced if the coordinator layer rejects participant indexes `> n` before dispatch, which I could not confirm. [3](#0-2) [7](#0-6) 

### Recommendation
Replace the indexing operations with checked lookups: in `decrypt_with_proof`, use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`, and in `blame_internal` use `self.commitments.get(&sender)` returning `sender` (or an error) on absence. Additionally, bound-check `sender`/`recipient` against `1 ..= n` in `AdditionalBlameMachine::blame`/`BlameMachine::blame` before use, and enforce `accuser <= n && faulty <= n` when parsing `InvalidDkgShare` transactions. [8](#0-7)

  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }
