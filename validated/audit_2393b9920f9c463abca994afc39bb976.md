### Title
Panic on truncated per-participant preprocess/signature-share vectors crashes the Bitcoin signing machine - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to CVE-2016-10349 (a heap-based buffer over-read crash on crafted input), `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` index into attacker-controlled `Vec<Preprocess>`/`Vec<SignatureShare>` values without checking their length. A participant who supplies a vector shorter than the number of transaction inputs causes an out-of-bounds indexing panic (Rust's memory-safe analog of an over-read crash), aborting the signing process.

### Finding Description
`TransactionMachine` produces one `AlgorithmMachine` per transaction input, so `self.sigs.len()` equals the number of inputs. In `sign`, per-participant preprocesses are supplied as `Vec<Preprocess<Secp256k1, ()>>` (read via `read_preprocess`, which reads one preprocess per input for *its own* machine — but peers send serialized bytes of their own choosing). The code then does `commitments[c].clone()` for `c` in `0 .. self.sigs.len()` with no length check. [1](#0-0) 

Likewise, `complete` calls `shares.remove(0)` once per input on each participant's `Vec<SignatureShare>`; an empty or truncated vector panics with "removal index (is 0) should be < len (is 0)". [2](#0-1) 

Nothing in the read path enforces that the vector length equals `self.sigs.len()`: `read_share`/`read_preprocess` deserialize a flat sequence of items per the reader, and the `HashMap<Participant, Vec<...>>` is taken as-is. [3](#0-2) 

### Impact Explanation
Any participant in a FROST Bitcoin signing session can send a preprocess or signature-share vector whose length is less than the number of transaction inputs. The honest processor indexing past the end of that vector panics, crashing the signing attempt (and the task handling it). Repeated across retries, this is a denial of service against the signing protocol — matching the CVE's crash/DoS impact class. It requires no privileges, no collusion, and no valid key material.

### Likelihood Explanation
Reachable by any unprivileged party able to submit preprocess/share bytes to a `TransactionSignMachine`/`TransactionSignatureMachine` (i.e., any cosigner in the threshold session). The panic is deterministic — a 0-element share vector or a 1-element preprocess vector for a 2-input transaction triggers it every time.

### Recommendation
Validate, in `sign` and `complete`, that every participant's inner vector has length exactly `self.sigs.len()` (return `FrostError`/`io::Error` on mismatch) before indexing. Similarly, reject extra-length vectors. Add the same length check to any coordinator-side deserialization that builds these `HashMap<Participant, Vec<...>>` values.

### Proof of Concept
```rust
// In TransactionSignMachine::sign (send.rs ~line 364):
// self.sigs.len() == 2 (a two-input transaction)
let mut commitments: HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>> = ...;
// Malicious participant P submits a Vec with only ONE preprocess instead of two:

// When c == 1: `commitments[1]` -> index out of bounds: the len is 1 but the index is 1
// Thread panics; signing session aborted.

// In TransactionSignatureMachine::complete (send.rs ~line 419):
// Malicious participant submits an empty share vector:

// `shares.remove(0)` -> "removal index (is 0) should be < len (is 0)" panic.
```

Both panics are reachable purely from peer-supplied serialized preprocess/share bytes, with no trust assumptions beyond participation in the signing set.
