Based on the investigation, the codebase shows a real asymmetry: this project has clearly hardened several `Path.join`-with-untrusted-data call sites using `resolveWithin` (e.g. the deep-link handler in `dispatcher.ts`) and even added dedicated tests for path-traversal safety (`clone-path-safety-test.ts`, `path-test.ts`). However, one call path that also consumes attacker-controlled path strings — the pull-request file list's double-click-to-open-in-editor flow — was not given the same treatment.

### Title
Unsanitized PR file path used to build external-editor open path allows traversal outside repository - (File: app/src/ui/open-pull-request/pull-request-files-changed.tsx)

### Summary
`PullRequestFilesChanged.onRowDoubleClick` passes the raw `file.path` (sourced from pull-request diff data, i.e., attacker-controlled content of a PR the user is reviewing) straight to the `onOpenInExternalEditor` callback, bypassing the `Path.join`+existence-check pattern used a few lines earlier in the same file, and bypassing the `resolveWithin` containment check that the app uses elsewhere for the exact same class of input (deep-link file paths).

### Finding Description
In `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, the context-menu handler builds a joined, existence-checked path before allowing "open in editor": [1](#0-0) 

But the double-click handler skips all of that and forwards the bare PR-provided path directly: [2](#0-1) 

That callback is wired to `App.onOpenInExternalEditor`, which joins the path onto the repository root with plain `Path.join` (no `resolveWithin`, no traversal check): [3](#0-2) 

Contrast this with the deep-link file-open handler, which treats an externally supplied path as hostile and explicitly guards it: [4](#0-3) 

and with the general-purpose `resolveWithin` helper that exists precisely to stop `..`/symlink escapes and is unit-tested for that purpose: [5](#0-4) 

The PR file list's `file.path` values originate from the pull request's changed-files data (a `CommittedFileChange` built from PR diff/API data for the reviewed PR, which can be opened from any fork/contributor), i.e., it is attacker-influenced content, exactly the class of "GitHub API object" input the task's valid-impact section calls out. `Path.join(repository.path, path)` does not prevent `path` values containing `../` segments from escaping the repository root, unlike `resolveWithin`.

### Impact Explanation
If a crafted PR contains a file entry whose path string includes traversal segments (e.g. `../../../../.ssh/id_rsa` or an OS-sensitive file), and the reviewer double-clicks that row in the "Files changed" pane of the PR viewer, `App.onOpenInExternalEditor` will compute a path outside the repository and hand it to the configured external editor via `dispatcher.openInExternalEditor(fullPath)`. This can cause an out-of-repository file to be opened/read, which may disclose file contents to the editor process (and, depending on the editor's own file-open handling, could have secondary effects). This satisfies the "file read outside the repo" impact criterion driven by an attacker-controlled GitHub API object (PR file list).

### Likelihood Explanation
The action requires only a normal user gesture already anticipated by the UI (double-clicking a file row while reviewing a PR); it does not require local/physical access, admin rights, prior malware, or leaked credentials. The main uncertainty — which I could not fully verify within the available tool budget — is whether GitHub's PR-files API/diff parsing on the Desktop side ever normalizes or rejects `..`-containing filenames before constructing `CommittedFileChange`; I was unable to locate the exact API-response-to-`CommittedFileChange` mapping code (`app/src/models/status.ts`, `app/src/lib/git/log.ts`) in the indexed content to confirm whether any sanitation happens upstream. Given that GitHub's own PR file listing generally reflects the literal path strings from the diff and Desktop's own `resolveWithin`/`sanitizeCloneName` additions show the team is aware this exact class of "path string from external data + `Path.join`" pattern is dangerous elsewhere, the missing guard here looks like a genuine gap rather than a covered case.

### Recommendation
In `PullRequestFilesChanged.onRowDoubleClick` (and anywhere else `file.path` from PR/API data reaches disk-path construction), resolve the path the same way the deep-link handler does — via `resolveWithin(repository.path, file.path)` — and refuse to invoke `onOpenInExternalEditor`/`openInExternalEditor` if resolution fails or returns a path outside the repository, mirroring the guard already present in `dispatcher.ts`.

### Proof of Concept
1. Attacker opens a pull request against the target repository (or a fork PR the victim reviews) containing a "file" whose path field is a traversal string, e.g. `../../../../.ssh/id_rsa` (or platform-appropriate sensitive-file traversal).
2. Victim opens the PR in GitHub Desktop's "Files changed" view (`PullRequestFilesChanged`), where `files` are populated from the PR's changed-file list.
3. Victim double-clicks the crafted row, triggering `onRowDoubleClick` → `this.props.onOpenInExternalEditor(file.path)`. [2](#0-1) 
4. `App.onOpenInExternalEditor` computes `Path.join(repository.path, path)` with no traversal check and opens the resulting path in the user's configured external editor. [3](#0-2) 
5. The editor opens the file outside the repository root, disclosing its content to the reviewer's editor/session — unlike the deep-link path, which is explicitly blocked by `resolveWithin` in `dispatcher.ts`.

  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
