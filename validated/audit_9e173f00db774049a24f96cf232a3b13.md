## Confirmed root cause

The `withdraw` function in `core/src/operator.rs` explicitly requires that the user's signature use `SinglePlusAnyoneCanPay` sighash: [1](#0-0) 

`SIGHASH_SINGLE|ANYONECANPAY` commits only to the input being spent and its *corresponding* output (output index 0, the payout output). It does **not** commit to the OP_RETURN output that carries the operator's x-only pubkey, which `create_payout_txhandler` appends *after* the user-signed input/output pair: [2](#0-1) 

The remaining funding for the payout (the actual BTC value fronted to the withdrawing user) is added afterward by the operator's wallet via RBF/`fund_raw_transaction`, using `ANYONECANPAY`-compatible funding so any extra input can be appended without invalidating the user's presigned input: [3](#0-2) 

Because the OP_RETURN output is unsigned/uncommitted by the withdrawing user, **whoever actually funds and broadcasts the completed payout transaction can put an arbitrary x-only pubkey in the OP_RETURN**, since nothing cryptographically ties that OP_RETURN pubkey to the party whose UTXO paid for the withdrawal.

On the verifier side, `update_finalized_payouts` reads the operator identity purely from this unauthenticated OP_RETURN field, with no check that the tx inputs are actually attributable/controlled by that operator: [4](#0-3) 

That value is persisted as `payout_payer_operator_xonly_pk` and later used to select who is entitled to reimbursement: [5](#0-4) 

The named operator's own `PayoutCheckerTask` polls for unhandled payouts keyed on its own xonly pubkey, and if it finds one (because someone else embedded its pubkey in the OP_RETURN), it will proceed to run `handle_finalized_payout`, which only validates that the DB-recorded payer pubkey equals the local operator's key — a check that is trivially satisfied because the attacker chose to write that key: [6](#0-5) [7](#0-6) 

This kicks off the full kickoff/reimburse flow (`get_reimbursement_txs` / kickoff / Reimburse tx), which pays the named operator back from its own round/collateral UTXOs for a payout it never funded: [8](#0-7) 

### Title
Unauthenticated OP_RETURN operator identity in payout transaction allows misattributing bridge reimbursement to an operator who never funded the withdrawal - (File: core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs, core/src/operator.rs)

### Summary
The party that actually funds a Bitcoin withdrawal payout (via RBF-added inputs) and the operator later credited with — and reimbursed for — that payout are bound only through an OP_RETURN field that is not covered by the user's presigned `SinglePlusAnyoneCanPay` signature. Anyone who completes and broadcasts the payout transaction can write any operator's x-only pubkey into that OP_RETURN output, causing the bridge to attribute the withdrawal (and its reimbursement entitlement) to an operator that never fronted any funds.

### Finding Description
The withdrawal/payout protocol is designed so multiple operators can race to front the same presigned user withdrawal: the user signs only the payout output with `SIGHASH_SINGLE | ANYONECANPAY` (`core/src/operator.rs:637`), which leaves every other part of the transaction — including the OP_RETURN carrying the operator's x-only pubkey appended in `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:418,432`) — completely unconstrained by any signature. The BTC that actually pays out the withdrawal is supplied afterward through wallet/RBF funding (`core/src/operator.rs:639-674`, `crates/clementine-tx-sender/src/rbf.rs`).

On the bridge side, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) determines "who paid" purely by parsing this OP_RETURN field from the confirmed on-chain payout tx — there is no verification that the named operator's key/UTXO set actually funded the transaction's inputs. The parsed value is written straight into `withdrawals.payout_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`), and this DB column is later used (a) by `get_first_unhandled_payout_by_operator_xonly_pk` for a named operator's own `PayoutCheckerTask` to discover "its" unhandled payout, and (b) by `validate_payer_is_operator` to authorize that operator's own reimbursement flow, which merely checks that the recorded payer key equals the local signer's key — a self-referential check with no independent proof that the local operator actually spent any of its own BTC.

The binding that should hold is:
`operator credited for reimbursement == operator whose funds actually left the outgoing UTXO`
but the protocol instead enforces only:
`operator credited for reimbursement == whatever xonly_pk value someone wrote in an unsigned OP_RETURN output`

These are not equal, and any actor able to complete/broadcast a payout transaction (an operator's own node completing another operator's withdrawal race, or a malicious operator/relay who alters the OP_RETURN before broadcast) can break the binding.

### Impact Explanation
This falls under the Critical impact category "an operator reimbursed for a payout it never funded." The victim operator whose pubkey is misappropriated will have `PayoutCheckerTask` (`core/src/task/payout_checker.rs`) automatically discover the fraudulent record and proceed through `handle_finalized_payout` → kickoff → `get_reimbursement_txs`/Reimburse (`core/src/operator.rs:839-885`, `2087-2150`), causing that operator's round/collateral UTXOs to pay the Reimburse output to itself for a withdrawal it never funded — while the entity who actually fronted the BTC receives nothing back through the protocol. This is direct bridge-value misattribution and a broken custody/attribution binding.

### Likelihood Explanation
The attack requires no privileged role: any unprivileged party capable of constructing and broadcasting a valid Bitcoin transaction that spends the presigned withdrawal input (satisfying the `SinglePlusAnyoneCanPay` constraint on output 0) can freely choose the OP_RETURN operator pubkey, since it is entirely outside the signed message. The design already anticipates multiple parties racing to complete the same presigned payout (hence `ANYONECANPAY`), which increases the practical opportunity for this misattribution.

### Recommendation
Bind the OP_RETURN operator-identity commitment to the actual funding of the transaction, e.g.:
- Have the funding operator sign (with their own key, over a sighash that covers the OP_RETURN output) an attestation that the OP_RETURN pubkey matches the operator whose UTXOs fund the transaction, and have `update_finalized_payouts`/`handle_finalized_payout` verify that attestation rather than trusting the raw OP_RETURN bytes; or
- Require the OP_RETURN output (or the additional funding input added via RBF) to be spendable only by/attributable to the same key referenced in the OP_RETURN (e.g., require the first additional funding input's controlling key to match the OP_RETURN pubkey), so the party who actually pays is cryptographically the same as the party credited.

### Proof of Concept
1. Operator A creates and broadcasts (via RBF-funded, `ANYONECANPAY`-signed) the payout transaction for a pending withdrawal, funding it entirely from its own wallet UTXOs, but — instead of writing its own key — writes Operator B's x-only pubkey into the OP_RETURN output (`core/src/builder/transaction/operator_reimburse.rs:407-436`); this is trivial because the OP_RETURN output is outside the user's signed sighash.
2. The transaction confirms on Bitcoin. Verifiers' `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses the OP_RETURN and records `payout_payer_operator_xonly_pk = B` in the `withdrawals` table (`core/src/database/verifier.rs:198-251`), even though B never signed or funded anything.
3. Operator B's `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-79`) finds this record via `get_first_unhandled_payout_by_operator_xonly_pk(B)` and calls `handle_finalized_payout`, whose only authenticity check (`validate_payer_is_operator`, `core/src/operator.rs:1686-1739`) is that the DB-recorded payer equals B's own key — which is true because A wrote it that way.
4. B's node proceeds through the kickoff/reimburse flow (`get_reimbursement_txs`, `core/src/operator.rs:2087-2150`), causing B's round/collateral funds to be paid out to B via the Reimburse transaction, crediting B for a withdrawal it never funded, while A (the actual funder) receives no reimbursement through the protocol.

        let (payout_blockhash, kickoff_txid) = self

            .await?;

        let mut current_round_idx = self.db.get_current_round_index(Some(&mut dbtx)).await?;

        let mut txs_to_send: Vec<(TransactionType, Transaction)>;

        loop {
            txs_to_send = self
                .get_next_txs_to_send(
                    Some(&mut dbtx),
                    &mut deposit_data,
                    payout_blockhash,
                    kickoff_txid,
                    current_round_idx,
                )
                .await?;

                // if no txs were returned, and we advanced the round in the db, ask for the next txs again
                // with the new round index
                let round_idx_after_operations =
                    self.db.get_current_round_index(Some(&mut dbtx)).await?;
                if round_idx_after_operations != current_round_idx {
                    current_round_idx = round_idx_after_operations;
                    continue;
                }
            }
            break;
        }

        dbtx.commit().await?;
        Ok(txs_to_send)
    }

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
