### Title
Deterministic CachedPreprocess reuse across distinct messages leaks the signer's secret share (ROS-style nonce reuse) - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug class is "replacing an object clears/migrates its associated metadata, so the stale object is later operated on with the wrong context." The analog in Serai: `SigningProtocol::preprocess_internal` replaces a freshly generated preprocess machine with a machine rebuilt from a **cached, deterministic seed** (`AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed`). Every signing operation under the same `context` therefore reuses the identical FROST nonces `(d, e)`, while the "new" machine is used to sign potentially different messages. When multiple distinct messages are signed under one context (e.g., `DkgConfirmer` confirming multiple `KeyPair`s under one `attempt`, or `share()` followed by `complete()`/`share()` with different inputs), the published signature shares form a linear system that leaks the signer's interpolated secret share.

### Finding Description
In `preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:100-148`), the coordinator stores a 32-byte seed in `CachedPreprocesses` keyed only by `context`, and rebuilds the sign machine via `from_cache`. `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`) derives nonces deterministically from that seed:

```rust
// crypto/frost/src/sign.rs
let mut rng = ChaCha20Rng::from_seed(*seed.0);
let (nonces, commitments) = Commitments::new::<_>(&mut rng, ...);
```

So every machine reconstructed for the same `context` has the same `(d, e)` nonce pair. `DkgConfirmer` (`signing_protocol.rs:252-327`) sets `context = (b"DkgConfirmer", self.attempt)` and invokes `share_internal` — which calls `preprocess_internal` then `machine.sign(preprocesses, msg)` — from both `share()` and `complete()`, with `msg = set_keys_message(...)` depending on the supplied `key_pair` and `removed` set. Each emitted share is `s = d + rho·e + λ·x·c` (`sign.rs:385-398`: `actual = base + binding_factor·actual`, then `sign_share`), where `rho` binds `group_key`, `hash_msg(msg)`, and the preprocesses challenge (`sign.rs:362-371`), and `c` is the per-message challenge.

For each *distinct* message signed under the same `attempt` context, the signer publishes a share with the same underlying `d, e` but different publicly computable `rho_i, c_i`. With three or more distinct messages, the system

```
s_i = d + rho_i·e + (λ·c_i)·x
```

is a linear system in the three unknowns `(d, e, x)` — solvable by anyone who observes the shares, recovering `x`, the validator's interpolated MuSig secret share. `share()` returns shares that are broadcast through tributary transactions, so the inputs needed are all public.

### Impact Explanation
Recovery of `x` (the validator's interpolated secret share for the set-confirmation MuSig) — combined with the other participants' public verification shares — enables forgery of DKG-confirmation/set-keys signatures attributed to that validator, and contributes to threshold key compromise. This is the exact failure the `CachedPreprocess` documentation warns about ("Reuse will enable third-party recovery of your private key share", `crypto/frost/src/sign.rs:83-92`), realized by the coordinator itself rather than by integrator misuse: the cache is keyed only by `context`, not by the message being signed, so distinct-message signings silently reuse nonces.

### Likelihood Explanation
Requires ≥3 distinct `set_keys_message`s (different `key_pair` or `removed` set) to be signed under one `(DkgConfirmer, attempt)` context, or a `share()`/`complete()` sequence over differing inputs — plausible whenever a set confirms keys for multiple networks or retried confirmations occur within one attempt. The shares are broadcast publicly. I could not fully verify within the available iterations how many distinct `key_pair` confirmations occur per attempt in `handle.rs`, so likelihood is contingent on multiple confirmations per attempt being reachable; however, no mechanism prevents it, and `share()`+`complete()` already double-invoke `share_internal`.

### Recommendation
Key `CachedPreprocesses` by the full signing context *including a digest of the message*, or delete the cached seed upon first `sign()` so any subsequent `share_internal` call under the same context generates a fresh seed (or fails). Alternatively, have `DkgConfirmer` cache the produced `AlgorithmSignatureMachine`/`share` after the first `share()` and have `complete()` reuse that share rather than re-running `share_internal`, guaranteeing a nonce is consumed exactly once per message.

### Proof of Concept
1. Under `context = (b"DkgConfirmer", attempt)`, the coordinator calls `share(key_pair_A)` → emits `s_1 = d + rho_1·e + λ·x·c_1` (publicly broadcast).
2. It later calls `share`/`complete` for `key_pair_B` and `key_pair_C` under the same attempt → emits `s_2`, `s_3` with the same `d, e` but known distinct `rho_2, rho_3, c_2, c_3` (rho/c recomputed by any observer from `group_key`, `hash_msg(msg)`, preprocesses per `sign.rs:362-398`).
3. Solve the 3×3 linear system over `C::F` for `(d, e, x)`; recover the validator's secret share `x`. Verify via `G·x` matching the interpolated verification share from `ThresholdKeys::view`.
