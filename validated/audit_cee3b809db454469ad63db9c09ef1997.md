**Rationale:**

The referenced pseudocode block (with the `update_attested_period == state_period` equality-skip logic) exists only in the documentation file [1](#0-0) , which is a conceptual/spec description, not the actual production verifier logic.

The real production implementation, `verify_sync_committee_attestation` in `modules/consensus/sync-committee/verifier/src/lib.rs`, uses a different gating mechanism entirely. State transitions involving `next_sync_committee` are gated strictly by `should_have_sync_committee_update(state_period, update_signature_period)`, which only returns `true` when `signature_period == state_period + 1` [2](#0-1) .

When this condition is false (i.e., the update does not cross a period boundary), the code takes the `else` branch, which preserves `current_sync_committee` and `next_sync_committee` unchanged via `..trusted_state`, regardless of whether a `sync_committee_update` was supplied and regardless of whether its merkle branch validated [3](#0-2) . There is no equality-check-skip path that lets a same-period update overwrite the trusted `next_sync_committee` — the update result is simply discarded in that branch.

When the condition is true (crossing a boundary), the code independently enforces that `attested_period == update_signature_period` [4](#0-3) , requires `sync_committee_update` to be `Some` (erroring otherwise) [5](#0-4) , and unconditionally verifies the merkle branch of `next_sync_committee` against `update.attested_header.state_root` before it can be committed [6](#0-5) . The `attested_header` itself must also pass the finality-branch check tying it to a BLS-signed, supermajority-attested header [7](#0-6) .

Since a correctly-sized `next_sync_committee_branch` alone cannot forge a valid merkle proof against a genuine `state_root` from a genuinely-signed attested header, and the branch structure/length is independently validated at the top of the function [8](#0-7) , there is no bypassable equality check in the actual implementation for an attacker to exploit. The described flaw applies to outdated spec pseudocode, not the deployed Rust verifier.

	// When the update crosses a sync-committee period boundary, require the attested
	// header to be in the same (new) period as the signature. Otherwise the attested
	// state has not yet rotated and its `next_sync_committee` field still holds
	// `committee_{state_period+1}` — i.e. the committee we are already trusting as
	// `next_sync_committee` — instead of the genuinely upcoming `committee_{state_period+2}`.
	// Accepting such an update would stage the previous-period committee again and brick
	// future updates once the chain enters `state_period + 2`.
	if should_have_sync_committee_update(state_period, update_signature_period) {
		let attested_period = compute_sync_committee_period_at_slot::<C>(update.attested_header.slot);
		if attested_period != update_signature_period {
			Err(Error::InvalidUpdate(
				"Attested header is not in the same sync-committee period as the signature".into(),
			))?
		}
	}
