## Title
IntentGatewayV2 (Tron) escrows the nominal input amount instead of the actual token balance received, allowing fee-on-transfer/rebasing tokens to under-collateralize `_orders` and drain shared escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the `_orders[commitment][token]` escrow ledger using the **requested** input amount (minus protocol fee), never checking what the contract actually received from `safeTransferFrom`/native transfer. The mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was explicitly patched to snapshot balances before/after transfer and use the *actual received* amount for both the commitment and the escrow credit (see the "Phase 1: Transfer tokens and record actual received amounts" comment and the `testPlaceOrder_FeeOnTransferToken_*` tests), but the Tron contract still uses the old, unguarded pattern. This is the same broken invariant as the external WSX report: the contract assumes the ledgered/reported amount matches what was actually transferred in, with no balance validation.

### Finding Description
In `placeOrder` (evm/tron/contracts/apps/IntentGatewayV2.sol, non-predispatch branch): [1](#0-0) 
the code does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
```
`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the caller-requested amount) minus the protocol fee bps — it is never reconciled against the gateway's actual pre/post balance delta: [2](#0-1) 

Contrast this with the corrected mainline contract, which explicitly measures `balanceOf` before and after the transfer and mutates the recorded amount to the actual delta before it's ever used for the commitment or escrow credit: [3](#0-2) 

If `token` is a fee-on-transfer, rebasing, or otherwise non-standard ERC-20, the Tron gateway's actual token balance after `placeOrder` is strictly less than the sum of what `_orders[*][token]` claims across all outstanding commitments for that token. Because `_orders` is keyed per-commitment but the underlying ERC-20 balance is a single shared pool across all commitments of that token, this desync is a real accounting break, not a per-order cosmetic issue.

### Impact Explanation
`withdraw()` (called from `fillOrder`/`cancelOrder`/`onAccept`) pays out based purely on the ledgered `_orders[commitment][token]` value: [4](#0-3) 
Since the ledger is inflated relative to the actual token balance held by the contract, the first orders to be filled/cancelled/refunded for a given fee-on-transfer token can successfully withdraw their (inflated) share, exhausting the real balance and leaving later, legitimately-escrowed orders for that same token unable to be filled or refunded — a direct loss of user funds for those orders. This is fund loss/lock triggered purely by normal use of `placeOrder` with a standard-looking-but-fee-charging ERC-20, requiring no relayer, prover, or admin compromise.

### Likelihood Explanation
Any unprivileged user can trigger this by calling the public `placeOrder` entrypoint with a fee-on-transfer or rebasing ERC-20 as an input token — a well-known and common token category (many deflationary/tax tokens on Tron/EVM chains). No proof forgery, malicious relayer, or governance action is needed; it happens deterministically the first time such a token is used through the Tron gateway.

### Recommendation
Apply the same fix already implemented in `evm/src/apps/IntentGatewayV2.sol`: snapshot `balanceOf(address(this))` before and after each `safeTransferFrom` (and the native-token equivalent), mutate `order.inputs[i].amount` to the actual received delta, and only then compute `reducedInputs`/the commitment/the `_orders` credit from that verified amount. Port this Phase-1 balance-snapshot logic into `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a 1%-fee-on-transfer ERC-20 as an allowed input token, `protocolFeeBps = 0` for simplicity.
2. User A calls `placeOrder` with `inputs[0].amount = 1000`. The gateway's actual received balance is `990` (1% fee taken), but `_orders[commitmentA][token] = 1000` (no protocol fee reduction applied, so `reducedInputs == order.inputs`).
3. User B similarly calls `placeOrder` with `inputs[0].amount = 1000`; gateway receives `990` more (total actual balance now `1980`), but ledger now totals `_orders[commitmentA][token] + _orders[commitmentB][token] = 2000`.
4. A solver fills/cancels order A: `withdraw()` transfers `1000` tokens out (per the ledger) — succeeds because actual balance (1980) still covers it, leaving `980` actual balance but `1000` still ledgered for order B.
5. When order B is filled/cancelled, `withdraw()` attempts to transfer `1000` tokens but the contract only holds `980` (further reduced by the outgoing transfer's own fee-on-transfer deduction) — the transfer either reverts (locking user B's funds indefinitely) or, on chains/tokens without revert-on-failure semantics, silently under-pays user B, both of which are direct fund-loss/lock outcomes traceable to escrowing the unverified nominal amount instead of the actual received balance.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
