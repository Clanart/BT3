Based on my review of the actual code, there **is** a real, confirmable reward-accounting flaw, but it is narrower than the invariant described in the question (the `totalVlMgpInVote` / `sum(userTotalVotedInVlmgp)` bookkeeping in `vote()` is actually internally consistent — every `totalUserVote` delta is applied symmetrically to both the per-user and the global counter at lines 208-219). The real issue is in the reward-per-token mechanics feeding `BribeRewardPool`, not in the vote-accounting invariant itself.

### Title
Instant, non-time-weighted `rewardPerTokenStored` update lets `vote()`+`castVotes()` in one call let a same-block voter capture a share of bribes they did not earn - ([File: wombat/WombatBribeManager.sol], [File: rewards/BaseRewardPoolV2.sol])

### Summary
`voteAndCast()` calls `vote()` (which calls `BribeRewardPool.stakeFor`, immediately increasing the caller's `_balances`/`totalSupply`) and then `castVotes()` (which triggers bribe harvesting and reward forwarding) in the same transaction. Because `BaseRewardPoolV2._provisionReward` updates `rewardPerTokenStored` as an instantaneous snapshot proportional to `totalStaked()` at the moment the reward is queued — with no time-weighted accrual (no duration/rewardRate model) — a voter whose stake is added immediately before the harvest is included in the `totalStaked()` denominator and thus captures pro-rata bribe rewards for that entire harvested epoch despite having just voted.

### Finding Description
`vote()` credits a voter's share of a pool's `BribeRewardPool` synchronously via `stakeFor`: [1](#0-0)  This runs the `updateRewards` modifier which snapshots `rewardPerTokenStored` for that account at its *current* value before adding stake, then increases `totalSupply`/`_balances`: [2](#0-1) 

The core reward math has no time-weighting: `_provisionReward` adds the newly harvested amount straight into `rewardPerTokenStored`, scaled by `totalStaked()` observed at that instant: [3](#0-2)  Unlike a Synthetix-style `rewardRate`/`periodFinish` design that streams rewards over a duration, this model treats the entire bribe amount as earned by whoever is staked the instant `_provisionReward` runs, regardless of how long they've been staked.

`voteAndCast()` chains `vote()` then `castVotes()` atomically: [4](#0-3)  `castVotes()` triggers `wombatStaking.vote(...)`, which harvests pending bribes, before the manager forwards fee amounts to the caller: [5](#0-4)  I was not able to fully trace, within the indexed context, the exact internal call in `WombatStaking.vote(...)` that invokes `queueNewRewards`/`donateRewards` on each pool's `BribeRewardPool` to confirm the precise per-pool bribe amount forwarded into `rewardPerTokenStored` — this detail lives in `wombat/WombatStaking.sol`, which was only partially indexed. That said, the architecture (harvest-then-distribute-to-rewarder pattern typical of this codebase) combined with the confirmed instant-snapshot math in `BaseRewardPoolV2` is sufficient to establish the reward-sniping mechanism.

Importantly, the `totalVlMgpInVote`/`userTotalVotedInVlmgp` global reconciliation invariant named in the question is **not** broken by this: every branch of `vote()` updates both counters symmetrically by the same `totalUserVote` [6](#0-5) , so duplicate/offsetting deltas net out correctly and cannot desynchronize these two values.

### Impact Explanation
This is a reward-sniping / front-running-the-distribution issue: an attacker who already holds locked vlMGP voting power can call `vote()` (or `voteAndCast()`) immediately before a keeper's `castVotes()`/harvest, be counted in `totalStaked()` at the moment `rewardPerTokenStored` is bumped, and thus claim a pro-rata share of bribes that accrued over the whole preceding epoch without having voted during that epoch. This dilutes/steals the *unclaimed yield* portion that honest long-standing voters would otherwise have received — not the principal (vlMGP or LP stake) of other users. This does not match "Direct theft of user funds" (principal) as cleanly as it matches "theft of unclaimed yield."

### Likelihood Explanation
Exploitation requires the attacker to (a) hold/lock enough vlMGP to be able to submit a nonzero vote (real capital, but no privileged role), and (b) time their `vote()`/`voteAndCast()` call to land in the block immediately preceding a keeper's `castVotes()` call, which is realistically front-runnable since `castVotes()` is a public, permissionless, gas-incentivized function whose calls are visible in the mempool. This is repeatable every epoch/cast cycle.

### Recommendation
Introduce time-weighted reward accrual (e.g., a `rewardRate`/`periodFinish`-based streaming model, or snapshotting eligible stake at the start of the epoch rather than at harvest time) in `BaseRewardPoolV2`/`BribeRewardPool`, and/or enforce a minimum bonding period between when a vote is registered (`stakeFor`) and when it becomes eligible to share in a bribe harvest, so that `rewardPerTokenStored` updates reflect balances that were actually staked throughout the period the bribe was earned.

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatBribeManager`, `BribeRewardPool`, and mock `WombatStaking`/`voter` contracts that simulate a pending bribe of amount `R` for a pool.
2. User A locks vlMGP and calls `vote()` for the pool at time `T0`, before any bribe accrues.
3. Advance time so bribe `R` accrues to the pool's bribe contract.
4. In one block/transaction, Attacker calls `vote()` (staking the same amount as User A) immediately followed (front-run or same tx via `voteAndCast`) by `castVotes()` which harvests `R` into the rewarder via `_provisionReward`.
5. Assert `earned(Attacker, rewardToken)` == `earned(UserA, rewardToken)` even though Attacker staked for 0 elapsed epoch time versus User A's full epoch — demonstrating the unearned yield capture.
6. Confirm separately that `totalVlMgpInVote` and `sum(userTotalVotedInVlmgp)` remain equal in both a single combined call and split calls (this part of the invariant will hold, confirming that specific claim in the question is not the actual bug).

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
