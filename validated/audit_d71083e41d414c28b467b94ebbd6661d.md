### Title
Bridge ERC721 delivery uses `transferFrom` instead of `safeTransferFrom`, so the destination contract is never notified of incoming NFTs - (File: contracts/service_chain/bridge/BridgeTransferERC721.sol)

### Summary
`BridgeTransferERC721.handleERC721Transfer` delivers a cross-chain NFT to a user-controlled destination address using the raw ERC721 `transferFrom` call instead of `safeTransferFrom`. This mirrors the reported `ERC223BeamToken.transferFrom` bug class: the transfer function moves the asset but never checks whether the recipient is a contract and never invokes the recipient's receiver hook (`onERC721Received`), silently breaking the "notify the receiver" guarantee that other parts of the same contract (and the ERC721 standard) rely on.

### Finding Description
`handleERC721Transfer` is the function that finalizes an incoming cross-chain NFT transfer once it has been voted on by bridge operators. When the bridge is not in mint/burn mode, it releases custody of the NFT with: [1](#0-0) 

`_to` originates from the original request submitted on the source chain via `requestERC721Transfer`, which is callable by any unprivileged token holder with an arbitrary destination address: [2](#0-1) 

The underlying `ERC721.transferFrom` implementation used by the bundled OpenZeppelin v2 library only updates ownership state and emits a `Transfer` event; it does **not** call `_checkOnERC721Received`. Only `safeTransferFrom` performs that check and invokes the recipient hook: [3](#0-2) 

Notably, the bridge's own *incoming* 1-step deposit path explicitly relies on an equivalent notification pattern - the bridge implements `onERC721Received`/`onERC20Received` receiver callbacks itself and requires callers to invoke them for correct internal accounting: [4](#0-3) [5](#0-4) 

However, on the *outgoing* delivery path, the bridge does not extend the same notification guarantee to third-party contracts that are meant to receive the bridged NFT (e.g., another bridge hop, an escrow/marketplace, or a vault contract that only credits ownership inside its own `onERC721Received` callback). Because `transferFrom` is used, such a contract will have its on-chain NFT balance changed without ever being informed, exactly the "receiver contract is not notified" root cause identified in the external report for `ERC223BeamToken.transferFrom`.

### Impact Explanation
If `_to` is a smart contract that gates internal accounting on the ERC721 `onERC721Received` callback (a widely used and recommended pattern to prevent NFTs from becoming unrecoverable), the NFT will be transferred out of the bridge's custody but the destination contract will never register the deposit. The asset becomes stuck/inaccessible inside a contract that has no code path to recognize or forward it, resulting in a genuine, unrecoverable loss of the bridged asset for the end user. This satisfies the "value movement to an unintended/unrecoverable destination" bar, at Medium severity — consistent with the severity rating given to the original `ERC223BeamToken.transferFrom` report.

### Likelihood Explanation
The destination address `_to` is fully attacker/user-controlled at `requestERC721Transfer` time on the source chain and is never restricted to EOAs or receiver-hook-aware contracts. Any relayed/voted bridge request (a routine, expected operation, not requiring any privileged compromise) that targets a contract implementing the standard "deposit only via safe transfer" pattern will trigger the bug. No malicious validator/operator behavior is required — normal bridge operation with a legitimate but hook-dependent recipient contract is sufficient.

### Recommendation
Replace the unsafe `transferFrom` with `safeTransferFrom` in `handleERC721Transfer` (and any other outbound transfer paths in the bridge/service-chain contracts using raw `transferFrom`), so that recipient contracts are correctly notified via `onERC721Received`, consistent with the notification behavior already implemented for the mint/burn branch and for inbound deposits.

### Proof of Concept
1. Deploy a "vault" contract that implements `IERC721Receiver.onERC721Received` and only records an NFT as deposited when that callback fires (a standard, common pattern).
2. On the source chain, call `requestERC721Transfer(tokenAddress, vaultAddress, tokenId, extraData)` — reachable by any unprivileged token holder. [2](#0-1) 
3. Bridge operators vote and relay the request; `handleERC721Transfer` executes on the destination chain in non-mint/burn mode. [1](#0-0) 
4. Ownership of `tokenId` moves to `vaultAddress` (verifiable via `ownerOf`), but `vaultAddress.onERC721Received` is never invoked, so the vault's internal accounting never recognizes the deposit — the NFT is now permanently stranded in a contract with no code path to move it out.

    function transferFrom(address from, address to, uint256 tokenId) public {
        //solhint-disable-next-line max-line-length
        require(_isApprovedOrOwner(msg.sender, tokenId), "ERC721: transfer caller is not owner nor approved");

        _transferFrom(from, to, tokenId);
    }

    /**
     * @dev Safely transfers the ownership of a given token ID to another address
     * If the target address is a contract, it must implement `onERC721Received`,
     * which is called upon a safe transfer, and return the magic value
     * `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`; otherwise,
     * the transfer is reverted.
     * Requires the msg.sender to be the owner, approved, or operator
     * @param from current owner of the token
     * @param to address to receive the ownership of the given token ID
     * @param tokenId uint256 ID of the token to be transferred
     */
    function safeTransferFrom(address from, address to, uint256 tokenId) public {
        safeTransferFrom(from, to, tokenId, "");
    }

    /**
     * @dev Safely transfers the ownership of a given token ID to another address
     * If the target address is a contract, it must implement `onERC721Received`,
     * which is called upon a safe transfer, and return the magic value
     * `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`; otherwise,
     * the transfer is reverted.
     * Requires the msg.sender to be the owner, approved, or operator
     * @param from current owner of the token
     * @param to address to receive the ownership of the given token ID
     * @param tokenId uint256 ID of the token to be transferred
     * @param _data bytes data to send along with a safe transfer check
     */
    function safeTransferFrom(address from, address to, uint256 tokenId, bytes memory _data) public {
        transferFrom(from, to, tokenId);
        require(_checkOnERC721Received(from, to, tokenId, _data), "ERC721: transfer to non ERC721Receiver implementer");
    }
