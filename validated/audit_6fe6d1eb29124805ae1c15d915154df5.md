### Title
`ThresholdKeys::read` accepts identity verification shares and inconsistent key sets, bypassing the identity check applied everywhere else - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes every `verification_shares` entry with `Ciphersuite::read_G`, which performs canonical-encoding and point-validity checks but deliberately does *not* reject the identity point (crypto/ciphersuite/src/lib.rs:91-101). Every other ingress point that reads attacker-controlled points — `Curve::read_G` used by `Commitments::read`/`read_preprocess`, `ReceivedOutput`, etc. — adds an explicit `is_identity` rejection (crypto/frost/src/curve/mod.rs:124-131). The resulting `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) performs no identity check and no consistency check between `secret_share` and `verification_shares`, so a subexpression — the per-participant verification share — silently skips the identity "sandbox" check that the rest of the codebase enforces.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:620-630) loops `for l in (1 ..= n).map(Participant)` and inserts `<C as Ciphersuite>::read_G(reader)?` results directly into `verification_shares`. `Ciphersuite::read_G` only checks canonicality, so `G::identity()` is accepted. `ThresholdKeys::new` then validates only the map length and that indexes `<= n`, and computes

```
group_key = Σ_{i ∈ 1..=t} verification_shares[i] * interpolation_factor(i, 1..=t)
```

(crypto/dkg/src/lib.rs:376-378). An identity verification share contributes `0`, so the group key silently drops that participant's share. Neither `new` nor `view` ever checks `verification_shares[i] == G * secret_share_i`, even for `i == params.i()`.

Analogously to CVE-2019-10400 (where a subexpression inside a non-assignment increment/decrement escaped the security transformation), here a verification share — a value that only ever participates as a summand/indexed lookup rather than as the "primary" secret — escapes the identity rejection that the FROST pipeline applies to every other externally supplied point.

### Impact Explanation
An unprivileged party that can feed bytes to `ThresholdKeys::read` can produce two distinct broken states:

1. **Unspendable group key / deterministic signing failure.** Set `verification_shares[k] = identity` for some `k ∈ 1..=t` while keeping real nonzero shares. `group_key` then equals the secret excluding `k`'s contribution, yet `view()`/`sign()` still interpolate `k`'s real share. Every produced signature fails `algorithm.verify` and every share fails `verify_share`, so the key set is permanently unusable — funds addressed to that `group_key` are unspendable and `complete` can only ever return `InternalError` (crypto/frost/src/sign.rs:491-494).
2. **Degenerate signing set.** Set `verification_shares[k] = identity` *and* `secret_share = 0` for `k`. The key set is now fully self-consistent: `k` produces the trivially forgeable share `s_k = bound nonce` (no secret involved), and `verify_share` passes against an identity verification share. The effective multisig excludes `k` while `k` is still counted toward `t`, so a key set advertising `t-of-n` is really `(t-1)-of-(n-1)` — participant `k` is cryptographically absent yet occupies a threshold slot and can be impersonated by anyone who knows the public nonce commitments.

Both are reachable purely from untrusted bytes fed to `ThresholdKeys::read`, with no cooperation from other participants.

### Likelihood Explanation
`ThresholdKeys` serialization is explicitly exposed as a read API for persisted/transferred key material (the FROST test suite itself reconstructs keys via this format, crypto/frost/src/tests/vectors.rs:118-131). Any deployment that loads `ThresholdKeys` from storage or a wire format not produced by the local DKG — backups, key recovery, coordinator-supplied material — deserializes attacker-influenceable bytes. The bug requires no broken RNG, no collusion, and no race; it is a pure input-validation gap. Likelihood is gated by whether an integrator treats serialized `ThresholdKeys` as untrusted input, hence Medium rather than High.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:361-365), reject identity verification shares (`if bool::from(share.is_identity()) { Err(...) }`), mirroring `Curve::read_G`. Additionally validate `verification_shares[&params.i()] == C::generator() * secret_share` so the holder's own share is bound to the key set, catching both inconsistent and degenerate encodings at deserialization time.

### Proof of Concept
```rust
// Assume honest keys produced by key_gen(...) for t=2, n=3, our i=1.
let mut buf = honest_keys.serialize().as_ref().to_vec();
// Layout: id_len || id || t || n || i || interp || secret_share || n * ver_share
// Overwrite the verification share for participant k=2 with the canonical
// encoding of C::G::identity() (e.g., 32 zero-ish identity bytes per to_bytes).
let share_start = /* offset of 2nd verification share */;
buf[share_start .. share_start + C::G::Repr::LEN].copy_from_slice(
  C::G::identity().to_bytes().as_ref()
);

// This succeeds today: Ciphersuite::read_G accepts the identity point.
let evil = ThresholdKeys::<C>::read::<&[u8]>(&mut buf.as_ref()).unwrap();

// group_key silently excludes participant 2's share.
assert_ne!(evil.group_key(), honest_keys.group_key());

// Signing with this key set can never produce a valid signature, and
// `complete` degrades to FrostError::InternalError; funds sent to
// evil.group_key() are unspendable. With secret_share also set to 0 and
// verification_shares[1] = identity, the key set is consistent yet
// participant 1's signature share is forgeable by anyone.
```
