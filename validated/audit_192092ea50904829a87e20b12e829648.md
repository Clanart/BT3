### Title
Unbounded Sequential Per-Index RPC Loop in `collect_withdrawal_utxos` / `collect_deposit_move_txids` Stalls Verifier Block Processing, Enabling Missed Challenge Windows — (File: `core/src/citrea.rs`)

---

### Summary

`collect_withdrawal_utxos` and `collect_deposit_move_txids` in `core/src/citrea.rs` iterate over every new Citrea deposit/withdrawal index with **one sequential, blocking RPC call per item**. These functions are called synchronously inside `handle_finalized_block` for every finalized Bitcoin block. An attacker who registers a large number of withdrawals on the permissionless Citrea bridge contract can make each Bitcoin block take arbitrarily long to process, starving the verifier's state machine of `dispatch_lcp_processed` events and preventing watchtower challenges from being sent within the on-chain timelock window.

---

### Finding Description

**Root cause — `collect_withdrawal_utxos` (and the identical `collect_deposit_move_txids`):**

```rust
// core/src/citrea.rs  lines 470-494
loop {
    let withdrawal_utxo = self
        .contract
        .withdrawalUTXOs(U256::from(start_idx))   // one HTTP round-trip per index
        .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
        .call()
        .await;
    match withdrawal_utxo {
        Err(e) if e.to_string().contains("execution reverted") => { break; }
        Err(e) => return Err(e.into()),
        Ok(_) => {}
    }
    // ... push result
    start_idx += 1;
}
```

There is no batch call, no pagination cap, and no loop-level timeout. The only per-call timeout is the global HTTP client timeout (default 60 s).

**Call chain that makes this safety-critical:**

1. `LcpSyncerTask::run_once` → `Verifier::handle_new_block` → `Verifier::handle_finalized_block` (`core/src/verifier.rs` lines 3053-3108)
2. Inside `handle_finalized_block`, `update_citrea_deposit_and_withdrawals` is awaited **before** `StateManager::dispatch_lcp_processed` is called.
3. `dispatch_lcp_processed` is the event that advances every kickoff state machine (watchtower challenge detection, disprove dispatch, etc.).
4. If `update_citrea_deposit_and_withdrawals` blocks for longer than the Bitcoin block interval (≈600 s), the verifier falls behind; if it blocks for longer than `operator_challenge_timeout_timelock` blocks, the challenge window is permanently missed.

**Attacker-controlled input:**

Any Citrea user can call `safeWithdraw` on the bridge contract to register a withdrawal UTXO. The verifier reads all indices from `last_withdrawal_idx + 1` to the current contract length, one call at a time, with no upper bound.

---

### Impact Explanation

If the verifier's `handle_finalized_block` is delayed past the `operator_challenge_timeout_timelock` (a Bitcoin relative timelock enforced in the `ChallengeTimeout` transaction), the verifier cannot send a watchtower challenge in time. A colluding malicious operator can then:

- Broadcast a kickoff with an invalid ZK proof / wrong payout data.
- Let the challenge window expire unchallenged.
- Collect the `ChallengeTimeout` path, spend the `KickoffFinalizer`, and proceed to claim reimbursement for a fraudulent withdrawal — stealing bridged BTC from the vault.

This breaks the core BitVM2 safety invariant: "one honest verifier is sufficient to prevent theft."

---

### Likelihood Explanation

- Registering a withdrawal on Citrea requires burning `bridge_amount` of cBTC per call, making large-scale spam capital-intensive.
- However, the attacker does not need to sustain the attack indefinitely — only long enough to cover the challenge window while a colluding operator's kickoff is live.
- The sequential-call design also degrades liveness under legitimate high-volume usage (no attacker required), as the number of honest withdrawals grows over the bridge's lifetime.
- No existing guard caps the number of items fetched per block or adds a loop-level deadline.

---

### Recommendation

1. **Replace sequential index polling with event-log queries.** The Citrea contract already emits events (e.g., `DepositReplaced` is fetched via `get_logs`). Apply the same pattern to deposits and withdrawals: query `WithdrawalRegistered` / `DepositRegistered` logs for the L2 height range, eliminating the per-index loop entirely.

2. **If index polling must be kept, add a per-block cap.** Process at most `MAX_ITEMS_PER_BLOCK` new entries per `handle_finalized_block` call and resume from the saved cursor on the next block.

3. **Add a loop-level timeout** so that `collect_withdrawal_utxos` / `collect_deposit_move_txids` fail fast rather than blocking indefinitely when the Citrea node is slow or the item count is large.

---

### Proof of Concept

1. Attacker holds cBTC and calls `safeWithdraw` on the Citrea bridge contract **N** times (e.g., N = 50,000), registering withdrawal UTXOs in a single Citrea block.
2. The next finalized Bitcoin block triggers `Verifier::handle_finalized_block`.
3. `collect_withdrawal_utxos` starts from `last_withdrawal_idx + 1` and makes **N sequential HTTP calls** to `withdrawalUTXOs(i)`. At 10 ms per call, N = 50,000 takes ≈ 500 s; at 50 ms per call it takes ≈ 2,500 s — well beyond one Bitcoin block interval.
4. `dispatch_lcp_processed` is never called for that block height; the kickoff state machine does not advance.
5. A colluding operator broadcasts a kickoff with an invalid bridge proof during this window.
6. The verifier's state machine, stuck processing spam withdrawals, never reaches the `KickoffEvent::Challenged` handler and never queues a `WatchtowerChallenge` transaction.
7. `operator_challenge_timeout_timelock` expires; the operator spends the `ChallengeTimeout` path, finalizes the kickoff, and claims reimbursement for a fraudulent withdrawal — stealing the bridged BTC.

**Exact corrupted state:** `dispatch_lcp_processed` is not delivered for the block containing the kickoff; the `KickoffStateMachine` never transitions to `Challenged`; the `WatchtowerChallenge` transaction is never added to the tx-sender queue; the challenge UTXO expires unspent.         &self,
        last_deposit_idx: Option<u32>,
        to_height: u64,

        let mut move_txids = vec![];

        let mut start_idx = match last_deposit_idx {

            None => 0,
        };

                .contract
                .depositTxIds(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;

                    tracing::trace!("Deposit txid not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}

            tracing::info!("Deposit txid found for index: {:?}", deposit_txid);

                .wrap_err("Failed to convert move txid to Txid")?;
            move_txids.push((start_idx as u64, move_txid));
            start_idx += 1;
        }
        Ok(move_txids)
    }

        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,

                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }

    pub async fn handle_finalized_block(
        &self,
        mut dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_height: u32,
        block_cache: Arc<block_cache::BlockCache>,
        light_client_proof_wait_interval_secs: Option<u32>,
    ) -> Result<(), BridgeError> {
        tracing::info!("Verifier handling finalized block height: {}", block_height);

        // before a certain number of blocks, citrea doesn't produce proofs (defined in citrea config)
        let max_attempts = light_client_proof_wait_interval_secs.unwrap_or(TEN_MINUTES_IN_SECS);
        let timeout = Duration::from_secs(max_attempts as u64);

        let (l2_height_start, l2_height_end) = self
            .citrea_client
            .get_citrea_l2_height_range(
                block_height.into(),
                timeout,
                self.config.protocol_paramset(),
            )
            .await
            .inspect_err(|e| tracing::error!("Error getting citrea l2 height range: {:?}", e))?;

        tracing::debug!(
            "l2_height_start: {:?}, l2_height_end: {:?}, collecting deposits and withdrawals...",
            l2_height_start,
            l2_height_end
        );
        self.update_citrea_deposit_and_withdrawals(
            dbtx,
            l2_height_start,
            l2_height_end,
            block_height,
        )
        .await?;

        self.update_finalized_payouts(dbtx, block_id, &block_cache)
            .await?;

        #[cfg(feature = "automation")]
        {
            // Save unproven block cache to the database
            self.header_chain_prover
                .save_unproven_block_cache(Some(&mut dbtx), &block_cache)
                .await?;
            while (self.header_chain_prover.prove_if_ready().await?).is_some() {
                // Continue until prove_if_ready returns None
                // If it doesn't return None, it means next batch_size amount of blocks were proven
            }
            // notify that lcp was processed for this height to state manager
            StateManager::<Self>::dispatch_lcp_processed(&self.db, dbtx, block_height).await?;
        }

        Ok(())
    }
