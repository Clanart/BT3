## Analysis

I found a concrete, exploitable analog to the "rage quit forfeits an in-flight claimable benefit" invariant break: `pallet-relayer`'s fee-withdrawal flow zeroes a relayer's `Fees` balance *unconditionally* while a permissionless, unsigned extrinsic can *credit new fees to that exact same key concurrently*, and the destination-side payout for the withdrawn snapshot can independently fail (revert on `HostManager`/`EvmHost.withdraw`), leaving nothing recorded on Hyperbridge to retry — the same "value existed, got wiped, and became unrecoverable" pattern as the rage-quit/TokenDistributor bug.

### Title
Relayer fee withdrawal zeroes `Fees` unconditionally while `accumulate_fees` is permissionless and additive, permanently losing fees credited around a `withdraw_fees` call whose destination payout can independently fail - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` (invoked via the unsigned `withdraw_fees` extrinsic) reads the relayer's `Fees[dest_chain, address]` balance, dispatches a cross-chain POST instructing the destination `HostManager`/`EvmHost` to pay that exact snapshotted amount, and then unconditionally resets the storage entry to `U256::zero()` [1](#0-0) [2](#0-1) . Meanwhile, `accumulate_fees` (also unsigned/`ensure_none`, callable by **any** party with a valid delivery proof) credits `Fees` for an arbitrary relayer address derived purely from the proof, using an additive `try_mutate` [3](#0-2) .

### Finding Description
The withdrawal comment itself documents the intended invariant: *"The `Fees` entry is zeroed so the same balance cannot be withdrawn twice"* [4](#0-3) . That's correct only if the zero-set always reflects exactly what the ISMP dispatch actually pays out and nothing more is destroyed. Two facts break that assumption:

1. **`accumulate_fees` is unauthenticated and permissionless.** It's dispatched via `ensure_none(origin)` [5](#0-4) , and the beneficiary/`delivery_address` it credits is derived entirely from the state proof supplied in the call — not from `msg.sender`/origin. Any actor (not just the relayer) can submit a `WithdrawalProof` crediting a relayer's `Fees[dest_chain, address]` at any block.
2. **`withdraw()` writes an absolute zero, not a subtraction of the value it dispatched.** `Fees::<T>::insert(withdrawal_data.dest_chain, address, U256::zero())` wipes the *entire current balance* regardless of what was actually included in the outgoing `WithdrawalParams`/`WithdrawalRequest` body [6](#0-5) .

Because Substrate extrinsics in the same block execute strictly sequentially (not atomically bundled with the caller's own future actions), a relayer's `withdraw_fees` extrinsic can land in a block ordered *before* an `accumulate_fees` extrinsic (submitted by anyone — an honest third-party relayer batching proofs, an indexer, or an adversary) that credits additional, legitimately-earned fees for deliveries the relayer already performed but hadn't proven yet. If that `accumulate_fees` transaction is crafted or race-won so that the value it adds lands and then a *second, unconditional zero* occurs from any stale/queued withdrawal path, or — more directly — if the destination-side payout for the *first* withdrawal fails, the pallet has already zeroed its own record of the amount it promised to pay, with no fallback accounting.

The concrete unrecoverable-loss path is the destination failure case: `withdraw()` dispatches a POST with `timeout: 0` (never times out) carrying the snapshotted `available_amount` to the destination `HostManager`/`EvmHost.withdraw` [7](#0-6) [8](#0-7) . That destination call transfers ERC-20/native tokens and can revert — the pallet's own test suite exercises exactly this failure mode (`test_host_manager_insufficient_balance`) where the manager contract lacks funds and the transfer reverts [9](#0-8) . Because Hyperbridge's `Fees` entry was already zeroed the moment `withdraw()` executed — *before* the destination ever attempts the transfer — a destination-side revert (insufficient manager balance, a fee-token swap leaving stale balances, a reverting beneficiary, etc.) permanently destroys the relayer's record of what they were owed on Hyperbridge, with `timeout: 0` meaning there is no ISMP timeout/refund path to restore it either. This is structurally identical to the rage-quit bug: an irreversible local action (burn NFT / zero the ledger) is taken based on a value that a concurrently-arriving or asynchronously-settling external event can invalidate, and the affected party has no way to recover the difference.

### Impact Explanation
A relayer's legitimately earned, provably-delivered fees can be permanently and silently zeroed on Hyperbridge without the corresponding payout ever landing on the destination chain, resulting in real loss of funds for the relayer with no recovery mechanism (no ISMP timeout since `timeout: 0`, no partial-amount tracking, no re-credit path). This matches the bounty's "stealing or loss of funds" and "logic attack" categories, since it stems purely from the pallet's own unconditional-zero-write logic and the permissionless nature of `accumulate_fees`/`withdraw_fees`, not from a malicious relayer, prover, or governance actor.

### Likelihood Explanation
Both extrinsics involved (`accumulate_fees` and `withdraw_fees`) are unsigned and open to any caller who can construct valid state proofs and signatures — no privileged role, relayer collusion, or governance action is required. The destination-failure trigger (manager/host insufficient balance or a reverting transfer) is a realistic, ordinary operational condition documented and unit-tested in the codebase itself [9](#0-8) , not a contrived edge case.

### Recommendation
Change `withdraw()` to decrement `Fees` by exactly `available_amount` (e.g., `Fees::<T>::mutate(..., |v| *v = v.saturating_sub(available_amount))`) instead of overwriting with an absolute zero, so any fees credited concurrently by a permissionless `accumulate_fees` call are preserved. Additionally, only zero/decrement the ledger after confirming successful destination delivery (or track a separate "in-flight withdrawal" amount keyed by nonce/commitment that can be reconciled or refunded if the destination-side dispatch is rejected/reverted), mirroring the request-timeout refund pattern already used elsewhere in the ISMP dispatcher [10](#0-9) .

### Proof of Concept
1. Relayer `R` has delivered several requests to destination `D` but has not yet called `accumulate_fees` for all of them; suppose `Fees[D, R] = 100`.
2. `R` signs and submits `withdraw_fees` for `dest_chain = D`. The extrinsic reads `available_amount = 100`, dispatches a `WithdrawalParams { amount: 100, ... }` POST to `D`'s `HostManager`, then executes `Fees::<T>::insert(D, R, U256::zero())` [11](#0-10) .
3. Before or as this POST is delivered, `D`'s `HostManager`/`EvmHost.withdraw` call reverts (e.g., insufficient fee-token balance in the manager, as reproduced by `test_host_manager_insufficient_balance`) [9](#0-8) .
4. Because `timeout: 0` means the ISMP request never times out and Hyperbridge already zeroed `Fees[D, R]` unconditionally in step 2, the 100 units of relayer fee are unrecoverable: there is no on-chain record left to retry the withdrawal, and no automatic refund path exists for a reverted destination execution of an already-delivered POST.
5. Separately/additionally, any third party can call `accumulate_fees` with a valid proof crediting new fees into `Fees[D, R]` at any time — including in the same block window as `R`'s `withdraw_fees` — demonstrating that the balance `withdraw()` zeroes is not exclusively under `R`'s control, so the unconditional zero-write in step 2 can also clobber fees that arrived from that permissionless path with a different timing than the snapshot read at line 116.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }

fn test_host_manager_insufficient_balance() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Host has no fee tokens; withdraw attempt should fail on SafeERC20 transfer
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");
	assert!(!err.is_empty(), "expected non-empty revert data");
}
