Given the evidence gathered, the strongest concrete, code-supported analog to the Wormhole "chain ID confusion" bug (trusting a mutable/reusable identifier instead of a stable canonical one, causing silent mis-binding of trust) is in GitHub Desktop's GitHub-repository identity resolution and persistence logic.

### Title
Repository identity resolution keyed on mutable owner/name instead of immutable GitHub repository ID enables silent repo-jacking of tracked repositories - (File: app/src/lib/stores/repositories-store.ts)

### Summary
The Wormhole bug stems from validating an incoming message against a reusable/confusable identifier (network chain ID vs. Wormhole chain ID) instead of a stable, protocol-specific ID, letting a wrong-but-plausible identifier pass validation. GitHub Desktop has an analogous invariant violation: it persists and re-resolves the local `GitHubRepository` record using the mutable pair `(ownerID, name)` rather than GitHub's immutable numeric repository ID, and it re-derives the "matched" account/owner/name for a tracked local repository from the raw git remote URL on every refresh, not from a stored canonical identity.

### Finding Description
`_upsertGitHubRepository` looks up whether a `GitHubRepository` already exists purely by `(ownerID, name)`: [1](#0-0) 

It then blindly overwrites the stored record's `htmlURL`/`cloneURL`/`permissions`/`private` fields with whatever the API returns for that owner/name, without ever comparing against GitHub's immutable numeric repository `id`: [2](#0-1) 

Feeding this pipeline, `matchGitHubRepository` re-derives the owner/name/account purely from the current git remote URL's hostname/owner/name string, every time the repository is refreshed — not from a durable, previously-verified identity: [3](#0-2) [4](#0-3) 

`repositoryWithRefreshedGitHubRepository` then calls the API for that owner/name using the authenticated account's token, and unconditionally treats whatever repository the API returns as the same repository the user has always been tracking: [5](#0-4) 

Because `owner`/`name` is a GitHub-assigned string that can be freed and re-registered (deleted account/org, renamed, or repo deleted and re-created by someone else) — a classic "repo-jacking" primitive — this is exactly the wrong-ID-space confusion pattern from the report: the code validates continuity of identity using a mutable, reusable string pair instead of the immutable numeric ID that GitHub's API actually returns in every repository object. Nothing in `_upsertGitHubRepository`, `matchGitHubRepository`, or `updateRemoteUrl` cross-checks the numeric ID: [6](#0-5) 

`updateRemoteUrl` compounds this: once the (wrongly re-matched) `GitHubRepository`/`apiRepo` pair disagrees with the locally configured git remote, and the URL protocol still matches, Desktop will silently run `git remote set-url` to rewrite the user's `origin` to the new `clone_url` — with no user prompt: [7](#0-6) 

### Impact Explanation
If an attacker reclaims an `owner/name` pair that a victim previously tracked in Desktop (e.g., victim's org/user was renamed/deleted and the name became available, or a private repo was deleted and someone else creates a public repo with the same owner/name), the next automatic refresh (`repositoryWithRefreshedGitHubRepository`, invoked on account changes, fetch, push, PR workflows, etc.) will silently bind the victim's local clone to the attacker's repository object. Combined with `updateRemoteUrl`, this can silently rewrite the tracked repository's `origin` remote to the attacker-controlled `clone_url`, so subsequent fetches/pulls pull attacker content and subsequent pushes go to the attacker's repository — a direct "silent corruption of what the user commits or pushes," matching the report's Impact criteria. It does not require local/physical access, admin rights, or leaked credentials — only that the attacker control a GitHub object (a repository) with a name/owner the victim previously interacted with.

### Likelihood Explanation
Likelihood is low-to-moderate and situational (comparable to the original report's Likelihood: 1): it requires the specific precondition of a name/owner becoming available and being reclaimed by an attacker before the victim removes or updates their local tracking info, and requires the protocol of the existing remote to match the new `clone_url`'s protocol for the silent rewrite path in `updateRemoteUrl` to trigger. However, unlike local-access or malware-based bugs, this path is fully attacker-triggerable from the outside (via public GitHub repository/account operations) and needs no unusual user action beyond normal Desktop usage (opening the app, fetching, or switching accounts).

### Recommendation
Persist and validate the GitHub API's immutable numeric repository `id` alongside `(owner, name)` in `IDatabaseGitHubRepository`/`GitHubRepository`, and require that `_upsertGitHubRepository` match/refresh existing records by that numeric ID (not just `[ownerID+name]`). When a numeric ID mismatch is detected for a previously-tracked `(owner, name)`, treat it as a new/foreign repository, warn the user, and require explicit confirmation before updating stored metadata or the git remote URL, rather than performing the `updateRemoteUrl` rewrite automatically.

### Proof of Concept
1. Victim clones and tracks `https://github.com/alice/project` in GitHub Desktop; Desktop stores a `GitHubRepository` keyed by `(ownerID(alice), "project")`.
2. Alice's account is later renamed/deleted (or the repo is deleted), freeing the `alice/project` slug.
3. Attacker creates a new GitHub account named `alice` (or a new repo `alice/project` if only the repo was deleted) with a repository `project`, setting its `clone_url` to an attacker-controlled remote configuration.
4. Victim's Desktop performs a routine refresh (`repositoryWithRefreshedGitHubRepository`, triggered by fetch/push/account-refresh); `matchGitHubRepository` re-resolves `owner=alice, name=project` from the still-configured remote URL, `api.fetchRepository('alice','project')` returns the attacker's new repository object (since GitHub reuses freed names/IDs are never checked), and `_upsertGitHubRepository`/`updateRemoteUrl` silently accept it as the same tracked repository, potentially rewriting the local `origin` to the attacker's `clone_url` ( [8](#0-7) ).
5. Victim's next `git push`/`git fetch` from Desktop is silently redirected to the attacker's repository, without any warning that the "same" tracked repository is now a different underlying GitHub object.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
