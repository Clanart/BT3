Based on my research, I found only one call site enforcing `RegisterPointerDisabled` in the entire codebase — `x/evm/keeper/msg_server.go:249` inside `RegisterPointer` — while the EVM pointer precompile's `AddCW20`, `AddNative`, `AddCW721`, and `AddCW1155` handlers (e.g. `precompiles/pointer/legacy/v562/pointer.go:173-226`, `precompiles/pointer/legacy/v555/pointer.go:204-258`, `precompiles/pointer/legacy/v552/pointer.go:196-249`) contain no reference to that flag at all. This mirrors the reported bug class exactly: an admission-control flag guards one entrypoint (`Msg` handler) but not a second, still-reachable entrypoint (EVM precompile) that performs the same privileged state mutation.

### Title
`RegisterPointerDisabled` governance pause can be bypassed via the EVM pointer precompile - (File: `precompiles/pointer/legacy/v562/pointer.go`)

### Summary
`x/evm`'s `MsgRegisterPointer` handler enforces the `RegisterPointerDisabled` chain parameter to let governance halt creation of new CW→ERC pointers [1](#0-0) . The EVM pointer precompile at `0x000000000000000000000000000000000000100b`, which any EVM contract or externally-owned account can call directly to create the same class of pointer objects (`AddCW20Pointer`, `AddNativePointer`, `AddCW721Pointer`, `AddCW1155Pointer`), never checks this parameter.

### Finding Description
`RegisterPointer` in `x/evm/keeper/msg_server.go` is the only place in the codebase that reads `GetRegisterPointerDisabled` before creating a pointer [1](#0-0) . It is used to gate both new pointer creation and pointer version migration for ERC20/ERC721/ERC1155 targets.

The pointer precompile (`0x100b`), implemented across several ABI versions (`precompiles/pointer/legacy/v552/pointer.go`, `v555/pointer.go`, `v562/pointer.go`, `v65/pointer.go`), exposes `AddCW20Pointer`, `AddNativePointer`, `AddCW721Pointer`, and `AddCW1155Pointer` as EVM-callable methods. Each handler queries the existing pointer registry, deploys a new pointer contract via `evm.Create`, and directly calls `p.evmKeeper.SetERC20CW20Pointer` / equivalent to register it [2](#0-1) . None of these EVM entrypoints call `GetRegisterPointerDisabled` or otherwise consult the same flag that the Cosmos `MsgRegisterPointer` path enforces.

This is structurally identical to the reported `MarginDex` issue: a pause/admission flag protects the "primary" transaction type (`add_tp_order`/`add_sl_order` vs. `MsgRegisterPointer`), while a second code path that performs the equivalent privileged mutation (`_open_trade`'s embedded orders vs. the pointer precompile) omits the same check.

### Impact Explanation
When governance sets `RegisterPointerDisabled = true` (a defensive/wind-down control, analogous to `is_accepting_new_orders`), the intent is to stop *any* new CW↔ERC pointer creation — for example during an incident response, a migration freeze, or to stop propagation of a buggy pointer contract version. Because the precompile path is unguarded, any EVM transaction sender can still create new pointers for arbitrary CW20/CW721/CW1155/native denoms during the pause, defeating the protocol's defensive control and potentially registering pointers using an unintended/stale pointer bytecode version while the chain is meant to be frozen for this feature.

### Likelihood Explanation
High reachability: the pointer precompile is a standard public EVM precompile at a fixed, documented address (`0x100b`), callable by any transaction sender or contract via a normal EVM call — no special permissions are required, matching the "unprivileged transaction sender" reachability bar. The only precondition is that governance has toggled `RegisterPointerDisabled = true`, which is exactly the scenario the flag exists to prevent from being circumvented.

### Recommendation
Add the same `GetRegisterPointerDisabled` check inside the pointer precompile's `Execute`/`AddCW20`/`AddNative`/`AddCW721`/`AddCW1155` handlers (all ABI-version variants under `precompiles/pointer/legacy/...` and the current one) before creating a new pointer, mirroring the check already present in `x/evm/keeper/msg_server.go`'s `RegisterPointer`.

### Proof of Concept
1. Governance passes a param-change setting `RegisterPointerDisabled = true` (verified via `TestRegisterPointerDisabled` behavior for `MsgRegisterPointer`, `x/evm/keeper/msg_server_test.go:836-907`, which confirms the Msg path rejects with `"registering CW->ERC pointers has been disabled"`).
2. An unprivileged EVM account calls the pointer precompile at `0x100b` with method `AddCW20Pointer(cwAddr)` (or `AddNativePointer`/`AddCW721Pointer`/`AddCW1155Pointer`) directly, exactly as exercised in `contracts/test/EVMPrecompileTest.js` / `precompiles/pointer/*` integration tests.
3. Because `AddCW20` (and siblings) never call `GetRegisterPointerDisabled`, the call succeeds: a new pointer contract is deployed via `evm.Create` and registered with `SetERC20CW20Pointer`, despite the governance-level pause.
