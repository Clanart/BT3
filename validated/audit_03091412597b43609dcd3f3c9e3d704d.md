### Title
Attacker-forced identity nonce sum in FROST preprocesses panics `Hram::hram`/`x()` instead of returning `FrostError` - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The external report is a parser-level bug: a deserialization path accepts attacker-supplied input whose type/shape is never validated, and a later `reflect.Set` panics instead of returning a validation error. The Serai analog is the FROST preprocess parsing path: `read_preprocess`/`Commitments::read` deserializes arbitrary group elements via `C::read_G`, which only enforces canonical encoding — it does not reject the identity point. IETF FROST requires rejecting identity nonce commitments. A malicious signing participant can choose its nonce commitments adaptively so the per-session aggregate nonce `R` is the point at infinity. When the Bitcoin `Schnorr` algorithm computes the BIP-340 challenge, `Hram::hram` calls `x(R)`, which executes `.expect("point at infinity")` and panics — converting attacker-controlled bytes into a panic rather than a `FrostError`.

### Finding Description
- `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) accepts any canonically encoded point, including identity, which is a valid canonical encoding on Ristretto/Ed25519/Secp256k1.
- `AlgorithmSignMachine::read_preprocess` (`crypto/frost/src/sign.rs:276-281`) feeds untrusted bytes through `Commitments::read` → `C::read_G` with no identity check on the nonce commitments.
- In `sign` (`crypto/frost/src/sign.rs:320-396`), each participant's nonce commitments are weighted by binding factors `rho` computed over the transcript of *all* preprocesses. Because preprocesses are exchanged before the binding factors are fixed per-session, a participant who sends last can solve for commitments making `Rs[n] = Σ rho_l * D_l` equal to identity (send `D_l = -(Σ_{j≠l} rho_j D_j)/rho_l`).
- `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:447+`) calls `algorithm.verify(group_key, &Rs, sum)`, which for `bitcoin::crypto::Schnorr` reaches `Hram::hram` (`networks/bitcoin/src/crypto.rs:59-73`). `hram` calls `x(R)` and `x(A)`; `x` does `key.to_encoded_point(true)` then `.x().expect("point at infinity")` (`crypto.rs:13-16`), panicking on the attacker-forged identity `R`.
- The panic occurs inside share verification/completion, so the attacker cannot be blamed via `InvalidShare`; the signing session crashes the host instead of cleanly rejecting the malformed preprocess.

### Impact Explanation
An unprivileged signing-set participant (or anyone able to submit preprocess/share bytes to `read_preprocess`/`read_share`/`complete`) can remotely panic the FROST signing path with a single crafted preprocess message. This mirrors the report's class: unvalidated deserialized input (identity point accepted by `read_G`) reaching a code path that assumes non-identity (`x()`/`expect`), producing a repeatable panic primitive. Where the caller wraps `complete` in a recoverable context this is session DoS; where it does not (e.g., `processor` signer loops that treat `unreachable!()` for unexpected error classes), it aborts block cosigning / batch signing / slash-report signing entirely. No confidentiality or forgery impact: the panic happens before any invalid signature is produced.

### Likelihood Explanation
Reachable whenever an attacker controls one preprocess slot in a signing session, which is the designed threat model for FROST (rogue participants are expected; `InvalidPreprocess`/`InvalidShare` errors exist precisely to blame them). The attack requires solving one linear relation over known `rho` values — computationally trivial — and the identity encoding is canonical, so it passes `read_G`'s round-trip check. Confirmed panic sites: `x()` at `crypto.rs:15`, `x_only` at `crypto.rs:22`. Caveat I could not fully verify within the iteration limit: whether every in-scope `Algorithm` (e.g., `IetfSchnorr` for Ristretto/Ed25519) also panics on identity `R` or returns `None`; the panic is confirmed for the Bitcoin `Schnorr`/`Hram` path, and `verify`'s `Option` return cannot express the panic — it propagates as a crash regardless.

### Recommendation
- Reject identity nonce commitments at parse/validation time: check `commitment.is_identity()` in `Commitments::read` or in `BindingFactor`/`sign` before computing `Rs`, returning `FrostError::InvalidPreprocess(l)`.
- Defense in depth: in `complete`/`verify`, check `R.is_identity()` before invoking `hram`, and make `Hram::hram`/`x()` return an error rather than `expect` on infinity.
- Add a regression test feeding a preprocess whose weighted nonce sum is identity through `read_preprocess` → `sign` → `complete` and asserting a `FrostError`, not a panic.

### Proof of Concept
1. Honest participants broadcast preprocesses with nonce commitments `{D_j}`. Attacker waits, computes binding factors `rho_j` from the `FROST_rho` transcript (deterministic given all preprocesses and `msg`), then publishes `D_l = -(Σ_{j≠l} rho_j·D_j) · rho_l^{-1}` (serialize via `Preprocess::write`; `read_G` accepts it since it's canonical).
2. All signers run `sign(...)`; `B.nonces` yields `R = identity`. `sign_share` itself succeeds.
3. On `complete(shares)` (or `verify`), `Hram::hram(&R=identity, &A, m)` calls `x(R)` → `to_encoded_point(true)` yields no x-coordinate → `expect("point at infinity")` panics (`networks/bitcoin/src/crypto.rs:15`).

Result: repeatable, attacker-triggered panic of the signing process from a single crafted preprocess message — the same "parsed-but-unvalidated input reaches a panic site" bug class as the free5GC `reflect.Set` type-confusion.
