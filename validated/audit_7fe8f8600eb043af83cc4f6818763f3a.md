## Title
Silent Suppression of Unresolved-Conflict-Marker Detection on Attacker-Crafted Repository State — Allows Committing Content That Still Contains Literal Conflict Markers - (File: `app/src/lib/git/status.ts`)

### Summary
The reported bug's abstracted pattern is: a value that is supposed to reflect ground truth is computed via a code path that can silently fail (staticcall reverting), and the failure is masked by a default/fallback value that is then trusted downstream for a security-relevant decision (pricing shares). The closest verified analog in GitHub Desktop is `getConflictDetails` in `app/src/lib/git/status.ts`, which wraps the calls that actually scan conflicted files for `<<<<<<<`/`=======`/`>>>>>>>` markers (`getMergeConflictDetails`, `getRebaseConflictDetails`, `getWorkingDirectoryConflictDetails`) in a single `try/catch` that, on **any** exception, discards the real per-file conflict data and substitutes an always-"clean" default: empty `conflictCountsByPath` and empty `binaryFilePaths`. [1](#0-0) 

### Finding Description
`getStatus` computes `doConflictedFilesExist` independently and correctly from raw `git status --porcelain=2` entries (`conflictedFilesInIndex.length > 0`), so the app still knows *that* files are conflicted. [2](#0-1) [3](#0-2) 

However, the *per-file* detail — specifically `conflictCountsByPath`, which is used to compute `conflictMarkerCount` on each `WorkingDirectoryFileChange` — comes exclusively from `getConflictDetails`, and that function swallows every error from the underlying git/filesystem scan and substitutes a hard-coded "no markers, no binaries" result:
```
} catch (error) {
  log.error('Unexpected error from git operations in getConflictDetails', error)
}
return {
  conflictCountsByPath: new Map<string, number>(),
  binaryFilePaths: new Array<string>(),
}
``` [4](#0-3) 

The scan itself (`getFilesWithConflictMarkers`) walks and reads every conflicted file's content from the attacker-controlled working tree, and `getBinaryPaths` shells out to `git` for `MERGE_HEAD`/`REBASE_HEAD`/`HEAD` diff information — both are direct consumers of untrusted, attacker-crafted repository content (arbitrarily large files, malformed encodings, unusual filenames/paths, submodule entries, or files that trip up the diff-parsing/binary-detection logic). [5](#0-4) [6](#0-5) 

This mirrors the `TricryptoLPStrategy.compoundAmount` pattern exactly at the abstraction level required: a code path meant to reflect the *true, current* state (in the audit report: sellable reward amount after checkpoint's side effects; here: which files/lines still contain raw conflict markers) is executed in a way that can fail, and on failure the system substitutes a value that looks "clean"/"safe" (0 sellable tokens → underpriced shares; here, zero marker counts → files reported as conflict-free) rather than propagating the failure to a blocking, fail-closed state. Both bugs turn a should-be-hard error into a silently accepted default that materially changes a security-relevant outcome for the app's consumer.

### Impact Explanation
`conflictMarkerCount` (derived from `conflictCountsByPath`) is what drives whether Desktop warns the user that a file still contains unresolved conflict markers before staging/committing it (see `app/src/ui/lib/conflicts/unmerged-file.tsx` and `app/src/lib/status.ts`, both of which key their "still has conflict markers" UI logic off this same value). If a crafted repository (attacker-controlled fetched/cloned repo, e.g. via a malicious PR the victim checks out and merges/rebases against) causes the inner scan to throw, `conflictCountsByPath` becomes an empty map for every conflicted file in that operation, and the UI/commit-flow behaves as though no files contain leftover conflict markers — even though `doConflictedFilesExist` is still (correctly) true. The net effect is that a user can be led to stage and commit files that still literally contain `<<<<<<<`/`=======`/`>>>>>>>` markers without the marker-count warning firing, i.e. silent corruption of what the user commits/pushes — one of the impact categories explicitly listed as valid in this exercise's scope.

### Likelihood Explanation
Exploitability depends entirely on being able to reliably trigger an exception inside `getFilesWithConflictMarkers`/`getBinaryPaths` (or their `git` invocations for `MERGE_HEAD`/`REBASE_HEAD`) using only content that ships inside a normal git repository (file content, encodings, submodule config, paths) — i.e. no local access, no admin rights, and no pre-existing host compromise, matching the "attacker controls a cloned/fetched repository" threat model. I was not able to fully verify, within the scope of read-only investigation, the exact conditions under which `getFilesWithConflictMarkers` (in `app/src/lib/git/diff-check.ts`, not directly inspected here) or `getBinaryPaths` actually throw for adversarial inputs — that would require deeper review of `diff-check.ts` and `diff.ts`'s binary-path detection, which is why I present this as a likely-but-not-fully-confirmed analog rather than a certainty.

### Recommendation
- In `getConflictDetails`, do not collapse a thrown error into an "all clean" result. On failure, either (a) propagate the error so `getStatus` fails closed and the caller can block committing until status can be computed reliably, or (b) mark the affected files with an explicit "unknown/could not verify conflict state" status distinct from "no markers found," and have the commit-warning UI treat "unknown" the same as "has markers" (fail closed, not fail open).
- Apply the same fail-closed treatment to `getWorkingDirectoryConflictDetails`'s inner `try { } catch (error) {}` around `getBinaryPaths`, which already silently discards errors independent of the outer catch. [7](#0-6) 
- Add regression tests (a crafted fixture repository that reliably throws from the marker-scan or binary-path git call while in a genuine merge/rebase conflict state) asserting that `getStatus` never reports `conflictMarkerCount: 0`/absent for a file that is known to be conflicted (`doConflictedFilesExist === true`) when the underlying scan failed.

async function getWorkingDirectoryConflictDetails(
  repository: Repository,
  conflictedFilesInIndex: ReadonlyArray<IStatusEntry>
) {
  const conflictCountsByPath = await getFilesWithConflictMarkers(
    repository.path
  )
  let binaryFilePaths: ReadonlyArray<string> = []
  try {
    // its totally fine if HEAD doesn't exist, which throws an error
    binaryFilePaths = await getBinaryPaths(
      repository,
      'HEAD',
      conflictedFilesInIndex
    )
  } catch (error) {}

  return {
    conflictCountsByPath,
    binaryFilePaths,
  }
}

async function getConflictDetails(
  repository: Repository,
  mergeHeadFound: boolean,
  conflictedFilesInIndex: ReadonlyArray<IStatusEntry>,
  rebaseInternalState: RebaseInternalState | null
): Promise<ConflictFilesDetails> {
  try {
    if (mergeHeadFound) {
      return await getMergeConflictDetails(repository, conflictedFilesInIndex)
    }

    if (rebaseInternalState !== null) {
      return await getRebaseConflictDetails(repository, conflictedFilesInIndex)
    }

    // If there's conflicted files in the index but we don't have a merge head
    // or a rebase internal state, then we're likely in a situation where a
    // stash has introduced conflicts
    if (conflictedFilesInIndex.length > 0) {
      return await getWorkingDirectoryConflictDetails(
        repository,
        conflictedFilesInIndex
      )
    }
  } catch (error) {
    log.error(
      'Unexpected error from git operations in getConflictDetails',
      error
    )
  }
  return {
    conflictCountsByPath: new Map<string, number>(),
    binaryFilePaths: new Array<string>(),
  }
}
