### Title
Non-canonical consensus encoding in `ReceivedOutput::read` permits malleable deserialization - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` parses the `TxOut` and `OutPoint` fields via rust-bitcoin's `consensus_decode`, which accepts non-minimal (non-canonical) CompactSize `VarInt` encodings, while `ReceivedOutput::write` always re-serializes canonically. Every other deserialization path in Serai (`Ciphersuite::read_F`, `Ciphersuite::read_G`, `SchnorrSignature::read`, `ThresholdKeys::read`, `Commitments::read`, `DLEqProof::read`, etc.) enforces canonical, bijective encodings; `ReceivedOutput::read` is the lone exception, making the serialized form non-injective — multiple distinct byte strings decode to the same `ReceivedOutput`.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
}
```

The `offset` field is read through `Secp256k1::read_F`, which rejects non-canonical scalars (`crypto/ciphersuite/src/lib.rs:74-83`). However, `TxOut` contains a `script_pubkey` whose length is encoded as a Bitcoin CompactSize varint. rust-bitcoin's `Decodable` implementation accepts non-minimal varints — e.g., a script length of `0x22` can legitimately be encoded as `16`, but is also accepted as `fd 16 00` or `fe 16 00 00 00` or `ff ...`. All four encodings decode to the identical `TxOut`.

`ReceivedOutput::write` calls `consensus::encode::serialize`, which emits only the minimal encoding. Therefore `read` → `write` is not an identity on the input bytes: a serialized `ReceivedOutput` received from a peer can round-trip to *different* bytes.

This is the direct analog of the upstream bug class: deserialization is not injective/deterministic at the byte level, so any protocol logic that commits to, hashes, signs, or byte-compares the serialized form of a `ReceivedOutput` (rather than the decoded value) will diverge between parties who received differently-encoded copies of the same logical output. `ReceivedOutput` is explicitly in scope and is consumed by `processor/src/networks/bitcoin.rs`, where scanned outputs are passed through processor message flows and eventually drive `SignableTransaction` construction.

### Impact Explanation
Wherever the serialized bytes of a `ReceivedOutput` are committed to — e.g., included in a message that is hashed into a sign ID/eventuality, compared for equality across processor/coordinator messages, or re-signed — an attacker who can supply a non-minimally-encoded `ReceivedOutput` causes honest parties to hold byte-divergent representations of the same output. Depending on where the encoding is committed, consequences include:

- Two honest nodes computing different hashes/IDs for the same spendable output, causing the signing session to fail or one party to report `InvalidParticipant` against an honest peer (liveness DoS / chain-halt analog of the upstream advisory).
- Duplicate-detection or deduplication keyed on raw bytes being bypassed, allowing the same outpoint to be registered twice.

I could not fully trace every consumer of `ReceivedOutput::serialize()` in `processor/` within the available context to confirm a specific hash-commitment site, so the precise severity (Medium vs High) depends on whether serialized bytes are hashed/compared before or after decode. The encoding violation itself is certain and is reachable from untrusted bytes fed to `ReceivedOutput::read`.

### Likelihood Explanation
Reachability is high: `ReceivedOutput::read` is a public API explicitly designed to consume externally supplied serialized data (it is listed among the in-scope untrusted-input readers). Producing a non-minimal varint requires no privilege and no brute force. Exploitation requires only that some downstream consumer treats the raw encoding as meaningful, which is the standard pattern for cross-processor message hashing/signing in this codebase.

### Recommendation
Reject non-canonical encodings in `ReceivedOutput::read` by re-serializing and comparing, mirroring `Ciphersuite::read_G`:

```rust
let output = TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
// enforce canonical encoding by checking consumed length / re-serialization
```

Concretely, either decode via `bitcoin::consensus::Decodable` on a counted reader and verify the consumed length matches the canonical `serialize(&output)` length, or implement a strict varint check so that only the minimal CompactSize form is accepted. Apply the same check to `OutPoint` (fixed-size, but verify anyway) and audit any other `consensus_decode` call sites reachable from untrusted input.

### Proof of Concept
