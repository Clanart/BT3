This is documented, by-design behavior rather than an unauthorized coin-movement bug, but it precisely mirrors the reported bug class: a puzzle-controlled "shared pooled address" that anyone can deposit XCH into, but only a privileged party (the singleton/PlotNFT owner) can sweep — with the CLVM layer never distinguishing legitimate pool rewards from arbitrary third-party deposits.

### Title
Pool/PlotNFT singleton owner can sweep arbitrary third-party deposits sent to the `p2_singleton`/`p2_singleton_or_delayed_puzhash` address, indistinguishable from legitimate farming rewards - (File: chia/wallet/puzzles/singleton_top_layer.py)

### Summary
The Chia pooling protocol pays block/farming rewards to a `p2_singleton` (or `p2_singleton_or_delayed_puzhash`) puzzle hash derived from a plot-NFT/pool singleton's `launcher_id` [1](#0-0) . This puzzle hash behaves like an ordinary XCH address to the outside world — any wallet user or spend-bundle submitter can send arbitrary XCH to it. However, the CLVM puzzle only checks that a coin's `parent_coin_info`, puzzle hash, and amount match the announcement asserted by the singleton — it performs no check that the coin actually originated from a real block reward (i.e., that its `parent_coin_info` equals `pool_parent_id(height, genesis_challenge)`) [2](#0-1) . Consequently, the singleton owner (the pool member/self-pooling owner, analogous to Sablier's "sender") can claim/sweep any coin sent to that address, not just legitimate rewards, exactly as the sender in the Sablier report could refund deposits made by other, unrelated depositors.

### Finding Description
`claim_p2_singleton()` builds a generic claim spend for a `p2_singleton_coin` using only the coin's identity (`p2_singleton_coin.name()`) and an assertion/announcement pair tying the claim to the singleton's inner-puzzle spend [2](#0-1) . Nothing in this puzzle or its Python driver verifies that the claimed coin is a genuine consensus reward coin (with `parent_coin_info` derived from `pool_parent_id`/`calculate_pool_reward`) as opposed to any XCH coin a third party chose to send to that puzzle hash.

Wallet-level bookkeeping in `PlotNFT2Wallet.coin_added()` does attempt to reject non-reward coins for its own local accounting — it raises `ValueError("A non-pooling reward coin was paid to PlotNFT...")` when a coin at `p2_singleton_puzzle_hash` doesn't have the expected genesis-challenge-derived parent prefix [3](#0-2) . Likewise, the legacy `PoolWallet.claim_pool_rewards()` filters candidate coins against a `coin_to_height_farmed` map built from the wallet's own recorded farming-reward transactions [4](#0-3) . These are local wallet-software conveniences and consensus-coinbase-shape assumptions, not CLVM-enforced invariants. Any actor who constructs a raw spend bundle using `claim_p2_singleton()`/`pay_to_singleton_or_delay_puzzle()` directly (bypassing the higher-level wallet convenience filters) can spend *any* coin present at the `p2_singleton` puzzle hash into the singleton's target, because on-chain validation only checks coin/puzzle/announcement consistency, not reward provenance.

This is structurally the same bug class as the Sablier report: a puzzle/contract exposes a shared deposit address that unrelated parties can fund, while a single privileged party (stream sender / singleton owner) can withdraw the entire balance regardless of who deposited it, because the contract has no concept of "depositor identity" or "ownership share" for funds sitting at that address.

### Impact Explanation
Any XCH sent by mistake, by an unaware farmer/observer, or as an intentional "donation"/misdirected payment to a pool/plot-NFT's `p2_singleton_puzzle_hash` (which is exposed via `pw_status`/plot-NFT tooling and looks like a normal address) can be unilaterally swept by the singleton owner to their own `target_puzzle_hash`, with no recourse for the original sender. This is an unauthorized coin movement from the depositor's perspective: funds they control are moved to a third party's target without their consent, solely because they reused a "reward-looking" address as a normal payment destination. Impact is medium: real economic loss is possible but requires a depositor to send funds to a pool-specific address outside the intended reward flow (a user-facing/trust-assumption issue, consistent with Sablier's own "Acknowledged" resolution rather than "High/Critical").

### Likelihood Explanation
Likelihood is low-to-medium: it requires a wallet user to send XCH to a `p2_singleton`/`p2_singleton_or_delayed_puzhash` address (which is not typically shared as a normal receive address, but can be obtained from plot-NFT status output or block explorers) and requires the singleton owner to construct a claim spend outside the standard reward-only wallet flow. It is reachable purely through standard spend-bundle submission with no privileged node/network access.

### Recommendation
Document explicitly (in user-facing tooling and address displays) that `p2_singleton`/`p2_singleton_or_delayed_puzhash` addresses are reward-only and must never be treated as general-purpose receive addresses; consider warning wallet UIs against manually sending regular XCH to a `pw_status`-reported `p2_singleton_puzzle_hash`. If stronger guarantees are desired, encode reward provenance (e.g., parent-id/height binding to `pool_parent_id`) as a CLVM-enforced condition in the claim puzzle rather than relying solely on wallet-side heuristics such as `PlotNFT2Wallet.coin_added()`'s prefix check.

### Proof of Concept
1. Obtain the `p2_singleton_puzzle_hash` for a target plot-NFT/pool wallet (returned by `PoolWallet.create_new_pool_wallet_transaction` / `pw_status`) [5](#0-4) .
2. As an unrelated wallet user, submit a standard spend bundle creating a coin of arbitrary amount at that puzzle hash (this is a normal `CREATE_COIN` to a valid puzzle hash; nothing prevents it).
3. As the singleton owner, construct a claim spend via `singleton_top_layer.claim_p2_singleton()` (or the delayed variant) for that coin, tying it to the singleton's current inner-puzzle spend, and push it alongside the singleton's own spend [2](#0-1) .
4. The coin is claimed into the singleton's target puzzle hash even though it never originated from `pool_parent_id`/`calculate_pool_reward`; the CLVM layer performs no such check. Existing tests (`test_singleton_top_layer`) demonstrate this exact "claim a p2_singleton_or_delayed" spend path using an "ARBITRARY_AMOUNT" test coin farmed directly to the p2_singleton puzzle hash, unrelated to any real block reward [6](#0-5) .

def claim_p2_singleton(
    p2_singleton_coin: Coin,
    singleton_inner_puzhash: bytes32,
    launcher_id: bytes32,
    delay_time: uint64 | None = None,
    delay_ph: bytes32 | None = None,
) -> tuple[Program, Program, CoinSpend]:
    assertion = Program.to([ConditionOpcode.ASSERT_COIN_ANNOUNCEMENT, std_hash(p2_singleton_coin.name() + b"$")])
    announcement = Program.to([ConditionOpcode.CREATE_PUZZLE_ANNOUNCEMENT, p2_singleton_coin.name()])
    if delay_time is None or delay_ph is None:
        puzzle = pay_to_singleton_puzzle(launcher_id)
    else:
        puzzle = pay_to_singleton_or_delay_puzzle(launcher_id, delay_time, delay_ph)
    claim_coinsol = make_spend(
        p2_singleton_coin, puzzle, solution_for_p2_singleton(p2_singleton_coin, singleton_inner_puzhash)
    )
    return assertion, announcement, claim_coinsol
