### Title
`updateRemoteUrl` silently rewrites the local git remote from an untrusted GitHub API `clone_url` field, without host validation - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes a repository's GitHub association (on fetch, push, pull, PR lookups, etc.), it calls `updateRemoteUrl()` with the `apiRepo` object returned by `api.fetchRepository(owner, name)` [1](#0-0) . That function will overwrite the repository's `origin` remote URL with `apiRepo.clone_url` as long as the URL's protocol (`http:`/`https:`) matches the current remote's protocol, with no check that the **hostname** is unchanged [2](#0-1) . Anything that can influence the `clone_url` field of the API response for a repository the user already has open in Desktop — a malicious/compromised GitHub Enterprise Server, a MITM'd or spoofed API response, or a repository transferred to an attacker-controlled owner — can cause Desktop to silently re-point the user's `origin` remote to an attacker-controlled git host.

### Finding Description
`updateRemoteUrl` is the mechanism responsible for keeping the local `origin` remote synced with what the GitHub API reports as the canonical `clone_url` for a repository (e.g., after a rename) [3](#0-2) . Its only defenses are:
1. `protocolsMatch` — verifies the URL scheme (`https:`) is unchanged, but says nothing about the host [4](#0-3) .
2. `remoteUrlUnchanged` — verifies the user hasn't manually edited the remote away from the last known API-derived URL, so this only protects against local edits, not against a compromised/attacker-supplied API response [5](#0-4) .

Crucially there is no comparison of `updatedRemoteUrl`'s hostname/owner against the endpoint or existing GitHub repository record — `urlsMatch`/`urlMatchesRemote` is only used to *detect drift*, not to *validate* the new URL is safe before applying `gitStore.setRemoteURL(...)` [6](#0-5) . This function is invoked from `repositoryWithRefreshedGitHubRepository`, which is called via `withRefreshedGitHubRepository` on nearly every network-triggered operation (fetch, push, pull, PR lookup) [7](#0-6) , and the `apiRepo` used comes straight from `api.fetchRepository(owner, name)` against whatever endpoint/account was previously associated with the repo [8](#0-7) . For GitHub Enterprise accounts, that endpoint is a server the app trusts implicitly once added; if that server is compromised, malicious, or MITM'd (unlike github.com, GHES doesn't enforce certificate pinning in this flow), it can return an arbitrary `clone_url` for the very repository Desktop is already tracking.

This directly parallels the seed report's pattern: a restriction/validation gate (`_requireValidRecipient` in the ERC20 case; `protocolsMatch`/`remoteUrlUnchanged` here) is meant to protect an invariant (who can receive tokens / which remote URL is trustworthy) but is too narrow, letting an externally-supplied, attacker-influenced value flow through and corrupt state that downstream operations (transfers / pushes) rely on.

### Impact Explanation
If the local `origin` is silently rewritten to an attacker-controlled host, subsequent `git push` operations performed by Desktop (using `gitStore.defaultRemote`/`currentRemote`, which is exactly the remote entry that was overwritten) will send the user's commits to the attacker's server instead of the intended GitHub repository. This is a "silent corruption of what the user commits or pushes" — the user believes they're pushing to their normal repo, but their proprietary source code (and potentially credentials sent via the git transport's auth negotiation) is exfiltrated to attacker infrastructure. There is no user-facing confirmation prompt before `setRemoteURL` runs.

### Likelihood Explanation
The precondition is that whatever supplies the `apiRepo.clone_url` value for an already-tracked repository must be attacker-influenced (e.g., a rogue/compromised GHES instance, a network-level response tamperer, or a GitHub-side repository transfer to an attacker-controlled owner whose clone URL differs only by host/owner but keeps the same protocol). This is a realistic "attacker controls a git remote/proxy response" scenario as scoped by the task, and it requires no unusual user action beyond normal use of Desktop (fetch/push/pull), since `withRefreshedGitHubRepository` runs implicitly on those paths.

### Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, validate that the new `clone_url`'s hostname matches the hostname of the account/endpoint used to fetch it (and/or matches the previously known `gitHubRepository.endpoint`), not just that the protocol matches. Reject (or prompt the user to confirm) any automatic remote-URL update that changes the host, and log/telemetry-flag such mismatches as suspicious.

### Proof of Concept
1. User has a repository in Desktop associated with a GitHub Enterprise account/endpoint `https://ghe.corp.example`.
2. Attacker compromises (or MITMs) that GHES instance, or otherwise causes `api.fetchRepository(owner, name)` to return a JSON payload with `clone_url: "https://ghe.attacker.example/owner/name.git"` (same `https:` protocol, different host) [8](#0-7) .
3. On the next fetch/push/pull, `repositoryWithRefreshedGitHubRepository` calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [9](#0-8) .
4. `protocolsMatch` is `true` (https == https) and `remoteUrlUnchanged` is `true` (user hasn't manually edited `origin`), so `gitStore.setRemoteURL('origin', 'https://ghe.attacker.example/owner/name.git')` executes silently [6](#0-5) .
5. The user's next `git push` sends their commits to `ghe.attacker.example` instead of the legitimate server, with no warning shown.

Note: I was unable to fully verify from the indexed code alone whether Desktop enforces TLS certificate pinning or other transport-level protections for GHES endpoints that might make step 2 harder in practice; a full assessment of that trust boundary would require examining the network/HTTP client configuration and GHES onboarding flow in more depth, which may require a live Devin session with full repository access.

```typescript
import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
