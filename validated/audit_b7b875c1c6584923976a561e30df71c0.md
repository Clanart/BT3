## Finding: Deep-link (`x-github-client://openRepo/...`) can silently fetch and checkout an attacker-chosen branch in an already-open repository, bypassing the confirmation flow that exists for new repositories

### Title
Unconfirmed branch checkout via attacker-controlled protocol-handler URL - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
GitHub Desktop registers a custom URL protocol (`x-github-client://`, mirrored via `github-mac://`/etc.) that is parsed by [1](#0-0)  into an `open-repository-from-url` action carrying an attacker-fully-controlled `url`, `branch`, `pr`, and `filepath`. This action reaches `Dispatcher.openRepositoryFromUrl` with no signature, origin, or user-intent verification — any web page, email, or chat message the user clicks can trigger it, exactly analogous to the report's "attacker triggers a privileged state-changing function with no restriction on the caller."

### Finding Description
When the URL action contains a `branch` parameter, `openRepositoryFromUrl` calls `openBranchNameFromUrl`: [2](#0-1) [3](#0-2) .

`openBranchNameFromUrl` first resolves the repository via `openOrCloneRepository`. If Desktop already has a repository whose origin/upstream `htmlURL` matches the attacker-supplied `url` (checked purely by string match, not authentication), `openOrCloneRepository` returns the **existing** repository silently via `selectRepository`, with no popup and no user confirmation: [4](#0-3) . This is the opposite of the new-repository path, which does show a `CloneRepository` popup for the user to review before anything happens — that guard is bypassed entirely for repos the user already has open.

Once the existing repository is resolved, the code automatically calls `appStore._fetch(...)` (pulling new refs from the remote) and then `checkoutLocalBranch(repository, branchName)`, which calls `checkoutBranch` directly: [5](#0-4) . There is no confirmation dialog, no diff review, and no check that the user actually intended to switch branches — the mere act of clicking a link is treated as sufficient authorization to fetch and checkout code.

The corrupted value here is **the current branch tip / working-directory contents of an already-registered repository** — an attacker-controlled state transition performed with the same lack of restriction the original report criticizes ("no restriction on registration/referral mechanism, dependent only on ad hoc guards").

### Impact Explanation
An attacker who knows (or guesses, e.g. via a public fork of a well-known repo) that the victim has a given GitHub repository open in Desktop can craft a link such as `x-github-client://openRepo/https://github.com/<org>/<repo>?branch=<attacker-branch>`. When the victim clicks it (from an email, issue comment, chat message, or malicious website), Desktop will silently fetch and switch the working directory to `<attacker-branch>` without any confirmation. This can:
- Silently discard/stash the user's in-progress work depending on their uncommitted-changes strategy.
- Place attacker-controlled file contents into the user's working directory, which the user may then unknowingly commit/pull further work onto and push — matching the accepted impact category "silent corruption of what the user commits or pushes."
- Be combined with the existing `filepath` parameter (also from `parseAppURL`) to immediately reveal a file from that branch via `shell.showItemInFolder` (a `resolveWithin` guard is already present for absolute-path/traversal cases, but it does not protect against the branch swap itself) [6](#0-5) .

### Likelihood Explanation
Likelihood is moderate-to-high: no local access, admin rights, or pre-existing malware is required — only a single click on an attacker-supplied link, which is a normal and expected way protocol handlers are exercised in Desktop (used legitimately for OAuth and "Open in Desktop" buttons). The precondition (victim already has the target repo cloned/open in Desktop with a matching origin URL) is common for popular or organization repos. The existing guard set (`testForInvalidChars` on the branch name, `resolveWithin` on filepath) validates format/traversal but does nothing to gate whether a checkout should happen at all, so it does not block this path. I could not fully verify from local code whether the victim's `UncommittedChangesStrategy` setting would interject a stash prompt in every case, since `checkoutBranch`'s internal implementation wasn't fully inspected during the final tool iteration; this affects the intrusiveness of the corruption (silent overwrite vs. stash-and-notify) but not the core finding that the branch switch itself proceeds without any consent-to-follow-this-link confirmation.

### Recommendation
- Require explicit user confirmation (a dialog naming the repository and target branch) before fetching/checking out a branch initiated from a protocol-handler URL, mirroring the confirmation already required for the "open new repository" path.
- Do not silently reuse an already-open repository match for privileged operations (fetch + checkout) triggered by an external URL; treat protocol-handler-initiated actions with the same scrutiny as `pr` and `open-repository` flows.
- Consider requiring the URL action to include a nonce/signature tied to a Desktop-initiated action (as already done for the `oauth` action's `state` parameter) so that arbitrary third parties cannot forge `open-repository-from-url?branch=...` links.

### Proof of Concept
1. Victim has previously cloned/opened `https://github.com/acme/widgets` in GitHub Desktop.
2. Attacker hosts a link (in an email, chat message, or web page):
   `x-github-client://openRepo/https://github.com/acme/widgets?branch=malicious-branch`
3. Victim clicks the link.
4. `parseAppURL` parses it into `{ name: 'open-repository-from-url', url: 'https://github.com/acme/widgets', branch: 'malicious-branch', ... }` [7](#0-6) .
5. `Dispatcher.dispatchURLAction` routes to `openRepositoryFromUrl` → `openBranchNameFromUrl` [8](#0-7) .
6. Because the repo is already known (`doesRepositoryMatchUrl` matches), Desktop silently selects it, fetches, and checks out `malicious-branch` with no confirmation dialog shown to the user [3](#0-2) .

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

  private async checkoutLocalBranch(repository: Repository, branch: string) {
    let shouldCheckoutBranch = true

    const state = this.repositoryStateManager.get(repository)
    const branches = state.branchesState.allBranches

    const { tip } = state.branchesState

    if (tip.kind === TipState.Valid) {
      shouldCheckoutBranch = tip.branch.nameWithoutRemote !== branch
    }

    const localBranch = branches.find(b => b.nameWithoutRemote === branch)

    // N.B: This looks weird, and it is. _checkoutBranch used
    // to behave this way (silently ignoring checkout) when given
    // a branch name string that does not correspond to a local branch
    // in the git store. When rewriting _checkoutBranch
    // to remove the support for string branch names the behavior
    // was moved up to this method to not alter the current behavior.
    //
    // https://youtu.be/IjmtVKOAHPM
    if (shouldCheckoutBranch && localBranch !== undefined) {
      await this.checkoutBranch(repository, localBranch)
    }
  }

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }

    return this.appStore._startOpenInDesktop(() => {
      this.changeCloneRepositoriesTab(CloneRepositoryTab.Generic)
      this.showPopup({
        type: PopupType.CloneRepository,
        initialURL: url,
      })
    })
  }
