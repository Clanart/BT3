Found it — the Tron deployment of `IntentGatewayV2.sol` deliberately avoids `SafeERC20` on the escrow-release path and uses a raw low-level `.call` with the `transfer` selector, checking only that the call didn't revert, not the ERC20 return value.

### Title
Escrow release/refund on Tron IntentGatewayV2 accepts silent-failure ERC-20 `transfer` as success, permanently burning escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron variant of `IntentGatewayV2` releases escrowed input tokens and accumulated transaction fees to a beneficiary using a raw low-level call to the token's `transfer` selector, checking only `success` (i.e. that the call did not revert) and never decoding/validating the returned `bool`. This is exactly the bug class from the external report (unchecked `transferFrom`/`transfer` return value): non-reverting ERC-20s that signal failure by returning `false` will pass this check even though no tokens moved, while the contract still permanently decrements/deletes escrow accounting as if the transfer succeeded.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the withdraw path releases escrow like this: [1](#0-0) 
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and for fee redemption: [2](#0-1) 
```
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
```
Right after each of these calls, the code unconditionally decrements the escrow ledger — `_orders[body.commitment][token] -= amount;` and `delete _orders[body.commitment][TRANSACTION_FEES];` — treating a merely non-reverting call as proof of a successful transfer.

`bool success` from a low-level `.call` only reflects whether the callee reverted; it does not validate the ABI-encoded return data. Any ERC20 implementation (or a token behind a proxy/adapter, paused token, blacklisted-recipient token, or fee-on-transfer/rebasing token with edge-case logic) that returns `false` instead of reverting on failure will make `success == true` while zero tokens actually moved to `beneficiary`. The escrow record is decremented/deleted anyway, so the funds are irrecoverably lost/stuck in the contract with no accounting entry left to redeem them through any other code path.

This is a direct structural regression versus the "canonical" EVM `IntentsBase._withdraw` used by the primary (non-Tron) deployment, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, reverting on a `false` return: [3](#0-2) 
```
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```
The Tron file instead reimplements the transfer manually with the unchecked-return-value pattern, reintroducing the exact class of bug the external report describes.

### Impact Explanation
`withdraw()` is reached from `onAccept` (fill settlement releasing escrow to the solver) and `onGetResponse` (refund path after cancellation), both privileged-callback entry points triggered by legitimate cross-chain message flow rather than any admin action. Whenever the escrowed/fee token used on the Tron deployment can return `false` on failure (a real category of ERC-20/TRC-20 tokens, not a hypothetical), a legitimate settlement or refund silently fails to deliver funds while the protocol's internal ledger marks the order finalized and the escrow consumed. The result is direct, permanent loss of user/solver funds with no remaining code path to reclaim them — this is loss of funds and false settlement finality, matching the bounty's "stealing or loss of funds" / "false proof or state acceptance" impact classes.

### Likelihood Explanation
Likelihood is contingent on which specific TRC-20/ERC-20 tokens are whitelisted for orders on the Tron deployment; if any supported or attacker-selectable token has non-reverting failure semantics (which is common in TRC-20 practice on Tron, mirroring the very tokens the original Fei report worried about), the bug is trivially triggerable by an ordinary user/solver placing and filling an order with that token — no malicious relayer, prover, or admin is required, satisfying the "unprivileged attacker, public entrypoint" bar.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (both the per-input-token loop and the fee-redemption block) with OpenZeppelin's `SafeERC20.safeTransfer`, matching `IntentsBase._withdraw` in the primary EVM deployment, so that a `false` return value reverts the whole transaction instead of being treated as success.

### Proof of Concept
1. Register/allow a TRC-20 token (or an ERC-20 wrapper) on the Tron `IntentGatewayV2` deployment whose `transfer` implementation returns `false` rather than reverting on failure (e.g., due to a paused state, blacklist, or insufficient balance edge case introduced after order placement but before settlement).
2. A user places an order and escrows this token via `placeOrder`; a solver fills it, or the order is cancelled and refunded.
3. Hyperbridge delivers the corresponding `RedeemEscrow`/`RefundEscrow` message, invoking `onAccept`/`onGetResponse` → `withdraw()`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, encodedFalse)` because the token contract does not revert.
5. `success` is `true`, so `TransferFailed` is not raised; `_orders[body.commitment][token] -= amount` executes and (if finalizing) `_filled[commitment]` is set — the order is marked as fully and correctly settled.
6. `beneficiary` never received the tokens (transfer returned `false`), and the escrow accounting no longer reflects any owed balance, so the funds are permanently stuck in the `IntentGatewayV2` contract with no remaining mechanism to release them to the rightful beneficiary.
