### Title
User funds sent to a multisig's Branch/Change/Forwarded addresses are silently absorbed by the multisig with no credit or refund path - (File: processor/src/networks/bitcoin.rs)

### Summary
The Cooler bug class is "anyone can invoke an action on a construct they don't own, yet any value transferred is attributed to (or absorbed by) the owner rather than the actor." Serai's Bitcoin integration has the same shape: `Scanner::scan_transaction` matches outputs purely by `script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:205`), and the Branch, Change, and Forwarded P2TR scripts are deterministically derivable by anyone from the public multisig group key plus fixed `hash_to_F` offsets (`processor/src/networks/bitcoin.rs:308-347`, `661-674`). An external user who pays one of these scripts has their output classified as `Branch`/`Change`/`Forwarded` instead of `External`, so it bypasses the deposit crediting path and is pushed directly into the scheduler's internal UTXO pool (`processor/src/multisigs/scheduler/utxo.rs:295`). The sender is never credited and there is no refund path for non-External outputs — the multisig keeps the funds.

### Finding Description
`Bitcoin::get_outputs` scans every transaction in a block and assigns each matched output a `kind` solely from which registered offset-script it pays (`processor/src/networks/bitcoin.rs:686-699`). Only `OutputType::External` outputs get `data` attached and flow up to Substrate for crediting; the comment in `OutputType` states `Change` outputs "should be added to the available UTXO pool with no further action" (`processor/src/networks/mod.rs:77-81`). In `Scheduler::add_outputs`, every non-Branch output — including externally-forged `Change` and `Forwarded` outputs — is appended to `self.utxos` (`processor/src/multisigs/scheduler/utxo.rs:293-295`), becoming spendable protocol balance aggregated into future payment plans. A `Branch` output is worse still: if its amount collides with an entry in `self.plans`, it triggers `self.execute(vec![utxo], payments, ...)`, i.e., a signed transaction spending the attacker's output to queued payments (`utxo.rs:276-291`).

The `presumed_origin` field (input[0]'s spent script, `bitcoin.rs:707-729`) is set on all outputs, but it is only consulted for refunds of credited deposits; there is no logic returning a non-External output to its sender. This is exactly the Cooler pattern: the "philanthropic/affiliate" capability (paying internal scripts on the owner's behalf) exists with no safeguard, and the value always ends up with the owner — here, the multisig.

### Impact Explanation
An unprivileged Bitcoin user can lose their entire transfer by paying a derivable internal address. These addresses are exposed through the `Network` trait (`forward_address`, `change_address`, `branch_address`) and are used in InInstruction/forwarding flows, so they are plausible payment targets a user could confuse for a deposit address — or be tricked into paying. Once paid, the output is absorbed into the multisig's UTXO set and spent on unrelated scheduled payments; the sender receives no Serai credit and cannot be refunded, matching the Cooler report's "users unaware of how the code works could lose all transferred funds" impact.

### Likelihood Explanation
Reachable by any party who can broadcast a Bitcoin transaction — no privileged position, key material, or validator status is needed. The offsets are fixed `Secp256k1::hash_to_F("Serai Bitcoin Output Offset", …)` constants and the group key is public, so the scripts are trivially computable. Exploitation as an attack (tricking victims into paying these addresses) requires social engineering, but accidental misattribution is also plausible given the addresses are structurally indistinguishable P2TR outputs from the deposit address. Note the in-code comment (`networks/mod.rs:68-69`) acknowledges forged branch outputs as "equally as usable," but that rationale only covers the protocol's perspective — it does not address the sender's loss or the Branch-triggered signing, so this remains a valid analog rather than a documented-safe case.

### Recommendation
Track and treat non-External outputs originating from transactions the multisig did not author differently: either refund them to `presumed_origin` via `refund_plan`, or at minimum emit a distinct event so they can be handled/credited manually. For `Branch` outputs, only execute `plans[amount]` when the branch output was created by a known in-flight plan (e.g., correlate via the eventuality/queued-plan bookkeeping in `queued_plans`/`created_output`) instead of accepting any on-chain output of the right amount. Consider requiring a whitelist/marker analogous to `canMakeRequest` so externally-originating payments to internal scripts are rejected rather than absorbed.
