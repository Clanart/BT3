### Title
Missing sign validation on `reward.mintingamount` governance parameter allows negative block minting/reward distribution - (File: kaiax/gov/param.go)

### Summary
The Octopus/appchain-anchor bug describes a class of issues where some setter functions validate a numeric/percentage bound while sibling setters of the same category omit the equivalent check, allowing an out-of-range value to reach downstream arithmetic and corrupt state. The Kaia governance parameter table in `kaiax/gov/param.go` exhibits the same inconsistency pattern for `reward.mintingamount`: unlike its sibling parameters `reward.minimumstake` and `reward.stakingrewardthreshold` (both `*big.Int`), which explicitly require `v.Sign() >= 0` in their `FormatChecker`, `reward.mintingamount` uses `noopFormatChecker`, which always returns `true` and performs no validation at all.

### Finding Description
In `kaiax/gov/param.go`, the `Params` map defines format checkers per governance parameter that gate what values are accepted when a governance vote sets a parameter: [1](#0-0) 
`RewardMinimumStake` explicitly rejects negative values via `v.Sign() >= 0`, and `RewardStakingRewardThreshold` does the same: [2](#0-1) 

However `RewardMintingAmount`, a `*big.Int` parameter of the exact same shape used for the same purpose (an amount fed directly into block reward computation), uses `noopFormatChecker` which unconditionally returns `true`: [3](#0-2) [4](#0-3) 

This value flows unchecked into `RewardConfig.MintingAmount` at block-reward-calculation time: [5](#0-4) 

and is then used directly as the block minting amount in every reward-splitting code path (`getDeferredRewardSimple`, `getDeferredRewardFullKore`, `getDeferredRewardFullFlex`, `getDeferredRewardFullLegacy`), which distribute `minted` among the proposer, stakers, and funds and finally call `state.AddBalance` for each recipient: [6](#0-5) [7](#0-6) 

If a negative `reward.mintingamount` is accepted by governance, `minted` becomes negative, and the ratio-split arithmetic (`SplitFlex`/`Split`, `calcRemainder`) propagates negative amounts to `spec.Rewards`. `FinalizeState` then calls `state.AddBalance(addr, amount)` with a negative `*big.Int` for one or more recipients, which — because Go's `big.Int` arithmetic does not itself panic on negative operands — silently *decreases* the recipient's balance instead of increasing it, rather than being rejected as invalid. This is a direct state-consistency/value-manipulation bug: an attacker able to push a negative minting amount through governance could drain balances of arbitrary reward recipients (proposer/stakers/funds) every block, or cause consensus divergence if only some nodes reject negative-balance operations while others silently accept them (e.g., depending on any invariant checks elsewhere in `state.AddBalance`/`SubBalance`).

### Impact Explanation
`reward.mintingamount` directly controls native-token (KAIA) issuance and is distributed to the proposer, stakers, and protocol funds on every block via `FinalizeState`. Because the format checker for this specific parameter (unlike its sibling `*big.Int` reward parameters) performs no sign validation, an out-of-range (negative) value silently reaching `RewardConfig.MintingAmount` corrupts the reward-distribution arithmetic in `getter.go`, and ultimately affects `state.AddBalance` calls for every validator/fund address in the block, every block, until the parameter is corrected. This matches the reported bug class's impact rating (crash/incorrect accounting during reward distribution) but is potentially more severe here because it affects native-currency accounting on every block rather than a bounded operation.

### Likelihood Explanation
Exploitation requires a negative `reward.mintingamount` to actually be accepted through the governance parameter-setting path (header-vote governance or `GovParamContract`). This is a privileged/governance action (comparable to the "governance parameters" allowed analog category), not something arbitrary unprivileged senders can trigger directly, so likelihood is low — consistent with the original report's own "Likelihood: 1" rating for the analogous appchain-anchor issue. The core defect — an inconsistent, missing validation in a setter that has an equivalent, correctly-validated sibling in the same code — is nonetheless a clear and provable root-cause gap.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` in `kaiax/gov/param.go` consistent with `RewardMinimumStake` and `RewardStakingRewardThreshold`, e.g. requiring `v.Sign() >= 0` (and optionally an explicit upper sanity bound), so that governance cannot set a negative or otherwise invalid minting amount that would propagate into `RewardConfig.MintingAmount` and corrupt reward distribution arithmetic in `kaiax/reward/impl/getter.go`.

### Proof of Concept
1. Submit/accept a governance vote (or `GovParamContract` update) setting `reward.mintingamount` to a negative `*big.Int` value, e.g. `-1000000000000000000`.
2. Because `RewardMintingAmount`'s `FormatChecker` is `noopFormatChecker` (always `true`), the vote/parameter update is accepted and stored in the `ParamSet`. [3](#0-2) 
3. At the next block, `NewRewardConfig` copies this negative value into `RewardConfig.MintingAmount`: [8](#0-7) 
4. `getDeferredRewardSimple`/`getDeferredRewardFullKore` etc. treat `minted` as the block's minting reward and split it among proposer/stakers/funds, producing negative amounts in `spec.Rewards`.
5. `FinalizeState` calls `state.AddBalance(addr, amount)` for each recipient with the negative amount, decreasing balances instead of crediting rewards — an unintended and unauthorized value movement compared to expected reward-distribution semantics. [9](#0-8) 

**Note on completeness:** The exact permission model for who can submit a `reward.mintingamount` change (header-vote validator set vs. `GovParamContract` owner) and the internal panic/invariant behavior of `state.AddBalance`/state-object subtraction on negative `big.Int` inputs could not be fully confirmed from the indexed code (the `state_object.go`/`statedb.go` `AddBalance` implementation bodies were not returned in the search results). A Devin session with full repository access would be needed to confirm the exact governance-submission privilege boundary and the low-level state-transition behavior for negative balances.

```go
// getDeferredRewardSimple is for Simple policy.
func getDeferredRewardSimple(config *reward.RewardConfig, execFee, blobFee *big.Int) (*reward.RewardSpec, error) {
	spec := reward.NewRewardSpec()
	minted := new(big.Int).Set(config.MintingAmount)

	// Non-deferred mode
	if !config.DeferredTxFee {
		var proposer *big.Int
		if config.Rules.IsMagma {
			// In non-deferred mode, no fees to distribute here at the end of block processing.
			// Just distribute the minting reward to the proposer and stop.
			proposer = new(big.Int).Set(minted)
			execFee = big.NewInt(0)
		} else {
			// But Simple policy had a bug where transaction fees were distributed to the proposer here at the end of block processing
			// despite configured to non-deferred mode. To keep the backward compatibility, the buggy behavior retains until Magma.
			proposer = new(big.Int).Add(minted, execFee)
		}
		spec.Minted = new(big.Int).Set(minted)
		// Both exec fees and blob fees are burned during state transition in non-deferred mode,
		// not at finalization. TotalFee/BurntFee are completed by specWithNonDeferredFee (GetBlockReward only).
		spec.TotalFee = execFee // Note that we've set it to 0 for non-deferred + Magma (see above).
		spec.BurntFee = big.NewInt(0)
		spec.Proposer = proposer
		spec.IncRecipient(config.Rewardbase, proposer)
		return spec, nil
```
