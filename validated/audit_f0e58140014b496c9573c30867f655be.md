### Title
PedPoP `calculate_share` releases blame ECDH proof before the per-message proof-of-possession is verified — attacker reusing a victim's per-message key learns the victim's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

The DKG encryption layer relies on a Schnorr proof-of-possession (PoP) over each per-message ephemeral key to prevent the "key co-option" attack documented in `encryption.rs`: if Eve copies Alice's ephemeral key `X` into her own message to Bob, a blame event would reveal `b·X`, which also decrypts Alice's message to Bob. The PoP is supposed to guarantee that only the actual owner of the ephemeral scalar can trigger such a reveal.

However, the PoP is only *queued* into a `BatchVerifier` (`Encryption::decrypt`, `crypto/dkg/pedpop/src/encryption.rs:479-485`), while the blame-revealing `EncryptionKeyProof` (containing the ECDH shared key `proof.key = enc_key_recipient · msg.key`) is computed unconditionally at `encryption.rs:487-499`. In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:479-482`), a non-canonical decrypted share triggers an early `?` return with `blame: Some(blame)` — *before* `batch.verify_with_vartime_blame()` at `lib.rs:493` ever runs. The invalid-PoP message therefore produces a publicly broadcastable ECDH key reveal, exactly the disclosure the PoP was added to prevent.

This is the same bug class as the reference report: a guarded path (`decrypt_with_proof` verifies `msg.pop` inline at `encryption.rs:374-379`; the batch path checks the PoP for messages that reach it) versus an unguarded sibling path (`from_repr` early-error return) that reaches the sensitive disclosure without passing the check.

### Finding Description

Flow:

1. `Encryption::decrypt` (`encryption.rs:469-501`) queues `msg.pop` for batch verification under `BatchId::Decryption(l)`, then *immediately* computes `key = ecdh(&self.enc_key, msg.key)` and returns `EncryptionKeyProof { key, dleq }` — without knowing whether the PoP is valid.
2. `KeyMachine::calculate_share` (`lib.rs:476-482`) decrypts each share, then calls `C::F::from_repr(share_bytes.0)`. On a non-canonical scalar it returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` via `?`, short-circuiting before `batch.verify_with_vartime_blame()` (`lib.rs:493`).
3. The caller (`processor/src/key_gen.rs:419-425`) serializes this blame into `ProcessorMessage::InvalidShare`, which is routed to the coordinator and verified publicly via `AdditionalBlameMachine` (`processor/src/key_gen.rs:504-563`), making the ECDH key effectively public.

Attack: Eve observes Alice's honest `EncryptedMessage` to Bob over the authenticated channel and copies `msg.key = X` (Alice's ephemeral public key) into her own message to Bob, with a garbage `pop` and arbitrary ciphertext bytes. Bob's `decrypt` computes `proof.key = b·X` — identical to the ECDH key protecting Alice's message, since `cipher()` (`encryption.rs:101-133`) derives the ChaCha20 key/IV deterministically from `context || ecdh`. The decrypted bytes are pseudorandom; whenever they fail `from_repr` (for Ristretto/ed25519-class fields, ~15/16 of random 32-byte strings are non-canonical since `l ≈ 2^252`), `calculate_share` returns the blame proof containing `b·X` immediately, never verifying the PoP. Anyone can then recompute the ChaCha keystream and decrypt Alice's ciphertext — recovering the secret share `f_Alice(Bob)` of Alice's dealer polynomial. Eve can retry with fresh ciphertext until a non-canonical decode occurs.

### Impact Explanation

Confidentiality break of the DKG: an unprivileged participant (or any party able to submit a share message to a victim) can force public disclosure of another participant's encrypted secret share by reusing that victim's ephemeral key — the precise attack the PoP comment at `encryption.rs:84-90` claims to prevent ("When they do, they'd reveal bX, revealing Alice's message to Bob… the proof-of-possession is also included… ensuring only those actually with per-message keys can claim to use them"). Revealing `f_Alice(Bob)` gives the attacker points on honest dealers' polynomials for arbitrary victim indexes; combined with shares legitimately addressed to the attacker and repetitions across multiple victims, this reduces the effective threshold secrecy and can contribute to recovering a dealer's contributed secret. It also deterministically aborts the key-generation session. Impact: confidentiality of secret shares (key share disclosure) — Medium.

### Likelihood Explanation

Reachable by any party who can deliver a `EncryptedMessage` to a PedPoP participant: the attack requires only copying an observed public point `X` and submitting malformed bytes — no discrete-log knowledge and no valid PoP needed, since the PoP check is skipped on the early-decode-error path. Per-attempt success probability is the probability that the keystream-masked ciphertext decodes as non-canonical (≈ 1 − l/2^256; ~94% for 252-bit fields), and retries are unbounded within a session attempt. One caveat I could not fully verify within this pass: whether a given deployment deduplicates blame submissions — but the reveal happens at the moment `InvalidShare` is produced, regardless of downstream blame adjudication, since the `EncryptionKeyProof` itself is what gets serialized and circulated (`processor/src/key_gen.rs:424`).

### Recommendation

Verify the PoP *before* releasing or computing the blame key material on every error path:

- In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:479-482`), do not attach `blame` to the `from_repr` failure until the queued batch has been verified; equivalently, verify the batch (or at least `BatchId::Decryption(l)` statements) before returning any `EncryptionKeyProof`.
- In `Encryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:479-499`), verify `msg.pop` synchronously before computing `ecdh`/building the proof, or return the proof only after the batch verification confirms `BatchId::Decryption(l)` passed.
- Mirror the guarded sibling: `Decryption::decrypt_with_proof` (`encryption.rs:374-379`) already checks `msg.pop.verify(...)` before using `proof.key` — the share-decoding path should enforce the same ordering.

### Proof of Concept

Precondition: a Pedersen DKG session (e.g., Ristretto, `t`/`n` params) where Eve is a participant sending a share to honest Bob; Eve can observe Alice→Bob's `EncryptedMessage` on the authenticated channel.

1. Alice sends Bob `EncryptedMessage { key: X, pop: π_A, msg: c_A }` where `c_A = f_A(Bob) ⊕ ChaCha20(K)`, `K = H(context || b·X)`, `b` = Bob's encryption secret.
2. Eve constructs `msg_evil = EncryptedMessage { key: X, pop: <arbitrary bytes>, msg: <random bytes c_E> }` — copied key, invalid PoP.
3. Bob's `machine.calculate_share(&mut rng, shares)` processes `msg_evil`:
   - `decrypt` queues `pop` under `BatchId::Decryption(Eve)` (unverified), computes `proof.key = b·X`, and returns the `EncryptionKeyProof` (`encryption.rs:487-499`).
   - `C::F::from_repr(c_E ⊕ ChaCha20(K))` yields `None` with ~15/16 probability → `PedPoPError::InvalidShare { participant: Eve, blame: Some(proof) }` returned at `lib.rs:480-482`, skipping `batch.verify_with_vartime_blame()`.
4. Bob's processor emits `ProcessorMessage::InvalidShare { blame: Some(proof.serialize()) }` (`processor/src/key_gen.rs:419-425`); `proof.key = b·X` is now public.
5. Any observer recomputes `K' = cipher(context, b·X)` and decrypts Alice's `c_A`, recovering Alice's share to Bob.
6. If step 3's decode happens to be canonical (≈1/16), Eve retries with new `c_E`; each attempt independently leaks with high probability.
