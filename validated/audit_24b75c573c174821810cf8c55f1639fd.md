### Title
On-chain price-derived swap ratio with zero-slippage buyback swap in `SmartWomConvert::smartConvert` enables sandwich-attack fund loss on every protocol harvest - (File: wombat/SmartWomConvert.sol)

### Summary
`SmartWomConvert::smartConvert` decides how much WOM to swap for mWOM by reading the pool's current exchange rate on-chain via `currentRatio()`, which calls `IWombatRouter(router).getAmountOut(...)` — a live pool-state price read analogous to reading `pool.slot0` in the Uniswap report. The buyback swap itself is executed with a hardcoded `0` minimum output, relying only on a much weaker aggregate check afterward.

### Finding Description
`currentRatio()` computes `mWomToWom` by querying `IWombatRouter.getAmountOut` against `womMWomPool` at call time [2](#0-1) . This value directly determines `convertRatio` and thus `amountToSwap`/`buybackAmount` inside `smartConvert` [3](#0-2) . The subsequent `_convertFor` performs the actual swap of `buybackAmount` WOM→mWOM through `IWombatRouter.swapExactTokensForTokens` with the minimum-out parameter hardcoded to `0`, i.e., no real slippage protection on the swap leg itself [4](#0-3) . The only downstream guard is `convertAmount + amountRec < _minRec` [5](#0-4) , and in the `smartConvert` path `_minRec` is set to the full `_amountIn`, i.e., a 1:1-with-input floor rather than a true slippage bound derived from actual market depth.

Critically, this whole flow is triggered automatically and without any caller-supplied slippage parameter whenever protocol fees are routed to mWOM: `WombatStaking::_sendRewards` calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` unconditionally on every harvest that produces WOM fees [1](#0-0) . This code path is reached by an ordinary wallet simply calling `deposit`, `withdraw`, or `harvest` on any `WombatPoolHelper`/`WombatPoolHelperV2` (or `depositLP`), since those all funnel into `WombatStaking::_toMasterWomAndSendReward` → `_sendRewards` [6](#0-5) . Because `currentRatio()` is read from the same manipulable Wombat pool used for the swap, and the buyback swap has zero slippage protection, an attacker can sandwich any such transaction: front-run to depress `womMWomPool`'s WOM→mWOM rate (or otherwise skew it) so that `smartConvert` computes a larger `buybackAmount` than intended, execute the zero-min-out swap against the manipulated pool, and back-run to restore price, extracting value that would otherwise have compounded into the protocol's mWOM reward pool.

### Impact Explanation
Because `smartWomConverter.smartConvert` is invoked unconditionally as part of fee distribution on ordinary deposit/withdraw/harvest calls, this is not merely a user-slippage issue for an individual swapper — it degrades the value of the WOM fee that would otherwise become mWOM yield queued to `BaseRewardPool` via `queueNewRewards`. Repeated sandwiching of this automatic, zero-slippage-protected conversion siphons value out of protocol-collected fees intended for reward distribution, representing theft/permanent loss of unclaimed yield destined for stakers.

### Likelihood Explanation
Likelihood is high: the vulnerable call is executed on essentially every harvest cycle (any user's `deposit`/`withdraw`/`harvest` on any active Wombat pool helper triggers it), requires no special permission, and MEV searchers routinely monitor mempools for sandwichable zero-slippage swaps. `womMWomPool` liquidity depth determines exact profitability but the `0` min-out on the buyback swap removes any economic barrier to the attack.

### Recommendation
Remove the on-chain-computed `0` minimum output in the buyback swap inside `SmartWomConvert::_convertFor`; require callers of `smartConvert` (i.e., `WombatStaking::_sendRewards`) to supply/verify an explicit, freshly-computed minimum acceptable mWOM amount for the swap leg itself (not just an aggregate floor equal to input amount), or replace the on-chain `getAmountOut`/spot-price-derived ratio decision with a TWAP-based or governance-configured static ratio, consistent with the cited report's recommendation to avoid deriving slippage bounds from manipulable on-chain spot prices.

### Proof of Concept
1. Attacker observes an upcoming `harvest`/`deposit`/`withdraw` transaction on any active Wombat pool helper (mempool-visible, permissionless to trigger by any wallet, including the attacker themselves calling `harvest()`).
2. Front-run: attacker swaps WOM into `womMWomPool` to shift the pool's exchange rate in a way that increases the `buybackAmount` computed by `smartConvert`'s `currentRatio()`/`maxSwapAmount()` logic [7](#0-6) .
3. Victim transaction executes, triggering `WombatStaking::_sendRewards` → `smartWomConverter.smartConvert(feeAmount, 0)` [8](#0-7) , which swaps `buybackAmount` WOM for mWOM at the manipulated rate with `0` minimum output [9](#0-8) .
4. Back-run: attacker reverses the initial swap, capturing the value difference extracted from the fee-conversion swap, while the aggregate check `convertAmount + amountRec >= _minRec` still passes since `_minRec` only enforces a 1:1 floor against the original input, not a market-fair rate.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
