### Title
Just-in-time voting lets an attacker capture bribe rewards without time-weighted exposure, diluting long-term voters' yield - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BribeRewardPool` (extending `BaseRewardPoolV2`) credits rewards instantly via `rewardPerTokenStored` updates in `_provisionReward`, rather than streaming them over time. Because `WombatBribeManager.vote()`/`unvote()` let any vlMGP holder instantly change their staked balance in the rewarder immediately before/after a `queueNewRewards`/`donateRewards` call (including atomically via `voteAndCast`), an attacker can capture a pro-rata share of a bribe reward while holding voting weight for effectively zero time, at the expense of long-term voters.

### Finding Description
`BribeRewardPool.stakeFor`/`withdrawFor` (called from `WombatBribeManager.vote`/`unvote`, [1](#0-0) , [2](#0-1) ) update `_balances`/`totalSupply` and snapshot `userRewardPerTokenPaid` via the `updateRewards` modifier, then immediately allow reward accrual against the new balance [3](#0-2) .

Reward accounting in `BaseRewardPoolV2._provisionReward` bumps `rewardPerTokenStored` **instantly and fully** based on `totalStaked()` at the moment `queueNewRewards`/`donateRewards` is called, with no time-weighting or streaming (unlike a `rewardRate`/`periodFinish` design): [4](#0-3) 

`earned()`/`_earned()` compute reward purely from current balance times the delta between `rewardPerToken` and the user's last-paid checkpoint, with no minimum holding duration check: [5](#0-4) 

Exploit flow:
1. Attacker holds (or briefly locks) some vlMGP giving `getUserVotable` capacity.
2. Attacker calls `WombatBribeManager.vote(_lps, [+X])`, which calls `stakeFor(msg.sender, X)` on the pool's `BribeRewardPool`, snapshotting `userRewardPerTokenPaid` at the pre-reward value and increasing `totalSupply`/`_balances[attacker]`.
3. In the same or immediately following transaction, `queueNewRewards`/`donateRewards` is triggered (either front-run against a pending manager/keeper call, or - even more directly - the attacker calls `WombatBribeManager.voteAndCast()`, which chains `vote()` then `castVotes()` in one atomic call, and `castVotes` harvests bribes from the Wombat voter and forwards them via `queueNewRewards` to the same rewarder the attacker just staked into).
4. `rewardPerTokenStored` jumps up based on `totalStaked()` that now includes the attacker's freshly added `X`.
5. Attacker calls `unvote(_lp)` (or `vote(_lps,[-X])`), which calls `withdrawFor(msg.sender, X, true)`, triggering `_getReward` and transferring the attacker's full pro-rata share of the reward - despite having held vote weight for zero time-weighted duration.

No modifier, cooldown, or minimum-staking-duration check in `vote`/`unvote`/`stakeFor`/`withdrawFor` prevents this. `onlyManager`/`onlyOperator` guard who can queue rewards or move balances internally, but not the timing relationship between staking and reward injection, and `vote`/`unvote`/`castVotes`/`voteAndCast` are all unprivileged/public functions.

### Impact Explanation
This results in theft of unclaimed yield from long-term voters: every bribe distribution can be partially or fully siphoned by opportunistic just-in-time voters who add stake right before (or atomically trigger) reward injection and withdraw immediately after, diluting the `rewardPerTokenStored`-based entitlement of voters who held their position throughout the epoch. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Highly feasible and repeatable: the attacker only needs some existing locked vlMGP (a normal, cheap precondition) and calls to public functions (`vote`, `unvote`, or the single atomic `voteAndCast`) with no cooldown protection. It can be repeated every time a bribe/reward is queued for any pool, and does not require flash loans, reentrancy, or elevated privileges - `voteAndCast` even removes the need to front-run anything, since the attacker triggers the harvest themselves in the same transaction as their vote increase.

### Recommendation
Convert bribe reward distribution to a time-streamed model (e.g., `rewardRate` over a `rewardsDuration`, à la Synthetix `StakingRewards`) instead of instantaneously bumping `rewardPerTokenStored` on `_provisionReward`. Alternatively/additionally, enforce a minimum holding period before a voter's newly added stake becomes eligible for a given reward snapshot (e.g., checkpoint votes by epoch and only allow claims for balances held before the epoch's bribe was queued), and/or add a cooldown between `vote` (increase) and `unvote`/`vote` (decrease) for the same pool.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, a `BribeRewardPool` for a test LP pool, mock `vlMGP` giving `attacker` and `longTermVoter` lockable balances, and a mock reward token.
2. `longTermVoter` calls `vote([lp],[+100e18])` and holds.
3. Advance no time (or arbitrary time) - simulate a pending bribe: mint reward tokens to a manager account.
4. In one transaction: `attacker` calls `vote([lp],[+100e18])` then immediately (same tx or next tx) the manager/`castVotes` path calls `queueNewRewards`/`donateRewards` injecting `1000e18` reward tokens, followed by `attacker` calling `unvote(lp)`.
5. Assert `rewardToken.balanceOf(attacker) > 0` and equals `attacker`'s pro-rata share (`100/(100+100) * 1000e18`), despite `attacker` holding stake for 0 elapsed blocks/time.
6. Assert `longTermVoter`'s remaining claimable balance after `earned()` is diluted by the attacker's share, i.e., `longTermVoter.earned(rewardToken) < 1000e18` even though they held their vote through the entire distribution period.

    function stakeFor(address _for, uint256 _amount)
        external
        virtual
        onlyOperator
        updateRewards(_for, rewardTokens)
    {
        totalSupply = totalSupply + _amount;
        _balances[_for] = _balances[_for] + _amount;

        emit Staked(_for, _amount);
    }

    /// @notice Updates informaiton for a user in case of a withdraw. Can only be called by the Masterchief operator
    /// @param _for Address account
    /// @param _amount Amount of withdrawed tokens by the user on masterchief
    function withdrawFor(
        address _for,
        uint256 _amount,
        bool claim
    ) external virtual onlyOperator updateRewards(_for, rewardTokens) {
        totalSupply = totalSupply - _amount;
        _balances[_for] = _balances[_for] - _amount;

        emit Withdrawn(_for, _amount);

        if (claim) {
            _getReward(_for);
        }
    }

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
