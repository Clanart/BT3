### Title
Aggregate Schnorr signature malleability via non-binding aggregation weights - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives the per-signature aggregation weights `z_i` from a transcript that binds only the per-signer challenges — not the nonce commitments `Rs` contained in the signature itself. Because the weights are publicly recomputable before the `Rs` are fixed, anyone observing a valid aggregate signature can produce a distinct, differently-encoded aggregate signature that still verifies for the same signers and message. This is the direct analog of ECDSA signature malleability, reachable through `SchnorrAggregate::read` + `verify`, and concretely through the Tendermint `verify_aggregate` path which accepts attacker-supplied bytes.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, verification checks:

```
Σ z_i·R_i + Σ z_i·c_i·A_i − s·G = 0
```

where each `z_i = weight(&mut digest)` and `digest` is built only from `dst` plus `append_message(b"challenge", challenge_i)` — see `verify` (lines 127–146) and `weight` (lines 22–65). The `Rs` and `s` come from untrusted bytes via `SchnorrAggregate::read` (lines 77–88).

Since `z_i` depends only on the challenges (which are derivable from the public keys, the `Rs` themselves, and the message — in `verify_aggregate` the challenges are recomputed as `challenge(genesis, key, R_i, msg)`), the weight sequence is fully determined by the public inputs. An observer can therefore malleate: pick any scalar `t`, replace `R_1` with `R_1 + t·G` and `s` with `s + z_1·t`. The verification equation is invariant:

```
z_1·(R_1 + t·G) − (s + z_1·t)·G = z_1·R_1 − s·G
```

The same holds for any subset of indices. Every such mutation yields a byte-distinct aggregate signature that `SchnorrAggregate::verify` accepts. The root cause is that the aggregation transcript omits the `Rs` (and `s`), so the weights fail to bind the signature's own contents — the exact structural flaw behind Schnorr half-aggregation malleability and the analog of ECDSA's `(r, s)` / `(r, n−s)` malleability.

The reachable public path is `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs` (lines 200–229), which deserializes a validator-supplied `AggregateSignature` via `SchnorrAggregate::<Ristretto>::read` and calls `aggregate.verify(DST, ...)` — no privileged position required, only the ability to submit or relay aggregate signature bytes.

### Impact Explanation
A third party (any node or relayer that sees the aggregated consensus signature) can produce an unlimited number of distinct valid aggregate signatures over the same signer set and message. Any consumer that treats aggregate signature bytes as unique — deduplication by signature hash, replay caches, slashing evidence keyed on signature bytes, or identification of "the" valid commit for a block — can be confused or bypassed. Two byte-distinct valid aggregates for the same consensus vote can be propagated as if they were different attestations. This mirrors the impact class of the reported ECDSA malleability issue (signature non-uniqueness) rather than forgery of a new message.

### Likelihood Explanation
The malleation requires only field arithmetic on publicly known values (`z_i` is recomputed from public challenges; `t` is attacker-chosen). No secret keys, no collusion, and no control over signers is needed — just access to one valid aggregate signature, which is broadcast by design. It is deterministically exploitable.

### Recommendation
Bind the aggregate signature's contents into the weight transcript. In both `SchnorrAggregator::aggregate`/`complete` and `SchnorrAggregate::verify`, append each `R_i`'s canonical encoding to the digest before deriving `z_i` (e.g., `digest.append_message(b"nonce", R_i.to_bytes())`, interleaved with the challenge), so the weights commit to the exact `Rs` being verified. Alternatively, hash the full serialized aggregate `(Rs, s-prefix)` into the transcript prior to weight derivation. This makes any mutation of `Rs` or `s` change the weights and break verification.

### Proof of Concept
```rust
// Given a valid aggregate signature `agg` for signers/challenges,
// produce a distinct valid aggregate for the same signers/message.

// 1. Recompute the weights exactly as `verify` does.
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
    digest.append_message(b"challenge", challenge.to_repr());
}
let z1 = weight::<_, C::F>(&mut digest); // weight for index 0

// 2. Choose arbitrary t, malleate R_0 and s.
let t = C::F::random(&mut OsRng);
let malleated = SchnorrAggregate {
    Rs: {
        let mut rs = agg.Rs().to_vec();
        rs[0] = rs[0] + C::generator() * t;
        rs
    },
    s: agg.s + z1 * t,   // z_i*t is a public scalar; no secret needed
};

// 3. `malleated.serialize()` is byte-distinct from `agg.serialize()`, yet:
assert!(malleated.verify(dst, keys_and_challenges));
```

The mutated `(Rs, s)` satisfies `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G = 0` because `z_1·(R_0 + tG) − (s + z_1 t)G = z_1·R_0 − sG`, leaving the verification sum unchanged.
