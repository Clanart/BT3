### Title
Improper authentication in EVM `addr` precompile `associate`/`associatePubKey` due to missing signed-message domain binding - (File: precompiles/addr/addr.go)

### Summary
The `associate` function of the `addr` precompile recovers an address-owning public key from an attacker-controlled `(v, r, s, customMessage)` tuple and immediately uses it to permanently bind an EVM address to a Sei address on-chain. [3](#0-2)  There is no on-chain enforcement that `customMessage` is the intended association message (e.g. the "Please sign this message to link your EVM and Sei addresses..." string used by the official client, seen only in the test harness) [4](#0-3) , nor any chain-ID/nonce/purpose domain separator baked into the hash before `crypto.Keccak256Hash`. [5](#0-4)  This is the same bug class as the reported cas-auth issue: a party can authenticate/associate itself using a credential (a signature) that was produced for a completely different purpose/source, because the verifying code does not bind the signature to the specific association context.

### Finding Description
`associate` takes raw ECDSA signature components and an arbitrary message from the transaction sender, computes `customMessageHash := crypto.Keccak256Hash([]byte(customMessage))`, and recovers `evmAddr`, `seiAddr`, and `pubkey` purely from `(v, r, s, customMessageHash)` via `helpers.GetAddresses`. [6](#0-5) [7](#0-6)  Because Ethereum ECDSA signatures are not bound to any specific application or message-purpose unless the verifier enforces a fixed prefix/domain, *any* valid `(v, r, s)` signature ever produced by a victim's private key over *any* message string can be replayed by an unrelated third party as `customMessage` here, since the contract performs no comparison against an expected canonical message format. The resulting `associateAddresses` call checks only that the derived `seiAddr` has not already been associated, then permanently writes the EVM<->Sei address link. [8](#0-7)  This means a signature leaked or observed from an entirely different context (a different dApp's `personal_sign` prompt, an off-chain login flow, a permit-style signature, etc.) can be repurposed to trigger an on-chain address association for the victim without their consent for that specific action — the "authenticate with credentials from a different source" failure mode.

### Impact Explanation
Address association is a security-sensitive, one-time, irreversible action gating EVM/Cosmos identity linkage used by precompiles, tokenfactory/bank flows, and other pointer/CW<->EVM bridging logic that key off `GetEVMAddress`/`GetSeiAddress`. [9](#0-8)  Because the "already associated" check in `associateAddresses` is one-directional (keyed off `seiAddr`), an attacker can front-run or grief a victim's association by submitting a replayed signature first, permanently taking the association for that Sei/EVM pair (since re-association is rejected once set), denying the legitimate association flow to the rightful signer and potentially disrupting any downstream funds/flows that assume the association happens under the victim's control and timing. [10](#0-9) 

### Likelihood Explanation
Exploitation requires only that the attacker obtain any one valid ECDSA signature produced by the victim's EVM key over any message — a low bar given how common `personal_sign`/`eth_sign` interactions are across the broader EVM ecosystem (logins, permits, mint approvals, etc.), and the attacker can submit the replay transaction themselves at any time since `associate` has no caller restriction. This is directly reachable by any unprivileged EVM transaction sender calling the precompile at `0x0000000000000000000000000000000000001004`.

### Recommendation
Bind the signed message to the specific association action and chain context on-chain rather than trusting client-supplied `customMessage` verbatim: require the contract to reconstruct/verify a fixed, canonical message template server-side (including the EIP-191 personal-sign prefix, chain ID, and the target Sei address/nonce) instead of hashing an arbitrary caller-supplied string, so a signature produced for any other purpose cannot be replayed into `associate`/`associatePubKey`.

### Proof of Concept
1. Victim signs any unrelated message `M` with their EVM key in a different application (e.g., a `personal_sign` login prompt), producing `(v, r, s)`.
2. Attacker observes/obtains this signature (e.g., via a malicious dApp, phished login page, or public disclosure) and calls the `addr` precompile's `associate(v, r, s, M)` with `M` exactly as originally signed. [11](#0-10) 
3. `GetAddresses` recovers the victim's `evmAddr`/`seiAddr`/`pubkey` from `(v,r,s, keccak256(M))`, and `associateAddresses` permanently links them on-chain, regardless of the fact that the signature was never intended to authorize association. [12](#0-11)

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p PrecompileExecutor) associatePublicKey(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	// Takes a single argument, a compressed pubkey in hex format, excluding the '0x'
	pubKeyHex := args[0].(string)

	pubKeyBytes, err := hex.DecodeString(pubKeyHex)
	if err != nil {
		return nil, 0, err
	}

	// Parse the compressed public key
	pubKey, err := btcec.ParsePubKey(pubKeyBytes)
	if err != nil {
		return nil, 0, err
	}

	// Convert to uncompressed public key
	uncompressedPubKey := pubKey.SerializeUncompressed()

	evmAddr, seiAddr, pubkey, err := helpers.GetAddressesFromPubkeyBytes(uncompressedPubKey)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
