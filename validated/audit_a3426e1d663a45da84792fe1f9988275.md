### Title
Unvalidated GitHub-profile display name is embedded into `Co-Authored-By` git trailers, allowing message/trailer injection - (File: `app/src/ui/changes/commit-message.tsx`)

### Summary
The bug class in the source report is "attacker-controlled input accepted without any character/format validation before being written into permanent state that the application (and its users) later trust." The closest reachable analog in GitHub Desktop is the co-author feature: a co-author's `name`/`email`, which come from the GitHub API and are therefore controlled by whichever GitHub user is selected, are concatenated into a `Co-Authored-By: <name> <email>` trailer with **no validation of illegal characters** (no newline/CR check, no "crud character" check), unlike the equivalent `user.name`/`user.email` values which *are* validated with `gitAuthorNameIsValid` before being accepted in Preferences/Repository Settings.

### Finding Description
When building a commit, Desktop constructs co-author trailers directly from the `Author` objects associated with a selected mentionable GitHub user: [1](#0-0) 

`a.name` and `a.email` originate from the GitHub API's mentionables/user endpoints (`IAPIMentionableUser.name`, `IAPIMentionableUser.email`, or `fetchUser().name`), i.e. an attacker-controlled GitHub profile display name: [2](#0-1) [3](#0-2) 

This value is passed unchanged into `mergeTrailers`, which shells out to `git interpret-trailers --trailer token=value`: [4](#0-3) 

and finally into `formatCommitMessage`, which produces the literal commit message text used for the commit: [5](#0-4) 

Compare this to the local git identity path, where Desktop explicitly validates that `user.name`/`user.email` do not consist solely of "crud" characters (and, separately, `sanitizedRefName`/`testForInvalidChars` are used elsewhere to strip newlines and control characters from user-typed branch names/URLs): [6](#0-5) [7](#0-6) 

No equivalent guard exists for GitHub API-sourced author `name`/`email` used in `getCoAuthorTrailers()`. Because `--trailer token=value` is passed to git without the app first stripping `\n`/`\r` from `value`, a GitHub account whose display name contains an embedded newline (a value the profile-name field on github.com does not itself forbid at the API/consumption layer Desktop relies on) would have that newline preserved through to the commit message body once the co-author is selected and a commit is made, since `mergeTrailers` is invoked without `--unfold` at commit time.

### Impact Explanation
This allows an attacker who can be added/searched as a co-author (any GitHub user visible to the mentionables/search API for a repo, e.g. an org member, a contributor, or anyone the victim manually searches for) to inject attacker-controlled lines into the commit message that the victim did not type and did not review as part of the summary/description fields — a silent corruption of what the user actually commits and pushes. Depending on content, this could be used to forge additional trailers (e.g., a fake `Signed-off-by:`/`Reviewed-by:` line, or content that spoofs a different author), or to smuggle text into commit history that renders differently in different tools (Desktop's own multi-line trailer folding vs. GitHub's web rendering of trailers).

### Likelihood Explanation
Reaching this path requires no local access, no admin rights, and no pre-existing malware: the attacker only needs to control a GitHub account (its display name) that becomes selectable/searchable as a co-author for a repository the victim is committing to, and the victim needs to add that account as a co-author (a normal, expected workflow) and commit. There is no confirmation dialog that shows or re-validates the raw trailer text before it becomes part of the permanent commit history.

### Recommendation
Apply the same "crud"/control-character validation used for local `user.name`/`user.email` (`gitAuthorNameIsValid`, or a newline/`\r`/`\n`-stripping pass such as `testForInvalidChars`/`sanitizedRefName`) to co-author `name` and `email` values before they are placed into `getCoAuthorTrailers()`, and/or reject/collapse embedded newlines when constructing the `Co-Authored-By` trailer value in `mergeTrailers`/`formatCommitMessage`.

### Proof of Concept
1. As attacker, set a GitHub account's public display name to a value containing an embedded newline followed by attacker-chosen text, e.g. `Foo\nSigned-off-by: Evil <evil@example.com>` (submitted via whatever channel populates the `name` field consumed by `IAPIMentionableUser`/`IAPIFullIdentity`).
2. As victim, in Desktop, open a repository this attacker account can be mentioned/co-authored in, add the attacker as a co-author via the autocomplete co-author picker (`commit-message.tsx`).
3. Make a commit. `getCoAuthorTrailers()` (`app/src/ui/changes/commit-message.tsx:577-585`) builds `Foo\nSigned-off-by: Evil <evil@example.com> <email>` as the trailer value, which is passed to `mergeTrailers`/`git interpret-trailers --trailer` (`app/src/lib/git/interpret-trailers.ts:152-176`) without newline stripping.
4. Inspect the resulting commit message: it contains an extra line/trailer that the victim never typed and did not intend to commit, verifying that the message was silently corrupted with attacker-controlled content.

Note: I was not able to execute this PoC against a live GitHub API response or confirm git's exact on-disk handling of an embedded `\n` inside a single `--trailer token=value` CLI argument (whether git's interpret-trailers itself strips/folds it before writing, which would reduce but not necessarily eliminate impact); this should be verified empirically by a Devin session with git/dugite available, since the index does not let me execute code.

```typescript
export async function mergeTrailers(
  repository: Repository,
  commitMessage: string,
  trailers: ReadonlyArray<ITrailer>,
  unfold: boolean = false
) {
  const args = ['interpret-trailers']

  // See https://github.com/git/git/blob/ebf3c04b262aa/Documentation/git-interpret-trailers.txt#L129-L132
  args.push('--no-divider')

  if (unfold) {
    args.push('--unfold')
  }

  for (const trailer of trailers) {
    args.push('--trailer', `${trailer.token}=${trailer.value}`)
  }

  const result = await git(args, repository.path, 'mergeTrailers', {
    stdin: commitMessage,
  })

  return result.stdout
}
```

```typescript
export async function formatCommitMessage(
  repository: Repository,
  context: ICommitContext
) {
  const { summary, description, trailers } = context

  // Git always trim whitespace at the end of commit messages
  // so we concatenate the summary with the description, ensuring
  // that they're separated by two newlines. If we don't have a
  // description or if it consists solely of whitespace that'll
  // all get trimmed away and replaced with a single newline (since
  // all commit messages needs to end with a newline for git
  // interpret-trailers to work)
  const message = `${summary}\n\n${description || ''}\n`.replace(/\s+$/, '\n')

  return trailers !== undefined && trailers.length > 0
    ? mergeTrailers(repository, message, trailers)
    : message
}
```

```typescript
// Git forbids names consisting entirely of these characters
// (what Git calls crud) but as long as there's at least one
// valid character in the name it'll strip the crud and be happy.
// See https://github.com/git/git/blob/e629a7d28a405e/ident.c#L191-L203
const crudCharactersRe = /^[\x00-\x20.,:;<>"\\']+$/

/**
 * Returns a value indicating whether the given `name` is a valid
 * Git author name that can be used for the `user.name` Git config
 * setting without producing an error about disallowed characters
 * at commit time.
 *
 * This logic is intended to be an exact copy of that of Git's own
 * logic, see https://github.com/git/git/blob/e629a7d28a/ident.c#L401
 *
 * Note that this method considers an empty string to be a valid
 * author name.
 */
export function gitAuthorNameIsValid(name: string): boolean {
  return !crudCharactersRe.test(name)
}
```

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
