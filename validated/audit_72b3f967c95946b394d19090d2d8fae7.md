## Analysis: Missing wrapper-invalidation guard for map field merges (Python pyext) — analogous to Vim's tagstack/quickfix double-free

### Title
Stale Python wrapper referencing freed submessage on map-field merge overwrite — (File: `python/google/protobuf/pyext/message.cc`)

### Summary
The Vim CVE's failed invariant is: a cleanup path (window close) frees shared data (tagstack), while a second structure (quickfix list) retains a reference to the same data and is unaware it was already freed, causing a double-free/UAF when the second structure is later cleaned up. The Python protobuf C-extension has already identified and partially fixed this exact bug class for **oneof** fields — `MaybeReleaseOneofBeforeMerge()` / `FixupMessageAfterMerge()` in `python/google/protobuf/pyext/message.cc` exist specifically to detach stale Python wrapper objects before a C++-level `MergeFrom` frees/replaces the underlying submessage they point to (regression test `testOneofSwitchMergeUAF` in `python/google/protobuf/internal/message_test.py:2184` documents the prior UAF and its fix). However, this protection is explicitly **skipped for map/repeated fields**: [1](#0-0) 

### Finding Description
`MaybeReleaseOneofBeforeMerge` walks `self->composite_fields` and releases/detaches cached Python wrapper objects for singular message fields before the C++ `MergeFrom` runs, precisely because that merge can free/replace the underlying `Message*` the wrapper still points to. The condition `!descriptor->is_repeated()` deliberately excludes map fields, with the comment "For message map with same keys, it is overwrite" — an explicit acknowledgment that overwrite (not merge-in-place) happens for map values at colliding keys, but no equivalent detach/fixup logic is applied.

Test evidence confirms the "overwrite" (replace, not recursive merge) semantics for message-valued map entries at colliding keys: [2](#0-1) 

The Python binding for direct map-container merges also performs the merge with no wrapper invalidation step at all: [3](#0-2) 

The consuming-application exposure: an ordinary client can drive this via the public `MergeFromString`/`ParseFromString` API on a Python protobuf message. `MergeFromStringImpl` (the implementation backing both) calls the general `message->MergeFrom(*temp_message)` for the non-cleared (repeat-merge) path: [4](#0-3) 

If application code has previously fetched a submessage wrapper for a map key (`msg.some_map[key]`, caching a `CMessage` Python object pointing at the C++ submessage), and the client then supplies bounded, attacker-controlled binary bytes to `msg.MergeFromString(data)` containing a map entry with the same key, the underlying C++ map-value storage is replaced/freed by the wire-level merge — but the cached Python wrapper is not detached, unlike the already-fixed oneof case.

### Impact Explanation
The dangling wrapper produces a use-after-free on subsequent attribute access, and can produce a double-free when the stale wrapper is later garbage-collected/deallocated and attempts its own cleanup of memory already freed by the map-merge overwrite — structurally identical to the Vim CVE's tagstack/quickfix double free (two owners disagree on liveness of the same allocation after one path already freed it). Impact is bounded to the CPython extension process (crash/heap corruption), matching the "Medium" severity class of the referenced Vim issue (local, low complexity attacker-triggerable crash rather than remote code execution).

### Likelihood Explanation
Likelihood is limited by requiring a specific application usage pattern: the app must first materialize a Python wrapper for a message-typed map value (`obj = msg.map_field[key]`), then call `MergeFromString`/`MergeFrom` again with attacker-supplied bytes/messages containing a colliding key for that same map field. This is a plausible, unprivileged, ordinary-client-triggerable pattern (no special flags needed, unlike Vim's requirement of several non-default flags), but it does depend on trusted application code holding a live reference across the merge call — I could not fully confirm from the available index whether `MessageMapContainer`'s Python-level value cache (analogous to `composite_fields`) persists a wrapper across a `MergeFrom` call in the exact way needed to reproduce the dangling pointer (I was unable to inspect the cache/read path in `map_container.cc` before running out of tool iterations), nor could I directly inspect `Map::UntypedMergeFrom`'s low-level free/replace mechanics in `map.h`/`map.cc` — the "replace" behavior is inferred from the observable test outcome in `map_test.inc:2706-2717` rather than from direct source reading of the merge internals.

### Recommendation
Extend the existing detach/fixup mechanism (`MaybeReleaseOneofBeforeMerge` / `FixupMessageAfterMerge`) to cover message-valued map fields with colliding keys, mirroring the protection already applied to oneof fields: before invoking the C++ `MergeFrom` for a map field, detach any cached Python wrapper for keys present in both source and destination maps, and re-attach/fix up pointers afterward (as already done for singular message fields).

### Proof of Concept
Conceptual reproduction (not run; no execution environment available):
```python
from map_unittest_pb2 import TestMessageMap

m = TestMessageMap()
m.map_int32_message[1].optional_int32 = 5
sub = m.map_int32_message[1]          # caches Python wrapper for map value at key 1

other = TestMessageMap()
other.map_int32_message[1].optional_int32 = 9
data = other.SerializeToString()      # attacker-controlled bounded bytes

m.MergeFromString(data)               # map value at key 1 is replaced/freed in C++
print(sub.optional_int32)             # use-after-free: sub still refers to freed submessage
```
This mirrors the pattern already exercised by `testOneofSwitchMergeUAF` for oneof fields, but for the map-field code path that `MaybeReleaseOneofBeforeMerge` explicitly does not cover. [5](#0-4)

PyObject* MapReflectionFriend::MergeFrom(PyObject* _self, PyObject* arg) {
  MapContainer* self = GetMap(_self);
  if (!PyObject_TypeCheck(arg, ScalarMapContainer_Type) &&
      !PyObject_TypeCheck(arg, MessageMapContainer_Type)) {
    PyErr_SetString(PyExc_AttributeError, "Not a map field");
    return nullptr;
  }
  MapContainer* other_map = GetMap(arg);
  Message* message = self->GetMutableMessage();
  if (message == nullptr) return nullptr;
  const Message* other_message = other_map->parent->message;
  const Reflection* reflection = message->GetReflection();
  const Reflection* other_reflection = other_message->GetReflection();
  internal::MapFieldBase* field =
      reflection->MutableMapData(message, self->parent_field_descriptor);
  const internal::MapFieldBase* other_field = other_reflection->GetMapData(
      *other_message, other_map->parent_field_descriptor);
  field->MergeFrom(message->GetArena(), *other_field);
  self->version++;
  Py_RETURN_NONE;
}
