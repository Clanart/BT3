### Title
Panic on missing participant proof in `GeneratorPromotion::complete` enables unprivileged-participant DoS - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
`GeneratorPromotion::complete` performs an out-of-bounds access equivalent on attacker-influenced input: after checking only the *count* and *upper bound* of the `proofs` map keys, it unconditionally unwraps `proofs.get(&i)` for every participant `i` in `1..=n`. A proof map with the correct length (`n - 1`) and all keys `<= n`, but keyed to the wrong set of participants (e.g., containing the receiver's own index or a duplicate claimed index, while omitting a required participant), causes an `unwrap()` panic — a denial of service. This mirrors CVE-2014-9844's bug class: a crafted/attacker-shaped input reaches a read/index path that assumes the input covers the expected domain, without a membership check.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` validates:

- `proofs.len() == params.n() - 1` [1](#0-0) 
- every key `<= params.n()` [2](#0-1) 

It then iterates `i` over `1 ..= params.n()` and does `proofs.get(&i).unwrap()` [3](#0-2) 

The two guards verify cardinality and range but never verify that the map keys form exactly the set `{1..=n} \ {params.i()}`. A map of size `n - 1` whose keys are, for example, `{1..=n} \ {k}` for some `k != params.i()` (i.e., containing `params.i()` itself or missing `k` while duplicating coverage elsewhere) passes both checks, then panics at the `unwrap()` when `i == k`.

Compare with the analogous FROST path, which does perform full set validation: `ThresholdKeys::view` checks for duplicates, membership of `i`, and max index [4](#0-3) , and `validate_map` in `crypto/frost/src/sign.rs` is used for `sign`/`complete` [5](#0-4) . `GeneratorPromotion::complete` lacks the equivalent check.

`GeneratorProof` is deserialized from untrusted bytes via `GeneratorProof::read` (`read_G` + `DLEqProof::read`) [6](#0-5) , and the participant key under which each proof enters the map is derived from DKG session data controlled by the sending participant, making the malformed map reachable from public inputs.

### Impact Explanation
An `unwrap()` panic inside `complete` aborts key promotion for the victim participant. In a network where promotion is required to migrate shares to a new generator, a single faulty proof set causes the victim's promotion to crash rather than return a `PromotionError`, denying the node its rotated `ThresholdKeys` and stalling the key-rotation ceremony. Consistent with the CVE class (out-of-bounds access on crafted input → denial of service), severity is Medium: availability impact only, no secret leakage or forgery.

### Likelihood Explanation
Reachability requires the caller to key the `proofs` map by a participant identifier an attacker can influence (the natural implementation keys received `GeneratorProof` messages by claimed/sender participant index). If the surrounding protocol keys proofs by a strongly authenticated index that always yields a distinct key per sender and all `n - 1` senders submit proofs, the missing-key condition can't arise. However, the library itself neither documents nor enforces that requirement — the caller-facing contract is only the count and bound checks the function performs — so a caller that naively inserts proofs under self-declared indexes (or under indexes derived from malleable session data) exposes the panic. Likelihood is therefore moderate: it depends on integrator keying behavior the library fails to make safe.

### Recommendation
Before indexing, validate the key set exactly, e.g.:

```rust
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  if !proofs.contains_key(&i) {
    Err(PromotionError::IncorrectAmountOfParticipants { ... })?;
  }
}
if proofs.contains_key(&params.i()) {
  Err(PromotionError::InvalidParticipant { n: params.n(), participant: params.i() })?;
}
```

Replace `proofs.get(&i).unwrap()` with a fallible lookup returning `PromotionError::InvalidProof(i)` or a dedicated `MissingProof` error, so malformed participation sets yield errors instead of panics.

### Proof of Concept
```rust
// Setup: honest ThresholdKeys for participant `i` in an n-of-n set (produced by promote()).
let (promotion, our_proof) = GeneratorPromotion::<C1, C2>::promote(&mut rng, base_keys);
let params = promotion_base.params(); // n participants, i = params.i()

// Attacker participant `k` registers their proof under the receiver's own index `i`
// (or any index collision that displaces a required participant). The assembled map:
let mut proofs: HashMap<Participant, GeneratorProof<C1>> = HashMap::new();
for l in 1 ..= params.n() {
  let l = Participant::new(l).unwrap();
  if l == params.i() || l == k { continue; }
  proofs.insert(l, honest_proof_for(l));       // all honest proofs
}
proofs.insert(params.i(), attacker_proof);      // mislabeled: keyed to self index
// proofs.len() == n - 1, all keys <= n  => passes both guards,
// but participant `k` is missing.

// Panics at `proofs.get(&k).unwrap()` instead of returning PromotionError.
let _ = promotion.complete(&proofs); // thread panics: index out of domain
```

The guards accept the map because only `proofs.len()` and `max(key) <= n` are checked; the missing participant `k` is only detected — by panic — inside the verification loop.

**Uncertainty noted:** the panic is only reachable if the integrator keys the `proofs` map by attacker-influenced participant identifiers; if keyed strictly by authenticated sender indexes with all participants present, the malformed set cannot be constructed. The defect (missing set-membership validation before `unwrap()`) is nonetheless present in the in-scope code.
