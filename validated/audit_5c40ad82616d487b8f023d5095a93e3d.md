### Title
Binding factor `rho` is identical for every nonce of a participant, letting a malicious co-signer force two bound nonces to be equal (R_j = R_k) via `read_preprocess` - ([File: crypto/frost/src/nonce.rs](crypto/frost/src/nonce.rs))

### Summary
`BindingFactor::calculate_binding_factors` is intended to derive a per-nonce, per-participant binding factor, mirroring FROST's `rho`. Because the transcript clone is never advanced inside the loop, `challenge(b"rho")` returns the same value for every nonce index. An attacker who submits a crafted preprocess (parsed by `AlgorithmSignMachine::read_preprocess`) can set the commitments of two nonces equal, forcing two aggregate bound nonces `R_j` and `R_k` to be the same point. When an algorithm signs with multiple nonces whose challenges differ, this reuses an effective nonce across distinct challenges and allows recovery of the victim's secret key share — the same class of damage as a use-after-free/stale-state bug: a value that must be single-use is consumed twice.

### Finding Description
In `crypto/frost/src/nonce.rs:161-173`:

```rust
pub(crate) fn calculate_binding_factors<T: Clone + Transcript>(&mut self, transcript: &T) {
    for (l, binding) in &mut self.0 {
      let mut transcript = transcript.clone();
      transcript.append_message(b"participant", ...);
      binding.binding_factors = Some(
        (0 .. binding.commitments.nonces.len())
          .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
          .collect(),
      );
    }
}
```

The inner `map` calls `transcript.challenge(b"rho")` on an identical, un-advanced clone for every nonce index. Every nonce of a participant therefore receives the *same* binding factor, despite the comment claiming per-nonce factors are generated "just to ensure it never comes up as a question."

`BindingFactor::nonces` (nonce.rs:194-212) then computes each aggregate bound nonce as `R_{n,g} = Σ_l (D_{l,n,g} + rho_l * E_{l,n,g})`. Since `rho_l` is constant across `n`, a malicious participant `l` who submits a preprocess via `Commitments::read`/`read_preprocess` (an unprivileged, attacker-reachable parsing path in `sign.rs:276-281`) can simply copy its first nonce's commitments into its second nonce: `D_{l,1} = D_{l,0}`, `E_{l,1} = E_{l,0}`. The bound contributions for nonces 0 and 1 from `l` are then identical. Honest parties apply their own `d + rho*e` with the same `rho` but independent `d`, `e`, so the attacker's contribution being duplicated is only exploitable when combined with *all* signers' contributions — but because `rho` is fixed before anyone's `D`/`E` for nonce 1 commits to anything distinct, the attacker can instead set `D_{l,1} = D_{l,0} + X`, `E_{l,1} = E_{l,0}` after seeing all other preprocesses in the signing set (it sees them before `sign` is called in `share_internal`/`sign`), making `R_1 = R_0 + X` for a chosen `X`, or outright `R_1 = R_0` when it controls the marginal contribution.

With two Schnorr-type signatures produced under the same aggregate nonce point `R` but different challenges `c_0 != c_1` (the multi-nonce path explicitly supported by this FROST variant, per `spec/cryptography/FROST.md` lines 28-37), the resulting shares satisfy `s_0 = r + c_0 * λ * x` and `s_1 = r + c_1 * λ * x`, so the attacker solves `λ * x = (s_0 - s_1) / (c_0 - c_1)` — direct recovery of the victim's Lagrange-weighted secret share, and with `t` shares, the group private key.

### Impact Explanation
Secret key share recovery / full threshold key recovery by an unprivileged signing participant who only supplies a crafted preprocess message — exactly the consequence FROST's per-nonce binding factors exist to prevent, and the analog of a use-after-free: a nonce-binding value meant to be fresh per use is reused.

### Likelihood Explanation
Reachable whenever an in-scope `Algorithm` declares more than one nonce (`params.algorithm.nonces()` length > 1) and issues per-nonce challenges that differ — the library is explicitly designed for this case (multiple nonces "effectively including multiple Schnorr signatures within one signature"). The attacker only needs to participate in one signing session and submit two duplicated commitment pairs in its serialized preprocess. Note: for single-nonce algorithms (e.g., plain Schnorr, the Bitcoin `TransactionSignMachine` path which uses one machine per input), the bug is latent and not exploitable; severity assumes a multi-nonce algorithm is in use (as supported for e.g. multi-generator/multi-signature algorithms).

### Recommendation
Advance or re-clone the transcript per nonce so each nonce index yields a distinct challenge, e.g. `transcript.append_message(b"nonce", C::F::from(n as u64).to_repr())` before `challenge(b"rho")`, or derive `rho_{l,n} = H(rho_transcript || l || n)` per the IETF draft's per-item encoding.

### Proof of Concept
Attacker `l` participates in a signing session for an algorithm with `nonces().len() == 2`. In its preprocess it sets `NonceCommitments` for nonce 1 equal to nonce 0 (`generators[g].0 = [D, E]` identical). `read_preprocess` accepts the bytes. In `sign`, `calculate_binding_factors` assigns `binding_factors[l] = [rho, rho]` (same value twice). `B.nonces` produces attacker contributions `D + rho*E` that are identical for both nonces; since the attacker knows its own `d, e` and sees all preprocesses before signing, it can pick `D_1 = D_0 + Δ` to force `R_1 = R_0`. The victim's `sign_share` returns two shares `s_0, s_1` over the same nonce point under different per-nonce challenges; the attacker recovers `λ·x = (s_0 − s_1)/(c_0 − c_1)`.

Residual uncertainty: whether the deployed in-scope algorithms actually emit distinct challenges per nonce was not fully verifiable from the indexed code; if all in-scope algorithms use exactly one nonce, the practical severity drops to latent/informational.
