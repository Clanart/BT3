### Title
Unprivileged depositor can permanently stall the Bitcoin output scanner via an unbounded retry loop in `get_outputs` - (File: processor/src/networks/bitcoin.rs)

### Summary
CVE-2018-17144's relevant bug class is a remotely triggerable denial of service that takes consensus-critical nodes offline. In Serai, `Bitcoin::get_outputs` in `processor/src/networks/bitcoin.rs` contains an infinite retry loop when resolving the parent transaction of a deposit's first input: any `get_transaction` error is retried forever with a 5-second sleep, with no exit condition. Because `get_outputs` is called while holding the scanner's write lock, an unprivileged party who deposits to a Serai address can permanently halt all block scanning for every multisig on that processor — a persistent, restart-resistant liveness failure analogous to a crash loop.

### Finding Description
When scanning a block, `get_outputs` iterates `block.txdata[1 ..]` and, for every transaction containing an output to a Serai P2TR script, resolves the "presumed origin" by fetching the parent transaction of `tx.input[0]`: [1](#0-0) 

```rust
let input = &tx.input[0];
let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
spent_tx.reverse();
let mut tx;
while {
  tx = self.rpc.get_transaction(&spent_tx).await;
  tx.is_err()
} {
  log::error!("couldn't get transaction from bitcoin node: {tx:?}");
  sleep(Duration::from_secs(5)).await;
}
tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
```

Any RPC error — including "transaction not found" from a node without `txindex`, a pruned node, or the parent being unavailable — causes an infinite retry. Unlike `median_fee` in the same file, which correctly propagates `NetworkError::ConnectionError` on `get_transaction` failure (lines 396–403), this loop treats every error as transient.

The call site is `processor/src/multisigs/scanner.rs`, where `network.get_outputs(&block, key)` is invoked while the scanner's write lock is held: [2](#0-1) 

Because the lock is held across the hang, no other scanning activity (other keys, block processing, `ack_block`, event emission) can proceed on that processor.

### Impact Explanation
An unprivileged party sends a Bitcoin transaction paying a Serai multisig address where the parent of `input[0]` is not retrievable by the processor's node (e.g., spends an old UTXO on a node without `txindex`, or the configured node is pruned/temporarily erroring). The processor's scanner thread hangs forever inside `get_outputs`, while holding the scanner write lock. All downstream functionality stalls: no `ScannerEvent::Block` emissions, no new deposits credited, no eventuality completions, no multisig rotation processing. Restarting does not help — on reboot the scanner rescan resumes at the same unprocessed block and hangs again at the same transaction. Across the validator set this degrades the bridge's ability to credit deposits, mirroring CVE-2018-17144's "remotely triggerable crash that could take many nodes offline" without requiring any privilege beyond sending a normal on-chain transaction.

### Likelihood Explanation
Triggering requires only publishing a valid Bitcoin transaction — no stake, no validator key, no malformed data. The failure mode activates whenever `get_transaction` returns an error for the referenced parent, which occurs under common and legitimate node configurations (no `txindex`, pruning, transient RPC errors are also retried forever). Since the code comments elsewhere in this file show errors are expected (`median_fee` propagates `NetworkError`), an RPC hiccup during scanning of a deposit block is sufficient to wedge the scanner permanently, not just under exotic setups.

### Recommendation
Bound the retry loop: propagate the failure as `NetworkError` (or skip `presumed_origin` population, which is explicitly only a heuristic per the TODO comment) after a bounded number of attempts, so scanning can proceed or fail visibly rather than hanging. At minimum, treat "not found" errors as non-retriable. Additionally, `tx.input[0]` should be accessed defensively (`tx.input.first()`) since the loop's reachability no longer guarantees non-empty inputs once error handling changes, and `swap_remove(vout)` should validate `vout < output.len()` rather than trusting the parent lookup implicitly.

### Proof of Concept
1. Configure a processor's Bitcoin RPC connection to a node without `txindex` (or simulate by making `get_transaction` return an error for a specific txid).
2. As an unprivileged user, construct and broadcast a transaction `D` whose `input[0].previous_output.txid` references a transaction the node cannot serve, with an output paying the Serai multisig's P2TR script (`p2tr_script_buf(group_key)`).
3. Mine/confirm `D` past `Bitcoin::CONFIRMATIONS` (6).
4. The scanner reaches that block, calls `get_outputs`, matches the output via `scanner.scan_transaction`, enters the `while tx.is_err()` retry loop at lines 719–724, and never returns — the write lock is held indefinitely and all subsequent `ScannerEvent`s cease. Observed effect: `scanner.events.recv()` produces no further events and `ack_block` cannot acquire the lock; restart reproduces the hang at the same block.

Note on uncertainty: whether running the processor against a non-`txindex` node is considered supported configuration affects whether this is judged integrator misuse; however the infinite retry also triggers on *any* transient RPC error for a legitimately retrievable parent, which does not depend on node configuration.
