### Title
Panic (DoS) in PedPoP blame handling via unvalidated Participant index — HashMap indexing on unregistered `decryptor`/`sender` — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Helm advisory is a "panic on crafted input" Denial-of-Service: an index file triggers an unrecoverable memory-safety panic in the `_repo` parser. The Serai analog is an unrecoverable panic in the PedPoP DKG's blame/decryption path. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` indexes `self.commitments[&sender]` with attacker-supplied `Participant` values. `Participant::new` only rejects zero, and the blame entry points (`BlameMachine::blame`, `AdditionalBlameMachine::blame`) perform no bounds check against the registered participant set, so any non-zero index `> n` causes a `HashMap` index panic — crashing the validator processing the blame transaction.

### Finding Description
The PedPoP protocol exposes public blame APIs that take untrusted `Participant` indexes plus an `EncryptedMessage` (reachable through `EncryptedMessage::read` / `EncryptionKeyProof::read`):

```rust
// crypto/dkg/pedpop/src/lib.rs
pub fn blame(
  &self,
  sender: Participant,
  recipient: Participant,
  msg: EncryptedMessage<C, SecretShare<C::F>>,
  proof: Option<EncryptionKeyProof<C>>,
) -> Participant {
  self.0.blame_internal(sender, recipient, msg, proof)
}
```

`blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609) calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which evaluates:

```rust
// crypto/dkg/pedpop/src/encryption.rs:387-388
&[C::generator(), msg.key],
&[self.enc_keys[&decryptor], *proof.key],
```

If `decryptor` (the `recipient`/`accuser` index) was never registered — e.g., `Participant(999)` when only `1..=n` were registered via `Decryption::register` — `HashMap`'s `Index` impl panics with "no entry found for key". The same panic exists at crypto/dkg/pedpop/src/lib.rs:599 (`self.commitments[&sender]`) for an out-of-range `sender`.

Reachability: the upstream Serai coordinator deserializes `InvalidDkgShare` transactions by reading `accuser` and `faulty` with only `Participant::new` (non-zero) validation (coordinator/src/tributary/transaction.rs:346-354), then hands them to the blame machine along with an attacker-controlled `blame` byte blob deserialized via `EncryptedMessage::read`. Nothing bounds the indexes to the DKG participant set `1..=n`.

To reach the panicking line, the attacker only needs the message's PoP Schnorr signature to verify (encryption.rs:374-379). Since the `msg` field is fully attacker-controlled and the PoP is over an ephemeral key the attacker themselves chooses, they can construct a `EncryptedMessage` with a valid `pop` for any claimed `sender` index, then provide `proof: Some(..)` (any `EncryptionKeyProof`; the `enc_keys[&decryptor]` lookup happens while building the DLEq statement, before `dleq.verify` runs). The panic fires before any verification result can be produced.

### Impact Explanation
An unprivileged participant (anyone able to submit an `InvalidDkgShare`/blame accusation, which requires only a syntactically valid signed transaction) can deterministically panic the host processing blame. As in the Helm advisory, the panic is unrecoverable from the library's perspective (`io::Result`/`PedPoPError` are never returned — the `HashMap` index panics across the API boundary), taking down the validator process mid-protocol. On a coordinator/validator that processes blame synchronously, this aborts DKG completion processing and can be repeated, constituting a persistent denial of service against the threshold-signing pipeline. Severity: Medium–High (remote, deterministic, zero-cost DoS; no key disclosure).

### Likelihood Explanation
Triggering requires only:
- a signed `InvalidDkgShare`-type message (any validator can produce one; the signature is over the tx, not proof of a real fault),
- `accuser` (or `faulty`) set to any non-zero index outside `1..=n`,
- a self-constructed `EncryptedMessage` with a valid PoP (trivially generated by encrypting to one's own key) and an arbitrary `EncryptionKeyProof`.

No collusion, no honest-party cooperation, and no race conditions are needed. The panic occurs on the very first `HashMap` lookup.

### Recommendation
Replace direct indexing with checked lookups in crypto/dkg/pedpop:
- In `Decryption::decrypt_with_proof` (encryption.rs:388), use `self.enc_keys.get(&decryptor)` and map `None` to `DecryptionError::InvalidProof` (the accuser is then blamed, which is correct: they cited a non-existent recipient).
- In `blame_internal` (lib.rs:599), use `self.commitments.get(&sender)` and treat a missing sender as the accuser being faulty, or validate `sender`/`recipient` against `1..=n` at the `blame` API boundary and return a `PedPoPError` instead of panicking.

### Proof of Concept
```rust
// Setup: n = 3, all participants registered via EncryptionKeyMessage::read + register
let mut machine = AdditionalBlameMachine::<Ed25519>::new(context, 3, commitment_msgs).unwrap();

// Attacker-controlled EncryptedMessage: encrypt a SecretShare to themselves so the
// PoP signature is valid for the claimed 'sender'
let msg: EncryptedMessage<Ed25519, SecretShare< ed25519::Scalar >> = /* crafted, valid pop */;

// attacker submits a blame where recipient (accuser index) = 999, a valid non-zero
// Participant that was never registered -> self.enc_keys[&decryptor] panics
let _ = machine.blame(
  Participant::new(1).unwrap(),    // sender (registered or not; either works)
  Participant::new(999).unwrap(),  // decryptor — never registered
  msg,
  Some(proof),                     // any EncryptionKeyProof; panic precedes verification
);
```

The panic occurs at `self.enc_keys[&decryptor]` in `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:388). Alternatively, `sender = Participant(999)` panics at `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599) once decryption is reached.

Caveat: I verified the panic sites and the `Participant::new`-only validation on the transaction read path; I did not trace the exact coordinator call site that passes these indexes into `blame`, so the final wiring step is inferred from the surrounding `InvalidDkgShare` handling rather than directly confirmed.
