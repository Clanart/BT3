Based on my research, most of the classic GitHub Desktop attack surfaces in this codebase (clone-path traversal, git argument injection, ref-name sanitization, OAuth CSRF, symlink escapes) have explicit, tested guards: `resolveWithin` [1](#0-0) , `sanitizeCloneName`/`isClonePathSensitive` [2](#0-1) , `sanitizedRefName` [3](#0-2) , and CSRF-random-state OAuth [4](#0-3) . The one place I found a real, code-evidenced gap analogous to the reported bug class ("a value is computed and staged, then a downstream state check — which doesn't fully validate the state that changed — lets the stale value be applied, silently destroying/losing data") is the Copilot merge-conflict-resolution write path.

### Title
Stale AI-computed conflict resolution can silently overwrite newer on-disk conflict content in `_applyCopilotConflictResolutions` - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When Desktop resolves merge/rebase/cherry-pick conflicts with Copilot, it snapshots each conflicted file's raw content once, sends the extracted hunks to the model, and reassembles a full resolved file from that snapshot. The reassembled content is cached in store state and only written to disk later, when the user clicks "Continue Merge." At write time, the code checks only whether the file *still has any unresolved conflict* — not whether the on-disk content still matches the snapshot the resolution was built from. If the underlying conflicted content changes during the (multi-second-to-multi-minute) gap between snapshot and write while the file remains marked conflicted, the stale resolution is written verbatim, discarding whatever conflict state is currently on disk.

### Finding Description
The conflict snapshot is taken once, up front, via `readFile` inside `buildConflictContext`: [5](#0-4)  and [6](#0-5) . That `rawContent` is the sole basis used later to splice the model's per-hunk output back into a full file via `reassembleResolvedFile`, which is explicitly a pure string-splice against the *original* snapshot, matched "by order, not by line number": [7](#0-6) . The resulting `resolvedContent` is stored in `copilotResolutions` and is not recomputed later: [8](#0-7) . The Copilot API round-trip that produces this snapshot-based content can run for minutes, as shown by the app's own timing telemetry buckets (>15s/30s/60s/120s): [9](#0-8) .

When the user finally confirms via "Continue Merge," `_applyCopilotConflictResolutions` writes the cached `resolvedContent` straight to disk: [10](#0-9) . The only staleness guard present checks whether the file has *no* remaining conflict markers at all (meaning the user fully resolved it themselves outside Desktop) — in that case the write is skipped: [11](#0-10) . Crucially, this guard is file-status-granular ("still conflicted: yes/no"), not content-integrity-granular — it never re-reads or re-diffs the current on-disk conflict-marker content against the `rawContent` snapshot that `resolvedContent` was built from. As long as the file is *still* reported as conflicted by git status, the stale, pre-computed `resolvedContent` is written unconditionally, exactly mirroring the reported pattern: a value accrued/computed earlier is applied later behind a guard that checks the wrong invariant (existence of a "locked"/"conflicted" state) instead of the invariant that actually matters (that the state has not changed since the value was computed).

### Impact Explanation
If the on-disk conflicted content for a file changes between the initial snapshot and the final write — while the file remains flagged as conflicted — the write silently discards the current, correct hunk content and replaces it with content reassembled from stale data. Because the working-directory file (not just the git index) is fully overwritten and then staged with `git add` [12](#0-11) , this is a silent corruption of exactly what the user is about to commit/push — the impact category explicitly called out as valid (silent corruption of what the user commits or pushes), without any additional unnatural user action beyond the normal "Continue Merge" click.

### Likelihood Explanation
I was not able to fully confirm, from local code alone, an unambiguous end-to-end attacker-controlled trigger for the on-disk content to change while `hasUnresolvedConflicts` still returns true (e.g., via `.gitattributes`-controlled `conflict-marker-size`/merge-driver behavior in an attacker-supplied branch, or via other repository-controlled `.gitattributes` settings that affect how git rewrites the working tree during the operation). The underlying design flaw — a file-level "still conflicted" check standing in for a content-integrity check on the exact snapshot used to build the cached resolution — is directly evidenced in the code cited above, but I could not verify a concrete, purely-attacker-driven (no user action) sequence that flips the on-disk bytes during the async gap without additional investigation using a live checkout (which is outside the scope of static/index-based review). This should be treated as a real logic gap with moderate-to-uncertain exploitability rather than a fully proven exploit chain.

### Recommendation
Before writing `resolution.resolvedContent`, re-read the file's current on-disk content and verify it still matches (or is derivable from) the `rawContent` snapshot the resolution was built from — e.g., by hashing `ctx.rawContent` at snapshot time and comparing against a hash of the current file content immediately before write, aborting/re-prompting the user if they differ, rather than relying solely on the coarse "still has some unresolved conflict" check.

### Proof of Concept
Not independently verified end-to-end (see Likelihood Explanation). Conceptually:
1. Start a merge/rebase against a branch that produces a multi-hunk conflict in a file.
2. Trigger "Resolve with Copilot"; the conflicted file's content is snapshotted via `readFile`.
3. While the Copilot call is in flight (can take over a minute per the app's own telemetry buckets), cause the on-disk conflicted content for that file to change while it remains flagged as conflicted by git status.
4. When Copilot's stale resolution returns and the user clicks "Continue Merge," `_applyCopilotConflictResolutions` writes the resolution computed from the old snapshot, silently discarding the newer on-disk conflict content, because the only gate is "is this file still conflicted" — not "does this match what the resolution was computed from."

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
