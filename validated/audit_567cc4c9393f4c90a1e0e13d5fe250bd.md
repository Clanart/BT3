### Title
Bank precompile `send()`/`sendNative()` bypass `SendEnabled` (pause) checks enforced by the `x/bank` message server - (File: `precompiles/bank/bank.go`, `precompiles/bank/legacy/v555/bank.go`)

### Summary
sei-chain's `x/bank` module exposes a `SendEnabled` parameter (per-denom "pause" switch) that operators/governance can flip off to freeze transfers of a specific denom. This check, `IsSendEnabledCoins`, is enforced only in the Cosmos `MsgSend`/`MsgMultiSend` handlers [4](#0-3) , not in the lower-level `SendCoins` primitive. The EVM Bank precompile's `send` method calls `bankKeeper.SendCoins` directly without ever calling `IsSendEnabledCoins`, `IsInDenomAllowList`, or `BlockedAddr` [5](#0-4) . This is structurally the same bug class as the reported Telcoin `slash()` finding: a privileged/alternate code path that moves funds while bypassing a pause-equivalent gate that the "normal" path enforces.

### Finding Description
`IsSendEnabledCoins` is the mechanism by which sei-chain can disable/pause transfers of a given coin denom [6](#0-5) . It is checked in the Cosmos SDK message-server entry points for `Send`/`MultiSend` before any balance movement occurs [7](#0-6) . However, the Bank precompile (reachable by any EVM contract that is the registered `ERC20NativePointer` for a denom) calls `p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, ...)` directly, with no `IsSendEnabledCoins` check, no `IsInDenomAllowList` check, and no `BlockedAddr` check on the recipient [8](#0-7) . The same pattern exists in `sendNative`, which moves `usei`/`wei` via `SendCoinsAndWei` with no send-enabled gating at all [9](#0-8) .

### Impact Explanation
If governance or an operator disables sending for a given denom (e.g., during an incident, exploit response, or compliance freeze) via the `SendEnabled` params, any pointer contract owner (or user through their associated ERC20 pointer) can still move that "frozen" denom by calling the Bank precompile's `send`, completely defeating the intended freeze. Funds that operators believe are frozen can still be transferred, which is a direct fund-movement/asset-freezing-bypass impact.

### Likelihood Explanation
Likelihood is contingent on `SendEnabled=false` being actively used as an incident-response/pause lever for a denom that also has a registered ERC20 native pointer — a plausible but not default-active operational state. Given that pointer registration is a normal permissionless/administrative flow in sei-chain and precompiles are reachable by any EVM caller, exploitation requires no special privilege once the pointer exists.

### Recommendation
Add an `IsSendEnabledCoins` check (and ideally the same `BlockedAddr`/allow-list checks the `MsgSend` handler performs) to the Bank precompile's `send` and `sendNative` implementations in `precompiles/bank/bank.go` and its legacy versions, mirroring the gating done in `sei-cosmos/x/bank/keeper/msg_server.go`.

### Proof of Concept
1. Governance/operator sets `SendEnabled` params to disable transfers for denom `X` (via `x/bank` params update).
2. A user attempts `MsgSend` of `X` through the normal Cosmos path — it fails with `ErrSendDisabled` per `IsSendEnabledCoins` in `msgServer.Send` [7](#0-6) .
3. The same user, holding an EVM contract registered as the `ERC20NativePointer` for denom `X`, calls the Bank precompile's `send(sender, receiver, "X", amount)` at address `0x0000000000000000000000000000000000001001` [3](#0-2) .
4. The precompile calls `bankKeeper.SendCoins` directly, succeeding and moving the "disabled" denom, proving the pause bypass.

		return nil, err
	}

		return nil, err
	}

		return nil, errors.New("invalid denom")
	}

	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())

	amount := args[3].(*big.Int)

		// short circuit
		return method.Outputs.Pack(true)
	}

		return nil, err

	if err != nil {
		return nil, err
	}

		return nil, err
	}
