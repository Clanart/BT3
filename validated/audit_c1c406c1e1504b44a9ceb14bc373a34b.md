## Title
Diff-expansion index drift lets an attacker-crafted repository make GitHub Desktop stage/commit different lines than the ones the user selected - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
This is the closest local analog of the Sherlock invariant-breaking bug class: a value (`Closure.targetX128`/`balances`) that is computed incrementally and drifts from the "real" reference value it is supposed to track, so a downstream consumer (`ValueLib`) trusts a number that no longer matches reality. In GitHub Desktop, the equivalent invariant is: **"the absolute line index a user selects in the diff UI must always resolve to the same underlying diff line that gets written into the patch applied to the index."** That invariant is maintained by `hunk.unifiedDiffStart`/`unifiedDiffEnd` bookkeeping, which is recomputed by hand every time a hunk is expanded (`expandTextDiffHunk` in `app/src/ui/diff/text-diff-expansion.ts:170-400`) and later blindly trusted by `formatPatch`/`formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts:143-144`, `:266-267`) via `absoluteIndex = hunk.unifiedDiffStart + lineIndex`.

### Finding Description
`formatPatch` and `formatPatchToDiscardChanges` decide whether a given diff line is included in the patch sent to `git apply --cached` purely by looking up `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is derived from `hunk.unifiedDiffStart` [1](#0-0) . This is the same "trust an incrementally-updated running counter" pattern as `Closure.addValue`'s `targetX128 +=` accumulation — the counters (`unifiedDiffStart`/`unifiedDiffEnd`) are updated arithmetically on every hunk-expansion operation rather than being recomputed from ground truth.

`expandTextDiffHunk` recomputes these offsets for the expanded hunk and for every hunk after it: `hunk.unifiedDiffStart + numberOfNewDiffLines` / `hunk.unifiedDiffEnd + numberOfNewDiffLines` [2](#0-1) , and merges of adjacent hunks subtract one more line for the removed hunk header (`numberOfNewDiffLines - 1`) [3](#0-2) . This bookkeeping is repository-content dependent: the number of lines pulled in during an expansion is driven by `newContentLines` — i.e. by the contents of the file as they exist in the working tree after checking out an attacker-controlled clone — and by hunk-merge decisions that depend on the *old* file's line counts (`hunk.header.oldLineCount`, `newLineCount`) coming straight from `git diff` output.

Because `DiffSelection` stores selections as **raw absolute integer indices** (`divergingLines: Set<number>`, see `withRangeSelection`/`withLineSelection`) rather than as references to specific `DiffLine` objects, any mismatch between the offset bookkeeping and the actual line layout after one or more expansion/merge operations causes `isSelected(absoluteIndex)` to test the wrong line. Unlike Closure's `realValue()` helper that can be used to audit drift, there is no equivalent recomputation-from-scratch check before `formatPatch` builds the patch that is fed to `git apply --cached`.

### Impact Explanation
If the offset arithmetic in `expandTextDiffHunk` (or the subsequent `getHunkHeaderExpansionType` recalculation for hunks after a merge) drifts by even one line relative to the true position, a user who intentionally selects one hunk/line for partial staging can end up having a *different* line staged and committed — this is a silent corruption of what the user commits, matching the "impact of breaking an invariant with unfairness/incorrect state" impact class from the source report, translated to Desktop's domain of "the user's selection must exactly match what's committed."

### Likelihood Explanation
This code path is reached whenever a user expands hunk context in a large diff (a routine action for reviewing changes before a partial commit) on a file from a cloned/fetched repository. The offset computation is driven entirely by file content and diff hunk boundaries that are controlled by whoever authored the repository content (an attacker who gets the victim to clone/pull their repo), satisfying the "attacker controls a cloned/fetched repository" precondition. No local/admin access or social engineering beyond "review this diff and stage part of it" is required.

### Recommendation
Do not rely purely on incrementally-adjusted `unifiedDiffStart`/`unifiedDiffEnd` integer offsets carried through multiple expand/merge transformations. Instead:
- Recompute hunk boundaries from scratch (a single pass over `newHunks` after every expansion) rather than propagating `+ numberOfNewDiffLines` deltas through chained operations, mirroring the report's suggestion to "recalculate the target" from first principles instead of trusting the incremental delta.
- Add invariant assertions (in debug/test builds) that verify, after each `expandTextDiffHunk` call, that iterating `newHunks` linearly reproduces the exact same `unifiedDiffStart` values that were computed incrementally, and fail loudly (throw) if they diverge, rather than silently producing a patch.
- Add regression tests specifically for repeated expand-up/expand-down/merge sequences (not just single-shot expansion, which is what `app/test/unit/text-diff-expansion-test.ts` appears to focus on) to catch any drift before it reaches `formatPatch`.

### Proof of Concept
I could not build or run a concrete failing sequence within the scope of this static index-based review — reproducing the drift requires executing `expandTextDiffHunk` repeatedly (multiple up/down expansions and hunk merges) against a real multi-hunk diff and asserting the resulting `unifiedDiffStart` for a given `DiffLine` against a from-scratch recomputation, which needs the actual test harness/runtime (`app/test/unit/text-diff-expansion-test.ts`) rather than static reading. This is a **suspected** invariant-drift path based on the code structure (chained incremental offset arithmetic feeding directly into `absoluteIndex` line-selection lookups with no verification step), not a confirmed exploited bug. Due to index size limits, I was not able to inspect the full `app/test/unit/text-diff-expansion-test.ts` file contents to confirm whether existing tests already cover chained expansion/merge sequences; I'd recommend starting a full Devin session with repo access to write and run a concrete multi-expansion PoC and check existing test coverage before treating this as confirmed.
