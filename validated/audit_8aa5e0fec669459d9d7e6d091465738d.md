## Title
Tron `IntentGatewayV2.placeOrder()` escrows the nominal input amount instead of the actual fee-on-transfer-adjusted balance received, letting orders in taxed tokens overdraw the shared escrow pool - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM `IntentGatewayV2.sol` explicitly patches a shares-vs-assets style accounting bug: before computing the order commitment and crediting `_orders[commitment][token]`, it mutates `order.inputs[i].amount` to the *actual* token balance received by the gateway, because fee-on-transfer (FOT) tokens deliver less than the caller specifies. The Tron variant of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) never received this fix: it transfers `order.inputs[i].amount` (the caller-specified nominal amount) via `safeTransferFrom`, but credits the escrow ledger with `reducedInputs[i].amount`, which is derived from the same nominal amount minus only the protocol fee — not from what the contract actually holds. For any input token that taxes transfers, the escrow ledger overstates the real balance held for that commitment.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder()`: [1](#0-0) 
the protocol-fee reduction is computed from `order.inputs[i].amount` (the value the user supplied), and the commitment hash is built over `reducedInputs`. Then in the escrow loop: [2](#0-1) 
`IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` pulls the nominal amount, but if `token` takes a transfer fee, the gateway's actual balance increase is strictly less than `order.inputs[i].amount`. The very next line still credits `_orders[commitment][token] += reducedInputs[i].amount`, a value derived from the *nominal* amount, not from the balance actually received.

Contrast this with the corresponding (fixed) logic in the primary EVM contract, which explicitly measures and re-bases on the actual received balance before computing the commitment or escrow credit: [3](#0-2) 

`_orders` is a single mapping keyed by `(commitment, token)`, but the underlying ERC-20 balance held by the gateway contract is one shared pool across every commitment that uses that token. Overstating one commitment's escrow entry doesn't just corrupt that order's own accounting — it creates a ledger claim in excess of what was actually deposited, and that excess can only be satisfied out of balance that belongs to other orders sharing the same token, exactly mirroring the BendDAO bug where one position's inflated "shares-as-assets" value came at the expense of another position's real backing.

### Impact Explanation
When the order using a fee-on-transfer input token is filled or refunded, `withdraw()` releases `_orders[commitment][token]` (the overstated amount) to the solver/beneficiary from the gateway's pooled token balance: [4](#0-3) 
This transfers out more of that token than the order itself ever contributed, drawing down balance that is simultaneously recorded as escrowed for unrelated orders in `_orders[otherCommitment][token]`. The result is loss of funds for other users: their subsequent fill/refund calls against the same token either revert (insufficient contract balance) — locking their escrowed funds — or, if enough of the shared pool remains, silently pay out from balance that was never theirs, breaking the "moves exactly once and only to the rightful beneficiary and amount" invariant for order escrow. An unprivileged user can trigger this simply by placing and then filling/cancelling an order denominated in any TRC20 with a transfer tax; no relayer, prover, or admin cooperation is required.

### Likelihood Explanation
Any TRC20 with a transfer fee/tax (a common token pattern, especially on Tron) placed as an `order.inputs[i].token` triggers the divergence unconditionally on every `placeOrder` call — there's no special setup, race, or privileged actor needed. The bug is silent (no revert, no event indicating a shortfall) until the pool's real balance can't cover cumulative overstated claims, at which point other users' fills/refunds start failing or draining unrelated escrow.

### Recommendation
Port the EVM fix to the Tron contract: measure the gateway's token balance before and after each `safeTransferFrom` in `placeOrder()`, use the actual received delta (not the caller-specified `order.inputs[i].amount`) as the basis for both the protocol-fee reduction and the commitment hash, and credit `_orders[commitment][token]` with that same actually-received, fee-adjusted amount — exactly mirroring `evm/src/apps/IntentGatewayV2.sol`'s "Phase 1: Transfer tokens and record actual received amounts" logic.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with `protocolFeeBps = 0` for simplicity, and a TRC20 `FeeOnTransferToken` that takes a 5% fee on every transfer (same harness style as `FeeOnTransferToken` used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2502`).
2. User A places order #1 with `inputs[0] = {token: FOT, amount: 1000}`. `safeTransferFrom` moves 1000 nominal, gateway actually receives 950. `_orders[commitment1][FOT]` is credited `1000` (no protocol fee configured, so `reducedInputs == inputs`), not `950`.
3. User B places a legitimate order #2 with the same `FOT` token, depositing e.g. `2000` nominal (gateway receives `1900`). `_orders[commitment2][FOT]` correctly-looking value is `2000`, contract's real `FOT` balance is `950 + 1900 = 2850`, but combined ledger claims are `1000 + 2000 = 3000` — already `150` short.
4. Order #1 is filled/cancelled and `withdraw()` pays out `_orders[commitment1][FOT] = 1000` to its beneficiary from the shared pool, even though order #1 only ever contributed `950`. The extra `50` comes out of the balance nominally backing order #2.
5. When User B later tries to redeem order #2's escrow, the contract's `FOT` balance is insufficient to cover `_orders[commitment2][FOT] = 2000`, and the transfer reverts (or a later comer's withdrawal succeeds by consuming remaining shared balance meant for someone else), demonstrating fund loss/lock traceable directly to the nominal-vs-actual escrow mismatch in `placeOrder()`.
