### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s, crediting funds that cannot be spent - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report describes a value-transfer primitive that reports success without the transfer actually happening — a "credited but not delivered" bug class. The analog in Serai's Bitcoin wallet is `Scanner::scan_block`, which iterates **all** transactions in a block, including `txdata[0]` (the coinbase). Coinbase outputs are encumbered by a 100-block maturity rule: they are unspendable until maturity. Any miner — an unprivileged external party — can pay the Serai multisig's P2TR script in a coinbase transaction, and `scan_block` will return it as a normal `ReceivedOutput`, indistinguishable from a spendable payment.

### Finding Description
`Scanner::scan_transaction` matches outputs purely by `script_pubkey` against the registered script map and constructs a `ReceivedOutput` carrying only the offset, `TxOut`, and `OutPoint` — no maturity or provenance metadata:

```rust
// networks/bitcoin/src/wallet/mod.rs:199-214
pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> { ... }

// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {          // includes block.txdata[0], the coinbase
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

The doc comment acknowledges the issue ("If received outputs must be immediately spendable, a post-processing pass is needed"), but the returned `ReceivedOutput` type carries no flag distinguishing coinbase outputs, and `SignableTransaction::new`/`multisig` will happily construct and FROST-sign a transaction spending such an outpoint. Notably, Serai's own processor had to work around this at the call site by explicitly skipping `block.txdata[1 ..]`'s predecessor (`for tx in &block.txdata[1 ..]` in `processor/src/networks/bitcoin.rs`), confirming the library-level trap is real rather than theoretical.

### Impact Explanation
- **Funds reported received that are not spendable**: a `ReceivedOutput` sourced from a coinbase can be fed to `SignableTransaction::new`, which will build a transaction spending an immature outpoint. Every `AlgorithmSignMachine` will produce valid signature shares and `complete()` will emit a fully-signed transaction — which the Bitcoin network will reject as a consensus violation (`bad-txns-premature-spend-of-coinbase`). The wallet believes the value is available; it is not.
- A miner (or mining pool, or anyone influencing coinbase construction — e.g., via a Stratum job or a pool payout address set to Serai's script) controls this with a purely public input: a Bitcoin transaction they cause to exist.
- Downstream accounting that sums `ReceivedOutput::value()` over `scan_block` overstates the immediately spendable balance; signing pipelines that consume scanned outputs waste a threshold-signing round and produce a dead transaction, and automated retry loops may strand the genuine inputs' sequencing.

### Likelihood Explanation
Any Bitcoin miner can direct coinbase payouts to arbitrary scriptPubKeys — no interaction with Serai is needed and the cost is only the miner choosing the Serai P2TR script as a coinbase output. Pool payouts and coinbase-splitting transactions make "coinbase paying a watched address" a routine occurrence, not an exotic edge case. The bug is deterministic once such an output appears in a scanned block.

### Recommendation
Do not scan `block.txdata[0]` inside `Scanner::scan_block` — iterate `block.txdata[1 ..]` directly so the maturity burden is enforced at the source rather than delegated to every caller. Alternatively, record a `coinbase`/`mature` flag on `ReceivedOutput` and have `SignableTransaction::new` reject immature outpoints. At minimum, callers must filter, but the current API makes the unsafe path the default.

### Proof of Concept
```rust
// Any miner includes an output paying the multisig's script in the coinbase:
let block: Block = /* block whose txdata[0] (coinbase) pays p2tr_script_buf(key) */;
let scanner = Scanner::new(key).unwrap();

// scan_block returns the coinbase output as a ReceivedOutput
let outputs = scanner.scan_block(&block);
assert_eq!(outputs.len(), 1); // credited

// It is consumed as if spendable:
let stx = SignableTransaction::new(
    vec![outputs[0].clone()], &payments, change, None, fee_rate,
).unwrap();
let machines = /* FROST multisig machines */;
let signed = sign(&machines, &stx); // fully signed, valid-looking TX

// Broadcast fails at the mempool/consensus layer:
// "bad-txns-premature-spend-of-coinbase" — funds were never spendable.
```

Caveat: the doc comment on `scan_block` mentions the maturity caveat, so an auditor may weigh this as a documented limitation; however, the type system gives callers no way to distinguish these outputs, and the accepted impact class ("funds reported received that are not spendable") is met directly.
