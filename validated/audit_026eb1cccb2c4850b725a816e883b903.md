### Title
`SignableTransaction::new` omits the OP_RETURN data output when calculating weight, vbytes, and fee — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `mintWithPermit` passing `_wstUSRAmount` instead of the derived `usrAmount` to `permit`, `SignableTransaction::new` computes the transaction weight/vbytes — and therefore the required fee and the change amount — from `payments` only, even though an additional variable-length OP_RETURN `TxOut` is pushed onto the real transaction before the weight is ever calculated. The value used for fee calculation does not correspond to the transaction actually constructed and signed.

### Finding Description
In `SignableTransaction::new`, when `data` is `Some`, an OP_RETURN output is appended to `tx_outs` (send.rs:194-202). Immediately after, the weight and vbytes are computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204), which rebuilds the output set solely from `payments` (send.rs:85-93) and does not include the data output. The same omission occurs in the change path (send.rs:225-227). Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is computed on a smaller virtual size than the real transaction.
- The `TooLowFee` minimum-relay-fee check (send.rs:211) is evaluated against this undercounted fee, so a transaction can be constructed that silently falls below `DEFAULT_MIN_RELAY_TX_FEE` once the data output is included.
- The change output value `input_sat - (payment_sat + fee_with_change)` (send.rs:228-230) is too large by exactly the fee attributable to the data output, so the effective fee rate is always below the caller-specified `fee_per_vbyte`.
- The `TooLargeTransaction` check against `MAX_STANDARD_TX_WEIGHT` (send.rs:241) also ignores the data output's weight.

The bug is reachable by an unprivileged caller: `data` is a public, caller-supplied byte vector (up to 80 bytes, send.rs:171-173), so the fee can be underpaid by roughly `data_len + output overhead` vbytes times `fee_per_vbyte`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
Any `SignableTransaction` created with a non-`None` `data` pays a fee rate strictly lower than the `fee_per_vbyte` requested, and can fall below the Bitcoin minimum relay fee despite passing the `TooLowFee` check, producing a transaction that is rejected by the mempool or stalls unconfirmed. The change output is simultaneously inflated by the unaccounted fee. While it does not directly steal funds, it produces an incorrectly-priced transaction the threshold signing set will sign — funds become unspendable-in-practice until re-signed, and relay guarantees are violated.

### Likelihood Explanation
`SignableTransaction::new` is the sole transaction-construction path in `networks/bitcoin` and accepts arbitrary `data` from callers. Every invocation with `data.is_some()` deterministically undercomputes the fee — there is no probabilistic element. Impact is bounded to fee underpayment / stuck transactions rather than forgery or key recovery, hence Medium.

### Recommendation
Compute weight and vbytes from the actual output set. Either pass `&tx_outs` into `calculate_weight_vbytes` (after the data output is appended) instead of rebuilding from `payments`, or append the data output only after performing the no-change weight calculation and recompute it on the final `tx_outs` (including the change output when applicable). For example, change `calculate_weight_vbytes` to accept `outputs: &[TxOut]` and call it with the fully populated `tx_outs` in both the base and with-change branches.

### Proof of Concept
```rust
// networks/bitcoin context: construct a transaction carrying near-max data
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, change.clone(), Some(data), fee_per_vbyte).unwrap();

// The real transaction includes the OP_RETURN output
let real_vbytes = tx.transaction().vsize() as u64;
// needed_fee was computed without the data output's vbytes
assert!(tx.needed_fee() < real_vbytes * fee_per_vbyte);
// The change output absorbs the shortfall, so fee() also underpays
assert_eq!(tx.fee(), tx.needed_fee());
```
