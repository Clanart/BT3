### Title
Quadratic-cost EVM log accumulation via `DBImpl.AddLog`/`GetAllLogs` re-copying the full log slice on every LOG opcode - ([File: x/evm/state/log.go])

### Summary
`DBImpl.AddLog`, which implements the `vm.StateDB` `AddLog` method invoked by the go-ethereum interpreter on every `LOG0`–`LOG4` opcode, computes the new log's index by calling `GetAllLogs()`, which allocates a fresh slice and copies the *entire* accumulated log list so far, on every single call within a transaction's execution. [1](#0-0) 

### Finding Description
`AddLog` is called once per `LOG` opcode executed by a contract:

```go
func (s *DBImpl) AddLog(l *ethtypes.Log) {
	l.Index = uint(len(s.GetAllLogs()))
	s.tempState.logs = append(s.tempState.logs, l)
	...
}

func (s *DBImpl) GetAllLogs() []*ethtypes.Log {
	res := make([]*ethtypes.Log, 0, len(s.tempState.logs))
	res = append(res, s.tempState.logs...)
	return res
}
``` [1](#0-0) 

Every invocation of `AddLog` allocates a new backing array and copies all previously accumulated log pointers into it just to compute `len()` for the new log's `Index` — a value that is already available as `len(s.tempState.logs)` without any copy. For `n` LOG opcodes executed within a single transaction, this makes the total cost of index bookkeeping `O(1 + 2 + 3 + ... + n) = O(n²)` instead of `O(n)`. The identical pattern exists in the `giga/deps/xevm` fork of the same package. [2](#0-1) 

This mirrors the CommonMark bug class precisely: a per-item operation that should be `O(1)` amortized is instead implemented by re-materializing and re-walking the entire previously-accumulated collection on every additional item, turning linear work into quadratic work as the collection grows.

### Impact Explanation
Any unprivileged EVM transaction sender can deploy or call a contract that emits a large number of `LOG` events (e.g., a tight loop of `LOG0` opcodes with no topics/data, the cheapest form). Because `LOG0` costs a small fixed base gas amount, a single transaction at typical Sei block gas limits can emit tens of thousands of log entries. Each such log triggers a full slice copy of everything logged so far in that transaction, producing quadratic CPU and allocation cost concentrated in `DeliverTx`/`EndBlock` execution of that one transaction — directly on the block-production critical path, since the log/receipt objects (via `GetAllLogs`) feed into transient receipts and deferred EndBlock work. [3](#0-2) 

Because the additional cost scales with the square of the number of logs rather than gas-metered linear cost, the wall-clock execution time of processing such a transaction can grow disproportionately to the gas actually charged, risking validator block-processing delay beyond target block time for a single crafted transaction.

### Likelihood Explanation
The path is trivially reachable: any account can submit a normal EVM transaction to a contract that emits many cheap log events (or deploys such a contract and calls it). No special privileges, precompile access, or governance action is required — this is exactly the "unprivileged EVM transaction sender" surface explicitly in scope. The bug is a plain implementation defect (unnecessary `GetAllLogs()` copy inside `AddLog`) rather than a hypothetical edge case, and it is present in both the `x/evm/state` and `giga/deps/xevm/state` copies of the code.

### Recommendation
Change `AddLog` to use the length of the underlying slice directly instead of calling `GetAllLogs()`:
```go
func (s *DBImpl) AddLog(l *ethtypes.Log) {
	l.Index = uint(len(s.tempState.logs))
	s.tempState.logs = append(s.tempState.logs, l)
	...
}
```
`GetAllLogs()` should be reserved for callers that actually need a defensive copy of the full log list (e.g., cross-transaction reads), not for internal index bookkeeping inside the hot per-opcode path. Apply the same fix to `giga/deps/xevm/state/log.go`.

### Proof of Concept
1. Deploy a contract whose fallback/entry function runs a loop emitting `LOG0` with empty data as many times as the gas limit allows (e.g., tens of thousands of iterations at a typical block gas limit).
2. Submit this transaction to the chain.
3. Observe that `DBImpl.AddLog` is invoked once per emitted log, and each call performs a full copy of the already-accumulated `tempState.logs` slice via `GetAllLogs()`, so the cumulative copy cost grows quadratically with the number of logs emitted in that single transaction, inflating the wall-clock time to process that one transaction well beyond what its gas cost implies.
