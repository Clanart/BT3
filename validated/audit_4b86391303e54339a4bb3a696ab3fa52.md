Based on my investigation, I found a concrete TOCTOU (time-of-check/time-of-use) analog in GitHub Desktop's partial-commit patch generation, structurally identical to the Basin invariant-break: two pieces of derived state (a line-selection bitmap and a diff snapshot) are supposed to stay mathematically consistent, but the code re-derives one of them independently right before the security-relevant operation, breaking the invariant.

### Title
Partial-commit line selection is matched against a freshly re-fetched diff, letting attacker-controlled working-tree content silently corrupt what gets staged/committed - (File: app/src/lib/git/apply.ts)

### Summary
When a user stages only some lines of a modified file, GitHub Desktop stores that choice as a bitmap of "diverging" absolute line indices (`DiffSelection`) computed against the diff that was rendered in the UI. When the commit is actually created, `applyPatchToIndex` does **not** reuse that diff — it calls `getWorkingDirectoryDiff` again to fetch a brand-new diff from disk, and then walks the new diff's hunks reusing the old index bitmap via `file.selection.isSelected(absoluteIndex)`. If the working-tree file changed between the two diff computations (e.g. hunks shifted, merged, or reordered), the same numeric index now points at a different line, so the wrong lines are selected/deselected when building the patch that gets applied to the index and committed.

### Finding Description
The relevant flow:
1. UI renders a diff and the user selects a subset of lines. The selection is a `DiffSelection` bitmap keyed by `absoluteIndex = hunk.unifiedDiffStart + lineIndex`, computed against *that specific diff snapshot*: [1](#0-0) 
Concretely: [2](#0-1) 
2. `_commitIncludedChanges` gathers the files with their (possibly stale) `WorkingDirectoryFileChange.selection` from `state.changesState.workingDirectory.files` — a state snapshot from the last `_loadStatus`/diff refresh — and hands them to `createCommit`: [3](#0-2) 
3. `createCommit` calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex`: [4](#0-3) [5](#0-4) 
4. `applyPatchToIndex` throws away the diff the selection was computed against and fetches a **new** one straight from disk, right before formatting the patch with the (old) `file.selection`: [6](#0-5) 

The app is aware that a diff "might have changed dramatically" since it was last computed, and has logic to re-map `selectableLines` (dropping now-invalid indices) — but that reconciliation only happens as a side effect of `updateChangesWorkingDirectoryDiff`, which runs on file-selection changes or explicit status refreshes: [7](#0-6) . It is **not** re-run immediately before `applyPatchToIndex` re-fetches the diff during `_commitIncludedChanges`, so there is a window where the selection bitmap (built against diff A) is applied against a freshly-fetched diff B with different hunk boundaries/line ordering, without any validation that the indices still refer to the same logical lines.

### Impact Explanation
The corrupted value is the **patch fed to `git apply --cached`**, i.e. the actual staged/committed diff. If working-tree content is mutated between the moment Desktop last rendered/validated the selection and the moment the user clicks "Commit" (a window that is normal in day-to-day use — background builds, formatters, git hooks such as `post-checkout`/`post-merge`, or content written by tools the repository itself configures), the line indices silently point at the wrong hunk/line, causing:
- inclusion of lines the user never selected (attacker-influenced content ends up in a signed/pushed commit without the user's consent or knowledge), or
- exclusion of lines the user did select, or
- a hunk-count mismatch that makes `git apply` fail (`patch does not apply`), an availability degradation.

This is a silent corruption of what the user commits/pushes — one of the explicitly in-scope impacts — because the UI never re-confirms the selection against the diff that is actually used to build the patch.

### Likelihood Explanation
This requires the working tree to change between the "diff shown/selected" moment and the "commit executed" moment — not local/physical device access or malware, just repository content dynamics that are common (auto-formatters, watch scripts, git hooks triggered by the repository's own configuration such as `.git/hooks` populated via `core.hooksPath`/husky-style setups committed to the repo, or a slow user leaving the Changes view open). Because Desktop already documents this exact race ("the diff might have changed dramatically since last we loaded it") but only partially mitigates it (dropping invalid indices during an explicit refresh, not at commit time), the underlying gap is real and reachable through ordinary, attacker-influenced repository behavior rather than a contrived scenario.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, either (a) re-fetch the diff and re-validate that `file.selection`'s selectable-lines set still matches the new diff's structure, aborting or re-prompting if it diverges materially, or (b) reuse the exact diff object the UI last rendered (with its hunk offsets) to build the patch rather than re-fetching a new diff at staging time, so the index bitmap and the diff it's applied against are always the same snapshot.

### Proof of Concept
1. Open a repository in Desktop, modify a tracked file so it has multiple hunks, and stage only specific lines via the line-by-line selection UI (building a `DiffSelection` against diff A).
2. Before clicking "Commit", have an external process (e.g. a `post-checkout`/file-watcher script shipped with the repository, or simply another editor) rewrite the file so that git would produce a diff B with a different number/position of hunks (e.g. add/remove lines earlier in the file, shifting all later hunk offsets).
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches diff B via `getWorkingDirectoryDiff` [8](#0-7)  and calls `formatPatch(file, diffB)`, which evaluates `file.selection.isSelected(absoluteIndex)` using indices computed for diff A's hunk layout [2](#0-1) .
4. Observe that the resulting commit includes/excludes lines that do not correspond to what the user visually selected, or that `git apply` fails outright due to a hunk-count mismatch.
