### Title
Silent, automatic fast-forwarding of all local branches to attacker-controlled remote refs during background fetch - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop periodically fetches from a repository's remote in the background (`FetchType.BackgroundTask`) and, after every fetch (including background ones), unconditionally fast-forwards **every** local branch that tracks an upstream and is a strict ancestor of it — not just the currently checked-out branch — with no confirmation dialog, no diff, and no user awareness. This mirrors the core flaw in the reported bug-class: an automated step (`burn_position`) proceeds on the assumption that a prior, user-reviewed state is still valid, when in fact intervening attacker-controlled state changes (re-org / remote content changes) have silently altered what that step actually commits to.

### Finding Description
`performFetch` in `app/src/lib/stores/app-store.ts` (around lines 5924-5988) runs `gitStore.fetch()` and then unconditionally calls `this.fastForwardBranches(repository)`, regardless of whether the fetch was user-initiated or a `FetchType.BackgroundTask`: [1](#0-0) 

`fastForwardBranches` (the private app-store method) calls `getBranchesDifferingFromUpstream` to compute every local branch that differs from its remote-tracking ref, and then invokes the git-level `fastForwardBranches` helper for all of them: [2](#0-1) 

`getBranchesDifferingFromUpstream` in `app/src/lib/git/for-each-ref.ts` explicitly returns every local branch (excluding only the current one) whose SHA differs from its upstream, with no restriction to "ahead" vs "behind": [3](#0-2) 

The git-level `fastForwardBranches` in `app/src/lib/git/fetch.ts` then rewrites those local branch refs directly via `git fetch . --stdin` using `upstreamRef:ref` pairs, silently moving the local branch pointer to whatever SHA is currently in the remote-tracking ref: [4](#0-3) 

Because this path is reached from `performFetch`, and `performFetch` is invoked for both user-initiated fetches and background/periodic fetches without any distinguishing gate before calling `fastForwardBranches`, any repository remote (or a MITM/malicious proxy sitting in front of it) that pushes new commits onto a branch the user is *not* currently viewing will have those commits silently adopted into the user's local branch the next time Desktop performs any fetch — including a background one the user never explicitly triggered. There is no confirmation dialog, no diff review, and no log entry surfaced to the user comparable to `ConfirmForcePush`'s explicit warning UI (`app/src/ui/rebase/confirm-force-push.tsx`), which exists for the analogous "history rewritten" case but not for this "history silently extended on a branch you're not even looking at" case.

### Impact Explanation
This corresponds to the "silent corruption of what the user commits or pushes" category of valid impact. If a user later checks out the silently-updated branch and creates a new commit (assuming, as in the original report, that the tip they last reviewed is still the tip), that new commit is built on top of content the user never inspected, and pushing it propagates the attacker-controlled ancestor commits with the appearance of the user's own endorsement. Because the fast-forward is fully automatic and can happen via a background task the user did not initiate, the user has no natural opportunity to notice or review the change before it becomes baked into their local branch state — analogous to how re-org reordering in the original report silently invalidated the assumption a subsequent step relied on.

### Likelihood Explanation
Any remote the repository is configured to fetch from (including forks/mirrors an attacker controls, or a compromised/MITM'd git server sitting between Desktop and the real remote) can trigger this: it only requires pushing new commits to a branch that some local branch in the user's clone tracks. Background fetches occur periodically without user action, so no unusual user steps are required beyond having the repository open in Desktop with periodic fetch enabled (the default). This is a plausible but not certain path to real harm — it relies on the user later switching to the silently-updated branch and committing/pushing without reviewing incoming history, which somewhat mirrors the "low likelihood of exact sequence" caveat the original judges applied to the re-org report itself.

### Recommendation
Restrict automatic/background fast-forwarding to the currently checked-out branch only, or surface a clear, reviewable notification (with diff/commit list) whenever non-active local branches are fast-forwarded as a result of a fetch — particularly for background/periodic fetches — so the user has visibility into content that was added to their local branches before they build further commits on top of it.

### Proof of Concept
1. Clone a repository in Desktop that has two branches, `main` (checked out) and `feature`, both tracking `origin`.
2. Attacker (who controls `origin`, e.g., a compromised git host, fork used as a remote, or a MITM proxy) pushes a new commit to `origin/feature` containing content the local user has not reviewed.
3. Desktop's periodic background fetch (`FetchType.BackgroundTask` in `performFetch`, `app/src/lib/stores/app-store.ts:5924-5988`) runs automatically.
4. `fastForwardBranches` (`app/src/lib/stores/app-store.ts:5614-5624`) computes `feature` as an eligible branch via `getBranchesDifferingFromUpstream` (`app/src/lib/git/for-each-ref.ts:74-143`) since it is a strict ancestor of `origin/feature`.
5. The git-level `fastForwardBranches` (`app/src/lib/git/fetch.ts:103-141`) silently updates the local `refs/heads/feature` to the attacker's new commit — no dialog, no diff, no log visible to the user.
6. The user later switches to `feature`, adds a new commit on top, and pushes — propagating the attacker's unreviewed commit as part of their own branch history.

/**
 * Gets all branches that differ from their upstream (i.e. they're ahead,
 * behind or both), excluding the current branch.
 * Useful to narrow down a list of branches that could potentially be fast
 * forwarded.
 *
 * @param repository Repository to get the branches from.
 */
export async function getBranchesDifferingFromUpstream(
  repository: Repository
): Promise<ReadonlyArray<ITrackingBranch>> {
  const { formatArgs, parse } = createForEachRefParser({
    fullName: '%(refname)',
    sha: '%(objectname)', // SHA
    upstream: '%(upstream)',
    symref: '%(symref)',
    head: '%(HEAD)',
  })

  const prefixes = ['refs/heads', 'refs/remotes']

  const result = await git(
    ['for-each-ref', ...formatArgs, ...prefixes],
    repository.path,
    'getBranchesDifferingFromUpstream',
    { expectedErrors: new Set([GitError.NotAGitRepository]) }
  )

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  const localBranches = []
  const remoteBranchShas = new Map<string, string>()

  // First we need to collect the relevant info from the command output:
  // - For local branches with upstream: name, ref, SHA and the upstream.
  // - For remote branches we only need the sha (and the ref as key).
  for (const ref of parse(result.stdout)) {
    if (ref.symref.length > 0 || ref.head === '*') {
      // Exclude symbolic refs and the current branch
      continue
    }

    if (ref.fullName.startsWith('refs/heads')) {
      if (ref.upstream.length === 0) {
        // Exclude local branches without upstream
        continue
      }

      localBranches.push({
        ref: ref.fullName,
        sha: ref.sha,
        upstream: ref.upstream,
      })
    } else {
      remoteBranchShas.set(ref.fullName, ref.sha)
    }
  }

  const eligibleBranches = new Array<ITrackingBranch>()

  // Compare the SHA of every local branch with the SHA of its upstream and
  // collect the names of local branches that differ from their upstream.
  for (const branch of localBranches) {
    const remoteSha = remoteBranchShas.get(branch.upstream)

    if (remoteSha !== undefined && remoteSha !== branch.sha) {
      eligibleBranches.push({
        ref: branch.ref,
        sha: branch.sha,
        upstreamRef: branch.upstream,
        upstreamSha: remoteSha,
      })
    }
  }

export async function fastForwardBranches(
  repository: Repository,
  branches: ReadonlyArray<ITrackingBranch>
): Promise<void> {
  if (branches.length === 0) {
    return
  }

  const refPairs = branches.map(branch => `${branch.upstreamRef}:${branch.ref}`)

  await git(
    [
      'fetch',
      '.',
      // Make sure we don't try to update branches that can't be fast-forwarded
      // even if the user disabled this via the git config option
      // `fetch.showForcedUpdates`
      '--show-forced-updates',
      // Prevent `git fetch` from touching the `FETCH_HEAD`
      '--no-write-fetch-head',
      // Take branch refs from stdin to circumvent shell max line length
      // limitations (mainly on Windows)
      '--stdin',
    ],
    repository.path,
    'fastForwardBranches',
    {
      // Fetch exits with an exit code of 1 if one or more refs failed to update
      // which is what we expect will happen
      successExitCodes: new Set([0, 1]),
      env: {
        // This will make sure the reflog entries are correct after
        // fast-forwarding the branches.
        GIT_REFLOG_ACTION: 'pull',
      },
      stdin: refPairs.join('\n'),
    }
  )
}
