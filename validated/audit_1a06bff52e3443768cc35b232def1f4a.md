## Finding

`formatPatch` builds the patch text using `formatPatchHeaderForFile`, which interpolates `file.path` directly into the classic unified-diff header without any escaping of special characters (newlines, `+++`/`---`/`diff --git` sequences): [1](#0-0) [2](#0-1) 

This header is prepended to the hunk body and returned as the full patch string: [3](#0-2) 

That string is piped verbatim as `stdin` to `git apply --cached --unidiff-zero --whitespace=nowarn -`: [4](#0-3) 

`file.path` is not application-generated — it comes straight from `git status --porcelain=2 -z` parsing, and the parser explicitly supports (and is tested with) filenames containing literal newline characters, because `-z` disables git's normal quoting/escaping of special characters in filenames: [5](#0-4) [6](#0-5) 

So a repository an attacker controls (one the victim clones/fetches) can contain a tracked/untracked file whose name embeds a newline followed by attacker-chosen content such as `+++ b/<other-tracked-path>`. When the victim uses GitHub Desktop's partial-stage feature (selecting/deselecting individual lines of that file's diff), `applyPatchToIndex` is invoked, `formatPatch` produces a header where the injected line becomes a syntactically valid second `--- `/`+++ ` header pair (git's traditional-diff header parser looks for the first `--- X` line immediately followed by a `+++ Y` line to determine the target path with `-p1` stripping). That means the path git actually resolves as the target of `+++` can be the attacker-forged path, not the single `file.path` that Desktop displayed and the user reviewed in the diff view.

### Title
Unescaped filenames in `formatPatch` allow attacker-controlled patch-header injection into `git apply --cached` (File: `app/src/lib/patch-formatter.ts`)

### Summary
`formatPatchHeaderForFile`/`formatPatchHeader` embed `WorkingDirectoryFileChange.path` raw into the `---`/`+++` unified-diff header lines with no escaping of newlines or diff-header metacharacters. Because git's status parser (run with `-z`) does not quote special characters in filenames, a malicious repository can contain a file whose name is itself a forged patch header. That forged content is piped as stdin into `git apply --cached` by `applyPatchToIndex`, potentially causing git to resolve the "new file" target from the attacker's injected `+++` line rather than the path actually shown/reviewed by the user.

### Finding Description
- Untrusted source: file names inside a cloned/fetched repository, parsed by `parsePorcelainStatus` without escaping newlines [5](#0-4) .
- Propagation: the raw path becomes `WorkingDirectoryFileChange.path`, which flows unmodified into `formatPatchHeaderForFile` and is concatenated into the patch header string [7](#0-6) .
- Sink: the resulting patch text is written as stdin to `git apply --cached --unidiff-zero -` [4](#0-3) , which is the only path used to determine which index entry gets written when the user stages a subset of lines in a file (partial commit).
- No sanitization/escaping of the path is performed anywhere between the untrusted filename and the header string.

### Impact Explanation
If the parsing behavior of the installed `git` binary treats the attacker's injected line as a valid `+++` header (which is plausible given git's traditional-diff header search logic operates on consecutive `--- `/`+++ ` lines, independent of any `diff --git` extended header), `git apply --cached` could write staged content against a different tracked path in the index than the one displayed/reviewed by the user in the Changes list. This is a silent-corruption-of-what-the-user-commits scenario — an in-scope impact category — because the user believes they are staging specific reviewed lines for file A, but the index entry actually modified could be file B.

### Likelihood Explanation
Moderate-low, with real uncertainty:
- It requires the victim to use partial line-selection staging (`applyPatchToIndex`) on a file from an attacker-controlled repository, not a whole-file stage.
- It requires a filename containing a raw newline character to actually exist in the malicious repository's tree and survive checkout on the victim's OS/filesystem — git blobs/trees can store such names, but not all filesystems (particularly Windows) permit checking out files with literal newlines in the name, which constrains cross-platform exploitability.
- The exact outcome depends on internal parsing details of the git version used by the client (whether the injected `+++` line is accepted as a fresh header versus causing the whole hunk to be rejected as corrupt). I was not able to execute the actual `git apply` binary to confirm the parser's exact behavior against a crafted multi-line header; this would need to be validated experimentally (as suggested by the proof idea) rather than purely from reading `apply.ts`/`patch-formatter.ts`.

### Recommendation
Reject or escape file paths that contain newline or other patch-header-breaking characters before calling `formatPatch`/`formatPatchToDiscardChanges`, e.g., refuse to build a partial-stage patch (fall back to whole-file `git add`) for any path containing `\n`, `\r`, or other control characters, or reliably quote such paths the way git itself does for tab/space output (C-style quoting) so they cannot break out of the `---`/`+++` header line.

### Proof of Concept
1. Craft a repository containing a tracked file whose exact byte name (as it would appear via `git status --porcelain=2 -z`) is:
   `legit\n+++ b/other-tracked-file`
   (i.e., a real newline character embedded in the filename), with `other-tracked-file` being another path present in the same repo.
2. Have the victim clone/fetch this repository in GitHub Desktop, modify `legit\n+++ b/other-tracked-file`, and use the diff view to select only some of the added/removed lines (triggering `applyPatchToIndex`/`formatPatch` rather than a full `git add`).
3. Inspect the exact bytes produced by `formatPatch(file, diff)` — confirm the header now contains a second, forged `--- `/`+++ ` pair.
4. Feed that exact patch text to `git apply --cached --unidiff-zero --whitespace=nowarn -` in a test repo and inspect `git diff --cached --name-only` afterward to confirm which path was actually modified in the index, per the proof idea in the question.

Because step 4 (verifying actual git parser behavior on the forged header) could not be executed in this review environment, I cannot state with full certainty whether git resolves to the forged path or rejects the patch as corrupt — this needs to be confirmed by running the PoC against a real `git apply` before treating this as a confirmed exploit rather than a credible header-injection weakness in the application code.

function formatPatchHeader(from: string | null, to: string | null): string {
  // https://en.wikipedia.org/wiki/Diff_utility
  //
  // > At the beginning of the patch is the file information, including the full
  // > path and a time stamp delimited by a tab character.
  // >
  // > [...] the original file is preceded by "---" and the new file is preceded
  // > by "+++".
  //
  // We skip the time stamp to match git
  const fromPath = from ? `a/${from}` : '/dev/null'
  const toPath = to ? `b/${to}` : '/dev/null'

  return `--- ${fromPath}\n+++ ${toPath}\n`
}

function formatPatchHeaderForFile(file: WorkingDirectoryFileChange) {
  switch (file.status.kind) {
    case AppFileStatusKind.New:
    case AppFileStatusKind.Untracked:
      return formatPatchHeader(null, file.path)

    // One might initially believe that renamed files should diff
    // against their old path. This is, after all, how git diff
    // does it right after a rename. But if we're creating a patch
    // to be applied along with a rename we must target the renamed
    // file.
    case AppFileStatusKind.Renamed:
    case AppFileStatusKind.Deleted:
    case AppFileStatusKind.Modified:
    case AppFileStatusKind.Copied:
    // We should not have the ability to format a file that's marked as
    // conflicted without more information about it's current state.
    // I'd like to get to a point where `WorkingDirectoryFileChange` can be
    // differentiated between ordinary, renamed/copied and unmerged entries
    // and we can then verify the conflicted file is in a known good state but
    // that work needs to be done waaaaaaaay before we get to this point.
    case AppFileStatusKind.Conflicted:
      return formatPatchHeader(file.path, file.path)
    default:
      return assertNever(file.status, `Unknown file status ${file.status}`)
  }
}
