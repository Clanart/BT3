### Title
Automatic remote URL rewrite trusts unverified GitHub API `clone_url`, allowing silent hijack of push/fetch destination - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically refreshes the "GitHub repository" metadata associated with a locally tracked repository and, based on that refreshed API data, will **automatically rewrite the local `origin` remote URL** without any user confirmation. The decision to rewrite is based entirely on trusting the `clone_url` field returned by the API response for that endpoint, with no cross-check against the repository identity (owner/name) that was originally resolved. This mirrors the referral-code bug's broken invariant: a value that should require explicit user consent to change is instead auto-overwritten based on an externally-supplied value that the app trusts as authoritative.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches the repository from the API (`api.fetchRepository(owner, name)`) and, if the repo already has a `gitHubRepository` association, calls `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then silently calls `gitStore.setRemoteURL(...)` to change the `origin` remote to whatever `clone_url` the API returned, as long as three heuristic conditions hold (protocol unchanged, the *previous* cached `cloneURL` still matches the current remote, and the new URL differs): [2](#0-1) 

The check `remoteUrlUnchanged` only verifies that the local remote still matches the **previously cached** `gitHubRepository.cloneURL` — it does not verify that the **new** `apiRepo.clone_url` still refers to the same owner/name/repository identity that the user originally cloned or that Desktop originally resolved to this account. `urlMatchesRemote` only compares hostname/owner/name structurally; it never validates that the API response is self-consistent with the account/endpoint the request was made against beyond what the server chooses to return. Any endpoint controller that can influence the `clone_url` field of the `fetchRepository` response (a compromised/malicious/MITM'd GitHub Enterprise endpoint, or a spoofed proxy sitting in front of one, per the "attacker controls ... a git remote/proxy response" and "GitHub API object" impact categories) can therefore cause Desktop to **silently repoint `origin` to an attacker-controlled host** the next time this refresh runs, with no prompt to the user.

This is directly analogous to the referral-code bug: a background/automatic call (analogous to the admin calling `setUniqRefferralCode()`) overwrites an important stored association (remote URL, analogous to a referral binding) based on trusting the latest externally-provided value, and the legitimate/expected value (the URL the user cloned/configured) is discarded without consent.

### Impact Explanation
If the remote is silently rewritten to an attacker-controlled URL:
- Subsequent `git push` operations from the user will silently go to the attacker's server instead of the intended GitHub repository — this is exactly the "silent corruption of what the user commits or pushes" category called out as valid impact.
- Subsequent `git fetch`/`pull` operations will pull code from the attacker's server, which could then be merged into the user's working tree/history without an out-of-band signal that the remote changed.
- Because `envForRemoteOperation`/credential helpers key off the host in the remote URL, depending on credential-manager configuration this could also affect which host receives authentication material during the operation, extending the risk into credential exposure territory.

### Likelihood Explanation
This refresh path (`repositoryWithRefreshedGitHubRepository`) runs as part of routine, non-interactive maintenance flows (e.g., account refresh / repository refresh), not just as a response to explicit user action, so the write can occur automatically in the background whenever the API's `clone_url` differs from what's cached. Exploitation requires the attacker to control the response of the configured API endpoint for the currently-associated GitHub Enterprise/GitHub instance (e.g., a compromised/malicious GHE server or a machine-in-the-middle position on that endpoint), which fits the report's allowed threat model of an attacker-controlled "GitHub API object" or "proxy response." No local access, admin rights, or social engineering is required — only that the app's configured endpoint (already an in-scope trust boundary for GHE-connected users) return a manipulated `clone_url`.

### Recommendation
- Do not silently rewrite `origin`/other remotes based solely on API responses. At minimum, require that the change be confirmed by the user (a banner/dialog similar to how other destructive Desktop operations prompt), especially when the new host differs from the currently configured host.
- Strengthen the invariant check: instead of only checking that the local remote still matches the previously cached `cloneURL`, additionally verify that the *new* `clone_url`'s owner/name pair still corresponds to the identifiers (`owner`, `name`) that were used to make the `fetchRepository(owner, name)` call, and treat a hostname change in particular as requiring explicit confirmation.
- Consider pinning/verifying the API endpoint's identity (e.g., certificate/host verification already handled by TLS, but also sanity-check that a GHE endpoint's `clone_url` host is consistent with the endpoint's own host) before trusting cross-host redirects.

### Proof of Concept
1. User configures a GitHub Enterprise account whose endpoint is (or later becomes, e.g. via DNS compromise/MITM/malicious admin of that GHE instance) attacker-influenced, and has a repository with `origin` pointing to `https://ghe.company.com/org/repo.git`.
2. Desktop periodically calls `repositoryWithRefreshedGitHubRepository` (e.g., during account refresh) which calls `api.fetchRepository(owner, name)` against that endpoint. [3](#0-2) 
3. The attacker-influenced endpoint returns an `IAPIFullRepository` with the same `owner`/`name` metadata but a `clone_url` pointing to `https://ghe.company.com.evil.tld/org/repo.git` (or any attacker host reachable via https), satisfying `protocolsMatch` and `remoteUrlUnchanged` (since the *previous* cached clone URL still matches the current remote) and failing `urlsMatch` (since the new URL differs). [4](#0-3) 
4. `gitStore.setRemoteURL('origin', 'https://ghe.company.com.evil.tld/org/repo.git')` executes with no user prompt, silently repointing `origin`.
5. The next `git push`/`git fetch` performed by the user via Desktop's UI transparently targets the attacker's host.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
