### Title
Out-of-range `Participant` index in blame evaluation panics via unchecked `HashMap` indexing, crashing the DKG blame process - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2021-44920 is a crash-class bug: a function dereferences an invalid address on attacker-influenced input, causing a segmentation fault and process abort. In Serai's memory-safe code, the reachable analog is an unhandled panic on attacker-controlled indexes. `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender` and `recipient` `Participant` values derived from an accusation, then index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` without verifying the indexes are in the participant set `1..=n`. `Participant::new` accepts any nonzero `u16`, far beyond `n`, so a blame accusation naming a non-existent participant triggers a `HashMap` index panic — an abort equivalent to the GPAC crash, reachable entirely through public inputs (`EncryptedMessage::read`, `EncryptionKeyProof::read`, and the accusation's participant fields).

### Finding Description
`blame_internal` performs two unchecked map lookups on caller-supplied participant indexes:

- `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` indexes `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388` — panics if `recipient` was never registered (e.g., `AdditionalBlameMachine::new` only registers `1..=n`, so `recipient = Participant(n+1)` panics).
- If decryption/proof succeed and the decrypted bytes parse as a scalar via `C::F::from_repr`, it evaluates `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` — panics for any `sender ∉ 1..=n`.

Nothing validates `sender`/`recipient` against `ThresholdParams::all_participant_indexes()` or map membership before indexing. The required cryptography is attacker-satisfiable: the PoP challenge binds `sender` as a mere transcript field (`pop_challenge` at `crypto/dkg/pedpop/src/encryption.rs:302-324`), so a malicious accuser generates a fresh ephemeral key and Schnorr PoP naming `sender = Participant(0xFFFF)`; since the accuser knows their own ECDH secret, they produce a valid `EncryptionKeyProof` (DLEq over `[generator, msg.key]` and `[enc_keys[recipient], proof.key]`) and a ciphertext that decrypts to a canonical scalar — reaching line 599.

### Impact Explanation
A single crafted blame accusation deterministically panics the evaluating process (`index` on a missing `HashMap` key is an unconditional panic). Analogous to CVE-2021-44920's segmentation fault, this aborts DKG fault-resolution processing; in a validator/processor context it is a remote, input-triggered denial of service. It cannot forge blame outcomes (the panic precedes any verdict), so impact is availability-only — consistent with Medium severity.

### Likelihood Explanation
Reachability is high for any deployment exposing `AdditionalBlameMachine::blame`/`BlameMachine::blame` to accusation messages from other participants: the attacker controls `sender`, `recipient`, `msg` (via `EncryptedMessage::read`), and `proof` (via `EncryptionKeyProof::read`), and needs no honest-party secret material since they know their own encryption key. Exploitation requires only a blame/accusation path fed by unauthenticated participant fields. Caveat: the crate documents that messages "must have been authenticated as having come from the sender," so exploitability depends on the caller passing the accused `sender` index from the accusation rather than from authenticated session state; the panic remains an in-library robustness failure either way.

### Recommendation
Before indexing, validate `sender` and `recipient` are members of the registered participant set in `blame_internal`/`decrypt_with_proof` — e.g., return `sender` (or a dedicated error) when `!self.commitments.contains_key(&sender)`, and use `self.enc_keys.get(&decryptor)` returning `DecryptionError::InvalidProof` on `None` instead of `HashMap::index`.

### Proof of Concept
```rust
// Any participant set, e.g. t=2, n=3. Build AdditionalBlameMachine
// with the three authenticated EncryptionKeyMessage<Commitments> msgs.
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Malicious accuser (participant 2) crafts a blame package naming a
// non-existent sender. Participant::new accepts any nonzero u16.
let fake_sender = Participant::new(0xFFFF).unwrap();
let recipient   = Participant::new(2).unwrap(); // the accuser, registered

// Accuser knows their own enc_key, so they compute the shared key
// kG' = enc_key * msg.key, build a valid EncryptionKeyProof (DLEq), and
// encrypt a canonical scalar under cipher(context, kG'). They also sign
// a valid PoP for `from = fake_sender` using a fresh ephemeral key.
let msg   /* EncryptedMessage<_, SecretShare<F>> */ = crafted_msg;
let proof /* EncryptionKeyProof */                  = crafted_proof;

// decrypt_with_proof succeeds (PoP + DLEq valid), from_repr succeeds,
// then line 599 evaluates `self.commitments[&fake_sender]`:
//   thread panics: "no entry found for key"
machine.blame(fake_sender, recipient, msg, Some(proof));
```

The panic sites are `crypto/dkg/pedpop/src/lib.rs:599` (`self.commitments[&sender]`) and, for an unregistered `recipient`, `crypto/dkg/pedpop/src/encryption.rs:388` (`self.enc_keys[&decryptor]`).
