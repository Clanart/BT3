### Title
Case-Sensitive String Matching in Hookify Rule Engine Allows Bypass of File/Command Protection Rules on Case-Insensitive Filesystems - (File: plugins/hookify/core/rule_engine.py)

### Summary
The `hookify` plugin's `RuleEngine._check_condition()` implements the `contains`, `equals`, `not_contains`, `starts_with`, and `ends_with` operators as raw, case-sensitive Python string comparisons, while the `regex_match` operator is compiled with `re.IGNORECASE`. This inconsistency mirrors the reported domain-normalization bug class: a security-relevant string comparison fails to normalize case before making an allow/deny decision, even though the downstream consumer (the filesystem, or a case-insensitive interpreter) treats differently-cased inputs as identical. A hookify rule author writing a `PreToolUse`/file-protection rule with `equals`/`ends_with`/`contains` on `file_path` (a documented, supported field per `config_loader.py`) can be silently bypassed by writing to a path that differs only in letter casing but resolves to the exact same file on the default case-insensitive filesystems used by macOS (APFS/HFS+) and Windows (NTFS).

### Finding Description
`plugins/hookify/core/rule_engine.py`'s `_check_condition` dispatches on `condition.operator`: [1](#0-0) 

Only `regex_match` goes through `_regex_match`, which uses a globally cached, case-insensitive compiled pattern: [2](#0-1) 

The other four string operators perform exact-case comparisons on `field_value`, which can be the `file_path` of a `Write`/`Edit`/`MultiEdit` tool call, extracted verbatim from `tool_input`: [3](#0-2) 

Documentation for hookify-style rule files (and the broader plugin-dev hook guidance) explicitly recommends using simple pattern/path checks like this to protect sensitive paths (`.env`, credentials, system directories) — e.g. `plugins/plugin-dev/skills/hook-development/references/migration.md` shows the exact pattern of checking `file_path` for protected names: [4](#0-3) 

A rule such as:
```yaml
---
name: block-env-writes
enabled: true
event: file
action: block
conditions:
  - field: file_path
    operator: ends_with
    pattern: .env
---
```
uses `field_value.endswith(pattern)`, which is case-sensitive. On macOS/Windows, `.claude/config.ENV` and `.claude/config.env` refer to the *same inode/file* at the OS level, but the rule only fires for the lowercase spelling — exactly analogous to `wilder` vs `wIlder` resolving to the same domain client-side while being treated as distinct on-chain. The Write tool itself performs no case normalization before hitting the filesystem, so the protection gate and the actual resource-identity check are desynchronized.

### Impact Explanation
An agent (or a user/prompt-injected instruction driving the agent) can write to, or overwrite content in, a file that a hookify rule was configured to protect (e.g., `.env`, `id_rsa`, `credentials.json`) simply by having Claude target a differently-cased path. Because case-insensitive filesystems resolve the alternate-case path to the identical underlying file, the write succeeds against the real protected resource despite the rule's intent, defeating a locally-configured PreToolUse safety/approval gate. This is a concrete unauthorized-file-write bypass of a trust boundary the user explicitly configured via `.claude/hookify.*.local.md`.

### Likelihood Explanation
Hookify's own documentation and testing examples showcase exactly these operators (`equals`, `contains`, `ends_with`) for path/content matching, and rule authors have no indication that these operators are unsafe on case-insensitive filesystems (unlike `regex_match`, which is documented/implemented as case-insensitive). Any environment running Claude Code on macOS or Windows with a hookify file-protection rule using a non-regex operator on `file_path` is exposed. The trigger requires no special privilege — an ordinary agent turn that writes with a differently-cased filename suffices.

### Recommendation
Normalize case consistently across all string operators in `_check_condition`, or explicitly document/enforce that `file_path` (and other filesystem-identity fields) must be compared after path/case normalization (e.g., `os.path.normcase`/lowering both `field_value` and `pattern` before `contains`/`equals`/`starts_with`/`ends_with`/`not_contains`), matching the case-insensitive behavior already used for `regex_match`. Alternatively, resolve `file_path` to its real filesystem path (or apply platform-aware case folding) before matching, so a case variation cannot silently defeat a configured protection rule.

### Proof of Concept
1. Create `.claude/hookify.block-env.local.md`:
```
---
name: block-env-writes
enabled: true
event: file
action: block
conditions:
  - field: file_path
    operator: ends_with
    pattern: .env
---
Blocked write to .env file
```
2. On macOS/Windows, have the agent call the `Write` tool with `file_path: "secrets.ENV"` (or any casing other than `.env`).
3. `rule_engine.py`'s `field_value.endswith(pattern)` evaluates `"secrets.ENV".endswith(".env")` → `False`; the rule does not fire and `hookify`'s `pretooluse.py` returns an empty decision, allowing the write. [5](#0-4) 
4. On a case-insensitive filesystem, `secrets.ENV` resolves to the same file as any existing `secrets.env` (or creates a file indistinguishable to any subsequent case-insensitive lookup), so the intended protection is bypassed against the real target resource.

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

        elif tool_name in ['Write', 'Edit']:
            if field == 'content':
                # Write uses 'content', Edit has 'new_string'
                return tool_input.get('content') or tool_input.get('new_string', '')
            elif field == 'new_text' or field == 'new_string':
                return tool_input.get('new_string', '')
            elif field == 'old_text' or field == 'old_string':
                return tool_input.get('old_string', '')
            elif field == 'file_path':
                return tool_input.get('file_path', '')

        elif tool_name == 'MultiEdit':
            if field == 'file_path':
                return tool_input.get('file_path', '')
            elif field in ['new_text', 'content']:
                # Concatenate all edits
                edits = tool_input.get('edits', [])
                return ' '.join(e.get('new_string', '') for e in edits)

        return None
