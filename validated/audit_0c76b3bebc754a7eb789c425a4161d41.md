### Title
`with-ft`/`with-nft` allowance wildcard sentinel collides with the literal asset name `"*"`, letting assets move past `restrict-assets?`/`as-contract?` allowances - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
The Sherlock report flags a case where a supposedly strict minimum check (3-day vesting) is silently satisfied by a much weaker check (1-day), letting a market operator do more than the spec intends. The analogous class of bug here is a validation routine that is supposed to check one specific asset but, due to an internal implementation shortcut, ends up authorizing a broader set of assets than the caller declared. In `check_allowances()` in `clarity/src/vm/functions/post_conditions.rs`, the code treats the literal fungible/non-fungible asset name `"*"` as a magic "wildcard, matches every asset in this contract" sentinel [1](#0-0) [2](#0-1) , but `"*"` is also a syntactically valid `ClarityName` that any Clarity contract can legitimately use as a real token name (e.g. `(define-fungible-token * u1000000)`), because operator-style identifiers are accepted by the Clarity lexer.

### Finding Description
`eval_allowance()` builds an `Allowance::Ft`/`Allowance::Nft` from whatever ASCII string the Clarity code passes as the asset name, with no restriction preventing the literal string `"*"` [3](#0-2) . Later, `check_allowances()` uses that exact same string internally as a sentinel meaning "any fungible/non-fungible asset in this contract, no matter its real name":

```
if let Some(wildcard_vec) = ft_allowances.get(&AssetIdentifier {
    contract_identifier: asset.contract_identifier.clone(),
    asset_name: ClarityName::from_literal("*"),
}) {
    merged.extend(wildcard_vec.iter().cloned());
}
``` [4](#0-3) 

Because there is no separate internal representation for "wildcard" versus "the token whose real name happens to be `*`", a developer who writes `(with-ft some-contract "*" 100)` intending to authorize only the specific FT named `"*"` in `some-contract` unintentionally authorizes movement of *every* fungible token defined in `some-contract`, up to amount `100` each, since the lookup in the FT-movement loop merges the exact-match and "wildcard" allowance lists without distinguishing them [5](#0-4) . The identical pattern exists for NFTs [6](#0-5) .

### Impact Explanation
`restrict-assets?`/`as-contract?` are supposed to enforce an equality: only the exact assets/amounts declared in the allowance list may move; anything else rolls back the transaction with a violation index [7](#0-6) . Any Clarity contract (e.g. a vault or DEX) that legitimately holds/interacts with a token literally named `"*"` and expresses an allowance for it via `with-ft`/`with-nft` will have that allowance silently reinterpreted as a blanket approval for every other fungible/non-fungible asset under the same contract principal. An unprivileged caller of such a vault's public entry point can therefore cause the contract to move a *different*, unintended asset out from under the allowance check — an asset moving past its declared post-condition/allowance, which matches the "asset moving past its post-conditions" Critical impact category.

### Likelihood Explanation
This requires a contract that defines (or is asked to authorize) an asset whose real name is the single character `"*"`, which is an unusual but syntactically legal `ClarityName`/token name in Clarity. It is not attacker-triggerable purely by transaction construction; it depends on a specific contract-author choice, so likelihood is lower than a pure protocol-level bug, but the root cause (sentinel value colliding with a legitimate value in the same namespace with no escaping/reservation) is a concrete implementation defect independent of any specific contract.

### Recommendation
Represent the "match all assets in a contract" wildcard as a distinct enum variant / dedicated field rather than overloading the `asset_name` string space with the literal `"*"`. If backward compatibility with the string-based API must be preserved, reserve `"*"` at the `ClarityName` validation layer for asset names used in `with-ft`/`with-nft` allowances, or require an explicit separate wildcard token type so a real asset genuinely named `"*"` cannot be aliased into an all-assets allowance.

### Proof of Concept
1. Deploy contract `bank.clar` that defines two fungible tokens: `(define-fungible-token * u1000000000)` and `(define-fungible-token real-token u1000000000)`, both held by `bank`.
2. `bank` exposes a public function that does:
   ```
   (as-contract? ((with-ft .bank "*" u100))
     (ft-transfer? real-token u100000 tx-sender recipient))
   ```
   intending to authorize moving up to 100 units of the token literally named `*` only.
3. Because `check_allowances()` treats `asset_name: "*"` as a wildcard for the whole `.bank` contract, the `ft-transfer?` of `real-token` (a completely different token, for a much larger amount than the declared `100`) passes the allowance check and is not rolled back, letting an unprivileged caller drain `real-token` far beyond what the `with-ft` allowance was meant to permit.
