### Title
Missing minimum/maximum `relative_lock_height` (heightlock) validation when joining a pool via `PlotNFT2Wallet` in `pw_join_pool` - (File: chia/wallet/wallet_rpc_api.py)

### Summary
The Sherlock report describes a `ProtectionPool` that can be initialized with `minProtectionDurationInSeconds == 0` because no bounds check is applied to a duration/lock parameter before it is persisted into pool state, allowing a downstream buyer to purchase "duration-less" coverage. The Chia analog is the pool-lock-height parameter (`relative_lock_height` / `heightlock`) that Chia's pooling protocol relies on to prevent a farmer from quickly leaving a pool after being credited a block reward pledged to that pool. For the legacy `PoolWallet` path this value is bounds-checked; for the newer `PlotNFT2Wallet` path reached through the same RPC endpoint, it is not.

### Finding Description
`PoolWallet` enforces `MINIMUM_RELATIVE_LOCK_HEIGHT` (5) and `MAXIMUM_RELATIVE_LOCK_HEIGHT` (1000) via `_verify_pooling_state()`, which is invoked from `_verify_initial_target_state()` inside `PoolWallet.join_pool()`: [1](#0-0) [2](#0-1) 

However, the same RPC entry point, `pw_join_pool()`, has a second code path for `PlotNFT2Wallet` (the newer plotnft implementation) that constructs a `PoolConfig` directly from the caller-supplied `request.relative_lock_height` and immediately calls `wallet.join_pool(...)`, with no call into any lock-height bounds check equivalent to `_verify_pooling_state`: [3](#0-2) 

`PoolConfig.heightlock` is the value later embedded into the on-chain `Heightlock` restriction that is supposed to enforce the pool's mandatory wait period before a self-pooling/leaving-pool transition can complete: [4](#0-3) [5](#0-4) [6](#0-5) 

The CLI-side helper `create_pool_args`/`join_pool` in `chia/cmds/plotnft_funcs.py` only rejects a lock height that is *too high* (`> 1000`), never checks for zero or unreasonably low values, and this is only a client-side/UX guard, not enforced by the RPC or wallet code itself: [7](#0-6) [8](#0-7) 

Because `pw_join_pool` is a wallet RPC callable directly by any local RPC caller controlling a `PlotNFT2Wallet`, and because no minimum bound analogous to `MINIMUM_RELATIVE_LOCK_HEIGHT` is applied on this path, a caller can join a pool (or the pool itself, since the value ultimately mirrors what the remote `/pool_info` endpoint or the RPC caller supplies) with `heightlock = 0` or another too-small value.

### Impact Explanation
The wait-time enforced by `relative_lock_height`/`heightlock` exists specifically to stop a farmer from farming a block for a pool and then immediately leaving before the pool can react/claim it — this is explicitly documented as an anti-cheat mechanism in `PoolWallet`'s docstring ("The pool is also protected, by not allowing members to cheat by quickly leaving a pool, and claiming a block that was pledged to the pool."). If the `PlotNFT2Wallet` join path accepts an unvalidated (e.g. zero) heightlock, a malicious or careless plot-NFT owner (or a malicious pool advertising a bad `relative_lock_height`) can create a pooling arrangement that provides no real lock/cooldown guarantee, defeating the trust assumption pool operators rely on and potentially enabling reward theft from a pool that assumed the standard minimum delay would apply.

### Likelihood Explanation
Reachable by any local wallet RPC caller who owns a `PlotNFT2Wallet` and calls `pw_join_pool` (directly, or indirectly through the `chia plotnft join` CLI, which itself derives `relative_lock_height` from the *pool's* HTTP response and only rejects overly large values, not overly small ones). No special privileges beyond normal wallet RPC access are required, and the missing check is a straightforward code-path divergence between the legacy `PoolWallet` and `PlotNFT2Wallet` handling within the same function.

### Recommendation
Add the same minimum/maximum `relative_lock_height` validation used for `PoolWallet` (`MINIMUM_RELATIVE_LOCK_HEIGHT`/`MAXIMUM_RELATIVE_LOCK_HEIGHT`, or an equivalent constant for `PlotNFT2Wallet`) to the `PlotNFT2Wallet` branch of `pw_join_pool()` in `chia/wallet/wallet_rpc_api.py`, and/or inside `PlotNFT2Wallet.join_pool()` / `PoolConfig` construction, before the `PoolConfig` is used to build coin spends.

### Proof of Concept
1. Call the wallet RPC `pw_join_pool` for a wallet id backed by `PlotNFT2Wallet`, supplying `relative_lock_height = 0` (or `1`) and an arbitrary `target_puzzlehash`/`pool_url`.
2. Observe that `wallet_rpc_api.py`'s `PlotNFT2Wallet` branch builds `PoolConfig(heightlock=0, ...)` and calls `wallet.join_pool(...)` directly with no bounds check, unlike the `PoolWallet` branch which routes through `create_pool_state` → `join_pool` → `_verify_initial_target_state` → `_verify_pooling_state`, which would reject `relative_lock_height < 5`.
3. The resulting plot-NFT pool coin embeds a `Heightlock(0)` restriction, meaning the mandatory pool-exit wait period is effectively bypassed.

Note: I could not fully trace whether `PlotNFT2Wallet.join_pool()` (defined in `chia/wallet/plotnft_wallet/plotnft_wallet.py`) performs its own internal lock-height bounds check further downstream — the code excerpts available to me only show the `_finish_leaving_pool` and `get_current_state` portions of that file, not the `join_pool` method body itself. If Devin session access confirms an internal check exists there, this finding would need to be downgraded or dropped; I recommend verifying `PlotNFT2Wallet.join_pool()`'s full body before treating this as conclusively unpatched.

    @classmethod
    def _verify_pooling_state(cls, state: PoolState) -> str | None:
        err = ""
        if state.relative_lock_height < cls.MINIMUM_RELATIVE_LOCK_HEIGHT:
            err += (
                f" Pool relative_lock_height ({state.relative_lock_height})"
                f"is less than recommended minimum ({cls.MINIMUM_RELATIVE_LOCK_HEIGHT})"
            )
        elif state.relative_lock_height > cls.MAXIMUM_RELATIVE_LOCK_HEIGHT:
            err += (
                f" Pool relative_lock_height ({state.relative_lock_height})"
                f"is greater than recommended maximum ({cls.MAXIMUM_RELATIVE_LOCK_HEIGHT})"
            )

        if state.pool_url in {None, ""}:
            err += " Empty pool url in pooling state"
        return err
