This confirms the analog: the `tokenfactory` module's denom `AllowList` (set via `MsgCreateDenom` or `MsgUpdateDenom`) acts as a denom-scoped blocklist mechanism, and the bank module's `Send` message enforces it on **both sender and receiver** for every transfer of that denom. [1](#0-0) [2](#0-1) [3](#0-2) 

The denom admin (an "authority" role reachable via a normal `MsgUpdateDenom` transaction) can retroactively install or edit an `AllowList` on an existing tokenfactory denom that already has holders. Any holder whose address is not in the (new) allow list is immediately unable to move their already-held balance of that denom — the same freezing effect as the USDT-blacklist scenario in the reference report, just implemented as an allow-list instead of a deny-list. Because the check is enforced identically on both `from` and `to` in `MsgSend`, a holder can go from being able to freely transact to permanently locked out with no override or admin bypass path once their tokens are already in their wallet. [4](#0-3) [5](#0-4) 

I did not find any fallback/whitelist grandfathering logic for token holders when an allow list is updated (unlike the `distribution` module's `BlockedAddr` handling, which explicitly falls back to the community pool to avoid stuck funds, per `sei-cosmos/x/distribution/keeper/keeper.go` and its accompanying tests). That fallback pattern in `distribution` is not applied to the tokenfactory allow-list/bank-send path. [6](#0-5) 

### Title
Tokenfactory denom allow-list update can permanently freeze existing holders' balances - (File: x/tokenfactory/keeper/msg_server.go, sei-cosmos/x/bank/keeper/msg_server.go)

### Summary
A tokenfactory denom admin can call `MsgUpdateDenom` to install or modify a denom's `AllowList` at any time after the denom has been created and distributed to holders. Because `x/bank`'s `MsgSend` handler enforces `IsInDenomAllowList` on both sender and recipient for tokenfactory-prefixed denoms, any address holding the denom that is not included in the (new) allow list becomes permanently unable to transfer its existing balance — mirroring the "blacklist freezes user assets" bug class from the reference report, except implemented as an allow-list.

### Finding Description
`MsgSend` in `sei-cosmos/x/bank/keeper/msg_server.go` calls `k.IsInDenomAllowList(ctx, from, ...)` and `k.IsInDenomAllowList(ctx, to, ...)`, rejecting the transfer with `ErrUnauthorized` if either address is absent from a non-empty allow list for a `factory/...` denom (`sei-cosmos/x/bank/keeper/send.go` lines 501-524). The allow list is settable at denom creation (`MsgCreateDenom`) and can also be updated later at will by the current admin via `MsgUpdateDenom`, handled in `x/tokenfactory/keeper/msg_server.go`'s `UpdateDenom`, which simply calls `server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)` with no restriction preventing removal of existing holders. There is no mechanism to grandfather balances already held by an address before it is excluded from the allow list — the balance remains on-chain under that user's account but cannot be sent by them (nor received back if sent out and returned), because the check applies unconditionally to `from`/`to` on every `MsgSend`.

### Impact Explanation
Any holder of a tokenfactory denom that had (or later has) an allow list can be excluded by the denom admin at any point, permanently freezing their already-acquired token balance in place — the tokens remain in their account (not stolen), but become non-transferable indefinitely unless the admin reverts the allow list. This matches the "funds frozen in the protocol" impact class from the reference report (the analog here is the tokenfactory admin acting as an authority who can retroactively lock out a holder, rather than USDT freezing at the ERC20 level).

### Likelihood Explanation
Reachable by any tokenfactory denom admin (a permissionless role obtainable by anyone who creates a denom via `MsgCreateDenom`) performing a single `MsgUpdateDenom` transaction against their own denom. No governance or validator collusion is required, and the admin role is the intended actor for this action — this is an inherent design property of the allow-list feature rather than an implementation bug, so likelihood of *misuse* depends on whether third parties actually hold tokens under an admin-controlled denom.

### Recommendation
Consider whether allow-list updates should only apply going forward to newly-minted supply, or provide a defined exit/redemption path (e.g., allow removal from a denom, or a burn/refund route) for addresses that hold balances at the time they are excluded from an updated allow list, so that existing balances are never rendered permanently non-transferable purely by an admin-side allow-list change.

### Proof of Concept
1. Admin creates denom `factory/{admin}/TEST` via `MsgCreateDenom` with no allow list (or an allow list containing user A).
2. User A acquires a balance of `factory/{admin}/TEST` through normal transfers.
3. Admin calls `MsgUpdateDenom` on the same denom with a new `AllowList` that omits user A's address.
4. User A attempts `MsgSend` of their existing balance — `IsInDenomAllowList` returns `false` for `from = A`, and the transaction is rejected with `"%s is not allowed to send funds"`.
5. User A's balance remains stuck; there is no way for them to move it while excluded from the allow list, matching the "assets frozen in the protocol" impact of the referenced report.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}
