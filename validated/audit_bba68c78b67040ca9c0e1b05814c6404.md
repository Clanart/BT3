### Title
`EnsureInstalled` legacy flow trusts raw `shop` param to load another store's offline session - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
When an app does not use the new embedded auth strategy (`use_new_embedded_auth_strategy? == false`), `ShopifyApp::EnsureInstalled` derives the acting shop entirely from the unauthenticated `params[:shop]` value, loads that shop's offline session, and only checks that the stored access token still works against Shopify — it never verifies that the incoming request was actually issued/signed by that shop's merchant (no HMAC, no ID token / JWT check). Any anonymous caller who supplies a known installed `shop` domain can drive controller logic using that shop's offline session.

### Finding Description
`current_shopify_domain` takes `params[:shop]`, only formats/validates it as a syntactically-trusted domain via `ShopifyApp::Utils.sanitize_shop_domain`, with no cryptographic binding to the requester: [1](#0-0) 

`installed_shop_session` then loads the stored offline session strictly by that derived domain: [2](#0-1) 

The legacy before_action chain (used whenever `use_new_embedded_auth_strategy?` is false) is: `check_shop_domain` → `check_shop_known` → `validate_non_embedded_session`, none of which authenticate the request itself: [3](#0-2) 

`validate_non_embedded_session` merely performs a REST `GET shop` call using `installed_shop_session` to confirm the stored offline token is still valid — it does not confirm the caller is that shop's merchant, only that the shop's token hasn't been revoked: [4](#0-3) 

Existing tests confirm this behavior explicitly: supplying only `shop: shopify_domain` as a GET param — with no HMAC, no ID token, no session token — is sufficient to reach the controller action using that shop's session and receive `:ok`: [5](#0-4) 

None of the checks that would normally close this gap are present in this path: `sanitize_shop_domain` only validates domain *format* (myshopify.com/shopify.com/etc.), not provenance; ID token/JWT verification (`ShopifyApp::TokenExchange#activate_shopify_session`) is only wired in when `use_new_embedded_auth_strategy?` is true; there is no HMAC verification middleware invoked for this controller path (HMAC checks in this codebase exist only for webhooks/app-proxy/callback, not for `EnsureInstalled` actions); and CSRF protections don't apply to GET requests. Consequently, an attacker who simply knows (or enumerates) a `shop` domain that has previously installed the app can send `GET /any_ensure_installed_action?shop=victim-shop.myshopify.com` and have the controller action execute with `victim-shop`'s offline session, as long as that shop's offline token is still valid.

### Impact Explanation
This allows cross-shop access: an unprivileged/anonymous caller can cause any `EnsureInstalled`-protected controller action to execute business logic (and any Shopify Admin API calls the app makes) using another store's offline access token, without proving control of that store. This matches Shopify's "cross-shop data access" HackerOne impact class — the "installed shop session" is loaded and used based purely on the attacker-supplied `shop` param.

### Likelihood Explanation
Preconditions: only applies to apps that do not enable `use_new_embedded_auth_strategy` (i.e., have not migrated to Shopify's token-exchange/managed-install flow) and still include `ShopifyApp::EnsureInstalled` on a controller. The victim shop must have previously installed the app (so an offline session exists) and must not have uninstalled/revoked the token. The attacker needs no secrets — only the target shop's `.myshopify.com` domain, which is often guessable/public. This is directly demonstrated by the existing unit test suite without any mocking of HMAC or JWT verification, indicating the code path genuinely has no such check.

### Recommendation
For the legacy (non-token-exchange) path, do not derive the acting shop purely from `params[:shop]`. At minimum:
- Require and verify a Shopify-signed value (HMAC query param or Shopify session cookie set during the OAuth/login flow) before trusting `params[:shop]` to select an offline session, or
- Encourage/force migration to `use_new_embedded_auth_strategy` (token exchange), which binds the session to a verified Shopify ID token, and treat the legacy `validate_non_embedded_session` path as deprecated/insecure and warn/log when it is used.

### Proof of Concept
Using the existing test harness pattern in `test/controllers/concerns/ensure_installed_test.rb`:
```ruby
test "cross-shop access via raw shop param" do
  victim_session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain)
    .with("victim-shop.myshopify.com").returns(victim_session)

  client = mock
  ShopifyAPI::Clients::Rest::Admin.expects(:new).with(session: victim_session).returns(client)
  client.expects(:get).with(path: "shop")

  # Anonymous attacker request, no HMAC/JWT/session token supplied
  get :index, params: { shop: "victim-shop.myshopify.com" }

  assert_response :ok # controller action executed using victim's offline session
end
```
This mirrors the existing passing test [5](#0-4) , demonstrating that supplying only the `shop` param is sufficient to invoke the action bound to that shop's stored offline session, with no verification that the requester is that shop's merchant.
