### Title
Outbound request/consensus delivery rewards become permanently unclaimable once the module/chain reward is set to zero after delivery - ([File: modules/pallets/relayer/src/outbound_request.rs])

### Summary
`pallet-ismp-relayer` computes the payable reward for an already-delivered, already-verified message at **claim time** by reading the *current* value of `OutboundRequestDeliveryReward[module_id]` (or `OutboundConsensusDeliveryReward[state_machine]`), instead of the value that was in effect when the delivery actually happened. If that reward is reduced to zero between delivery and claim, the relayer who already performed the delivery (and whose entitlement is permanently recorded on the destination chain's receipt/epoch slot) can never claim it — the reward is locked forever. This is the same broken invariant as the reported bug: an underlying entitlement (staker's vault rewards / relayer's delivery reward) is retroactively excluded from a "currently valid" set (`getVaults(epoch)` / `OutboundRequestDeliveryReward > 0`) even though it was earned while the set still included it.

### Finding Description
`process_outbound_request_delivery_claim` performs its verification pipeline strictly against **current** on-chain configuration: [1](#0-0) 

The reward amount used for the transfer is fetched live from storage at claim time, not pinned to the value that existed when the request was actually delivered (i.e., when `RequestReceipts[commitment]` was written on the destination and the relayer earned the entitlement): [2](#0-1) 

The doc comment on the setter explicitly states that a module can be de-listed by zeroing its reward: [3](#0-2) 

The exact same pattern exists for the consensus-delivery reward path (`OutboundConsensusDeliveryReward[state_machine]`), which is likewise looked up at claim time rather than pinned at delivery time, per the module documentation: [4](#0-3) [5](#0-4) 

Sequence that reproduces the loss:
1. A relayer delivers a hyperbridge-originated `PostRequest` from module `M` to a destination while `OutboundRequestDeliveryReward[M] = X > 0`. The destination's `RequestReceipts[commitment]` now permanently records the delivering relayer's address — this entitlement is immutable once written.
2. Before the relayer submits `claim_outbound_request_delivery_reward`, `set_outbound_request_delivery_reward(M, 0)` is called (a normal, expected lifecycle operation for de-registering a module, exactly analogous to `removeVault` in the report).
3. The relayer now calls `claim_outbound_request_delivery_reward` with a valid state proof of the already-delivered receipt and a valid signature from the address that performed the delivery.
4. `ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured)` at line 149 fails, because the pallet re-reads `OutboundRequestDeliveryReward[M]` at claim time, which is now zero.
5. The delivery is real, the receipt proof is real, the signature is valid, `OutboundRequestsClaimed` was never set for this commitment — yet the claim path is permanently blocked. There is no other path to redeem this specific, already-earned reward: `RequestCommitments` retains the commitment, `OutboundRequestsClaimed` stays unset, but the reward gate cannot be satisfied ever again for this `module_id` unless a *future* governance action happens to reconfigure the reward back to a nonzero value — a coincidence the relayer cannot rely on and which, if it did happen, would create ambiguity about historical vs. current reward rates.

This is structurally identical to the Suzaku `Rewards::claimRewards` bug: an already-accrued, already-recorded entitlement is filtered out by a live/current-state lookup (`getVaults(epoch)` vs. `OutboundRequestDeliveryReward[module_id]`) instead of a lookup pinned to the epoch/delivery at which the entitlement was earned.

### Impact Explanation
Funds (treasury-funded relayer incentive payouts) become permanently locked/unclaimable for legitimately delivered, cryptographically-proven work, matching the bounty's "loss of funds" / "logic attack" categories. Because the relayer incentive system is core to Hyperbridge's liveness model (it is what pays for proof delivery across the bridge), a stuck reward directly harms protocol economics and relayer trust, and the treasury retains funds it owes but can never be forced to pay out through the normal claim path.

### Likelihood Explanation
Reward de-configuration via `set_outbound_request_delivery_reward(module_id, 0)` / `set_outbound_consensus_delivery_reward(state_machine, 0)` is a documented, expected governance operation ("Setting `amount = 0` removes the module from the allowlist"), not an attack. Any ordinary module deprecation, reward-rate migration, or clean-up performed between a relayer's delivery and its (asynchronous, batched, sometimes delayed) claim submission triggers this bug. Given relayers batch and defer claims (see `tesseract/relayer/src/claim_rewards.rs`, `outbound_request_claim.rs`), the delivery-to-claim window is nontrivial and this is likely to occur during normal operational reward-schedule updates.

### Recommendation
Snapshot the reward rate at the time the entitlement is created (e.g., store the reward amount alongside the receipt/epoch data, or index historical reward rates by block/epoch) instead of reading the live `OutboundRequestDeliveryReward` / `OutboundConsensusDeliveryReward` map at claim time. Alternatively, disallow zeroing/reducing a reward entry while any outstanding, unclaimed, already-delivered commitments still reference it, or provide a governance-gated fallback payout path for entitlements that predate a reward-rate change.

### Proof of Concept
1. Configure `OutboundRequestDeliveryReward[module_id] = 100`.
2. Relayer delivers a hyperbridge-originated `PostRequest` from `module_id` to an EVM destination; `RequestReceipts[commitment]` is written with the relayer's address (per `HandlerV2`/`EvmHost` semantics referenced in `outbound_request.rs`).
3. Call `set_outbound_request_delivery_reward(module_id, 0)` (governance/`RelayerOrigin`), simulating module de-listing.
4. Relayer submits `claim_outbound_request_delivery_reward` with the valid `PostRequest`, a correct state proof of `RequestReceipts[commitment]`, and a correctly-signed `outbound_request_delivery_message`.
5. Observe `Error::<T>::OutboundRequestNoRewardConfigured` at [6](#0-5) 
even though the commitment is present in `RequestCommitments`, is not present in `OutboundRequestsClaimed`, and the delivery/signature verification would otherwise succeed — the reward for this specific delivered commitment can never again be claimed through this call.

//! Outbound consensus delivery rewards.
//!
//! Relayers that deliver mandatory (authority-set rotation) consensus proofs
//! to an EVM destination earn a per-chain `OutboundConsensusDeliveryReward`.
//! The on-chain attribution lives in the destination's
//! `EvmHost._epochs[set_id]` slot, populated by `HandlerV2.handleConsensus`
//! via `EvmHost.recordEpoch(set_id, msg.sender)` the first time a consensus
//! proof brings the new set id on chain. This module proves the slot value
//! against Hyperbridge's stored state commitment for the destination and
//! transfers the configured reward.
