### Title
Deterministic `CachedPreprocess` reuse across signing sessions enables FROST nonce reuse and key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` persists a single 32-byte `CachedPreprocess` seed in the database keyed only by `self.context`, and reconstructs the signing machine from that same seed via `AlgorithmSignMachine::from_cache` on every call — including every call to `share_internal`. Because `from_cache` feeds the seed to `AlgorithmMachine::seeded_preprocess`, the FROST nonces `(d, e)` and the advertised preprocess commitments are fully deterministic for a given `(context, key)` pair. The seed is never rotated or consumed after a signing attempt, so every `share_internal` invocation for the same context reuses identical nonce scalars.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmSignMachine::from_cache` reconstructs nonces deterministically via `seeded_preprocess(cache)` (crypto/frost/src/sign.rs:268-274). In `preprocess_internal`, the seed is loaded from `CachedPreprocesses::get(self.txn, &self.context)`, decrypted, and passed to `from_cache` each time; it is only written once (when absent) and never updated after use (coordinator/src/tributary/signing_protocol.rs:123-147). `share_internal` then calls `preprocess_internal` again and signs a caller-supplied `msg` with peer-supplied preprocesses read via `read_preprocess` (lines 150-168).

The signature share produced in `crypto/frost/src/sign.rs` is `s = d + ρ·e + c·λ·x_i`, where `d, e` are the signer's nonces (deterministic per seed), `ρ` is the binding factor derived from the `rho_transcript` over all participants' preprocesses (crypto/frost/src/sign.rs:361-379, crypto/frost/src/nonce.rs:161-171), `c = hram(R, A, msg)`, and `λ` the Lagrange coefficient for the `included` set. The FROST binding-factor mechanism only defeats nonce-reuse/ROS attacks if each session uses fresh nonces; here the victim's nonces are constant across sessions.

### Impact Explanation
An unprivileged co-signer can initiate repeated `share_internal` rounds for the same context with different preprocess sets / messages / participant sets, collecting multiple shares bound to the same `(d, e)`:

```
s_j = d + ρ_j·e + c_j·λ_j·x_i
```

`ρ_j`, `c_j`, `λ_j` are all publicly derivable. Each additional session adds one equation while the unknowns remain the three scalars `(d, e, x_i)`. After ~3 sessions the attacker solves the linear system and recovers the victim's secret share `x_i`; combined with the attacker's own shares, this can reach threshold and forge signatures — equivalent to stealing funds controlled by the threshold key.

### Likelihood Explanation
The attacker only needs to cause multiple signing rounds under the same `context` (e.g., retries with varying preprocess sets, or any repeated signing for the same key if `context` is a stable per-multisig identifier). All inputs required — preprocess bytes fed to `read_preprocess` and the signed `msg` — are public protocol inputs. The only uncertainty is whether `context` is guaranteed unique per signing session; the code path in `preprocess_internal` provides no consumption/rotation of the seed and no per-attempt entropy, so any context reuse is fatal.

### Recommendation
Do not reuse a `CachedPreprocess` seed across distinct signing attempts. Either:
- derive the effective nonce seed as `H(seed || session_binding)` where `session_binding` commits to the full signing attempt (participants, message digest, attempt index), or
- delete/rotate `CachedPreprocesses` after `share_internal` consumes it, or
- bind the retrieved seed to the hash of the received peer preprocesses before calling `from_cache`, so identical local seeds cannot pair with different `ρ` values.

### Proof of Concept
1. Attacker (a threshold participant) requests a signature under context `C`, supplying preprocess set `P1`, message `m1`. Victim emits share `s1 = d + ρ1·e + c1·λ1·x`.
2. Attacker triggers a second round for the same context with modified preprocess set `P2` (changing `ρ`, `c`, or `λ`), obtaining `s2`.
3. Repeat for `s3`. Solve the 3x3 linear system over the curve field for `(d, e, x)`; `x` is the victim's FROST secret share (`params.secret_share()` used in `sign_share`, crypto/frost/src/algorithm.rs:208-210).
4. With the attacker's own `t-1` shares plus recovered `x`, reconstruct the group secret / produce valid signatures for arbitrary messages.
