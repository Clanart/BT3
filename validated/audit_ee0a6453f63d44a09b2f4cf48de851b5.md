## Analysis Summary

I searched for the specific broken-invariant pattern in the C4 report — a shared/pooled resource that gets consumed by whichever caller commits/acts on it, rather than by the actor who actually created it — and looked for a Desktop analog where user-controlled data (AI output, remote data, deep-link data) ends up applied to the wrong context.

The closest structural analog in this codebase is GitHub Desktop's Copilot conflict-resolution flow, where AI-generated file resolutions are staged as attacker-influenceable content (a malicious repository can craft conflict markers/content that Copilot "resolves") and are later written to disk keyed only by file **path**, not by the specific conflict/operation instance that produced them.

### Title
Stale Copilot conflict resolutions can be written to disk for a different, unrelated Git operation on the same file path - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` writes previously-computed `copilotResolutions` to disk whenever invoked, matching each resolution to a working-directory file purely by `resolution.path`. The resolutions are stored in the repository-wide `multiCommitOperationState` rather than being bound to the specific merge/rebase/cherry-pick operation (or its underlying commit SHAs/branch tips) that produced them.

### Finding Description
`_startCopilotConflictResolution` stores the AI's resolutions into `multiCommitOperationState.copilotResolutions` after calling Copilot: [1](#0-0) 

Later, `_applyCopilotConflictResolutions` reads `copilotResolutions` back out of the same state object and writes each resolution's content to the file at `resolution.path`, gated only by whether that path is *currently* conflicted on disk — not by whether the on-disk conflict is the same conflict instance the resolution was generated for: [2](#0-1) 

The only staleness guard present, `ownsCurrentRun`, protects against a *concurrent* stale async Copilot call clobbering a *newer in-flight* run's controller/progress/result: [3](#0-2)  It does **not** protect against the sequential case where a user backs out of one conflicted operation (merge) and starts a second, unrelated conflicted operation (e.g., a rebase or cherry-pick) that happens to conflict on a file with the same repository-relative path. Nothing in `_applyCopilotConflictResolutions` checks that the stored `copilotResolutions` were computed against the `ourBranch`/`theirBranch`/commit tips of the *currently active* `conflictState`; it only checks `step.kind === ShowCopilotConflicts` to pull manual overrides, and checks that the on-disk file still shows unresolved conflict markers: [4](#0-3) 

This mirrors the C4 finding's broken invariant: a value produced for one specific instance (Bob's proposal fractions / Copilot's resolution of merge-A's conflict) is consumed by a different instance (Alice's buyout / a later, unrelated merge/rebase operation) because the code only tracks the *pooled* resource (all deposited fractions / the stored resolutions), not the resource's binding to the instance that created it.

### Impact Explanation
If stale `copilotResolutions` from an aborted/abandoned conflict resolution flow are not fully cleared before a new conflicted operation begins on the same file path, `_applyCopilotConflictResolutions` can overwrite the working tree with AI-resolved content that does not correspond to the current merge/rebase/cherry-pick's actual conflict, silently corrupting what the user then commits and pushes — exactly the "silent corruption of what the user commits or pushes" impact class called out as valid. Because the underlying content is itself derived from repository data (conflict markers) that an attacker-controlled remote branch can shape, this creates a path for a malicious remote to influence what gets written to the user's disk under a mismatched operation context.

### Likelihood Explanation
This requires the specific sequence: start operation A → get Copilot resolutions → leave the `ShowCopilotConflicts`/result state without it being cleared → start operation B with a conflicting file at the same path → trigger `_applyCopilotConflictResolutions` again. I confirmed the code paths for storing and consuming `copilotResolutions` and the fact that path-matching plus "still has unresolved markers" is the only gate, but I was not able to fully trace every caller that clears `multiCommitOperationState` (e.g., `_endMultiCommitOperation`, abort flows, and the initializers used by merge/rebase/cherry-pick start) within the available search budget to confirm definitively whether `copilotResolutions` is always reset to `null` on every transition between operations. This is the main uncertainty in this analog and would need direct verification of `_endMultiCommitOperation`/`initializeMultiCommitOperationState` call sites in `app-store.ts`.

### Recommendation
Bind `copilotResolutions` (and the manual-override map) to an operation-identifying token — e.g., the multi-commit-operation's own instance/step identity or the conflict's base/target commit SHAs — and validate that token in `_applyCopilotConflictResolutions` before writing any file, rejecting stale resolutions instead of relying solely on path-matching and "still conflicted" checks. Explicitly clear `copilotResolutions`, `copilotResolutionSummary`, and `copilotSkippedFiles` whenever a multi-commit operation is aborted, ended, or reinitialized for a new operation.

### Proof of Concept
Not executable from static analysis alone; a concrete reproduction would require:
1. Start a merge, hit conflicts, and click "Resolve with Copilot" to populate `multiCommitOperationState.copilotResolutions` for file `foo.txt`.
2. Abort/back out of that merge without confirming ("Back to manual" / abort) before the store's `copilotResolutions` field is cleared.
3. Start a second, unrelated operation (rebase/cherry-pick) that also produces a conflict in `foo.txt`.
4. Trigger `_applyCopilotConflictResolutions` (e.g., via "Always use Copilot" auto-continue) and verify whether the resolution content applied belongs to the original merge (step 1) rather than the new operation's conflict.

Given the unresolved uncertainty about whether state-clearing on operation transition already prevents step 3–4, this should be verified in a live Desktop build rather than asserted as fully confirmed from static review alone.

```typescript
  public async _applyCopilotConflictResolutions(
    repository: Repository
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    const { multiCommitOperationState } = state
    if (multiCommitOperationState === null) {
      return
    }

    const { copilotResolutions, step } = multiCommitOperationState
    if (copilotResolutions === null || copilotResolutions.length === 0) {
      return
    }

    // Respect any manual overrides the user chose in the result dialog
    const manualResolutions =
      step.kind === MultiCommitOperationStepKind.ShowCopilotConflicts
        ? step.conflictState.manualResolutions
        : new Map<string, ManualConflictResolution>()

    this.statsStore.increment('copilotConflictResolutionAcceptedCount')
    if (manualResolutions.size > 0) {
      this.statsStore.increment('copilotConflictResolutionWithOverridesCount')
    }

    const pathsToStage: string[] = []

    for (const resolution of copilotResolutions) {
      if (manualResolutions.has(resolution.path)) {
        continue
      }

      // Delete-vs-modify conflicts are resolved by setting a manual
      // resolution (ours/theirs) rather than writing file content.
      // The existing stageManualConflictResolution flow handles the
      // actual git checkout --ours/--theirs and staging at commit time.
      if (resolution.deleteConflictAction !== undefined) {
        const file = state.changesState.workingDirectory.files.find(
          f => f.path === resolution.path
        )
        if (file === undefined) {
          continue
        }
        const deletedSide = getDeletedSideFromStatus(file)
        if (deletedSide === undefined) {
          continue
        }
        // "keep" → choose the non-deleted side, "delete" → choose the deleted side
        const manualChoice =
          resolution.deleteConflictAction === 'keep'
            ? deletedSide === 'ours'
              ? ManualConflictResolution.theirs
              : ManualConflictResolution.ours
            : deletedSide === 'ours'
            ? ManualConflictResolution.ours
            : ManualConflictResolution.theirs
        this._updateManualConflictResolution(
          repository,
          resolution.path,
          manualChoice
        )
        continue
      }

      const absolutePath = await resolveWithin(repository.path, resolution.path)
      if (absolutePath === null) {
        log.warn(
          `Copilot resolution skipped: path outside repository: ${resolution.path}`
        )
        continue
      }

      // If the user resolved this file externally (e.g. in their editor) while
      // the result dialog was open, git status will report it with no remaining
      // conflict markers. Overwriting it with Copilot's stored content would
      // silently clobber their work, so skip it and let their resolution stand.
      // This mirrors how the manual conflicts dialog determines a file is
      // resolved (`hasUnresolvedConflicts`).
      const onDiskFile = state.changesState.workingDirectory.files.find(
        f => f.path === resolution.path
      )
      if (
        onDiskFile !== undefined &&
        isConflictedFileStatus(onDiskFile.status) &&
        !hasUnresolvedConflicts(onDiskFile.status)
      ) {
        continue
      }

      await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
      pathsToStage.push(resolution.path)
```
