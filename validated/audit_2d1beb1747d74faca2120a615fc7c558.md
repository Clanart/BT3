Audit Report

## Title
`BlockIdRepairType::FecSetRoot` response verification lacks exact Merkle-proof-length checking, letting an intermediate double-Merkle-tree node be accepted as a leaf (`fec_set_root`) - ([File: core/src/repair/serve_repair.rs])

## Summary
`ledger/src/shred/merkle_tree.rs`'s double-Merkle-tree hashing has no leaf/intermediate domain separation, and `verify_merkle_proof`/`get_merkle_root` only require that the proof reduces `index` to `0`, not that `proof.len()` matches the real tree depth. `serve_repair.rs`'s `verify_response` enforces this length check for the `ParentAndFecSetCount` branch but omits it for the `FecSetRoot` branch, allowing a responding peer to substitute a genuine intermediate node plus a shortened proof for the actual leaf, causing the requester to accept and propagate a forged `fec_set_merkle_root` as the trust anchor for subsequent `ShredForBlockId` repair requests.

## Finding Description
`join_nodes` hashes parent nodes identically at every tree level with no leaf-vs-intermediate prefix [1](#0-0) , unlike the separate `merkle-tree/src/merkle_tree.rs` implementation, which explicitly documents the need for `LEAF_PREFIX`/`INTERMEDIATE_PREFIX` "to prevent trivial second pre-image attacks" [8](#0-7) . `get_merkle_root`/`verify_merkle_proof` fold the supplied proof against `node`/`index` and only check that the final shifted `index` equals `0`, with no dependency on an expected tree depth [2](#0-1) . Consequently, a shorter proof combined with a coarser starting index that also reduces to `0` after fewer folds reproduces the same root, even when `node` is actually an intermediate hash rather than the true leaf.

Whether this is exploitable depends entirely on the caller enforcing `proof.len()` against the real tree depth. The `ParentAndFecSetCount` branch of `verify_response` does this correctly via `parent_proof.len() != proof_size * SIZE_OF_MERKLE_PROOF_ENTRY` [3](#0-2) . The `FecSetRoot` branch, however, only checks `fec_set_proof.is_empty()` before calling `verify_merkle_proof`, never validating the proof length against the real tree depth [4](#0-3) . This gap exists because the `FecSetRoot` request variant carries no `fec_set_count`/tree-size field the requester could use to compute the expected proof length [5](#0-4) .

The accepted `fec_set_root` is immediately propagated as the trust anchor for per-shred verification: it is queued into `ShredForBlockId` requests [6](#0-5)  and compared directly against each fetched shred's own computed Merkle root in `verify_response` for `ShredRepairType::ShredForBlockId` [7](#0-6) .

## Impact Explanation
This breaks the invariant that a verified `fec_set_root` must correspond exactly to the FEC-set leaf at `fec_set_index` of the block identified by `block_id`. Any peer answering a `BlockIdRepairType::FecSetRoot` request — which by design can be any cluster peer that has observed the block via Turbine, not a privileged or trusted validator — can supply a genuine intermediate node hash of the same double-Merkle tree together with only the upper portion of the corresponding real proof. `verify_response` will incorrectly report success, causing the requester's repair state machine to accept a forged `fec_set_merkle_root` value and fan it out as the expected root for `ShredForBlockId` requests. This is a false-acceptance defect in the repair pipeline's verification logic, matching the "repair"/"false acceptance" category of in-scope impact, though the claim itself notes that full escalation to accepting forged shred *content* additionally requires a leader-signed Merkle root to collide with the forged intermediate hash — a step that was not confirmed as blocked or unblocked by any downstream signature check within the scope of this review.

## Likelihood Explanation
No malicious-validator or privileged-role assumption is required: any unprivileged peer that answers a repair-socket request (repair requests can be sent to and answered by arbitrary cluster peers) can trigger this using data (an intermediate hash) it legitimately possesses from observing the block via Turbine — no preimage search is needed. The `FecSetRoot` request format structurally cannot carry the tree-size information needed to close the gap, unlike the sibling `ParentAndFecSetCount` path, so this is a standing design gap on every `FecSetRoot` exchange rather than a rare edge case.

## Recommendation
- Include the FEC-set-count/tree size in the `FecSetRoot` request (or let the requester derive/bound it from the already-received `ParentAndFecSetCount` response) so `verify_response` can strictly check `fec_set_proof.len() == get_proof_size(tree_size) * SIZE_OF_MERKLE_PROOF_ENTRY`, mirroring the existing `ParentAndFecSetCount` check.
- Add domain separation between leaf and intermediate hashing in `join_nodes`/the leaf-hashing path in `ledger/src/shred/merkle_tree.rs`, analogous to `merkle-tree/src/merkle_tree.rs`'s `LEAF_PREFIX`/`INTERMEDIATE_PREFIX`, so an intermediate node can never be substituted for a leaf regardless of proof length.

## Proof of Concept
1. A validator sends `BlockIdRepairType::FecSetRoot { slot, block_id, fec_set_index }` to peer P.
2. P, having observed the block via Turbine, knows an intermediate hash of the same double-Merkle tree.
3. P replies with `BlockIdRepairResponse::FecSetRoot { fec_set_root: <intermediate_node_hash>, fec_set_proof: <upper-level entries of the real proof> }`.
4. `verify_response` at `core/src/repair/serve_repair.rs:327-353` only checks `fec_set_proof.is_empty()`, not its length against the real tree depth; `verify_merkle_proof` folds the shortened proof and returns `Ok(())` because the coarser starting index also reduces to `0` after fewer shifts.
5. The requester accepts `<intermediate_node_hash>` as the validated `fec_set_merkle_root` and issues `ShredForBlockId` requests using it as the expected per-shred Merkle root (`core/src/repair/block_id_repair_service.rs:634-657`), a value not actually corresponding to the leaf at `fec_set_index`.

pub fn get_merkle_root<'a, I>(index: usize, node: Hash, proof: I) -> Result<Hash, Error>
where
    I: IntoIterator<Item = &'a MerkleProofEntry>,
{
    let (index, root) = proof
        .into_iter()
        .fold((index, node), |(index, node), other| {
            let parent = if index % 2 == 0 {
                join_nodes(node, other)
            } else {
                join_nodes(other, node)
            };
            (index >> 1, parent)
        });
    (index == 0)
        .then_some(root)
        .ok_or(Error::InvalidMerkleProof)
}

/// Given a flattened merkle `proof` for `node` at `index`,
/// verify the proof against merkle root `root`
pub fn verify_merkle_proof(
    node: Hash,
    index: usize,
    proof: &[u8],
    expected_root: Hash,
) -> Result<(), Error> {
    let proof = proof
        .chunks(SIZE_OF_MERKLE_PROOF_ENTRY)
        .map(<&MerkleProofEntry>::try_from)
        .map(|entry| entry.map_err(|_| Error::InvalidMerkleProof))
        .collect::<Result<Vec<_>, Error>>()?;
    let merkle_root = get_merkle_root(index, node, proof)?;

    (merkle_root == expected_root)
        .then_some(())
        .ok_or(Error::InvalidMerkleProof)
}

use {solana_hash::Hash, solana_sha256_hasher::hashv};

// We need to discern between leaf and intermediate nodes to prevent trivial second
// pre-image attacks.
// https://flawed.net.nz/2018/02/21/attacking-merkle-trees-with-a-second-preimage-attack
const LEAF_PREFIX: &[u8] = &[0];
const INTERMEDIATE_PREFIX: &[u8] = &[1];

macro_rules! hash_leaf {
    {$d:ident} => {
        hashv(&[LEAF_PREFIX, $d])
    }
}

macro_rules! hash_intermediate {
    {$l:ident, $r:ident} => {
        hashv(&[INTERMEDIATE_PREFIX, $l.as_ref(), $r.as_ref()])
    }
}
