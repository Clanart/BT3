# Title
Missing destination-chain binding in `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` allows non-membership proofs from an unrelated state machine to falsely settle timeouts for requests actually delivered on the real destination - (File: evm/src/core/HandlerV2.sol)

### Summary
`handlePostRequestTimeouts` and `handleGetRequestTimeouts` verify a non-membership proof of the receipt key against `host.stateMachineCommitment(message.height)`, but never assert that `message.height`'s state machine actually corresponds to `request.dest` (or the response's routed chain). Because a Hyperbridge host tracks commitments for multiple remote state machines simultaneously (`HostParams.stateMachines`), an attacker can pick a genuinely-verified, unrelated state commitment (for a chain that never received the request) and prove "non-membership" of a receipt key that could never exist there — even though the request was actually delivered and processed on the real destination.

### Finding Description
In `handlePostRequestTimeouts`: [1](#0-0) 

The function:
1. Fetches `state = host.stateMachineCommitment(message.height)` — an attacker-supplied `StateMachineHeight{stateMachineId, height}`.
2. Confirms the request is "known" via `host.requestCommitments(requestCommitment)`, which only proves the request was genuinely dispatched from this source host (with a real `dest`).
3. Verifies non-membership of `REQUEST_RECEIPTS_STORAGE_PREFIX || requestCommitment` against `state.stateRoot`.
4. Dispatches the timeout.

Nowhere is `request.dest` checked against `message.height.stateMachineId`. Compare this with the sibling function `handlePostRequests`, which explicitly enforces `leaf.request.dest.equals(host.host())`: [2](#0-1) 

That binding check is present for inbound requests but absent for timeouts. Since `HostParams.stateMachines` allows a single host to accept state commitments from several distinct remote chains, an attacker can:
1. Take a real, still-committed `PostRequest` whose true `dest` is Chain B (already delivered/processed on Chain B, so its receipt exists in Chain B's real trie).
2. Submit `handlePostRequestTimeouts` with `message.height` pointing to a different, legitimately-consensus-verified chain (Chain C) that the host also tracks.
3. Produce a valid non-membership proof against Chain C's `stateRoot` for the same storage key — trivially true, since Chain C's trie never contained anything related to this request.
4. The handler accepts this as proof the request was never processed, even though it actually was processed on the real destination, Chain B.

This directly violates the stated invariant: "timeouts must only succeed when non-membership is proven against the correct receipt key and the message was still pending." The receipt key here is checked against the *wrong* state root — one from a state machine that was never the actual destination.

The same structural issue exists in `handleGetRequestTimeouts`, which shares the identical pattern: [3](#0-2) 

The `request.timeout() > state.timestamp` check is also evaluated against the attacker-chosen chain's clock rather than the real destination's clock, making the timeout-elapsed check equally forgeable.

### Impact Explanation
If exploitable, this allows an attacker to force `host.dispatchTimeOut` to fire for a request that was already legitimately delivered and executed on its true destination. Depending on the source application's `onPostRequestTimeout`/`onGetTimeout` handler semantics (refund, unlock, mint, revert escrow), this can cause double-settlement: funds released once via the destination's real execution and a second time via the falsely-accepted timeout refund on the source chain — a wrongful mint/unlock/refund of protocol- or user-escrowed assets, matching the Critical impact category.

### Likelihood Explanation
Exploitability depends on whether the deployed host configuration actually tracks commitments for more than one remote state machine (`HostParams.stateMachines` being multi-entry) and whether such a state root can be obtained without cooperation from a malicious relayer (an attacker only needs to observe an already-published, legitimately-verified consensus state for any other tracked chain — this does not require a malicious relayer or node, since consensus updates are permissionless and public). I was not able to fully trace `EvmHost.dispatchTimeOut`'s internal logic within the available tool budget to rule out a downstream secondary check tying `request.dest` to the proof's chain id; this should be verified directly in `evm/src/core/EvmHost.sol`.

### Recommendation
In both `handlePostRequestTimeouts` and `handleGetRequestTimeouts`, explicitly assert that `message.height.stateMachineId` (converted via the `StateMachine` library) matches `request.dest` (respectively the response-routing chain) before accepting the non-membership proof, mirroring the `leaf.request.dest.equals(host.host())` check already present in `handlePostRequests`.

### Proof of Concept
Conceptual PoC steps (would need to be executed against a running testnet/foundry deployment with multiple tracked state machines to confirm, since I could not execute code):
1. Deploy/host tracks two remote chains B and C in `HostParams.stateMachines`.
2. Dispatch a real `PostRequest` from source host S with `dest = B`.
3. Have Chain B legitimately deliver and process the request (receipt written into Chain B's trie).
4. Obtain a legitimate, already-verified consensus/state commitment for Chain C at some height where `state.timestamp > request.timeoutTimestamp`.
5. Generate a non-membership proof of `REQUEST_RECEIPTS_STORAGE_PREFIX || hash(request)` against Chain C's `stateRoot` (trivially valid, key never existed there).
6. Call `handlePostRequestTimeouts(host, {timeouts: [request], height: <Chain C height>, proof: <non-membership proof against Chain C>})`.
7. Observe whether `host.dispatchTimeOut` fires and the source-side timeout handler executes, despite Chain B already having processed the request — confirming double-settlement. [4](#0-3)

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
