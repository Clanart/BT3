## Confirmed Analog

The Tron variant of `IntentGatewayV2.sol` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) declares `using SafeERC20 for IERC20;` [1](#0-0)  but its `withdraw()` and `onAccept` `SweepDust` handler never call `safeTransfer`. Instead they use a raw low-level `call` to the ERC20 `transfer` selector and only check that the *call itself* did not revert: [2](#0-1) [3](#0-2) 

Compare this with the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`), which correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` for the equivalent escrow release path [4](#0-3) .

### Title
Tron `IntentGatewayV2.withdraw()`/`SweepDust` accept a boolean-`false` ERC20 `transfer()` as success, silently burning escrowed user funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
This mirrors the referenced report: a function whose surrounding codebase and naming imply a "safe" transfer (the sibling EVM contract uses `SafeERC20.safeTransfer`), but the Tron contract performs an unchecked raw `call` and only inspects whether the *call* reverted — not whether the token's `transfer()` actually returned `true`.

### Finding Description
`withdraw()` is the internal function invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` ISMP request is authenticated [5](#0-4) . It performs the token payout using:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [6](#0-5) 

Many ERC20 tokens (including well-known non-compliant tokens, and TRC20 tokens common on Tron, where this contract is specifically deployed) return `false` on failure instead of reverting. In that case `token.call(...)` succeeds at the EVM/TVM level (`success == true`) even though the underlying transfer never moved funds, because the low-level `call` return-value check only reflects whether the callee reverted — the ABI-decoded `bool` return payload of `transfer()` is never decoded or checked. Despite this failure, `withdraw()` unconditionally:
- decrements `_orders[body.commitment][token] -= amount;` (escrow accounting) [7](#0-6) 
- sets `_filled[body.commitment] = beneficiary;` marking the order permanently settled [8](#0-7) 
- emits `EscrowReleased`/`EscrowRefunded` [9](#0-8) 

The same unchecked pattern exists in the `SweepDust` branch of `onAccept` [10](#0-9) .

### Impact Explanation
Because escrow bookkeeping and the "filled" state are updated as if the transfer succeeded, tokens that return `false` on failure (rather than reverting) get their escrowed balance permanently zeroed and the order marked filled/refunded with no tokens ever reaching the beneficiary. The order can never be retried (the commitment is already marked `_filled`/decremented), so the solver's or user's funds are permanently locked in the gateway with no recovery path — a direct loss-of-funds condition matching the bounty's "stealing or loss of funds" and "false state acceptance" categories.

### Likelihood Explanation
The payout path is triggered by any legitimate, correctly-authenticated cross-chain `RedeemEscrow`/`RefundEscrow` ISMP message — it requires no malicious relayer, prover, or admin. The only condition needed is that the configured fee/output token on the Tron deployment is one of the (commonly encountered on Tron/TRC20 ecosystems) non-compliant tokens that signal failure via a `false` return rather than a revert. This is a realistic, unprivileged-attacker-independent condition tied purely to token behavior, not to any compromised actor.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in both `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;`), consistent with `IntentsBase._withdraw` in the canonical EVM contract, so that both call failure and a `false` return value are treated as failures and revert the state-mutating escrow accounting.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with a token whose `transfer()` returns `false` on failure (e.g., insufficient balance edge case, blacklist, or a non-standard token contract) instead of reverting, and escrow funds for an order using that token via `placeOrder`.
2. Trigger an authenticated `RedeemEscrow`/`RefundEscrow` ISMP request that calls `onAccept` → `withdraw()` for that commitment where the underlying `transfer()` call returns `false` (e.g., token contract intentionally returns false due to an internal condition).
3. Observe: `token.call(...)` returns `success = true` (the call did not revert), so `if (!success) revert TransferFailed();` does not trigger.
4. `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary's token balance never increased, and the escrowed tokens remain permanently stuck in the contract with no way to re-trigger the withdrawal for that commitment.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
