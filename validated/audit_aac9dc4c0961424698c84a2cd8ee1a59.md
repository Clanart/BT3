### Title
Path-containment check in `resolveWithin` uses a boundary-less string prefix comparison, allowing escape from the intended repository root - (`File: app/src/lib/path.ts`)

### Summary
`resolveWithin` (and its `Posix`/`Win32` variants) is the sole guard used to confirm that an attacker/repo-influenced relative path stays inside a trusted root directory before Desktop acts on it (e.g. revealing a file via the OS shell). The final containment test is a bare `String.prototype.startsWith` comparison with no path-separator boundary check, which is the exact same "missing strict boundary" class of bug as the reported `ceilingPrice == floorPrice` issue: a check that looks like a range/containment guard but silently accepts values just outside the intended boundary.

### Finding Description
The guard is: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` treats `realRoot` as a plain string prefix rather than a directory boundary. Because there is no check that the character immediately after `realRoot` in `realResolved` is a path separator (or that the two strings are exactly equal), any real path whose *string* begins with `realRoot` is accepted as "within" the root - even if it is actually a sibling directory. For example, if `realRoot` is `/Users/victim/Documents/GitHub/repo`, then `/Users/victim/Documents/GitHub/repo-secrets/id_rsa` also satisfies `startsWith(realRoot)` even though it is not inside `repo` at all.

The only way to reach a path whose realpath diverges like this from a name that was supposed to stay under the root is through a symlink: the function resolves the untrusted relative path under the root, then calls `realpath()` on the result, which follows symlinks. If a cloned/fetched repository (fully attacker-controlled content) contains a symlink whose target's realpath happens to share `realRoot` as a string prefix without a following separator (a coincidental or attacker-arranged sibling path on the victim's disk), the existing traversal test in `app/test/unit/path-test.ts` (`fails for paths that use a symlink to traverse outside of the root`) does not cover this boundary case - it only tests symlinks resolving to an entirely different (non-prefix) location, so the missing-separator gap is unexercised and unguarded.

`resolveWithin` gates a concrete, remotely triggerable action: opening a repository from a deep link. [2](#0-1) 

```
if (filepath !== null) {
  if (isAbsolute(filepath)) {
    log.error(`Refusing to open absolute path: ${filepath}`)
    return
  }

  const resolved = await resolveWithin(repository.path, filepath)

  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } else {
    log.error(
      `Prevented attempt to open path outside of the repository root: ${filepath}`
    )
  }
}
```

This is invoked from `openRepositoryFromUrl`, which is reachable via the `x-github-client://openRepo/<url>?filepath=<path>` custom protocol handler that any web page/link can trigger (`app/src/lib/parse-app-url.ts`, `app/src/main-process/main.ts`). The attacker fully controls: (1) the repository that gets cloned/opened (`url`), and thus its contents including any symlinks placed inside it, and (2) the `filepath` query parameter that is joined against the repository root and passed through `resolveWithin`.

### Impact Explanation
`resolveWithin`'s only job is to prevent exactly this: letting a value derived from attacker-controlled input (a cloned repo's contents plus a URL-supplied `filepath`) escape the trusted root directory. The `startsWith` check without a separator boundary breaks that invariant, so `shell.showItemInFolder` can be made to reveal/select a filesystem path outside of the cloned repository - a "read outside the repo" primitive matching the specified valid-impact class. It is used as the load-bearing containment guard everywhere in the codebase where path escape must be prevented (`copilot-conflict-context.ts`, `app-store.ts`), so any consumer relying on this boundary is subject to the same weakness.

### Likelihood Explanation
Exploitation requires: (1) the victim clicking an attacker-supplied `x-github-client://openRepo/...` link (the documented, unprompted "Open in Desktop" flow, not local/physical access), and (2) a coincidental or crafted sibling-path relationship on the victim's filesystem between the repository clone directory and another directory/file whose name shares the root's name as a prefix (achievable via a symlink placed inside the attacker's own repository, since realpath of a symlink is fully attacker-directed relative to wherever the symlink points, and Desktop's default clone directory naming is predictable, e.g. `~/Documents/GitHub/<repo-name>`). This makes the bug's likelihood "medium" rather than trivial to weaponize in one click, similar to how the original report's sandwich-attack precondition is not something every attacker can trigger unassisted, but the underlying validation defect is unambiguous and unguarded by any test.

### Recommendation
Replace the bare prefix comparison with a proper boundary-aware check, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests covering sibling directories/symlinks whose realpath shares the root as a string prefix without a following separator (e.g. root `/tmp/repo`, symlink target `/tmp/repo-evil`), to close the exact gap not exercised by the existing `path-test.ts` symlink cases.

### Proof of Concept
1. Victim has (or will have) a GitHub Desktop clone at `~/Documents/GitHub/demo`.
2. Attacker hosts a public repository that Desktop will clone as `~/Documents/GitHub/demo-secret` is not directly controllable, but attacker instead ships a repository containing a symlink `leak -> /Users/victim/Documents/GitHub/demoXYZ` (any real directory outside `demo` whose absolute path begins with the string `.../demo`, e.g. a directory the attacker knows exists via its own `.git` config or a name they got the victim to create) inside the repository named `demo`.
3. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/attacker/demo?filepath=leak`.
4. Desktop clones/opens `attacker/demo` at `~/Documents/GitHub/demo`, then calls `resolveWithin('~/Documents/GitHub/demo', 'leak')`.
5. `realpath` follows the `leak` symlink to `.../demoXYZ`; `realResolved.startsWith(realRoot)` (`'.../demoXYZ'.startsWith('.../demo')`) evaluates `true` despite `demoXYZ` not being inside `demo`.
6. `shell.showItemInFolder(resolved)` reveals/selects a file/folder outside the intended repository root, confirming the containment invariant is broken by the missing separator check.
