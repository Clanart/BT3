### Title
Zero `GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee`, halting the chain - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` when computing the KIP-71 dynamic base fee, but the `kip71.gastarget` governance parameter has no non-zero enforcement, unlike the sibling parameter `kip71.basefeedenominator` which explicitly rejects zero.

### Finding Description
`NextMagmaBlockBaseFee` computes the baseFee delta as `parentBaseFee * gasUsedDelta / gasTarget / baseFeeDenominator` whenever `parentGasUsed != gasTarget`: [2](#0-1) 

The function explicitly guards against a zero `BaseFeeDenominator` ("To avoid panic, set the fluctuation range small") [3](#0-2) , but performs no equivalent guard for `gasTarget`. If `gasTarget == 0`, then any block with `parentGasUsed > 0` takes the "used more gas than target" branch and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [4](#0-3) , which is a `big.Int` division by zero and panics.

The governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, i.e. no validation at all, whereas the neighboring `Kip71BaseFeeDenominator` param explicitly checks `v != 0`: [1](#0-0) 

This is structurally identical to the reported bug class: a governance/config-controlled divisor lacking a minimum-value (non-zero) enforcement, while a sibling value in the same code path (BaseFeeDenominator / xpTiers-vs-other-checks) is properly validated — an inconsistency indicating this was simply missed rather than intentional.

### Impact Explanation
`NextMagmaBlockBaseFee` (and its header-verification counterpart `VerifyMagmaHeader`) is executed by every full node while producing or validating every block header once the Magma hardfork is active [5](#0-4) . If `kip71.gastarget` is governance-voted to `0` (or otherwise reaches state as `0`) and a following block has `GasUsed > 0` (which is virtually guaranteed on any active chain), every node computing or verifying that block's base fee panics simultaneously. Because this occurs in consensus-critical block processing, it forces a chain-wide halt (denial of service across all honest nodes) rather than a localized loss of funds — arguably a stronger analog than the report's "locked tokens," since here it is a hard chain stop with no state (like "cancel game") to recover through.

### Likelihood Explanation
Governance parameters are changed through validator on-chain votes as described by the `kaiax/gov` module and `VoteData`/`VerifyVote` flow [6](#0-5) . Reaching `gastarget = 0` requires either a governing-node/validator vote passing this value (accepted today because `noopFormatChecker` performs no validation) or a misconfigured genesis/hard-fork parameter set. This requires validator/governance-level access rather than an arbitrary unprivileged transaction, which lowers likelihood relative to a fully permissionless trigger, but it is directly reachable through the intended governance parameter-setting mechanism with zero code-level protection, unlike most other numeric KIP-71 parameters.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `v == 0`, consistent with `Kip71BaseFeeDenominator`'s `v != 0` check. Additionally, as defense in depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should apply the same "avoid panic" fallback used for `BaseFeeDenominator` (substitute a safe default) when `gasTarget == 0`.

### Proof of Concept
1. Via governance vote (or a chain configured/hard-forked with `Governance.KIP71.GasTarget = 0`), set `kip71.gastarget` to `0`. The `NewVoteData`/`FormatChecker` pipeline currently accepts this value since `Kip71GasTarget` uses `noopFormatChecker` [7](#0-6) .
2. Once the parameter takes effect (post-Magma hardfork), any subsequent block with nonzero `GasUsed` (essentially any real block) triggers `NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)`.
3. Since `parentGasUsed (>0) != gasTarget (0)` and `parentGasUsed > gasTarget`, execution reaches:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 -> panic: division by zero
``` [4](#0-3) 
4. This function is called both when block producers build a header's `BaseFee` and when other nodes verify it via `VerifyMagmaHeader`, so all nodes processing this block panic, halting the network.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
