### Title
Out-of-range participant index in a PedPoP blame accusation panics the node via unchecked HashMap indexing - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept attacker-influenced `sender`/`recipient` `Participant` indexes and index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` directly, panicking when the index was not part of the DKG — a remotely triggerable denial of service analogous to CVE-2017-18265 (crash on a crafted protocol message).

### Finding Description
`blame_internal` calls `Decryption::decrypt_with_proof(sender, recipient, msg, proof)`. When `proof` is `Some`, `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` to build the DLEq verification generators — a HashMap index on `participant` that was only ever populated for `1 ..= n`. If `recipient` is any `Participant` not registered in the DKG, the indexing panics.

Likewise, if decryption succeeds (or proof is `None` is not reached — see below), `blame_internal` later evaluates `self.commitments[&sender]` in `share_verification_statements`, panicking on an unregistered `sender`.

`Participant::new` accepts any `u16` in `1 ..= u16::MAX`, so a blame/accusation flow keyed by a participant index outside `1 ..= n` is well-formed input but crashes the process instead of returning `PedPoPError`/`DecryptionError`.

Relevant code:

- `crypto/dkg/pedpop/src/encryption.rs` (~line 388): `&[self.enc_keys[&decryptor], *proof.key]` inside `decrypt_with_proof`.
- `crypto/dkg/pedpop/src/lib.rs` (~line 599): `&self.commitments[&sender]` inside `blame_internal`.
- `crypto/dkg/pedpop/src/lib.rs` (~lines 623–631, 674–682): public `blame` entry points taking caller/accusation-supplied `sender`/`recipient`.

### Impact Explanation
A single crafted blame accusation naming a participant index not in the DKG set (e.g., `Participant(n + 1)`) with any `EncryptionKeyProof` crashes the processor evaluating the blame. A crashed validator stops signing batches/transactions, halting liveness of the multisig for its operator. This mirrors the reported bug class: a remote peer sends a malformed-but-parseable protocol message that hits an unchecked code path and aborts the application.

### Likelihood Explanation
The blame flow is specifically designed to process accusations about other parties, so the `sender`/`recipient` indexes are exactly the parts of the message an accuser controls. No cryptographic validity is required to reach the panic: `decrypt_with_proof` hits `enc_keys[&decryptor]` before verifying the proof (the `msg.pop` check can be satisfied trivially since the accuser chooses `msg` and can sign a valid PoP with their own ephemeral key). Any participant — or anyone able to route a blame request naming an invalid index — triggers it. Uncertainty: whether the calling processor sanitizes `sender`/`recipient` against the validator set before invoking `blame`; within the in-scope crates themselves, no bounds check exists, and `AdditionalBlameMachine::new`'s own doc notes usage "may cause ... panics," indicating the API does not defend itself.

### Recommendation
Replace unchecked indexing with lookups that return errors:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  return Err(DecryptionError::InvalidProof); // or a dedicated OutOfRangeParticipant error
};
let Some(commitments) = self.commitments.get(&sender) else {
  return PedPoPError::MissingParticipant(sender) / dedicated error
};
```

Validate at the `blame`/`blame_internal` entry that `sender` and `recipient` are members of `1 ..= n` before touching the maps.

### Proof of Concept
```rust
// After a DKG completes for params n = 2, t = 2:
// `blame_machine` is an AdditionalBlameMachine built via
// AdditionalBlameMachine::new(context, n, commitment_msgs).

let out_of_range = Participant::new(3).unwrap(); // n = 2

// Craft any EncryptedMessage with a self-consistent PoP, plus any EncryptionKeyProof
// (contents never verified before the panic).
let msg: EncryptedMessage<C, SecretShare<C::F>> = /* arbitrary, well-formed */;
let proof: EncryptionKeyProof<C> = /* arbitrary bytes */;

// Panics inside Decryption::decrypt_with_proof at `self.enc_keys[&decryptor]`
// because `out_of_range` was never registered.
let _ = blame_machine.blame(Participant::new(1).unwrap(), out_of_range, msg, Some(proof));
```

Equivalently, a valid `recipient` plus a `sender` outside `1 ..= n` panics later at `self.commitments[&sender]` once decryption succeeds.
