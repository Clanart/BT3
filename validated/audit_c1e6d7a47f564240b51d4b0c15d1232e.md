Confirmed: the memo written by `create_update_state_spend()` is `[launcher_id, root_hash, new_puz_hash]`, where `new_puz_hash` is the **inner** puzzle hash (line 410-413, 518-524), not the full singleton puzzle hash. That value is only carried as CREATE_COIN hint data, and the honest wallet's own `next_full_puz_hash` (which becomes the real created coin's puzzle hash) is separately computed by hashing `create_host_fullpuz(new_puz_hash, root_hash, launcher_id)`. On the receiving side, `singleton_removed()` (`chia/data_layer/data_layer_wallet.py:802-871`) takes the **actual** on-chain `full_puzzle_hash` from `condition[1]` (the real CREATE_COIN destination, trustworthy) but takes `root` and `inner_puzzle_hash` straight out of the unauthenticated memo field `condition[3]` and stores a `LineageProof` built by re-hashing `create_host_layer_puzzle(inner_puzzle_hash, root)` — **without ever checking that this recomputed hash equals `full_puzzle_hash`**.

### Title
DataLayer wallet trusts unauthenticated CREATE_COIN memo to reconstruct singleton lineage/root without verifying it against the actual committed puzzle hash - (File: chia/data_layer/data_layer_wallet.py)

### Summary
`DataLayerWallet.singleton_removed()` derives the new `SingletonRecord` (root, inner puzzle hash, and lineage proof) from the CREATE_COIN condition's memo list rather than from data that is cryptographically bound to the coin actually created on-chain, and never cross-checks the reconstructed puzzle hash against the real `full_puzzle_hash` taken from the same condition.

### Finding Description
When a DL singleton is spent, `singleton_removed()` reads the CREATE_COIN condition's target puzzle hash (`condition[1]`, real/consensus-committed) as `full_puzzle_hash`, and separately reads `condition[3][1]` and `condition[3][2]` as `root` and `inner_puzzle_hash` (the memo/hint fields): [1](#0-0) 

It then builds the new coin and its `SingletonRecord`/`LineageProof` using those memo-derived `root`/`inner_puzzle_hash` values, recomputing a tree hash rather than validating it equals `full_puzzle_hash`: [2](#0-1) 

Memos attached to a `CREATE_COIN` condition are not enforced by CLVM/consensus to match the actual puzzle of the created coin — they are hint data only, as documented for other wallets (e.g. NFT/DID hint handling elsewhere in the codebase). The legitimate root-publish path (`create_update_state_spend()`) does compute `next_full_puz_hash` independently of the memo it writes: [3](#0-2) [4](#0-3) 

but the receiving side never performs the equivalent check (`create_host_layer_puzzle(inner_puzzle_hash, root).get_tree_hash_precalc(...) == full_puzzle_hash`) before persisting the record. This is structurally the same bug class as GHSA-35g4-qx3c-vjhx: a downstream consumer trusts an attacker-suppliable "next state" pointer (there: `m.room.create`'s claimed predecessor; here: the CREATE_COIN memo's claimed root/inner-puzzle-hash) instead of verifying it against the actual committed/consensus state (there: the tombstoned room's real events; here: the coin's real puzzle hash).

By contrast, `dl_verify_proof_internal()` in `chia/data_layer/data_layer_util.py:880-896` does perform this exact check correctly — reconstructing the expected puzzle hash from the claimed `inner_puzzle_hash`/root and comparing it against the coin's actual on-chain `puzzle_hash` — showing that the project treats this comparison as a required invariant elsewhere but omits it in `singleton_removed()`.

### Impact Explanation
Any DataLayer singleton owner (or anyone able to construct a spend of that singleton, e.g. via mempool submission with a crafted memo) can cause every observing wallet (subscribers tracking that `launcher_id`, offer counterparties, or the local DataLayer service via `dl_latest_singleton`) to record a `root` value that does not correspond to the actual puzzle hash committed on-chain for that singleton coin. Because `DataLayerRpcApi`/`DataLayer.get_root()` and offer/proof construction paths read `SingletonRecord.root` as if it were chain-authoritative "current_root" (see `.cursor/context/data-layer.md`), this can mislead Data Layer clients about what root is actually current for a store, corrupt locally-derived `LineageProof`s used to build the wallet's next spend (breaking future updates/self-DoS for the legitimate owner), and desynchronize wallet-tracked singleton history from the real on-chain lineage.

### Likelihood Explanation
Reachable by an unprivileged single spend: any wallet that controls (or can influence via a shared/careless spend) a DL singleton's solution can put an inconsistent memo in the CREATE_COIN condition while letting the real destination puzzle hash be whatever the singleton actually computes. No special network position or malicious peer/node capability is required — a single crafted spend bundle triggers the flawed reconstruction in every syncing wallet's `singleton_removed()`.

### Recommendation
In `singleton_removed()`, after parsing `root`/`inner_puzzle_hash`/`full_puzzle_hash` from the spend's conditions, recompute `create_host_layer_puzzle(inner_puzzle_hash, root).get_tree_hash_precalc(inner_puzzle_hash)` (equivalently `create_host_fullpuz(...)`) and reject/ignore the update (log and return without persisting a `SingletonRecord`) unless it equals `full_puzzle_hash`, mirroring the check already performed in `dl_verify_proof_internal()`.

### Proof of Concept
1. Attacker controls (or is) the owner of a DL singleton with `launcher_id L`, current root `R0`.
2. Attacker crafts a spend of the singleton coin whose inner puzzle legitimately creates a child coin with real puzzle hash `full_puzzle_hash = create_host_fullpuz(IPH_real, R_real, L).get_tree_hash()` (a valid state transition to some real root `R_real`), but supplies a CREATE_COIN memo `[L, R_fake, IPH_fake]` with an arbitrary, unrelated `R_fake`/`IPH_fake`.
3. Broadcast the spend bundle; it is accepted by consensus because CLVM does not validate memo contents against the puzzle hash.
4. Every wallet tracking `L` (subscribers, DataLayer service via `dl_latest_singleton`, offer counterparties) calls `singleton_removed()`, which stores a `SingletonRecord` with `root = R_fake` and a `LineageProof.inner_puzzle_hash` computed from `(IPH_fake, R_fake)` — inconsistent with the real coin's `full_puzzle_hash`.
5. Downstream consumers relying on `SingletonRecord.root` (RPC `dl_latest_singleton`, offer summaries, `DataLayer.get_root()`/`get_sync_status()`) now report an incorrect current root for store `L`, and any subsequent spend the legitimate owner builds using this corrupted lineage/record may fail or diverge from the actual chain state.
