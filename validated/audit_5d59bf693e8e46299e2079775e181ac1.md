Only `map-set` writes exist for `last-update` (2 matches, both inside `price-resolve` itself) — there is no `map-delete` or admin/DAO function anywhere in the codebase that can reset an entry in this map. Once a bad timestamp is written, it can never be cleared.

### Title
Missing future-timestamp bound in `oracle-timestamp-fresh` lets a single price update permanently freeze that asset's oracle path - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`oracle-timestamp-fresh` is supposed to gate price freshness and enforce a monotonically increasing per-feed timestamp, but its staleness computation silently treats *any* future-dated `ts` as `delta = 0`, so the "not too stale" check can never reject a timestamp that is ahead of `stacks-block-time`. Once such a timestamp is accepted, it is written into the `last-update` map as the new floor for the monotonic check, and since the map has no reset/delete path anywhere in the codebase, every subsequent legitimate (block-time-bound) price update for that asset fails `(>= ts prev)` forever, permanently reverting price resolution — and every market operation that needs that asset's price — with `ERR-ORACLE-INVARIANT`.

### Finding Description
`oracle-timestamp-fresh` is defined as: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When `ts > stacks-block-time` (a future-dated timestamp), `delta` is forced to `u0`, so `(<= delta max-staleness)` is trivially true regardless of how far in the future `ts` is. There is no symmetric upper-bound check. This is called from `price-resolve`: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

If a price update for a feed is ever accepted with an anomalously large `timestamp` (e.g., a relayer submits a valid-but-far-future-dated VAA, or any mis-set/corrupted `publish-time`), `map-set last-update key timestamp` permanently raises the floor `prev` for that `{type, ident}` key. From that point forward, any real update — whose `publish-time` is necessarily bounded by actual wall-clock/block time — will always satisfy `ts < prev`, failing `(>= ts prev)` and reverting with `ERR-ORACLE-INVARIANT` on every call, forever. There is no DAO/admin function in the codebase (`v0-4-market.clar`, `v0-1-data.clar`, etc.) that writes to or clears the `last-update` map, so this state cannot be repaired once corrupted — matching the "Denial of Settlement" bug class described in the external report (a stored counter/marker pushed to an unreachable value with no recovery path).

This is analogous to the reported bug's root cause pattern: a value is written once to an extreme/unreachable state (there: `observationsDone = type(uint16).max`; here: `last-update = <huge future timestamp>`), and every future legitimate state transition that depends on incrementing/comparing against that value reverts permanently, freezing the vault/market.

### Impact Explanation
Every market function that needs to value the affected asset — `borrow`, `collateral-add`/`collateral-remove`, `liquidate`, and the notional/health-check evaluation path (`price-multi-resolve` → `get-notional-evaluation`) — calls `price-resolve` for that asset's oracle config and would begin reverting with `ERR-ORACLE-INVARIANT` on every call once the feed's `last-update` is poisoned: [3](#0-2) 

Since no repair path exists, this results in permanent freezing of user funds (collateral and debt positions) denominated in or backed by the affected asset — users can no longer add/remove collateral, borrow, repay, or be liquidated against that asset, and the DAO has no on-chain mechanism to unfreeze it. This lands squarely on the in-scope **Critical — permanent freezing of funds** impact class.

### Likelihood Explanation
The trigger condition (a single accepted update whose `publish-time`/timestamp is ahead of `stacks-block-time`) requires an anomalous or malicious price update to be relayed and accepted; `write-feeds`/price-feed submission is callable by any user as part of normal market operations, so the attack surface is broad, but reliably forging a far-future, cryptographically valid Pyth timestamp is constrained by the oracle infrastructure. Likelihood is therefore moderate: it depends on either a misbehaving/compromised relay, clock skew abuse, or a bug in the decoder/storage layer letting an out-of-bounds `publish-time` through — but the root defect (missing upper bound in `oracle-timestamp-fresh`) is unambiguously present in Zest's own code path, independent of any specific third-party data content.

### Recommendation
Add an explicit upper bound to `oracle-timestamp-fresh` so timestamps that are further in the future than an acceptable clock-skew tolerance are rejected rather than silently passing with `delta = 0`, e.g.:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   (- ts stacks-block-time)   ;; measure future drift too
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```
Additionally, provide a DAO-governed recovery function to reset/override a poisoned `last-update` entry so a single bad timestamp cannot permanently and irreversibly disable price resolution for an asset.

### Proof of Concept
1. A relayer/user submits (via any market entrypoint accepting `price-feeds`) a Pyth update for feed `F` whose `publish-time` is set far in the future relative to `stacks-block-time` (e.g., due to clock skew, malformed data, or a compromised/misbehaving data source that Zest's decoder/storage layer does not reject on the upper bound).
2. `price-resolve` calls `oracle-timestamp-fresh(future_ts, last-update-time, max-staleness)`; because `future_ts > stacks-block-time`, `delta` is forced to `u0`, so the staleness check passes trivially, and `future_ts >= last-update-time` also holds (it's a new high value), so the whole check passes.
3. `map-set last-update {type, ident} future_ts` permanently stores this value as the new floor.
4. All subsequent legitimate updates for feed `F` have real, block-time-bound `publish-time` values, so `ts < future_ts` always, and `(>= ts prev)` always fails → `price-resolve` always returns `ERR-ORACLE-INVARIANT`.
5. `borrow`, `collateral-add`, `collateral-remove`, and `liquidate` for any asset priced via feed `F` (or any position requiring valuation of that asset for health checks) now permanently revert, freezing the affected funds with no on-chain recovery mechanism.
