### Title
Instruction-account serialization work is performed before the VM-startup compute check, letting depleted-budget instructions get free CPU work - ([File: program-runtime/src/vm.rs])

### Summary
`vm.rs::execute()` calls `serialize_parameters()` — which copies every instruction account's data into a freshly allocated VM memory buffer, an operation whose cost scales with the total size of the accounts attached to the instruction — *before* the only compute check related to spinning up the VM (the heap-cost `consume_checked` inside the `create_vm!` macro) is evaluated. This mirrors the seda-wasm-vm bug: expensive setup work (ELF/VM/memory-region bring-up) runs unconditionally, and the gas check that could have prevented it only happens afterward.

### Finding Description
In `program-runtime/src/vm.rs::execute()`: [1](#0-0) 

`serialize_parameters()` builds the full set of memory regions and copies each instruction account's data into an `AlignedMemory` buffer. This work is done unconditionally, with no compute-meter check beforehand.

Only afterward, inside the `create_vm!` macro, is any compute check performed, and it only covers the fixed heap-size cost, not the size of the data that was just copied: [2](#0-1) 

The actual `execute` call flow confirms the ordering: `serialize_parameters` → `set_memory_context` → `create_vm!` (which is where `compute_meter.consume_checked(heap_cost)` finally happens): [3](#0-2) 

The compute meter itself is a simple saturating counter (`ComputeMeter::consume_checked`) that has no knowledge of, and is never pre-charged for, the cost of the account-data copy that `serialize_parameters` performs: [4](#0-3) 

Crucially, the "loaded accounts data size" limit — the mechanism that is supposed to bound how much account data a transaction may pull in — is enforced purely as a **byte-count cap** during account loading, independent of and never deducted from the `ComputeMeter` that gates instruction execution: [5](#0-4) 

The compute-unit-equivalent cost for loaded-accounts-data-size (`calculate_loaded_accounts_data_size_cost`) is computed only for the cost-model / block-cost-limit / scheduler accounting path, not applied to the runtime `ComputeMeter` that `create_vm!` and other builtin dispatchers check: [6](#0-5) [7](#0-6) 

So, unlike builtin instructions (which pre-charge a fixed CU cost before doing any work, e.g. `declare_process_instruction!`): [8](#0-7) 

...and unlike CPI dispatch (which charges the flat `invoke_units` cost before doing any translation work): [9](#0-8) 

...BPF program invocation via `vm.rs::execute()` performs the size-proportional `serialize_parameters` memcpy with **no size-proportional gas charge whatsoever**, and the one compute check that does exist (heap cost) is both fixed-size and placed after the copy.

The corrupted invariant: "no compute-meter-gated, size-proportional work should be performed before the corresponding compute is charged" is violated for the instruction-parameter serialization step of every BPF program invocation.

### Impact Explanation
An attacker can construct a single transaction that:
1. Attaches large accounts (up to the transaction's `loaded_accounts_data_size_limit`, itself only bounded by a byte-count cap unrelated to the compute meter) to a final instruction that invokes a BPF program.
2. Arranges for earlier instructions in the same transaction (or nested CPIs) to consume nearly all of `compute_unit_limit`, leaving the compute meter with only a handful of units remaining by the time the final instruction is dispatched.

When that final instruction is dispatched, `execute()` unconditionally performs the full `serialize_parameters()` memcpy over all attached account data before the heap-cost check in `create_vm!` fires and aborts with `ComputationalBudgetExceeded`. The validator pays real CPU/memory-copy cost that is not gated by, or refunded against, the transaction's already-exhausted compute budget. Because this cost scales with account data size (bounded only by the loaded-accounts-data-size cap, not by remaining CU), an attacker can cheaply (in terms of paid compute) force the leader/validator to repeatedly perform large memory copies across many transactions, resulting in non-RPC-remote CPU exhaustion / chain slowdown — the same class of impact described in the seed report.

### Likelihood Explanation
The path is reachable by any unprivileged user submitting an ordinary transaction; it requires no malicious peer, validator, or trusted plugin — only ordinary transaction construction (multiple instructions/CPIs to deplete the compute meter, plus large account attachments on the final instruction). No feature gate disables this ordering, and the code path is on the hot BPF-loader invocation route used by essentially all transactions.

### Recommendation
Charge (or at least bound-check) the compute cost associated with the size of the data that `serialize_parameters()` will copy — proportional to `account_lengths`/instruction data size — via `invoke_context.compute_meter.consume_checked(...)` before calling `serialize_parameters()` in `program-runtime/src/vm.rs::execute()`, mirroring the pattern already used for CPI (`invoke_units` charged before `translate_instruction`/`translate_accounts`) and for builtins (`declare_process_instruction!` charging CU before running instruction logic). At minimum, verify that the remaining compute meter can cover the eventual heap-cost check before performing the account serialization.

### Proof of Concept
Conceptual PoC (not run, derived from code inspection):
1. Build a transaction with `ComputeBudgetInstruction::set_compute_unit_limit` set just high enough to cover several cheap instructions plus a token remainder.
2. Include N cheap instructions (e.g., no-op/system transfers) engineered to consume almost all of the requested compute budget, leaving remaining compute below the `create_vm!` heap-cost threshold (`invoke_context.get_compute_budget().heap_size` heap cost, computed via `calculate_heap_cost`).
3. As the final instruction, invoke a BPF program with several accounts attached whose combined data size approaches the transaction's `loaded_accounts_data_size_limit` (bounded only by `svm/src/account_loader.rs::LoadedTransactionDataSize`, not by compute units).
4. Observe that `vm.rs::execute()` performs the full `serialize_parameters()` copy over all that account data, and only then fails with `InstructionError::ComputationalBudgetExceeded` from the `create_vm!` heap-cost check — i.e., the expensive copy happened despite the instruction being guaranteed (by prior compute exhaustion) to fail on VM startup.

Note: I was not able to fully verify runtime-level guards (e.g., whether `process_message`/`transaction_processor.rs` performs any additional pre-check that would short-circuit this before `execute()` is reached) due to index size limits on some files; a Devin session with full repository access would be needed to trace `svm/src/transaction_processor.rs` and `runtime/src/bank.rs` exhaustively to rule out an additional upstream guard.

macro_rules! create_vm {
    ($vm:ident, $program:expr, $invoke_context:expr $(,)?) => {
        let invoke_context = &*$invoke_context;
        let stack_size = $program.get_config().stack_size();
        let heap_size = invoke_context.get_compute_budget().heap_size;
        let heap_cost_result =
            invoke_context
                .compute_meter
                .consume_checked($crate::__private::calculate_heap_cost(
                    heap_size,
                    invoke_context.get_execution_cost().heap_cost,
                ));
        let $vm = heap_cost_result.and_then(|_| {
            let (mut stack, mut heap) = $crate::__private::MEMORY_POOL
                .with_borrow_mut(|pool| (pool.get_stack(stack_size), pool.get_heap(heap_size)));
            let vm = $crate::__private::create_vm(
                $program,
                $invoke_context,
                stack
                    .as_slice_mut()
                    .get_mut(..stack_size)
                    .expect("invalid stack size"),
                heap.as_slice_mut()
                    .get_mut(..heap_size as usize)
                    .expect("invalid heap size"),
            );
            vm.map(|vm| (vm, stack, heap))
        });
    };
}

pub struct ComputeMeter(Cell<u64>);

impl ComputeMeter {
    /// Consume compute units
    pub fn consume_checked(&self, amount: u64) -> Result<(), Box<dyn std::error::Error>> {
        let compute_meter = self.0.get();
        let exceeded = compute_meter < amount;
        self.0.set(compute_meter.saturating_sub(amount));
        if exceeded {
            return Err(Box::new(InstructionError::ComputationalBudgetExceeded));
        }
        Ok(())
    }

    fn increase_calculated_data_size(
        &mut self,
        data_size_delta: usize,
        error_metrics: &mut TransactionErrorMetrics,
    ) -> Result<()> {
        // this branch is unreachable in practice (though not by construction),
        // since it would imply an account >4gb in size
        let Ok(data_size_delta) = u32::try_from(data_size_delta) else {
            self.loaded_accounts_data_size = u32::MAX;
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            return Err(TransactionError::MaxLoadedAccountsDataSizeExceeded);
        };

        self.loaded_accounts_data_size = self
            .loaded_accounts_data_size
            .saturating_add(data_size_delta);

        if self.loaded_accounts_data_size > self.requested_loaded_accounts_data_size_limit {
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)
        } else {
            Ok(())
        }
    }
