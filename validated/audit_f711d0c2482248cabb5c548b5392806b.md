This confirms the mechanism precisely: the withdrawal input UTXO is a user-owned dust UTXO (their withdrawal registration key on Bitcoin, `core/src/test/common/setup_utils.rs:480-497`) that the user signs with `TapSighashType::SinglePlusAnyoneCanPay` — a sighash type that, by design, covers only input[0] and output[0] and explicitly permits `ANYONECANPAY` (arbitrary additional inputs/funders) to be added by whoever assembles the final transaction [1](#0-0) . The `create_payout_txhandler` builds output[0] (payment to user), output[1] (anchor) and output[2] (`OP_RETURN` containing the caller-supplied `operator_xonly_pk`) — none of these beyond output[0] are covered by the user's signature, and the `operator_xonly_pk` embedded in the `OP_RETURN` is fully unauthenticated, chosen unilaterally by whoever constructs and broadcasts the transaction [2](#0-1) .

Downstream, verifiers attribute the entire payout — and thus reimbursement eligibility — purely from that unauthenticated `OP_RETURN` field: `update_finalized_payouts` parses the `OP_RETURN` xonly pubkey directly out of the on-chain transaction and stores it as `payout_payer_operator_xonly_pk` with no cryptographic binding to whoever actually funded the extra input(s) [3](#0-2) . That stored pubkey then drives `get_first_unhandled_payout_by_operator_xonly_pk`, feeding `PayoutCheckerTask` to assign that specific operator the kickoff/reimbursement flow [4](#0-3) , and `validate_payer_is_operator`/`send_asserts` only check that the DB-recorded payer matches the operator's own key — they never verify the operator actually supplied the funding input [5](#0-4) [6](#0-5) .

This satisfies exactly the analog pattern called out in your rules ("the operator credited versus the party that paid"). Because `SinglePlusAnyoneCanPay` intentionally leaves the funding input and the `OP_RETURN` uncommitted, any unprivileged party who obtains a user's off-chain-shared payout signature (a normal part of the protocol's withdrawal flow, not a privileged secret) can independently fund and broadcast the payout transaction directly to Bitcoin — bypassing the operator's gRPC entirely — while stamping an arbitrary victim operator's `xonly_pk` into the `OP_RETURN`. The verifier set will then durably attribute that payout, and the associated `bridge_amount` vault reimbursement, to the victim operator who never fronted anything.

### Title
Unauthenticated `OP_RETURN` operator attribution in `payout_tx` lets anyone misattribute a fronted withdrawal to an operator who never paid it - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The payout transaction's `OP_RETURN` output, which records which operator is credited for fronting a withdrawal, is not covered by the user's `SinglePlusAnyoneCanPay` signature and is not signed by the claimed operator at all. Any party holding the user's off-chain payout signature can construct and broadcast the payout tx with their own funding input while attributing the payout to an arbitrary operator's `xonly_pk`, causing that operator to be credited for (and later reimbursed on) a withdrawal it never fronted.

### Finding Description
`create_payout_txhandler` builds the payout tx with the caller-supplied `operator_xonly_pk` embedded in an `OP_RETURN` output, and applies the user's signature only to input[0]/output[0] via `set_p2tr_key_spend_witness` [2](#0-1) . The required sighash type is enforced to be `SinglePlusAnyoneCanPay`, which by Bitcoin's taproot sighash semantics commits only to the single input/output pair at the same index and explicitly allows `ANYONECANPAY` (additional inputs added by any party) [1](#0-0) . Consequently the `OP_RETURN` output (index 2) and the identity of whoever funds the transaction are entirely outside the user's signature's commitment.

`update_finalized_payouts` reads this `OP_RETURN` field directly from the confirmed Bitcoin transaction and persists it as the authoritative "payer operator" for the withdrawal, with no further cryptographic check that the named operator actually supplied the value [3](#0-2) . `is_kickoff_malicious` and `send_asserts`/`validate_payer_is_operator` only compare the DB-recorded payer key against the current operator's own key or the kickoff's claimed operator — they never verify that the same key actually put up the Bitcoin value [7](#0-6) [6](#0-5) .

This breaks the intended bridge-custody binding: `payer who funded the withdrawal == operator credited/reimbursed for the withdrawal`. Before the attack, that equality holds by protocol design (operator calls `withdraw`/`InternalWithdraw`, verifies the signature itself, and funds the tx with its own wallet via `fund_raw_transaction`, per `core/src/operator.rs:620-674`). After the attack, the party that funded the payout (attacker) and the party credited/reimbursed (victim operator) diverge.

### Impact Explanation
This matches the Critical impact category "an operator reimbursed for a payout it never funded." The victim operator becomes obligated to run (or is automatically enrolled by `PayoutCheckerTask`/`get_first_unhandled_payout_by_operator_xonly_pk`, `core/src/task/payout_checker.rs:39-60`) the kickoff/reimbursement flow for a payout it did not make, ultimately claiming `bridge_amount` from the move-to-vault UTXO via `create_reimburse_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:341-385`) for value it never fronted — a direct, unauthorized transfer of vault funds attributed to a party outside the actual payer/reimbursement equality.

### Likelihood Explanation
The only prerequisite is possession of the user's off-chain `SinglePlusAnyoneCanPay`-signed withdrawal message and knowledge of a target operator's public `xonly_pk` (operators' keys are public protocol parameters). No verifier, operator, or watchtower privilege is required — any party who can observe or receive this signature (which is passed over gRPC to `Withdraw`/`InternalWithdraw`, and is inherently meant to be shared off-chain with whichever operator services it) can broadcast a rival transaction directly to the Bitcoin network before/instead of the honest operator, since `ANYONECANPAY` inputs and the `OP_RETURN` are entirely unconstrained by the user's signature.

### Recommendation
Bind the `OP_RETURN` operator attribution cryptographically to the actual funding party, e.g., by requiring the operator to also sign (or contribute a signature covering) the `OP_RETURN` output and the funding input(s), or by using a sighash type that commits to all outputs (`All` instead of `Single`) so an operator's own signature is required over the complete payout transaction including the attribution field, preventing any third party from rewriting who is credited as payer.

### Proof of Concept
1. User creates a withdrawal request and produces a `SinglePlusAnyoneCanPay` signature over `(input_outpoint, output_script_pubkey, output_amount)` per `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-203`), then submits it (e.g., via `Withdraw`/`InternalWithdraw` gRPC, intended for a specific operator).
2. Attacker Eve, who obtains this signature (e.g. by observing the gRPC call, or running her own client pretending to relay to an operator), independently constructs the payout transaction using `create_payout_txhandler`-equivalent logic: input[0] = the same user dust UTXO with the user's signature, output[0] = the same user payout output, but sets the `OP_RETURN` `operator_xonly_pk` to a targeted honest Operator O's public key instead of her own.
3. Eve funds the transaction with her own additional Bitcoin input(s) (permitted because sighash is `ANYONECANPAY`) to cover `output[0]`'s value, and broadcasts it directly to the Bitcoin network — bypassing Operator O's and Eve's own gRPC service entirely.
4. Once confirmed, `update_finalized_payouts` parses the `OP_RETURN`, recording Operator O as `payout_payer_operator_xonly_pk` for this withdrawal (`core/src/verifier.rs:2312-2350`).
5. `PayoutCheckerTask` for Operator O (`core/src/task/payout_checker.rs:39-60`) picks up this "unhandled payout" attributed to O and drives O through the kickoff/reimbursement flow, ultimately entitling O to claim `bridge_amount` from the deposit's move-to-vault UTXO via the `Reimburse` transaction — funds O never fronted.
