## Title
Unrestricted, repeatable `updateEndRemainingAllocation()` breaks the fixed-denominator invariant, letting any unprivileged caller re-snapshot `totalEndRemainingAllocation` mid-stream to redistribute/overpay `totalBonus` - (File: `rewards/Airdrop.sol`)

### Title
Unrestricted `updateEndRemainingAllocation()` allows re-snapshotting the bonus denominator, enabling overpayment of `totalBonus` and unfair bonus redistribution among claimers - (File: `rewards/Airdrop.sol`)

### Summary
`Airdrop.claim()` only calls `updateEndRemainingAllocation()` internally when `totalEndRemainingAllocation == 0` [1](#0-0)  , but `updateEndRemainingAllocation()` itself is `public`, unguarded by any "already set" check, and can be called by anyone at any time after `periodsEndTime[4]` [2](#0-1) . Since `totalRemainingAllocation` strictly decreases as users `claim()` [3](#0-2) , any unprivileged actor can re-invoke `updateEndRemainingAllocation()` between two legitimate claims to shrink the denominator used in `getBonusAmount()`, breaking the intended one-time, fixed snapshot and causing bonus payouts to no longer sum to `totalBonus`.

### Finding Description
`getBonusAmount()` computes `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation`, and this is only meaningful as a fair pro-rata split if `totalEndRemainingAllocation` is fixed once (at the moment `periodsEndTime[4]` is reached) to the sum of all allocations still outstanding at that instant [4](#0-3) . The `claim()` function's guard `if (totalEndRemainingAllocation == 0)` is intended to perform that one-time initialization lazily on the first post-period-4 claim [1](#0-0) .

However, `updateEndRemainingAllocation()` has no such guard - it unconditionally overwrites `totalEndRemainingAllocation = totalRemainingAllocation` whenever `block.timestamp >= periodsEndTime[4]`, and is callable by anyone with zero preconditions (no allocation, no role) [2](#0-1) . Because `totalRemainingAllocation` is only ever decremented (in `claim()`, `register()` is only usable pre-start) [5](#0-4) [6](#0-5) , each subsequent unprivileged call to `updateEndRemainingAllocation()` can only ratchet the denominator downward as more users claim.

An attacker (needing no allocation at all) can watch the mempool and, between two legitimate `claim()` transactions, call `updateEndRemainingAllocation()` to re-lock `totalEndRemainingAllocation` to the then-current (already shrunk) `totalRemainingAllocation`. This breaks the conservation invariant that `Σ(userAllocation_i / totalEndRemainingAllocation) == 1` for all remaining allocation holders: once part of the group has already claimed against the original larger denominator, re-snapshotting to a smaller value causes the remaining allocation holders' bonus shares to sum to more than their fair remaining share of `totalBonus`, while `totalBonus` itself is never decremented when paid out [7](#0-6) . The net effect is systematic overpayment out of the same `aidropToken` balance that also backs other users' unclaimed principal, redistributing value between claimants based purely on transaction ordering that any unprivileged party can manipulate.

### Impact Explanation
This is a direct Conservation/Custody violation: a party with no privilege and no capital can alter the bonus entitlement of other users purely by call ordering. The practical consequences are:
- Some claimants receive a bonus larger than their fair proportional share, effectively taking value from the shared bonus/token pool that should back other still-unclaimed allocations.
- Because `aidropToken` balance is shared across principal and bonus payouts, later legitimate claimants can face `InsufficientBalance` reverts [8](#0-7) , freezing their entitled principal+bonus with no on-chain refill mechanism, satisfying the "funds frozen ≥24h" / insolvency impact class.

### Likelihood Explanation
Extremely low barrier: `updateEndRemainingAllocation()` is `public`, requires zero token holdings, and only needs `block.timestamp >= periodsEndTime[4]` [2](#0-1) . Any EOA can front-run/back-run legitimate claims for the entire multi-month window after period 4 ends, and can repeat the manipulation on every subsequent claim since `claim()` never re-locks the value once it becomes non-zero.

### Recommendation
Add a "set-once" guard to `updateEndRemainingAllocation()` (e.g., only allow the update `if (totalEndRemainingAllocation == 0)`, mirroring the check already present in `claim()`), so the denominator is snapshotted exactly once and can never be altered afterward.

### Proof of Concept
Foundry test outline:
1. Deploy `Airdrop`, `register()` three users (Alice, Bob, attacker with 0 or 1 wei allocation) pre-start.
2. Warp to `periodsEndTime[4]`.
3. Baseline run: Alice calls `claim()` (triggers internal `updateEndRemainingAllocation()`, locking `totalEndRemainingAllocation = totalRemainingAllocation_0`). Record Bob's `getBonusAmount(bob)`.
4. Attack run (fresh deployment/state): Alice calls `claim()` first (as above, locking denominator). Attacker then directly calls `updateEndRemainingAllocation()` after Alice's claim but before Bob's, re-snapshotting `totalEndRemainingAllocation` to the now-smaller `totalRemainingAllocation_1`. Bob then calls `claim()`.
5. Assert `Bob`'s realized bonus in the attack run differs from the baseline (larger), and assert `Σ(bonus paid)` across all claimants exceeds `totalBonus`, or that a final legitimate claimant reverts with `InsufficientBalance` due to depleted `aidropToken` balance.
