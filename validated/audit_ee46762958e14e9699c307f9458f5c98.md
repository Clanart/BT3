Based on my analysis, I found a concrete analog in the Desktop codebase.

### Title
Unbounded memory allocation when rendering an image diff for a crafted oversized blob - ([File: app/src/lib/git/show.ts])

### Summary
`getBlobContents` (used to fetch blob content for image diffs via `getBlobImage`) invokes `git show <commitish>:<path>` with `encoding: 'buffer'` and no `maxBuffer` override. Because `git()` in `app/src/lib/git/core.ts` sets `maxBuffer: Infinity` whenever `encoding === 'buffer'`, git is allowed to buffer an arbitrarily large blob fully into process memory before any size check runs, unlike the sibling `getPartialBlobContentsCatchPathNotInRef` function which explicitly caps `maxBuffer` to a caller-supplied `length`.

### Finding Description
`git()`'s default options compute `maxBuffer: options?.encoding === 'buffer' ? Infinity : kStringMaxLength` [1](#0-0) . `getBlobContents` calls `git(['show', ...], ..., { successExitCodes: new Set([0, 1]), encoding: 'buffer' })` without passing a `maxBuffer`, so it inherits `Infinity` [2](#0-1) . This is used by `getBlobImage` to fetch binary blob content for rendering as an image diff: `const contents = await getBlobContents(repository, commitish, path)` followed by `contents.toString('base64')` [3](#0-2) . This path is only reached for files whose extension matches `imageFileExtensions` (png, jpg, gif, ico, webp, bmp, avif) and whose diff was reported binary by git, gated in `convertDiff` [4](#0-3) .

There is no size check anywhere on this path before the buffer is materialized and base64-encoded. Contrast this with `getFilesDiffText`, which explicitly checks `if (stdout.length > 10 * 1024 * 1024) throw ...` after fetching with the same `encoding: 'buffer'` pattern [5](#0-4) , and with `getPartialBlobContentsCatchPathNotInRef`, which caps `maxBuffer: length` [6](#0-5) . The `MaxReasonableDiffSize`/`isBufferTooLarge` guard in the same file only applies to the raw diff text buffer (from `git diff`), not to `getBlobImage`'s blob buffer, so it does not protect this path [7](#0-6) .

An attacker who controls a repository the victim clones/fetches/checks out (a malicious remote, or a crafted PR the user views) can commit a file with an image extension (e.g. `evil.png`) whose blob content is many gigabytes (git blobs support arbitrary content regardless of "real" PNG validity — git only needs to detect it as binary to mark the diff binary). When the user opens Desktop's Changes/History view and Desktop attempts to render the image diff for that file, `getBlobImage` → `getBlobContents` shells out to `git show <sha>:evil.png` with `maxBuffer: Infinity`, causing dugite/Node to buffer the entire blob into memory, followed by a `toString('base64')` doubling the string allocation, well beyond the `MaxDiffBufferSize`/`MaxReasonableDiffSize` limits that are enforced for the text-diff path.

### Impact Explanation
This can exhaust process memory and crash the Desktop renderer/main process (denial of service) purely by the user viewing a diff/PR from an untrusted repository — no privileged action, no local access, and no user interaction beyond normal repository browsing (which is the core Desktop workflow). This matches the reported bug class: unbounded memory allocation while deserializing/materializing attacker-supplied structured data (here, a git blob) without a size ceiling before allocation.

### Likelihood Explanation
Likelihood is high for any user who clones or checks out a branch/PR from an untrusted or compromised remote and views the file's diff/history in Desktop, since image-diff rendering is a default, automatic UI behavior for image-extension files rather than an opt-in action.

### Recommendation
Apply the same defensive pattern already used elsewhere in the codebase (`getFilesDiffText`'s 10MB post-fetch check, or `getPartialBlobContentsCatchPathNotInRef`'s `maxBuffer` cap) to `getBlobContents`/`getBlobImage`: either pass a bounded `maxBuffer` to the underlying `git show` invocation, or stat/check the blob size (e.g., via `git cat-file -s`) before fetching full contents, and reject/skip rendering oversized blobs as is already done for oversized text diffs.

### Proof of Concept
1. Attacker creates a repository with a file `evil.png` whose git blob content is, e.g., 4GB of binary-looking bytes (so `git diff` reports it as `Binary files ... differ`), and pushes/shares it (as a remote, a branch, or a PR).
2. Victim, using GitHub Desktop, clones/fetches the repository and selects the commit/PR containing `evil.png` in the Changes or History view.
3. Desktop's `convertDiff` sees `diff.isBinary === true` and extension `.png` is in `imageFileExtensions`, calling `getImageDiff` → `getBlobImage` → `getBlobContents(repository, commitish, 'evil.png')` [4](#0-3) [3](#0-2) .
4. `git(['show', 'commitish:evil.png'], ..., { encoding: 'buffer' })` runs with `maxBuffer: Infinity` [1](#0-0) , causing Node/dugite to buffer the full multi-gigabyte blob in memory, then `contents.toString('base64')` allocates a further ~1.33x string, producing an out-of-memory crash or severe resource exhaustion in the Desktop app process.

export async function getPartialBlobContentsCatchPathNotInRef(
  repository: Repository,
  commitish: string,
  path: string,
  length: number
): Promise<Buffer | null> {
  const args = ['show', `${commitish}:${path}`]

    maxBuffer: length,
    expectedErrors: new Set([GitError.PathExistsButNotInRef]),
    encoding: 'buffer',

export async function getBlobImage(
  repository: Repository,
  path: string,
  commitish: string
): Promise<Image> {
  const extension = Path.extname(path)
  const contents = await getBlobContents(repository, commitish, path)
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(extension),
    contents.length
  )
}
