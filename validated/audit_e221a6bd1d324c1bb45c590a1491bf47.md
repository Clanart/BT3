### Title
Auction bid pool leaves inserted bid in state after `AddBid` returns an error - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool.AddBid` performs `insertBid` (which mutates `bidMap`, `bidTargetMap`, and `bidWinnerMap` and thereby claims the sender's per-block "winner slot") before calling `getBidTxGasLimit`. If `getBidTxGasLimit` fails, `AddBid` returns an error to the caller without undoing the `insertBid` mutation, so the bid remains lodged in the pool even though the RPC caller was told the bid was rejected.

### Finding Description
`AddBid` executes a three-step sequence: validate → insert → compute gas limit, but only the last step's error is unwound; the middle step's effects are not rolled back on a later failure: [1](#0-0) 

`insertBid` mutates `bp.bidMap`, `bp.bidTargetMap[blockNumber][targetTxHash]`, and critically `bp.bidWinnerMap[blockNumber][sender]`, which is the structure used to enforce "one bid per sender per block": [2](#0-1) 

After `insertBid` succeeds, `AddBid` calls `getBidTxGasLimit`, which can fail (e.g., `system.EncodeAuctionCallData` error or `types.IntrinsicGas` error): [3](#0-2) 

If this later call fails, `AddBid` returns the error to the RPC layer (`SubmitBid`), which reports the bid as rejected to the searcher/auctioneer: [4](#0-3) 

However, the bid entry inserted by `insertBid` is never removed. This is the same bug class as the reported virtio_net CVE: partial initialization/state changes are not unwound when a later step in the same multi-step operation fails, leaving the system in an inconsistent state that the caller believes did not happen.

Consequences of the stale entry:
- `bp.bidWinnerMap[blockNumber][sender]` now holds this "failed" bid's hash, so `senderHasDifferentWinner` will reject any subsequent, well-formed bid from the same sender for that block (via `ErrBidSenderExists`) in both `validateBid` and `insertBid`.
- `bp.bidTargetMap[blockNumber][targetTxHash]` now holds a bid with `GasLimit` never set (`SetGasLimit` line 269 is skipped), so if this bid is later read via `GetTargetTxMap`/`PostInsertBlock` consumers (block-building/auction winner selection) it carries an uninitialized/zero gas limit while still occupying the target's bid slot, potentially causing the winning bid slot for that transaction to be effectively wasted or misused, and blocking a legitimate lower-or-higher bid from replacing it depending on FCFS/`ErrLowBid` logic in `insertBid`.

### Impact Explanation
This allows any unprivileged auction bidder (public RPC caller of `auction_submitBid`) to lock a "winner" slot for a given block-number/sender pair, denying legitimate future bids from the same sender and potentially interfering with the auction's fee/bid selection for that block, even though the API told them their submission failed. This is a state-consistency/auction-integrity issue reachable directly by any public caller, matching the "gasless and auction modules" and "auction bidder" reachable-path categories in scope. It does not appear to allow direct fund theft, but it can corrupt auction admission state and potentially block/redirect the intended winning-bid selection for a block, which affects auction settlement fairness.

### Likelihood Explanation
The trigger requires `getBidTxGasLimit` to fail after `insertBid` succeeds. This can happen through `system.EncodeAuctionCallData` or `types.IntrinsicGas`/`FloorDataGas` returning an error for a bid whose fields otherwise pass `validateBid` (which does not perform ABI-encoding or intrinsic-gas computation). I was not able to fully verify, within the remaining tool budget, the exact conditions under which `EncodeAuctionCallData` or `IntrinsicGas` return errors for a bid that already passed `validateBid`'s checks (data size, gas limit, signatures) — this is the main uncertainty in confirming attacker-triggerable reachability of the error path.

### Recommendation
In `AddBid`, either (a) compute `getBidTxGasLimit` before calling `insertBid` so no state mutation occurs until all fallible steps succeed, or (b) explicitly roll back the `insertBid` mutation (remove from `bidMap`, `bidTargetMap`, `bidWinnerMap`) if `getBidTxGasLimit` fails, mirroring the "extract disable/enable helpers and use them symmetrically in error paths" fix pattern from the referenced virtio_net CVE fix.

### Proof of Concept
Conceptual PoC (exact trigger for `getBidTxGasLimit` failure not fully confirmed):
1. A searcher calls the public `auction_submitBid` RPC with a validly-signed bid (passes `validateBid`) but with `Data`/`CallGasLimit` crafted so that `system.EncodeAuctionCallData` or `types.IntrinsicGas`/`blockchain.FloorDataGas` returns an error (e.g., malformed ABI encoding inputs for the bid struct, if such a path exists).
2. `AddBid` calls `insertBid`, which succeeds and registers the bid in `bidMap`/`bidTargetMap`/`bidWinnerMap`.
3. `getBidTxGasLimit` fails; `AddBid` returns an error; `SubmitBid` reports failure to the caller.
4. The same sender submits a second, well-formed bid for the same block; it is rejected with `auction.ErrBidSenderExists` from `senderHasDifferentWinner`, because the pool still believes the sender has an active/different winning bid for that block — despite the RPC having reported the first submission as failed. // AddBid adds a bid to the bid pool.
// Required mutex is locked in each function.
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) senderHasDifferentWinner(bid *auction.Bid) bool {
	hash, ok := bp.bidWinnerMap[bid.BlockNumber][bid.Sender]
	if !ok {
		return false
	}
	return !bid.Equals(bp.bidMap[hash])
}

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}
