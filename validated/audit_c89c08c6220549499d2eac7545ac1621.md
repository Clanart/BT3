## Title
Unbounded stake-program index scan in `calculate_non_circulating_supply` degrades `getSupply`/`getLargestAccounts` - (File: `runtime/src/non_circulating_supply.rs`)

## Summary
`calculate_non_circulating_supply`, invoked by both `getSupply` and `getLargestAccounts`, calls `bank.get_filtered_indexed_accounts(&IndexKey::ProgramId(stake::program::id()), ..., None)` with the byte-limit parameter hard-coded to `None` [1](#0-0) , unlike the RPC layer's own `get_filtered_indexed_accounts` wrapper used for `getProgramAccounts`, which always forwards the operator-configured `scan_results_limit_bytes`.

## Finding Description
The stake-account collection path is only reached when the secondary `ProgramId` index is enabled: `bank.rc.accounts.accounts_db.account_indexes.contains(&AccountIndex::ProgramId)` [2](#0-1) . When enabled, the call passes `None` as `byte_limit_for_scan`, and the owner-equality closure at line 42 is applied only after each pubkey is loaded via `do_load` inside the index scan — it filters the *result*, not the *scan cardinality* [1](#0-0) . This is the same code construct documented in the underlying `load_by_index_key_with_filter`/`index_scan_accounts` primitives, where the abort condition is driven solely by the caller-supplied `byte_limit_for_scan` option — confirmed by `test_get_filtered_indexed_accounts_limit_exceeded` in `runtime/src/bank/tests.rs`, which shows the scan only aborts when `Some(limit)` is explicitly supplied. In contrast, `JsonRpcRequestProcessor::get_filtered_indexed_accounts` (used for `getProgramAccounts`) always forwards `self.config.scan_results_limit_bytes` to the same underlying scan. This is a genuine inconsistency in `non_circulating_supply.rs` relative to the pattern already established elsewhere in the RPC layer for the identical primitive.

## Impact Explanation
When the `ProgramId` secondary index is enabled and populated with a large number of stake-owned accounts, every `getSupply`/`getLargestAccounts` request performs an unbounded index scan and `do_load` for each entry, increasing CPU/IO/latency proportionally to the number of indexed accounts, with no configured circuit breaker analogous to the one protecting `getProgramAccounts`. This matches the "single-client low-rate RPC crash/degradation" impact category and is confined to a single RPC node; it has no cross-validator or consensus effect.

## Likelihood Explanation
Exploitation requires two non-default preconditions on the target node: `--full-rpc-api` and the opt-in `--account-index program-id` secondary index. It further requires the attacker to fund rent-exempt balances for a large number of accounts assigned to `stake::program::id()`, which is an economic throttle on attack cost. Given these preconditions, however, the degradation is straightforward, deterministic, and repeatable.

## Recommendation
Thread the same configured byte-limit (`scan_results_limit_bytes`) used by `JsonRpcRequestProcessor::get_filtered_indexed_accounts` into `calculate_non_circulating_supply`'s call to `bank.get_filtered_indexed_accounts`, so the scan can abort with a `ScanError` once results exceed the configured limit, and propagate that error to the RPC caller (as `RpcCustomError::ScanError`) rather than allowing an unbounded scan.

## Proof of Concept
1. Run a validator/test cluster with `--account-index program-id` and `--full-rpc-api` enabled.
2. As an unprivileged client, submit many `SystemProgram::create_account` (or `Allocate`+`Assign`) transactions assigning `stake::program::id()` as owner for a large number of freshly funded pubkeys, each paying the rent-exempt minimum.
3. Confirm via a direct call to `bank.get_filtered_indexed_accounts(&IndexKey::ProgramId(stake::program::id()), |_| true, None)` (mirroring the pattern in `runtime/src/bank/tests.rs::test_get_filtered_indexed_accounts`) that the number of scanned/loaded entries grows linearly with attacker-created accounts, and contrast with `test_get_filtered_indexed_accounts_limit_exceeded`, which shows the abort mechanism only activates when an explicit `Some(byte_limit)` is passed.
4. Measure `getSupply`/`getLargestAccounts` latency before and after step 2 to observe degradation proportional to the injected account count.
