### Title
`ReceivedOutput::read` accepts a claimed output value with no binding to the chain, and `SignableTransaction`/`TransactionSignMachine` sign a Taproot sighash committing to that unverified amount — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs), [File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The fee-on-transfer bug class is "the credited amount is assumed equal to the transferred/claimed amount." The Serai analog lives in `bitcoin-serai`'s wallet: `ReceivedOutput` is the unit of "funds received," and its `read` deserializer accepts an attacker-supplied `TxOut` (value + script) and `OutPoint` verbatim, with no check that the outpoint exists or that the claimed value matches the actual on-chain output. Downstream, `SignableTransaction::new` sums these claimed values to fund payments and compute change, `multisig` verifies only the `script_pubkey` (never the value), and `TransactionSignMachine::sign` commits to the forged amounts via `Prevouts::All`, producing threshold signatures over a sighash built on fabricated input values.

### Finding Description
`ReceivedOutput::read` blindly trusts three consensus-decoded fields:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output;
  let outpoint;
  {
    let mut buf_r = BufReader::with_capacity(0, r);
    output =
      TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
    outpoint =
      OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

There is no consistency requirement between `outpoint`, `output.script_pubkey`, and `offset` — `ReceivedOutput` has no constructor at all that validates the triple; `Scanner::scan_transaction` is the only honest producer (mod.rs:199-214) and nothing in `read` enforces that provenance.

`SignableTransaction::new` then treats the claimed value as real money received:

```rust
// networks/bitcoin/src/wallet/send.rs:175
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
```

and computes change as `input_sat - payment_sat - fee_with_change` (send.rs:228-230).

`multisig` checks only the script:

```rust
// networks/bitcoin/src/wallet/send.rs:276-279
let offset = keys.clone().offset(self.offsets[i]);
if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
  None?;
}
```

The claimed `value` is never checked against anything. Finally, `sign` feeds the unverified prevouts into the BIP-341 sighash:

```rust
// networks/bitcoin/src/wallet/send.rs:373-390
let mut cache = SighashCache::new(&self.tx.tx);
let prevouts = Prevouts::All(&self.tx.prevouts);
...
cache.taproot_key_spend_signature_hash(i, &prevouts, TapSighashType::Default)
```

### Impact Explanation
An unprivileged party who can feed serialized bytes into `ReceivedOutput::read` (explicitly in-scope untrusted input) can cause a FROST threshold group to sign a transaction spending inputs with fabricated amounts, or spending outpoints that do not exist. Because `Prevouts::All` commits every input's `value` and `script_pubkey` into the sighash, the group produces a valid FROST signature over a message (the sighash) constructed from attacker-chosen amounts — the signed transaction is consensus-invalid and unbroadcastable, so the signing session is burned and any "received" balance derived from the forged output is unspendable. This matches the accepted impact classes "concrete signing of an unintended message" and "funds reported received that are not spendable": the pipeline reports `value()` (mod.rs:116-118) as received balance while the funds do not exist.

### Likelihood Explanation
Reachability depends on an integrator feeding non-scanner-produced bytes to `ReceivedOutput::read` (e.g., outputs relayed between nodes), which is precisely the untrusted-bytes surface enumerated for this audit. Within the crate there is no defense: no existence/value check in `read`, no value check in `multisig`, and `Prevouts::All` faithfully commits the lie into the signed message. Exploitation requires no collusion and no key material.

### Recommendation
Bind `ReceivedOutput` to observed chain data:
- Make `ReceivedOutput::read` (or a wrapper) require the `outpoint`'s txid to actually commit to `output` — i.e., verify against the source transaction/block, or restrict construction to `Scanner::scan_transaction`/`scan_block` and mark `read` as trusted-inputs-only.
- In `SignableTransaction::multisig`, additionally verify `prevouts[i]` equals the output at `outpoint` on chain (or at minimum that `offset` + claimed script correspond to a scanned script registered via `Scanner`), so fabricated values cannot reach `Prevouts::All`.
- If deserialization of untrusted `ReceivedOutput`s is required, treat the value as a claim and re-scan the referenced transaction before scheduling a spend.

### Proof of Concept
1. Attacker learns a registered offset `o` whose script `S = p2tr_script_buf(group_key + G*o)` the scanner watches (offsets/scripts are observable on chain).
2. Attacker serializes `Scalar::o || TxOut{ value: 21_000_000_0000_0000 (fake), script_pubkey: S } || OutPoint{ txid: arbitrary, vout: 0 }` and delivers it to a node path that calls `ReceivedOutput::read` (mod.rs:122).
3. Node builds `SignableTransaction::new(vec![forged], payments, change, None, fee)` — the forged `input_sat` (send.rs:175) passes the `NotEnoughFunds` check (send.rs:215) and funds real payments plus inflated change.
4. `tx.multisig(&keys)` succeeds because only `script_pubkey` is compared (send.rs:277); each participant runs `sign`, which computes `taproot_key_spend_signature_hash` over `Prevouts::All` containing the fake `value` (send.rs:375-390) and emits FROST signature shares.
5. `complete` (send.rs:417-428) yields a fully-signed transaction that is consensus-invalid (prevout doesn't exist / amount mismatch), while the node has recorded `output.value()` as received balance (mod.rs:116-118) and expended a threshold signing session on a message the group never intended to authorize.
