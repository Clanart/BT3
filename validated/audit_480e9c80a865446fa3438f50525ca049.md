### Title
TextFormat/DebugString redaction of `debug_redact=true` fields is opt-in, not the default — sensitive fields are printed in plaintext by the standard public `TextFormat::Printer` API - ([File: src/google/protobuf/text_format.cc], [File: java/core/src/main/java/com/google/protobuf/TextFormat.java])

### Summary
Grafana Agent exposed inline secrets in plaintext because its config/debug HTTP endpoints serialized configuration structures without redacting sensitive fields by default; only an explicit opt-in flag disabled the endpoints/enabled obfuscation. Protobuf has an analogous mechanism — the `debug_redact` field option, meant to prevent sensitive proto fields (e.g. credentials) from leaking into human-readable/debug text output — but the redaction behavior is gated behind explicit printer flags (`redact_debug_string_` in C++, `enablingSafeDebugFormat` in Java) rather than being the default for the general-purpose, publicly documented `TextFormat::Printer` / `TextFormat.printer()` API. Any application code that uses the ordinary `TextFormat::PrintToString`/`TextFormat::Print` (C++) or `TextFormat.printToString` (Java) paths to render a message to logs, an API response, or a debug page — instead of `Message::DebugString()` which does set `SetRedactDebugString(true)` — will print `debug_redact=true` fields (and any nested message/enum-driven sensitivity) in cleartext.

### Finding Description
The `debug_redact` option is declared in `google/protobuf/descriptor.proto`: [1](#0-0) 

In C++, redaction is only applied when the printer's `redact_debug_string_` flag is set, which is done explicitly inside `StringifyMessage()` (used by `Message::DebugString()`), not by the default `TextFormat::Printer` constructor or the plain `TextFormat::Print`/`PrintToString` entry points: [2](#0-1) 

The actual redaction check `TryRedactFieldValue` only redacts when `redact_debug_string_` is true; if a caller uses the generic printer without turning that flag on, the field is printed as normal: [3](#0-2) 

The same opt-in pattern exists in the Java implementation: `shouldRedact()` requires both a sensitive field state AND `enablingSafeDebugFormat` to be true — the plain `TextFormat.printer().printToString(message)` invocation used throughout application code does not necessarily enable this flag: [4](#0-3) [5](#0-4) 

The failed invariant that transfers from the Grafana bug: "sensitive/credential-bearing configuration data must never be rendered in plaintext by a general-purpose serialization/introspection path that a consuming application may expose." In Grafana, the missing check was that the `/-/config` endpoint used a generic YAML marshal without secret-scrubbing by default. In Protobuf, the missing check is structurally identical: the generic `TextFormat::Print`/`PrintToString` path (and Python's `text_format.py` `PrintField`/`PrintFieldValue`, which this search did not find any `debug_redact` gating for at all) does not enforce redaction; only the specialized `DebugString()`/"safe debug format" call sites do.

### Impact Explanation
If a consuming application uses `TextFormat::Printer` (C++) or `TextFormat.printer()` (Java), or Python's `text_format.PrintField`, to render a message containing fields marked `debug_redact = true` (e.g., an API key, OAuth token, or credential embedded in a proto config message) for a log, admin UI, or diagnostic HTTP response — the same class of exposure surface as Grafana's `/-/config` — the secret is exposed in plaintext, since these are the exact code paths library authors and application developers are told to use for “safe” debug output when they don't call `DebugString()` directly. This is a confidentiality-only issue (CWE-200/CWE-312 analog), matching the CVSS profile of the original report (`C:L`), because the exposure requires the message to already be reachable by the untrusted consumer through an application-controlled channel — Protobuf itself has no HTTP endpoint.

### Likelihood Explanation
Moderate. `TextFormat::Printer`/`TextFormat.printer()` (and the Python `text_format` module) are documented, supported public APIs — not internal/test-only surfaces — that are commonly reused for human-readable dumps in logging or debug UIs, exactly analogous to how Grafana used generic YAML marshaling for its config-dump endpoint. Because redaction is opt-in per call site (`SetRedactDebugString`/`enablingSafeDebugFormat`) rather than a property of the field annotation being universally honored by every print path, any call site that doesn't specifically go through `DebugString()`/"safe debug format" silently loses redaction. Whether Python's `text_format.py` implements `debug_redact` filtering at all could not be confirmed in this pass; the searched code (`PrintField`/`PrintFieldValue`) shows no redaction check, but the full extent of Python coverage was not exhaustively verified given tool-call limits.

### Recommendation
- Audit all public entry points that ultimately call `PrintField`/`PrintFieldValue`/`PrintUnknownFields` (C++, Java, Python, others) to ensure `debug_redact`-marked fields are redacted regardless of which specific printer configuration flag path is used, not only via `DebugString()`.
- Consider making redaction of `debug_redact=true` fields the default behavior for all `TextFormat` printing entry points, requiring an explicit "insecure/unredacted" opt-out flag instead of an opt-in `SetRedactDebugString`/`enablingSafeDebugFormat`.
- Verify parity across language implementations (Python's `text_format.py` in particular) to confirm `debug_redact` is enforced uniformly.
- Document clearly for API consumers which `TextFormat` entry points redact sensitive fields and which do not, so applications building admin/debug endpoints don't inadvertently choose an unredacted path.

### Proof of Concept
Given a proto schema (as in the repo's own test fixtures) with a sensitive field:
```proto
message TestNestedMessageEnum {
  string redacted_string = 3 [debug_redact = true];
}
``` [6](#0-5) 

Calling `message.DebugString()` correctly redacts the field (per `StringifyMessage` setting `SetRedactDebugString(true)`): [7](#0-6) 

But constructing a plain `TextFormat::Printer printer;` (default-constructed, without calling `printer.SetRedactDebugString(true)`) and calling `printer.PrintToString(message, &result)` will print `redacted_string: "actual-secret-value"` in cleartext, because `TryRedactFieldValue` only substitutes `kFieldValueReplacement` when `redact_debug_string_` is true: [8](#0-7) 

This reproduction was traced through source but not executed in a build environment; confirming the exact default value of `redact_debug_string_` in the `Printer` constructor (not located in this search pass) would be needed to fully validate that the default-constructed printer indeed leaves the flag `false`. This remaining verification step should be performed with direct repository/build access to compile and run the C++ test harness (`ProtobufToStringOutputTest`-style scenario) against a default-constructed `TextFormat::Printer`.

bool TextFormat::Printer::TryRedactFieldValue(
    const Message& message, const FieldDescriptor* field,
    BaseTextGenerator* generator, bool insert_value_separator) const {
  TextFormat::RedactionState redaction_state =
      DescriptorPool::MemoizeProjection(
          field, [](const FieldDescriptor* field) {
            return TextFormat::GetRedactionState(field);
          });
  if (redaction_state.redact) {
    if (redact_debug_string_) {
      IncrementRedactedFieldCounter();
      if (insert_value_separator) {
        generator->PrintMaybeWithMarker(MarkerToken(), ": ");
      }
      generator->PrintString(kFieldValueReplacement);
      if (insert_value_separator) {
        if (single_line_mode_) {
          generator->PrintLiteral(" ");
        } else {
          generator->PrintLiteral("\n");
        }
      }
      return true;
    }
  }
  return false;
}

    // The criteria for redacting a field is as follows: 1) The enablingSafeDebugFormat printer
    // option must be on. 2) The field must be considered "sensitive". A sensitive field can be
    // marked as sensitive via two methods: a) via a direct debug_redact=true annotation on the
    // field, b) via an enum field marked with debug_redact=true that is within the proto's
    // FieldOptions, either directly or indirectly via a message option.
    private boolean shouldRedact(final FieldDescriptor field, TextGenerator generator) {
      FieldDescriptor.RedactionState state = field.getRedactionState();
      return enablingSafeDebugFormat && state.redact;
    }
