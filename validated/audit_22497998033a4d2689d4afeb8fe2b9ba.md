# CVE-2017-20186 Analog Assessment — Chia Wallet-Side Unbounded CLVM Re-execution of Received Coin Spends

### Title
Wallet re-executes received coin puzzles at full block-cost budget without the mempool's per-tx cost cap, enabling a spend-triggered CPU exhaustion DoS - (File: `chia/wallet/util/compute_memos.py`)

### Summary
The external CVE describes a denial-of-service triggered by a crafted, attacker-controlled input (`cleanName`) reaching a handler function without adequate bound checking, crashing/hanging the service. The closest reachable analog in this repo is `compute_memos_for_spend()`, which re-runs an attacker-supplied puzzle reveal/solution pair (from any coin sent to a victim wallet) at a cost budget equal to the entire block-cost limit, with no mempool-style half-cost cap, and this function is invoked repeatedly across multiple independent wallet subsystems whenever the wallet observes a matching coin.

### Finding Description
`compute_memos_for_spend()` runs a coin's puzzle reveal against its solution using `INFINITE_COST`, which is defined as `MAX_BLOCK_COST_CLVM` (11,000,000,000) — i.e., the same cost budget allowed for an entire block, not the tighter `max_tx_clvm_cost` (`MAX_BLOCK_COST_CLVM / 2`) that gates a single spend bundle in mempool admission: [1](#0-0) [2](#0-1) 

This routine (and the `compute_memos()` wrapper that calls it per coin_spend) is invoked from several independent wallet code paths whenever the wallet observes a coin relevant to it:
- Clawback coin identification, for every clawback merkle coin the wallet is either sender or recipient of: [3](#0-2) 
- CR-CAT coin addition, for every CR-CAT coin observed: [4](#0-3) 
- Notification processing, for any coin exceeding a configurable amount threshold, executed against the coin's *parent* spend: [5](#0-4) 
- Outgoing/incoming transaction record construction and RPC memo lookups: [6](#0-5) [7](#0-6) 

Each of these call sites re-executes the puzzle with no cost cap tighter than the full block budget, and the same on-chain spend can be re-executed multiple independent times by a single wallet across these subsystems (state manager, clawback manager, notification manager, CR-CAT wallet) as it processes the corresponding coin states during sync.

### Impact Explanation
Mempool admission for a single spend bundle is deliberately capped at half the block-cost budget (`max_tx_clvm_cost`) specifically to bound worst-case CLVM execution time for untrusted, attacker-submitted transactions, per the documented pipeline: [8](#0-7) 

The wallet's memo-computation path bypasses that tighter bound and instead allows up to the *full* block-cost budget per coin_spend, and does so repeatedly across independent subsystems for the same received coin. A sender can construct (and get confirmed, since a single-spend block can legitimately consume nearly the full block-cost budget) a coin whose puzzle is maximally expensive to evaluate — similar in spirit to the recursive/expensive CLVM patterns the project's own malicious-generator test suite exercises (`SINGLE_ARG_INT_LADDER_COND`, `deep_recursion`, etc.): [9](#0-8) [10](#0-9) 

and send that coin to a victim's wallet, a clawback address, a CR-CAT recipient, or simply any address the wallet is watching above the notification-amount threshold. Every such coin the victim's wallet subsequently processes forces the wallet's synchronous sync loop to re-run the same near-block-cost CLVM evaluation, potentially several times per coin across `wallet_state_manager`, `clawback_manager`, `notification_manager`, and `cr_cat_wallet`. This is a spend-triggered transaction-processing slowdown/halt of the victim's wallet sync, reachable purely by an unprivileged party sending coins/spends the victim wallet must process — no malicious peer or node compromise required.

### Likelihood Explanation
Likelihood is moderate-to-high for wallet users who accept unsolicited payments, clawback offers, CR-CAT transfers, or notifications, since the attack requires only crafting and confirming a normal, otherwise-valid coin spend with an expensive puzzle and sending/annotating it toward the victim's puzzle hash(es) being watched by their wallet. No special privileges beyond normal spend-bundle submission are needed, and `notification_manager.potentially_add_new_notification` is evaluated for any sufficiently large coin without any confirmation that it's addressed to the local wallet in advance of executing the parent spend.

### Recommendation
Cap `compute_memos_for_spend()`/`compute_memos()` at the same `max_tx_clvm_cost` bound the mempool enforces for untrusted single spends (or a materially smaller wallet-specific budget), fail closed on exceeding it, and avoid redundant re-execution of the same coin_spend's CLVM program across multiple independent wallet subsystems (cache the computed memos/conditions once per coin_spend instead of recomputing in `wallet_state_manager`, `clawback_manager`, `notification_manager`, and `cr_cat_wallet` separately).

### Proof of Concept
1. Construct a coin spend whose puzzle reveal, similar to the project's own `SINGLE_ARG_INT_LADDER_COND`/`deep_recursion` test patterns, consumes CLVM cost approaching `MAX_BLOCK_COST_CLVM` while producing a `CREATE_COIN` output with a memo list, targeting a victim puzzle hash (or a clawback/notification puzzle hash controlled by the victim).
2. Get the spend confirmed on chain (a single-spend block can legitimately consume near the full block-cost budget).
3. As the victim wallet syncs and observes the resulting coin state, it triggers `compute_memos_for_spend()`/`compute_memos()` from one or more of `wallet_state_manager._add_coin_state`, `ClawbackManager.identify`, `NotificationManager.potentially_add_new_notification`, or `CRCATWallet.add_crcat_coin`, each re-running the attacker's puzzle at up to `INFINITE_COST` (11,000,000,000) with no mempool-style half-cost restriction, repeatedly consuming CPU during wallet sync.

Note: I was not able to fully verify, within the indexed context, whether `NotificationManager.potentially_add_new_notification` is invoked for coin states unrelated to the local wallet's own puzzle hashes (which would materially widen the blast radius beyond "coins sent to this wallet"); confirming that caller context would require inspecting the wallet sync driver code that isn't fully covered by the current search results.

def compute_memos_for_spend(coin_spend: CoinSpend) -> dict[bytes32, list[bytes]]:
    _, result = run_with_cost(coin_spend.puzzle_reveal, INFINITE_COST, coin_spend.solution)
    memos: dict[bytes32, list[bytes]] = {}
    for condition in result.as_python():
        if condition[0] == ConditionOpcode.CREATE_COIN and len(condition) >= 4:
            # If only 3 elements (opcode + 2 args), there is no memo, this is ph, amount
            coin_added = Coin(coin_spend.coin.name(), bytes32(condition[1]), uint64(int_from_bytes(condition[2])))
            if type(condition[3]) is not list:
                # If it's not a list, it's not the correct format
                continue
            memos[coin_added.name()] = [mem for mem in condition[3] if isinstance(mem, bytes)]
    return memos

### Pipeline (in order)

1. **Peak check**: mempool must be initialized

2. **Coin spend processing** (per spend):

   `timestamp = peak.timestamp`.

5. **Fee = removal_amount − addition_amount**
