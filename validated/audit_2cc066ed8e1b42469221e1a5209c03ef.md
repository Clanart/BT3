### Title
ProtoJSON Timestamp parser (`upb`-based bindings) accepts impossible dates such as non-leap-year February 29 - ([File: upb/json/decode.c])

### Summary
The `upb`-based ProtoJSON `Timestamp` decoder (shared by the upb core, PHP, and Ruby bindings) converts year/month/day digits straight into a Julian/epoch-day count using a leap-year-aware formula, but never validates that the day is *legal* for the given month and year. As a result, a syntactically well-formed but calendrically impossible date such as `2001-02-29` (2001 is not a leap year) is silently accepted and converted into a valid `Timestamp.seconds` value instead of being rejected, exactly analogous to the JOJO report's root cause: a leap-year assumption baked into date arithmetic that is not cross-checked against the actual calendar.

### Finding Description
`jsondec_epochdays()` in `upb/json/decode.c` (duplicated verbatim in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`) computes: [1](#0-0) 
This formula (Howard Hinnant's civil-to-days algorithm) is mathematically correct for *valid* calendar dates — it correctly folds in leap years via `leap_days = y_adj/4 - y_adj/100 + y_adj/400`. However, `jsondec_timestamp()` feeds the raw parsed `year`, `mon`, `day` digits directly into this formula without first checking that `day` is within the valid range for that `mon`/`year` combination (e.g., rejecting Feb 29 unless the year is a leap year, or rejecting day 31 for a 30-day month): [2](#0-1) 
Because the arithmetic silently "wraps" any digit combination into a well-defined epoch day, an out-of-range day like `2001-02-29` does not fail — it is treated as valid and converted to a `seconds` value, exactly as if the input had rolled over into the next month.

This bug class was confirmed by upstream conformance tests. The Bazel/CI known-failure lists for the `upb`-backed language bindings explicitly document this as a known non-conformance: [3](#0-2) [4](#0-3) [5](#0-4) 
And the corresponding required conformance test case that is expected to fail explicitly for this reason: [6](#0-5) 

By contrast, the canonical C++ (`src/google/protobuf/json/internal/parser.cc`) implementation uses the identical epoch-day formula: [7](#0-6) 
This test id does not appear in a C++-specific known-failure list in this checkout, which suggests (but I could not fully confirm, since I was not able to view the exact validation/rejection logic surrounding `TakeTimeDigitsWithSuffixAndAdvance` before running out of tool budget) that the C++ implementation performs additional bounds checking that the upb-derived implementations lack. This is the one point of uncertainty in this analysis.

### Impact Explanation
This is a **data-integrity / parsing-correctness** issue, not a memory-safety or RCE issue. An ordinary client sending bounded ProtoJSON through the public `Timestamp` JSON parse API on the PHP, Ruby, or upb-core backends can cause an invalid, non-existent calendar date to be silently accepted and converted into a specific, attacker-chosen `seconds` integer. Any consuming application that trusts `Timestamp` fields parsed from JSON to represent valid calendar dates (e.g., expiration checks, audit/log correctness, date-range validation) can be fed semantically corrupt data that passes protobuf's own JSON parsing without error. This matches the "incorrect calculation due to unvalidated calendar assumption" failure mode of the original report, transferred to Protobuf's ProtoJSON well-known-type parsing surface.

### Likelihood Explanation
High likelihood of occurrence for any application using PHP or Ruby protobuf bindings (or the upb core JSON decoder directly) that accepts untrusted ProtoJSON `Timestamp` payloads — this is a public, unauthenticated parse-API surface with no additional preconditions. It is already a confirmed, reproducible discrepancy per the project's own conformance suite (the relevant test is marked `REQUIRED`, meaning upstream expects it to be enforced, yet the upb-based backends fail it).

### Recommendation
In `jsondec_timestamp()` (`upb/json/decode.c`, and the duplicated code in `php-upb.c` / `ruby-upb.c`), validate `mon` is in `[1,12]` and `day` is within the correct day-count for that `mon`/`year` (accounting for leap years via the same `y%4==0 && (y%100!=0 || y%400==0)` rule already implicit in `jsondec_epochdays`) before computing `epoch_days`, rejecting the input with `jsondec_err(d, "Malformed timestamp")` otherwise — mirroring whatever explicit day-of-month/leap-year check the canonical C++ parser is presumed to perform, which should be confirmed and back-ported.

### Proof of Concept
Send a ProtoJSON payload with a PHP or Ruby protobuf binding (upb-based):
```json
{"optionalTimestamp": "2001-02-29T00:00:00Z"}
```
Per the conformance suite, this is expected to be rejected (`ExpectParseFailureForJson("TimestampJsonInputNonLeapFeb29", ...)`, `conformance/binary_json_conformance_suite.cc:3703-3704`), but the known-failure lists confirm the upb-derived parsers accept it and produce a `Timestamp.seconds` value instead of an error, as documented in `conformance/failure_list_ruby.txt:27`, `conformance/failure_list_jruby_ffi.txt:27`, and `upb/conformance/conformance_upb_failures.txt:26`.

/* jsondec_epochdays(1970, 1, 1) == 1970-01-01 == 0. */
int jsondec_epochdays(int y, int m, int d) {
  const uint32_t year_base = 4800; /* Before min year, multiple of 400. */
  const uint32_t m_adj = m - 3;    /* March-based month. */
  const uint32_t carry = m_adj > (uint32_t)m ? 1 : 0;
  const uint32_t adjust = carry ? 12 : 0;
  const uint32_t y_adj = y + year_base - carry;
  const uint32_t month_days = ((m_adj + adjust) * 62719 + 769) / 2048;
  const uint32_t leap_days = y_adj / 4 - y_adj / 100 + y_adj / 400;
  return y_adj * 365 + leap_days + month_days + (d - 1) - 2472632;
}
