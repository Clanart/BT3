Based on my investigation, I found a validation gap in the deep-link branch handling that mirrors the report's core flaw: **a value is validated against the wrong invariant (character blacklist) instead of the invariant that actually matters downstream (git treating a leading `-` as an option, not a ref)** — just as the report's bug validated "is this an `address`" instead of "is this an arbitrary-format `bytes` identifier."

### Title
Deep-link `branch` parameter is checked for a disallowed-character set but not for a leading dash, allowing git argument injection on `openrepo`/`x-github-client` URLs - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL` validates the `branch` query parameter from an `x-github-client://openrepo/...`, `github-mac://openrepo/...`, or `github-windows://openrepo/...` deep link using `testForInvalidChars`, which only rejects control characters and a fixed punctuation set. [1](#0-0) 
That function reuses the same `invalidCharacterRegex` as `sanitizedRefName`, but unlike `sanitizedRefName`, `testForInvalidChars` never strips or rejects a leading `-`/`+`; only the separate sanitize path does that stripping. [2](#0-1) 
`parseAppURL` returns the raw, unsanitized `branch` value straight through to the caller. [3](#0-2) 

### Finding Description
The attacker primitive here is identical in shape to the Cosmos-address report: **a value that should be treated as an opaque, format-agnostic ref string is instead validated with a narrow, format-specific check (a blacklist regex) that doesn't cover the case that actually matters to the consumer (git's CLI argument parser).** A branch name of `-orphan`, `--upload-pack=/tmp/x`, or similar contains no disallowed characters and passes both `testForInvalidChars` and the `pr` correlation check, so `parseAppURL` classifies the URL as a legitimate `open-repository-from-url` action with that branch string intact. [4](#0-3) 

This value then flows unmodified through `dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl`, which fetches and calls `checkoutLocalBranch(repository, branchName)` after an automatic fetch, with no additional sanitization applied between the parser and the checkout call. [5](#0-4) 

The same `dispatchCLIAction` path for `clone-url` actions reuses `openBranchNameFromUrl` with an externally supplied `branch` too. [6](#0-5) 

### Impact Explanation
If `checkoutLocalBranch`'s underlying git invocation (in `app/src/lib/git/checkout.ts`) passes the branch string as a bare positional argument without a `--` end-of-options separator before it — a pattern I was not able to fully confirm before running out of tool calls — a leading-dash branch value would be interpreted by git as a flag rather than a ref name. Depending on the exact git subcommand used for local branch checkout, this class of bug typically enables unintended git behavior (e.g., forcing `--orphan`, redirecting `--upload-pack`/`--exec` style trust-boundary options, or otherwise altering the checkout target) triggered purely by the victim clicking an attacker-supplied `x-github-client://openrepo/...?branch=...` link — i.e., silent corruption of repository state without the user's informed action, consistent with the impact class called out in the task (silent corruption of what the user commits/pushes; no local access or credentials required).

### Likelihood Explanation
The parsing/validation gap itself is confirmed in code: `testForInvalidChars` has no leading-`-` guard while `sanitizedRefName` does, and `parseAppURL` uses the weaker check. [7](#0-6) [8](#0-7) 
What I could **not** verify before running out of tool calls is whether `app/src/lib/git/checkout.ts`'s `checkoutBranch` (or the underlying `git()` call it makes) already inserts a `--` separator before the ref argument, which would neutralize this at the exec layer even though the parser-layer guard is weak. Given the existing hardening seen elsewhere in this codebase (`resolveWithin`, `sanitizeCloneName`, `isClonePathSensitive` all show a mature, defense-in-depth posture around URL/path-derived values), it's plausible the git-exec layer already has this guard — I flag this explicitly as unconfirmed rather than asserting exploitability.

### Recommendation
Have `parseAppURL` reject (or `sanitizedRefName`-normalize) any `branch` value that begins with `-`, in addition to the existing character blacklist, before returning the `IOpenRepositoryFromURLAction`. Independently, confirm/ensure `app/src/lib/git/checkout.ts` always passes ref/branch arguments after a `--` separator so that git-exec layer is not solely reliant on caller-side string validation.

### Proof of Concept
```
x-github-client://openrepo/https://github.com/octokit/octokit.net?branch=--orphan
```
`parseAppURL` will classify this as `open-repository-from-url` with `branch: '--orphan'` because `testForInvalidChars('--orphan')` returns `false` (no disallowed characters match), passing straight through to `openBranchNameFromUrl` → `checkoutLocalBranch`. [9](#0-8) 

**Caveat:** I was unable to inspect `app/src/lib/git/checkout.ts`'s exact git invocation before running out of tool calls, so I cannot fully confirm whether an exec-layer `--` guard already prevents exploitation. This should be verified directly before treating this as a confirmed, exploitable finding.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
