## CVE-2017-9210 Analog: Unbounded Recursive Puzzle-Layer Matching Causes Stack Exhaustion DoS in Wallet Offer/Coin Processing

### Title
Unbounded recursion in outer-puzzle driver matching allows an attacker-crafted spend/offer to crash a victim wallet via stack exhaustion - (File: chia/wallet/outer_puzzles.py)

### Summary
CVE-2017-9210 describes infinite/deep recursion in QPDF's "unparse" functions causing stack exhaustion from a crafted document. The chia-blockchain codebase contains an analogous bug class: recursive "outer puzzle" driver matching that walks nested CLVM curry layers with no depth limit. A malicious counterparty can craft a coin puzzle with an arbitrarily deep chain of recognized layers (CAT/singleton/ownership/metadata/CR), and when a victim wallet tries to identify/uncurry that puzzle (via an offer file, or via a coin sent to the wallet), the process recurses once per layer with no bound, risking a Python `RecursionError`/native stack exhaustion that can crash wallet processing.

### Finding Description
`match_puzzle()` dispatches to per-asset-type drivers (CAT, Singleton, Ownership, Metadata, CR) that each recursively call back into the same top-level matching function through `self._match`, once per curried "layer," with no maximum-depth check: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The same unbounded recursion pattern repeats for `get_inner_puzzle`, `get_inner_solution`, `construct`, and `solve` in each driver, all following the `also()` chain of `PuzzleInfo`: [5](#0-4) 

Each layer only costs a small, constant amount of CLVM curry overhead to add (`curry()` just wraps `[2, (1, self), fixed_args]`): [6](#0-5) 

so an attacker can cheaply stack thousands of recognized layers (e.g., nested CAT-in-CAT, or CR-in-CAT-in-Singleton) in a single puzzle reveal without hitting CLVM cost limits, since the recursion of concern happens entirely in Python driver code after the CLVM program has already been parsed/executed — not inside the CLVM interpreter itself.

This code path is reached from attacker-influenced data in at least two ways:
1. Offer processing: `Offer.from_spend_bundle()` and `Offer._get_offered_coins()` call `match_puzzle()`/`get_inner_puzzle()`/`get_inner_solution()` on `coin_spend.puzzle_reveal` taken directly from an offer file supplied by an untrusted trade counterparty. [7](#0-6) [8](#0-7) 
2. Coin-type identification: `WalletStateManager` uses `UncurriedNFT.uncurry()` and `match_did_puzzle()` on puzzle reveals of coins observed on-chain, which originate from spends an attacker fully controls before sending value to a victim's puzzle hash. [9](#0-8) 

Notably, the codebase already shows awareness of this exact bug class elsewhere: `sha256_treehash()` in `tree_hash.py` is explicitly implemented as an iterative stack machine specifically "so we don't have to worry about blowing out the python stack" when handling deeply nested CLVM structures. [10](#0-9) 
That defensive pattern was not applied to the outer-puzzle driver matching/traversal code, which remains naively recursive over attacker-controlled layer depth.

### Impact Explanation
A crafted offer file or a coin spend that creates a coin destined for a victim's wallet can trigger unbounded Python recursion in wallet code responsible for offer parsing or coin-type classification. This can raise an uncaught `RecursionError` or exhaust the process's native call stack, crashing or hanging the wallet's processing of that transaction/offer — a spend-triggered transaction-processing halt. This is a Medium-severity denial-of-service against wallet users and offer counterparties, consistent with the CVSS 5.5 (local, no privileges, requires user interaction) rating of the source CVE.

### Likelihood Explanation
Building a deeply layered puzzle reveal is cheap: each layer is a small curry wrapper, so an attacker can produce a puzzle with hundreds or thousands of nested "recognized" layers within ordinary program-size limits. No additional privilege beyond crafting an offer file or a normal spend bundle is required, and the recursive code fires automatically whenever the victim wallet tries to process the offer or classify the received coin, so exploitation requires only that the victim open/accept the offer or receive the coin — a very likely trigger for a wallet user or offer counterparty.

### Recommendation
Convert the recursive `match`/`get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` traversal in `chia/wallet/outer_puzzles.py` and the individual driver classes (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) into an iterative loop over the layer chain, or enforce an explicit maximum nesting depth (mirroring the non-recursive design already used in `sha256_treehash`). Additionally, bound recursion depth in `PuzzleInfo.also()`/`check_type()` traversal and validate a sane maximum uncurry depth before invoking these drivers on any untrusted `puzzle_reveal`.

### Proof of Concept
1. Construct an innermost ACS puzzle.
2. Programmatically wrap it in N (e.g., 50,000) nested layers using `construct_cat_puzzle`/`CAT_MOD.curry` or `NFT_OWNERSHIP_LAYER.curry`/`SINGLETON_TOP_LAYER_MOD.curry`, each layer only a few curry bytes.
3. Place this puzzle as the `puzzle_reveal` of a coin in either (a) a `WalletSpendBundle` sent as an offer file to a victim, triggering `Offer.from_spend_bundle`/`_get_offered_coins`, or (b) a real spend creating a coin sent to a victim wallet's puzzle hash, triggering `WalletStateManager.determine_coin_type` → `UncurriedNFT.uncurry`/`match_did_puzzle`.
4. Observe that `match_puzzle()`/`get_inner_puzzle()` recursion depth scales with N, causing `RecursionError` or a native stack overflow when the victim wallet processes the offer/coin.
