### Title
Unauthenticated encryption-key registration in PedPoP lets a MITM substitute recipient ECDH keys and decrypt all secret shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG round-1 message (`EncryptionKeyMessage<Commitments>`) carries each participant's ECDH public key (`enc_key`) alongside their Feldman commitments, but the Schnorr proof-of-knowledge only binds the commitments (`cached_msg`), not `enc_key`. `Decryption::register`/`Encryption::register` accept whatever `enc_key` arrives on the wire for a given `Participant`. A man-in-the-middle (or any party able to alter the forwarded message bytes, which the protocol treats only as an "authenticated channel" assumption) can replace a victim's `enc_key` with a key they control. All subsequent `EncryptedMessage` secret shares addressed to that participant are encrypted under the attacker's key (`ecdh(key, to)` in `encrypt`), and the per-message PoP does not protect this: it proves possession of the *ephemeral sender* key, not the recipient key. The attacker decrypts the victim's shares directly with `cipher(context, ecdh)`, recovering a threshold key share — directly analogous to CVE-2019-25031's "unauthenticated cleartext channel → injected configuration is consumed as trusted" class, mapped here as "unauthenticated channel → injected ECDH key is consumed as the recipient's encryption key." ### Finding Description
`generate_coefficients` builds the round-1 broadcast as `encryption.registration(Commitments { commitments, cached_msg, sig })` [4](#0-3) , where `sig` is a Schnorr PoK over `challenge(context, i, nonce_bytes, cached_msg)` and `cached_msg` is the serialization of the commitments only [5](#0-4) . `EncryptionKeyMessage::read` parses `msg` and `enc_key` as independent fields with no signature covering `enc_key` [6](#0-5) . On receipt, `verify_r1` calls `self.encryption.register(l, msg)`, which inserts `msg.enc_key` into `enc_keys` under participant `l` with only a duplicate-registration assertion — no check that `enc_key` was authorized by `l` [7](#0-6) [8](#0-7) . `encrypt` then derives the shared secret as `ecdh(&key, to)` where `to` is `self.decryption.enc_keys[&participant]` — the attacker-substituted key [9](#0-8) [10](#0-9) . The `pop` Schnorr signature inside `EncryptedMessage` only proves knowledge of the ephemeral key `key` (public `pub_key`), binding `from` and the ciphertext — it never involves the recipient key, so it provides no defense [11](#0-10) .

### Impact Explanation
An attacker who replaces victim participant `v`'s `enc_key` with public key `A` (knowing the corresponding secret `a`) receives every `EncryptedMessage` addressed to `v` encrypted under `A * key`. They compute the shared key `msg.key * a` = `A * key` and run `cipher(context, …).apply_keystream` to recover each `SecretShare<C::F>` plaintext [12](#0-11) . Collecting the shares that honest participants send to `v` (or substituting `enc_key` for several participants) yields enough Feldman shares to reconstruct the DKG secret polynomial(s) — equivalent to recovering the threshold group's secret key material and defeating the threshold property. The victim's `calculate_share` fails (decrypted share bytes won't satisfy `share_verification_statements`), producing blame traffic, but the shares have already been leaked; detection does not undo key compromise.

### Likelihood Explanation
Requires a MITM position or a relay that does not enforce per-participant authentication on round-1 messages — the protocol documentation itself only assumes messages are "sent … over an authenticated channel" [13](#0-12) , and the cryptographic layer provides no binding to enforce it, mirroring CVE-2019-25031 where the vulnerable script relied on an unauthenticated fetch. The attack is deterministic once the channel assumption is violated and costs no interaction beyond forwarding modified bytes. Within the threat model of this audit (unauthenticated injection of attacker-chosen data into a trusted path), this is a reachable medium-severity analog.

### Recommendation
Bind `enc_key` into the round-1 authentication: either extend the PoK `cached_msg` to include `enc_key.to_bytes()` (so the Schnorr PoK covers the commitments *and* the encryption key), or add a second Schnorr signature over `enc_key` under the participant's first commitment. Then `register`/`verify_r1` will reject substituted keys [14](#0-13) [15](#0-14) .

### Proof of Concept

```rust
// Attacker intercepts victim v's EncryptionKeyMessage bytes and rewrites enc_key:
let a = Zeroizing::new(C::random_nonzero_F(&mut rng));      // attacker secret
let mut msg = EncryptionKeyMessage::<C, Commitments<C>>::read(&mut bytes, params)?;
// msg.sig still verifies: challenge only covers cached_msg (commitments), not enc_key
msg.enc_key = C::generator() * a.deref();                    // forged registration
// Honest senders call encryption.encrypt(rng, v, share) which computes
//   ecdh(&key, enc_keys[&v]) == A * key
// Attacker, on the intercepted EncryptedMessage, computes msg.key * a == A * key
// and decrypts: cipher::<C>(context, &ecdh(&a, msg.key)).apply_keystream(&mut msg.msg)
// yielding SecretShare plaintext — v's incoming shares are fully recovered.
// v's calculate_share fails share_verification_statements, but leakage already occurred.
```

```rust
fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {
  Zeroizing::new(public * private.deref())
}

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
```

```rust
    for i in 0 .. t {
      // Step 1: Generate t random values to form a polynomial with
      coefficients.push(Zeroizing::new(C::random_nonzero_F(&mut *rng)));
      // Step 3: Generate public commitments
      commitments.push(C::generator() * coefficients[i].deref());
      cached_msg.extend(commitments[i].to_bytes().as_ref());
    }

    // Step 2: Provide a proof of knowledge
    let r = Zeroizing::new(C::random_nonzero_F(rng));
    let nonce = C::generator() * r.deref();
    let sig = SchnorrSignature::<C>::sign(
      &coefficients[0],
      // This could be deterministic as the PoK is a singleton never opened up to cooperative
      // discussion

      // general obsession with canonicity and determinism though
      r,
      challenge::<C>(self.context, self.params.i(), nonce.to_bytes().as_ref(), &cached_msg),
    );

    // Additionally create an encryption mechanism to protect the secret shares
    let encryption = Encryption::new(self.context, self.params.i(), rng);

    let msg =
      encryption.registration(Commitments { commitments: commitments.clone(), cached_msg, sig });
```
