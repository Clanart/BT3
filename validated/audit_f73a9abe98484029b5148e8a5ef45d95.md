### Title
Payout attribution (OP_RETURN operator xonly-pk) is unsigned, allowing an unprivileged withdrawing user to mint an unfunded operator reimbursement - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The `payout_tx` built by `create_payout_txhandler` commits the withdrawing user's signature only to the input/output pair at index 0 (`SinglePlusAnyoneCanPay`), leaving the OP_RETURN output that records which operator "fronted" the withdrawal completely outside the user's signature. Anyone holding the user's withdrawal signature (i.e. the withdrawing user themselves) can therefore construct and broadcast an alternative payout transaction that fully self-funds the withdrawal while stamping an arbitrary, unrelated operator's x-only pubkey into the OP_RETURN. The bridge's verifier logic trusts this on-chain OP_RETURN as ground truth for "who fronted the payout," feeding a state machine that automatically reimburses that operator from the deposit's `MoveToVault` UTXO — even though that operator never funded anything.

### Finding Description
`create_payout_txhandler` builds a payout transaction with the withdrawal UTXO as input 0, the user's requested payout as output 0, an anchor output, and an OP_RETURN output holding `operator_xonly_pk` (the party claimed to have fronted the withdrawal): [1](#0-0) 

The only cryptographic commitment over this transaction is the user's Schnorr signature verified against the sighash of input 0, described explicitly as requiring `SinglePlusAnyoneCanPay`: [2](#0-1) 

`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` binds the signature only to input 0 and its corresponding output (index 0). It does **not** bind the OP_RETURN output (index 2, holding the claimed operator pubkey) or any additional funding inputs. Consequently, any party possessing this signature — most naturally the withdrawing user, since it is their own signature over their own withdrawal UTXO — can build a completely different transaction that:
- reuses input 0 and the same output 0 (satisfying the signature),
- adds whatever additional inputs are needed to cover the payout amount (self-funded, from the attacker's own wallet),
- sets the OP_RETURN to any operator's public x-only key of the attacker's choosing (operator public keys are protocol-public information),
and broadcast it directly to Bitcoin, bypassing every RPC-side check in `operator.rs::withdraw` / `rpc/aggregator.rs` (profitability check, DB withdrawal-index matching, etc.), since those only apply to the honest RPC path.

Verifiers subsequently scan finalized blocks and trust the OP_RETURN of whatever payout transaction they observe as the payer attribution, with no cross-check that the embedded operator actually supplied the transaction's funding: [3](#0-2) 

This attribution is persisted and later consumed by two automated, no-additional-authorization paths:
1. `PayoutCheckerTask`, which is filtered purely by the stored `payout_payer_operator_xonly_pk` and, once found, drives the credited operator's own reimbursement flow (`handle_finalized_payout`) without verifying that operator actually paid: [4](#0-3) 
2. `is_kickoff_malicious`, which likewise trusts the same DB-stored attribution to decide whether a kickoff is legitimate: [5](#0-4) 

Following the normal reimbursement path (Round → Kickoff → ReadyToReimburse → Reimburse), the credited operator's reimbursement transaction spends the `MoveToVault` UTXO's full bridge amount to that operator's reimbursement address: [6](#0-5) 

Nothing in this chain (schema, DB update, `PayoutCheckerTask`, `is_kickoff_malicious`, or the reimburse-tx builder) verifies that the operator credited by the OP_RETURN actually supplied the funding inputs of the payout transaction on-chain. The equality the protocol needs — `payout_payer_operator_xonly_pk == the operator who actually funded the payout` — is not enforced by any signature or consensus rule; it is merely parsed text from an unsigned output.

### Impact Explanation
This breaks the core custody-attribution invariant of the bridge: **BTC leaves the `MoveToVault` UTXO to reimburse an operator that never fronted the corresponding withdrawal.** Concretely, a withdrawing user (an unprivileged party — no operator/verifier/aggregator role required) can:
- self-fund their own withdrawal payout transaction (paying themselves back with their own capital via the additional inputs they add), while
- stamping an arbitrary honest operator's x-only pubkey in the unsigned OP_RETURN output,

causing that innocent operator to be automatically credited as the payer in the `withdrawals` table, and — via the automated `PayoutCheckerTask` / kickoff / reimburse pipeline (when automation is enabled) — to receive a full `bridge_amount` reimbursement from the deposit's vault UTXO for a withdrawal they did not fund. This is a direct instance of "an operator reimbursed for a payout it never funded," and represents a real, unauthorized BTC transfer out of bridge custody with no economic backing. It can also be used to sabotage a targeted honest operator by forcing them into an automated kickoff/challenge lifecycle they never initiated, risking downstream disprove/challenge complications for a payout they have no record of having made.

### Likelihood Explanation
The attack requires no privileged role. The withdrawing user already legitimately possesses the exact signature needed (it is their own signature over their own withdrawal UTXO, created as part of the normal withdrawal flow); operator x-only public keys are protocol-public data known to all participants (needed for N-of-N deposit signing). Constructing the alternate transaction only requires reusing publicly documented transaction-building logic (`create_payout_txhandler`) with a different OP_RETURN payload and broadcasting directly to the Bitcoin network — no interaction with any Clementine RPC endpoint (and therefore none of its profitability/DB checks) is needed at all. This makes the attack straightforward for any user who wants to obtain a "free" reimbursement grant to an operator of their choosing (e.g., a colluding operator, or themselves if they also happen to run an operator instance).

### Recommendation
Bind the OP_RETURN operator-attribution output to the same signature that authorizes the withdrawal, e.g. by having the user sign with `SIGHASH_ALL` (or `SIGHASH_SINGLE|ANYONECANPAY` extended to also cover the OP_RETURN output) so the operator identity cannot be altered without invalidating the user's signature, or by requiring a separate signature/commitment from the actual funding operator over the transaction (covering all its inputs/outputs) that verifiers must additionally validate before trusting the OP_RETURN attribution. Additionally, before crediting an operator via `update_finalized_payouts`/`mark_payout_handled`, verifiers/operators should validate that the embedded operator xonly-pk corresponds to inputs actually traceable to that operator (or otherwise cryptographically prove the operator authorized fronting this specific withdrawal), rather than trusting an unsigned OP_RETURN.

### Proof of Concept
1. Withdrawing user requests a Citrea withdrawal, producing a legitimate `dust_utxo` (its own P2TR output) and a valid `in_signature` with `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` over input 0 / output 0, exactly as used by `operator.rs::withdraw` (see `core/src/operator.rs:614-637`) and the test helper `generate_withdrawal_transaction_and_signature` (used identically to produce this signature in `core/src/test/manual_reimbursement.rs:86-103`).
2. Instead of (or in addition to) submitting `WithdrawParamsWithSig` to a real operator, the user independently calls `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-435`) with:
   - the same `input_utxo` / `output_txout` / `user_sig` (still valid, since the signature only commits to input/output index 0),
   - `operator_xonly_pk` = the public key of a targeted, unrelated operator "B" instead of the actual funder.
3. The user funds any additional required inputs from their own wallet (equivalent to `fund_raw_transaction` in `operator.rs:652-674`) and broadcasts the transaction directly via Bitcoin RPC — the signature check in `operator.rs:630-637` only ever validates input 0/output 0, so this transaction is fully valid.
4. Once finalized, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses the OP_RETURN and stores `payout_payer_operator_xonly_pk = B` for this withdrawal.
5. Operator B's `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) picks up this "unhandled payout" attributed to itself and drives `handle_finalized_payout` → Kickoff → Reimburse (`core/src/builder/transaction/operator_reimburse.rs:341-385`), paying `bridge_amount` out of the deposit's `MoveToVault` UTXO to operator B, who never funded the withdrawal.

Note: I was not able to fully trace whether any additional guard exists elsewhere in the codebase (outside `core/src/**` in-scope paths) that cross-checks the OP_RETURN funder against actual UTXO provenance; based on the reviewed code paths (`operator.rs`, `verifier.rs`, `task/payout_checker.rs`, `builder/transaction/operator_reimburse.rs`), no such check exists.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
