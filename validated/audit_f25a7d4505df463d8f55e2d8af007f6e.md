### Title
Attacker-controlled `offset`/`TxOut` in `ReceivedOutput` lets a caller adopt and spend outputs belonging to a different registered offset (cross-account BOLA) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`ReceivedOutput` pairs a scalar `offset` (the HDKD sub-account identifier) with a `TxOut`/`OutPoint`, and `ReceivedOutput::read` accepts all three fields verbatim from untrusted bytes. `SignableTransaction::new` consumes `Vec<ReceivedOutput>` and `SignableTransaction::multisig` re-keys the threshold group's signing key with each supplied `offset` (`keys.clone().offset(self.offsets[i])`), checking only that `key + G*offset` matches the attacker-supplied `prevouts[i].script_pubkey`. It never validates that the supplied `offset` corresponds to the branch/sub-account the caller is authorized to spend, nor that the claimed `TxOut` value/script matches the actual on-chain UTXO. This is the direct analog of the Capgo BOLA: `offset` plays the role of `x-limited-key-id` — a client-controlled object selector adopted without an ownership check.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `Scanner::register_offset` partitions funds across distinct offset-derived Taproot scripts (used upstream to distinguish `OutputType::External`, `Forwarded`, change, etc.). The `offset` inside `ReceivedOutput` is therefore an object/capability identifier: possessing a `ReceivedOutput { offset, output, outpoint }` is sufficient to drive `SignableTransaction::multisig` into signing a spend under `key + G*offset`.

`ReceivedOutput::read` (mod.rs:122-134) deserializes `offset` via `Secp256k1::read_F` and consensus-decodes `output`/`outpoint` with no binding between them. In `send.rs`:

- `SignableTransaction::new` copies `input.offset` into `self.offsets` and `input.output` into `self.prevouts` verbatim (send.rs:176, 253).
- `multisig` only asserts `p2tr_script_buf(key + G*offset) == prevouts[i].script_pubkey` (send.rs:276-279) — consistency between two attacker-supplied fields, not ownership of the referenced object.
- `sign` commits to `Prevouts::All(&self.tx.prevouts)` (send.rs:375), i.e., the attacker-declared prevout data, and produces valid threshold signatures for whatever input set was declared.

Because the check is only *internal consistency*, any offset which legitimately maps to an existing on-chain script (a different user's forwarded deposit, the change branch, a different coin's `OutputType` classification in `processor/src/networks/bitcoin.rs` where `kinds[offset_repr]` assigns the type) can be adopted by simply supplying that offset and a matching fabricated/observed `TxOut`.

### Impact Explanation
An unprivileged party who can feed `ReceivedOutput` bytes (via `ReceivedOutput::read`) into the signing path can cause the threshold group to sign spends of UTXOs residing at offset-derived addresses belonging to other depositors/branches — cross-tenant resource adoption, exactly the Capgo shape. Secondary impact: since `prevouts` are attacker-declared and committed via `Prevouts::All`, the signer endorses a sighash over unverified input values, enabling construction of transactions the group never reviewed (unintended-message signing) when the declared data diverges from chain state.

### Likelihood Explanation
Reachable wherever `ReceivedOutput::read` parses untrusted input and the result flows into `SignableTransaction`/`TransactionMachine`. Requires the attacker to know a victim offset (offsets are determined by registered order and are enumerable/observable from deposits) and the corresponding UTXO — both public on-chain data. No secret is needed; severity is bounded by how much of the wallet pipeline is exposed to unauthenticated input, hence High rather than Critical.

### Recommendation
Bind `ReceivedOutput` to scanner-issued records: on `read`/construction, verify `p2tr_script_buf(key + G*offset) == output.script_pubkey` against the *Scanner's own* `scripts` map (rejecting offsets not registered by the local key), and verify the `OutPoint`/`TxOut` against the chain (value and script of the real UTXO) before admitting the input into `SignableTransaction`. Treat `offset` as a capability requiring provenance (returned only by `Scanner::scan_*`), not as a caller-supplied parameter.

### Proof of Concept
1. Honest depositor registers `offset_b` (`Scanner::register_offset`) and receives funds at `script_b = p2tr(key + G*offset_b)` in UTXO `U`.
2. Attacker crafts bytes: `offset_b || TxOut{value, script_b} || outpoint(U)` and passes them through `ReceivedOutput::read`.
3. Attacker submits this `ReceivedOutput` (plus their payment destination) to `SignableTransaction::new`; `multisig` passes since `p2tr_script_buf(key + G*offset_b) == script_b`.
4. `TransactionSignMachine::sign` produces valid shares over `taproot_key_spend_signature_hash(..., Prevouts::All(...))`; `complete` yields a signed transaction spending `U` to the attacker — a spend of another offset's funds never authorized by the depositor.
