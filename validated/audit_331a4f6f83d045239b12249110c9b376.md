### Title
Bid pool spam with low-value bids can permanently exhaust `MaxBidPoolSize`, censoring legitimate higher-value auction bids - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool.insertBid` only evicts/replaces an existing bid when the new bid targets the *same* `(blockNumber, targetTxHash)` slot and has a strictly higher `Bid` value. When the pool is at capacity (`len(bidMap) >= maxBidPoolSize`) and an incoming bid targets a *different* `(blockNumber, targetTxHash)`, it is rejected outright with `ErrBidPoolFull`, regardless of how much higher its `Bid` value is than the lowest-value bid currently occupying the pool. [1](#0-0) 

### Finding Description
The bid pool caps total entries via `maxBidPoolSize` (operator-configured via `--auction.max-bid-pool-size`), and `insertBid` enforces this cap only via a hard rejection—there is no "lowest bid eviction" mechanism analogous to a min-bid-heap:

```go
if existingBid, ok := bp.bidTargetMap[blockNumber][targetTxHash]; ok {
    if existingBid.Bid.Cmp(bid.Bid) >= 0 {
        return auction.ErrLowBid
    }
    // replace within same slot
} else {
    if int64(len(bp.bidMap)) >= bp.maxBidPoolSize {
        return auction.ErrBidPoolFull
    }
}
``` [1](#0-0) 

Each `(blockNumber, targetTxHash)` pair only ever competes against bids for the *same* target transaction; bids for distinct target transactions never compete with each other for capacity even though they share the same finite `bidMap`. A searcher can generate an unbounded number of throwaway sender keys and submit bids for many distinct `targetTxHash` values with minimal `Bid` amounts (bid > 0 is the only value constraint, per `validateBid` rule 3) to occupy up to `maxBidPoolSize` slots. Each sender can only place one active bid per block number (`senderHasDifferentWinner`), but this does not limit the number of distinct sender keys an attacker controls. [2](#0-1) [3](#0-2) 

The only external gate on submitting a bid is providing a searcher signature (trivially self-generated) plus an `Auctioneer` signature. Per the module's own documentation, the `Auctioneer` is an independent off-chain service whose signature merely attests that the bid came through it—it is not described as filtering by bid economic value beyond KIP-249 format checks, so any bid with a positive, nonzero value that the Auctioneer relays is admissible. [4](#0-3) 

Once the pool reaches `maxBidPoolSize` with attacker-controlled low-value bids spread across many distinct target transactions, a legitimate searcher's high-value bid for their own target transaction is rejected with `ErrBidPoolFull` even though it is worth far more than any bid already occupying the pool, because `insertBid` never compares the incoming bid against the globally lowest bid in the pool—only against a bid in the exact same target-tx slot. [5](#0-4) 

### Impact Explanation
This is a griefing/DoS vector against the auction (MEV) settlement mechanism: an attacker can deny arbitrary legitimate bidders' access to the bid pool for the current allowed block window (`[currentBlockNumber+1, currentBlockNumber+allowFutureBlock]`), preventing their (higher-value) bids from ever being inserted, extracted into a bundle, and settled on-chain. This causes:
- Loss of auction revenue that would otherwise accrue to the protocol/proposer from the legitimate high-value bid.
- Denial of service to a specific target transaction's auction (censorship of the searcher's ability to compete), which maps to "acceptance of an invalid transaction" resulting in incorrect auction settlement (wrong/no winner is admitted despite a higher bid existing).

Because `maxBidPoolSize` is meant to be a finite operator-tunable bound (the flag exists specifically to bound memory/resource usage), any production deployment configuring it to a practical, finite value is exposed to this griefing pattern.

### Likelihood Explanation
Medium. The path requires cooperation of the `Auctioneer` service to countersign the low-value bids, which is a design assumption of the auction module (the Auctioneer is not intended to be a bid-quality/value gate—it exists to attest bid provenance/ordering per KIP-249). Since generating many searcher keys and bids of minimal positive value (e.g., `bid = 1`) is cheap and permissionless from the searcher side, and no code path evicts existing lower-value bids in the pool to make room for a strictly higher-value bid targeting a different transaction, exploitation is feasible whenever `maxBidPoolSize` is set to a bounded (non-default) value in production, which is the intended operational configuration.

### Recommendation
When `insertBid` finds the pool full (`len(bidMap) >= maxBidPoolSize`) and the incoming bid targets a new `(blockNumber, targetTxHash)` slot, instead of unconditionally rejecting with `ErrBidPoolFull`, compare the incoming bid's value against the globally lowest-value bid currently in the pool (maintained via a min-heap or similar structure keyed by `Bid`). If the incoming bid's value exceeds the lowest bid in the pool, evict the lowest bid and admit the new one; otherwise reject. This preserves the pool's capacity bound while ensuring the DoS/spam-with-low-value-entries pattern cannot crowd out legitimate higher-value bids.

### Proof of Concept
1. Operator runs a CN with `--auction.max-bid-pool-size=N` (a finite bound).
2. Attacker (through the cooperating/permissive Auctioneer flow) submits `N` `auction_submitBid` RPC calls, each from a distinct throw-away key, each with a distinct `targetTxHash` (e.g., self-crafted dummy target transactions), and each with `Bid = 1` (minimum positive value satisfying `validateBid` rule 3).
3. `insertBid` accepts all `N` bids because each occupies a new `(blockNumber, targetTxHash)` slot and `len(bidMap) < maxBidPoolSize` until the last one — see the capacity check at [6](#0-5) 
4. A legitimate searcher now submits a bid with `Bid = 1000` (far larger than any attacker bid) targeting their own real target transaction. Since this is a new `targetTxHash`/slot and `len(bidMap) >= maxBidPoolSize`, `insertBid` returns `auction.ErrBidPoolFull`, and `AddBid`/`SubmitBid` propagate this failure to the RPC caller — see [7](#0-6) [8](#0-7) 
5. The legitimate high-value bid never enters the bundle-building path (`GetTargetTxMap`) and never wins the auction for its target transaction, despite being economically superior to every bid already occupying the pool.

	hash, ok := bp.bidWinnerMap[bid.BlockNumber][bid.Sender]
	if !ok {
		return false
	}
	return !bid.Equals(bp.bidMap[hash])

## Bid pool validation rules

A bid pool is responsible for managing the valid bids from the `Auctioneer`. The bid must satisfy the following rules:

1. The `bid.Sender` must not be in the winner list of the same block number if the new bid doesn't have the same target block and hash as the previous bid.
2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
3. The `bid.Bid` must be greater than 0.
4. The `bid.Data` size must be less than or equal to `BidTxMaxDataSize`.
5. The `bid.CallGasLimit` must be less or equal to `BidTxMaxCallGasLimit`.
6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.

Please note that `Auctioneer` also validates the searcher's bid according to the KIP-249.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
