### Title
Silent block-rule bypass via malformed flow-style `conditions:` YAML in `Rule.from_dict` / `extract_frontmatter` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` treats the `conditions` frontmatter key and the legacy `pattern` key with different robustness guarantees. The hand-rolled YAML parser in `extract_frontmatter` only recognizes block-style (`- key: value`) lists; a flow-style list (`conditions: [{field: ..., operator: ..., pattern: ...}]`) is silently captured as a plain scalar string. Because `Rule.from_dict` only builds conditions `if isinstance(cond_list, list)` and only falls back to the legacy `pattern` field `if simple_pattern and not conditions` **and no `pattern` key is present**, a rule authored purely in the explicit "conditions" style with a flow-style list is loaded as `enabled=True`, `action='block'`, but with an empty `conditions` list — which `RuleEngine._rule_matches` treats as "never match" (`plugins/hookify/core/rule_engine.py:117-118`). The rule silently becomes a no-op while looking fully configured, unlike the always-robust legacy `pattern` form.

### Finding Description
- `extract_frontmatter` (`plugins/hookify/core/config_loader.py:106-195`) only enters "list mode" when a top-level key has an *empty* value followed by `- item` lines (`plugins/hookify/core/config_loader.py:140-153`). A single-line/flow-style YAML list such as `conditions: [{field: command, operator: regex_match, pattern: "rm -rf"}]` has a non-empty value on the same line, so it falls into the "simple key-value pair" branch (`plugins/hookify/core/config_loader.py:145-152`) and is stored as a raw string, not a `list`.
- `Rule.from_dict` (`plugins/hookify/core/config_loader.py:44-84`) does:
  ```python
  if 'conditions' in frontmatter:
      cond_list = frontmatter['conditions']
      if isinstance(cond_list, list):
          conditions = [Condition.from_dict(c) for c in cond_list]
  simple_pattern = frontmatter.get('pattern')
  if simple_pattern and not conditions:
      ...  # legacy fallback
  ``` [1](#0-0) 
  If the file only supplies `conditions:` (no `pattern:` key at all, which is normal for the "complex rule" style documented in `plugins/hookify/commands/hookify.md:108-124`), and that `conditions` value is mis-parsed into a string, `conditions` stays `[]` and there is no `pattern` to fall back to. `Rule.from_dict` still returns a fully-populated `Rule` with `enabled=True` and `action='block'`.
- `load_rule_file` treats this as a successful parse — no exception is raised, so no warning is printed (unlike malformed files that raise `ValueError/KeyError/AttributeError/TypeError`) (`plugins/hookify/core/config_loader.py:260-274`).
- In `RuleEngine._rule_matches`, `if not rule.conditions: return False` unconditionally (`plugins/hookify/core/rule_engine.py:117-118`), so this rule can never block or warn on anything, regardless of how dangerous the matching `tool_input`/`command`/`new_text` is.
- The legacy `pattern:` form has no equivalent failure mode: it is always a scalar (`frontmatter.get('pattern')`), so `extract_frontmatter`'s scalar branch reliably captures it, and `Rule.from_dict` always converts a non-empty `pattern` into exactly one working `Condition` (`plugins/hookify/core/config_loader.py:56-73`). This breaks the stated invariant that legacy and explicit rule forms must yield equivalent effective security semantics: an author (the LLM performing `/hookify` generation, or a repo-shipped `.claude/hookify.*.local.md` file) who writes the "complex/explicit" condition style with flow-style YAML gets a rule that is loaded, shown as enabled/active, but structurally inert.
- Reachability: `/hookify rule creation` (`plugins/hookify/commands/hookify.md`) explicitly documents and encourages the "conditions" list style for "more complex rules" (`plugins/hookify/commands/hookify.md:108-124`); nothing prevents the generating LLM (which can be steered by attacker-controlled repository/conversation content processed during `/hookify` generation) or a repo-shipped rule file from using flow-style YAML for that list, since the loader accepts and silently mis-parses it. There is no schema validation, no round-trip check, and no warning surfaced to the user that the resulting block rule has zero effective conditions.

### Impact Explanation
A rule that the user or team believes is actively blocking sensitive operations (e.g., blocking edits that write secrets/API keys to `.env`, or blocking `rm -rf`/exfiltration commands) can be rendered permanently inert by a single YAML formatting quirk introduced via `/hookify` generation or a repo-committed rule file, without any error surfaced. This directly enables the intended "block" protection to be silently bypassed, allowing sensitive code, prompts, tokens, diffs, or local files to reach an unintended sink (e.g., a `Write`/`Edit`/`Bash` action that the block rule was supposed to prevent) — matching the "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" impact category.

### Likelihood Explanation
- No special privilege is required: any content that can influence `/hookify` rule generation (conversation content, repo files analyzed by the conversation-analyzer agent) or any repo-shipped `.claude/hookify.*.local.md` file can trigger this.
- The explicit "conditions" style is the officially documented format for anything beyond a single-field/single-pattern rule (`plugins/hookify/commands/hookify.md:108-124`), so it is a normal, expected authoring path, not an edge case.
- The bug is deterministic and reproducible: any flow-style list under a top-level key with no matching `pattern:` fallback reproduces the same silent zero-condition rule.
- Because `load_rule_file` reports no warning/error for this case (unlike other malformed inputs), detection by the user is unlikely without directly inspecting the parsed `Rule` object.

### Recommendation
- Make `extract_frontmatter` reject or explicitly detect flow-style (`[...]`/`{...}`) YAML values for keys that are expected to be lists, either by supporting basic JSON/flow-style parsing or by raising a parse error instead of silently coercing to a scalar string.
- In `Rule.from_dict`, treat a non-list `conditions` value as a hard error (raise `ValueError`) rather than silently defaulting to an empty list, so `load_rule_file`'s existing `except (ValueError, KeyError, AttributeError, TypeError)` warning path fires.
- Add a validation step after `Rule.from_dict` that rejects/warns on any rule with `enabled=True` and zero effective `conditions` (dead rule), since such a rule can never fire regardless of `action`.
- Consider replacing the hand-rolled YAML parser with a real YAML library (`yaml.safe_load`) to eliminate this class of parser-divergence bugs entirely.

### Proof of Concept
Unit test plan against `plugins/hookify/core/config_loader.py`:
```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule
from plugins.hookify.core.rule_engine import RuleEngine

content = """---
name: block-env-leak
enabled: true
event: file
action: block
conditions: [{field: new_text, operator: contains, pattern: API_KEY}]
---

Blocked: attempted to write API_KEY to a file.
"""

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Expected (bug): conditions silently empty despite explicit intent
assert rule.action == 'block'
assert rule.enabled is True
assert rule.conditions == []  # BUG: should contain one Condition

engine = RuleEngine()
tool_input = {"tool_name": "Write", "tool_input": {"file_path": ".env", "content": "API_KEY=supersecret"}}
result = engine.evaluate_rules([rule], tool_input)
assert result == {}  # BUG: block rule never fires, secret write proceeds unblocked
```
Compare against the equivalent legacy form to demonstrate the differential:
```python
legacy_content = """---
name: block-env-leak-legacy
enabled: true
event: file
action: block
pattern: API_KEY
---

Blocked: attempted to write API_KEY to a file.
"""
fm2, msg2 = extract_frontmatter(legacy_content)
legacy_rule = Rule.from_dict(fm2, msg2)
assert len(legacy_rule.conditions) == 1  # legacy form works correctly
```
Expected assertion failure highlights the invariant violation: the "complex/explicit" form documented by `/hookify` silently loses its blocking capability while the legacy form remains functional for equivalent intent.
