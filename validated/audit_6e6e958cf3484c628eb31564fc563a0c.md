### Title
Unbounded/unchecked atom-length in `is_atom_canonical()` allows an attacker-controlled spend bundle to trigger an unhandled `IndexError` during mempool admission - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical()` on the raw, attacker-supplied `puzzle_reveal` and `solution` bytes of every coin spend in a submitted spend bundle, before any other structural validation of those buffers occurs. [1](#0-0)  `is_clvm_canonical()` walks the buffer atom-by-atom, delegating length-prefix decoding to `is_atom_canonical()`. [2](#0-1) 

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` decodes a variable-length size prefix (up to 5 extra bytes, encoding atom lengths up to ~2^40) and returns `1 + prefix_len + atom_len` as the total consumed length — but it never checks that `atom_len` bytes actually exist in `clvm_buffer` beyond the prefix. [3](#0-2)  The caller, `is_clvm_canonical()`, then does `offset += atom_len` and loops back to read `clvm_buffer[offset]` on the next iteration without any bounds check. [4](#0-3)  Because `atom_len` is attacker-controlled and can trivially exceed the buffer's actual length (e.g., a solution encoding a declared atom length far larger than the bytes actually present), `offset` becomes out-of-range and the subsequent `clvm_buffer[offset]` access raises an unhandled `IndexError`.

This mirrors the GIMP `read_channel_data()` root cause pattern: a length/size field parsed from untrusted input is used to compute a buffer-consumption size without validating it against the actual remaining buffer length, leading to an out-of-bounds access. In CPython, indexing a `bytes` object out of range raises `IndexError` rather than corrupting memory, so the direct memory-safety consequence from the GIMP CVE does not carry over — but the unchecked-length root cause and its DoS consequence do.

### Impact Explanation
`validate_spend_bundle()` is invoked directly from `MempoolManager.add_spend_bundle()`, which is the standard mempool-admission path reachable by any unprivileged spend-bundle submitter over RPC or peer protocol. [5](#0-4)  Neither `validate_spend_bundle()` nor `add_spend_bundle()` wraps the `is_clvm_canonical()` calls in a `try`/`except`, so an `IndexError` raised there propagates uncaught out of `add_spend_bundle()`. Depending on the caller context (e.g. within the full-node's mempool/blockchain-lock-protected request handling), this can abort processing of that call path, representing a spend-triggered transaction-processing halt for at least that request/coroutine. I was not able to fully trace every caller of `add_spend_bundle()` up through the RPC/peer message handlers within this session to confirm whether a top-level generic exception handler ultimately swallows it gracefully or whether it destabilizes the mempool lock/task — this should be verified with an end-to-end reproduction.

### Likelihood Explanation
Triggering this requires only crafting a single coin spend whose `puzzle_reveal` or `solution` CLVM byte stream contains an atom with a declared length prefix greater than the number of bytes actually following it in the buffer — a small, cheaply constructed encoding. Any wallet user, offer counterparty, or spend-bundle submitter can produce and submit such a bundle to a full node's mempool.

### Recommendation
In `is_atom_canonical()`, validate that `offset + prefix_len + atom_len <= len(clvm_buffer)` before returning, and have `is_clvm_canonical()` treat an out-of-bounds atom (or bounds violation encountered while decoding) as non-canonical (return `False`) rather than allowing the walk to proceed with an out-of-range offset. Additionally, wrap the `is_clvm_canonical()` calls in `validate_spend_bundle()` (or catch `IndexError` specifically) so malformed CLVM buffers fail cleanly with `Err.INVALID_COIN_SOLUTION` instead of raising an unhandled exception.

### Proof of Concept
Construct a `CoinSpend` whose `solution` bytes are a single large-length atom prefix with insufficient trailing data, e.g. a buffer consisting of the 5-byte-extension prefix `0xFC | (n>>40)` encoding a huge `atom_len` followed by only a handful of actual bytes (fewer than `atom_len`). Submit this via a `SpendBundle` to `MempoolManager.add_spend_bundle()`. Tracing through `is_clvm_canonical()` → `is_atom_canonical()` shows `offset` is advanced by the (unchecked) `atom_len` value; on the next loop iteration `clvm_buffer[offset]` accesses past the end of the buffer, raising `IndexError` instead of the expected `False`/`INVALID_COIN_SOLUTION` result. Existing tests such as `test_mempool_requires_canonical_clvm` in `chia/_tests/core/mempool/test_mempool_manager.py` exercise the canonical-length-prefix check with adjacent-but-valid data; a variant using a length prefix that exceeds the actual buffer size (rather than merely non-minimal) should be added to confirm the unhandled-exception behavior. def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
