### Title
SSRF via unvalidated on-chain DataLayer mirror URLs consumed by subscription fetch loop - (File: chia/data_layer/data_layer.py)

### Summary
Any wallet holder can create a "mirror" coin on chain for **any** DataLayer store (`launcher_id`), embedding arbitrary attacker-chosen URLs in the coin's memos via `DataLayerWallet.create_new_mirror()`. This function performs no ownership check on `launcher_id` and no validation of the `urls` parameter beyond basic encoding. Any node that later tracks/subscribes to that store id will ingest these URLs as legitimate "mirror servers" and periodically issue outbound HTTP GET/POST requests to them from `DataLayer.fetch_and_validate()` / `http_download()` / `get_downloader()` / `get_plugin_info()`, with no allow/deny-list for loopback, RFC1918/private ranges, link-local addresses, or cloud metadata endpoints (e.g. `169.254.169.254`).

### Finding Description
`create_new_mirror()` builds a standard coin spend whose memos are `[launcher_id, *urls]`, with `urls` supplied directly from the RPC caller and no checks that the caller owns `launcher_id` or that the URLs are well-formed/safe. [1](#0-0) 

When any node's wallet observes a coin sent to `create_mirror_puzzle().get_tree_hash()`, `DataLayerWallet.coin_added()` decodes the launcher id/URLs from the parent spend and, if that launcher is tracked, stores the mirror unconditionally in the local `dl_store`, with only an empty-URL-list check. [2](#0-1) 

The DataLayer service's periodic management loop calls `update_subscriptions_from_wallet()`, which reads these mirror URLs from wallet RPC and writes them straight into the local subscription server list with no URL validation (only `rstrip("/")`). [3](#0-2) 

Those server URLs are then used directly by `fetch_and_validate()` to build download targets and by `http_download()` to perform an `aiohttp` GET against `server_info.url + "/" + filename`, and by `get_downloader()`/`get_plugin_info()` to POST to plugin URLs — none of which restrict destination scheme, host, or IP range. [5](#0-4) [4](#0-3) 

This mirrors the KubeSphere CVE-2026-71208 pattern: a resource whose connection endpoint is supplied by an external, low-privileged actor (there, a Cluster CRD; here, an on-chain mirror coin memo) is consumed by a reconciliation-style loop that issues outbound requests with only URL-syntax parsing and no network-destination allow/deny-listing.

### Impact Explanation
A local/self-hosted or wallet-connected DataLayer node that subscribes to (or owns, since owned stores are pseudo-subscribed) a store id targeted by a malicious mirror will make outbound HTTP requests, on a recurring schedule (`manage_data_interval`), to attacker-chosen destinations. This enables SSRF against internal services, cloud metadata endpoints, or other network-restricted hosts reachable from the DataLayer process, without requiring any interaction beyond the victim node syncing the chain and tracking the targeted `launcher_id`. Confidentiality impact (e.g., leaking cloud credentials via metadata service, or probing internal network topology) is the primary concern, consistent with the CVSS vector's `C:H/I:N/A:N`.

### Likelihood Explanation
Creating a mirror coin only requires a small amount of XCH and no special permissions; `create_new_mirror()` performs no ownership check on `launcher_id`, so any wallet user can target any DataLayer store, including stores widely subscribed to by third parties. Since owned and subscribed stores are automatically synced by the periodic management loop, exploitation requires no user interaction on the victim side beyond normal DataLayer operation.

### Recommendation
Validate mirror and plugin URLs before use: enforce an allow-list of schemes (http/https only), resolve and reject destinations pointing to loopback, link-local (169.254.0.0/16, including 169.254.169.254), RFC1918 private ranges, and other non-routable/internal addresses, both at `add_mirror`/`create_new_mirror` time and again immediately before each outbound request in `http_download()`, `get_downloader()`, and `get_plugin_info()`, since DNS can change between validation and use (TOCTOU). Consider making this filtering configurable but secure-by-default, with an explicit opt-in for local/private mirrors in trusted deployments.

### Proof of Concept
1. Attacker wallet calls RPC `dl_new_mirror` (backed by `DataLayerWallet.create_new_mirror()`) with `launcher_id` set to a victim's DataLayer store id (obtained from any public offer/subscription) and `urls=["http://169.254.169.254/latest/meta-data/", "http://10.0.0.5:6379/"]`, paying a small fee. [1](#0-0) 
2. Once confirmed on chain, any node tracking that `launcher_id` (owner or subscriber) picks up the mirror via `coin_added()` and stores it. [2](#0-1) 
3. On the next `periodically_manage_data()` cycle, `update_subscription()` → `update_subscriptions_from_wallet()` copies the URLs into the local subscription table, and `fetch_and_validate()` → `http_download()` issues an outbound GET to `http://169.254.169.254/latest/meta-data/...` from the victim's DataLayer process. async def http_download(

    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
