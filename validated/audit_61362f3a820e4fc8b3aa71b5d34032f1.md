### Title
Coinbase outputs reported as spendable UTXOs, causing invalid spends and stuck multisig plans - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` returns `ReceivedOutput`s for coinbase transaction outputs with no maturity marker, even though Bitcoin consensus forbids spending coinbase outputs until they are 100 blocks deep. `ReceivedOutput` exposes only `offset`, `output`, and `outpoint`, so downstream code cannot distinguish an immature coinbase output from a normal spendable UTXO. Any miner can deliberately pay the multisig's Taproot script in their coinbase, injecting an unspendable-but-reported output into Serai's UTXO set.

### Finding Description
`scan_block` iterates over `block.txdata` including index 0 (the coinbase) and returns matching outputs as plain `ReceivedOutput`s [1](#0-0) . The accompanying comment acknowledges the issue but delegates filtering to an unnamed "post-processing pass" that is not part of the type [2](#0-1) . `ReceivedOutput` carries no `is_coinbase`/maturity field [3](#0-2) , and `scan_transaction`/`scan` provide no signal; the only way to detect maturity is to re-check whether the outpoint's txid equals `block.txdata[0]`, which the API does not expose.

This is the same class as the reference bug: a snapshot (scanned UTXO set) admits an item the protocol cannot actually act on, and the mismatch only surfaces later at spend/verification time. Downstream, the UTXO scheduler treats every reported output as immediately available input [4](#0-3) , and `TransactionSignMachine::sign` commits to `Prevouts::All(&self.tx.prevouts)` so the signed transaction unconditionally spends the immature coinbase [5](#0-4) .

### Impact Explanation
Once scheduled, the coinbase output is drained from `self.utxos` and bound into a signed plan transaction that is consensus-invalid for ~100 blocks. The transaction cannot be published/confirmed, so its Eventuality never resolves; the input is not restored to the scheduler (there is an explicit TODO noting inputs are never restored) [6](#0-5) . The result is funds reported received that are not spendable, plus a stalled plan that blocks the outputs bundled with it and can stall multisig retirement, which requires all Eventualities to resolve. Unlike the reference issue, no honest-vs-attacker discrimination is needed — the invalid output is accepted unconditionally.

### Likelihood Explanation
The attack requires mining a block containing a coinbase output paying Serai's script_pubkey, which any miner can do at the cost of normal block subsidy handling (they can pay Serai a dust amount). No Serai role, validator status, or threshold collusion is needed — the coinbase output is delivered via a public Bitcoin transaction, squarely within attacker-controlled inputs. While not continuously repeatable, each mined block is a fresh opportunity, and a mining pool could do this deliberately.

### Recommendation
Track coinbase status on `ReceivedOutput` (e.g., an `is_coinbase: bool` or store the block height/number), set it in `scan_block` for `txdata[0]`, and have the scheduler/consumer exclude such outputs until `current_height - coinbase_height >= 100`. Alternatively, change `scan_block` to skip `txdata[0]` and expose a separate `scan_coinbase` API so the default path is safe.

### Proof of Concept
1. A miner mines a Bitcoin block whose coinbase (`block.txdata[0]`) includes an output paying `ScriptBuf::new_p2tr_tweaked(multisig_key)` — the exact script `Scanner::scripts` keys on.
2. `Scanner::scan_block` returns it as a `ReceivedOutput` indistinguishable from a normal deposit; the processor records it and the scheduler places it in `self.utxos`.
3. On the next `schedule`, the coinbase output is selected into an aggregation/payment `Plan`; `TransactionSignMachine::sign` produces valid FROST signature shares committing to `Prevouts::All`, and `TransactionSignatureMachine` emits a fully signed transaction.
4. Bitcoin nodes reject the transaction (BIP-30/consensus coinbase maturity, COINBASE_MATURITY = 100). The signed Eventuality can never resolve, the plan is stuck, and the coinbase output plus all co-scheduled inputs remain out of the usable UTXO set until manual intervention — a repeat of this injects further immature outputs each time the attacker mines a block.
