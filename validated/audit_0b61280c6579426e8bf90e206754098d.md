## Analysis

The seed bug is a state-mutating function reachable by any caller because it has no restriction on `msg.sender`. Searching Hyperbridge's EVM contracts for the same class of defect (public entrypoint that should be gated to a specific trusted caller but isn't) surfaces `CallDispatcher.dispatch()`.

Every privileged mutator in the core protocol (`EvmHost.dispatchIncoming`, `storeStateMachineCommitment`, `recordEpoch`, `withdraw`, etc.) is wrapped in the `restrict(...)` modifier [1](#0-0) [2](#0-1) . The pallet-side privileged calls (`bandwidth`, `host-executive`, `relayer`) are all gated by `AdminOrigin`/`ensure_none` unsigned-with-signature checks [3](#0-2) [4](#0-3) . But `CallDispatcher.dispatch()`, the shared utility contract used by `IntentGatewayV2` (predispatch/postdispatch execution) and the Hyper Fungible Token apps for calldata execution, is fully public with no caller check at all:

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [5](#0-4) 

It also has a `receive()` to accept ETH [6](#0-5) . This is one shared, singleton deployment per chain, reused by `IntentGatewayV2` for predispatch/postdispatch calldata (tokens are transferred into it, then `dispatch()` is invoked, then remaining balance is swept back) [7](#0-6)  and by `HyperFungibleToken`/`WrappedHyperFungibleToken` for post-mint calldata execution, per the docs' own warning that "the dispatcher contract holds tokens temporarily during execution" [8](#0-7) .

### Title
`CallDispatcher.dispatch()` has no access control and drains any residual balance held by the shared dispatcher - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with no caller restriction, no `onlyGateway`/`restrict` modifier, and no check that the request originates from `IntentGatewayV2`, a `HyperFungibleToken`, or any other authorized app contract. Because `CallDispatcher` is deployed once and shared across every app that uses calldata execution (predispatch/postdispatch escrow flows, HFT mint-then-call flows), any ETH or ERC20 balance that is left sitting in this contract — even momentarily, or as leftover dust — is directly and permanently stealable by an unprivileged caller who simply calls `dispatch()` themselves with a `Call[]` that transfers the balance to an address they control.

### Finding Description
`CallDispatcher.dispatch()` executes an attacker-supplied array of `(to, value, data)` calls using the dispatcher's *own* balance (`to.call{value: call.value}(call.data)`), and the only check performed is that the target has code — there is zero authentication of `msg.sender`:

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
``` [5](#0-4) 

Compare this with every other state-mutating entrypoint in the codebase that touches funds or protocol state — `EvmHost` uses `restrict(_hostParams.handler)` / `restrict(_hostParams.hostManager)` on `dispatchIncoming`, `withdraw`, `storeStateMachineCommitment`, etc. [9](#0-8) [1](#0-0) , and every `HyperApp` callback is behind `onlyHost` [10](#0-9) . `CallDispatcher` is the one execution surface in the fund-movement path that received no equivalent `onlyGateway`/`restrict` guard — exactly the missing-access-control class described in the seed report.

Because `CallDispatcher` is a single shared deployment reused by `IntentGatewayV2` predispatch/postdispatch flows and by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution [11](#0-10) [12](#0-11) , tokens are routed *through* it as an intermediate holder before being swept back to the calling gateway:

```solidity
function _execute(Order calldata order, uint256 outputsLen) internal {
    ...
    ICallDispatcher(dispatcher).dispatch(order.output.call);
    // sweep remaining balances back to this contract
``` [13](#0-12) 

The docs explicitly acknowledge that unlimited approvals or fee-on-transfer/rounding behavior can leave non-zero balances sitting in the dispatcher ("Token approvals in the Call[] should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution") [8](#0-7) . Any such balance — dust left after an incomplete sweep, a lingering unlimited approval granted to `CallDispatcher` by a Call in one order's calldata, or plain native ETH sent via `receive()` — is not protected in any way: because `dispatch()` has no caller check, anyone can call `CallDispatcher.dispatch()` directly with `Call[]{to: token, data: transfer(attacker, balance)}` or `Call[]{to: attacker, value: address(this).balance}` to move that value out, with no relationship to the calling gateway, order, or user at all.

### Impact Explanation
This is unauthorized execution and theft of funds through a public entrypoint with a completely missing access-control check — the exact bug class of the seed report, mapped onto the one shared fund-holding utility contract in the Hyperbridge EVM stack that lacks the `restrict`/`onlyHost`/`onlyGateway` pattern used everywhere else. Any value that transiently or residually sits in `CallDispatcher` (native ETH or ERC20) is directly stealable by any unprivileged address.

### Likelihood Explanation
`dispatch()` is a plain `external` function with no modifier at all — the likelihood of exploitation depends only on whether/when the shared `CallDispatcher` instance holds a non-zero balance (via `receive()`, leftover approvals from prior `Call[]` batches, fee-on-transfer token remainders, or an incomplete sweep), a condition that is entirely plausible given the contract is shared across every order/app using calldata execution and the documentation itself calls out the residual-approval risk.

### Recommendation
Restrict `CallDispatcher.dispatch()` to the set of authorized caller contracts (e.g., pass the allowed gateway/app address(es) at construction and require `msg.sender == authorizedCaller`, mirroring the `restrict`/`onlyHost` pattern used elsewhere), or make `CallDispatcher` non-shared/ephemeral per call so it never has standing balance available to an unrelated caller.

### Proof of Concept
1. Any order/app flow (e.g. `IntentGatewayV2.placeOrder` predispatch, or an HFT `onAccept` with calldata) transfers tokens into the shared `CallDispatcher` and grants it an approval as part of the `Call[]` it executes, per [14](#0-13) .
2. If the sweep-back step does not fully recover balance (fee-on-transfer token, rounding, or a lingering unlimited `approve` granted to the dispatcher by prior calldata), `CallDispatcher` is left holding value.
3. An attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — no authorization check exists in [5](#0-4)  to prevent this — draining the token/ETH balance to the attacker's address.

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```

Orders support arbitrary calldata execution at two points in the lifecycle — before escrow (predispatch) and after fill (postdispatch). Both are executed through the `CallDispatcher` contract, which takes an ABI-encoded `Call[]` array:

```solidity
struct Call {
    address to;      // Target contract (must have code, reverts with NotContract otherwise)
    uint256 value;   // ETH to send with call
    bytes data;      // Calldata to execute
}
```

The `CallDispatcher` executes each call sequentially and reverts the entire batch if any call fails.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.
