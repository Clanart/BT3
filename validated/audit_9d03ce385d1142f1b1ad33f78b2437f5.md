## Analysis

The reported bug class — a low-level `call` that reports `success == true` for a non-existent (destructed) contract, causing the protocol to believe a transfer happened when it did not — has a direct local analog in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Title
Escrow release accepts destructed-token transfers as successful in Tron `IntentGatewayV2.withdraw` / `SweepDust` handler - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
Unlike the primary EVM `IntentGatewayV2` and `IntentsBase.sol`, which release escrow via OpenZeppelin `SafeERC20.safeTransfer` (which internally verifies the target has code before making the call), the Tron variant of `IntentGatewayV2` reimplements the transfer manually with a raw low-level `.call()` and only checks the boolean `success` flag, never checking that the token address has deployed code and never decoding/validating the ERC-20 return payload. ### Finding Description
Per EVM/Tron VM semantics (explicitly called out in the Solidity docs cited in the original report), a low-level `call` to an address with no deployed code returns `success == true` even though no code executed. `withdraw()` treats `success == true` as proof that `amount` tokens were actually transferred to `beneficiary`, and unconditionally decrements the escrow ledger `_orders[body.commitment][token] -= amount` and emits `EscrowReleased`/`EscrowRefunded`.

An order's escrowed `input` token address is chosen entirely by the order creator at `placeOrder`/`newOrder` time — the same actor controlling the token contract. Tron's VM (unlike post-Cancun EVM chains guarded by EIP-6780) still permits an ordinary `SELFDESTRUCT` at any point in a contract's lifetime, not only within its creating transaction. This lets a user:

1. Deploy their own conforming ERC-20 contract, use it as an order's escrowed input, and have the order successfully escrowed (the token functions correctly at escrow time, so `safeTransferFrom` on creation succeeds).
2. Wait for a solver to fill the order on the destination chain (the solver sends real output assets to the user).
3. Self-destruct the input token contract before/while the `RedeemEscrow` message (dispatched by the destination gateway after fill) is delivered back to the Tron source chain.
4. When `onAccept`/`withdraw` executes, `token.call(...)` against the now-destructed address returns `success == true` trivially. `TransferFailed` is never raised, escrow accounting is zeroed out, and `EscrowReleased` fires — but the solver receives nothing.

The solver has already paid out the order's outputs and is the rightful beneficiary of the escrowed input tokens; this path lets the order creator make the escrow release appear successful while permanently denying the solver its payment.

### Impact Explanation
This is a direct loss-of-funds vector for solvers filling intents through the Tron `IntentGatewayV2` deployment: the escrow is marked settled/released on-chain, the commitment is consumed (no re-claim possible since `_orders[...] -= amount` already occurred and `_filled` is set), yet the actual ERC-20 balance never moves to the beneficiary. This falls squarely within "stealing or loss of funds" / "false state acceptance" for intent settlement escrow.

### Likelihood Explanation
The attacker is the unprivileged order creator — no relayer, prover, or admin compromise is required. It relies only on the order creator's own token contract supporting self-destruct, which they fully control since they authored it, and on Tron's VM still allowing unrestricted `SELFDESTRUCT` (Tron has not adopted EIP-6780). No special timing beyond "solver fills, then attacker destructs the token before/around redeem delivery" is needed, and the relayer delivering the `RedeemEscrow` proof is a normal, honest participant — the false acceptance happens purely due to the missing existence/return-data check in `withdraw`.

### Recommendation
Bring the Tron `IntentGatewayV2` implementation in line with `IntentsBase.sol`/main EVM `IntentGatewayV2`: replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, which reverts when the target has no code (`AddressEmptyCode`) and validates the ERC-20 return payload, exactly like `IntentsBase.sol` does at: [3](#0-2) 

### Proof of Concept
1. On Tron, deploy a compliant ERC-20 `EvilToken`.
2. Call `newOrder`/`placeOrder` on the Tron `IntentGatewayV2`, escrowing `EvilToken` as an input asset; escrow succeeds via `safeTransferFrom`.
3. A solver fills the order on the destination chain, delivering the order's outputs to the user.
4. Before (or as) the destination gateway's `RedeemEscrow` POST is relayed back and processed by `onAccept`, call `selfdestruct` on `EvilToken`.
5. `withdraw()` executes: `token.call(...)` against the now-empty address returns `success == true`; `_orders[commitment][token]` is decremented, `EscrowReleased` fires, but the solver's balance of `EvilToken` never increases — funds are lost to the solver while the protocol records the escrow as settled.
