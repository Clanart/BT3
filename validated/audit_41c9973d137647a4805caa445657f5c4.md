### Title
Incorrect internal LP bookkeeping in `depositLP` allows over-minting of receipt tokens for fee-on-transfer/deflationary LP tokens - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.depositLP()` mints receipt tokens (and stakes into MasterWombat / triggers reward accounting) based on the nominal `_lpAmount` parameter rather than the amount actually received via `safeTransferFrom`, unlike the sibling `deposit()` function which correctly measures actual balance change.

### Finding Description
In `deposit()`, the contract measures LP tokens actually received before minting receipt tokens: [1](#0-0) 

By contrast, `depositLP()` transfers the LP token from the caller and then unconditionally uses the caller-supplied `_lpAmount` for both staking accounting and receipt-token minting, without checking the actual balance change on the contract: [2](#0-1) 

If `poolInfo.lpAddress` (the Wombat LP/asset token custodied by `WombatStaking`) is, or becomes (e.g. via upgrade, as noted in the referenced Sherlock finding regarding upgradeable tokens), a deflationary/fee-on-transfer token, `IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount)` will move less than `_lpAmount` tokens into the contract, but `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` still mints the full nominal amount of receipt tokens. This receipt token is staked 1:1 into MasterMagpie's emission and reward accounting via the pool helper contracts, so the discrepancy directly inflates the caller's claim on staking rewards and, upon withdrawal, on the underlying pooled assets, at the expense of other users of the pool.

### Impact Explanation
This is a direct analog of the Sherlock M-01 pattern: internal bookkeeping assumes the requested/transferred amount equals the amount actually received, without verifying it against a real balance diff. In `WombatStaking`, the receipt token minted from `depositLP` represents a claim on pooled LP assets and is used as the staking token in `MasterMagpie`/`BaseRewardPool` reward accounting. An inflated mint relative to actual LP custody understates the "backing" per receipt token, meaning later legitimate withdrawers/holders cannot be fully redeemed - i.e., protocol insolvency and theft of value from honest depositors, and a distortion of the reward emission share (over-rewarded yield to the attacker), which persists permanently once minted.

### Likelihood Explanation
This requires the pool's underlying LP token to have non-standard, balance-reducing transfer behavior (fee-on-transfer or rebasing/deflationary). Wombat LP/asset tokens are normally standard, non-fee ERC20s, so under the currently deployed token set this may not be triggerable. However, per the cited Sherlock precedent, this class of bug is rated at least medium risk because pool tokens can be upgradeable or a future/different LP-style pool could be onboarded with such semantics, and the code path itself (unlike `deposit()`) does nothing to defend against it, despite an available and already-used pattern (`beforeBalance`/`afterBalance` diff) directly adjacent in the same contract.

### Recommendation
In `depositLP()`, measure the actual LP balance received by the contract (before/after `safeTransferFrom`) and use that measured amount — not the caller-supplied `_lpAmount` — for `_toMasterWomAndSendReward` and for `IMintableERC20(poolInfo.receiptToken).mint(...)`, mirroring the pattern already used in `deposit()`.

### Proof of Concept
1. Assume/onboard a pool whose `lpAddress` implements a transfer fee (or an existing LP token is later upgraded to add one).
2. Attacker calls the pool helper's `depositLP(_lpAmount)`, which calls `WombatStaking.depositLP(lpToken, _lpAmount, attacker)`.
3. `IERC20(poolInfo.lpAddress).safeTransferFrom(attacker, address(this), _lpAmount)` results in the contract receiving `_lpAmount - fee` tokens.
4. `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` and `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` both use the full nominal `_lpAmount`, over-crediting the attacker's receipt-token balance and reward-eligible stake relative to the LP tokens actually custodied.
5. The attacker can later withdraw/burn receipt tokens and claim rewards proportional to the inflated amount, draining value that should belong to other depositors. [2](#0-1)

        address _lpAddress,
        uint256 _lpAmount,
        address _for
    ) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {
        // Get information of the Pool of the token
        Pool storage poolInfo = pools[_lpAddress];

        // Transfer lp to this contract and stake it to wombat
        IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);

        IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);

        emit NewLPDeposit(_for, poolInfo.lpAddress, _lpAmount, poolInfo.receiptToken, _lpAmount);
    }
