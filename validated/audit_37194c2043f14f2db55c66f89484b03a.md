This confirms the mechanism: `get_payout_txs_for_withdrawal_utxos` and `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) key off *whichever* `spending_txid` in `bitcoin_syncer_spent_utxos` actually matches `w.withdrawal_utxo_txid`/`w.withdrawal_utxo_vout` — this is populated generically by `save_transaction_spent_utxos` (`core/src/bitcoin_syncer.rs:143-164`) for **any** transaction that spends that outpoint, with no requirement that it be the operator's own previously-broadcast payout tx. The OP_RETURN's `operator_xonly_pk` is extracted from whatever tx wins that race and stored permanently via `update_payout_txs_and_payer_operator_xonly_pk`. [1](#0-0) 

The withdrawal signature is enforced to use `TapSighashType::SinglePlusAnyoneCanPay`, which per BIP-341/342 signs only input 0's outpoint/amount/script and the single corresponding output (output index 0 — the user's payout amount/address), leaving the anchor output and OP_RETURN output completely unsigned and thus freely rewritable by anyone who has seen the signature (e.g., in the operator's broadcast/mempool payout tx, which is public). [2](#0-1) [3](#0-2) 

`verify_storage_proofs` (`circuits-lib/src/bridge_circuit/storage_proof.rs:44-133`) only recovers the dust-UTXO outpoint/vout that was registered at withdrawal time on Citrea — a value fixed regardless of which specific Bitcoin transaction ultimately spends it — and `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:186-204`) only checks that this outpoint/vout equals `payout_spv.transaction.input[payout_input_index].previous_output`. This check is satisfied by *any* transaction spending that outpoint, honest or attacker-crafted, since the previous_output reference is identical by construction. [4](#0-3) 

`update_finalized_payouts` then blindly trusts whichever tx confirmed and extracts `operator_xonly_pk` from its OP_RETURN, permanently recording it in the `withdrawals` table via `update_payout_txs_and_payer_operator_xonly_pk`. Later, `is_kickoff_malicious` (`core/src/verifier.rs:1857-1914`) compares the honest operator's kickoff against this DB-recorded value and flags the honest operator's kickoff as malicious if it doesn't match, which blocks its Reimburse and can lead to a Disprove/challenge burning its collateral. [5](#0-4) 

### Title
Front-runnable payout OP_RETURN under `SinglePlusAnyoneCanPay` lets an attacker hijack payer credit for a withdrawal UTXO - (File: core/src/bitcoin_syncer.rs, core/src/verifier.rs, circuits-lib/src/bridge_circuit/storage_proof.rs)

### Summary
The withdrawal signature enforced by `parse_withdrawal_sig_params` uses `TapSighashType::SinglePlusAnyoneCanPay`, which signs only input 0 and output 0, leaving the payout tx's OP_RETURN (containing `operator_xonlypk`) completely unsigned and mutable by anyone who observes the signature in a broadcast/mempool tx. `verify_storage_proofs` and the bridge circuit's binding checks only validate that the payout tx's input matches the Citrea-registered withdrawal outpoint/vout — not that it's the specific tx the honest operator broadcast — so any competing transaction spending that same outpoint with a rewritten OP_RETURN can win the on-chain race and get permanently recorded as the payout's payer.

### Finding Description
The claimed binding — "the transaction whose `WithdrawalOutpointTxid`+`vout` `verify_storage_proofs` recovers == the transaction whose OP_RETURN `operator_xonlypk` is used in `deposit_constant`, for the SAME payer" — does not actually hold, because:

1. `parse_withdrawal_sig_params` enforces `SinglePlusAnyoneCanPay` [6](#0-5) , meaning the withdrawal signature never covers the OP_RETURN output (`op_return_txout` is appended after the user payout output and anchor output in `create_payout_txhandler` [7](#0-6) ).
2. `verify_storage_proofs` returns only the registered dust UTXO (`WithdrawalOutpointTxid`, `vout`) tied to the Citrea withdrawal record, which is fixed independent of which Bitcoin transaction ultimately spends it [8](#0-7) , and `bridge_circuit` only checks equality of that outpoint/vout against `payout_spv.transaction.input[payout_input_index].previous_output` [3](#0-2) .
3. On the host side, `save_transaction_spent_utxos` in the bitcoin syncer records the outpoint-spend generically for *whichever* transaction confirms [9](#0-8) , and `get_payout_txs_for_withdrawal_utxos` / `update_finalized_payouts` picks up that transaction's OP_RETURN, parsing whatever `operator_xonly_pk` it contains and storing it permanently [10](#0-9) .

Exploit flow: the honest operator broadcasts (or RBF-funds via `fund_raw_transaction`) a payout tx spending the user's withdrawal dust UTXO, signed under `in_signature.sighash_type == SinglePlusAnyoneCanPay` [11](#0-10) . Because this tx is broadcast to the public mempool before confirmation, an attacker observing it can extract the same valid `taproot::Signature` (which only commits to input 0 + output 0), and construct a variant transaction with the identical input0/output0 but a rewritten OP_RETURN (e.g. garbage bytes, or another operator's pubkey), attaching a higher fee to win the race for confirmation. Since neither the storage proof nor the SPV proof binds to the operator's originally-intended txid, the attacker's variant — once mined — becomes the canonical spend of that outpoint. `update_finalized_payouts` then records the attacker-chosen (or invalid) `operator_xonly_pk` for that withdrawal, and `is_kickoff_malicious` subsequently flags the honest operator's kickoff as malicious because it no longer matches the DB-recorded payer [12](#0-11) , permanently blocking that operator's Reimburse via that kickoff (and potentially exposing it to a Disprove/challenge that burns collateral).

### Impact Explanation
The honest operator who genuinely fronted the withdrawal in BTC is permanently prevented from having their `operator_xonly_pk` bound in any accepted bridge-circuit proof for that withdrawal, since the withdrawal UTXO is now spent by the attacker's variant tx and cannot be re-spent. This is a "false claim proved (or a true claim made unprovable)" / "honest operator permanently unable to be reimbursed" critical-category impact. It is repeatable against any withdrawal for which an operator has broadcast (or is about to broadcast) a payout tx before it reaches sufficient confirmations, across any deposit/operator pairing, since the flaw is structural (sighash design + generic outpoint-spend tracking) rather than tied to specific keys or configuration.

### Likelihood Explanation
Preconditions: attacker must observe the honest operator's payout tx in the mempool (public data) before it confirms, and must be able to get a competing spend of the same outpoint mined first — feasible via a higher-fee replacement given `fund_raw_transaction`/RBF is already used by operators themselves [13](#0-12) . No privileged access, key compromise, or majority hashrate is required — only fee-paying capability, which matches the unprivileged threat model. This is a real, demonstrable race condition inherent to the protocol's chosen sighash flag and generic outpoint-based payout tracking, not a theoretical concern.

### Recommendation
Bind the payout tx's identity (not just its spent input) into the withdrawal registration/verification path — e.g., require the withdrawal signature to cover the OP_RETURN output as well (drop `SinglePlusAnyoneCanPay` in favor of a sighash that commits to all outputs, or add a second signature/commitment specifically over the operator pubkey output), or have operators pre-register their intended payout txid/OP_RETURN with the aggregator/verifiers before broadcast so `update_finalized_payouts` can reject a canonical spend whose OP_RETURN doesn't match the pre-registered commitment for that withdrawal.

### Proof of Concept
`cargo test` plan (circuits-lib + core integration):
1. In `circuits-lib`, construct two payout transactions, `honest_tx` and `attacker_tx`, both spending the same `input[0].previous_output` (the withdrawal dust UTXO) and with identical `output[0]` (user payout amount/script), but with differing OP_RETURN outputs (`honest_op_xonlypk` vs `attacker_chosen_bytes`). Sign both inputs with the *same* `SinglePlusAnyoneCanPay` signature (reuse is valid since only input0+output0 are covered) and assert both signatures verify via `SECP.verify_schnorr` against the recovered sighash for each tx.
2. pub fn verify_storage_proofs(
    storage_proof: &StorageProof,
    state_root: [u8; 32],
) -> (WithdrawalOutpointTxid, u32, MoveTxid) {
    let utxo_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_utxo)
            .expect("Failed to deserialize UTXO storage proof");

    let vout_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_vout)
            .expect("Failed to deserialize vout storage proof");

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_deposit_txid)
            .expect("Failed to deserialize deposit storage proof");

    let storage_address: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(UTXOS_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let storage_key_utxo: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2);

    let storage_key_vout: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2 + 1);

    let storage_address_deposit: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(DEPOSIT_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let deposit_storage_key: alloy_primitives::Uint<256, 4> =
        storage_address_deposit + U256::from(storage_proof.index);

    let deposit_storage_key_bytes = deposit_storage_key.to_be_bytes::<32>();

    if deposit_storage_key_bytes != deposit_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid deposit storage key. left: {:?} right: {:?}",
            deposit_storage_key_bytes,
            deposit_storage_proof.key.as_b256().0
        );
    }

    if storage_key_utxo.to_be_bytes() != utxo_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal UTXO storage key. left: {:?} right: {:?}",
            storage_key_utxo.to_be_bytes::<32>(),
            utxo_storage_proof.key.as_b256().0
        );
    }

    if storage_key_vout.to_be_bytes() != vout_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal vout storage key. left: {:?} right: {:?}",
            storage_key_vout.to_be_bytes::<32>(),
            vout_storage_proof.key.as_b256().0
        );
    }

    storage_verify(&utxo_storage_proof, state_root);

    storage_verify(&deposit_storage_proof, state_root);

    storage_verify(&vout_storage_proof, state_root);

    let buf: [u8; 32] = vout_storage_proof.value.to_be_bytes();

    // ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract
    let vout = u32::from_le_bytes(
        buf[28..32]
            .try_into()
            .expect("Vout value conversion failed"),
    );

    let wd_outpoint = WithdrawalOutpointTxid(utxo_storage_proof.value.to_be_bytes());

    let move_txid = MoveTxid(deposit_storage_proof.value.to_be_bytes());

    (wd_outpoint, vout, move_txid)
}
