Based on my investigation, I found a strong analog in the Alpenglow VAT (Validator Admission Ticket) burn logic in Agave.

### Title
Vote account balance TOCTOU in VAT burn causes validator panic - ([File: runtime/src/bank.rs])

### Summary
`Bank::maybe_burn_vat_from_staked_accounts` assumes that vote accounts selected by `clone_and_filter_for_vat` (filtered for having "non-zero stake and sufficient balance" as of epoch-stakes snapshot time) still hold enough lamports to cover `vat_to_burn_per_epoch` when the burn is actually executed. But the function fetches the *live* current balance via `self.get_account(vote_pubkey)` rather than the balance that was validated at filter time, and subtracts unconditionally with `.expect(...)`. [1](#0-0) 

### Finding Description
`maybe_burn_vat_from_staked_accounts` iterates the vote accounts recorded in `epoch_stakes` (a point-in-time snapshot taken during epoch-boundary processing) and, for each, fetches the corresponding account's *current* lamports from the bank at burn time: [2](#0-1) 

The comment explicitly documents the invariant the code relies on: "Vote accounts have already been filtered by `clone_and_filter_for_vat` to only include accounts with non-zero stake and sufficient balance," and the `.expect(...)` message states "Vote accounts should have already been filtered to contain enough balance for the VAT" [3](#0-2) .

This is the exact broken-invariant pattern from the external report: a critical-path balance check is satisfied at one point in time (filtering/snapshot), but the value actually consumed at execution time is the live, mutable account balance, which can be changed by an ordinary, unprivileged actor in between. Vote account withdrawals are performed via the vote program's `Withdraw` instruction, which any account with the `authorized_withdrawer` key can invoke to reduce the vote account's lamports down to the rent-exempt minimum (or to zero, closing/deinitializing the account) [4](#0-3) . A validator operator (who legitimately controls their own vote account's withdraw authority) is not a "malicious peer/node" in the sense excluded by scope — this is a standard, permitted, unprivileged transaction — but it can drive the vote account's balance below `vat_to_burn_per_epoch` after the epoch-stakes snapshot was taken and before the corresponding VAT burn executes for that epoch.

When that happens, `account.lamports().checked_sub(vat_to_burn_per_epoch)` returns `None`, and the code unconditionally unwraps it with `.expect(...)`, panicking the node [5](#0-4) . Because this runs inside bank processing at the epoch boundary (a required, non-optional step for every validator that reaches this slot when Alpenglow is enabled), a panic here is not an isolated node crash — it manifests deterministically for every validator that processes that slot, i.e., a consensus-wide halt rather than a single-node failure.

The existing "guard" — `clone_and_filter_for_vat`'s balance filtering — does not stop this path because it only checks balances at snapshot time, not at burn time; there is a time-of-check/time-of-use (TOCTOU) gap between when `epoch_stakes` is computed and when `maybe_burn_vat_from_staked_accounts` actually executes and reads live balances.

### Impact Explanation
A panic inside bank processing during epoch-boundary handling that is reached by all validators processing the affected slot constitutes a consensus halt / liveness failure of the cluster (every validator running this code crashes deterministically on the same slot), which is one of the explicitly in-scope impacts (consensus halt / non-RPC crash caused by an unprivileged actor's ordinary transaction). This is a native, protocol-level DoS vector, distinct from any malicious-validator or gossip assumption.

### Likelihood Explanation
Any account holding a vote account with an authorized-withdrawer key it controls can trigger this: withdraw enough lamports from its own vote account (down to the rent-exempt minimum) after being included in a filtered VAT-eligible snapshot but before the burn is applied for that epoch. Because `vat_to_burn_per_epoch` and the VAT admission threshold are protocol-fixed quantities and the withdraw instruction is a normal, permissionless vote-program operation available to any vote-account withdraw authority, the timing window (between epoch-stakes computation and the burn step within the same or a following slot) is realistically exploitable without any privileged or malicious-network assumptions.

### Recommendation
- Re-validate/clamp the balance at burn time instead of relying on the earlier filter: use `saturating_sub` (burning at most what is available, or skipping accounts that no longer qualify) rather than `checked_sub().expect(...)`.
- Alternatively, snapshot and burn against the same balance value used for the eligibility filter (e.g., store the filtered balance alongside `epoch_stakes` and use it directly) rather than re-reading a possibly-changed live account balance.
- Add adversarial test coverage that withdraws from a VAT-eligible vote account between epoch-stakes computation and VAT burn execution to ensure the code path can never panic.

### Proof of Concept
1. Attacker controls a vote account `V` that is included in the epoch's `VersionedEpochStakes` after passing `clone_and_filter_for_vat`'s balance/stake filter (i.e., `V`'s balance ≥ threshold that included `vat_to_burn_per_epoch` headroom at snapshot time).
2. Before the bank reaches the slot that executes `maybe_burn_vat_from_staked_accounts` for that epoch, the attacker (as `V`'s `authorized_withdrawer`) submits an ordinary `VoteInstruction::Withdraw` transaction, withdrawing lamports down to (or near) the rent-exempt minimum via `withdraw()` in `programs/vote/src/vote_state/mod.rs` [6](#0-5) .
3. When `maybe_burn_vat_from_staked_accounts` runs, it fetches `V`'s now-reduced live balance and computes `account.lamports().checked_sub(vat_to_burn_per_epoch)`, which is `None` [7](#0-6) .
4. The `.expect(...)` panics, crashing every validator that processes this slot under the Alpenglow feature — a cluster-wide consensus halt caused entirely by an unprivileged vote-account owner's normal transaction.

Note: I was unable to fully trace `clone_and_filter_for_vat`'s exact filtering threshold/timing relative to `maybe_burn_vat_from_staked_accounts`'s invocation point within the same slot pipeline due to tool-call limits reached before completing that read; a background Devin session with full file access would be needed to confirm the exact snapshot-to-burn timing window and whether any additional re-check exists elsewhere in the call chain (e.g., in `runtime/src/alpenglow_epoch_type.rs` or `runtime/src/slot_params.rs`, which also reference `vat_to_burn_per_epoch`).

/// Withdraw funds from the vote account
pub fn withdraw<S: std::hash::BuildHasher>(
    instruction_context: &InstructionContext,
    vote_account_index: IndexOfAccount,
    target_version: VoteStateTargetVersion,
    lamports: u64,
    to_account_index: IndexOfAccount,
    signers: &HashSet<Pubkey, S>,
    rent_sysvar: &Rent,
    clock: &Clock,
) -> Result<(), InstructionError> {
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;
    let vote_state = get_vote_state_handler_checked(&vote_account, target_version)?;

    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let remaining_balance = vote_account
        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }

    vote_account.checked_sub_lamports(lamports)?;
    drop(vote_account);
    let mut to_account = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to_account.checked_add_lamports(lamports)?;
    Ok(())
