## Title
Copilot conflict-resolution can silently drop entire unresolved conflict hunks into a clean-looking commit when hunk-index bookkeeping outruns the model's per-hunk resolution list - (File: `app/src/lib/copilot-conflict-resolution.ts`)

## Summary
`reassembleResolvedFile` splices Copilot's per-hunk `resolvedContent` back into a conflicted file by walking marker blocks and consuming one entry from `hunkResolutions` per block found. The bug-class from the report — a guard (`amount > 0` / `if (hunkIndex < hunkResolutions.length)`) that gates whether a value is used, but whose *false* branch silently discards data instead of failing loudly — is reproduced here.

## Finding Description
In `reassembleResolvedFile`, each `<<<<<<<`…`>>>>>>>` block found in `rawContent` is matched positionally (by `hunkIndex`, not by content) against `hunkResolutions[hunkIndex]`: [1](#0-0) 

```
// Splice in the resolved content for this hunk
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  if (resolved.length > 0) {
    resultLines.push(...resolved.split(/\r?\n/))
  }
}
hunkIndex++
```

If the raw file on disk contains *more* well-formed conflict blocks than there are entries in `hunkResolutions`, the `if (hunkIndex < hunkResolutions.length)` guard is false for the extra blocks, and the code falls through: nothing is pushed for that block at all (not the original conflict markers, not an error, not even a warning) — the entire hunk (both "ours" and "theirs" content) vanishes from the reassembled file. This mirrors the Party bug: a bounds/zero check silently short-circuits the intended validation/error path instead of surfacing the mismatch, causing a loss of user content.

The upstream guard `validateResolutionPaths` only compares hunk *counts* between the model's raw response and the hunk count recorded in `IFileConflictContext` at context-gathering time: [2](#0-1) 

It does **not** re-derive the hunk count from `ctx.rawContent` (the actual bytes later fed into `reassembleResolvedFile`) — it trusts whatever hunk count was recorded earlier when the conflict context was built. `reassembleResolutions` then passes `ctx.rawContent` and `raw.hunks` straight into `reassembleResolvedFile`: [3](#0-2) 

Any skew between the hunk count used for validation and the hunk count `reassembleResolvedFile` actually encounters in `rawContent` — e.g., the working-directory conflicted file being re-written by a concurrent `git` operation, a hook, or an attacker-controlled merge driver between the time `IFileConflictContext` was captured and the time the user clicks "Continue Merge" — results in this silent drop, not a `CopilotValidationError`.

The reassembled content is then written verbatim to disk and staged without any post-hoc "does this file still contain unresolved markers / did content shrink unexpectedly" check: [4](#0-3) 

The only other safety net (`hasUnresolvedConflicts` re-check) only fires when the user manually resolved the file externally — it doesn't protect against `hunkResolutions` being too short relative to the disk content.

## Impact Explanation
This falls squarely in the requested threat model: the content of a fetched/merged remote branch (attacker-controlled) drives conflict-block counts, and Copilot's structured output is model-generated/untrusted data being spliced back into the user's tree. If the number of on-disk conflict blocks exceeds the model's returned `hunks` array for that file (or if a legitimate re-parse mismatch occurs), the affected hunk(s) — including the user's own "ours" changes and the incoming "theirs" changes — are deleted from the file with no error, no warning to the user, and no marker left behind. The file is then `git add`ed and can be committed and pushed with silently missing code, which is exactly the "silent corruption of what the user commits or pushes" impact category.

## Likelihood Explanation
Likelihood is moderate: it depends on `hunks.length` diverging from the actual marker-block count in `rawContent` at reassembly time, which the current validation does not explicitly re-verify against the bytes used for splicing (it trusts an earlier count). There is a time-of-check/time-of-use gap between building `IFileConflictContext` and calling `_applyCopilotConflictResolutions`, and the code path silently tolerates the mismatch rather than throwing, so any condition that causes this divergence (model returning fewer hunks than markers, or the working tree changing between context capture and apply) reaches this silent-drop branch instead of a `CopilotValidationError`.

## Recommendation
In `reassembleResolvedFile`, treat `hunkIndex >= hunkResolutions.length` as a hard error (throw `CopilotValidationError`) rather than silently skipping the block, mirroring how malformed markers are already handled defensively. Additionally, `validateResolutionPaths` (or a new check just before reassembly) should recompute the expected hunk count directly from `ctx.rawContent` at apply time, not only from the hunk count captured earlier in `IFileConflictContext`, to close the TOCTOU gap.

## Proof of Concept
1. Start a merge/rebase/cherry-pick against an attacker-controlled remote branch that introduces `N` conflict markers in `file.ts`.
2. `IFileConflictContext` for `file.ts` is built with `hunks.length === N`, and Copilot is prompted; suppose it returns a valid response with `N` hunk resolutions matching that count (passes `validateResolutionPaths`).
3. Before the user clicks "Continue Merge" (i.e., before `_applyCopilotConflictResolutions` runs), the on-disk conflicted file gains one additional conflict block relative to what was captured — e.g., a concurrent `git` fetch/checkout, a background auto-merge tool, or another process rewrites the working-directory copy of `file.ts` to have `N+1` markers, while the cached `IFileConflictContext`/`copilotResolutions` state used by `_applyCopilotConflictResolutions` still reflects the original `N`-hunk resolution.
4. `_applyCopilotConflictResolutions` reads `ctx.rawContent`/on-disk content with `N+1` blocks but only has `N` `hunkResolutions`; `reassembleResolvedFile` walks the `N+1`th block, hits `hunkIndex (N) < hunkResolutions.length (N)` → false, and drops that entire block silently.
5. The reassembled file — missing the last conflict's code entirely, without any conflict markers or comment — is written to disk via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged with `git add`, then committed/pushed by the user without their knowledge.

Note: I was not able to fully trace every caller that could produce this TOCTOU window (e.g., exact conditions that could cause the working-directory conflicted file to change between context capture and apply) within the available index; a Devin session with full repo/terminal access would be needed to confirm the exact reachable trigger and reproduce it end-to-end.
