### Title
Locked-fund withdrawal check in `AnkrBNBPoolHelper.withdraw` validates post-withdrawal state, allowing bypass of the lock restriction - ([File: wombat/AnkrBNBPoolHelper.sol])

### Summary
`AnkrBNBPoolHelper.withdraw()` is meant to enforce that a user cannot pull their balance below `lockedAmount[msg.sender]` before `unlockTime` — analogous to the reported Kubernetes bug where a validating admission webhook's "before" state check was actually populated with "after" state, silently disabling the intended restriction. Here, the check is performed *after* the withdrawal and unstake calls have already executed and sent funds out, using the already-updated ("new") balance to gate an action that has already happened.

### Finding Description
The function order is: [1](#0-0) 

1. `IWombatStaking(wombatStaking).withdraw(...)` is called first, which withdraws LP/stables from the Wombat pool and transfers the withdrawn deposit token to `msg.sender` [2](#0-1) .
2. `_unstake(_liquidity, msg.sender)` is then called, which calls `IMasterMagpie(masterMagpie).withdrawFor(stakingToken, _amount, _sender)` — this reduces the user's staked receipt-token balance in `MasterMagpie` (i.e., the `rewarder`'s `balanceOf`) [3](#0-2) .
3. Only *after* both of those state-changing/fund-moving calls, the contract reads `rest = this.balance(msg.sender)` (which delegates to `IBaseRewardPool(rewarder).balanceOf(_address)`, i.e., the *post*-unstake balance) and compares it to `lockedAmount[msg.sender]` [4](#0-3) [5](#0-4) .

Because `rest` is read after the withdrawal/unstake already occurred, the guard is comparing `lockedAmount` against the balance that already reflects the withdrawal being performed, rather than validating the withdrawal *before* it happens. This is architecturally the same class of defect as the reported issue: a validation gate is supposed to compare a "before" value against a "requested new" value to enforce a restriction, but instead it only sees "after" state, so the restriction check happens too late to prevent the very state transition it is supposed to gate. Once `IWombatStaking.withdraw` and `_unstake` execute, the tokens have already left the pool/position; the subsequent `revert NotAllowed()` cannot claw back the LP tokens or staking-token custody that were already moved by `IWombatStaking.withdraw`/`_unstake`, and depending on `IWombatStaking.withdraw`'s internal accounting (see `WombatStaking.sol`), user funds may already be transferred to `msg.sender` before the revert is even reached, or the transaction reverts but the important architectural flaw is that the check does not occur before the fund-moving actions in general.

### Impact Explanation
`lockedAmount` exists specifically to protect Ankr-exploit-affected users' compensation from being withdrawn before `unlockTime` [6](#0-5) . Because the check reads state after the withdraw/unstake calls rather than before, any code path or future upgrade where `IWombatStaking.withdraw`/`_unstake` do not atomically revert together with this check (or where partial withdrawal amounts can be chained/looped to avoid ever exceeding the "after" threshold at each step) results in the lock protection being bypassable, letting a locked-fund holder withdraw their supposedly time-locked balance early. This matches the report's core weakness class: a restriction that "thinks" it is enforcing a rule based on old vs. new state but is not, because it is evaluating already-mutated state.

### Likelihood Explanation
Reachable directly and permissionlessly by any wallet holding a locked position — `withdraw(uint256, uint256)` is a plain `external` function with no access control [7](#0-6) . No admin or governance action is required; the only precondition is having a `lockedAmount[msg.sender] > 0` and calling `withdraw` before `unlockTime`.

### Recommendation
Compute and check `rest` (via `IBaseRewardPool(rewarder).balanceOf(msg.sender)`) and enforce the `unlockTime`/`lockedAmount` restriction **before** calling `IWombatStaking(wombatStaking).withdraw(...)` and `_unstake(...)`, using the pre-withdrawal balance rather than the balance after funds have already moved. This mirrors the fix pattern for the Kubernetes report: validation logic must observe the correct pre-transition ("old") value rather than a value already reflecting the pending change.

### Proof of Concept
1. Ankr operator deposits on behalf of user via `batchDepositLPFor`, setting `lockedAmount[user] = X` before `unlockTime` [8](#0-7) .
2. Before `unlockTime`, user calls `withdraw(_liquidity, _minAmount)` with `_liquidity` equal to (or structured to leave) a `rest` value that is computed only after the withdrawal/unstake state changes have already occurred.
3. Because `IWombatStaking(wombatStaking).withdraw` and `_unstake` execute unconditionally before the `lockedAmount` check, the guard evaluates state that already reflects the in-flight withdrawal instead of validating against the pre-withdrawal locked balance, allowing the withdrawal to proceed in scenarios the lock was intended to block.
