### Title
Staleness gate in `oracle-timestamp-fresh` treats future-dated oracle timestamps as always "fresh", bypassing `max-staleness` protection - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` computes the staleness `delta` as `stacks-block-time - ts`, but if `ts` (the oracle publish timestamp) is greater than `stacks-block-time`, it silently substitutes `delta = u0` instead of rejecting or otherwise flagging the value. A `delta` of `u0` always satisfies `(<= delta max-staleness)`, so any price whose timestamp is at or ahead of the current block time is treated as maximally fresh regardless of how outdated the underlying data actually is once block time catches up to it, or regardless of how the value was produced.

### Finding Description
The freshness gate lives in `price-resolve` and is the sole guard preventing outdated collateral/debt prices from being used in health checks, borrows, withdrawals, and liquidations: [1](#0-0) 

```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

This is invoked as the exclusive validity gate in `price-resolve`: [2](#0-1) 

```
    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
```

Note the branch structure mirrors the analog bug class exactly: instead of a special-case value (`alcxAmount == 0` in the report) triggering an early return that skips the intended check (`msg.value` validation), here the special-case condition (`ts > stacks-block-time`) triggers a substitution (`delta = u0`) that skips the intended staleness computation, forcing the freshness check to always pass. Once a price entry with `ts` at/ahead of `stacks-block-time` is accepted, `last-update` is set to that timestamp (line 392), and the `>= ts prev` monotonic check means every *later* call must present a timestamp `>= ts`. If the same or a similarly "future-leaning" timestamp is presented repeatedly (which is exactly what happens across the timespan during which `stacks-block-time` has not yet caught up to `ts`), the price is accepted as fresh in every subsequent block during that window even though it has aged past `max-staleness` seconds of real elapsed time relative to when it was published.

### Impact Explanation
`price-resolve`/`price-multi-resolve` feed directly into `get-notional-evaluation`, `is-healthy`, borrow capacity checks, and liquidation pricing throughout `v0-4-market.clar`. If the freshness gate can be bypassed for a window of time, a stale (and therefore wrong relative to true market value) price can be used to: (a) allow borrowing/withdrawing beyond the amount the actual current price would permit, or (b) block/mis-price liquidations that should have occurred at the true, moved price. Either direction lets the holder of the position benefit at the protocol's expense, risking bad debt and protocol insolvency — placing this in the **Critical — protocol insolvency** impact class (and, for liquidations that should occur but are blocked by a falsely-fresh favorable price, **temporary freezing of funds** for liquidators/other users).

### Likelihood Explanation
This does not require compromising Pyth/DIA or manipulating third-party oracle data content — only a timestamp that is at or ahead of the consuming Stacks block's `stacks-block-time` at write time (a realistic occurrence given the asynchronous nature of relayer submission vs. chain block timestamps), after which the flawed comparison mechanically produces `delta = u0` on every subsequent read until `stacks-block-time` advances past `ts`. This is a deterministic logic bug in Zest's own gating function, not oracle data trustworthiness, so likelihood is non-trivial though bounded by how often/long such timestamp relationships arise.

### Recommendation
Do not clamp `delta` to `u0` when `ts > stacks-block-time`; instead treat a timestamp ahead of the current block time as invalid (reject via `ERR-ORACLE-INVARIANT`) or compute delta using an absolute value / explicit future-timestamp rejection so the `max-staleness` bound cannot be silently satisfied by construction:
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```

### Proof of Concept
1. A relayer submits a Pyth price update to `pyth-storage-v4` in a block whose `stacks-block-time` is `T`, but with `publish-time = T + 30` (30 seconds ahead), which `pyth-storage-v4`'s own staleness check only bounds from below, not above. [3](#0-2) 
2. `market.clar`/`v0-4-market.clar` calls `price-resolve`, which reaches `oracle-timestamp-fresh(ts=T+30, prev, max-staleness)`; since `ts > stacks-block-time`, `delta` is forced to `u0`, so `(<= delta max-staleness)` is trivially true and `last-update` is set to `T+30`.
3. Over the next ~30 seconds of real/chain time (until `stacks-block-time` reaches `T+30`), any transaction calling `price-resolve` with the same or a still-"future" timestamp continues to pass the freshness check unconditionally, even though the price is effectively aging without being refreshed — allowing borrow/withdraw/health-check operations to use a price that should already be considered stale under the asset's configured `max-staleness`.
