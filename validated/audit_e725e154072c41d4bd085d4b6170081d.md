### Title
FROST cached preprocess re-loaded after `sign` consumes it — nonce reuse across `share()`/`complete()` leaks validator key share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The external report describes the ERC1155Supply bug: `unwind` could be invoked inside a `build` callback, reading `totalSupply` before it was updated — a stale-state read enabling re-entrant reuse of a value that should have been consumed. Serai's `SigningProtocol` exhibits the same class of flaw: the ChaCha20 seed backing a FROST preprocess is written to `CachedPreprocesses` in the DB once and is **never deleted or marked consumed** after `SignMachine::sign` uses the derived nonces. Any code path that invokes `share_internal` a second time under the same `context` reconstructs identical `(d, e)` nonces from `AlgorithmSignMachine::from_cache`, and if the preprocess set or message differs, produces a second share under a different binding factor `rho` and challenge `c` — directly enabling recovery of the signer's secret share.

### Finding Description
`preprocess_internal` stores a random seed in `CachedPreprocesses` the first time it runs for a `(b"DkgConfirmer", attempt)` context, then unconditionally re-loads that same seed on every later call and feeds it to `AlgorithmSignMachine::from_cache` [1](#0-0) . `from_cache` deterministically regenerates the same `Commitments::new` nonces from the seed [2](#0-1) . Although `sign` consumes the in-memory machine (`fn sign(self, ...)`), the DB copy of the seed survives.

`DkgConfirmer::share` calls `share_internal`, which calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` [3](#0-2) . `DkgConfirmer::complete` then calls `share_internal` **again** on the same context to rebuild the signature machine [4](#0-3) . Both entry points take attacker-influenced inputs: the `preprocesses: HashMap<Participant, Vec<u8>>` (bytes parsed via `read_preprocess` → `Commitments::read`) and `key_pair`, which feeds `set_keys_message` to form `msg` [5](#0-4) .

The file's own safety argument states nonce reuse requires "the received nonce commitments (or the message to be signed) … be distinct and sign … be called again" — exactly what happens if `share` and `complete` are driven with non-identical preprocess sets/messages, which the code does not enforce (the acknowledged TODO checks only that on-chain commitments match the presumed preprocess) [6](#0-5) .

In `AlgorithmSignMachine::sign`, `rho` is derived from `group_key`, `hash_msg(msg)`, and the hash of all included preprocesses; each share has the form `s_i = d + e·rho_i + c·λ_i·x_i` (via `sign_share` with nonces `d + e·rho`) [7](#0-6) . Two shares from the same `(d, e)` under different `(rho, c)` yield the secret share `x_i` by linear algebra — the classic FROST nonce-reuse key extraction.

### Impact Explanation
Reuse of FROST nonces across two signing sessions with distinct binding factors/challenges exposes the validator's MuSig secret key share (`self.key`, the Ristretto validator key used in `musig(...)`). Compromise of this key undermines the DKG-confirmation root of trust: an attacker who extracts a validator's share can forge confirmation shares and, combined with enough other shares, produce unauthorized `set_keys` signatures for attacker-controlled key pairs.

### Likelihood Explanation
Triggering requires `share_internal` to run twice on one context with different preprocess commitments or a different `key_pair`/message. Both arguments originate from received protocol messages (preprocesses broadcast by other validators; the `key_pair` being confirmed) and from re-execution of block handling, so a participant who can get a distinct preprocess set or key pair finalized between the `share` and `complete` invocations — including across a partial rebuild, a bound the comments explicitly flag — reaches the reuse. It does not require colluding validators, BFT failure, or key leakage; it requires a logical inconsistency in which messages are fed to the two calls, the precise condition the in-code safety analysis says must never occur but is not enforced. I could not fully trace `coordinator/src/tributary/handle.rs` (tool budget exhausted) to confirm whether `share` and `complete` are fed identical preprocess maps in all paths, so reachability rests on the absence of any equality check between the two calls' inputs.

### Recommendation
- Delete (or tombstone) `CachedPreprocesses[context]` after the first successful `machine.sign`, and make `preprocess_internal` refuse to sign if no unconsumed cache exists while a prior preprocess was already published for that context.
- Have `complete` verify that the preprocess set/message are identical to those used by `share` (e.g., store `hash(preprocesses) || hash(msg)` alongside the seed and compare before re-signing), implementing the TODO check noted in the file.
- Alternatively persist the produced `SignatureMachine` state rather than re-deriving it via a second `sign`.

### Proof of Concept
```text
Context: DkgConfirmer for attempt A on a tributary spec where we are validator i.

1. preprocess(): generates seed S via OsRng, stores Enc(S) in
   CachedPreprocesses[(b"DkgConfirmer", A)], publishes commitments (D,E)
   derived from S.
2. share(preprocesses_P, key_pair_K):
   - share_internal -> preprocess_internal reloads S -> nonces (d, e)
   - sign(preprocesses_P, msg_K) -> share s1 = d + e·rho_P + c1·λ_i·x_i
   - returns s1; seed S remains in DB.
3. complete(preprocesses_Q, key_pair_K', shares) where
   preprocesses_Q ≠ preprocesses_P (a distinct participant subset or distinct
   commitment bytes from any included validator) or key_pair_K' ≠ key_pair_K:
   - share_internal reloads the SAME S -> identical (d, e)
   - sign(preprocesses_Q, msg_K') -> machine containing share
     s2 = d + e·rho_Q + c2·λ_i·x_i with (rho_Q, c2) ≠ (rho_P, c1).
   - The machine is used for share verification; s2 is recomputed and is
     observable as our published share for the second session.
4. Given s1, s2 and public rho_P, rho_Q, c1, c2:
   s1 - s2 = e·(rho_P - rho_Q) + x_i·λ_i·(c1 - c2)
   Combined with the nonce relation e = (s1 - d ... ) standard two-equation
   solve recovers λ_i·x_i, i.e. our effective signing share — private key
   material for the MuSig validator key.
```

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }

  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

      params.keys.original_secret_share(),
      &params.algorithm.nonces(),

    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
