### Title
Unchecked `u64` arithmetic on attacker-controlled amounts bypasses the insufficient-funds check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

CVE-2015-8836 is an integer-overflow class bug: an attacker-controlled size value overflows internal arithmetic and defeats a bounds check. The analog in Serai's in-scope code is `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`, which sums attacker-influenced payment amounts and computes fees with plain `u64` `sum`, `+`, and `*` operators instead of checked arithmetic. A crafted `payments` list can wrap `payment_sat` to a small value, defeating the `NotEnoughFunds` check and producing a `SignableTransaction` — and subsequently a FROST-signed Bitcoin transaction — whose outputs exceed its inputs.

### Finding Description

`SignableTransaction::new` computes the total value being paid out with an unchecked saturating-free sum:

```rust
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
``` [1](#0-0) 

The only validation on each amount is a lower bound (`*amount < DUST` is rejected); there is no upper bound such as the 21M BTC consensus cap [2](#0-1) . In release builds `sum::<u64>()` wraps on overflow. The same pattern repeats in the funds check (`input_sat < (payment_sat + needed_fee)`), the fee computation (`fee_per_vbyte * vbytes`), and the change calculation (`payment_sat + fee_with_change`) [3](#0-2) .

With two or more payments whose amounts sum past `u64::MAX` (e.g., two payments of `u64::MAX - 100`), `payment_sat` wraps to a small number, so `input_sat < payment_sat + needed_fee` is false and `NotEnoughFunds` is never raised. The change calculation `input_sat.checked_sub(payment_sat + fee_with_change)` likewise operates on the wrapped sum, so it happily creates a change output consuming nearly the entire input. The constructed `SignableTransaction` is then fed to `TransactionSignMachine::sign`, which produces a real FROST signature share over `taproot_key_spend_signature_hash` for a transaction whose outputs can never be satisfied [4](#0-3) .

There is also a secondary overflow: `needed_fee = fee_per_vbyte * vbytes` can wrap if a large fee rate is supplied, silently producing a near-zero `needed_fee` that passes the `TooLowFee` check while the transaction's actual implicit fee (`inputs - outputs`) is computed differently.

### Impact Explanation

The reachable outcome is that the threshold signers produce signatures for a transaction that violates the wallet's own funds invariant — outputs exceeding inputs — which the Bitcoin network will reject as consensus-invalid. Every FROST signing attempt consumes a single-use preprocess (nonce reuse is the documented key-leak hazard), so a malicious party who can influence the payment list can force the multisig to burn preprocesses and produce permanently unbroadcastable signed transactions, denying service to legitimate withdrawals. The wrapped `payment_sat` also corrupts change output values, which can mis-account internal bookkeeping (the "funds reported" surface) even though the on-chain result is a null transaction.

### Likelihood Explanation

Reachability requires an unprivileged party to influence the `payments` slice passed to `SignableTransaction::new` — i.e., transaction data that the multisig is asked to sign, which is within the reachable-inputs model (transaction data they cause to be signed). No key material or validator access is needed; only control over proposed payment amounts, which are by construction arbitrary `u64` values. The bug requires no race and is deterministic in release builds (wrapping arithmetic). In debug builds it panics instead, which is still a remotely-triggered abort.

### Recommendation

Use checked arithmetic throughout `SignableTransaction::new` and `fee()`:

- `payment_sat`: `payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))` and reject with a new `TransactionError` variant on overflow.
- `needed_fee`: `fee_per_vbyte.checked_mul(vbytes)` and reject on overflow.
- The funds check: `payment_sat.checked_add(needed_fee)` before comparing against `input_sat`.
- Optionally enforce `amount <= MAX_MONEY` (21M BTC) per payment so the semantics match Bitcoin consensus.

### Proof of Concept

```rust
use serai_bitcoin::wallet::{SignableTransaction, ReceivedOutput, Scanner};
use bitcoin::ScriptBuf;

// `input` is a legitimately-scanned ReceivedOutput worth, say, 100_000 sats.
let input: ReceivedOutput = scanner.scan_transaction(&funding_tx).remove(0);

// Attacker proposes payments whose individual values pass the DUST check
// but whose sum wraps u64.
let payments = vec![
    (ScriptBuf::new(), u64::MAX - 100),
    (ScriptBuf::new(), u64::MAX - 100),
];

// payment_sat wraps to u64::MAX - 202 (mod 2^64 => ~2^64 - 202 ... still huge),
// use three payments so the wrap lands *below* input_sat:
let payments = vec![
    (ScriptBuf::new(), u64::MAX / 2),
    (ScriptBuf::new(), u64::MAX / 2),
    (ScriptBuf::new(), u64::MAX / 2),
];
// payment_sat == (3 * (u64::MAX/2)) mod 2^64, a small value < input_sat.

// In a release build this returns Ok(...) despite outputs totaling ~1.5 * u64::MAX
// far exceeding the 100k-sat input. In debug it panics on overflow.
let tx = SignableTransaction::new(
    vec![input],
    &payments,
    Some(change_script),
    None,
    1,
);
assert!(tx.is_ok()); // NotEnoughFunds was bypassed by the wrap
```

Feeding the resulting `SignableTransaction` into `multisig()` / `TransactionSignMachine::sign` produces valid FROST signatures committing to the overflowing transaction.
