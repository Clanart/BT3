### Title
Attacker-Controlled Nonce Commitment to the Identity Point Panics BIP-340 `Hram::hram`, Permanently Aborting Bitcoin Multisig Signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
In the original report, a privileged parameter (`changeInterval`) could be set to a value that makes a downstream operation produce an invalid result and revert, permanently bricking upkeep. The Serai analog is a panic on the transaction-signing critical path: the Bitcoin `Hram::hram` implementation calls `x(R)`, which unconditionally `expect`s the aggregate nonce `R` to be a non-infinity point. `read_G` accepts the canonical encoding of the point at infinity (it round-trips `to_bytes`), and `read_preprocess` deserializes participant preprocesses containing those nonce points without an identity check. A participant who submits a preprocess whose nonce commitment makes the summed nonce `R = nonce_sums[0][0]` equal to the identity (or who influences the sum toward identity by cancelling other commitments) causes `Schnorr::sign_share` → `IetfSchnorr::sign_share` → `H::hram` to panic inside `TransactionSignMachine::sign`, aborting the multisig signing session.

### Finding Description
`TransactionSignMachine::read_preprocess` (networks/bitcoin/src/wallet/send.rs:351-353) feeds attacker bytes into `AlgorithmSignMachine::read_preprocess`, which deserializes nonce commitments via `C::read_G`. `C::read_G` (crypto/ciphersuite/src/lib.rs:91-101) only rejects non-canonical encodings; the identity point is a canonical `GroupEncoding`, so it is accepted. In `sign` (send.rs:355-398), preprocesses are combined and `sig.sign(...)` eventually calls `Schnorr::sign_share` → `FrostSchnorr::sign_share` (crypto/frost/src/algorithm.rs:201-211), which computes `H::hram(&nonce_sums[0][0], &params.group_key(), msg)`. `Hram::hram` (crypto.rs:59-73) calls `x(R)`/`x(A)`, and `x` (crypto.rs:13-16) does `.expect("point at infinity")`. If the adversary's preprocess bytes make the aggregate nonce the identity — trivially by submitting the identity encoding as their nonce commitment when they are the sole/other-cancelling commitment — `hram` panics. There is no `is_identity` check anywhere in `crypto/frost/src/sign.rs` or in the nonce-sum path. Since panics in the signing machine abort the attempt, a malicious participant can repeat this on every retry, mirroring the "continuous Denial-of-Service on any upkeep action" of the original bug: the Bitcoin transaction can never be signed while that participant's poisoned preprocess is included.

### Impact Explanation
An unprivileged threshold participant (or anyone able to submit preprocess bytes to `read_preprocess`, e.g. via the coordinator's preprocess relay) can deterministically abort every `TransactionSignMachine::sign`/`complete` execution for a Bitcoin spend, preventing the multisig from producing a valid BIP-340 witness. This is a persistent DoS of fund movement on the in-scope `networks/bitcoin` signing path — the same consequence class as `executeAllCommitments()` being bricked.

### Likelihood Explanation
Triggering requires only publishing a preprocess containing the canonical identity encoding (32 zero-ish bytes depending on encoding), or nonce commitments summing to identity — both accepted by `read_G`. No leaked keys, collusion threshold, or privileged role beyond an ordinary signer in the session is needed. The panic is deterministic once the poisoned bytes are consumed, and blame/punishment for an unparseable preprocess is not enforced inside this code path, so the attack can be retried.

### Recommendation
Reject the identity point (and ideally enforce the "nonce commitment must be non-identity" rule) in `read_preprocess`/`Preprocess::read` and in the nonce-sum aggregation in `crypto/frost/src/sign.rs`, and/or make `Hram::hram`/`x` return a recoverable error rather than panicking on infinity. At minimum, validate `!nonce_sums[i][j].is_identity()` before calling `sign_share`, and treat preprocesses containing identity commitments as invalid/faulty input.

### Proof of Concept
1. Construct a preprocess for the `Schnorr` Bitcoin algorithm whose serialized nonce commitment is `Secp256k1::G::identity().to_bytes()` (canonical, passes `read_G`).
2. Feed it through `TransactionSignMachine::read_preprocess` into `sign` as the (or a nonce-cancelling) commitment map for input 0.
3. `sign` → `AlgorithmSignMachine::sign` → `Schnorr::sign_share` computes `Hram::hram(&identity, &group_key, sighash)`.
4. `x(&identity)` hits `.expect("point at infinity")` at crypto.rs:15 and panics, aborting `TransactionSignMachine::sign` — repeatable on every attempt.

Uncertainty: whether an upstream coordinator layer deduplicates or rejects identity preprocesses before this path was not fully verified within the iteration budget; the panic itself is unconditional in the in-scope code shown.
