### Title
Scanner reports zero/dust-value outputs as received funds, causing fee loss when spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` reports any transaction output paying to a registered script as a `ReceivedOutput`, with no check on `output.value`. A zero-value or dust output is therefore reported identically to a spendable output. When such an output is later fed to `SignableTransaction::new` as an input, it contributes 0 (or near-0) satoshis while still consuming ~57 vbytes of fee weight, meaning the "received funds" cost more to spend than they are worth. This mirrors the reported bug class: value is taken/counted on one side while the computed usable result is effectively zero, with no guard rejecting it.

### Finding Description
The original USSD issue is that `mintForToken()` accepts a user's tokens, computes a `stableCoinAmount` that rounds to 0, and still completes the transfer — the user loses the deposit and receives nothing. The invariant violated is "an operation that yields zero usable value must be rejected rather than silently consuming the input."

In `bitcoin-serai`, `Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, with no minimum-value check (`networks/bitcoin/src/wallet/mod.rs:199-214`). Bitcoin consensus permits outputs with `value = 0` (they are nonstandard for relay but valid if mined). `ReceivedOutput::value()` simply returns `output.value.to_sat()` (`mod.rs:116-118`).

Downstream, `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) accepts caller-supplied `Vec<ReceivedOutput>` as inputs. Each input is serialized into `tx_ins` unconditionally (lines 177-185) and contributes to `input_sat` only its actual value (line 175). A 0-value output adds weight — every Taproot input adds ~230 weight units / ~57 vbytes per the documented model in `calculate_weight_vbytes` (lines 71-83) — while adding nothing to `input_sat`. The fee (`fee_per_vbyte * vbytes`) is charged regardless (line 206).

Notably, the Serai processor already recognizes this hazard: `processor/src/multisigs/scanner.rs:564` filters scanned outputs with `if output.balance().amount.0 >= N::DUST`, and `Bitcoin::DUST` is defined as 10,000 sats specifically because "this value MUST exceed the cost to spend said output" (`processor/src/networks/bitcoin.rs:638`, `processor/src/networks/mod.rs:295-301`). The wallet-level `Scanner` — the component actually producing `ReceivedOutput`s consumed by `SignableTransaction` — has no equivalent filter.

### Impact Explanation
An unprivileged third party who learns a registered script (e.g., a deposit/change address derived via `register_offset`, which are deterministic given the key and offset) can craft and mine a transaction containing a 0-value or sub-spend-cost output to that script. The wallet reports it as a received output worth `value()` sats. If the wallet owner (or automated logic) includes it as an input to `SignableTransaction::new`, the transaction pays the marginal fee for that input while gaining nothing — a direct loss of funds proportional to `fee_per_vbyte * 57` per dust input, and if the dust input tips the balance check, the honest inputs fund a payment plus an inflated fee. In the extreme, an output worth less than its spend cost is economically unspendable: "funds reported received that are not spendable."

### Likelihood Explanation
The attacker only needs to get one nonstandard transaction mined (a miner can include 0-value outputs; they are consensus-valid). The path requires no privileged position, no collusion, and no key material — just knowledge of a script the victim scans for, which for deposit-address schemes is necessarily known to the depositor. Whether the loss materializes depends on wallet-side input selection including the dust output, but the library provides no defense or warning: `SignableTransaction::new` validates payments against `DUST` (line 166) yet never validates inputs against spend cost.

### Recommendation
Reject or skip outputs whose value cannot cover their spend cost in `Scanner::scan_transaction` (e.g., ignore `output.value == 0` at minimum, ideally below a dust threshold consistent with the processor's `N::DUST`), matching the check already present in `processor/src/multisigs/scanner.rs:564`. Alternatively/additionally, `SignableTransaction::new` could skip or error on inputs whose value is below the marginal fee they incur.

### Proof of Concept
```rust
// networks/bitcoin context (regtest)
let mut scanner = Scanner::new(key).unwrap();
let script = p2tr_script_buf(key).unwrap();

// Attacker mines a tx with a 0-value output to the victim's scanned script.
let attacker_tx = Transaction {
    /* ... */,
    output: vec![TxOut { value: Amount::ZERO, script_pubkey: script }],
};

// Scanner reports it as a received output with no value check.
let outputs = scanner.scan_transaction(&attacker_tx);
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 0); // reported, worth nothing

// Feeding it into SignableTransaction consumes ~57 vbytes of fee
// while contributing 0 satoshis to input_sat.
```
