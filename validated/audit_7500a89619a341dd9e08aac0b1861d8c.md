### Title
Silent loss of AI-resolved conflict content when hunk count mismatches marker count — `reassembleResolvedFile()` drops resolutions instead of preserving user content - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`reassembleResolvedFile()` in `app/src/lib/copilot-conflict-resolution.ts` reassembles a fully-resolved file by walking the raw conflicted file line-by-line and splicing per-hunk AI resolutions into each well-formed `<<<<<<<`/`=======`/`>>>>>>>` block, matching resolutions to conflict blocks purely by **position/order**, not by any stable identifier (e.g., byte offset, hunk id, or hash of the conflict body). This is structurally the same class of bug as the reported `AllocationVesting.lockFutureClaimsWithReceiver()` issue: a value is silently truncated/mismatched due to an implicit, unchecked correspondence between two independently derived quantities.

### Finding Description [1](#0-0) 

The function walks `lines` looking for `<<<<<<<` markers via `reassemblyOursMarker`, verifies a `=======` separator and `>>>>>>>` closing marker exist ahead, and if well-formed, replaces the whole block with `hunkResolutions[hunkIndex].resolvedContent`, then increments `hunkIndex`:

The broken invariant: `hunkResolutions` is assumed to line up 1:1, in the same order, with the conflict blocks discovered by regex-scanning the raw file content. Nothing in this function (or, as far as is discoverable from the indexed code, anywhere upstream) ties a given `IHunkResolution` back to the specific conflict block it was generated for. If the number of well-formed conflict blocks found during reassembly differs from `hunkResolutions.length` — or their order differs — from what was originally extracted/sent to Copilot, the splicing silently misaligns:

- If `hunkIndex >= hunkResolutions.length` for a real conflict block, the block is entirely **deleted** — the `<<<<<<<...>>>>>>>` region (all of "ours", "theirs", and any resolution) vanishes from the final content with no error, exactly analogous to the reported case where debited value is silently smaller than intended.
- If ordering drifts (e.g., because a conflict block in the raw file is judged malformed by `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` — for instance a conflict body itself containing a bare `=======`-looking line, or nested `<<<<<<<` markers from the attacker's own file/commit content — pushing that block through as literal, unresolved conflict-marker text and NOT incrementing `hunkIndex`), every subsequent real conflict block gets resolved with the **wrong** hunk's AI-generated content, silently corrupting the merge result the user is about to commit.

Because the source file is a **cloned/fetched repository's working tree during a merge conflict**, an attacker who controls one side of the conflicting content (e.g., a malicious branch/PR that the victim merges) can craft conflict bodies containing extra `=======`/`<<<<<<<`/`>>>>>>>`-looking lines to deliberately desynchronize the regex-based block counting from whatever hunk-extraction logic produced `hunkResolutions`, causing GitHub Desktop to silently drop or swap resolved content in the file the user then stages and commits.

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes." A user resolving merge conflicts via the Copilot conflict-resolution feature could unknowingly commit a file where:
- part of a conflict was silently deleted (losing code that should have been kept from either "ours" or "theirs"), or
- code intended for one location is spliced into another location entirely, reintroducing logic errors or, more seriously, injecting attacker-controlled ("theirs") code into a position the reviewer believes is a different, already-reviewed hunk.

Since the corruption happens before the user reviews/commits, and the UI historically shows the reassembled content in the Changes tab as if it were the correctly resolved file, the user has no obvious signal that misalignment occurred, unless they carefully diff every hunk against the two conflicting versions.

### Likelihood Explanation
Requires only that the victim (a) merges/rebases against attacker-influenced content that produces a genuine merge conflict, and (b) uses the Copilot-assisted conflict resolution flow. No admin rights, local access, or prior compromise are needed — the attacker's contribution is ordinary repository content (a branch, PR, or fetched ref) with specially crafted conflict-adjacent text. The `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` regexes are simple line-anchored patterns (`^<{7}`, `^={7}$`, `^>{7}`) that are trivially satisfiable by ordinary text a malicious contributor could include in a file (e.g., a documentation file about git conflict markers, or code containing a comment block using `=======` as a divider), making an accidental or deliberate desync plausible.

### Recommendation
Do not rely on positional/ordinal correspondence between `hunkResolutions` and conflict blocks discovered during reassembly. Instead:
1. Tag each extracted conflict hunk with a stable identifier (e.g., a hash of its raw ours/theirs content, or its byte offset in the original file) when hunks are first extracted for the AI resolution request, and carry that identifier through `IHunkResolution`.
2. In `reassembleResolvedFile()`, match each discovered block to its resolution by that identifier rather than by `hunkIndex++`, and treat any unmatched block (extra or missing) as a hard error rather than silently deleting content or continuing with a mismatched index.
3. Fail closed: if the count of well-formed conflict blocks found during reassembly does not exactly equal `hunkResolutions.length`, abort the auto-resolution for that file and fall back to manual resolution, rather than producing a "best effort" spliced file that gets displayed/staged as fully resolved.

### Proof of Concept
Conceptual sequence (exact reproduction requires exercising the full Copilot conflict-resolution pipeline, which was not fully visible in the indexed code — the routine that produces `hunkResolutions` from the raw file was not retrievable):
1. Attacker crafts a branch where a file's "theirs" version contains, inside an otherwise normal code block, a line consisting of exactly `=======` or `<<<<<<<` (e.g., inside a comment/ASCII-art divider), positioned so that when merged it lands adjacent to or inside a real conflict region.
2. Victim merges the attacker's branch locally, producing a real merge conflict in that file (plus, depending on exact placement, an ambiguous/extra marker-like line).
3. Victim invokes Copilot's "Resolve with Copilot" flow. The upstream extraction logic and `reassembleResolvedFile()`'s regex-based rescanning of the raw file can now disagree on how many well-formed conflict blocks exist / in what order, because the extra marker-like line changes what `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` detect on the second pass.
4. `reassembleResolvedFile()` either drops a whole conflict block (when `hunkIndex >= hunkResolutions.length`) or applies the wrong resolution to a hunk (index drift), producing a file that looks fully resolved in the Changes tab but silently differs from what either the user or the AI intended.
5. The user stages and commits the corrupted file without any warning from Desktop.

Note: the routine(s) that produce `hunkResolutions` and detect conflict hunks in the first place were not found in the indexed portion of the codebase, so the exact upstream extraction logic (and whether it already guards against this desync) could not be fully verified — this should be checked against the full source in a live session (via `codebase_search`/`grep_search` for `IHunkResolution`, `hunkResolutions`, and the conflict-hunk extraction function) before treating this as fully confirmed exploitable, versus a defense-in-depth gap.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
