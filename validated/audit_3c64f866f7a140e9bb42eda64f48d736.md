### Title
`SignableTransaction` fee/weight accounting omits the OP_RETURN data output, undercharging fees for attacker-controlled data - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Polynomial report describes an accounting mismatch: the protocol credits the declared `amount` while only `amount - fee` is actually received, with no way to stop supporting the misbehaving asset. The analog in bitcoin-serai is a declared-vs-actual accounting mismatch in `SignableTransaction::new`: the fee is priced from a reconstructed transaction that omits the OP_RETURN output carrying caller/attacker-supplied `data`, so the signed transaction commits more weight than was paid for — the effective fee rate is lower than the requested `fee_per_vbyte`, and can silently fall below the minimum relay fee the code claims to enforce.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), the `data` argument is pushed onto `tx_outs` as an OP_RETURN output before the weight is calculated, but `calculate_weight_vbytes` is invoked with the `payments` slice rather than `tx_outs` — both for the no-change and the with-change calculation — so the OP_RETURN output is never counted in `weight`/`vbytes`:

```rust
// tx_outs already contains the OP_RETURN output (send.rs ~L194-202)
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;          // send.rs ~L204-206
...
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change)); // ~L225-226
```

Inside `calculate_weight_vbytes` (`send.rs` ~L62-127) the transaction is rebuilt solely from `payments` plus an optional change output; the data output is absent. With the maximum permitted `data` of 80 bytes (`TooMuchData` check at ~L171), the omitted output adds roughly 90 bytes (~360 WU, ~90 vbytes) of unaccounted weight. Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` undercharges by `fee_per_vbyte * ~90` sat.
2. The `TooLowFee` guard (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, ~L211) uses the understated `vbytes`, so a `fee_per_vbyte` at the minimum relay boundary produces a real transaction whose actual fee rate is below the relay minimum — it will be rejected/never confirm.
3. The `TooLargeTransaction` check on `weight` (~L241) is likewise computed on a smaller transaction than the one signed.

The `data` bytes originate from the Bitcoin deposit `InInstruction` (extracted via `extract_serai_data` in `processor/src/networks/bitcoin.rs` and carried into send paths), i.e., transaction data an unprivileged depositor causes the multisig to sign — a reachable public input. This mirrors the report's class: the system accounts for value (here, fee-per-weight) on a declared object while the actual object differs, and once signed the discrepancy cannot be corrected.

### Impact Explanation
Any `SignableTransaction` built with a non-empty `data` payload pays a lower effective sat/vbyte rate than the caller specified and than the minimum-relay check intends. At boundary fee rates the resulting signed transaction is non-standard for relay and will not propagate/confirm, freezing the multisig's UTXOs in an unconfirmed spend (the inputs are consumed by the signed eventuality until expiry/re-sign). Repeated attacker-supplied 80-byte payloads widen the gap. Severity: Medium — reliability/fund-availability loss via under-priced transactions, reachable from untrusted transaction data.

### Likelihood Explanation
Triggered whenever a send includes an OP_RETURN payload (up to 80 bytes accepted) at a low `fee_per_vbyte`; depositors controlling instruction data can force worst-case inflation. No privileged access, key material, or collusion is needed — only data the protocol embeds on the signer's behalf.

### Recommendation
Pass the fully-built output list (or `tx_outs`/`data` explicitly) into `calculate_weight_vbytes` so `weight`, `vbytes`, `needed_fee`, the `TooLowFee` bound, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually being signed — analogous to crediting `amount_received` rather than the declared `amount`.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` with `fee_per_vbyte` exactly at the minimum relay rate (`DEFAULT_MIN_RELAY_TX_FEE / 1000` equivalent).
2. Observe `needed_fee()` was computed without the ~90-vbyte OP_RETURN output, while the final `tx` contains it.
3. The signed transaction's actual fee rate is `needed_fee / actual_vsize`, which is below the minimum relay fee, so `send_raw_transaction` rejects it despite `TooLowFee` not firing — the discrepancy grows with `data.len()`.
