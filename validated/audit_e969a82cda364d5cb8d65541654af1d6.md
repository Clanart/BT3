### Title
NFT metadata/solution parsing crashes wallet sync via unguarded `assert` on attacker-crafted coin spend - (File: chia/wallet/nft_wallet/nft_puzzle_utils.py)

### Summary
`get_metadata_and_phs()` in `chia/wallet/nft_wallet/nft_puzzle_utils.py` parses the solution of an on-chain NFT coin spend to recover the updated metadata and destination puzzle hash. It ends with a bare `assert puzhash_for_derivation` with no exception handling around it, and the same missing-validation pattern appears in `update_metadata()`, which blindly indexes into the update condition (`update_condition.rest().rest().first()`) without checking condition shape. [1](#0-0) 

This mirrors the CVE-2017-14641 bug class: a parser that trusts externally supplied, attacker-controlled structured data (there: an MP4 metadata atom; here: a CLVM solution/condition list for an NFT coin spend) and dereferences/derives a value from it without verifying the expected shape exists, causing the process to crash instead of gracefully rejecting the malformed input.

### Finding Description
`get_metadata_and_phs(unft, solution)` runs the p2 puzzle against the innermost solution taken from an NFT coin's parent spend, then iterates the resulting conditions looking for a `CREATE_COIN` (opcode 51) with `amount == 1` to derive `puzhash_for_derivation`, and for opcode `-24` to update metadata via `update_metadata()`: [1](#0-0) 

- If a spend author (anyone who can construct/broadcast a NFT-shaped coin spend, e.g. a counterparty in an offer or a malicious sender of an NFT to a victim wallet) crafts a solution whose p2-puzzle output never emits a valid `(51 puzhash 1 (memo))` condition, the loop finishes with `puzhash_for_derivation is None`, and the trailing `assert puzhash_for_derivation` raises `AssertionError`.
- Similarly, `update_metadata()` unconditionally does `update_condition.rest().rest().first()` on any `-24` condition without checking `list_len()`, so a condition with fewer elements throws an unhandled `ValueError`/`EvalError` instead of being treated as invalid and skipped (contrast with the `condition.list_len() < 2` guard already present for the `51` case just above it). [2](#0-1) 

This function is invoked from the wallet's NFT sync path when a coin recognized as NFT-shaped receives a new spend: `NFTWallet.puzzle_solution_received()` calls `get_metadata_and_phs(uncurried_nft, data.parent_coin_spend.solution)` directly, with no try/except around the call. [3](#0-2) 

Because `UncurriedNFT.uncurry()` only checks the puzzle's curried structure (singleton + NFT state layer mods) to decide something is "NFT-shaped" — it does not, and cannot, validate what solution will be provided at spend time — any wallet that is tracking/watching an NFT-shaped coin (e.g. because it's a recipient in an offer, or simply observes the coin on chain) is exposed to a spend crafted by an unprivileged third party with an incomplete/malformed solution.

### Impact Explanation
An unprivileged spend-bundle submitter can construct a spend of an NFT-shaped coin (with themselves or a victim's puzzle) whose solution deliberately omits the expected `CREATE_COIN` condition with the amount/memo NFT convention, or supplies a malformed `-24` metadata-update condition. When this spend is confirmed on chain and a wallet (the coin's tracked owner/recipient, or any client syncing NFT state for that coin, such as during an offer/DID transfer flow) processes it, `get_metadata_and_phs`/`update_metadata` throws an unhandled exception during `puzzle_solution_received`. This halts that specific coin's wallet-side transaction/state processing (a spend-triggered processing halt), consistent with the DoS/crash class of CVE-2017-14641, though scoped to the wallet sync code path rather than the consensus/mempool path.

### Likelihood Explanation
Likely to be triggerable: the attacker only needs the ability to build and get onto the chain a coin spend of any coin the victim wallet is tracking as an NFT (e.g., as part of a crafted offer, DID/NFT transfer, or minting flow that a victim wallet observes); no privileged access, malicious node, or timing race is required — only a single confirmed spend with an atypical solution shape.

### Recommendation
Wrap the condition-derivation logic in `get_metadata_and_phs` in explicit validation instead of a bare `assert`, returning/raising a well-defined, caught error (or skipping/ignoring the coin update) if no valid `CREATE_COIN` memo condition is found. Add a `list_len()` guard in `update_metadata`/`get_metadata_and_phs` before indexing into the `-24` condition, mirroring the existing guard used for the `51` condition. Callers such as `NFTWallet.puzzle_solution_received` should catch and log malformed-solution errors per-coin rather than letting them propagate.

### Proof of Concept
1. Victim wallet is tracking (or about to receive) an NFT-shaped coin `C` (singleton + NFT state layer curried puzzle).
2. Attacker creates a spend of `C` whose p2-inner-puzzle solution results in conditions that contain no `CREATE_COIN` condition with `amount == 1` (or one whose 4th arg isn't a 32-byte memo), or that contains an `-24` metadata-update condition with fewer than expected components.
3. Attacker's spend bundle is submitted and confirmed in a block (standard mempool/consensus acceptance does not require NFT-convention conditions to be present for a spend to be valid).
4. Victim's wallet, syncing the coin as NFT via `NFTWallet.puzzle_solution_received`, calls `get_metadata_and_phs(uncurried_nft, data.parent_coin_spend.solution)`; the loop fails to set `puzhash_for_derivation`, and the trailing `assert puzhash_for_derivation` raises `AssertionError` uncaught, halting processing of that coin/wallet sync step. [4](#0-3)

```python
def get_metadata_and_phs(unft: UncurriedNFT, solution: SerializedProgram) -> tuple[Program, bytes32]:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(Program.from_serialized(solution)))
    metadata = unft.metadata
    puzhash_for_derivation: bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.list_len() < 2:
            # invalid condition
            continue
        condition_code = condition.first().as_int()
        log.debug("Checking condition code: %r", condition_code)
        if condition_code == -24:
            # metadata update
            metadata = update_metadata(metadata, condition)
            metadata = Program.to(metadata)
        elif condition_code == 51:
            atom = condition.rest().rest().first().as_int()

            if atom == 1:
                # destination puzhash
                if puzhash_for_derivation is not None:
                    # ignore duplicated create coin conditions
                    continue
                memo = bytes32(condition.at("rrrff").as_atom())
                puzhash_for_derivation = memo
                log.debug("Got back puzhash from solution: %s", puzhash_for_derivation)
    assert puzhash_for_derivation
    return metadata, puzhash_for_derivation
```
