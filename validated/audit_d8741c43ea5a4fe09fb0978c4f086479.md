### Title
`ThresholdKeys` accepts attacker-controlled interpolation weights and an inconsistent secret share, letting the submitter dictate the aggregated group key — (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is "a manipulable public input is used as a weight in an aggregation, letting an attacker inflate their effective stake." Serai's analog lives in `ThresholdKeys::new` / `ThresholdKeys::read`: the `Interpolation::Constant(Vec<F>)` coefficients (the exact analog of a per-participant weight such as `balanceOf`) and the `verification_shares`/`secret_share` are all taken verbatim from attacker-supplied bytes, and no consistency check binds the secret share to the published verification share or to the resulting `group_key`.

### Finding Description
`ThresholdKeys::read` deserializes an untrusted byte stream: it reads `t`, `n`, `i`, then a tag selecting `Interpolation::Constant` followed by `n` arbitrary scalars used directly as interpolation coefficients, plus `secret_share` and `n` verification-share points [1](#0-0) . `ThresholdKeys::new` then computes the group key by summing `verification_shares[i] * interpolation_factor(i)` over participants `1..=t`, where `Interpolation::Constant` returns `c[i-1]` with zero validation [2](#0-1) . Crucially, `ThresholdKeys::new` never checks `C::generator() * secret_share == verification_shares[i]` and never checks the coefficients are sane/nonzero — it only bounds the participant indexes and enforces `t == n` for Constant interpolation [3](#0-2) .

This is the Serai shape of the `_lpStakingYax` inflation: just as the Solidity code multiplied a manipulable reserve by `_stakeAmount / _supply` to get a weight, here the supplier of the serialized keys chooses the weights (`c[i]`) and the points being weighted (`verification_shares`), so the derived `group_key` — the identity under which all subsequent FROST signatures verify — is whatever the byte supplier wants.

### Impact Explanation
An unprivileged party whose serialized `ThresholdKeys` are fed to `ThresholdKeys::read` can craft coefficients and verification shares so that `group_key()` equals a public key they fully control (e.g., set `verification_shares[1] = attackerPub`, all other entries arbitrary, coefficient vector making `group_key = attackerPub`). Every subsequent `view(included)` interpolates `secret_share` and per-participant `verification_shares` using those same attacker-chosen factors [4](#0-3) , so `AlgorithmSignMachine`/`Schnorr::sign_share` produce and accept shares under the attacker-chosen key — i.e., signatures under a group key whose "voting power" the attacker inflated from nothing. This is a concrete forged-signature / incorrect-verifier-formula outcome, not merely a bookkeeping issue.

### Likelihood Explanation
Reachability requires the attacker to supply bytes reaching `ThresholdKeys::read` (explicitly in the listed untrusted-input surface) — e.g., key material relayed in DKG/coordination messages rather than locally produced by `key_gen`, `musig`, `PedPoP`, or `GeneratorPromotion`, all of which construct `Interpolation` internally and would produce consistent inputs. Because honestly-produced `ThresholdKeys` always satisfy the missing invariants, the absent checks are never exercised in the honest path and the crafted-input path is fully reachable.

### Recommendation
In `ThresholdKeys::new` (so `read` inherits it), verify `C::generator() * secret_share == verification_shares[i]` for the local participant `i`, reject all-zero or degenerate `Interpolation::Constant` vectors, and (defense in depth) recompute `group_key` over the submitted `t`/`n`/coefficients and reject identity. Prefer treating `ThresholdKeys::read` output as untrusted until this consistency check passes.

### Proof of Concept
```rust
// Attacker-controlled bytes for ThresholdKeys::<Secp256k1>::read:
//   curve id ok; t = n = 1; i = 1; interpolation tag = 0 (Constant)
//   coefficients = [F::ONE]
//   secret_share  = attacker_scalar           // arbitrary
//   verification_shares[1] = G * attacker_scalar  // attacker-controlled point
//
// ThresholdKeys::new computes:
//   group_key = verification_shares[1] * c[0] = G * attacker_scalar
// i.e. the "aggregated" key is the attacker's solo key.
//
// keys.view([Participant(1)]) then yields secret_share = attacker_scalar * 1
// (+offset if any), and sign_share produces
//   s = r + H(R, group_key, msg) * attacker_scalar
// which verifies under group_key — a valid threshold signature for a key the
// attacker generated unilaterally, with no DKG ever performed.
```
The attack mirrors the original: the attacker substitutes a self-chosen quantity for what should be an honest weight, and the aggregation formula (coefficients × verification shares, vs. reserves × stake/supply) amplifies it into control of the outcome.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }
