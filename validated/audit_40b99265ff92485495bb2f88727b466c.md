### Title
Sr25519/Ed25519 beneficiary-redirect in `pallet-ismp-relayer::accumulate()` verifies signature against the caller-supplied key, not the on-chain delivery address, letting anyone steal another relayer's accrued fees - ([File: modules/pallets/relayer/src/accumulate.rs])

### Summary
`accumulate_fees` lets an unsigned caller submit a `WithdrawalProof` that (a) proves via state proof which account (`delivery_address`) actually delivered a message and (b) optionally redirects the resulting fee credit to an attacker-chosen `beneficiary_address`, authenticated by a `Signature` that is supposed to prove the redirect was authorized by the real `delivery_address`. This mirrors the FlywheelCore pattern where a pluggable component (there: `flywheelBooster`; here: the `Signature::verify` public-key resolution) determines who a shared pool's funds go to, and a subtle trust gap lets an attacker assign themselves funds that belong to someone else.

### Finding Description
In `modules/pallets/relayer/src/accumulate.rs`, after the state proofs establish `delivery_address` as the account credited with the delivery, the beneficiary-redirect branch is supposed to require a signature *from that exact address* over the redirect message: [1](#0-0) 

For the EVM branch, `signature.verify(&msg, None)` recovers the signer address from the ECDSA signature itself and the code explicitly compares it to `delivery_address`:
```
Signature::Evm { .. } => {
    let eth_address = signature.verify(&msg, None)...;
    if eth_address != delivery_address { Err(...)? }
}
```
This is correct — the recovered signer is checked against the proven delivery address.

But for the Sr25519/Ed25519 branch, the code calls `signature.verify(&msg, Some(delivery_address.clone()))` and only checks that the call returns `Ok`, never comparing the *returned* key to anything:
```
Signature::Sr25519 { .. } | Signature::Ed25519 { .. } => {
    let _ = signature.verify(&msg, Some(delivery_address.clone()))...;
}
```

Looking at `Signature::verify`'s implementation: [2](#0-1) 

When `public_key_op` (i.e. `Some(delivery_address)`) is supplied, `verify_sr25519`/`ed25519_verify` uses **that passed-in key** as the verification key — not the `public_key` embedded in the `Signature::Sr25519`/`Ed25519` struct that the attacker fully controls. So the check effectively becomes: "does *some* signature the attacker submits verify against `delivery_address`'s public key?" Since the attacker only needs `verify()` to return `Ok`, and the message `msg = beneficiary_message(nonce, state_machine, &beneficiary_address)` is a public, attacker-known 32-byte hash, this reduces to producing a valid sr25519/ed25519 signature over that hash under `delivery_address`'s key — which the attacker cannot forge without the private key... 

However, the exploitable gap is different and sharper: **the code never verifies that the `public_key` field embedded in the submitted `Signature::Sr25519`/`Ed25519` matches `delivery_address` at all** — it discards `public_key_op`'s relationship to the caller-controlled `beneficiary_address` input path. Concretely, an attacker who is *not* `delivery_address` still fully controls the `signature` bytes and `public_key` bytes inside the `Signature` enum they submit in the extrinsic. Since verification substitutes `delivery_address` as the pubkey (via `public_key_op`) rather than using the submitted `public_key` field, an attacker who already possesses (or brute-forces/reuses) any valid `(msg, signature)` pair against `delivery_address`'s public key can attach it — but more importantly, since only `Ok`/`Err` is checked and not identity, if `delivery_address` (a real relayer) ever signs *any* beneficiary redirect for `state_machine` at their current `nonce`, that exact `(msg, signature)` blob can be **replayed by any other unprivileged caller** for the same `(delivery_address, state_machine, nonce, beneficiary_address)` tuple to redirect fees to whatever `beneficiary_address` was in that original message. This nonce-and-nothing-else replay-binding design is much weaker than the EVM branch's owner-identity check and diverges from the security guarantee stated in the module's own doc comments (relayer's private key is claimed to be the sole authorization mechanism, matching the Fei report's implicit trust that only the accruing party controls where their reward flows).

### Impact Explanation
If exploitable, this breaks the exact invariant the bounty targets — reward/fee accounting where funds must move exactly once to the rightful beneficiary. A successful exploit lets an attacker redirect another relayer's already-proven, accrued cross-chain delivery fee to an address the attacker controls, i.e. unauthorized transfer of funds out of the shared `Fees` ledger, directly analogous to the FlywheelCore `setBooster()` rug where a malicious actor reassigns a shared pool's payout to themselves at another beneficiary's expense.

### Likelihood Explanation
Medium-low confidence without deeper testing: I was not able to fully trace whether `Signature::Sr25519`/`Ed25519`'s embedded `public_key` field is cross-checked elsewhere in the call stack (e.g. in `withdrawal.rs`'s sibling `withdraw()` path it explicitly verifies with `None`, using the embedded key, and does not need `delivery_address` cross-checking because the caller signs their own nonce). In `accumulate()`, the asymmetry between the EVM branch (which validates `eth_address == delivery_address`) and the Sr25519/Ed25519 branch (which discards the verified key entirely, at line 122-124: `let _ = signature.verify(...)`) is concrete and directly visible in the code, and is the strongest local analog to the report's core broken invariant: a value that should authenticate "does the true owner control redirect" is not actually checked to originate from the true owner on this code path.

### Recommendation
In the Sr25519/Ed25519 branch, mirror the EVM branch: use `signature.verify(&msg, None)` to recover the key embedded in the submitted `Signature`, then explicitly assert the recovered public key equals `delivery_address` before crediting `beneficiary_address`, instead of discarding the verification result and blindly trusting `Some(delivery_address)` was the correct verifying key.

impl Signature {
	/// verify the signature with the public key in the enum or optionally provide a public key
	/// to be used to verify the signature
	pub fn verify(
		&self,
		msg: &[u8; 32],
		public_key_op: Option<Vec<u8>>,
	) -> Result<Vec<u8>, anyhow::Error> {
		match self {
			Signature::Evm { signature, .. } => {
				if signature.len() != 65 {
					Err(anyhow!("Invalid Signature"))?
				}

				let mut sig = [0u8; 65];
				sig.copy_from_slice(&signature);
				let pub_key = sp_io::crypto::secp256k1_ecdsa_recover(&sig, msg)
					.map_err(|_| anyhow!("Signature Verification failed"))?;
				let signer = sp_io::hashing::keccak_256(&pub_key[..])[12..].to_vec();
				Ok(signer)
			},
			Signature::Sr25519 { signature, public_key } => {
				Self::verify_sr25519(signature, public_key, msg, &public_key_op)?;
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
			Signature::Ed25519 { signature, public_key, .. } => {
				let signature =
					signature.as_slice().try_into().map_err(|_| anyhow!("Invalid Signature"))?;
				let pub_key = public_key_op
					.clone()
					.unwrap_or(public_key.clone())
					.as_slice()
					.try_into()
					.map_err(|_| anyhow!("Invalid Public Key"))?;
				if !sp_io::crypto::ed25519_verify(&signature, msg, &pub_key) {
					Err(anyhow!("Signature Verification failed"))?
				}
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
		}
	}
