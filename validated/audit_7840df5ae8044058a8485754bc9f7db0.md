## Analysis

The external report's core broken invariant: a signing/authorization primitive is accepted and acted upon by a **destination system** without binding the signed payload to enough context to make consent unambiguous — the signature only covers the raw message, not the identity of the recipient/domain that will act on it, so it can be reused where it was never intended.

The local analog is in `pallet-hyper-fungible-token`'s calldata-execution feature. When an ISMP token transfer arrives with a non-empty `data` field carrying `SubstrateCalldata`, the pallet lets the beneficiary pre-authorize an arbitrary `RuntimeCall` on the destination chain via a signature, instead of requiring the call to originate as a normal signed extrinsic from that account.

### Title
Cross-chain calldata-execution signature lacks chain/domain binding, enabling authorization replay across parachains - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` lets a beneficiary authorize a `RuntimeCall` to be dispatched on the destination chain by signing `(account_nonce, runtime_call)`. The signed payload never includes the destination chain identity (genesis hash, `StateMachine`/para id, or even this pallet's module id) — only a per-chain `frame_system` nonce and the raw call bytes. [1](#0-0) 

### Finding Description
For the Ed25519 and Sr25519 branches:
```
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
let msg = sp_io::hashing::keccak_256(&payload);
```
and for the ECDSA branch the same `(nonce, runtime_call)` payload is hashed with only an Ethereum personal-sign style byte-length prefix (`ETHEREUM_MESSAGE_PREFIX`) added — still no chain/domain separator. [2](#0-1) 

`nonce` is `frame_system::Pallet::<T>::account_nonce(beneficiary)` — a value scoped to *this* chain's `frame_system`, not a value that is unique across the whole bridge topology. `pallet-hyper-fungible-token` is designed to be deployed as an independent instance on every connected chain (per the docs, "Each token is its own bridge application," with separate `ContractToAsset`/chain configuration per deployment). Any two deployments of this pallet (on different parachains, or the same parachain's asset registered under different `local_asset_id`s) can independently reach the same nonce value for accounts sharing the same 32-byte `AccountId` derivation (e.g. the same EVM address zero-padded via `EvmToSubstrate`, which is deterministic and identical across every deployment using the default converter). [3](#0-2) 

Because the signed message is only `(nonce, runtime_call)` with no chain id, a signature the beneficiary produced authorizing a specific `runtime_call` to run at nonce `n` on Chain A is equally valid input to `on_accept` on Chain B (or against a different `local_asset_id`/token deployment on the same chain) at the moment that beneficiary's nonce there is also `n`. The pallet has no defense against this: it only checks that the recovered/verified key equals `beneficiary`, and increments the local nonce — it never checks that the signature was produced *for this chain and this pallet instance*. [4](#0-3) 

This directly mirrors the report's bug class: a "signing" step (`eth_signMessage`) that is missing the context (origin/domain) that a comparable, safe operation (`eth_signTransaction`) always includes, so a signed authorization can be captured and reused in an unintended context — here, replayed onto a different chain/module instance to execute a `RuntimeCall` the signer never intended to authorize there.

### Impact Explanation
An attacker who captures (or is handed, e.g. via a dApp UI) a beneficiary's signature+`runtime_call` for one HFT deployment can relay that same `PostRequest`/`SubstrateCalldata` payload as a bridged transfer targeting a different HFT-integrated chain (or asset) where the beneficiary's nonce happens to coincide, causing `Dispatchable::dispatch(RawOrigin::Signed(beneficiary))` to execute unauthorized on that chain. Since the dispatch origin is `Signed(beneficiary)`, subject only to `BaseCallFilter`, this is unauthorized execution on behalf of the victim's account — matching "unauthorized transaction or execution" / "logic attacks" in the bounty's impact gate. [5](#0-4) 

### Likelihood Explanation
Exploitability depends on: (1) the same pallet/token being deployed on multiple chains or as multiple local assets with default `EvmToSubstrate` (a documented, likely-common configuration), and (2) the victim's nonce coinciding across the two contexts (trivially true at nonce 0 for a fresh account, or forceable by an attacker who front-loads no-op signed calls to align nonces). The signature capture itself only requires the beneficiary to have signed and disclosed/broadcast a `SubstrateCalldata` once (e.g. handed to a wallet/dApp/relayer as part of a normal bridge transfer), which is the exact "no consent for this specific context" failure mode the external report flags.

### Recommendation
Bind the signed payload to a chain-specific domain separator before hashing, e.g. include the local genesis hash, `T::Version::get().spec_version`, and/or the pallet's own module id / `local_asset_id`, alongside `(nonce, runtime_call)`. This follows the same principle MetaMask enforces for `eth_signMessage`/EIP-712: signed data must be scoped to the exact context it is meant to authorize, not just the raw payload.

### Proof of Concept
1. Deploy `pallet-hyper-fungible-token` on Chain A and Chain B (e.g. two parachains both bridging the same asset, or the same chain registering two `local_asset_id`s for the same underlying token) using the default `EvmToSubstrate` converter.
2. Beneficiary `B` (EVM address `0xAAA...`) is at `account_nonce == 0` on both Chain A and Chain B.
3. `B` signs `keccak256((0u32, runtime_call_A).encode())` intending to authorize `runtime_call_A` only on Chain A, as part of a legitimate bridged transfer.
4. An attacker (or a compromised relayer/dApp that merely relayed the transfer, not a "malicious peer" assumption — any observer of the on-chain `PostRequest` body can read/replay this) constructs a second `PostRequest`/`Message` targeting Chain B with the same `SubstrateCalldata{ signature, runtime_call: runtime_call_A }` and beneficiary bytes, bridged via any valid transfer to `B` on Chain B.
5. On Chain B, `on_accept` computes `nonce = account_nonce(B) == 0`, re-derives the same `msg`, verifies the same signature successfully, and dispatches `runtime_call_A` as `RawOrigin::Signed(B)` on Chain B — a call `B` never authorized for that chain. [6](#0-5)

/// Converts an EVM address to a substrate AccountId
pub trait EvmToSubstrate<T: frame_system::Config> {
	fn convert(addr: H160) -> T::AccountId;
}

/// Default implementation: zero-pads the 20-byte address into a 32-byte AccountId
impl<T: frame_system::Config> EvmToSubstrate<T> for ()
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn convert(addr: H160) -> <T as frame_system::Config>::AccountId {
		let mut account = [0u8; 32];
		account[12..].copy_from_slice(&addr.0);
		account.into()
	}
}
