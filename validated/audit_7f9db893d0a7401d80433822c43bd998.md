## Title
Stale relayer-fee metadata after GET response delivery enables fee double-payment / mispayment analogous to the SubaccountRouter top-up bug - (`evm/src/core/EvmHost.sol`)

## Summary
The reported RFX bug is a class of "partial state update forgets to clear/refresh a fee-bearing value that a sibling code path depends on," causing a fee to be paid out incorrectly. `EvmHost.sol` has the same structural flaw: `dispatchIncoming(GetResponse)` pays the relayer the fee stored in `_requestCommitments[commitment]` but — unlike every other terminal state-transition in the same contract — never deletes that entry afterward.

## Finding Description
`EvmHost.dispatch(DispatchGet)` stores the relayer fee for an outbound GET request in `_requestCommitments[commitment]` [1](#0-0) .

When the response finally arrives, `dispatchIncoming(GetResponse, address relayer)` pays that same `fee` out of `_requestCommitments[commitment]` to the delivering relayer, but the entry is **never deleted**: [2](#0-1) 

Compare this with the two `dispatchTimeOut` overloads in the exact same contract, both of which explicitly `delete _requestCommitments[commitment];` as the very first line, precisely to prevent the stale fee entry from being reused: [3](#0-2) 

Because `_requestCommitments[commitment]` is only cleared as replay protection on the **timeout** path and never on the **successful response** path, the commitment's `FeeMetadata{sender, fee}` remains fully populated after the relayer has already been paid. Two independent, permissionless entrypoints then read/act on that stale value:

1. `fundRequest(bytes32 commitment, uint256 amount)` only checks `metadata.sender != address(0)` before adding `amount` to `metadata.fee` — it has no concept of "already responded": [4](#0-3) 
Since the sender field is never cleared for GET requests that received a response, `fundRequest` will happily accept and lock funds against a commitment whose response has already been delivered and paid out — the added fee has no remaining payout path (this matches the "donation to the protocol" caveat in the docs, but it is silently possible for *any* already-answered GET request, not just already-delivered POST requests as documented).
2. If a timeout for the same commitment is later dispatched by the handler (`dispatchTimeOut(GetRequestTimeout, meta, commitment)`), the stale, still-populated `meta.fee`/`_requestCommitments[commitment].fee` (potentially topped up via (1)) is refunded again to `meta.sender`: [5](#0-4) 

This is the same root cause as the RFX report: a top-up/refund path (`fundRequest`, or the eventual timeout refund) operates on a fee value that a sibling "settlement" path (`dispatchIncoming(GetResponse)`) already consumed but failed to zero out, so the same fee pool can be paid out more than once or accepted for a request that can no longer legitimately use it.

## Impact Explanation
This falls under the accepted Hyperbridge impact classes: potential double-payment of relayer/protocol fee token (fund loss to the fee-token treasury/payer) and false acceptance of a `fundRequest` top-up against an already-settled request commitment, both without requiring a malicious relayer, prover, or admin — any external account holding fee tokens can call `fundRequest` on a commitment whose GET response has already been paid out.

## Likelihood Explanation
`fundRequest` is a fully public, permissionless function with only an `_requestCommitments[commitment].sender != 0` guard, and that guard remains true for GET requests indefinitely after their response is delivered because the entry is never deleted on that path. Triggering the scenario requires no relayer/governance collusion — it only requires knowing a GET request commitment that has already received a response, which is discoverable from public `GetRequestEvent`/`GetRequestHandled` events. The second half of the chain (an actual double-refund at timeout) depends on whether the upstream handler/routing layer can still produce a valid timeout message for an already-responded GET request; I could not fully verify that guard within `HandlerV2.sol`/the coprocessor in the time available, so that specific double-payout leg is not fully proven and should be validated by the engineering team. The `fundRequest`-accepts-a-donation-on-an-answered-GET-request leg, however, is directly demonstrable from the code shown above.

## Recommendation
Mirror the pattern already used in both `dispatchTimeOut` overloads: `delete _requestCommitments[commitment];` immediately after the relayer fee is paid out in `dispatchIncoming(GetResponse)` (on the success branch), so the commitment's `FeeMetadata` cannot be topped up via `fundRequest` or reused by a later timeout dispatch. Additionally, `fundRequest` should explicitly reject commitments whose corresponding response/request has already been finalized (e.g., check `_responseReceipts[commitment]` in addition to `sender != 0`).

## Proof of Concept
1. Caller dispatches a `DispatchGet` with `fee = X`, `payer = attacker`; `_requestCommitments[commitment] = {sender: attacker, fee: X}` is stored (`evm/src/core/EvmHost.sol:999-1001`).
2. The response is proven and delivered; `dispatchIncoming(GetResponse, relayer)` pays `X` fee tokens to `relayer` from the host's balance but leaves `_requestCommitments[commitment]` populated with `{sender: attacker, fee: X}` (`evm/src/core/EvmHost.sol:824-847`).
3. Attacker (or anyone) calls `fundRequest(commitment, Y)` — the `metadata.sender != address(0)` check passes because the entry was never deleted, so `metadata.fee` becomes `X + Y` and the tokens are pulled from the caller (`evm/src/core/EvmHost.sol:1031-1051`).
4. If the routing/handler layer can still produce/accept a `GetRequestTimeout` message for this already-answered commitment (unverified guard outside `EvmHost.sol`), `dispatchTimeOut(GetRequestTimeout, meta, commitment)` refunds the full `X + Y` to `meta.sender`, i.e., the relayer fee `X` has now been paid out twice (once to the relayer in step 2, once refunded in step 4), and the `Y` top-up is either lost or refunded — both outcomes represent fee-token loss/duplication unaccounted for by the protocol.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;

            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

        emit RequestFunded({commitment: commitment, newFee: metadata.fee});
    }
