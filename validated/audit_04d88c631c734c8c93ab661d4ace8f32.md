Confirmed: `VWAPOracle` and `IIntentPriceOracle.recordSpread` are purely observational — they compute and log a spread after tokens have already moved, with no return value or revert path that `fillOrder` checks. The IntentGateway calls `recordSpread` in `fillOrder` only after `_fillSameChain`/`_fillCrossChain` have already transferred tokens to the beneficiary.

### Title
Price oracle is fill-and-forget: `fillOrder` accepts any solver-chosen output amount with no pre-trade price/deviation check - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`fillOrder` invokes `IIntentPriceOracle(_params.priceOracle).recordSpread(...)` (`evm/src/apps/IntentGatewayV2.sol:448-451`) strictly *after* `_fillSameChain`/`_fillCrossChain` have already transferred the escrowed input tokens to the solver and delivered the output tokens to the beneficiary [1](#0-0) . `VWAPOracle.recordSpread` (`evm/src/utils/VWAPOracle.sol:170-216`) only writes a cumulative weighted-average spread to storage and emits an event — it never reverts, returns a bounded value, or is consulted by `fillOrder` before releasing funds [2](#0-1) . This is the exact bug class from the external report: a trading/fill path with a "price recorder" that has no enforcement power, so trades execute at whatever price the counter-party (solver) supplies, unconstrained by any on-chain minimum-acceptable-price or maximum-deviation check.

### Finding Description
For "same-token" cross-chain/same-chain swaps (the class `VWAPOracle` is documented to track — see `@dev Only supports same-token swaps` [3](#0-2) ), the only on-chain amount check performed before releasing user funds is `solverAmount < totalRequired` in `_fillCrossChain` [4](#0-3) , or `remaining`/proportional-fill bookkeeping in `_fillSameChain` [5](#0-4) . Both checks only guarantee the solver supplies *at least* `order.output.assets[i].amount` — a value fixed by the user/SDK at order-placement time, before the fill executes.

Between order placement and fill, market conditions or fee-token/base-asset value can diverge substantially (this is intent/limit-order design, so it's expected the user pre-commits to `amountOut`). The `priceOracle` hook was clearly *intended* as the governance-configurable safety mechanism referenced by `Params.priceOracle` — the gateway is architected to consult a price oracle around every fill. But the concrete `VWAPOracle` implementation, and the `IIntentPriceOracle` interface it satisfies, provide no `revert`-capable pre-check: `recordSpread` has no return value that `fillOrder` inspects, and it is called only *after* `_fillCrossChain`/`_fillSameChain` already moved funds (`evm/src/apps/IntentGatewayV2.sol:442-451`). There is no `maxDeviationBps`, no minimum spread enforcement, and no revert on adverse spread anywhere in `VWAPOracle` or the interface it implements [6](#0-5) .

Consequently, even when a gateway deployment wires up `_params.priceOracle`, there is no code path anywhere in the repo that uses that oracle to reject a fill whose solver-supplied amounts represent an anomalous/manipulated spread from the historical VWAP. The oracle can only ever passively record a bad trade after it has happened — matching precisely the "lack of slippage checks... no mechanism to limit the maximum acceptable price change" pattern from the external report.

### Impact Explanation
For any order type where the escrow/output relationship isn't already the exact 1:1 amount fixed by the user (e.g., partial fills reaching remaining thresholds, or any future gateway/oracle wiring that assumes `priceOracle` provides protective enforcement), there is no on-chain backstop against a solver filling at a spread far worse than fair market value once the order's fixed amounts are satisfied. Because `recordSpread` cannot revert the fill, any assumption by integrators/governance that "the price oracle protects users" is false — the gateway silently accepts and settles trades at any post-fact-recorded bad spread, and beneficiaries only discover the loss via the emitted `SpreadRecorded` event, after their funds have already moved [7](#0-6) .

### Likelihood Explanation
High for any deployment relying on `_params.priceOracle` as a protective control, since the current interface/implementation cannot express or enforce a bound — the vulnerability is deterministic and requires no privileged actor, just a solver filling at the user-specified (but potentially stale/mispriced) output amount. No malicious peer, relayer, or governance compromise is required.

### Recommendation
Change `IIntentPriceOracle.recordSpread` (or add a companion `checkSpread`/`validateFill`) to return a boolean/revert when the computed `spreadBps` for a fill exceeds a governance-configured maximum deviation from the recorded cumulative VWAP, and have `IntentGatewayV2.fillOrder` call this *before* `_fillSameChain`/`_fillCrossChain` transfer any tokens, reverting the entire fill on violation.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `_params.priceOracle` set to a `VWAPOracle` instance, intending it as a slippage/spread guard for same-token cross-chain swaps.
2. A user places a same-token order (e.g., USDC on chain A → USDC on chain B) with `output.assets[0].amount` computed from a stale quote.
3. A solver fills the order via `fillOrder`, supplying exactly `totalRequired` (satisfying `_fillCrossChain`'s only check, `solverAmount < totalRequired`) even though this represents a spread far worse than the token's historical VWAP.
4. `_fillCrossChain` transfers the escrowed input to the solver and the output to the beneficiary — completing before `recordSpread` is even called [1](#0-0) .
5. `VWAPOracle.recordSpread` executes afterward, updates `_tokenSpreads` and emits `SpreadRecorded` with a large negative `spreadBps`, but this has zero effect on the already-settled fill — there is no revert path.

Note: I was unable to fully verify whether any other in-repo caller (e.g., `pallet-intents-coprocessor` in `modules/pallets/intents-coprocessor/src/types.rs`, which also references `priceOracle`) wires spread enforcement differently on the Substrate side; the index did not surface enough of that file's contents to confirm. If deeper verification of that Rust pallet's behavior is needed, a full Devin session with repository access would be required to inspect it in full.

    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }
