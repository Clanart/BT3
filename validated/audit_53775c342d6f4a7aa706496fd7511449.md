### Title
FROST spec promises a DLEq proof binding multi-generator nonce commitments, but `NonceCommitments`/`Commitments::read` accept unproven commitments — ([File: crypto/frost/src/nonce.rs](https://github.com/Annirich/serai--017/blob/develop/crypto/frost/src/nonce.rs#L33-L80))

### Summary
`spec/cryptography/FROST.md` states that nonce commitments across multiple generators are bound by "an extended CP93's Discrete Log Equality Proof" hashed into a single proof for `d + be`. The implementation contains no DLEq at all: `grep` for `DLEq|dleq` across `crypto/frost/**` returns zero hits, and `GeneratorCommitments::read`/`NonceCommitments::read`/`Commitments::read` simply deserialize two points per generator (`crypto/frost/src/nonce.rs:34-35`, `74-79`, `133-137`). A participant's preprocess therefore carries no proof that `D`/`E` commitments over different generators commit to the same scalars.

### Finding Description
In `NonceCommitments::new`, an honest signer generates `commitments[j] = (g_j * d, g_j * e)` for the same nonce pair `(d, e)` over every generator `g_j` (`crypto/frost/src/nonce.rs:53-69`). The spec's extension exists precisely so a malicious signer cannot send `g1 * a` and `g2 * b` with `a != b`. Yet `read_preprocess` (`crypto/frost/src/sign.rs:276-281`) only reads the raw points, and `sign` (`crypto/frost/src/sign.rs:325-359`) transcripts and inserts them into `BindingFactor` without verifying equality of discrete logs. The `Algorithm` trait doc (`crypto/frost/src/algorithm.rs:44-48`) explicitly disclaims this check ("No guarantees the commitments are internally consistent... Any Algorithm which specifies multiple generators for a single nonce must handle that itself"), directly contradicting the spec which claims the library performs it. For any `Algorithm` returning `nonces()` with more than one generator per nonce, an attacker-controlled preprocess can encode inconsistent nonce scalars: `nonce_sums`/`B.bound()` are built from attacker-chosen points (`crypto/frost/src/sign.rs:371-383`), and `verify`/`verify_share` evaluate `R + cA - sG` against those points (`crypto/frost/src/algorithm.rs:213-230`), so the attacker effectively chooses a different effective nonce per generator while all per-share checks still pass against the supplied commitments.

### Impact Explanation
An unprivileged signer reachable through `read_preprocess`/`sign` can submit commitments that are not internally consistent across generators. For a multi-generator algorithm this breaks the binding between the commitment the group signs under (`nonce_sums`) and the scalar the attacker actually uses (`sign_share` receives the locally-generated nonces, but verification statements are reconstructed from attacker-supplied `bound` commitments). This yields a discrepancy between what the specification guarantees (DLEq-bound multi-generator commitments) and what is enforced, enabling inconsistent-signature/malleability attacks and potential share-forgery in algorithms relying on the documented guarantee. It also silently shifts a security-critical requirement onto algorithm implementers, who are told by the public spec that the check already exists.

### Likelihood Explanation
Reachable by any participant able to send a preprocess message (untrusted bytes into `Commitments::read` → `sign`). Exploitable whenever a deployed `Algorithm` uses `nonces()` with `generators.len() > 1` — the exact case the spec's DLEq extension was designed for. No multi-generator algorithm ships in the scoped crates, so exploitation today depends on a consumer relying on the documented guarantee; the discrepancy itself is unconditional.

### Recommendation
Either implement the documented DLEq proof inside `Preprocess`/`NonceCommitments` — prove once for `d + be` across all generators after hashing commitments to a binding factor, and verify it in `read_preprocess`/`sign` before inserting into `B` — or correct `spec/cryptography/FROST.md` to state that multi-generator consistency is *not* enforced by the library and must be proven inside `Algorithm::Addendum`/`process_addendum`. Given the spec's stated intent, enforcing the DLEq in the library is preferable.

### Proof of Concept
1. Call `machine.read_preprocess` with bytes encoding `GeneratorCommitments([g1 * a, g1 * e])` followed by `GeneratorCommitments([g2 * b, g2 * e])` where `a != b`, for an `Algorithm` whose `nonces()` returns `vec![vec![g1, g2]]`.
2. Observe it parses successfully (`NonceCommitments::read` performs only point decoding via `Curve::read_G`, `nonce.rs:74-79`), and `sign` accepts it into `BindingFactor` (`sign.rs:356`) with no DLEq verification anywhere — confirmed by the absence of any `dleq` reference in `crypto/frost` and the trait doc's own disclaimer at `algorithm.rs:44-48`.
3. The resulting `Rs` (`B.nonces(&nonces)`, `sign.rs:383`) reflect nonce `a` under `g1` and nonce `b` under `g2`, while the spec asserts this is impossible.
