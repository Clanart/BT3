### Title
No operator can ever be reimbursed for a payout tx whose withdrawal UTXO is spent without a valid OP_RETURN operator tag, permanently freezing the corresponding deposit's move-to-vault UTXO - ([File: core/src/verifier.rs])

### Summary
`Operator::withdraw` (`core/src/operator.rs:560-627`) constructs the payout transaction from a user-supplied `SinglePlusAnyoneCanPay` signature that only commits input 0 and output 0 of the payout tx, so anyone who has that signature (the withdrawer itself) can construct their own competing spend of the same `withdrawal_utxo` that satisfies output 0 but attaches no OP_RETURN (or a malformed one). Once such a transaction confirms first, `Verifier::update_finalized_payouts` records `payout_payer_operator_xonly_pk = NULL` for that withdrawal index, and `Database::get_first_unhandled_payout_by_operator_xonly_pk` can never match `NULL` against any operator's specific key, so no operator's `PayoutCheckerTask::run_once` ever calls `Operator::handle_finalized_payout` for that index, permanently freezing the associated deposit's move-to-vault UTXO.

### Finding Description
Binding claimed: for every withdrawal `idx` where `withdrawals.payout_txid IS NOT NULL`, there exists some operator `op` such that `Database::get_first_unhandled_payout_by_operator_xonly_pk(op.xonly_pk)` eventually returns `idx`, which leads `PayoutCheckerTask::run_once` to call `Operator::handle_finalized_payout` and eventually spend the move-to-vault UTXO via a Reimburse tx.

Root cause and path:
1. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with a single input (`withdrawal_utxo`, spent via `SpendPath::KeySpend` using only `user_sig`) and a third output that is an OP_RETURN embedding the *operator's own* xonly pubkey — but this OP_RETURN output is added by whichever party constructs the transaction, not committed by the signature.
2. The user's signature is required to have `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:161-187`), which by Bitcoin's sighash rules commits only input index 0 and output index 0 — no other outputs (including the OP_RETURN) are covered by the signature, and `ANYONECANPAY` means other inputs are unrestricted too.
3. Consequently, anyone who has the raw `(withdrawal_index, in_signature, in_outpoint, out_script_pubkey, out_amount)` tuple — which the withdrawer itself always has, since they are the one calling Citrea's `withdraw()` and supplying this exact signature to the aggregator/operators via gRPC — can independently construct and broadcast a transaction spending `withdrawal_utxo` with output 0 fixed as required, but with no OP_RETURN output (or an OP_RETURN with garbage/invalid xonly-pk bytes) at all, and get it mined ahead of any operator's own `Operator::withdraw` (`core/src/operator.rs:560-692`) broadcast, e.g., by paying a higher fee.
4. When this transaction confirms, `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses the payout tx's OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`; when missing or invalid it explicitly sets `operator_xonly_pk = None` (lines 2316-2321), and persists `payout_payer_operator_xonly_pk = NULL` via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`).
5. `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) filters `WHERE w.payout_payer_operator_xonly_pk = $1`; SQL equality against a bound, non-null operator xonly-pk value never matches a `NULL` column, so this query never returns this withdrawal `idx` for *any* operator's key.
6. `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-51`) returns `Ok(false)` forever for this row because `unhandled_payout` is always `None`, so `Operator::handle_finalized_payout` (`core/src/operator.rs:839+`) is never called, no kickoff is ever produced, and the Reimburse tx that would spend the deposit's move-to-vault UTXO never exists.
7. As an additional confirmation of the trap, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1914`) explicitly treats a `None` `operator_xonly_pk_opt` as malicious (lines 1882-1885) — so even if some operator tried to manually claim this withdrawal via a kickoff (bypassing the normal `PayoutCheckerTask` flow), it would be flagged malicious and challenged, closing off any alternate recovery path.

No existing guard prevents this: `SECP.verify_schnorr` in `Operator::withdraw` only verifies the signature is valid for output 0/input 0 — it does not, and structurally cannot, constrain outputs beyond index 0 because of the `SinglePlusAnyoneCanPay` sighash semantics. `only_aggregator_and_self`, `is_deposit_valid`, `is_profitable`, and database uniqueness constraints are irrelevant here since the malicious transaction is broadcast directly to Bitcoin, bypassing all Clementine gRPC-layer checks entirely.

### Impact Explanation
The deposit's move-to-vault UTXO (holding the bridged BTC for that deposit) becomes permanently frozen: no operator can ever be credited as the payer for this withdrawal index, so no Reimburse tx targeting this deposit can ever be constructed or broadcast by any operator, and the withdrawal is marked handled (`payout_txid` set) so the withdrawal path itself cannot be re-attempted. This is repeatable for every withdrawal an attacker chooses to race in this way, across any number of deposits and independent of which operator(s) are online, matching the "move-to-vault UTXO permanently frozen" critical impact category. Note the withdrawer only spends funds they already control as the input to their own race transaction — the direct monetary loss is that the corresponding deposit's BTC is stranded (never released to any operator's collateral loop) rather than an immediate transfer of bridge funds to the attacker.

### Likelihood Explanation
The attacker needs no privileges beyond what is explicitly in-scope: they call `withdraw` on the Citrea contract themselves, and hold the `SinglePlusAnyoneCanPay` signature and `withdrawal_utxo` outpoint they authored. They only need to broadcast a competing Bitcoin transaction (paying normal Bitcoin fees) that reuses the same input+output-0 but strips or corrupts the OP_RETURN, and get it confirmed before any operator's payout tx. Given operators poll/react asynchronously and the attacker can prepare and fee-bump their transaction immediately upon initiating the withdrawal, this is straightforward and repeatable per-withdrawal at the cost of ordinary Bitcoin transaction fees.

### Recommendation
Do not rely on an unauthenticated third output (OP_RETURN) to determine payer credit for a `SinglePlusAnyoneCanPay`-signed payout transaction. Either (a) commit the operator-identifying data inside the sighash-covered portion of the transaction (e.g., require `SIGHASH_ALL` scoped to the specific operator-constructed transaction, or use `SIGHASH_SINGLE` with the OP_RETURN placed at index 0 alongside the payout, or add operator commitment via a covered input/output), or (b) provide an off-Bitcoin (e.g., Citrea-committed or aggregator-signed) mechanism to record legitimate operator fronting independent of what confirms on Bitcoin, so that a race-won unauthenticated OP_RETURN cannot permanently orphan the withdrawal. Additionally, consider allowing an operator (or the protocol) to reclaim/mark a withdrawal as "unfrontable" and unlock a fallback reimbursement/verifier-authorized path for withdrawals whose payout tx lacks a valid operator tag, rather than freezing the deposit's move-to-vault UTXO indefinitely.

Test outline:
1. Run a single deposit via `run_single_deposit` to obtain `move_txid`/`deposit_outpoint`.
2. Use `generate_withdrawal_transaction_and_signature` (or `sign_withdrawal_output`) to get `(withdrawal_utxo, payout_txout, sig)` with `TapSighashType::SinglePlusAnyoneCanPay`.
3. Register the withdrawal in mock Citrea (as in existing e2e tests) so `withdrawal_utxo`/`payout_txout` are known to operators.
4. Instead of calling `operator.withdraw(...)`, directly build and broadcast (via `rpc.send_raw_transaction`) a transaction spending `withdrawal_utxo` with output 0 = `payout_txout` (satisfying the committed signature) and NO OP_RETURN output (or a garbage OP_RETURN), signed with `sig`.
5. Mine blocks so the tx and finality depth pass, letting `Verifier::update_finalized_payouts` process it.
6. Assert `db.get_payout_info_from_move_txid(None, move_txid).await.unwrap().unwrap().0 == None` (operator xonly pk recorded as NULL) — left side of the binding.
7. Mine arbitrarily many additional blocks and poll (with timeout) `PayoutCheckerTask::run_once` for every configured operator (or `db.get_handled_payout_kickoff_txid(None, payout_txid)`); assert it never returns `true`/`Some` (right side of the binding never satisfied) even after extended block mining, proving the withdrawal — and thus the deposit's move-to-vault UTXO — is permanently orphaned from any Reimburse path.
