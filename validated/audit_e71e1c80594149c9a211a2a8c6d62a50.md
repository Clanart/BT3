### Title
`WombatStaking.depositLP` mints receipt tokens 1:1 with the requested amount instead of the actual LP tokens received, breaking accounting for fee-on-transfer/deflationary LP tokens - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` transfers `_lpAmount` of `poolInfo.lpAddress` from the caller and then mints the exact same `_lpAmount` of receipt tokens, without verifying how many LP tokens the contract actually received. Every other transfer-then-account flow in this same contract and its pool helpers explicitly guards against this by measuring the balance before and after the transfer.

### Finding Description
In `WombatStaking.deposit()` the contract correctly computes the actual amount of LP tokens obtained from the external pool by diffing balances before and after the deposit call, and only mints receipt tokens for the amount actually received: [1](#0-0) 

By contrast, `depositLP()` skips this defensive pattern entirely — it transfers `_lpAmount` in via `safeTransferFrom` and immediately mints `_lpAmount` worth of receipt tokens, assuming the transferred-in amount equals the amount received: [2](#0-1) 

The pool helpers that call into `WombatStaking` (e.g. `WombatPoolHelperV2.depositLP`, `AnkrBNBPoolHelper.depositLP`) do use a before/after balance diff on their own receipt/staking token balance, but that only protects against fee-on-transfer on the *receipt* token flow — it does nothing to protect `WombatStaking` itself, since `WombatStaking.depositLP` is the function that actually custodies the underlying LP token and mints the 1:1-backed receipt token supply: [3](#0-2) 

If the configured `poolInfo.lpAddress` for any pool is (or later becomes, e.g. via a token upgrade/rebasing mechanism) a fee-on-transfer or rebasing/deflationary token, `WombatStaking` will hold strictly less of that LP token than the amount of receipt tokens it minted for the depositor. This creates a permanent shortfall between the receipt-token supply (claims) and the actual custodied LP balance (backing).

### Impact Explanation
Because receipt tokens are burned 1:1 against LP custody on withdrawal (`withdraw`/`burnReceiptToken`), an under-collateralized pool means that once enough receipt-token holders attempt to withdraw, the contract will run out of the underlying LP token before all legitimate claims are honored — later withdrawers permanently lose access to their funds. This satisfies the "protocol insolvency" / "permanent freezing of funds" impact bar, since the deficit compounds with every deposit of the affected token and is unrecoverable without an external bailout.

### Likelihood Explanation
Triggering this requires only an ordinary wallet calling the already-public `depositLP()` function against a pool whose `lpAddress` behaves as fee-on-transfer/deflationary; no privileged role is needed to exploit the missing balance check itself. The likelihood is bounded by whether such an LP token is ever configured for a pool, but the code contains no defense against it — unlike the parallel `deposit()` path in the very same contract, which explicitly guards against exactly this scenario, confirming the omission in `depositLP()` is a genuine, exploitable inconsistency rather than an intentional design choice.

### Recommendation
Mirror the pattern already used in `deposit()`: measure `IERC20(poolInfo.lpAddress).balanceOf(address(this))` before and after the `safeTransferFrom` call in `depositLP()`, and mint/route the receipt token and downstream reward accounting using the actual received delta rather than the caller-supplied `_lpAmount`.

### Proof of Concept
1. Admin (non-maliciously) whitelists a pool whose `lpAddress` implements a transfer fee or rebase (deflationary) mechanic.
2. An ordinary user calls `WombatStaking.depositLP(lpAddress, 1000e18, user)`.
3. Due to the token's fee-on-transfer behavior, `WombatStaking` actually receives, say, 990e18 tokens, but `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` mints 1000e18 receipt tokens — a 10e18 deficit is created.
4. Repeating deposits/withdrawals accumulates the shortfall until the pool cannot fulfill all outstanding receipt-token redemptions, permanently freezing/losing funds for the last withdrawers. [2](#0-1)

    function depositLP(
        address _lpAddress,
        uint256 _lpAmount,
        address _for
    ) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {
        // Get information of the Pool of the token
        Pool storage poolInfo = pools[_lpAddress];

        // Transfer lp to this contract and stake it to wombat
        IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);

        _toMasterWomAndSendReward(_lpAddress, _lpAmount, true); // triggers harvest from wombat exchange
        IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);

        emit NewLPDeposit(_for, poolInfo.lpAddress, _lpAmount, poolInfo.receiptToken, _lpAmount);
    }
