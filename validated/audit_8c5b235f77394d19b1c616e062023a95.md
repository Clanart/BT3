### Title
SignableTransaction signs a sighash committing to attacker-controlled prevout data, producing signatures that are invalid on-chain and permanently failing the spend - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Tokemak issue (the swap reverts because the tokens it tries to spend were never made available), `SignableTransaction`/`TransactionMachine` build and sign a spend over `ReceivedOutput` fields that are never validated against on-chain state. The only check performed is that the output's `script_pubkey` matches `key + offset·G` (`multisig`, send.rs:277). The `value` and `outpoint` carried inside `ReceivedOutput` are trusted blindly, yet the Taproot sighash commits to all prevouts (`Prevouts::All`, send.rs:375). A forged `ReceivedOutput` therefore causes the threshold group to sign a transaction whose signatures Bitcoin consensus will reject, leaving the real UTXO unspent — the spend "cannot get done".

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122`) deserializes `offset`, a `TxOut` (script_pubkey + value), and an `outpoint` from untrusted bytes with no validation that the outpoint exists or that `output.value` equals the actual UTXO amount.

`SignableTransaction::new` then:
- sums `input.output.value` as `input_sat` for fee/change math (send.rs:175),
- stores `inputs` verbatim into `prevouts` (send.rs:253),
- and `multisig` only verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` (send.rs:277) — it does not check the value or outpoint.

At signing time, `TransactionSignMachine::sign` computes `cache.taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), TapSighashType::Default)` (send.rs:375–386), so every signature cryptographically commits to the claimed prevout `TxOut`s. Bitcoin consensus, however, verifies taproot key-spend signatures against the real prevouts fetched from the UTXO set. If the deserialized `TxOut.value` differs from the actual output (or the outpoint doesn't exist / was already spent), every validator produces a valid FROST share, `complete` assembles a fully-signed `Transaction` (send.rs:417–427), yet the transaction can never be included in a block.

Like the referenced bug — where `LiquidationRow` calls `swap` without ever transferring the sell tokens, so the operation reverts every time — here the spend path proceeds as if the inputs were provisioned correctly, but the "balance" the signatures commit to was never what is actually on chain, so the spend can never succeed.

### Impact Explanation
An unprivileged party able to feed `ReceivedOutput` bytes into a signing flow (per the threat model, untrusted bytes to `ReceivedOutput::read` / `multisig` / `sign` are in scope) can make the threshold network sign a transaction that is invalid by consensus: the FROST ceremony completes "successfully", a signed `Transaction` is returned, but broadcast always fails. This yields a persistent denial of service on spends of the targeted UTXO(s) — the real outputs stay locked (rewards/funds "stuck", mirroring the original report's impact) — and can repeatedly burn signer bandwidth/nonce rounds. Additionally, fee and change computation is driven by the forged `value` (send.rs:175, 228–234), so honest accounting of the wallet balance is corrupted even before the spend fails.

### Likelihood Explanation
Any path where `ReceivedOutput`s are serialized, relayed, or re-deserialized across trust boundaries exposes this. An attacker does not need a key share or validator status: they only need to supply a `ReceivedOutput` whose `script_pubkey` matches a registered offset script (publicly derivable — offsets are `hash_to_F(KEY_DST, ...)` values, see `processor/src/networks/bitcoin.rs:333–344`) while corrupting `value`/`outpoint`. The `multisig` check does not reject this because it validates only the script. Severity is Medium: the consequence is stuck funds and wasted signing rounds rather than theft or key compromise.

### Recommendation
Bind each input to verified chain data before signing. Either:
- resolve `outpoint` via RPC inside `multisig`/`SignableTransaction::new` and assert the returned `TxOut` equals `input.output` (value and script_pubkey), refusing to build the machine otherwise; or
- treat `ReceivedOutput` as authenticated-only data (MAC/encrypt or restrict `read` consumers to scanner-produced outputs) so externally supplied values cannot reach the signer.
