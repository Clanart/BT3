### Title

Bitcoin deposit data from a later transaction overwrites earlier scanned outputs' instructions - (File: processor/src/networks/bitcoin.rs)

### Summary

`Bitcoin::get_outputs` accumulates matched outputs across an entire block, but when each transaction is processed it assigns that transaction's extracted Serai data and presumed origin to every accumulated output, including outputs from earlier transactions. An attacker can therefore place a transaction paying Serai's external address later in the same block and overwrite an earlier depositor's instruction data, redirecting the deposit into an attacker-chosen instruction or refund origin.

### Finding Description

For each non-coinbase transaction, `get_outputs` calls `Scanner::scan_transaction` and appends any matching outputs to the block-wide `outputs` vector. The `outputs` vector is not reset per transaction. After processing a transaction, the code extracts `data` and `presumed_origin` and iterates over `&mut outputs`, assigning those values to all accumulated outputs rather than only outputs created by the current transaction. [1](#0-0) 

`extract_serai_data` accepts attacker-controlled transaction metadata: the last push of an `OP_RETURN` output, or the second-to-last witness item when the revealed script starts with the expected `OP_SHA256 ... OP_EQUALVERIFY` pattern. [2](#0-1) 

The overwritten `data` is security-sensitive: `instruction_from_output` decodes `OutputType::External` output data as `Shorthand`, converts it to `RefundableInInstruction`, pairs it with the output balance, and optionally uses the overwritten presumed origin as the refund origin. [3](#0-2) 

### Impact Explanation

An attacker who broadcasts a valid Bitcoin transaction paying Serai's external address, and has it ordered after a victim's deposit in the same finalized block, can overwrite the earlier output's instruction with arbitrary valid `Shorthand`. This can change the action associated with the victim's deposited balance, including redirecting the resulting minted assets or refund path to the attacker. This is a cross-transaction data-confusion vulnerability analogous to intent redirection: attacker-controlled bytes cause an earlier, unrelated deposit to invoke an unintended internal action.

### Likelihood Explanation

The attacker only needs to send a transaction to Serai's known external address and have it included after the victim transaction in a scanned block. Transaction ordering is not entirely attacker-controlled, but miners, coordinated transaction submission, and ordinary block-order variability make the condition feasible. No validator key, private key, malformed curve point, or invalid Bitcoin transaction is required.

### Recommendation

Track and mutate only the outputs found in the current transaction. For example, maintain `let tx_outputs = scanner.scan_transaction(tx)`, populate `data`/`presumed_origin` on `tx_outputs`, and only then extend the block-wide result vector with those finalized outputs. A regression test should place two transactions paying the external address in one block with distinct instructions and assert each output retains its own transaction's data and origin.

### Proof of Concept

```text
Block:
  tx0:
    output[0] -> Serai external address, 100_000 sats
    output[1] -> OP_RETURN encode(
      RefundableInInstruction {
        origin: victim_origin,
        instruction: Transfer(victim_serai_address),
      }
    )

  tx1:  // later in block.txdata
    input -> valid attacker input
    output[0] -> Serai external address, >= DUST sats
    output[1] -> OP_RETURN encode(
      RefundableInInstruction {
        origin: attacker_origin,
        instruction: Transfer(attacker_serai_address),
      }
    )
```

When processing `tx0`, Serai correctly records its instruction. When processing `tx1`, `extract_serai_data(tx1)` returns the attacker's instruction and the subsequent loop over all accumulated `outputs` overwrites `tx0`'s output as well. The scanner eventually decodes both outputs using the attacker's `Transfer(attacker_serai_address)` instruction.

fn instruction_from_output<N: Network>(
  output: &N::Output,
) -> (Option<ExternalAddress>, Option<InInstructionWithBalance>) {
  assert_eq!(output.kind(), OutputType::External);

  let presumed_origin = output.presumed_origin().map(|address| {
    ExternalAddress::new(
      address
        .try_into()
        .map_err(|_| ())
        .expect("presumed origin couldn't be converted to a Vec<u8>"),
    )
    .expect("presumed origin exceeded address limits")
  });

  let mut data = output.data();
  let max_data_len = usize::try_from(MAX_DATA_LEN).unwrap();
  if data.len() > max_data_len {
    error!(
      "data in output {} exceeded MAX_DATA_LEN ({MAX_DATA_LEN}): {}. skipping",
      hex::encode(output.id()),
      data.len(),
    );
    return (presumed_origin, None);
  }

  let shorthand = match Shorthand::decode(&mut data) {
    Ok(shorthand) => shorthand,
    Err(e) => {
      info!("data in output {} wasn't valid shorthand: {e:?}", hex::encode(output.id()));
      return (presumed_origin, None);
    }
  };
  let instruction = match RefundableInInstruction::try_from(shorthand) {
    Ok(instruction) => instruction,
    Err(e) => {
      info!(
        "shorthand in output {} wasn't convertible to a RefundableInInstruction: {e:?}",
        hex::encode(output.id())
      );
      return (presumed_origin, None);
    }
  };

  let mut balance = output.balance();
  // Deduct twice the cost to aggregate to prevent economic attacks by malicious miners against
  // other users
  balance.amount.0 -= 2 * N::COST_TO_AGGREGATE;

  (
    instruction.origin.or(presumed_origin),
    Some(InInstructionWithBalance { instruction: instruction.instruction, balance }),
  )
