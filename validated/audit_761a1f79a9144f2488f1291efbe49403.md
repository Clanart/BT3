### Title
Panic on out-of-range `sender`/`recipient` participant index in PedPoP blame evaluation allows a malicious DKG participant to crash an honest party - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender` and `recipient` `Participant` indexes supplied by the accusing party and index `HashMap`s with them (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`) without validating that the index is within `1 ..= n`. A `Participant` can be any non-zero `u16`. A crafted blame claim naming a non-existent sender causes a `HashMap` index panic — the Rust analog of CVE-2016-2145's unchecked-access crash on attacker-controlled input — killing the node process evaluating blame.

### Finding Description
`Decryption::decrypt_with_proof` first verifies the message's proof-of-possession and the accuser-supplied `EncryptionKeyProof` DLEq, evaluating `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388`. After `decrypt_with_proof` returns `Ok`, `blame_internal` indexes `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599`. Neither `sender` nor `recipient`/`decryptor` is checked against `params.n()` or map membership anywhere in `blame`, `blame_internal`, or `decrypt_with_proof` (`crypto/dkg/pedpop/src/lib.rs:575-609`, `crypto/dkg/pedpop/src/encryption.rs:366-397`). `Participant::new` accepts any non-zero `u16`, so `sender = Participant(0xFFFF)` is a representable value far outside the registered `1 ..= n` keys. Because these are `std::collections::HashMap` `Index` accesses, a missing key panics.

All gates needed to reach the panic are satisfiable by the attacker: the PoP only binds the *claimed* `sender` value into the Schnorr challenge via `pop_challenge` (`crypto/dkg/pedpop/src/encryption.rs:302-324`) — it does not authenticate that `sender` is a real participant, so the accuser can sign a PoP claiming `from = Participant(0xFFFF)`. The DLEq proof is over the accuser's own ECDH key (`enc_keys[decryptor]` where `decryptor` is the accuser's real index), which the accuser can produce since they know their own encryption private key (`crypto/dkg/pedpop/src/encryption.rs:381-392`).

### Impact Explanation
A single malicious DKG participant (or any party able to file a blame claim) crashes any honest node or third-party auditor that evaluates the claim via `BlameMachine::blame` or `AdditionalBlameMachine::blame`. This is an unauthenticated-cost, deterministic process crash: the accusing party supplies only public inputs (participant indexes, a self-crafted `EncryptedMessage`, and a self-generated `EncryptionKeyProof`). In a coordinator/tributary deployment this aborts the DKG fault-resolution path and can be used to prevent blame from ever being assigned, stalling key rotation and any signing dependent on it.

### Likelihood Explanation
Blame evaluation is exactly the path a faulty/malicious participant wants to disrupt, so the actor most incentivized to trigger this is the one with access to it. Crafting the inputs requires only standard Schnorr/DLEq proving over the accuser's own keys — no threshold cooperation, no forged signatures. The only caveat: `blame` requires the caller to pass the attacker-chosen `sender` index through; the documented protocol says the message should be authenticated as coming from `sender`, but nothing in the library enforces or validates this, and an accusing party can name an arbitrary index in their accusation.

### Recommendation
Validate `sender` and `recipient` before indexing: in `blame_internal` and `decrypt_with_proof`, use `HashMap::get` and return a defined fault (e.g., blame the accuser or return an error) when the index is absent, rather than relying on `Index` panics. `AdditionalBlameMachine::new` should also enforce that each registered `commitments` vector has length `t`.

### Proof of Concept
```rust
// Honest node completed a PedPoP DKG with n participants and holds a
// BlameMachine (or an auditor built AdditionalBlameMachine::new over the
// authenticated commitment messages for participants 1..=n).

// Malicious accuser (participant i, with encryption key e_i) crafts:
let bogus_sender = Participant::new(n + 1).unwrap(); // any index > n

// 1. A self-made EncryptedMessage with a valid PoP bound to `bogus_sender`.
//    pop_challenge binds only the claimed sender index, not its validity:
let k = Zeroizing::new(C::random_nonzero_F(&mut rng));
let pub_key = C::generator() * k.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(&mut rng));
let pop = SchnorrSignature::<C>::sign(
  &k, nonce,
  pop_challenge::<C>(context, C::generator() * nonce.deref(), pub_key,
                     bogus_sender, share_repr.as_ref()),
);
let msg = EncryptedMessage { key: pub_key, pop, msg: /* arbitrary repr */ };

// 2. A valid EncryptionKeyProof for the accuser's own ECDH key:
let proof_key = pub_key * e_i;            // = e_i * msg.key
let proof = EncryptionKeyProof {
  key: Zeroizing::new(proof_key),
  dleq: DLEqProof::prove(&mut rng, &mut encryption_key_transcript(context),
                         &[C::generator(), pub_key], &e_i_zeroizing),
};

// 3. File the accusation. The honest evaluator runs:
blame_machine.blame(bogus_sender, accuser_i, msg, Some(proof));
//    -> decrypt_with_proof passes (valid PoP + valid DLEq for accuser's key)
//    -> blame_internal evaluates self.commitments[&bogus_sender]
//    -> HashMap Index panic: process aborts mid-blame-resolution
```
Relevant code: `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`), `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366-397`), `AdditionalBlameMachine::new`/`blame` (`crypto/dkg/pedpop/src/lib.rs:649-682`).
