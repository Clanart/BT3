### Title
Payout tx OP_RETURN operator attribution is unauthenticated under `SinglePlusAnyoneCanPay`, allowing forged payer credit/blame - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the payout tx's user input with `TapSighashType::SinglePlusAnyoneCanPay`, which per BIP-341/BIP-143 only commits to the specific input being signed and to output index 0 (the withdrawer's payout output). The OP_RETURN output at index 2, which carries the `operator_xonly_pk` that `update_finalized_payouts`/`is_kickoff_malicious` use to attribute the payout to an operator, is completely outside the signed message and can be freely substituted by anyone who can observe the withdrawer's signature and win the on-chain race for the withdrawal UTXO.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk` (as read by `is_kickoff_malicious`) == the operator that actually funded/broadcast the confirmed payout output for withdrawal `i`.

Trace:
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds the payout tx: input 0 = withdrawer's committed UTXO (key-spend), output 0 = withdrawer payout, output 1 = anchor, output 2 = OP_RETURN with an arbitrary `operator_xonly_pk` chosen solely by whoever assembles the transaction, with **no signature over this output at all**.
- The witness for input 0 is `user_sig`, verified with `sighash_type = SinglePlusAnyoneCanPay` (core/src/operator.rs:630-637, `calculate_sighash_txin`/`calculate_pubkey_spend_sighash` at core/src/builder/transaction/txhandler.rs:210-233). For `*PlusAnyoneCanPay` types the code uses `Prevouts::One(txin_index, ...)`, i.e. the sighash commits only to the single signed input's prevout and (for SIGHASH_SINGLE) to output index 0. Outputs 1 and 2, and any additional inputs added by whoever funds the transaction, are unauthenticated by this signature.
- `update_finalized_payouts` (core/src/verifier.rs:2283-2352) reads whatever transaction ends up confirmed spending the withdrawal UTXO, parses the OP_RETURN blindly (`get_first_op_return_output` + `parse_op_return_data`), and writes it via `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:199-250) with no cross-check against who actually funded the extra inputs.
- `is_kickoff_malicious` (core/src/verifier.rs:1859-1915) and the operator-side `get_first_unhandled_payout_by_operator_xonly_pk` (core/src/database/verifier.rs:282-313, consumed in core/src/task/payout_checker.rs:41-47) both trust this DB column as ground truth for "who paid."

Exploit: the withdrawer's `input_signature` (`SinglePlusAnyoneCanPay`) is disclosed off-chain to operators (per `WithdrawParams`/`WithdrawParamsWithSig`, core/src/rpc/clementine.proto:239-253) and/or becomes public the moment any payout tx enters the mempool (witness data is public). An unprivileged attacker who obtains this signature — trivially, since the rules permit the attacker to "call `withdraw`" and thus legitimately possess/observe a withdrawer signature, or by scraping mempool — can build an alternate payout transaction that: keeps input 0 and output 0 byte-identical (required by the sighash), funds the withdrawal amount with the attacker's own added inputs (as `fund_raw_transaction` does for the legitimate operator, core/src/operator.rs:652-666), and sets the OP_RETURN to an arbitrary `operator_xonly_pk` — e.g., a real, uninvolved operator B's key. If this attacker-built transaction is the one that gets confirmed spending the withdrawal UTXO (via RBF fee-race, first-broadcast race, or simply because it is submitted for a withdrawal an honest operator A has not yet claimed), `update_finalized_payouts` will record operator B as payer. Depending on which real kickoff later targets that `move_to_vault_txid`, `is_kickoff_malicious` will either falsely treat operator A's legitimate kickoff as malicious (mismatched `operator_xonly_pk`, since the DB now says B), or let B's/an unrelated kickoff pass as non-malicious for a payout B never made, entitling it to reimbursement it did not fund.

No existing guard prevents this: `Verifier::is_kickoff_malicious` only re-checks equality of the DB-recorded `operator_xonly_pk` against `kickoff_data.operator_xonly_pk` and a Winternitz-committed truncated blockhash — neither of which is tied to who funded the payout's extra inputs. `SECP.verify_schnorr` in `operator.rs::withdraw`/aggregator's optimistic payout path only verifies the withdrawer's own signature over input 0/output 0, never the OP_RETURN. There is no on-chain or off-chain commitment binding the payer's identity to the OP_RETURN bytes.

### Impact Explanation
- If the attacker names an honest operator that did not fund the withdrawal, that operator's later legitimate kickoff for a *different, genuinely fronted* withdrawal is unaffected (attribution is keyed per `move_to_vault_txid`/withdrawal index), but if the attacker's forged payout displaces the honest operator's own broadcast for the *same* withdrawal (front-running/RBF), the honest operator's expectation of reimbursement for real fronted funds is destroyed, and if that operator nonetheless attempts to kick off believing it is the payer, `is_kickoff_malicious` will flag it malicious (operator_xonly_pk mismatch), leading to Challenge/Disprove/ChallengeNACK and burning its collateral — Critical.
- Conversely, if the attacker names any operator (including itself if it also holds an operator key, or a targeted operator to grief) whose own automation (`PayoutCheckerTask` via `get_first_unhandled_payout_by_operator_xonly_pk`) is misled into believing it fronted the payout, that operator can be induced to kick off and be reimbursed for a payout it never actually funded from its own resources — matching "an operator reimbursed for a payout it never funded" — Critical.
- The blast radius is per-withdrawal and repeatable: any withdrawal UTXO not yet confirmed spent is subject to this OP_RETURN substitution, across all deposits/withdrawals and all operators, as long as the attacker can win the confirmation race and front the withdrawal amount itself.

### Likelihood Explanation
The attacker needs: (1) knowledge of a withdrawer's `SinglePlusAnyoneCanPay` signature for a pending withdrawal (obtainable as an unprivileged party per the given threat model, or observable in mempool once any operator broadcasts), (2) enough BTC to fund the withdrawal's output amount via their own added inputs (a real cost, roughly equal to the withdrawal amount), and (3) the ability to win a fee/priority race for the withdrawal UTXO's confirmation (ordinary RBF/fee-bidding, no hashrate majority required). No verifier/operator private key, TLS cert, or aggregator privilege is required. This is feasible with only unprivileged capabilities explicitly granted (broadcast Bitcoin transactions, craft OP_RETURN/witness/sighash flag) and is repeatable across every withdrawal.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the funding of the payout, e.g., by using a sighash type that commits to all outputs (or at least the OP_RETURN output) such as `SIGHASH_ALL` for the user's portion combined with a separate operator-signed commitment, or by having the aggregator/N-of-N pre-commit (sign) the specific `(withdrawal_index, operator_xonly_pk)` pairing so that `is_kickoff_malicious`/`update_finalized_payouts` verify a signature over the OP_RETURN payload rather than trusting unauthenticated transaction bytes observed on-chain.

### Proof of Concept
`cargo test` (regtest, e2e-style, no mainnet/live Citrea) plan:
1. Set up a deposit and a withdrawal exactly as in `core/src/test/deposit_and_withdraw_e2e.rs`, obtaining `withdrawal_utxo`, `payout_txout`, and the withdrawer's `sig` (`SinglePlusAnyoneCanPay`) via `generate_withdrawal_transaction_and_signature`.
2. Using `builder::transaction::create_payout_txhandler`, build tx_A with `operator_xonly_pk = A` (simulating operator A's legitimate broadcast) and tx_E with `operator_xonly_pk = B` (attacker's forged version), both reusing `sig`, both funded with independent extra inputs/wallets, both spending the same `withdrawal_utxo`.
3. Assert both `tx_A` and `tx_E` pass `SECP.verify_schnorr` against the same sighash (`calculate_sighash_txin(0, SinglePlusAnyoneCanPay)`), proving the OP_RETURN is unauthenticated.
4. Broadcast tx_E first and mine it (simulating the race win); confirm `bitcoin_syncer`/`update_finalized_payouts` records `payout_payer_operator_xonly_pk = B` via `db.get_payout_info_from_move_txid`.
5. Have operator A construct/send a kickoff for the same deposit (`kickoff_data.operator_xonly_pk = A`) and assert `Verifier::is_kickoff_malicious` returns `true` (mismatch: DB says B, kickoff says A), while the attacker never needed any Clementine credential to cause this.
6. (Optional second assertion) Attribute B in tx_E, then run operator B's `PayoutCheckerTask`/`get_first_unhandled_payout_by_operator_xonly_pk` and show B is offered the "unhandled payout," and if B kicks off with `operator_xonly_pk = B`, `is_kickoff_malicious` returns `false`, proving B could be reimbursed for a payout it never funded.
