### Title
Systemic floor-division rounding in CPI/syscall byte-cost metering causes materially underpriced compute units - (File: `program-runtime/src/cpi.rs`, `syscalls/src/mem_ops.rs`)

### Summary
Every compute-unit charge in the agave CPI translation path and the SBF memory-operation syscalls that scales with byte length uses `checked_div(cpi_bytes_per_unit)` (integer floor division) instead of a ceiling/ceil-rounding division. This is the same class of bug as the reported `GoodDollarExchangeProvider` issue: a fixed-point calculation is truncated to a coarser precision than intended, and the truncated (rounded-down) quantity is used directly to charge/mint/consume a resource, so the actual resource cost is systematically higher than what is billed.

### Finding Description
In `program-runtime/src/cpi.rs`, every CPI-related byte-cost charge is computed as `len / cpi_bytes_per_unit` with no ceiling adjustment, e.g.:
- instruction data + account meta translation cost: [1](#0-0) 
- C-ABI variant: [2](#0-1) 
- account-info array cost: [3](#0-2) 
- per-account data length cost (Rust and C AccountInfo paths): [4](#0-3) [5](#0-4) 
- callee-account data cost and syscall-restriction path: [6](#0-5) 

The same pattern (`mem_op_base_cost.max(n / cpi_bytes_per_unit)`) is used for `memcpy`/`memmove`/`memcmp`/`memset` in `syscalls/src/mem_ops.rs`: [7](#0-6) 

With `cpi_bytes_per_unit = 250` (the default, see [8](#0-7) ), any length that is not an exact multiple of 250 has its remainder discarded rather than rounded up. For example, `len = 249` yields a computed cost contribution of `0`, and `len = 499` yields `1` instead of `2`. Because `checked_div` floors, the charged compute is always `≤` the "true" proportional cost, and the shortfall (up to `249/250` of one unit per call site) is never billed. This mirrors the root cause pattern in the report: a value is computed and truncated to a coarser resolution than the resource-accounting model assumes, and that truncated value is used as-is instead of restoring correctness via a matching round-trip (there, `*1e10`/`/1e10`; here, rounding the division up rather than down).

### Impact Explanation
Each CPI invocation and every `sol_memcpy`/`memmove`/`memcmp`/`memset` syscall call site independently loses up to `cpi_bytes_per_unit - 1` (249) units of properly chargeable compute due to floor division, several times per CPI call (instruction data, account metas, account-info array, and each account's data length are each rounded down independently). An unprivileged on-chain program can invoke CPI and memory syscalls in a loop, choosing lengths just below multiples of 250 bytes, to repeatedly get a "discount" relative to the actual work performed by the runtime (memory translation/copy, account data scanning, etc.), without correspondingly reducing runtime work. This is a form of materially underpriced compute: the validator does the full byte-proportional work but bills less than the configured `cpi_bytes_per_unit` rate intends, which can be exploited to pack more actual work into a transaction's compute budget than the fee/compute model assumes, degrading the compute-to-fee guarantees the network relies on for resource pricing and DoS protection.

### Likelihood Explanation
High reachability: this code executes on every CPI (`sol_invoke_signed`) and on every `sol_memcpy`/`memmove`/`memcmp`/`memset` syscall call, which are used by essentially all deployed SBF programs and are fully attacker-controlled (arbitrary lengths, arbitrary repetition counts up to the compute budget). No special privileges or validator/operator role is required — any unprivileged user-deployed program can trigger it.

### Recommendation
Change all `len.checked_div(cpi_bytes_per_unit)` computations in `program-runtime/src/cpi.rs` and the `mem_op_consume` helper in `syscalls/src/mem_ops.rs` to compute a ceiling division, e.g. `len.saturating_add(cpi_bytes_per_unit - 1).checked_div(cpi_bytes_per_unit)`, consistent with how `calculate_heap_cost` already correctly rounds up heap costs (`program-runtime/src/vm.rs`, lines 35-46). Any such change is consensus-affecting and would need to be gated behind a new feature flag/SIMD given it changes compute-unit accounting for existing transactions.

### Proof of Concept
Not applicable in the strict sense of a crash/PoC transaction, but the underbilling is directly demonstrable arithmetically from the code: for `cpi_bytes_per_unit = 250` and a CPI call with `data.len() = 249`, `instruction_data_cost = 249 / 250 = 0` (see [9](#0-8) ) instead of the intended `1`; repeating such a CPI or `sol_memcpy(n=249)` call (see [10](#0-9) ) `k` times inside a single transaction's compute budget performs `k` real 249-byte copy/translation operations while being billed `0` bytes-based compute units for each, only ever paying the flat `mem_op_base_cost`/`invoke_units` floor.

use {super::*, crate::translate_mut};

fn mem_op_consume(invoke_context: &mut InvokeContext, n: u64) -> Result<(), Error> {
    let compute_cost = invoke_context.get_execution_cost();
    let cost = compute_cost.mem_op_base_cost.max(
        n.checked_div(compute_cost.cpi_bytes_per_unit)
            .unwrap_or(u64::MAX),
    );
    invoke_context.compute_meter.consume_checked(cost)
}
