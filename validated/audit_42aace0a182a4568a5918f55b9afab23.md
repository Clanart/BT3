## Title
Inconsistent LP-token accounting in `WombatStaking.depositLP()` mints receipt tokens against a stated amount instead of the actually-received balance, enabling insolvency with non-standard LP tokens - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` transfers the caller's LP token via `safeTransferFrom` and then mints receipt tokens and stakes to Master Wombat using the caller-supplied `_lpAmount` parameter directly, instead of measuring the actual balance change as the sibling function `deposit()` does.

### Finding Description
In `WombatStaking.deposit()`, the contract correctly captures a before/after balance diff of `poolInfo.lpAddress` to compute `lpReceived`, and mints receipt tokens based on that measured amount: [1](#0-0) 

However, `depositLP()` does not follow this pattern. It transfers `_lpAmount` via `safeTransferFrom`, then immediately stakes and mints receipt tokens for the full stated `_lpAmount`, without verifying the actual amount received by the contract: [2](#0-1) 

`depositLP()` is reachable by any ordinary wallet through `WombatPoolHelper.depositLP()` / `WombatPoolHelperV2.depositLP()` / `AnkrBNBPoolHelper.depositLP()`, all of which forward the user-chosen `_lpAmount` unchanged: [3](#0-2) 

If the registered `poolInfo.lpAddress` token (the Wombat Asset/LP token for a given pool) behaves as a fee-on-transfer, rebasing, or otherwise non-standard ERC20 — i.e. the amount received by `WombatStaking` after `safeTransferFrom` is less than `_lpAmount` — the contract will:
1. mint `receiptToken` to `msg.sender` for the full `_lpAmount` even though less LP was actually custodied, and
2. attempt to stake `_lpAmount` (not the actual received amount) into Master Wombat via `_toMasterWomAndSendReward` → `_stakeToWombatMaster`, which approves and calls `IMasterWombat(masterWombat).deposit(poolInfo.pid, _lpAmount)`.

This creates a structural mismatch between `receiptToken` total supply (the claim on the pool) and the actual LP tokens held/staked for that pool, i.e. the receipt token becomes under-collateralized for that pool.

### Impact Explanation
Under-collateralization of the receipt token means the pool can become insolvent: since receipts are burned 1:1 on withdrawal (`WombatPoolHelper.withdraw()` → `WombatStaking.withdraw()`/`burnReceiptToken()`), users who withdraw first can drain the pool, leaving later withdrawers unable to redeem their receipt tokens — a permanent freezing of funds and protocol insolvency for that pool, matching the explicitly in-scope category "WombatStaking LP custody and receipt tokens."

### Likelihood Explanation
Likelihood depends on whether an LP/Asset token registered via the owner-only `registerPool()` exhibits fee-on-transfer or other balance-reducing transfer semantics. Standard Wombat Asset tokens are typically fee-free, but the contract itself provides no defense-in-depth against such tokens — unlike `deposit()`, which already guards against this scenario using the before/after balance pattern. This is a direct code-level inconsistency reachable by any unprivileged user calling `depositLP` once any qualifying LP token is in use; no privileged/malicious admin action is required to trigger the divergence beyond normal pool registration.

### Recommendation
Mirror the pattern used in `deposit()`: measure `poolInfo.lpAddress.balanceOf(address(this))` before and after the `safeTransferFrom` call in `depositLP()`, and use the resulting delta (actual received amount) for `_toMasterWomAndSendReward` staking and for `IMintableERC20(poolInfo.receiptToken).mint(...)`, instead of the raw `_lpAmount` parameter.

### Proof of Concept
1. Owner registers a pool via `registerPool()` whose `_lpAddress` is a token that deducts a transfer fee (e.g. 1%) on `transferFrom`.
2. A user calls `WombatPoolHelper.depositLP(_lpAmount)` with `_lpAmount = 100`.
3. `WombatStaking.depositLP()` executes `safeTransferFrom(_for, address(this), 100)`, but the contract only receives `99` LP tokens due to the fee.
4. `_toMasterWomAndSendReward(_lpAddress, 100, true)` attempts to stake `100` (via `_stakeToWombatMaster` approving/depositing `100` to Master Wombat) while only `99` is actually held — and `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, 100)` mints receipts for the full `100`.
5. Repeated deposits progressively widen the gap between receipt token supply and actual LP custody/stake, so that eventually not all receipt holders can be redeemed — freezing funds for the last withdrawers. [4](#0-3)
