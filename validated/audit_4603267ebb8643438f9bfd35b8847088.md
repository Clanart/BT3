### Title
Unbounded attacker-controlled count in `SchnorrAggregate::read` permits memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts a little-endian `u32` element count embedded in the serialized signature and then parses that many group elements into an in-memory `Vec<C::G>` with no upper bound. This mirrors the containerd bug class (unbounded parsing of an attacker-controlled collection leading to resource exhaustion): any component that deserializes a `SchnorrAggregate` from untrusted bytes — most concretely over a streaming `io::Read` rather than a fixed slice — will keep allocating curve points until the input ends or the process is OOM-killed.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `read` performs:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
``` [1](#0-0) 

There is no bound on `u32::from_le_bytes(len)` (up to 4,294,967,295 entries) and no correlation check between the declared count and any available-size limit. Because the input is a generic `R: Read`, an attacker feeding a stream of valid group encodings drives the `Rs` vector to grow unboundedly. The same pattern exists elsewhere in scope-adjacent parsing (`Payment::read` in `processor/src/plan.rs` allocates `vec![0; u32]` directly from the wire, and `OutInstructionTarget::read` in `networks/ethereum/src/machine.rs` loops over an unchecked `u32` call count), confirming the codebase does not enforce a uniform cap on parsed collection lengths. ### Impact Explanation
Memory exhaustion / denial of service of the process performing deserialization, consistent with CWE-400. `C::read_G` accepts any canonically encoded point, so an attacker does not need valid signatures — only valid encodings — to force allocation. Each element expands into an in-memory `C::G` (decompressed form, typically larger than its wire encoding for curves that store extended/projective coordinates or `u64` limbs, e.g. `dalek-ff-group` / `ed448` field elements are 4–8× wider than their packed 32/57-byte reprs). A single hostile aggregate-signature payload streamed to `read` can therefore consume multiple GiB of heap before the first byte-level failure, killing the signer/verifier process and halting any threshold-signing or verification activity it hosts.

### Likelihood Explanation
The count field is fully attacker-controlled public input, and the API is explicitly listed among the untrusted-byte entry points (`read` / `verify` APIs). Exploitation requires the target to call `SchnorrAggregate::read` on peer-supplied bytes (e.g., a signature-aggregation verification path or a serialized proof message received over a network reader). Cost to the attacker is roughly proportional to bytes sent (~one point encoding per element), which is the same asymmetric-cost profile as the reference containerd advisory (image bytes → unbounded group-file parsing). Severity is Medium: availability-only, no secret leakage or forgery, and bounded by the victim's willingness to keep reading.

### Recommendation
Cap the declared `Rs` count before allocation, e.g. reject `len` above a protocol-appropriate maximum (or above `n`/the expected signer count known to the caller). Prefer `Vec::with_capacity` only after the bound check, and/or take the count from the expected `keys_and_challenges` length in `verify` so parsing is bound by context rather than wire data. Apply the same audit to other length-prefixed readers (`Payment::read`, `OutInstructionTarget::read`, `SignedTransaction`-style `vec![0; u32]` allocations).

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;

// Stream that emits a valid, canonically-encoded point forever.
struct EndlessPoints { enc: Vec<u8>, pos: usize }
impl io::Read for EndlessPoints {
  fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
    for b in buf.iter_mut() { *b = self.enc[self.pos]; self.pos = (self.pos + 1) % self.enc.len(); }
    Ok(buf.len())
  }
}

// 0xFFFFFFFF Rs declared; the loop then consumes the endless stream,
// growing `Rs` until the process is OOM-killed.
let mut payload = u32::MAX.to_le_bytes().to_vec();
// generator() encodes to a valid point for every ciphersuite
let g = <C as Ciphersuite>::generator().to_bytes();
let mut reader = payload.chain(EndlessPoints { enc: g.as_ref().to_vec(), pos: 0 });
let _ = SchnorrAggregate::<C>::read(&mut reader); // never returns; memory grows unboundedly
```
With a `Read` source over a socket/file, only ~4 GiB/sustained valid encodings are needed to push `Rs` toward hundreds of GiB of resident `C::G` values.
