### Title
Floor division in CPI/syscall byte-cost accounting rounds to zero, allowing systematically underpriced compute for sub-`cpi_bytes_per_unit` byte payloads - (File: program-runtime/src/cpi.rs)

### Summary
Multiple compute-unit charging sites in the CPI and syscall code compute a byte-based compute cost using `checked_div(cpi_bytes_per_unit)` (or the analogous `mem_op_base_cost`/`hash_byte_cost` divisions), which — like the VTVL `_baseVestedAmount` truncation bug — performs integer floor division without any rounding-up (`ceil`) adjustment. When the numerator (bytes) is smaller than the divisor (`cpi_bytes_per_unit`), the result truncates to zero, so the byte-proportional portion of the charge is not collected at all.

### Finding Description
The pattern `(bytes as u64).checked_div(cpi_bytes_per_unit).unwrap_or(u64::MAX)` appears repeatedly for charging compute units proportional to data size during CPI account/instruction translation and various syscalls: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The same truncating pattern is used generically for other memory/syscall operations, e.g. `mem_op_consume` in `SyscallMemcpy`/`memmove`, and in `SyscallGetReturnData`, `SyscallGetEpochStake`, and `SyscallGetSysvar`/`fetch_and_write_sysvar`: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

Unlike `calculate_pages_for_bytes`/`calculate_loaded_accounts_data_size_cost` in the cost model, which explicitly add `divisor - 1` before dividing to round up (ceiling division), these CPI/syscall charge sites use plain floor division with no rounding correction: [10](#0-9) 

This mirrors exactly the VTVL bug pattern: `amount * numerator / denominator` where a small numerator relative to the denominator truncates to zero, and the "affected quantity" (compute units charged) is postponed/never collected until enough bytes accumulate to cross the divisor threshold. In this case, `cpi_bytes_per_unit` (250 in the default cost table) becomes the "denominator" analogous to `finalVestingDurationSecs`, and any byte count below it (e.g., a CPI call with 0–249 bytes of instruction data, account data, or account-info array) causes the byte-cost term to be exactly zero. Several of these sites (`SyscallMemcpy`, `mem_op_consume`) do apply a `.max(mem_op_base_cost)` floor which mitigates the effect there, but several others — the CPI account/instruction-data translation costs in `program-runtime/src/cpi.rs` and the `SyscallGetEpochStake`/`SyscallGetSysvar` id-cost components — add the truncated term directly via `saturating_add` with no floor, so the byte-cost term can be silently zero.

### Impact Explanation
Because CPI invocations, syscalls like `sol_get_epoch_stake`, and `sol_get_sysvar` are core unprivileged-user-reachable operations, a program can structure many small CPI calls / syscall calls (each transferring or referencing well under 250 bytes of instruction data, account data, or account-info metadata) to have their byte-proportional compute charge rounded down to zero on every single call. This does not bypass the flat per-call base costs (`invoke_units`, `syscall_base_cost`, etc.), but it does mean the marginal, size-proportional compute-cost component that is supposed to reflect the real work of copying/validating that data is never charged for these small transfers. Aggregated across a transaction (which can perform many CPIs up to the instruction-trace/CU limits), this results in materially underpriced compute relative to the work actually performed, understating the true resource cost of the transaction versus the compute budget consumed.

### Likelihood Explanation
This is easily and deterministically reachable by any unprivileged program: any BPF program can invoke `sol_invoke_signed`/CPI with small instruction data and account data, or call syscalls like `sol_get_epoch_stake` and `sol_get_sysvar`, without any special privileges. No malicious validator, config change, or off-chain condition is required — it only depends on message/CPI construction, which is fully within reach of ordinary transaction senders.

### Recommendation
Change the byte-cost computation in the affected CPI and syscall paths to use ceiling division (as already done in `cost-model`'s `calculate_pages_for_bytes`), e.g. `bytes.saturating_add(cpi_bytes_per_unit - 1).checked_div(cpi_bytes_per_unit)`, or otherwise ensure a non-zero minimum charge is applied whenever `bytes > 0`, consistent with how `mem_op_consume` already applies a `mem_op_base_cost` floor.

### Proof of Concept
1. Construct a transaction whose program issues repeated CPI calls (`sol_invoke_signed`) each with instruction data and/or account data under `cpi_bytes_per_unit` (default 250) bytes.
2. Observe that `translate_instruction_rust`/`translate_instruction_c` and `translate_accounts_common` compute `(data.len() as u64).checked_div(cpi_bytes_per_unit)` which floors to `0` for any `data.len() < cpi_bytes_per_unit`, at [2](#0-1)  and [4](#0-3) .
3. Repeat this pattern across many CPIs within the compute budget/instruction-trace limits; the byte-proportional compute charge for each such CPI is zero, even though real work (translation/validation/copy) occurs each time — directly analogous to the VTVL linear-vesting truncation-to-zero bug where per-unit amounts below the divisor threshold are never charged/vested.
