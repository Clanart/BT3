### Title
`SignableTransaction::new` omits the OP_RETURN data output from fee/weight accounting, producing transactions whose actual fee rate is below the intended (and possibly below minimum relay) rate - (networks/bitcoin/src/wallet/send.rs)

### Summary
The reward-splitting bug in the external report is an instance of a general class: a "total" (totalRewards) computed independently from the sum of the individually accounted "parts" (per-recipient amounts), letting the aggregate diverge from what each component was charged. In Serai's Bitcoin wallet, `SignableTransaction::new` exhibits the same class: the fee and weight are computed from only the inputs, payments, and change, while an optional OP_RETURN data output is appended to `tx_outs` but is never fed into `calculate_weight_vbytes`. The resulting transaction is larger than the size the fee was priced for, so the effective sat/vbyte rate is lower than `fee_per_vbyte`, and can even fall below `DEFAULT_MIN_RELAY_TX_FEE` despite the explicit minimum-fee check.

### Finding Description
`SignableTransaction::new` builds the output set in two places that disagree:

1. The OP_RETURN output is pushed onto `tx_outs` when `data` is `Some` (`send.rs:194-202`).
2. The weight/vbyte estimate used for `needed_fee` and for the minimum-fee check calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` and later `Some(&change)` (`send.rs:204`, `send.rs:225-226`). `calculate_weight_vbytes` reconstructs a `Transaction` whose `output` list contains only `payments` plus optional change (`send.rs:85-99`) — the `data` parameter is not part of its signature at all, so the OP_RETURN output's bytes (up to 80 bytes of payload plus output/script overhead) are never counted.

Consequences of the mismatch:

- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`, `send.rs:227`, `send.rs:232`) prices a smaller transaction than the one actually produced. The real fee paid is still `sum(inputs) - sum(outputs)` (`send.rs:138-141`), but it buys a bigger tx, so the achieved fee rate is strictly less than the caller-requested `fee_per_vbyte` whenever `data` is supplied.
- The minimum-relay guard `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`) also uses the undercounted `vbytes`, so a transaction can pass this check while its true fee rate is below the network minimum relay fee.
- The `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) uses the same undercounted `weight`, so a tx that is actually non-standard can be accepted.
- The change amount is computed as `input_sat - payment_sat - fee_with_change` (`send.rs:228-230`), so the change output itself is correct in value, but it is attached to a transaction whose relay/confirmation properties were mispriced.

### Impact Explanation
Any spend that carries `data` produces a transaction paying a lower fee rate than requested. In the worst case the transaction's true fee rate is under `DEFAULT_MIN_RELAY_TX_FEE` (1000 sat/kvB), causing standard Bitcoin nodes to reject it from the mempool. The result is a signed transaction that cannot be broadcast/confirmed — the plan's payment never lands even though all internal accounting "succeeded", matching the report's impact of "funds... accumulate that cannot be utilized" / a deposit that reverts. Since `median_fee` in `processor/src/networks/bitcoin.rs:431` is used to pick `fee_per_vbyte`, the effective rate may also silently undercut the intended confirmation target even when still above the relay minimum, degrading to stuck transactions that require reconstruction.

### Likelihood Explanation
Deterministic whenever `SignableTransaction::new` is called with `data: Some(..)` — no adversary is required. The deficit is proportional to the OP_RETURN output's serialized size (~9 + script overhead + up to 80 bytes), i.e. roughly 100 vbytes worst case. Whether the tx actually falls under the relay minimum depends on how close `fee_per_vbyte` is to the minimum and the tx's total size, but the fee-rate shortfall occurs on every call with data. The `data` argument is part of the public wallet API and reachable via transaction data a requester causes to be signed, so no privileged position is needed to trigger it.

### Recommendation
Include the data output in the weight/vbyte estimate. Either extend `calculate_weight_vbytes` to take `data: Option<&[u8]>` and push the `TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }` into the estimation transaction, or build the final `tx_outs` (including OP_RETURN and change) once and compute weight from that directly so the accounted parts can never diverge from the total. Both call sites (`send.rs:204`, `send.rs:225-226`) and the `MAX_STANDARD_TX_WEIGHT` check must use the data-inclusive size.

### Proof of Concept
```rust
// networks/bitcoin: any call supplying data produces an under-priced fee.
// In SignableTransaction::new (send.rs):
//   tx_outs.push(OP_RETURN output)              // line ~195: data output added
//   calculate_weight_vbytes(n, payments, None)  // line ~204: data NOT included
//   calculate_weight_vbytes(n, payments, change)// line ~226: data NOT included

// Concretely: payments = [(addr, 1000)], data = Some(vec![0; 80]),
// fee_per_vbyte chosen so needed_fee just passes the min-fee check.
// needed_fee = FEE * vbytes(payments only)
// actual tx also contains an OP_RETURN output of ~91 bytes (~91 extra wu/4 vbytes
// plus output overhead), so actual_vsize > vbytes used for pricing.
// effective_rate = needed_fee / actual_vsize < fee_per_vbyte,
// and can be < DEFAULT_MIN_RELAY_TX_FEE => mempool rejection.
// Additionally, `weight` compared to MAX_STANDARD_TX_WEIGHT excludes the
// OP_RETURN output, so an oversized tx can slip past the TooLargeTransaction guard.
```
Relevant code: `networks/bitcoin/src/wallet/send.rs:194-235` (data output appended after weight estimation), `send.rs:62-127` (`calculate_weight_vbytes` has no `data` parameter and builds outputs solely from `payments`/`change`), `send.rs:206-213` (fee and min-fee check on the undercounted `vbytes`), `send.rs:241` (weight limit check on the undercounted `weight`).
