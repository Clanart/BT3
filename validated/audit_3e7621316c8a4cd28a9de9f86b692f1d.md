### Title
Missing byte-consumption for `Digest::Other` items desyncs header digest parsing, allowing legitimate ISMP consensus digests to be misread or dropped - ([File: evm/src/consensus/Codec.sol])

### Summary
`Codec.DecodeHeader` fails to consume the SCALE-encoded payload of a `Digest::Other` item (kind `0`) before moving to the next loop iteration, desynchronizing the byte cursor for every digest item that follows it in the same header.

### Finding Description
In Substrate's `DigestItem` enum, variant `0` (`Other`) wraps a `Vec<u8>`, which SCALE-encodes as a compact length prefix followed by that many raw bytes — exactly like `Consensus`/`Seal`/`PreRuntime` encode their `(ConsensusEngineId, Vec<u8>)` payload via `decodeDigestItem`. However, in `DecodeHeader`: [1](#0-0) 

only `digest.isOther = true` is set for `kind == DIGEST_ITEM_OTHER`; the compact length and the associated data bytes are never read from `slice`. Contrast this with `DIGEST_ITEM_CONSENSUS`/`SEAL`/`PRERUNTIME`, which correctly call `decodeDigestItem` to advance the offset past the id, length, and payload: [2](#0-1) 

Because the loop reads the discriminant byte via `Bytes.readByte(slice)` at the top of each iteration and relies on each branch to fully consume that item's remaining bytes, skipping the `Other` payload leaves the slice's offset pointing at the first byte of the un-consumed `Other` data. The next loop iteration then misinterprets that stray data byte as the next digest item's `kind`, and every subsequent read (including the parsing of a following `DIGEST_ITEM_CONSENSUS` ISMP digest) is offset-shifted and garbage. This can cause:
- The real ISMP `consensus` digest's `consensusId`/`data` to be read from the wrong bytes entirely, so `digest.consensus.consensusId == ISMP_CONSENSUS_ID` never matches in `HeaderImpl.stateCommitment`.
- The loop's `kind` byte matching one of the other branches by coincidence and being decoded incorrectly, or reverting due to out-of-bounds `Bytes.read`, or silently continuing with wrong `mmrRoot`/`childTrieRoot`/`timestamp` values.

`HeaderImpl.stateCommitment` depends on correctly finding the `ISMP_CONSENSUS_ID` and `ISMP_TIMESTAMP_ID` digests to build the trusted `StateCommitment`: [3](#0-2) 

This state commitment is the value ultimately trusted by the BEEFY consensus clients (`EcdsaBeefy.sol`, `SP1Beefy.sol`) for verifying finalized parachain state, so corrupting its derivation from a mis-parsed header is a consensus-parsing-correctness bug at the heart of state-root trust establishment.

### Impact Explanation
If a legitimate Substrate/parachain header ever includes a non-empty `Digest::Other` item preceding the pallet-ismp `Consensus` digest, `DecodeHeader` will desynchronize parsing and the resulting `Digest[]` will not accurately reflect the header's encoded digests. Depending on the garbage bytes read afterward, this can either (a) cause the ISMP consensus digest to be missed, reverting `stateCommitment` with `TimestampNotFound`, silently dropping/rejecting a valid header, or (b) in the worse case, misinterpret unrelated bytes as `mmrRoot`/`childTrieRoot`/`timestamp`, propagating an incorrect state commitment forward. Either failure mode undermines the invariant that decoded `Digest` fields accurately reflect their true encoded content and could allow acceptance of a wrong (non-attested) root/timestamp as the trusted state commitment.

### Likelihood Explanation
Exploitability/triggering depends entirely on whether relay-chain/parachain headers processed by Hyperbridge's BEEFY consensus client actually include a populated `Digest::Other` item. This is not attacker-controlled in the sense of an unprivileged on-chain call — the header content is produced by the block-production layer of the source chain being bridged, not by an unprivileged Hyperbridge caller. I was not able to confirm from this codebase whether any of the specific runtimes bridged by Hyperbridge emit non-empty `Other` digests in normal operation (this would require checking the actual relaying chain's runtime/pallet configuration, which is outside this repo). If such digests are never emitted by the bridged runtimes, this bug is latent/dormant; if they are, it is a real parsing-correctness defect that could break header verification for otherwise valid headers.

### Recommendation
In `Codec.DecodeHeader`, for `kind == DIGEST_ITEM_OTHER`, decode and consume the compact-length-prefixed byte vector (mirroring `decodeDigestItem`'s length+data reading) and populate `digest.other` with it, e.g.:
```solidity
} else if (kind == DIGEST_ITEM_OTHER) {
    digest.isOther = true;
    uint256 len = ScaleCodec.decodeUintCompact(slice);
    digest.other = Bytes.read(slice, len);
}
```
This both fixes the offset desync for subsequent items and populates `Digest.other` as the struct's field name implies.

### Proof of Concept
Construct a SCALE-encoded header with digest list `[Other(non-empty bytes), Consensus(ISMP, 64-byte root data)]`, call `Codec.DecodeHeader`, and assert that either the call reverts (out-of-bounds read due to offset shift) or that `digests[1].isConsensus == false` / `digests[1].consensus.data != original 64-byte root` — demonstrating the ISMP digest is corrupted/dropped because the `Other` item's payload bytes were never consumed from the slice.

    /// @dev Decodes a SCALE-encoded digest item (4-byte consensus id + length-prefixed data).
    function decodeDigestItem(ByteSlice memory slice) internal pure returns (DigestItem memory) {
        bytes4 id = Bytes.toBytes4(read(slice, 4), 0);
        uint256 length = ScaleCodec.decodeUintCompact(slice);
        bytes memory data = Bytes.read(slice, length);
        return DigestItem(id, data);
    }

                mmrRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 0, 32));

                timestamp = ScaleCodec.decodeUint256(self.digests[j].consensus.data);
            }
        }

        // sanity check
        if (timestamp == 0) revert TimestampNotFound();

        return StateCommitment({timestamp: timestamp, overlayRoot: mmrRoot, stateRoot: childTrieRoot});
