### Title
NFT royalty amount truncates to zero due to division-before-multiplication in `compute_royalty_amount` / `royalty_calculation` - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount` and the related `NFTWallet.royalty_calculation` helper divide by the royalty split count *before* multiplying by the royalty percentage, mirroring the exact "division before multiplication" defect described in the DODO V3 report. Because the split-count division happens first, an offer maker who requests multiple royalty-bearing NFTs while offering a small fungible amount can make the integer division truncate to zero, eliminating the royalty payment to the NFT creator entirely, independent of the configured royalty percentage.

### Finding Description
`compute_royalty_amount` computes:
```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
``` [1](#0-0) 

This performs the division by `royalty_split` first, then multiplies by `percentage`, then divides by `MAX_ROYALTY_BASIS_POINTS` (10000). If `abs(offered_amount) < royalty_split`, the first integer division (`//`) truncates to `0` before the multiplication by `percentage` even occurs, forcing the final royalty to `0` regardless of how high `percentage` is set (up to 100%).

The same pattern appears in the informational `royalty_calculation` static method used by the wallet RPC (`nft_calculate_royalties`) and CLI offer summaries:
```
"amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
``` [2](#0-1) 

This is used both to display royalty amounts to the maker/taker and, critically, `compute_royalty_amount` is used to actually construct the `CreateCoin` royalty payment condition sent to the royalty-holder's address during `make_nft1_offer`:
```
extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
payment_list.append((launcher_id, CreateCoin(address, extra_royalty_amount, [address])))
``` [3](#0-2) 

Here `amount` (offered fungible amount, attacker/maker controlled) and `request_side_royalty_split` (number of royalty-bearing NFTs the maker requests in the same offer, also maker controlled) are both fully controlled by whoever constructs the offer. By deliberately choosing a small fungible offer amount relative to the number of bundled royalty NFTs (`abs(amount) < request_side_royalty_split`), the maker can force `compute_royalty_amount` to return `0`, entirely bypassing the royalty owed to the NFT creator, even for a 100% royalty NFT.

### Impact Explanation
This allows an offer maker to unilaterally and deterministically zero out royalty payments that should be owed to third-party NFT creators/royalty holders on any offer that bundles multiple royalty-enabled NFTs against a small fungible amount, purely via integer-truncation, rather than negotiating a genuinely zero-value trade. Since the royalty payment (or its absence) is fully baked into the offer's spend bundle and CLVM conditions before it's ever broadcast, and the wallet-side code is what determines the `CreateCoin` sent to the royalty address, this results in NFT creators being deprived of the royalty they are entitled to as part of the offer settlement — a form of offer settlement value theft from a party (the royalty holder) that isn't a direct counterparty to the negotiation.

### Likelihood Explanation
Reachable by any unprivileged wallet user constructing an offer via the standard `Offer`/`TradeManager` flow (`NFTWallet.make_nft1_offer`), with no special privileges required — only a specific combination of a small offered fungible amount and multiple royalty NFTs requested in a single offer, both of which are attacker-chosen parameters.

### Recommendation
Reorder the arithmetic to multiply before dividing, and only apply the final division to minimize precision loss, e.g.:
```
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
Apply the same fix to the `royalty_calculation` static method: `abs(amount) * percentage // (len(royalty_assets_dict) * MAX_ROYALTY_BASIS_POINTS)`.

### Proof of Concept
Using `compute_royalty_amount` directly:
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount

# maker offers 3 mojos of XCH while requesting 2 NFTs from the same collection
# with a 99.99% royalty configured (percentage=9999)
result = compute_royalty_amount(offered_amount=-3, royalty_split=2, percentage=9999)
print(result)  # 0  -- royalty entirely skipped

# correct order (multiply first) would yield:
# abs(-3) * 9999 // (2 * 10000) = 29997 // 20000 = 1
```
The existing test suite in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` confirms the division-first ordering is the implemented behavior (e.g. `test_royalty_split_across_multiple_nfts`), but does not test the boundary case where `abs(offered_amount) < royalty_split`, which is exactly where the precision-loss zeroing occurs. [4](#0-3) 

**Note on verification limits:** I was unable to locate and inspect the CLSP source for `NFT_TRANSFER_PROGRAM_DEFAULT` (the on-chain ownership-transfer puzzle that enforces the `trade_price * TRADE_PRICE_PERCENTAGE / 10000` royalty check) in the indexed codebase, only its Python driver wrapper [5](#0-4) . I could not confirm from this index whether the on-chain puzzle independently re-derives/enforces a minimum royalty amount that would reject an under-paid offer, or whether it merely checks announcements matching whatever royalty amount the wallet supplied (in which case the Python-side truncation above is fully exploitable on-chain). def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
