## Title
MessageSet parsing in the Objective-C runtime spawns a fresh `GPBCodedInputStream` whose recursion-depth inheritance is a custom, unverified addition and is not exercised by the surrounding dispatch logic - (File: `objectivec/GPBMessage.m`, `objectivec/GPBCodedInputStream.m`, `objectivec/GPBCodedInputStream_PackagePrivate.h`)

## Summary
The Sherlock report's failed invariant is: a sensitive operation (`collectRedemption`) performs one safety check (`isRedeemPaused`) but omits a sibling check (`isCollateralEnabled`) that every other entry point in the same contract enforces, allowing the disabled-collateral invariant to be silently bypassed through one specific code path. The transferable analog I looked for is a parser code path that reimplements a safety invariant (recursion-depth bounding across a "spawned" sub-parse) outside of the normal, uniformly-enforced mechanism, so that the guarantee depends on a second, independently-maintained implementation instead of the single audited one.

I found exactly this pattern in the Objective-C runtime's MessageSet handling: `-[GPBMessage parseMessageSet:extensionRegistry:forcedExtension:]` (`objectivec/GPBMessage.m`) constructs a brand-new `GPBCodedInputStream` via a bespoke initializer, `-initWithData:parentRecursionDepth:` (declared in `objectivec/GPBCodedInputStream_PackagePrivate.h`), whose stated purpose is to "mirror the depth-inheritance done by the C++ ParseContext spawn helper" and keep native call-stack growth bounded by `kDefaultRecursionLimit`. This is a second, parallel implementation of the recursion-limit invariant that C++'s `ParseContext::Spawn` provides centrally — it only protects callers who explicitly know to use it.

However, I was **not able to confirm this is an exploitable divergence**, and per the task rules this class of finding (recursion-depth/stack-growth bounding) is explicitly an unbounded-recursion/resource-exhaustion analog, which the rules require me to exclude even if the check were missing or wrong. I could not obtain the body of `-initWithData:parentRecursionDepth:` or `GPBCodedInputStream.m`'s recursion-limit enforcement logic within the remaining tool budget to prove whether the depth is actually enforced correctly or bypassable, so I cannot state with certainty that a bypass exists, only that the code introduces a duplicated/bespoke enforcement point that is a plausible location for such a divergence.

## Finding Description
` [1](#0-0) ` documents that `initWithData:parentRecursionDepth:` exists specifically so that `-[GPBMessage parseMessageSet:...]` can spawn a second `GPBCodedInputStream` for a MessageSet item's raw payload while still inheriting the caller's recursion depth, rather than resetting to zero as a naively-constructed fresh stream would. The call site is ` [2](#0-1) `, where the comment explicitly says this "mirrors the depth-inheritance behavior of the C++ ParseContext spawn helper" (` [3](#0-2) `).

This mirrors the structural bug class in the Sherlock report: in the trusted C++ core, recursion-depth propagation across a "spawned" sub-parse of an already-buffered payload is handled by a single, well-tested mechanism (`ParseContext::Spawn`), used consistently for MessageSet items across C++ (` [4](#0-3) `), Java (` [5](#0-4) ` — recursion depth decremented before recursing into `mergeMessageSetExtensionFromBytes`), and Java Lite (` [6](#0-5) `, which explicitly decrements `remainingInputRecursionLimit` and throws if it goes negative). The Objective-C runtime instead re-derives this guarantee via a bespoke, one-off initializer whose enforcement logic lives in a different translation unit (`GPBCodedInputStream.m`) than the call site that depends on it (`GPBMessage.m`), and whose correctness is not obviously covered by the same test/fuzz corpus that exercises the primary `readGroup:`/nested-message recursion-limit path.

I was unable to retrieve the implementation of `initWithData:parentRecursionDepth:` in `GPBCodedInputStream.m` (the file exists and has 24 matches for `recursionDepth`, but the tool budget was exhausted before I could read the function body) to confirm whether it actually increments/validates the depth correctly, whether it is reachable with attacker-controlled nesting (e.g., a MessageSet item embedding another MessageSet item recursively), or whether the “raises `GPBCodedInputStreamErrorRecursionDepthExceeded` if `parentDepth` is already at the limit” claim in the header comment is actually implemented that way in the `.m` file.

## Impact Explanation
If the depth propagation in `initWithData:parentRecursionDepth:` were incomplete or the check were bypassable (e.g., off-by-one, or the depth not actually being enforced before recursing into the child stream's own `readGroup:`/message parsing), a crafted binary Protobuf payload with nested MessageSet items could cause unbounded native call-stack growth in Objective-C consuming applications, i.e., a stack-overflow crash. Per the rules, resource-exhaustion/stack-growth/DoS-only outcomes are explicitly out of scope and a crash by itself does not establish a higher-severity impact. I therefore cannot elevate this beyond the excluded category without being able to prove the check is actually broken, which I could not do with the remaining budget.

## Likelihood Explanation
Unknown/unconfirmed. The pattern (a duplicated, hand-written recursion-depth-inheritance mechanism used only for one specific parsing path) is exactly the kind of "second implementation of a should-be-uniform invariant" that produced the original Sherlock bug class, making it a reasonable place to look, but I have no confirmed evidence of an actual defect in this codebase's implementation of it.

## Recommendation
Given the uncertainty, the appropriate follow-up (not a confirmed finding) would be to have a Devin agent read the full implementation of `-[GPBCodedInputStream initWithData:parentRecursionDepth:]` in `objectivec/GPBCodedInputStream.m`, compare it line-by-line against `ParseContext::Spawn` in C++ and the Java Lite decrement-and-check pattern in `GeneratedMessageLite.java`, and construct a MessageSet payload with maximally nested items to confirm whether the recursion limit is enforced identically. If it is not — e.g., if the depth is copied but never checked before spawning, or if `parseMessageSet:` can be re-entered without incrementing the depth on some code path — that should be reported through Google's OSS security process, but as a robustness/DoS-hardening issue rather than a "collateralEnabled"-style logic/integrity bypass, since no data-corruption or logic-bypass impact analogous to the Sherlock report was established.

## Proof of Concept
Not established. I was unable to read the body of `-initWithData:parentRecursionDepth:` and `readGroup:`/`mergeFromCodedInputStream:` recursion bookkeeping in `objectivec/GPBCodedInputStream.m` within the remaining tool budget, so I could not construct or validate a concrete payload demonstrating a bypass. This should be treated as an unconfirmed lead requiring direct code review of `objectivec/GPBCodedInputStream.m`, not a proven vulnerability.
