Based on my research, I found a concrete analog: the sei-chain codebase has extensively hardened against exactly this bug class (unbounded memory growth from large replies) across the EVM RPC HTTP/WS layers (`evmrpc/config/config.go` batch/body/log/trace caps), the ABCI `/store/*/subspace` query path (PR #4009 pair/byte caps), and the per-tx state-access tracer (`sei-cosmos/types/tracer.go` `maxStoreTraceModuleBytes`). However, one reachable surface appears to lack an equivalent bound: the `bank` precompile's `all_balances` method.

### Title
Unbounded memory allocation in the `bank` precompile's `all_balances` method via attacker-inflated denom count - ([File: precompiles/bank/bank.go])

### Summary
The `bank` precompile exposes an `all_balances(address)` EVM method that calls `bankKeeper.GetAllBalances` and marshals every coin balance held by the target address into the ABI-encoded return value, with no cap on the number of denominations or output size, and gas priced only on input size rather than output size or iteration count.

The precompile then builds a `CoinBalance` struct per denom and ABI-packs the full list into the return data with no length/size limit, unlike other precompile/RPC paths that were bounded (e.g. `MaxLogBytes`, `MaxTraceStructLogBytes`, `BatchResponseMaxSize`): [4](#0-3) 

Cosmos SDK's bank module does not require an account to be "registered" for a denom nor enforce a minimum non-zero balance; any sender can create an entry for an arbitrary number of distinct denoms in a victim (or their own) account simply by sending dust amounts. `RequiredGas` for this precompile method is derived from `ExtractMethodID`/`MethodById` and priced via `p.Precompile.RequiredGas(input, isTransaction)` based on the 4-byte selector plus fixed-size ABI-encoded input (an address), not on the number of denoms that will ultimately be iterated and serialized — I was not able to fully trace the exact numeric formula inside `RequiredGas`/`DefaultGasCost` before running out of iterations, so the precise per-unit gas cost is unverified, but the call signature confirms cost is computed from `input`, not from the keeper's iteration/output size.

### Impact Explanation
An attacker who inflates the number of distinct denominations held by an address (via ordinary bank sends of dust amounts, or cheaply via tokenfactory-created denoms) can call `all_balances` on that address from any EVM transaction/`eth_call`. Each call forces the node to iterate and heap-allocate one `CoinBalance` struct (and an ABI-encoded copy) per denom, with no upper bound, analogous to CVE-2018-5748's "large reply causes unbounded memory consumption" pattern. Repeated or concurrent invocation (directly or via `eth_call`/RPC clients, or from within a contract) can drive node memory consumption disproportionate to the gas charged, creating a resource-exhaustion / RPC-node crash risk.

### Likelihood Explanation
Moderate-to-high: reachable by any unprivileged EVM transaction sender or public JSON-RPC caller invoking `eth_call`/a transaction against the fixed `bank` precompile address `0x0000000000000000000000000000000000001001`, requiring only the ability to hold or reference an address with many denom balances — achievable at low cost given tokenfactory denom creation and dust-amount bank sends are permissionless.

### Recommendation
Bound `all_balances` the same way `/store/*/subspace` and the tracer paths were bounded: cap the number of denoms/coins returned (and/or total serialized byte size), truncating with an explicit error or a `next_key`-style continuation, and/or scale `RequiredGas` for this method with the actual number of balance entries iterated (e.g., charge gas per denom similar to `IterateAccountBalances` cost) rather than solely on input size.

### Proof of Concept
1. From an EOA, create N (e.g., 50,000) distinct tokenfactory denoms or send 1-unit dust amounts of N distinct existing denoms to a target address, so that address holds N coin balance entries.
2. Deploy/call a contract (or use `eth_call`) invoking the `bank` precompile's `all_balances(address)` at `0x0000000000000000000000000000000000001001` against that address.
3. Observe `PrecompileExecutor.all_balances` iterate all N balances and ABI-pack them into the return data without any cap, while `RequiredGas` charges only for the small fixed-size input — repeat calls to amplify memory pressure on validator/RPC nodes.

**Caveat:** I could not fully verify the numeric gas formula inside `RequiredGas`/`DefaultGasCost` (`precompiles/common/precompiles.go`) within available iterations to confirm it is *entirely* independent of denom count; this should be double-checked against the actual implementation before treating the gas-cost claim as certain.
