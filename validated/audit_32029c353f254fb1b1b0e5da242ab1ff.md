Zero-value/dust outputs are reported as received funds and silently consumed into fees — (File: networks/bitcoin/src/wallet/mod.rs, networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a contract that burns a user's shares while paying out `0` tokens because the zero case is never rejected. The Serai analog lives in `bitcoin-serai`'s wallet: `Scanner::scan_transaction` reports any output whose `script_pubkey` matches a registered script as a `ReceivedOutput`, with no check that the output carries any spendable value, and `SignableTransaction::new` rejects dust *payments* but never validates the value of *inputs*. An unprivileged third party can send a zero-value or dust output to the vault's P2TR script; it is scanned as a deposit, then consumed by a transaction whose cost exceeds the output's value — the input is "burned" while contributing nothing, or the deposit is reported received yet can never be economically spent.

### Finding Description
`Scanner::scan_transaction` matches outputs solely on `script_pubkey` and pushes a `ReceivedOutput` unconditionally — there is no `value > 0` or `value >= DUST` check [1](#0-0) . `ReceivedOutput` itself is just `offset`, `output`, `outpoint`, with `value()` read straight from the `TxOut` [2](#0-1) .

On the spend side, `SignableTransaction::new` explicitly validates that every *payment* is at least `DUST` (546 sats) [3](#0-2) , and sums inputs into `input_sat` without any per-input value check [4](#0-3) . A zero-value or dust input is therefore accepted, and if it is the only input covering `payment_sat + needed_fee`, the wallet produces and signs a transaction spending it [5](#0-4)  — the input is consumed while providing nothing, exactly the "shares burned, zero transferred" shape. This is symmetric to the codebase's own asymmetry: change below dust is deliberately dropped from outputs, yet dust on the input side is silently swallowed into the fee.

### Impact Explanation
An unprivileged attacker can send a 0-value or sub-dust output to any registered vault script. The scanner reports it as received funds (`ReceivedOutput` with `value() == 0`), which downstream accounting treats as a deposit. When the wallet later spends it, the input's UTXO is destroyed while contributing `0` sats — the analogue of burning LP shares while transferring `0` vusd. With only dust inputs, the resulting transaction is also non-standard (dust economics), so funds are reported received that are not practically spendable. Severity: Medium.

### Likelihood Explanation
Any Bitcoin user can create a zero/dust-valued P2TR output to the vault's script_pubkey; it requires no privileges and only costs the attacker the transaction fee. Whether harm materializes depends on the integrator crediting scanned outputs and attempting to spend them, but the wallet layer provides no defense: `scan_transaction` admits the output and `SignableTransaction::new` consumes it without erroring.

### Recommendation
Reject zero-value and sub-dust outputs in `Scanner::scan_transaction` (or at minimum expose a filtering flag), and in `SignableTransaction::new` enforce that each input's value is at least `DUST`, erroring rather than silently consuming a worthless input — mirroring the existing `DustPayment` check on payments.

### Proof of Concept
1. Construct a `Scanner` for key `K`; it registers `p2tr_script_buf(K)` [6](#0-5) .
2. Attacker broadcasts a transaction with `TxOut { value: Amount::ZERO, script_pubkey: p2tr_script_buf(K) }`.
3. `scanner.scan_transaction(&tx)` returns a `ReceivedOutput` with `value() == 0` — reported received [7](#0-6) .
4. `SignableTransaction::new(vec![that_output], &payments, change, None, FEE)` proceeds: `input_sat = 0` enters `input_sat < payment_sat + needed_fee`, so it errors only if it can't cover the payment; if the attacker-funded zero output is combined alongside real inputs, it is silently spent for no gain, increasing `needed_fee` while adding `0` to `input_sat` [8](#0-7) . The consumed zero-value input raises the fee (extra ~67.5 vbytes per input) while contributing nothing — value burned, nothing received.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
