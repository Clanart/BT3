The wolfSSL report class is secret-dependent table indexing leaking via cache resolution. Serai's `straus` and `pippenger` (the "constant-time" non-vartime variants) index tables/buckets with secret scalar nibbles. I need to check where the non-vartime `multiexp` is used with secret scalars reachable by attacker-chosen inputs.### Title
Secret-dependent table indexing in constant-time `multiexp` leaks scalar windows via cache side-channel - (File: crypto/multiexp/src/straus.rs)

### Summary
The wolfSSL report class is a lookup table indexed by secret data, exploitable at cache-line/sub-cache-line resolution. Serai's `multiexp` — the function used as the *constant-time* path by `BatchVerifier::verify` — dispatches to `straus` and `pippenger`, both of which index per-point tables and buckets with windowed bits of the scalar.

### Finding Description
In `straus` (`crypto/multiexp/src/straus.rs:42-44`), the supposedly constant-time implementation performs `res += tables[s][usize::from(groupings[s][b])]`, where `groupings` are `window`-sized chunks of the scalar produced by `prep_bits` (`crypto/multiexp/src/lib.rs:54-74`). This is a secret-dependent memory index, identical in class to the wolfSSL T-Table access. The same issue exists in `pippenger` at `crypto/multiexp/src/pippenger.rs:26` (`buckets[usize::from(bits[p][n])] += pairs[p].1`), a secret-indexed write into `2^window` bucket entries.

This contrasts with the rest of the codebase, which carefully uses linear scans with `conditional_select` (e.g., `Scalar::pow` in `crypto/dalek-ff-group/src/lib.rs:223-230`, `FieldElement::pow` in `crypto/dalek-ff-group/src/field.rs:257-264`, `Point::mul` in `crypto/ed448/src/point.rs:258-265`). Straus/Pippenger have no such mitigation.

Reachability with secret scalars: `BatchVerifier::verify` calls `multiexp` on queued statements (`crypto/multiexp/src/batch.rs:93-94`). In PedPoP, `KeyMachine::calculate_share` queues `share_verification_statements::<C>(i, commitments, share)` where `share` is the decrypted secret key share `C::F` (`crypto/dkg/pedpop/src/lib.rs:487-491`), then calls `batch.verify_with_vartime_blame()` → `self.verify()` → `multiexp`. Each participant's statement set produces ≥2 scalar/point pairs containing the secret share, so Straus(3) is selected (`crypto/multiexp/src/lib.rs:135-137`). An unprivileged DKG participant who submits shares to the victim triggers this computation; a co-located attacker with cache-line (or finer, SGX-style) resolution observes which of the 8 Straus table entries is touched per window, recovering the share scalar nibble-by-nibble. RNG-sampled batch weights in `queue` (`batch.rs:49-85`) are also leaked the same way.

### Impact Explanation
Recovery of a participant's secret share `C::F` during PedPoP `calculate_share` directly yields key-share recovery: the leaked share is the victim's contribution to the threshold secret. Medium severity, matching the source advisory's CVSS 5.5 (local attacker, high confidentiality impact).

### Likelihood Explanation
Requires an attacker with shared-cache observability of the victim process (co-located VM/SGX-host model exactly as in CVE-2024-1543), plus a protocol run in which the victim evaluates shares — obtainable by any unprivileged DKG participant who causes `calculate_share` to run. The leakage is deterministic per window (a direct index, not noise), so extraction is straightforward given cache resolution.

### Recommendation
Replace the secret-indexed lookup in `straus` with a constant-time selection over all `2^window` table entries (as done in `Scalar::pow`), or use a fixed-window loop with `ConditionallySelectable`. For `pippenger`, either restrict the constant-time entry point to Straus and mark Pippenger vartime-only, or perform bucket accumulation via constant-time conditional adds over all buckets. Alternatively, gate `multiexp` behind documentation that its "constant-time" claim excludes cache-line adversaries and ensure secret scalars (shares, nonces, weights) never reach it — though this is fragile given `BatchVerifier::verify` is invoked with secret share statements.

### Proof of Concept
Conceptual: during `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:463-499`), the victim's decrypted share scalar enters `batch.queue` → `BatchVerifier::verify` → `multiexp` → `straus(pairs, 3)`. For each window `b`, `tables[s][groupings[s][b]]` (straus.rs:43) touches exactly one of 8 per-point table entries; a Prime+Probe or SGX-stepping observer maps touched cache lines back to `groupings[s][b]`, yielding the 3-bit windows of the secret share. Reassembling all windows recovers the full scalar, hence the victim's threshold share.
