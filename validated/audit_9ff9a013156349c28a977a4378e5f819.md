Based on the investigation, I found a strong local analog to the reported bug pattern (unbounded array parameter processed without an early size limit, unlike sibling RPC methods that do enforce limits).

### Title
`getRecentPrioritizationFees` accepts unbounded `pubkeys` array with no length limit, unlike sibling RPC methods - (File: `rpc/src/rpc.rs`)

### Summary
Agave's JSON-RPC surface enforces explicit array-size limits on most user-supplied list parameters before doing any real work: `getMultipleAccounts` is capped by `MAX_MULTIPLE_ACCOUNTS`, `getSignatureStatuses` by `MAX_GET_SIGNATURE_STATUSES_QUERY_ITEMS`, `getInflationReward` by `MAX_GET_INFLATION_REWARD_ADDRESSES`, and `getProgramAccounts`/`programSubscribe` filters by `MAX_GET_PROGRAM_ACCOUNT_FILTERS` (enforced via `verify_filters`). However, `get_recent_prioritization_fees` takes an arbitrary-length `pubkeys: Vec<Pubkey>` and performs no such check before calling into `PrioritizationFeeCache::get_prioritization_fees`. This mirrors exactly the class of bug in the external report: an array-typed filter/query parameter that is not bounded early, letting an attacker force expensive processing proportional to array size.

### Finding Description
The RPC handler is defined as: [1](#0-0) 

Unlike its neighboring limit constants defined right after it in the same file: [2](#0-1) 

and the pattern used for other array parameters, e.g. `getInflationReward`: [3](#0-2) 

there is no equivalent `if pubkeys.len() > MAX_...` guard anywhere before `get_recent_prioritization_fees` is invoked. The underlying cache method it calls iterates every cached slot and, for each slot, iterates the entire caller-supplied `account_keys` slice doing a hashmap lookup per key: [4](#0-3) 

Because the number of cached slots can be up to ~150 blocks (as documented in the client-facing docs) and `account_keys.len()` is fully attacker-controlled with no upper bound, the total work is `O(cached_slots * pubkeys.len())` per single RPC call, with no cap on `pubkeys.len()`. Also note this handler runs directly on the async RPC dispatch path (no `spawn_blocking`), unlike scan-heavy endpoints such as `get_filtered_program_accounts`, which explicitly offload to a blocking thread pool: [5](#0-4) 

So a request with, say, hundreds of thousands or millions of pubkeys is deserialized and processed inline, consuming CPU/memory on a request-handling task and potentially degrading or stalling the JSON-RPC service for other legitimate low-rate callers on that node — the same "unbounded array causes disproportionate resource consumption" primitive as the reported `FilterCriteria.Topics` issue.

### Impact Explanation
This is an unprivileged, remotely triggerable RPC-only resource-exhaustion primitive: any external client can send a single `getRecentPrioritizationFees` request with an oversized `pubkeys` array and force the validator's RPC-serving thread to do unbounded work, degrading RPC availability/latency for that node (single-client low-rate RPC degradation/crash class). It does not affect consensus, funds, or execution correctness — it's a node-local availability issue scoped to the RPC subsystem.

### Likelihood Explanation
High likelihood of triggerability: the endpoint is public, requires no special privileges, and the missing check is a simple omission relative to consistently-applied sibling limits elsewhere in the same file (`MAX_MULTIPLE_ACCOUNTS`, `MAX_GET_SIGNATURE_STATUSES_QUERY_ITEMS`, `MAX_GET_INFLATION_REWARD_ADDRESSES`, `MAX_GET_PROGRAM_ACCOUNT_FILTERS`). A single crafted JSON-RPC POST is sufficient to exploit it; no gossip/peer trust or state manipulation is required.

### Recommendation
Add an early length check on `pubkeys` in `get_recent_prioritization_fees` (or in its RPC trait binding, mirroring `MAX_GET_INFLATION_REWARD_ADDRESSES`/`MAX_MULTIPLE_ACCOUNTS`), e.g. define a `MAX_GET_RECENT_PRIORITIZATION_FEES_ACCOUNTS` constant in `rpc-client-types/src/request.rs` and reject requests exceeding it with `Error::invalid_params` before touching the cache, consistent with the existing validation pattern in `rpc/src/rpc.rs`.

### Proof of Concept
1. Start a validator with the RPC service enabled (`enable_rpc_transaction_history` not even required — `getRecentPrioritizationFees` works on the default full RPC API).
2. Send a JSON-RPC request:
```json
{"jsonrpc":"2.0","id":1,"method":"getRecentPrioritizationFees","params":[[<N distinct base58 pubkeys, N = e.g. 1_000_000>]]}
```
3. Observe that `JsonRpcRequestProcessor::get_recent_prioritization_fees` (rpc/src/rpc.rs:2440) performs `O(cached_slots * N)` hashmap lookups synchronously on the request path with no rejection, unlike `getMultipleAccounts`/`getInflationReward`/`getProgramAccounts`, which reject oversized inputs immediately via their respective `MAX_*` checks.

Note: I was unable to fully inspect the exact `#[rpc(name = "getRecentPrioritizationFees")]` trait-binding wrapper function body in this session (the tool budget was exhausted before that specific read completed), so I cannot 100% rule out that a length check exists purely in that wrapper rather than in `JsonRpcRequestProcessor::get_recent_prioritization_fees`. However, no `MAX_GET_RECENT_PRIORITIZATION_FEES_*`-style constant exists anywhere in `rpc-client-types/src/request.rs` (confirmed by listing all `MAX_*` constants there), which strongly suggests no such limit exists for this endpoint, unlike every other array-parameter RPC method surveyed.

    pub fn get_prioritization_fees(&self, account_keys: &[Pubkey]) -> Vec<(Slot, u64)> {
        self.cache
            .read()
            .unwrap()
            .iter()
            .map(|(slot, slot_prioritization_fee)| {
                let mut fee = slot_prioritization_fee
                    .get_min_compute_unit_price()
                    .unwrap_or_default();
                for account_key in account_keys {
                    if let Some(account_fee) =
                        slot_prioritization_fee.get_writable_account_fee(account_key)
                    {
                        fee = std::cmp::max(fee, account_fee);
                    }
                }
                (*slot, fee)
            })
            .collect()
    }
