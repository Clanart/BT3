Based on my research, I found a genuine analog in sei-chain's ERC pointer-upgrade mechanism, though it manifests through in-place bytecode replacement rather than an OpenZeppelin proxy/inheritance pattern.

### Title
Pointer contract "upgrade" replaces bytecode in-place without any storage-layout compatibility check, risking storage slot collision - (File: x/evm/keeper/pointer_upgrade.go)

### Summary
The original report flags missing storage gaps in upgradeable base contracts, which lets a later version's variable additions overwrite a child contract's existing storage slots. Sei-chain has no OpenZeppelin `Initializable`/`UUPSUpgradeable` contracts in its production pointer contracts [1](#0-0) , but it implements an equivalent "upgrade in place" mechanism for CW↔ERC pointer contracts that has the same root cause: replacing an implementation's code at a fixed address while the old account's storage persists, with no mechanism to verify or reserve for storage-layout compatibility between versions.

### Finding Description
`UpsertERCPointer` in `x/evm/keeper/pointer_upgrade.go` is the shared routine used to create or upgrade native/CW20/CW721/CW1155 → ERC pointer contracts. When a pointer for a given token already exists, instead of deploying a fresh contract, it re-runs the new pointer artifact's constructor bytecode at the **existing contract address** via `evm.GetDeploymentCode(...)` and then overwrites only the code via `k.SetCode(...)`: [2](#0-1) 

This preserves all of the account's prior storage (balances, allowances, minted amounts, name/symbol strings, etc.) while swapping in a new implementation's constructor and runtime code — conceptually identical to a delegatecall-based proxy upgrade, but done by direct state-machine intervention instead of Solidity inheritance. There is no versioned storage layout contract, no gap reservation, and no check that the new pointer artifact's storage slot assignments are backward compatible with the old one's. The pointer contracts (`CW20ERC20Pointer`, native ERC pointers, CW721/CW1155 pointers) are simple non-upgradeable contracts by design (`contract CW20ERC20Pointer is ERC20 { ... }` with only a constructor, no initializer pattern) [3](#0-2) , meaning nothing in their own source anticipates being redeployed onto pre-existing storage.

Multiple legacy precompile implementations (`v552`, `v555`, `v562`) show that the on-chain pointer/precompile logic has evolved release over release [4](#0-3) , and a dedicated migration path (`MigrateAllPointers`) exists specifically to re-upgrade every pointer contract on-chain to the current artifact [5](#0-4) . This confirms in-place, storage-preserving upgrades are an expected, recurring operation, not an edge case.

### Impact Explanation
If a future pointer contract version reorders, removes, or adds state variables relative to an older version (analogous to adding new variables in a base contract without a storage gap), the constructor executed by `GetDeploymentCode` at the pre-existing address will write to storage slots that the old contract populated with different semantics (e.g. a `balances` mapping base slot shifting to overlap with what used to be `totalSupply`, or vice versa). This can corrupt already-recorded user balances/allowances for existing pointer tokens, causing fund-accounting corruption (loss or fabrication of balances) for any CW20/CW721/CW1155/native token that has a registered pointer — reachable by any unprivileged user who owns or interacts with a pointer token, since pointer creation/upgrade is triggered by ordinary `MsgRegisterPointer` messages or automatic first-touch pointer creation, not an admin-gated action [6](#0-5) .

### Likelihood Explanation
Likelihood is **conditional on a future protocol upgrade** shipping a new pointer artifact whose storage layout is incompatible with the previous version — the same trigger condition as the original report (a new base-contract release adding variables). It is not exploitable by an attacker crafting a single malicious transaction today; it is a systemic design gap that could be silently triggered by ordinary chain-upgrade pointer migrations. I could not directly diff the Solidity source across pointer versions (only the currently compiled bytecode/ABI is present under `x/evm/artifacts/`, prior `.sol` sources for older pointer versions are not present in the indexed codebase), so I cannot confirm a concrete storage-layout diff has already shipped; this is a structural risk rather than a proven active bug.

### Recommendation
Adopt an explicit, versioned storage-layout contract for each pointer type (mirroring OpenZeppelin's storage-gap pattern) so that new pointer artifact versions are constrained to append-only storage layouts, or alternatively require full state migration/reinitialization logic (rather than raw constructor re-execution) whenever a pointer's storage layout changes, verified by tooling (e.g., OpenZeppelin's `@openzeppelin/hardhat-upgrades` storage-layout checks) as part of the artifact-generation pipeline in `x/evm/artifacts/`.

### Proof of Concept
Not independently reproducible from the available index because no historical pointer-artifact source differs in storage layout was found; the structural weakness is demonstrated by the code path itself:
1. `MsgRegisterPointer` (or the internal `UpsertERCPointer` call during automatic pointer upgrades) detects an existing pointer via `getter(liveCtx(), pointee)` [7](#0-6) .
2. It calls `evm.GetDeploymentCode` with the **new** artifact's init bytecode but the **old** contract's address, executing the new constructor against the old account's storage, then overwrites only the code via `k.SetCode` [8](#0-7) .
3. Any mismatch between the old and new artifact's storage-slot assignment for state variables would corrupt prior state (balances/allowances) at that address, exactly mirroring the impact described for missing storage gaps in the reported base contracts.

func MigrateERCCW20Pointers(ctx sdk.Context, k *keeper.Keeper) error {
	iter := prefix.NewStore(ctx.KVStore(k.GetStoreKey()), append(types.PointerRegistryPrefix, types.PointerERC20CW20Prefix...)).ReverseIterator(nil, nil)
	defer func() { _ = iter.Close() }()
	seen := map[string]struct{}{}
	for ; iter.Valid(); iter.Next() {
		cwAddr := string(iter.Key()[:len(iter.Key())-2]) // last two bytes are version
		if _, ok := seen[cwAddr]; ok {
			continue
		}
		seen[cwAddr] = struct{}{}
		addr := common.BytesToAddress(iter.Value())
		oName, err := k.QueryERCSingleOutput(ctx, "cw20", addr, "name")
		if err != nil {
			logger.Error("Failed to upgrade pointer due to failed name query", "pointer", cwAddr, "err", err)
			continue
		}
		oSymbol, err := k.QueryERCSingleOutput(ctx, "cw20", addr, "symbol")
		if err != nil {
			logger.Error("Failed to upgrade pointer due to failed symbol query", "pointer", cwAddr, "err", err)
			continue
		}
		_ = k.RunWithOneOffEVMInstance(ctx, func(e *vm.EVM) error {
			_, err := k.UpsertERCCW20Pointer(ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx)), e, cwAddr, utils.ERCMetadata{
				Name:   oName.(string),
				Symbol: oSymbol.(string),
			})
			return err
		}, func(s1, s2 string) {
			logger.Error("Failed to upgrade pointer at step", "pointer", cwAddr, "from-step", s1, "to-step", s2)
		})
	}
	return nil
}

func (server msgServer) RegisterPointer(goCtx context.Context, msg *types.MsgRegisterPointer) (*types.MsgRegisterPointerResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	if server.GetRegisterPointerDisabled(ctx) {
		return nil, fmt.Errorf("registering CW->ERC pointers has been disabled")
	}
	var existingPointer sdk.AccAddress
	var existingVersion uint16
	var currentVersion uint16
	var exists bool
	switch msg.PointerType {
	case types.PointerType_ERC20:
		currentVersion = erc20.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW20ERC20Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC721:
		currentVersion = erc721.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW721ERC721Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC1155:
		currentVersion = erc1155.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW1155ERC1155Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	default:
		panic("unknown pointer type")
	}
	if exists && existingVersion >= currentVersion {
		return nil, fmt.Errorf("pointer %s already registered at version %d", existingPointer.String(), existingVersion)
	}
