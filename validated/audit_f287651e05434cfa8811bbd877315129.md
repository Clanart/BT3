### Title
Aggregator gRPC server accepts state-mutating RPCs from unauthenticated peers when `client_verification=false` - ([File: core/src/servers.rs] / [File: core/src/rpc/interceptors.rs])

### Summary
When `BridgeConfig.client_verification` is `false` (the default unless the `CLIENT_VERIFICATION` env var is explicitly set to `true`), `create_grpc_server` builds a `ServerTlsConfig` with only a server identity and wraps the service in `Interceptors::Noop`, which unconditionally returns `Ok(req)` without ever checking `req.peer_certs()`. Any TCP client that completes a TLS handshake with no client certificate can therefore invoke every aggregator RPC, including state-mutating ones.

### Finding Description
The binding this deployment is supposed to enforce is: *a TLS session accepted by the aggregator's gRPC listener == a session whose leaf certificate equals `aggregator_cert` or `our_cert`*, which is exactly what `only_aggregator_and_self` checks [1](#0-0) .

That binding is only wired up when `config.client_verification` is `true`: [2](#0-1) 

When `client_verification` is `false` (its value is derived from `read_string_from_env("CLIENT_VERIFICATION").is_ok_and(|s| s == "true" || s == "1")`, i.e. `false` by default absent an explicit env var), two things happen simultaneously:
1. `ServerTlsConfig::new().identity(server_identity)` is built with no `.client_ca_root(...)`, so the TLS handshake never requests, let alone validates, a client certificate.
2. The service is wrapped with `Interceptors::Noop`, whose `call` implementation is `Ok(req)` with zero inspection of `req.peer_certs()` [3](#0-2) .

Because both the TLS layer and the interceptor layer skip verification together, no code path in the request lifecycle ever evaluates the `leaf_cert == aggregator_cert || leaf_cert == our_cert` equality — the check simply never runs. `create_aggregator_grpc_server` even emits a warning only when verification *is* enabled [4](#0-3) , confirming that the disabled state is the expected/default operating mode for this code path, not a misconfiguration guarded against elsewhere.

An attacker's exploit is trivial: open a `rustls` TLS connection to the aggregator's public port with no client identity (or a self-signed one), then send any state-mutating gRPC request (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`). The TLS handshake succeeds (server never demands a cert), the request passes through `AddMethodMiddlewareLayer` and `InterceptedService`, and `Noop::call` returns `Ok(req)` unconditionally, dispatching the request to the real RPC handler as if it came from a legitimate aggregator client.

No other guard in the reachable path substitutes for this check: `AddMethodMiddlewareLayer` only annotates the `grpc-method` metadata used by `is_internal`, it performs no identity check; rate limiting/concurrency layers are explicitly out of scope and provide no authentication; and downstream handlers for `Setup`/`NewDeposit`/etc. are not shown to independently re-verify caller identity — they rely on the interceptor layer for that purpose.

### Impact Explanation
This is a High-severity finding under the stated categories: "an unauthenticated state-changing or broadcasting call." Any unprivileged internet host can invoke aggregator RPCs that orchestrate bridge setup and fund-moving flows (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`) without holding any TLS certificate, key share, or authorization. The blast radius is not limited to a single deposit or operator — because `client_verification` is a single global toggle applied identically to verifier, operator, and aggregator servers, disabling it removes authentication from the entire internal RPC surface, including `Internal`-marked methods intended to be self-only, at every entity in the bridge, not just the aggregator port called out in the question.

### Likelihood Explanation
The only precondition is the default configuration: `CLIENT_VERIFICATION` env var unset (or any value other than `"true"`/`"1"`), which is the out-of-the-box default per `BridgeConfig::from_env` [5](#0-4) . The attacker needs no BTC, no fees, no prior interaction with the bridge — only network reachability to the aggregator's TCP port and a TLS client library capable of an anonymous/self-signed handshake. This is fully repeatable and requires no privileged access of any kind.

### Recommendation
Do not allow the TLS/authentication layer to be fully disabled for production deployments, or at minimum make the interceptor itself enforce peer-certificate verification independent of the `client_verification` toggle. Concretely: always call `.client_ca_root(...)` on `ServerTlsConfig` (mTLS mandatory), and remove/guard the `Noop` variant of `Interceptors` so it cannot be selected for network-reachable listeners; if a no-verification mode is still desired for local/dev use, restrict it to Unix-socket transports only, which already bypass TLS entirely by design.
