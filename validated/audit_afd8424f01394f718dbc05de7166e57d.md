### Title
Unauthenticated disclosure of encrypted emergency-stop transaction via `InternalGetEmergencyStopTx` - ([File: core/src/rpc/interceptors.rs])

### Summary
The `Internal*`-prefixed aggregator RPCs (including `internal_get_emergency_stop_tx`) are only restricted to the aggregator's own client certificate by `only_aggregator_and_self` when `client_verification=true` [1](#0-0) . When `client_verification=false`, the server installs the `Noop` interceptor which performs no caller-identity check at all [2](#0-1) , so any unauthenticated caller reaching the aggregator's gRPC port can invoke `internal_get_emergency_stop_tx` and retrieve the encrypted emergency-stop transaction for any `move_to_vault_txid` it observed on-chain.

### Finding Description
The intended binding is: `is_internal(req) == true` implies `caller == aggregator's own client certificate`, enforced in `only_aggregator_and_self` [3](#0-2) . This binding is only wired in when the `OnlyAggregatorAndSelf` interceptor variant is selected, which itself is gated by `config.client_verification` in `create_grpc_server` [2](#0-1) . When `client_verification=false`, the interceptor becomes `Noop`, which returns `Ok(req)` unconditionally for every method, `Internal`-prefixed or not [4](#0-3) . In that mode the "Internal" naming convention that is supposed to gate `internal_get_emergency_stop_tx` to the aggregator's own certificate provides no actual protection, and the RPC is reachable identically to any other public method on the aggregator's gRPC surface. Any caller who knows a `move_to_vault_txid` (public once the transaction confirms) can call `InternalGetEmergencyStopTx` and receive the stored encrypted emergency-stop transaction row, which was written by `verify_and_save_emergency_stop_sigs` via `insert_signed_emergency_stop_tx_if_not_exists`.

Notably, this is a configuration-contingent gap, not a defect independent of deployment configuration: with `client_verification=true`, `only_aggregator_and_self` fully blocks non-self callers from `Internal`-prefixed methods regardless of the caller knowing the txid. The code's own warning — emitted only when `client_verification=true` is set on the aggregator server [5](#0-4)  — indicates that running the aggregator with client verification disabled is an anticipated/expected operational mode (likely because the aggregator must also accept calls from unauthenticated depositor-facing clients), which increases the plausibility that this precondition is met in real deployments rather than being purely theoretical.

### Impact Explanation
No bridge UTXO is spent, no reimbursement is credited, and no collateral is burned by this call alone — the returned emergency-stop transaction is still encrypted under `emergency_stop_encryption_public_key`, so the attacker cannot decrypt or broadcast it. The impact is limited to premature disclosure of the existence/availability of a protocol commitment (the encrypted emergency-stop transaction) to an unauthorized party ahead of its intended controlled reveal, matching the "premature disclosure of a protocol commitment" High-severity category. It does not, by itself, let the attacker move funds, forge a claim, or freeze a UTXO. The disclosure is repeatable across every deposit/move-to-vault txid the attacker observes, but the blast radius per attempt is confined to leaking ciphertext, not value.

### Likelihood Explanation
Exploitability strictly requires the deployment to run the aggregator with `client_verification=false` (the `Noop` interceptor path); if `client_verification=true`, `only_aggregator_and_self` fully closes this path for any non-self caller. Given the codebase's own warning about enabling client verification on the aggregator, `client_verification=false` is a plausible, and possibly typical, aggregator configuration, which raises likelihood. Attacker cost is minimal (no fees beyond the deposit/move-to-vault flow that already occurred, and a single unauthenticated gRPC call); the txid is trivially obtainable from the public chain once move-to-vault confirms.

### Recommendation
Do not rely solely on the `client_verification` TLS toggle to enforce `Internal`-prefixed method restriction. Add an explicit, non-bypassable application-level authorization check inside `internal_get_emergency_stop_tx` (and any other `Internal*` handler) that fails closed when peer-certificate verification is unavailable, rather than defaulting to `Ok(req)` in `Noop`/no-peer-cert cases for internal methods specifically.

### Proof of Concept
Not independently reproducible as a pure code defect: a `cargo test` demonstrating this requires standing up the aggregator with `client_verification=false` (or in `Noop` interceptor mode), completing a deposit/move-to-vault flow so `verify_and_save_emergency_stop_sigs` populates the DB row, then issuing an unauthenticated `InternalGetEmergencyStopTx` call with only the public `move_to_vault_txid` and asserting the encrypted transaction bytes are returned. Because the vulnerable condition is gated entirely behind the `client_verification` configuration flag rather than an intrinsic logic flaw in `is_internal`/`only_aggregator_and_self` (which correctly enforces the binding when enabled), this finding is configuration-dependent rather than a standalone code-level authorization bug.

fn is_internal(req: &Request<()>) -> bool {

        return false;
    };

}

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}
