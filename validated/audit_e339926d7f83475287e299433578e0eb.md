### Title
Sybil self-referral via `registerCode`/`useCode` allows unbacked MGP referral-reward extraction on every claim - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.useCode` only blocks a user from referring themselves (`codeOwners[_code] == msg.sender`), but does nothing to prevent two addresses controlled by the same attacker from linking as referer/referee. Because `trigger()` (called by `MasterMagpie._multiClaim`) mints referral credits purely as a percentage of the referee's own claimed MGP with no check on independent, genuine third-party activity, an attacker controlling two EOAs can generate extra, protocol-funded MGP (`refererAmount` + `refereeAmount`) on every claim, on top of the reward the referee already receives from staking.

### Finding Description
`useCode` at [1](#0-0)  enforces only:
- code must exist,
- `codeOwners[_code] != msg.sender` (can't refer literally the same address),
- caller has no existing referer.

Nothing checks that the referer and referee are economically independent parties. An attacker fully controls both A (registers code) and B (uses code) — both are ordinary unprivileged EOAs.

When B stakes in MasterMagpie and calls any claim function, `_multiClaim` computes `totalReward` (B's own accrued MGP reward) and, if a `referral` contract is set, calls `IReferralStorage(referral).trigger(_user, totalReward)`: [2](#0-1) .

Inside `trigger()`, as long as `myReferer[_referee] != address(0)` (true here because B called `useCode`), the function computes `refererAmount` and `refereeAmount` as percentages of `_amount` (B's total claimed reward) and adds them to `refererInfo.rewardAmount` (A) and `refereeInfo.rewardAmount` (B) respectively: [3](#0-2) . These amounts are **not deducted from B's already-paid `totalReward`** — MasterMagpie already sent/queued the full `totalReward` to B via `_sendMGP`/`_sendVlMGPFor`/`_sendMGPForVlMGPPool` before `trigger()` is even called [4](#0-3) . The referral amounts are additive credits drawn later from `ReferralStorage`'s own MGP balance via `claimReward()`: [5](#0-4) .

Since A and B are the same attacker, every claim B makes for their own staking activity now also mints bonus MGP payable to A (the "referer") plus a referee bonus to B, both funded from the referral pool, with zero genuine independent referral occurring. Repeating stake/claim cycles scales this indefinitely with no cap tied to unique referred users, capital committed by a third party, or any sybil-resistance check (KYC, minimum stake divergence, cooldown, etc.).

No existing modifier stops this: `useCode` has no `nonReentrant`/pausable dependency relevant here, `trigger()` is correctly gated to `_onlyMasterMagpie`, but the underlying business logic never verifies that referer ≠ referee's alternate address.

### Impact Explanation
This allows any single attacker with two wallets to continuously extract extra MGP from `ReferralStorage`'s reward budget for every claim of their own genuine staking rewards, without ever bringing in a real referred user. This matches the "theft of unclaimed yield" impact class — MGP intended to reward organic referral growth is drained by self-dealing loops, diluting/depleting the pool available to legitimate referrers and constituting an economic exploit of the referral reward budget.

### Likelihood Explanation
- Requires only two attacker-controlled EOAs and enough capital to stake and generate any nonzero claimable MGP in MasterMagpie — a low, easily met precondition.
- Fully repeatable: every claim cycle by B mints new referral credit to A and B.
- No privileged role is needed; `registerCode`, `useCode`, and the claim path are all public/external functions reachable by any unprivileged account.
- The only variable factor is `tiers[tierId].rewardPercentage` and `sharePercent`, which determine the payout percentage but do not prevent the exploit itself — as long as any tier has nonzero `rewardPercentage`, gains are realized.

### Recommendation
Add sybil-resistance to the referral linkage, e.g.:
- Require a minimum time delay or unrelated on-chain identity signal between registration and first `useCode` use per code (does not fully solve, but raises cost).
- Cap total referral rewards per referer proportional to genuinely externally-sourced deposits, or require KYC/off-chain vetting for referral program eligibility (protocol/business decision).
- More robust: fund the referrer/referee bonus by "sharing" part of what would otherwise be paid to the referee (i.e., actually redirect/reduce the referee's own MGP payout in `_multiClaim`/`trigger`, rather than crediting an additive bonus from a separately funded pool), removing the "something for nothing" mint characteristic. This at minimum removes the "unbacked" component of the incentive (attacker would only be redistributing their own reward between two of their own wallets, netting to zero rather than a real gain).

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `ReferralStorage`, `MGP`, and a staking pool; fund `ReferralStorage` with a fixed MGP balance (simulating protocol-funded referral pool) and set a tier (`setTier(1, rewardPercentage)`) and `sharePercent`.
2. Baseline: EOA `C` stakes X MGP-equivalent tokens in MasterMagpie, no referral code used, claims via `multiclaim`. Record `MGP.balanceOf(C)` delta = `totalReward`.
3. Sybil case: EOA `A` calls `registerCode(codeA)`. EOA `B` (same attacker) calls `useCode(codeA)`. `B` stakes the same amount X as `C` did and calls `multiclaim`, triggering `ReferralStorage.trigger(B, totalReward)`.
4. Both `A` and `B` call `claimReward()`.
5. Assert: `MGP.balanceOf(B) + MGP.balanceOf(A) (from claimReward) > totalReward` that `C` received for identical staking activity — i.e., attacker controlling A+B nets strictly more MGP than an honest non-referred staker for identical stake/claim behavior, proving unbacked extra emission drawn from `ReferralStorage`'s pool.
6. Repeat the stake/claim loop N times and confirm the extra payout accumulates linearly, demonstrating unlimited/repeatable extraction limited only by the referral pool's MGP balance.

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
