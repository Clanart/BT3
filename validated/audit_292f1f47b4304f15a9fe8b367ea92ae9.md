### Title
Stale line-index diff selection silently applied to a different on-disk diff during partial commit, allowing attacker-triggered file mutation to commit unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
Desktop's partial-commit feature lets a user select individual diff lines to include. The selection (`DiffSelection`) is stored purely as line-index offsets into the diff hunk structure that was rendered at selection time, not tied to file content/hashes. At commit time, Desktop re-computes a brand-new diff from the working directory (`getWorkingDirectoryDiff`) and blindly re-applies the old index-based selection to this new diff (`formatPatch`) with no comparison against the diff the user actually reviewed.

### Finding Description
The flow is:
1. User opens the Changes view; Desktop computes a diff and the user selects specific lines via `DiffSelection.withLineSelection`/`withRangeSelection`, which records only integer line indices [7](#0-6) .
2. When the user clicks Commit, `_commitIncludedChanges` snapshots `state.changesState.workingDirectory.files` and passes the selected `WorkingDirectoryFileChange` objects (including their stale `selection`) straight into `createCommit` [8](#0-7) .
3. `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff from disk right before staging (`const diff = await getWorkingDirectoryDiff(repository, file)`) [9](#0-8) .
4. `formatPatch` walks this *freshly fetched* diff and calls `file.selection.isSelected(absoluteIndex)` using the *old* line indices to decide which lines to include [10](#0-9) .

If the on-disk file content changes between the moment the user made their line selection and the moment `createCommit` runs — e.g., because the repository (attacker-controlled, freshly cloned/fetched) contains a `.gitattributes` clean/smudge filter, an `.git/hooks/*` script (if hooks aren't disabled), a background editor auto-format, or any async process that touches the tracked file — the hunk layout shifts. The stale numeric selection then maps onto different lines than what the user reviewed and approved. Because `formatPatch` has no way to detect that the underlying diff changed (no hash/version check comparing the diff used at selection time vs. commit time), this fails silently: `git apply --cached` succeeds against the new diff and the wrong content is staged and committed. There is a comment acknowledging Desktop's data-flow ambitions around immutability elsewhere in the codebase, but no actual staleness guard exists on this path [11](#0-10) .

This is the structural analog of the Sherlock H-5 bug: a value (fund balance / diff-line snapshot) is captured at one point in time, and a later mutation by an external actor (refund / file mutation) is not accounted for before the snapshot is consumed, producing an incorrect result that is applied without re-validation.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes" — one of the explicitly valid impact categories. A user could unknowingly commit and push content they never reviewed or approved (e.g. lines they explicitly deselected get included, or vice versa), which can leak unintended data or introduce unreviewed/malicious code into a shared branch. Because the failure mode is silent (no error, no unusual UI state), the user has no signal that the commit doesn't match what they saw in the diff viewer.

### Likelihood Explanation
The likelihood is constrained by the need for a race window between selection and commit and a mechanism to trigger a file mutation in that window (e.g., clean/smudge filters, git hooks, LFS pointers resolving, or file-watcher-triggered saves from an editor/build tool acting on the malicious repo's configured tooling). I was not able to verify from the index whether Desktop explicitly disables local hook execution for arbitrary repos or sanitizes `.gitattributes` filters before this window, which would materially affect exploitability — this is a gap in what I could confirm from available files and would need to be checked in a live environment before treating this as fully confirmed.

### Recommendation
Before applying a stored `DiffSelection` to the freshly-fetched diff in `applyPatchToIndex`, verify the new diff is structurally/content-equivalent to the diff the selection was computed against (e.g., compare a hash of the diff object, or hunk boundaries/line counts), and if it has changed, abort the partial commit and force the user to re-review the diff rather than silently applying stale indices to new content.

### Proof of Concept
Not independently executable from static code review alone; based on code-path tracing:
1. Clone/open an attacker-authored repository containing a modified tracked file and a mechanism that mutates that file shortly after being read (e.g., a `.gitattributes` `filter.<name>.smudge`/`clean` script, or, if enabled, a `post-checkout`/`pre-commit` hook that rewrites the file).
2. In the Changes view, the user reviews the diff and selects only certain lines via the line-selection UI (backed by `DiffSelection`) — recorded purely as integer indices [12](#0-11) .
3. Trigger the mutation (attacker-controlled filter/hook fires, or an external process modifies the file) so the file's line layout shifts before the user clicks Commit.
4. On commit, `applyPatchToIndex` fetches a new diff and reuses the stale `DiffSelection` indices [13](#0-12) , producing a patch that includes/excludes different lines than the user intended, which is committed without error.

    const to = from + length

    // selected and we're being asked to select more or when no lines are
    // selected and we're being asked to unselect something.

      return this

      if (typeMatchesSelection(this.defaultSelectionType, selected)) {

          newDivergingLines.delete(i)
        }

          if (this.isSelectable(i)) {
            newDivergingLines.add(i)
          }
        }
      }

        newDivergingLines.size === 0 ? null : newDivergingLines,

    } else {

      for (let i = from; i < to; i++) {

          newDivergingLines.add(i)
        }
      }

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
