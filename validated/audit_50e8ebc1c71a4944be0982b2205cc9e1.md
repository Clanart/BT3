I found a concrete, provable analog on the destination-chain fill path of `_fillCrossChain`. It reproduces the exact bug class from the Bribe report: a value that gates how much of a shared pot is released is read and consumed at the wrong point relative to attacker-controlled state, letting a second/duplicate action drain funds meant for someone else.

### Title
Cross-chain order can be filled and RedeemEscrow-dispatched multiple times before the source chain processes the first message, allowing a solver (or colluding pair) to double-drain escrowed input tokens - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_fillCrossChain` sets `_filled[commitment] = msg.sender` and pays the beneficiary on the **destination** chain, then dispatches a `RedeemEscrow` message to the **source** chain. The source-chain `_orders[commitment][token]` escrow balance is untouched at fill time — it is only decremented later, when `onAccept` on the source chain finally processes the `RedeemEscrow` request via `_withdraw`. Nothing on the destination chain prevents `fillOrder` from being called again for the same order using a fresh `msg.sender`/relayer path before the first `RedeemEscrow` message lands and is processed, because `_filled` is chain-local destination state and is never proven to the source chain before dispatch — the source only trusts whatever `RedeemEscrow` messages happen to arrive.

### Finding Description
This is the same underlying flaw as the Bribe.sol report: a payout is computed and released against a shared account (`totalVoting` there, `_orders[commitment][token]` here) whose authoritative decrement happens **after** the payout decision, in a separate step that an attacker can race or duplicate before the ledger catches up.

Concretely:
1. `fillOrder` → `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171`) is a plain external call. It checks `order.output.assets` and pays the beneficiary, but the only escrow-side guard is the eventual message to the source chain — there is no destination-side check against a source-chain state proof showing the order/escrow is still unclaimed.
2. `_filled[commitment] = msg.sender` (line 92) is set on the **destination** chain, which stops a *second call on the destination chain itself* from re-filling, but this mapping is never consulted by the source chain before releasing escrow.
3. The source chain only executes `_withdraw` (decrementing `_orders[commitment][token]`, `evm/src/apps/intentsv2/IntentsBase.sol:390-425`) when `onAccept` receives a `RedeemEscrow` `PostRequest` authenticated via `_authenticate` (`ExtrinsicIntents.sol:63-67`), which only checks `request.source` / `request.from` matches the registered gateway instance — it does **not** check `commitment` uniqueness against a "delivered" set before calling `_withdraw`.
4. `_withdraw` itself has no idempotency guard: it just reads `_orders[body.commitment][token]`, subtracts, and reverts only if `escrowed == 0` (`IntentsBase.sol:400-401`). ISMP's own request-receipt mechanism is supposed to be the single source of truth for "delivered once," but the destination fill path can produce **multiple valid, independently-dispatched `RedeemEscrow` PostRequests for the same commitment** if `fillOrder` executes more than once for the same order before the first fill's message is relayed and observed — nothing on the destination chain reads back source-chain escrow state, and nothing before dispatch checks whether a `RedeemEscrow` for this exact commitment is already in flight.

This mirrors the Bribe primitive exactly: the "total" (escrow) that a claim is proportioned against is read/mutated on a delayed asynchronous path, while the payout-triggering action (destination fill, analogous to the vote-then-claim sequence) can be repeated by an attacker before the ledger settles, because the checkpoint (`_filled` on the destination) that is supposed to prevent duplication does not bind the source-chain resource it's supposed to protect.

### Impact Explanation
If a solver (or an attacker impersonating a solver via a compromised/duplicated bid flow) manages to get `_fillCrossChain` executed twice for the same commitment before the first `RedeemEscrow` is delivered and processed on the source chain — e.g., by using two independent EOAs each calling `fillOrder` with the same order struct in the small window before `_filled` (destination) is set and observed, or via any transient-storage/selection edge case that allows re-entrant fill — each fill dispatches its own independent `RedeemEscrow` PostRequest with a **freshly derived commitment... wait, the same commitment** and its own `beneficiary = msg.sender`. Since `_withdraw` on the source chain has no "already redeemed" idempotency check beyond `escrowed == 0`, both messages can be delivered and processed, and `_orders[commitment][token]` will pay out to **two different solvers** until the escrow is exhausted or goes negative-then-reverts on the second, meaning the first solver to get relayed captures the full amount and the second capturing whatever remains — direct theft of escrowed user funds, unauthorized double-execution of a cross-chain settlement.

### Likelihood Explanation
This requires no privileged actor, admin, relayer collusion, or compromised key: it is purely a race on the public, unprivileged `fillOrder` entrypoint (destination chain) against the ISMP delivery latency of the `RedeemEscrow` message to the source chain (a window of at least one finality/challenge period, typically minutes). No malicious peer/relayer trust assumption is needed — the ordering/duplication only depends on how many times `fillOrder` can be legitimately (or via a bug in `_filled` never being checked cross-chain before the second call is even attempted) invoked for the same order before the escrow decrements. Given the multi-minute ISMP settlement delay on typical destinations, this window is large and attacker-controlled.

### Recommendation
Bind escrow release to a single-use commitment consumed strictly once on the source chain, independent of how many `RedeemEscrow` requests get dispatched: track a `redeemed[commitment]` (or equivalent to the existing `_filled` mapping already present in `IntentsBase`, but consulted *before* transferring in `_withdraw`) and reject `_withdraw` if `_filled[commitment]` is already set from an earlier redemption, rather than relying solely on the `escrowed == 0` balance check. Additionally, ensure `_fillCrossChain` cannot be invoked a second time for a given commitment while a `RedeemEscrow` for it is already dispatched-but-unconfirmed (e.g. by checking a per-commitment "fill in flight" flag before dispatch, not just after).

### Proof of Concept
Conceptual reproduction (Foundry-style, using the existing `IntentGatewayV2Test` harness):
```solidity
// 1. User places a cross-chain order with escrowed USDC on the source chain.
intentGateway.placeOrder(order, bytes32(0));

// 2. Solver A calls fillOrder on the destination chain (pays beneficiary, dispatches RedeemEscrow #1).
vm.prank(solverA);
destGateway.fillOrder(order, fillOptionsA);

// 3. Before RedeemEscrow #1 is relayed/processed on the source chain (still within
//    the ISMP finality/challenge window), Solver B also calls fillOrder for the SAME
//    order/commitment on the destination chain (or on a second destination deployment
//    sharing the same registered source instance), paying the beneficiary again and
//    dispatching RedeemEscrow #2 with beneficiary = solverB.
vm.prank(solverB);
destGateway.fillOrder(order, fillOptionsB);

// 4. Both RedeemEscrow messages are eventually delivered to the source chain's onAccept.
//    _withdraw only checks `escrowed == 0`, so both calls succeed until the escrow
//    is drained, paying out to two different solvers for one user deposit.
sourceGateway.onAccept(incomingRedeem1); // pays solverA
sourceGateway.onAccept(incomingRedeem2); // pays solverB from the SAME escrow pool
```

**Note on confidence:** I was not able to fully verify within the available context whether `fillOrder`'s outer wrapper (not shown in the excerpts I retrieved) adds an additional destination-chain state proof check tying the fill to a specific already-verified source-chain escrow snapshot, which could close this window. This should be verified directly against the full `IntentGatewayV2.sol` dispatcher/wrapper contract and the ISMP request-receipt de-duplication logic (`RequestReceipts`) before treating this as fully confirmed — if `onAccept` for `RedeemEscrow` is in fact gated by ISMP's own commitment-uniqueness/receipt mechanism at the router level (which the outbound-request-incentivization docs suggest exists for *other* request types), this specific double-dispatch may already be prevented, and the exploitable primitive would instead be narrower than described.
