### Title
Attacker-controlled Copilot conflict resolution writes file content keyed by a stale/attacker-influenced path without re-validating current conflict identity - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`applyCopilotConflictResolutions` in `app-store.ts` iterates `copilotResolutions` (produced from AI hunks reconstructed from repository conflict content via `reassembleResolutions` in `app/src/lib/copilot-conflict-resolution.ts`) and writes `resolution.resolvedContent` straight to `resolveWithin(repository.path, resolution.path)` if the path resolves inside the repo and the working-directory file is not currently showing unresolved conflicts.

### Finding Description
The resolution objects are keyed purely by `path` [1](#0-0) , mirroring the C4 bug's pattern of trusting a stale key (`plotId`) without re-binding it to the current occupant/state. In `app-store.ts`, the resolution-to-file matching is also done by simple `path` string equality against the current working directory listing, with no check that the file is the *same conflicted entry* the resolution was computed for (e.g. no oldPath/rename tracking, no hash/identity binding): [2](#0-1) 

The only staleness guard is: skip if the on-disk file is a conflicted status with no remaining unresolved markers (meaning the user resolved it externally). This guard is **not equivalent to identity binding** — it only detects "already resolved," not "resolved to a *different* file/content than what the model analyzed." If, between the time the conflict content was captured (`fileContexts`/`rawContent` in `reassembleResolutions`) and the time resolutions are applied, the underlying working-directory file at that path has been renamed/replaced/re-created (e.g. via `git mv`, an external tool, or a hostile `post-checkout`/merge driver acting on an attacker-crafted repo mid-merge), `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` will overwrite whatever now resides at that path — content that was never actually reviewed as "still conflicted at this path" beyond the coarse conflict-marker check.

This is structurally the same invariant break as the C4 report: an operation "moves" (the file's identity changes at a path) but the tracking key (`path` string) used later to authorize a write is never re-validated against the object's *current* identity, so a stale reference is trusted.

### Impact Explanation
This falls in the "silent corruption of what the user commits" category explicitly called out as valid impact. Overwriting file content at a path based on a stale path-keyed resolution during an in-progress merge/rebase/cherry-pick (itself potentially initiated against an attacker-controlled remote/fetched branch with conflicting content designed to trigger this window) can cause Desktop to write attacker-influenced or simply wrong content into the user's working tree and subsequently stage it (`git add`) for commit, without a re-validation step tying the resolution back to the exact conflicted blob it was generated from.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires a merge/rebase/cherry-pick conflict flow using the Copilot resolution feature, and a path collision/replacement window between resolution computation and application. This is a narrower, less certain trigger than the original C4 finding (which was a straightforward, always-reachable state bug). I was not able to find explicit test coverage in `app/test/unit/**` for this specific race/identity-mismatch scenario, so I cannot confirm whether this has already been mitigated by logic elsewhere (e.g., a freshness check before `applyCopilotConflictResolutions` is invoked) that I didn't locate in the indexed portion of the codebase.

### Recommendation
Bind each resolution to more than its `path` string — e.g., include the original conflicted blob SHA or a snapshot hash of `rawContent` alongside the path, and re-verify at apply-time (`app-store.ts`) that the current on-disk conflicted file's content/identity still matches what was captured before writing `resolvedContent`. If it doesn't match, skip and surface a warning rather than silently overwriting.

### Proof of Concept
Not independently reproducible from static analysis alone; the indexed code shows the missing identity check but I could not confirm exploitability (i.e., whether a real race window exists in practice, given `applyCopilotConflictResolutions` is likely invoked synchronously in the same commit flow). This should be validated by tracing the caller of `applyCopilotConflictResolutions` and confirming the time gap between `reassembleResolutions` snapshot capture and the write in `app-store.ts:7258`.
