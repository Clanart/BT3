### Title
Owner/repository records are keyed by mutable GitHub `login` string, allowing a reclaimed username to hijack cached remote-URL/permission data - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
The external report's broken invariant is: a mapping keyed on a *mutable identifier* (operator key) is not invalidated when the underlying entity changes, so a later resolution silently returns the wrong (or attacker-controlled) principal. GitHub Desktop has a structurally identical pattern: its local repository database identifies a GitHub owner purely by the case-insensitive string `${endpoint}/users/${login}` [1](#0-0) , and identifies a `GitHubRepository` by `[ownerID+name]` [2](#0-1) . Neither key incorporates GitHub's immutable numeric account/repo ID. GitHub logins and repository names can be freed (via rename/deletion) and reclaimed by a different, attacker-controlled account. When that happens, Desktop's `putOwner`/`_upsertGitHubRepository` logic transparently reuses the old local `ownerID`/`GitHubRepository` row for the new owner of that string, merging attacker-supplied API data (`clone_url`, `ssh_url`, `permissions`, `parentID`) into a record the user already trusts.

### Finding Description
`putOwner` resolves an owner purely from `getOwnerKey(endpoint, login)` and reuses the existing DB row if the key matches, only refreshing the `login` casing: [3](#0-2) . `_upsertGitHubRepository` then looks up an existing `GitHubRepository` row keyed by `[ownerID+name]` and overwrites its `cloneURL`/`htmlURL`/`permissions`/`parentID` fields with whatever the API now reports for that owner/name pair: [4](#0-3) .

The account/repo resolution path that feeds this upsert is itself string-based: `matchGitHubRepository` derives `owner`/`name` purely by parsing the local git remote URL and matching the account's hostname [5](#0-4) , and `api.fetchRepository(owner, name)` queries GitHub by those strings. `repositoryWithRefreshedGitHubRepository` (invoked, e.g., on account/selection changes) uses this to fetch fresh repo data and then calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` before persisting the new `GitHubRepository` via `upsertGitHubRepository`/`setGitHubRepository`: [6](#0-5) .

**Attacker primitive**: no local access is required. The attacker only needs to register a GitHub account/organization using a username that was previously used by a legitimate owner the victim already has a Desktop-tracked repository for (a real, known GitHub phenomenon — usernames become available after rename or account deletion), and create a repository there with a matching name. Desktop's periodic/account-driven repository refresh will then resolve `owner login string -> local ownerID -> local GitHubRepository row` and silently splice in the attacker's clone URL, permissions, and fork/parent metadata, because none of these lookups verify GitHub's immutable owner/repo IDs against what was previously stored.

**Why existing guards don't stop this**: `shallowEquals` only skips a DB write if the new API payload happens to be identical to what's stored — it doesn't validate identity continuity, so a differing attacker payload always overwrites [7](#0-6) . There is no numeric-ID cross-check anywhere in `putOwner` or `_upsertGitHubRepository`, and the code comment in `app-store.ts` even acknowledges Desktop "never clear[s] GitHub repository associations", relying entirely on this same-key-reuse logic to keep associations "fresh" [8](#0-7) .

### Impact Explanation
If exploited, this can lead to `updateRemoteUrl` rewriting the user's tracked git remote to the attacker's `clone_url`/`ssh_url`, so a subsequent `git push` initiated from Desktop's UI silently sends the user's commits to the attacker-controlled repository, and a subsequent `fetch`/`pull` retrieves attacker-controlled history/content into the user's working copy. It also corrupts permissions (`hasWritePermission`) and fork parent (`parentID`) metadata used elsewhere in the UI/merge logic. This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Likelihood is Low: it requires a username/org-name to become available and be re-registered by an attacker, and it requires the victim to still have a local Desktop repository whose GitHub association keys off that reclaimed login/name and to trigger a refresh (e.g., switching accounts, reopening the repo) after the takeover. No local access, malware, or credential leakage is required — only ordinary use of Desktop plus a public account/repo the attacker controls, consistent with the valid-impact criteria.

### Recommendation
Key local `owners`/`gitHubRepositories` records (and the resolution logic in `putOwner`, `_upsertGitHubRepository`, `matchGitHubRepository`) on GitHub's immutable numeric account/repository IDs rather than (or in addition to, with a mandatory match) the mutable `login`/`name` strings. When the API-reported ID for a given login/name diverges from the ID last associated with the locally cached `ownerID`/`GitHubRepositoryID`, treat it as a new/different repository (create a fresh record and prompt/re-verify) instead of overwriting the existing one, and avoid silently rewriting the remote URL (`updateRemoteUrl`) in that case.

### Proof of Concept
1. Victim clones `https://github.com/alice/project` in GitHub Desktop; Desktop persists `owners` row `key = api.github.com/users/alice` and a `gitHubRepositories` row `[ownerID, "project"]` with `alice`'s `clone_url`/permissions (`putOwner`/`_upsertGitHubRepository`) [9](#0-8) .
2. `alice` renames her GitHub account (or it is deleted); the username `alice` becomes available.
3. Attacker registers GitHub account `alice` and creates a repository named `project` with attacker-controlled content.
4. Victim triggers a repository refresh in Desktop (e.g., switches accounts or reopens the repo), causing `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` (string-based owner/name match) → `api.fetchRepository("alice", "project")` → attacker's repo data returned → `updateRemoteUrl` + `upsertGitHubRepository` overwrite the previously trusted local record with the attacker's `clone_url`/permissions [6](#0-5) .
5. Victim's next push/fetch from Desktop now interacts with the attacker's repository under the guise of the originally trusted `alice/project`.

Note: I was not able to fully trace `updateRemoteUrl`'s implementation body or `API.fetchRepository`'s exact GitHub endpoint call within the indexed content (only file/function locations were found), so the exact mechanics of the remote-URL rewrite step could not be independently confirmed line-by-line; a Devin session with full repository access would be needed to verify that final step in detail.

  private async putOwner(
    endpoint: string,
    login: string,
    ownerType?: GitHubAccountType
  ): Promise<Owner> {
    const key = getOwnerKey(endpoint, login)
    const existingOwner = await this.db.owners.get({ key })
    let id

    // Since we look up the owner based on a key which is the product of the
    // lowercased endpoint and login we know that we've found our match but it's
    // possible that the case differs (i.e we found `usera` but the actual login
    // is `userA`). In that case we want to update our database to persist the
    // login with the proper case.
    if (
      existingOwner === undefined ||
      existingOwner.login !== login ||
      // This is added so that we update existing owners with an undefined type.
      (ownerType !== undefined && existingOwner.type !== ownerType)
    ) {
      id = existingOwner?.id
      const existingId = id !== undefined ? { id } : {}
      id = await this.db.owners.put({
        ...existingId,
        key,
        endpoint,
        login,
        type: ownerType,
      })
    } else {
      id = forceUnwrap('Missing owner id', existingOwner.id)
    }

    return new Owner(login, endpoint, id, ownerType ?? existingOwner?.type)
  }

  public async upsertGitHubRepositoryFromMatch(
    match: IMatchedGitHubRepository
  ) {
    return await this.db.transaction(
      'rw',
      this.db.gitHubRepositories,
      this.db.owners,
      async () => {
        const { account } = match
        const owner = await this.putOwner(account.endpoint, match.owner)
        const existingRepo = await this.db.gitHubRepositories
          .where('[ownerID+name]')
          .equals([owner.id, match.name])
          .first()

        if (existingRepo) {
          return this.toGitHubRepository(existingRepo, owner)
        }

        const skeletonRepo: IDatabaseGitHubRepository = {
          cloneURL: null,
          htmlURL: null,
          lastPruneDate: null,
          name: match.name,
          ownerID: owner.id,
          parentID: null,
          private: null,
        }

        const id = await this.db.gitHubRepositories.put(skeletonRepo)
        return this.toGitHubRepository({ ...skeletonRepo, id }, owner, null)
      }
    )
  }

  public async setGitHubRepository(repo: Repository, ghRepo: GitHubRepository) {
    // If nothing has changed we can skip writing to the database and (more
    // importantly) avoid telling store consumers that the repo store has
    // changed and just return the repo that was given to us.
    if (isRepositoryWithGitHubRepository(repo)) {
      if (repo.gitHubRepository.hash === ghRepo.hash) {
        return repo
      }
    }

    await this.db.transaction('rw', this.db.repositories, () =>
      this.db.repositories.update(repo.id, { gitHubRepositoryID: ghRepo.dbID })
    )
    this.emitUpdatedRepositories()

    const updatedRepo = new Repository(
      repo.path,
      repo.id,
      ghRepo,
      repo.missing,
      repo.alias,
      repo.workflowPreferences,
      repo.isTutorialRepository,
      repo.gitDir,
      repo.mainWorktreePath
    )

    assertIsRepositoryWithGitHubRepository(updatedRepo)
    return updatedRepo
  }

  private async _upsertGitHubRepository(
    endpoint: string,
    gitHubRepository: IAPIRepository | IAPIFullRepository,
    ignoreParent = false
  ): Promise<GitHubRepository> {
    const parent =
      'parent' in gitHubRepository && gitHubRepository.parent !== undefined
        ? await this._upsertGitHubRepository(
            endpoint,
            gitHubRepository.parent,
            true
          )
        : await Promise.resolve(null) // Dexie gets confused if we return null

    const { login, type } = gitHubRepository.owner
    const owner = await this.putOwner(endpoint, login, type)

    const existingRepo = await this.db.gitHubRepositories
      .where('[ownerID+name]')
      .equals([owner.id, gitHubRepository.name])
      .first()

    // If we can't resolve permissions for the current repository chances are
    // that it's because it's the parent repository of another repository and we
    // ended up here because the "actual" repository is trying to upsert its
    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
