### Title
Unbounded per-authority `txLookup.auths` list with O(n) linear-scan removal enables tx-pool DoS - (File: blockchain/tx_pool.go)

### Summary
`txLookup` maintains a map from EIP-7702 (`TxTypeEthereumSetCode`) authority addresses to a slice of transaction hashes that reference that authority. This slice has no upper bound of its own, and every insertion/removal is an O(n) linear scan under the global `txLookup.lock`, itself nested under `pool.mu`/`pool.txMu`. An attacker who submits many `SetCode` transactions from many distinct (even cheaply reused) sender accounts, all pointing at the same authority address, can grow one `auths[addr]` entry to the size of the whole pool. Every subsequent pool churn event (promote, demote, evict, reorg) that removes one of these transactions then pays an O(n) cost to splice that authority's list, and this happens repeatedly for every remaining member of the list — a quadratic-cost pattern directly analogous to the `activeTransactionBlocks`/`removeUserActiveBlocks` issue in the reference report.

### Finding Description
`txLookup` tracks authorizations per address: [1](#0-0) 

Insertion happens unconditionally for every added transaction that carries `SetCodeAuthorities()`, with no cap on `len(t.auths[addr])`: [2](#0-1) 

Removal does a `slices.Index` scan plus a slice-shift (`append(list[:i], list[i+1:]...)`) — O(n) per call, and this happens on every `txLookup.Remove`, which fires from `pool.removeTx`, `promoteExecutables` drop paths, `demoteUnexecutables`, and the eviction loop — i.e., on essentially every tx-pool state transition, not just when a full transaction is explicitly cancelled: [3](#0-2) 

Unlike `pool.queue`/`pool.pending`, which are capped per-account (`NonExecSlotsAccount`) and globally (`NonExecSlotsAll`), those caps limit the *number of transactions per sender/globally*, not the number of transactions *per referenced authority address*. Because EIP-7702 lets any sender's transaction name an arbitrary authority address, many distinct senders (each individually within the normal per-account/global admission limits) can all set the *same* authority address, concentrating an unbounded number of hash entries into a single `auths[addr]` bucket that is bounded only by the pool's overall global slot limit (which is typically in the thousands, i.e., "large" relative to expected auth-list sizes — the same caveat the original report calls out for `activeTransactionBlocks`).

### Impact Explanation
Every `txLookup.Add`/`Remove` operation is currently assumed cheap (amortized O(1) map operation), but with a large `auths[addr]` bucket engineered by an attacker, each add/remove pays cost proportional to the bucket size. Because these calls occur under the pool's core locks (`txLookup.lock`, and callers hold `pool.mu`/`pool.txMu`), and fire on ordinary pool maintenance (`promoteExecutables`, `demoteUnexecutables`, `removeTx`, the eviction ticker) that runs for *every* transaction in the pool — including transactions unrelated to the attack — this degrades the tx pool's processing throughput for the whole node. Since block building (worker) depends on the tx pool, this is a mempool/pool-admission level DoS reachable by any unprivileged transaction sender able to submit cheap `SetCode` transactions, not merely a localized inefficiency for the attacker's own account.

### Likelihood Explanation
- Reachable purely via ordinary `AddLocal`/`AddRemote` transaction submission — no privileged role needed.
- Requires only that the attacker fund (or reuse) enough sender accounts to submit `SetCode` transactions that all authorize the same target address, staying within existing per-account/global transaction-count admission rules while concentrating all of them on one authority.
- The number of transactions needed to make a bucket "large enough to hurt" scales with `NonExecSlotsAll`/`ExecSlotsAll`, which are non-trivial but attacker-fundable given the analogous report emphasizes this exact bug class (unbounded per-key list + O(n) removal) is exploitable well before hitting any global hard limit.

### Recommendation
- Track each authority's referencing hashes with a set (`map[common.Hash]struct{}`) instead of a slice, giving O(1) add/remove instead of O(n) scan+shift.
- Introduce and enforce an explicit per-authority-address cap (e.g., reject/replace-only-one-pending-tx-per-authority, as most `SetCode`/EIP-7702 tx pool designs do), so a single authority address cannot accumulate more than a small bounded number of pending pooled authorizations regardless of how many distinct senders submit them.

### Proof of Concept
1. Generate `N` funded EOAs (`N` up to `NonExecSlotsAll`).
2. From each EOA, submit one `TxTypeEthereumSetCode` transaction whose authorization list names the same fixed authority address `A` (each transaction individually valid and admissible under existing per-account/global caps).
3. Observe `pool.all.auths[A]` (internal `txLookup.auths`) grow to size `N`.
4. Trigger ordinary pool churn (new block causing `reset`/`demoteUnexecutables`/`promoteExecutables`, or the periodic eviction ticker) that calls `removeTx`/`txLookup.Remove` on members of this set of `N` transactions: each removal now costs O(N) due to `removeAuthorities`'s linear scan and slice-shift, and removing all `N` costs O(N²) — all executed while holding the pool's core locks, stalling admission/promotion of every other user's transactions during that window.

// addAuthorities tracks the supplied tx in relation to each authority it
// specifies.
func (t *txLookup) addAuthorities(tx *types.Transaction) {
	for _, addr := range tx.SetCodeAuthorities() {
		list, ok := t.auths[addr]
		if !ok {
			list = []common.Hash{}
		}
		if slices.Contains(list, tx.Hash()) {
			// Don't add duplicates.
			continue
		}
		t.auths[addr] = append(list, tx.Hash())
	}
}

// removeAuthorities stops tracking the supplied tx in relation to its
// authorities.
func (t *txLookup) removeAuthorities(tx *types.Transaction) {
	hash := tx.Hash()
	for _, addr := range tx.SetCodeAuthorities() {
		list := t.auths[addr]
		// Remove tx from tracker.
		if i := slices.Index(list, hash); i >= 0 {
			list = append(list[:i], list[i+1:]...)
		} else {
			logger.Error("Authority with untracked tx", "addr", addr, "hash", hash)
		}
		if len(list) == 0 {
			// If list is newly empty, delete it entirely.
			delete(t.auths, addr)
			continue
		}
		t.auths[addr] = list
	}
}
