## #Analog Found

### Title
Zero-slippage WOM→mWOM swap in `SmartWomConvert.convert` reachable via `ArbWomUp3.incentiveDeposit` enables sandwich-attack theft of user funds - (File: `wombat/ArbWomUp3.sol`, `wombat/SmartWomConvert.sol`)

### Summary
`ArbWomUp3.incentiveDeposit`, an unprivileged, user-callable function, hard-codes `_minRec = 0` when it forwards part of a user's deposited WOM to `SmartWomConvert.convert` for an on-chain WOM→mWOM swap. Because the minimum-received check is bypassed with a literal `0`, the swap executes without any slippage protection and can be sandwiched, causing the depositing user to receive fewer `mWOM` tokens than the pre-trade market price would dictate — this is the same root cause the report describes for `UniswapHelper.buyFlanAndBurn`.

### Finding Description
Any wallet can call the external, unprivileged function `incentiveDeposit(_amount, _convertRatio, _bullMode, _mode)` and choose `_mode == 2`: [1](#0-0) 

This routes into `_deposit`, where, for `_mode == 2`, half of the deposited WOM is swapped through `SmartWomConvert` with the minimum-received argument hard-coded to `0`: [2](#0-1) 

`SmartWomConvert.convert` simply forwards the caller-controlled `_convertRatio` and the received `_minRec` (here `0`) into `_convertFor`: [3](#0-2) 

Inside `_convertFor`, the buyback portion of the WOM is swapped for `mWOM` through the Wombat router with `amountOut` un-bounded except by the caller-supplied `_minRec`; since that value is `0` here, the post-swap check `convertAmount + amountRec < _minRec` can never revert regardless of how bad the execution price is: [4](#0-3) 

This mirrors the reported bug class exactly: a swap executed with pool-provided output amounts and no effective minimum-price protection, letting a bot front-run the swap (buying `mWOM` to push its price up), let the victim's swap execute at the manipulated rate, then back-run by selling `mWOM` back — extracting value at the depositor's expense.

### Impact Explanation
The mis-priced `mWOM` output from the sandwiched swap is immediately locked into `mWomSV` on the victim's behalf: [5](#0-4) 

Because the resulting tokens are locked (not merely held), the shortfall is not simply a slippage inconvenience recoverable by the user — the user's WOM has already been irrevocably converted into fewer, now-locked `mWOM`/`mWomSV` shares at attacker-manipulated prices. This is a direct, concrete loss of user funds during normal, permissionless usage of a documented protocol entry point, not a governance/oracle/admin issue.

### Likelihood Explanation
`incentiveDeposit` is a normal external user function with no access control; `_convertRatio` and `_mode` are both freely chosen by the caller, so any WOM holder using the advertised incentive/lock flow (`_mode == 2`) triggers the vulnerable zero-slippage path. The size of the exploit is bounded by the depositor's convert amount and pool depth of the WOM/mWOM Wombat pool, but no special privilege or unusual configuration is required to trigger it — only an attacker monitoring the mempool for `incentiveDeposit` calls.

### Recommendation
Do not hard-code `_minRec = 0` in `ArbWomUp3._deposit`. Instead, thread a user-supplied (or oracle/TWAP-derived) minimum acceptable `mWOM` output through `incentiveDeposit` into `IConverter(smartWomConvert).convert(toSwap, _convertRatio, _minRec, _mode)`, and enforce it exactly as `SmartWomConvert._convertFor` already supports via its `_minRec` parameter (which is currently defeated only by the caller passing `0`).

### Proof of Concept
1. Attacker watches mempool for a call to `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` with `_convertRatio < DENOMINATOR` (so a non-zero buyback swap occurs).
2. Attacker front-runs with a WOM→mWOM buy on the same Wombat pool referenced by `womMWomPool`, pushing the mWOM price up.
3. Victim's transaction executes `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` → `_convertFor` → `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` at the now-inflated price, receiving less `mWOM` than fair value, per [6](#0-5) .
4. Attacker back-runs, selling `mWOM` back to the pool, capturing the price difference at the victim's expense; the victim's shortfall is locked into `mWomSV` per [5](#0-4) .
