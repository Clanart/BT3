### Title
Unbounded quadratic Lagrange interpolation in `ThresholdKeys::read` enables denial of service - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t` and `n` values up to `u16::MAX`, then invokes `ThresholdKeys::new`, which calculates the group key using `t` separate Lagrange interpolation factors. Each interpolation factor iterates over all `t` participants, resulting in quadratic CPU consumption from a serialized key approximately two megabytes in size. Repeated submission or parallel processing of these payloads can exhaust CPU capacity available to threshold-key handling.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the supplied byte stream and allows any nonzero `t <= n <= 65535` combination. For `Interpolation::Lagrange`, it then reads exactly `n` verification shares and calls `ThresholdKeys::new`. [1](#0-0) 

`ThresholdKeys::new` constructs the participant set `1..=t` and calls `interpolation_factor` once for every participant in that set. [2](#0-1) 

For Lagrange interpolation, every `interpolation_factor` call scans the complete included participant list and performs field multiplication for each other participant. [3](#0-2) 

Therefore, deserializing a key with `t = n = 65535` performs roughly `65535²` field operations—over 4.2 billion loop iterations—before `ThresholdKeys::read` can return. The required input is only the curve ID, parameters, one secret scalar, and 65,535 encoded points.

### Impact Explanation
An unprivileged party who can submit untrusted bytes to `ThresholdKeys::read` can force the recipient into hours-scale or effectively non-terminating CPU work with a payload of only a few megabytes. Repeating the payload can saturate all workers or threads responsible for importing, restoring, validating, or processing threshold keys. This creates a denial of service affecting unrelated key-generation, signing, recovery, or wallet operations sharing that compute capacity.

The attacker does not need valid distributed key material. Every verification share can encode the same valid group point because the expensive group-key calculation begins before semantic consistency with the secret share is otherwise established. [4](#0-3) 

### Likelihood Explanation
The input is fully public and deterministic: two bytes each control `t`, `n`, and `i`; one byte selects Lagrange interpolation; and the remaining data consists of canonical scalar and point encodings. The maximum participant count is bounded only by `u16`, not by an application-level participant limit or serialized-message limit. [5](#0-4) 

Likelihood depends on an integration exposing `ThresholdKeys::read` to imported state, backups, peer messages, or other attacker-controlled bytes. Wherever that boundary exists, the attack requires no valid threshold share and no successful signature verification.

### Recommendation
- Enforce a protocol-specific maximum `n` and `t` before allocating or decoding verification shares.
- Reject `ThresholdKeys::read` inputs whose `n` exceeds the configured participant limit.
- Avoid recomputing every Lagrange factor independently. Precompute coefficients or calculate group keys with a bounded multiexponentiation.
- Move the resource-limit check before `ThresholdKeys::new`, rather than relying on the generic `u16` representation bounds.
- Add a deserialization regression test asserting that maximum-sized declarations cannot trigger quadratic work.

### Proof of Concept
The following conceptual Rust creates the smallest high-impact Lagrange encoding for a ciphersuite `C`. The generator encoding is repeated for every verification share; the individual points are valid even though the aggregate does not represent a meaningful DKG output.

```rust
use std::io::Cursor;
use ciphersuite::{group::{ff::PrimeField, GroupEncoding}, Ciphersuite};
use frost::ThresholdKeys;

fn malicious_keys<C: Ciphersuite>() -> Vec<u8> {
  let mut bytes = Vec::new();

  // Curve identifier expected by ThresholdKeys::read.
  bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  bytes.extend(C::ID);

  // t = n = u16::MAX, i = 1.
  bytes.extend(u16::MAX.to_le_bytes());
  bytes.extend(u16::MAX.to_le_bytes());
  bytes.extend(1u16.to_le_bytes());

  // Lagrange interpolation.
  bytes.push(1);

  // Secret share: any canonical scalar, including zero.
  bytes.extend(C::F::ZERO.to_repr().as_ref());

  // n valid verification shares, all equal to the generator.
  let point = C::generator().to_bytes();
  for _ in 0 .. u16::MAX {
    bytes.extend(point.as_ref());
  }

  bytes
}

fn trigger<C: Ciphersuite>() {
  let bytes = malicious_keys::<C>();
  let _ = ThresholdKeys::<C>::read(&mut Cursor::new(bytes));
}
```
