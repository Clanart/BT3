## Title
Unsanitized `GitHubRepository.htmlURL` reaches `shell.openExternal` with no scheme validation, breaking the "only https(s) github links are opened" invariant — (File: `app/src/lib/commit-url.ts`)

### Summary
`createCommitURL` builds the "View on GitHub" URL by directly string-interpolating `gitHubRepository.htmlURL` with no scheme or host validation. That value flows unmodified from an API response (`html_url`) through storage and back out to `shell.openExternal` in the main process, which itself performs no scheme allow-listing before calling Electron's `shell.openExternal`.

### Finding Description
`createCommitURL` takes `baseURL = gitHubRepository.htmlURL` and returns `` `${baseURL}/commit/${SHA}` `` (with an optional `#diff-<hash>` suffix) without checking that `baseURL` starts with `https://` or matches an expected host: [1](#0-0) 

`htmlURL` is a plain, unauthenticated string field on the `GitHubRepository` model: [2](#0-1) 

It is populated verbatim from the API's `html_url` field when repositories (or PR base/head repos, fork parents, etc.) are upserted, with no scheme/host validation performed anywhere in the persistence path: [3](#0-2) 

The consumer, `onViewCommitOnGitHub` in `app.tsx`, calls `createCommitURL` and, if non-null, forwards the result straight to `dispatcher.openInBrowser`: [4](#0-3) 

`_openInBrowser` in the app store calls `shell.openExternal(url)` with no validation: [5](#0-4) 

The renderer's `shell.openExternal` is proxied over IPC to the main process's `open-external` handler, which also performs no scheme enforcement — it only conditionally logs when the URL starts with `http://`/`https://`, but calls `shell.openExternal(path)` unconditionally for any string, including `file://`, custom protocol handlers, or other schemes: [6](#0-5) 

By contrast, Desktop does apply protocol validation elsewhere (e.g., `validateURL` used for GitHub Enterprise endpoint entry, which explicitly rejects non-`https:` protocols), showing the app is aware of this class of risk but did not apply the same guard to `htmlURL`-derived open-external calls: [7](#0-6) 

This same unsanitized-`htmlURL` pattern is repeated in other call sites (e.g. `buildCommitUrl`/`buildPullRequestUrl` in the Copilot conflicts summary dialog), confirming this isn't an isolated one-off: [8](#0-7) 

### Impact Explanation
If an attacker controls the API responses returned to Desktop for a given endpoint (e.g., a malicious/compromised GitHub Enterprise Server that the user has added as an account, or a repository/parent/fork object embedded in an API response with an attacker-influenced `html_url`), they can set `html_url` to a non-`http(s)` value such as `file://\\attacker-share\payload` or a custom URI scheme. When the victim right-clicks a commit and selects "View on GitHub", the crafted value is passed unchecked to `shell.openExternal`, which resolves it via the OS shell (e.g., `ShellExecute` on Windows). Depending on OS/handler configuration this can result in opening arbitrary local paths/UNC shares or invoking installed custom-protocol handlers, which is a well-known vector for triggering unintended local file access or code execution outside of any Desktop-controlled sandboxing.

### Likelihood Explanation
Exploitation requires the attacker to control the account endpoint's API responses (e.g., operate/compromise a GHES instance the victim connects to, or otherwise inject a crafted repository/API object that Desktop upserts into `GitHubRepository.htmlURL`). This matches the "git remote/proxy response" and "GitHub API object" attacker models listed as in-scope. It requires the victim to explicitly right-click a commit and choose "View on GitHub" for that repository — a normal, expected user action, not an unnatural step.

### Recommendation
Validate `baseURL`/`htmlURL` before using it to build `commitURL`/`pullRequestUrl`, restricting the scheme to `https:` (and ideally matching the expected endpoint host). Additionally, harden the shared `open-external` IPC handler in `main.ts` to reject/refuse any URL that isn't `http:`/`https:` rather than merely gating the log line on the scheme, ensuring the invariant is enforced centrally regardless of which UI code path calls `openInBrowser`.

### Proof of Concept
1. Add/point a GitHub Enterprise account at an attacker-controlled server responding to the GitHub API-compatible endpoints Desktop uses (`repos/:owner/:name`, PR endpoints, etc.).
2. Have the malicious server return an API repository object whose `html_url` is `file://C:/some/path` (or a registered custom scheme).
3. Clone/open the repository in Desktop so `upsertGitHubRepository` persists this `htmlURL` unmodified: [3](#0-2) 
4. Right-click a commit in History and select "View on GitHub" — `onViewCommitOnGitHub` → `createCommitURL` → `dispatcher.openInBrowser` → `shell.openExternal` chain executes with the attacker-controlled non-`http(s)` string: [9](#0-8) [6](#0-5) 
5. Observe `shell.openExternal` invoked with the crafted scheme instead of an `https://github.com/...` URL.

```typescript
export function createCommitURL(
  gitHubRepository: GitHubRepository,
  SHA: string,
  filePath?: string
): string | null {
  const baseURL = gitHubRepository.htmlURL

  if (baseURL === null) {
    return null
  }

  if (filePath === undefined) {
    return `${baseURL}/commit/${SHA}`
  }

  const fileHash = crypto.createHash('sha256').update(filePath).digest('hex')
  const fileSuffix = '#diff-' + fileHash

  return `${baseURL}/commit/${SHA}${fileSuffix}`
```

```typescript
    const repository = this.getRepository()

      !repository.gitHubRepository

      filePath

      return
    }
```

```typescript
export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
```
