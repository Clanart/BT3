### Title
Copilot conflict resolution write path uses a stale working-directory snapshot, allowing silent overwrite of a user's manual conflict resolution - ([File: app/src/lib/stores/app-store.ts])

### Summary
`AppStore._applyCopilotConflictResolutions` writes AI-generated conflict resolutions to disk. It fetches the current `IRepositoryState` **once** at the top of the function and then iterates `copilotResolutions`, `await`ing filesystem operations (`resolveWithin`, `writeFile`) per file. The "is this file already resolved by the user?" guard is checked against that single, pre-loop snapshot instead of being re-validated immediately before each write. This is structurally the same class of bug as the reported broker.go issue: a set of async operations (writes) execute against shared, mutable state while a concurrent actor (background refresh / user edit / git status change) can mutate that state, and the one guard meant to make the operation safe is evaluated too early to catch the race.

The code comment explicitly acknowledges the threat model this is trying to defend against: *"If the user resolved this file externally... while the result dialog was open, git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work, so skip it."* However, `onDiskFile` is looked up in `state.changesState.workingDirectory.files`, which was fetched **before the loop started** and is never refreshed. Between the moment `state` is captured and the moment each `writeFile` executes, multiple `await` points give the event loop a chance to run other async work that mutates `repositoryStateCache` for the same repository — e.g. `_refreshRepository`, `refreshChangesSection`, the periodic repository indicator refresher (`refreshIndicatorForRepository`), or another invocation of `_startCopilotConflictResolution`/`_applyCopilotConflictResolutions`. None of these paths are blocked or serialized against `_applyCopilotConflictResolutions`; there is no `withIsApplyingCopilotResolutions`-style guard analogous to `withIsCommitting`/`withPushPullFetch` used elsewhere in the same file (compare `app/src/lib/stores/app-store.ts:5364-5391` and `5427-5450`).

The broker.go bug's core defect is: a publish/broadcast loop iterates a shared map while a concurrent shutdown path mutates the same shared state, with no synchronization, and any invariant the code assumes ("subscriber list won't change mid-broadcast") silently breaks. Here, the invariant assumed by the "skip already-resolved files" guard ("the working-directory snapshot reflects the file's status at write time") is broken the same way: the guard is checked against data that can go stale during the very `await`s that make the race possible, and nothing prevents the state from changing underneath the loop.

### Impact Explanation
If the working-directory state is updated between the stale `state` capture and the `writeFile` call (for example because the user manually finished resolving that same conflicted file in an external editor and Desktop's periodic/background refresh already updated `repositoryStateCache`, or because a second Copilot resolution run raced with this one), the stale-snapshot check fails to detect that the file is already resolved and Copilot's stored `resolvedContent` is written anyway — silently overwriting the user's real, correct resolution. Since `resolution.resolvedContent` is derived by an LLM turn that processes the contents of the conflicted files in the repository (attacker-controlled if the conflicting branch/commit came from an untrusted remote or a crafted merge), this is a path by which content ultimately influenced by an attacker-controlled repository can land in files that get `git add`'d and subsequently committed/pushed by the user without their awareness — matching the explicitly allowed "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The race window exists on every call because the guard is unconditionally checked against a snapshot taken once at function entry while several `await` points (path resolution and disk I/O per file, potentially multiple files) elapse before the write. Desktop performs frequent, non-user-driven background refreshes of repository/working-directory state (e.g. `refreshIndicatorForRepository`, focus-triggered `_refreshRepository`), so the state genuinely can change during this window without any deliberate user action, making the trigger condition plausible rather than purely theoretical. That said, I was not able to fully trace whether `refreshChangesSection`/background refreshers can run concurrently with an open "Continue Merge" flow for the *same* repository state slice that includes `workingDirectory.files` for a conflicted path (i.e., whether some other guard elsewhere serializes multi-commit-operation state against background refresh) — this would need to be verified by running/instrumenting the actual application, which is beyond what static code inspection can confirm with certainty.

### Recommendation
- Re-fetch `this.repositoryStateCache.get(repository)` immediately before evaluating the "already resolved" guard for each file inside the loop, rather than relying on the snapshot captured before the loop.
- Serialize `_applyCopilotConflictResolutions` against other mutators of the same conflict/working-directory state (e.g. via a `withIsApplyingCopilotResolutions` guard mirroring `withIsCommitting`/`withPushPullFetch`), and/or take a fresh `git status` right before writing each file instead of trusting cached UI state.
- Consider making the write+stage operation atomic per file (check-then-write with no intervening `await`), or re-verify conflict markers are still present in the on-disk file content immediately before overwriting it.

### Proof of Concept
Not independently executed (no filesystem/terminal access in this environment); the following describes how the race would be exercised:
1. Attacker sets up a repository/branch such that merging it produces conflicts in multiple files, and crafts conflict content that biases the Copilot conflict-resolution model toward a particular output for `fileB` (the “resolvedContent”).
2. Victim runs Copilot conflict resolution over multiple conflicted files (`fileA`, `fileB`, ...) via `_startCopilotConflictResolution`, which succeeds and stores `copilotResolutions`.
3. Victim opens the result dialog, then manually re-resolves `fileB` in an external editor and saves it — a background refresh (e.g. periodic repository indicator refresh or window focus refresh) updates `repositoryStateCache.changesState` to reflect `fileB` as resolved.
4. Victim clicks "Continue Merge", invoking `_applyCopilotConflictResolutions`. Because `state` was captured once at function entry (or refreshed too early relative to step 3, depending on exact timing), the loop's `onDiskFile` check for `fileB` still reflects the old conflicted status and does not skip it, so `writeFile` overwrites the victim's manual fix with the attacker-influenced Copilot content, which then gets `git add`-ed and later committed/pushed.
