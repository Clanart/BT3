## Title
Cross-chain escrow withdrawal reverts (and locks funds) when a `WithdrawalRequest` amount exceeds the tracked `_orders` escrow balance - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` (and its duplicate in `evm/tron/contracts/apps/IntentGatewayV2.sol`) only guards against a *zero* escrow balance before subtracting the requested amount from `_orders[commitment][token]`. It never checks that `amount <= escrowed`. This is the same broken invariant as the external report: a withdrawal that is not first clamped to available balance throws inside the arithmetic, reverting the whole call.

### Finding Description
`_withdraw` decrements escrow per token without bounding the amount to what is actually escrowed: [1](#0-0) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;   // <-- unchecked vs. amount, only checks != 0
```

The equivalent Tron contract path is identical: `if (_orders[body.commitment][token] == 0) revert UnknownOrder(); ... _orders[body.commitment][token] -= amount;` [2](#0-1) 

Because Solidity 0.8 arithmetic reverts on underflow, if `amount > escrowed` the subtraction reverts, exactly mirroring the external report's root cause ("Contract potentially can fail due to throw from another contract while withdrawing an amount of tokens that exceeds available assets").

This function is reached from cross-chain flows that are authenticated as coming from the paired gateway instance but whose `amount` field is derived on the **remote** chain, not recomputed/clamped locally: `onAccept` decodes a `WithdrawalRequest` for `RedeemEscrow`/`RefundEscrow` and calls `withdraw()`/`_withdraw()` directly with the amounts supplied in the incoming message [3](#0-2) . Likewise the same-chain cancel path in `IntrinsicIntents._cancelSameChain` builds `remainingTokens` from the *current* `_orders` balance so it is safe, but the partial-fill path computes `escrowedAmount` proportionally with integer division (`(order.inputs[i].amount * fillAmount) / totalRequired`) — a rounding source that can accumulate and diverge from the actual `_orders` balance across repeated partial fills, so a later full-fill/cancel `_withdraw` call can request an amount larger than what remains escrowed for that token: [4](#0-3) 

For same-chain full/partial fills the reachable end-state is a permanently stuck order: any solver who tries to complete the fill hits a revert instead of receiving escrow, and since `_filled[commitment]` is only set to the beneficiary on success and cleared/never set on revert, the order cannot be finalized by anyone — the user's escrowed input tokens (and any solver-provided beneficiary tokens already sent before the revert-causing state change reverts the whole tx) become unusable. Because the fill loop sends output tokens to the beneficiary via `safeTransferFrom`/native call `before` calling `_withdraw` at the end of `_fillSameChain`, a revert in `_withdraw` unwinds the whole transaction (Solidity txn atomicity), so no unilateral fund loss occurs in this single-call site, but the order becomes permanently unfillable (denial of settlement) since every future fill attempt recomputes the same divergent proportional amount and reverts identically.

### Impact Explanation
This does not create incorrect beneficiary/amount transfers by itself (Solidity 0.8 checked arithmetic prevents silent underflow-based theft), but it produces a hard, unrecoverable order-settlement DoS: once the proportional/rounding drift causes `amount > escrowed` for a given token in a partially-filled order, every subsequent attempt to complete that order (fill, or same-chain cancel across the *same* code path) reverts, permanently locking the user's escrowed funds in the gateway with no path to refund or completion. This matches the bounty's "loss of funds" / "logic attack" class in the intent-settlement custody path, since the gateway is the on-chain fund custodian for order escrow.

### Likelihood Explanation
Triggering it requires only unprivileged, permissionless actions available to any solver: performing a sequence of partial fills on a same-chain order whose `totalRequired`/`fillAmount` ratios don't divide evenly, so that the sum of proportional `escrowedAmount` values (each independently floor-divided) diverges from the token's real residual balance in `_orders`. No relayer, prover, or admin compromise is needed — a solver simply chooses fill amounts (`options.outputs[i].amount`) to produce division remainders across multiple partial fills of the same commitment.

### Recommendation
Clamp the withdrawal amount to the actual escrow balance instead of only checking `escrowed == 0`, mirroring the fix requested in the original report:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
if (amount > escrowed) amount = escrowed;
_orders[body.commitment][token] = escrowed - amount;
```
Apply the same fix to the duplicated logic in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`. Additionally, review the proportional partial-fill accounting in `IntrinsicIntents._fillSameChain` to eliminate rounding drift (e.g., by tracking escrow released cumulatively rather than recomputing proportionally each time) so the final full-fill request is guaranteed to equal the exact residual balance.

### Proof of Concept
Exact confirmation of an exploitable rounding sequence would require exercising `_fillSameChain` with concrete numbers (e.g., `totalRequired = 3`, sequential `solverAmount` fills of `1` each causing `escrowedAmount = (inputAmount * 1) / 3` computed three times, whose sum can differ from `inputAmount` when `inputAmount` isn't divisible by 3) against the deployed `IntentGatewayV2` in a Foundry test such as `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`. This part is not fully verified against the live contract state transitions (only the source-level arithmetic pattern was confirmed by reading `IntrinsicIntents.sol` and `IntentsBase.sol`); a background agent with test-execution access should add a Foundry PoC using multiple partial fills with a non-divisible `totalRequired` to confirm the revert on the final `_withdraw` call.
