Confirmed: `evm/tron/contracts/apps/IntentGatewayV2.sol` has no `fillOrder` function of its own — it only implements `placeOrder`, `cancelOrder`, `onAccept`/`withdraw`, and `onGetResponse`. This confirms `placeOrder` in this file never re-measures the actual token balance received via `IERC20.safeTransferFrom`, unlike the sibling contract `evm/src/apps/IntentGatewayV2.sol`, which explicitly snapshots `balBefore`/`balAfter` for this exact reason.

### Title
Escrow ledger in Tron `IntentGatewayV2.placeOrder` is credited from the declared amount instead of the actual token balance received, allowing internal accounting to exceed real custody - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder`'s non-predispatch escrow path pulls tokens with `safeTransferFrom` but credits `_orders[commitment][token]` using `reducedInputs[i].amount` — a value derived purely from the user-declared `order.inputs[i].amount` minus the protocol fee — without ever checking what the contract's token balance actually increased by. This is the same class of bug as the external report: an off-chain/declared accounting value (vault/escrow balance) is trusted instead of the delta actually observed in custody, so the internal ledger can permanently exceed the real underlying balance.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the non-predispatch token intake branch is: [1](#0-0) 


`reducedInputs[i].amount` is `order.inputs[i].amount - protocolFee`, computed purely from the caller-supplied `order.inputs[i].amount` [2](#0-1) . There is no balance-delta measurement (`balanceOf` before/after `safeTransferFrom`), unlike the parallel EVM contract which explicitly does this for the same reason: [3](#0-2) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

The main EVM contract's own test suite explicitly documents that this measurement exists precisely to keep escrow consistent with actual custody for fee-on-transfer tokens: `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` asserts "Escrow should equal actual received amount, not the user-specified amount" [4](#0-3) . The Tron contract lacks this safeguard entirely for both the non-predispatch path (line 453/457) and effectively also credits from `reducedInputs[i].amount` in the predispatch path (line 435), while only checking `balance < requiredAmount` (an inequality, not equality) before crediting the fee-reduced amount rather than the actually-swept `balance`.

`_orders[commitment][token]` is a shared per-token accounting map, and the token custody in the contract is fungible — it is not partitioned per order. Every `placeOrder` call against any fee-on-transfer or otherwise non-1:1-transfer ERC-20 credits more into `_orders` than the contract's real balance increases by. Because payouts in `withdraw()` transfer exactly the recorded `_orders[...][token]` value to the beneficiary [5](#0-4) , the shortfall is not borne by the depositor who caused it — it is borne by the shared token pool, i.e., by whichever other order happens to be redeemed later and finds insufficient real balance, or by the protocol having promised more in aggregate escrow entries than it holds.

### Impact Explanation
This meets the "stealing or loss of funds" bar in the Hyperbridge impact gate: the escrow ledger for a shared custody token can be inflated beyond the contract's actual balance by any unprivileged user simply placing an order in a fee-on-transfer (or any token whose `transferFrom` delivers less than the nominal amount) ERC-20. Because `_orders` values are summed and paid out per-commitment on `RedeemEscrow`/`RefundEscrow`/`cancelOrder`, later legitimate withdrawals for other orders sharing that token can fail or be shorted once the contract's real balance is exhausted — a direct loss/lock of funds belonging to other users, triggered purely by an ordinary user action, with no relayer, prover, or admin compromise required.

### Likelihood Explanation
High under real-world conditions: many widely-used ERC-20s implement fee-on-transfer, rebasing, or deflationary-burn mechanics (as demonstrated by the project's own `FeeOnTransferToken` test fixture used against the sibling EVM contract). Any user can trigger this simply by using such a token as an order input on the Tron deployment; no special privileges, timing races, or governance actions are needed — only calling the public `placeOrder` entrypoint.

### Recommendation
Mirror the EVM implementation: snapshot `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom` in `placeOrder`, mutate `order.inputs[i].amount` (and thus the fee-reduction/commitment calculation) to the actual measured delta, and credit `_orders[commitment][token]` from that measured value instead of the caller-declared `order.inputs[i].amount`. Apply the same fix to the predispatch sweep branch so `_orders[commitment][token]` is credited from the swept `balance` actually captured by the gateway, not from `reducedInputs[i].amount` derived from the pre-transfer declared amount.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a 1%-fee-on-transfer ERC-20 (e.g., the repo's own `FeeOnTransferToken` fixture at [6](#0-5) ).
2. Attacker approves the gateway for `1000e18` of the FOT token and calls `placeOrder` with `inputs = [{token: FOT, amount: 1000e18}]` and `protocolFeeBps = 0`.
3. Due to the 1% transfer fee, `IERC20(token).safeTransferFrom` at line 453 delivers only `990e18` to the gateway, but line 457 credits `_orders[commitment][FOT] += reducedInputs[0].amount == 1000e18` (since `reducedInputs == order.inputs` when `protocolFeeBps == 0`).
4. The gateway's real FOT balance is now `990e18`, but its ledger claims `1000e18` is redeemable for this commitment alone — an immediate 10e18 shortfall that grows with every additional order using this or any other lossy-transfer token, eventually causing `withdraw()`'s token `.call(transfer(...))` to fail or short-pay for whichever order is redeemed once the shared FOT balance is exhausted, at the expense of other orders' rightful beneficiaries.

```text
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
```
