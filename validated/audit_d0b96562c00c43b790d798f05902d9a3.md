## Finding

The core issue is real, though the exact mechanism differs from the literal "identical non-witness fields, different witness" framing in the question. Investigation shows a more direct and definitely reachable exploit path through the same code.

### Title
Unauthenticated OP_RETURN operator attribution lets any party forge which operator is credited for a payout - ([File: core/src/verifier.rs], [File: core/src/database/verifier.rs], [File: core/src/task/payout_checker.rs])

### Summary
`update_finalized_payouts` in `core/src/verifier.rs` attributes a payout transaction to an operator purely by parsing an unauthenticated OP_RETURN xonly-pubkey out of whichever transaction happens to spend the registered `withdrawal_utxo`, with no cryptographic check that the named operator produced, signed, or funded that transaction. Combined with the withdrawer's payout-authorizing signature being scoped to `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` (enforced in `parse_withdrawal_sig_params`, `core/src/rpc/parser/operator.rs:174-187`), any party holding the withdrawer's `(input_outpoint, input_signature)` pair can build their own payout transaction that spends the same withdrawal UTXO, satisfies the single committed output, and stamps an arbitrary (real) operator's public xonly_pk into the OP_RETURN, thereby causing that operator's `PayoutCheckerTask` to bind a `kickoff_txid`/reimbursement to a payout it never funded.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk (recorded in withdrawals table) == the operator that actually produced/funded/broadcast the payout transaction`.

Trace:
1. `Actor::withdraw`-style flow requires the withdrawer to sign with `TapSighashType::SinglePlusAnyoneCanPay`, enforced at [1](#0-0)  This sighash flag commits only to the withdrawal input's outpoint/amount/scriptPubkey and the single output at the same index — it explicitly does **not** commit to any other input or output, including the OP_RETURN output that names the fronting operator, as built in [2](#0-1) 
2. `update_finalized_payouts` scans blocks for whichever transaction spends the registered `withdrawal_utxo_txid`/`vout` (via `get_payout_txs_for_withdrawal_utxos`, [3](#0-2) ) and parses the operator xonly_pk straight out of the OP_RETURN bytes with **no signature or authenticity check** on that field: [4](#0-3) 
3. `PayoutCheckerTask::run_once` polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered by the operator's own pubkey, then calls `handle_finalized_payout` and `mark_payout_handled`, binding a fresh `kickoff_txid` to the discovered `payout_txid`: [5](#0-4) 
4. `Operator::handle_finalized_payout` never re-verifies that the operator itself actually produced/broadcast that specific `payout_txid` — it only looks up an unused kickoff connector and signs a new kickoff for this deposit: [6](#0-5) 
5. `get_handled_payout_kickoff_txid` then trustingly returns this `kickoff_txid` as reimbursable for that `payout_txid`: [7](#0-6) 

Exploit: an unprivileged attacker (who can be, or can simply observe, the withdrawer calling `withdraw` on the Citrea Bridge contract per the threat model) obtains the public `(input_outpoint, input_signature)` pair for a pending withdrawal. Because the signature only binds input+matching output, the attacker constructs their **own** transaction spending that same `withdrawal_utxo`, adding their own fee-funding inputs and an OP_RETURN containing a real, already-known operator's xonly_pk, and races it into a block before that operator (or anyone else) broadcasts the "real" payout. `update_finalized_payouts` records this attacker-built tx as `payout_payer_operator_xonly_pk = <victim operator>`, and that operator's own `PayoutCheckerTask` automatically binds a kickoff and proceeds to claim reimbursement for a payout it never made.

Existing guards fail because: `Verifier::is_deposit_valid` and the storage-proof/SPV checks in `circuits-lib/src/bridge_circuit/mod.rs` only verify that *some* payout transaction correctly spends the committed withdrawal outpoint into the committed user output — they never re-check who is credited as the operator (that attribution is a purely off-circuit, unauthenticated DB heuristic based on OP_RETURN bytes).

### Impact Explanation
The named operator's kickoff/reimburse chain proceeds and pays out bridge collateral (`Reimburse` transaction) to that operator for a payout transaction it never funded — matching the explicit Critical category "an operator reimbursed for a payout it never funded." This is repeatable for any withdrawal for which the attacker can observe/derive `(input_outpoint, input_signature)`, against any operator whose xonly_pk is public knowledge, and does not require compromising any key, majority hashrate, or verifier collusion.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only to see a pending Citrea withdrawal's `(input_outpoint, input_signature, output_script_pubkey, output_amount)` — data that is either publicly committed on Citrea or directly known if the attacker is the withdrawer — and to win a race to get their own funding transaction mined first (fees only, no special access). This requires no verifier/operator privilege, no TLS interception, and no protocol collusion, making it fully within the unprivileged attacker's declared capabilities.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically — e.g., require the operator to co-sign or otherwise authenticate the payout transaction (or its OP_RETURN commitment) with a key/signature that only the legitimate fronting operator can produce, and have `update_finalized_payouts`/`get_first_unhandled_payout_by_operator_xonly_pk` verify that signature before crediting a payout to an operator, rather than trusting raw OP_RETURN bytes.

Plan:
1. Set up a deposit and a Citrea-registered withdrawal (`withdrawal_utxo`, `input_signature` with `SinglePlusAnyoneCanPay`) as in existing e2e helpers (`core/src/test/common/setup_utils.rs::generate_withdrawal_transaction_and_signature`).
2. As the "attacker" (not the target operator), construct a transaction spending `withdrawal_utxo` with the same committed output at index 0, but with attacker-funded extra inputs/change and an OP_RETURN containing the target (victim) operator's real xonly_pk, and broadcast it before the operator sends its own payout tx.
3. Mine to finality and run the verifier's block-sync task (invoking `update_finalized_payouts`).
4. Assert `db.get_payout_info_from_move_txid(...)` returns `payout_payer_operator_xonly_pk == victim_operator_xonly_pk` for this attacker-built `payout_txid`.
5. Run the victim operator's `PayoutCheckerTask::run_once` and assert `db.get_handled_payout_kickoff_txid(None, attacker_payout_txid)` returns `Some(kickoff_txid)`, proving the victim operator's kickoff was bound to a payout it never funded — with no check anywhere that `attacker_payout_txid`'s value actually reached the withdrawer via the victim operator's own funds.

    pub async fn handle_finalized_payout<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        deposit_outpoint: OutPoint,
        payout_tx_blockhash: BlockHash,
    ) -> Result<bitcoin::Txid, BridgeError> {
        let (deposit_id, deposit_data) = self
            .db
            .get_deposit_data(Some(dbtx), deposit_outpoint)
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        // get unused kickoff connector
        let (round_idx, kickoff_idx) = self
            .db
            .get_unused_and_signed_kickoff_connector(
                Some(dbtx),
                deposit_id,
                self.signer.xonly_public_key,
            )
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(
            "Operator: Current round index: {}, round idx for kickoff: {}",
            current_round_index,
            round_idx
        );
        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first
            // if current_round_index should only be smaller than round_idx, and should not be smaller by more than 1
            // so sanity check:
            if current_round_index.next_round() != round_idx {
                return Err(eyre::eyre!(
                    "Internal error: Expected the current round ({:?}) to be equal to or 1 less than the round of the first available kickoff for deposit reimbursement ({:?}) for deposit {:?}. If the round is less than the current round, there is an issue with the logic of the fn that gets the first available kickoff. If the round is greater, that means the next round do not have any kickoff connectors available for reimbursement, which should not be possible.",
                    current_round_index, round_idx, deposit_outpoint
                ).into());
            }
            tracing::info!(
                "Operator: Starting next round to be able to get reimbursement for the payout"
            );
            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;
        }

        // get signed txs,
        let kickoff_data = KickoffData {
            operator_xonly_pk: self.signer.xonly_public_key,
            round_idx,
            kickoff_idx,
        };
