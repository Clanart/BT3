### Title
Missing chainId/replay-domain binding in the aggregator's EIP-712 withdrawal-verification signature - (File: `core/src/rpc/ecdsa_verification_sig.rs`)

### Summary
The `CLEMENTINE_EIP712_DOMAIN` used to authorize optimistic-payout and operator-withdrawal requests only sets `name` and `version`, omitting `chainId` (and `verifyingContract`), so the same aggregator-signed authorization is valid across any deployment that shares the aggregator's verification key and struct schema.

### Finding Description
`recover_address_from_ecdsa_signature` recovers the signer address from an EIP-712 prehash computed with a hard-coded, environment-agnostic domain: [1](#0-0) 
This domain is used both when the aggregator signs the withdrawal parameters (`sign_withdrawal_verification_signature`) and when the verifier checks that signature before signing an optimistic payout (`sign_optimistic_payout`): [2](#0-1) [3](#0-2) 
Because the domain carries no `chainId` (or other network/deployment discriminator), the hash committed to by the aggregator's signature is identical for any Clementine instance built with the same `ClementineVerification`/`v1` domain — e.g. a testnet deployment and a mainnet deployment, or two independently operated bridge instances sharing the same aggregator verification keypair. The only per-request binding is `deposit_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, and `output_amount` — none of which encode which network/deployment the signature was intended for.

### Impact Explanation
If two Clementine deployments (e.g. staging/testnet vs. production, or two independently configured bridge networks) are configured with the same `aggregator_verification_address`/secret key, a verification signature produced for a withdrawal on one deployment can be replayed to satisfy the `verification_signature` check on the other deployment for a colliding `deposit_id`/outpoint/output combination, since `verifier.rs::sign_optimistic_payout` only compares the recovered address to `config.aggregator_verification_address` and never binds the signature to the specific deployment or chain. This bypasses the intended "must be authorized by this network's aggregator" gate on optimistic payouts, which is exactly the analog of the reported cross-chain replay class (EIP-712 domain without `chainId`). That said, exploiting it requires an actual cross-deployment key/config collision (shared aggregator verification key across two live bridge instances) and matching withdrawal parameters, which the repository's documented configuration guidance would normally avoid — the vulnerability is a real soundness gap in the signature scheme rather than a currently demonstrated concrete-funds-loss path within a single well-configured deployment.

### Likelihood Explanation
Low-to-medium: it requires operators to reuse the same aggregator verification keypair across multiple Clementine networks/environments, which is a deployment/configuration matter, but the domain separator itself provides no cryptographic protection against that scenario — the code offers no chainId binding to prevent it even if all other configuration is correct.

### Recommendation
Include a chain/network identifier (and ideally `verifyingContract` or an explicit network tag) in `CLEMENTINE_EIP712_DOMAIN`, e.g. populate the `chain_id` field of `eip712_domain!` from `protocol_paramset.network` or a dedicated deployment identifier, so that signatures produced for one Clementine network cannot be replayed on another sharing the same aggregator key.

### Proof of Concept
1. Configure two Clementine deployments, A and B, both with `aggregator_verification_address` pointing at the same key.
2. Aggregator signs an `OptimisticPayoutMessage` for deployment A's withdrawal (`deposit_id`, `input_outpoint`, `output_script_pubkey`, `output_amount`).
3. Because `CLEMENTINE_EIP712_DOMAIN` has no chainId, the identical signature verifies successfully in deployment B's `sign_optimistic_payout` if B ever processes a withdrawal with matching parameters (or if B's verifiers are given the message post-hoc), bypassing the intended per-deployment authorization boundary. pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
