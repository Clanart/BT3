### Title
Unvalidated Check-Run `htmlUrl` from GitHub API Reaches `shell.openExternal` Without Scheme Restriction - (File: app/src/ui/check-runs/ci-check-run-popover.tsx)

### Summary
`CICheckRunPopover.onViewCheckDetails` and `onViewJobStep` take the `htmlUrl` field of an `IRefCheck` object — populated from the GitHub Checks/Statuses API, which can be set by any third-party CI/App integration (or a malicious fork's workflow run) — and pass it directly to `Dispatcher.openInBrowser`, which calls `shell.openExternal` with zero scheme/host validation. This mirrors the reported bug class: a powerful, unrestricted primitive (`delegatecall`/`shell.openExternal`) invoked with attacker-influenced input instead of being restricted to trusted, predefined values.

### Finding Description
`onViewCheckDetails` builds `url` from `checkRun.htmlUrl` (falling back to a same-origin PR URL only when `htmlUrl` is `null`) and calls `this.props.dispatcher.openInBrowser(url)`: [5](#0-4) 
`onViewJobStep` does the same via `getCheckRunStepURL`: [6](#0-5) 

`Dispatcher.openInBrowser` forwards straight to `AppStore._openInBrowser`, which is a thin wrapper over `shell.openExternal`: [2](#0-1) 

The renderer-side `shell` object proxies to the main process via `main-process-proxy.ts`'s `openExternal`, which is served by the `open-external` IPC handler. That handler performs **no scheme allow-listing** — it only *logs* when the value starts with `http(s)://`, and unconditionally calls Electron's `shell.openExternal(path)` for anything else: [3](#0-2) 

This is a materially weaker guard than the one the app already applies elsewhere for exactly this class of risk — the sandboxed-markdown link interceptor explicitly requires `/^https?:/` on the anchor's parsed `protocol` before it will even invoke `onMarkdownLinkClicked` (which itself forwards to `openInBrowser`): [4](#0-3) 

No equivalent check exists on the check-run/job-step code path, so any non-`http(s)` scheme (e.g. `file://`, a registered custom URI handler, or on Windows a bare executable/UNC path that `shell.openExternal` will hand to the OS shell to execute) supplied as a check run's `details_url`/`html_url` reaches `shell.openExternal` unmodified.

### Impact Explanation
Electron's `shell.openExternal` is a well-known dangerous sink when given attacker-controlled, non-`http(s)` values: depending on OS, it can invoke arbitrary registered protocol handlers, open local files directly (potential code execution for executable file types on Windows), or trigger UNC-path/NTLM-hash leakage. Since check runs are populated by third-party GitHub App/CI integrations tied to a repository (including forks contributing PRs), an attacker who controls or compromises a CI integration — or crafts a PR that a permissive Action reports a check run for — can set `details_url` to a malicious value that a victim then "clicks" in the Checks popover, achieving code execution, file access, or credential leakage outside the sandboxed renderer, consistent with the report's "unprivileged, attacker-controlled data reaching a powerful trusted primitive" pattern.

### Likelihood Explanation
The check-run popover is reachable via normal use (viewing PR check statuses), requires only a single click on "View check details" or a job step, and requires no local access, admin rights, or pre-existing compromise — only the ability to make a repository display a check run with an attacker-chosen `html_url`/`target_url`, which is within the capability of any GitHub App/CI integration or third-party status provider associated with the repo (including on forks). This is a plausible, low-effort path, though it does depend on the victim clicking the link.

### Recommendation
Apply the same `https?:` scheme validation used in `sandboxed-markdown.tsx`'s `setupLinkInterceptor` to every value passed to `Dispatcher.openInBrowser`/`shell.openExternal`, ideally centralized inside `_openInBrowser` (or the `open-external` IPC handler in `main.ts`) rather than duplicated per call site, so that any current or future caller (check runs, job steps, PR badges, etc.) is protected by construction instead of relying on each UI component to remember to validate.

### Proof of Concept
1. Configure (or compromise) a GitHub App/CI integration that posts a Check Run to a repository/PR, setting `details_url` (surfaced as `IRefCheck.htmlUrl`) to a malicious value, e.g. `file:///C:/Windows/System32/calc.exe` or a custom-registered URI scheme payload instead of an `https://` URL.
2. Victim opens the PR in GitHub Desktop and opens the Checks popover (`CICheckRunPopover`).
3. Victim clicks "View check details" (or a failing job step), invoking `onViewCheckDetails`/`onViewJobStep`. [1](#0-0) 
4. `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` → `shell.openExternal(url)` is invoked with the unvalidated URL, with no `https?:` gate as exists in the markdown path. [2](#0-1) [3](#0-2) 
5. Electron/OS handles the non-http(s) URI according to its registered handler/shell semantics, potentially executing code or leaking data outside the app's sandbox.
