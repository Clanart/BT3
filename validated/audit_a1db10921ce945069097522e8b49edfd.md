## Finding

Uncontrolled Python-level recursion in the wallet's outer-puzzle driver dispatch (`chia/wallet/outer_puzzles.py` and its `match`/`get_inner_puzzle`/`get_inner_solution` implementations in `cat_outer_puzzle.py`, `ownership_outer_puzzle.py`, `metadata_outer_puzzle.py`, `cr_outer_puzzle.py`, `singleton_outer_puzzle.py`) allows an untrusted offer/spend-bundle puzzle reveal to drive unbounded Python call-stack recursion, crashing the wallet process (DoS), analogous to the uncontrolled-recursion class in CVE-2021-46195.

### Title
Uncontrolled recursion in wallet outer-puzzle driver dispatch via attacker-crafted nested asset layers - (File: chia/wallet/outer_puzzles.py)

### Summary
The wallet's asset-driver framework (`match_puzzle`, `get_inner_puzzle`, `get_inner_solution`, `construct_puzzle`) recurses once per "outer puzzle" layer detected in a puzzle reveal, with no depth limit, when processing puzzle reveals that originate from an untrusted counterparty (e.g. an `Offer`/`SpendBundle` that a wallet user loads and parses).

### Finding Description
`match_puzzle()` dispatches to each `*OuterPuzzle.match()` implementation (CAT, ownership, metadata, singleton, CR): [1](#0-0) 

Each driver's `match`, `get_inner_puzzle`, and `get_inner_solution` methods recurse into `self._match`/`self._get_inner_puzzle`/`self._get_inner_solution` (which are bound to the same top-level `match_puzzle`/`get_inner_puzzle`/`get_inner_solution` functions) whenever the puzzle is wrapped in another recognized outer layer (e.g. CAT-inside-CAT), with no cap on nesting depth: [2](#0-1) [3](#0-2) [4](#0-3) 

This is directly reachable with **attacker-controlled data**: the standard test fixture already demonstrates that a puzzle reveal can legally curry an asset layer around another instance of itself (CAT-in-CAT): [5](#0-4) 

An `Offer` built from an untrusted `SpendBundle` calls `match_puzzle()` directly on each coin spend's `puzzle_reveal` when computing offered coins, with no bound on how many nested layers are inspected: [6](#0-5) 

Because `curry()`/`uncurry()` only add a small, fixed byte overhead per layer (a few dozen bytes), a malicious offer author can nest thousands of CAT/ownership/metadata layers inside a single coin's puzzle reveal while staying well within normal spend-bundle size limits. Unlike CLVM execution (which is metered by cost and therefore self-limiting), this Python-side layer walk is **not CLVM-cost-metered at all** — it is pure Python recursion performed before/independently of any `run_with_cost()` call, so Chia's normal mempool cost limits do not protect against it.

### Impact Explanation
When the victim wallet parses such an offer (e.g. via `Offer.from_bytes`/`from_spend_bundle` → `_get_offered_coins` → `match_puzzle`, or via `TradeManager` offer-taking flows that call the same driver functions), the unbounded Python recursion exceeds the interpreter's recursion limit and raises `RecursionError`, or in constrained environments exhausts the C stack, crashing or hanging the wallet process. This is a spend/offer-triggered transaction-processing halt — a legitimate wallet user or offer counterparty can be denied service simply by receiving/loading a malicious offer file, matching the CVE's "excessive CPU/memory consumption via uncontrolled recursion" bug class.

### Likelihood Explanation
High for any wallet user who inspects or accepts offers from untrusted counterparties (a normal, expected wallet workflow) — the attacker needs only to construct one coin spend whose puzzle reveal nests thousands of curried outer-puzzle layers, which is straightforward using the same `construct_cat_puzzle`/`curry` APIs already exercised in test code.

### Recommendation
Impose a maximum recursion/nesting depth (or convert `match_puzzle`/`get_inner_puzzle`/`get_inner_solution`/`construct_puzzle` recursion to an iterative loop with an explicit depth cap) before processing untrusted puzzle reveals in `Offer` and related trade-manager code paths, and reject offers/spend bundles whose puzzle reveals exceed that depth.

### Proof of Concept
Construct a coin spend whose `puzzle_reveal` is `construct_cat_puzzle(CAT_MOD, tail, construct_cat_puzzle(CAT_MOD, tail, construct_cat_puzzle(CAT_MOD, tail, ...)))` nested N (~5,000+) times, as shown structurally by the existing double-nesting test: [7](#0-6) 
Package it into a `SpendBundle`/`Offer` and have a victim wallet call `Offer.from_spend_bundle()` or otherwise invoke `match_puzzle()`/`get_inner_puzzle()` on it, triggering `RecursionError`/stack exhaustion.

def test_cat_outer_puzzle() -> None:

    cat_driver: PuzzleInfo | None = match_puzzle(uncurried_cat_puzzle)

    assert cat_driver.type() == "CAT"
    assert cat_driver["tail"] == tail

    assert inside_cat_driver["tail"] == tail
