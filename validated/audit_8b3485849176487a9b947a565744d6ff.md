## Finding

### Title
Reward claim for a hyperbridge-originated request becomes permanently unclaimable if the request times out before the delivery claim lands - ([File: modules/pallets/relayer/src/outbound_request.rs])

### Summary
The reported bug class is: a request/state-update that is fired near the end of a time-bounded window can complete *after* the window closes, and the finalize call then reverts because the on-chain check is bound to a state (round/phase) that has already moved on — permanently losing the value that was staked to make the request. The local analog is the `OutboundRequestDeliveryReward` claim pipeline in `pallet-relayer`: it gates the reward payout on the *existence* of the request's commitment in `pallet_ismp`'s `RequestCommitments` map, but that same commitment is unconditionally deleted the moment the ISMP timeout handler processes a timeout for the request — even if the request was, in fact, delivered to the destination just before the timeout was processed.

### Finding Description
`process_outbound_request_delivery_claim` requires: [1](#0-0) 

i.e. the commitment must still be present in `pallet_ismp::child_trie::RequestCommitments` and must not already be claimed. This is stated explicitly as a hard gate in the design doc: [2](#0-1) 

Separately, the core ISMP timeout handler unconditionally deletes the request commitment as soon as a valid timeout proof (non-membership on destination + elapsed `timeout_timestamp`) is submitted, regardless of whether the message was actually delivered and executed on the destination chain in the interim: [3](#0-2) [4](#0-3) 

There is no cross-check between the two paths: `handle_timeouts` only verifies a *non-membership* proof at the height it uses, and does not consult whether a later delivery (with a receipt proven at a higher/newer destination height) has since landed. If a relayer legitimately delivers a hyperbridge-originated system request (host-executive, intents-coprocessor, token-governor, or the relayer pallet's own withdrawal message — all of which are eligible for `OutboundRequestDeliveryReward`) close to its `timeout_timestamp`, and *anyone* (a different relayer, or the same one) submits the ISMP timeout message for that same request before the `claim_outbound_request_delivery_reward` extrinsic lands, `RequestCommitments::get(commitment)` will return `None` thereafter. Any subsequent (and honestly-proven) delivery-reward claim for that request permanently fails with `OutboundRequestNotKnown`, and there is no alternate path to recover the reward — the destination-side execution already happened (the module's `onAccept`/`on_accept` ran), but the source-side incentive for having delivered it is gone forever, because the *only* on-chain trace the claim pipeline consults (`RequestCommitments`) has been erased by an unrelated cleanup path.

### Impact Explanation
This falls squarely under the bounty's "reward claims" impact bucket: a rightful beneficiary (the relayer that actually delivered the message) is permanently denied a reward it earned, with the treasury-side payout path (`OutboundRequestDeliveryReward` → treasury transfer in `process_outbound_request_delivery_claim`) becoming forever unreachable for that commitment once the timeout handler runs first. Because delivery and timeout-cleanup are two independent, permissionless, asynchronous flows racing against the same expiry boundary (exactly the invariant broken in the seed report), this is a genuine loss-of-funds/lock condition rather than a griefing-only issue — the reward amount stays locked in the treasury for that commitment with no way to release it to the actual deliverer.

### Likelihood Explanation
Both paths are permissionless and unsigned/spam-protected only by `validate_unsigned` — anyone can submit the ISMP timeout message for a hyperbridge-originated system request as soon as its `timeout_timestamp` and challenge period have elapsed, and anyone can independently submit the delivery-reward claim. Under normal network delay or during periods of chain congestion (the same "high-demand / slow validators" scenario flagged in the seed report), a request delivered right before its timeout boundary races against a timeout-cleanup transaction submitted immediately after the boundary. Given system requests (host-executive, intents-coprocessor, relayer withdrawal) are dispatched with a real `timeout_timestamp` (confirmed present in `modules/pallets/host-executive/src/lib.rs` and `modules/pallets/relayer/src/withdrawal.rs`), this race is not a purely theoretical edge case but a structural gap in the reward pipeline's invariants — it doesn't require a malicious relayer, prover, or governance actor, only ordinary network timing.

### Recommendation
Do not gate `OutboundRequestDeliveryReward` payout solely on `RequestCommitments` presence. Instead:
- Before the ISMP timeout handler deletes a request commitment for a module that is on the `OutboundRequestDeliveryReward` allowlist, check whether a receipt already exists at the destination (or defer/soft-delete the commitment into a claimable-but-timed-out record) so a legitimate delivery claim can still be honored.
- Alternatively, record claim eligibility (commitment → module_id/reward) in a separate, append-only map that is populated at dispatch time and is *not* touched by the timeout-cleanup path, so the reward-claim pipeline no longer depends on `RequestCommitments` still being present.

### Proof of Concept
1. `pallet-host-executive` (or `pallet-relayer`'s withdrawal path) dispatches a `PostRequest` with a non-zero `timeout_timestamp` via `IsmpDispatcher::dispatch_request`, which is inserted into `pallet_ismp::child_trie::RequestCommitments`.
2. A relayer delivers the request to the destination chain just before `timeout_timestamp` elapses; `RequestReceipts[commitment]` is now set on the destination.
3. Because of network/finality delay, the relayer's `claim_outbound_request_delivery_reward` extrinsic (which needs to wait for the destination state commitment to land on Hyperbridge, per `docs/outbound-request-incentivization.md` lines 181-193) has not yet been submitted.
4. Meanwhile, any actor submits a valid `TimeoutMessage::Post` with a non-membership proof taken at an earlier destination height (before the receipt was written) — this passes `handlers/timeout.rs`'s checks and calls `host.delete_request_commitment(&request)`, removing the commitment from `RequestCommitments`.
5. The relayer's later, legitimate `claim_outbound_request_delivery_reward` call now fails at `RequestCommitments::<T>::get(commitment).is_some()` with `Error::OutboundRequestNotKnown`, permanently forfeiting the reward despite valid on-chain proof of delivery.

```markdown
### Verification pipeline

`process_outbound_request_delivery_claim` runs these checks in order. Ordering is deliberate: every cheap rejection happens before the state-proof verification, so non-allowlisted claims and replays are dropped without ever touching the trie verifier.

1. **Hash the request.** `commitment = hash_request::<IsmpHost>(&Request::Post(request))`. The relayer never gets to pick the commitment.

2. **Source check.** `request.source` must equal `IsmpHost::host_state_machine()`. Rejects forged claims for requests that didn't originate on this hyperbridge instance.

3. **Local presence check.** `pallet_ismp::child_trie::RequestCommitments::get(commitment).is_some()`. Defence in depth on top of the source check: the dispatcher already enforces source on insert, so anything missing from the trie was never dispatched here.

4. **Idempotency.** Reject if `OutboundRequestsClaimed[commitment]` is set.
```
