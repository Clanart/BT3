### Title
`AuctionEntryPoint` owner can unilaterally rug bidder deposits by redirecting `depositVault`/`auctioneer` (KIP-249) - (File: `kaiax/auction/impl/execution.go`, `contracts/bindings/auction/Kip249.go`)

### Summary
The KIP-249 `AuctionEntryPoint` contract exposes owner-gated `changeAuctioneer(address)` and `changeDepositVault(address)` functions that can be called at any time to swap the addresses the whole auction subsystem trusts, with no timelock, delay, or notice to searchers who already have deposits locked in the current `depositVault`. This is structurally identical to the reported `Vault.changeController()` rug: an admin flips a single trusted address and every subsequent value-moving operation (bid settlement, deposit accounting) is redirected to an address the admin controls.

### Finding Description
`IAuctionEntryPoint` defines `changeAuctioneer` and `changeDepositVault` as plain mutator functions returning no access proof beyond the underlying `onlyOwner`-style gate implemented in the (off-repo) system contract implementation; the interface/bindings expose them as ordinary transactions any authorized caller can send at will [1](#0-0) , and likewise `changeDepositVault` [2](#0-1) .

The Kaia client itself never validates or restricts these changes — every block it simply re-reads whatever `auctioneer` and `AuctionEntryPoint` address are currently registered and trusts them going forward: [3](#0-2)  reads `system.ReadAuctioneer` from the (potentially just-changed) entry point with no continuity check against the previous value, and the module's own README documents that a change simply clears in-flight bids rather than blocking or delaying the switch: [4](#0-3) .

Searcher deposits/balances are tracked and retrievable through `getNoncesAndDeposits`, which is scoped to whatever `depositVault`/entry point is currently active [5](#0-4) . If the entry point owner calls `changeDepositVault` to point at a vault contract they control, or `changeAuctioneer` to point at an auctioneer key they control, they can immediately begin approving self-serving winning bids or divert accounting/settlement of already-deposited searcher funds — exactly the "admin flips one address, then drains everything already deposited under the old trust assumption" pattern flagged in the original Vault report.

### Impact Explanation
Searchers who have already locked KAIA as bid deposits with the `AuctionEntryPoint`/`depositVault` have no on-chain guarantee that address will remain the same. A malicious or compromised owner can redirect `depositVault`/`auctioneer` in a single transaction and then, acting as the new auctioneer, sign auction transactions that route bid funds/proceeds to themselves, or point the deposit accounting to a vault they control — resulting in unauthorized value movement/theft of searcher deposits. This matches the Medium-severity "rug via unilateral controller change" bug class.

### Likelihood Explanation
The change requires only a normal transaction from whichever key currently holds owner/admin rights over the `AuctionEntryPoint` — no consensus, no delay, no notification to depositors, and the client-side auction module (`kaiax/auction`) blindly re-reads and trusts the new value on the very next block, so the "attack" surface is a single, always-reachable state-changing call.

### Recommendation
Do not allow `changeAuctioneer`/`changeDepositVault` to take effect for markets/deposits that already exist under the old address. Introduce a timelock/delay before the new address becomes active, require depositors' funds to be withdrawable or migrated before the switch, or restrict changes to when there are zero outstanding deposits, mirroring the code423n4 recommendation of moving such control into a controlled factory/governance flow instead of an instantaneous unilateral admin call.

### Proof of Concept
1. Searchers deposit KAIA into the current `depositVault` associated with `AuctionEntryPoint`, tracked via `getNoncesAndDeposits` [5](#0-4) .
2. The `AuctionEntryPoint` owner calls `changeDepositVault(maliciousVault)` and/or `changeAuctioneer(maliciousAuctioneer)` [6](#0-5) .
3. On the very next block, `kaiax/auction`'s `updateAuctionInfo` re-reads and trusts the new auctioneer/entry-point state with no validation against prior values [7](#0-6) .
4. The malicious auctioneer now signs "winning" auction bids that are honored by the client, and/or the new deposit vault is used for settlement — enabling theft/misdirection of searcher funds that were locked in good faith under the previous configuration.

// updateAuctionInfo updates the auctioneer address and auction entry point address for the given block number.
// It expects the `num` is after Randao fork.
// It returns true if the non-zero auctioneer address and auction entry point address are set, otherwise false.
func (a *AuctionModule) updateAuctionInfo(num *big.Int) bool {
	auctioneer := common.Address{}
	auctionEntryPointAddr := common.Address{}
	auctionEntryPointVersion := ""
	bidTxGasBuffer := uint64(0)

	defer func() {
		a.bidPool.updateAuctionInfo(auctioneer, auctionEntryPointAddr, auctionEntryPointVersion, bidTxGasBuffer)
	}()

	header := a.Chain.GetHeaderByNumber(num.Uint64())
	if header == nil {
		return false
	}
	_, err := a.Chain.StateAt(header.Root)
	if err != nil {
		return false
	}

	backend := backends.NewBlockchainContractBackend(a.Chain, nil, nil)

	// 1. Read auction entry point address
	auctionEntryPointAddr, err = system.ReadActiveAddressFromRegistry(backend, system.AuctionEntryPointName, num)
	if err != nil {
		return false
	}

	if auctionEntryPointAddr == (common.Address{}) {
		return false
	}

	// 2. Read auctioneer address
	auctioneer, err = system.ReadAuctioneer(backend, auctionEntryPointAddr, num)
	if err != nil {
		return false
	}

	if auctioneer == (common.Address{}) {
		return false
	}
