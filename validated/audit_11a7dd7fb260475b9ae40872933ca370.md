### Title
Distribution precompile `rewards()` view accepts msg.value with no non-payable guard, permanently stranding funds - ([File: precompiles/distribution/distribution.go])

### Summary
The Distribution precompile (`0x0000000000000000000000000000000000001007`) dispatches every view method except `rewards(address)` through a `ValidateNonPayable` check that rejects (reverts) calls carrying `msg.value`. `rewards()` is missing this guard, so an EVM caller can attach non-zero `value` to a `rewards(address)` call and have it succeed. The `usei`/`wei` value is transferred by the EVM's native value-transfer mechanism into the precompile's associated Sei account balance before `Execute` even runs, but because the call succeeds (rather than reverting), that value is never refunded and the precompile exposes no function to withdraw it back out. This is the exact bug class from the external report: a payable entry point that can receive more/arbitrary value than intended, with no mechanism to reclaim the surplus from the contract's balance.

### Finding Description
In `Execute`, all mutating/view methods that should reject value do so via `pcommon.ValidateNonPayable(value)`, e.g. `WithdrawValidatorCommissionMethod`: [1](#0-0) 

But `RewardsMethod` is dispatched directly with no such check: [2](#0-1) 

The `rewards` implementation itself never inspects or refunds `value` at all — it takes only `(ctx, method, args)`, not `value`: [3](#0-2) 

This omission is consistent across essentially every historical version of the precompile (`legacy/v580` through `legacy/v67`, and the current `distribution.go`), all of which define `rewards(ctx, method, args)` without a `value` parameter or non-payable validation, while other stateful entry points do call `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` (which explicitly refunds the payer) or `ValidateNonPayable` (which reverts, and thus rolls back the EVM value transfer via the journal). The project's own integration-test suite documents this exact quirk: [4](#0-3) 

Contrast with every other precompile pattern (bank `sendNative`, staking `delegate`, wasmd `execute`/`instantiate`) which either explicitly refunds the exact payer amount via `HandlePaymentUsei`/`HandlePaymentUseiWei` before debiting it again for the intended operation, e.g.: [5](#0-4) 
or reject payable calls outright with `ValidateNonPayable`, whose revert unwinds the EVM value transfer.

### Impact Explanation
Because `rewards()` is a `view` function that never calls `HandlePaymentUsei`/`HandlePaymentUseiWei`/`ValidateNonPayable`, any `usei`/`wei` sent as `msg.value` to it is deposited into the precompile's backing Sei account by the EVM's value-transfer step and simply stays there — the call completes successfully instead of reverting, so there is no automatic unwind. There is no withdrawal function on the Distribution precompile (or generic sweep mechanism analogous to the coinbase-surplus sweep) that returns balances parked at the precompile's account back to users. Any caller who mistakenly (or via a buggy/compromised frontend/integrator contract) attaches value to a `rewards()` call permanently loses those funds — this is a direct, unrecoverable-by-the-user fund freezing/loss condition reachable from a single unprivileged EVM transaction.

### Likelihood Explanation
Likelihood is moderate: this requires a caller to attach non-zero `value` to what is semantically a pure read-only "view" method, which is not the default usage pattern from tooling (most SDKs/ethers `staticcall`/`call` wrappers for `view` functions don't attach value by default). However, since the ABI marks the function `external view` (not `payable`), and no runtime check catches an inadvertent value attachment (e.g., a hand-rolled `eth_call`/raw transaction, a proxy/router contract forwarding leftover `msg.value`, or a bug in an integrating contract), this class of accidental fund loss is realistic and has already been called out as a known "quirk" in the project's own test comments, indicating awareness but no fix at the precompile-execution layer.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` dispatch branch in `Execute` (all versions, primarily the current `precompiles/distribution/distribution.go`), matching the pattern already used for `WithdrawValidatorCommissionMethod` and other query methods, so that any value sent to `rewards()` causes the call to revert, letting the EVM's journal/rollback restore the sender's balance rather than stranding it at the precompile address.

### Proof of Concept
1. Associate an EVM account with a Sei address and fund it with `usei`.
2. Call the Distribution precompile at `0x0000000000000000000000000000000000001007` via `rewards(address)` (`RewardsMethod`), attaching a non-zero `value` in the transaction (e.g., using a raw `eth_call`/`eth_sendRawTransaction` or a wrapper contract that forwards `msg.value`), instead of the ethers.js default (which typically omits value for `view` calls).
3. Observe the call succeeds (returns reward data) rather than reverting.
4. Query the precompile's backing Sei account balance (`p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address)`) before/after — the sent value has been credited there with no corresponding refund, and there is no exposed method on the Distribution precompile to withdraw it back to the sender, confirming permanent loss/freezing of the transferred funds.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
