## Finding: Unchecked ERC20 boolean return value in escrow withdrawal (Tron IntentGatewayV2)

### Title
Escrow withdrawal/dust-sweep accepts `success=true` from a low-level `.call` without checking the encoded ERC20 `transfer` boolean return, permanently burning escrowed funds for tokens that return `false` on failure - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
This is the direct analog of the Compound `enterMarket`/`exitMarket` bug: a call that can signal failure without reverting (a returned error code/boolean) is not validated by the caller. In the Tron variant of `IntentGatewayV2`, escrow payouts use a raw low-level `.call` to invoke `IERC20.transfer`, checking only that the call itself did not revert (`success`), while ignoring the ABI-encoded boolean return value that ERC20 uses to signal transfer failure. The main EVM `IntentGatewayV2.sol` correctly uses `SafeERC20.safeTransfer`/`safeTransferFrom` (which decodes and asserts the boolean), but the Tron contract imports `SafeERC20` and even declares `using SafeERC20 for IERC20;` yet bypasses it for the payout paths.

### Finding Description
In `withdraw()` and the `SweepDust` handler inside `onAccept()`, ERC20 payouts are performed like this: [1](#0-0) 
and in the dust-sweep branch: [2](#0-1) 
and for fee redemption: [3](#0-2) 

All three sites do `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only branch on the low-level `success` flag (i.e., whether the call reverted), never decoding/asserting the returned `bool` that `transfer` uses to report failure per the ERC20 standard. Any TRC20/ERC20 token that returns `false` instead of reverting on a failed transfer (a well-known "non-compliant token" pattern, and the exact behavioral analog of Compound's non-reverting error codes) will make `success == true` even though no tokens moved.

Despite `SafeERC20` being imported and aliased for `IERC20` in this same file [4](#0-3) , the payout code paths deliberately use the raw `.call` pattern instead of `safeTransfer`, unlike the primary EVM `IntentGatewayV2.sol`, which uses `safeTransferFrom`/`safeTransfer` throughout [5](#0-4) .

Once `success` is (incorrectly) treated as a real transfer, the escrow accounting is decremented and the commitment is marked as settled/filled, exactly as if the beneficiary had been paid: [6](#0-5) 

### Impact Explanation
This is a fund-loss bug in the bridge's custody/settlement path, not a peer/relayer/admin issue. For any input or output token on Tron whose `transfer` implementation returns `false` instead of reverting on failure (e.g., paused state, blacklist, insufficient allowance-style guard implemented via return value, or any TRC20 quirk), the beneficiary receives zero tokens while:
- the escrow record `_orders[body.commitment][token]` is decremented to zero (or below the "unknown order" guard threshold), and
- `EscrowReleased`/`EscrowRefunded`/`DustSwept` events fire signalling successful settlement,
- `_filled[body.commitment]` is set, permanently marking the order as filled.

Because the accounting already reflects "paid," the tokens are permanently stuck in the contract with no code path to re-attempt payout to the rightful beneficiary. This is a direct, in-scope "loss of funds" / "false settlement acceptance" impact on bridge custody.

### Likelihood Explanation
Exploitability does not require a malicious relayer, prover, or admin - it depends only on the token contract's transfer semantics for tokens configured as valid `order.inputs`/`order.output.assets`. Any token whose `transfer()` can return `false` without reverting (a known ERC20 anti-pattern; some TRC20 tokens on Tron follow this exact pattern) triggers the bug automatically the first time a transfer to that token's balance-insufficient/blocked recipient occurs during ordinary withdraw/sweep/fee-redemption flow — no attacker action beyond normal usage of the intent-fill flow is needed.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust`/fee-redemption branches of `onAccept()` with `IERC20(token).safeTransfer(...)`, consistent with the already-imported `SafeERC20` library and with the main EVM `IntentGatewayV2.sol` implementation. This ensures both call-revert and ERC20 boolean-return failures cause a revert instead of being silently accepted as success.

### Proof of Concept
1. Deploy (or use) an ERC20/TRC20 token whose `transfer` returns `false` (rather than reverting) under some condition — e.g., recipient blacklisted, or contract paused — a legitimate, standards-permitted implementation choice.
2. Configure this token as a valid `order.inputs`/output asset and have a user create/escrow an order in `IntentGatewayV2` (Tron) using this token.
3. Once the order is filled/refunded, `onAccept` → `withdraw()` executes:
   `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();`
   at [7](#0-6) .
4. Trigger the token's failure condition (e.g., blacklist the beneficiary, or pause the token) so `transfer` returns `false` while the external call itself does not revert.
5. `success` is `true`, so the code proceeds: `_orders[body.commitment][token] -= amount;` and emits `EscrowReleased`, marking the order filled — but the beneficiary's balance never increased. The tokens remain trapped in the `IntentGatewayV2` contract with no remaining code path to redeliver them to the beneficiary.
