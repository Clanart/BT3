### Title
Use-after-free of a live map-value wrapper on `Message.MergeFrom()`/`MergeFromString()` overwrite of a duplicate map key - (File: `python/google/protobuf/pyext/message.cc`)

### Summary
CVE-2018-4022 is a use-after-free in MKVINFO caused by processing an attacker-controlled file such that a previously-referenced object is freed while a stale pointer to it remains reachable and is later dereferenced. The transferable invariant is: *any code path that lets a public parser API silently free/replace an object that is still referenced by a live handle is a use-after-free hazard.* In the Python C++ (`pyext`) implementation of protobuf, `MaybeReleaseOneofBeforeMerge()` — the function specifically added to fix exactly this class of bug for oneof fields — explicitly excludes repeated/map fields (`!descriptor->is_repeated()`), and the map-field merge path (`MapFieldBase::MergeFrom`) silently overwrites an existing key's message value at the C++ level with no notification to the Python wrapper layer, unlike the deliberate `MaybeReleaseSubMessage()` protection used for explicit map-entry deletion.

### Finding Description
`CMessage.MergeFrom()` / `MergeFromString()` (`python/google/protobuf/pyext/message.cc:1977-2014`, `2074-2169`) call `MaybeReleaseOneofBeforeMerge(self, other)` before doing the actual merge, in order to detach any live Python `CMessage` wrapper that is about to be invalidated: [1](#0-0) 

That helper walks `self->composite_fields`, but only for **non-repeated** message fields: [2](#0-1) 

The comment inline documents the gap explicitly: *"For normal repeated message, MergeFrom will append the messages. For message map with same keys, it is overwrite"* — i.e., the author knew map entries can be overwritten by `MergeFrom`, but the release-before-merge protection deliberately does not cover this case, presumably because map-value wrappers aren't tracked via `composite_fields` on the top-level message.

When a `Message.MergeFrom()`/`MergeFromString()` call is made with `other` containing a map entry whose key already exists in `self`, the underlying C++ `MapFieldBase::MergeFrom` (invoked transitively through `message->MergeFrom(*other_message->message)` at `message.cc:2008` or `message->MergeFrom(*temp_message)` at `message.cc:2161`) overwrites the map slot's `Message*` value directly — this deallocates/reconstructs the sub-message storage for that key without any callback into the Python extension layer.

Contrast this with the *safe* pattern used elsewhere in the same file, `MessageMapSetItem` (explicit deletion of a map entry), which correctly detaches any live wrapper before releasing the underlying entry: [3](#0-2) 

No equivalent call happens for the top-level `Message.MergeFrom`/`MergeFromString` path when the *overwritten* value is a map entry that a Python wrapper (`CMessage`) already points to (obtained via `msg.some_map[key]`, which caches/creates a wrapper through `BuildSubMessageFromPointer` in `GetCMessage()` at `python/google/protobuf/pyext/map_container.cc:585-592`). The wrapper's `->message` pointer becomes dangling.

The protobuf project's own Python-implementation-agnostic test suite acknowledges this exact hazard as a known, un-mitigated crash risk in the C++ extension: [4](#0-3) 

The test comment states: *"During the call to MergeFrom(), the C++ implementation will have deallocated the underlying message... The line below is likely to cause a segmentation fault,"* and the assertion that would trigger the crash is explicitly skipped for `api_implementation.Type() == 'cpp'`.

### Impact Explanation
Under the stated threat model (ordinary client sending bounded, well-formed binary protobuf through the public `MergeFromString`/`ParseFromString` API to a trusted, valid schema), a consuming application that:
1. Reads a map field entry into a local variable (`v = msg.map_field[k]`, creating/caching a `CMessage` wrapper around a raw `Message*`), then
2. Calls `msg.MergeFrom(other)` or `msg.MergeFromString(bytes)` with attacker-controlled bytes containing the same map key `k`,

ends up with `v` holding a dangling native pointer into freed/reused C++ heap memory. Any subsequent Python-level access to `v` (attribute read, `str()`, serialization, comparison, etc.) dereferences freed memory inside the CPython extension, which can lead to memory corruption, information disclosure, or crashes — directly analogous to CVE-2018-4022's confidentiality/integrity/availability impact (C:H/I:H/A:H), and reachable purely through the public binary-parsing API with no privileged access, malicious schema, or unbounded input required.

### Likelihood Explanation
The trigger requires only two ordinary, well-documented API calls (accessing a map entry, then merging a message with a duplicate key) — a realistic and common application pattern (e.g., caching sub-objects, then merging incremental updates from the wire). No malformed wire format, huge payloads, or resource exhaustion is needed; a small, valid, schema-compliant protobuf message with one duplicated map key is sufficient. This is High likelihood for any application code that retains references to map sub-message values across `MergeFrom`/`MergeFromString` calls, which is a plausible and unremarkable usage pattern.

### Recommendation
Extend `MaybeReleaseOneofBeforeMerge` (or add a parallel pre-merge pass) to also detect and detach live wrappers for message-map fields whose key set overlaps between `self` and `other`, mirroring the existing `MaybeReleaseSubMessage`/wrapper-detach pattern already used in `MessageMapSetItem` (`map_container.cc:649-659`) for explicit key deletion. Concretely, before calling `message->MergeFrom(*other)`, iterate any live `MessageMapContainer` wrappers on `self`, and for each key present in both `self` and `other`, call `parent->MaybeReleaseSubMessage()` on the corresponding cached `CMessage` so any live Python handle is safely detached (deep-copied) rather than left pointing at soon-to-be-overwritten storage.

### Proof of Concept
Based on `python/google/protobuf/internal/message_test.py:3122-3161` (`testMergeFrom`), which already documents (but skips for the C++ backend) the exact reproduction:

```python
from google.protobuf.internal import api_implementation
assert api_implementation.Type() == 'cpp'  # or 'upb', depending on binding
msg = map_unittest_pb2.TestMap()
msg.map_int32_foreign_message[222].c = 123

msg2 = map_unittest_pb2.TestMap()
msg2.map_int32_foreign_message[222].d = 20

old_map_value = msg2.map_int32_foreign_message[222]   # caches a live CMessage wrapper
msg2.MergeFrom(msg)          # or msg2.MergeFromString(msg.SerializeToString())
                              # C++ overwrites map slot 222's Message storage
old_map_value.c              # use of now-dangling pointer -> UB / potential segfault
```

The existing repository comment on this test explicitly confirms: *"the C++ implementation will have deallocated the underlying message... The line below is likely to cause a segmentation fault."* I was not able to execute this reproduction in a live environment (no execution tooling available in this session); the analysis is based on static tracing of `message.cc`/`map_container.cc` and the project's own acknowledging test comment, which should be independently confirmed by running the above snippet against the `cpp`/`upb` Python implementation.
