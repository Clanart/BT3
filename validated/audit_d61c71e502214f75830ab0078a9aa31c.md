## Title
Unbounded / cycle-unsafe `root_owner()` allows self-owned object cycles to permanently DoS code-object publish, upgrade, and lazy module self-init — (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks an object's ownership chain with no nesting bound and no cycle guard, unlike the other ownership-traversal helpers in the same module (`owns`, `verify_ungated_and_descendant`) which both explicitly cap traversal at `MAXIMUM_OBJECT_NESTING` and abort on cycles. `root_owner()` is the exact primitive that the new lazy-module-initialization / code-object-ownership feature relies on to gate both `code::publish_package` (object owner recording, used for upgrades to object-hosted packages) and `init::assert_may_self_initialize` (the authorization check that mints a signer for a module to self-initialize). An object owner can create a genuine self-ownership cycle with a single ordinary `object::transfer` call (transferring an object to itself), after which any call to `root_owner()` on that object infinite-loops and aborts on out-of-gas, permanently bricking publish/upgrade and lazy self-init for that code object.

### Finding Description
`root_owner()`: [1](#0-0) 

has no depth counter and no `exists<ObjectCore>` re-check inside the loop — it only checks `is_object(obj_owner)` and reads `.owner()` again. Compare this with the module's own hardened traversal helpers, both of which bound iteration explicitly: [2](#0-1) [3](#0-2) 

A self-ownership cycle is directly reachable through the existing, unprivileged `transfer` entrypoint. The module's own test confirms the *first* self-transfer call succeeds and creates the cycle (only the *second* attempt aborts, because `verify_ungated_and_descendant` walks the chain *before* the mutation, so it does not see the cycle it is about to create): [4](#0-3) 

Once `ObjectCore.owner == self`, `root_owner()` loops forever (`is_object(self)` is always true and `obj_owner` never changes), which the Move VM only terminates via an out-of-gas abort.

This directly reaches publish-path/code-safety logic:
- `code::publish_package` computes `root_owner()` for the target address whenever lazy module initialization is enabled and the address is an object, to record the deploy owner used to gate self-init on future upgrades: [5](#0-4) 
- `init::assert_may_self_initialize` calls `root_owner()` on every lazy self-init attempt for an object-hosted module, which mints the module's own signer (the mechanism gating protected write-set mutation for module init): [6](#0-5) 

So a corrupted (cyclic) owner field on a code object turns `root_owner()` into an unconditional out-of-gas abort at exactly the two call sites that gate object-code publishing/upgrading and native module-init validation.

### Impact Explanation
Any account controlling an object used as a code-deployment target (via `object_code_deployment::publish`, which creates the `ManagingRefs`-controlled object) can self-transfer that object to itself once, corrupting `ObjectCore.owner` into a self-cycle. After that:
- Every future `code::publish_package`/`object_code_deployment::upgrade` call targeting that object address will abort (out-of-gas) as soon as `root_owner()` is invoked (when lazy module initialization is enabled), permanently blocking upgrades to that code object.
- Every call path that relies on `init::internal_maybe_initialize`/`assert_may_self_initialize` for that object address (lazy module self-init) will similarly abort forever, blocking legitimate protected state initialization for any module living at that address.

This is a "native validation ... reaches protected state mutation" failure: a missing bound in a security-relevant ownership-traversal primitive breaks the invariant that publish/upgrade/self-init authorization checks always terminate, resulting in a permanent denial of the publish/upgrade/init flow for the affected code object. Because the object may be shared infrastructure (e.g., owned by a DAO/multisig/resource account whose control changes hands), a single malicious or careless transaction from anyone able to transfer the object can permanently disable upgrade capability for all future stakeholders — high impact, since (per the framework's own design intent in `object_code_deployment.move`) upgrade capability is meant to be durable and object-scoped, not bricklable by a benign-looking self-transfer.

### Likelihood Explanation
High likelihood: creating the cycle requires only one ordinary, unprivileged `object::transfer(owner, obj, obj_address)` call by whoever currently owns the object (no admin/governance privilege needed), and `allow_ungated_transfer` is true by default. The triggering code paths (`code::publish_package` owner recording, `init::assert_may_self_initialize`) are exercised on every publish/upgrade to an object-hosted package and every lazy self-init call once the `LAZY_MODULE_INITIALIZATION` feature is enabled.

### Recommendation
Bound `root_owner()`'s traversal the same way `owns()` and `verify_ungated_and_descendant()` do — cap iterations at `MAXIMUM_OBJECT_NESTING` and abort with a defined error (e.g. `EMAXIMUM_NESTING`) instead of looping unboundedly:
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    let count = 0;
    while (is_object(obj_owner)) {
        count += 1;
        assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Additionally, consider preventing self-ownership transfers outright (reject `to == object` in `transfer_raw`) since it is the root cause enabling the cycle in the first place.

### Proof of Concept
1. Create an object `O` (e.g. via `object_code_deployment::publish`, which creates a named object owned by the publisher and stores `ManagingRefs`).
2. As the current owner, call `object::transfer(owner, O, address_of(O))` — a self-transfer. This succeeds (as shown by the module's own `test_cyclic_ownership_transfer_should_fail` test, whose *first* transfer call succeeds and sets `ObjectCore.owner(O) == O`).
3. With `LAZY_MODULE_INITIALIZATION` enabled, attempt `object_code_deployment::upgrade(...)` on `O`, or trigger any module at `O` that calls `init::internal_maybe_initialize`.
4. `code::publish_package` (or `init::assert_may_self_initialize`) calls `object::address_to_object<ObjectCore>(O).root_owner()`, which infinite-loops on the self-cycle and the transaction aborts on out-of-gas — permanently, for every subsequent attempt, since the cycle can never be fixed via `transfer` (any further self-transfer attempt also aborts, per `verify_ungated_and_descendant`'s nesting check, and no other function un-cycles ownership).

    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
