Based on the investigation, the closest reachable analog to the Envoy ext_proc bug class (processing multiple items in one batch, where handling an early item invalidates/corrupts shared state that later processing relies on) is a pointer-aliasing bug in Kaia's bundle transaction commit logic during block building.

### Title
Incorrect blob-gas rollback due to pointer aliasing in bundle transaction processing corrupts block header state - ([File: work/worker.go])

### Summary
`commitBundleTransaction` executes multiple transactions belonging to a single bundle (e.g., a gasless `[Lend, Approve, Swap]` bundle or an auction `[BidTx]` bundle) in one loop over `bundle.BundleTxs`, similar to how the Envoy ext_proc handler iterates multiple `ProcessingResponse` messages packed into a single gRPC message. When any bundle transaction fails partway through the batch, the function attempts to roll back all effects via a captured "snapshot" and a `restoreEnv` closure. However, the blob-gas accumulator snapshot is a shallow pointer copy, not a value copy, so the rollback silently fails to undo mutations already applied by earlier or aborted iterations in the same batch.

### Finding Description
In `work/worker.go`, `commitBundleTransaction` captures rollback state before iterating the bundle's transactions: [1](#0-0) 

`env.header.BlobGasUsed` is declared as `*uint64` (a pointer field on the block header). The line `blobGasUsedSnapshot := env.header.BlobGasUsed` copies only the pointer value, so `blobGasUsedSnapshot` and `env.header.BlobGasUsed` alias the same underlying `uint64`. Inside the per-tx loop, blob transactions mutate that shared value in place: [2](#0-1) 

Because `*env.header.BlobGasUsed += tx.BlobGas()` writes through the pointer that `blobGasUsedSnapshot` also references, the subsequent `restoreEnv()` call — which merely reassigns `env.header.BlobGasUsed = blobGasUsedSnapshot` (the same pointer) — cannot undo the already-applied increment. This is functionally analogous to the Envoy bug class: processing item N in a batch (a blob tx inside the bundle) mutates shared state that the "cleanup/rollback" path for the batch assumes is still pristine, because the reference used for rollback was never actually independent of the live object.

By contrast, `env.header.GasUsed` (a plain `uint64` value field) is correctly value-copied into `gasUsedSnapshot` and is correctly restored, showing the intended pattern was value-semantics rollback — the `BlobGasUsed` pointer field breaks that invariant.

### Impact Explanation
Any bundle that includes a blob-type transaction which fails or reverts inside `commitBundleTransaction` (e.g., a gasless `LendTx`/`ApproveTx`/`SwapTx` bundle or auction bid bundle where one of the packed transactions is an EIP-4844 blob transaction and reverts with `ErrRevertedBundleByVmErr` or `ErrTxGeneration`) leaves `env.header.BlobGasUsed` permanently inflated by the failed transaction's blob gas, even though `markAllTxUnexecutable()` and `restoreEnv()` are invoked specifically to undo that transaction's effects. The proposer then builds a block whose header `BlobGasUsed` field over-reports the actual blob gas consumed by the transactions that remain in the block. This corrupts:
- The `excessBlobGas` computation used for the blob fee market in subsequent blocks (fee/gas accounting divergence).
- Cross-node consistency: if other honest nodes independently recompute `BlobGasUsed` from the transactions actually included in the block (as EIP-4844 validation typically does), they will disagree with the proposer's self-reported value, causing block rejection or, in the worst case, an accepted block whose header field doesn't match its body — a state-divergence / invalid-block-acceptance condition.

Since triggering this only requires an unprivileged sender submitting a bundle-eligible transaction set (gasless swap/approve or auction bid) that includes a blob transaction designed to fail mid-bundle, this is reachable by a normal transaction sender / auction bidder without any special privilege.

### Likelihood Explanation
Medium. It requires: (1) the attacker's transaction to be selected into a bundle by the gasless or auction `TxBundlingModule`, (2) the bundle to include a blob-type transaction, and (3) that transaction (or an earlier one in the same bundle) to fail so the revert path (`markAllTxUnexecutable`/`restoreEnv`) executes. Constructing a bundle transaction that both qualifies for bundling and reliably reverts is feasible for the transaction's own sender by crafting the swap/bid logic to revert on-chain, so the trigger conditions are attacker-controlled and repeatable across blocks.

### Recommendation
Change `commitBundleTransaction`'s blob-gas snapshot/restore to use value semantics instead of pointer aliasing, e.g. snapshot the dereferenced value (`blobGasUsedVal := *env.header.BlobGasUsed`) and on restore write it back through the pointer (`*env.header.BlobGasUsed = blobGasUsedVal`) rather than reassigning the pointer itself. Add a regression test that includes a reverting blob transaction inside a bundle and asserts `header.BlobGasUsed` is unchanged after the bundle fails.

### Proof of Concept
1. Construct a gasless (or auction) bundle whose last transaction is an EIP-4844 blob transaction crafted to revert (e.g., swap conditions unmet) — reachable via normal `eth_sendRawTransaction` plus the module's bundling detection in `ExtractTxBundles`.
2. During block building, `ApplyTransactions` → `commitBundleTransaction` executes the bundle; the blob tx increments `*env.header.BlobGasUsed` at [3](#0-2)  before the failure is detected at the following tx or via receipt status check.
3. `restoreEnv()` is invoked at [4](#0-3) , but because `blobGasUsedSnapshot` aliases the live pointer, `env.header.BlobGasUsed`'s dereferenced value still reflects the failed transaction's blob gas.
4. The resulting block header's `BlobGasUsed` no longer matches the blob gas of the transactions actually retained in the block, which can be detected by comparing `header.BlobGasUsed` before/after the failed-bundle path in a unit test around `commitBundleTransaction`.

Note: I was unable to fully confirm, within the available iterations, whether the downstream block/header validators (`blockchain/block_validator.go`) recompute and strictly reject a mismatched `BlobGasUsed` value at block-import time on other nodes, or whether they trust the proposer-reported header field for this scenario. This would determine whether the ultimate effect is "block rejected during consensus (divergence/halt)" or "invalid header value silently accepted, permanently skewing the blob fee market." Confirming this requires reading `blockchain/block_validator.go`'s blob gas validation logic in a follow-up session.

```go
func (env *Task) commitBundleTransaction(bundle *builder.Bundle, bc BlockChain, nodeAddr common.Address, vmConfig *vm.Config) (error, *types.Transaction, []*types.Log) {
	lastSnapshot := env.state.Copy()
	gasUsedSnapshot := env.header.GasUsed
	blobGasUsedSnapshot := env.header.BlobGasUsed
	blobsSnapshot := env.blobs
	tcountSnapshot := env.tcount
	txs := []*types.Transaction{}
	receipts := []*types.Receipt{}
	logs := []*types.Log{}

	markAllTxUnexecutable := func() {
		for _, txOrGen := range bundle.BundleTxs {
			if txOrGen.IsConcreteTx() {
				tx, _ := txOrGen.GetTx(0)
				tx.MarkUnexecutable(true)
			}
		}
	}

	restoreEnv := func() {
		env.state.Set(lastSnapshot)
		env.header.GasUsed = gasUsedSnapshot
		env.tcount = tcountSnapshot
		// blob related env are restored to the snapshot
		env.header.BlobGasUsed = blobGasUsedSnapshot
		env.blobs = blobsSnapshot
	}
```
