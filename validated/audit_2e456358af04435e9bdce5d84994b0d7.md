### Title
`ThresholdKeys::read` allocates attacker-controlled vector capacity from an unchecked `n` before validating parameters or payload availability - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs` is the same bug class as GHSA-cxmj-83gh-fp49: a dimension/count field (`n`, a `u16`) is read from untrusted bytes and immediately used to size a heap allocation (`Vec::with_capacity(usize::from(n))`) before the value is validated against `ThresholdParams` rules or against how many bytes the reader actually contains. A tiny input can therefore force a multi-megabyte allocation that is only released after the subsequent reads fail.

### Finding Description
The deserialization path is:

1. `t`, `n`, `i` are read as raw `u16`/`Participant` values from the reader (crypto/dkg/src/lib.rs:591-602). No validation happens here — `ThresholdParams::new` is only invoked at the end, after all allocations and reads.
2. The interpolation tag is read. When it is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` (crypto/dkg/src/lib.rs:607-612), allocating `n * size_of::<C::F>()` bytes up front.
3. Only afterward are `n` field elements, a secret share, and `n` verification-share group elements read into a `HashMap` keyed `1 ..= n` (crypto/dkg/src/lib.rs:620-623), and only then is `ThresholdKeys::new(ThresholdParams::new(t, n, i)?, ...)` called (crypto/dkg/src/lib.rs:625-630), which is where `t <= n`, `i <= n`, and the constant-interpolation `t == n` requirement are actually enforced.

So a payload of roughly 8 bytes (`id_len` + `id` aside) declaring `n = 65535` causes:

- `Vec::with_capacity(65535)` of field elements: ~2 MB for a 32-byte scalar (Ristretto/k256/p256), ~3.7 MB for an ed448-width scalar — committed before a single field element is read.
- A `HashMap` grown to 65535 entries of `(Participant, C::G)` as long as the attacker keeps feeding valid point encodings (65535 × 33 bytes ≈ 2.1 MB of payload buys ~65535 × `size_of::<C::G>()` plus HashMap overhead of resident memory even though `ThresholdKeys::new` will reject the set).

The loop `for l in (1 ..= n).map(Participant)` also performs `n` `read_G` calls; each canonical point accepted extends the committed memory. Critically, the "guarded" element data analogous to the advisory's inner array — the `n` scalars and `n` points — are only checked for *existence* (EOF), never for consistency with `t` or for any allocation ceiling, until after the peak allocation has already occurred.

This is reachable by an unprivileged party wherever serialized `ThresholdKeys` are accepted from untrusted input — `ThresholdKeys::read` is a public API listed among the reachable deserialization surfaces — e.g. a node loading a key blob supplied by an external peer, or any protocol framing that embeds a serialized `ThresholdKeys` structure.

### Impact Explanation
Per the advisory's own severity bar (CVSS 4.0, VA:L → Medium): a payload of under 100 bytes forces a ~2-4 MB heap allocation plus up to 65535 decompression operations and HashMap insertions before erroring. Repeated submissions (e.g., an endpoint retrying `ThresholdKeys::read` on attacker bytes) translate directly into memory pressure, allocator churn, and CPU burn for scalar/point decoding. On memory-constrained validators this can cause OOM termination of the signing process — precisely the "allocation amplification where a small payload encodes disproportionate dimensions" pattern the advisory describes, and unlike the `RrCodec` path in `coordinator/src/p2p.rs` (which caps at `MAX_LIBP2P_REQRES_MESSAGE_SIZE`), there is no byte-length cap anywhere in `ThresholdKeys::read`.

### Likelihood Explanation
Reachable by any unprivileged actor able to supply bytes to `ThresholdKeys::read`. The attack requires no key knowledge, no collusion, and no malformed curve encodings — only a large declared `n` and enough well-formed point encodings to keep the `read_G` loop running, or even nothing at all for the `Vec::with_capacity` amplification (the capacity is committed before the first scalar read; a payload ending at byte ~10 still triggers the 65535-element reservation). It is limited to ~2-4 MB of instantaneous allocation per call (bounded by `u16`), keeping it at Medium rather than High, matching the advisory's VA:L rating.

### Recommendation
Validate before allocating in `ThresholdKeys::read`:

- Reorder so `ThresholdParams::new(t, n, i)` is constructed and checked (rejecting `t > n`, `i > n`, zero values) immediately after reading `t`, `n`, `i`, before any allocation.
- When the interpolation tag is `Constant`, enforce `t == n` before calling `Vec::with_capacity`, and replace `with_capacity(n)` with an incremental `Vec::new()`/`push` loop (or a `with_capacity(min(n, MAX_REASONABLE_N))`), since real multisigs never approach `n = 65535`.
- Optionally impose an explicit protocol maximum on `n` (e.g., a documented sane bound far below `u16::MAX`) and reject larger `n` prior to reading `n` field/group elements, so allocation and work are bounded by configured limits rather than attacker-declared ones.

### Proof of Concept
```rust
use std::io;
use frost::curve::Ristretto; // or any in-scope Ciphersuite
use dkg::ThresholdKeys;      // re-exported via frost::ThresholdKeys
use ciphersuite::Ciphersuite;

fn attacker_payload() -> Vec<u8> {
    let mut buf = vec![];
    // Curve ID: correct length + bytes so the id check passes
    buf.extend(&u32::try_from(<Ristretto as Ciphersuite>::ID.len()).unwrap().to_le_bytes());
    buf.extend(<Ristretto as Ciphersuite>::ID);
    // t = 1, n = 65535, i = 1  (all plausible until ThresholdParams::new is finally called)
    buf.extend(&1u16.to_le_bytes());      // t
    buf.extend(&u16::MAX.to_le_bytes());  // n = 65535
    buf.extend(&1u16.to_le_bytes());      // i (non-zero => valid Participant)
    // Interpolation::Constant
    buf.push(0u8);
    // Stop here — the Vec::with_capacity(65535) is already committed
    // before the first read_F fails on EOF.
    buf
}

#[test]
fn allocation_amplification() {
    let payload = attacker_payload(); // ~40 bytes
    // Peak RSS jumps ~2 MB (32-byte F) just for the with_capacity reservation,
    // despite the payload containing zero field elements.
    let res = ThresholdKeys::<Ristretto>::read(&mut payload.as_slice());
    assert!(res.is_err()); // errors only *after* the allocation
}
```

With a longer but still small payload of 65535 valid `read_F`-compatible encodings plus 65535 valid point encodings (~4.3 MB), the attacker additionally forces a fully populated `HashMap<Participant, C::G>` and completes `ThresholdParams::new` — at which point `Interpolation::Constant` with `t = 1 != n` is finally rejected, or with `t = n = 65535` it proceeds to `ThresholdKeys::new`'s group-key sum over 65535 `read_G` results. In all cases the allocated structures exist before any semantic consistency check on `n`.
