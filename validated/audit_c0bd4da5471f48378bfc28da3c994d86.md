### Title
Escrow settlement in `IntentGatewayV2` (Tron) treats a failed ERC20/TRC20 `transfer()` as success, causing silent, unrecoverable loss of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron variant of `IntentGatewayV2` release escrowed tokens using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the *call itself* did not revert. The ABI-encoded return data (the `bool` that ERC20/TRC20 `transfer()` is supposed to return on failure) is never decoded or checked. This is the structural mirror of the FortaStaking report: there, a transfer to a zero/incompatible recipient made the *fund-release step revert*, permanently blocking settlement while state stayed consistent (fail-closed). Here the failure mode is the opposite and worse: the fund-release step can silently **not move any tokens** while the call still reports success, so the contract advances its escrow/settlement bookkeeping (`_orders[...] -= amount`, `_filled[commitment] = beneficiary`) as if payment happened — permanently losing the escrowed funds with no way to retry.

### Finding Description
In the escrow release path: [1](#0-0) 

```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here is `true` whenever the external call does not revert — it does **not** reflect the `bool` return value that `IERC20.transfer` is contractually required to return on failure. Any token contract that returns `false` on a failed transfer instead of reverting (a widely-used, standards-compliant ERC20 pattern; also common among Tron TRC20 tokens, which is presumably why this file avoids OpenZeppelin's `SafeERC20` in the first place) will make this branch report `success = true` while zero tokens actually moved. The code then unconditionally decrements `_orders[...]` and marks the order `_filled`/refunded, permanently retiring the escrow record. There is no subsequent path to re-attempt the transfer — `UnknownOrder` guards prevent a second `withdraw()` call once the entry is zeroed out.

The same unchecked pattern (`token.call(...)`, checking only `success`) is repeated in the `SweepDust` handler: [2](#0-1) 

For contrast, the mainline (non-Tron) `IntentGatewayV2`/`IntentsBase` use `SafeERC20.safeTransfer`, which decodes and checks the return data: [3](#0-2) 

This confirms the Tron contract is missing an equivalent safety check rather than intentionally accepting this risk.

`withdraw()` is reachable through fully public, unprivileged entrypoints — no relayer, prover, or governance action is required to trigger the loss:
- Directly via `cancelOrder()` same-chain path, which calls `withdraw(body, true)`.
- Via `onAccept` for `RedeemEscrow`/`RefundEscrow` requests, which come from an authenticated ISMP instance of the same `IntentGatewayV2` contract on another chain but still deliver an order-creator-chosen `token` address end-to-end.

Because the input/output token address for an order is chosen freely by the order creator at `placeOrder()` time: [4](#0-3) 

an order creator can escrow a token whose `transfer()` returns `false` under attacker-controlled conditions (blacklist-style tokens, pausable tokens, or a custom token deployed by the order creator themselves) targeting the solver's beneficiary address. The solver performs the legitimate cross-chain fill, but when settlement runs, the payout silently fails, the escrow is marked spent, and the solver receives nothing with no recovery path — a direct, unauthorized loss of funds for the rightful beneficiary.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant: `_orders` accounting is decremented and `_filled` is set as if the beneficiary was paid, while the beneficiary receives zero tokens and has no mechanism to reclaim them. This is a direct, unprivileged loss-of-funds bug in a fund-custody/settlement contract, not a peer/relayer/prover trust issue.

### Likelihood Explanation
Any user can call `placeOrder()` with an arbitrary token address they control or select a token with known non-reverting failure semantics; no special privilege, front-running, or malicious infrastructure operator is required. The vulnerable code path (`withdraw`) is exercised on every settlement and refund, making the bug trivially reachable whenever such a token is used.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls in `withdraw()` and the `SweepDust` handler with a transfer helper that decodes and enforces the boolean return value (e.g., check `success && (returndata.length == 0 || abi.decode(returndata, (bool)))`, matching the pattern already used elsewhere via `SafeERC20`), or adopt `SafeERC20.safeTransfer` consistently as done in the non-Tron `IntentsBase`/`IntentGatewayV2` contracts.

### Proof of Concept
1. Order creator deploys a minimal ERC20/TRC20-like contract whose `transfer()` function always returns `false` (without reverting) when called with a specific `beneficiary` address, and returns `true` normally otherwise.
2. Order creator calls `placeOrder()` escrowing that token as an output asset, naming a target solver's address as the eventual beneficiary.
3. A solver fills the order in good faith on the destination chain.
4. Settlement triggers `withdraw()` on the source chain (via `RedeemEscrow`/`onAccept` or `cancelOrder`); `token.call(transfer(beneficiary, amount))` succeeds at the call level but returns `false`.
5. `success` is `true`, so `_orders[commitment][token] -= amount` executes and the order is marked filled — the escrowed tokens are never transferred to the solver and cannot be reclaimed, since the escrow record has already been zeroed.
