### Title
Single failing transfer in `IntentGatewayV2.withdraw()` permanently locks all escrowed order funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` loops over every escrowed token of an order and performs an external transfer (native call or ERC20 `transfer`) for each one, reverting the *entire* function if any single transfer fails. This is exactly the Notional `_redeemMaturedPositions` pattern: a core settlement/refund hook that touches multiple assets atomically, where one poisoned asset or beneficiary permanently blocks the release of all the others.

### Finding Description
`withdraw(WithdrawalRequest memory body, bool isRefund)` [1](#0-0)  iterates `body.tokens` and, for each token, either sends native value via a low-level `.call` or invokes `IERC20.transfer` via a raw `.call` with a success check:

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
``` [2](#0-1) 

If any single token in `body.tokens` cannot be transferred — because `beneficiary` is a contract whose receive/fallback reverts on native value, or because one of the ERC20s in the order is paused/blacklisted for that beneficiary (the same "USDC blocked" scenario Index Coop itself flagged in the cited report) — the whole `withdraw()` call reverts, and none of the other tokens (nor the fee redemption that follows in the same function) are released.

`withdraw()` is invoked from `onGetResponse`, the ISMP module callback that Hyperbridge's own host calls once when a GET response proving non-fulfillment is delivered:
```solidity
function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
    if (incoming.response.values[0].value.length != 0) revert Filled();
    WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
    withdraw(body, true);
}
``` [3](#0-2) 

This mirrors `moduleIssueHook`/`moduleRedeemHook` in the Notional report: a single module callback invoked by the framework, looping unconditionally over a list of positions/assets, where a revert on one item aborts processing of all items in that call. Per Hyperbridge's own ISMP handler docs, a failed module callback means no receipt/commitment update happens and the message is either replayable or must be redelivered [4](#0-3) , but this "replay" property does not help here: if the underlying condition is permanent (beneficiary always reverts on native transfer, or a token is permanently blacklisted for that address), the callback fails identically on every possible redelivery attempt, and the escrowed order funds for *every other token in the same order* — which are otherwise perfectly redeemable — remain locked forever alongside the poisoned one.

### Impact Explanation
This fits the "loss of funds" / "logic attack" bounty category: legitimate order escrow that should be released "exactly once and only to the rightful beneficiary and amount" instead becomes permanently unredeemable because of an unrelated poisoned token/beneficiary pairing bundled into the same multi-token order. The user who placed/filled a multi-asset order loses access to all escrowed assets in that order, not just the problematic one, with no code path in `withdraw()` to skip or isolate the failing leg.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires an order whose beneficiary is a contract that reverts on receiving native tokens, or one of its tokens becoming non-transferable to the beneficiary (blacklist/pause) after escrow but before redemption — both realistic conditions for real-world stablecoins and smart-contract wallets, and exactly the scenario Index Coop itself acknowledged as plausible in the cited report ("USDC tokens being blocked ... unlikely but outside of our control"). No malicious relayer, prover, or admin is required — only a normal beneficiary address that later becomes unable to receive one of the order's assets.

### Recommendation
Do not let a single token/native transfer failure abort redemption of the remaining escrowed assets in `withdraw()`. Options:
- Process each token transfer independently (try/catch or low-level call without aborting the loop) and track any that fail as a separately claimable "stuck" balance the beneficiary can retry/redirect later.
- Split `withdraw()` into per-token redemption entry points so a manager/beneficiary can redeem the healthy assets even if one token is permanently blocked.
- Avoid combining unrelated assets into a single all-or-nothing settlement call in intent-fulfillment/refund hooks.

### Proof of Concept
1. User places a multi-token order via `IntentGatewayV2` (Tron) with `inputs = [ETH, TOKEN_X]`, escrowing both.
2. Order later needs to be refunded/withdrawn (e.g., via `onGetResponse` after a fill-check GET response), calling `withdraw(body, true)` with `body.tokens = [ETH, TOKEN_X]`.
3. If `beneficiary` is a smart-contract wallet with no payable `receive()`, the ETH leg's `beneficiary.call{value: amount}("")` fails, reverting `withdraw()` entirely — even though `TOKEN_X` transfer would have succeeded.
4. Because the underlying condition (beneficiary can't receive ETH) is permanent, every retry of the same withdrawal (whether by resubmitting the timeout/GET-response message or any other trigger) fails identically, and both the ETH and TOKEN_X escrow amounts are permanently stuck in the `IntentGatewayV2` contract with no code path to redeem them separately.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
