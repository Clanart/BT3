### Title
`Scanner` reports outputs of any value as spendable inputs — missing minimum-value bound lets unspendable dust be credited as funds - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The bug class is a missing minimum-bound parameter: the Dopex `reLP()` passed `amountAMin = 0`/`amountBMin = 0` to `addLiquidity()`, so the protocol accepted any unfavorable output amount. The Serai analog is `Scanner::scan_transaction`, which accepts a P2TR output purely on `script_pubkey` match and returns it as a `ReceivedOutput` with no minimum-value check — the scanner's equivalent of `amountMin = 0`. A sender can therefore cause the wallet/multisig to credit an output whose value is below the fee required to spend it, i.e. funds reported received that are not economically spendable.

### Finding Description
`SignableTransaction` defines `DUST = 546` and rejects payments below it, acknowledging that outputs under the dust limit are not relayable/spendable under standard policy (`networks/bitcoin/src/wallet/send.rs:32`, `165-169`). The Bitcoin network layer goes further and requires `DUST = 10_000` so received outputs remain worth aggregating at up to 5 sat/vbyte (`processor/src/networks/bitcoin.rs:624-638`).

`Scanner::scan_transaction` performs no analogous floor. It iterates `tx.output`, matches `output.script_pubkey` against the registered scripts, and unconditionally pushes a `ReceivedOutput` carrying whatever `output.value` the attacker chose (`networks/bitcoin/src/wallet/mod.rs:199-214`). There is no `if output.value < DUST { continue }` — the minimum-amount parameter is effectively zero. `scan_block` similarly forwards coinbase and all other transactions' outputs (`mod.rs:221-227`).

`SignableTransaction::new` then treats every `ReceivedOutput` as a usable input, summing `input.output.value` and only requiring `input_sat >= payment_sat + needed_fee` (`send.rs:175`, `215-221`). Inputs below dust drag the transaction into non-standard territory or consume witness/input weight worth more than their own value.

### Impact Explanation
An unprivileged third party can send a 1-sat (or otherwise sub-dust) P2TR output to the multisig's scanned address or to any registered offset script. `scan_transaction`/`scan_block` report it as a `ReceivedOutput`, i.e. the wallet credits funds that cannot be spent under standard relay policy (a P2TR key-spend input costs ~57 vbytes, so a 1-sat input can never pay its own fee at any positive fee rate). This is "funds reported received that are not spendable" and mirrors the original finding's consequence (protocol receives less than the fair/usable amount because the bound was 0). The value credited exceeds the value recoverable, inflating the apparent balance and forcing the processor to either burn value consolidating it or account for it as an operating cost.

### Likelihood Explanation
Reachable by any external party able to craft a Bitcoin transaction — no validator status, collusion, or leaked key required. The attacker only needs the public P2TR script of the group key or any branch/change offset script (all derivable from the public key via `p2tr_script_buf`). Sending dust to a Bitcoin address is trivially cheap. Exploitation is bounded: it degrades accounting/spendability rather than stealing funds, matching a Medium-class analog rather than High.

### Recommendation
Enforce a minimum value in `Scanner::scan_transaction`: skip outputs with `output.value.to_sat() < DUST` (or a network-defined spendability floor such as the processor's `10_000` sat constant) before pushing a `ReceivedOutput`. This adds the missing `amountMin` bound at the point of crediting, symmetric to the existing `DustPayment` rejection on the send path.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs:199-214 — no value check
pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for (vout, output) in tx.output.iter().enumerate() {
    let Ok(vout) = u32::try_from(vout) else { break };
    if let Some(offset) = self.scripts.get(&output.script_pubkey) {
      res.push(ReceivedOutput {
        offset: *offset,
        output: output.clone(),        // @audit: value unchecked; any amount accepted
        outpoint: OutPoint::new(tx.compute_txid(), vout),
      });
    }
  }
  res
}
```
1. Derive the multisig's P2TR script via `p2tr_script_buf(group_key)` (`mod.rs:80-86`).
2. Broadcast a transaction with an output `{ value: 1 sat, script_pubkey: <group P2TR> }`.
3. `Scanner::scan_block`/`scan_transaction` returns a `ReceivedOutput` with `value() == 1`, crediting 1 sat.
4. `SignableTransaction::new(vec![that_output], …)` fails `NotEnoughFunds`/`TooLowFee` for any realistic fee (`send.rs:211-221`): a ~57-vbyte input at ≥1 sat/vbyte needs ≥57 sats, so the credited sat is unspendable — precisely the `amountMin = 0` failure mode: the protocol accepted a below-par amount with no minimum bound.

Contrast with the send path's own bound, proving the invariant exists but is not applied on receipt:
```rust
// networks/bitcoin/src/wallet/send.rs:32,165-169

for (_, amount) in payments {
  if *amount < DUST { Err(TransactionError::DustPayment)?; }
}
```
