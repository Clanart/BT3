### Title
Unchecked ERC-20 `transfer()` return value in intent escrow settlement causes permanent fund loss — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` settles escrowed intent funds using a raw low-level `.call()` encoding `IERC20.transfer.selector` and only checks that the *call itself* did not revert — it never decodes/validates the boolean return value that the ERC-20 standard requires `transfer()` to report success/failure through. This is the same broken-invariant class as the reported "deprecated `.transfer()`" bug (blind trust in an external value-moving primitive), except here it manifests as a **silent-failure** rather than a forced revert: any ERC-20 that returns `false` instead of reverting on a failed transfer lets settlement accounting finalize while the tokens never leave the contract, permanently stranding the beneficiary's funds.

### Finding Description
In `withdraw()`, escrowed token payout is performed like this: [1](#0-0) 

`_filled[body.commitment] = beneficiary` is set unconditionally at the top of `withdraw()`, and for every token the code does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
`success` here only reflects whether the callee's EVM execution reverted — it says nothing about the ABI-decoded `bool` that `IERC20.transfer` is supposed to return. Any ERC-20 implementation that follows the (still common) pattern of returning `false` on failure instead of reverting (e.g., transfer to a blacklisted/paused/insufficient-balance-guarded recipient, or any conforming-but-non-reverting token used as an order input) will make `success == true` even though no tokens moved. The code then proceeds to decrement `_orders[commitment][token]` and marks the commitment as `_filled`/`EscrowReleased`/`EscrowRefunded` — there is no retry path once this happens.

The same unchecked pattern also exists in the `SweepDust` branch of `onAccept` and for the transaction-fee payout: [2](#0-1) [3](#0-2) 

By contrast, the primary EVM contracts consistently use `SafeERC20.safeTransfer`/`safeTransferFrom`, which does decode and check the return value (e.g. `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);` in `EvmHost.sol`, and `IERC20(_underlying).safeTransfer(beneficiary, message.amount);` in `WrappedHyperFungibleToken.sol`), confirming the Tron variant's manual low-level call is a deviation that drops the standard safety check. [4](#0-3) [5](#0-4) 

### Impact Explanation
This falls under "bridged assets/order escrow" moving incorrectly: settlement (`withdraw`) is treated as final and irreversible (`_filled` is set, escrow accounting is decremented, `EscrowReleased`/`EscrowRefunded` is emitted) even when the actual token transfer silently failed. The tokens remain locked in the `IntentGatewayV2` contract with no accounting entry pointing back to the rightful beneficiary and no way to re-trigger payout, resulting in a genuine loss of user/solver funds for any order whose input/output token is a non-reverting ERC-20. This can be triggered by an ordinary user/solver simply by using such a token as an order asset — no relayer, prover, or admin compromise is required.

### Likelihood Explanation
Likelihood is moderate: it requires the order to use an ERC-20 token that returns `false` rather than reverting on failed transfers (a real but non-universal ERC-20 behavior, present in some legacy/compliance-gated tokens), and a scenario that causes the transfer to actually fail (e.g., recipient blacklisted, paused token, or insufficient balance edge-cases arising from race conditions in escrow accounting). Given that intents systems are explicitly designed to accept arbitrary user-specified tokens, an attacker/user can choose such a token deliberately to grief their own or a counterparty's settlement, or the condition can arise incidentally.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()`, the fee payout, and the `SweepDust` branch with `SafeERC20.safeTransfer`, which decodes and enforces the ERC-20 return value (consistent with the rest of the codebase, e.g. `EvmHost.sol` and `WrappedHyperFungibleToken.sol`). This ensures a failed/false-returning transfer reverts the whole settlement, preventing accounting finalization (`_filled`, `_orders[...] -= amount`) without the funds actually landing.

### Proof of Concept
1. Create/deploy a minimal ERC-20 (or use one with blacklist logic) whose `transfer()` returns `false` instead of reverting when the recipient is blacklisted/paused, and register it as an order's input/output token.
2. Place and fill/settle an order using this token as escrowed asset; ensure the transfer condition that returns `false` is met when `withdraw()` is invoked (e.g., beneficiary temporarily blacklisted by the token issuer at settlement time, or any other non-reverting failure branch of that token).
3. Observe that `withdraw()` at `evm/tron/contracts/apps/IntentGatewayV2.sol:697-698` receives `success == true` from the low-level call (since the callee did not revert), so `_orders[body.commitment][token] -= amount` executes and `EscrowReleased`/`EscrowRefunded` is emitted, while the beneficiary's token balance is unchanged — the tokens remain stuck in the `IntentGatewayV2` contract with no recorded claim.
