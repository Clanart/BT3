### Title
Denial of Service via Infinite Loop in Offer Ancestor-Coin Resolution - (File: chia/wallet/trading/offer.py)

### Summary
`chia.wallet.trading.offer.Offer.get_root_removal()` walks a coin's spend ancestry inside an `Offer` object by repeatedly looking up the coin whose `name()` equals the current coin's `parent_coin_info`, stopping only when it reaches a "non-ephemeral" removal (a coin whose parent is not itself a removal in the same bundle). Because `Offer.from_bytes()`/`from_bech32()` parse an untrusted, attacker-supplied byte blob into arbitrary `CoinSpend`/`Coin` objects without any validation that `parent_coin_info` values correspond to real, non-cyclic chain ancestry, a malicious offer can declare two (or more) removal coins whose `parent_coin_info` fields point at each other's `name()`. This produces a cycle in which neither coin is ever classified as "non-ephemeral," causing the `while` loop in `get_root_removal()` to iterate forever, analogous to the ImageMagick MIFF-parsing infinite loop in CVE-2015-8901 that hangs on crafted (non-validated) container structure.

### Finding Description
`get_root_removal()`: [1](#0-0) 

computes `non_ephemeral_removals` as the set of removals whose `parent_coin_info` is *not* the `name()` of any other removal in the same offer bundle, then loops, replacing `coin` with the removal whose `name()` equals `coin.parent_coin_info`, until `coin` lands in that non-ephemeral set.

All of this data comes straight from the untrusted spend bundle: `Offer.from_bytes()` / `Offer.from_spend_bundle()` build the `_bundle` (and thus `removals()`) purely from parsed `CoinSpend` objects with no on-chain verification of coin ancestry: [2](#0-1) 

Nothing enforces that `parent_coin_info` values form an acyclic ancestry chain (unlike real on-chain coins, whose IDs are deterministically derived hashes that cannot form cycles). An attacker can therefore construct two synthetic removal coins A and B in the offer's `_bundle.coin_spends` such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`. Both coins then fail the "non-ephemeral" test (each one's parent is present in the removal-name set), so the `while coin not in non_ephemeral_removals:` loop in `get_root_removal()` alternates between A and B forever.

`get_root_removal()` is invoked, per-offered-coin, by `get_primary_coins()`: [3](#0-2) 

which is itself reachable from wallet code that inspects/validates a counterparty-supplied offer (offer summary/validity/trade flows in `chia/wallet/trade_manager.py`) before the wallet decides whether to accept it — i.e., an offer counterparty can hand this crafted blob to a victim's wallet during normal offer examination/handling, without the victim ever pushing anything on-chain.

### Impact Explanation
A crafted offer file/bech32 blob causes the recipient wallet process (or, if surfaced through Data Layer's offer verification/take-offer path, a Data Layer client) to hang in an unbounded Python loop when it attempts to compute the offer's primary/root coins. This is a synchronous, single-threaded loop with no cost or iteration bound, so it will consume CPU indefinitely and block the asyncio event loop, halting the wallet's ability to process further RPCs, sync, or transactions until the process is killed — a spend/offer-triggered transaction-processing halt reachable by any offer counterparty, matching the CVE-2015-8901 bug class (unbounded loop over attacker-controlled, weakly-validated structured input).

### Likelihood Explanation
Likelihood is moderate: constructing the crafted `CoinSpend` pair with mutually-referencing `parent_coin_info` values requires only building a raw `WalletSpendBundle`/offer byte blob (no signature validity or CLVM execution correctness is required to reach the vulnerable ancestry-walk, since it inspects `Coin.parent_coin_info`/`name()` fields directly, before/independently of full spend validity checks). No special privileges are needed — this is exactly the "offer counterparty" trust boundary explicitly in scope. The main uncertainty (not fully confirmed with the available tool calls) is the exact call path in `chia/wallet/trade_manager.py` that triggers `get_primary_coins()`/`get_cancellation_coins()` on an offer before the user actively accepts it; this should be verified directly in that file to confirm whether the hang occurs during offer receipt/inspection versus only after acceptance.

### Recommendation
- In `get_root_removal()`, bound the ancestry walk (e.g., cap iterations at the number of removals in the bundle) and raise a `ValueError`/`ValidationError` if a cycle is detected instead of looping unboundedly.
- Validate, when constructing `Offer` from untrusted bytes, that the removal-coin `parent_coin_info` graph is acyclic (a simple visited-set check) before any ancestry-dependent computation (`get_primary_coins`, `get_cancellation_coins`, `get_root_removal`) is performed.
- Add a fuzz/unit test with two or more mutually-referencing ephemeral coins to ensure `Offer` parsing/inspection fails fast rather than hanging.

### Proof of Concept
1. Construct two `CoinSpend`s, A and B, with otherwise-valid settlement puzzles/solutions such that `A.coin.parent_coin_info == B.coin.name()` and `B.coin.parent_coin_info == A.coin.name()` (both created purely from the offer-side, without needing real on-chain ancestry).
2. Assemble a `WalletSpendBundle` containing these two coin spends (plus whatever additional spends are needed to make `Offer.__post_init__` succeed without exceptions) and wrap it via `Offer(requested_payments, bundle, driver_dict)` / serialize with `bytes(offer)`.
3. Deliver the resulting offer bech32 string to a victim wallet (e.g., as a file to `take_offer` examine-only mode, or through Data Layer's `verify_offer`/`take_offer` RPC).
4. When the victim's code path invokes `offer.get_primary_coins()` (directly, or via `get_cancellation_coins()`/trade-manager flows), `get_root_removal()` enters the A→B→A→B… cycle and never returns, hanging the wallet process indefinitely.

```python
    # This returns the non-ephemeral removal that is an ancestor of the specified coin
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```

```python
        primary_coins: set[Coin] = set()
        for _, coins in self.get_offered_coins().items():
            for coin in coins:
```
