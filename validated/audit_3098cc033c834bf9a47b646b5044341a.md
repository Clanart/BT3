### Title
`SignableTransaction` computes weight/`needed_fee` without the OP_RETURN `data` output, underpaying the fee for any transaction carrying data - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output to `tx_outs` when `data` is supplied, but the subsequent call to `calculate_weight_vbytes` — which determines `weight` (used for the `TooLargeTransaction` check) and `vbytes` (used to derive `needed_fee` and the `TooLowFee` check) — is only given `payments`, never the data output. The change-output fee path (`fee_with_change`) has the same omission. The resulting transaction is signed and broadcast paying the specified fee rate for a smaller virtual size than it actually occupies.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the data output is pushed onto `tx_outs` before the weight calculation: [1](#0-0) 

`calculate_weight_vbytes` reconstructs a candidate `Transaction` solely from `inputs`, `payments`, and an optional `change` script — there is no parameter for the data output: [2](#0-1) 

Both fee computations therefore exclude the OP_RETURN output's ~11–90 serialized bytes: [3](#0-2) 

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` is computed on an underestimated `vbytes`, so the signed transaction's *effective* fee rate is strictly below the requested `fee_per_vbyte` (up to ~40% below for small transactions with a full 80-byte payload).
- The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the same underestimated `vbytes`. When `fee_per_vbyte` is at or near the relay minimum, the actual transaction falls below the minimum relay fee and is rejected/dropped by Bitcoin nodes' mempool policy — it can never confirm.
- The `TooLargeTransaction` check at line 241 uses `weight` which likewise omits the data output, marginally understating the standardness check.

### Impact Explanation
Any payout/forwarding transaction that carries a `data` payload is broadcast with a lower effective fee rate than the scheduler requested, and can be made entirely non-relayable when the configured rate is near the relay minimum. The UTXOs consumed by that `SignableTransaction` are then locked in an unconfirmable transaction until the coordinator abandons it and funds a fresh signing round over a corrected transaction — funds scheduled for payment are effectively not spendable for the duration, and repeated data-bearing transactions amplify this into persistent payout stall. This is an incorrect fee formula reachable purely through transaction data that causes a `SignableTransaction` to be constructed with `data: Some(..)`.

### Likelihood Explanation
`data` is a caller-supplied field of up to 80 bytes (checked at line 171) attached via `OP_RETURN`; in Serai's processor flow, transaction data accompanying payments/forwards is user-influenced (it is the same mechanism by which `extract_serai_data` carries instructions on the deposit side). The bug triggers deterministically on every construction with `data.is_some()` — no race or special conditions needed. Exploitation requires no collusion or privileged position beyond causing a data-bearing payout to be scheduled at a low fee rate.

### Recommendation
Include the data output in the weight/vbytes accounting: either pass the already-built `tx_outs` (or the data length) into `calculate_weight_vbytes`, or build the candidate transaction from the final `tx_outs` list including the `OP_RETURN` output — for both the non-change and `fee_with_change` calculations — so `needed_fee`, `TooLowFee`, and `TooLargeTransaction` reflect the transaction that will actually be signed.

### Proof of Concept
Conceptual, from the code in `networks/bitcoin/src/wallet/send.rs`:

```rust
// inputs worth 100_000 sats, one payment, 80 bytes of data, fee_per_vbyte at relay minimum
let tx = SignableTransaction::new(
  vec![received_output],                    // one ReceivedOutput
  &[(payment_script, 50_000)],
  None,
  Some(vec![0xaa; 80]),                     // OP_RETURN output added to tx_outs
  fee_per_vbyte,                            // == DEFAULT_MIN_RELAY_TX_FEE rate
).unwrap();

// tx.needed_fee() == fee_per_vbyte * vbytes(tx without OP_RETURN)
// tx.transaction().output contains the extra ~91-byte OP_RETURN output
// actual fee rate = needed_fee / actual_vsize < min relay fee
// => node rejects on send_raw_transaction; inputs unspendable in this tx
```

The discrepancy is directly visible: `tx_outs` (used in the final `Transaction`) contains the OP_RETURN output pushed at lines 194–202, while `calculate_weight_vbytes` at line 204 only receives `payments`, so `needed_fee` and the `TooLowFee`/`TooLargeTransaction` checks are computed for a strictly smaller transaction than the one produced.
