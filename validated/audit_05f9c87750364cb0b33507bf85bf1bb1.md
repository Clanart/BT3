### Title
Unchecked `uint64` multiplication in `multiplierGasMeter.adjustGas` can silently overflow and wrap, corrupting Cosmos gas metering - (File: sei-cosmos/store/types/gas.go)

### Summary
`multiplierGasMeter.adjustGas` (and the identical logic in `infiniteMultiplierGasMeter.adjustGas`) computes `original * g.multiplierNumerator / g.multiplierDenominator` using native Go `uint64` arithmetic with no overflow check, exactly mirroring the reported pattern of `RATE_DECIMALS_MULTIPLIER * tokenAmount() / duration` in an `unchecked` Solidity block: a multiply-then-divide that can silently wrap around the integer's range instead of reverting/panicking.

### Finding Description
`Gas` is defined as `uint64` [1](#0-0) . The multiplier gas meter adjusts every gas amount before delegating to the base meter: [2](#0-1) 

This mirrors the audited bug class exactly: `original * multiplierNumerator` is computed with plain Go integer multiplication, which wraps silently on overflow instead of panicking (Go does not check for overflow on native integer types, just like Solidity's `unchecked` block does not). The result of that (possibly wrapped) product is then divided by `multiplierDenominator`, further obscuring the corruption — matching the `RATE_DECIMALS_MULTIPLIER * tokenAmount() / duration` pattern from the report, where multiply-then-divide in unchecked context loses correctness silently instead of reverting.

By contrast, note that the plain `basicGasMeter.ConsumeGas` explicitly guards against overflow using `addUint64Overflow` and panics with `ErrorGasOverflow` [3](#0-2) , showing the codebase is aware overflow safety matters for gas accounting — yet `adjustGas`'s multiplication has no equivalent protection before the (already-corrupted) result is passed into that guarded addition.

This multiplier meter is on the ante-handler path for every Cosmos transaction: `SetGasMeter` constructs it directly from `CosmosGasMultiplierNumerator`/`Denominator` chain params and the transaction's `gasLimit` [4](#0-3) , and it's also used pervasively for EVM/precompile gas conversion via `NewGasMeterWithMultiplier` / `NewInfiniteGasMeterWithMultiplier` [5](#0-4) .

### Impact Explanation
For overflow of `original * multiplierNumerator` to occur, `original` (a per-operation gas cost, e.g. a KVStore read/write cost or an EVM-derived gas amount) would need to be extremely large (on the order of `2^64 / multiplierNumerator`). Individual gas-consuming operations in the codebase (`KVGasConfig`, `TransientGasConfig`) are small constants [6](#0-5) , and `ConsumeGas` is invoked with the running/limit-bounded gas amount, not attacker-supplied raw magnitudes, so triggering a genuine `uint64` overflow through this exact path in production configurations is not evidently reachable with realistic multiplier and gas-limit values. I could not find a code path where `amount` passed into `ConsumeGas`/`adjustGas` is a value large enough (close to `math.MaxUint64`) to trigger the overflow under normal or even adversarial single-transaction gas limits, since gas limits are bounded by consensus block gas parameters well below `2^64`.

### Likelihood Explanation
Low/unproven. Unlike the original report where `tokenAmount()` is a fully attacker-controlled `uint256` field that can reach values on the order of `2^256`, here `original` (the gas amount) is bounded by protocol-level gas limits and cost tables that are many orders of magnitude smaller than `uint64.max / multiplierNumerator` under any observed configuration. I was not able to confirm a code path allowing an unprivileged transaction sender to force `original` (or `multiplierNumerator`) to values large enough to overflow `uint64` within this function.

### Recommendation
As a defense-in-depth measure, add explicit overflow checking to `adjustGas` in `sei-cosmos/store/types/gas.go` (mirroring the existing `addUint64Overflow` pattern used elsewhere in the same file) so that a multiplication overflow panics with `ErrorGasOverflow` rather than silently wrapping, consistent with the rest of the gas-accounting code's safety posture.

### Proof of Concept
Not constructible with currently reachable inputs: I was unable to identify a caller that supplies a `Gas` (`uint64`) value to `ConsumeGas`/`adjustGas` large enough (approaching `2^64 / multiplierNumerator`) under realistic or maximum protocol gas-limit/multiplier configurations, so this analog could not be validated as an exploitable finding within the current call graph — it is reported as a structural code-pattern match to the audited bug class rather than a confirmed exploitable vulnerability.

func (g *basicGasMeter) ConsumeGas(amount Gas, descriptor string) {
	g.lock.Lock()
	defer g.lock.Unlock()

	var overflow bool
	g.consumed, overflow = addUint64Overflow(g.consumed, amount)
	if overflow {
		g.consumed = math.MaxUint64
		g.incrGasExceededCounter("overflow", descriptor)
		panic(ErrorGasOverflow{descriptor})
	}
	if g.consumed > g.limit {
		g.incrGasExceededCounter("out_of_gas", descriptor)
		panic(ErrorOutOfGas{descriptor})
	}
}

// Helpers for setting gas meter with parent ctx multiplier
func NewGasMeterWithMultiplier(ctx Context, limit uint64) GasMeter {
	if ctx.GasMeter() == nil {
		return NewGasMeter(limit, 1, 1)
	}
	n, d := ctx.GasMeter().Multiplier()
	return types.NewMultiplierGasMeter(limit, n, d)
}

func NewInfiniteGasMeterWithMultiplier(ctx Context) GasMeter {
	if ctx.GasMeter() == nil {
		return NewInfiniteGasMeter(1, 1)
	}
	n, d := ctx.GasMeter().Multiplier()
	return types.NewInfiniteMultiplierGasMeter(n, d)
}
