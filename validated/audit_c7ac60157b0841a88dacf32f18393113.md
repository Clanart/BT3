## Analog identified: sibling-directory bypass in `resolveWithin`'s containment check

### Title
Path-containment check in `resolveWithin` uses a raw `String.startsWith` prefix test, allowing sibling-directory escape - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` is Desktop's central guard against path traversal/symlink escape, used to safely join an attacker/data-controlled relative path segment (`file.path`, a deep-link `filepath`, etc.) onto a trusted root directory. Its final containment check is a naive string-prefix comparison, the same class of bug as the ULTI report's broken numeric-bound check: a boundary comparison that "looks correct" in the common case but fails to correctly delimit the boundary, letting attacker-influenced input slip past the guard.

### Finding Description
The core logic is: [1](#0-0) 

```
  const resolved = resolve(normalizedRoot, normalizedRelative)
  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)
  return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` does not respect path boundaries. If `realRoot` is, e.g., `/Users/victim/Documents/GitHub/myrepo` (no trailing separator — `path.resolve`/`normalize` strip it), then any path that shares that literal string prefix — such as `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa` or `/Users/victim/Documents/GitHub/myrepo.bak/config` — will also satisfy `realResolved.startsWith(realRoot)` even though it lies entirely **outside** the intended root directory. A correct containment check must additionally verify that the character immediately following `realRoot` in `realResolved` is the path separator (or that `realResolved === realRoot`).

This is exactly analogous to the ULTI bug class: a threshold/boundary comparison (`10000 - MAX_SWAP_SLIPPAGE_BPS` vs. `minUltiAmount`) that appears to enforce a safety bound but is subtly miscalibrated, letting a value cross the intended boundary undetected. Here the "boundary" is a filesystem directory edge, and the miscalibration is the missing separator check after `startsWith`.

`resolveWithin` is Desktop's canonical safety primitive and is called from at least three attacker-reachable/data-driven paths:
- `app/src/ui/dispatcher/dispatcher.ts` (`openRepositoryFromUrl`) — resolves a `filepath` query parameter taken from an `x-github-client://openRepo/...` deep link (`parseAppURL`, `app/src/lib/parse-app-url.ts`) before calling `shell.showItemInFolder(resolved)`. [2](#0-1) 
- `app/src/lib/copilot-conflict-context.ts` (`buildConflictContext`) — resolves each conflicted file's `file.path` before reading its contents and sending them to the Copilot conflict-resolution model. [3](#0-2) 
- `app/src/lib/stores/app-store.ts` — another call site relying on the same guarantee.

### Impact Explanation
If an attacker can arrange for the resolved sibling path to exist and be named such that it shares a prefix with the current repository's real path (e.g., cloning repositories with predictable/sequential names into the same parent directory, which GitHub Desktop does by default — `myrepo`, then a maliciously suggested clone folder name like `myrepo-2` or a repo the user is tricked into cloning next to an existing one), `resolveWithin` will incorrectly treat files in that sibling directory as "inside" the trusted repository. Depending on the call site this can result in:
- Reading arbitrary files outside the intended repository and exfiltrating their contents to the Copilot API (`buildConflictContext` path) — a credential/secret-exfiltration primitive.
- Using `shell.showItemInFolder` to reveal/interact with files outside the repo via a crafted deep link.

This matches the "Valid Impact" criteria (file read outside the repo, controlled via a deep link or a fetched/cloned repository's conflict content) without requiring local access, admin rights, or social engineering beyond normal app usage (clicking a link, resolving a merge conflict).

### Likelihood Explanation
Exploitation requires the resolved path to traverse out of the root and back into an existing, attacker-predictable sibling path — this is a real but constrained precondition (a same-named/prefixed sibling directory must exist on disk). This is comparable in likelihood framing to the original report's "Medium" rating: the flaw is real and the guard is genuinely broken, but a specific environmental condition (sibling directory naming collision) is needed to turn it into a full escape, similar to how the original bug required a second, independent miscalculation to become exploitable.

### Recommendation
Fix the containment check to enforce a proper boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests specifically for sibling-directory names that share a prefix with the root (e.g. root `.../myrepo` vs. resolved `.../myrepo-evil/secret`), mirroring the existing symlink-escape tests in `app/test/unit/path-test.ts`.

### Proof of Concept
1. Root: `/tmp/path-test/myrepo` (a real repository directory).
2. Sibling: `/tmp/path-test/myrepo-evil/secret.txt` (created on disk, e.g. by a previous clone or by the OS).
3. Call `resolveWithin('/tmp/path-test/myrepo', '../myrepo-evil/secret.txt')`.
4. Trace through `_resolveWithin` (`app/src/lib/path.ts:36-72`):
   - `resolved = path.resolve('/tmp/path-test/myrepo', '../myrepo-evil/secret.txt')` → `/tmp/path-test/myrepo-evil/secret.txt`
   - `realRoot = '/tmp/path-test/myrepo'`, `realResolved = '/tmp/path-test/myrepo-evil/secret.txt'`
   - `realResolved.startsWith(realRoot)` → `true` (string prefix match), so the function returns the out-of-root path instead of `null`.
5. This can be triggered end-to-end through `buildConflictContext` if a conflicted file entry's `path`/`oldPath` can be made to contain a `../` segment resolving into a sibling directory, or through the `filepath` parameter of an `x-github-client://openRepo/...` deep link handled in `dispatcher.ts`.

Note: I was not able to fully verify, from the indexed code alone, whether git's own tree/status parsing in this fork ever yields a `file.path`/`oldPath` containing `../` segments (git normally rejects such tree entries), so the conflict-context call site's exploitability depends on that additional (unverified) precondition. The `path.ts` boundary flaw itself, however, is confirmed directly from the source shown above.
