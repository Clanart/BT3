## Finding

The Connext bug pattern (swallowing an external‑call failure and continuing execution while leaving converted funds "in limbo") has a direct analog in the Cosmos EVM `x/erc20` IBC callback path.

### Title
Permanent loss of user funds when native‑ERC20 reconversion fails during IBC timeout/error‑ack processing - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
When an ICS20 transfer of a coin backed by a "native ERC20" token pair times out or receives an error acknowledgement, `OnTimeoutPacket`/`OnAcknowledgementPacket` call `ConvertCoinToERC20FromPacket`, which tries to convert the refunded bank coin back into its ERC20 representation via `ConvertCoinNativeERC20`. That function escrows the sender's coins into the module account *before* attempting the EVM `transfer` call that unescrows the corresponding tokens. If the EVM call fails (a scenario the code's own doc comments acknowledge as expected — e.g. a self‑destructed ERC20 contract), the error is swallowed by the caller, which emits an event and returns `nil`. Because Cosmos SDK does not automatically roll back state written earlier in a call unless an error is ultimately propagated to the message router, the already‑escrowed coins remain stuck in the `x/erc20` module account forever — never burned (burn only occurs after a successful transfer) and never returned to the sender.

### Finding Description [1](#0-0) 
In `ConvertCoinNativeERC20`, coins are escrowed from the sender to the module account first: [2](#0-1) 
Only after a successful EVM transfer are the escrowed coins burned: [3](#0-2) 

The IBC callback that invokes this function on timeout/error‑ack explicitly documents that the EVM call can fail (e.g. self‑destructed contract) and, in that case, simply logs an event and returns `nil`, treating the whole packet‑lifecycle callback as successful: [4](#0-3) 

The doc comment states the intended fallback behavior is that "the user receives the corresponding bank token from the TokenPair instead" — i.e., the coin should remain untouched with the sender. However, the actual code path in `ConvertCoinNativeERC20` already moves the coin out of the sender's account into the module account (`SendCoinsFromAccountToModule`) before the EVM call that can fail, so the documented fallback ("user keeps the bank coin") is violated: the coin is neither with the sender, nor burned, nor delivered as ERC20 — it is permanently trapped in the `x/erc20` module account. Unlike `ConvertERC20`/`ConvertCoin`, which pre‑check `acc.HasCodeHash()` and delete the token pair before touching balances when a contract is self‑destructed, `ConvertCoinToERC20FromPacket` performs no such pre‑check before calling `ConvertCoinNativeERC20`. [5](#0-4) 

### Impact Explanation
This satisfies the Critical "permanent freezing/locking of user funds" impact class: an unprivileged user's escrowed IBC funds are irrecoverably trapped in a module account. The user cannot retry (their coin balance is gone, not in ERC20 form as documented, and not in bank form either), and there is no code path to reclaim the trapped module‑account balance.

### Likelihood Explanation
The trigger conditions are realistic and reachable by an ordinary user/relayer flow: a native ERC20 token pair can become non‑functional (self‑destructed contract, paused/blocked transfer, revert on transfer to a blacklisted address, insufficient module‑held token balance from prior conversions) — precisely the conditions the code comments themselves anticipate ("self-destructed ERC20 contract or an invalid function"). Any IBC transfer of that denom that times out or receives an error acknowledgement will hit this path.

### Recommendation
Before escrowing coins in `ConvertCoinNativeERC20` (or specifically in the packet‑driven reconversion path), verify the ERC20 contract is still valid/functional (mirroring the `acc.HasCodeHash()` check done in `ConvertERC20`/`ConvertCoin`), and/or restructure `ConvertCoinNativeERC20` so the escrow step and the EVM transfer step are atomic — i.e., only commit the escrow if the EVM transfer succeeds, or execute the EVM call first and only escrow/burn afterward. At minimum, `ConvertCoinToERC20FromPacket` should not silently swallow the error if `ConvertCoinNativeERC20` has already mutated sender balances; it must ensure the sender genuinely retains the bank coin as documented, not merely emit a telemetry event while funds sit in the module account.

### Proof of Concept
1. Register a native ERC20 token pair for contract `C`.
2. User converts some tokens via `MsgConvertERC20`, then sends the resulting bank coin over IBC (`MsgTransfer`).
3. Before the packet resolves, self‑destruct `C` (or otherwise make its `transfer` function revert, e.g. via a pausable/blacklist token).
4. Let the packet time out or receive an error acknowledgement, invoking `OnTimeoutPacket`/`OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`.
5. `SendCoinsFromAccountToModule` succeeds (coin moves sender → `x/erc20` module account); the subsequent `CallEVM("transfer", …)` fails because `C` is self‑destructed.
6. `ConvertCoinNativeERC20` returns an error; `ConvertCoinToERC20FromPacket` swallows it, emits `EventTypeFailedConvertERC20`, and returns `nil`.
7. Final state: sender's bank balance is diminished, the coin was never burned, no ERC20 tokens were delivered — the amount is permanently stuck in the `x/erc20` module account with no recovery mechanism.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}

// ConvertCoinToERC20FromPacket converts the IBC coin to ERC20 after refunding the sender
// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}
