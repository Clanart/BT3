### Title
`git clone --recursive` explicitly disables Git's clone-protection safeguard - (File: `app/src/lib/git/clone.ts`)

### Summary
`app/src/lib/git/clone.ts` builds the environment for every `git clone` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while running `clone --recursive` against an attacker-supplied URL. [1](#0-0)  This mirrors the report's underlying bug class exactly: a security-relevant parameter that guards against a dangerous state is force-set to the "disabled/zero" value instead of being validated or left to Git's own safe default, and the surrounding code has no check to prevent or warn about this.

### Finding Description
The `clone()` function accepts an arbitrary, attacker-influenced `url` (it is invoked directly with content from GitHub API clone URLs, CLI `--cli-clone` arguments, and `x-github-client://openRepo/<url>` deep links routed through `parseAppURL`/`openOrCloneRepository`). [2](#0-1) [3](#0-2)  Before shelling out to `git`, it builds an env object that always includes `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, and then runs `clone --recursive` (i.e. submodules are followed automatically): [4](#0-3) 

`GIT_CLONE_PROTECTION_ACTIVE` is a real Git environment variable that upstream Git added to distinguish "we are inside an in-progress clone" so that Git's internal defenses (which reject risky repository states such as symlinked `.git` directories, embedded configuration that could redirect hooks, or nested repository structures encountered during `--recursive` submodule population) can decide whether to apply. Deliberately forcing this flag to `'false'` for every single clone means Desktop is telling Git "the clone-protection context is not active" instead of letting Git determine and apply that protection itself. Because this happens for a URL an attacker fully controls (any git host serving a clone, including nested submodule URLs discovered during the recursive clone), it removes a defense-in-depth guard that specifically exists to stop malicious repository content encountered mid-clone from causing unsafe behavior (e.g. from crafted submodule trees) — the same "attacker controls a cloned/fetched repository" primitive called out in the impact criteria.

Notably, other parts of this same file show the developers are otherwise careful about hardening the clone path — e.g. `isClonePathSensitive()` guards against path-traversal into `~/.ssh`, `~/.gnupg`, etc. [5](#0-4)  — which makes the unconditional disabling of `GIT_CLONE_PROTECTION_ACTIVE` stand out as an inconsistency: one class of risk (destination path) is checked, while a Git-native safety toggle for the clone operation itself is unconditionally turned off with no compensating check.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` suppresses any of Git's internal clone-time protections (as its name and Git's own use of the variable suggest), then cloning or recursively pulling in submodules from an attacker-controlled repository could bypass a defense Git otherwise relies on during `--recursive` operations, potentially resulting in unsafe repository states being accepted (e.g., through crafted submodule/`.git` structures) that Git would otherwise reject. This lines up with the valid-impact category "attacker controls a cloned/fetched repository ... result is code execution, file write or read outside the repo."

### Likelihood Explanation
Likelihood is high in terms of reachability: every clone in Desktop (via UI clone dialog, CLI `--cli-clone`, and the `x-github-client://openRepo/<url>` deep link) passes through this exact code path with `--recursive` and the disabled protection flag, and the URL (including any submodule URLs subsequently resolved) is fully attacker-influenced content in the deep-link/clone-URL scenario. However, I could not fully verify from the available codebase context alone the precise upstream Git semantics that `GIT_CLONE_PROTECTION_ACTIVE=false` disables in the specific Git/dugite version vendored by this app, nor find an inline comment in this repo explaining the rationale for setting it to `'false'`. This should be confirmed against the vendored Git version's source/release notes before treating this as a confirmed exploitable regression.

### Recommendation
Do not unconditionally force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Either omit the variable and let Git apply its own default in-clone protection semantics, or explicitly document (with a reference to the corresponding Git security fix) why disabling it is safe in this context, and add a regression test asserting protected behavior is preserved when cloning a repository containing a submodule with a crafted/symlinked `.git` directory.

### Proof of Concept
1. Register/observe that Desktop handles the `x-github-client://openRepo/<url>` protocol via `parseAppURL` → `dispatchURLAction` → `openOrCloneRepository(url)` → clone popup / `clone()`. [2](#0-1) [3](#0-2) 
2. Host a malicious Git repository whose tree contains a submodule entry crafted to abuse repository-state protections that Git's clone-protection mechanism is designed to reject during `--recursive` submodule population.
3. Send a victim a link such as `x-github-client://openRepo/https://attacker.example/evil-repo`, or have them clone `https://attacker.example/evil-repo` directly through the normal Clone Repository dialog.
4. Because `clone()` always runs with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and `--recursive`, verify (against the specific vendored Git version) whether the crafted submodule content is processed in a way that Git's protection would otherwise have blocked. [1](#0-0) 

Confirming step 4 conclusively requires checking the exact vendored `dugite`/Git version's handling of `GIT_CLONE_PROTECTION_ACTIVE`, which I was unable to do from the indexed codebase alone.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
