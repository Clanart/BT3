### Title
PedPoP returns a blame proof containing an ECDH shared key before verifying message authenticity - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary

A malicious DKG participant can cause an honest recipient to emit an `EncryptionKeyProof` for an ephemeral encryption key copied from another participant’s encrypted share. Because `calculate_share` returns that proof immediately when the decrypted bytes are not a canonical scalar, it bypasses the batched proof-of-possession failure path that would normally suppress the blame proof. [1](#0-0) 

### Finding Description

`Encryption::decrypt` queues the sender’s per-message Schnorr proof for batch verification, but immediately computes `self.enc_key * msg.key`, decrypts the ciphertext, and returns an `EncryptionKeyProof` containing that ECDH point. [2](#0-1) 

`KeyMachine::calculate_share` then deserializes the decrypted bytes before the batch verifier checks the queued proof-of-possession; if deserialization fails, it returns `InvalidShare` with `blame: Some(blame)`. [3](#0-2) 

Only the later batch-failure path maps a failed decryption proof to `blame: None`; the earlier scalar-deserialization error therefore bypasses that protection. [4](#0-3) 

The disclosed proof is sufficient to decrypt any other ciphertext encrypted with the same recipient/key pair: `decrypt_with_proof` verifies that `proof.key` is the ECDH result for `msg.key` and the recipient’s registered encryption key, then uses `proof.key` to derive the cipher. [5](#0-4) 

The cipher derives its ChaCha20 key by hashing the serialized ECDH point, so disclosure of `proof.key` is equivalent to disclosure of the message-decryption secret. [6](#0-5) 

### Impact Explanation

An attacker who observes an honest encrypted share can copy its ephemeral `msg.key`, submit malformed ciphertext under their own participant ID, and cause the victim to return a valid proof revealing `victim_enc_key * copied_msg_key`. When that proof is propagated for blame, the attacker can derive the cipher and decrypt the captured honest share, recovering another participant’s secret contribution. [7](#0-6) 

The returned `EncryptionKeyProof` serializes the ECDH point directly as its first field, making the shared secret available to anyone receiving the blame proof. [8](#0-7) 

### Likelihood Explanation

The attacker only needs to supply a syntactically valid `EncryptedMessage` under their own participant ID and arrange for the resulting blame proof to be returned or published, which is the intended purpose of the blame mechanism. [9](#0-8) 

For scalar fields whose canonical encodings occupy substantially less than the full byte range, such as the 253-bit Curve25519 scalar, randomly decrypted ciphertext bytes are non-canonical with high probability, making the early error path easy to reach. [3](#0-2) 

### Recommendation

Do not attach an `EncryptionKeyProof` to a scalar-deserialization failure until the associated proof-of-possession has been verified. In particular, verify the queued `BatchId::Decryption` statements before returning `Some(blame)` for malformed plaintext, or make `InvalidShare` use `blame: None` whenever the message’s PoP has not already been established as valid. [10](#0-9) 

### Proof of Concept

Conceptually, the attacker captures `alice_to_bob`, copies its `key` field into a malformed message attributed to the attacker, and chooses ciphertext bytes that decrypt to a non-canonical scalar:

```rust
// Serialized EncryptedMessage layout:
// copied_key || syntactically_valid_but_invalid_pop || malformed_ciphertext
let forged_bytes = [
  alice_to_bob.key_bytes(),
  generator_bytes,       // Canonical R
  zero_scalar_bytes,     // Canonical s; the resulting PoP is invalid
  &[0xff; SCALAR_BYTES], // Ciphertext selected to deserialize incorrectly
].concat();

let forged = EncryptedMessage::<C, SecretShare<C::F>>::read(
  &mut forged_bytes.as_slice(),
  params,
)?;

shares.insert(eve_participant, forged);
let result = bob_key_machine.calculate_share(&mut rng, shares);
```

When the forged ciphertext decrypts to non-canonical scalar bytes, `result` is `InvalidShare { participant: eve, blame: Some(proof) }`. The attacker extracts `proof.key`, derives the same ChaCha20 stream used by `cipher`, applies it to the captured honest ciphertext, and decodes the resulting scalar as Alice’s share.   // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
