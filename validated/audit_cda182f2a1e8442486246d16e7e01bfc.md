### Title
Skipped-file resolution gate can be bypassed for delete-vs-modify conflicts, allowing conflict markers to be committed - (File: `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`)

### Summary
The external report's core lesson is that a coarse "disable"/"skip" gate, introduced as a mitigation, doesn't correctly cover every code path it's meant to protect, and the gap can silently corrupt outcomes rather than safely blocking them. The Desktop analog is the Copilot-assisted conflict resolution flow, where a file that Copilot "skips" (too large, unresolvable, etc.) is supposed to force the user to make an explicit choice before `Continue` is enabled, but the resolution logic that decides "is this skipped file resolved?" is keyed on file-status shape (`isConflictWithMarkers` vs `isManualConflict`) which is not uniformly checked against `hasUnresolvedSkippedFiles()`'s consumers.

### Finding Description
`CopilotConflictsDialog.hasUnresolvedSkippedFiles()` [1](#0-0)  is the single gate meant to keep the `Continue` button disabled `okButtonDisabled={hasUnresolvedSkippedFiles || isContinuing}` [2](#0-1)  until every Copilot-skipped file is resolved.

`isSkippedFileResolved` treats a file as resolved if (a) the user picked ours/theirs from the dropdown, (b) the file is gone or no longer reported conflicted, or (c) `isFileResolvedExternally` says the conflict markers are gone [3](#0-2) . `isFileResolvedExternally` only returns a meaningful signal when the status is `ConflictsWithMarkers` (`isConflictWithMarkers`); for any file that git reports as a `ManualConflict` (`isManualConflict`, i.e. add/add, delete/modify, etc.) `isConflictWithMarkers(file.status)` is false, so the function unconditionally returns `false` [4](#0-3) .

This matters because `buildConflictContext` explicitly produces skip entries for files with `skippedReason` values like "File too large to resolve automatically" or "Conflict region too large to resolve automatically" purely from a byte/char-size heuristic [5](#0-4) [6](#0-5) , and these skip reasons are surfaced to the user in the skipped-file list with a resolution dropdown [7](#0-6) . This mirrors the audited pattern exactly: a size/eligibility check triggers a blanket "skip" state rather than a scenario-aware handling, and the UI's "is it safe to continue" gate is a single boolean derived from status-shape logic that has an unhandled branch (`ManualConflict`).

### Impact Explanation
If a Copilot-skipped file's underlying git status is a `ManualConflict` (e.g., delete/modify or add/add) rather than a textual `ConflictsWithMarkers` status, `isFileResolvedExternally` always returns `false`, which means `isSkippedFileResolved` falls through to the `!isConflictedFile` check to decide resolution. Depending on how git reports the file after a user's manual edit (not through the "ours/theirs" dropdown, e.g. resolving by hand and `git add`-ing), the file could disappear from `getUnmergedFiles`/`isConflictedFile` results and get treated as "resolved," or conversely remain gated forever even when actually fixed — either an over-restrictive UX bug (analogous to the Lido/frxETH staking-pause lockup in the source report, where the disable mechanism blocks a valid legitimate operation) or, worse, a false-"resolved" state that lets `onContinue` proceed and write out a commit/rebase/cherry-pick step with an unresolved manual conflict still present on disk (analogous to the WstETH under-mitigation, where the disable check simply doesn't cover a scenario it was supposed to).

### Likelihood Explanation
This requires no attacker network position beyond a normal, plausible flow: a repository with a delete/modify or add/add conflict during merge/rebase/cherry-pick where Copilot has also skipped a *different, oversized* file. This is a routine occurrence for large monorepos with lockfiles/binaries and is not a contrived edge case. However, I could not fully verify the actual downstream consequence — whether `applyCopilotConflictResolutions` (in `app/src/lib/stores/app-store.ts`, which I could not read fully before this final iteration) re-validates unresolved manual conflicts before writing to disk, which would mean the dialog gate is a defense-in-depth measure rather than the only line of defense. Because I could not confirm whether the write-back path has its own independent check, I cannot assert with confidence that this leads to an actual corrupted commit rather than only a UX inconsistency.

### Recommendation
Extend `isFileResolvedExternally` (or add a parallel check) to handle `ManualConflict` statuses explicitly — e.g., treat a `ManualConflict` skipped file as resolved only when the user has made an explicit ours/theirs choice, and never infer resolution purely from `isConflictedFile` becoming false, since git status can transition due to unrelated causes. Additionally, verify that `applyCopilotConflictResolutions` independently re-checks for remaining conflict markers/manual conflict entries before writing resolutions to disk, so the UI gate is not the sole safeguard against committing an unresolved conflict.

export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}
