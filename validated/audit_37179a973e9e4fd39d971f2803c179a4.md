## Analysis

The bug-class analog exists in the **Tron variant** of the intent-settlement contract: [1](#0-0) . Although the file imports `SafeERC20` and declares `using SafeERC20 for IERC20;`, the escrow-redemption and dust-sweep paths bypass it entirely and use a raw low-level `.call` that only checks whether the *call itself* reverted — never decoding/validating the ABI-encoded `bool` return value that ERC20 `transfer` is supposed to return.

### Title
Unchecked ERC20 transfer return value causes silent settlement finalization with permanent fund loss - (`File: evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` on the Tron deployment finalize escrow settlement (decrementing `_orders`, setting `_filled[commitment]`, and emitting `EscrowReleased`/`EscrowRefunded`/`DustSwept`) based solely on whether the low-level `token.call(...)` did not revert, never checking the boolean returned by `transfer`. This is precisely the ERC20-non-conformance issue described in the external report: the standard does not require reverting on failure, so a token that returns `false` instead of reverting will be treated as a successful transfer.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

`success` is only `false` if the callee reverted or the call target has no code. If the token contract executes normally and simply returns `abi.encode(false)` (a fully spec-compliant behavior per ERC20, and explicitly the scenario the external report warns about), `success` is `true`, the decoded return payload is discarded, and the code proceeds to:
- decrement escrow accounting (`_orders[...] -= amount`),
- set `_filled[body.commitment] = beneficiary` unconditionally at the top of the function [3](#0-2) ,
- emit `EscrowReleased`/`EscrowRefunded` as if the payout succeeded.

The same pattern repeats in the fee-token payout inside the same function [4](#0-3)  and in the governance-triggered `SweepDust` handler [5](#0-4) .

Contrast with the main EVM `IntentGatewayV2` and `IntentsBase`, which consistently use `IERC20(token).safeTransfer(...)` / `safeTransferFrom(...)` and properly revert on a `false` return [6](#0-5) . The Tron file has regressed to unchecked raw calls despite importing `SafeERC20`, reintroducing exactly the vulnerability class the bug report flagged and that the team claims was fixed project-wide ("All calls to compliant ERC20s now check for return booleans").

### Impact Explanation
Because `_filled[body.commitment]` is set and escrow balances are decremented irrespective of whether tokens actually moved, a silently-failing (return-false, not-revert) ERC20 transfer results in:
- The solver/beneficiary receiving **no tokens**.
- The escrow record for that commitment being wiped out (`_orders[...] -= amount`, and `_filled` marked), so there is no retry path — `withdraw` cannot be invoked again for the same commitment (guarded by `_orders[...] == 0` check reverting with `UnknownOrder`) — permanently locking the escrowed funds inside the contract.
- `onGetResponse`/`onAccept` finalize as a normal success from Hyperbridge's perspective, so this false state (transfer succeeded) becomes the accepted outcome even though the actual balance movement never happened — a direct fund-loss/lock condition reachable by an unprivileged party simply by the escrowed token exhibiting non-reverting failure semantics.

### Likelihood Explanation
Likelihood depends on whether any token integrated into the Tron intent gateway can return `false` on transfer failure instead of reverting. This is common on TRC20/BEP20-style tokens historically (including USDT-like tokens on non-Ethereum chains), and the report itself is explicitly about this exact class of non-conformance. Given the shell/gateway administrator can list assets, exploitability is gated by asset listing, but any listed token with this property — or any token whose balance temporarily prevents a transfer (e.g., paused, blacklisted recipient) — turns an ordinary settlement/timeout/refund flow into permanent fund loss without any malicious actor being required.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used via `using SafeERC20 for IERC20;`), consistent with the rest of the codebase, so that both call failure and a `false` return value revert the transaction before escrow state is finalized.

### Proof of Concept
1. Register (or have escrowed) a non-standard ERC20/TRC20 token whose `transfer` returns `false` on failure rather than reverting (e.g., insufficient balance, paused, or blacklisted recipient), used as an order input token in `IntentGatewayV2` (Tron).
2. Trigger `onAccept` with `RequestKind.RedeemEscrow` (or `RefundEscrow`) for a commitment holding this token, or trigger `RequestKind.SweepDust`.
3. Inside `withdraw()`, `token.call(...)` returns `(true, abi.encode(false))` because the call itself doesn't revert.
4. `success == true` passes the `if (!success) revert TransferFailed();` check; the transfer never actually delivered tokens to `beneficiary`.
5. `_orders[body.commitment][token] -= amount;` executes, zeroing escrow accounting, and `_filled[body.commitment]` is already set — the commitment is now considered settled with `EscrowReleased`/`EscrowRefunded` emitted, but the beneficiary received nothing and the tokens remain stuck in the contract with no way to re-trigger payout for that commitment.
