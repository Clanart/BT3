### Title
Unsanitized tag names allow git argv/flag injection during push (e.g. `--upload-pack=`/`--receive-pack=`) - (File: `app/src/lib/git/push.ts`, `app/src/lib/stores/git-store.ts`)

### Summary
Tag names collected by `GitStore` (via `addTagToPush`/`storeTagsToPush`) are later spread directly into the `git push` argv in `app/src/lib/git/push.ts` with no `--` end-of-options marker and no check that a tag name does not start with `-`. Because git's own `check-ref-format` rules do **not** forbid a ref name that begins with a dash, a remote can legitimately expose (and the user can fetch) a tag such as `--upload-pack=./evil` or `--receive-pack=./evil`, which git will accept as a valid tag ref. When that tag is later included in a push, it is appended as a bare argv token rather than a ref, letting it be parsed by `git push` as a command-line option instead of a tag name.

### Finding Description
`GitStore.addTagToPush` stores an arbitrary tag-name string with no validation: [1](#0-0) 

That array (`this._tagsToPush`) is later handed unchanged into `pushRepo`/`push`: [2](#0-1) 

and in `push.ts` the tag list is spread straight into the `git push` argv, with no `--` separator preceding it to force git to treat subsequent tokens as positional refspecs rather than options: [3](#0-2) 

Separately, `fetchTagsToPush` derives "tags to push" by running a `git push --dry-run --follow-tags --porcelain` and parsing the resulting `refs/tags/<name>` lines verbatim, with only a leading `refs/tags/` prefix stripped — no character/format validation is applied to the extracted name: [4](#0-3) 

Git's `check-ref-format` rules (which govern what ref/tag names git will accept when fetching from a remote) do not prohibit a name beginning with `-`. This means a malicious remote can advertise a tag literally named `--upload-pack=...` or `--receive-pack=...`, which will be accepted as a valid local ref once fetched, later detected as "unpushed" by `fetchTagsToPush`, and stored via `addTagToPush`/`storeTagsToPush` without sanitization.

### Impact Explanation
If such a tag name reaches the `push` argv unguarded, git will interpret it as an option rather than a refspec. In particular `--receive-pack=<path>` instructs git to execute `<path>` as the "remote" program that receives the pushed pack — for `ssh://` or local/`file://` remotes this results in execution of an attacker-chosen (relative or absolute) path on the user's machine in the context of the GitHub Desktop process. Combined with a malicious commit that drops an executable script at a predictable path in the working tree, this is a path to local code execution triggered purely by fetching a hostile remote and performing a normal push — squarely within the "attacker controls a fetched repository/remote response" threat model in scope.

### Likelihood Explanation
Requires: (1) the user adds/fetches a remote controlled by the attacker (or a remote pointed at a local/file path, as with a malicious submodule), (2) that remote exposes a tag whose name is a git option flag, and (3) the app's tag-to-push flow (fetch → `fetchTagsToPush` → `addTagToPush`/`storeTagsToPush` → `push`) picks it up and pushes it. This is a multi-step but fully attacker-drivable chain requiring no unnatural user action beyond fetch/push, which are core, expected GitHub Desktop workflows.

### Recommendation
- In `app/src/lib/git/push.ts`, insert a literal `--` argument before appending `tagsToPush` (and before the branch refspec) to `args`, so git treats everything after it strictly as positional refspecs, not options.
- Additionally/alternatively, validate every tag name accepted into `_tagsToPush` (and returned by `fetchTagsToPush`) to reject any string starting with `-`, matching the general defensive pattern GitHub Desktop should use everywhere ref/branch/tag names derived from remote data are passed to git argv.

### Proof of Concept
1. Set up a bare "attacker" repository. Create a tag named `--upload-pack=/tmp/pwn.sh` (valid per `git check-ref-format`, since a leading dash is not disallowed) pointing at any commit, and add a benign script `pwn.sh` to that commit's tree.
2. In GitHub Desktop, clone/add this repository as a remote and fetch it (tags are fetched along).
3. Make a local commit and push. GitHub Desktop's `fetchTagsToPush` (`app/src/lib/git/tag.ts:86-134`) will surface `--upload-pack=/tmp/pwn.sh` as an "unpushed tag," which flows into `GitStore.addTagToPush`/`storeTagsToPush` (`app/src/lib/stores/git-store.ts:501-506`).
4. On the subsequent push, `push.ts` (`app/src/lib/git/push.ts:57-65`) spreads this string directly into the `git push` argv without a `--` guard, causing git to interpret it as the `--upload-pack`/`--receive-pack`-style option rather than a tag refspec, demonstrating argv injection.

**Caveat:** I confirmed the vulnerable sink (`push.ts`) and the unsanitized storage path (`addTagToPush`/`storeTagsToPush`) directly, but I was not able to fully re-verify within the available tool calls the exact internal call site in `git-store.ts` that feeds `fetchTagsToPush`'s remote-derived results into `addTagToPush` (grep confirmed both symbols exist in the same file with 12 combined matches, but I could not display that specific excerpt before running out of iterations). If that particular wiring differs from what's described (e.g., if `addTagToPush` is only reachable from the user-typed `create-tag-dialog.tsx` flow, which is validated by `RefNameTextBox`), the remote-fetched-tag attack path would need re-confirmation — the underlying `push.ts` argv-injection sink itself, however, is confirmed and unguarded regardless of the exact tag-name origin.
