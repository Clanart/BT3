### Title
Attacker-controlled participant count causes oversized allocation in `ThresholdKeys::read` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` trusts the serialized `n` participant count before validating the threshold parameters and immediately calls `Vec::with_capacity(n)` when the interpolation byte selects `Interpolation::Constant`. An attacker can therefore trigger an allocation of up to 65,535 field-element slots with only a valid curve identifier, three `u16` values, and one interpolation byte; no corresponding field-element data is required.

### Finding Description
The deserializer reads `t`, `n`, and participant index `i` directly from untrusted input [1](#0-0) . If the next byte is `0`, it executes `Vec::with_capacity(usize::from(n))` before parsing any coefficients [2](#0-1) . `ThresholdParams::new` is not invoked until after the interpolation vector, secret share, and all `n` verification shares have been processed [3](#0-2) . Consequently, `n = u16::MAX` produces an immediate request for 65,535 scalar slots—about 2 MiB for a 32-byte field element—even if the stream ends immediately afterward.

### Impact Explanation
An unprivileged party that can cause a service to deserialize attacker-controlled `ThresholdKeys` bytes can force large transient heap allocations from a very small request. Repeated requests can consume allocator capacity, increase memory fragmentation and GC/allocator pressure, and degrade or terminate the process when allocations fail. The allocation size is controlled solely by the serialized participant count and is not bounded by the actual bytes supplied.

### Likelihood Explanation
The attack requires a reachable call to `ThresholdKeys::read` on untrusted bytes for any in-scope `Ciphersuite`. Constructing the triggering input requires only the correct curve identifier and a few serialized fields, making exploitation inexpensive and repeatable.

### Recommendation
Do not allocate based on `n` before validating and bounding it. In `ThresholdKeys::read`:

1. Validate `ThresholdParams::new(t, n, i)` immediately after reading `t`, `n`, and `i`.
2. Replace `Vec::with_capacity(usize::from(n))` with incremental `push`es so short inputs cannot reserve `n` elements.
3. Enforce a protocol/deployment maximum participant count before deserialization work.
4. Prefer streaming parsers that fail on EOF before reserving attacker-specified capacity.

### Proof of Concept
The following input reaches the vulnerable allocation without supplying `n` scalar encodings:

```rust
// crypto/dkg/src/lib.rs
fn poc<C: dkg::Ciphersuite>() {
    let mut bytes = Vec::new();

    bytes.extend_from_slice(
        &u32::try_from(C::ID.len()).unwrap().to_le_bytes(),
    );
    bytes.extend_from_slice(C::ID);

    bytes.extend_from_slice(&1u16.to_le_bytes());          // t
    bytes.extend_from_slice(&u16::MAX.to_le_bytes());      // n = 65,535
    bytes.extend_from_slice(&1u16.to_le_bytes());          // i
    bytes.push(0);                                         // Constant interpolation

    // Executes Vec::with_capacity(65_535), then errors on EOF.
    let _ = dkg::ThresholdKeys::<C>::read(&mut bytes.as_slice());
}
```

The allocation occurs at `crypto/dkg/src/lib.rs:608`, while the first attempted scalar read is only at line 610 [4](#0-3) .
