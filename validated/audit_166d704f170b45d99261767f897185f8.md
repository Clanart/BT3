## Analysis Summary

The Starlette advisory's failed invariant is: **attacker-controlled string length flows directly into a quadratic-time parsing routine with no length bound**. Searching the protobuf codebase for the same invariant across JSON-parsing surfaces shows that Java's `JsonFormat` implementation already contains an explicit fix for exactly this bug class — a `MAX_NUMERIC_STRING_LENGTH` guard added specifically to stop `BigDecimal(String)`'s O(N²) behavior [1](#0-0)  validated by `testParserRejectOverlyLongNumericStrings` [2](#0-1) . That fix proves the maintainers treat "unbounded numeric-string length feeding a super-linear parser" as an in-scope ProtoJSON DoS class.

The Python runtime's equivalent public ProtoJSON parsing path does **not** carry the same guard.

### Title
Unbounded-length numeric strings in ProtoJSON parsing feed CPython's superlinear `int()`/`float()` conversion without a length bound — (File: `python/google/protobuf/json_format.py`)

### Summary
`json_format.Parse()` is a supported public ProtoJSON parsing API. For scalar integer/float fields, quoted numeric JSON string values are passed straight into `_ConvertInteger()` / `_ConvertFloat()`, which call Python's built-in `int(value)` / `float(value)` with no upper bound on the string's length [3](#0-2) [4](#0-3) . CPython's decimal-string-to-integer conversion is documented to be superlinear (quadratic-ish) for very long digit strings — the same underlying algorithmic hazard that motivated Java's `BigDecimal(String)` mitigation in this same repository. Java's own `JsonFormat.java` explicitly documents and caps this ("BigDecimal(String) has O(N^2) time complexity for N-digit strings ... allowing a DoS with a single long numeric JSON value") [1](#0-0) , but no equivalent `MAX_NUMERIC_STRING_LENGTH`-style check exists on the Python conversion path.

### Finding Description
`_ConvertScalarFieldValue()` dispatches integer/float typed fields to `_ConvertInteger` and `_ConvertFloat` [5](#0-4) . Both accept an attacker-supplied JSON string value of arbitrary length and pass it unmodified to `int(value)` or `float(value)`:

- `_ConvertInteger` calls `int(value)` directly on the untrusted string [6](#0-5) .
- `_ConvertFloat` calls `float(value)` directly on the untrusted string [7](#0-6) .

Neither function checks `len(value)` before conversion, unlike the sibling Java implementation which explicitly rejects any numeric string over 1000 characters *before* invoking the expensive parser [8](#0-7) . Field type ultimately being `int32`/`int64`/`float`/`double` is irrelevant to the cost of the conversion itself — the conversion routine must still scan/process the entire attacker-controlled string before any range check can reject it, exactly mirroring the Starlette pattern where the malformed/oversized input is fully processed by an unbounded algorithm before validation fails.

This directly transfers the external invariant: "the presence of a downstream bounds/range check does not protect against an upstream unbounded-cost parse of attacker length." Starlette validated ranges only *after* the O(N²) regex/merge step ran to completion; protobuf-Python validates numeric bounds only *after* `int()`/`float()` fully consumes the string.

### Impact Explanation
Any application that calls `google.protobuf.json_format.Parse()` on attacker-supplied ProtoJSON — a supported, common integration pattern (e.g., gRPC-gateway/REST-to-protobuf bridges, config ingestion) — can be driven into disproportionate CPU consumption per request by supplying a single scalar field with a very long digit string (e.g., `{"optionalInt32": "9999...(hundreds of thousands of digits)..."}`). This is a per-request CPU exhaustion vector consistent with CWE-400/CWE-407, matching the Starlette bug class. Severity depends on the CPython version/build in use (see Likelihood).

### Likelihood Explanation
CPython's `int(str)` conversion has historically exhibited superlinear behavior on very long digit strings (tracked upstream as CVE-2020-10735), and Python 3.11+ mitigates this globally via `sys.set_int_max_str_digits` (default limit ~4300 digits). No occurrence of `set_int_max_str_digits` or any protobuf-side length guard was found in this repository's Python sources, so protection is fully dependent on the *host interpreter's* default configuration rather than protobuf's own input validation — in contrast to Java, where the mitigation is explicit and self-contained inside `JsonFormat.java` regardless of the JDK version. On interpreters/configurations where the global digit limit is disabled or raised (a supported CPython configuration), the quadratic cost is fully reachable through the public `json_format.Parse` API with a single, boundedly-sized JSON payload.

### Recommendation
Add an explicit maximum numeric-string length check in `_ConvertInteger` and `_ConvertFloat` in `python/google/protobuf/json_format.py`, mirroring the Java fix's `MAX_NUMERIC_STRING_LENGTH` constant and rejecting oversized numeric strings with a `ParseError` before calling `int()`/`float()`. This removes protobuf's Python JSON parser's dependence on interpreter-level mitigations for this specific input-validation concern, consistent with the defense-in-depth approach already present in the Java runtime.

```python
def _ConvertInteger(value):
  """Convert an integer.

  Args:
    value: A scalar value to convert.

  Returns:
    The integer value.

  Raises:
    ParseError: If an integer couldn't be consumed.
  """
  if isinstance(value, float) and not value.is_integer():
    raise ParseError("Couldn't parse integer: {0}".format(value))

  if isinstance(value, str) and value.find(' ') != -1:
    raise ParseError('Couldn\'t parse integer: "{0}"'.format(value))

  if isinstance(value, bool):
    raise ParseError(
        'Bool value {0} is not acceptable for integer field'.format(value)
    )

  try:
    return int(value)
  except ValueError as e:
    # Attempt to parse as an integer-valued float.
    try:
      f = float(value)
    except ValueError:
      # Raise the original exception for the int parse.
      raise e  # pylint: disable=raise-missing-from
    if not f.is_integer():
      raise ParseError(
          'Couldn\'t parse non-integer string: "{0}"'.format(value)
      ) from e
    return int(f)
```

```python
def _ConvertFloat(value, field):

  if isinstance(value, float):
    if math.isnan(value):
      raise ParseError('Couldn\'t parse NaN, use quoted "NaN" instead')
    if math.isinf(value):
      if value > 0:
        raise ParseError(

        raise ParseError(
            "Couldn't parse -Infinity or value too small, "
```
