### Title
External party can send to Serai's internal Branch/Change/Forwarded scripts, causing deposits to be misclassified as non-External and credited to Serai rather than the sender - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Analogous to CVE-2022-4871 (untrusted `sort` argument interpreted as a control directive without validation), `Bitcoin::get_outputs` interprets an attacker-chosen output `script_pubkey` as a trusted classification signal: any output paying to any registered Scanner script is assigned an internal `OutputType` purely from the offset map, with no distinction between outputs Serai itself created and outputs an arbitrary external sender created.

### Finding Description
`Scanner::scan_transaction` matches outputs solely by `output.script_pubkey` against the `scripts` map (`networks/bitcoin/src/wallet/mod.rs:205`). `scanner()` in `processor/src/networks/bitcoin.rs:314-346` registers four scripts per key with *publicly derivable* offsets: `Scalar::ZERO` (External), `hash_to_F(KEY_DST, b"branch")`, `hash_to_F(KEY_DST, b"change")`, `hash_to_F(KEY_DST, b"forward")`. In `get_outputs` (`processor/src/networks/bitcoin.rs:686-700`), each scanned output is classified via `kinds[offset_repr_ref]`, and only `OutputType::External` outputs receive the deposit `data` extracted from the transaction's `InInstruction` (`processor/src/networks/bitcoin.rs:730-735`); outputs of kind Branch/Change/Forwarded are treated as Serai-internal operational outputs.

Because `BRANCH_OFFSET`, `CHANGE_OFFSET`, and `FORWARD_OFFSET` are deterministic `hash_to_F` values over a constant public DST and the group key is public, any unprivileged party can compute the branch/change/forward `p2tr_script_buf` scripts and send a normal Bitcoin transaction paying to them. The processor will accept that output as an internal output — an untrusted input (the on-chain `script_pubkey`) is "injected" into the classification logic and changes the accounting semantics of the deposit, exactly like the unsanitized `sort` parameter being injected into the query's `ORDER BY`.

### Impact Explanation
A deposit sent to the change or branch script is recorded with `kind != External`, so it never receives `output.data`/`presumed_origin` treatment as a user deposit and is instead folded into Serai's internal UTXO pool (used to fund burns/branches per `spec/processor/UTXO Management.md`). The sender's funds are reported as Serai-owned change/branch funds rather than a creditable deposit — funds are received that the depositor cannot claim, effectively donating/stealing the deposit into the multisig. Conversely, an attacker can deliberately create fake "Change"/"Branch" outputs to pollute the input-accumulation and burn-funding logic, influencing which inputs the scheduler treats as internal liquidity.

### Likelihood Explanation
The scripts are fully computable offline by anyone knowing the (public) multisig key; triggering only requires sending a standard Bitcoin transaction — the exact "Bitcoin transactions they send" reachability in scope. Medium likelihood: exploitation costs the attacker funds (or a confused depositor loses funds by sending to a derivable-but-valid Serai address), but the misclassification is deterministic and requires no privilege, and the polluted outputs flow into the scheduler as authentic internal outputs.

### Recommendation
Distinguish self-created outputs from externally created ones: e.g., require that Change/Branch/Forwarded-kind outputs appear in a transaction that also spends a known Serai input (as Serai's own change/branch outputs always do), or only emit kind != External for outpoints whose creating transaction was produced by the signing pipeline (tracked eventualities). Reject or flag external transactions paying to internal scripts rather than silently reclassifying them.

### Proof of Concept
```rust
// Attacker (unprivileged) with knowledge of the public group key `key`:
let scanner_offsets = {
    let mut s = Scanner::new(key).unwrap();
    s.register_offset(Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change"));
    s
};
// Compute the change script Serai uses internally:
let change_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change");
let mut change_offset_even = change_offset;
while p2tr_script_buf(key + (ProjectivePoint::GENERATOR * change_offset_even)).is_none() {
    change_offset_even += Scalar::ONE; // mirror register_offset's increment-until-even
}
let internal_script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * change_offset_even)).unwrap();

// Attacker broadcasts a tx paying `internal_script` with >= DUST sats.
// In get_outputs, scan_transaction matches it, kinds[offset] == OutputType::Change,
// the output is pushed without `data` and later treated as Serai's own change
// funding burns — the depositor's deposit is absorbed as internal funds.
```
Root cause: `scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) trusts `script_pubkey` alone, and `get_outputs` (`processor/src/networks/bitcoin.rs:686-735`) maps the resulting offset directly to an `OutputType` without checking that the transaction originated from Serai's own spending activity.
