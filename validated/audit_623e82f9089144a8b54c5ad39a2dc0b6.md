### Title
Uncommitted scanner state: `ram_outputs` pruned before `seen`/`latest_scanned_block` txn commits, allowing duplicate output crediting - ([File: processor/src/multisigs/scanner.rs](https://github.com/Kirstentat/serai--012/blob/main/processor/src/multisigs/scanner.rs))

### Summary

The Serai Bitcoin scanner keeps a two-layer state exactly analogous to ZetaChain's EVM-stateDB vs Cosmos-SDK split: a dirty in-RAM dedup set (`ram_outputs`, `ram_scanned`) and a committed database state (`seen` output IDs, `latest_scanned_block`). Like the ZetaChain bug, the dirty layer is mutated before — and independently of — the commit of the backing layer. `ack_block` removes output IDs from `ram_outputs` while holding the scanner lock, the lock is then released, and only afterwards does the caller commit the transaction that sets `seen` and `latest_scanned_block`. An output whose RAM entry was pruned but whose `seen` flag was never committed is indistinguishable from a fresh output on rescan — the same pattern as ZetaChain's precompile operating on stale balances before the dirty EVM state overwrote committed changes.

### Finding Description

In `Scanner::run`, each scanned output ID is inserted into the in-memory set `scanner.ram_outputs` at scan time (`processor/src/multisigs/scanner.rs:634-639`). The dedup check is `seen || scanner.ram_outputs.contains(&id)` — correctness requires that every output which has been emitted (but whose `seen` flag is not yet on disk) remains present in `ram_outputs`.

`ack_block` (`scanner.rs:322-355`) acquires the scanner via `long_term_acquire`, calls `ScannerDb::save_scanned_block(txn, number)` — which marks outputs `seen` inside a still-uncommitted `txn` — and immediately removes those IDs from `ram_outputs` (line 341). It then stores the held lock in `self.held_scanner`. The caller later invokes `release_lock()` and commits the txn *after* the write lock is relinquished (see the test flow, `processor/src/tests/scanner.rs:96-101`: `ack_block` → `release_lock` → `txn.commit()`).

The code itself acknowledges the invariant is broken:

```
// There's also no concern ram_outputs was pruned, yet seen wasn't set, as pruning
// from ram_outputs will acquire a write lock ... and during its holding of the
// write lock, it commits the transaction setting seen and the latest scanned block.
//
// This last case isn't true. Committing seen/latest_scanned_block happens after
// relinquishing the write lock.
// TODO2: Only update ram_outputs after committing the TXN in question.
```
(`processor/src/multisigs/scanner.rs:624-633`)

Because the prune happens inside the lock but the commit happens outside it, any rescan path that reads `seen` between `ram_outputs.remove` and `txn.commit()` sees stale state: `seen == false` and `ram_outputs` no longer contains the ID. Rescans are a normal, expected path — `new_scanner` in tests explicitly re-scans already-scanned blocks from disk state (`processor/src/tests/scanner.rs:92-94`), and the comments note rescanning from a prior block on reboot repopulates RAM. An attacker does not need to trigger the race directly: they only need to send a Bitcoin transaction paying a registered offset script (`Scanner::scan_transaction`/`register_offset`, `networks/bitcoin/src/wallet/mod.rs:180-214`), which any unprivileged party can do. The window is created entirely by the node's own commit ordering.

Two outcomes follow depending on where the output is re-observed:

- If the re-scan hits the dedup panic path (`panic!("scanned an output multiple times")`, `scanner.rs:636-638`) on a partially-consistent state, the scanner task dies — liveness loss on the deposit pipeline.
- If the RAM entry is pruned and `seen` is uncommitted (e.g., reboot or lock interleaving where the txn is dropped/reordered rather than committed), the output is re-emitted in a `ScannerEvent::Block`, delivered to the scheduler (`processor/src/multisigs/mod.rs:700-799`) as a new deposit — double-crediting funds that were received once, the same class as the ZetaChain double-spend.

### Impact Explanation

A Bitcoin deposit output can be reported to the multisig scheduler more than once. Downstream, emitted outputs feed `plans_from_block`/`prepare_send` and `scheduler.created_output`, so a duplicated output becomes spendable balance the multisig never actually received — enabling withdrawals funded by other deposits (a protocol-level double-spend). Alternatively the inconsistency surfaces as the `panic!("scanned an output multiple times")`, halting scanning. Both are reachable solely from an external Bitcoin transaction the attacker sends; no validator key, collusion, or RPC access is required.

### Likelihood Explanation

The race window is the gap between `release_lock` and `txn.commit()`, which the code comments confirm exists and is explicitly marked `TODO2`. It widens under reboots/crashes in that window and under concurrent ack/scan activity during multisig rotation (when `need_ack` throttling and `check_multisig_completed` interleave lock acquisitions). Likelihood is moderate: it requires an unlucky interleaving or restart, but no attacker privilege beyond sending an ordinary deposit transaction. Impact severity (double-credited deposits across a threshold multisig) keeps this at High/Medium rather than Low.

### Recommendation

Apply the `TODO2` already in the code: do not mutate `ram_outputs` in `ack_block` until after the transaction setting `seen` and `latest_scanned_block` has committed. Concretely, return the removed IDs (or stage them) from `ack_block`, commit the txn first, then prune `ram_outputs` — mirroring the ZetaChain fix of committing dirty state before the dependent action reads/writes committed state. Equivalently, make the `seen` check authoritative by committing `seen` inside the same critical section that removes the RAM entries.

### Proof of Concept

1. Register a key; scanner starts (`Scanner::new`, `processor/src/multisigs/scanner.rs:383-427`).
2. Attacker broadcasts a Bitcoin tx paying the key's P2TR script (or a registered offset script). `scan_transaction` matches on `script_pubkey` alone (`networks/bitcoin/src/wallet/mod.rs:199-213`), so no further privilege is needed.
3. Block is scanned; output ID inserted into `ram_outputs` (`scanner.rs:639`), `ScannerEvent::Block` emitted.
4. Processor calls `ack_block`: `save_scanned_block` writes `seen` into the uncommitted txn; `ram_outputs.remove(id)` executes (`scanner.rs:336-342`); lock is stored in `held_scanner`.
5. `release_lock()` is called; before `txn.commit()` completes (or the txn is dropped on crash), a rescan path re-evaluates the output: `ScannerDb::seen` returns false, `ram_outputs` lacks the ID → the output passes dedup and is re-emitted in a second `ScannerEvent::Block`, or the rescan hits `panic!("scanned an output multiple times")`.
6. The scheduler processes the duplicated output as an additional deposit in `plans_from_block`/`prepare_send`, crediting balance never received. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
