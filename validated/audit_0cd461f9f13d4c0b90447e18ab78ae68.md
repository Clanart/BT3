### Title
Duplicate DID recovery IDs allowed at DID creation lower the effective recovery threshold below `num_of_backup_ids_needed` - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
The report describes a lack of duplicate-entry checks in an initialization/setter function that populates a list used to compute a total, allowing an attacker/careless caller to inflate a derived value. The closest reachable analog in this codebase is the DID wallet's recovery-list ("backup_ids") mechanism: `DIDWallet.create_new_did_wallet` (and the puzzle-generation helpers that curry `backup_ids`/`num_of_backup_ids_needed` into the DID inner puzzle) never check that `backup_ids` contains unique DID identifiers, and `num_of_backup_ids_needed` is only checked to be `<= len(backup_ids)` (as a raw count), not `<= number of unique backup_ids`.

### Finding Description
`DIDInfo` stores `backup_ids: list[bytes32]` and `num_of_backup_ids_needed: uint64` with no invariant enforcing uniqueness of `backup_ids`. [1](#0-0) 

`DIDWallet.create_new_did_wallet` initializes `backup_ids=[]` and later callers/updaters (e.g. `create_new_did_wallet_from_coin_spend`, `find_lost_did` in `wallet_state_manager.py`) rebuild `backup_ids` directly from on-chain solution data without deduplication. [2](#0-1) 

The only sanity check present anywhere in the deserialization path is a raw count comparison, not a uniqueness check: [3](#0-2) 

The `backup_ids` list (and its curried hash) is what actually gets committed into the on-chain DID inner puzzle via `create_innerpuz` / `get_inner_puzhash_by_p2`, which simply hashes whatever list is provided: [4](#0-3) [5](#0-4) 

`num_of_backup_ids_needed` is the CLVM-enforced threshold of independent recovery-DID attestations needed to reconstitute/recover a DID's ownership. If the same DID id is inserted multiple times into `backup_ids` (either by user error at creation time in `create_new_did_wallet`/`generate_new_decentralised_id`, or through the recovery/import path in `deserialize_backup_data` and `create_new_did_wallet_from_coin_spend`, which rebuild the list straight from solution data), `len(backup_ids)` can be inflated while the number of *distinct* authorized recovering entities stays the same. Because the threshold check compares the count against the (possibly duplicated) list length rather than against a de-duplicated set, a single recovering DID controller listed multiple times could satisfy `num_of_backup_ids_needed` on their own, effectively lowering the intended multi-party recovery threshold to 1 without this being obvious from `num_of_backup_ids_needed` alone.

### Impact Explanation
This maps to "unauthorized coin movement": the whole point of `num_of_backup_ids_needed` is to require multiple independent recovery DIDs to co-sign a recovery spend before a DID singleton's ownership can be reassigned. If duplicates go unchecked, a party who is supposed to be only one of several required co-signers (e.g., 1-of-3 by count but the "3" entries are really 1 unique DID repeated three times) can unilaterally recover/reassign the DID and, transitively, everything gated on DID ownership (NFTs, credential-restricted CAT flows via VC/DID ownership checks, etc.), bypassing the intended multi-party trust model.

### Likelihood Explanation
Medium. This requires either: (a) a wallet user error at DID creation time (no client-side validation rejects duplicate `backup_ids`), or (b) a malicious backup-string / recovery-file import via `create_new_did_wallet_from_recovery` → `deserialize_backup_data`, which parses attacker-supplied backup data and only checks `num_of_backup_ids_needed <= len(backup_ids)`, not distinctness. Since DID backup data/recovery files are commonly shared/exported between parties, a maliciously crafted backup string with duplicated recovery IDs is a plausible, low-cost attack vector reachable by any user importing a DID backup.

### Recommendation
- Enforce uniqueness of `backup_ids` wherever the list is constructed or accepted: `create_new_did_wallet`/`generate_new_decentralised_id` (user-supplied), `deserialize_backup_data` (imported backup string), and `create_new_did_wallet_from_coin_spend`/`find_lost_did` (on-chain solution reconstruction).
- Change the threshold validation from `num_of_backup_ids_needed > len(backup_ids)` to `num_of_backup_ids_needed > len(set(backup_ids))`, and reject construction if `len(backup_ids) != len(set(backup_ids))`.
- Consider adding the same check to the CLVM-side recovery-count enforcement if it exists at the puzzle level, so a maliciously duplicated `backup_ids_hash` cannot be used to reduce the effective quorum on-chain.

### Proof of Concept
1. A DID owner calls `create_new_did_wallet` (or exports/imports via `create_new_did_wallet_from_recovery`) with `backup_ids = [DID_A, DID_A, DID_A]` and `num_of_backup_ids_needed = 3`.
2. `deserialize_backup_data` only checks `num_of_backup_ids_needed (3) <= len(backup_ids) (3)` — passes, even though there is only 1 unique recovering party. [6](#0-5) 
3. `create_innerpuz`/`get_inner_puzhash_by_p2` curry this duplicated list into the on-chain DID puzzle exactly as given, with no dedup step. [4](#0-3) 
4. Owner of `DID_A` alone can now satisfy whatever attestation-count logic checks `num_of_backup_ids_needed` against the (duplicated) `backup_ids` list, effectively controlling DID recovery unilaterally despite the nominal "3 signers required" configuration.

Note: I was unable to locate the actual CLVM puzzle source (`did_innerpuz.clsp`/`.clvm`) in the indexed codebase to confirm exactly how the on-chain recovery spend counts/verifies attestations against `num_of_backup_ids_needed` at the puzzle level (only the Python curry/hash helpers were found). This is a limitation of the current index coverage; a full Devin session with filesystem access would be needed to confirm the exact on-chain recovery-count enforcement logic before fully validating the on-chain (not just wallet-side) severity of this issue.

```python
    @staticmethod
    def deserialize_backup_data(backup_data: str) -> DIDInfo:
        """
        Get a DIDInfo from a serialized string
        :param backup_data: serialized
        :return: DIDInfo
        """
        details = backup_data.split(":")
        origin = Coin(bytes32.fromhex(details[0]), bytes32.fromhex(details[1]), uint64(details[2]))
        backup_ids = []
        if len(details[3]) > 0:
            for d in details[3].split(","):
                backup_ids.append(bytes32.from_hexstr(d))
        num_of_backup_ids_needed = uint64(details[5])
        if num_of_backup_ids_needed > len(backup_ids):
            raise Exception
        innerpuz: Program = Program.from_bytes(bytes.fromhex(details[4]))
        metadata: str = ""
        for d in details[6:]:
            metadata = metadata + d + ":"
        if len(metadata) > 0:
            metadata = metadata[:-1]
        did_info = DIDInfo(
            origin_coin=origin,
            backup_ids=backup_ids,
            num_of_backup_ids_needed=num_of_backup_ids_needed,
            parent_info=[],
            current_inner=innerpuz,
            temp_coin=None,
            temp_puzhash=None,
            temp_pubkey=None,
            sent_recovery_transaction=True,
            metadata=metadata,
        )
        return did_info
```

```python
def create_innerpuz(
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )
```

```python
def get_inner_puzhash_by_p2(
    p2_puzhash: bytes32,
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list: list[bytes32] | None = None,
    recovery_list_hash: Program | None = None,
) -> bytes32:
    """
    Calculate DID inner puzzle hash based on a P2 puzzle hash
    :param p2_puzhash: P2 puzzle hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :return: DID inner puzzle hash
    """

    if recovery_list is None and recovery_list_hash is None:
        raise ValueError("Cannot construct DID inner puzzle without information about recovery list")

    # Allow both recovery_list and recovery_list_hash to be provided but
    # in that case the list is ignored and the hash is used
    # this matches the behaviour of create_innerpuz
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash.as_atom()
    else:
        assert recovery_list is not None
        backup_ids_hash = shatree_atom_list(recovery_list)

    # singleton_struct = (MOD_HASH . (LAUNCHER_ID . LAUNCHER_PUZZLE_HASH))
    singleton_struct = shatree_pair(
        SINGLETON_TOP_LAYER_MOD_HASH_TREE_HASH,
        shatree_pair(shatree_atom(launcher_id), SINGLETON_LAUNCHER_PUZZLE_HASH_TREE_HASH),
    )

    return curry_and_treehash(
        DID_INNERPUZ_MOD_HASH_QUOTED,
        p2_puzhash,
        shatree_atom(backup_ids_hash),
        shatree_int(num_of_backup_ids_needed),
        singleton_struct,
        metadata.get_tree_hash(),
    )
```
