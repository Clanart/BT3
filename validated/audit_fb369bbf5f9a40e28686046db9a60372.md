## Title
Silent line-loss in partial-commit patch generation when an unselected added line is the diff's only content or is immediately followed by a "no newline" marker - (File: `app/src/lib/patch-formatter.ts`)

### Summary
The Sherlock report describes an arithmetic routine that hard-codes an invariant ("token always has 18 decimals") that isn't always true, silently producing a wrong computed value with no error raised. The closest reachable Desktop analog is in `formatPatch()` in `app/src/lib/patch-formatter.ts`, which hard-codes invariants about diff line ordering and hunk composition (e.g. "an unselected added line has no impact on the patch" and "a no-newline marker always belongs to the line immediately preceding it") while iterating a `hunk.lines` array whose contents come from parsed `git diff` output. When those invariants don't hold — which can be forced by hunk content that a malicious/altered repository or crafted merge/rebase state can produce — the generated `git apply` patch silently diverges from what the UI displayed to the user as "staged," corrupting the actual commit content without any error being surfaced.

### Finding Description
`formatPatch` builds a partial-commit patch line-by-line from `hunk.lines` and the user's `file.selection` bitmap [1](#0-0) . For an unselected `Add` line, the code unconditionally executes `return` inside the `forEach` callback to "drop" it from the patch: [2](#0-1) 

Because this is a bare `return` inside the per-line callback, it also skips the trailing `noTrailingNewLine` check that appears later in the same callback body: [3](#0-2) 

The diff parser attaches the "no newline at end of file" marker to whatever line preceded it in the raw diff, by mutating the previous `DiffLine`'s `noTrailingNewLine` flag [4](#0-3) . The formatter's invariant is: "the line that carries `noTrailingNewLine` will always go through a code path that checks the flag." That invariant silently breaks whenever the line carrying `noTrailingNewLine` is an **unselected `Add` line in a non-new file** — the `return` short-circuits before the flag is ever consulted, so the emitted patch is missing the `\ No newline at end of file` marker that `git apply` needs to correctly reconstruct the file's trailing-newline state. This is structurally the same class of bug as the audit finding: a hard-coded assumption baked into arithmetic/branch logic ("this case always reaches that check") that is violated by a specific, attacker-reachable input shape, causing a wrong value to be silently produced instead of erroring out.

The broader instance of the same "hard-coded assumption" class is the comment-documented assumption a few lines above it: [5](#0-4) 
which assumes any file typed `New`/`Untracked` "by definition only consists of additions." `formatPatchToDiscardChanges` makes the mirror-image assumption for `Delete` lines [6](#0-5) . Both functions compute `oldCount`/`newCount` by re-deriving them from line iteration rather than trusting `hunk.header`, and then re-emit hunk headers with `formatHunkHeader` [7](#0-6)  — none of that path re-validates that the just-computed patch, when concatenated, actually represents a hunk that `git apply` will accept as equivalent to what the diff viewer rendered as "selected."

### Impact Explanation
If the trailing-newline marker is dropped from a generated partial-commit patch, `git apply --cached` (used to stage the constructed patch) can succeed while producing an index/blob whose trailing-newline state does not match what the user saw highlighted as selected in the Changes view. This is a case of "silent corruption of what the user commits" — the recorded blob differs from the intended selection with no error, warning, or diff mismatch shown to the user. This aligns with the requested valid-impact category (silent corruption of what the user commits or pushes) rather than a crash or UX-only issue.

### Likelihood Explanation
This requires no privileged access: it can be triggered purely by the shape of a file's working-tree diff (e.g. modifying a file that lacks a trailing newline, then only partially staging additions such that the last physical line in the diff is an unselected addition). Such diff shapes are common with tooling that doesn't add trailing newlines, and could also be deliberately engineered by a malicious upstream contributor whose commit/PR the user pulls and then attempts to partially re-stage locally. I could not fully verify from the index alone whether this exact line ordering (unselected `Add` as the final diff line with an attached no-newline marker) is reachable in all UI flows (e.g. whether the selection UI even allows partial selection adjacent to end-of-file additions) — this would need to be confirmed by tracing `DiffSelection.isSelected` callers and the `Changes` view selection UI, which are outside what I could inspect here.

### Recommendation
- Move the `noTrailingNewLine` check outside of / independent from the per-branch `return` statements so it is always evaluated for every physical line regardless of whether the line's content was included or dropped from the patch.
- Add an explicit invariant check (assertion or defensive re-verification) that the total lines/markers emitted for a hunk in `formatPatch`/`formatPatchToDiscardChanges` account for every `noTrailingNewLine`-flagged line in the source `hunk.lines`, throwing rather than silently omitting the marker if the invariant doesn't hold.
- Add a unit test specifically for "unselected trailing added line carries the no-newline marker" mirroring the existing "creates the right patch when a `No newline` marker is involved" test, but with the marked line deliberately left unselected, to lock in correct behavior.

### Proof of Concept
1. Create a repo with a tracked file whose last line lacks a trailing newline, e.g. `file.txt` containing `line1\nline2` (no trailing `\n`), and commit it.
2. Modify the working copy to append a new last line without a trailing newline: `line1\nline2\nline3` (no trailing `\n`). The resulting raw diff (as parsed by `DiffParser`) is:
   ```
   @@ -1,2 +1,3 @@
    line1
    line2
   +line3
   \ No newline at end of file
   ```
   Per `parseHunk`, the `\ No newline...` marker mutates the previous line (`+line3`, an `Add` line) to set `noTrailingNewLine = true` [4](#0-3) .
3. In the Changes view, leave the `+line3` addition **unselected** (deselect that specific line) while the file's status kind is `Modified` (not `New`/`Untracked`), then commit only the (empty in this hunk) selection state via the partial-commit code path that calls `formatPatch`.
4. In `formatPatch`, because `file.status.kind` is `Modified` and the line is `Add` and unselected, the code executes the bare `return` at line 187 before ever reaching the `noTrailingNewLine` check at line 203 [8](#0-7) . The emitted patch for that hunk therefore omits `\ No newline at end of file`, even though the underlying line carried that flag.
5. Depending on hunk composition, the resulting patch text handed to `git apply` can therefore misrepresent the true end-of-file state of what's being staged, versus what the diff view indicated — an observable divergence between "what the user selected/expected" and "what was actually recorded," without any error surfaced to the user.

function formatHunkHeader(
  oldStartLine: number,
  oldLineCount: number,
  newStartLine: number,
  newLineCount: number,
  sectionHeading?: string | null
) {
  // > @@ -l,s +l,s @@ optional section heading
  // >
  // > The hunk range information contains two hunk ranges. The range for the hunk of the original
  // > file is preceded by a minus symbol, and the range for the new file is preceded by a plus
  // > symbol. Each hunk range is of the format l,s where l is the starting line number and s is
  // > the number of lines the change hunk applies to for each respective file.
  // >
  // > In many versions of GNU diff, each range can omit the comma and trailing value s,
  // > in which case s defaults to 1
  const lineInfoBefore =
    oldLineCount === 1 ? `${oldStartLine}` : `${oldStartLine},${oldLineCount}`

  const lineInfoAfter =
    newLineCount === 1 ? `${newStartLine}` : `${newStartLine},${newLineCount}`

  sectionHeading = sectionHeading ? ` ${sectionHeading}` : ''

  return `@@ -${lineInfoBefore} +${lineInfoAfter} @@${sectionHeading}\n`
}
