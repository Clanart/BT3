### Title
Panic on unvalidated participant index in blame evaluation (`HashMap` index on missing key) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The CVE-2021-47386 bug class — a structure field retained/dereferenced under the assumption it is always valid, where attacker-influenced input produces a missing entry (NULL-equivalent) — maps onto Serai's PedPoP blame path. `BlameMachine::blame_internal` indexes `self.commitments[&sender]` directly with a `Participant` supplied by the caller, without checking that `sender` is within `1 ..= n`. `Participant::new` only rejects zero, so a participant index `> n` reaches a `HashMap` `Index` impl that panics on a missing key, aborting the processor.

### Finding Description
`AdditionalBlameMachine::new` builds `commitments` containing exactly the indexes `1 ..= n` (crypto/dkg/pedpop/src/lib.rs:656-660). `blame()` / `blame_internal` then take `sender` and `recipient` from an external accusation message and, after decrypting the accused message with `decrypt_with_proof`, evaluate `share_verification_statements(recipient, &self.commitments[&sender], ...)` (crypto/dkg/pedpop/src/lib.rs:596-605). There is no check that `sender <= n`; a `Participant` such as `Participant::new(u16::MAX)` is a perfectly valid value (any nonzero u16, crypto/dkg/src/lib.rs:29-36) yet has no entry in `commitments`. In the processor's `VerifyBlame` handler, `accuser`/`accused` arrive inside a `CoordinatorMessage` and are forwarded directly to `AdditionalBlameMachine::blame` (processor/src/key_gen.rs:504-549) after only `EncryptedMessage` parsing checks — the participant indexes are never range-checked against `params.n()`.

### Impact Explanation
Any party able to submit a `VerifyBlame` accusation naming a nonexistent participant index (or any accusation where `sender` is out of the `1 ..= n` range) causes an index-out-of-map panic inside the processor while handling blame. This is a remotely-triggered crash of the key-generation/blame-verification path: the misbehavior cannot be attributed (blame resolution itself crashes), denying the protocol's fault-resolution mechanism and halting that processor's DKG handling. The same unchecked-index pattern (`HashMap` `Index` on a caller-controlled `Participant`) also exists on `self.commitments[&l]` in `calculate_share` (lib.rs:490), though that one is guarded by `validate_map`; the `blame` entry point is not.

### Likelihood Explanation
Reachability requires only that a blame/accusation message carry an out-of-range `Participant`. `Participant` deserialization and construction enforce only nonzero (crypto/dkg/src/lib.rs:121-126), and `AdditionalBlameMachine`'s documented precondition ("commitments must be authenticated/valid") does not constrain the `sender`/`recipient` arguments to `blame`, which are exactly the attacker-influenced values. No collusion, key material, or protocol position is required — a single malformed accusation suffices, mirroring the CVE where a single crafted `val` byte pattern triggered the NULL dereference.

### Recommendation
In `BlameMachine::blame_internal` (and/or `AdditionalBlameMachine::blame`), validate `sender` and `recipient` against the known participant set (`self.commitments.contains_key`) before indexing; return a defined error or a default blame outcome instead of panicking. Similarly, in the processor's `VerifyBlame` handler, reject `accuser`/`accused` values `> params.n()` before invoking the blame machine. Replace `self.commitments[&sender]` with a checked `get` that treats a missing sender as the accuser's fault or an invalid accusation.
