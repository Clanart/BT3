### Title
BIP-340 signatures produced for odd-Y group keys are consensus-invalid, making the multisig unable to spend - ([File: networks/bitcoin/src/crypto.rs])

### Summary
`SignableTransaction` / `TransactionMachine` in `networks/bitcoin/src/wallet/send.rs` produce BIP-340 key-path signatures via the `Schnorr` algorithm in `networks/bitcoin/src/crypto.rs`. The code handles BIP-340's even-Y requirement for the nonce `R` (negating the challenge and `s` when `R` is odd), but never normalizes the group key `A` to even Y. Since the on-chain script commits to the x-only key — which Bitcoin consensus lifts to the even-Y point — any threshold group key with odd Y produces signatures that verify internally but are invalid under consensus rules, permanently blocking spends.

### Finding Description
`p2tr_script_buf` commits to `x_only(group_key)`, which explicitly "drops its sign" ( [1](#0-0) ). Bitcoin consensus therefore verifies the signature against `P = lift_x_even(x(A))`. When the aggregated `group_key` has odd Y, the effective public key is `-A`, so a valid BIP-340 signature must satisfy `s·G = R' + c·(-A)`, i.e., the secret share must be used as `-share`.

The `Hram` implementation only corrects for `R` parity: it negates the challenge when `R` is odd ( [2](#0-1) ), and `verify` negates `s` when `sig.R` is odd ( [3](#0-2) ). `sign_share` passes `params.secret_share()` raw, and `Schnorr::verify` checks `s·G == R + c·A` against the raw `group_key` ( [4](#0-3) ). No negation keyed on `needs_negation(&group_key)` exists anywhere in the signing path. Per-input offsets (`keys.clone().offset(self.offsets[i])`, send.rs:276-281) are arbitrary scalars with no parity normalization, so an odd-Y per-input key is entirely possible.

The analogous failure to the reported bug — a wrong/zero parameter making an operation always fail — is that the wrong key representative (odd-Y instead of even-Y) is fed into the signature equation, so for that class of inputs signing always produces an invalid result.

### Impact Explanation
For any input whose per-input offset-adjusted group key has odd Y (~50% of keys), the FROST `complete()` integrity check in `AlgorithmSignatureMachine::complete` passes (the math is internally consistent), a 64-byte witness signature is emitted, and the transaction is then rejected by every Bitcoin node under BIP-340 validation. Funds in such outputs cannot be spent through this signing path — a silent, permanent signing failure for affected keys.

### Likelihood Explanation
Each input's effective key is `group_key + offset·G` with an arbitrary offset scalar; there is no mechanism in `SignableTransaction::new`, `multisig`, or `Schnorr` that forces or detects odd parity. Any threshold set or offset producing an odd-Y aggregate key hits this deterministically.

### Recommendation
In `Schnorr::sign_share`, conditionally negate the effective secret contribution (equivalently, negate the produced share) when `needs_negation(&params.group_key())` is true, and in `Schnorr::verify`/`verify_share` use the even-Y representative of `group_key` so the internal integrity check matches consensus semantics. Alternatively, normalize keys to even Y at `ThresholdKeys::offset`/`multisig` time.

### Proof of Concept
1. Construct `ThresholdKeys<Secp256k1>` (with an `offset`) such that `needs_negation(offset_keys.group_key())` is true — simply retry offsets until the group key's compressed encoding is tagged `CompressedOddY`.
2. Build a `SignableTransaction` spending a `ReceivedOutput` whose `script_pubkey == p2tr_script_buf(group_key)`.
3. Run `multisig` → `preprocess` → `sign` → `complete` among `t` honest participants; `complete` returns a `[u8; 64]` signature successfully.
4. Verify the signature with `bitcoin`'s `XOnlyPublicKey::verify` (or `secp256k1` schnorr verify against `x_only(group_key)`): it fails, since consensus uses `lift_x_even` = `-group_key` while the signature was produced against `+group_key`.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }

        sig.serialize()[1 ..].try_into().unwrap()
