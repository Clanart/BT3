## Title
Stale line-index `DiffSelection` reused against a freshly re-fetched diff during partial-commit staging causes silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-file staging flow keeps two representations of "what the user wants to commit" that are supposed to stay in sync but are not: the `DiffSelection` bitmap (a set of *absolute line indices* computed against a diff snapshot rendered in the UI) and the *actual* working-directory diff, which is re-fetched from disk immediately before staging. When these two diverge — because the tracked file's on-disk content changed between the moment the selection was made/preserved and the moment staging runs — the stale, index-based selection is blindly applied to the new diff's line layout, silently including or excluding the wrong lines from the commit. This mirrors the `supply`/`totalSupply` desync pattern in the source report: two values meant to represent the same state are used interchangeably without being resynced first.

### Finding Description
`applyPatchToIndex` re-fetches the diff for a file right before staging it, but then formats the patch using the `WorkingDirectoryFileChange`'s existing `selection` object, which is an *absolute-line-index* bitmap: [1](#0-0) 

`formatPatch` trusts this selection blindly, calling `file.selection.isSelected(absoluteIndex)` against the hunks of the newly fetched diff: [2](#0-1) 

The selection is not necessarily derived from the diff being staged. `updateChangedFiles` (invoked on every status refresh) deliberately *preserves* the previous selection object across working-directory refreshes rather than recomputing it against the newly observed diff: [3](#0-2) 

The UI's own diff-loading code acknowledges this exact class of problem for the *rendered* diff (only clearing `selectableLines`, not fully re-validating the bitmap against new line positions), explicitly noting the diff "might have changed dramatically since last we loaded it": [4](#0-3) 

But this reconciliation happens only for the *rendered* diff selected in the Changes view — it does not re-validate the selection at commit time against the diff that `applyPatchToIndex` independently re-fetches during `_commitIncludedChanges` → `createCommit` → `stageFiles`: [5](#0-4) [6](#0-5) 

If a tracked file's content on disk shifts between hunk boundaries the user last saw (e.g., due to an attacker-controlled `.gitattributes` `clean`/`smudge` filter or `text=auto` line-ending normalization reapplying on re-add/status, both of which are fully controlled by the contents of a cloned/fetched repository, or any other benign background modification such as an editor auto-format triggered by repo tooling), the absolute-index bitmap no longer aligns to the same logical lines in the new diff. `formatPatch` will still happily generate a patch, applying selection bits to unrelated hunk lines — staging and committing content the user never reviewed or intended, while appearing to have committed exactly what was shown in the UI.

### Impact Explanation
This breaks the core trust guarantee of Desktop's partial-commit ("stage select lines") feature: what the user visually selected is not guaranteed to be what actually gets committed and (subsequently) pushed. Because `git apply --cached` is applied against a freshly fetched diff with an out-of-date selection bitmap, the corruption is silent — no error is raised, and the commit dialog reports success. This can cause unintended code (or unintended omissions, e.g. leaving out a fix the user believed they staged, or including a line the user explicitly deselected) to be committed and later pushed to a shared/public remote.

### Likelihood Explanation
Exploitation requires influencing the on-disk content of a tracked file during the (typically short, but non-zero) window between the UI's diff render/selection and the `getWorkingDirectoryDiff` refetch inside `applyPatchToIndex`. A repository attacker fully controls `.gitattributes` filters (`clean`/`smudge`) and content normalization rules that are re-applied on file-system events Desktop already watches and reacts to (status refresh, `updateChangedFiles`), so this is plausible without any unusual user action beyond normal partial-staging usage on a cloned/fetched malicious repository. It is likelihood "Medium" rather than "High" because it needs a timing window and a filter/normalization mechanism to actually shift line positions, but no admin rights, local access, or leaked credentials are required.

### Recommendation
Do not reuse a `DiffSelection` bitmap across different diff snapshots. Before staging, `applyPatchToIndex`/`formatPatch` should validate that the diff used to build the selection is identical (e.g., via content hash or hunk fingerprint) to the diff being staged, and abort/refresh the selection if they differ — analogous to resyncing `supply` and `totalSupply` before using either value. Alternatively, always regenerate the selection against the freshly fetched diff immediately prior to staging rather than reusing state carried over from a prior render.

### Proof of Concept
1. Clone an attacker-controlled repository containing a `.gitattributes` filter (or `text=auto`/line-ending rule) that alters a tracked file's line layout when it is re-processed by Git (e.g., on `git add`/status refresh).
2. In Desktop, open the file's diff and select a subset of lines for a partial commit.
3. Trigger a filesystem event that causes Desktop to refresh working-directory status (e.g., editor autosave, or the filter reprocessing the file) before clicking "Commit" — `updateChangedFiles` preserves the old `selection` object unchanged (`app/src/lib/stores/updates/changes-state.ts:56`).
4. Click Commit. `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` refetches the diff (`app/src/lib/git/apply.ts:60`) and applies the stale selection indices via `formatPatch` (`app/src/lib/patch-formatter.ts:157`), producing a patch that stages different lines than what was visually selected.
5. Inspect the resulting commit: it contains content different from what the user selected in the UI, demonstrating silent corruption of what was committed.
