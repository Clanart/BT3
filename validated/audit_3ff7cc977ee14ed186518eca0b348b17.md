### Title
SignableTransaction excludes the OP_RETURN data output from fee/weight calculation, underpaying the fee and stranding multisig funds - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/blackvul/serai--010))

### Summary
The OpenQ bug class is "a deposit carries two components; only one is accounted, the rest silently vanishes/locks." `SignableTransaction::new` exhibits the same class: the OP_RETURN data output is pushed into the actual transaction's outputs but is never included in the weight/vbyte estimate used to compute `needed_fee`, so the transaction's real fee rate is lower than requested — potentially below the minimum relay fee — leaving the signed transaction unbroadcastable and the consumed inputs effectively locked.

### Finding Description
`SignableTransaction::new` builds `tx_outs` including a zero-valued OP_RETURN output when `data` is provided (up to 80 bytes, `networks/bitcoin/src/wallet/send.rs:193-202`). However, the fee is computed via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, whose synthetic transaction contains only the `payments` outputs and optional change — the data output is never passed in (`send.rs:85-93`, `send.rs:204`, `send.rs:225-226`).

Concretely:

1. `tx_outs.push(OP_RETURN output)` happens before any weight calculation, but `calculate_weight_vbytes` only iterates `payments`.
2. `needed_fee = fee_per_vbyte * vbytes` where `vbytes` omits ~8 (amount) + ~1–3 (script len) + up to 82 bytes of OP_RETURN data — roughly 90 extra bytes (~360 WU).
3. With change, `fee_with_change` uses the same data-omitted estimate, and the change amount is computed as `input_sat - payment_sat - fee_with_change`. The change is therefore slightly larger than it should be, but the real problem is that the *actual* fee (`inputs - outputs`) equals the underestimated `fee_with_change`, while the actual vsize is larger.
4. The `TooLowFee` check compares the underestimated `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes` (`send.rs:211-213`), so a `fee_per_vbyte` of 1 sat/vB passes the check while producing a real fee rate of ~0.7–0.9 sat/vB, which Bitcoin Core will reject from the mempool.
5. `TransactionSignMachine::sign` and `complete` produce the final transaction deterministically from `self.tx.tx` — the multisig signs the under-fee'd transaction, and any re-attempt through the same code path with the same fee rate reproduces it.

This mirrors the OpenQ issue: an untrusted caller can supply `data` (the Serai burn/bridge path attaches arbitrary InInstruction data to transactions) and one component of the request — the data output's weight — is silently unaccounted, causing the produced transaction to be non-relayable and the inputs' funds to be unavailable until a higher fee rate is manually used.

### Impact Explanation
Any transaction built with a `data` payload and a near-minimum fee rate produces a real fee rate below Bitcoin's minimum relay fee. The resulting fully-signed transaction is rejected by the network; the consumed `ReceivedOutput`s cannot be spent by that transaction, and naively re-signing through the same path yields the same failure. Funds in the threshold multisig's UTXOs are effectively frozen for transactions carrying data at low fee rates — a loss-of-availability of funds analogous to the locked deposits in the original report.

### Likelihood Explanation
The `data` parameter accepts up to 80 bytes (`send.rs:171-173`, `send.rs:194-202`) and is used for externally-triggered bridge/burn flows, so an unprivileged user can cause data-bearing transactions to be constructed. The bug triggers whenever `fee_per_vbyte` is at or near 1 sat/vB — the exact minimum the `TooLowFee` guard enforces — which is the natural configuration in low-fee environments.

### Recommendation
Include the OP_RETURN data output in the synthetic transaction used by `calculate_weight_vbytes` — e.g., pass the fully-formed `tx_outs` (payments + data) plus the optional change output into the weight calculation, so `needed_fee`, `fee_with_change`, and the `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` checks all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
```rust
// networks/bitcoin — demonstrate the fee underestimation
let inputs = vec![received_output]; // any ReceivedOutput
let data = vec![0u8; 80];           // max allowed InInstruction payload

let tx = SignableTransaction::new(
  inputs, &payments, None, Some(data.clone()), 1, // 1 sat/vB
).unwrap();

// tx.needed_fee() == vbytes(payments-only) * 1
// tx.transaction() contains an extra ~90-byte OP_RETURN output.
// Real fee rate = tx.fee() / actual_vsize < 1 sat/vB,
// so a Bitcoin Core node rejects it under the minimum relay fee policy,
// while the TooLowFee check at send.rs:211 passed using the smaller estimate.
assert!(
  tx.fee() * 1000 / actual_vsize(&tx) <
    u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE)
);
```

Relevant code: `calculate_weight_vbytes` builds outputs only from `payments` (`send.rs:85-98`), the OP_RETURN output is added to `tx_outs` separately (`send.rs:194-202`), the fee estimate omits it (`send.rs:204-206`), and the change/fee path repeats the omission (`send.rs:224-234`).
