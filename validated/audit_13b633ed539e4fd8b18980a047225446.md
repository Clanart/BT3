### Title
Hardcoded Zero Slippage Protection in `WombatPoolHelperV2.depositFor()` Enables MEV Sandwich Theft of User Deposits - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor()` hardcodes the Wombat pool deposit's minimum liquidity output to `0`, removing all slippage protection for the depositing user. This function is reachable from an ordinary, unprivileged wallet transaction via `ManualCompound.compound()`, which any user can call to compound their own claimed rewards.

### Finding Description
`depositFor` transfers the deposit token from `msg.sender`, approves the `wombatStaking` contract, and then calls the internal `_deposit` helper with a hardcoded `_minimumLiquidity` of `0`: [1](#0-0) 

That value flows unmodified into `IWombatStaking.deposit`, which itself forwards it as `_minimumLiquidity` straight into the external `IWombatPool.deposit(...)` call: [2](#0-1) [3](#0-2) 

Because `_minimumLiquidity` is `0`, the Wombat pool's `deposit()` call will accept any LP output amount, no matter how unfavorable, so long as it is greater than zero. This is functionally identical to the reported GMX issue where `minMarketTokens`/`minLongTokenAmount`/`minShortTokenAmount` are hardcoded to `0` — the depositor has no protection against price/slippage/impact between transaction submission and execution.

This function is directly reachable by an unprivileged wallet: `ManualCompound.compound()` is a public, unprivileged entrypoint that any user can call to compound their own claimed rewards, and it invokes `ISimpleHelper(_helperAddress).depositFor(receivedBalance, msg.sender)` when a pool helper is configured for a reward token: [4](#0-3) 

Since `compound()` is a normal, ungated call available to any wallet (and, in practice, likely triggered as part of routine compounding flows), an MEV searcher can sandwich the resulting Wombat pool deposit transaction: front-run it to skew the pool's internal price/coverage ratio, let the zero-slippage deposit execute at the manipulated rate (minting fewer LP/receipt tokens than fair value), and back-run to restore the price and capture the difference.

### Impact Explanation
A sandwich attacker can extract value directly from the depositing user's compounded rewards by manipulating the Wombat pool state around the zero-slippage deposit call, resulting in the user receiving fewer receipt/LP tokens (and consequently fewer future staking rewards) than the fair-market amount. This is a direct, reachable loss of user funds triggered purely by an ordinary user calling `compound()`, with no privileged role required by either the victim or the attacker.

### Likelihood Explanation
Likelihood is significant: `compound()` is a normal user-facing function with no access control, and depositing into an AMM-style pool with `0` minimum output is a well-known, easily automatable MEV target (sandwich bots continuously monitor mempools for such patterns). No special conditions or privileged actors are needed to trigger the vulnerable code path — only a routine reward-compounding transaction.

### Recommendation
Do not hardcode `_minimumLiquidity` to `0` in `WombatPoolHelperV2.depositFor()`. Either:
- Add a `_minimumLiquidity` parameter to `depositFor` (and to `ManualCompound.compound()`'s call site) so callers/compounders can supply a computed slippage-protected minimum, or
- Compute an expected minimum LP output on-chain (e.g., via the Wombat pool's quote/preview function) and apply a reasonable slippage tolerance before calling `IWombatStaking.deposit`.

### Proof of Concept
1. A user calls `ManualCompound.compound(...)` with a reward token that is configured with a `tokenHelper` pointing at a `WombatPoolHelperV2` instance.
2. `ManualCompound` calls `WombatPoolHelperV2.depositFor(receivedBalance, msg.sender)`.
3. `depositFor` calls `_deposit(_amount, 0, _for, address(this))`, which calls `IWombatStaking(wombatStaking).deposit(lpToken, _amount, 0, _for, address(this))`.
4. `WombatStaking.deposit` calls `IWombatPool(poolInfo.depositTarget).deposit(depositToken, _amount, 0, address(this), block.timestamp, false)` — with `0` as the minimum LP output.
5. An MEV bot observes the pending transaction, front-runs it with a trade that skews the pool's asset coverage ratio unfavorably for the deposit, lets the zero-slippage deposit mint a reduced amount of LP tokens to the user, then back-runs to restore the pool state and pocket the difference — all while the on-chain call succeeds because no minimum output check reverts it.
