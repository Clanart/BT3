### Title
Governance `unitprice` vote accepted with no upper-bound cap, enabling arbitrary gas-price inflation via a single-validator vote - ([File: kaiax/gov/param.go])

### Summary
`GovernanceUnitPrice` (the `governance.unitprice` gas-price parameter) is registered with `FormatChecker: noopFormatChecker`, meaning no minimum/maximum bound is enforced on the value a vote can set. Unlike other numeric governance parameters that have explicit sanity checks (e.g. `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` are cross-checked against each other in `checkConsistency`, `Kip71BaseFeeDenominator` requires `v != 0`, `IstanbulPolicy` requires `v <= 2`), `unitprice` has no such constraint anywhere in the vote-verification pipeline.

### Finding Description
`GovernanceUnitPrice` is defined with a no-op format checker: [1](#0-0) 

Compare this to KIP-71 parameters that receive additional protection, either via format checkers or cross-parameter consistency checks performed in `checkConsistency`: [2](#0-1) [3](#0-2) 

`checkConsistency`'s `default` case only rejects unrecognized parameter names; for the whitelisted numeric/string parameters (including `GovernanceUnitPrice`, listed among the parameters that "are valid as long as it passes the format checks in `NewVoteData()`") no additional bound is applied: [4](#0-3) 

Because `unitprice` feeds directly into the effective gas price used for fee calculation and balance checks in transaction processing (`buyGas`, `checkFeePayerBalance`, `checkSenderBalance` in `blockchain/state_transition.go`), and into fee-delegation ratio splitting in `types.CalcFeeWithRatio`, a vote setting `unitprice` to a value orders of magnitude larger than the previous value would be accepted without any sanity/bound validation, unlike the analogous KIP-71 base-fee bounds which are explicitly protected against inconsistent/malicious values.

### Impact Explanation
If `governance.unitprice` is voted to an excessively large value, every subsequent transaction's gas fee (and, for fee-delegated transactions, both the sender's and fee payer's share via `CalcFeeWithRatio`) will be computed against that inflated price. Users and fee-payers would be forced to pay drastically more than intended, or transactions from honest senders/fee-payers would begin reverting due to insufficient balance checks in `buyGas`. This mirrors the reported "no cap on member fee" bug class: an admin/governance-controlled fee parameter that can be pushed to an unreasonable value causes unauthorized-magnitude value extraction/fee abuse from ordinary transaction senders and fee-delegation counterparties, with no protocol-level safeguard analogous to the bound checks that exist for other governance/fee parameters (KIP-71 lower/upper bound, base-fee-denominator nonzero check).

### Likelihood Explanation
This requires a governance vote to be cast and reach quorum during an epoch, so it depends on validator/governing-node cooperation (single mode is governed by the `GoverningNode`), which is a real-world non-trivial but existing capability of the governance module. There is no additional gate preventing an extreme value once a vote is placed and accepted, in contrast to KIP-71 parameters, which is the specific gap being highlighted; the absence of validation is a code-level bug regardless of how often the governing party might exploit it.

### Recommendation
Add a `FormatChecker` for `GovernanceUnitPrice` that enforces reasonable minimum/maximum bounds (analogous to the `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` cross-check and the `BaseFeeDenominator != 0` check), and/or add a `checkConsistency` case for `GovernanceUnitPrice` in `kaiax/gov/headergov/impl/header.go` that rejects unreasonable jumps relative to the current value.

### Proof of Concept
1. As the governing node (in `single` governance mode) or via validator quorum, submit a header vote for `governance.unitprice` with an extreme `uint64` value (e.g., `uint64(math.MaxUint64)` or several orders of magnitude above the current 25 Gkei default).
2. `NewVoteData` will accept the value because `GovernanceUnitPrice`'s `FormatChecker` is `noopFormatChecker` (`kaiax/gov/param.go:259-264`).
3. `VerifyVote`/`checkConsistency` in `kaiax/gov/headergov/impl/header.go:213-223` passes the vote through with no additional validation, since `GovernanceUnitPrice` is in the "valid as long as it passes format checks" list.
4. Once the vote is committed at the epoch boundary, `GetParamSet` reflects the new `UnitPrice`, which subsequently affects `st.gasPrice` used in `StateTransition.buyGas` (`blockchain/state_transition.go:294-376`), inflating fees charged to senders and fee payers with no upper bound.
