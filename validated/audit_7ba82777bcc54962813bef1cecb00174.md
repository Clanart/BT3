### Title
Trusting an unsafe repository directory via `safe.directory` is permanent and can never be revoked from Desktop - (File: `app/src/lib/git/config.ts`)

### Summary
When Desktop detects a repository owned by a different OS user, it warns that "adding untrusted repositories may automatically execute files in the repository" and offers a one-way "Trust Repository" action. That action calls `addSafeDirectory`, which appends the path to the global `safe.directory` git config. There is no corresponding function or UI control to remove a path from `safe.directory` once added, so the trust decision is permanent for the lifetime of the machine's git config, unlike the reported bug's "cannot toggle back a security flag once set" pattern.

### Finding Description
The bug class in the external report is a boolean/permission flag that can only ever move in one direction due to a bad guard, making the sensitive state impossible to revert. The Desktop analog is `addSafeDirectory`: [1](#0-0) 

This is invoked from two UI flows when Git reports `kind: 'unsafe'` (dubious ownership) for a path: [2](#0-1) [3](#0-2) 

Both UI messages explicitly warn that untrusted repositories "may automatically execute files in the repository" — i.e., the `safe.directory` guard is a real code-execution gate, not a cosmetic setting. `getRepositoryType` classifies a path as `unsafe` based on ownership mismatch reported by `git rev-parse`: [4](#0-3) 

Once a path is added via `addGlobalConfigValueIfMissing('safe.directory', path)`, that entry lives in the user's global `.gitconfig` indefinitely. A `grep` across the entire repository confirms `addSafeDirectory`/`addGlobalConfigValueIfMissing` are only ever called to *add* entries — no `removeSafeDirectory`, no `git config --global --unset safe.directory`, and no UI affordance exists to undo a trust decision. The invariant "a directory's ownership-trust state should be re-evaluated / revocable" is broken exactly the same way the DSToken bug broke "liquidate-only state should be revocable": the state transition works one way only.

### Impact Explanation
Once a path (e.g., `C:\Users\Shared\project` or a removable/mapped drive letter) is trusted, Desktop will never again warn about dubious ownership for that exact path, even if that path is later reused, remounted, or repopulated by a different/malicious owner (shared machines, re-imaged drives, USB drives, network shares, drive-letter reuse on Windows). Since Desktop's own warning states that untrusted repos "may automatically execute files," a stale trust entry silently disables that protection for future content at the same path — this is a real, if narrow, path-confusion/persistence-of-trust issue rather than a one-time API logic bug.

### Likelihood Explanation
This requires the same absolute path to be reused by a different, less-trusted owner after the user has trusted it once (e.g., shared/multi-user Windows machines, removable media, university/corporate lab computers, or drive-letter reassignment) — a plausible but not attacker-fully-controlled scenario. It does not require local malware or admin rights beyond normal multi-user file-system reuse, and does not require any unnatural user action beyond the one legitimate "Trust Repository" click Desktop itself prompts for.

### Recommendation
Provide a Desktop-level revocation path: track paths added via `addSafeDirectory` (e.g., in Desktop's own state, not just git's global config) and re-validate the actual current owner against the owner at the time of trust before relying on the cached decision to skip the unsafe-repository dialog. At minimum, add a `removeSafeDirectory`/`git config --global --unset-all safe.directory <path>` function exposed in repository settings, so users can revoke previously granted trust, mirroring the requested fix pattern in the source report (allow the state to be toggled both ways instead of only forward).

### Proof of Concept
1. On a shared or reimaged Windows machine, User A creates/owns a directory `D:\shared\repo` and User B (or Desktop under a different profile) opens it in GitHub Desktop; Desktop detects `kind: 'unsafe'` via `getRepositoryType` and shows the "potentially unsafe" warning.
2. User clicks "Trust repository", triggering `onTrustDirectory` → `addSafeDirectory('D:\shared\repo')`, permanently adding the path to the global `safe.directory` list [3](#0-2) .
3. Later, the same drive letter/path is reused by a different, untrusted party (e.g., a re-mounted USB drive, VM snapshot, or shared workstation profile) who plants malicious `.git/hooks`, `.gitattributes` filters, or config-based command execution at that exact path.
4. Because `safe.directory` still contains `D:\shared\repo`, Git and Desktop treat the new content as trusted and skip the "unsafe repository" warning entirely — the code-execution guard the report intended to protect never re-triggers, since no path in the codebase ever calls a removal equivalent of `addSafeDirectory` [5](#0-4) .

This is inferred from static code paths only; I was not able to execute Desktop or reproduce the ownership-reuse scenario end-to-end, so the exact reachability under Desktop's full runtime (e.g., any additional owner re-check logic that might exist elsewhere but wasn't indexed) could not be fully confirmed. If you need certainty on runtime behavior, a Devin session with full filesystem/multi-user access would be needed to reproduce it live.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```

```typescript
export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }
```
