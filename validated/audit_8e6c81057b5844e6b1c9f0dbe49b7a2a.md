Based on the exploration, I found a concrete Desktop analog: **the hidden-Unicode/line-ending warning banner that Desktop already built to protect against "Trojan Source"-style attacks is not wired into the default (unified) diff view.**

### Title
Bidirectional-Unicode and line-ending tampering warnings are silently omitted in the default (unified) diff view - (File: `app/src/ui/diff/diff-contents-warning.tsx`)

### Summary
Desktop computes `hasHiddenBidiChars` and `lineEndingsChange` for every text diff [1](#0-0) [2](#0-1) , and these fields are threaded all the way through `IRawDiff`/`ITextDiffData` [3](#0-2) [4](#0-3) . However, the component that actually surfaces this to the user, `DiffContentsWarning`, is only ever rendered from `side-by-side-diff.tsx` [5](#0-4) ; it is not referenced anywhere in the unified diff render path. Since unified diff is the application's default presentation, the safety data ("the string that tells you what you're really about to commit") is computed but never emitted to most users in the primary UI path — mirroring the reported bug class of a critical verification value being calculated but never surfaced for observation.

### Finding Description
`DiffParser.parse()` scans the raw diff text for invisible bidirectional-Unicode control characters (`HiddenBidiCharsRegex`) and Git's line-ending conversion warning, attaching both as first-class fields on the diff result [6](#0-5) . These fields propagate through `buildDiff` for every code path — working directory diffs, committed diffs, and merge-conflict resolution diffs [7](#0-6) [8](#0-7) .

The only consumer that turns this data into a visible warning is `DiffContentsWarning`, which explicitly warns about "bidirectional Unicode text that may be interpreted or compiled differently than what appears below" [9](#0-8) . A repo-wide search shows this component is imported/used only inside `side-by-side-diff.tsx` [10](#0-9) ; there is no corresponding invocation in the unified-diff render path (`Diff`/`renderTextDiff` in `app/src/ui/diff/index.tsx`), even though that component consumes `ITextDiff.hasHiddenBidiChars`/`lineEndingsChange` fields elsewhere for equality checks only [11](#0-10) .

New consumers of the diff pipeline, such as the Copilot merge-conflict resolution changes tab, default to unified view (`showSideBySideDiff: false`) [12](#0-11) , so a resolution diff that legitimately sets `hasHiddenBidiChars: true` is rendered through `SeamlessDiffSwitcher` without ever exposing the warning banner to the user, unless they manually toggle to split view.

### Impact Explanation
An attacker who controls a cloned/fetched branch, fork, or pull request can embed invisible bidirectional-Unicode control characters (e.g. RTL/LTR overrides) in source files so that the rendered text in Desktop's default unified diff view looks benign while the bytes that get staged and committed/pushed differ from what the reviewer perceives — the classic "Trojan Source" attack. Desktop's own mitigation for exactly this scenario exists in code but is unreachable from the default view, so the safety net silently fails for the majority of users who never switch to side-by-side mode. This can lead to a user unknowingly committing or pushing maliciously altered code, satisfying the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Likelihood is high for exposure because unified is Desktop's default diff mode and the copilot conflict-resolution feature explicitly initializes to unified as well [13](#0-12) . No local access, elevated privileges, or unusual user action is required — simply reviewing a diff from an untrusted fetched/cloned source in the default view is sufficient to miss the warning.

### Recommendation
Render `DiffContentsWarning` (or an equivalent banner) from the unified diff render path in `app/src/ui/diff/index.tsx` in addition to `side-by-side-diff.tsx`, so the `hasHiddenBidiChars`/`lineEndingsChange` signals are surfaced regardless of which diff mode the user has selected, and ensure the Copilot conflict-resolution diff view inherits the same warning treatment.

### Proof of Concept
1. Create/fetch a branch containing a file with an embedded bidi override character (e.g. U+202E) inserted such that the displayed code differs from the actual byte order.
2. Open the file's diff in Desktop using the default unified view.
3. Observe that `diff.hasHiddenBidiChars` is `true` internally [2](#0-1) , but no warning banner is shown to the user because `DiffContentsWarning` is not invoked outside `side-by-side-diff.tsx` [14](#0-13) .
4. Toggle "Split" (side-by-side) view on the same file and observe the warning now appears, confirming the inconsistency is view-mode-dependent rather than data-dependent.

   * Parse a well-formed unified diff into hunks and lines.
   *
   * @param text A unified diff produced by git diff, git log --patch
   *             or any other git plumbing command that produces unified
   *             diffs.
   */
  public parse(text: string): IRawDiff {
    this.text = text

    try {
      const headerInfo = this.parseDiffHeader()

      const headerEnd = this.le
      const header = this.text.substring(0, headerEnd)

      // empty diff
      if (!headerInfo) {
        return {
          header,
          contents: '',
          hunks: [],
          isBinary: false,
          maxLineNumber: 0,
          hasHiddenBidiChars: false,
        }
      }

      if (headerInfo.isBinary) {
        return {
          header,
          contents: '',
          hunks: [],
          isBinary: true,
          maxLineNumber: 0,
          hasHiddenBidiChars: false,
        }
      }

      const hunks = new Array<DiffHunk>()
      let linesConsumed = 0
      let previousHunk: DiffHunk | null = null

      do {
        const hunk = this.parseHunk(linesConsumed, hunks.length, previousHunk)
        hunks.push(hunk)
        previousHunk = hunk
        linesConsumed += hunk.lines.length
      } while (this.peek())

      const contents = this.text
        .substring(headerEnd + 1, this.le)
        // Note that this simply returns a reference to the
        // substring if no match is found, it does not create
        // a new string instance.
        .replace(/\n\\ No newline at end of file/g, '')

      return {
        header,
        contents,
        hunks,
        isBinary: headerInfo.isBinary,
        maxLineNumber: getLargestLineNumber(hunks),
        hasHiddenBidiChars: HiddenBidiCharsRegex.test(text),
      }

      hunks: diff.hunks,

      hasHiddenBidiChars: diff.hasHiddenBidiChars,

  }

    repository,
    file,

    newestCommitish,
    oldestCommitish,

  )

export function textDiffEquals(
  x: ITextDiff | ILargeTextDiff,
  y: ITextDiff | ILargeTextDiff
) {
  if (x === y) {
    return true
  }

  if (
    x.text === y.text &&
    x.kind === y.kind &&
    x.hasHiddenBidiChars === y.hasHiddenBidiChars &&
    x.lineEndingsChange === y.lineEndingsChange &&
    x.hunks.length === y.hunks.length
  ) {
    // This is a performance optimization which lets us avoid iterating over all
    // lines (deep equality on all hunks). We're already comparing the diff text
    // above so the only thing that can change with the diff text staying the
    // same is whether or not the last line is followed by a trailing newline.
    // That information is encodeded in the noTrailingNewLine property which
    // exists on all lines but is only ever set on lines in the last hunk
    return (
      x.hunks.length === 0 ||
      x.hunks[x.hunks.length - 1].equals(y.hunks[y.hunks.length - 1])
    )
  }

  return false
}
