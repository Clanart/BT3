### Title
Reintroduction of Git's local-clone submodule protection (`protocol.file.allow=always`) allows a malicious repository to write files outside the working directory - (File: `app/src/lib/git/submodule.ts`)

### Summary
The external report's broken invariant is: *an attacker-controlled object (a pool) is allowed to set a security-relevant parameter (the interest rate) before the legitimate party's follow-up transaction lands, and the code trusts that state without re-validating it.* The Desktop analog is structurally similar but manifests as a trust/ordering problem in submodule handling: Desktop's submodule-update helper can be invoked with a flag that re-enables Git's `file://` transport for submodules (`protocol.file.allow=always`), a protection Git upstream disabled by default specifically to stop malicious repositories from using crafted submodules to escape the repository sandbox (the class of bug fixed by Git in response to GHSA-9v9h-cgj8-h64p / CVE-2022-39253, involving local-clone hardlinking of symlinked paths).

### Finding Description
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` builds the `git submodule update --init --recursive` arguments and conditionally prepends `-c protocol.file.allow=always` when its `allowFileProtocol` boolean is `true`: [1](#0-0) 

This override defeats Git's own hardening: modern Git defaults `protocol.file.allow` to `user` (requiring explicit local opt-in) precisely because a hostile repository can define a submodule pointing at a `file://` URL, and Git's "local clone" fast path (hardlinking objects) can be abused together with symlinks committed by the attacker to write files outside the intended checkout directory. By force-setting `protocol.file.allow=always` at the CLI level, Desktop is unconditionally re-enabling exactly the mode that upstream Git decided was unsafe to leave on by default for untrusted repositories.

The flag is threaded from `checkoutBranch` / `checkoutCommit` all the way from user-facing checkout flows: [2](#0-1) 

Because the `.gitmodules` file and submodule commit pointers are fully attacker-controlled content inside a cloned/fetched repository (or a fork/PR branch checked out via `_checkoutPullRequest`), a malicious repository author can craft a submodule entry whose URL uses the `file://` scheme and whose target commit contains symlinks designed to be hardlinked/exported outside the repo root during the "local clone" `submodule update --init --recursive` step. When a user opens such a repository in Desktop and Desktop runs the submodule update with `protocol.file.allow=always`, the guard Git shipped to stop this bug class is bypassed.

### Impact Explanation
If the underlying Git local-clone/hardlink behavior can still be triggered under `protocol.file.allow=always` (the exact scenario the CVE fix targeted), this allows a malicious, unprivileged repository to cause file writes outside the intended repository directory purely by being cloned/checked out in Desktop — matching the "file write... outside the repo" impact category. Even absent a fully weaponizable symlink primitive on a patched Git binary, this represents Desktop deliberately disabling an upstream security control for all submodule operations, widening the attack surface for any future or platform-specific Git submodule/local-clone bug.

### Likelihood Explanation
The trigger requires no unusual user action beyond the normal act of cloning/opening a repository and checking out a branch or PR that contains a malicious submodule definition — the same "attacker controls a cloned/fetched repository" primitive called out as in-scope. No admin rights, local access, or prior compromise is needed; the vulnerable code path (`checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation`) runs automatically as part of everyday checkout operations whenever the caller passes `allowFileProtocol = true`.

### Recommendation
- Do not pass `protocol.file.allow=always` for submodules whose remote/`.gitmodules` content originates from an untrusted or third-party repository (any fork, PR branch, or repository not created by the local user via `git init`).
- If local `file://` submodules must be supported for Desktop's own internal/test flows, scope the override narrowly (e.g., only for repositories Desktop itself created) rather than threading a broad boolean through the general checkout/pull/clone code paths.
- Add a regression test that verifies `protocol.file.allow` is not force-enabled when updating submodules on a freshly cloned, externally-sourced repository.

### Proof of Concept
1. Attacker creates a public repository containing a `.gitmodules` entry with `url = file:///<relative-or-absolute-path>` pointing at another local path within the exported object set, together with committed symlinks structured to exploit Git's local-clone hardlink export (per the pattern fixed in CVE-2022-39253).
2. Victim clones or opens the repository in GitHub Desktop and checks out the branch (or a PR branch via `_checkoutPullRequest`).
3. Desktop calls `checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation` with `allowFileProtocol = true`, causing `git -c protocol.file.allow=always submodule update --init --recursive` to run, re-enabling the `file://` transport Git disabled by default.
4. If the host's Git version is not independently hardened against the symlink/hardlink export bug, files are written outside the repository working directory as a direct result of opening the malicious repository in Desktop.

Note: I was not able to fully enumerate every call site that sets `allowFileProtocol = true` (matches were found in `app-store.ts` and `dispatcher.ts` but not fully inspected due to iteration limits), so the exact set of user-triggerable flows (versus Desktop-internal/test-only flows) that pass `true` should be verified before treating this as fully confirmed exploitable in production; a Devin session with full repo access is recommended to trace all callers of `updateSubmodulesAfterOperation`/`checkoutBranch`/`checkoutCommit` and confirm whether `allowFileProtocol` can be `true` for repositories not created locally by the user.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
