### Title
DID transfer does not clear the recovery `backup_ids` list, letting a seller retain a path back to ownership after selling the DID - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
`DIDWallet.transfer_did()` moves a DID singleton to a new owner's puzzle hash but preserves the DID's `backup_ids` (recovery list) unless the caller explicitly clears it beforehand. This mirrors the Footium bug class: a privileged capability set by the previous owner (there: ERC20/ERC721 approvals on an escrow; here: the recovery/backup DID list on a DID singleton) is not reset on transfer of the underlying asset, so the seller retains latent authority over the asset after it has changed hands.

### Finding Description
`transfer_did` builds the new inner puzzle for the recipient by reusing the existing `backup_ids` and `num_of_backup_ids_needed` from `self.did_info`, only clearing them via `reset_recovery_list()` if that helper determines that clearing is safe (i.e., the list is already empty) — otherwise the recovery configuration is carried straight into the new owner's puzzle: [1](#0-0) 

The `get_innerpuz_for_new_innerhash` helper explicitly documents this as a known, un-enforced responsibility of the seller: [2](#0-1) 

`reset_recovery_list()` only returns the reset hash when `num_of_backup_ids_needed == 0` and `backup_ids` is already empty — otherwise it returns `None`, i.e., it does not proactively clear a populated recovery list on transfer: [3](#0-2) 

The CLI/RPC surface reinforces that clearing the recovery list is an opt-in, seller-controlled action (`reset_recovery` flag on the transfer command), not an automatic invariant of the DID singleton transfer itself: [4](#0-3) 

The `DIDTransferDID` request type in fact currently forces `with_recovery_info=True` and rejects attempts to disable it, meaning recovery information is always propagated on transfer through this endpoint: [5](#0-4) 

This is structurally the same defect pattern as the Footium report: a stateful "authorization" object bound to an asset (there: token approvals inside `FootiumEscrow`; here: `backup_ids`/`num_of_backup_ids_needed` inside the DID inner puzzle) is not reset when the asset's ownership (the club NFT / the DID singleton) is transferred to a new party, letting the previous owner retain a privileged lever over the asset.

### Impact Explanation
If a DID seller configures `backup_ids` to include an address/DID they control (or simply leaves an existing pre-configured recovery list untouched) and then sells/transfers the DID to a buyer without explicitly resetting the recovery list, the seller retains recovery-tier control over the DID inner puzzle state that ships with the transferred coin. Because DID recovery configuration is curried directly into the puzzle hash and is preserved verbatim across `transfer_did`, a buyer who is not aware of, or does not manually clear, the recovery list inherits an asset whose ownership can potentially be contested/reclaimed by the recovery DIDs the seller retained. This affects DID identity, and by extension any NFTs tied to that DID via ownership layer, undermining the buyer's expectation of exclusive ownership after a completed transfer — a concrete instance of unauthorized/unexpected control over a transferred asset.

### Likelihood Explanation
Likelihood depends on user/tooling behavior rather than a protocol-level enforced invariant: the wallet CLI defaults `reset_recovery` to `False` (i.e., "keep recovery info") for the `did transfer` command, and the newer `DIDTransferDID` RPC request type hard-codes `with_recovery_info=True`, disallowing callers from disabling it altogether. Combined with the explicit code comment noting the seller "should clean the recovery list" as a manual precaution, this makes retention of the recovery list on transfer the default/likely path unless a user actively knows to reset it — a reasonably likely misuse scenario for any DID marketplace/transfer flow.

### Recommendation
- Make recovery-list clearing the default behavior of `transfer_did`/`DIDTransferDID`, requiring an explicit opt-in (with clear warnings) to preserve the recovery configuration across an ownership transfer, rather than defaulting to preservation.
- Reconsider forcing `with_recovery_info=True` unconditionally in `DIDTransferDID.__post_init__`, since that removes the caller's ability to reset recovery info via that RPC path.
- Surface a prominent warning in wallet UX/CLI when transferring a DID with a non-empty `backup_ids` list, so buyers can verify recovery configuration was cleared before accepting a transfer.

### Proof of Concept
1. Attacker creates a DID wallet and sets `backup_ids = [attacker_secondary_did]`, `num_of_backup_ids_needed = 1` (a legitimate recovery setup).
2. Attacker lists/sells the DID to Victim and calls `transfer_did`/`did transfer` without passing `reset_recovery` (default `False`), or via the `DIDTransferDID` RPC, which always keeps `with_recovery_info=True`.
3. Because `reset_recovery_list()` only clears the hash when the list is already empty (`chia/wallet/did_wallet/did_wallet.py:1017-1032`), the resulting new DID inner puzzle sent to Victim still curries in `backup_ids=[attacker_secondary_did]` and `num_of_backup_ids_needed=1`.
4. Victim now owns a DID singleton whose puzzle still encodes the attacker's recovery DID as an authorized recovery party, a fact not obvious from the DID address alone.

Note: I was not able to fully confirm in this session whether the chialisp-level DID recovery spend path (the `-24`/attest mechanism referenced in `create_recovery_message_puzzle`) is still exercised by any wallet RPC in this snapshot — grep for `create_recovery_spend`/`recovery_spend` only matched `CHANGELOG.md`, suggesting the interactive multi-party recovery flow may have been reduced/removed from the wallet layer. If that flow is fully non-functional, the practical severity of this finding is reduced to "stale/misleading recovery metadata persisting on the puzzle" rather than an actively exploitable recovery-based takeover; this would need verification against the actual `.clsp` DID inner puzzle logic and any remaining RPC endpoints that consume `backup_ids`, which the indexed code search did not surface.

    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash
