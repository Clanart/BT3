### Title
Untrusted repository file paths bypass repository-boundary checks in `revealInFileManager`/discard-changes trash flow, allowing symlink-based writes/reads outside the repo - ([File: app/src/lib/app-shell.ts])

### Summary
`app-shell.ts`'s `revealInFileManager` and `git-store.ts`'s `discardChanges` build absolute filesystem paths from a `WorkingDirectoryFileChange.path` value using `Path.join`/`Path.resolve` against `repository.path`, with no check that the resolved path actually stays inside the repository. This is the exact same class of bug described in the RSCO-5 report: a value that originates from attacker-controlled content (here, file/directory entries introduced by a cloned/checked-out repository) is trusted to stay within a bounded region (repository working directory ≈ zkvm's user memory space) without an explicit containment check, while sibling code elsewhere in the same codebase (Copilot conflict resolution, `openRepositoryFromUrl`) was hardened with `resolveWithin` specifically to close this gap.

### Finding Description
`app/src/lib/path.ts` defines `resolveWithin(rootPath, ...pathSegments)`, whose doc comment states it guarantees the resolved path "reside[s] at, or underneath" `rootPath`, and its test suite explicitly proves it rejects symlink-based escapes: [4](#0-3) . This helper was added and wired into three call sites that read the intent from the comments — `dispatcher.ts`'s deep-link file opener, `copilot-conflict-context.ts`'s conflict-hunk reader, and `app-store.ts`'s Copilot conflict-resolution writer — all guarding against "path traversal and symlink escapes" for paths that ultimately derive from checked-out repository content: [5](#0-4) [6](#0-5) .

However, `revealInFileManager` — reachable from many context menus over `WorkingDirectoryFileChange.path`/`CommittedFileChange.path` (changes list, conflict resolution UI, PR files-changed view, history view) — still does a raw `Path.join(repository.path, path)` with no equivalent check: [1](#0-0) . The `IAppShell` interface itself documents the danger ("Do not use this method with non-validated paths") for `openPath`/`showFolderContents`, but `revealInFileManager`, `openFile`/"Open with Default Program", and "Open in External Editor" menu actions all pass raw joined paths built from repo-reported file entries: [7](#0-6) [8](#0-7) .

More seriously, `discardChanges` in `git-store.ts` uses `Path.resolve(this.repository.path, file.path)` (unbounded resolution — resolves `..` segments freely) as the target passed to `shell.moveItemToTrash`/`rm`: [9](#0-8) . If a working-directory entry's path can be steered (e.g., via a directory that git checked out as a symlink pointing outside the repository, with subsequently-untracked entries appearing to live "under" it), `Path.resolve`/`Path.join` will happily construct an absolute path outside the repository, and the code path performs a destructive filesystem operation (permanent delete via `rm`, or a trash-move) on it — with no `resolveWithin`-style containment check to stop it, unlike the Copilot write path that performs an analogous "write file at attacker-influenced relative path" operation and was hardened.

### Impact Explanation
If the resolved path can be pushed outside `repository.path` (via a symlink checked out from the malicious repository, a directory a submodule/checkout places at an unexpected location, or any future refactor that feeds a non-repo-relative string into these functions), the consequences are: (1) `discardChanges`'s trash/`rm` path is a genuine destructive file-write primitive outside the repo directory — silent data loss for arbitrary files reachable through the symlink target; (2) `revealInFileManager`/`openFile`/"Open in External Editor" reveal or hand off arbitrary host paths to the OS shell or user-configured external editor, which is an information/attack-surface expansion beyond the intended repository sandbox. This matches the Impact criteria: file write/read outside the repo, from an attacker-controlled cloned/checked-out repository.

### Likelihood Explanation
Medium-low but plausible without any unnatural user steps: opening/cloning a malicious repository and interacting with ordinary UI affordances (discard changes, reveal in Finder/Explorer, open in editor) are all normal user actions the report's threat model already allows. The exact reachability of an out-of-repo path via git-checked-out symlinks is bounded by modern git's own symlink-checkout protections (`core.protectNTFS`/`protectHFS`), which is why this is flagged as Medium-likelihood rather than trivially exploitable — but Desktop's own path-construction code provides zero defense-in-depth here, in contrast to the Copilot/deep-link code paths that were deliberately hardened against exactly this scenario.

### Recommendation
Route every place that turns a repository-relative, git-reported `file.path`/`oldPath` into an absolute filesystem path through `resolveWithin(repository.path, path)` (or an equivalent containment check) before using it in `revealInFileManager`, `openFile`, "Open in External Editor" handlers, and — most importantly — `discardChanges`'s trash/`rm` operations, mirroring the pattern already used in `copilot-conflict-context.ts` and `app-store.ts`'s Copilot resolution flow. Reject or skip any file entry whose resolved path escapes the repository root, exactly as `openRepositoryFromUrl` and the Copilot flows already do.

### Proof of Concept
Not independently executable from static analysis alone (would require validating exact `git checkout` symlink-protection behavior on each OS/git version). Conceptual PoC: clone a malicious repository that checks out a tracked symlink `evil -> /Users/victim/Documents` (or an OS-specific equivalent) at the repo root; in Desktop, if any working-directory entry is subsequently reported with a path rooted under `evil/`, right-clicking "Discard Changes" on it calls `Path.resolve(repository.path, 'evil/<name>')` in `git-store.ts` and moves/deletes the resolved (out-of-repo) target via `shell.moveItemToTrash`/`rm`, with no `resolveWithin` check to stop it — unlike the equivalent Copilot file-write path, which does perform this check.

**Caveat:** I could not fully verify, from static code alone, whether current git's symlink-checkout protections (`core.protectNTFS`/`protectHFS`, enabled by default in modern git and dugite) fully block the "untracked file under a checked-out symlink directory" scenario in all supported OS/git-version combinations Desktop ships with — this is the key open question determining whether the missing `resolveWithin` check in `app-shell.ts`/`git-store.ts` is a genuinely triggerable escape or a defense-in-depth gap. A Devin session with terminal access could construct and run the PoC repository against the actual dugite/git version bundled with this app to confirm exploitability.
