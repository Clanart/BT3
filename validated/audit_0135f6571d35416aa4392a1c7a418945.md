### Title
Partial-commit staging re-fetches the diff independently of the line-selection snapshot, allowing repository-driven content shifts to silently commit unintended lines - (File: `app/src/lib/git/apply.ts`)

### Summary
The Sherlock bug's broken invariant is "eligibility is decided against one data source (EMA), but the seizure amount is computed against a different, live data source (spot), with no re-validation that the two agree." The Desktop analog is structurally identical: a user's partial-commit line selection (`DiffSelection`) is built by index against a diff snapshot rendered in the UI, but `applyPatchToIndex` independently re-fetches a *fresh* diff from disk at staging time and re-applies that index-based selection to it, without verifying the fresh diff still matches the one the user reviewed.

### Finding Description
When a user stages part of a file (hunk/line-level selection), the UI computes a `DiffSelection` against a diff object it currently holds, via `changeFileLineSelection` (`app/src/ui/dispatcher/dispatcher.ts`, `app/src/lib/stores/app-store.ts`). That selection is purely `absoluteIndex`-based (line offsets within the diff), as used in `formatPatch`: [1](#0-0) 

When the commit is actually created, `applyPatchToIndex` does **not** reuse the diff the selection was made against — it calls `getWorkingDirectoryDiff(repository, file)` again, fetching a brand-new diff from the current on-disk state, and then feeds that fresh diff plus the old index-based `file.selection` into `formatPatch`: [2](#0-1) [3](#0-2) 

`stageFiles` drives this per-file for every partially-selected file just before commit: [4](#0-3) 

There is no guard anywhere in this path comparing the diff used to build the selection against the diff used to format the patch (e.g. no hash/etag/hunk-count equality check). If the working-directory file content changes between the moment the user selects lines in the Changes view and the moment `applyPatchToIndex` runs, the line-index offsets in `file.selection` are silently reinterpreted against different hunk boundaries in the newly fetched diff. `formatPatch`'s selection-vs-content mismatch handling (dropping/keeping lines based on `file.selection.isSelected(absoluteIndex)`) has no way to detect that "index 17" no longer refers to the same logical line the user actually clicked.

A realistic, attacker-controlled trigger for the content shift is repository-attribute-driven text normalization, which — unlike custom clean/smudge filter *drivers* — does not require any local trust configuration to execute. A malicious/compromised repo can ship a `.gitattributes` (`text=auto`, `eol=lf/crlf`, keyword expansion via built-in attributes) that Desktop applies automatically on checkout/re-checkout events (`app/src/ui/add-repository/git-attributes.ts` shows Desktop itself writing such directives, confirming these attributes are honored). If checkout-time normalization re-runs (e.g., after a stash pop, branch switch performed by the same window, or an external editor triggering a line-ending rewrite consistent with the repo's own `.gitattributes`) while the Changes view's line-selection state is still alive from a previous diff render, `applyPatchToIndex`'s independent re-fetch can produce a hunk layout that no longer lines up with the indices in `file.selection`.

### Impact Explanation
This falls into the explicitly valid "silent corruption of what the user commits or pushes" category. If line offsets shift, `formatPatch` can include lines the user explicitly deselected (accidentally committing/pushing content they intended to exclude — e.g. secrets, debug code, or unrelated changes) or exclude lines the user selected (silently dropping intended changes), with **no error, warning, or diff shown before the commit lands**. The commit is created and, in typical workflows, pushed automatically or shortly after, so the corrupted content leaves the local machine.

### Likelihood Explanation
The likelihood is constrained rather than trivial: it requires a real content shift on disk between the selection UI render and the staging call, and Desktop's UI generally re-renders the diff on file-system-watcher events, which narrows (but per the retrieved code, does not provably close) the race window. I could not confirm in the time available whether `DiffSelection` (in `app/src/models/diff/diff-selection.ts`) carries any content fingerprint that `applyPatchToIndex`/`formatPatch` check before applying a stale selection — this is the key open question that would determine whether the window is actually exploitable or already effectively mitigated by re-render invalidation elsewhere in the store.

### Recommendation
- Tie `DiffSelection` to a content fingerprint (e.g. hash of the diff text or per-hunk headers) computed when the selection was made, and have `applyPatchToIndex` verify the freshly-fetched diff matches that fingerprint before applying `formatPatch`.
- If the fingerprint doesn't match, abort staging for that file and force a UI re-diff/re-selection instead of silently applying stale offsets to new content.
- Apply the same fix (or reuse the same primitive) in `discardChangesFromSelection` / `formatPatchToDiscardChanges`, which has the identical index-vs-fresh-diff pattern.

### Proof of Concept
Not fully constructible from the retrieved code alone, since confirming exploitability requires verifying `DiffSelection`'s internal representation and whether any store-level guard invalidates selections on file-watcher-detected changes (file not fully reviewed: `app/src/models/diff/diff-selection.ts`). Conceptually:
1. Modify a tracked file in a repo whose `.gitattributes` triggers line-ending/text normalization.
2. In Desktop's Changes view, select a subset of lines in the resulting diff (partial stage).
3. Before committing, trigger a re-checkout/normalization event that shifts hunk boundaries (e.g., stash+pop, or switching branches and back) without the Changes view discarding the stale `DiffSelection`.
4. Commit; inspect the resulting commit diff via `git show` to check whether the staged lines correspond to the originally selected content or to shifted lines.

Given the unresolved verification gap noted above, treat this as a **candidate** finding requiring confirmation of `diff-selection.ts` internals rather than a fully proven exploit chain.
