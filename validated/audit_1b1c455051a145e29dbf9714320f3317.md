### Title
Unauthenticated operator attribution in `payout_tx` OP_RETURN allows misattributed reimbursement - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The `payout_tx` that fronts a Citrea withdrawal binds the user's payment (input #0 → output #0) with `SIGHASH_SINGLE | ANYONECANPAY`, but the OP_RETURN output that names the "fronting operator" is **not covered by any signature at all** — it is added by whoever assembles and broadcasts the final transaction. The bridge's payer-attribution logic (`update_finalized_payouts`, `get_first_unhandled_payout_by_operator_xonly_pk`, `is_kickoff_malicious`) trusts this OP_RETURN field as proof of who fronted the peg-out, without verifying that the named operator actually funded the transaction. This breaks the same binding class as the Aloe courier bug: "the entity credited" vs "the entity that actually paid."

### Finding Description
`create_payout_txhandler` builds the payout transaction with only the user's key-spend witness set on input #0: [1](#0-0) 

The user's signature uses `SinglePlusAnyoneCanPay`, which only commits to input #0 and output #0 — additional funding inputs and the OP_RETURN output are entirely unconstrained by it: [2](#0-1) 

In `Operator::withdraw`, this same unauthenticated pattern is used: the operator's own xonly pubkey is stuffed into the OP_RETURN and the transaction is funded via wallet RBF, with only the pre-existing user signature verified: [3](#0-2) 

Any party capable of constructing a Bitcoin transaction whose input #0/output #0 match the user's presigned `SinglePlusAnyoneCanPay` signature (obtainable once observed in the mempool, in a prior broadcast attempt, or from the Citrea-side withdrawal registration data) can add their own funding input, front the withdrawal themselves, and place an **arbitrary registered operator's xonly-pubkey** in the OP_RETURN instead of their own.

Downstream, the chain-sync logic blindly extracts this OP_RETURN value and records it as the "payer": [4](#0-3) 

That value is written straight into the `withdrawals` table via `update_payout_txs_and_payer_operator_xonly_pk` and later read back by each operator's own automated payout checker, filtered only by the operator's own xonly public key: [5](#0-4) 

The `PayoutCheckerTask` picks up any such "unhandled payout" automatically and starts the kickoff/reimbursement process on the operator's behalf: [6](#0-5) 

Crucially, malicious-kickoff detection only checks that the (unauthenticated) OP_RETURN pubkey equals the kickoff sender's pubkey — never that the named operator actually funded the payout output: [7](#0-6) 

and the equivalent operator-side check has the identical gap: [8](#0-7) 

Because the SPV/LCP/bridge-circuit checks only verify that *a* valid payout transaction paying the correct amount to the correct output was included in a block matching the committed blockhash — not who funded it — a forged attribution passes every downstream validation. The named (but non-paying) operator's automation will consequently execute a full kickoff and be reimbursed via the round/collateral mechanism for a peg-out it never funded.

**Binding broken:** `operator credited as payer (OP_RETURN pubkey)` should equal `operator who funded/broadcast the payout output`, but nothing enforces this equality — the OP_RETURN is neither signed by the named operator nor bound by the user's partial signature.

### Impact Explanation
This matches the Critical bucket "an operator reimbursed for a payout it never funded." An unprivileged party who fronts a withdrawal (using their own BTC to pay the user-signed output) can name any other registered operator in the OP_RETURN. That operator's automated `PayoutCheckerTask` will then autonomously initiate a kickoff and successfully claim reimbursement from the round/collateral pool for a payment it never made, since every on-chain verification step (SPV inclusion, blockhash commitment, LCP/state proof) is satisfied by the real (but misattributed) transaction. This produces a genuine, unearned outflow of bridge/collateral value that isn't backed by that operator's own fronting, i.e., a misattributed reimbursement / bridge-value leak.

### Likelihood Explanation
The attacker needs no privileged role (verifier/operator/aggregator/security-council), no key compromise, and no majority hashrate — only the ability to observe a presigned `SinglePlusAnyoneCanPay` payout signature (visible once used in any mempool transaction or surfaced through the Citrea withdrawal-registration flow) and enough capital to front the fixed output amount, exactly like a legitimate operator would. The only "cost" is fronting the payment itself; there is no additional cost to mislabel the OP_RETURN attribution field, making this cheap to execute as a griefing/misattribution vector against any target operator whose xonly pubkey is public.

### Recommendation
Bind the OP_RETURN operator-attribution field to the actual funding party cryptographically — e.g., require the named operator's signature over the full transaction (including the OP_RETURN and funding inputs), or otherwise verify during `is_kickoff_malicious`/`validate_payer_is_operator` that the operator claiming reimbursement supplied the funding input(s) of the payout transaction (e.g., by checking the additional inputs' provenance/signature belongs to that operator), not merely that the unauthenticated OP_RETURN bytes match their pubkey.

### Proof of Concept
1. Operator A (or the Citrea backend) reveals/broadcasts (or an observer captures from mempool) a valid `SinglePlusAnyoneCanPay` user signature over `(input_outpoint, output_txout)` for withdrawal `W`, exactly as constructed in `create_payout_txhandler` / `Operator::withdraw`. [9](#0-8) 
2. Attacker (or any operator B who wants to grief a competitor) builds their own transaction reusing input #0/output #0 (with the valid witness), adds their own funding input(s) covering the output amount plus fee, but sets the OP_RETURN to victim operator C's xonly pubkey instead of their own. [10](#0-9) 
3. Attacker broadcasts and gets this transaction confirmed before A's/legit version.
4. Verifier chain-sync records `payout_payer_operator_xonly_pk = C` for withdrawal `W`. [11](#0-10) 
5. Operator C's `PayoutCheckerTask` finds this "unhandled payout" tagged with its own key and automatically triggers `handle_finalized_payout` → kickoff → reimbursement, even though C never funded the payout output. [12](#0-11) 
6. All subsequent malicious-kickoff and payer-validation checks pass because they only compare the unauthenticated OP_RETURN pubkey to the kickoff sender's pubkey, never verifying actual funding. [7](#0-6)

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
