### Title
Missing zero-address check on individual validator reward addresses in `assignStakingRewards` permanently burns staking rewards - (File: kaiax/reward/impl/getter.go)

### Summary
`assignStakingRewards` (and its Flex counterpart) allocates each qualifying CN's excess-stake reward directly to `cn.RewardAddr` sourced from `StakingInfo` without ever validating that the address is non-zero, unlike the KIF/KEF/KPF fund addresses in the same package which are explicitly checked with `common.EmptyAddress(...)` before use. If a validator's on-chain reward address (read from the AddressBook/AddressBookV2 system contract) is unset or zero — e.g. immediately after a CN is registered/staked but before its reward address is configured, or after a mis-ordered admin update — every block's `FinalizeState` will silently `AddBalance` that validator's staking reward to `0x0`, permanently burning it.

### Finding Description
`kaiax/reward/impl/getter.go`'s `assignStakingRewards` builds a `cnTotalStakingMap` keyed by `cn.RewardAddr` and allocates `alloc[cn.RewardAddr] = reward` for every consolidated node whose staking amount exceeds `minStake`: [1](#0-0) 

This differs from the immediately adjacent `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` functions in the same file, which explicitly guard KIF/KEF/KPF fund recipients with `common.EmptyAddress(...)` checks before crediting them, redirecting the amount to the proposer if the fund address is unset: [2](#0-1) [3](#0-2) 

No equivalent guard exists for `cn.RewardAddr`. The resulting `RewardSpec.Rewards` map (which may contain the zero address as a key) is consumed directly in block finalization: [4](#0-3) 

`state.AddBalance(addr, amount)` performs an unconditional balance credit; if `addr` is `common.Address{}`, the minted/fee reward is credited to the zero address, which is unspendable — effectively burning it every block for as long as the condition persists.

`RewardAddrs` (and thus `cn.RewardAddr`) is populated straight from the AddressBook/AddressBookV2 system-contract call results with no zero-address filtering at the staking layer either: [5](#0-4) [6](#0-5) 

The only zero-address sanity check performed at this layer is on the shared `kefAddr`/`kifAddr` fund addresses (which falls back to `emptyStakingInfo`), not on individual `rewardAddrs` entries: [7](#0-6) 

### Impact Explanation
This falls under "staking and reward distribution" and results in a concrete, protocol-visible value-loss/reward-misdirection: a validator's earned KAIA reward is sent to the unspendable zero address instead of the validator (or, per the pattern used for KIF/KEF, redirected to the proposer as a fallback). Because block finalization is deterministic and mandatory (`FinalizeState` is invoked on every block for every full/consensus node), this is not a transient failure — any block during the window where a qualifying validator's registered reward address is zero will burn that validator's reward share, with no way to recover the funds and no error/log path recording it as anomalous (the code path treats it as a normal, successful allocation). This is a supply-accounting/economic-fairness defect reachable purely through validator/staking-registration data, one of the explicitly in-scope areas (staking and reward distribution).

### Likelihood Explanation
Medium. The zero-address condition requires a validator to be counted in `ConsolidatedNodes()` with staking amount ≥ `minStake` while its `RewardAddr` field from AddressBook/AddressBookV2 is zero. This can occur during CN onboarding races (staking registered before/without a reward address configured), migration/registration bugs, or a legitimate operator oversight — it does not require an attacker; it is a data-validation gap that turns an ordinary configuration mistake into an unrecoverable burn instead of a graceful fallback, which is exactly the failure mode the referenced report warns about ("accidentally... resulting in ... unusable"/"permanently locked").

### Recommendation
Short term: in `assignStakingRewards` (and `assignStakingRewardsFlex`), skip or redirect (e.g., to the proposer, mirroring the KIF/KEF/KPF pattern) any CN whose `RewardAddr` is `common.EmptyAddress`, instead of silently allocating to the zero address. Apply the same `common.EmptyAddress` check consistently wherever `cn.RewardAddr`/`sInfo.RewardAddrs[idx]` values are consumed for balance transfers (including `GetRewardAddress` in `blockstate.go`).

Long term: validate/sanitize all address-typed fields returned from AddressBook/AddressBookV2/MultiCall system-contract calls at the staking module boundary (`parseCallResult`/`parsePermissionlessCallResult`) rather than only at the point of use, so that a zero reward address is treated uniformly (e.g., excluded from reward eligibility or logged as a misconfiguration) across all downstream consumers.

### Proof of Concept
1. Register/stake a CN node via the AddressBook (or AddressBookV2) such that its staking amount exceeds `reward.minstake`, but its associated reward address entry is left as `address(0)` (unset), which the AddressBook contracts do not appear to reject for individual CN reward-address fields (only the shared KIF/KEF sanity check exists at the staking layer, per `kaiax/staking/impl/getter.go:304-311`).
2. Block proposer's `FinalizeState` calls `GetDeferredReward` → `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` → `assignStakingRewards`, which computes `alloc[common.Address{}] = <reward amount>` for that node (`kaiax/reward/impl/getter.go:514-531`).
3. `FinalizeState` then executes `state.AddBalance(common.Address{}, amount)` for every subsequent block while the condition holds (`kaiax/reward/impl/blockstate.go:53-55`), permanently burning that validator's staking-reward share with no recovery path and no distinguishing error from a normal successful distribution.

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
