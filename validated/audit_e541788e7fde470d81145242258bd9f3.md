### Title
Governance-settable `GasTarget = 0` causes division-by-zero panic in KIP-71 base fee computation - (File: params/kip71_config.go)

### Summary
`KIP71Config.GasTarget` can be set to `0` through a governance vote because its `FormatChecker` is a no-op that accepts any `uint64`, unlike `BaseFeeDenominator`, which has an explicit non-zero format check and even a defensive runtime fallback. When `GasTarget == 0`, `NextMagmaBlockBaseFee()` divides by `gasTarget` and panics with a division-by-zero error.

### Finding Description
The governance parameter table defines `Kip71GasTarget` with `FormatChecker: noopFormatChecker`, meaning no validation is performed on submitted values, in contrast to `Kip71BaseFeeDenominator`, which explicitly rejects `0`: [3](#0-2) 

`NextMagmaBlockBaseFee()` in `params/kip71_config.go` defends against `BaseFeeDenominator == 0` by substituting a fallback value: [4](#0-3) 

However, no equivalent guard exists for `GasTarget`. When `parentGasUsed != gasTarget` (which is true whenever `gasTarget == 0` and any gas was used), the code computes: [5](#0-4) 
and an analogous division in the decreasing-usage branch: [6](#0-5) 

Both branches call `x.Div(x, new(big.Int).SetUint64(gasTarget))`. Go's `big.Int.Div` panics on division by zero when the divisor is `0`, which is exactly the analog of the reported "Division by Zero" bug pattern (an unguarded division whose denominator can be driven to zero by reachable input), just manifesting in the KIP-71 base-fee computation instead of a liquidation flow.

`NextMagmaBlockBaseFee` is invoked both when verifying headers (`VerifyMagmaHeader`) and when computing/predicting the next base fee (e.g., in `feehistory.go`'s `processBlock`, called from `eth_feeHistory` RPC and internally during block assembly), so the panic is reachable both during ordinary block processing by every node and via public RPC calls that use `kip71Config.NextMagmaBlockBaseFee`. [7](#0-6) 

### Impact Explanation
If `Kip71GasTarget` is voted to `0` (a plausible misconfiguration or malicious governance proposal, since no format validation prevents it), every node computing the next block's base fee — during header verification, block finalization, and `eth_feeHistory`/gas price RPC calls — will panic. This causes a chain-wide crash/halt (denial of service across all nodes) rather than a localized transaction revert, which is a more severe consequence than the original bug report's failed liquidation. This falls squarely within the "KIP-71 pricing" and "governance parameters" categories in scope, and results in a consensus-critical process failing on all honest nodes simultaneously (equivalent to state-divergence-inducing halt / acceptance-of-invalid-configuration impact).

### Likelihood Explanation
Governance parameter changes for KIP-71 fields are a normal, expected mechanism (used to tune `GasTarget`, `BaseFeeDenominator`, etc.), and the code demonstrates that the developers were aware `BaseFeeDenominator == 0` is dangerous (they added an explicit check + fallback for it) but did not apply the same protection to `GasTarget`. This asymmetry strongly suggests an oversight rather than an intentional design choice, and it can be triggered by a single governance vote (from a governing node/council member in `single`/other governance modes) without needing any complex conditions — the very next block after activation with `parentGasUsed != 0` triggers the panic.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s check), and additionally add a defensive runtime fallback in `NextMagmaBlockBaseFee()` for `gasTarget == 0` (e.g., treat it as `parentGasUsed == gasTarget` no-op case or substitute a safe default), so that even a value that bypasses format checking (e.g., legacy/pre-existing chain configs) cannot cause a panic.

### Proof of Concept
1. Submit a governance vote (or set via chain config) `governance.kip71.gastarget = 0` under a governance mode that allows single/majority approval; `NewVoteData` accepts it because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`. [2](#0-1) 
2. Once the parameter activates (`ParamSet.GasTarget == 0`), the next block header's base fee is computed via `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` in `kaiax/gov/impl/api.go`'s `ToKip71Config()`-derived config.
3. If `parentHeaderGasUsed > 0` (any transaction was included in the parent block), the code enters the `parentGasUsed > gasTarget` branch and executes `x.Div(x, new(big.Int).SetUint64(0))`. [5](#0-4) 
4. `big.Int.Div` panics with "division by zero", crashing the node process during header verification/finalization on every node in the network, and also crashing `eth_feeHistory` RPC handling. [7](#0-6)
