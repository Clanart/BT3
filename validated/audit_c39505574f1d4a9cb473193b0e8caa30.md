### Title
`SignableTransaction::new` computes `needed_fee` on a weight/vbytes estimate that excludes the OP_RETURN `data` output, so the signed transaction underpays its fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` supports an optional `data` parameter which appends an OP_RETURN output to the transaction. However, both calls to `calculate_weight_vbytes` pass only `payments` as the output set — the OP_RETURN output is never included in the size estimate. Analogous to the LiFi bug where the `_depositAndSwap` variant that reserves funds for fees isn't used, the fee-reserving calculation here is run against a transaction shape that omits the extra output, producing a `needed_fee` and actual fee below what the transaction's real vsize requires.

### Finding Description
In `SignableTransaction::new`:

- The OP_RETURN output is appended to `tx_outs` at `send.rs:194-202` when `data` is `Some`.
- The weight/vbytes used for the fee are computed from `payments` only: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, and the with-change recompute at lines 225-227 also uses `payments`.
- `calculate_weight_vbytes` (lines 62-127) builds a mock `Transaction` whose `output` list is derived solely from `payments` plus optional `change`; there is no parameter for, or inclusion of, the OP_RETURN output.
- `needed_fee` is then checked against the minimum relay fee (lines 206-213) and charged in the funds check (lines 215-221) and change computation (line 228) using this undersized vbytes value.

A `data` value of up to 80 bytes is permitted (line 171). An OP_RETURN output adds roughly 9 bytes of output overhead plus the script (`OP_RETURN` opcode + push opcode + up to 80 bytes), i.e. ~90 non-witness bytes ≈ ~90 vbytes that are entirely uncounted in `needed_fee`.

Concretely: with `fee_per_vbyte` at the minimum-passing rate and a base transaction of ~150 vbytes, the code charges ~150 sats of fee, but the real transaction is ~240 vbytes, giving an effective rate of ~0.63 sat/vB — below the 1 sat/vB default minimum relay policy enforced by Bitcoin Core. The same undercount affects the change-value computation, since `fee_with_change` also ignores the OP_RETURN size.

### Impact Explanation
Any `SignableTransaction` created with `Some(data)` pays a lower effective feerate than the caller-specified `fee_per_vbyte`. For transactions near the minimum relay fee, the discrepancy can push the effective rate below `DEFAULT_MIN_RELAY_TX_FEE`, making the fully-signed, consensus-valid transaction non-relayable by default-policy nodes — the spends never confirm and the inputs remain locked until a replacement plan is constructed. Because the OP_RETURN path is used for protocol data outputs, an unprivileged party who can cause data-bearing transactions to be built (e.g., payments/plans carrying a `data` payload) can force the coordinator to produce transactions that underpay relative to the intended rate and may be dropped from mempools. This mirrors the report's impact class: failing to reserve for the additional cost causes the operation to fail at broadcast time.

### Likelihood Explanation
Triggering requires only that a transaction be constructed with the `data` argument populated — the bug is deterministic whenever `data.is_some()`, no edge cases needed. Whether the underpayment causes an outright relay failure depends on `fee_per_vbyte` being near minimum policy; at higher feerates the effect is a silently degraded effective feerate (~90 vbytes of unpaid size) rather than failure. Since `data` supports up to 80 bytes and the code explicitly permits it, this is reachable through normal transaction-building flows rather than misuse.

### Recommendation
Include the OP_RETURN output in the size estimate. Either pass the assembled `tx_outs` (or a count/size of the data output) into `calculate_weight_vbytes` instead of `payments`, or add the OP_RETURN output's serialized size (`TxOut` for `ScriptBuf::new_op_return(data)`) to the weight before computing `needed_fee`. Apply the same fix in the `change` branch so `fee_with_change` reflects the final transaction layout.

### Proof of Concept
```rust
// In networks/bitcoin, inside a test exercising send.rs:

// Inputs exactly covering payments + needed_fee, a change address, and 80-byte data
let data = vec![0xaa; 80];

let tx = SignableTransaction::new(
  inputs,                      // sum = payments + needed_fee + change
  &payments,
  Some(change_script),
  Some(data.clone()),          // OP_RETURN output appended at send.rs:194-202
  1,                           // 1 sat/vB, near DEFAULT_MIN_RELAY_TX_FEE
).unwrap();

// The real transaction includes the OP_RETURN output...
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// ...but needed_fee/vbytes were computed at send.rs:204 via
// calculate_weight_vbytes(tx_ins.len(), payments, None) — payments only.
// The ~90 vB OP_RETURN output was never counted, so:
//
//   effective_rate = tx.fee() / actual_vbytes(tx.transaction())
//                  < fee_per_vbyte
//
// For a ~150 vB base tx: fee paid = ~150 sat, actual vsize ~240 vB
// => ~0.63 sat/vB < 1 sat/vB min relay; the TooLowFee check at
// send.rs:211 passed because it used the undersized vbytes.
```
