### Title
`PayoutCheckerTask` Permanently Frozen by Crafted Payout OP_RETURN Targeting Operator Without Deposit Signatures — (`core/src/task/payout_checker.rs`)

### Summary

`PayoutCheckerTask::run_once()` always fetches the **lowest-index** unhandled payout for the operator and returns a hard error — without marking the entry as handled — when the deposit signatures are absent from the operator's DB. Because the query always returns the same lowest-index stuck entry, the task retries on it forever and never advances to subsequent entries. An unprivileged attacker can manufacture this stuck entry by spending a withdrawal UTXO with an OP_RETURN containing a target operator's xonly pk for a deposit the operator has no signatures for, permanently blocking that operator's reimbursement automation.

### Finding Description

**Root cause — sequential queue with no skip path**

`PayoutCheckerTask::run_once()` fetches the first unhandled payout:

```rust

The underlying query is:

```sql
SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
FROM withdrawals w
WHERE w.payout_txid IS NOT NULL
   AND w.is_payout_handled = FALSE
   AND w.payout_payer_operator_xonly_pk = $1
ORDER BY w.idx ASC
LIMIT 1

If `get_deposit_data_with_move_tx()` returns `None` for the fetched entry, the task immediately returns `Err` without ever calling `mark_payout_handled()`:

`mark_payout_handled()` — the only function that sets `is_payout_handled = TRUE` — is never reached: [3](#0-2) [4](#0-3) 

The task retries every 60 seconds in production, always hitting the same stuck entry, never advancing.

**How the attacker manufactures the stuck entry**

The `payout_payer_operator_xonly_pk` column in the `withdrawals` table is populated by `update_finalized_payouts()` in `verifier.rs`, which extracts the xonly pk from the OP_RETURN of whatever transaction spends the withdrawal UTXO on-chain: [5](#0-4) 

The withdrawal UTXO is a Bitcoin UTXO controlled by the user (the withdrawer). The user can spend it with any OP_RETURN they choose. Attack steps:

1. **Attacker deposits BTC** before operator O joined the federation. Operator O has no deposit signatures for this deposit in its `deposits` table.
2. **Attacker registers a withdrawal** on Citrea for that deposit. The verifier syncs this into O's `withdrawals` table via `update_citrea_deposit_and_withdrawals()`, setting `move_to_vault_txid` to the deposit's move-tx. [6](#0-5) 
3. **Attacker spends the withdrawal UTXO** with a Bitcoin transaction whose OP_RETURN contains operator O's xonly pk (a public value). The verifier sets `payout_payer_operator_xonly_pk = O` and `payout_txid = <attacker_tx>` for that withdrawal row.
4. **`PayoutCheckerTask` for O** picks up this row as the first unhandled payout. `get_deposit_data_with_move_tx(move_to_vault_txid)` returns `None` because O never participated in that deposit. The task returns `Err` and retries forever on the same row.
5. **All subsequent legitimate payouts** that O actually fronted are blocked because the query always returns the lowest-index stuck entry first.

### Impact Explanation

The operator's reimbursement automation (`PayoutCheckerTask`) is permanently frozen. The operator cannot automatically initiate the kickoff → challenge-timeout → reimburse chain for any payout they fronted. If the operator does not notice and manually call `get_reimbursement_txs()` for each affected deposit within the challenge-timeout window, they will miss the reimbursement window and lose their collateral (bridged BTC they fronted). The attacker controls the timing: they can trigger the freeze at the moment most damaging to the operator (e.g., when the operator has many pending payouts near their timeout).

There is no built-in skip or rescue mechanism. The only recovery is a privileged manual DB update (`UPDATE withdrawals SET is_payout_handled = TRUE WHERE idx = N`), which is not exposed through any RPC.

### Likelihood Explanation

The precondition — a deposit made before operator O joined — is satisfied naturally whenever a new operator is added to the federation, which is an expected operational event. The attacker only needs to be a prior bridge user. Operator xonly public keys are public. The attack costs only Bitcoin transaction fees.

### Recommendation

1. **Do not hard-error on missing deposit data.** Instead of returning `Err`, log a warning and skip the entry (advance past it without marking it handled, or mark it with a separate `is_payout_skipped` flag) so subsequent legitimate entries can be processed.
2. **Add an admin RPC** to manually mark a payout entry as skipped/handled, analogous to the `dequeueCrab()` escape hatch recommended in H-2.
3. **Validate OP_RETURN attribution before trusting it.** Before setting `payout_payer_operator_xonly_pk`, verify that the spending transaction is a valid Clementine payout tx (correct script path, correct structure) rather than accepting any OP_RETURN from any spending transaction.

### Proof of Concept

1. Deploy Clementine with operators A, B, C. Make a deposit with those operators → `deposits` table in A/B/C DBs has the entry; operator O (not yet added) has no entry.
2. Add operator O to the federation.
3. Register a Citrea withdrawal for the deposit from step 1. O's `withdrawals` table now has the row with `move_to_vault_txid = T`.
4. Craft a Bitcoin transaction spending the withdrawal UTXO with `OP_RETURN <O_xonly_pk>`. Broadcast it.
5. After finality, O's verifier sets `payout_payer_operator_xonly_pk = O`, `payout_txid = <attacker_tx>`, `is_payout_handled = FALSE` for that row.
6. O's `PayoutCheckerTask` fires. `get_first_unhandled_payout_by_operator_xonly_pk` returns the row. `get_deposit_data_with_move_tx(T)` returns `None`. Task returns `Err`.
7. O now fronts a legitimate payout for a different withdrawal (higher index). `PayoutCheckerTask` still returns the stuck row first. The legitimate payout is never processed automatically. O misses the reimbursement window.

```rust
    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
