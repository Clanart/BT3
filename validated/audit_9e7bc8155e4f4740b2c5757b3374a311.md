### Title
`Debug` impls on `ThresholdCore`/`ThresholdView`/`ThresholdKeys` print `Interpolation::Constant` coefficients, which are the secret key shares - (File: crypto/dkg/src/lib.rs)

### Summary
The Yii 2 advisory concerns secret credentials being written to logs on a failure path (CWE-532). The analog in Serai is that the `Debug` representations of the threshold key structures leak secret material: `Interpolation::Constant(Vec<F>)` derives `Debug` and its vector literally contains "constant coefficients, one for each of the secret key shares", and both `ThresholdCore` and `ThresholdView` emit `.field("interpolation", &self.interpolation)` — printing every secret share in plaintext whenever these types are `{...:?}`-formatted into logs or error reports.

### Finding Description
`Interpolation::Constant` is defined at `crypto/dkg/src/lib.rs:212-221` with `#[derive(... Debug ...)]`. Its documentation states the coefficients are "one for each of the secret key shares" — under Constant interpolation, the coefficient for participant `i` *is* their secret key share (`interpolation_factor` at `crypto/dkg/src/lib.rs:226-249` returns `c[i - 1]` directly, with no blinding).

`ThresholdCore`'s manual `Debug` impl (`crypto/dkg/src/lib.rs:266-276`) carefully redacts `secret_share` via `finish_non_exhaustive()`, but prints `interpolation`, which under Constant interpolation re-exposes the very same secret shares — including *other participants'* shares, not just our own. `ThresholdView`'s `Debug` impl (`crypto/dkg/src/lib.rs:316-329`) does the same, and `ThresholdKeys` derives `Debug` (`crypto/dkg/src/lib.rs:291`), which transitively formats `core`'s `Debug` and also prints `scalar`/`offset` in plaintext.

The surrounding code demonstrates the intended secrecy policy: `SecretShare` in pedpop redacts its bytes (`crypto/dkg/pedpop/src/lib.rs:242-246`), `Encryption` redacts `enc_key` (`crypto/dkg/pedpop/src/encryption.rs:410-420`), and `SignData` redacts `data` (`coordinator/src/tributary/transaction.rs:53-63`). The `interpolation` field breaks that policy. Any failure path that logs a `ThresholdKeys`/`ThresholdView`/signing-machine structure (e.g., `format!("{e:?}")` on a machine embedding keys, or `log::debug!("{view:?}")` by an integrator) writes the full set of secret shares to logs — recoverable by anyone with log access, exactly the CWE-532 shape of the advisory.

### Impact Explanation
Disclosure of `Interpolation::Constant`'s coefficient vector discloses *all* participants' secret key shares for keys generated with Constant interpolation (which `ThresholdKeys::new` permits when `t == n`, e.g. MuSig-style full-participation keys). An attacker with read access to logs — a weaker position than key access — can recover the group private key outright, enabling complete theft of funds controlled by the threshold key. This is secret-key recovery, not merely metadata leakage.

### Likelihood Explanation
Likelihood is conditional rather than direct: the leak fires only when (a) Constant interpolation is in use (restricted to `t == n` setups) and (b) a `ThresholdKeys`, `ThresholdView`, or a type embedding them is `Debug`-formatted into logs/errors. Serai's own crates redact secrets in `Debug`, suggesting the ecosystem treats `Debug` output as log-safe, which makes accidental formatting plausible in downstream processor/coordinator error paths. Because exploitation additionally requires log access, this rates Medium rather than High.

### Recommendation
Manually implement `fmt::Debug` for `Interpolation` that prints only the variant tag (e.g. `"Constant(..)"` / `"Lagrange"`) without the coefficient vector, matching the redaction precedent set by `SecretShare` and `Encryption`. Also consider a manual `Debug` for `ThresholdKeys`/`ThresholdView` omitting `scalar`/`offset`, since whether those tweaks are secret is application-dependent and should not be assumed public.
