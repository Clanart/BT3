### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-shop impersonation - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates an inbound webhook solely by checking the HMAC over the raw request body against the app's shared secret. The shop identity that is subsequently used to route/attribute the webhook — `shop_domain`, read straight from the `X-Shopify-Shop-Domain` request header — is never included in, or cross-checked against, that HMAC computation. [1](#0-0) 

### Finding Description
`hmac_valid?` computes/compares an HMAC-SHA256 solely over `request.raw_post` (`data`), using the app's configured secret(s): [2](#0-1) 

`verify_request` only calls `hmac_valid?(data)`; it never validates `shop_domain` (or any other header) as part of, or bound to, that signature: [3](#0-2) 

Because the HMAC is computed purely from the body, any request carrying a body+signature pair that is valid for *one* shop's webhook delivery remains cryptographically valid when replayed with a different, attacker-chosen `X-Shopify-Shop-Domain` header — the header is completely outside the signed data. Downstream code trusts this header as the "sender" identity for authorization/attribution purposes without any further verification, exactly analogous to the unverified `_srcChainSender` in the referenced report: a message-attribution parameter is accepted and acted upon without being covered by the cryptographic proof that authenticates the payload.

The generated job template built on top of this mechanism uses the unverified `shop_domain` to look up and destructively act on a shop record with no further checks: [4](#0-3) 

The same header-derived value is used generically for all custom-controller/job wiring documented for `WebhookVerification`: [5](#0-4) 

For topics whose body content is static/predictable across shops (e.g. `app/uninstalled`, `shop/redact`, or any topic where the body payload an attacker's own shop receives is identical/predictable to what any other shop would receive), the attacker — who legitimately controls one shop installation and therefore legitimately receives real, validly-signed webhook deliveries for that shop — can capture a `(body, HMAC)` pair from their own store's webhook and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain. `verify_request` will accept it because the HMAC check only covers the (unchanged) body.

### Impact Explanation
An unrelated, unprivileged merchant who has installed the app on their own shop (an "unrelated-merchant" trust level) can force the app to process a webhook attributed to a different (victim) shop, since the shop-attribution header is not authenticated. Depending on the topic and job wired up by the app (which are explicitly recommended/generated by this gem, e.g. `AppUninstalledJob#perform` calling `shop.destroy`), this enables cross-shop impact up to destructive action on another merchant's shop record purely by replaying a self-obtained, validly-signed webhook body with a forged domain header. This is a cross-shop access/impersonation vulnerability rooted in the gem's verification design.

### Likelihood Explanation
Likelihood is high for topics with static/near-static body content, because the attacker only needs to install the app on a single shop (no special privilege) to obtain a legitimately-signed webhook payload, then simply resend it with a modified header — no cryptographic secret needs to be recovered or guessed. It requires knowledge of the target victim's exact shop domain, which is often discoverable/guessable (`*.myshopify.com`).

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` header as trusted shop identity unless it is cryptographically bound to the verified payload. At minimum:
- Bind the shop domain into the HMAC/signature verification (e.g., include it as part of the data verified, or independently verify it against the shop that the topic's payload could only legitimately originate from).
- Where possible, cross-check the shop domain against a shop that is known to have an active, valid session/webhook subscription for that specific webhook id/topic before executing any job logic that reads/writes shop-scoped data, mirroring the recommendation in the source report: validate the entity the action is being taken on behalf of matches the verified sender identity.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and subscribes to a topic with static/predictable body content (e.g. `app/uninstalled`).
2. Attacker uninstalls the app from their store; Shopify delivers a webhook POST to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this exact `(B, HMAC)` pair (they are the legitimate recipient/proxy of the delivery, or intercepts it via their own infrastructure since it targets their own app/shop).
4. Attacker sends a new POST directly to the app's webhook receive endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `WebhookVerification#verify_request` calls `hmac_valid?(B)`, which succeeds because it only checks the body, per: [6](#0-5) 
6. The `shop_domain` header is passed downstream to whichever job handles the topic (e.g. `AppUninstalledJob`), and the job executes shop-scoped/destructive logic against `victim-shop.myshopify.com` as if the event genuinely originated from that shop. [7](#0-6)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
