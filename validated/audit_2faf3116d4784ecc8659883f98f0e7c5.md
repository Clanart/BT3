### Title
`ReceivedOutput::read` trusts a serialized scalar offset without verifying it matches the output's script_pubkey, allowing forged spendable-output claims - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput` pairs a Bitcoin `TxOut`/`OutPoint` with the scalar `offset` needed to derive the spending key for that output. `ReceivedOutput::read` deserializes all three fields from raw bytes with no consistency check that `script_pubkey` actually equals `p2tr_script_buf(key + offset*G)` for the wallet key the output will be spent under. An untrusted byte stream can therefore cause an output to be reported as received with an arbitrary offset, producing coins the signer cannot actually spend (or that are attributed to the wrong derived key).

### Finding Description
`ReceivedOutput::read` reads `offset` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns the triple as a valid, spendable output (lines 122–133). There is no cryptographic binding between `offset` and `output.script_pubkey`: the struct stores no base key and performs no recomputation of the expected P2TR script.

`Scanner::scan_transaction` is the only producer that establishes this binding, by looking the script up in `self.scripts` and attaching the registered offset (lines 199–214). Any consumer that ingests `ReceivedOutput`s from serialized form — the wire format produced by `write`/`serialize` (lines 136–148) — bypasses that binding entirely.

Downstream code trusts the deserialized offset. The processor's `Output::key()` recomputes the owning key as `scriptKey - offset*G`, which is self-consistent for *any* supplied pair, so a tampered offset silently re-attributes the output to `key + o_real*G - o_forged*G` rather than erroring. During signing, the offset is applied to the threshold keys for that input, so a mismatched offset makes the multisig sign under a key that does not control the UTXO.

### Impact Explanation
An attacker who controls the serialized `ReceivedOutput` bytes fed to `ReceivedOutput::read` (e.g., an untrusted output source/cache supplying scanner results) can:

- Report outputs as received that are not spendable: claim a real or fabricated `TxOut`/`OutPoint` with any offset. The wallet treats them as owned inputs; the resulting signed transaction is invalid or the input is unspendable, corrupting balance accounting.
- Misattribute ownership: take an output genuinely paying `key + o1*G` and tag it with offset `o2`. The derived key becomes `key + (o1 - o2)*G`, so the funds are booked under a key that cannot spend them, while the signer set produces a useless signature and burns fees attempting the spend.

This maps the report's "unauthorized action triggered by attacker-controlled descriptive bytes" class onto Serai's shape: untrusted description bytes (the serialized offset) are acted on as authoritative authorization data without verification.

### Likelihood Explanation
Reachability requires the integration to receive `ReceivedOutput`s over an untrusted channel rather than producing them solely via local `Scanner` calls. `read`/`serialize` exist precisely for transport/storage, and the API gives callers no way to revalidate the binding without re-running a `Scanner` — which itself cannot detect a forged outpoint. Exploitation needs only crafted bytes; no key material, collusion, or validator misbehavior is required. Impact is integrity of funds accounting rather than direct theft, placing this at Medium.

### Recommendation
Bind the offset to the output at deserialization or first use: either store/recover the base key in `ReceivedOutput` and assert `output.script_pubkey == p2tr_script_buf(key + offset*G)` inside `read`/`sign`, or re-validate every deserialized `ReceivedOutput` against the wallet's `Scanner` (`scanner.scripts` / `scan_transaction`) before admitting it into the spendable set, rejecting any output whose offset is not the registered one for that script.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read:
// 1. Take a real output paying to the wallet's offset-1 script:
//    script = p2tr_script_buf(key + o1 * G)
// 2. Rewrite the offset field to a different scalar o2.
let mut forged = Vec::new();
forged.extend(o2.to_bytes());            // wrong offset
forged.extend(serialize(&txout_o1));     // TxOut paying to key + o1*G
forged.extend(serialize(&outpoint));     // real outpoint

let ro = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
// ro.offset() == o2, but the output pays to key + o1*G.
// Output::key() derives key + (o1 - o2)*G != group key,
// so the funds are reported received yet unspendable,
// and signing applies o2, producing an invalid spend.
```
Root cause is at `networks/bitcoin/src/wallet/mod.rs` lines 122–133 (`ReceivedOutput::read` performs no binding check) versus lines 199–214 (`scan_transaction` is the only path that establishes offset↔script consistency).
