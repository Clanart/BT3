### Title
Malformed `ThresholdKeys` using constant interpolation causes an out-of-bounds panic - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::new` accepts `Interpolation::Constant(Vec<F>)` without checking that the coefficient list contains one coefficient per participant. With any `t = n >= 1` parameter set and an empty or truncated coefficient vector, construction indexes past the end of the vector while deriving the group key. When malformed bytes are supplied through `ThresholdKeys::read` and deserialized into this state, an unauthenticated input can panic the process.

### Finding Description
`ThresholdKeys::new` only validates the participant count, participant indexes, and that constant interpolation is used solely when `t == n`. It does not validate `Interpolation::Constant(c).len() >= n` or, more precisely, that coefficients exist for participants `1..=t` [1](#0-0) .

The interpolation implementation directly indexes the coefficient vector with `c[usize::from(u16::from(i) - 1)]` [2](#0-1) . Immediately afterward, `ThresholdKeys::new` evaluates that interpolation for every participant in `1..=params.t()` while computing `group_key` [3](#0-2) . Therefore, a constant interpolation containing fewer than `t` coefficients deterministically panics.

### Impact Explanation
This is a denial of service reachable with attacker-supplied key material or serialized `ThresholdKeys` data. A malformed object containing `ThresholdParams { t: 1, n: 1, i: 1 }`, a nominal verification share for participant `1`, and `Interpolation::Constant(vec![])` reaches `c[0]` and panics. The same issue applies to larger `t == n` sets with a truncated vector.

The panic occurs during object construction/deserialization validation, before callers can reject the key as invalid. Depending on where `ThresholdKeys::read` or `ThresholdKeys::new` is invoked, this can terminate a signing, recovery, or message-processing task.

### Likelihood Explanation
Likelihood is moderate for APIs that deserialize `ThresholdKeys` from protocol messages, backups, recovery data, or otherwise untrusted bytes. The malformed state is trivial to construct because the missing length precondition is the only defect required; no discrete-log calculation, signature forgery, race, or validator collusion is needed.

For caller-constructed keys, likelihood is lower because a correct caller would normally provide all `n` coefficients. The exposed panic becomes relevant when deserialization admits structurally malformed coefficients or when an API consumer supplies a truncated `Constant` vector.

### Recommendation
Validate constant-interpolation length before indexing it. `ThresholdKeys::new` should require `c.len() == usize::from(params.n())`—or at minimum `c.len() >= usize::from(params.t())`—and return a `DkgError` rather than panic. The same invariant should be enforced during `ThresholdKeys::read` deserialization. A regression test should construct `t == n` keys with empty and truncated `Interpolation::Constant` vectors and assert an error is returned.

### Proof of Concept
```rust
use std::collections::HashMap;
use zeroize::Zeroizing;

use dkg::{Interpolation, Participant, ThresholdKeys, ThresholdParams};
use ciphersuite::Ciphersuite;

fn malformed_constant_keys<C: Ciphersuite>() {
  let participant = Participant::new(1).unwrap();
  let params = ThresholdParams::new(1, 1, participant).unwrap();

  let verification_shares =
    HashMap::from([(participant, C::generator())]);

  // Panics at interpolation_factor(1): c[0] on an empty Vec.
  let _ = ThresholdKeys::new(
    params,
    Interpolation::Constant(vec![]),
    Zeroizing::new(C::F::ZERO),
    verification_shares,
  );
}
```
