### Title
Unbounded `io.ReadAll(r.Body)` in NewRelic/Datadog RPC tracing wrappers bypasses `MaxRequestContentLength`, enabling memory-exhaustion DoS on public RPC endpoint - (File: networks/rpc/http_newrelic.go)

### Summary
When APM tracing is enabled (`NEWRELIC_APP_NAME`/`NEWRELIC_LICENSE` or `DD_TRACE_ENABLED`), every incoming JSON-RPC HTTP request is first passed to `getRPCRequests(r)`, which reads the entire request body into memory via `io.ReadAll(r.Body)` with no size limit, before the core `Server.ServeHTTP` path ever runs its `validateRequest` size check.

### Finding Description
The Kaia RPC HTTP server enforces a configurable request-size ceiling (`common.MaxRequestContentLength`, default 512 KiB) inside `validateRequest` and `newHTTPServerConn` (`io.LimitReader(r.Body, ...)`), which is exactly the fix pattern the referenced advisory (GHSA-9398-5ghf-7pr6 / CVE-2022-39294) describes for `conduit-hyper`.

However, when the optional NewRelic or Datadog HTTP handlers are installed in `NewHTTPServer`, they wrap the entire handler chain and run first: [2](#0-1) 

Both wrapper handlers call `getRPCRequests(r)` unconditionally at the top of the handler, before `handler.ServeHTTP` (which eventually reaches `validateRequest`) is ever invoked: [3](#0-2) [4](#0-3) 

`getRPCRequests` itself performs an unbounded read: [5](#0-4) 

There is no `Content-Length` check, no `http.MaxBytesReader`, and no `io.LimitReader` applied before this `io.ReadAll` call. A client can send a POST request with `Transfer-Encoding: chunked` (avoiding any `Content-Length` header) and stream an arbitrarily large body; `io.ReadAll` will keep growing its internal buffer, consuming memory proportional to the attacker-controlled body size, well beyond the intended 512 KiB (or configured `maxRequestContentLength`) limit — the exact bug class described in the external report (unchecked request length prior to buffering the whole body, `hyper::body::to_bytes` analog is `io.ReadAll`).

### Impact Explanation
Any unauthenticated public RPC caller reaching a Kaia node's HTTP JSON-RPC endpoint (when the node operator has enabled NewRelic or Datadog APM tracing, a supported production feature) can send oversized/chunked bodies repeatedly to force large memory allocations per request, bypassing the node's configured `MaxRequestContentLength` protection entirely for this code path. Concurrent abuse can exhaust node memory, causing process crash or severe degradation — a Denial-of-Service against the RPC endpoint, matching CWE-400/CWE-1284 and the High severity of the referenced advisory.

### Likelihood Explanation
Exploitation requires only a normal HTTP POST/chunked request to a public RPC endpoint — no authentication, no special transaction crafting, and no privileged access. The only precondition is that the node operator has enabled the NewRelic or Datadog tracing integration, which is a documented, supported deployment option (not a malicious/operator-only configuration) intended for production monitoring. Given this, likelihood is Medium-High for nodes running APM tracing.

### Recommendation
Apply the same size enforcement used elsewhere (`common.MaxRequestContentLength`) before reading the body in `getRPCRequests`, e.g. wrap `r.Body` with `http.MaxBytesReader(w, r.Body, int64(common.MaxRequestContentLength))` or `io.LimitReader` prior to `io.ReadAll`, and reject/abort with `413 Request Entity Too Large` when the limit is exceeded, mirroring `validateRequest`'s existing check. Alternatively, invoke `validateRequest` (or an equivalent Content-Length/limit check) before calling `getRPCRequests` in both `newNewRelicHTTPHandler` and `newDatadogHTTPHandler`.

### Proof of Concept
1. Start a Kaia node with the HTTP RPC server enabled and set `NEWRELIC_APP_NAME`/`NEWRELIC_LICENSE` (or `DD_TRACE_ENABLED=true`) so `newNewRelicHTTPHandler`/`newDatadogHTTPHandler` wraps the RPC server.
2. Send a POST request to the RPC HTTP endpoint using `Transfer-Encoding: chunked` (no `Content-Length` header) with a body many times larger than `common.MaxRequestContentLength` (default 512 KiB), e.g. several hundred MB of streamed data.
3. Observe that `getRPCRequests` → `io.ReadAll(r.Body)` buffers the entire body in memory before `validateRequest`'s size check is ever reached, unlike a direct request to the non-instrumented path where `validateRequest` would reject it with `413` based on `Content-Length` (which the attacker can omit).
4. Repeat concurrently to exhaust node memory and induce a crash/OOM, denying RPC service to legitimate callers.
