### Title
Unauthenticated `NonceGen` Flooding Evicts In-Progress Deposit Sessions, Permanently DOSing Deposit Finalization — (`core/src/verifier.rs`, `core/src/rpc/verifier.rs`)

---

### Summary

The `NonceGen` gRPC endpoint on every verifier carries no per-call authentication check. `AllSessions` enforces a hard cap of `MAX_NUM_SESSIONS = 2000` sessions; when the cap is exceeded the **oldest** session is silently evicted. An attacker who can reach the verifier's gRPC port can flood it with 2 000 single-nonce `NonceGen` calls between the moment the aggregator obtains a session ID and the moment `deposit_sign` consumes it. The eviction removes the legitimate deposit session, causing `remove_session_with_id` to return `"Session not found"`, aborting the entire deposit pipeline. The user's BTC remains locked in the deposit address until the `user_takes_after` timelock expires.

---

### Finding Description

**Root cause — `AllSessions::add_new_session_with_id` evicts the oldest session without caller identity checks**

`AllSessions` is the in-memory store for MuSig2 secret nonces on every verifier. [1](#0-0) 

When `sessions.len() >= MAX_NUM_SESSIONS` (2 000), the loop calls `remove_oldest_session()` until the constraint is satisfied, then inserts the new session. The oldest session is determined purely by insertion order (`session_queue`), with no regard for whether it belongs to an active deposit. [2](#0-1) 

**The `NonceGen` RPC handler has no authentication check** [3](#0-2) 

Any caller that can reach the verifier's gRPC port can invoke `NonceGen` with `num_nonces = 1` (the minimum valid value, 132 bytes per session). There is no rate-limit, no caller identity verification, and no deposit-binding in the handler.

**The deposit signing pipeline depends on the session surviving until `deposit_sign`**

The aggregator calls `nonce_gen` on every verifier, receives a `session_id`, and embeds it in the `DepositSignSession` sent back to verifiers. [4](#0-3) 

Inside `deposit_sign`, the verifier immediately calls `remove_session_with_id(session_id)`. If the session was evicted, this returns an error and the entire deposit pipeline aborts. [5](#0-4) 

**Exploit flow (exact analog to M-05)**

| Step | M-05 (Inverse Finance) | Clementine analog |
|------|------------------------|-------------------|
| 1 | Victim calls `repay(500)` | Aggregator calls `nonce_gen` → verifier stores session S with ID X |
| 2 | Attacker sees tx in mempool | Attacker observes the `NonceGenFirstResponse` (session ID is public in the gRPC stream) |
| 3 | Attacker frontruns with `repay(1)` | Attacker calls `nonce_gen(1)` × 2 000 → fills `AllSessions` to `MAX_NUM_SESSIONS` |
| 4 | Victim's `repay(500)` fails: `debt < amount` | Aggregator calls `deposit_sign` with ID X → `remove_session_with_id(X)` returns `"Session not found"` |
| 5 | Victim cannot repay | Deposit pipeline aborts; user's BTC locked until `user_takes_after` |

The attacker needs only 2 000 gRPC calls (each carrying 1 nonce = 132 bytes). Total attacker traffic: ~264 KB per targeted verifier.

---

### Impact Explanation

- **Deposit DOS**: Every in-flight deposit can be aborted by evicting the corresponding nonce session on any one verifier. Because the deposit pipeline requires all N verifiers to succeed, a single verifier's session eviction is sufficient.
- **Temporary BTC lock**: The user's BTC remains in the deposit address. Recovery requires waiting for the `user_takes_after` timelock (configurable; can be weeks on mainnet) before the user can reclaim funds via the script's timeout path.
- **Repeatable**: The attacker can repeat the attack on every retry, permanently preventing deposit finalization for targeted users.
- **No cryptographic break required**: The attack requires only network access to the verifier's gRPC port and the ability to make 2 000 cheap RPC calls.

---

### Likelihood Explanation

- The `NonceGen` handler contains no authentication or rate-limiting logic at the code level.
- The `ClementineVerifier` proto service definition does not mandate mTLS for `NonceGen`.
- The CLI tool exposes `NonceGen` as a direct command, confirming it is intended to be callable by external parties.
- If the verifier's gRPC port is reachable (e.g., on a non-mainnet deployment, or if mTLS is misconfigured), the attack is trivially executable.
- Even with mTLS, any party holding a valid certificate (e.g., another verifier or a watchtower) can mount the attack.

---

### Recommendation

1. **Bind `NonceGen` to a specific deposit context**: Require the caller to supply a deposit outpoint or a signed deposit commitment alongside the nonce request. Reject requests that do not correspond to a known, pending deposit.

2. **Protect active sessions from eviction**: Before evicting the oldest session, check whether it is currently referenced by an active deposit pipeline (e.g., by maintaining a set of "pinned" session IDs). Never evict a pinned session.

3. **Rate-limit `NonceGen` per caller identity**: Enforce a per-connection or per-certificate limit on the number of concurrent nonce sessions.

4. **Enforce mTLS at the code level**: Add a gRPC interceptor that rejects requests from callers without a valid, bridge-registered certificate, rather than relying on deployment configuration.

        let session = self.sessions.remove(&id).ok_or_eyre("Session not found")?;

        self.session_queue.retain(|x| *x != id);

    /// Removes the oldest session from the AllSessions.
    /// Returns the number of bytes removed.
    fn remove_oldest_session(&mut self) -> Result<usize, eyre::Report> {
        match self.session_queue.pop_front() {
            Some(oldest_id) => {
                let removed_session = self.sessions.remove(&oldest_id);
                match removed_session {
                    Some(session) => Ok(Self::session_bytes(&session)?),
                    None => Ok(0),
                }
            }
            None => Err(eyre::eyre!("No session to remove")),
        }
    }
