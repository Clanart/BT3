### Title
Unbounded length-prefixed allocation in `SchnorrAggregate::read` enables memory-exhaustion DoS from untrusted bytes - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` in the in-scope `crypto/schnorr` crate reads an attacker-controlled `u32` element count and then grows a `Vec<C::G>` without any bound, mirroring the Quagga CVE-2017-5495 class (an input buffer that grows without limit based on untrusted input). Unlike other deserializers in the codebase that validate sizes against protocol parameters (`ThresholdKeys::read` caps by `n`, PedPoP `Commitments::read` caps by `params.t()`), `SchnorrAggregate::read` has no upper bound.

### Finding Description
`SchnorrAggregate::read` reads a 4-byte little-endian length and loops `u32::from_le_bytes(len)` times pushing decompressed points into a `Vec` [1](#0-0) . The declared count can be up to 4,294,967,295 with no sanity check against the remaining input, the number of signatures actually being verified, or any protocol constant. For each 32 bytes of attacker input, the code performs a full point decompression (`C::read_G`, which does canonicalization checks and curve operations [2](#0-1) ) and stores an in-memory `ProjectivePoint`/`ExtendedPoint` several times larger than its 32-byte wire encoding, plus `Vec` growth overhead. This gives both a memory amplification factor and a CPU amplification factor (decompression + `to_bytes` round-trip per element) over the attacker's bandwidth cost. `verify` then builds a pairs vector and runs `multiexp_vartime` over all `Rs` [3](#0-2) , compounding CPU cost. The writer side even acknowledges counts up to `u32::MAX` as a possibility ("more than 4 billion signatures in aggregate"), confirming no bound was ever intended [4](#0-3) .

### Impact Explanation
An unprivileged party who can cause `SchnorrAggregate::read` to be invoked on bytes they control (the format is length-prefixed and self-delimiting, so any consumer taking aggregate signatures over the wire is exposed) can force the process to allocate memory and burn decompression CPU proportional to — and amplified over — the bytes they send, or abort the process via allocation failure. This is exactly the pre-authentication, attacker-driven unbounded-allocation DoS of the source advisory: a daemon killed by the OOM killer or the host. The validate rules accept analogs reachable by "untrusted bytes fed to ... a verify ... API"; `SchnorrAggregate` is a public API of `crypto/schnorr` consumed with untrusted encodings.

### Likelihood Explanation
Whether a given deployment exposes `SchnorrAggregate::read` directly on unauthenticated input is an integration decision, but the function is the crate's canonical way to ingest an aggregate signature, and the analogous bounded readers elsewhere show the codebase's convention of enforcing size limits at the deserialization boundary — which is missing here. Exploitation requires only sending bytes; no key material, no threshold collusion, no valid signature.

### Recommendation
Bound the read. Either (a) take an expected/maximum signature count as a parameter (as `MultiDLEqProof::read` takes `discrete_logs` [5](#0-4)  and PedPoP `Commitments::read` takes `ThresholdParams` [6](#0-5) ), rejecting larger counts before reading, or (b) read incrementally in chunks and stop on stream exhaustion, as `networks/ethereum` `Call::read` explicitly does to cap the DoS of a false length claim [7](#0-6) .

### Proof of Concept
Conceptual: construct a buffer `u32::MAX.to_le_bytes() || valid_compressed_point * N` and pass it to `SchnorrAggregate::<C>::read(&mut buf.as_ref())`. With `N` ≈ 10^7 (~320 MB sent), the process holds ~10^7 decompressed points (~1+ GB on curve25519-dalek's `EdwardsPoint`/`RistrettoPoint`, more with heap bookkeeping) and performs 10^7 decompressions. Repeated across connections, the daemon is OOM-killed — the same pre-auth memory exhaustion as CVE-2017-5495's newline-less telnet buffer, with the only difference being the growth trigger (length prefix + point stream vs. newline delimiter).

Note: I was unable to fully trace every in-scope reader for a strictly stronger variant (e.g., a `vec![0; u32]` upfront allocation); `ThresholdKeys::read`'s `Vec::with_capacity(n)` is capped by `u16`, and the largest unbounded upfront allocation found (`Block::read`'s `Vec::with_capacity(txs)` over `u32`) is in `coordinator/tributary`, which is outside the permitted scope. `SchnorrAggregate::read` is the strongest in-scope match.
