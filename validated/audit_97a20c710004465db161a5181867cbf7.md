### Title
DNS Rebinding Protection Effectively Disabled by Default on the EVM JSON-RPC HTTP Server via Hardcoded `Vhosts: ["*"]` - (File: evmrpc/server.go)

### Summary
The EVM JSON-RPC HTTP server binds to `0.0.0.0` and constructs its `HTTPConfig` with `Vhosts: []string{"*"}` unconditionally, which disables the Host-header validation that the `virtualHostHandler` is explicitly designed to provide against DNS rebinding attacks.

### Finding Description
`evmrpc/rpcstack.go` implements a `virtualHostHandler` whose documented purpose is DNS-rebinding protection: it validates the incoming `Host` header against an allow-list and rejects requests whose Host doesn't match, "prevent[ing] DNS rebinding attacks, where a 'random' domain name points to the service ip address (but without CORS headers)" [1](#0-0) . This handler is inserted into the HTTP stack via `NewHTTPHandlerStack` for every RPC HTTP server [2](#0-1) .

However, when the actual EVM RPC HTTP server is constructed in `NewEVMHTTPServer`, `Vhosts` is hardcoded to `[]string{"*"}` rather than being derived from configuration or defaulting to `localhost`/loopback-only when the server binds to `0.0.0.0`/localhost: [3](#0-2) 

Because `virtualHostHandler.ServeHTTP` treats the presence of `"*"` in the vhost map as "allow any hostname," the wildcard entry makes the protection a no-op for every non-IP Host header [4](#0-3) . The server listens on `LocalAddress = "0.0.0.0"` [5](#0-4) [6](#0-5) , and there is no code path that ties the `Vhosts` value to the CLI/app.toml-configurable `CORSOrigins` or to the bind address, unlike `CorsAllowedOrigins`, which is derived from `config.CORSOrigins` [7](#0-6) .

This is the direct structural analog of GHSA-xw59-hvm2-8pj6: an HTTP JSON-RPC server exposes tool/method invocation to any origin reachable via the network stack, and the DNS-rebinding mitigation exists in code but is disabled by a permissive default (`"*"` vs. the advisory's "no default enablement"). A browser-based attacker can use DNS rebinding to have a victim's browser resolve an attacker-controlled domain to `127.0.0.1`/the node's local address, then issue same-origin (per the browser) POST requests to the EVM JSON-RPC endpoint bypassing CORS (since CORS only applies fetch/XHR responses reading, not blocking cross-origin simple POST requests) and Host validation is disabled by the wildcard.

### Impact Explanation
If the JSON-RPC node's default `CorsAllowedOrigins` is also permissive or the request is a "simple" cross-origin POST (CORS does not block simple requests from being sent, only from being read by JS in some cases; but JSON-RPC POST with `Content-Type: application/json` is not "simple" per CORS spec so browsers preflight it — still, DNS rebinding classically targets exactly this Host-check gap), an attacker's website can reach the node operator's local/private JSON-RPC endpoint (e.g. `eth_sendTransaction`-equivalent `sei_*`/`eth_*` methods, `debug_*`, `txpool_*`) and invoke methods with the privileges of whichever local wallet/session context the browser or co-located tooling trusts. This can enable unauthorized transaction submission or state/account information disclosure from a node operator's local RPC endpoint reachable via `0.0.0.0`.

### Likelihood Explanation
Exploitation requires the JSON-RPC HTTP port to be reachable from a network where DNS rebinding is feasible (commonly localhost/LAN-bound nodes without additional auth) and requires user interaction (visiting a malicious page), matching the advisory's own CVSS vector `AC:L/PR:N/UI:R`. Default `LocalAddress = "0.0.0.0"` binding [5](#0-4)  combined with the unconditional `Vhosts: []string{"*"}` [8](#0-7)  means the mitigation is disabled for every deployment regardless of operator config, making this a systemic default rather than a rare misconfiguration.

### Recommendation
Do not hardcode `Vhosts: []string{"*"}`. Make it configurable (mirroring `CorsAllowedOrigins`/`config.CORSOrigins`) and default it to a safe allow-list (e.g., `localhost`, `127.0.0.1`, and the node's own advertised hostname) rather than the wildcard, consistent with go-ethereum's own upstream default behavior that this vendored `rpcstack.go` was forked from.

### Proof of Concept
1. Start a `sei-chain` node with the EVM JSON-RPC HTTP server enabled (default config binds to `0.0.0.0:<HTTPPort>`).
2. From a browser, host a page at `attacker.example` and use DNS rebinding to repoint `attacker.example` to the node's IP after initial page load.
3. Issue an XHR/fetch POST with `Host: attacker.example` and `Content-Type: application/json` containing a JSON-RPC payload (e.g., `{"jsonrpc":"2.0","method":"eth_accounts","params":[],"id":1}`) to the rebound IP.
4. Because `virtualHostHandler` allows any Host due to the `"*"` entry [9](#0-8) , the request reaches the RPC dispatcher instead of being rejected with `403 invalid host specified`, demonstrating the DNS-rebinding mitigation is inert by default.

// virtualHostHandler is a handler which validates the Host-header of incoming requests.
// Using virtual hosts can help prevent DNS rebinding attacks, where a 'random' domain name points to
// the service ip address (but without CORS headers). By verifying the targeted virtual host, we can
// ensure that it's a destination that the node operator has defined.
type virtualHostHandler struct {
	vhosts map[string]struct{}
	next   http.Handler
}

func newVHostHandler(vhosts []string, next http.Handler) http.Handler {
	vhostMap := make(map[string]struct{})
	for _, allowedHost := range vhosts {
		vhostMap[strings.ToLower(allowedHost)] = struct{}{}
	}
	return &virtualHostHandler{vhostMap, next}
}
