### Title
Untyped, undomained signature scheme in `pallet-hyper-fungible-token`'s calldata execution allows cross-chain signature replay to dispatch arbitrary runtime calls as the victim - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` optionally executes an arbitrary `runtime_call` on behalf of a `beneficiary` account, authorized by a raw `MultiSignature` over `(nonce, runtime_call)`. This payload contains no chain id, genesis hash, pallet identifier, or any domain separator — exactly the "untyped data signing" bug class from the seed report. Because the signed message is generic and reusable, a signature the beneficiary produced in one context (another chain running the same pallet/runtime, or any other protocol that happens to sign the same encoded tuple) can be replayed by an unprivileged attacker who fully controls the incoming cross-chain `Message.data` field to dispatch an arbitrary call as that beneficiary's `Signed` origin.

### Finding Description
In `on_accept`: [1](#0-0) 

The verification flow is:
1. `beneficiary` is derived purely from attacker-controlled `message.to` (any account, EVM or substrate) — the message body comes from the source-chain gateway contract, which any user can call with arbitrary `to`/`data` fields per the ABI-compatible `Message { from, to, amount, data }` layout. [2](#0-1) 
2. `SubstrateCalldata { signature, runtime_call }` is fully attacker-supplied inside `message.data`. [3](#0-2) 
3. The pallet fetches the beneficiary's current `frame_system` nonce and hashes `(nonce, runtime_call).encode()` with keccak256 (Ed25519/Sr25519), or with an Ethereum-prefixed keccak256 for ECDSA, and recovers/verifies against the beneficiary's public key. [4](#0-3) 
4. If verification succeeds, the pallet dispatches `runtime_call` with `RawOrigin::Signed(beneficiary)`, then increments the beneficiary's nonce. [5](#0-4) 

The signed payload `(nonce, runtime_call)` contains none of:
- a chain id / genesis hash (confirmed absent anywhere in the pallet),
- the pallet's own module id / "purpose" tag distinguishing this from any other signature scheme,
- the source chain or the destination gateway contract address,
- a domain separator of any kind.

This directly mirrors the Rigor `Community.sol`/`Project.sol` bug: signatures are bound only to `(nonce, payload)`, so identical byte-for-byte signable data can arise in unrelated contexts (a different chain running the same pallet version, a differently-configured deployment with the same call index layout, or any other application that happens to sign `(u32/u64 nonce, SCALE bytes)` under the same key type) and be replayed here. Unlike a normal signed extrinsic (which is bound via `SignedExtension`s to `CheckGenesis`/`CheckSpecVersion`/`CheckMortality` etc.), this bespoke scheme has none of Substrate's usual anti-replay domain binding.

### Impact Explanation
An attacker who obtains any valid `MultiSignature` from a victim over the exact bytes `(current_nonce, runtime_call).encode()` — e.g., because the same runtime/pallet is deployed on more than one chain (testnet/mainnet, or two parachains sharing a runtime image) and the victim's nonce coincides, or because the victim signed conceptually similar raw data elsewhere — can submit that signature through the bridge (as attacker-controlled `message.data`) to force the victim's account to execute an arbitrary `runtime_call` chosen by the attacker (subject only to `BaseCallFilter`), under `RawOrigin::Signed(beneficiary)`. This is unauthorized execution/transaction manipulation on a victim account: possible outcomes include transferring the victim's balance, approving/spending assets, or invoking any other filtered-in dispatchable, i.e. direct fund loss with a wrong effective beneficiary of the action. This falls squarely under "unauthorized transaction or execution" / "logic attacks" in the bounty's impact gate.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — it only requires an unprivileged user to call the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract's transfer function with a crafted `data` payload embedding a previously-obtained victim signature and any `runtime_call`, and it requires that a signature of the exact `(nonce, runtime_call)` shape by the victim exist (e.g. from another chain deployment of the same pallet, which the project itself documents as multi-chain: "communicates with peer instances across networks via Hyperbridge"). Likelihood depends on the specific reuse vector (multi-deployment nonce collision or generic-payload phishing), so it is assessed as medium — the guard is entirely missing rather than merely weak, so any concrete reuse opportunity is exploitable with no additional privilege.

### Recommendation
Follow the seed report's own recommendation: stop signing untyped tuples. Bind every signed payload to a domain that makes it non-fungible across contexts:
- Include the local chain's genesis hash / `frame_system::block_hash(0)` (or a fixed genesis constant) in the signed payload.
- Include the pallet's own module id / a fixed purpose string (e.g. `b"pallet-hyper-fungible-token::exec"`).
- Include the source `StateMachine` the message arrived from, and/or the destination contract address that dispatched it, so a signature produced for chain A cannot be replayed via chain B.
- Prefer a proper typed-data scheme (SCALE `TypeInfo`-based or EIP-712-analog for the ECDSA branch) instead of a raw `(nonce, call)` tuple, consistent with how `IntentGatewayV2` already correctly uses EIP-712 with `DOMAIN_SEPARATOR`/`SELECT_SOLVER_TYPEHASH` elsewhere in the codebase. [6](#0-5) 

### Proof of Concept
1. Deploy/observe that `pallet-hyper-fungible-token` with the same `Config`/call-index layout is registered on two chains (e.g., a testnet and mainnet instance, or two parachains sharing a runtime), both bridging to the same `HyperFungibleToken` EVM contract family.
2. Victim `Alice` (AccountId `A`) has nonce `N` on Chain A (fresh account) and signs — for any legitimate reason on Chain A, e.g. a documented HFT calldata-execution transfer — the payload `(N, call_bytes).encode()` with her key, producing `sig`.
3. Alice's account also exists (same key derivation) with nonce `N` on Chain B, which also runs the pallet and accepts the same peer contract.
4. Attacker, an unprivileged user, calls the source EVM `HyperFungibleToken` contract on the chain paired with Chain B, setting `Message.to = Alice_on_ChainB`, `Message.data = SubstrateCalldata { signature: Some(sig), runtime_call: call_bytes }`.
5. Hyperbridge delivers the `PostRequest` to Chain B's `on_accept`; the pallet computes `nonce = account_nonce(Alice) == N`, recomputes `keccak256((N, call_bytes).encode())`, and successfully verifies `sig` against Alice's key (since chain identity/genesis was never part of what was signed).
6. `call_bytes` (chosen by the attacker to match whatever the victim originally authorized in shape, or coincidentally reused if the same call index/nonce collide) dispatches as `RawOrigin::Signed(Alice)` on Chain B — unauthorized execution the victim never intended for that chain.

Note: the exact reuse trigger (multi-chain deployment nonce collision, or a victim separately signing the same tuple shape for an unrelated purpose) could not be fully confirmed from static analysis alone since it depends on deployment topology outside this repository; however, the root cause — the complete absence of any domain separator in the signed payload — is unambiguously present and directly analogous to the seed report's finding.
