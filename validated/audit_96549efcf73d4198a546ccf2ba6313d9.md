### Title
Unanchored `"diff --git "` string-splitting in `parse_diff_into_files` lets attacker-controlled diff content forge fake file boundaries, hiding malicious hunks from security review - (File: `plugins/security-guidance/hooks/gitutil.py`)

### Summary
`parse_diff_into_files` (and its sibling `extract_file_paths_from_diff`) splits unified diff text on the literal substring `"diff --git "` without anchoring to line boundaries, and then applies a naive single-line regex to recover the file path. An attacker who controls the content of a reviewed file (e.g. adds a line/comment/string literal containing `diff --git a/x b/y`) can forge a fake per-file boundary inside a real hunk, causing the reviewer to misattribute or silently drop the subsequent (actually malicious) diff content instead of sending it to the LLM security review.

### Finding Description
`parse_diff_into_files` builds its list of `(file_path, diff_content)` review units via: [1](#0-0) 

Both this function and `extract_file_paths_from_diff` use `diff_output.split("diff --git ")`: [2](#0-1) 

`str.split()` matches the substring anywhere in the text, not only at the start of a line. In a real `git diff` output, added/removed hunk lines are plain text (no escaping guarantee for the literal ASCII sequence `diff --git `), and `GIT_CMD` explicitly disables path quoting via `-c core.quotePath=false`: [3](#0-2) 

If an attacker-controlled source file (whose diff is what gets reviewed) contains a line — e.g. inside a string literal, comment, or generated code — that happens to include the exact text `diff --git a/<decoy> b/<decoy>`, the whole-diff `.split("diff --git ")` call fragments the true file's hunk at that point. The code after the split point is treated by the parser as belonging to a brand-new "file" whose path is taken from `header_match` on the immediately following line: [4](#0-3) 

Two exploitable outcomes:
1. If the injected text (plus following characters) happens to satisfy the `^a/(.+?) b/(.+)$` header regex, the remaining real hunk content — which can include genuinely malicious added code that comes after the injection point in the same file — is silently reassigned to a bogus decoy `file_path`. If that decoy path doesn't pass `_is_reviewable_source` (e.g. an extensionless or dotfile-looking decoy name), the whole tail segment is dropped from `files` and never reaches the LLM review.
2. If the "header" doesn't match, the fragment is discarded outright at the `if not header_match: continue` check, again dropping the trailing (attacker's real, malicious) hunk lines from the returned `files` list.

Either way, the required guard — the LLM-based `analyze_code_security` / `agentic_review` scan performed over `parse_diff_into_files`'s output — never sees the injected/attacker-crafted malicious lines, because the parser's file-boundary detection can be spoofed purely by diff *content*, not by an actual second file in the commit.

### Impact Explanation
This breaks the intended invariant that the diff-splitting step faithfully preserves the mapping between a changed file and its full hunk content for review. By crafting ordinary repo content (a comment, string, or generated text containing the literal `diff --git a/x b/y` pattern), an attacker can cause the security-guidance Stop-hook/commit-review pipeline to silently omit part of the actual diff from the vulnerability scan — a logic-level bypass of the review guard that the plugin exists to enforce. This matches "Logic-level service disruption caused by bypassing a required guard" since the security review that Claude Code's Stop hook depends on can be selectively blinded to attacker-controlled content.

### Likelihood Explanation
No special privilege is required: any content that ends up in a diff Claude reviews (a file edited/added during the session, or committed content in the commit-review / push-sweep paths) can contain this text. The trigger string (`diff --git a/x b/y`) is short, ASCII, and not filtered by any existing check; `_is_reviewable_source`/pathspec/realpath-based repo scoping (`_diff_pathspec`) operate on real git-classified paths and don't protect against content-level parser confusion. This is reliably reproducible with a static crafted diff and does not depend on race conditions or timing.

### Recommendation
Make the file-boundary split line-anchored and reuse git's own reliable metadata instead of ad-hoc text splitting: split on `re.compile(r'^diff --git ', re.MULTILINE)` (or use `git diff --name-status`/`--numstat` plus targeted `git diff -- <path>` calls per file) so that a `diff --git ` sequence embedded inside a hunk's `+`/`-`/context line body can never be mistaken for a real per-file header line.

### Proof of Concept
Unit test for `parse_diff_into_files` in `plugins/security-guidance/hooks/gitutil.py`:
1. Construct a synthetic diff string representing one real file `real.py` whose added hunk contains a line whose text is exactly `diff --git a/decoy b/decoy` (e.g. `+    # marker: diff --git a/decoy b/decoy`) followed by more genuinely "malicious" added lines (e.g. `+eval(user_input)`).
2. Call `parse_diff_into_files(diff_text)`.
3. Assert (expected, currently failing): the returned list contains exactly one entry for `real.py` whose `diff_content` includes the `eval(user_input)` line.
4. Actual observed behavior: the parser splits into two "files" — `real.py` (truncated before the marker) and a `decoy` entry (or dropped entirely because `decoy` has no extension and fails `_is_reviewable_source`) — demonstrating that `eval(user_input)` never appears in any returned tuple, i.e., it is dropped from review scope.
