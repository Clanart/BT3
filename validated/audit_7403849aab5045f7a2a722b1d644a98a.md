### Title
GetRequest timeouts settle without any destination-state proof, letting a "no-response" finalization race ahead of an already-computed response - ([File: modules/ismp/core/src/handlers/timeout.rs])

### Summary
`ismp::handlers::timeout::handle` verifies `PostRequest` timeouts by validating the destination's consensus state, waiting for its challenge period, and requiring a non-membership proof that the request was never processed on the destination. [1](#0-0)  For `GetRequest` timeouts the handler skips all of that: it only checks the *source* chain's own clock (`get.timed_out(host.timestamp())`) and a purely local `response_receipt` flag before dispatching `on_timeout` and deleting the request commitment. [2](#0-1)  This mirrors the Y2K bug: one finalization path (`triggerDepeg`/valid `GetResponse`) requires external proof plus a challenge/liveness window, while the other (`triggerEndEpoch`/`TimeoutMessage::Get`) is unconditionally callable the instant a local timestamp elapses, regardless of whether the "true" outcome already exists but hasn't been proven yet.

### Finding Description
The docs explicitly describe this asymmetry as by-design: "there are no proofs for Get timeouts, we only need to ensure that the timeout timestamp has elapsed on the host." [3](#0-2)  Compare the two branches in `timeout::handle`:

- `Post`: calls `validate_state_machine` (enforces consensus-client-not-frozen + challenge period elapsed), fetches the destination `StateCommitment`, and calls `state_machine.verify_non_membership(...)` against a real destination state root before allowing the timeout to fire. [1](#0-0) 
- `Get`: only checks `host.response_receipt(&response).is_some()` (a purely local flag set when a proven `GetResponse` has already landed on **this** chain) and `get.timed_out(host.timestamp())` — no consensus-client check, no challenge period, no state proof at all. [4](#0-3) 

Meanwhile, delivering the legitimate `GetResponse` back to the source chain is the "slow path": the relayer must wait for the destination height to be finalized *and* for the configured challenge period to elapse before the response can even be submitted, as implemented by `wait_for_challenge_period`/`waitForChallengePeriod` in the relayer/SDK tooling. [5](#0-4) [6](#0-5) 

This produces exactly the M-11 pattern: the destination has already computed the true answer (the GET was in fact serviced, or the underlying condition — e.g. escrow status, price, order fill — has already changed), but because the response-with-proof pipeline is gated behind a challenge/finality delay, an unprivileged caller can race ahead and submit `TimeoutMessage::Get` the moment `timeout_timestamp` elapses. The handler deletes the request commitment (`host.delete_request_commitment`) and invokes `IsmpModule::on_timeout`, permanently foreclosing the "response" branch — the later legitimate `GetResponse` will be rejected as `UnknownRequest` once its commitment is gone, since the response handler checks `host.request_commitment(commitment)`/`host.requestCommitments(...)` before dispatch (see the `PostRequest`/`GetResponse` handlers requiring `meta.sender != address(0)`). [7](#0-6) 

### Impact Explanation
Any `IsmpModule` that uses `GetRequest`/`on_timeout` to gate a fund-moving or state-committing decision (e.g., "if the counterparty didn't answer in time, release escrow / cancel order / assume unfilled and refund") is forced into the wrong branch even though the true, already-computed destination state says otherwise. Because the timeout path requires zero proof and no challenge period while the honest response path requires both, an attacker (or simply an unlucky relayer delay) can force premature, incorrect finalization — unauthorized execution / wrong-beneficiary settlement exactly matching the bounty's "false state acceptance" and "logic attack" categories. This is not a hypothetical relayer-honesty assumption break; it is a structural gap in the on-chain guard itself, reachable by any permissionless caller of the timeout handler once the local clock condition is met.

### Likelihood Explanation
`handleGetRequestTimeouts`/`TimeoutMessage::Get` processing is explicitly permissionless ("Access: Permissionless (can be called by anyone)"). [8](#0-7)  No relayer, prover, or admin compromise is required — only that the destination's real response takes longer to arrive/prove than the source's raw timeout window, which is the normal operating mode given mandatory challenge-period waits on the response path. This makes the race condition triggerable under ordinary network conditions, not just adversarial ones.

### Recommendation
Require GET-request timeouts to also prove non-membership of a response commitment at a challenge-period-elapsed destination state height (symmetric with the `Post` path), or alternatively require the destination's finalized/challenge-period-cleared timestamp (not just the source's local clock) to have passed `timeout_timestamp` before a `TimeoutMessage::Get` can be processed. This closes the gap where an unproven "no answer" outcome can be finalized strictly faster than the proven "answer exists" outcome.

### Proof of Concept
1. Application `A` dispatches a `GetRequest` to state machine `D` with `timeout_timestamp = T`.
2. `D` processes the query before `T` and the answer becomes committed to `D`'s state (e.g., condition resolves in favor of the honest outcome). A relayer begins constructing the `GetResponse` proof but must additionally wait for `D`'s state to reach `T_finalize` and then for `challenge_period` to elapse before it can even be submitted, per `wait_for_challenge_period`. [5](#0-4) 
3. As soon as the source chain's local `host.timestamp()` exceeds `T`, any address calls the timeout handler. On Substrate this hits `TimeoutMessage::Get` in `timeout::handle`, which only checks `host.response_receipt(&response).is_some()` (false, since the response hasn't been delivered yet) and `get.timed_out(host.timestamp())` (true) — no proof of `D`'s actual state is required. [4](#0-3) 
4. The handler deletes the request commitment and invokes `on_timeout` on the source module, committing the "unanswered" outcome.
5. When the honestly-computed `GetResponse` proof later arrives (after the mandatory challenge period), it is rejected because the request commitment no longer exists (`UnknownRequest`/`meta.sender == address(0)` checks), so the true outcome can never be applied — the module is left in the state dictated by the premature timeout, identical in effect to Y2K's `triggerEndEpoch` firing before a legitimate depeg could ever be proven.

pub async fn wait_for_challenge_period(
	client: Arc<dyn IsmpProvider>,
	last_consensus_update: Duration,
	counterparty_state_id: StateMachineId,
) -> anyhow::Result<()> {
	let challenge_period = client.query_challenge_period(counterparty_state_id).await?;
	if challenge_period != Duration::ZERO {
		log::info!(
			target: LOG_TARGET, "Waiting for challenge period {challenge_period:?} for {} on {}",
			counterparty_state_id.state_id,
			client.name()
		);
	}

	tokio::time::sleep(challenge_period).await;
	let current_timestamp = client.query_timestamp().await?;
	let mut delay = current_timestamp.saturating_sub(last_consensus_update);

	while delay <= challenge_period {
		tokio::time::sleep(challenge_period - delay).await;
		let current_timestamp = client.query_timestamp().await?;
		delay = current_timestamp.saturating_sub(last_consensus_update);
	}
	Ok(())
}

export async function waitForChallengePeriod(chain: IChain, stateMachineHeight: StateMachineHeight): Promise<void> {
	// Get the challenge period for this state machine
	const challengePeriod = await chain.challengePeriod(stateMachineHeight.id)

	if (challengePeriod === BigInt(0)) return

	// Get the state machine update time
	const updateTime = await retryPromise(() => chain.stateMachineUpdateTime(stateMachineHeight), {
		maxRetries: 3,
		backoffMs: 500,
		logMessage: "Fetching consensus update time while waiting for the challenge period",
		shouldRetry: (error) => !MissingConsensusUpdateTimeError.isError(error),
	})
	// Check current timestamp
	let currentTimestamp = await chain.timestamp()
	// Calculate time passed since update
	let timeElapsed = currentTimestamp - updateTime

	if (timeElapsed > challengePeriod) return

	// First sleep for the whole challenge period
	await sleep(Number(challengePeriod) * 1000)

	// Keep sleeping until challenge period has fully elapsed
	while (timeElapsed <= challengePeriod) {
		// Sleep for remaining time
		const remainingTime = challengePeriod - timeElapsed
		await sleep(Number(remainingTime) * 1000)

		// Check timestamp again
		currentTimestamp = await chain.timestamp()
		timeElapsed = currentTimestamp - updateTime
	}
}
