### Title
Attacker-controlled DKG messages cause panic (assert / HashMap index) crashing the node — ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The PedPoP encryption layer uses `assert!` and unchecked `HashMap` indexing on state driven by messages read from untrusted bytes (`EncryptionKeyMessage::read`, `EncryptedMessage::read`, `EncryptionKeyProof::read`). A participant-controlled message stream can force a panic — the Rust analog of the null-pointer-deref DoS in CVE-2023-24832 — aborting the DKG/key-management process.

### Finding Description
Two reachable panic sites exist in `crypto/dkg/pedpop/src/encryption.rs`:

1. `Decryption::register` hard-asserts that a participant registers at most one encryption key: [1](#0-0) 
   `register` is invoked via `Encryption::register` on a message whose contents come from `EncryptionKeyMessage::read`, i.e., raw bytes supplied by another party: [2](#0-1) [3](#0-2) 
   A second `EncryptionKeyMessage` attributed to the same `Participant` (e.g., replayed across DKG attempts/retries) triggers the `assert!` and panics rather than returning `io::Error`.

2. `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` unconditionally: [4](#0-3) 
   `decryptor` derives from the blame/accusation message being processed. If a blame path is reached for a participant whose `EncryptionKeyMessage` was never registered (absent or deduplicated upstream), the `HashMap` index panics. Likewise `Encryption::encrypt` indexes `self.decryption.enc_keys[&participant]`: [5](#0-4) 

Note the parallel case the code itself acknowledges: `Commitments` docs state the caller must detect duplicate messages because "this library does not handle networking" (`crypto/dkg/pedpop/src/lib.rs:98-101`). `Encryption::register` makes no such contract explicit — it just panics.

### Impact Explanation
An unprivileged counterparty who can get DKG messages delivered (the same reachability class as `read_preprocess`/`read_share` inputs) can abort the victim's process mid-DKG. In Serai's deployment this halts validator key generation / resharing, a liveness failure of the signing set. This is a remote, input-triggered crash — the exact impact class of the reported CVE (null-deref → runtime crash), mapped onto Rust panics.

### Likelihood Explanation
Triggering only requires delivering a duplicated `EncryptionKeyMessage`, or a blame proof referencing an unregistered decryptor — both are byte streams parsed by `*_::read` and handed to `Encryption`/`Decryption`. No secret knowledge, valid proofs, or cryptographic breaks are needed; the panic occurs before or independent of signature verification (the `assert!` precedes any crypto, and the `enc_keys[&decryptor]` lookup precedes key use).

### Recommendation
- Replace `assert!(!self.enc_keys.contains_key(&participant))` in `Decryption::register` with a returned `io::Error`/typed error, and document or enforce single-registration.
- Replace `self.enc_keys[&decryptor]` and `self.decryption.enc_keys[&participant]` with `.get()` + error propagation.
- Audit other `unwrap()`/index operations on values derived from `Read` inputs (e.g., `preprocesses.remove(l).unwrap()` in `crypto/frost/src/sign.rs:348` and `verification_shares[i]`/`included[0]` paths in `crypto/dkg/src/lib.rs:376-378,518-521`) to confirm invariants are enforced before indexing.

### Proof of Concept
```rust
// After a victim calls Encryption::register(participant, msg1),
// deliver a second EncryptionKeyMessage for the same participant:
let mut buf = msg2.serialize(); // attacker-crafted bytes
let msg2 = EncryptionKeyMessage::<C, M>::read(&mut &buf[..], params).unwrap();
encryption.register(participant, msg2); // panic: "Re-registering encryption key for a participant"

// Similarly, a blame path calling Decryption::decrypt_with_proof with a
// `decryptor` Participant never registered panics on `self.enc_keys[&decryptor]`.
```

**Caveat:** I could not fully trace the caller paths feeding `Decryption::register`/`decrypt_with_proof` from network input within the available iterations. The panic sites themselves are confirmed in-scope code reachable only via attacker-influenced `*_::read` messages; if the surrounding protocol hard-deduplicates registrations before calling `register`, the second site (`enc_keys` indexing on blame) remains reachable whenever a decryptor index not present in `enc_keys` is supplied.

    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
