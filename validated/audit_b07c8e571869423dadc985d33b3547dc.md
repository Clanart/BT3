### Title
PedPoP returns ECDH blame proofs before validating the message proof-of-possession - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` can be forced to return an `EncryptionKeyProof` for an attacker-selected message key before the message’s Schnorr proof-of-possession has been verified. A malicious DKG participant can copy the ephemeral key from a victim’s encrypted share, submit an invalid-PoP message using that key, and receive a blame proof containing the recipient’s ECDH result for the victim key. That result is sufficient to decrypt the victim’s original share.

### Finding Description
`EncryptedMessage` explicitly relies on `pop` to prevent an attacker from reusing another message’s ephemeral key and inducing the recipient to reveal the corresponding ECDH key during blame handling. [1](#0-0)  However, `Encryption::decrypt` only queues `msg.pop` into the supplied batch verifier, then immediately computes `ecdh(self.enc_key, msg.key)`, decrypts the ciphertext, and constructs an `EncryptionKeyProof` containing that ECDH point and a DLEq proof. [2](#0-1) 

In `calculate_share`, the decrypted bytes are parsed as a scalar before the queued batch is verified. If parsing fails, the function immediately returns `PedPoPError::InvalidShare` with `Some(blame)`, bypassing the later batch verification that would reject the invalid PoP and map `BatchId::Decryption` to `blame: None`. [3](#0-2) 

The PoP challenge binds the nonce, message key, authenticated sender index, and ciphertext bytes. [4](#0-3)  An attacker who controls a different participant index therefore cannot validly reuse the victim’s `msg.key`, but can make the PoP deliberately invalid while keeping the copied key.

### Impact Explanation
The returned `EncryptionKeyProof` exposes `bX`, where `b` is the recipient’s private DKG encryption key and `X` is the victim message’s ephemeral public key. The proof is generated specifically as `DLEq(G, X; bG, bX)` and serialized with the shared point as its first field. [5](#0-4) [6](#0-5) 

Anyone receiving or publishing this blame output can reconstruct the ChaCha20 keystream from `bX` and decrypt the victim’s original `EncryptedMessage`. [7](#0-6)  This leaks a PedPoP secret share and, with enough compromised shares, can enable recovery of the threshold secret.

### Likelihood Explanation
A malicious DKG participant can send an `EncryptedMessage` under their own authenticated participant index while setting `key` to a previously observed victim ephemeral key and using an invalid Schnorr PoP. They choose arbitrary ciphertext bytes; after decryption, those bytes fail canonical scalar decoding with high probability because a random 32-byte value is usually not a canonical scalar. If the result happens to decode successfully, the attack can be repeated with different ciphertext bytes.

No discrete logarithm, collusion, leaked key, or invalid curve input is required. The attack depends only on sending malformed bytes to `calculate_share` and obtaining the returned blame proof.

### Recommendation
Do not construct or return an `EncryptionKeyProof` until the message PoP has been verified.

Concretely:

- Verify `msg.pop` synchronously before deriving `ecdh`, or delay scalar parsing and all proof-returning error paths until after `batch.verify_with_vartime_blame()` accepts the queued `BatchId::Decryption` statement.
- Separate plaintext decryption from blame-proof generation so `Encryption::decrypt` cannot emit `EncryptionKeyProof` for a message whose PoP has only been queued.
- Preserve `blame: None` for every decryption-authentication failure.
- Add a regression test that copies a legitimate `msg.key`, corrupts `pop.s`, chooses bytes that decrypt to a non-canonical scalar, and asserts that `calculate_share` returns `InvalidShare { blame: None }`.

### Proof of Concept
Conceptual reproduction:

```rust
// Alice -> Bob legitimate message:
let alice_to_bob: EncryptedMessage<C, SecretShare<C::F>> = /* observed */;

// Eve is another DKG participant and submits under Participant::EVE.
let mut forged = EncryptedMessage {
  key: alice_to_bob.key,          // Reuse Alice's ephemeral public key X.
  pop: invalid_schnorr_pop,       // Valid encoding; invalid for sender EVE.
  msg: Zeroizing::new(SecretShare([0xff; 32])),
};

let err = bob_key_machine
  .calculate_share(rng, shares_including_eves_forged_message)
  .unwrap_err();

// With high probability, the forged plaintext is non-canonical, so this error
// is returned before the queued PoP failure is checked.
let PedPoPError::InvalidShare {
  participant,
  blame: Some(proof),
} = err else { panic!() };

// proof.serialize() exposes bX. Applying the DKG encryption transcript and
// ChaCha20 keystream derived from bX decrypts Alice's original message.
```

The decisive ordering flaw is that `decrypt` returns the proof immediately after queuing PoP verification, [2](#0-1)  while `calculate_share` returns that proof on non-canonical plaintext before checking the batch. [8](#0-7)

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res

  key: C::G,
  sender: Participant,
  msg: &[u8],

  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt

  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
