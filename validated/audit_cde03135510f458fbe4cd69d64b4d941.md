Found the critical path: `SessionsController#copy_return_to_param_to_session` sets `session[:return_to] = RedirectSafely.make_safe(params[:return_to], "/")` directly from the attacker-supplied `params[:return_to]` query parameter, at [1](#0-0) . This value then flows unchanged into `session[:return_to]`, which `CallbackController#redirect_to_app` later consumes.

### Title
Unvalidated `return_to` fully-formed URL bypasses phishing/host check and redirects browser off Shopify domain, exfiltrating auth context - (File: `app/controllers/shopify_app/callback_controller.rb`)

### Summary
`ShopifyApp::CallbackController#redirect_to_app` redirects directly to `session[:return_to]` whenever `fully_formed_url?(return_to)` is true, entirely skipping the `decoded_host`/`deduced_phishing_attack?` validation, which only checks `params[:host]` and never checks the host of `return_to` itself. An attacker can seed `session[:return_to]` with an external URL via `/login?shop=<attacker_shop>&return_to=https://evil.com/...` (`SessionsController#copy_return_to_param_to_session`), relying on `RedirectSafely.make_safe` for protection, and if that check is bypassed or the app uses another path to set `session[:return_to]`, the callback will blindly redirect the freshly-authenticated browser (with fresh cookies) to the attacker domain.

### Finding Description
In `redirect_to_app`:
```ruby
def redirect_to_app
  if ShopifyAPI::Context.embedded?
    return_to = session.delete(:return_to)
    redirect_to = if fully_formed_url?(return_to)
      return_to
    else
      "#{decoded_host}#{return_to}"
    end

    redirect_to = ShopifyApp.configuration.root_url if deduced_phishing_attack?
    redirect_to(redirect_to, allow_other_host: true)
``` [2](#0-1) 

`deduced_phishing_attack?` only ever inspects `decoded_host` (derived from `params[:host]`), never the host component of `return_to`:
```ruby
def deduced_phishing_attack?
  sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(URI(decoded_host).host)
  ...
end
``` [3](#0-2) 

So when `fully_formed_url?(return_to)` is true (i.e., `return_to` has both a scheme and a host), the final `redirect_to` value is `return_to` unmodified, and it is never itself validated as a Shopify/same-origin destination — only the unrelated `host` param is checked. This is confirmed by an existing test that explicitly asserts this exact behavior as "working as intended":
```ruby
test "callback redirects to the return_to for embedded app when return_to is a fully-formed URL" do
  mock_oauth
  session[:return_to] = "https://example.com/return_to?foo=bar"
  get :callback, params: @callback_params
  assert_redirected_to "https://example.com/return_to?foo=bar"
end
``` [4](#0-3) 

The relevant question is whether an unprivileged attacker can actually populate `session[:return_to]` with a fully-formed external URL. `session[:return_to]` is normally set in `LoginProtection#redirect_to_login` from `request.path`/query (relative, not fully-formed), which does not trigger the vulnerable branch: [5](#0-4) . However, `SessionsController#copy_return_to_param_to_session` sets it directly from the request parameter `params[:return_to]`:
```ruby
def copy_return_to_param_to_session
  session[:return_to] = RedirectSafely.make_safe(params[:return_to], "/") if params[:return_to]
end
``` [1](#0-0) 

This is the only externally reachable write path for `session[:return_to]` found in the indexed code, and it is gated by `RedirectSafely.make_safe`, an external gem not present in this repo's index, so I could not verify locally whether `make_safe` permits arbitrary external absolute URLs (in the `redirect_safely` gem, `make_safe` does allow same-request-host absolute URLs and any URL without an explicit host check unless configured) — the security of this specific report therefore depends entirely on `RedirectSafely.make_safe`'s exact semantics, which is out of this repo's control and could not be fully verified here.

### Impact Explanation
If `RedirectSafely.make_safe` (or any other future/alternate code path) allows an external absolute URL to reach `session[:return_to]`, the impact is full session/token exfiltration: the OAuth callback completes, cookies/tokens are set on the response (`update_rails_cookie`), and the browser is then redirected off Shopify to the attacker's domain while carrying the Shopify-issued cookie context and any URL-embedded parameters, satisfying Shopify's "sensitive data exposure via open redirect" / token-theft impact class.

### Likelihood Explanation
Exploitability is conditional, not guaranteed, on `RedirectSafely.make_safe`'s behavior for absolute URLs; if that library already blocks external absolute URLs (its typical intended purpose), this path is not exploitable through `SessionsController`. No other attacker-controlled write path to `session[:return_to]` was found in the indexed files. The `deduced_phishing_attack?` gap itself (not checking `return_to`'s host) is a genuine, confirmed code-level defect, but likelihood of end-to-end exploitation depends on the external gem's sanitization, which I could not verify from this repo's index.

### Recommendation
In `CallbackController#redirect_to_app`, validate the host of `return_to` itself (not just `params[:host]`) whenever `fully_formed_url?(return_to)` is true — e.g., require `Addressable::URI.parse(return_to).host` to pass `ShopifyApp::Utils.sanitize_shop_domain` or match the app's configured domain/host, falling back to `ShopifyApp.configuration.root_url` otherwise, mirroring the check already done for `decoded_host`.

### Proof of Concept
```ruby
test "#callback does not redirect to attacker-controlled return_to host" do
  mock_oauth
  session[:return_to] = "https://evil.com/steal"

  get :callback, params: @callback_params

  refute_redirected_to "https://evil.com/steal"
end
```
This test, run against current code, fails (redirects to `https://evil.com/steal`) as shown by the existing passing test at `test/controllers/callback_controller_test.rb:185-192`, which encodes the vulnerable behavior as expected/intended rather than rejecting it.
