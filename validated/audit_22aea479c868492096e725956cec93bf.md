Based on my research, the strongest local analog to the sudoswap report is in the Tron port of the Intent Gateway, where the withdraw path performs escrow accounting on the *assumption* that a low-level token call succeeded, without validating the actual ERC-20 return value — mirroring the original bug's core flaw of moving/accounting for funds without properly validating the actual outcome of the transfer.

### Title
Unchecked ERC20 return-value handling in `IntentGatewayV2.withdraw()` desyncs escrow accounting from actual fund delivery, causing loss of escrowed tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron port of the Intent Gateway's `withdraw()` function releases escrowed order tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level call itself did not revert (`success`), never inspecting the ERC-20 boolean return value. It then unconditionally decrements the escrow accounting (`_orders[body.commitment][token] -= amount`) as if the transfer definitely succeeded. This is the same defect class as the sudoswap report: an asset-moving effect (transfer) and the state that is supposed to track/validate it are decoupled, and the validation that should gate accounting from believing a transfer succeeded is missing.

### Finding Description
Compare the canonical EVM implementation with the Tron port:

The mainline EVM `_withdraw()` in `IntentsBase.sol` uses `SafeERC20.safeTransfer`, which reverts on a `false` return, and decrements escrow *before* the external call (checks-effects-interactions): [1](#0-0) 

The Tron port's `withdraw()` instead:
1. Only checks escrow existence with `== 0`, not `amount <= escrowed`.
2. Sends tokens with a bare `.call(...)` and checks only that the *call* didn't revert, never the ERC-20 return data.
3. Decrements `_orders[body.commitment][token] -= amount` *after* the transfer, based purely on the assumption the transfer worked. [2](#0-1) 

Because `success` is only `true`/`false` based on whether the target contract *reverted*, any ERC-20 token that returns `false` on failure instead of reverting (a documented category of non-compliant tokens, and trivially implementable by an attacker who places an order using their own token as the escrowed input) will cause:
- The `if (!success) revert TransferFailed();` check to pass (call succeeded, no tokens delivered or fewer than expected).
- The escrow ledger `_orders[body.commitment][token]` to still be decremented by the full `amount`, permanently marking the funds as "withdrawn" even though the beneficiary received nothing.

This exactly parallels the original bug's "recommendation": validate the actual outcome/right recipient/right amount, don't just assume it based on the surrounding control flow. Here, the surrounding control flow (`success`) does not actually validate that value moved to the beneficiary.

### Impact Explanation
Any beneficiary/solver expecting to be paid out of escrow for orders whose input token returns `false` on failed transfers (e.g., insufficient balance edge cases, blacklist/pausable tokens, or a token an attacker deliberately designs to sometimes return `false`) can have the destination-chain fill/refund message processed, the order irreversibly finalized (`_filled[commitment]` set, escrow zeroed), and the entitled beneficiary receive zero tokens — a direct, unrecoverable loss of the escrowed asset with no way to re-trigger withdrawal since `_orders[...]` has already been decremented and `_filled[...]` marks the order as settled.

### Likelihood Explanation
The order's input token is chosen freely by the user who calls `placeOrder` — this is a fully permissionless, unprivileged action (no malicious relayer, prover, or governance actor required). An attacker who places an order using a token they control that returns `false` under specific conditions (or a widely-used non-reverting token that happens to hit an edge case, e.g. paused/blacklisted transfers) can trigger this on the Tron deployment whenever settlement runs through `withdraw()`. The bug is deterministic and locally provable from the code (no dependency on external actors) — the only requirement is that `withdraw()` be reached with such a token in `body.tokens`, which happens for both `RedeemEscrow` and `RefundEscrow` request kinds processed via `onAccept`.

### Recommendation
Match the mainline EVM contract's pattern: use `SafeERC20.safeTransfer` (or explicitly decode and check the boolean return value when present, and require nonzero returndata length for non-standard tokens) so that a failed transfer reverts the entire transaction, rather than allowing escrow state to be decremented independent of confirmed fund delivery. Additionally, decrement `_orders[body.commitment][token]` *before* the external call (checks-effects-interactions), consistent with the already-fixed mainline implementation, to remove any window where fund movement and accounting can diverge.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer()` returns `false` (without reverting) whenever `to == <attacker-chosen address>` or under an attacker-controlled condition (e.g., a toggle they flip after the order is placed but before settlement).
2. Attacker calls `placeOrder` on the source chain (Tron) with `EvilToken` as one of `order.inputs`, following normal escrow flow — fully permissionless.
3. A legitimate solver fills the order cross-chain as usual; the destination chain dispatches a `RedeemEscrow` (or the user cancels, triggering `RefundEscrow`) settlement message back to the Tron source chain.
4. `onAccept()` calls `withdraw(body, isRefund)`. Attacker has set `EvilToken.transfer` to return `false` for this call.
5. In `withdraw()`: `_orders[body.commitment][token] == 0` check passes (escrow existed), `token.call(...)` succeeds at the EVM-call level (`success == true`) even though `EvilToken.transfer` internally returned `false` and moved no tokens, so `TransferFailed` is never raised.
6. `_orders[body.commitment][token] -= amount` executes, zeroing the escrow record; `_filled[commitment]` is set, `EscrowReleased`/`EscrowRefunded` is emitted.
7. The intended beneficiary (solver or user) receives 0 `EvilToken`, but the protocol considers the order fully and correctly settled — the escrowed tokens are permanently lost/stuck with no further recourse. [2](#0-1) [3](#0-2)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
