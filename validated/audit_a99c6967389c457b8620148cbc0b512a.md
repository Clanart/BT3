### Title
`SchnorrAggregate::verify` accepts an empty aggregate, allowing trivial forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the DODO report where parameter `K` had an upper bound (`k <= 10**18`) but no lower bound (`k > 0`), `SchnorrAggregate::verify` enforces only an *equality* bound — `self.Rs.len() == keys_and_challenges.len()` — and never enforces the lower bound that at least one signature be present. With both lists empty the verification equation degenerates to `-s * G == 0`, which any attacker satisfies by setting `s = 0`. An empty `SchnorrAggregate` is fully attacker-controlled via `SchnorrAggregate::read`, which reads a `u32` count of `0` and then `s`. This is a reachable, public `read`/`verify` API surface fed untrusted bytes.

### Finding Description
In `crypto/schnorr/src/aggregate.rs:127-146`, verification builds the half-aggregation equation `sum(z_i * R_i + z_i * c_i * A_i) - s * G == 0`. When `Rs` and `keys_and_challenges` are both empty, the loop at `aggregate.rs:139-143` pushes no pairs and only `(-s, G)` remains (`aggregate.rs:144`). The equality check at `aggregate.rs:128` passes for `0 == 0`, so the proof of "at least one valid signature" reduces to `s == 0`. The same missing-non-empty pattern exists in `DLEqProof::verify` (`crypto/dleq/src/lib.rs:160-180`), which checks `generators.len() == points.len()` but not `> 0`; with empty inputs an attacker computes the transcript challenge themselves (it depends only on the domain-separated transcript with nothing appended) and sets the proof's `c` field to it, forging a DLEq proof that binds nothing. `SchnorrAggregator::complete` correctly returns `None` for empty inputs (`aggregate.rs:176`), confirming the protocol intends a non-empty set — the verifier just never enforces it on the untrusted side.

### Impact Explanation
Any verifier that derives authorization from `SchnorrAggregate::verify` returning `true` over attacker-supplied `(Rs, keys_and_challenges)` accepts a forgery asserting that zero signers signed. For `DLEqProof::verify`, a proof that "these points share a discrete log" verifies while proving nothing, which would pass any caller that supplies the generator/point lists dynamically from untrusted input. Both are forged-proof/forged-signature outcomes, not merely "unusual behavior".

### Likelihood Explanation
Requires an integrator to pass an empty (or attacker-influenced-length) key list to `verify`. The lists are parameters to a public verification API over deserialized untrusted data, and the library itself is in-scope `crypto/schnorr`. Since no in-scope caller currently feeds an empty list, exploitability depends on the consumer; consistent with the Medium severity of the source report, this is a missing validation boundary in a security-critical verification routine rather than a guaranteed compromise.

### Recommendation
Add a lower-bound check mirroring the intent in `SchnorrAggregator::complete`:
```rust
if self.Rs.len() != keys_and_challenges.len() || self.Rs.is_empty() {
    return false;
}
```
in `crypto/schnorr/src/aggregate.rs:128`, and analogously reject `generators.is_empty()` in `DLEqProof::verify` (`crypto/dleq/src/lib.rs:166`) and `MultiDLEqProof::verify` (`crypto/dleq/src/lib.rs:264-294`).

### Proof of Concept
```rust
// Attacker crafts bytes: len = 0, s = 0
let mut bytes = vec![];
bytes.extend(0u32.to_le_bytes());        // zero Rs
bytes.extend(C::F::ZERO.to_repr().as_ref());
let agg = SchnorrAggregate::<C>::read(&mut bytes.as_slice()).unwrap();
// Forged "aggregate signature" verifies against an empty signer set
assert!(agg.verify(b"some_dst", &[]));   // multiexp over [(-0, G)] is identity
```
The same holds for `DLEqProof`: with `generators = &[]`, `points = &[]`, set `c` equal to the challenge obtained by running `transcript.domain_separate(b"dleq")` then `challenge(&mut transcript)` locally (all public operations), any `s`; `verify` returns `Ok(())`.

Uncertainty: I did not locate an in-scope production caller that passes attacker-controlled-length lists into these verifiers (`SchnorrAggregate` appears unused by `networks/bitcoin`), so the severity rests on the verification API itself failing to enforce the documented non-empty precondition, matching the Medium bar of the source report.
