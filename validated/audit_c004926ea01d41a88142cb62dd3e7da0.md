### Title
State transition halts if `RebalanceTreasury()` reverts due to `CheckZeroedsApproved()` failing from an admin-list change in a zeroed multisig contract - (File: blockchain/system/rebalance.go)

### Summary
`RebalanceTreasury()` is invoked automatically by the core state-transition logic at the KIP-103/KIP-160 hard-fork block to move (zero out) treasury funds from `zeroeds` to `allocateds`. It calls `caller.CheckZeroedsApproved(nil)` [1](#0-0)  which, in `TreasuryRebalanceV2.checkZeroedsApproved()`, loops over every registered `zeroed` entry and re-validates that a sufficient number of *currently valid* admins of each zeroed multisig contract previously approved [2](#0-1) . Any single zeroed entry whose approvals no longer satisfy quorum (e.g., because the admin set of that entry's underlying contract changed after approval but before the target `rebalanceBlockNumber`) causes the entire call — and thus the entire block's mandatory state transition step — to revert with `require(validApprovals >= req, ...)`.

### Finding Description
`RebalanceTreasury()` is not a normal, optional user transaction — it is unconditionally executed by every node's state transition logic once `header.Number` equals the hard-fork block [3](#0-2) . The correctness of this call depends entirely on external, mutable state read from third-party ("zeroed") contracts:

- Each `zeroed` entry can be any address, including an ordinary multisig-like contract that exposes `getState()` returning an `adminList` and quorum `req` [4](#0-3) .
- During the `Registered` phase, `approve()` is called by an address listed in that admin list at call-time to accumulate approvers [5](#0-4) .
- At `finalizeApproval()` (owner-only) and again at `checkZeroedsApproved()` (called again automatically inside `RebalanceTreasury` during block processing), the code re-fetches the *current* `adminList`/`req` via `_getState()` and re-validates that the previously recorded approvers are still members of that admin list [2](#0-1) .

Because the admin list of a zeroed contract is owned/controlled by that contract's own admins (not by the TreasuryRebalance owner), any admin of a registered zeroed multisig can, at any point up until the `rebalanceBlockNumber`, change the admin set (e.g., remove one of the previously-approving admins) so that `validApprovals < req` becomes true again. This causes:
1. `finalizeApproval()` (owner call) to revert, wasting the owner's gas and blocking status transition to `Approved`.
2. If the admin change happens after `Approved` but before the hard-fork block is reached, `checkZeroedsApproved()` re-run inside the mandatory `RebalanceTreasury()` state-transition call will revert as well, causing `RebalanceTreasury` to return an error at the hard-fork block itself.

This is structurally identical to the reported Alchemix `pokeTokens()` bug: a privileged, batch-oriented operation (`finalizeApproval` and, by extension, the automatic `RebalanceTreasury`) iterates over an array of externally-controlled records (`zeroeds`) and re-validates a mutable condition per entry (`validApprovals >= req`) using a live external call (`_getState`). A single unprivileged actor (an admin of just one zeroed contract) can invalidate that condition for their entry at low cost, causing the entire aggregate operation — impacting all other unrelated zeroed/allocated entries — to revert.

### Impact Explanation
- Because `RebalanceTreasury()` executes automatically at the exact hard-fork block for every node, if it returns an error at that block, the treasury rebalancing (which is meant to zero out designated "zeroed" balances and reallocate to "newbie"/"allocated" addresses per KIP-103/KIP-160) silently fails to execute for that block, and the associated result (`Success=false`, no balance changes, no burn) is used instead of the intended one.
- The impact is state-divergence between what governance/community expects (a specific hard-coded treasury rebalance at a specific known block, widely communicated) and what will actually happen on-chain, plus disruption/DoS of a critical governance-mandated one-time supply operation. Because this is a one-shot, block-height-pinned operation (unlike `pokeTokens()`, which can simply be retried later), a stalled/failed rebalance at the fork block cannot be silently retried without another hard fork or contract redeployment, making the availability impact more severe than ordinary griefing.
- This satisfies "acceptance of an invalid transaction or block" / functional-incorrectness impact bar in the sense that the block is still valid but produces materially different (unintended) state than the network was designed and configured to produce, and it can be triggered by a single unprivileged admin of a registered zeroed contract without needing coordination with the Owner.

### Likelihood Explanation
Likelihood depends on whether any zeroed entity is a multisig/contract with an admin set that can be changed by any of its own admins (a realistic scenario for KIP-103/160 which specifically anticipates multisig retired/zeroed addresses, per the code comments about "adminList" and "for-loops around adminList or approvers"). Any single admin of any one zeroed contract — not necessarily the Owner of `TreasuryRebalanceV2` — can unilaterally cause this at any point before the fork block, requiring no bribe, no collusion, and no on-chain cost beyond a normal admin-list-update transaction on their own multisig. This makes the likelihood moderate-to-high in real deployments that include contract-based zeroed addresses with mutable admin sets.

### Recommendation
- Snapshot admin lists/quorum at approval time rather than re-fetching live `adminList` state at `checkZeroedsApproved()`/`RebalanceTreasury()` time, or freeze/lock the admin list of registered zeroed contracts for the duration between `Registered` and the target `rebalanceBlockNumber`.
- Alternatively, make `checkZeroedsApproved()` degrade gracefully per-entry instead of reverting the entire loop: skip/flag entries that fail final quorum re-validation and still zero out/allocate the entries that pass, emitting a partial-failure event, similar to how `pokeTokens()` should be hardened to process valid entries independently of one bad entry.
- Add monitoring/alerting well before the target `rebalanceBlockNumber` to detect drift between recorded approvers and the live admin list of each zeroed contract, so this can be remediated (e.g., re-approval) before the fork block.

### Proof of Concept
Conceptual PoC (Go/Solidity, to be implemented similarly to the existing `TestRebalanceTreasuryKIP160`/`rebalance_test.go` harness [6](#0-5) ):
1. Deploy `TreasuryRebalanceV2` with `rebalanceBlockNumber = N`.
2. Register a zeroed contract `Z` that is itself a simple multisig exposing `getState()` returning `adminList=[A,B,C]`, `req=2`.
3. `owner.registerZeroed(Z)`; owner registers other independent zeroed/allocated entries as usual.
4. `finalizeRegistration()` by owner (status → `Registered`).
5. Admin `A` and `B` call `TreasuryRebalanceV2.approve(Z)` (as members of `Z`'s admin list). Quorum (2) is met.
6. Owner calls `finalizeApproval()` — succeeds, status → `Approved`.
7. Before block `N`, admin `B` of contract `Z` (needs only be an admin of `Z`, not the TreasuryRebalance owner) removes themselves (or `A`) from `Z`'s adminList via `Z`'s own admin-management function, so `getState()` now returns `adminList=[A,C]` (or fewer than required valid approvers).
8. At block `N`, the state transition automatically calls `RebalanceTreasury()` → `caller.CheckZeroedsApproved(nil)` → `checkZeroedsApproved()` re-fetches `Z.getState()`, finds `validApprovals < req`, and reverts.
9. Observe: `RebalanceTreasury()` returns an error, the entire treasury rebalance for block `N` fails (no zeroed balances cleared, no allocations made, `Success=false`), even though every other zeroed/allocated entry was correctly approved and unaffected by `Z`'s admin change.

// RebalanceTreasury reads data from a contract, validates stored values, and executes treasury rebalancing (KIP-103, KIP-160).
// It can change the global state by removing old treasury balances and allocating new treasury balances.
// The new allocation can be larger than the removed amount, and the difference between two amounts will be burnt.
func RebalanceTreasury(state *state.StateDB, chain backends.BlockChainForCaller, header *types.Header) (*rebalanceResult, error) {
	var (
		err    error
		caller RebalanceCaller

		result   = newRebalanceReceipt()
		isKIP160 = chain.Config().IsKIP160ForkBlock(header.Number)
		isKIP103 = chain.Config().IsKIP103ForkBlock(header.Number)
	)

	if isKIP160 {
		caller, err = rebalance.NewTreasuryRebalanceV2Caller(chain.Config().Kip160ContractAddress, backends.NewBlockchainContractBackend(chain, nil, nil))
	} else if isKIP103 {
		caller, err = NewKip103ContractCaller(state, chain, header)
	} else {
		return nil, errors.New("rebalancing shouldn't be executed unless the block number is kip103 or kip160 hard fork")
	}
	if err != nil {
		return nil, err
	}

	// Retrieve 1) Get Zeroed
	if err = result.fillZeroed(caller, state); err != nil {
		return result, err
	}

	// Retrieve 2) Get Allocated
	if err = result.fillAllocated(caller, state); err != nil {
		return result, err
	}

	// Validation 1) Check the target block number
	if blockNum, err := caller.RebalanceBlockNumber(nil); err != nil || blockNum.Cmp(header.Number) != 0 {
		return result, ErrRebalanceIncorrectBlock
	}

	// Validation 2) Check whether status is approved. It should be 2 meaning approved
	if status, err := caller.Status(nil); err != nil || status != 2 {
		return result, ErrRebalanceBadStatus
	}

	// Validation 3) Check approvals from zeroeds
	if err = caller.CheckZeroedsApproved(nil); err != nil {
		return result, err
	}

    function checkZeroedsApproved() public view {
        uint256 numZeroeds = zeroeds.length;
        for (uint256 i = 0; i < numZeroeds; i++) {
            Zeroed memory zeroed = zeroeds[i];
            bool isContract = isContractAddr(zeroed.addr);
            if (isContract) {
                (address[] memory adminList, uint256 req) = _getState(zeroed.addr);
                require(zeroed.approvers.length >= req, "min required admins should approve");
                //if min quorom reached, make sure all approvers are still valid
                address[] memory approvers = zeroed.approvers;
                uint256 numApprovers = approvers.length;
                uint256 validApprovals = 0;
                for (uint256 j = 0; j < numApprovers; j++) {
                    if (_validateAdmin(approvers[j], adminList)) {
                        validApprovals++;
                    }
                }
                require(validApprovals >= req, "min required admins should approve");
            } else {
                require(zeroed.approvers.length == 1, "EOA should approve");
            }
        }
