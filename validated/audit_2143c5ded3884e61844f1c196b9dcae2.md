## Title
Hardcoded zero slippage protection in `ArbWomUp3._deposit` (mode 2) exposes users to sandwich/MEV attacks on WOM→mWom swap - (File: `wombat/ArbWomUp3.sol`)

### Summary
`ArbWomUp3.incentiveDeposit` with `_mode == 2` routes half of the user's deposited WOM through `SmartWomConvert.convert`, but the minimum-received slippage parameter is hardcoded to `0` instead of being derived from user input or an on-chain quote, effectively disabling the slippage protection that the underlying convert/swap machinery otherwise supports.

### Finding Description
`ArbWomUp3.incentiveDeposit` is a public, unprivileged entry point that lets any wallet deposit WOM for MGP-lock incentives [1](#0-0) . When `_mode == 2`, `_deposit` splits the deposit: half is deposited directly into `mWom`, and half is routed through `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` [2](#0-1) .

The third argument to `convert` is `_minRec`, which `SmartWomConvert.convert` forwards into `_convertFor` as the minimum acceptable output [3](#0-2) . Inside `_convertFor`, whenever `_convertRatio < DENOMINATOR` (i.e., `buybackAmount > 0`), a portion of WOM is swapped for mWom through the Wombat router via `swapExactTokensForTokens`, and the combined swap+deposit output is checked against `_minRec`: `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` [4](#0-3) .

Because `ArbWomUp3._deposit` always passes `0` as `_minRec`, this check can never revert — regardless of how much the swap output is manipulated by front/back-running the transaction. The swap itself calls the router with the actual amount received from the pool with no user-configurable floor, so a mempool attacker can sandwich the embedded WOM→mWom swap and extract most of its value from the depositor.

### Impact Explanation
Any ordinary wallet calling `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` with `_convertRatio < 10000` triggers an on-chain AMM swap with zero slippage protection baked into the calling contract, even though the underlying `SmartWomConvert.convert`/`_convertFor` interface was designed to support a caller-supplied minimum. This is a direct analog of the reported issue class (function accepts/ignores a slippage parameter, hardcoding it to a non-protective value), enabling a sandwich attacker to capture value that otherwise belongs to the depositing user — a direct theft of user funds.

### Likelihood Explanation
Any unprivileged wallet triggers this path simply by calling `incentiveDeposit` with `_mode == 2`, which is a normal, documented usage mode (`// 1 stake, 2 lock`) [5](#0-4) . No special permissions, governance action, or unusual conditions are required — only a public mempool where MEV searchers can observe and sandwich the pending transaction, which is the standard threat model referenced in the original report.

### Recommendation
Add a `_minRec` (or equivalent minimum-mWom-received) parameter to `incentiveDeposit`/`_deposit` and thread it through to `IConverter(smartWomConvert).convert(toSwap, _convertRatio, _minRec, 0)` instead of hardcoding `0`, so users can bound their acceptable slippage on the embedded swap.

### Proof of Concept
1. User calls `incentiveDeposit(_amount, _convertRatio, false, 2)` with `_convertRatio < 10000`.
2. `_deposit` computes `toSwap = _amount - toDeposit` and calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` [6](#0-5) .
3. `SmartWomConvert._convertFor` executes `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` and then only checks `convertAmount + amountRec < _minRec` where `_minRec == 0` [7](#0-6) , so the check never blocks execution regardless of price impact.
4. A searcher front-runs the pending transaction to push the WOM/mWom pool price against the user, lets the swap execute at the worsened rate, then back-runs to restore the price, capturing the difference as profit extracted from the victim's deposit.
