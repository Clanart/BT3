## Analysis

The Chakra report's root cause is that a cryptographically signed message's *semantic fields* (the `ERC20Method`) are not validated at the destination — the code trusts that a signed payload is what it claims to be without checking a field that should determine how it's processed. The same pattern exists in `shopify_app`'s webhook processing.

`ShopifyApp::PayloadVerification#hmac_valid?` computes the webhook signature **only over the raw request body**: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, and separately exposes `shop_domain` straight from the `X-Shopify-Shop-Domain` header — a header that is **not part of the HMAC digest**: [2](#0-1) 

The `X-Shopify-Topic` header is likewise unauthenticated; only the body is signed. Both `WebhooksController#receive` (default flow) and the officially documented custom-controller pattern route webhook processing using these unauthenticated headers: [3](#0-2) [4](#0-3) 

Generated jobs then trust the `shop`/`shop_domain` value to look up and act on a `Shop` record and open a Shopify session for it: [5](#0-4) 

### Title
Webhook HMAC does not bind `X-Shopify-Shop-Domain`/`X-Shopify-Topic`, enabling cross-shop webhook replay - (File: `lib/shopify_app/controller_concerns/payload_verification.rb`, `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`hmac_valid?` verifies only `request.raw_post` against the shared app secret; the shop-domain and topic headers used to route and attribute the webhook are never included in the signed data.

### Finding Description
Any merchant who has installed the app receives real webhooks for their own shop, each carrying a valid HMAC computed with the app's shared secret (the same secret used for every shop, per [6](#0-5) ). Because `verify_request` only checks that the HMAC matches the raw body ( [7](#0-6) ), that same signed body can be replayed to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header — the signature still validates because those headers were never part of what was signed. This mirrors the reported bug class: a field that determines how a trusted, signature-verified message should be handled (`ERC20Method` there, `shop_domain`/`topic` here) is never itself validated/bound to the signature.

### Impact Explanation
Webhook jobs use the unauthenticated `shop_domain` to look up the target `Shop` and open a session for it, e.g. `Shop.find_by(shopify_domain: shop_domain)` then `shop.with_shopify_session` in the generated job template ( [8](#0-7) ). An attacker/merchant who is a legitimate install of the app can replay a validly-signed webhook body they received for their own shop while substituting a victim shop's domain, causing app logic to execute in the victim shop's session context using attacker-controlled body content — a cross-shop confusion/injection primitive. The same applies to the mandatory privacy webhook jobs (`customers/redact`, `customers/data_request`, `shop/redact`) which take the same unauthenticated `shop_domain` ( [9](#0-8) ).

### Likelihood Explanation
Requires an attacker to first obtain one legitimately-signed webhook (trivial: install the app on any shop and observe the real webhook Shopify sends them), then replay it with modified headers to the app's public webhook endpoint. No secret material needs to be recovered; only header substitution on a captured, validly-signed request.

### Recommendation
Bind the shop domain (and ideally topic) into the authenticated payload — e.g., verify that `shop_domain`/`topic` in the headers correspond to the actual `Shop` record the webhook is legitimately registered for, or include these header values in the HMAC computation (as Shopify itself does not do), and reject any webhook whose header-declared shop does not match a shop for which that specific delivery was registered.

### Proof of Concept
1. Install the app as shop A and capture a legitimate webhook POST (valid `X-Shopify-Hmac-Sha256` over the raw body, `X-Shopify-Shop-Domain: shop-a.myshopify.com`).
2. Replay the identical body/HMAC to the webhook endpoint, changing only `X-Shopify-Shop-Domain` to `shop-b.myshopify.com` (a victim shop).
3. `verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` passes because the HMAC only covers the body.
4. The downstream job (per the generator templates) loads `Shop` "shop-b", opens its session, and processes attacker-supplied body content attributed to shop B.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
