Confirmed: `_commitIncludedChanges` in `app/src/lib/stores/app-store.ts` reads the `WorkingDirectoryFileChange.selection` (line indices) captured in React/store state at whatever point the user last interacted with the diff view, and hands those files straight to `createCommit` → `stageFiles` → `applyPatchToIndex` without re-validating the selection against a freshly-read diff. `applyPatchToIndex` then re-fetches the diff from disk via `getWorkingDirectoryDiff` at commit time and builds a patch by re-applying the old index-based `selection.isSelected(absoluteIndex)` to this new diff. The one place that *does* revalidate selectable lines against a freshly loaded diff — `updateChangesWorkingDirectoryDiff` in `app-store.ts` — only runs on the "Changes" view refresh path, not on the actual commit path, and it only prunes to "selectable" lines, it doesn't reconcile semantic identity of a line at a given index.

### Title
Index-based partial-commit selection is revalidated against the working-directory diff only in the UI-refresh path, not at commit time - ([File: app/src/lib/git/apply.ts])

### Summary
Partial (line-level) staging in Desktop is driven entirely by absolute line indices captured against a diff snapshot rendered earlier in the UI. At commit time, `applyPatchToIndex` re-reads the diff from disk and reapplies those stale indices, with no check that the file content (and therefore the meaning of each index) is unchanged since the user made their selection.

### Finding Description
`app/src/lib/patch-formatter.ts:formatPatch()` and `app/src/lib/git/apply.ts:applyPatchToIndex()` build the patch to stage using `file.selection.isSelected(absoluteIndex)` [1](#0-0) , where `absoluteIndex` is a position in whatever diff is fetched **at commit time**: [2](#0-1) . This `getWorkingDirectoryDiff` call happens inside `stageFiles`/`applyPatchToIndex`, not against the diff the user reviewed when they made the selection in the Changes view.

The `selection` object itself, however, is created and mutated purely from index positions computed against the diff that was loaded when the file was last displayed (`_changeFileLineSelection` → `updateWorkingDirectoryFileSelection`) [3](#0-2) . When the commit action fires, `_commitIncludedChanges` takes the files exactly as stored in `changesState.workingDirectory.files` [4](#0-3)  and passes them to `createCommit`, which calls `stageFiles` → `applyPatchToIndex` [5](#0-4) .

Only the interactive refresh path (`updateChangesWorkingDirectoryDiff`) re-fetches the diff and trims the selection down to currently "selectable" line indices — and even there, the comment acknowledges the guard is weak: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines"* [6](#0-5) . This refresh only fires on selection/focus changes, and there is no guarantee it runs, or completes, immediately before `_commitIncludedChanges` reads `state.changesState.workingDirectory.files`. Nothing recomputes or diffs content between the time the user finished picking lines and the moment `applyPatchToIndex` re-reads the file from disk.

**Broken invariant:** "the byte ranges the user visually selected for inclusion are the byte ranges that end up in the commit." Because selection is keyed by index into a diff, and the diff used to build the actual patch is re-derived from disk at a different point in time, any content change to the working-directory file between selection and commit (a build tool, a formatter-on-save, an editor autosave, a git hook triggered by a background fetch/checkout, or any other process writing to the file) can shift hunk boundaries so that the previously-selected indices now correspond to entirely different, unreviewed lines. `git apply --cached` will happily apply the same numeric hunk against a shifted context, and if it fails to match context, the operation errors out — but if the file changed in a way that keeps line offsets numerically valid (e.g. edits elsewhere in the file, or a hunk with `--unidiff-zero` matching by line number rather than context), the wrong content is silently staged and committed.

### Impact Explanation
This is a "silent corruption of what the user commits" scenario: the user believes they reviewed and approved a specific set of lines, but the actual commit content can differ from what was shown, without any error or warning. In the general case this requires some other local process to be racing the write (arguably a "local access" precondition), which weakens applicability under the stated valid-impact rules — this is the main uncertainty in this finding. It becomes more concerning specifically where Desktop itself triggers concurrent working-directory mutation from an attacker-influenced source (e.g., a malicious `post-checkout`/`post-merge`/filter/smudge hook shipped in a cloned repository executing during a background `_refreshRepository` or LFS filter step) while a commit is being prepared, but I could not find code in this repo that clearly demonstrates such an automatic self-race without additional user action, so I cannot fully confirm this crosses into the "attacker controls a cloned repository" category without further investigation of hook/LFS filter timing relative to `_commitIncludedChanges`.

### Likelihood Explanation
Low-to-Medium. It requires a concurrent modification to the exact file being partially staged, occurring in the narrow window between UI selection and the commit's `git apply --cached` call. In common workflows (format-on-save tools, linters, LFS smudge filters, or hostile repo hooks that fire on refresh operations Desktop performs automatically) this window is realistic, but it isn't a one-click remote-triggered exploit — it depends on some other process editing the file during that window.

### Recommendation
Before staging, re-fetch the working-directory diff for each file included in the commit and re-validate (not just prune) the user's line selection against it — e.g., by hashing or diffing the file content used to compute the original selection against the content used to build the patch, and aborting/prompting if they differ, rather than silently reapplying stale absolute indices. Alternatively, base partial-commit patches on content-anchored context (as `git apply` normally does, rather than `--unidiff-zero`) so a mismatch fails loudly instead of silently applying to shifted content.

### Proof of Concept
1. In a repository, modify `foo.txt` so the Changes view shows several hunks.
2. In the diff view, select only a specific line (say, line 20) for the next commit — this becomes a `DiffSelection` bound to `absoluteIndex` 20 in the diff loaded at that time, per `_changeFileLineSelection` in `app/src/lib/stores/app-store.ts:3886-3894`.
3. Before pressing "Commit", have another process (an editor autosave, a build watcher, or — in the attacker-repo scenario — a git hook fired by a background `fetch`/`refresh`) insert or remove lines earlier in `foo.txt`, shifting what content sits at absolute index 20, without changing the total structure enough to break `git apply`'s zero-context hunk matching (`--unidiff-zero` in `app/src/lib/git/apply.ts:52-58`).
4. Click "Commit". `applyPatchToIndex` calls `getWorkingDirectoryDiff` fresh against the now-modified file [7](#0-6)  and `formatPatch` reapplies the stale `absoluteIndex`-based selection to it [8](#0-7) , producing and committing a patch that does not correspond to the line the user actually reviewed and selected.
