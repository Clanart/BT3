### Title
Uncontrolled panic (HashMap index on unregistered participant) in PedPoP blame path enables remote DoS - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class in CVE-2022-34665 is a null-pointer dereference reachable by a low-privilege local party, yielding denial of service. The Rust analog is an uncontrolled panic on attacker-supplied indexes. In `BlameMachine::blame` / `AdditionalBlameMachine::blame`, the `recipient` and `sender` `Participant` values come from an arbitrary accusation and are never range-checked against `n`. The first use of `recipient` is the indexing expression `self.enc_keys[&decryptor]` inside `Decryption::decrypt_with_proof`, evaluated while building the DLEq verification arguments — before the proof is checked — so a registered `Participant` index that was never assigned an encryption key (any `recipient > n`) causes `HashMap`'s `index` impl to panic, crashing the evaluator.

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys only for `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs:656-660`). `AdditionalBlameMachine::blame` accepts `sender: Participant, recipient: Participant` from an accusation with no bounds check (`lib.rs:674-682`) and forwards them to `blame_internal` (`lib.rs:575-609`), which calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`.

Inside `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366-397`):

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],   // encryption.rs:388
)
```

The `self.enc_keys[&decryptor]` index is evaluated to construct the argument list before `DLEqProof::verify` runs. If `decryptor` (the accusation's `recipient`) is any `Participant` outside `1 ..= n` — e.g. `Participant::new(n + 1)` or `u16::MAX`, both constructible via the public `Participant::new` (`crypto/dkg/src/lib.rs:29-35`) — the key is absent and `HashMap::index` panics. A symmetric panic exists at `self.commitments[&sender]` (`lib.rs:599`) for an out-of-range `sender` when execution reaches share verification.

Reaching line 388 requires only that `msg.pop` be a valid Schnorr signature over `pop_challenge`, which the attacker can generate themselves (pick scalar `k`, set `key = k*G`, sign the challenge — the PoP intentionally has no external root of trust, per the comments at `encryption.rs:300-301`), and pass `Some(_)` for `proof` — the DLEq proof itself is never examined before the panic.

### Impact Explanation
`AdditionalBlameMachine` is the public arbitrator any node can instantiate to adjudicate DKG fault claims. A single malicious accusation naming a non-existent recipient deterministically panics the evaluator thread, aborting the DKG/blame-evaluation process. Under CVSS terms this is an availability-only impact (A:H, no C/I), matching the Medium-severity DoS profile of the reference CVE.

### Likelihood Explanation
Triggering requires a well-formed `EncryptedMessage` with a valid PoP (trivially craftable) and a blame accusation naming `recipient` outside `1 ..= n`. No secret knowledge, valid DLEq proof, or collusion is needed. Exploitability depends on the caller exposing `blame` to unauthenticated accusations, which is the documented purpose of `AdditionalBlameMachine` ("capable of evaluating Blame regardless of if the caller was a member in the DKG protocol", `lib.rs:639-648`).

### Recommendation
Range-check `sender` and `recipient` in `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `blame_internal` against the registered participant set (e.g., return an error or treat out-of-range parties as faulty) before indexing. Additionally, replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `get(...)`/`ok_or`-style lookups so malformed accusations produce errors rather than panics.

### Proof of Concept
```rust
// n = 3 DKG completed normally; all of 1..=3 registered.
let mut machine = AdditionalBlameMachine::<Ed25519>::new(context, 3, commitment_msgs).unwrap();

// Attacker crafts a message it can sign a PoP for.
let k = <Ed25519 as Ciphersuite>::random_nonzero_F(&mut rng);
let key = Ed25519::generator() * k;
let msg: EncryptedMessage<Ed25519, SecretShare<_>> = /* encrypt with known key k,
    producing a valid SchnorrSignature pop */;

// Accusation naming a recipient that was never a participant (4 > n = 3).
machine.blame(
  sender,
  Participant::new(4).unwrap(), // never registered in enc_keys
  msg,
  Some(any_proof),              // contents irrelevant; never verified
);
// Panics at encryption.rs:388 on self.enc_keys[&decryptor] (index out of map).
```

The panic occurs during argument evaluation of `dleq.verify`, so even a garbage `EncryptionKeyProof` suffices; the only gate is the attacker-generated PoP signature.
