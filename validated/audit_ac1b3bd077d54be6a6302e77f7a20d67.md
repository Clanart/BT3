### Title
`Scanner::register_offset` silently rejects colliding offsets, blocking registration of legitimate deposits - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::register_offset` returns `None` when the script derived from a requested offset is already present in `self.scripts` (`networks/bitcoin/src/wallet/mod.rs:187-189`). Because offsets are surjective — each requested offset is incremented until `key + offset*G` yields an even-Y point usable as a P2TR output key — an offset requested by a later deposit can be bumped into a script already registered by an earlier deposit. The duplicate-script guard then aborts registration entirely rather than recording the new deposit's binding, permanently dropping that output registration from the scanner's intended bookkeeping.

### Finding Description
The bug class from the external report is an over-strict guard placed on a state-management path that blocks a legitimate operation without adding security. `register_offset` exists to register scanning state; it is not authorizing a fund transfer. Its loop (`mod.rs:184-195`) mutates the caller's offset (`offset += Scalar::ONE`) until `p2tr_script_buf(self.key + G*offset)` succeeds, then rejects registration if `self.scripts.contains_key(&script)`. Since the map is keyed by `ScriptBuf` while callers key their state by the *requested* offset, two distinct requested offsets can converge to the same script: if `o_b` requested later iterates to `o_b + k == o_a` (already registered), registration fails and the function returns `None`. The docstring itself acknowledges the surjectivity hazard ("offsets are surjective, not bijective, and the order offsets are registered in may determine the validity of future offsets", lines 170-175).

An unprivileged party reaches this via a Bitcoin deposit they send: the deposit's `InInstruction` data determines the offset the processor registers. By choosing data whose derived offset, post-increment, collides with an existing registered script, the attacker triggers the `None` return.

### Impact Explanation
When `register_offset` returns `None`, the deposit's output cannot be registered under its intended offset binding. Worse, `scan_transaction` (`mod.rs:205-211`) still matches outputs by `script_pubkey` and returns the *first* registered offset, so coins the attacker sends to the colliding script are attributed to the earlier offset's `ReceivedOutput`. The result is deposits that are either never credited under their intended instruction or misattributed to another registration — funds reported received that are not spendable under the intended binding, a permanent accounting/spendability failure rather than a transient liveness issue.

### Likelihood Explanation
The attacker fully controls the `InInstruction` data feeding offset derivation, and collisions require only that the incremented offset land on an already-registered value — feasible given the 50%-per-iteration increment walk over a growing registration table. No validator collusion, key material, or privileged access is needed.

### Recommendation
Do not return `None` on script collision. Either bind received outputs to the requested (pre-increment) offset so distinct deposits remain distinguishable, or make the `scripts` map support multiple logical registrations per script (e.g., `HashMap<ScriptBuf, Vec<Scalar>>` or a reverse map preserving the requested offset) and surface collisions explicitly so the caller can handle them rather than silently dropping the registration.

### Proof of Concept
1. Honest registration: `register_offset(o_a)` returns `Some(o_a)`, inserting `script_a -> o_a`.
2. Attacker crafts a deposit whose derived offset `o_b` produces an odd point, so the loop tries `o_b + 1 == o_a`. `p2tr_script_buf` returns `script_a`, `scripts.contains_key` is true, and the function returns `None` — the deposit's registration is silently dropped.
3. Any subsequent payment to `script_a` is returned by `scan_transaction` with `offset == o_a`, conflating the attacker's output with the earlier registration.
