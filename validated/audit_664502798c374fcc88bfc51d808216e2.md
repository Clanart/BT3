### Title

Forged `ReceivedOutput` objects decouple the claimed `TxOut` from the referenced UTXO - (`networks/bitcoin/src/wallet/mod.rs`)

### Summary

Medium. `ReceivedOutput::read` accepts an offset, an arbitrary `TxOut`, and an arbitrary `OutPoint`, but does not verify that the `OutPoint` actually references that `TxOut`. [1](#0-0)  A scanner-produced `ReceivedOutput` is trustworthy because `Scanner::scan_transaction` derives both fields from the same transaction output. [2](#0-1) 

### Finding Description

A `ReceivedOutput` combines a scalar offset, a claimed output, and the UTXO reference supposedly containing that output. [3](#0-2)  The deserializer reads all three independently and has no check that `outpoint` resolves to `output`, or that the output was actually observed by the scanner. [4](#0-3) 

`SignableTransaction::new` trusts the claimed `output.value` as spendable balance, uses the claimed `outpoint` as the transaction input, and stores the claimed `output` as the prevout. [5](#0-4) [6](#0-5)  `SignableTransaction::multisig` only verifies that the supplied prevout's `script_pubkey` matches the wallet key after applying the stored offset; it does not validate the `outpoint` indirection. [7](#0-6)  Signing then commits to the supplied prevout vector, while Bitcoin consensus resolves each input through its actual `OutPoint`. [8](#0-7) 

This mirrors the symlink-policy flaw: the visible address/script is validated, while the separately supplied reference—the `OutPoint` target—is followed without being authenticated against the claimed `TxOut`.

### Impact Explanation

An unprivileged party who can submit serialized `ReceivedOutput` bytes can report an arbitrary-value deposit to a wallet's public P2TR script while naming a nonexistent or unrelated outpoint. Downstream balance, accounting, or spend-construction code can treat these bytes as funds received even though they are not spendable.

If the mismatch is used to build a transaction, the signers may produce shares for a transaction that Bitcoin nodes reject because the supplied prevout does not match the real UTXO. This can cause fraudulent crediting, failed withdrawals, or signing work on transactions that cannot confirm.

### Likelihood Explanation

The attacker only needs the wallet's public P2TR script and the ability to feed serialized data to `ReceivedOutput::read`, which is within the stated input model. The issue is reachable wherever serialized scan results are persisted, forwarded between components, or accepted from an untrusted producer without an independent UTXO lookup.

If every `ReceivedOutput` is guaranteed to come directly from `Scanner::scan_transaction` and is never deserialized from untrusted storage or messages, the path is not reachable.

### Recommendation

Treat deserialization as parsing rather than proof of receipt. Resolve each `outpoint` against the containing transaction or a trusted UTXO view and require the resolved `TxOut` to equal the supplied `output`, including value and `script_pubkey`.

Add an authenticated constructor or verification API that also recomputes `p2tr_script_buf(key + offset * G)` and rejects outputs not belonging to the expected scanner registration. Do not let `SignableTransaction::new` accept wire-deserialized `ReceivedOutput` objects until that binding has been verified.

### Proof of Concept

```rust
// wallet_script is the wallet's public P2TR script.
let forged_txout = TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: wallet_script,
};

// This points to no confirmed output containing forged_txout.
let forged_outpoint = OutPoint::new(Txid::from_byte_array([0; 32]), 0);

let mut bytes = Scalar::ZERO.to_bytes().to_vec();
bytes.extend(serialize(&forged_txout));
bytes.extend(serialize(&forged_outpoint));

// Accepted despite the false OutPoint -> TxOut association.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000);

// The wallet accepts the script/offset relationship without resolving the outpoint.
let tx = SignableTransaction::new(
    vec![forged],
    &[(attacker_script, 900_000)],
    Some(change_script),
    None,
    fee_per_vbyte,
).unwrap();
assert!(tx.multisig(&wallet_keys).is_some());
```

The resulting transaction is signed over the fabricated prevout data but is invalid once nodes resolve `Txid::from_byte_array([0; 32]):0` to the real UTXO set. [7](#0-6) [9](#0-8)
