## Title
Code objects created by `object_code_deployment::publish` are left transferable (`allow_ungated_transfer = true`), letting a generic `object::transfer_call`/`transfer` silently hand over code upgrade/freeze authority - (File: `aptos-move/framework/aptos-framework/sources/object_code_deployment.move`)

### Summary
`object_code_deployment::publish` creates the on-chain code object via `object::create_named_object`, which by default sets `ObjectCore.allow_ungated_transfer = true` [1](#0-0) . Unlike other privileged/soulbound object patterns in the same codebase (collections, ambassador tokens) which explicitly call `disable_ungated_transfer` right after creation [2](#0-1) [3](#0-2) , `object_code_deployment::publish` never disables transfer on the code object [4](#0-3) . Both `upgrade` and `freeze_code_object` gate their privileged action solely on `object::is_owner(code_object, publisher_address)` [5](#0-4)  and `code::freeze_code_object` similarly checks only `object::is_owner` [6](#0-5) . Since ownership of an object with `allow_ungated_transfer = true` can be changed by anyone holding it via the generic, permissionless `object::transfer_call`/`object::transfer` entry functions [7](#0-6) [8](#0-7) , ownership (and with it upgrade/freeze authority over the deployed module code) can be transferred exactly like an NFT, without any code-specific gate or disable step.

### Finding Description
The publish flow does not follow the "one code object, one owner, no transfer" model implied by the module's own documentation ("Requires the publisher to be the owner of the code_object"), because it never restricts the object's transferability:

1. `publish` creates the object with `object::create_named_object` (default `allow_ungated_transfer: true`) and never generates/uses a `TransferRef` to call `disable_ungated_transfer` or `set_untransferable` [4](#0-3) .
2. `object::verify_ungated_and_descendant`, invoked by `transfer_raw`, only checks `allow_ungated_transfer` and the ownership chain - it performs no type-aware check to prevent transfer of an object that stores a `PackageRegistry`/`ManagingRefs` resource [9](#0-8) .
3. `upgrade`/`freeze_code_object` derive authorization purely from current `ObjectCore.owner`, with no additional binding to the original publisher or any transfer-lock [5](#0-4) .

As a result, the code object behaves like any transferable digital asset even though it actually functions as a capability that grants module-upgrade and freeze rights. A publisher who is misled (e.g., by a malicious dApp/marketplace payload built as an "NFT transfer" that actually targets the code-object address, or by simply reusing wallet flows that call `object::transfer_call` generically) into calling `0x1::object::transfer_call`/`transfer` on their code object silently and irrevocably transfers upgrade/freeze control of their live, on-chain module to the recipient address. There is no confirmation, warning, or code-object-specific restriction anywhere in the publish/upgrade/freeze path that would prevent this.

### Impact Explanation
This breaks a code-safety invariant required by the "Publish Pivots": *"Object code deployment and resource-account publish flows must not leak upgrade or freeze authority to unprivileged callers."* Once ownership is transferred, the new owner is fully privileged: they can call `upgrade` to replace the deployed module bytecode (subject only to the compatibility policy already recorded, e.g. `compat`), or call `freeze_code_object` to permanently lock the package, denying the original developer any further ability to patch it. For modules published under `compat` (not `immutable`) policy - the common case for actively maintained code - a transferred code object gives the new owner the ability to push arbitrary new module logic (as long as it satisfies structural compatibility checks) to an address that users/integrators already trust and interact with, i.e., unauthorized code replacement on a live, trusted address. This is high impact: it is a direct authority-hijack of a protected publish/upgrade capability, reachable without any privileged access besides tricking/misusing a routine, permissionless `object::transfer` call.

### Likelihood Explanation
Likelihood is moderate: it requires the current code-object owner to execute a transfer of that specific object address, which normal wallet UIs are unlikely to prompt for by accident, but the primitive itself (`object::transfer_call`) is fully generic, permissionless, and works uniformly across every object type on Aptos, including code objects. A malicious dApp, a phishing transaction, or a developer's own scripting mistake (e.g., accidentally reusing an address in a batch "transfer NFTs to new wallet" operation) is sufficient to trigger it, and there is no code-level safeguard (no `disable_ungated_transfer`, no type check, no extra confirmation flag) anywhere in `object_code_deployment.move` to prevent or even flag it.

### Recommendation
In `object_code_deployment::publish` (and any other place that creates a code object), generate a `TransferRef` from the `ConstructorRef` and immediately call `object::disable_ungated_transfer` (or `object::set_untransferable`) on the code object before returning, so that ownership of deployed code can never be changed via the generic transfer entry functions. If transfer of code ownership is intentionally desired as a feature (e.g., to support code hand-off), it should be implemented as an explicit, code-object-aware function (e.g., `object_code_deployment::transfer_ownership`) that is clearly distinct from the generic NFT-style `object::transfer`, ideally requiring an explicit two-step accept/claim flow rather than a single unilateral transfer.

### Proof of Concept
1. Account A calls `object_code_deployment::publish(A, metadata, code)` to deploy a package. This creates a named object `O` at `create_object_address(A, seed)` with `ObjectCore.owner = A` and `allow_ungated_transfer = true` (default from `create_named_object`) [4](#0-3) [1](#0-0) .
2. Account A is induced (e.g., by a malicious dApp presenting a payload disguised as an NFT/asset transfer) to sign and submit `0x1::object::transfer_call(A, O, B)` (or the typed `object::transfer<PackageRegistry>`), which succeeds because `allow_ungated_transfer` is `true` and no additional check exists for code objects [8](#0-7) .
3. `ObjectCore.owner` for `O` is now `B`.
4. Account B calls `object_code_deployment::upgrade(B, new_metadata, new_code, O)`. The check `object::is_owner(O, B)` now passes [10](#0-9) , so B successfully replaces the module bytecode at the trusted address `O` (as long as compatibility rules for the declared `compat` policy are satisfied), or alternatively calls `freeze_code_object(B, O)` to permanently lock A out of ever upgrading their own deployed code again [11](#0-10) .

Note: I was not able to execute an actual on-chain/e2e test to confirm end-to-end runtime behavior (e.g., whether any additional framework-level guard outside the files reviewed blocks this), since I only have read access to the indexed source. The e2e tests in `object_code_deployment.rs` cover deploy/upgrade/freeze authorization by direct owner mismatch [12](#0-11) [13](#0-12)  but none test the scenario of the code object being transferred via `object::transfer`/`transfer_call` and then upgraded/frozen by the new owner, which would independently confirm this exact path.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    public entry fun upgrade(
        publisher: &signer,
        metadata_serialized: vector<u8>,
        code: vector<vector<u8>>,
        code_object: Object<PackageRegistry>,
    ) {
        let publisher_address = signer::address_of(publisher);
        assert!(
            object::is_owner(code_object, publisher_address),
            error::permission_denied(ENOT_CODE_OBJECT_OWNER),
        );

        let code_object_address = code_object.object_address();
        assert!(exists<ManagingRefs>(code_object_address), error::not_found(ECODE_OBJECT_DOES_NOT_EXIST));

        let extend_ref = &borrow_global<ManagingRefs>(code_object_address).extend_ref;
        let code_signer = &extend_ref.generate_signer_for_extending();
        code::publish_package_txn(code_signer, metadata_serialized, code);

        event::emit(Upgrade { object_address: signer::address_of(code_signer), });
    }
