### Title
Unprivileged griefing eviction of a victim app's paid bandwidth subscriptions via unrestricted cross-chain sponsorship - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` credits `(app_chain, app)` byte allowances from a `PurchaseMessage` whose `chain`/`app` fields are taken from the message body rather than being bound to `request.source`/the caller. This is the documented "sponsorship" feature, but it also means *any* unprivileged account that can call `purchase()` on *any* registered `BandwidthManager` can direct credits at an arbitrary victim `(app_chain, app)` pair. Combined with the hard 1024-entry FIFO cap and its eviction rule (oldest entry dropped, "lost bytes" burned), an attacker can force-fill a victim's subscription queue with a stream of cheap purchases to evict the victim's existing, already-paid-for subscriptions — permanently destroying bandwidth the victim legitimately purchased. This is structurally the same broken invariant as the Morpho report: an unprivileged actor performs ordinary, permitted operations (repeated small "supplies") against a shared accumulator (the FIFO subscription list) to force a bad, unrecoverable outcome (lost allowance / worse rate) onto unrelated legitimate participants who never opted into being affected by that actor's actions.

### Finding Description
`Pallet::on_accept` in `modules/pallets/bandwidth/src/lib.rs` handles inbound purchase messages: [1](#0-0) 

It only checks that `request.from` matches the registered `BandwidthManager` for `request.source` — it never checks that the payer/source chain has any relationship to the `msg.chain`/`msg.app` being credited. The docs confirm this is deliberate "sponsorship": *"The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`"* — i.e. anyone paying on any registered source chain can target any `(app_chain, app)` pair.

`push_subscription` enforces the 1024-cap by evicting the oldest live entry and emitting `SubscriptionEvicted` with the lost bytes: [2](#0-1) 

`MAX_SUBSCRIPTIONS` is a fixed constant (1024) shared by every `(chain, app)` bucket: [3](#0-2) 

`BandwidthCredited`/`push_subscription` never checks who the caller is relative to the app being credited, nor rate-limits how many subscriptions a single unrelated payer may append to another app's queue in a short window. There is no per-payer / per-purchase-size floor tying a new entry's "cost to evict" to the value of what it evicts — an attacker paying the cheapest tier (TierOne) many times can push the victim's queue past 1024 entries and start evicting the victim's larger/earlier tiers.

This mirrors the Morpho bug-class: a shared, order-sensitive accumulator (delta / FIFO queue) that is mutated by unprivileged public entry points, where an attacker's sequence of ordinary operations against *someone else's* bucket forces a worse, permanent outcome (borrower delta / evicted bandwidth) onto legitimate users who did nothing wrong.

### Impact Explanation
This is a real loss-of-funds/loss-of-value vector under the bounty's "stealing or loss of funds" / "transaction manipulation" categories: a victim app that has already paid (in ERC-20/native fee tokens on the EVM `BandwidthManager`) for bandwidth can have its unconsumed, unexpired subscriptions silently evicted and permanently lost (`SubscriptionEvicted { lost_bytes }`) by an unrelated, unprivileged third party who never needed the victim's cooperation, a compromised relayer, or governance access. The attack requires no malicious peer, prover, or admin — only a normal `purchase()` call repeated enough times, which is exactly the "public-entrypoint... unprivileged attacker" primitive the task requires.

### Likelihood Explanation
Feasibility is bounded by cost: each evicting purchase must be paid for on the EVM side to the registered `BandwidthManager`, so the attacker needs to fund `1024 − existing_entries` cheap purchases before eviction of the victim's real entries begins. This makes the attack a paid griefing campaign rather than a free/flash exploit — it is not as cheap as the Morpho single-transaction flash supply/withdraw, but it is still an unprivileged, permissionless, purely on-chain path to destroy another party's paid-for state with no protocol safeguard (no per-payer cap, no minimum-tier-to-evict rule, no `app`-ownership check on which `(chain, app)` a purchase may target). Any well-funded competitor or bad actor targeting a specific app with a known bandwidth budget could execute this deterministically.

### Recommendation
- Bind sponsorship more tightly: either require `request.source == msg.chain` by default and gate cross-chain sponsorship behind an explicit allow-list/opt-in from the target app, or require the purchaser to prove some relationship to the app being credited.
- Change the eviction policy so a smaller/cheaper subscription cannot evict a larger/more-valuable one purchased earlier — e.g. evict by remaining-value or refuse insertion (reject the purchase, refund) rather than silently destroying the oldest entry when it is more valuable than the one being inserted.
- Rate-limit or fee-scale purchases targeting an `(app_chain, app)` bucket per unique payer within a time window to prevent cheap flood-and-evict campaigns.

### Proof of Concept
1. Victim app `V` on chain `C_v` has, e.g., 10 live `TierFour` subscriptions credited via legitimate purchases (`Allowance::<T>::get(C_v, V)` has 10 entries).
2. Attacker deploys/holds funds on any chain `S` with a registered `BandwidthManager` (`BandwidthManager::<T>::get(S)` is `Some`).
3. Attacker calls `BandwidthManager.purchase({ app: V, tier: TierOne, months: 1, chain: C_v })` 1024 − 10 = 1014 times, each dispatching a `PurchaseMessage` with `msg.chain = C_v`, `msg.app = V`.
4. Each message passes `on_accept`'s only check (`request.from == registered manager on S`) — nothing ties `msg.chain`/`msg.app` to `S` or to the attacker's identity.
5. `push_subscription` appends 1014 cheap `TierOne` entries to `Allowance::<T>::get(C_v, V)`, filling the list to 1024.
6. Attacker submits one more `TierOne` purchase targeting `(C_v, V)`. `push_subscription` evicts the oldest entry — one of V's original `TierFour` subscriptions — emitting `SubscriptionEvicted { lost_bytes: <TierFour bytes> }`.
7. Repeating the last purchase 10 more times evicts all 10 of V's legitimately paid `TierFour` subscriptions, permanently destroying that bandwidth while V's queue is now dominated by attacker-inserted cheap `TierOne` entries that themselves quickly drain/expire — net effect: V loses paid-for bandwidth it never consumed, imposed entirely by an unprivileged third party.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
