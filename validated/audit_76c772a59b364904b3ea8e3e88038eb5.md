### Title
`is_deposit_valid` accepts a `ReplacementDeposit` whose `old_move_txid` never corresponds to a real prior vault spent by the security council - (File: core/src/verifier.rs, core/src/deposit.rs)

### Summary
`Verifier::is_deposit_valid` in `core/src/verifier.rs` and the deposit-script builder in `core/src/deposit.rs::get_deposit_scripts` only verify that a `ReplacementDeposit`'s claimed `old_move_txid` is baked into the funding output's scriptPubKey and that the amount/height/security-council/actors are correct. Neither function, nor any other reachable code path in this repo, checks that `old_move_txid` actually names a `move_to_vault` transaction that was previously created, funded, and spent via the `Multisig::from_security_council` script path.

### Finding Description
The invariant that should hold is: `ReplacementDepositData.old_move_txid == txid(move_to_vault_tx)` for some move tx that genuinely existed and was spent by `Multisig::from_security_council` (i.e. a real replacement of value the bridge already held).

Tracing the code:
- `DepositData::get_deposit_scripts` for `DepositType::ReplacementDeposit` builds two leaf scripts: `ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid)` and `Multisig::from_security_council(...)` [1](#0-0) . This is purely a scriptPubKey-derivation function — `old_move_txid` is treated as opaque data pushed into the script, with no lookup against chain history [2](#0-1) .
- `Verifier::is_deposit_valid` recomputes the expected scriptPubKey from `deposit_data.get_deposit_scripts(...)` and compares it against the on-chain output at `deposit_outpoint`, and checks the output amount equals `bridge_amount` and the block height is above `start_height` [3](#0-2) . Nowhere in this function is `old_move_txid` looked up on-chain, checked against the verifier's DB of processed deposits, or checked against `get_replacement_deposit_move_txids` from the Citrea client [4](#0-3) .
- `check_nofn_correctness`, called alongside `is_deposit_valid` in `deposit_sign`/`deposit_finalize`/`set_operator_keys`, only checks that the deposit's aggregated nofn key matches Citrea's contract key — it says nothing about `old_move_txid` [5](#0-4) .
- The attacker's exploit: fund any UTXO with `bridge_amount` sats to `Address = taproot([ReplacementDepositScript(nofn_pk, random_txid), Multisig::from_security_council])`, exactly as `generate_replacement_deposit_address` builds it [6](#0-5) . Submit `DepositParams` with `DepositType::ReplacementDeposit{old_move_txid: random_txid}` to the aggregator's `new_deposit` RPC [7](#0-6) . Every verifier's `is_deposit_valid` check passes because the depositor constructed the funding output to exactly match the script/amount/height expectations that are self-referential to the attacker's own claims — there is no cross-check that `random_txid` was ever a real move tx.

The comment in `deposit.rs` even documents the intended invariant that is not enforced: "These kinds of deposits are created by the bridge, using security council to unlock the previous deposit and move the funds to create a new deposit" [8](#0-7) .

However, verifying real economic impact requires tracing what happens **after** verifiers N-of-N presign this move tx. In this repo, clementine's own state only tracks the deposit as a normal deposit once signed — the deposit_data uniqueness constraint (`insert_deposit_data_if_not_exists`) prevents double-signing the same `deposit_outpoint`, but does not prevent a *new*, self-funded `deposit_outpoint` claiming to replace a fabricated `old_move_txid`. The actual "replacement" semantics that matter for bridge accounting (associating `old_move_txid`'s Citrea-side deposit index with the new move tx, so that future withdrawals/payouts route against the *correct* deposit index) are enforced entirely on the **Citrea Bridge Contract side** via `DepositReplaced` events and `get_replacement_deposit_move_txids`, which are read by clementine but whose validation logic lives in the out-of-scope Citrea contract [9](#0-8) .

### Impact Explanation
Within this repo, the concrete effect of this gap is that Clementine's verifiers will happily produce a fully-valid N-of-N pre-signed move-to-vault transaction for a "replacement" deposit whose claimed prior vault never existed. This is real proof of an unauthenticated logic gap in `is_deposit_valid`/`get_deposit_scripts`: an attacker can obtain N-of-N signatures over a vault UTXO tagged as "replacing" an arbitrary txid. That said, whether this results in "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" or a "false claim proved" as defined in the impact rubric depends on what the Citrea contract does with a `ReplacementDeposit` movetx whose `old_move_txid` it never recorded as replaced (i.e., whether the Citrea side independently validates that `old_move_txid` corresponds to a real deposit index before crediting cBTC or unlocking withdrawal accounting for it). That contract-side validation is out of scope for this repository per the rules ("third-party crate, Citrea contract... defects with no path through this repository"), and I could not locate Citrea contract source in this repo to confirm whether it independently rejects an unregistered `old_move_txid`. Since the deposit is self-funded by the attacker (same `bridge_amount` sats they paid in), and no additional bridged value is misappropriated purely by this Clementine-side gap without a corresponding Citrea-side crediting bug, I cannot confirm the "direct theft of bridged BTC/cBTC" impact is fully reachable through this repository alone.

### Likelihood Explanation
The precondition — funding a bitcoin output to a fully attacker-computable taproot address and submitting a `DepositParams` payload — requires only ordinary unprivileged access (Bitcoin RPC + aggregator gRPC), matching the stated attacker model. The missing cross-check in `is_deposit_valid` is deterministic and always reachable; no race condition or privileged data is needed.

### Recommendation
In `Verifier::is_deposit_valid` (`core/src/verifier.rs`), when `deposit_data.deposit.deposit_type` is `ReplacementDeposit`, add a check that `old_move_txid` corresponds to a `move_to_vault` transaction that the verifier's own DB (or the Citrea light-client-verified deposit index, via `get_replacement_deposit_move_txids`) recognizes as an existing, previously-signed deposit, and that it has genuinely been spent via the `Multisig::from_security_council` script path (i.e., verify the actual spending transaction's witness/script-path against the recorded old move tx's taproot leaves) before signing.

### Proof of Concept
Given the repo's out-of-scope boundary around the Citrea contract, a fully self-contained `cargo test` that demonstrates value leaving a move-to-vault UTXO without a matching fronted withdrawal cannot be constructed purely with mocked Citrea (`MockCitreaClient::get_replacement_deposit_move_txids` always returns an empty vec, per `core/src/test/common/citrea/client_mock.rs:212-218`, so it performs no validation either way, masking rather than confirming the invariant). The concrete, reproducible assertion that IS provable in-repo:

/// Struct for deposit script that replaces an old move tx with a replacement deposit (to update bridge design on chain)
/// It commits to the old move txid inside the script.
#[derive(Debug, Clone)]
pub struct ReplacementDepositScript(pub(crate) XOnlyPublicKey, Txid);

impl SpendableScript for ReplacementDepositScript {
    fn as_any(&self) -> &dyn Any {
        self
    }

    fn kind(&self) -> ScriptKind {
        ScriptKind::ReplacementDepositScript(self)
    }

    fn to_script_buf(&self) -> ScriptBuf {
        let citrea_replace: [u8; 13] = "citreaReplace".as_bytes().try_into().expect("length == 13");

        Builder::new()
            .push_x_only_key(&self.0)
            .push_opcode(OP_CHECKSIG)
            .push_opcode(OP_FALSE)
            .push_opcode(OP_IF)
            .push_slice(citrea_replace)
            .push_slice(self.1.as_byte_array())
            .push_opcode(OP_ENDIF)
            .into_script()
    }
}

    async fn get_replacement_deposit_move_txids(
        &self,
        from_height: u64,
        to_height: u64,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let mut replacement_move_txids = vec![];

        // get logs
        let filter = self.contract.event_filter::<DepositReplaced>().filter;
        let logs = self.get_logs(filter, from_height, to_height).await?;

        for log in logs {
            let replacement_raw_data = &log.data().data;

            let idx = DepositReplaced::abi_decode_data(replacement_raw_data, false)
                .wrap_err("Failed to decode replacement deposit data")?
                .0;
            let new_move_txid = DepositReplaced::abi_decode_data(replacement_raw_data, false)
                .wrap_err("Failed to decode replacement deposit data")?
                .2;

            let idx = u32::try_from(idx).wrap_err("Failed to convert idx to u32")?;
            let new_move_txid = Txid::from_slice(new_move_txid.as_ref())
                .wrap_err("Failed to convert new move txid to Txid")?;

            replacement_move_txids.push((idx, new_move_txid));
        }

        Ok(replacement_move_txids)
    }
