Confirmed: `IsRewardEligible()` in `kaiax/valset/types.go` returns true for `ValActive` state regardless of the `Suspended` flag, and `parsePermissionlessCallResult` in `kaiax/staking/impl/getter.go` filters staking-eligible nodes solely by `valset.NodeState(p.State).IsRewardEligible()`, with no check of the `Suspended` field.

### Title
Suspended validators are excluded from consensus committee but still receive block/staking rewards - ([File: kaiax/valset/types.go], [File: kaiax/staking/impl/getter.go])

### Summary
The `Suspended` flag on a validator (managed via `AddressBookV2`'s suspender role, see `SuspendValidator`/`UnsuspendValidator` in `contracts/bindings/addressbookv2/AddressBookV2.go`) is only enforced when computing the consensus `Committee()`, but is ignored everywhere else that determines reward eligibility, mirroring the reported bug class where a "suspended" actor is blocked from only one action (here: block signing/proposing) but not others (here: earning block rewards).

### Finding Description
`NodeMap.Committee()` explicitly excludes suspended nodes: `v.FilterByState(ValActive).ExcludeSuspended()` [1](#0-0) . However, `NodeState.IsRewardEligible()` only checks `s == ValActive` and has no knowledge of the `Suspended` flag at all [2](#0-1) .

This `IsRewardEligible()` predicate is used directly by the permissionless staking-info parser to decide which validator node IDs/reward addresses/staking amounts are included in `StakingInfo` (which subsequently drives reward distribution): `if !valset.NodeState(p.State).IsRewardEligible() { continue }` [3](#0-2) . Since this check is purely state-based and does not consult any per-node `Suspended` flag from AddressBookV2, a validator that has been suspended by the on-chain suspender role while remaining in state `ValActive` is still included as reward-eligible.

Separately, `Council()` (used to compute the full validator set, e.g. via `GetCouncil`, and consumed in `consensus/istanbul/core/core.go`'s `getRoundCommitteeState` for computing `qualified` validators) also does not exclude suspended nodes — only `Committee()` does [4](#0-3) . The demoted/qualified calculation therefore treats a suspended `ValActive` node as still "qualified" (only `Committee()` excludes it), consistent with the test `TestApplyViolationTransition_SuspendedNotExempt`'s comment that "Suspended is informational, not a violation exemption" [5](#0-4) , and with `getQualifiedValidators` which is documented as `qualified = committee = {VA} − {Suspended}` only in the permissionless getter path, not in the general reward/staking eligibility path [6](#0-5) .

### Impact Explanation
This results in reward redirection: an admin (suspender) intending to fully penalize/ban a malicious or compromised validator by suspending it can prevent that validator from participating in consensus signing/proposing, but cannot prevent it from continuing to receive minted block rewards and staking rewards distributed via `StakingInfo`/`FinalizeState` in `kaiax/reward/impl/blockstate.go`. This is a concrete unauthorized value movement / reward-redirection bug: value (KAIA rewards) continues to flow to an address the governance/suspender explicitly intended to cut off from core validator privileges.

### Likelihood Explanation
Likelihood is high given normal operational use: any time the suspender role suspends a `ValActive` validator (a supported, intended admin action per the `valops suspend-validator` CLI command in `cmd/kcn/abv2.go`), the inconsistency is triggered automatically on the very next reward computation, with no additional attacker action required.

### Recommendation
Make `IsRewardEligible()` (or its callers) aware of the `Suspended` flag, e.g., have `parsePermissionlessCallResult` and any other reward/staking-eligibility computation consult the same `ExcludeSuspended()`/`Suspended` semantics used by `Committee()`, so that suspension consistently removes a validator from both consensus participation and reward eligibility.

### Proof of Concept
1. Suspender calls `SuspendValidator` on `AddressBookV2` for a `ValActive` node (via `valops suspend-validator` CLI, `cmd/kcn/abv2.go:89-93`).
2. `valset` module correctly excludes the node from `Committee()` (`kaiax/valset/types.go:263-265`), so it cannot sign/propose blocks.
3. At `GetStakingInfo`/`parsePermissionlessCallResult` time, the node's `p.State` is still `ValActive`, so `IsRewardEligible()` returns `true` and the node's `NodeIds`/`RewardAddrs`/`StakingAmounts` are included in `StakingInfo` (`kaiax/staking/impl/getter.go:200-209`).
4. `RewardModule.FinalizeState` distributes staking/minting rewards based on this `StakingInfo`, crediting the suspended validator's reward/staking address despite it being suspended (`kaiax/reward/impl/blockstate.go:30-56`).
