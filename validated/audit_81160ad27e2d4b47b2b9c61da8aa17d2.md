## Analysis

This maps to the same invariant class as the reported bug: **a compound accounting operation that debits the user before performing the compensating credit, where an error on the second step is silently discarded, causing the debit to be permanently committed while the credit never happens.**

### Title
Silently swallowed conversion error commits partial escrow, permanently trapping user funds during IBC refund auto-conversion - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertCoinNativeERC20` performs a two-step, non-atomic operation: it first escrows the user's bank coins into the `erc20` module account, then attempts to unescrow/transfer the equivalent ERC20 tokens to the receiver via an EVM call. If the EVM call fails, the function returns an error but the already-executed escrow is not rolled back. This function is invoked from `ConvertCoinToERC20FromPacket`, which is called from `OnAcknowledgementPacket` (on error-ack) and `OnTimeoutPacket` to auto-convert refunded IBC coins back to ERC20. Critically, that caller **swallows the error** and returns `nil`, so the surrounding Cosmos SDK message execution (`MsgTimeout`/`MsgAcknowledgement`) is treated as fully successful and its cache-context — including the partial escrow — is committed.

### Finding Description [1](#0-0) 
`ConvertCoinNativeERC20` escrows coins from the sender to `types.ModuleName` first: [2](#0-1) 
then attempts to unescrow ERC20 tokens via `CallEVM`. If that call errors, the function `return err`s immediately with no compensating refund of the coins just escrowed: [3](#0-2) 

The caller path that invokes this during IBC refund handling explicitly discards the error: [4](#0-3) 

Both `OnAcknowledgementPacket` (error-ack case) and `OnTimeoutPacket` route through `ConvertCoinToERC20FromPacket`: [5](#0-4) 

Because the middleware always returns `nil` here regardless of the inner conversion outcome, the enclosing Cosmos SDK `Msg` handler (processing `MsgTimeout`/`MsgAcknowledgement`) reports success, so baseapp commits its cache-context multistore — which already contains the completed `SendCoinsFromAccountToModule` escrow — even though the paired unescrow/transfer to the receiver never happened.

This is the direct structural analog of the H-01 report: a value-moving operation is split into a "take" step and a "give-back/complete" step; when a flag/condition (`_dontMint` there, an EVM call failure here) causes early return before the second step, and the framework doesn't distinguish "partial success" from "total failure," the user's funds are extracted without the corresponding credit ever landing.

### Impact Explanation
The escrowed coins become permanently stuck in the `erc20` module account: they are never released back to the sender (no refund/rollback logic exists) and never converted to the ERC20 representation (the EVM call already failed, and there is no automatic retry mechanism). This is a direct, unauthorized, and irreversible loss of user funds for any account performing outbound IBC transfers of native-ERC20-backed token pairs (`pair.IsNativeERC20()`) whose transfer times out or is rejected by the counterparty chain, whenever the ERC20 contract-side transfer to the receiver fails at that specific moment (e.g., contract paused, blacklist logic reverting, self-destructed contract, or any deterministic revert condition in the ERC20 contract logic). This matches the "permanent freezing, locking, theft, or unauthorized extraction of user funds ... token-pair-backed balances" Critical impact criterion.

### Likelihood Explanation
Triggering requires only ordinary, unprivileged actions: initiate an outbound IBC transfer of a native ERC20 token pair, then have the packet time out or receive an error acknowledgement (both are ordinary, non-privileged network conditions, not requiring a malicious relayer — a slow/offline counterparty naturally produces a timeout). The only additional requirement is that the ERC20 contract's `transfer` call revert at the refund-conversion step, which is plausible for many real-world ERC20 tokens (pausable tokens, blacklists, contracts later self-destructed/upgraded) — this is explicitly acknowledged as an expected failure mode by the code's own comments ("such as an attempt to call a self-destructed ERC20 contract or an invalid function").

### Recommendation
Make `ConvertCoinNativeERC20` atomic with respect to its own escrow step: use a branched/cached context (`ctx.CacheContext()`) for the escrow + EVM-unescrow sequence, and only write it back to the parent context if both steps succeed; otherwise discard the cache so the escrow never persists. Alternatively, in `ConvertCoinToERC20FromPacket`, on conversion failure, explicitly refund the escrowed coins back to the sender from the module account before returning `nil`. Do not allow a caller to swallow an error from a function that already mutated persistent state without also reverting or compensating that mutation.

### Proof of Concept
1. Register a native ERC20 token pair (`pair.IsNativeERC20() == true`) for an ERC20 contract that can be made to revert on `transfer` (e.g., a pausable/blacklistable mock ERC20, or deploy behind a proxy and self-destruct/upgrade it later).
2. User holds the corresponding bank coin `pair.Denom` and sends an ICS20 `MsgTransfer` out to another chain.
3. Force the packet to time out (or have the counterparty return an error acknowledgement).
4. On timeout/error-ack processing, IBC's transfer module refunds the bank coin to the sender, then `x/erc20` middleware's `OnTimeoutPacket`/`OnAcknowledgementPacket` calls `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`.
5. Before this refund packet is processed, pause/blacklist/break the ERC20 contract so the internal `CallEVM(... "transfer" ...)` reverts.
6. `ConvertCoinNativeERC20` returns an error after already executing `SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins)`.
7. `ConvertCoinToERC20FromPacket` catches the error, emits `types.EventTypeFailedConvertERC20`, and returns `nil`.
8. The `MsgTimeout`/`MsgAcknowledgement` handler succeeds; baseapp commits the multistore including the escrow.
9. Verify: sender's bank balance of `pair.Denom` is now missing the refunded amount, the module account (`erc20`) holds it, and the sender's ERC20 balance was never credited — funds are permanently stuck with no user-facing recovery path.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}
