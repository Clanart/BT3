### Title
Unbounded-length offer string parsing in `Offer.from_bech32` enables wallet-side DoS via oversized bech32m input — (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.from_bech32()` intentionally disables the bech32 length safety cap (`max_length=90`) that protects every other bech32-consuming code path in the wallet (addresses, puzzle hashes). It passes `max_length=len(offer_bech32)`, i.e. no bound at all, so an untrusted offer string of arbitrary size is fully decoded — including an O(n) checksum computation over the whole payload — before any semantic validation of the offer occurs. This mirrors the reported gnark issue: attacker-controlled numeric/encoded input is parsed with unbounded cost at a trust boundary before cheap sanity checks can reject it.

### Finding Description
`bech32_decode()` in `chia/util/bech32m.py` L73-88 accepts a `max_length` parameter defaulting to 90 (the BIP-173/350 standard bound), and is used with that safe default everywhere addresses are decoded, e.g. `AddressParamType.convert()` (`chia/cmds/param_types.py` L168-201) and `decode_puzzle_hash()`/`ensure_valid_address()` (`chia/wallet/util/address_type.py` L27-55).

However, `Offer.from_bech32()` explicitly overrides this bound: [1](#0-0) 

```python
@classmethod
def from_bech32(cls, offer_bech32: str) -> Offer:
    _hrpgot, data = bech32_decode(offer_bech32, max_length=len(offer_bech32))
    ...
```

By passing `max_length=len(offer_bech32)`, the length check inside `bech32_decode` (`if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length: return (None, None)`, `chia/util/bech32m.py` L80) is a no-op — it can never reject any string based on size. The function then:
1. Iterates the entire string doing per-character `ord()` checks (`chia/util/bech32m.py` L76).
2. Runs `CHARSET.find(x)` for every remaining character (`chia/util/bech32m.py` L85), an O(32) scan each.
3. Computes `bech32_verify_checksum` via `bech32_polymod`, which loops over the *entire* decoded value list (`chia/util/bech32m.py` L37-46).

All of this work is proportional to the raw string length and happens before `convertbits`, `try_offer_decompression`, or any consensus-level validation. The offer string is reachable from an unprivileged local RPC caller / wallet user handling an untrusted offer file or bech32 blob supplied by an offer counterparty, via `TakeOffer.parsed_offer` (`Offer.from_bech32(self.offer)`, `chia/wallet/wallet_request_types.py` L2304-2312) consumed by `WalletRpcApi.take_offer()` (`chia/wallet/wallet_rpc_api.py` L2050-2065), and via `check_offer_validity` (`chia/wallet/wallet_rpc_api.py` L2042-2048), both of which call `Offer.from_bech32(request.offer)` directly on attacker-supplied strings before any size gate. ### Impact Explanation
A malicious offer counterparty (or anyone providing an "offer" string/file to a wallet user) can craft an extremely long bech32m-looking payload and hand it to the victim's wallet via `take_offer`/`check_offer_validity` RPC or the equivalent CLI command. Because the length guard is disabled, the entire string is scanned and checksum-verified with cost linear (or worse, due to `CHARSET.find`) in the input length before the code ever reaches the puzzle-decompression/validation stage that has documented output caps. This can consume significant CPU/memory on the wallet process for a single crafted "offer," degrading wallet responsiveness/availability — a resource-exhaustion condition triggered by a single untrusted spend-adjacent artifact, consistent with a Medium-severity availability issue.

### Likelihood Explanation
High reachability: any wallet user who opens/accepts an offer file from an untrusted counterparty, or any local RPC caller who submits a string to `take_offer`/`check_offer_validity`, triggers this path with no authentication beyond normal wallet RPC access. No proof, signature, or protocol negotiation is required before the expensive parsing occurs — only a syntactically bech32-charset string is needed to reach the checksum loop.

### Recommendation
Do not bypass the standard bech32 `max_length` bound for offers. Apply a fixed, generous but bounded `max_length` (sized to the largest legitimate compressed/encoded offer) in `Offer.from_bech32`, and reject/short-circuit early (e.g., check `len(offer_bech32)` against the bound before invoking `bech32_decode`) so oversized inputs fail fast without incurring per-character and checksum costs proportional to attacker-chosen size.

### Proof of Concept
1. Construct a string of the form `"offer1" + ("q" * N)` for a very large `N` (e.g., tens of millions of characters) — it need not be a valid checksum, since checksum verification itself is the expensive step reached only after the length check, which is disabled.
2. Submit it as `request.offer` to the wallet RPC `check_offer_validity` or `take_offer` endpoint, or pass it as `path_or_hex` to the `take_offer` CLI command, which calls `Offer.from_bech32`.
3. Observe `bech32_decode(offer_bech32, max_length=len(offer_bech32))` process the full string — no early rejection occurs regardless of size, unlike address decoding paths that use the default `max_length=90` and reject any input longer than 90 characters immediately.

```python
def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
    bech = bech.lower()
    pos = bech.rfind("1")
    if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length:
        return (None, None)
    if not all(x in CHARSET for x in bech[pos + 1 :]):
        return (None, None)
    hrp = bech[:pos]
    data = [CHARSET.find(x) for x in bech[pos + 1 :]]
    if not bech32_verify_checksum(hrp, data):
        return (None, None)
    return hrp, data[:-6]
```
