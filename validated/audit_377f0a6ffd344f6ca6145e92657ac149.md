### Title
Rebasing tokens registered for gasless swaps desynchronize UniswapV2Pair reserves, enabling unprivileged `skim()` theft of unaccounted balance - ([File: kaiax/gasless/impl/tx_pool.go], [File: contracts/bindings/uniswap/factory/UniswapV2Factory.go])

### Summary
Kaia's gasless module (KIP-247) lets any unprivileged token holder swap an ERC20 token for gas via `GaslessSwapRouter.swapForGas`, pricing the swap against a standard UniswapV2Pair's cached `reserve0`/`reserve1` state. [1](#0-0)  If the registered swap token is a rebasing token, its actual `balanceOf(pair)` can drift above (or below) the pair's tracked reserves, exactly the underlying root cause described in the external report for Allo's `_fundPool`, where a token's real balance diverges from the protocol's tracked accounting. In the UniswapV2Pair used here, that untracked surplus is not lost to a permissioned pool operator — it is directly stealable by any unprivileged caller through the pair's public, permissionless `skim(address)` function. [2](#0-1) 

### Finding Description
The gasless module allows admin-added ERC20 tokens (via `GaslessSwapRouter.addToken`) to be swapped through UniswapV2Factory/Router02/Pair contracts. [3](#0-2)  The tx-pool-level check (`checkBalanceForSwap`) validates `amountIn` against `GetAmountIn`, which is computed from the pair's `getReserves()` — a cached snapshot (`reserve0`, `reserve1`) rather than the live `balanceOf` of the pair contract. [4](#0-3) 

The UniswapV2Pair contract's reserves are only ever brought back in sync with actual token balances via `sync()`, and any balance held by the pair in excess of tracked reserves can be withdrawn to an arbitrary address by calling the standard, permissionless `skim(address)` function. [5](#0-4)  If the token added to a gasless-swap-enabled pool is a rebasing token, a positive rebase increases the pair's `balanceOf` without the reserves being updated, creating exactly the same class of unaccounted-surplus condition flagged in the original report (`Allo._fundPool`/`increasePoolAmount` not tracking real balance changes). Unlike the Allo case where funds are merely "stuck," here the divergence is actively exploitable: any unprivileged caller can invoke `skim()` on the pair to redirect the un-tracked rebased tokens to themselves, at the expense of liquidity providers who funded the pool that the gasless swap flow depends on.

### Impact Explanation
This allows any transaction sender (no special privilege required) to extract value that rightfully belongs to liquidity providers of a pool used to back gasless transactions, constituting unauthorized value movement out of a DeFi pool integrated into a core Kaia protocol module (KIP-247 gasless). Because the gasless flow's pricing (`getAmountIn`/`getAmountOut`) also relies on these reserves, a manipulated/rebased reserve-vs-balance gap could additionally skew the gas-lending economics for the block proposer who fronts gas for `GaslessApproveTx`/`GaslessSwapTx`.

### Likelihood Explanation
Exploitation requires only that a rebasing token be registered as a gasless-swap-supported token (an admin action via `GaslessSwapRouter.addToken`) and a subsequent rebase event; after that, any public caller can call the permissionless `skim()` function on the pair — no privileged role, validator collusion, or consensus-level access is needed, only a standard transaction.

### Recommendation
- Disallow or explicitly vet rebasing/fee-on-transfer tokens from being added via `GaslessSwapRouter.addToken`.
- Track actual balances (not just cached reserves) when computing swap amounts, or force a `sync()` call as part of the gasless swap execution flow so that any positive/negative rebase is absorbed into reserves rather than being skimmable by an outside caller.
- Consider restricting or removing pool-level `skim()` reachability for tokens used in the gasless swap pools, or require an allowlist review process that excludes non-standard ERC20 tokens.

### Proof of Concept
1. Admin registers a rebasing ERC20 token `T` via `GaslessSwapRouter.addToken(T, factory, router)`, and a `T`/WKAIA UniswapV2Pair is created and seeded with liquidity as in `setupLiquidity`. [6](#0-5) 
2. Token `T` undergoes a positive rebase, increasing `T.balanceOf(pairAddress)` without any `mint`/`transfer` call to the pair (rebase mechanics update balances directly).
3. The pair's `getReserves()` still reports the pre-rebase `reserve0`/`reserve1`. [7](#0-6) 
4. Any unprivileged account calls `pair.skim(attacker)`, which transfers `balanceOf(pair) - reserve` of both tokens to `attacker`, capturing the rebase surplus that should have accrued to LPs. [8](#0-7) 
5. Gasless swaps continuing to use `getAmountIn`/`getAmountOut` against the pair's reserves are unaffected in correctness terms, but the value siphoned via `skim()` is a direct, unauthorized transfer of pool assets funding the gasless ecosystem.

	Reserve1           *big.Int
	BlockTimestampLast uint32

) {

}
