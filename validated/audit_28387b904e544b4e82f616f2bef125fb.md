## Analog Found

### Title
Threshold Bypass in `MofN` Custody Puzzle via Unenforced Merkle Leaf Uniqueness - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
The custody architecture's `MofN` construct (Chia's on-chain M-of-N multisig/threshold puzzle, `MofN_MOD`/`OneOfN_MOD`) relies entirely on off-chain, client-side Python validation to guarantee that every leaf (member puzzle hash) in its Merkle tree is unique. The on-chain CLVM puzzle only receives and trusts a curried Merkle root plus a caller-supplied proof structure; it never independently verifies that the tree the root was derived from contains distinct leaves. This mirrors the external report's core concern about off-chain Merkle tree construction correctness not being enforced on-chain.

### Finding Description
`MofN.__post_init__` is the only place that checks for duplicate leaves before a tree is built: [1](#0-0) 

This check happens purely in the Python wallet driver. The actual on-chain puzzle is produced by currying `MofN_MOD` or `OneOfN_MOD` directly with a Merkle root: [2](#0-1) 

Nothing in the CLVM puzzle itself (which only receives a `root` argument via curry) can recompute or validate that the underlying set of leaves used to produce that root was free of duplicates — that invariant exists solely in the `MofN` dataclass, which is bypassable by anyone constructing the puzzle reveal directly (e.g., a malicious co-signer during vault setup, or any tool that curries `MofN_MOD`/`OneOfN_MOD` without going through the `MofN` class).

The multi-proof generation logic in `MofNMerkleTree._m_of_n_proof` walks the leaf list and, for any leaf hash present in `spends_to_prove`, reveals the same `(puzzle_reveal, solution)` pair at that leaf's position: [3](#0-2) 

If a Merkle tree is constructed (bypassing the dataclass guard) with the same member puzzle hash appearing at two or more leaf positions, an attacker holding just one real key/authorization for that puzzle hash can reveal the identical `puzzle_reveal`/`solution` pair at multiple leaf slots. Since the puzzle only counts how many distinct proof "slots" were satisfied against the curried root — not how many distinct underlying members approved — this lets a single real approver satisfy an `M`-of-`N` threshold intended to require `M` independent approvals.

### Impact Explanation
This directly maps to "unauthorized coin movement" from the validation criteria: a custody/vault arrangement configured (even accidentally, or by one dishonest party during multi-party setup) with a duplicated leaf in its `MofN`/`OneOfN` Merkle tree would silently have its effective security threshold reduced — e.g., an intended "2-of-3 independent signer" vault could become spendable by a single signer whose puzzle hash was duplicated in the tree, without any on-chain signal that the threshold was compromised.

### Likelihood Explanation
Exploitation requires that the vulnerable Merkle tree (with duplicate leaves) actually gets deployed on-chain as the custody puzzle — this can happen if the trusted Python `MofN` driver is bypassed (custom tooling, a malicious co-participant crafting the initial vault puzzle during setup, or a future code path that curries `MofN_MOD`/`OneOfN_MOD` directly). Since the check is enforced only in one Python class and not in the CLVM itself, likelihood depends on how strictly all puzzle-construction paths funnel through `MofN`.

### Recommendation
Enforce leaf uniqueness on-chain as part of the `MofN_MOD`/`OneOfN_MOD` CLVM logic itself (e.g., reject proofs where the same revealed puzzle/solution pair is used to satisfy more than one leaf slot within a single spend), or otherwise ensure the on-chain puzzle cannot be constructed/spent successfully from a Merkle root built with duplicate leaves, rather than relying solely on the off-chain `MofN.__post_init__` guard.

### Proof of Concept
Conceptual: construct two `PuzzleWithRestrictions` members whose `puzzle_hash(_top_level=False)` values are identical (bypassing `MofN.__post_init__`'s duplicate check by currying `MofN_MOD`/`OneOfN_MOD` directly rather than via the `MofN` dataclass), set `m=2, n>=2` including this duplicated hash, then produce a `solve()`-style solution that reveals the single real `ProvenSpend` at both corresponding leaf positions via `MofNMerkleTree._m_of_n_proof` — satisfying the `m=2` requirement with only one real signature/authorization.

class MofNMerkleTree(MerkleTree):  # Special subclass that can generate proofs for m of n puzzles in the tree
    def _m_of_n_proof(self, puzzle_hashes: list[bytes32], spends_to_prove: dict[bytes32, ProvenSpend]) -> Program:
        if len(puzzle_hashes) == 1:  # we've reached a leaf node
            if puzzle_hashes[0] in spends_to_prove:
                spend_to_prove = spends_to_prove[puzzle_hashes[0]]
                # If it's one that we've been requested to prove, the format is (() puzzle_reveal . solution)
                return Program.to((None, (spend_to_prove.puzzle_reveal, spend_to_prove.solution)))
            else:
                return Program.to(hash_an_atom(puzzle_hashes[0]))
        else:
            first, rest = self.split_list(puzzle_hashes)
            first_proof = self._m_of_n_proof(first, spends_to_prove)
            rest_proof = self._m_of_n_proof(rest, spends_to_prove)
            if first_proof.atom is None or rest_proof.atom is None:
                # If either side has returned as a cons, part of the subtree needs to be revealed
                # so we just return the branch as is
                return Program.to((first_proof, rest_proof))
            else:
                return Program.to(hash_a_pair(bytes32(first_proof.as_atom()), bytes32(rest_proof.as_atom())))

    def generate_m_of_n_proof(self, spends_to_prove: dict[bytes32, ProvenSpend]) -> Program:
        return self._m_of_n_proof(self.nodes, spends_to_prove)
