### Title
ThresholdKeys deserialization/constructor never binds `secret_share` to `params.i()` — participant index can be swapped to claim another participant's key share - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::new` (and therefore `ThresholdKeys::read`, which rebuilds keys from untrusted bytes) validates the participant index range, the verification-share count, and the interpolation mode — but never checks that the deserialized `secret_share` actually corresponds to `verification_shares[params.i()]` (i.e., `C::generator() * secret_share == verification_shares[i]`). This is the Serai analog of the IDOR class in the reference report: the "object ID" (the participant index `i`) can be manipulated in serialized key material to bind a secret share that belongs to a different index, with no ownership/consistency check.

### Finding Description
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs, lines 349–391) the only checks are:

- `verification_shares.len() == n` and every key `<= n` (lines 355–365),
- `Interpolation::Constant` only when `t == n` (lines 367–374),
- `group_key` is computed by interpolating `verification_shares[1..=t]` (lines 376–378).

The stored `secret_share` is never compared against `verification_shares[params.i()]`. `ThresholdParams::new` (lines 166–179) only bounds `i <= n`. Nothing ties the identity `i` to the secret object it claims. The test-vector importer (`crypto/frost/src/tests/vectors.rs`, lines 117–131) shows the serialization layout is fully attacker-controllable: `t`, `n`, `i`, interpolation tag, `secret_share`, and all `verification_shares` are just bytes fed to `ThresholdKeys::read`.

Downstream, `ThresholdKeys::view` interpolates `secret_share` at `params.i()` and `AlgorithmSignMachine::sign` produces a FROST share; `AlgorithmSignatureMachine::complete` then verifies each share against `view.verification_share(l)`. The code itself acknowledges this gap: the final error path states the only known cause is "to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs, lines 491–494).

### Impact Explanation
An attacker who can supply the serialized `ThresholdKeys` bytes loaded by a participant (key-distribution channel, restored backup, or any untrusted input routed through `ThresholdKeys::read`) swaps `i` so that the victim's stored `secret_share` actually belongs to index `j` while the params claim `i` — the exact IDOR shape: accessing/claiming another participant's object by manipulating its identifier with no ownership check.

Consequences:
- The victim signs with a share that does not satisfy `verification_shares[i]`; in `AlgorithmSignatureMachine::complete` the batch blame verification attributes the failure to `l == i` (crypto/frost/src/sign.rs, lines 474–489), so the honest victim is reported as the faulty signer (`FrostError::InvalidShare(i)`), enabling false accusation/slashing.
- If `verification_shares` are also crafted consistently, the victim produces shares under a group key for which their share is a different index's share — an incorrect verifier relationship that silently corrupts every signing session the keys are used in (unspendable outputs / funds reported under a key no honest quorum actually controls as labeled).

### Likelihood Explanation
Reachable whenever `ThresholdKeys::read` consumes bytes not generated by the local, verified PedPoP `calculate_share`/`BlameMachine::complete` path — which internally guarantees consistency but is bypassed entirely on deserialization. Any integrator that loads key material from storage or the network without re-running the DKG is exposed. Medium likelihood; impact is integrity/attribution rather than direct share recovery.

### Recommendation
In `ThresholdKeys::new` (and hence `ThresholdKeys::read`), verify ownership: reject unless `C::generator() * *secret_share == verification_shares[&params.i()]`. This binds the claimed participant index to the secret share exactly once at construction, closing the swap.

### Proof of Concept
```rust
// crypto/dkg: take keys for a valid (t, n) group produced by any DKG.
// Serialize participant j's keys, rewrite the `i` field to a different
// participant index i (<= n), leaving secret_share = share_j and
// verification_shares unchanged.
let mut bytes = keys_j.serialize();
// overwrite the little-endian u16 `i` field with i
bytes[i_offset .. i_offset + 2].copy_from_slice(&i.to_le_bytes());

// ThresholdKeys::read accepts it: no check that G * share_j == vshares[i]
let forged = ThresholdKeys::<C>::read::<&[u8]>(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.params().i(), i_participant); // claims index i
// ...but original_secret_share() is still participant j's share.

// During FROST signing, AlgorithmSignatureMachine::complete blames
// participant i (the victim index) via InvalidShare(i).
```
