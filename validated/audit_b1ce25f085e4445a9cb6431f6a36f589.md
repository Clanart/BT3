### Title
`ThresholdKeys::read` accepts identity/arbitrary verification shares, letting deserialized keys resolve to an attacker-controlled or identity group key - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to the referenced deserialization allowlist bypass, `ThresholdKeys::read` deserializes attacker-supplied bytes into a full threshold key without enforcing the validation applied elsewhere. Verification shares are read with `Ciphersuite::read_G` (canonicality check only, no identity rejection) rather than the identity-rejecting `frost::Curve::read_G`, and `ThresholdKeys::new` computes `group_key` from verification shares `1..=t` without checking the shares or the result. An attacker who supplies serialized `ThresholdKeys` bytes can therefore construct a key whose `group_key()` is the identity (trivially forgeable Schnorr signatures) or any point with a known discrete log (a key fully controlled by the attacker, presented as the set's group key).

### Finding Description
`ThresholdKeys::read` at `crypto/dkg/src/lib.rs:574-632` performs the following on untrusted input:

- Reads `t`, `n`, `i` and builds `ThresholdParams` via `ThresholdParams::new` (lines 591-602, 625-626), which validates only `t <= n` and `i <= n`.
- Reads the interpolation byte; for `Constant` it reads `n` scalars via `C::read_F` (lines 604-616).
- Reads `secret_share` via `C::read_F` (line 618).
- Reads `n` verification shares via `<C as Ciphersuite>::read_G(reader)` (lines 620-623).

The critical point is which `read_G` is used. `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only enforces canonical encoding (`point.to_bytes() == encoding`); it explicitly accepts the identity point. By contrast, `frost::Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) rejects identity:

```rust
fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
  let res = <Self as Ciphersuite>::read_G(reader)?;
  if res.is_identity().into() {
    Err(io::Error::other("identity point"))?;
  }
  Ok(res)
}
```

`ThresholdKeys::read` is defined over `C: Ciphersuite`, not `C: Curve`, so the weaker decoder is silently used — the same "allowlist present but bypassed via a different code path" shape as the referenced CVE.

Then `ThresholdKeys::new` (lines 349-391) checks only the count and index range of `verification_shares`, and computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

There is no rejection of identity verification shares, no check that `group_key` is non-identity, and no check that `G * secret_share == verification_shares[i]` (the self-consistency invariant PedPoP establishes via `share_verification_statements` and `multiexp_vartime` in `crypto/dkg/pedpop/src/lib.rs:430-521` is not re-verified here — deserialization trusts it implicitly).

### Impact Explanation
An attacker supplying the byte stream to `ThresholdKeys::read` (e.g., a key blob served by an untrusted server, peer, or recovery source) fully controls every verification share and the secret share:

1. **Identity group key.** With `Interpolation::Lagrange`, set all verification shares `1..=t` to the identity encoding. `group_key = Σ (identity * λ_i) = identity`. The resulting `ThresholdKeys` reports a group key of identity, under which Schnorr signatures are trivially forgeable by anyone (`s·G = R + c·0`), and any downstream signature/share verification anchored to those shares is degenerate.
2. **Attacker-owned group key.** Choose any scalar `k`, solve the `t` Lagrange-weighted share equations (the attacker picks the shares freely), and produce a `group_key = k·G` while `view()`/signing paths still function. The key material deserializes and presents as a valid threshold key whose group key the attacker alone controls — funds or authorizations directed to `group_key()`/`original_group_key()` are not spendable by the threshold set and are controlled by the attacker. This mirrors the "untrusted bytes produce a semantically different object than the allowlist intended" consequence of the reference bug.

No colluding threshold or malicious-validator assumption is needed — only the ability to feed bytes to `ThresholdKeys::read`, which the scan rules explicitly allow.

### Likelihood Explanation
Reachability depends on the integrator deserializing `ThresholdKeys` from input influenced by an untrusted party (key backup/recovery services, exchanged key material). The primitive itself imposes no authentication on the byte stream — `read` validates the curve ID, parameter ranges, and canonicality, but nothing semantic. Wherever serialized keys cross a trust boundary, exploitation is deterministic (no probabilistic steps) and cheap.

### Recommendation
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read`/`ThresholdKeys::new`:

- Reject identity verification shares and an identity `group_key` (apply the same identity rejection `Curve::read_G` enforces).
- Verify `C::generator() * secret_share == verification_shares[params.i()]` on deserialization so the secret share is provably consistent with the declared verification shares.
- Optionally require `t` verification shares `1..=t` be non-identity before computing `group_key`, and document that `ThresholdKeys::read` must only consume authenticated input if such checks are deemed out of scope.

### Proof of Concept
Conceptually, for a `Lagrange`-interpolation `ThresholdKeys` over any supported ciphersuite `C`:

```
id_len = u32_le(len(C::ID)); id = C::ID
t = 1, n = N, i = 1
interpolation byte = 1 (Lagrange)
secret_share    = canonical encoding of arbitrary scalar s
share_1..N      = canonical encoding of the identity point
```

`ThresholdParams::new(1, N, 1)` succeeds; `C::read_F` accepts `s`; `Ciphersuite::read_G` accepts each identity encoding (it is canonical). `group_key = identity * λ_1 = identity`. The resulting `ThresholdKeys` yields `original_group_key() == identity`, so verification against the reported group key succeeds for any `R = s'·G` forgery, demonstrating that the deserialized object violates the non-identity-group-key invariant the rest of the codebase (FROST preprocess/signature paths via `Curve::read_G`) assumes.

One caveat I could not fully verify within the available tool budget: whether the in-scope callers actually feed `ThresholdKeys::read` with bytes an unprivileged party controls end-to-end; the finding is stated at the library level, where the reachability is "untrusted bytes into `ThresholdKeys::read`" per the scan rules.
