### Title
Unchecked unsigned subtraction in `GPBCodedInputStreamBytesUntilLimit` can underflow when the read position advances past `currentLimit` - (File: `objectivec/GPBCodedInputStream.m`)

### Summary
The Solidity report identifies a root-cause pattern: an unsigned subtraction `A - B` performed without first verifying `A >= B`, letting the result wrap to a huge value and be trusted downstream as "remaining amount." The closest structural analog in this Protobuf checkout is `GPBCodedInputStreamBytesUntilLimit`, which computes `state->currentLimit - state->bufferPos` with no guard that `bufferPos <= currentLimit`. [1](#0-0) 

### Finding Description
`GPBCodedInputStreamPushLimit` sets `state->currentLimit` as a logical boundary for a nested message/group, only validating that the new limit does not exceed the *previous* limit: [2](#0-1) 

`currentLimit` is enforced only at the points where generated/consuming code explicitly polls `GPBCodedInputStreamBytesUntilLimit(state) > 0` between fields (e.g., in message-parsing loops) — it is not re-checked inside every primitive read (varint/fixed/length-delimited skip), which instead bound themselves against the *physical buffer* (`bufferSize`), not against the logical sub-message `currentLimit`. As seen in `SkipRawData`'s handling of length-delimited fields, the only size validation shown is `CheckFieldSize(size)` (an overflow-style check), not a check against `currentLimit`: [3](#0-2) 

If a field near the end of a sub-message's byte range decodes to a value (e.g. a multi-byte varint, or a fixed32/fixed64) whose consumption advances `bufferPos` past `currentLimit` but still within the overall buffer, no exception is raised at that moment. The very next call to `GPBCodedInputStreamBytesUntilLimit` then computes `currentLimit - bufferPos` as an unsigned (`size_t`) subtraction where `bufferPos > currentLimit`, wrapping to a near-`SIZE_MAX` value instead of producing a caught error. This mirrors the reported bug's failed invariant exactly: the code assumes the minuend is always the larger value ("`rewardsPerTokenEnd` should exceed `userRewardsClaimed`" / "`currentLimit` should exceed `bufferPos`"), and no check exists to catch the inverted case.

### Impact Explanation
A wrapped, enormous `BytesUntilLimit()` result would be treated by generated parsing loops as "many more bytes remain in this sub-message," causing the parser to keep consuming subsequent, unrelated bytes in the buffer as if they still belonged to the already-overrun sub-message. This corrupts message field interpretation (fields from a different, later part of the stream get attributed to the wrong message/group) rather than being caught as a truncation/malformed-input error. It does not by itself grant memory-unsafe access beyond the buffer (reads still stay bounded by `bufferSize`), so the impact is data/parsing integrity corruption within trusted consuming applications, not RCE or heap corruption.

### Likelihood Explanation
This requires attacker control only over an otherwise well-formed, bounded ProtoJSON/binary payload reaching the public Objective-C `GPBCodedInputStream` parse path with nested messages/groups — consistent with the assumed threat model (ordinary client, bounded input, trusted schema). However, I was not able to fully confirm, within the available index, that no other guard (e.g., an implicit check inside `ReadRawVarint64`/`ReadRawLittleEndian32/64` comparing against `currentLimit` rather than only `bufferSize`) prevents `bufferPos` from ever exceeding `currentLimit` before `BytesUntilLimit` is invoked. This is the key uncertainty: if such a per-primitive-read check exists elsewhere in the file (not captured by my search), the underflow path may be unreachable in practice, which would downgrade this from a real Medium-severity issue to a purely theoretical one.

### Recommendation
Add an explicit invariant check in `GPBCodedInputStreamBytesUntilLimit` (and equivalent consuming code) to detect `bufferPos > currentLimit` and raise `GPBCodedInputStreamErrorInvalidSubsectionLimit` (or equivalent) instead of returning a wrapped `size_t`, e.g.:
```objc
size_t GPBCodedInputStreamBytesUntilLimit(GPBCodedInputStreamState *state) {
  if (state->bufferPos > state->currentLimit) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidSubsectionLimit, nil);
  }
  return state->currentLimit - state->bufferPos;
}
```
This mirrors the guarded, sign-aware comparisons already used elsewhere in this codebase, such as the C++ `EpsCopyInputStream::IsRequestedLessThanOrEqualTo` / `HasEnoughTillLimit` helpers and the explicit overflow-conscious `isBeyondLimit` check in Java's `CodedInputStream`: [4](#0-3) [5](#0-4) 

### Proof of Concept
I could not construct and run a concrete minimal reproduction within this session (no execution/tooling access, and full confirmation of whether per-primitive reads already guard against `currentLimit` was not completed from the indexed excerpts alone). A definitive PoC would require: (1) confirming in the full `GPBCodedInputStream.m` source whether `ReadRawVarint64`/fixed-width readers check against `currentLimit` per-call, and if not, (2) crafting a nested message where a scalar field's encoding straddles the sub-message's `PushLimit` boundary, then observing whether `GPBCodedInputStreamBytesUntilLimit` returns a wrapped huge value on the next poll — this should be verified in a full checkout/Devin session rather than asserted here without evidence.
