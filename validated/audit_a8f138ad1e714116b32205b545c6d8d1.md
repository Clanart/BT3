### Title
Webhook shop-domain spoofing via unsigned `X-Shopify-Shop-Domain` header - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` computes the webhook HMAC over the raw request body only. The `shop_domain` value that downstream application code (and the documented custom-webhook pattern) uses to attribute the webhook payload to a specific shop is read from the `X-Shopify-Shop-Domain` header, which is **not** part of the HMAC-signed data. This is the same bug class as the reported `MatchOrder.protocol` field: a value that drives shop-identity-sensitive logic is excluded from the cryptographic signature that is supposed to guarantee authenticity of the whole request.

### Finding Description
`verify_request` only validates `request.raw_post` against the HMAC: [1](#0-0) 

`shop_domain` is derived independently from a header that is never included in that HMAC computation: [2](#0-1) 

`hmac_valid?` confirms only that `secret` (the app's single client secret, shared across every shop that has the app installed) was used to sign the given body — it says nothing about which shop the body legitimately belongs to: [3](#0-2) 

The gem's own documentation instructs developers to build custom webhook controllers exactly this way — trusting the unsigned `shop_domain` value to route/attribute the (verified-only-for-secret) payload: [4](#0-3) 

Because `ShopifyApp.configuration.secret` is one shared value for the whole app (not a per-shop secret), any merchant that has installed the app can trigger legitimate webhook deliveries from their own shop, compute/observe a valid HMAC for that body, then replay the same signed body to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` header to name a victim shop. The signature check still passes (it never inspected the header), so the job/queue receives attacker-controlled webhook data labeled as belonging to the victim shop of the attacker's choosing — a direct analog of manipulating the unsigned `protocol` field to make the contract execute the wrong logic path for the wrong asset owner.

### Impact Explanation
This enables cross-shop data injection: any installed (unrelated) merchant can forge webhook events that the app processes as if they originated from a shop they do not control, feeding malicious or misleading data (e.g., fake `orders/create`, `app/uninstalled`, or custom topic payloads) into another shop's background jobs/session state. Depending on what the consuming job does (updates records, revokes access, adjusts billing, etc.), this can lead to cross-shop state corruption or unauthorized actions attributed to a victim shop, satisfying the "cross-shop access via accepted forged signed request" bar.

### Likelihood Explanation
Exploitation only requires normal, unprivileged access to the app (installing it on any shop, which is available to any merchant/attacker in a public app), and does not require compromising Shopify's platform HMAC secret — only the ability to send an HTTP POST with a spoofed header alongside a validly-signed body obtained from the attacker's own installation. This is straightforward for any external, unrelated party who is a legitimate but adversarial user of the app.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header (or any other header/param outside the signed body) for shop attribution unless it is cryptographically bound to the signature. Prefer verifying shop identity via the payload body's own shop-identifying fields (which are covered by the HMAC) or via a per-shop verification step (e.g., checking the resolved shop against an existing, previously-authenticated session/webhook registration for that topic+shop) before trusting `shop_domain` for any state-changing operation.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger any webhook topic the app subscribes to (e.g. update a product) to obtain a body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed with the shared app secret).
2. Send `POST /webhooks/<topic>` to the app with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), and header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` passes because it only checks `hmac_valid?(request.raw_post)`.
4. The custom webhook controller pattern documented in `docs/shopify_app/webhooks.md` (`SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`) enqueues the job with `shop_domain == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
