### Title
`sanitizeCloneName` validates a directory-name string that can silently resolve to a different filesystem path than the one Git actually writes to — ([File: app/src/lib/remote-parsing.ts])

### Summary
The bug class in the report is a **check/act mismatch**: one code path validates value *A*, but a separate code path executes against a related-but-different value *B*, and the two are assumed to always agree. GitHub Desktop's clone-destination flow has the same structural weakness: `sanitizeCloneName` (and the emptiness check built on top of it) validates a *string* that represents the final path component, but never accounts for filesystem-level normalization (Windows trailing dot/space collapsing) that can make the *actual* directory Git writes to different from the one that was validated. [1](#0-0) 

### Finding Description
`sanitizeCloneName` is used to turn an attacker-controlled repository name (parsed from a URL a user pastes/clicks, or an `owner/name` shortcut) into a single path component that is later joined onto the user's chosen base clone directory: [2](#0-1) [3](#0-2) 

The sanitizer only special-cases the literal strings `"."` and `".."`: [4](#0-3) 

It does **not** reject (or normalize) names that are made up entirely of dots/spaces, or that end in trailing dots/spaces (e.g. `"..."`, `"foo. "`, `"foo..."`). On Windows, the Win32 filesystem API strips trailing dots and spaces from a single path component before resolving it — a long-documented quirk (the basis of several historical "path collapse" bugs). A component that becomes empty after this stripping is treated as `.` (i.e., it collapses back onto its parent directory) rather than the literal name the application validated.

This produces exactly the report's broken invariant: the emptiness/path check (`validateEmptyFolder`, called from `validatePath`) is performed against the *string* path returned by `Path.join(baseDir, sanitizedName)`, e.g. `C:\Users\victim\Documents\GitHub\...`: [5](#0-4) 

…but the actual destination that `git clone` (and Node's own `fs` calls when Windows resolves the path) will use for that string can collapse to `C:\Users\victim\Documents\GitHub` itself — the *parent* directory that likely already contains the user's other repositories, not an empty, newly created directory. The existing hardening in `app/src/lib/git/clone.ts` (`isClonePathSensitive`) and the traversal tests in `app/test/unit/clone-path-safety-test.ts` only guard against `..`/backslash traversal into fixed sensitive locations (`.ssh`, `.gnupg`, etc.) — they do not defend against this trailing-dot collapse, and neither does `resolveWithin`/`resolveWithinPosix` get applied anywhere in the clone flow (that helper is only used for the Copilot conflict-resolution file writer): [6](#0-5) [7](#0-6) 

So the existing guards do not stop this path: `isClonePathSensitive` checks a fixed deny-list of paths, not "does this resolved path actually equal the parent-of-clone directory due to OS-level normalization," and `sanitizeCloneName`'s traversal check is a string-equality check (`=== '..'`), which a trailing-dot payload never triggers.

### Impact Explanation
If exploitable, a maliciously crafted repository URL/name (fully attacker-controlled: it can come from a `git@`/`https://` remote a user is invited to clone, an `x-github-client://` deep link, or an `owner/name` shortcut typed by the user after being social-engineered into pasting it) can cause the "new repository directory" that Desktop believes it's creating and validating as empty to actually resolve, at the OS level, to the shared parent folder the user stores all their repositories in. Consequences include:
- Git writing/overwriting files directly into the shared parent directory instead of an isolated subdirectory (file write outside the intended, sandboxed clone target).
- The emptiness check giving misleading results (it may pass or fail based on the state of the *parent* directory rather than the intended new folder), letting a clone proceed into a non-empty, shared location without the user's informed consent, silently mixing malicious repository content into the user's existing folder structure.

This matches the report's "impact" pattern precisely: the check is performed on one derived value while the operation executes against a materially different one, and the divergence is only visible after the fact.

### Likelihood Explanation
This is **not fully verified** — I do not have a Windows sandbox available through the tools to confirm Node's `fs.readdir`/`dugite`'s underlying `git.exe` process actually exhibits the classic trailing-dot collapse for this specific call pattern (behavior here depends on the exact Win32 API used by both Node's `fs` layer and by `git.exe`, and modern Node/libuv sometimes reject such paths outright rather than silently collapsing them). The finding should be treated as a **plausible, code-evidenced gap** in the sanitizer's coverage (it demonstrably only excludes `.`/`..`, nothing else) rather than a confirmed, reproduced exploit. Likelihood is Windows-only, requires the user to accept/paste a crafted URL or click a deep link, and depends on OS/Node/Git version-specific path-normalization behavior that would need to be validated in a real Windows environment before treating this as confirmed-high-severity.

### Recommendation
- In `sanitizeCloneName` (app/src/lib/remote-parsing.ts), reject or strip components that consist entirely of dots/spaces, or that end in trailing dots/spaces on any platform, not just the exact strings `.`/`..`.
- After computing the final clone path, validate the *canonicalized* result (e.g., using `resolveWithin`, already implemented in `app/src/lib/path.ts`, or `fs.realpath`-based resolution) against the intended base directory before calling `validateEmptyFolder` and before invoking `git clone`, so the value that is checked is guaranteed to be the value that is ultimately used, closing the check/act gap the same way the C4 report recommends unifying the two token/amount checks.
- Add a regression test mirroring `clone-path-safety-test.ts` that specifically exercises Windows trailing-dot/space payloads (e.g. `sanitizeCloneName('repo...')`, `sanitizeCloneName('...')`) and asserts the resolved path cannot collapse onto the parent directory.

### Proof of Concept
Conceptual (Windows-only, unverified in this environment):
1. Attacker hosts/publishes a repository reachable via a URL whose repo-name component sanitizes to `"..."`, e.g. `https://github.com/attacker/....git` or shares the shortcut `attacker/...`.
2. Victim opens Clone dialog, pastes the URL. `updateUrl` computes `safeName = sanitizeCloneName('...')` → `"..."` (not rejected because it isn't literally `.` or `..`), producing `path = Path.join(<baseDir>, '...')`.
3. `validatePath` → `validateEmptyFolder(path)` runs `readdir` against the string `<baseDir>\...`.
4. If the Win32 path resolver collapses the trailing dots (as it does for many Win32 APIs when a path segment consists solely of dots), the underlying OS call actually targets `<baseDir>` itself instead of a new `...` subfolder, so the emptiness check reports on the wrong directory.
5. On clicking "Clone," `dispatcher.clone(url, path, …)` → `git clone … -- <url> <baseDir>\...` is invoked by `git/clone.ts`; if `git.exe` performs the same trailing-dot normalization, cloning writes into `<baseDir>` directly rather than into an isolated subdirectory, without `isClonePathSensitive` or `sanitizeCloneName` detecting the divergence. export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

  private async validateEmptyFolder(
    path: string | null
  ): Promise<null | Error> {
    if (path === null) {
      return new Error(
        'Unable to read path on disk. Please check the path and try again.'
      )
    }

    try {
      const directoryFiles = await readdir(path)

      if (directoryFiles.length === 0) {
        return null
      } else {
        return new Error(
          'This folder contains files. Git can only clone to empty folders.'
        )
      }
    } catch (error) {
      if (error.code === 'ENOTDIR') {
        // path refers to a file or other file system entry
        return new Error(
          'There is already a file with this name. Git can only clone to a folder.'
        )
      }

      if (error.code === 'ENOENT') {
        // Folder does not exist
        return null
      }

      log.error(
        'CloneRepository: Path validation failed. Error: ' + error.message
      )
      return new Error(
        'Unable to read path on disk. Please check the path and try again.'
      )
    }
  }

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

import * as Path from 'path'
import {

describe('sanitizeCloneName', () => {
  it('returns a simple name unchanged', () => {
    assert.equal(sanitizeCloneName('Hello-World'), 'Hello-World')
  })

  it('extracts last component from backslash-separated traversal', () => {
    assert.equal(sanitizeCloneName('x..\\..\\..\\..\\foo'), 'foo')
  })

  it('rejects names that resolve to .. or empty', () => {
    assert.equal(sanitizeCloneName('..'), null)
    assert.equal(sanitizeCloneName(''), null)
    assert.equal(sanitizeCloneName('.git'), null)
  })
