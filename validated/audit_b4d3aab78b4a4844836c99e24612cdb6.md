### Title
Attacker-controlled `WWW-Authenticate` realm header misclassifies a malicious remote as an "enterprise" GitHub host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind` in the Git credential-helper trampoline decides whether a remote host should be treated as `'enterprise'` (i.e., a trusted GitHub Enterprise instance eligible for GitHub sign-in / stored-account credentials) partly by inspecting the `wwwauth[...]` credential fields that Git forwards from the server's `WWW-Authenticate` HTTP header during authentication.

### Finding Description
When `getCredential` cannot classify a host as `github.com`/GHE by URL shape (`isDotCom`/`isGHE`) and has no existing matching account, it falls back to scanning `cred.entries()` for a `wwwauth[...]` key and treats any value containing `realm="GitHub"` as proof the host is an enterprise GitHub server: [1](#0-0) 
This `wwwauth[...]` value originates from an HTTP response header sent by whatever server Git is talking to — i.e., it is fully attacker-controlled if the attacker operates the remote (or a MITM/proxy in front of it), matching the "attacker controls ... a git remote/proxy response" precondition. There is no check that the URL's hostname is an actual, previously-trusted GitHub Enterprise server; the classification is driven entirely by a string the remote chose to send back.

Once classified as non-`generic`, `getCredential` treats the host as GitHub-like and, if no matching account exists, invokes the interactive GitHub sign-in path instead of the generic-credential path: [2](#0-1) 
This is the "broken invariant": the code assumes `endpointKind !== 'generic'` implies "this is a real GitHub/GHE endpoint," but that invariant is only enforced by a header the remote server fully controls.

### Impact Explanation
If `ui.promptForGitHubSignIn(endpoint)` (in `app/src/lib/trampoline/trampoline-ui-helper.ts`) proceeds to build an OAuth/device authorization request against the attacker-supplied `endpoint`'s host — using `getOAuthAuthorizationURL`/`requestOAuthToken` in `app/src/lib/api.ts`, which embed Desktop's own `ClientID`/`ClientSecret` — an attacker-run remote could induce Desktop to send its confidential OAuth client secret to an attacker-controlled server, or bind a new "account" record for the attacker's endpoint that later gets used for further requests. I was not able to confirm this last step because I ran out of turns before reading `trampoline-ui-helper.ts::promptForGitHubSignIn` and the sign-in-store flow it calls into, so I cannot state with certainty that no additional origin check exists further down that chain.

### Likelihood Explanation
The trigger conditions are plausible under the report's threat model: a user adds/clones a repository whose remote points at an attacker-controlled or attacker-proxied HTTP(S) server, and Git performs any authenticated operation (fetch/push/clone) against it, causing our credential-helper trampoline to run with the attacker-chosen `WWW-Authenticate` header. No local access, admin rights, or social engineering beyond "user has a remote pointing at attacker's server" is required. However, likelihood of a *complete, high-impact* exploit is uncertain without confirming the downstream sign-in flow's own endpoint validation.

### Recommendation
Do not rely on the `WWW-Authenticate` `realm` value alone to classify a remote as `enterprise`; corroborate with an actual capability probe (as already done via `isGitHubHost(endpoint)` a few lines below) or require it to match a previously verified/added GHE account before offering the GitHub sign-in path. Ensure any OAuth/device-flow code path invoked from this classification validates the endpoint via `isGitHubHost` (or similarly trusted mechanism) rather than trusting the header alone.

### Proof of Concept
1. Host a malicious HTTP git server (or a MITM proxy) at `https://evil.example.com/foo.git`.
2. Configure it to respond to Git's HTTP Basic auth probe with `WWW-Authenticate: Basic realm="GitHub"`.
3. Add this URL as a remote in Desktop and perform any authenticated Git operation (fetch/clone/push).
4. `getEndpointKind` returns `'enterprise'` for `evil.example.com`: [3](#0-2) 
5. Because no account matches `evil.example.com`, `getCredential` invokes `ui.promptForGitHubSignIn(endpoint)` with `endpoint = https://evil.example.com/...`: [4](#0-3) 
6. **Unverified step**: whether the resulting sign-in flow then performs an OAuth exchange against `evil.example.com` using Desktop's `ClientID`/`ClientSecret` (as `getOAuthAuthorizationURL`/`requestOAuthToken` in `app/src/lib/api.ts` would do for a legitimate GHE endpoint) — this needs confirmation by reading `trampoline-ui-helper.ts` and the sign-in store, which I did not get to inspect.

**Caveat**: This finding is a real, source-confirmed classification/trust bug in `getEndpointKind`, but the severity depends on downstream code I couldn't verify in the time available. I recommend a follow-up Devin session to trace `trampolineUIHelper.promptForGitHubSignIn` → `sign-in-store.ts` → `api.ts` OAuth calls to confirm whether the attacker-controlled endpoint is used verbatim for the OAuth authorize/token exchange (which would confirm client-secret exfiltration / unauthorized account binding) or whether an additional check blocks it.
