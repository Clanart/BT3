### Title
Webhook shop attribution can be forged independently of HMAC signature verification - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` and `ShopifyApp::PayloadVerification#hmac_valid?` only validate the raw request body against a global app secret; the `X-Shopify-Shop-Domain` header used for shop attribution is never included in the HMAC computation or otherwise bound to the signed payload. An attacker who owns Shop A and can trigger any genuine webhook to their own shop can capture the valid body+HMAC pair and replay it to `ShopifyApp::WebhooksController#receive` with the shop-domain header rewritten to Shop B, and the request will still pass `hmac_valid?`.

### Finding Description
`WebhooksController#receive` builds a `ShopifyAPI::Webhooks::Request` directly from `request.raw_post` and `request.headers.to_h`, and hands it to `ShopifyAPI::Webhooks::Registry.process` [1](#0-0) . Before that, `verify_request` (from `WebhookVerification`) is run as a `before_action` and only checks `hmac_valid?(request.raw_post)` [2](#0-1) .

`hmac_valid?` computes `OpenSSL::HMAC.digest` of the **raw body only**, using the app's global `secret`/`old_secret`, and compares it via `secure_compare` to the `X-Shopify-Hmac-Sha256` header [3](#0-2) . The `X-Shopify-Shop-Domain` header is read separately by `shop_domain` and is not part of the signed data at all [4](#0-3) . Because the app secret is the same across all shops installing the app, any legitimately-signed webhook to Shop A carries a body+HMAC pair that is equally "valid" regardless of which shop-domain header accompanies it — the signature proves the body came from an app-secret holder (Shopify), not which shop it is attributed to.

Since `receive` forwards `request.headers.to_h` unmodified to `Registry.process`, and shop attribution downstream (e.g. `Shop.find_by(shopify_domain: shop)` inside generated job handlers such as `handle(topic:, shop:, body:, ...)`) is derived purely from that header [5](#0-4) , an attacker who swaps the header value between capturing and replaying the request causes the app to process Shop A's payload under Shop B's identity/access token, with `verify_request` unable to detect the tampering because it never inspects or signs the shop-domain header.

### Impact Explanation
This is a cross-shop confusion via forged webhook attribution: an attacker who owns Shop A can cause the app to run a webhook job as if it originated from Shop B, using Shop B's stored session/access token while operating on Shop A's payload data. Depending on the registered handler (e.g., data-sync jobs, redact jobs, order-processing jobs), this can corrupt or leak Shop B's data, trigger unwanted actions against Shop B's store using Shop B's token, or falsify audit/compliance webhooks (e.g., a fabricated `shop/redact` or `customers/redact` completion) — matching Shopify's "forged webhook request" / cross-tenant data exposure impact class.

### Likelihood Explanation
Feasible for any unprivileged attacker who legitimately controls one shop: they only need to install the app on Shop A (a normal, unprivileged action), trigger an event that fires a webhook to their app (fully attacker-controlled, e.g., updating one of their own resources), capture the resulting raw body + `X-Shopify-Hmac-Sha256` value via network capture/proxy on their own traffic, and replay it with a modified `X-Shopify-Shop-Domain` header. No secret, no victim token, and no host misconfiguration is required — the flaw is structural: `hmac_valid?` never covers the domain header. This is fully repeatable for any webhook topic the app subscribes to.

### Recommendation
Bind shop attribution cryptographically to the request instead of trusting an unsigned header: verify that `shop_domain` (sanitized via `ShopifyApp::Utils.sanitize_shop_domain`) corresponds to a shop that actually has an active session/webhook registration consistent with the payload's own `shop_id`/`shop_domain` fields where Shopify includes them in the JSON body, and/or reject requests whose header-derived shop does not match any independently-verifiable value. At minimum, treat the shop-domain header as untrusted metadata and cross-check it against the payload body's own shop identifiers before dispatching shop-scoped jobs.

### Proof of Concept
```ruby
# integration test style PoC
class WebhookCrossShopAttributionTest < ActionDispatch::IntegrationTest
  test "hmac_valid? does not bind shop domain to signature" do
    body = "{}"
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "API_SECRET_KEY", body)
    )

    # Genuine webhook captured for attacker's own Shop A
    post shopify_app.webhooks_path("order_update"),
      params: body,
      headers: {
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "shop-a.myshopify.com",
      }
    assert_response :ok # accepted, attributed to shop-a

    # Replay same body+hmac with rewritten shop-domain header
    post shopify_app.webhooks_path("order_update"),
      params: body,
      headers: {
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "shop-b.myshopify.com", # victim shop
      }
    assert_response :ok
    # ShopifyAPI::Webhooks::Registry.process is invoked with shop: "shop-b.myshopify.com"
    # despite the HMAC only proving the body's origin, not shop attribution.
  end
end
```
Expected result: both requests pass `verify_request`/`hmac_valid?` unchanged, and the second request causes the handler to receive `shop: "shop-b.myshopify.com"`, demonstrating that `hmac_valid?` validates the body only and never the `X-Shopify-Shop-Domain` header used for shop attribution.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
