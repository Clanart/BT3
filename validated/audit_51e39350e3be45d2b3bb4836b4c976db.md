Based on my analysis, I found a valid analog to the reported divide-before-multiply truncation bug.

### Title
NFT royalty amount truncated by divide-before-multiply in `compute_royalty_amount` when royalty is split across multiple NFTs, causing royalty recipients to be underpaid in offer settlements - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`compute_royalty_amount` computes an NFT creator's royalty payment for an offer using `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`, which performs an integer division (`// royalty_split`) *before* the multiplication by `percentage`. This is the same divide-before-multiply rounding-truncation pattern flagged in the referenced Sherlock report for `TwoTokenPoolUtils.sol`, and it causes the royalty amount actually paid out during offer settlement to be strictly less than the mathematically correct value whenever `royalty_split > 1` (i.e., an offer contains more than one royalty-enabled NFT sharing the same fungible payment). [1](#0-0) 

### Finding Description
The correct royalty amount owed to a single NFT (when `royalty_split` NFTs of the same percentage share a fungible payment) is:

```
correct = (abs(offered_amount) * percentage) // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```

Instead, the code computes:

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

Due to Python's left-to-right evaluation of `//` and `*` (equal precedence), this is:

```
((abs(offered_amount) // royalty_split) * percentage) // MAX_ROYALTY_BASIS_POINTS
```

The early `// royalty_split` floors the base amount before it is multiplied by `percentage`, discarding remainder value that the correct formula would have retained until the final division. Concretely, for `abs(offered_amount)=10`, `royalty_split=3`, `percentage=9999` (99.99%):
- Correct: `(10 * 9999) // (3 * 10000) = 99990 // 30000 = 3`
- Actual (buggy): `(10 // 3) * 9999 // 10000 = 3 * 9999 // 10000 = 29997 // 10000 = 2`

This function is invoked from `NFTWallet.make_nft1_offer` (used by `create_offer_for_ids` for royalty-enabled NFTs) to build the actual `CreateCoin` royalty payment(s) that get baked into the settlement spend bundle, so the truncation directly reduces on-chain value paid to the NFT royalty address whenever an offer bundles multiple royalty NFTs against the same fungible asset (setting `request_side_royalty_split`/`offer_side_royalty_split` > 1). [2](#0-1) [3](#0-2) 

The identical pattern also appears in `NFTWallet.royalty_calculation`, used by the `nft_calculate_royalties` RPC to preview/display expected royalty amounts to users before they accept an offer: [4](#0-3) 

### Impact Explanation
Any wallet user constructing or taking an NFT offer that bundles two or more royalty-enabled NFTs against the same fungible asset (a normal, unprivileged "complex NFT offer" flow already exercised by `test_complex_nft_offer`) will settle with the royalty recipient(s) receiving less than the protocol-intended percentage of the trade. This is a concrete under-payment in offer settlement, i.e., value that should flow to the royalty address is instead retained by the offering party — an asset-movement discrepancy reachable purely through standard offer creation/acceptance, with no privileged access required.

### Likelihood Explanation
This triggers deterministically any time `royalty_split > 1`, which occurs whenever a single offer offers/requests more than one royalty-bearing NFT against the same fungible currency — a supported and tested scenario (`test_complex_nft_offer`, `test_royalty_split_across_multiple_nfts`). No malicious peer or special privilege is needed; a normal maker/taker constructing such an offer is sufficient to trigger the discrepancy.

### Recommendation
Reorder the arithmetic so the multiplication happens before any division, matching the Sherlock recommendation for the analogous Solidity issue:

```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```

Apply the same fix to the equivalent expression in `NFTWallet.royalty_calculation` (`amount` field) so royalty previews shown via `nft_calculate_royalties` match the amount actually settled on-chain.

### Proof of Concept
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount

# royalty_split=3 (offer bundles 3 royalty NFTs against the same fungible asset)
result = compute_royalty_amount(offered_amount=-10, royalty_split=3, percentage=9999)
print(result)  # -> 2 (current buggy behavior)

# correct value using multiply-before-divide:
correct = (abs(-10) * 9999) // (3 * 10000)
print(correct)  # -> 3

assert result != correct  # demonstrates the truncation-induced underpayment
``` [5](#0-4)

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
