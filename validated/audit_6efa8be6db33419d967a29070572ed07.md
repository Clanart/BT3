## Title
Discarding changes on a file behind an attacker-controlled symlink path in the working directory can delete/overwrite files outside the repository - (File: `app/src/lib/stores/git-store.ts`)

## Summary
`GitStore.discardChanges()` builds the on-disk path to remove/trash purely with `Path.resolve(this.repository.path, file.path)` and hands it directly to `shell.moveItemToTrash()` / `rm()`, with **no check that the resolved path actually stays inside the repository**. This is the same missing-invariant class as the CreamFi report: a value that is trusted to be "in range" (there, `redeemTokens <= accountTokens[redeemer]`; here, "the file to delete/trash is inside `repository.path`") is used without validation. Elsewhere in this very codebase (`copilot-conflict-context.ts`, `app-store.ts`) the exact same class of write operation is guarded with `resolveWithin()`, which explicitly defends against symlink-based directory escapes, proving the maintainers know this check is required — it is simply missing on this older path.

## Finding Description
`discardChanges` iterates the files the user asked to discard and, for any file that isn't a submodule and isn't `Deleted`, either trashes it or deletes it: [1](#0-0) 

Both branches build the filesystem path from repository-relative `file.path` with a plain resolve/join and no containment check:
```
await this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))
...
await rm(Path.join(this.repository.path, file.path))
```
`file.path` ultimately comes from `git status` parsing (`WorkingDirectoryFileChange`). Nothing in this call chain verifies that the real (symlink-resolved) location of that path is still under `repository.path`.

Compare this with the guard the same codebase added for a functionally identical operation — writing/overwriting a working-directory file identified by a repo-relative path — in the Copilot conflict-resolution flow: [2](#0-1) 

and in `buildConflictContext`: [3](#0-2) 

Both explicitly call `resolveWithin(workingDirectory, file.path)`, which resolves symlinks via `realpath` and rejects any path whose real location escapes the root: [4](#0-3) 

The project's own tests demonstrate exactly the attack this guard stops — a symlinked directory component used to walk outside the intended root: [5](#0-4) 

`discardChanges` performs the equivalent filesystem mutation (delete/overwrite a file at a repo-relative path) but was never updated to use `resolveWithin`, or any other containment check. A cloned/checked-out working directory can legitimately contain a symlink as a tracked or untracked entry (git tracks symlinks as blob type `120000`), so a malicious repository can commit a symlink such as `evil-dir -> /home/user` (or a Windows junction/symlink) and then have an "untracked"/"modified" entry appear to Desktop with a path like `evil-dir/some-file`. `Path.resolve`/`Path.join` performs no filesystem I/O and does not care that `evil-dir` is a symlink; when `shell.moveItemToTrash` / `rm` subsequently operate on that string, the OS follows the symlink component and the resulting delete/trash targets a file outside the repository the user thinks they're discarding changes in.

## Impact Explanation
This breaks the invariant "Discard Changes only touches files inside the cloned repository." An attacker who controls a cloned/fetched repository (a valid GitHub Desktop threat actor per the report's scope) can arrange for a discard-changes action the victim performs on an innocuous-looking file to instead delete or move-to-trash a file located anywhere on the victim's filesystem that is reachable by symlink target, i.e. "file write/delete outside the repo" caused by attacker-controlled repository content, and it happens silently — the user only sees a normal "Discard changes" confirmation for what appears to be a repo-relative path.

## Likelihood Explanation
Requires the victim to clone/open a malicious repository and use the "Discard changes" action (from the Changes list context menu or the confirmation dialog) on a file path that is nested under an attacker-supplied symlinked directory — a normal, expected user interaction with an attacker-controlled repo, not physical/admin access or pre-existing malware. Git happily tracks and checks out symlinks by default on macOS/Linux (and on Windows when symlinks are enabled), so setting this up is straightforward for the attacker; the only friction is convincing/waiting for the victim to invoke Discard Changes on that entry, which is a common, everyday Desktop action.

## Recommendation
Add the same containment check the newer code already uses before any filesystem mutation in `discardChanges`:
```ts
const target = await resolveWithin(this.repository.path, file.path)
if (target === null) {
  // treat like a failed operation / skip, do not touch the filesystem
  continue
}
await this.shell.moveItemToTrash(target)
```
and equivalently guard the `rm(Path.join(...))` calls. This mirrors `resolveWithin` usage already present in `copilot-conflict-context.ts` and `app-store.ts`.

## Proof of Concept
1. Attacker creates a repository containing a symlink `lure -> /home/victim` (created with `ln -s /home/victim lure && git add lure && git commit`), plus commits a benign file so the repo looks normal.
2. Victim clones the repository with GitHub Desktop; the checkout creates `lure` as an actual symlink pointing to their home directory.
3. Attacker's repo (or a follow-up local edit prompted via README instructions) causes an "untracked" entry to be listed at `lure/.ssh/authorized_keys`-style nested path, or more simply the attacker ships the repo already containing an uncommitted local change under `lure/some-file` that the victim is asked to "discard" (e.g. via instructions in the README: "please discard the local test artifact under lure/tmp.txt before continuing").
4. Victim selects "Discard changes" on that file in the Changes list.
5. `GitStore.discardChanges` resolves `Path.resolve(repository.path, 'lure/tmp.txt')`, which the OS follows through the `lure` symlink, and `shell.moveItemToTrash`/`rm` deletes/trashes a file inside the victim's home directory instead of anything inside the cloned repo.

*Note: I was not able to execute this end-to-end in the sandbox (no filesystem/terminal access here), so the exact list of Desktop UI entry points that surface an actionable "Discard changes" item for a path nested inside a symlinked directory should be verified by a Devin session with repo access before treating this as fully confirmed; the missing `resolveWithin` guard itself, however, is directly verifiable in the cited source.*

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
