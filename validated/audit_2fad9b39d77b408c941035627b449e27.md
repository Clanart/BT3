### Title
Denial of service via identity point in FROST preprocess reaches `x()` panic in Bitcoin Schnorr HRAM - (File: networks/bitcoin/src/crypto.rs)

### Summary
`Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) accepts the point at infinity: `ProjectivePoint::from_bytes`/`EdwardsPoint::from_bytes` decode the identity as a canonical encoding, and the re-encode check (`point.to_bytes() == encoding`) passes. `TransactionSignMachine::read_preprocess` (networks/bitcoin/src/wallet/send.rs:351-353) and `TransactionSignatureMachine::read_share` (send.rs:409-411) feed these attacker-controlled bytes into nonce commitments `R` / `A` with no identity rejection. `Hram::hram` (crypto.rs:59-73) calls `x(R)`/`x(A)`, and `x` (crypto.rs:13-16) executes `encoded.x().expect("point at infinity")`, which panics on the identity point. The file's own doc comments acknowledge this: "If either `R` or `A` is the point at infinity, this will panic" (crypto.rs:54).

This is the Serai analog of CVE-2017-9128's crafted-file crash: untrusted bytes fed to a `read_*`/verify path trigger a crash in reachable production code.

### Finding Description
An unprivileged cosigner submits a FROST preprocess whose nonce commitment is the serialized point at infinity. The nonce is summed into `nonce_sums`/`nonces` for `sign_share` and into the per-signer `R` used by `Schnorr::verify`/`verify_share` (crypto.rs:139-159), which route into `Hram::hram`. Because the Bitcoin BIP-340 HRAM requires the x-coordinate of `R` and `A`, and the identity has no x-coordinate, `x()` panics. The same applies to a maliciously constructed `ThresholdKeys`/group key via `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), which never rejects an identity `group_key` or identity verification shares, and to `SchnorrSignature::read` consumers — although `Signed::read` (coordinator/tributary/src/transaction.rs:62-69) does reject identity `R`, the generic FROST `read_preprocess`/`read_share`/`Commitments::read` paths in crypto/dkg/pedpop (lib.rs:109-128) do not.

### Impact Explanation
A single malformed preprocess or share byte stream crashes the signing/verification process (`expect`/panic), aborting the threshold signing attempt. In a processor running the Bitcoin `TransactionMachine`, one faulty participant can repeatedly kill every signing session it joins — a persistent liveness denial of service on fund movement, matching the CVE's availability impact.

### Likelihood Explanation
Any party able to submit preprocess/share bytes (a DKG or signing participant) can craft the encoding; no key knowledge is needed. Identity encodings are canonical and pass `read_G`. The only prerequisite is reaching a code path where `hram` is evaluated over the malicious nonce — i.e., normal `sign`/`complete`/`verify_share` execution.

### Recommendation
Reject the point at infinity inside `Ciphersuite::read_G` (or at least inside `read_preprocess`/`read_share`/`Commitments::read`/`ThresholdKeys::new` for nonce commitments, verification shares, and the group key), mirroring the existing identity check in `Signed::read`. Alternatively, make `x()`/`Hram::hram` return an error instead of panicking on infinity.

### Proof of Concept
1. Build a Bitcoin `SignableTransaction` and `TransactionMachine`.
2. In place of a real preprocess, supply `read_preprocess` bytes where one nonce commitment is the 33-byte SEC1 identity encoding `0x00` (secp256k1) — `Secp256k1::read_G` accepts it.
3. Call `TransactionSignMachine::sign`/`complete` (or `Schnorr::verify_share`) — evaluation reaches `Hram::hram(&identity, ..)` → `x(&identity)` → `expect("point at infinity")` → panic.

Caveat: I confirmed `read_G` performs no identity rejection and that `x()` panics on infinity; I did not fully trace `frost`'s `IetfSchnorr::sign_share`/`verify_share` internals to confirm no earlier identity filter exists — if FROST already rejects identity nonces before `hram`, this reduces to a lower-confidence finding.
