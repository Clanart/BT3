## Analysis

The WordPress bug reduces to one broken invariant: a value that should be constrained to "inside the upload directory" is taken from attacker-reachable state and handed directly to a filesystem delete/write call, with no path-containment check. The equivalent broken invariant in GitHub Desktop is present in `discardChanges` in `app/src/lib/stores/git-store.ts`, which resolves a file path taken from `git status` output — content that is derived from the *working tree layout of a cloned/checked-out repository*, i.e. attacker-controlled — and passes it straight to `shell.moveItemToTrash` / `rm` without ever validating that the resolved path stays inside the repository.

### Title
Arbitrary file deletion via repository-controlled path escaping `discardChanges` - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` resolves `file.path` — a path string that originates from `git status --porcelain=2` output for the checked-out working tree — with plain `Path.resolve` / `Path.join` against the repository root, then either moves the resulting absolute path to the OS trash or unlinks it outright. No call in this path narrows the resolved location back into the repository the way `resolveWithin` (`app/src/lib/path.ts`) does elsewhere in the codebase.

### Finding Description
`discardChanges` builds the on-disk path to delete like this: [1](#0-0) 

`file.path` comes from `WorkingDirectoryFileChange`, which in turn is populated from `IStatusEntry.path`, a raw string parsed out of `git status --porcelain=2 -z` output: [2](#0-1) 

Nothing in `status.ts`/`status-parser.ts` restricts this string to a "normal" relative path once the checked-out working tree contains an entry that resolves outside the repository root when joined with `repository.path` (e.g. a tracked symlink at the repo root whose target is outside the repo, combined with a nested untracked/modified entry reported under that symlinked directory name). `Path.resolve`/`Path.join` do not follow symlinks or otherwise prevent escape — they operate purely on the string — so `Path.resolve(this.repository.path, file.path)` can produce an absolute path that, once the OS resolves the symlink component at access time, is a location entirely outside the user's repository.

Contrast this with the pattern Desktop already uses in other places that handle untrusted, repository-derived paths, such as `resolveWithin`, which explicitly `realpath`s both the root and the candidate and rejects anything that doesn't stay under the root: [3](#0-2) 
and its use guarding file reads from conflict content: [4](#0-3) 

`discardChanges` has no equivalent guard before calling `shell.moveItemToTrash` or `rm`.

### Impact Explanation
If exploitable, this allows an attacker who controls the contents of a cloned/checked-out repository to cause GitHub Desktop to delete or move-to-trash a file outside the repository working directory when the user performs the ordinary "Discard changes" action — the same class of impact as the WordPress report (attacker-influenced value reaches `unlink`/file-remove with no containment check), landing squarely in the "file write/delete outside the repo" bucket called out as valid impact.

### Likelihood Explanation
This requires the working tree to actually contain a filesystem entry (via a symlink component checked out from the repository) whose resolved path under `repository.path` lands outside the repo, and for the user to then choose to discard that specific entry from the Changes list — this is a plausible but non-trivial setup dependent on git's own symlink-checkout behavior and OS filesystem semantics, so likelihood is moderate rather than trivial, and would need to be confirmed empirically against current git/Desktop symlink handling.

### Recommendation
Before calling `shell.moveItemToTrash` or `rm` in `discardChanges`, resolve `file.path` with `resolveWithin(repository.path, [file.path])` (already available in `app/src/lib/path.ts`) and skip/reject the operation if it returns `null`, matching the guard pattern already used in `copilot-conflict-context.ts`.

### Proof of Concept
1. Attacker publishes a repository containing a tracked symlink `evil -> /Users/victim/Library/Application Support/GitHub Desktop` (or any sensitive absolute/relative-escaping target) committed at the repo root.
2. Victim clones the repository in GitHub Desktop and, through normal repository activity (e.g. a build script, or a nested tracked path under the symlinked directory), ends up with a working-directory entry whose `git status` path is reported as `evil/<something>`.
3. Victim opens the Changes list and clicks "Discard changes" on that entry.
4. `discardChanges` computes `Path.resolve(repository.path, 'evil/<something>')`, which the OS resolves through the symlink to a path outside the repository, and calls `shell.moveItemToTrash`/`rm` on it, deleting/moving a file the victim never intended to touch. [5](#0-4)

  public async discardChanges(
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true,
    askForConfirmationOnDiscardChangesPermanently: boolean = false
  ): Promise<void> {
    const pathsToCheckout = new Array<string>()
    const pathsToReset = new Array<string>()

    const submodules = await listSubmodules(this.repository)

    for (const file of files) {
      const foundSubmodule = submodules.some(s => s.path === file.path)

      if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
        if (moveToTrash) {
          try {
            await this.shell.moveItemToTrash(
              Path.resolve(this.repository.path, file.path)
            )
          } catch (e) {
            if (askForConfirmationOnDiscardChangesPermanently) {
              throw new DiscardChangesError(e, this.repository, files)
            }

            // The user has received the confirmation dialog in past and has
            // chosen to always discard the changes permanently if trash failes.
            // We need to remove the file manually.
            if (file.status.kind === AppFileStatusKind.Untracked) {
              await rm(Path.join(this.repository.path, file.path))
            }
          }
        } else if (moveToTrash === false) {
          // The user has received the confirmation dialog and has chosen to
          // discard the changes permanently. We need to remove the file
          // manually.
          if (file.status.kind === AppFileStatusKind.Untracked) {
            await rm(Path.join(this.repository.path, file.path))
          }
        }
      }

      if (
        file.status.kind === AppFileStatusKind.Copied ||
        file.status.kind === AppFileStatusKind.Renamed
      ) {
        // file.path is the "destination" or "new" file in a copy or rename.
        // we've already deleted it so all we need to do is make sure the
        // index forgets about it.
        pathsToReset.push(file.path)

        // checkout the old path too
        pathsToCheckout.push(file.status.oldPath)
        pathsToReset.push(file.status.oldPath)
      } else {
        pathsToCheckout.push(file.path)
        pathsToReset.push(file.path)
      }
    }

const unmergedEntryRe =
  /^u ([DAU]{2}) (N\.\.\.|S[C.][M.][U.]) (\d+) (\d+) (\d+) (\d+) ([a-f0-9]+) ([a-f0-9]+) ([a-f0-9]+) ([\s\S]*?)$/

function parseUnmergedEntry(field: string): IStatusEntry {
  const match = unmergedEntryRe.exec(field)

  if (!match) {
    log.debug(`parseUnmergedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for unmerged entry`)
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    path: match[10],
  }
}
