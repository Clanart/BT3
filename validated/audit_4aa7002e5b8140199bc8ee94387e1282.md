## Title
Stale line-index-based partial selection can be silently applied to a different diff, corrupting the resulting commit - (File: `app/src/models/diff/diff-selection.ts`, `app/src/lib/stores/app-store.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The IonPool bug is a case where a partial, incremental state update (`_accrueInterestForIlk`) is later combined with a subsequent update computed from a different baseline, so the final applied value silently reflects the wrong period. GitHub Desktop has a structurally identical pattern in how partial ("some lines but not all") commit selections are tracked and re-applied: `DiffSelection` records *which line indices* are selected, and when the working directory is refreshed, Desktop only intersects the old diverging-line indices with the new set of selectable indices — it never verifies that index `N` in the new diff still refers to the same logical line it did in the old diff. When the patch used to actually stage/commit is generated, it is built from a value obtained independently (`applyPatchToIndex` re-fetches the diff right before applying), reusing that same index-based selection. If the file's diff shape changes between the time the user made a partial selection and the time the patch is generated, the "selected" indices can now point at different content, and the wrong lines are silently staged and committed.

### Finding Description
`DiffSelection` stores partial selections purely as a `Set<number>` of line indices (`divergingLines`), not as any content-addressed identity: [1](#0-0) 

When Desktop reloads a diff (e.g. after a status refresh), it does not recompute the selection from scratch; it only narrows the existing `divergingLines` to intersect with the new `selectableLines`: [2](#0-1) 

This "narrowing" is invoked by `updateChangesWorkingDirectoryDiff`, which explicitly acknowledges it isn't validating that the previously selected lines still correspond to the same content — only that the index still exists as a selectable line in the new diff: [3](#0-2) 

Crucially, that reconciliation only happens for the single file currently displayed in the Changes view (`selectedFileIDsBeforeLoad.length !== 1` short-circuits). For every other file whose diff isn't currently open, `updateChangedFiles` (invoked on every `_loadStatus`) blindly reapplies the old `existingFile.selection` object onto the freshly-fetched file with no adjustment at all: [4](#0-3) 

When the user finally commits, `_commitIncludedChanges` hands the working-directory files (carrying these stale index-based selections) to `createCommit` → `stageFiles`, which for any partially-selected file calls `applyPatchToIndex`: [5](#0-4) [6](#0-5) 

`applyPatchToIndex` re-fetches the diff independently at staging time and builds the patch from `file.selection` against *that* new diff: [7](#0-6) 

`formatPatch` decides what to include purely by `file.selection.isSelected(absoluteIndex)` against the hunk lines of whatever diff it was given — it has no way to know whether index `absoluteIndex` still represents the same logical change the user reviewed: [8](#0-7) 

The broken invariant is the same as in the IonPool report: a value (`divergingLines` / `supplyFactor`) that was computed against one baseline (one diff / one ilk's last-accrual timestamp) is carried forward and combined with, or applied against, a different baseline (a new diff / a different ilk's timestamp) without being fully recomputed, producing a result that is internally consistent-looking (`getSelectionType()` still reports `Partial`) but semantically wrong.

### Impact Explanation
If a file's diff shape shifts between the time a user makes a line-level partial selection and the time `stageFiles`/`applyPatchToIndex` actually builds the patch, the commit produced can silently include different additions/deletions than what the user selected and reviewed in the UI — i.e. "silent corruption of what the user commits." Since the mismatch is only guarded against for the single actively-displayed file, any other file with a lingering partial selection is fully exposed. Because a repository's content (including `.gitattributes` filters, line-ending normalization rules, and file contents delivered on fetch/pull/checkout) is attacker-controlled when cloned from a hostile remote, a maliciously crafted repository can be engineered to shift diff line positions for files the user has already partially staged mentally, while Desktop's periodic background refresh (`_refreshRepository`/`_loadStatus`) reloads status without re-validating those selections.

### Likelihood Explanation
This requires a specific timing window (working-directory content changing between selection and staging for a file that is not the one currently open in the diff viewer) and depends on repository-controlled mechanisms (e.g. `.gitattributes`-driven content normalization applied during Desktop-initiated git operations such as pull/checkout/stash) to shift diff line indices without user action. This is not trivially triggerable on demand and the exact reachable end-to-end exploit chain (which specific Desktop-initiated operation reliably shifts an *unrelated* file's diff mid-session) is not confirmed in this codebase; it is a structural weakness rather than a demonstrated, fully wired exploit.

### Recommendation
Make partial selections content-addressed rather than purely index-based: when a diff is reloaded (for any file, not just the currently displayed one), recompute the selection against the new hunks by matching line content/hash instead of raw index, or invalidate (clear to full/none rather than "best effort" narrow) any partial selection whenever the underlying diff has structurally changed since the selection was captured. At minimum, `applyPatchToIndex` should re-validate that the diff it fetches immediately before staging matches the diff the selection was computed against (e.g. by diff/hunk fingerprint) and abort/re-prompt rather than silently applying a possibly-mismatched selection.

### Proof of Concept
Conceptual (not verified end-to-end in this environment):
1. Open Desktop on a repository; select File A in the Changes list and select only a subset of lines in its diff (partial selection).
2. Without committing, switch focus to File B (so File A is no longer the "currently displayed" file feeding `updateChangesWorkingDirectoryDiff`'s reconciliation).
3. Trigger a Desktop-initiated operation that rewrites File A's on-disk content in a way that shifts line positions but keeps the same number of "selectable" lines (e.g., a repository-controlled `.gitattributes` filter applied during an auto `git add`/checkout/stash operation Desktop performs) — this happens via the untouched `updateChangedFiles` path, which reapplies `existingFile.selection` verbatim.
4. Select File A again and click Commit without re-opening/re-reviewing its diff. `applyPatchToIndex` re-fetches the (now different) diff and applies the stale line-index selection via `formatPatch`, staging/committing different lines than the ones originally selected.
