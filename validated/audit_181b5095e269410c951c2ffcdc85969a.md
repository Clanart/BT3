## Title
Data Race on Cached `StakingInfo.cachedGini`/`consolidatedNodes` Fields Shared via LRU Cache Across Concurrent Readers — ([File: kaiax/staking/staking_info.go])

## Summary
`StakingInfo` objects are cached and shared by pointer (via `stakingInfoCache` and `PreloadBuffer`) and exposed through `GetStakingInfo`/`GetInfo` under an `RWMutex` that is released before the object is used. The object itself contains lazily-initialized, unsynchronized mutable fields (`consolidatedNodes`, `cachedGini`, `cachedGiniMinStake`) that are read-modified-written outside of any lock whenever `Gini()`/`ConsolidatedNodes()` are called — e.g. from proposer/committee selection and from `ToResponse()` (the public `klay_getStakingInfo` RPC). This is structurally the same bug class as the Algernon CVE: a mutex protects the lookup/insertion of a shared object, but is released before the (non-thread-safe) methods on that shared object are invoked, so concurrent callers race on its internal state.

## Finding Description
`PreloadBuffer.GetInfo` (kaiax/staking/impl/preload_buffer.go:70-78) and the staking info LRU cache (`s.stakingInfoCache`, populated in `PreloadFromState`, kaiax/staking/impl/preload_buffer.go:88-124) return a `*staking.StakingInfo` pointer while holding only `ss.mu.RLock()`/`RUnlock()` — the lock protects the map, not the pointed-to object. The very same `*StakingInfo` pointer can be retrieved concurrently by multiple call sites (block processing/committee-selection goroutines, and simultaneously the JSON-RPC `klay_getStakingInfo` handler, `StakingInfoResponse`/`ToResponse`).

`staking.StakingInfo` (kaiax/staking/staking_info.go:33-57) has three fields that are not part of the "input" data but are computed and cached lazily, in place, with no mutex: [1](#0-0) 

`ConsolidatedNodes()` performs an unsynchronized check-then-write on `si.consolidatedNodes`: [2](#0-1) 

`Gini()` performs the same unsynchronized check-then-write pattern on `si.cachedGini`/`si.cachedGiniMinStake`: [3](#0-2) 

Because the object is fetched under `RLock`/`RUnlock` and then handed to the caller with no ownership transfer or copy, two goroutines invoking `Gini()` (or `ConsolidatedNodes()`, which `Gini()`/`ToResponse()` transitively call) on the same shared pointer at the same time race on writing `si.cachedGini`, `si.consolidatedNodes`, and `si.cachedGiniMinStake`. This mirrors the Algernon pattern exactly: `sync.RWMutex` protects only the container lookup (`LoadCommonFunctions`/`ss.preloaded` map), while the actual mutation of the shared, non-thread-safe object (`LState`/`StakingInfo`) happens after the lock is released.

## Impact Explanation
Concurrent calls into `Gini()`/`ConsolidatedNodes()` on the same cached `StakingInfo` instance (e.g., one from block/committee processing computing the proposer list with `useGini=true`, and one from a concurrent `klay_getStakingInfo` RPC call, or two RPC calls at different `minStake` values) can race on the `*float64` and `*[]consolidatedNode` pointer fields. Under Go's memory model this is undefined behavior: a torn/partial write to `si.cachedGini` (pointer assignment observed non-atomically) can cause a reader to dereference a stale/garbage pointer, or `si.cachedGiniMinStake` can be updated inconsistently with `si.cachedGini`, causing a goroutine to read a Gini value computed for the *wrong* `minStake`. Since Gini directly feeds `generateProposerListWeighted` (kaiax/valset/impl/getter_proposers.go) used in weighted-random proposer selection, a corrupted/incorrect Gini value can cause a node to compute a different proposer list than its peers — i.e., state/consensus divergence between honest nodes for pre-Kore weighted-random proposer selection. It can also cause a crash (nil/garbage pointer dereference) in the RPC path, or return an internally-inconsistent `StakingInfoResponse` to an unprivileged RPC caller.

## Likelihood Explanation
`GetStakingInfo`/`GetInfo` is on a hot path invoked by both block-processing/proposer-selection code and by the public JSON-RPC `klay_getStakingInfo` API, both of which can run concurrently against the same underlying LRU/preload-cache entry (the block-processing goroutine and a normal user's RPC call are naturally concurrent). Any unprivileged RPC caller repeatedly requesting staking info while a block containing a proposer-selection computation is being processed can trigger the race; the Algernon report notes this class of race is reliably detected by the Go race detector under "modest concurrency," consistent with what would be expected here.

## Recommendation
Protect the lazily-computed fields of `StakingInfo` with their own mutex (or `sync/atomic`/`sync.Once`), or eagerly compute `consolidatedNodes` at construction time so the object becomes immutable after creation and safe to share by pointer. Alternatively, have `GetStakingInfo`/`GetInfo`/`PreloadFromState` return a defensive copy per caller instead of sharing the same mutable pointer across goroutines, matching the guarantee implied by the surrounding `RWMutex`.

## Proof of Concept
Because the affected code lives entirely in Go source without an obvious single external harness in the index, a concrete PoC requires exercising two goroutines against the same cached `*StakingInfo`:
1. Populate the staking cache (e.g., via `PreloadFromState` or the normal getter path) so a single `*StakingInfo` is stored and returned by both `GetInfo`/`GetStakingInfo`.
2. Concurrently call `si.Gini(minStakeA)` from one goroutine (simulating proposer-list generation) and `si.Gini(minStakeB)` (`minStakeB != minStakeA`) from another (simulating a concurrent `klay_getStakingInfo` RPC call), e.g. via `go test -race` on a test that fetches the same cached object twice and calls `Gini`/`ToResponse` concurrently.
3. Run with `-race`; the Go race detector will report a data race on `si.cachedGini`/`si.consolidatedNodes`, and in a tight loop the returned Gini value can be observed to not match either requested `minStake`, demonstrating both memory-unsafety and result corruption.

Note: I was unable to fully trace every call site that shares a single `*StakingInfo` pointer across goroutines (e.g., precisely how the LRU `stakingInfoCache` in `kaiax/staking/impl/getter.go`/`init.go` and the JSON-RPC `klay_getStakingInfo` handler concurrently retrieve it) within the indexed context. The index has size limits, and some file contents (e.g. `kaiax/staking/impl/getter.go` in full, and the RPC-facing `klay_getStakingInfo` handler) were not fully retrievable — a Devin session with full repository access would allow definitive confirmation of the concurrent call graph and construction of a running PoC.

	// Cache hits only if the same minStake is used.
	if si.cachedGini == nil || si.cachedGiniMinStake != minStake {
		g := si.computeGini(minStake)
		si.cachedGini = &g
		si.cachedGiniMinStake = minStake
	}

}
