### Title
OP_RETURN data output omitted from weight calculation causes underestimated fee and overweight transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` appends an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` to `tx_outs`, but computes the transaction weight and required fee via `calculate_weight_vbytes`, which is only ever passed `payments` — the data output is never included in the weight estimate. The resulting `needed_fee` and `TooLowFee`/`TooLargeTransaction` checks are computed against a transaction that is smaller than the one actually built and signed. Analogous to the reference bug (fee computed against the wrong quantity), the fee here is proportional to a size that excludes part of the real transaction.

### Finding Description

In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before the weight/fee computation:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` reconstructs a `Transaction` whose outputs are built solely from `payments` (plus optional change) — the OP_RETURN output is absent. Consequences:

1. **Underpaid fee**: With a maximal 80-byte payload, the OP_RETURN script is ~83 vbytes (`0x6a 0x4c 0x50` + 80 bytes) and the output adds ~92 vbytes to the real transaction. `needed_fee` covers only `payments`-sized vbytes, so the actual fee rate (`fee / actual_vbytes`) is below `fee_per_vbyte`.
2. **Weakened min-fee check**: `TooLowFee` is evaluated against the underestimated `vbytes`, so a transaction can pass the `DEFAULT_MIN_RELAY_TX_FEE` check while its real feerate is below minimum relay policy. The signed transaction would be rejected by peer mempool acceptance and never confirm — the "fee is substantial/proportionate" invariant is broken exactly as in the reference finding where the fee tracked the wrong quantity.
3. **Skipped change edge**: the change-dust decision uses `fee_with_change`, also computed without the data output, so the change/leftover split is computed against the wrong fee.
4. **Overweight transaction**: the `MAX_STANDARD_TX_WEIGHT` check at the end uses the underestimated `weight`, allowing construction of a transaction exceeding the 400,000 WU standardness limit.

### Impact Explanation

A `data`-bearing transaction is produced with a feerate below what the caller requested and potentially below Bitcoin's minimum relay feerate, or above the standardness weight cap. The threshold signature machinery will still sign and broadcast it, yielding a transaction that peers refuse to relay/accept — funds locked in the multisig inputs become unspendable until a replacement is coordinated, and any protocol flow that depends on timely confirmation (e.g., Serai's Bitcoin rotations/relays that use the data output) stalls. This is an incorrect fee formula directly reachable through the public `SignableTransaction::new` API by whoever supplies `payments`/`data`.

### Likelihood Explanation

Any invocation passing `Some(data)` triggers the miscalculation; the error magnitude scales with the data length (up to ~92 vbytes for the 80-byte cap). Exploitation/impact requires only that a caller rely on `needed_fee()`/`fee_per_vbyte` being honored — no malicious validator or leaked key is needed.

### Recommendation

Compute weight and fee against the actual `tx_outs` (or pass the fully-built output list including the OP_RETURN output) into `calculate_weight_vbytes`. Concretely, either move the `data` output construction before the weight calculation and pass `tx_outs`' script/amount pairs, or add a `data_len` term to the vbyte estimate. Then re-check `TooLowFee`, the change-dust threshold, and `MAX_STANDARD_TX_WEIGHT` against the corrected weight.

### Proof of Concept

```rust
// networks/bitcoin/src/wallet/send.rs
// In SignableTransaction::new, with data = Some(vec![0u8; 80]):

// tx_outs gains an OP_RETURN output of ~92 serialized bytes...
tx_outs.push(TxOut {
  value: Amount::ZERO,
  script_pubkey: ScriptBuf::new_op_return(...), // ~83-byte script
});

// ...but the weight is computed only over `payments`:
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None); // data output missing

let mut needed_fee = fee_per_vbyte * vbytes; // ~92 vbytes of fee missing

// Actual fee rate paid by the signed tx:
//   fee() == input_sat - sum(outputs) == needed_fee (when no change)
//   real_vbytes ≈ vbytes + 92  =>  real_feerate < fee_per_vbyte
// TooLowFee and MAX_STANDARD_TX_WEIGHT are likewise evaluated on `vbytes`/`weight`,
// so a sub-minimum-relay or >400k WU transaction passes validation and gets signed.
```
