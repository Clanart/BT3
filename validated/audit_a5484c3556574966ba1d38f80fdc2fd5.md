### Title

OP_RETURN data is excluded from transaction weight and fee accounting - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` appends a caller-controlled OP_RETURN output before estimating the transaction’s weight, but the estimator only receives `payments` and optional `change`, not `data`. When change is created, the transaction commits to the underestimated fee, allowing an 80-byte payload to consume block space without paying the corresponding fee. At the minimum relay rate, this can produce a transaction below Bitcoin’s minimum feerate.

### Finding Description

`SignableTransaction::new` accepts arbitrary `data` and adds it as a zero-value OP_RETURN output before fee estimation. [1](#0-0) 

The fee estimate calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, so the already-added OP_RETURN output is omitted from `vbytes`. [2](#0-1) 

When change is present, the estimate again uses only `payments` and `change`; if sufficient funds remain, the change output is set to `input_sat - payment_sat - fee_with_change`, locking the actual fee to the underestimated value. [3](#0-2) 

The final `SignableTransaction` contains the OP_RETURN output, while `needed_fee` remains based on the smaller transaction. [4](#0-3) 

### Impact Explanation

An attacker or integrator-supplied flow that can specify transaction data obtains up to 80 bytes of transaction space without paying the corresponding fee. More importantly, a transaction constructed at the minimum relay rate can fall below the relay minimum once the omitted OP_RETURN output is included. The signed transaction may fail to propagate or confirm, temporarily stalling the spend despite consuming/signing the selected inputs.

### Likelihood Explanation

The bug is deterministic whenever `data` and `change` are both supplied. The public test suite already exercises `SignableTransaction::new` with `Some(data)` and change, but only checks the OP_RETURN contents, not the resulting feerate. [5](#0-4) 

### Recommendation

Include the serialized OP_RETURN output in both fee-estimation calls. Prefer constructing the complete output vector—including payments, OP_RETURN data, and a representative change output—before calculating weight. Also compare the required minimum relay fee against the final transaction’s actual vsize, not the underestimated `vbytes`.

### Proof of Concept

```rust
use bitcoin_serai::{
  bitcoin::Transaction,
  wallet::SignableTransaction,
};

// `output` is a previously scanned ReceivedOutput and `change` is a valid
// P2TR change script.
let signable = SignableTransaction::new(
  vec![output],
  &[],
  Some(change),
  Some(vec![0; 80]),
  1, // 1 sat/vbyte, the minimum relay-rate boundary used by this code
).unwrap();

// Because the OP_RETURN output was omitted from `calculate_weight_vbytes`,
// this is the fee for a transaction without the data output.
let underestimated_fee = signable.needed_fee();

// After signing, the actual transaction contains the OP_RETURN output and
// therefore has a substantially larger vsize.
let signed_tx: Transaction = sign_transaction(signable.clone());
assert_eq!(signable.fee(), underestimated_fee);
assert!(signed_tx.vsize() as u64 > underestimated_fee);

// Consequently, the effective feerate is below 1 sat/vbyte even though the
// constructor accepted fee_per_vbyte = 1 and performed its minimum-fee check.
```

The relevant defect is that the OP_RETURN output is pushed into `tx_outs` before the estimate, yet the estimator is called with `payments` rather than `tx_outs`. [6](#0-5)
