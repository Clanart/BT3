## Title
Payout attribution relies on an unauthenticated OP_RETURN field, letting anyone re-target reimbursement credit for a withdrawal to an arbitrary operator - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`)

### Summary
Clementine attributes "who fronted a withdrawal" purely by reading an unsigned OP_RETURN output from the confirmed `payout_tx` on Bitcoin, and this attribution directly drives which operator's automated reimbursement/kickoff flow is triggered. Because the withdrawal-owner's signature only commits to the input and the matching-index output (`SIGHASH_SINGLE | ANYONECANPAY`), the OP_RETURN output that carries the "paying operator's" xonly public key is *not* covered by any signature and can be freely substituted by whoever finally assembles/broadcasts the transaction — breaking the binding between "the operator credited" and "the party that actually paid."

### Finding Description
`create_payout_txhandler` builds the payout transaction with the user's withdrawal UTXO as input 0 (`SpendPath::KeySpend`) and appends an OP_RETURN output carrying `operator_xonly_pk`: [1](#0-0) 

The only cryptographic check performed on this transaction is that the user's signature is valid for `SinglePlusAnyoneCanPay` over input 0: [2](#0-1) 

`SinglePlusAnyoneCanPay` intentionally only commits to the signed input and the *output at the same index* (output 0, the user's payout). This is confirmed by the sighash construction, which uses `Prevouts::One` (single-input commitment) for this sighash flavor: [3](#0-2) 

Consequently, the anchor output (index 1) and — critically — the OP_RETURN output carrying the operator's xonly public key (index 2) are **not** covered by the withdrawal signature. Anyone who has the presigned withdrawal input/output pair (given to operators off-chain per the withdrawal RPC, or observable once the payout tx is broadcast/still unconfirmed in the mempool) can assemble a competing transaction: reuse input 0 + output 0 verbatim (satisfying the signature check), add their own funding input(s) for the anchor/fee, and put a **different** operator's xonly public key in the OP_RETURN.

Once confirmed, `update_finalized_payouts` parses this attacker-controlled OP_RETURN and stores whatever xonly_pk it contains as `payout_payer_operator_xonly_pk` in the DB, with no check that this pubkey belongs to whoever actually funded the transaction: [4](#0-3) 

This value is exactly what drives the automated, unattended reimbursement pipeline. `PayoutCheckerTask` picks up "unhandled payouts" solely filtered by `payout_payer_operator_xonly_pk = self.operator.signer.xonly_public_key` and immediately calls `handle_finalized_payout`, which advances the kickoff/round state machine toward reimbursement: [5](#0-4) 

`validate_payer_is_operator` (used by `get_reimbursement_txs`) and `is_kickoff_malicious` (used by verifiers to decide whether to challenge a kickoff) both trust this same DB-recorded OP_RETURN pubkey as ground truth for "the payer is the operator": [6](#0-5) [7](#0-6) 

Because none of these checks verify that the named operator actually signed/broadcast/funded the transaction (only that the bytes in an unauthenticated OP_RETURN match), the reimbursement chain is triggered — and verifiers will not flag the kickoff as malicious — for an operator who never paid anything.

### Impact Explanation
This breaks the binding "the operator credited (and thus reimbursed from the vault) versus the party that actually paid the withdrawal." A party who fronts the user's withdrawal (paying the fee and the output amount) can put a different, unwitting operator's xonly_pk into the free OP_RETURN slot. That operator's own automation (`PayoutCheckerTask` → `handle_finalized_payout` → kickoff → `reimburse_tx`) will treat the payout as its own and proceed to claim the bridge amount from `MoveToVaultTx` via `create_reimburse_txhandler`, without verifiers challenging it (since `is_kickoff_malicious` only compares OP_RETURN pubkey to kickoff pubkey, both attacker-controlled/consistent): [8](#0-7) 

This is a "Critical" impact per the specified taxonomy: an operator is reimbursed for a payout it never funded (and, symmetrically, the operator that actually intended to front the withdrawal for its own credit can have its transaction pre-empted/replaced in the mempool by a competing spend of the same UTXO, permanently losing its reimbursement right for that withdrawal).

### Likelihood Explanation
The attack requires no privileged role, key compromise, or protocol secret — only visibility of the presigned withdrawal input/output/signature (available to any operator via the normal withdrawal RPC path, or observable pre-confirmation in the mempool) and the ability to fund/broadcast a Bitcoin transaction with a higher fee (a normal RBF race). Any registered operator (least-privileged actor already in the system) can perform this to redirect credit to itself instead of the operator whose data it intercepted, making this readily reachable in the deployed configuration.

### Recommendation
Do not derive payer attribution from an unauthenticated OP_RETURN field. Either (a) commit the operator's xonly_pk into the signed part of the transaction (e.g., have the user's signature use `SIGHASH_ALL` variants that cover the OP_RETURN output, or otherwise cryptographically bind the operator identity to the specific broadcast transaction), or (b) require an operator-signed attestation (separate from the OP_RETURN bytes) proving that operator actually authored/funded that specific txid before treating it as a "handled" payout in `update_finalized_payouts`, `validate_payer_is_operator`, and `is_kickoff_malicious`.

### Proof of Concept
1. Operator A obtains the user's `WithdrawParams` (signature over input 0 / output 0 with `SinglePlusAnyoneCanPay`) and begins constructing/broadcasting its `payout_tx` (input 0 = withdrawal UTXO + user sig, output 0 = user payout, output 2 = OP_RETURN with A's xonly_pk), per `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`).
2. Operator B observes this transaction (still unconfirmed) or independently obtains the same `WithdrawParams`, and constructs its own transaction reusing input 0 and output 0 verbatim (both are covered by the user's `SinglePlusAnyoneCanPay` signature, so it remains valid), but funds the fee itself and sets output 2's OP_RETURN to B's own xonly_pk, then broadcasts with a higher fee (RBF).
3. B's transaction confirms. `update_finalized_payouts` (`core/src/verifier.rs:2312-2342`) parses B's xonly_pk from the OP_RETURN and records it as `payout_payer_operator_xonly_pk`.
4. B's own `PayoutCheckerTask` (`core/src/task/payout_checker.rs:41-79`) picks up the unhandled payout matching its key and drives `handle_finalized_payout` → kickoff → `reimburse_tx`, claiming the bridge amount from the vault — despite A being the operator that intended (or actually attempted) to front the withdrawal.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
