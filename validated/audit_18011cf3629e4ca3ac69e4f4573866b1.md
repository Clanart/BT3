### Title
Hardcoded `_filled` mapping storage-slot assumption in cross-chain order cancellation enables false proof acceptance / double settlement - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._calculateCommitmentSlotHash` hardcodes the storage slot of the `_filled` mapping as slot `2` via the constant `FILLED_SLOT_BIG_ENDIAN_BYTES`, and this value is used to build the Hyperbridge `DispatchGet` storage-proof key that `_cancelFromSource` relies on to prove an order was never filled on the destination chain. [1](#0-0) [2](#0-1) 

### Finding Description
The same-chain, refund-vs-fill invariant for cross-chain orders is enforced entirely by reading a specific EVM storage slot on the *destination* chain via an ISMP `GET` request, rather than by any authenticated contract call: [3](#0-2) 

The key is built from a compile-time constant (`FILLED_SLOT_BIG_ENDIAN_BYTES = 0x…02`) that encodes an assumption about exactly where `_filled` lives in the destination contract's storage layout: [4](#0-3) 

The response handler trusts the proven value at that slot unconditionally — if the value is empty it treats the order as unfilled and immediately refunds escrow: [5](#0-4) 

This is structurally the same class of bug as the EIP‑4758 report: the code relies on a low-level assumption ("selfdestruct destroys the contract" / "the `_filled` mapping is always at slot 2") to enforce a business invariant ("a cancelled sale can no longer be bought" / "a filled order can never be refunded"). The invariant is not re-derived from an authenticated, versioned source of truth — it is baked into a raw storage offset. The gateway contracts are explicitly upgradeable (they support a governance-driven `UpgradeContract` request kind that repoints the ERC‑1967 proxy and runs migration calldata): [6](#0-5) 

Any future implementation that reorders base contracts, inserts a new state variable ahead of `_filled` in the linearized storage layout (a very easy migration mistake, exactly the kind that upgradeable-proxy audits exist to catch), or is deployed with a slightly different inheritance chain than the one `FILLED_SLOT_BIG_ENDIAN_BYTES` was derived from, will cause the source-chain GET proof to authenticate the *wrong* storage cell. Because Hyperbridge's storage-proof verification only proves that a value exists at a given key at a given height — it has no semantic knowledge of what "slot 2" is supposed to mean — a perfectly valid, honestly-relayed storage proof will be accepted for a slot that no longer corresponds to `_filled`. If that unrelated slot happens to read as empty even though the order was genuinely filled (the overwhelmingly common case, since most other slots default to zero/empty), `onGetResponse` will pass its only guard (`incoming.response.values[0].value.length != 0 → revert Filled()`) and call `_withdraw(..., true, true)` to refund the source-chain escrow — even though the solver has already delivered output tokens to the user on the destination chain.

Unlike the ordinary double-spend paths I traced in this contract (which are correctly guarded by the `_orders[commitment][token]` escrow-balance decrement reverting on double withdrawal), this path is a *state-proof authenticity* failure, not an accounting failure: the storage-proof mechanism itself is being pointed at the wrong location, so the accounting guard downstream never sees a conflict because the fill and the refund are, from the proof's perspective, reading two unrelated pieces of storage.

### Impact Explanation
If the assumed slot ever diverges from the real one (upgrade, refactor, or a redeployment with different base-contract ordering), an attacker (the order's own user, who is the only party authorized to call `_cancelFromSource`) can collect the destination fill from a solver *and* reclaim the full source-side escrow, resulting in direct fund loss for the protocol/solver and a false-state acceptance of an "unfilled" storage proof for an order that was in fact filled. This matches the bounty's explicit "false proof/state acceptance" and "double-claim/double-settlement" categories, and requires no malicious relayer, prover, or governance actor — only an honest proof of the wrong slot.

### Likelihood Explanation
This is not exploitable under the current, single, matched deployment of `IntentsBase`/`ExtrinsicIntents` as long as the slot constant and the actual compiled layout agree (the presence of a dedicated foundry test referencing `FILLED_SLOT` suggests the current build is self-consistent). The risk surfaces specifically at the moment of an implementation upgrade or a differently-inherited deployment (e.g., the parallel `evm/tron/contracts/apps/IntentGatewayV2.sol` variant, which duplicates the same hardcoded-slot pattern independently) — a routine, expected operational event for this protocol given it ships upgrade tooling as a first-class cross-chain message. I was not able to fully enumerate every base contract in the actual linearized storage layout of the deployed proxy implementation within this pass, so I cannot state with certainty that the slot is *currently* mismatched; the vulnerability is the fragility of the design (an unchecked, unverified hardcoded slot number used as a cross-chain trust anchor) rather than a proven-live storage collision today.

### Recommendation
Do not authenticate cross-chain settlement state via a hardcoded raw storage slot. Either (a) expose the fill/refund status through a dedicated, ABI-stable view/query mechanism that is verified structurally rather than by slot offset, (b) add a storage-layout invariant check (e.g., a deploy-time or upgrade-time assertion, or Foundry's storage-layout diff tooling enforced in CI) that fails loudly if `_filled`'s slot ever moves, or (c) bind the GET-proof key derivation to a value that is recomputed from the actual compiled layout at build time rather than duplicated as a separate constant in multiple files (`IntentsBase.sol` and the Tron `IntentGatewayV2.sol`), which today can independently drift out of sync.

### Proof of Concept
1. Deploy an upgraded/alternate `ExtrinsicIntents`/`IntrinsicIntents` implementation (via the supported `RequestKind.UpgradeContract` governance path, or via a differently-ordered Tron deployment) where an added base-contract storage variable shifts `_filled` off slot `2`.
2. User places a cross-chain order and a solver fills it on the destination chain, receiving `_filled[commitment] = solver` at its *real* (shifted) slot.
3. After `order.deadline`, the user calls `cancelOrder` on the source chain (`_cancelFromSource`), which dispatches a `DispatchGet` keyed on `_calculateCommitmentSlotHash(commitment)` — i.e., the stale slot `2`.
4. A relayer honestly proves the (empty) value at slot `2` on the destination chain at the required height.
5. `onGetResponse` sees `value.length == 0`, does not revert, and calls `_withdraw(body, true, true)`, refunding the full escrow to the user on the source chain — while the solver already paid out on the destination chain, resulting in a double payment funded by the protocol/solver.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    /**
     * @dev Handles the response to a Hyperbridge GET request dispatched during
     * `_cancelFromSource`. Verifies that the `_filled` storage slot on the destination
     * chain is empty (meaning the order was never filled), then refunds the escrowed
     * tokens to the original user. Reverts with `Filled` if the slot is non-empty.
     *
     * @param incoming The incoming GET response from Hyperbridge containing the storage proof.
     */
    function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
        if (incoming.response.values[0].value.length != 0) revert Filled();

        WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
        _withdraw(body, true, true);
    }
