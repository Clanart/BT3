## Title
Non-unique `FileChange.id` for renamed/copied files causes checkbox-inclusion and diff-selection state to be silently applied to the wrong file - (File: `app/src/models/status.ts`)

### Summary
`FileChange` builds its `id` by naively concatenating status kind, `path`, and `oldPath` with a bare `+` separator, with no escaping of `+` characters that may legitimately appear in file/directory names: [1](#0-0) 

Because this delimiter is not unique, two distinct renamed/copied files can produce the exact same `id` string. That `id` is the sole key used throughout the Changes list to look up selection state, resolve "which file was clicked/checked," and merge diff-selection state across status refreshes, so a collision causes the app to silently associate one file's include/exclude or partial-line-selection state with a different file.

### Finding Description
`FileChange`'s constructor computes:
```
this.id = `${status.kind}+${path}+${status.oldPath}`
```
for `Renamed`/`Copied` files. Since `path` and `oldPath` are arbitrary, attacker-controlled repository paths, the `+` separator is not collision-free. For example:
- File A: `path = "dir/a+b"`, `oldPath = "old/c"` → `id = "Renamed+dir/a+b+old/c"`
- File B: `path = "dir/a"`, `oldPath = "old/b+c"` → `id = "Renamed+dir/a+old/b+c"`

Wait — concretely, choosing `path="a+b", oldPath="c"` and `path="a", oldPath="b+c"` both yield `id = "Renamed+a+b+c"`.

This `id` is the single key used to:
- Deduplicate/index files in `WorkingDirectoryStatus`, where the last file with a given `id` silently overwrites earlier index entries: [2](#0-1) 
- Merge/preserve diff selection state across status polls in `updateChangedFiles`, via `filesByID.get(file.id)` — a colliding `id` causes a completely unrelated file's prior line-selection state (`selection.withSelectableLines`, partial line sets) to be transplanted onto the new file: [3](#0-2) 
- Toggle the "include in commit" checkbox for a set of files, using `new Set<string>(files.map(f => f.id))` and `modifiedIds.has(f.id)` — if two different files share an `id`, checking/unchecking one silently checks/unchecks the other as well: [4](#0-3) 

No code path validates uniqueness of `id` or escapes the `+` delimiter, so this is an unguarded invariant violation analogous to the Cosmos SDK "collision of formatted coins" bug — here, two structurally distinct file changes collapse into the same rendering/identity key.

### Impact Explanation
An attacker who controls a cloned/fetched repository can name files/directories so that a routine rename/move (e.g. renaming a parent folder that contains two crafted files) produces two `Renamed`/`Copied` entries whose `path`+`oldPath` combination collides under the `+` concatenation scheme. Once that happens:
- The victim's per-file "include in commit" checkbox state can be silently applied to the wrong file (staging or excluding content the user did not intend).
- Partial line-selection state (which lines of a diff are staged) computed for one file can be reused for a completely different file's diff, since selection is stored purely as line-index sets and reused across the colliding `id` without content validation.

This results in silent corruption of what the user actually stages/commits — the user believes they excluded or partially staged one file, but the app applies that decision to a different file, which matches the "silent corruption of what the user commits" impact category.

### Likelihood Explanation
Triggering the collision requires only that the attacker control file/directory names in the repository (fully within their control for any repo they publish/fetch) and that the victim perform an ordinary rename/move operation (e.g., `git mv` of a folder, or an auto-detected rename during merge/checkout) touching two attacker-named paths — no elevated privileges, physical access, or social engineering beyond normal repository interaction is needed.

### Recommendation
Replace the ambiguous `+`-concatenated `id` with a delimiter-safe encoding (e.g., JSON-encode `[status.kind, path, oldPath]`, or use a hash of the individual fields, or a separator guaranteed not to appear in paths such as a NUL character or length-prefixed encoding) in the `FileChange` constructor at `app/src/models/status.ts`, and add a runtime assertion/dedup check when building `WorkingDirectoryStatus.fileIxById` to detect and surface `id` collisions instead of silently overwriting entries.

### Proof of Concept
1. In a repository, create two renamed/copied working-directory changes such that:
   - File A ends with `path = "a+b"`, `oldPath = "c"`
   - File B ends with `path = "a"`, `oldPath = "b+c"`
   (e.g., by renaming a directory containing appropriately named files in one `git mv` operation so both appear as `Renamed` entries in a single `git status` pass.)
2. Both produce `FileChange.id === "Renamed+a+b+c"` per the constructor logic at [5](#0-4) .
3. Partially stage File A (select a subset of lines) then in Desktop's Changes list uncheck/discard or re-select File B's checkbox; because `WorkingDirectoryStatus.fileIxById` and `_changeFileIncluded`'s `modifiedIds` Set key on `id`, the operation intended for File B is applied to File A's stored selection state as well, causing the eventual commit/stage to differ from what the user selected in the UI.

   * @param files The list of changes in the repository's working directory.

   *                   NOTE: we need to track this separately to the file list selection

    public readonly includeAll: boolean | null = true

    files.forEach((f, ix) => this.fileIxById.set(f.id, ix))
  }

  /**
   * Update the include state of all files in the working directory
   */
  public withIncludeAllFiles(includeAll: boolean): WorkingDirectoryStatus {
    const newFiles = this.files.map(f => f.withIncludeAll(includeAll))
    return new WorkingDirectoryStatus(newFiles, includeAll)
  }

  /** Find the file with the given ID. */
  public findFileWithID(id: string): WorkingDirectoryFileChange | null {
    const ix = this.fileIxById.get(id)
    return ix !== undefined ? this.files[ix] || null : null
  }

  /** Find the index of the file with the given ID. Returns -1 if not found */
  public findFileIndexByID(id: string): number {
    const ix = this.fileIxById.get(id)
    return ix !== undefined ? ix : -1
  }

  public _changeFileIncluded(
    repository: Repository,
    file:
      | WorkingDirectoryFileChange
      | ReadonlyArray<WorkingDirectoryFileChange>,
    include: boolean
  ): Promise<void> {
    const files = Array.isArray(file) ? file : [file]
    const modifiedIds = new Set<string>(files.map(f => f.id))

    this.repositoryStateCache.updateChangesState(repository, state => {
      const workingDirectory = WorkingDirectoryStatus.fromFiles(
        state.workingDirectory.files.map(f =>
          modifiedIds.has(f.id) ? f.withIncludeAll(include) : f
        )
      )

      return { workingDirectory }
    })

    this.emitUpdate()
    return Promise.resolve()
  }
