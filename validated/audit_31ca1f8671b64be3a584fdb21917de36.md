### Title
OP_RETURN `data` output is omitted from fee/weight accounting, causing the change output to be over-allocated and the transaction to underpay its target fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is a withdrawal/transfer that updates the per-item state but never decrements the shared accounting total (`numTokensReservedForVesting`), leaving a stale global ledger. The Serai analog lives in `SignableTransaction::new`: a caller-supplied OP_RETURN `data` output is pushed into the real transaction's `tx_outs`, yet the weight/vbytes used to compute `needed_fee` — and therefore the change amount — is computed only over `payments`, silently excluding the `data` output from the accounting.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight calculation:

- `tx_outs` gains the OP_RETURN output at `send.rs:194-202`, adding a real serialized output (up to 80 bytes of data plus output overhead) to the final transaction.
- The weight calculation at `send.rs:204` calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds its dummy transaction from `payments` alone (`send.rs:85-93`). The `data` output that was already pushed into `tx_outs` is never represented in the measured weight.
- `needed_fee` is then set from this under-counted `vbytes` at `send.rs:206`, and the minimum-relay check at `send.rs:211` is likewise evaluated against the under-counted size.
- When a change output is created, its value is `input_sat - (payment_sat + fee_with_change)` (`send.rs:228-230`), where `fee_with_change` is also derived from the data-excluded `vbytes_with_change` (`send.rs:225-227`).

The result mirrors the report exactly: value is moved out of the inputs (an extra output is emitted) while the shared accounting figure — the required fee derived from serialized size — is not updated to reflect it. The unaccounted bytes are absorbed into the change output instead of the fee, so the actual fee `sum(inputs) - sum(outputs)` (`fee()`, `send.rs:138-141`) is strictly less than the intended `fee_per_vbyte * actual_vsize`.

### Impact Explanation
An unprivileged party who can influence the `data` argument (e.g., embedding an 80-byte OP_RETURN, the maximum allowed by the `send.rs:171-173` check) causes the produced transaction to underpay relative to the specified `fee_per_vbyte`. In the worst case the effective feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` or the mempool minimum, so the signed transaction — which the signing set produces and which carries all inputs' value — is rejected for relay/mining. The funds committed as inputs are then locked pending a new signing round: value is spent by the transaction but the transaction cannot confirm, i.e., funds accounted as outgoing are not actually spendable/settled. Even when relay succeeds, every signer's view of the fee (`needed_fee`) is inconsistent with the true feerate, matching the report's "inconsistent data / improper allocation" consequence.

### Likelihood Explanation
Triggering requires only that `data` be `Some(_)` when constructing a `SignableTransaction` — a public constructor argument, not requiring malicious validators or leaked keys. The miscalculation is deterministic: the OP_RETURN output is never included in `calculate_weight_vbytes`, so any non-empty `data` shifts the true vsize upward while `needed_fee` stays fixed. Whether the transaction becomes unrelayable depends on margins, but the accounting invariant (actual fee ≥ `fee_per_vbyte * vsize`) is violated for every non-empty `data` payload.

### Recommendation
Include the `data`/OP_RETURN output in the transaction template used by `calculate_weight_vbytes` (e.g., append a `TxOut` of the correct serialized size for the OP_RETURN before computing `weight`/`vbytes`), so `needed_fee` and the change deduction at `send.rs:228` reflect the full transaction size — analogous to decrementing `numTokensReservedForVesting` for the amount actually transferred.

### Proof of Concept
```rust
// Pseudo-PoC against networks/bitcoin/src/wallet/send.rs
let tx = SignableTransaction::new(
    vec![output],                       // one received input
    &payments,                          // payments summing below input value
    Some(change_script),                // change address
    Some(vec![0xaa; 80]),               // max-size OP_RETURN data
    fee_per_vbyte,
).unwrap();

// The OP_RETURN output exists on the real tx:
assert!(tx.tx.output.iter().any(|o| o.script_pubkey.is_op_return()));

// But needed_fee was computed on a tx WITHOUT the OP_RETURN output,
// so the actual fee is less than fee_per_vbyte * actual vsize:
let actual_fee = tx.fee();              // sum(inputs) - sum(outputs)
let actual_vsize = tx.tx.vsize() as u64;
assert!(actual_fee < fee_per_vbyte * actual_vsize);   // underpaid fee
// The difference was absorbed into the change output (over-allocation).
```

Note on certainty: this finding rests on the confirmed fact that `calculate_weight_vbytes` at `send.rs:204`/`225` receives `payments` only while the OP_RETURN output is pushed earlier at `send.rs:194-202`. I did not fully trace whether upstream callers (e.g., `processor/src/networks/bitcoin.rs::make_signable_transaction`, which passes `None` for `data`) ever expose a non-None `data` value derived from untrusted input in production flows; if `data` is always `None` in practice, the bug is latent in the library API rather than reachable on the deployed path, which would lower its practical severity.
