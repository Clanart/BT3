### Title
Scanner reports immature coinbase outputs as spendable, causing transactions spending them to be rejected and funds to stall - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Curve report's bug class is a stored/recorded balance that diverges from the actually spendable balance, locking user funds. In Serai, `Scanner::scan_block` iterates over *every* transaction in `block.txdata`, including `txdata[0]` — the coinbase transaction — and emits `ReceivedOutput`s for coinbase payouts to a registered script_pubkey. Bitcoin consensus rules make coinbase outputs unspendable for 100 blocks, so the scanner reports funds as received that are not yet spendable. Any downstream consumer that uses `scan_block`'s results directly as transaction inputs will construct a transaction the network rejects.

### Finding Description
`Scanner::scan_block` loops over all of `block.txdata` without excluding the coinbase:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```
(networks/bitcoin/src/wallet/mod.rs:221-227)

`scan_transaction` (mod.rs:199-214) matches purely on `output.script_pubkey` membership in `self.scripts`, with no maturity check possible at that layer since `TxOut` carries no coinbase flag — only the *position* (`txdata[0]`) marks a coinbase. The doc comment concedes the hazard: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" (mod.rs:216-220). There is no `is_coinbase` flag or maturity field on `ReceivedOutput` (mod.rs:89-97), so a caller cannot distinguish the immature output from a normal one after the fact — only by re-checking the outpoint's transaction against `txdata[0]`.

This is the direct analog of the Curve finding: a recorded balance (`stored_balances` there, the emitted `ReceivedOutput` set here) that does not reflect the spendable balance. Withdrawal of a rebased amount reverts on-chain there; spending an immature coinbase fails consensus validation (`bad-txns-premature-spend-of-coinbase`) here. In both cases the recorded state and the spendable state disagree, and the mismatch surfaces only at spend time.

Reachability: any miner — an unprivileged third party — can include a payout to the multisig's P2TR script_pubkey in their coinbase (e.g., a pool payout, or a deliberate dust/griefing payment to a known vault address). The scanner then emits a `ReceivedOutput` indistinguishable from a spendable one. When that output is consumed as an input to `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256), which performs input/fee/dust accounting with no maturity awareness, the resulting signed transaction is invalid until 100 confirmations elapse.

### Impact Explanation
Funds reported received that are not spendable: the coinbase output is counted toward the vault's usable inputs immediately. A transaction built over it is rejected by every node, and if the scheduler retries with the same input set, payments stall for up to ~100 blocks. Unlike a low-fee rejection, no amount of fee bumping fixes it. If the offending block is also orphaned before maturity, the recorded output never becomes spendable at all while still having been emitted as received. On the Curve scale (funds stuck, no recovery path) this maps to a Medium: the freeze is bounded by maturity under normal conditions, but permanently unrecoverable if the coinbase's block is reorged out.

### Likelihood Explanation
Medium-low in frequency, trivial in cost. Any miner or mining pool can pay a registered vault script in a coinbase; pool payout addresses in particular commonly receive coinbase outputs as routine operation. No threshold collusion, malicious node, or leaked key is required — only an ordinary on-chain transaction to a public address.

### Recommendation
Either drop `block.txdata[0]` inside `scan_block` (`for tx in &block.txdata[1..]`), or extend `ReceivedOutput`/`scan_transaction` callers with the block context needed to flag coinbase outputs and enforce a 100-block maturity delay before they may be selected as inputs in `SignableTransaction::new`. If coinbase outputs must be reported, carry a maturity height on `ReceivedOutput` so downstream input selection can exclude immature ones rather than discovering it via a rejected broadcast.

### Proof of Concept
1. A miner (or a test harness using `bitcoin::Block` construction) creates a block whose coinbase transaction pays `p2tr_script_buf(scanner.key)` — the same script `Scanner::new` registers at mod.rs:164.
2. `scanner.scan_block(&block)` returns a `ReceivedOutput` for that coinbase payout; `res` is non-empty and the output is indistinguishable from one produced by a normal transaction (mod.rs:221-227).
3. `SignableTransaction::new(vec![received], &payments, None, None, fee_per_vbyte)` succeeds, since it only validates dust/fee/weight (send.rs:150-256).
4. Broadcasting the signed transaction fails consensus validation with premature-spend-of-coinbase; every retry over the same `ReceivedOutput` fails identically until 100 confirmations. The vault's bookkeeping already counted the funds as received.

Caveat: I verified the root cause in `scan_block`/`scan_transaction`/`SignableTransaction` within the in-scope `networks/bitcoin/src` files. I was not able to confirm in the final iteration whether the out-of-scope `processor` crate performs the documented "post-processing pass" before feeding outputs back as inputs; if it does filter `txdata[0]`, the exposure is limited to direct `bitcoin-serai` consumers of `scan_block`, which remains a real defect in the API but reduces end-to-end exploitability.
