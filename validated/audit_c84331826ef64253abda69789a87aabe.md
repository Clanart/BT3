### Title
`ArbWomUp3.incentiveDeposit` double-count correction recomputed from a mutable balance the user controls, enabling repeated tier-bracket rewards - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount()` subtracts `calDoubledCounted(_account)` to avoid re-rewarding a tier bracket a user was already paid for, but `calDoubledCounted()` derives the "already rewarded" amount purely from the live, mutable value `mWomSV.getUserTotalLocked(_account)` rather than from a persisted record. Because that value falls whenever the user calls `mWomSV.startUnlock`, an attacker can shrink their recorded locked balance between calls to `incentiveDeposit` and claim MGP rewards for the same WOM tier bracket multiple times.

### Finding Description
In `wombat/ArbWomUp3.sol`, `incentiveDeposit` (lines 88-105) computes `rewardToSend = getRewardAmount(_amount, msg.sender, _mode == 2)` before performing the deposit/lock. For `_mode == 2` (lock path), `getRewardAmount` (lines 107-129) computes: [1](#0-0) 

`accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)` and then computes the tiered reward for the full `accumulated` value, subtracting `calDoubledCounted(_account)` — which recomputes the tiered reward for the *current* `mWomSV.getUserTotalLocked(_account)` alone (lines 131-144) — to avoid re-paying for the portion the user was already rewarded for in prior deposits.

The flaw is that `mWomSV.getUserTotalLocked(_user)` is not a monotonically increasing ledger of "amount ever rewarded"; it is `_amountInMasterMagpie - getUserAmountInCoolDown(_user)` [2](#0-1) , and calling `mWomSV.startUnlock(_amountToCoolDown)` immediately moves locked balance into cooldown, reducing `getUserTotalLocked` by `_amountToCoolDown` [3](#0-2) . `startUnlock` is a public, unprivileged function callable directly by the token holder.

Exploit flow:
1. Attacker calls `incentiveDeposit(100, ..., _mode=2)`. At this point `getUserTotalLocked` is 0, so `accumulated = 100`, full first-tier reward is paid, and `_deposit` locks ~100 mWOM in `mWomSV`, raising `getUserTotalLocked` to ~100.
2. Attacker calls `mWomSV.startUnlock(100)`, moving the entire locked balance into cooldown. `getUserTotalLocked(attacker)` drops back to 0, while the tokens are simply sitting in cooldown (still owned/controllable by the attacker, eventually withdrawable).
3. Attacker calls `incentiveDeposit(100, ..., _mode=2)` again. `getRewardAmount` now computes `accumulated = 100 + 0 = 100` (same bracket), and `calDoubledCounted(_account)` reads the now-zero `getUserTotalLocked`, returning 0. The full first-tier reward is paid out again for a bracket the attacker already fully claimed in step 1.
4. This can be repeated indefinitely (subject to `coolDownInSecs` and available `maxSlot` unlock slots, and the `mgpleft` cap), draining the contract's MGP balance via `vlMGP.lockFor(rewardToSend, msg.sender)`.

None of the existing guards prevent this: `nonReentrant`/`whenNotPaused` on `incentiveDeposit` protect against reentrancy/pausing only, not against sequential legitimate transactions; `bracketRewarded` mapping exists but is explicitly marked "not in use" [4](#0-3)  and is never read or written anywhere in the contract, so there is no persisted, monotonic record of rewards already paid per user.

### Impact Explanation
This is a direct theft-of-funds vector against the reward pool: an attacker can repeatedly re-claim MGP rewards for the same WOM/mWOM tier bracket by cycling lock → startUnlock → lock again, draining `mgp` tokens held by `ArbWomUp3` via `vlMGP.lockFor`. The reward payout is capped only by `IERC20(mgp).balanceOf(address(this))` (line 127-128), so the attacker can extract the entire MGP incentive balance intended for all legitimate participants, matching "Critical - Direct theft of user funds."

### Likelihood Explanation
Low capital is required — the attacker only needs enough WOM to reach the first non-zero reward tier, and can reuse the same mWOM/WOM repeatedly since `startUnlock` merely moves the balance to cooldown rather than removing it from the attacker's control. The only friction is `coolDownInSecs` (time between unlock cycles) and `maxSlot` (limited number of concurrent cooldown slots), but these only throttle the rate of exploitation, not prevent it — the attacker can still repeatedly harvest rewards over time, or use multiple unlock slots in parallel, with unlimited repeatability until the MGP balance is exhausted. No special privileges are needed.

### Recommendation
Replace the live-balance-derived double-count correction with a persisted, monotonically increasing per-user ledger of MGP (or WOM-tier-equivalent) rewards already paid — e.g., actually use the existing (currently unused) `bracketRewarded` mapping: track the highest `accumulated` value ever used to compute a reward for each account, and only reward the tiered amount corresponding to the increase over that stored high-water mark, updating it every call. Do not derive "amount already rewarded" from `mWomSV.getUserTotalLocked`, since that value is mutable by the user via `startUnlock`.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `mWOM`, mock `MasterMagpie`, `vlMGP`, and a mock `smartWomConvert`/`IConverter`. Fund `ArbWomUp3` with a large MGP balance and configure `rewardTier = [0, 100e18, 200e18]`, `rewardMultiplier` with nonzero values via `setMultiplier`.
2. Mint WOM to attacker EOA; approve `ArbWomUp3`.
3. Call `incentiveDeposit(100e18, 0, false, 2)` as attacker. Assert `vlMGP` balance locked for attacker increases by `R1` (expected first-tier reward), and record MGP balance of `ArbWomUp3` after (`B1`).
4. Call `mWomSV.startUnlock(mWomSV.getUserTotalLocked(attacker))` as attacker, confirm `mWomSV.getUserTotalLocked(attacker)` returns 0 afterward while `getUserAmountInCoolDown(attacker)` equals the locked amount.
5. Call `incentiveDeposit(100e18, 0, false, 2)` again as attacker (fresh WOM approved/transferred). Assert `rewardToSend` computed equals `R1` again (i.e., `calDoubledCounted` returned 0 despite the attacker having already been rewarded for that bracket), and that `ArbWomUp3`'s MGP balance drops by `R1` a second time for the same bracket.
6. Assert cumulative reward paid to attacker (`2*R1`) exceeds what a single monotonic reward ledger would allow for depositing `200e18` total WOM once — demonstrating the double-count invariant is broken.
