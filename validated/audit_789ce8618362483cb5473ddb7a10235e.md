### Title
Clone hardens itself against path traversal but explicitly disables Git's upstream submodule RCE protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` runs `git clone --recursive` with the option `GIT_CLONE_PROTECTION_ACTIVE: 'false'` merged into the environment, which turns off Git's own defense-in-depth check against malicious submodule paths that collide with `.git` during a recursive clone.

### Finding Description
The report's underlying pattern is "the caller trusts an operation as safe/successful without the check that the underlying primitive itself needs in order to actually be safe." Here, Desktop's `clone` function builds the recursive clone environment as: [2](#0-1) 
and always appends `--recursive` to the clone args: [3](#0-2) 

Git's own hardening (the fix family for the "clone can lead to arbitrary code execution" class of bugs) is gated behind a "protection active" check that specifically defends against submodule names that, on a given filesystem, resolve to the same path as `.git` (via case-folding, Unicode NFC/NFD normalization, or short-name aliasing on Windows), which would let the attacker overwrite hook scripts inside the freshly cloned repository. By explicitly forcing this environment flag to `'false'` on every clone (including untrusted, attacker-supplied clone URLs), Desktop is deliberately opting the whole `--recursive` clone path out of that specific Git-side safety check, on every platform, for every repository the user clones.

Notably, elsewhere in the same file Desktop *does* implement its own bespoke protection against a different but related attacker primitive — path traversal in the destination clone path — via `isClonePathSensitive`: [4](#0-3) 
This shows the team is aware of and defends against attacker-controlled clone inputs causing writes outside the intended directory, but the submodule-colliding-with-`.git` primitive (which is the more directly RCE-capable one, since it can plant a hook that executes on the very next `git` invocation in that repo) is explicitly turned off rather than left at Git's default (enabled).

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE` corresponds to the check that rejects submodule/worktree paths colliding with `.git` (the mechanism behind Git's CVE-2024-3200x series fixes), disabling it means: an attacker who controls a repository (or a submodule referenced by it) that a Desktop user clones with "Clone repository" can craft a submodule name/path that, on a case-insensitive or Unicode-normalizing filesystem (default on macOS APFS and Windows NTFS), resolves into the repo's `.git` directory. This lets the attacker plant or overwrite files such as `.git/hooks/post-checkout` (or similar) during the clone, which Desktop will then execute automatically on a subsequent Git operation on that same repository — full local code execution, achieved purely by the victim cloning an attacker-controlled repository through the normal Desktop UI. This matches the required threat model: an unprivileged Desktop user, attacker controls only a cloned/fetched repository, resulting in code execution.

### Likelihood Explanation
Likelihood depends entirely on what `GIT_CLONE_PROTECTION_ACTIVE=false` actually disables in the vendored Git binary Desktop ships (dugite's Git build). I could not access Git's C source in this index to confirm the exact semantics of this variable or which CVE fix it gates, nor confirm the vendored Git version's behavior when the variable is unset vs. explicitly `false`. This is the key uncertainty: if the variable's default (when unset) is already `false`/inactive and Desktop is just being explicit, this would not be a regression; but the deliberate, explicit setting to `'false'` strongly suggests the intent is to suppress a check that would otherwise trigger (Git's own checks are opt-in "active" states that must be explicitly enabled/disabled by the invoking process based on its trust model). Every recursive clone in Desktop goes through this exact code path, so if the variable does disable the protection, the exposure is on the default/most common clone flow.

### Recommendation
1. **Short term:** Verify against the vendored dugite/Git version what `GIT_CLONE_PROTECTION_ACTIVE` controls exactly (check Git release notes/changelog for the version bundled). If it corresponds to the submodule-path-collision protections from the CVE-2024-320xx series, remove the override so Git's default (protection enabled) applies, or explicitly set it to `'true'`/leave it unset.
2. **Long term:** Add a regression test (analogous to `app/test/unit/clone-path-safety-test.ts`) that attempts to clone a crafted repository with a submodule whose name collides with `.git` under case-insensitive/normalized filesystem semantics, and assert that Desktop's clone rejects/sanitizes it, mirroring the existing `isClonePathSensitive` test coverage.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
