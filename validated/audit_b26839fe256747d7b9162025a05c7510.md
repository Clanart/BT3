### Title
Stale per-path manual conflict resolution silently reapplied to a later, unrelated conflict during rebase/cherry-pick - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` carries the entire `manualResolutions` map forward, unconditionally, across successive Git status refreshes of an in-progress rebase, keyed only by file **path** rather than by the specific commit/conflict instance that produced it. Because Desktop's "is this file resolved" and "continue" logic (`getConflictedFiles`/`getResolvedFiles`, `stageManualConflictResolution`) also key purely on path, a resolution the user picked for commit N's conflict on `foo.ts` gets silently re-applied — without ever being shown to the user — to a different conflict that arises on the same path from a later commit N+1 in the same rebase/cherry-pick, letting an attacker-controlled repository steer what content is silently staged and committed.

### Finding Description
`updateConflictState` decides what `manualResolutions` to keep when a new `git status` is observed: [1](#0-0) 

For a rebase, `manualResolutions` from `prevConflictState` is preserved verbatim as long as the new status is still classified as a "rebase" conflict — there is no check on whether `currentTip`/`rebaseCurrentCommit` changed, i.e. whether Desktop moved from resolving commit N's conflicts to commit N+1's conflicts within the same interactive rebase.

The UI/flow for a rebase step passes this same map straight through unmodified between "continue" steps: [2](#0-1) 

Whether a conflicted file is considered "resolved" (and therefore hidden from the user and excluded from blocking "Continue rebase") is decided purely by path lookup, with no association to the specific conflict content or commit: [3](#0-2) [4](#0-3) 

Finally, when the rebase is continued, every path present in `manualResolutions` is staged via `git checkout --ours/--theirs` against whatever is *currently* on disk for that path, with no verification that this is the same conflict the user actually reviewed: [5](#0-4) [6](#0-5) 

This is the same broken-invariant pattern as the referenced report: state that is only valid for one specific operation instance (there: `outstandingAmount` tied to a specific trade fill; here: a manual resolution tied to a specific conflict instance) is cleared/reused across instance boundaries instead of being tied to — and only valid for — the instance that produced it, leading to silent, incorrect application of stale state to a new instance.

### Impact Explanation
An attacker who controls the branch/commits being rebased onto (e.g. a malicious upstream repository or PR branch the user fetches and rebases onto) can craft two or more commits that each conflict on the same file path. When the user resolves the first conflict (e.g. "Use theirs") and continues, the second, differently-crafted conflict on the same path is never surfaced for review: Desktop treats it as already resolved and, on "Continue rebase", runs `git checkout --theirs -- <path>` against the new (attacker-controlled) conflicted content and stages/commits it. This is a silent corruption of what the user commits, potentially embedding attacker-chosen code/content into the user's history and any subsequent push, entirely without the user seeing the second conflict's content. No local access, admin rights, or social engineering beyond a normal fetch/rebase is required — this is a standard unprivileged Desktop workflow (rebase onto an attacker-influenced branch).

### Likelihood Explanation
Rebasing onto branches from external contributors/forks is a routine Desktop workflow, and interactive/linear rebases spanning many commits touching the same files are common (e.g., long-lived feature branches, stacked PRs). Crafting a rebase target with repeated conflicting commits on the same path requires nothing beyond standard git operations on a repository the attacker controls, and does not depend on any implementation detail the user could reasonably notice (the second conflict simply never appears in the UI).

### Recommendation
Tie `manualResolutions` entries to the specific conflict instance rather than the bare file path — e.g., invalidate/clear resolutions for a path whenever the rebase's current commit (`rebaseInternalState`/`currentTip`) changes, or key resolutions by `(path, conflictMarkerHash | commit sha)` instead of `path` alone. At minimum, `updateConflictState` should drop stale entries whenever the observed commit being replayed changes, so a resolution can never be silently carried across distinct conflict instances.

### Proof of Concept
1. Attacker prepares a remote branch `evil` with two commits, both modifying line X of `shared.ts`, each designed to conflict with the user's local commits at the exact same hunk.
2. Victim fetches `evil` and runs `git rebase evil` (or rebases their branch onto it) in Desktop.
3. Commit 1 conflicts on `shared.ts`; user reviews it and picks "Use theirs" via `updateManualConflictResolution` → stored in `conflictState.manualResolutions` keyed by `"shared.ts"`.
4. User clicks "Continue rebase". `continueRebase` stages `shared.ts` per the stored resolution and rebase proceeds to commit 2.
5. Commit 2 also conflicts on `shared.ts` with different (malicious) content. `git status` reports it as conflicted, but `updateConflictState` keeps the old `manualResolutions` map (per `app/src/lib/stores/updates/changes-state.ts:263-292`), so `getConflictedFiles`/`getResolvedFiles` (`app/src/lib/status.ts:151-173`) treat `shared.ts` as already resolved — it never reappears in the conflicts dialog and "Continue rebase" is enabled immediately.
6. On the next "Continue rebase" click, `continueRebase` (`app/src/lib/git/rebase.ts:438-458`) calls `stageManualConflictResolution` with the *original* "theirs" resolution against commit 2's new conflict markers, silently staging and committing the attacker's second payload without the user ever seeing it.

/**
 * Determine if we have any conflict markers or if its been resolved manually

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
