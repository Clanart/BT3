### Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL based on trusted GitHub API `clone_url` field enables silent push/fetch hijacking - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes the GitHub metadata associated with a tracked repository, it calls `updateRemoteUrl()`, which compares the previously cached `GitHubRepository.cloneURL` against the repository's current git remote and, if they still match (i.e. the user hasn't manually edited the remote) but the freshly-fetched `apiRepo.clone_url` differs, silently runs `git remote set-url` to rewrite the user's `origin` remote to whatever URL the API returned - with no user confirmation, diff, or warning. [1](#0-0) 

### Finding Description
`repositoryWithRefreshedGitHubRepository()` (invoked automatically after account/repo refresh, e.g. `refreshSelectedRepositoryAfterAccountChange`) re-derives `owner`/`name` from the *current* remote URL via `matchGitHubRepository`, fetches fresh repository data from the GitHub API (`api.fetchRepository(owner, name)`), and then calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` before persisting the new `GitHubRepository` record: [2](#0-1) 

`updateRemoteUrl` trusts the `clone_url` field of the API response as authoritative and mutates the on-disk git config directly:
```
const remoteUrlUnchanged =
  gitStore.defaultRemote &&
  urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
``` [3](#0-2) 

`setRemoteURL` performs `git remote set-url <name> <url>` with no additional validation of the destination host/owner and no user-facing prompt: [4](#0-3) 

The broken invariant mirrors the report's core problem: a security-relevant value (here, the trusted destination of `git push`/`git fetch`, analogous to "voting power") is derived from a mutable, externally-controlled input (the GitHub API's `clone_url`, analogous to a transferable token balance) and is propagated without any secondary confirmation step tying the change back to explicit user intent. Just as DToken updates voting power purely from `balanceOf` without accounting for the transfer event's trust implications, Desktop updates the git remote purely from the API's `clone_url` without accounting for the fact that this value can change for reasons other than a benign rename (e.g., a compromised/malicious GitHub Enterprise endpoint, a MITM'd or malicious proxy sitting in front of `api.fetchRepository`, or attacker control over how a renamed/transferred repository resolves). Existing guards (`protocolsMatch`, `remoteUrlUnchanged`, `urlsMatch`) only check *shape/consistency*, not *trust*/*origin* of the new URL - they will happily pass for any attacker-supplied `clone_url` on the same protocol.

### Impact Explanation
If the URL returned by the API object is attacker-influenced (e.g., a malicious/compromised GHES instance the user is signed into, or a network position able to tamper with the API response before Desktop's HTTPS client validation boundary is exercised in an unexpected way, or a chained repository-transfer scenario), Desktop will silently repoint `origin` to an attacker-controlled repository. Every subsequent `git push` from that point on is silently redirected to the attacker's repository (silent corruption of what the user pushes), and every subsequent `git fetch`/pull can bring in attacker-controlled history/content. Because credential helpers issue credentials keyed to the destination host, this can also result in the user's git credentials being sent to a new, attacker-chosen host during the next authenticated operation (credential exfiltration risk). This matches the report's "Valid Impact" categories: attacker controls a GitHub API object / git remote or proxy response, resulting in silent corruption of what is pushed and potential credential exfiltration.

### Likelihood Explanation
The refresh path runs automatically in the background (on account change, selected-repository refresh, etc.) without requiring any unusual user action, and none of the existing checks validate that the new `clone_url` is actually still associated with the same trusted destination the user originally cloned from - they only check URL-shape consistency. However, exploitation depends on an attacker being able to influence the API response itself (a malicious/compromised GitHub Enterprise server, a network path capable of altering the API response, or engineering a repository-transfer edge case), which is a narrower precondition than the DToken report's trivially-repeatable multi-address exploit, so likelihood should be assessed as medium rather than high.

### Recommendation
Do not silently call `git remote set-url` based solely on the GitHub API's `clone_url`. At minimum:
- Require explicit user confirmation (a dialog showing old vs. new remote URL) before rewriting `origin`.
- Pin the expected host/owner authority by verifying the new `clone_url`'s hostname continues to match the account's configured `endpoint` before considering it a legitimate rename, and independently confirm the underlying repository identity (e.g., via the immutable repository ID) rather than owner/name strings alone.
- Log/audit remote URL changes so users can detect unexpected repository redirection.

### Proof of Concept
1. User has a tracked repository whose `origin` remote matches its cached `GitHubRepository.cloneURL` (i.e., unmodified by the user).
2. Desktop performs an automatic GitHub repository refresh (e.g., triggered by an account update) which calls `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository(owner, name)`. [5](#0-4) 
3. The API response (attacker-influenced via a malicious/compromised GitHub Enterprise endpoint or a manipulated proxy in the request path) returns an `apiRepo.clone_url` pointing to an attacker-controlled repository with the same protocol as the current remote.
4. `updateRemoteUrl` finds `protocolsMatch && remoteUrlUnchanged && !urlsMatch` all true and calls `gitStore.setRemoteURL(...)`, silently rewriting `origin` to the attacker's URL with no user prompt. [6](#0-5) 
5. The next `git push` performed by the user in Desktop silently pushes to the attacker's repository instead of the intended one.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
