### Title
Unchecked `payment_sat + needed_fee` overflow bypasses the `NotEnoughFunds` guard, producing an unspendable/overdrawn transaction and an underflow panic in `fee()` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is "a secondary deduction (referrer fee) is subtracted from a base amount (settlement fee) without the base being bounded against it, so subtraction underflows and the operation reverts." In `SignableTransaction::new`, the solvency check `input_sat < (payment_sat + needed_fee)` computes `payment_sat + needed_fee` with unchecked `u64` addition, and `needed_fee` itself is `fee_per_vbyte * vbytes` — an unchecked multiplication of an externally supplied rate. Both can wrap, letting construction succeed while `sum(outputs) > sum(inputs)`. The subsequent `fee()` getter then performs a bare `sum(prevouts) - sum(outputs)` subtraction which underflows and panics, and if the machine path is reached the multisig produces a consensus-invalid transaction, burning a signing round and stalling the plan — the same "operation can never complete because a fee component was not bounded" shape as the Buffer finding.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- `needed_fee` is computed by unchecked multiplication of the caller/untrusted-supplied `fee_per_vbyte`: `let mut needed_fee = fee_per_vbyte * vbytes;` (line 206). A large `fee_per_vbyte` wraps `needed_fee` to a small value, also defeating the `TooLowFee` minimum-relay check at lines 211-213.
- The funds check uses unchecked addition: `if input_sat < (payment_sat + needed_fee)` (line 215). `payment_sat` is an unchecked `sum::<u64>()` over attacker-influenced payment amounts (line 187). If `payment_sat + needed_fee` wraps below `input_sat`, `NotEnoughFunds` is skipped even though the payments exceed the inputs.
- The change path recomputes with `fee_with_change = fee_per_vbyte * vbytes_with_change` and only guards the leftover via `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228) — the inner `payment_sat + fee_with_change` itself is unchecked and can wrap, so `checked_sub` can return `Some` and push a change output on an insolvent transaction.
- The resulting `SignableTransaction` has `sum(outputs) > sum(inputs)`. `fee()` at lines 138-141 does `sum(prevouts) - sum(outputs)` with a plain `-`, which panics on underflow; callers such as the processor use `tx.0.fee()` when accounting for forwarded outputs (`processor/src/multisigs/mod.rs:884`), turning the arithmetic flaw into a crash. Alternatively, `TransactionSignMachine::sign` (lines 373-397) signs a `Prevouts::All` Taproot sighash for a transaction Bitcoin will reject (outputs exceed inputs), wasting the FROST signing session and leaving the payment plan permanently unexecutable — the direct analog of "`createFromRouter` reverts, the option cannot be opened."

### Impact Explanation
An unprivileged party who can influence payment amounts (via on-chain instructions that become `payments`) or the fee rate can drive construction into a state that either panics the processor in `fee()` (liveness failure for the whole multisig scheduler) or produces a threshold-signed transaction the network rejects, permanently stalling the associated payments. Like the original, the root cause is a missing upper bound on a fee component relative to the amount it is deducted from.

### Likelihood Explanation
Requires payment amounts/fee rate large enough to wrap `u64` arithmetic, or an aggregate of payments whose sum exceeds inputs only after wraparound. Real coin amounts are bounded, so the practical trigger is primarily a wrapped `payment_sat + needed_fee` via `fee_per_vbyte * vbytes` overflow — still entirely determined by inputs to `new`, with no internal bound. Medium likelihood, matching the original's Medium severity.

### Recommendation
Use `checked_add`/`checked_mul` (or `saturating_*`) for `payment_sat`, `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, and `payment_sat + fee_with_change`, returning `NotEnoughFunds`/`TooLowFee`-style errors on overflow; bound `fee_per_vbyte` to a sane maximum; and make `fee()` use `checked_sub` or store the fee at construction so a constructed `SignableTransaction` is provably solvent.
