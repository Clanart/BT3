### Title
`openFile()` invoked without `isSafeFileExtension` check in conflict-resolution UI allows execution of attacker-supplied `.exe`/`.cmd`/`.bat` files - (File: `app/src/ui/lib/conflicts/unmerged-file.tsx`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx`)

### Summary
Desktop restricts "Open with Default Program" for `.exe`, `.cmd`, `.bat`, `.sh` files on Windows via `isSafeFileExtension()` in most file-list context menus, but several conflict-resolution UI surfaces call `openFile()` directly without ever checking the extension, executing whatever file the merge/rebase/cherry-pick brought into the working directory.

### Finding Description
`isSafeFileExtension` gates dangerous extensions on Windows: [1](#0-0) 

This check is correctly applied before allowing "Open with Default Program" in the commit history and PR file views, where the action is `enabled: isSafeExtension && fileExistsOnDisk`: [2](#0-1) [3](#0-2) 

However, the equivalent "Open with Default Program" action wired up for merge-conflict resolution calls `openFile(absoluteFilePath, dispatcher)` with no extension check and no `enabled` gate at all: [4](#0-3) 

The same unguarded pattern exists in the new Copilot-conflict-resolution dialog, both in the per-file overflow menu and in the double-click handler on the file list: [5](#0-4) [6](#0-5) 

`openFile()` itself performs no validation — it blindly hands the path to the OS shell: [7](#0-6) 

This is the exact "inconsistent usage of a protective wrapper" pattern from the seed report: `safeTransferFrom` vs `transferFrom` used inconsistently across the same contract. Here, `isSafeFileExtension`-gated `openFile()` is used in some call sites and un-gated `openFile()` is used in others touching the same primitive (opening a working-directory file with the OS default handler).

### Impact Explanation
A conflicted file (introduced by the "theirs" side of a merge/rebase/cherry-pick, i.e., from a remote branch, fork, or PR the user is merging — fully attacker-controlled content) can be named with a dangerous extension (e.g. `payload.cmd`, `payload.bat`, `payload.exe` renamed as a text-like conflicted file, or a `.sh` on macOS/Linux where marked executable). If the user, in the course of the ordinary conflict-resolution workflow, clicks "Open with Default Program" from the file's overflow/resolution menu (or double-clicks the file row in the Copilot conflicts "Changes" tab), the file is opened via `shell.openExternal('file://...')`, and on Windows this directly executes `.exe`/`.cmd`/`.bat` files. This yields arbitrary code execution under the user's account, achieved purely by the victim doing the normal thing a merge-conflict UI invites them to do (inspect the conflicting file).

### Likelihood Explanation
Merge/rebase/cherry-pick conflicts routinely occur when integrating a collaborator's or a PR author's branch — an attacker only needs to craft a branch/PR that produces a conflicting file with a dangerous extension and get the victim to merge/rebase against it, a very ordinary collaboration flow. Opening a conflicted file to inspect its content before resolving is a natural, expected user action in this dialog, unlike attacks requiring atypical or "unnatural" steps. The new Copilot-conflicts flow (`copilot-conflicts-dialog.tsx`, `copilot-conflicts-changes.tsx`) is a recently-added surface, increasing the chance this un-guarded path was not covered by the extension check that was already applied elsewhere in the codebase.

### Recommendation
Apply `isSafeFileExtension()` (and `fileExistsOnDisk` gating where relevant) consistently at every call site that surfaces "Open with Default Program" for a working-directory/conflicted file, specifically:
- `makeMarkerConflictDropdownClickHandler` in `app/src/ui/lib/conflicts/unmerged-file.tsx`
- `onOverflowMenuClick` in `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`
- `onOpenBinaryFile` / `onRowDoubleClick` in `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx`

Ideally, move the extension check inside `openFile()` itself (in `app/src/ui/lib/open-file.ts`) so all current and future call sites are protected by default, rather than relying on each caller to remember to check `isSafeFileExtension`.

### Proof of Concept
1. Attacker creates a branch that, when merged/rebased into the victim's branch, produces a conflict on a new file `run.cmd` containing a malicious batch script (or a `.exe` binary as the conflicting blob).
2. Victim runs Desktop, starts a merge/rebase/cherry-pick against the attacker's branch, hits the conflict, and opens the "File resolution options" (or Copilot conflicts overflow menu) for `run.cmd`.
3. Victim clicks "Open with Default Program". Unlike the equivalent menu item in the Commits/PR file views, no `isSafeFileExtension` check runs.
4. On Windows, `run.cmd` is executed directly by the OS shell via `shell.openExternal('file://.../run.cmd')`, achieving code execution under the victim's account — silently bypassing the `RestrictedFileExtensions` protection that exists elsewhere in the same codebase.

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
