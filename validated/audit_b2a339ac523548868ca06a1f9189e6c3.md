## Title
Stale line-selection indices are silently reapplied to a freshly re-fetched diff during commit staging, allowing wrong/attacker-influenced hunks to be committed without warning - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The reported LoopFi bug is a class of "value computed at time T1, consumed unsafely at time T2 after state has changed, with no re-validation" — the liquidator computes `virtualDebt` once, then a state-changing action between computation and consumption breaks the invariant. GitHub Desktop's partial-commit ("stage selected lines") pipeline has the same broken-invariant shape: the `DiffSelection` bitmap the user builds while reviewing a diff in the UI is a set of **positional line indices**, and it is reused later against a **newly fetched diff** at commit time without ever checking that the diff hasn't changed in the interim.

### Finding Description
When a user partially selects lines/hunks to include in a commit, the UI diff is loaded once and cached, and the user's line choices are stored as a `DiffSelection` — a bitmap keyed by `absoluteIndex` (a line's position inside the diff's hunks), see `formatPatch`'s use of `hunk.unifiedDiffStart + lineIndex` and `file.selection.isSelected(absoluteIndex)`. [1](#0-0) 

That cached `WorkingDirectoryFileChange` (path + status + `DiffSelection`) is what gets passed all the way down to `createCommit`: [2](#0-1) 

`createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`: [3](#0-2) [4](#0-3) 

Critically, `applyPatchToIndex` does **not** reuse the diff that produced the UI selection. It fetches a **brand-new** diff from disk at staging time and immediately formats/applies a patch from it using the *old* selection object: [5](#0-4) 

`formatPatch` then walks the *new* diff's hunks/lines and asks the *old* `file.selection.isSelected(absoluteIndex)` whether each positional index is selected — there is no comparison of the two diffs' contents, hunk boundaries, or line counts: [6](#0-5) 

Because `DiffSelection` is purely positional (not content-addressed), if the on-disk file changes between when the UI diff/selection was built and when `applyPatchToIndex` re-reads the diff, the index positions from the stale selection line up with **different lines/hunks** in the new diff. There is no staleness check anywhere in this path (`app-store.ts`, `update-index.ts`, `apply.ts`, `patch-formatter.ts`) that verifies the diff used to build the selection is still the diff being staged.

### Impact Explanation
This breaks the core guarantee of partial staging: "only the lines the user explicitly selected are committed." A file change occurring in the window between the user finalizing their selection (e.g. deliberately deselecting a suspicious/incomplete hunk) and the click-to-commit staging step can cause Desktop to silently commit different content than what the user reviewed and approved — i.e., silent corruption of what the user commits, with no error surfaced (unlike the CDPVault bug, which at least reverts loudly; here the wrong patch can apply cleanly if line counts happen to still be compatible, or in the worst case `git apply` fails and the user is left confused, but in intermediate cases content is silently miscommitted).

### Likelihood Explanation
The window is small but is not something requiring local/physical access or a compromised host: it can be induced by any process controlled by the attacker as part of the cloned/fetched repository's own developer tooling (e.g., a `postinstall`/`prepare` script, a file-watcher/build tool, or a git hook set up as part of normal project onboarding) that rewrites tracked files while Desktop is open. Because the check-then-act gap (`diff read for UI` → `user selects lines` → `diff re-read for staging` → `patch applied by position`) has no re-validation, an attacker who controls repository tooling that legitimately runs in the background during normal development has multiple opportunities to land a write inside this window, similar in spirit to the front-run repay in the original report, but exploiting an unguarded TOCTOU (time-of-check-to-time-of-use) gap on diff/selection consistency rather than an arithmetic underflow.

### Recommendation
Before staging a partially-selected file, re-verify that the diff `applyPatchToIndex` is about to use matches the diff the `DiffSelection` was computed against (e.g., by comparing the diff's blob/oid or serialized hunk text, not just re-fetching and blindly trusting index positions). If the file has changed, abort the commit for that file and force Desktop to re-render the diff/selection UI for the user to re-confirm, rather than silently applying stale positional selections to new content.

### Proof of Concept
1. In the Desktop UI, open a file with multiple hunks and deselect one hunk (e.g. a suspicious block) so the cached `DiffSelection` excludes lines N..M of the diff rendered at time T1.
2. Before the user clicks "Commit", a background process (e.g., a repo-provided `postinstall`/watch script) rewrites the file such that lines are inserted/removed above the previously deselected hunk, shifting line positions (hunk boundaries change but git status still reports the file as modified with a similar selection-type).
3. User clicks Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff fresh from disk — now with shifted hunks/line positions.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) walks the new hunks and evaluates `file.selection.isSelected(absoluteIndex)` using the OLD positional bitmap, which now maps to different lines than what the user actually deselected.
5. The committed patch silently includes/excludes different content than the user intended, with no error and no indication to the user that the staged diff diverged from what they reviewed. [7](#0-6) [1](#0-0)
