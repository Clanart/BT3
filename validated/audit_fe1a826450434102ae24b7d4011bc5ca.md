### Title
`BalanceHandler.prevEventsLen` checkpoint is overwritten (not stacked) across nested/recursive precompile calls, causing native balance events to be mis-aggregated into StateDB - (File: `precompiles/common/balance_handler.go`)

### Summary
This is the direct Cosmos EVM analog of the yAxis `CDP.sol` bug: a single scalar "checkpoint" value that is meant to track incremental progress is unconditionally overwritten on each call instead of being saved/restored per invocation, so nested invocations corrupt the outer invocation's bookkeeping. In yAxis, `totalCredit` was overwritten instead of accumulated. In Cosmos EVM, `BalanceHandler.prevEventsLen` — the marker used to slice "new" bank events for translating them into StateDB balance deltas — is reset by every call to `BeforeBalanceChange`, with no save/restore across reentrant precompile calls sharing the same handler instance.

### Finding Description
`BalanceHandler` records an event-log high-water mark before a precompile's native action runs, then on completion replays only the events emitted *after* that mark to update the EVM `StateDB` balances: [1](#0-0) [2](#0-1) 

In the normal path, `runNativeAction` in `precompiles/common/precompile.go` allocates a fresh `BalanceHandler` per call via `BalanceHandlerFactory.NewBalanceHandler()`: [3](#0-2) 

However, the codebase's own test suites show this invariant is broken when a single handler instance is shared/reused across nested/recursive precompile invocations (e.g., a contract calling itself or another precompile from within a precompile call, or an EVM call that recurses through `_beforeTokenTransfer`/callback hooks). The debug precompile's `Run` explicitly uses a persistent `p.GetBalanceHandler()` rather than creating a new instance per call: [4](#0-3) 

The repo's own tests document exactly this defect as a known, reproduced bug:
- `evmd/tests/integration/balance_handler/balance_handler_test.go`: *"tests the balance handler bug where recursive precompile calls share the same `BalanceHandler` instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [5](#0-4) 
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`: *"Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated"* — and the accompanying test cases show diverging outcomes (contract native balance ends at `0` vs `50`, and event counts of `20` vs `29`) depending on whether an inner recursive call reverts, directly demonstrating that the outer call's balance-event window is corrupted by the inner call's checkpoint overwrite. [6](#0-5) [7](#0-6) 

The `StakingReverter.sol` test contract and its `0_edge_case_revert.js`/`test_integration.go` tests further confirm the underlying pattern: precompile calls that occur before/after an inner reverted call must be tracked precisely, and an incorrect checkpoint makes it possible for state (delegations, native balances) to diverge from what the StateDB reflects. [8](#0-7) 

### Impact Explanation
When `prevEventsLen` is overwritten by a nested call instead of being saved/restored (stack-like) per call frame, the outer call's `AfterBalanceChange` will either:
1. Replay bank events belonging to the *inner*, already-processed or reverted call (double-counting balance deltas into the StateDB), or
2. Skip legitimate bank events emitted by the outer call because the checkpoint was advanced past them by the inner call.

Either direction breaks the 1:1 accounting invariant between the native `x/bank` ledger and the EVM `StateDB` balance view that the EVM keeper commits back to state. This can result in an EVM-visible balance that is higher or lower than the true bank-keeper balance for a user or contract, i.e., unauthorized creation or loss of spendable value at the StateDB layer, and observed test divergences between contract balances (`0` vs `50`) and reward/escrow amounts depending purely on unprivileged internal call structure (recursion/try-catch), not on an actual difference in economic reality. This matches the "duplication/irreversible accounting corruption of spendable user value across native balances/EVM balances" critical-impact category.

### Likelihood Explanation
The trigger is fully unprivileged: any EVM contract that calls a precompile recursively, or that triggers a precompile call from within an ERC-20 hook (`_beforeTokenTransfer`) that itself performs another precompile call or reverts partway, exercises this path. The repository's own dedicated regression tests (`balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`, `StakingReverter.sol` edge cases) demonstrate the bug is reliably reproducible with straightforward, permissionless transaction flows — no validator, relayer, or governance privilege is required.

### Recommendation
Make the balance-event checkpoint reentrancy-safe:
- Save/restore `prevEventsLen` per call frame (push/pop a stack, or capture and restore the previous value after `AfterBalanceChange` completes) instead of unconditionally overwriting a single shared field, mirroring the `CDP.sol` fix of accumulating/preserving prior state rather than clobbering it.
- Ensure `BalanceHandlerFactory.NewBalanceHandler()` is used consistently for every native-action invocation (including the debug/test precompile path) rather than reusing a single handler instance across recursive calls (as `debug.go`'s `GetBalanceHandler()` pattern currently allows).
- Add an explicit reentrancy guard/assertion so that if a `BalanceHandler` is reentered before its `AfterBalanceChange` completes, it fails loudly instead of silently corrupting the event slice.

### Proof of Concept
The repository already contains a working PoC in `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go::TestHandleMsgTransfer`, subtest `"test recursive precompile call with reverts"` vs `"without reverts"`: a recursive ERC-20 contract with a `_beforeTokenTransfer` override triggers an ICS-20 precompile transfer, and depending on whether the inner recursive precompile call reverts, the contract's tracked native bond-denom balance ends up as `0` (reverting case) vs `50` (non-reverting case) with different emitted event counts (`20` vs `29`) purely due to the `prevEventsLen` checkpoint being overwritten by the nested call. [9](#0-8) 
A second, more isolated PoC is `evmd/tests/integration/balance_handler/balance_handler_test.go::TestRecursivePrecompileCallsWithDebugPrecompile`, which deploys a caller contract that recurses through the debug precompile and asserts a specific (already-corrupted) event count (`15` total events, `10` debug-precompile events) as the expected/observed buggy behavior. [10](#0-9)
