### Title
Nested/Recursive Precompile Calls Cause Duplicate Balance-Change Application via Stale `prevEventsLen` Cursor in `BalanceHandler` - (File: `precompiles/common/balance_handler.go`)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` use a single `prevEventsLen` cursor into `ctx.EventManager().Events()` to decide which bank events to translate into `StateDB.AddBalance`/`SubBalance` calls <cite repo="blackvul/push-chain-evm--014" path="precompiles/common/balance_handler.go" start="43,68" end="48,71" />. When a precompile call recursively invokes the EVM/another precompile before its own `AfterBalanceChange` runs, the nested call's own `BeforeBalanceChange`/`AfterBalanceChange` pair already consumes and applies its bank events to the `StateDB` [1](#0-0) . Because bank events are never truncated from the shared `ctx.EventManager()`, the outer call's stale `prevEventsLen` (captured before the nested call happened) causes it to re-process the same events a second time, applying the balance delta twice against `StateDB` while the `x/bank` keeper only moved the funds once.

### Finding Description
This is the same bug class as the referenced `BalancerOracle::update()` finding: a boundary/cursor value (`lastUpdate`/timestamp there, `prevEventsLen`/event-index here) is captured once at the start of an operation and then used to gate what "new" data should be consumed, but a nested or interleaved update mutates the underlying source (price feed there, `ctx.EventManager()` events here) before the boundary is consulted, causing stale/duplicate consumption of state.

Concretely:
1. `RunNativeAction` creates a fresh `BalanceHandler` per precompile call and calls `BeforeBalanceChange(ctx)`, recording `prevEventsLen = len(ctx.EventManager().Events())` [2](#0-1) .
2. The precompile's `action(ctx)` executes; if it performs a nested EVM call that re-enters a precompile (directly recursive, or via another precompile), that nested call performs its own `BeforeBalanceChange`/`Execute`/`AfterBalanceChange` cycle, translating its bank events (`CoinSpent`/`CoinReceived`/precisebank fractional events) into `StateDB.AddBalance`/`SubBalance` [3](#0-2) .
3. Those bank events remain appended to the *same* `ctx.EventManager()` — they are never removed or marked "consumed".
4. When control returns to the outer call, `AfterBalanceChange` iterates `events[bh.prevEventsLen:]`, which spans from before the nested call started, and therefore includes the events already applied by the nested call's own `AfterBalanceChange`. These get re-applied to `StateDB` a second time.
5. Result: `StateDB` balances (visible to subsequent EVM instructions, e.g. `balanceOf`/`.balance`, in the same transaction, and ultimately committed to the underlying accounts) drift from the true `x/bank` balances by the duplicated delta — an accounting desync between native bank state and EVM-visible state.

The repository itself contains a dedicated regression test explicitly documenting this exact defect: `evmd/tests/integration/balance_handler/balance_handler_test.go` states "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [4](#0-3) . The test drives a contract (`DebugPrecompileCaller.sol`) that recursively calls a precompile which in turn re-enters the EVM to call itself again [5](#0-4) , and the debug precompile's `Call0` handler performs exactly this recursive `CallEVMWithData` re-entry from within `Execute`, i.e., inside the window between `BeforeBalanceChange` and `AfterBalanceChange` of the outer call [6](#0-5) .

### Impact Explanation
Any production precompile built on `precompiles/common/Precompile.RunNativeAction` (e.g. `precompiles/erc20`, `precompiles/staking`, `precompiles/distribution`, `precompiles/gov`, `precompiles/ics20`) is exposed if it can be induced to re-enter the EVM/another balance-changing precompile from within its own execution before returning. Since bank-event translation into `StateDB` is duplicated rather than the actual coin movement, an attacker able to trigger such reentrancy can cause the EVM-visible balance of an account to inflate beyond what is actually backed by the `x/bank`/`x/precisebank` ledger — i.e., unauthorized duplication/accounting corruption of spendable EVM balance, matching the Critical impact gate ("unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances ... precompile-mediated assets").

### Likelihood Explanation
The precondition is a precompile that (a) uses `BalanceHandlerFactory`/`RunNativeAction`, and (b) internally calls back into the EVM (`CallEVM`/`CallEVMWithData`) that can result in another balance-changing bank event being emitted before the outer `AfterBalanceChange` executes. This is a realistic pattern for hook/callback-oriented precompiles (e.g., ICS20 with IBC callbacks, ERC20 precompile calling a contract that calls back into a bank-moving precompile) and is unprivileged — any user can construct a contract that triggers this reentrant call sequence, exactly as demonstrated by the existing `DebugPrecompileCaller` test contract.

### Recommendation
Do not rely on a single cursor into a shared, ever-growing event list across nested calls. Options:
- Snapshot and truncate/mark the specific event slice consumed by a `BalanceHandler` instance so nested handlers cannot see or re-process events already claimed by an ancestor (e.g., tag events with a handler/call ID rather than relying purely on positional length).
- Alternatively, track a stack of `prevEventsLen` values so an outer handler's window excludes ranges already consumed by inner handlers, or make `AfterBalanceChange` idempotent per event (e.g., remove/mark consumed events instead of leaving them for later re-scan).
- More robust: apply balance changes directly at the point bank events are emitted (synchronously) instead of deferring to a length-diffed batch scan, removing the shared-cursor dependency entirely.

### Proof of Concept
The repository's own integration test reproduces the scenario end-to-end:
1. Deploy `DebugPrecompileCaller.sol`, which calls the debug precompile's `callback` method, which recursively re-enters the EVM to call the precompile again before returning [5](#0-4) .
2. The debug precompile's `Call0` performs the nested `CallEVMWithData` re-entrant call from inside `Execute`, i.e., between the outer call's `BeforeBalanceChange` and `AfterBalanceChange` [6](#0-5) .
3. `evmd/tests/integration/balance_handler/balance_handler_test.go::TestRecursivePrecompileCallsWithDebugPrecompile` executes this flow and documents the resulting event/balance-handling anomaly directly in its comments and assertions [7](#0-6) .

**Note on uncertainty:** I could not fully trace, within the available tool budget, whether the specific `evmd/tests/testdata/debug` precompile variant (built on `RunNativeAction`/`BalanceHandlerFactory`) still reproduces a *balance-value* discrepancy in `StateDB` versus merely an event-count anomaly — the test as read asserts event counts (`15` events, `10` `debug_precompile` events) rather than asserting on final account balances. Confirming the precise magnitude/direction of balance duplication for a real value-transferring precompile (e.g., `precompiles/erc20` or `precompiles/staking` re-entering another bank-moving precompile) would require executing the test suite or writing a targeted PoC that recursively triggers a coin-transferring precompile and diffing `StateDB.GetBalance` against `bankKeeper.GetBalance` post-execution — this should be validated with a running Devin session that can execute Go tests.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

func (p Precompile) Call0(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	// data := crypto.Keccak256([]byte("function callback()"))[:4]
	counter := new(big.Int).SetBytes(contract.Input[1:])
	counter = new(big.Int).Add(counter, big.NewInt(1))

	args := math.U256Bytes(counter)
	selector := []byte{0xff, 0x58, 0x5c, 0xaf}
	data := append(selector, args...)

	caller := contract.Caller()
	fmt.Printf("Execute debug precompile %s, %p\n", caller.String(), p.BalanceHandlerFactory)
	rsp, err := p.evmKeeper.CallEVMWithData(ctx, p.Address(), &caller, data, true, nil)
	fmt.Println("callback response:", rsp.Ret, err)
	if err != nil {
		return nil, err
	}
	return nil, nil
}
