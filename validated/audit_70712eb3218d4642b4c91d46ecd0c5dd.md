### Title
`ThresholdKeys` accepts identity verification shares, yielding a permanently forgeable/unusable identity group key — (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes a missing non-zero check when writing a new value into state: an uninitialized (zero) upgrade target is stored as the wallet type, which `isWallet()` treats as invalid, permanently bricking the wallet. The Serai analog is that `ThresholdKeys::new` computes the `group_key` as a weighted sum of the caller-supplied `verification_shares` and never checks that any share — or the resulting `group_key` — is non-identity. `ThresholdKeys::read` routes untrusted bytes through `C::read_G` straight into `ThresholdKeys::new` with no identity rejection, so a serialized key set whose verification shares are the identity deserializes to a `ThresholdKeys` whose `group_key()` is the group identity — the elliptic-curve equivalent of "wallet type 0": a state value the rest of the protocol implicitly assumes is a real key.

### Finding Description
`ThresholdKeys::new` validates only the *count* and *indexes* of `verification_shares`, then computes `group_key` by summing `verification_shares[i] * interpolation_factor(i)` for `i` in `1..=t` [1](#0-0) . There is no check that any verification share is non-identity, nor that the resulting `group_key` is non-identity. `ThresholdKeys::read` feeds attacker-controlled bytes through `C::read_G` into this constructor for every participant `1..=n` [2](#0-1) . `read_G` for the dalek-backed groups only enforces canonical, torsion-free encodings; identity points deserialize successfully (`from_bytes` rejects non-canonical/non-torsion-free points, never identity) [3](#0-2) . Downstream, `view()` happily builds `ThresholdView`s from these shares [4](#0-3) , and `AlgorithmSignatureMachine::complete` verifies the aggregate with `SchnorrSignature::verify(group_key, c)`, whose statement `R + cA - sG == 0` is trivially satisfiable by anyone when `A` (the group key) is the identity: pick any `r`, set `R = rG`, `s = r` [5](#0-4) . The code itself acknowledges the resulting inconsistency only as an `InternalError` after the fact — "the only known way to cause this … is to deserialize a semantically invalid FrostKeys" [6](#0-5)  — confirming the invalid state is accepted at construction and only detected (if at all) when signing fails.

### Impact Explanation
A `ThresholdKeys` deserialized or constructed with identity verification shares produces `group_key() == identity`. Any funds, outputs, or protocol roles bound to that group key are protected by a Schnorr key with discrete log 0: signatures for it are forgeable by any party with no secret knowledge, so the key is simultaneously "broken" (honest shares produce shares that only verify against identity, and the underlying real secret can never match) and fully forgeable. This mirrors the report's impact — a state transition writes a zero/invalid sentinel that the system's validity predicate should have rejected, permanently corrupting the key object.

### Likelihood Explanation
Exploitation requires a party to feed crafted bytes to `ThresholdKeys::read` (explicitly in scope as untrusted input) or to call `ThresholdKeys::new` with identity shares. In deployment, `ThresholdKeys` blobs are produced by DKG protocols (PedPoP/MuSig/dealer) that populate honest shares, so the practical trigger is deserialization of keys sourced from storage or messages an attacker can influence; where that trust holds, impact reduces to a non-identity group key with mismatched shares (signing simply errors). Still, the missing invariant check is real and the forgery is unconditional once reached — Medium likelihood, High impact where reachable.

### Recommendation
In `ThresholdKeys::new`, reject any identity `verification_share` and reject a `group_key` that is the identity; equivalently, enforce non-identity in `read_G` paths used for verification shares (mirroring `Group::random`'s explicit identity ban [7](#0-6) ). This is the direct analog of the recommended "make sure the new type is not zero" mitigation.

// verification share is the identity point.

buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());           // t = 1
buf.extend(1u16.to_le_bytes());           // n = 1
buf.extend(1u16.to_le_bytes());           // i = 1
buf.push(1);                              // Interpolation::Lagrange
buf.extend(C::F::ZERO.to_repr().as_ref());          // secret_share = 0
buf.extend(C::G::identity().to_bytes().as_ref());   // verification_shares[1] = identity

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // "walletType == 0" state accepted

// Any (R = rG, s = r) now verifies under this key:
//   R + c*identity - sG = rG - rG = 0

    if (included.len() < self.params().t.into()) ||
      (usize::from(self.params().n()) < included.len())
    {
      Err(DkgError::IncorrectAmountOfParticipants {
        t: self.params().t,
        n: self.params().n,
        amount: included.len(),
      })?;
    }
    included.sort();
    {
      let mut found = included[0] == self.params().i();
      for i in 1 .. included.len() {
        if included[i - 1] == included[i] {
          Err(DkgError::DuplicatedParticipant(included[i]))?;
        }
        found |= included[i] == self.params().i();
      }
      if !found {
        Err(DkgError::NotParticipating)?;
      }
    }
    {
      let last = *included.last().unwrap();
      if u16::from(last) > self.params().n() {
        Err(DkgError::InvalidParticipant { n: self.params().n(), participant: last })?;
      }
    }

    // The interpolation occurs multiplicatively, letting us scale by the scalar now
    let secret_share_scaled = Zeroizing::new(self.scalar * self.original_secret_share().deref());
    let mut secret_share = Zeroizing::new(
      self.core.interpolation.interpolation_factor(self.params().i(), &included) *
        secret_share_scaled.deref(),
    );

    let mut verification_shares = HashMap::with_capacity(included.len());
    for i in &included {
      let verification_share = self.core.verification_shares[i];
      let verification_share = verification_share *
        self.scalar *
        self.core.interpolation.interpolation_factor(*i, &included);
      verification_shares.insert(*i, verification_share);

      The offset is included by adding it to the participant with the lowest ID.

      This is done after interpolating to ensure, regardless of the method of interpolation, that

      add the offset to every key share before interpolating, yet for Constant interpolation, we
      _have_ to add it as we do here (which also works even when we intend to perform Lagrange
      interpolation).
    */
    if included[0] == self.params().i() {
      *secret_share += self.offset;
    }
    *verification_shares.get_mut(&included[0]).unwrap() += C::generator() * self.offset;

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }
