### Title
Unchecked u64 addition overflow in `SignableTransaction::new` lets the `NotEnoughFunds` check wrap and produce a transaction paying more than its inputs - (networks/bitcoin/src/wallet/send.rs)

### Summary
The Astaria finding is an underflow caused by subtracting a value (`firstBidTime`, a timestamp) from a value (`maxDuration`, a small duration) without proving ordering. The analogous class in Serai's in-scope code is unchecked `u64` arithmetic in `SignableTransaction::new`: `payment_sat + needed_fee` is computed with a plain `+` (and `payment_sat` itself via a wrapping `sum::<u64>()`), so a sufficiently large attacker-controlled payment amount wraps the sum and bypasses the `NotEnoughFunds` check that exists to guarantee `sum(inputs) >= sum(outputs)`.

### Finding Description
In `SignableTransaction::new`, the payment amounts are `u64` values supplied by the caller (in the Serai stack these originate from user Burn requests, i.e., public inputs flowing into `make_signable_transaction` in `processor/src/networks/bitcoin.rs:441`). The relevant code:

- `payment_sat` is computed as `payments.iter().map(|payment| payment.1).sum::<u64>()` with no overflow check (send.rs:187).
- The solvency check is `if input_sat < (payment_sat + needed_fee)` using an unchecked `+` (send.rs:215).
- The change path repeats the same unchecked `+` inside `input_sat.checked_sub(payment_sat + fee_with_change)` (send.rs:228).

A single payment of `u64::MAX` (or a set of payments summing past `u64::MAX`) causes `payment_sat + needed_fee` to wrap to a small value, so the `NotEnoughFunds` guard passes even though the real total of the `TxOut` values pushed into `tx_outs` vastly exceeds `input_sat`. The resulting `SignableTransaction` is returned `Ok` and handed to the FROST `TransactionMachine`, which signs it.

The same wrapping affects `fee()`: `sum(prevouts) - sum(outputs)` (send.rs:139-141) is an unchecked subtraction that underflows once outputs exceed inputs, panicking in debug or wrapping to a huge fee in release — a direct underflow in the same sense as the original finding.

### Impact Explanation
- The threshold multisig produces signatures over an invalid transaction (`taproot_key_spend_signature_hash` at send.rs:386), i.e., concrete signing of a message that can never confirm. The payment plan is recorded as a spendable plan while the signed TX is rejected by every node, leaving payments permanently stuck and corrupting the scheduler's `queued_plans`/`plans` accounting (`created_output` expects `actual < expected` from the created output, which never materializes).
- `fee()` underflow can panic the signing/verification path — a reachable DoS — or report a wrapped fee, feeding incorrect values into `operating_costs` accounting downstream.

### Likelihood Explanation
The trigger is a Burn/payment whose amount is an attacker-chosen `u64`. There is no upper bound against `MAX_MONEY` or against the wallet's actual balance before the overflowed check; any single payment `> u64::MAX - needed_fee` (e.g., `u64::MAX` itself) suffices. This requires the integrator/processor to schedule a payment amount it cannot afford, which is precisely what the `NotEnoughFunds` error exists to catch — so the overflow converts a routine rejection into a signed invalid transaction. No malicious validator, peer, or RPC is needed; only the public payment amount.

### Recommendation
Use checked/saturating arithmetic in `SignableTransaction::new`:
- Compute `payment_sat` with `try_fold`/`checked_add` and return `NotEnoughFunds` (or a dedicated error) on overflow.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`, failing with `NotEnoughFunds` on overflow.
- Optionally bound each payment to Bitcoin's `MAX_MONEY` (21e14 sats) alongside the existing `DUST` lower bound.
- Make `fee()` use `checked_sub` and document the invariant that outputs never exceed inputs.

### Proof of Concept
Against `SignableTransaction::new` (release-mode wrapping arithmetic):

```rust
// One input worth `input_sat` sats; a single payment of u64::MAX.
let payments = vec![(p2tr_script_buf(key).unwrap(), u64::MAX)];

// payment_sat = u64::MAX; needed_fee = fee_per_vbyte * vbytes (small, e.g. ~100)
// payment_sat + needed_fee wraps to ~needed_fee - 1, which is < input_sat
let res = SignableTransaction::new(inputs, &payments, Some(change), None, 1);

// Returns Ok(SignableTransaction) whose tx spends `input_sat` yet creates
// a TxOut worth u64::MAX sats — an invalid transaction that TransactionMachine
// will still produce signatures for via taproot_key_spend_signature_hash.
let tx = res.unwrap();
// tx.fee() underflows: sum(prevouts) - sum(outputs) < 0 -> panic (debug) /
// wrapped u64 (release).
```

Exact supporting lines: unchecked `payment_sat + needed_fee` guard and wrapping `sum::<u64>()` at `networks/bitcoin/src/wallet/send.rs:187,215,228`; unchecked subtraction in `fee()` at `send.rs:139-141`; attacker-influenced amounts mapped straight into `payments` at `processor/src/networks/bitcoin.rs:433-452`.

One caveat on severity framing: exploitation requires the scheduler/processor to route an unaffordable payment amount into `make_signable_transaction` rather than rejecting it earlier; I verified the arithmetic path is unchecked, but did not fully trace whether an upstream layer clamps Burn amounts to a real balance. If upstream always bounds payments to available funds, this degrades to a defensive-check gap rather than a reachable exploit.
