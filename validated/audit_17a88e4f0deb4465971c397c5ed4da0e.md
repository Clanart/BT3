### Title
Case-alias file paths from a merge conflict bypass Copilot conflict-resolution duplicate checks and let one resolution silently clobber another - (File: `app/src/lib/path.ts`, `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
The external report's broken invariant is: a loop assumes each "entry" in a list uniquely identifies one underlying resource, string-deduplicates on that identifier, but the identifier can alias the same resource twice (Double Entry Point token ⇔ balance read twice ⇔ double credit). The GitHub Desktop analog is in the Copilot merge-conflict auto-resolution pipeline: `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:367-469`) and the resolution-apply step in the app store treat each conflicted **path string** as identifying one file. `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`) dedupes purely by string equality (`Set` of `resolution.path`). But `resolveWithin` (`app/src/lib/path.ts:36-100`) resolves paths through `realpath()` only for the *validation check* while returning the original (non-canonicalized) joined path string for actual use — so two differently-cased path strings that are the *same file* on a case-insensitive filesystem both pass validation as "different, valid" paths.

### Finding Description
- `matchExistingRepository` and the fixture repos confirm Desktop repos commonly run with `core.ignorecase = true` (see `app/test/fixtures/*/​_git/config`), the default on macOS/Windows.
- A malicious remote branch can be crafted so that merging it produces a merge conflict containing two case-only-different paths for what is the same file on disk (e.g. `Config.js` vs `config.js`), a well-known git edge case with case-insensitive core config.
- `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:367-469`) is fed the list of conflicted paths straight from git status/porcelain output and builds one `IFileConflictContext` per path string, without ever canonicalizing to the real on-disk file.
- `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`) only rejects duplicates when the returned path strings are byte-identical (`Set(resolutions.map(r => r.path))`), so `Config.js` and `config.js` are treated as two distinct, valid entries — exactly analogous to the vault's `_sort` failing to catch a Double Entry Point token because it dedupes on address, not on economic identity.
- In the write path (`app/src/lib/stores/app-store.ts:7171-7270`), each resolution is independently resolved via `resolveWithin(repository.path, resolution.path)` (`app/src/lib/path.ts:36-71`) and written with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`. `resolveWithin` calls `realpath()` only to confirm the target stays under the repo root — it still returns `resolved` (the case-preserving join of root + the model's path), not the canonical real path. On a case-insensitive filesystem both `Config.js` and `config.js` resolve (via realpath) to the same on-disk inode, but `resolveWithin` hands back two different string paths, and two separate `writeFile` calls occur against what is physically one file.
- The second `writeFile` silently overwrites the first's content. `pathsToStage` still contains both distinct path strings, and `git add -- Config.js config.js` is issued (`app-store.ts:7262-7267`); git (with `ignorecase=true`) will fold these into a single index entry reflecting only the last write.

### Impact Explanation
The user sees the resolution dialog and status report indicating both conflicts were "resolved" and staged, but only the last-applied resolution's content is ever committed — the other conflict's resolution (which may contain functionally different code, e.g. a security fix or a data-format change) is silently dropped without any error or warning. This is a silent corruption of what the user commits, driven entirely by attacker-controlled repository content (a crafted branch merged by the victim), matching the accepted "silent corruption of what the user commits or pushes" impact category. It requires no local/physical access, no prior malware, and no unnatural user steps beyond the normal "merge and resolve conflicts with Copilot" workflow.

### Likelihood Explanation
Requires: (1) the victim to merge/rebase a branch containing a case-only path conflict (attacker fully controls the branch content and can engineer this), (2) `core.ignorecase=true`, which is the default on macOS and Windows Desktop installs, and (3) the user to use the Copilot auto-resolve conflict feature. This is a realistic, low-effort setup for an attacker who can get a branch merged (fork PR, compromised collaborator branch, or supply-chain style repo). Likelihood is moderate — it needs a specific but easily engineered git state, and doesn't require any interaction beyond the feature's normal use.

### Recommendation
Canonicalize conflicted file identities before deduplication and before performing per-path writes: in `resolveWithin` (or immediately after it in `buildConflictContext`/the apply step), use the `realpath()`-resolved value (not the case-preserving `resolved` string) as the canonical key for both `validateResolutionPaths`'s duplicate check and the `pathsToStage`/write logic. Reject or merge conflict resolutions whose canonical real paths collide, the same way the SwapFacet fix recommends settling/consuming state per iteration so a later iteration cannot re-read stale, already-consumed state.

### Proof of Concept
1. Attacker prepares a branch that, when merged into the victim's current branch, produces a git conflict state containing two conflicted entries that differ only in case, e.g. `src/Config.js` and `src/config.js`, both marked as unmerged in `git status --porcelain=2` (achievable via a case-only rename/add on one side combined with a modify on the other, under `core.ignorecase=true`).
2. Victim opens Desktop, triggers Copilot conflict resolution. `buildConflictContext` (`copilot-conflict-context.ts:367-469`) builds two independent `IFileConflictContext` entries, one per path string, and reads/writes what is actually a single on-disk file.
3. Copilot's model returns two distinct `resolutions[]` entries for `src/Config.js` and `src/config.js` with different resolved contents. `validateResolutionPaths` (`copilot-conflict-resolution.ts:473-521`) passes because the two strings are not equal, so no duplicate error is raised.
4. In the apply step (`app-store.ts:7171-7270`), `resolveWithin(repository.path, "src/Config.js")` and `resolveWithin(repository.path, "src/config.js")` each pass the "inside repo" check (both realpath-resolve under root) and return two distinct path strings; `writeFile` is called twice against the same physical file, and `git add -- src/Config.js src/config.js` stages only whichever content was written last.
5. The commit dialog and result summary report both files as resolved/staged, but the repository history now silently contains only one of the two intended resolutions — the other is lost with no error surfaced to the user.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
): Promise<ICopilotConflictContext> {
  const results = await Promise.all(
    files.map(async (file): Promise<IFileConflictContext> => {
      // Delete-vs-modify conflicts have no text markers on disk. Include
      // them in the context with metadata so the model can recommend
      // keep or delete — no file content is needed.

          hunks: [],

          hunks: [],

        }
      }
```
