## Title
Bandwidth purchases pull funds before cross-chain acceptance is guaranteed, with no user-side refund path if `on_accept` fails or the manager is deregistered - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` performs an unconditional `safeTransferFrom` of the buyer's fee token *before* the ISMP dispatch to `pallet-bandwidth` is guaranteed to be honored on Hyperbridge, and the dispatch is sent with `timeout: 0`. If the pallet-side acceptance fails for any reason that is independent of `msg.sender`'s control (unconfigured tier, stale/rotated manager registration), the buyer's payment is permanently stuck in the `BandwidthManager` contract. There is no user-callable refund or withdrawal function; the only exit for funds sitting in the contract is the governance-only `Withdraw` action, which is authenticated purely as "any request from Hyperbridge" and sends to an arbitrary `beneficiary` chosen by governance — not necessarily the original buyer. This mirrors the referenced report's core defect: assets are escrowed on deposit but have no path back to the depositor short of a privileged actor intervening.

### Finding Description
`purchase()` in [1](#0-0)  pulls `amount` of the fee token from `msg.sender` into the contract and only afterwards dispatches a zero-fee, zero-timeout `BandwidthPurchaseMsg` POST to `pallet-bandwidth`. Because `timeout: 0`, the pallet explicitly treats any `on_timeout` invocation as an invariant violation rather than a recoverable path: [2](#0-1) . There is no timeout-driven refund mechanism at all.

On the Hyperbridge side, `on_accept` independently validates two things that the EVM-side `purchase()` cannot see: (1) that a `BandwidthManager` is currently registered for `request.source` and that `request.from` matches it exactly, and (2) that the target tier has a `TierConfig` on the pallet: [3](#0-2) . Both checks are enforced with `anyhow::anyhow!` errors, i.e. hard on_accept failures, not partial/degraded credits.

The docs confirm these two configuration axes are governed independently and can drift out of sync: "A tier is unconfigured until both sides have set it... Adding a tier requires a coordinated upgrade of the pallet enum and the manager contract" and governance can register/overwrite managers via `set_manager` at any time: [4](#0-3) , [5](#0-4) .

Concretely:
- Governance calls `set_manager(source, newManagerAddr)` to rotate/redeploy a chain's `BandwidthManager` (a routine, non-malicious admin operation, e.g. contract upgrade). Any `purchase()` transaction already broadcast against the *old* manager address that lands after the rotation will fail `on_accept`'s `request.from == manager.0` check (`"purchase from unauthorised sender"`), because the pallet now expects the new manager's address.
- Similarly, if a tier is revoked on the pallet (`set_tier(tier, None)`) while the EVM-side `tierPrice[tier]` is still non-zero (the two configs are updated by separate calls, `set_tier` vs `dispatch_set_tiers`), a buyer's `purchase()` call succeeds on-chain (manager's own check only inspects its local `tierPrice`) but fails at `on_accept` with `"tier ... is not configured"`.

In every one of these failure modes, the buyer's ERC-20 payment has already been transferred into `BandwidthManager` by the time the pallet rejects the message. The only function capable of moving tokens back out of the contract is the `Withdraw` governance action inside `onAccept`: [6](#0-5) , driven exclusively by `dispatch_withdraw` on the pallet: [7](#0-6) . That path sends to whatever `beneficiary` governance specifies — normally the protocol treasury — with no on-chain accounting tying a specific stuck balance back to the specific buyer who paid it. The buyer has no self-service recovery; recovery requires governance to notice the stuck balance and manually route it back, exactly the "guardian must remove liquidity" pattern in the referenced report.

### Impact Explanation
Funds move exactly once, into escrow, and then have no unprivileged exit. A buyer's fee-token payment can become permanently locked in `BandwidthManager` through ordinary, expected operational events (manager redeployment/rotation, or a tier being reconfigured on one side before the other), with no way for the buyer to reclaim it and no on-chain record linking the locked balance back to them for governance to make them whole. This is a direct loss-of-funds condition for the unprivileged caller of a public entrypoint (`purchase()`), consistent with the bounty's "loss of funds" impact category.

### Likelihood Explanation
No malicious actor, relayer, or prover is required. The failure is triggered purely by ordinary governance/config-lifecycle timing: `set_manager` rotation racing with in-flight purchases, or `set_tier`/`dispatch_set_tiers` updates being applied on one side before the other — both are documented as two independently-governed axes of the same feature (`docs/content/developers/evm/bandwidth/overview.mdx`). Given bandwidth tiers and manager addresses are expected to be updated over the system's operational lifetime, this is a realistic, recurring condition rather than a rare edge case.

### Recommendation
- Give `BandwidthManager` a user-triggered refund path: track `amount` and `payer` per dispatched commitment, and allow the original payer to reclaim the escrowed amount if the pallet reports (or a bounded time elapses without) a successful credit — effectively give purchases a real timeout/failure-refund lifecycle instead of `timeout: 0`.
- Alternatively/additionally, have `on_accept`'s hard failure paths (unregistered manager, unconfigured tier) surface into an on-chain refundable record, or reject the ISMP message in a way that pallet-ismp turns into a timeout back to the source chain, so the existing request/timeout machinery — not manual governance sweep — drives the refund.
- If governance sweeps are kept as a backstop, require the `Withdraw` action to reference the specific stuck purchase commitment(s) so funds are provably returned to the correct payer rather than swept to a generic treasury beneficiary.

### Proof of Concept
1. Governance registers `BandwidthManager` A for `source = EVM-8453` on `pallet-bandwidth` via `set_manager`, and configures tier `2` with a `TierConfig` and a matching non-zero `tierPrice[2]` on manager A.
2. A buyer calls `manager_A.purchase(app, tier=2, months=1, chain)`. `safeTransferFrom` pulls the fee token into manager A; the dispatch with `timeout: 0` is sent.
3. Before the message is delivered, governance redeploys the manager contract and calls `set_manager(EVM-8453, manager_B)` (e.g., for an upgrade).
4. The buyer's in-flight message is delivered to `pallet-bandwidth`'s `on_accept`. `BandwidthManager::<T>::get(&EVM-8453)` now returns `manager_B`, but `request.from == manager_A`, so the check at [8](#0-7)  fails with `"purchase from unauthorised sender"`.
5. No credit is issued, `on_timeout` never fires (`timeout: 0`), and the buyer's fee tokens remain in manager A with no callable function to reclaim them — only a governance-issued `Withdraw` to an arbitrary `beneficiary` can move them.

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

The fee tokens collected by `BandwidthManager.purchase()` accumulate in the manager contract. Governance drains them with `dispatch_withdraw`:

```rust
BandwidthPallet::dispatch_withdraw(
    RawOrigin::Root.into(),
    StateMachine::Evm(8453),
    fee_token_address,              // ERC-20 to withdraw. Use H160::zero() for native ETH.
    treasury_address,               // Beneficiary.
    U256::from(1_000_000_000u128),  // Amount, in fee-token decimals.
);
```

The pallet dispatches `[ACTION_WITHDRAW, abi.encode(Withdrawal)]` where `Withdrawal { token, beneficiary, amount }`. The manager's `onAccept` handler:

- If `token != address(0)`: `IERC20(token).safeTransfer(beneficiary, amount)`.
- If `token == address(0)`: `beneficiary.call{value: amount}("")` — reverts with `InsufficientNativeToken` if the call fails (insufficient balance, beneficiary rejects ETH, etc.).

The `token` field is named explicitly because the host occasionally swaps fee tokens (e.g. accepting native ETH on dispatch and routing through Uniswap). Stale balances of an old fee token still sit in the manager and are recoverable by specifying the old token's address.

Emits `Withdrawn(token, beneficiary, amount)` on the manager and `WithdrawalDispatched { target, token, beneficiary, amount, commitment }` on the pallet.
