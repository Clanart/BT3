### Title
Index-out-of-bounds panic on unvalidated `sender`/`recipient` `Participant` index in PedPoP blame evaluation - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

The Linea fix concerns a verification loop that trusted a range/index derived from attacker-influenced data and read one element past the end of a collection ("index out of range [N] with length N"). The same class exists in `pedpop`: `BlameMachine::blame_internal` and `AdditionalBlameMachine::blame` take `sender` and `recipient` as arbitrary `Participant` values (any non-zero `u16`) and index the `commitments` map with them via `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`), with no `contains_key`/range check. A participant index `> n` (e.g., `Participant::new(0xFFFF)` in a much smaller DKG) causes an unconditional panic inside blame adjudication.

### Finding Description

`Participant` only enforces non-zero (`crypto/dkg/src/lib.rs:29`), so the domain of accepted indexes is `1..=u16::MAX`, while `commitments` is populated exactly for `all_participant_indexes()` = `1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`, `crypto/dkg/src/lib.rs:195-198`). `blame()` forwards caller-supplied `sender`/`recipient` to `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:623-631`, `crypto/dkg/pedpop/src/lib.rs:674-682`), and `blame_internal` does `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) before any other validation. HashMap `Index` panics on a missing key, so any `sender ∈ (n, 65535]` — or any `sender` whose commitments were rejected/absent — crashes the evaluating party instead of returning `sender` as faulty. `AdditionalBlameMachine::new` is explicitly designed for arbiters that were *not* DKG members evaluating blame over other parties' messages (`crypto/dkg/pedpop/src/lib.rs:639-649`), i.e., it exists precisely to consume accusations whose `(sender, recipient)` pair originates from untrusted peers. Unlike the share-verification path, where `self.commitments[&l]` is safe because `l` was drawn from `validate_map`-checked keys (`crypto/dkg/pedpop/src/lib.rs:468-472`, `crypto/dkg/pedpop/src/lib.rs:57-83`), the blame path performs no equivalent validation.

### Impact Explanation

Blame evaluation runs after the DKG aborts and is the only mechanism for attributing fault. A malicious DKG participant (or an arbitrary accuser whose report is relayed to an arbiter) can include an out-of-range participant index in an accusation and crash every honest `BlameMachine`/`AdditionalBlameMachine` that processes it. In a validator/processor context where these messages come from other parties' transactions, this is a remotely triggerable panic: the node dies mid-blame-adjudication, preventing completion of blame handling and halting the dependent key-rotation/signing pipeline. Since `panic` is not `catch_unwind`-wrapped anywhere in this API, a single malformed accusation is sufficient — no collusion, no valid shares needed. This is an availability impact on the threshold-key infrastructure, rated Medium: it requires the panic to propagate in a context without task-level isolation.

### Likelihood Explanation

Triggering requires only that an accuser submit a blame claim with a `sender` index `> n` — a fully attacker-chosen field constrained only to be non-zero. `Participant` deserialization accepts any non-zero `u16` (`crypto/dkg/src/lib.rs:121-126`), so a 2-byte value suffices. Any party able to make an accusation processed by `blame()`/`AdditionalBlameMachine::blame()` can trigger it deterministically.

### Recommendation

Validate `sender` and `recipient` against `self.commitments`/`all_participant_indexes()` before indexing, e.g. `self.commitments.get(&sender).ok_or(...)`/early-return `sender` as faulty when the index is absent. Apply the same check in `AdditionalBlameMachine::new`/`blame` since it adjudicates third-party accusations. More broadly, replace all `map[&key]` indexing on attacker-derived `Participant` values in pedpop/dkg with `get` + error handling.

### Proof of Concept

```rust
// DKG with n = 3; arbiter builds an AdditionalBlameMachine from the 3
// commitment messages (each a valid EncryptionKeyMessage<C, Commitments<C>>).
let machine = AdditionalBlameMachine::<Secp256k1>::new(context, 3, commitment_msgs).unwrap();

// Attacker (or a confused/malicious accuser) submits blame naming a
// Participant that does not exist in this DKG.
let forged_sender = Participant::new(0xFFFF).unwrap(); // valid Participant, > n
let _ = machine.blame(
    forged_sender,          // never inserted into `commitments` (only 1..=3)
    Participant::new(1).unwrap(),
    msg,                    // any EncryptedMessage<C, SecretShare<C::F>>
    None,
);
// panic: `self.commitments[&sender]` in `blame_internal`
// (crypto/dkg/pedpop/src/lib.rs:599) — no entry found for key
```
