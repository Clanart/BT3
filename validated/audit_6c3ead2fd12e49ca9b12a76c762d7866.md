### Title
Unsanitized attacker-controlled PR head ref/clone URL used to add git remotes and construct branch refs during PR checkout - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_findPullRequestBranch`/`_checkoutPullRequest` in `app-store.ts` consume `headCloneUrl` and `headRefName` taken directly from the GitHub API's pull-request object (`pull.head.repo.clone_url`, `pull.head.ref`). These fields are populated by whoever created the PR — any GitHub user who opens a PR against a repository the victim has open in Desktop. Unlike the `openrepo://` deep-link path, which validates the `branch` query parameter with `testForInvalidChars` before use [1](#0-0) , this API-driven code path performs no equivalent validation before using the values to add a remote and build a ref name.

### Finding Description
When a user checks out a pull request (via the "Switch to this pull request" notification, the "Open in Desktop" PR link flow, or drag-and-drop cherry-pick), Desktop calls `_checkoutPullRequest`/`_findPullRequestBranch` with `headRepoOwner`, `headCloneUrl`, and `headRefName` sourced straight from the API response of the untrusted PR author [2](#0-1) [3](#0-2) .

Inside `_findPullRequestBranch`, if no existing remote matches the clone URL, Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the attacker-supplied clone URL, then concatenates the attacker-supplied `headRefName` into a ref string used to look up/checkout a branch: [4](#0-3) 

Neither `headCloneUrl` nor `headRefName` passes through `testForInvalidChars`/`sanitizedRefName` (used elsewhere for deep-link branch names, `app/src/lib/sanitize-ref-name.ts`) or any URL-scheme allowlist before being handed to `addRemote` and eventually `_createBranch`: [5](#0-4) 

By contrast, the equivalent attacker-controlled value on the deep-link path (`openrepo://…?branch=`) is explicitly checked against the ref-name character blocklist before use [1](#0-0) . This asymmetry means the invariant "any git ref/URL string that originates from an untrusted party must be validated before being used to construct a remote/ref" is enforced on the deep-link path but not on the PR-API path.

### Impact Explanation
If `addRemote`/the underlying git invocation does not defensively separate the URL argument from git flags (e.g. via a `--` separator), a PR head `clone_url` value such as `--upload-pack=/some/malicious/script` could be interpreted by git as an option rather than a remote URL, potentially resulting in arbitrary command execution when Desktop later fetches from that remote. Even absent argument-injection, an attacker-controlled clone URL/ref is used to silently create local git remotes and branches (`pr/<n>` naming) in the victim's checked-out repository, which is a form of corruption of the local repository state used for subsequent commits/pushes if the user is not careful about which remote/branch they are actually on.

### Likelihood Explanation
The trigger requires only that an attacker open a pull request against any repository the victim has cloned in Desktop, and the victim take a normal, expected action (clicking a PR checks/comment notification, "Open in Desktop", or drag-drop cherry-pick) — no local access, no leaked credentials, and no unnatural steps are required, satisfying the report's "attacker controls a GitHub API object" criterion. I was not able to fully confirm from local code alone whether the underlying `addRemote`/git-spawn implementation defends against argument-injection style clone URLs (I could not retrieve the body of `app/src/lib/git/remote.ts`'s `addRemote` or the process-spawning code within my search budget), so the severity of this specific path (argument injection vs. "merely" unsanitized ref/remote creation) is not fully verified and should be validated directly against `app/src/lib/git/remote.ts`.

### Recommendation
Apply the same validation used for deep-link branch names (`testForInvalidChars`/`sanitizedRefName`) to `headRefName` before constructing `remoteRef` in `_findPullRequestBranch`, and validate `headCloneUrl` against an expected git-URL shape (rejecting values beginning with `-`) before passing it to `addRemote`. Confirm that `addRemote`'s underlying git invocation uses an explicit `--` separator between options and positional URL/name arguments.

### Proof of Concept
1. Attacker opens a pull request against a public repository the victim has open in GitHub Desktop, from a fork whose `clone_url` or branch `ref` is crafted to begin with `-` (e.g. `--upload-pack=...`) — this requires only owning a fork, no privileged repo access.
2. Victim receives (or navigates to) the PR and clicks "Switch to this pull request" (e.g. from `pull-request-checks-failed.tsx`'s `onSubmit` or `pull-request-comment.tsx`'s `onSubmit`), triggering `dispatcher.checkoutPullRequest(repository, pullRequest)` [3](#0-2) .
3. This calls `_checkoutPullRequest` → `_findPullRequestBranch`, which passes the attacker-controlled `headCloneUrl` unmodified into `addRemote` [6](#0-5) .
4. Whether this results in git argument injection depends on the exact implementation of `addRemote`, which I could not inspect in this session — this should be verified directly in `app/src/lib/git/remote.ts` before treating this as a confirmed code-execution primitive.
