Looking at the authentication architecture in `servers.rs`, `interceptors.rs`, and `operator.rs` to trace the analog.

### Title
`Noop` Interceptor When `client_verification = false` Exposes `InternalWithdraw` and Privileged Operator gRPC Methods to Any Unauthenticated Caller — (`core/src/servers.rs`, `core/src/rpc/operator.rs`)

---

### Summary

`create_grpc_server` installs a `Noop` interceptor (zero authentication) when `client_verification = false`. The `InternalWithdraw` RPC — which triggers a payout transaction without the aggregator's ECDSA verification signature — has no independent authentication guard of its own. Any network-reachable caller can therefore invoke it, bypassing the `aggregator_verification_address` check that the sibling `Withdraw` RPC enforces. The misleading `BridgeConfig` comment ("Client certificates are always validated against the CA certificate according to mTLS regardless of this setting") is factually wrong when `client_verification = false`, because the server does not even request a client certificate in that branch.

---

### Finding Description

**Root cause — `servers.rs` lines 106–138:**

```rust
let tls_config = if config.client_verification {
    ServerTlsConfig::new()
        .identity(server_identity)
        .client_ca_root(client_ca)   // mTLS: client cert required
} else {
    ServerTlsConfig::new().identity(server_identity)  // no client cert at all
};

let service = InterceptedService::new(
    service,
    if config.client_verification {
        OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
    } else {
        Noop   // ← zero authentication
    },
);
``` [1](#0-0) 

When `client_verification = false` the TLS layer does not request a client certificate and the interceptor is `Noop`:

```rust
Interceptors::Noop => Ok(req),   // passes every request unconditionally
``` [2](#0-1) 

**Misleading config comment — `config/mod.rs` lines 134–138:**

```rust
/// Whether client certificates should be restricted to Aggregator and Self certificates.
///
/// Client certificates are always validated against the CA certificate
/// according to mTLS regardless of this setting.
pub client_verification: bool,
``` [3](#0-2) 

The comment is false: when `client_verification = false`, `client_ca_root` is never set, so the TLS layer does not validate any client certificate at all.

**Exposed privileged method — `rpc/operator.rs` lines 168–190:**

`InternalWithdraw` has no `aggregator_verification_address` check and no `cfg!(test)` guard:

```rust
async fn internal_withdraw(
    &self,
    request: Request<WithdrawParams>,
) -> Result<Response<RawSignedTx>, Status> {
    let (...) = parser::operator::parse_withdrawal_sig_params(request.into_inner())?;
    let payout_tx = self.operator.withdraw(...).await?;
    Ok(Response::new(RawSignedTx::from(&payout_tx)))
}
``` [4](#0-3) 

Compare with `Withdraw` (lines 192–258), which conditionally enforces the ECDSA verification signature:

```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // ... recover and compare address from sig ...
    return Err(BridgeError::ECDSAVerificationSignatureMissing).map_to_status();
}
``` [5](#0-4) 

`InternalWithdraw` is documented as "intended for operator's own use, so it doesn't include a signature from aggregator": [6](#0-5) 

The `OnlyAggregatorAndSelf` interceptor is the sole mechanism that enforces "self-only" access for `Internal*` methods:

```rust
if is_internal(&req) {
    if leaf_cert == our_cert { Ok(req) }
    else { Err(Status::unauthenticated("Unauthorized call to internal method (not self)")) }
}
``` [7](#0-6) 

When `client_verification = false`, this check never runs.

**Additional exposed methods under the same condition:**

- `InternalEndRound` — advances the operator's round state (spends collateral chain), gated only by `cfg!(feature = "automation")`, no cert check of its own.
- `InternalCreateSignedTxs` / `InternalCreateAssertCommitmentTxs` — return fully signed Bitcoin transactions. [8](#0-7) 

---

### Impact Explanation

An attacker who can reach the operator's TCP gRPC port when `client_verification = false`:

1. **Calls `InternalWithdraw`** with a valid `withdrawal_id`, the user's `SIGHASH_SINGLE|ANYONECANPAY` taproot signature, and the matching withdrawal UTXO. The operator's `withdraw()` logic validates the Citrea withdrawal UTXO and profitability, then broadcasts the payout transaction. The operator's fee-paying UTXOs are consumed and the withdrawal is finalized without the aggregator's ECDSA verification signature — bypassing the `aggregator_verification_address` guard entirely.

2. **Calls `InternalEndRound`** (automation build) to force the operator to advance its round state, spending the collateral chain out of sequence and potentially leaving the operator unable to respond to a pending challenge within the timelock window, risking collateral loss.

The payout destination is bound by the user's taproot signature, so direct BTC theft from the vault is not possible via this path alone. The material impacts are: operator fee-paying UTXO exhaustion, forced round advancement that can break the challenge-response safety window, and complete bypass of the `aggregator_verification_address` authentication layer.

---

### Likelihood Explanation

`client_verification = false` is not the default in the reference testnet4 config (`client_verification = true`), but:

- The misleading comment actively tells operators the CA validation still applies, making it plausible that an operator sets `false` believing only the "restrict to aggregator/self" policy is relaxed.
- The aggregator server creation code emits a `tracing::warn!` only when `client_verification = true`, implying `false` is the expected aggregator posture — operators may copy that pattern to their own verifier/operator configs.
- The Unix-socket path in `create_grpc_server` (lines 178–222) adds no `InterceptedService` wrapper at all, meaning any local process can call all methods including `InternalWithdraw` regardless of `client_verification`. [9](#0-8) [10](#0-9) 

---

### Recommendation

1. **Remove `Noop` as a valid production interceptor.** When `client_verification = false`, still install `OnlyAggregatorAndSelf` (or a weaker variant that at least rejects unauthenticated callers for `Internal*` methods). Never silently drop all authentication.

2. **Add a defense-in-depth check inside `InternalWithdraw`** that verifies the caller's peer certificate matches the operator's own client certificate, independent of the interceptor layer — mirroring the pattern used by `Withdraw`'s `aggregator_verification_address` check.

3. **Fix the misleading `BridgeConfig` comment** to accurately state that `client_verification = false` disables client certificate validation entirely, not merely the aggregator/self restriction.

4. **Apply the same `cfg!(test)` guard used in `InternalFinalizedPayout`** to `InternalEndRound` and `InternalCreateSignedTxs`, which are also described as test-only utilities.

---
