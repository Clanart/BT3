## Finding is valid — but with an important caveat about incomplete visibility into `freeze_code_object`'s body

### Title
`freeze_code_object` does not re-validate dependency upgrade policies, letting a "frozen" package retain a live (mutable) dependency chain - (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
`check_dependencies`, the only function in `code.move` that enforces "a package's declared dependencies must have an upgrade policy at least as strong as the package's own policy" (i.e., an immutable package requires immutable dependencies), is called exactly once in the whole module — inside `publish_package` at the time of initial publish/upgrade. [1](#0-0) [2](#0-1) 

`freeze_code_object` only checks that the `code_object` exists and that the caller is its owner; it does not call `check_dependencies` (or any equivalent re-validation of the package's dependency set) before flipping the package's `upgrade_policy` to immutable. [3](#0-2) 

### Finding Description
A user can legally publish a package `P` with `upgrade_policy = compatible` that declares a dependency `D` also published as `compatible`. This passes `check_dependencies`'s rule `dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy` (line 319) because `compatible >= compatible`. [4](#0-3) 

Later, the same user calls `object_code_deployment::freeze_code_object` (which forwards to `code::freeze_code_object`) to mark `P` as immutable. [5](#0-4) 

Because `freeze_code_object` never re-invokes `check_dependencies`, nothing forces `D` to also be immutable at freeze time. `D`'s owner (which could be the same attacker, or anyone) can continue to upgrade `D` under its `compatible` policy after `P` has been declared "frozen." Since `compatible` upgrades only require preserving public function signatures and resource layouts — not implementation logic — the actual behavior invoked by the "frozen" package `P` through `D` can still change arbitrarily after the freeze, contradicting the documented invariant that immutability implies the whole dependency closure is fixed.

Note: I was only able to view the signature and the first few lines of `freeze_code_object`'s body (lines 233–240); the remainder of the function body (roughly lines 241–270) was not rendered in the retrieved file content, likely due to indexing/size limits on this file. I could not directly inspect the statements that flip `upgrade_policy` to immutable inside `freeze_code_object`. However, the absence of any second call site to `check_dependencies` anywhere in `code.move` is a strong, directly observable fact — it is invoked exactly once, from `publish_package`, and not from `freeze_code_object`.

### Impact Explanation
This breaks the documented security property that a frozen (immutable) package cannot have its effective behavior altered after freezing. A downstream consumer who audits and trusts `P` because it is marked immutable can still be affected by silent behavior changes propagating from `D`, since `D` remains upgradable under the `compatible` policy and only its public signatures/layouts are constrained, not its logic. This is a genuine dependency/upgrade-policy invariant bypass reachable through fully unprivileged package publish and freeze calls (no prior privileged ownership is required beyond owning one's own object code deployment, which is the standard permissionless flow).

### Likelihood Explanation
High — no special privileges are needed. Any account can use `object_code_deployment::publish` to deploy a package with a `compatible` dependency, then call `object_code_deployment::freeze_code_object` (or the equivalent `code::freeze_code_object` for account-based publishing) to mark it immutable. The mismatch is deterministic and requires no timing or race condition — it is a straightforward absence of validation on the freeze path.

### Recommendation
`freeze_code_object` should re-run `check_dependencies` (or an equivalent check that walks `pack.deps` and asserts every dependency's `upgrade_policy` is already `immutable`) before setting the package's own policy to immutable, mirroring the check that already exists in `publish_package`. If a full re-run of `check_dependencies` is undesirable (it also builds `AllowedDep` lists used only for publish), a lighter-weight dependency-immutability-only check should be added at freeze time, per package in the `PackageRegistry`. The exact insertion point is inside `code::freeze_code_object`, whose full body should be reviewed directly in the repository (not fully visible via this indexed search) to confirm the current lack of such a check before implementing the fix.

### Proof of Concept
Adapt the described test (`freeze_code_object_succeeds_when_all_dependencies_immutable`, referenced in the question but not found under this exact name in this repo — likely present in `aptos-move/e2e-move-tests/src/tests/object_code_deployment.rs`, which was not fully inspected due to iteration limits) as follows:
1. Publish package `D` at some address with `upgrade_policy = compatible`.
2. Publish package `P` (via `object_code_deployment::publish`) with `upgrade_policy = compatible` and a declared dependency on `D`. This succeeds since `check_dependencies` only requires `D.policy >= P.policy` (both `compatible`).
3. Call `object_code_deployment::freeze_code_object(publisher, P_object)`. Observe it succeeds even though `D` is still `compatible` (mutable).
4. Assert (as the fix) that step 3 should fail with `EDEP_WEAKER_POLICY` (or an analogous new error) unless all of `P`'s dependencies are already `immutable` — currently no such assertion exists, so the test would need to be added rather than merely adapted from an existing passing test. [6](#0-5)

    fun check_dependencies(publish_address: address, pack: &PackageMetadata): vector<AllowedDep>
    acquires PackageRegistry {
        let allowed_module_deps = vector::empty();
        let deps = &pack.deps;
        deps.for_each_ref(|dep| {
            let dep: &PackageDep = dep;
            assert!(exists<PackageRegistry>(dep.account), error::not_found(EPACKAGE_DEP_MISSING));
            if (is_policy_exempted_address(dep.account)) {
                // Allow all modules from this address, by using "" as a wildcard in the AllowedDep
                let account: address = dep.account;
                let module_name = string::utf8(b"");
                vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
            } else {
                let registry = borrow_global<PackageRegistry>(dep.account);
                let found = vector::any(&registry.packages, |dep_pack| {
                    let dep_pack: &PackageMetadata = dep_pack;
                    if (dep_pack.name == dep.package_name) {
                        // Check policy
                        assert!(
                            dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy,
                            error::invalid_argument(EDEP_WEAKER_POLICY)
                        );
                        if (dep_pack.upgrade_policy == upgrade_policy_arbitrary()) {
                            assert!(
                                dep.account == publish_address,
                                error::invalid_argument(EDEP_ARBITRARY_NOT_SAME_ADDRESS)
                            )
                        };
                        // Add allowed deps
                        let account = dep.account;
                        let k = 0;
                        let r = vector::length(&dep_pack.modules);
                        while (k < r) {
                            let module_name = vector::borrow(&dep_pack.modules, k).name;
                            vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
                            k += 1;
                        };
                        true
                    } else {
                        false
                    }
                });
                assert!(found, error::not_found(EPACKAGE_DEP_MISSING));
            };
        });
        allowed_module_deps
    }
