## Finding: Unvalidated Arbitrary File Deletion via `delete_plot` Harvester RPC — (File: `chia/plotting/util.py`)

### Summary
The harvester's `delete_plot` RPC endpoint accepts an attacker/operator-supplied `filename` string and passes it straight to `remove_plot()`, which performs an unconditional `Path(path).unlink()` with no check that the path resides within any configured plot directory, has a `.plot`/`.plot2` extension, or is even a regular plot file. This is the same bug class as CVE-2020-18190 (path/parameter-controlled unlink with no containment check): any caller able to reach this RPC endpoint can delete an arbitrary file on the harvester's filesystem.

### Finding Description
The RPC handler extracts `filename` directly from the untrusted request body and forwards it unchanged: [1](#0-0) 

This calls into `Harvester.delete_plot()`, which does not resolve or validate the path against the harvester's known plot directories (`plot_manager.plots`, `get_plot_directories()`), it simply forwards to the low-level `remove_plot()` utility: [2](#0-1) 

The utility function performs no path normalization, no containment check against configured plot directories, no extension check, and no verification that the path corresponds to an entry actually tracked by `PlotManager`: [3](#0-2) 

Any string can be supplied as `filename` — including absolute paths outside of `plot_directories`, or relative paths using `../` traversal from the process's working directory — and `remove_plot()` will delete it if it exists and the process has permission, regardless of whether it's a plot file or something else entirely (config files, database files, keyring files, etc., depending on process permissions and the RPC caller's chosen path).

### Impact Explanation
A local RPC caller reaching the harvester's `/delete_plot` endpoint can delete arbitrary files reachable by the harvester process user, not just files inside configured plot directories. This can be used to destroy plot files belonging to other users/paths, corrupt or remove harvester/farmer configuration or database files, or otherwise cause data loss and denial of service for the farming operation — with no ownership or containment check gating the operation.

### Likelihood Explanation
The endpoint is reachable by any client holding valid harvester RPC credentials (the "local RPC caller" persona explicitly in scope). There is no additional authorization layer beyond RPC access; the code path performs the deletion unconditionally as long as the target path exists on disk, requiring only knowledge/guessing of a target path.

### Recommendation
In `remove_plot()` (or in `HarvesterRpcApi.delete_plot`/`Harvester.delete_plot`), resolve the supplied path and verify it is (a) an exact match to an entry currently tracked in `PlotManager.plots`/`failed_to_open_filenames`, or (b) canonicalizes to a location strictly inside one of the configured plot directories, before calling `unlink()`. Reject the request otherwise.

### Proof of Concept
1. Obtain valid harvester RPC access (local RPC caller).
2. Call the `delete_plot` RPC with a `filename` pointing outside any configured plot directory, e.g. a path to the harvester's own config file or another user's file that the process has permission to delete:
```
POST /delete_plot
{"filename": "/home/user/.chia/mainnet/config/config.yaml"}
``` [1](#0-0) 
3. `Harvester.delete_plot()` forwards the path unchanged to `remove_plot()`, which unlinks it without any containment or ownership check. [3](#0-2)
