### Title
`ThresholdKeys::read` deserializes an inconsistent key (secret share vs. verification shares / interpolation coefficients) without semantic validation, causing self-attributed blame — (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to `createNewEpoch` accepting unvalidated parameters, `ThresholdKeys::read` in `crypto/dkg/src/lib.rs` reconstructs a `ThresholdKeys` object from untrusted bytes while checking only *structural* properties (canonical encodings, participant bounds, share count). It never validates the *semantic* consistency of the loaded parameters: that the deserialized `secret_share` corresponds to `verification_shares[params.i]` (`G * secret_share == verification_shares[i]`), nor that the `Interpolation::Constant` coefficients are consistent with the committed verification shares. The resulting struct is used directly for FROST signing, producing a state machine with an incorrect configuration.

### Finding Description
`ThresholdKeys::read` reads the curve ID, `(t, n, i)`, the interpolation variant, the `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new`. `ThresholdKeys::new` only checks that `verification_shares.len() == n`, that all participant indexes are `≤ n`, and that `Constant` interpolation is only used when `t == n`. No check verifies `C::generator() * secret_share == verification_shares[i]` — the exact analog of the missing `newBasisPoints`/parameter-consistency checks in the report. Likewise, for `Interpolation::Constant`, the `n` coefficients read from the stream are never validated against the verification shares, so `interpolation_factor` returns attacker-chosen weights `c[i-1]` with no relation to the committed shares. The code itself acknowledges the consequence: `AlgorithmSignatureMachine::complete` in `crypto/frost/src/sign.rs` notes "The only known way to cause this... is to deserialize a semantically invalid FrostKeys."

### Impact Explanation
An unprivileged party able to supply the serialized `ThresholdKeys` bytes (the explicitly in-scope `ThresholdKeys::read` path) causes the victim to initialize FROST with an inconsistent key configuration — the analog of an incorrectly initialized epoch. Concretely:

- The victim's `view()`/`sign_share` computes shares under a `secret_share` and interpolation factors that do not match the group-committed verification shares.
- In `AlgorithmSignatureMachine::complete`, per-share batch verification (`verify_share` → `BatchVerifier::verify_vartime_with_vartime_blame`) fails and returns `FrostError::InvalidShare(l)` attributing fault to participants whose shares were in fact generated honestly — including the victim's own index, which is reported back by the processor as an `InvalidParticipant`/`InvalidShare` accusation, feeding the blame/slashing pipeline.
- Worse, the all-shares-valid-yet-invalid path hits `FrostError::InternalError`, which the processor/coordinator call sites treat as `unreachable!()` / panic, crashing the signing task.

Either way the outcome is an operational integrity failure for the validator (unjustified fault attribution/slashing risk or abort), mirroring the report's "incorrect or undesirable configurations" classification.

### Likelihood Explanation
Exploitation requires attacker control of the `ThresholdKeys` byte stream (e.g., any path loading keys from non-secret-attested storage or transport). That is a narrower reach than a pure on-chain input, matching the Medium severity of the source report: it requires a specific supply path, but once reached, every signature attempt deterministically misattributes blame or panics. Within FROST itself no further conditions are needed — the malformed state is used unconditionally on the next `sign`/`complete`.

### Recommendation
Add semantic validation in `ThresholdKeys::new`/`read` so the deserialized parameters are proven consistent before use:
- `C::generator() * secret_share == verification_shares[params.i()]` — reject otherwise.
- For `Interpolation::Constant(c)`, verify the coefficients are consistent with the verification shares (e.g., recompute `verification_shares[i] == G * Σ_j c[j]·i^j` for the relevant participants, or at minimum that the implied group key matches `group_key` derived from the verification shares).
This rejects malformed configurations at initialization instead of at signing time, exactly as the report recommends validating `createNewEpoch` parameters up front.

### Proof of Concept
1. Take a valid `ThresholdKeys::serialize()` output for params `(t = n = 2, i = 1)`, `Interpolation::Constant([c0, c1])`, share `s_1`, shares `{1: V1, 2: V2}` where `V1 = s_1·G`.
2. Mutate only the `secret_share` field to `s'_1 = s_1 + 1` (still canonical). `read_F`/`read_G` accept all encodings; `ThresholdParams::new(t, n, i)` and the count/index checks in `ThresholdKeys::new` pass, so `ThresholdKeys::read` returns `Ok`.
3. Use the loaded keys in `AlgorithmMachine::new(alg, keys).preprocess(..)` then `sign(..)` for a 2-of-2 set. The victim emits `share = d'·λ + nonce terms` where `d'·G ≠ V1`.
4. In `complete`, the summed `s` fails `algorithm.verify`, so the batch blame loop runs `verify_share` for each `l`; the victim's own share fails against `view.verification_share(i)`, producing `FrostError::InvalidShare(own_i)` — a false self-accusation — or `InternalError` if statements pass inconsistently. The processor's `unreachable!()` arms on `InternalError` turn the misconfiguration into a crash/abort, and `InvalidShare(own_i)` propagates as an `InvalidParticipant` message blaming the victim.

Alternatively mutate the Constant coefficients `c` while keeping shares fixed: `interpolation_factor` (dkg/src/lib.rs `Interpolation::Constant(c) => c[i-1]`) then yields attacker-chosen weights, again desynchronizing the emitted share from the committed verification share with the same outcome.
