### Title
OP_RETURN data output omitted from fee/weight calculation causes transactions to under-pay fees and become un-relayable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes value becoming locked because a code path that should account for it (`withdrawETH` handling ETH vs. WETH) does not exist. The Serai analog is in `SignableTransaction::new`: when an `OP_RETURN` data output is attached, it is pushed into the real transaction's output list but is never included in the transaction passed to `calculate_weight_vbytes`. The fee, the change-amount, the minimum-relay check, and the max-weight check are therefore all computed on a smaller transaction than the one actually produced — value accounting that silently omits an entire output, exactly the class of "funds handled by a path that doesn't see them".

### Finding Description
`SignableTransaction::new` pushes the `OP_RETURN` output into `tx_outs` before estimating weight:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` rebuilds a `Transaction` from `payments` only (lines 62–99), so `vbytes` — and therefore `needed_fee = fee_per_vbyte * vbytes` (line 206) — excludes the OP_RETURN output (up to 80 bytes of data plus output overhead). The same omission propagates to `fee_with_change` (lines 225–227), so when change exists the change output is inflated by the missing fee and the *actual* fee stays at the underestimated value. Consequences:

- The real transaction pays a systematically lower fee rate than the caller requested. With a single input, one payment, change, and 80 bytes of data at `fee_per_vbyte = 1`, the actual rate drops to roughly 0.5–0.6 sat/vB — below `DEFAULT_MIN_RELAY_TX_FEE` — so the signed transaction is rejected by Bitcoin nodes and the inputs' funds are frozen until the transaction is reconstructed without the bug.
- The `TooLowFee` guard (line 211) cannot catch this because it uses the same underestimated `vbytes`.
- `needed_fee()` misreports the fee to integrators using it for accounting.
- The `TooLargeTransaction` check (line 241) uses `weight` that omits the data output, so a transaction near `MAX_STANDARD_TX_WEIGHT` can pass the check yet produce a non-standard transaction.

The `data` field is attacker-influenceable: in Serai's protocol flow, `InInstruction` data supplied by depositors is embedded into transactions the multisig builds, so an unprivileged party controls the size of the omitted output and can maximize the under-payment at low requested fee rates.

### Impact Explanation
Any `SignableTransaction` carrying data pays less than the requested fee rate; at the lowest legitimate rates the transaction falls under the network minimum relay fee, is rejected on broadcast, and the funds it spends remain locked until a corrected transaction is built. Fee accounting reported via `needed_fee()` is wrong whenever data is attached, and the standardness weight check is unsound. This mirrors the source report's "value passes through a path that never accounts for it" defect.

### Likelihood Explanation
Every transaction built with `data.is_some()` miscomputes its fee — no edge-case timing required. Whether it crosses the min-relay threshold depends on the configured fee rate and input count; at 1 sat/vB even modest data suffices. Depositors supplying `InInstruction` data make the mis-sizing attacker-tunable.

### Recommendation
Include the OP_RETURN output in the weight estimation — e.g., pass the fully built `tx_outs` (or `payments` plus the data output) into `calculate_weight_vbytes` for both the change and no-change paths, so `needed_fee`, `TooLowFee`, and `TooLargeTransaction` reflect the transaction actually produced.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs logic, with fee_per_vbyte = 1
let tx = SignableTransaction::new(
  vec![one_input],                        // e.g. ~58 vB P2TR input
  &[(payment_script, 1000)],              // one payment
  Some(change_script),                    // change absorbs fee difference
  Some(vec![0xAA; 80]),                   // OP_RETURN, ~90 vB of output
  1,
).unwrap();

// vbytes computed from inputs+payments+change only; OP_RETURN (~90 vB) excluded
// needed_fee = ~160 sat, actual tx vsize ≈ 250 vB
// tx.fee() == needed_fee (change absorbed the rest) → effective rate ~0.64 sat/vB
// < DEFAULT_MIN_RELAY_TX_FEE → send_raw_transaction rejects it; inputs frozen
```
