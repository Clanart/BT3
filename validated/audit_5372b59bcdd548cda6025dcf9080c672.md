## Finding: Asymmetric Decimal-Scaling Bug in `pallet-hyper-fungible-token` Causes Silent Value Corruption

### Title
Cross-chain decimal-scaling helpers `convert_to_balance`/`convert_to_erc20` silently drop scaling when local decimals exceed remote decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` was built specifically to fix the exact bug class in the external report — it stores per-chain ERC20 `Precisions` and rescales amounts at the send/receive boundary [1](#0-0) . However, the two conversion helpers that perform this rescaling are not symmetric: they only correctly scale when the remote (ERC20) side has **more or equal** decimals than the local asset. When the local asset's decimals exceed the remote side's decimals, `u8::saturating_sub` clamps the exponent to zero and the raw value is passed through unscaled, reproducing exactly the "silent value corruption on mint" bug from the report.

### Finding Description
The core conversion logic:
```rust
// modules/pallets/hyper-fungible-token/src/impls.rs:43-58
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [2](#0-1) 

Both functions assume `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals`, `saturating_sub` returns `0`, so the multiplier/divisor becomes `10^0 = 1` and **no scaling is applied at all** — the raw numeric value crosses the chain boundary unchanged, exactly as in the reported Wormhole bridge bug.

This helper is called on both the outbound (`send`) and inbound (`on_accept`/`on_timeout`) paths:
- Outbound: `convert_to_erc20(amount, erc_decimals, decimals)` where `decimals` is read dynamically from the local asset via `fungibles::metadata::Inspect::decimals` [3](#0-2) .
- Inbound: `convert_to_balance(message.amount, erc_decimals, decimals)` with the same dynamic decimals lookup [4](#0-3) , and identically in `on_timeout` [5](#0-4) .

Critically, `local_decimals` is **not** the value validated/stored at `register_token` time — it is fetched live from the `Assets` pallet's metadata on every call. The benchmark code comment confirms an intended invariant that "`register_token` rejects an evm side with fewer decimals than the local asset" [6](#0-5) , meaning the protection (if it exists) is only a registration-time check against the *decimals value observed at registration*. `pallet-assets` metadata (including `decimals`) can be mutated after asset creation via `set_metadata`, which is callable by the asset's own admin/owner — an account that need not be the bridge's `CreateOrigin`. If the local asset's decimals are later increased above the registered `erc_decimals` (a normal, non-privileged, non-adversarial operational action available to any asset admin, not the bridge governance), every subsequent `send`/`on_accept`/`on_timeout` call for that asset silently stops scaling, causing:
- Outbound: the ERC20 side receives an amount `10^(local_decimals - erc_decimals)` times **larger** than intended → inflation on mint on the destination EVM chain.
- Inbound: the local side mints/unlocks an amount `10^(local_decimals - erc_decimals)` times **smaller** than intended → value destruction for the recipient (and value stuck on the EVM side since the burn already happened there).

### Impact Explanation
This is a direct fund-loss / fund-inflation bug matching the bounty's impact categories ("stealing or loss of funds", "transaction manipulation", "logic attacks"). Any transfer through `send()` while the decimal relationship is inverted mints/unlocks the wrong amount without reverting, without an event flag, and without any error — the transaction succeeds and appears legitimate on-chain. Because the scaling arithmetic silently no-ops instead of failing, there is no automatic circuit breaker; every transfer for the misconfigured asset is corrupted, and value can be minted on the EVM side far in excess of what was escrowed/burned on the substrate side (classic "mint from nothing" scenario).

### Likelihood Explanation
The asset's decimal metadata is fetched dynamically at each call rather than pinned at registration, so any change to an asset's `decimals` metadata after `register_token`/`update_token` (a routine, permissionless-adjacent, non-admin action available to whoever controls that asset's metadata in `pallet-assets`) flips the vulnerable branch on. No relayer collusion, no compromised prover, and no bridge-governance action is required — only a legitimate asset-metadata update on a bridged asset already registered with the pallet, following which ordinary users' `send` calls corrupt value.

### Recommendation
- Snapshot and store `local_decimals` in the `Precisions`/registration storage at `register_token` time instead of re-querying live metadata on every send/receive, and require `update_token`/`update_asset_precision` to explicitly refresh it.
- Make `convert_to_balance`/`convert_to_erc20` symmetric and safe: explicitly branch on whether `erc_decimals >= local_decimals` or vice versa, and use checked (not saturating) exponent arithmetic so any decimals mismatch it can't resolve returns an error rather than silently defaulting to a no-op scale factor.
- Add an invariant check in the message-processing path that rejects a transfer if the derived scale factor is `1` while `erc_decimals != local_decimals`, since that specific combination is the failure signature of the saturating-sub bug.

### Proof of Concept
1. Register asset `X` (local decimals = 6) via `register_token` with an EVM chain configured at `decimals = 18` (satisfies the registration-time check erc_decimals(18) >= local_decimals(6)).
2. Asset `X`'s owner (any non-bridge-admin account with authority over that asset in `pallet-assets`) later calls `pallet_assets::set_metadata` to change `X`'s decimals from 6 to 24.
3. A user calls `HyperFungibleToken::send` with `asset_id = X`, `amount = 1_000_000` (1.0 token at old 6-decimal assumption, now interpreted as 24-decimal precision).
4. Inside `send`, `decimals` is read live as `24`, `erc_decimals = 18`. `convert_to_erc20(amount, 18, 24)` computes `18u8.saturating_sub(24) = 0`, so `erc20_amount = amount * 10^0 = 1_000_000` unchanged [7](#0-6) .
5. The correct value should have been divided by `10^6` (down-scaled from 24 to 18 decimals) — the value has instead been passed through 1,000,000x too large, and the EVM `onAccept` mints an inflated amount to the beneficiary relative to what was burned/escrowed on the substrate side.
