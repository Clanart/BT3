### Title
Webhook HMAC verification does not bind the request payload to the `X-Shopify-Shop-Domain` header, enabling cross-shop webhook spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates an incoming webhook solely by validating an HMAC over the raw request body against the app's shared client secret. The `shop_domain` used to route/process the webhook is read directly from the `X-Shopify-Shop-Domain` header, which is *not* covered by the HMAC. Because the same signing secret is shared across every shop that has installed the app, any merchant who legitimately receives real, validly-signed webhooks for their own shop can replay that exact (body, HMAC) pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The verification logic accepts this as authentic, causing attacker-controlled payloads to be processed under another shop's identity — an analog of the reported bug class where one component (the "vault"/HMAC over the body) is verified for authenticity but a critical, coupled identity value (the "TwabController/PrizePool"/shop-domain claim) is never checked against that same trust anchor.

### Finding Description
`WebhookVerification#verify_request` computes/validates HMAC over `request.raw_post` only: [1](#0-0) 

`shop_domain` is derived independently from a request header with no cryptographic tie to the verified payload: [2](#0-1) 

`hmac_valid?` in `PayloadVerification` reinforces that only the body (`data`) is signed/verified, with no shop-domain or header binding: [3](#0-2) 

Downstream, generated job/controller templates trust the header-derived shop value to select tenant context and process the payload as that shop's data: [4](#0-3) [5](#0-4) 

Because the HMAC secret (`ShopifyApp.configuration.secret` / `old_secret`) is shared by the app across all installed shops rather than being unique per shop, any authorized (even low-trust) merchant installer can capture a genuinely signed webhook delivered to them and resend it to the same endpoint with a modified `X-Shopify-Shop-Domain` header pointing at a different (victim) shop. The signature check passes because it only re-verifies the untouched body, and the shop-scoping logic then attributes the attacker's payload to the victim shop.

### Impact Explanation
This allows a malicious or compromised merchant with the app installed to inject a forged, "verified" webhook that gets processed under a different shop's tenant context. Depending on what the app's webhook jobs do (e.g. update order/product records, trigger `shop.with_shopify_session` API calls, mutate billing or fulfillment state), this constitutes a cross-shop/cross-tenant forged-request acceptance: an accepted forged signed request that lets one tenant inject data or side effects into another tenant's processing pipeline, which is the exact analog class called out in the report — trusting a component ("valid HMAC") as a proxy for full authenticity while not validating a coupled critical claim (the shop identity carried in the header).

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate installer of the target Shopify app (any merchant who installs a public/embedded app gets real webhooks delivered and can intercept/replay them, since the shared secret is not shop-specific and Shopify does not need HTTPS-hidden knowledge beyond a normal MITM-free capture of their own traffic). No secret compromise or elevated privilege is required beyond being any installer of the app, which is inherent to the multi-tenant nature of Shopify apps using `shopify_app`'s default webhook verification, making this readily reachable from an unrelated-merchant HTTP request.

### Recommendation
Bind the verified identity to the signed payload rather than trusting an unauthenticated header:
- Where the webhook body/topic includes shop-identifying data (e.g. via `ShopifyAPI::Webhooks::Request`), cross-check that the resolved `shop_domain` matches a shop record whose stored webhook/session state is consistent with the payload, and reject mismatches.
- Prefer per-shop unique webhook signing where available, or additionally validate that the `X-Shopify-Webhook-Id`/topic and shop combination is one the app actually expects/has an active session for before processing, rejecting webhooks for shops without an active, matching installation record prior to job dispatch.
- Document/require downstream job authors to re-validate `shop_domain` against `Shop.find_by(shopify_domain:)` and treat it as untrusted input needing authorization checks tied to the actual signing context, not solely to route data.

### Proof of Concept
1. Install the target app as Merchant A (attacker), who legitimately receives real webhooks from Shopify signed with the app's shared secret, e.g. `carts/update` with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's `secret`.
2. Capture one such request (body + valid HMAC header) from Merchant A's own traffic.
3. Replay the identical POST to the app's webhook endpoint (`POST /webhooks/carts_update`), keeping the body and `X-Shopify-Hmac-Sha256` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because the body/HMAC pair is untouched and validated against the shared secret — independent of the domain header. [6](#0-5) 
5. The webhook is routed/processed with `shop_domain = "victim-shop.myshopify.com"`, and generated job code looks up `Shop.find_by(shopify_domain: shop_domain)` and executes `shop.with_shopify_session` using the attacker's forged payload, attributing it to the victim shop. [7](#0-6)

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
