### Title
Empty aggregate Schnorr signatures verify as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` accepts an aggregate containing zero nonces and a zero scalar, while `SchnorrAggregate::verify` accepts it when supplied an empty `keys_and_challenges` list. [1](#0-0) [2](#0-1)  This is a fail-open analog: an empty credential/signature set is treated as successfully authenticated instead of being rejected.

### Finding Description
`SchnorrAggregate::read` deserializes an attacker-controlled `u32` count without requiring it to be nonzero, then reads that many `R` values followed by scalar `s`. [1](#0-0)  `verify` only checks that `Rs.len()` equals `keys_and_challenges.len()`, so two empty lists pass the structural check. [3](#0-2)  With no signatures, the verification multiexponentiation contains only `-sG`; if `s = 0`, it is identity and verification returns true. [4](#0-3)  The legitimate aggregation API refuses to produce an empty aggregate by returning `None`, confirming that an empty aggregate is not a valid signature object. [5](#0-4) 

### Impact Explanation
An unprivileged party can forge bytes which deserialize to an accepted aggregate signature without possessing any private key. [1](#0-0) [4](#0-3)  Any caller which obtains an empty verifier set through missing configuration, failed key lookup, or attacker-influenced input and relies on `verify` as an authorization check will incorrectly accept the forged aggregate. [2](#0-1) 

### Likelihood Explanation
The forged encoding is deterministic and requires no brute force, secret material, or valid signer participation. [1](#0-0)  Exploitation requires the verifier path to invoke `verify` with an empty `keys_and_challenges` slice rather than rejecting that condition before verification. [3](#0-2)  Because `SchnorrAggregator::complete` cannot legitimately create this state, accepting it from deserialization is a verifier fail-open rather than intended aggregate behavior. [5](#0-4) 

### Recommendation
Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`. [1](#0-0) [3](#0-2)  `verify` should require `keys_and_challenges` to be nonempty before evaluating the multiexponentiation, matching `SchnorrAggregator::complete`’s refusal to emit an empty aggregate. [4](#0-3) [5](#0-4)
