### Title
Unverified minting-time DID association allows self-grant of higher-tier NFT provenance/collection status - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
The Discourse bug allowed a user who paid for a lower subscription tier to self-assign higher-tier benefits because the client-supplied "which tier am I" value was trusted without server-side verification against an authoritative grant. The Chia analog is in NFT minting: when an NFT is minted with DID ownership (`did_id` parameter), the eve spend's ownership layer can be curried with **any** DID value chosen entirely by the minter, and the code explicitly acknowledges this is unauthenticated until a later DID-signed transfer occurs.

### Finding Description
`NFTWallet.generate_new_nft()` builds the eve NFT coin's ownership layer using a DID value supplied directly by the caller, with no on-chain proof that the named DID actually approved or "owns" this NFT: [1](#0-0) 

The code contains its own explicit warning about this: [2](#0-1) 

which states verbatim: "eve coin DID can be set to whatever so we keep it empty — WARNING: wallets should always ignore DID value for eve coins as they can be set to any DID without approval." This value flows into `create_ownership_layer_puzzle()`/`construct_ownership_layer()` and becomes the on-chain `current_owner` field of the singleton's ownership layer puzzle hash for the eve coin: [3](#0-2) 

The same unverified value is also persisted locally as `minter_did` and surfaced through the wallet's NFT info/records: [4](#0-3) 

Only a subsequent DID transfer/update spend cryptographically proves ownership by requiring a message spend from the actual DID singleton and asserting matching announcements (as tested in `test_ownership_layer`/`test_default_transfer_program`, which show `ASSERT_ANNOUNCE_CONSUMED_FAILED` when the DID's own announcement is missing): [5](#0-4) 

But the *eve* coin itself — the very first, freshly-minted state of the NFT that every wallet/marketplace/offer sees immediately after mint — carries a self-declared DID with zero cryptographic proof of authorization from that DID. Any code path (wallet UI, marketplace indexer, offer-matching logic, royalty/collection-tier logic) that reads this pre-confirmation `owner_did`/`minter_did` value as evidence of legitimate collection membership is trusting a value that is, by the code's own admission, attacker-controlled.

### Impact Explanation
This is directly analogous to "self-grant to higher tier": a user who has not obtained authorization from a curated/verified DID (e.g., a well-known creator's DID used to signal an authentic, higher-value NFT collection) can mint an NFT that *appears* to belong to that DID's collection from the moment of minting. Any downstream consumer — offer construction/matching, royalty calculation keyed off DID-based collection identity (`NFTWallet.royalty_calculation`, `make_nft1_offer`), or a counterparty inspecting `minter_did`/`owner_did` before accepting a trade — can be deceived into treating a self-labeled, unauthorized NFT as if it were vetted/verified. This enables offer-settlement deception: a taker could pay a premium (higher trade price / royalty expectation) for what is presented as a DID-verified collection item that the real DID never approved, resulting in economic loss for the counterparty (offer settlement theft by forged asset identity/provenance).

### Likelihood Explanation
Likelihood is high for the "cosmetic/provenance forgery" variant: any wallet can call `generate_new_nft` with an arbitrary `did_id` and no signature from that DID is required at mint time; this is a single, unprivileged wallet action requiring no special access. The residual risk depends entirely on whether any code (in this repo or a marketplace/dApp built on top) treats the *unconfirmed* eve-coin DID field as proof of authorized affiliation instead of waiting for a verified DID transfer/update spend — the codebase itself flags this as a known trap ("WARNING: wallets should always ignore DID value for eve coins").

### Recommendation
- Ensure all wallet-side and RPC-surfaced NFT metadata (`minter_did`, `owner_did`, NFTInfo fields) is clearly marked as unverified/pending until a DID-authorized transfer/update spend has been observed and validated on-chain.
- Any offer-building, royalty, or collection-membership logic that keys off DID association must require proof of a DID-signed transfer (the announcement-based mechanism already used for `transfer_did`/ownership updates) rather than trusting the eve-coin curried DID value.
- Consider surfacing a distinct "unverified/self-declared minter DID" flag through the RPC/NFTInfo so downstream consumers (marketplaces, offer UIs) cannot mistake it for verified provenance.

### Proof of Concept
1. Call `NFTWallet.generate_new_nft(metadata, action_scope, target_puzzle_hash, royalty_puzzle_hash, percentage, did_id=<any bytes32 the attacker does not control>)`.
2. The resulting eve NFT coin's ownership layer is curried with `current_owner = did_id` via `create_ownership_layer_puzzle` → `construct_ownership_layer`, with no signature or spend from that DID (see `nft_wallet.py:501-509`, `nft_puzzle_utils.py:180-211`).
3. `minter_did` is stored locally and reported via wallet/RPC NFT info as if authoritative.
4. A counterparty or marketplace that reads this DID before the NFT undergoes a genuine DID-authorized transfer spend (which is the only point at which an `AssertCoinAnnouncement`/`CreateCoinAnnouncement` from the real DID singleton is enforced, per `test_ownership_layer`/`test_default_transfer_program`) will treat the NFT as belonging to that DID's (potentially higher-tier/verified) collection despite no approval ever having occurred on-chain.

```python
def construct_ownership_layer(
    current_owner: bytes32 | None,
    transfer_program: Program,
    inner_puzzle: Program,
) -> Program:
    return NFT_OWNERSHIP_LAYER.curry(NFT_OWNERSHIP_LAYER_HASH, current_owner, transfer_program, inner_puzzle)


def create_ownership_layer_puzzle(
    nft_id: bytes32,
    did_id: bytes,
    p2_puzzle: Program,
    percentage: uint16,
    royalty_puzzle_hash: bytes32 | None = None,
) -> Program:
    log.debug(
        "Creating ownership layer puzzle with NFT_ID: %s DID_ID: %s Royalty_Percentage: %d P2_puzzle: %s",
        nft_id.hex(),
        did_id,
        percentage,
        p2_puzzle,
    )
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (nft_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    if not royalty_puzzle_hash:
        royalty_puzzle_hash = p2_puzzle.get_tree_hash()
    transfer_program = NFT_TRANSFER_PROGRAM_DEFAULT.curry(singleton_struct, royalty_puzzle_hash, percentage)
    nft_inner_puzzle = p2_puzzle

    nft_ownership_layer_puzzle = construct_ownership_layer(
        bytes32(did_id) if did_id else None, transfer_program, nft_inner_puzzle
    )
    return nft_ownership_layer_puzzle
```
