### Title
Division by zero in mempool block-bundle assembly when dedup savings fully offset a spend's cost - (File: `chia/full_node/mempool.py`)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `item_cost = cost - cost_saving` for every mempool item it considers when assembling a spend bundle for a candidate block, then immediately uses `item_cost` as the divisor in an unguarded `fee / item_cost` expression passed to `log.info`. `cost_saving` is attacker-influenced through the deduplication mechanism (`IdenticalSpendDedup.get_deduplication_info`), and can be made equal to the item's total cost, driving `item_cost` to `0` and raising an uncaught `ZeroDivisionError`. This mirrors the CVE-2021-20243 bug class in ImageMagick's `resize.c`: an untrusted, attacker-controlled input drives an internal ratio calculation's denominator to zero, causing undefined/crashing behavior in an availability-critical code path.

### Finding Description
`create_bundle_from_mempool_items()` iterates mempool items ordered by priority to build a spend bundle for the next block: [1](#0-0) 

`item_cost` is derived from the item's total CLVM cost (`item.conds.cost`) minus `cost_saving`, which is the sum of costs of coin spends that are deduplicated against previously-included identical coin spends (see `IdenticalSpendDedup.get_deduplication_info`, which accumulates `dedup_coin_spend.cost` for every coin spend eligible for dedup): [2](#0-1) 

For a mempool item whose only coin spend is fully eligible for dedup and whose recorded per-spend cost equals the item's total `conds.cost` (a plausible situation for a single-spend bundle, e.g. identical settlement/offer spends submitted by multiple counterparties), `cost_saving` can equal `cost` exactly, making `item_cost == 0`. The very next statement,

```python
log.info(
    "Cumulative cost: %d, fee per cost: %0.4f, item cost: %d", cost_sum, fee / item_cost, item_cost
)
```

performs `fee / item_cost` with no zero-guard, unlike the analogous, correctly-guarded fee-rate computations elsewhere in the codebase (e.g. `MempoolManager.validate_spend_bundle()` explicitly checks `if cost == 0: return Err.UNKNOWN` before computing `fees / cost`): [3](#0-2) 

No equivalent `item_cost == 0` guard exists in `create_bundle_from_mempool_items`.

### Impact Explanation
If reached, `fee / item_cost` raises `ZeroDivisionError`, an unhandled Python exception inside the per-item `try` block whose scope (based on the surrounding code) is intended to catch dedup-specific `SkipDedup` exceptions, not generic arithmetic errors. An uncaught exception here aborts `create_bundle_from_mempool_items()` for the full node attempting to build a block, which is a spend-triggered transaction-processing halt: a single crafted, unprivileged spend bundle submitted to the mempool (structured so a later identical dedup-eligible spend arrives with `cost_saving == cost`) can repeatedly disrupt block assembly for any node/farmer that includes it in its candidate-block pipeline, degrading availability of block production.

### Likelihood Explanation
This method is actively used in the codebase (referenced from `full_node_api.py` and `mempool_manager.py`) and is reachable purely by submitting spend bundles to the mempool — no privileged access, malicious peer, or protocol-layer exploit is required. Reachability requires being able to submit two spend bundles that spend the identical coin with an identical solution (satisfying dedup eligibility) such that the deduplicated coin's recorded cost equals the whole item's cost — realistic for single-spend items such as CAT/offer settlement or simple standard-coin spends. I was not able to fully verify from the available index whether the enclosing `try/except` also happens to catch bare `Exception` (which would downgrade this to a "skip this item" rather than a hard failure); this should be confirmed by reading the exact `except` clause following line 718 in `chia/full_node/mempool.py`, which was not fully visible in the retrieved context.

### Recommendation
Guard the divisor before computing the fee-per-cost log value, mirroring the pattern already used in `mempool_manager.py`:
```python
item_cost = cost - cost_saving
if item_cost > 0:
    log.info("Cumulative cost: %d, fee per cost: %0.4f, item cost: %d", cost_sum, fee / item_cost, item_cost)
else:
    log.info("Cumulative cost: %d, item cost: %d (fully deduplicated)", cost_sum, item_cost)
```
Additionally, ensure `create_bundle_from_mempool_items`'s per-item exception handling catches unexpected arithmetic/runtime errors defensively (logging and skipping the offending item) so that no single malformed or adversarial mempool item can abort block assembly entirely.

### Proof of Concept
1. Submit spend bundle A spending coin `C` with a puzzle/solution combination that the mempool marks `eligible_for_dedup` (e.g., a settlement-payments/offer coin spend), noting its recorded per-spend cost equals the item's total `conds.cost` (single-spend bundle).
2. Submit a second, conflicting/complementary spend bundle B that also spends `C` with the exact same solution (dedup match) as a single-spend item, so during `IdenticalSpendDedup.get_deduplication_info()` its `cost_saving` accumulates the full previously recorded cost.
3. When `create_bundle_from_mempool_items()` processes item B during block-candidate assembly, `item_cost = cost - cost_saving` evaluates to `0`.
4. The subsequent `log.info(..., fee / item_cost, ...)` raises `ZeroDivisionError`, aborting block-bundle creation for that call on the affected node.
