### Title
Reward misattribution in `pallet-consensus-incentives`: single-batch relayer reward is credited only to `messages[0]`'s signer, not to whoever actually submitted each state machine's consensus proof - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` rewards relayers for delivering `ConsensusMessage`s that advance a remote chain's state-machine height. When a single call to `handle` (unsigned, permissionless) processes a batch containing several `Message::Consensus` entries — potentially advancing several different, unrelated state machines — the pallet extracts the rewarded relayer's identity from **only the first message in the batch** (`messages.get(0)`), then pays that single signer for the height advance of **every** state machine touched anywhere in the batch. There is no per-`state_machine_id` binding between the `StateMachineUpdated` event being rewarded and the specific `ConsensusMessage`/signature that actually produced it.

### Finding Description
`FeeHandler::on_executed` computes `maybe_relayer_account` once, from `messages[0]`: [1](#0-0) 

It then iterates over `highest_per_state_machine` — a de-duplicated map of every `StateMachineId` whose height advanced anywhere in the `events` vector for this batch — and calls `process_message` for each, always passing the *same* `relayer_account` derived from `messages[0]`: [2](#0-1) 

`process_message`/`calculate_reward` compute the reward purely from the height delta on that state machine (`latest - baseline`) and transfer it from the treasury to `relayer_account`: [3](#0-2) 

The comment on lines 125-132 documents that a prior fix collapsed duplicate `StateMachineUpdated` events *for the same chain* to avoid double-paying the same relayer within one batch — but it does not address the case where the batch's `events` vector contains `StateMachineUpdated` entries for **multiple different chains**, each actually proven by a different `ConsensusMessage`/signer bundled into the same `handle` call. `handle` on `pallet-ismp` is unsigned/permissionless (see the messaging docs), so any caller can assemble a batch containing:
- their own trivially-signed `ConsensusMessage` as index 0 (e.g., for a chain with `StateMachinesCostPerBlock == 0`, or one they already caught up), and
- one or more *other, independently valid* `ConsensusMessage`s (harvested from the public relayer network / mempool / on-chain history) that genuinely advance other chains' heights.

Because `relayer_account` is bound to `messages[0]` only, and the reward loop pays that account for **every** chain's height advance found in `events`, the attacker collects the treasury reward for state-machine updates they did not prove, diverting it from the relayer(s) who actually did the consensus-proof work for those other chains.

### Impact Explanation
This is a "wrong beneficiary" fund-movement bug against the `T::TreasuryAccount`: legitimate relayers do the costly work of fetching/submitting `ConsensusMessage`s for state machines with configured `StateMachinesCostPerBlock`, but an unprivileged party can redirect that reward to themselves by bundling their own message first in a multi-consensus-message batch. This directly matches the Hyperbridge Impact Gate's "stealing or loss of funds" / "logic attacks" / "wrong beneficiary" categories — the treasury pays the wrong account, and `LastRewardedHeight` is advanced for the victim chain regardless, so the legitimate relayer permanently loses that reward window (the watermark only moves forward, so the honest relayer cannot re-claim it later).

### Likelihood Explanation
No malicious peer, relayer collusion, governance, or leaked key is required — only that `pallet-ismp`'s message-handling entrypoint accepts a batch of independently-signed `ConsensusMessage`s in one call and that `on_executed` is invoked once per batch with all resulting events. Any unprivileged caller able to submit the unsigned `handle`/`submit_proof` extrinsic with a hand-assembled batch (their own cheap/zero-cost consensus message plus a rebroadcast of someone else's genuine consensus message for a different chain) can trigger this. The only prerequisite is that more than one `StateMachineId` with a configured `StateMachinesCostPerBlock` advances within the same processed batch, which is a normal, expected operating condition for the relayer incentive system.

### Recommendation
Bind the rewarded relayer identity to the specific `ConsensusMessage` (and therefore specific `StateMachineId`) that produced each `StateMachineUpdated` event, rather than using a single signer derived from `messages[0]` for the whole batch. Concretely, iterate `messages`, recover the signer from each `Message::Consensus` entry's own `consensus_proof`/`signer`, and correlate it with the specific state-machine ids advanced by *that* message (e.g., by having the consensus client report which `StateMachineId`s an individual `ConsensusMessage` proved) before crediting `LastRewardedHeight` and transferring the treasury reward. If a single `ConsensusMessage` can legitimately advance multiple chains, split/pro-rate the reward per proven chain per message rather than assuming batch-wide attribution to the first entry.

### Proof of Concept
1. Governance configures `StateMachinesCostPerBlock` for chains A and B (both non-zero).
2. Chain B's honest relayer submits a valid `ConsensusMessage` advancing B's height by `N` blocks (would normally earn `N * cost_B`).
3. An attacker observes this valid, publicly-verifiable message (unsigned extrinsics carry no privacy) and constructs their own `handle` call containing a batch: `[attacker's trivial ConsensusMessage for chain A (index 0, signed by attacker)`, `honest relayer's ConsensusMessage for chain B (index 1, re-submitted verbatim)]`.
4. `pallet-ismp` processes both messages, verifies both consensus proofs are valid (they are — proof B was already legitimate), and emits `StateMachineUpdated` for both A and B.
5. `on_executed` recovers `relayer_account` = attacker (from `messages[0]`), then loops `highest_per_state_machine = {A: ..., B: ...}`, transferring **both** A's and B's rewards to the attacker via `process_message`, and advances `LastRewardedHeight` for both A and B.
6. The honest relayer who did the actual work of producing B's consensus proof receives nothing, and cannot re-claim it later because `LastRewardedHeight[B]` has already moved past that height range.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
