### Title
Unauthenticated panic via unregistered `decryptor` key lookup in PedPoP blame adjudication - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a caller-supplied `Participant` that was never checked against the registered key set. A missing key panics via `HashMap`'s `Index` impl, crashing the process — the same bug class as CVE-2026-19481 (a map assumed to contain a given key resolves to nothing, and the failure surfaces as a hard process error rather than a recoverable error). The reachable path is `AdditionalBlameMachine::blame` / `BlameMachine::blame` → `blame_internal` → `decrypt_with_proof`, all of which accept attacker-controlled `sender`/`recipient`/`msg`/`proof` values.

### Finding Description
`enc_keys` is populated exclusively by `Decryption::register`, which is called once per participant during round-1 commitment verification (`SecretShareMachine::verify_r1` at `crypto/dkg/pedpop/src/lib.rs:315`) or for `1..=n` in `AdditionalBlameMachine::new` (`crypto/dkg/pedpop/src/lib.rs:656-659`). Any `Participant` index outside that set — e.g., `Participant::new(n + k)` for any `k`, since `Participant` only enforces nonzero (`crypto/dkg/src/lib.rs:122-125`) — has no entry.

In `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366-397`):
1. The message PoP is verified with `pop_challenge(..., from, ...)` — an attacker can satisfy this by signing with a key they generate, exactly as `encrypt` does (`encryption.rs:153-166`).
2. If `proof` is `Some`, line 388 evaluates `self.enc_keys[&decryptor]` as an argument to `dleq.verify`. The `HashMap` index panics before the DLEq proof is even checked, so no valid proof is needed — any `EncryptionKeyProof` bytes suffice to reach the panic.

Neither `blame` nor `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-632`, `674-682`) bounds `recipient` (or `sender`, though `sender` is only used for `commitments[&sender]` later, which is also unguarded) against `n` or `enc_keys`. An arbitrary nonzero `u16` therefore crashes the node evaluating blame.

### Impact Explanation
A single DKG participant (or anyone able to submit a blame accusation for adjudication) can crash every honest party running `blame`, aborting the key-generation session and denying service. In Serai's deployment, blame adjudication happens on validator/processor nodes; a panic there kills the process, not just the protocol instance — identical in effect to the busboy synchronous-throw DoS. The panic is guaranteed, deterministic, and costs the attacker only a valid Schnorr signature over a self-chosen key.

### Likelihood Explanation
Reachability requires the attacker to be a DKG participant sending (or triggering relay of) a blame accusation with an out-of-range `recipient` and `Some(proof)`. `EncryptedMessage::read` and `EncryptionKeyProof::read` (`encryption.rs:171-177`, `267-269`) accept arbitrary bytes, and the only gate before the panic is `msg.pop.verify`, which the attacker fully controls. Likelihood is moderate-high for any exposed blame path; it is a crash/abort rather than fund theft, consistent with a Medium/High DoS analog.

### Recommendation
- In `Decryption::decrypt_with_proof`, replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor)` and return `DecryptionError::InvalidProof` (or a new `InvalidParticipant` variant) on `None`.
- Similarly guard `self.commitments[&sender]` in `blame_internal` and `self.commitments[&l]` in `calculate_share` (`pedpop/src/lib.rs:490, 599`), plus `self.decryption.enc_keys[&participant]` in `Encryption::encrypt` (`encryption.rs:466`), so all untrusted `Participant` keys are membership-checked before indexing.
- Validate `sender`/`recipient <= n` at the `blame` entry points.

### Proof of Concept
```rust
// After AdditionalBlameMachine::new(context, n, commitment_msgs) for n = 5:
let attacker_index = Participant::new(1).unwrap();
// Craft a message whose PoP verifies under `from = attacker_index`:
// pick scalar k, set msg.key = G*k, sign pop with known nonce — same as `encrypt`.
let msg: EncryptedMessage<C, SecretShare<C::F>> = /* validly-PoP'd message */;
let proof = Some(EncryptionKeyProof { key: Zeroizing::new(C::G::identity()), dleq: /* any parseable DLEqProof */ });

// recipient = 200 was never registered in enc_keys
machine.blame(attacker_index, Participant::new(200).unwrap(), msg, proof);
// -> panics at encryption.rs:388: `self.enc_keys[&decryptor]`
//    HashMap index on absent key -> thread panic -> process abort
```

The panic fires while evaluating the `dleq.verify` arguments at `crypto/dkg/pedpop/src/encryption.rs:388`, before any cryptographic check on `proof`, so the attacker needs only a validly-PoP'd `EncryptedMessage` and an out-of-range `recipient` index.

Note: I was unable to fully trace the upstream caller path in `processor/src/key_gen.rs` (grep hit counts only, no content returned) to confirm exactly how `sender`/`recipient` arrive from wire messages; the panic itself is verified in the in-scope library code, but the surrounding integrator call site determining unauthenticated reachability is inferred from the public `blame` API contract.
