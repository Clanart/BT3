### Title
Silent commit of unresolved merge/rebase/cherry-pick conflict markers when a manual resolution path fails to match the working-directory file list - (File: `app/src/lib/git/commit.ts`, `app/src/lib/git/rebase.ts`, `app/src/lib/git/cherry-pick.ts`)

### Summary
`RootManager.propagate` fails "closed": one bad external call aborts the whole batch. The Desktop analog is the opposite failure mode with the same root cause (no fail-safe handling of an unexpected per-item condition inside a loop): when applying a set of manual conflict resolutions, a lookup mismatch for a single path is only logged and skipped (`continue`), while the rest of the pipeline still proceeds to stage and commit that same file's current on-disk content as if it had been resolved. Because the "skip" is silent and non-fatal, the commit is created successfully but can contain literal, unresolved conflict markers.

### Finding Description
`createMergeCommit`, `continueRebase`, and `continueCherryPick` all follow the same pattern:

```ts
for (const [path, resolution] of manualResolutions) {
  const file = files.find(f => f.path === path)
  if (file === undefined) {
    log.error(`couldn't find file ${path} even though there's a manual resolution for it`)
    continue        // <-- swallowed, not fatal
  }
  await stageManualConflictResolution(repository, file, resolution)
}

const otherFiles = files.filter(f => !manualResolutions.has(f.path))
await stageFiles(repository, otherFiles)
``` [1](#0-0) [2](#0-1) [3](#0-2) 

`manualResolutions` is a `Map<path, ManualConflictResolution>` built up earlier from UI events (`dispatcher.updateManualConflictResolution`) and stored per-path in `conflictState.manualResolutions`. [4](#0-3)  It is looked up against a separately supplied `files: ReadonlyArray<WorkingDirectoryFileChange>` array by exact string equality (`f.path === path`). If, for any reason, the path key stored when the user chose "ours"/"theirs" does not exactly match the `path` field of the conflicted entry in the `files` array handed to the commit-time function (e.g. a stale/newer status snapshot, a differently-cased or differently-Unicode-normalized path on a Desktop-supported case-insensitive filesystem, or a rename that changes the reported path between the time the resolution was recorded and the time the commit fires), the `if (file === undefined)` branch fires. It does not throw and does not abort the operation — it only logs and moves on.

The critical broken invariant is downstream: `stageManualConflictResolution` (which performs `git checkout --ours/--theirs` and re-adds the conflict-resolved blob) is never invoked for that file. [5](#0-4)  However, the actual conflicted `WorkingDirectoryFileChange` object still exists in `files` under its own real path, and — because `otherFiles = files.filter(f => !manualResolutions.has(f.path))` only excludes entries whose path is literally a key of the map — the mismatched file is *not* excluded. It is passed into `stageFiles`, which for any file with `DiffSelectionType.All` simply runs `git update-index --add` against whatever is currently on disk: [6](#0-5) . `update-index --add` takes the literal working-tree bytes — including any `<<<<<<<`/`=======`/`>>>>>>>` markers still present because the intended conflict resolution never ran — and stages them at stage 0, which clears Git's "unmerged" state for that path.

Once the index no longer records the file as unmerged, `git commit --no-edit --cleanup=strip` (used by `createMergeCommit`) has no `expectedErrors` set for an "unresolved conflicts" condition and will succeed normally [7](#0-6) , silently baking the literal conflict-marker text into the committed blob. The `continueRebase`/`continueCherryPick` paths do include `GitError.UnresolvedConflicts` in `expectedErrors` for the underlying `git rebase --continue`/`git cherry-pick --continue` calls [8](#0-7) , but that check only catches the case where the index *still has* multi-stage/unmerged entries — which is exactly the case this bug avoids, since the mismatched file's markers were already staged as an ordinary (non-conflicted) blob. There is no re-validation step anywhere in these functions that scans staged content for residual conflict markers before calling `git commit`.

### Impact Explanation
This results in silent corruption of what the user commits and, subsequently, pushes: a file the user believed they had explicitly resolved (e.g., chose "theirs") is instead committed with raw `<<<<<<<`/`=======`/`>>>>>>>` conflict-marker text embedded in tracked source, build config, or CI files. This can break builds, leak content from the "losing" side of the merge that the user intended to discard, or — since a malicious repository/branch supplies the conflicting content on the "their" side — allow an attacker-controlled repo to have its injected content (or marker-wrapped payloads) land verbatim in the victim's commit and pushed history without any warning dialog, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The likelihood hinges on getting the `path` string used as the `manualResolutions` map key to diverge from the `path` field on the corresponding entry in the `files` array supplied at commit time — the exact preconditions (stale status snapshot vs. fresh status, Unicode normalization, or case-folding path differences) could not be conclusively reproduced from static analysis alone within the scope of this investigation. The code path itself (silent `continue` + unconditional downstream staging of the same file) is confirmed and unconditional, but I could not verify from the indexed code exactly which of the plausible triggers (status timing, filesystem case-insensitivity, Unicode normalization) reliably produces the path mismatch in practice; this would require dynamic testing.

### Recommendation
Treat a `manualResolutions` lookup miss as fatal rather than logged-and-skipped: abort the commit (return `RebaseResult.Aborted`/`CherryPickResult.UnableToStart`/throw) instead of calling `continue`, and additionally exclude any such file from `otherFiles`/`stageFiles` so it can never be staged with its raw on-disk (possibly still-conflicted) content. Independently, add a defensive check before the final `git commit` call in `createMergeCommit` (and equivalent guard in the other two functions) that verifies none of the about-to-be-committed files still contain conflict markers or unmerged index stages, mirroring the `UnresolvedConflicts`/`diff --check` style validation already used elsewhere in the codebase.

### Proof of Concept
Conceptual reproduction (exact trigger for the path mismatch not fully verified — see Likelihood):
1. Clone a malicious repository and perform a merge/rebase/cherry-pick that produces a text conflict in `important-file.txt`.
2. In the Desktop UI, resolve the conflict via the manual-resolution menu (`ManualConflictResolution.theirs`), which calls `dispatcher.updateManualConflictResolution(repository, path, ManualConflictResolution.theirs)` and stores `path` as the map key. [9](#0-8) 
3. Before the user presses "Commit merge", trigger a condition where the subsequently-fetched `files` array reports a different string for the same physical path (e.g., a case or Unicode-normalization difference introduced by the malicious repo's file naming, or a stale vs. refreshed status call).
4. `createMergeCommit`/`continueRebase`/`continueCherryPick` runs, logs `couldn't find file ... even though there's a manual resolution for it`, and continues.
5. `stageFiles` runs `git update-index --add` on `important-file.txt`, staging its current on-disk contents (still containing `<<<<<<<`/`=======`/`>>>>>>>`).
6. `git commit --no-edit --cleanup=strip` succeeds with no error, producing a commit that literally contains unresolved conflict markers, which the user then pushes unaware.

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
```

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })
```
