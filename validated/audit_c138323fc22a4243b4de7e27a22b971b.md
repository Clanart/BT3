### Title
Unresolved merge-conflict markers can be silently committed due to naïve `git diff --check` output parsing - ([File: app/src/lib/git/diff-check.ts])

### Summary
The ERC-4337 report's broken invariant is: a single packed/derived signal (`ValidationData`) is trusted by multiple downstream functions without validating that it truly encodes what those functions assume, allowing a "failure" and a "success" to combine into an incorrect result. The GitHub Desktop analog is `getFilesWithConflictMarkers()`, which derives the *only* signal Desktop uses to decide whether a conflicted file still contains unresolved `<<<<<<<`/`=======`/`>>>>>>>` markers, by regex-parsing the text output of `git diff --check`. That count (`conflictMarkerCount`) is then trusted, unvalidated, by multiple independent call sites to gate whether a file is "safe to commit" — the exact same broken-invariant/propagation pattern.

### Finding Description
`getFilesWithConflictMarkers` shells out to `git diff --check` and extracts marker counts using the regex: [1](#0-0) 

```
const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)
```

This is the sole source of truth for `conflictMarkerCount`, which is then propagated into `ConflictsWithMarkers` status objects built in `parseConflictedState`: [2](#0-1) 

That derived value is subsequently consumed, without re-validation, by at least two independent decision points:

1. `hasUnresolvedConflicts`, used across `app-store.ts`, `sidebar.tsx`, and `unmerged-file.tsx` to decide whether the UI should still warn the user / block continuing a merge: [3](#0-2) 

```
if (isConflictWithMarkers(status)) {
    return status.conflictMarkerCount > 0
}
```

2. `stageManualConflictResolution`, which short-circuits entirely (no `checkoutConflictedFile`/`addConflictedFile`/`removeConflictedFile` call) when `conflictMarkerCount === 0`, assuming the user already resolved the file manually: [4](#0-3) 

Just like `isFailed()` in the report only inspected one bit of a packed value instead of validating the full semantic space (aggregator vs. pass/fail), `getFilesWithConflictMarkers` infers "no markers" purely from whether a *line-oriented regex against free-form `git diff --check` text output* happens to match — it does not independently confirm the working-tree file is actually free of `<<<<<<<`/`=======`/`>>>>>>>` sequences. Because the regex anchors on `^(.+):\d+: leftover conflict marker` per line, any output shape that git produces which does not conform exactly to that per-line format (e.g., `git diff --check` suppressing/altering output for a file due to `.gitattributes`-driven diff drivers, `core.quotepath`/path-quoting for filenames with unusual bytes, or a file that git's `diff --check` heuristics decide not to flag for a given hunk shape) causes `conflictCountsByPath.get(path)` to fall back to `0` via `?? 0` — indistinguishable from "genuinely resolved."

This mirrors the report's core defect precisely: several independent code paths (`hasUnresolvedConflicts`, `stageManualConflictResolution`) each re-derive a boolean "is this actually resolved" decision from the same under-validated packed/text signal, and a mismatch between what git's diff heuristic reports and what is truly in the file lets an unresolved state and a "resolved" signal "cancel out" into a false green light — analogous to the `xor()` cancellation in `setSig()`.

### Impact Explanation
If `conflictMarkerCount` under-reports (reports `0`) for a file that a user cloned/fetched/merged and that still contains literal conflict markers, GitHub Desktop will:
- Not display a conflict warning banner in the sidebar (`sidebar.tsx`) or the merge-conflicts flow (`app-store.ts`).
- Allow `stageManualConflictResolution` to skip resolution entirely, leaving whatever content is currently in the working tree/index untouched.
- Allow the user to commit and push a file that still contains raw `<<<<<<<`/`=======`/`>>>>>>>` merge markers, silently corrupting the resulting commit — a direct match for the "silent corruption of what the user commits or pushes" impact class. This can also affect downstream code correctness/security if the corrupted file is source code that gets built/executed later, and it happens without any explicit, unnatural user action — the user follows the normal "resolve → commit" flow that Desktop already told them was clean.

### Likelihood Explanation
This requires an attacker-controlled or unusual merge scenario (e.g., a crafted repository/branch designed to produce a merge whose diff-hunk shape or per-file diff-driver behavior causes `git diff --check` to not emit a `leftover conflict marker` line for a file that still has markers) combined with the user merging/resolving via Desktop's UI. This is a real, reachable path (merging a remote/fetched branch is a completely ordinary, expected Desktop action) but depends on specific `git diff --check` output edge cases that I was not able to fully enumerate or reproduce in this investigation (no shell/tool access to test crafted diffs, unusual `.gitattributes` diff drivers, or path-quoting edge cases against real `dugite`/git behavior). This uncertainty should be resolved by a background agent with terminal access.

### Recommendation
Do not rely solely on `git diff --check`'s free-text heuristic output as the single source of truth for "no markers remain." Instead, independently scan the actual working-tree file content for the literal conflict marker sequences (`<<<<<<<`, `=======`, `>>>>>>>`) as a second, authoritative check before allowing `hasUnresolvedConflicts` to return `false` or `stageManualConflictResolution` to short-circuit. This closes the same class of gap the SmartSession fix addressed: stop trusting a partially-validated derived signal and add an explicit, independent check for the exact condition being asserted.

import { git } from './core'

/**
 * Returns a list of files with conflict markers present
 *
 * @param repositoryPath filepath to repository
 * @returns filepaths with their number of conflicted markers
 */
export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

function parseConflictedState(
  entry: UnmergedEntry,
  path: string,
  conflictDetails: ConflictFilesDetails
): ConflictedFileStatus {
  switch (entry.action) {
    case UnmergedEntrySummary.BothAdded: {
      const isBinary = conflictDetails.binaryFilePaths.includes(path)
      if (!isBinary) {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
          conflictMarkerCount:
            conflictDetails.conflictCountsByPath.get(path) || 0,
        }
      } else {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
        }
      }
    }
    case UnmergedEntrySummary.BothModified: {
      const isBinary = conflictDetails.binaryFilePaths.includes(path)
      if (!isBinary) {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
          conflictMarkerCount:
            conflictDetails.conflictCountsByPath.get(path) || 0,
        }
      } else {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
        }
      }
    }
    default:
      return {
        kind: AppFileStatusKind.Conflicted,
        entry,
      }
  }
}

/** Typechecker helper to identify conflicted files */
export function isConflictedFile(
  file: AppFileStatus
): file is ConflictedFileStatus {
  return file.kind === AppFileStatusKind.Conflicted
}

/**
 * Returns a value indicating whether any of the files in the
 * working directory is in a conflicted state. See `isConflictedFile`
 * for the definition of a conflicted file.
 */
export function hasConflictedFiles(
  workingDirectoryStatus: WorkingDirectoryStatus
): boolean {
  return workingDirectoryStatus.files.some(f => isConflictedFile(f.status))
}

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
