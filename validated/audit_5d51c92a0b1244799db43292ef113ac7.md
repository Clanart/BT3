### Title
Duplicate `withdrawal_utxo` registration lets one Bitcoin payout satisfy two withdrawal indices, giving an operator a second unearned Reimburse cycle - (File: core/src/database/verifier.rs)

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins the `withdrawals` table to `bitcoin_syncer_spent_utxos` purely on the physical `(txid, vout)` of the `withdrawal_utxo`, with no per-`idx` uniqueness enforced anywhere in this repo. If two `withdrawals` rows (index `idx` and index `j`) end up with the identical `withdrawal_utxo_txid`/`withdrawal_utxo_vout`, a single real Bitcoin payout transaction `P` spending that outpoint is joined twice, and `update_payout_txs_and_payer_operator_xonly_pk` stamps `payout_txid = P` on both rows. `Operator::get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/task/payout_checker.rs`) then hands the operator two separate reimbursement cycles for what was physically a single fronted payout.

### Finding Description
Binding claimed: for payout transaction `P` spending outpoint `O`, the number of distinct `idx` for which `update_payout_txs_and_payer_operator_xonly_pk` records `payout_txid = P` should be `1`. This binding is broken because nothing in the schema or code enforces uniqueness of `(withdrawal_utxo_txid, withdrawal_utxo_vout)` across `withdrawals.idx`: [1](#0-0) 

The join used to discover payouts for a finalized block keys strictly on the outpoint value, not on any per-row identity: [2](#0-1) 

`Verifier::update_finalized_payouts` iterates every `(idx, payout_txid)` pair returned by that join, and for each one independently re-derives the same `operator_xonly_pk` from `payout_tx`'s OP_RETURN (which is identical for both rows since it's the same physical transaction), then persists `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` for both `idx` values: [3](#0-2) [4](#0-3) 

`get_first_unhandled_payout_by_operator_xonly_pk` selects unhandled rows only by `payout_txid IS NOT NULL`, `is_payout_handled = FALSE`, and matching `payout_payer_operator_xonly_pk` — with no check that the same `payout_txid` was already consumed by another `idx`: [5](#0-4) 

`PayoutCheckerTask::run_once` blindly trusts this result and, for each unhandled row it finds (first `idx`, then later `j`), resolves `move_to_vault_txid` for that specific `idx`/`j`, fetches that deposit's data, and calls `Operator::handle_finalized_payout` for it: [6](#0-5) 

`handle_finalized_payout` looks up deposit data strictly from the (distinct, real) deposit tied to `idx`/`j`'s `move_to_vault_txid`, and allocates a fresh unused kickoff connector for that specific `deposit_id`, entering the Kickoff → Reimburse flow that ultimately spends that deposit's move-to-vault UTXO into the operator's reimbursement chain: [7](#0-6) 

Root cause: the withdrawal record inserted for index `j` (`upsert_move_to_vault_txid_from_citrea_deposit` + `update_withdrawal_utxo_from_citrea_withdrawal`) is populated verbatim from whatever the Citrea Bridge contract reports for `withdrawalUTXOs(j)`, with no validation in this repo that the `(txid, vout)` value is unique across all previously-registered withdrawal indices: [8](#0-7) [9](#0-8) 

Because index `j` must correspond to a genuinely-existing deposit slot (the `withdrawals` row requires a non-null `move_to_vault_txid`, populated only from `collect_deposit_move_txids`), the second, colliding registration causes deposit `j`'s own move-to-vault UTXO to be consumed by a Kickoff/Reimburse cycle for the operator even though the operator never separately paid out to deposit `j`'s withdrawal destination — the "payout" it is credited with for `idx=j` is in fact tx `P`, which only ever paid the destination for the original withdrawal `idx`.

None of the existing guards mentioned in the audit rules intercept this: `Verifier::is_deposit_valid`, `Operator::is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `verify_storage_proofs`, and `SPV::verify` all operate on deposit/kickoff/watchtower data and never re-check that a `payout_txid` is uniquely attributed to a single withdrawal index before the operator automation consumes it. `validate_payer_is_operator` (used later in `get_reimbursement_txs`) only checks that `payout_payer_operator_xonly_pk` matches the operator, which is also satisfied for both `idx` and `j` since both rows were stamped with the same operator key.

### Impact Explanation
The operator's automated `PayoutCheckerTask` is tricked into calling `handle_finalized_payout` twice for what was physically one payout transaction, spending deposit `j`'s move-to-vault UTXO into a Kickoff/Reimburse chain that the operator never actually earned (they fronted BTC only once, to withdrawal `idx`'s destination, never to withdrawal `j`'s). This matches the Critical categories "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" and "an operator reimbursed for a payout it never funded." The blast radius scales with however many distinct, previously-unwithdrawn deposit slots the attacker can register a colliding `withdrawal_utxo` against, and is repeatable per operator/per deposit pair as long as an eligible deposit index exists to donate its `move_to_vault_txid`.

### Likelihood Explanation
Exploitability hinges on a precondition outside this repo's control: whether the Citrea Bridge contract's `withdraw()` permits registering the identical `(txId, outputId)` bytes for two different withdrawal indices. Nothing in this repo's ABI usage (`core/src/citrea.rs`, `core/src/test/withdraw.rs`) shows on-chain uniqueness enforcement of the outpoint across withdrawal ids, and this repo unconditionally trusts and stores whatever Citrea returns via `collect_withdrawal_utxos`/`update_citrea_deposit_and_withdrawals`. Assuming the contract allows it (which cannot be fully confirmed since its Solidity source is not present in this repository — only the generated ABI `scripts/Bridge.json` is available, and generated files are out of scope for direct review), triggering the collision requires only a normal `withdraw()` call plus paying whatever value that call requires, which is well within an unprivileged attacker's stated capabilities. If Citrea's contract instead enforces per-outpoint uniqueness at withdrawal-registration time, this specific attack path is blocked upstream of clementine, but that dependency itself is a gap: this repo has no independent, defense-in-depth check against duplicate `withdrawal_utxo` values across `idx`.

### Recommendation
Add a uniqueness constraint (unique index) on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table, and/or validate uniqueness in `update_withdrawal_utxo_from_citrea_withdrawal` before accepting new Citrea-reported withdrawal UTXOs, rejecting or flagging any index `j` whose withdrawal UTXO already exists on another `idx`. Additionally, harden `get_payout_txs_for_withdrawal_utxos` and `update_payout_txs_and_payer_operator_xonly_pk` to detect and refuse assigning the same `payout_txid` to more than one `idx`.

### Proof of Concept
In `core/src/database/verifier.rs` tests module, add a `cargo test` that:
1. Inserts two `withdrawals` rows, `idx=A` and `idx=B`, each with a distinct real `move_to_vault_txid`, but calls `update_withdrawal_utxo_from_citrea_withdrawal` with the **same** `OutPoint` `O` for both `A` and `B`.
2. Inserts a single spending transaction `P` into `bitcoin_syncer_spent_utxos` that spends `O`, within one `block_id`.
3. Calls `get_payout_txs_for_withdrawal_utxos(block_id)` and asserts the result contains two rows `(A, P)` and `(B, P)` — demonstrating the binding "distinct idx count for payout_txid = P == 1" is violated (result is 2).
4. Calls `update_payout_txs_and_payer_operator_xonly_pk` with both `(A, P, Some(op_pk), hash)` and `(B, P, Some(op_pk), hash)`.
5. Calls `get_first_unhandled_payout_by_operator_xonly_pk(op_pk)` twice (marking the first result handled via `mark_payout_handled` in between), and asserts it returns first `A` then `B` as two *distinct* unhandled payouts for the *same* underlying `payout_txid = P`, proving the operator would be handed two `handle_finalized_payout` cycles for one physically-fronted transaction.

                    TxidDB(*txid),

                    BlockHashDB(*block_hash),

            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",

            converted_values.into_iter(),

                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");
