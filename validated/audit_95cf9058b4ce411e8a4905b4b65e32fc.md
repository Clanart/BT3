Based on my investigation, I found a strong local analog to the reported bug class (unused/unenforced input parameter that should gate execution) in the EVM handler's GET response path.

### Title
Missing timeout enforcement in `handleGetResponses()` allows a timed-out `GetRequest` to be double-processed (response + timeout) - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handleGetResponses()` receives a batch of `GetResponseLeaf` entries, each wrapping a `GetResponse` whose `request` carries a `timeout()` value — exactly the kind of field the external report flags as "present but unprocessed." Unlike its sibling `handlePostRequests()`, which explicitly enforces `if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();` [1](#0-0) , `handleGetResponses()` contains only a comment acknowledging the timeout is skipped: `// don't check for timeouts because it's checked on Hyperbridge` [2](#0-1) .

### Finding Description
`handleGetResponses()` verifies the MMR inclusion proof and a duplicate-response check via `host.responseReceipts(...)`, then unconditionally calls `host.dispatchIncoming(leaf.response, _msgSender())` for every response in the batch [3](#0-2) . It never reads `leaf.response.request.timeout()`, so a response can be delivered to the destination application after the request's own timeout deadline has elapsed on this chain.

Meanwhile, `handleGetRequestTimeouts()` independently allows the *same* `GetRequest` to be timed out once `request.timeout() > state.timestamp` no longer holds, verifying a non-membership proof and calling `host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment)` [4](#0-3) . Both entry points are permissionless and both gate only on `host.requestCommitments(commitment)` being non-zero — neither function in this file clears that commitment as part of the response path, only the duplicate-response receipt is checked. This mirrors the Substrate handler's documented invariant that a module callback must not fire twice for the same request and that commitment deletion order is what prevents replay [5](#0-4) , but the EVM `handleGetResponses` path does not enforce the equivalent timeout ordering guarantee itself — it defers entirely to an off-chain assumption ("checked on Hyperbridge").

### Impact Explanation
If a relayer submits a valid state/inclusion proof for a `GetResponse` whose underlying request has already passed its `timeout()` on this chain, `handleGetResponses` will still accept it and invoke the destination module's response callback via `dispatchIncoming`. Since the same commitment can also still satisfy `handleGetRequestTimeouts`'s non-membership check (no membership proof for the response was ever required to exist on the source side within the timeout window), the same `GetRequest` commitment can be driven down both the "successful response" and "timed-out" code paths. This is exactly the double-settlement / duplicate-execution class called out in the impact gate: an application module could receive both `on_response` and `on_timeout` for one intent/order, causing state to be settled or refunded twice, or a paymaster/solver-style module to release funds against a request it should have treated as failed.

### Likelihood Explanation
Both entrypoints are fully permissionless (`external`, no access control beyond `notFrozen`), require only a standards proof any relayer/watcher can submit, and need no relayer/prover/admin collusion — matching the "unprivileged attacker" requirement. The missing check is a straightforward code-path asymmetry versus `handlePostRequests`, which does perform this exact check, making it a concrete, provable local coding defect rather than a speculative protocol-level assumption.

### Recommendation
Add the same timeout guard used in `handlePostRequests` to `handleGetResponses`: revert with `MessageTimedOut()` when `block.timestamp >= leaf.response.request.timeout()`, and/or have `dispatchIncoming`/`dispatchTimeOut` atomically delete the request commitment so that only one of "response" or "timeout" can ever be dispatched for a given commitment, never both.

### Proof of Concept
1. A `GetRequest` is dispatched from chain A with `timeout_timestamp = T`.
2. The remote state is queried and a `GetResponse` is produced/committed before `T`, but the relayer delays submission.
3. After `T` has elapsed, another actor calls `handleGetRequestTimeouts` with a valid non-membership proof; `host.dispatchTimeOut` fires `on_timeout` on the source module.
4. Separately (before or after step 3, since `requestCommitments` is not cleared by the response path shown), the delayed relayer submits the late `GetResponse` via `handleGetResponses`; because no timeout check exists there, `host.dispatchIncoming` fires `on_response` for the same commitment.
5. The destination module has now received both terminal callbacks for one request, an outcome the timeout-handling contract (per `docs/content/protocol/ismp/timeouts.mdx` and the Rust handler's commitment-deletion ordering) explicitly intends to prevent [6](#0-5) .

**Note on completeness:** I was unable to inspect the full body of `EvmHost.sol`'s `dispatchIncoming`/`dispatchTimeOut`/`requestCommitments` implementations before the tool budget ran out, so I cannot fully confirm whether `dispatchIncoming` internally clears `requestCommitments` in a way that would close this race. The asymmetric timeout check between `handlePostRequests` and `handleGetResponses` in `HandlerV2.sol`, however, is directly confirmed in the code shown above and is the concrete, locally-provable defect.

The timeout `handle` is used to notify onchain `IsmpModule`s of outgoing requests that have now timed out. A relayer will construct the `TimeoutMessage` which holds a batch of these messages, and their relevant proofs. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the messages have indeed timed out
- Assert that the claimed messages are known by the host
- Assert that the relevant state machine's time has advanced past the `timeout_timestamp` of specified messages.
- Assert that the relevant non-membership proofs for the messages are valid
- Finally dispatch the timeouts to the relevant `IsmpModule::on_timeout` and delete the commitments for the outgoing messages.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_timeout` does not return `Ok`, the commitment of the relevant messages will not be deleted, allowing the timeout to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their timeout handler. This model ensures that if a timeout cannot be executed successfully, it can be retried later.
