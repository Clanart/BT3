### Title
Spot-price dependence in gasless swap admission/repayment check allows repayment-shortfall / lending loss for the proposer - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
Analogous to the GammaVault bug (collateral computed from an instantaneous, manipulable price rather than a manipulation-resistant reference), Kaia's gasless-transaction module validates and admits `GaslessSwapTx` bundles using a single, point-in-time on-chain price read (`GetAmountIn`) from a DEX router contract. This spot price can be moved by any unprivileged actor in an adjacent transaction/bundle, which can desynchronize the admission-time sufficiency check from the actual execution-time swap outcome, creating a path for the block proposer's lent gas to not be recouped.

### Finding Description
`checkBalanceForSwap` in [1](#0-0)  computes the amount of token required for a `GaslessSwapTx` by calling the external DEX router's `getAmountIn` as a live, single-block view call: [2](#0-1) 

This call resolves to `GaslessSwapRouter.GetAmountIn`, which is bound to Uniswap V2-style routing per [3](#0-2) . Uniswap V2 `getAmountsIn`/`getAmountsOut` derive the exchange rate purely from the pool's current reserves (the instantaneous "spot price"), exactly the same class of manipulable, non-TWAP price source flagged in the GammaVault report. There is no reference to any TWAP, oracle, or manipulation-resistant price feed anywhere in the gasless/auction/gov code paths that were inspected.

This spot price is used twice, asymmetrically in time:
1. At tx-pool admission time (`IsReady`/`GetCheckBalance`), to gate whether a `GaslessSwapTx` is promotable, based on `swapArgs.AmountIn >= requiredAmountIn` computed from the *current* reserves.
2. At block-building/execution time — potentially in a different block or after other transactions execute — the block proposer has already prepended a `LendTxGenerator` transaction (per the module's own documented block-building rule: "LendTxGenerator is prepended before GaslessApproveTx" — [4](#0-3) ) that fronts gas KAIA to the sender, expecting the subsequent swap to repay `amountRepay` from swap proceeds.

Because the sufficiency check performed by the tx pool is re-evaluated from mutable reserves at whatever moment `IsReady`/`GetCheckBalance` executes, and the DEX pool is a permissionless, publicly tradable pool, any unprivileged party can submit ordinary swap transactions against the same pool to shift reserves between the check and the final execution of the bundle. This is analogous to the GammaVault flaw where an attacker moves the spot price between assessment and enforcement to create an exploitable mismatch, rather than relying on a price that is resistant to single-transaction manipulation (e.g., TWAP).

### Impact Explanation
If reserves are manipulated downward for the output token immediately before the bundle executes, the actual swap can yield materially less than what was assessed as "sufficient" when the tx was promoted, risking that `amountRepay` cannot be fully recovered from the swap output, or forcing the whole atomic bundle (`[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]`) to fail at a later stage than intended. Given `minAmountOut >= amountRepay` is still enforced on-chain in `SwapForGas` (per `checkBalanceForSwap`'s comment: "tx.minAmountOut >= tx.amountRepay"), an attacker manipulating price against the sender does not directly steal repayment funds through this path alone — the strongest concretely provable effect is that a legitimate `GaslessSwapTx` that was validated as executable using the manipulated spot price can be forced to revert on execution (slippage below `minAmountOut`), consuming the proposer-fronted lending transaction's gas and potentially causing repeated proposer gas loss or repeated failed inclusion (fee/gasless abuse and DoS against the proposer's gas-lending mechanism), which is a fee-delegation / gasless settlement abuse concern reachable by any transaction sender who can also trade against the referenced pool.

### Likelihood Explanation
Likelihood is Medium: exploitation requires only ordinary swap transactions against the same permissionless DEX pool used by `GaslessSwapRouter`, something any public-RPC caller/unprivileged sender can do; it does not require validator, peer, or governance privileges. However, actually causing measurable financial loss to the proposer (rather than just occasional legitimate-user failures) requires precise timing around mempool promotion and block assembly, which is achievable but non-trivial for an attacker without additional visibility into pending bundle contents.

### Recommendation
Do not rely on a single, spot-price `getAmountIn`/`getAmountOut` call read at admission time as the sole basis for gating gasless-swap promotion when the underlying pool is a standard constant-product AMM. Re-validate sufficiency immediately before/at inclusion within the same block context that will execute the swap (not merely at `IsReady`), add a manipulation-resistant safety margin, or require the router to expose and use a TWAP-based quote for admission decisions so that promoted transactions are less sensitive to transient reserve movement between promotion and inclusion.

### Proof of Concept
Conceptual PoC (repo-grounded, not executed):
1. Attacker observes a pending `GaslessApproveTx` + `GaslessSwapTx` bundle in the mempool targeting `GaslessSwapRouter.SwapForGas` for `token` via a Uniswap V2 pool.
2. Attacker submits a large swap against the same pool (permissionless, publicly tradable) shortly before the bundle is selected for block building, shifting reserves and thus the spot price returned by `getAmountIn`/`getAmountsOut`.
3. `checkBalanceForSwap` at [2](#0-1)  was evaluated against the pre-manipulation reserves and marked the swap as sufficient/ready.
4. By the time the bundle executes on-chain (after the attacker's swap lands), the actual on-chain swap in `SwapForGas` produces less output than assumed, causing the swap to revert (failing the `minAmountOut`/`amountRepay` on-chain checks), after the proposer has already fronted gas via `LendTxGenerator`, resulting in wasted/unrecovered gas expenditure for the proposer for that block-building attempt.

Note: the actual Solidity source of `GaslessSwapRouter.sol` (its `getAmountIn`/`swapForGas` internals) is not present in this repository — only Go bindings in [5](#0-4)  were available — so the exact on-chain slippage-protection guarantees of `SwapForGas` could not be fully confirmed from the indexed code; a Devin session with access to the full contract source (likely in an external/private repo referenced by KIP-247) would be needed to conclusively verify whether `minAmountOut` fully neutralizes the spot-price manipulation risk at execution time.

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}

### Block building rules

Upon detection of GaslessTxs, the following logics are executed:

- Per sender, if exists, GaslessApproveTx is relocated before GaslessSwapTx.
- LendTxGenerator is prepended before GaslessApproveTx.
- A new bundle is generated which contain either `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` or `[LendTxGenerator, GaslessSwapTx]`
- If the bundle has conflict with any previous bundles, it is excluded from the returned bundle list.
