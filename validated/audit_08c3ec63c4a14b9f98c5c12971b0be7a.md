### Title
Unbounded allocation in `ThresholdKeys::read` driven by attacker-controlled participant count - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts a u16 `n` field read directly from untrusted bytes and immediately performs `Vec::with_capacity(usize::from(n))` for the `Constant` interpolation variant, before any consistency check between `t`, `n`, and `i`. A two-byte prefix lets an unprivileged caller force an allocation proportional to a fully attacker-chosen count, the same bug class as CVE-2018-5748 (denial of service via memory consumption triggered by an oversized response).

### Finding Description
In `ThresholdKeys::read`, after the curve-ID check, `t`, `n`, and `i` are read as raw u16s [1](#0-0) . If the next byte selects `Interpolation::Constant`, the code runs `Vec::with_capacity(usize::from(n))` — up to 65,535 field elements (~2 MiB for 32-byte fields) — purely on the attacker's declared `n`, with no bound tied to the bytes actually present [2](#0-1) . It then loops `1 ..= n` inserting into a `HashMap` of verification shares [3](#0-2) , and only afterwards calls `ThresholdParams::new(t, n, i)` / `ThresholdKeys::new`, which would reject nonsensical parameters — too late to prevent the allocation [4](#0-3) . Other in-scope deserializers (e.g., `PedPoP`/`musig` reads, `networks/bitcoin`) use fixed-size or u8-bounded reads, so they do not exhibit this amplification; notably the codebase is aware of the pattern, as `coordinator` code comments on guarding `vec![0; len]` allocations with explicit size limits [5](#0-4) , a guard missing here.

### Impact Explanation
A single tiny input (≈13 bytes: curve ID, `t/n/i`, interpolation tag) forces a multi-megabyte heap allocation per call. Repeated invocations of `ThresholdKeys::read` on attacker-supplied bytes (e.g., in any component that deserializes keys or sessions from network/storage input) cause sustained memory exhaustion and process termination — a remote denial of service against nodes performing threshold operations, matching the CVE's "memory consumption via a large reply" class without needing the attacker to transmit the full inflated payload.

### Likelihood Explanation
Reachability is high wherever `ThresholdKeys::read` is applied to bytes an unprivileged party can influence — it is explicitly among the untrusted-read APIs enumerated for this audit. The only mitigation is that the amplification is bounded by `u16` (~65,535 entries) rather than `u32`/`u64`, capping a single-call cost at a few MiB plus a `HashMap` pre-sizing, and `read_F`/`read_G` failures abort early — but the `with_capacity` allocation happens regardless. That bound keeps this at Medium rather than High.

### Recommendation
Validate `ThresholdParams::new(t, n, i)` (and a sane upper bound on `n`, e.g., `<= u8::MAX + 1` consistent with `Participant`) before allocating; replace `Vec::with_capacity(n)` with `Vec::new()` or cap it by the reader's remaining length; and bound the verification-shares loop the same way.

### Proof of Concept
Serialize a `ThresholdKeys`-shaped buffer for any `Ciphersuite` `C`: `u32` len of `C::ID` || `C::ID` || `t=1` || `n=0xFFFF` || `i=1` || `interpolation=0` (Constant). The total input is under 20 bytes, yet `ThresholdKeys::<C>::read` executes `Vec::with_capacity(65535)` of `C::F`-sized elements at `crypto/dkg/src/lib.rs:608` before any `read_F` is attempted or `ThresholdParams` validates the parameters. Repeating the call linearly amplifies resident memory versus bytes received.
