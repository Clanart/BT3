### Title
Cached FROST preprocess seed is never deleted after `from_cache`, enabling nonce reuse and secret key recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The upstream bug class is "state not cleared after teardown, causing stale reuse on a later code path" (`server->smbd_conn` left dangling after `smbd_destroy`). The direct analog in Serai is `SigningProtocol::preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs`: a FROST preprocess seed is persisted in `CachedPreprocesses` and re-loaded via `AlgorithmSignMachine::from_cache` on every call, but it is never deleted. The `SignMachine::from_cache` contract explicitly states "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:216-224`). Because `share` and `complete` each rebuild a machine from the same seed and call `sign` on attacker-influenced inputs, the same nonce can be used to produce two signature shares over different challenges, which leaks the signer's secret key.

### Finding Description
`preprocess_internal` stores a ChaCha20 seed (XOR-encrypted with a key derived from the validator's secret) in `CachedPreprocesses` keyed by `context = (b"DkgConfirmer", attempt)`, then loads it back and calls `from_cache` (`coordinator/src/tributary/signing_protocol.rs:123-145`). The entry is only written if absent and is never removed, so every call to `preprocess_internal` for a given attempt deterministically reconstructs a machine with the *same* nonces (the nonces are derived from the seed in `seeded_preprocess`, `crypto/frost/src/sign.rs:121-144`).

`DkgConfirmer::share` calls `share_internal`, which calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` where `msg = set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:288-301`). `DkgConfirmer::complete` *again* calls `share_internal` — with whatever `preprocesses` and `key_pair` are supplied at completion time — and then completes the machine (`signing_protocol.rs:312-327`). If the preprocess map or the `key_pair` presented at `complete` time differs from what was presented at `share` time, `sign` is executed twice with identical nonces but a different binding-factor/challenge transcript. Two FROST shares `z_i = d_i + e_i·ρ_i + λ_i·s·c` over the same nonce `(d_i, e_i)` with distinct challenges `c` yield the secret share `s = (z_1 − z_2) / (λ_i·(c_1 − c_2))`. Since shares are broadcast, the validator's MuSig/FROST secret key is recoverable by anyone observing both shares.

### Impact Explanation
Recovery of `self.key`, the validator's Ristretto secret key used in the tributary MuSig for DKG confirmations (`musig(musig_context(...), self.key.clone(), participants)` at `signing_protocol.rs:118-121`). Compromise of this key lets an attacker forge the validator's confirmation signatures and impersonate it in the DKG-confirmer signing protocol — full key-share recovery, the exact consequence the `from_cache` documentation warns about. This qualifies as key share recovery under the acceptance criteria.

### Likelihood Explanation
The seed is unconditionally reused: `share` and `complete` each invoke `share_internal`, so `sign` runs at least twice per attempt on the same nonce. Divergence of the FROST challenge between the two runs only requires the supplied `preprocesses` map or `key_pair` bytes to differ — both are untrusted inputs read via `read_preprocess`/`read_share` from incoming protocol messages (`signing_protocol.rs:155-168`, `183-192`). Any inconsistency between the data seen at share time and at complete time (different signing subsets, different key_pair, re-delivered messages after the deterministic-ordering boundary) produces the two-challenge/one-nonce condition. The nonce reuse is deterministic given divergent inputs; it does not depend on RNG failure.

### Recommendation
Delete the `CachedPreprocesses` entry before (or atomically with) each `from_cache` call, and distinguish the machine-rebuild path from a fresh `sign`: either persist the built `AlgorithmSignMachine`'s outputs rather than the raw seed, or ensure `complete` reuses the identical `preprocesses`/`msg` that were signed at `share` time (e.g., persist the exact signed inputs keyed by context and assert equality on re-entry) so a second `sign` can only ever reproduce the identical share. At minimum, a one-shot flag keyed by `(context, msg, preprocess-set)` should reject any second `sign` under the same seed with different inputs.

### Proof of Concept
1. For `DkgConfirmer` attempt `a`, `share(preprocesses_A, key_pair_A)` is invoked. `share_internal` → `preprocess_internal` creates/loads seed `S` from `CachedPreprocesses[(b"DkgConfirmer", a)]`, rebuilds nonces `(d, e)` deterministically, and `sign` emits share `z_1 = d + e·ρ_A + λ·s·c_A` over `msg_A = set_keys_message(set, removed_A, key_pair_A)`.
2. `complete(preprocesses_B, key_pair_B, shares)` is invoked with `preprocesses_B ≠ preprocesses_A` (different included subset or different commitment bytes) and/or `key_pair_B ≠ key_pair_A`. `share_internal` reloads the same undeleted seed `S`, regenerates identical nonces `(d, e)`, and `sign` emits/uses `z_2 = d + e·ρ_B + λ·s·c_B` with `c_B ≠ c_A`.
3. With `z_1`, `z_2`, the public binding factors, Lagrange coefficient `λ`, and both challenges computable from public transcript data, solve `s = (z_1 − z_2)·(λ·(c_A − c_B))⁻¹` to recover the validator's secret key.

Note: I was unable to fully trace `handle.rs`'s call sites to confirm how often `share` and `complete` can be driven with divergent inputs for the same attempt; the protocol ordering guarantees in `coordinator/src/tributary/handle.rs` would determine the exact delivery conditions, but the uncleared-seed invariant violation itself is unconditional.
