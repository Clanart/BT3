The pattern in the smart-contract bug is: an operation trusts an attacker-influenced identity/object without cross-checking it against the object it's supposed to correspond to, and then uses that trust to silently mutate protected state (the pool/loan binding). The Desktop analog with the strongest local-code support is `updateRemoteUrl`, which silently rewrites a repository's `origin` URL based on data returned by the GitHub API, keyed only by `owner/name`, without verifying that the API repository object is actually the *same* repository the user originally cloned.

### Title
Silent git remote URL rewrite based on unverified GitHub API repository identity enables push/fetch redirection ("repo-jacking") - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` automatically calls `gitStore.setRemoteURL` to change the local `origin` remote whenever the GitHub API's `clone_url` for the `owner/name` pair differs from what's currently configured, based only on `owner/name` string matching rather than a stable, unspoofable repository identifier.

### Finding Description
`repositoryWithRefreshedGitHubRepository` looks up the associated GitHub repository purely from the parsed remote URL, via `matchGitHubRepository`, which matches on `owner`/`name` extracted from the remote string and the account's hostname only [1](#0-0) . It never compares against a persistent GitHub repository id. This match result is then used to call the GitHub API for the same `owner/name` [2](#0-1) , and the returned `apiRepo.clone_url` is fed into `updateRemoteUrl`, which will call `gitStore.setRemoteURL(...)` to silently rewrite the local `origin` whenever the protocol matches, the previously cached clone URL matched the remote, and the newly-fetched URL differs [3](#0-2) .

Because the lookup key is `owner/name` (a squattable, reusable string) rather than the GitHub repository's immutable numeric id, if the original repository is deleted, transferred away, or renamed and the `owner/name` slot becomes available again, an attacker who claims that same `owner/name` on GitHub (or GHE) controls the exact "GitHub API object" (`apiRepo.clone_url`) that Desktop consumes to decide the new remote URL — mirroring the external report's core flaw of trusting caller-supplied/attacker-controlled object data instead of verifying it matches the original bound identity. This code path runs automatically as part of routine refresh operations (`_fetch`, `_selectRepositoryRefreshTasks`, `performFetch`), i.e., every time the user fetches/opens the repository, with no user confirmation before the remote is changed [4](#0-3) .

### Impact Explanation
If exploited, a user's `origin` remote can be silently repointed to a repository controlled by an attacker. Subsequent `git push` operations (all of which use `gitStore.defaultRemote`/`safeRemote.url` computed from the just-rewritten remote) would then send the user's commits, branches, and potentially embedded secrets to the attacker's repository instead of the intended one — a silent corruption of what the user pushes, and a confidentiality/integrity impact without any unusual user action, matching the "Valid Impact" criteria (attacker controls a GitHub API object; result is silent corruption of what the user pushes).

### Likelihood Explanation
The safeguards in place (`protocolsMatch`, `remoteUrlUnchanged`) reduce, but do not eliminate, likelihood: they only require that the user hadn't manually customized the remote and that the protocol (https/ssh) stayed the same — properties an attacker reclaiming a released `owner/name` slot on the same host can trivially satisfy. The main precondition is that the original repository at that `owner/name` must have moved/been deleted and the name must be reclaimed, which is a known real-world "repo-jacking" pattern (already documented for supply-chain attacks against renamed/deleted GitHub repos). No admin rights, local access, or leaked credentials are needed by the attacker; it requires only that they be able to create/control a public repository with the reused name.

### Recommendation
Do not rely solely on `owner/name` string matching to decide whether to silently rewrite a trusted remote URL. Persist and check the GitHub repository's immutable `id` (already stored on `GitHubRepository`, see `repositoriesStore.upsertGitHubRepository`) and require that `apiRepo.id === gitHubRepository.dbID`-equivalent identity before calling `setRemoteURL`; if the id differs, treat it as a different repository and either leave the remote untouched or prompt the user for explicit confirmation before changing `origin`.

### Proof of Concept
1. User clones `https://github.com/victim-org/project.git` in Desktop; Desktop associates the local repo with the GitHub API record for `victim-org/project`.
2. `victim-org` deletes or renames `project` (or the org/account is deleted), freeing up the `owner/name` slot.
3. Attacker creates a new repository at the exact same path, e.g., `victim-org/project` is unavailable, but if `victim-org` renamed away, an attacker registers a same-named repo under a similarly reachable path that Desktop's `matchGitHubRepository` would still resolve to (owner/name + hostname only) — most directly, attacker takes over the abandoned `owner` account/org entirely and republishes `project` with a fresh `clone_url` pointing at attacker infrastructure or an attacker-owned GitHub repo.
4. On the victim's next fetch/refresh (`_fetch`, background fetch, or simply opening the repo), `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('victim-org','project')`, which now returns the attacker's `apiRepo.clone_url`.
5. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (nothing had been hand-edited), and `urlsMatch === false`, so it calls `gitStore.setRemoteURL(...)`, silently rewriting `origin` to the attacker's URL.
6. The next `git push`/`git fetch` executed by Desktop (or by the user via CLI, since the on-disk `.git/config` was modified) now interacts with the attacker-controlled endpoint.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
