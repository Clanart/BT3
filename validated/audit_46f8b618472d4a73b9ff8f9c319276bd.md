### Title
Attacker-controlled `n` drives unchecked `Vec::with_capacity` allocation in `ThresholdKeys::read` — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes the participant count `n` from untrusted bytes and immediately reserves `n` field elements via `Vec::with_capacity(usize::from(n))` — before `ThresholdParams::new` validates the parameters and before confirming the reader actually contains that many scalars. A ~9‑byte header claiming `n = 0xFFFF` forces a multi-megabyte allocation on every call, a direct analog of CVE-2026-53428's unbounded range-expansion allocation in mdex.

### Finding Description [1](#0-0) 

The read path:

1. Reads `t`, `n`, `i` as three `u16`s straight from the reader (`read_u16`, lines 591–602). `n` is fully attacker-controlled, up to 65535.
2. Reads the interpolation tag. For `Interpolation::Constant`, it executes `Vec::with_capacity(usize::from(n))` (line 608) — eagerly reserving `n * size_of::<C::F>()` bytes (≈3.7 MB for a 56-byte field like Ed448; ≈2 MB for 32-byte fields) purely from a 2-byte field in the input.
3. Only afterwards — after the allocation and after attempting to read `n` scalars and `n` verification-share points — does it call `ThresholdParams::new(t, n, i)` (line 626) and `ThresholdKeys::new` (line 625), which is where semantic validation of `t`/`n`/`i` occurs.

Because `read` accepts any `io::Read`, the reader can be truncated immediately after the header. The `with_capacity` reservation still happens; the subsequent `read_F` loop then fails on the first element and the oversized buffer is dropped — meaning each crafted message causes a large alloc/free cycle. The pattern exactly mirrors the mdex bug: a small length/range field expanded into a heap allocation with no bound checked against the actual input size. The analogous-but-safe pattern exists elsewhere in the same codebase: `Commitments::read` sizes its allocation from the locally-known `params.t()` rather than from the wire [2](#0-1) .

### Impact Explanation
Denial of service via memory allocation amplification. `ThresholdKeys::read` is one of the sanctioned untrusted-input entry points (key material fed to sign/verify flows, recovery inputs, etc.). Each ~9-byte message forces an allocation of up to roughly `65535 * size_of::<C::F>` (~2–4 MB), plus an `n`-iteration `read_G` loop for `verification_shares` (line 621) if the attacker supplies data. Repeated submissions cause sustained allocator pressure and memory churn on the host running the ciphersuite code. Unlike the mdex CVE (8 bytes per element, unbounded u32 range), the amplification here is bounded by `u16` (`n ≤ 65535`), so the severity is lower — a per-message cost in the low megabytes rather than hundreds of MB — but it is still a byte-proportional-to-kilobyte-input → megabyte-allocation mismatch with no upper bound check against the actual buffer length.

### Likelihood Explanation
Reachable wherever an application deserializes `ThresholdKeys`/`ThresholdView` material or DKG output received over a channel — e.g., key-share delivery, recovery flows, or any path feeding attacker bytes into `ThresholdKeys::read`. Requires no privileges: the attacker only needs to supply a crafted byte stream; the allocation fires before any parameter or signature validation can reject the input. The maximum impact per message is capped at ~4 MB by the `u16` width, so a meaningful DoS requires repeated submissions rather than a single payload as in the mdex advisory.

### Recommendation
Validate the parameters before allocating: parse `t`, `n`, `i` and immediately run `ThresholdParams::new(t, n, i)` (and reject `n` exceeding any sane protocol bound, e.g. `MAX_KEY_SHARES_PER_SET`) prior to the `with_capacity` call. Additionally, avoid speculative `with_capacity` on wire-derived counts — either drop the reservation and let `push` grow the vector (allocation then stays proportional to bytes actually read, as `SchnorrAggregate::read` already does [3](#0-2) ), or cap the reservation at a small constant and let it grow.

### Proof of Concept
Conceptual, against `crypto/dkg/src/lib.rs`:

```rust
// ~10 byte payload: valid C::ID header, t=1, n=0xFFFF, i=1, interpolation=Constant (0)
let mut payload = vec![];
payload.extend((C::ID.len() as u32).to_le_bytes());
payload.extend(C::ID);
payload.extend(1u16.to_le_bytes());        // t
payload.extend(0xFFFFu16.to_le_bytes());   // n = 65535
payload.extend(1u16.to_le_bytes());        // i
payload.push(0);                           // Interpolation::Constant
// Truncate here: no scalars follow.

let mut cursor = payload.as_slice();
let _ = ThresholdKeys::<C>::read(&mut cursor); // Errs, but only after
// Vec::with_capacity(65535) has reserved ~2-4 MB of heap per call.
```

Looping this call produces repeated multi-megabyte alloc/free cycles per ~10 bytes of attacker input; the allocation happens before `ThresholdParams::new`/`ThresholdKeys::new` can reject the parameters [4](#0-3) .

Caveat: I was unable to verify the concrete callers that feed untrusted bytes into `ThresholdKeys::read` within the iteration budget; the reachability assumption rests on the task's own list of sanctioned untrusted-read APIs.
