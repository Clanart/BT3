## Title
Deposits accepted while share value has collapsed to zero (no `inkind > 0` check) - permanent loss of depositor principal ([File: mainnet/contracts/vault/v0-vault-usdc.clar] and equivalent vault contracts)

### Summary
The referenced MetaStreet/LiquidityManager bug allows deposits into a tick whose realized value-per-share has collapsed near zero; a subsequent bad-debt event zeroes the node and strands both the old and new depositor's claim. The same root-cause class — accepting deposits at a share price that has already collapsed toward zero without validating the resulting share amount — is present in the Zest vault contracts (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`).

### Finding Description
Each vault computes shares to mint on deposit via `convert-to-shares-preview`: [1](#0-0) 

```clarity
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

When total-supply (`ts`) is non-zero but total-assets (`ta`) has been driven to zero (or is very small relative to `ts`), the function returns `u0` shares (or a rounded-down dust amount) for *any* deposit amount, since `mul-div-down` truncates.

`total-assets` can be driven toward zero by the vault's own `socialize-debt` function, which unconditionally reduces the `assets` variable and writes down `lindex` proportionally when bad debt is socialized: [2](#0-1) 

The `deposit` function then takes the user's real underlying tokens, computes `inkind` via `convert-to-shares-preview`, and mints `inkind` zTokens — but it never asserts that `inkind > u0`: [3](#0-2) 

```clarity
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
    (ok inkind)))
```

Compare this to `redeem`, which explicitly guards against a zero-value outcome: [4](#0-3) 

```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```

`deposit` has no equivalent check. With the default `min-out` of `u0` (or any caller not setting a strict slippage bound), a deposit into a vault whose share price has collapsed (`ta` near/at `u0` while `ts > u0`, e.g. after `socialize-debt` writes down `assets`) will:
1. Pull the depositor's real underlying tokens into the vault (`receive-underlying amount account`), incrementing `assets`.
2. Mint `u0` (or a rounded-down dust) zTokens to the depositor.

This is the exact analog of the reported bug: a user deposits into a pool/vault whose realized value-per-share is at/near the insolvency boundary, and their principal becomes unrecoverable (no shares to redeem it with) while the value silently accrues to the pre-existing zToken holders who benefit from the increase in `assets` without dilution.

### Impact Explanation
This is **Critical** — direct, permanent loss of a depositor's principal (theft of funds at rest, since remaining shareholders benefit from the un-diluted increase in `assets`) whenever a vault's `assets`-to-`zft`-supply ratio collapses toward zero via `socialize-debt` (bad-debt write-down) prior to a deposit landing.

### Likelihood Explanation
Requires a vault to first experience meaningful bad debt socialization (via `v0-market.clar` / `v0-4-market.clar`'s bad-debt socialization path calling `vault-socialize-debt`) that reduces `assets` to zero or near-zero while `zft` supply remains outstanding. This is a plausible, reachable end-state during a severe under-collateralized liquidation event (the same event class the referenced report exploits), and once reached, any subsequent depositor with default/loose `min-out` silently loses funds.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` to the `deposit` function in every vault contract, mirroring the check already present in `redeem`. Additionally, consider preventing deposits (analogous to MetaStreet's fix) when `total-assets-preview` falls below a defined health threshold relative to `total-supply-preview`, rather than only guarding the exact-zero case.

### Proof of Concept
1. Vault has `assets = A`, `zft` total-supply = `S` (`S > 0`), from normal operation.
2. A large bad-debt event occurs; `socialize-debt` is invoked with `scaled-amount` large enough that `principal-reduction >= current-assets`, driving `(var-set assets u0)` while `zft` supply remains `S`.
3. A user calls `deposit(amount, min-out=0, recipient)`. `convert-to-shares-preview` computes `ta = 0`, returns `inkind = u0`.
4. `deposit` passes all asserts (`amount > 0`, `inkind (=0) >= min-out (=0)`, cap check), transfers `amount` underlying tokens from the user into the vault, mints `u0` zTokens to the user, and increases `assets` by `amount`.
5. User has permanently lost `amount` of underlying tokens with zero shares to redeem against it; the value is captured by existing `zft` holders.
