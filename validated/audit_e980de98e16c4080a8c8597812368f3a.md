`indexed` keyword on `string` parameter in `ValidatorCommissionWithdrawn` event causes irretrievable validator identity for RPC/event consumers - (File: precompiles/distribution/Distribution.sol)

### Summary
The `IDistr` interface used by the distribution precompile declares `event ValidatorCommissionWithdrawn(string indexed validator, uint256 amount);` with the `validator` (a Sei bech32 validator operator address) marked `indexed`. Because `string` is a dynamic/reference type, Solidity's ABI encoding for indexed dynamic parameters stores only `keccak256(validator)` in the log topic, not the original string.

### Finding Description
`IDistr` in [1](#0-0)  declares the `validator` parameter as `indexed` while its type is `string`. Every other analogous event in the same interface and elsewhere in the staking/distribution precompiles correctly keeps validator-address strings non-indexed, e.g. `DelegationRewardsWithdrawn(address indexed delegator, string validator, uint256 amount)` [2](#0-1) , `MultipleDelegationRewardsWithdrawn(address indexed delegator, string[] validators, uint256[] amounts)` [3](#0-2) , and the staking precompile's `Undelegate`, `ValidatorCreated`, `ValidatorEdited` events [4](#0-3) . This shows `ValidatorCommissionWithdrawn` is an outlier/bug rather than an intentional design choice.

The compiled ABI confirms the on-chain behavior: `{"indexed":true,"internalType":"string","name":"validator","type":"string"}` appears in `precompiles/distribution/abi.json` [5](#0-4) , and the same broken definition is baked into every legacy ABI snapshot (`legacy/v630`, `v640`, `v65`, `v66`, `v67`), meaning this bug has existed across multiple precompile versions [6](#0-5) .

This event is emitted whenever `withdrawValidatorCommission()` or `withdrawValidatorCommissionWithAuthorization(address validatorOperator)` is called by an unprivileged EVM transaction sender through the distribution precompile [7](#0-6) [8](#0-7) . Because the topic only contains `keccak256(validatorAddressString)`, no downstream reader (JSON-RPC `eth_getLogs` consumer, block explorer, DApp indexer, or any off-chain accounting system) can recover which validator's commission was withdrawn from the log topic alone — the topic is an opaque, one-way hash.

### Impact Explanation
Any application, exchange, custodian, or accounting/monitoring system that relies on Sei's public EVM JSON-RPC log/event interface to track validator commission withdrawals (a legitimate on-chain economic event) cannot correlate the emitted `ValidatorCommissionWithdrawn` log to a specific validator without independently guessing/brute-forcing every validator's bech32 address and hashing it to match. This breaks off-chain accounting, auditing, and any DApp UI that lists commission withdrawal history, and is a real production defect reachable from any public RPC client observing precompile events — but it does not on its own cause fund loss, unauthorized transfers, or double-spending; the underlying accounting state at the distribution module level is unaffected because the module itself doesn't rely on the log topic.

### Likelihood Explanation
This is deterministic and triggers on every single call to `withdrawValidatorCommission` or `withdrawValidatorCommissionWithAuthorization` through the distribution precompile — no attacker action, special conditions, or privileged access is required; any unprivileged EVM transaction sender interacting with the distribution precompile (address `0x...1007`) reaches this code path immediately.

### Recommendation
Remove the `indexed` keyword from the `validator` parameter in `ValidatorCommissionWithdrawn` in `precompiles/distribution/Distribution.sol`, matching the pattern already used by the sibling events (`DelegationRewardsWithdrawn`, `MultipleDelegationRewardsWithdrawn`), and regenerate the corresponding ABI JSON files (`precompiles/distribution/abi.json` and any active legacy copies used for live event decoding) plus the Go event-signature/topic-building helpers in `precompiles/common/evm_events.go` if a `ValidatorCommissionWithdrawnEventSig`/builder analog exists for this event.

### Proof of Concept
1. Submit an EVM transaction calling `withdrawValidatorCommission()` (or `withdrawValidatorCommissionWithAuthorization`) against the distribution precompile at `0x0000000000000000000000000000000000001007`.
2. The precompile emits a log whose second topic is `keccak256(validatorBech32Address)` per the ABI definition in `precompiles/distribution/abi.json`.
3. Query the log via `eth_getLogs`/`eth_getTransactionReceipt` on the public JSON-RPC endpoint.
4. Observe that the `validator` field cannot be decoded back to the original bech32 string from the topic — only a 32-byte hash is available, unlike the non-indexed `validator` string in `DelegationRewardsWithdrawn`, which is fully recoverable from log data.
