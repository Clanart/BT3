## Finding

### Title
`is_deposit_valid` Collateral Check Re-Applied at `deposit_finalize` Blocks In-Flight Deposits When Operator Exits Mid-Session — (`core/src/verifier.rs`)

### Summary

`Verifier::is_deposit_valid` is called at both the `deposit_sign` stage and the `deposit_finalize` stage of the MuSig2 deposit pipeline. The function performs a live on-chain collateral check for every operator in the deposit. If an operator spends their collateral UTXO (i.e., exits the protocol) between the two calls, the finalization check fails and the in-progress deposit can never be completed, locking the user's BTC in the deposit UTXO until the `user_takes_after` recovery timelock expires.

---

### Finding Description

The deposit pipeline in Clementine is a multi-step, multi-party MuSig2 process coordinated by the Aggregator. The overall timeout is up to 2 hours (`OVERALL_DEPOSIT_TIMEOUT`). The two relevant verifier-side entry points are:

**Step 1 — `deposit_sign`** calls `is_deposit_valid`: [1](#0-0) 

**Step 2 — `deposit_finalize`** also calls `is_deposit_valid`: [2](#0-1) 

Inside `is_deposit_valid`, the following live on-chain check is performed for every operator listed in the deposit data: [3](#0-2) 

`collateral_check` queries the Bitcoin node to determine whether the operator's collateral UTXO is currently unspent. If the operator exits the protocol (spends their collateral UTXO) at any point between `deposit_sign` and `deposit_finalize`, this check transitions from `true` to `false`. The second call to `is_deposit_valid` inside `deposit_finalize` then returns `BridgeError::InvalidDeposit`, aborting the finalization and preventing the move-to-vault transaction from being created.

The `collateral_check` function is defined in: [4](#0-3) 

The deposit data is constructed by the Aggregator at `new_deposit` time by fetching the current operator set: [5](#0-4) 

Once the deposit data is fixed (operator set is baked in), any operator in that set who exits the protocol before `deposit_finalize` completes will cause the deposit to fail.

---

### Impact Explanation

The user's BTC is sent to the deposit address before the MuSig2 pipeline begins. If the pipeline fails at `deposit_finalize`, the move-to-vault transaction is never created. The user's BTC remains locked in the deposit UTXO and is only recoverable via the `user_takes_after` timelock script path — a significant delay. This constitutes a **temporary but material lock of bridged BTC** caused by a legitimate protocol event (operator exit), not by any user error.

---

### Likelihood Explanation

The deposit pipeline can take up to 2 hours (`OVERALL_DEPOSIT_TIMEOUT`). An operator exit is a normal, permissionless protocol operation — any operator can spend their collateral UTXO at any time. The window between `deposit_sign` and `deposit_finalize` is non-trivial. Any operator exit during an active deposit session triggers this failure. The existing test suite explicitly acknowledges that operator removal causes deposit failure, but only tests the case where removal happens *before* the deposit starts, not *during* it: [6](#0-5) 

---

### Recommendation

The collateral liveness check (`is_collateral_usable`) is appropriate as a gate at deposit *initiation* (`deposit_sign`) to prevent new deposits from being created with operators who have already exited. However, re-applying this live on-chain check at `deposit_finalize` introduces a TOCTOU window. The fix is to skip the live collateral check inside `is_deposit_valid` when called from `deposit_finalize`, since the operator set was already validated and committed at `deposit_sign` time. One approach: add a boolean parameter `skip_collateral_check` to `is_deposit_valid`, or split the function into two — one for initiation-time validation (with collateral check) and one for finalization-time validation (without it).

---

### Proof of Concept

1. Operator O has a valid collateral UTXO. User U sends `bridge_amount` BTC to the deposit address.
2. Aggregator calls `new_deposit`. `deposit_sign` is called on all verifiers; `is_deposit_valid` passes because O's collateral is unspent.
3. The MuSig2 pipeline is in progress (nonce aggregation, partial signature collection).
4. Operator O decides to exit the protocol and broadcasts a transaction spending their collateral UTXO. It confirms on Bitcoin.
5. Aggregator calls `deposit_finalize` on all verifiers. Each verifier calls `is_deposit_valid` again.
6. `collateral_check` for O now returns `false` (UTXO is spent). The check at line 638 fires:
   ```
   "Operator O is in the deposit data from aggregator but its collateral is spent"
   ```
   `deposit_finalize` returns `BridgeError::InvalidDeposit`.
7. The move-to-vault transaction is never created. U's BTC is locked in the deposit UTXO until the `user_takes_after` timelock expires. [7](#0-6)
