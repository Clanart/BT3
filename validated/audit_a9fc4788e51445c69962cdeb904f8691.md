### Title
Java ProtoJSON parser accepts non-string JSON values for `string`-typed fields without raising a parse error - (File: `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`)

### Summary
The CVE describes `graphql-go`'s `coerceString`/`coerceBool` failing to validate that a scalar's runtime JSON value matches its declared type (e.g. a non-string value silently accepted where a `String` scalar was declared), instead of raising the spec-mandated request error. The protobuf analog is in the Java ProtoJSON (`JsonFormat`) parser: conformance testing proves that a JSON value of the wrong kind (a bare number) supplied for a `string`-typed protobuf field is accepted and coerced rather than rejected, violating the same "declared scalar type must be validated" invariant that the C++ reference JSON parser (`src/google/protobuf/json/internal/parser.cc`) enforces correctly.

### Finding Description
The C++ ProtoJSON implementation explicitly type-checks scalar kinds before assignment. For `TYPE_STRING`/`TYPE_BYTES` it requires a JSON string token via `ParseStrOrBytes`, and for `TYPE_BOOL` it requires `JsonLexer::kTrue`/`kFalse` (only degrading to string-coercion under an explicit `allow_legacy_nonconformant_behavior` opt-in flag). [1](#0-0) 

The conformance suite explicitly encodes the spec requirement that a non-string JSON value for a string field is a parse error: [2](#0-1) 

However, the Java binding's `failure_list_java.txt` (and the PHP and JRuby binding failure lists) record `StringFieldNotAString` — as well as `RepeatedFieldWrongElementTypeExpectingStringsGotInt`/`GotBool` — as REQUIRED conformance tests that the binding's JSON parser fails, i.e. the parser accepts a JSON integer/bool where the schema declares a `string` field and does *not* raise the request/parse error the specification mandates: [3](#0-2) [4](#0-3) [5](#0-4) 

This is the same failed invariant as the CVE: the declared scalar type (`string`) is not validated against the actual JSON token type before the value is coerced/stored, deviating from the strict type check that the canonical C++ implementation performs and that the JSON/ProtoJSON specification requires.

I was not able to pin down the exact line numbers of the Java `JsonFormat` scalar-conversion code path responsible for this permissive behavior within the available indexed context (searches for the relevant `case STRING:` branch in `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java` returned matches but the surrounding coercion logic could not be retrieved in this session). This is a limitation of the current investigation, not a claim that the code doesn't exist — the failure-list evidence (a REQUIRED conformance test failing) is strong independent proof that the behavior exists in the shipped Java parser.

### Impact Explanation
Unlike the GraphQL-go CVE where the only proven guaranteed-reachable impact was a stack-overflow via deep nesting (explicitly out of scope per this analog's rules, since it's a resource-exhaustion/depth-limit class), the protobuf analog's impact is data-integrity related: type coercion silently accepts semantically wrong input (e.g., a numeric literal or boolean is silently converted into a string, or an incompatible value populates a field the schema declared as `string`). Consuming applications that rely on ProtoJSON to strictly validate a client-supplied schema-typed payload (e.g., treating "REQUIRED" JSON conformance as an implicit trust boundary) can receive messages whose scalar values don't match the wire type the application logic assumes, potentially causing downstream logic errors, authorization bypasses, or data corruption. There is no evidence of memory-safety impact (no `VA:H`-style crash) — this is a correctness/spec-conformance defect, not a memory-corruption bug.

### Likelihood Explanation
High likelihood of reachability: JSON parsing via `JsonFormat.parser().merge(...)` in Java (and equivalent PHP/JRuby public JSON parse entry points) is a supported public API that any ordinary client-facing service exposing ProtoJSON ingestion would invoke on attacker-controlled bounded JSON payloads, with no privileged access required. The conformance suite is run against every officially shipped language binding, and these are REQUIRED (not RECOMMENDED) test failures which are explicitly acknowledged, non-trivial and reproducible today by simply submitting `{"someStringField": 12345}` against a `TestAllTypes`-shaped schema.

### Recommendation
Align the Java, PHP, and JRuby ProtoJSON scalar-value coercion logic with the C++ reference implementation's strict type checks (`ParseSingular`/`ParseStrOrBytes` in `parser.cc`): reject (raise `InvalidProtocolBufferException`/`GPBDecodeException`) whenever the JSON token kind for a `string`/`bytes`-typed field is not a JSON string, and remove any implicit numeric/boolean-to-string coercion in these bindings' JSON parsers, matching the "REQUIRED" conformance expectations already codified in `binary_json_conformance_suite.cc`.

### Proof of Concept
Using the standard protobuf `conformance` test harness with the `Required.*.JsonInput.StringFieldNotAString` case against the Java, PHP, or JRuby conformance runner:
```json
{"optionalString": 12345}
```
Per `binary_json_conformance_suite.cc:3117-3118`, this MUST cause a parse failure for a schema declaring `optional_string` as a `string` field. The recorded, current failure-list entries confirm the Java/`failure_list_java.txt` (line 45), PHP/`failure_list_php.txt` (line 24), and JRuby/`failure_list_jruby.txt` (lines 64/73/137/146) bindings instead accept this input, demonstrating the missing scalar-type check analogous to the CVE's `coerceString`/`coerceBool` defect. Full conformance-run output (pass/fail assertions) was not independently executed in this session — the failure-list files themselves are the checked-in, versioned record that the upstream project maintains to track this exact known non-conformance in these bindings.
