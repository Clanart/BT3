### Title
Presumed origin of Bitcoin deposits recorded from `tx.input[0]` rather than the actual payer - (File: processor/src/networks/bitcoin.rs)

### Summary
The external report's bug class is *recording an assumed value instead of the value reported by the source of truth*: `doBorrow` adds the requested `amountCall` to `totalDebt` rather than reading the post-operation debt from the cToken, while `accrue`/`doRepay` read the actual state. Serai's Bitcoin scanner exhibits the same shape: `Bitcoin::get_outputs` attributes every scanned output of a transaction to a `presumed_origin` derived by assuming `tx.input[0]` is the depositor, rather than determining the actual party who funded the Serai-bound output. The assumed value is written into the `Output` and consumed downstream by the multisig scheduler for attribution/refund handling.

### Finding Description
In `processor/src/networks/bitcoin.rs`, `get_outputs` scans each transaction, and for any transaction containing a matched output, unconditionally resolves `tx.input[0]`'s spent `script_pubkey` into an `Address` and assigns it as `presumed_origin` to **all** outputs found in that transaction: [1](#0-0) 

```rust
let spent_output = {
  let input = &tx.input[0];                                  // assumed to be the payer
  ...
  tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
};
Address::new(spent_output.script_pubkey)                     // presumed_origin
```

The code itself acknowledges the assumption ("This may identify the P2WSH output ... as the origin", `TODO`), mirroring how `doBorrow` "assumed" the borrow amount. The `Output` struct (`presumed_origin: None` → `Some(...)`) is then emitted via `ScannerEvent::Block` and persisted in `processor/src/multisigs/scanner.rs:594-704`, and `presumed_origin` is referenced throughout `processor/src/multisigs/mod.rs` and the schedulers for attribution (e.g., refund destinations for outputs carrying `InInstruction` data extracted by `Self::extract_serai_data(tx)`).

The assumption that `input[0]` equals the depositor is false for any collaboratively constructed transaction (PayJoin, CoinJoin, multi-party spends) and, more generally, for any transaction where the party funding the Serai output is not the owner of the first input. There is no cryptographic link between `tx.input[0]` and the intent expressed in the OP_RETURN `data` — `data` is attacker-controlled bytes, and `presumed_origin` is attacker-influenced via input ordering/transaction construction.

### Impact Explanation
An unprivileged party constructs a transaction paying a Serai external address (plus OP_RETURN `InInstruction` data) inside a PayJoin/CoinJoin where the attacker controls `input[0]` but the victim's inputs fund the Serai output — or vice versa, arranges a victim's deposit to be misattributed. Consequences aligned with the report's "accounting views are inaccurate" impact, escalated to fund movement:

- If the `InInstruction` is unfulfillable and the protocol refunds the deposit to `presumed_origin`, the refund is sent to the owner of `input[0]` — a party who did not fund the deposit. An attacker-merchant in a PayJoin can capture the victim's refunded deposit.
- Even without refund flow, all downstream attribution of the deposit (origin of a `kind == OutputType::External` output with `data`) is recorded incorrectly and only corrected, if ever, by an operation that re-derives state — the same "wrong until the next accrual" staleness pattern as `totalDebt`.

This maps to "funds reported received [and attributed to an origin] that are not spendable [by the recorded party]" / funds directed to the wrong party.

### Likelihood Explanation
The vulnerable path is reachable by any unprivileged Bitcoin user: they only need to broadcast a transaction whose outputs match a registered Serai script (`Scanner::scan_transaction` matches `script_pubkey` only, `networks/bitcoin/src/wallet/mod.rs:199-214`) and whose `input[0]` they choose. PayJoin-style transactions are commonplace on Bitcoin, and the attacker fully controls input ordering in any transaction they construct. No validator, peer, or RPC collusion is required. The severity is bounded by the value of deposits that get misattributed/refunded, matching the original report's Medium severity (inaccurate accounting feeding fund-handling decisions).

### Recommendation
Do not assume `tx.input[0]` is the payer. Either:
- Derive the origin from a value the depositor actually commits to (e.g., require the `InInstruction` data to carry an explicit refund/origin field signed or committed by the payer), or
- Treat `presumed_origin` as an untrusted hint only — never use it as a refund destination without the depositor cryptographically binding it, and document that limitation.

At minimum, attribute `presumed_origin` per-output using an input that demonstrably funded the payment (e.g., SumInputs heuristics are insufficient; prefer explicit commitment), and stop blindly indexing `tx.input[0]` for every scanned output in the transaction.

### Proof of Concept
1. Victim initiates a PayJoin-style payment to Serai's external P2TR address with OP_RETURN data (or attacker constructs the tx paying Serai with attacker-authored `data`).
2. Attacker ensures their own UTXO is `tx.input[0]` while the Serai-bound output is funded by victim inputs.
3. `Bitcoin::get_outputs` scans the block, matches `output.script_pubkey`, reads `tx.input[0].previous_output`, fetches that prevout via `self.rpc.get_transaction`, and sets `presumed_origin = Address::new(attacker_script_pubkey)` on the emitted `Output`.
4. Scanner emits `ScannerEvent::Block { outputs }` (`processor/src/multisigs/scanner.rs:704`) and `save_outputs` persists it; downstream refund/attribution logic in `processor/src/multisigs/mod.rs` treats the attacker's address as the depositor, exactly as `bank.totalDebt += amountCall` treated a requested amount as actual.

Note: the exact downstream consumer of `presumed_origin` (refund path in `processor/src/multisigs/mod.rs` and `scheduler/utxo.rs`) could not be fully read within available search depth; the misattribution itself, its attacker-controlled reachability, and its persistence are confirmed at `processor/src/networks/bitcoin.rs:686-739`.
