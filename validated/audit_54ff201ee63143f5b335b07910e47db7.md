### Title
Path-containment check in `resolveWithin` uses a naive string-prefix comparison without a path-separator boundary, allowing repository-root escape via the `x-github-client://openrepo` deep-link `filepath` parameter - (File: `app/src/lib/path.ts`)

### Summary
`ChainLinkDataConsumer` used one coarse, shared parameter (`allowedPriceUpdateDelay`) to validate freshness across heterogeneous feeds, so the check was correct for one feed but silently wrong for the other. The Desktop analog is `_resolveWithin()` in `app/src/lib/path.ts`, which uses a single coarse invariant — `realResolved.startsWith(realRoot)` — to decide whether a resolved path is "inside" the repository root, for every caller regardless of platform/path shape. Just like the shared heartbeat, this one-size-fits-all check is valid for the common case but silently wrong at the boundary: a plain string-prefix test with no trailing separator check treats any sibling path that merely shares the root's characters as prefix as "inside" the root.

### Finding Description
`resolveWithin` is the app's core guard against directory-traversal/escape when resolving attacker-influenced relative paths against a trusted root (e.g. a repository path): [1](#0-0) 

The final containment check is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a raw string-prefix comparison. It does not verify that `realResolved` is either exactly equal to `realRoot` or that the next character after the shared prefix is a path separator. As a result, any directory whose name simply begins with the same characters as `realRoot` (a sibling directory, e.g. `realRoot + "-something"` or `realRoot + "2"`) will incorrectly satisfy the `startsWith` check and be treated as "inside" the root, even though it is a completely different directory on disk.

This function is reachable from an attacker-controlled, unprivileged input: the `x-github-client://openrepo/...` deep link handler. `parseAppURL` extracts an attacker-supplied `filepath` query parameter: [2](#0-1) 

`handleAppURL` in the main process forwards this parsed action to the renderer without further path validation: [3](#0-2) 

`Dispatcher.openRepositoryFromUrl` then only rejects absolute paths and otherwise calls the vulnerable containment check before exposing the resolved file to the user: [4](#0-3) 

Because `isAbsolute(filepath)` only blocks absolute inputs, an attacker can still supply a relative traversal payload such as `../MyRepo-evil/secret.txt`. If the user has (or can be induced to have, e.g. by cloning a maliciously-named or attacker-suggested repo alongside their target repo) a sibling directory whose path is `repository.path + <suffix>`, `resolve()` will produce a path in that sibling directory, and `realResolved.startsWith(realRoot)` will still return `true` because the sibling's absolute path literally starts with the victim repository's path string. The existing guard therefore fails to stop escape at the exact boundary where correctness matters, in the same way the shared Chainlink heartbeat was correct for one feed but not the other.

### Impact Explanation
A successful escape lets `shell.showItemInFolder(resolved)` reveal/open a file located outside the intended repository root, driven entirely by a link the user clicks (deep link) — this matches the "file read outside the repo" class of impact called out as valid for this analysis. The same `_resolveWithin` primitive is reused elsewhere in the codebase (`app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`), so any other caller that resolves an untrusted relative segment against a trusted root inherits the same boundary weakness, widening the blast radius beyond just the `openrepo` deep link.

### Likelihood Explanation
Exploitation requires only that the attacker can get the user to click a crafted `x-github-client://openrepo/<owner>/<repo>?filepath=...` link (no local access, no admin rights, no leaked credentials) and that a sibling directory sharing the root path as a string prefix exists on disk — a condition that is plausible in normal developer workflows (e.g., `repo`, `repo-old`, `repo2`, `repo-backup` directories are common). The existing mitigations (`isAbsolute` check, null-byte check) do not address this specific string-prefix boundary flaw, so likelihood is non-trivial though it depends on directory-naming conditions outside the attacker's direct control.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`, line 71) to require an exact match or a boundary-respecting prefix, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the platform-appropriate separator from the `options` parameter (`join`/`normalize`/`resolve` already vary by platform, so the separator check should too, to keep consistency with `win32`/`posix` variants).

### Proof of Concept
1. User has a local repository at `/Users/alice/Projects/MyRepo` (tracked in Desktop) and, incidentally or by prior action, also has a sibling folder `/Users/alice/Projects/MyRepo-secrets/creds.txt`.
2. Attacker sends the user a link: `x-github-client://openrepo/alice/MyRepo?filepath=..%2FMyRepo-secrets%2Fcreds.txt`.
3. `parseAppURL` parses this into `{ name: 'open-repository-from-url', url: 'alice/MyRepo', filepath: '../MyRepo-secrets/creds.txt', branch: null, pr: null }` [2](#0-1) .
4. `handleAppURL`/`onDidLoad` forwards the action to the renderer [3](#0-2) .
5. `Dispatcher.openRepositoryFromUrl` finds/opens the `MyRepo` repository, `filepath` is not absolute so it passes the `isAbsolute` check, and `resolveWithin('/Users/alice/Projects/MyRepo', '../MyRepo-secrets/creds.txt')` is called [5](#0-4) .
6. Inside `_resolveWithin`, `resolved` becomes `/Users/alice/Projects/MyRepo-secrets/creds.txt`; `realResolved.startsWith(realRoot)` evaluates `'/Users/alice/Projects/MyRepo-secrets/creds.txt'.startsWith('/Users/alice/Projects/MyRepo')` → `true` [1](#0-0) .
7. `shell.showItemInFolder(resolved)` opens/reveals `creds.txt`, a file outside the actual repository root, purely as a result of the user clicking the link.
