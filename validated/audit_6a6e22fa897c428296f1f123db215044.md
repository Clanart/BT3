## Finding: Confirmed – Bank precompile does not reject or reconcile `msg.value`, permanently stranding native funds

### Title
Native funds sent via `CALL` with nonzero `msg.value` to the bank precompile are permanently locked with no recovery path - (File: precompiles/bank/bank.go)

### Summary
The bank precompile at `0x0000000000000000000000000000000000000804` exposes only read-only query methods (`Balances`, `TotalSupply`, `SupplyOf`) but never guards against or reconciles a nonzero `contract.Value()`, unlike the sibling `erc20` precompile which explicitly rejects value transfers.

### Finding Description
`Precompile.Execute` in [1](#0-0)  calls `cmn.SetupABI` and dispatches only to `Balances`, `TotalSupply`, or `SupplyOf` — all query methods, since `IsTransaction` always returns `false` [2](#0-1) . Crucially, it never inspects `contract.Value()`.

Compare this to the `erc20` precompile, which explicitly guards against this exact scenario: [3](#0-2) 

The `erc20` precompile also wires a `BalanceHandlerFactory` into its base `Precompile` struct so that any native balance changes during precompile execution are reconciled against the bank module: [4](#0-3) 

The `bank` precompile's `NewPrecompile` sets up its embedded `cmn.Precompile` **without** a `BalanceHandlerFactory`: [5](#0-4) 

In `RunNativeAction`/`runNativeAction`, the `balanceHandler` is only invoked `if p.BalanceHandlerFactory != nil`, so for the bank precompile `balanceHandler` is `nil` and no `BeforeBalanceChange`/`AfterBalanceChange` reconciliation ever occurs: [6](#0-5) 

Under standard EVM `CALL` semantics, the value transfer from caller to the callee (precompile) address happens in the EVM's core call logic before/independent of the precompiled contract's `Run` being invoked — this is generic go-ethereum behavior wired through the `vm.Contract.Value()` field, not something the precompile can opt out of at the call-transfer level. Since:
1. The bank precompile has no `ErrCannotReceiveFunds`-style guard (unlike `erc20`), and
2. There is no `BalanceHandler` to detect and reconcile/reject the stray value, and
3. All exposed bank precompile methods are read-only queries with no way to move funds out of the precompile's own address,

any value sent to `0x...0804` becomes permanently unreachable. It is credited to the precompile's associated account balance in the `x/vm` statedb (and ultimately reconciled to the real `x/bank` balance of that address on commit) but there is no method, fallback, or governance path in this precompile to withdraw or redirect it.

### Impact Explanation
This matches the "Critical permanent freezing, locking ... of user funds" impact category. An unprivileged attacker (or, more likely, a confused/buggy caller) that sends native value in a `CALL` to the bank precompile address permanently loses that value — it cannot be recovered by the sender, the precompile, or any admin/governance mechanism exposed in the precompile itself, since the precompile only implements query methods.

### Likelihood Explanation
Likelihood is moderate: this requires an unprivileged caller (EOA or contract) to intentionally or mistakenly attach `msg.value` on a call to the bank precompile address. It does not require any privileged role — any ordinary transaction or contract call flow can trigger it, and the existing test comment/guard in `erc20.go` shows the team is aware of and has already patched this exact class of issue for the `erc20` precompile, but the same protection was not applied to `bank.go`.

### Recommendation
Add the same guard used in `precompiles/erc20/erc20.go` to `precompiles/bank/bank.go`'s `Execute` function: reject any call where `contract.Value().Sign() == 1` with an error (e.g., reusing or duplicating `ErrCannotReceiveFunds`), causing the EVM call to revert and preventing the value transfer from being committed at all. Apply the same audit to any other non-payable precompiles lacking a `BalanceHandlerFactory` and an explicit value check.

### Proof of Concept
1. Deploy a test contract with a function that does:
   ```solidity
   (bool ok, ) = BANK_PRECOMPILE_ADDRESS.call{value: 1 ether}("");
   ```
   or directly `.call{value: 1 ether}(abi.encodeWithSignature("balances(address,string)", addr, denom))`.
2. Since `Execute` never checks `contract.Value()` and dispatches straight into `Balances`, the call succeeds (query executes and returns data) while the attached `msg.value` is transferred to the precompile address at the EVM level.
3. Assert: the caller's native balance decreases by 1 ether, and no balance appears recoverable from the bank precompile address afterward, since it exposes no transfer/withdraw method (only `Balances`, `TotalSupply`, `SupplyOf`).

Note: I could not fully trace, within the available iterations, the exact low-level code path in `x/vm/keeper` that performs the geth-level value transfer into `statedb` and the subsequent settlement of `stateDB` balance diffs into real `x/bank` coin balances (i.e., the precise keeper/statedb commit function that converts an EVM `AddBalance` on the precompile address into an actual `x/bank` credit). This part is inferred from the standard Cosmos EVM statedb balance-tracking architecture and the parallel `erc20`/`BalanceHandler` mitigation pattern found in the codebase, not from a directly-cited commit routine, so it would be worth a background agent additionally confirming that final settlement step with a live test.

```go
func (p Precompile) Execute(ctx sdk.Context, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte
	switch method.Name {
	// Bank queries
	case BalancesMethod:
		bz, err = p.Balances(ctx, method, args)
	case TotalSupplyMethod:
		bz, err = p.TotalSupply(ctx, method, args)
	case SupplyOfMethod:
		bz, err = p.SupplyOf(ctx, method, args)
	default:
		return nil, fmt.Errorf(cmn.ErrUnknownMethod, method.Name)
	}

	return bz, err
}
```

```go
		return nil, fmt.Errorf(ErrCannotReceiveFunds, contract.Value().String())
```
