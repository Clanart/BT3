Unauthenticated OP_RETURN operator attribution in the payout transaction lets the reimbursement credit be misattributed to an operator that never fronted the withdrawal - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`Withdraw`/`InternalWithdraw` construct the `payout_tx` with the fronting operator's `xonly_pk` embedded in a plain `OP_RETURN` output. The only cryptographic authorization on this transaction is the user's withdrawal signature, which per the codebase is required to use `SIGHASH_SinglePlusAnyoneCanPay`. That sighash type commits only to input 0 and output 0 (the user payout output); it does **not** cover the anchor output or the `OP_RETURN` output that carries the operator attribution. Downstream logic (`update_finalized_payouts`, `PayoutCheckerTask`/`handle_finalized_payout`, and `is_kickoff_malicious`) trusts this unauthenticated `OP_RETURN` field as the sole source of truth for "which operator fronted this withdrawal," which is exactly the custody-attribution binding the analog rule calls out: *the operator credited versus the party that actually paid*.

### Finding Description
- The withdrawal signature the user hands to operators off-chain is generated (and validated) as `SIGHASH_SinglePlusAnyoneCanPay`: [8](#0-7) [2](#0-1) 

- `create_payout_txhandler` builds a transaction with 1 input (the user's withdrawal UTXO, key-spend) and 3 outputs: the user payout, a CPFP anchor, and an `OP_RETURN` carrying `operator_xonly_pk`: [3](#0-2) 

  Because `SIGHASH_SINGLE | ANYONECANPAY` only commits to output index 0 (the user's payout output) and input index 0, the anchor output and the `OP_RETURN` output (indices 1 and 2) are **not covered by the user's signature**. Anyone who has (or intercepts) the user's off-chain signature and the withdrawal outpoint can therefore rebuild this exact transaction with an arbitrary `operator_xonly_pk` value in the `OP_RETURN`, and it remains a validly signed Bitcoin transaction.

- This `OP_RETURN` value is later read back with zero additional authentication and used as ground truth for which operator gets reimbursement credit: [4](#0-3) 

  This feeds directly into `is_payout_handled`/`payout_payer_operator_xonly_pk` in the `withdrawals` table, which `PayoutCheckerTask` uses to select "the operator that fronted this withdrawal" and hand them a kickoff assignment/reimbursement path: [5](#0-4) [6](#0-5) 

- The verifier's fraud check (`is_kickoff_malicious`) treats a kickoff as legitimate precisely when the OP_RETURN-derived `operator_xonly_pk` equals `kickoff_data.operator_xonly_pk` — i.e., it uses the same unauthenticated field as its sole binding between "who claimed to pay" and "who is claiming reimbursement": [7](#0-6) 

The equality this construction is supposed to enforce is:
`operator credited for reimbursement == operator whose BTC actually left their wallet to fund the user's payout`

Because the `OP_RETURN` byte is unauthenticated by the withdrawal signature, this equality can be broken: the "operator credited" side is fully attacker-controllable, independent of the "who paid" side.

### Impact Explanation
If a party other than the honest fronting operator can insert their own `operator_xonly_pk` (or that of a target operator) into the broadcast payout transaction's `OP_RETURN` before/while it confirms, the `withdrawals.payout_payer_operator_xonly_pk` column will misattribute the payout. Two directions of harm map to the listed Critical impacts:
- An operator could be credited/flagged as having fronted a withdrawal it never funded, letting it claim the reimbursement kickoff/round chain for BTC it did not spend (operator reimbursed for a payout it never funded).
- Conversely, an honest operator who did front the withdrawal could have its attribution overwritten/contested if a second, differently-attributed payout-shaped transaction is what gets indexed by `update_finalized_payouts`, potentially leaving the honest operator unable to obtain its rightful reimbursement (honest operator permanently unable to be reimbursed).

### Likelihood Explanation
The exploit requires possession of the user's `SIGHASH_SinglePlusAnyoneCanPay` signature and withdrawal outpoint, both of which are explicitly described in the codebase as being shared "off-chain" and are visible once the operator broadcasts the payout transaction to the mempool (mempool transactions are public before confirmation, and RBF/CPFP fee-bumping infrastructure already exists in this codebase, meaning replacement transactions with the same signed input are routine). Whether a real attacker can reliably win the race to get their own replacement mined ahead of/instead of the legitimate operator's broadcast is an operational/timing question I was not able to fully verify within the tool budget (e.g., whether `fund_raw_transaction`/RBF replacement rules, mempool policy, or additional out-of-band checks make this infeasible in practice). This is the main remaining uncertainty in this analysis.

### Recommendation
Bind the `OP_RETURN` operator-attribution output (and the anchor output) to the user's signature by using `SIGHASH_ALL` (or `SIGHASH_ALL | ANYONECANPAY` if input flexibility for fee bumping is still required) instead of `SIGHASH_SINGLE | ANYONECANPAY`, or otherwise cryptographically commit to the operator's identity as part of the data the user signs (e.g., require the operator's key to be included in the message the aggregator/verifiers verify before treating a payout as attributable). Any accounting logic that keys reimbursement eligibility off `OP_RETURN` content should additionally require operator-side proof of expenditure (e.g., that the operator's own funds funded the transaction inputs beyond input 0) rather than trusting unauthenticated output data alone.

### Proof of Concept
Conceptual PoC (not runnable without live signing infrastructure, but derivable from the cited code):
1. User signs withdrawal input with `SIGHASH_SinglePlusAnyoneCanPay` per `sign_withdrawal_output` and shares `(withdrawal_utxo, payout_txout, sig)` with Operator A.
2. Operator A calls `withdraw`, which builds `create_payout_txhandler(input_utxo, output_txout, operator_A_xonly_pk, sig, network)` and broadcasts it (unconfirmed, in mempool).
3. Before confirmation, an attacker (or Operator B) observes the mempool transaction, extracts `(withdrawal_utxo, output_txout, sig)`, and rebuilds the same tx via `create_payout_txhandler` but with `operator_B_xonly_pk` substituted for the `OP_RETURN` value and a different anchor/fee-bump structure, keeping input 0 and output 0 identical. Because the sighash only covers input 0 / output 0, `sig` still verifies (`core/src/operator.rs:630-637` check passes) for this modified transaction.
4. Attacker broadcasts with higher fee (RBF) so it replaces Operator A's original broadcast.
5. Once confirmed, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses `operator_B_xonly_pk` from the `OP_RETURN` and marks `payout_payer_operator_xonly_pk = operator_B`, even though Operator A's payout output values are unchanged (input still comes from the user's withdrawal UTXO). Operator B is now eligible for reimbursement it never funded via `PayoutCheckerTask`/`handle_finalized_payout`.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
