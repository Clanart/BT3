## Analysis Summary

The strongest local analog to the `UltraLRT` accounting bug is in the Solana vote program's SIMD-0123 "block revenue sharing" feature: the `pending_delegator_rewards` liability counter on a vote account is incremented by a **permissionless** instruction, but no code path in the reward-distribution logic ever decrements it back down after the funds it represents are actually paid out — mirroring the report's pattern of a manual/external completion path that never reduces the tracked accounting variable (`queuedShares`).

### Title
`pending_delegator_rewards` on vote accounts is never decremented after block-reward distribution, permanently inflating the vote account's locked/withdraw-restricted balance - ([File: programs/vote/src/vote_state/handler.rs])

### Summary
`pending_delegator_rewards` is a liability field on `VoteStateV4` that represents delegator-owed lamports currently held in a vote account, and `withdraw()` refuses to let the withdraw authority take out lamports below `rent_exempt_minimum + pending_delegator_rewards`. The only mutator found for this field in the codebase is `add_pending_delegator_rewards()`, invoked from the permissionless `DepositDelegatorRewards` instruction. The reward-distribution code in `runtime/src/bank/partitioned_epoch_rewards/` only *reads* `pending_delegator_rewards` (to compute each stake account's share of the block reward) but never writes a reduced value back to the vote account, and never debits the vote account's lamports balance to match what it credits to stake accounts.

### Finding Description
`deposit_delegator_rewards()` lets **any signer** (not the vote account's withdraw/stake authority) transfer lamports into a vote account and simultaneously bump `pending_delegator_rewards`: [1](#0-0) 

The lock is enforced in `withdraw()`: [2](#0-1) 

The only place `pending_delegator_rewards` is mutated is `add_pending_delegator_rewards()`; no corresponding `sub_pending_delegator_rewards()` (or equivalent) exists anywhere in `vote_state/handler.rs`: [3](#0-2) 

During epoch-reward distribution, `calculate_block_reward()` reads `pending_delegator_rewards` purely to size the reward given to each delegated stake account: [4](#0-3) 

`build_updated_stake_reward()` then credits the *stake* account with `block_reward` lamports: [5](#0-4) 

and `distribute_epoch_rewards_in_partition()` only adjusts bank capitalization for `stake_reward_lamports_minted` and `block_reward_lamports_burned` — the successfully-distributed `block_reward_lamports_distributed` amount is neither added to capitalization nor debited from the vote account's own lamport balance, and `pending_delegator_rewards` on the vote account is never reduced: [6](#0-5) 

This is structurally identical to the `UltraLRT` bug: a value-tracking counter (`queuedShares` / `pending_delegator_rewards`) is incremented through one path, but the corresponding "completion"/redemption path (`completeExternalWithdrawalRequest()` / epoch-reward distribution) never decrements it, so the tracked liability permanently overstates the real outstanding amount.

### Impact Explanation
Because `withdraw()`'s lock (`rent_exempt + pending_delegator_rewards`) never shrinks, every successful reward distribution cycle makes the discrepancy between the *tracked* liability and the *actual* remaining liability worse. Concretely:
- The vote account's withdraw authority permanently loses access to an ever-growing amount of the vote account's lamports, even though the delegator rewards those lamports nominally represent have already been paid out to stake accounts — a direct, unprivileged fund-lock/loss vector.
- Since `DepositDelegatorRewards` requires no relationship to the vote account's authorities (only the depositor's own signature), any third party can grief a validator's vote account by repeatedly depositing small amounts, permanently ratcheting up the locked balance with no possible recovery path in the current code.
- The mismatch between real lamports transferred to stake accounts vs. capitalization changes tracked in `distribute_epoch_rewards_in_partition()` also risks a capitalization-mismatch class failure (checked at snapshot-load time via `MismatchedCapitalization`), which can affect the whole network deterministically once the feature is active.

### Likelihood Explanation
This depends on feature activation (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing` — SIMD-0123/SIMD-0232/SIMD-0291), so it is not yet exploitable on networks where these are inactive. Once active, the trigger is trivial and requires no privileged access: calling `DepositDelegatorRewards` is a single permissionless instruction, and the missing decrement is a straightforward code-path gap, not a race condition or edge case.

### Recommendation
Add an explicit decrement of `pending_delegator_rewards` at the same points block rewards are actually distributed (`store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition`), and correspondingly debit the vote account's lamport balance (or otherwise reconcile it with the bank's capitalization tracking) so the liability field always reflects the true outstanding, undistributed delegator-reward balance. Add an invariant assertion (e.g., in tests or via `assert_capitalization_diff`-style checks) that `pending_delegator_rewards` never exceeds the vote account's real lamport balance minus rent-exemption.

### Proof of Concept
1. Enable `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing`.
2. Any signer calls `VoteInstruction::DepositDelegatorRewards { deposit: N }` against a target vote account, per the tested flow in `programs/vote/src/vote_processor.rs` (`test_deposit_delegator_rewards`), incrementing `pending_delegator_rewards` by `N` — see the assertions confirming the field updates on each call: [7](#0-6) 
3. Trigger an epoch boundary so `distribute_partitioned_epoch_rewards` runs and stake accounts are credited block rewards derived from `pending_delegator_rewards` via `calculate_block_reward`.
4. Inspect the vote account after distribution: `pending_delegator_rewards` is unchanged (no decrement code path exists), while the reward has already been paid to stake accounts — `withdraw()`'s minimum-balance check still enforces the full pre-distribution `pending_delegator_rewards`, permanently over-locking the withdraw authority's funds.

**Uncertainty note:** Due to index size limits, I could not exhaustively confirm there is no decrement logic located in a file outside what my searches returned (e.g., a helper deep in `stakes.rs` or an as-yet-unindexed file). I recommend a Devin session with full repository access to grep the entire `runtime/src/bank/partitioned_epoch_rewards/` and `programs/vote/` directories for any `pending_delegator_rewards -=`/`sub_pending_delegator_rewards`/`set_pending_delegator_rewards` calls to fully rule this out before treating this as confirmed.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    /// Process reward credits for a partition of rewards
    /// Store the rewards to AccountsDB, update reward history record and total capitalization.
    fn distribute_epoch_rewards_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) {
        let pre_capitalization = self.capitalization();
        let (
            DistributionResults {
                stake_reward_lamports_minted,
                stake_reward_lamports_burned,
                block_reward_lamports_distributed,
                block_reward_lamports_burned,
                updated_stake_rewards,
            },
            store_stake_accounts_us,
        ) = measure_us!(self.store_stake_accounts_in_partition(partition_rewards, partition_index));

        // increase total capitalization by the distributed rewards
        self.capitalization
            .fetch_add(stake_reward_lamports_minted, Relaxed);

        // decrease total capitalization by burned block rewards
        self.capitalization
            .fetch_sub(block_reward_lamports_burned, Relaxed);

        // decrease distributed capital from epoch rewards sysvar
        self.update_epoch_rewards_sysvar(
            stake_reward_lamports_minted + stake_reward_lamports_burned,
            block_reward_lamports_distributed + block_reward_lamports_burned,
        );

        // update reward history for this partitioned distribution
        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),
            partition_index,
            store_stake_accounts_us,
            store_stake_accounts_count: updated_stake_rewards.len(),
            distributed_rewards: stake_reward_lamports_minted,
            burned_rewards: stake_reward_lamports_burned,
            distributed_block_rewards: block_reward_lamports_distributed,
            burned_block_rewards: block_reward_lamports_burned,
        };

        report_partitioned_reward_metrics(self, metrics);
    }
