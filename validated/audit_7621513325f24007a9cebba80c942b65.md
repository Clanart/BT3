## Finding

The bug-class in the report is: a security check enforced in one function (`balanceOf`) is not applied to a sibling/plural function (`balanceOfBatch`), letting an invariant be bypassed through the unguarded path. The direct analog in GitHub Desktop is the repo-relative path-containment check (`resolveWithin`) that is enforced for **one** file-path consumer but skipped by every other consumer that turns a git-reported file path into a filesystem path for OS-level actions (reveal in file manager, open with default program, open in external editor).

### Title
Unvalidated repository-relative file paths allow symlink/traversal escape when revealing or opening files from a malicious repo - (File: `app/src/lib/app-shell.ts`)

### Summary
Desktop has a helper, `resolveWithin`, specifically built to guarantee that a path segment coming from repository data resolves to a location *inside* the repository root, using `fs.realpath` to defeat symlink tricks and directory traversal [1](#0-0) . It is used in exactly one place — `Dispatcher.openRepositoryFromUrl`, which explicitly rejects absolute paths and calls `resolveWithin` before invoking `shell.showItemInFolder` [2](#0-1) . However, `revealInFileManager`, the function used by nearly every "Reveal in File Manager" / "Open with default program" / "Open in external editor" context-menu action in the app, does a raw `Path.join(repository.path, path)` with no containment or symlink check at all before calling `shell.showItemInFolder` [3](#0-2) . The same unguarded pattern repeats in `sidebar.tsx`'s `onOpenItem` [4](#0-3) , `filter-changes-list.tsx`'s context-menu path builders [5](#0-4) , `selected-commits.tsx` [6](#0-5) , `pull-request-files-changed.tsx` [7](#0-6) , `unmerged-file.tsx` [8](#0-7) , and `copilot-conflicts-dialog.tsx` [9](#0-8) .

### Finding Description
The corrupted invariant is: *"a path derived from a repository-tracked/working-directory file (`file.path`) must resolve to a real filesystem location inside `repository.path`."* Desktop's own comment on `resolveWithin` and the doc-comment on `IAppShell.showItemInFolder`/`openPath` ("Do not use this method with non-validated paths") both acknowledge this invariant must be enforced before calling into the shell [10](#0-9) . Yet `revealInFileManager`, which is wired to every changes list, commit history, PR-files, and conflict-resolution context menu, never calls `resolveWithin`; it simply concatenates strings with `Path.join` [11](#0-10) . A committed symlink whose name is a path segment (e.g. a tracked symlink `evil` pointing at `/` or at a sensitive absolute directory) plus a git-reported path like `evil/some/inner/file` will lexically join to a string that still looks like it's "under" `repository.path`, but `fs.realpath`/the OS filesystem call actually follows the symlink and lands outside the repository tree entirely. `resolveWithin` is specifically designed to catch this by comparing `realpath(resolved)` against `realpath(root)` — but that check simply isn't invoked on any of these call sites.

### Impact Explanation
An attacker who controls a cloned/fetched repository (a valid Desktop threat category, since Desktop routinely opens arbitrary repos supplied via clone URLs, `x-github-desktop://openRepo` deep links, or PR checkouts) can plant a symlink in the tree such that `git status`/diff reports a working-directory or committed file path built on that symlink. When the victim right-clicks and chooses "Reveal in File Manager" or "Open with default program," Desktop calls `shell.showItemInFolder`/`shell.openPath` with a path that physically resolves outside the repository, exposing or launching content in a directory the user never intended to browse or execute (e.g. reveal-then-open workflows that can be steered to a spoofed same-named file at a system location, or invoking OS default-app execution on a spoofed target). This aligns with the report's core theme: a guard proven necessary in one code path is silently absent everywhere else that touches the same class of untrusted input.

### Likelihood Explanation
This requires no local access, no admin rights, and no social engineering beyond the normal, expected Desktop workflow of cloning/opening a repository and using standard context-menu actions ("Reveal in File Manager", "Open with default program") that are core, frequently used features. The only "unnatural" step is a context-menu click that users perform routinely, so likelihood is meaningfully higher than typical local-access-required issues, matching the accepted "attacker controls a cloned/fetched repository" threat model.

### Recommendation
Route every consumer that turns a repository-relative `file.path` into a filesystem path — `revealInFileManager`, `onOpenItem`/`openFile` call sites, and the various context-menu builders in `filter-changes-list.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `unmerged-file.tsx`, and `copilot-conflicts-dialog.tsx` — through `resolveWithin(repository.path, file.path)` (as already done in `dispatcher.ts`'s `openRepositoryFromUrl`) and refuse the action (with a logged warning, mirroring the existing `log.error('Prevented attempt to open path outside of the repository root...')` pattern) whenever it returns `null`.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink named `link` pointing to `/` (or another sensitive absolute path), plus a file that git will report as `link/secret` in status/diff output for that repo state.
2. Victim clones/opens this repository in Desktop.
3. Victim right-clicks the reported change/file and selects "Reveal in File Manager" (or "Open with default program").
4. `revealInFileManager(repository, "link/secret")` executes `Path.join(repository.path, "link/secret")` with no `resolveWithin` check [11](#0-10) , then calls `shell.showItemInFolder(fullyQualifiedFilePath)`; because `link` is a symlink to `/`, the OS follows it and reveals/opens a location entirely outside the cloned repository, unlike the guarded `openRepositoryFromUrl` path which would have returned `null` and refused the action [12](#0-11) .

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
 * Reveals a file from a repository in the native file manager.

 * @param repository The currently active repository instance
 * @param path The path of the file relative to the root of the repository

export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
```
