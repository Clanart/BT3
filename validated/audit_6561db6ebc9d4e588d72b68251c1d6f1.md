### Title
Unprivileged callers can overwrite an existing ERC pointer contract's bytecode with no storage-layout validation, corrupting pointer accounting - ([File: x/evm/keeper/pointer_upgrade.go])

### Summary
The pointer precompile at `0x100b` exposes `addCW20Pointer` / `addCW721Pointer` / `addCW1155Pointer` / `addNativePointer` methods that any EVM caller can invoke with no access control. When a pointer for the given CW/native token already exists, these methods route into `Keeper.UpsertERCPointer`, which redeploys the pointer contract's constructor over the *existing* contract address and unconditionally overwrites the deployed bytecode via `k.SetCode`, without any check that the new code's storage layout is compatible with what is already stored (balances, allowances, owners, approvals, etc.). This mirrors the Quantstamp/Bemo Finance finding: an admin/anyone-triggerable code-replace operation with "no validation whatsoever ... which in theory could allow ... to modify the storage of the contract breaking the accounting of the system."

### Finding Description
`AddCW20`/`AddCW721`/`AddCW1155`/`AddNative` in `precompiles/pointer/pointer.go` have no `onlyOwner`/admin gating and are reachable by any transaction sender through the EVM precompile at `PointerAddress = 0x000000000000000000000000000000000000100b`: [1](#0-0) 

They call into `Keeper.UpsertERCCW20Pointer` → `Keeper.UpsertERCPointer`: [2](#0-1) 

`UpsertERCPointer` checks whether a pointer already `exists` for the pointee; if so, it does **not** deploy a fresh contract — it re-packs the constructor args against the *currently embedded artifact binary* (`artifacts.GetBin(typ)`), runs it via `evm.GetDeploymentCode` against the existing address, and then directly overwrites the on-chain bytecode with `k.SetCode(writeCtx, contractAddr, ret)`: [3](#0-2) 

There is no verification anywhere in this path that:
- the storage layout of the new embedded pointer bytecode is compatible with the storage already written under the old bytecode (balances/allowances/owners for CW20/CW721/CW1155 pointers), and
- the "version" recorded for the pointer (`SetERC20CW20PointerWithVersion(... cw20.CurrentVersion(ctx))`) actually matches what was deployed before the overwrite — the setter simply always re-stamps the pointer with `CurrentVersion`, i.e. this is effectively a blind "update code" operation analogous to the reported `OP::UPDATE_CODE` handler in `financial.fc`, which likewise took new code from the caller and executed `set_code`/`set_c3` without validating the storage migration.

Because this precompile method is public (any caller, not gated to governance or an admin), any unprivileged user can trigger a redeploy/overwrite of bytecode for an already-existing pointer at any time — for example immediately after a chain upgrade changes the embedded pointer artifact (`artifacts.GetBin("cw20")`/`"cw721"`/`"cw1155"`/`"native"`) to a new storage layout, or even mid-block to intentionally clobber the pointer's live bytecode with the current binary's constructor semantics.

### Impact Explanation
If a chain upgrade ships a new pointer-contract artifact whose storage layout differs from a previously-deployed pointer's layout (e.g. a new field, reordered mapping slots, or new `minters`/`allowances` bookkeeping), the very first unprivileged call to `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer`/`addNativePointer` for an existing pointee will overwrite that pointer's live bytecode without migrating its existing storage. Because ERC pointer contracts back the CW↔EVM bridge for token balances, this can corrupt or desynchronize on-chain accounting for existing pointer holders (e.g. `balanceOf`/`ownerOf`/`allowance` reads mapping to the wrong slots under the new implementation), leading to fund-loss/freezing conditions for holders of the pointed asset. This satisfies "unauthorized transfer via precompile or pointer" / permanent freezing criteria, since the caller triggering it needs no special privilege and the write path performs no compatibility check.

### Likelihood Explanation
Likelihood depends on there being an artifact/storage-layout change between pointer versions deployed at different times (this is the normal expected evolution path per `x/evm/AGENTS.md`: "Pointers are versioned and can be upgraded"). Any user can trivially call the public precompile method for any existing pointer target at any time to force the redeploy path, so exploitability itself requires zero privilege — only the precondition of a storage-layout-incompatible artifact update needs to occur (which the pointer-upgrade design explicitly anticipates and which governance proposals like `HandleAddERCNativePointerProposalV2` are built to perform, meaning the team does intend future incompatible upgrades to occur through this exact code path).

### Recommendation
- Gate `UpsertERCPointer`'s in-place `SetCode` overwrite path to a privileged/governance caller only when the pointer already `exists`, exactly as the upgrade-proposal handlers already do; require unprivileged precompile calls to only be able to create new pointers, not silently overwrite existing bytecode.
- Before overwriting bytecode for an existing pointer, verify pointer-code-version compatibility (store and check an explicit "pointer code version" per pointee, distinct from blindly re-stamping `CurrentVersion` on every write) and refuse or explicitly migrate storage when versions differ, mirroring the report's recommended pattern of snapshotting the old storage layout and running an explicit `migrate()` step after `set_code`.
- Add an explicit storage-migration function analogous to CosmWasm's `migrate` entrypoint for pointer redeploys, so that any accounting-relevant storage (balances, allowances, owners) is provably preserved across an artifact bytecode change.

### Proof of Concept
1. Deploy/register a CW20↔ERC20 pointer for `cw20Addr` via `addCW20Pointer(cw20Addr)` under artifact version N; the pointer contract at `contractAddr` accumulates real balances via normal ERC20 usage forwarded from CW20 state. [1](#0-0) 
2. Chain upgrades and ships a new `cw20` pointer artifact (version N+1) with an incompatible storage layout (e.g., additional/reordered storage slots for allowances or minters) baked into `x/evm/artifacts/cw20`.
3. Any unprivileged EVM account calls `addCW20Pointer(cw20Addr)` again. Because `existingAddr, _, exists := getter(...)` returns `exists=true`, the keeper runs `evm.GetDeploymentCode` with the new artifact bytecode against the *existing* `contractAddr` and calls `k.SetCode(writeCtx, contractAddr, ret)`, overwriting the runtime bytecode in place with zero checks against the old layout. [4](#0-3) 
4. Subsequent reads of balances/allowances on the pointer contract now interpret the pre-existing storage slots under the new (incompatible) layout, producing incorrect balances/allowances/ownership for existing holders — with the operation having been triggered by an arbitrary unprivileged caller, not an admin.

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
