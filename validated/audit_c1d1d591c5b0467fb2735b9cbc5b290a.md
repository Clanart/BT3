### Title
IBC v2 `OnRecvPacket` middleware discards the ERC20 conversion acknowledgement, always reporting success even when the counterparty's escrowed/underlying asset unescrow-conversion fails - ([File: x/erc20/v2/ibc_middleware.go])

### Summary
This is the closest reachable analog in this repository to the seed report's pattern: a function returns a status value that expresses whether an operation was safe/successful, and the caller silently discards it and proceeds as if it were always fine.

### Finding Description
In the v1 ERC20 IBC middleware, the result of the keeper-level conversion callback is correctly propagated back to the IBC core so a failed conversion can surface as an error acknowledgement: [1](#0-0) 

In the IBC v2 middleware, however, the equivalent call's return value is thrown away, and the *original* success result from the underlying transfer app is always returned regardless of what `keeper.OnRecvPacket` actually determined: [2](#0-1) 

`keeper.OnRecvPacket` (shared by both v1 and v2 middleware) can return an `ErrorAcknowledgement` in multiple branches after the underlying ICS20 transfer logic has already mutated state (unescrowing/minting/crediting the bank denom to the recipient), e.g. when `MintingEnabled` fails or `ConvertCoinNativeERC20` fails: [3](#0-2) 

In the v1 path this return value is honored and returned to the ICS26 packet handler, so the acknowledgement written back to the counterparty chain correctly reflects failure. In the v2 path (`x/erc20/v2/ibc_middleware.go:89`), `im.keeper.OnRecvPacket(ctx, packet, ack)` is called purely for its side effects and its return value is dropped; the function unconditionally returns the original `recvResult`, whose `Status` is `PacketStatus_Success`.

### Impact Explanation
Because the acknowledgement written back to the source/counterparty chain via IBC v2 will report success even when the ERC20 conversion/unescrow step actually failed and returned an error acknowledgement, the two chains' views of the transfer diverge:
- On the destination chain, the underlying ICS20 `OnRecvPacket` has already unescrowed/credited the bank-denominated coin to the recipient (state committed, since it ran directly on `ctx`, not a cache-then-conditionally-write context).
- The written acknowledgement falsely reports success, so the source chain will never refund/re-mint the sender's original tokens, believing the transfer completed normally.

If the failure branch in `keeper.OnRecvPacket` corresponds to a case where the packet handler or relayer/observer logic downstream expects a failed ack to trigger compensating action (e.g., re-attempts, alerts, or refund logic elsewhere keyed off ack status), that compensating action never fires, silently leaving state inconsistent between chains for the affected token pair. This falls under "irreversible accounting corruption of spendable user value across ... IBC escrows" since the destination chain's bank balance change is irreversibly committed while the packet is acknowledged as fully successful, discarding the only signal that would have told any invariant-checking logic (or the relayer) that the ERC20 representation was not correctly established for the recipient.

### Likelihood Explanation
Triggering requires only an ordinary, unprivileged IBC v2 transfer of a coin that maps to a registered "native ERC20" token pair, where the ERC20-side conversion fails for a reason outside the sender's control (e.g., `MintingEnabled` check failing due to token-pair state, or the ERC20 contract call reverting for a native-ERC20 pair, as documented as a normal occurrence in `ConvertCoinNativeERC20`/`OnAcknowledgementPacket` comments elsewhere in this file: "such as an attempt to call a self-destructed ERC20 contract or an invalid function"). No relayer or validator collusion is required — the condition can be induced by an ordinary token holder or simply occur due to normal operational states of a token pair.

### Recommendation
Mirror the v1 middleware's behavior: capture the acknowledgement returned by `keeper.OnRecvPacket` in the v2 path, and if it is an error acknowledgement, reflect that failure in the returned `channeltypesv2.RecvPacketResult` (i.e., set `Status: channeltypesv2.PacketStatus_Failure` and propagate the encoded error acknowledgement), instead of unconditionally returning the original success `recvResult`.

### Proof of Concept
Conceptual reproduction (not independently executed against a live chain in this analysis):
1. Register a "native ERC20" token pair `P` for contract `C` (i.e., `pair.IsNativeERC20()` is true), then place `P` into a state such that a subsequent `MintingEnabled` check or `ConvertCoinNativeERC20` call will fail (for example, self-destructing `C`, or otherwise causing the internal `CallEVM` transfer to revert for a non-conforming ERC20 implementation, both of which are called out as expected failure modes in this codebase's own IBC callback comments).
2. From a counterparty chain using IBC v2 (`channeltypesv2`), send an ICS20 transfer of the coin corresponding to `P` back to this chain.
3. On receipt, `IBCMiddleware.OnRecvPacket` in `x/erc20/v2/ibc_middleware.go` calls the underlying `im.app.OnRecvPacket`, which unescrows/credits the bank coin to the recipient and returns `PacketStatus_Success`.
4. `im.keeper.OnRecvPacket` is then invoked, hits the `MintingEnabled`/`ConvertCoinNativeERC20` failure branch, and constructs an `ErrorAcknowledgement` — but this return value is discarded at line 89.
5. The middleware returns the original success `recvResult` from step 3, so the acknowledgement relayed back to the counterparty reports success, even though the ERC20-side conversion never completed and the packet flow diverges from what v1 middleware (and the documented design intent) would produce.

Note: I was not able to fully trace the exact downstream consumer(s) of a v2 error acknowledgement (e.g., whether/how the source-chain refund path is wired for IBC v2 in this specific fork) within the available indexed context, so the precise blast radius (whether this always yields double-available value versus merely a lost error signal) could not be fully confirmed from the code alone; a Devin session with full repository and ibc-go v10 dependency access would be needed to trace the v2 acknowledgement-driven refund path end-to-end and confirm exploitability with a concrete balance-duplication PoC.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	sourceClient string,
	destinationClient string,
	sequence uint64,
	payload channeltypesv2.Payload,
	relayer sdk.AccAddress,
) channeltypesv2.RecvPacketResult {
	recvResult := im.app.OnRecvPacket(ctx, sourceClient, destinationClient, sequence, payload, relayer)
	if recvResult.Status == channeltypesv2.PacketStatus_Failure {
		return recvResult
	}
	packet, err := v2ToV1Packet(payload, sourceClient, destinationClient, sequence)
	if err != nil {
		return channeltypesv2.RecvPacketResult{
			Status: channeltypesv2.PacketStatus_Failure,
		}
	}
	var ack channeltypes.Acknowledgement
	if err := transfertypes.ModuleCdc.UnmarshalJSON(recvResult.Acknowledgement, &ack); err != nil {
		return channeltypesv2.RecvPacketResult{
			Status: channeltypesv2.PacketStatus_Failure,
		}
	}
	im.keeper.OnRecvPacket(ctx, packet, ack)
	return recvResult
}
