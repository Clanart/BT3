Based on my investigation, I found a genuine analog: `addRemote` in `app/src/lib/git/remote.ts` performs `git remote add <name> <url>` with zero validation of the URL scheme, and this function is fed directly by an attacker-influenced value in the PR-checkout flow.

### Title
Unvalidated PR-fork `clone_url` from GitHub API is passed straight into `git remote add`/`git fetch`, allowing an unprivileged fork owner to smuggle a malicious Git transport URL - (File: app/src/lib/stores/app-store.ts)

### Summary
When a user checks out a pull request from a fork, Desktop takes the `clone_url` of the PR's `head.repo` — a field returned by the GitHub API but semantically controlled by whoever owns the fork — and passes it unvalidated to `addRemote()`, which shells out to `git remote add name url`. The remote is then fetched via `_fetchRemote`. Neither `addRemote` nor the call site restricts the URL's transport scheme (e.g. rejecting `ext::`, `fd::`, or other non-`https`/`ssh`/`git` transports), so a crafted `clone_url` value could be used to make the local Git installation invoke an unexpected transport helper. This mirrors the reported bug-class: an attacker supplies a "fake" resource reference (a fake vault / here, a fake remote URL) that the victim's own trusted code path uses without whitelisting, and the trusted path performs a privileged action (spending protocol assets / here, spawning a Git transport process) on the attacker's behalf.

### Finding Description
`addRemote` has no allow-list of URL schemes: [1](#0-0) 

It's invoked directly with `headCloneUrl`, obtained from the PR object, inside `_findPullRequestBranch`: [2](#0-1) 

That value originates from either the deep-link handler (`openPullRequestFromUrl`, using `pullRequest.head.repo.clone_url` fetched from the API for an arbitrary PR number supplied via an `x-github-client://` URL) or from `checkoutPullRequest` in the dispatcher, using `pullRequest.head.gitHubRepository.cloneURL`: [3](#0-2) [4](#0-3) 

Once the remote is added, Desktop calls `_fetchRemote`, which shells out to `git fetch` against that remote — meaning whatever transport scheme is embedded in the URL will be invoked by the local Git binary: [5](#0-4) 

None of the existing hardening in this codebase covers this path. The `resolveWithin` / path-traversal guards in `app/src/lib/path.ts`, the `sanitizeCloneName` clone-path protections in `app/src/lib/remote-parsing.ts`, and the `isClonePathSensitive` check in `app/src/lib/git/clone.ts` all address the *destination path* of a clone, not the *transport scheme* of a remote URL used for `remote add`/`fetch`. `envForProxy` in `app/src/lib/git/environment.ts` only special-cases `https?://` prefixes for proxy resolution and otherwise passes any URL through untouched — it makes no attempt to reject dangerous schemes: [6](#0-5) 

### Impact Explanation
If Git is invoked against a remote URL using an unexpected transport helper (rather than `https://`/`ssh://`/`git://`), the local Git installation will spawn that transport's helper process on the victim's machine using attacker-supplied arguments embedded in the URL, as part of a normal, low-friction "checkout PR" action that requires no special user awareness of the danger. This is a code-execution-adjacent primitive achieved purely by an untrusted, attacker-controlled API object (`clone_url`) flowing into a privileged local operation (`git remote add` + `git fetch`) without any transport allow-listing, directly analogous to the original report's "fake vault passed as argument with no validation" pattern.

### Likelihood Explanation
Likelihood is limited by two factors I could not fully verify from the index alone: (1) whether GitHub.com's API actually permits registering/returning a fork `clone_url` with an arbitrary non-standard scheme (this would typically be constrained server-side), and (2) whether the installed Git binary has non-standard transport helpers enabled/available to it (some risky protocol helpers require explicit opt-in via `protocol.<name>.allow` in modern Git, which I did not find referenced anywhere as being restricted or enabled in this codebase — `GIT_ALLOW_PROTOCOL`/`protocol.` allow-listing produced no hits). This means the exploitability strongly depends on Git's own default protocol allow-list behavior, which this codebase does not customize in either direction.

### Recommendation
Before calling `addRemote` (and before any `fetch`/`clone`/`ls-remote` invocation that uses a URL sourced from GitHub API responses, PR objects, or deep links), validate that the URL uses an explicit allow-list of schemes (`https:`, `git:`, `ssh:`, or the `user@host:path` SCP-like form already parsed by `parseRemote` in `app/src/lib/remote-parsing.ts`). Reject anything else, mirroring the pattern already used for filesystem paths in `resolveWithin`/`isClonePathSensitive`. Additionally, consider explicitly setting `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (or the equivalent `-c protocol.allow=never` plus per-scheme `-c protocol.<scheme>.allow=always`) in the environment used for these operations, providing defense-in-depth independent of Desktop's own validation.

### Proof of Concept
Exact reproduction requires confirming GitHub API/UI acceptance of a non-standard-scheme `clone_url` for a fork, which I could not verify from the index. Conceptually:
1. Attacker forks a repository and (through some means that yields a `head.repo.clone_url`/`head.gitHubRepository.cloneURL` containing a non-`https`/`ssh`/`git` transport string, e.g. an `ext::` style value) opens a PR against the victim's repo, or crafts an `x-github-client://openRepo/...&pr=<n>` deep link pointing at such a PR.
2. Victim, using GitHub Desktop, clicks "Checkout" on the PR (`pull-request-list.tsx` → `dispatcher.checkoutPullRequest` → `appStore._checkoutPullRequest`) or opens the deep link (`dispatcher.openRepositoryFromUrl` → `openPullRequestFromUrl`).
3. `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the unvalidated URL, then `_fetchRemote` executes `git fetch <remote>`, causing Git to invoke whatever transport the URL specifies with attacker-controlled arguments.

Given the uncertainty about (1) GitHub API's own constraints on `clone_url` values and (2) the specific Git version/build's protocol allow-list defaults, this should be treated as a **plausible but unverified** analog — a Devin session with terminal access should confirm both the API-side and Git-runtime-side assumptions before treating this as confirmed-exploitable.
