### Title
Missing domain/audience separation in EVM↔Sei address association (`associate`, `associatePubKey`, `AssociateTx`) allows force-linking a victim's accounts using a signature never intended for Sei - (File: `precompiles/addr/addr.go`)

### Summary
The SAML advisory's root cause is that a cryptographic assertion (SAML response) carries no binding to the specific "audience" (the relying party) it was created for, so it can be replayed against a different consumer than intended. Sei's `addr` precompile (`Associate`) and the analogous `AssociateTx`/`MsgAssociate` flow have the same class of defect: they recover a secp256k1 public key from a raw `(v, r, s)` signature over `keccak256(customMessage)` with no chain ID, no contract/precompile address, and no EIP-191 ("\x19Ethereum Signed Message:\n") domain prefix baked into the digest, and then use that recovered key to force-link a Sei bech32 address to an EVM address.

### Finding Description
`PrecompileExecutor.associate` in [1](#0-0)  takes attacker-supplied `v, r, s, customMessage`, hashes the message with a bare `crypto.Keccak256Hash([]byte(customMessage))` (no EIP-191 prefix, no chain ID, no contract-address tag), and passes it to `helpers.GetAddresses` to recover the signer's EVM address, Sei address, and pubkey: [2](#0-1) 

`helpers.GetAddresses`/`RecoverPubkey` in [3](#0-2)  perform a plain `ecrecover` over whatever 32-byte hash is supplied — there is no verification that the signature was ever intended for the Sei "associate" audience. The same unbound-digest pattern is used by `HandleAssociateTx` in [4](#0-3) , which is reachable directly from a submitted `AssociateTx`/`MsgAssociate`.

Compare this to `AuthorityToPreAssociate`, which handles the structurally similar EIP-7702 `SetCodeAuthorization` case and explicitly documents the exact bug class and why it must be defended against: [5](#0-4) 

That function was hardened to check `auth.ChainID` against the local chain before pre-associating the recovered authority ( [6](#0-5) ), and a regression test explicitly verifies foreign-chain authorizations are rejected: [7](#0-6) .

No equivalent binding exists for the `associate`/`associatePubKey` precompile methods or `AssociateTx`: any raw ECDSA signature a victim ever produced over a message whose keccak256 digest can be reproduced by an attacker-chosen `customMessage` string (i.e., any unprefixed/raw digest signature the victim made for a wholly different context, chain, or protocol) can be replayed here, because the digest carries no marker of "this is for Sei address association." This is the direct analog of SAML's missing audience check: a signature/assertion produced for one context is accepted by a different consumer because the consumer never checks who/what it was meant for.

### Impact Explanation
Association permanently and irreversibly links a Sei bech32 address to an EVM address in on-chain state (`AssociateAddresses`), bridging usei/wei balances and account state between the two address spaces. The codebase's own comment on the sibling EIP-7702 code path states the consequence of an unauthorized/forced association: "migrating their direct-cast balance and orphaning staking/distribution state" ( [8](#0-7) ). Because the `associate`/`AssociateTx` paths lack the domain/chain binding that was added for the EIP-7702 path, an attacker who can obtain any raw (non-domain-separated) signature made by a victim — potentially from an unrelated chain or protocol — could force that victim's Sei and EVM identities to be linked without consent, exposing them to the same fund/state-migration risk the EIP-7702 fix was written to prevent.

### Likelihood Explanation
Exploitability depends on an attacker being able to source a raw (unprefixed) ECDSA signature from a victim whose signed message can be reproduced as an attacker-chosen `customMessage` string — I was not able to fully confirm from the available files whether front-end tooling always applies an EIP-191 personal-sign prefix before calling this precompile (test files `precompiles/addr/addr_test.go` and `integration_test/precompile_tests/precompiles/addr.spec.ts` reference `personal_sign`, but their contents were not available in the index to confirm whether the on-chain hash construction accounts for that prefix). This uncertainty affects how easily an attacker can find a naturally-occurring victim signature that satisfies the digest, so likelihood should be treated as moderate/uncertain pending confirmation of caller-side signing conventions.

### Recommendation
Bind the association digest to a Sei-specific domain: include a fixed purpose string (e.g., `"sei-associate"`), the chain ID, and/or the precompile/module address inside the hashed payload (and/or require an EIP-191 personal-sign prefix) so a signature can only be valid for this specific association action on this specific chain — mirroring the chain-ID check already added to `AuthorityToPreAssociate` for EIP-7702 authorizations.

### Proof of Concept
Conceptual (not fully verified against live front-end signing conventions due to index limitations):
1. Victim signs a raw, unprefixed 32-byte digest for an unrelated purpose/protocol/chain such that the signed digest equals `keccak256(M)` for some string `M`.
2. Attacker observes the public `(v, r, s)` and reconstructs `M`.
3. Attacker calls the `addr` precompile's `associate(v, r, s, M)` (or submits an `AssociateTx`/`MsgAssociate` with `CustomMessage = M`), per [9](#0-8) .
4. `helpers.GetAddresses` recovers the victim's EVM/Sei address pair from the replayed signature and force-associates them via `associateAddresses`, without the victim ever intending an association on Sei.

**Note:** Due to index size limits, the exact client-side signing scheme used by the reference dApp/tests (`precompiles/addr/addr_test.go`, `integration_test/precompile_tests/precompiles/addr.spec.ts`) could not be fully retrieved to confirm whether an EIP-191 prefix is already applied out-of-band before submission, which would partially mitigate this. A Devin session with full repository access would be needed to inspect those files and confirm exploitability end-to-end.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func GetAddresses(V *big.Int, R *big.Int, S *big.Int, data common.Hash) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	pubkey, err := RecoverPubkey(data, R, S, V, true)
	if err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, err
	}

	return GetAddressesFromPubkeyBytes(pubkey)
}

func GetAddressesFromPubkeyBytes(pubkey []byte) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	evmAddr, err := PubkeyToEVMAddress(pubkey)
	if err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, err
	}
	seiPubkey := PubkeyBytesToSeiPubKey(pubkey)
	seiAddr := sdk.AccAddress(seiPubkey.Address())
	return evmAddr, seiAddr, &seiPubkey, nil
}

func HandleAssociateTx(ctx sdk.Context, ek *evmkeeper.Keeper, atx *ethtx.AssociateTx, readOnly bool) (sdk.Context, error) {
	V, R, S := atx.GetRawSignatureValues()
	V = new(big.Int).Add(V, utils.Big27)
	// Hash custom message passed in
	customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
	if err != nil {
		return ctx, err
	}
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	}
	if !IsAccountBalancePositive(ctx, ek, seiAddr, evmAddr) {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
	}
	if !readOnly {
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, seiPubkey); err != nil {
			return ctx, err
		}
	}
	return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil
