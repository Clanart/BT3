### Title
Missing caller-authorization check in `CW721ERC721Pointer.transferFrom`/`approve`/`setApprovalForAll` allows any account to transfer or approve any pointer-wrapped CW721 NFT - ([File: contracts/src/CW721ERC721Pointer.sol])

### Summary
`CW721ERC721Pointer` is the ERC721 pointer contract that wraps a CosmWasm CW721 collection so it can be used through the EVM. Its overridden `transferFrom`, `approve`, and `setApprovalForAll` functions never reference `msg.sender` and never call the standard `_isApprovedOrOwner` / operator-approval check that the base `ERC721` implementation relies on. [1](#0-0) 

### Finding Description
In OpenZeppelin-style ERC721 implementations, `transferFrom(from, to, tokenId)` must verify that `msg.sender` is either the token owner, an address individually approved for `tokenId`, or an operator approved for all of `from`'s tokens (`_isApprovedOrOwner`). `CW721ERC721Pointer` overrides this function but only checks that the caller-supplied `from` argument equals the actual on-chain owner returned by `ownerOf(tokenId)` — it never checks who is calling:

```solidity
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    ...
    _execute(bytes(req));
}
``` [2](#0-1) 

Since `from` is attacker-controlled and only validated for correctness (not for identity of the caller), **any address can call `transferFrom(ownerAddr, attackerAddr, tokenId)` for any token it does not own or is not approved for**, and the pointer contract will execute a CosmWasm `transfer_nft` message on behalf of the real owner via the wasmd precompile delegatecall (`_execute`).

The same pattern exists in `approve` and `setApprovalForAll`: neither checks that `msg.sender` is the token owner or an already-approved operator before granting a new approval:

```solidity
function approve(address approved, uint256 tokenId) public override {
    string memory spender = ...
    string memory req = _curlyBrace(_formatPayload("approve", ...));
    _execute(bytes(req));
}

function setApprovalForAll(address operator, bool approved) public override {
    ...
    _execute(bytes(_curlyBrace(_formatPayload("approve_all", op))));
}
``` [3](#0-2) 

`_execute` performs a `delegatecall` into the wasmd precompile using `Cw721Address` as the target contract, meaning these CosmWasm messages are dispatched with the pointer contract's own authority over the underlying CW721 collection, not the caller's: [4](#0-3) 

A `grep` for `msg.sender` in this file returns zero matches, confirming caller identity is never checked anywhere in the transactional (state-changing) functions.

### Impact Explanation
This is a direct analog of the CVE-2026-73239 bug class (IDOR / missing permission checks on individual objects — here, individual NFTs instead of Allura "Artifacts"). Any unprivileged EVM transaction sender can:
1. Call `approve(attacker, tokenId)` on someone else's pointer-wrapped NFT to grant themselves spending rights, or
2. Call `transferFrom(victimOwner, attacker, tokenId)` directly to steal any NFT held in the pointed-to CW721 collection.

This results in unauthorized transfer of NFT assets (fund/asset loss) through a public precompile/pointer surface reachable by any transaction, satisfying the "unauthorized transfer via precompile or pointer" impact criterion.

### Likelihood Explanation
High likelihood: the vulnerable functions are `public`/`override` entry points on a standard ERC721 interface that any EVM account or contract can call directly with attacker-chosen arguments (`from`, `to`, `tokenId`, `operator`). No special privilege, governance action, or validator collusion is required — a single crafted transaction is sufficient.

### Recommendation
Add the standard ERC721 authorization check before dispatching any state-changing CW721 message:
- In `transferFrom`, require `msg.sender == from || isApprovedForAll(from, msg.sender) || getApproved(tokenId) == msg.sender` (i.e., restore `_isApprovedOrOwner` semantics) before calling `ownerOf`/`_execute`.
- In `approve`, require `msg.sender == ownerOf(tokenId) || isApprovedForAll(ownerOf(tokenId), msg.sender)`.
- In `setApprovalForAll`, ensure the CW721 `approve_all`/`revoke_all` message is executed with `msg.sender` as the CW721-side granter (via the wasmd precompile's caller mapping), not merely relayed as attacker-supplied parameters.
- Apply the same audit to `CW1155ERC1155Pointer.sol` and `CW20ERC20Pointer.sol` for equivalent missing-authorization patterns in their transfer/approval overrides.

### Proof of Concept
1. Owner O registers/points a CW721 collection via the pointer precompile (`AddCW721Pointer`), creating `CW721ERC721Pointer` instance `P` for CW721 contract `C`. O owns `tokenId = 1` in `C`.
2. Attacker A (unrelated EOA, no approval) sends an EVM transaction calling:
   `P.transferFrom(O, A, 1)`
3. Inside `transferFrom`, `require(from == ownerOf(tokenId), ...)` passes because `from == O` matches the real owner — no check is made that `msg.sender == O` or that A is approved.
4. `_execute` delegatecalls the wasmd precompile to submit `{"transfer_nft":{"recipient": A_seiAddr, "token_id": "1"}}` against `C`.
5. Token `1` is transferred from O to A without O's consent, purely via the pointer contract's public `transferFrom`.
