## Title
Automatic remote-URL rewrite trusts unauthenticated GitHub API `clone_url` field, enabling silent push/fetch redirection - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently overwrites the local `origin` remote's URL with whatever `clone_url` is currently returned by the GitHub API for the tracked repository, based only on a same-owner/name heuristic rather than any user confirmation. [1](#0-0) 

### Finding Description
The broken invariant mirrors the Aave issue: a security-relevant piece of state (there: the collateral flag; here: the trusted push/fetch destination `origin` URL) is overwritten automatically whenever certain loosely-checked conditions are met, without the operation that depends on that state (borrowing / pushing code) re-validating it.

`updateRemoteUrl` compares:
- `protocolsMatch` — only checks that the URL scheme string is the same (`https:` vs `https:`), not host or owner,
- `remoteUrlUnchanged` — checks that the *current* remote still structurally matches the *previously stored* `gitHubRepository.cloneURL` (owner+name+host, case-insensitively) via `urlMatchesRemote`,
- `urlsMatch` (negated) — the new API URL differs from the current remote.

If all three hold, it calls `gitStore.setRemoteURL(...)` to rewrite `origin` to `apiRepo.clone_url` with **no user prompt**. [2](#0-1) 

The `apiRepo` object comes directly from a GitHub API response fetched during repository refresh (`withRefreshedGitHubRepository`) — this is exactly the "attacker controls a GitHub API object" primitive named in the report's Valid Impact scope. A GitHub Enterprise instance, an org repository that gets transferred/renamed by a compromised account, or a MITM'd/malicious API endpoint can cause the API to return a `clone_url` for the same repository ID/owner/name shape that actually points to an attacker-controlled remote (e.g., a repo with a spoofed but structurally-matching owner/name on a different host is rejected by the hostname check, but a same-host repo transferred to attacker's namespace, or a same-name repo used to overwrite the association, is not).

`urlMatchesRemote` only checks parsed `hostname`, `owner`, and `name` case-insensitively — it does not verify any cryptographic identity or repository ID, so once the DB's cached `gitHubRepository.cloneURL` and the current git remote agree, the function will happily follow the API's reported "new" location. [3](#0-2) 

Existing guards do not stop this path: `protocolsMatch` is a scheme-string comparison unrelated to trust, and `remoteUrlUnchanged`/`urlsMatch` only enforce that the *current* remote is what Desktop last remembered — they provide no defense against the API itself returning a different destination for the same tracked repository record.

### Impact Explanation
If exploited, `origin` is silently repointed to an attacker-controlled remote. Subsequent `git push` operations issued by Desktop (and shown to the user as "push to origin") would ship the user's future commits — and potentially their credentials/tokens embedded in an HTTPS remote URL if the user's git credential helper is not scoped per-host — to the attacker's server. This matches the "silent corruption of what the user commits or pushes" and "credential exfiltration" categories in the Valid Impact list.

### Likelihood Explanation
This requires the attacker to control the GitHub API's `clone_url` response for a repository record Desktop is already tracking, which is a plausible attacker position for compromised GitHub Enterprise servers, transferred/renamed repositories under attacker control, or a network-level MITM against an endpoint without pinned certificate validation — all explicitly allowed per the task's Valid Impact section (no local access, no leaked credentials, no admin rights required). It does not require any unnatural user interaction; the rewrite happens automatically as part of routine repository refresh.

### Recommendation
Before rewriting an existing remote URL based on API data, Desktop should prompt the user for confirmation (similar to the existing "convert to fork" / upstream-remote confirmation flows already present in the codebase, e.g. `_updateExistingUpstreamRemote`), and/or verify the repository's numeric API ID against the stored `dbID` in addition to owner/name/host before trusting a `clone_url` change. [4](#0-3) 

### Proof of Concept
1. User adds/clones a GitHub repository in Desktop; `gitHubRepository.cloneURL` and local `origin` remote both point to `https://github.com/victim-org/repo`.
2. Attacker (through a compromised GHE deployment, a repository transfer, or a MITM'd API response) causes a subsequent `getRepository` API call for that same tracked record to return `clone_url: https://github.com/attacker-org/repo` while owner/name string shape still parses identically enough to pass `urlMatchesRemote`/protocol checks (e.g., the record's cached `cloneURL` was itself already updated once from an earlier legitimate rename, then hijacked).
3. On the next repository refresh (background poll, fetch, or checkout), `updateRemoteUrl` is invoked and silently calls `gitStore.setRemoteURL('origin', 'https://github.com/attacker-org/repo')`. [5](#0-4) 
4. The user, unaware of the change, performs a normal push via Desktop's UI; the commits (and any embedded credentials) go to the attacker's repository instead of `victim-org/repo`.

Note: I was unable to fully trace every call site of `withRefreshedGitHubRepository`/`updateRemoteUrl` due to index size limits on `app-store.ts` (only match counts were retrievable, not full call context) — a Devin session with full repository access would be needed to confirm the exact triggering conditions (e.g., whether periodic background refresh alone can trigger this without any user action) and to validate the practical exploitability window in detail.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
