### Title
ProtoJSON field-name duplicate-key enforcement is representation-unaware, allowing silent field overwrite via alternate name spellings - ([File: python/google/protobuf/internal/json_format.py])

### Summary
The FreeIPA/389-ds bug enforces uniqueness on a Kerberos principal name attribute using an equality check that fails to account for equivalent representations of the same principal (canonicalization gap), letting an attacker with LDAP write access create a "different" name that is actually the same principal, bypassing the uniqueness guarantee and silently overwriting/impersonating a privileged identity. The transferable invariant is: *a value that is logically identical to an existing bound value can be spelled differently at the wire/text level, and if the uniqueness/duplication check only compares raw spellings and not canonical identity, the check is bypassed.*

The Python pure implementation of ProtoJSON parsing (`json_format.Parse`) has the direct analog: it enforces a "no duplicate JSON key" rule intended to reject payloads that set the same field twice, but the duplicate check compares the *raw JSON key string*, not the canonical field it resolves to. Because a single protobuf field can be addressed by multiple JSON spellings (`lowerCamelCase` name, `original_name`, and custom `json_name`), an attacker can supply the "same" field twice under two different spellings and have the duplicate-key check silently pass, with the second occurrence overwriting the first ("last write wins") instead of being rejected.

### Finding Description
`json_format.Parse`'s per-message parsing resolves a JSON object key to a `FieldDescriptor` using `FindFieldByCamelcaseName`, then `FindFieldByName`, then a manual scan of `field->json_name()` (see the field-resolution logic pattern also mirrored in `src/google/protobuf/json/internal/descriptor_traits.h:169-187`, `FieldByName`). The "reject duplicate keys" logic tracks *keys already seen in the JSON object*, not *fields already seen in the message* — so it is keyed on the untranslated string from the wire, exactly analogous to 389-ds comparing raw principal-name attribute values instead of the canonicalized principal identity.

This is a documented, acknowledged oversight in this exact checkout: [1](#0-0) 

```

    # implementation, but would be a breaking change to fix. The duplicate field
    # checker intends reject inputs with duplicate key names, but it only
    # catches keys that are exact matches and not alternate spellings that
    # correspond to the same field.
    parsed_message = json_format_proto3_pb2.TestMessage()
    json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
    self.assertEqual(parsed_message.int32_value, 2)

def testDuplicateFieldAlternateNamesMap(self):

    parsed_message = json_format_proto3_pb2.TestMap()

        '{"int32Map": {"1": 2}, "int32_map": {"3": 4}}', parsed_message
```

Contrast this with the intended, working case where the duplicate check does succeed because the spelling is identical: [2](#0-1)

```
        'Failed to load JSON: duplicate key int32Value.',
```

### Impact Explanation
For a consuming application that treats "no duplicate keys" as a security-relevant validation gate for untrusted ProtoJSON input (e.g. rejecting payloads that attempt to set a privileged/sensitive field twice, or relying on "first/only occurrence wins" semantics to prevent a client from smuggling a second, attacker-controlled value for a field after some validation step has already inspected the first occurrence), an attacker sending a single JSON payload can supply the sensitive field under its canonical name and then again under an alternate valid spelling (`snake_case`, `camelCase`, or a custom `json_name`). The duplicate-key rejection is bypassed, and "last one wins" quietly overwrites the previously validated value — a canonicalization/identity-comparison failure directly analogous to the FreeIPA finding, where a realm-unaware/representation-unaware uniqueness check let an equivalent-but-differently-spelled principal name slip past enforcement. Impact is confined to logic that depends on the "reject duplicate field" invariant (e.g., double-submission or optimistic validate-then-set patterns); it does not itself grant memory corruption or RCE.

### Likelihood Explanation
Trivial to trigger: any client can send a bounded, well-formed JSON object through the public `json_format.Parse` API (and the same field-resolution ambiguity exists in the shared JSON parsing internals used elsewhere), with two keys that are different strings but resolve to the same field via the descriptor's name/camelCase-name/json_name lookup order. No privileges, malicious schema, or internal API access are required — this is squarely within the "ordinary client, supported public parse API, trusted schema" threat model. The bug is explicitly acknowledged as a known, reproduced, non-fixed oversight in the test suite and conformance failure lists.

### Recommendation
Change the duplicate-detection state to be keyed on the resolved `FieldDescriptor` (or its canonical full name / field number) rather than on the raw JSON key string, for both scalar and map fields, across all ProtoJSON parser implementations (`python/google/protobuf/internal/json_format.py`, `src/google/protobuf/json/internal/parser.cc`, and language-specific JSON parsers). This mirrors how the wire/binary format enforces "last field wins" only per field number, and would make the duplicate check consistent with the descriptor's canonical identity, closing the same class of "different spelling, same identity" bypass documented for 389-ds/FreeIPA.

### Proof of Concept
Using the pure-Python ProtoJSON parser in this checkout:
```python
from google.protobuf import json_format
import json_format_proto3_pb2 as pb2  # generated test proto with int32_value field

msg = pb2.TestMessage()
# "int32_value" (original) and "int32Value" (default camelCase) both resolve
# to the same FieldDescriptor, but are different JSON key strings, so the
# duplicate-key checker (keyed on raw string) does not flag this as a repeat.
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2  # second, alternately-spelled occurrence silently won
```

```text
  static absl::optional<Field> FieldByName(const Desc& d,
                                           absl::string_view name) {
    if (const auto* field = d.FindFieldByCamelcaseName(name)) {
      return field;
    }

    if (const auto* field = d.FindFieldByName(name)) {
      return field;
    }

    for (int i = 0; i < d.field_count(); ++i) {
      const auto* field = d.field(i);
      if (field->json_name() == name) {
        return field;
      }
    }

    return absl::nullopt;
  }
```
