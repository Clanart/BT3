## Analysis

The Tapioca finding is fundamentally: **an index/quantity computed against snapshot A (share ratio at deposit time) is recorded and later reused against snapshot B (a different, changed exchange rate), producing silent value drift with no re-validation.** The Desktop analog is the same structural bug applied to diff line indices instead of share ratios: a `DiffSelection`'s absolute line indices are computed against one diff snapshot but applied — without re-validation of content, only line count — against a second, independently re-fetched diff snapshot when staging a partial commit. ### Title
Silent mis-staging of unrelated file lines due to stale `DiffSelection` line-index reuse against a freshly re-fetched diff - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
`WorkingDirectoryFileChange.selection` stores *absolute line indices* computed against a specific diff object the UI rendered. When the user commits a partial selection, `applyPatchToIndex` independently re-runs `git diff` via `getWorkingDirectoryDiff` to build the patch, and then `formatPatch`/`formatPatchToDiscardChanges` apply the old selection's indices to this brand-new hunk layout using only `isSelected(absoluteIndex)`. If the working tree changes between the moment the selection indices were computed (diff render) and the moment `applyPatchToIndex` re-diffs the file (commit time), the index numbering can shift while `selectableLines`/count-based validation still appears "valid," causing the wrong lines to be silently included in, or excluded from, the resulting commit.

### Finding Description
`DiffSelection` tracks selected/deselected state keyed purely by an **absolute line index** (`hunk.unifiedDiffStart + lineIndex`), not by line content or hash. This index space is only revalidated at the `selectableLines` granularity — i.e., Desktop checks whether a given index is *still an includeable line* after a diff refresh, but not whether that index still corresponds to the *same content* as when the user selected it: [4](#0-3) 

This comment in the code itself acknowledges the invariant is not truly preserved: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines such that any previously selected line which now no longer exists or has been turned into a context line isn't still selected."* This means: if a line at index N remains an "includeable" (Add/Delete) line after the underlying file changes — e.g., another process, a background `git` hook, an editor autosave, or a concurrent Desktop operation modifies the file so hunks shift but line *counts* at that offset stay compatible — the selection is preserved and reused unchanged, even though index N now refers to different textual content.

At commit time, `stageFiles` → `applyPatchToIndex` re-fetches the diff independently of whatever diff object the renderer last displayed: [5](#0-4) 

The freshly fetched `diff` (from `getWorkingDirectoryDiff`) is then passed into `formatPatch(file, diff)`, which walks the *new* hunk/line layout and, per line, tests `file.selection.isSelected(absoluteIndex)` — an index that was computed against the *old* diff, not the new one: [6](#0-5) 

There is no check anywhere in `applyPatchToIndex`/`formatPatch` that the `diff` passed in is the same diff object (or even structurally equivalent) to the one the selection was built for. The only defense (`selectableLines`) is refreshed lazily by the renderer/app-store when a diff reload happens for the *currently viewed* file, but:
1. It only prunes indices that stopped being includeable lines — it does not detect an index that is still includeable but now maps to unrelated content (e.g., after a hunk shift caused by edits above the hunk, insertion/deletion of blank lines, or Add/Delete lines swapping order in a similar-sized change).
2. It is driven by a UI-side effect (`selectedFileIdBeforeLoad` comparison) that only runs for the file currently selected in the Changes list — a commit invoked immediately (e.g., via keyboard shortcut, "Commit and push", or scripted automation) races against this reconciliation.
3. `applyPatchToIndex` re-diffs the file *again*, independently, at commit time — a third snapshot that the reconciliation step in `app-store.ts` never sees or validates against.

### Impact Explanation
This causes **silent corruption of what the user commits/pushes** — a directly in-scope impact category. Concretely, a user reviews a diff, deselects a sensitive/unwanted hunk (e.g., a debug line, secret, or unrelated change), and commits. If the working tree changes between diff render and the `git commit` staging step (attacker-influenced via a malicious pre-commit/post-checkout hook writing to the file, a file-watcher-triggered formatter, LFS smudge/clean filter, or a symlinked file target modified externally — all of which are plausible in a "cloned/fetched repository controls its own git hooks/filters" threat model), Desktop can silently stage content the user never selected, or omit content the user did select, without any error or warning. The resulting commit's content diverges from what was shown/reviewed in the UI, and the user has no indication that mis-staging occurred, since `applyPatchToIndex` and `formatPatch` never fail — `git apply --cached` succeeds as long as the patch is structurally valid.

### Likelihood Explanation
Moderate. It requires a content-changing event between the rendering of the diff selection and the commit's internal re-diff, most plausibly delivered via a repository-controlled hook (`post-checkout`, filter/clean/smudge, `pre-commit` that rewrites files before Desktop's second diff pass reads them) — placing control in the hands of a cloned/fetched repository's author, consistent with the accepted attacker model. Desktop already explicitly documents (in the `app-store.ts` comment) that it is aware selection state can go stale and only partially mitigates it, indicating the underlying race is a known, unresolved gap rather than a purely theoretical one.

### Recommendation
Instead of keying `DiffSelection` purely by absolute index, bind the diff object used to build the patch (in `applyPatchToIndex`) to the exact diff snapshot the selection was created against — reject/re-validate (re-diff and re-map selection by content, e.g. via a content hash or unified stable line identity) rather than reusing raw indices if the newly fetched diff for staging differs structurally (hunk boundaries, line counts, or content) from the diff the selection was computed for. At minimum, `stageFiles`/`applyPatchToIndex` should re-fetch the diff *before* the user finalizes the commit and diff it against the diff last shown to the user, aborting or warning if they diverge, rather than silently proceeding with `git apply --cached`.

### Proof of Concept
1. Open a repository in Desktop with a tracked file `foo.txt` containing several lines, with a `pre-commit` hook (or a smudge/filter or another background process) that appends/removes a line near the top of the file when triggered.
2. Modify `foo.txt`, view the diff in Desktop, and deselect one specific "Add" line (call it line index N) that the user does not want to commit.
3. Trigger a scenario where the file is externally rewritten (by the hook, filter, or a race with another background write) between diff render and commit — shifting line offsets by ± the number of lines the hook inserts/removes, but keeping line count and includeable-line status compatible at index N.
4. Click "Commit" — `stageFiles` → `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` and calls `formatPatch(file, diff)`, which evaluates `file.selection.isSelected(N)` against the *new* hunk layout at `app/src/lib/patch-formatter.ts:144-157`.
5. Because index N is reused verbatim, the line actually staged/excluded is not the line the user reviewed and (de)selected — the created commit's content silently diverges from the reviewed diff, with no error surfaced to the user.
