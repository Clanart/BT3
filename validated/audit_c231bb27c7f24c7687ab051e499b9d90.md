Recursive Clone Explicitly Disables Git's Nested-Repo/Submodule Clone Protection - ([File: app/src/lib/git/clone.ts])

### Summary
Git added `GIT_CLONE_PROTECTION_ACTIVE` as part of the fix for CVE-2024-32002 (a `git clone --recursive` remote code execution vulnerability caused by malicious submodules whose case-folded/similarly-named paths collide with `.git`, allowing an attacker-controlled repository to write files into the superproject's `.git` directory — including hooks — during clone, on case-insensitive filesystems or via symlink tricks). GitHub Desktop's `clone` function unconditionally sets this variable to `'false'` for every clone it performs, which mirrors the "pause the safety check while the risky operation still runs" pattern from the report: the guard designed specifically to stop this class of attack is turned off precisely during the `--recursive` clone that is supposed to be protected by it.

### Finding Description
`clone()` in [1](#0-0)  builds the environment for the `git clone --recursive` invocation and explicitly injects `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into `env` before spawning `git`: [2](#0-1) 

This env var is the flag upstream Git uses to track/enforce the anti-recursive-clone-hijack protections added after CVE-2024-32002/CVE-2024-32004/CVE-2024-32465 (the "clone confusion" hardening for symlinked `.git` dirs and case-colliding submodule paths encountered while recursively cloning submodules). By force-setting it to `false` on every invocation, GitHub Desktop disables that guard for the entire clone (including all nested submodule clones triggered by `--recursive`), rather than leaving it in its default (protective) state.

The only other safeguard present, `isClonePathSensitive()` [3](#0-2) , checks the *top-level destination path* the user chose. It does nothing to constrain where files land *inside* the cloned tree once Git starts materializing a malicious submodule with a colliding/symlinked path — that is exactly the class of write-outside-worktree Git's own protection exists to stop, and this local check cannot substitute for it.

### Impact Explanation
An attacker who controls a repository (directly, or a repository containing a malicious submodule reference) that a Desktop user clones with `--recursive` can attempt to exploit the case-collision / symlinked-`.git` submodule path technique that CVE-2024-32002 covers. With `GIT_CLONE_PROTECTION_ACTIVE=false`, Desktop's embedded Git no longer performs the check meant to reject such colliding submodule paths, re-opening a path to writing arbitrary files inside `.git` (e.g., `hooks/`) of the superproject during the clone, which can lead to code execution the next time a hook fires (e.g., on the very next `git` operation Desktop performs, such as `checkout`/`commit`) or corruption of the repository outside the intended worktree — matching the "attacker controls a cloned repository → code execution / file write outside repo" impact class.

### Likelihood Explanation
Every clone performed through this code path (any user-initiated "Clone repository" action, "Open in Desktop" from a URL, or opening a PR from a fork that triggers a clone) always passes through `clone()` with `--recursive` and the disabled protection — there is no conditional or opt-in; it applies unconditionally to all repositories, including ones from URLs a user was sent (deep links) or public repos with attacker-controlled submodules. No unusual local access, admin rights, or social engineering beyond "clone this repository" is required, which is within the normal, expected Desktop workflow.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override so Git's built-in clone protections remain active for `git clone --recursive`. If protection is disabled to work around a compatibility issue with legitimate submodule setups, that workaround should be scoped and justified explicitly, and Desktop should instead rely on/ship a Git version where this protection is correct rather than disabling it wholesale.

### Proof of Concept
1. Attacker publishes a repository containing a submodule entry whose path, when case-folded (e.g., on macOS/Windows) or combined with symlink tricks, collides with `.git` (per the technique described in CVE-2024-32002).
2. Victim clones the repository in GitHub Desktop (`Clone repository`, or via `x-github-client://openRepo` deep link, or opening a PR from a fork), invoking `clone()` in [4](#0-3) .
3. Because `env.GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, the embedded Git does not apply the check that would normally reject the colliding submodule path, allowing the malicious submodule content to be written into the superproject's `.git` directory (e.g., overwriting/adding a hook).
4. On a subsequent Git operation performed by Desktop (checkout, commit, etc.) the planted hook executes in the context of the victim's Desktop process/environment.

Note: I could not execute Git locally to confirm the exact current upstream semantics/version-gating of `GIT_CLONE_PROTECTION_ACTIVE` (the repository history only contains a single "Initial commit," so no code history/PR discussion is available to confirm the original rationale for this override), so I recommend a Devin/engineer session with terminal access to reproduce this against the bundled Git version and confirm exploitability end-to-end.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
