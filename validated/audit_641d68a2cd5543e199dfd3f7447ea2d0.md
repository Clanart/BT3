Based on my investigation, I found a plausible structural analog in GitHub Desktop's "Open Repository from URL" deep-link flow, though I could not fully verify whether a user-facing confirmation dialog intercepts this path — that would need to be confirmed in a running Desktop session.

### Title
Deep link `x-github-client://openRepo/...?pr=N` silently adds an attacker-controlled fork remote and checks out its branch without a distinct trust prompt - (File: app/src/ui/dispatcher/dispatcher.ts)

### Summary
The Sherlock finding is a broken-invariant bug: the renewal-check logic validates *identity* fields (time, token, lending contract) but omits validating the *value* that actually matters (protection amount), letting an attacker exploit the gap between what was checked and what should have been checked. The closest structural analog in GitHub Desktop is the `openrepo` deep-link handler, which validates superficial fields of the incoming URL (hostname, PR-number format, branch-name format) but does not validate the *trust-relevant* value — the actual fork remote URL returned by the GitHub API for the PR's head repository — before adding it as a new git remote and fetching/checking it out.

### Finding Description
`parseAppURL` in [1](#0-0)  validates only that `pr` is numeric and that `branch` matches `^pr/\d+$`; the `url` (target repository) itself is passed through unchecked as `parsedPath`.

This action flows into `dispatcher.dispatchURLAction` → `openRepositoryFromUrl` → `openPullRequestFromUrl`, shown at [2](#0-1) . Here, `pullRequest` is fetched from the API using attacker-supplied `url`/`pr` values, and then `pullRequest.head.repo.clone_url` and `pullRequest.head.ref` (both fields the PR *author* controls when opening a pull request from a fork) are passed straight into `_checkoutPullRequest`.

`_findPullRequestBranch` in [3](#0-2)  only checks whether an existing remote's URL matches `headCloneUrl` via `urlMatchesRemote`; if none matches, it unconditionally calls `addRemote(repository, forkRemoteName, headCloneUrl)` — adding a brand-new git remote pointing at the PR-author-controlled fork — followed by a fetch and automatic branch creation/checkout at lines 8684-8717. No step in this path re-validates that the fork clone URL is one the user has consented to trust versus just an artifact of whichever PR number the deep link happened to reference.

### Impact Explanation
Clicking a single crafted `x-github-client://openRepo/<owner>/<repo>?pr=<N>` link (which can be embedded on any web page, since Desktop registers this as its default protocol handler in [4](#0-3) ) causes Desktop to silently: add a new git remote pointing to an attacker-controlled fork, fetch it, and check out its branch into the user's local working copy — without any dialog distinct from ordinary navigation confirming "you are about to add and trust this new remote." This corrupts the state of what the user is about to build/commit/push from, and a subsequently-added fork remote persists in `.git/config` for future fetches/pulls.

### Likelihood Explanation
Exploitation requires the attacker to have (or create) a public PR (even against an unrelated/low-traffic repo) so the API lookup succeeds, and lure the victim into clicking a link — a comparatively low bar since Desktop repository/PR deep links are a documented, expected user interaction pattern (see [5](#0-4) ) that users are conditioned to click without suspicion.

### Recommendation
Before silently adding a new remote and checking out a fork branch reached via `openrepo` deep links, surface an explicit confirmation UI naming the fork owner/URL that is about to be added, distinct from the "Clone/Open" confirmation for the primary `url` parameter, mirroring the missing-amount-validation fix pattern from the Carapace report (validate the actual value being trusted, not just superficial identity fields).

### Proof of Concept
1. Attacker opens a public pull request from their own fork against any existing public repository, with a distinctive branch.
2. Attacker crafts `x-github-client://openRepo/<owner>/<repo>?pr=<N>` and embeds it in a webpage/email.
3. Victim (with Desktop installed and registered as protocol handler) clicks the link.
4. `parseAppURL` → `dispatchURLAction` → `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` executes `addRemote(repository, forkRemoteName, headCloneUrl)` and checks out the attacker's branch, all without a dedicated "trust this fork" prompt (per the traced code above).

I could not confirm from static code alone whether an additional runtime confirmation dialog exists elsewhere in the popup/dispatcher flow that gates this specific checkout step; verifying the actual UI behavior would require running Desktop and exercising this deep link.

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }

* Start with our prefix
* The PR associated with the remote is closed
