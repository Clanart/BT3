### Title
Global, session-wide `Authorization` header injection lets any attacker-controlled GitHub asset URL harvest the signed-in user's API token via a confused-deputy request - (File: `app/src/main-process/authenticated-image-filter.ts`)

### Summary
`installAuthenticatedImageFilter` installs a single, application-global `webRequest.onBeforeSendHeaders` listener that decides whether to attach the signed-in user's real API token to *any* outgoing request in the app, based only on the request's `origin` and a loosely-matched `pathname` regex. Nothing ties this decision to the specific repository, pull request, or webview context that legitimately needs the credential. This is the same class of bug as the PRBProxy report: an access-control-relevant value (the account token, keyed only by `origin`) is kept in a single shared, unnamespaced map (`originTokens`) that is consulted for *every* request in the process, so any untrusted content that can cause the renderer to fetch a URL matching the pattern gets the privileged credential attached automatically.

### Finding Description
`originTokens` is a `Map<origin, token>` populated from the list of signed-in accounts and consulted for every network request that flows through the shared `OrderedWebRequest` pipeline: [1](#0-0) 

The gating logic is intentionally broad:
- `isGitHubRepoAssetPath` matches **any** path of the shape `/<anything>/<anything>/assets/<anything>/<anything>` — it does not verify that `<owner>/<repo>` corresponds to the repository currently open, or to any repository the requesting webview/window is scoped to. [2](#0-1) 
- The token lookup key is only the request's `origin` (`github.com` / the enterprise host), not the window, webContents, partition, or repository context that triggered the request. [3](#0-2) 

GitHub Desktop routinely renders attacker-influenced content from GitHub API objects (issue/PR bodies, comments, commit statuses, etc.) that can contain arbitrary `<img>` tags pointing at `https://github.com/{owner}/{repo}/assets/{id}/{guid}` or `/user-attachments/assets/{guid}` — these are exactly the "GitHub-hosted user-attachment" URLs GitHub itself generates when any user (including unprivileged/anonymous commenters on public repos) pastes an image into an issue or PR. Because the filter only checks origin + path shape, it will attach the *victim's own token* to a request for **any** `owner/repo` asset GUID the attacker chooses to embed — including asset URLs belonging to private repositories the attacker does not have access to but suspects the victim does.

This is structurally identical to the PRBProxy issue: a piece of state that gates a privileged action (`permissions`/`plugins` there, the bearer token here) is stored in one place, addressed by an attacker-influenceable key (`target` address there, request `origin`/`pathname` here), and is not scoped to the entity that should own it (the proxy owner there, the specific repository/webview context here). Any content the "target" renders can piggyback on that shared state.

### Impact Explanation
An attacker who can get a victim to view a GitHub object containing an `<img>` tag (a PR description, issue comment, or commit message on any repository the attacker can write to, including a fully attacker-owned public repo the victim is merely browsing) can:
- Trigger the victim's GitHub Desktop instance to send a request to `https://github.com/<target-owner>/<target-repo>/assets/<id>/<guid>` **with the victim's real OAuth token attached**, without any consent or awareness from the victim.
- Use the binary success/failure (image renders vs. broken image) as an oracle to confirm whether the victim's account has access to a specific private asset/repository they should not be able to probe from an untrusted context — a confused-deputy token-misuse / unauthorized information-disclosure primitive.
- Because the check is global to the process rather than scoped to the legitimate consumer of the credential (the actual GitHub API client), this effectively acts as an unintentional "token oracle" reachable from any renderer surface that loads images from attacker-influenced markdown.

This does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim opens/browses a GitHub object (issue, PR, comment) that an unprivileged attacker can create.

### Likelihood Explanation
Likelihood is moderate-to-high in Desktop's normal operation: rendering of PR/issue/commit content from remote/API sources is core, everyday functionality, and GitHub itself generates `.../assets/...` and `/user-attachments/assets/...` URLs for any pasted image, including from public repos or comments made by unauthenticated/low-privilege contributors. No exotic user action is required beyond viewing content that Desktop already renders as part of its normal PR/issue workflow.

### Recommendation
- Scope the Authorization-attachment decision to the specific repository/context that is legitimately allowed to use the credential (e.g., only attach the token when the `owner/repo` segment of the path matches a repository the current webview/window is actually displaying), rather than matching on origin + a generic path shape across the whole app.
- Bind `originTokens`/the authorization decision to the requesting `webContents`/partition (per-window state) instead of a single shared, ambient map, mirroring the PRBProxy fix of moving shared, unnamespaced permission-like state out of a generic accessible location into a properly scoped owner-keyed store.
- Consider validating that the asset GUID belongs to a resource the current session has already legitimately fetched/authorized (e.g., via a signed URL or a server-issued short-lived token) rather than re-attaching the long-lived account token to any matching path.

### Proof of Concept
1. As an unprivileged attacker, open (or comment on) any public GitHub repository/issue/PR and paste an image so GitHub generates a `user-attachments`/asset URL, or manually craft `<img src="https://github.com/<victim-accessible-private-owner>/<repo>/assets/<id>/<guid>">` inside a PR/issue body/comment.
2. Have the victim (signed in to Desktop with an account that may have access to the target private repo) open that PR/issue/commit in GitHub Desktop, which renders the markdown/HTML including the `<img>` tag.
3. The renderer issues a `GET` request for that image URL; `installAuthenticatedImageFilter`'s `onBeforeSendHeaders` listener matches on `origin` (`https://github.com`) and the generic `isGitHubRepoAssetPath` regex, and attaches `Authorization: token <victim-token>` regardless of whether the currently open repository has anything to do with `<victim-accessible-private-owner>/<repo>`. [4](#0-3) 
4. The attacker observes (via the rendered image loading successfully vs. showing broken-image state) whether the victim's account can access that private asset/repo — an access-control probe performed with the victim's own token, driven entirely by attacker-controlled content.

```typescript
function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}
```

```typescript
export function installAuthenticatedImageFilter(
  orderedWebRequest: OrderedWebRequest
) {
  let originTokens = new Map<string, string>()

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { origin, pathname } = new URL(details.url)
    const token = originTokens.get(origin)

    if (
      token &&
      (isEnterpriseAvatarPath(pathname) || isGitHubRepoAssetPath(pathname))
    ) {
      return {
        requestHeaders: {
          ...details.requestHeaders,
          Authorization: `token ${token}`,
        },
      }
    }

    return {}
  })
```
