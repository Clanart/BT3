## Finding

### Title
`update_token` invalidates `ContractToAsset` for pending transfers, permanently locking escrowed funds on timeout - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
The Union Finance report describes admin functions (`removeAdapter`/`removeToken`) that mutate protocol state without checking whether funds are still outstanding against that state, leaving user funds permanently stranded. The Hyperbridge `hyper-fungible-token` pallet has the same broken invariant in `update_token`: it can rewrite or delete the `(StateMachine, contract) -> AssetId` reverse mapping (`ContractToAsset`) for a chain/token pair while ISMP `PostRequest`s dispatched under the *old* mapping are still in flight. When those requests eventually time out, `on_timeout` cannot resolve the asset and errors out, so the escrow release never happens and the user's locked funds are never refunded.

### Finding Description
`send()` escrows/burns the sender's funds into `pallet_account()` and dispatches a `PostRequest` whose `to` field is whatever `TokenContracts::<T>::get(dest, asset_id)` currently resolves to: [1](#0-0) 

If that cross-chain request later times out, `on_timeout` must reverse-look-up the asset from the `(dest, to)` pair embedded in the *original request*: [2](#0-1) 

`update_token` is the only path that mutates `ContractToAsset`. For `add_chains`, it deletes the *old* reverse mapping for the chain before writing a new contract address; for `remove_chains`, it deletes both `ContractToAsset` and `TokenContracts` entirely — with no check for any request still in flight to that `(chain, contract)`: [3](#0-2) 

Sequence:
1. Alice calls `send()` to `dest = Evm(X)` while `TokenContracts[Evm(X), asset] = old_contract`. Her funds are moved into `pallet_account()` and a `PostRequest{ dest: Evm(X), to: old_contract, timeout_timestamp, ... }` is dispatched.
2. Before that request resolves, governance calls `update_token` to re-point `Evm(X)` at a new contract (`add_chains`) or to remove `Evm(X)` support (`remove_chains`). Either way, `ContractToAsset::<T>::remove(Evm(X), old_contract)` executes.
3. Alice's request later times out. `on_timeout` executes `ContractToAsset::<T>::get(dest, &to)` with `to = old_contract`, which now returns `None`, so it returns `HftError::UnknownContractOnTimeout` and the extrinsic/callback fails.
4. There is no other pallet entry point that releases funds from `pallet_account()` back to a sender. Alice's escrowed/burned funds are permanently stuck — exactly the "removed adapter/token can still hold funds" pattern from the seed report, just triggered by rewriting the reverse-lookup table instead of removing an adapter list entry.

The pallet performs no check, before mutating `TokenContracts`/`ContractToAsset`, for whether any dispatched-but-unresolved request still references the mapping being changed.

### Impact Explanation
Any user funds in transit at the moment of a routine token/contract migration (a normal, expected operational action — the pallet's whole reason for having `update_token`) can become irrecoverable. This is a direct loss/lock of user funds with no remediation path in the pallet, matching the "Bridged assets ... must move exactly once and only to the rightful beneficiary" pivot — here the beneficiary receives nothing and the funds are frozen in `pallet_account()` indefinitely.

### Likelihood Explanation
No attacker action is required — this is a routine, expected admin operation (contract re-pointing or chain deprecation, both first-class supported inputs) that will affect any user transfer already in flight at that moment. Given production bridges regularly rotate/redeploy peer contracts, this is a realistic and repeatable failure mode rather than an edge case.

### Recommendation
Before removing or overwriting a `TokenContracts`/`ContractToAsset` entry in `update_token`, either:
- Retain the old `ContractToAsset` entry (don't delete it) so `on_timeout`/refunds for previously-dispatched requests can still resolve, only removing it after some grace period safely past the maximum in-flight timeout, or
- Track outstanding dispatched requests per `(chain, contract)` and reject the update/removal while any are unresolved, or
- Add a governance-only "sweep"/manual refund entry point keyed by the stale mapping so operators can settle stranded escrow if migration must happen immediately.

### Proof of Concept
1. Register `asset_id` for `StateMachine::Evm(1)` with `token_contract = C_old`.
2. Call `HyperFungibleToken::send(alice, { asset_id, destination: Evm(1), amount, timeout: T, ... })`. This escrows `amount` into `pallet_account()` and dispatches `PostRequest{ dest: Evm(1), to: C_old, timeout_timestamp: T, ... }`.
3. Before the request resolves, call `update_token` with `add_chains = { Evm(1) -> ChainConfig{ token_contract: C_new, .. } }` (or `remove_chains = [Evm(1)]`). This executes `ContractToAsset::<T>::remove(Evm(1), C_old)`.
4. Simulate/deliver the timeout for the original request: `Pallet::<T>::on_timeout(Request::Post(original_post))`.
5. Observe the call returns `Err(HftError::UnknownContractOnTimeout)` (see `ContractToAsset::<T>::get(dest, &to).ok_or(HftError::UnknownContractOnTimeout)?` in `on_timeout`), and no funds are ever released from `pallet_account()` back to Alice — her `amount` is permanently stuck. 	fn on_timeout(&self, request: Request) -> Result<Weight, anyhow::Error> {
		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
				}
				let beneficiary: T::AccountId = sender_bytes.into();

				// Look up the asset from the destination contract address
				let local_asset_id = ContractToAsset::<T>::get(dest, &to)
					.ok_or(HftError::UnknownContractOnTimeout)?;
