### Title
Attacker-controlled `WWW-Authenticate` realm triggers unverified GitHub Enterprise sign-in flow to arbitrary host - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
The reported Canto issue is a broken-invariant/DoS bug: removing an entry from a whitelist (`whitelistedUSDCVersions`) silently invalidates an assumption the rest of the contract relies on (that all backing tokens remain withdrawable), because the withdraw path trusts a per-token flag instead of verifying the actual backing state. The Desktop analog is `getEndpointKind()` in the Git credential-helper trampoline, which similarly substitutes a cheap, attacker-influenceable signal for the real trust check normally used to decide whether a remote is a legitimate GitHub host.

### Finding Description
When Git needs credentials for an HTTP(S) remote, it captures any `WWW-Authenticate` response headers from the server and forwards them to Desktop's credential helper as `wwwauth[...]` parameters. `getEndpointKind()` classifies the endpoint using these headers *before* falling back to the network-verified `isGitHubHost()` check: [1](#0-0) 

If the response contains `realm="GitHub"`, the endpoint is immediately classified as `'enterprise'` — a classification that is normally only reached after `isGitHubHost()` performs an authenticated meta-endpoint probe with certificate/redirect checks. Any HTTP server the user's Desktop talks to (a malicious git remote, a compromised/forked repo's configured URL, or a MITM/corporate proxy) fully controls this header and can force the `'enterprise'` classification without ever being a real GitHub Enterprise Server.

Once classified `'enterprise'`, `getCredential()` checks whether an account already exists for that endpoint; if not, it invokes the UI prompt: [2](#0-1) 

`promptForGitHubSignIn()` then wires Desktop's real "Sign in to GitHub Enterprise" flow directly to the attacker-supplied origin: [3](#0-2) 

This mirrors the Canto bug's broken invariant: a flag/signal (`whitelistedUSDCVersions[_usdcVersion]` / `realm="GitHub"`) is trusted as a proxy for a stronger guarantee (real USDC backing / verified GitHub host identity) that the rest of the system depends on, and an external actor can manipulate that signal to break the guarantee — here causing Desktop's legitimate GitHub Enterprise sign-in UI (and the credentials/OAuth token a user enters into it) to be pointed at an arbitrary attacker-controlled host, bypassing the `isGitHubHost()` verification path that exists specifically to prevent this.

### Impact Explanation
If a user adds/clones from or is redirected (via proxy or fork remote) to an attacker-controlled HTTP(S) endpoint that returns `WWW-Authenticate: realm="GitHub"`, Desktop will present its trusted-looking "Sign in to GitHub Enterprise" dialog pre-populated with that attacker origin. A user who completes sign-in (basic auth or OAuth) is sending their credentials/PAT/OAuth token to a host that was never verified to be a genuine GitHub Enterprise instance, resulting in credential/token exfiltration to the attacker.

### Likelihood Explanation
Requires the attacker to control an HTTP endpoint the victim's Git operations reach (a git server, a MITM/corporate proxy, or a repository whose remote the user is induced to add/fetch from) and for the credential helper to be invoked without an existing stored account for that endpoint — both realistic in the stated threat model ("attacker controls...a git remote/proxy response"). The header-based shortcut is reached before, and instead of, the network-verified `isGitHubHost()` check, so no certificate/redirect/response-body validation of the target's actual GitHub identity occurs.

### Recommendation
Do not trust the `wwwauth[...]` `realm="GitHub"` signal on its own to classify an endpoint as `'enterprise'`. Always corroborate it with the existing `isGitHubHost()` network verification (or an equivalent authenticated check) before routing the endpoint into the GitHub Enterprise sign-in flow, so that only endpoints passing real identity verification (as already implemented at [4](#0-3)  ) can trigger the trusted sign-in UI.

### Proof of Concept
1. Attacker stands up an HTTP(S) git server (or a MITM proxy) that responds to Git's credential probe with header `WWW-Authenticate: realm="GitHub"`.
2. Victim adds this server as a remote in GitHub Desktop and performs a `fetch`/`pull`/`push` (e.g., via a forked-repo remote flow or a corporate proxy substitution).
3. Git forwards the captured header to Desktop's credential helper as `wwwauth[...]=realm="GitHub"`.
4. `getEndpointKind()` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) matches the realm and returns `'enterprise'` without calling `isGitHubHost()`.
5. `getCredential()` finds no existing account for the endpoint and calls `ui.promptForGitHubSignIn(endpoint)`.
6. `promptForGitHubSignIn()` (`app/src/lib/trampoline/trampoline-ui-helper.ts:80-99`) calls `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with the attacker's origin, and shows the standard Sign-In dialog.
7. If the victim proceeds with sign-in, their GitHub Enterprise credentials/token exchange occurs against the attacker's server instead of a verified GitHub host.

/**
 * Attempts to determine whether or not the url belongs to a GitHub host.
 *
 * This is a best-effort attempt and may return `undefined` if encountering
 * an error making the discovery request
 */
export async function isGitHubHost(url: string) {
  const { hostname } = new window.URL(url)

  const endpoint =
    hostname === 'github.com' || hostname === 'api.github.com'
      ? getDotComAPIEndpoint()
      : getEnterpriseAPIURL(url)

  if (isDotCom(endpoint) || isGHE(endpoint)) {
    return true
  }

  if (isKnownThirdPartyHost(hostname)) {
    return false
  }

  // github.example.com,
  if (/(^|\.)(github)\./.test(hostname)) {
    return true
  }

  // bitbucket.example.com, etc
  if (/(^|\.)(bitbucket|gitlab)\./.test(hostname)) {
    return false
  }

  if (getEndpointVersion(endpoint) !== null) {
    return true
  }

  // Add a unique identifier to the URL to make sure our certificate error
  // supression only catches this request
  const metaUrl = `${endpoint}/meta?ghd=${crypto.randomUUID()}`

  const ac = new AbortController()
  const timeoutId = setTimeout(() => ac.abort(), 2000)
  suppressCertificateErrorFor(metaUrl)
  try {
    const response = await fetch(metaUrl, {
      headers: { 'user-agent': getUserAgent() },
      signal: ac.signal,
      credentials: 'omit',
      method: 'HEAD',
      redirect: 'error',
    })

    tryUpdateEndpointVersionFromResponse(endpoint, response)

    return response.headers.has('x-github-request-id')
  } catch (e) {
    log.debug(`isGitHubHost: failed with endpoint ${endpoint}`, e)
    return undefined
  } finally {
    clearTimeout(timeoutId)
    clearCertificateErrorSuppressionFor(metaUrl)
  }
}
