### Title
Consensus-incentive relayer rewards can be stolen via frontrunning by forging a signature over public proof bytes - (`modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives` implements `FeeHandler::on_executed` to pay whoever "delivered" a `ConsensusMessage` to Hyperbridge. It derives the reward recipient (`relayer_account`) purely by recovering a public key from `consensus_msg.signer`, a signature over `keccak256(consensus_proof)`. Because `consensus_proof` is public data included in the (unsigned) extrinsic itself, and the recovered signer is never checked against the transaction's actual origin or against any privileged/authorized set, anyone observing a pending `Message::Consensus` in the mempool can strip the honest submitter's `signer` field, replace it with their own signature over the same `consensus_proof` bytes, and resubmit — frontrunning the honest relayer and stealing the reward, exactly the class of bug described in the referenced report (public data usable by anyone to claim a reward meant for the original submitter).

### Finding Description
`ConsensusMessage` carries a `signer: Vec<u8>` field alongside the `consensus_proof` [1](#0-0) . This field is attacker-fillable data submitted via the permissionless `handle_unsigned` extrinsic [2](#0-1) .

When `pallet_ismp`'s `execute` runs `handle_incoming_message` for each message and then calls `T::FeeHandler::on_executed(messages_with_weights, events)` [3](#0-2) , the consensus-incentives implementation determines who gets paid like this:

```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
        Signature::decode(&mut &consensus_msg.signer[..])
            .ok()
            .and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
            .map(|pub_key| pub_key.into())
    } else { None }
});
``` [4](#0-3) 

The recovered public key is used directly as the paid `relayer_account`, with the reward transferred from the treasury and reputation minted to it [5](#0-4) , [6](#0-5) .

The critical flaw: `data` is `keccak256(consensus_proof)`, and `consensus_proof` is not secret — it is the exact payload broadcast in the mempool by the honest relayer (confirmed by tesseract's own consensus clients, which populate `signer` with essentially arbitrary/self-chosen bytes such as `H256::random().encode()` or `counterparty.address()`, showing the field was never meant to authenticate anything cryptographically tied to proof possession) [7](#0-6) , [8](#0-7) . Anyone can copy `consensus_proof` out of a pending mempool transaction, sign `keccak256(consensus_proof)` with their own throwaway keypair, and submit their own `Message::Consensus` with a higher priority/earlier inclusion. `verify_consensus` in the ISMP consensus handler only validates the proof content itself, not who submitted it [9](#0-8) , so the frontrunner's copy is accepted identically, the state machine is updated under the frontrunner's transaction, and the reward is paid to the frontrunner's `relayer_account` instead of the honest submitter. The honest relayer's original transaction then either fails (duplicate/stale height) or succeeds with no reward since `on_executed` only looks at `messages.get(0)` of whichever batch lands and pays that batch's signer once.

This mirrors the reported MessageProcessor pattern precisely: valid, public transaction data (there `oracleMessage`/`oracleSignature`, here `consensus_proof`) can be lifted from the mempool and resubmitted by an unrelated party who substitutes themselves as the beneficiary of a `maybePaySender`-style reward payout, with no access control tying the payout to the legitimate submitter.

### Impact Explanation
This is a direct, unauthorized transfer of relayer rewards (funds movement to the wrong beneficiary) from the Hyperbridge treasury account, satisfying "stealing or loss of funds" / "wrong beneficiary or amount" under the bounty's impact gate. It also lets an attacker with no special access permanently capture all consensus-relaying rewards on any state-machine pair with `StateMachinesCostPerBlock` configured, since the corrupted `relayer_account` value requires nothing more than reading public mempool data and producing a signature over it with a fresh key — no relayer role, admin, or leaked key needed.

### Likelihood Explanation
High. Mempool visibility of pending unsigned `handle_unsigned` extrinsics is normal, `consensus_proof` bytes are fully public inside the transaction, and producing `sig.verify_and_get_sr25519_pubkey` compatible signatures over arbitrary public data with a throwaway key is trivial and cheap. Any bot monitoring the txpool for `Message::Consensus` submissions can execute this every time `StateMachinesCostPerBlock` makes the reward economically worthwhile.

### Recommendation
Do not derive the reward recipient from attacker-suppliable data inside the message payload. Instead, tie `relayer_account` to the actual transaction origin (e.g., require a signed extrinsic and use `ensure_signed(origin)`, or bind the `signer` field to a value authenticated by the chain's own unsigned-extrinsic validation/`ValidateUnsigned` logic that checks proof-of-relayer possession, not merely "any valid signature over public proof bytes"). At minimum, reject `on_executed` if `consensus_msg.signer` was not produced by whoever is validated as the actual proof submitter through `validate_unsigned`.

### Proof of Concept
1. An honest relayer submits `Ismp::handle_unsigned([Message::Consensus(ConsensusMessage { consensus_proof, consensus_state_id, signer: sig_honest })])` where `sig_honest` is honest-relayer's signature over `keccak256(consensus_proof)`.
2. Attacker observes this pending extrinsic in the mempool, extracts `consensus_proof` (public bytes), and signs `keccak256(consensus_proof)` with an attacker-controlled keypair to produce `sig_attacker`.
3. Attacker submits `Ismp::handle_unsigned([Message::Consensus(ConsensusMessage { consensus_proof, consensus_state_id, signer: sig_attacker })])` with higher priority/earlier block inclusion.
4. Attacker's transaction is processed first: `update_client` verifies and accepts the (identical, valid) `consensus_proof` [10](#0-9) ; `on_executed` recovers `sig_attacker` → attacker's pubkey as `relayer_account` and pays the treasury-funded reward to the attacker [11](#0-10) .
5. The honest relayer's original transaction subsequently fails or is a no-op (the consensus state / commitment height has already advanced), and they receive nothing despite having produced/discovered and broadcast the proof first.

pub fn update_client<H>(host: &H, msg: ConsensusMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host.consensus_client_id(msg.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized { consensus_state_id: msg.consensus_state_id },
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;
	host.is_consensus_client_frozen(msg.consensus_state_id)?;
	host.is_expired(msg.consensus_state_id)?;

	let (new_state, intermediate_states) = consensus_client.verify_consensus(
		host,
		msg.consensus_state_id,
		trusted_state,
		msg.consensus_proof,
	)?;
	host.store_consensus_state(msg.consensus_state_id, new_state)?;
