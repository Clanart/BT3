## Analog Found: Plot-NFT pool-state can get permanently stuck due to unrolled `target_state` flag

### Title
Stuck `target_state` flag can permanently block plot-NFT pool switching if `generate_travel_transactions` fails after being set - (File: chia/pools/pool_wallet.py)

### Summary
`PoolWallet.join_pool()` and `PoolWallet.self_pool()` set `self.target_state` as a "pending" guard flag *before* calling `generate_travel_transactions()`, which performs coin selection, puzzle construction, and spend-bundle creation that can raise exceptions. If it raises after the flag is set, `self.target_state` is never reset, and every subsequent call to `join_pool`/`self_pool` is rejected because of the guard check, permanently locking the plot-NFT out of pool transitions — the same class of bug as the reported Arcadia `inAuction` flag issue where a revert after setting a "busy" flag leaves the object stuck.

### Finding Description
In `join_pool()`, after all pre-checks pass, the code sets the pending-state guard and then attempts to build the travel transaction: [1](#0-0) 

The same pattern exists in `self_pool()`: [2](#0-1) 

Both guard subsequent calls with a check that raises if `self.target_state is not None`: [3](#0-2) [4](#0-3) 

`generate_travel_transactions()` — invoked immediately after `self.target_state` is set — performs several operations that can raise exceptions: it asserts `new_inner_puzzle != inner_puzzle`, raises `RuntimeError("Invalid state")` for unrecognized inner puzzles, and calls `generate_fee_transaction()` → `standard_wallet.generate_signed_transaction()`, which can fail (e.g., insufficient balance for the requested fee, coin-selection errors): [5](#0-4) 

There is no `try/except` around the `self.target_state = target_state` … `await self.generate_travel_transactions(...)` sequence in either `join_pool` or `self_pool` to reset the flag back to `None` on failure. The only place `target_state` is normally cleared is when the corresponding on-chain state transition is later observed and applied — a path that never happens if the transaction was never successfully created.

### Impact Explanation
Once `self.target_state` is stuck non-`None`, the user's plot-NFT wallet is permanently unable to submit any further `join_pool` or `self_pool` calls through the normal wallet RPC flow, since both entry points immediately raise `ValueError` when `self.target_state is not None`. This denies the wallet owner the ability to change pool assignment (e.g., leaving a malicious/underperforming pool or self-pooling), which is a legitimate wallet-state DoS reachable purely by a local RPC caller triggering a fee-insufficient or otherwise failing travel-transaction attempt — no privileged or network-adversarial action required.

### Likelihood Explanation
This can be triggered by an ordinary user action: calling `join_pool`/`self_pool` with a `fee` that exceeds available standard-wallet balance (causing `generate_signed_transaction` to raise inside `generate_fee_transaction`), or any other transient failure during travel-spend construction. Because the guard flag is set unconditionally before the fallible work, any such failure — even a benign and recoverable one — leaves the wallet stuck, making the likelihood of accidental triggering moderate to high in real usage (e.g., insufficient balance is a common condition).

### Recommendation
Wrap the `generate_travel_transactions()` call (and any other fallible step after `self.target_state` is set) in `join_pool()`/`self_pool()` in a `try/except`, resetting `self.target_state = None` (and `next_transaction_fee`/`next_tx_config` if appropriate) on any exception before re-raising, so a failed attempt does not leave the plot-NFT permanently unable to transition pool state.

### Proof of Concept
1. Create a plot-NFT wallet currently `SELF_POOLING` or `FARMING_TO_POOL`.
2. Ensure the standard wallet's spendable balance is lower than the `fee` argument that will be passed to `join_pool(target_state, fee, action_scope)`.
3. Call `join_pool()`. Pre-checks pass; `self.target_state = target_state` executes; `generate_travel_transactions()` calls `generate_fee_transaction()` → `standard_wallet.generate_signed_transaction()`, which raises due to insufficient funds to cover `fee`.
4. The exception propagates out of `join_pool()`, but `self.target_state` remains set to the attempted `target_state`.
5. Any subsequent call to `join_pool()` or `self_pool()` immediately raises `ValueError("Cannot join a pool while waiting for target state: ...")` / `ValueError("Cannot self pool when already having target state: ...")`, permanently preventing the wallet from changing pool state through normal RPC calls.
