Based on my investigation, the strongest local analog to the Vyper "incorrectly allocated named re-entrancy locks" bug class is in how GitHub Desktop scopes its per-repository re-entrancy guards.

### Title
Per-repository operation locks are keyed by a derived `Repository.hash`, not by the actual on-disk git directory, allowing guarded operations to race across aliased repository/worktree identities - (File: app/src/lib/stores/repository-state-cache.ts, app/src/lib/stores/git-store-cache.ts)

### Summary
Desktop's re-entrancy guards for git operations (`isCommitting`, `isPushPullFetchInProgress`, `isGeneratingCommitMessage`) are stored in `RepositoryStateCache`, keyed by `repository.hash`, and the underlying `GitStore` instances are cached in `GitStoreCache`, also keyed by `repository.hash`. [1](#0-0) [2](#0-1) 

### Finding Description
`Repository.hash` is not an identity of the physical working directory; it is a composite hash of `path`, `id`, `gitHubRepository?.hash`, `missing`, `alias`, `workflowPreferences.forkContributionTarget`, and `isTutorialRepository`: [3](#0-2) 

The `withPushPullFetch`, `withIsCommitting`, and `withIsGeneratingCommitMessage` guards in `app-store.ts` all read/write mutual-exclusion flags from `repositoryStateCache.get(repository)`, i.e. bucketed by this hash: [4](#0-3) [5](#0-4) 

The Desktop code itself acknowledges that this "key" is unstable and not tied to the actual repo on disk: when a linked worktree is renamed, the comment explicitly notes that the path change "changes the repository's path and therefore its hash, which is the key used by the state cache," requiring an explicit `transferState` call to carry state to the new identity: [6](#0-5) [7](#0-6) 

This is structurally the same broken invariant as the Vyper advisory: a lock/guard that is supposed to protect a single shared resource (the physical `.git` working tree) is instead allocated per a narrower/looser "key" (the app-level `Repository` record's hash) that does not uniquely and durably map to that resource. Just as the Vyper `@nonreentrant` locks were allocated per-function instead of per-`key`, Desktop's commit/push/pull/fetch locks are allocated per-`Repository` object identity instead of per underlying git directory (`resolvedGitDir`). Two `Repository` records that resolve to the same working tree (e.g., a repository and one of its linked worktrees before `gitDir`/`mainWorktreePath` are resolved, or the same path added under two different repository IDs) receive independent `GitStore` instances and independent `isCommitting`/`isPushPullFetchInProgress` flags, so operations meant to be serialized against that working tree are not actually mutually exclusive.

### Impact Explanation
If two logical `Repository` records end up pointing at overlapping git state, concurrent operations (e.g., a commit via one record racing a pull/reset/checkout via the other) can interleave against the same index/refs, since Desktop's exclusion is enforced only within a single hash bucket. This maps to the "silent corruption of what the user commits or pushes" impact category: a commit could be created or amended while another in-flight operation (fetch, reset, rebase) mutates the working directory or HEAD, producing inconsistent trees or partially-applied resets without any user-visible warning, because both `performFailableOperation` calls believe they hold exclusive access.

### Likelihood Explanation
Likelihood is difficult to confirm to "attacker fully controls this end-to-end" certainty from the index alone; I was not able to fully trace, within available tool budget, the exact code path in the worktree-add/switch flow (`repositoriesStore.switchWorktree`, worktree auto-detection) that would definitively produce two concurrently-live `Repository` records aliasing the same `.git` directory during normal use of an attacker-supplied repo containing multiple worktrees/submodules. The evidence establishes the broken invariant (hash-keyed locks vs. path-based physical identity, explicitly acknowledged in the worktree-rename code) but a full proof of an attacker-triggerable race requires further tracing of worktree discovery/creation code that I could not complete in this session.

### Recommendation
Key `GitStoreCache` and the re-entrancy flags in `RepositoryStateCache` by the resolved physical git directory (`repository.resolvedGitDir`, canonicalized) rather than by the composite `Repository.hash`, so that any two `Repository` records referring to the same working tree share the same lock and `GitStore` instance, closing the gap between the guarded resource and the guard's key — mirroring the Vyper fix that scoped locks by `key` rather than by call site.

### Proof of Concept
Not independently verified end-to-end due to tool-budget limits; the concrete, verifiable code evidence is:
1. `Repository.hash` is computed from `path/id/gitHubRepository/missing/alias/workflowPreferences/isTutorialRepository`, not from the resolved `.git` directory. [8](#0-7) 
2. `GitStoreCache.get` and `RepositoryStateCache.get/update` both bucket exclusively by `repository.hash`. [9](#0-8) [10](#0-9) 
3. The `_moveWorktree` code explicitly documents that changing a repository's path changes its hash/state-cache key, requiring manual `transferState`, confirming the key is not a stable proxy for the physical repository. [11](#0-10) 

Because I could not confirm a concrete attacker-triggerable step sequence producing two simultaneously-active `Repository` records over the same working tree within the remaining investigation budget, this should be treated as a plausible but unconfirmed analog rather than a fully proven exploit chain.

  /**
   * Move the entire cached state for a repository from one identity to another.
   *
   * This is used when a worktree is renamed: the repository's path (and
   * therefore its hash) changes, but it still refers to the same working
   * directory, so all of the existing in-memory state (working directory
   * changes, commit message, history, etc.) should be carried over to the new
   * identity rather than reset to its initial values.
   */
  public transferState(source: Repository, target: Repository) {
    if (source.hash === target.hash) {
      return
    }

    const sourceState = this.repositoryState.get(source.hash)
    if (sourceState === undefined) {
      return
    }

    this.repositoryState.set(target.hash, sourceState)
    this.repositoryState.delete(source.hash)
  }

export class GitStoreCache {
  /** GitStores keyed by their hash. */
  private readonly gitStores = new Map<string, GitStore>()

  public constructor(
    private readonly shell: IAppShell,
    private readonly statsStore: IStatsStore,
    private readonly onGitStoreUpdated: (
      repository: Repository,
      gitStore: GitStore
    ) => void,
    private readonly onDidError: (error: Error) => void
  ) {}

  public remove(repository: Repository) {
    if (this.gitStores.has(repository.hash)) {
      this.gitStores.delete(repository.hash)
    }
  }

  public get(repository: Repository): GitStore {
    let gitStore = this.gitStores.get(repository.hash)
    if (gitStore === undefined) {
      gitStore = new GitStore(repository, this.shell, this.statsStore)
      gitStore.onDidUpdate(() => this.onGitStoreUpdated(repository, gitStore!))
      gitStore.onDidError(error => this.onDidError(error))

      this.gitStores.set(repository.hash, gitStore)
    }

    return gitStore
  }

  private async withIsCommitting(
    repository: Repository,
    fn: () => Promise<boolean>
  ): Promise<boolean> {
    const state = this.repositoryStateCache.get(repository)
    // ensure the user doesn't try and commit again
    if (state.isCommitting) {
      return false
    }

    this.repositoryStateCache.update(repository, () => ({
      isCommitting: true,
      hookProgress: null,
      subscribeToCommitOutput: null,
    }))
    this.emitUpdate()

    try {
      return await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isCommitting: false,
        hookProgress: null,
        subscribeToCommitOutput: null,
      }))
      this.emitUpdate()
    }
  }
