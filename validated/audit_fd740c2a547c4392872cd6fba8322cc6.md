## Finding

### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the declared input amount instead of the actual tokens received, allowing fee-on-transfer/deflationary tokens to over-credit escrow and drain other users' deposits - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The mainline EVM `IntentGatewayV2.sol` was hardened to snapshot token balances before/after every transfer and rewrite `order.inputs[i].amount` to the *actually received* amount before computing the commitment and crediting escrow [1](#0-0) . The Tron fork of the same contract was never given this fix: it computes the commitment and the escrow credit from the caller-declared `order.inputs[i].amount` *before* the token transfer happens, and never re-measures the contract's balance afterward for the direct-transfer path.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the sequence is:

1. `reducedInputs`/`commitment` are computed from `order.inputs[i].amount` (the caller-declared amount) [2](#0-1) .
2. Tokens are pulled with a plain `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`, with **no balance-before/after check**, and the escrow map is credited with the pre-computed `reducedInputs[i].amount`: [3](#0-2) 

For any ERC-20 with a transfer fee, rebase, or any other mechanism where `balanceOf(this)` increases by less than the nominal `amount` passed to `transferFrom`, `_orders[commitment][token]` is credited with more than the tokens the contract actually received. This is structurally identical to `AggMonetaryPolicy2` calculating a rate off a `total_debt` value that hasn't been refreshed to reflect the real state — here, the escrow ledger (`_orders`) is never refreshed to reflect the *real* balance the contract holds before it is relied upon by `cancelOrder`/`withdraw`.

The escrow ledger is a single mapping keyed by `(commitment, token)`, but the underlying ERC-20 balance is a shared pool across every order using that token. `cancelOrder`'s same-chain path passes the original `order.inputs` (not the reduced/actual amounts) into `withdraw(body, true)`, which decrements `_orders[commitment][token]` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for the full declared amount [4](#0-3) . Because the escrow bookkeeping was never corrected to the amount actually held, this transfer can pull tokens deposited by *other* users of the same token from the shared contract balance.

### Impact Explanation
An attacker can:
1. Place an order using a fee-on-transfer (or similarly lossy) ERC-20 as an input, declaring `amount = X`.
2. The contract actually receives `X - fee`, but `_orders[commitment][token]` is credited `X` (or `X` minus protocol fee, still greater than what was actually received).
3. Immediately cancel the order (same-chain path, no waiting), which pays out the full escrowed (overstated) amount from the gateway's pooled token balance.

This lets the attacker withdraw more tokens than they deposited, funded by other users' legitimately escrowed balances of the same token — a direct theft of bridged/escrowed funds and a violation of "bridged assets... must move exactly once and only to the rightful beneficiary and amount." At minimum this also causes insolvency/DoS: later legitimate withdrawals of the same token can revert due to insufficient actual balance even though their escrow entry is correct, permanently locking funds.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — only an unprivileged caller supplying an arbitrary ERC-20 address as an input token, which `placeOrder` permits without restriction to a token allowlist. Fee-on-transfer and similar tokens are common in the wild, and the attack is a two-step self-service (`placeOrder` then `cancelOrder`) executable entirely by an ordinary user.

### Recommendation
Port the fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: snapshot `balanceOf(address(this))` before and after each `safeTransferFrom`, set `order.inputs[i].amount` (and therefore `reducedInputs`/escrow credit) to the actual delta received, and only then compute the commitment and credit `_orders`. Ensure `cancelOrder`/`withdraw` always operate on `_orders[commitment][token]` rather than raw `order.inputs` amounts, so the escrow ledger can never diverge from the ERC-20 balance actually custodied by the contract.

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 `FOT` with e.g. a 5% transfer fee (as already modeled in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` `FeeOnTransferToken`) [5](#0-4) .
2. User A places an order on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000}`. The contract actually receives `950` FOT, but `_orders[commitment][FOT] += reducedInputs[0].amount` credits `1000` (or `1000` minus protocol fee) — see `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 444-463.
3. User B independently places a legitimate order with the same `FOT` token, contributing real tokens to the shared pool.
4. User A calls `cancelOrder` (same-chain path) before the deadline expires with `order.deadline`/no fill; `withdraw` transfers out the full escrowed `1000` FOT to A, exceeding A's actual net contribution of `950`, drawn from the pool that includes B's deposit.
5. When B later attempts to have their order filled/cancelled, `safeTransfer` reverts due to insufficient contract balance, or B receives less than entitled — demonstrating fund theft/lock.

Note: I could not fully read the Tron contract's `withdraw`/`onAccept` body beyond what's shown (lines 614-650) due to tool-call limits, so I was unable to directly view the internal `withdraw` function definition confirming the exact decrement/transfer logic; this is inferred from the analogous, fully-read `_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` (lines 390-410) which the Tron file's `cancelOrder`/`onAccept` clearly mirrors in structure (same `WithdrawalRequest`, `RequestKind.RedeemEscrow/RefundEscrow` pattern). A background engineer should verify the exact `withdraw` implementation in the Tron file to confirm the transfer amount and decrement arithmetic before patching.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
