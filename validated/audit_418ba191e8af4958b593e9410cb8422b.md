### Title
Unprivileged sender can force Serai to credit unspendable coinbase outputs via `scan_block` - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the Cooler `roll()` issue — where anyone could permissionlessly extend a loan and impose extra obligations on the borrower — `Scanner::scan_block` accepts outputs from *any* transaction in a block, including the coinbase transaction, and reports them as spendable `ReceivedOutput`s. A miner (or any party whose transaction lands in `block.txdata[0]`, i.e., the miner) can pay the Serai key's script in a coinbase output, and the scanner will report it as received even though the output cannot be spent for 100 blocks. The cost to the attacker is only the (reclaimable-after-maturity) output value, mirroring "attacker pays a small amount to force the victim into a worse position."

### Finding Description
`Scanner::scan_block` iterates over *all* transactions in the block, `block.txdata` including index 0 (the coinbase), and calls `scan_transaction` on each. Any output paying a registered script is emitted as a `ReceivedOutput` with no maturity or coinbase flag [1](#0-0) .

`scan_transaction` matches solely on `output.script_pubkey` and constructs the `ReceivedOutput` unconditionally [2](#0-1) .

`ReceivedOutput` carries only `offset`, `output`, and `outpoint` — there is no field indicating coinbase status or required maturity height, so downstream consumers cannot distinguish it from a normally spendable output [3](#0-2) .

The code itself acknowledges the hazard only in a doc comment: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" — i.e., the spendability invariant is delegated to callers rather than enforced [4](#0-3) .

### Impact Explanation
A miner can send value to Serai's (registered) script inside the coinbase transaction. `scan_block` reports this output as a received, spendable UTXO. Any consumer that selects it as an input to a withdrawal/batch transaction will produce a transaction that is *provably invalid* under Bitcoin consensus (BIP-34/COINBASE_MATURITY = 100 blocks): the network rejects it, and the signed batch is wasted. This is "funds reported received that are not spendable" — the scanner's output is consumed as spendable when it cannot be. Like the `roll()` bug, an unprivileged party spends a small, recoverable cost (the coinbase output returns to them only after maturity — actually they forfeit nothing beyond normal mining proceeds) to impose cost and risk on the victim (failed/invalid withdrawal transactions, stalled batches, forced re-signing).

### Likelihood Explanation
Only a miner can place outputs in `block.txdata[0]`, so the attacker must control a found block — but miners are unprivileged third parties, and the trigger requires no malformed input: it is a fully valid block. Any processor/coordinator flow that calls `scan_block` (rather than `scan_transaction` over `block.txdata[1 ..]`) and immediately feeds results into `ReceivedOutput`-driven coin selection is affected. The doc comment shifts responsibility to the caller, but nothing in the type system or API prevents the misuse, and Serai's own scan-and-spend pipeline consumes these outputs for withdrawals.

### Recommendation
Have `scan_block` skip `block.txdata[0]` by default, or tag `ReceivedOutput` with a coinbase/maturity flag and an `earliest_spendable_height` so consumers can filter immature outputs. If coinbase crediting is intentional, enforce maturity at the `Scanner` level rather than relying on every caller to perform the "post-processing pass."

### Proof of Concept
```rust
// A miner crafts a coinbase tx paying Serai's registered script.
let coinbase_tx: Transaction = /* tx with output[0].script_pubkey == serai_p2tr_script */;
let block = Block { header, txdata: vec![coinbase_tx, /* other txs */] };

let outputs = scanner.scan_block(&block);
// outputs contains a ReceivedOutput for the coinbase payment,
// indistinguishable from a spendable output:
assert_eq!(outputs[0].outpoint().txid, block.txdata[0].compute_txid());

// Consumer builds a withdrawal spending outputs[0] immediately.
// Resulting tx spends an immature coinbase -> rejected by Bitcoin consensus.
```

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
