### Title
Same-chain partial fill releases the entire shared escrow bucket for an input token on the first completing output leg, corrupting funds owed to other legs - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes the escrow amount to release for a completed output leg by reading the *entire* remaining balance stored under `_orders[commitment][token]` instead of a value scoped to that specific output leg. Because `_orders` is keyed only by `(commitment, token)` — not by output/input index — any order whose `inputs` array repeats the same token address across multiple entries (backing multiple, independently-progressing output legs) will have all of those legs' escrow collapsed into a single storage slot. The first leg to reach `amountFilled == totalRequired` sweeps the *whole* slot, not its proportional share, exactly mirroring the M-20 pattern of computing a balance-based amount from a shared/aggregate value that includes funds belonging to a different accounting bucket.

### Finding Description
In `_fillSameChain`: [1](#0-0) 
```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```
When an output leg finishes (`amountFilled == totalRequired`), the code does not compute the proportional/remaining amount owed specifically to that leg. Instead it reads the raw current value of `_orders[commitment][token]` — the aggregate escrow balance for that token under the whole commitment.

Escrow accounting, however, is not per-leg: `_withdraw` and `_cancelSameChain` both operate on the same flat mapping [2](#0-1) , confirming `_orders[commitment][token]` is a single bucket per `(commitment, token)` pair, not per output index. If an order's `inputs` array places the same token address at two or more indices (e.g. `inputs[0].token == inputs[2].token`, each index backing a different output asset with its own `totalRequired`/partial-fill progress in `_partialFills[commitment][outputToken]`), the escrow for both legs is deposited into (and tracked from) the *same* storage slot.

Because the "full completion" branch just reads whatever is currently sitting in that shared slot rather than computing this leg's proportional share, whichever output leg happens to reach 100% fill *first* drains the entire slot — including the portion of escrow that was placed to back the other, still-partially-filled leg on that same input token. The later leg then either:
- reverts (`_withdraw` reverts with `UnknownOrder` once `_orders[commitment][token] == 0`, denying the still-in-progress leg its due release), or
- receives less than it is entitled to on eventual completion, because `escrowedAmount` for the "full completion" branch on the second leg to close reads `0` or an already-drained amount.

This is a false-computation-of-amount bug: `escrowedAmount` should be `order.inputs[i].amount - (already released for this leg)`, not "whatever remains in the shared per-token bucket," exactly as M-20 flags `getVaultBalance() - reservedFunds` as an incorrect way to isolate a delta for one purpose from a value shared with another purpose (`reservedFunds`).

### Impact Explanation
An unprivileged filler/solver controls `FillOptions.outputs[i].amount` per leg and can order the sequence of transactions/fills to make the leg with the smaller `totalRequired` (or one they choose to complete first) finish before the other leg sharing the same input token. This lets the filler:
- extract escrowed input tokens intended to back a *different* output leg (wrong beneficiary/wrong amount — moving funds that should remain locked for another leg's fill), and
- cause the legitimate solver who fills the remaining leg to be shorted or reverted (loss/lock of funds for the honest party / order creator, since `_withdraw` will revert with `UnknownOrder` once the shared bucket is emptied).

This falls squarely within the bounty's "wrong beneficiary or amount," "logic attack," and "fund loss" categories, and requires no relayer/prover/admin/governance collusion — only a same-chain order with a repeated input token across indices, which nothing in `placeOrder`/`_fillSameChain` forbids.

### Likelihood Explanation
Requires only that an order be constructed (by the user, or a filler cooperating with a user, or even accidentally) with the same ERC-20 token address appearing at two or more `inputs[]` indices tied to different output assets — a configuration the contract does not reject anywhere in `placeOrder` or `_fillSameChain`. Given intents commonly bundle multiple output assets in one order, and nothing enforces distinct input tokens per leg, this is a realistic, attacker-reachable configuration via the public `fillOrder`/`placeOrder` entry points.

### Recommendation
Track escrow per output-leg index rather than aggregated only by `(commitment, token)`, or compute `escrowedAmount` for the completing branch as the leg's own proportional remainder (`order.inputs[i].amount - previouslyReleasedForThisLeg`) instead of reading the shared token-level balance. If the "release-all-remaining-dust" behavior on final completion is intentional, it must first verify that no other output leg still depends on the same input-token slot before sweeping it in full.

### Proof of Concept
1. User places a same-chain order with `order.inputs = [ {token: X, amount: 100}, {token: X, amount: 50} ]` and two output legs (`order.output.assets[0]`, `order.output.assets[1]`) — both inputs use the same token `X`, so `_orders[commitment][X] = 150` after `placeOrder`.
2. Filler calls `fillOrder` supplying `options.outputs[0].amount == order.output.assets[0].amount` (fully completes leg 0) while leaving leg 1 unfilled (`options.outputs[1].amount == 0`).
3. In `_fillSameChain`, leg 0 hits `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][X]` reads the full `150`, not the `100` proportional to leg 0. The filler receives `150` worth of input token X for filling only leg 0's required output.
4. `_withdraw` executes `_orders[commitment][X] = 150 - 150 = 0`.
5. A later filler attempting to complete leg 1 (`options.outputs[1].amount == order.output.assets[1].amount`) triggers `escrowedAmount = _orders[commitment][X] == 0`, and `_withdraw` reverts with `UnknownOrder` — leg 1 can never be filled, and the honest second filler/beneficiary is denied any input-token payout despite the order creator having escrowed `50` tokens meant for that leg.
