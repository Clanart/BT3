### Title
Mutable protocol-fee parameters corrupt already-placed order commitments, permanently locking escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` bakes the *current* protocol-fee-reduced token amounts into the order commitment hash that keys escrow storage. `_params.protocolFeeBps` and `_destinationProtocolFees[...]` can be changed at any time via the `UpdateParams` request path, with no restriction that ties a fee change to unfilled/uncommitted orders. Because the fee-reduced amounts are never persisted in a retrievable form (only hashed into the commitment), any later change to the fee parameters makes it impossible to reconstruct the exact commitment needed to cancel/refund an already-placed order, permanently locking the user's escrowed tokens. This is the direct analog of the C4 report's "owner changes a live parameter (plots-per-size / vesting) that silently invalidates already-committed user state, with no contract-side check protecting existing commitments."

### Finding Description
In `placeOrder`, the escrow commitment is computed using fee-reduced inputs, then the original (raw) inputs are restored before emitting the public `OrderPlaced` event: [1](#0-0) 

The reduced amount, not the raw amount, is what actually gets stored in escrow: [2](#0-1) 

The fee rate itself comes from mutable state that can be rewritten at any time by an `UpdateParams` cross-chain governance request, with no linkage to in-flight orders: [3](#0-2) [4](#0-3) 

Later, when anyone (the user, a solver, or the destination-chain module) attempts to cancel/refund the order, the commitment is recomputed from the `order` struct supplied to `cancelOrder`, and `withdraw()` looks up `_orders[commitment][token]` using that recomputed commitment: [5](#0-4) [6](#0-5) 

Because the fee-adjusted `inputs` used at escrow-storage time are not retrievable from chain state (they only exist transiently inside `placeOrder`'s hash computation), and the party requesting cancellation only has the public/raw order fields, they can only reproduce the correct commitment by re-deriving the exact `protocolFeeBps` that was in effect **at order placement time**. If that fee value has since been updated (a routine, permissionless-from-the-app's-perspective operation reachable through normal `UpdateParams`/`_destinationProtocolFees` governance flow), the commitment computed for cancellation will never match the one stored in `_orders`, and `withdraw()` unconditionally reverts with `UnknownOrder` for every token in the order: [7](#0-6) 

There is no fallback path, no stored snapshot of the fee used per-order, and no way to retry with a corrected value — the escrowed tokens become permanently unreachable, exactly mirroring the report's "already-vested tokens suddenly unvested" / "rarity changed after purchase" pattern, where a live, unconstrained parameter silently invalidates previously committed user state with zero contract-side protection.

### Impact Explanation
Any order placed while `protocolFeeBps` (global or destination-specific) is non-zero is permanently at risk: if the fee is updated before the order is filled and the user needs to cancel/refund (order expires unfilled, or destination-side refund is triggered), the escrowed input tokens and fees become unrecoverable. This is a direct, unprivileged loss/lock of user funds — the exact "loss or lock of funds" category called out in the bounty scope.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin collusion — only the ordinary, expected operational flow of updating protocol fees (which the code explicitly supports as a routine `UpdateParams` action) occurring between order placement and order cancellation/expiry. Given that fee updates are a normal governance/ops action and orders can remain unfilled for their full deadline window, this is a realistically frequent occurrence, not an edge case.

### Recommendation
Store the fee-reduced amounts (or the exact fee rate applied) on-chain, retrievable by commitment, so cancellation/refund flows read the authoritative escrowed amount rather than requiring an external party to reconstruct it via a potentially stale fee rate. Alternatively, snapshot `protocolFeeBps` per order at placement time and include it in the `WithdrawalRequest`/order metadata so refunds/cancellations always resolve against the correct historical value.

### Proof of Concept
1. `protocolFeeBps` (or a destination-specific fee) is set to a non-zero value, e.g. 100 bps.
2. User calls `placeOrder` with `inputs = [100 tokens]`; the commitment stored in `_orders` is computed using `reducedInputs = [99 tokens]` (line 372-374 / 457).
3. Governance issues a routine `UpdateParams` request changing the fee to 50 bps (line 635-639) before the order is filled.
4. Order expires unfilled or the destination side requests a refund. `cancelOrder` recomputes `commitment = keccak256(abi.encode(order))` using the order's known raw `inputs = [100 tokens]` — but this hash was never the one used to key escrow (`_orders` was keyed with the 99-token-reduced version), and even attempting to reproduce the reduced version now yields a 99.5-token reduction under the new fee, still mismatching the original 99.
5. `withdraw()` finds `_orders[commitment][token] == 0` for the (wrong) recomputed commitment and reverts with `UnknownOrder`, permanently locking the escrowed 99 tokens with no recovery path.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
