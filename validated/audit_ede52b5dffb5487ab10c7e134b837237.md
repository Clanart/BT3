### Title
`Scanner::scan_block` reports coinbase outputs as received without enforcing maturity, causing funds to be credited which cannot yet be spent — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the reference report is a state/condition that should gate a user-facing intake operation (`deposit`/`mint` while shutdown) but is never enforced. The Serai analog is the Bitcoin wallet `Scanner`: `scan_block` scans every transaction in `block.txdata`, including the coinbase transaction at index 0, even though coinbase outputs are immature and unspendable for 100 blocks. A `ReceivedOutput` for a coinbase output is indistinguishable from a spendable one, so an unprivileged miner can cause Serai's wallet layer to report funds as received which are not actually spendable.

### Finding Description
`Scanner::scan_transaction` pushes a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script, with no notion of the output's maturity state (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` iterates `block.txdata` from index 0, so it feeds the coinbase transaction through `scan_transaction` as well (`networks/bitcoin/src/wallet/mod.rs:221-227`).

The code acknowledges the hazard only in a doc comment — "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" — but no such check exists in the API, mirroring how `LMPVault` documents `_shutdown` and `isShutdown()` yet never enforces it in `deposit()`/`mint()`.

That this is a real condition to enforce is proven by the rest of the codebase: the processor's `get_outputs` explicitly skips the coinbase with `for tx in &block.txdata[1 ..]` and the comment "Skip the coinbase transaction which is burdened by maturity" (`processor/src/networks/bitcoin.rs:690-691`). The public `scan_block` API offers no equivalent protection; any caller that uses it (or scans a block's transactions without reimplementing the `[1 ..]` skip) will emit a `ReceivedOutput` for an output that cannot be spent for ~100 blocks.

The trigger is fully reachable by an unprivileged party: anyone who mines a block (or on test/signet-like contexts, anyone producing blocks) can place a coinbase output paying to a Serai scanner script, or more generally, any party-aware mining pool can include a payment to the multisig's registered script in their coinbase.

### Impact Explanation
A `ReceivedOutput` is the unit Serai's wallet/scanner pipeline treats as "funds received and available." An immature coinbase output reported as received will be counted toward the multisig's balance and can drive downstream logic (batch planning, refund plans, `InInstruction` crediting) against a UTXO that Bitcoin consensus forbids spending for 100 blocks. This yields "funds reported received that are not spendable": the credited balance is unbacked for the maturity window, and any plan constructed referencing that outpoint fails at broadcast or, worse, credits the depositor before the funds are actually movable — an accounting-vs-spendability gap directly analogous to users being allowed to deposit into a vault that can no longer generate yield.

### Likelihood Explanation
Low-to-moderate: it requires a block producer to include the payment in a coinbase rather than a normal transaction. However, coinbase outputs paying arbitrary scripts occur routinely (miners paying out to pool participants, or any miner including an extra output). No attacker privilege beyond producing a block is needed, and the scanner API gives no warning at the type level that `ReceivedOutput`s from `scan_block` must be post-filtered — the safeguard lives only in a doc comment and in a separate caller (`get_outputs`), exactly like the missing `isShutdown` check.

### Recommendation
Enforce the maturity condition inside the scanner rather than relying on callers. In `scan_block` (`networks/bitcoin/src/wallet/mod.rs:221-227`), skip `block.txdata[0]`, or annotate each `ReceivedOutput` with whether it is coinbase-derived and require consumers to check it before use — analogous to adding `require(!isShutdown())` to `deposit`/`mint` instead of documenting the flag. At minimum, align `scan_block` with `get_outputs`' `txdata[1 ..]` behavior (`processor/src/networks/bitcoin.rs:690-691`) so all intake paths apply the same restriction.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs semantics
let scanner = Scanner::new(key).unwrap();

// A block whose coinbase pays to the scanner's p2tr script
let mut block: Block = attacker_produced_block();
block.txdata[0].output.push(TxOut {
  value: Amount::from_sat(50_0000_0000), // coinbase subsidy output
  script_pubkey: p2tr_script_buf(key).unwrap(), // registered script
});

// scan_block includes the coinbase (txdata[0]) in its scan
let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput for an outpoint consensus-immature
// for 100 blocks — reported received, not spendable.
assert_eq!(outputs[0].outpoint.txid, block.txdata[0].compute_txid());
```
Contrast with the enforced path in `processor/src/networks/bitcoin.rs:690-691` (`&block.txdata[1 ..]`), which shows the maturity check is required but missing from `scan_block`.
