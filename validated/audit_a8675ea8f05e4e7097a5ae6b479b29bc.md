## Analysis

The Yearn report's core defect is: a swapper module executes attacker/operator-suppliable arbitrary calldata through a shared execution primitive, and the caller of that primitive is not properly restricted, so funds sitting in/flowing through it can be diverted outside of the invoking contract's accounting checks.

The direct local analog is Hyperbridge's `CallDispatcher`, the shared contract used by `IntentGatewayV2`/`IntentsBase` to execute arbitrary order-supplied calldata for both predispatch (before escrow) and postdispatch (after fill) flows.

### Title
Unrestricted `CallDispatcher.dispatch` combined with incomplete sweep lets any caller steal dust left by intent order calldata routing - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch` [1](#0-0)  has no caller restriction whatsoever — it is `external` with no modifier limiting it to `IntentGatewayV2`. `IntentsBase._execute` and `IntentGatewayV2.placeOrder`'s predispatch handling only sweep back the specific tokens declared in `order.output.assets` / `order.inputs`, not the full set of tokens the dispatcher may hold after arbitrary calldata execution [2](#0-1) [3](#0-2) . Because the documented use case for pre/postdispatch calldata is multi-hop DeFi routing ("solvers can route through DEXes, lending protocols, or other DeFi primitives") [4](#0-3) , any intermediate token used mid-route (e.g., a WETH leg of a multi-hop swap) is never part of `order.output.assets`/`order.inputs` and therefore never gets swept — it accumulates as unrecoverable balance sitting in the single, shared `CallDispatcher` instance used by every order across the whole gateway.

### Finding Description
Every order's predispatch and postdispatch calldata is dispatched through the same singleton `CallDispatcher` contract (`_params.dispatcher`) [5](#0-4) . `dispatch()` blindly executes any `Call[]` passed to it against any target, with the only checks being that the target has code and the call succeeds [1](#0-0) . There is no `onlyGateway`/`restrict` guard, unlike the analogous `HostManager.onAccept`, which enforces `restrict(_params.host)` before acting on cross-chain instructions [6](#0-5) .

The sweep logic that is supposed to reclaim any leftover balance after calldata execution only iterates over the order's own declared asset list:
```solidity
for (uint256 i; i < outputsLen;) {
    address token = address(uint160(uint256(order.output.assets[i].token)));
    ...
}
``` [7](#0-6)  This does not sweep any token that isn't in `order.output.assets`. The predispatch path in `placeOrder` has the identical structure — it only builds sweep/transfer calls for `order.inputs`, not for every balance the dispatcher might be holding after `order.predispatch.call` executes [8](#0-7) .

Combining these two facts: any order whose predispatch/postdispatch calldata performs a multi-hop swap (e.g., TokenA → WETH → TokenB) will strand WETH dust in the `CallDispatcher`. Since `dispatch()` has no access control, that stranded balance — and any other order's stranded balance accumulated over time, across the entire gateway's lifetime — is directly stealable by any unprivileged external account, simply by calling `CallDispatcher.dispatch()` themselves with a `Call[]` that transfers the dispatcher's balance of the stranded token to themselves. No order needs to be placed by the attacker, no proof, no relayer, and no privileged role is required.

### Impact Explanation
This is a direct "stealing or loss of funds" / "unauthorized transaction or execution" primitive: value that belongs to the protocol/users (residual output of order fulfillment) is exposed to permissionless drain via a contract that was intended to be an internal execution helper for `IntentGatewayV2` only. Because `CallDispatcher` is a single shared instance for the entire gateway (not scoped per-order or per-transaction), dust accumulates across all orders that use multi-hop postdispatch/predispatch routing, growing the drainable balance over time without bound.

### Likelihood Explanation
Likelihood is high given normal, expected usage: the documented intent-gateway calldata feature explicitly encourages routing through DEXes/lending protocols before delivering to the beneficiary [9](#0-8) , which is exactly the pattern (multi-hop swaps) that leaves non-order-asset dust behind. No malicious relayer, prover, or governance actor is needed — the attacker only needs to observe the dispatcher's token balances (public, on-chain) and issue one call directly to `CallDispatcher.dispatch`.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by the registered `IntentGatewayV2` instance(s) that own it (mirroring `HostManager`'s `restrict(caller)` pattern), and/or make the sweep step in `_execute`/`placeOrder` enumerate and reclaim *all* token balances actually touched during calldata execution (e.g., by having the calldata declare every intermediate token it may produce, or by tracking balances of a bounded allow-list of intermediate tokens) rather than only the order's declared input/output asset list.

### Proof of Concept
1. User places (or a solver fills) an order whose `output.call` (or `predispatch.call`) performs a multi-hop swap through the `CallDispatcher`, e.g. `TokenOut -> WETH -> TokenBeneficiaryWants`, leaving a small WETH remainder on the dispatcher because `order.output.assets` only lists `TokenBeneficiaryWants`.
2. `IntentsBase._execute` sweeps only `TokenBeneficiaryWants` per `order.output.assets`; the WETH remainder stays on `CallDispatcher` [10](#0-9) .
3. Any external address (no relationship to the order, no privileges) calls:
   ```solidity
   CallDispatcher(dispatcherAddr).dispatch(
       abi.encode([Call({
           to: WETH,
           value: 0,
           data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, WETH.balanceOf(dispatcherAddr))
       })])
   );
   ```
   This succeeds unconditionally because `dispatch()` has no caller check [1](#0-0) , transferring the stranded WETH to the attacker.
4. Repeated across every order using multi-hop calldata, this generalizes to systematic, permissionless draining of all dust accumulated in the shared `CallDispatcher`.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
