### Title
Blame proof for uncanonical share leaks ECDH key before PoP verification, enabling cross-message decryption - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` emits an `EncryptionKeyProof` (which reveals the ECDH shared key between the recipient's encryption key and the message's per-message key) whenever the decrypted share bytes fail `C::F::from_repr`. This error is returned early, before the queued proof-of-possession (PoP) signature is ever batch-verified. A malicious participant can therefore copy another participant's per-message key `X`, attach a non-canonical ciphertext and a garbage PoP, and force the victim to publish the ECDH key `b*X` — which is also the shared key protecting the honest participant's message — defeating the exact side-effect the PoP was added to prevent.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` loops over `shares` calling `self.encryption.decrypt(...)`, which unconditionally computes `key = ecdh(&self.enc_key, msg.key)` and returns an `EncryptionKeyProof { key, dleq }` for every message (`crypto/dkg/pedpop/src/encryption.rs:487-499`). The PoP is only queued into the `BatchVerifier` under `BatchId::Decryption(l)` — it is not verified yet.

At `crypto/dkg/pedpop/src/lib.rs:479-482`, if `C::F::from_repr(share_bytes.0)` returns `None` (non-canonical scalar bytes), the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` immediately. The `batch` containing the unverified PoP is dropped; `batch.verify_with_vartime_blame()` is never reached. The early-returned `blame` is the full ECDH-revealing proof.

The struct-level comment in `crypto/dkg/pedpop/src/encryption.rs:83-91` documents precisely this attack class: without the PoP, Eve can claim key `X` belonging to Alice's message, and the resulting blame statement "would reveal bX, revealing Alice's message to Bob". The early return reintroduces this bypass: the blame proof is released on the `from_repr` path regardless of whether the PoP over `(context, R, key, from, msg)` (`pop_challenge`, encryption.rs:484) would verify.

The processor propagates this leaked proof verbatim: `processor/src/key_gen.rs:419-425` serializes `blame` into `ProcessorMessage::InvalidShare`, making `key = enc_key_victim * X` public.

### Impact Explanation
Eve (a DKG participant) observes Alice's `EncryptedMessage` to Bob, which carries `key = X` and ciphertext `c_A`. Eve sends Bob `EncryptedMessage { key: X, pop: <invalid>, msg: <all-0xFF / non-canonical scalar bytes> }`. Bob's `calculate_share`:

1. Computes `ecdh(bob_enc_key, X)` — identical to the shared key used for Alice's message — and wraps it in an `EncryptionKeyProof` with a valid DLEq.
2. Fails `from_repr` on the garbage plaintext, returning `Err(InvalidShare { blame: Some(proof) })` before PoP verification.
3. Bob (via the processor) publishes the blame proof.

Anyone can now run `cipher(context, ecdh)` on Alice's ciphertext and recover her plaintext secret share sent to Bob. This is confidential cross-participant information the access-control analog (PoP) was designed to protect; the failed operation still produces the privileged side effect (publication of `bX`), mirroring the Shopify pattern where a rejected cross-organization action still emitted PII.

Severity is Medium rather than High: for PedPoP the plaintext is a single polynomial evaluation `f_Alice(Bob)`, which alone does not recover the group key or Bob's aggregate share, but it does destroy the confidentiality guarantee of the DKG encryption layer for the co-opted message.

### Likelihood Explanation
Reachable by any participant (or anyone able to submit a `shares` entry for a participant index passing `validate_map`, lib.rs:468-472) using only attacker-controlled bytes fed to `EncryptedMessage::read` / `calculate_share`. No cooperation, no valid PoP, and no honest-behavior prerequisite beyond observing a victim's encrypted share message (which is broadcast/relayed by design). Deterministic — the 0xFF-filled ciphertext is guaranteed to fail `from_repr` for any prime field.

### Recommendation
Verify the PoP synchronously (or reorder the batch so `Decryption` failures are resolved) *before* returning any `EncryptionKeyProof`. Concretely, in `calculate_share`, either:

- check `msg.pop.verify(...)` (or run an interim `batch.verify` on `BatchId::Decryption`) prior to decoding `share_bytes` and prior to exposing `blame`, returning `InvalidShare { blame: None }` on PoP failure; or
- withhold the `EncryptionKeyProof` from the error until the batch verifier confirms the `Decryption(l)` statement passed, mapping to `blame: None` otherwise — mirroring the distinction already made between `BatchId::Decryption` (self-explainable, `None`) and `BatchId::Share` (`Some(blame)`).

The non-canonical-scalar early return should be treated as a PoP-verified-only blame path.
