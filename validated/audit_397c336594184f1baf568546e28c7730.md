### Title
Underlying tokens sent directly to `WrappedHyperFungibleToken` (or accrued via WETH-refund fallback) get permanently locked with no recovery path - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken` locks an underlying ERC20 (or WETH) balance in the contract itself as bridging collateral, with no internal per-user ledger — solvency is tracked implicitly by `IERC20(_underlying).balanceOf(address(this))`. There is no `rescue`/`sweep` function for the `_underlying` token anywhere in this contract, its non-upgradeable/upgradeable variants, or `HyperFungibleToken`. Any underlying tokens that reach the contract outside the `send()`/`onAccept()`/`onPostRequestTimeout()` accounting flow — e.g. a plain ERC20 `transfer()` to the contract address, or WETH dust left behind by the `_isWeth` unwrap/re-wrap fallback in `onAccept`/`onPostRequestTimeout` — become permanently stuck, exactly mirroring the referenced `Incentivizer` bug class (M06).

### Finding Description
`send()` pulls the underlying token via `safeTransferFrom` [1](#0-0) , and the only two paths that ever move the underlying token back out are `onAccept` (destination unlock) and `onPostRequestTimeout` (refund), both keyed strictly off the `message.amount` decoded from the ISMP request body [2](#0-1) [3](#0-2) .

Critically:
- There is no accounting variable tracking "tokens legitimately locked via `send()`" versus the contract's raw ERC20 balance — the contract simply assumes `balanceOf(this) == sum of all outstanding sent amounts`.
- Nothing prevents an EOA from calling `IERC20(underlying).transfer(address(wrappedHFT), amount)` directly instead of `send()`. Such a transfer produces no ISMP request, no commitment, and no bookkeeping entry anywhere referencing the sender — the tokens simply sit in the contract's balance forever.
- The WETH-unwrap fallback logic in `onAccept`/`onPostRequestTimeout` — `IWETH(_underlying).withdraw(message.amount)` then attempt native push, and on failure re-wrap and `safeTransfer` — assumes the withdraw/deposit round-trip is exact, but any surplus native ETH pushed to the contract via `receive() external payable {}` [4](#0-3)  that isn't consumed by this exact flow has no exit path either.
- Searching this contract, `HyperFungibleToken.sol`, and the upgradeable variants for a rescue/sweep function for the underlying/native asset returns nothing — unlike `IntentGatewayV2`/`IntentsBase`, which explicitly implement a `SweepDust`/`_sweepDust` mechanism for exactly this class of stray/residual balance [5](#0-4) . `WrappedHyperFungibleToken` has no equivalent for its locked/underlying token.

### Impact Explanation
This falls squarely under the accepted "loss of funds / fund lock" category from the impact gate. Any user (or an integrator's automation) that mistakenly sends the underlying/wrapped asset directly to the bridge contract instead of calling `send()` loses those funds permanently — there is no admin, governance, or user-triggered recovery mechanism in the contract. Because the contract is a live bridge custody contract holding potentially large TVL of the underlying asset, this is a genuine, permanent, unrecoverable fund loss, not a cosmetic issue.

### Likelihood Explanation
High likelihood of occurring organically (as acknowledged by the original report's own rationale — "due to human nature, users may transfer directly ... instead of calling the stake/send function"). No malicious actor, relayer, prover, or governance compromise is required — it is a public-entrypoint-adjacent design gap (the lack of an entrypoint to recover funds) triggerable by any normal ERC20 `transfer` call from any address.

### Recommendation
Add a permissioned or beneficiary-scoped rescue function to `WrappedHyperFungibleToken` (and its upgradeable variant) that can sweep any of the underlying token's balance that exceeds the sum of all currently outstanding locked amounts (i.e., track locked accounting explicitly with a `totalLocked` counter incremented in `send()` and decremented in `onAccept`/`onPostRequestTimeout`, then allow sweeping `balanceOf(this) - totalLocked`), mirroring the `SweepDust` pattern already used in `IntentGatewayV2`/`IntentsBase`.

### Proof of Concept
1. Deploy/observe a live `WrappedHyperFungibleToken` instance for token `X` on chain A.
2. From any EOA, call `IERC20(X).transfer(address(wrappedHFT), 1000e18)` directly (bypassing `send()`).
3. Observe: no `Sent` event is emitted, no commitment/order is created, and `wrappedHFT`'s balance of `X` increases by 1000e18 with no code path in `send()`, `onAccept()`, `onPostRequestTimeout()`, or any other function in the contract that can move those specific 1000e18 tokens back to the original sender or any recipient.
4. Confirm via `grep`/code review that no `rescue`, `sweep`, `recover`, or similar function exists in `WrappedHyperFungibleToken.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`, or `HyperFungibleToken.sol` — the funds are permanently locked in the contract. [6](#0-5)

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }

     * @dev Transfers accumulated protocol dust (surplus tokens) to a specified beneficiary.
     * Called by Hyperbridge governance to sweep protocol-owned tokens that have accumulated
     * from fees, surplus splits, and calldata execution residuals.
     *
     * Supports both native tokens and ERC-20 tokens.
     *
     * @param req The sweep request containing the beneficiary address and token amounts.
     */
    function _sweepDust(SweepDust memory req) internal {
        uint256 outputsLen = req.outputs.length;
        for (uint256 i; i < outputsLen;) {
            TokenInfo memory info = req.outputs[i];
            address token = address(uint160(uint256(info.token)));
            uint256 amount = info.amount;

            if (token == address(0)) {
                (bool sent,) = req.beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(req.beneficiary, amount);
            }
            unchecked {
                ++i;
            }
            emit DustSwept(token, amount, req.beneficiary);
        }
    }
