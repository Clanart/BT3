The broken invariant in the report is: "a batch operation over an attacker-controlled list where one bad item causes the whole batch call to fail, and that failure is silently absorbed rather than surfaced per-item" — leading the victim's tool to treat unresolved/unsafe state as safe. The Desktop equivalent is in the merge-conflict marker counting pipeline.

### Title
Conflict-marker detection failure silently downgrades all unresolved merge conflicts to "resolved," enabling commit of unresolved `<<<<<<<` markers - (File: `app/src/lib/git/status.ts`)

### Summary
`getConflictDetails` wraps the calls that determine which conflicted files still contain literal conflict markers (`<<<<<<<`/`=======`/`>>>>>>>`) in a try/catch that silently swallows *any* error and returns empty results for the *entire* batch of conflicted files, not just the one that failed. [1](#0-0) 

### Finding Description
When a merge/rebase/cherry-pick leaves conflicted files, Desktop computes `conflictMarkerCount` for every conflicted path in one shot via `getFilesWithConflictMarkers`, which runs a single `git diff --check` over the whole repository and regex-parses the combined stdout for `leftover conflict marker` lines: [2](#0-1) 

This is the batch primitive: one `git` invocation's output is parsed to populate a `Map<string, number>` that is later used per-file. `getConflictDetails` calls this (and `getBinaryPaths`) inside a `try { ... } catch (error) { log.error(...) }` block that, on *any* exception, returns an empty map/array for **all** conflicted files in the repository: [3](#0-2) 

Downstream, `parseConflictedState` looks up `conflictDetails.conflictCountsByPath.get(path) || 0` — defaulting to `0` markers whenever the path isn't present in the map (whether because the file was actually clean or because the whole detection call failed): [4](#0-3) 

`conflictMarkerCount === 0` is exactly the signal the rest of the app uses to treat a file as fully resolved: `hasUnresolvedConflicts` returns `false`, `mapStatus` reports `"Resolved"`, the merge-conflicts dialog shows the green checkmark "No conflicts remaining", and `stageManualConflictResolution` treats it as already handled: [5](#0-4) [6](#0-5) [7](#0-6) 

So a repository (fetched/cloned/merged content is fully attacker-controlled) that causes `git diff --check` to throw — e.g., a pathological path, an extremely large or unusual filename, encoding that trips the underlying `dugite`/`git` invocation, or any condition that makes this particular `git()` call reject instead of returning exit code 0/2 — will cause **every** currently-conflicted file in the working directory to be reported as having `0` markers, even files that still contain live `<<<<<<<`/`=======`/`>>>>>>>` text. This mirrors the reward-token bug class exactly: one malicious "item" in a batch (one problematic conflicted file/path) poisons the outcome for all legitimate items in the same batch, and the failure path (the catch block) makes the unsafe case indistinguishable from the safe case (0 markers either way).

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits scenario: the merge/rebase/cherry-pick UI would show conflicted files as "Resolved" with no manual action taken, and nothing stops the user from proceeding to commit. Because the underlying file on disk still contains the literal `<<<<<<<`/`=======`/`>>>>>>>` conflict markers, the resulting commit (and anything pushed from it) would contain broken/unintended content — silently corrupting the commit the user believes is clean. This is analogous to the original report's "solver believes reward is claimable, but the value is actually unrecoverable/corrupted" — here, the user believes the merge is resolved, but the committed content is corrupted.

### Likelihood Explanation
Likelihood is uncertain without confirming a concrete input that makes `git diff --check` (or `getBinaryPaths`'s `git` call inside `getMergeConflictDetails`/`getRebaseConflictDetails`) throw rather than exit 0/2 for at least one path in a batch of many conflicted files. The `successExitCodes` set for `getFilesWithConflictMarkers` only tolerates `[0, 2]`; any other exit code (e.g. from a git internal error triggered by an unusual path/encoding in a maliciously crafted merge commit) throws and hits the catch-all in `getConflictDetails`. I could not fully verify which specific malformed repository state reliably produces such a non-{0,2} exit or a JS-level exception from the `git()` wrapper without running the code, so the exact trigger condition remains unconfirmed.

### Recommendation
Do not fail the whole batch when marker-detection tooling errors: either surface the error to the user and refuse to mark any conflicted file as resolved (fail closed, e.g. default unknown paths to a non-zero/sentinel marker count) rather than defaulting to `0`, or scope failures per-file so a bad path doesn't erase results for the rest of the working directory's legitimate conflicted files.

### Proof of Concept
Not independently verified end-to-end (would require constructing a repository/merge state that makes the `git diff --check` invocation in `getFilesWithConflictMarkers` throw rather than return exit code 0 or 2). Conceptually:
1. Attacker crafts a repository/branch such that merging it locally leaves at least one conflicted file whose path or content causes `git diff --check` to exit with a code other than 0/2, or causes the `git()` wrapper to reject.
2. Victim merges/rebases this branch in Desktop, hits conflicts, and opens the conflicts dialog.
3. `getConflictDetails` → `getMergeConflictDetails`/`getRebaseConflictDetails` → `getFilesWithConflictMarkers` throws; the outer catch in `getConflictDetails` swallows it and returns `{ conflictCountsByPath: new Map(), binaryFilePaths: [] }` for the entire status result.
4. All conflicted files, including ones the attacker intentionally left with real `<<<<<<<` markers, are reported with `conflictMarkerCount: 0` and shown as "Resolved."
5. Victim commits, unknowingly including literal, unresolved conflict-marker text in the resulting commit/push.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
