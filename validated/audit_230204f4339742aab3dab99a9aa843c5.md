### Title
Goroutine/CGO memory leak in `VMWrapper.Create` on wasm compile timeout enables memory-exhaustion DoS via `MsgStoreCode` - (File: sei-wasmd/x/wasm/keeper/vm_wrapper.go)

### Summary
`VMWrapper.Create` wraps `wasmvm.WasmerEngine.Create` (the Rust/CGO wasm module compilation call) with a 15-second timeout. On timeout it returns an error to the caller and releases the mutex, but it never cancels or waits for the background goroutine performing the actual CGO compilation call. This mirrors the CVE-2017-17934 bug class: a "push" (start of a resource-heavy operation, MSLPushImage/compile-and-cache) that lacks a matching, always-executed "pop"/cleanup on the abnormal/slow path, leaking the associated memory.

### Finding Description
`VMWrapper.Create` is: [1](#0-0) 

The function launches a goroutine that calls into the Wasmer CGO engine (`w.WasmerEngine.Create(code)`), which allocates significant native memory to compile and cache the wasm module. The `select` races this goroutine against a 15-second timer:

- If the goroutine finishes first, the timer is stopped and the result is returned normally (the "pop"/cleanup path).
- If the timer fires first, `Create` returns immediately with an error while the goroutine keeps running in the background, uncancelled and unawaited. There is no `context.Context` cancellation plumbed into the underlying CGO call, and the Rust/Wasmer engine has no way to interrupt an in-flight compilation.

Because `defer w.mu.Unlock()` runs as soon as `Create` returns (on the timeout branch), the mutex is released while the abandoned goroutine is still executing the CGO compilation. This means:
1. A caller can immediately submit another `MsgStoreCode` with another slow-to-compile module, acquire the mutex, and spawn yet another leaked goroutine.
2. Each abandoned goroutine holds native (Rust-side) memory for the CGO compilation call until it eventually finishes (or never returns, e.g., if the input is crafted to make compilation pathologically slow), and the final write to the named return values `checksum, err` in the already-returned function is a benign but wasted memory write (also a data race on the named return variables, since the caller already read/returned them).
3. Nothing bounds the number of concurrently in-flight abandoned compilation goroutines; each one consumes CGO/Rust heap memory that is only reclaimed when (if) the underlying `Create` call ever completes.

This is directly analogous to the ImageMagick MSL bug: `MSLPushImage` allocates/pushes state, and mishandled `MSLPopImage`/`ProcessMSLScript` control flow (error/branch paths) fails to release it, leaking memory per malicious input. Here, `VMWrapper.Create`'s timeout branch is the "unmatched pop" — the compile ("push") is started but its cleanup is skipped on the timeout path, and the underlying engine offers no cancellation, so the leak is unbounded per repeated malicious submission.

### Impact Explanation
Any unprivileged CosmWasm contract deployer able to submit `MsgStoreCode` can repeatedly submit wasm binaries engineered to be slow to compile/validate (e.g., pathological module structure that stresses the Wasmer validator/compiler) so that each `VMWrapper.Create` call exceeds the 15s `CreateTimeout`. Each such submission leaves a goroutine (and the CGO/Wasmer native memory it holds) running indefinitely. Because the mutex is released immediately on timeout, the attacker is not rate-limited by `VMWrapper`'s own locking and can pipeline many `MsgStoreCode` submissions, each contributing an unreclaimed native memory allocation. Sustained abuse accumulates unbounded native heap growth on every full node (validators and public RPC nodes alike, since `StoreCode` is processed by all nodes executing the block), eventually leading to out-of-memory conditions and crashing the process — a crash of default-configuration nodes, and potentially a validator halt if it affects consensus nodes uniformly.

### Likelihood Explanation
`MsgStoreCode` is a standard, unprivileged Cosmos message (subject to normal gas metering and any code-upload permissions, but not requiring elevated authority in most deployments), and the timeout path is reachable purely by submitting adversarial wasm bytecode that is slow to compile/validate — no special network position, validator key, or governance action is required. This makes the trigger easily reachable by any transaction sender.

### Recommendation
- Plumb a cancellable context (or equivalent abort signal) through to the underlying `WasmerEngine.Create`/CGO call so that on timeout the compilation is actually aborted and its native memory released, rather than merely abandoned.
- If the Wasmer/CGO layer cannot support cancellation, bound the number of concurrently in-flight background `Create` goroutines (e.g. do not release/reacquire ability to spawn more before prior ones finish, or track and cap outstanding goroutines/memory) so a burst of slow-to-compile submissions cannot cause unbounded concurrent native memory usage.
- Avoid writing to the named return values (`checksum, err`) from the abandoned goroutine after the function has already returned via the timeout branch, to eliminate the underlying data race in addition to the leak.
- Consider rejecting or pre-validating wasm size/complexity heuristics before invoking `Create`, and/or lowering `CreateTimeout` combined with hard-aborting the CGO call, to shrink the exploitable window.

### Proof of Concept
1. Craft a wasm module that is valid enough to reach the Wasmer compiler/validator but is deliberately structured (e.g., extremely large function tables, deeply nested control flow, or other adversarial structures) so that `wasmvm.WasmerEngine.Create` takes longer than 15 seconds to compile.
2. Submit `MsgStoreCode` with this payload. `VMWrapper.Create` (sei-wasmd/x/wasm/keeper/vm_wrapper.go:28-45) times out at 15s, returns an error to the caller, and releases `w.mu`, while the spawned goroutine keeps running the CGO compile in the background, retaining native memory.
3. Repeat step 2 many times in quick succession (each new call can proceed as soon as the mutex is released, i.e., immediately after each timeout). Each repetition leaves another orphaned goroutine/CGO call consuming native memory that is not reclaimed until (if) that particular compile ever finishes.
4. Observe growing resident memory (RSS) on the node processing these transactions as the number of abandoned in-flight compilations increases, eventually leading to OOM and process crash under sustained submission.

Note: I could not fully trace the exact call path from `MsgStoreCode`'s `msg_server.go`/`keeper.go` through to `VMWrapper.Create` within the available tool budget (the final grep for `k.wasmVM.Create` returned no matches, likely due to indexing/method-name differences), so the precise chain from message handling to this function should be verified in a follow-up session; the vulnerable mechanism itself in `vm_wrapper.go` is confirmed directly from the file contents.

func (w *VMWrapper) Create(code wasmvm.WasmCode) (checksum wasmvm.Checksum, err error) {
	w.mu.Lock()
	defer w.mu.Unlock()
	timer := time.NewTimer(CreateTimeout)
	done := make(chan struct{}, 1)
	go func() {
		checksum, err = w.WasmerEngine.Create(code)
		done <- struct{}{}
	}()
	select {
	case <-done:
		timer.Stop()
		return
	case <-timer.C:
		err = errors.New("create wasm code timed out")
		return
	}
}
