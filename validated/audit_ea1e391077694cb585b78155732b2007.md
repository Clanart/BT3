### Title
Unbounded pointer arithmetic on attacker-controlled CLVM atom length in mempool canonical-form check can raise an uncaught `IndexError` on a truncated solution - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_clvm_canonical()` / `is_atom_canonical()` in `chia/full_node/mempool_manager.py` compute an atom's length purely from its header byte(s) and then advance a `offset` cursor by that computed length without first checking whether the remaining buffer actually contains that many bytes. This mirrors the CVE-2016-2177 bug class: deriving an offset/length from attacker-controlled header data and using it for indexing without validating it against the real buffer boundary before dereferencing.

### Finding Description
`is_atom_canonical()` reads the header byte at `offset`, derives `prefix_len` and then loops `prefix_len` times doing: [1](#0-0) 
each iteration does `offset += 1; atom_len |= clvm_buffer[offset]` with no bounds check that `offset < len(clvm_buffer)`. If the CLVM solution bytes end right after a header byte that declares a multi-byte length prefix (e.g. a `0xC0`-class header claiming one more prefix byte but the buffer is truncated there), indexing `clvm_buffer[offset]` raises an unhandled `IndexError`.

Similarly, in the caller `is_clvm_canonical()`: [2](#0-1) 
the returned `atom_len` (computed purely from the header, never validated against remaining buffer size) is added to `offset` and the loop re-reads `clvm_buffer[offset]` on the next iteration (if `tokens_left` has not reached 0), which can also index past the end of the buffer and raise `IndexError` before the final length check at the end of the function is ever reached.

This function is invoked during mempool admission to decide DEDUP eligibility for a spend, per the documented pipeline: "DEDUP eligibility requires canonical CLVM serialization" (`.cursor/context/mempool.md`), i.e. it runs on the serialized solution bytes of coin spends inside an unprivileged submitter's spend bundle before the bundle is otherwise validated by the Rust CLVM engine.

### Impact Explanation
An unprivileged spend-bundle submitter can craft a coin spend whose solution bytes contain a truncated multi-byte atom-length header (a valid, otherwise well-formed CLVM atom header cut short) as an argument. When `MempoolManager` evaluates DEDUP eligibility for that spend, `is_clvm_canonical()`/`is_atom_canonical()` will raise an uncaught `IndexError` instead of returning `False`/rejecting gracefully. Depending on whether this exception propagates uncaught through the admission pipeline, this can disrupt processing of that spend bundle (and, if not isolated per-bundle, other pending mempool work), which matches the accepted "spend-triggered transaction-processing halt" impact category. This is a logic/indexing defect, not a resource-exhaustion issue: the crash is deterministic from a single malformed but small solution, not from resource consumption.

### Likelihood Explanation
Reaching this code only requires submitting an ordinary spend bundle (e.g. via `push_tx`) with a coin spend whose solution encodes an atom with a truncated multi-byte length prefix. No special privileges, signatures over unintended data, or node compromise are required — any actor able to submit a spend bundle to a full node's mempool can attempt to trigger this path. However, I was not able to fully confirm within the available tool budget whether the call site that invokes `is_clvm_canonical()` wraps it in a try/except that would downgrade a raised `IndexError` into an ordinary rejection status — this reduces confidence in whether the exception actually escapes to disrupt node processing versus being silently caught. This should be verified against the exact call site before treating this as a confirmed live DoS.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access in the prefix-reading loop, and in `is_clvm_canonical()` validate `offset + atom_len <= len(clvm_buffer)` before advancing `offset`, returning `False` (not-canonical) instead of allowing an out-of-range index to raise. Additionally confirm/ensure the call site catches any parsing exception from this function and treats it as "not eligible for DEDUP" rather than letting it propagate.

### Proof of Concept
Construct a CLVM solution buffer where the last atom in the encoded list has a header byte in the `0xC0`–`0xFE` range that declares one or more additional length-prefix bytes, but truncate the buffer immediately after that header byte (before the promised prefix bytes and atom body are present), e.g.:
```python
from chia.full_node.mempool_manager import is_clvm_canonical
# 0xC0 header declares 1 extra length-prefix byte + 8-bit length, but buffer ends here
buf = b"\xc0"
is_clvm_canonical(buf)  # raises IndexError instead of returning False
```
Submitting a spend bundle whose coin-spend `solution` bytes contain such a truncated atom as an argument would cause the DEDUP-eligibility canonical check to raise this exception during mempool admission.

**Note on confidence**: I was unable to fully trace, within the available search budget, whether the mempool admission code path that calls `is_clvm_canonical()` catches exceptions from it. This should be verified directly in `chia/full_node/mempool_manager.py` (where `BundleCoinSpend`/DEDUP eligibility is computed) before treating the halt impact as fully confirmed. [3](#0-2)

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value


def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
