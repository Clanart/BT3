### Title
Ineffective placement of the `--` end-of-options terminator in `checkoutBranch` argument construction - (File: app/src/lib/git/checkout.ts)

### Summary
`checkoutBranch` builds its `git checkout` argv via `getBranchCheckoutArgs`, which appends the `--` end-of-options marker as the *last* element of the array, after the untrusted `branch.name` (and, for remote branches, after `'-b'`/`branch.nameWithoutRemote`) rather than *before* them: [1](#0-0) 

The resulting argv for a local branch is `['checkout', branch.name, '--']`, and for a remote branch `['checkout', branch.name, '-b', branch.nameWithoutRemote, '--']`: [2](#0-1) 

A trailing, empty `--` provides no protection to the tokens that precede it — git (like any POSIX-style argv parser) evaluates options left-to-right, so a value that begins with `-`/`--` and is placed *before* `--` is still eligible to be parsed as an option, not an operand. The invariant the review asks about ("attacker text reaches the child process only as an inert operand, never as an option") is therefore **not enforced by this code**; it is enforced only if `branch.name` itself is guaranteed, by something else, to never start with `-`.

### Finding Description
`branch.name` objects reaching `checkoutBranch` are constructed in two ways:
1. From user-typed input in Create Branch / Rename Branch dialogs, which is passed through `sanitizedRefName`, an explicit function that strips a leading `-`/`+` from proposed names — showing the Desktop team is aware that leading-dash ref names are dangerous: [3](#0-2) [4](#0-3) 

2. From `getBranches` in `for-each-ref.ts`, which parses raw `git for-each-ref` output (i.e., real refs that already exist in the repository, e.g. `refs/heads/*` and `refs/remotes/*`) and constructs `Branch` objects directly from `%(refname:short)`/`%(refname)` with **no sanitization at all**: [5](#0-4) 

These `Branch` objects are exactly what flow into `checkoutBranch` (e.g. via `_checkoutBranch` in `app-store.ts`, branch dropdown, PR checkout, etc.), and they bypass `sanitizedRefName` entirely.

The only thing preventing exploitation is whatever validation git itself performs at the moment a ref is created (during `clone`/`fetch`, remote-tracking ref creation, or resolving a remote's default `HEAD` symref into a local `refs/heads/<name>` at clone time). I was not able to confirm from the codebase whether git's underlying ref-creation paths (as opposed to `git branch <name>`, which does reject `-`-prefixed names) uniformly reject a refname component beginning with `-` when it originates from a fetched/cloned remote. This means the security of `checkoutBranch` against a malicious remote that advertises a ref/HEAD name starting with `-` currently depends entirely on git's own internal ref-name validation during fetch/clone, not on any check inside GitHub Desktop's own argv construction.

### Impact Explanation
If a remote-supplied ref name (e.g., a maliciously named branch that becomes a repository's default branch on clone, or another mechanism by which an attacker-influenced ref name reaches a `Branch` object) can bypass `sanitizedRefName` and begin with `-`/`--`, then `checkoutBranch`'s argv places it before the (ineffective) `--`, letting git interpret it as an option to `git checkout` (e.g. `--upload-pack=...`, or other flags), potentially leading to spawning arbitrary programs or corrupting the checkout state. This would match the "Critical" impact class described in scope (git executing attacker-chosen options).

### Likelihood Explanation
Likelihood is uncertain without being able to execute git to confirm whether its own fetch/clone-time ref validation rejects leading-hyphen ref components (this is enforced by `git branch`'s `strbuf_check_branch_ref`, but I could not verify it applies uniformly to refs created via fetch/clone/update-ref). Regardless of that external dependency, the code in `checkout.ts` itself does not implement the operand-isolation invariant correctly — the `--` separator is placed in a position where it cannot protect the preceding tokens, which is a structural weakness independent of whether it's currently reachable by a specific attack path.

### Recommendation
- Move the `--` separator to precede the untrusted branch/ref tokens instead of following them, e.g. build args as `['checkout', '--', branch.name]` for the simple case, and for the `-b <name>` remote-branch-creation case, ensure `nameWithoutRemote` cannot be misinterpreted (it already is safe as the literal value of `-b`, but should still be defensively validated).
- Apply the same sanitization/rejection used in `sanitizedRefName`/`testForInvalidChars` (or an equivalent "does not start with `-`" check) to `Branch` objects sourced from `getBranches`/`for-each-ref`, not just to user-typed branch names, before they are used to build any git argv.
- Add a regression test in `app/test/unit/git/checkout-test.ts` that constructs a `Branch` whose `name` (and `nameWithoutRemote`) begins with `-`/`--` and asserts it is checked out safely (treated as a literal ref) rather than being interpreted as a git option.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}
