## Title
Hunk-count validation and file reassembly use two independently-drifting conflict-marker parsers, letting a crafted merge conflict get silently committed with unresolved markers and un-reviewed raw content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot conflict-resolution feature parses conflict markers twice with two different, hand-rolled scanners: `extractConflictHunks` (used to build the prompt and to compute the "expected hunk count" gate) and the marker walk inside `reassembleResolvedFile` (used to splice the model's resolutions back into the on-disk file). These two scanners treat a malformed/truncated conflict block differently: the counting scanner silently drops it from the hunk count, while the reassembly scanner copies the dangling `<<<<<<<` marker and everything that follows it through **verbatim** into the file that is written to disk and staged for commit. Because the validation gate (`validateResolutionPaths`) only checks that the model returned the hunk count computed by the *counting* scanner, a file shaped to exploit this divergence passes validation while the actually-written "resolved" file still contains an unresolved conflict block, silently corrupting what the user commits.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-278`) walks a conflicted file and, for each `<<<<<<<` marker, requires a subsequent `>>>>>>>` to close the hunk. If it never finds a closing marker, the hunk is dropped entirely: [1](#0-0) 
This count (`hunks.length`) becomes `IFileConflictContext.hunks`, which is what `buildConflictContext` sends to the model and what `validateResolutionPaths` uses as the required number of resolutions per file: [2](#0-1) 

Separately, `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) re-scans the **same raw file content** independently to splice the model's per-hunk resolutions back in. When it encounters a marker block that lacks a separator or a closing `>>>>>>>`, it does *not* drop it — it copies the `<<<<<<<` line (and, by falling through to the generic line-copy branch, everything that follows) straight into the result: [3](#0-2) 

Consider a file with two conflict regions where the first is well-formed and the second is truncated/malformed (no `=======`/`>>>>>>>` before EOF or before an unrelated line that only coincidentally looks like a marker). `extractConflictHunks` returns `hunks.length === 1` (it silently discards the malformed block), so the model is only required to (and does) return one resolved hunk, which satisfies `validateResolutionPaths`. But `reassembleResolvedFile` walks the identical raw content and, upon reaching the second, malformed block, falls into the "copy through as regular content" branch — permanently baking the dangling `<<<<<<<` marker and the unresolved raw text into the reassembled file that `reassembleResolutions` returns as `IFileResolution.resolvedContent` (`app/src/lib/copilot-conflict-resolution.ts:609-642`), which is what the app subsequently writes to disk and stages.

No code path cross-checks that the number of marker blocks `reassembleResolvedFile` actually walks over matches the number of hunks the model resolved; the two scanners are structurally distinct (one aggregates diff3 base sections and discards unmatched hunks outright, the other only recognizes the standard `<<<<<<<`/`=======`/`>>>>>>>` triad and falls back to raw copy-through on any mismatch) and can diverge on crafted or malformed input.

### Impact Explanation
This breaks the invariant that "the model's output plus the untouched non-conflicted lines make up the fully resolved file" (documented as the design intent in the function's own comment: "This guarantees that all non-conflicted code is preserved exactly"). Instead, a malformed/truncated block from the **attacker-controlled side of a merge** (a branch or PR the victim merges) can be smuggled through untouched, complete with a literal `<<<<<<<` conflict marker, directly into the commit the user makes via Desktop's AI conflict-resolution flow. This is silent corruption of what the user commits and, if pushed, propagates broken/marker-laden source into the shared repository without any warning, error, or visible diff review forcing the user to notice the leftover marker before finalizing.

### Likelihood Explanation
The attacker precondition is realistic and matches the valid-impact scope: an attacker who controls one side of a merge (a branch/PR/fetched ref) can shape file content so that, after git inserts conflict markers, one region ends up malformed relative to the standard triad while another remains well-formed in the same file — e.g. by including content that itself contains a line beginning with seven `<` or a truncated marker sequence, or by exploiting diff3/edge-case merge outputs. The feature is exercised whenever a user invokes Copilot-assisted conflict resolution on a merge/rebase/cherry-pick, which is an ordinary, unprivileged user action requiring no special local access. I was not able to trace, within the available tool budget, whether the write path forces a mandatory diff review before staging/committing the reassembled content, so the exact user-facing friction before the corrupted content lands in a commit is not fully confirmed — this should be verified before deciding severity precisely.

### Recommendation
Make `reassembleResolvedFile` reuse the exact same marker-parsing logic as `extractConflictHunks` (ideally a single shared parser) so hunk counting and hunk splicing can never disagree, and have it assert (throwing a `CopilotValidationError`) if the number of well-formed blocks it walks does not exactly equal `hunkResolutions.length`, rather than silently falling back to copying raw, unresolved marker content into the output. Additionally, scan the final reassembled content for leftover conflict-marker patterns (`<{7}`, `={7}`, `>{7}`) before writing/staging it, and refuse to apply the resolution if any are found.

### Proof of Concept
Not independently executed against a live build (no filesystem/terminal access in this environment), but derivable directly from the two functions:

1. Author a merge-conflicted file with two marker regions:
```
context
<<<<<<< HEAD
ours-1
=======
theirs-1
>>>>>>> feature
middle
<<<<<<< HEAD
ours-2 (attacker crafts this branch/file so the merge tool never closes this block properly, e.g. no trailing >>>>>>> before EOF)
```
2. `extractConflictHunks` returns `hunks.length === 1` (only the first, well-formed block; the second is discarded per lines 240-242 of `copilot-conflict-context.ts`).
3. `validateResolutionPaths` therefore requires exactly 1 hunk resolution from the model, which the model supplies.
4. `reassembleResolvedFile` walks the same raw file: it correctly splices the model's resolution into the first block, but upon reaching the second `<<<<<<<` line (`hasSeparator=false`, `closingIndex=-1`), takes the "malformed marker — copy through as regular content" branch [3](#0-2) , leaving the literal `<<<<<<<` line and all subsequent raw "ours-2" content in the final `resolvedContent` that is returned to the write path. [4](#0-3)
