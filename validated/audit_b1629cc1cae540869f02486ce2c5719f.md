### Title
NFT Royalty Underpayment via Chained Truncated Integer Division in Offer Royalty Calculation - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`NFTWallet.make_nft1_offer` and `compute_royalty_amount` compute NFT creator royalties using two sequential floor (`//`) divisions: first splitting the fungible trade amount across `offer_side_royalty_split` NFTs to derive `trade_prices`, and second applying `percentage / MAX_ROYALTY_BASIS_POINTS` to that already-truncated value. This chained truncation is structurally the same bug class as the reported Locke.sol issue (`rewards = a*b/c/d` truncating twice), and it causes the NFT royalty recipient to systematically receive less than the mathematically owed royalty, with worse loss the more NFTs are bundled into a single offer/request or the smaller the fungible amount relative to `royalty_split`.

### Finding Description
In `chia/wallet/nft_wallet/nft_wallet.py`, when building a multi-NFT offer: [1](#0-0) 

`amount` (the fungible payment amount) is floor-divided by `offer_side_royalty_split` (count of royalty-bearing NFTs on the offer side) to get a per-NFT `trade_price`. This already discards the remainder of the division.

That truncated `trade_price` is then fed into `compute_royalty_amount`: [2](#0-1) 

which performs a *second* truncating division: `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`. Because `royalty_split` is applied again inside `compute_royalty_amount` (called with `request_side_royalty_split`), and the numerator has already lost precision from the first division in `trade_prices`, the two truncations compound. The equivalent standalone helper `royalty_calculation` has the identical pattern: [3](#0-2) 

This mirrors the reported Locke.sol bug class precisely: `reward = a * b / c / d` where each `/` truncates independently rather than being algebraically combined (e.g., `a*b*percentage // (c*d*MAX_ROYALTY_BASIS_POINTS)`), so the final result is strictly less than or equal to the mathematically correct value, and can truncate fully to zero as demonstrated by the existing test: [4](#0-3) 

### Impact Explanation
The NFT creator (royalty recipient) is a third party who has no ability to influence or verify the offer construction happening in the taker's/maker's wallet; they can only observe the final royalty payment enforced on-chain via the `-10` condition and `NFT_TRANSFER_PROGRAM_DEFAULT` puzzle. Because the royalty amount is computed client-side with compounding truncation before being embedded into the spend bundle's condition list and puzzle-announcement assertions, any truncation loss is baked into the on-chain settlement and is unrecoverable — the royalty coin created is smaller than intended, and there is no re-computation or correction step. For small `trade_price` values (many NFTs bundled, or low percentage, or small fungible amount), the royalty can round down to zero mojos even though a non-zero royalty was configured, directly costing the royalty recipient value with no recourse. This satisfies "reward redirection" impact in the sense that value that should flow to the royalty address is instead retained (never created) as change/excess elsewhere in the transaction.

### Likelihood Explanation
This triggers on any standard, unprivileged flow: any wallet user constructing or taking an offer for a royalty-bearing NFT via `NFTWallet.make_nft1_offer` (offers/CLI/RPC `take_offer`/`create_offer_for_ids`) that bundles more than one royalty NFT, or uses a percentage/amount combination whose product is not evenly divisible. No malicious peer, node, or special privilege is required — it is a deterministic arithmetic property of the offer construction code exercised by ordinary trading activity, and is even implicitly acknowledged by the codebase's own `test_small_amount_truncates_to_zero` test, which documents the truncate-to-zero behavior as expected rather than flagging it as a shortfall relative to the mathematically-owed royalty.

### Recommendation
Combine the multiple divisions into a single division at the end of the full numerator product to minimize truncation loss, e.g. compute royalty as `(abs(offered_amount) * percentage) // (royalty_split * MAX_ROYALTY_BASIS_POINTS)` instead of chaining `// royalty_split` and `// MAX_ROYALTY_BASIS_POINTS` (and instead of pre-truncating `trade_prices` via `amount // offer_side_royalty_split` before the percentage is even applied). Round in the royalty recipient's favor (ceiling) if any rounding must occur, or explicitly document/enforce a minimum bundle amount so truncation cannot fully zero out a configured non-zero royalty.

### Proof of Concept
Using `NFTWallet.make_nft1_offer` semantics as in `compute_royalty_amount`/`trade_prices` (chia/wallet/nft_wallet/nft_wallet.py:67-75, 896-902):

1. Offer bundles 3 royalty-bearing NFTs against a single requested fungible amount of 100 mojos (`offer_side_royalty_split = 3`).
2. `trade_prices` computes `100 // 3 = 33` per NFT (loses 1 mojo already).
3. Suppose royalty `percentage = 250` (2.5%). `compute_royalty_amount(33, royalty_split=1 (already split), percentage=250)` → `33 * 250 // 10000 = 8250 // 10000 = 0`.
4. The royalty recipient receives 0 mojos even though `100 * 250 // 10000 = 2` mojos would be mathematically owed per NFT under the correct combined formula, and even the exact (non-compounded) per-NFT-split value `33*250/10000 ≈ 0.825` would still be non-zero versus the compounded double-truncation.
5. As NFT count in `royalty_split` increases or fungible amount decreases, the loss ratio grows, and can be repeated/observed via `test_small_amount_truncates_to_zero` (chia/_tests/wallet/nft_wallet/test_nft_royalty.py:42-44), which already documents zero-royalty truncation as accepted behavior.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
