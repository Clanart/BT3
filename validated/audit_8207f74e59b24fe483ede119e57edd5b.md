### Title
Unhandled `AssertionError` in `compute_spend_hints_and_additions()` on malformed `CREATE_COIN` puzzle-hash argument - (File: `chia/wallet/util/compute_hints.py`)

### Summary
`compute_spend_hints_and_additions()` extracts the `CREATE_COIN` puzzle-hash argument via `condition.at("rf").atom` and immediately asserts it is not `None` without any prior type validation of the CLVM node (atom vs. pair), analogous to the OpenSSL PKCS#12 bug where an `ASN1_TYPE` union member is read without checking the discriminating type tag first.

### Finding Description
In `chia/wallet/util/compute_hints.py`: [1](#0-0) 

```
if op != ConditionOpcode.CREATE_COIN.value:
    continue
cost += ConditionCost.CREATE_COIN.value

rf = condition.at("rf").atom
assert rf is not None

coin: Coin = Coin(cs.coin.name(), bytes32(rf), uint64(condition.at("rrf").as_int()))
```

`condition.at("rf")` returns whatever CLVM node occupies that path in the `CREATE_COIN` condition list — it can legally be either an atom or a cons pair (a list), since CLVM does not statically distinguish these. The code accesses `.atom` on that node and then blindly `assert`s it is non-`None`, exactly mirroring the ASN1_TYPE bug: the "type" (atom vs. pair) of the underlying CLVM node is never checked before the value is dereferenced as the expected representation. Any inner puzzle output whose `CREATE_COIN` puzzle-hash slot is a pair (e.g. `(51 (1 . 2) 100)`) instead of an atom causes `.atom` to be `None` and the bare `assert` to raise an uncaught `AssertionError`.

This function is called from `wallet_state_manager.py`, `cat_wallet.py`, `did_wallet.py`, `trade_manager.py`, `offer.py`, and `cr_cat_wallet.py` [2](#0-1)  during coin/offer/spend-bundle processing, i.e., on puzzle reveals and solutions that are attacker-controlled inputs (incoming coin spends synced by the wallet, or coin spends embedded in an offer file a counterparty presents to a wallet user).

### Impact Explanation
An unprivileged party can craft a coin spend (or an offer) whose inner puzzle emits a `CREATE_COIN` condition with a non-atom (pair) puzzle-hash argument. When a victim wallet processes this spend during sync or offer inspection, `compute_spend_hints_and_additions()` raises an unhandled `AssertionError` (Python's equivalent of a hard crash/invalid dereference) instead of a graceful validation error. Depending on the calling context and exception handling upstream, this can halt wallet transaction processing for that spend/offer, denying service to the wallet — the same "spend-triggered transaction-processing halt" class of impact called out as in-scope, analogous to the OpenSSL DoS.

### Likelihood Explanation
Reaching this code path only requires constructing a spend (puzzle + solution) that outputs a `CREATE_COIN` condition with a pair in the puzzle-hash slot — trivially achievable in CLVM (e.g., `(51 (q . 1) 100)`), and then getting a wallet to run/parse it via normal sync, CAT/DID coin tracking, or offer construction/acceptance flows. No privileged access or network position is required, matching "Likely" reachability from a wallet-facing surface.

### Recommendation
Validate `condition.at("rf")` is an atom before use and raise a proper `ValidationError`/`Err.INVALID_CONDITION` (matching the existing error-handling style already used elsewhere in this function) instead of relying on a bare `assert`, e.g.:
```python
rf = condition.at("rf").atom
if rf is None:
    raise ValidationError(Err.INVALID_CONDITION, "CREATE_COIN puzzle hash must be an atom")
```
Apply the same explicit atom/pair validation pattern to any other `.at(...).atom` access in this and related condition-parsing helpers that currently rely on bare `assert` rather than raised, catchable errors.

### Proof of Concept
1. Construct a `CoinSpend` whose puzzle, when run with its solution, outputs:
   `(51 (81 . 82) 100)` — a `CREATE_COIN` condition (opcode 51) where the puzzle-hash argument is the cons pair `(81 . 82)` rather than a 32-byte atom.
2. Pass this `CoinSpend` to `compute_spend_hints_and_additions()` (directly, or indirectly by having the wallet sync a coin created by such a puzzle, or by embedding it in an `Offer` that a wallet user inspects/accepts via `trade_manager.py`/`offer.py`).
3. `condition.at("rf").atom` evaluates to `None` because the node is a pair, not an atom.
4. `assert rf is not None` raises an unhandled `AssertionError`, aborting the calling wallet operation instead of returning a controlled validation error. [3](#0-2)
