### Title
Unbounded non-compoundable reward sweep in `ManualCompound.compound()` allows theft of other users' stranded token balances - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` refunds "non-compoundable" reward tokens by sweeping the **entire current contract balance** of any token listed in the caller-supplied `_rewards` array, rather than only the amount actually claimed for `msg.sender` in that transaction. Since the contract can legitimately hold a non-compoundable token balance belonging to another user (left behind by a prior `compound()` call whose `_rewards` list did not include that token), any unprivileged caller can later name that token in their own `_rewards` argument and drain the stranded balance to themselves.

### Finding Description
`compound()` at [1](#0-0)  does:
```
IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
for(uint256 i; i < _lps.length; i++) {
    ...
    if (!compoundableRewards[_rewards[i][j]]) {
        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
        if (rewardBalance > 0)
            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
    }
}
```
`multiclaimOnBehalf` claims rewards for `_account = msg.sender` (the compound caller) but the underlying `BaseRewardPool.getReward()` unconditionally sends **all** of that account's `rewardTokens`, not just the tokens named in the caller's `_rewards` array ( [2](#0-1) ). The `_rewards` array is only used afterward, in `ManualCompound`, to decide which received tokens to sweep back as "non-compoundable." If a prior caller's `_rewards[i]` list omits a token that `getReward()` still transferred to `ManualCompound` (e.g., because it was newly added, or simply left out of the client-constructed array), that token's balance stays in the `ManualCompound` contract after their transaction completes — it is not "interrupted" mid-transaction (EVM calls are atomic), but rather **left stranded by design due to the mismatch between what `getReward()` transfers and what the refund loop checks**.

A subsequent unprivileged attacker can then call `compound()` supplying any valid staking-token pool in `_lps` (even one where they have zero pending reward) and specify the stranded token address in the corresponding `_rewards[i]` entry. Because `!compoundableRewards[token]` is true and `balanceOf(address(this))` reflects the *entire* stranded balance (which may include another user's funds, not just what the attacker's own claim generated this transaction), the full balance is swept to the attacker via `safeTransfer(msg.sender, rewardBalance)`.

Existing checks (`compoundableRewards` mapping, `onlyOwner` admin functions, `_onlyCompounder` modifier on `multiclaimOnBehalf`) do not prevent this: `_onlyCompounder` only restricts who may call `multiclaimOnBehalf` (satisfied automatically since `ManualCompound` itself is the registered compounder), but places no restriction on which tokens an arbitrary caller can list in `_rewards`, nor does it tie the refund amount to the amount actually claimed in the current call.

### Impact Explanation
This is theft of unclaimed yield: another staker's accrued non-compoundable reward token, legitimately owed to them but stranded in `ManualCompound`, can be swept in full by an unrelated attacker who has no stake in that reward and did not earn it. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
The precondition — a non-compoundable token balance sitting in `ManualCompound` that wasn't included in a previous caller's `_rewards[i]` list — is plausible in normal operation: any user whose `_rewards` array (constructed by a wallet, script, or manually) does not perfectly enumerate every reward token being distributed for the pools they claim from will unintentionally strand tokens in the contract. No special privileges, capital, or admin misconfiguration are required by the attacker; they only need to observe a nonzero balance of a non-compoundable token on the contract and call `compound()` naming it. This is fully repeatable for any token that becomes stranded in the future.

### Recommendation
Track the amount of each reward token actually received by `ManualCompound` during the current `multiclaimOnBehalf` call (e.g., balance-before/balance-after per token, or have `multiclaimOnBehalf`/`getReward` return exact amounts) and refund only that delta to `msg.sender`, instead of sweeping `balanceOf(address(this))`. Alternatively, maintain a per-user accounting ledger for un-swept non-compoundable rewards so stray balances cannot be claimed by an uninvolved caller.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, a `BaseRewardPool` with two reward tokens `A` (added later to `compoundableRewards`) and `B` (kept non-compoundable), and `ManualCompound` registered as the pool's compounder.
2. Have User1 stake into the pool and accrue rewards in both `A` and `B`.
3. Have User1 call `ManualCompound.compound(_lps=[pool], _rewards=[[A]], ...)` — note `B` is intentionally omitted from `_rewards[0]`. Confirm via `getReward()`'s behavior that `B` was nonetheless transferred to `ManualCompound` (assert `B.balanceOf(ManualCompound) > 0` after the call, while User1's `B` balance did not increase).
4. From an attacker EOA with no stake (or a pool with zero pending reward), call `ManualCompound.compound(_lps=[pool], _rewards=[[B]], ...)`.
5. Assert attacker's `B` balance increases by the full stranded amount (User1's reward), and `ManualCompound`'s `B` balance drops to zero — confirming theft of another user's unclaimed yield.
