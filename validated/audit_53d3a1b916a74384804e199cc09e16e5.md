### Title
Silent, unconfirmed rewrite of a repository's git remote URL from an untrusted GitHub API `clone_url` field — ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The External Report's core invariant break is: a value that is fully controlled by an untrusted, remote-served object (the snap's shared config, mutated via `fil_configure`) is written into shared application state and *acted upon without a fresh, explicit user confirmation*, later influencing security-relevant behavior (message signing / network shown to the user). The closest verifiable analog in GitHub Desktop is `updateRemoteUrl()` in [1](#0-0) , which silently overwrites the repository's `origin` remote URL using the `clone_url` field taken directly from a GitHub API repository object, with no user prompt, whenever the repository's GitHub metadata is refreshed.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches a repository object from the GitHub API (`api.fetchRepository(owner, name)`) and, if a `gitHubRepository` association already exists, passes the raw API response straight into `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [2](#0-1) 

Inside `updateRemoteUrl`, the only checks performed before rewriting the local remote are: (1) that the *protocol* (http vs ssh) of the old and new URL match, and (2) that the currently configured remote still equals the previously cached `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited it). If both hold, and the new `clone_url` differs, the function calls `gitStore.setRemoteURL(...)` and silently rewrites `origin`'s URL — no dialog, no diff shown, no user acknowledgment: [3](#0-2) 

Critically, `protocolsMatch` only compares the URL *scheme*, not the host or path. It does not check that the new host is the same GitHub/GHES host, or that the repo identity (owner/name) is unchanged in any authenticated sense beyond string equality of the previously stored `cloneURL`. There is no user-facing confirmation step comparable to the one used elsewhere in the codebase for the conceptually identical "upstream remote differs from expected" case — `UpstreamAlreadyExists`, which explicitly asks the user "Would you like to update the remote to use the expected URL?" before changing a remote: [4](#0-3) 

This asymmetry is the broken invariant: for the *upstream* (fork parent) remote, Desktop asks the user before rewriting a remote URL; for the *origin* remote synced from `apiRepo.clone_url`, Desktop rewrites it automatically and silently as part of routine background refreshes (e.g. `refreshSelectedRepositoryAfterAccountChange`, called on account sign-in changes): [5](#0-4) 

The attacker primitive matches the "attacker controls a GitHub API object" category from the Valid Impact list: any party who can influence what `GET /repos/{owner}/{name}` returns for a repository the user has already added to Desktop — a malicious/compromised GitHub Enterprise Server instance, an on-path attacker against a GHES endpoint (many enterprise setups use custom/self-signed certs and users are trained to accept exceptions), or simply the repository owner renaming/transferring the repo to a different clone URL that keeps the same scheme — can cause the field `clone_url` to point anywhere, and Desktop will push that value directly into `git remote set-url origin <value>` without the user ever seeing or approving the new destination.

### Impact Explanation
Once `origin`'s URL is silently rewritten, all subsequent "Push"/"Fetch"/"Pull" actions the user performs through the normal Desktop UI transparently target the attacker-controlled remote instead of the repository the user believes they are working with. This is exactly "silent corruption of what the user commits or pushes": commits the user believes are being pushed to their trusted repository are instead sent to a different destination chosen by whoever controls the API response. Since Desktop also negotiates credentials/tokens for git network operations against the configured remote host, redirecting the remote to an attacker-controlled host can also enable credential/token exfiltration during the push/fetch handshake (the account's OAuth token or credential helper output would be presented to whatever host `origin` now points at, if it is same-protocol/GHES-like enough to be accepted).

### Likelihood Explanation
The refresh path is reached through routine background application flows already present in the code (`refreshSelectedRepositoryAfterAccountChange`, invoked on account changes) — not through unusual, contrived, or privileged user action, and requires no local access, admin rights, or leaked credentials. The only precondition is that an attacker can affect the content of the GitHub API repository object returned for a repo the victim already has linked in Desktop, which is plausible for GHES admins, on-path attackers against enterprise endpoints, or a repository owner performing a rename/transfer. I could not fully verify from the indexed code every trigger path that calls `repositoryWithRefreshedGitHubRepository` (9 references were found in `app-store.ts` but not all were retrieved), so the exact frequency/triggers of this refresh in the running app is not fully confirmed from local evidence alone.

### Recommendation
Do not silently rewrite `origin`'s remote URL based on an API-provided `clone_url`. At minimum, apply the same pattern already used for the upstream-remote case (`UpstreamAlreadyExists`): show a confirmation dialog displaying both the current and proposed remote URL and require explicit user approval before calling `setRemoteURL`. Additionally, validate that the new URL's host matches the account's configured endpoint (`account.endpoint`) rather than only checking protocol equality, to prevent a same-protocol/different-host redirection from being silently accepted.

### Proof of Concept
1. User adds a repository to GitHub Desktop that is linked to a GitHub/GHES repo, `origin` = `https://good-host/org/repo.git`, matching the cached `gitHubRepository.cloneURL`.
2. An attacker who controls the GHES server (or is on-path for a GHES endpoint with a custom cert, or is the repo owner performing a hostile rename/transfer) causes `GET repos/{owner}/{name}` to return `clone_url: "https://attacker-host/org/repo.git"` (same `https` scheme).
3. Desktop performs a routine refresh (e.g. `refreshSelectedRepositoryAfterAccountChange` on sign-in/account switch) calling `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`, per [6](#0-5) .
4. `updateRemoteUrl` passes both guard checks (`protocolsMatch` true, `remoteUrlUnchanged` true, `urlsMatch` false) and silently executes `git remote set-url origin https://attacker-host/org/repo.git`, per [7](#0-6) , confirmed by the existing unit test asserting this exact automatic rewrite behavior: [8](#0-7) .
5. The user's next "Push" in Desktop's UI silently sends commits (and negotiates credentials) to `attacker-host` with no warning shown.

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
