### Title
Distribution precompile `rewards()` view method omits the non-payable/value-refund check, permanently stranding SEI sent with the call - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile (`0x0000000000000000000000000000000000001007`) enforces `pcommon.ValidateNonPayable(value)` (which reverts the whole call, undoing the EVM value transfer) on every state-changing method, and refunds the payer via `pcommon.HandlePaymentUsei` on the one method that legitimately accepts value. The `rewards` view method, however, is dispatched without either check, so a call to it that carries non-zero `msg.value` succeeds normally while the transferred usei/wei is never returned to the caller and the precompile exposes no function to reclaim it.

### Finding Description
In `Execute`, the dispatch switch calls `p.rewards(ctx, method, args)` for `RewardsMethod`, notably not passing `value` at all, unlike every other view method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`), which at least receive `value` as a parameter: [1](#0-0) 

All other state-mutating handlers explicitly call `pcommon.ValidateNonPayable(value)` (directly or via `p.validateInput`), which causes the call to revert (and thus rolls back any attempted value transfer) if `msg.value != 0`: [2](#0-1) [3](#0-2) 

The generic non-payable and payment-handling helpers used across all precompiles show the intended pattern: either reject the value outright, or explicitly refund it to the payer via `bankKeeper.SendCoins` back to the caller: [4](#0-3) 

Because EVM `CALL` semantics transfer `msg.value` (converted to usei/wei) into the precompile's associated account balance before the precompile logic executes, and `rewards()` neither reverts on non-zero value nor refunds it, any usei/wei sent alongside a `rewards()` call is permanently credited to the distribution precompile's account with no code path that returns or sweeps it back to the sender. The integration test suite for this precompile explicitly documents this exact gap: `rewards()` is called out as "the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)", and the test author deliberately skipped writing a "view rejects value" test for it: [5](#0-4) 

### Impact Explanation
Any unprivileged EVM transaction sender who calls `rewards()` on the distribution precompile (`0x1007`) with non-zero `value` causes that SEI amount to become permanently stuck at the precompile's address — it is not refunded, not applied to any protocol logic, and there is no owner/admin sweep function for this balance. This is a direct, unrecoverable loss of user funds triggerable by any public RPC client, matching the concrete-fund-loss/freezing criteria.

### Likelihood Explanation
Trivial to trigger: any account that can send an EVM transaction can call `rewards(address,string)` (or any other read method routed the same way) on `0x1007` while attaching a non-zero `value`. No special privileges, precompile whitelisting, or unusual state are required — only a mistaken or naive dApp/user sending value with what looks like a "free" view call.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` at the start of `p.rewards(...)` (mirroring the check already used for every other handler in this precompile and consistent with the pattern in `pcommon.ValidateNonPayable`/`HandlePaymentUsei`), so any accidental value sent with a call to `rewards()` reverts the transaction instead of being silently stranded. As a broader hardening measure, audit all precompiles for view/query methods that receive `value` but skip the non-payable check, and consider enforcing it centrally in the dynamic-gas precompile dispatcher rather than per-method.

### Proof of Concept
1. Deploy/interact with the distribution precompile ABI at `0x0000000000000000000000000000000000001007`.
2. Send an EVM transaction calling `rewards(delegatorAddress, validatorAddress)` with `value: 1000000000000000000` (1 SEI in wei) using an associated EVM account.
3. Observe the transaction succeeds (status = 1) and returns the expected reward data, exactly like the existing test flow that exercises `rewards()`: [6](#0-5) 
4. Query the caller's SEI balance before and after: the sent value is debited from the caller and never refunded, because `p.rewards` receives no `value` argument and performs no refund, unlike `withdrawValidatorCommission`, `setWithdrawAddress`, etc., which either reject or account for the value.
5. There is no admin/owner function elsewhere in the precompile or module to reclaim the amount credited to the precompile's account, resulting in a permanent loss for the caller.

func ValidateNonPayable(value *big.Int) error {
	if value != nil && value.Sign() != 0 {
		return errors.New("sending funds to a non-payable function")
	}

	return nil
}

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account

		return sdk.Coin{}, err
	}
