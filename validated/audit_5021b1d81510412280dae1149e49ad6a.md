### Title
Webhook `shop_domain` (recipient identity) is Not Bound to the HMAC Signature, Enabling Cross-Shop Webhook Replay - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The Wormhole VAA bug pattern (missing chain-ID / receiver-address binding, allowing a validly-signed message to be replayed against an unintended recipient) has a direct analog in `shopify_app`'s webhook verification flow. `ShopifyApp::WebhookVerification#verify_request` only authenticates the **raw body bytes** against the app's HMAC secret; it never authenticates which shop the request claims to be from. The shop identity used by downstream job dispatch, `shop_domain`, is read straight from the unauthenticated `X-Shopify-Shop-Domain` header.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes the HMAC over `request.raw_post` using `ShopifyApp.configuration.secret`/`old_secret`, which are **app-wide secrets shared by every shop that has the app installed**, not shop-specific keys: [1](#0-0) 

`WebhookVerification#verify_request` only checks that this body-only HMAC is valid; it performs no check that the claimed `shop_domain` matches anything cryptographically bound to the signature. The `shop_domain` helper simply trusts the header: [2](#0-1) 

The gem's own documentation instructs developers to build custom webhook controllers exactly this way — pass the header-derived `shop_domain` straight into a background job: [3](#0-2) 

And the generated privacy/webhook job templates use that `shop_domain` value directly to look up the target shop and act on it (e.g. delete/redact data, process the shop-level lifecycle): [4](#0-3) [5](#0-4) 

Because the HMAC secret is identical for all shops using the app (it is the app's client secret, not a per-shop key), any body+HMAC pair that is valid for *one* shop's webhook delivery is *also a valid HMAC for every other shop* — the signature carries no information about which shop it was destined for, exactly like the reported VAA missing chain-ID/receiver binding.

### Impact Explanation
An unrelated merchant who has the app installed on their own store can capture one legitimate webhook delivery from Shopify to the app (any topic, e.g. `shop/redact`, `customers/redact`, `app/uninstalled`) along with its valid `X-Shopify-Hmac-Sha256` value. Because the HMAC secret is shared app-wide, that same body+HMAC pair remains valid when replayed with the `X-Shopify-Shop-Domain` header rewritten to target a *different, victim* shop. `verify_request` passes (body+secret HMAC is untouched), and the downstream job (e.g. `ShopRedactJob`/`CustomersRedactJob`/custom `WebhooksController` consumers) executes shop-scoped, privileged logic (data redaction, uninstall cleanup, business logic tied to `Shop.find_by(shopify_domain: shop_domain)`) against the victim shop chosen by the attacker. This is a cross-shop access/state-change vulnerability triggered purely by an unauthenticated, forged header on an otherwise-valid signed request — the webhook analog of the VAA cross-chain replay.

### Likelihood Explanation
Any actor who can install the app on any shop (including a free/trial/dev store) can obtain a legitimate signed webhook payload, since app installation is essentially open to any merchant. Replaying it with a modified `X-Shopify-Shop-Domain` header requires no secret knowledge, no privileged access, and no interaction from the victim — a single crafted HTTP POST to the app's public webhook endpoint. The gem's documented pattern of trusting the header-derived `shop_domain` for downstream shop-scoped actions makes this directly reachable in any app built following the official docs/generators.

### Recommendation
Bind the authenticated shop identity to the signature verification step rather than trusting the `X-Shopify-Shop-Domain` header in isolation:
- Derive/verify the shop from data that is part of the signed payload (or from Shopify's registered webhook metadata / an HMAC computed per-shop using the shop's known access token/secret) instead of an unauthenticated header.
- Reject webhook payloads where the header-claimed shop does not match a shop that currently has a webhook subscription/session on record for that specific topic/webhook ID, and use the API library's own webhook ID/verification metadata to correlate rather than the raw header alone.
- Document explicitly (and enforce in `WebhookVerification`) that `shop_domain` must not be treated as authenticated data by consumer applications.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any merchant can do this).
2. Shopify sends a legitimate webhook (e.g. `customers/redact`) to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed using the app's shared secret over the raw body.
3. Attacker intercepts/replays this exact request but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb`) validates the HMAC successfully (secret is shared, body untouched).
5. The controller/job (per docs pattern) calls `SomeJob.perform_later(shop_domain: "victim-shop.myshopify.com", webhook: <attacker-controlled body>)`, or a generated job does `Shop.find_by(shopify_domain: "victim-shop.myshopify.com")` and executes shop-scoped logic — acting on the victim shop using attacker-supplied webhook content, without any authentication that the victim shop actually sent this webhook.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
