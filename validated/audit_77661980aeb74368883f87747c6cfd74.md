### Title
Missing validation of `decryptor` participant causes index-out-of-bounds panic in PedPoP blame decryption - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The TensorFlow advisory is a `CHECK_EQ` failure: `TensorListReserve` assumed a `num_elements` tensor of size 1 and aborted when an unvalidated attacker-controlled shape was supplied (CWE-617, reachable assertion → availability loss). The Serai analog is the unchecked `HashMap` index `self.enc_keys[&decryptor]` inside `Decryption::decrypt_with_proof`. When a blame/accusation message names a `decryptor` participant that never registered an `EncryptionKeyMessage` (e.g., the accuser themselves, or any participant index absent from `enc_keys`), indexing the map panics — a reachable assertion failure on attacker-influenced input, mirroring the missing-validation-to-crash bug class.

### Finding Description
`Decryption` maintains `enc_keys: HashMap<Participant, C::G>`, populated only through `Decryption::register`, which inserts one entry per participant that supplied a valid `EncryptionKeyMessage` (`crypto/dkg/pedpop/src/encryption.rs:347-362`).

`decrypt_with_proof` — the path used to adjudicate an accusation that a sender failed to deliver a valid encrypted share — indexes the map directly:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-392
if let Some(proof) = proof {
  proof
    .dleq
    .verify(
      &mut encryption_key_transcript(self.context),
      &[C::generator(), msg.key],
      &[self.enc_keys[&decryptor], *proof.key],   // line 388: unchecked index
    )
    .map_err(|_| DecryptionError::InvalidProof)?;
  cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
```

There is no `enc_keys.contains_key(&decryptor)` check and no error variant for "unknown decryptor"; `DecryptionError` only covers `InvalidSignature` and `InvalidProof` (`encryption.rs:332-338`). The `decryptor: Participant` argument is derived from the accusation under adjudication — an accusation names an accused sender and an accuser/decryptor, both parsed from attacker-supplied bytes via `Participant::new` (any `u16` in `1..=u16::MAX` is accepted). If the named decryptor never registered an encryption key — which is trivially satisfiable since a malicious participant can simply withhold or the accuser can name an unrelated index — `self.enc_keys[&decryptor]` panics, exactly like the `CHECK_EQ` in `CheckIsAlignedAndSingleElement`: an implicit assumption ("decryptor is always a registered key holder") enforced by a hard panic instead of a checked error.

This is distinct from `Decryption::register`'s duplicate-registration `assert!` (`encryption.rs:356-359`), which is reachable only if the caller double-registers — here the crash is driven by the *accusation's* data, not by caller misuse.

### Impact Explanation
An unprivileged DKG participant (or anyone able to submit a blame/accusation transaction naming a `decryptor`) can deterministically panic the node evaluating the accusation by naming a participant index with no registered encryption key. In a consensus/tributary context where blame transactions are processed by all honest validators, a single crafted accusation halts DKG-shares adjudication — or the process itself — producing a remote denial of service with no key material or signature validity required. This matches the advisory's availability-only (A:H) impact.

### Likelihood Explanation
The panic requires only that the referenced `decryptor` is absent from `enc_keys`. That occurs whenever (a) the accused/accuser names a participant who never broadcast an `EncryptionKeyMessage`, or (b) an arbitrary valid `Participant` index within the `u16` range but outside the registered set is used. No cryptographic validity (valid signature, valid DLEq) is needed before the index is dereferenced — the PoP verification and DLEq verification happen around the lookup, but the lookup itself is unconditional once `proof` is `Some`. Reachability is therefore high; exploit reliability is deterministic. Overall likelihood is medium: it requires the blame/accusation path to be exercised, which is a less-frequent code path than the happy-case DKG flow.

### Recommendation
Replace the panicking map index with a checked lookup in `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:388`):

```rust
let enc_key = self
  .enc_keys
  .get(&decryptor)
  .ok_or(DecryptionError::InvalidProof)?;
proof
  .dleq
  .verify(&mut encryption_key_transcript(self.context), &[C::generator(), msg.key], &[*enc_key, *proof.key])
  .map_err(|_| DecryptionError::InvalidProof)?;
```

The same pattern should be audited for the other direct map indexes in this module (`Encryption::encrypt` uses `self.decryption.enc_keys[&participant]` at `encryption.rs:466`, and `ThresholdView::original_verification_share`/`verification_share` in `crypto/dkg/src/lib.rs:672-682` index by `Participant`), ensuring every attacker-influenced `Participant` is validated before map access rather than assumed present.

### Proof of Concept
Conceptual, against the PedPoP blame path with ciphersuite `C`:

```rust
// Honest decryptor D registers their EncryptionKeyMessage for participants 1..=n.
// Attacker A submits an accusation naming decryptor = Participant::new(0xFFFF) (or any
// index that never registered), plus a well-formed EncryptedMessage/EncryptionKeyProof
// under A's own key so `proof` is Some.
//
// When the adjudicator runs:
decryption.decrypt_with_proof::<Share>(
    accuser,                          // `from`
    Participant::new(0xFFFF).unwrap(),// `decryptor` — valid Participant, never registered
    msg,                              // EncryptedMessage with a valid PoP so we reach line 388
    Some(attacker_proof),             // EncryptionKeyProof<C>
);
// Execution reaches crypto/dkg/pedpop/src/encryption.rs:388:
//   self.enc_keys[&decryptor]  ->  panics: "no entry found for key"
// DecryptionError is never returned; the thread unwinds, DoS-ing the adjudicator.
```

The panic occurs before `DecryptionError::InvalidProof` can be produced, because the `enc_keys` lookup — not the DLEq verification — is the failing operation.

Caveat: the exact call-site plumbing that feeds an accusation's `decryptor` value into `decrypt_with_proof` (inside `crypto/dkg/pedpop/src/lib.rs` / `processor`'s blame handling) was not fully traced within this session's tool budget; the panic site itself and the absence of any membership check are verified in `encryption.rs:381-392`. If the caller already restricts `decryptor` to registered participants, the reachable surface narrows to the `Encryption::encrypt` index at `encryption.rs:466`, which has the same missing-validation shape.
