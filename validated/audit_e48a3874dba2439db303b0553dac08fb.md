### Title
`ThresholdKeys::read`/`new` derive the authoritative `group_key` entirely from attacker-supplied verification shares without checking the local `secret_share` belongs to the group — an untrusted serialized key set can silently substitute a group key whose secret the attacker fully controls - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the external report — where the `AddressRegistry` owner can swap the `GOVERNANCE` account to redirect privileged functionality — `ThresholdKeys::new` computes the effective `group_key` (the "account" the protocol trusts for deposits and signature verification) purely by interpolating `verification_shares[1..=t]`, and `ThresholdKeys::read` accepts both the verification shares and the local `secret_share` from raw untrusted bytes. No check verifies that `C::generator() * secret_share == verification_shares[params.i()]`, nor that the reconstructed group key corresponds to any previously-established identity. A party feeding crafted bytes into `ThresholdKeys::read` can therefore install a `ThresholdKeys` whose `group_key()` resolves to a key whose discrete log the attacker knows outright (e.g., verification shares all built from a single known scalar), while the victim's `secret_share` is arbitrary garbage.

### Finding Description
`ThresholdKeys::new` derives the group key from only the first `t` verification shares:

```rust
// crypto/dkg/src/lib.rs:376-390
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation vector, the `secret_share`, and all `n` verification shares straight from the reader and passes them to `new` (crypto/dkg/src/lib.rs:574-632). The only validations are count of shares, `participant <= n`, and `ThresholdParams::new`'s `t <= n`/`i <= n` checks (crypto/dkg/src/lib.rs:166-179). Nowhere is the consistency condition `G * secret_share == verification_shares[i]` enforced — the group key is whatever the attacker-written bytes interpolate to.

The impact propagates because downstream consumers treat `group_key()` as the authoritative identity: `networks/bitcoin/src/wallet/mod.rs` `tweak_keys`/`p2tr_script_buf` and `Scanner::new`/`register_offset` derive deposit addresses directly from `group_key()` (networks/bitcoin/src/wallet/mod.rs:46-86, 162-196), and `SignableTransaction::multisig` re-derives spend keys as `keys.clone().offset(...)`, all anchored on that group key (networks/bitcoin/src/wallet/send.rs:273-285). FROST's `sign` even binds `self.params.keys.group_key()` into `rho_transcript` (crypto/frost/src/sign.rs:363), so the substituted identity is committed into every signature transcript.

The crate itself acknowledges the hazard only implicitly: `recover_key` performs the missing check manually at reconstruction time (`C::generator() * res == group_key`, crypto/dkg/recovery/src/lib.rs:80-82), and `AlgorithmSignatureMachine::complete` notes the failure mode as "deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:492-494) — confirming invalid deserialized key sets are reachable but only caught after shares are produced.

### Impact Explanation
Any consumer that deserializes a `ThresholdKeys` from an untrusted channel (state sync, peer-provided backup, imported blob) and then uses `group_key()` to determine where funds are received — exactly what the Bitcoin wallet scanner and multisig code do — will have deposits addressed to a key whose full secret the attacker knows, since the attacker chose all `n` verification shares to interpolate to a known discrete log. The victim's stored `secret_share` is inconsistent with the group, so the victim can never produce a valid spend; the attacker can spend unilaterally. Funds are reported received yet are spendable only by the attacker — direct theft, matching the "attacker becomes sole recipient" outcome of the original report.

### Likelihood Explanation
Low-to-medium. Exploitation requires the deployment to accept serialized `ThresholdKeys` from an attacker-influenced source rather than only from its own honest DKG output, and requires the attacker to arrange deposits/attribution against the substituted `group_key`. No threshold collusion or validator misbehavior is needed — a single unauthenticated byte stream into `ThresholdKeys::read` suffices. The resulting keys "work" in the sense that the group key, address derivation, and FROST transcript all function normally; shares merely never verify (`InvalidShare`), which may be mistaken for peer faults rather than a poisoned key set.

### Recommendation
- In `ThresholdKeys::new` (and therefore `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject on mismatch, so a deserialized share is provably a member of the claimed group.
- Where available, bind serialized keys to an externally authenticated/expected `group_key` digest rather than trusting the interpolated value.
- Mirror the consistency check already present in `dkg/recovery` (`C::generator() * recovered == group_key`) at construction time instead of only at recovery.

### Proof of Concept
```rust
// Attacker: build bytes for ThresholdKeys::read where the group key is fully known.
let x = <Secp256k1 as Ciphersuite>::F::random(&mut OsRng);      // attacker-known secret
let n = 5u16; let t = 3u16;

// Write header: id, t, n, i = 1, Lagrange interpolation.
// Write arbitrary garbage as our own secret_share (never checked).
// Write verification shares V_l = G * (x / lagrange_factor(l, {1,2,3})) for l in 1..=n
// so that interpolation over participants 1..=t yields group_key == G * x.
let keys = ThresholdKeys::<Secp256k1>::read(&mut bytes.as_slice()).unwrap();
assert_eq!(keys.group_key(), Secp256k1::generator() * x);        // accepted

// Victim: Scanner::new(tweak_keys(keys).group_key()) -> deposits go to a key
// whose discrete log (x) the attacker knows; victim shares can never verify.
```
