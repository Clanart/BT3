### Title
Forfeit calculation in `_calExpireForfeit`/`getRewardablePercentWAD` uses live, self-manipulable lock state, letting a user avoid yield forfeiture owed to other vlMGP stakers - (File: `rewards/vlMGPBaseRewarder.sol`, `VLMGP.sol`)

### Summary
`vlMGPBaseRewarder._calExpireForfeit` (called from both `queueMGP` and `_sendReward`) computes the forfeitable portion of a reward payout by calling `VLMGP.getRewardablePercentWAD(_account)` at the exact moment the reward is processed, rather than using a snapshot taken when the reward was earned or when the unlock was initiated. Because a user's own `cancelUnlock`/`lock`/`startUnlock` calls directly and instantly change the inputs to `getRewardablePercentWAD` (`getUserTotalLocked`/`getUserAmountInCoolDown`), the user can manipulate this ratio to 100% "fully locked" immediately before the forfeit check runs, reducing `forfeitAmount` to zero and keeping reward that should have been redistributed to other stakers.

### Finding Description
`_calExpireForfeit` in `rewards/vlMGPBaseRewarder.sol` reads a live percentage: [1](#0-0) 

That percentage comes from `VLMGP.getRewardablePercentWAD`, which is a pure function of the account's *current* `getUserTotalLocked` / `getUserAmountInCoolDown` split: [2](#0-1) 

`getUserTotalLocked` and `getUserAmountInCoolDown` are themselves derived from `userUnlockings[_user]`, which `cancelUnlock` mutates with no penalty and no cooldown-completion requirement (only requires the slot currently be in cooldown): [3](#0-2) 

`queueMGP` (the manager-only entry point) transfers a fixed `_amount` in, then computes the forfeit against the account's *current* ratio at call time: [4](#0-3) 

The same live-ratio pattern is used in `_sendReward`, which is reached through the ordinary `getReward`/`getRewards` claim path (itself invoked internally during `VLMGP.unlock()` via `multiclaimFor`, before the slot being unlocked is finalized): [5](#0-4) [6](#0-5) 

Because the forfeiture percentage is a pure function of mutable state that the account itself fully controls (via its own unprivileged `cancelUnlock`/`lock`), and because `cancelUnlock` reverses cooldown status with zero cost, an account with tokens partially in cooldown can move all its tokens back to "fully locked" status immediately before any forfeit-checking payout is processed for it, causing `forfeitAmount` to compute as `0` and `rewardableAmount == _amount`. Whatever amount would otherwise have been forfeited and pushed into `_queueNewRewardsWithoutTransfer` (which increases `rewardPerTokenStored` for **all** other vlMGP stakers) is instead retained entirely by the manipulating account. No existing modifier (`nonReentrant`, `whenNotPaused`, `onlyManager`) prevents this, because they only gate direct reentrancy/pausing/access-control, not the sequencing of the account's own separate `cancelUnlock`/`lock` calls relative to when its reward is processed.

Note: because this ratio manipulation is achievable by the account itself acting on its own unlock slots, and because the reward-processing path (`getReward`/`getRewards`/`_sendReward`) is itself invoked from within `VLMGP.unlock()` (which the attacker calls), the attacker does not strictly need to front-run a separate manager transaction — they can sequence `cancelUnlock` and `lock` in transactions immediately preceding their own `unlock()` call within the same block, fully self-controlled. The "front-run the manager's `queueMGP`" framing in the question is one variant of this same root cause (TOCTOU on `getRewardablePercentWAD`).

### Impact Explanation
This diverts yield that the protocol design intends to forfeit from users leaving/reducing their commitment and redistribute to remaining/loyal vlMGP stakers (via `_queueNewRewardsWithoutTransfer`, which raises `rewardPerTokenStored` for everyone else). By manipulating their own lock state at the exact moment of forfeit evaluation, an attacker can retain 100% of a reward payout that should have been partially forfeited, directly reducing the amount other vlMGP holders receive. This matches "theft of unclaimed yield diverted from other vlMGP holders."

### Likelihood Explanation
- No special privileges are needed: `cancelUnlock`, `lock`, `startUnlock`, and `unlock` are all public/external functions callable by any vlMGP holder on their own account.
- Preconditions: attacker must hold vlMGP with an active unlock/cooldown slot (a normal, permissionless state to be in) at the time a reward/forfeit-checked payout for them is about to be processed.
- No flash loan or capital beyond normal vlMGP holdings is required, since `cancelUnlock` is free and doesn't require waiting for the cooldown to complete.
- Repeatable on every reward distribution/claim cycle for the account, as long as they can time their `cancelUnlock`/`lock` calls relative to the forfeit-check execution (same block or preceding block state).

### Recommendation
Snapshot the rewardable/forfeit ratio at the time the reward is accrued (e.g., at each `updateReward`/`_updateFor` checkpoint or when the unlock slot's cooldown period ends) rather than recomputing it live from current mutable lock state at claim/queue time. Alternatively, disallow `cancelUnlock` from restoring "fully locked" weight instantaneously (e.g., require the restored amount to go through a symmetric re-lock delay/penalty), so a user cannot toggle their forfeit ratio to zero cost immediately before a payout is finalized.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, and `vlMGPBaseRewarder` with a manager set for `queueMGP`.
2. User A locks MGP, then calls `startUnlock` for part of the balance to create a cooldown slot with `rewardablePercentWAD < 100%` (call `getRewardablePercentWAD` to confirm baseline < 1e18).
3. Manager prepares to call `queueMGP(amount, userA, receiver)` (or trigger a claim path that leads to `_sendReward` for userA), representing an owed reward with baseline expected `forfeitAmount > 0` (compute via `calExpireForfeit`).
4. In the same block/transaction ordering, have User A call `cancelUnlock(slotIndex)` (and optionally `lock`) right before the manager's `queueMGP` (or before the `getReward` call triggered inside `unlock()`), then let the payout execute.
5. Assert: `forfeitAmount` computed inside `queueMGP`/`_sendReward` is `0` (or near `0`), versus a baseline test without the `cancelUnlock` step where `forfeitAmount > 0` and is credited via `_queueNewRewardsWithoutTransfer` to `rewardPerTokenStored`.
6. Assert other stakers' `earned()` value is lower in the manipulated scenario than in the baseline, demonstrating diverted yield.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
```
