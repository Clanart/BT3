## Analysis

Reducing the external report to one invariant: **a "verification" step that claims to validate real, executed state should not silently pass based on caller-declared metadata that is never bound to the actual bytes actually stored/executed on-chain.** In the EIP20 case, the caller-declared `approve` return value doesn't match actual token behavior; callers trust it blindly and get burned.

I generated and evaluated four local candidates in the Aptos publish path:
1. `check_dependencies` wildcard exemption for addresses `0x1`-`0xa` in `code.move` — intentional, documented design.
2. `freeze_code_object` ownership/registry gating in `code.move` — correctly checks `object::is_owner`.
3. `object_code_deployment::upgrade`/`freeze_code_object` — correctly checks ownership via `ManagingRefs`/`ExtendRef`.
4. **`PackageMetadata.source_digest`/`modules[].source` never bound to the actual bytecode bundle passed to `request_publish`, and `aptos move verify-package`'s `verify()` only diffs metadata fields, never fetches/compares real on-chain bytecode** — this is the strongest, independently-provable candidate.

### Title
Package "source verification" only compares self-declared metadata, never the actual on-chain bytecode - (File: `aptos-move/cli/src/stored_package.rs`, `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
`aptos_framework::code::publish_package` stores a `PackageMetadata` struct containing `source_digest`, `manifest`, and per-module `source`/`source_map` fields alongside the actually-published bytecode bundle [1](#0-0) , but nothing in the on-chain publish path checks that this metadata (source text, source digest, manifest) actually corresponds to the bytecode bundle that is verified and stored. `validate_publish_request` in the VM only checks module names, native validation, allowed dependencies, and module attributes — it never touches `source_digest` or module source fields [2](#0-1) .

The CLI's `VerifyPackage` command, documented as "verifies the bytecode matches a local compilation" [3](#0-2) , actually only fetches the `PackageRegistry` resource with `with_bytecode = false` [4](#0-3)  and calls `CachedPackageMetadata::verify`, which compares only `name`, `deps`, `modules` (metadata, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest` fields between the locally-rebuilt metadata and the on-chain metadata [5](#0-4) . It never diffs actual `.mv` bytecode bytes.

### Finding Description
`source_digest` is defined as "the sha256 of each individual source, sorted and re-hashed" [6](#0-5)  — a hash over the *source text the publisher chooses to attach*, not over the compiled bytecode itself. A publisher calling `publish_package_txn`/`code::publish_package` supplies both the real `code: vector<vector<u8>>` bundle (which is bytecode-verified, compatibility-checked, and stored) and an independently-crafted `PackageMetadata` (including `modules[].source`, `manifest`, `source_digest`). Since `check_dependencies`, `check_upgradability`, `check_coexistence`, and `request_publish[_with_allowed_deps]` never cross-check metadata source content against the bytecode bundle, a publisher can attach source/metadata for module `A` that is completely unrelated to the real bytecode that ends up live on-chain for that module.

Downstream, the CLI's `aptos move verify-package` (and `CachedPackageRegistry`/`stored_package::verify`) trusts this on-chain metadata as ground truth: it recompiles the metadata a user believes matches the deployed code, compares it field-by-field against the on-chain `PackageMetadata`, and reports success — all without ever pulling and diffing the actual deployed `.mv` bytes. The `verify()` function's own doc/contract implies bytecode-level trust but its implementation only asserts metadata self-consistency [5](#0-4) .

### Impact Explanation
Anyone auditing or depending on a package via `aptos move verify-package` can be given a false assurance that "source matches on-chain bytecode" when the two are unrelated by construction, since the check never touches bytecode. This directly matches the Publish Impact Gate's "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" criterion: a malicious or careless publisher can publish arbitrary bytecode while attaching plausible-looking (but disconnected) source metadata, and any tooling relying on `verify()`/`VerifyPackage` for code-review/trust decisions is misled into believing the deployed code was audited/reviewed when it was not.

### Likelihood Explanation
This requires no privileged access — any permissionless publisher (account publish or object-code publish/upgrade) can supply mismatched metadata, since `publish_package_txn` takes attacker-controlled BCS-serialized metadata directly [7](#0-6) , and no validation path (Move-side `code.move` or Rust-side `aptos_vm.rs::validate_publish_request`) ever cross-checks it against the bytecode. It is a deterministic, always-reachable gap in the standard publish flow, not a rare race condition.

### Recommendation
Either (a) have the VM compute and store a metadata `source_digest`-equivalent that is bound to the actual compiled bytecode bundle at publish time (e.g., hash of the bytecode itself, verified natively rather than trusted from the Move-level struct), or (b) have `aptos move verify-package` / `CachedPackageRegistry` always fetch actual on-chain bytecode (`with_bytecode = true`) and byte-compare it against the freshly-built package, rather than relying solely on metadata-field equality.

### Proof of Concept
1. Compile package `P` containing module `m` with legitimate logic; extract its bytecode bundle `code_real`.
2. Craft a `PackageMetadata` whose `modules[0].source`/`source_map`/`manifest`/`source_digest` describe an unrelated, benign-looking source file `m_fake.move` (attacker controls the BCS bytes passed to `publish_package_txn`).
3. Submit `code::publish_package_txn(owner, bcs(fake_metadata), vec![code_real])`. `validate_publish_request` and `code.move` only check module names/deps/attributes — nothing rejects the mismatched metadata [8](#0-7) .
4. A reviewer runs `aptos move verify-package --account owner` against the fake `m_fake.move` source tree; `stored_package::verify` compares only metadata fields (all match by construction) and reports "Successfully verified source of package" [9](#0-8) , despite the actual live bytecode having nothing to do with `m_fake.move`.

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
