### Title
Asymmetric `saturating_sub` decimal-scaling in `hyper-fungible-token` lets `send()` mint an inflated, unbacked token amount on the destination chain - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The bug pattern in the external report — a conversion routine that fails to correctly rescale an amount between two different decimal bases before it is used to move value — has a direct, unprivileged analog in Hyperbridge's `hyper-fungible-token` pallet. `convert_to_erc20` and `convert_to_balance` assume `erc_decimals >= local_decimals` and use `saturating_sub` to compute the scaling exponent. When that assumption is false (`erc_decimals < local_decimals`), the exponent collapses to `0` and the amount is passed through **unscaled**, so a small locally-escrowed amount is dispatched cross-chain as a value that the destination ERC20 contract will interpret as a token amount `10^(local_decimals-erc_decimals)` times larger than the value actually escrowed.

### Finding Description
`convert_to_erc20` and `convert_to_balance` are defined as: [1](#0-0) 

Both use `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent. This formula is only correct when `erc_decimals >= local_decimals`. If the remote ERC20 representation of an asset uses **fewer** decimals than the local Substrate asset (e.g. local asset uses 18 decimals while the wrapped ERC20 on the EVM side uses 6, a very plausible configuration since `Precisions` is set independently per `(asset_id, destination)` pair), `saturating_sub` returns `0`, so both functions multiply/divide by `10^0 = 1` — i.e. no rescaling happens at all.

This is invoked directly from the public, unprivileged `send()` extrinsic: [2](#0-1) 

Here `amount` is the raw local-balance value (already expressed in `local_decimals`, e.g. `1e18` for "1 token" on an 18-decimal asset). It is escrowed/burned locally at that magnitude, then passed into `convert_to_erc20(amount, erc_decimals, decimals)` to compute `erc20_amount`, which becomes the `Message.amount` dispatched to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract: [3](#0-2) 

If `erc_decimals (6) < local_decimals (18)`, `convert_to_erc20` returns the raw value `1e18` unchanged instead of the correct `1e18 / 10^12 = 1e6`. The destination EVM contract mints/unlocks `Message.amount` raw units of a 6-decimal ERC20, i.e. it credits `1e18` raw units = `1,000,000,000,000` tokens instead of `1`. The user has escrowed only 1 token's worth of value on the source chain but receives a mint order for a trillion times more value on the destination chain — an unbacked, inflated mint reachable by any ordinary user calling `send()`.

The mirrored bug exists in `on_accept` via `convert_to_balance`, which under the same asymmetric condition would under-credit the local beneficiary instead — a fund-loss variant of the same root cause: [4](#0-3) 

Neither `convert_to_erc20` nor `convert_to_balance` validates that `erc_decimals >= local_decimals` before applying `saturating_sub`; no guard exists elsewhere in `send()` or `on_accept` to reject or correctly handle the reverse-decimals case.

### Impact Explanation
This is a direct fund-inflation / unauthorized-mint primitive: the amount actually locked/burned on the source chain does not match the amount encoded in the cross-chain message, and there is no additional check reconciling the two. Any asset pair configured with `erc_decimals < local_decimals` turns `send()` into a mechanism that mints value on the destination chain far in excess of what was escrowed, which can then be redeemed/sold by the caller — a direct "stealing/loss of funds" and "false state acceptance" scenario matching the bounty's accepted impact categories.

### Likelihood Explanation
Triggering the bug requires no privileged role, relayer collusion, or malformed proof — only a normal call to the public `send()` extrinsic on an asset whose configured `Precisions` entry has `erc_decimals < local_decimals`. Whether such a configuration currently exists in production `Precisions`/`TokenContracts` storage could not be confirmed from the indexed code (governance-set values are not visible here), so likelihood is contingent on that specific asset-pair configuration being present or introduced. Given many local assets natively use 18 decimals while common EVM stablecoins (e.g., USDC-style tokens) commonly use 6, this is a realistic configuration, not a purely theoretical one.

### Recommendation
Fix `convert_to_erc20` and `convert_to_balance` to correctly handle both directions instead of relying on `saturating_sub`, e.g.:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and symmetrically for `convert_to_balance`. Add an invariant/test asserting round-trip conversion correctness for all supported decimal combinations, and add explicit unit tests for `erc_decimals < local_decimals` configurations.

### Proof of Concept
1. Configure an asset in `hyper-fungible-token` with `local_decimals = 18` and register `Precisions::<T>::insert(asset_id, destination, 6)` (i.e., the destination ERC20 wrapper uses 6 decimals).
2. User calls `send()` with `amount = 1_000_000_000_000_000_000` (1 token, 18-decimal units); the pallet locks/burns this amount locally.
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, returning `1e18` unchanged instead of the correct `1e6`.
4. The dispatched `Message.amount` field carries `1e18`; the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract mints/releases `1e18` raw units of its 6-decimal ERC20 — equivalent to `1,000,000,000,000` tokens — to the recipient, vastly exceeding the single token actually escrowed on the source chain.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,

	let dec_str = (value /

	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount

/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
