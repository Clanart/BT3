### Title
Missing URL-scheme validation in the `open-external` IPC handler allows arbitrary protocol invocation from attacker-controlled CI/API URLs - (File: `app/src/main-process/main.ts`)

### Summary
The Solidity report describes a privileged function (`updatePoolPrice`) that lacked an access-control check, letting anyone trigger a sensitive state change. The equivalent broken-invariant pattern in GitHub Desktop is a *missing validation* guard on a privileged, attacker-reachable primitive: the main-process `open-external` IPC handler forwards whatever string the renderer sends straight to Electron's `shell.openExternal()` without checking the URI scheme, even though the same codebase elsewhere (the sandboxed markdown link interceptor) explicitly enforces an `http(s)` allowlist before treating a link as safe to open.

### Finding Description
The IPC handler for `open-external` only inspects the string to decide whether to *log* it as a browser navigation — it performs no scheme allowlisting before calling `shell.openExternal(path)`: [1](#0-0) 

Compare this to `SandboxedMarkdown`'s link interceptor, which is careful to only forward `https?:` links to the click handler that ultimately calls `shell.openExternal`: [2](#0-1) 

However, `dispatcher.openInBrowser` / `_openInBrowser` is called from many other UI surfaces that render GitHub-API-derived data, e.g. CI check run detail links (`ci-check-run-popover.tsx`) and PR review/comment UI, and those code paths do not necessarily pass through the same `^https?:` filter as the markdown iframe — they hand the URL supplied by the API response (e.g., a check run's `target_url`/`details_url`, which is fully controlled by whoever configures the CI integration on a fork) directly to `_openInBrowser`, which forwards it unchanged to the main process: [3](#0-2) 

Because the main-process handler never enforces a protocol allowlist, any renderer code path that fails to pre-filter the scheme (unlike the markdown iframe) lets an attacker who controls a repository's CI status/check-run metadata (a "GitHub API object" the user does not need to clone, just view) supply a non-`http(s)` URI. `shell.openExternal` will hand that URI to the OS's registered handler for that scheme.

### Impact Explanation
`shell.openExternal` with an uncontrolled scheme is a well-known Electron risk: OS-registered custom URI-scheme handlers on Windows/macOS can accept URI content as command-line-like arguments (e.g., `search-ms:`, vendor-specific protocol handlers, or file-manager/`file://` disclosure), potentially resulting in code execution, local file exposure, or triggering unwanted privileged OS-level actions — all without the user doing anything more than clicking a rendered link/button whose target originates from attacker-controlled fork/CI metadata rather than a URL the user typed. This matches the "link the user clicks" / "GitHub API object" attacker profile in the Valid Impact list.

### Likelihood Explanation
The click surfaces that funnel into `openInBrowser` (CI check-run links, PR notification links, review comment links) are populated from third-party/fork-controlled data (CI provider `target_url`, review/comment payloads) that a malicious contributor or malicious CI integration can freely set. The main-process gate that should provide defense-in-depth performs no scheme check at all, so protection depends entirely on every individual renderer call site remembering to pre-filter to `https?:` — which is inconsistent, as shown by the markdown iframe doing it and the IPC handler itself not doing it as a backstop.

### Recommendation
Add a strict scheme allowlist (`http:`/`https:`, plus perhaps `mailto:`) inside the `open-external` IPC handler in `app/src/main-process/main.ts` and reject/log-and-drop anything else before calling `shell.openExternal`, so the check is centralized in the main process rather than relying on every renderer call site to filter correctly.

### Proof of Concept
1. Configure (or compromise) a CI integration on a public fork so that a check run's `target_url` is set to a non-`http(s)` URI (e.g., a Windows-registered custom protocol handler string, or `file://...`).
2. Open the corresponding PR/notification in GitHub Desktop and click "View on [CI Provider]" in the check-run popover, which invokes `dispatcher.openInBrowser(target_url)` → `_openInBrowser` → IPC `open-external`.
3. Observe that `app/src/main-process/main.ts`'s handler passes the URI unchanged to `shell.openExternal`, with no scheme check comparable to the one enforced in `sandboxed-markdown.tsx`, allowing the OS to invoke whatever handler is registered for that scheme.

Note: I could not fully trace every call site of `openInBrowser`/`dispatcher.openInBrowser` (e.g., exact code in `ci-check-run-popover.tsx`, `pull-request-checks-failed.tsx`) to confirm each one omits scheme pre-filtering, since those specific render functions weren't retrieved in full. Given index size limits, a Devin session with full file access would be needed to confirm every call site's filtering behavior before treating this as fully confirmed rather than a strong analog based on the asymmetry already observed between `sandboxed-markdown.tsx` and `main.ts`.

```typescript
  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
```
