### Title
GitHub identity for a local repository is keyed on mutable `[owner, name]` instead of a stable repository ID, letting a renamed/re-registered GitHub repository silently inherit a stranger's cached permissions, fork/parent lineage and branch-protection bypass state - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
GitHub Desktop caches metadata about every GitHub-backed local repository (`permissions`, `parentID`, `cloneURL`, `htmlURL`, `private`, etc.) in an IndexedDB record keyed by `[ownerID+name]`, and re-associates that cached record whenever it refreshes from the API. It never checks GitHub's immutable repository ID before merging fresh API data into an existing local record. If the object at a given `owner/name` on GitHub.com changes identity (the original repo is deleted/renamed away and a different, attacker-controlled repo now answers at that same `owner/name`), Desktop will merge the new object's data into the pre-existing `GitHubRepository` database row, carrying over the stale `dbID` and, in the fork/parent case, deliberately preserving the *old* cached `parentID` (`ignoreParent` path in `_upsertGitHubRepository`). This is the same broken invariant as the report: an access-control/identity object is silently "moved" and the local trust state (permissions, protection status, lineage) does not get revalidated against the new identity, nor is any of this surfaced to the user.

### Finding Description
`RepositoriesStore._upsertGitHubRepository` looks up whether a `GitHubRepository` row already exists using only `[ownerID+name]`: [1](#0-0) 

and then blindly writes the new API payload into that *same* row (same `id`, i.e. same `dbID`), including permissions and clone/html URLs: [2](#0-1) 

There is no reconciliation against GitHub's actual immutable repo id (`gitHubRepository.owner.id`+repo id are available on the API payload but are never compared to the previously-stored identity). The model itself documents that `dbID` "is no relation to the API ID": [3](#0-2) 

The refresh path that drives this is `repositoryWithRefreshedGitHubRepository`, which re-derives `owner`/`name` purely from the *local git remote URL* via `matchGitHubRepository`, then calls `api.fetchRepository(owner, name)` and merges the result: [4](#0-3) 

Because identity resolution is name-based end-to-end (remote URL → owner/name → API lookup → DB upsert keyed by owner/name), if the entity now living at that `owner/name` is different from the one originally associated (classic GitHub "repo-jacking": the original repo is renamed/deleted and someone else creates a new repo re-using the freed name), Desktop transparently inherits the new object's `permissions` field into the existing `GitHubRepository` row. That `permissions` value directly drives security-relevant UI/logic such as `hasWritePermission()` (gating the branch-protection API check and the "no write access" warning) and the fork/parent chain used across the app: [5](#0-4) [6](#0-5) 

Additionally, when upserting the *parent* of a fork (`ignoreParent = true`), the code explicitly falls back to the previously cached `parentID` rather than clearing it when the API no longer reports a parent, on the theory that "going from having a parent to not having a parent is incredibly rare": [7](#0-6) 

This assumption is exactly the kind of "invisible, inherited trust relationship survives an ownership change" flaw described in the report — the local record keeps pointing at stale lineage/permission data that the user never explicitly reviewed, and nothing in the UI flags that the underlying GitHub object's identity has changed.

`updateRemoteUrl` compounds this: it will only rewrite the local git remote automatically when the clone URL differs and the previous remote is unmodified, meaning for a same-owner/same-name identity swap the remote silently keeps pointing at (and users keep pushing/fetching from) the new object without any indication that it isn't the repository they originally added: [8](#0-7) 

### Impact Explanation
An attacker who can cause a different GitHub object to occupy a previously-used `owner/name` slot (e.g. by registering a repo name vacated after a rename/deletion, a well-documented "repo-jacking" primitive that requires no special privilege on GitHub) can cause GitHub Desktop, for any user who already has that name associated locally, to silently:
- merge the attacker's repository's `permissions` blob into the trusted local record, which controls whether Desktop shows/hides the "no write access" warning and whether it even queries branch protection (`hasWritePermission` gate),
- retain stale fork/`parentID` lineage across the swap,
- keep git operations (fetch/push) transparently pointed at the attacker-controlled repository without any re-confirmation dialog, since the identity check is purely name-based.
This matches the report's core impact: identity/permission state from one object leaking onto (or persisting on) a different object after a transfer, invisibly to the user.

### Likelihood Explanation
This requires no local access, no prior malware, and no leaked credentials — only that the attacker control (or later claim) a GitHub repository name that a victim has already added to Desktop, which is a realistic, previously-documented external condition (name squatting after rename/deletion, aka repo-jacking). Desktop performs this refresh automatically on ordinary background refresh flows (`repositoryWithRefreshedGitHubRepository`) without any user action, increasing the likelihood a victim is affected without noticing.

### Recommendation
Track GitHub repositories by their immutable API id (already present on `IAPIRepository`/`IAPIFullRepository`) rather than by `[ownerID+name]`. When refreshing, verify that the API id returned for a given `owner/name` matches the id previously associated with the local `GitHubRepository` record; if it doesn't, treat it as a new/unrelated repository (create a fresh record, or at minimum reset `permissions`, `parentID`, and prompt the user) instead of merging its data into the existing trusted record.

### Proof of Concept
1. Victim clones `github.com/alice/project` in Desktop; Desktop stores a `GitHubRepository` row keyed by `[owner=alice, name=project]` with `permissions: 'admin'` and no parent.
2. Alice renames/deletes `alice/project` (freeing the name) — the local git remote in the victim's clone still points at `alice/project`.
3. Attacker (or anyone) creates a new, unrelated repository also named `alice/project` under an account they control, or alice's account is compromised/renamed and a different `alice/project` now exists with different permissions/fork lineage.
4. Desktop's background refresh calls `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` (derives `owner=alice, name=project` purely from the unchanged local remote URL) → `api.fetchRepository('alice','project')`, which now returns the new repository's data.
5. `RepositoriesStore._upsertGitHubRepository` finds the existing row via `[ownerID+name]` and overwrites its `permissions`/`cloneURL`/`htmlURL` fields in place (same `dbID`), and `updateRemoteUrl` leaves the git remote untouched since owner/name match — the victim's Desktop client is now silently operating against a different GitHub object while all cached trust state (and the UI) still reflects the original relationship.
