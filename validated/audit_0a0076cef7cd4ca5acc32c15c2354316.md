### Title
Missing deadline/freshness validation on signed App Proxy requests allows indefinite replay of leaked signed URLs - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#verify_proxy_request` validates only that the HMAC `signature` query parameter matches the other query parameters (including `timestamp`), but never checks that `timestamp` is recent. A signed app‑proxy request URL therefore remains valid forever and can be replayed at any point in the future, exactly analogous to a signed transaction with no deadline that can be "saved for later" and executed under different conditions.

### Finding Description
`query_string_valid?` recomputes the HMAC over all query parameters except `signature` and compares it to the supplied `signature` — it never inspects or enforces recency of the `timestamp` field that Shopify includes in every proxied request: [1](#0-0) 

`timestamp` is treated purely as one more signed field, not as an expiry/deadline check. The gem's own test suite demonstrates this: a query string with `timestamp=1466106083` (year 2016) is asserted to be `valid?` today, with no rejection for staleness: [2](#0-1) 

This mirrors the reported bug class ("No deadline parameter in `sellAllAmount()`/`buyAllAmount()`"): a cryptographically valid, signed request — captured once — has no expiration and can be executed/replayed at an arbitrarily later time, regardless of how much application/shop state has changed since it was issued.

The `WebhookVerification`/`PayloadVerification` concerns have the same property (HMAC over body only, no nonce/timestamp freshness check), but app proxy is the stronger analog because the signed query string (including `shop`, `path_prefix`, `timestamp`, `signature`) is exposed directly in browser-reachable URLs (Referer headers, browser history, shared links, proxy/CDN logs), making leakage and later replay by an unrelated party far more plausible than for server-to-server webhook deliveries: [3](#0-2) 

### Impact Explanation
Any app proxy endpoint that uses `ShopifyApp::AppProxyVerification` for authorization (per the gem's own recommended pattern) will accept a previously valid signed request indefinitely: [4](#0-3) 

If such a leaked/old request URL is replayed after the shop's state, session, or granted permissions have changed (e.g., app uninstalled and reinstalled, shop-specific data rotated, or the endpoint performs a state-changing action gated only on this signature), the app will treat it as a fresh, legitimate request from Shopify's proxy, because the concern only proves "this query string was signed with the shared secret at some point," not "this request is current." This is a direct instance of "accepted forged/stale signed request" due to missing deadline enforcement.

### Likelihood Explanation
Likelihood is elevated because:
- App proxy URLs are GET requests embedded in storefront pages/links, so they are far more likely to be logged, cached, bookmarked, or leaked via Referer headers than a webhook POST body.
- The vulnerability requires no additional exploitation technique — replaying the exact same URL is sufficient, as proven directly by the existing test asserting an 8+ year old timestamp validates successfully.
- No configuration option exists in `AppProxyVerification` to opt into a freshness window.

### Recommendation
Add a mandatory freshness check in `verify_proxy_request`/`query_string_valid?`: reject requests whose `timestamp` is older than a small configurable window (e.g., a few minutes), similar to standard HMAC-with-timestamp anti-replay patterns. Apply the same freshness/nonce-based anti-replay protection to `PayloadVerification#hmac_valid?` used by `WebhookVerification`, tracking `X-Shopify-Webhook-Id` to reject duplicate/stale deliveries.

### Proof of Concept
1. Attacker observes/logs a legitimate storefront request to an app-proxy endpoint, e.g.
   `GET /apps/my-app?shop=some-random-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd`
2. Years later, the attacker replays the exact same URL against the app.
3. `AppProxyVerification#verify_proxy_request` calls `query_string_valid?`, which recomputes the HMAC and finds it matches — the request passes, exactly as shown by the existing passing test using this same 2016 timestamp: [5](#0-4) 
4. Any app logic gated solely on this "verified" request (e.g., serving/altering shop-scoped data based on the `shop` param) executes as if the request were fresh, with no deadline ever enforced.

# frozen_string_literal: true

module ShopifyApp
  module AppProxyVerification
    extend ActiveSupport::Concern
    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_proxy_request
    end

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
```

## Verify HTTP requests sent via an app proxy

See [`ShopifyApp::AppProxyVerification`](/lib/shopify_app/controller_concerns/app_proxy_verification.rb).

The engine provides a mixin for verifying incoming HTTP requests sent via an App Proxy. Any controller that `include`s `ShopifyApp::AppProxyVerification` will verify that each request has a valid `signature` query parameter that is calculated using the other query parameters and the app's shared secret.

### Recommended usage of `ShopifyApp::AppProxyVerification`

The App Proxy Controller Generator automatically adds the mixin to the generated app_proxy_controller.rb
Additional controllers for resources within the App_Proxy namespace, will need to include the mixin like so:

```ruby
# app/controllers/app_proxy/reviews_controller.rb
class ReviewsController < ApplicationController
  include ShopifyApp::AppProxyVerification
  # ...
end
```
