### Title
Unbounded EIP-7702 authorization-list loop executed under an infinite gas meter before intrinsic-gas admission - (File: x/evm/ante/preprocess.go)

### Summary
`EVMPreprocessDecorator.AnteHandle` iterates over every EIP-7702 `SetCodeAuthorizations()` entry in an incoming `MsgEVMTransaction` and, for each one, performs full ECDSA signature recovery plus a store-backed address-association attempt, all while the ante context is running under `sdk.NewInfiniteGasMeterWithMultiplier`. This loop runs *before* `BasicDecorator` validates intrinsic gas, so its cost is bounded only by how many authorization tuples the attacker can fit into a transaction, not by any enforced gas or count limit at the point the loop executes.

### Finding Description
The EVM ante chain in `NewAnteHandler` is ordered as: `EVMNoCosmosFieldsDecorator` → `EVMPreprocessDecorator` → `BasicDecorator` → `EVMFeeCheckDecorator` → `EVMSigVerifyDecorator` → `GasDecorator`. [1](#0-0) 

`EVMPreprocessDecorator.AnteHandle` sets an infinite gas meter and then calls `associateAuthorizationAuthorities`, which loops over `ethTx.SetCodeAuthorizations()` with no cap on the number of iterations: [2](#0-1) [3](#0-2) 

For every authorization tuple, `helpers.AuthorityToPreAssociate` recovers the authority's public key via full `ecrecover`/RLP encoding (`RecoverAddressesFromAuthorization`), checks chain ID / nonce / code, and — if not already associated — attempts a cache-context `AssociateAddresses` call: [4](#0-3) [5](#0-4) 

Only *after* this loop completes does `BasicDecorator` compute `core.IntrinsicGas(...)` (which does account for a per-authorization cost) and reject the transaction if `etx.Gas() < intrGas`: [6](#0-5) 

Because the EVM ante pipeline is a separate router path that does not run the standard Cosmos `NewConsumeGasForTxSizeDecorator` (that decorator is only present in the non-EVM `anteDecorators` list), there is no gas-metered cost charged for iterating the authorization list before this expensive work is performed: [7](#0-6) 

The identical unmetered iteration also exists in the DeliverTx-specific legacy ABCI path: [8](#0-7) 

This matches the reported bug class precisely: a `for` loop bounded by an attacker/user-controlled collection size (the authorization list) with no enforced maximum, executed in a security-critical code path (`EVMPreprocessDecorator`, part of the EVM ante pipeline) reachable from a single submitted transaction.

### Impact Explanation
The number of authorizations that fit in a `SetCodeTx` is limited only by whatever transaction-size admission limit CometBFT/mempool enforces (referenced indirectly by the exclusion for `test_many_delegations` in `integration_test/exec_specs/config/remote-exclusions.list` as exceeding "Sei/Cosmos admission-size limits" — the exact numeric limit was not located in the indexed code, so the precise iteration ceiling could not be confirmed). Within that byte budget, an attacker can pack thousands of authorization tuples (~100 bytes each) into one transaction. Each tuple forces the ante handler to perform elliptic-curve signature recovery and a Cosmos-SDK cache-context read/association attempt — all under an infinite gas meter and prior to intrinsic-gas rejection. A validator processing such a transaction (or several in the same block, since CheckTx also runs this same unmetered loop per `EvmCheckTxAnte`) could see materially increased per-transaction CPU time in both `CheckTx` and `DeliverTx`, directly threatening block-production timing (the required <2.5s target) if enough such transactions are crafted, since the cost is not gas-priced and thus not economically deterred proportional to actual computation performed.

### Likelihood Explanation
Likelihood is limited by (a) the transaction still ultimately failing intrinsic-gas or fee checks if the attacker cannot pay for the declared gas, and (b) an unconfirmed but apparently-enforced tx-size admission ceiling that bounds the maximum authorization-list length. Because the loop's cost is incurred *before* those downstream checks reject the transaction, and because it runs identically (and for free, from the attacker's perspective, if the tx is ultimately rejected without fees being deducted) in `CheckTx`, an attacker can repeatedly resubmit maximally-sized SetCode transactions to the mempool of any node to burn CPU cycles without cost, which is a realistic and repeatable attack vector rather than a one-off edge case.

### Recommendation
- Enforce a documented, on-chain maximum authorization-list length before entering `associateAuthorizationAuthorities` in `x/evm/ante/preprocess.go` and the corresponding legacy-ABCI path in `app/ante/evm_delivertx.go` / `app/ante/evm_checktx.go`, rejecting the transaction early if exceeded.
- Move (or duplicate) the intrinsic-gas check (`core.IntrinsicGas`, currently in `BasicDecorator`) ahead of `EVMPreprocessDecorator` in the EVM ante chain ordering so the authorization-list cost is gas-checked before any per-authorization work is performed, in both `CheckTx` and `DeliverTx` paths.
- Charge metered gas (rather than relying on the infinite gas meter) for each `ecrecover`/association attempt performed in the pre-association loop, so cost scales with the actual work done and is capped by the declared, fee-backed gas limit.

### Proof of Concept
1. Craft an EIP-7702 `SetCodeTx` (`ethtx.SetCodeTx`) whose `AuthList` contains the maximum number of authorization tuples that fit under the node's transaction-size admission limit (each tuple: chainId, address, nonce, r, s, yParity — approximately valid/garbage signatures are fine since `RecoverAddressesFromAuthorization` performs full `ecrecover` work regardless of whether the signature ultimately validates to a useful authority).
2. Set the transaction's declared `Gas` field low enough that it will fail `core.IntrinsicGas` validation (or leave the sender underfunded so `EVMFeeCheckDecorator` rejects it) — since these checks only run *after* `EVMPreprocessDecorator`, the entire authorization-recovery loop still executes and its cost is fully incurred.
3. Submit this transaction via `broadcast_tx_sync`/`CheckTx` to a node's public RPC repeatedly; since fees are never deducted (rejection happens post-loop), the transaction can be resubmitted cheaply and indefinitely, while each submission forces the node to perform the full unmetered `AuthorityToPreAssociate` loop over the crafted authorization list, as seen in `EVMPreprocessDecorator.AnteHandle` (`x/evm/ante/preprocess.go:110`) and `EvmCheckTxAnte` (`app/ante/evm_checktx.go:65`).
4. Measure `CheckTx`/`DeliverTx` latency for these transactions versus a baseline transaction to observe the disproportionate, size-driven CPU cost incurred before any gas is charged.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}

// RecoverAddressesFromAuthorization recovers the EVM address, Sei address, and public
// key of the account that signed an EIP-7702 SetCode authorization (the "authority").
// The authorization sig hash is keccak256(0x05 || rlp([chainId, address, nonce])) and
// the recovery id is carried directly in auth.V (yParity, 0 or 1), which GetAddresses
// expects bumped by 27. This mirrors go-ethereum's SetCodeAuthorization.Authority(), but
// additionally returns the recovered public key so the authority can be associated with
// its true Sei address.
func RecoverAddressesFromAuthorization(auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	var buf bytes.Buffer
	buf.WriteByte(eip7702MagicPrefix)
	if err := rlp.Encode(&buf, []any{auth.ChainID, auth.Address, auth.Nonce}); err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, err
	}
	sigHash := crypto.Keccak256Hash(buf.Bytes())
	v := new(big.Int).SetUint64(uint64(auth.V) + 27)
	return GetAddresses(v, auth.R.ToBig(), auth.S.ToBig(), sigHash)
}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
