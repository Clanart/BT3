### Title
Coinbase outputs are reported as spendable wallet inputs before maturity - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_block` scans `block.txdata[0]`, the coinbase transaction, along with ordinary transactions. A miner can therefore cause a `ReceivedOutput` to be reported for a Serai-controlled script even though consensus prevents that output from being spent for 100 blocks.

### Finding Description
`scan_transaction` accepts every matching transaction output and converts it into a `ReceivedOutput` without checking whether the containing transaction is coinbase or whether its coinbase maturity interval has elapsed. [1](#0-0)  `scan_block` then iterates over all transactions in `block.txdata`, explicitly including index `0`. [2](#0-1) 

The resulting `ReceivedOutput` is indistinguishable from an immediately spendable payment: it carries the output value, outpoint, and spend offset through the same representation used for ordinary outputs. [3](#0-2)  The signing path treats all supplied `ReceivedOutput` values as transaction inputs and signs a sighash committed to all of their prevouts. [4](#0-3) 

The function comment acknowledges that the caller must post-process coinbase outputs or scan `block.txdata[1 ..]`. [5](#0-4)  However, the API itself still reports a not-currently-spendable coinbase output through the normal `ReceivedOutput` channel.

### Impact Explanation
A miner can send a newly created coinbase output to a scanned Serai address. Consumers of `scan_block` can then account for that output as received funds and select it for spending even though Bitcoin consensus rejects a spend before coinbase maturity.

This can cause deposits to be credited before the represented funds are actually spendable and can cause subsequently generated withdrawal transactions to be invalid. If multiple outputs are aggregated, one immature coinbase input can invalidate the entire transaction rather than merely delaying that input.

### Likelihood Explanation
Any miner producing a block can place the Serai script in the coinbase transaction; no private key, validator access, malformed encoding, or trusted input is required. Exploitation requires a consumer to use `scan_block` directly without applying the documented post-processing step.

### Recommendation
Do not return coinbase outputs from `Scanner::scan_block`. Scan `block.txdata[1 ..]` in the API, or record coinbase outputs separately with enough block-height context to suppress them until they satisfy Bitcoin's 100-block maturity rule. If compatibility requires retaining the current behavior, expose an explicit `including_immature_coinbase` API rather than returning coinbase outputs as ordinary `ReceivedOutput` values.

### Proof of Concept
1. Construct a `Scanner` for an even group key.
2. Mine a Bitcoin block whose coinbase has an output paying `p2tr_script_buf(key)`.
3. Call `scanner.scan_block(&block)`.
4. The function returns a `ReceivedOutput` whose outpoint refers to the coinbase transaction.
5. Pass that `ReceivedOutput` into `SignableTransaction::new`/`TransactionSignMachine` immediately.
6. The resulting signed transaction commits to that coinbase prevout, but Bitcoin consensus rejects it until the coinbase reaches maturity.

  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));

    res
