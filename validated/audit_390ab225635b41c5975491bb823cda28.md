### Title
Checks-Effects-Interactions violation in escrow withdrawal allows reentrant double-release of funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core broken invariant is: *a low-level `call()` hands control to an address before the caller's state is finalized, and the callee can leverage that window to corrupt protocol accounting.* In Hyperbridge's Tron `IntentGatewayV2`, the escrow-release function `withdraw()` performs exactly this pattern — it sends value to an attacker-influenced address (or invokes an attacker-influenced token contract) via `.call(...)` *before* decrementing the escrow ledger — unlike the hardened equivalent (`IntentsBase.sol::_withdraw`) used by the main EVM IntentGateway, which decrements first.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` releases escrowed order funds to `beneficiary`: [1](#0-0) 

For each token in `body.tokens`, the function:
1. Checks `_orders[commitment][token] == 0` (only a non-zero check, not an exact-amount check).
2. Performs a low-level `.call` — either a native ETH transfer to `beneficiary`, or `token.call(transfer(...))` where `token` is fully attacker-selectable at order-creation time.
3. **Only after** the external call returns does it decrement `_orders[body.commitment][token] -= amount`.

This is the inverse of the safe ordering used elsewhere in the same codebase. The equivalent function in the current/main EVM app explicitly writes the effect first: [2](#0-1) 

Both `beneficiary` (the solver for `RedeemEscrow`, or the original user for `RefundEscrow`) and `token` (chosen by the order creator when the order was placed) are attacker-influenceable, ordinary, unprivileged values — no relayer, prover, or admin collusion is required to control them. Because the ledger entry `_orders[commitment][token]` is still unmodified at the moment control is handed to `beneficiary`/`token`, any code that gets executed during that `.call` (a malicious `receive()` for native transfers, or an attacker-authored `transfer()` implementation on a malicious ERC-20 used as the order's input token) runs while the escrow accounting still shows the full, undecremented balance for that (commitment, token) pair. This directly matches the report's primitive: "attacker constructs payload… during the low-level call, executes before the caller's protective state is set."

The same call-before-effect pattern also appears in the fee-forwarding tail of the function and in `onAccept`'s `SweepDust` handling in the same file, both of which perform the external transfer before clearing/decrementing the corresponding balance entry: [3](#0-2) 

### Impact Explanation
If a second entry into the vulnerable accounting path can be triggered during the reentrant window (e.g. via a `body.tokens` array containing more than one escrow leg for the same commitment being processed in the same call, or via any other permissionless path that reads/writes `_orders[commitment][token]` — this codebase also tracks `_partialFills` for same-chain fills, which is a plausible additional entry point I was not able to fully audit within the available tool budget), the escrow for a single settled order could be paid out more than once, i.e. **loss/duplicate release of bridged/escrowed funds to the wrong or same beneficiary twice** — squarely within the bounty's "stealing or loss of funds" / "double-claim/double-settlement" categories.

### Likelihood Explanation
Medium-to-uncertain. The `_filled[commitment]` finalize flag is set correctly *before* the loop (so a naive "call `withdraw` twice for the same commitment from a fresh top-level message" is not the primary vector), and I could not locate/verify the Tron Host contract in this index to confirm whether it mirrors the main `EvmHost.sol`'s receipt-before-call replay protection for `dispatchIncoming`/`onAccept`. That verification gap means I cannot fully confirm end-to-end exploitability of a *second* invocation of `withdraw` for the same commitment; what is concretely and locally provable is the CEI-violation itself — external call executed with attacker-controlled code before the corresponding `_orders[commitment][token]` state is updated, which is a real deviation from the safe pattern used in the sibling `IntentsBase.sol` implementation and a latent reentrancy hazard regardless of which exact second-entry path is used.

### Recommendation
- In `withdraw()` (and the `SweepDust`/fee-forwarding blocks) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, decrement/clear the relevant `_orders[...]` mapping entries **before** performing the external `.call`/token transfer, mirroring the pattern already used in `IntentsBase.sol::_withdraw`.
- Add an explicit `nonReentrant` guard (already used elsewhere in `evm/src/apps/IntentGatewayV2.sol`) to `onAccept`/`onGetResponse`/`withdraw` in the Tron contract for defense in depth.
- Audit all other permissionless paths (e.g. `_partialFills`) that touch `_orders[commitment][token]` to confirm none can be reached mid-reentrancy.

### Proof of Concept
1. Attacker places an order using a self-deployed, "malicious" ERC-20-like `token` as an input asset, escrowing `amount` into `_orders[commitment][token]`.
2. Attacker (as solver) legitimately fills the order on the destination chain, causing a valid `RedeemEscrow` PostRequest to be dispatched back with `beneficiary` = attacker-controlled address.
3. Hyperbridge relays this request; `onAccept` → `withdraw(body, false)` executes on `IntentGatewayV2.sol` (tron):
   - `_orders[commitment][token]` is still `amount` (nonzero) when `token.call(transfer(beneficiary, amount))` is invoked.
   - Because `token` is attacker-authored code, execution control passes to the attacker at this point, with `_orders[commitment][token]` still un-decremented — the exact corrupted value described above.
4. Depending on what other state-mutating entry point can be reached from that attacker-controlled code during this window (native `receive()` reentry, or the malicious token's own logic calling back into the gateway through any reachable path touching the same `_orders[commitment][token]` slot), a second release against the same escrow balance becomes possible before the original call returns and applies its decrement.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
