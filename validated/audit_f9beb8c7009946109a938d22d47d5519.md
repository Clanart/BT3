## Analysis

The Fastssz report's underlying bug class is a **decoder differential**: the same untrusted bytes are interpreted into two different shapes by two different code paths (one used for validation, another for consensus-critical processing), and an attacker can craft input that is "safe" under one interpretation but different — and harmful — under the other.

The closest verifiable analog in this codebase is a **hostname-parsing differential** in the git remote URL parser used for credential/account selection.

### The corrupted value

`app/src/lib/remote-parsing.ts` implements `parseRemote()` with a hand-rolled regex instead of a standards-compliant URL parser: [1](#0-0) 

The HTTPS pattern is:
```
^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$
``` [2](#0-1) 

Both `.+` groups are greedy and `.` matches `/`. The optional `(?:.+@)?` "userinfo" prefix is not anchored to the authority component (it can consume path segments before the first `/`), and the hostname group `(.+)` simply grabs everything up to the last two `/`-separated path segments. Per RFC 3986 / WHATWG `URL`, the authority (hostname) of a URL ends at the **first** `/`, `?`, or `#` after `://` — an `@` appearing later, inside the path, has no bearing on host resolution.

For an input such as:
```
https://evil.com/x@github.com/octocat/Hello-World.git
```
- Real URL authority (what git/libcurl will actually connect to): **`evil.com`**
- `parseRemote()`'s regex: `(?:.+@)?` greedily consumes `evil.com/x@`, leaving hostname group `(.+)` = **`github.com`**, owner=`octocat`, name=`Hello-World`.

This is the "corrupted value": Desktop's own hostname extraction disagrees with the actual network authority for the exact same string.

### Where it is trusted

`findAccountForRemoteURL()` uses this mis-parsed hostname to decide which signed-in account's token should be treated as matching the remote: [3](#0-2) 

It compares `parsedURL.hostname` (from the flawed regex) against each account's endpoint host (parsed correctly via `getHTMLURL`/`URL.parse`), and returns the account whose hostname matches. If the attacker forces `parseRemote` to report `github.com` for a URL whose real authority is `evil.com`, the user's real GitHub.com account is selected as "matching" a remote that actually points at the attacker's server.

### The attacker-controlled entry point

This URL is reachable from an unprompted, attacker-controlled surface: GitHub Desktop's custom protocol handler. `parseAppURL()` extracts an `open-repository-from-url` action whose `url` field is taken verbatim from the deep link with no host validation: [4](#0-3) 

`dispatchURLAction` routes this straight into `openRepositoryFromUrl` → `openOrCloneRepository(url)`: [5](#0-4) [6](#0-5) 

A link such as `x-github-client://openRepo/https://evil.com/x@github.com/octocat/repo.git` requires only a single click by the victim — matching the "link/deep link the user clicks" impact category.

### Why existing guards don't stop this

- `parseAppURL` only validates the `branch`/`pr` query parameters (`testForInvalidChars`, digit/format regexes) — the `url` itself is passed through unchecked.
- `findAccountForRemoteURL`'s comparison uses `parseRemote`'s non-standard hostname extraction rather than a proper `URL`/`url.parse` authority parse, so it never sees the true host.
- Other parts of the codebase (`api.ts`, `trampoline-credential-helper.ts`, `same-origin-filter.ts`) correctly use `URL.parse`/`new URL()` for authority extraction, so the mismatch is confined to this one non-standard parser — but it's exactly the parser used for the account/credential-matching decision.

### What I could not fully verify

I was not able to read the full body of `openOrCloneRepository` (in `dispatcher.ts`) within the available budget to trace the final step that would confirm the mismatched-hostname account is actually used to attach the GitHub.com token to the outgoing HTTPS request/clone against `evil.com` (versus git's own credential-helper flow independently rejecting the mismatched host later). The trampoline credential helper (`trampoline-credential-helper.ts`, using `new URL()`/`isDotCom`) appears to independently gate credential handoff by the *real* request host, which could act as a secondary control that prevents the token from reaching `evil.com` even if `findAccountForRemoteURL` mis-selects an account earlier for UI/state purposes. Confirming whether that secondary control fully neutralizes the parsing differential (or whether the mis-selected account otherwise leaks information, e.g. via cloning as an authenticated user of a private-looking URL, or mismatched-repo state confusion) requires tracing `openOrCloneRepository` and the store methods it calls, which I could not complete this session.

Given this residual uncertainty about the final credential-attachment step, I cannot assert with full confidence that token exfiltration is achievable end-to-end; I can only confirm the parsing differential itself and its use in account/credential matching logic. I'd recommend a Devin session with full repository access to trace `openOrCloneRepository`, `AppStore._openOrCloneRepository` (or equivalent), and the clone/fetch credential-attachment path to determine definitively whether the mismatched hostname reaches an actual token-bearing network request.

export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
```
