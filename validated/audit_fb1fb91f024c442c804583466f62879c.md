### Title
Attacker-controlled `n`/`t` in `ThresholdKeys::read` triggers O(t²) Lagrange interpolation with t field inversions during deserialization - (File: crypto/dkg/src/lib.rs)

### Summary
The Django advisory is a complexity-class bug: a cheap-to-produce input forces the victim to perform disproportionately expensive computation (NFKC normalization). The Serai analog lives in `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg/src/lib.rs`: a serialized `ThresholdKeys` blob lets the sender pick `t` and `n` (each up to `u16::MAX = 65535`), and reconstruction of `group_key` runs Lagrange `interpolation_factor` for every one of the `t` participants, where each call iterates over all `t` indexes and performs a field inversion — O(t²) scalar multiplications plus t modular inversions, on top of `n` canonical point decompressions.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the untrusted byte stream (dkg/src/lib.rs:591-602), then reads `n` scalars and `n` points (lines 604-623) and calls `ThresholdKeys::new` (lines 625-631). `ThresholdParams::new` only enforces `0 < t <= n <= 65535` (lines 166-179). `ThresholdKeys::new` computes the group key as the sum over participants `1..=t` of `verification_shares[i] * interpolation.interpolation_factor(i, &t)` (lines 376-378). For `Interpolation::Lagrange`, `interpolation_factor` loops over all `t` included participants performing a scalar multiply each, and then calls `denom.invert().unwrap()` (lines 229-247). So the total work is `t × t` scalar multiplications and `t` field inversions — with `t = 65535`, roughly 4.3 × 10^9 field multiplications and 65535 inversions from a single ~4 MB input, plus 65535 `read_G` decompressions each doing a `from_bytes` + `to_bytes` canonicality round-trip (ciphersuite/src/lib.rs:91-101).

### Impact Explanation
An unprivileged party who can get a victim to deserialize a `ThresholdKeys` blob (`ThresholdKeys::read` is a public API intended for loading keys received/loaded by participants) forces minutes-to-hours of CPU burn in a single call. This is the same DoS shape as CVE-2025-64458: a bounded but attacker-maximizable parameter drives superlinear cryptographic work with no pre-validation cap.

### Likelihood Explanation
`ThresholdKeys::serialize`/`read` are the persistence/transport format for DKG outputs; any deployment that reads key material from a shared store, message, or peer-provided blob exposes this. Setting `t = n = 65535` requires no secrets, no valid shares — `from_repr`/`from_bytes` accept any canonical scalars/points, and the quadratic interpolation runs inside `ThresholdKeys::new` before any semantic validity would matter. Cost to the attacker is ~4 MB of bytes; cost to the victim is billions of field operations.

### Recommendation
Cap `t`/`n` at a protocol-realistic bound in `ThresholdParams::new` (real deployments are at most a few hundred signers) or reject oversized parameters in `ThresholdKeys::read` before allocating/looping. Additionally, precompute a single `included` product or use batch inversion for the denominators so `ThresholdKeys::new` interpolation is O(t) inversions total rather than O(t) each, and compute the group key with `multiexp_vartime` instead of `t` individual scalar-point multiplications.
