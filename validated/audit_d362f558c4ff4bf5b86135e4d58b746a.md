## Analysis

**Binding claimed to be broken:** `operator_xonly_pk` recovered from the payout transaction's OP_RETURN (used both in `Verifier::update_finalized_payouts`/`is_kickoff_malicious` and in `bridge_circuit`'s `deposit_constant`) **should equal** the identity of whoever actually funded the payout output. I traced this and confirmed the binding is **not enforced** — it is trivially forgeable by anyone who holds a withdrawal signature, including the withdrawer themselves.

### Root cause: SIGHASH_SINGLE|ANYONECANPAY leaves the OP_RETURN unsigned

The withdrawal signature accepted by the protocol is required to use `TapSighashType::SinglePlusAnyoneCanPay`: [1](#0-0) 

This sighash type only commits to input 0 (ANYONECANPAY) and the *single* output at the same index (0) — the user's own payout output. It does **not** cover output 1 (anchor) or output 2, the OP_RETURN carrying the operator's `xonly_pubkey`: [2](#0-1) 

Because ANYONECANPAY also allows arbitrary additional inputs to be appended, **any holder of a valid withdrawal signature** — which per the threat model includes the withdrawer/attacker themselves, since they generate this very signature when calling `withdraw`/`Withdraw` — can independently construct and broadcast an alternate, still-validly-signed payout transaction that:
- spends the exact same withdrawal UTXO with the same signature,
- keeps output 0 (payout to self) intact,
- funds any extra value itself,
- and sets output 2's OP_RETURN to **any operator's `xonly_pubkey`**, including a completely uninvolved, honest operator's key.

### Downstream: blind trust in the OP_RETURN

`update_finalized_payouts` parses whatever xonly pubkey appears in the OP_RETURN with no cross-check against who actually funded the transaction's other inputs: [3](#0-2) 

This value is persisted as `payout_payer_operator_xonly_pk` in the `withdrawals` table: [4](#0-3) 

The victim operator's own automation polls this table filtered by **its own key** and, with no verification that it itself broadcast the transaction, proceeds to claim reimbursement: [5](#0-4) [6](#0-5) 

`is_kickoff_malicious` — the guard meant to catch mismatched attribution — only checks that the kickoff's declared operator matches the (attacker-forged) DB value and that the committed blockhash matches; it has no way to verify who funded the payout's extra inputs: [7](#0-6) 

Finally, `deposit_constant`/`host_deposit_constant` in the bridge circuit derive `operator_xonlypk` from the same forgeable OP_RETURN field, so the ZK proof is internally self-consistent (kickoff operator == OP_RETURN operator) but never proves that operator actually funded the payout: [8](#0-7) [9](#0-8) 

### Impact

An attacker (the withdrawer) can self-fund their own withdrawal payout and stamp an arbitrary, uninvolved operator's public key into the unsigned OP_RETURN output. That operator's own automated `PayoutCheckerTask` will then autonomously issue a kickoff and, absent a challenge disproving the underlying funding source (which nothing in this codebase checks), claim reimbursement for a payout it never made — draining that deposit's bridge_amount to an operator with zero real expenditure. This matches the Critical category "an operator reimbursed for a payout it never funded," and is repeatable per withdrawal/deposit against any operator whose public xonly key is known (which is generally public information for registered operators).

### Title
Forgeable payout OP_RETURN operator attribution via unsigned output under SIGHASH_SINGLE|ANYONECANPAY enables reimbursement of a payout an operator never funded - (File: core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs, core/src/database/verifier.rs, core/src/task/payout_checker.rs)

### Summary
The mandated withdrawal sighash type `SinglePlusAnyoneCanPay` never commits to the payout transaction's OP_RETURN output, so anyone holding a valid withdrawal signature — including the withdrawer/attacker itself — can broadcast an alternate, still-valid payout transaction that keeps the required payout output but rewrites the OP_RETURN to name an arbitrary, uninvolved operator as the payer. `update_finalized_payouts` blindly records this forged identity, and that operator's own `PayoutCheckerTask` automation will subsequently issue a kickoff and claim reimbursement for a payment it never made.

### Finding Description
Broken binding: `operator_xonly_pk` parsed from `payout_tx`'s OP_RETURN (`parse_op_return_data` / `XOnlyPublicKey::from_slice` in `Verifier::update_finalized_payouts`, `circuits-lib/src/bridge_circuit/mod.rs::deposit_constant`) should equal "the operator that actually funded the payout's additional inputs," but nothing enforces this equality.

Root cause: the withdrawal signature must be `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs::parse_withdrawal_sig_params`), which under BIP-341 signs only input 0 (ANYONECANPAY) and output 0 (SIGHASH_SINGLE). `create_payout_txhandler` places the operator-identifying OP_RETURN at output 2, entirely outside the signed message. Anyone possessing that signature (the withdrawer/attacker themselves, since they produce it) can build a competing payout transaction — same withdrawal input+signature, same output 0, self-funded additional inputs (ANYONECANPAY permits appending inputs), and any OP_RETURN payload — and broadcast/race it into confirmation instead of the legitimate operator's payout tx.

`update_finalized_payouts` (`core/src/verifier.rs`) then writes whatever xonly pubkey is embedded in that OP_RETURN into `withdrawals.payout_payer_operator_xonly_pk` with no check against the actual funding source. The targeted, entirely uninvolved operator's own `PayoutCheckerTask` (`core/src/task/payout_checker.rs`) polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered by its own key and, finding this forged row, calls `handle_finalized_payout`, issuing a real kickoff for reimbursement. `is_kickoff_malicious` (`core/src/verifier.rs`) only cross-checks the (attacker-forged) DB operator key against the kickoff's declared operator and the payout blockhash — both of which are internally consistent because the kickoff really is issued by that key and the blockhash is real — so the guard passes. The bridge circuit's `deposit_constant`/`journal_hash` derive `operator_xonlypk` from the same forgeable field, so the ZK proof only proves self-consistency between the kickoff and OP_RETURN, never that the named operator funded the payout.

### Impact Explanation
The deposit's escrowed `bridge_amount` is released via the standard kickoff→challenge-timeout→Reimburse path to an operator who performed no fronting work, at zero cost to the attacker beyond funding their own withdrawal (which they receive anyway). This is a direct instance of "an operator reimbursed for a payout it never funded" (Critical). The attack is repeatable against any withdrawal and any operator whose xonly pubkey is known (operator keys are protocol-public), and scales across every deposit processed through the standard (non-optimistic) payout path.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's granted capabilities: the ability to deposit/withdraw via the Citrea bridge contract, choose a Schnorr signature and sighash flag, and broadcast a Bitcoin transaction. No verifier, operator, or aggregator privilege is needed, and no race against a specific honest operator's broadcast is even strictly required — the attacker can simply be the first (or only) party to submit the payout tx with a forged OP_RETURN. Cost is limited to normal Bitcoin fees and self-funding their own withdrawal amount, which they already intend to receive.

### Recommendation
Bind the operator identity cryptographically to the funding of the payout, e.g., by requiring the withdrawal signature to cover the OP_RETURN output (use `SIGHASH_ALL` semantics for a fixed-shape transaction template, or fold a commitment to the operator pubkey into the signed message/output set), or by having verifiers/operators require the OP_RETURN operator pubkey to be one who has proven (via wallet-level provenance or a separate signature) that they supplied the extra funding inputs, rather than trusting arbitrary bytes taken from an unsigned output.

### Proof of Concept
`cargo test` in `core/src`:
1. Build a withdrawal UTXO and derive a `SinglePlusAnyoneCanPay` signature over it and a chosen payout output (as done in `generate_withdrawal_transaction_and_signature`/`sign_withdrawal_output`).
2. Using `create_payout_txhandler`, construct transaction A with `operator_xonly_pk = victim_operator_pk` (a key never involved in the deposit) and separately transaction B with `operator_xonly_pk = real_operator_pk`, both reusing the identical signed input/output 0 but differing only in the OP_RETURN (output 2) and additional funding inputs — assert both signatures verify (`SECP.verify_schnorr`) against the same sighash, proving the OP_RETURN is unconstrained.
3. Feed transaction A through `Verifier::update_finalized_payouts` (via a constructed `block_cache::BlockCache`) and assert `db.get_payout_info_from_move_txid` returns `Some(victim_operator_pk)`.
4. Assert `payout_checker`'s `get_first_unhandled_payout_by_operator_xonly_pk(victim_operator_pk)` now returns this withdrawal, despite `victim_operator_pk` never having constructed or broadcast the payout transaction — demonstrating the forged attribution flows directly into the reimbursement-triggering path.
