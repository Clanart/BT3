### Title
Corrupted lazy-field bytes are not cleared, causing `getSerializedSize()`/`toByteString()` to diverge from `writeTo()` output - (File: `java/core/src/main/java/com/google/protobuf/LazyFieldLite.java`)

### Summary
`LazyFieldLite.ensureInitialized()` sets a `corrupted` flag and resets the *parsed* value (`value`) and cached bytes (`memoizedBytes`) to a safe empty state when the delayed bytes fail to parse, but it never clears `delayedBytes` itself. Because `toByteString()` and `getSerializedSize()` both check `delayedBytes` *before* `memoizedBytes`, they keep returning the stale, pre-corruption raw bytes/size, while `writeTo()` checks `memoizedBytes` first and writes the empty result. This is the same bug class as the Citadel finding: a flag is set to signal "this data is invalid/should not be trusted," but the underlying value is not correspondingly reset, so different code paths keep consuming stale data.

### Finding Description
`ensureInitialized(MessageLite defaultInstance)` is the routine that lazily parses a length-delimited sub-message stored in `delayedBytes`: [1](#0-0) 

On parse failure it does:
```java
this.corrupted = true;
this.value = defaultInstance;
this.memoizedBytes = ByteString.EMPTY;
```
but `delayedBytes` (the original, unparseable bytes) is left untouched. This violates the class's own documented state machine, which says any reader must consistently prefer `memoizedBytes`/`delayedBytes` over the parsed `value` for serialization [2](#0-1) , but that document implicitly assumes only one of them holds "true" data at a time — after the corruption path runs, both `delayedBytes` (stale/original) and `memoizedBytes` (fresh/empty) are simultaneously non-null and disagree.

Three consumer methods now disagree about the field's serialized representation:
- `toByteString()` returns `delayedBytes` (the stale, corrupt bytes) because it is checked first: [3](#0-2) 
- `getSerializedSize()` returns `delayedBytes.size()` (the stale, non-zero size) for the same reason: [4](#0-3) 
- `writeTo()` instead checks `memoizedBytes` first, and writes the now-empty `ByteString.EMPTY`: [5](#0-4) 

So for a corrupted lazy field, `getSerializedSize()` reports the size of the *original* bytes while `writeTo()` writes *zero* bytes for that field.

### Impact Explanation
`AbstractMessageLite.toByteArray()`/`toByteString()` — the standard public serialization path for any `MessageLite`, i.e. `Message#toByteArray()` that ordinary application/client code calls after `parseFrom()` — pre-allocates an output buffer sized exactly by `getSerializedSize()` and then calls `writeTo()` to fill it: [6](#0-5) 

If a message contains a lazily-parsed sub-message/extension that fails to parse (attacker-controlled malformed bytes for that inner message, e.g. an invalid varint or invalid embedded field, while the outer message and length-delimiting framing are perfectly valid), the outer message's computed size will overcount by the size of the corrupted inner bytes, while `writeTo()` only emits an empty field for that slot. This desynchronizes the declared/allocated length from the actual bytes produced for that field. Downstream, this breaks the wire-format invariant that `getSerializedSize()` == number of bytes actually written, corrupting any outer length-delimited framing (e.g., the parent message or a length-prefixed stream) that relies on that value, and can leave allocated buffers under-filled/inconsistent. This is a data-integrity break in the serialization contract that an ordinary parse→re-serialize round trip on attacker-supplied bytes can trigger — directly analogous to the Citadel bug where a "flag was set but the underlying value wasn't correspondingly updated," letting an unprivileged actor drive downstream logic (here, wire-size accounting) off of stale/inconsistent state.

### Likelihood Explanation
This requires: (1) a message using `LazyFieldLite` (Java Lite generated code for `lazy=true` message fields or lazily-parsed extensions), and (2) attacker-supplied bytes for that inner field that fail to parse (e.g., a truncated/invalid sub-message) while the outer envelope remains well-formed so parsing overall succeeds and the app later re-serializes the object. Both conditions are reachable through the fully public, bounded, `parseFrom()` → `toByteArray()` path with no privileged access required — an ordinary client can craft such bytes deterministically. This is a Medium/High-likelihood defect once the schema uses lazy message fields, since the trigger is purely a malformed nested submessage, not any resource-exhaustion or huge-input condition.

### Recommendation
In `ensureInitialized()`'s catch block, clear `delayedBytes` (set it to `null`) at the same time `value`/`memoizedBytes` are reset to the safe empty state, so all three getters (`toByteString()`, `getSerializedSize()`, `writeTo()`) consistently treat the field as empty once `corrupted` is set — mirroring the Citadel fix recommendation of "always update the underlying data whenever the flag/state changes," rather than only flipping a flag and leaving stale bytes referenced elsewhere.

### Proof of Concept
Conceptual reproduction (bounded, ordinary API usage, no special privileges):
1. Build an outer `MessageLite` whose generated code stores a specific sub-message field in a `LazyFieldLite` (lazy message field or extension).
2. Serialize the outer message but substitute the inner field's length-delimited payload with bytes that are well-formed enough to pass outer framing but fail to parse as the target sub-message type (e.g., corrupt a required varint tag inside).
3. Call `OuterMessage.parseFrom(bytes)` — parsing succeeds; the lazy field is stored in `delayedBytes` and not yet parsed.
4. Access something that triggers `ensureInitialized()` (e.g., call the corresponding getter), which fails to parse, sets `corrupted = true`, `value = defaultInstance`, `memoizedBytes = ByteString.EMPTY`, but leaves `delayedBytes` non-null with the original corrupt bytes: [7](#0-6) 
5. Call `outerMessage.getSerializedSize()` — for that field it returns `delayedBytes.size()` (non-zero, original size): [8](#0-7) 
6. Call `outerMessage.toByteArray()`, which pre-sizes the buffer using step 5's value, then calls `writeTo()`, which for that field writes `memoizedBytes` (`ByteString.EMPTY`, zero bytes): [9](#0-8) 
7. Result: the allocated/declared size and the actually-written bytes for the field diverge — demonstrating the stale-state/flag inconsistency.

I was not able to execute this reproduction in a live JVM within this session (no code-execution tool available here); the analysis above is based on direct reading of the cited source lines, which show the unconditional divergent-priority checks (`delayedBytes` first in `toByteString()`/`getSerializedSize()`, `memoizedBytes` first in `writeTo()`) combined with the catch block that updates `value`/`memoizedBytes` but not `delayedBytes`. Confirming the downstream effect on an actual outer-message length prefix or `CodedOutputStream` buffer would require running this reproduction with generated lazy-field message classes, which a Devin session with code execution could verify.

  protected void ensureInitialized(MessageLite defaultInstance) {
    if (value != null) {
      return;
    }
    synchronized (this) {
      if (value != null) {
        return;
      }
      try {
        if (delayedBytes != null) {
          // The extensionRegistry shouldn't be null here since we have delayedBytes.
          MessageLite parsedValue =
              defaultInstance.getParserForType().parseFrom(delayedBytes, extensionRegistry);
          this.value = parsedValue;
          this.memoizedBytes = delayedBytes;
        } else {
          this.value = defaultInstance;
          this.memoizedBytes = ByteString.EMPTY;
        }
      } catch (InvalidProtocolBufferException e) {
        // Nothing is logged and no exceptions are thrown. Clients will be unaware that this proto
        // was invalid.
        this.corrupted = true;
        this.value = defaultInstance;
        this.memoizedBytes = ByteString.EMPTY;
      }
    }
  }
