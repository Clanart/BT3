## Finding

### Title
Unauthenticated `address` field lets any caller mint reputation rewards to an arbitrary beneficiary in `pallet-state-coprocessor::handle_get_requests` - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
The external report's core invariant is "an actor who can influence a mint call can direct unlimited/unbound token creation to a beneficiary of their choosing because no independent check ties the beneficiary to the entity that actually did the work." The local analog is `pallet-state-coprocessor`'s GET-request-response handler, which mints reputation tokens to a caller-supplied `address` field with no cryptographic binding to whoever actually produced the proof or performed the relay work — unlike its sibling pallet, `pallet-messaging-incentives`, which cryptographically recovers the beneficiary from an sr25519 signature.

### Finding Description
`GetRequestsWithProof::address` is a plain `Vec<u8>` supplied directly by the caller of `handle_get_requests`: [1](#0-0) 

After verifying the source membership proof and destination state proof (both of which rely only on *public* chain data — anyone with RPC access to source and destination chains can construct them, no private key or exclusive relaying role required), the pallet mints `ReputationAsset` directly to whatever account `address` decodes to: [2](#0-1) 

Contrast this with `pallet-messaging-incentives`, which never trusts a bare `address`/`signer` field as an account identifier — it *cryptographically recovers* the beneficiary from a signature over the request payload before minting: [3](#0-2) 

In `state-coprocessor`, there is no equivalent recovery step — `address` is taken at face value, reshaped into an `AccountId`, and directly credited: [4](#0-3) 

The same unauthenticated `address` is also persisted as the "relayer" in the request receipt and in the `GetRequestHandled` event, so the false attribution propagates into the on-chain delivery record, not just the mint: [5](#0-4) 

### Impact Explanation
Because proof construction only requires public source/destination chain state (dedup and receipt checks only prevent *replay* of the same request, not impersonation of the deliverer), any unprivileged party who can observe an in-flight, not-yet-answered GET request can independently assemble the same `source`/`response` proofs and submit `handle_get_requests` with `address` set to their own account. This diverts the reputation mint — and the on-chain "who delivered this" attribution — away from whichever party did the actual off-chain proof-fetching/verification work to an unrelated attacker account, purely by winning a race to submit the extrinsic first. This is a "wrong beneficiary" fund-diversion class bug matching the required impact gate (rewards/tokens must move only to the rightful beneficiary), directly analogous to the external report's "any authorized caller can mint to an address of their choosing without further checks."

### Likelihood Explanation
Medium-to-high. No signature, no relayer registration, and no exclusive-knowledge requirement gates who can submit `handle_get_requests` with a self-chosen `address` — the only real barrier is being first to submit a valid proof once the underlying data becomes available, which is an ordinary transaction-ordering race, not a privileged-access requirement. I was not able to fully confirm the exact dispatch origin/extrinsic wrapper in `modules/pallets/state-coprocessor/src/lib.rs` (call_index, origin check) within the available iterations — the analysis of `impls.rs` is solid, but I could not verify whether an additional origin filter (e.g., restricting the caller to a specific pre-registered coprocessor account) exists at the dispatch layer, which if present could reduce but not eliminate the impact (the `address` beneficiary would still be uncoupled from that verified origin).

### Recommendation
Bind the reputation-mint (and receipt) beneficiary to a value that cannot be freely chosen by the caller: either (a) require a signature over `address` (or over the request/response payload) analogous to `pallet-messaging-incentives::relayer_for`, and recover the account from that signature rather than trusting the raw bytes, or (b) restrict `handle_get_requests` to a signed/authenticated origin and use `ensure_signed(origin)` as the beneficiary directly instead of accepting an arbitrary `address` parameter.

### Proof of Concept
1. Monitor a source chain for an outstanding `GetRequest` that has not yet been responded to on Hyperbridge (`response_receipt` unset).
2. Independently fetch the source membership proof and the destination state proof for the requested keys using public RPC endpoints — no special role or key is required.
3. Submit `handle_get_requests` (via whatever extrinsic wraps it in `modules/pallets/state-coprocessor/src/lib.rs`) with `GetRequestsWithProof { requests, source, response, address: <attacker_account_bytes> }`.
4. If `MintPerByte` (shared with `pallet-messaging-incentives`) is non-zero, `ReputationAsset::mint_into(&attacker_account, amount)` executes and `ReputationMinted { relayer: attacker_account, ... }` fires, even though the attacker did not perform any privileged relaying role — merely repackaged publicly available proof data before the legitimate deliverer could submit.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
