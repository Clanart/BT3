### Title
Permissionless, cross-chain-sponsored `purchase()` calls let an attacker evict and destroy another app's already-paid bandwidth allowance via FIFO cap eviction - (File: `evm/src/apps/BandwidthManager.sol` / `modules/pallets/bandwidth/src/lib.rs`)

### Summary
The Sherlock report's core broken invariant is: *an unprivileged actor can repeatedly call a permissionless "add value" entrypoint with minimal cost to dilute/destroy value that legitimate participants already have vested/committed*. The local analog is Hyperbridge's bandwidth subscription model: `BandwidthManager.purchase()` is permissionless and cross-chain-sponsored (any caller can credit *any* `(app_chain, app)` pair), and `pallet-bandwidth` stores allowances as a FIFO list capped at 1024 entries per `(chain, app)` where a full list **evicts the oldest entry outright** on the next purchase.

### Finding Description
`pallet-bandwidth` keys allowance storage by `(app_chain, app)` taken from the purchase message body, not by `request.source` — this is explicitly designed so "a treasury on a single chain can sponsor bandwidth for an app deployed across many chains" [1](#0-0) . Because the sponsorship target is attacker-controlled and unauthenticated beyond `(chain, app)`, **anyone** can dispatch cheap `TierOne`/short-duration purchases against a victim app's bucket.

Each purchase appends a new row to a FIFO list capped at 1024 entries; same-tier repurchases don't merge, they queue [2](#0-1) . When the list is full, the next push **evicts the oldest entry**, regardless of how much `remaining_bytes` or how long an `expires_at` that entry still carries:

> "Pushing onto a full list (1024 entries) evicts the oldest entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain." [3](#0-2) 

The docs assume this "only happens under pathological repeat-buy behavior" at the rate of one purchase per cycle, treating 1024 buys as "years of headroom" [3](#0-2) . That assumption only holds if purchases against a given `(chain, app)` bucket are rate-limited or gated to the app's own legitimate top-up cadence — but `purchase()` has no such restriction: it is a public entrypoint that pulls the fee token from `msg.sender` and dispatches an ISMP POST that the pallet accepts from any registered manager for any encoded `(app, tier, months, chain)` [4](#0-3) .

An attacker who wants to grief/destroy a rival app's bandwidth allowance (e.g., a competing bridge integrator, or simply to force it into `GateError::Insufficient` and drop its ISMP traffic) can:
1. Buy the cheapest configured tier (`TierOne`, `months=1`) targeting the victim's `(app_chain, app)` 1024 times.
2. Each purchase queues a new tiny/short-lived subscription at the tail.
3. Once the list hits the 1024 cap, each subsequent purchase evicts the **oldest** entry from the head — which, if the victim had earlier purchased a large, long-duration tier, is exactly the entry containing most of the victim's paid-for, unconsumed `remaining_bytes`.
4. That paid allowance is permanently gone (`SubscriptionEvicted`), even though the victim already paid the fee token for it and never consumed it.

This mirrors the reward-dilution bug class: an unrestricted, low-cost, repeatable public call is used to unilaterally destroy/dilute a counterparty's already-committed value, with no minimum-value or per-target rate-limit guard analogous to what the Sherlock report recommends ("minimum amount... to ensure a meaningful increase," "restrict who can add").

### Impact Explanation
This is a loss-of-funds impact: an app pays real fee-token value for bandwidth (`tier.price × months`), and that paid, unconsumed allowance can be unilaterally destroyed by any third party spending only on cheap tiers, without needing a malicious relayer, prover, or admin. The victim app is also left unable to dispatch ISMP messages (`GateError::Insufficient`/`NoAllowance` once its allowance is evicted), disrupting cross-chain execution for that app — a logic attack against the "bridged assets... must move exactly once and only to the rightful beneficiary" invariant, since the paid bandwidth never reaches consumption by its payer.

### Likelihood Explanation
Requires only calling a fully public `purchase()` function up to 1024 times with the cheapest tier against a known, arbitrary `(app_chain, app)` target — no privileged role, relayer collusion, or governance access needed. Cost is bounded by `1024 × price(TierOne, 1 month)`, which for a low-priced tier could be economically trivial relative to destroying a competitor's larger prepaid allowance.

### Recommendation
- Rate-limit or gate purchases per `(app_chain, app)` bucket to the address that is authorized to manage that app's bandwidth (or require sponsor allowlisting), rather than accepting sponsorship from any caller unconditionally.
- On eviction, refund or pro-rate the destroyed `remaining_bytes` value back to whoever paid for that entry instead of silently discarding it.
- Consider merging/coalescing same-tier entries instead of always appending, and/or raising the cap or making it configurable per app so cheap flooding cannot reach the eviction threshold within economically feasible cost.

### Proof of Concept
1. Victim app buys a `TierFour` (large bytes, long duration) subscription for `(app_chain=X, app=A)` via `BandwidthManager.purchase()` — this becomes the head of the FIFO list.
2. Attacker calls `BandwidthManager.purchase()` 1024 times from any account, each time encoding `chain = X, app = A, tier = TierOne, months = 1` — each dispatches a `BandwidthPurchaseMsg` credited to `(X, A)`'s bucket.
3. Once the list length reaches 1024, the 1025th purchase (attacker's) triggers eviction of the oldest entry — the victim's large `TierFour` subscription — emitting `SubscriptionEvicted` with the victim's lost `remaining_bytes`, per the documented eviction behavior [3](#0-2) .
4. Victim's app now has only attacker's dust `TierOne` entries backing it and quickly hits `GateError::Insufficient`, while the fee token it spent on `TierFour` is unrecoverable.
