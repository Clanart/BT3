### Title
`mWomSV.cancelUnlock()` missing `nonReentrant` mirrors the same double-decrement `totalAmountInCoolDown` underflow vulnerability found in `VLMGP.cancelUnlock()` - (wombat/mWomSV.sol)

### Summary
`mWomSV.cancelUnlock()` at [1](#0-0)  is marked `whenNotPaused` but not `nonReentrant`, exactly mirroring the `VLMGP.cancelUnlock()` pattern at [2](#0-1) . Since `startUnlock()` and `unlock()` both call `IMasterMagpie(masterMagpie).multiclaimFor()` before finalizing their state writes ( [3](#0-2)  and [4](#0-3) ), a reentrant call into `cancelUnlock()` during that external call can decrement `totalAmountInCoolDown` twice for the same slot amount, structurally identical to the VLMGP case.

### Finding Description
The code path is confirmed identical to VLMGP: `startUnlock` and `unlock` call out to `multiclaimFor` on `masterMagpie` (an external, attacker-influenceable claim/reward-distribution call) before `slot.amountInCoolDown` is zeroed or before `totalAmountInCoolDown` bookkeeping is finalized in `unlock`, and `cancelUnlock` itself has no reentrancy guard, only `whenNotPaused`, at [1](#0-0) . If a reward token hook attached to mWomSV's pool in MasterMagpie can call back into `mWomSV.cancelUnlock(prevSlot)` mid-`startUnlock`/`unlock`, `totalAmountInCoolDown` would be decremented via `cancelUnlock` while the original slot's `amountInCoolDown` was already added/still counted, producing the same double-decrement pattern described in the VLMGP finding.

However, I was unable to confirm the actual reentrancy entry point in this codebase within the available context. I inspected `rewards/MasterMagpie.sol` and `rewards/BaseRewardPool.sol`/`BaseRewardPoolV2.sol` exist, but could not retrieve their `multiclaimFor`/`_multiClaim`/reward-sending implementation to verify (a) whether reward tokens are added by a privileged `rewardManager`/`poolManager` only (which would make this an admin-configuration precondition and out of scope per the rules), and (b) whether the token transfer during claim uses a raw `.transfer`/`.call` that could trigger a callback on an attacker-controlled ERC777/ERC1363-style token, or is restricted to `safeTransfer` on a pre-vetted whitelist of tokens that an unprivileged attacker cannot register.

Since the rules explicitly require rejecting "misconfiguration-only paths" and reward-token registration in this codebase's `MasterMagpie`/`BaseRewardPool` pattern is typically gated behind `onlyRewardManager`/`onlyPoolManager` (not an unprivileged capability), and I could not verify a concrete unprivileged path for an attacker to introduce a malicious reentrant reward token into the mWomSV pool within the available index, I cannot confirm this meets the "unprivileged attacker only" precondition required by the rules.

### Impact Explanation
If the reentrant path were confirmed reachable by an unprivileged attacker, the impact would match the VLMGP case: permanent freezing of `totalAmountInCoolDown` accounting due to underflow, breaking `unlock()` for all mWomSV holders (Immunefi: permanent freezing of funds, >24h). This mirrors the scoped impact described for VLMGP.

### Likelihood Explanation
Cannot be assessed with confidence — the likelihood hinges entirely on whether an unprivileged attacker can get a malicious, reentrant reward token registered and routed through `multiclaimFor` for the mWomSV pool specifically. This requires verifying `rewards/MasterMagpie.sol`'s reward-token registration access control and `BaseRewardPool`'s reward-sending mechanism, which I could not fully retrieve in this session.

### Recommendation
Regardless of the reentrancy entry-point uncertainty, `cancelUnlock()` in both `VLMGP.sol` and `wombat/mWomSV.sol` should add the `nonReentrant` modifier as defense in depth, consistent with `startUnlock()`, `unlock()`, and `forceUnLock()` which already use it.

### Proof of Concept
Not provided — reachability of an attacker-controlled reentrant call into `cancelUnlock()` via `multiclaimFor()` could not be verified from the available `MasterMagpie.sol`/`BaseRewardPool.sol` reward-token registration and transfer logic in this session. A concrete Foundry PoC would require first confirming an unprivileged path to attach a reentrant reward token to the mWomSV pool.
