### Title
`ReceivedOutput::read` accepts a claimed scalar offset with no binding to the output's script or outpoint, letting untrusted bytes fabricate or poison reported deposits - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`ReceivedOutput` couples three independent fields — a secret-free scalar `offset`, a `TxOut`, and an `OutPoint` — and its deserialization path (`ReceivedOutput::read`) accepts all three verbatim from untrusted bytes. The only consumer-side consistency check lives much later in `SignableTransaction::multisig`, which rejects the whole transaction (`None`) when `p2tr_script_buf(key + G*offset) != prevout.script_pubkey`. There is no validation that the `offset` actually derives the output's `script_pubkey`, that the outpoint exists, or that the output is even pay-to-Taproot at the point the object is created/accepted — the access-control analog of accepting a crafted request and treating its claims as authoritative.

### Finding Description

`Scanner::scan_transaction` constructs `ReceivedOutput` honestly: the `offset` is looked up from the internal `scripts` map keyed by `output.script_pubkey`, so `key + G*offset == script_pubkey` holds by construction (networks/bitcoin/src/wallet/mod.rs:199-213).

`ReceivedOutput::read`, however, performs no such binding. It reads an arbitrary `Scalar` via `Secp256k1::read_F`, then a `TxOut` and `OutPoint` via consensus decoding, and returns the tuple as a trusted `ReceivedOutput` (networks/bitcoin/src/wallet/mod.rs:122-134). Downstream code treats the fields as authoritative:

- `SignableTransaction::new` collects `input.offset` verbatim into `self.offsets` and stores `input.output` as prevouts (send.rs:175-176, 252-253).
- `SignableTransaction::multisig` re-keys the threshold keys per input with `keys.clone().offset(self.offsets[i])` and only then checks the script match; on mismatch it silently returns `None` (send.rs:275-282). Callers in the tree unwrap this (`tx.clone().multisig(&keys[&i]).unwrap()` in tests), turning a poisoned input into a panic or an unsignable transaction.
- `ReceivedOutput::value()`, `outpoint()`, `offset()` are exposed directly, so an accepted forged object inflates reported balance and feeds UTXO scheduling before any check runs.

Two attacker-reachable shapes exist from a single crafted byte stream:

1. **Mismatched offset**: real or fabricated `TxOut`/`OutPoint` with an `offset` that does not satisfy `p2tr(key + G*offset) == script_pubkey`. The deposit is reported as received, but `multisig` returns `None` — funds are accounted but can never be signed for (or the caller panics on `unwrap`).
2. **Fabricated outpoint**: a `TxOut`/`OutPoint` referencing a non-existent or third-party UTXO, paired with a self-consistent `offset`. Nothing in `read` or `SignableTransaction` verifies the outpoint exists on-chain, so phantom inputs enter `prevouts` and sighash commitments (`Prevouts::All`, send.rs:375).

This mirrors CVE-2025-60914's class: a data-acceptance endpoint trusting attacker-controlled fields without enforcing the invariant the honest producer guarantees.

### Impact Explanation

An unprivileged party who can cause `ReceivedOutput::read` to parse their bytes (any transport/relay/DB path that round-trips serialized outputs) can: (a) register deposits that are reported as received balance yet are provably unspendable, stalling or crashing the signing flow when `multisig` returns `None`; or (b) inject phantom prevouts into `SignableTransaction`, corrupting fee accounting (`input_sat` vs `payment_sat`) and the `Prevouts::All` sighash commitment. Both are integrity failures of received-funds reporting — funds reported received that are not spendable — the concrete impact class for Medium.

### Likelihood Explanation

The honest producer (`Scanner`) is safe; the vulnerability requires an untrusted serializer reaching `ReceivedOutput::read`. The type exposes `serialize`/`read` precisely so outputs can cross process/storage boundaries, and sibling code (`Output::read` in the processor) reads `ReceivedOutput` from a generic `io::Read` without re-validation. The precondition is therefore a realistic integration surface rather than exotic, but it does depend on the integrator accepting serialized outputs from a non-authoritative source, which keeps this at Medium rather than higher.

### Recommendation

Bind the offset to the output at acceptance time: give `ReceivedOutput` a constructor/`read` variant that takes the group key (or the `Scanner`) and verifies `p2tr_script_buf(key + G*offset) == output.script_pubkey` before returning `Some`. At minimum, `SignableTransaction::new` should reject inputs whose `offset` does not derive the prevout's `script_pubkey` (fail at construction with an error, not `None` inside `multisig`), and document that `read` must only consume self-produced data.

### Proof of Concept

```rust
// networks/bitcoin context; Secp256k1, Scalar, p2tr_script_buf, ReceivedOutput
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf};

// An honest group key the wallet scans for
let group_key = ProjectivePoint::GENERATOR * Scalar::from(42u64);

// Attacker crafts a ReceivedOutput claiming deposit, with a WRONG offset:
let forged_offset = Scalar::from(7u64); // does NOT derive the script below
let txout = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: p2tr_script_buf(group_key).unwrap(), // script = group_key + 0
};
let outpoint = OutPoint::null(); // or any fabricated/real outpoint

let mut buf = vec![];
buf.extend_from_slice(&forged_offset.to_bytes());
buf.extend_from_slice(&bitcoin::consensus::serialize(&txout));
buf.extend_from_slice(&bitcoin::consensus::serialize(&outpoint));

// read() accepts it unconditionally — no check that offset maps to the script
let output = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(output.offset(), forged_offset);   // claimed offset accepted
assert_eq!(output.value(), 100_000);          // phantom/poisoned balance reported

// When the wallet later tries to spend it:
let tx = SignableTransaction::new(vec![output], &payments, Some(change), None, fee).unwrap();
assert!(tx.multisig(&keys).is_none()); // unsignable: funds "received" but unspendable
```

The gap is that `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) never enforces the invariant `Scanner::scan_transaction` guarantees, and the check is deferred to `SignableTransaction::multisig` (send.rs:276-279) where failure is a silent `None` rather than rejection at ingestion.
