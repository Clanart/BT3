### Title
Unbounded Recursive RLP Decoding of Nested AccountKeyRoleBased Causes Stack Overflow DoS - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key of a role-based account key via `NewAccountKeySerializer`/`AccountKeySerializer.DecodeRLP`, which itself may re-decode into another `AccountKeyRoleBased` if the attacker sets the inner key type to `AccountKeyTypeRoleBased` again. There is no depth limit enforced during this decode path, so an attacker can craft a transaction whose `Key` field contains many (e.g., tens of thousands of) levels of self-nested `AccountKeyRoleBased` encodings. Because decoding happens before any semantic check rejects nesting, this can exhaust the goroutine stack and crash the node — directly analogous to the reported Play Framework issue (CVE-2020-27196), where eager recursive parsing of a deeply nested payload without a depth guard causes a `StackOverflowError`/DoS.

### Finding Description
`TxInternalDataAccountUpdate.Key` (and the fee-delegated variant) is typed as `accountkey.AccountKey`, decoded via `AccountKeySerializer.DecodeRLP`: [1](#0-0) 

When the encoded key type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` decodes a list of RLP byte-strings and, for **each element**, calls `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, which in turn can itself resolve to another `AccountKeyTypeRoleBased`, recursing indefinitely: [2](#0-1) 

The only guard against nested composite keys, `CheckInstallable`/`CheckUpdatable` (which reject `IsCompositeType()` sub-keys with `ErrNestedCompositeType`), runs **after** the full transaction (including the `Key` field) has already been fully RLP-decoded: [3](#0-2) [4](#0-3) 

So the unbounded recursion during `Transaction.DecodeRLP`/`UnmarshalBinary` (used when receiving `eth_sendRawTransaction`/`kaia_sendRawTransaction` or p2p tx propagation) happens well before `Validate()` is ever invoked: [5](#0-4) 

The `rlp.Stream` decoding path (`Stream.List`/`ListEnd`) enforces byte-size limits but does not track or cap decode recursion depth: [6](#0-5) 

The similarly-shaped JSON path (`AccountKeyRoleBased.UnmarshalJSON`) has the same issue, recursing into `AccountKeySerializer.UnmarshalJSON` without depth limiting: [7](#0-6) [8](#0-7) 

This is functionally the same bug class as the Play Framework advisory: eager, unbounded recursive parsing driven entirely by attacker-controlled nesting depth, with no depth cap before the parser commits to full recursive descent.

### Impact Explanation
A Go stack overflow triggers a fatal, unrecoverable runtime crash (`runtime: goroutine stack exceeds limit`) — it cannot be caught by `recover()`. Since transaction decoding occurs in the RPC handler/tx-pool ingestion path for every submitted transaction and also during p2p transaction gossip, an unprivileged party who can submit a transaction (or broadcast one over the p2p tx-propagation channel that gets locally decoded) can crash the target node process, producing a denial-of-service. If exploited broadly (e.g., relayed by an honest node before local semantic validation catches it), this could cause crashes across multiple nodes simultaneously.

### Likelihood Explanation
High: constructing the malicious payload requires only crafting a nested `AccountKeyRoleBased` RLP encoding (or JSON payload for the `kaia_signTransaction`/`decodeAccountKey`-style JSON entry points) with no special privileges, valid signature is not even strictly required to reach the decode step since decoding precedes signature/consensus validation and can occur on the receiving node just from receiving raw bytes.

### Recommendation
Enforce a maximum recursion/nesting depth check in `AccountKeyRoleBased.DecodeRLP` and `UnmarshalJSON` (and generally in `AccountKeySerializer.DecodeRLP`/`UnmarshalJSON`) before recursing — reject any inner key whose type is `AccountKeyTypeRoleBased` immediately (role-based keys should never contain nested role-based keys, matching the existing `isNested` semantic check in `checkAccountKeyZeroValues`), and/or add an explicit depth counter threaded through the RLP `Stream`/JSON decode calls that aborts decoding once a small fixed limit (e.g., 1) is exceeded, consistent with the "composite key not allowed" invariant enforced later in `CheckInstallable`.

### Proof of Concept
1. Construct account key bytes `K0` for `AccountKeyPublic` (or any leaf key).
2. Build `AccountKeyRoleBased_1 = RLP([RLP(AccountKeySerializer{keyType: RoleBased, key: AccountKeyRoleBased_0})])` where `AccountKeyRoleBased_0` wraps `K0`.
3. Repeat step 2 iteratively N times (N ≈ 10,000–100,000), each time wrapping the previous serialized `AccountKeyRoleBased` as the sole element of a new `AccountKeyRoleBased`.
4. Embed the final deeply-nested blob as the `Key` field of a `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate`) transaction, RLP-encode the full transaction.
5. Submit the transaction via `eth_sendRawTransaction`/`kaia_sendRawTransaction`, or have it relayed via p2p; observe that decoding via `Transaction.UnmarshalBinary` → `AccountKeyRoleBased.DecodeRLP` recurses N times and crashes the node with a stack overflow, before `Validate()`/`CheckInstallable` is ever reached.

Note: I was not able to execute this PoC in a live environment (no code execution/terminal access here); the depth and exact crash threshold would need to be empirically confirmed by a Devin agent with Go build/test access.

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// List starts decoding an RLP list. If the input does not contain a
// list, the returned error will be ErrExpectedList. When the list's
// end has been reached, any Stream operation will return EOL.
func (s *Stream) List() (size uint64, err error) {
	kind, size, err := s.Kind()
	if err != nil {
		return 0, err
	}
	if kind != List {
		return 0, ErrExpectedList
	}

	// Remove size of inner list from outer list before pushing the new size
	// onto the stack. This ensures that the remaining outer list size will
	// be correct after the matching call to ListEnd.
	if inList, limit := s.listLimit(); inList {
		s.stack[len(s.stack)-1] = limit - size
	}
	s.stack = append(s.stack, size)
	s.kind = -1
	s.size = 0
	return size, nil
}

// ListEnd returns to the enclosing list.
// The input reader must be positioned at the end of a list.
func (s *Stream) ListEnd() error {
	// Ensure that no more data is remaining in the current list.
	if inList, listLimit := s.listLimit(); !inList {
		return errNotInList
	} else if listLimit > 0 {
		return errNotAtEOL
	}
	s.stack = s.stack[:len(s.stack)-1] // pop
	s.kind = -1
	s.size = 0
	return nil
}
