### Title
OP_RETURN Data Output Excluded From Fee/Weight Calculation Causes Underpaid Fees and Stuck Transactions — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` to the transaction, but `calculate_weight_vbytes` is invoked only with `payments`, never including the `data` output. The resulting `vbytes`/`weight` and therefore `needed_fee` are computed on a transaction that is smaller than the one actually built and broadcast. Analogous to a fixed 2,300-gas stipend that is silently insufficient, this is a fixed (under-)estimate of the resources the transfer requires: the constructed transaction pays a lower effective fee rate than the caller requested, and can fall below the minimum relay fee or mempool policy even though `new` returned `Ok`.

### Finding Description
The `data` output is pushed to `tx_outs` before the weight calculation:

- `tx_outs.push(TxOut { ... ScriptBuf::new_op_return(...) })` at `send.rs:194-202`
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at `send.rs:204`

`calculate_weight_vbytes` reconstructs a transaction using only `payments` (and optionally `change`) — it has no parameter for the OP_RETURN output (`send.rs:62-99`). So for any `data` of length `n`, the real transaction is larger by roughly `8 (value) + compactsize + 2 (OP_RETURN + push opcode) + n` bytes, i.e. up to ~91 vbytes for 80-byte data, none of which is charged to `needed_fee` (`send.rs:206`, `send.rs:227`).

Two consequences follow:

1. The paid fee rate is `fee / actual_vbytes`, which is strictly below the caller-requested `fee_per_vbyte` whenever `data` is present.
2. The `TooLowFee` guard at `send.rs:211` validates `needed_fee` against the under-estimated `vbytes`, so a transaction whose *actual* fee rate is below `DEFAULT_MIN_RELAY_TX_FEE` can pass validation when `data` is set — the check at `send.rs:165-169` even permits `amount` checks against the wrong denominator.

When a change output exists, `fee_with_change` is also computed from `vbytes_with_change` that still excludes the OP_RETURN output (`send.rs:225-227`), so the change amount is slightly too large and the deficit compounds.

### Impact Explanation
Transactions carrying the full 80-byte `data` pay ~8-12% less than the intended fee rate (on a typical 1-input/2-output ~150-250 vbyte transaction, ~90 unaccounted vbytes). At fee rates near the relay minimum — precisely where Serai's batched withdrawals operate — the signed transaction can be rejected by relay policy or sit unconfirmed indefinitely, delaying/stranding user withdrawals. The fee paid may also silently burn additional change value (`send.rs:228-233` decides change inclusion using the under-charged `fee_with_change`, so leftover below `DUST` goes to miners). This is a Medium-severity liveness/availability issue: validly constructed transactions systematically underperform the specified fee rate.

### Likelihood Explanation
Any out-instruction flow that attaches `data` (the `data` parameter exists specifically to embed payload in withdrawals/batches) and uses a `fee_per_vbyte` near the minimum relay fee triggers the under-estimate deterministically — no attacker needed, though an attacker able to influence the `data` field (e.g., via instruction bytes reflected into transactions) can maximize the deficit with a full 80-byte payload. Reachable purely through public inputs to `SignableTransaction::new`.

### Recommendation
Pass the OP_RETURN output into the weight calculation — e.g., extend `calculate_weight_vbytes` to accept the full `tx_outs` list (including the `new_op_return` `TxOut`) rather than only `payments`/`change`, and recompute `vbytes`/`needed_fee`/`fee_with_change` from that. Re-validate the `TooLowFee` and change-dust checks against the corrected vbytes.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs concept demo
let data = Some(vec![0xAAu8; 80]);
let payments = &[(dest_script.clone(), 100_000u64)];

let tx_no_data = SignableTransaction::new(
    inputs.clone(), payments, change.clone(), None, fee_per_vbyte,
).unwrap();
let tx_with_data = SignableTransaction::new(
    inputs, payments, change, data, fee_per_vbyte,
).unwrap();

// needed_fee() is identical, yet tx_with_data.transaction() is ~91 vbytes larger:
assert_eq!(tx_no_data.needed_fee(), tx_with_data.needed_fee()); // BUG: same fee charged
assert!(tx_with_data.transaction().weight() > tx_no_data.transaction().weight());
// effective rate: tx_with_data.fee() / actual_vbytes < fee_per_vbyte
```
