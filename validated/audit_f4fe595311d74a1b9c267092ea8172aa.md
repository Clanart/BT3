### Title
Reachable panic via point-at-infinity aggregate nonce in BIP-340 `Hram` during FROST signing - ([File: networks/bitcoin/src/crypto.rs])

### Summary
Analogous to the FreeRDP reachable-`WINPR_ASSERT` abort, Serai's Bitcoin Schnorr path contains a reachable panic (`expect("point at infinity")`) on attacker-influenced input. A malicious FROST participant can submit preprocess nonce commitments crafted so the weighted aggregate nonce `R` is the point at infinity, causing `x(R)` inside `Hram::hram` to panic on every honest signer that processes the preprocess — a deterministic, remotely-triggered DoS of the signing session. The code explicitly documents this panic but incorrectly assumes it has only "negligible probability ... even with malicious participants present" [1](#0-0) .

### Finding Description
`Hram::hram` hashes `x(R)` where `x` calls `key.to_encoded_point(true)` and then `.expect("point at infinity")` on `encoded.x()` [2](#0-1) [3](#0-2) . `R` is the aggregate binding nonce computed by modular-frost from all participants' preprocess commitments, which each signer ingests from untrusted bytes via `read_preprocess` [4](#0-3) . Because `C::read_G` accepts any canonically-encoded point — including the identity — and no identity check on nonce commitments is visible in this path, a malicious participant can wait for all honest preprocesses, choose their first commitment point `D_j = O` (so `rho_j * D_j = O` regardless of the binding factor `rho_j`, which is itself a function of the attacker's own commitments and thus cannot be precomputed around), and set `E_j = -(sum of all other participants' bound contributions)`. The resulting aggregate `R = O` deterministically, and `hram` panics inside `sign_share`/`verify_share` on every honest machine.

### Impact Explanation
An unprivileged signing participant can crash (panic → abort/unwind) every honest validator's `TransactionSignMachine::sign` / `AlgorithmSignMachine` for a Bitcoin multisig session by supplying a single malicious preprocess. This is a Medium-severity availability loss: threshold signing for Bitcoin withdrawals halts. No key material leaks, but the signing round cannot complete.

### Likelihood Explanation
High once the attacker is a FROST participant in the signing set: the trigger is deterministic (identity is a valid canonical group encoding and scalar multiplication `rho * O = O` makes the attacker's contribution independent of the challenge-derived binding factor). Reachability is through the documented public-input surface (`read_preprocess` → `sign` → `hram`) [5](#0-4) . Likelihood is limited to sessions where the adversary is one of the `t` signers or can inject preprocess bytes into a signer's input path.

### Recommendation
In `x`/`x_only`/`hram` (networks/bitcoin/src/crypto.rs), return an error instead of panicking on the point at infinity, or reject identity/invalid nonce commitments when reading preprocesses (check `R != O` and each commitment `!= O` before signing). If `Algorithm::sign_share`/`verify` can surface `FrostError`, propagate a `InvalidCommitment`-style error rather than `expect`.

### Proof of Concept
1. Honest signers broadcast preprocesses `(D_i, E_i)` for a Bitcoin `TransactionMachine`.
2. Attacker (participant `j`) computes `T = sum over i != j of (D_i + rho_i * E_i)` (the exact FROST binding combination used by `FrostSchnorr`).
3. Attacker submits preprocess `D_j = <33-byte canonical identity encoding>`, `E_j = -T`.
4. `read_preprocess` accepts both points via `C::read_G` (identity is canonical).
5. In `sign`, every honest signer computes aggregate `R = O`, calls `Hram::hram`, which calls `x(&O)` → `to_encoded_point(true)` → `x()` returns `None` → `expect("point at infinity")` panics, aborting the signing session.

Caveat: this analysis assumes modular-frost's preprocess processing does not itself reject identity commitment points before `hram` is reached; if `FrostSchnorr` validates nonces for non-identity upstream, the panic is unreachable and the finding reduces to the documented defensive panic. I could not fully verify that check within the available iterations.
