## Finding [1](#0-0) 

### Title
Commit is created from a stale, unrevalidated `workingDirectory` snapshot, allowing a cloned repository's automated processes to make Desktop commit/push content the user never reviewed - (File: app/src/lib/stores/app-store.ts)

### Summary
`AppStore._commitIncludedChanges` reads the list of files (and their per-file/per-line `DiffSelection`) to stage and commit straight from `repositoryStateCache` — an in-memory snapshot populated by the *last* `_loadStatus()` call — instead of re-running `git status`/re-diffing immediately before staging. [2](#0-1)  This mirrors the Oracle bug's root cause: a cached "last known good" value (`latestVersion` in the oracle case, `changesState.workingDirectory` here) is trusted for a critical operation without verifying it still matches ground truth, and the code paths that do this validation elsewhere in the same file (e.g. `updateChangesWorkingDirectoryDiff`, `_changeFileSelection`, `updateChangesStashDiff`) explicitly re-check state-before vs state-after an async load and bail out on divergence — but `_commitIncludedChanges` has no equivalent re-validation against the actual working directory before calling `createCommit`. [3](#0-2) [4](#0-3) 

### Finding Description
The commit flow is:
1. Desktop periodically/opportunistically refreshes `changesState` via `_loadStatus`, which stores the working directory files and per-file `DiffSelection` (line selections) in `repositoryStateCache`. [5](#0-4) 
2. When the user clicks "Commit", `_commitIncludedChanges` pulls `state.changesState.workingDirectory.files` from that cache — not a fresh `getStatus()` call — filters to the selected files, and passes them straight to `createCommit`. [6](#0-5) 
3. `createCommit` unconditionally resets the index and calls `stageFiles(repository, files)` using those (possibly stale) `WorkingDirectoryFileChange` objects. [7](#0-6) 
4. `stageFiles` stages full files via `updateIndex` (whatever is currently on disk, no content check) for `DiffSelectionType.All`, and applies the *previously computed* patch via `applyPatchToIndex` for partial selections. [8](#0-7) 

If the on-disk content of a tracked file changes between the last status/diff refresh and the moment the user clicks Commit (e.g. a background/automated process triggered by the repository itself modifies a tracked file — a build step, watch task, editor auto-format-on-save hook, or any tool the cloned repo instructs the user to run), Desktop:
- For fully-selected files: stages and commits whatever is on disk *right now*, which can differ from the diff the user actually reviewed in the Changes panel — the UI never re-diffs before commit.
- For partially-selected files: applies a hunk-based patch computed from the stale diff to content that has since changed, which can silently drift what actually lands in the commit versus the reviewed hunks (or fail unpredictably, itself another form of undefined behavior around what gets committed).

No code path forces a synchronous, blocking re-status/re-diff and cancels commit on divergence, unlike the pattern intentionally used elsewhere for diff loading and file selection to guard against exactly this kind of staleness. [9](#0-8) 

### Impact Explanation
This directly matches "silent corruption of what the user commits or pushes": the content actually staged and committed can diverge from the diff the user reviewed and approved in the UI, without any warning, error, or re-confirmation. An attacker who controls a cloned/fetched repository (e.g. via build scripts, watch tasks, or any automated tooling the repo instructs/causes the user to run alongside Desktop) can arrange for tracked files to be rewritten in the small window between Desktop's last status refresh and the user's commit action, causing Desktop to commit and potentially push attacker-influenced content while showing the user a stale, no-longer-accurate diff as "what will be committed."

### Likelihood Explanation
The window is real but narrow — it requires content on disk to change after the last background/foreground status refresh and before the user presses Commit, which any repo-driven automated process (watchers, build tools, formatters) can realistically trigger while the user is actively working. It does not require local/physical access, admin rights, prior malware, or leaked credentials — only a repository the user has cloned and is actively working in, which is squarely in scope for "attacker controls a cloned/fetched repository."

### Recommendation
Before staging/committing, re-validate the cached `workingDirectory` snapshot against a fresh `getStatus()` (and re-diff for partially selected files), and abort/re-prompt the commit if the file's content or diff hunks have changed since the last snapshot the user viewed — mirroring the "stateBeforeLoad vs stateAfterLoad" staleness guard pattern already used in `updateChangesWorkingDirectoryDiff` and `_changeFileSelection`. [10](#0-9) 

### Proof of Concept
1. Open a repository in Desktop containing a tracked file `foo.txt`, modify a few lines, and let Desktop refresh status/diff so the Changes panel shows a specific diff for `foo.txt`.
2. Before clicking Commit, have any external process associated with the repo (e.g. a script the README instructs the user to run, a file watcher/build tool configured in the repo, or an editor auto-format-on-save triggered by opening the file) rewrite `foo.txt` on disk with different content, without Desktop performing another status/diff refresh in that window.
3. Click "Commit" in Desktop. `_commitIncludedChanges` uses the stale `workingDirectory.files`/selection captured from the prior refresh [6](#0-5) , and `stageFiles`/`updateIndex` stage the *current* on-disk content for a fully-selected file [11](#0-10) .
4. Inspect the resulting commit: it contains the content written in step 2, not the content shown in the diff the user reviewed and approved in step 1.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
