### Title
Byte-offset diff truncation in `build_investigate_prompt` silently drops attacker-placed high-risk lines from the security review model - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_investigate_prompt` calls `cap_diff_for_prompt`, which truncates each file's diff content at a fixed byte offset (`DIFF_PER_FILE_BYTES`) and the concatenated total at another fixed offset (`DIFF_TOTAL_BYTES`), always keeping the head and dropping the tail. An attacker who controls diff content (e.g., an external contributor whose commit/push is fed into the commit-review or push-sweep hooks) can pad a file with low-risk content before the dangerous line so that the truncation boundary lands before it, causing the review LLM to never see the actual vulnerable code while the truncation marker gives the model (and downstream metrics) the false impression that only insignificant, non-security-relevant tail content was cut.

### Finding Description
`cap_diff_for_prompt` in [1](#0-0)  truncates each `(path, content)` pair purely by byte position: `content[:DIFF_PER_FILE_BYTES]` for the per-file cap and `content[:room]` for the running total cap, appending a generic "truncated" marker. `build_investigate_prompt` uses this capped output directly to build the Stage‑1 investigate prompt sent to the review model, with no risk-aware selection of *which* lines survive within a file: [2](#0-1) .

This is inconsistent with the file-level selection logic elsewhere in the same pipeline: when the number of changed *files* exceeds the cap, `_prioritize_diff_files` scores and reorders files by security-relevant path tokens (`auth`, `exec`, `subprocess`, `deser`, etc.) so the highest-risk files are kept: [3](#0-2) . No equivalent risk-aware logic exists *within* a single file's diff content — `cap_diff_for_prompt` (and its `llm.py` counterpart `_cap_files_for_prompt`, which shares the same byte-slicing logic) always drops the same suffix of bytes regardless of where the dangerous `+` line sits: [4](#0-3) .

Exploit flow: an attacker who can get a large-diff commit into a repo reviewed by the commit-review, Stop, or push-sweep hooks — all of which pipe `diff_files` through this cap before invoking the agentic reviewer (see `handle_commit_review_posttooluse` and `handle_push_sweep_posttooluse` calling `_agentic_review_with_race`/`agentic_review`, which itself builds the same capped `diff_text`: [5](#0-4) ) — pads a single changed file with `DIFF_PER_FILE_BYTES` (80,000 bytes by default) or more of low-risk filler (comments, dead branches, whitespace) placed *before* the truly dangerous line (e.g., a newly-added `os.system(user_input)` call). Because truncation is a pure byte-offset cut, the dangerous line lands past the cutoff and is replaced by the generic marker `"... [truncated by security-guidance: file exceeds per-file byte cap]"`. The review model (Stage‑1 investigate) only sees the padded, benign prefix and the marker — it never sees the injected vulnerability, so it correctly (from its perspective) reports no finding for that file. Existing checks (self-refute stage, diff-intersect filter, `_prioritize_diff_files`) all operate on candidates the investigate stage already produced, so they cannot recover a finding that never existed because the input was truncated before the sink was visible.

### Impact Explanation
This breaks the review's core invariant that a change under review is fully inspectable by the reviewer model, allowing an attacker-controlled diff to smuggle a security-sensitive line past the automated security-guidance review undetected. In the context of this Immunefi program (Claude Code plugin bounty), it corresponds to disclosure/omission of the exact kind the truncation marker is supposed to make visible: it drops the "diff content" that the user relies on the security-guidance plugin to inspect, weakening the plugin's guarantee and allowing dangerous behavior (arbitrary command injection, secret exfiltration code, SSRF, etc.) introduced by the diff to bypass detection when it should have been flagged.

### Likelihood Explanation
The precondition is simply that the attacker (any contributor whose commits/diffs are fed through the commit-review, Stop, or push-sweep hooks) can produce a diff of significant size in a single file — no admin, maintainer, or credential access is required, only the ability to author a large enough change (single files with tens of thousands of bytes of padding are common and unremarkable, e.g. generated code, long comment blocks, or large data literals). The byte caps (`DIFF_PER_FILE_BYTES=80000`, `DIFF_TOTAL_BYTES=400000`) are entirely attacker-visible defaults, so crafting a payload that lands exactly past the cutoff is deterministic and repeatable.

### Recommendation
Make truncation risk-aware within a file, not just across files: when a file's diff content exceeds `DIFF_PER_FILE_BYTES`, prioritize retaining `+`/`-` hunks that match `_SECURITY_RISK_PATH_TOKENS`-style sink keywords (`exec`, `subprocess`, `eval`, `pickle`, `os.system`, network calls, etc.) or simply retain the highest-density hunks of `+` lines instead of a naive head-truncation; alternatively, chunk oversized files into multiple review calls so no `+`/`-` line is ever dropped, only reordered. At minimum, keep the *tail* as well as the head (e.g., head+tail sampling) so an attacker cannot rely on a single deterministic byte offset to hide a payload.

def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```

def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )

# Path tokens that bump a file's review priority when a commit exceeds
# MAX_DIFF_FILES and we have to pick a subset. These are exactly the surfaces
# single-shot and agentic reviews disagree on most (auth, routing, IPC,
# subprocess, deserialization). Matched as lowercase substrings against the
# path; not regex — keep it cheap.
_SECURITY_RISK_PATH_TOKENS = (
    "auth", "login", "session", "token", "secret", "credential", "perm",
    "acl", "rbac", "iam", "policy",
    "route", "handler", "controller", "endpoint", "api/", "/api", "gateway",
    "middleware", "view",
    "exec", "subprocess", "shell", "spawn", "command",
    "client", "request", "fetch", "http", "url",
    "serialize", "pickle", "yaml", "parse", "deser",
    # Short tokens that would substring-match unrelated names (`format`,
    # `transform`, `sandbox`, `platform`) are intentionally omitted —
    # `sql`/`query` already cover the DB surface.
    "sql", "query",
)
# Suffixes that pass _is_reviewable_source but are almost always low-signal
# in large scaffolds — generated clients, migrations, test fixtures, config
# shims. These go to the BACK of the priority sort, not dropped outright.
_LOW_PRIORITY_SUFFIXES = (
    ".gen.ts", ".gen.tsx", ".generated.ts", "_gen.py",
    ".test.ts", ".test.tsx", ".test.py", ".spec.ts", ".spec.js",
    ".config.js", ".config.ts", ".config.mjs", ".config.cjs",
)
_LOW_PRIORITY_PATH_TOKENS = (
    "/migrations/", "/alembic/versions/", "/__tests__/", "/fixtures/",
)


def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
```
