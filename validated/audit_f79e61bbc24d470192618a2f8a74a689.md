### Title
Path-traversal via prefix-only `startsWith` check in `resolveWithin` allows escaping the repository root when opening a deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` (used by the `x-github-client://openRepo/...?filepath=...` deep-link handler) is supposed to guarantee that a resolved path stays inside the target repository. Its final containment check is a plain string `startsWith` comparison between the resolved real path and the repository's real path, with no check for a path-separator boundary. This is the classic "prefix-only" path-traversal bug: a sibling directory whose name simply *starts with* the repository directory's name (e.g. `repo` vs `repo-1`, `repo-backup`, `repo2`) will be treated as "inside" the repository even though it is a completely different folder.

### Finding Description
`_resolveWithin` in [1](#0-0)  resolves the root and the user/attacker-supplied path with `fs.realpath` (which follows symlinks) and then validates containment with:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This check does not verify that `realResolved` is exactly `realRoot` or `realRoot + path.sep + ...`. A path such as `/Users/alice/Documents/repo-attacker-controlled/secret.txt` satisfies `.startsWith('/Users/alice/Documents/repo')` even though it lives in an entirely different, sibling directory.

This function is the sole guard used by `openRepositoryFromUrl` in the dispatcher when handling the `filepath` query parameter of an `openRepo` deep link: [2](#0-1) 
The `filepath` value itself is fully attacker-controlled — it comes straight from `parseAppURL`'s query-string parsing with only an `isAbsolute` rejection (relative path traversal segments like `..` are normalized away by `path.resolve`, but the sibling-prefix bug bypasses this entirely via a symlink or an actual sibling folder): [3](#0-2) 

Two realistic ways to trigger the sibling-prefix collision exist in Desktop's own environment:
1. Desktop itself creates sibling directories with incrementing suffixes (`repo`, `repo-1`, `repo-2`, …) when cloning a repository whose folder name already exists, so users routinely have directories on disk that are prefix-extensions of one another.
2. A cloned repository can contain a symlink (a valid git object type) that points from inside the repo to a sibling directory/file outside it; `realpath` on the resolved path would then land in that sibling location, which the buggy `startsWith` check would still accept because of the shared name prefix.

### Impact Explanation
When the check passes, `openRepositoryFromUrl` calls `shell.showItemInFolder(resolved)` [4](#0-3) , revealing/selecting an attacker-chosen file *outside* the intended repository in the user's file manager — without any warning that it is outside the repo (the existing guard comment/log implies containment is guaranteed, so the "outside repo root" log branch is never hit). This breaks the invariant the code explicitly documents ("Prevented attempt to open path outside of the repository root") and can expose the existence/location of sensitive sibling files (e.g. another private repo, a backup folder, credentials directory) to a user who merely clicked a link, and can trick the user into further interacting with (opening/executing) that revealed file. `resolveWithin` is also reused elsewhere (`app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`) for similar containment checks, so the same primitive could affect those call sites too.

### Likelihood Explanation
This requires only that the user click a specially crafted `x-github-client://openRepo/...?filepath=...` link (or open such a URL via the CLI/protocol launcher) — no local access, no admin rights, and no prior compromise are needed. The precondition (a sibling directory whose name is a superstring of the repo's directory name) is very plausible given that Desktop itself generates such names when resolving clone-path collisions, and/or the attacker can supply a symlink inside the very repository referenced by the deep link to redirect resolution to a sibling path.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to require an exact match or a match followed by the platform path separator:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
where `sep` is the appropriate separator for the `options` path module in use (`Path.sep`, `Path.posix.sep`, or `Path.win32.sep`). Apply the same fix to all `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` variants and add regression tests covering sibling-directory-prefix collisions (`repo` vs `repo2`).

### Proof of Concept
1. User has (or Desktop has created due to a naming collision) two folders: `~/Documents/repo` (the trusted, currently open repository) and `~/Documents/repo-secrets` (any sibling folder, could be another private clone).
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/attacker/repo?filepath=../repo-secrets/config.json`
   — actually simpler: the attacker gets the victim to open a repo whose working tree contains a symlink `evil -> ../../repo-secrets` (committed to the malicious repo and cloned by the victim), then sends:
   `x-github-client://openRepo/<attacker-repo-url>?filepath=evil/config.json`
3. `openRepositoryFromUrl` resolves the repo, then calls `resolveWithin(repository.path, 'evil/config.json')`.
4. `realpath` resolves `evil/config.json` to `/Users/alice/Documents/repo-secrets/config.json`. `realRoot` is `/Users/alice/Documents/repo`.
5. `'/Users/alice/Documents/repo-secrets/config.json'.startsWith('/Users/alice/Documents/repo')` → `true`, so the check incorrectly passes.
6. `shell.showItemInFolder('/Users/alice/Documents/repo-secrets/config.json')` reveals the out-of-repo file to the user, confirming the containment guarantee is broken.
