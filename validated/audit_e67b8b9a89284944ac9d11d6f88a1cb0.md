### Title
Cached FROST preprocess is never invalidated, enabling deterministic nonce reuse across multiple `sign` invocations and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug is a check-then-use over shared mutable state: `__nft_obj_type_get()` iterated a list that `nft_unregister_obj()` could mutate concurrently, with no revocation between lookup and use. The Serai analog lives in `SigningProtocol::preprocess_internal`: a FROST `CachedPreprocess` (a seed from which both nonce commitments and the secret nonces are deterministically re-derived) is read from the DB but never deleted or marked consumed. Every subsequent call for the same `context` reconstructs an `AlgorithmSignMachine` with *identical* secret nonces and calls `sign` again, with attacker-influenced preprocesses. This directly violates the documented invariant that a cached preprocess "MUST only be used once" (spec/cryptography/FROST.md:51-55, crypto/frost/src/sign.rs:211-213).

### Finding Description
`preprocess_internal` looks up `CachedPreprocesses::get(self.txn, &self.context)`; if absent it generates a machine, caches `machine.cache()` (the ChaCha20Rng seed XOR-masked), and stores it. If present it reuses it unchanged — there is no delete/consume step:

- coordinator/src/tributary/signing_protocol.rs:123-145 (`get` → reuse → `from_cache`)
- `from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)` regenerates the identical `nonces` and `commitments` (crypto/frost/src/sign.rs:121-144, 268-274).

`share_internal` calls `preprocess_internal(...)` then `machine.sign(preprocesses, msg)` (signing_protocol.rs:156-170). Critically, `DkgConfirmer::complete` calls `share_internal` *again* (signing_protocol.rs:321-324), so the same seed drives `sign` a second time, and any additional `share`/`complete` invocation under the same `context` (e.g. `(b"DkgConfirmer", self.attempt)`, signing_protocol.rs:275) repeats it.

Inside `sign`, the effective nonce is `base + actual * binding_factor` where `base`/`actual` come from the reused seed, while `binding_factor` (rho) is derived from the attacker-supplied preprocesses via `B.calculate_binding_factors(&rho_transcript)` (crypto/frost/src/sign.rs:348-396). The share is `s = (d + e·ρ) + λ·x·c` where `c` is the Schnorr challenge over the aggregate `R`. With a fixed seed, `d` and `e` are constant across calls, while `ρ`, `λ`, and `c` vary with the preprocess set supplied in each call.

### Impact Explanation
Each `sign` call with a distinct preprocess set yields one linear equation in the unknowns `(d, e, λx-coupled secret terms)`. Concretely, when the *signer set* changes across calls, the Lagrange coefficient `λ` changes too, so each equation carries known `ρ_i`, `λ_i`, `c_i` with three unknown scalars `d, e, x` (the secret share): `s_i = d + e·ρ_i + λ_i·x·c_i`. Three calls with distinct preprocess maps give three equations in three unknowns — solvable for `x`, the validator's FROST/MuSig secret share, by any participant who observes the broadcast shares. The `preprocesses` map is populated from bytes supplied by other participants (`read_preprocess` on untrusted input), so choosing distinct preprocess sets is within an unprivileged participant's control. Recovery of the secret share collapses the threshold scheme: the attacker can subsequently forge `SignatureShare`s for arbitrary messages.

Even the two shares emitted by the natural `share` → `complete` flow already leak when preprocesses differ between the calls, and each further retry adds an equation.

### Likelihood Explanation
Reachability requires `share_internal`/`preprocess_internal` to run multiple times under one `context`. `DkgConfirmer::share` followed by `DkgConfirmer::complete` does exactly this (two `sign` executions on the same seed), and `complete` is expected to be called after `share` in the normal protocol flow. For full key recovery, three distinct preprocess sets must reach `sign` — achievable if a participant submits different preprocess bytes across attempts within the same context, or across the share/complete boundary where the preprocess map is re-supplied. The `context` is keyed only by `attempt`, so nothing prevents repeat invocation within an attempt; I was unable to fully trace `handle.rs` to confirm how many distinct preprocess sets can reach `share_internal` in practice, which is the main uncertainty on likelihood.

### Recommendation
Consume the cache on use: after `CachedPreprocesses::get` returns an existing entry, delete/tombstone it before calling `from_cache`, and have `complete` reuse the machine/state produced by `share` rather than re-running `share_internal` (which re-executes `sign`). Alternatively, persist per-context a counter or the emitted preprocess hash and panic on a second `sign` under the same context, enforcing the documented single-use invariant.

### Proof of Concept
1. A participant (validator) triggers `DkgConfirmer::share` with preprocess set P₁ and observes share `s₁`.
2. The same or another participant causes `share`/`complete` to run with distinct preprocess sets P₂, P₃ (different included signers or different commitment bytes) under the same `attempt`.
3. Because `CachedPreprocesses` is never consumed, all three calls derive identical `(d, e)` from the same seed via `ChaCha20Rng::from_seed`.
4. Solve the linear system `s_i = d + e·ρ_i + λ_i·x·c_i` (i=1..3) for `x`, the victim's secret share; verify against `ThresholdKeys::verification_share`.
