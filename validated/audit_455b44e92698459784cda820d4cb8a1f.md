### Title
`Scanner::register_offset` scripts map is global, not per-user: an earlier registration colliding onto an offset's even-Y point permanently DoSes or hijacks later registrations - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner` tracks registered offsets in a single global `HashMap<ScriptBuf, Scalar>` keyed only by the derived P2TR script. Because `register_offset` mutates the caller-supplied offset (incrementing until `key + offset*G` is even), two *distinct* requested offsets can resolve to the *same* script. Whichever registration happens first wins the `scripts` entry; any later registration that resolves to that script gets `None`. An unprivileged party who can influence which offsets get registered (e.g., deposit/HDKD offset assignment fed by attacker-controlled bytes) can pre-register a colliding offset and either (a) permanently block a victim's offset registration, or (b) cause the victim's deposits to be attributed to the attacker's `ReceivedOutput::offset`, since `scan_transaction` resolves scripts back through the single shared map.

### Finding Description
In `Scanner::register_offset` (`networks/bitcoin/src/wallet/mod.rs:180-196`), the requested `offset` is incremented in a loop until `p2tr_script_buf(self.key + GENERATOR * offset)` returns `Some` (i.e., the tweaked point has even Y). The resulting script is then checked against `self.scripts` — a global `HashMap<ScriptBuf, Scalar>` shared across all callers/contexts (line 155). If the script is already present, registration fails with `None` (line 188); otherwise the (incremented) offset is stored under that script (line 190).

This is the same bug class as `usedNonces` being global rather than per-address: the deduplication key space is shared across all offset registrants, so an offset "consumed" by one registrant invalidates the registration of a different registrant whose offset happens to collide. Because ~50% of offsets increment once, offset `o` (odd result → bumps to `o+1`) collides with offset `o+1` (already even). The script space is therefore surjective, and ordering decides ownership — as the doc comment itself admits ("offsets are surjective, not bijective, and the order offsets are registered in may determine the validity of future offsets", lines 174-175).

`scan_transaction` (lines 199-214) then maps any output paying to that script back to the *first-registered* offset, producing a `ReceivedOutput` carrying the attacker's offset value for a deposit intended under a different logical offset.

### Impact Explanation
Two concrete harms, both reachable by an unprivileged party able to cause offsets to be registered from public/untrusted data:

1. **Arbitrary DoS of registrations**: an attacker who can get offset `o` registered before a victim's `o+1` (or vice versa) causes the victim's `register_offset` to return `None` permanently — there is no retry path, since both derive to the identical script. This is the direct analog of "transaction from wallet B with nonce X reverts because wallet A used nonce X".
2. **Misattributed deposits**: if the victim's deposit transaction is broadcast anyway (the script is still the valid P2TR for `key + (o+1)*G`), `scan_transaction` returns a `ReceivedOutput` with the *attacker's* offset. Whatever downstream bookkeeping keys received funds by the registered offset will credit the attacker's registration for the victim's funds. The funds remain spendable (the tweaked key is identical), but attribution — the entire purpose of per-offset scanning — is corrupted.

### Likelihood Explanation
Collision requires only that two requested offsets map to the same even point — a 1-step increment happens with probability ~1/2 per registration, so the collision window is adjacent offsets, which is realistic when offsets are derived sequentially from attacker-influenced identifiers (e.g., per-deposit indices or hashes). The attacker needs only to observe or predict the victim's offset — offsets to public keys/scripts are publicly computable since the victim's script is published on-chain — then induce registration of a colliding offset first. No key material, validator status, or malformed curve/hash inputs are required.

### Recommendation
Track registrations per registrant/context rather than in a single global map — e.g., `HashMap<(context_id, ScriptBuf), Scalar>` or a nested `HashMap<context_id, HashMap<ScriptBuf, Scalar>>` — so one party's registration cannot consume another's script. Alternatively, reject increment-based resolution when the *adjusted* offset would collide with a different requested offset, and make `scan_transaction` attribute outputs by the (context, script) pair rather than script alone.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs behavior, conceptual PoC
let mut scanner = Scanner::new(key).unwrap();

// Victim intends to register offset o+1, where key + (o+1)*G is even.
let victim_offset = Scalar::from(2u64); // suppose this yields an even point

// Attacker registers offset o = victim_offset - 1, where key + o*G is ODD.
// register_offset increments o -> o+1, deriving the SAME script.
let attacker_requested = victim_offset - Scalar::ONE;
let attacker_actual = scanner.register_offset(attacker_requested).unwrap();
assert_eq!(attacker_actual, victim_offset); // incremented into victim's script

// Victim's registration now fails entirely — global scripts map already has the script.
assert_eq!(scanner.register_offset(victim_offset), None);

// Worse: a deposit paying to the victim's script is attributed to the attacker.
let outputs = scanner.scan_transaction(&victim_deposit_tx);
assert_eq!(outputs[0].offset(), attacker_actual /* = victim_offset value, but the
    registration entry belongs to the attacker's earlier registration */);
```

Root cause: `self.scripts` at `wallet/mod.rs:155` is a single map shared across all registrations, and the collision check at line 187 (`self.scripts.contains_key(&script)`) keys deduplication on the script alone — the "nonce" is tracked collectively, not per registrant.
