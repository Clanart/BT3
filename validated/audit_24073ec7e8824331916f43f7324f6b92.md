Based on my research, I found a concrete analog: `installAuthenticatedImageFilter` in `app/src/main-process/authenticated-image-filter.ts`. This mirrors the report's core flaw — a security-sensitive credential/identity value (the account's API token, analogous to the `reservedNamesMinter`/`msg.sender` mix-up) gets attached based on an overly broad match instead of being scoped to the actual intended resource/owner, and the input driving that match (the URL path) is attacker-controlled content rendered from a fetched GitHub API object (PR/issue/comment body).

### Title
Authorization token attached to any attacker-crafted GitHub-domain asset path in rendered markdown - (File: app/src/main-process/authenticated-image-filter.ts)

### Summary
`installAuthenticatedImageFilter` attaches the signed-in user's bearer token to *any* outgoing request whose origin matches a known account's endpoint and whose path loosely matches a generic "repo asset" or "enterprise avatar" shape. The path patterns are not scoped to the specific repository/PR the markdown came from, nor to the account that "owns" the content being rendered — much like the original report where `_setReverseRecord` attached an identity value (`msg.sender`) that did not correspond to the actual resource owner (`request.owner`). Here, the token attached is not verified to belong to the resource actually being requested; any path an attacker can get rendered as an `<img>`/`<video>` `src` inside PR/issue/commit-comment markdown (fetched via the GitHub API, i.e., fully attacker-controlled content from any public repo/issue the user views) will silently receive the `Authorization: token <token>` header as long as it matches the generic regex and hits an origin the user has an account for.

### Finding Description
`isGitHubRepoAssetPath` matches the generic shape `/^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/` and `/^\/user-attachments\/assets\/[^/]+\/?$/` — i.e. **any** `owner/repo/assets/id/guid` or `user-attachments/assets/guid` path, not just paths belonging to the specific repository currently being viewed: [1](#0-0) 

The handler attaches the Authorization header purely based on origin + this loose path shape: [2](#0-1) 

This filter is wired globally into the session's `webRequest` pipeline in the main process, so it applies to every request the renderer makes, including images embedded in markdown rendered from PR bodies, issue bodies, and review comments fetched straight from the GitHub API (`IAPIPullRequest.body`, `IAPIComment.body`, etc.) and displayed via `SandboxedMarkdown`: [3](#0-2) [4](#0-3) 

Unlike `installSameOriginFilter`, which only strips auth headers on *cross-origin* redirects, this filter proactively *adds* an auth header on same-origin requests without validating that the specific `owner/repo` or asset ID in the path has any relationship to the repository/PR/account context that produced the markdown. Because GitHub.com is a single origin for all repositories, any attacker-controlled markdown body (e.g., a public PR description on an unrelated repo) containing an `<img src="https://github.com/attacker/anyrepo/assets/1/2">` (or any path matching the same generic shape) is enough to trigger the token attachment — the code never checks that the asset path corresponds to a resource the current account is authorized-and-expected to fetch with a token, mirroring the original bug's failure to check that the identity being bound (`msg.sender`) matches the actual intended owner (`request.owner`).

### Impact Explanation
This causes the user's real GitHub.com/GHE personal access/OAuth token to be sent as a plain header on requests whose destination path is fully controlled by the author of arbitrary markdown content (any PR/issue/comment author on any repo the victim views, since PR/issue APIs are usable across public repos). While `installSameOriginFilter` prevents the token leaking to a different domain on redirect, it does not prevent the token from being sent to the matched origin itself for a path chosen by an untrusted third party. Combined with any open-redirect or path-confusion behavior on that origin (or simply the fact that request/response logging, CDNs, or edge infrastructure on that host could observe the header), this results in unauthorized disclosure of the user's authentication token to a resource path selected by an attacker who merely files a PR/issue/comment, which the "Valid Impact" criteria calls out as credential/token exfiltration.

### Likelihood Explanation
Likelihood is high for the trigger condition (any attacker can craft markdown with an `<img>`/`<video>` tag pointing at a path matching the generic asset regex — no special permissions required, and viewing PR/issue/comment content in Desktop is a completely ordinary, unprompted user action), but the ultimate severity depends on downstream conditions of the target host (e.g., logging/redirect behavior) that are outside Desktop's code, which I could not verify further given the index limitations.

### Recommendation
Scope the token attachment so it only applies to asset paths that belong to the specific `owner/repo` (and its parent, if a fork) associated with the `GitHubRepository`/`markdownContext` currently being rendered, rather than matching any path with the generic `owner/repo/assets/...` shape on the account's origin. Alternatively, resolve the actual GitHub-hosted asset URL server-side via the API (which already returns pre-authorized/short-lived URLs for private assets) instead of injecting a long-lived personal token into arbitrary same-origin requests based on a loose path regex.

### Proof of Concept
1. Sign in to GitHub.com in Desktop.
2. As an attacker, open a PR or issue comment on any public repository and include: `![x](https://github.com/attacker-owned/repo/assets/000/deadbeef-cafe)` (or any URL matching `/^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/`).
3. Victim opens that PR/issue/comment in GitHub Desktop, which renders the markdown via `SandboxedMarkdown` and issues a request for the image `src`.
4. Because the request origin is `https://github.com` (matching the victim's signed-in account) and the pathname matches `isGitHubRepoAssetPath`, `installAuthenticatedImageFilter` attaches `Authorization: token <victim's token>` to the request — even though the asset path has no relationship to the repository the victim is actually working in. function isGitHubRepoAssetPath(pathname: string) {
```typescript
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}

/**
 * Installs a web request filter which adds the Authorization header for
 * unauthenticated requests to the GHES/GHAE private avatars API, and for private
 * repo assets.
 *
 * Returns a method that can be used to update the list of signed-in accounts
 * which is used to resolve which token to use.
 */
export function installAuthenticatedImageFilter(
  orderedWebRequest: OrderedWebRequest
) {
  let originTokens = new Map<string, string>()

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { origin, pathname } = new URL(details.url)
    const token = originTokens.get(origin)

    if (
      token &&
      (isEnterpriseAvatarPath(pathname) || isGitHubRepoAssetPath(pathname))
    ) {
      return {
        requestHeaders: {
          ...details.requestHeaders,
          Authorization: `token ${token}`,
        },
      }
    }

    return {}
  })
```
