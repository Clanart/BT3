### Title
"Always allow" permission rules persist at the repository root and are not cleared when repo ownership/identity changes across worktrees or forks - (File: permission settings storage, per `CHANGELOG.md`)

### Summary
The Aave Lens report describes approvals indexed by an NFT owner/profile pair that are never cleared when the underlying NFT (profile) is transferred to a new owner, so old approvals silently persist and could be exploited or misapplied by a future owner. The closest analog in claude-code is the "Always allow" permission-rule persistence model: approvals are saved at the git repository root and explicitly designed to **persist across sessions and worktrees** rather than being scoped to the specific checkout, branch, or user session that requested them [1](#0-0) . Because these rules are tied to the repository root path rather than to a specific trusted identity/session, a rule granted under one context (e.g., a worktree checked out from a particular branch/remote) remains active for any other worktree or session that shares the same root, even if the repo's remote, branch content, or ownership context has since changed.

### Finding Description
Claude Code's permission system supports "Always allow" rules that a user grants during a session for a specific tool/command pattern. The changelog documents that these rules are saved at the repository root specifically so that "approvals granted in a git worktree persist across sessions and worktrees" [1](#0-0) . This is the same trust-boundary design choice flagged as Medium severity in the Aave Lens report: an approval is keyed to a coarse-grained identifier (repository root / worktree family) rather than to the specific context in which the grant was made, and there is no mechanism shown in the changelog to invalidate or re-scope these rules when the underlying repository content, remote, or branch changes.

Separately, the same persistence philosophy is echoed in "Changed 'always allow' rules to save at the repository root" fix history, and in the fact that managed-settings allow rules were found to remain active even after an admin removed them, until process restart [2](#0-1)  — a directly analogous "approval not cleared" defect that Anthropic itself classified as a bug and fixed.

### Impact Explanation
If a repository's remote/ownership context changes (e.g., a worktree is repointed at a different fork, or a shared directory is reused for a different untrusted codebase) while an "Always allow" rule from a prior, trusted context is still saved at the repo root, tool actions (e.g., Bash commands) could be silently auto-approved in the new, potentially untrusted context without a fresh prompt — mirroring the "old approvals intact when profile is transferred back" scenario from the report. This does not grant new privileges beyond what the user already approved once, but it removes the expected re-confirmation step, which the original report's judge treated as impacting "the function of the protocol or its availability" rather than being a direct asset-loss vulnerability.

### Likelihood Explanation
This requires a user to reuse a repository root across differing trust contexts (worktree repointed to a different remote, or directory reused for a different project) — a real but not default workflow. Anthropic's own changelog shows they are actively aware of and fixing several similar "approval / rule state not cleared on context change" issues (e.g., managed-settings allow rules staying active after removal until restart), indicating this class of bug recurs in this codebase's permission-persistence design [3](#0-2) .

### Recommendation
Scope "Always allow" rules to a fingerprint that includes the repository's remote URL/identity (not just the worktree root path), and invalidate or re-confirm previously granted rules when the underlying repository's remote or root commit history diverges unexpectedly. This mirrors the original report's recommended mitigation of resetting/re-validating approvals whenever the underlying "owner" (here, repo identity) changes.

### Proof of Concept
Not independently reproducible from the indexed changelog/documentation alone — this is inferred from Anthropic's own release notes describing the persistence behavior and related historical fixes. A concrete PoC would require: (1) granting an "Always allow" Bash rule in worktree A of repo root R; (2) repointing or reusing root R's worktree for a different remote/untrusted content; (3) observing whether the prior rule still silently auto-approves matching commands. This should be validated with a live Devin session against the actual settings-resolution code (not present in the indexed excerpts) rather than asserted as confirmed. [1](#0-0) [3](#0-2)
