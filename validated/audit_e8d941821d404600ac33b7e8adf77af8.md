## Title
Aggregator gRPC Endpoint Exposes Unauthenticated Broadcasting/State-Changing RPCs (`InternalSendTx`, `Setup`, `NewDeposit`) - (File: `core/src/servers.rs`, `core/src/rpc/aggregator.rs`)

## Summary
The bug class in the external report — a state-changing function meant to be called only by a single trusted caller (`EndPoint`) being reachable by any caller — has a direct analog in Clementine's Aggregator gRPC server. By explicit, documented design, the Aggregator "does not enforce client certificates" [1](#0-0)  while Verifier/Operator servers apply an mTLS interceptor (`OnlyAggregatorAndSelf`) that restricts callers to the aggregator or the entity itself [2](#0-1) . Because the Aggregator server is created through the same `create_grpc_server` helper but skips this authentication layer, every RPC exposed by `ClementineAggregator` — including `InternalSendTx`, which directly inserts an arbitrary caller-supplied raw Bitcoin transaction into the broadcasting/fee-bumping pipeline — is reachable by any network client with no authentication, not just the intended "clementine-backend service" caller.

## Finding Description
Verifier and Operator servers gate every RPC by peer TLS certificate: normal methods require the aggregator's certificate or the entity's own certificate, and any RPC whose name is prefixed `Internal` additionally requires the entity's *own* certificate (self-only) [3](#0-2) [4](#0-3) .

The Aggregator server is built with the identical `create_grpc_server` function [5](#0-4) , and that function only installs the `OnlyAggregatorAndSelf` interceptor `if config.client_verification` [6](#0-5) . Per the project's own documentation, "The aggregator does not enforce client certificates but does use TLS for encryption" [1](#0-0)  — i.e., this is the intended, documented production posture for the aggregator, not a misconfiguration.

As a consequence, the `Internal`-prefixed naming convention that signals "self-only" on the Verifier/Operator surface provides **no protection at all** on the Aggregator surface, since no certificate check (and hence no `is_internal` gating) is ever applied to Aggregator requests. This exposes, to any network caller who can reach the Aggregator's TCP/TLS endpoint:

- `internal_send_tx` — accepts an arbitrary raw signed Bitcoin transaction and a fee type, and unconditionally hands it to the aggregator's own `tx_sender` for the automation RBF/CPFP fee-bumping and broadcast pipeline [7](#0-6) .
- `setup` — re-runs the multi-actor protocol setup pipeline across all operators/verifiers [8](#0-7) .
- `new_deposit` — triggers the full MuSig2 nonce/sign/finalize pipeline with every verifier and operator [9](#0-8) .

These are exactly the kind of state-changing/broadcast-triggering methods the external report's `onlyEndpoint` fix targeted: functions intended to be invoked only by one specific, trusted caller ("clementine-backend service" per the proto comments [10](#0-9) ) but reachable by anyone.

## Impact Explanation
This satisfies the High-severity bucket explicitly defined by the rules: "an unauthenticated state-changing or broadcasting call." `internal_send_tx` is the sharpest instance — it lets any unauthenticated party force the aggregator's Bitcoin infrastructure to accept and attempt to broadcast/fee-bump a transaction of the attacker's choosing, consuming the aggregator's own fee-paying UTXOs and CPFP/RBF machinery for transactions the protocol never intended to send. `setup`/`new_deposit` similarly let any unauthenticated caller trigger expensive, protocol-critical coordination flows across every operator and verifier in the bridge on demand.

## Likelihood Explanation
No credentials, roles, or secrets are required — only network reachability to the Aggregator's gRPC port, which per the documented deployment model is the intended way for external clients (the backend service, and by extension anyone who can reach that address/port) to interact with the bridge. Since the code path providing authentication (`OnlyAggregatorAndSelf`) is architecturally never wired to the Aggregator service, this is deterministic and always exploitable wherever the Aggregator is deployed as documented.

## Recommendation
Add an explicit authentication/authorization layer to the Aggregator's gRPC surface (e.g., API-key or mTLS-based restriction to the legitimate backend service caller), particularly for `internal_send_tx`, `setup`, and `new_deposit`. At minimum, apply the same `is_internal`-style self-only restriction concept to `Internal`-prefixed Aggregator RPCs, since currently the naming convention implies a protection that is never enforced on this server.

## Proof of Concept
1. Deploy Clementine per documented instructions (Aggregator without `client_verification`, as documented in `docs/usage.md`).
2. From any machine with network access to the Aggregator's TLS port, construct a `ClementineAggregatorClient` (no client certificate required beyond generic TLS).
3. Call `internal_send_tx` with an arbitrary valid raw Bitcoin transaction hex and a `fee_type` — the aggregator will accept it and queue it into its `tx_sender` for broadcast/fee-bumping [11](#0-10) , without verifying the caller is the intended backend service.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
