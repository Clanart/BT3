Audit Report

## Title
`get_filtered_program_accounts()` (`getProgramAccounts` RPC path) performs an unbounded full-scan with no `byte_limit_for_scan`, unlike the SPL-token/index-key path - ([File: accounts-db/src/accounts.rs])

## Summary
`Bank::get_filtered_program_accounts` forwards directly to `Accounts::load_by_program_with_filter`, which scans all accounts owned by `program_id` with `ScanConfig::default()` and no size cap, materializing the entire result set into an in-memory `Vec<KeyedAccountSharedData>` before returning it to the RPC layer. [1](#0-0) 
This is in contrast to the sibling `load_by_index_key_with_filter` path used for SPL-token owner/mint filtered queries, which tracks accumulated result size and aborts the scan via `ScanError::Aborted` once `byte_limit_for_scan` is exceeded. [2](#0-1) 

## Finding Description
`get_filtered_program_accounts` at the RPC layer dispatches to `Bank::get_filtered_program_accounts` for any `getProgramAccounts` call that does not match an SPL-token owner/mint filter shape, and that function calls straight into `Accounts::load_by_program_with_filter`, which has no `byte_limit_for_scan` parameter at all — unlike `load_by_index_key_with_filter`, which explicitly wires an `Option<usize>` byte limit through to `accumulate_and_check_scan_result_size`/`maybe_abort_scan`. [3](#0-2) [4](#0-3) 
This asymmetry is confirmed to exist verbatim in this repository: `runtime/src/bank.rs`'s `get_filtered_program_accounts` (lines 5121–5132) has no size-limit parameter, while `get_filtered_indexed_accounts` (lines 5134+) explicitly threads a `byte_limit_for_scan: Option<usize>` through to the accounts layer. [5](#0-4) 

## Impact Explanation
This matches the allowed "single-client low-rate RPC crash/degradation" impact category: an unprivileged client can issue a `getProgramAccounts` call against a program that owns a very large number of accounts with no narrowing filter, forcing the validator's RPC thread to allocate and serialize the entire matching account set in one response, with no in-process circuit breaker on the number of bytes/accounts collected before this fix would be applied.

## Likelihood Explanation
Likelihood is high for triggering resource strain: the request requires only a syntactically valid `program_id`, no special permissions, and no assumptions about malicious peers/validators — any RPC client can issue it directly against a public JSON-RPC endpoint. Mitigation currently depends entirely on operator-side configuration (rate limiting, request body size limits, disabling `getProgramAccounts`) rather than any code-level safeguard analogous to `byte_limit_for_scan` in the non-indexed path.

## Recommendation
Thread an explicit `byte_limit_for_scan` (or equivalent account-count cap) through `Bank::get_filtered_program_accounts` → `Accounts::load_by_program_with_filter` → `AccountsDb::scan_accounts`, reusing the existing `accumulate_and_check_scan_result_size`/`maybe_abort_scan` pattern already implemented for `load_by_index_key_with_filter`, and surface a clear `RpcCustomError` when the scan is aborted for exceeding the limit, mirroring the "Slot range too large" pattern used elsewhere in the RPC layer.

## Proof of Concept
1. Identify or deploy a program that owns a very large number of accounts on the target cluster.
2. Issue `getProgramAccounts` for that `program_id` with no `filters`.
3. The RPC layer's `get_filtered_program_accounts` routes to `Bank::get_filtered_program_accounts` → `Accounts::load_by_program_with_filter`, which uses `ScanConfig::default()` with no byte-limit enforcement, unlike the index-key path.
4. Observe unconstrained memory allocation and serialization proportional to the full matching account set, with no server-side abort mechanism analogous to the one implemented for SPL-token filtered variants. [3](#0-2)

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    pub fn load_by_index_key_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }
