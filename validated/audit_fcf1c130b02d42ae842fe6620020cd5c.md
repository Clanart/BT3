## Analysis

The reported issue class — code assuming ERC-20 `transferFrom`/`approve` calls always return a decodable `bool`, which reverts against non-standard tokens (e.g. USDT-style tokens with no return data) — has a direct analog in this repository's IBC callback flow.

The `x/erc20` module already defends against non-standard ERC-20 return semantics in some places. In `ConvertCoinNativeERC20` and `convertERC20IntoCoinsForNativeToken`, the code explicitly checks `len(res.Ret) == 0` and falls back to inspecting emitted `Transfer` events via `validateTransferEventExists` before trying to unpack a bool. [1](#0-0) [2](#0-1) 

However, `IBCReceivePacketCallback` in `x/ibc/callbacks/keeper/keeper.go` does **not** apply this same defensive pattern when it calls `approve` on the token's ERC-20 contract on behalf of the isolated receiver address, then immediately unpacks the return value as a `bool`: [3](#0-2) 

`tokenPair.GetERC20Contract()` here can point to an arbitrary, permissionlessly-registered native ERC20 contract (registration is permissionless when `PermissionlessRegistration` param is enabled). [4](#0-3) 
If that contract is a non-standard ERC-20 (returns no data on `approve`, like USDT), `res.Ret` will be empty and `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` fails, causing `IBCReceivePacketCallback` to return an error before the destination contract's `transferFrom` step ever runs.

Because the receiver of the underlying ICS20 transfer is a deterministic, non-user-controlled "isolated address" generated per packet/sender/channel (`types.GenerateIsolatedAddress`), and the callback is what's supposed to move the tokens into the destination contract via `transferFrom`, a failure at the `approve` step leaves the transferred tokens credited to that isolated address permanently, with no path to recovery (no known private key controls it, and it's only used as a callback intermediary). [5](#0-4) [6](#0-5) 

I was not able to fully verify, within available tool budget, how `ibc-go v10`'s destination-callback middleware treats an error returned from `ContractKeeper.IBCReceivePacketCallback` (i.e., whether the packet `OnRecvPacket` itself is still considered successful with funds already credited, or whether the whole receive is failed/reverted). This distinction is critical to confirming permanent-freeze impact vs. a simple recoverable failure, and I could not locate the relevant `ibc-go` callback dispatch code in the indexed portion of this repo to confirm it.

### Title
Unhandled non-standard ERC-20 `approve()` return value in IBC receive-packet callback can strand IBC-transferred tokens - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`ContractKeeper.IBCReceivePacketCallback` blindly unpacks the `approve` call's return data as a `bool` without handling the empty-return-data case that non-standard ERC-20 tokens produce, unlike the equivalent logic already implemented in `x/erc20/keeper/msg_server.go`.

### Finding Description
When an inbound ICS20 transfer with a destination callback targets a native ERC20 token pair whose underlying contract does not return a boolean from `approve()` (non-standard ERC-20, analogous to USDT), the call `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` at [7](#0-6)  fails to decode a `bool` from zero-length return data, causing the function to return an error and abort before executing the destination contract call that would move tokens out of the isolated receiver address via `transferFrom`.

### Impact Explanation
If the callback failing does not roll back the underlying ICS20 token receipt (funds already credited to the isolated address as part of packet processing), the transferred tokens become permanently stuck at a deterministic address with no corresponding private key and no remaining code path to move them out, since the escape hatch (the target contract's `transferFrom`) is never reached. This matches the in-scope "permanent freezing/locking of user funds" impact triggerable by an ordinary, unprivileged IBC transfer sender.

### Likelihood Explanation
Triggerable by any unprivileged user/relayer submitting a standard ICS20 transfer with a destination-callback memo for a natively-registered, non-standard ERC-20 token pair. No special privileges are required, only that such a token pair exists (registration can be permissionless per `x/erc20` params).

### Recommendation
Apply the same `len(res.Ret) == 0` / event-log fallback pattern used in `convertERC20IntoCoinsForNativeToken`/`ConvertCoinNativeERC20` (checking for an `Approval` event when return data is empty) to the `approve` call inside `IBCReceivePacketCallback`, or use a Safe-approve-style helper.

### Proof of Concept
Not independently reproduced; I was unable to confirm within the available context whether `ibc-go v10`'s destination callback middleware fails the entire receive-packet processing (making the ICS20 transfer itself revert, which would eliminate the freezing impact) or only fails the callback while the underlying transfer completes (which would produce the stranded-funds condition described above). Confirming this middleware behavior is necessary before treating this as a confirmed Critical finding.
