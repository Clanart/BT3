### Title
Out-of-range `Participant` index in blame evaluation panics on HashMap lookup - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP `BlameMachine::blame` / `AdditionalBlameMachine::blame` APIs accept attacker-supplied `sender` and `recipient` `Participant` indexes and pass them directly into `blame_internal`, which indexes `self.commitments[&sender]` without any bounds check. A blame accusation naming a participant outside `1..=n` causes a panic instead of a clean error, crashing the evaluating node — the Serai analog of the reachable-DoS crash class in CVE-2023-22065.

### Finding Description
`BlameMachine::blame` takes `sender: Participant` and `recipient: Participant` from the caller, who supplies an accusation received from another party (`crypto/dkg/pedpop/src/lib.rs:623-632`). It forwards them unmodified to `blame_internal`:

```rust
let faulty = self.blame_internal(sender, recipient, msg, proof);
```

Inside `blame_internal`, the sender index is used as a raw HashMap key (`crypto/dkg/pedpop/src/lib.rs:596-600`):

```rust
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],
    Zeroizing::new(share),
  ))
  .is_identity(),
) {
```

`self.commitments` is only ever populated with keys `Participant(1)..=Participant(n)` — either via `verify_r1` iterating `all_participant_indexes()` (`lib.rs:313-336`) or via `AdditionalBlameMachine::new` iterating `1..=n` (`lib.rs:656-660`). Neither `blame`, `blame_internal`, nor `AdditionalBlameMachine::blame` validates that `sender` or `recipient` lies within `1..=n`. `Participant::new` only rejects zero; any nonzero u16 up to 65535 is a valid `Participant`, and `std::collections::HashMap`'s `Index` impl panics on a missing key. `AdditionalBlameMachine` is explicitly designed to evaluate blame "regardless of if the caller was a member in the DKG protocol" (`lib.rs:639-648`), i.e. it processes accusations originating from untrusted third parties, making attacker-controlled indexes a realistic input.

### Impact Explanation
A party submitting a blame accusation (or relayed accusation evaluated by `AdditionalBlameMachine`) with `sender` or `recipient` set to a nonzero index not present in the DKG (e.g. `n + 1`) triggers a panic in the evaluating process. In a validator/processor deployment where blame evaluation runs on the node's thread, this aborts the DKG fault-handling path and can crash the process — an availability loss caused purely by unauthenticated/untrusted protocol inputs, matching the "hang or repeatable crash" impact of the reference CVE.

### Likelihood Explanation
`Participant` is a plain `u16` wrapper (`crypto/dkg/src/lib.rs:24-35`); constructing `Participant(n + 1)` is trivial and requires no cryptographic work. Any party able to submit or relay a blame claim can supply arbitrary indexes. The panic is deterministic and repeatable, and there is no earlier validation gate: `validate_map` is applied to commitment/share maps in other flows but never to the `blame` arguments.

### Recommendation
In `blame_internal` (or at the `blame` entry points), validate that both `sender` and `recipient` exist in `self.commitments` (or are within `1..=n`) before indexing, and return a defined result (e.g. blame the accuser/`sender`, or an error variant) instead of indexing. Replace `self.commitments[&sender]` with `.get(&sender)` and handle `None` gracefully.

### Proof of Concept
```rust
// After a normal PedPoP DKG producing BlameMachine `bm` with params n = 3:
// (or equivalently AdditionalBlameMachine::new(context, 3, commitment_msgs))

let bm: BlameMachine<Ristretto> = /* ... */;

// An accusation naming a non-existent sender. Participant::new only rejects 0.
let bogus_sender = Participant::new(4).unwrap(); // n = 3
let recipient = Participant::new(1).unwrap();
let msg: EncryptedMessage<Ristretto, SecretShare<_>> = /* any captured/malformed message */;

// Panics: `self.commitments[&sender]` -> HashMap index on missing key
let (_additional, _faulty) = bm.blame(bogus_sender, recipient, msg, None);
```

The panic occurs at `crypto/dkg/pedpop/src/lib.rs:599` (`&self.commitments[&sender]`) when `sender` is a nonzero participant index greater than `n`, since `commitments` only contains `1..=n` keys and no bounds check is performed on the blame arguments.

Note: the same unchecked indexing pattern exists in `ThresholdView::verification_share`/`original_verification_share` (`crypto/dkg/src/lib.rs:672-682`), but those take indexes already constrained by the view's `included` set; the `blame` path is the one where the index is fully attacker-controlled.

One caveat I could not fully verify: whether `encryption.decrypt_with_proof` (called earlier in `blame_internal`) rejects an out-of-range sender before the `commitments` index is reached — if it internally maps the sender index to registered encryption keys, it may also panic or error first. Either outcome is still an unhandled crash or, at best, an error path that returns `sender`/`recipient` blame for indexes that were never validated, so the missing validation finding stands.
