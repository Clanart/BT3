### Title
Out-of-bounds slice panic in `consoleLog.decode` due to unchecked `big.Int.Int64()` truncation on attacker-controlled offsets - (File: `blockchain/vm/contracts.go`)

### Summary
The `CONSOLE_LOG` precompiled contract's argument decoder computes dynamic-type (`StringTy`/`BytesTy`) offsets by reading a 32-byte big-endian word from user-controlled `input` and truncating it with `big.Int.Int64()`, then using that value directly as a slice index without checking that it is non-negative. A crafted `input` blob to the console-log precompile can make this computed `start` value negative, causing a Go slice-bounds-out-of-range runtime panic when the code executes `params[start : start+registerSize]`.

### Finding Description
`consoleLog.decode` in `blockchain/vm/contracts.go` handles `StringTy` and `BytesTy` arguments identically: [1](#0-0) 

For each dynamic argument, `start` is derived from `big.NewInt(0).SetBytes(params[pos:pos+registerSize]).Int64()`. `Int64()` on a `*big.Int` built from an arbitrary 32-byte word does not error or clamp — it simply returns the low 64 bits reinterpreted as a signed `int64`. An attacker can choose the 32-byte word such that the resulting `int64` is negative (e.g. a word whose low 8 bytes have the high bit set, like `0xFFFFFFFFFFFFFFFF`). The subsequent bound checks only compare against `len(params)`:
- `if len(params) < start+registerSize { return error }`

When `start` is a large negative number, `start+registerSize` is also negative, and `len(params) < (negative number)` is always `false`, so the check is bypassed. Execution then reaches `params[start : start+registerSize]`, a negative-index slice operation, which panics in Go with `slice bounds out of range`.

This precompile is reachable from ordinary contract execution: any contract that calls the address mapped to `consoleLog` (used to emulate Hardhat's `console.log`) with crafted calldata reaches `consoleLog.Run` → `toLogString` → `decode`: [2](#0-1) 

The selector dispatch table in `common/console_log.go` includes many entries with `StringTy`/`BytesTy` arguments (e.g. selector `0x41304fac` for `{StringTy}`), all of which funnel into the vulnerable `decode` logic: [3](#0-2) 

This is structurally analogous to CVE-2025-63657: a crafted, unprivileged request (there, an HTTP request driving `mk_mimetype_find`; here, a transaction/call driving `consoleLog.decode`) supplies attacker-controlled length/offset data that is used for an array access without adequate bounds validation, leading to an out-of-bounds access and a crash/DoS condition.

### Impact Explanation
If the panic is not recovered somewhere up the call stack (e.g., inside `RunPrecompiledContract` in `blockchain/vm/evm.go`, which I was unable to fully inspect before running out of investigation budget), any transaction sender or contract deployer could trigger a Go runtime panic during EVM execution of a call to the console-log precompile, crashing the node process that processes the transaction — a Denial-of-Service reachable via a single, ordinary transaction. If the panic is caught by a `recover()` wrapper around precompile execution, the practical impact is downgraded to an execution revert rather than a node crash, and this would not qualify as a valid high-severity analog under the stated rules.

### Likelihood Explanation
The `consoleLog` precompile appears intended for local/dev networks. I was unable to confirm from the available context whether `consoleLog` is registered in precompile sets active on public/production networks, or whether panics from precompile `Run` implementations are globally recovered by the EVM interpreter. **This is a material uncertainty I could not resolve within the available tool budget** — confirming both points (production reachability of the precompile address, and the presence/absence of panic recovery around `RunPrecompiledContract`) is necessary to establish a concrete, exploitable DoS.

### Recommendation
- Validate that `start`/`size` values derived from `Int64()` are non-negative and within `len(params)` before slicing, in both the `StringTy` and `BytesTy` branches of `consoleLog.decode`.
- Prefer `Uint64()`-based bounds checks (with explicit range/overflow checks) rather than `Int64()` truncation when deriving offsets from attacker-controlled 256-bit words.
- Confirm and, if necessary, add a `recover()` around precompiled-contract execution so no single malformed precompile input can crash the node.
- Confirm whether the `CONSOLE_LOG` precompile is enabled on production networks; if so, treat this as a directly reachable transaction-triggered DoS.

### Proof of Concept
1. Craft `input` for the `CONSOLE_LOG` precompile using selector `0x41304fac` (`log(string)`), which maps to `{StringTy}`.
2. After the 4-byte selector, provide the 32-byte "offset" word with value `0xFFFFFFFFFFFFFFFF...FF` (or any value whose low 8 bytes, interpreted as `int64`, are negative), e.g.:
   `41304fac` + `ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff`
3. Deploy/call a trivial contract that performs a raw `CALL` to the console-log precompile address with the above calldata (or call it directly if reachable as a top-level `to` address in a transaction).
4. `consoleLog.decode` computes `start = int64(-1)`, the length checks are bypassed because `start+registerSize` is negative, and `params[start:start+registerSize]` triggers a Go slice-bounds-out-of-range panic. [1](#0-0)

// Instead, we just join all the parameters with a space.
func (c *consoleLog) toLogString(input []byte) (string, error) {
	if len(input) < 4 {
		return "", errors.New("input too short")
	}
	selector := binary.BigEndian.Uint32(input[:4])
	params := input[4:]

	types, ok := common.ConsoleLogSignatures[selector]
	if !ok {
		return "", errors.New("unknown selector")
	}
	decoded, err := c.decode(params, types)
	if err != nil {
		return "", err
	}

	return strings.Join(decoded, " "), nil
}
