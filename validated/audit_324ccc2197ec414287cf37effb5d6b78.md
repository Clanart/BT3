### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers a ~2 MiB heap allocation from a handful of bytes, enabling unauthenticated memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2020-24697 (unauthenticated remote DoS via a crafted signed message), an unprivileged party who can feed bytes into `ThresholdKeys::read` can specify `n = 0xFFFF` in the serialization header and select `Interpolation::Constant`, causing `Vec::with_capacity(65535)` of field elements (~2 MiB) to be allocated before a single scalar byte is read. Repeated malicious messages exhaust memory, crashing the process.

### Finding Description
`ThresholdKeys::read` parses the keys format: a ciphersuite ID, then `t`, `n`, `i` (each `u16`), then an interpolation tag. When the tag is `0` (`Interpolation::Constant`), the code does: [1](#0-0) 

`Vec::with_capacity(usize::from(n))` reserves `n * size_of::<C::F>()` bytes immediately — up to 65535 × 32 B ≈ 2 MiB — before any `C::read_F` call validates that the input actually contains that many scalars. The attacker only needs to supply the fixed header (correct `C::ID`, `t`, `n`, `i`, tag byte); the subsequent `read_F` will hit EOF and return an `io::Error`, but the allocation already occurred.

Note that `ThresholdParams::new(t, n, i)` is only invoked *after* the allocation and the scalar reads, at line 626, so its validation provides no mitigation: [2](#0-1) 

This mirrors the advisory's shape: parsing attacker-controlled length/signing fields performs work (here allocation) proportional to attacker-chosen parameters, before input validity is established.

### Impact Explanation
A remote party able to submit bytes deserialized as `ThresholdKeys` (e.g., during key-generation message exchange or any node endpoint accepting serialized key material) can cause ~2 MiB of heap allocation per message with a ~10-byte input — an amplification factor of ~200,000×. A stream of such messages exhausts memory or triggers allocator pressure/OOM, a denial of service matching the CVSS 7.5 availability-only impact of the reference CVE. No signature, key share, or honest participation is required.

### Likelihood Explanation
`ThresholdKeys::read` is a listed reachable deserialization sink. The code path requires only: valid `C::ID` (public constant), tag byte `0`, and `n = u16::MAX`. `read_F` failures occur after the allocation, so the attack does not depend on producing valid scalars, points, or proofs. Cost per attempt is trivial; impact scales with message rate.

### Recommendation
Defer allocation until data is validated: either push into a `Vec::new()` inside the `read_F` loop (matching how `verification_shares` is read at line 621, which uses `HashMap::new()` and is not vulnerable), or cap `n` before `with_capacity` — e.g., reject `t > n` / `n` exceeding a sane bound before allocating, or read the scalars into a bounded structure. Alternatively, call `ThresholdParams::new(t, n, i)` first so `n` is sanity-checked prior to any allocation.

### Proof of Concept
```rust
// Construct a malicious ThresholdKeys serialization for e.g. Ristretto
let mut buf = vec![];
buf.write_all(&(C::ID.len() as u32).to_le_bytes()).unwrap();
buf.write_all(C::ID).unwrap();
buf.write_all(&1u16.to_le_bytes()).unwrap();        // t = 1
buf.write_all(&u16::MAX.to_le_bytes()).unwrap();    // n = 65535
buf.write_all(&1u16.to_le_bytes()).unwrap();        // i = 1
buf.write_all(&[0u8]).unwrap();                     // Interpolation::Constant
// No scalar bytes follow.

// Vec::with_capacity(65535) reserves ~2 MiB here before read_F fails on EOF
let res = ThresholdKeys::<C>::read(&mut buf.as_slice());
assert!(res.is_err()); // errors, but the allocation already happened
```
Replaying this in a loop against any endpoint deserializing `ThresholdKeys` forces repeated ~2 MiB allocations proportional to attacker message rate rather than attacker bandwidth.
