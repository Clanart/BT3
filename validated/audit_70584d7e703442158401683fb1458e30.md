### Title
`aptos move verify-package` certifies on-chain packages by comparing declared metadata/source text only, never the actual executed module bytecode - (File: aptos-move/cli/src/stored_package.rs)

### Summary
The bug-class from the report is "the value used to gate/compute trust doesn't include the actual value that matters" (unclaimed rewards excluded from `totalAssets()`). The Aptos-native analog is: the value used to gate/certify trust in a published package (`PackageMetadata`) does not include, and is never cross-checked against, the actual on-chain module bytecode that the VM will execute.

### Finding Description
`code::PackageMetadata::modules` (`aptos-move/framework/aptos-framework/sources/code.move:56-60`, mirrored in `aptos-move/framework/natives/src/code.rs:58-71`) stores only a module `name` and an optional gzipped `source` text blob — informational fields supplied by the publisher, with no on-chain link (hash or otherwise) to the actual compiled bytecode blob passed as the separate `code: vector<vector<u8>>` argument to `code::publish_package_txn`. The Move VM's `validate_publish_request` (`aptos-move/aptos-vm/src/aptos_vm.rs:1803-1841`) only checks that module *names* in the bytecode bundle match `expected_modules` from the metadata — it does not check that the bytecode's semantics correspond to the declared `source` text or `source_digest`.

`aptos move verify-package` (`aptos-move/cli/src/commands.rs:2098-2140`) is the tool users/auditors rely on to confirm "the on-chain copy matches" a trusted local source tree. It:
1. Rebuilds the package locally, extracting `compiled_metadata`.
2. Fetches the on-chain `PackageRegistry` via `CachedPackageRegistry::create(client, self.account, false)` — note `with_bytecode = false` (`aptos-move/cli/src/stored_package.rs:42-67`), so no module bytecode is downloaded at all.
3. Calls `package.verify(&compiled_metadata)` (`aptos-move/cli/src/stored_package.rs:193-241`), which only field-by-field compares the two `PackageMetadata` structs (name, deps, `modules` [name+source text], manifest, upgrade_policy, extension, source_digest).

Because `modules[].source` is publisher-supplied display text and is never checked against the real bytecode by the Move VM at publish time, a publisher can submit metadata whose `source`/`source_digest` matches an innocuous, publicly reviewable source tree while simultaneously submitting a `code` bundle compiled from different, malicious source. `verify-package` will report success ("Successfully verified source of package") because it only compares the two metadata objects, never the actual bytecode bytes that will execute.

### Impact Explanation
This directly matches the "Publish Pivots" invariant: *"Package metadata... must describe the code that is actually verified and stored"* and the impact category *"Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes."* Any downstream trust decision built on `aptos move verify-package` (self-custody wallets, governance approving an upgrade, an integrator vetting a dependency before allow-listing it) can be misled into believing the deployed bytecode matches an audited/trusted source when it does not, since the tool's success output gives no bytecode-level guarantee at all.

### Likelihood Explanation
No privileged capability is required — any account/object owner who can publish a package can trivially submit metadata with an innocuous `source`/`source_digest` alongside an unrelated `code` bundle; the framework's `validate_publish_request` only checks module-name registration, not source-to-bytecode correspondence. This is fully unprivileged and always exploitable for any package whose owner chooses to lie, i.e., wherever a package publisher is not already fully trusted (the exact scenario `verify-package` exists to protect against).

### Recommendation
- Have `verify-package` default to fetching and diffing actual on-chain bytecode (`with_bytecode = true`) against freshly compiled module bytes, not just metadata objects, and fail loudly if bytecode differs from what the declared source would produce.
- Consider binding `PackageMetadata` to the bytecode cryptographically (e.g., a bytecode-hash field checked natively at publish time against the bundle) so metadata cannot diverge from committed bytes.
- At minimum, clearly document (and ideally warn at runtime) that `verify-package`'s default mode only validates metadata/source-text equality, not bytecode equality, so integrators do not treat a "Successfully verified" result as a bytecode-level guarantee.

### Proof of Concept
1. Attacker writes `evil.move` containing malicious logic and compiles it to `evil.mv`.
2. Attacker also prepares an innocuous `good.move` source tree that a victim would trust.
3. Attacker calls `code::publish_package_txn` (or `aptos move publish` with custom payload construction) supplying `metadata_serialized` built from `good.move`'s `PackageMetadata` (correct `source`, `source_digest`, module name matching) but supplying `code = [evil.mv bytecode]` under the same module name.
4. The VM's `validate_publish_request` only checks that the module name in `evil.mv` matches an `expected_modules` entry from the metadata (`aptos-move/aptos-vm/src/aptos_vm.rs:1816-1822`) — it succeeds because names match.
5. A victim later runs `aptos move verify-package --account <attacker>` against a local checkout of `good.move`. `VerifyPackage::execute` fetches metadata only (`with_bytecode=false`) and calls `package.verify(&compiled_metadata)`, which compares `good.move`'s rebuilt metadata against the on-chain metadata (also derived from `good.move`'s source text) — the comparison passes and the CLI prints "Successfully verified source of package", even though the module actually executing on-chain is `evil.mv`.             bytecode_version: fix_bytecode_version(

            ..self.included_artifacts.build_options(&self.move_options)?

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")
