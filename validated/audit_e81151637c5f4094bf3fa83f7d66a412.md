### Title
Attacker-controlled transaction metadata is applied to unrelated Bitcoin deposits, enabling refund or instruction hijacking - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
`Bitcoin::get_outputs` accumulates matching outputs across every transaction in a block, but applies the currently iterated transaction’s presumed origin and embedded Serai data to the entire accumulated list. An attacker can place an ordinary transaction after a victim’s deposit in the same block and cause the victim’s output to inherit the attacker’s origin and instruction payload. If the attacker supplies an invalid payload and their own inferred origin, the victim’s deposit is scheduled as a refund to the attacker; alternatively, a valid attacker-controlled instruction can consume the victim’s deposited balance.

### Finding Description
`get_outputs` initializes `outputs` once before iterating over all non-coinbase transactions. [1](#0-0) 

For each transaction, newly scanned outputs are appended to this shared `outputs` vector. [2](#0-1) 

The subsequent enrichment check only tests whether the accumulated vector is non-empty, not whether the current transaction produced an output. [3](#0-2) 

The presumed origin is then derived from `tx.input[0]` of the currently iterated transaction, even if that transaction did not create the output being annotated. [4](#0-3) 

Finally, `extract_serai_data(tx)` and the current transaction’s `presumed_origin` are assigned to every accumulated output, including outputs created by earlier transactions. [5](#0-4) 

When an `External` output is later processed, its data is decoded as a `RefundableInInstruction`; if decoding or conversion fails, the presumed origin is retained as the refund destination. [6](#0-5) 

That retained origin is converted into a `PlanFromScanning::Refund`. [7](#0-6) 

The resulting plan spends the victim’s output to the supplied `refund_to` address. [8](#0-7) 

### Impact Explanation
An attacker can redirect the economic effect of a victim’s Bitcoin deposit without access to validator functionality, private keys, RPC internals, or malformed consensus objects. With an invalid Serai payload, the attacker can make the victim’s deposit look refundable to the attacker’s address, causing the multisig to sign a transaction transferring the victim’s funds to the attacker. [5](#0-4) [9](#0-8) 

With a valid attacker-selected payload, the attacker can instead attach an instruction of their choosing to the victim-funded balance because the output’s data field is overwritten wholesale. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
The attacker only needs to broadcast a transaction that confirms after the victim’s deposit within the same Bitcoin block. The attack does not require the attacker’s transaction to pay Serai or create a scanner-recognized output; it merely needs to appear after a transaction that did. Bitcoin transaction ordering is not controlled by users, but attackers can exploit naturally observed deposits, fee competition, miner transaction selection, or delayed inclusion to obtain the required ordering.

### Recommendation
Track and annotate outputs on a per-transaction basis. The origin and `extract_serai_data(tx)` result must only be applied to outputs returned by `scanner.scan_transaction(tx)` for that same transaction. Concretely, store the scan results in a per-transaction vector and skip enrichment when that vector is empty rather than testing the block-level accumulator. Alternatively, populate `presumed_origin` and `data` when constructing each output, before pushing it into the block-level result.

### Proof of Concept
Consider a block containing:

1. `tx_victim`, which pays at least `Bitcoin::DUST` to the multisig’s external P2TR address and embeds a legitimate instruction.
2. `tx_attacker`, ordered after `tx_victim`, which spends an attacker-controlled input whose previous output resolves to the attacker’s address and contains an OP_RETURN payload that intentionally fails `Shorthand` decoding or `RefundableInInstruction` conversion.

Processing proceeds as follows:

```rust
// tx_victim:
outputs.push(victim_output);

// tx_attacker produces no scanner outputs, but outputs is still non-empty.
let presumed_origin = Address::new(attacker_prevout.script_pubkey);
let data = Self::extract_serai_data(tx_attacker);

for output in &mut outputs {
  if output.kind == OutputType::External {
    output.data.clone_from(&data); // victim's legitimate data replaced
  }
  output.presumed_origin.clone_from(&presumed_origin); // now attacker
}
```

The victim output is therefore reported with attacker-controlled `data` and `presumed_origin`. Because the replacement data fails to decode into a valid refundable instruction, `instruction_from_output` returns the attacker-controlled origin with no instruction. The caller then creates `PlanFromScanning::Refund(victim_output, attacker_address)`, which schedules the victim’s UTXO as a payment to the attacker. [11](#0-10) [7](#0-6)
