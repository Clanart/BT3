### Title
Zero-value / dust outputs sent to a Serai address are reported as received yet can never be spent - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The Kairos bug class is "a code path that only works for nonzero amounts, so a 0-amount case silently locks value". In Serai's Bitcoin wallet, `Scanner::scan_transaction` registers *any* transaction output whose `script_pubkey` matches a registered key/offset as a `ReceivedOutput`, without checking the output's value. An attacker can send a 0-value (or sub-dust) output to Serai's P2TR address; it is scanned and tracked as funds received, but it is economically unspendable — spending it costs a nonzero input weight while contributing 0 sats, and the network layer's `DUST` floor (`Bitcoin::DUST = 10_000`, in `processor/src/networks/bitcoin.rs`) is only applied to *outgoing* payments/change, never to scanned inputs.

### Finding Description
`scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` hits (networks/bitcoin/src/wallet/mod.rs:199-213). There is no `output.value` check — no rejection of `Amount::ZERO` and no rejection of values below `DUST`/cost-to-spend. `ReceivedOutput::read` (lines 122-134) likewise accepts any decoded `TxOut` regardless of value, so even serialized outputs fed to readers preserve the zero-value case.

The downstream spend path (`SignableTransaction::new`, networks/bitcoin/src/wallet/send.rs:150+) treats every provided `ReceivedOutput` as an input and enforces `DUST` only on `payments` and `change`, not on inputs. A 0-value input makes the transaction valid but strictly worse: it adds ~57 vbytes of weight per input with zero contribution, inflating the fee; when the change computation (`input_sat.checked_sub(payment_sat + fee_with_change)`, lines 228-234) can no longer fund change, the leftover simply becomes extra fee — value is burned rather than recovered. Meanwhile the processor records the scanned output as a received balance even though it can never be economically consolidated, exactly the "funds reported received that are not spendable" shape of the zero-amount bug.

### Impact Explanation
An unprivileged party can send 0-value (or 1-sat) P2TR outputs to any Serai branch/change/main address. These are permanently tracked as received outputs, yet spending them always destroys value. At the accounting layer they count toward `inputs` balances while contributing nothing, leading to inflated `NotEnoughFunds` pressure and fees paid to spend worthless UTXOs — funds effectively stuck in the contract/wallet, mirroring the NFT-stuck impact of the original report.

### Likelihood Explanation
Sending a dust/zero-value output to a known address is cheap and permissionless; Serai's addresses (group key, per-`register_offset` keys for branches/change) are fixed and publicly derivable from the chain. No collusion or privileged access is needed — only a public Bitcoin transaction, which the rules explicitly allow.

### Recommendation
In `Scanner::scan_transaction` (or at the `get_outputs` boundary in the processor), reject outputs whose `value` is below the spend threshold — e.g., `if output.value < DUST-ish minimum { continue }` — before constructing a `ReceivedOutput`. Alternatively keep a separate "unspendable receipt" class so zero-value outputs don't enter the input-selection / balance accounting path.

### Proof of Concept
```rust
// Any party builds a tx paying 0 sats to Serai's own p2tr script
let tx = Transaction {
  // ... one arbitrary input owned by the attacker
  output: vec![TxOut {
    value: Amount::ZERO,                       // 0-value output
    script_pubkey: p2tr_script_buf(group_key).unwrap(), // Serai's script
  }],
  ..Default::default()
};

// networks/bitcoin/src/wallet/mod.rs:199-213 — matched by script_pubkey alone
let outputs = scanner.scan_transaction(&tx);
assert_eq!(outputs.len(), 1);       // reported as received
assert_eq!(outputs[0].value(), 0);  // yet contributes nothing

// SignableTransaction::new happily accepts it as an input, adding weight
// (and thus fee) while contributing 0 sats — never economically spendable.
```
