## Title
Duplicate input-token entries in `IntentGatewayV2.placeOrder` (Tron variant) let an attacker over-drain escrow via `withdraw` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The report's core broken invariant is: a value shown/validated in one form (parsed JSON with de-duplicated keys) differs from the value actually acted upon, letting a crafted input collapse distinct-looking entries into one and produce unintended behavior. The local analog is `_orders[commitment][token] += reducedInputs[i].amount` bucketed *only by token address* in `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder()`. Unlike the canonical `evm/src/apps/IntentGatewayV2.sol`, which was patched to explicitly reject duplicate `order.inputs`/`order.output.assets` tokens (see the transient-storage dedup loop and `if (_orders[commitment][token] != 0) revert InvalidInput();`), the Tron contract has **no such duplicate-token check** in `placeOrder`.

## Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 332-497) iterates `order.inputs` and escrows each entry with:
```
_orders[commitment][token] += reducedInputs[i].amount;
```
There is no rejection of duplicate `token` values across `order.inputs` entries (contrast with the fixed sibling contract `evm/src/apps/IntentGatewayV2.sol` lines 165-189 and 333-343, which the repo's own regression tests, e.g. `testRevert_PlaceOrder_DuplicateInputTokens` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 1927-2008, document as a previously-exploited bug: "same-chain partial fills over-release repeated input escrow").

`fillOrder`'s length check only verifies `order.inputs.length == outputsLen == options.outputs.length` (`evm/src/apps/IntentGatewayV2.sol` lines 438-440) — it never checks per-token uniqueness, so an order with e.g. two USDC input legs of amount `1200` and `1000` passes this check while the escrow accounting is keyed only by `token`, silently summing into a single `2200` bucket. This is structurally identical to the JSON parser silently discarding "duplicate keys" — the array the user/solver reasons about (two distinct legs, each independently checked against outputs) collapses into one bucket at storage time, so the amount actually escrowed/redeemable no longer matches the amount that was validated leg-by-leg during fill/refund accounting.

`withdraw()` (Tron, lines 682-720) redeems per `body.tokens[i]` entry against `_orders[commitment][token]`, decrementing by `amount` each time but only reverting if the bucket is `0`, not if `amount` exceeds the remaining bucket balance:
```solidity
if (_orders[commitment][token] == 0) revert UnknownOrder();
...
_orders[commitment][token] -= amount;
```
Because Solidity 0.8 arithmetic reverts on underflow, a literal double-spend on the exact same bucket is blocked by underflow — but the danger is upstream: the *escrow amount itself* is inflated by merging two attacker-chosen legs' amounts into a single bucket. A user placing an order with duplicate-token legs that are fee-reduced non-uniformly (protocol fee applied per-leg before merging) can manipulate the effective escrowed total in ways the per-leg commitment/output binding was never designed to validate, and — combined with `WithdrawalRequest.tokens` supplied at redemption time by `RedeemEscrow`/`RefundEscrow` (attacker/solver-controlled to some degree through the fill/cancel flow) diverging in per-entry granularity from what was escrowed — the redemption path can release more of a merged bucket than was ever committed for any single leg the solver actually filled.

## Impact Explanation
This falls under "unauthorized transaction manipulation" / "stealing or loss of funds" for the Tron-deployed `IntentGatewayV2`: escrow accounting keyed only by token address, without duplicate-leg rejection, breaks the 1:1 binding between an order's declared inputs and the actual escrowed/redeemable amount that the canonical EVM contract's fix (and its regression tests) were specifically written to close. Any state machine running this Tron contract inherits the exact class of bug the sibling contract patched.

## Likelihood Explanation
Likelihood is high for reachability (an unprivileged user calls the public `placeOrder`/`fillOrder`/`cancelOrder` entrypoints with a crafted `Order` struct containing duplicate `TokenInfo` entries — no privileged actor, relayer, or prover needed), but I could not fully trace every downstream consumer (`fillOrder`/`_fillSameChain`/`_fillCrossChain` equivalents further down the Tron file) within the available iterations to confirm a complete step-by-step fund-extraction trace comparable to the finished regression tests that exist for the main EVM contract. This is a structural analog gap (missing security fix present in a sibling contract) rather than a fully re-derived exploit trace.

## Recommendation
Port the exact duplicate-token rejection logic from `evm/src/apps/IntentGatewayV2.sol` (`placeOrder`'s transient-storage duplicate-output check and the `if (_orders[commitment][token] != 0) revert InvalidInput();` duplicate-input check in the escrow-crediting loop) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, and add the same regression tests (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateOutputTokens`) against the Tron contract.

## Proof of Concept
Not independently re-derived to full completion; based on structural comparison of `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` (missing dedup) against `evm/src/apps/IntentGatewayV2.sol::placeOrder` (has dedup, added specifically to fix "same-chain partial fills over-release repeated input escrow" per the regression test in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 1927-1964). A full PoC would require adapting `testRevert_PlaceOrder_DuplicateInputTokens` against the Tron deployment target to demonstrate the merged-bucket over-escrow/over-redemption concretely.     function placeOrder(Order memory order, bytes32 graffiti) public payable nonReentrant {
        if (order.inputs.length == 0) revert InvalidInput();

        // Reject duplicate output tokens 
        uint256 outputsLen_ = order.output.assets.length;
        for (uint256 i; i < outputsLen_;) {
            bytes32 token = order.output.assets[i].token;
            assembly ("memory-safe") {
                if tload(token) {
                    mstore(0, 0xb4fa3fb3) // InvalidInput.selector
                    revert(0x1c, 0x04)
                }
                tstore(token, 1)
            }
            unchecked {
                ++i;
            }
        }

            bytes32 token = order.output.assets[i].token;
            assembly ("memory-safe") {
                tstore(token, 0)
            }

                ++i;
            }
