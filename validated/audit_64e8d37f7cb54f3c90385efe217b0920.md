## Analog Identified: Undefined-behavior double→float narrowing conversion in upb's JSON decoder

### Title
Undefined-behavior float truncation on out-of-range double in `jsondec_double` (ProtoJSON parsing) - `upb/json/decode.c`

### Summary
The CVE describes libtiff invoking undefined behavior by converting a value that is "outside the range of representable values of type float" — i.e., narrowing a floating-point value to `float` when the source magnitude exceeds `FLT_MAX`, which C/C++ (C17 §6.3.1.5, C++ `[conv.double]`) define as UB rather than "saturate to infinity." The protobuf codebase has the exact same invariant violation in the upb ProtoJSON decoder's numeric-field handler.

### Finding Description
`jsondec_double()` parses a JSON number or numeric string into a `double` (`val.double_val`), then, for fields declared as `float`, performs an implicit narrowing conversion *before* validating the value is in range:

```c
if (upb_FieldDef_CType(f) == kUpb_CType_Float) {
  float f = val.double_val;   // <-- conversion happens here, unconditionally
  if (val.double_val != INFINITY && val.double_val != -INFINITY) {
    if (f == INFINITY || f == -INFINITY) jsondec_err(d, "Float out of range");
  }
  val.float_val = f;
}
``` [1](#0-0) 

The check `if (f == INFINITY || f == -INFINITY)` only runs *after* `float f = val.double_val;` has already executed. When `val.double_val` is a finite value larger in magnitude than `FLT_MAX` (e.g. `1e300`), the conversion itself is undefined behavior per the C standard — the "out of range detection" strategy assumes IEEE saturate-to-infinity semantics, but the language does not guarantee this. The double is fully attacker-controlled: it comes directly from `jsondec_number(d)` (a bare JSON number token) or from `strtod()` on a quoted JSON string, both parsed straight from the untrusted JSON payload. [2](#0-1) 

This exact vendored copy of the upb decoder is duplicated verbatim in the PHP and Ruby native extensions, both reachable from their respective public `JsonDecode`/`decode` APIs: [3](#0-2) [4](#0-3) 

Contrast this with the hardened equivalents elsewhere in the tree, which correctly test the double's magnitude *before* narrowing:
- C++ upb-based JSON parser (`ParseFp`) checks `std::isfinite(n) && !std::isfinite(static_cast<float>(n))` only to *detect* the condition, but still performs the same speculative narrowing cast to check — however this is in `float` context of `static_cast` in C++, whose behavior for double→float overflow is likewise formally UB, though this file explicitly comments on it as an accepted risk elsewhere in the codebase (`src/google/protobuf/json/internal/parser.cc:302-311`).
- The dedicated helper `SafeDoubleToFloat()` in `src/google/protobuf/io/strtod.cc` was written specifically to avoid this UB by clamping *before* casting: [5](#0-4) 
- Java's `JsonFormat.parseFloat()` explicitly range-checks against `Float.MAX_VALUE` before casting. [6](#0-5) 
- C#'s `ParseSingleNumberValue` checks `float.IsInfinity(converted) && !double.IsInfinity(value)` after cast but C# defines float overflow-to-infinity behavior, so it is not UB there (unlike C/C++). [7](#0-6) 

The upb `jsondec_double` implementation never adopted the `SafeDoubleToFloat`-style pre-check, leaving the UB pattern in the C code used by PHP, Ruby, and (transitively) other upb-based language bindings.

### Impact Explanation
The out-of-range narrowing conversion is undefined behavior in the strict sense: while common compilers/platforms (IEEE-754, x86/ARM with typical codegen) will saturate to `±INFINITY` in practice — matching the CVE's own characterization of the libtiff bug ("might allow ... denial of service ... or possibly have unspecified other impact") — the standard does not guarantee this, and UBSan/hardened builds will flag it as a defect. This is reachable purely from parsing an untrusted, bounded ProtoJSON payload against a trusted `.proto` schema containing a `float` field, with no privileged access or hostile schema required.

### Likelihood Explanation
High likelihood of triggering the UB: any ProtoJSON message with a `float`-typed field where the attacker supplies a JSON number (or numeric string) whose magnitude exceeds `FLT_MAX` (~3.4e38), e.g. `{"my_float_field": 1e300}`, exercises this code path directly through the public `upb_JsonDecode` entry point used by PHP's `GPBUtil::decode`/`Message::mergeFromJsonString` and Ruby's `Message.decode_json`.

### Recommendation
In `upb/json/decode.c` (and the corresponding generated copies in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`), replace the unconditional `float f = val.double_val;` narrowing with an explicit range check performed on the `double` value *before* narrowing (mirroring `SafeDoubleToFloat` in `src/google/protobuf/io/strtod.cc`), e.g. compare `val.double_val` against `FLT_MAX`/`-FLT_MAX` first and only cast when in range, saturating manually to `±INFINITY` for out-of-range finite inputs.

### Proof of Concept
Given a trusted schema with `float my_float_field = 1;`, decode the following ProtoJSON via the public `upb_JsonDecode` API (or PHP/Ruby `decode_json`):
```json
{"myFloatField": 1e300}
```
Trace: `jsondec_double` hits `JD_NUMBER` → `val.double_val = jsondec_number(d)` = `1e300` → `upb_FieldDef_CType(f) == kUpb_CType_Float` branch executes `float f = val.double_val;`, narrowing `1e300` (double) to `float`, which is outside the representable range of `float` — an undefined-behavior conversion, exactly analogous to the CVE-2017-7596 class of "outside the range of representable values of type float" UB. Compiling and running this path under `-fsanitize=undefined` should report the violation at `upb/json/decode.c:811` (and equivalently at `php-upb.c:5742` / `ruby-upb.c:4495`).

static upb_MessageValue jsondec_double(jsondec* d, const upb_FieldDef* f) {
  upb_StringView str;
  upb_MessageValue val;

  switch (jsondec_peek(d)) {
    case JD_NUMBER:
      val.double_val = jsondec_number(d);
      break;
    case JD_STRING:
      str = jsondec_string(d);
      if (str.size == 0) {
        jsondec_checkempty(d, str, f);
        val.double_val = 0.0;
      } else if (jsondec_streql(str, "NaN")) {
        val.double_val = NAN;
      } else if (jsondec_streql(str, "Infinity")) {
        val.double_val = INFINITY;
      } else if (jsondec_streql(str, "-Infinity")) {
        val.double_val = -INFINITY;
      } else {
        char* end;
        val.double_val = strtod(str.data, &end);

              upb_FieldDef_FullName(f));
        }
      }
      break;
    default:
      jsondec_err(d, "Expected number or string");
  }

float SafeDoubleToFloat(double value) {
  // static_cast<float> on a number larger than float can result in illegal
  // instruction error, so we need to manually convert it to infinity or max.
  if (value > std::numeric_limits<float>::max()) {
    // Max float value is about 3.4028234664E38 when represented as a double.
    // However, when printing float as text, it will be rounded as
    // 3.4028235e+38. If we parse the value of 3.4028235e+38 from text and
    // compare it to 3.4028234664E38, we may think that it is larger, but
    // actually, any number between these two numbers could only be represented
    // as the same max float number in float, so we should treat them the same
    // as max float.
    if (value <= MAX_FLOAT_AS_DOUBLE_ROUNDED) {
      return std::numeric_limits<float>::max();
    }
    return std::numeric_limits<float>::infinity();
  } else if (value < -std::numeric_limits<float>::max()) {
    if (value >= -MAX_FLOAT_AS_DOUBLE_ROUNDED) {
      return -std::numeric_limits<float>::max();
    }
    return -std::numeric_limits<float>::infinity();
  } else {
    return static_cast<float>(value);
  }
}
