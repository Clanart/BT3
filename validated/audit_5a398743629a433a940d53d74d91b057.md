### Title
Output delivery to beneficiary is not verified against the actual amount received before escrow is released to the solver, enabling silent underpayment with fee-on-transfer/deflationary output tokens - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The core broken invariant in the referenced Particle report is: a value assumed to satisfy an obligation (`liquidityAdded`) is never checked against what was actually required (`lien.liquidity`) before the debt is considered settled. Hyperbridge's `IntentGatewayV2` cross-chain and same-chain fill paths contain the same class of bug: the amount a solver is *instructed* to send (`totalRequired`/`beneficiaryTotal`) is used to authorize full escrow release and to mark the order `Filled`, but the contract never checks the beneficiary's actual received balance delta. The input side of the same protocol explicitly guards against this (see the fee-on-transfer escrow test), proving the missing check on the output side is an inconsistency, not an intentional design choice.

### Finding Description
In `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171`), the solver-provided output is delivered with:
```solidity
IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
``` [1](#0-0) 

There is no balance-before/balance-after check on `beneficiary` to confirm it actually received `totalRequired + beneficiaryShare`. Immediately afterward, the function unconditionally dispatches a `RedeemEscrow` message that will release the *full* escrowed input tokens to the solver on the source chain: [2](#0-1) 

The same pattern exists on the same-chain path in `IntrinsicIntents._fillSameChain`, where `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` is used to compute `isFullyFilled` and to release proportional escrow via `_withdraw`, again without confirming the beneficiary's received balance: [3](#0-2) 

By contrast, the escrow-side (input) accounting for `placeOrder` explicitly measures actual received tokens to defend against fee-on-transfer tokens — proven by the test asserting `Escrow should equal actual received amount`: [4](#0-3) 

No equivalent check exists for the output leg. If `order.output.assets[i].token` is a fee-on-transfer/rebasing/deflationary token (a legitimate, non-malicious ERC20 property, not an attacker-introduced condition), the beneficiary receives strictly less than `totalRequired`, yet:
- the order is marked `Filled` (cross-chain) or `isFullyFilled = true` (same-chain), and
- the solver still receives the *entire* escrowed input amount via `RedeemEscrow`/`_withdraw`.

### Impact Explanation
This is a direct "loss of funds" / "wrong beneficiary amount" bug matching the bounty's accepted impact classes: the escrowed input tokens (belonging to the order's user) move to the solver in full while the user's promised output is short-delivered, with no recovery path — the order is already finalized (`_filled[commitment]` set) and cannot be re-filled or refunded. This mirrors the LP-never-made-whole outcome described in the seed report, except here the victim is the order's beneficiary rather than an LP.

### Likelihood Explanation
The condition triggers deterministically whenever the output token has non-standard transfer semantics (a known, real-world token category — e.g. historical USDT fee-mode, PAXG, and various rebasing tokens). No relayer/prover/governance compromise is required; it is triggered purely by normal solver execution of `fillOrder`/`fillOrder` on an order whose output asset happens to apply a transfer fee, and the contract's own test-suite shows the developers are already aware of and specifically test for this exact token behavior on the input side but not on the output side — indicating a genuine, provable code gap rather than a purely theoretical one.

### Recommendation
Before finalizing the fill (marking `_filled`, computing `isFullyFilled`, or dispatching `RedeemEscrow`), measure `IERC20(token).balanceOf(beneficiary)` before and after the transfer and use the actual delta to determine whether the required amount was satisfied; revert (or treat as a partial fill) if the delta is less than `totalRequired`. Apply the same before/after balance check pattern already used for `placeOrder`'s fee-on-transfer handling symmetrically to the output/fill path in both `ExtrinsicIntents._fillCrossChain` and `IntrinsicIntents._fillSameChain`.

### Proof of Concept
1. Order creator places a cross-chain order with `order.output.assets[0].token` set to a fee-on-transfer ERC20 (e.g., 1% fee) and `amount = 1000e18`, escrowing `1000 USDC` as input.
2. A solver calls `fillOrder` on the destination chain with `options.outputs[0].amount = 1000e18` (satisfies `solverAmount >= totalRequired`).
3. `safeTransferFrom(msg.sender, beneficiary, 1000e18)` is executed, but due to the 1% fee, the beneficiary only receives `990e18`.
4. `_fillCrossChain` proceeds unconditionally: `_filled[commitment] = msg.sender`, and a `RedeemEscrow` message is dispatched.
5. On the source chain, `onAccept` → `_withdraw` releases the **full** `1000 USDC` escrow to the solver.
6. Net result: beneficiary received `990e18` instead of `1000e18`, solver received full `1000 USDC` input, and the order is permanently marked `Filled` with no recourse — token loss for the order's beneficiary that existing checks never catch.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
