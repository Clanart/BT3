### Title
OP_RETURN data output excluded from transaction weight/vsize calculation, causing fee underpayment and standardness-check bypass - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` computes the transaction's weight, vsize, and required fee from `payments` only, even though a zero-value `OP_RETURN` output carrying up to 80 bytes of attacker-supplied `data` is appended to `tx_outs` beforehand. The fee, minimum-relay-fee check, and `MAX_STANDARD_TX_WEIGHT` check therefore all ignore the real bytes the output adds to the signed transaction.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` at lines 194–202. However, weight/vbytes are computed at line 204 via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, and `calculate_weight_vbytes` (lines 62–94) builds its template transaction's `output` field solely from `payments` — the `data` output is never represented. The same omission occurs in the with-change recomputation at line 226. [1](#0-0) [2](#0-1) 

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) are computed on a vsize smaller than the real transaction's by ~11–92 vbytes (the serialized `TxOut` plus script). Since the change amount is `input_sat - payment_sat - fee_with_change` (line 228), the actual fee paid (`sum(inputs) - sum(outputs)`, line 139–141) equals this undercomputed value, so the real fee rate is strictly below the caller-requested `fee_per_vbyte`. [3](#0-2) 
2. The `TooLowFee` guard at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so a transaction can pass the check while its true fee rate falls below minimum relay fee and is rejected by peers' mempools. [4](#0-3) 
3. The `TooLargeTransaction` guard at line 241 checks the undercounted `weight`, so a transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` (by up to ~4×92 non-witness weight units ≈ 368 WU plus output overhead) is accepted as signable but is non-standard and will never relay. [5](#0-4) 

`data` is supplied by the caller of `SignableTransaction::new`, and the resulting transaction is what the threshold network signs via `TransactionMachine::sign` → `taproot_key_spend_signature_hash`. An unprivileged party who can cause the wallet to build/sign a transaction with a `data` payload reaches this path with public inputs only. [6](#0-5) 

### Impact Explanation
The signed transaction systematically pays a lower feerate than requested and can be non-standard (below min relay fee or over `MAX_STANDARD_TX_WEIGHT`), meaning Bitcoin nodes will refuse to relay or accept it. The threshold wallet thereby produces signed transactions that cannot be broadcast, freezing the committed inputs for that signing session and, at the boundary cases, producing a permanently unrelayable transaction — funds the protocol believes it spent/sent are not actually spendable on the network. This mirrors the Belt Finance class (an accounting/calculation error on the produced artifact) mapped onto Serai's Bitcoin wallet: the size/fee accounting of the signed object is wrong.

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data: Some(..)` triggers it; no collusion or privileged access is needed since `data` is an untrusted caller-supplied byte vector (checked only for length ≤ 80 at line 171). The bug is deterministic, not probabilistic. Impact is bounded: it causes fee underpayment / relay failure rather than theft, so Medium.

### Recommendation
Include the OP_RETURN output in the template transaction used by `calculate_weight_vbytes` — e.g., compute weight/vbytes from the fully assembled `tx_outs` (or pass the `data` length into the calculation) for both the no-change and with-change calls, so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check reflect the true serialized transaction.

### Proof of Concept
```rust
// Conceptual: inputs covering payments + "needed" fee, with an 80-byte OP_RETURN.
let data = vec![0u8; 80];
let st = SignableTransaction::new(
    inputs,                       // ReceivedOutputs summing to payment + needed_fee
    &payments,                    // e.g., one payment
    Some(change_script),
    Some(data),
    fee_per_vbyte,                // e.g., 1 sat/vB (min relay)
).unwrap();

// st.needed_fee() was computed on a vsize missing the ~91-vbyte OP_RETURN output.
// Real vsize of st.transaction() once witnessed ≈ assumed_vsize + ~91,
// so the real feerate is ~1 - 91/real_vsize sat/vB < 1 sat/vB:
// the transaction fails the min-relay-fee policy it "passed" at line 211,
// and peers will reject it despite the threshold network having signed it.
```
Steps: construct inputs whose sum equals `payment_sat + needed_fee` exactly (so no change ambiguity); observe `fee()` equals `needed_fee`, yet `transaction().vsize()` exceeds the `vbytes` used in the fee formula by the serialized OP_RETURN output size.
