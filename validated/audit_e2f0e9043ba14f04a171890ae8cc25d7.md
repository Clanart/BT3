### Title
Encrypted PedPoP shares are not bound to their intended recipient, allowing replay that frames an honest sender - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Like CVE-2019-5472 (an action authorized for one role/resource being accepted for another), `EncryptedMessage`'s proof-of-possession binds the ciphertext to the `from` participant but never to the intended recipient or the recipient's registered encryption key. An unprivileged party who observes a valid encrypted share `A -> B` can re-submit those exact bytes as `A -> C`. The message passes the per-message PoP check, fails to decrypt into a valid share, and causes honest participant `A` to be provably blamed.

### Finding Description
`encrypt` computes the ChaCha20 key via `ecdh(key, to)` where `to` is the recipient's registered encryption key (`self.decryption.enc_keys[&participant]`), but the PoP challenge `pop_challenge::<C>(context, pub_nonce, pub_key, from, msg)` only commits the sender index `from`, the ephemeral key, and the ciphertext — not the recipient index nor the recipient's `enc_key` (crypto/dkg/pedpop/src/encryption.rs:154-166, 466). [1](#0-0) [2](#0-1) 

On the receive path, `KeyMachine::calculate_share` drains a `HashMap<Participant, EncryptedMessage>` keyed only by claimed sender `l`; the queued PoP verification (`Encryption::decrypt`) checks the signature under `from = l` and then decrypts with the caller's own `enc_key` (encryption.rs:479-499, lib.rs:476-491). Since nothing in the verified data says "this ciphertext was for participant C", a replayed `A -> B` message verifies under `A`, decrypts under `C`'s key to garbage, and either fails `C::F::from_repr` or the share-verification multiexp. [3](#0-2) 

Blame then turns against the honest sender: `blame_internal` verifies the same recipient-agnostic PoP, uses the accuser-provided `EncryptionKeyProof` to decrypt, sees a non-canonical/invalid share, and returns `sender` as faulty (lib.rs:575-608). [4](#0-3) 

### Impact Explanation
A participant (or any party able to feed messages to the DKG transport) can take an authentic `A -> B` share off the wire and deliver it to `C` attributed to `A`. `C` aborts with `InvalidShare { participant: A }`, and the consensus-level blame check (`AdditionalBlameMachine::blame`) confirms `A` as the faulty party. In Serai this is a fatal slashing/blame condition — an honest validator is punished and the DKG/key-gen session aborts. It is a concrete integrity violation reachable purely from replayed public protocol bytes.

### Likelihood Explanation
Requires only the ability to observe and re-deliver DKG messages, which the protocol assumes (messages travel over authenticated-but-broadcast channels; `EncryptedMessage::read` accepts untrusted bytes). No key compromise, no collusion, no malicious-validator assumption — the replayed bytes are genuinely produced by the honest sender. Deterministic and reliable.

### Recommendation
Bind the recipient into the PoP: extend `pop_challenge` (crypto/dkg/pedpop/src/encryption.rs) to also append the intended recipient's `Participant` index and/or the recipient's registered `enc_key` (`self.decryption.enc_keys[&participant]`), and pass the expected recipient through `decrypt`/`decrypt_with_proof`. This makes an `A -> B` ciphertext unverifiable when presented as `A -> C`, so blame correctly falls on the relayer rather than the honest sender.

### Proof of Concept
1. Run PedPoP with n >= 3, i.e., participants A=1, B=2, C=3, all honest.
2. A runs `generate_secret_shares`; observe `shares[B]`, an `EncryptedMessage` whose `pop` signs `pop_challenge(context, R, key, from=A, ciphertext)` — recipient not committed.
3. Attacker delivers `shares[B]` to C as the entry for sender A in C's `shares` map (`calculate_share`).
4. C's batch PoP check for `from=A` passes (challenge has no recipient binding); decryption under `enc_key_C` yields garbage; `C::F::from_repr` fails or share verification fails → `PedPoPError::InvalidShare { participant: A, blame: Some(proof) }`.
5. Any party calls `BlameMachine::blame(sender=A, recipient=C, msg=shares[B], proof)`; `decrypt_with_proof` verifies the (recipient-agnostic) PoP, decrypts to garbage via C's revealed ECDH key, and returns `A` — the honest sender is adjudicated faulty.
