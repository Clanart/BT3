### Title
Hunk expansion desyncs diff line-selection indices, silently flipping deselected changes into a commit - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The reported Popcorn bug is a mismatch between two indices that are supposed to move together: shares are minted using one snapshot of `totalAssets`/`totalSupply`, then redeemed against a *different*, already-mutated snapshot, silently under-charging the fee. The same invariant-break class — "an index/offset computed against stale state is reused against shifted state" — exists in GitHub Desktop's diff hunk-expansion + line-selection code, where a positional index into `hunk.lines` is reused as a stable "line identity" across a mutation that inserts new lines before it.

### Finding Description
`DiffSelection` records which lines a user has (de)selected as a `Set<number>` of **absolute indices**, computed as `hunk.unifiedDiffStart + lineIndex` [1](#0-0) . These absolute indices are the sole "identity" used later by `formatPatch`/`formatPatchToDiscardChanges` to decide, line by line, whether to keep a `+`/`-` line in the generated patch [2](#0-1) .

When a user expands a hunk upward (clicking "Expand Up" on a diff whose content comes from an attacker-controlled cloned/fetched repository), `expandTextDiffHunk` inserts `numberOfLinesToAdd` new context lines **before** the hunk's existing lines while keeping `hunk.unifiedDiffStart` unchanged: [3](#0-2) 

Because `unifiedDiffStart` is not advanced and the new lines are spliced in at position 0 of `hunk.lines`, every pre-existing line's position within `hunk.lines` shifts down by `numberOfLinesToAdd`, so its absolute index (`unifiedDiffStart + lineIndex`) also shifts by `numberOfLinesToAdd`. The old absolute indices that were stored in the user's `DiffSelection.divergingLines` set are **not remapped** — nothing in `expandTextDiffHunk`, `expandWholeTextDiff`, or the call sites in `side-by-side-diff.tsx` recomputes or shifts the `divergingLines` set to match the new positions. The only post-expansion reconciliation found is `withSelectableLines`, which merely intersects the existing `divergingLines` set with a freshly computed `selectableLines` set and drops entries that are no longer selectable — it never shifts indices [4](#0-3) , [5](#0-4) .

Concretely: if a user deselects an added/deleted line at absolute index `X` (to exclude it from the commit) and then expands the same hunk upward by `N` lines, that line moves to absolute index `X+N`, while index `X` now belongs to one of the newly-inserted context lines. `divergingLines` still contains `X`. On the next `formatPatch` call, `file.selection.isSelected(absoluteIndex)` is evaluated per-line using the *new* `absoluteIndex` values, so:
- The line that is now at `X` (a context line) is unaffected (context lines are always included regardless of selection).
- The line the user actually deselected, now at `X+N`, is looked up as `isSelected(X+N)`, which no longer matches the diverging entry `X` — the line silently reverts to the *default* selection state instead of the user's explicit choice.

### Impact Explanation
This causes what the user visually unchecked (or checked) in the diff view to silently diverge from what actually gets committed or discarded via `git apply`/discard patches produced by `formatPatch` / `formatPatchToDiscardChanges` [6](#0-5) [7](#0-6) . An attacker who controls the content/shape of a repository's tracked files (via a crafted upstream commit that produces a diff with hunks large enough to require expansion) can engineer a working-directory diff where a victim who reviews and deselects specific lines before expanding the hunk unknowingly commits (or fails to discard) lines they explicitly excluded — i.e., silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitation requires only normal Desktop usage: opening a diff whose hunks are eligible for expansion (any hunk not already showing the full file, `DiffHunkExpansionType.Up/Down/Both`), partially selecting/deselecting lines, then expanding the hunk — a very common workflow when reviewing large diffs. No local access, admin rights, or unusual steps beyond normal diff review are needed; the only "unnatural" element is that the user must deselect a line before expanding, which is a plausible, unprompted-but-ordinary sequence during code review of a large file.

### Recommendation
When a hunk is expanded (or hunks are merged) in `expandTextDiffHunk`, remap `DiffSelection.divergingLines` alongside the hunks: build a translation from old absolute indices to new ones (shifting by `numberOfLinesToAdd` for all lines at or after the insertion point when expanding up, and doing the analogous shift for hunks below/after the expanded one) and apply it to the file's current `DiffSelection` before or as part of updating `selectableLines`, instead of only filtering by the new `selectableLines` set in `withSelectableLines`. Alternatively, key selection state off a stable line identity (e.g., original file line number) rather than a positional index that depends on hunk boundaries which change on expansion.

### Proof of Concept
1. Modify a tracked file such that `git diff` produces a single large hunk far from file boundaries (so it is eligible for `DiffHunkExpansionType.Both`/`Up`).
2. In Desktop's Changes view, open the diff and deselect one specific `+`/`-` line inside that hunk (this records its absolute index in `divergingLines` via `withLineSelection` / `withRangeSelection`, see `app/src/models/diff/diff-selection.ts:205-282`).
3. Click "Expand Up" on the hunk to reveal `DefaultDiffExpansionStep` (20) more context lines above it (`app/src/ui/diff/text-diff-expansion.ts:170-325`).
4. Commit only the selected lines via the "Commit" button, which invokes `formatPatch(file, diff)` (`app/src/lib/patch-formatter.ts:129`).
5. Inspect the resulting commit/patch: the line deselected in step 2 is included (or, depending on default selection type, the opposite divergence occurs) because `isSelected` is now evaluated against a shifted absolute index that no longer matches the stored `divergingLines` entry.

Note: I was not able to execute this end-to-end in a running Desktop instance from static analysis alone; the index-shift and lack of any remapping call are confirmed directly in the cited source, but the exact UI trigger path for "Expand Up" (button handler in `side-by-side-diff.tsx`) was only partially inspected before the tool budget ran out, so the precise call sequence from click to `expandTextDiffHunk`/state update should be verified in a live session.

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}
