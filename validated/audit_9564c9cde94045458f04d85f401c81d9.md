### Title
Partial-commit line selection is applied against a freshly re-fetched diff, allowing content that differs from what the user reviewed to be silently committed - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported Masset bug is a case of an internal accounting value (vault balance) being derived from an *assumed* quantity instead of the *actually confirmed* quantity from the external system (the lending pool), leaving a window where the two diverge and downstream operations act on stale data. The GitHub Desktop analog is the partial-commit ("stage selected lines") pipeline: a file's `DiffSelection` records *line indices* computed against a diff that was fetched at an earlier point in time (when the user reviewed and checked/unchecked lines in the UI), but `applyPatchToIndex` re-fetches a brand-new diff from the working directory at staging time and re-applies those old line indices to it without revalidating that the two diffs still match.

### Finding Description
`WorkingDirectoryFileChange.selection` (a `DiffSelection`) stores which lines a user wants included in a commit as absolute line indices (`hunk.unifiedDiffStart + lineIndex`) relative to a specific diff snapshot [1](#0-0) .

When the app actually stages a partially-selected file, `applyPatchToIndex` fetches a **new** diff directly from the working directory and immediately builds the patch from it using the stored selection, with no check that this diff is the same one the selection was computed against: [2](#0-1) 

`formatPatch` then walks the (new) diff's hunks and includes/excludes lines purely by `absoluteIndex`/`file.selection.isSelected(absoluteIndex)` [3](#0-2) . If the file's on-disk content (and therefore its diff/hunk layout) has changed between the moment the user made their line selection and the moment `stageFiles` → `applyPatchToIndex` runs, the same numeric line index can now point at a completely different line of a completely different meaning (e.g. an added secret line vs. a deleted line, or a line in a different hunk). Line index is treated as ground truth, but the value it depends on (the diff/hunk layout) is not re-validated before use, exactly mirroring the report's flaw of trusting an assumed quantity instead of confirming the current state of the external source.

The application is aware this exact class of staleness exists, but the mitigation is only applied to the *actively displayed single-file diff*, not to the staging path: `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` when the diff is reloaded for display and explicitly notes the diff "might have changed dramatically since last we loaded it" [4](#0-3) . This reconciliation happens on diff view refresh, not immediately before `_commitIncludedChanges` calls `createCommit`, and `createCommit`/`stageFiles`/`applyPatchToIndex` never re-check selection validity against the diff used to build the actual patch: [5](#0-4) [6](#0-5) .

### Impact Explanation
If the working tree content backing a file changes between the time the user selects specific lines for a partial commit and the time Desktop actually stages the file, the resulting commit can silently include lines the user never chose to include, or omit lines the user did choose — i.e. "silent corruption of what the user commits or pushes," which is explicitly listed as valid impact. Concrete ways an attacker-influenced repository can cause the working tree to be rewritten between diff-load and stage without further user action include repository-defined content filters (`.gitattributes` `clean`/`smudge`/`filter` drivers checked into a cloned/fetched malicious repository) that produce non-deterministic or state-dependent output on successive invocations, or Git LFS/other smudge filters re-materializing content differently on a second read. Because `applyPatchToIndex` unconditionally re-reads the diff via `getWorkingDirectoryDiff` at commit time [7](#0-6) , this second read is exactly the diff whose hunk layout the stale line indices are blindly applied to.

### Likelihood Explanation
This requires a repository (cloned or fetched, satisfying the "attacker controls a cloned/fetched repository" criterion) that ships a filter/attribute mechanism able to change file materialization between two git invocations, combined with normal user behavior (opening a file diff, selecting a subset of lines, then committing) — no unusual or unnatural steps are required beyond the standard "review diff, stage some lines, commit" workflow that Desktop explicitly supports. The precondition (diff changes between selection and staging) is narrower than a simple file edit race, so likelihood is moderate rather than trivial, but the code path has no defensive re-validation at all, so once the precondition is met the corruption is guaranteed and silent (no error, no warning to the user).

### Recommendation
Before building/applying the patch in `applyPatchToIndex`, compare the freshly fetched diff's structural fingerprint (e.g. hunk headers/line counts, or a hash of the diff content) against the diff the current `DiffSelection` was computed from, and abort/re-prompt the user (similar to the existing `selectableLines` reconciliation logic used for the display path) rather than silently applying stale line indices to new content. Alternatively, always regenerate the selection's `selectableLines`/diff immediately before staging (not just when the diff panel is visible), and fail the commit operation if selection cannot be unambiguously mapped onto the new diff.

### Proof of Concept
1. Clone a malicious repository containing a `.gitattributes` entry with a custom `clean`/`smudge` filter (or an LFS-like filter) that returns different content on successive checkouts/reads of a tracked file (e.g., embeds a counter or timestamp).
2. In Desktop, open the Changes view and view the diff for that file; the diff shown reflects the filter's first-read output. The user selects only a subset of lines to include (partial commit).
3. Before clicking "Commit", the filter's underlying state changes (e.g., due to a background git operation, a second checkout, or any git invocation that re-triggers the smudge filter) so that a subsequent `git diff` on the same file now has a different hunk layout/content, while the app has not reloaded/reconciled the selection for this file.
4. The user clicks "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now different) and builds the patch using the old line-index selection [2](#0-1) .
5. The resulting commit contains lines that do not correspond to what the user visually selected in step 2 — e.g., unintended content is committed/pushed, or intended content is silently dropped, with no error surfaced to the user.
