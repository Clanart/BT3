### Title
Unvalidated `filepath` parameter in deep-link `openRepo` handler enables path traversal outside the cloned repository - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` validates the `branch` and `pr` query-string parameters of an `openRepo` deep link with strict regexes, but the `filepath` parameter — documented as "the file to open after cloning the repository" — is returned completely unvalidated. This is the same bug class as the reported "improper parameter validation" in the `early-purchase` program: some fields got parameter validation while a sibling field with equally consequential downstream use was left unchecked.

### Finding Description
In `parseAppURL`, when the `openRepo` action is parsed, `pr` and `branch` are checked before being returned: [1](#0-0) 

`filepath`, however, is pulled straight from the query string with `getQueryStringValue(query, 'filepath')` and placed unmodified into the returned `IOpenRepositoryFromURLAction`, with no call to `testForInvalidChars` or any path-traversal/absolute-path check: [2](#0-1) 

The whole point of this deep-link handler is that `url` is attacker-controlled: it is triggered by an "Open in Desktop" link on a third-party or malicious web page (or a crafted `x-github-client://openRepo/...` / `github-mac://openRepo/...` / `github-windows://openRepo/...` URL), handled in the main process via `app.on('open-url', ...)` / `handleAppURL` and the Windows `--protocol-launcher` command-line path: [3](#0-2) [4](#0-3) 

Because `filepath` bypasses the same validation applied to `branch`/`pr` in the identical function, a value like `../../../../.ssh/id_rsa` or an absolute path is preserved verbatim through the deep-link → dispatcher pipeline. `IOpenRepositoryFromURLAction.filepath` is consumed later in `app/src/ui/dispatcher/dispatcher.ts` (multiple `filepath` references) to open a file after the repository is cloned/opened. Unlike `sanitizeCloneName`/`isClonePathSensitive` (used for the clone *destination* path) or `resolveWithin` (used elsewhere in the codebase to constrain path joins to a root), there is no equivalent containment check applied to `filepath` before it is joined against the repository's local path and handed to the OS to open — I was not able to fully trace the exact join/open call site in `dispatcher.ts` within the available tool budget, so the precise sink (e.g. `Path.join(repository.path, filepath)` passed to `shell.openExternal`/an editor invocation) should be confirmed directly in that file before remediation.

### Impact Explanation
If the downstream consumer joins `repository.path` with the unsanitized `filepath` (the documented purpose of the field) and opens the result, an attacker who gets a victim to click a single crafted "Open in Desktop" style link can cause Desktop to open an arbitrary file outside the newly cloned repository (e.g., SSH keys, `.netrc`, `.gitconfig`, or an executable), similar in spirit to the "off-chain implications of arbitrary ID/parameter values" and "uninitialized/no validation" issues in the original report. This falls into the valid-impact category of "a link or deep link the user clicks" leading to file read/exposure outside the repo boundary.

### Likelihood Explanation
Likelihood is moderate-to-uncertain: the vulnerable input path (attacker-controlled deep link → `parseAppURL` → unvalidated `filepath`) is confirmed and reachable with a single click, matching the codebase's own threat model (note the analogous protections already built for `branch`, `pr`, and clone paths). However, without confirming the exact `dispatcher.ts` sink that consumes `filepath`, it is not certain whether an additional sanitization step already exists downstream (e.g., a call to `resolveWithin`) that would neutralize traversal before use. This uncertainty should be resolved by inspecting the `filepath` consumption sites in `app/src/ui/dispatcher/dispatcher.ts`.

### Recommendation
Apply the same defense-in-depth pattern already used elsewhere in the codebase: validate `filepath` in `parseAppURL` (reject values containing `..`, absolute-path prefixes, or `testForInvalidChars`-style disallowed characters, mirroring the `branch` check), and additionally use `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` (already implemented in `app/src/lib/path.ts`) at the point where `filepath` is joined to the repository's local path, rejecting the request if the resolved path escapes the repository root.

### Proof of Concept
1. Host or send a link: `x-github-client://openRepo/https://github.com/octocat/Hello-World?branch=main&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim clicks the link; the OS invokes GitHub Desktop's registered protocol handler, triggering `app.on('open-url')` → `handleAppURL` in `app/src/main-process/main.ts`.
3. `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'https://github.com/octocat/Hello-World', branch: 'main', pr: null, filepath: '../../../../.ssh/id_rsa' }` — `filepath` passes through unchanged because no validation is applied to it (confirmed in `app/src/lib/parse-app-url.ts:98-125`), unlike `branch`.
4. Desktop clones/opens the repository and, per the field's documented purpose, attempts to open `filepath` relative to the repo — if the consuming code in `dispatcher.ts` does a raw `Path.join` without a `resolveWithin`-style containment check, the resolved path escapes the cloned repository directory.

**Confidence caveat:** I confirmed the missing validation at the parsing layer with certainty, but could not confirm within the available tool calls whether `dispatcher.ts`'s consumption of `filepath` already re-validates the path before opening it. This should be verified directly against `app/src/ui/dispatcher/dispatcher.ts` before treating this as a confirmed exploitable end-to-end vulnerability.

    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }
