## Title
Double settlement of GET requests via stale non-membership timeout proof after a valid response was already delivered - (File: `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol`)

### Summary
The External report's core broken invariant is: **a time-based liveness assumption (sequencer/clock advancing in lockstep with execution) is trusted without a fallback check, so when it breaks, the protocol executes a settlement path twice / at the wrong time, causing fund loss.** In Hyperbridge's EVM host, the equivalent broken invariant is that `dispatchIncoming(GetResponse)` never invalidates the `_requestCommitments` entry for a GET request, and `handleGetRequestTimeouts` only checks a **destination-chain non-membership proof at an arbitrary historical height**, not whether the request has already been answered on the *source* host. A relayer can deliver a valid `GetResponseMessage` (paying the fee and calling `onGetResponse`) and later also deliver a `GetTimeoutMessage` using an earlier destination state commitment that still shows "no response," triggering a second payout and a second app-level callback (`onGetTimeout`) for the same GET request.

### Finding Description
`EvmHost.dispatchIncoming(GetResponse, address)` handles a delivered GET response: [1](#0-0) 

Note it stores a `ResponseReceipt`, calls `onGetResponse`, and pays out `_requestCommitments[commitment].fee` to the relayer — but it never deletes `_requestCommitments[commitment]`.

`EvmHost.dispatchTimeOut(GetRequestTimeout, ...)` (used for GET timeouts) does the opposite bookkeeping: [2](#0-1) 

It deletes `_requestCommitments[commitment]` (this is the *only* place that clears it for GET requests) and pays `meta.fee` back to `meta.sender`, then calls `onGetTimeout` on the destination module.

`HandlerV2.handleGetRequestTimeouts` is the entrypoint that authorizes calling `dispatchTimeOut`: [3](#0-2) 

Its only checks are: challenge period elapsed, `request.timeout() > state.timestamp` (i.e., a *destination* state commitment whose timestamp is past the request's timeout), `meta.sender != address(0)` (i.e., `_requestCommitments` still populated — true even after a response was already delivered, because the response path never clears it), and a **non-membership proof of the response at the specific `message.height` supplied by the relayer** — not necessarily the latest known destination height.

`HandlerV2.handleGetResponses` explicitly documents that it does not check the request's own timeout, trusting the "liveness" of Hyperbridge's own timeout enforcement: [4](#0-3) 

Putting these together: nothing on the source EVM host cross-checks `_responseReceipts[commitment]` before allowing `dispatchTimeOut` to run, and nothing forces the timeout proof to use the *latest* destination height. A relayer (or even a legitimate, non-malicious actor racing two valid proofs) can:
1. Submit `handleGetResponses` with a valid response and membership proof at destination height `H2` (after `onGetResponse` executes and the fee is transferred).
2. Later submit `handleGetRequestTimeouts` with a non-membership proof against an **earlier** destination state commitment `H1 < H2` whose `state.timestamp` already exceeds `request.timeout()` but that predates the height at which the response was actually written into destination state — a state exactly analogous to a "sequencer down" gap between destination clock/timestamp advancement and its own execution/state commitment.
3. `handleGetRequestTimeouts` passes all checks (`meta.sender != 0` still true, non-membership proof at `H1` is genuinely valid), and `dispatchTimeOut` executes: pays `meta.fee` a second time and invokes `onGetTimeout` on the module that already received `onGetResponse` for the same commitment.

### Impact Explanation
This is a double-settlement / double-claim bug that produces:
- **Direct fund loss**: the fee token pool pays `fee` twice for a single GET request — once as relayer reward in `dispatchIncoming(GetResponse)`, once as sender refund in `dispatchTimeOut`.
- **Unauthorized double execution**: any `IApp` module that implements both `onGetResponse` and `onGetTimeout` for the same GET request (e.g., Intent Gateway–style withdraw/cancel flows) can have both callbacks fire for one logical request, risking duplicate refunds/withdrawals or inconsistent module state, matching the "replay/double-claim/double-settlement" and "false state acceptance" categories in the impact gate.

### Likelihood Explanation
No malicious peer, prover, or governance actor is required — an ordinary relayer holding a still-valid state commitment from before the response was written to destination state can trigger this at any time the two independent state proofs (response-membership at a later height, non-membership at an earlier one) coexist, which is a routine consequence of asynchronous state commitment updates rather than an attack on consensus. This is functionally the same broken invariant as the sequencer-uptime report: a liveness/ordering gap between "chain time advancing" and "chain state actually reflecting the event" is not defended against, so downstream settlement logic executes twice.

### Recommendation
- Have `dispatchIncoming(GetResponse, ...)` delete `_requestCommitments[commitment]` (mirroring the timeout path), so a request cannot be both answered and later timed out.
- In `handleGetRequestTimeouts`, additionally check `host.responseReceipts(commitment)` is empty before allowing the timeout dispatch, and/or require the non-membership proof height to be the chain's latest known committed height for the destination, not an arbitrary historical one.

### Proof of Concept
1. User's module dispatches a `GetRequest` with a non-zero `timeout_timestamp` and a relayer fee.
2. Destination computes the response; a relayer submits `handleGetResponses` with a valid membership proof at destination height `H2`. `dispatchIncoming(GetResponse,...)` runs: `onGetResponse` executes, `fee` is paid to the relayer, `_requestCommitments[commitment]` is left intact.
3. The same (or another) relayer submits `handleGetRequestTimeouts` referencing an earlier already-stored destination state commitment `H1 < H2` where `state.timestamp > request.timeout()` but the response was not yet written into destination storage at `H1`. All checks in `handleGetRequestTimeouts` pass (`meta.sender != 0`, valid non-membership proof at `H1`).
4. `dispatchTimeOut` executes: `onGetTimeout` fires on the module a second time and `meta.fee` is paid out again — a duplicate settlement for a single GET request commitment.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    /**
     * @dev Dispatch an incoming GET timeout to the source module.
     * @notice Does not refund any protocol fees.
     * @param timeout - timed-out get request bundled with the relayer that submitted the timeout proof
     * @param meta - fee metadata for the original request
     * @param commitment - request commitment
     */
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
