### Title
Cross-Module Signature Replay Between `withdraw_fees` and `accumulate_fees` Due to Identical Message Encoding and Shared Nonce - (File: modules/pallets/relayer/src/withdrawal.rs, modules/pallets/relayer/src/accumulate.rs)

### Summary
The relayer pallet signs two semantically different authorizations — "withdraw my accrued balance to beneficiary B" (`withdraw_fees`) and "redirect newly-accumulated delivery fees to beneficiary B" (`accumulate_fees`) — using message-hash functions that produce **byte-identical** digests for the same `(nonce, state_machine, beneficiary)` inputs, and both consume the **same shared `Nonce<T>` storage** keyed by `(address, state_machine)`. Because `Signature::verify` signs only the raw 32-byte hash with no domain separator, a signature a relayer creates to authorize one call is also valid on the other, unprivileged, publicly-submittable (`ensure_none`) entrypoint.

### Finding Description
`withdrawal.rs::message()` computes, when a beneficiary is present: [1](#0-0) 

`accumulate.rs::beneficiary_message()` computes: [2](#0-1) 

Both are `keccak256(&(nonce: u64, state_machine: StateMachine, beneficiary: Vec<u8>).encode())` — SCALE-encoding a `Vec<u8>` and a `&[u8]` slice produces the same bytes, so for identical `(nonce, state_machine, beneficiary)` values the two functions yield the exact same 32-byte digest.

Both call sites verify this digest with `Signature::verify`, which contains no call-specific or pallet-specific domain tag — it recovers/validates purely against the raw hash: [3](#0-2) 

Both flows also read/increment the *same* `Nonce<T>` storage map, keyed only by `(address, state_machine)`, with no separate namespace for "withdrawal nonce" vs "beneficiary-redirect nonce": [4](#0-3) 

- `withdraw_fees` (unsigned, `ensure_none`) reads the nonce for the *signer* recovered from `withdrawal_data.signature`, builds `message(nonce, dest_chain, beneficiary)`, and validates it: [5](#0-4) 

- `accumulate_fees` (also unsigned, `ensure_none`) reads the nonce for `delivery_address` (the relayer address recovered from the *proven* destination receipt, not the caller), builds `beneficiary_message(nonce, state_machine, &beneficiary_address)`, and validates it — anyone can submit this call with any `(beneficiary_address, signature)` pair as long as a valid proof for undelivered commitments is supplied: [6](#0-5) 

Because `withdraw_fees` and `accumulate_fees` are both permissionless (`ensure_none(origin)`), an attacker who observes a relayer's signature for one call — e.g. from the public unsigned-transaction pool (`propagate: true` in `validate_unsigned`) or from any off-chain/API preview — can resubmit it through the *other* entrypoint before the relayer's original nonce is consumed: [7](#0-6) 

This breaks the stated invariant that "each withdrawal or payee redirection signature must be single-use and bound to the exact destination chain and beneficiary": nothing in the signed payload identifies *which pallet call* the signature authorizes, so the same signature is valid for two structurally different economic operations (spending an already-accrued balance vs. redirecting the beneficiary of freshly-proven fee accumulation). The attacker can:
1. Front-run a relayer's `withdraw_fees(nonce=N, dest_chain=C, beneficiary=B)` signature by feeding the identical `(N, C, B)`-derived signature into `accumulate_fees` as `beneficiary_details`, together with an attacker-supplied but validly-proven `WithdrawalProof` for the relayer's other unclaimed commitments on chain `C`.
2. This redirects that batch's accrued fee credit to `B` and consumes the shared nonce, invalidating and griefing the relayer's original, differently-intended `withdraw_fees` submission (its signature check will fail because the nonce read at execution time has already advanced).
3. More generally, the lack of a domain separator means the pallet cannot guarantee a signature's use is bound to the specific call/context it was authorized for — a core precondition of the reviewed invariant — even though the direct beneficiary value in this particular replay is not attacker-substitutable (it is fixed by the replayed signature itself).

### Impact Explanation
This is a genuine authorization-boundary defect: a signature meant to authorize action A validly authorizes structurally different action B without the signer's consent, and lets an unprivileged third party force consumption/redirection of a relayer's proven fee-accumulation entry and/or grief a pending withdrawal by nonce exhaustion. It does not, by itself, let an attacker redirect funds to an address of the attacker's own choosing (the beneficiary is fixed inside the replayed signature), so it falls short of "wrongful mint/unlock/withdrawal to an attacker-chosen address," but it does violate the single-use, context-bound signature invariant and enables unauthorized cross-call execution/fund redirection of relayer-owned fee balances.

### Likelihood Explanation
Requires an attacker to observe a relayer's signed `(nonce, dest_chain, beneficiary)` payload before its nonce is consumed (via the public unsigned tx-pool, an off-chain API, or logs) and to have (or forge via a valid state proof) a `WithdrawalProof` for the same relayer's undelivered commitments on the same chain. Both are plausible given `propagate: true` unsigned gossip and the permissionless nature of `accumulate_fees`.

### Recommendation
Add an explicit domain-separation tag (e.g., a distinct byte prefix or enum discriminant such as `b"WITHDRAW"` vs `b"BENEFICIARY"`) to the signed payload in both `message()` and `beneficiary_message()`, and/or split `Nonce<T>` into separate storage maps per call purpose so a signature/nonce pair produced for one entrypoint can never be structurally valid for the other.

### Proof of Concept
1. Relayer R has funds accrued in `Fees::<T>` on chain `C` and unclaimed commitments delivered on `C`.
2. R signs `message(N, C, B) = keccak256((N, C, B).encode())` intending to call `withdraw_fees` to send its current balance to beneficiary `B`; this unsigned extrinsic enters the public tx pool per `validate_unsigned`'s `propagate: true`. [7](#0-6) 
3. Attacker observes the pending extrinsic, extracts `withdrawal_data.signature`, and constructs a `WithdrawalProof` (with valid `source_proof`/`dest_proof`) for R's other unclaimed commitments on `C`, setting `beneficiary_details = (B, R's signature)`.
4. Attacker submits `accumulate_fees` before R's `withdraw_fees` lands. Since `Nonce::<T>::get(R, C)` is still `N`, `beneficiary_message(N, C, B)` equals `message(N, C, B)` byte-for-byte, so `signature.verify(&msg, ...)` succeeds in `accumulate()`, redirecting the newly-proven fee batch to `B` and incrementing the shared nonce to `N+1`. [8](#0-7) 
5. R's original `withdraw_fees(N, C, B)` then executes with `Nonce::<T>::get(R,C) == N+1`, recomputes `message(N+1, C, B)`, fails signature verification against R's stale signature, and reverts — demonstrating the signature/nonce from one call context was consumed by the other, unintended context.

	pub fn verify(
		&self,
		msg: &[u8; 32],
		public_key_op: Option<Vec<u8>>,
	) -> Result<Vec<u8>, anyhow::Error> {
		match self {
			Signature::Evm { signature, .. } => {
				if signature.len() != 65 {
					Err(anyhow!("Invalid Signature"))?
				}

				let mut sig = [0u8; 65];
				sig.copy_from_slice(&signature);
				let pub_key = sp_io::crypto::secp256k1_ecdsa_recover(&sig, msg)
					.map_err(|_| anyhow!("Signature Verification failed"))?;
				let signer = sp_io::hashing::keccak_256(&pub_key[..])[12..].to_vec();
				Ok(signer)
			},
			Signature::Sr25519 { signature, public_key } => {
				Self::verify_sr25519(signature, public_key, msg, &public_key_op)?;
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
			Signature::Ed25519 { signature, public_key, .. } => {
				let signature =
					signature.as_slice().try_into().map_err(|_| anyhow!("Invalid Signature"))?;
				let pub_key = public_key_op
					.clone()
					.unwrap_or(public_key.clone())
					.as_slice()
					.try_into()
					.map_err(|_| anyhow!("Invalid Public Key"))?;
				if !sp_io::crypto::ed25519_verify(&signature, msg, &pub_key) {
					Err(anyhow!("Signature Verification failed"))?
				}
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
		}
	}
