### Title
Unauthorized claim-on-behalf via `multiclaimFor()` sends MGP/rewards to arbitrary address, risking permanent freeze of funds - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.multiclaimFor()` lets any unprivileged wallet trigger a reward claim on behalf of an arbitrary `_account`, with both the claimant identity and the token receiver set to that same `_account`. There is no check that `msg.sender == _account` or any `tx.origin`-style validation. This mirrors the reported `ERC20Rewarder.claim()` bug class: if `_account` is a contract that is not designed to receive unsolicited ERC20 transfers (e.g., a pool helper, integrator, or any contract lacking rescue logic), tokens pushed to it by a third party can become permanently stuck.

### Finding Description
`multiclaimFor` is defined as: [1](#0-0) 

It forwards to the internal `_multiClaim(_stakingTokens, _account, _account, _rewardTokens)`, using the caller-supplied `_account` as both `_user` (whose accrued rewards are debited) and `_receiver` (destination of the transferred tokens): [2](#0-1) 

Inside `_multiClaim`, MGP rewards are sent via `_sendMGP`/`_sendVlMGPFor`/`_sendMGPForVlMGPPool` and other reward tokens via `_claimBaseRewarder`, which ultimately calls into `BaseRewardPool.getReward(_account, _receiver)` (and the V2/mWOMSV variants), transferring tokens directly to `_receiver`: [3](#0-2) [4](#0-3) 

None of these functions verify that the caller is authorized to act on behalf of `_account`; the only access control present (`onlyMasterMagpie`) restricts who can call the reward-pool-level `getReward`, not who can invoke `multiclaimFor` at the `MasterMagpie` entry point. Compare this with the legitimate delegated-claim path, `multiclaimOnBehalf`, which is explicitly gated to a trusted compounder role and sends funds to `msg.sender` (the compounder), not to `_account`: [5](#0-4) 

`multiclaimFor`, by contrast, is unauthenticated and sends the payout to the target account itself — exactly the unauthorized "claim-on-behalf" pattern described in the report.

### Impact Explanation
Any ordinary wallet can call `multiclaimFor(_stakingTokens, _rewardTokens, victimContract)` for any address, including smart contracts that integrate with the Magpie protocol (e.g., pool helpers, vaults, or other periphery contracts) but that do not implement arbitrary-token rescue functions. Because the reward transfer is pushed unconditionally to `_receiver = _account`, MGP and other reward tokens can be forced into a contract that has no way to move them back out, permanently freezing those funds. This satisfies the "permanent freezing of unclaimed yield/funds" impact bar.

### Likelihood Explanation
The function is `external`, has no `onlyMasterMagpie`/role restriction, and needs no special permissions or pre-conditions — any address with pending rewards accrued for a contract account (e.g., any contract that ever staked/interacted with `MasterMagpie` pools on behalf of itself) can be targeted at any time. This makes the likelihood high whenever any non-EOA contract has an unclaimed reward balance in the system.

### Recommendation
Restrict `multiclaimFor` so the reward-claim destination cannot be forced onto an arbitrary third-party address without that party's consent: either remove the unauthenticated variant entirely, require `msg.sender == _account`, or send the harvested reward to `msg.sender` while crediting `_account`'s books (as `multiclaimOnBehalf` already does for the trusted compounder flow), and additionally gate any "claim for others" path behind an explicit allowance/approval mechanism from `_account`.

### Proof of Concept
1. Wallet `Eve` (or any address) calls `MasterMagpie.multiclaimFor(stakingTokens, rewardTokens, victimContract)`, where `victimContract` is a contract integrated with `MasterMagpie` (e.g., a pool helper or vault) that has accrued MGP/reward-token balances but has no logic to forward or rescue unexpectedly received ERC20 tokens.
2. `_multiClaim` executes with `_user = _receiver = victimContract`; `_sendMGP`/`_sendVlMGPFor`/`_claimBaseRewarder` transfer the accrued MGP and bonus reward tokens directly to `victimContract`.
3. Because `victimContract` was never designed to receive or move out these tokens, the funds are locked in `victimContract` indefinitely — a permanent freeze triggered entirely by an unprivileged third party, with no action required from `victimContract`'s owner/operator.

```text
    function _multiClaim(address[] calldata _stakingTokens, address _user, address _receiver, address[][] memory _rewardTokens) internal nonReentrant {
        uint256 length = _stakingTokens.length;
        if (length != _rewardTokens.length) revert LengthMismatch();

        uint256 vlMGPPoolAmount;
        uint256 mWOmPoolAmount;
        uint256 defaultPoolAmount;

        for (uint256 i = 0; i < length; ++i) {
            address _stakingToken = _stakingTokens[i];
            UserInfo storage user = userInfo[_stakingToken][_user];
            
            updatePool(_stakingToken);
            uint256 claimableMgp = _calNewMGP(_stakingToken, _user) + unClaimedMgp[_stakingToken][_user];

            if (_stakingToken == address(vlmgp)) {
                vlMGPPoolAmount += claimableMgp;
            } else if (MPGRewardPool[_stakingToken]) {
                mWOmPoolAmount += claimableMgp;
            } else {
                defaultPoolAmount += claimableMgp;
            }

            unClaimedMgp[_stakingToken][_user] = 0;
            user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
            _claimBaseRewarder(_stakingToken, _user, _receiver, _rewardTokens[i]);
        }

        if (vlMGPPoolAmount > 0) {
            _sendMGPForVlMGPPool(_user, _receiver, vlMGPPoolAmount);
        }

        if (mWOmPoolAmount > 0) {
            _sendMGP(_user, _receiver, mWOmPoolAmount);
        }

        if (defaultPoolAmount > 0) {
            _sendVlMGPFor(_user, _receiver, defaultPoolAmount);
        }

        uint256 totalReward = vlMGPPoolAmount + mWOmPoolAmount + defaultPoolAmount;

        if (totalReward > 0 && referral != address(0)) {
            IReferralStorage(referral).trigger(_user, totalReward);
        }
    }
```
