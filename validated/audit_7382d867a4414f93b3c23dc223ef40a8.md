## Title
Webhook `shop_domain` (from `X-Shopify-Shop-Domain` header) is not covered by HMAC verification, allowing cross-shop webhook forgery — ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates a webhook request purely by validating the HMAC over the raw request body, but the shop identity used to route/process that webhook (`shop_domain`, read from the `X-Shopify-Shop-Domain` header) is never included in the HMAC computation. This mirrors the audited `QuickAccManager` bug: a cryptographic check validates one piece of data (the signature/HMAC over the body), while a separate, unauthenticated identity field (`id` in the Solidity report, `shop_domain` header here) is blindly trusted for authorization/context.

### Finding Description
`hmac_valid?` in [1](#0-0)  computes the HMAC exclusively over `request.raw_post` (the body). `WebhookVerification#verify_request` gates the request solely on this check: [2](#0-1) . The module also exposes `shop_domain`, sourced from the `X-Shopify-Shop-Domain` header, which is **not** part of the HMAC-signed data: [3](#0-2) .

The gem's own documentation instructs developers to use this unauthenticated `shop_domain` value directly for authorization/business logic: [4](#0-3) . The generated job template goes further, using the header-derived `shop_domain` to look up a `Shop` record and open an authenticated Shopify API session for that shop, then processes the webhook body inside it: [5](#0-4) .

Because the app's webhook HMAC secret (`ShopifyApp.configuration.secret`) is a single shared per-app secret used for every shop's webhooks — not a per-shop secret — any merchant who has installed the app receives real, validly-signed webhook deliveries for their own shop. Since the header is excluded from the signed data, that merchant can:
1. Capture a legitimate webhook delivered to their app endpoint for their own shop (valid HMAC over the body they control, e.g. by triggering a `products/update` on their own store with attacker-chosen content).
2. Replay the exact same body/HMAC pair but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `hmac_valid?` still passes (body unchanged), so `verify_request` accepts the request.
4. Downstream code (per the documented pattern) resolves `shop_domain` to the victim shop, loads the victim's Shopify session, and processes attacker-controlled payload data in the victim's shop context.

This is structurally identical to the `QuickAccManager` bug: the signature (HMAC) authenticates data integrity but not the identity binding, and the identity field used for privilege/context resolution is attacker-controlled and unchecked against the signed payload.

### Impact Explanation
An attacker (any merchant that has installed the app) can forge webhook events that get processed under a different, victim shop's authenticated session/context, using payload content the attacker fully controls. Depending on what the app's webhook job does (e.g., create/update records, trigger Admin API mutations keyed by the payload), this enables cross-shop data injection or state changes using another merchant's access token — a cross-shop access violation triggered by an accepted forged/replayed signed request.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate (if unrelated) app-installing merchant able to receive at least one real webhook and replay it with a modified header — no secret leakage or privileged access is needed, and this is precisely the pattern the project's own documentation and generators recommend implementing.

### Recommendation
Bind the shop identity to the signed payload rather than trusting the header:
- Compute/validate the HMAC over the header plus body (or otherwise cryptographically bind `shop_domain` into the signed data), or
- Always derive the shop from the verified webhook body/topic metadata provided by the `shopify_api` gem's registry dispatch rather than the raw, unauthenticated header, and cross-check it against any shop-specific state before use, or
- Document/require verifying that the resolved `shop_domain` matches an expected value (e.g., topic-specific webhook resource ownership) before using it to load a session.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g., updates a product) causing Shopify to POST a legitimately HMAC-signed webhook to the app's webhook endpoint, with body `B` and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request, keeping body `B` and its valid `X-Shopify-Hmac-Sha256` header unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` still returns true since only the body is hashed: [1](#0-0) .
5. The app's job (following the documented pattern) calls `Shop.find_by(shopify_domain: "victim-shop.myshopify.com")` and processes attacker-controlled body `B` under `victim-shop`'s authenticated session: [6](#0-5) .

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
