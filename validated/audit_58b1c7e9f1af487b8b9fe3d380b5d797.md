### Title
Hidden bidi-character warning suppressed for large/long-line diffs, allowing silent commit of Trojan-Source content - (File: app/src/ui/diff/index.tsx)

### Summary
GitHub Desktop detects invisible bidirectional Unicode characters (`Trojan Source`-style attacks) in diffs and shows a `DiffContentsWarning` banner to alert the user before they stage/commit a file. However, when a diff is classified as `DiffType.LargeText` (triggered by a hardcoded `MaxCharactersPerLine = 5000` threshold or overall size threshold with no user-facing override), the app renders a collapsed placeholder (`renderLargeTextDiff`) instead of the actual diff view, and the `DiffContentsWarning`/bidi-detection banner is never shown unless the user manually clicks "Show Diff".

### Finding Description
`isDiffTooLarge` in `app/src/lib/git/diff.ts` flags any diff containing a line longer than the hardcoded `MaxCharactersPerLine` (5000 characters) as `DiffType.LargeText`: [1](#0-0) 

The `DiffParser` computes `hasHiddenBidiChars` for every diff, including `LargeText` diffs, and this flag is faithfully propagated: [2](#0-1) 

But in the UI, `Diff.render()` only calls `renderLargeText` (which builds an `ITextDiff` and renders `SideBySideDiff`, the component that shows `DiffContentsWarning`) when `this.state.forceShowLargeDiff` is `true`. By default it renders `renderLargeTextDiff()`, a placeholder panel with a "Show Diff" button and no mention of the bidi-character warning: [3](#0-2) [4](#0-3) 

Meanwhile, staging/committing is entirely decoupled from whether the diff was ever visually rendered: `applyPatchToIndex` accepts both `DiffType.Text` and `DiffType.LargeText` diffs for partial-commit patch generation, and full-file staging (`git add`) doesn't even look at the diff view at all: [5](#0-4) [6](#0-5) 

So the "broken invariant" is: the presence of one line longer than 5000 characters anywhere in the file's diff (attacker-controlled, e.g., a minified/very long line appended to an otherwise normal source file in a fetched/cloned repository) silently disables the bidi-warning UI, while the underlying `git add`/commit path is completely unaffected by this display state. A user pulling a branch containing such a file, seeing "the diff is too large to be displayed," will commonly just accept default `DiffSelectionType.All` staging and commit/push without ever seeing the Trojan-Source warning that exists specifically to prevent this class of attack.

### Impact Explanation
This defeats the purpose of the existing `hasHiddenBidiChars` mitigation (added to counter Trojan-Source-style attacks) for any file containing a single sufficiently long line. An attacker who controls a repository/branch a victim will fetch and review in Desktop can smuggle bidi-reordering characters that change the *displayed* meaning of code without triggering Desktop's warning, and the victim ends up committing/pushing code whose actual byte content silently differs from what a warned-off reviewer would have caught. This matches the "silent corruption of what the user commits or pushes" impact category, since the safety mechanism that exists precisely to prevent unnoticed semantic corruption is bypassed by attacker-supplied content shape (long line length), not by any local/privileged action.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: crafting a file/diff with one line over 5000 characters (e.g., a minified asset, generated code, or a single long comment line) is trivial for an attacker who controls the repository content, and it requires no unusual interaction from the victim beyond the completely normal workflow of pulling a branch and clicking "Commit". The victim doesn't need to explicitly avoid clicking "Show Diff" — most users treat the "diff too large" placeholder as informational and proceed to commit without expanding it, which is the default/expected behavior the app is designed around (`forceShowLargeDiff` defaults to `false`).

### Recommendation
Decouple the bidi-character security warning from the "diff too large to render" performance gate. Specifically:
- Surface `diff.hasHiddenBidiChars` (already computed and available on `ILargeTextDiff`) in `renderLargeTextDiff()`/`renderUnrenderableDiff()` in `app/src/ui/diff/index.tsx`, even when the full side-by-side diff is not rendered.
- Consider blocking or requiring explicit confirmation before staging/committing a file whose diff has `hasHiddenBidiChars === true`, regardless of whether it was classified as `Text`, `LargeText`, or `Unrenderable`.

### Proof of Concept
1. Attacker prepares a branch/repo with a file containing one very long line (>5000 characters, e.g. a long minified line) plus a change elsewhere in the same file that includes bidi-override characters (e.g. `U+202E`) altering the visual order of a security-relevant statement (classic Trojan Source pattern).
2. Victim clones/fetches the branch in GitHub Desktop and opens the Changes view for that file.
3. Because the diff contains a line exceeding `MaxCharactersPerLine` (5000), `isDiffTooLarge` returns `true`, and `Diff.render()` shows `renderLargeTextDiff()` — a placeholder with only a "Show Diff" button, not `SideBySideDiff`/`DiffContentsWarning`. [7](#0-6) 
4. The victim, without clicking "Show Diff", stages the file (default `DiffSelectionType.All`) and commits/pushes it via the normal commit flow, which uses `stageFiles`/`update-index` and is entirely independent of whether the diff was visually expanded. [8](#0-7) 
5. The commit is pushed containing the bidi-reordering characters, with the victim never having seen the "This diff contains bidirectional Unicode text..." warning that would normally have been shown for a shorter-line diff.

/** Is the diff too large for us to reasonably represent? */
function isDiffTooLarge(diff: IRawDiff) {
  for (const hunk of diff.hunks) {
    for (const line of hunk.lines) {
      if (line.text.length > MaxCharactersPerLine) {
        return true

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
