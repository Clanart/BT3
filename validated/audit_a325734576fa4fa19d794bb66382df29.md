### Title
`ReceivedOutput::read` deserializes `offset`, `TxOut`, and `OutPoint` with no binding between them, letting untrusted bytes register funds under a key/context that does not actually hold them - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The bug class in the external report is *attributing value to a context that doesn't hold it*: yield generated on chain B was credited to the treasury on chain A, so chain A's books claim spendable funds that aren't backed there. The Serai analog is `ReceivedOutput` deserialization. A `ReceivedOutput` is the protocol's claim "an outpoint paying value V to key `key + offset·G` exists and is spendable." `ReceivedOutput::read` accepts all three fields (`offset`, `output`, `outpoint`) independently from an untrusted byte stream and never checks that the `outpoint` exists, that the claimed `TxOut` matches the chain data at that outpoint, or — most importantly — that `output.script_pubkey` equals `p2tr_script_buf(scanner_key + offset·G)`.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) reads a `Scalar` offset via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns them as a coherent spendable output. There is no consistency check anywhere in the deserialization path: [1](#0-0) 

Compare with `scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`), the trusted source of `ReceivedOutput`s, which only emits an output after looking up `output.script_pubkey` in the scanner's `scripts` map and attaching the *correct* registered offset. The deserialization path has no equivalent binding, so bytes that were never produced by `scan_transaction` are accepted as equivalent.

The only downstream guard is `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`), which checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`. This catches a mismatched *offset/script* pair, but it does not verify the `outpoint` exists on chain or that the claimed `value` matches the real UTXO: [2](#0-1) 

### Impact Explanation
An unprivileged party supplying bytes to `ReceivedOutput::read` can fabricate an output: e.g., claim a large `TxOut.value` at an `outpoint` whose real value is dust or which doesn't exist, while keeping the `script_pubkey` consistent with a valid registered offset so `multisig` accepts it. Consequences:

- **Inflated accounting**: `SignableTransaction::new` computes `input_sat` purely from claimed `input.output.value` (`send.rs:175`), so fake value passes `NotEnoughFunds` and mints phantom spendable balance — the direct analog of crediting yield that isn't backed by collateral on that chain.
- **Signing of a transaction that can never confirm**: `taproot_key_spend_signature_hash` with `Prevouts::All` commits to the *claimed* prevout values (`send.rs:373-390`), producing a valid-looking signed transaction the network will reject, burning threshold-signing sessions and stalling withdrawals of the real inputs — the "DoSed withdrawals due to unbacked accounting" impact from the source report.

### Likelihood Explanation
Reachability requires only that attacker-controlled bytes reach `ReceivedOutput::read`, which is one of the explicitly in-scope untrusted sinks. The fabricated output passes `multisig`'s script check whenever the attacker uses a `script_pubkey` genuinely registered to the scanner key (publicly derivable via `p2tr_script_buf`), so the only requirement is a bogus `outpoint`/`value` pair. The attack fails closed only if every consumer re-verifies each output against the chain before use; nothing in the in-scope crate enforces that.

### Recommendation
Bind the `ReceivedOutput` invariant at the trust boundary:

1. Add a `ReceivedOutput::verify(&self, key: ProjectivePoint) -> bool` that checks `p2tr_script_buf(key + GENERATOR * self.offset) == Some(self.output.script_pubkey.clone())`, and require it after any `ReceivedOutput::read` on untrusted input.
2. Require consumers to resolve `outpoint` against the chain (or only accept outputs from `scan_transaction`) before counting `value` toward spendable balance in `SignableTransaction::new`.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read
let real_key: ProjectivePoint = /* scanner group key */;
let offset = Scalar::ZERO; // external output script

// script_pubkey consistent with key so `multisig` accepts it,
// but outpoint/value fabricated (outpoint is dust or nonexistent)
let fake = ReceivedOutput {
    offset,
    output: TxOut {
        value: Amount::from_sat(1_000_000_000), // claimed, not real
        script_pubkey: p2tr_script_buf(real_key).unwrap(),
    },
    outpoint: OutPoint { txid: attacker_txid, vout: 0 },
};

let mut buf = fake.serialize();
let decoded = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted, no checks

// Passes NotEnoughFunds on phantom 10 BTC
let stx = SignableTransaction::new(vec![decoded], &payments, change, None, fee).unwrap();
// Passes script_pubkey check -> produces a signed tx the network rejects
stx.multisig(&keys).unwrap();
```
