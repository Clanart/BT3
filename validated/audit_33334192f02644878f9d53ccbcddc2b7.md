### Title
Missing atomicity in `Verifier::sign_optimistic_payout` allows two concurrent requests for the same withdrawal UTXO to both collect N-of-N signatures - (File: `core/src/verifier.rs`)

### Summary
`Verifier::sign_optimistic_payout` gates signing solely on a live, non-atomic `is_utxo_spent` chain query and has no per-`deposit_id`/per-`input_outpoint` lock or DB reservation. Two concurrent `OptimisticPayoutSign` requests for the same withdrawal UTXO but different destination outputs can each pass the check before either transaction is broadcast/confirmed, letting each request independently complete a full MuSig2 N-of-N signing session.

### Finding Description
The binding claimed is: `number_of_vault_UTXOs_spent_for_withdrawal(i) == 1`. In `sign_optimistic_payout` (`core/src/verifier.rs:1570-1713`), the only guard against a double-spend attempt is: [1](#0-0) 

This is a check against the current Bitcoin/mempool state at call time, not a mutual-exclusion mechanism. There is no lock, session table, or DB uniqueness constraint keyed on `deposit_id`/`input_outpoint` inside this function or in `core/src/rpc/verifier.rs::optimistic_payout_sign` (`core/src/rpc/verifier.rs:72-142`) that would prevent a second, concurrent call for the same `deposit_id` from proceeding while the first call is still in flight. Each call to `Aggregator::optimistic_payout` (`core/src/rpc/aggregator.rs:1010-1230`) creates an independent nonce session via `create_nonce_streams`, so two racing aggregator calls produce two fully independent MuSig2 signing sessions on every verifier: [2](#0-1) 

The withdrawal UTXO (`input_outpoint`) is authenticated only by a `SIGHASH_SINGLE|ANYONECANPAY` Schnorr signature checked against the key embedded in that UTXO's own script: [3](#0-2) 

Per this repo's threat model, the attacker legitimately owns/creates this withdrawal UTXO and controls its key (they chose its bytes and call Citrea's `withdraw`), so they can produce two independently valid signatures over two different destination outputs for the same input. The only additional gate that ties a specific `output_script_pubkey`/`output_amount` to an externally-authorized value is the optional ECDSA `verification_signature` check: [4](#0-3) 

This check is skipped entirely whenever `aggregator_verification_address` is not configured (it is an `Option` in config), in which case nothing in `sign_optimistic_payout` or `optimistic_payout` binds the destination output to a single, previously-authorized value, and nothing serializes concurrent signing attempts for the same `deposit_id`. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`), which is the only place that records "a payout happened" for a withdrawal index, runs only after a payout tx is mined and finalized — well after N-of-N signatures for a competing spend could already have been produced.

### Impact Explanation
If two concurrently-signed optimistic payout transactions both reach full N-of-N signature, both are broadcastable spends of the single move-to-vault UTXO backing withdrawal index `i`. Whichever is not the one actually confirmed represents fully valid N-of-N partial signatures produced for an unauthorized/competing spend of the vault UTXO — matching the Critical category "N-of-N partial signatures for an unauthorised spend." This is repeatable per deposit/withdrawal whenever the race window (between the `is_utxo_spent` check and either transaction confirming) can be won by two requests, and does not depend on any operator or verifier misbehavior.

### Likelihood Explanation
Exploitability without any privileged key depends on the deployment leaving `aggregator_verification_address` unset, which is a valid, supported configuration in this codebase (the field is `Option<Address>` and the code path explicitly skips the ECDSA check when it is `None`). Under that configuration, the attacker only needs: to have made a legitimate Citrea withdrawal (control of the withdrawal UTXO key), the ability to produce two `SIGHASH_SINGLE|ANYONECANPAY` signatures over two different chosen outputs, and the ability to fire two concurrent gRPC requests to the aggregator before either resulting transaction confirms on Bitcoin — all attacker capabilities explicitly in scope. Cost is limited to normal Bitcoin fees for one legitimate deposit/withdrawal cycle. If `aggregator_verification_address` IS configured, the ECDSA gate binds the signed request to one specific destination chosen at Citrea's manual-verification step, which would block this specific unprivileged race (that mitigation depends on Citrea operational behavior, outside this repo).

### Recommendation
Add an atomic, application-level reservation for `(deposit_id, input_outpoint)` before performing MuSig2 signing in `sign_optimistic_payout` — e.g., a DB row with a unique constraint inserted (and committed) in the same logical step as the "is spent" check, or an in-memory per-deposit lock held for the duration of the sign+broadcast flow — so that only one in-flight optimistic payout signing session can exist per withdrawal at a time, independent of whether `aggregator_verification_address` is configured.

### Proof of Concept

```rust
// cargo test in core/src, single verifier instance, no live Bitcoin/Citrea required
// (mock only the is_utxo_spent RPC call to return false for both branches, matching
// a pre-confirmation race window)

#[tokio::test]
async fn test_concurrent_optimistic_payout_race() {
    // setup: single Verifier with a completed deposit `i`, aggregator_verification_address = None
    // create two valid taproot signatures sig_a, sig_b over the SAME withdrawal_utxo input
    // (SIGHASH_SINGLE|AnyoneCanPay) but two DIFFERENT output_script_pubkey/output_amount pairs

    let fut_a = verifier.sign_optimistic_payout(
        session_a, agg_nonce_a, deposit_id, sig_a, withdrawal_utxo, dest_a, amount_a, None,
    );
    let fut_b = verifier.sign_optimistic_payout(
        session_b, agg_nonce_b, deposit_id, sig_b, withdrawal_utxo, dest_b, amount_b, None,
    );

    let (res_a, res_b) = tokio::join!(fut_a, fut_b);

    // BINDING UNDER TEST: only one of the two spends of withdrawal_utxo's vault UTXO
    // should ever be signable.
    assert!(
        !(res_a.is_ok() && res_b.is_ok()),
        "both concurrent requests for the same deposit produced a partial signature: {res_a:?} {res_b:?}"
    );
}
```
The test should be run against the real `sign_optimistic_payout`/`is_utxo_spent` path (mocking only the Bitcoin RPC layer's spent-state query to simulate the pre-confirmation window), asserting the second request is rejected as soon as the first partial signature is produced — not merely once a transaction confirms on-chain.
