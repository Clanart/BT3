### Title
Stale cached preprocess reused to produce multiple shares for divergent signing sets/messages enables private share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Fractional bug allowed an object marked `committed` in a prior (failed) context to finalize under the state of a different context, because there was no binding between the "committed" object and the currently active proposal ID. Serai's tributary `SigningProtocol` has the same shape: a FROST preprocess is `commit`ted once and cached in `CachedPreprocesses` keyed **only** by `context` (e.g. `(b"DkgConfirmer", attempt)`), with no binding to the participant preprocess set or the message. Every subsequent `share_internal`/`complete` call deterministically regenerates the *same* nonces from that seed and signs whatever `(preprocesses, msg)` is supplied, so the same nonce can be spent across multiple distinct binding-factor sets.

### Finding Description
`SigningProtocol::preprocess_internal` stores a 32-byte RNG seed under `CachedPreprocesses[context]` the first time a signing context runs, then reloads it on every later call:

- coordinator/src/tributary/signing_protocol.rs:123-147 — if `CachedPreprocesses::get(txn, &context)` already exists, no new seed is generated; `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` is invoked with the same seed each time.
- crypto/frost/src/sign.rs:121-144 — `seeded_preprocess` feeds the seed into `ChaCha20Rng`, so `Commitments::new` regenerates *identical* nonces `d, e` and identical commitments for every reload.
- coordinator/src/tributary/signing_protocol.rs:150-180 — `share_internal` calls `preprocess_internal` (reusing the seed) and then `machine.sign(preprocesses, msg)`, where `preprocesses` and `msg` are supplied per-call and are not checked against any previously used values.
- crypto/frost/src/sign.rs:283-398 — `sign` computes each participant's binding factors `rho` from the *supplied* preprocesses (`B.calculate_binding_factors` over `rho_transcript` containing the `preprocesses` challenge and `hash_msg(msg)`), then emits `share = algorithm.sign_share(...)` with nonce `d + rho·e`.

`DkgConfirmer` exposes this to remote input: `share(preprocesses, key_pair)` (signing_protocol.rs:304-310) is invoked with `preprocesses` received from other validators' `Commitments` tributary messages, and `msg` is `set_keys_message(set, removed, key_pair)` (signing_protocol.rs:296-301). `DkgConfirmer::complete` (signing_protocol.rs:312-327) calls `share_internal` *again* with a freshly supplied `preprocesses` map. Nothing verifies that the preprocess set or `key_pair` used in `complete` matches what was used in `share`, nor that `share` is only called once per context — the design intends idempotent recovery after reboot, but achieves it by silently re-signing with the same nonce under whatever inputs are currently provided.

Concretely, for participant `i` with secret share `x_i` and cached nonces `d, e`:

`share = λ_i·x_i + d + rho(S, msg)·e`

Two invocations of `share()`/`share_internal` with different `preprocesses` sets `S_1 ≠ S_2` (or different `key_pair`, hence different `msg`) yield `rho_1 ≠ rho_2` while `d, e` are identical. Given two published shares `s_1, s_2`: `e = (s_1 − s_2)/(rho_1 − rho_2)`, then `d`, then `x_i = (s_1 − d − rho_1·e)/λ_i`. The coordinator/tributary protocol can reach this state whenever `share` is invoked more than once for a context whose inputs changed (e.g. `share()` returning `Err(InvalidParticipant)`/blame then being retried, reboot-then-reattempt flows the comments explicitly contemplate, or `complete` being fed a different set than `share`). The divergent set only requires a peer to publish a *different valid preprocess* in the second delivery — untrusted bytes reaching `read_preprocess` (sign.rs:276-281) — since the code never pins the cached nonce to the set/message first used.

### Impact Explanation
Reuse of a FROST nonce across two distinct signing sessions leaks the victim's private key share (documented in crypto/frost/src/sign.rs:85-87 and spec/cryptography/FROST.md:51-55). Since these shares are MuSig-combined shares of the tributary/validator-set key (`musig(musig_context(...))` at signing_protocol.rs:118-121), recovering them breaks the threshold assumption: an attacker accumulating recovered shares can forge signatures over `set_keys_message` and other tributary-signed payloads, effectively extracting the validator-set signing capability — the same "settle with a stale committed object" failure as the Fractional bug, realized as nonce reuse.

### Likelihood Explanation
The determinism is deliberate (reboot recovery), and the exposure window requires `share_internal` to run twice for one `context` with different accepted inputs. The code explicitly anticipates repeated invocation after reboot ("on reboot, we'll get told of active signing items, and may be in this branch again" in the sibling signers; `unwrap_or_else` rebuilds in key_gen.rs show the same pattern), and `commit`/`complete` round-tripping through `share_internal` twice per confirmation means a second `preprocesses` delivery is part of normal operation. A validator that supplies differing-but-valid preprocess bytes across the two rounds (or across a retry after a reported `InvalidParticipant`) induces divergent `rho` under a reused nonce. That makes this at least Medium/High under the report's own standards.

### Recommendation
Bind the cached preprocess to the exact session it serves. When generating `CachedPreprocesses[context]` in `preprocess_internal`, record the digest of the first `(sorted participant preprocesses, msg)` it is used to sign, and refuse `share_internal`/`complete` calls whose inputs do not match. Alternatively, key the cache by `(context, hash(preprocesses, msg))` and treat any second distinct key for the same `context` as a fatal protocol violation rather than re-signing. `DkgConfirmer::complete` should reuse the machine/share produced by `share` (which must be the same invocation's output) instead of regenerating a share from the cached seed.

### Proof of Concept
```rust
// Against SigningProtocol (conceptual, within the tributary flow):
// Attempt A: peer set P1 provides preprocesses S1 for context ("DkgConfirmer", k)
let share1 = confirmer.share(S1, key_pair)?;         // share1 = λx + d + ρ(S1,m)·e, broadcast

// Attempt B (retry/blame/reboot): a peer now provides S2 != S1 (e.g. one different
// preprocess commitment) for the SAME context and key_pair
let share2 = confirmer.share(S2, key_pair)?;         // share2 = λx + d + ρ(S2,m)·e, broadcast

// Anyone seeing both shares:
//   e = (share1 - share2) * (ρ(S1,m) - ρ(S2,m))^-1   (ρ is publicly computable from
//                                                     rho_transcript at sign.rs:361-371)
//   x = (share1 - d - ρ(S1,m)*e) / λ_i               -> validator's MuSig share recovered
```
The reuse is guaranteed because `from_cache` + `seeded_preprocess` (crypto/frost/src/sign.rs:121-144, 268-274) deterministically regenerate `d, e` from the seed stored in `CachedPreprocesses` (signing_protocol.rs:123-147), and neither `share_internal` nor `sign` records or enforces which preprocess set/message the seed was first bound to.
