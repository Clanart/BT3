### Title
Unhandled `StopIteration` crash when processing a malformed offer's coin ancestry - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_root_removal()` walks a coin's ancestry inside the coins bundled in an offer, looking for the "root" non-ephemeral removal. When given a coin whose ancestry chain does not terminate inside the bundle's own removal set (a condition an attacker fully controls when crafting an offer file), the internal `next()` generator call raises an uncaught `StopIteration`, crashing the code path that processes the offer instead of cleanly rejecting it.

### Finding Description
`get_root_removal()` walks parent links using `next()` over `all_removals` with no bound and no fallback for "no match found": [1](#0-0) 

The initial guard only checks that the *starting* coin's name or parent is present in `all_removal_ids`, not that every step of the ancestry actually resolves to a removal in the bundle: [2](#0-1) 

Because an `Offer` is built directly from an untrusted, attacker-supplied `SpendBundle` (the offer file), an attacker can construct a set of coin spends where one coin's `parent_coin_info` does not match the `.name()` of any other coin in `all_removals`, while still satisfying the initial-guard check (e.g. by making the *starting* coin itself present in `all_removal_ids`, but crafting the chain so a subsequent lookup misses). When `get_root_removal()` (invoked from `get_pending_amounts()`, which iterates every offered coin and calls `get_root_removal` on it) reaches that link, `next(c for c in all_removals if c.name() == coin.parent_coin_info)` finds no match and raises `StopIteration`, an exception type that is not a `ValueError`/`ValidationError` and is not caught anywhere in this call chain.

This differs from the OctoRPKI bug (an unbounded loop hitting a max-iteration limit and crashing) in the specific mechanism, but the bug class is the same: attacker-controlled graph/chain data drives a traversal routine into a state the code doesn't defensively handle, and the process halts with an unhandled exception instead of cleanly rejecting the malformed input.

### Impact Explanation
Any wallet code path that summarizes or displays pending amounts for a received/untrusted offer (offer counterparty reviewing an offer before deciding whether to take it) can hit this unhandled exception, halting that computation. This matches the "spend-triggered transaction-processing halt" acceptance criterion: an unprivileged, attacker-crafted offer bundle can deterministically cause a crash in offer-handling logic, a denial-of-service against the offer counterparty's node process for that call. It does not lead to any inflation, unauthorized coin movement, or bypass of consensus rules — the impact is limited to a crash/halt on the specific request, which corresponds to CWE-834/CWE-754 (uncontrolled iteration reaching an unhandled/exceptional error condition).

### Likelihood Explanation
Likelihood is limited by scope: I was not able to fully verify that `get_pending_amounts()`/`get_root_removal()` sit directly in the automatic path taken by the `get_offer_summary` RPC or `take_offer` RPC before a user consents — my search located references in `chia/wallet/trade_manager.py`, `chia/wallet/trade_record.py`, and `chia/wallet/wallet_rpc_api.py`, but I ran out of iterations before confirming the exact call sequence and whether earlier validation (e.g., `Offer.is_valid()`/bundle structural checks) would reject a broken ancestry chain before `get_root_removal()` is ever reached. If such upstream validation exists and rejects offers whose coin ancestries don't resolve within the bundle, this finding would be moot (the exception would already be replaced with a normal rejection earlier in the pipeline). This uncertainty should be resolved by tracing `Offer.__init__`/`Offer.is_valid()` and the exact RPC handlers that call `get_pending_amounts()`/`summary()`.

### Recommendation
- In `get_root_removal()`, replace the bare `next(...)` with a version that raises a caught, descriptive `ValueError` (or returns `None`) when no matching parent is found, and ensure all callers (including `get_pending_amounts()`) handle that outcome by rejecting the offer instead of propagating an unhandled exception.
- Add an explicit bound/cycle check when walking the ancestry (e.g., cap iterations at `len(all_removals)`) so a malformed or cyclic parent chain cannot cause unbounded work or an uncaught exception.
- Add a regression test that constructs an `Offer` whose coin_spends contain a coin with a `parent_coin_info` not matching any other removal's `name()`, and verify `get_pending_amounts()`/`summary()` fail gracefully rather than raising `StopIteration`.

```python
    # This returns the non-ephemeral removal that is an ancestor of the specified coin
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
