### Title
Deterministic FROST nonce reuse across repeated `share`/`preprocess` calls via persisted `CachedPreprocess` seed - (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
The Linux bug class is "an initializer can fail (or be re-run) silently, leaving an iterator holding stale/wild state that subsequent `next`/`exit` calls dereference." The Serai analog is `SigningProtocol::preprocess_internal` at `coordinator/src/tributary/signing_protocol.rs:100-148`: the FROST `AlgorithmSignMachine` is deterministically rebuilt from a DB-persisted `CachedPreprocess` seed keyed only by `context`, and that seed is never invalidated after the machine is consumed. Every call to `preprocess()`/`share()`/`complete()` for the same context (e.g., `DkgConfirmer`'s `(b"DkgConfirmer", attempt)` at lines 275-276) reconstructs identical nonces and emits an identical preprocess. A second `sign` invocation over the same nonces but a different included signer set yields a second valid FROST share, enabling algebraic recovery of the signer's secret key share.

### Finding Description
`preprocess_internal` computes an encryption key from `b"Cached Preprocess Encryption Key" || context || key`, then:

1. If `CachedPreprocesses::get(txn, &context)` is `None`, it creates a machine via `AlgorithmMachine::new(...).preprocess(&mut OsRng)` and stores `machine.cache()` XOR-masked into the DB (lines 123-134).
2. It then always reloads that seed and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` (lines 137-145), which routes to `AlgorithmMachine::seeded_preprocess` in `crypto/frost/src/sign.rs:121-144`, regenerating `nonces`/`commitments` via `ChaCha20Rng::from_seed(*seed.0)`.

Because the seed is keyed only on `context` and is never deleted or rotated after `sign()` consumes it, any re-execution of `share_internal`/`complete` for the same `(context)` rebuilds the same `nonces` vector and emits the same serialized preprocess. `DkgConfirmer::share` (lines 288-310) and `SubstrateSignData`/batch equivalents funnel through this path. `threshold_i_map_to_keys_and_musig_i_map` (lines 208-250) shows the `included` set is derived from whichever preprocess map is supplied for that attempt, so two Share rounds over the same attempt with different participant subsets are plausible — e.g., after a reboot re-fire (the codebase notes messages are "re-fired" on reboot, `coordinator/src/main.rs:117-118`) or a second `SubstrateSign{label: Share}` transaction with a different preprocess collection.

The FROST share is `s_i = d + e·rho_i + λ_i·secret·c` (`crypto/frost/src/sign.rs` sign path). Two shares emitted over the same `(d, e)` nonces with different `rho_i`/`c` (different included set ⇒ different binding factors and challenge) let any observer solve the linear system for `secret`. Both shares are published on the tributary, so the recoverer needs no special access.

### Impact Explanation
Recovery of the validator's secret key share. For `DkgConfirmer` the leaked secret is the validator's Ristretto key used as the MuSig private component; possession of it lets the attacker forge that validator's tributary `Signed` transactions (e.g., fake DKG commitments, fake sign data) until the set rotates. For contexts signing actual batches/plans, it leaks the FROST secret share of the network threshold key. This is direct key-share recovery, an accepted impact.

### Likelihood Explanation
No malicious validator or peer message is required: the trigger is the signer itself executing a second share round for a context whose seed was already consumed — a reboot/re-delivery between the share round and completion, or two Share transactions carrying different preprocess subsets for the same attempt. Both produce two on-chain shares over identical nonces, and the recovery math is simple linear algebra over publicly published data.

### Recommendation
Delete (or rotate) `CachedPreprocesses` for a context the first time `share_internal` produces a share — e.g., a `CachedPreprocesses::kill(txn, &context)` after successful `machine.sign(...)`, and make `preprocess_internal` fail loudly if asked to sign twice for one context. Alternatively, mix a monotonic attempt counter or the full included-set hash into the seed context so regenerated machines can never reproduce identical nonces for differing signing sessions.

### Proof of Concept
```rust
// Conceptual: same SigningProtocol context used twice with different signer sets.
// Round 1
let (_m1, share1) = protocol.share_internal(&participants, preprocesses_set_A, &msg)?;
// After reboot or a second Share tx with a different preprocess map:
let (_m2, share2) = protocol.share_internal(&participants, preprocesses_set_B, &msg)?;
// share1 and share2 commit to identical nonces (same CachedPreprocess seed),
// but different rho_i and challenge c. Solve:
//   share1 - share2 = e*(rho1 - rho2) + λ*secret*(c1 - c2) ... (d cancels partially;
//   with per-participant binding, subtracting the d,e-terms leaves a linear eq in `secret`).
```
Concretely: `CachedPreprocesses::get` at `signing_protocol.rs:137` is read again on every call; `from_cache` at `crypto/frost/src/sign.rs:268-274` → `seeded_preprocess` at lines 121-144 deterministically regenerates `nonces` from the persisted seed, and nothing in `share_internal` removes the DB entry, so nonce reuse is guaranteed on any re-invocation.
