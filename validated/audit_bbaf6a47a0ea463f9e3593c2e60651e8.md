This confirms the association model: `putOwner` keys owners by `endpoint + login` (a string) [1](#0-0) , and `upsertGitHubRepositoryFromMatch` keys GitHub repositories by `[ownerID+name]`, i.e., login string + repo name string, not any GitHub-issued immutable numeric repository ID [2](#0-1) . There is no cross-check against a previously stored immutable repo/owner ID before trusting a freshly fetched API repository as "the same" repository.

### Title
Silent remote-URL and GitHub-association hijack via owner/name repository re-matching, with no immutable-ID pinning - (File: app/src/lib/stores/app-store.ts, app/src/lib/repository-matching.ts, app/src/lib/stores/updates/update-remote-url.ts)

### Summary
GitHub Desktop periodically "refreshes" the GitHub metadata for a local repository by parsing the local git remote URL into `{hostname, owner, name}` and calling the GitHub API for that literal `owner/name` pair, then trusting whatever repository the API returns as the same logical repository — including automatically rewriting the user's local `origin` remote URL to match. There is no check that the returned repository's stable/immutable identity (e.g., GitHub's numeric repo ID) matches what was previously associated with that local repository.

### Finding Description
`repositoryWithRefreshedGitHubRepository` derives the owner/name to query purely from string-parsing the current default remote URL via `matchGitHubRepository`, which only compares `parsedRemote.hostname`/`owner`/`name` against account endpoints — never against a previously stored numeric/immutable ID [3](#0-2) . It then calls `api.fetchRepository(owner, name)` and, if a response comes back, unconditionally treats it as "the" repository for further processing [4](#0-3) .

Crucially, if the returned `apiRepo.clone_url` differs from the existing remote, `updateRemoteUrl` will silently call `gitStore.setRemoteURL` to overwrite the user's `origin` URL — the *only* guard is that the protocol matches and that the currently configured URL still matches what was last known from the GitHub API (`remoteUrlUnchanged`) [5](#0-4) . No user confirmation dialog is shown for this particular auto-update path (unlike the analogous `_updateExistingUpstreamRemote`/`UpstreamAlreadyExists` flow, which does prompt the user before changing the `upstream` remote) [6](#0-5) .

On top of that, the local database persists the association keyed by `endpoint+login` string and `[ownerID+name]` string pair, not by GitHub's immutable repository ID: `putOwner` looks the owner up (and updates) purely by login string [1](#0-0) , and `upsertGitHubRepositoryFromMatch`/`upsertGitHubRepository` match/insert by `[ownerID+name]` [2](#0-1) .

This mirrors the `restartDca` bug class: `createDca`-style validation (checking whether a resource "already exists"/is the same one, verifying its identity before reusing it) is present in the initial "create"/clone flow, but is missing from the background "refresh"/"restart" flow (`repositoryWithRefreshedGitHubRepository`), which re-derives and re-trusts identity from a mutable, attacker-influenceable string (a GitHub `owner/name` login pair) rather than a stable identifier, then performs a state-mutating action (rewriting the git remote) without re-validating that the entity is the same one the user originally set up.

### Impact Explanation
If the GitHub API returns a different repository for the same `owner/name` string than the one the user originally cloned — for example after a repository is deleted/renamed and the name is reclaimed by a different, malicious repository at the same owner login, or after an org/user rename frees up the login for squatting — Desktop will silently rewrite the local repository's `origin` remote to point at the attacker's `clone_url` [7](#0-6) . Subsequent fetches/pulls initiated by the user then pull code from the attacker-controlled repository, and pushes/pull-request URLs built from `gitHubRepository`/`htmlURL` (e.g. `_openCreatePullRequestInBrowser`, which builds a URL directly from `gitHubRepository.htmlURL`) point at the attacker's project [8](#0-7) . This is a silent corruption of what the user fetches/pushes without their consent — matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires the attacker to control a GitHub API object returned for a specific `owner/name` pair (e.g., by name-squatting after a rename/deletion, a scenario explicitly allowed under the "attacker controls...a GitHub API object" impact criteria). It does not require local/physical access, admin rights, or leaked credentials — only that the user's account has previously configured a remote for a repository whose name later becomes available for reuse, and Desktop's periodic background refresh (`repositoryWithRefreshedGitHubRepository`) runs while that reuse window is open. The existing TODO/known-gap comment in the code itself (`// TODO: We currently never clear GitHub repository associations`) indicates the team is aware this identity-tracking is not robust [9](#0-8) , but the gap analyzed here (silent remote URL rewrite without identity pinning or user confirmation) is broader than that comment covers.

### Recommendation
1. Short term: before calling `updateRemoteUrl`/`setRemoteURL` from the background refresh path, verify the freshly fetched `apiRepo`'s immutable ID matches the previously stored `gitHubRepository`'s ID (not just owner/name strings); if it doesn't match, treat it as a different repository and require explicit user confirmation before altering the remote — the same pattern already used for the `upstream` remote via `UpstreamAlreadyExists` [6](#0-5) .
2. Long term: persist and key local GitHub-repository associations by GitHub's immutable numeric repository ID rather than `[ownerID+name]` string pairs, and never silently rewrite `origin` without user confirmation.
3. Add regression/unit tests (as already partly exist in `update-remote-url-test.ts`) covering the case where the fetched API repository's ID differs from the previously associated one, asserting that the remote is *not* silently changed.

### Proof of Concept
1. User clones `https://github.com/alice/project`, and Desktop associates the local repo with GitHub repository `alice/project` (owner login `alice`, name `project`) purely via `matchGitHubRepository`'s string parse of the remote URL [3](#0-2) .
2. `alice/project` is deleted or `alice` renames her account/repo, freeing the `alice/project` name.
3. Attacker creates a new account with login `alice` (or, on GitHub Enterprise with more permissive naming, creates a repo `project` under the freed org/login) and pushes malicious content there.
4. On the next background refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('alice', 'project')`, gets the attacker's new repo back, and since `updateRemoteUrl`'s guard conditions are satisfied (protocols match, remote URL previously matched the last-known GitHub clone URL, and URLs now differ), it calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` silently [7](#0-6) .
5. The user's next `git fetch`/`git pull`/PR-related operation now targets the attacker's repository without any dialog or confirmation.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

    const repoStore = this.repositoriesStore

    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }
