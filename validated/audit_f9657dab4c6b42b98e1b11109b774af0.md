### Title
Unauthenticated `ReceivedOutput` Deserialization Permits Forged Bitcoin Deposits - (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an attacker-supplied offset, transaction output, and outpoint without proving that the outpoint exists on-chain or was produced by `Scanner` from a matching transaction output [1](#0-0) . This bypasses the normal scan path, which derives an output only when an observed transaction’s `script_pubkey` matches a registered key/offset [2](#0-1) . The processor deserializer then accepts the forged `ReceivedOutput` as an `Output`, reports its attacker-chosen amount through `balance`, and maps it back to a multisig key by subtracting the supplied offset [3](#0-2) [4](#0-3) .

### Finding Description
The serialized `ReceivedOutput` format contains three unauthenticated claims: the scalar offset, the `TxOut` including its value and script, and the claimed Bitcoin outpoint [5](#0-4) . `ReceivedOutput::read` merely parses those fields and constructs the object, with no check that the outpoint exists, is unspent, belongs to a valid transaction, or appeared in a block scanned by the trusted `Scanner` path [1](#0-0) .

The analogous missing-authentication sink is that downstream consumers treat the deserialized object as a received, spendable output solely because parsing succeeded. For the group key `K`, an attacker chooses an offset `o` and sets the fake `TxOut` script to `P2TR(K + oG)`, causing `Output::key` to recover `K` and `Output::balance` to report the forged amount [3](#0-2) . `SignableTransaction::multisig` only verifies the internal consistency condition `P2TR(K + oG) == prevout.script_pubkey`; it does not authenticate that the referenced outpoint carries that script or value on-chain [6](#0-5) .

After that self-consistency check, the signing path commits to the forged previous output and generates a Taproot key-spend sighash for it [7](#0-6) . Signature completion then attaches the resulting Schnorr signature to the fabricated transaction input [8](#0-7) .

### Impact Explanation
An unprivileged party who can supply serialized output bytes can cause Serai to report an arbitrary Bitcoin balance as received under an active multisig key even though no such spendable UTXO exists [4](#0-3) . The forged object can also drive threshold signing of a transaction spending the nonexistent or unrelated outpoint because signing validates only the offset/script relationship supplied by the attacker [9](#0-8) [6](#0-5) .

This produces funds that are reported received but are not spendable, and it can cause processors to coordinate FROST signatures over an unintended Bitcoin transaction [7](#0-6) .

### Likelihood Explanation
The attack requires only control of bytes passed to `ReceivedOutput::read` or the containing Bitcoin `Output::read`; no private key, validator key, network privilege, or malformed curve encoding is needed [1](#0-0) [4](#0-3) . Constructing a passing forgery is straightforward because the required offset and corresponding P2TR script are both attacker-selected fields [10](#0-9) [11](#0-10) .

### Recommendation
Do not deserialize `ReceivedOutput` into a trusted spendable-output type without authenticating its provenance. The deserializer should either remain a raw transport representation or require the expected base key/block context and verify that `outpoint` resolves to a confirmed transaction output whose `TxOut` exactly matches the serialized value and `P2TR(key + offset * G)` script. At the `processor::Output::read` boundary, persist and reload a scanner-produced commitment, such as block ID plus transaction/output index, and revalidate it against chain data before reporting balance or creating signing inputs.

### Proof of Concept
For target group key `K`:

```rust
use k256::{ProjectivePoint, Scalar};
use bitcoin_serai::{
  bitcoin::{
    Amount, OutPoint, TxOut, Txid,
    consensus::serialize,
    hashes::Hash,
  },
  wallet::{p2tr_script_buf, ReceivedOutput, SignableTransaction},
};

let mut offset = Scalar::ONE;
let script = loop {
  let spend_key = K + (ProjectivePoint::GENERATOR * offset);
  if let Some(script) = p2tr_script_buf(spend_key) {
    break script;
  }
  offset += Scalar::ONE;
};

let forged_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: script,
};
let forged_outpoint = OutPoint {
  txid: Txid::from_raw_hash(*bitcoin::hashes::sha256d::Hash::all_zeros()),
  vout: 0,
};

let mut bytes = offset.to_bytes().to_vec();
bytes.extend(serialize(&forged_txout));
bytes.extend(serialize(&forged_outpoint));

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000);
```

`ReceivedOutput::read` accepts those bytes even though `forged_outpoint` was never observed in a block [1](#0-0) . Passing `forged` to `SignableTransaction::new` uses the forged `TxOut` as the previous output and the forged `OutPoint` as the transaction input [9](#0-8) . Calling `multisig` with keys for `K` succeeds because the attacker intentionally set `TxOut.script_pubkey` to `P2TR(K + offset * G)` [6](#0-5) . The resulting transaction is signed for the fabricated outpoint but is not spendable because the referenced UTXO does not carry the claimed value/script on-chain [7](#0-6) .
