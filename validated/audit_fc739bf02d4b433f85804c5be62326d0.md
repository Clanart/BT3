### Title
Unauthenticated `shop` param drives session/token selection in `EnsureInstalled`, enabling cross-shop session confusion - (File: app/controllers/concerns/shopify_app/ensure_installed.rb)

### Summary
`current_shopify_domain` and `installed_shop_session` derive the acting shop purely from `params[:shop]` after only format sanitization via `ShopifyApp::Utils.sanitize_shop_domain`, with no HMAC or session-token/JWT verification in this legacy (non-`use_new_embedded_auth_strategy`) code path. `validate_non_embedded_session`'s `client.get(path: "shop")` call only checks whether the stored offline token for that attacker-supplied shop is still valid on Shopify's side - it does not verify that the caller is that merchant.

### Finding Description
`check_shop_domain` (line 46-48) gates access solely on `current_shopify_domain` being present, which is computed from `params[:shop]` [1](#0-0) . `installed_shop_session` then looks up the stored offline session for that shop via `SessionRepository.retrieve_shop_session_by_shopify_domain(current_shopify_domain)` [2](#0-1) . In the legacy flow (`use_new_embedded_auth_strategy?` false), `check_shop_known` and `validate_non_embedded_session` are the only additional gates [3](#0-2) . `validate_non_embedded_session` skips the REST check entirely when `loaded_directly_from_admin?` is true (i.e., `params[:embedded] == "1"` and embedded_app configured) [4](#0-3) [5](#0-4) ; otherwise it calls Shopify's `shop` REST endpoint using `installed_shop_session` to check the token is still valid, redirecting to OAuth only on a 401 [6](#0-5) .

Critically, none of `check_shop_domain`, `current_shopify_domain`, `check_shop_known`, or `validate_non_embedded_session` verify that the request actually originates from Shopify Admin or from the shop's authenticated merchant. There is no HMAC verification of query parameters and no session-token/JWT decoding anywhere in this concern. The `embedded`/`params[:embedded] == "1"` check is a plain string comparison an attacker fully controls, and it is used only to *skip* the (weak) revalidation call, not to *require* stronger proof. This matches the test suite's own behavior: passing `shop: "shop1.myshopify.com"` alone (no HMAC, no token) is sufficient to reach `:ok` as long as a session happens to exist for that domain [7](#0-6) , and supplying `embedded=1` alone skips even the token-liveness check [8](#0-7) .

Consequently, `validate_non_embedded_session`'s REST call is not an identity check — it verifies "is this stored offline token for shop X still valid on Shopify's side," not "did the current requester prove control of shop X." Any client that can reach a controller including `EnsureInstalled` (legacy path) and knows/guesses a target `shop` domain (Shopify shop domains are not secret and are often discoverable/guessable, e.g. `storename.myshopify.com`) will have the controller load and act using that shop's previously-installed offline session, satisfying "strongest verified identity source wins" is violated: the weakest, fully attacker-controlled channel (raw `shop` query param) determines which merchant's session and access token are used, with no stronger channel (HMAC, session token, OAuth-bound cookie) ever required or cross-checked.

### Impact Explanation
This is a cross-shop session confusion: an unprivileged caller supplying an arbitrary/victim `shop` param can cause the app to load and operate with that victim shop's stored offline access token (`installed_shop_session`), and any downstream controller action gated by `EnsureInstalled` will execute using the victim shop's Admin API session. This corresponds to Shopify HackerOne's "cross-shop access: loading/acting with another store's offline session" impact class — the app fails to bind the acting shop to a cryptographically verified identity for the request.

### Likelihood Explanation
The path is reachable on any GET request to a controller including `ShopifyApp::EnsureInstalled` using the legacy (non-token-exchange) configuration — this is the gem's default unless `use_new_embedded_auth_strategy?` is enabled [3](#0-2) . The only precondition is that the target shop has previously installed the app (has a stored offline session) — a normal, common state — and that the attacker knows or can guess the `myshopify.com` domain. No secrets, HMAC, or session tokens are required from the attacker; only the `shop` (and optionally `host`/`embedded`) query params. This is deterministic and repeatable per request.

### Recommendation
In the legacy (non-token-exchange) `EnsureInstalled` path, require verification that the request genuinely originates from Shopify for the claimed shop before trusting `params[:shop]` to select a session — e.g., verify the Shopify-signed HMAC on the query string (as Shopify's embedded app launch/HMAC-signed URL does) or require and decode a Shopify session token (JWT) bound to the shop, and only fall back to `params[:shop]` when no stronger identity channel is present, never allowing the raw param to override a verified identity. At minimum, `validate_non_embedded_session`'s REST call should not be treated as an identity proof; identity binding must happen before `installed_shop_session` is used for any state-reading/state-changing action.

### Proof of Concept
```ruby
test "unauthenticated shop param alone selects arbitrary shop's offline session" do
  victim_session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain)
    .with("victim-shop.myshopify.com").returns(victim_session)

  client = mock
  ShopifyAPI::Clients::Rest::Admin.expects(:new).with(session: victim_session).returns(client)
  client.expects(:get).with(path: "shop")

  # Attacker sends no HMAC, no session token, no proof of controlling victim-shop
  get :index, params: { shop: "victim-shop.myshopify.com" }

  assert_response :ok # controller proceeds using victim shop's offline session
end
```
This reproduces the existing "returns :ok if the shop is installed" test [7](#0-6)  but demonstrates that supplying an arbitrary shop domain — with no HMAC/session-token proof — is sufficient for the controller to bind the request to that shop's stored offline session, confirming the invariant ("loaded session must correspond to the merchant proven to control the shop, not a raw param") is violated.
