### Title
Unauthenticated participant index causes out-of-bounds map lookup panic - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`AdditionalBlameMachine::blame` and `BlameMachine::blame` accept attacker-controlled `Participant` values and pass them directly into `blame_internal` without checking whether they belong to the DKG participant set. When a decryption proof is supplied, `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` before validating that `decryptor` was registered. A public caller can therefore use a nonzero participant index outside the configured `1..=n` set to trigger a panic.

### Finding Description
`Participant::new` only rejects zero and does not constrain the participant to the protocol's `n`. `BlameMachine::blame` forwards its `sender` and `recipient` arguments to `blame_internal`. Inside `Decryption::decrypt_with_proof`, the message PoP is checked first, then the optional `EncryptionKeyProof` path indexes `self.enc_keys[&decryptor]` while constructing the DLEQ verification points.

Because `enc_keys` only contains registered participants, a nonexistent nonzero `recipient` causes `HashMap` indexing to panic. The invalid participant is reachable through `AdditionalBlameMachine::blame`, which is intended to process externally supplied accusations and serialized messages/proofs.

### Impact Explanation
An unauthenticated party able to submit a blame statement can crash the process evaluating blame by specifying an unregistered recipient and providing any syntactically decodable `EncryptionKeyProof`. This is a remote denial of service against DKG completion/dispute handling. Depending on the caller's panic handling, it can prevent blame adjudication and abort threshold-key completion.

### Likelihood Explanation
The attacker only needs to supply:

- a valid `EncryptedMessage` whose PoP verifies for the claimed sender,
- an arbitrary `EncryptionKeyProof` encoding sufficient for `Some(proof)` to be passed, and
- a `recipient` participant index not present in the registered encryption-key map.

The code does not reject the out-of-range recipient before indexing the map. No key compromise, collusion, or malformed cryptographic internals are required.

### Recommendation
Validate both `sender` and `recipient` against `self.commitments` / `self.encryption.enc_keys` before performing proof verification or map indexing. Prefer `HashMap::get` and return `PedPoPError::InvalidParticipant` or an equivalent blame error instead of indexing. The same validation should be applied to `self.commitments[&sender]` before it is used later in `blame_internal`.

### Proof of Concept
```rust
// Assume `additional` was constructed with n = 2:
let sender = Participant::new(1).unwrap();
let recipient = Participant::new(3).unwrap(); // Valid Participant, but not registered.

// `msg` is a genuine encrypted share whose PoP was produced for `sender`.
// `proof` is any value successfully decoded with EncryptionKeyProof::read;
// it does not need to verify because the recipient lookup panics first.
additional.blame(sender, recipient, msg, Some(proof));
```

The panic occurs at `self.enc_keys[&decryptor]` in `Decryption::decrypt_with_proof`, before `proof.dleq.verify` can reject the invalid proof.
