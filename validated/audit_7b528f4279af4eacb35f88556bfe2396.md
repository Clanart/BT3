## Analysis Summary

The Sherlock bug is fundamentally about a **unit/index mismatch**: a value computed against one coordinate system (raw token precision) is compared/consumed against another (a different precision), silently producing a wrong result (`0`) instead of erroring, breaking an invariant (liquidatability). The Desktop analog I found is structurally the same class of bug: a **stale line-index used across two different coordinate systems** — the "absolute diff line index" recorded in a `DiffSelection` (built against the pre-expansion hunk layout) is later re-applied against the **shifted** hunk layout that results from `expandTextDiffHunk`, causing selection state to silently point at the wrong line when a hunk is expanded upward.

I was not able to fully trace, within the remaining iterations, whether `changes.tsx`/`side-by-side-diff.tsx` clears or remaps the `DiffSelection` object whenever `expandTextDiffHunk` fires for the *Changes* (working directory) view specifically (as opposed to the read-only History/PR views). This is the key open question that determines whether the path is fully reachable in the current app wiring, and it should be verified with a live repro before treating this as fully confirmed.

### Title
Stale diff-line indices after hunk expansion can silently swap which lines are staged/committed - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
`DiffSelection` (`app/src/models/diff/diff-selection.ts`) tracks per-line staging choices using integer "absolute" line indices computed as `hunk.unifiedDiffStart + lineIndex` [1](#0-0) . These indices are meaningful only relative to a *specific* `hunk.lines` array layout. `expandTextDiffHunk` rewrites a hunk's `lines` array by **prepending** newly-revealed context lines when expanding upward, while leaving `hunk.unifiedDiffStart` for that hunk unchanged [2](#0-1) . This means every pre-existing line inside that hunk now sits at a different offset within `hunk.lines`, so the same numeric absolute index that used to point at line N now points at a different, newly-inserted line.

### Finding Description
1. A user opens a diff for a file with unstaged changes and manually selects/deselects individual lines for a partial commit. This selection is stored as a `Set<number>` of absolute line indices inside `DiffSelection` (`divergingLines`) [3](#0-2) .
2. The user then expands a hunk upward (a normal, common UI action to reveal more context) via `expandTextDiffHunk`.
3. For an "expand up" operation, new lines are spliced in **before** the hunk's existing lines: `updatedHunkLines = isExpandingUp ? [newDiffHunkLine, ...newLineDiffs, ...allHunkLinesButFirst] : ...` [4](#0-3) . The resulting hunk keeps the same `unifiedDiffStart` [5](#0-4) .
4. Consequently, a pre-existing diff line that used to be at `hunk.unifiedDiffStart + k` is now at `hunk.unifiedDiffStart + k + numberOfLinesToAdd`. The `DiffSelection` object, however, was never remapped/shifted — its `divergingLines` set still contains the old index `k`.
5. When `formatPatch` later evaluates `file.selection.isSelected(hunk.unifiedDiffStart + lineIndex)` per line to build the commit patch [6](#0-5) , index `k` now resolves to one of the newly-added context/expansion lines (or, in edge cases, a wholly different original line) rather than the line the user actually intended to (de)select.
6. Nothing in `formatPatch`, `applyPatchToIndex` (`app/src/lib/git/apply.ts`), or `DiffSelection` cross-checks that the selection's index space still matches the current hunk layout — there is no version/generation tag on `DiffSelection` tying it to a specific hunk arrangement, so the mismatch is silent.

### Impact Explanation
This breaks the same invariant the Sherlock report calls out: **the value used to decide inclusion/exclusion is computed against the wrong coordinate space**, and the code proceeds anyway instead of failing loudly. In the GitHub Desktop context, this manifests as: a line the user explicitly excluded from a commit gets silently included (or vice versa), producing a patch applied via `git apply --cached` that does not match the user's actual intent — i.e., **silent corruption of what the user commits**. This is a core Desktop guarantee (partial/interactive staging integrity) and falls squarely within the requested impact class ("silent corruption of what the user commits or pushes").

### Likelihood Explanation
Hunk expansion is a common, one-click UI action exposed directly in the diff view whenever a file has collapsed context (`enableDiffExpansion` / expand-up buttons in `side-by-side-diff.tsx` / `side-by-side-diff-row.tsx`). Any user who expands a hunk after having already made line-level selections in that same view is on this path — no unusual steps, no admin/local-access requirement, and no attacker-supplied repository content is even strictly necessary (though an attacker-crafted repo with many small consecutive hunks/gaps could make this more likely to trigger by encouraging expansion). The main uncertainty is whether the current `Changes` (working-directory, stageable) view actually invokes `expandTextDiffHunk` on the same `DiffSelection` used for staging, versus only using it in read-only (History/PR) viewers — I was unable to confirm this wiring in the time available, so likelihood should be validated with a concrete manual repro in the Changes tab before treating this as certain.

### Recommendation
- Tie `DiffSelection` state to the specific hunk-layout "generation" it was computed against, and remap/invalidate `divergingLines` indices whenever `expandTextDiffHunk` shifts hunk contents (particularly for `isExpandingUp`, where indices shift by `numberOfLinesToAdd`).
- Alternatively, avoid mutating index-space at all for existing lines: instead of prepending new lines within the same hunk range, allocate new indices only for the newly added lines and never reuse/renumber indices of lines that already had selection state.
- Add an invariant check in `formatPatch`/`isSelected` that asserts the selection's line-count/expected line identity matches the current hunk's line at that index (e.g., compare line text or a stable per-DiffLine id, not just a numeric offset) before treating that index's selection state as authoritative.

### Proof of Concept
Conceptual repro (needs to be validated against the live UI wiring for the Changes view):
1. Modify a file with a diff that has at least two hunks separated by more than the default expansion step, and stage the second hunk's changes but deliberately deselect one specific line inside the first hunk via the per-line checkbox.
2. Click "Expand Up" on the first hunk (or on a gap) enough times to prepend ≥1 new context line before the deselected line.
3. Inspect (or intercept) the patch generated by `formatPatch` for the commit: the line the user deselected is no longer the one omitted from the patch — instead, one of the newly revealed context/expansion lines (or a different original line) is what maps to that stale index.
4. Complete the commit; diff the resulting commit against the user's actual on-screen selection state to show the mismatch — a line the user intended to exclude/include silently gets the opposite treatment.
