## Finding: Confirmed — NUL-splitting in `diffFromRawDiffOutput` can be defeated by attacker-controlled file content, causing the rendered diff to diverge from the actual diff

### Correction to the premise
A hostile remote's tracked `.gitattributes` **cannot** define an actual `textconv`/external diff driver *command* — that requires an entry in `.git/config` (or global/system config), which is not attacker-controlled content in the clone. So the "malicious custom diff driver" framing in the question is not directly exploitable. However, `.gitattributes` **can** flip the bare `diff` boolean attribute (e.g. `secret.bin diff`) to force Git's internal unified-diff machinery to treat an otherwise binary-looking blob (one containing NUL bytes) as text, per `gitattributes(5)`'s documented "Performing text diffs of binary files" mechanism. This requires no local config trust at all — only the cloned repo's own `.gitattributes` and blob content, matching the "attacker controls a cloned/fetched repository" threat model.

### Finding Description
`diffFromRawDiffOutput` in [1](#0-0)  converts the entire raw `git diff -z --patch-with-raw` output buffer to a UTF-8 string, splits it on every `\0` byte, and feeds only `pieces.at(-1)` to `DiffParser`. This is correct only under the assumption that NUL bytes appear exclusively in the leading `--raw`-format section (used to NUL-delimit filenames/renames) and never inside the trailing unified-diff/patch text.

That assumption breaks when the diffed blob itself is forced to be treated as text and contains embedded NUL bytes: the raw byte content (including any NULs) is copied verbatim into the `+`/`-` hunk lines of the patch section. Since none of the callers (`getWorkingDirectoryDiff`, `getCommitDiff`, `getBranchMergeBaseDiff`, `getCommitRangeDiff`, see [2](#0-1)  and [3](#0-2) ) perform any independent binary/NUL check before calling `diffFromRawDiffOutput`, embedded NULs inside the patch text are indistinguishable from the raw-section delimiters. `String.split('\0')` then chops the patch text (including its `diff --git`/`index`/`---`/`+++` header lines) into multiple pieces, and only the fragment **after the last embedded NUL** is handed to `DiffParser.parse` via `pieces.at(-1)`.

`DiffParser.parseDiffHeader` (`app/src/lib/diff-parser.ts:174-190`) simply scans forward for a line starting with `+++` to end the header — it does not require a preceding `diff --git`/`index`/`---` block. Because the attacker fully controls the raw bytes of the diffed file (and thus every byte of the `+`/`-` lines in the resulting hunk), they can:
1. Place a NUL byte at a chosen offset in the blob.
2. Arrange the bytes immediately after that NUL to begin with `++` so that, once prefixed by the unified-diff `+` marker, the resulting line starts with `+++` (satisfying `lineStartsWith('+++')`).
3. Follow it with a line matching `diffHeaderRe` (`@@ -l,s +l,s @@`) and subsequent `+`/`-`/` ` prefixed lines.

`DiffParser` will accept this as a well-formed, self-contained diff (see `parse()` at [4](#0-3) ), while everything before the last NUL — the real `diff --git` header and any genuine hunks — is silently discarded from `pieces`. If the crafted content doesn't happen to produce a valid `+++`/`@@` sequence, the fallback is that `parseDiffHeader` returns `null` and the file is rendered with **zero hunks** (`app/src/lib/diff-parser.ts:409-418`), i.e. "no changes shown" for a file that in fact changed substantially.

### Impact Explanation
The diff panel shown to the user (working-directory changes, commit view, branch comparisons) can be made to display either (a) no changes at all, or (b) a fabricated/partial hunk, for a file whose real content differs significantly — as verifiable by comparing against `git show`/`git diff` ground truth run outside Desktop. Since commit/push/PR-review decisions in Desktop are driven by what's rendered in this diff view, this can hide malicious content changes from a reviewer or committer, satisfying the "silent corruption of what the user commits or pushes" impact class in spirit (the mismatch is between rendered diff and reality, which is exactly the trust signal users act on before committing/pushing).

### Likelihood Explanation
Requires the attacker to control a cloned/fetched repository's tracked `.gitattributes` and a specific blob's bytes — both are entirely within the "attacker controls repository content" scope. No local config, no diff-driver command, no user action beyond viewing/opening the repo/diff is needed. Crafting the exact byte alignment to land the forged `+++`/`@@` sequence right after a NUL requires some trial-and-error/tooling but is deterministic and reproducible offline.

### Recommendation
Do not use a global `split('\0')` over the whole buffer. Locate only the raw-format section's terminator boundaries explicitly (e.g. parse the leading NUL-terminated raw records up to the count implied by `--raw`/`-z` semantics, or switch to a delimiter that cannot appear in patch text, or avoid `-z` combined with `--patch-with-raw` and instead invoke `--raw` and `--patch` as separate commands). At minimum, validate that the extracted patch text begins with a `diff --git` header before parsing, and treat any file whose raw content contains NUL bytes as binary in the renderer independent of Git's own `diff` attribute decision.

### Proof of Concept
1. Create a hostile repo with `.gitattributes` containing: `payload.bin diff`
2. Commit `payload.bin` with content: legitimate line(s) + a NUL byte + crafted bytes forming `++<fake-old>\n@@ -1,1 +1,1 @@\n+forged benign content\n` immediately following the NUL, after which the real malicious lines actually reside *before* the injected NUL.
3. Clone this repo in GitHub Desktop and open the commit/working directory diff for `payload.bin`.
4. Compare the hunks rendered in Desktop against `git show <sha> -- payload.bin` / `git diff -z --patch-with-raw` run manually — they diverge: Desktop shows the forged/partial hunk (or no hunk at all) while the real hunk containing the actual change is dropped. [1](#0-0) [5](#0-4) [4](#0-3)

export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}

function diffFromRawDiffOutput(output: Buffer): IRawDiff {
  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')

  const pieces = result.split('\0')
  const parser = new DiffParser()
  return parser.parse(forceUnwrap(`Invalid diff output`, pieces.at(-1)))
}
