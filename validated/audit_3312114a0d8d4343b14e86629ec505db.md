### Title
`ThresholdKeys::new` only consumes the first `t` verification shares to derive `group_key` and never validates the remaining shares or the secret share, so crafted `ThresholdKeys::read` bytes yield keys whose later verification shares / group key are attacker-controlled - (File: crypto/dkg/src/lib.rs)

### Summary
Mirroring the audited `verifyCertChain` flaw — where validation effectively terminates at a trusted point in the middle of the list so trailing entries are never checked — `ThresholdKeys::new` derives the group key exclusively from `verification_shares[1 ..= t]` and performs no consistency check on entries `t + 1 ..= n`, nor on whether `secret_share` is the discrete logarithm of `verification_shares[i]`. Untrusted bytes fed to `ThresholdKeys::read` therefore deserialize into a semantically invalid key object that every downstream consumer (`group_key()`, `Scanner`, `view()`, share verification/blame) treats as authentic.

### Finding Description
`ThresholdKeys::new` (crypto/dkg/src/lib.rs:347-391) performs only three checks:

- `verification_shares.len() == params.n()` (line 355)
- every key's index `<= params.n()` (lines 361-365)
- `Interpolation::Constant` requires `t == n` (lines 367-374)

It then computes the group key as a sum over only the first `t` shares:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

(crypto/dkg/src/lib.rs:376-378)

Nothing verifies that shares `t + 1 ..= n` lie on the same polynomial — equivalently, that the same `group_key` is obtained when interpolating any other size-`t` subset, or that each `verification_shares[l]` is consistent with the commitments that produced it. Likewise, `G * secret_share == verification_shares[i]` is never asserted (the dealer only `debug_assert!`s it in `crypto/dkg/dealer/src/lib.rs:64`, and PedPoP constructs consistent shares internally, so the gap only manifests on the `read` path).

`ThresholdKeys::read` (crypto/dkg/src/lib.rs:573-632) reads `t`, `n`, `i`, the interpolation variant, `secret_share`, and exactly `n` group elements via `C::read_G`, then forwards them to `ThresholdKeys::new`. Canonical encoding is enforced per-element, but the semantic invariant "all `n` verification shares and `secret_share` belong to one degree-`t-1` polynomial" is checked for zero of the trailing `n - t` entries — the exact bug class of the report (a list whose tail escapes validation because termination is keyed to a position/prefix rather than to "every element verified").

Downstream, these unchecked values are consumed as ground truth:

- `ThresholdKeys::group_key()` / `original_group_key()` (lines 435-447) — used by `Scanner::new`/`register_offset` in `networks/bitcoin/src/wallet/mod.rs:162-196` to define which outputs count as received funds.
- `ThresholdKeys::view()` (lines 463-533) interpolates `verification_shares[i]` for every `included` participant; for `i > t` the result is attacker-chosen.
- `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:447-495) verifies each participant's share against `self.view.verification_share(l)` on the blame path — so per-share validity for participants `> t` is judged against attacker-supplied points.

### Impact Explanation
Two distinct consequences, both reachable purely through byte input to `ThresholdKeys::read`:

1. **Attacker-known group key / unspendable "received" funds.** Because `group_key` is the interpolation of only `verification_shares[1..=t]`, the byte supplier can set those entries to `G * x_i` for `x_i` they know, making `group_key = G * Σ λ_i·x_i` a key whose discrete log they hold, while the victim's `secret_share`/`view()` machinery treats it as the threshold key. Anything addressed to `group_key()` — e.g., Bitcoin outputs reported as received by `Scanner::new(group_key)` — is spendable by the attacker alone, not by the validator set. This is "funds reported received that are not spendable (by the intended group)."

2. **Share-validation forgery and blame corruption.** For any participant index `l > t`, the supplier sets `verification_shares[l]` arbitrarily. When `l` is in a signing set, `view().verification_share(l)` equals this bogus point (scaled by the interpolation factor), so in `complete` a malicious `l` can present a share that verifies against `Y_l = G·y_l'` they chose — a share valid for no polynomial-consistent key — while an honest `l`'s correct share fails against a corrupted `Y_l` and is reported `InvalidShare(l)`. Invalid shares that verify individually while breaking the aggregate collapse into `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")` (sign.rs:494), i.e., an unattributable signing failure — the verifier's per-share formula is wrong relative to the actual group key.

### Likelihood Explanation
The vulnerability requires attacker-controlled bytes to reach `ThresholdKeys::read`, which the scope rules explicitly list as an accepted reachable surface (untrusted bytes to `ThresholdKeys::read`). All production construction paths (`dkg::dealer::key_gen`, `pedpop::KeyMachine::calculate_share`, `dkg_musig::musig`) generate self-consistent maps, so the bug is latent precisely on the deserialization/persistence path, where a corrupted or hostile key blob is silently accepted instead of rejected — matching the report's exploit model of slipping an unchecked element past a validator that believes it has validated the whole structure. Medium: concrete integrity loss and unblamable fault injection, gated on reaching the `read` surface.

### Recommendation
In `ThresholdKeys::new` (and hence `read`):

- Assert `C::generator() * secret_share == verification_shares[&params.i()]` (rejecting mistyped/crafted key blobs).
- Verify all `n` verification shares are consistent with a single degree-`t-1` polynomial — e.g., check that `group_key` is invariant when interpolated over additional size-`t` subsets, or equivalently verify each share `l` against the commitment-derived stripe sums rather than trusting the raw map. This is the direct analog of the report's recommendation that the root certificate occupy exactly the final position — i.e., validate *every* element, not a prefix.
- Add negative deserialization tests: keys with a tampered `verification_shares[t + k]`, with `secret_share` not matching `verification_shares[i]`, and with `n`/`t` mutated must be rejected.

### Proof of Concept
```rust
use std::collections::HashMap;
use zeroize::Zeroizing;
use rand_core::{RngCore, OsRng};
use dalek_ff_group::Ristretto as C;
use ciphersuite::{group::{ff::Field, Group}, Ciphersuite};
use dkg::{Participant, ThresholdParams, ThresholdKeys, Interpolation, DkgError};

#[test]
fn trailing_verification_shares_unchecked() {
  let (t, n) = (2u16, 4u16);
  // Honest polynomial of degree t-1: f(x) = s + a*x
  let s = <C as Ciphersuite>::F::random(&mut OsRng);
  let a = <C as Ciphersuite>::F::random(&mut OsRng);
  let f = |x: u16| s + a * <C as Ciphersuite>::F::from(u64::from(x));

  let mut shares = HashMap::new();
  for l in 1 ..= n {
    let l = Participant::new(l).unwrap();
    shares.insert(l, C::generator() * f(u16::from(l)));
  }
  // Corrupt the tail entry that group_key never reads (t=2 uses only indices 1,2)
  shares.insert(Participant::new(4).unwrap(), C::generator() * <C as Ciphersuite>::F::random(&mut OsRng));

  // Secret share also unchecked: give participant 1 a completely wrong secret
  let keys = ThresholdKeys::<C>::new(
    ThresholdParams::new(t, n, Participant::new(1).unwrap()).unwrap(),
    Interpolation::Lagrange,
    Zeroizing::new(<C as Ciphersuite>::F::random(&mut OsRng)),
    shares.clone(),
  );
  // ACCEPTED: shares[3]/shares[4] and secret_share never validated, yet
  // keys.group_key() == G*f(0) as if everything were consistent.
  assert!(keys.is_ok());

  // The same bytes round-trip through the serialization path unchecked:
  let mut buf = vec![];
  keys.unwrap().write(&mut buf).unwrap();
  assert!(ThresholdKeys::<C>::read(&mut buf.as_slice()).is_ok());
}
```

A symmetric variant sets `verification_shares[1..=t] = G*x_i` for known `x_i`, producing `ThresholdKeys` whose `group_key()` discrete log is known to whoever crafted the bytes — any address/scanner registration derived from it is attacker-controlled while the victim's `secret_share` signs for a different, useless share.
