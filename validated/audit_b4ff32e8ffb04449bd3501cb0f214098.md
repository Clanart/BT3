### Title
DataLayerWallet.singleton_removed trusts unverified memo fields for DL root/inner_puzzle_hash without cross-checking against the coin's actual (consensus-verified) puzzle hash - ([File: chia/data_layer/data_layer_wallet.py])

### Summary
`DataLayerWallet.singleton_removed()` extracts a DL singleton's next `root` and `inner_puzzle_hash` from the `CREATE_COIN` condition's memo/hint field (`condition[3][1]`, `condition[3][2]`), but never verifies that these memo-derived values actually reconstruct the coin's real, consensus-committed `puzzle_hash`. This mirrors the reported bug class: one code path (`full_puzzle_hash = bytes32(condition[1])`) reflects the cryptographically/consensus-verified truth (the actual puzzle hash the `CREATE_COIN` condition commits to), while a separate, independent extraction (`root`/`inner_puzzle_hash` from the memo list) is trusted as the semantic payload without cross-validation against that verified value.

### Finding Description
In `chia/data_layer/data_layer_wallet.py`, `singleton_removed()`: [1](#0-0) 

parses the output conditions of a spent DL singleton and, upon finding a `CREATE_COIN` condition with an odd amount, takes:
- `full_puzzle_hash = bytes32(condition[1])` — the actual puzzle hash of the created coin, which is the value enforced by mempool/consensus condition processing (this is "the signature" in the SAML analogy: cryptographically tied to the real coin).
- `root`/`inner_puzzle_hash` from `condition[3][1]` / `condition[3][2]` — values pulled from the memo/hint list attached to the `CREATE_COIN` condition. Memos/hints in Chia are informational metadata and are **not** enforced by CLVM/consensus to correspond to the actual puzzle.

The function then persists a `SingletonRecord` using these unchecked `root`/`inner_puzzle_hash` values: [2](#0-1) 

Critically, it never checks that `create_host_layer_puzzle(inner_puzzle_hash, root).get_tree_hash_precalc(inner_puzzle_hash) == full_puzzle_hash` before trusting `root`/`inner_puzzle_hash` as the new Data Layer store root/tree state. This is exactly the "independent extraction with no cross-validation" pattern from the report: the verified quantity (`full_puzzle_hash`) and the trusted semantic payload (`root`, `inner_puzzle_hash`) are extracted from different, unlinked parts of the condition, and only the former is consensus-guaranteed.

Contrast this with the correct pattern used elsewhere in the codebase for the same class of problem, e.g. `CATWallet.match_hinted_coin()` which explicitly recomputes the puzzle hash from the hint and compares it to the coin's actual puzzle hash: [3](#0-2) 

and `VerifiedCredential.get_next_from_coin_spend()`, which performs a final cross-check between the reconstructed puzzle and the actual coin puzzle hash before accepting the parsed state: [4](#0-3) 

`DataLayerWallet.singleton_removed()` omits this cross-check entirely.

### Impact Explanation
Any party who can produce a valid spend of a tracked DL singleton (the store owner, or any Data Layer client which the local wallet is subscribed to/tracking) can set an arbitrary memo (`root`, `inner_puzzle_hash`) unrelated to the coin's real puzzle hash. `DataLayerWallet` will record this forged `root` as the new authoritative Merkle root for the store in `dl_store`, and will build the child's `LineageProof` from these unverified values. Because the local wallet's Data Layer state (root/lineage) drives what proofs/roots are trusted and offered to Data Layer clients (and what lineage is used to construct subsequent spends), a wallet syncing this state can be tricked into believing a different (attacker-chosen) Merkle root/tree state is authoritative for the store, corrupting the locally cached "verified" Data Layer root and any spends built against it — without invalidating the underlying, validly-verified coin creation. This is a forged/duplicated "assertion" (the root value) accepted alongside a validly verified signature (the coin's actual, consensus-committed puzzle hash), directly matching the CVE's bug class of accepted-but-unverified prepended data.

### Likelihood Explanation
Reachable purely through a Data Layer singleton spend that any current owner/counterparty of the tracked singleton can construct (no special privilege beyond already being authorized to spend that particular singleton, which is a normal condition for a Data Layer store operator or any wallet syncing others' announced DL updates). No malicious peer/node capability is required — only the ability to submit a spend (a spend bundle) whose memo field diverges from its actual puzzle hash. This is directly reachable by any Data Layer client/participant.

### Recommendation
In `singleton_removed()`, after extracting `root` and `inner_puzzle_hash` from the memo, recompute `create_host_layer_puzzle(inner_puzzle_hash, root).get_tree_hash_precalc(inner_puzzle_hash)` and assert it equals `full_puzzle_hash` before persisting the `SingletonRecord`; if it doesn't match, treat the singleton as unrecognized/melted (log and return), the same defensive pattern already used in `CATWallet.match_hinted_coin()` and `VerifiedCredential.get_next_from_coin_spend()`.

### Proof of Concept
1. Set up a tracked DL singleton store with an existing `SingletonRecord` (owner spends normally at least once so the wallet is subscribed/tracking it).
2. Craft a spend of that DL singleton whose inner puzzle solution outputs a `CREATE_COIN` condition where:
   - the actual puzzle (`condition[1]`) is any valid host-layer puzzle hash the spender legitimately controls (satisfies consensus/mempool acceptance), and
   - the memo list (`condition[3]`) hints an arbitrary, unrelated `root`/`inner_puzzle_hash` pair that does NOT reconstruct that puzzle hash.
3. Push the spend bundle; it is accepted by consensus/mempool since memo/hint contents are not enforced.
4. Observe that `DataLayerWallet.singleton_removed()` records the forged `root`/`inner_puzzle_hash` in `dl_store` as the new `SingletonRecord`, diverging from the coin's real puzzle/state — without any error, because no cross-check between the memo-derived values and `full_puzzle_hash` is performed.
