### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/fee calculation, producing transactions that can be non-relayable — a protocol-critical operation silently fails like a payment that cannot complete - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
Analog to the reported bug class — a protocol-critical flow (liquidation) fails unconditionally because a required dependent action (the return transfer) cannot succeed — `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` builds a transaction containing an OP_RETURN data output, but computes the transaction weight and required fee using only `payments`, never `tx_outs`. The resulting `SignableTransaction` can pay a fee rate below the configured rate and even below the minimum relay fee, so a transaction carrying `data` can be produced that the Bitcoin network will not relay. The signing/spend flow completes "successfully" yet yields a transaction that cannot be accepted — the same shape as a liquidation that "succeeds" except for the unavoidable failing payout step.

### Finding Description
`SignableTransaction::new` accepts an optional `data` field and appends an OP_RETURN `TxOut` to `tx_outs` (up to 80 bytes of data, lines 194–202). However, both weight calculations use `payments` (the parameter slice), not `tx_outs`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// ...
let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
``` [1](#0-0) 

`calculate_weight_vbytes` builds the dummy transaction's outputs solely from `payments` plus the optional change output — the OP_RETURN output pushed onto `tx_outs` is invisible to it. The OP_RETURN output adds roughly 90+ serialized bytes (8-byte value + script length + OP_RETURN + up to 80-byte push, all non-witness data), i.e. ~23+ vbytes that are never charged for. `needed_fee = fee_per_vbyte * vbytes` is therefore underestimated, and the `TooLowFee` check at line 211 validates the fee against the underestimated `vbytes`.

Additionally, because the check at line 215 only requires `input_sat >= payment_sat + needed_fee` (with the underestimated `needed_fee`), a transaction can be constructed whose true fee rate falls below `bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE`. Nodes will reject such a transaction from their mempool, so the multisig's spend — the operation everything else in the pipeline depends on — can never confirm, even though `SignableTransaction::new`, `multisig`, and FROST signing all succeed without error.

### Impact Explanation
Any `SignableTransaction` created with `data` (e.g., transactions that must carry instruction data back to Bitcoin) is systematically under-priced relative to the caller's intended fee rate. With a minimally configured `fee_per_vbyte` (the code permits any rate passing the min-relay check on the underestimated size), the produced transaction is below the default minimum relay fee and will be rejected by standard nodes — the funds in the consumed inputs cannot move via this transaction, permanently failing that spend attempt, directly paralleling a liquidation that reverts on its mandatory payout. Even at higher configured rates the transaction pays materially less per actual vbyte than requested, increasing the chance of being stuck. Note the related calculation: the change-output sufficiency check at line 228 uses `fee_with_change` derived from the same underestimated weight, so change and fee are both computed against a smaller-than-real transaction.

### Likelihood Explanation
The underestimation is unconditional whenever `data` is `Some`; whether it causes outright non-relay depends only on how close `fee_per_vbyte` is to the minimum relay bound — a configuration the code itself deems acceptable. Reachability is via the data attached to Bitcoin-bound transactions (the same mechanism used to carry `InInstruction`-style payloads), which external deposit flows can cause to be signed — matching the allowed public-input surface of messages/data an unprivileged party causes to be signed. No malicious validator, key leak, or broken-BFT assumption is required.

### Recommendation
Compute weight over the actual output set: call `calculate_weight_vbytes` with the full `tx_outs` (after the OP_RETURN push) — e.g., refactor it to accept `&[TxOut]` or compute weight directly on the fully constructed `Transaction`. Apply the same correction to the change-aware calculation so `fee_with_change` covers payments + OP_RETURN + change. Ideally restructure `calculate_weight_vbytes` to take the real `tx_ins`/`tx_outs`, eliminating the possibility of divergence between the sized transaction and the signed transaction.

### Proof of Concept
```rust
// In-scope: networks/bitcoin/src/wallet/send.rs
// 1. Construct inputs/payments such that fee_per_vbyte == DEFAULT_MIN_RELAY_TX_FEE/1000.
// 2. Pass data = Some(vec![0u8; 80]).
let tx = SignableTransaction::new(inputs, &payments, None, Some(data), fee_per_vbyte).unwrap();
// tx.needed_fee() == fee_per_vbyte * vbytes_without_opreturn
// Actual tx.output includes the OP_RETURN output (~93 extra serialized bytes),
// so tx.fee() / tx.transaction().vsize() < fee_per_vbyte
// and can fall below the minimum relay fee -> bitcoind rejects the broadcast.
```
The fix is confirmed by the code itself: `tx_outs` (which includes the OP_RETURN) is what gets embedded in `self.tx` (lines 246–251), while `vbytes` is derived exclusively from `payments` — a direct size/fee mismatch provable by comparing `tx.transaction().vsize()` against `needed_fee / fee_per_vbyte`.
