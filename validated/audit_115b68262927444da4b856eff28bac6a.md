### Title
Attacker-controlled participant count causes quadratic CPU exhaustion during key deserialization - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n` as a `u16` and then deserializes `n` verification shares. With Lagrange interpolation and `t == n == u16::MAX`, `ThresholdKeys::new` computes every interpolation coefficient over all `t` participants, causing approximately 4.3 billion field operations from a serialized input of only a few megabytes. This is an externally reachable denial-of-service primitive.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from untrusted input, then reads `n` group elements into `verification_shares` before calling `ThresholdKeys::new` [1](#0-0) . `ThresholdParams::new` permits any nonzero `t <= n` up to `u16::MAX` and does not impose a practical participant limit [2](#0-1) .

When interpolation is `Lagrange`, `interpolation_factor` loops over every included participant and performs field multiplications plus an inversion [3](#0-2) . `ThresholdKeys::new` calls that function once for each of the first `t` participants while deriving `group_key`, making deserialization cost `O(t²)` [4](#0-3) .

### Impact Explanation
A single malicious `ThresholdKeys` blob can consume CPU resources disproportionate to its size. With `t = n = 65,535`, the nested work performs over 4 billion Lagrange iterations, each involving field arithmetic, before the object can be used or rejected. Repeated submissions can exhaust validator, processor, or API-thread capacity.

### Likelihood Explanation
The bytes are sufficient to trigger the expensive path: no valid secret-sharing relationship is needed because `ThresholdKeys::new` derives `group_key` from the supplied verification shares and does not compare `secret_share` against them [5](#0-4) . Any endpoint or storage/recovery path that invokes `ThresholdKeys::read` on untrusted bytes exposes the issue.

### Recommendation
Enforce a protocol-specific maximum `n` and `t` before constructing `ThresholdKeys`, with the limit chosen from the maximum participant set actually supported. Reject `Lagrange` parameter combinations whose interpolation work exceeds a fixed operation budget, or derive the group key using an algorithm with bounded aggregate cost and precomputed denominators where appropriate.

### Proof of Concept
The following byte construction triggers the expensive path for any in-scope `Ciphersuite` with canonical scalar and point encodings:

```rust
let n = u16::MAX;
let mut bytes = Vec::new();

// ThresholdKeys serialization header.
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);

// t = n = u16::MAX; local participant i = 1.
bytes.extend(n.to_le_bytes());
bytes.extend(n.to_le_bytes());
bytes.extend(1u16.to_le_bytes());

// Interpolation::Lagrange.
bytes.push(1);

// Arbitrary canonical secret share.
bytes.extend(C::F::ONE.to_repr().as_ref());

// n canonical verification shares.
for _ in 0..n {
  bytes.extend(C::generator().to_bytes().as_ref());
}

// Enters O(n^2) Lagrange work inside ThresholdKeys::new.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```

The relevant path is `ThresholdKeys::read` → `ThresholdKeys::new` → `Interpolation::Lagrange::interpolation_factor`, resulting in roughly `65,535²` coefficient iterations.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
