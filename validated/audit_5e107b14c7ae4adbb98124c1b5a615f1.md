### Title
`ThresholdKeys::read` eagerly allocates a full `n`-sized interpolation vector from attacker-controlled bytes before validating parameters - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` in `crypto/dkg` deserializes attacker-supplied bytes and, when the interpolation tag indicates `Constant`, immediately calls `Vec::with_capacity(usize::from(n))` using the raw `u16` `n` field read moments earlier. The allocation happens before `ThresholdParams::new` validates `n` and before any check that the remaining input actually contains `n` field elements. An unprivileged party feeding crafted bytes to `ThresholdKeys::read` can force a ~2 MB heap allocation (65535 × 32-byte `F` elements) from fewer than a dozen input bytes — the same bug class as GHSA-g94r-2vxg-569j (eager intermediate allocation exceeding limits relative to input size, CWE-789).

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:591-616`), the function reads `t`, `n`, and `i` as raw `u16`s, then reads a single interpolation-tag byte. For tag `0` (`Interpolation::Constant`), it executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
```

(`crypto/dkg/src/lib.rs:607-613`)

Key points:

- `n` is fully attacker-controlled (any `u16`, up to 65535).
- `Vec::with_capacity(n)` reserves space for 65535 field elements (~2 MB for a 32-byte scalar) **before** the first `read_F` call and before `ThresholdParams::new(t, n, i)` at line 626 can reject a malformed parameter set.
- If the stream ends immediately after the tag byte, the very first `C::read_F` errors out, but the oversized allocation has already occurred and been dropped — pure amplification with no commitment of input bytes.
- The same pattern applies to `verify_r1`/share handling paths only indirectly; `ThresholdKeys::read` is the public deserialization surface explicitly exposed to untrusted input (e.g., multisig key material received during reshare/recovery flows).

Unlike the coordinator-side readers (`SignData::read`, `Block::read`) which are out of scope, this one sits directly in the in-scope `crypto/dkg` crate and is reachable via the listed `ThresholdKeys::read` sink.

### Impact Explanation
A remote party that can cause a validator/processor to deserialize `ThresholdKeys` (reshare, key-recovery, or restore flows that accept peer-supplied key bytes) can force large transient heap allocations with trivial input. Repeated calls let an attacker churn large allocations and reads at negligible bandwidth cost, degrading or crashing the node (denial of service). No secret material is at risk; impact is availability only.

### Likelihood Explanation
The attacker controls all serialized bytes, including `n` and the interpolation tag, and the oversized allocation is unconditional once tag `0` is set. Exploitation requires only the ability to submit crafted key bytes to a deserialization path — no valid key share, no collusion, no authentication bypass. The amplification is capped at ~2 MB per call (u16-bound), which limits single-call severity to Medium, but calls can be repeated indefinitely.

### Recommendation
In `crypto/dkg/src/lib.rs` `ThresholdKeys::read`:

1. Validate `t`, `n`, `i` via `ThresholdParams::new` **before** any allocation keyed on `n`, or read elements incrementally (`Vec::new()` + `push`) so memory grows only with bytes actually present.
2. Apply the same ordering fix anywhere else in-scope that pre-allocates from an untrusted length field before limit checks (e.g., the `verification_shares` loop at lines 620-623 currently relies on read failures rather than a cheap pre-check of remaining length vs. `n`).

### Proof of Concept
Feed `ThresholdKeys::read` the following bytes (conceptual, for a curve with a valid `C::ID` prefix):

```
[4B C::ID len][C::ID bytes]            // valid curve ID
u16 t = 0x0001                          // any value; validated too late
u16 n = 0xffff                          // 65535 participants claimed
u16 i = 0x0001                          // participant index
u8  interpolation = 0x00                // Constant
<EOF>                                   // no further bytes
```

At `crypto/dkg/src/lib.rs:608`, `Vec::with_capacity(65535)` allocates ~2 MB. The first `C::read_F` then fails on EOF, returning an error — but the allocation was already performed. Repeating this with fresh inputs produces sustained allocation pressure disproportionate to the ~15-byte payloads, with no validity requirement on the surrounding parameter set.
