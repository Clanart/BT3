### Title
Hardcoded zero minimum-received allows sandwich attack on WOM→mWOM conversion in `ArbWomUp3.incentiveDeposit` mode 2 - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit` is a public, unprivileged function that, in mode 2, internally calls `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)` with the `_minRec` parameter hardcoded to `0`, removing the slippage protection that `SmartWomConvert` otherwise supports and exposes to callers.

### Finding Description
`ArbWomUp3.incentiveDeposit` (external, `whenNotPaused nonReentrant`, callable by any wallet) calls `_deposit`, and for `_mode == 2` executes: [1](#0-0) 

The call `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` passes `_minRec = 0` unconditionally, even though the caller (the depositing wallet) has no way to specify their own minimum. Inside `SmartWomConvert`, `convert` forwards to `_convertFor`, which performs an actual on-chain swap through the Wombat router when a buyback portion is required: [2](#0-1) [3](#0-2) 

The swap `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` uses a `0` minimum-out (line 195), and the only downstream check is `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` — but since `_minRec` was already forced to `0` by `ArbWomUp3`, this check is a no-op. This differs from the report's exact pattern (no `sqrtPriceLimit`), but is the same root-cause bug class: a swap executed on behalf of an unprivileged user's transaction with no meaningful slippage bound, enabling a classic sandwich attack (front-run to push the WOM/mWOM pool price unfavorably, then back-run to restore it), extracting value from the user's swapped WOM.

### Impact Explanation
Since `mgpAmountToLcok`/reward calculations elsewhere use `_minRec` properly (e.g., `SmartWomConvert._convertFor` and `WombatStaking`), but `ArbWomUp3` strips this protection specifically for its mode-2 deposit path, any unprivileged wallet calling `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` has part of its WOM deposit swapped at an attacker-controlled price with no floor, resulting in a direct, quantifiable loss of the user's deposited funds to a sandwiching MEV bot. This is a direct theft of user funds during a normal, permissionless user action.

### Likelihood Explanation
Likelihood is high in practice: any call to `incentiveDeposit` with `_mode == 2` and `_convertRatio < DENOMINATOR` (so that a `buybackAmount > 0` swap actually occurs) is trivially detectable in the mempool and profitable to sandwich, especially for larger deposit amounts, requiring no special privileges from the attacker.

### Recommendation
Add a `_minRec` (or equivalent slippage) parameter to `ArbWomUp3.incentiveDeposit`/`_deposit` for mode 2, forward the user-supplied value into `IConverter(smartWomConvert).convert(toSwap, _convertRatio, _minRec, 0)` instead of hardcoding `0`, and/or require `SmartWomConvert`'s internal `swapExactTokensForTokens` call to use a non-zero computed minimum-out derived from an on-chain quote (`getAmountOut`) with acceptable slippage tolerance.

### Proof of Concept
1. Attacker monitors mempool for `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` transactions where `_convertRatio < DENOMINATOR`.
2. Attacker front-runs by swapping WOM→mWOM in the same Wombat pool (`womMWomPool`) used by `SmartWomConvert`, pushing the mWOM price up.
3. Victim's transaction executes `_deposit` → `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` → `SmartWomConvert._convertFor` → `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, ...)`, receiving a much lower `amountRec` than fair value, with the `_minRec == 0` check never reverting.
4. Attacker back-runs, swapping mWOM→WOM to restore the pool price and capturing the price difference as profit, at the victim's expense. [4](#0-3) [5](#0-4)
