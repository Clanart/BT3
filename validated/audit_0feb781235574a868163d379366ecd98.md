## Finding

### Title
Order-based hunk splicing in AI conflict resolution can misalign and silently corrupt committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile()` in `app/src/lib/copilot-conflict-resolution.ts` reassembles the final file that Desktop writes to disk and stages for commit after Copilot-assisted conflict resolution, by walking the raw on-disk conflict markers and splicing the model's per-hunk resolutions back in **by ordinal index, not by matched content or line anchor** [1](#0-0) . Its marker-detection loop is a naive linear scan that stops at the *first* line matching the closing/separator regexes, which is the same class of "local miscount silently produces a wrong aggregate value" bug as the Wildcat rounding issue — instead of asset amounts being off by one unit, here a conflict block boundary can be off, causing `hunkIndex` to desynchronize from the boundaries the model actually reasoned about, and the wrong AI-resolved content is spliced into the file that the user then commits/pushes.

### Finding Description
`reassembleResolvedFile` detects a conflict block by matching `^<{7}(?:\s|$)`, then linearly scans forward for the first line matching `^={7}$` (separator) and the first subsequent line matching `^>{7}(?:\s|$)` (closing marker) [2](#0-1) . Once a block is located, the code jumps past it and splices in `hunkResolutions[hunkIndex].resolvedContent`, then increments `hunkIndex` for the *next* conflict marker found in the file [3](#0-2) .

This function is the reassembly half of a two-pass pipeline:
1. `extractConflictHunks` (in `copilot-conflict-context.ts`) parses the on-disk file to build the hunks sent to the model, and per its own tests, has to actively guard against context "bleeding" past nested/adjacent markers (`'does not bleed conflict markers into context lines'`) [4](#0-3) .
2. `reassembleResolvedFile` re-parses the *same* raw file independently, using a simpler first-match scan, to decide where to splice the model's ordered resolutions back in [5](#0-4) .

Because both passes are separate re-implementations of marker detection rather than sharing hunk boundary offsets, a conflict block whose "ours"/"theirs" content contains attacker-controlled text that itself matches the closing regexes (`=======`/`>>>>>>> ...`) — e.g. a file that legitimately or maliciously embeds literal conflict-marker-looking lines (documentation about git, a previous unresolved nested conflict, or a crafted string in source/lock files) — causes `reassembleResolvedFile`'s scan to terminate at the wrong line. This truncates the block early, silently drops or duplicates remaining file lines, and desynchronizes `hunkIndex` for every subsequent conflict in the file, so later hunks receive the wrong model-provided `resolvedContent`. `validateResolutionPaths` only checks that the *count* of hunks matches between context and model response [6](#0-5) ; it does not — and cannot — verify that `reassembleResolvedFile`'s independent re-scan aligns with the boundaries `extractConflictHunks` used, so this class of misalignment is invisible to existing validation.

### Impact Explanation
The corrupted value is the reassembled file content (`resolvedContent`) written back to the working directory and staged for commit [7](#0-6) . Since the attacker controls the content of a merged/rebased branch or PR (a repository object the user fetches/merges through Desktop), this fits the "silent corruption of what the user commits or pushes" impact category: the user reviews the model's per-hunk suggestions (segmented by `extractConflictHunks`'s boundaries) but the actual bytes written to disk can differ because of the independent, looser boundary detection in `reassembleResolvedFile`, all without any error or warning surfaced to the user.

### Likelihood Explanation
Exploitation requires the user to run Desktop's Copilot conflict-resolution feature on a merge/rebase/cherry-pick that includes a file authored (partly) by the attacker, where that file's ours/theirs content contains a line matching `^={7}$` or `^>{7}(?:\s|$)`. This is a plausible but non-trivial precondition (crafted file content, not a generic every-conflict scenario), and I was not able to fully verify `extractConflictHunks`'s exact marker-matching implementation within the available context to conclusively prove a boundary divergence occurs on every such input — only that the reassembly function's design (independent naive re-scan, ordinal splicing) makes this class of desync structurally possible and unguarded by `validateResolutionPaths`. This should be verified against the full `copilot-conflict-context.ts` implementation before treating it as confirmed.

### Recommendation
Have `extractConflictHunks` return the exact line-range (start/end) offsets of each conflict block it identified, and have `reassembleResolvedFile` splice resolutions using those same offsets rather than performing an independent re-scan of the raw file. This removes the possibility of the two passes disagreeing on block boundaries, and any file content containing marker-like lines will still be reassembled consistently with what the model reviewed.

### Proof of Concept
Conceptual PoC (I could not execute this against the repo in this session, so it should be validated with an actual unit test):
1. Create a merge conflict where the "theirs" side (attacker-controlled branch) contains a source file whose content includes a literal line `>>>>>>> some-other-branch` as legitimate file text (e.g., a code comment quoting a diff, or a config/lock file value).
2. Trigger Desktop's Copilot conflict resolution on this file, which has at least two real conflict hunks.
3. `extractConflictHunks` correctly segments the two real hunks (per its "does not bleed conflict markers" guarantee) and sends them to the model; the model returns two `resolvedContent` entries in order.
4. `reassembleResolvedFile`'s scan for the first hunk hits the embedded literal `>>>>>>> some-other-branch` line as its "closing marker" before reaching the real closing marker, truncating the first hunk's replaced region early and leaving genuine conflict-block remainder text in place, then misassigns `hunkResolutions[1]` (intended for the second real conflict) into the wrong location while the true second conflict block is left with `hunkResolutions[2]` (out of range, silently skipped) — corrupting the file the user then commits.

 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the

 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *

 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
