### Title
`ThresholdKeys::read` accepts identity verification shares via `Ciphersuite::read_G`, permitting a zero/identity group key (the address(0) analog) - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is "missing zero-value validation on an address/key parameter lets value flow to the null address." In Serai, the analog lives in `ThresholdKeys::<C>::read`. FROST-facing code reads points through `Curve::read_G`, which explicitly rejects the identity point at `crypto/frost/src/curve/mod.rs:125-131`. `ThresholdKeys::read`, however, deserializes all `n` verification shares through `<C as Ciphersuite>::read_G` (`crypto/dkg/src/lib.rs:620-623`), which only enforces canonical encoding and validity — it happily accepts the identity point (`crypto/ciphersuite/src/lib.rs:91-101`). `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) performs no identity check on any verification share, never checks that `secret_share` corresponds to `verification_shares[i]`, and never checks the resulting `group_key` for identity.

### Finding Description
`ThresholdKeys::read` is a listed untrusted-input sink. An attacker supplying serialized `ThresholdKeys` bytes can set every verification share to the identity point (the encoding-level equivalent of `address(0)`). Because:

- `Ciphersuite::read_G` accepts identity (`crypto/ciphersuite/src/lib.rs:95-100`), unlike `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-130`);
- `ThresholdKeys::new` derives `group_key` purely as the interpolated sum of the shares (`crypto/dkg/src/lib.rs:376-378`) with no non-identity assertion;
- no check binds `secret_share` to `verification_shares[params.i()]`;

the deserialized keys produce a group key of identity (or otherwise attacker-chosen/corrupt). An identity group key corresponds to secret key `0` (plus any scalar/offset tweaks, which are public), so any output locked to it is spendable by anyone — exactly the "funds minted/sent to address(0)" impact.

### Impact Explanation
A `ThresholdKeys` blob with identity verification shares yields `group_key == identity`. A Bitcoin address/outputs derived from such a key are spendable by the private key `offset` alone (known to everyone), i.e., funds reported "received" by the multisig are trivially stealable, or shares interpolated over identity points silently corrupt the group key so signatures the threshold produces are for a key nobody intended.

### Likelihood Explanation
Requires attacker-controlled bytes reaching `ThresholdKeys::read` — the sanctioned untrusted-input path. No threshold collusion, malicious validator assumptions, or leaked keys are needed; the gap is a missing input-validation check identical in kind to the original `updateFounders` finding.

### Recommendation
In `ThresholdKeys::new` (or in `read`), reject identity verification shares — e.g., use an identity-rejecting read for verification shares — and assert the interpolated `group_key` is not identity. Optionally verify `C::generator() * secret_share == verification_shares[i]` during deserialization.

### Proof of Concept
1. Serialize a `ThresholdKeys` blob for a `Curve` type `C` (e.g., Ristretto): valid `C::ID`, `t = n = 1`, `i = 1`, `Interpolation::Lagrange`, any `secret_share`, and one `verification_shares[1]` encoded as the 32-byte canonical identity encoding.
2. Feed to `ThresholdKeys::<C>::read`. `Ciphersuite::read_G` accepts the identity encoding (`crypto/ciphersuite/src/lib.rs:91-101`), `ThresholdParams::new(1,1,1)` succeeds, and `ThresholdKeys::new` returns `Ok` (`crypto/dkg/src/lib.rs:380-391`).
3. `keys.group_key()` returns the identity point; any funds addressed to it are spendable with secret `0` (modulo the public offset), analog to burning/stealing funds sent to `address(0)`.
