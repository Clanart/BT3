### Title
Unbounded persistent growth of the OCC `MultiVersionStore.multiVersionMap` never reclaims keys across blocks - ([File: sei-cosmos/store/multiversion/store.go])

### Summary
The go-bitswap advisory describes an engine that accumulates unbounded per-peer/per-key ledger state in memory with no eviction, causing a persistent (not just per-request) memory leak that a remote party can trigger for free. The sei-chain OCC (optimistic concurrent execution) parallel-execution scheduler has the analogous defect: its `multiversion.Store` is created **once** and reused for the entire lifetime of the validator/full-node process, and every storage key ever written by *any* transaction across *every* block is inserted into `Store.multiVersionMap` (a `*sync.Map`) but the entry for that key is **never removed**, even after the corresponding `MultiVersionValue` becomes empty.

### Finding Description
`scheduler.tryInitMultiVersionStore` guards store creation with: [1](#0-0) 
This means `s.multiVersionStores` (and the underlying `multiversion.Store` per store key) is constructed exactly once for the scheduler's lifetime — it is *not* reset or replaced per block. The identical pattern exists in the giga path: [2](#0-1) 

Each block, `ProcessAll` calls `tryInitMultiVersionStore` (a no-op after the first call) and then drives execution/validation through the same long-lived `Store`: [3](#0-2) 

Inside `Store`, every key that is ever written by a transaction's writeset is inserted into `multiVersionMap` via `mvVal.(MultiVersionValue)` (created lazily on first write) and indexed by key string: [4](#0-3) 

When a transaction's writeset is superseded (e.g., on re-execution/abort/incarnation bump), `removeOldWriteset` only calls `mvVal.(MultiVersionValue).Remove(index)` to drop that transaction's *version* from the value object — it never deletes the outer `multiVersionMap` entry for the key itself, even when the `MultiVersionValue` ends up holding zero versions: [5](#0-4) 

Because the map is keyed by the raw storage key string (`keyString := string(key)`), and because EVM contract execution, CosmWasm execution, tokenfactory denom creation, pointer registration, and virtually every other message type writes to storage keys that frequently include monotonically-increasing or per-call-unique components (nonces, counters, newly-created denom/pointer/account keys, unique contract storage slots), an unprivileged sender can cause a new, permanent entry to be added to this process-lifetime `sync.Map` with every transaction that touches a previously-unseen key. Unlike the mempool (`sei-tendermint/internal/mempool/tx.go`), the JSON-RPC filter/subscription APIs (`evmrpc/filter.go`, `evmrpc/subscribe.go`), and the receipt stores (`sei-db/ledger_db/receipt/*`, `giga/evmonly/receipt_store.go`), all of which were confirmed to have explicit capacity limits and/or periodic pruning/cleanup loops, no equivalent bound or GC pass exists for `multiVersionMap`.

### Impact Explanation
This is a memory-only, unbounded-growth structure held by the block-execution hot path (OCC parallel execution), analogous to the go-bitswap `Engine`'s peer ledger leak. Every historical unique key ever touched by any transaction remains resident in process memory for the life of the node, growing without limit as the chain height increases. This degrades read/write latency on the `sync.Map` over time and eventually exhausts node memory, causing validator/full-node crashes or forced restarts — i.e., validator halt / block delay beyond the liveness threshold once the leak accumulates enough entries, satisfying the "crash of default-configuration node" and "validator halt" impact bar in the rubric.

### Likelihood Explanation
No privileged access, malicious peer, or governance action is required — a normal EVM transaction sender or CosmWasm caller that repeatedly writes to new storage keys (e.g., minting NFTs with incrementing token IDs, incrementing per-address nonces/mappings, deploying new contracts, registering new tokenfactory denoms or CW↔ERC pointers) directly and continuously grows this map on every node running the OCC parallel scheduler. Because normal chain usage inherently produces new keys every block, this leak accumulates passively even without an active attacker, and can be accelerated arbitrarily by a single account submitting a high volume of "new key" transactions.

### Recommendation
Add a cleanup path to `multiversion.Store.removeOldWriteset` (and any equivalent write-clearing sites) that deletes the outer `multiVersionMap` entry once a key's `MultiVersionValue` no longer has any versions/estimates present (i.e., only delete keys that no in-flight transaction references, mirroring the "`if !ok { continue }` / else remove-if-empty" GC pattern the receipt-store pruners already use elsewhere in this codebase, e.g., `sei-db/ledger_db/receipt/litt_receipt_store.go`'s `startPruning`/`pruneBlocksBelow`). Alternatively, recreate `Store.multiVersionMap` per block (accepting the cost of losing warm-cache benefits) so the structure cannot grow past a single block's key set.

### Proof of Concept
1. Run a node with OCC/parallel execution enabled (the `tasks.Scheduler` path).
2. Submit a stream of EVM transactions from a single account that each write to a fresh, never-before-seen storage key per transaction (e.g., deploy trivial contracts that `SSTORE` to `keccak256(nonce)`-derived slots, or repeatedly call `mint`/`createDenom`/`RegisterPointer` style entry points that key state by an incrementing/unique identifier).
3. Observe that `sei-cosmos/store/multiversion.Store.multiVersionMap` size (instrumented via `sync.Map` length or heap profiling) grows monotonically with the number of unique keys submitted and never shrinks, even long after the corresponding transactions have committed and their writesets have been superseded/removed via `removeOldWriteset`.
4. Continue for enough blocks/transactions and observe RSS growth without bound, eventually leading to OOM on the node.

func (s *Store) removeOldWriteset(index int, newWriteSet WriteSet) {
	writeset := make(map[string][]byte)
	if newWriteSet != nil {
		// if non-nil writeset passed in, we can use that to optimize removals
		writeset = newWriteSet
	}
	// if there is already a writeset existing, we should remove that fully
	oldKeys, loaded := s.txWritesetKeys.LoadAndDelete(index)
	if loaded {
		keys := oldKeys.([]string)
		// we need to delete all of the keys in the writeset from the multiversion store
		for _, key := range keys {
			// small optimization to check if the new writeset is going to write this key, if so, we can leave it behind
			if _, ok := writeset[key]; ok {
				// we don't need to remove this key because it will be overwritten anyways - saves the operation of removing + rebalancing underlying btree
				continue
			}
			// remove from the appropriate item if present in multiVersionMap
			mvVal, found := s.multiVersionMap.Load(key)
			// if the key doesn't exist in the overall map, return nil
			if !found {
				continue
			}
			mvVal.(MultiVersionValue).Remove(index)
		}
	}
}
