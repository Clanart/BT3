### Title
LP/WOM reward "sandwich" arbitrage via unrestricted deposit-then-withdraw in `WombatStaking`/`WombatPoolHelper` - (File: wombat/WombatStaking.sol)

### Summary
An ordinary wallet can deposit a large amount of stable/LP tokens into `WombatStaking`/`WombatPoolHelper`, and then immediately withdraw it in the same or very next transaction, capturing a disproportionate share of the WOM rewards harvested from `MasterWombat` — rewards that accrued over time and should belong to long-term stakers, not to the attacker's momentary stake.

### Finding Description
`WombatStaking.deposit()` transfers user funds into the underlying Wombat pool, mints receipt tokens, and only afterwards the pool helper stakes those receipt tokens into `MasterMagpie` via `depositFor` [1](#0-0) . On withdrawal, `WombatStaking.withdraw()` first calls `_toMasterWomAndSendReward(_lpToken, _liquidity, false)` — which triggers `IMasterWombat(masterWombat).withdraw(...)`, harvesting all WOM rewards accrued in the underlying Wombat pool since the last harvest — and only *after* that does `WombatPoolHelper.withdraw()` call `_unstake()`, which reduces the user's staked balance in `MasterMagpie` [2](#0-1) [3](#0-2) .

Crucially, `BaseRewardPoolV2.totalStaked()` reads the live receipt-token balance staked in `MasterMagpie`, and newly harvested rewards are distributed into `rewardPerTokenStored` proportional to `totalStaked()` **at the moment `queueNewRewards` is called** [4](#0-3) . Because the harvest-and-reward-queueing step in `withdraw()` happens *before* the caller's own stake is removed from `MasterMagpie`, the withdrawing user's (potentially very large, freshly deposited) stake is still counted when the harvested WOM is distributed. Immediately afterward, `_unstake()` triggers `MasterMagpie._harvestAndUnstake()` → `_harvestBaseRewarder()`, which pays the user their share of that just-queued reward pool based on their (still large) `balanceOf(_account)` [5](#0-4) [6](#0-5) .

There is no lock-up period, cooldown, or time-weighting between deposit and withdrawal, so a user can inject a large stake right before triggering a harvest/withdraw and collect a share of rewards that accrued to long-standing stakers over the entire period since the last harvest.

### Impact Explanation
This allows theft of unclaimed yield from legitimate long-term LPs: an attacker with no meaningful time-at-risk can claim a share of WOM rewards proportional to a large but momentary stake, diluting the rewards genuinely earned by other depositors. This can be repeated indefinitely (using a flashloan or simply capital available for the duration of one or two transactions) to continuously extract value from the reward pool, directly reducing the yield available to real stakers.

### Likelihood Explanation
Both `deposit()`/`depositLP()` and `withdraw()` on `WombatStaking` are unrestricted, callable by any pool helper on behalf of any user with no minimum holding period, and the harvest that queues new rewards is unconditionally triggered on every deposit and withdrawal call [7](#0-6) [8](#0-7) . Any wallet with sufficient capital (or access to a flashloan-like source of the deposit token) can execute this sequence, making the attack straightforward and repeatable without needing any privileged role.

### Recommendation
Introduce a minimum staking duration (lock-up) before a user's stake is eligible to receive newly harvested rewards, or snapshot/checkpoint reward eligibility prior to processing a deposit within the same harvest cycle, so that reward distribution reflects time-weighted stake rather than instantaneous balance at harvest time. Alternatively, decouple the harvest trigger from `withdraw()` so that a withdrawing user's balance is removed from `totalStaked()` before newly harvested rewards are queued into `rewardPerTokenStored`.

### Proof of Concept
1. Attacker acquires a large amount of the pool's deposit token.
2. Attacker calls `WombatPoolHelper.deposit()` → `WombatStaking.deposit()`, which deposits into the Wombat pool and stakes the resulting receipt tokens for the attacker via `MasterMagpie.depositFor` [1](#0-0) .
3. Attacker immediately calls `WombatPoolHelper.withdraw()` → `WombatStaking.withdraw()`. This calls `_toMasterWomAndSendReward(..., false)`, which withdraws LP from `MasterWombat`, harvesting all pending WOM accrued since the last harvest, and queues it into `BaseRewardPoolV2` via `queueNewRewards`, using `totalStaked()` that still includes attacker's large stake [9](#0-8) .
4. `WombatPoolHelper.withdraw()` then calls `_unstake()` → `MasterMagpie.withdrawFor()` → `_harvestAndUnstake()`, which pays the attacker their proportional share of the just-harvested WOM based on their large (still-present) `balanceOf`, before finally reducing their stake [5](#0-4) .
5. Attacker withdraws their original capital plus a disproportionate share of WOM rewards earned by other long-term stakers, and can repeat the sequence.

        Pool storage poolInfo = pools[_lpToken];

        address[] memory bonusTokens = assetToBonusRewards[_lpToken];
        uint256 bonusTokensLength = bonusTokens.length;

        uint256 womBeforeBalance = IERC20(wom).balanceOf(address(this));
        uint256[] memory beforeBalances = _rewardBeforeBalances(_lpToken);

        if(_isStake)
            _stakeToWombatMaster(_lpToken, lpAmount); // triggers harvest from wombat exchange

            IMasterWombat(masterWombat).withdraw(poolInfo.pid, lpAmount); // triggers harvest from wombat exchange
        uint256 womRewards = IERC20(wom).balanceOf(address(this)) - womBeforeBalance;
        _sendRewards(_lpToken, wom, poolInfo.rewarder, womRewards);

        for (uint256 i; i < bonusTokensLength; i++) {
            uint256 bonusBalanceDiff = IERC20(bonusTokens[i]).balanceOf(address(this)) - beforeBalances[i];
            if (bonusBalanceDiff > 0) {
                _sendRewards(_lpToken, bonusTokens[i], poolInfo.rewarder, bonusBalanceDiff);
            }
        }

        emit WomHarvested(womRewards);

    }
