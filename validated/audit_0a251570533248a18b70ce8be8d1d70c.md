### Title
Attacker-supplied `ReceivedOutput` value/offset is trusted and committed into the Taproot sighash without on-chain verification - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

The Float Protocol incident class — an attacker manipulating a trusted input value (the oracle price) to extract value at a corrupted accounting rate — maps onto Serai's Bitcoin wallet: `ReceivedOutput::read` accepts a fully attacker-controlled `TxOut` (including its `value`), `OutPoint`, and scalar `offset` from untrusted bytes, and `SignableTransaction`/`TransactionSignMachine` then treat `output.value` as ground truth for fee/change accounting and commit it into the BIP-341 signature message via `Prevouts::All`. The only consistency check (`multisig`) verifies the prevout's `script_pubkey` against the derived offset key — never the value, and never that the outpoint exists on chain.

### Finding Description

`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) decodes `offset`, `TxOut`, and `OutPoint` directly from the reader with no validation that the output exists or that the value matches the chain:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
```

`SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:175-235`) then:

1. Sums `input.output.value` into `input_sat` (line 175) and uses it for `NotEnoughFunds` and change computation — the "price" the protocol believes it holds.
2. Stores `prevouts` from the same unverified `TxOut`s (line 253).

In `TransactionSignMachine::sign` (`send.rs:373-390`), `Prevouts::All(&self.tx.prevouts)` commits those attacker-chosen amounts into `taproot_key_spend_signature_hash`, and each FROST share signs that message. The sole guard in `multisig` (`send.rs:275-279`) is:

```rust
if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey { None?; }
```

— script-only. An attacker can supply a `ReceivedOutput` whose `outpoint` references a real deposit of 1,000 sats but whose `output.value` claims 1,000,000 sats (and any `offset` producing the right script, e.g. `Scalar::ZERO` for the base key).

### Impact Explanation

This is the direct analog of depositing against a manipulated oracle price:

- **Inflated accounting**: `input_sat`, `fee()`, and the change amount are computed from the forged value, so `SignableTransaction` reports funds received that do not exist — "funds reported received that are not spendable."
- **Signing an unintended message**: the threshold group produces valid FROST/BIP-340 signature shares over a sighash that attests a false input amount. Because BIP-341 commits prevout amounts, the resulting transaction is consensus-invalid and unbroadcastable — the "deposit" the protocol thinks it is spending does not exist, permanently bricking the UTXO set entry the signer believed it controlled and emitting signatures over fabricated balance statements. Any downstream system that credits deposits based on `ReceivedOutput.value()` (as `get_outputs`/`Output::balance` plumbing does) is crediting against a manipulated "price".

### Likelihood Explanation

Any party able to feed bytes to `ReceivedOutput::read` or to propose inputs to `SignableTransaction::new` — i.e., an unprivileged depositor/relayer supplying output proofs — reaches this path with purely public inputs. No collusion, key leakage, or malicious validator is required; the attack is a single crafted serialization. The corresponding real-world exploit (Float) required only a thin-liquidity oracle; here the "oracle" is the deserialized `TxOut`, which is trivially manipulable.

### Recommendation

- Bind `ReceivedOutput` to reality: verify `outpoint` resolves on chain and the chain `TxOut` equals the claimed `output` (value and script) before admitting it to `SignableTransaction::new`, or make `scan_transaction` the only constructor and keep `read` outputs unverified-quarantined.
- In `multisig`, additionally re-derive the expected `script_pubkey` from `offset` *and* reject any `ReceivedOutput` not produced by `Scanner::scan_*` for a confirmed transaction.
- Document that `ReceivedOutput::read` yields untrusted claims whose `value()` must not be used for accounting until verified.

### Proof of Concept

// networks/bitcoin/src/wallet/mod.rs + send.rs
// Attacker serializes a forged ReceivedOutput:
let forged = ReceivedOutput {
    offset: Scalar::ZERO,                       // passes p2tr_script_buf(group_key) check
    output: TxOut {
        value: Amount::from_sat(1_000_000),     // manipulated "price"
        script_pubkey: p2tr_script_buf(group_key).unwrap(),
    },
    outpoint: real_outpoint_for_a_1000_sat_output,
};
let bytes = forged.serialize();
// Victim side:
let input = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
let tx = SignableTransaction::new(vec![input], &payments, change, None, FEE).unwrap();
// input_sat == 1_000_000 -> NotEnoughFunds check defeated, change inflated,
// sighash commits the false amount via Prevouts::All; FROST signs it.
