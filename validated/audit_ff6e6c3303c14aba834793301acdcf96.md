Confirmed: `getUserTotalLocked` in `mWomSV.sol` decreases immediately when a user calls `startUnlock`, since it subtracts `getUserAmountInCoolDown` from the total balance recorded in `MasterMagpie`. [1](#0-0) [2](#0-1) 

### Title
Reward double-counting correction based on live, user-mutable mWomSV balance allows re-claiming already-rewarded tiers - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount`/`calDoubledCounted` in `ArbWomUp3.sol` compute the "already rewarded" portion of a tiered MGP reward purely by re-reading `mWomSV.getUserTotalLocked(_account)` at call time, instead of from a monotonic stored counter. Because a user can freely lower that live balance via `mWomSV.startUnlock`, they can shrink the base the subtraction is computed on and then re-deposit a tiny amount through `incentiveDeposit(..., _mode == 2)` to have the same tier bracket rewarded twice.

### Finding Description
`incentiveDeposit` calls `getRewardAmount(_amount, msg.sender, _mode == 2)`, which for `_mode == 2` (lock) computes:
- `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)` (tier reward for the hypothetical new total)
- `mgpReward = (rewardAmount for accumulated) - calDoubledCounted(_account)` where `calDoubledCounted` recomputes the tier reward for the *current* `mWomSV.getUserTotalLocked(_account)` value. [3](#0-2) 

This subtraction is meant to give only the *marginal* reward for the newly added amount, assuming the locked balance is monotonically non-decreasing. However, `getUserTotalLocked` is a live value that falls whenever the user calls `mWomSV.startUnlock(_amountToCoolDown)`, which immediately increases `getUserAmountInCoolDown` and thus reduces `getUserTotalLocked` by that amount, without waiting for the cooldown to finish. [2](#0-1) 

Exploit flow:
1. User calls `incentiveDeposit` with `_mode == 2` for a large amount, gets locked into `mWomSV` via `lockFor`, and is rewarded MGP for reaching tier N (`bracketRewarded`/tier state is not actually persisted anywhere — the `bracketRewarded` mapping is declared but explicitly commented `// not in use` and never written or read). [4](#0-3) 
2. User calls `mWomSV.startUnlock(x)` to move part of their locked balance into cooldown, lowering `getUserTotalLocked(account)`.
3. User calls `incentiveDeposit` again with a small `_amount` and `_mode == 2`. `calDoubledCounted(account)` now returns a smaller "already rewarded" figure (because the live balance is lower), so `mgpReward` for the same tier bracket is computed again, effectively re-rewarding the bracket the user already claimed in step 1.
4. `vlMGP.lockFor(rewardToSend, msg.sender)` pays out the duplicated MGP reward directly to the attacker. [5](#0-4) 

No modifier (`nonReentrant`, `whenNotPaused`) or accounting elsewhere prevents this, because the contract has no monotonic per-user "amount already rewarded" state — the only such variable, `bracketRewarded`, is dead code. [6](#0-5) 

### Impact Explanation
This lets an unprivileged user repeatedly re-claim MGP rewards for tier brackets they already climbed, by cycling `startUnlock`/re-deposit, draining the contract's MGP balance meant for legitimate incentive distribution to other users. This matches direct theft of protocol/user funds (the MGP reward pool), though the loss is bounded by `IERC20(mgp).balanceOf(address(this))` since `getRewardAmount` clamps to `mgpleft`. Given the question's precondition ("MGP balance is below twice the capped reward"), the practical extra amount an attacker can extract in a single duplication cycle is capped by the remaining MGP balance, but the mechanism is repeatable across multiple lock/unlock cycles as long as MGP balance remains, so cumulative theft is not naturally bounded to just a single duplication.

### Likelihood Explanation
This requires no privileged role — only calling public functions on `ArbWomUp3` and `mWomSV` (`startUnlock` is external and permissionless for the caller's own balance). It requires only the WOM/mWom capital the user already intends to deposit, plus one extra small deposit transaction; `startUnlock` does not require waiting for the cooldown to complete before `getUserTotalLocked` drops. This is a very low-capital, fully repeatable griefing/theft primitive as long as MGP funding remains and the tier/reward parameters (`rewardTier`, `rewardMultiplier`) are configured with more than one tier.

### Recommendation
Replace the live-balance-derived `calDoubledCounted` with an explicit, monotonically-increasing per-user "amount already rewarded" state variable (e.g. properly wire up and enforce `bracketRewarded[account]`, updating it on every reward payout and using it — not `mWomSV.getUserTotalLocked`) as the basis for marginal-reward computation, so a user's recorded rewarded amount can never decrease regardless of subsequent `startUnlock`/withdraw actions.

### Proof of Concept
Hardhat plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie` (or mocked equivalent), `mWom`, `wom`, `vlMGP`, `mgp` tokens; configure `rewardTier = [0, T1, T2]`, `rewardMultiplier` accordingly via `setMultiplier`; fund the `ArbWomUp3` contract with MGP just under `2 * cappedReward`.
2. User A performs a single `incentiveDeposit(bigAmount, ratio, false, 2)` that crosses tier T1; record `mgpBalanceAfterA = vlMGP` locked amount for A and remaining MGP balance in `ArbWomUp3`.
3. Reset state (separate fork/run). User B performs the same economic action split: `incentiveDeposit(bigAmount, ratio, false, 2)`, then `mWomSV.startUnlock(smallAmount)`, then `incentiveDeposit(tinyAmount, ratio, false, 2)`.
4. Assert: total MGP locked to user B via `vlMGP` across both calls is strictly greater than `mgpBalanceAfterA` for the equivalent total deposited amount, and that `calDoubledCounted(B)` after step 3 does not match the sum of rewards actually already paid out to B, demonstrating the reconciliation invariant is broken.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
    }
