### Title
Scanner::scan_block reports immature coinbase outputs as spendable funds - (networks/bitcoin/src/wallet/mod.rs)

### Summary
The transfer-fee bug class — "the contract assumes the full claimed amount was received/spendable, while the actual usable amount is less" — maps onto `Scanner::scan_block`, which reports every output paying to a registered script as a `ReceivedOutput`, including outputs of the coinbase transaction. Coinbase outputs are consensus-unspendable for 100 blocks, so the scanner reports funds as received that cannot actually be spent.

### Finding Description
`scan_block` iterates over `block.txdata` starting at index 0, feeding every transaction — including the coinbase — into `scan_transaction`. `scan_transaction` only matches `output.script_pubkey` against registered scripts and immediately emits a `ReceivedOutput` carrying the output's full `value` and `outpoint`. There is no maturity check, no block-height check, and no marker distinguishing coinbase outputs. [1](#0-0) 

The only mitigation is a doc comment telling the caller to post-filter or call `scan_transaction(&block.txdata[1 ..])` themselves. The processor does perform this skip (`for tx in &block.txdata[1 ..]`), proving the library itself returns a materially incorrect result that each consumer must independently compensate for. [2](#0-1) 

This is the exact analog of the reported bug: the accounting primitive (`ReceivedOutput::value()`, `SignableTransaction::new`) treats the nominal on-chain amount as fully spendable input value, while the protocol rules make part of it — all of a coinbase output — unusable. Just as `supplyLogic` credits the declared `amount` rather than the post-fee received amount, `scan_block` credits the nominal `TxOut.value` rather than the spendable amount (zero until maturity).

### Impact Explanation
A `ReceivedOutput` for an immature coinbase can be passed to `SignableTransaction::new`, where its `output.value` is summed into `input_sat`, passes the `NotEnoughFunds` check, and produces a transaction whose prevouts commit (via `Prevouts::All` in the BIP-341 sighash) to the coinbase outpoint. Any node will reject the transaction per BIP-30/coinbase-maturity consensus rules, so the multisig signs and broadcasts an unspendable transaction — funds were reported received that are not spendable, and signing effort is wasted on a transaction that can never confirm until the wallet is rebuilt with other inputs.

### Likelihood Explanation
Reachable by an unprivileged party with public inputs only: any miner (or anyone who can influence coinbase payouts, e.g. a mining pool paying the pool reward to the scanned P2TR address) causes a coinbase output matching a registered script to appear in `block.txdata[0]`. No validator collusion, leaked keys, or malicious-RPC assumptions are needed — just a Bitcoin transaction paying the multisig address, which the threat model allows. The bug only triggers if the consumer relies on `scan_block` (or fails to re-implement the coinbase skip), which is why it is Medium rather than higher.

### Recommendation
Either drop coinbase outputs inside `scan_block`/`scan_transaction` (skip `block.txdata[0]`, mirroring the processor), or record the coin height on `ReceivedOutput` and reject its use in `SignableTransaction::new` until `current_height - coin_height >= 100`. This is the analog of "compare balance before and after the transfer": derive spendability from consensus rules rather than trusting the nominal output amount.

### Proof of Concept

```rust
// A miner builds a block whose coinbase pays the multisig's P2TR script.
let coinbase = Transaction {
  // coinbase input: prevout = OutPoint::null(), script_sig = height + arbitrary
  output: vec![TxOut {
    value: Amount::from_sat(6_2500_0000),
    script_pubkey: p2tr_script_buf(key).unwrap(), // matches scanner's registered script
  }],
  .. // ...
};

// scan_block reports it identically to a normal payment:
let outputs = scanner.scan_block(&block);
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 6_2500_0000);
// Yet this outpoint is consensus-unspendable for 100 blocks.

// The wallet happily builds a "valid" spend:
let tx = SignableTransaction::new(
  vec![outputs[0].clone()], &payments, change, None, FEE,
).unwrap(); // succeeds — input_sat counted in full
// The resulting signed transaction is rejected by every node
// ("bad-txns-premature-spend-of-coinbase").
```

The test `send_and_get_output` even exercises this path — it scans `block.txdata[0]` (the coinbase) and immediately spends the result, which only works in regtest because it mines 100 maturity blocks first; the library gives no such guarantee to callers.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
```
