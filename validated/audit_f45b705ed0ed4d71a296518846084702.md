### Title
Unbounded glob/file-parse in hookify `load_rules` enables repo-content DoS against hook execution budget - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` globs `.claude/hookify.*.local.md` and parses every matched file on every `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` hook invocation, with no cap on the number of matched files, no per-file size limit, and no caching across the fresh-process invocations that Claude Code spawns for each hook call. An attacker who can add files to a repository's `.claude/` directory (e.g., via a PR merged by a maintainer, or any flow that lands untrusted files in the working tree) can create thousands of small rule files or a few files with huge frontmatter/message content to blow up per-call latency.

### Finding Description
`load_rules()` builds the glob pattern `os.path.join('.claude', 'hookify.*.local.md')` and calls `glob.glob(pattern)` with no limit on match count [1](#0-0) . It then iterates every matched file and calls `load_rule_file()`, which does an unrestricted `f.read()` of the whole file into memory before any size check [2](#0-1) , followed by the custom hand-rolled YAML-like line-by-line frontmatter parser (`extract_frontmatter`), whose cost scales with content size/line count and has no bound either [3](#0-2) .

Each of `pretooluse.py`, `posttooluse.py`, `stop.py`, and `userpromptsubmit.py` is invoked by Claude Code as a brand-new `python3` process per tool call, and each directly calls `load_rules(event=...)` with no memoization/cache file — confirmed in `posttooluse.py`, which calls `load_rules(event=event)` fresh every time [4](#0-3) . This means every single tool call in a Claude Code session re-globs and re-parses the entire rule set from disk with the cost scaling linearly with attacker-controlled file count/size, with no cross-call cache to amortize it.

Each hook invocation is subject to a `"timeout": 10` (seconds) configured in `hooks.json` for every event type [5](#0-4) . If `load_rules()` + `RuleEngine.evaluate_rules()` exceed this budget, the hook process is presumably killed/times out, and — combined with the already-known behavior that hook errors are swallowed and safely default to allow via the blanket `except Exception` handlers wrapping `main()` in each hook script (e.g., `posttooluse.py`) [6](#0-5)  — a timeout/failure here degrades into either (a) sustained latency on every tool call for the duration of the session, or (b) fail-open behavior where hook enforcement silently stops applying once the hook can no longer complete in time. There is no allowlist, approval prompt, file-count guard, or size guard anywhere in `config_loader.py` that would stop this.

### Impact Explanation
Scoped impact is resource-exhaustion Denial-of-Service against Claude Code's hook enforcement layer: an attacker who can plant many/large `.claude/hookify.*.local.md` files in a repository can make every subsequent `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` hook call slow (degrading the interactive session) or push it past the 10-second timeout, which — combined with the exception-swallowing fail-open pattern in the hook scripts — can silently disable rule enforcement (blocking/warning rules stop firing) rather than causing an operation to fail safely closed. This matches a resource-exhaustion / enforcement-bypass class of impact rather than direct code execution or secret disclosure.

### Likelihood Explanation
Feasibility depends entirely on the attacker being able to write files under `.claude/` in the working repository (e.g., through a merged PR, a compromised dependency/submodule, or any repo-content injection path already trusted enough to land files in the tree) — no privileged access to the Claude Code process itself is required. Once such files exist, the DoS is deterministic and repeatable on every hook invocation for as long as the session/repo state persists, since there is no caching, count limit, or size limit anywhere in the load path.

### Recommendation
In `plugins/hookify/core/config_loader.py`:
- Cap the number of files considered by `load_rules()` (e.g., `glob.glob(pattern)[:MAX_RULE_FILES]`) and emit a warning when the cap is exceeded.
- Enforce a maximum file size before reading (`os.path.getsize` check, or read with a bounded `f.read(MAX_BYTES)`) in `load_rule_file()`.
- Enforce a maximum total content size across all rule files and/or a maximum count of `conditions` per rule to bound `extract_frontmatter` parsing cost.
- Consider caching parsed rules across invocations within a session (e.g., keyed on file mtimes/hashes) to avoid full re-parse on every single tool call.
- Ensure timeout/failure of the hook process defaults to a safe, visible state (e.g., surfaced warning) rather than being silently swallowed, so DoS-induced fail-open is observable.

### Proof of Concept
Integration/fuzz test plan (pytest-style) against `plugins/hookify/core/config_loader.load_rules` and `plugins/hookify/core/rule_engine.RuleEngine.evaluate_rules`:
1. In a temp working directory, create a `.claude/` directory.
2. Test A (file-count fuzz): generate `N = 5000` files named `.claude/hookify.rule{i}.local.md`, each with minimal valid frontmatter (`name`, `enabled: true`, `event: all`, one `conditions` entry) and a short message.
3. Test B (size fuzz): generate a single `.claude/hookify.big.local.md` with a `conditions` list of `M = 50000` entries and/or a multi-megabyte message body.
4. For each case, `cd` into the temp dir, call `time.perf_counter()` around `rules = load_rules(); RuleEngine().evaluate_rules(rules, sample_input_data)`.
5. Assert wall-clock time stays under the hook timeout budget, e.g. `assert elapsed < 8.0` (leaving margin under the 10s `hooks.json` timeout), or alternatively assert that `load_rules()` raises/logs when file count or aggregate size exceeds a defined cap (once such a cap is implemented) rather than processing unboundedly.
6. Expected current behavior (pre-fix): elapsed time grows roughly linearly/unbounded with `N`/`M` with no guard rail triggered, demonstrating the missing cap; post-fix, assert a `MAX_RULE_FILES`/`MAX_FILE_SIZE` constant exists and is enforced, keeping elapsed time bounded regardless of attacker-supplied `N`/`M`.

def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.

    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()
