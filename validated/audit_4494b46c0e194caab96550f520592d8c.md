### Title
Unrecovered type-assertion panic in pointer precompile from malicious CW20/CW721/CW1155 query response - (File: precompiles/pointer/pointer.go)

### Summary
The pointer precompile's `AddCW20`, `AddCW721`, and `AddCW1155` handlers query an arbitrary, caller-specified CosmWasm contract and then blindly type-assert JSON fields from the response to `string` without checking the second `ok` return value, causing a Go runtime panic ("interface conversion: interface {} is nil, not string") when the queried contract's `token_info`/`contract_info` response omits `name`/`symbol` or returns them as non-string/null values.

### Finding Description
`AddCW20` calls `p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))` against a CW address fully controlled by the transaction sender (`args[0]`), unmarshals the JSON response into `map[string]interface{}`, then does: [1](#0-0) 
The same unchecked pattern exists in `AddCW721`: [2](#0-1) 
and `AddCW1155`: [3](#0-2) 
Any attacker can deploy a CosmWasm contract whose `token_info`/`contract_info` query handler returns JSON with `"name": null` (or omits the field, or returns a number/object), then call the `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` precompile method (address `0x000000000000000000000000000000000000100b`) pointing at that contract. The Go type assertion `formattedRes["name"].(string)` panics on a `nil` or wrong-typed interface value because the single-value form of a type assertion panics instead of returning `ok=false`.

This panic propagates out of the precompile call into `msgServer.EVMTransaction`'s deferred `recover()`, which explicitly re-panics after logging: [4](#0-3) 
Because the panic is re-raised rather than converted into a transaction error, it depends on `baseapp`'s outer `runTx` recover to avoid crashing the whole node. sei-chain's `msgServer.EVMTransaction` deliberately re-panics (rather than converting to `err`) for genuine EVM panics, which is inconsistent with the rest of message-handling and risks an unhandled panic reaching consensus-critical code paths (`DeliverTx`/OCC block execution) if the outer recovery in baseapp does not fully sanitize state before continuing, especially under OCC's parallel execution where a panicking goroutine can corrupt scheduling state.

### Impact Explanation
An unprivileged pointer-creator/contract-deployer can trigger this panic deterministically and for free (aside from gas) by pointing the precompile at a contract they control. At minimum this reliably fails/aborts every transaction attempting `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` against a malicious contract; at worst — given the explicit re-panic in `msgServer.EVMTransaction` instead of returning it as a normal `err` — it can propagate into block-processing code, causing non-deterministic node behavior or a validator crash if the panic occurs during OCC parallel execution and is not uniformly caught across all validators, which could manifest as a chain halt or state divergence.

### Likelihood Explanation
High likelihood: constructing a malicious CW20/CW721/CW1155 contract that returns a `null` or missing `name`/`symbol` field is trivial, requires no special privileges, and the precompile path (`AddCW20`/`AddCW721`/`AddCW1155`) is directly reachable by any EVM transaction sender calling the pointer precompile at `0x...100b`.

### Recommendation
Replace the unchecked single-value type assertions with the two-value form and return a proper error instead of panicking, e.g.:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("invalid or missing name field in contract query response")
}
symbol, ok := formattedRes["symbol"].(string)
if !ok {
    return nil, 0, fmt.Errorf("invalid or missing symbol field in contract query response")
}
```
Apply this in `AddCW20`, `AddCW721`, and `AddCW1155` in `precompiles/pointer/pointer.go` (and any legacy versions under `precompiles/pointer/legacy/*` still in the active precompile registry). Additionally, review `msgServer.EVMTransaction`'s decision to re-panic instead of converting non-OCC-related panics into a normal transaction error, since re-panicking any EVM-precompile-induced fault increases blast radius beyond the single failing transaction.

### Proof of Concept
1. Deploy a CosmWasm contract `Malicious` whose `ExecuteMsg`/`QueryMsg` handler for `{"token_info":{}}` (or `{"contract_info":{}}` for CW721/1155) returns raw JSON `{"name": null, "symbol": null, "decimals": 0, "total_supply": "0"}` (or simply omits `name`/`symbol`).
2. From any EVM account, send a transaction calling the pointer precompile (`0x000000000000000000000000000000000000100b`) method `addCW20Pointer(cwAddr)` (or `addCW721Pointer`/`addCW1155Pointer`) with `cwAddr` set to `Malicious`'s bech32 address.
3. `PrecompileExecutor.AddCW20` unmarshals the response and executes `formattedRes["name"].(string)`, which panics with `interface conversion: interface {} is nil, not string` since `formattedRes["name"]` is `nil`.
4. The panic is caught and re-raised by `msgServer.EVMTransaction`'s deferred recover, propagating up through `applyEVMMessage`/`EVMTransaction` and requiring `baseapp`'s top-level panic recovery to prevent broader disruption.
