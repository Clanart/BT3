### Title
`ReceivedOutput::read` accepts an arbitrary `TxOut` value decoupled from the on-chain outpoint, so downstream accounting uses a recorded amount that may exceed the actual transferred amount — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes an accounting divergence: `poolAmount` is incremented by the *declared* transfer amount rather than the *actual* amount received (fee-on-transfer). The Serai analog lives in `ReceivedOutput`: its deserializer trusts an untrusted `TxOut` — including its `value` — for a given `OutPoint`, without any binding to the real on-chain output. All downstream balance/fee math (`input_sat`, `fee()`, change computation) consumes this recorded-but-unverified value.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) parses an offset, a `TxOut`, and an `OutPoint` from untrusted bytes. There is no check that `output.value` (or even `script_pubkey`) matches the output actually present on-chain at `outpoint`. The scanner that normally produces honest `ReceivedOutput`s — `Scanner::scan_transaction` (`mod.rs:199-214`) — only matches `script_pubkey`, but a `ReceivedOutput` fed via `read` need not have come from a scanner at all.

`SignableTransaction::new` then treats the declared `output.value` as real money:

- `input_sat` sums the declared values (`send.rs:175`).
- Funding sufficiency is checked against it (`send.rs:215-221`).
- Change is computed as `input_sat - payment_sat - fee_with_change` (`send.rs:228-234`).
- The declared `TxOut`s are stored as `prevouts` and committed to in the BIP-341 sighash via `Prevouts::All` (`send.rs:253`, `send.rs:375-386`).

This is the same shape as `poolAmount += _amount`: a stored amount is assumed equal to the real transferred amount when it is not.

### Impact Explanation
A party supplying `ReceivedOutput` bytes with an inflated `value` (e.g., a coordinator or RPC-sourced serialization passed to `ReceivedOutput::read`) causes the wallet to build and threshold-sign a transaction that accounts for more input value than exists. Because BIP-341 key-spend sighashes commit to every prevout's `script_pubkey` and `value`, the resulting signatures commit to false prevout data: the signed transaction is consensus- and sighash-invalid and can never be broadcast. Funds the protocol believes were spent/allocated are not actually spendable, the signing round produces a worthless transaction, and any accounting layer crediting the declared `value` is corrupted — the exact "recorded value larger than actual holdings" consequence of the original report.

### Likelihood Explanation
Any unprivileged party who can feed bytes to `ReceivedOutput::read` (explicitly in the reachable surface: untrusted bytes to `ReceivedOutput::read`) can trigger it. It requires no threshold collusion, no leaked keys, and no malicious validator — only a dishonest supplier of scanned-output data, which is precisely the boundary between a scanner/indexer and the signing machine.

### Recommendation
Do not treat the `TxOut` inside a `ReceivedOutput` as authoritative. Either:
- Have the signing path re-fetch prevouts from a trusted source (RPC `gettxout`) keyed by `OutPoint` before computing `input_sat` and building the sighash, or
- Document and enforce at the type level that `SignableTransaction::new` only accepts `ReceivedOutput`s produced by `Scanner::scan_transaction`/`scan_block`, and make `ReceivedOutput::read` validate the output against a trusted backend before use.

### Proof of Concept
1. Craft bytes for `ReceivedOutput::read`: a valid scalar `offset`, a `TxOut` with `script_pubkey` equal to the wallet's P2TR script but `value = 10 BTC`, and an `OutPoint` whose real on-chain output is worth only `0.001 BTC`.
2. Feed this to `SignableTransaction::new` with a payment of `9 BTC` and a normal `fee_per_vbyte`.
3. `input_sat = 10 BTC` passes the `NotEnoughFunds` check, and the machine proceeds.
4. Run `multisig` → `preprocess` → `sign`: `taproot_key_spend_signature_hash(i, Prevouts::All(&prevouts), Default)` commits to the fabricated `10 BTC` prevout.
5. `complete` emits a fully-signed `Transaction` that every Bitcoin node rejects (prevout amount mismatch / nonexistent value). The declared `9 BTC` payment is unspendable; the signing round and any off-chain accounting based on `value()` are invalid.
