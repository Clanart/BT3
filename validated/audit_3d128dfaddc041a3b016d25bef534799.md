### Title
Stale `CachedPreprocess` reused across sign calls causes deterministic FROST nonce reuse and key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`preprocess_internal` derives every FROST signing nonce from a 32-byte seed stored in the `CachedPreprocesses` DB table keyed by `self.context`. The seed is written once and read back on every subsequent call, but is never deleted or rotated. `share_internal` calls `preprocess_internal` again, so every `share()` invocation for the same context rebuilds an `AlgorithmSignMachine` from the identical seed, regenerating identical nonces. Calling `share()`/`preprocess()` twice for the same context (different preprocess sets, different messages, or a retry/restart) produces two FROST signature shares with reused nonces — the exact "consumed resource still referenced" class as CVE-2021-47563 — enabling recovery of the validator's secret key share.

### Finding Description
In `preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:123-145`), the machine's RNG seed is XOR-encrypted and stored under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` only `if CachedPreprocesses::get(...).is_none()`. The stored seed is then loaded via `from_cache` → `AlgorithmMachine::seeded_preprocess`, which seeds `ChaCha20Rng::from_seed(*seed.0)` and deterministically derives `nonces` and `commitments` from it (`crypto/frost/src/sign.rs:127-141`). Because the cache entry is never cleared:

- `share_internal` (line 156) calls `self.preprocess_internal(participants).0`, reconstructing a machine with the same nonces each time it runs.
- `DkgConfirmer::share` / `preprocess` can each invoke these paths multiple times per `(b"DkgConfirmer", attempt)` context (lines 274-310), e.g., when a new set of peer preprocesses arrives or the node re-runs the attempt after restart.

FROST shares have the form `s_i = d_i + e_i·ρ_i + c·λ_i·x_i`. If the same `(d_i, e_i)` pair is used in two sessions where the peer commitments (hence binding factor `ρ` and challenge `c`) or message differ, two shares suffice to solve for `x_i`, the signer's interpolated secret share. If two such sessions complete, the two published Schnorrkel signatures reuse the same `R`, yielding direct nonce-reuse key extraction on the public signature.

### Impact Explanation
Reuse of a cached preprocess is explicitly documented as fatal: "Reusing preprocesses would enable a third-party to recover your private key share" (`spec/cryptography/FROST.md:51-55`). Here the code itself performs the reuse with no integrator misuse required — the seed persists after `sign()` consumes the machine, so a second signing under the same context deterministically reuses the nonce. Recovery of a validator's `secret_share` breaks the t-of-n security assumption: combined with publicly known group parameters, it contributes to threshold compromise / forgery of set-keys signatures.

### Likelihood Explanation
The trigger only requires `preprocess_internal` to run twice for one context while any session parameter differs (peer preprocess set, included participants, or message). Node restarts during a DKG confirmation attempt, re-gossiped preprocess sets, or retries all reach this path from data supplied by other participants' preprocess messages. No attacker-controlled secret access is needed; the shares/signatures leak the share algebraically.

### Recommendation
Delete the `CachedPreprocesses` entry after loading it in `preprocess_internal` (consume-on-read), or key the cache by a unique session nonce rather than just `context`/`attempt`, so a seed can never seed two `AlgorithmSignMachine`s.

### Proof of Concept
1. `DkgConfirmer::share(preprocesses_A, key_pair)` → `share_internal` → `preprocess_internal` loads seed S → `sign(preprocesses_A, msg)` emits share `s₁` using nonces `(d, e)` derived from `ChaCha20Rng::from_seed(S)`.
2. A second call `DkgConfirmer::share(preprocesses_B, key_pair')` (different included set or message) → `preprocess_internal` loads the *same* seed S → emits `s₂` = `d + e·ρ' + c'·λ·x`.
3. With `s₁ - s₂ = e·(ρ - ρ') + x·λ·(c - c')` and `d,e` common, plus the public preprocess commitments, an observer of both shares (or of both final signatures sharing `R`) solves for the victim's share `x`. [1](#0-0) [2](#0-1) [3](#0-2)

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
