### Title
Unbounded `callGasLimit`/`verificationGasLimit` lets any sponsored user drain the SimplexPaymaster's EntryPoint deposit via the ERC-4337 unused-gas penalty - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` is a permissionless ERC-4337 paymaster that sponsors gas for **any** user operation as long as `paymasterData` references a registered ERC-20 token the sender can pay with [1](#0-0) . The contract explicitly caps only `paymasterPostOpGasLimit` via `MAX_POST_OP_GAS_LIMIT` to bound the EntryPoint's unused-gas penalty [2](#0-1) , and this cap is enforced in `_validatePaymasterUserOp` [3](#0-2) . However, the same unused-gas penalty in EntryPoint v0.7/v0.8 is computed over the *entire* unused execution allowance — including `callGasLimit` and `verificationGasLimit`, which are packed in `accountGasLimits` and fully attacker-controlled — not just `paymasterPostOpGasLimit`. Neither `_validatePaymasterUserOp` nor `_fetchDetails` places any bound on `callGasLimit`/`verificationGasLimit`, so the mitigation the developers already implemented for one component of the penalty (`postOpGasLimit`) leaves the (typically much larger) `callGasLimit` component completely unmitigated.

### Finding Description
The token amount charged to the sponsored user is derived by OpenZeppelin's `PaymasterERC20._postOp`/`_erc20Cost`, which prices `actualGasCost` plus a fixed `_postOpCost()` cushion (30,000 gas, per the test suite) — a fixed constant unrelated to the caller-chosen `callGasLimit` [4](#0-3) [5](#0-4) . This mirrors exactly the external report's finding that `actualGasCost` (and by extension the token charge derived from it) never includes the EntryPoint's post-hoc 10% unused-execution-gas penalty.

The contract's own comment acknowledges the risk exists for `paymasterPostOpGasLimit` and caps it accordingly: *"Unbounded, the EntryPoint's unused-gas penalty is drained from this contract's deposit to a caller-chosen beneficiary; the cap keeps that penalty under the `_postOpCost` cushion the user already pays."* [2](#0-1) . But no equivalent cap exists for `callGasLimit` or `verificationGasLimit`. Since any unprivileged user can submit a UserOperation naming `SimplexPaymaster` as sponsor (paying with any registered token, even a trivially small permit/allowance amount), they can set `callGasLimit` to a very large value while making `callData` cheap/no-op, causing most of the reserved execution gas to go unused. Under the ERC-4337 v0.7+ penalty mechanism, 10% of that unused gas is charged to the paymaster's EntryPoint deposit — a value the paymaster never recoups from the user, since the token charge is computed only from `actualGasCost` + the fixed `_postOpCost()` cushion, not from the reserved-but-unused `callGasLimit`.

### Impact Explanation
This falls squarely within the "stealing or loss of funds" and "paymaster balance must move exactly once and only to the rightful beneficiary and amount" bounty categories. An unprivileged attacker (any address able to build a UserOperation, no relayer/prover/governance compromise needed) can repeatedly drain the paymaster's EntryPoint-held native deposit — which is funded by markup surplus recycled via `swapAndDeposit`/governance — with operations that cost the paymaster far more than the fixed `_postOpCost()` cushion the attacker pays in tokens.

### Likelihood Explanation
High. The paymaster is explicitly designed to be "fully onchain, permissionless" for any user paying with a registered stablecoin [1](#0-0) . Constructing a UserOperation with an inflated `callGasLimit` and minimal `callData` requires no special access, no relayer/prover collusion, and no governance action — only knowledge of the paymaster address and a small token allowance/permit (the docs note "$5" is the recommended authorization amount) [6](#0-5) .

### Recommendation
Cap `callGasLimit` and `verificationGasLimit` (extracted from `userOp.accountGasLimits`) in `_validatePaymasterUserOp`, the same way `paymasterPostOpGasLimit` is already bounded by `MAX_POST_OP_GAS_LIMIT`. Alternatively/additionally, charge the user in `_postOp`/`_fetchDetails` for the worst-case 10% unused-execution-gas penalty based on the difference between the reserved gas limits and actually-used gas, so the sponsored user — not the paymaster — bears the cost of oversized limits they set.

### Proof of Concept
1. Attacker (any address) obtains a small allowance/permit for a registered token (e.g., USDC) to `SimplexPaymaster`, satisfying `_fetchDetails`'s registered/active token check [7](#0-6) .
2. Attacker submits a UserOperation naming `SimplexPaymaster` as sponsor, with `paymasterPostOpGasLimit` set at/under `MAX_POST_OP_GAS_LIMIT` (100,000, passes the check at lines 347-350) but with `callGasLimit` set to a very large value (bounded only by the block gas limit / bundler acceptance) while `callData` executes a trivial no-op call.
3. `_validatePaymasterUserOp` accepts the operation since it only checks `postOpGasLimit` [8](#0-7) , and `_fetchDetails` returns a fixed pricing formula unrelated to `callGasLimit` [7](#0-6) .
4. EntryPoint executes the cheap call, leaving most of `callGasLimit` unused, and — per ERC-4337 v0.7+ semantics — deducts 10% of that unused gas from the paymaster's deposit as a penalty, charged after `_postOp` has already fixed the user's token payment.
5. Repeating this operation drains the paymaster's EntryPoint deposit while the attacker pays only the fixed, small `_postOpCost()`-based token amount.

Note: the exact OpenZeppelin `PaymasterERC20`/`PaymasterCore` `_postOp` and `_erc20Cost` implementation is not vendored in this repository's index, so the precise arithmetic of `actualGasCost` accounting was inferred from `SimplexPaymaster.sol`'s NatSpec and the Foundry test's `POST_OP_COST` constant rather than directly read; this does not affect the core finding, since the paymaster's own comments confirm the unused-gas-penalty risk model and confirm only `paymasterPostOpGasLimit` is mitigated.

    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }

    /// @notice Estimate the token cost for a given gas amount and fee, mirroring
    ///         PaymasterERC20._erc20Cost (including its postOp gas cushion).
    function estimateTokenCost(
        address token,
        uint256 gasAmount,
        uint256 maxFeePerGas
    ) external view returns (uint256) {
        TokenConfig memory cfg = tokenConfigs[token];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(token);

        uint256 weiCost = gasAmount * maxFeePerGas + _postOpCost() * maxFeePerGas;
        return (weiCost * _tokenPrice(cfg)) / _tokenPriceDenominator();
    }
