### Title
Attacker-controlled interpolation selector/coefficients in `ThresholdKeys::read` re-weight the victim's real secret share, enabling key-share recovery - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2021-44486 is a bug where crafted input manipulates a function pointer used inside `op_write`, hijacking the operation performed on attacker-influenced data. The Serai analog lives in `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`): a single attacker-controlled byte selects the interpolation "function" applied to the secret share (`0` → `Interpolation::Constant` with a fully attacker-supplied coefficient vector, `1` → `Interpolation::Lagrange`), with no integrity check binding the choice to the key material. This is exactly the reported class — untrusted bytes choosing the operator applied to sensitive data — and because the serialized `secret_share` is left untouched, mutating only the interpolation selector/coefficients lets an attacker re-weight a victim's genuine share by a known constant and recover it from produced signatures.

### Finding Description
`ThresholdKeys::write`/`read` serialize `params`, an interpolation tag, the constant-interpolation coefficients (when tag = 0), the secret share, and the verification shares, with no MAC or hash binding the fields together (`crypto/dkg/src/lib.rs:538-561`, `574-632`). On deserialization:

- The tag byte at `crypto/dkg/src/lib.rs:604-616` picks the interpolation method.
- For `Interpolation::Constant`, `n` scalars are read verbatim from the stream and become `c` (`crypto/dkg/src/lib.rs:607-613`).
- `interpolation_factor` returns `c[i-1]` directly for `Constant` (`crypto/dkg/src/lib.rs:226-249`).
- `ThresholdKeys::new` only requires `t == n` for `Constant` (`crypto/dkg/src/lib.rs:367-374`) and computes `group_key` as `sum over i in 1..=t of verification_shares[i] * c[i-1]` (`crypto/dkg/src/lib.rs:376-378`).
- `view()` computes the signing secret as `interpolation_factor(i) * scalar * secret_share` (`crypto/dkg/src/lib.rs:494-498`).

An attacker who modifies a victim's serialized `ThresholdKeys` blob (a reachability surface explicitly in scope for untrusted bytes fed to `ThresholdKeys::read`) can:

1. Keep the victim's real `secret_share` and `verification_shares` fields intact.
2. Flip the interpolation tag to `0` (Constant) and supply attacker-chosen coefficients — e.g., `c_j = 1` for the victim's index `j`, `t = n` so `ThresholdKeys::new` accepts it, adjusting the verification shares however needed so the resulting `group_key` is an attacker-chosen key `A` (or simply leaving them and signing under the computed key).
3. The victim now signs messages; each Schnorr share is `s = nonce + challenge * (c_j * share)` where `c_j` is known to the attacker (`crypto/frost/src/algorithm.rs:201-211` computes `sign_share` from `params.secret_share()`, i.e., the interpolated share).

### Impact Explanation
Key-share recovery (an accepted impact class). With two completed signatures `(R1, s1)`, `(R2, s2)` under the mutated view, the attacker computes `share' = (s1 - s2) / (challenge1 - challenge2)` = `c_j * share`, then `share = share' * c_j^{-1}` — recovering the victim's real threshold secret share. Repeating/coordinating across participants recovers the full group private key. Root cause is identical in shape to the CVE: an untrusted-input-selected operator is applied to security-critical data without integrity protection.

### Likelihood Explanation
Exploitation requires the attacker to supply or tamper with the serialized `ThresholdKeys` a victim loads (e.g., key material passed through untrusted channels or modifiable storage); the format itself performs no authenticity check, so any such path is fully exploitable. It cannot be mounted purely from network signing messages (preprocesses/shares), which bounds the likelihood below that of a purely remote attack — Medium likelihood, High impact.

### Recommendation
Authenticate the serialized `ThresholdKeys` blob (e.g., MAC/signature over the whole encoding, or store it alongside a commitment that is verified on `read`), and/or derive and store the `group_key` at DKG time and re-verify that `ThresholdKeys::new` reproduces it before signing. At minimum, reject `Interpolation::Constant` on `read` unless the caller explicitly expects constant interpolation (e.g., MuSig-produced keys), so a tag flip is detectable.

### Proof of Concept
```rust
// Victim has ThresholdKeys<C> with params (t, n, i), Lagrange interpolation,
// secret share `x_i`, verification shares V.
// Attacker obtains serialized blob = ThresholdKeys::serialize() and rewrites it:

let mut blob = honest_keys.serialize().to_vec();
// Layout: id_len(4) || C::ID || t(2) || n(2) || i(2) || interp_tag(1) || ...
// Overwrite t with n so Constant interpolation is accepted,
// set interp_tag = 0, and splice in n attacker-chosen coefficients c_j:
//   c_j = k (known nonzero scalar) for the victim's index j.
// The secret_share and verification_shares regions are left as-is
// (or verification_shares adjusted so group_key is attacker-favorable).

let forged = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// forged loads: secret_share = real x_i, interpolation = Constant(c).

// Victim signs two messages with forged.view(included) containing i.
// Each signature share is s = d + e*rho + challenge * (c_j * x_i).
// Attacker observes (R1, s1), (R2, s2), computes challenges c1, c2 itself:
let share_weighted = (s1 - s2) * (c1 - c2).invert().unwrap(); // = c_j * x_i
let x_i_recovered = share_weighted * c_j.invert().unwrap();   // victim's real share
```
