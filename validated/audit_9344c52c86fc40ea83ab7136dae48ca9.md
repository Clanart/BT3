## Analysis

The Lyra report's broken invariant is: an **internal accounting value** (`lockedCollateral.base`) is allowed to drift from the **actual on-chain balance** (sETH balance) because a code path can bail out early without reconciling the two, and downstream logic keeps trusting the stale internal value for consequential decisions.

The closest analog in GitHub Desktop is the same class of bug applied to **partial/line-level commit selection**: Desktop caches a user's line-selection (`DiffSelection`, indexed by absolute diff-line positions) against one diff snapshot, but re-derives a **fresh** diff at staging time and blindly re-applies the old index-based selection to it, without verifying the two diffs still agree on hunk/line layout.

### Title
Stale line-index `DiffSelection` re-applied to a freshly regenerated diff silently corrupts partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines/hunks of a file, Desktop stores the selection as a set of **absolute line indices** into the diff that was on screen at selection time. At commit time, Desktop discards the index and regenerates a **brand new diff from disk**, then reapplies the old index-based selection to that new diff to build the patch that is `git apply --cached` into the index. If the working-tree file changed between when the selection was made/preserved and when the commit executes, the indices no longer point at the same logical lines, so the wrong lines get silently staged and committed.

### Finding Description
`stageFiles` resets the index and, for any file with a partial selection, calls `applyPatchToIndex`: [1](#0-0) 

`applyPatchToIndex` fetches a **new** diff of the file straight from the working tree and then builds the patch via `formatPatch`, using the file's cached `selection`: [2](#0-1) 

`formatPatch` decides what to keep purely by asking `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is `hunk.unifiedDiffStart + lineIndex` computed against this **new** diff: [3](#0-2) 

The `selection` object itself, however, was built against a diff that could be older. When status is refreshed, `updateChangedFiles` deliberately **carries the old `DiffSelection` object forward unchanged** onto the new `WorkingDirectoryFileChange`: [4](#0-3) 

Selectable-line pruning only happens for the single file currently open in the diff viewer, and only when that specific diff is re-fetched for *display* purposes: [5](#0-4) 

That reconciliation is disconnected from the diff independently re-fetched inside `applyPatchToIndex` at commit time — there is no shared identity/hash check between "the diff the selection indices refer to" and "the diff the patch will be built against." `_commitIncludedChanges` simply takes whatever `workingDirectory.files` currently holds and passes it straight to `createCommit` → `stageFiles`: [6](#0-5) [7](#0-6) 

So the exact corrupted value is the `DiffSelection`'s set of **absolute line indices**, treated as authoritative and portable across diff snapshots, when it is only valid for the specific diff it was derived from.

### Impact Explanation
If the underlying file changes between the time a partial selection is made (or silently carried over by a background status refresh) and the time the user presses Commit — e.g. because of an ordinary `pull`/fetch-driven working-tree update, an external editor autosave, or a repository-shipped tool (formatter/lint-staged/build step) touching the file — the index positions the app uses to decide "selected vs. not selected" no longer correspond to the same logical lines in the freshly generated diff. `git apply --cached` will then stage a hunk whose selected/unselected lines do not match what the user saw and clicked in the UI. The resulting commit (and any subsequent push) silently contains different content than the user intended and approved, with no error or warning surfaced by Desktop — a direct instance of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
No attacker action beyond normal, expected repository content/behavior is required: any ordinary background status refresh, pull, or externally-driven file modification while a partial selection is pending is enough to desynchronize the cached indices from the on-disk diff. `updateChangedFiles` is invoked on every status poll, so the window in which stale indices can be silently carried forward is continuously present during normal use, not a rare race.

### Recommendation
Do not let `applyPatchToIndex`/`formatPatch` reuse line-index selections against a diff object different from the one that produced them. Persist (or hash) the diff each `DiffSelection` was computed against, and before staging, re-diff the file and re-validate/re-map the selection (as is already partially done in `updateChangesWorkingDirectoryDiff` via `withSelectableLines`) for *every* file being committed — not just the one currently open in the diff viewer — refusing or re-prompting the user if the underlying diff has materially changed since the selection was made.

### Proof of Concept
1. Open a repository in Desktop; modify `file.txt` producing several hunks.
2. In the Changes view, select only specific lines within one hunk (partial `DiffSelection` built from diff `D1`).
3. Without touching the Changes tab, let the working tree change underneath (e.g., `git pull` brings in an upstream change to the same file, or an external process/editor auto-formats it), producing diff `D2` with shifted line offsets. Desktop's periodic status refresh runs `updateChangedFiles`, which reuses the old selection unchanged (`app/src/lib/stores/updates/changes-state.ts:56`).
4. Click Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches a fresh diff (`D2`) and applies the old index-based selection from step 2 via `formatPatch`'s `isSelected(absoluteIndex)` check (`app/src/lib/patch-formatter.ts:157`).
5. Inspect the resulting commit: the staged hunk content corresponds to different lines than what was visually selected in step 2, demonstrating silent corruption of the committed content.
