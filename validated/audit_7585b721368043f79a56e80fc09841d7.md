### Title
Schnorr Signature Verified After Expensive Pre-Checks in Aggregator `optimistic_payout` — (`File: core/src/rpc/aggregator.rs`)

---

### Summary

The aggregator's public `optimistic_payout` gRPC endpoint performs multiple expensive operations — including a verifier-compatibility broadcast, two Bitcoin RPC calls, two database queries, and a full `TxHandler` construction — before verifying the caller-supplied Schnorr signature. Because the aggregator enforces no client-certificate restriction, any TLS peer can trigger this work repeatedly with a syntactically valid but cryptographically invalid signature, exhausting aggregator and verifier resources and denying service to the optimistic-payout withdrawal flow.

---

### Finding Description

`AggregatorServer::optimistic_payout` in `core/src/rpc/aggregator.rs` executes the following sequence: [1](#0-0) 

1. **Line 1029** — `check_compatibility_with_actors(CompatibilityCheckScope::VerifiersOnly)`: fans out gRPC calls to every configured verifier. [2](#0-1) 

2. **Lines 1033–1042** — `rpc.is_utxo_spent(&input_outpoint)`: a live Bitcoin-node RPC call. [3](#0-2) 

3. **Lines 1057–1071** — two PostgreSQL queries (`get_move_to_vault_txid_from_citrea_deposit`, `get_withdrawal_utxo_from_citrea_withdrawal`). [4](#0-3) 

4. **Lines 1074–1088** — `rpc.get_txout_from_outpoint(&input_outpoint)`: a second Bitcoin-node RPC call. [5](#0-4) 

5. **Lines 1112–1121** — `create_optimistic_payout_txhandler(...)` and `calculate_pubkey_spend_sighash(...)`: full Taproot transaction construction and sighash computation.

Only **after** all of the above does the handler verify the caller's Schnorr signature: [6](#0-5) 

The aggregator server is explicitly documented as not enforcing client certificates:

> "The aggregator does not enforce client certificates but does use TLS for encryption." [7](#0-6) 

This is confirmed in the server setup: verifier/operator servers wrap their service in `OnlyAggregatorAndSelf`, but the aggregator uses `Noop`: [8](#0-7) 

The `aggregator_verification_address` field — the only application-layer auth guard — is `Option<Address>` and is absent from the `optimistic_payout` handler entirely (it is only checked in the verifier's `sign_optimistic_payout` and the operator's `withdraw` RPC, and even there only when the operator is configured with it): [9](#0-8) 

---

### Impact Explanation

An attacker who can reach the aggregator's TLS port (no client certificate required) can:

1. Observe on-chain data to obtain a valid `deposit_id`, `input_outpoint`, `output_script_pubkey`, and `output_amount` for any live withdrawal.
2. Craft a request with a syntactically valid but cryptographically invalid Schnorr signature.
3. Flood the endpoint up to the configured rate limit (default `ratelimit_req_count = 1000` per 60 s).

Each request forces the aggregator to fan out to all N verifiers, issue two Bitcoin-node RPC calls, execute two DB queries, and build a full `TxHandler` — all before the signature check rejects the request. With N=4 verifiers and 1000 req/min, this generates ≥4 000 verifier gRPC calls per minute from a single attacker connection, saturating both the aggregator and the verifier pool. Legitimate `optimistic_payout` requests are queued behind or dropped, stalling the optimistic withdrawal flow and effectively locking bridged BTC in the vault until the attack stops. [10](#0-9) 

---

### Likelihood Explanation

- The aggregator's gRPC port is reachable by any party that can establish a TLS connection (no mTLS client-cert gate).
- All inputs needed to craft a plausible-looking request (deposit ID, UTXO outpoint, script pubkey, amount) are publicly visible on-chain and in the Citrea bridge contract.
- The only cost to the attacker is TLS handshake overhead; no on-chain transaction or privileged key is required.
- The default rate limit (1 000 req/60 s) is high enough to sustain a damaging load.

---

### Recommendation

Move the Schnorr signature verification to the **earliest possible point** in `optimistic_payout`, before any Bitcoin RPC call, DB query, or verifier fan-out. Concretely:

1. After parsing `input_outpoint` and `output_script_pubkey`, immediately fetch the prevout (one RPC call) and verify the Schnorr signature against the sighash of the minimal payout transaction.
2. Only after the signature is confirmed valid should the handler proceed to `check_compatibility_with_actors`, DB lookups, and full `TxHandler` construction.

Additionally, consider enforcing `aggregator_verification_address` as a **mandatory** field rather than `Option`, so that every `optimistic_payout` request must carry a valid ECDSA authorization from the aggregator key before any work is done. [11](#0-10)

### Proof of Concept

```
# Attacker has TLS access to the aggregator (no client cert needed).
# Obtain valid withdrawal params from on-chain / Citrea bridge contract:
#   deposit_id = 42
#   input_outpoint = <txid>:<vout>  (the withdrawal UTXO)
#   output_script_pubkey = <valid P2TR script>
#   output_amount = <bridge_amount - anchor>

# Craft a request with a random (invalid) 64-byte Schnorr signature.
# Send at the rate limit: 1000 req / 60 s.

for i in $(seq 1 1000); do
  grpcurl -d '{
    "withdrawal": {
      "withdrawal_id": 42,
      "input_signature": "<64 random bytes as hex>",
      "input_outpoint_txid": "<txid bytes>",
      "input_outpoint_vout": 0,
      "output_script_pubkey": "<valid P2TR script bytes>",
      "output_amount": 999900000
    }
  }' <aggregator_host>:<port> clementine.ClementineAggregator/OptimisticPayout &
done
wait
```

Each request causes the aggregator to:
- Fan out to all verifiers via `check_compatibility_with_actors` (line 1029)
- Issue `is_utxo_spent` to bitcoind (line 1035)
- Query PostgreSQL twice (lines 1059, 1065)
- Issue `get_txout_from_outpoint` to bitcoind (line 1076)
- Build a full `TxHandler` (line 1112)
- Compute a Taproot sighash (line 1120)
- **Then** fail at `verify_schnorr` (line 1125)

The aggregator and verifier pool are saturated; legitimate withdrawal requests time out. [11](#0-10) [12](#0-11)
