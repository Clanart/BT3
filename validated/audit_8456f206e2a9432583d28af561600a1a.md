### Title
Cached FROST preprocess seed is reused across every signing invocation for a DKG-confirmation context, enabling nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a 32-byte `CachedPreprocess` seed keyed only by the context tuple `(b"DkgConfirmer", attempt)`. Once written, the seed is never deleted, rotated, or consumed. Every subsequent call to `share_internal` / `complete` rebuilds the identical FROST nonces via `SignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)`. If the coordinator ever produces a share under the same context with a different message (different `KeyPair`) or a different preprocess set, the same nonce pair `(d, e)` is reused across distinct binding factors/challenges, which the FROST spec and the code's own documentation state enables third-party recovery of the signer's private key share.

### Finding Description
The cached seed lifecycle in `preprocess_internal`:

- If no entry exists, a fresh preprocess is generated and only `machine.cache()` (the seed) is stored, XOR-encrypted, under `CachedPreprocesses[context]`. [1](#0-0) 
- On every call — including every `share_internal` and `complete` — the same seed is decrypted and fed to `AlgorithmSignMachine::from_cache`, which deterministically regenerates the same nonces and commitments. [2](#0-1) 
- `from_cache` → `seeded_preprocess` uses `ChaCha20Rng::from_seed(*seed.0)`, so nonce generation is fully deterministic given the seed. [3](#0-2) 
- The library's own contract states a cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share," yet the caller never removes the entry after first use. [4](#0-3) 

The divergence sources:

- `DkgConfirmer::share` is invoked from `generated_key_pair`, which unconditionally overwrites `DkgKeyPair` with whatever `key_pair` the processor reports — there is no `is_none()` guard — and then signs `set_keys_message(set, removed, key_pair)` with the cached nonces. [5](#0-4) 
- `DkgConfirmer::complete` later calls `share_internal` again under the same context, reading `key_pair` back from `DkgKeyPair` — if `generated_key_pair` ran a second time with a different `key_pair` between `share` and `complete` (no guard prevents it), `complete` signs a different message with the same `(d, e)` nonces. [6](#0-5) 
- The signed message varies with `key_pair` and `removed`, and the effective nonce also varies with the binding factor `rho`, which commits to `hash_msg(msg)` and the preprocess set. [7](#0-6) 

Two shares `s_i = d + e·rho_i + c_i·λ_i·x` produced with the same `(d, e)` under different `rho`/`c` pairs give the attacker linear equations in `(d, e, x)`; with as few as three distinct shares under one reused seed, the private key share `x` is fully recoverable. Even two distinct-message shares reduce the secret to a solvable system combined with the published commitments.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret share on Ristretto directly compromises the validator-set signing key used to confirm DKG key pairs (`set_keys_message`). The confirmation signature is a Schnorrkel signature produced by `share_internal` over attacker-influenced preprocess data (`ConfirmationNonces` originate from `Transaction::DkgShares` published by all validators). Reuse of `(d, e)` across two different signed messages is the classic Schnorr nonce-reuse key-recovery primitive, the exact failure the `CachedPreprocess` documentation warns against.

### Likelihood Explanation
The unsafe condition is latent rather than guaranteed: within a single happy-path attempt, `share()` and `complete()` sign the same message, producing identical shares (harmless). The hazard materializes whenever `generated_key_pair` runs more than once for the same `attempt` with a different `KeyPair` — for example when the processor regenerates or re-reports a key pair (the DB write is an unconditional `set`, so nothing detects the second report), or when local state divergence produces a different `set_keys_message`. Because the seed persists indefinitely in `CachedPreprocesses`, any such second signing silently reuses the nonces. The design relies entirely on callers never re-invoking signing for a context, an invariant enforced nowhere in code.

### Recommendation
Delete (or mark consumed) the `CachedPreprocesses` entry the first time a share is produced for a context — e.g., a `Consumed`/single-use flag checked in `preprocess_internal` that panics on second use. Additionally, guard `generated_key_pair` so `DkgKeyPair::set`/`KeyToDkgAttempt::set` refuse a second, differing `key_pair` for the same `(genesis, attempt)` instead of overwriting. Alternatively, bind the message into the seed derivation so distinct messages cannot share nonces.

### Proof of Concept
Conceptual reproduction against `DkgConfirmer`:

```rust
// Attempt N: processor reports key_pair K1
generated_key_pair(txn, key, spec, &K1, N);       // share1 = d + e*rho1 + c1*λ*x  (seed S cached)

// Same attempt: processor re-reports with a different pair K2
// (DkgKeyPair::set overwrites unconditionally; no guard exists)
generated_key_pair(txn, key, spec, &K2, N);       // share2 = d + e*rho2 + c2*λ*x  (seed S reused)

// Later: tributary finalizes DkgConfirmed for attempt N
// complete() re-derives seed S again and signs msg(K2 or K1') -> share3
```

With `share1` and `share2` public on the tributary (Label::Share data is published), plus the broadcast preprocess commitments `D = d·G`, `E = e·G`, an observer solves:

```
share1 - share2 = e·(rho1 - rho2) + (c1 - c2)·λ·x
```

Each additional distinct-message share under the same attempt adds an equation in the same three unknowns `(d, e, x)`; three shares yield a unique solution for the signer's private key share `x`. The root cause is that `CachedPreprocesses::set` is write-once-read-forever: [8](#0-7)

pub fn generated_key_pair<D: Db>(
  txn: &mut D::Transaction<'_>,
  key: &Zeroizing<<Ristretto as Ciphersuite>::F>,
  spec: &TributarySpec,
  key_pair: &KeyPair,
  attempt: u32,
) -> Result<[u8; 32], Participant> {
  DkgKeyPair::set(txn, spec.genesis(), attempt, key_pair);
  KeyToDkgAttempt::set(txn, key_pair.0 .0, &attempt);
  let preprocesses = ConfirmationNonces::get(txn, spec.genesis(), attempt).unwrap();
  DkgConfirmer::new(key, spec, txn, attempt)
    .expect("claiming to have generated a key pair for an unrecognized attempt")
    .share(preprocesses, key_pair)
}
