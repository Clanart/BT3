## Finding: Spoofed `WWW-Authenticate` header from an attacker-controlled remote can force a false "GitHub Enterprise" classification and trigger an OAuth sign-in bound to that attacker host

### Title
Untrusted `WWW-Authenticate` header from a git remote is trusted to classify a host as GitHub Enterprise, bypassing the real verification check - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Uniswap report's root cause is that an unvalidated/unauthorized action (spending tokens) is taken on the basis of an assumption that was never actually enforced (approval), so an untrusted external interaction (the router call) breaks a security invariant. The closest Desktop analog is `getEndpointKind` in `trampoline-credential-helper.ts`, which classifies a remote host as `'enterprise'` (i.e., "this is GitHub, safe to treat with GitHub trust semantics") based on an attacker-controlled `WWW-Authenticate` HTTP header echoed back by the remote/proxy, instead of relying on the actual verification path (`isGitHubHost`).

### Finding Description
`getEndpointKind` is used by the credential trampoline to decide how a git host's credential request should be handled: [1](#0-0) 

The comment explains the design intent explicitly: Git forwards any `WWW-Authenticate` header it captured from the remote server to the credential helper, and Desktop treats a header containing `realm="GitHub"` as a "happy path" to conclude the host is GitHub Enterprise, **without making its own verification request** (`isGitHubHost`) — that real check is only reached if the header is absent: [2](#0-1) 

This header is fully attacker-controlled: any git server, proxy, or MITM the client is fetching/cloning/pushing to can set `WWW-Authenticate: realm="GitHub"` on its 401 response. Just like `sellProfits` assumed tokens were already approved when they were not, `getEndpointKind` assumes the header reflects a genuinely-verified trust classification when it is merely unauthenticated attacker input relayed by dugite/git.

Once `endpointKind !== 'generic'` is returned, `getCredential` takes the GitHub-trust branch: [3](#0-2) 

If no existing Desktop account matches that endpoint, the code calls `ui.promptForGitHubSignIn(endpoint)`, presenting the user a "Sign in to GitHub" flow scoped to the attacker's arbitrary remote URL, rather than falling back to the generic (plain username/password) credential path that would be used for a non-GitHub host. Any account produced by that flow is then merged into the credential and handed back to git for that endpoint via `credWithAccount`: [4](#0-3) 

I was not able to fully trace `promptForGitHubSignIn`'s internal OAuth/device-flow request targets in `trampoline-ui-helper.ts` within the available investigation budget, so I cannot confirm with certainty whether the resulting sign-in network calls are made against the attacker's endpoint (in which case this is a direct token-exfiltration/phishing vector) or are hard-scoped to github.com regardless of the spoofed classification (in which case the impact is limited to a misleading trust-classification UI/state issue). This should be verified directly against `trampoline-ui-helper.ts` and the enterprise sign-in flow before treating the OAuth-leak scenario as confirmed.

### Impact Explanation
At minimum, this allows any git server the user interacts with (clone/fetch/push/pull, including through an interposed proxy) to force Desktop into believing that host is a trusted GitHub Enterprise host, causing:
- A GitHub sign-in prompt to be shown for a host that is not actually GitHub, which the user may complete, potentially binding a real account/token to that (attacker) endpoint for future automatic credential injection by `findGitHubTrampolineAccount` origin matching.
- If the enterprise sign-in flow's requests are not host-pinned to a verified GitHub origin, unauthorized OAuth/account binding and credential exfiltration to the attacker's endpoint (matching the "unauthorized OAuth or account binding" / "credential exfiltration" impact classes explicitly listed as in-scope).

### Likelihood Explanation
The trigger requires nothing more than an attacker-controlled or MITM'd git remote responding with a crafted `WWW-Authenticate` header during a normal git HTTPS operation — no local access, no leaked credentials, no social engineering step beyond the user's ordinary act of cloning/fetching from or pushing to a remote they don't fully trust (or being on a network path with a malicious proxy). This satisfies the "attacker controls a git remote/proxy response" precondition in the given valid-impact scope.

### Recommendation
Do not use the unauthenticated `WWW-Authenticate` header content as sufficient evidence to classify a host as GitHub/Enterprise. Always fall through to the authoritative `isGitHubHost(endpoint)` check (or an equivalent verified lookup) before granting `'enterprise'` trust classification, and ensure that any sign-in/OAuth flow triggered as a result is verified to only ever communicate with confirmed GitHub origins, never with the raw attacker-supplied endpoint.

### Proof of Concept
1. Set up a malicious git HTTPS server (or a MITM proxy) for a repo URL, e.g. `https://evil.example.com/repo.git`.
2. Configure the server to respond to Git's credential probe with HTTP 401 and header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, clone or add this remote and trigger a fetch/push.
4. Observe that `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:153-166`) classifies the host as `'enterprise'` purely from the spoofed header, and, absent a stored account for that endpoint, Desktop calls `ui.promptForGitHubSignIn('https://evil.example.com')` instead of treating it as a generic host.
5. Further verification is needed (in `trampoline-ui-helper.ts`) to confirm whether the resulting sign-in flow performs any network requests against the attacker endpoint itself, which would confirm direct credential/token exfiltration.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
