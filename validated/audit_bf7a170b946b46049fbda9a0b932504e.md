### Title
PedPoP emits blame proofs (revealing the ECDH shared key) for messages whose proof-of-possession was never verified - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
Analogous to the Ranger "unauthenticated download exposes protected data" class: `KeyMachine::calculate_share` returns an `EncryptionKeyProof` — which reveals the recipient's ECDH shared key for a message — via the non-canonical-scalar error path *before* the batch-verified Schnorr proof-of-possession on that message is ever checked. An unauthenticated sender can therefore obtain a decryption key for a message they cannot prove possession of, including a replayed copy of another participant's per-message key — the exact attack the PoP exists to prevent.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` does three things: (1) queues the message's PoP (`msg.pop`) into a deferred `BatchVerifier`, (2) computes `key = ecdh(&self.enc_key, msg.key)`, and (3) returns an `EncryptionKeyProof { key, dleq }` proving that `key` is the correct shared key between the recipient's registered `enc_key` and `msg.key` [1](#0-0) . The PoP is only enforced later, when the caller runs `batch.verify_with_vartime_blame()` [2](#0-1) .

However, in `KeyMachine::calculate_share`, the decrypted bytes are parsed as a scalar *inside the loop, before the batch is verified*: if `C::F::from_repr` fails, the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` immediately [3](#0-2) . The `blame` is the `EncryptionKeyProof` containing `proof.key = enc_priv_recipient * msg.key` — sufficient to decrypt anything encrypted to that ECDH pair, since `cipher` derives the ChaCha20 key solely from `context` and the shared point [4](#0-3) .

The code itself documents this threat model: without the PoP, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X ... they'd reveal bX, revealing Alice's message to Bob" [5](#0-4) . The early-return path bypasses the PoP check entirely, resurrecting this attack.

### Impact Explanation
`blame` proofs are designed to be published for adjudication (e.g., to `AdditionalBlameMachine`, explicitly usable by non-participants) [6](#0-5) . By replaying a victim sender's `key` point `X` (observed on the authenticated-but-not-confidential channel) with a ciphertext crafted to be a non-canonical scalar, the attacker causes the victim recipient to emit a publicly-verifiable `EncryptionKeyProof` revealing `bX` — decrypting the honest sender's actual secret share to that recipient. Repeating across senders targeting one recipient recovers that recipient's full FROST key share; doing so for `t` recipients recovers the group secret key. This is key-share recovery reachable by any protocol participant with no proof of possession.

### Likelihood Explanation
Any DKG participant (or anyone able to send a `EncryptedMessage<C, SecretShare>` attributed to a participant index in the caller's `shares` map) can perform this with public observations only: copy an observed `key` field, fill the share bytes with a non-canonical encoding (e.g., all `0xff`), and a dummy `pop`. No discrete logs, forgery, or collusion is needed — the only requirement is that the error's `blame` field be propagated, which is its designed purpose.

### Recommendation
Verify the PoP before using or releasing decryption output: in `calculate_share`, do not attach `blame` on the scalar-parse path unless the queued PoP for that `from` has passed batch verification — e.g., split PoP verification into its own batch that is verified before decryption results are consumed/returned, or verify `msg.pop` synchronously inside `Encryption::decrypt` and withhold the `EncryptionKeyProof` on failure (returning `InvalidShare { blame: None }` as for decryption failures). Additionally, bind the PoP challenge to the intended recipient so replayed keys are rejected even in deferred verification.

### Proof of Concept
1. Honest Alice runs `generate_secret_shares`, producing `EncryptedMessage { key: X, pop, msg }` to Bob over an observable (authenticated, non-confidential) channel.
2. Eve, a fellow participant, sends Bob `EncryptedMessage { key: X, pop: <arbitrary valid-encoding sig>, msg: SecretShare([0xff; 32]) }` as her share.
3. Bob's `calculate_share` calls `encryption.decrypt`: it *queues* Eve's invalid PoP, computes `key = bX` (Bob's enc_priv times X), and returns `EncryptionKeyProof { key: bX, dleq }`.
4. `C::F::from_repr([0xff; 32])` fails → `InvalidShare { participant: Eve, blame: Some(proof) }` is returned before `batch.verify_with_vartime_blame()` runs, so the invalid PoP is never detected.
5. The published `blame.key = bX` feeds `cipher(context, bX)`, which decrypts Alice's real `msg` — recovering Alice's secret share to Bob without Eve ever proving possession of `X`.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}

  pub(crate) fn decrypt<R: RngCore + CryptoRng, I: Copy + Zeroize, E: Encryptable>(
    &self,
    rng: &mut R,
    batch: &mut BatchVerifier<I, C::G>,
    // Uses a distinct batch ID so if this batch verifier is reused, we know its the PoP aspect
    // which failed, and therefore to use None for the blame
    batch_id: I,
    from: Participant,
    mut msg: EncryptedMessage<C, E>,
  ) -> (Zeroizing<E>, EncryptionKeyProof<C>) {
    msg.pop.batch_verify(
      rng,
      batch,
      batch_id,
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    );

    let key = ecdh::<C>(&self.enc_key, msg.key);
    cipher::<C>(self.context, &key).apply_keystream(msg.msg.as_mut().as_mut());
    (
      msg.msg,
      EncryptionKeyProof {
        key,
        dleq: DLEqProof::prove(
          rng,
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &self.enc_key,
        ),
      },
    )
  }
