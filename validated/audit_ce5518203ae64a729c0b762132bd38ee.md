### Title
Tokenfactory `AllowList` and `BlockedAddr` Restrictions Bypassed via Bank Precompile `sendNative` - (File: precompiles/bank/bank.go)

### Summary
The bank precompile at `0x1001` exposes two EVM-callable transfer methods: `send` and `sendNative`. `send` is routed through the Cosmos bank module's `MsgServer.Send`, which enforces `IsInDenomAllowList` (tokenfactory allow-list restriction) and `BlockedAddr` checks before transferring. `sendNative`, used to move `usei`/wei value attached to an EVM call, calls `p.bankKeeper.SendCoinsAndWei()` directly on the `BankKeeper`, skipping both checks entirely.

### Finding Description
`precompiles/bank/bank.go`'s `send` method builds a `banktypes.MsgSend` and executes it via `p.bankMsgServer.Send(...)`: [1](#0-0) 

`sei-cosmos/x/bank/keeper/msg_server.go`'s `Send` handler enforces the allow-list and blocked-address restrictions before calling `SendCoins`: [2](#0-1) 

`IsInDenomAllowList` is the function that enforces tokenfactory's per-denom allow-list restriction set via `MsgUpdateDenom`/`SetDenomAllowList`: [3](#0-2) 

However, `sendNative` in the same precompile file bypasses `bankMsgServer` entirely and calls `SendCoinsAndWei` on the raw `bankKeeper`, which never invokes `IsInDenomAllowList` or `BlockedAddr`: [4](#0-3) 

This mirrors the reported bug class exactly: a security/authorization check (`checkSQL` in the report, `IsInDenomAllowList`/`BlockedAddr` here) is applied on one code path that mutates the same underlying resource (`send`) but is missing on a sibling path (`sendNative`) that performs an equivalent mutation (moving `usei`/wei balance) through a different, unchecked entry point.

### Impact Explanation
`usei` (the chain's native staking/fee denom) does not commonly have a tokenfactory allow-list configured, since it's not a tokenfactory-created denom, which limits blast radius somewhat. However, any tokenfactory-created denom holder who is subject to a `BlockedAddr` restriction (e.g., module accounts, the reserved EVM coinbase address range) or an allow-list restriction on the `usei` base denom (which is technically settable by governance/admin through the generic `SetDenomAllowList` keeper method, not limited to `factory/`-prefixed denoms at the type level, though `IsInDenomAllowList` only checks denoms with the `factory/` prefix) can have their outbound/inbound restriction bypassed by routing the transfer through `sendNative`'s `value`-based transfer path instead of `send`. Concretely, `BlockedAddr` recipients (which include reserved EVM-coinbase-prefixed addresses used internally by the chain, per `BlockedAddr`'s coinbase-prefix check) can be sent funds via `sendNative` when they should be rejected, and any tokenfactory admin who configured an allow-list-restricted denom expecting `send`-based transfers to be gated can have that expectation violated for `usei`/wei value transfers specific to `sendNative`'s scope. This is an authorization/access-control bypass (CWE-284 analog) reachable by any EVM caller with `usei` balance in a single transaction.

### Likelihood Explanation
High likelihood of triggering: `sendNative` is a standard, documented method on the widely-used bank precompile (`0x1001`), callable by any EVM account with a non-zero `msg.value`, requiring no special permissions — this matches the "unprivileged transaction sender" reachability bar. No governance or operator action is needed to trigger the divergent code path; it exists in every deployment of the current precompile version.

### Recommendation
1. In `precompiles/bank/bank.go`'s `sendNative`, apply the same `BlockedAddr` and `IsInDenomAllowList` checks (or route the transfer through `bankMsgServer`-equivalent Send logic) that `send` applies, before calling `SendCoinsAndWei`.
2. Centralize the allow-list/blocked-address enforcement inside the `BankKeeper.SendCoins`/`SendCoinsAndWei` primitives themselves (defense in depth), rather than relying on each call site (msg server, precompile methods) to remember to perform them, exactly as the original report recommends centralizing `checkSQL` in middleware rather than per-action.
3. Add regression tests analogous to `TestSendCoinsWithAllowList` and `TestMultiSendAllowList` that specifically exercise `sendNative` against a blocked recipient and an allow-list-restricted denom to prevent recurrence.

### Proof of Concept
1. Chain operator (or governance) restricts a denom via `SetDenomAllowList`/`MsgUpdateDenom`, or a `BlockedAddr` recipient exists (e.g., the reserved EVM-coinbase-prefixed address space checked in `BlockedAddr`).
2. Attacker deploys/calls a contract that invokes `IBank.sendNative{value: X}(toNativeAddress)` on `0x0000000000000000000000000000000000001001` targeting the restricted/blocked recipient.
3. `sendNative` calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly: [5](#0-4) 
4. No `IsInDenomAllowList` or `BlockedAddr` check is performed, so the transfer succeeds where the equivalent `IBank.send(...)` call (routed through `bankMsgServer.Send`) would have been rejected with `"is not allowed to receive funds"`.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
