### Title
`ReceivedOutput::read` accepts untrusted offset/script_pubkey pairings without verification, causing unspendable funds to be reported as received — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an `offset` scalar, a `TxOut`, and an `OutPoint` from attacker-controlled bytes with no consistency check. It never verifies that `offset` actually derives the key embedded in `output.script_pubkey` — i.e., that `p2tr_script_buf(key + G * offset) == output.script_pubkey`. This mirrors the bug class of CVE-2021-20267: insufficient verification of a claimed identity/address binding, allowing a spoofed binding to be accepted.

### Finding Description
`Scanner::scan_transaction` only ever constructs a `ReceivedOutput` whose `offset` was proven to produce the scanned `script_pubkey` via `self.scripts` (networks/bitcoin/src/wallet/mod.rs:205-211). However, `ReceivedOutput::read` (lines 122-134) accepts an arbitrary `offset` and arbitrary `script_pubkey` independently:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    output = TxOut::consensus_decode(&mut buf_r)...;
    outpoint = OutPoint::consensus_decode(&mut buf_r)...;
    Ok(ReceivedOutput { offset, output, outpoint })
}
```

The deserialized `offset` is a semantically meaningful secret-bearing claim — it is the scalar used to spend the output — yet nothing ties it to the output's script. Downstream, `Output::key()` (processor/src/networks/bitcoin.rs:112-122) derives the owning multisig key as `script_key - G * offset`, trusting the pairing; `SignableTransaction::new`/scheduling similarly trusts `output.offset()` to sign for the spend. An attacker who can feed crafted `ReceivedOutput`/`Output` bytes (e.g., into the processor's serialized output pipeline via `Output::read` at processor/src/networks/bitcoin.rs:145-166, which unwraps embedded fields without revalidation) can:

- Cause an output legitimately paying `key` to be attributed to `key - G*evil_offset`, i.e., a *different* multisig — spoofing which validator set "owns" funds (the direct analog of impersonating another system's address to intercept its traffic).
- Cause outputs to be reported received (`balance()` returns the TxOut value) while the associated `offset` cannot spend them, or while the spend is attributed to the wrong key set.

### Impact Explanation
Accepted impact: funds reported received that are not spendable / funds misattributed to the wrong multisig key. The processor treats `Output::key()`-derived keys as the owning multisig; a mismatched `offset` either silently attributes the deposit to a nonexistent/unrelated group key (signing for it fails or produces an unspendable plan) or credits balances that cannot be moved — a denial of service on funds and potential misrouting of deposits, matching the advisory's DoS/interception consequence.

### Likelihood Explanation
The in-scope surface explicitly includes untrusted bytes fed to `ReceivedOutput::read`. `Output::read` performs `.unwrap()` on nested decodes and passes through `ReceivedOutput::read` with no re-derivation, so any DB record, inter-component message, or synced blob containing a serialized `Output`/`ReceivedOutput` crosses this boundary. A peer or anyone able to inject such bytes gets a fully "valid" parse of an inconsistent claim.

### Recommendation
Either:
1. Make `ReceivedOutput` construction proof-carrying — store nothing claimable; have `read` take the multisig `key` (or a `&Scanner`) and recompute `p2tr_script_buf(key + G*offset) == output.script_pubkey`, rejecting mismatches; or
2. Keep deserialization dumb but rename/make it `pub(crate)`/`unsafe`-equivalent and require every consumer (`Output::read`, `SignableTransaction::new`, scheduler) to re-verify `offset` against `script_pubkey` before use.
