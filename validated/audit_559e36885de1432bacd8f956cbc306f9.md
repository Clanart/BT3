### Title
OP_RETURN data output is omitted from the fee/weight calculation, so signed Bitcoin transactions pay a lower effective fee rate than requested and can fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends the caller-supplied OP_RETURN `data` output to `tx_outs`, but computes the transaction's weight/vbytes — and therefore `needed_fee` — from `payments` only, via `calculate_weight_vbytes`. Analogous to the Optimism Portal forwarding `gasleft() - FINALIZE_GAS_BUFFER` after an unbudgeted SSTORE consumed part of the budget, the transaction here is signed with a fee budgeted for a smaller transaction than the one actually produced: the OP_RETURN output consumes vsize that was never accounted for, leaving the broadcast transaction with a lower effective fee rate than `fee_per_vbyte` intended.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before fee estimation:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds its mock transaction from `payments` only; it never sees `tx_outs`, so the OP_RETURN output (8 bytes value + script length + `OP_RETURN` + pushdata opcode + up to 80 bytes of data, i.e. up to ~92 extra bytes of base size) is excluded from `weight` and `vbytes`. The same omission occurs in the change path, which passes `payments, Some(&change)` but still not the data output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is computed for a transaction smaller than the one actually signed.
- The `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, again using the underestimated `vbytes`, so it cannot catch the shortfall.
- The `TooLargeTransaction` check uses the underestimated `weight`, so a transaction that actually exceeds `MAX_STANDARD_TX_WEIGHT` can be constructed.

The real transaction's fee rate is `needed_fee / actual_vsize < fee_per_vbyte`. When `fee_per_vbyte` is exactly 1 sat/vB (the floor imposed by `median_fee` in `processor/src/networks/bitcoin.rs`, which returns `Fee(fee.max(1))`), the actual rate drops below Bitcoin's 1000 sat/kvB minimum relay fee once the data output pushes actual vsize more than a few bytes above the estimate.

### Impact Explanation
A transaction produced and signed through this path forwards less fee-rate than the caller specified — the direct analog of the SafeCall receiving less gas than `_tx.gasLimit`. At boundary fee rates the resulting transaction is non-standard and will be rejected by Bitcoin Core's mempool (`min relay fee not met`), so the signed transaction cannot be relayed or confirmed: the inputs are committed to a TX that cannot enter the chain, i.e., funds reported as being sent are not spendable/confirmable. Even at higher fee rates, the transaction systematically pays less than the requested rate, degrading confirmation reliability for every data-carrying spend.

### Likelihood Explanation
`data` is an unprivileged caller-supplied parameter of `SignableTransaction::new` (bounded to 80 bytes, so deliberately exposed for use). Any invocation with `data = Some(..)` triggers the undercount. The underpayment is deterministic and proportional to the data length; it hits the relay-fee boundary whenever the requested rate is 1 sat/vB and the OP_RETURN output adds more vsize than the headroom in `needed_fee / vsize`.

### Recommendation
Include the OP_RETURN output in the fee/weight estimate — i.e., pass the fully-populated `tx_outs` (or `payments` plus the data output) to `calculate_weight_vbytes`, and likewise account for it in the change variant:

```rust
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, data.as_deref(), None);
```

where `calculate_weight_vbytes` appends the OP_RETURN `TxOut` to its mock transaction. Equivalently, mirroring the report's "swap the SSTORE and the require" fix, build the complete output set (payments + data + change decision) first and then compute `needed_fee` from the true final weight, re-validating `TooLowFee`, `NotEnoughFunds`, and `TooLargeTransaction` against that final figure.

### Proof of Concept
```rust
// networks/bitcoin: one input of e.g. 10_000 sats, one payment, 80-byte data, 1 sat/vB
let data = Some(vec![0u8; 80]);
let st = SignableTransaction::new(inputs, &payments, None, data, 1).unwrap();
// needed_fee == 1 * vbytes(tx without OP_RETURN) and passes the TooLowFee check
// actual tx has an extra ~91-byte OP_RETURN output:
assert!(st.fee() as f64 / actual_vsize as f64) < 1.0 // below min relay rate
