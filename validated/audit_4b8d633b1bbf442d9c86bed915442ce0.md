### Title
Missing upper bound on clawback `time_lock` allows a coin sender to permanently deny a recipient's claim — ([File: chia/wallet/puzzles/clawback/drivers.py])

### Summary
Chia's clawback mechanism (`chia/wallet/puzzles/clawback/drivers.py`) is functionally a two-party vesting construct: a sender locks a coin for a `timelock` period, during which only the sender can reclaim it, and after which the recipient can claim it via `ASSERT_SECONDS_RELATIVE`. Like the reported `createVestingSchedule`, the timelock parameter is only bounded on the low end and has no upper bound, letting the party who creates the lock set a value that makes the recipient's claim effectively unreachable.

### Finding Description
`create_clawback_merkle_tree()` validates only the lower bound of the `timelock` argument: [1](#0-0) 

```
def create_clawback_merkle_tree(timelock: uint64, sender_ph: bytes32, recipient_ph: bytes32) -> MerkleTree:
    if timelock < 1:
        raise ValueError("Timelock must be at least 1 second")
```

There is no upper-bound check. This `timelock` value becomes the recipient's `ASSERT_SECONDS_RELATIVE` condition inside the claim puzzle (via `create_merkle_solution`), meaning the recipient's coin cannot be spent by the recipient until `timelock` seconds have elapsed since the coin's creation: [2](#0-1) 

Meanwhile, the sender's side of the merkle tree (`create_p2_puzzle_hash_puzzle(sender_ph)`) has no such timelock condition at all — the sender can claw the coin back to themselves at any time, unconstrained by `timelock`. The `ClawbackMetadata.time_lock` field, which is a `uint64` and thus can be set arbitrarily close to `2**64-1`, is streamed directly into the REMARK condition and used to reconstruct the puzzle for wallet display/matching, with no validation of a sane maximum: [3](#0-2) [4](#0-3) 

This is directly analogous to the `createVestingSchedule` bug: an operator/sender-controlled duration parameter that gates a beneficiary's ability to claim funds has only a trivial lower-bound guard and no sanity upper bound, so a malicious or careless sender can create a lock that effectively never expires for the recipient, while retaining full unilateral control (claw-back) over the coin themselves.

### Impact Explanation
A sender can construct a clawback coin with `time_lock` set to an astronomically large value (e.g., `uint64` max, corresponding to hundreds of billions of years). The recipient's `ASSERT_SECONDS_RELATIVE` condition will never be satisfiable in practice, so the recipient can never claim the coin through the intended claim path, while the sender retains the unilateral ability to claw the coin back to themselves at any time. This produces a denial of the recipient's economic right to funds they were told they'd receive, mirroring the "users never vesting their tokens" impact in the source report.

### Likelihood Explanation
Low, matching the source report's likelihood characterization: it requires the coin-creating party (the "admin" analog — the sender constructing the clawback spend) to be malicious or to make an error when choosing the timelock, and it requires the recipient/wallet to not surface or reject an unreasonable lock duration before treating the coin as "received."

### Recommendation
Add a sensible upper bound to `timelock` in `create_clawback_merkle_tree()` (and validate `ClawbackMetadata.time_lock` similarly wherever it is constructed, e.g., in `ClawbackPuzzleDecorator.create`/`solve`), rejecting values beyond a reasonable maximum (e.g., a fixed number of days/years) so that the recipient's claim path cannot be rendered practically unreachable. Wallet UIs that display/accept incoming clawback coins should also surface and optionally reject unreasonable lock durations before treating the transaction as trusted.

### Proof of Concept
1. Sender constructs a coin spend using `ClawbackPuzzleDecorator`/`create_merkle_puzzle` with `time_lock = uint64(2**64 - 1)` (or any value far beyond any practical block-time horizon) and `recipient_ph` set to the victim's puzzle hash.
2. The resulting puzzle passes `create_clawback_merkle_tree()`'s only check (`timelock < 1`) and is accepted into a valid spend bundle/mempool with no error, per `chia/wallet/puzzles/clawback/drivers.py:70-77`.
3. The recipient receives the coin (per `match_clawback_puzzle`/wallet sync) and is recorded as an incoming clawback transaction, but any future recipient claim attempt using `create_merkle_solution` will include `ASSERT_SECONDS_RELATIVE, time_lock`, which cannot be satisfied within any realistic blockchain lifetime — see `chia/_tests/wallet/clawback/test_clawback_lifecycle.py:151-165` for the analogous mechanics where an insufficiently-elapsed timelock causes `Err.ASSERT_SECONDS_RELATIVE_FAILED`.
4. The sender, unconstrained by any timelock on their own claw-back path, can reclaim the coin to themselves at any time, leaving the recipient permanently unable to claim it.

```python
def create_merkle_solution(
    timelock: uint64,
    sender_ph: bytes32,
    recipient_ph: bytes32,
    inner_puzzle: Program,
    inner_solution: Program,
) -> Program:
    """
    Recreates the full merkle tree of a p2_1_of_n clawback coin. It uses the timelock and each party's
    puzhash to create the tree.
    The provided inner puzzle must hash to match either the sender or recipient puzhash
    If it's the sender, then create the clawback solution. If it's the recipient then create the claim
    solution.
    Returns a program which is the solution to a p2_1_of_n clawback.
    """
    merkle_tree = create_clawback_merkle_tree(timelock, sender_ph, recipient_ph)
    inner_puzzle_hash = inner_puzzle.get_tree_hash()
    if inner_puzzle_hash == sender_ph:
        cb_inner_puz = create_p2_puzzle_hash_puzzle(sender_ph)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_p2_puzzle_hash_solution(inner_puzzle, inner_solution)
    elif inner_puzzle_hash == recipient_ph:
        condition = [80, timelock]
        cb_inner_puz = create_augmented_cond_puzzle(condition, inner_puzzle)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_augmented_cond_solution(inner_solution)
    else:
        raise ValueError("Invalid Clawback inner puzzle.")
    solution: Program = Program.to([merkle_proof, cb_inner_puz, cb_inner_solution])
    return solution
```
