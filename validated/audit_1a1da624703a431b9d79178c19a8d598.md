### Title
Single Kickoff State Machine Error Permanently Blocks All Bridge State Transitions — (`core/src/states/mod.rs`)

### Summary

`process_block_parallel` in `core/src/states/mod.rs` collects errors from every kickoff and round state machine processed in a block and returns a combined error if **any** of them failed. Because the state is never persisted on failure, the state manager restarts and retries the same block indefinitely. A single persistently-failing kickoff duty (e.g., disprove construction triggered by operator-controlled assert data) therefore freezes the entire bridge automation layer: no watchtower challenge, disprove, or round-advance duty can execute for any other kickoff until the stuck one is manually resolved.

---

### Finding Description

`process_block_parallel` drives all kickoff and round state machines forward in parallel. Individual state machine actions wrap their duty calls in `capture_error`, which stores errors in the context rather than aborting the state machine's transition: [1](#0-0) 

After all futures complete, `process_block_parallel` drains every context's error list and returns a combined error if the list is non-empty: [2](#0-1) 

Because `save_state_to_db` is only called **after** a successful return from `process_block_parallel`, a failure here means no state machine's new state is written to the database. The `BackgroundTaskManager` restarts the task; `reload_state_manager_from_db` reloads the last committed snapshot, which still points `next_height_to_process` at the same block: [3](#0-2) 

On the next iteration the same block is fetched, the same matchers fire, the same duties are dispatched, and the same error is captured — creating an infinite retry loop.

The duties that can fail persistently include `Duty::VerifierDisprove`, dispatched from `send_disprove` inside the kickoff state machine: [4](#0-3) 

`send_disprove_tx` constructs the disprove witness from operator-supplied assert data and calls `set_p2tr_script_spend_witness`. If the operator crafts assert data that causes this construction to fail (e.g., a malformed witness length that violates script-path constraints), the error is captured, `process_block_parallel` returns an error, and the state manager never advances past that block: [5](#0-4) 

The same pattern applies to `Duty::WatchtowerChallenge` dispatched from `send_watchtower_challenge`: [6](#0-5) 

---

### Impact Explanation

Once the state manager is stuck on a block:

- **No verifier can send a watchtower challenge** for any kickoff in any subsequent block.
- **No verifier can send a disprove transaction** for any kickoff, including ones where the operator is provably fraudulent.
- **No operator round state machine advances**, blocking `ReadyToReimburse` and collateral-burn flows.

A malicious operator who triggers the stuck state for their own kickoff therefore also prevents verifiers from challenging **other** operators' kickoffs. Any operator whose kickoff is in the `challenged` state during the freeze window can let the disprove deadline expire unchallenged, retaining bridged BTC they should have lost.

---

### Likelihood Explanation

The trigger requires a persistent error in one kickoff's duty. Concrete paths:

1. **Operator-controlled assert data**: `send_disprove_tx` passes `disprove_inputs` (derived from operator witness data) directly into `set_p2tr_script_spend_witness`. A witness vector whose element count or byte length violates the expected script-path index causes a non-transient error on every retry.
2. **Missing DB row**: If `get_deposit_signatures` returns `None` for a kickoff (e.g., due to a partial DB write during a prior crash), the `ok_or_eyre` at line 3003 of `verifier.rs` returns a persistent error.
3. **tx_sender RPC down for one kickoff type**: A tx_sender that rejects a specific transaction type (e.g., `Disprove`) will fail every retry for that kickoff while succeeding for others, yet still blocks all others. [7](#0-6) 

---

### Recommendation

1. **Decouple per-machine errors from block-level success.** Log captured errors and continue saving the state of all successfully-processed machines. Only re-queue the specific failing machine for the next block rather than retrying the entire block.

2. **Implement a per-kickoff retry budget.** After N consecutive failures for the same kickoff, mark it as `stuck` in the database, skip it in future iterations, and emit a high-severity alert. This prevents one broken kickoff from blocking the rest.

3. **Save partial state on error.** At minimum, advance `next_height_to_process` and persist the state of machines that completed without error, so the retry only re-runs the failing machine.

---

### Proof of Concept

1. Operator sends a kickoff transaction with assert data crafted so that `set_p2tr_script_spend_witness` in `send_disprove_tx` will fail (e.g., a witness element count that mismatches the expected Taproot leaf index).
2. A challenge is sent for this kickoff; the kickoff state machine enters `challenged` state and eventually dispatches `Duty::VerifierDisprove`.
3. `send_disprove` wraps the call in `capture_error`; the error is stored in `context.errors`.
4. `process_block_parallel` reaches the error-collection check at line 609–614 of `core/src/states/mod.rs` and returns `Err(...)`.
5. `save_state_to_db` is never called; `next_height_to_process` remains at the current block.
6. The `BackgroundTaskManager` restarts the state manager task; `reload_state_manager_from_db` reloads the pre-failure snapshot.
7. The same block is fetched and processed; the same error recurs — infinite loop.
8. All other kickoffs (including ones where a different operator is fraudulent) cannot advance. Their disprove deadlines expire. The fraudulent operators retain bridged BTC. [8](#0-7) [9](#0-8)

    pub async fn process_block_parallel(
        &mut self,
        context: &mut context::StateContext<T>,
    ) -> Result<(), eyre::Report> {
        let block_height = context.cache.block_height;

        // Process all machines, for those unaffected collect them them, otherwise return
        // a future that processes the new events.
        let (mut final_kickoff_machines, mut kickoff_futures) =
            Self::update_machines(&mut self.kickoff_machines, context);
        let (mut final_round_machines, mut round_futures) =
            Self::update_machines(&mut self.round_machines, context);

        // Here we store number of iterations to detect if the machines do not stabilize after a while
        // to prevent infinite loops. If a matcher is used, it is deleted, but a bug in implementation
        // can technically cause infinite loops.
        let mut iterations = 0;

        // On each iteration, we'll update the changed machines until all machines
        // stabilize in their state.
        while !kickoff_futures.is_empty() || !round_futures.is_empty() {
            // Execute all futures in parallel
            let (kickoff_results, round_results) =
                join(join_all(kickoff_futures), join_all(round_futures)).await;

            // Unzip the results into updated machines and state contexts
            let (mut changed_kickoff_machines, mut kickoff_contexts): (Vec<_>, Vec<_>) =
                kickoff_results.into_iter().unzip();
            let (mut changed_round_machines, mut round_contexts): (Vec<_>, Vec<_>) =
                round_results.into_iter().unzip();

            // Merge and handle errors
            let mut all_errors = Vec::new();
            for ctx in kickoff_contexts.iter_mut().chain(round_contexts.iter_mut()) {
                all_errors.extend(std::mem::take(&mut ctx.errors));
            }

            if !all_errors.is_empty() {
                // Return first error or create a combined error
                return Err(eyre::eyre!(
                    "Multiple errors occurred during state processing: {:?}",
                    all_errors
                ));
            }
