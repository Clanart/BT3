### Title
Unbounded recursive puzzle-driver "also"-chain unwinding lets a crafted offer/spend puzzle crash wallet transaction processing via Python recursion exhaustion - (File: `chia/wallet/outer_puzzles.py`)

### Summary
The ModSecurity CVE describes a parser that recursively walks attacker-supplied nested structures without a depth limit, letting a small, cheap-to-construct payload exhaust CPU/stack and stall request processing. Chia's wallet driver-matching code for offers/spend bundles has the same shape: `match_puzzle()` and every concrete outer-puzzle driver (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`, `TransferProgramPuzzle`) recursively unwind the CLVM "curry" layers of a puzzle reveal via `self._match(...)`/`also()` with no depth check, and `PuzzleInfo.also()`/`check_type()` mirror the same unbounded recursion on the derived `PuzzleInfo` tree.

### Finding Description
`chia/wallet/outer_puzzles.py` defines:
```python
def match_puzzle(puzzle: UnknownPuzzle) -> PuzzleInfo | None:
    for driver in driver_lookup.values():
        potential_info: PuzzleInfo | None = driver.match(puzzle)
``` [1](#0-0) 

Each driver's `match()` recurses into the puzzle's inner layer without any depth limit, e.g. `CATOuterPuzzle.match()`:
```python
next_constructor = self._match(UnknownPuzzle(known_program=inner_puzzle))
if next_constructor is not None:
    constructor_dict["also"] = next_constructor.info
``` [2](#0-1) 

The same unbounded self-recursion pattern repeats in `OwnershipOuterPuzzle.match/get_inner_puzzle/get_inner_solution`, `MetadataOuterPuzzle`, `SingletonOuterPuzzle`, and `CROuterPuzzle`. [3](#0-2) [4](#0-3) 

`PuzzleInfo.also()`/`check_type()` mirror this on the resulting dict-based structure, again with no depth bound:
```python
def also(self) -> PuzzleInfo | None:
    if "also" in self.info:
        return PuzzleInfo(self.info["also"])
``` [5](#0-4) 

An offer's inspection/summarization path calls exactly this recursive matcher on every coin spend of an untrusted offer bundle:
```python
puzzle_driver = match_puzzle(parent_puzzle)
...
inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
``` [6](#0-5) 

and `Offer.from_spend_bundle()` also invokes `match_puzzle()` per coin spend when parsing a submitted spend bundle/offer file. [7](#0-6) 

None of these Python-level recursive walks are metered by CLVM cost, because `match_puzzle`/`uncurry()` inspect the static puzzle shape without running it — unlike `sha256_treehash()`, which the codebase explicitly reimplemented iteratively "so we don't have to worry about blowing out the python stack," the driver-matching code has no equivalent protection. [8](#0-7) 

### Impact Explanation
An attacker can construct an offer file (or a spend bundle presented as an offer) whose puzzle reveal is wrapped in thousands of cheap CAT/singleton/ownership/CR curry layers, each legitimately matchable by `driver_lookup`. Because currying is inexpensive and unmetered at this stage, a payload comparable in size to the "300KB" example from the original CVE can encode enough nested layers to exceed Python's default recursion limit (~1000) when the victim's wallet calls `match_puzzle()`/`get_inner_puzzle()`/`get_inner_solution()` to inspect or accept the offer. This raises an unhandled `RecursionError` deep inside `TradeManager`/`Offer` processing, aborting that offer-processing / spend-parsing call for the wallet service handling it — a spend-triggered transaction-processing halt for the specific wallet operation, without any consensus-level coin movement occurring.

### Likelihood Explanation
Constructing arbitrarily deep curried puzzle layers is cheap and requires no signature, no on-chain fee, and no cooperation from the victim beyond opening/inspecting an offer file or examining a submitted spend bundle — a normal, expected wallet operation for any offer counterparty. No special privileges are needed; only the ability to hand a wallet user or RPC caller a crafted offer/spend payload.

### Recommendation
Bound recursion depth in `match_puzzle()` and all outer-puzzle drivers (`match`, `construct`, `solve`, `get_inner_puzzle`, `get_inner_solution`) and in `PuzzleInfo.also()`/`check_type()`, either by converting the "also"-chain walk to an iterative loop (as already done for `sha256_treehash()`) or by enforcing an explicit maximum layer count before recursing further, raising a controlled error instead of letting Python's recursion limit be hit.

### Proof of Concept
1. Build an inner puzzle `ACS = Program.to(1)`.
2. Repeatedly wrap it thousands of times using `construct_cat_puzzle(CAT_MOD, tail, puzzle)` (or any other outer-puzzle constructor recognized by `driver_lookup`), each iteration nesting the previous result as the new inner puzzle — this is exactly the "double_cat_puzzle" pattern already exercised in tests but iterated thousands of times instead of twice. [9](#0-8) 
3. Package the resulting deeply-layered puzzle reveal into an offer/spend bundle coin spend.
4. Have the victim wallet call `match_puzzle()` (directly, or transitively via `Offer._get_offered_coins()`/`Offer.from_spend_bundle()` when inspecting or accepting the offer).
5. Observe an unhandled `RecursionError` aborting the offer-processing call, halting that wallet operation.
