## Title
Missing HTML-context escaping (`<`, `>`) in upb's JSON string encoder enables reflected script injection when ProtoJSON output is embedded in HTML — (`upb/json/encode.c`, also `php-upb.c`, `ruby-upb.c`)

## Summary
The CVE-2019-16935 root cause is a documentation server that emits an attacker-controllable string (`server_title`) into an HTML page without any HTML/JS-context escaping, so `<script>` and similar payloads execute in the victim's browser. The transferable Protobuf analog is a **missing HTML-context escape in the ProtoJSON string encoder**. Protobuf's various JSON encoders are documented and tested to deliberately escape `<`, `>` (and several Unicode "invisible"/bidi characters) *specifically to prevent XSS* when JSON produced from a protobuf message is later embedded into an HTML page or `<script>` block by a consuming application — this is exactly the same threat model as the reported bug. However, the `upb`-based JSON encoder (`upb/json/encode.c`, duplicated verbatim in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`) omits this hardening entirely, while the C++ (`src/google/protobuf/json/internal/writer.cc`), Java (`JsonFormat.java`), and C# (`JsonFormatter.cs`) encoders all implement it.

## Finding Description
Every "hardened" ProtoJSON string writer in this codebase explicitly escapes `<` and `>` (plus a defined set of bidi/invisible Unicode code points) with the express purpose of preventing script injection when the resulting JSON is later interpolated into HTML/JS by a downstream application:

- C++: `MustEscape()` explicitly special-cases `'<'` and `'>'` "to prevent security bugs in JavaScript" [1](#0-0) , and `WriteEscapedUtf8` treats `<>` as unsafe characters requiring escape [2](#0-1) .
- Java: `replacementChars` explicitly escapes `<>&='` "to prevent XSS risks" [3](#0-2) , with a regression test explicitly named for this purpose (`testHtmlEscape`, referencing bug b/73832901) [4](#0-3) .
- C#: `CommonRepresentations` escapes `<` and `>` with the comment "Escaping of < and > are required for HTML security" [5](#0-4) , plus additional bidi/invisible character handling "to prevent security bugs in javascript" [6](#0-5) .

In contrast, the `upb` JSON encoder's `jsonenc_put_escaped_char()` only escapes control characters (`< 0x20`), `\n`, `\r`, `\t`, `\"`, `\f`, `\b`, `\\` — it has **no case for `<` or `>`**, and any other byte (including `<` and `>`) is written through unescaped via `jsonenc_putbytes(e, &ch, 1)`: [7](#0-6) . This exact function body is duplicated in the PHP native extension [8](#0-7)  and the Ruby native extension [9](#0-8) , both of which call `upb_JsonEncode()` from their public serialization entry points in `message.c`.

The failed invariant: "ProtoJSON output of an attacker-controlled string field must be safe to embed directly in an HTML/`<script>` context," which the C++/Java/C# implementations enforce as a deliberate, documented, tested invariant, but which the `upb`-backed encoder (used by Ruby and PHP) does not enforce.

## Impact Explanation
An application that takes an attacker-controlled string (e.g., a username, comment, or any client-supplied field bound via a trusted schema) into a protobuf message and then serializes that message to JSON using the Ruby or PHP protobuf library (backed by `upb`), and subsequently embeds that JSON text into an HTML page or inline `<script>` block (a common pattern for hydrating client-side state), will pass through literal `</script>`, `<img onerror=...>`-style payloads unescaped. This is the identical XSS delivery mechanism as CVE-2019-16935, just relocated to the serialization layer instead of the RPC documentation page — the missing check is the same class of "string emitted into an HTML-adjacent sink without HTML-safe encoding." Severity is Medium, consistent with the CVSS 6.1 (AV:N/AC:L/PR:N/UI:R) rating of the original report, since exploitation requires the consuming application to reflect the JSON into an HTML/script context (a reasonable and common consuming-application assumption, not an internal API misuse).

## Likelihood Explanation
Likelihood is Medium-to-High for any Ruby or PHP protobuf-JSON consumer that follows the common pattern of embedding `to_json`/`serializeToJsonString()` output into server-rendered HTML (a widely-used technique for passing initial state to client-side JS). No privileged access or malicious schema is required — an ordinary client supplying a bounded string value through a normal, trusted schema field reaches this code path deterministically.

## Recommendation
Port the `<`/`>` (and ideally the same invisible/bidi Unicode ranges already handled in `src/google/protobuf/json/internal/writer.cc`) escaping logic into `upb/json/encode.c`'s `jsonenc_put_escaped_char()`, and regenerate/resync `php-upb.c` and `ruby-upb.c` from that source so PHP and Ruby ProtoJSON output receives the same HTML-safety guarantee as the C++, Java, and C# implementations. Add a cross-language regression test (mirroring Java's `testHtmlEscape`) asserting that `<` and `>` are escaped as `\u003c` / `\u003e` in `upb`-backed JSON output.

## Proof of Concept
Using the Ruby or PHP protobuf extension (backed by `upb_JsonEncode`):
```ruby
msg = MyMessage.new(name: "</script><script>alert(1)</script>")
puts msg.to_json
# Expected (matching C++/Java/C# behavior): {"name":"\u003c/script\u003e\u003cscript\u003ealert(1)\u003c/script\u003e"}
# Actual (upb encoder): {"name":"</script><script>alert(1)</script>"}
```
Tracing: `to_json` → `upb_JsonEncode()` → `jsonenc_string()` → `jsonenc_stringbody()` → `jsonenc_put_escaped_char()` [10](#0-9)  — no branch handles `'<'`/`'>'`, so they fall to the `default` case and are copied through raw via `jsonenc_putbytes`. I was not able to execute this in a sandbox from this environment; this reproduction should be run and confirmed by whoever picks up the fix, comparing output against the C++ (`writer.cc`) / Java (`JsonFormat.java`) encoders for the same input string.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
