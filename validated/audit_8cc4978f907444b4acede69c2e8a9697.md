### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers disproportionate upfront allocation (resource-amplification DoS) - ([File: crypto/dkg/src/lib.rs])

### Summary
CVE-2019-15225 is a resource-exhaustion bug class: a small attacker-controlled input forces work/memory far larger than the bytes delivered. The closest reachable analog in the in-scope crates is `ThresholdKeys::<C>::read`, which reads a 2-byte `n` and immediately performs `Vec::with_capacity(usize::from(n))` and `HashMap` insertion of `n` group elements before any of the corresponding bytes have been received.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses `t`, `n`, `i` from a 6-byte header, then, for `Interpolation::Constant`, executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
```

and afterwards loops `(1 ..= n)` calling `<C as Ciphersuite>::read_G(reader)?` into a `HashMap` of `n` verification shares. `n` is a raw `u16`, so a message of roughly a dozen bytes obligates the reader to reserve capacity for up to 65,535 scalar elements and then attempt up to 65,535 point deserializations. `Vec::with_capacity` commits the allocation before any payload bytes are validated, and the `with_capacity`/`read_F`/`read_G` workload is driven entirely by the claimed count, not by bytes actually present — the same amplification shape as the Envoy regex bug, where the attacker supplies a tiny input that dictates outsized resource use. `ThresholdKeys::read` is explicitly one of the untrusted-byte entry points in scope.

By contrast, sibling readers bound allocation to declared limits (`Commitments::read` allocates `params.t()` which is checked against `ThresholdParams`, crypto/dkg/pedpop/src/lib.rs:110-127) or size vectors from attacker bytes only after limit checks (`Transaction::read` checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating, coordinator/src/tributary/transaction.rs:286-294). `ThresholdKeys::read` performs the `with_capacity` and begins the `n`-element loops without ever validating `n` against `ThresholdParams` until `ThresholdParams::new` runs at the very end — after the memory and deserialization work is already committed.

### Impact Explanation
An unprivileged party that can feed bytes to `ThresholdKeys::read` (e.g., a key-share/blob loading path or any API accepting serialized threshold keys) can, with each ~10-byte message, force an allocation for up to ~65,535 scalars plus a 65,535-element `HashMap` insertion loop of attempted `read_G` calls. Repeating the malformed input yields sustained allocator pressure and CPU burn on the deserialization attempts — memory-exhaustion/amplification DoS against the node process, matching the CVE's C:N/I:N/A:H profile.

### Likelihood Explanation
Reachability depends on an integrator exposing `ThresholdKeys::read` on untrusted input; it is a listed in-scope entry point, so any code path deserializing threshold keys from network/storage bytes an unprivileged party can influence is exposed. The amplification is modest in absolute terms (~a few MB and ~65k failed/curtailed deserializations per message) and the memory is transient if the stream is truncated, so severity is Medium rather than High.

### Recommendation
Validate `n` against `ThresholdParams` bounds (and against `t`/`i` consistency) before allocating, or avoid speculative `with_capacity(n)` entirely: read scalars/points incrementally with `Vec::push` and cap `n` early by calling `ThresholdParams::new(t, n, i)` prior to the `Interpolation::Constant` branch.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, Participant};
use frost::curve::Ristretto; // example curve

fn main() {
    // ID header for the curve (as emitted by ThresholdKeys::write)
    let mut buf = vec![];
    buf.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
    buf.extend(Ristretto::ID);
    // t = 1, n = 0xFFFF, i = 1
    buf.extend(&1u16.to_le_bytes());
    buf.extend(&u16::MAX.to_le_bytes());
    buf.extend(&1u16.to_le_bytes());
    // Interpolation::Constant -> Vec::with_capacity(65535) allocated here,
    // before a single scalar byte has been supplied
    buf.push(0);
    // No further bytes: read_F fails, but the ~65k-element allocation
    // (and for Lagrange, the 65k read_G loop bound) was already obligated.
    let _ = ThresholdKeys::<Ristretto>::read(&mut Cursor::new(buf));
}
```

A slightly different attack with a valid curve ID and `n = 65535` yields a multi-MB allocation plus 65,535 attempted point deserializations per malformed message; looping it consumes allocator bandwidth and memory proportional to the claimed count rather than the delivered bytes — the same small-input/large-resource asymmetry as CVE-2019-15225.
