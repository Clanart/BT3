### Title
`ReceivedOutput::read` accepts an unverified `offset`/`script_pubkey` binding, letting untrusted bytes claim spendability the `Scanner` never authorized - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner` is the only component that establishes the binding between a `ReceivedOutput`'s scalar `offset` and its `output.script_pubkey` (an output is ours and spendable under `key + offset·G` iff the scanner matched the script to a registered offset). `scan_transaction` enforces this by looking up `output.script_pubkey` in `self.scripts` and attaching the corresponding offset (networks/bitcoin/src/wallet/mod.rs, `scan_transaction`/`register_offset`). However, `ReceivedOutput::read` (the `#[cfg(feature = "std")]` untrusted deserialization path, lines 122-134) decodes `offset`, `output`, and `outpoint` directly from attacker-controlled bytes with no check that `output.script_pubkey == p2tr(key + offset·G)`. The authorization granted by scanning is thereby over-extended to any claimed pairing: a serialized `ReceivedOutput` asserts "this outpoint is spendable with `key + offset`" without any component ever having verified it.

### Finding Description
The `ReceivedOutput` type conflates a claim ("bytes I was given") with a proof ("the scanner verified script ↔ offset"). `scan_transaction` only produces a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` succeeds, so an honestly-produced value always satisfies `script_pubkey == p2tr_script_buf(key + GENERATOR·offset)`. `ReceivedOutput::read` performs no equivalent check — it accepts any `Scalar` offset alongside any `TxOut`/`OutPoint`, including a `script_pubkey` that belongs to an unrelated key, or an offset that was never registered. Consumers downstream (e.g. `Output::key()` in `processor/src/networks/bitcoin.rs` lines 112-122, which reconstructs the owning key as `script_key - offset·G`, and `SignableTransaction` signing, which spends each input as `key + offset`) trust this binding. A forged `ReceivedOutput` therefore reports the wrong owning key and is not actually spendable by the multisig: the BIP-340 signature produced under `key + offset` will not satisfy the real output's script.

### Impact Explanation
An unprivileged party able to feed `ReceivedOutput::read` bytes into a component that treats scanned outputs as received/spendable (the serialize/read round-trip is the documented transport format — `serialize()`/`write` at lines 136-148 are the inverse of `read`) can cause the protocol to record funds as received under a key it does not control, or produce a signing session whose inputs can never be correctly signed. Concretely: an outpoint paying to an attacker's P2TR key can be paired with `offset = 0` and the multisig's script; `Output::key()` then mis-derives the owning key, and any spend attempt produces an invalid witness. This mirrors the ENS finding: authority intended for one scope (a scanner-verified script↔offset pair) is implicitly extended to anything carrying the right shape.

### Likelihood Explanation
Reachability requires the serialized `ReceivedOutput` channel to carry attacker-influenced bytes between components that do not re-scan the chain (e.g. messages relayed between processor instances or restored state). The offset and outpoint are fully attacker-chosen; no PoP, signature, or hash binds them to the script. Exploitation yields either misattributed funds or unspendable-by-the-multisig recorded outputs — an integrity/availability impact consistent with Medium.

### Recommendation
Make the trust explicit: either (a) have `ReceivedOutput::read`/`Output::read` re-verify `output.script_pubkey == p2tr_script_buf(expected_key + GENERATOR·offset)` given the scanner key, or (b) split the type so that only `Scanner::scan_transaction` can construct the "verified" variant used by signing/`key()` derivation, and deserialized values carry an unverified marker requiring re-validation against the registered `scripts` map before use.

### Proof of Concept
Construct `ReceivedOutput` bytes where `offset = Scalar::ZERO` (or any registered offset) but `output.script_pubkey` is a P2TR script for an unrelated attacker key `P_attacker`, and `outpoint` references that real on-chain output:

```rust
// networks/bitcoin/src/wallet/mod.rs
let attacker_key = ProjectivePoint::random(&mut OsRng);
let forged = ReceivedOutput {
  offset: Scalar::ZERO,                                   // claims multisig ownership
  output: TxOut {
    value: Amount::from_sat(10_000),
    script_pubkey: p2tr_script_buf(attacker_key).unwrap(), // actually pays attacker
  },
  outpoint: real_outpoint,
};
let bytes = forged.serialize();
// Any component deserializing this believes outpoint is spendable as `multisig_key + 0·G`
let decoded = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// decoded.offset() == 0, yet the output's discrete log is unknown to the multisig
// Output::key() (processor/src/networks/bitcoin.rs:112) mis-derives the owner,
// and SignableTransaction signing produces an invalid witness for this input.
```

No scan ever registered `attacker_key`'s script under offset `0`; the deserialization path extended scanner-derived authority to an unverified claim. (Caveat: end-to-end severity depends on whether deployments feed `ReceivedOutput::read`/`Output::read` untrusted data rather than re-scanning blocks; the indexed code does not show every caller, so the strongest confirmed claim is that the verification invariant is dropped at the trust boundary.)
