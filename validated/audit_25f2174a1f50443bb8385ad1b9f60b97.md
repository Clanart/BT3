### Title
Pull Request Checkout Trusts a Mutable Branch Name Instead of the Reviewed Commit SHA - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_checkoutPullRequest`/`_findPullRequestBranch` in `app/src/lib/stores/app-store.ts` resolve a pull request to a local branch purely by *ref name* (`headRefName`) after re-fetching the fork remote, never comparing the fetched commit to `pullRequest.head.sha` — the SHA that was actually shown to the user (in a notification, the PR list, or a deep link) at decision time. This is the same broken invariant as the reported `mint()` bug: the user approves an action based on a value they were shown (SHA/price), but the action executes against whatever value is live on an attacker-controlled source (branch tip/`cost`) at execution time, with no on-chain/on-disk check to bind the two together.

### Finding Description
`_checkoutPullRequest` is invoked from several places where the user is shown information about a specific PR state and then, sometime later (possibly after user interaction, dialog rendering, or an async fetch), triggers a checkout of "that" PR: [1](#0-0) 
- from the PR list `onItemClick` [2](#0-1) 
- from a "checks failed" notification dialog [3](#0-2) 
- from a PR review notification dialog [4](#0-3) 
- from the `x-github-client://openRepo/...?pr=NNN` deep link handler, which itself does an extra async round trip (`fetchPullRequest`, `_refreshRepository`) before checkout [5](#0-4) 

All of these ultimately call: [6](#0-5) 

which delegates to `_findPullRequestBranch`: [7](#0-6) 

Note that the function receives only `headRefName` (a mutable branch name) — never the commit SHA. It fetches the fork remote and then does `findRemoteBranch(remoteRef)`, i.e. it resolves the branch name to *whatever commit currently sits at the tip of that ref*, and checks that out. The `PullRequest`/`PullRequestRef` model *does* carry a `sha` field for the head ref [8](#0-7)  but it is never read or compared inside `_checkoutPullRequest`/`_findPullRequestBranch`.

**Broken invariant / corrupted value:** the value the user implicitly "approved" (the PR content shown in the notification, the diff already rendered for that PR, or the PR referenced in the clicked link) is `head.sha` at time T1. The value actually materialized on disk after checkout is "tip of `fork-remote/branch-name` at time T2 (post-fetch)" — a value fully controlled by the PR author (an unprivileged, untrusted party — anyone can open a PR from a fork). Nothing in the checkout path re-verifies that these two values are the same, so a PR author can force-push new content to the same branch between T1 and T2 and have Desktop silently check out the new content under the guise of "the PR the user was just looking at."

**Why existing guards do not stop this:**
- The fetch is a legitimate, expected part of the flow (`_findPullRequestBranch` explicitly fetches "because the PR may be newer than our last fetch"), so there's no anomaly to flag.
- There is no SHA-pinned checkout option (e.g. `git checkout <sha>` or a local branch created at `<sha>` with detached-HEAD warning) — checkout always resolves through the mutable ref name.
- Desktop's git-hooks interception model actively executes repository-defined hooks (including `post-checkout`) for git operations that support `interceptHooks` [9](#0-8) [10](#0-9) , so content that lands in the working tree via this stale-ref checkout can itself run local commands once checked out (via a hook, a build script the user runs, an editor task, etc.) — the resolution to "wrong" commit content is what enables everything downstream.

### Impact Explanation
An unprivileged attacker who has opened (or forked-and-opened) a pull request against a repository the victim has open in Desktop can:
1. Get the victim to look at/act on the PR (via a normal PR review flow, a PR-checks-failed notification, or simply having the PR listed) — this is normal, expected interaction with GitHub, not a special user step.
2. Force-push new commits to the head branch between the moment the victim decides to check it out and the moment Desktop performs the fetch+checkout.
3. Desktop checks out attacker-controlled content that the victim did not review, without any warning that the branch tip changed from what was previously known.

This is a silent corruption of "what the user thinks they are getting" analogous to the report's "silent corruption of what the user commits" — here it is what the user pulls into their working directory and subsequently trusts, builds, or runs, which can lead to local code execution once the victim runs project tooling against the unexpectedly-changed tree.

### Likelihood Explanation
Moderate-to-high. Force-pushing to a PR head branch is a normal git operation available to any PR author (no special repo permissions needed since it's the attacker's own fork/branch) and can be timed to a window that is on the order of the network fetch inside `_findPullRequestBranch`/`_checkoutPullRequest`, or simply happen naturally between when Desktop displayed the PR (e.g., a notification created earlier) and when the user finally clicks to check it out. No credentials, local access, or social engineering beyond "have a PR open" is required.

### Recommendation
Thread the PR's `head.sha` through `checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch`, and after fetching, verify that the resolved remote branch tip equals the expected SHA. If they differ, either:
- refuse to check out and surface a clear "the pull request has changed since it was fetched" prompt requiring explicit re-confirmation, or
- checkout the ref in a detached/pinned state at the exact expected SHA, matching the content the user actually reviewed/approved, mirroring the `expectedPaymentToken`/`maxTotal` guard added to `mint()` in the referenced fix.

### Proof of Concept
1. Attacker forks a public repository and opens PR #1 from branch `feature` with an innocuous commit.
2. Victim, using GitHub Desktop, receives a "PR review"/"checks failed" notification for PR #1, or simply selects it from the PR list, and clicks "Checkout"/"Switch to pull request".
3. Immediately after the click (or during the network round trip inside `_findPullRequestBranch`), attacker force-pushes `feature` with new commits (e.g., a modified build script, `.vscode/tasks.json`, or a package manifest with a malicious postinstall script).
4. `_findPullRequestBranch` fetches the fork remote and resolves `fork-remote/feature` to the new, attacker-modified tip; `_checkoutBranch` checks it out.
5. Desktop reports success as if PR #1 (the content the victim reviewed) was checked out; the actual working tree contains the attacker's new, unreviewed commits, with no SHA-mismatch warning to the victim.

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }

/**
 * Returns the names of executable Git hooks found in the given repository.
 *
 * @param path   The file system path to the Git repository (root of working
 *               directory).
 * @param gitDir The path to the .git directory for this repository. Used as
 *               the default hooks location when core.hooksPath is not set.
 * @param filter An optional array of hook names to filter the results.
 *               Including '*' will return all hooks.
 */
export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
}

export const createHooksProxy = (
  getShellEnv: (cwd: string) => Promise<ShellEnvResult>,
  tmpHooksDir: string,
  onHookProgress?: HookCallbackOptions['onHookProgress'],
  onHookFailure?: HookCallbackOptions['onHookFailure']
) => {
  return async (conn: Connection) => {
    const startTime = Date.now()
    const proxyArgs = await conn.getArgs()
    const proxyEnv = await conn.getEnv()
    const proxyCwd = await conn.getCwd()
    const hasStdin = await conn.isStdinConnected()

    const hookName = basename(proxyArgs[0], __WIN32__ ? '.exe' : undefined)

    const abortController = new AbortController()
    const abort = () => abortController.abort()
    conn.on('close', abort)

    await writeline(conn.stderr, `Running ${hookName} hook...`)
    onHookProgress?.({ hookName, status: 'started', abort })

    // GIT_ vars are considered safe to pass to hooks unless explicitly excluded
    // GITHEAD_ are set by git-merge (https://github.com/git/git/blob/83a69f19359e6d9bc980563caca38b2b5729808c/builtin/merge.c#L1590)
    const safePrefixes = ['GIT_', 'GITHEAD_']

    const safeEnv = Object.fromEntries(
      Object.entries(proxyEnv).filter(
        ([k]) =>
          safePrefixes.some(prefix => k.startsWith(prefix)) &&
          !excludedEnvVars.has(k)
      )
    )

    if (abortController.signal.aborted) {
      debug(`${hookName}: aborted before execution`)
      await exitWithError(conn, `hook ${hookName} aborted`)
      return
    }

    const stdinPath = hasStdin
      ? join(
          tmpHooksDir,
          `${hookName}-${crypto.randomUUID().slice(0, 8)}.stdin`
        )
      : undefined

    const args = [
      ...['hook', 'run', hookName],
      // We always copy our pre-auto-gc hook in order to be able to tell the
      // user that the reason their commit is taking so long is because Git is
      // performing garbage collection, but it's unlikely that the user has a
      // pre-auto-gc hook configured themselves, so we tell Git to ignore
      // missing hooks here.
      ...(hookName === 'pre-auto-gc' ? ['--ignore-missing'] : []),
      ...(hasStdin ? [`--to-stdin=${stdinPath}`] : []),
      '--',
      ...proxyArgs.slice(1),
    ]

    const terminalOutput: Buffer[] = []
    const gitPath = resolveGitBinary(resolve(__dirname, 'git'))
    const shellEnv = await ensureGitExecPathEnv(await getShellEnv(proxyCwd))

    if (shellEnv.kind === 'failure') {
      let errMsg = `Failed to load shell environment for hook ${hookName}.`
      debug(errMsg)

      if (shellEnv.shellKind) {
        const friendlyName = shellFriendlyNames[shellEnv.shellKind]
        if (shellEnv.shellKind === 'git-bash') {
          errMsg += `\n${friendlyName} not found. Please ensure Git for Windows is installed and added to your PATH.`
        } else {
          errMsg += `\n${friendlyName} not found. Please ensure it's installed and added to your PATH.`
        }
      }

      errMsg += '\n\nConfigure the shell to use in Preferences > Git > Hooks.'

      return exitWithError(conn, errMsg)
    }

    if (hasStdin && stdinPath) {
      try {
        await pipeline(conn.stdin, createWriteStream(stdinPath), {
          signal: abortController.signal,
        })
      } catch (error) {
        const message = abortController.signal.aborted
          ? `hook ${hookName} aborted`
          : `Failed to buffer stdin for ${hookName} hook: ${
              error instanceof Error ? error.message : String(error)
            }`

        debug(message, error instanceof Error ? error : undefined)
        await exitWithError(conn, message)
        onHookProgress?.({ hookName, status: 'failed' })
        return
      }
    }

    const { code, signal } = await new Promise<{
      code: number | null
      signal: NodeJS.Signals | null
    }>((resolve, reject) => {
      const child = spawn(gitPath, args, {
        cwd: proxyCwd,
        // GITHUB_DESKTOP lets hooks know they're run from GitHub Desktop.
        // See https://github.com/desktop/desktop/issues/19001
        env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' },
        signal: abortController.signal,
      })
        .on('close', (code, signal) => resolve({ code, signal }))
        .on('error', err => reject(err))

      // git-hook run takes care of ensuring we only get hook output on stderr
      // https://github.com/git/git/blob/4cf919bd7b946477798af5414a371b23fd68bf93/hook.c#L73C6-L73C22
      child.stderr.pipe(conn.stderr, { end: false }).on('error', reject)
      child.stderr.on('data', data => terminalOutput.push(data))
      conn.stdin.pipe(child.stdin).on('error', reject)
    })
