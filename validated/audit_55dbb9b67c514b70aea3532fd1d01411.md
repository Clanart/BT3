### Title
DkgConfirmer builds the MuSig context over all validators while shares are indexed over non-removed signers, breaking confirmation signing and misattributing blame — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The analog of "state set in a constructor that isn't executed in the actual runtime context" is `SigningProtocol::preprocess_internal` / `share_internal`: the MuSig threshold keys are initialized over `spec.validators()` — the *entire* validator list — while the preprocess/share maps and the embedded participant index are computed over the *non-removed* validators only. Whenever `removed` is non-empty, the participant index space used to construct `ThresholdKeys` disagrees with the index space of the preprocesses fed to `sign()`, so the machine operates on state "constructed" under a different context than the one it executes in.

### Finding Description

`DkgConfirmer::preprocess_internal` collects `participants` from `self.spec.validators()` with no filtering for `self.removed` (coordinator/src/tributary/signing_protocol.rs:280-281, and identically at line 293). These keys are passed to `musig(musig_context(...), key, participants)` inside `SigningProtocol::preprocess_internal` (line 119), which derives our MuSig `Participant` index and the aggregate `group_key` from positions in that full list.

Separately, `threshold_i_map_to_keys_and_musig_i_map` (lines 208-250) computes `our_threshold_i` via `spec.i(removed, ...)` — the index among *non-removed* validators — and re-indexes every signer who provided preprocesses into a compacted MuSig index space `1..=k` over only the non-removed providers (lines 241-244).

When `removed` is non-empty, these two index spaces diverge: `self.params.multisig_params.i()` inside `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:288-313) is our position in the full validator list, while `included` is populated from compacted `1..=k` preprocess keys. Two consequences follow:

1. If our full-list index lands inside `1..=k`, `sign()` hits `FrostError::DuplicatedParticipant`, which `share_internal` maps to `unreachable!` (lines 172-176) — a panic.
2. Otherwise `view(included)` produces a `ThresholdView` over a mismatched signing set and the aggregate key silently includes the removed validators' keys, so any produced signature is bound to a group key nobody intended.

Additionally, `DkgConfirmer::share`/`complete` is invoked from `generated_key_pair` (coordinator/src/tributary/handle.rs:47-60), which unconditionally overwrites `DkgKeyPair` and immediately calls `share` — signing `set_keys_message(set, removed, key_pair)` with a `CachedPreprocess` seed keyed only by `(b"DkgConfirmer", attempt)` (line 275). The seed context binds neither `key_pair`, `removed`, nor the participant set; the file's own header (lines 50-54) admits the "on-chain commitments match presumed preprocess" check is an unimplemented TODO. If `share`/`complete` is ever driven with a differing `key_pair` or preprocess set under the same attempt, the same deterministic nonces sign a second distinct message, enabling secret-share recovery.

### Impact Explanation

When a validator is removed during a DKG attempt (an organic protocol event — a validator that goes offline or is voted out via `RemoveParticipantDueToDkg`), DKG confirmation signing executes with misaligned participant indexes. Outcomes: coordinator panic on `unreachable!` arms, a `set_keys` MuSig signature aggregated over a key that includes removed validators (an unintended-message/unintended-key signature), or — in `complete` (handle.rs:535-545) — a returned `Participant` in the MuSig index space being passed to `spec.reverse_lookup_i(&removed, p)`, misidentifying and fatal-slashing an innocent validator. The unbound cached seed additionally creates a nonce-reuse → root-of-trust key share recovery path if the message or preprocess set varies under one attempt.

### Likelihood Explanation

The trigger — `removed` non-empty at confirmation time — occurs through ordinary protocol operation (any validator removed via `RemoveParticipantDueToDkg` before the attempt's confirmation). No malicious input is required; the defect is a pure index-space inconsistency between `spec.validators()` (line 280) and `spec.i(removed, ...)` (line 216). The nonce-reuse variant requires `generated_key_pair` to run with distinct key pairs or preprocess sets under one attempt, which the code does not defend against (the guarding check is a stated TODO).

### Recommendation

In `DkgConfirmer::preprocess_internal` and `share_internal`, build `participants` from `spec.validators()` filtered by `self.removed` (i.e., only validators for which `spec.i(removed, key)` returns `Some`), so the MuSig index space in `musig()` matches the compacted space used by `threshold_i_map_to_keys_and_musig_i_map`. Additionally, bind the cached-preprocess context to the message actually signed — e.g., derive `CachedPreprocesses` from `(context, set_keys_message digest, preprocesses digest)` — and implement the pending check that our on-chain published commitments equal the commitments derived from the cached seed before publishing shares (signing_protocol.rs:50-54).

### Proof of Concept

1. A validator set runs a DKG attempt where at least one validator `R` is removed (`removed_as_of_dkg_attempt` returns `[R]`), e.g., after a `RemoveParticipantDueToDkg` quorum in `handle_application_tx` (handle.rs:258-284).
2. Confirmation begins: `dkg_confirmation_nonces` → `DkgConfirmer::preprocess` builds `ThresholdKeys` via `musig(...)` over `participants = spec.validators()` — including `R` — so our `Participant` index `i_full` is our position in the full list (signing_protocol.rs:118-121, 280).
3. Non-removed signers publish `DkgShares` with `confirmation_nonces`; removed `R` cannot publish (`accumulate` returns `NotReady` for removed signers, handle.rs:103-105), so `ConfirmationNonces` holds `k-1` entries over the `k` non-removed validators.
4. `generated_key_pair` → `DkgConfirmer::share` → `threshold_i_map_to_keys_and_musig_i_map` maps preprocesses to compacted indexes `1..=k` and inserts `our_threshold_i = spec.i(removed, our_key).start` — a non-removed index (lines 216-244).
5. `AlgorithmSignMachine::sign` pushes `multisig_params.i()` (= `i_full`, computed over all validators) into `included` alongside keys `1..=k` (crypto/frost/src/sign.rs:290-295). With `R` positioned before us, `i_full > i_threshold`, and `included` mixes two index spaces; if `i_full` collides with a compacted key, `DuplicatedParticipant` → `unreachable!` panic (sign.rs:306-309, signing_protocol.rs:175). Otherwise `view(included)` yields a `ThresholdView` over a set whose indexes don't correspond to the MuSig key positions, producing a signature bound to a `group_key` that includes `R` — or an `Err(p)` in the MuSig index space that `complete` mis-translates via `reverse_lookup_i(&removed, p)` into a `RemoveParticipantDueToDkg` against a different, innocent validator (handle.rs:535-545).
6. Independently, `CachedPreprocesses` is keyed only by `(b"DkgConfirmer", attempt)` (signing_protocol.rs:123-137, 275); a second `share`/`complete` under the same attempt with a different `key_pair` (which `generated_key_pair` would overwrite at handle.rs:54) or different `removed` re-derives identical nonces via `ChaCha20Rng::from_seed` (crypto/frost/src/sign.rs:127) and signs a distinct `set_keys_message`, yielding two Schnorr shares `s = d + b·e·ρ + c·share` with identical `d, e` but different challenges `c` — the validator's secret share is then recoverable by linear combination, compromising the MuSig root-of-trust key.
