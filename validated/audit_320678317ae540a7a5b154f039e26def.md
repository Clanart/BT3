Confirmed: `CallDispatcher` at `evm/src/utils/CallDispatcher.sol:25-62` is a shared singleton contract (not deployed per-order), and `IntentGatewayV2.placeOrder` at `evm/src/apps/IntentGatewayV2.sol:203-280` sweeps its *entire* balance rather than the delta produced by that specific order's predispatch call.

### Title
Predispatch escrow sweep steals the shared CallDispatcher's full balance instead of the order's own output - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
When `placeOrder` has a `predispatch` payload, it funds the shared, stateless `CallDispatcher` singleton, executes arbitrary user-supplied calldata on it, then "sweeps" tokens back by reading `dispatcher`'s *total* balance (`address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)`) rather than the amount actually produced by this order's own predispatch call.

### Finding Description
In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:203-280`), the predispatch flow is:
1. Assets are transferred to `dispatcher = _params.dispatcher` [1](#0-0) .
2. `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` executes arbitrary attacker-supplied calldata in the dispatcher's own context [2](#0-1) .
3. The gateway then reads `dispatcher`'s balance directly (`address(dispatcher).balance` or `IERC20(token).balanceOf(dispatcher)`) to build a sweep call that transfers that **entire** balance to the gateway: [3](#0-2) 
4. `received` is then computed and any excess over `order.inputs[i].amount` is only *logged* as `DustCollected`, while the funds physically remain escrowed in the gateway under this attacker-controlled order's commitment [4](#0-3) .

Crucially, `CallDispatcher` (`evm/src/utils/CallDispatcher.sol:25-62`) is a single stateless, shared contract used by every `placeOrder`, `fillOrder`/`_execute` (`evm/src/apps/intentsv2/IntentsBase.sol:438-460`) call across all users and all chains — it has a permanent `receive()` and holds whatever value/tokens are sent to it during any in-flight or reverted step. If any residual balance is left on the dispatcher (e.g., another concurrent transaction's predispatch/output leg reverts, is front-run, sends dust, or completes a swap with slippage leftovers, or an unrelated `_execute` sweep from a different order's fill is still in flight in the same block), the corrupted value read is `address(dispatcher).balance` / `balanceOf(dispatcher)` — a shared, non-order-scoped value — instead of the delta actually attributable to *this* order's own predispatch execution.

Because the sweep transfers the dispatcher's *entire* current balance to the calling order's placer, and the code only compares `received` against the order's declared amount to decide whether to log "dust" (never returning it to whoever it belonged to), an attacker can construct a predispatch call that leaves the dispatcher underfunded/empty on entry, then win a race (or simply act opportunistically) to place an order right when the dispatcher is transiently holding another party's tokens (e.g., mid-execution of another user's own `placeOrder` predispatch, or leftover balance from a reverted/aborted composed call earlier in the same block), and capture those funds into their own escrowed order.

This is the direct analog of the CGC bug: the code re-derives a decision-critical value (`balance`) from **shared mutable state that is not scoped/cached to the operation's own delta**, and every downstream calculation (`requiredAmount` check, `balancesBefore`, `received`) trusts that raw read as if it exclusively reflected this order's own predispatch output.

### Impact Explanation
This is a direct fund-theft vector: any transient or leftover balance sitting in the shared `CallDispatcher` — belonging to a different order/caller — can be swept into an unrelated attacker's escrow via `placeOrder`'s predispatch sweep, resulting in wrong-beneficiary fund movement and loss for the original balance owner. It falls squarely within "stealing or loss of funds" and "logic attacks" in the bounty's accepted impact set, since the shared dispatcher's balance is treated as this-order-exclusive without any accounting isolation (no per-call escrow accounting, no `msg.sender`-scoped balance tracking, no atomic pull-then-verify against a pre-call snapshot that excludes shared residue).

### Likelihood Explanation
Likelihood depends on whether the `CallDispatcher` can realistically hold residual balance belonging to another party at the moment a competing `placeOrder` predispatch sweep executes (e.g., via multiple `placeOrder`/`fillOrder`/`_execute` calls interleaved in the same block, a partially-failed multi-call batch that leaves dust, or a griefing counterparty deliberately sending tokens to the publicly-known dispatcher address right before an attacker's `placeOrder` transaction). Since `CallDispatcher`'s address is public and it accepts arbitrary incoming ETH/tokens via `receive()`/ERC20 transfers with no access control, an attacker fully controls the timing of their own `placeOrder`+predispatch call and can engineer scenarios (e.g., self-created leftover dust from a previous own transaction, or opportunistic sniping of a pending transaction visible in the mempool) to trigger the sweep while exploitable balance sits on the dispatcher.

### Recommendation
Track and sweep only the delta actually produced by *this order's own* predispatch call, not the dispatcher's raw balance:
- Snapshot `dispatcher`'s balance/`balanceOf` immediately **before** step 1 (asset transfer-in) rather than only immediately before the sweep dispatch, and use `postDispatchBalance - preDispatchBalance` bounded to `requiredAmount` as the sweep amount.
- Alternatively, make the `CallDispatcher` non-shared per invocation (deploy ephemerally, or use a `transfer(exact amount)` call rather than "sweep full balance") so no cross-order state can leak in.
- Enforce that the sweep call transfers exactly `requiredAmount` (or the newly-produced delta) rather than the dispatcher's total balance, closing the "steal shared residual balance" path entirely.

### Proof of Concept
Conceptual sequence (cannot be fully instrumented without a live fork/mempool, but the code path is deterministic):
1. Some balance `B` (native ETH or ERC20) ends up sitting on the shared `CallDispatcher` address — e.g., left over from another user's in-flight `placeOrder` predispatch step 1 (`evm/src/apps/IntentGatewayV2.sol:212-220`) that has transferred assets to `dispatcher` but not yet completed its own sweep in the same transaction, or dust from a prior `_execute` sweep (`evm/src/apps/intentsv2/IntentsBase.sol:438-460`).
2. Attacker calls `placeOrder` with a trivial `predispatch.call` (e.g., a no-op call to any contract) and `predispatch.assets` set to a minimal amount, and `order.inputs[i].amount == B` (or less).
3. At `evm/src/apps/IntentGatewayV2.sol:236-251`, `balance = address(dispatcher).balance` (or `balanceOf(dispatcher)`) reads the *combined* balance including the unrelated `B`, satisfies `balance >= requiredAmount`, and the full `balance` (including `B`) is swept to the gateway and escrowed under the attacker's `commitment`.
4. The rightful owner of `B` loses those funds; the attacker's order now holds more escrowed value than they contributed, ready to be withdrawn on cancel/fill settlement.
