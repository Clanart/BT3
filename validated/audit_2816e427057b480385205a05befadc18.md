## Finding: Protocol-fee amount mismatch permanently locks escrowed funds on order cancellation

### Title
Escrow refund reverts and permanently locks user funds when protocol fees are enabled - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` escrows the **protocol-fee-reduced** input amount, but every cancellation/refund path (`cancelOrder`, and the `WithdrawalRequest` it constructs) uses the **original, un-reduced** `order.inputs` amount when calling `withdraw()`. Because `withdraw()` only guards against a fully-empty escrow slot (`== 0`) instead of verifying `amount <= escrowed`, the closing subtraction underflows and reverts whenever a fee was applied — permanently trapping the user's escrowed tokens with no way to cancel or refund them. This is the same bug class as the Linea report: a value that is transformed/stored under one representation (`DEPLOYED_STATUS` vs `NATIVE_STATUS`, here "reduced" vs "original" amount) is checked/consumed elsewhere using an incompatible representation, and the guard doesn't account for the valid alternate state, causing funds to be locked.

### Finding Description
In `placeOrder`, when `protocolFeeBps > 0`, the amount stored in escrow is the fee-reduced amount: [1](#0-0) [2](#0-1) 

```
_orders[commitment][token] += reducedInputs[i].amount;
```

But every cancellation/refund flow builds its `WithdrawalRequest` using `order.inputs` — the full, un-reduced amount — not `reducedInputs`:

- Same-chain cancel: [3](#0-2) 
- Source-chain GET-based cancel context: [4](#0-3) 
- Destination-chain `RefundEscrow` dispatch: [5](#0-4) 

All three feed into `withdraw()`, which checks the escrow slot only for zero, then subtracts the (larger) requested `amount`: [6](#0-5) 

```
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
...
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
...
_orders[body.commitment][token] -= amount;
```

Since `amount` (`order.inputs[i].amount`, the pre-fee amount) is strictly greater than `_orders[body.commitment][token]` (the post-fee amount actually escrowed) whenever `protocolFeeBps > 0`, the unchecked-looking subtraction is actually Solidity 0.8 checked arithmetic and underflows, reverting the whole transaction. The `== 0` guard does not catch this because the balance is non-zero, just insufficient — exactly analogous to the Linea bug where the check only handled one specific status/value and not the other valid one (`DEPLOYED_STATUS`).

### Impact Explanation
Any order placed while a nonzero destination-specific or default protocol fee (`_params.protocolFeeBps` / `_destinationProtocolFees[...]`) is configured can never be successfully cancelled/refunded through `cancelOrder`: the same-chain path, the source-chain GET-response path, and the destination-chain `RefundEscrow` dispatch path all revert on the underflow inside `withdraw()`. If the order also isn't filled by a solver (destination-chain fill flow is not present in this contract and may itself carry the same or a different amount convention), the user's escrowed input tokens are permanently stuck in the `IntentGatewayV2` contract with no recovery path — a direct, unrecoverable loss of user funds, matching the bounty's "loss of funds" / "bridge custody must move exactly once and only to the rightful beneficiary and amount" criteria.

### Likelihood Explanation
This is triggerable by any ordinary user placing an order on any deployment/chain pair where a protocol fee is configured (a normal, expected operating configuration, not an edge case) and then attempting to cancel it — no privileged actor, malicious relayer, or governance action is required. The bug reproduces deterministically on every cancellation attempt once `protocolFeeBps > 0`.

### Recommendation
Store and pass the fee-reduced amount consistently through every code path that touches `_orders`. Concretely, `cancelOrder` should build the `WithdrawalRequest.tokens` from the same reduced amounts that were escrowed (e.g., by recomputing `reducedInputs` from `order.inputs` and `protocolFeeBps`/`_destinationProtocolFees`, mirroring the exact logic in `placeOrder`), rather than reusing `order.inputs` directly. Additionally, `withdraw()` should replace the `== 0` check with a proper `amount > _orders[body.commitment][token]` bound check that reverts clearly instead of relying on an arithmetic underflow, so any future mismatch fails safely rather than silently locking funds.

### Proof of Concept
1. Admin/governance sets `_params.protocolFeeBps = 100` (1%) via `setParams`/`UpdateParams`.
2. User calls `placeOrder` with `order.inputs = [{token: USDC, amount: 1000}]`. `reducedInputs[0].amount = 990` is computed and `_orders[commitment][USDC] += 990` is stored (`placeOrder`, lines 356-368, 434-435).
3. Order expires without being filled. User (or anyone, per the expiry branch) calls `cancelOrder(order, options)`.
   - Same-chain case: `withdraw()` is invoked with `body.tokens = order.inputs = [{USDC, 1000}]` (line 527-530).
   - `withdraw()` executes `token.call(transfer(beneficiary, 1000))`, succeeding since the contract holds pooled balances across orders, then attempts `_orders[commitment][USDC] -= 1000` where `_orders[commitment][USDC] == 990` — this underflows and reverts (Solidity 0.8 checked math), reverting the entire `cancelOrder` transaction.
4. Every subsequent cancellation attempt for this order reverts identically; the user's 990 USDC remains locked in the contract indefinitely.
