### Title
`ReceivedOutput::read` accepts an offset/script_pubkey mismatch, recording funds as received that can never be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes the spending `offset`, the `TxOut`, and the `OutPoint` independently, with no check that the offset actually derives the key committed to by `output.script_pubkey`. The only consistency check happens much later in `SignableTransaction::multisig`, which silently returns `None` on mismatch. A `ReceivedOutput` decoded from untrusted bytes can therefore describe an on-chain output the threshold key cannot spend — the analog of "funds deposited into the bridge with no withdraw path."

### Finding Description
`Scanner` guarantees by construction that a scanned output's `script_pubkey` equals `p2tr_script_buf(key + G*offset)` (`scan_transaction`, mod.rs:199-214; `register_offset`, mod.rs:180-196). That invariant is lost when a `ReceivedOutput` is reconstructed from bytes:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output = TxOut::consensus_decode(&mut buf_r)...;
  let outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

`read_F` accepts any canonical scalar, and the `TxOut` carries an arbitrary `script_pubkey`. Nothing binds them. `SignableTransaction::new` (send.rs:150-256) then treats `input.output.value` as spendable balance for fee/change math, and only at `multisig()` time (send.rs:275-279) does the check `p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey → None` fire — aborting the signing machine with no error, no retry path, and no way to substitute a corrected offset. Worse, the value accounting uses the attacker-controlled `TxOut` embedded in the bytes, not chain truth, so a crafted `ReceivedOutput` can inflate `input_sat`, causing real spendable inputs bundled alongside to be consumed by a transaction that can never be signed.

### Impact Explanation
Funds reported received that are not spendable. A `ReceivedOutput`/`Output` decoded from untrusted bytes (this type is deserialized by peers' `Output::read` paths) whose `offset` does not map to its `script_pubkey` causes `multisig()` to return `None`, permanently blocking spending of every input in the batch — including legitimate ones. There is no recovery path, mirroring the reported bug class (stuck funds, no withdraw).

### Likelihood Explanation
Reachable by an unprivileged party wherever serialized `Output`/`ReceivedOutput` bytes cross a trust boundary (network messages, coordinator-supplied plans). The mismatch is a single flipped scalar or substituted `TxOut`; detection is deferred to a `None` return that callers cannot distinguish from "wrong keys."

### Recommendation
Validate at parse time: either store/derive the expected script from the offset and reject mismatches in `ReceivedOutput::read` (requires carrying the group key context), or make `multisig()`/`SignableTransaction::new` return a distinct error identifying the offending input so it can be quarantined rather than stalling the whole transaction.

### Proof of Concept
1. Obtain a valid `ReceivedOutput` for group key `K` with offset `o`.
2. Serialize it, then replace the offset bytes with `o + 1` (or replace `output.script_pubkey` with a different P2TR script) and feed the bytes to `ReceivedOutput::read` — it succeeds.
3. Pass it to `SignableTransaction::new` together with a genuine input, then `multisig(keys)` returns `None` (send.rs:277-279): the genuine input's funds are unspendable through this flow with no error surfaced.
