### Title
Missing identity check on DKG encryption keys lets a participant force ECDH to the identity point, leaking their secret shares to any observer - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
`EncryptionKeyMessage::read` accepts any canonically-encoded group element as a participant's share-encryption public key (`enc_key`), including the identity point. When a PedPoP participant registers `enc_key = identity`, every honest participant who encrypts a secret share to them computes `ecdh = ephemeral_scalar * identity = identity`, producing a ChaCha20 key derived solely from the public context and the constant identity encoding. All secret shares addressed to the malicious participant are then encrypted under a publicly known key, and any passive observer of the authenticated channel can decrypt them and recover that participant's FROST secret share. This is an "insufficient input validation of untrusted bytes fed to a `read` API" analog of CVE-2019-11098, reachable entirely by an unprivileged DKG participant.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `EncryptionKeyMessage::read` parses the per-participant encryption key with `C::read_G`, which enforces canonical encoding but imposes no semantic validation — no rejection of the identity element:

```rust
// crypto/dkg/pedpop/src/encryption.rs:57-59
pub fn read<R: io::Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
  Ok(Self { msg: M::read(reader, params)?, enc_key: C::read_G(reader)? })
}
```

`C::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only checks that the point decodes and re-encodes canonically; the Ristretto/Ed25519 identity encoding passes both checks.

`Decryption::register` stores this key with no validation beyond a duplicate-participant assert (`encryption.rs:351-362`). Later, `encrypt` computes the shared secret as `ephemeral_key * enc_key` (`encryption.rs:95-97`, `153-154`). For `enc_key = identity`, the ECDH result is always the identity point. `cipher` (`encryption.rs:101-133`) then derives the ChaCha20 key by transcribing `context` and `shared_key.to_bytes()` — both fully public/constant — and uses a static IV (`b"DKG IV v0.2\0"`). The keystream is therefore reproducible by anyone who knows the protocol context.

The malicious participant's own decryption path (`Encryption::decrypt`, `encryption.rs:487-488`) computes `enc_priv * ephemeral_pub`, which is *not* the identity, so the attacker cannot decrypt their own shares either — but that is not needed: the objective is to leak their incoming shares to colluding or passive observers. In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-490`), every other participant's `SecretShare` ciphertext to this participant is protected only by this public keystream, so an observer recovers `share_j(P)` for every sender `j`, and hence P's full secret share `Σ_j poly_j(P)` and corresponding `ThresholdKeys` secret share.

Nothing upstream rejects the key either: `verify_r1` (`pedpop/src/lib.rs:315-331`) only validates the PoK signature over the commitments and the message count; `enc_key` is never inspected.

### Impact Explanation
The PedPoP DKG's confidentiality guarantee — that each participant's secret share is known only to them — is broken for the attacking participant's share. A passive observer (or any participant who later obtains the ciphertexts) recovers a valid FROST `secret_share` corresponding to a `verification_share` in the final `ThresholdKeys` (`pedpop/src/lib.rs:479-484, 528`). This reduces the effective security of the threshold key: the attacker needs only `t - 1` additional shares to reconstruct the group private key, and in any composition where a single share is meaningful (e.g., share-targeted coercion, or a later compromise of `t - 1` parties), the margin is gone. Per the assessment criteria this is key-share recovery caused by insufficient validation of untrusted bytes supplied through `EncryptionKeyMessage::read`/`read_G`.

### Likelihood Explanation
The attack requires only that one DKG participant broadcast a malformed `EncryptionKeyMessage` — a single canonical identity encoding in place of a real `enc_key`. No honest participant rejects it: `read_G` accepts it, `register` stores it, and `encrypt` uses it without complaint. The protocol completes apparently normally for the attacker (they are faulty anyway), while every honest sender unknowingly publishes the attacker's share contributions encrypted under a constant key. The only mitigating factor is that the leaked material is one participant's share rather than the group key directly, keeping this at Medium severity.

### Recommendation
Reject degenerate encryption keys at deserialization/registration time. In `Decryption::register` (and/or `EncryptionKeyMessage::read`), check `bool::from(msg.enc_key.is_identity())` and return an error; more generally, consider requiring a proof of possession for `enc_key` (a Schnorr PoK bound to `context` and `participant`, mirroring the existing PoP on per-message keys) so that a registered key provably has a known discrete logarithm and the ECDH result is never the identity.
