### Title
Unchecked `u64` arithmetic allows payment/fee overflow into an invalid signed Bitcoin transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts and multiplies the fee rate without checked arithmetic, allowing the accounting values to wrap while the transaction retains the original oversized outputs. [1](#0-0) [2](#0-1)  The resulting transaction can proceed through threshold signing because signing commits to the already-created transaction and prevouts rather than rechecking the wrapped totals. [3](#0-2) 

### Finding Description
`input_sat` and `payment_sat` are computed with `sum::<u64>()`, and `payment_sat + needed_fee` and `payment_sat + fee_with_change` use unchecked addition. [1](#0-0) [4](#0-3)  In an optimized build, `u64` overflow wraps, so two payments of `1 << 63` make `payment_sat` become zero while both `TxOut`s are still created with `Amount::from_sat(1 << 63)`. [5](#0-4)  The insufficient-funds check then compares the input total against the wrapped payment total plus fee rather than the actual output total. [6](#0-5)  Similarly, `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change` can wrap to a small fee and bypass the intended fee accounting. [7](#0-6) [8](#0-7) 

### Impact Explanation
An unprivileged requester who can cause chosen payment amounts to be included can cause the threshold wallet to produce threshold signature shares for a transaction whose declared outputs exceed its actual inputs. [9](#0-8) [5](#0-4)  `multisig` only verifies that each prevout script corresponds to the offset key, not that the arithmetic used during construction remained valid. [10](#0-9)  Signing then computes a Taproot sighash over the malformed transaction and all prevouts and each participant signs that digest. [11](#0-10)  `complete` attaches the resulting Schnorr signatures to the malformed transaction and returns it, yielding a concrete signing of an unintended, consensus-invalid transaction. [12](#0-11) 

### Likelihood Explanation
The overflow requires only two payment amounts of `2^63` satoshis or another combination whose sum wraps to a small value; each amount independently passes the existing dust check because it is far above `DUST`. [13](#0-12) [14](#0-13)  The issue is exploitable where payment values originate from withdrawal or transaction requests and where release builds disable integer-overflow checks. [9](#0-8) [5](#0-4)  In debug builds the same input may panic instead of producing the malformed transaction, but the arithmetic is still not a safe release-mode authorization boundary. [6](#0-5) 

### Recommendation
Compute `input_sat` and `payment_sat` with `checked_add` or `try_fold`, compute both fee values with `checked_mul`, and compare funding using a checked `payment_sat.checked_add(needed_fee)` calculation. [1](#0-0) [4](#0-3)  Reject any payment or aggregate amount exceeding Bitcoin’s `MAX_MONEY`, and return a transaction-construction error rather than wrapping or panicking. [15](#0-14)  Apply the same checked arithmetic to `fee()` so fee reporting cannot underflow after construction. [16](#0-15) 

### Proof of Concept
A caller supplies two payments whose amounts each equal `1u64 << 63`; `payment_sat` wraps to zero while the constructed transaction still contains two outputs of `2^63` satoshis. [5](#0-4)  With one legitimate spendable `ReceivedOutput` sufficient to cover the normal fee, `input_sat < payment_sat + needed_fee` succeeds or fails based on the wrapped total and permits construction. [17](#0-16) [6](#0-5)

  (payment_script_1, 1u64 << 63),

The generated sighash commits to the malformed transaction and all prevouts, and successful `complete` returns the transaction with witness signatures attached. [3](#0-2) [18](#0-17)

    mut self,
