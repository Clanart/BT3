### Title
`x()`/`x_only()` panic on the point at infinity, crashing signers on attacker-controlled nonces - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The external report describes a getter (`getUnderlyingPrice`) whose callers expect a graceful return value on error, but which instead reverts deep inside its call tree (`sampleSupply` → `require`). The Serai analog lives in `networks/bitcoin/src/crypto.rs`: `x()` and `x_only()` unconditionally `expect` that the point passed is not the point at infinity, yet they are reachable from `Hram::hram` / `Schnorr::verify` with an aggregate nonce `R` that a malicious signing participant can force to be the identity element. The result is a panic — an abort of the honest signer — instead of a graceful `FrostError`/failed verification, exactly matching the "revert where the caller expects a non-exceptional result" bug class.

### Finding Description
`x()` extracts the x-coordinate of a `ProjectivePoint` and panics on the point at infinity:

```rust
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
``` [1](#0-0) 

`x_only()` does the same via `XOnlyPublicKey::from_slice(...).expect(...)`: [2](#0-1) 

These are called from `Hram::hram`, which hashes `x(R)` and `x(A)` to derive the BIP-340 challenge during `sign_share` and `verify`: [3](#0-2) 

The aggregate nonce `R` is the sum of the per-participant nonces supplied as public preprocess data (untrusted bytes reaching `read_G` / the `nonce_sums` argument). A malicious participant who knows (or waits to observe) the other participants' nonce sums can publish their own nonce `D_i = -(Σ D_j)`, making the aggregate `R = Σ D = identity`. When the honest signer's `sign_share` (or the aggregator's `verify`) evaluates `Hram::hram(&R, &A, m)`, `x(&identity)` hits `expect("point at infinity")` and the process aborts. The documentation itself concedes the panic exists ("This may panic if called with nonces ... which are the point at infinity", dismissing it as "negligible probability"), but the probability is not negligible when the nonce is adversarially chosen rather than random: [4](#0-3) 

The correct shape is for `verify`/`verify_share` to return `None`/`Err` (the non-exceptional error channel already used throughout `frost::algorithm::Algorithm`), instead of panicking — the direct analog of "return `0` instead of reverting".

### Impact Explanation
Any participant in a threshold signing session can force every other honest signer (and the aggregator) to panic/abort by contributing a preprocess nonce that zeroes out the aggregate `R`. This is a reachable denial of service of the signing protocol from purely public, attacker-supplied bytes — no malicious node operator, leaked keys, or collusion required. In a validator context this can stall multisig signing or, where panics propagate across FFI/task boundaries, crash the processor. Severity is bounded to Medium because it is liveness/availability impact with no key leakage, matching the external report's classification.

### Likelihood Explanation
The attacker only needs to be a signing-set participant publishing a preprocess message — the weakest reachability tier allowed by scope. They select their nonce after learning the sum of the others' nonce commitments (or can hit the identity for `R` in `verify_share`/`hram` paths that sum attacker-influenced points). No timing luck is involved; the identity output is deterministic once the nonce is chosen. The only mitigating factor is whether upstream `read_G` rejects identity encodings, which I could not fully verify in the available iterations — if `read_G` for secp256k1 accepts the identity encoding (compressed point `0x0000...` is not valid SEC1 for identity, but additive cancellation `D_i = -ΣD_j` produces a valid non-identity encoding per participant while the *sum* is identity), the attack works regardless of per-point validation, since each individual nonce point is a valid curve point. That makes this reliably reachable.

### Recommendation
Make `x()`/`x_only()` total: return `Option<[u8; 32]>`/`Option<XOnlyPublicKey>` and propagate `None` up through `Hram::hram` (which must become fallible, or the `Schnorr` `Algorithm` impl must pre-check `nonces`/`group_key` for the identity point before hashing and return `FrostError`/`None` from `verify`). `verify_share` should reject any participant whose contribution drives the nonce sum to the identity rather than panicking. At minimum, guard `sign_share`/`verify`/`verify_share` with an early `is_identity()` check on the aggregated `R` and `A` and return the existing error channel — the direct equivalent of the report's "use try/catch and return 0 when errored" mitigation.

// Attacker is participant i in a t-of-n signing session.
// After observing the other participants' nonce commitments/preprocesses,
// the attacker publishes nonce commitments D_i, E_i such that:
//     D_i = -(sum of all other participants' D_j)
// Each participant's D_j is a valid, non-infinity secp256k1 point, so
// per-point encoding checks pass. But the binding-factor aggregate:
//     R = sum_j B_j * D_j
// can be driven to ProjectivePoint::IDENTITY (e.g. all binding factors 1,
// or more generally the attacker chooses D_i to cancel the weighted sum).
//
// Honest signer path:
//   sign_share(params, nonce_sums, nonces, msg)
//     -> IetfSchnorr::sign_share computes R = aggregate(nonce_sums)
//     -> Hram::hram(&R /* == identity */, &A, msg)
//     -> x(&R) -> to_encoded_point(true) has no x-coordinate
//     -> .expect("point at infinity") => PANIC, honest signer aborts
//
// Aggregator path:
//   verify(group_key, nonces, sum)
//     -> same hram call => same panic instead of returning None.
//
// Triggering input is only the attacker's published preprocess
// (public message bytes); no secret access, no malformed encodings needed.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
