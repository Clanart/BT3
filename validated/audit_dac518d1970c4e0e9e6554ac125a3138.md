### Title
Unchecked `payment_sat + needed_fee` addition bypasses the insufficient-funds bound and produces an unspendable transaction / panic - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` validates that inputs cover payments plus the fee with a plain `u64` addition (`input_sat < (payment_sat + needed_fee)`). Because each `payment.1` is an attacker-influenced `u64` transaction amount, a crafted payment sum can overflow, wrapping the bound below `input_sat`. The analog to CVE-2018-20194's mishandled "limit <= value" case is direct: a limit-check expression is evaluated on a value that was allowed to wrap before comparison. The resulting `SignableTransaction` then contains outputs exceeding inputs, and `fee()` computes `sum(inputs) - sum(outputs)` with an unchecked subtraction that underflows (panic in debug, wrapped garbage fee in release), while the FROST machines still produce valid signatures over a consensus-invalid transaction.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), `payment_sat` is the raw `u64` sum of all requested payment amounts, and `needed_fee` is `fee_per_vbyte * vbytes` (also unchecked multiplication). The insufficient-funds check is:

```rust
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
``` [1](#0-0) 

If `payment_sat + needed_fee` exceeds `u64::MAX`, the addition overflows. In debug builds it panics; in release builds it wraps to a small value, the `NotEnoughFunds` check is bypassed, and `tx_outs` retains payments worth more than all inputs combined. The follow-up change computation uses `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228), so no change output is pushed, but the oversized payment outputs remain. The signed transaction is consensus-invalid (outputs > inputs, output values exceeding `MAX_MONEY` are even rejected by `Amount` invariants downstream) and `SignableTransaction::fee()` (`sum(inputs) - sum(outputs)`, lines 139-141) underflows, panicking or returning a wrapped nonsense fee — the same underflow shape as the reference bug, where the guard condition was evaluated after a value had already wrapped.

### Impact Explanation
- Denial of service: a signing session built on such a transaction panics in `fee()` (or at the `payment_sat + needed_fee` addition itself in debug builds) and the resulting tx is rejected by the Bitcoin network, so the threshold group burns a signing round and produces an unspendable/invalid transaction.
- The unwrapped arithmetic also means `fee()` can return a wrapped value while callers (e.g., `prepare_send`-style accounting) rely on it for operating-cost bookkeeping.

### Likelihood Explanation
Triggering it requires a payment amount large enough that `payment_sat + needed_fee` overflows `u64` — i.e., a single payment near `u64::MAX` or a sum of payments approaching it. Such amounts exceed Bitcoin's supply and would only be reachable if upstream plan/payment construction fails to bound amounts before calling `SignableTransaction::new`. That precondition limits it to a Medium-severity robustness/DoS issue rather than an exploitable signature forgery; the nonce binding, `Prevouts::All` sighash, and per-input re-keying in `TransactionSignMachine::sign`/`complete` are otherwise correctly enforced (send.rs lines 355-428).

### Recommendation
Use `checked_add`/`checked_sub` (or `Amount`'s checked arithmetic) for `payment_sat`, `needed_fee`, and the `fee()` subtraction, returning `TransactionError::NotEnoughFunds`/`TooMuchData`-style errors on overflow, e.g. `input_sat < payment_sat.checked_add(needed_fee).ok_or(NotEnoughFunds)?`.

### Proof of Concept
```rust
// Regtest-style; any script that serializes works.
let output: ReceivedOutput = /* an input worth 1_000_000 sats */;
let script = p2tr_script_buf(some_even_key).unwrap();
// payment_sat + needed_fee overflows u64
let payments = [(script.clone(), u64::MAX - 10), (script, 1000)];
// Debug: panics on `payment_sat + needed_fee`.
// Release: wraps, NotEnoughFunds bypassed, tx built with outputs >> inputs.
let tx = SignableTransaction::new(vec![output], &payments, None, None, 1);
// tx.fee() then computes 1_000_000 - huge -> u64 underflow panic
```
The wrapped tx is consensus-invalid (`outputs > inputs`), so even though `multisig()`/`sign()`/`complete()` produce valid Schnorr shares, the broadcast fails — a reachable underflow panic/invalid-signature-output path from attacker-controlled payment amounts.
