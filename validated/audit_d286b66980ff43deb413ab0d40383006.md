Found the analog. `determineMergeability` in `app/src/lib/git/merge-tree.ts` mirrors the Phoenix SDK flaw closely: it treats `git merge-tree` exit code `1` as a normal, parseable outcome and blindly derives conflict state from stdout without distinguishing a real "no conflicts / conflicts found" result from other failure modes that also happen to exit non-zero and still emit stdout.

### Title
Merge-tree conflict computation trusts stdout on non-zero exit without validating error class - ([File: app/src/lib/git/merge-tree.ts])

### Summary
`determineMergeability` calls `git merge-tree --write-tree --name-only --no-messages -z <ours> <theirs>` and accepts exit codes `0` and `1` as equally valid for parsing. [1](#0-0) 
It then unconditionally parses `stdout` by counting NUL bytes to infer the number of conflicted files, only special-casing the `CannotMergeUnrelatedHistories` git error via a `.catch`. [2](#0-1) 

### Finding Description
`git merge-tree --write-tree` can exit with code `1` for multiple distinct situations (merge conflicts, or other non-fatal problems reported via the `--name-only` machine format), but the code does not check `result.gitError` or otherwise validate *why* the command exited `1` before trusting `stdout` — it only carves out the single `CannotMergeUnrelatedHistories` case in the rejection path. Any other error condition that also causes exit code 1 while still writing partial/unexpected NUL-separated content to stdout will be silently misinterpreted through the `(stdout.match(/\0/g)?.length ?? 0) - 1` heuristic, producing an incorrect `ComputedAction` (`Clean` vs `Conflicts` vs correct count). This is structurally identical to the Phoenix bug: the caller widens its "acceptable" outcome space (all exit codes it doesn't explicitly reject) and then processes the raw payload as trustworthy without checking a proper success/error discriminant field (`gitError`) that the wrapper (`git()` in `app/src/lib/git/core.ts`) already computes for exactly this purpose. [3](#0-2) 

`ours` and `theirs` are branch tips that can point at commits/trees introduced by a fetched/cloned remote (e.g. a PR branch or a malicious fork a user is comparing against), so the attacker fully controls the tree contents that `git merge-tree` operates on and, indirectly, the shape of git's stdout/exit behavior for degenerate trees (e.g. crafted submodule entries, huge numbers of path conflicts, or malformed tree structures that git's `--name-only` machine format doesn't cleanly enumerate).

### Impact Explanation
`determineMergeability`'s result (`ComputedAction.Clean` vs `Conflicts`) feeds directly into Desktop's merge/rebase preview UI, which tells the user whether a merge can proceed cleanly. If a maliciously crafted branch causes this heuristic to under-report conflicts (report `Clean` when conflicts actually exist, or a wrong `conflictedFiles` count), the user could be led to merge/commit/push a result that silently drops or overwrites conflicting changes without the expected conflict-resolution step — matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the attacker-controlled branch's tree structure to trigger a `git merge-tree` exit code of `1` through a path other than genuine conflicts (or to produce stdout that miscounts NUL separators), which is not fully confirmed without executing `git merge-tree` against adversarial inputs. This is a plausible but unverified condition, since I could not execute git locally to enumerate all causes of exit code 1 for `--name-only` machine output.

### Recommendation
Check `result.gitError` (as `git()` already computes it) before parsing `stdout`, and only treat the output as parseable when the exit code/error corresponds to the specific "clean" or "conflicts found" cases documented for `git merge-tree --write-tree`; any other non-zero exit/error should be propagated as a failure rather than silently parsed, mirroring the fix pattern used elsewhere in the codebase (e.g. `tag.ts`'s `fetchTagsToPush`, which explicitly checks `exitCode !== 0 && exitCode !== 1` before parsing and rethrows `result.gitError` otherwise). [4](#0-3) 

### Proof of Concept
Not independently reproducible from the index alone — confirming this requires running `git merge-tree --write-tree --name-only --no-messages -z` against a crafted pair of trees (e.g. containing conflicting submodule/gitlink entries or extreme path structures) to find an exit-code-1 scenario that is not `CannotMergeUnrelatedHistories` and observe whether the NUL-count heuristic in `determineMergeability` mis-reports the conflict state. I was unable to execute git or the test suite in this environment to validate that exact trigger, so this should be treated as a code-level structural finding (missing `gitError` discrimination before trusting stdout) rather than a confirmed exploited PoC. [5](#0-4)

import { Branch } from '../../models/branch'
import { ComputedAction } from '../../models/computed-action'
import { MergeTreeResult } from '../../models/merge'
import { Repository } from '../../models/repository'
import { git, isGitError } from './core'
import { GitError } from 'dugite'

export async function determineMergeability(
  repository: Repository,
  ours: Branch,
  theirs: Branch
) {
  return git(
    [
      'merge-tree',
      '--write-tree',
      '--name-only',
      '--no-messages',
      '-z',
      ours.tip.sha,
      theirs.tip.sha,
    ],
    repository.path,
    'determineMergeability',
    { successExitCodes: new Set([0, 1]) }
  )
    .then<MergeTreeResult>(({ stdout }) => {
      // The output will be "<tree-id>\0[<filename>\0]*" so we can get the
      // number of conflicted files by counting the number of null bytes and
      // subtracting one for the tree id.
      const conflictedFiles = (stdout.match(/\0/g)?.length ?? 0) - 1
      return conflictedFiles > 0
        ? { kind: ComputedAction.Conflicts, conflictedFiles }
        : { kind: ComputedAction.Clean }
    })
    .catch<MergeTreeResult>(e =>
      isGitError(e, GitError.CannotMergeUnrelatedHistories)
        ? Promise.resolve({ kind: ComputedAction.Invalid })
        : Promise.reject(e)
    )
}
