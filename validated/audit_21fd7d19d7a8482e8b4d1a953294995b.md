## Title
Uncontrolled recursion in `PuzzleWithRestrictions.from_memo` allows an unauthenticated coin/memo sender to cause wallet process abort via stack exhaustion — (`File: chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody-architecture spec (used by plotnft/pool and custody wallets) from an on-chain hint `Program` (`memo`). When the memo encodes an `MofN` node, the method recurses into itself once per member with no depth bound. Because the `memo` is attacker-controlled data attached to a coin (via the CLVM hint/memo mechanism reachable by any coin creator/spend-bundle submitter), a crafted, deeply-nested `MofN`-of-`MofN`-of-... memo can drive unbounded Python recursion when a victim's wallet parses it, aborting the wallet process — the same bug class as the smithy-rs CVE (uncontrolled recursion in a generated deserializer for a recursive shape, triggered by a small malicious input).

### Finding Description
`PuzzleWithRestrictions.from_memo()` is the single entry point wallets use to interpret custody-architecture (CHIP-0043) memo data attached to coins: [1](#0-0) 

The relevant recursive step is:
```
m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
``` [2](#0-1) 

Each `MofN` node's memo can itself contain further `MofN` member memos, and `member_memos` is parsed directly from attacker-supplied CLVM program data with no cap on either the branching factor or nesting depth: [3](#0-2) 

There is no depth/size check anywhere in `from_memo`, `MofNHint.from_program`, or the calling wallet code before recursing — unlike `sha256_treehash`, which was deliberately rewritten to be iterative specifically to avoid Python stack exhaustion on attacker-influenced CLVM trees: [4](#0-3) 

`from_memo` has no such iterative-safety treatment despite processing untrusted, attacker-shaped input in the same threat model.

This memo-parsing path is invoked by plotnft/pool driver and wallet code when interpreting coins/singletons using the custody architecture: [5](#0-4) 

I was not able to fully trace every call site (e.g., the exact code path in `chia/wallet/plotnft_wallet/plotnft_wallet.py` that feeds a synced coin's hint into `from_memo`) within the tool budget available, so the precise wallet-sync trigger point should be confirmed by a follow-up review of `chia/wallet/plotnft_wallet/plotnft_wallet.py` and `chia/wallet/puzzles/custody/restriction_utilities.py`.

### Impact Explanation
A crafted memo/hint on a coin sent to (or observed by) a victim's wallet — for example inside a plotnft/pool singleton transition, a custody-architecture payment, or any coin whose hint a syncing wallet chooses to interpret as a `PuzzleWithRestrictions` memo — can encode arbitrarily deep nested `MofN` structures. Parsing such a memo drives unbounded Python-level recursion in `from_memo`, exhausting the interpreter stack and aborting/crashing the wallet process. This is a denial-of-service against wallet nodes triggerable by any party able to get a coin with a malicious memo observed by the victim (no signature or special privilege required to construct the memo content itself, since memos are unauthenticated hint data).

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment that actively uses the custody-architecture (CHIP-0043)/plotnft-v2 memo-parsing path in wallet sync, since:
- Memo/hint content is fully attacker-controlled and unauthenticated (hints are not signed or validated against consensus rules).
- No existing bound limits nesting depth or member count before recursive parsing.
- The equivalent CLVM tree-hash code in this same codebase was already hardened against this exact class of stack-exhaustion issue, showing the concern is known project-wide but was not applied uniformly to this newer memo-parsing code.

### Recommendation
Convert `PuzzleWithRestrictions.from_memo()` / `MofNHint.from_program()` parsing to an iterative (stack-based) algorithm, or add an explicit maximum recursion/nesting-depth and member-count check that rejects malformed memos before recursing, mirroring the iterative design already used in `sha256_treehash`.

### Proof of Concept
1. Construct a `MofNHint` `Program` whose `member_memos` list contains an entry that itself is a valid `PuzzleWithRestrictions` memo encoding another deeply nested `MofN` (repeat N times, e.g. N = tens of thousands, well within CLVM program size limits).
2. Attach this memo as a hint/memo on a coin sent to (or otherwise observed by) a victim wallet that runs custody-architecture/plotnft-v2 memo interpretation.
3. When the victim wallet calls `PuzzleWithRestrictions.from_memo()` on the observed memo, the recursive `[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]` call chain recurses N levels deep, exceeding the Python recursion limit and crashing/aborting the wallet process.

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int
    member_memos: list[Program]

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),
