## Title
GitHub Desktop trusts a stale `owner+name` identity when re-associating and rewriting remotes, allowing a repository-squatting attacker to silently redirect fetch/push targets - (`app/src/lib/stores/repositories-store.ts`, `app/src/lib/stores/updates/update-remote-url.ts`)

## Summary
The Sherlock report's root cause is that a derived invariant (`target * n`) is keyed off a value (`e`) that can change server-side, and the protocol never recomputes the invariant against the *current* state, so a stale comparison lets an attacker extract value. GitHub Desktop has a structurally identical pattern: it persists and re-uses a `GitHubRepository` association keyed by the **mutable** pair `owner + name` (`app/src/lib/stores/repositories-store.ts`) instead of GitHub's immutable repository id, and then uses a "did the previously cached URL still match?" comparison in `updateRemoteUrl` to decide whether to *automatically* rewrite the user's git remote — all without re-validating that the entity behind that `owner/name` slug is still the same repository the user originally added.

## Finding Description
`RepositoriesStore` looks up and upserts `GitHubRepository` records using the compound key `[ownerID+name]`: [1](#0-0) 

This key is not GitHub's stable numeric repository id — it is the owner login and repository name, both of which are mutable (renames) and, in the case of the owner login, reusable once a username is freed/changed. `upsertGitHubRepositoryFromMatch` will happily reuse (or newly create) a DB record for whatever repository currently occupies that `owner/name` slug: [2](#0-1) 

Periodically (e.g. on account change, or whenever Desktop needs an authenticating account) `repositoryWithRefreshedGitHubRepository` re-resolves the association by parsing the *current git remote URL* into an `owner/name` pair (`matchGitHubRepository`), fetching that repo from the API, and unconditionally merging the fresh API data into the persisted association: [3](#0-2) 

Note the code's own acknowledgment that it never invalidates this stale mapping (`TODO: We currently never clear GitHub repository associations`) — but the deeper issue is that even the "refresh" path re-derives identity from the same mutable `owner/name` string, so if whatever now sits at that path is a different repository, Desktop treats it as a legitimate continuation of the original one.

Critically, this refreshed data feeds `updateRemoteUrl`, which will **automatically rewrite the local git remote URL** (`git remote set-url`) if the previously cached `gitHubRepository.cloneURL` still equals the current git remote and the protocol matches: [4](#0-3) 

The guard `remoteUrlUnchanged` only checks that the local remote still equals the *stale, cached* `cloneURL` — it does not verify that the repository behind that URL is still the entity the user actually trusted. If a repository's `owner/name` slug is vacated (deletion, rename-away, org/user departure) and later reoccupied by an attacker-controlled repository at the exact same `owner/name`, the next background refresh will:
1. Resolve `owner/name` to the attacker's repository via the GitHub API.
2. See that the cached `cloneURL` (still the old value) matches the user's existing git remote, and that protocols match.
3. Silently call `setRemoteURL` — although in the same-slug-reuse case the URL string is often unchanged, the more consequential effect is that `setGitHubRepository`/`_upsertGitHubRepository` immediately promotes the attacker's repository's metadata (private/public flag, permissions, parent/fork chain) into the trusted association used elsewhere (branch protection checks, `hasWritePermission`, credential/account matching via `findAccountForRemoteURL`/`getAccountForRepository`), and any legitimate rename-redirect scenario where the API's `clone_url` differs will cause Desktop to auto-repoint the remote via `gitStore.setRemoteURL` with no user confirmation.

No existing guard re-validates identity by a stable id; the only checks are string-equality on mutable owner/name and cloneURL/protocol, which is exactly the "stale value not recomputed against current, attacker-influenced state" pattern from the Sherlock report.

## Impact Explanation
- Fetch/push operations, credential lookup (`getAccountForRepository`), and branch-protection/force-push warnings (`refreshBranchProtectionState`, `hasWritePermission`) all key off this potentially-hijacked `GitHubRepository` association, so a squatted `owner/name` can degrade or bypass client-side safety prompts and silently change where the user's commits are pushed/fetched from (`updateRemoteUrl` calling `gitStore.setRemoteURL`).
- This is "silent corruption of what the user commits or pushes," matching the specified valid-impact category (git remote/proxy response controlled by an attacker driving unauthorized changes to local git state) without requiring local access, admin rights, or social engineering beyond normal GitHub repository lifecycle events (delete/rename/username reuse) that are outside the user's control.

## Likelihood Explanation
Exploitation requires a specific precondition — the original repository's `owner/name` slug becoming available for reuse (deletion/rename/username change) and an attacker claiming it before the victim's Desktop client performs its next periodic refresh. This is a real but narrow window and GitHub does provide some protections (e.g., temporary reservation of freed org/repo names), which lowers likelihood from "trivial" to "situational." Still, the underlying code path performs the automatic remote rewrite with zero user confirmation and zero stable-identity check, which is the core defect being reported.

## Recommendation
- Persist and key `GitHubRepository` associations by GitHub's immutable numeric repository id (already available in API responses) rather than `owner+name`.
- Before calling `updateRemoteUrl`'s `setRemoteURL`, or before merging refreshed API data into the cached `GitHubRepository`, verify the immutable id of the fetched repository matches the immutable id of the previously associated repository; if it differs, treat it as a new/unknown repository and prompt the user rather than silently updating.

## Proof of Concept
1. User adds/clones `https://github.com/victim-org/example.git` in Desktop; Desktop persists a `GitHubRepository` row keyed by `(ownerID for victim-org, "example")` with `cloneURL = https://github.com/victim-org/example.git`. [5](#0-4) 
2. `victim-org` renames or deletes the `example` repository (or the org/user is renamed/removed), freeing the `victim-org/example` slug.
3. Attacker creates a repository that resolves to the same `owner/name` pair (e.g., by acquiring the freed org name or by the org recreating a differently-purposed repo under the same name).
4. On the next background refresh (e.g., `refreshSelectedRepositoryAfterAccountChange` → `repositoryWithRefreshedGitHubRepository`), Desktop parses the still-configured local remote URL into `owner=victim-org, name=example`, fetches that repository from the API — now the attacker's — and merges its metadata into the trusted local association. [6](#0-5) 
5. `updateRemoteUrl` compares the (still-matching) cached `cloneURL` to the current remote and, finding `remoteUrlUnchanged && protocolsMatch`, will call `gitStore.setRemoteURL` on any subsequent legitimate rename event without any user prompt, and permission/branch-protection state now reflects the attacker's repository. [7](#0-6)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
