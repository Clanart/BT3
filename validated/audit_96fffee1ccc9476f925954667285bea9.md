### Title
Pointer-created ERC20 view of an arbitrary CW20 token can change balances without a Transfer event, breaking downstream EVM accounting for non-standard CW20 balance mutations - ([File: app/receipt.go], [File: contracts/src/CW20ERC20Pointer.sol], [File: precompiles/pointer/pointer.go])

### Summary
`CW20ERC20Pointer` is a stateless ERC20 wrapper that always queries the live CW20 balance rather than maintaining its own ledger [1](#0-0) . The only mechanism that produces an ERC20 `Transfer`/`Approval` log for this pointer is `translateCW20Event`, which synthesizes logs solely for a hard-coded whitelist of CW20 action strings (`mint`, `burn`, `send`, `transfer`, `transfer_from`, `send_from`, `burn_from`) [2](#0-1) . Any CW20 contract whose balance changes through an execute message that does not surface one of these recognized `action` attributes (e.g. a custom "rebase"/airdrop/interest-accrual/governance-mint routine, which is exactly the "weird-ERC20" class referenced in the source report) will still change `balanceOf()` as observed through the pointer, but will emit no corresponding `Transfer` log on the EVM side.

### Finding Description
Pointer creation for an arbitrary CW20 contract is permissionless — any user can register an ERC20 pointer for any CW20 address via the pointer precompile's `AddCW20`-style entrypoint [3](#0-2) . Once registered, `CW20ERC20Pointer.balanceOf` never uses any local `_balances` bookkeeping; it queries the underlying CW20 contract directly on every read [1](#0-0) , so any change made to the CW20's balances — through *any* CosmWasm execute path, not just the ones proxied by the pointer's own `transfer`/`transferFrom` — is immediately visible to EVM callers.

The only place `Transfer`/`Approval` events are synthesized for this pointer is `app.translateCW20Event`, and it is driven by a closed set of recognized `action` values pulled from the wasm event attributes [4](#0-3) . This is precisely the "weird ERC20" pattern described in the referenced report (tokens whose balance can change without an accompanying `Transfer` event): a CW20 that implements a non-standard action (e.g., an auto-rebase/airdrop/yield-accrual message, or any custom `ExecuteMsg` variant a CW20 author adds beyond the base cw20 spec) will silently desynchronize the pointer's `balanceOf()` results from the EVM-visible event stream, because `GetActionsFromWasmEvent`/`translateCW20Event` only recognizes the standard cw20-base action names.

### Impact Explanation
Any EVM contract or off-chain indexer that treats the pointer's `Transfer` events as the single source of truth for balance changes (a very common ERC20 integration pattern — vaults/lending markets that credit deposits based on incoming `Transfer` events, DEX reserve tracking via event logs, bridges/relays keyed off `Transfer`) will diverge from the real, `balanceOf()`-observable state whenever the wrapped CW20 mutates balances via a non-whitelisted action. This can lead to funds being miscredited or under-credited within any protocol built atop the pointer (fund loss or permanent accounting freeze for affected users), exactly mirroring the impact described in the referenced Optimism-bridge finding: "cannot bridge/settle correctly because balances change without the expected event."

### Likelihood Explanation
Reachable by any unprivileged user: pointer creation for a CW20 is permissionless, and a CW20 contract deployer only needs to add a single custom `ExecuteMsg` variant (or use any CW20 fork with rebasing/airdrop/interest logic) to trigger the gap. No special privileges, governance action, or validator collusion is required — a normal CosmWasm contract deployer plus a normal pointer-registration transaction is sufficient to reproduce the desync.

### Recommendation
Do not rely on a fixed whitelist of CW20 action names to decide whether a `Transfer` log should be synthesized. Instead, detect balance changes generically (e.g., diff `balanceOf` for the addresses touched by any wasm execute against the CW20 contract inside the same transaction, or require pointer-wrapped CW20s to conform to a strict "standard-only" execute schema and reject/flag pointers for tokens exposing additional balance-mutating messages) so that every real balance change on a pointer-wrapped CW20 is guaranteed to have a corresponding synthetic `Transfer` event.

### Proof of Concept
1. Deploy a CW20 contract that extends the base cw20 message set with a custom action, e.g. `{"rebase": {}}`, that increases/decreases holder balances directly in contract storage without emitting an `action=transfer/mint/burn/...` wasm attribute recognized by `translateCW20Event`.
2. Call the pointer precompile to register an `CW20ERC20Pointer` for this CW20 (permissionless, see `AddCW20`/pointer registration entrypoint).
3. Execute the custom `rebase` message on the CW20 directly via CosmWasm, changing a holder's balance.
4. Query `balanceOf()` on the EVM pointer contract — it reflects the new (changed) balance immediately (per `contracts/src/CW20ERC20Pointer.sol:36-42`).
5. Query `eth_getLogs`/receipt logs for the pointer address over the block containing the rebase tx — no `Transfer` event is present, because `translateCW20Event` only recognizes `mint/burn/send/transfer/transfer_from/send_from/burn_from` (`app/receipt.go:154-169`), demonstrating the balance-changed-without-Transfer-event condition.

Note: I could not fully verify whether any additional generic "balance-diff" safety net exists elsewhere in the receipt-generation pipeline beyond `translateCW20Event`; my search of `app/receipt.go` and the pointer contracts found no such fallback, but a live Devin session with full repo access would be needed to rule out any other synthesis path with certainty.
