### Title
Untrusted `ReceivedOutput` bytes can fabricate unspendable wallet funds - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` without authenticating that the outpoint exists, contains the claimed output, or belongs to the wallet, allowing fabricated inputs to be treated as received funds and reach transaction signing. [1](#0-0) 

### Finding Description
`ReceivedOutput::read` deserializes a scalar offset, a consensus-encoded `TxOut`, and a consensus-encoded `OutPoint`, then returns the three fields together without any consistency or provenance check. [1](#0-0) 

Legitimate scanner-created outputs establish this relationship by matching a transaction output’s `script_pubkey` and recording the transaction’s real `OutPoint`. [2](#0-1) 

The deserialized object can bypass that provenance: `SignableTransaction::new` consumes the claimed `OutPoint`, output value, and offset when constructing the transaction input and previous-output data. [3](#0-2) 

Before signing, `SignableTransaction::multisig` only checks that `keys.offset(offset).group_key()` produces the claimed `TxOut` script; it does not verify that the referenced UTXO exists or that the claimed `TxOut` is the actual output at that outpoint. [4](#0-3) 

### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` data can fabricate a wallet receipt naming an arbitrary value and outpoint while using a script derived from the wallet’s public key. [1](#0-0) 

That fabricated receipt can pass the wallet’s local key/script consistency check and be incorporated into a transaction-signing machine even though the claimed input is absent, has a different value, or belongs to a different script on-chain. [4](#0-3) 

The result is funds reported as received that are not actually spendable, with the fabricated input able to influence balance accounting, fee selection, change calculation, and the transaction presented for threshold signing. [3](#0-2) 

### Likelihood Explanation
The required input is only attacker-controlled bytes accepted by `ReceivedOutput::read`; the offset can be zero or another offset matching a publicly known wallet script. [1](#0-0) 

No private key, malformed curve encoding, colluding validator, or invalid transaction is needed because the parser never binds the serialized claim to scanner output or confirmed blockchain data. [2](#0-1) 

The impact is limited to systems that accept these serialized records from an untrusted source rather than treating them as trusted scanner/database state. [1](#0-0) 

### Recommendation
Do not expose `ReceivedOutput::read` as an authentication boundary for received funds. [1](#0-0) 

Deserialize into an explicitly untrusted representation, then revalidate the `OutPoint` against confirmed blockchain data and compare the chain-returned `TxOut` and script to the wallet-derived script before creating a trusted `ReceivedOutput`. [2](#0-1) 

At minimum, document that serialized `ReceivedOutput` values require authenticated storage and add a constructor-time or deserialization-time validation API that checks the output, outpoint, and wallet offset together. [4](#0-3) 

### Proof of Concept
1. Obtain the wallet’s public group key and choose `offset = 0`. [4](#0-3) 
2. Build a `TxOut` with an arbitrary large value and `script_pubkey = p2tr_script_buf(group_key).unwrap()`. [5](#0-4) 
3. Append a fabricated `OutPoint` that does not correspond to that `TxOut`. [1](#0-0) 
4. Feed the concatenated scalar, `TxOut`, and `OutPoint` encodings to `ReceivedOutput::read`; it returns a structurally valid `ReceivedOutput`. [1](#0-0) 
5. Pass it to `SignableTransaction::new` and then `multisig(&keys)`; the script check succeeds because the fabricated `TxOut` uses the wallet script, even though the referenced UTXO is not spendable. [3](#0-2) [4](#0-3)
