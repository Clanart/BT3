### Title
Hookify `tool_matcher` allow-listing enables Bash/Edit/Write/MultiEdit rule bypass via unenumerated tool alias - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._matches_tool` performs a strict, literal, pipe-split equality check against `tool_name` with no normalization or awareness that `Edit`, `Write`, and `MultiEdit` (and any future tool aliases) are functionally equivalent "file write" operations. A `block` rule whose `tool_matcher` frontmatter field enumerates only some of the equivalent tool names (e.g. `"Edit|Write"`) never fires when Claude performs the identical dangerous file mutation via `MultiEdit`, silently allowing the exact operation the rule was written to deny.

### Finding Description
`RuleEngine._rule_matches` (`plugins/hookify/core/rule_engine.py:96-125`) short-circuits to `False` whenever `rule.tool_matcher` is set and `_matches_tool` fails: [1](#0-0) . `_matches_tool` itself does pure string-set membership after splitting on `|`, with no case normalization, no wildcard sub-matching, and — critically — no concept that different `tool_name` values can produce equivalent side effects: [2](#0-1) .

`_extract_field` explicitly supports `MultiEdit` as a first-class file-mutation tool, concatenating all `new_string` values from its `edits` array into the same `new_text`/`content` field that `Edit`/`Write` rules key off of: [3](#0-2) . This confirms the engine treats `MultiEdit` as semantically equivalent to `Edit`/`Write` for content inspection, yet `tool_matcher` treats it as a wholly distinct, unrelated string.

`Rule.from_dict` exposes `tool_matcher` directly from user-authored frontmatter with no validation or canonicalization: [4](#0-3) . A defender writing a `block` rule intended to stop dangerous file writes might reasonably set `tool_matcher: "Edit|Write"` (this exact enumeration style — omitting `MultiEdit` — is the pattern explicitly demonstrated for Claude Code's native hook matcher docs, e.g. `"Read|Write|Edit"`), reasoning that "Edit" and "Write" cover file mutation. Because the sibling `event: file` default classification (used when `tool_matcher` is *not* set) correctly includes `Edit`, `Write`, and `MultiEdit` in `pretooluse.py`'s event routing (`tool_name in ['Edit', 'Write', 'MultiEdit']`, `plugins/hookify/hooks/pretooluse.py:46-49`), the presence of the `tool_matcher` override field creates an inconsistent, narrower enforcement surface that a rule author can unknowingly weaken.

Exploit flow: an attacker who can influence Claude's action selection (e.g. via prompt injection embedded in repository content, an issue/PR body, or tool output that Claude reads) can steer Claude to perform the same dangerous content write using `MultiEdit` instead of `Edit`/`Write` whenever it detects (or is instructed) that a `block` rule targets those two tool names specifically. Since `RuleEngine.evaluate_rules` is invoked identically for all `PreToolUse` events and returns `{}` (allow) whenever no rule matches (`plugins/hookify/core/rule_engine.py:93-94`), the operation proceeds with no `permissionDecision: deny`, bypassing the intended block.

### Impact Explanation
This breaks the core invariant that "a matching block rule must reliably deny the protected operation." A hookify `block` rule guarding against dangerous file content (e.g. writing malicious code, credentials, or CI config) can be routed around by using `MultiEdit`, resulting in unauthorized file mutation that the plugin's approval/deny control was specifically configured to prevent — matching the "Unauthorized local command execution/action that bypasses Claude Code approval or deny controls" impact category, scoped to file-write enforcement rather than direct shell execution (Bash tool names have no equivalent alias in this codebase, so the Bash vector is not demonstrated).

### Likelihood Explanation
Exploitability is conditioned on a specific but plausible defender choice: the rule author must set an explicit `tool_matcher` override that enumerates `Edit`/`Write` without `MultiEdit` (or vice versa/any subset), rather than relying on the default `event: file` classification, which is not vulnerable to this specific bypass. `tool_matcher` is a real, exposed, unvalidated frontmatter field, and the adjacent Claude Code hook-matcher documentation in this same repository trains authors toward exactly this incomplete enumeration style (`"Read|Write|Edit"`), making the misconfiguration realistic and repeatable once present. No admin privilege is needed beyond the ability to get Claude to choose the alternate tool for an otherwise-identical write, which is achievable via ordinary prompt-injection vectors already in scope.

### Recommendation
Normalize tool matching in `RuleEngine._matches_tool` (`plugins/hookify/core/rule_engine.py:127-142`) so that recognized tool-name aliases are grouped by capability class instead of literal string identity — e.g., treat `Edit`, `Write`, and `MultiEdit` as members of a canonical `"file"` capability set, and expand any `tool_matcher` entry referencing one member to implicitly include its aliases (or warn/reject rule files whose `tool_matcher` partially covers a known alias group). At minimum, document and validate that `tool_matcher` for file-mutation rules must include `MultiEdit` alongside `Edit`/`Write`, and add a loader-time lint (`config_loader.load_rule_file`) that flags `tool_matcher` values covering some but not all known aliases for the same operation class.

### Proof of Concept
Unit test extending `plugins/hookify/core/rule_engine.py`'s existing `__main__` harness:
```python
rule = Rule(
    name="block-secret-write",
    enabled=True,
    event="file",
    tool_matcher="Edit|Write",
    action="block",
    conditions=[Condition(field="new_text", operator="contains", pattern="API_KEY=")],
    message="Blocked: secret written to file"
)
engine = RuleEngine()

# Same dangerous content via Write -> correctly blocked
write_input = {"hook_event_name": "PreToolUse", "tool_name": "Write",
               "tool_input": {"file_path": "x.env", "content": "API_KEY=secret"}}
assert engine.evaluate_rules([rule], write_input)["hookSpecificOutput"]["permissionDecision"] == "deny"

# Identical dangerous content via MultiEdit -> bypasses the block rule
multiedit_input = {"hook_event_name": "PreToolUse", "tool_name": "MultiEdit",
                    "tool_input": {"file_path": "x.env",
                                   "edits": [{"old_string": "", "new_string": "API_KEY=secret"}]}}
result = engine.evaluate_rules([rule], multiedit_input)
assert result == {}   # FAILS to deny — demonstrates the bypass
```
Expected assertion failure on current code confirms that the identical protected content write is denied via `Write`/`Edit` but silently allowed via `MultiEdit`, validating the tool-matching representation gap.

```python
    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```
