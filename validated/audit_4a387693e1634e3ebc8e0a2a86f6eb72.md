## Finding: Stale-diff line-offset drift silently corrupts commits/discards via zero-context `git apply`

The Halborn report's core issue is a **missing state-resync before/after an operation that mutates important state**, so a mutation runs against an outdated invariant. Desktop has a structural analog: **line-selection state computed against a diff snapshot is applied via `git apply --unidiff-zero` without re-validating that the diff still matches the current working-tree content**, so it can silently apply hunks to the *wrong lines* if the file changed between diff generation and the stage/discard action.

### Title
Silent misapplication of partial-selection patches due to stale diff vs. current working tree in `applyPatchToIndex`/`discardChangesFromSelection` - (File: `app/src/lib/git/apply.ts`)

### Summary
Desktop's partial-staging and partial-discard features build a Git patch from a diff object plus a `DiffSelection` bitmap that references **absolute line indices in that specific diff**. Two code paths consume this bitmap unsafely:

- `discardChangesFromSelection` [1](#0-0)  builds the patch straight from the `diff` object handed to it by the caller (originally rendered in the UI) — it never re-reads the file's current diff before calling `git apply`.
- `applyPatchToIndex` [2](#0-1)  does re-fetch a fresh diff via `getWorkingDirectoryDiff` right before formatting the patch [3](#0-2) , but it reuses `file.selection`, whose line indices were computed against the *previous* diff (e.g. from when the user checked boxes in the Changes view, or from `_commitIncludedChanges`'s cached `workingDirectory.files`, see `app/src/lib/stores/app-store.ts:3680-3690`).

Both patches are applied with `--unidiff-zero`, which git deliberately does with **zero lines of context**, meaning it trusts the encoded line numbers rather than verifying surrounding content. If the file's line structure shifted between the moment the diff/selection was captured and the moment the patch is applied (a TOCTOU window that Desktop leaves open across UI interaction, background refreshes, and `stageFiles`' multi-step git plumbing), `git apply --unidiff-zero` will not fail loudly — it will happily patch different lines than the ones the user actually reviewed and selected.

### Finding Description
- `formatPatch`/`formatPatchToDiscardChanges` in `app/src/lib/patch-formatter.ts:129-232` and `:251-335` build hunks purely from `hunk.unifiedDiffStart`-relative absolute indices and `selection.isSelected(absoluteIndex)`, with **no correlation back to actual file content** at apply time.
- `stageFiles` in `app/src/lib/git/update-index.ts:109-169` resets the index and then calls `applyPatchToIndex` for every partially-selected file — the comment even states "the index has been completely reset, the job of this function is to set up the index... that reflects what the user has selected in the app," assuming the selection is still valid for the current file state, with no re-validation step analogous to `CheckSlashing`.
- `applyPatchToIndex` refreshes the diff (`getWorkingDirectoryDiff`) but not the selection, so the freshly fetched hunk boundaries may not line up with the stale `selection` bitmap.
- `discardChangesFromSelection` (git-level) skips even that partial refresh and works entirely off the caller-supplied `diff` [1](#0-0) , invoked from `GitStore.discardChangesFromSelection` → `AppStore._discardChangesFromSelection` [4](#0-3)  → UI `onDiscardChanges` handler in `app/src/ui/changes/changes.tsx:76-100`, none of which reload the diff immediately before the destructive `git apply` call.
- The window between "diff shown/selection made" and "patch applied" is not instantaneous: Desktop periodically calls `_refreshRepository`/`_loadStatus` in the background for the selected repository (see `app/src/lib/stores/app-store.ts:4047-4144` and status refresh triggers throughout checkout/fetch/pull flows), and any tracked file can also be rewritten by Git's own clean/smudge filters, `.gitattributes`-driven `text=auto` normalization, or LFS pointer smudging — all of which are configurable by content that ships inside a cloned/fetched repository.

### Impact Explanation
If an attacker-controlled repository (or a repository whose clean/smudge/LFS filters run during Desktop's normal background status refresh) causes tracked-file content to shift between the point the user reviews a diff/selects lines and the point Desktop applies the patch, `git apply --unidiff-zero` can attach the previously-selected hunk to a different location in the file. Because this is a zero-context apply, git will not reject the patch just because the surrounding text differs — it applies at the numbered line offsets. The result is **silent corruption of what the user actually commits or discards**: the user believes they are staging/discarding line N of a reviewed diff, but the tool stages or destructively discards unrelated content at that offset in the now-different file, without any error or warning surfaced to the user. This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires no local/physical access, admin rights, or pre-existing malware — only that the victim opens/works with an attacker-supplied or attacker-influenced repository (a normal Desktop workflow: clone, fetch, or open a PR branch) where tracked file content can change between the diff render and the user's stage/discard click. Desktop's own background refresh cadence, hook/filter execution during status/checkout, and the multi-await staging pipeline (`stageFiles` looping through renamed/normal/deleted/partial files sequentially) create a realistic window for this race, especially on larger repos or slower disks where the window is seconds rather than milliseconds.

### Recommendation
Before applying any partial patch (stage or discard), Desktop should re-fetch the file's current diff and re-validate that the `DiffSelection`'s referenced hunks/line ranges still correspond to identical context in the freshly-fetched diff (or reject/refresh the selection if they don't), instead of trusting a previously-computed, potentially stale bitmap. At minimum, `discardChangesFromSelection` should re-derive the diff immediately before formatting/applying the patch, mirroring the (still-insufficient) refetch already present in `applyPatchToIndex`, and both paths should abort with a user-visible error rather than silently applying a zero-context patch when the underlying content no longer matches.

### Proof of Concept
1. Clone/open a repository in GitHub Desktop and modify a tracked text file so it shows a multi-hunk diff in the Changes view.
2. In the diff view, select only specific lines from hunk 2 for partial staging (or open "Discard changes" on a selection).
3. Before clicking "Commit"/"Discard", have an external process (simulating a repo-provided filter/hook or a concurrent build/watch script triggered by repo content) insert/remove lines earlier in the same file, shifting subsequent line numbers, without changing the content the user actually selected.
4. Click "Commit selected changes" (or confirm "Discard changes").
5. Observe that `git apply --unidiff-zero` (via `applyPatchToIndex`/`discardChangesFromSelection` in `app/src/lib/git/apply.ts`) applies/removes the previously selected hunk at the old line offsets in the now-shifted file — inspect the resulting commit or working tree to confirm the staged/discarded content no longer corresponds to what was displayed and selected by the user.

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
}

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
