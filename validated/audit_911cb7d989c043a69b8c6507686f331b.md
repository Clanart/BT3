### Title
Sub-dust outputs sent to Serai's Bitcoin addresses are silently dropped and permanently unrecoverable - (File: processor/src/multisigs/scanner.rs)

### Summary
An unprivileged sender can send a Bitcoin output below `N::DUST` (546 sats) to any of Serai's registered addresses (external, branch, change, or forward). The processor's scanner detects the output via `Bitcoin::get_outputs` but then silently discards it in `processor/src/multisigs/scanner.rs`. The block is still marked as scanned and acked, so the output is never revisited, never added to the scheduler's UTXO set, and is skipped even during multisig rotation (`force_spend`). The BTC remains owned by a multisig key that no code path will ever sign for again — funds are permanently locked with no withdrawal/recovery mechanism, the same class as the referenced Allo finding (funds stuck in-contract with no way to return them).

### Finding Description
`Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-740`) returns every `ReceivedOutput` the `Scanner` matches by `script_pubkey`, including arbitrarily small ones — `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) performs no value check. The drop happens in the scanning loop:

```rust
// processor/src/multisigs/scanner.rs:562-567
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
```

Outputs below `N::DUST` are filtered out before being emitted in `ScannerEvent::Block` and before the `seen`/`ram_outputs` dedup bookkeeping (`scanner.rs:594-640`). The block is then acked as fully scanned. Consequences:

1. The output never reaches `Scheduler::schedule` (`processor/src/multisigs/scheduler/utxo.rs:303`), so it never enters `self.utxos`.
2. Retirement (`force_spend`, `utxo.rs:423-432`) only drains `self.utxos`, so these outputs are never forwarded to a successor multisig. Once the old key set retires, no registered scheduler/scanner ever references them again.
3. There is no sweep/recover/"withdraw" path anywhere in the UTXO stack — `refund_plan` and `forward_plan` only operate on outputs that were already reported.

The result is funds that are cryptographically owned by Serai's threshold key yet unreachable by any planned transaction — permanently stuck, exactly mirroring the Allo case where a failed distribution leaves tokens locked in the strategy with no manager withdrawal.

### Impact Explanation
Permanent loss of user/protocol funds. Any BTC output < 546 sats sent to a Serai address is neither credited nor spendable through any code path; after the owning multisig rotates out, it is abandoned forever. While individually small, attackers can cheaply grief (a sub-dust output costs ~546 sats), and edge cases — e.g. a branch/change output reduced below dust by fee amortization edge cases, or a refund output — produce accounting divergence where on-chain balance exceeds all tracked `utxos` with no reconciliation mechanism.

### Likelihood Explanation
Trivially reachable by any unprivileged party: sending a dust-value transaction to Serai's publicly known external/forward address requires only a Bitcoin transaction. The drop is unconditional and silent; no operator action can recover the funds through the implemented scheduler/scanner.

### Recommendation
Don't silently drop outputs. Either:
- Report sub-dust outputs in `ScannerEvent::Block` (flagged) and persist them in the scheduler's UTXO set so `force_spend`/aggregation can sweep them when economical, or
- Track them in a dedicated "below-dust" registry under the owning key, so multisig retirement can include them in a consolidation transaction and so accounting reconciles with the on-chain balance.

### Proof of Concept
1. Obtain the current multisig's external address (`Bitcoin::external_address` / `p2tr_script_buf(key)`).
2. Broadcast a transaction paying e.g. 300 sats (< `DUST = 546`) to that script_pubkey; wait `CONFIRMATIONS` blocks.
3. `get_outputs` returns the `ReceivedOutput` (script matches), but `scanner.rs:564` drops it; the block is acked and `ram_scanned` advances.
4. Observe `Scheduler::utxos` never contains the outpoint; issue a multisig rotation — the `force_spend` plan at `utxo.rs:423-432` excludes it; the 300 sats remain under the retired key with no code path able to spend them.
