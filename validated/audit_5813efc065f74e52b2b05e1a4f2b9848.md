## Finding: 0-of-0 multisig spending condition allows STX to be spent with zero signatures [1](#0-0) 

### Title
Zero-signature ("0-of-0") multisig spending conditions authenticate transactions with no signatures at all - (File: `stacks-common/src/types/mod.rs`, `stackslib/src/chainstate/stacks/auth.rs`)

### Summary
`MultisigSpendingCondition::verify()` and `OrderIndependentMultisigSpendingCondition::verify()` only check that the number of signatures collected equals (or is at least) `signatures_required`. Neither the codec deserializer nor `StacksAddress::from_public_keys` enforce `signatures_required >= 1`. When `signatures_required == 0` and no auth fields are present, the equality `num_sigs == signatures_required` (0 == 0) is trivially satisfied, and `StacksAddress::from_public_keys` happily derives a deterministic address from an empty public-key list. Any transaction whose spending condition sets `signatures_required = 0`, `fields = []`, and `signer` equal to that deterministic hash therefore authenticates successfully with **zero signatures** — i.e., an asset moves without any actual private-key authorization, exactly analogous to the referenced report's "proposal passes with 0 votes" bug where a threshold of 0 makes the approval check vacuous.

### Finding Description
In `MultisigSpendingCondition::verify()`:
```
if num_sigs != self.signatures_required { ... error ... }
...
let addr = StacksAddress::from_public_keys(0, &self.hash_mode.to_address_hash_mode(), self.signatures_required as usize, &pubkeys)...
if addr.bytes() != &self.signer { ... error ... }
``` [2](#0-1) 

and in `OrderIndependentMultisigSpendingCondition::verify()`:
```
if num_sigs < self.signatures_required { ... error ... }
``` [3](#0-2) 

Both checks are satisfied when `fields` is empty and `signatures_required == 0` (0 == 0, and 0 < 0 is false). The subsequent address-derivation call:
```
pub fn from_public_keys(version: u8, hash_mode: &AddressHashMode, num_sigs: usize, pubkeys: &Vec<StacksPublicKey>) -> Option<StacksAddress> {
    if pubkeys.len() < num_sigs { return None; }
    ...
    let hash_bits = public_keys_to_address_hash(hash_mode, num_sigs, pubkeys);
    StacksAddress::new(version, hash_bits).ok()
}
``` [1](#0-0) 
only rejects `num_sigs > pubkeys.len()`; with `num_sigs = 0` and `pubkeys = []` it happily proceeds. For `SerializeP2SH`/`SerializeP2WSH`, `public_keys_to_address_hash` calls `to_bits_p2sh`/`to_bits_p2sh_p2wsh`, which build a Bitcoin-style `OP_CHECKMULTISIG` script from `num_sigs` and the (empty) key list:
```
fn to_bits_p2sh_p2wsh<K: PublicKey>(num_sigs: usize, pubkeys: &Vec<K>) -> Hash160 {
    let mut bldr = Builder::new();
    bldr = bldr.push_int(num_sigs as i64);
    for pubk in pubkeys { ... }
    bldr = bldr.push_int(pubkeys.len() as i64);
    bldr = bldr.push_opcode(btc_opcodes::OP_CHECKMULTISIG);
    ...
}
``` [4](#0-3) 
This produces a fixed, publicly computable `Hash160` (a "0-of-0" script hash) with no dependency on any private key. Nowhere — not in `consensus_deserialize` for `MultisigSpendingCondition`/`OrderIndependentMultisigSpendingCondition` (which only checks the number of signature fields matches `signatures_required`, never that `signatures_required >= 1`) [5](#0-4) , nor in `TransactionAuth::verify`/`verify_origin` [6](#0-5) , nor in mempool admission (`can_include_tx` → `process_transaction_precheck` → `tx.verify()`) [7](#0-6)  — is there a check rejecting `signatures_required == 0`.

### Impact Explanation
Any STX or asset that ends up controlled by the deterministic "0-of-0" P2SH/P2WSH address (e.g., through a wallet/tool bug that constructs a multisig threshold of 0, a misconfigured multi-party custody setup, or an operator error) can be spent by **anyone**, without any signature, because the auth verification step is vacuously true. This breaks the fundamental equality that "a transaction is authenticated only if it presents signatures matching its committed public-key set/threshold" — an asset moves without any real authorization, matching the report's Critical impact category ("forging ... a transaction so an asset moves without authorization").

### Likelihood Explanation
Exploitation does not require a miner, signer, or victim's private key — the attacker only needs funds to exist at the deterministic, computable "0-of-0" address, which can arise from any tooling bug that allows a caller to specify `signatures_required = 0` when constructing a multisig `TransactionSpendingCondition` (nothing in the type or its constructors prevents this; `new_multisig_p2sh`, `new_multisig_p2wsh`, `new_multisig_order_independent_p2sh/p2wsh` all forward `num_sigs` unchecked) [8](#0-7) . Likelihood of funds actually landing there depends on external tooling correctness, so this is a latent/configuration-dependent, rather than directly remotely triggerable, bug — but once funds are present, the drain is trivial and permissionless.

### Recommendation
Add an explicit minimum-threshold check (`signatures_required >= 1`) in:
- `MultisigSpendingCondition::consensus_deserialize` and `OrderIndependentMultisigSpendingCondition::consensus_deserialize` [5](#0-4) 
- `MultisigSpendingCondition::verify` / `OrderIndependentMultisigSpendingCondition::verify` [2](#0-1) 
- `StacksAddress::from_public_keys` for `SerializeP2SH`/`SerializeP2WSH` modes, rejecting `num_sigs == 0` [1](#0-0) 

### Proof of Concept
1. Construct a `MultisigSpendingCondition` with `hash_mode = MultisigHashMode::P2SH`, `fields = vec![]`, `signatures_required = 0`.
2. Compute `signer = to_bits_p2sh(0, &Vec::<StacksPublicKey>::new())` (a fixed, public Hash160).
3. Build a `StacksTransaction` with this spending condition as origin auth, no `TransactionAuthField`s, targeting the derived address.
4. Call `verify()`: `num_sigs` (0, from empty `fields`) equals `signatures_required` (0); `StacksAddress::from_public_keys(0, P2SH, 0, [])` returns `Some(addr)` whose bytes equal `signer` by construction — verification succeeds with no signature present.
5. If STX/assets are held at this address (e.g. via wallet misconfiguration), any party can submit this unsigned transaction to spend them.
