### Title
Duplicate Value Creation via Mismatched Acknowledgement in ERC20 IBC Middleware `OnRecvPacket` - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
The ERC20 IBC middleware's `OnRecvPacket` callback escrows already-credited bank coins from the recipient into the `x/erc20` module account before attempting an EVM call to unescrow native ERC20 tokens to that recipient. If the EVM call fails (e.g. paused/self-destructed contract, reverted transfer), the function returns a new `channeltypes.NewErrorAcknowledgement`, but the coin escrow into the module account that already occurred is never reversed, and no compensating refund is issued to the recipient.

### Finding Description
`x/erc20/ibc_middleware.go` `OnRecvPacket` first invokes the underlying ICS20 transfer module's `OnRecvPacket`, which — on success — mints/unlocks the voucher `sdk.Coin` directly into the recipient's bank balance [1](#0-0) . This state change is committed to the live context; it is not wrapped in any `ctx.CacheContext()` isolation.

The erc20 keeper's `OnRecvPacket` is then called with that already-successful acknowledgement. For a registered native ERC20 token pair, it calls `k.ConvertCoinNativeERC20`, and if that call errors, it discards the original success acknowledgement and returns a brand-new `channeltypes.NewErrorAcknowledgement(err)` instead [2](#0-1) .

Inside `ConvertCoinNativeERC20`, the function first escrows the coin from the recipient's account into the `x/erc20` module account via `SendCoinsFromAccountToModule`, and only afterward performs the EVM `transfer` call that would unescrow ERC20 tokens back to the recipient [3](#0-2) . If the EVM call fails (contract paused, self-destructed, reverted, or the balance-invariance check fails), the function returns an error without reversing the `SendCoinsFromAccountToModule` step [4](#0-3) .

Because `k.OnRecvPacket`/`k.ConvertCoinNativeERC20` return a Go value (an `Acknowledgement`), not an actual Go `error`, from the perspective of the ibc-go `RecvPacket` message handler the packet processing succeeds — all state mutations performed during the callback (the initial bank credit to the recipient AND the subsequent escrow of those same coins into the module account) are persisted, regardless of the acknowledgement's success/error content.

The resulting Error Acknowledgement is relayed back to the source chain, where the standard ICS20 `OnAcknowledgementPacket` logic (or the erc20 middleware equivalent, `ConvertCoinToERC20FromPacket`) treats an error ack as proof the transfer never completed, and refunds/unescrows the original amount back to the sender [5](#0-4) .

Net effect: the sender is refunded on the source chain as if the transfer failed, while on the destination chain the equivalent value has already been debited from the recipient and is now stuck in the `x/erc20` module account (an escrow with no user-facing recovery path — mirroring the LayerZero `oft_adapter_fa.move` bug class where funds locked in escrow have no release mechanism when the remote leg fails). The combination duplicates the transferred value across the two chains and permanently locks the destination-side coins in a module account.

### Impact Explanation
This breaks the core Cosmos EVM asset-representation invariant that native coins, ERC20 views, and IBC escrows must remain 1:1 consistent. It results in:
1. Duplicate spendable value: the sender is refunded on the source chain while the (equivalent) coins remain debited/escrowed on the destination chain — an accounting corruption that lets an unprivileged party trigger a mismatch between two chains' balances from ordinary IBC transfer flow.
2. Permanent freezing of the recipient's coins in the `x/erc20` module account, with no exposed message/keeper method to release them back to the affected recipient.

This matches the "Critical unauthorized … duplication … irreversible accounting corruption of spendable user value across native balances … IBC escrows" and "Critical permanent freezing … of user funds" impact classes in scope.

### Likelihood Explanation
Triggering requires only an ordinary IBC transfer of a registered native-ERC20-backed denom to a chain where the ERC20 contract has become non-functional for the transfer call at the moment of receipt — e.g., the contract is paused, blocklisted, self-destructed, or reverts the `transfer` call for any reason (insufficient allowance/logic bug/pausable token). The `x/erc20` module deliberately supports "self-destructed ERC20 contract" as an anticipated failure mode (it is explicitly tested for in the sender-side ack/timeout paths), confirming this is a realistic, reachable state rather than a purely theoretical one. No privileged action or malicious relayer is required — a single ordinary unprivileged IBC transfer plus a broken/paused destination-side ERC20 contract is sufficient.

### Recommendation
Ensure the erc20 middleware's `OnRecvPacket` (and the equivalent v2 path) never returns an Error Acknowledgement after committed state changes that give value to a user account:
- Wrap `k.ConvertCoinNativeERC20`'s escrow-then-EVM-call sequence in a `ctx.CacheContext()` and only commit (`write()`) it if the entire attempt including the EVM unescrow call succeeds; otherwise discard the cache so the recipient retains the plain bank coin rather than losing it to the module account, and return the ORIGINAL success acknowledgement (not a new Error ack) so the source chain does not also refund the sender.
- Alternatively, if the erc20 conversion step fails, always fall through to leaving the recipient with the bank-token representation (as `OnAcknowledgementPacket`/`OnTimeoutPacket` do via `ConvertCoinToERC20FromPacket`'s "log and no-op" pattern) instead of converting the underlying acknowledgement to an error.

### Proof of Concept
1. Register a native ERC20 token pair for contract `C` via `RegisterERC20`, denom `D`.
2. Send `D` cross-chain via ICS20 `MsgTransfer` from chain B to chain A, targeting recipient `R` on chain A. The base ICS20 `OnRecvPacket` mints/credits `D` (voucher) coins to `R`'s bank balance and returns a success ack [1](#0-0) .
3. Before the packet is relayed, self-destruct contract `C` on chain A (`EVMKeeper.DeleteAccount`), or otherwise make its `transfer` function revert.
4. The erc20 keeper's `OnRecvPacket` calls `ConvertCoinNativeERC20`, which escrows `R`'s just-received `D` coins into the erc20 module account, then attempts `CallEVM(..., "transfer", R, amount)`, which fails because `C` is self-destructed/paused [3](#0-2) .
5. `k.OnRecvPacket` returns `channeltypes.NewErrorAcknowledgement(err)` instead of the original success ack [6](#0-5) ; this is committed as the packet's on-chain acknowledgement, while `R`'s `D` coins remain stuck in the module account.
6. On chain B, the relayed error acknowledgement triggers `OnAcknowledgementPacket` → refund of the sender's original amount, as if the transfer never happened.
7. Result: sender on chain B has been refunded the full amount, while recipient `R`'s equivalent coins are irreversibly stuck in the erc20 module account on chain A — value has been effectively duplicated across the two chains, and `R`'s funds are permanently locked with no user-facing recovery function.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

		// convert the token from Cosmos Coin to its ERC20 representation
