### Title
Native ERC20 IBC receive can duplicate value: unescrow to recipient is committed before the erc20 middleware's error-ack path triggers a source-chain refund - ([File: x/erc20/keeper/ibc_callbacks.go])

### Summary
`x/erc20/ibc_middleware.go`'s `OnRecvPacket` runs the standard ICS20 `OnRecvPacket` (which unescrows/credits the native-ERC20-backed bank coin to the recipient and writes those state changes directly to `ctx`, uncached) and, if that succeeds, immediately hands off to `erc20types.Keeper.OnRecvPacket`. In the "native ERC20" case, that keeper method calls `k.MintingEnabled(...)` (`x/erc20/keeper/mint.go`) before converting the coin to its ERC20 representation. If `MintingEnabled` fails — e.g. governance disables the module/token pair, the recipient is on the bank blocklist, or `SendEnabled` is turned off for the denom — the function returns `channeltypes.NewErrorAcknowledgement(err)`. This is functionally the "pause" analog from the source report: an ordinary, unprivileged-triggerable, mid-flight state condition blocks part of the receive-side handling.

### Finding Description
` [1](#0-0) ` shows that `im.Module.OnRecvPacket` (the underlying ICS20 transfer app) executes and mutates state on the same, uncached `ctx` before the erc20 keeper callback runs. There is no `ctx.CacheContext()`/`writeFn()` pattern wrapping this sequence, unlike the pattern used elsewhere in the codebase for EVM callback execution (see `x/ibc/callbacks/keeper/keeper.go` which explicitly uses `cachedCtx`/`writeFn()` to allow reverting effects on failure) ` [2](#0-1) `.

In `x/erc20/keeper/ibc_callbacks.go`, Case 2 for a native ERC20 token pair calls `k.MintingEnabled` and, on failure, returns an error acknowledgement without undoing the unescrow that the underlying transfer app already performed:
` [3](#0-2) `

`MintingEnabled` can fail for reasons that are not privileged/attacker-controlled at packet-processing time (module disabled by governance, token pair disabled, recipient blocked, or `IsSendEnabledCoin` false) ` [4](#0-3) `.

Because the packet is a "return" of a native ERC20 token (the token was originally sent out from this chain and escrowed there), the underlying ICS20 `OnRecvPacket` un-escrows the coin from the local escrow account and credits it to the recipient's bank balance as part of standard ICS20 logic — this already happened in `ctx` before `MintingEnabled` is evaluated. When `MintingEnabled` subsequently fails and an error acknowledgement is returned:
- The recipient already has the unescrowed bank coin (state committed on this chain).
- The error acknowledgement is relayed back to the sending chain, which will process it via `OnAcknowledgementPacket`/refund logic and restore (unescrow or re-mint) the sender's original tokens there.

This produces two spendable balances for what was originally a single unit of value: the recipient's credited amount on the receiving chain and the refunded amount on the sending chain — a duplication of spendable user value across an IBC escrow, mirroring the "burn on one side / mint or credit elsewhere with no consistency guarantee" bug class described in the source report, except here the destination-side credit is not rolled back when the mid-flow condition (analogous to "paused") triggers.

### Impact Explanation
If confirmed on the actual relay/refund semantics of the underlying `ibc-go` v10 transfer/refund path used here, this would constitute unauthorized duplication of spendable user value across native balances and IBC escrows, which is explicitly in the allowed Critical impact set (duplication of spendable user value across native balances / IBC escrows). It can be triggered without any privileged action, purely by an ordinary condition becoming true mid-packet-flow (e.g., a `SendEnabled=false` state, or an already-blocklisted recipient), which is consistent with the repo's own test harness explicitly exercising `SetSendEnabled(..., false)` to force this exact failure branch (`evmd/tests/ibc/ibc_middleware_test.go` line ~731-736) ` [5](#0-4) `.

### Likelihood Explanation
Moderate-to-low confidence/likelihood: I was not able to fully trace whether ibc-go v10's core `RecvPacket` transaction handling reverts the entire packet-processing state when an application module returns an error acknowledgement (some ibc-go versions treat "error acknowledgement" purely as an ack-byte decision without state rollback, others rely on callback middleware wrapping with `CacheContext`). The repository's own IBC-callbacks code deliberately uses `CacheContext`/`writeFn` to guard against exactly this class of problem in a different code path, suggesting the maintainers are aware of the pattern, but the erc20 IBC middleware (`x/erc20/ibc_middleware.go`) does not apply the same protection. This is the central uncertainty that determines whether this is truly exploitable or already safe by virtue of ibc-go's core semantics.

### Recommendation
Wrap the sequence "run underlying ICS20 `OnRecvPacket`" + "run erc20 middleware post-processing" in a cached context (`ctx.CacheContext()`), and only call `writeFn()` to commit the combined state changes if the overall acknowledgement is successful. If the erc20-specific step (`MintingEnabled` / `ConvertCoinNativeERC20`) fails and an error acknowledgement must be returned, discard the cached context so the underlying transfer app's unescrow/mint never gets committed, preventing any duplicate-credit scenario.

### Proof of Concept
Could not be fully constructed/verified in this session because it requires tracing ibc-go v10's exact core packet-commit semantics (specifically whether `RecvPacket` reverts application-level state changes when the module returns a failure acknowledgement, or whether it always commits and merely embeds the failure in the ack payload). The existing test `TestOnRecvPacketNativeErc20` with `tc.withCallback` and `SetSendEnabled(..., false)` in `evmd/tests/ibc/ibc_middleware_test.go` (lines 728-808) exercises the exact failure branch and could be extended to explicitly check (a) the recipient's bank balance after the error ack, and (b) whether the source chain, upon relaying the error ack back, also credits/refunds the sender — which would confirm or refute the duplication.

Given the significant unresolved uncertainty about ibc-go's core commit/rollback behavior for error acknowledgements, I present this with reduced confidence rather than as a definitively confirmed Critical finding. If the audit process requires strict confirmation before reporting, this should be validated against ibc-go v10 source before treating it as conclusive.

```go
func (k Keeper) MintingEnabled(
	ctx sdk.Context,
	receiver sdk.AccAddress,
	token string,
) (types.TokenPair, error) {
	if !k.IsERC20Enabled(ctx) {
		return types.TokenPair{}, errorsmod.Wrap(
			types.ErrERC20Disabled, "module is currently disabled by governance",
		)
	}

	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	if !pair.Enabled {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrERC20TokenPairDisabled, "minting token '%s' is not enabled by governance", token,
		)
	}

	if k.bankKeeper.BlockedAddr(receiver.Bytes()) {
		return types.TokenPair{}, errorsmod.Wrapf(
			errortypes.ErrUnauthorized, "%s is not allowed to receive transactions", receiver,
		)
	}

	// NOTE: ignore amount as only denom is checked on IsSendEnabledCoin
	coin := sdk.Coin{Denom: pair.Denom}

	// check if minting to a recipient address other than the sender is enabled
	// for for the given coin denom
	if !k.bankKeeper.IsSendEnabledCoin(ctx, coin) {
		return types.TokenPair{}, errorsmod.Wrapf(
			banktypes.ErrSendDisabled, "minting '%s' coins to an external address is currently disabled", token,
		)
	}

	return pair, nil
```
