### Title
Missing Cross-Validation of `time_to_send_watchtower_challenge` Against `watchtower_challenge_timeout_timelock` Breaks Fraud-Proof Liveness — (`crates/clementine-config/src/protocol.rs`, `core/src/config/mod.rs`)

---

### Summary

`ProtocolParamset` loading (both TOML-file and env-var paths) validates only `finality_depth >= 1` and nothing else. `BridgeConfig::check_general_requirements` validates only genesis-hash, start-height ordering, and finality depth. Neither path enforces the critical ordering invariant `time_to_send_watchtower_challenge < watchtower_challenge_timeout_timelock`. When this invariant is violated, verifiers schedule their watchtower-challenge transactions to land **at or after** the block at which the operator can already claim `WatchtowerChallengeTimeout`, permanently disabling the fraud-proof path for every challenged kickoff.

---

### Finding Description

**Root cause — missing validation in config loading:**

`ProtocolParamset::from_toml_file` and `ProtocolParamset::from_env` accept all timelock fields without any ordering check: [1](#0-0) 

The only guard present is: [2](#0-1) 

`BridgeConfig::check_general_requirements` adds no timelock ordering checks either: [3](#0-2) 

**How the invariant is consumed at runtime:**

When a kickoff is challenged, `on_challenged_entry` inserts a `BlockHeight` matcher that fires at:

```
kickoff_height + config.time_to_send_watchtower_challenge
``` [4](#0-3) 

The operator's `WatchtowerChallengeTimeout` transaction becomes spendable after:

```
kickoff_height + watchtower_challenge_timeout_timelock
``` [5](#0-4) 

**The two parameters live in different config structs and are never cross-validated:**

- `time_to_send_watchtower_challenge: u16` — in `BridgeConfig`
- `watchtower_challenge_timeout_timelock: u16` — in `ProtocolParamset` [6](#0-5) [7](#0-6) 

If an operator sets `TIME_TO_SEND_WATCHTOWER_CHALLENGE >= WATCHTOWER_CHALLENGE_TIMEOUT_TIMELOCK` (e.g., both equal to 288, or the former larger), the verifier's challenge-send block is ≥ the operator's timeout-claim block. The operator broadcasts `WatchtowerChallengeTimeout` first, spending the `WatchtowerChallenge` UTXO. The verifier's challenge transaction is then invalid (input already spent), so no watchtower challenge is ever recorded on-chain.

---

### Impact Explanation

With no watchtower challenge on-chain, the `disprove_if_ready` gate never fires (it requires `watchtower_challenges.keys().all(|idx| operator_challenge_acks.contains_key(idx))`): [8](#0-7) 

A malicious operator who submitted an invalid withdrawal can therefore complete the full kickoff → assert → reimburse cycle without being disproved. The operator's collateral is not slashed, and the bridged BTC is paid out to the attacker's address. This is a permanent, irreversible loss of bridged BTC and operator collateral — matching the "High impact" gate (theft/permanent lock of bridged BTC and bridge-controlled UTXOs).

---

### Likelihood Explanation

Low. Triggering the bug requires the admin to deploy with `time_to_send_watchtower_challenge >= watchtower_challenge_timeout_timelock`. The default regtest values (216 vs 288) are safe. However, the code provides no guard, so a misconfigured deployment — or a future refactor that changes one value without updating the other — silently enables the attack. This is the direct analog of the external report's pattern: a parameter that must satisfy an ordering constraint relative to another parameter, with no enforcement at load time.

---

### Recommendation

Add a cross-validation check in both `ProtocolParamset::from_toml_file` / `ProtocolParamset::from_env` and `BridgeConfig::check_general_requirements`:

```rust
// In check_general_requirements or a new validate() method:
if self.time_to_send_watchtower_challenge
    >= self.protocol_paramset().watchtower_challenge_timeout_timelock
{
    return Err(BridgeError::ConfigError(format!(
        "time_to_send_watchtower_challenge ({}) must be strictly less than \
         watchtower_challenge_timeout_timelock ({})",
        self.time_to_send_watchtower_challenge,
        self.protocol_paramset().watchtower_challenge_timeout_timelock
    )));
}
```

Additionally validate the full timelock ordering chain required by the protocol:
- `operator_challenge_timeout_timelock < operator_challenge_nack_timelock`
- `operator_challenge_nack_timelock < disprove_timeout_timelock`
- `assert_timeout_timelock < disprove_timeout_timelock`
- `num_signed_kickoffs <= num_kickoffs_per_round` (currently `get_kickoff_utxos_to_sign` silently returns fewer kickoffs via `.take()` if this is violated) [9](#0-8) 

---

### Proof of Concept

1. Deploy Clementine with:
   ```
   TIME_TO_SEND_WATCHTOWER_CHALLENGE=288
   WATCHTOWER_CHALLENGE_TIMEOUT_TIMELOCK=288
   ```
   Both values parse and load without error — no validation rejects them.

2. A malicious operator submits an invalid withdrawal and broadcasts a kickoff at block H.

3. A verifier detects the challenge and schedules `TimeToSendWatchtowerChallenge` at block H + 288.

4. At block H + 288, the operator simultaneously (or slightly earlier) broadcasts `WatchtowerChallengeTimeout`, spending the `WatchtowerChallenge` UTXO with `Sequence::from_height(288)`.

5. The verifier's watchtower-challenge transaction is rejected by Bitcoin nodes (input already spent).

6. `spent_watchtower_utxos` is populated by the timeout event, not a real challenge. `watchtower_challenges` remains empty. `disprove_if_ready` never fires because `watchtower_challenges.keys().all(...)` is vacuously true but `operator_challenge_acks` is also empty — or the operator simply proceeds to assert and reimburse before the disprove window.

7. The operator claims reimbursement. Bridged BTC is lost. No collateral is slashed.
