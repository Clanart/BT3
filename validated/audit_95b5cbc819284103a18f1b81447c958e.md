### Title
Silent Partial Failure of Batch File Restoration During "Discard Changes" via Overly Permissive `checkoutIndex` Exit-Code Acceptance - (File: `app/src/lib/git/checkout-index.ts`, `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` restores a batch of files to their `HEAD` state via `resetPaths` followed by `checkoutIndex`. `checkoutIndex` invokes `git checkout-index -f -u -q --stdin -z` and explicitly whitelists exit code `1` as a *success* code, without inspecting `stderr` or verifying that every requested path was actually restored. `git checkout-index` processes multiple paths in one invocation and, per path, can fail for reasons other than "missing from index" (permission errors, a path colliding with a directory/symlink, case-collisions, etc.), printing a per-path error but continuing with the remaining paths and returning a single non-zero exit code for the whole batch. Because Desktop accepts exit code `1` unconditionally as success, `git()` never throws, `performFailableOperation` reports success, and the UI tells the user the discard succeeded even when one or more attacker-influenceable files in the batch were never actually reverted.

### Finding Description
`checkoutIndex` is defined as: [1](#0-0) 

Note the `successExitCodes: new Set([0, 1])` combined with the doc comment claiming the function "will not yield errors for paths that don't exist in the index (-q)" — that claim is about the `-q` flag suppressing the specific "does not exist in index" case, but it does not mean all non-zero exits are that benign case. `git checkout-index` can exit non‑zero for a batch for many other reasons (e.g. inability to write to a path because it now points to a symlink placed by a previous checkout of an attacker-controlled ref, a permission‑denied path, or a path/directory name collision), and it will still process and successfully restore the *other* paths in the same invocation, producing a mixed-result batch collapsed into one exit code.

This is invoked from the core discard flow: [2](#0-1) 

`performFailableOperation` only surfaces an error if the underlying `git()` call throws a `GitError`, which it will not do here because exit code `1` is in `successExitCodes`. The generic `git()` executor's error-detection logic depends entirely on `successExitCodes`/`expectedErrors`, per `app/src/lib/git/core.ts`: [3](#0-2) 

Once `checkoutIndex` returns without error, `_discardChanges` in `app-store.ts` proceeds straight to `_refreshRepository` with no verification step: [4](#0-3) 

The documented design explicitly states the checkout step is supposed to be the authoritative "replace the modified files in the working directory" step of Discard Changes: [5](#0-4) 

This is the structural analog of the reported TON bug: a single-shot resource/status check ("exit code accepted") is used to gate a multi-item batch operation, and any individual item's failure inside that batch is silently absorbed instead of being surfaced to the caller, which then proceeds as if the whole operation fully succeeded.

### Impact Explanation
An attacker who controls content the victim has fetched/checked out (e.g., a branch or PR the user's HEAD points to, or files planted by a prior malicious checkout/clone) can arrange for a working-directory path that a legitimate "Discard Changes" operation will target to be something `checkout-index` cannot overwrite cleanly (for example, a directory-vs-file collision or a path Git can't write due to a placed symlink), while other unrelated files in the same discard batch restore normally. Because Desktop treats the whole batch's exit code `1` as success, the user is told the discard succeeded and the changes list is refreshed as if clean, even though the targeted file was never actually reverted to its committed content. If the user is unaware and continues working, this can lead to unintended content persisting in the working tree that the user believes was discarded, undermining the integrity guarantee of "Discard Changes" (the app silently fails to enforce what the user asked to be removed). The severity is bounded because `git status`/refresh will typically eventually re-surface the file as still modified, so it is not a fully invisible, permanent corruption of what gets committed — it degrades trust in a security-relevant action rather than causing untraceable state corruption.

### Likelihood Explanation
Requires the app to run a multi-file discard against a working tree containing a repository-supplied problematic path (directory/file collision, unwritable/symlinked path, etc.) — realistic when a user fetches/checks out attacker-supplied branches (a common Desktop workflow for reviewing PRs) and then attempts to discard local edits. No admin rights, local pre-existing malware, or social engineering beyond opening/checking out a repository is needed. Likelihood is moderate: it depends on specific filesystem-collision conditions being present, which is a narrower trigger than typical exploitation.

### Recommendation
1. In `checkoutIndex` (`app/src/lib/git/checkout-index.ts`), do not treat exit code `1` as unconditional success. Instead, parse `stderr`/`stdout` from `checkout-index` to confirm whether the non-zero exit was solely due to "does not exist in index" (already suppressed by `-q`) versus a genuine per-path failure.
2. Propagate failures for any path that could not be restored, and surface them to the caller (`GitStore.discardChanges`) so that `_discardChanges` can inform the user which files were not actually discarded rather than reporting blanket success.
3. Consider verifying post-condition state (e.g., re-running `git status`/diff on the discarded paths) before declaring the discard operation successful, mirroring the TON report's recommendation to validate that the full multi-item operation actually completed rather than trusting a single opaque completion signal.

### Proof of Concept
1. Set up a repository where a tracked file path (e.g. `foo/bar`) exists at `HEAD`.
2. Modify the working directory such that `foo` is replaced by an actual directory containing an unrelated file, or place a symlink at `foo/bar` pointing outside the repo (simulating content introduced by checking out an attacker-controlled branch/commit).
3. In Desktop, select `foo/bar` together with several other genuinely modified, unrelated files and choose "Discard Changes".
4. Observe: `resetPaths` + `checkoutIndex` runs as one batch; `git checkout-index` exits with code `1` and prints a per-path error for `foo/bar` to stderr while successfully restoring the other files.
5. Because `successExitCodes` includes `1`, `checkoutIndex` resolves without throwing, `performFailableOperation` reports success, and Desktop's UI shows the discard as completed for all selected files — with no error dialog — even though `foo/bar` retains attacker-influenced/unexpected content instead of the committed version. export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
