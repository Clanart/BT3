### Title
Dust/zero-value deposits are reported as received funds but cannot be spent without a net loss - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The report's bug class — a recorded claim/balance that is not backed by spendable funds, causing a withdrawal failure — maps onto Serai's Bitcoin wallet: `Scanner::scan_transaction` records *any* output paying to a registered `script_pubkey` as a `ReceivedOutput` ("A spendable output", per its doc comment), with no check that the output's value exceeds the cost of spending it. An unprivileged attacker can send dust or even zero-valued outputs to a scanned address; these are reported as received funds, yet including them in `SignableTransaction::new` costs more in fees than they contribute, making the "received" funds effectively unspendable.

### Finding Description
`Scanner::scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, with no minimum-value check (`networks/bitcoin/src/wallet/mod.rs:199-214`). `ReceivedOutput::read` likewise accepts any `TxOut` value from untrusted bytes (`networks/bitcoin/src/wallet/mod.rs:122-134`).

When such outputs are spent, `SignableTransaction::new` treats them as ordinary inputs (`networks/bitcoin/src/wallet/send.rs:175-185`). The `DUST` check (`send.rs:165-169`) applies only to *payments*, never to inputs. Each Taproot input adds ~58 vbytes of weight (fixed witness of one 64-byte signature, per `calculate_weight_vbytes` at `send.rs:71-83`), so at a fee rate above ~9 sat/vB a maximal dust output (545 sats) costs more to include than it is worth. A zero-value output is pure loss at any fee rate, yet is still reported as received.

### Impact Explanation
An attacker can cheaply create many dust/zero-value outputs paying to a victim's scanned address (deposit addresses, registered offsets). The wallet reports these as received balances, but the aggregate spendable balance is less than reported: every dust input consumed burns `input_vbytes * fee_rate - value` satoshis. Repeated dusting accumulates liabilities that can only be settled at a loss — the same shape as accumulated maintainer fees exceeding pool funds, causing a withdrawal/DoS of economically spendable funds. At high fee rates the dust may be permanently unspendable.

### Likelihood Explanation
Any unprivileged party who can send a Bitcoin transaction can trigger this; no key material, validator status, or malformed encodings are required. Cost to the attacker is one transaction with many dust outputs.

### Recommendation
Reject or flag outputs below `DUST` (546 sats) in `Scanner::scan_transaction`, and enforce the same floor in `ReceivedOutput::read`. Alternatively, report the output value alongside a fee-adjusted "spendable value" so callers can exclude inputs whose inclusion is net-negative at the current fee rate.

### Proof of Concept
1. Obtain the victim's `p2tr_script_buf(key)` address (public).
2. Broadcast a transaction with N outputs of 1 sat (or 546-1 sats) each to that address.
3. `scanner.scan_transaction(&tx)` returns N `ReceivedOutput`s, each reported via `ReceivedOutput::value()` as received funds.
4. `SignableTransaction::new(vec![dust_output], &payments, change, None, fee_per_vbyte)` succeeds whenever `input_sat >= payment_sat + needed_fee` is met by *other* inputs; each dust input increases `needed_fee` by ~`58 * fee_per_vbyte` sats while contributing ≤545 sats — at fee rates ≥10 sat/vB every dusted output is a net liability, and the wallet's reported received amount exceeds what can actually be withdrawn.
