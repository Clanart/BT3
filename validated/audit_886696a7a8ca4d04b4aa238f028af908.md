### Title
Copilot conflict-resolution writes AI content using a stale conflict snapshot, allowing attacker-crafted merge content to silently overwrite unresolved changes - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop's "Resolve with Copilot" feature reads the current conflict markers of a file, sends them to a Copilot model over the network (a round trip the code's own telemetry buckets at 15s/30s/60s/120s+), and later — when the user clicks "Continue Merge" — writes the model's resolved content back to disk and stages it with `git add`. The write path only skips a file if it is *found* in a previously captured `state.changesState.workingDirectory` snapshot and that snapshot shows no remaining conflict markers. If the file is not found in that stale snapshot at all, or the snapshot is otherwise out of date relative to the live working tree, the code writes and stages the Copilot content unconditionally, with no fresh `git status` check immediately before the write.

### Finding Description
The write happens in `_applyCopilotConflictResolutions`: [1](#0-0) 

For each accepted resolution, the path is re-validated for traversal with `resolveWithin`, and then the code attempts to guard against clobbering a file the user already resolved manually: [2](#0-1) 

The guard comment explicitly acknowledges the race ("If the user resolved this file externally... while the result dialog was open") but the check is keyed off `state.changesState.workingDirectory.files`, which is `state = this.repositoryStateCache.get(repository)` captured at the top of the function — not a freshly retrieved `getStatus()` result. When `onDiskFile === undefined` (file no longer appears in that stale snapshot, e.g. because the underlying conflict set changed between the AI request and confirmation), the `if` condition is `false` and the function falls straight through to `writeFile(...)` and `git add`, with no re-check against the actual current disk content.

This mirrors the audited ERC20 pattern precisely: the vault's `deposit()` assumed the balance change from `transferFrom` would exactly match the requested `amount`, an assumption safe for "normal" tokens but broken for tokens whose balance can change out from under the check (fee-on-transfer/rebase). Here, `_applyCopilotConflictResolutions` assumes the conflict state captured before a long asynchronous network operation is still an accurate description of the working directory at write time — an assumption broken any time the working tree changes during that window (external editor, background git status refresh, another Desktop operation, or content designed by whoever controls the conflicting branch/PR to produce hunks that get flagged/unflagged unexpectedly by `hasUnresolvedConflicts`).

Because the conflict content itself originates from files that can be shaped by an attacker who controls the incoming branch, PR, or fetched history being merged/rebased/cherry-picked, the attacker has some influence over which files and hunks get routed through this flow (though `validateResolutionPaths` does constrain the model's response to the original file-path set gathered at context-build time — see `app/src/lib/copilot-conflict-resolution.ts:473-521` — so this is not an arbitrary-file-write primitive, only a stale-state overwrite of files that were part of the conflict set).

### Impact Explanation
If the stale-snapshot guard is bypassed, Desktop silently writes model-generated content to a working-directory file and stages it with `git add`, without a final confirmation that the content matches what the user currently has on disk. This is "silent corruption of what the user commits" — the user believes they are committing their own conflict resolution (or an externally-edited one) but instead an unreviewed, potentially stale AI-generated version is staged and can be committed/pushed.

### Likelihood Explanation
This requires a specific timing window (an in-flight, and often multi-second-to-minutes-long, Copilot round trip during which the working directory's conflict state changes) rather than any local/physical access or leaked credentials, so it is a realistic but narrow race condition tied to normal usage of the merge/rebase/cherry-pick + "Resolve with Copilot" flow with an attacker-influenced conflicting branch/PR.

### Recommendation
Before writing any Copilot-resolved file to disk in `_applyCopilotConflictResolutions`, re-fetch live `git status` for the repository and re-evaluate `hasUnresolvedConflicts` / conflict marker presence against that fresh result, rather than the `state` object captured before the (potentially long) network round trip. Treat "file missing from current status" the same as "resolved externally" and skip the write, surfacing the discrepancy to the user instead of silently applying stale content.

### Proof of Concept
Not independently verified end-to-end (would require exercising the Copilot SDK integration), but the code path is directly demonstrable by:
1. Trigger a merge/rebase/cherry-pick against a branch with conflicting content and start "Resolve with Copilot".
2. While the request is in flight, externally modify or remove the conflicted file from the working directory such that it no longer appears (or appears differently) in `state.changesState.workingDirectory.files` by the time the result returns.
3. Click "Continue Merge" in the result dialog — `_applyCopilotConflictResolutions` finds `onDiskFile === undefined`, skips the "resolved externally" guard, and writes/stages the Copilot content over the current file state, per [3](#0-2) .
