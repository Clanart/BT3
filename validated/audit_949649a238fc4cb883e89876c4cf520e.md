### Title
`SignableTransaction::new` excludes the OP_RETURN data output from fee/weight estimation, producing a fee below the requested rate — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` payload which is appended to the transaction as an OP_RETURN output. However, `calculate_weight_vbytes` is only ever called with `payments`, so the OP_RETURN output (up to ~80 bytes of data plus output overhead) is omitted from both the weight and vbytes computation. The resulting `needed_fee` is systematically underestimated whenever `data` is specified: the signed transaction pays a lower effective fee rate than the caller-requested `fee_per_vbyte`, and can even fall below the minimum relay fee while passing the `TooLowFee` check. This mirrors the reported bug class: the fee calculated for an operation does not match the fee the operation actually requires to be processed/relayed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is pushed onto `tx_outs` before fee estimation:

- Lines 194–202: `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })`
- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);`

`calculate_weight_vbytes` (lines 62–127) reconstructs a transaction whose `output` vector is built exclusively from `payments` (lines 85–93) plus an optional `change` output. It never receives `tx_outs` and has no parameter for the OP_RETURN output. Therefore `vbytes` does not account for the data output's size (8-byte value + varint + script of up to ~83 bytes ≈ 90+ vbytes).

The same omission occurs in the change path at lines 225–226, where `fee_with_change` is computed from `payments` and `change`, again excluding the data output already present in `tx_outs`.

Consequences:
1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is underestimated, so `needed_fee()` (line 133) reports a lower fee than required to hit the requested rate.
2. The `TooLowFee` check (lines 211–213) compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, where both sides use the underestimated `vbytes`. A caller-supplied `fee_per_vbyte` that is at/above the minimum on the estimated size can yield an actual fee rate below the relay minimum once the real (larger) transaction is serialized, yet construction succeeds.
3. With a change output, `input_sat - (payment_sat + fee_with_change)` (line 228) gives the change output more value than it should have, pushing the actual paid fee even further below `fee_per_vbyte`.

### Impact Explanation
A caller passing public inputs (`payments`, `change`, `data`, `fee_per_vbyte`) receives a `SignableTransaction` whose actual fee rate is strictly lower than the rate they specified — the fee "does not follow a predictable calculation". In the worst case the produced transaction's true fee rate is under the Bitcoin minimum relay fee, so a validly FROST-signed transaction cannot be relayed or confirmed, temporarily locking the inputs (the funds are committed as `sum(inputs) - sum(outputs)` and the transaction must be reconstructed at a higher rate). Even when relayable, the signed transaction silently underpays relative to intent, degrading confirmation reliability — the same user-visible harm as a message not being relayed because the deposited fee is insufficient.

### Likelihood Explanation
Triggered deterministically whenever `SignableTransaction::new` is invoked with `data: Some(_)`: every such transaction's `needed_fee` and minimum-fee check use a vbytes figure that omits up to ~90 vbytes of real transaction size. The magnitude of the shortfall scales with `fee_per_vbyte` and the data length. No attacker cooperation, timing, or privileged position is required; it is a pure arithmetic omission reachable entirely through public inputs to the in-scope API.

### Recommendation
Include the OP_RETURN output in fee estimation. Either:
- Pass the finalized `tx_outs` (payments + data output + optional change placeholder) into `calculate_weight_vbytes` instead of reconstructing outputs from `payments` alone, or
- Add a `data_len`/`op_return: Option<&ScriptBuf>` parameter to `calculate_weight_vbytes` so the estimated transaction matches the signed one byte-for-byte in output count and size.

Additionally, compute the `TooLowFee` minimum against the same fully-populated transaction so the check reflects the real serialized size.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Call SignableTransaction::new with a data payload and a borderline fee rate.

let data = vec![0u8; 80]; // maximum allowed
let payments: &[(ScriptBuf, u64)] = &[(some_script, 10_000)];

let signable = SignableTransaction::new(
    vec![input],            // one ReceivedOutput with sufficient value
    payments,
    Some(change_script),    // change address
    Some(data.clone()),
    fee_per_vbyte,          // e.g. 1 sat/vbyte
).unwrap();

// The estimated vbytes omit the OP_RETURN output:
//   calculate_weight_vbytes(inputs, payments, change) builds outputs only from
//   `payments` (+change) — send.rs:85-99 — while the real tx has an extra
//   ~90-vbyte OP_RETURN output pushed at send.rs:195-201.
//
// Therefore:
//   signable.needed_fee() == fee_per_vbyte * vbytes_without_data
// while the actual serialized transaction is ~90 vbytes larger, so:
//   actual_fee_rate = signable.fee() / real_vbytes < fee_per_vbyte
//
// With fee_per_vbyte chosen near DEFAULT_MIN_RELAY_TX_FEE/1000, the TooLowFee
// check (send.rs:211) passes yet the completed transaction's real fee rate is
// below the relay minimum — an unrealyable, fully valid signed transaction.
```
