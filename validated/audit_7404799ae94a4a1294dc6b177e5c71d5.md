## Title
Permanent escrow lock when cross-chain settlement/cancellation `onAccept` reverts, because `IntentGatewayV2` dispatches `RedeemEscrow`/`RefundEscrow`/cancel-`DispatchGet` messages with `timeout: 0` - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2` escrows a user's input tokens on the source chain, then relies on a single cross-chain settlement message (`RedeemEscrow` after a solver fills, or `RefundEscrow` after a destination-side cancel) to release that escrow back on the source chain. Every one of these dispatches hard-codes `timeout: 0` ("never expires"). If the source-chain `onAccept` handler for that message permanently reverts (e.g. the beneficiary is blacklisted/paused by the escrowed ERC-20, or any other deterministic revert condition in `_withdraw`), the ISMP host deletes the request receipt "so it can be retried" — but since `timeout` is 0 the request can never be timed out, and since the revert condition is deterministic, retries never succeed either. The escrowed funds become permanently unreachable, with no fallback path, exactly mirroring the source-report pattern of an unrecoverable destination-side failure with no cancel/refund on the source.

### Finding Description
The three cross-chain settlement/cancellation dispatches in `ExtrinsicIntents.sol` all set `timeout: 0`:

- `_fillCrossChain` → `RedeemEscrow` `DispatchPost` with `timeout: 0` [1](#0-0) 
- `_cancelFromSource` → `DispatchGet` with `timeout: 0` [2](#0-1) 
- `_cancelFromDest` → `RefundEscrow` `DispatchPost` with `timeout: 0` [3](#0-2) 

Per the protocol documentation, `timeout: 0` means the message "will never expire" and can only be resolved by successful delivery — there is no timeout-triggered refund path available for these calls. [4](#0-3) 

When the settlement message is finally delivered to the source-chain gateway, `EvmHost.dispatchIncoming` invokes `IApp.onAccept`. If that call fails, the host simply deletes the request receipt "so it can be retried" and returns — it does not revert the whole batch, and it does not provide any alternate recovery mechanism: [5](#0-4) 

The ISMP-level danger callout confirms the intended design: a failing `on_accept` is supposed to let the request "time out gracefully on the source" — but that graceful path only exists when a non-zero timeout is configured. [6](#0-5) 

On the source chain, `onAccept` for `RedeemEscrow`/`RefundEscrow` calls `_authenticate` then `_withdraw`, which performs `IERC20(token).safeTransfer(beneficiary, amount)` for each escrowed token: [7](#0-6)  and [8](#0-7) 

If `beneficiary` (the solver for `RedeemEscrow`, or `order.user` for `RefundEscrow`) is deterministically rejected by the escrowed token (e.g. a blacklist/pause on a token like USDC, or any other permanent revert condition reachable by an unprivileged party who can be named as `order.user`/solver in an order they construct), `safeTransfer` reverts every single time. Because the destination side has already unrecoverably completed its half of the transaction — the solver delivered output tokens and the fill is committed (`_filled[commitment] = msg.sender`) for `RedeemEscrow`, or the order has been marked `_filled[commitment] = order.user` to block future fills for `RefundEscrow` — there is no way to re-route, redirect, or otherwise change the beneficiary or retry with different parameters. The escrow stays locked in `_orders[commitment][token]` on the source chain forever: no timeout ever fires (timeout = 0), and every relayer retry of the same message hits the same deterministic revert.

This is the direct on-chain analog of the Linea report: transaction 1 (destination fill / destination cancel) succeeds and is irreversible, while transaction 2 (source-chain settlement) can fail indefinitely with no cancel/refund mechanism, resulting in permanent fund loss.

### Impact Explanation
This is a direct loss-of-funds bug matching the bounty's "stealing or loss of funds" and "bridged assets ... must move exactly once and only to the rightful beneficiary" criteria. Escrowed input tokens (which can be arbitrary ERC-20 value, potentially large amounts for a market-making/solver flow) become permanently locked in the `IntentGatewayV2` contract with no cancellation, retry-with-different-beneficiary, or governance-driven escape hatch, since the only recovery primitives (`cancelOrder` routes) are themselves blocked once `_filled[commitment]` is non-zero from the irreversible destination-side action.

### Likelihood Explanation
The triggering condition (a beneficiary address that a specific token will always refuse to transfer to — blacklist, pause, non-standard `transfer` return-value handling that a wrapped `safeTransfer` treats as failure, or a beneficiary contract that reverts on token receipt) is realistic for common tokens like USDC/USDT and is fully within an unprivileged user's/solver's control when constructing an order or selecting a fill beneficiary. No malicious relayer, prover, or admin is required — the failure is a deterministic property of the token/beneficiary pair combined with the protocol's own hard-coded `timeout: 0`.

### Recommendation
Do not hard-code `timeout: 0` for `RedeemEscrow`/`RefundEscrow`/cancellation-`DispatchGet` messages. Configure a bounded timeout so that if `onAccept` cannot be executed successfully after the timeout elapses, `onPostRequestTimeout`/`onGetTimeout` can trigger a deterministic fallback (e.g., refund escrow to `order.user` regardless of the originally intended beneficiary, or allow governance/permissionless sweep after expiry) so escrowed funds are never permanently unreachable.

### Proof of Concept
1. Deploy `IntentGatewayV2` on source chain S and destination chain D, with escrow token `T` = USDC (has `isBlacklisted`).
2. User places a cross-chain order on S, escrowing `T`, with `order.output.beneficiary` left as their own address but naming a solver they control who is later blacklisted, OR: for the `_cancelFromDest` path, the `order.user` address itself becomes blacklisted by `T`'s issuer for unrelated reasons after order placement but before cancellation.
3. Destination-side action completes irrevocably:
   - Fill path: solver calls `fillOrder`, delivering output tokens to the beneficiary and dispatching `RedeemEscrow` via `DispatchPost{ timeout: 0 }` (`ExtrinsicIntents.sol:139-156`).
   - Cancel-from-destination path: caller invokes `cancelOrder` on D, marking `_filled[commitment] = order.user` and dispatching `RefundEscrow` via `DispatchPost{ timeout: 0 }` (`ExtrinsicIntents.sol:240-267`).
4. Relayer delivers the message to S; `EvmHost.dispatchIncoming` calls `onAccept`, which calls `_withdraw`, which calls `IERC20(T).safeTransfer(beneficiary, amount)` — this reverts because `beneficiary` is blacklisted.
5. `EvmHost.dispatchIncoming` deletes the request receipt and returns without reverting the batch (`EvmHost.sol:809-816`), leaving the message "retryable."
6. Any number of relayer retries reproduce the same revert since the blacklist condition is permanent and `timeout: 0` means the message can never be timed out.
7. Escrowed `T` remains locked in `_orders[commitment][T]` on chain S indefinitely; `cancelOrder` cannot be invoked again because `_filled[commitment]` is already non-zero (`Filled()` revert in `cancelOrder`, `IntentGatewayV2.sol:470-490`).

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

The request `handle` is used to notify onchain `IsmpModule`s of new requests to be processed. A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
