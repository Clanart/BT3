### Title
`ReceivedOutput::read` accepts an unverified scalar offset, allowing deserialized outputs to be mis-attributed to the wallet key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The MLflow advisory is an unsafe-deserialization bug class: untrusted bytes are materialized into an object whose fields are trusted without validation. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134`, which deserializes a spending `offset`, a `TxOut`, and an `OutPoint` as three independent fields without ever verifying that `offset` actually maps the wallet's key to `output.script_pubkey`. The honest construction path, `Scanner::scan_transaction`, derives the offset exclusively from the registered `scripts` map (`mod.rs:199-214`), so offset and script are guaranteed consistent — `read` drops that invariant entirely.

### Finding Description
`ReceivedOutput` couples a scalar `offset` (used to re-key the threshold key via `ThresholdKeys::offset`, `crypto/dkg/src/lib.rs:414-417`) with a claimed `output`. The only producer that establishes correctness is `Scanner`, which inserts `offset` into `scripts` keyed by `p2tr_script_buf(key + offset*G)` (`mod.rs:180-196`) and therefore guarantees the offset is the one that regenerates the output's script. `ReceivedOutput::read` performs `Secp256k1::read_F` for the offset and `TxOut::consensus_decode`/`OutPoint::consensus_decode` for the rest (`mod.rs:123-131`) with no consistency check. Any untrusted byte stream (e.g., a peer-supplied or coordinator-relayed serialized output) can pair an arbitrary `offset` with an arbitrary `script_pubkey`/`OutPoint`, and consumers will treat the result as a spendable wallet output. This is an undocumented deserialization invariant violation — the type has no `verify`/`validate` and callers receive no signal that the tuple is incoherent.

### Impact Explanation
A malicious counterparty supplying serialized `ReceivedOutput` bytes can cause two concrete harms, both matching the accepted impact criteria:
1. **Funds reported received that are not spendable**: attacker serializes a `ReceivedOutput` with a real on-chain output paying to the wallet's registered script but a bogus `offset` (or vice versa: an output paying to an attacker key paired with the wallet's offset). The wallet records/credits it as a received output. When it tries to spend, `keys.offset(output.offset())` produces a signing key whose tweaked point does not match `output.script_pubkey`, so the spend is either impossible or produces an invalid transaction.
2. **False attribution of foreign outputs**: pairing an attacker-controlled script_pubkey with a wallet offset causes the wallet to treat outputs it does not own as its own balance, which can drive incorrect change/fee computation in `send.rs`.

Severity: Medium — the primitive is a silent integrity failure on untrusted input; it does not directly leak key material, but corrupts wallet state and spendability decisions.

### Likelihood Explanation
Reachable by any unprivileged party that can cause serialized `ReceivedOutput` bytes to be fed to `ReceivedOutput::read` (stored/relayed output records), per the allowed input surface. Exploitation requires only constructing `offset || TxOut || OutPoint` bytes; no signatures, collusion, or privileged position needed. The probability of the inconsistency being detected downstream is low because nothing re-derives the script from the offset after deserialization.

### Recommendation
After deserializing in `ReceivedOutput::read` (or at first use in `send`), recompute `p2tr_script_buf(scanner_key + G * offset)` and reject the input unless it equals `output.script_pubkey`. Alternatively, store only the `outpoint`/`output` and re-derive the offset from `Scanner::scripts` at load time, so deserialized data can never introduce a key/script mismatch.

### Proof of Concept
```rust
// Attacker-controlled bytes:
let mut buf = vec![];
// bogus offset (e.g., Scalar::ONE) instead of the offset Scanner::register_offset returned
buf.extend(Scalar::ONE.to_bytes());
buf.extend(serialize(&victim_txout));   // a real TxOut paying to the wallet's script_pubkey
buf.extend(serialize(&real_outpoint));

let ro = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // succeeds
// ro.offset() == 1, but key + 1*G does NOT map to victim_txout.script_pubkey
// Wallet credits ro.value(); any spend via keys.offset(ro.offset()) targets a key
// unrelated to the output -> funds recorded as received are unspendable.
```
Contrast with `Scanner::scan_transaction` (`mod.rs:205-211`), which only emits `ReceivedOutput`s whose offset was proven to regenerate the exact `script_pubkey` via `register_offset`.
