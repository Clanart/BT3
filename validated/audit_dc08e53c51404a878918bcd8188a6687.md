### Title
Cross-chain token amount rounds down to zero during ERC20→Substrate conversion, silently accepting a fund transfer and burning the deposited value — `hyper-fungible-token` pallet (`modules/pallets/hyper-fungible-token/src/impls.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token::on_accept` (and the equivalent `on_timeout` refund path) converts an incoming ERC20-denominated amount to the pallet's local balance using `convert_to_balance`, which performs an integer division by `10^(erc_decimals - local_decimals)`. When the attacker-controlled `message.amount` is small relative to that scale factor, the division truncates to zero, and the pallet proceeds to mint/transfer `0` to the beneficiary and emits a success event — exactly the same "scale-down-then-round-to-zero, no zero check" pattern described in the external report's `getAmounts`/`getLiquidityDeltas` bug.

### Finding Description
`convert_to_balance` performs a plain floor division with no minimum-amount or zero-result check: [1](#0-0) 

It is invoked directly inside `on_accept` (the ISMP inbound handler that credits a beneficiary for a cross-chain transfer originated on an EVM chain) without any post-conversion validation: [2](#0-1) 

The same unguarded conversion is used again in the `on_timeout` refund path: [3](#0-2) 

Because `erc_decimals` and `local_decimals` are independently configured per `(AssetId, StateMachine)` via governance (`Precisions` storage, set in `register_token`/`update_token`, which only enforce `erc_decimals >= local_decimals`), any asset pair with a decimals gap is affected: [4](#0-3) 

If `message.amount` (fully attacker-controlled — it is decoded straight from the request body) is smaller than `10^(erc_decimals - local_decimals)`, `convert_to_balance` returns `0`. `on_accept` then calls `mint_into`/`transfer` with `amount = 0` and still emits `TokenReceived { amount: 0, ... }` as a successful, finalized message — there is no revert, no rejection, and no way for the beneficiary to be made whole after the fact, since the message has already been accepted by the ISMP router as valid and final.

### Impact Explanation
This directly parallels the seed report's "false zero-amount acceptance" primitive: a value that should require a real token movement is silently coerced to `0` by decimal rescaling, and the system accepts the operation as fully valid regardless. Here, the accepted-but-uncredited state corresponds to a real, irreversible loss: whatever ERC20 amount was locked/burned on the EVM side for that dispatch is not represented as any minted/transferred value on the Substrate side. Because `on_accept` is invoked as part of finalizing an ISMP request, this is a genuine "false state acceptance" / fund-loss bug within the bridge's core token-relay module, not a peripheral issue.

### Likelihood Explanation
This requires no privileged access, malicious relayer, or compromised prover — it triggers purely from an ordinary cross-chain message with a small `amount` field relative to the configured `Precisions` gap for that asset/chain pair, which any user (or an attacker intentionally probing dust amounts) can construct. The only precondition is that governance has registered an asset pair with `erc_decimals > local_decimals` (a normal, expected configuration, e.g. an 18-decimal EVM token mapped to a 6- or 0-decimal local asset), which the registration code explicitly allows.

### Recommendation
In `convert_to_balance` (or immediately after calling it in `on_accept`/`on_timeout`), reject amounts that convert to zero when the original ERC20 amount was non-zero (e.g. return an error such as `AmountTooSmallForConversion` rather than silently proceeding), or round up when precision would otherwise be lost, and audit all other decimal-rescaling call sites in the codebase for the same silent-truncation pattern (e.g. the analogous `adjustDecimals`/`adjustDecimalsFloor` helpers used elsewhere in the SDK, which already correctly round up for fees — this pallet function should follow the same convention for inbound transfers).

### Proof of Concept
1. Governance registers a token pair where the EVM-side contract uses `erc_decimals = 18` and the local Substrate asset uses `local_decimals = 6` (permitted since `18 >= 6` passes the `ErcDecimalsBelowLocal` check).
2. An attacker (or any user) triggers a cross-chain dispatch to the registered `HyperFungibleToken` EVM contract with `message.amount = 1` (1 wei, i.e., `< 10^(18-6) = 10^12`).
3. The message reaches `on_accept` on Hyperbridge; `convert_to_balance(1, 18, 6)` computes `1 / 10^12 = 0`.
4. `mint_into`/`transfer` is called with `amount = 0`; the call succeeds, `TokenReceived { amount: 0 }` is emitted, and the request is finalized as successfully processed — with no error and no path to reclaim the corresponding value burned/locked on the EVM side. [1](#0-0) [5](#0-4)

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
