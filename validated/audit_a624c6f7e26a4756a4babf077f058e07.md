### Title
Stale cached preprocess enables FROST nonce reuse across distinct signing inputs - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug class: a getter returns a handle to mutable driver-owned state after dropping the lock, and a concurrent write can replace/free that state so the caller consumes a stale object. The Serai analog lives in `SigningProtocol::preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:100-148`): the cached FROST preprocess seed stored under `CachedPreprocesses` keyed by `context` is read back and handed to `AlgorithmSignMachine::from_cache` on *every* invocation, but it is never consumed, invalidated, or rebound to the specific signing inputs (participant preprocesses and message). Each call to `share_internal`/`preprocess_internal` re-derives the identical deterministic nonces from the identical seed (`seeded_preprocess` in `crypto/frost/src/sign.rs:121-144` uses `ChaCha20Rng::from_seed(*seed.0)`), while the inputs that must be bound to that nonce — the `preprocesses` map and the `key_pair` embedded in `set_keys_message` — are supplied per-call and can differ between calls.

### Finding Description
- `CachedPreprocesses::set` runs only if the context key is absent (`signing_protocol.rs:123-135`); afterwards the same decrypted seed is returned forever (`signing_protocol.rs:137-145`). There is no delete-on-use and no binding of the cached seed to the preprocesses/message it was first issued for.
- `DkgConfirmer::share` (`signing_protocol.rs:304-310`) and `DkgConfirmer::complete` (`signing_protocol.rs:312-327`) each accept an externally supplied `HashMap<Participant, Vec<u8>>` of serialized preprocesses (parsed via `machine.read_preprocess` at `signing_protocol.rs:165`, i.e., attacker-influenced bytes) and a `key_pair` that determines the signed message via `set_keys_message` (`signing_protocol.rs:296-300`). The `context` is only `(b"DkgConfirmer", attempt)` (`signing_protocol.rs:275`), so all calls within one DKG attempt share one nonce seed regardless of which preprocesses/key_pair are passed.
- The file's own header acknowledges the missing check: the decided nonces' commitments are not verified to match the on-chain preprocesses before shares are published (`signing_protocol.rs:50-54`, TODOs), and `complete` re-executes `share_internal` a second time (`signing_protocol.rs:321-324`) — a second signing pass under the same seed with independently supplied inputs.
- If `share()` is invoked once with preprocess set/message A and again (e.g., via `share` then `complete`, or repeated handling of tributary data) with a distinct preprocess set or distinct `key_pair`/message B, the same binomial nonce `(d, e)` signs two different challenges. Two Schnorr/FROST shares under one nonce over different `msg`/binding-factor transcripts allow algebraic recovery of the validator's MuSig secret key share — the exact failure the FROST docs warn about (`spec/cryptography/FROST.md:51-55`, "Reusing preprocesses would enable a third-party to recover your private key share").

### Impact Explanation
Reuse of a FROST nonce across two distinct (preprocess set, message) pairs exposes the validator's private MuSig key share (`self.key`), since each share is `d + e*rho + lambda*s*c` and two equations with different `rho`/`c` over the same `d, e` yield `s`. Recovery of a validator key in `DkgConfirmer` compromises the root-of-trust key used to confirm validator sets on Substrate, enabling forgery of set-key confirmations. This maps to the accepted impact class: concrete signing of an unintended message plus key share recovery.

### Likelihood Explanation
All inputs required to trigger the divergence — the serialized preprocess map and the `key_pair` — are supplied per call and parsed through `read_preprocess`/`set_keys_message` from protocol data, not from local secrets. The code path re-executes `share_internal` unconditionally inside `complete` (`signing_protocol.rs:321-326`), and the author-documented invariant ("commitments generated from the decided nonces are in fact its commitments on-chain") is explicitly unimplemented (TODO at `signing_protocol.rs:51`). Likelihood is bounded by needing two executions under the same `(b"DkgConfirmer", attempt)` context with differing inputs — e.g., a DKG confirmation retried after the decided key pair or signer set changed — which the design deliberately supports via DB-backed re-execution rather than in-memory state. Caveat: a fully worked trigger depends on tributary message ordering, which I could not fully trace within `handle.rs`.

### Recommendation
Bind the cached seed to the inputs it was issued for: store alongside `CachedPreprocesses` a hash of the canonical participant set and the preprocess bytes/message (or the published preprocess commitments), and refuse `share_internal`/`complete` when the supplied `preprocesses`/`key_pair` hash differs. Additionally, delete or tombstone the cached seed once a share has been produced for a context, and implement the documented TODO of verifying our on-chain preprocess equals the one derived from the cached seed before publishing any share.

### Proof of Concept
Conceptual sequence against `DkgConfirmer`:
1. Call `share(preprocesses_A, key_pair_A)`. `preprocess_internal` caches seed S under context `(b"DkgConfirmer", attempt)` and returns machine M₁ with nonces derived from `ChaCha20Rng::from_seed(S)`. A share `s_A = d + e·rho_A + λ·x·c_A` is produced and returned.
2. Call `complete(preprocesses_B, key_pair_B, shares)` (or `share` again) where `preprocesses_B` differs from A or `key_pair_B` yields a different `set_keys_message`. `share_internal` → `preprocess_internal` reloads the *same* seed S (`signing_protocol.rs:137`), reconstructing identical nonces `d, e` (`sign.rs:127-132`).
3. The second call computes `s_B = d + e·rho_B + λ·x·c_B` with `rho_B, c_B` distinct because the preprocess commitments and message differ.
4. Given `s_A, s_B` and public `rho_A, rho_B, c_A, c_B, λ`, solve the two linear equations for `d` and then `x` — the validator's MuSig secret share — since `d, e` are identical across both shares.
