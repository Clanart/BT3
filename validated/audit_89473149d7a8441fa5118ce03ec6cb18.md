### Title
Division-by-zero panic in reward distribution when a consolidated validator node has zero CN-staking and zero CL-staking — ([File: kaiax/staking/staking_info.go])

### Summary
`consolidatedNode.Split()` divides a reward amount by `StakingAmount + CLStakingInfo.CLStakingAmount` without checking that this sum is non-zero. When the block's proposer/reward-address maps to a consolidated node whose own CN-stake is `0` (rounded down from staking-less-than-1-KAIA, or from de-staking) and whose linked Consensus-Liquidity (CL) pool also has `0` staked, this produces a `big.Int` division by zero, which panics at runtime.

### Finding Description
`consolidatedNode.Split` computes: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	...
	totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)   // <-- panics if totalAmount == 0
	...
}
```

`StakingAmount` and `CLStakingAmount` are both integer KAIA amounts rounded down from wei via integer division by `params.KAIA`: [2](#0-1) [3](#0-2) 

So a CN with less than 1 KAIA staked, whose linked CL pool also has less than 1 KAIA staked, produces `StakingAmount == 0 && CLStakingAmount == 0`, i.e. `totalAmount == 0`.

`Split()` is invoked without any non-zero guard from the reward proposer-assignment path: [4](#0-3) 

```go
cns := si.ConsolidatedNodes()
for _, cn := range cns {
	if cn.RewardAddr != config.Rewardbase {
		continue
	}
	if cn.CLStakingInfo == nil {
		break // Early exit if there's no CL for proposer
	}
	cnAmount, clAmount := cn.Split(proposer)   // no check that StakingAmount+CLStakingAmount > 0
	...
}
```

The only guard is `cn.CLStakingInfo != nil` — it never checks `StakingAmount + CLStakingAmount > 0`. The KIP-82/Kore staker-reward paths (`assignStakingRewards`, `assignStakingRewardsFlex`) are safe because they only call `Split()` when the combined stake already exceeds a positive `minStake` threshold, but the proposer-reward path in `specWithProposerAndFundsFlex` (and its non-flex counterpart `specWithProposerAndFunds`, called similarly at `kaiax/reward/impl/getter.go:366` and `:388`) applies `Split()` to whichever node is credited as `config.Rewardbase` for the block, with no analogous floor check.

This mirrors the external report's bug class exactly: an unchecked value that can legitimately be `0` becomes a division denominator, causing an unhandled revert/panic (`SafeMath`-style DoS in the Solidity report; a Go `big.Int` division-by-zero panic here).

### Impact Explanation
A `big.Int` division by zero in Go panics. `GetBlockReward`/`GetDeferredReward` in `kaiax/reward` is used for RPC reward queries and potentially block-level reward computation. A panic here crashes the calling goroutine/process (RPC handler or block-processing routine), producing a Denial of Service for any node that attempts to compute the reward for the affected block (RPC nodes serving `kaia_getReward`-style calls, or full nodes finalizing/re-processing the block). If reached during block finalization/state transition, it can also cause state divergence between nodes that crash versus nodes that don't reach the code path, undermining consensus.

### Likelihood Explanation
Reachability requires a validator's consolidated node to simultaneously have a rounded CN-stake of `0` KAIA and a linked CL pool with rounded stake of `0` KAIA, while remaining the credited `Rewardbase` for a block. Ordinary `WeightedRandom` qualification (post-Istanbul) filters out validators below `reward.minstake` from being qualified/proposer, which reduces likelihood under typical mainnet configuration. However:
- Under `RoundRobin`/`Sticky` proposer policies, or under the WeightedRandom fallback rule ("if no validator meets the minimum staking requirement, all council members are qualified"), an under-staked or zero-staked council member can become the proposer.
- A CL pool can independently exist with zero (or sub-1-KAIA) delegated stake at the time a block is credited to that validator, since CL delegation and CN staking are managed by different, unprivileged actors (delegators/stakers) via ordinary transactions.
This is a real but conditional/edge-case reachability path, dependent on governance policy and timing of staking/CL-delegation actions, all of which are unprivileged, transaction-driven operations.

### Recommendation
In `consolidatedNode.Split` (`kaiax/staking/staking_info.go`), guard against `totalAmount == 0` (return `amount, big.NewInt(0)` similarly to the `CLStakingInfo == nil` case) before performing the division. Additionally, in `specWithProposerAndFundsFlex`/`specWithProposerAndFunds` (`kaiax/reward/impl/getter.go`), only take the CL-split branch when the combined stake is non-zero, consistent with the guards already used in `assignStakingRewards`/`assignStakingRewardsFlex`.

### Proof of Concept
1. Register a validator `V` in the AddressBook with `StakingAmount` just under 1 KAIA (rounds to `0` after `/params.KAIA`), and register a CL pool for `V` via `CLRegistry` with a staked amount also under 1 KAIA (rounds to `0`).
2. Ensure `V` becomes qualified/proposer for a block — e.g. run under `istanbul.policy = RoundRobin`/`Sticky`, or arrange (via ordinary unstake transactions) that all council members fall below `reward.minstake` so the WeightedRandom fallback "all qualified" rule applies, and `V` is selected as proposer for block `N`.
3. Call `GetBlockReward(N)` (or let `FinalizeState`/reward computation run for block `N`) after Prague hardfork (`config.Rules.IsPrague`) with `UseFlexReward` enabled or disabled.
4. In `specWithProposerAndFundsFlex`/`specWithProposerAndFunds`, the code finds `cn` matching `config.Rewardbase == V`, sees `cn.CLStakingInfo != nil`, and calls `cn.Split(proposer)`.
5. Inside `Split`, `totalAmount = StakingAmount(0) + CLStakingAmount(0) = 0`, and `clAmount.Div(clAmount, totalAmount)` panics with division by zero, crashing the node/RPC handler processing that block's reward. [1](#0-0) [5](#0-4)

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

// specWithProposerAndFundsFlex assigns proposer, kif, kef, kpf to the reward spec.
// This must be the last step of building the RewardSpec as it finalizes the Proposer, KEF, KIF fields.
func specWithProposerAndFundsFlex(spec *reward.RewardSpec, config *reward.RewardConfig, proposer, kif, kef, kpf *big.Int, si *staking.StakingInfo) *reward.RewardSpec {
	newSpec := spec.Copy()

	// If KIF, KEF, or KPF address is not set, proposer takes it.
	if common.EmptyAddress(si.KIFAddr) {
		newSpec.KIF = common.Big0
		proposer.Add(proposer, kif)
	} else {
		newSpec.KIF = kif
		newSpec.IncRecipient(si.KIFAddr, kif)
	}

	if common.EmptyAddress(si.KEFAddr) {
		newSpec.KEF = common.Big0
		proposer.Add(proposer, kef)
	} else {
		newSpec.KEF = kef
		newSpec.IncRecipient(si.KEFAddr, kef)
	}

	if common.EmptyAddress(si.KPFAddr) {
		newSpec.KPF = common.Big0
		proposer.Add(proposer, kpf)
	} else {
		newSpec.KPF = kpf
		newSpec.IncRecipient(si.KPFAddr, kpf)
	}

	newSpec.Proposer = proposer
	if !config.Rules.IsPrague || si.CLStakingInfos == nil {
		newSpec.IncRecipient(config.Rewardbase, proposer)
		return newSpec
	}

	// Handle CLStakingInfo for proposer after Prague
	cns := si.ConsolidatedNodes()
	for _, cn := range cns {
		if cn.RewardAddr != config.Rewardbase {
			continue
		}
		if cn.CLStakingInfo == nil {
			// Early exit if there's no CL for proposer
			break
		}

		cnAmount, clAmount := cn.Split(proposer)

		newSpec.IncRecipient(cn.RewardAddr, cnAmount)
		newSpec.IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)
		return newSpec
	}

	newSpec.IncRecipient(config.Rewardbase, proposer)
	return newSpec
}
