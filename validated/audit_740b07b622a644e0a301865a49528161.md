## Title
Attacker-Controlled `WWW-Authenticate` Realm Spoofing Triggers Unauthorized GitHub Sign-In / Credential Handoff - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
GitHub Desktop's credential-helper trampoline classifies a git remote as a trusted GitHub Enterprise endpoint based on an unauthenticated substring match against the `WWW-Authenticate` header that the remote server returned during Git's HTTP auth negotiation. A malicious or MITM'd git remote can spoof this header to make an arbitrary host look like a GitHub host, causing Desktop to (a) pop a native GitHub sign-in/OAuth prompt bound to the attacker's endpoint, and (b) subsequently treat that attacker endpoint as a legitimate GitHub account so the credential helper hands back real GitHub credentials for connections to it.

### Finding Description
Git's credential protocol forwards any `WWW-Authenticate` response headers it receives during HTTP auth to the configured credential helper as `wwwauth[]=<value>` fields (this is documented Git behavior, referenced directly in the code comment). GitHub Desktop's trampoline credential helper receives this data verbatim via `parseCredential`, which performs no validation on the keys/values it parses [1](#0-0) .

`getEndpointKind` then trusts this attacker-supplied value directly:
```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
``` [2](#0-1) 

Any remote HTTP git server (or a proxy/MITM sitting on the connection) that answers a 401 with `WWW-Authenticate: Basic realm="GitHub"` will cause this check to classify the connection's endpoint as `'enterprise'`, regardless of the actual hostname. This bypasses the earlier, sound hostname-based checks `isGist`/`isDotCom`/`isGHE` [3](#0-2) .

Once classified as non-`generic`, `getCredential` checks whether an existing account matches the endpoint; since it won't (the endpoint is attacker-controlled, e.g. `evil.example.com`), it invokes the real Desktop UI to prompt the user to sign in to GitHub for that endpoint, and stores the resulting account bound to it:
```
if (endpointKind !== 'generic' && !accounts.some(a => a.endpoint === apiEndpoint)) {
  ...
  const account = await ui.promptForGitHubSignIn(endpoint)
  ...
  return credWithAccount(cred, account)
}
``` [4](#0-3) 

This is the exact bug-class analog to the seed report: a malformed/attacker-controlled protocol field (there, a spaced `Content-Length`; here, a spoofed `WWW-Authenticate` realm) is trusted by a downstream parser using loose matching instead of strict validation, producing a state confusion between what the transport (Git/libcurl) actually connected to and what Desktop's internal classification believes it connected to.

### Impact Explanation
- **Unauthorized OAuth / account binding**: A user cloning or fetching from a malicious repository unexpectedly gets prompted to "Sign in to GitHub" for an attacker-chosen host, and if completed, an account record for that host is created and persisted via `credWithAccount`/`AccountsStore`.
- **Credential/token exfiltration path**: Once such an account exists (or if the substring check matches for a host the user is later duped into associating with a real account), subsequent `getCredential`/`getGitHubCredential` calls for that same attacker endpoint will find the matching account by endpoint/origin and hand the user's real GitHub token back to Git, which then uses it to authenticate the actual network connection — to the attacker's server. This satisfies "credential/token exfiltration" and "unauthorized OAuth or account binding" in the valid-impact list, driven purely by a network response the attacker controls, no local access or prior compromise required.

### Likelihood Explanation
Triggering this requires only that the user perform a normal Git network operation (clone/fetch/push/pull) against a repository whose HTTP remote is attacker-controlled or MITM'd, and that the server return a 401 with a crafted `WWW-Authenticate` header — no special headers, no unusual repo content, and no additional user action beyond the sign-in prompt (which mimics Desktop's normal GitHub onboarding flow, making it plausible for users to complete it without suspicion, especially against a spoofed "GitHub Enterprise" login screen).

### Recommendation
- Stop using a loose `String.includes('realm="GitHub"')` substring match on unauthenticated data to decide trust; anchor/parse the `realm` parameter strictly and never let it override actual hostname-based classification (`isGist`/`isDotCom`/`isGHE`) as the primary signal.
- Require the actual hostname to be validated against Desktop's known GitHub/GHE endpoint criteria (`isGitHubHost`) before using `wwwauth[]` content as anything beyond a UX hint, and never let it independently promote an unknown host straight to `'enterprise'`.
- Reject or ignore `wwwauth[]` values containing untrusted formatting, and add input validation to `parseCredential` to reject unexpected/duplicate top-level keys instead of blindly trusting `Map.set` overwrite semantics.

### Proof of Concept
1. Stand up a plain HTTP git server at `http://evil.example.com/repo.git` that, on any request requiring auth, responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone/add `http://evil.example.com/repo.git` as a remote and perform a fetch.
3. Git invokes Desktop's credential helper trampoline with `wwwauth[0]=Basic realm="GitHub"` among the credential fields [2](#0-1) .
4. Observe `getEndpointKind` returns `'enterprise'` and Desktop shows a "Sign in to GitHub" prompt for `evil.example.com` [4](#0-3) ; if the user signs in, an account bound to that endpoint is created, and future credential requests to it will be answered with that account's real token.

Note: I could not fully trace `ui.promptForGitHubSignIn` / `AccountsStore.addAccount` persistence semantics (e.g., exactly how `endpoint` is normalized/stored) within the indexing coverage available, since those files were not returned in full by search. A Devin session with full repository access would be needed to confirm the exact persistence path and whether any existing endpoint-normalization logic partially mitigates the account-binding step.
