### Title
Deterministic FROST nonce reuse via repeated `share_internal` re-derivation from `CachedPreprocesses` enables secret share recovery — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates the *same* FROST nonces on every invocation by reloading a fixed 32-byte `CachedPreprocess` seed from the DB (keyed only by `context`) and re-deriving `(nonces, commitments)` via `ChaCha20Rng::from_seed`. Every call to `share_internal` — and therefore to `DkgConfirmer::share` and `DkgConfirmer::complete` — calls `preprocess_internal` again, producing an `AlgorithmSignMachine` whose secret nonces `(d, e)` are identical to those used in all prior calls for the same context. If signing is driven more than once with distinct attacker-influenced preprocess sets (the 'preprocesses' challenge feeding `rho` and the Schnorrkel challenge), the participant emits multiple signature shares of the form `s = d + e·rho_i + c_i·λ·x` over the *same* `(d, e)`. Collecting enough such shares gives a solvable linear system, recovering the validator's MuSig secret key share — the analog of a use-after-free: a one-shot secret (nonce) is reused after its single-use lifetime should have ended.

### Finding Description
In `crypto/frost/src/sign.rs`, `seeded_preprocess` derives nonces deterministically from the cached seed: `ChaCha20Rng::from_seed(*seed.0)` then `Commitments::new(rng, ...)` (lines 121–144). `from_cache` (lines 268–274) rebuilds the machine from the same seed with no consumed-marker, so each reconstruction yields byte-identical `(d, e)` pairs.

In `coordinator/src/tributary/signing_protocol.rs`:
- `preprocess_internal` (lines 100–148) loads the `CachedPreprocesses` entry keyed by `self.context` = `(b"DkgConfirmer", attempt)` (line 275) and calls `AlgorithmSignMachine::from_cache`, regenerating identical nonces every call.
- `share_internal` (lines 150–181) calls `self.preprocess_internal(participants).0`, so *each* share generation re-derives the same nonces.
- `DkgConfirmer::share` (lines 304–310) calls `share_internal`, and `DkgConfirmer::complete` (lines 312–327) calls `share_internal` **again** — a second signing with the same nonces. There is no guard preventing `share`/`complete` from being invoked multiple times per attempt with different `preprocesses` maps supplied by the caller.

The preprocess set is attacker-controlled: participant preprocess bytes enter via `read_preprocess`/`process_addendum` and change `rho` via the `preprocesses` challenge (`sign.rs` lines 361–371) and the Schnorrkel signature challenge. The file's own header (lines 34–54) documents that nonce reuse "will enable recovering the private key" and that safety depends solely on BFT ordering — with an explicit `TODO` acknowledging the missing check that published preprocesses match the presumed set — yet the nonce derivation itself stays fixed regardless of which preprocesses/msg are actually signed.

### Impact Explanation
A validator's Ristretto secret key share is the root of trust for confirming DKG results on-chain. Each share emitted is `s_i = d + e·rho_i + c_i·(λ·x)`. With `k` distinct shares over reused `(d, e)`, the system has unknowns `d, e, λx` — so as few as three shares over adversarially-divergent preprocess sets (different `rho`, different `c`) fully determine `λ·x`, and `x` since `λ` is public. This yields the validator's private key, enabling forgery of DKG-confirmation signatures and arbitrary tributary protocol messages as that validator. Impact: full private-key recovery from publicly observable signature shares — Critical severity class.

### Likelihood Explanation
Reachability requires `share`/`complete` (or repeated `share`) to be invoked with at least three distinct preprocess sets or messages under the same `(b"DkgConfirmer", attempt)` context. The preprocess map contents are contributed by external participants and the code path re-executes signing from persisted state rather than consuming a one-shot machine, so any re-execution with differing inputs (conflicting preprocess submissions, retries with mutated inputs, or `complete` invoked with a different set than `share`) triggers reuse. The file's own safety argument admits the invariant rests on BFT finality of inputs plus a `TODO` check that was never implemented; the nonce layer itself provides zero defense. Likelihood is gated by whether an attacker can cause re-execution with divergent inputs, but no in-code mechanism prevents it — Medium likelihood conditional on driver behavior, with deterministic leakage once triggered.

### Recommendation
Bind the cached preprocess to the exact data signed, per the file's own TODO:
1. Store the published preprocess bytes alongside `CachedPreprocesses` and abort `share_internal` if the regenerated preprocess does not match what was previously published for this context.
2. Additionally bind the sign inputs: on first `share`/`complete` for a context, persist a hash of `(sorted preprocesses, msg)`; refuse to produce another share if a subsequent call presents a different tuple.
3. Alternatively derive nonces as `H(seed || H(preprocesses || msg || context))` so reused seeds over divergent sessions yield independent nonces — while noting this permits ROS-style grinding and option 1/2 is preferable.

### Proof of Concept
1. Validator participates in `DkgConfirmer` for `(spec, attempt)`; `preprocess()` publishes `P` derived from cached seed `S` (signing_protocol.rs:123–147).
2. Attacker-coordinated preprocess set `A_1` is finalized; `share(A_1, kp)` emits `s_1 = d + e·rho_1 + c_1·λx` (lines 288–309 → 150–181 → sign.rs:283–410).
3. A second divergent set `A_2` (attacker swaps their own preprocess bytes) reaches `complete(A_2, kp, shares)` or a repeated `share(A_2, kp)`; `share_internal` rebuilds the machine from the same `S` (line 156 → 137–145), so `s_2 = d + e·rho_2 + c_2·λx` with identical `d, e`.
4. A third distinct set yields `s_3`. Solve the 3×3 linear system over `Ristretto::F` for `(d, e, λx)`; divide by the known Lagrange coefficient `λ` to recover `x`, the validator's private key. Verify against `G·x` equal to the validator's on-chain public key.
