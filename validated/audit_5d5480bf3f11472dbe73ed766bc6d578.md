### Title
Untrusted offset in `ReceivedOutput::read` is not bound to the output's script_pubkey, letting an attacker report funds under a key that cannot spend them - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to a path traversal where an attacker-controlled filename is trusted to locate a target, `ReceivedOutput::read` deserializes an attacker-controlled `offset` scalar and stores it alongside an attacker-controlled `TxOut`/`OutPoint` without verifying that `key + offset·G` actually produces `output.script_pubkey`. The scanner path (`scan_transaction`) always pairs offsets with scripts correctly, but `read` accepts any pairing, so bytes fed to it can describe an output that is "received" yet not spendable under the claimed offset.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs:122-134`, `ReceivedOutput::read` reads `offset` via `Secp256k1::read_F` and then consensus-decodes `output` and `outpoint`, constructing `ReceivedOutput { offset, output, outpoint }` with no consistency check. The struct's invariant — that `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` — is only enforced implicitly when the `Scanner` itself produces the `ReceivedOutput` (`scan_transaction`, lines 205-211 look up `self.scripts.get(&output.script_pubkey)`). The deserialization path bypasses this binding entirely, exactly like the ChurchCRM bug where `$rawUploadedFile['name']` is trusted without validating where it lands.

### Impact Explanation
Any component that accepts a serialized `ReceivedOutput` from an untrusted source (e.g., a peer or coordinator relaying scanned outputs) can be made to record an output whose declared `offset` does not derive the output's script key. When the wallet later attempts to spend it, `SignableTransaction::multisig` in `networks/bitcoin/src/wallet/send.rs:273-285` checks `p2tr_script_buf(offset.group_key()) != self.prevouts[i].script_pubkey` and returns `None`, so the signing machine refuses to build the transaction — funds the wallet believes it owns are unspendable. This yields a "funds reported received that are not spendable" condition: the wallet misattributes the output to a key offset it controls, and spends fail or must be manually repaired. It also enables misdirection — an `offset` crafted so `key + offset·G` matches a *different* registered script could mislabel the output's purpose (external vs. change vs. forwarded) in downstream classification logic like `kinds[offset_repr]` in `processor/src/networks/bitcoin.rs:693-695`.

### Likelihood Explanation
Reachability requires an attacker to supply serialized `ReceivedOutput` bytes to a reader. The `read`/`serialize` round-trip is a public API explicitly designed for crossing trust boundaries (it is the canonical wire/storage encoding for spendable outputs). Within the local scanner-only flow the invariant holds, so the severity hinges on integrators trusting `ReceivedOutput::read` output — a medium-confidence Medium: concrete availability/misattribution impact, but no direct signature forgery or key recovery.

### Recommendation
Either (a) make `ReceivedOutput::read` take the scanning `key` and verify `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`, returning an error on mismatch, or (b) rename/document it as trusted-only and provide a `Scanner::read_output(key, bytes)` verifying constructor. At minimum, have `SignableTransaction::new`/`multisig` treat the offset↔script mismatch as a hard deserialization error rather than a late `None`.
