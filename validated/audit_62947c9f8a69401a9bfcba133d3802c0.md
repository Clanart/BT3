### Title
Stale-diff TOCTOU in partial-commit staging causes silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported bug's broken invariant is: an operation commits to an economic/state outcome (a swap fill) without re-validating that the actual result still matches what the user approved, allowing attacker/market-driven drift between "what was shown" and "what was executed." The equivalent invariant in GitHub Desktop's commit pipeline is that a user reviews a diff, selects specific hunks/lines to stage, and expects that exact reviewed content to be committed. `applyPatchToIndex` breaks this invariant by re-fetching a fresh diff from disk at staging time instead of reusing the diff the user actually reviewed and selected against.

### Finding Description
When a user stages a partial commit (selecting individual lines/hunks), the UI computes a `DiffSelection` whose selected indices are relative to a specific `ITextDiff`/`ILargeTextDiff` object that was rendered on screen. At commit time, `applyPatchToIndex` does not reuse that reviewed diff object; it independently re-reads the working directory and recomputes a brand-new diff: [1](#0-0) 
It then formats a patch by applying the *old* selection's absolute line indices against the *newly fetched* diff: [2](#0-1) 

`formatPatch` blindly maps `file.selection.isSelected(absoluteIndex)` onto whatever hunks/lines exist in the diff passed to it: [3](#0-2) 

`createCommit` orchestrates this: it clears the index and calls `stageFiles`, which for partially-selected files calls `applyPatchToIndex` — again using whatever the working tree looks like at that moment, not what was reviewed: [4](#0-3) [5](#0-4) 

If the working-tree file content changes between the moment the diff was rendered/selected in the UI and the moment `git commit` actually runs (e.g., a build tool, linter/formatter, IDE auto-save, background sync, or any process shipped/triggered by a cloned repository's tooling modifies the file during that window), the hunk boundaries and line offsets shift. The stale absolute indices from the old selection no longer correspond to the same logical lines in the new diff, so `formatPatch` can select the wrong lines, include content the user never saw or intended to stage, or drop content the user intended to include — and the resulting patch is applied to the index and committed without any re-diff/re-confirmation check.

### Impact Explanation
This is a silent corruption of what the user commits: the app will happily create a commit (and the user may subsequently push it) containing lines that were never part of the reviewed/approved diff. Unlike the reference report's `SwapFacility`, where a missing `minOutAmount` check lets on-chain price drift silently produce a worse-than-expected fill, here a missing "diff hasn't changed" check lets working-tree drift silently produce a different-than-reviewed commit. There is no verification anywhere in `applyPatchToIndex`/`stageFiles`/`createCommit` that the diff used to build the patch is the same diff the selection was computed from.

### Likelihood Explanation
Medium-low: it requires the working tree to change between diff-render time and commit time. This is plausible in real developer workflows (auto-formatters, file watchers, build scripts triggered by opening/using a cloned project, editor autosave) and does not require local/physical device access, malware, or leaked credentials — the mutating process can be entirely legitimate tooling shipped with a cloned repository. The window is normally short but commit can be delayed arbitrarily by the user (e.g., leaving the "commit" confirmation open), widening the race window.

### Recommendation
Before formatting/applying the patch, re-validate that the diff associated with the current `DiffSelection` still corresponds to the on-disk file: e.g., compare the diff's `text`/hash of the underlying file content (or the diff generation timestamp/content hash) captured when the selection was made vs. what `getWorkingDirectoryDiff` returns immediately before staging, and abort/re-prompt the user if they differ, rather than silently applying stale-indexed selections to a new diff.

### Proof of Concept
1. Modify a tracked file, open Desktop's Changes view; a diff with two hunks is rendered and the user selects only hunk 2 for the commit (`DiffSelection` created against this diff instance).
2. Before clicking "Commit", an external process (e.g., an npm `pre-commit`-style watcher, formatter-on-save, or any tool the repository ships) rewrites the file so that hunk boundaries/offsets shift (e.g., adds/removes leading blank lines, reformats whitespace).
3. User clicks "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` calls `getWorkingDirectoryDiff` again, obtaining a diff with different hunk offsets than the one the selection was computed against [6](#0-5) .
4. `formatPatch` applies the stale absolute indices to the new hunk layout, producing a patch that stages different lines than the ones the user selected/reviewed [7](#0-6) .
5. The commit is created and can be pushed, containing content the user never explicitly approved — no error, warning, or diff re-check is surfaced.
