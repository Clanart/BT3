## Title
Poisoned Alive check-run notification permanently suppresses future legitimate check-failure alerts for the same commit SHA - (`app/src/lib/stores/notifications-store.ts`)

### Summary
`NotificationsStore.handleChecksFailedEvent` maintains an in-memory `skipCommitShas` / `skipCheckRuns` set that, once a commit SHA or check-run ID is added, is never removed until the user switches the selected repository. Both insertion points are reachable from unauthenticated, attacker-influenced data (the Alive websocket event and/or the GitHub REST API), and neither is validated against a specific PR/check-suite context before being treated as a durable "already handled" marker. This mirrors the zebra `SentHashes` pattern: a rejected/invalid object leaves a stale "seen" entry keyed by an identifier that a later, honest object can also carry, causing the honest object's notification to be silently dropped.

### Finding Description
`NotificationsStore` keeps two long‑lived Sets scoped to the currently selected repository: [1](#0-0) 

`handleChecksFailedEvent` is invoked for every `pr-checks-failed` Alive event received over the websocket channel: [2](#0-1) 

If the commit named in the event cannot currently be resolved locally (`getCommit` returns `null` — e.g., because the referenced commit hasn't been fetched yet, or the event names an unrelated/garbage SHA), the SHA is permanently added to `skipCommitShas` and the function returns. Likewise, if the check runs for the check suite are added: [3](#0-2) 

every `check.id` belonging to `event.check_suite_id` is unconditionally added to `skipCheckRuns`, regardless of whether the check truly failed. From that point on, `if (this.skipCommitShas.has(commitSHA)) return` at line 336 and `if (checkSuiteCheckRunIds.every(id => this.skipCheckRuns.has(id))) return` at line 374 will silently suppress **any subsequent** `pr-checks-failed` event for that same commit SHA or check-run set — including a legitimate one that arrives later once the commit is actually fetched/pushed or the checks genuinely fail.

The only cleanup path is `resetCache()`, called solely on `selectRepository` when the user switches to a *different* repo: [4](#0-3) 

There is no cleanup tied to the specific PR, check suite, or the passage of time — analogous to zebra's `SentHashes` entry only being cleared by unrelated commit-path activity, with no guarantee that cleanup ever occurs while the user stays on the same repository.

The event source itself is attacker-influenceable: Alive events arrive over a subscribed websocket channel and are minimally validated — `notify()` only checks the `type` field before dispatching: [5](#0-4) 

`isValidRepositoryForEvent` only checks that `owner`/`repo` match the currently selected GitHub repository; it performs no authentication of the specific `commit_sha`, `check_suite_id`, or `pull_request_number` against the actual PR state, and the same-owner/repo check is easy to satisfy for any repo the user has open: [6](#0-5) 

### Impact Explanation
A crafted (or replayed/race-condition-triggered) `pr-checks-failed` Alive message for a commit SHA that Desktop cannot yet resolve locally poisons `skipCommitShas` for that SHA for the remainder of the session on that repository. If that exact commit is later legitimately pushed/fetched and its CI genuinely fails, Desktop will silently swallow the "checks failed" notification the user relies on to catch broken builds before merging or deploying. This is a silent-suppression-of-security/quality-signal issue: it doesn't corrupt what is committed/pushed, but it does undermine one of Desktop's explicit user-facing safety signals (CI failure alerts tied to a user's own commits), which is the closest analogue in this codebase to the "delay/deny visibility of the honest event" impact of the original bug. Severity is bounded — no code execution, no credential exposure, no file-system impact — comparable in class (availability/integrity of an in-app safety signal, not data-plane compromise) to the "Medium, availability-bounded" rating of the original advisory.

### Likelihood Explanation
The `skipCommitShas`/`skipCheckRuns` poisoning is easy to trigger unintentionally (any Alive event racing ahead of a local fetch, or referencing a commit the user hasn't fetched yet, permanently disables that SHA/check-run-set for the session) and is plausible for a network-adjacent actor able to influence Alive/API responses (MITM on a misconfigured GHE endpoint, or an actor with the ability to enqueue Alive messages for a channel the user is subscribed to) to trigger deliberately. It requires no local access, no admin rights, and no prior malware — only the ability to get one crafted or mistimed event routed to the client, satisfying the "unprivileged, attacker-controlled API/notification object" criteria.

### Recommendation
- Scope `skipCommitShas`/`skipCheckRuns` per (repository, PR number, check_suite_id) rather than as a single global set for the lifetime of the selected repository, and expire entries after a bounded TTL.
- Do not add a commit SHA to `skipCommitShas` on a *transient* lookup failure (`getCommit` returning `null` because the commit isn't fetched yet); retry or fetch before giving up, and only suppress permanently on a durable, verified condition (e.g., verified non-matching author after a successful commit lookup).
- Re-validate check-run state against the API at delivery time rather than trusting the Alive payload's `check_suite_id`/`commit_sha` as an infallible identity key for permanent suppression.

### Proof of Concept
1. Attacker sends (or a race condition delivers) an Alive `pr-checks-failed` event for `owner/repo` that the victim currently has selected, with `commit_sha = X` where `X` is a commit not yet present in the victim's local clone (e.g., a SHA for a commit that will shortly be pushed as part of the honest PR workflow).
2. `handleChecksFailedEvent` calls `getCommit(repository, X)` — this fails/returns `null` because `X` isn't fetched yet — and `X` is added to `skipCommitShas` at line 344-345.
3. Later, the victim (or a teammate) legitimately pushes/fetches commit `X`, and CI genuinely fails; GitHub sends the honest `pr-checks-failed` Alive event for the same `commit_sha = X`.
4. `handleChecksFailedEvent` hits the guard at line 336 (`if (this.skipCommitShas.has(commitSHA)) return`) and silently drops the legitimate failure notification — the user never sees the CI-failure alert for this commit until they switch to a different repository and back (which calls `resetCache()`).

I could not fully verify from local code evidence how attacker-reachable the Alive websocket channel is in practice (e.g., whether channel messages are cryptographically signed end-to-end beyond the `signed_channel` field passed to `AliveSession`), since the `@github/alive-client` library internals are outside this repository's indexed code. This affects confidence in the "unauthenticated network attacker" likelihood claim; the race-condition/self-triggered variant (event outracing local fetch) does not require that assumption and is confirmed directly from local code.
