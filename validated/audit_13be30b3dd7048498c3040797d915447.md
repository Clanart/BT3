### Title
Unbounded recursive puzzle-driver traversal in offer/outer-puzzle matching causes stack-exhaustion crash - (File: `chia/wallet/outer_puzzles.py`)

### Summary
Chia's outer-puzzle "driver" framework (used for CAT, singleton, ownership, metadata, and CR/VC layers) recursively unwraps a puzzle reveal by calling each driver's `match`/`get_inner_puzzle`/`construct`/`solve` methods, which in turn call back into the shared dispatch function for every nested layer. The recursion depth is bounded only by how many recognizable layers are curried into an attacker-supplied puzzle, with no depth limit anywhere in the call chain. Because these functions are invoked directly on untrusted puzzle reveals taken from offer files / spend bundles supplied by an offer counterparty, a malicious counterparty can construct a puzzle with thousands of nested recognizable layers (e.g. CAT-of-CAT-of-CAT…) and crash the victim's wallet process with a Python `RecursionError`/stack overflow simply by having them inspect or accept the offer — the same bug class as CVE-2018-12066 (unbounded recursive expression parsing causing stack consumption and daemon crash), except here the "expression" is a CLVM puzzle structure and the "expression parser" is the Python driver-matching code.

### Finding Description
`match_puzzle()` iterates known drivers and calls `driver.match(puzzle)`: [1](#0-0) 

Each concrete driver's `match()` recurses into `self._match(...)` on the inner puzzle whenever another recognizable layer is found — for example the CAT driver: [2](#0-1) 

and similarly the singleton, ownership, metadata, and CR drivers each call back into `self._match`/`self._get_inner_puzzle`/`self._construct`/`self._solve` for their inner puzzle: [3](#0-2) [4](#0-3) 

None of these recursive call chains enforce a maximum nesting depth. The recursion is entered from processing of untrusted, attacker-supplied puzzle reveals in the offers/trading path: [5](#0-4) [6](#0-5) 

`Offer.from_spend_bundle()`/`_get_offered_coins()` are exercised any time a wallet user (or RPC caller) parses, summarizes, or accepts an offer — i.e., paths reachable purely by an offer counterparty crafting a malicious offer file, with no signature or on-chain acceptance required to trigger the crash, since matching happens before/independently of full puzzle-hash validation against the real coin.

Constructing an arbitrarily deep chain of recognizable layers is straightforward: e.g. CAT layers can be nested by using a previously-constructed CAT puzzle as the inner puzzle of another CAT puzzle, exactly as chia's own tests demonstrate is a valid, matchable CLVM structure: [7](#0-6) 

Python's default recursion limit (~1000) is far smaller than the number of nesting layers that can be cheaply encoded in a CLVM puzzle reveal, so an attacker-controlled puzzle with a few thousand nested layers reliably exhausts the interpreter stack.

Notably, this codebase is aware of exactly this class of hazard elsewhere and deliberately avoids it: `sha256_treehash()` is implemented iteratively "so we don't have to worry about blowing out the python stack": [8](#0-7) 

but the outer-puzzle driver dispatch chain in `chia/wallet/outer_puzzles.py` and its constituent drivers were not given the same non-recursive treatment.

### Impact Explanation
An unprivileged offer counterparty (or anyone who can get a victim to load/parse/accept an offer file, e.g. via `chia wallet take_offer`, `get_offer_summary` RPC, or DataLayer/NFT marketplace tooling built on `Offer`) can crash the victim's wallet process with a crafted offer, halting normal transaction processing for that wallet instance until restarted. This matches the "spend-triggered transaction-processing halt" impact class called out in scope, analogous to the BIRD CVE's stack-consumption daemon crash from recursive BGP mask-expression parsing.

### Likelihood Explanation
High feasibility: no cryptographic material, valid signature, or actual on-chain spend is required to trigger the crash — only a syntactically valid, deeply nested puzzle reveal embedded in an offer file that a victim wallet parses via `Offer.from_bech32`/`from_spend_bundle`. Building thousands of nested CAT/singleton/ownership layers is mechanical and requires no special resources.

### Recommendation
Add an explicit maximum recursion/nesting depth to the outer-puzzle driver dispatch chain (`match_puzzle`, `get_inner_puzzle`, `construct_puzzle`, `solve_puzzle` in `chia/wallet/outer_puzzles.py` and each driver's `match`/`get_inner_puzzle`/`construct`/`solve`), or convert the traversal to an iterative (stack-based) algorithm similar to `sha256_treehash()`. At minimum, catch `RecursionError` at the boundary where untrusted offer data is first parsed (`Offer.from_bech32`, `Offer.from_spend_bundle`, `_get_offered_coins`) and convert it into a graceful "invalid/unsupported offer" error rather than allowing it to propagate and terminate the wallet process.

### Proof of Concept
1. Build a CAT puzzle `p0` (or singleton/ownership/CR layer) as an arbitrary innermost puzzle.
2. Repeatedly wrap it N times (N ≈ 2000–5000) using the same layer's `construct_cat_puzzle`/`puzzle_for_singleton`/etc., using the previous layer's puzzle as the inner puzzle each time, exactly as done for `double_cat_puzzle` in [9](#0-8) , but iterated N times instead of twice.
3. Embed the resulting deeply nested puzzle as the `puzzle_reveal` of a coin spend inside a `WalletSpendBundle`, and wrap it as an `Offer` (`Offer.from_spend_bundle`) or serialize to a `.offer` file.
4. Have the victim call `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` (as done in `Offer.from_spend_bundle`/`_get_offered_coins`) by loading/summarizing/accepting the offer — the recursive `match`/`_match` calls exceed Python's recursion limit and raise `RecursionError`, crashing or hanging the wallet's processing of that request.

def test_cat_outer_puzzle() -> None:

    tail = bytes32.zeros

    double_cat_puzzle: Program = construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)
