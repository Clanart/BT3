### Title
Silent remote URL rewrite from unvalidated GitHub API `clone_url` allows push/fetch hijack - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` mirrors the reported bug-class: a value received from an external/untrusted source (there, `msg.value`; here, the GitHub API's `clone_url` field) is consumed and silently applied without validating that it matches the invariant the surrounding logic assumes (there, the payment type matching `_type`; here, the URL's host/identity matching the account/repository the user actually trusts). No revert/abort path exists when the assumption is violated — the operation just silently proceeds with the unexpected value.

### Finding Description
`updateRemoteUrl` rewrites the user's local git remote to `apiRepo.clone_url` whenever the previously-tracked GitHub clone URL differs from the current remote and the "protocol" of the new URL matches the current remote's protocol: [1](#0-0) 

The only guard is `protocolsMatch`, which checks that `URL.parse(remoteUrl).protocol === URL.parse(updatedRemoteUrl).protocol` — it does **not** check that the hostname is unchanged: [2](#0-1) 

`urlMatchesRemote`, used for the `remoteUrlUnchanged`/`urlsMatch` checks, only compares the *old* cached `cloneURL` against the *current* remote, and the *new* `clone_url` against the current remote to decide whether an update is warranted — it never validates the new `clone_url` against the trusted endpoint hostname (e.g. `github.com` or the user's GHE hostname): [3](#0-2) 

As a result, if the `apiRepo.clone_url` value that reaches this function ever points to a different host than the one the repository is legitimately associated with (e.g., a malicious/compromised GitHub Enterprise Server, a MITM/proxy on the API path, or a repo owner who can otherwise influence what clone URL is reported for their repo), the function will happily rewrite the user's `origin` remote to that attacker-controlled host as long as the URL scheme (`https`) is unchanged. The test suite confirms the code path performs this rewrite unconditionally on hostname/owner/name changes as long as protocol matches: [4](#0-3) 

This is the direct analog of the reported issue: the code accepts an externally-supplied value (`clone_url`) that could be of an "unexpected type" (a different host than intended) and, instead of rejecting/aborting the action, silently applies it — corrupting the value (`git remote` URL) that determines where the user's future `git push`/`git fetch` traffic and credentials go.

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes" and "credential/token exfiltration" in the specified impact scope: once `origin`'s URL is silently repointed to an attacker-controlled host, subsequent pushes send the user's commits (and, via the git credential helper, potentially their GitHub credentials/token when prompted for the "new" host) to the attacker's server instead of the real GitHub/GHE endpoint, without any user-visible warning dialog.

### Likelihood Explanation
The likelihood of the *provider side* (a malicious clone_url reaching this function) could not be fully confirmed from local code alone — I was not able to trace, within the remaining tool budget, the exact call site in `app-store.ts` that supplies `apiRepo` to `updateRemoteUrl`, nor whether Desktop cross-checks that `clone_url`'s hostname matches the account's API `endpoint` before this point. Because of this remaining uncertainty about the full attacker-controlled data path, I cannot assert this is a fully proven, exploitable vulnerability with high confidence — only that the `updateRemoteUrl`/`urlMatchesRemote` logic itself contains no hostname-identity check and is the closest structural analog to the reported bug class in this codebase.

### Recommendation
In `updateRemoteUrl`, before rewriting the remote, additionally validate that the new `clone_url`'s hostname equals the hostname of the account's trusted API `endpoint` (or of the existing remote), not merely that the URL scheme matches. If the hostname differs, refuse the silent update and instead surface a prompt asking the user to confirm the remote change.

### Proof of Concept
Given the confirmed unit test behavior:
1. User has `origin` = `https://github.com/my-user/my-repo` and a cached `GitHubRepository.cloneURL` of the same value.
2. The GitHub API response object for that repository (obtained via a compromised/malicious GHE instance or a MITM proxy on the API request, both explicitly in-scope attacker positions per the task's Valid Impact list) reports `clone_url: "https://attacker-controlled-host/my-user/my-repo"`.
3. `updateRemoteUrl` sees `protocolsMatch = true` (both `https`), `remoteUrlUnchanged = true` (old cached cloneURL still matches current remote), and `urlsMatch = false` (new host differs) — exactly mirroring the test at [4](#0-3) , except with a foreign host substituted for `my-updated-repo`.
4. The function calls `gitStore.setRemoteURL('origin', 'https://attacker-controlled-host/my-user/my-repo')` with no user confirmation, silently redirecting all future push/fetch traffic.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
