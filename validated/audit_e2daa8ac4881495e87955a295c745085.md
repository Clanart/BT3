### Title
Windows trailing-dot/space normalization bypasses `sanitizeCloneName`'s `..` traversal guard, allowing directory-traversal clone destinations - ([File: app/src/lib/remote-parsing.ts])

### Summary
`sanitizeCloneName` in `app/src/lib/remote-parsing.ts` is meant to reduce an attacker-controlled repository name (parsed from a URL) to a single, safe path component and explicitly reject any component that resolves to `..`, so that it can never be used to escape the user's chosen base clone directory. The check only rejects the *exact* string `'..'`, but on Windows, the underlying filesystem/Win32 APIs silently strip trailing dots and spaces from path components before creating them. This means a crafted repository name whose sanitized component is something Node considers different from `'..'` (e.g. `'.. '`, `'..  '`, `'...'` variants that don't exactly equal `'..'`) can still be turned into the literal parent-directory reference `..` once passed to `mkdir`/git on Windows, bypassing both `sanitizeCloneName`'s guard and the sibling guard `isClonePathSensitive` in `app/src/lib/git/clone.ts`, neither of which model Win32 trailing-character trimming.

### Finding Description
`sanitizeCloneName` (app/src/lib/remote-parsing.ts:88-116) extracts the last non-empty `/`, `\`, or `:`-separated component from an attacker-supplied repository name, strips a trailing `.git`, and then only rejects the result if it is exactly `'..'`, exactly `'.'`, or empty: [1](#0-0) 

This comparison is a strict, byte-for-byte string equality check, not a filesystem-normalization-aware check. Windows' CreateDirectory/CreateFile APIs (and thus Node's `fs`/`path` calls that ultimately reach them) drop trailing spaces and trailing dots from individual path components before resolving them on disk. Consequently, a component such as `".. "` (two dots + trailing space) or `"..."` variants engineered to reduce to `..` after OS trimming will:
1. Fail to match `lastComponent === '..'` in `sanitizeCloneName`, so it is returned as a seemingly "safe" component.
2. Pass through `Path.resolve`/`Path.join` in JavaScript (Node's `path` module does **not** replicate Win32's trailing-dot/space trimming), so `isClonePathSensitive` in `app/src/lib/git/clone.ts` also sees an apparently benign resolved path and does not flag it: [2](#0-1) 
3. When git/Windows actually creates the destination directory, the OS trims the trailing characters, and the effective directory used is the parent (`..`) of the intended base clone folder — i.e., the actual clone destination silently escapes the directory the user chose in the Clone dialog.

This is structurally the same class of bug as the reported `pow_u32` issue: a security-relevant algorithm has a narrow validation rule (checking initial/first-bit case, or checking exact `'..'` string) that is provably correct for the "obvious" representation of the dangerous input but silently fails for an equivalent input from a different representation of the same dangerous value (an even exponent that isn't handled by the loop's base case; a `..`-equivalent string that isn't handled by the exact-match check).

### Impact Explanation
If exploitable, this allows an attacker-controlled remote/repository name (from a link, deep link, or crafted `owner/name` GitHub API response) to make GitHub Desktop clone into a directory outside the user-selected base folder on Windows, e.g. the immediate parent directory of `Documents\GitHub`. Combined with the `--recursive` clone flag and `git clone`'s own working-tree writing, this could let a remote server plant files at an unintended, higher-privilege-adjacent location on disk (write outside the intended repo/base directory), which is explicitly in-scope impact for this exercise (file write outside the repo).

### Likelihood Explanation
This requires no local access, admin rights, or pre-existing malware — only that the victim clones a URL/repository whose owner or name segment is attacker-chosen (e.g., pasted link, "Open in Desktop" deep link, or a malicious GitHub API-reported repo/owner name reaching `parseRepositoryIdentifier`/`sanitizeCloneName`). The guard exists specifically to stop this class of attack (per its own doc comment referencing "path traversal attacks where a crafted URL tricks the UI into deriving a clone path outside the intended base directory"), confirming the code authors treat this as a real, previously-considered threat model; the trailing-dot/space Windows normalization is a well-documented OS quirk that this particular string-equality guard does not account for. I was not able to execute the actual Win32 `CreateDirectory` trimming behavior in this environment to empirically confirm the exact winning payload characters (this needs a Windows host / Node `fs.mkdir` test), so the precise bypass string should be verified in a live Devin session before treating this as fully confirmed.

### Recommendation
Do not rely solely on exact string equality against `'..'`/`'.'` in `sanitizeCloneName`. Additionally: strip trailing dots/spaces (matching Win32 semantics) before performing the traversal check, or better, validate the *final resolved path* against the intended base directory using an OS-normalized comparison (e.g., actually create the directory or use `fs.realpath`-style resolution) rather than trusting `Path.resolve`, which does not model Win32 trimming. The same hardening should be applied to `isClonePathSensitive` in `app/src/lib/git/clone.ts`.

### Proof of Concept
Conceptual (not verified on a live Windows host due to sandbox limitations):
1. Attacker crafts a URL/deep-link such as `https://evil.example.com/owner/x..\..\..\..\.. .git` (or an equivalent encoding) so that after `parseRepositoryIdentifier` → `sanitizeCloneName`, the last component reduces to a string like `".. "` (trailing space) that is not `'==' '..'` textually.
2. `sanitizeCloneName` returns `".. "` as a "safe" component instead of `null`.
3. `Path.join(baseDir, ".. ")` in `clone.ts`/`clone-repository.tsx` and `isClonePathSensitive` see a resolved path still nominally under `baseDir` (Node does not trim the trailing space during `path.resolve`).
4. When Desktop invokes `git clone ... -- <url> <path>` on Windows, the OS-level path handling trims the trailing space from the final path component, causing the effective clone target directory to be the parent of `baseDir` instead of a subdirectory of it. [3](#0-2) [4](#0-3)

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
