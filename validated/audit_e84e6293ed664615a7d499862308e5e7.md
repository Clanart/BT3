### Title
Uninitialized heap buffer passed to user-supplied `CopyingInputStream::Read()` in `CopyingInputStreamAdaptor::Next()` - (File: `src/google/protobuf/io/zero_copy_stream_impl_lite.cc`)

### Summary
`CopyingInputStreamAdaptor` (used by `IstreamInputStream`, `FileInputStream`, and any custom `CopyingInputStream` adapter, and reachable from `CodedInputStream`/`Message::ParseFrom(std::istream&)` and similar public parse entry points) allocates its internal working buffer with `new uint8_t[buffer_size_]` [1](#0-0)  without zero-initializing it, and then passes that raw pointer to `copying_stream_->Read(buffer_.get(), buffer_size_)` [2](#0-1) , trusting the return value (`buffer_used_`) to indicate how many bytes were actually written. This mirrors the `acc_reader` advisory's failed invariant exactly: an uninitialized buffer is exposed to a `Read`-style implementation, and the code trusts the count reported by that implementation rather than the buffer's actual initialized state.

### Finding Description
`CopyingInputStreamAdaptor::Next()` is the classic adaptor that turns any object implementing the simple `CopyingInputStream::Read(void* buffer, int size)` interface into a `ZeroCopyInputStream` [3](#0-2) . On every call to `Next()`, it lazily allocates the backing buffer via `AllocateBufferIfNeeded()`:
```
void CopyingInputStreamAdaptor::AllocateBufferIfNeeded() {
  if (buffer_ == nullptr) {
    buffer_.reset(new uint8_t[buffer_size_]);
  }
}
```
`new uint8_t[buffer_size_]` is a non-value-initializing array-new for a scalar/POD type, so the bytes are indeterminate until written. `Next()` then does:
```
buffer_used_ = copying_stream_->Read(buffer_.get(), buffer_size_);
...
*size = buffer_used_;
*data = buffer_.get();
```
The contract documented on `CopyingInputStream::Read` is "Reads up to `size` bytes into the given buffer. Returns the number of bytes read." [4](#0-3) . This directly parallels the `acc_reader` bug class: the buffer is uninitialized, and it is up to the (potentially buggy) `Read` implementation to correctly report how many bytes it actually wrote. If a `Read` implementation over- or under-reports `buffer_used_` relative to what it actually wrote (a bug in the implementation, exactly as `acc_reader`'s issue described), the adaptor will treat `buffer_used_` bytes of the buffer as valid protobuf wire data — some fraction of which is uninitialized heap memory carried into `*data`/`*size`, which then flows into `CodedInputStream`/`EpsCopyInputStream` parsing and potentially into parsed field values, strings, or bytes that end up observable in the resulting message (memory disclosure), or into arithmetic assuming trusted lengths.

Where this differs from the advisory (and needs disclosure): the "attacker-controlled" component here is not the wire bytes but the **`CopyingInputStream::Read()` implementation itself** — i.e., trusted application code that implements the adaptor interface (e.g., a custom stream wrapper around a socket or file). Protobuf's C++ API contract explicitly places the burden on the `Read()` implementation to be correct; this is analogous to `Read` implementations in Rust's `std::io::Read` trait. Protobuf itself does not sanitize or zero the buffer before exposing it, exactly matching the described failed invariant in the advisory ("uninitialized buffer passed to a user-provided Read implementation").

### Impact Explanation
If a `CopyingInputStream::Read()` implementation has an off-by-one/miscounting bug (returns a count larger than the bytes it actually wrote), `CopyingInputStreamAdaptor` will hand up to `buffer_size_` bytes of **uninitialized heap memory** to the parser as if they were legitimate wire bytes. Because protobuf's parser can copy raw bytes fields, strings, and unknown fields verbatim into the resulting `Message` (which the calling application may then serialize back out, log, or return to a peer), this can result in **disclosure of uninitialized heap memory contents** to an external party — a real (if lower-severity than RCE) confidentiality impact, consistent with the "Undefined Behavior / memory exposure" characterization in the original advisory. There is no direct RCE vector from this alone.

### Likelihood Explanation
This is a **library API contract issue rather than one exploitable via a public binary/ProtoJSON parse endpoint with attacker-controlled bytes**: the vulnerable input is not the serialized protobuf bytes, but a bug in a *trusted, application-supplied* `CopyingInputStream::Read()` implementation. Per the stated attacker model ("ordinary client sending bounded binary Protobuf or ProtoJSON through a supported public parse API… schemas, generated code, registries, application code… are trusted and valid"), the `Read()` implementation is trusted application code, not attacker-controlled. Therefore this does not transfer as a High-severity, remotely-triggerable analog under the stated threat model — it only manifests if the *application's own* stream-adaptor implementation is buggy, which is an application-code correctness issue, not a Protobuf parser vulnerability reachable by an ordinary client sending bytes.

### Recommendation
Even though likelihood under the stated threat model is low, defense-in-depth would suggest zero-initializing (or using `absl::make_unique<uint8_t[]>` value-initialized, or `std::vector<uint8_t>(buffer_size_, 0)`) the buffer in `AllocateBufferIfNeeded()`, and/or clamping `buffer_used_` returned by `Read()` to `[0, buffer_size_]` with a hard check (similar to the `IllegalStateException` guard Java's `CodedInputStream.StreamDecoder.tryRefillBuffer()` already has for `bytesRead > buffer.length`) [5](#0-4) , which C++'s `CopyingInputStreamAdaptor::Next()` currently lacks.

### Proof of Concept
Not independently reproduced/run in this session (no execution environment available); this is a static-analysis-based finding. Conceptually:
1. Implement a `CopyingInputStream` subclass whose `Read(void* buffer, int size)` writes fewer bytes than `size` into `buffer` but returns `size` (simulating a buggy caller-supplied `Read`, analogous to the `acc_reader` bug).
2. Wrap it in `CopyingInputStreamAdaptor` and feed it to a `CodedInputStream`/`Message::ParseFromZeroCopyStream`.
3. Observe (e.g., under MSan) that uninitialized bytes from `new uint8_t[buffer_size_]` [1](#0-0)  are read as parsed field data.

Given that the triggering condition requires a bug in *trusted* application code (the `Read()` implementation) rather than attacker-controlled wire bytes reaching a public parse API, this finding should be treated as **Low/Informational** under the stated scope, not High — I am flagging it as the closest structural analog found, but it does not meet the "ordinary client sending bounded bytes through a public parse API" bar required for High severity.
