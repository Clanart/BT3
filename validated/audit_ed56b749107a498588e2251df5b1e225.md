### Title
Unsanitized program log messages displayed verbatim in CLI transaction output enable terminal/ANSI control-character injection - (File: `cli-output/src/display.rs`)

### Summary
`solana` CLI commands that print transaction results (e.g. transaction confirmation, block/history inspection) call `write_log_messages`, which writes each `log_message` string straight to the user's terminal with no filtering of ANSI/terminal control sequences. Because log messages originate from an on-chain program's `sol_log` calls (attacker-controlled content, only required to be valid UTF-8), a malicious program invoked by a transaction the user is inspecting/confirming can inject terminal escape sequences to spoof or hide output, mirroring the Snap `text()` Markdown/CtrlChar injection class described in the external report — the CLI is the "less trusted" untrusted-input renderer, and the operator is the human deciding based on displayed information.

### Finding Description
`write_log_messages` in `cli-output/src/display.rs` iterates over `log_messages` and writes each one directly with `writeln!(w, "{prefix}  {log_message}")`, with no escaping or stripping of control characters: [1](#0-0) 

This is invoked from `println_transaction`/`writeln_transaction`, which are used across the CLI/ledger-tool to display transaction results to a human operator (e.g. `CliTransactionConfirmation`'s `VerboseDisplay`, `CliBlock`/`CliBlockWithEntries` display, and the `solana logs` streaming command): [2](#0-1) [3](#0-2) [4](#0-3) 

The log messages themselves are produced by the on-chain program's `sol_log` syscall, which stores arbitrary program-supplied bytes as long as they parse as valid UTF-8 — there is no filter for non-printable or ANSI escape byte sequences: [5](#0-4) [6](#0-5) 

So the full path is: untrusted/malicious program → `sol_log(arbitrary UTF-8 string)` → `LogCollector` → RPC `logMessages` → CLI display code (`write_log_messages`, `println_transaction`, `process_logs`) → raw terminal output, with no sanitization at any stage. This is directly analogous to the Snap report's core defect: untrusted, dapp/program-controlled text being fed into a rendering surface that interprets control sequences, letting the untrusted party manipulate what the trusted party (the snap/CLI) shows to the human who must decide whether to trust or act on it.

### Impact Explanation
A malicious program included in a transaction (e.g. via CPI from an otherwise benign-looking instruction, or a scam token/dApp instructing the user to run `solana confirm`, `solana transaction-history --show-transactions`, or use `solana logs`) can emit log lines containing ANSI/terminal escape sequences to:
- Overwrite or hide prior terminal lines (e.g. clear-line/cursor-movement codes) to make a failed/malicious transaction appear to show a benign log trail, or to hide genuinely suspicious log output from a security-conscious operator inspecting logs before deciding to retry, approve a follow-up action, or trust an address.
- Spoof status text (e.g. fake "Status: Ok" or fake account/log content) that a human operator relies on when deciding to proceed with subsequent trust decisions (e.g., re-signing, sending funds, approving a program).

This does not directly move funds by itself, but it undermines the integrity of the CLI's transaction-confirmation UI in the exact way the report flags: false information displayed to the user who decides fund-affecting actions based on it.

### Likelihood Explanation
Likelihood is low-to-moderate. It requires a user to run a CLI command that renders logs/transaction output from a transaction containing a call into a malicious/untrusted program (a realistic scenario for anyone interacting with unaudited on-chain programs, or streaming logs on a public RPC with `solana logs`, which by design surfaces logs from arbitrary transactions across the cluster). No privileged access or protocol violation is needed — any program can call `sol_log` with attacker-chosen bytes, and CLI users regularly review this text to make trust decisions.

### Recommendation
Sanitize log messages (and other program-controlled strings such as memos) before writing to the terminal in `write_log_messages`/`println_transaction`/`process_logs` — strip or escape non-printable/control characters (e.g., using something like `strip-ansi-escapes` or filtering to printable ASCII/Unicode graphic characters) prior to `writeln!`. Apply the same treatment anywhere raw log/memo/return-data strings from transaction results are printed to a terminal.

### Proof of Concept
1. Deploy or use a BPF program that calls `sol_log("\x1b[2K\x1b[1AProgram log: All good, funds sent safely")` (crafted ANSI escape + fake status text) as part of its execution.
2. Have a victim run `solana confirm <signature> --verbose` or `solana logs` while this transaction executes.
3. `write_log_messages` in `cli-output/src/display.rs:655-669` writes the raw string to the terminal via `println_transaction`/`writeln_transaction`; the embedded escape sequence executes in the victim's terminal emulator, rewriting/erasing preceding output and displaying attacker-chosen text, misleading the operator about the actual transaction/log content.

fn write_log_messages<W: io::Write>(
    w: &mut W,
    log_messages: Option<&Vec<String>>,
    prefix: &str,
) -> io::Result<()> {
    if let Some(log_messages) = log_messages
        && !log_messages.is_empty()
    {
        writeln!(w, "{prefix}Log Messages:",)?;
        for log_message in log_messages {
            writeln!(w, "{prefix}  {log_message}")?;
        }
    }
    Ok(())
}
