### Title
Ambiguous unescaped delimiter in `createEqualityHash` causes `GitHubRepository`/`Repository` identity collisions from attacker-controlled API data - (File: app/src/models/equality-hash.ts)

### Summary
`createEqualityHash()` builds an "equality hash" by naively joining heterogeneous fields with a bare `'+'` separator and no escaping: [1](#0-0) 

This is structurally the same defect class as the `OrderNFT` bug: a value meant to be a *unique* encoding of a tuple of fields is actually many-to-one, because the encoding scheme allows the field boundary (the `'+'` separator) to be reproduced by the field contents themselves. `GitHubRepository.hash` and `Repository.hash` are both built this way and are documented as guaranteeing that "objects with the same hash are guaranteed to be structurally equal": [2](#0-1) [3](#0-2) 

That guarantee is false whenever any of the joined string fields can contain `'+'`.

### Finding Description
`GitHubRepository.hash` is computed from `name`, `owner.login`, `dbID`, `isPrivate`, `htmlURL`, `cloneURL`, `issuesEnabled`, `isArchived`, `permissions`, and `parent?.hash`, all concatenated with `'+'`: [4](#0-3) 

`name`, `htmlURL`, and `cloneURL` are free-form strings that originate directly from a GitHub/GitHub-Enterprise API response — an object type the threat model explicitly allows the attacker to control (a malicious or compromised GHE server, or a fork/parent repository the attacker owns, feeding data through `API.fetchRepository`/repo refresh code paths that construct `GitHubRepository` instances). Because the separator character `'+'` is not escaped or length-prefixed, two semantically different tuples can serialize to the *identical* hash string, e.g.:

- `name = "foo+bar"`, `owner.login = "baz"`
- `name = "foo"`, `owner.login = "bar+baz"`

both yield `...foo+bar+baz...` for that segment of the joined string. Since `htmlURL`/`cloneURL` are likewise attacker-supplied strings, the remaining fields can be crafted to make the *entire* joined string byte-identical between two objects that differ in security-relevant fields (e.g. `permissions`, `cloneURL`, or which repo is the `parent`).

This hash is consumed as a cheap "did anything change" check in `RepositoriesStore.setGitHubRepository`, which skips writing to the database, and skips notifying store consumers, whenever the freshly-fetched `ghRepo.hash` equals the previously stored `repo.gitHubRepository.hash`: [5](#0-4) 

It is also embedded into `Repository.hash`: [6](#0-5) 

and `Repository.hash`/`GitHubRepository.hash` values are used as cache keys and change-detection keys throughout the app, e.g. `GitStoreCache` keys its per-repository `GitStore` (branches, HEAD, history, etc.) by `repository.hash`: [7](#0-6) 

and `RepositoryStateCache.transferState`/repository-selection logic compares `.hash` to decide whether two `Repository` objects represent "the same" identity or a changed one: [8](#0-7) [9](#0-8) 

Because these hashes are treated as unique, collision-free identifiers ("guaranteed to be structurally equal"), an attacker who controls the fields feeding into the hash (via a malicious GitHub Enterprise endpoint, a crafted fork/parent repository, or any API repository object ingested by Desktop) can make a `GitHubRepository` that has actually changed (different `cloneURL`, different `permissions`, different `name`/owner pairing) hash identically to a previously trusted one. This defeats the change-detection logic and lets stale/incorrect cached data (cloneURL, permission level, or shared `GitStore`/working-directory state) silently persist and be reused for what is, from the API's point of view, a different repository object.

### Impact Explanation
This maps to the "silent corruption of what the user commits or pushes" impact category. Because `RepositoriesStore.setGitHubRepository` uses hash equality to decide whether to persist a GitHub-repository record update, a crafted collision can suppress a legitimate update to `cloneURL` or `permissions` while the app continues to believe the old (now-forged) values are current. Separately, because `GitStoreCache` and `RepositoryStateCache` key cached git state (branches, staged changes, commit message, ahead/behind info) by the same non-injective hash, a collision between two different `Repository`/`GitHubRepository` identities can cause Desktop to reuse or transfer cached working-directory/commit state from one repository context to another that only appears identical due to the hash collision, rather than genuinely being the same repository. This is exactly the class of "ambiguous decode → same identity, different underlying object" bug described in the report, just applied to Desktop's model-equality hashing instead of an NFT `tokenId`.

### Likelihood Explanation
Exploitation requires the attacker to control the content of `name`, `owner.login`, `htmlURL`, or `cloneURL` fields returned from a GitHub API-compatible endpoint the user has added as an account (particularly plausible for GitHub Enterprise, where the "GitHub API object" is entirely attacker-served), or a repository/fork the attacker owns whose metadata Desktop ingests when resolving forks/parents. Crafting an exact byte-for-byte collision requires care (all subsequent fields in the join must also match), but is fully mechanical once the delimiter-collision technique is applied, and no signature, escaping, or type-tagging currently prevents it — `createEqualityHash` performs no validation of its inputs (unlike `decodeId`'s missing bounds check in the original report).

### Recommendation
Do not build equality/identity hashes with an unescaped, ambiguous separator. Use a length-prefixed or escaped encoding (e.g. `JSON.stringify` of the tuple, or prefixing every field with its length like `field.length + ':' + field`), or use a proper structural-hash/serialization function so that no combination of field values can produce a colliding output for two different input tuples. This mirrors the report's fix recommendation of removing decoding ambiguity by validating/encoding unambiguously rather than relying on an assumption that never holds for attacker-controlled string content.

### Proof of Concept
```ts
import { createEqualityHash } from '../../src/models/equality-hash'

// Two structurally different tuples...
const hashA = createEqualityHash('foo+bar', 'baz', 1, false, 'https://a', 'https://a.git')
const hashB = createEqualityHash('foo', 'bar+baz', 1, false, 'https://a', 'https://a.git')

// ...produce the identical "equality hash" string:
console.assert(hashA === hashB, 'collision reproduced')
```

Applied to `GitHubRepository`, an attacker-controlled API server can serve, across two fetches of what Desktop treats as "the same" repository record, JSON payloads where `name`/`owner.login` (or `htmlURL`/`cloneURL`) differ but the concatenation is identical, causing `RepositoriesStore.setGitHubRepository` (`app/src/lib/stores/repositories-store.ts:569-572`) to treat the update as a no-op and skip persisting the new, differing values.

export class GitStoreCache {
  /** GitStores keyed by their hash. */
  private readonly gitStores = new Map<string, GitStore>()

  public constructor(
    private readonly shell: IAppShell,
    private readonly statsStore: IStatsStore,
    private readonly onGitStoreUpdated: (
      repository: Repository,
      gitStore: GitStore
    ) => void,
    private readonly onDidError: (error: Error) => void
  ) {}

  public remove(repository: Repository) {
    if (this.gitStores.has(repository.hash)) {
      this.gitStores.delete(repository.hash)
    }
  }

  public get(repository: Repository): GitStore {
    let gitStore = this.gitStores.get(repository.hash)
    if (gitStore === undefined) {
      gitStore = new GitStore(repository, this.shell, this.statsStore)
      gitStore.onDidUpdate(() => this.onGitStoreUpdated(repository, gitStore!))
      gitStore.onDidError(error => this.onDidError(error))

      this.gitStores.set(repository.hash, gitStore)
    }

    return gitStore
  }
