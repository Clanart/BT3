## Analog Found: Sandwich Attack on `SimplexPaymaster.swapAndDeposit`

The bug-class from the report — a public/permissioned action that executes an AMM swap protected only by a static, execution-time-independent slippage bound rather than by monitoring the pool's actual state before/after the trade — has a direct, provable analog in `SimplexPaymaster.sol`. [1](#0-0) 

### Title
Oracle-anchored, fixed-slippage AMM swap in `swapAndDeposit()` lets an attacker sandwich the trade and extract paymaster treasury value - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster.swapAndDeposit()` swaps accumulated ERC-20 fee tokens for the native asset through a Uniswap V2-style router, in order to refund the EntryPoint deposit that funds gas sponsorship. The minimum acceptable output (`amountOutMin`) is computed from two Chainlink oracle prices and a fixed `swapSlippageBps` tolerance (up to `MAX_SWAP_SLIPPAGE_BPS = 1_000`, i.e. 10%), not from the pool's actual reserves at call time. This is structurally identical to the reported AeraVaultV1 bug: a protocol-controlled contract executes a spot-price-agnostic trade against a public AMM, bounded only by a static tolerance band, so an attacker can manipulate the pool's spot price around the transaction and extract value at the protocol's expense. [2](#0-1) [3](#0-2) 

### Finding Description
`swapAndDeposit()` derives `expectedWei` purely from `nativeOracle` and the token's `tokenOracle` — both external, off-chain-fed Chainlink prices — and then applies a flat `swapSlippageBps` discount to get `amountOutMin`: [4](#0-3) 

This value is passed to `IUniswapV2Router02.swapExactTokensForETH`. Because Chainlink prices are independent of the Uniswap V2 pool's instantaneous reserves, `amountOutMin` bears no relation to what the pool would fairly return before an attacker perturbs it. Up to `swapSlippageBps` (governance-capped at `MAX_SWAP_SLIPPAGE_BPS = 1_000`, i.e. 10%), the swap will still succeed even if the pool's spot price has been pushed 10% against the paymaster. [5](#0-4) 

The code's own comment on `swapAndDeposit` acknowledges the general danger of calldata interference and mitigates *one* narrow variant of it (mid-bundle UserOp interleaving) by gating the call to `treasury`: [6](#0-5) 

However, the `treasury`-only gate does **not** stop an unrelated attacker from front-running/back-running the treasury's ordinary transaction on the public Uniswap V2 pool itself:
1. Attacker front-runs the treasury's `swapAndDeposit` call, swapping into the pool to push the token/WETH spot price down within the tolerated band.
2. The treasury's `swapExactTokensForETH` executes against the now-worse price; since `amountOutMin` is oracle-derived (not pool-derived), the trade still clears as long as the deviation stays within `swapSlippageBps`.
3. Attacker back-runs, reversing their initial trade and pocketing the difference — value that came directly out of the paymaster's own fee-token balance (funds meant to refund the EntryPoint / ultimately belong to the protocol/treasury).

This is precisely the invariant break identified in the source report: a static, oracle-based slippage bound substitutes for genuine spot-price protection, letting an attacker manipulate the AMM around the trusted party's transaction and extract value.

### Impact Explanation
This directly matches the required impact class of "stealing or loss of funds": ERC-20 fee-token balances held by `SimplexPaymaster` (revenue that should convert 1:1-minus-fair-spread into native gas funding the EntryPoint deposit) can be siphoned to an attacker via AMM manipulation, up to the full `swapSlippageBps` tolerance on every `swapAndDeposit` call. Because `swapSlippageBps` is governance-configurable up to 10%, and `amountIn` can be the entire token balance (`amountIn == 0` swaps the whole balance), a single call can leak up to ~10% of the swapped notional to the attacker, repeatable on every fee-recycling cycle.

### Likelihood Explanation
`swapAndDeposit` is not privileged beyond the `treasury` sender-check, but the vulnerable state — the Uniswap V2 pool — is fully public and unauthenticated by anyone. No malicious relayer, prover, operator, or governance actor is required: any unprivileged attacker capable of monitoring the mempool/block-builder for the treasury's transaction (a benign, expected, recurring operational call, not a "malicious peer" precondition) can execute the sandwich. Given `swapAndDeposit` is described as a routine fee-recycling operation ("keeps collected fees flowing to the paymaster's gas funding without a governance round-trip"), it is expected to be called regularly and predictably, making the target easy to anticipate.

### Recommendation
- Compute `amountOutMin` from the pool's *own* current reserves (or a TWAP) with a tight slippage bound, in addition to (or instead of) the oracle-derived bound, so execution price cannot drift far from the pool's pre-trade state.
- Alternatively/additionally, check that the pool's spot price is within a bounded deviation of the oracle price both before and after the swap (reject if `lastChangeBlock`-equivalent freshness indicates same-block manipulation), mirroring the report's recommended `lastChangeBlock` mitigation.
- Consider routing through a private/MEV-protected channel (e.g., Flashbots-style bundle) for `swapAndDeposit` submissions, as the original report also suggests for AeraVaultV1.

### Proof of Concept
1. Treasury holds a large `token` balance in `SimplexPaymaster` and calls `swapAndDeposit(token, 0)` (full balance) with `swapSlippageBps` set to its governance-permitted maximum (10%).
2. Attacker observes the pending transaction in the public mempool and front-runs with a large swap of `token` into the same Uniswap V2 pool, moving the WETH/token spot price down by close to 10%.
3. The treasury's `swapExactTokensForETH(amountIn, amountOutMin, ...)` executes: `amountOutMin` was computed solely from Chainlink prices minus 10%, so the degraded pool price still satisfies the router's minimum-output check and the trade succeeds at the worse rate.
4. Attacker back-runs, reversing their initial trade and extracting the spread — i.e., the difference between the fair (oracle-implied) output and the actual (manipulated-pool) output that the paymaster contract just received — as profit, at the paymaster's expense. [7](#0-6)

    /// @dev The minimum output is derived onchain from the Chainlink oracles
    ///      (markup-free price minus `swapSlippageBps`), so the caller cannot
    ///      influence the execution price. Still treasury-gated: were this
    ///      permissionless, a UserOp's calldata could invoke it mid-bundle and
    ///      swap away other ops' pending prefunds, breaking their postOp
    ///      refunds. The treasury sends ordinary transactions, which can never
    ///      execute mid-bundle.
    function swapAndDeposit(address token, uint256 amountIn) external {
        if (msg.sender != treasury) revert UnauthorizedCall();
        address router = IDispatcher(host()).uniswapV2Router();
        if (router == address(0)) revert InvalidRouter(router);
        TokenConfig memory cfg = tokenConfigs[token];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(token);

        uint256 balance = IERC20(token).balanceOf(address(this));
        if (amountIn == 0 || amountIn > balance) amountIn = balance;

        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);
        uint256 expectedWei = (amountIn * tokenUsd * 1e18) / (nativeUsd * (10 ** cfg.tokenDecimals));
        uint256 amountOutMin = (expectedWei * (10_000 - swapSlippageBps)) / 10_000;

        address[] memory path = new address[](2);
        path[0] = token;
        path[1] = IUniswapV2Router02(router).WETH();

        IERC20(token).forceApprove(router, amountIn);
        uint256[] memory amounts = IUniswapV2Router02(router).swapExactTokensForETH(
            amountIn,
            amountOutMin,
            path,
            address(this),
            block.timestamp
        );

        uint256 deposited = address(this).balance;
        entryPoint().depositTo{value: deposited}(address(this));
        emit FeesRecycled(token, amountIn, amounts[1], deposited);
    }
