Based on the investigation, I found a genuine, verifiable analog: the upb JSON encoder (`jsonenc_put_escaped_char`, shared verbatim across `upb/json/encode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, and `php/ext/google/protobuf/php-upb.c`) omits the HTML/JS-context escaping of `<` and `>` that the C++ (`src/google/protobuf/json/internal/writer.cc`), Java (`JsonFormat.java`), and C# (`JsonFormatter.cs`) JSON printers deliberately implement.

### Title
Inconsistent HTML/JS-unsafe character escaping in upb-based JSON serialization — (File: `upb/json/encode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, `php/ext/google/protobuf/php-upb.c`)

### Summary
Protobuf's canonical C++ JSON writer, Java `JsonFormat`, and C# `JsonFormatter` all deliberately escape `<`, `>` (Java additionally escapes `&`, `=`, `'`) inside JSON string values specifically to prevent "security bugs in javascript" — i.e., to keep attacker-controlled protobuf string field content from breaking out of an HTML/`<script>` context when a consuming application naively embeds the produced JSON into an HTML page. The shared upb JSON encoder used by the Ruby and PHP native extensions (`jsonenc_put_escaped_char`) and by upb generally does not perform this extra escaping, only escaping the JSON-spec-mandated characters (`"`, `\`, control chars). This reproduces the OneUptime bug class: an attacker-controlled value that flows through a "safe" serialization path in most implementations, but is missing the same hardening in another implementation, enabling stored/reflected script injection wherever a consuming application embeds the serialized output in an HTML/JS context.

### Finding Description
- C++: `MustEscape()` in `src/google/protobuf/json/internal/writer.cc:239-240` explicitly escapes `<` and `>` "to prevent security bugs in JavaScript" [1](#0-0) .
- Java: `JsonFormat.java` explicitly escapes `<>&='` for the same stated reason, with a regression test (`testHtmlEscape`, tagged `b/73832901`) asserting `</script>` is escaped to `\u003c/script\u003e` [2](#0-1) [3](#0-2) .
- C#: `JsonFormatter.cs` hardcodes `\u003c`/`\u003e` replacements for `<`/`>` with the comment "Escaping of < and > are required for HTML security" [4](#0-3) .
- upb (shared by Ruby and PHP native extensions): `jsonenc_put_escaped_char` only special-cases `\n \r \t " \f \b \\` and generically `\u`-escapes control chars < 0x20 — it has no case for `<` or `>` at all [5](#0-4) , and the identical function exists verbatim in `upb/json/encode.c` [6](#0-5) . The same escaped function body is compiled into `php/ext/google/protobuf/php-upb.c`.
- PHP's pure-PHP fallback encoder (`GPBJsonWire.php`) independently confirms the same gap: `isJsonEscaped()`/`jsonNiceEscape()` only treat control chars, `"`, and `\` as requiring escaping — no `<`/`>` handling [7](#0-6) .

The invariant that transfers from the OneUptime report is: *attacker-controlled string content must be neutralized before it reaches a context where a browser will interpret it as markup/script*. In OneUptime, this failed because `securityLevel: "loose"` plus raw `innerHTML` insertion allowed a `click` directive to execute JS. In protobuf, the C++/Java/C# JSON printers implement exactly this neutralization defensively (escaping `<`/`>` even though it's not required by the JSON spec) precisely because downstream consumers sometimes embed protobuf-JSON output directly into HTML/`<script>` blocks. The upb-based encoder (Ruby, PHP, and any other language binding built on upb, e.g. via the C extension) and PHP's pure fallback both omit this defense, silently emitting raw `<`/`>` bytes.

### Impact Explanation
Any application using Ruby's or PHP's protobuf `to_json`/`serializeToJsonString` (which routes through upb, or PHP's pure fallback `GPBJsonWire`) on a message containing an attacker-supplied string field (e.g., a user-controlled name, comment, or description field) and then embeds that JSON text into an HTML page or inline `<script>` block (a documented and Google-anticipated consumption pattern, per the explicit comments in the C++/Java/C# code) is exposed to stored/reflected XSS. A string value such as `</script><script>alert(document.cookie)</script>` would pass through Ruby/PHP JSON serialization unescaped for `<`/`>`, whereas the equivalent Java/C++/C# output would be safely escaped. This is a parity/hardening gap between officially supported protobuf runtimes rather than a hypothetical.

### Likelihood Explanation
High likelihood of occurrence: Ruby and PHP protobuf users routinely call the public JSON serialization API on messages carrying arbitrary user-supplied string fields, and it is common practice (and explicitly anticipated by protobuf's own C++/Java/C# escaping code and comments) to embed such JSON directly into HTML templates or `<script>` tags for client-side hydration. No privileged access or unusual input is required — an ordinary client only needs to control a string field's contents through the normal, bounded, valid ProtoJSON/binary parse → serialize round trip.

### Recommendation
Bring `jsonenc_put_escaped_char` (in `upb/json/encode.c`, and consequently `ruby-upb.c`/`php-upb.c`) and PHP's `GPBJsonWire::isJsonEscaped`/`jsonNiceEscape` into parity with the C++ `MustEscape()` / Java `replacementChars` / C# `CommonRepresentations` tables by additionally escaping `<` and `>` (and ideally the same extended set: `&`, `=`, `'`, zero-width/invisible Unicode ranges) as `\uXXXX` sequences. Add a cross-language conformance test (mirroring Java's `testHtmlEscape`) asserting that `<`, `>` and `</script>` are escaped identically across all JSON-producing protobuf runtimes.

### Proof of Concept
1. Build a message with a string field set to `"</script><script>alert(1)</script>"`.
2. Serialize to JSON:
   - Java: `JsonFormat.printer().print(msg)` → produces `\u003c/script\u003e...` (safe, per `JsonFormatTest.testHtmlEscape`) [3](#0-2) .
   - Ruby (upb-backed) / PHP (upb extension or pure `GPBJsonWire`): the equivalent call emits the raw `<`/`>` bytes verbatim, because neither `jsonenc_put_escaped_char` [5](#0-4)  nor `GPBJsonWire::isJsonEscaped` [7](#0-6)  special-case `<`/`>`.
3. If the consuming application embeds this JSON string into an HTML page inside a `<script>var msg = {ruby_or_php_json};</script>` block, the embedded `</script>` closes the script tag early, allowing the trailing `<script>alert(1)</script>` to execute — reproducing the same "attacker string reaches an HTML/script-interpreting sink unescaped" root cause as the OneUptime Mermaid/`innerHTML` XSS, but rooted in a genuine cross-language inconsistency inside protobuf's own JSON serialization implementations.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
