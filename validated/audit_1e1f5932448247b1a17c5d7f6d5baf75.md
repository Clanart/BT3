### Title
Argument Injection via Unsanitized `remote.name` in Git Push Argv - (File: `app/src/lib/git/branch.ts`)

### Summary
`deleteRemoteBranch` and `push` both build the `git push` argv by splicing `remote.name` directly into the positional argument list without validating that it isn't itself an option-like string (e.g. starting with `-`/`--`). Since `IRemote.name` is populated from whatever a `.git/config` `[remote "…"]` subsection is named, an attacker who can supply repository content containing a crafted `.git` directory can make `remote.name` an arbitrary flag string, which git then parses as a command-line option instead of a remote identifier.

### Finding Description

and `push` constructs an equivalent argv: [2](#0-1) 

Neither call validates `remote.name` before it is spliced into the argv passed to `git()` (which spawns git directly via `execFile`-style argv, not a shell — so shell metacharacters are not the risk, but git's own option parser is).

`remote.name` originates from `getRemotes`, which parses the output of `git remote -v` with a permissive regex and uses whatever string git reports as the remote's name: [3](#0-2) 

`IRemote` itself has no validation on `name`: [4](#0-3) 

Git config subsection names (the `"…"` part of `[remote "…"]`) are largely free-form strings once quoted, so a `.git/config` can legally define a remote whose name is, e.g., `--receive-pack=/tmp/evil.sh`. If such a `.git` directory is opened by GitHub Desktop as a local repository (or embedded in a downloaded repo/submodule folder that the user adds), `git remote -v` will echo that literal string back as the remote name, `getRemotes()` will surface it unmodified, and any later `push`/`deleteRemoteBranch` call will place it as the second positional argv element — where git's own parser, not a shell, treats any leading-`-` token as an option regardless of position (unless preceded by a literal `--` separator, which is not used here).

**Correction to the submitted PoC idea:** the option that actually achieves code execution on `git push` is `--receive-pack=<path>` (or its alias `--exec=<path>`), not `--upload-pack`. `--upload-pack` is a `fetch`/`clone`/`ls-remote`-side option (it tells the *sending* side which program to run to serve objects) and is not a recognized `git-push` option; passing `--upload-pack=...` to `git push` would just produce an "unknown option" error, not code execution. The underlying injection primitive described in the question is real, but the specific flag named is wrong for the `push` sink — the exploitable flag for this code path is `--receive-pack`.

### Impact Explanation
If the remote's URL uses a transport where `--receive-pack=<program>` is honored client-side (notably `file://`/local-path or `ssh://` transports, where the client tells the remote which program to invoke instead of `git-receive-pack`), an attacker-controlled remote name lets the attacker substitute an arbitrary local script/binary path as the "receive-pack" program that gets executed when the push runs. This is arbitrary command execution scoped to the user's push operation, triggered simply by the user performing a normal push/delete-remote-branch action on a repository whose `.git/config` was attacker-crafted.

### Likelihood Explanation
Exploitation requires the attacker's malicious `remote` name to actually enter the user's `.git/config` — this cannot happen via a normal `git clone` of a hosted repo, since clone always creates a fresh `origin` remote and remote subsection names are never transmitted over the wire. It requires the user to open a folder that already contains an attacker-supplied `.git` directory (e.g., a downloaded/zipped project bundle, or a repository containing a malicious submodule/worktree metadata) as a local repository in GitHub Desktop, and then to perform a push or delete-remote-branch on that maliciously named remote. This is a plausible but less common path than a straightforward clone-based attack, and depends on the remote's transport actually honoring client-supplied `--receive-pack`.

### Recommendation
Before splicing `remote.name` (and similarly `remoteBranchName`/branch names) into git argv, reject or `--` -separate any value beginning with `-`. Concretely, in `app/src/lib/git/branch.ts` and `app/src/lib/git/push.ts`, validate `remote.name` does not start with `-` (throwing/aborting instead of proceeding), or insert a literal `--` before the refspec/positional arguments so git stops option parsing at that point, e.g. `['push', '--', remote.name, refspec]`. Apply the same treatment everywhere `remote.name` or other config-derived identifiers are placed into a git argv (`app/src/lib/git/remote.ts`'s `removeRemote`, `setRemoteURL`, `getRemoteURL`, `updateRemoteHEAD`, etc.).

### Proof of Concept
1. Craft a `.git/config` containing:
```
[remote "--receive-pack=/tmp/evil.sh"]
    url = /tmp/some-local-bare-repo.git
    fetch = +refs/heads/*:refs/remotes/x/*
```
2. Distribute this repository folder to the victim; victim opens it as a local repository in GitHub Desktop.
3. `getRemotes()` returns `{ name: "--receive-pack=/tmp/evil.sh", url: "/tmp/some-local-bare-repo.git" }`.
4. Victim performs a push (or delete-remote-branch); `push.ts`/`branch.ts` build `['push', '--receive-pack=/tmp/evil.sh', 'main:main']`.
5. Because the URL is a local path, git's local transport invokes `/tmp/evil.sh` as the "receive-pack" program instead of `git-receive-pack`, achieving code execution.

A focused unit test (as suggested in the question) constructing such an `IRemote` and asserting the raw argv passed to `git()` starts with `['push', '--receive-pack=...', ...]` demonstrates the argv corruption without needing full git execution.

export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}
