## Analysis

Reducing the external report to its core primitive: a subtraction-based guard was written assuming one operand is always ≥ the other, so the "safety" arithmetic silently collapses to a no-op value instead of failing or computing the correct (signed) result — and nothing downstream catches this, so an invalid/unexpected input flows through unguarded.

The direct local analog is in `modules/pallets/hyper-fungible-token/src/impls.rs`, in the decimal-conversion helpers used to translate between the local Substrate balance and the remote ERC20 `U256` amount for the `hyper-fungible-token` bridge pallet: [1](#0-0) 

### Title
Decimal-scaling functions silently no-op instead of correctly scaling when local decimals exceed remote ERC20 decimals — ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` and `convert_to_erc20` compute the decimal-difference exponent with `erc_decimals.saturating_sub(local_decimals)`. This is only correct when `erc_decimals >= local_decimals`. If a token is configured the other way around (`local_decimals > erc_decimals` — e.g. a token bridged as an 18-decimal Substrate asset representing a 6-decimal ERC20 like USDC), `saturating_sub` returns `0` instead of the true (negative) difference. Rather than reverting or performing the inverse operation, both helpers silently treat the exponent as `0`, i.e. they apply *no* scaling at all, exactly like the "always true" `require(_balanceFrom.sub(_amount) >= 0)` pattern in the external report: the guard exists syntactically but never performs its intended function once the assumption it depends on is violated.

### Finding Description
`convert_to_balance` is documented to "divide by `10^(erc_decimals - local_decimals)` to scale down from ERC20 precision" on inbound transfers, and `convert_to_erc20` to "multiply by `10^(erc_decimals - local_decimals)` to scale up to ERC20 precision" on outbound transfers [2](#0-1) . Both implicitly assume `erc_decimals >= local_decimals`. Neither function validates that assumption, and neither the pallet nor any call site (per the search of `convert_to_balance`/`convert_to_erc20` usage in `module.rs`/`lib.rs`) appears to assert `erc_decimals >= local_decimals` at token registration time. When the assumption is inverted, `saturating_sub` clamps the exponent to `0`, so:
- `convert_to_balance` credits the raw ERC20 `U256` value as the local balance, unscaled.
- `convert_to_erc20` encodes the raw local balance as the outbound ERC20 amount, unscaled.

In the outbound direction this is the dangerous case: a user burns/locks `X` units of the local (higher-decimal) asset, and the pallet is supposed to shrink that to `X / 10^(local_decimals - erc_decimals)` before dispatching the ERC20 mint/release message on the EVM side. Because the exponent is clamped to `0` instead of computing the negative difference, the full, unscaled `X` is dispatched, inflating the beneficiary's ERC20 credit by a factor of `10^(local_decimals - erc_decimals)`.

### Impact Explanation
This directly fits the "unauthorized/incorrect amount moved" and "false state acceptance" classes: any holder of the affected asset who triggers an outbound (ISMP dispatch) redemption receives (or credits a destination address with) an ERC20 amount many orders of magnitude larger than what was actually burned/escrowed on the Substrate side, causing token-supply inflation and direct fund loss for the bridge/token issuer. This is a pure math/logic bug in bridged-asset custody accounting, not dependent on a malicious relayer, prover, or governance actor — it triggers on ordinary use whenever a token is registered with `local_decimals > erc_decimals`, which is a realistic configuration (bridging low-decimal ERC20 stablecoins into a higher-decimal Substrate balance representation).

### Likelihood Explanation
Likelihood depends on whether any currently-registered token actually has `local_decimals > erc_decimals`; this is a plausible, common configuration (e.g., 6-decimal USDC ERC20 mapped to an 18-decimal Substrate balance) but I was not able to confirm the exact registered decimal values or the full call sites in `module.rs`/`lib.rs` within the available search budget — those would need to be checked to confirm the vulnerable configuration is (or could be) live. The bug itself is unconditionally present in the code as written.

### Recommendation
Do not use `saturating_sub` to compute a decimals difference that can legitimately be negative. Either:
1. Enforce and validate `erc_decimals >= local_decimals` at token registration (reject/require otherwise), or
2. Compute a signed difference and branch: multiply when `erc_decimals > local_decimals`, divide when `local_decimals > erc_decimals`, so both directions scale correctly regardless of which side has more precision.

### Proof of Concept
1. Register (or assume a runtime configuration allows) a token in `hyper-fungible-token` with `local_decimals = 18` and `erc_decimals = 6`.
2. A user holds/locks `X` local-balance units (18-decimal) and triggers the outbound path that calls `convert_to_erc20(X, erc_decimals=6, local_decimals=18)`.
3. `erc_decimals.saturating_sub(local_decimals)` = `6u8.saturating_sub(18u8)` = `0`, so the function returns `U256::from(X) * 10^0 = X` instead of the correct `X / 10^12`.
4. The dispatched ISMP message instructs the destination EVM `hyper-fungible-token`/token-governor contract to release/mint `X` raw ERC20 units (6-decimal denomination) — 10^12× more than the correct amount — resulting in massive over-issuance/fund loss on the destination chain.

I could not fully verify the exact registered decimal configuration or trace every call site of these helpers due to the search budget; a Devin session with full repo access should confirm the call sites in `module.rs`/`lib.rs` and any existing decimals-validation logic before treating this as conclusively exploitable in the current deployment.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
