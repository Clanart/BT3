### Title
Untrusted `ThresholdKeys::read` bytes act as flag injection: attacker-selected interpolation tag and unchecked secret-share/verification-share binding yield a fully attacker-defined group key - (File: crypto/dkg/src/lib.rs)

### Summary
The GitLab report is a flag-injection bug: an API parameter (`ref`) was concatenated into a fixed-format command, letting the attacker inject a new flag (`--output=...`) that changed the operation's semantics. The Serai analog lives in `ThresholdKeys::read` / `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:574-632`), where untrusted serialized bytes carry a type-flag byte selecting the interpolation method plus all key material, and `ThresholdKeys::new` accepts the resulting object without ever checking that `generator() * secret_share == verification_shares[i]` — so attacker-controlled bytes reinterpreted as "the flag byte + fields" silently redefine the cryptographic identity of the key set.

### Finding Description
`ThresholdKeys::read` parses, in order: a curve ID, `t`, `n`, `i`, then a one-byte *flag* (`0` → `Interpolation::Constant` consuming `n` attacker-supplied scalars, `1` → `Interpolation::Lagrange`, other → error) at `crypto/dkg/src/lib.rs:604-616`, then `secret_share` (`:618`) and `n` verification shares (`:620-623`), and forwards everything to `ThresholdKeys::new`.

`ThresholdKeys::new` (`:349-391`) validates only:
- `verification_shares.len() == n` (`:355-360`)
- every participant index `<= n` (`:361-365`)
- `Constant` interpolation only when `t == n` (`:367-374`)

It then computes `group_key = Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i)` (`:376-378`) — entirely from attacker-supplied points — and stores the attacker-supplied `secret_share` without checking it is consistent with `verification_shares[i]` (i.e. `G * secret_share == verification_shares[i]` is never evaluated anywhere in `new` or `read`).

This mirrors the report exactly: a field expected to be inert data is deserialized into a discriminator (`0`/`1`) that swaps the entire semantic interpretation of the following bytes, and the resulting object is trusted as a coherent key set. Flipping a Lagrange encoding to `0` makes the next `n` scalars parse as polynomial coefficients (Constant interpolation), producing a wholly different `group_key` from the same buffer; or the attacker supplies a freshly-minted blob whose `verification_shares` have known discrete logs, making `group_key()` a key the attacker alone controls, while `secret_share` is set to an unrelated value (no consistency check exists to catch it).

### Impact Explanation
Anything downstream that treats `ThresholdKeys::read` output as "the participant's share of *the* group key" is subverted:
- `group_key()` (`:445-447`) returns an attacker-chosen public key. If the deserialized keys are used to register a multisig key with the Bitcoin scanner (`Scanner::new`/`register_offset`, `networks/bitcoin/src/wallet/mod.rs:162-196`), deposits to the resulting P2TR script are spendable by the attacker's known discrete log — funds reported as received by the multisig are actually the attacker's.
- `view()`/`sign` produce shares under `secret_share` which cannot be consistent with `verification_shares`, so an injected blob causes either signature-share forgery capability for the attacker (who knows the group key's log outright and needs no shares) or deterministic blame/verify failure against honest participants.
- This is reachable per the engagement rules: `ThresholdKeys::read` is explicitly listed as an untrusted-bytes sink.

Severity: High — attacker-defined group key and/or signing corruption from pure deserialization of attacker bytes; exploitation requires only that a deserialized `ThresholdKeys` be used without an external consistency check, which the type's API (returning `Ok` from `new`) actively invites.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API over arbitrary bytes. Any persisted, transmitted, or restored key-share blob crossing a trust boundary (backup/restore, transport between coordinator and signer, message-delivered key material) reaches it. The exploit needs no curve math on the attacker's part: choose any `n` scalars/points with known logs, encode tag `0` or `1`, set `t = n`, and `ThresholdKeys::new` returns `Ok`. The missing `G * secret_share == verification_shares[i]` check means even honest-party secret material can be paired with attacker verification shares, or vice versa, without detection until signing fails — or never, if the attacker owns the whole synthetic set.

### Recommendation
In `ThresholdKeys::new` (and therefore `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]`, rejecting inconsistent blobs. Additionally, when deserializing, bind the interpolation tag cryptographically (e.g., reject `Constant` unless the caller explicitly requested it, rather than trusting the in-band flag byte), so a flag flip cannot silently reinterpret the encoding.

### Proof of Concept
```rust
// crypto/dkg pseudocode — attacker crafts a blob for ThresholdKeys::read
// t = 1, n = 1, i = 1, interpolation = Lagrange (tag 1)
let a = Scalar::random(&mut OsRng);          // attacker-known scalar
let fake_share = a;                           // G * a is the "verification share"
let blob = encode([
  id_len || C::ID,
  t=1u16, n=1u16, i=1u16,
  0x01,                                      // Lagrange
  fake_share.to_repr(),
  (G * a).to_bytes(),                        // verification_shares[1]
]);
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// group_key = G * a — discrete log known to attacker.
// Any Scanner::new(keys.group_key()) deposit is spendable by 'a'.
// Alternatively, set secret_share = b != a: read() still returns Ok —
// the G*secret_share == verification_shares[i] check does not exist.
// Signing under these keys produces shares honest peers cannot verify,
// while the attacker's fully-known group key signs unilaterally.
```
