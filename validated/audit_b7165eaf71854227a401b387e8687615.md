### Title
Webhook shop-domain header is not bound to the HMAC-verified payload, allowing cross-shop webhook replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` validates only the raw request body against a shared, per-app HMAC secret, while the shop identity used for all downstream processing (`shop_domain`) is read from the unauthenticated `X-Shopify-Shop-Domain` header. Because the HMAC secret is the same for every shop that has the app installed, and the header is not part of the signed payload, a party who is able to obtain one valid `(body, HMAC)` pair (e.g., from a webhook delivered to their own installed shop) can replay that exact body/HMAC with a different `X-Shopify-Shop-Domain` header value. The request passes `verify_request`, and the application then looks up/acts on a different ("victim") shop using data that was never actually associated with that shop — the same class of bug as the external report: one payload field is authenticated/validated (`apiData`'s implied token in the swap contract vs. the report's `swapData`), while a second, functionally decisive field is trusted without cross-validation.

### Finding Description
The verification concern only checks the HMAC of the raw body: [1](#0-0) 

and separately exposes an unauthenticated `shop_domain` method sourced purely from a client-suppliable header: [2](#0-1) 

`hmac_valid?` itself is defined in `PayloadVerification` and validates the body against `ShopifyApp.configuration.secret`/`old_secret`, i.e. a single app-wide secret shared by every merchant that installs the app — it is not shop-specific: [3](#0-2) 

The generated job/controller templates that shopify_app tells developers to use for custom webhook processing consume `shop_domain` (or the equivalent `webhook_request.shop`) directly to select the shop/session that the webhook body will be processed against, without any check that the body actually originated for that shop: [4](#0-3) [5](#0-4) 

Because the header (`shop_domain`) and the HMAC-covered body are never cross-validated against each other, an attacker who controls a shop where the app is installed can:
1. Receive a legitimate webhook for their own shop (`body`, valid `HMAC`).
2. Resend the identical `body`/`HMAC` pair to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain.
3. `verify_request` passes because the body/HMAC pair is valid (same shared secret for all shops).
4. Downstream code (`Shop.find_by(shopify_domain: shop_domain)` → `shop.with_shopify_session`) activates the victim's shop/session and processes the attacker-originated body under it.

This directly parallels the report's root cause: authenticity is asserted for one field (the HMAC-covered body / `apiData.tokenFrom`) while a second, operationally decisive field (the shop-domain header / `swapData`'s token) is trusted without being tied to the same authenticated payload.

### Impact Explanation
An attacker-controlled shop can inject arbitrary attacker-chosen webhook bodies (topic-appropriate JSON) that get processed under a victim shop's session/access token, since the shop selection is entirely decoupled from the cryptographically verified data. Depending on the webhook job's logic (e.g., updating orders/products/customers, writing metafields, or dispatching business logic tied to the shop's Shopify Admin session), this enables cross-shop data corruption/injection using the victim's own authenticated Shopify session — a cross-tenant confidentiality/integrity violation.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop have the app installed (a normal, unprivileged merchant) so they can capture one legitimate, validly signed webhook body/HMAC pair for any topic the app subscribes to, then replay it at the shared webhook endpoint with a forged shop-domain header. No secret material, developer access, or victim cooperation is needed; the only "special" requirement is app installation, which any external actor can obtain by installing the app on a test/attacker-controlled store — this is an anonymous/unrelated-merchant-reachable path.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting the header independently:
- Include the shop domain (and/or webhook id) as part of the HMAC-covered material, or derive shop identity strictly from a field inside the verified body rather than the `X-Shopify-Shop-Domain` header.
- If the header must be used, cross-validate it against a shop identifier embedded in and covered by the signed body before using it to select a shop/session.
- Consider using per-shop webhook secrets where supported, so a valid signature for shop A cannot be replayed as if it belonged to shop B.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Resend the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyApp::WebhookVerification#verify_request` (lib/shopify_app/controller_concerns/webhook_verification.rb) calls `hmac_valid?(request.raw_post)`, which succeeds because the HMAC is valid for the shared app secret regardless of which shop it was issued for.
4. The downstream job/controller (as in `lib/generators/shopify_app/add_webhook/templates/webhook_job.rb.tt`) resolves `Shop.find_by(shopify_domain: shop_domain)` using the attacker-forged header, finds `victim.myshopify.com`, and processes the attacker's captured (and possibly attacker-influenced) webhook body under the victim shop's session — demonstrating the cross-shop processing caused by the unvalidated shop-domain/body inconsistency.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
