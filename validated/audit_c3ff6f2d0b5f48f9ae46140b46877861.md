## Title
Symlink-based path escape in file context-menu actions bypasses the app's own `resolveWithin` safety guard - (File: `app/src/lib/app-shell.ts`, `app/src/ui/lib/open-file.ts`)

### Summary
GitHub Desktop already recognizes that file paths derived from a repository's working directory can be used to escape the repository root via directory traversal or filesystem symlinks, and it fixed this for a couple of routes (`app/src/lib/copilot-conflict-context.ts`, `app/src/ui/dispatcher/dispatcher.ts`) by resolving every path through `resolveWithin()`, which explicitly canonicalizes symlinks and rejects any result that isn't a real descendant of the repo root [1](#0-0) . However, the exact same class of attacker-controlled path — a `WorkingDirectoryFileChange`/`CommittedFileChange` path taken straight from git status/diff output of a cloned or fetched repository — is used unchecked in `revealInFileManager`, `openFile`, and the "Open in External Editor" context-menu handlers, all of which simply `Path.join(repository.path, path)` with no `resolveWithin` guard. This mirrors the report's pattern exactly: a safety invariant ("only operate within the locked/whitelisted domain") is enforced on one code path but omitted on a functionally identical sibling path, breaking the invariant.

### Finding Description
`app-shell.ts`'s own JSDoc warns "Do not use this method with non-validated paths" for `openPath`/`showFolderContents`, yet `revealInFileManager` builds the path with plain `Path.join` and hands it straight to `shell.showItemInFolder`: [2](#0-1) 

Similarly, `openFile` (used for "Open with Default Program" from the Changes list, History list, and Pull Request files list) takes a `fullPath` built the same unchecked way and passes it to `shell.openExternal`: [3](#0-2) 

These are invoked from multiple UI surfaces using file paths that originate directly from git status data of the checked-out repository, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

By contrast, when the app itself identified this exact risk (opening a file whose path can escape the repo through a symlink or traversal), it explicitly guarded it in `copilot-conflict-context.ts`: [7](#0-6) 

and in the deep-link file-open handler in `dispatcher.ts`: [8](#0-7) 

`resolveWithin` is specifically designed to defeat this: its own test suite verifies it "fails for paths that use a symlink to traverse outside of the root": [9](#0-8) 

A git tree can contain a tracked symlink entry (mode `120000`) whose target is an arbitrary string, e.g. `../../../../.ssh/id_rsa` or an absolute path. When a user clones or fetches such a malicious repository on macOS/Linux, git materializes that entry as a real filesystem symlink inside the working directory pointing outside the repo. If the user then right-clicks that entry in the Changes list, History file list, or PR "Files changed" list and selects "Open with Default Program," "Reveal in Finder," or "Open in External Editor," the app resolves `repository.path + <tracked symlink name>` with plain `Path.join`, which does not dereference or validate the symlink target, and hands that path to `shell.openExternal`/`shell.showItemInFolder`/the external editor launcher, which does follow the symlink at the OS level.

### Impact Explanation
This allows an attacker who controls a cloned/fetched repository to get the victim's own Desktop client to open or reveal an arbitrary file outside the repository (e.g., SSH private keys, cloud credential files, browser profile files) via a single, natural user action (opening a changed/committed file from the UI) — matching the "file write or read outside the repo" impact class. Opening the file with the default program or an external editor can disclose its contents to the attacker if that program renders/echoes it somewhere observable, and at minimum it silently causes command execution/interaction with an out-of-repo, attacker-chosen filesystem target.

### Likelihood Explanation
The action is a single context-menu click a user would perform routinely after cloning a repo and reviewing its changed/committed files — no admin rights, no local access, and no unusual steps are required. The only precondition is that the OS support real symlinks for tracked git entries (true for macOS/Linux, Desktop's primary/majority platforms), which is the same precondition the project's own `resolveWithin` symlink test already accounts for.

### Recommendation
Route every file path derived from repository contents through `resolveWithin(repository.path, path)` before using it in `revealInFileManager`, `openFile`, and the "Open in External Editor" handlers (`app.tsx`'s `onOpenInExternalEditor`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `filter-changes-list.tsx`, and `copilot-conflicts-dialog.tsx`'s `onOverflowMenuClick`), refusing the action (as `openRepositoryFromUrl` already does) when the resolved path escapes the repository root.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink entry, e.g. `git add -f evil-link` where `evil-link -> ../../../../.ssh/id_rsa`, and commits it.
2. Victim clones or fetches/checks out this repository in GitHub Desktop on macOS/Linux; the symlink is materialized on disk pointing to the victim's real SSH key.
3. Victim opens the Changes/History/PR file list, right-clicks `evil-link`, and selects "Open with Default Program" or "Reveal in Finder."
4. `openFile`/`revealInFileManager` join `repository.path` with `evil-link` via `Path.join` (no `resolveWithin` check) and pass the result to `shell.openExternal`/`shell.showItemInFolder`, which follow the symlink and open/reveal `~/.ssh/id_rsa` outside the repository.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher

  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,

  }
}
```
