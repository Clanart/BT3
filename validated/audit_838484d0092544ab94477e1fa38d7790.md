## Analog Found: Unbounded Lifetime VWAP Oracle Never Decays — Intent Settlement Uses Permanently Stale Spread Data

### Title
Intent Settlement `VWAPOracle` Computes an All-Time Cumulative Average With No Time Window, Causing Permanent Price Lag That Defeats Its Anti-Manipulation Purpose - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
The reported GTE-perps bug is an EMA whose window is 900× longer than intended (2.5h instead of 15m), causing the mark-price component to lag real market conditions. The Hyperbridge analog is `VWAPOracle`, the `IIntentPriceOracle` implementation consulted during cross-chain intent settlement: its `spread()` value is a **lifetime, ever-growing cumulative weighted average with no window or decay at all** — an infinitely worse case of the same broken invariant (a price signal meant to reflect *current* market conditions instead reflects the average of the entire history since deployment).

### Finding Description
`recordSpread()` accumulates every fill's weighted spread into `CumulativeSpreadData` forever: [1](#0-0) 

and `spread()` simply divides the running totals: [2](#0-1) 

The struct even tracks `lastUpdate`, implying an intended time-based mechanism, but this field is written and never read anywhere in the contract: [3](#0-2) 

There is no reset, no ring buffer, no timestamp-bucketing, and no way for `totalVolume`/`weightedSpreadSum` to ever shrink or "forget" old fills — the exact class of bug in the report, where a value meant to represent a bounded recent window (15 minutes) instead spans a much longer, effectively unbounded period. Here the period is unbounded by construction: after enough historical volume accumulates, `spread()` becomes numerically frozen and cannot move to reflect a market/spread regime change within any reasonable timeframe, no matter how extreme a current fill's spread is.

This oracle is consumed as `IIntentPriceOracle` by the intent settlement path (`sourceChainHash`/`token`-keyed spread used to gauge whether a filler's proposed price is fair), per the interface declared in `IntentPriceOracle.sol` and the doc comment "Gas-efficient oracle for tracking cumulative VWAP spreads for same-token swaps... Tracks spreads per (source chain, token address)": [4](#0-3) 

### Impact Explanation
Because `spread()` is diluted by all historical volume, once meaningful volume has passed through a `(sourceChain, token)` pair, the reported spread becomes essentially insensitive to new fills — an attacker/filler can settle intents at spreads far worse than the current fair-market spread while the oracle continues to report a stale, historically-averaged value that looks "normal." Any downstream logic (in `IntentGateway`/fill-acceptance code that references this oracle for slippage or manipulation checks) is therefore checking against a value that can never reflect a rapid adverse move, permanently defeating the anti-manipulation purpose of the oracle and enabling fillers to extract value from users at consistently degraded exchange rates — a direct fund-loss vector in intent settlement, matching the report's core defect (price component that cannot track real conditions within its intended horizon) but unbounded in severity since there is no window at all.

### Likelihood Explanation
No privileged or malicious-peer assumption is required: `recordSpread()` is called by the `_intentGateway` on every normal fill via the `restrict(_intentGateway)` modifier, so the drift accumulates from ordinary protocol usage. Any unprivileged filler benefits automatically as volume/history grows — there's no attacker action needed beyond normal participation in the intent-fill flow, and the flaw is deterministic and permanent, not a timing race.

### Recommendation
Implement an actual time-windowed VWAP: bucket fills by timestamp (e.g., ring buffer of N most-recent time slots or a decaying/expiring window keyed off `lastUpdate`), and evict/decay contributions older than the intended lookback (analogous to the report's two remediation options: reduce to the real intended window, or use `lastUpdate`/timestamp-based pruning so `weightedSpreadSum`/`totalVolume` only reflect recent fills).

### Proof of Concept
1. Deploy `VWAPOracle`, `init()` with token decimals for a `sourceChain`/token pair.
2. Call `recordSpread()` repeatedly (as `_intentGateway`) over time with large `inputAmountNormalized` volume and near-zero spread (e.g., 0–1 bps) to build up `totalVolume` into a large number, as shown in the existing test suite's cumulative-fill pattern: [5](#0-4) 
3. Once `totalVolume` is large, call `recordSpread()` with an intentionally bad fill (e.g., -500 bps, filler stealing 5% from the user).
4. Observe via `spread()` that the reported aggregate barely moves (diluted by historical volume), so any consumer relying on `spread()` to detect/reject anomalous fills fails to flag the manipulation — the oracle never "catches up" because there is no time window to age out the old data, unlike the intended 15-minute EMA in the reference report.

```text
    function spread(bytes memory sourceChain, address token) external view returns (int256) {
        bytes32 chainHash = keccak256(sourceChain);
        CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];
        if (data.totalVolume == 0) return 0;

        return data.weightedSpreadSum / int256(data.totalVolume);
    }
```

```text
    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
        data.weightedSpreadSum += weightedSpread;

        data.fillCount += 1;
        data.lastUpdate = block.timestamp;
    }
```
