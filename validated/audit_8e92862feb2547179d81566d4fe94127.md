### Title
Integer/length overflow enables an attacker-controlled infinite/near-infinite scan loop in `ArrayDecoders.skipField` and `RepeatedField`/`TcParser` packed-length arithmetic - (File: `java/core/src/main/java/com/google/protobuf/ArrayDecoders.java`, `src/google/protobuf/generated_message_tctable_lite.cc`)

### Summary
The Juno advisory's failed invariant is: an attacker-controlled length/count value is consumed by a decompression loop without checking for arithmetic overflow, so the loop's termination condition never becomes false, causing unbounded CPU consumption (DoS) from a single crafted message. The closest actual-code analog inside this protobuf checkout is in the length-delimited/group skipping and packed-field parsing paths, where negative or overflowed lengths derived from a wire varint feed into pointer/position arithmetic. Unlike Juno, this repository already contains explicit regression tests and guards for exactly this class of bug, so the invariant is *defended*, not broken, in the current code — I could not prove a live break of an existing check.

### Finding Description
`ArrayDecoders.skipField` and the C++ `TcParser` fast paths compute a `limit`/`fieldLimit` from an attacker-supplied varint length added to the current buffer position (`java/core/src/main/java/com/google/protobuf/ArrayDecoders.java:437-488`, e.g. `final int fieldLimit = position + packedDataByteSize;`). If `packedDataByteSize` (attacker controlled, decoded straight from the wire) is negative or large enough to overflow the `int` addition, the resulting `fieldLimit` can wrap and no longer bound the `while (position < fieldLimit)` loop correctly — this is structurally the same "attacker length feeds unchecked arithmetic that drives a loop bound" pattern as the Sierra decompression overflow in Juno.

The repository's own tests show this exact class of defect was previously reachable and had to be explicitly hardened:
- `java/core/src/test/java/com/google/protobuf/ArrayDecodersTest.java:373-384` (`testException_skipField_infiniteLoop`) constructs a payload with a start-group tag followed by a length-delimited field whose length varint decodes to `-6`, explicitly documented as the "Payload that triggers the infinite loop," and asserts (with a 1-second JUnit timeout) that `skipField` now throws `InvalidProtocolBufferException` instead of looping forever.
- `java/core/src/test/java/com/google/protobuf/ArrayDecodersTest.java:351-362` similarly crafts a negative-size varint to confirm `skipField` rejects it.
- `src/google/protobuf/generated_message_tctable_lite.cc:1136-1146` (`TcParser::RepeatedVarint`) contains an explicit anti-overflow guard: `int limit = 10; while ((*ptr2 & 0x80) && limit--) ptr2++;` with the comment "Defend against overflowing available data due to malformed input of infinite number of bytes with top bit set," directly mirroring the Juno "attacker-controlled count causes infinite loop" scenario but with a hard iteration cap.
- `src/google/protobuf/generated_message_tctable_lite_test.cc:903-949` (`PackedEnumSmallRangeLargeSize`) is a dedicated regression test verifying "the parser doesn't overflow an int32 when computing the array's new length" for a crafted length near `INT32_MAX`.

I could not locate the underlying `CodedInputStream.pushLimit`/`getBytesUntilLimit` implementation in this pass (tool budget exhausted before rendering `CodedInputStream.java`), so I cannot fully confirm whether every packed/length-delimited call site enforces the same negative-length/overflow check that `skipField` now has, or whether it is limited to that one function.

### Impact Explanation
If an unchecked arithmetic overflow of this kind were present (as the tests imply it once was), a single crafted Protobuf message parsed through a public `parseFrom`/`mergeFrom` API could drive a parsing loop into an unbounded or extremely long iteration count, consuming CPU and denying service to the consuming application — the same impact class as the Juno Sierra-bytecode DoS. This would be High severity if reachable, since it requires no privileged access and is triggerable via ordinary bounded wire input.

### Likelihood Explanation
Low/Not currently demonstrated to be exploitable. The exact scenario described in the Juno report (unchecked length arithmetic overflow driving an infinite loop) is already covered by dedicated, passing regression tests in this codebase (`testException_skipField_infiniteLoop`, `PackedEnumSmallRangeLargeSize`), and the fast-path C++ decoder has an explicit hard cap (`limit = 10`) preventing runaway scanning on malformed varints. No bypass of these specific checks was found or demonstrated within the scope of this pass.

### Recommendation
- Audit all remaining call sites that compute `position + length`-style bounds (particularly any packed-field or length-delimited helpers outside `ArrayDecoders.skipField`, and any equivalent arithmetic in `CodedInputStream`/native `upb` decoders) to confirm they reject negative or overflowing lengths before using them as loop bounds, consistent with the fix validated by `testException_skipField_infiniteLoop`.
- Add/keep timeout-bound fuzz/regression tests (as already done) for every decoder that derives a loop bound from an attacker-supplied varint, to catch regressions of this overflow class.

### Proof of Concept
No new reproducible overflow was found in this pass; the existing repository regression test already documents and exercises the strongest available analog:

```java
  /** Decodes a packed 32-bit varint field. Returns the position after all read values. */
  static int decodePackedVarint32List(
      byte[] data, int position, ProtobufList<?> list, Registers registers) throws IOException {
    final IntArrayList output = (IntArrayList) list;
    position = decodeLengthPrefixVarint(data, position, data.length, registers);
    final int packedDataByteSize = registers.int1;
    final int fieldLimit = position + packedDataByteSize;
    while (position < fieldLimit) {
      position = decodeVarint32(data, position, registers);
      output.addInt(registers.int1);
    }
    if (position != fieldLimit) {
      throw InvalidProtocolBufferException.truncatedMessage();
    }
    return position;
  }
```

```text
// This test checks that the parser doesn't overflow an int32 when computing the
// array's new length.
TEST(GeneratedMessageTctableLiteTest, PackedEnumSmallRangeLargeSize) {
  if constexpr (internal::HasAnySanitizer()) {
    GTEST_SKIP() << "This test attempts to allocate 8GB of memory, which OOMs "
                    "in sanitizer mode.";
  }

#ifdef _WIN32
  // This test OOMs on Windows.  I think this is because Windows is committing
  // the entirety of the 8GB malloc'ed range, whereas Linux maps it but doesn't
  // commit it.
  return;
#endif

  // This test is only meaningful on 64-bit platforms.  On 32-bit platforms, we
  // can't allocate 2^31 4-byte elements anyway; that is a straightforward OOM.
  if (sizeof(size_t) < 8) {
    return;
  }

  // Create a serialized proto that contains just `field 1: length ~2^31`.  We
  // don't put the actual data in there, just the field header.
  uint8_t serialize_buffer[64];
  uint8_t* serialize_ptr = serialize_buffer;
  serialize_ptr = WireFormatLite::WriteTagToArray(
      1, WireFormatLite::WIRETYPE_LENGTH_DELIMITED, serialize_ptr);
  // INT32_MAX is not a valid array length because RepeatedField uses a bit of
  // space for its metadata.  We can be a little short of it, that's fine.
  serialize_ptr = WireFormatLite::WriteUInt32NoTagToArray(
      std::numeric_limits<int32_t>::max() - 64, serialize_ptr);

  absl::string_view serialized{
      reinterpret_cast<char*>(&serialize_buffer[0]),
      static_cast<size_t>(serialize_ptr - serialize_buffer)};

  // This isn't a legal proto because the given array length (a little less than
  // 2^31) doesn't match the actual array length (0).  But all we're checking
  // for here is that we don't have UB when deserializing.
  proto2_unittest::TestPackedEnumSmallRange proto;
  // Add a few elements to the proto so that when we MergeFromString, the final
  // array length is greater than INT32_MAX.
  for (int i = 0; i < 128; i++) {
    proto.add_vals(proto2_unittest::TestPackedEnumSmallRange::FOO);
  }
  EXPECT_FALSE(proto.MergeFromString(serialized));
```
