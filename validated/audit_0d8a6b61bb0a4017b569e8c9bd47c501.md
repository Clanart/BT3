### Title
Attacker can vote-then-cast-then-unvote to appropriate an entire zero-supply reward backlog in a single low-latency sequence - (File: rewards/BaseRewardPoolV2.sol / rewards/BribeRewardPool.sol / wombat/WombatBribeManager.sol)

### Summary
`_provisionReward()` in `BaseRewardPoolV2.sol` routes incoming bribe rewards into `queuedRewards` whenever `totalStaked() == 0`, and dumps the entire accumulated backlog into `rewardPerTokenStored` on the very next provision that occurs while `totalStaked() > 0`, with no time-weighting. [1](#0-0)  Because `WombatBribeManager.vote`/`unvote` call `BribeRewardPool.stakeFor`/`withdrawFor` with no minimum holding period, and `castVotes()` (which triggers the harvest/`queueNewRewards` call that performs the provision) is fully permissionless, an attacker who is the sole staker at the moment of provisioning can capture the whole backlog and immediately unvote to claim it. [2](#0-1) [3](#0-2) 

### Finding Description
`BribeRewardPool` (a `BaseRewardPoolV2`) tracks `totalSupply`/`_balances` that mirror a user's locked-MGP vote weight for a given Wombat pool, updated only via `stakeFor`/`withdrawFor`, both restricted to `onlyOperator` (the `WombatBribeManager`). [4](#0-3) 

Reward provisioning logic:
```
if (totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    if (rewardInfo.queuedRewards > 0) {
        _amountReward += rewardInfo.queuedRewards;
        rewardInfo.queuedRewards = 0;
    }
    rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
}
``` [5](#0-4) 

If no one has active vote-weight on a pool (`totalSupply == 0`) while bribes keep accruing on Wombat's side for that pool's still-live on-chain vote allocation, every harvested reward silently piles up in `queuedRewards`. The very first account whose stake causes `totalStaked() > 0` at the moment the *next* `_provisionReward` call fires (triggered from `castVotes()` → `wombatStaking.vote()` → bribe harvest → `queueNewRewards`) absorbs the entire backlog into `rewardPerTokenStored`, split only among whoever currently holds shares — potentially just that one attacker.

Exploit path:
1. Attacker (holding vlMGP they legitimately locked) calls `WombatBribeManager.vote(...)` with a positive delta for the target pool. This calls `BribeRewardPool.stakeFor`, which runs `updateRewards` and sets `userRewardPerTokenPaid[attacker] = rewardPerTokenStored` (pre-backlog value), then sets `totalSupply = attacker's balance` (only staker). [6](#0-5) [7](#0-6) 
2. Attacker (or anyone) calls the permissionless `castVotes()`, which harvests bribes and forwards them via `queueNewRewards`/`_provisionReward` to the rewarder while `totalStaked()` is nonzero (attacker's stake only) — the whole `queuedRewards` backlog plus the fresh harvest is converted into `rewardPerTokenStored` in one step, attributed entirely to the attacker's share. [3](#0-2) 
3. Attacker calls `unvote()` (or `vote()` with a negative delta), which calls `withdrawFor(..., claim=true)`. `updateRewards`/`earned()` computes `(rewardPerTokenStored_new − userRewardPerTokenPaid_old) * balance`, i.e. the full backlog, and pays it out immediately. [8](#0-7) [9](#0-8) 

No modifier, cooldown, or minimum-holding check exists in `vote`/`unvote`/`stakeFor`/`withdrawFor` to prevent this same-block-in/out pattern, so the reward-index update mechanism itself is what fails to protect long-term voters.

### Impact Explanation
This lets an unprivileged holder of locked MGP extract bribe yield that accrued while nobody (or other, legitimate long-term voters) held vote-weight, without bearing any of the time/opportunity cost of actually voting for that pool. This matches the "theft or permanent freezing of unclaimed yield" impact class: yield destined for the pool's real voters is diverted to a single opportunistic actor who enters and exits around the harvest transaction.

### Likelihood Explanation
Preconditions: (a) attacker must already hold locked MGP (vlMGP) to vote — capital cost, but this is normal user capability, not a privileged role; (b) a window must exist where `totalSupply` in `BribeRewardPool` is zero (or attacker is sole staker) while Wombat-side votes/bribes for that pool are still live/accruing — a realistic, recurring condition whenever voters unvote before the next `castVotes()` cycle, or immediately after a new pool is added; (c) `castVotes()` is public/permissionless, so the attacker (or anyone) can trigger the provisioning at will, making the timing attacker-controlled rather than dependent on chance. This is repeatable per pool per idle period and does not require flash loans, reentrancy, or any privileged role.

### Recommendation
Time-weight the backlog release (e.g., accrue `queuedRewards` proportionally to time-since-idle rather than dumping it entirely on the first non-zero-supply provision), or require a minimum staking duration between `vote` and `unvote`/claim before backlog rewards can be attributed to a given staker, or snapshot eligibility for queued rewards to those who held stake during the idle accrual window (e.g., checkpoint-based distribution) instead of only to whoever holds `totalSupply` at the instant of release.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy/fork Magpie's `WombatBribeManager`, `BribeRewardPool`, and `WombatStaking` with a pool that has zero `totalSupply` in its `BribeRewardPool` but nonzero live votes at the Wombat voter (simulate a prior voter having unvoted).
2. Advance bribes on the mocked/forked Wombat bribe contract so a large reward accrues for that pool while `BribeRewardPool.totalSupply == 0`; confirm `rewards[token].queuedRewards` grows and `rewardPerTokenStored` stays flat.
3. Attacker account locks MGP, calls `vote([pool], [positiveDelta])` — assert `totalSupply == attacker balance` and `userRewardPerTokenPaid[token][attacker] == rewardPerTokenStored` (pre-backlog).
4. Attacker calls `castVotes(false)` — assert `rewardPerTokenStored` jumps by the full backlog amount (`queuedRewards` now 0).
5. Attacker calls `unvote(pool)` — assert attacker receives the entire backlog reward via `RewardPaid` event/token transfer, while a "victim" account that had no stake during steps 1-4 receives nothing despite the reward having accrued from bribes for that pool.
6. Assert the invariant fails: `rewardPerTokenStored` moved fully into the attacker's claimed amount with `userRewardPerTokenPaid[attacker]` reconciling only against the attacker's brief presence, not against any real voting duration.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,

    function vote(address[] calldata _lps, int256[] calldata _deltas) override public {
        if (_lps.length != _deltas.length)
            revert LengthMismatch();

        uint256 length = _lps.length;
        int256 totalUserVote;

        for (uint256 i; i < length; i++) {
            Pool storage pool = poolInfos[_lps[i]];
            if (!pool.isActive)
                revert PoolNotActive();
            int256 delta = _deltas[i];
            totalUserVote += delta;
            if (delta != 0) {
                if (delta > 0) {
                    pool.totalVoteInVlmgp += uint256(delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] += uint256(delta);
                    IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
                } else {
                    pool.totalVoteInVlmgp -= uint256(-delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta);
                    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
                }
            }
        }

        if (msg.sender != delegatedPool) {
            if (totalUserVote > 0) {
                userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);
                totalVlMgpInVote += uint256(totalUserVote);

                totalVlMgpInVote -= uint256(-totalUserVote);
