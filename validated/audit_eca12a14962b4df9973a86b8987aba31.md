### Title
Unbounded per-proposal deposit fan-out causes unbatched `RefundDeposits`/`DeleteDeposits` iteration in `EndBlocker`, enabling block-delay DoS - (File: sei-cosmos/x/gov/keeper/deposit.go)

### Summary
Sei's governance module lets any number of distinct accounts each submit a `MsgDeposit` on the same proposal with no per-deposit minimum amount check. Each unique depositor creates one persisted `Deposit` record. When a proposal's voting period ends, `EndBlocker` unconditionally calls `keeper.RefundDeposits` (or `keeper.DeleteDeposits`) for that proposal, and both functions iterate **every** deposit record for the proposal and perform a `bankKeeper.SendCoinsFromModuleToAccount`/`BurnCoins` call per record with **no budget cap**, unlike the vote-tallying loop in the same `EndBlocker`, which is explicitly bounded by `MaxVotesProcessedPerBlock`.

### Finding Description
`AddDeposit` only dedupes deposits per `(proposalID, depositorAddr)` key, and `MsgDeposit.ValidateBasic` places no floor on the deposit amount: [1](#0-0) 

An attacker can therefore generate an arbitrarily large number of distinct accounts and have each submit a minimal (e.g. `1usei`) `MsgDeposit` on a single proposal, creating one `Deposit` record per account: [2](#0-1) 

When the proposal's voting period ends (or it fails minimum deposit), `EndBlocker` calls `RefundDeposits` or `DeleteDeposits` for that proposal **unconditionally and without any record-processing budget**, unlike the tally loop right above it, which is explicitly capped by `MaxVotesProcessedPerBlock`: [3](#0-2) 

Both `RefundDeposits` and `DeleteDeposits` fully iterate the deposit prefix for that proposal and perform a bank operation per entry, with no pagination or per-block limit: [4](#0-3) [5](#0-4) 

This is the same bug class as the referenced OpenQ report: an unprivileged actor can inflate the number of records tied to a single logical entity (a bounty/proposal) with no floor on per-record cost, and a later administrative operation (refund) is forced to iterate all of them synchronously with no bound.

### Impact Explanation
Because the governance module explicitly bounds vote/tally work per block (`MaxVotesProcessedPerBlock = 1000`) but leaves deposit refund/deletion completely unbounded, an attacker who fans out tens of thousands of 1-account deposits onto one proposal can force `EndBlocker` to perform tens of thousands of KV-store reads/deletes plus bank transfers/events in the single block where that proposal's voting period ends. This synchronous, unbounded work executes inside block processing (not inside a per-tx gas meter), so it does not fail with an out-of-gas panic — instead it inflates wall-clock EndBlock processing time, which can push block production past the network's block-time budget (block delay beyond 2.5 seconds), a chain-liveness impact explicitly in scope. It also mirrors the original "refund DoS" pattern: cheap attacker-created records force expensive administrative draining logic with no cap.

### Likelihood Explanation
Likelihood is moderate-to-high: creating many accounts and submitting minimal-value `MsgDeposit` transactions requires no special privilege, no validator/consensus compromise, and no governance majority — only paying per-tx fees, which can be made arbitrarily cheap relative to the resulting EndBlock cost since deposit amount has no floor. The trigger condition (a targeted proposal's voting period ending) is fully attacker-controllable by the attacker submitting and depositing on their own proposal.

### Recommendation
Apply the same bounded-batch pattern already used for `IterateActiveProposalsQueue`/`TallyIncremental` to deposit refunding and deletion: cap the number of deposit records processed by `RefundDeposits`/`DeleteDeposits` per block (persisting a cursor to resume in subsequent blocks), and/or enforce a minimum per-deposit amount (or minimum number of unique depositors cost) so that inflating record count is not economically free relative to the resulting refund/delete cost.

### Proof of Concept
1. Submit a governance proposal with `MsgSubmitProposal`.
2. From N distinct funded accounts (N large, e.g. tens of thousands), each submits `MsgDeposit{ProposalId: id, Amount: 1usei}` — each creates a new, distinct `Deposit` record since dedup key is `(proposalID, depositor)`.
3. Let the proposal's voting period end (or ensure it fails to meet the minimum deposit so it's deleted while inactive).
4. In the `EndBlock` that transitions the proposal, `keeper.RefundDeposits`/`keeper.DeleteDeposits` iterates and processes all N deposit records with no per-block cap, in contrast to the capped `TallyIncremental`/`MaxVotesProcessedPerBlock` path in the same function, causing that block's processing time to spike proportionally to N.

func (keeper Keeper) DeleteDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		err := keeper.bankKeeper.BurnCoins(ctx, types.ModuleName, deposit.Amount)

			panic(err)
		}

// AddDeposit adds or updates a deposit of a specific depositor on a specific proposal
// Activates voting period when appropriate
func (keeper Keeper) AddDeposit(ctx sdk.Context, proposalID uint64, depositorAddr sdk.AccAddress, depositAmount sdk.Coins) (bool, error) {
	// Checks to see if proposal exists
	proposal, ok := keeper.GetProposal(ctx, proposalID)
	if !ok {
		return false, sdkerrors.Wrapf(types.ErrUnknownProposal, "%d", proposalID)
	}

	// Check if proposal is still depositable
	if (proposal.Status != types.StatusDepositPeriod) && (proposal.Status != types.StatusVotingPeriod) {
		return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
	}
	if keeper.IncrementalTallyEnabled(ctx) && proposal.Status == types.StatusVotingPeriod {
		if proposal.VotingEndTime.Before(ctx.BlockTime()) || keeper.voteDelegationSnapshotFrozen(ctx, proposal) {
			return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
		}
	}

	// update the governance module's account coins pool
	err := keeper.bankKeeper.SendCoinsFromAccountToModule(ctx, depositorAddr, types.ModuleName, depositAmount)
	if err != nil {
		return false, err
	}

	// Update proposal
	proposal.TotalDeposit = proposal.TotalDeposit.Add(depositAmount...)
	keeper.SetProposal(ctx, proposal)

	// Check if deposit has provided sufficient total funds to transition the proposal into the voting period
	activatedVotingPeriod := false

	if proposal.Status == types.StatusDepositPeriod && proposal.TotalDeposit.IsAllGTE(keeper.GetDepositParams(ctx).GetMinimumDeposit(proposal.IsExpedited)) {
		keeper.ActivateVotingPeriod(ctx, proposal)

		activatedVotingPeriod = true
	}

	// Add or update deposit object
	deposit, found := keeper.GetDeposit(ctx, proposalID, depositorAddr)

	if found {
		deposit.Amount = deposit.Amount.Add(depositAmount...)
	} else {
		deposit = types.NewDeposit(proposalID, depositorAddr, depositAmount)
	}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}
