Based on my investigation, I found a structurally similar analog to the Bunni idle-balance bug in the Intent Gateway's same-chain partial-fill escrow accounting.

### Title
Partial-fill escrow release uses the order-declared input amount instead of the tracked escrow balance, breaking the fixed-ratio assumption for fee-on-transfer or under-collateralized escrow tokens - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` computes the amount of escrowed input tokens to release to a solver on a partial fill by scaling the **static, order-declared** `order.inputs[i].amount` by the fill ratio (`fillAmount / totalRequired`), rather than scaling the **live** `_orders[commitment][token]` escrow balance. This assumes `_orders[commitment][token]` always equals `order.inputs[i].amount` for the lifetime of the order — the same "amount deposited equals amount recorded" assumption that the Bunni report shows can be silently broken.

### Finding Description
In `IntrinsicIntents.sol`: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

On the *final* fill, the code correctly reads the live tracked balance `_orders[commitment][token]` (this is the fix for the rounding-dust class of bug, per the `Finding #4` test comments). But on every *partial* fill before the last one, it derives the release amount purely from the immutable `order.inputs[i].amount` field carried in calldata — a value fixed at order-placement time and baked into the EIP-712/keccak commitment — multiplied by the fill ratio.

This mirrors the Bunni bug precisely: the deposit logic assumed idle-balance/ratio invariants hold based on a value computed once, without validating that the real underlying balance still matches that assumption after a fee or discrepancy is introduced. Here, the invariant `_orders[commitment][token] == order.inputs[i].amount` is assumed to hold from placement through every partial fill, but nothing in `_withdraw`/`_orders` accounting re-derives or checks it — `_orders[commitment][token]` is only ever decremented, never used to *bound or validate* the per-fill release amount until the very last fill.

If the amount actually escrowed for a given input token (`_orders[commitment][token]`) is ever less than `order.inputs[i].amount` — for example, because the input token takes a transfer fee (fee-on-transfer ERC-20) so the contract received less than the nominal `amount` credited to `_orders` at placement, or because of any other path where the credited/nominal amount diverges from the real token balance held — then every partial-fill release computed from the stale `order.inputs[i].amount` figure over-releases funds relative to the real backing balance. Each partial solver drains proportionally more than their true entitled share of the *actual* escrow, and the final fill's `_orders[commitment][token]` read will underflow or leave the last solver with less than expected, since `_withdraw` decrements `_orders[commitment][token]` unconditionally: [2](#0-1) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();

_orders[body.commitment][token] = escrowed - amount;
```

An `escrowed - amount` underflow reverts (Solidity 0.8 checked arithmetic), so the practical failure mode is that early partial-fill solvers drain the real balance faster than the nominal ratio implies, and the last solver(s) attempting to complete the order get reverted `UnknownOrder`/underflow, permanently locking their fill and the remaining real balance in a state where the order can never be completed (denial of settlement / fund lock), or — if the discrepancy runs the other way — early solvers under-collect and later solvers absorb the shortfall unfairly.

### Impact Explanation
This breaks the "escrow moves exactly once and only to the rightful beneficiary and amount" invariant central to the bounty scope. Depending on which direction the real-vs-nominal balance diverges:
- Solvers filling early can extract more real tokens per unit of output delivered than their fair proportional share, effectively stealing value from the pool of escrowed funds meant for later solvers/the user's refund.
- Alternatively, the order can become permanently unfillable to completion (a stuck/locked state, since the final branch reads the live balance and any prior over-release causes reverts on completion), locking user funds in escrow indefinitely.

### Likelihood Explanation
This is reachable by any unprivileged solver calling the public `fillOrder` entrypoint with a legitimate order using any ERC-20 token whose escrowed balance can diverge from the amount recorded at placement (e.g., fee-on-transfer tokens, or any order path where `_orders[commitment][token]` is credited with a nominal value distinct from what was actually received/held). No relayer, prover, or admin compromise is required — it is purely a function of the token behavior and the existing partial-fill arithmetic using a stale, non-revalidated `order.inputs[i].amount` instead of the authoritative live escrow ledger.

### Recommendation
Compute the partial-fill escrow release directly from `_orders[commitment][token]` (the live, authoritative escrow balance) using the same fill ratio, instead of the static `order.inputs[i].amount`, e.g.:
```solidity
uint256 currentEscrow = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
escrowedAmount = (currentEscrow * fillAmount) / remaining;
```
so each partial release is proportional to what is actually still escrowed rather than what was nominally declared at placement, eliminating any drift between the recorded ledger and the real backing balance.

### Proof of Concept
Conceptual walk-through (full PoC would need a Foundry test with a fee-on-transfer ERC-20 as the input token, analogous to `ERC4626FeeMock` in the original report):
1. User places an order with `inputs[0] = {token: FeeToken, amount: 1000e6}`; `placeOrder` calls `safeTransferFrom(user, gateway, 1000e6)` but the fee-on-transfer token only delivers e.g. 900e6 to the gateway, while `_orders[commitment][FeeToken]` is nonetheless credited `1000e6` (the nominal declared amount) because the code does not measure the gateway's balance delta.
2. Solver A partially fills 50% of the output. `_fillSameChain` computes `escrowedAmount = (1000e6 * fillAmount) / totalRequired` — i.e., 50% of the *nominal* 1000e6 = 500e6 — and `_withdraw` transfers 500e6 out and decrements `_orders[commitment][FeeToken]` to 500e6, even though the gateway's real FeeToken balance is only 900e6 to begin with (now 400e6 after this transfer).
3. Solver B fully fills the remainder. The final branch reads `_orders[commitment][FeeToken]` (500e6) and attempts to transfer 500e6, but the gateway's real balance is only 400e6 — the transfer reverts, permanently blocking order completion and locking the remaining 400e6 (or, in the reverse-fee-direction case, over-releasing to Solver A at Solver B's/the user's expense).
