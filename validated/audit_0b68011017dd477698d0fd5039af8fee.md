## Analysis Summary

The external report's core invariant is: *"a value derived from user-influenced state must be validated against the actual set of things that legally exist before it is trusted."* In `UF-4`, `_tokenIdCounter.current()` was used to bound a random token id without accounting for "does not exist yet." The Aptos-native analog is the framework's **lazy module initialization** feature (`aptos_framework::init`), which derives a self-init decision for object-hosted modules from a recorded "deploy owner," but conflates two different states — *"this address was never an object"* and *"this address was an object that has since been deleted"* — because both make `object::is_object(addr)` return `false`.

I traced 3 candidate paths (freeze_code_object ownership checks, `check_dependencies` policy-exempted-address wildcard, and `init::assert_may_self_initialize`) and the strongest, with a concrete logic gap supported by the module's own documented invariant, is in `init.move`. [1](#0-0) 

### Title
Lazy module self-initialization fails open for deleted object-hosted modules with no recorded deploy owner - (File: `aptos-move/framework/aptos-framework/sources/init.move`)

### Summary
`init::assert_may_self_initialize` is meant to guarantee — per its own doc comment — that "a module on an object cannot self-initialize once the object changed owner, **or was deleted**, since that module's code was last published." [2](#0-1)  The implementation, however, only enforces this for modules whose `deploy_owner` was actually recorded at publish time. For any address with no recorded owner, it falls back to `!object::is_object(addr)`, treating "no record" as proof the address is a plain account. That assumption fails for an object address that existed and was published to (without a record — e.g., published while `LAZY_MODULE_INITIALIZATION`/lazy recording did not apply) and later had its `ObjectCore` deleted: `object::is_object(addr)` becomes `false` just like an ordinary account, so the guard is satisfied and self-init is allowed on a defunct object address.

### Finding Description
`record_deploy_owner` is only invoked from `code::publish_package` when `features::is_lazy_module_initialization_enabled() && object::is_object(addr)` at publish time. [3](#0-2)  If a module is published to an object address while that condition doesn't hold (feature not enabled at that moment, or race with governance flag rollout), no `deploy_owner` is ever recorded for it — `recorded_deploy_owner` returns `option::none()`. [4](#0-3) 

`assert_may_self_initialize` then computes:
```
let ok = if (recorded.is_some()) {
    object::is_object(addr) && recorded.destroy_some() == root_owner()
} else {
    !object::is_object(addr)
};
``` [5](#0-4) 

The `else` branch is documented and tested as fail-closed only for the "always was a plain account" case (`self_init_allowed_for_account_address`) and correctly fails closed for a *live* object with no record (`self_init_blocked_when_object_has_no_recorded_owner`) — both tests are present. [6](#0-5)  But there is no test — and no code path — distinguishing a *deleted* object with no record from a plain account, because both yield `object::is_object(addr) == false`. In that case `ok = true`, and `internal_maybe_initialize` mints a `signer` for that address. [7](#0-6) 

### Impact Explanation
This falls under the "module-init ... failure that reaches protected state mutation" category. A signer for an address whose object was deleted (and thus should have no owner authority left) can still be minted by anyone invoking the module's public entry points, allowing that module's `init` logic to `move_to`/mutate resources at that formerly object-owned address as if it were still validly self-initializing. This subverts the explicitly documented safety guarantee ("or was deleted ... blocks self-init") for the subset of object-hosted modules that were published without a recorded owner, which is a state reachable simply by publishing before the feature/record path applied.

### Likelihood Explanation
Reaching this requires an object-hosted module with no `deploy_owner` record (achievable at publish time depending on feature-flag state) whose object is later deleted, and then a caller triggering that module's lazy-init entry point. This is a narrower precondition than a fully generic bypass, and I was unable to fully verify the exact runtime semantics of `object::is_object`/`object::delete` in this repo before running out of tool budget (the file `object.move` search for these definitions did not return in the final iteration), so this should be treated as moderate-to-unconfirmed confidence pending direct inspection of `object::is_object` and `object::delete`.

### Recommendation
Track "this address was ever an object" independently of "was a record made," e.g. by recording an explicit `deploy_owner = none` marker (as opposed to "no entry at all") whenever a module is published to any object address, and require `assert_may_self_initialize` to fail closed whenever an `InitializationState` entry exists for the module but carries no matching current owner — rather than relying on `object::is_object` to distinguish "never an object" from "deleted object."

### Proof of Concept
Conceptual reproduction (not verified end-to-end due to inability to confirm `object::is_object`/`delete` internals in this session):
1. Publish a module to an object address at a time when `record_deploy_owner` is not invoked for it (no entry recorded).
2. Delete the object (`object::delete`) — this removes `ObjectCore`, so `object::is_object(addr)` becomes `false`.
3. Call an entry function on that module that calls `init::internal_maybe_initialize`. `recorded_deploy_owner` returns `none`, `object::is_object(addr)` is `false`, so `ok = true`, and a signer for the deleted-object's address is returned, contradicting the documented deletion-blocks-self-init guarantee.

**Confidence note:** I could not complete verification of `object::is_object`/`object::delete` source in this session due to reaching the tool-call limit; this finding should be validated against those definitions before treating it as confirmed.

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }

    /// The object root owner recorded for `module_id` at its last publish, or `none` if the module
    /// has no such record (an account module, or an object module never recorded).
    fun recorded_deploy_owner(addr: address, module_id: ModuleId): Option<address> {
        if (!exists<InitializationState>(addr)) return option::none();
        let modules = &InitializationState[addr].modules;
        if (modules.contains(&module_id)) modules.borrow(&module_id).deploy_owner else option::none()
