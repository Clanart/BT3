### Title
Single-block median fee oracle lets an attacker inflate `needed_fee`, dropping/DOSing scheduled payments - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::median_fee` estimates the fee rate for `SignableTransaction`s from the median per-vbyte fee of transactions in a *single* block — a value any unprivileged party can bias upward by broadcasting high-fee transactions. An inflated estimate flows into `make_signable_transaction` → `BSignableTransaction::new`, which returns `NotEnoughFunds` (yielding `Ok(None)` = no transaction) or causes payments to fall below `DUST` and be silently dropped during fee amortization. This mirrors the Ubiquity finding: a fixed, externally-influenceable estimation input (there, a hardcoded 1-ether `get_dy` probe on a thin pool; here, the median fee of one manipulable block) produces a deviated value that temporarily blocks withdrawals until conditions normalize.

### Finding Description
`median_fee` computes `(in_value - out) / vsize` for every non-coinbase transaction in the block fetched at `block_number`, sorts them, and takes `fees[len / 2]`, flooring at 1 sat/vbyte (`Fee(fee.max(1))`). There is no upper bound, no averaging across blocks (the code even notes `TODO2: Use an fee representative of several blocks`), and no sanity cap. [1](#0-0) 

`make_signable_transaction` uses this fee for both the dry-run (`calculating_fee = true`, used by `needed_fee`) and the real transaction (`calculating_fee = false`). [2](#0-1) 

Inside `SignableTransaction::new`, `needed_fee = fee_per_vbyte * vbytes`; if `input_sat < payment_sat + needed_fee` it returns `NotEnoughFunds`, which `make_signable_transaction` maps to `Ok(None)` — no signable transaction is produced for that attempt. [3](#0-2) 

Even when inputs cover the inflated fee, the scheduler amortizes the fee across payments and zeroes any payment that ends below `N::DUST` (10,000 sats for Bitcoin), then drops it. [4](#0-3) 

### Impact Explanation
- Payments whose summed value cannot cover the inflated `needed_fee` produce `Ok(None)` from `signable_transaction`/`needed_fee`, stalling the corresponding plan for that block — a temporary withdrawal DOS, exactly the report's "withdrawals blocked until conditions normalize" impact.
- Payments that do proceed pay a fee far above market rate, and borderline payments are pushed below `DUST` and dropped, permanently removing them from the plan rather than delaying them.

### Likelihood Explanation
An attacker controls the median by ensuring more than half of a block's non-coinbase transactions carry a high fee rate. This costs real satoshis (attacker pays the fees), so it is an economic rather than free attack, but it requires no privileged position — any Bitcoin user can submit transactions, matching the allowed input surface ("Bitcoin transactions they send"). Persistence is limited to blocks the attacker can dominate, hence Medium: bounded-cost, temporary disruption of the signing pipeline plus possible silent payment drops.

### Recommendation
- Compute the fee over multiple recent blocks (e.g., a rolling median over N blocks), and/or cap the estimate at a configured maximum acceptable fee rate.
- On `NotEnoughFunds` due to fee spikes, retry payments in a later plan rather than producing `None` indefinitely.
- Refuse to silently drop payments pushed below `DUST` by a transient fee spike; requeue them when the estimate normalizes.

### Proof of Concept
1. A plan is scheduled with payments summing to `P` sats and inputs summing to `I` where `I - P` is modest.
2. In the block the processor samples for `block_number`, the attacker floods >50% of non-coinbase transactions with, e.g., 1000 sat/vbyte fees (paying the cost themselves).
3. `median_fee` returns ~1000 sat/vbyte. For a ~200-vbyte transaction, `needed_fee` ≈ 200,000 sats.
4. `BSignableTransaction::new` computes `input_sat < payment_sat + needed_fee` → `NotEnoughFunds` → `Ok(None)`; no withdrawal transaction is signed or broadcast for that attempt.
5. If `I` does cover it, the amortization loop in `processor/src/networks/mod.rs` (lines ~480-530) subtracts the inflated fee proportionally; any payment reduced below 10,000 sats is set to 0 and dropped, so funds that would have been paid out are instead burned as fee.

  async fn median_fee(&self, block: &Block) -> Result<Fee, NetworkError> {
    let mut fees = vec![];
    if block.txdata.len() > 1 {
      for tx in &block.txdata[1 ..] {
        let mut in_value = 0;
        for input in &tx.input {
          let mut input_tx = input.previous_output.txid.to_raw_hash().to_byte_array();
          input_tx.reverse();
          in_value += self
            .rpc
            .get_transaction(&input_tx)
            .await
            .map_err(|_| NetworkError::ConnectionError)?
            .output[usize::try_from(input.previous_output.vout).unwrap()]
          .value
          .to_sat();
        }
        let out = tx.output.iter().map(|output| output.value.to_sat()).sum::<u64>();
        fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
      }
    }
    fees.sort();
    let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);

    // The DUST constant documentation notes a relay rule practically enforcing a
    // 1000 sat/kilo-vbyte minimum fee.
    Ok(Fee(fee.max(1)))
  }
