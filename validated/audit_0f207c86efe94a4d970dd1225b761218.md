### Title
Double-application of bank balance-change events to EVM StateDB during nested/recursive precompile calls causes EVM balance to desync (inflate) from native bank balance - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The external report describes a bug where `RevenueTraderP1.manageToken` reads a stale, un-refreshed exchange rate because an actor can call `assetRegistry.refresh()` before `manageToken`, causing `furnace.melt()` to be skipped and the sell price to be computed from stale state. The Cosmos EVM analog is a state-synchronization ordering bug in the precompile → StateDB balance-sync mechanism: `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` [1](#0-0)  tracks bank events using a raw event-log index (`prevEventsLen`) rather than a properly scoped/consumed cursor. When a precompile's native action recursively triggers another balance-changing precompile call (or bank operation) within the same EVM call frame, the outer call's `AfterBalanceChange` re-scans and re-applies bank events that an inner/nested call already applied to the `StateDB`, producing a duplicated `AddBalance`/`SubBalance` on the EVM state without a matching duplicate movement of real bank coins.

### Finding Description
`RunNativeAction`/`runNativeAction` records the event-log length before executing the precompile's native action and, after execution, replays every bank event emitted since that length onto the EVM `StateDB` via `AddBalance`/`SubBalance` [2](#0-1) . The `BalanceHandler.AfterBalanceChange` walks `events[bh.prevEventsLen:]` and unconditionally applies every `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` event found in that window to the StateDB [3](#0-2) .

This design assumes the event window recorded by one precompile invocation is never touched by another `BeforeBalanceChange`/`AfterBalanceChange` pair. That assumption breaks when a precompile's native action itself performs an EVM call (e.g., `evmKeeper.CallEVMWithData`) that re-enters another precompile (or itself) which also emits bank events and runs its own `BeforeBalanceChange`/`AfterBalanceChange` cycle on the *same* underlying event manager/context. The debug precompile in the repo demonstrates exactly this recursive-call pattern (`Call0` invokes `CallEVMWithData` back to the same precompile address) [4](#0-3) , and a dedicated integration test explicitly documents the resulting defect: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [5](#0-4) 

In the vulnerable pattern (also present in the still-existing `testutil/testdata/debug/debug.go` file that calls a shared `p.GetBalanceHandler()` rather than allocating a fresh handler per call) [6](#0-5) , the outer call's `prevEventsLen` is captured *before* the nested call runs. When the nested call finishes its own `AfterBalanceChange` (applying its bank events to StateDB) and returns, the outer call's later `AfterBalanceChange` still iterates from its own, earlier, `prevEventsLen` through the current event length — which now also contains the events already consumed and applied by the nested call. The result is that the same `coin_spent`/`coin_received` delta is applied to the `StateDB` twice, inflating (or deflating) the EVM-visible balance of an address relative to its actual `x/bank` balance.

### Impact Explanation
This breaks the core invariant that native bank coin balances and EVM `StateDB` balances must remain 1:1 consistent (the asset-representation invariant explicitly called out for `x/erc20`/bank/precompile flows). A contract that triggers nested/recursive precompile calls that emit bank balance-change events (e.g., a precompile call whose native action performs a `bankKeeper` transfer and then calls back into another balance-changing precompile in the same transaction) can cause the EVM `StateDB` to record more (or less) native coin balance than actually exists in `x/bank`. Because EVM balance is spendable (usable for `value` transfers, gas, and downstream contract logic) this constitutes unauthorized duplication/creation of spendable value on the EVM side without a corresponding real bank-side backing — a critical accounting corruption matching the "unauthorized minting/duplication ... of spendable user value across native balances, EVM balances" impact category.

### Likelihood Explanation
Triggering requires only an unprivileged user deploying/calling a contract that invokes a precompile whose native action performs a nested EVM call into another (or the same) balance-changing precompile — no privileged access is required. The repository's own test suite was purpose-built to reproduce this exact "recursive precompile calls" scenario, indicating the maintainers consider it a real, reachable condition under the current precompile call architecture [7](#0-6) .

Note: I could not conclusively determine within available tool calls whether `stateDB.GetCacheContext()` (used to obtain the `ctx` in `runNativeAction`) produces a fresh, isolated `EventManager` for every nested precompile invocation, or whether it shares the outer context's underlying event log across nested calls. If the cache context always resets the event manager to zero length for every call, this specific double-application path would not manifest via `RunNativeAction`'s production code path (only the deprecated/test-only `GetBalanceHandler` pattern would be affected). This should be verified directly against `statedb.StateDB.GetCacheContext` / `CommitWithCacheCtx` semantics before treating this as fully confirmed in production precompiles (staking, distribution, gov, ics20, erc20, slashing) versus only in the test/debug precompile code paths.

### Recommendation
- Ensure each precompile invocation (including nested/re-entrant ones) operates against an EventManager scope that cannot be observed or re-consumed by an outer/ancestor call — e.g., by having `BeforeBalanceChange`/`AfterBalanceChange` consume (truncate/mark) events rather than merely recording a length that can be invalidated by nested consumption.
- Do not allow a shared/singleton `BalanceHandler` instance (as in the `GetBalanceHandler()` pattern) to be reused across nested precompile calls; always allocate a call-scoped handler as `RunNativeAction` already attempts, and additionally guard against outer handlers re-scanning events already consumed by an inner handler.
- Add an invariant check (e.g., after tx execution) that the aggregate EVM `StateDB` balance delta for the native denom equals the aggregate real `x/bank` balance delta for the same addresses within the same transaction, to catch any divergence.
- Remove or fix the stale `testutil/testdata/debug/debug.go` (which still uses the vulnerable `GetBalanceHandler()` pattern) so it cannot be mistaken for a safe example.

### Proof of Concept
The repository already contains a working reproduction:
1. Deploy `DebugPrecompileCaller` and register the debug precompile, per `evmd/tests/integration/balance_handler/balance_handler_test.go` [8](#0-7) .
2. Call `callback(0)` on the caller contract, which drives the debug precompile's `Call0` to recursively `CallEVMWithData` back into itself [4](#0-3) , each recursion level running its own `BeforeBalanceChange`/`AfterBalanceChange` cycle over a shared/overlapping event window.
3. The test asserts on emitted event counts to reveal the aberrant handling of the balance-change event window across recursion levels [9](#0-8) .

To turn this into a fund-duplication PoC on a production (non-debug) precompile, one would need to identify a stateful precompile whose native action both emits a `bank` balance-change event and performs a nested EVM call into another balance-changing precompile within the same call — I was not able to fully confirm this exists among the production precompiles (`staking`, `distribution`, `gov`, `slashing`, `erc20`, `ics20`) within available tool calls, due to running out of iterations to trace `GetCacheContext`/`CommitWithCacheCtx` event-manager isolation semantics precisely.

```go
// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

```

```go
// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug

	// Create and register debug precompile

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()
```
