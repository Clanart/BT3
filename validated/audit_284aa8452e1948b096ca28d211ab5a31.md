## Finding

### Title
Stale line-selection indices used against a freshly re-fetched diff can silently stage/commit different content than the user selected - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The Rubicon bug is a classic "assumed quantity ≠ actual quantity" defect: `BathHouse` computes `initialLiquidityNew` from the amount it *intended* to transfer and later uses that stale number to drive a `deposit()` call, without re-checking the *actual* balance the contract holds after the (fee-taking) transfer completed [1](#0-0) . The analogous broken invariant in GitHub Desktop is that the partial-commit/patch-generation code assumes a `WorkingDirectoryFileChange`'s line-selection state (built by index against one diff) is still valid against a **different diff object fetched later**, without re-validating that the two diffs describe the same content.

### Finding Description
When staging files for a commit, `stageFiles` calls `applyPatchToIndex` for every file that has a partial (line-level) selection [2](#0-1) . `applyPatchToIndex` re-fetches the diff from disk at that moment:

```
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
``` [3](#0-2) 

`formatPatch` then decides which lines to include using `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is computed purely from the position of the line inside the *newly fetched* diff's hunks:

```
const absoluteIndex = hunk.unifiedDiffStart + lineIndex
...
} else if (file.selection.isSelected(absoluteIndex)) {
``` [4](#0-3) 

`file.selection`, however, was populated earlier by the UI against the diff that was *displayed* to the user (the "Changes" list diff), not against this freshly re-parsed diff. There is no check anywhere in this path that the diff used to build the selection and the diff used to build the patch are the same diff (no content hash, no hunk-header equality check, nothing analogous to re-reading `balanceOf` before trusting a transfer amount). `DiffHunkHeader.equals` even exists in the model but is never consulted here [5](#0-4) .

If the tracked file's on-disk content changes between the moment the user reviews/selects lines and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs (e.g. because a Git filter such as an LFS/`clean`/`smudge` driver bundled with Desktop rewrites the file, or because another concurrent git operation touches the working tree), the new diff's hunk boundaries and per-line indices can differ from what produced `file.selection`. The same absolute index now points at a different line, so `formatPatch`/`formatPatchToDiscardChanges` will silently include lines the user never approved, or drop lines the user explicitly wanted committed — without any error, since git's `apply --cached` will happily accept a syntactically valid but semantically wrong patch.

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes": the user could deliberately deselect a line (e.g. one containing a secret, a debug credential, or unwanted content) and still have it committed and pushed because the index used to test selection no longer refers to the line they saw. Conversely, a line the user wanted included could be dropped. Because this happens inside `git apply --cached` with no diagnostic, the user has no visibility that the committed diff differs from what they approved in the UI.

### Likelihood Explanation
Likelihood is **low-to-medium**. It requires the tracked file's on-disk bytes to change between diff-display time and commit time without the user noticing (e.g. via a repository-defined content filter such as `filter=lfs`/custom clean-smudge drivers referenced in `.gitattributes`, which GitHub Desktop's bundled Git/Git-LFS will invoke automatically on checkout/stage), or an external process racing the commit. Unlike the Rubicon bug (deterministic, triggers on every deflationary token), this needs a timing/content-mutation condition that a malicious repository can *attempt* to induce via attributes/filters but cannot fully guarantee will land inside this exact window every time. I could not find any explicit re-validation logic (hash/hunk-header comparison) guarding this path, which is the concrete missing guard analogous to the missing `balanceOf` re-check in the original report.

### Recommendation
- Before using `file.selection` against a newly parsed diff in `applyPatchToIndex`/`formatPatch`/`formatPatchToDiscardChanges`, verify that the diff's hunk headers (or a content hash of the diff) match the diff the selection was computed against; if they differ, abort staging and force the UI to refresh the diff and clear/re-map the selection.
- Alternatively, pass the diff object (not just the file's selection) through the full commit pipeline as a single, immutable unit fetched once, and re-diff+re-render the changed file to the user for re-confirmation if the working tree changes before commit.
- Add an integrity check that the number of context/added/removed lines actually written into the hunk (`oldCount`/`newCount`) is consistent with the header extracted from the *live* diff, failing loudly instead of silently producing a patch from mismatched indices.

### Proof of Concept
Conceptual reproduction (exact reliable PoC would require crafting a Git filter/hook that mutates the working file between two `getWorkingDirectoryDiff` calls; I could not fully verify a guaranteed trigger window from static analysis alone, so this is presented as a code-path proof rather than an exploited runtime PoC):
1. Malicious repository ships a tracked text file with a `.gitattributes` entry wiring it to a `clean`/`smudge` filter (e.g. `filter=lfs`) that is already configured on the victim's machine (Desktop ships/configures Git LFS).
2. Victim opens the file's diff in Desktop and deselects one line (e.g. a line containing a secret) — `file.selection` is built against diff *D1*.
3. Between that action and clicking "Commit", the filter driver rewrites the working-tree content (this can occur on any subsequent checkout/refresh Desktop triggers, e.g. background status refresh performing an implicit `git checkout`/smudge re-application).
4. `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff, now *D2*, with shifted hunk boundaries [1](#0-0) .
5. `formatPatch` applies `file.selection` (built for D1) to D2's line indices [4](#0-3) , silently including the previously deselected secret line in the resulting commit.
