### Title
Missing event emission on `SimplexPaymaster._withdrawAssets` treasury sweep - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster.onAccept` dispatches five governance actions gated by `RequestKind`. Four of them (`_setParams`, `_registerToken`, `_deactivateToken`) emit dedicated events documenting the state change, matching the report's underlying complaint about `initRedeemToken`. The fifth, `_withdrawAssets`, moves real funds — either the EntryPoint deposit or an ERC-20 surplus balance — to `treasury`, but emits no event at all. [1](#0-0) 

### Finding Description
`onAccept` decodes `RequestKind.WithdrawAssets` and calls `_withdrawAssets(token, amount)`: [2](#0-1) 

```solidity
function _withdrawAssets(address token, uint256 amount) internal {
    if (token == address(0)) {
        entryPoint().withdrawTo(payable(treasury), amount);
    } else {
        IERC20(token).safeTransfer(treasury, amount);
    }
}
``` [3](#0-2) 

Every other governance path in this file — `_setParams` (`ParamsUpdated`), `_registerToken` (`TokenRegistered`), `_deactivateToken` (`TokenDeactivated`) — emits an event immediately after the state mutation: [4](#0-3) 

Only `_withdrawAssets`, the one function that actually transfers value out of the contract, has no corresponding emission. This directly mirrors the reported class: a sensitive fund-moving action performed silently, with no on-chain audit trail for off-chain monitors, indexers, or governance dashboards to detect or reconcile.

### Impact Explanation
Under the stated impact gate this alone is not "stealing or loss of funds" or "false proof/state acceptance" — the transfer is still gated by `onlyHost` + Hyperbridge-source authentication in `onAccept`, so an unprivileged attacker cannot trigger the withdrawal themselves. However, the missing event materially weakens the operational-security guarantees the rest of the contract deliberately builds in: the contract's own documentation states "every administrative action ... is an onAccept request authenticated as originating from Hyperbridge governance," implying observability is part of the trust model. Without `Withdrawn`-style event, off-chain indexers/relayers/monitoring cannot detect or alert on treasury sweeps, silently degrading the detectability of a compromised governance path (e.g., a malicious or buggy governance proposal draining the EntryPoint deposit or ERC-20 surplus) until balances are manually checked. This is a low-severity, defense-in-depth / observability gap rather than a fund-loss primitive on its own.

### Likelihood Explanation
Every legitimate call to `_withdrawAssets` goes through the normal governance-triggered `WithdrawAssets` path and always hits this code, so the missing event fires (or rather, fails to fire) on every single treasury withdrawal — 100% of intended usage, not an edge case. No malicious actor is required to trigger it; it is a deterministic gap in the codebase.

### Recommendation
Add a `Withdrawn(address indexed token, address indexed beneficiary, uint256 amount)` event (mirroring `BandwidthManager.sol`'s existing `Withdrawn` event pattern) and emit it inside `_withdrawAssets` after the transfer/withdrawTo succeeds, so treasury sweeps are auditable on-chain, consistent with every other governance action in the contract.

### Proof of Concept
1. Deploy `SimplexPaymaster` and register a token/oracle via `RequestKind.RegisterToken` (observe `TokenRegistered` event fires).
2. Accumulate an ERC-20 surplus balance in the paymaster (e.g., via normal `_postOp` fee collection).
3. Deliver an `onAccept` request with `RequestKind.WithdrawAssets` for that token/amount to `treasury`.
4. Observe on-chain: `treasury`'s balance increases, `IERC20.Transfer` event is emitted by the token contract itself, but no `SimplexPaymaster`-level event records the withdrawal — compare against `_registerToken`/`_deactivateToken`/`_setParams` calls in the same test, which each emit a dedicated `SimplexPaymaster` event.
5. Confirm via `evm/tests/foundry/` test coverage (or a new test) that no `Withdrawn`/similar log is asserted or exists, whereas equivalent tests for `BandwidthManager.sol`'s `Withdraw` action do assert on `Withdrawn`. [5](#0-4)
