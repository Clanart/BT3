### Title
On-path attacker can frame honest DKG participants for fatal slashing via unauthenticated share-ciphertext malleation - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2022-21287 describes an attacker positioned on the communication segment compromising a cluster. The direct analog in Serai is the PedPoP DKG share channel: `EncryptedMessage` uses ChaCha20 as a bare keystream XOR (`apply_keystream`) with no MAC, and the only integrity/authenticity check on the ciphertext is the sender's Schnorr proof-of-possession, which is verified inside the blame path itself. A MITM who flips any bit of a secret-share ciphertext causes the recipient's `calculate_share` to raise `InvalidShare`, and the subsequent blame adjudication (`blame_internal` / `decrypt_with_proof`) resolves the fault as the **sender's**, because the corrupted ciphertext cannot have a valid PoP. The honest sender is then reported as fatally faulty (`ProcessorMessage::Blame`).

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, shares are encrypted with `cipher().apply_keystream()` (lines 130, 154, 488), i.e., raw ChaCha20 with no authentication tag. The `pop` Schnorr signature binds `(context, key, sender, msg)` via `pop_challenge` (lines 302-324), but it is only verified at the very end of adjudication, inside `Decryption::decrypt_with_proof` (lines 374-379) — where `DecryptionError::InvalidSignature` returns `sender` as the faulty party in `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:582-585`).

The concrete flow:

1. MITM intercepts an `EncryptedMessage<C, SecretShare>` from honest participant `s` to `r` and flips a bit in `msg` (the ciphertext).
2. `r`'s `KeyMachine::calculate_share` queues the PoP in the batch under `BatchId::Decryption(s)`; the batch fails, so `r` emits `InvalidShare { participant: s, blame: None }` (`lib.rs:493-499`).
3. The coordinator calls `VerifyBlame`; `blame` is `None`, so `decrypt_with_proof` verifies `msg.pop` directly (no ECDH proof needed). Since the ciphertext was altered, the signature check fails → `InvalidSignature` → `sender` (`s`) is returned as faulty (`encryption.rs:374-379`, `lib.rs:584-585`).
4. `processor/src/key_gen.rs:504-560` returns `ProcessorMessage::Blame { participant: accused }` — the honest sender is slashed.

The code comments themselves acknowledge the channel is only "assumed-to-exist external authenticated" (`encryption.rs:300-301`), but the blame mechanism then *punishes* honest participants for channel corruption, turning a passive integrity failure into an attribution oracle against the wrong party.

### Impact Explanation
A network-adjacent attacker (matching the CVE's `AV:A` communication-segment model, and reachable via untrusted bytes into `EncryptedMessage::read` at `processor/src/key_gen.rs:409,508`) can repeatedly corrupt share messages so that honest senders are adjudicated faulty and fatally slashed on every DKG attempt. By selectively framing participants, the attacker can expel honest validators from a session/attempt and bias which participants survive key generation — an analogue of "takeover" of the threshold set. Alternatively, corrupting a valid share so the recipient computes garbage yields inconsistent group-key views (denial / unspendable-key outcomes).

### Likelihood Explanation
Requires man-in-the-middle positioning between two DKG participants during the share-distribution round — difficult but precisely the attacker model the CVE assigns a Medium severity to (`AC:H`, `AV:A`). No cryptographic break is needed; a single bit flip suffices, and the DKG runs over authenticated-but-not-integrity-protected-by-design channels where the protocol explicitly delegates transport security to the environment.

### Recommendation
Authenticate the full `EncryptedMessage` (key ‖ pop ‖ ciphertext) under a key derived at DKG registration, or append a MAC keyed by the ECDH secret so ciphertext tampering is detectable *before* blame attribution. Distinguish "transport corruption" from "sender fault" in `blame_internal` — e.g., require the accuser's `EncryptionKeyProof` and verify the PoP against the *decrypted* transcript, or include the recipient in `pop_challenge` plus a MAC so a MITM cannot convert channel corruption into a signature failure attributable to the sender.

### Proof of Concept
1. Run a PedPoP DKG with `t`/`n` over a relay the attacker controls.
2. For a chosen honest sender `s`, take the serialized `EncryptedMessage<C, SecretShare>` destined for `r` (parsed via `EncryptedMessage::read`) and XOR one bit into the trailing ciphertext bytes (the `msg` field after `key` and `pop`).
3. Forward to `r`. `r`'s `calculate_share` fails `batch_verify` on `BatchId::Decryption(s)`, emitting `InvalidShare { participant: s, blame: None }`.
4. `VerifyBlame` → `decrypt_with_proof(s, r, msg, None)` → `msg.pop.verify(...)` fails → `InvalidSignature` → `blame_internal` returns `s` → `ProcessorMessage::Blame { participant: s }`. Honest `s` is reported for slashing, exactly as in `tests.rs`'s `invalid_ecdh_blame` flow, but caused by an on-path party rather than a faulty participant.
