### Title
stSTX Price Always Rounds Down Regardless of Debt vs. Collateral Context, Underestimating Debt Value — (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `resolve-ststx` price transformation always rounds down when converting the STX price into an stSTX price, regardless of whether that price is subsequently used to value stSTX as **collateral** (where rounding down is safe/conservative) or as **debt** (where rounding down under-values what the borrower owes). Since stSTX is a borrowable asset in the deployed configuration (`CAP-STSTX-DEBT` is non-zero), this is the same rounding-direction bug class as the Ramses report: a single rounded value is reused for both the "add" and "subtract" side of a health/debt calculation without flipping the rounding direction to always favor the protocol.

### Finding Description
`resolve-ststx` computes the stSTX price by multiplying the STX price by the staking ratio and always rounding down: [1](#0-0) 

This single price value is then plugged into `calculate-asset-notional-value`, which does apply a `round-up` flag — but only to the second-stage multiplication (`amount * price`, then divided by decimals via `normalize`). It correctly rounds collateral notional down and debt notional up at that stage: [2](#0-1) 

However, the `price` itself — already baked with a "round down" bias from `resolve-ststx` — is treated as a fixed input to both branches. For collateral, "price rounds down" is the conservative, protocol-favoring direction. For debt, "price rounds down" is the *wrong* direction: it under-states the USD value of what the borrower owes, exactly the "value favors the user instead of the platform" pattern described in the Ramses report, just applied to the price-resolution stage instead of the `secondsDebtDeltaX96` stage.

The same one-directional-rounding pattern also exists in `resolve-ztoken` (`div-down`), used for the zToken callcodes (`CALLCODE-ZSTX`, `CALLCODE-ZSBTC`, `CALLCODE-ZSTSTX`, `CALLCODE-ZUSDC`, `CALLCODE-ZUSDH`, `CALLCODE-ZSTSTXBTC`): [3](#0-2) 

stSTX is confirmed to be a debt-enabled asset in the mainnet initialization proposal (non-zero borrow cap), so the debt path through `resolve-ststx` is reachable in production, not merely a theoretical/disabled configuration: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because the stSTX price used for **debt** valuation is always rounded down (never up), every borrower's stSTX-denominated debt is systematically undervalued in USD terms in `get-notional-evaluation` / `calculate-asset-notional-value`. This directly affects health-factor and liquidation-threshold checks that rely on `debt-total`: a borrower's real debt burden is understated, letting them borrow more than intended and delaying/avoiding liquidation while actually under-collateralized. At scale and repeated across many positions/blocks, this can lead to protocol insolvency (bad debt not caught by liquidation), which falls under the **Critical** impact class (protocol insolvency), or at minimum under-recovery on liquidation of stSTX debt positions (theft of protocol funds), which is **High**.

### Likelihood Explanation
The rounding error itself is guaranteed to occur on every single stSTX price resolution used for debt (deterministic, not probabilistic), since `mul-div-down` never rounds up. The magnitude per call is small (integer division truncation), but it applies to every debt valuation of every stSTX-borrowing account on every accrual/health check, and the bias is unidirectional (always favors the borrower), so it does not average out — it can be amplified by repeated borrow/health-check cycles or by protocol size. This mirrors exactly the concern raised in the referenced Ramses report about small, non-amplifiable-seeming rounding errors being dangerous when consistently biased in one direction.

### Recommendation
Make the price-resolution rounding direction context-aware, the same way `normalize`'s `round-up` parameter already is:
- Thread a `round-up` parameter into `resolve-ststx` (and `resolve-ztoken`) so that when the resolved price feeds a **debt** valuation, the internal `mul-div`/`div` operation rounds up, and when it feeds a **collateral** valuation, it rounds down.
- Ensure `price-resolve` / `resolve-callcode` propagate this flag from the caller (`calculate-asset-notional-value`, liquidation math, etc.) instead of using a single, context-agnostic rounding direction baked into the oracle callcode transform.

### Proof of Concept
1. stSTX/STX staking ratio and STX price combine via `resolve-ststx`: `price = mul-div-down(stx_price, ratio, STSTX_RATIO_DECIMALS)`, which truncates any fractional remainder — always rounding down. [1](#0-0) 
2. A user borrows stSTX (debt-enabled per `CAP-STSTX-DEBT`). [4](#0-3) 
3. `get-notional-evaluation` calls `calculate-asset-notional-value`, which computes `debt-notional = normalize(actual * price, decimals, true)` — the `true` (round-up) only affects the final division, not the already-truncated `price` value produced in step 1. [6](#0-5) 
4. The resulting `debt-total` is systematically lower than the true USD value of the debt, every time it's computed, letting the account appear healthier than it actually is in LTV/liquidation checks that consume `debt-total`.

(define-private (calculate-asset-notional-value
          (asset-entry {
              id: uint, addr: principal, decimals: uint,
              oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
              collateral: bool, debt: bool, price: uint })
          (acc { clist: (list 64 { aid: uint, amount: uint }),
                  dlist: (list 64 { aid: uint, scaled: uint }),
                  coll-total: uint,
                  debt-total: uint }))
  (let ((asset-id (get id asset-entry))
        (price (get price asset-entry))
        (decimals (get decimals asset-entry))
        (collateral-list (get clist acc))
        (debt-list (get dlist acc))
        (coll-amount (find-collateral-amount collateral-list asset-id))
        (coll-notional (if (> coll-amount u0)
                           (normalize (* coll-amount price) decimals false)
                           u0))

        (debt-scaled   (find-debt-scaled debt-list asset-id))
        (debt-notional (if (> debt-scaled u0) ;; use cache instead here
                           (let ((cached (unwrap-panic (accrue-and-cache asset-id)))
                                 (ib (get index cached))
                                 (actual (mul-div-up debt-scaled ib INDEX-PRECISION)))
                             (normalize (* actual price) decimals true))
                           u0)))

    { clist: collateral-list,
      dlist: debt-list,
      coll-total: (+ (get coll-total acc) coll-notional),
      debt-total: (+ (get debt-total acc) debt-notional) }))

(define-private (normalize (value uint) (decimals uint) (round-up bool))
  (let ((decimal-factor (pow u10 decimals)))
    (if round-up
      (div-up value decimal-factor)
      (div-down value decimal-factor))))
