## Title
`rewards()` view in the distribution precompile lacks the non-payable value check, permanently stranding sent SEI/wei - (File: `precompiles/distribution/distribution.go`)

### Summary
The distribution precompile's `rewards()` method, exposed at the well-known precompile address `0x...1007`, is registered as a `view` function in the Solidity interface but the Go executor never validates that `msg.value` is zero before executing the query. Every other read-only method on the same precompile (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) calls `p.validateInput(value, args, N)`, which internally calls `pcommon.ValidateNonPayable(value)` to reject any call carrying value. `rewards()` is the sole exception.

### Finding Description
In the `Execute` dispatcher, `RewardsMethod` is routed without even passing `value` to the handler: [1](#0-0) 

The `rewards` function itself takes no `value` parameter and performs no payability check, unlike its siblings such as `params`, which explicitly calls `p.validateInput(value, args, 0)` (which enforces `ValidateNonPayable`): [2](#0-1) [3](#0-2) 

The same missing check exists identically across every legacy snapshot of the precompile (v580, v605, v606, v610, v614, v620, v630, v640, v65, v66, v67), showing this is a long-standing, unpatched pattern rather than a one-off regression: [4](#0-3) 

This is corroborated by an explicit comment in the integration test suite acknowledging the gap: [5](#0-4) 

Because the EVM `CALL` opcode allows attaching value to any call regardless of the target function's `view`/non-payable declaration in the ABI, a caller can invoke `rewards(address)` with a non-zero `value`. The Sei EVM->Cosmos precompile bridge debits the sender's EVM balance for that value as part of normal call-value transfer semantics before/independently of the precompile's own logic (as is standard in the precompile framework, evidenced by the `ValidateNonPayable` check existing specifically to reject such transfers on all other view methods). Since `rewards()` never rejects the value and never forwards/credits it anywhere (it only performs a query and packs a response), the transferred usei/wei is stranded — credited to the precompile's own module/contract account with no method to recover it, and debited from the caller with no state update crediting them elsewhere.

### Impact Explanation
Any unprivileged EVM account or contract can call `rewards(address)` with attached value and have that value irrecoverably stranded at the precompile address, since there is no querier logic that returns or accounts for it, and no other function to reclaim funds sent to the distribution precompile module account this way. This is a direct, concrete loss of funds for any caller who (knowingly or via a buggy integrating contract) sends value with this specific call — matching the "possible loss of funds" bug class from the reference report, but reachable purely via a standard EVM transaction to a public precompile rather than an admin migration step.

### Likelihood Explanation
Likelihood is low-to-moderate: exploitation requires a caller (or a contract calling on their behalf) to mistakenly or deliberately attach `value` to a call that the Solidity ABI declares `view`. Some tooling/wallets prevent sending value to `view` functions at the ABI-encoding layer, but raw transactions, low-level `call{value: x}()`, or misconfigured integrating contracts can still trigger it. The bug is a known asymmetry across the entire precompile's method set and every legacy version, indicating no attempt has been made to close the gap despite all sibling query methods enforcing the check.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check (or `p.validateInput(value, args, 1)`) at the start of `rewards()` in `precompiles/distribution/distribution.go` (and mirror the fix in all legacy versions if they remain reachable), rejecting any call to `rewards()` that carries non-zero value, consistent with every other read-only method on this precompile.

### Proof of Concept
1. An EVM account calls the distribution precompile at `0x0000000000000000000000000000000000001007` using the `rewards(address)` selector, via a low-level call such as `distributionPrecompile.call{value: 1 ether}(abi.encodeWithSignature("rewards(address)", delegatorAddress))`.
2. `Execute` in `precompiles/distribution/distribution.go` dispatches to `RewardsMethod`/`p.rewards(ctx, method, args)` without checking `value`. [1](#0-0) 
3. `rewards()` runs the query, packs the output, and returns successfully; the transaction succeeds while the attached value has been transferred to the precompile account with no mechanism inside `rewards()` (or elsewhere in the distribution precompile) to return or account for it. [6](#0-5) 
4. Compare against `params()`, which would revert such a call due to `ValidateNonPayable` inside `validateInput`, confirming `rewards()` is the outlier. [3](#0-2)

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
