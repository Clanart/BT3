## Finding

<br>

### Title
Path-boundary check in `resolveWithin` uses unanchored prefix comparison, allowing symlink-based escape from the intended directory root - (File: `app/src/lib/path.ts`)

### Summary
The report's underlying pattern is a *bounds check that looks correct but is incomplete*: `readMem`/`writeMem` validate 4-byte alignment but never validate that the address stays inside the intended memory region, so a crafted address can land outside the allowed range. The Desktop analog is `_resolveWithin()` in [1](#0-0) , the sole guard used across the app to keep attacker-influenced file paths (conflict file paths from a cloned repo, or a `filepath` query parameter from a deep link) confined to the repository root. It resolves symlinks with `realpath` and then checks containment with a raw string `startsWith`, without requiring a path-separator boundary after the root. That is the same class of defect: a check exists, but it does not enforce the real invariant ("must be *inside* root", not "string starts with root").

### Finding Description
`resolveWithin` is implemented as: [2](#0-1) 

The final line:
```js
return realResolved.startsWith(realRoot) ? resolved : null
```
compares raw strings. `startsWith` has no notion of path segments, so any real path whose *string* begins with `realRoot` passes, even if it is a completely different, sibling directory (e.g. `realRoot = "/Users/victim/Documents/GitHub/project"` and `realResolved = "/Users/victim/Documents/GitHub/project-secrets/id_rsa"` — the latter `startsWith` the former even though it lives outside `project`). A correct check must require `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`.

This function is the single choke point relied on to keep attacker-controlled, repository-relative paths inside the repo before doing filesystem I/O. It is invoked from three attacker-reachable paths:

- `app/src/lib/copilot-conflict-context.ts:393` — resolves a merge-conflict file's path (taken from `git status`/working-directory file list, i.e. attacker controls file names inside a cloned/fetched repository) before `readFile`. [3](#0-2) 
- `app/src/lib/stores/app-store.ts:7233` — resolves a conflict-resolution path before `writeFile`, i.e. the resolved content is written to whatever path `resolveWithin` approves. [4](#0-3) 
- `app/src/ui/dispatcher/dispatcher.ts:1963` — resolves the `filepath` query parameter of an `x-github-client://openRepo/...` deep link (fully attacker-controlled, parsed in `parseAppURL`) before calling `shell.showItemInFolder`. [5](#0-4) [6](#0-5) 

Existing regression tests (`app/test/unit/path-test.ts`) only cover symlinks that traverse fully outside the root (`../..`) and correctly reject them, and a "traverse-out-and-back-in" case that legitimately resolves back to the exact root — they never test the "sibling directory whose name is prefixed by the root's name" scenario, so the missing-separator bug is not caught. [7](#0-6) 

### Impact Explanation
If an attacker can arrange (or predict) a sibling directory on the victim's disk whose name is a superstring of the cloned repository directory's name (common with predictable default clone locations such as `~/Documents/GitHub/<repo>` next to another checkout like `~/Documents/GitHub/<repo>-private` or `<repo>2`), a symlink placed inside the malicious/fetched repository (or a conflict scenario) can cause:
- **Silent write outside the repo** via the Copilot conflict-resolution auto-stage flow (`app-store.ts`), corrupting or planting content in a directory the user did not intend to touch.
- **Disclosure of file existence/metadata and content** via the Copilot conflict-context reader (`readFile`) being fed content from outside the repo into an AI context payload.
- **Arbitrary file/folder reveal** via the `filepath` deep-link parameter reaching `shell.showItemInFolder` outside the repo root.

This mirrors the accepted C4 judgment on the MIPS finding: no fully generic exploit chain is demonstrated end-to-end without some environmental assumption (a coincidentally-named sibling directory), but the validating primitive itself is broken, guards elsewhere in the code rely on it being correct, and if the precondition is met the consequence is real filesystem escape.

### Likelihood Explanation
Medium/low-to-medium. It requires a specific naming coincidence between the repository directory and another directory on disk, which is not fully attacker-controlled (the attacker cannot rename the victim's clone-target directory), but default GitHub Desktop clone paths (`~/Documents/GitHub/<owner>-<repo>` naming schemes, or repos cloned into flat folders) make such prefix collisions plausible in real setups (e.g., forks, `repo` vs `repo-fork`, `repo` vs `repo2`). No local access, admin rights, or prior malware is needed — only a cloned/fetched malicious repository or a clicked deep link, both explicitly in-scope attacker primitives.

### Recommendation
Change the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to enforce a path-separator boundary:
```js
import { sep } from 'path'
...
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
Add a regression test using a sibling directory whose name is a superstring of the root (e.g. `root` vs `root-evil`) reachable through a symlink, asserting `resolveWithin` returns `null`.

### Proof of Concept
1. Victim has `~/Documents/GitHub/project` (a Desktop-managed repo) and, elsewhere on disk (already existing, e.g. another checkout or backup), `~/Documents/GitHub/project-secrets/notes.txt`.
2. Attacker delivers a repository (via clone URL, fetch, or a merge that introduces a conflicting file) containing a symlink `evil -> /Users/victim/Documents/GitHub/project-secrets`.
3. Trigger any of the three call sites with a path like `evil/notes.txt`:
   - For the deep-link case: `x-github-client://openRepo/<attacker-repo-url>?filepath=evil%2Fnotes.txt`.
4. In `_resolveWithin`, `realRoot = "/Users/victim/Documents/GitHub/project"`, `realResolved = "/Users/victim/Documents/GitHub/project-secrets/notes.txt"`. `realResolved.startsWith(realRoot)` evaluates `true` because the string `"project-secrets"` starts with `"project"`, even though the symlink escaped the intended directory entirely.
5. The function returns the joined path as valid, and the caller proceeds to read/write/reveal `notes.txt`, which lives outside `project`.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
