### Title
`ThresholdKeys` accepts a zero (identity) group key, letting anyone forge signatures for the "multisig" - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is "a component can be enabled/used before a required value is set, so a zero/default value is consumed downstream" (oracle turned on with an unset, i.e. zero, price; zero price then used as a divisor). In Serai's in-scope code the analogous shape is `ThresholdKeys::new` / `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: the group key is computed by interpolating attacker-influenced `verification_shares`, and the result is never checked for being the identity (zero) element. A group key of `0` makes every Schnorr/FROST verification equation degenerate, exactly as a price of `0` made the oracle's output free and its adaptor's denominator zero.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads `t`, `n`, `i`, an interpolation method, a secret share, and then `n` arbitrary group elements as verification shares via `<C as Ciphersuite>::read_G(reader)` (lines 620-623). These bytes are untrusted input per the reachability model.

`ThresholdKeys::new` (lines 349-391) validates only:
- `verification_shares.len() == n` (line 355),
- participant indexes `<= n` (line 361),
- `t == n` when `Interpolation::Constant` is used (lines 367-373).

It then computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

(lines 376-378)

There is no check that the resulting `group_key` is non-identity, no check that any verification share is non-identity, and no consistency check between `secret_share` and `verification_shares[i]` (nothing enforces `G * secret_share == verification_shares[i]`). The returned `ThresholdKeys` is fully "turned on" with a degenerate group key — the direct analog of `turnOnOracle()` being callable while the price is still zero.

For `Interpolation::Lagrange` on a signing set `{1, 2}` (i.e. `t = n = 2`), the interpolation factors are `λ₁ = 2` and `λ₂ = -1` (from `interpolation_factor`, lines 229-247: `num *= l`, `denom *= l - i`). An attacker who controls the serialized bytes therefore needs only to choose `V₂ = 2·V₁` for arbitrary non-identity `V₁` (e.g. `V₁ = G`, `V₂ = 2G`), yielding `group_key = 2·V₁ − V₂ = 0` (the identity point). Both points are ordinary valid encodings, so they pass `read_G`'s canonicality checks.

### Impact Explanation
With `group_key` equal to the identity, the Schnorr/FROST verification relation `s·G == R + c·A` degenerates to `s·G == R`. Any attacker can therefore produce a valid-looking aggregate signature for *any* message by picking an arbitrary scalar `s`, setting `R = s·G`, and outputting `(R, s)`. This is an unconditional signature forgery against the threshold group key — equivalent in consequence to the report's "price is zero, so the asset is free": the zero-value group key makes the protected resource free to spend/sign for. Since Serai's Bitcoin layer derives deposit/spend authority from these keys, an identity group key accepted via `ThresholdKeys::read` corresponds to a multisig anyone can sign for, i.e. total loss of funds for any protocol instance that ingests the malicious key blob.

### Likelihood Explanation
Reachability is direct: `ThresholdKeys::read` is explicitly an untrusted-byte sink, it calls `ThresholdKeys::new` on the decoded fields without any group-key sanity check, and constructing the malicious shares requires only solving a trivial linear relation among two valid points. The required precondition is that some component deserializes `ThresholdKeys` from attacker-influenced storage/transmission rather than from the DKG output path (`key_gen`, `PedPoP`, `musig`), which all construct consistent shares. That deployment assumption is exactly the "untrusted bytes fed to `ThresholdKeys::read`" channel in scope.

### Recommendation
- In `ThresholdKeys::new`, reject a computed `group_key` equal to `C::G::identity()` (and optionally reject identity verification shares), mirroring the report's recommendation that `setMarkPrice` reject a zero price.
- Preferably bind the shares together at construction: verify `C::generator() * secret_share == verification_shares[i]` so a deserialized blob must be internally consistent, analogous to requiring `turnOnOracle` to atomically set the price rather than allowing the "enabled but unset" state.
- In `ThresholdKeys::read`, after constructing the keys, re-derive the group key consistency (non-identity, and `secret_share` matching `verification_shares[i]`) and return an `io::Error` on failure.

### Proof of Concept
For a 2-of-2 Lagrange-interpolated key blob:

1. Serialize header: valid `C::ID`, `t = 2`, `n = 2`, `i = 1`, interpolation byte `1` (Lagrange).
2. Secret share: any valid `C::F` encoding (e.g. `1`).
3. Verification shares: `V₁ = G` for participant 1, `V₂ = 2·G` for participant 2 (or any pair with `2·V₁ = V₂`).

`ThresholdKeys::read` succeeds and produces keys with `group_key() == identity`. The signer-verifier then accepts, for any message `m`, the signature `(R, s)` where `s` is arbitrary and `R = s·G`, because `s·G − c·A = s·G = R` when `A` is the identity point — a universal forgery, matching the "zero denominator / zero price" consequence of enabling a component whose critical value was never set.

Note: this analysis assumes `read_G` accepts the chosen (non-identity) points, which holds since they are canonical encodings; the degeneracy arises purely from the missing post-interpolation identity check in `ThresholdKeys::new`.
