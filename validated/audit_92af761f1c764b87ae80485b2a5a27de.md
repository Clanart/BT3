### Title
mWOMSVBaseRewarder never forfeits cooldown-period bonus rewards because `_calExpireForfeit` ignores `mWOMSV.getRewardablePercentWAD` - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` computes `rewardableAmount = _amount` unconditionally instead of scaling by `mWOMSV.getRewardablePercentWAD(_account)` as the sibling `vlMGPBaseRewarder._calExpireForfeit` does with `vlMGP.getRewardablePercentWAD(_account)`. This means `forfeitAmount` is always `0`, so any mWomSV staker that starts (or is mid-way through) unlock/cooldown keeps 100% of bonus rewards instead of the reduced, time-weighted share the protocol's own `getRewardablePercentWAD` formula defines. Honest lockers who keep their tokens fully committed never receive the forfeited-reward redistribution because forfeiture never happens.

### Finding Description
`mWomSV.getRewardablePercentWAD` (wombat/mWomSV.sol:181-206) explicitly computes a reduced reward-eligibility percentage for accounts with tokens in cooldown, and this getter is part of the shared `ILocker` interface implemented by `mWOMSV` and referenced by `mWOMSVBaseRewarder.mWOMSV` (rewards/mWOMSVBaseRewarder.sol:22).

The analogous reward pool for vlMGP correctly applies this discount: [1](#0-0) 

But `mWOMSVBaseRewarder._calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD` and instead sets `rewardableAmount = _amount` directly: [2](#0-1) 

Since `rewardableAmount == _amount` always, `forfeitAmount = _amount - rewardableAmount` is always `0`, and the "ignore dust" branch (`forfeitAmount < _amount/1000`) is a no-op. This function is called from `_sendReward` (rewards/mWOMSVBaseRewarder.sol:362-376), which is reached from `getReward`/`getRewards`, both gated only by `onlyMasterMagpie` — i.e., reachable by any unprivileged user through `MasterMagpie.claimBaseRewarder`/`getReward` on their own stake. No modifier or reward-index logic elsewhere recomputes or enforces the intended forfeiture; `balanceOf` in `mWOMSVBaseRewarder` (line 146-149) and in `mWomSV` (line 101-103) also count cooldown amounts equally with locked amounts for reward accrual purposes, so cooldown users keep earning at the full rate and then keep 100% of it on claim.

### Impact Explanation
This is a persistent, quantifiable "theft/permanent misdirection of yield" bug (Immunefi impact class: theft of unclaimed yield / protocol insolvency risk for the reward pool's intended distribution rules). Every mWomSV staker who enters `startUnlock` cooldown - a routine, fully permitted action for any staker - keeps receiving their full share of bonus rewards for the entire cooldown duration, when by design (mirroring vlMGP) they should be forfeiting a portion proportional to `1 - getRewardablePercentWAD`. The forfeited amount is supposed to be redistributed to remaining/fully-committed stakers via `_queueNewRewardsWithoutTransfer`; because it never triggers, those honest long-term stakers systematically lose the yield they were entitled to under the intended tokenomics, while every user who chooses to unlock captures rewards they should not be eligible for.

### Likelihood Explanation
Trivial to trigger and 100% reproducible: any unprivileged holder of mWOM can `lock()`, wait for reward accrual (or none at all is even required — the bug applies at every claim regardless of cooldown state), call `startUnlock()` and then `getReward()`/`claimBaseRewarder()` through `MasterMagpie`. No capital beyond ordinary staking is required, and the effect is deterministic and repeatable on every claim for every mWomSV pool reward token.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
```

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder` with a reward token; set a non-trivial `coolDownInSecs`.
2. Attacker locks `X` mWOM via `mWomSV.lock`.
3. Manager queues bonus rewards via `queueNewRewards` so `earned(attacker, token) > 0`.
4. Record `earnedBefore = mWOMSVBaseRewarder.earned(attacker, token)` and `expectedForfeit = earnedBefore * (1e18 - mWomSV.getRewardablePercentWAD(attacker)) / 1e18` (should be > 0 once cooldown starts).
5. Attacker calls `mWomSV.startUnlock(X)` to move the full balance into cooldown.
6. Attacker calls `MasterMagpie.claimBaseRewarder`/`getReward` for the mWomSV pool.
7. Assert: `mWOMSVBaseRewarder.calExpireForfeit(attacker, token) == 0` always (bug), while `expectedForfeit > 0` per `getRewardablePercentWAD`, and the received `toSend` amount equals full `earnedBefore` instead of the discounted amount — quantifying the stolen/misdirected yield versus `vlMGPBaseRewarder`, where an equivalent test on `queueMGP`/`_calExpireForfeit` shows `forfeitAmount > 0` for an account with `getRewardablePercentWAD < 1e18`.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
