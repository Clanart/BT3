### Title
Uncontrolled recursion in `AccountKeyRoleBased.DecodeRLP` allows stack-exhaustion DoS via a nested account-key transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each inner element as a full `AccountKeySerializer`, which itself can decode into another `AccountKeyRoleBased`. There is no depth limit on this recursion, mirroring the CVE-2021-46195 bug class (uncontrolled recursion in a recursive-descent decoder leading to CPU/stack exhaustion).

### Finding Description
`AccountKeyRoleBased.DecodeRLP` reads a list of RLP-encoded byte blobs and, for each one, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` in turn determines the key type from the encoded stream and recursively decodes into whatever `AccountKey` implementation matches that type — including `AccountKeyRoleBased` itself: [2](#0-1) 

`NewAccountKey` allows constructing a fresh `AccountKeyRoleBased` from a type tag with no restriction against nesting at this stage: [3](#0-2) 

The only place I found that explicitly rejects a "RoleBased key nested inside a RoleBased key" is `checkAccountKeyZeroValues` in the `EncodeAccountKey` RPC helper, which is a convenience/validation function for constructing keys via JSON, not part of the core RLP transaction-decoding path: [4](#0-3) 

Because RLP decoding (`Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → the specific `TxInternalDataAccountUpdate`'s `AccountKey` field → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`) happens before any such semantic "no nested RoleBased" check can run, an attacker can build an `AccountUpdate`-type transaction whose `AccountKey` field is an `AccountKeyRoleBased` containing an inner RLP blob that itself decodes to another `AccountKeyRoleBased`, repeated to an arbitrary nesting depth. Each nesting level adds Go call frames: `DecodeRLP` → `rlp.DecodeBytes` → `Stream.Decode` → `decodeDecoder` → `DecodeRLP` (repeat). A sufficiently deep chain of nested `AccountKeyRoleBased` blobs will exhaust the goroutine stack and crash the process (Go recovers small stack overflows by growing the stack, but sufficiently deep/adversarial recursion combined with reflection-heavy `rlp` decode paths can still cause excessive CPU/memory consumption or a fatal `runtime: goroutine stack exceeds` crash, which is not recoverable via `recover()`).

### Impact Explanation
Because the vulnerable decode path is exercised as part of ordinary RLP transaction decoding, this is reachable by any unprivileged actor able to submit a raw transaction over public RPC (e.g. `eth_sendRawTransaction`) or to a peer's transaction pool. A crafted `AccountUpdate` (or `FeeDelegatedAccountUpdate`) transaction containing deeply nested `AccountKeyRoleBased` blobs would be decoded by every full node that receives the transaction (mempool ingestion, block validation), potentially causing a Denial of Service across the network, not just a single node — an unbounded-recursion DoS via a single submitted transaction, analogous to the GCC/rust-demangle bug class described in CVE-2021-46195.

### Likelihood Explanation
Constructing the malicious payload only requires standard RLP encoding tools; no cryptographic material or special privileges are needed since the recursive decode happens before signature verification of the AccountUpdate key (decode is a prerequisite step to even reach signature checks). This makes exploitation straightforward for any transaction sender.

### Recommendation
Add an explicit recursion-depth guard in `AccountKeyRoleBased.DecodeRLP` (and/or `AccountKeySerializer.DecodeRLP`) to reject account keys where a `RoleBased` key contains another `RoleBased` key (matching the intent already expressed in `checkAccountKeyZeroValues`'s "roleBasedKey cannot contains a roleBasedKey as a role key" check), and enforce this check during decode rather than only in the RPC encode helper. Consider adding a general nesting-depth limit to the `rlp` package's `Decoder` interface handling to defend against similar recursive-type attacks in other custom decoders.

### Proof of Concept
1. Construct an `AccountKeyRoleBased` value `k0` (e.g., three `AccountKeyPublic` role keys).
2. Recursively wrap: `k1 = AccountKeyRoleBased{k0}`, `k2 = AccountKeyRoleBased{k1}`, … repeated N times (N large, e.g., tens of thousands), each RLP-encoded via `AccountKeySerializer` as shown in `EncodeRLP`: [5](#0-4) 
3. Embed the outermost encoded key bytes as the `AccountKey` field of a legacy `AccountUpdate` or `FeeDelegatedAccountUpdate` transaction, RLP-encode the transaction, and submit it via `eth_sendRawTransaction` or the P2P transaction-propagation path.
4. When any node decodes the transaction (`Transaction.DecodeRLP`, `blockchain/types/transaction.go:240`) the nested `AccountKeyRoleBased.DecodeRLP` calls recurse N times, consuming stack/CPU proportional to N, potentially crashing the receiving node's process.

**Note on confidence:** I was unable to fully verify, within the available search budget, whether `TxInternalDataAccountUpdate.Validate`/`CheckInstallable` enforces a "no nested RoleBased" rule at some point that would reject such a transaction before it is fully processed — but since the recursive decode occurs during `DecodeRLP` itself (prior to and independent of any subsequent `Validate`/`CheckInstallable` call), such a post-decode check would not prevent the recursion/stack-exhaustion from occurring during decode. If the codebase's `CheckInstallableRoleBased` (referenced but not located in my search) already limits nesting depth *during* decode, this finding would not apply — this should be double-checked directly in `blockchain/types/accountkey/account_key_role_based.go`'s `CheckInstallable` implementation and wherever `DecodeRLP` is invoked for incoming transactions in the tx pool.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
