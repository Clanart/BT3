## Analog Found: Address‑association TOCTOU allowing orphaned/stale identity mappings (chain halt)

### Title
Missing reverse-mapping check in EVM↔Sei address association enables stale "direct-cast" identity to survive re-association, which can halt the chain via distribution's validator-removal hook — (File: `x/evm/keeper/address.go`, `utils/helpers/associate.go`, `precompiles/addr/addr.go`)

### Summary
The bug-class in the report is a time-of-check/time-of-use flaw where an identifier is validated once, then a different, no-longer-consistent piece of state is used/mutated later. sei-chain's EVM↔Sei address-association mechanism has a structurally analogous flaw: `SetAddressMapping` writes two independent KV entries (EVM→Sei and Sei→EVM) but the callers that gate this write only check *one* direction of the mapping before writing, never checking or invalidating the *other* direction's stale entry.

### Finding Description
`SetAddressMapping` unconditionally overwrites both keys without checking whether the EVM address was already pointing at a *different* Sei address: [1](#0-0) 

`AssociateAddresses` (the shared helper used by both the `associate`/`associatePubKey` precompile methods and the ante-handler association flow) only guards against re-associating the *seiAddr* side; it never checks whether `evmAddr` is already mapped to some other seiAddr before calling `SetAddressMapping`: [2](#0-1) 

The `addr` precompile's `associateAddresses` entry point performs the same one-sided check — `GetEVMAddress(ctx, seiAddr)` — but never checks `GetSeiAddress(ctx, evmAddr)` for a pre-existing, different owner: [3](#0-2) 

The code base itself documents the exact consequence of this gap. `EVMPreprocessDecorator` (ante handling for EVM txs) explains that EIP‑7702 `SetCode` can install a **direct-cast** EVM→Sei mapping (i.e., `sdk.AccAddress(evmAddr[:])` with no real pubkey behind it) for an authorization authority. If a later `associatePubKey`/`associate` call re-associates that same EVM address to the authority's *true*, pubkey-derived Sei address, `SetAddressMapping` will silently overwrite the EVM→Sei entry, but the stale Sei→EVM entry for the direct-cast address is left in the store — orphaning any staking/distribution state that had already been created under the direct-cast identity: [4](#0-3) [5](#0-4) 

This is a TOCTOU by construction: the "check" (`_, found := evmKeeper.GetEVMAddress(ctx, seiAddr)`) validates only one key of a two-key relationship, while the "use" (`SetAddressMapping`) mutates both keys of the pairing. Anything that established the pairing earlier via the *other* direction (the direct-cast route, which requires no signature and can be created merely by SetCode delegation) becomes a dangling, unreachable-but-still-referenced Sei address whose validator/distribution/staking state is never cleaned up.

The fix already shipped — `AssociateAuthorizationAuthorities`/`associateAuthorizationAuthorities`, called in both the legacyabci and x/evm ante pipelines before EVM execution — is explicitly a **best-effort, narrow mitigation** scoped only to SetCode authorization authorities that pass `helpers.AuthorityToPreAssociate`'s replay/chain-id/nonce/account-code checks: [6](#0-5) 
It does not touch the generic root cause in `SetAddressMapping`/`AssociateAddresses`/`addr` precompile — any other path that establishes a direct-cast mapping and is later re-associated through `associate`/`associatePubKey` (or any future direct-cast producer) remains exposed to the same orphaning.

### Impact Explanation
Per the code's own documented failure mode, an orphaned direct-cast identity that retained staking/delegation records can trigger the distribution module's validator-removal hook against state that is no longer reachable/consistent, which the in-repo comment states "can then halt the chain." A chain halt from a single crafted EVM transaction sequence (deploy SetCode delegation to establish direct-cast identity outside the pre-association allowlist, then call `associatePubKey`/`associate` for the real pubkey) is a Critical/High-impact consensus-safety issue, matching the "validator halt" / "permanent freezing" categories in the validation criteria.

### Likelihood Explanation
Reachability is fully within an unprivileged EVM transaction sender's control: SetCode (EIP‑7702) transactions and the `addr` precompile's `associate`/`associatePubKey` methods are both public, permissionless EVM entry points reachable by any account with gas. The only constraint is crafting a SetCode authorization/authority combination that `AuthorityToPreAssociate`'s best-effort filter does not pre-associate (the code comment concedes this filter is not exhaustive), followed by an ordinary call to the `addr` precompile. No validator, node, or governance privilege is required.

### Recommendation
Make the address-association write path itself TOCTOU-safe instead of relying on a narrow, best-effort pre-association pass:
- In `SetAddressMapping` (and/or `AssociateAddresses`/the `addr` precompile's `associateAddresses`), check `GetSeiAddress(ctx, evmAddress)` for an existing, different owner before writing, and either reject the association or explicitly migrate/clean the stale reverse entry (delete the old Sei→EVM key, migrate any staking/distribution/delegation records tied to the direct-cast identity, or reject if such state exists) in the same atomic operation.
- Do not rely on a best-effort, allowlist-based pre-association pass at ante time as the sole safeguard; enforce the invariant "an EVM address maps to exactly one Sei address, and that Sei address's prior direct-cast entry is fully reconciled or removed" directly at the point of mutation.

### Proof of Concept
1. Attacker crafts an EIP-7702 `SetCode` transaction naming an authority address/authorization combination that fails `helpers.AuthorityToPreAssociate`'s pre-checks (e.g., a marginal nonce/chain-id edge case not covered by the best-effort filter), so `associateAuthorizationAuthorities` skips it while go-ethereum's EVM execution still applies the delegation, per [4](#0-3) .
2. This installs SetCode delegation code and, via normal EVM state semantics, results in a direct-cast Sei address `sdk.AccAddress(evmAddr[:])` accumulating staking/distribution state (e.g., becomes/interacts with a validator operator or delegator record) under that direct-cast identity.
3. Attacker (or the true key owner) later calls the `addr` precompile's `associatePubKey`/`associate` with the authority's true public key, per [7](#0-6) . The check `_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)` passes because the *new* pubkey-derived seiAddr was never previously associated.
4. `SetAddressMapping` overwrites the EVM→Sei key to point at the new seiAddr but leaves the old direct-cast Sei→EVM key pointing at the same evmAddr, per [1](#0-0) , orphaning the staking/distribution state recorded under the direct-cast identity.
5. When distribution's validator-removal hook later processes the orphaned/inconsistent record, the chain halts, as anticipated by the code's own comment.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

		return nil, 0, err

		return nil, 0, err

	// Takes a single argument, a compressed pubkey in hex format, excluding the '0x'

	if err != nil {
		return nil, 0, err

	pubKey, err := btcec.ParsePubKey(pubKeyBytes)
	if err != nil {
		return nil, 0, err

	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

// AssociateAuthorizationAuthorities pre-associates every EIP-7702 SetCode authorization
// authority in the transaction with its true (pubkey-derived) Sei address before EVM
// execution installs delegation code for it. Authorities are distinct accounts from the tx
// sender, so the sender association performed by the caller does not cover them. Without
// this, SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey
// call can remap, orphaning any staking/distribution state created under the direct-cast
// identity (which can then halt the chain via the distribution validator-removal hook).
//
// This is the legacyabci counterpart of x/evm/ante's EVMPreprocessDecorator so both ante
// paths associate authorities identically. It is best-effort: only authorities whose
// authorization the EVM will actually apply are pre-associated — helpers.AuthorityToPreAssociate
// enforces the same chain-id/nonce/account-code checks go-ethereum uses, which also prevents
// replaying a publicly-visible authorization a user signed for another chain to force-associate
// them. Each association runs in its own cache context and is only committed on success, so an
// already-associated, skipped, or failing authority affects only itself and never rejects the
// transaction (matching go-ethereum, which would still accept it). Non-SetCode transactions
// carry no authorizations and are a no-op.
