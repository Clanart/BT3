## Title
Unchecked ERC20 return-data in escrow settlement lets silent-failure tokens permanently lock user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles escrowed intent funds (fills, refunds, fee redemption, and dust sweeps) using raw low-level `.call()` invocations of the ERC20 `transfer` selector instead of OpenZeppelin's `SafeERC20`. The code only checks that the external call did not revert (`success`), but never decodes/validates the returned boolean. This is exactly the class of bug described in the external report ("SafeERC20 should be used... token may have no return value... lead to failure of calls") — except here the failure mode is worse: any token that returns `false` on failure (rather than reverting), or returns no data at all, is treated as a successful transfer, while the contract has already deducted the escrow accounting and marked the order as finalized.

### Finding Description
In `withdraw()` [1](#0-0) , escrowed tokens are released with:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

The same unchecked pattern is used for transaction-fee redemption in the same function [3](#0-2) , and for dust sweeps in `onAccept`'s `SweepDust` branch [4](#0-3) .

`success` here only reflects whether the call to the token contract reverted at the EVM level. If the ERC20 token:
- returns no data (many legacy/non-standard tokens), or
- explicitly returns `false` on failure instead of reverting (the exact USDT-style behavior cited in the external report),

then `success` is `true` even though no tokens were actually moved. The contract does not decode/verify `returndata` against `true`, unlike `SafeERC20.safeTransfer`, which explicitly checks both call success and returned boolean/data length.

Critically, `withdraw()` unconditionally sets `_filled[body.commitment] = beneficiary` at the top of the function before any transfer occurs, and decrements `_orders[body.commitment][token] -= amount` right after the unchecked call [5](#0-4) . Because the order is already marked filled/refunded and the escrow balance already zeroed out, there is no retry path — this is the same settlement function reachable from `onAccept` for both `RedeemEscrow` and `RefundEscrow` requests [6](#0-5) , i.e. a normal, unprivileged cross-chain fill/refund flow, not an admin action.

Compare this to the canonical (non-Tron) EVM `IntentsBase._withdraw`, which correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` [7](#0-6)  and `IERC20(...).safeTransfer(beneficiary, fees)` [8](#0-7) . The Tron deployment diverges from this safe pattern and reintroduces the exact class of bug the external audit report flagged and had marked "Resolved" elsewhere in the codebase.

### Impact Explanation
For any input/output/fee token deployed on the Tron chain that does not strictly follow the EIP-20 boolean-return convention on failure, a legitimate solver's fill or a user's refund will be recorded as settled (`_filled` set, `_orders` decremented, `EscrowReleased`/`EscrowRefunded` emitted) while the tokens never leave the contract and never reach the beneficiary. This is a direct loss/lock of escrowed bridge funds — the solver or user gets nothing, and the tokens are stranded in the `IntentGatewayV2` contract with no code path to reclaim them, since the commitment is already finalized. This matches the "stealing or loss of funds" and "false ... acceptance" categories of the bounty scope, and lives squarely in the bridge's intent-settlement/escrow custody logic.

### Likelihood Explanation
The vulnerability triggers under normal, unprivileged operation whenever the configured input/output/fee token is a non-conforming ERC20 (missing return data, or returning `false` instead of reverting), which is a well-documented and common real-world token behavior (e.g. USDT-style implementations, the same example cited in the source report). No malicious relayer, prover, or admin is required — any user or solver interacting with such a token through the standard fill/refund/redeem flow triggers the loss.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` and the `SweepDust` branch of `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the fix already applied in `IntentsBase._withdraw` and `_sweepDust` for the main EVM deployment.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an input token `T` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g. simulate an insufficient-balance/blacklist condition that legacy tokens signal via `return false`).
2. A solver fills a cross-chain order; Hyperbridge delivers a `RedeemEscrow` request to `onAccept`, which calls `withdraw(body, false)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (external call itself didn't revert) even though `T.transfer` internally returned `false` and moved no tokens.
4. `_filled[body.commitment] = beneficiary` was already set at function entry, and `_orders[body.commitment][token] -= amount` executes, permanently marking the order as settled.
5. The beneficiary's on-chain token balance is unchanged — the escrowed tokens remain locked in the `IntentGatewayV2` contract with no remaining path to redeem them, while off-chain systems and events (`EscrowReleased`) report the fill as successful.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
