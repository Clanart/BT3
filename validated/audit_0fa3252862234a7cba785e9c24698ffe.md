### Title
Pool singleton travel spends are not cryptographically bound to their fee payment, unlike every other asset wallet - ([File: chia/pools/pool_wallet.py])

### Summary
`PoolWallet.generate_travel_transactions()` creates the fee payment for a `join_pool`/`self_pool` singleton transition by calling `generate_fee_transaction()`, which builds a bare fee-only spend with **no announcement condition** linking it to the singleton travel spend. Every other subwallet in the codebase (DID, NFT, CAT/CR-CAT, VC, DataLayer, PlotNFT2) uses `create_tandem_xch_tx()` with an `AssertCoinAnnouncement`/`CreateCoinAnnouncement` pair that makes the fee spend and the primary state-changing spend consensus-enforced as an atomic unit. The pool wallet's fee spend relies solely on wallet-side bundling convention (`merge_spends=True` at action-scope exit) rather than a CLVM-enforced assertion, so the fee payment can be detached from the singleton state update.

### Finding Description
`generate_fee_transaction()` calls the plain `standard_wallet.generate_signed_transaction([], [], action_scope, fee=fee, ...)` with no `extra_conditions` tying it to the singleton spend: [1](#0-0) 

`generate_travel_transactions()` then independently builds the singleton spend (`outgoing_coin_spend`) and, only if `fee > 0`, calls `generate_fee_transaction(fee, action_scope)` — the two spends are appended as separate `TransactionRecord`s with no shared announcement condition: [2](#0-1) 

Compare this to the codebase-wide pattern used by every other asset wallet, where `create_tandem_xch_tx` is always passed an `AssertCoinAnnouncement`/`CreatePuzzleAnnouncement` corresponding to a `CreateCoinAnnouncement` embedded in the primary spend's solution, so that CLVM execution fails if either spend is missing from the final bundle: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The only thing keeping the pool's fee spend attached to the singleton travel spend is `WalletStateManager.add_pending_transactions()` aggregating pending `TransactionRecord.spend_bundle`s into one bundle when the action scope exits with `merge_spends=True` (the default): [7](#0-6) 

This is a wallet-side/RPC-side convention, not a consensus-level constraint. Because the singleton travel spend carries no `ASSERT_COIN_ANNOUNCEMENT` requiring the fee coin's announcement, the singleton spend is independently valid and minable by itself. Anything that separates the two transactions before they reach the mempool — pushing with `push=False` and only forwarding the singleton transaction, `merge_spends=False` call paths, signing/offline flows that drop one `TransactionRecord`, or a spend-bundle submitter who simply removes the fee coin spend from the aggregated bundle before broadcasting — results in the pool singleton transitioning state (`join_pool`/`self_pool`) with the intended fee never being paid, or with the fee coin being spent without ever confirming the intended state transition, since nothing in the CLVM program enforces they are spent together.

### Impact Explanation
Because the fee coin spend and singleton state-transition spend are only tied together by client-side bundling, an unprivileged spend-bundle submitter (or any code path that manipulates/re-splits the pending transactions before push) can submit only the pool singleton travel spend without its paired fee spend. This bypasses fee obligations for pool state transitions without violating any CLVM condition, and — mirroring the referenced report's core defect — the fee can be "lost" or omitted relative to the state update actually landing on chain, since there is no cryptographic guarantee they are co-spent.

### Likelihood Explanation
Requires only normal use of the existing pool wallet transaction-building API and a caller/attacker able to control how the resulting `TransactionRecord`s are pushed (e.g. via `push=False` construction, offline signing flows, or direct bundle submission) — all reachable via standard wallet/RPC calls without any privileged access, in contrast to every other asset wallet that closes this gap with an announcement assertion.

### Recommendation
Add an `AssertCoinAnnouncement`/`CreateCoinAnnouncement` pair binding `generate_fee_transaction()`'s fee spend to the singleton travel spend in `generate_travel_transactions()`, following the same pattern already used by `Wallet.create_tandem_xch_tx()` callers in `did_wallet.py`, `nft_wallet.py`, `data_layer_wallet.py`, and `plotnft_wallet.py`, so the fee spend and singleton spend are consensus-enforced as an atomic unit rather than relying solely on `merge_spends` bundling convention.

### Proof of Concept
1. Call `PoolWallet.join_pool(target_state, fee, action_scope)` with `fee > 0`; this invokes `generate_travel_transactions()`, which appends two independent `TransactionRecord`s — one for `generate_fee_transaction()` (no announcement) and one for the singleton travel spend — to `action_scope.side_effects.transactions`.
2. Before the action scope's `merge_spends` aggregation is applied (e.g., using `push=False` and independently forwarding only the singleton `TransactionRecord.spend_bundle`, or stripping the fee `CoinSpend` from the aggregated bundle prior to broadcast), submit only the singleton travel `CoinSpend`.
3. The singleton spend is valid and minable on its own because it contains no `ASSERT_COIN_ANNOUNCEMENT` referencing the fee coin, unlike the pattern in `did_wallet.transfer_did`/`create_update_spend`, `nft_wallet.generate_unsigned_spendbundle`, `data_layer_wallet.create_update_state_spend`, and `plotnft_wallet.join_pool`/`melt_plotnft`, all of which would fail CLVM execution if their paired fee announcement condition is not satisfied.

    async def add_pending_transactions(
        self,
        tx_records: list[TransactionRecord],
        push: bool = True,
        merge_spends: bool = True,
        sign: bool | None = None,
        additional_signing_responses: list[SigningResponse] | None = None,
        extra_spends: list[WalletSpendBundle] | None = None,
        singleton_records: list[SingletonRecord] = [],
        plotnft_exiting_info: PlotNFTTargetStateInfo | None = None,
    ) -> list[TransactionRecord]:
        """
        Add a list of transactions to be submitted to the full node.
        Aggregates the `spend_bundle` property for each transaction onto the first transaction in the list.
        """
        if sign is None:
            sign = self.config.get("auto_sign_txs", True)
        agg_spend = WalletSpendBundle.aggregate([tx.spend_bundle for tx in tx_records if tx.spend_bundle is not None])
        if extra_spends is not None:
            agg_spend = WalletSpendBundle.aggregate([agg_spend, *extra_spends])
        actual_spend_involved: bool = agg_spend != WalletSpendBundle([], G2Element())
        if merge_spends and actual_spend_involved:
            tx_records = [
                dataclasses.replace(
                    tx,
                    spend_bundle=agg_spend if i == 0 else None,
                    name=agg_spend.name() if i == 0 else bytes32.secret(),
                )
                for i, tx in enumerate(tx_records)
            ]
