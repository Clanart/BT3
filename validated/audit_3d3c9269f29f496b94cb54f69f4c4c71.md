### Title
`ReceivedOutput::read` accepts attacker-claimed offset/output/outpoint tuples with no binding check, letting forged UTXOs be treated as spendable multisig funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the OpenQ report — where `mintBounty` accepted an arbitrary `organization` identifier with no proof that `msg.sender` controlled it — `ReceivedOutput::read` deserializes an arbitrary `(offset, TxOut, OutPoint)` triple from untrusted bytes and returns it as a fully-formed "spendable output" object, performing zero validation that the claimed `offset` actually derives the `script_pubkey` in `output`, or that the claimed `outpoint`/`value` correspond to anything real.

### Finding Description
`ReceivedOutput` is the type the `Scanner` produces when it sees an on-chain output paying to `p2tr_script_buf(key + offset*G)` for a registered `offset` — i.e., a legitimate `ReceivedOutput` carries a cryptographic guarantee that `offset` is bound to `output.script_pubkey` (established in `scan_transaction`, networks/bitcoin/src/wallet/mod.rs:199-214, via the `scripts` map keyed on the exact script).

`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) discards that guarantee entirely:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
}
```

It accepts any scalar as `offset` and any `TxOut`/`OutPoint`, with no check that `output.script_pubkey == p2tr_script_buf(scanner_key + GENERATOR * offset)`. The three fields are mutually unbound — exactly the "any ID claimable by anyone" shape of the source bug, transplanted to Serai's "offset claims this output" relation.

An unprivileged party who can feed bytes to `ReceivedOutput::read` (listed as an untrusted-bytes sink) can therefore fabricate:

1. **A fake deposit**: a `ReceivedOutput` with the multisig's real script, an arbitrary `outpoint`, and an arbitrary `value`. `value()` (line 116-118) then reports funds received that don't exist on chain and are not spendable — matching the accepted impact class "funds reported received that are not spendable".
2. **A mis-bound spendable input**: a real on-chain `TxOut` paying to the multisig's base/external script (`offset = 0`), but re-labeled with a nonzero `offset` (e.g., the change or forward offset from `processor/src/networks/bitcoin.rs:333-344`). The signing path will sign with `key + offset*G`, which does not match the BIP-341 tweaked key committed in the script, producing a signature that validates nothing — the multisig signs an unintended, unbroadcastable spend while believing it controls the UTXO.

### Impact Explanation
Downstream consumers treat a `ReceivedOutput` as authoritative evidence of a spendable deposit (the processor's scheduler consumes `outputs`/`value()` for `Plan` construction; see `processor/src/tests/wallet.rs:86-103`). A forged `ReceivedOutput` therefore inflates accounted balances with phantom UTXOs, and any signing attempt built on it either wastes a signing session on an invalid input or burns fees on a transaction that cannot confirm. The mis-bound offset case additionally tricks the threshold group into producing a signature under a wrong key for a message committing to prevouts the wallet mislabeled.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary (coordinator-to-signer, database restore, or any peer-supplied scan result). The parser itself provides no defense — `offset` is read as an opaque scalar and never re-derived against `output.script_pubkey`. Note `read` lacks access to the scanner key, so the binding check cannot be performed inside `read` itself; it must be performed by the consumer, and nothing in the API forces that.

Severity: Medium — exploitation requires a consumer to trust deserialized `ReceivedOutput`s without re-validating against the Scanner/chain, but the type's invariants are undocumented and silently dropped on deserialization.

### Recommendation
- Provide `ReceivedOutput::read` only alongside a verification entry point, e.g. `Scanner::verify_received(&self, output: &ReceivedOutput) -> bool` that re-checks `self.scripts.get(&output.output.script_pubkey) == Some(&output.offset)`, and document that deserialized outputs MUST be passed through it.
- Alternatively, serialize the internal `key` and verify `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` inside `read` itself.
- Document on `ReceivedOutput::read` that no semantic binding between `offset`, `output`, and `outpoint` is established by deserialization.

### Proof of Concept
```rust
// Attacker constructs bytes: offset = change_offset (nonzero),
// output = a real TxOut paying to the multisig's EXTERNAL address (offset 0 script),
// outpoint = a real confirmed outpoint the attacker saw on chain.
let mut buf = vec![];
buf.extend(change_offset.to_bytes());          // claims wrong offset
buf.extend(serialize(&external_script_txout)); // script = p2tr(key), not p2tr(key + change*G)
buf.extend(serialize(&real_outpoint));
let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted unconditionally

// Wallet believes `forged` is spendable via key + change_offset*G.
// SignableTransaction/multisig signs with the offset key; the resulting signature
// does not satisfy the BIP-341 output, so the input is unspendable despite being
// reported as received funds at `forged.value()`.

// Phantom deposit variant: fabricate outpoint+value entirely; `read` accepts it and
// `value()` reports funds that were never received on chain.
```

Caveat: I was unable to verify whether `SignableTransaction::new` or other downstream code in `networks/bitcoin/src/wallet/send.rs` re-validates the offset↔script binding before signing (the file was not read). If such a check exists there, the practical impact reduces to the phantom-accounting case only.
