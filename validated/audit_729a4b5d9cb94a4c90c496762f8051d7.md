Based on my research, the strongest reachable analog to the "withdraw arbitrary token without validation" bug class is in `rewards/ManualCompound.sol`'s `compound()` function, which sweeps out the entire contract balance of any caller-specified token without verifying that the balance actually corresponds to rewards claimed on behalf of that specific caller.

### Title
Arbitrary token balance sweep via unvalidated caller-supplied reward token list in `compound()` - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` lets any caller supply an arbitrary `_rewards` array of token addresses. For any token in that array that is not registered as `compoundableRewards[token]`, the function transfers the contract's *entire current balance* of that token to `msg.sender`, rather than only the amount actually claimed for that caller in the current transaction.

### Finding Description
`compound()` first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0)  which claims rewards on the caller's behalf and routes them into this contract. It then iterates the caller-supplied `_rewards` array and, for tokens that are not compoundable, transfers whatever balance of that token currently sits in the contract to `msg.sender`: [2](#0-1) 

The critical flaw is that the amount transferred is `IERC20(_rewards[i][j]).balanceOf(address(this))` — the contract's total balance of that token — not the amount that was actually just claimed for `msg.sender` via `multiclaimOnBehalf`. There is no check tying the swept balance to what was legitimately earned by the caller in this call, similar to how the reported `incentives.sol` bug let `withdrawIncentives` release tokens without checking the token was actually owed/valid. If any balance of an arbitrary ERC20 (including reward or governance-adjacent tokens) is already sitting in `ManualCompound` — whether from dust left over by a prior partial compound, rounding remainders from the `convert`/`lock`/`helper` deposit paths further down in the same function [3](#0-2) , or another in-flight compound for a different user — any subsequent caller can list that token address in `_rewards` and drain the full balance for free, even though they have no claim on it.

### Impact Explanation
This allows theft of yield/reward tokens that belong to other users or were queued for legitimate compounding, matching the "theft or permanent freezing of unclaimed yield" impact category. Since `compoundableRewards` mapping is admin-controlled but the `_rewards` list passed to `compound()` is fully attacker-controlled and unchecked against it for correctness of amount, an ordinary wallet can extract tokens it never earned.

### Likelihood Explanation
Likelihood depends on residual token balances accumulating in `ManualCompound` (e.g., rounding dust from `convertFor`/`lockFor`/`depositFor`, or timing races between concurrent `compound()` calls). This is plausible in normal operation given repeated compounding activity across many users, but I was unable to fully verify the exact mechanics of `multiclaimOnBehalf` in `rewards/MasterMagpie.sol` (I could not complete reading its implementation before running out of tool iterations), so I cannot confirm with certainty how often/how much residual balance would be present, or whether reentrancy guards elsewhere prevent overlapping calls.

### Recommendation
Track the exact amount received for the caller during `multiclaimOnBehalf` (e.g., balance-before/balance-after delta per call) and only transfer that delta for non-compoundable tokens, instead of sweeping the entire contract balance.

### Proof of Concept
1. Some balance of token `X` (not in `compoundableRewards`) ends up sitting in `ManualCompound` (e.g., dust from a previous user's `compound()` conversion step, or another user's in-progress claim).
2. Attacker calls `compound(_lps, _rewards, ...)` with `_lps` set to any pool they have even a trivial/zero position in, and `_rewards` including token `X`.
3. Since `compoundableRewards[X]` is false, the loop transfers `IERC20(X).balanceOf(address(this))` — the full existing balance, not just anything newly claimed — to the attacker via [4](#0-3) .

**Note on verification limits:** I could not fully trace `multiclaimOnBehalf`'s internal accounting in `rewards/MasterMagpie.sol` within the available tool budget, so the exact preconditions for residual balances to exist are not fully confirmed. A Devin session with full repo access would be needed to trace this completely and confirm exploitability end-to-end.
