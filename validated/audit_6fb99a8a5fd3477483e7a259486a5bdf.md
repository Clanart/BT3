### Title
Stop-hook security review state is consumed and permanently discarded on `_skip(9)` (empty review set) with no restore path, silently dropping in-flight edits from the automated code-security review — (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
This is a direct structural analog of the audited Salty.IO bug class: a multi-step process that (1) atomically consumes/clears an accounting/queue of pending work, then (2) performs the actual "distribution" (here: LLM security review) as a separate, failure-prone step, with only some failure branches restoring the consumed state. The `handle_stop_hook` function in `security_reminder_hook.py` mirrors this pattern almost exactly, including a comment explicitly describing the very race the original report flags.

### Finding Description
`handle_stop_hook` calls `consume_stop_state(session_id)` once, up front, which atomically reads and **clears** `touched_paths` (the list of files edited during the turn that are pending a Stop-hook security review) from persisted session state [1](#0-0) . `touched_paths` is the accounting structure analogous to `rewardsForPools`/`profitsForPools` in the Salty.IO report — it records "what should receive the benefit" (here, a security review) before that benefit is actually delivered.

After the snapshot, the function proceeds through a series of early-exit `_skip(reason, restore=False)` checks. Only one of them, the network-reachability check, explicitly restores the consumed state via `restore_unreviewed_stop_state`: [2](#0-1) 

The developers' own comment acknowledges the underlying hazard this pattern creates ("the next UPS would see an empty list, fall through the preservation guard, and re-baseline past the unreviewed edits") in `diffstate.py`: [3](#0-2) 

However, restoration is only wired up for the `ensure_anthropic_reachable()` failure at `_skip(10, restore=True)`. Every other exit path that occurs **after** `consume_stop_state` clears `touched_paths` does not restore it, including:
- `_skip(2)` — max stop-hook firings reached for this asyncRewake loop [4](#0-3) 
- `_skip(3)` — review disabled or missing API credentials [5](#0-4) 
- `_skip(4)` — no `cwd` in hook input [6](#0-5) 
- `_skip(9)` — `compute_v2_review_set` returns an empty review set (e.g., transient git state issue, race with a concurrent `git` operation, or a path-filtering edge case) [7](#0-6) 

`_skip(9)` is the most concerning of these because it is data-dependent and can be triggered non-deterministically by transient git/filesystem conditions (analogous to the Salty.IO "swap fails due to low reserves" trigger), not a static configuration choice like `_skip(2)`/`_skip(3)`. If `compute_v2_review_set` fails to resolve `review_paths` for a turn that did touch real files (e.g., a git error, a repo-root detection failure, or a stash/HEAD mismatch), the edited files recorded in `touched_paths` are dropped from state and never re-queued for review on a later turn.

### Impact Explanation
Following the Salty.IO judge's reasoning ("rewards are just delayed... unless storage is cleared without distribution, in which case they're lost"), the impact here is that files edited during a turn can be permanently excluded from the plugin's automated Stop-hook LLM security review, with no accounting error or user-visible signal beyond a low-severity debug log line and a `skip_reason` telemetry counter. This is a silent trust-boundary degradation of `security-guidance`, a plugin whose entire purpose is to catch security-sensitive code changes (secrets, injection, path traversal, etc.) introduced by the agent before the turn ends. Since the failure mode is "review never happens" rather than "review happens later," a maliciously or accidentally introduced vulnerability in the dropped file(s) escapes the automated backstop for that turn and is not retried by any later Stop-hook firing, because the very state that would drive the retry has already been erased.

### Likelihood Explanation
Likelihood is low-to-medium: `_skip(9)` requires `compute_v2_review_set` to return no paths despite `touched_paths` being non-empty — a case that can plausibly occur from git edge cases (detached HEAD, mid-operation repo states, path normalization mismatches between the recorded touched path and git's view of the working tree) similar to how the original bug required reserve-manipulation to fail a swap. This is a defense-in-depth control, so the practical security impact depends on whether other layers (PreToolUse hooks, model self-review) also miss the same issue — but the report's core point stands: the accounting/consumption asymmetry is a structural bug independent of how often it fires.

### Recommendation
Apply the same restore call used for `_skip(10, restore=True)` to every skip branch that occurs after `consume_stop_state`, at minimum `_skip(9)` (data-dependent, review-set-empty) and ideally `_skip(2)`/`_skip(4)` as well unless there is an explicit, documented reason those cases should not re-queue the paths for a future Stop fire. Alternatively, restructure the function so `touched_paths` is only cleared after `review_paths`/`diff_output` are confirmed non-empty and the review has actually run (or definitively failed for a reason where retry would never help, e.g., feature disabled), rather than clearing eagerly and restoring only on select paths.

### Proof of Concept
Not independently reproducible from the indexed file contents alone (no test harness for this hook was found in the index). The vulnerable control flow is directly evidenced by the code itself: `consume_stop_state` unconditionally clears `touched_paths` at line 1728, and of the five `_skip()` call sites that can execute afterward, only the one at line 1786 passes `restore=True`; lines 1768, 1772, 1790, and 1797 do not, so any turn that reaches one of those four unreverted skip points loses its `touched_paths` review queue for that set of edits permanently.

```python
def restore_unreviewed_stop_state(session_id, paths, baseline_sha):
    """Put consumed touched_paths back so the next Stop reviews them.

    consume_stop_state cleared touched_paths on disk; if Stop then exits
    early for a transient reason (CCR API unreachable, Haiku HTTP error)
    the next UPS would see an empty list, fall through the preservation
    guard, and re-baseline past the unreviewed edits. Restoring keeps the
    guard armed. Prepend+dedupe so any concurrent next-turn PostToolUse
    appends survive.
    """
    if not paths:
        return

    def _restore(state):
        existing = state.get("touched_paths", [])
        merged = list(dict.fromkeys(list(paths) + list(existing)))
        if len(merged) > 200:
            merged = merged[:200]
        state["touched_paths"] = merged
        if baseline_sha and not state.get("baseline_sha"):
            state["baseline_sha"] = baseline_sha
    with_locked_state(session_id, _restore)
```
