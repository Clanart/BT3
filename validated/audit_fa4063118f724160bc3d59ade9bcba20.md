Confirmed: `applyPatchToIndex` in `app/src/lib/git/apply.ts` re-fetches the working-directory diff independently at stage time and applies a *line-index-based* selection (`file.selection`) computed earlier by the UI against that freshly-fetched diff, with no check that the file's content still matches what was diffed when the user made the selection.

### Title
Line-index based partial-commit selection is silently re-applied to a changed working-directory diff, corrupting what the user commits - (File: app/src/lib/git/apply.ts)

### Summary
`git/commit.ts`'s `createCommit` → `stageFiles` → `applyPatchToIndex` builds the patch used for a partial ("select lines to commit") commit by calling `getWorkingDirectoryDiff(repository, file)` fresh at staging time [1](#0-0) , then reuses the `DiffSelection` (a set of *absolute line indices*) that was computed earlier by the UI against a possibly different, earlier snapshot of the file's diff [2](#0-1) . There is no comparison between the diff hash/content the user actually reviewed and selected lines against, and the diff that is freshly fetched right before the patch is generated and applied to the index.

### Finding Description
The invariant broken here mirrors the report's core issue: a value ("the snapshot"/here, the index positions the user selected while reviewing a diff) is treated as authoritative and reused later for a security/integrity-sensitive operation (composing the exact commit), even though the underlying data it was computed against ("the price snapshot"/here, the working-directory file content) can change in between without any restriction or re-validation.

- The user reviews a diff rendered by the UI and picks specific hunks/lines to include via `DiffSelection`, which stores selection **by absolute line index** (`file.selection.isSelected(absoluteIndex)`), not by content hash [3](#0-2) .
- When the commit is actually executed, `applyPatchToIndex` calls `getWorkingDirectoryDiff(repository, file)` again to obtain a diff, and then calls `formatPatch(file, diff)` using the (old) selection indices against this new diff [4](#0-3) .
- If the tracked file's content on disk changes between the moment the user made their line selection in the UI and the moment `_commitIncludedChanges` actually runs `createCommit` (e.g., because a build tool, linter, IDE auto-format, or — most relevant to the "attacker controls a cloned/fetched repository" threat model — a git hook shipped inside a cloned/fetched malicious repository such as `post-checkout`/`post-merge`/`post-index-change`, or an LFS smudge/clean filter, modifies the file in the background), the hunk boundaries and line ordering shift.
- `formatPatch` will then apply the stale index-based selection to the new hunk layout, generating a valid-looking patch that no longer corresponds to what the user actually reviewed and consented to commit. `git apply --cached` will accept this patch as long as it applies cleanly against the index, with no content-identity check.
- There is no code path (confirmed via the "createCommit"/`apply.ts` files) that re-diffs and compares against a captured hash/version of the file at selection time, nor a "the file has changed since you selected these lines, please re-review" guard. Existing guards only check structural things like binary/diff-kind or amend/rename bookkeeping [5](#0-4) , not content staleness.

### Impact Explanation
This lets an attacker who controls a fetched/cloned repository (via a bundled git hook or filter, or any background process able to touch a tracked file mid-review) silently corrupt what the user actually commits and pushes — the app will report and push a commit that does not match the diff the user consciously approved in the Changes view, without any warning banner or diff re-validation. This falls squarely under "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories.

### Likelihood Explanation
The race window exists on every partial commit (a very common workflow — line/hunk-level staging is a flagship Desktop feature) and does not require local/physical access, admin rights, or pre-existing malware: it only requires a hook/filter/background writer bundled with or triggered by content the user has already fetched/cloned, which is within the explicitly allowed attacker model ("attacker controls a cloned/fetched repository"). The window between line-selection and clicking "Commit" is user-controlled and can be arbitrarily long, increasing exploitability.

### Recommendation
Bind the `DiffSelection` to the exact diff/content it was computed against (e.g., store a content hash or the diff text itself alongside selection state) and, immediately before generating/applying the patch in `applyPatchToIndex`, re-diff and verify the file's content/hash is unchanged from what was captured when the selection was made. If it has changed, abort the partial-commit apply and force the UI to refresh the diff and require the user to re-select, rather than silently reusing stale line indices against new content.

### Proof of Concept
Not independently executable from the index alone (requires exercising the electron app + git process), but the code path is directly demonstrable:
1. In Desktop, modify a tracked file and open the Changes view; deselect several lines/hunks (partial selection is recorded as line indices via `DiffSelection`).
2. Before pressing "Commit", have a background process (simulating an attacker-supplied `post-checkout`/`post-merge` hook or file watcher from the cloned repo) insert/remove lines above the selected hunk in the same file, shifting line numbers but not blocking git's internal cleanliness.
3. Click "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` [6](#0-5)  and calls `formatPatch(file, diff)` using the old `file.selection` indices [7](#0-6) .
4. Inspect the resulting commit: it includes/excludes different lines than what the user visually selected in step 1, with no error or warning shown, demonstrating silent corruption of the committed content.
