Confirmed: `_calExpireForfeit` in `vlMGPBaseRewarder.sol` computes forfeiture using a **live, current-block** call to `vlMGP.getRewardablePercentWAD(_account)`, not a value snapshotted at the time the reward accrued. This is the root cause that makes the described attack work.

### Title
Forfeiture bypass via `cancelUnlock` before `getReward`/`getRewards` lets a cooldown staker reclaim 100% rewardable percent and steal forfeited yield - ([File: wombat/mWomSV.sol], [File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder._calExpireForfeit` (and analogously the mWomSV/vlMGP reward flow) determines what fraction of a user's *already-accrued* `userRewards[token][account]` is forfeited by calling `vlMGP.getRewardablePercentWAD(_account)` at the moment of `getReward`, rather than using the percent that applied while the reward index (`rewardPerTokenStored`) was accruing during cooldown. Because `cancelUnlock` instantly restores `amountInCoolDown` to the fully-locked balance with no forfeiture-triggering side effect, a user can call `cancelUnlock(_slotIndex)` immediately before `getReward`/`getRewards` in the same transaction/block to make `getRewardablePercentWAD` return ~100%, collecting the full historical accrual with zero forfeiture that should have applied for the period spent in cooldown.

### Finding Description
- `getRewardablePercentWAD` in `wombat/mWomSV.sol` (and identically in `VLMGP.sol`) is a pure function of the *current* `userUnlockings` state: `fullyInLock`, `inCoolDown`, and elapsed time since `startTime`/`endTime` [1](#0-0) .
- `vlMGPBaseRewarder._calExpireForfeit` calls this function live at the time rewards are paid out, applying it to the entire accumulated `_amount` (`userRewards[token][account]`, which includes reward-index growth accrued over the whole cooldown period), not just to reward accrued after cooldown started [2](#0-1) .
- `cancelUnlock(_slotIndex)` in `wombat/mWomSV.sol` simply zeroes out `slot.amountInCoolDown` and decrements `totalAmountInCoolDown`, with no reward settlement call at all (contrast with `startUnlock`/`unlock`, which call `IMasterMagpie(masterMagpie).multiclaimFor(...)` before mutating cooldown state) [3](#0-2) . The equivalent `cancelUnlock` in `VLMGP.sol` has the same gap [4](#0-3) .
- `getReward` on the rewarder is guarded only by `onlyMasterMagpie` and `updateReward(_account)`, which runs `_updateFor` to roll `userRewardPerTokenPaid`/`userRewards` up to the current `rewardPerTokenStored` — this update does **not** apply any forfeiture; forfeiture is applied only later in `_sendReward` via `_calExpireForfeit`, using whatever `getRewardablePercentWAD` returns *at send time* [5](#0-4) .

Exploit flow:
1. Attacker locks MGP/mWOM, calls `startUnlock(amount)` to move a share into a cooldown slot.
2. While in cooldown, `queueNewRewards()` calls elsewhere increase `rewardPerTokenStored`; the attacker's `earned()`/`userRewards` accrue against the full `balanceOf` (cooldown-locked shares still count toward `balanceOf` per `vlMGPBaseRewarder.balanceOf` calling `stakingInfo`), since `_earned`/`rewardPerToken` are balance-based and not percent-adjusted at accrual time.
3. Immediately before calling `getReward`/`getRewards`, attacker calls `cancelUnlock(_slotIndex)`, restoring the cooldown amount back to `fullyInLock`.
4. `getReward` is then called (same block/tx via a helper contract or MasterMagpie's `multiclaimFor`), and `_calExpireForfeit` reads `getRewardablePercentWAD` returning ~100% since there's no longer anything in `userUnlockings` cooldown, so `forfeitAmount` computes to 0 despite the accrual history including time spent in cooldown at a materially lower rewardable percent.
5. Attacker receives the full `userRewards[token][account]`, and can immediately call `startUnlock` again to re-enter cooldown, repeating the cycle for future accrual periods.

Existing checks that fail to stop this: there is no time-weighted or checkpointed reward-forfeiture accounting — forfeiture is a spot check at claim time, and `cancelUnlock` provides a free, unlimited-frequency way to manipulate that spot check to zero cost (no cooldown re-entry penalty, no lockup on re-cancel).

### Impact Explanation
This is theft of unclaimed yield that should have been forfeited to other lockers per the protocol's documented forfeiture design (Immunefi impact class: "theft of unclaimed yield"). Every reward-token balance accrued during a user's cooldown period can be fully rescued from forfeiture, and the forfeited amount that should have been redistributed to `_queueNewRewardsWithoutTransfer` (and thus to other non-cooldown lockers) is instead retained by the attacker. This can be repeated indefinitely (start cooldown → wait for reward accrual → cancel just before claim → claim → repeat), scaling with reward inflow and attacker capital (locked MGP/mWOM balance).

### Likelihood Explanation
Fully realizable by an unprivileged EOA: `startUnlock`, `cancelUnlock`, and `getReward`/`getRewards` (via MasterMagpie) are all public/external with no special roles required, gated only by `whenNotPaused`/`onlyMasterMagpie` (satisfied by calling through MasterMagpie's normal claim path) and index-boundary/cooldown-state checks that do not prevent this sequence. It requires no flash loan, only holding one's own locked position, and can be repeated every time meaningful reward inflow accrues, making it high-likelihood and low-cost.

### Recommendation
Snapshot/checkpoint the rewardable percent at the time reward accrues rather than reading it live at claim time — e.g., update `userRewardPerTokenPaid`/apply forfeiture proportionally on every state change that affects `getRewardablePercentWAD` (start/cancel/unlock), or make `cancelUnlock` call `_updateFor`/`multiclaimFor` before restoring `amountInCoolDown` (mirroring `startUnlock`/`unlock`) so at least the reward index is settled before the percent changes, and additionally track forfeiture per time-weighted interval rather than a single spot-check at withdrawal.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`/`mWomSV`, `vlMGPBaseRewarder`/`mWOMSVBaseRewarder`, `MasterMagpie`, and a mock reward token.
2. Fund two users, Alice (control) and Bob (attacker), each locking equal MGP amounts.
3. Both call `startUnlock(amount)` for identical amounts at the same timestamp.
4. Advance time partway through cooldown; call `queueNewRewards()` to accrue significant `rewardPerTokenStored` growth for both.
5. For Alice: directly call `getReward(alice, alice)` while still in cooldown (or after cooldown naturally expires) — record `MGP`/reward token received and forfeited amount via `calExpireForfeit` before send.
6. For Bob: call `cancelUnlock(slotIndex)` immediately followed by `getReward(bob, bob)` in the same transaction (or block) — record received amount.
7. Assert `bobReceived > aliceReceived` for identical accrual/lock history, and assert `forfeitAmount` computed for Bob is 0 or near-zero versus a materially positive value for Alice, demonstrating the conservation invariant violation.

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
```

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
