### Title
Compute unit charge for SBF VM startup (heap cost) occurs after expensive parameter serialization and memory-region setup - (File: `program-runtime/src/vm.rs`)

### Summary
Analogous to the Tally VM issue where gas for VM spin-up (`GAS_STARTUP`) was charged only right before invoking the tally function—after expensive runtime/module/memory setup had already run—Agave's `execute()` function in the SBF loader path performs `serialize_parameters()` (which copies/serializes every instruction account's data into a VM-mapped buffer) and `set_memory_context()` (which builds the full `MemoryMapping`) *before* the `create_vm!` macro charges the compute meter for the VM heap/startup cost.

### Finding Description
The relevant control flow is in `program_runtime::vm::execute()`: [1](#0-0) 

serializes all instruction accounts unconditionally, with cost proportional to total account data size, and: [2](#0-1) 

sets up the memory mapping regions. Only afterward does the `create_vm!` macro attempt to charge the compute meter for the heap cost: [3](#0-2) 

with the actual charge performed via `ComputeMeter::consume_checked`: [4](#0-3) 

There is no upfront check (before `serialize_parameters`/`set_memory_context`) that the remaining compute budget is sufficient to cover the VM startup/heap cost. The caller, `process_instruction_inner` in the BPF loader, invokes `execute()` directly for any non-builtin program with whatever compute is remaining, with no pre-flight compute sufficiency check: [5](#0-4) 

This mirrors the SEDA bug class precisely: the "startup" charge (here, heap cost via `calculate_heap_cost`) is deducted only after already-expensive, unmetered-until-then work (serialization proportional to account data size, memory-region construction) has executed.

### Impact Explanation
An attacker (or any transaction/CPI chain) can arrange for a program invocation to occur with just barely insufficient remaining compute units to cover the heap cost, but with many/large writable accounts attached to the instruction. The runtime will still perform full parameter serialization (copying all account data, potentially large, into VM-mapped buffers) and build the complete memory mapping, before finally failing the heap-cost charge in `create_vm!` and aborting. This is unmetered CPU/memory work that scales with account data size and is not gated by the compute budget, allowing cheaper-than-priced consumption of validator CPU time—a materially underpriced-compute condition, matching the class of the original report (DoS / chain slowdown via cheap-but-expensive-to-process invocations).

### Likelihood Explanation
This path is reachable by any unprivileged user through ordinary top-level instructions or CPI: simply consume most of the compute budget (e.g., via CPI calls or compute-heavy syscalls) then invoke a BPF program with several large writable accounts attached, timed so remaining CUs are just under the heap-cost threshold. No special privileges are required, and the serialization cost scales with attacker-controlled account sizes (up to the loaded-accounts-data-size limit), making repeated exploitation straightforward within normal transaction construction.

### Recommendation
Perform a cheap, early sufficiency check against `invoke_context.get_remaining()` for at least the anticipated heap/startup cost (`calculate_heap_cost(heap_size, ...)`) before calling `serialize_parameters()` / `set_memory_context()` in `execute()`, and bail out early with `ComputationalBudgetExceeded` if insufficient, avoiding the costly serialization and memory-mapping work when the instruction cannot possibly proceed.

### Proof of Concept
Conceptual: construct a transaction/CPI sequence that (a) consumes compute via cheap syscalls/CPIs until remaining CUs are just below the heap cost threshold, then (b) invokes a BPF program instruction referencing several maximally-sized writable accounts. Measure that `serialize_parameters` and `set_memory_context` execute fully (proportional CPU cost to account sizes) before the instruction fails on the heap-cost `consume_checked` inside `create_vm!`, demonstrating unmetered work prior to the compute charge.

macro_rules! create_vm {
    ($vm:ident, $program:expr, $invoke_context:expr $(,)?) => {
        let invoke_context = &*$invoke_context;
        let stack_size = $program.get_config().stack_size();
        let heap_size = invoke_context.get_compute_budget().heap_size;
        let heap_cost_result =
            invoke_context
                .compute_meter
                .consume_checked($crate::__private::calculate_heap_cost(
                    heap_size,
                    invoke_context.get_execution_cost().heap_cost,
                ));
        let $vm = heap_cost_result.and_then(|_| {
            let (mut stack, mut heap) = $crate::__private::MEMORY_POOL
                .with_borrow_mut(|pool| (pool.get_stack(stack_size), pool.get_heap(heap_size)));
            let vm = $crate::__private::create_vm(
                $program,
                $invoke_context,
                stack
                    .as_slice_mut()
                    .get_mut(..stack_size)
                    .expect("invalid stack size"),
                heap.as_slice_mut()
                    .get_mut(..heap_size as usize)
                    .expect("invalid heap size"),
            );
            vm.map(|vm| (vm, stack, heap))
        });
    };

impl ComputeMeter {
    /// Consume compute units
    pub fn consume_checked(&self, amount: u64) -> Result<(), Box<dyn std::error::Error>> {
        let compute_meter = self.0.get();
        let exceeded = compute_meter < amount;
        self.0.set(compute_meter.saturating_sub(amount));
        if exceeded {
            return Err(Box::new(InstructionError::ComputationalBudgetExceeded));
        }
        Ok(())
    }
