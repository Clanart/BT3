### Title
Secp256k1 signature malleability accepted by `sol_secp256k1_recover` syscall and secp256k1 precompile - ([File: syscalls/src/lib.rs], [File: precompiles/src/secp256k1.rs])

### Summary
Both the `sol_secp256k1_recover` BPF syscall and the on-chain secp256k1 precompile `verify()` routine accept ECDSA signatures without enforcing a canonical (low-S) form. Because ECDSA signatures are inherently malleable — for any valid `(r, s, recovery_id)` there exists an equally valid `(r, -s mod n, recovery_id ^ 1)` that recovers to the identical public key — any unprivileged on-chain program (or off-chain client) that treats a secp256k1 signature as a unique nonce/dedup key for replay protection can be bypassed with an alternate, still-valid signature encoding.

### Finding Description
The syscall implementation in `SyscallSecp256k1Recover` parses the signature with `libsecp256k1::Signature::parse_standard_slice` and directly calls `libsecp256k1::recover`, with no check that `s` is in the lower half of the curve order: [1](#0-0) 

The same absence of canonicalization exists in the runtime's secp256k1 native-program verification routine, `agave_precompiles::secp256k1::verify`, which is also directly exercised as a precompile from `process_precompile`: [2](#0-1) 

This is not merely a hypothetical concern — the codebase's own test suite explicitly documents and confirms this behavior as reachable/exploitable at both layers. The syscall test flips the `s` value and recovery id and shows both signatures recover to the *same* public key: [3](#0-2) 

And the precompile's own unit test (`test_malleability`) constructs two distinct-but-valid signatures over the same message and shows `verify()` accepts both as independently valid instructions: [4](#0-3) 

### Impact Explanation
Neither the `sol_secp256k1_recover` syscall (callable by any unprivileged BPF program) nor the secp256k1 precompile enforce canonical low-`s` signatures. Any on-chain program built on top of these primitives (e.g., cross-chain bridges, oracle attestation programs, multisig/guardian verification schemes) that uses the raw signature bytes as a uniqueness key to prevent double-processing of a signed message can be replayed by an attacker who derives the alternate `(r, -s, v^1)` encoding of an already-observed valid signature and resubmits it as "new." This mirrors exactly the EVM SWC-117 class of bug cited in the source report, but here it is exposed to every program author via a core syscall/precompile rather than a single dApp's custom `verify()`.

### Likelihood Explanation
The malleable transform is a pure, deterministic scalar/field operation (`s' = -s mod n`, flip the recovery id) requiring no secret key knowledge, and is directly demonstrated as producing an accepted, identically-recovering signature in the repo's own tests. Exploitability is entirely contingent on downstream program logic that de-duplicates by raw signature bytes rather than by the recovered public key + message + nonce; this is a common but not universal pattern, so likelihood is dependent on consuming-program design, not on the syscall/precompile itself being broken.

### Recommendation
Add an explicit canonical-signature check (reject `s > secp256k1_order/2`, mirroring OpenZeppelin's `ECDSA.sol` `tryRecover` low-s enforcement) inside `SyscallSecp256k1Recover` in `syscalls/src/lib.rs` and inside `agave_precompiles::secp256k1::verify` in `precompiles/src/secp256k1.rs` before calling `libsecp256k1::recover`, or clearly document (beyond internal tests) that consumers of these primitives MUST NOT rely on raw signature bytes for replay protection and must instead dedupe on `(recovered_pubkey, message)`.

### Proof of Concept
The existing repository tests already constitute a PoC demonstrating malleable-signature acceptance: [5](#0-4) [6](#0-5)

    fn test_malleability() {
        agave_logger::setup();

        let secret_bytes: [u8; 32] = rand::random();
        let secret_key = libsecp256k1::SecretKey::parse(&secret_bytes).unwrap();
        let public_key = libsecp256k1::PublicKey::from_secret_key(&secret_key);
        let eth_address = eth_address_from_pubkey(&public_key.serialize()[1..].try_into().unwrap());

        let message = b"hello";
        let message_hash = {
            let mut hasher = keccak::Hasher::default();
            hasher.hash(message);
            hasher.result()
        };

        let secp_message = libsecp256k1::Message::parse(message_hash.as_bytes());
        let (signature, recovery_id) = libsecp256k1::sign(&secp_message, &secret_key);

        // Flip the S value in the signature to make a different but valid signature.
        let mut alt_signature = signature;
        alt_signature.s = -alt_signature.s;
        let alt_recovery_id = libsecp256k1::RecoveryId::parse(recovery_id.serialize() ^ 1).unwrap();

        let mut data: Vec<u8> = vec![];
        let mut both_offsets = vec![];

        // Verify both signatures of the same message.
        let sigs = [(signature, recovery_id), (alt_signature, alt_recovery_id)];
        for (signature, recovery_id) in sigs.iter() {
            let signature_offset = data.len();
            data.extend(signature.serialize());
            data.push(recovery_id.serialize());
            let eth_address_offset = data.len();
            data.extend(eth_address);
            let message_data_offset = data.len();
            data.extend(message);

            let data_start = 1 + SIGNATURE_OFFSETS_SERIALIZED_SIZE * 2;

            let offsets = SecpSignatureOffsets {
                signature_offset: (signature_offset + data_start) as u16,
                signature_instruction_index: 0,

                message_data_offset: (message_data_offset + data_start) as u16,
                message_data_size: message.len() as u16,
                message_instruction_index: 0,

            both_offsets.push(offsets);
        }

        let mut instruction_data: Vec<u8> = vec![2];

        for offsets in both_offsets {
