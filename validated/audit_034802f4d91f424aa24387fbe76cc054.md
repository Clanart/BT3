### Title
Unchecked `IERC20.transfer` return value causes silent reward-payment failure with permanent state desync in ArbWomUp / ArbWomUp2 `incentiveDeposit` - ([File: wombat/ArbWomUp.sol], [File: wombat/ArbWomUp2.sol])

### Summary
`ArbWomUp.incentiveDeposit()` and `ArbWomUp2.incentiveDeposit()` reward callers with USDT/BUSD via a raw `IERC20(...).transfer(...)` call whose boolean return value is never checked, while every other token movement in the same contracts (and the wider codebase) consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`. If the reward token returns `false` on failure instead of reverting, the contract still marks the reward as paid, permanently losing the user's owed yield.

### Finding Description
In `wombat/ArbWomUp.sol`, `incentiveDeposit` is an unprivileged, user-callable entry point: [1](#0-0) 

`claimedReward[msg.sender] += rewardToSend;` is updated *before* checking whether `IERC20(usdt).transfer(msg.sender, rewardToSend)` actually succeeded, and the raw `bool` return value of `transfer` is discarded. The contract otherwise uses `SafeERC20`/`safeTransferFrom` everywhere else (e.g., `_deposit` uses `safeTransferFrom`), showing the transfer-out path was overlooked: [2](#0-1) 

The same pattern recurs in the upgraded `ArbWomUp2.sol`, where `busd` is paid out via a bare `.transfer` with no return-value check, again immediately after `claimedReward` bookkeeping is finalized: [3](#0-2) 

Because `getRewardAmount`/`calDoubledCounted` gate the reward using `claimedReward[_account]` as the source of truth for "already paid" amounts, once `claimedReward` is incremented the user can never re-claim that reward slice through this contract again — regardless of whether the token transfer that was supposed to pay it actually succeeded: [4](#0-3) 

### Impact Explanation
If the configured reward token (`usdt`/`busd`) is a non-standard ERC20 that returns `false` on failure rather than reverting (e.g., paused, blacklist-based, or otherwise non-reverting token implementations, which is a realistic possibility since these addresses are admin-configurable via `__arbWomUp_init`/`setup`), a normal user calling `incentiveDeposit` will have their WOM deposit accepted (`safeTransferFrom` succeeds) and `claimedReward` permanently incremented, but never receive the corresponding USDT/BUSD reward. This is a permanent, unrecoverable loss of the user's earned yield with no compensating mechanism, matching the "permanent freezing/loss of unclaimed yield" impact bar.

### Likelihood Explanation
The trigger condition depends on the specific reward-token implementation deployed/configured by the admin at a given point in time (transfer failing without reverting), and is not guaranteed for every ERC20. This makes the bug real and directly reachable by any unprivileged caller of `incentiveDeposit`, but its likelihood is conditional on the token behavior rather than always exploitable, consistent with a Medium-severity classification (mirroring the original Swivel-return-value finding's severity).

### Recommendation
Replace the raw `IERC20(usdt).transfer(...)` / `IERC20(busd).transfer(...)` calls in both `ArbWomUp.incentiveDeposit` and `ArbWomUp2.incentiveDeposit` with `SafeERC20.safeTransfer`, consistent with the rest of the codebase's token-movement calls. Alternatively, explicitly capture and `require()` the boolean return value before updating `claimedReward`.

### Proof of Concept
1. Admin deploys `ArbWomUp` with `usdt` pointed at an ERC20 whose `transfer` returns `false` on failure instead of reverting (e.g., a token with a pausable/blacklist transfer path that returns false).
2. A user calls `incentiveDeposit(_amount)`; `_deposit` succeeds (`safeTransferFrom` pulls WOM), `rewardToSend` is computed, `claimedReward[msg.sender] += rewardToSend` executes.
3. `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` (e.g., token temporarily paused or user hits a token-level restriction) — execution continues normally since the return value is discarded, and `USDTRewarded` is still emitted.
4. The user never receives the USDT reward, and because `claimedReward[msg.sender]` was already incremented, `getRewardAmount` will compute a reduced/zero reward on any future call, permanently denying the user that portion of yield.

        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 busdReward = (rewardAmount / DENOMINATOR) - this.calDoubledCounted(_account);
        uint256 busdleft = IERC20(busd).balanceOf(address(this));

        return busdReward > busdleft ? busdleft : busdReward;
    }
