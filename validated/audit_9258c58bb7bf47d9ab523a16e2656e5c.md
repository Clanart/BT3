## Analysis

The Hats-protocol bug pattern is: two functions that are supposed to enforce the *same* invariant, but only one of them actually enforces it, so callers relying on the unguarded twin get bypassed results. GitHub Desktop has a directly analogous pattern in its merge-conflict / Copilot-resolution code, around the `resolveWithin` symlink/traversal guard.

### Title
Unguarded filesystem read of conflicted file content allows symlink-based disclosure of files outside the repository - (File: `app/src/lib/git/diff.ts`)

### Summary
`buildConflictContext`, which gathers conflicted-file content to send to the Copilot conflict-resolution feature, explicitly guards every file read with `resolveWithin` to block path traversal and symlink escapes. `getResolutionDiff`, which renders the same conflicted file's content in the "Changes" diff preview of the very same Copilot conflict-resolution dialog, reads the identical class of path (`repository`-relative `filePath` for a conflicted `WorkingDirectoryFileChange`) but does so with a raw `Path.join` + `readFile`, with no equivalent guard.

### Finding Description
`buildConflictContext` treats a conflicted file's on-disk path as untrusted and resolves it defensively: [1](#0-0) 

`getResolutionDiff`, used by the same feature's "Changes" tab (`CopilotConflictsChanges.loadDiffForFile`) to show a preview diff for the exact same conflicted files, instead does: [2](#0-1) 

`Path.join(repository.path, filePath)` performs no traversal/symlink check, and Node's `readFile` follows symlinks. `resolveWithin` (`app/src/lib/path.ts`) is the codebase's canonical guard for exactly this: it resolves the path, `realpath`s both the root and the resolved target, and rejects anything whose real path escapes the root — precisely to stop "a symlink to traverse outside of the root," as covered by the project's own tests: [3](#0-2) 

`filePath` here comes from `conflictedFiles[i].path`, i.e. a tracked path from a merge/rebase/cherry-pick that the attacker's repository/branch controls. Git's own merge algorithm can leave a symlink materialized at a conflicted working-tree path (e.g. a type-change conflict where one side is a regular file and the other is a symlink); git does not block a symlink from being the on-disk state of a conflicted entry. If that symlink target resolves outside the repository (e.g., to `~/.ssh/id_rsa`, `~/.aws/credentials`, or any file readable by the Desktop process), the guarded function (`buildConflictContext`) will refuse to read it, but `getResolutionDiff` will silently follow the symlink and load the target file's bytes into `baseContent`, which then get written into a temp file, diffed, and rendered directly in the Copilot conflict resolution UI (`copilot-conflicts-changes.tsx`'s `loadDiffForFile`): [4](#0-3) 

### Impact Explanation
This is a file read outside the repository triggered purely by content that ships inside a fetched/merged repository — no local access, admin rights, or pre-existing malware needed. The attacker only needs to get the victim to merge, rebase, or cherry-pick a branch (their own PR, a `git pull`, etc.) that produces a type-change conflict where the conflicted path is a symlink pointing at a sensitive file. Opening the built-in Copilot conflict-resolution "Changes" view (which is a normal, expected part of resolving conflicts, not an "unnatural user step") is enough to have the target file's content decoded into the diff/temp files and rendered in-app, matching the report's "file read outside the repo" / "credential exfiltration" impact class.

### Likelihood Explanation
Moderate-to-high: the Copilot conflict-resolution flow auto-loads a diff for the initially selected conflicted file on mount (`componentDidMount` → `loadDiffForFile`), and re-loads it whenever selection changes, so the vulnerable code path executes automatically as soon as the dialog opens for a conflict set containing the malicious entry — it is not an edge-case path. The sibling function in the same feature (`buildConflictContext`) already demonstrates the maintainers are aware this class of input requires a symlink/traversal guard, which makes the omission in `getResolutionDiff` a straightforward inconsistency rather than a deliberate design choice.

### Recommendation
Route `getResolutionDiff`'s working-tree read through the same guard used elsewhere in this feature, e.g.:
```ts
const absolutePath = await resolveWithin(repository.path, filePath)
if (absolutePath === null) {
  // treat as unreadable / skip, consistent with buildConflictContext
}
const baseContent = await readFile(absolutePath, 'utf8')
```
mirroring `app/src/lib/copilot-conflict-context.ts:390-407`, so both code paths that read a conflicted file's content enforce the identical containment invariant.

### Proof of Concept
1. Attacker prepares a branch where a tracked path `secret-link` is a symlink pointing to `../../../../.ssh/id_rsa` (or an absolute path to a sensitive file), while the victim's current branch has `secret-link` as a normal tracked text file.
2. Victim fetches and merges/rebases the attacker's branch in Desktop; git reports a type-change conflict on `secret-link`, leaving the symlink materialized in the working tree.
3. Victim opens the "Resolve conflicts with Copilot" dialog's Changes tab; `CopilotConflictsChanges` auto-selects `secret-link` and calls `getResolutionDiff(repository, 'secret-link', ...)`.
4. `getResolutionDiff` executes `readFile(Path.join(repository.path, 'secret-link'), 'utf8')`, following the symlink and loading the private key's contents into `baseContent`, which is written to a temp file and diffed/rendered in the UI — disclosing file content from outside the repository.
