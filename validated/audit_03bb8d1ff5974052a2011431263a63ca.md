### Title
Deterministic nonce reuse across `share`/`complete` calls within one DKG confirmation context enables recovery of a validator's MuSig secret share - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
CVE-2021-21204 is a use-after-free: an object is used after its lifetime should have ended, corrupting derived state. The Serai analog is the reuse of a `CachedPreprocess` after it should have been invalidated — the coordinator persists the FROST preprocess seed keyed only by `("DkgConfirmer", attempt)`, re-derives identical secret nonces on every call to `preprocess_internal`/`share_internal`, and never deletes the cache. FROST explicitly documents that reusing a cached preprocess enables third-party recovery of the private key share.

### Finding Description
`SigningProtocol::preprocess_internal` encrypts and stores a `CachedPreprocess` under `CachedPreprocesses: (context) -> [u8; 32]` where the context is `(b"DkgConfirmer", self.attempt)`. On every subsequent call it reads the same seed back and calls `AlgorithmSignMachine::from_cache`, which deterministically regenerates the same nonces via `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:127). The entry is never cleared after `share_internal` runs, violating the documented contract that the preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share" and that after `from_cache` "the preprocess must be deleted so it's never reused" (crypto/frost/src/sign.rs:85-92, 216-219).

`share_internal` is invoked by `DkgConfirmer::share` (line 304) and again by `DkgConfirmer::complete` (line 321), each time re-deriving the same nonce machine. The safety argument in the module doc (lines 25-48) relies entirely on the BFT layer guaranteeing identical received messages — but it binds the nonce to `(b"DkgConfirmer", attempt)` only, not to `key_pair` or to the specific preprocess set. The signed message is `set_keys_message(&self.spec.set(), &removed, key_pair)`, so two invocations of `share_internal` within the same attempt that differ in either `key_pair` or in the finalized preprocess set produce two signature shares `s = d + b·e·ρ_l + λ_i·x_i·c` under identical `d`, `e`, and differing `ρ_l`/`c` — a linear system that yields the validator's MuSig secret share `x_i`. This is the classical ROS/FROST nonce-reuse key-recovery attack, triggered by determinism rather than RNG failure.

Unverified reachability detail (tool budget exhausted): I confirmed `DkgConfirmer::share`/`complete` are driven from `coordinator/src/tributary/handle.rs` per tributary transaction, but did not fully verify whether a single attempt can legitimately observe two distinct `key_pair` values or two distinct finalized preprocess sets (e.g., a first `share` on a preprocess set, then `complete` on a differing one, or competing key-pair candidates in one attempt). The `expect`/unreachable paths suggest the author assumes a single consistent call, yet nothing in `share_internal` enforces this — no marker is written after the first share to forbid a second, differently-parameterized call.

### Impact Explanation
Recovery of a validator's MuSig secret share for the set's DKG confirmation signing. This key is the validator's root-of-trust key used to confirm validator sets on Substrate; its compromise lets an attacker forge `set_keys` confirmations (combined with quorum participation) and pivot to broader consensus trust violations — the same impact class as the upstream heap-corruption finding (corrupted secret state from a lifetime violation).

### Likelihood Explanation
Conditional on reachability of a second, distinct `share_internal` under one attempt: the code itself states the BFT layer is the only protection and explicitly flags unresolved TODOs ("we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)", "review how we're handling Processor preprocesses"). Any path that re-fires share generation for an attempt with different preprocesses or a different key pair — reboot-and-re-execute ordering differences, or a tributary transaction carrying a different `KeyPair` — silently produces nonce reuse. Medium likelihood.

### Recommendation
Delete the `CachedPreprocesses` entry after first consumption in `share_internal` (single-use semantics), and additionally bind the derived nonces to the full signing context — hash `key_pair` and the sorted preprocess set into the seed or into a one-time-use guard keyed on `(context, msg_hash, preprocess_set_hash)` that rejects any second call with different parameters, matching the TODO of verifying published commitments against presumed nonces before emitting shares.

// set_keys candidate KeyPairs (or two differing preprocess sets).
let mut confirmer = DkgConfirmer::new(&key, &spec, &mut txn, attempt).unwrap();

// First call: nonces derived from CachedPreprocesses[("DkgConfirmer", attempt)]
let share_a = confirmer.share(preprocesses.clone(), &key_pair_a).unwrap();

// Second call: identical seed -> identical (d, e); different msg -> different c.
// share_b uses the same nonce scalars.
let share_b = confirmer.share(preprocesses, &key_pair_b).unwrap();
