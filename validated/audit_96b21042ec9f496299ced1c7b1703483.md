### Title
`ReceivedOutput::read` accepts an unauthenticated offset with no binding to the output's `script_pubkey`, allowing forged/unspendable outputs to enter the wallet - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a missing-authentication flaw: an installer endpoint performs a privileged write (`updateOrInsert` on the admin row) gated only by a check an unauthenticated client can bypass. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`, which deserializes an attacker-supplied scalar `offset`, `TxOut`, and `OutPoint` with no consistency check whatsoever. `Scanner::scan_transaction` is the only honest producer of `ReceivedOutput`, and it guarantees `offset` is the registered scalar satisfying `script_pubkey == P2TR(key + offset*G)`. `read` reconstructs the object from raw bytes while dropping that invariant entirely — the equivalent of writing privileged state without verifying the caller is authorized to set it.

### Finding Description
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) does:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

The `offset` field is the secret-free *spend offset*: the output is spendable only if `output.script_pubkey` equals the P2TR script for `key + G*offset` (see `Scanner::register_offset`, lines 180-196, and `scan_transaction`, lines 199-214, which is the only code path that correctly establishes this relation via `self.scripts.get(&output.script_pubkey)`). `read` performs no such check: any `offset` is accepted for any `output`. There is also no check that the `OutPoint` refers to the transaction that actually contained `output`.

Any consumer that treats a deserialized `ReceivedOutput` as a genuine received output — e.g., feeding it into `send.rs` spend construction, which signs under `key + offset` — will produce signatures for a key that does not match the on-chain script, or will attempt to spend outpoints that were never scanned.

### Impact Explanation
Per the accepted impact classes, this yields **funds reported received that are not spendable** (or not actually received):

- An attacker supplying crafted bytes to `ReceivedOutput::read` can attach an arbitrary `offset` to a real or fabricated `TxOut`/`OutPoint`. The wallet then reports a received output whose implied spend key (`key + offset*G`) does not correspond to the output's `script_pubkey`, so no valid threshold signature can ever spend it — funds are counted but unspendable, or a nonexistent deposit is recorded.
- Because the attacker cannot produce `script_pubkey = key + offset*G` for a key they control (the group key's discrete log is unknown), the impact is misattributed/unspendable outputs rather than theft — capping severity at **Medium**.
- In an automated pipeline, signing attempts against these outputs waste nonce preprocesses and can stall legitimate spends queued behind them.

### Likelihood Explanation
Reachable whenever untrusted bytes are passed to `ReceivedOutput::read` — e.g., output records relayed across process/network boundaries rather than produced locally by `Scanner::scan_transaction`. It requires no privilege and no collusion; the attacker only needs to control the serialized buffer. Exploitation does not compromise key material, so likelihood is real but the ceiling is integrity-of-wallet-state rather than key recovery.

### Recommendation
Either make `ReceivedOutput` deserialization self-validating or keep it impossible to construct an invalid one:

- Add a `ReceivedOutput::read`-time check that recomputes `p2tr_script_buf(key + G*offset)` and compares it to `output.script_pubkey` (requires storing/Passing the scanner's base key, or moving `read` onto `Scanner` so the registered `scripts` map can be consulted — returning `Err` if `scripts.get(&output.script_pubkey) != Some(offset)`).
- Alternatively, restrict construction to `Scanner` (private fields, no public `read` producing unvalidated state) and serialize `ReceivedOutput` only as `(OutPoint)` with the offset re-derived from the scanner at load time.

### Proof of Concept
1. Let `K` be the threshold group key and `S = Scanner::new(K)` with a registered offset `o` for script `P`.
2. Attacker serializes: `offset' = <arbitrary scalar>` (e.g., `o + 1`), `output` = a real P2TR `TxOut` paying to some script `P'` unrelated to `K + (o+1)*G`, and any `OutPoint`.
3. `ReceivedOutput::read` returns `Ok` — no rejection path exists.
4. Wallet records the output as received with value `output.value`; spend construction signs with key `K + offset'*G`, which does not correspond to `P'`, so the transaction is invalid / the funds are unspendable despite being reported as received.

Confidence note: I verified `ReceivedOutput::read`, `Scanner::register_offset`, and `scan_transaction` directly; I did not fully trace `send.rs` consumers, so the exact downstream spend path is inferred from `offset()`'s documented role as "the scalar offset to obtain the key usable to spend this output" (mod.rs:91-92).
