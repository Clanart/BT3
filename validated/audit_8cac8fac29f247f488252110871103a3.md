### Title
`ThresholdKeys::read` accepts key sets without verifying the secret share or fixing the group key, enabling crafted "wallets" whose group key an attacker secretly controls - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes attacker-controlled `t`, `n`, `i`, `interpolation`, `secret_share`, and `verification_shares`, then passes them to `ThresholdKeys::new`. `new` computes `group_key` solely as the interpolation of `verification_shares[1..=t]` and never checks that `C::generator() * secret_share == verification_shares[i]` (nor that any verification share outside `1..=t` is consistent). An unprivileged party that can feed bytes into `ThresholdKeys::read` can therefore hand the victim a fully self-consistent key set whose group key's discrete logarithm — and every signing set's effective key — is known to the attacker. This is the direct analog of the Chivo wallet-theft incident: the victim "owns" a wallet whose private key the attacker actually holds.

### Finding Description
`ThresholdKeys::new` builds the group key as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [1](#0-0) 

The only validation performed is a count check (`verification_shares.len() == n`), an index bound (`participant <= n`), and the `Constant`-interpolation `t == n` restriction [2](#0-1) . There is no check anywhere that `secret_share * G == verification_shares[params.i()]`, and no check that the remaining shares `t+1..=n` interpolate to the same key — they are simply indexed into later by `view()` [3](#0-2) .

`read` trusts all of these fields from the wire, including the `Interpolation::Constant` coefficient vector (which makes the `interpolation_factor` entirely attacker-chosen constants rather than Lagrange coefficients) [4](#0-3) .

### Impact Explanation
Because `view()` interpolates `secret_share` against `included` and `ThresholdView::secret_share()` is what `sign_share` consumes, an attacker who constructs the serialized keys can produce a key set that:

- Reports a `group_key()` the attacker knows the discrete log of (they choose `verification_shares[1..=t]` as `k_j * G` with known `k_j`, so `dlog(group_key) = Σ λ_j·k_j` is known), and
- Still passes every subsequent consistency check: `view()` recomputes interpolated verification shares from the same map, so `sign()` produces shares that verify against `verify_share`, and `recover_key`'s final `G * res == group_key` check also passes if `secret_share` is set to the corresponding `dlog(verification_shares[i])` [5](#0-4) .

The victim therefore treats funds/keys at this `group_key` as theirs while the attacker holds the equivalent private key — wallet theft — or, alternatively, the attacker sets inconsistent `t+1..=n` shares so funds received are unspendable by the honest threshold (only subsets within `1..=t` ever cohere), both matching accepted impact classes.

### Likelihood Explanation
Requires an integration path where `ThresholdKeys::<C>::read` consumes bytes not produced by the node's own DKG/`serialize()` — e.g., key import, backup restore, or peer-supplied key material. Within the in-scope surface, `read` performs curve-ID binding and parameter validation but no cryptographic binding between `secret_share`, `verification_shares`, and `group_key`, so the attack needs only chosen bytes and no misbehavior by other validators. Medium likelihood: exploitation depends on an untrusted-bytes reachability path, but requires no collusion and no probabilistic wins.

### Recommendation
In `ThresholdKeys::new`, assert `C::generator() * secret_share == verification_shares[&params.i()]`. Additionally, for `Interpolation::Lagrange`, verify that the supplied `verification_shares` are consistent for all `n` participants (e.g., that the group key recomputed over any `t`-subset is identical, or document that `read` must only ever consume locally-produced bytes and enforce that contract in callers). At minimum, check the `group_key` implied by `1..=t` equals the group key implied by the expected signing sets the node will use.

### Proof of Concept
Attacker constructs bytes for `ThresholdKeys::<C>::read` (format per `write`/`read` at `crypto/dkg/src/lib.rs:565-633`):

1. Pick `t = n` (e.g., 2), `i = 1`, interpolation byte `0` (`Constant` with coefficients `[1, 1]` — permitted since `t == n`).
2. Choose scalars `k_1, k_2`; set `verification_shares = {1: k_1·G, 2: k_2·G}`.
3. Set `secret_share = k_1` so the own-share consistency holds under `view()`.

Result: `keys.group_key() = k_1·G + k_2·G = (k_1 + k_2)·G`, whose private key `k_1 + k_2` is known to the attacker. `keys.view([1, 2])` succeeds, `sign()` emits shares that pass `verify_share`, and `recover_key` succeeds — yet every signature under this "wallet" is replicable by the attacker alone, and any funds addressed to `group_key` are the attacker's, mirroring the Chivo wallet theft class.
