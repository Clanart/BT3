## Analog Identified

The ENS bug's core broken invariant: **an external transfer/callback executes before the contract's internal bookkeeping (ownership/fuses) is finalized**, letting the callback re-enter and detach the token record from the real custody state. The Hyperbridge local analog is the **same checks-effects-interactions inversion** in the Tron IntentGatewayV2's escrow-release path, which reinstates a pattern the EVM sibling contract deliberately fixed with a CEI reorder (confirmed by `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` and `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`).

### Title
Escrow accounting decremented *after* external token transfer in `withdraw` allows reentrant double-release via malicious input token - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw` on the Tron variant performs the external transfer call to the beneficiary **before** decrementing the escrow accounting for that token, and only checks that the escrow slot is non-zero rather than checking it is sufficient for the amount being paid out.

### Finding Description
In the fixed EVM path, `_withdraw` in `IntentsBase.sol` decrements `_orders[commitment][token]` before making the external call: [1](#0-0) 

The Tron `withdraw` function reverses this order — it calls out to the beneficiary/token *first*, and only updates `_orders[commitment][token]` afterward: [2](#0-1) 

The guard at line 691 (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`) only verifies the escrow slot is non-zero — it never checks `amount <= _orders[body.commitment][token]`. Because `token` is attacker-supplied (it comes from `order.inputs[i].token`, chosen freely when the attacker calls `placeOrder`), an attacker can register a malicious "ERC20" as one of the order's input tokens. When `withdraw` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for that entry, the malicious token contract's code runs *before* `_orders[commitment][token] -= amount` executes. At that point in execution, the storage still reflects the full pre-payout escrow balance for that token — the on-chain bookkeeping has not yet caught up with the just-issued transfer, exactly mirroring the NameWrapper pattern where `owner`/fuses lag behind the ERC1155 transfer.

`_filled[body.commitment]` is set at the very top of `withdraw` (line 684), which blocks reentry into `fillOrder`'s `Filled()`-guarded surface, but it does **not** protect the per-token escrow bookkeeping itself, since the decrement for other tokens/legs in the same `body.tokens` array, or any other function that reads `_orders[commitment][token]` for that specific token before the decrement lands, will still observe the stale, un-debited balance.

### Impact Explanation
This is a direct violation of the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant. The order-of-operations bug means the transfer and the accounting update are not atomic from the perspective of any code executed inside the token's `transfer` hook, creating the same class of "detached" state the ENS report describes: value has already left custody while the ledger still shows it present.

### Likelihood Explanation
The attacker needs no relayer, prover, or admin — they simply need to register their own malicious token contract as one of `order.inputs` when calling the public, unprivileged `placeOrder`, and have it eventually settle via `withdraw` (called from `onAccept` upon proof-verified message delivery). This is fully attacker-controlled input, unlike the relayer/prover assumptions explicitly excluded by the bounty scope.

### Recommendation
Apply the same CEI fix already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` by `amount` (and validate `amount <= escrowed`, not merely `escrowed != 0`) before performing any external call or token transfer, for every token in the loop.

### Proof of Concept
1. Attacker calls `placeOrder` with one input token set to a contract they control that implements `IERC20.transfer` with a hook (returns `true` but executes arbitrary logic first).
2. Order proceeds through the normal fill/cross-chain flow until `onAccept` → `withdraw` is invoked for that commitment.
3. In the loop, `withdraw` reaches the attacker's token, calls `token.call(...transfer...)` — control transfers into the attacker's contract **before** `_orders[commitment][token] -= amount` runs.
4. Inside that hook, `_orders[commitment][token]` still shows the pre-payout (undebited) balance; any code path reachable from there that reads this value operates on stale escrow state, breaking the exactly-once payout invariant that later loop iterations / fee release depend on.

**Confidence caveat:** I was not able to fully trace, within the available searches, a second public function that reads `_orders[commitment][token]` mid-callback to complete a concrete double-payout in the same transaction (e.g., confirming whether `cancelOrder`'s guard also checks `_filled` before dispatching a refund). The CEI-ordering defect itself, however, is directly evidenced in the code and is a verbatim regression of a pattern the project's own EVM implementation and test suite (`IntrinsicIntentsReentrancyTest.sol`) treats as a confirmed, fixed vulnerability class.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
