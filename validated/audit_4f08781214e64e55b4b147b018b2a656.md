### Title

Untrusted fee-rate input causes arithmetic-overflow denial of service - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` multiplies a caller-controlled `fee_per_vbyte` by the transaction’s calculated virtual size without checking for `u64` overflow. [1](#0-0)  In builds with overflow checks enabled, a large public fee-rate argument causes an immediate panic instead of returning `TransactionError`. [2](#0-1) 

### Finding Description

The transaction constructor accepts `fee_per_vbyte` as a public `u64` argument. [2](#0-1)  It computes `vbytes` from the supplied inputs and outputs, then evaluates `fee_per_vbyte * vbytes` directly. [3](#0-2)  No bound is placed on `fee_per_vbyte`, and `vbytes` is nonzero for any transaction that passes the earlier nonempty input/output validation. [4](#0-3)  Therefore, values such as `u64::MAX` reliably overflow before fee validation occurs. [5](#0-4) 

### Impact Explanation

An unprivileged caller able to submit transaction-construction parameters can abort the current thread or process when overflow checks are enabled. [2](#0-1)  This converts malformed public input into a denial of service rather than a recoverable `TransactionError`. [6](#0-5) 

### Likelihood Explanation

The attack requires only an unusually large `fee_per_vbyte` value and otherwise valid minimal transaction parameters. [2](#0-1)  No private key material, valid blockchain output, signature, or privileged role is needed because the overflow occurs while deriving the required fee. [1](#0-0) 

### Recommendation

Replace `fee_per_vbyte * vbytes` with `checked_mul` and return an existing or new `TransactionError` on overflow. [5](#0-4)  The later `payment_sat + needed_fee` addition should likewise use `checked_add`, and fee arithmetic should consistently reject values exceeding `u64`. [7](#0-6) 

### Proof of Concept

```rust
use networks_bitcoin::wallet::{ReceivedOutput, SignableTransaction};
use bitcoin::{Amount, OutPoint, ScriptBuf, TxOut};

fn overflow_fee(input: ReceivedOutput) {
    let payment_script = ScriptBuf::new();

    // Any nonzero vbytes makes this multiplication overflow.
    let _ = SignableTransaction::new(
        vec![input],
        &[(payment_script, 546)],
        None,
        None,
        u64::MAX,
    );
}
```

A `ReceivedOutput` can be supplied by the caller through transaction-construction inputs, while `fee_per_vbyte` is directly caller-controlled. [2](#0-1)  With `u64::MAX` as the fee rate, execution reaches `fee_per_vbyte * vbytes` and panics under overflow checks. [3](#0-2)
