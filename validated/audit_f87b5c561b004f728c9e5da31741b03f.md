### Title
Unrestricted scheme pass-through in `open-external` IPC handler allows OS protocol-handler invocation from untrusted content - (`app/src/main-process/main.ts`)

### Summary
The main-process IPC handler for `open-external` forwards any string supplied by the renderer directly to Electron's `shell.openExternal()` with no scheme allowlist. The `http://`/`https://` check that exists in the handler is only used for logging, not for gating the call, so any URI scheme reaches the OS shell.

### Finding Description
The handler is registered as: [1](#0-0) 

```
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```
The `if` block only decides whether to write an informational log line — there is no `else`/`return`/`throw` that blocks non-http(s) values from reaching `shell.openExternal(path)`. Consequently, any scheme (`file://`, `javascript:`, a registered custom protocol, or on Windows a shell command URI such as those abused via `search-ms:` or similar handlers) is passed straight to the OS.

On the renderer side, this channel is exposed with no additional validation through the proxy chain: [2](#0-1) 

which is wired into the app-wide shell abstraction: [3](#0-2) 

and ultimately invoked by generic UI components such as `LinkButton`, which calls `shell.openExternal(uri)` on click with no scheme check of its own: [4](#0-3) 

`LinkButton`/`shell.openExternal` are the general-purpose mechanisms used to open links rendered from remote content (issue/PR bodies, markdown, release notes, etc.) throughout the renderer, so if any such untrusted-content renderer surfaces a clickable URI to the user (rather than opening it automatically), a click funnels an attacker-chosen string all the way to the OS shell.

### Impact Explanation
`shell.openExternal` with an unrestricted scheme is a well-known Electron security anti-pattern: depending on OS and installed handlers, it can be used to invoke local applications, trigger OS deep-link/protocol handlers, or (historically, on Windows) leverage certain URI schemes to reach `cmd`/`PowerShell`-adjacent behavior via specific registered handlers. This is a renderer-to-OS boundary crossing driven entirely by attacker-controlled content (a repository's issue/PR body or markdown), matching the "renderer-sandbox/IPC escape" impact category, since it takes attacker input that should be confined to the browser/render sandbox and lets it reach OS-level protocol dispatch outside of Electron/Chromium's own scheme restrictions.

### Likelihood Explanation
Exploitability requires the user to click a rendered link whose `href`/`uri` value is attacker-controlled (e.g., an issue/PR body or markdown content rendered in the app) and is passed to `LinkButton`/`shell.openExternal` instead of being routed through some other renderer-only handling. I was not able to fully confirm within index limits whether the markdown renderer (`app/src/ui/lib/sandboxed-markdown.tsx`) intercepts/sanitizes `href` values (e.g. restricting to `http`/`https`) before they reach `LinkButton`/`openExternal`, since that file's click-interception logic was not retrieved in the available search results. If such a scheme filter exists upstream in the markdown click handler, this could reduce practical reachability for markdown-rendered content specifically, though the IPC handler itself remains unrestricted for any other caller of `openExternal` (e.g., deep links, PR quick view, notifications).

### Recommendation
Add an explicit scheme allowlist inside the `open-external` IPC handler in `app/src/main-process/main.ts` (e.g., only allow `http:`/`https:`, and `mailto:` if needed), rejecting/logging-and-refusing anything else before calling `shell.openExternal`, so the safety boundary is enforced at the trust boundary (main process) rather than relying on renderer-side callers to pre-filter.

### Proof of Concept
From the renderer devtools console (or any component with access to the app's IPC bridge):
```js
await ipcRenderer.invoke('open-external', 'malicious-scheme://payload')
```
Tracing the handler in `app/src/main-process/main.ts:581-597` shows this string fails the `http://`/`https://` prefix check but is not rejected — it falls through unconditionally to `shell.openExternal(path)` at line 591, confirming the call is made regardless of scheme. [1](#0-0)
