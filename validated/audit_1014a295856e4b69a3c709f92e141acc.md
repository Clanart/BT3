### Title
Unbounded attacker-controlled loop in `SchnorrAggregate::read`/`verify` enables resource-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report describes a loop whose iteration count is bounded only by the size of an attacker-controlled array, so that once the required resources exceed the block's allocation every iteration fails and the operation can never complete (denial of service). The direct analog in Serai is `SchnorrAggregate`: its `read` function trusts a `u32` count field to size a `Vec<C::G>` with no maximum check, and its `verify` function then performs per-element transcript hashing and multiexponentiation over that attacker-sized vector. An unprivileged party who can cause an untrusted byte stream to be passed to `SchnorrAggregate::read` or a large `keys_and_challenges` slice to `verify` can force unbounded, quadratic-cost work per call.

### Finding Description
`SchnorrAggregate::read` reads a 4-byte little-endian length and then loops `u32::from_le_bytes(len)` times calling `C::read_G(reader)`, pushing each decoded point into `Rs` (crypto/schnorr/src/aggregate.rs:77-88). There is no sanity bound on the count — it can be up to ~4.29 billion, limited only by however many bytes the caller is willing to stream. Unlike the coordinator-side `Transaction::DkgCommitments` reader, which explicitly rejects `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT`, this reader performs no maximum-elements check.

The heavier cost is in `verify` (crypto/schnorr/src/aggregate.rs:127-146):

```rust
for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
  let z = weight(&mut digest);
  ...
}
```

Each call to `weight` (lines 22-65) hashes the full accumulated `DigestTranscript` and then performs ~`NUM_BITS + 128` sequential scalar doublings/ additions (`for _ in 0 .. WORD_LEN_IN_BITS { res += res; }` per 64-bit word). Because the digest already contains every previously appended `challenge` message, each iteration re-hashes O(n) transcript data, making total verification work quadratic in the number of aggregated signatures — all driven by attacker-supplied input, with no cap anywhere in the call chain.

### Impact Explanation
Any node/service that deserializes or verifies a `SchnorrAggregate` supplied by an untrusted peer (the same trust model as `SchnorrSignature::read`/`Commitments::read`, which the scope rules treat as attacker-reachable) can be made to burn CPU/memory proportional to — and in `verify`, quadratic in — the declared signature count. In a consensus or validator context this is exactly the reported failure mode: the work required to process one message exceeds what can be executed before timeout/block-gas limits, so the operation can never succeed and the node is stalled or the batch repeatedly fails. This is a Medium-severity availability issue reachable purely from public input bytes; it leaks no secrets.

### Likelihood Explanation
An attacker needs only to present a `SchnorrAggregate` serialization (or a verification request) with a large signature count. `read` accepts any `u32` count; `verify` only checks `self.Rs.len() == keys_and_challenges.len()`, not a maximum. Each 32-byte encoded point adds ~64 scalar doublings plus a growing transcript hash. A few thousand signatures already yields millions of field operations per verification attempt, and the count is bounded only by message size, not by any protocol constant (e.g., threshold `t` or participant count `n`).

### Recommendation
Bound the aggregation size at both layers:

- In `SchnorrAggregate::read`, reject counts above a protocol-meaningful maximum (e.g., the maximum participant set size, `u16::MAX`, or an explicit `MAX_AGGREGATE`) before allocating/looping, mirroring the `TRANSACTION_SIZE_LIMIT` guard used in `coordinator/src/tributary/transaction.rs`.
- In `verify`, early-return when `keys_and_challenges.len()` exceeds that bound.
- Optionally precompute weights incrementally (e.g., a single challenge stream) to remove the quadratic re-hashing in `weight`.

### Proof of Concept
```rust
use io::Cursor;
use serai_schnorr::aggregate::SchnorrAggregate; // path: crypto/schnorr/src/aggregate.rs

// Attacker-crafted input: u32 count = u32::MAX followed by a large
// buffer of valid (or merely well-formed) point encodings.
let mut buf = u32::MAX.to_le_bytes().to_vec();
buf.extend(std::iter::repeat(valid_point_bytes).flatten().take(N * POINT_LEN));

// read() iterates min(u32::MAX, available points) times with no cap:
let agg = SchnorrAggregate::<C>::read(&mut Cursor::new(&buf)).unwrap();

// verify() then does O(n * 64) scalar doublings and O(n^2) transcript
// hashing — unbounded work driven entirely by attacker bytes:
agg.verify(b"dst", &keys_and_challenges); // keys_and_challenges.len() == agg.Rs().len()
```

Relevant code: `SchnorrAggregate::read` loop over `u32` count (crypto/schnorr/src/aggregate.rs:77-88), `weight` per-signature wide reduction (crypto/schnorr/src/aggregate.rs:22-65), and the unbounded `verify` loop (crypto/schnorr/src/aggregate.rs:127-146).

Note on scope: the crypto crates themselves do not enforce gas/size accounting; whether a given deployment exposes `SchnorrAggregate::read`/`verify` on attacker-controlled bytes determines real-world exploitability, but within the stated reachability model (untrusted bytes fed to `read`/`verify` APIs) the analog stands on Serai's own code.
