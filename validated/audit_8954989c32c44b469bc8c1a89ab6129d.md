### Title
Incomplete Unicode bidi-character detection regex allows Trojan-Source style diffs to bypass Desktop's hidden-character warning - (File: `app/src/lib/diff-parser.ts`)

### Summary
GitHub Desktop warns users when a diff contains "invisible bidirectional Unicode characters" via `HiddenBidiCharsRegex` in [1](#0-0) . This regex only matches the explicit-embedding/override characters (`U+202A`–`U+202E`) and the isolate characters (`U+2066`–`U+2069`), but omits the directional-mark characters `U+200E` (LRM), `U+200F` (RLM), and `U+061C` (ALM), which are also part of the well-known "Trojan Source" (CVE-2021-42574) character set used to visually reorder source code while leaving the underlying bytes/logic different from what's displayed. This mirrors the GoGoPool `getExpectedAVAXRewardsAmt` bug pattern: a simplified/incomplete formula stands in for what should be an authoritative, complete calculation, producing a wrong security-relevant output (here, a false "safe" result on `hasHiddenBidiChars`) that downstream logic and UI trust.

### Finding Description
`DiffParser.parse()` computes `hasHiddenBidiChars: HiddenBidiCharsRegex.test(text)` for every parsed diff [2](#0-1) , and this flag is propagated all the way to the UI as part of `IRawDiff`/`ITextDiff` [3](#0-2) [4](#0-3) . The `DiffContentsWarning` component uses exactly this boolean to decide whether to surface the "This diff contains bidirectional Unicode text..." alert to the user [5](#0-4) .

Because the regex is `/[\u202A-\u202E]|[\u2066-\u2069]/` [6](#0-5) , a file whose content uses only `U+200E`/`U+200F`/`U+061C` to reorder displayed glyphs (a subset of the same Trojan Source attack class) will not set `hasHiddenBidiChars`, and Desktop will render the diff with no warning at all. The same incomplete regex is reused when checking freshly expanded hunk lines in `expandTextDiffHunk` [7](#0-6) , so expanding context around such a file also produces no warning.

This is the same bug class as the GoGoPool finding: a security-relevant estimate/detector is implemented with a narrower, less rigorous character/formula set than the full "real" definition (Avalanche's actual reward formula vs. the actual Unicode Bidi_Control set), so the app's downstream decision (slash amount / show-warning) is silently wrong for a subset of otherwise-valid inputs, and no other guard closes the gap.

### Impact Explanation
A malicious/compromised remote or pull request author can craft a source file using only the `U+200E`, `U+200F`, or `U+061C` bidi marks (which are excluded from `HiddenBidiCharsRegex`) to make reviewed code visually differ from what actually executes/compiles, without triggering Desktop's bidi warning. A user reviewing the diff in Desktop before committing/pushing/merging sees no indication that hidden reordering characters are present, so they may unknowingly approve, commit, or push code whose true logic differs from what is displayed — a form of silent corruption of what the user believes they are committing/reviewing, consistent with the accepted Trojan Source attack class.

### Likelihood Explanation
The trigger requires only that the attacker control the content of a file in a fetched/cloned repository or a PR diff being reviewed in Desktop — no local access, no admin rights, and no unusual user action beyond normal diff review, which is squarely within Desktop's intended workflow. The gap is deterministic (three specific, well-documented code points are simply absent from the regex), so it reproduces reliably.

### Recommendation
Extend `HiddenBidiCharsRegex` in `app/src/lib/diff-parser.ts` to include the full set of Unicode bidi-control/format characters used in the Trojan Source disclosure (`U+200E`, `U+200F`, `U+061C`, in addition to the existing `U+202A`–`U+202E` and `U+2066`–`U+2069` ranges), and add regression tests covering each character individually to prevent silent regressions of coverage.

### Proof of Concept
1. Create a file containing a line with `U+200E` (LRM) or `U+061C` (ALM) positioned so that it visually swaps the order of two tokens (e.g., reversing the apparent order of a string literal and a trailing comment/semicolon), while the actual byte sequence performs different logic than what is displayed.
2. Commit this to a branch/PR and open it (or fetch it) in GitHub Desktop.
3. Observe the diff view: `DiffContentsWarning` renders no bidi warning banner because `HiddenBidiCharsRegex.test(text)` returns `false` for text containing only `U+200E`/`U+200F`/`U+061C` [6](#0-5) [8](#0-7) .
4. Compare against a file using `U+202E` (RLO) — Desktop correctly shows the warning — demonstrating the regex's coverage gap is character-set-specific, not a general failure.
