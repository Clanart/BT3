### Title
Missing per-client rate limiting on the JSON-RPC HTTP service allows a single low-rate client to exhaust the shared blocking-thread pool and degrade/crash RPC service for all users - ([File: rpc/src/rpc_service.rs])

### Summary
Every other network-facing ingress path in Agave enforces some form of token-bucket / connection rate limiting: QUIC/TPU connections are gated by `ConnectionRateLimiter` and a global `TokenBucket` before `setup_connection` even runs [1](#0-0) , and streams are throttled per-connection via `throttle_stream`/`ConnectionStreamCounter` [2](#0-1) . Gossip pull requests are similarly budgeted per-IP via `try_consume_pull_request_scan_budget` [3](#0-2) , and repair requests are metered with a `TokenBucket`-based `data_budget` plus a ping-cache liveness check before any expensive work is done [4](#0-3) .

The JSON-RPC HTTP service (`rpc/src/rpc_service.rs`) has no equivalent mechanism. `JsonRpcService::new` builds the `jsonrpc_http_server` with only CORS settings and `max_request_body_size`; there is no per-IP or per-connection request throttle, no token bucket, and no concurrency cap on individual RPC methods [5](#0-4) . Expensive RPC methods such as `getProgramAccounts` / `getTokenAccountsByOwner` perform full accounts-index/AccountsDB scans dispatched via `spawn_blocking` onto a shared, size-limited `rpc_blocking_threads` pool [6](#0-5) , and the only safeguard present is a *byte-size* cap on the result set (`scan_results_limit_bytes`), not a *rate* or *concurrency* cap on how many scans a single client can trigger [7](#0-6) . The runtime comment for `service_runtime()` even documents that CPU-bound calls like `getMultipleAccounts`/`getProgramAccounts` share a fixed-size blocking pool "so we can configure the number of worker threads ... and use spawn_blocking() to avoid blocking the worker threads" [8](#0-7) .

### Finding Description
The broken invariant is: "an unprivileged network client can trigger an unbounded number of CPU/IO-heavy operations against a shared, fixed-size resource pool with no per-client throttling." This is exactly the invariant broken in the external report (unlimited authenticated calls to an expensive validation endpoint with no rate limiter, CAPTCHA, or lockout).

In Agave's JSON-RPC service, a single client can open many concurrent HTTP connections/requests (or pipeline requests) invoking `getProgramAccounts`, `getTokenAccountsByOwner`, or `getTokenAccountsByDelegate` — all of which route through `get_filtered_program_accounts` → `bank.get_filtered_program_accounts` → `spawn_blocking` [6](#0-5) . Because:
1. `rpc_service.rs` applies no per-IP/per-connection admission or rate control before dispatching to the JSON-RPC handler [5](#0-4) , and
2. The blocking-task pool used to serve these scans is a single, shared, fixed-size `rpc_blocking_threads` runtime (`service_runtime`) used by *all* RPC clients and *all* CPU-bound RPC methods [8](#0-7) ,

a single unprivileged client can saturate the blocking pool with a modest, sustained number of concurrent `getProgramAccounts`-class requests. The corrupted/exhausted value is the pool of available blocking-thread slots in the `rpc_blocking_threads` Tokio runtime — once fully occupied by attacker-issued scans, all other RPC calls that depend on `spawn_blocking` (including `getAccountInfo`, `getMultipleAccounts`, etc.) queue and stall for legitimate clients on the same validator/RPC node.

Existing guards do not stop this path because:
- `byte_limit_for_scans` (`scan_results_limit_bytes`) only truncates the *result size* after the scan has already consumed CPU time walking the accounts index; it does not bound how many scans can run concurrently or per unit time [7](#0-6) .
- There is no `TokenBucket`/`KeyedRateLimiter` analog (as used for QUIC connections in `streamer/src/nonblocking/connection_rate_limiter.rs`) wired into `rpc_service.rs` or the `jsonrpc_http_server` request middleware.
- `RpcRequestMiddleware` (constructed alongside the IO handler) is only used for snapshot/health HTTP GETs, not for throttling JSON-RPC POST method calls [9](#0-8) .

### Impact Explanation
This falls under the accepted "single-client low-rate RPC crash/degradation" impact category. An attacker does not need a high request rate — only enough concurrent expensive scan requests to occupy all `rpc_blocking_threads` slots (default sized relative to CPU count, per the runtime comment) to starve the pool for a sustained period, degrading or effectively denying RPC service to all other unprivileged clients hitting that node. This is a non-consensus, non-privileged degradation of a public-facing service, which is explicitly within scope.

### Likelihood Explanation
Likelihood is high for any validator/RPC node running with `full_rpc_api`/`getProgramAccounts` enabled (a common configuration for public RPC endpoints). No authentication, staking, or privileged access is required; an anonymous client only needs standard JSON-RPC HTTP access, which is the same access level assumed in the original bug report (an unauthenticated/low-friction, "invite-only" adjacent endpoint). The main uncertainty is the exact default value of `rpc_blocking_threads`/`rpc_threads` used in this codebase and whether some deployments set a very large blocking-thread pool, which would raise the number of concurrent requests needed but not eliminate the underlying architectural gap.

### Recommendation
- Add per-IP/per-connection request-rate limiting to the JSON-RPC HTTP service in `rpc/src/rpc_service.rs`, mirroring the existing `TokenBucket`/`KeyedRateLimiter` infrastructure already used for QUIC (`streamer/src/nonblocking/connection_rate_limiter.rs`) and repair (`core/src/repair/serve_repair.rs`).
- Specifically rate-limit or cap concurrency for CPU/IO-heavy methods (`getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, `getLargestAccounts`) per source IP, independent of the existing byte-size result limit.
- Consider isolating expensive scan methods onto a bounded, separately-sized semaphore/thread pool so that pool exhaustion by scan-heavy requests cannot starve latency-sensitive RPC methods (`getAccountInfo`, `getBalance`, `sendTransaction`) served from the same blocking pool.

### Proof of Concept
1. Run a validator/RPC node with `--full-rpc-api` and `getProgramAccounts` enabled, using default `rpc_blocking_threads`.
2. From a single unauthenticated client, open N concurrent HTTP connections (N ≈ configured `rpc_blocking_threads`) each issuing `getProgramAccounts` for a program with a large number of accounts and no filters, so scans consume `spawn_blocking` slots for extended time (via `get_filtered_program_accounts` → `bank.get_filtered_program_accounts` → `spawn_blocking`, `rpc/src/rpc.rs:2283-2301`).
3. From a second, legitimate client, concurrently issue lightweight calls such as `getAccountInfo`/`getMultipleAccounts` (also routed through `spawn_blocking`, `rpc/src/rpc.rs:551-591`).
4. Observe that the legitimate client's requests queue/stall behind the attacker's scans because `rpc_service.rs` applies no rate limiting or method-level concurrency isolation before dispatch (`rpc/src/rpc_service.rs:718-743`), demonstrating single-client, low-request-rate degradation of the shared RPC blocking pool.

Note: I was unable to directly confirm within the indexed code the exact default numeric value of `rpc_blocking_threads` (the grep matched `validator/src/commands/run/args/json_rpc_config.rs`, but the file's content with the default constant was not returned by the index) — this would need to be checked directly in a full checkout to precisely quantify the number of concurrent connections required to trigger pool exhaustion.

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}

pub fn service_runtime(
    rpc_threads: usize,
    rpc_blocking_threads: usize,
    rpc_niceness_adj: i8,
) -> Arc<TokioRuntime> {
    // The jsonrpc_http_server crate supports two execution models:
    //
    // - By default, it spawns a number of threads - configured with .threads(N) - and runs a
    //   single-threaded futures executor in each thread.
    // - Alternatively when configured with .event_loop_executor(executor) and .threads(1),
    //   it executes all the tasks on the given executor, not spawning any extra internal threads.
    //
    // We use the latter configuration, using a multi threaded tokio runtime as the executor. We
    // do this so we can configure the number of worker threads, the number of blocking threads
    // and then use tokio::task::spawn_blocking() to avoid blocking the worker threads on CPU
    // bound operations like getMultipleAccounts. This results in reduced latency, since fast
    // rpc calls (the majority) are not blocked by slow CPU bound ones.
    //
    // NB: `rpc_blocking_threads` shouldn't be set too high (defaults to num_cpus / 2). Too many
    // (busy) blocking threads could compete with CPU time with other validator threads and
    // negatively impact performance.
    let rpc_threads = 1.max(rpc_threads);
    let rpc_blocking_threads = 1.max(rpc_blocking_threads);
    Arc::new(
        TokioBuilder::new_multi_thread()
            .worker_threads(rpc_threads)
            .max_blocking_threads(rpc_blocking_threads)
            .on_thread_start(move || renice_this_thread(rpc_niceness_adj).unwrap())
            .thread_name("solRpcEl")
            .enable_all()
            .build()
            .expect("Runtime"),
    )
}
