### No vulnerability found for this question.

**Analysis:** The claimed attack path is already blocked by the existing check. `DepositData::get_watchtowers()` concatenates verifiers' xonly-derived keys with `actors.watchtowers` without deduplication and sorts [1](#0-0) . However, `are_all_watchtowers_unique()` builds a `HashSet` from that same (duplicate-containing) list — which collapses any duplicate xonly key into a single entry — and compares its length against `get_num_watchtowers()`, which is the raw, non-deduplicated count (`get_num_verifiers() + actors.watchtowers.len()`) [2](#0-1) [3](#0-2) .

If an attacker inserts a watchtower xonly key that collides with an existing verifier's xonly-derived key, the deduplicated `HashSet` length will be strictly less than `get_num_watchtowers()`, so `are_all_watchtowers_unique()` returns `false`. `Verifier::is_deposit_valid` calls this check right after the `MAX_EXTRA_WATCHTOWERS`/`MAX_NUMBER_OF_WATCHTOWERS` bound checks and returns `BridgeError::InvalidDeposit` on failure [4](#0-3) . This is exactly the rejection the question describes as the expected/correct behavior — and tracing the code confirms it is what actually happens, not silently bypassed. The dedup-free `extend+sort` in `get_watchtowers()` does not defeat the uniqueness check because the check re-applies dedup via `HashSet` and compares against the un-deduplicated expected count, catching any collision (whether the duplicate is against a verifier-derived key or against another extra watchtower entry).

No divergence in `get_watchtowers()` output can occur across verifiers for an accepted deposit, since any collision causes rejection before presigning proceeds, so the kickoff tx watchtower-challenge UTXO ordering binding is preserved.
