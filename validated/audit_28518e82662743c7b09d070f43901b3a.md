### Title
Distribution precompile `rewards()` view method strands `msg.value` sent with the call - (File: `precompiles/distribution/distribution.go`)

### Summary
The `distribution` Cosmos precompile at `0x0000000000000000000000000000000000001007` dispatches the `rewards()` (query) method without any non-payable guard, unlike every other query method on the same precompile. A caller who attaches `msg.value` to a `rewards()` call has that value transferred into the precompile's EVM balance by the standard EVM `CALL` value-transfer semantics, but the executor never converts or refunds it, permanently stranding the sent funds — the same root cause as the referenced Allo.sol issue (a payable/value-accepting entry point that never uses or forwards the received funds).

### Finding Description
`PrecompileExecutor.Execute` in `distribution.go` explicitly calls `pcommon.ValidateNonPayable(value)` for `WithdrawValidatorCommissionMethod` but omits it for `RewardsMethod`: [1](#0-0) 

`rewards()` itself only performs a `DelegationTotalRewards` query and packs the result — it never touches `value`, never calls `pcommon.HandlePaymentUsei` (the helper other payable precompile methods use to convert `usei`/`wei` and either consume or refund the payer), and never transfers anything back: [2](#0-1) 

Compare this with `HandlePaymentUsei`, the pattern every legitimately payable precompile method uses to either consume the sent coin for a real bank/staking/gov action or explicitly refund it to the payer: [3](#0-2) 

The repository's own integration test suite documents this exact gap as a known, deliberate quirk rather than a fixed bug: [4](#0-3) 

Because Sei precompiles are dispatched through the standard go-ethereum `CALL` opcode path, sending `value` to any precompile address triggers the EVM's native value transfer (debiting the caller and crediting the precompile's StateDB balance) before the precompile's `Run`/`Execute` logic ever runs. Since `rewards()` performs no compensating transfer, refund, or `HandlePaymentUsei` conversion, the usei/wei credited to the distribution precompile's address is never moved to any spendable cosmos account and has no code path to reclaim it — it is permanently lost from the sender's perspective.

### Impact Explanation
Any unprivileged EVM transaction sender or smart-contract caller can call `rewards(address)` on the distribution precompile with non-zero `msg.value` and have those funds absorbed with no economic effect and no way to recover them, since the precompile is not a real contract with owner-controlled withdrawal logic and the executor never issues a refund. This is a concrete, permanent fund-loss bug reachable by a single ordinary transaction, matching the Medium-severity fund-loss class of the referenced report.

### Likelihood Explanation
Likelihood is low-to-moderate in practice (a caller must mistakenly or carelessly attach value to a `view`-labeled method, since front-end tooling and the Solidity ABI mark `rewards()` as non-payable at the interface level), but the on-chain precompile itself performs no enforcement, so any raw transaction, low-level `call{value: x}(...)`, or misconfigured integration contract can trigger the fund loss deterministically and irreversibly.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used by `WithdrawValidatorCommissionMethod` and other query/payable-restricted methods to the `RewardsMethod` case in `Execute`, rejecting any non-zero `value` before performing the query, consistent with every other read-only method on this precompile.

### Proof of Concept
1. Deploy or use an existing contract (e.g. the repo's `PrecompileCaller.sol`) that performs `target.call{value: v}(data)`.
2. Encode a call to `rewards(address delegator)` on `0x0000000000000000000000000000000000001007` with `v > 0` and any valid delegator address.
3. Submit the transaction; observe it succeeds (no revert), the rewards data is returned, and the caller's balance is debited by `v` while no corresponding bank transfer occurs — the value is stranded on the precompile's EVM-side balance with no recovery path.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
