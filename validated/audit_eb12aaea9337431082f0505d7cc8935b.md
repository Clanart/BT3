### Title
Sandwichable zero-slippage-protected WOM→mWOM buyback swap inside `smartConvert` drains protocol fee value on every permissionless `harvest()` call - ([File: wombat/WombatStaking.sol], [File: wombat/SmartWomConvert.sol])

### Summary
`WombatStaking.harvest(_lpToken)` is callable by any address and internally triggers `_sendRewards`, which for `isMWOM` fees with a non-zero `smartWomConverter` calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`. Inside `SmartWomConvert`, the eligibility check (`currentRatio()`) and the actual buyback swap both read live reserves of `womMWomPool` in the same transaction, and the underlying `swapExactTokensForTokens` call is executed with `amountOutMin = 0`, protected only by a weak aggregate floor (`convertAmount + amountRec >= _amountIn`, i.e. a 1:1 floor, not a fair-price floor). This lets an attacker sandwich the harvest transaction to capture the price-impact spread that should have accrued to the protocol's mWOM fee backing.

### Finding Description
`harvest()` has no caller restriction — the only guards are `whenNotPaused` and `_onlyActivePool`, which merely checks `pools[_lpToken].isActive`: [1](#0-0) [2](#0-1) 

`harvest` calls `_toMasterWomAndSendReward`, which calls `_sendRewards` for the harvested WOM. When a fee entry has `isMWOM == true` and `smartWomConverter != address(0)`, it calls `smartConvert(feeAmount, 0)`: [3](#0-2) 

`smartConvert` first reads `currentRatio()`, a spot price derived from a live `getAmountOut` call against `womMWomPool`, to decide whether/how much of the fee should be routed through an actual AMM swap (`buybackAmount`) versus a 1:1 `mWom.deposit`: [4](#0-3) 

The actual swap, executed moments later inside the same transaction via `_convertFor`, uses `amountOutMin = 0` for the AMM call itself: [5](#0-4) 

The only protection is an aggregate check that the total obtained (`convertAmount + amountRec`) is at least `_minRec`, and `smartConvert` passes `_minRec = _amountIn` — i.e., it only guarantees a break-even 1:1 WOM:mWOM outcome, not that the swap executed at a fair/undistorted market price: [6](#0-5) 

Because both the eligibility check and the actual swap read the same pool state within one attacker-observable transaction, an attacker can front-run `harvest(_lpToken)` with a large swap against `womMWomPool` to distort price, causing the protocol's buyback swap to execute at a manipulated price (bounded below only by the loose 1:1 floor, not by the true undistorted rate), then back-run to restore the pool and capture the price-impact spread. Existing modifiers (`whenNotPaused`, `_onlyActivePool`, `nonReentrant` — note `harvest` itself lacks `nonReentrant`) do nothing to prevent this, since none of them constrain price or caller identity for triggering the fee-conversion leg.

### Impact Explanation
This is a protocol-fee/backing siphoning vector: the fee amount meant to be converted into mWOM for backing/buyback purposes is executed against a manipulable, effectively slippage-unprotected AMM trade. Each harvest call routed through the `isMWOM` + `smartWomConverter` branch can be sandwiched, letting an attacker extract part of the price-impact spread that would otherwise translate into more mWOM backing for the protocol. This is a repeatable value leak on `queueNewRewards`-bound fee tokens, reducing mWOM backing over time (protocol insolvency contribution), matching the "theft of protocol fee value" / "theft of unclaimed yield" Immunefi impact classes.

### Likelihood Explanation
- `harvest(_lpToken)` is fully permissionless — any EOA can call it whenever a pool `isActive` and unpaused, and pool helpers also call it via `WombatPoolHelper.harvest()`/`AnkrBNBPoolHelper.harvest()`.
- The attacker needs only WOM/mWOM and capital to move `womMWomPool`'s spot price, a standard flash-loan-able sandwich requiring no special privileges.
- The condition is fully repeatable on every harvest that hits a fee with `isMWOM = true` while `smartWomConverter != address(0)` and the fee amount is large enough that the swap leg (`buybackAmount`) has meaningful size, which is an admin-configurable but plausible/expected production setup for this contract.
- The magnitude of extractable value is bounded by the pool's liquidity depth and the 1:1 floor, meaning attacker profit is proportional to fee size and pool depth — non-trivial for larger harvests but not unlimited.

### Recommendation
Do not rely on a single in-transaction spot read of `womMWomPool` (`currentRatio()`) plus a zero-`amountOutMin` swap. Instead:
1. Pass a real `minAmountOut` computed off a manipulation-resistant reference (e.g., a TWAP oracle or a governance/oracle-set fair ratio) into the actual `swapExactTokensForTokens` call inside `_convertFor`, rather than `0`.
2. Tighten `smartConvert`'s `_minRec` to reflect a fair expected output (not just 1:1 break-even), or allow the caller of `harvest`'s pool-helper wrapper to supply a slippage-bounded parameter that is checked against a trusted price source.
3. Consider restricting/throttling how much fee-conversion volume can be executed per block/transaction, or route the swap through a TWAP-based or batched auction mechanism instead of a single spot AMM call.

### Proof of Concept
Foundry fork test plan (Arbitrum fork, since scope references `rewards/ArbitrumMWomAirdrop.sol` and the wom/mWOM pool ecosystem there):
1. Fork mainnet Arbitrum state including `WombatStaking`, `SmartWomConvert`, and the live `womMWomPool`.
2. Configure/observe a fee entry with `isMWOM = true` and `smartWomConverter` set (or deploy a copy with realistic ratio/threshold matching the on-chain config), and accrue pending WOM rewards on an active pool sufficient to trigger the buyback leg (`currentRatio() < buybackThreshold`).
3. As "attacker", front-run: swap a sized amount of WOM/mWOM into `womMWomPool` via the Wombat router to push `currentRatio()` under `buybackThreshold` and distort the pool towards a rate favorable for the attacker's back-run.
4. Call `harvest(_lpToken)` from an arbitrary attacker-controlled address (demonstrating no caller check blocks it), triggering `_sendRewards` → `smartConvert` → `_convertFor`'s swap at the distorted price.
5. As "attacker", back-run: swap back to restore the pool to its pre-attack price.
6. Assert: attacker's WOM/mWOM balance nets positive (profit) versus their starting balance; and that `feeTosend` (mWOM value queued to `feeInfo.to`/rewarder in `_sendRewards`) is measurably lower than a control run of the same harvest without the sandwich (i.e., quantify the mWOM shortfall relative to fair-price execution), confirming value was diverted from protocol fee backing to the attacker.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
