### Title
Quadratic interpolation blow-up in `ThresholdKeys::read` enables DoS from small crafted key blobs - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a fully attacker-controlled `n`/`t` pair and, for `Interpolation::Lagrange`, computes the group key by evaluating `interpolation_factor` for each of the first `t` participants. `interpolation_factor` is itself O(t), so deserialization performs O(t²) field multiplications/inversions — algorithmic-complexity DoS analogous to the ReDoS in the fluentd report, reachable by feeding untrusted bytes to `ThresholdKeys::read`.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s (lines 591–602), then reads `n` verification-share points and calls `ThresholdKeys::new` (lines 620–631). `ThresholdKeys::new` computes the group key by summing `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` over all `t` participants in `1..=t` (lines 376–378). For `Interpolation::Lagrange`, `interpolation_factor` loops over the entire `included` slice (`for l in included`, lines 234–242), performing two field multiplications per element plus a field inversion per call. Total cost is therefore Θ(t²) field multiplications plus Θ(t) inversions.

`ThresholdParams::new` only enforces `t <= n` and both being non-zero `u16`s (lines 166–179), so a crafted blob can set `t = n = 65535`. The serialized input is only ~n·(point size) ≈ 2 MB for ristretto/ed25519-class curves, yet deserialization performs ~4.3×10⁹ field multiplications and ~65k inversions — a disproportionate amount of work per byte of input, the exact shape of a ReDoS: bounded input causing super-bounded computation.

The bug class is "untrusted input steers a parser into excessive compute"; here the "regex" is Lagrange interpolation and the "crafted pattern" is a maximally-sized threshold parameter set.

### Impact Explanation
Any component that calls `ThresholdKeys::read` on bytes influenced by an unprivileged party (the rules explicitly list `ThresholdKeys::read` as a reachable untrusted-bytes sink) can be stalled for a long time inside a single `read` call — there is no size limit on `t`/`n`, no pre-check that the claimed parameters are reasonable, and the Θ(t²) scalar work happens after only ~2 MB of input has been consumed. On multiexp-heavy paths the same quadratic factor also shows up in `ThresholdView::view` (interpolation factor recomputed per included signer, lines 500–506), so the cost recurs on every signing-session setup using those keys, amplifying the effect beyond a one-time parse.

### Likelihood Explanation
Likelihood is bounded by how often `ThresholdKeys::read` is called on remote-influenced data. Keys are normally generated locally, so the attack requires a path where serialized keys are accepted from a peer or from shared/mutable storage — e.g., recovery/re-share flows or any deployment that loads keys from a source an unprivileged party can write. Where such a path exists, the trigger is trivial: flip two bytes in a valid serialization to set `n`/`t` to `0xffff` and pad with dummy points. Because it only degrades availability (no secret leakage, no forgery), this maps to Medium, consistent with the fluentd advisory's Medium rating for the same bug class.

### Recommendation
Enforce a sane upper bound on `t` and `n` inside `ThresholdKeys::read` (or `ThresholdParams::new`) before performing any interpolation — e.g., reject parameter sets above a documented maximum consistent with Serai's validator-set size, or at minimum reject `t` values whose quadratic interpolation cost is unreasonable for the input length. Alternatively, compute the group key with a single multiexponentiation of precomputed Lagrange coefficients (which is still Θ(t²) scalar ops but could instead be replaced by incremental prefix products) and short-circuit `read` early when `n` exceeds the actual remaining input length divided by point size, so the expensive `ThresholdKeys::new` call is never reached for truncated blobs.

### Proof of Concept
```rust
// crypto/dkg — demonstrates O(t^2) deserialization DoS
use std::io::Write;
use ciphersuite::Ristretto;
use dkg::{ThresholdKeys, Participant};

fn main() {
  let t: u16 = u16::MAX;      // 65535
  let n: u16 = u16::MAX;
  let i: u16 = 1;

  let mut blob = vec![];
  // C::ID for Ristretto
  blob.write_all(&(Ristretto::ID.len() as u32).to_le_bytes()).unwrap();
  blob.write_all(Ristretto::ID).unwrap();
  blob.write_all(&t.to_le_bytes()).unwrap();
  blob.write_all(&n.to_le_bytes()).unwrap();
  blob.write_all(&i.to_le_bytes()).unwrap();
  blob.write_all(&[1u8]).unwrap(); // Interpolation::Lagrange
  blob.extend_from_slice(&[0u8; 32]); // secret_share (nonzero scalar encoding)
  for _ in 0 .. n {
    blob.extend_from_slice(&Ristretto::generator().to_bytes()); // n points ~2MB
  }

  // This call performs ~t^2 ≈ 4.3e9 field multiplications in
  // ThresholdKeys::new -> interpolation_factor, hanging the caller.
  let _ = ThresholdKeys::<Ristretto>::read(&mut blob.as_slice());
}
```
With `t = n = 65535`, `ThresholdKeys::new` iterates `1..=t`, and each iteration's `interpolation_factor` (`crypto/dkg/src/lib.rs:226-249`) loops over all `t` included participants — quadratic work triggered entirely by two attacker-controlled `u16`s in an otherwise ~2 MB input.
