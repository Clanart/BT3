Audit Report

## Title
Stake accounts closed between epoch-reward calculation and multi-block partitioned distribution silently forfeit already-computed inflation rewards - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

## Summary
Agave's epoch reward payout computes each delegator's `stake_reward`/`block_reward` once at the epoch boundary (`calculate_stake_rewards_and_commissions`) but pays it out over up to `num_partitions` subsequent blocks (`distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition`). Because `build_updated_stake_reward` re-reads the account from the live, mutable `StakesCache` at distribution time rather than a fixed snapshot, a stake account that becomes fully deactivated and is withdrawn/closed by its owner between calculation and its assigned distribution block causes the already-computed reward to be permanently discarded into `stake_reward_lamports_burned`/`block_reward_lamports_burned` instead of paid.

## Finding Description
The reward pipeline is: `calculate_stake_rewards_and_commissions` iterates `stake_delegations` from `StakesCache` at the epoch boundary and computes a `PartitionedStakeReward` per delegated stake pubkey [1](#0-0) . These calculated rewards are stored in `PartitionedStakeRewards` and later hashed into `partition_indices` for multi-block distribution in `distribute_partitioned_epoch_rewards` [2](#0-1) .

At each distribution block, `build_updated_stake_reward` looks up the stake pubkey in `stakes_cache_accounts`, a live, current-block snapshot, not the state captured at calculation time, and returns `DistributionError::AccountNotFound` if the account is no longer present: [3](#0-2) .

`store_stake_accounts_in_partition` handles this error by logging and moving the reward amount into `stake_reward_lamports_burned`/`block_reward_lamports_burned` instead of retrying, redirecting, or halting: [4](#0-3) . The function's own doc comment states this should be unreachable ("there should never be rewards burned") [5](#0-4) , confirming it is a defensive path rather than a validated invariant, and the burned amounts are excluded from `stake_reward_lamports_minted`, so capitalization is never increased to compensate — the reward is permanently lost, not merely delayed.

The exploitable window exists because `get_reward_distribution_num_blocks` can span up to 10% of an epoch's slots when stake account counts exceed `partitioned_rewards_stake_account_stores_per_block` [6](#0-5) , and `StakesCache` is continuously mutated by ordinary permissionless transactions during that window. A stake account that was actively earning rewards during the rewarded epoch but fully cools down by the calculation block boundary can be legitimately closed via an ordinary `Withdraw` instruction (removing it from `StakesCache`) before its assigned partition block arrives, since a fully-deactivated stake account's entire balance becomes withdrawable. This exact reachable error path is independently confirmed by the existing unit test `test_build_updated_stake_reward`, which asserts `build_updated_stake_reward` returns `DistributionError::AccountNotFound` for a stake pubkey missing from `stakes_cache_accounts` [7](#0-6) .

Existing guards are insufficient: there is no protocol rule linking the stake program's `Withdraw`/close path to an outstanding, uncredited partitioned reward, and no snapshot of calculation-time stake state is retained/used at distribution time to allow payout of a since-closed account.

## Impact Explanation
This is a fund-loss/accounting-correctness bug: the corrupted value is the delegator's `stake_reward` (and `block_reward`) lamports, which are computed and tracked during calculation but never credited to any account and instead absorbed into the `stake_reward_lamports_burned` counter during distribution. Although the affected party is the same staker who performed the closing transaction (a self-timing race rather than attacker-vs-victim theft), it is still an unprivileged, protocol-level failure to honor an already-committed reward, producing false accounting between the calculation and distribution phases.

## Likelihood Explanation
Triggering requires only ordinary, permissionless stake operations (deactivate, wait for cooldown, `Withdraw`) timed within the multi-block distribution window (which can span up to 10% of an epoch's slots), racing against the delegator's own partition-assigned distribution block, which is determined by a hash of the parent blockhash and thus not precisely predictable in advance. This makes it a plausible but narrow corner case rather than a high-frequency exploit, consistent with the code authors' expectation that this path should be unreachable in practice.

## Recommendation
Avoid discarding rewards on `AccountNotFound`/`ArithmeticOverflow` in `store_stake_accounts_in_partition`. Either (1) snapshot the exact stake account state used during calculation and carry it through to distribution so a since-closed account still receives its payout (e.g., via a redirect/refund mechanism), or (2) add an explicit protocol-level restriction preventing full withdrawal/closure of a stake account that still has an outstanding partitioned reward scheduled for a future block.

## Proof of Concept
1. Set up a validator/stake pair whose stake account is delegated and actively earning rewards during epoch N, with enough total delegated accounts that `get_reward_distribution_num_blocks` yields `num_partitions > 1`.
2. Ensure the stake account fully deactivates (cooldown completes) by the epoch N+1 boundary (calculation block), so `calculate_stake_rewards_and_commissions` still computes a non-zero `stake_reward` for the delegator based on effective stake during epoch N.
3. Before the block corresponding to this delegator's assigned partition index is reached, submit a `Withdraw` instruction removing the entire account balance, closing it and removing it from `StakesCache`.
4. When `distribute_epoch_rewards_in_partition` reaches this partition, `build_updated_stake_reward` returns `Err(DistributionError::AccountNotFound)`, and `store_stake_accounts_in_partition` records the reward into `stake_reward_lamports_burned` instead of paying it — reproducible directly via the existing `test_build_updated_stake_reward` unit test pattern [7](#0-6) .

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
