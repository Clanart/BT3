I found a concrete analog in the `getPartialBlobContentsCatchPathNotInRef` function, where a `maxBuffer` resource-exhaustion condition on an attacker-controlled `git show` output is caught and silently converted into a truncated result, rather than surfacing the truncation to the caller who uses it for syntax highlighting.

### Title
Truncated buffer from `maxBuffer` overrun is silently returned as valid blob content - ([File: app/src/lib/git/show.ts])

### Summary
`getPartialBlobContentsCatchPathNotInRef` runs `git show <commitish>:<path>` with an attacker-influenceable `length` as `maxBuffer`. When the underlying `git` process output exceeds that buffer (e.g., because a cloned/fetched repository contains an attacker-crafted large blob), dugite throws an `ExecError` with `ERR_CHILD_PROCESS_STDIO_MAXBUFFER`. Instead of propagating this as an error condition or clearly indicating truncation, the `.catch()` handler swallows it and returns `coerceToBuffer(e.stdout)` — the partial, cut-off buffer — as if it were valid, complete blob content. [1](#0-0) 

### Finding Description
This mirrors the sgReceive bug-class pattern: an operation on attacker-influenced input (`git show` on a blob from a possibly attacker-crafted/cloned repository) can hit a resource limit (`maxBuffer`), and the failure/limit path does not fail safe — instead of erroring out or clearly flagging incompleteness, it returns partial data through the normal success path (`.then` value), indistinguishable at the type level from a fully-read blob. The only signal that this occurred is that the buffer's `.length` matches roughly `length`, which callers do not check.

The generic `git()` core function does have handling for `isMaxBufferExceededError` [2](#0-1) , but `getPartialBlobContentsCatchPathNotInRef` re-catches that specific error and converts it into a "successful" partial buffer return rather than re-throwing or tagging it as truncated.

This function backs syntax highlighting via `getPartialBlobContents`, used with `MaxHighlightContentLength` limits [3](#0-2) . In that intended use, truncation may be benign because the caller already expects/limits partial content. However, `getPartialBlobContentsCatchPathNotInRef` is a general-purpose exported function, and nothing in its signature or contract communicates to a caller that the returned `Buffer` might be silently truncated mid-content (e.g., mid-UTF-8 sequence, mid-diff-hunk, mid-JSON) rather than the true full blob when `length` is smaller than actual content size. A future or existing caller that relies on this function for anything beyond a fixed, small display window (for example, checksums, integrity comparisons, or complete-content assumptions) would silently operate on corrupted/incomplete data without any indication.

### Impact Explanation
If a caller (current or future) uses `getPartialBlobContentsCatchPathNotInRef`/`getPartialBlobContents` outside the narrow highlighting-truncation use case, an attacker who controls the content of a cloned/fetched repository (e.g., a very large file at a given path) can cause Desktop to silently treat truncated blob content as complete. This falls into the "silent corruption of what the user commits or pushes" class only if such content is later re-serialized or trusted for decision-making; within the current codebase, the identified caller (`syntax-highlighting/index.ts`) intentionally accepts partial content, which limits real-world impact today. I could not verify from the available index whether the maxBuffer-exceeded path is exercised in production with a value that materially differs from `MaxHighlightContentLength`, or whether other callers of `getPartialBlobContentsCatchPathNotInRef` exist beyond highlighting — the codebase index is limited and a full call-site audit was not possible from Ask-only search.

### Likelihood Explanation
Likelihood is low-to-moderate for a security-impactful outcome: the only observed caller already expects partial content, so today's real behavior is closer to a code-quality/defense-in-depth gap than in-the-wild exploitable corruption. It would become a more serious analog to the original sgReceive finding if a new caller were added that used the "complete" buffer contract without checking for truncation.

### Recommendation
Have `getPartialBlobContentsCatchPathNotInRef` explicitly return a truncation flag alongside the buffer (e.g., `{ buffer, truncated: boolean }`), and update `getPartialBlobContents`/callers to fail closed (or at least explicitly log/handle) when truncation occurs outside of the highlighting use case, rather than silently returning a `Buffer` indistinguishable from complete content.

### Proof of Concept
1. Clone/fetch a repository containing a very large blob at a known path.
2. Call `getPartialBlobContentsCatchPathNotInRef(repository, commitish, path, length)` with `length` smaller than the blob size.
3. Observe that the returned `Buffer` is silently truncated at `length` bytes with no error or flag, identical in shape to a full, valid blob read via the success path [4](#0-3) .

```typescript
export async function getPartialBlobContentsCatchPathNotInRef(
  repository: Repository,
  commitish: string,
  path: string,
  length: number
): Promise<Buffer | null> {
  const args = ['show', `${commitish}:${path}`]

  return git(args, repository.path, 'getPartialBlobContentsCatchPathNotInRef', {
    maxBuffer: length,
    expectedErrors: new Set([GitError.PathExistsButNotInRef]),
    encoding: 'buffer',
  })
    .then(r =>
      r.gitError === GitError.PathExistsButNotInRef ? null : r.stdout
    )
    .catch(e =>
      isMaxBufferExceededError(e) ? coerceToBuffer(e.stdout) : Promise.reject(e)
    )
}
```

```typescript
export const isMaxBufferExceededError = (
  error: unknown
): error is ExecError & { code: 'ERR_CHILD_PROCESS_STDIO_MAXBUFFER' } => {
  return (
    error instanceof ExecError &&
    error.code === 'ERR_CHILD_PROCESS_STDIO_MAXBUFFER'
  )
}
```
