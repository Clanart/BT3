### Title
Unbounded quadratic Lagrange interpolation in `ThresholdKeys::read`/`ThresholdKeys::new` enables remote CPU-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2020-10745 is an unauthenticated remote denial of service where a small crafted input causes the server to burn disproportionate CPU. The same class exists in Serai's DKG crate: `ThresholdKeys::read` accepts attacker-controlled `t`/`n` parameters up to `u16::MAX` (65535) with no upper bound, and `ThresholdKeys::new` then computes the group key via Lagrange `interpolation_factor` calls, each of which is O(t) field operations — yielding O(t²) field multiplications plus O(t) field inversions. Feeding ~4 MB of untrusted bytes triggers ~4 billion field multiplications and 65535 inversions, tying up a core for a very long time.

### Finding Description
`ThresholdParams::new` only validates `t <= n` and `t, n != 0`; both are `u16`, so an attacker can set `t = n = 65535` with only two bytes [1](#0-0) . In `ThresholdKeys::read`, the interpolation tag selects `Lagrange` (1 byte, zero coefficient bytes needed), then `n` verification shares are read and `ThresholdKeys::new` is invoked [2](#0-1) . `ThresholdKeys::new` computes the group key by calling `interpolation_factor` for each of `t` participants [3](#0-2) . For `Interpolation::Lagrange`, `interpolation_factor` loops over the entire `included` set performing field multiplications and a field inversion per call [4](#0-3) . That makes group-key computation O(t²) multiplications + O(t) inversions, all driven by a 4-byte `(t, n)` header. The same quadratic cost recurs in `ThresholdKeys::view`, which calls `interpolation_factor` per included signer [5](#0-4) .

### Impact Explanation
An unprivileged remote party supplying crafted `ThresholdKeys` bytes (any path feeding `ThresholdKeys::read`, or constructing `ThresholdParams`/`ThresholdKeys` from deserialized share data) forces ~t² ≈ 4.3×10⁹ field multiplications and 65535 field inversions. The work happens synchronously inside deserialization, before any cryptographic check can reject the input, so a single message monopolizes a CPU core; repeated messages constitute a full availability denial of service — the exact impact class of the Samba CVE (C:N/I:N/A:H, CVSS 7.5).

### Likelihood Explanation
`ThresholdKeys::read` is an explicitly exposed deserialization entry point for untrusted bytes, and nothing upstream caps `n` below `u16::MAX` at the crypto layer. Only ~4 MB of syntactically valid point/scalar encodings are required to reach maximal quadratic cost; even `n = 8192` (~0.5 MB input) already yields ~67 million field multiplications plus 8192 inversions — orders of magnitude more CPU per input byte than ordinary parsing.

### Recommendation
Enforce a protocol-level maximum on `ThresholdParams::n` (e.g., the on-chain `MAX_KEY_SHARES_PER_SET` bound) inside `ThresholdParams::new` or at least inside `ThresholdKeys::read` before allocating/looping. Additionally, reject `n`/`t` values exceeding the expected session parameters when reading keys for a known set, and compute the group key with a single O(n) multiexp where interpolation coefficients are precomputed, rather than per-participant O(t) Lagrange evaluation.

// Crafted buffer: C::ID header, t = n = 0xffff, i = 1, interpolation = Lagrange (1),
// then secret_share scalar and n point encodings.
let mut buf = vec![];
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(0xffffu16.to_le_bytes()); // t
buf.extend(0xffffu16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes());      // i
buf.push(1);                         // Interpolation::Lagrange
buf.extend(<Ristretto as Ciphersuite>::F::ONE.to_repr());
for _ in 0 .. 0xffffu16 {
  buf.extend((<Ristretto as Ciphersuite>::generator()).to_bytes());
}
// This call performs ~4.3e9 field multiplications and 65535 inversions inside
// ThresholdKeys::new -> interpolation_factor before returning.
let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
