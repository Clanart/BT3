### Title
Flash-deposit reward sniping via instant reward-per-token snapshot in `queueNewRewards`/`balanceOf` - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2.balanceOf` reads a live, un-time-weighted balance from `IMasterMagpie.stakingInfo` [1](#0-0) , and `_provisionReward`/`queueNewRewards` applies newly funded rewards instantly and fully into `rewardPerTokenStored` in a single lump-sum update rather than streaming them over time [2](#0-1) . Because the earned-reward formula only compares the *current* `rewardPerToken` against the caller's last-paid checkpoint and multiplies by the *current* balance, a staker who deposits immediately before a `queueNewRewards` call and withdraws immediately after captures a proportional share of the entire reward drop despite having zero real holding duration.

### Finding Description
The relevant flow:
1. `MasterMagpie.deposit` → `_deposit` calls `_harvestBaseRewarder` (→ `rewarder.updateFor(account)`) **before** `user.amount` is incremented, so the attacker's pre-deposit checkpoint (`userRewardPerTokenPaid`) is set to the `rewardPerToken` value that exists *before* the reward injection [3](#0-2) [4](#0-3) .
2. A manager (any account with `managers[msg.sender] == true`) calls `queueNewRewards`, which is a routine, expected operation (e.g., a keeper distributing weekly rewards) rather than an admin exploit. `_provisionReward` immediately updates `rewardInfo.rewardPerTokenStored += amountReward * 10**decimals / totalStaked()` [5](#0-4) . Because `totalStaked()` reads `IERC20(stakingToken).balanceOf(operator)` live [6](#0-5) , the attacker's freshly deposited large balance is already included, diluting the increment for all existing (legitimate, long-term) stakers.
3. The attacker calls `MasterMagpie.withdraw`, which calls `_harvestAndUnstake` → `_harvestBaseRewarder` **before** decrementing `user.amount` [7](#0-6) . At this point `updateFor` → `earned` → `_earned` computes `userShare * (rewardPerToken_now - userRewardPerTokenPaid_checkpoint) / 1e18`, using the attacker's full (still un-decremented) flash-sized balance from `balanceOf` [8](#0-7) [9](#0-8) .
4. The attacker can then claim via `multiclaim`/`getReward`, receiving a reward share proportional to size rather than to time-weighted holding, and then reclaim the flashed principal.

No mechanism (lockup period, minimum holding block, or streamed reward vesting) prevents this — the model is a lump-sum/instantaneous `rewardPerTokenStored` bump rather than a Synthetix-style `rewardRate`/duration-based drip. `nonReentrant` on `deposit`/`withdraw` does not help since these are two independent, sequential external calls, not a reentrant call chain.

### Impact Explanation
This is a direct transfer of yield from long-term stakers to the flash attacker: the reward drop's `rewardPerTokenStored` increment is diluted by the attacker's temporary stake, and the attacker captures a proportional share of that same reward drop for near-zero real holding time, while genuine long-term stakers receive a smaller `rewardPerToken` increment than they would have otherwise. This matches "theft of unclaimed yield" / disproportionate value extraction from other users' funds.

### Likelihood Explanation
The attack requires only: (1) enough capital or a flash-loanable staking token liquid enough to move `totalStaked()`, and (2) visibility into a pending `queueNewRewards` transaction in the mempool (front-running is permitted attacker behavior; `queueNewRewards` calls are routine and often predictable/scheduled). No privileged role is needed by the attacker — the manager's `queueNewRewards` call is a normal, expected protocol operation that the attacker merely sandwiches. This is a well-known reward-sniping pattern in MasterChef/Synthetix-style pools that lack reward streaming, and is straightforward to repeat every time new rewards are queued.

### Recommendation
Do not apply the full reward amount into `rewardPerTokenStored` instantly. Instead, stream new rewards over a fixed duration (Synthetix `rewardRate`/`periodFinish` pattern), and/or add a minimum staking-duration requirement (or checkpoint balances at the start of a reward epoch) so `balanceOf`/`earned` cannot capture rewards for balances that were not present for the accrual period.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie` + `BaseRewardPoolV2` with a staking token and a reward token; register a `manager`.
2. Have a "long-term" staker deposit a normal amount and let time pass with no reward yet queued.
3. Have the attacker flash-loan a large amount of the staking token and call `MasterMagpie.deposit(stakingToken, largeAmount)`.
4. In the same block, `manager` calls `rewarder.queueNewRewards(rewardAmount, rewardToken)`.
5. In the same block, attacker calls `MasterMagpie.withdraw(stakingToken, largeAmount)` then `multiclaim`/`getReward` to realize `earned()`.
6. Assert: `attacker.earned()` (realized reward) / `attacker.stakeDuration (~0 blocks)` vastly exceeds `longTermStaker.earned()` / `longTermStaker.stakeDuration`, and that `longTermStaker`'s realized share of `rewardAmount` is measurably reduced compared to a control run where the attacker never deposits.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
