### Title
GitHub Desktop disables Git's built-in clone-time RCE protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) while cloning untrusted repositories with `--recursive` - ([File: app/src/lib/git/clone.ts])

### Summary
The Apollon report's broken invariant is: a security check (price-staleness validation) is applied to only a curated subset of attacker-influenced inputs while the code path that actually executes trusts the *rest* unconditionally, letting attacker-controlled values slip past the guard. In GitHub Desktop the same pattern appears in the `clone()` implementation: Desktop validates only the *destination path* for safety (`isClonePathSensitive`) but explicitly force-disables Git's own built-in protection against malicious nested-submodule payloads for every clone, then immediately performs a `--recursive` clone that walks into those (attacker-controlled) submodules.

### Finding Description
`clone()` builds the environment for every `git clone` call with: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE: 'false'` is set unconditionally, for every clone Desktop performs, regardless of who owns/controls the remote being cloned. Immediately after, the clone args always include `--recursive`: [2](#0-1) 

Only the local destination path is validated for safety before the clone runs: [3](#0-2) 

There is no validation of the *content* of the repository being cloned - specifically, no check on submodule URLs/names declared in `.gitmodules`, which is attacker-controlled data embedded in the very repository the user is cloning. Git's upstream clone-protection mechanism exists precisely to catch malicious/conflicting submodule paths (e.g., a submodule name that collides with `.git` on case-insensitive or normalization-insensitive filesystems) before recursively initializing them, because a successful collision lets an attacker plant files inside the superproject's `.git` directory (hooks, config) that execute during the same clone/checkout. By forcing `GIT_CLONE_PROTECTION_ACTIVE=false` on every clone, Desktop removes this protection for all clones, not just ones it has independently vetted, and combines that with automatic recursive submodule initialization.

This is structurally identical to the report's pattern: the code enforces a safety check on only one narrow, easily-validated parameter (the local destination path) while a much larger, fully attacker-controlled surface (nested submodule definitions inside the cloned tree) is explicitly exempted from the corresponding upstream safety check.

The same recursive-submodule execution path is reused elsewhere with a similar all-or-nothing flag, `allowFileProtocol`, which - when true - re-enables `protocol.file.allow=always` for the entire recursive submodule tree rather than for a specific, reviewed submodule: [4](#0-3) 

### Impact Explanation
If Git's clone protection is what stands between "clone a malicious repository" and "arbitrary file write inside `.git` / hook execution," unconditionally disabling it for every clone means any repository a user clones (or is prompted to clone via a crafted GitHub URL/deep link/x-github-client link) with a crafted `.gitmodules` entry could, upon the same `--recursive` clone Desktop always performs, write attacker-chosen content into the superproject's git-controlled directories. That is squarely in-scope impact: "attacker controls a cloned/fetched repository... result is code execution [or] file write ... outside the repo[/intended tree]."

### Likelihood Explanation
Likelihood is high for the trigger conditions (any normal "Clone repository" action in Desktop hits this exact code path, unconditionally, since the flag is not gated by trust level of the remote), but I could not fully verify from the indexed code alone what Git version(s) bundled with Desktop implement/enforce `GIT_CLONE_PROTECTION_ACTIVE` and what the precise upstream default/behavior is when unset vs. `'false'`. That verification requires inspecting the vendored `git`/`dugite` binary behavior, which is outside what the code index can confirm.

### Recommendation
- Do not disable Git's built-in clone protections by default; only opt out for specific, already-trusted operations (e.g., background/local automation) if any exist, not for all user-initiated clones of arbitrary remotes.
- If `GIT_CLONE_PROTECTION_ACTIVE=false` is set to work around a compatibility issue, gate it and add a follow-up validation step that inspects `.gitmodules`/resulting submodule paths for collisions or path traversal before recursively initializing them, mirroring the destination-path validation (`isClonePathSensitive`) that already exists.
- Apply the same "validate the whole surface, not a narrow slice" principle to `allowFileProtocol`, scoping it to the reviewed submodule rather than the entire recursive tree.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` entry crafted to collide with `.git`/hook paths in a way that Git's clone-time protection (guarded by `GIT_CLONE_PROTECTION_ACTIVE`) is designed to reject.
2. Victim clicks a GitHub Desktop clone action (UI clone dialog, `x-github-client://openRepo` deep link, or "Open in Desktop" from a repo page) pointing at the attacker's repository.
3. Desktop calls `clone()` in `app/src/lib/git/clone.ts`, setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and running `git clone --recursive -- <url> <path>`.
4. Because the protection is disabled, Git proceeds to initialize the malicious submodule structure that upstream protection would otherwise refuse, potentially writing files into the superproject's `.git` directory as part of the same operation - exact resulting execution/write primitive depends on the Git version bundled with Desktop, which was not verifiable from the indexed source alone. function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
