## Title
`convert_to_erc20`/`convert_to_balance` silently skip scaling when local decimals exceed remote ERC20 decimals, causing up to 10^N over-minting on the destination chain - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
The `hyper-fungible-token` pallet scales amounts between the local Substrate asset's decimal precision and the remote EVM contract's ERC20 decimal precision using `10u128.pow(erc_decimals.saturating_sub(local_decimals))`. `saturating_sub` silently clamps to `0` whenever `local_decimals > erc_decimals`, which is exactly the common real-world case (e.g. a Substrate asset with 10/12/18 decimals bridging to a 6-decimal USDC-style ERC20 on EVM). In that case the amount is sent to the destination completely unscaled, causing the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract to mint/release `10^(local_decimals - erc_decimals)` times more tokens than the value actually escrowed/burned on the source chain — an unbounded, unprivileged over-mint, directly analogous to the IdleProvider decimal-misscaling bug (H-9) where `exchangeRate()`'s scale was cancelled against the wrong decimals variable.

### Finding Description
`convert_to_erc20` and `convert_to_balance` are defined as: [1](#0-0) 

Both use `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent. This is only correct when `erc_decimals >= local_decimals` (scale down from a higher-precision remote token to a lower-precision local one). When `local_decimals > erc_decimals` — e.g. a native/local asset configured with 12 or 18 decimals paired against a destination chain contract registered with `erc_decimals = 6` (a USDC/USDT-style token) — `saturating_sub` returns `0`, so the exponent is `0` and **no scaling is applied at all**, instead of the required scale-**up** by `10^(local_decimals - erc_decimals)`.

This function is invoked directly in the public, unprivileged `send` extrinsic: [2](#0-1) 

Here `amount` is the raw local balance (already scaled to `decimals`, the local asset's precision), and `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` is placed directly into the cross-chain `Message.amount` field, which the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract treats as an amount denominated in its own (`erc_decimals`) precision and mints/unlocks verbatim. When `decimals > erc_decimals`, the value is sent unscaled, so the destination contract mints `10^(decimals - erc_decimals)` times more tokens than the value the user actually locked/burned on the source chain.

The `erc_decimals` value comes from `Precisions` storage, set once via `register_token`/`update_token` (privileged, but not attacker-controlled at exploit time) — any token pairing where the local asset's decimals exceed the configured remote contract decimals (a completely ordinary, expected configuration for bridging low-decimal stablecoins like USDC/USDT to higher-decimal Substrate assets) makes every `send()` call by any unprivileged signed user trigger the bug. No malicious relayer, prover, or admin action is required — the flaw is purely arithmetic and fires on every legitimate transfer once such a token pair exists.

The inverse path (`on_accept`/`on_timeout`, using `convert_to_balance` with `erc_decimals`/`decimals` reversed) has the mirrored defect: when `local_decimals > erc_decimals`, incoming/refunded amounts are also under-scaled, so a receiving/refund credit is far smaller than intended — a fund-loss bug on the return leg of the same asset pair. ### Impact Explanation
This directly falls under "stealing or loss of funds" and "transaction manipulation / logic attack" in the bounty scope. On the outbound `send` path, any unprivileged user who locks/burns a small local amount can cause the destination chain contract to mint/release an amount inflated by `10^(local_decimals - erc_decimals)` — for a typical 18-vs-6 decimal pairing this is a 10^12 amplification, effectively unbounded fund creation on the destination chain funded by nothing on the source chain (WrappedHFT custody would be drained, or HFT mint creates unbacked supply). On the inbound/timeout path, the mirrored bug silently truncates legitimate credits/refunds to a tiny fraction of their intended value, causing permanent loss of bridged funds for the recipient/sender.

### Likelihood Explanation
High. The bug requires no attacker privilege, malicious relayer, or governance compromise — only a routine, expected token-decimal configuration (local asset decimals greater than the destination ERC20 decimals, which is the norm when bridging 6-decimal stablecoins like USDC/USDT to typical Substrate assets with 10/12/18 decimals). Any signed account can trigger it by simply calling `send`.

### Recommendation
Fix the scaling helpers to handle both directions explicitly instead of relying on `saturating_sub`, e.g.:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and equivalently invert the operation (multiply vs divide) in `convert_to_balance`. Add unit tests covering both `erc_decimals > local_decimals` and `erc_decimals < local_decimals` cases, matching the existing `Precisions` configuration matrix used across the test suite.

### Proof of Concept
1. Register a local asset with `decimals = 18` (e.g. via `pallet-assets` metadata) and call `register_token` with a `ChainConfig { token_contract: <destination HFT address>, decimals: 6 }` for an EVM destination (mirrors a USDC-style 6-decimal destination token) — a normal, expected configuration.
2. A user calls `send(SendParams { asset_id, amount: 1, destination, .. })` locking/burning `1` raw unit (i.e., `10^-18` of a whole token) of the local asset.
3. In `lib.rs::send`, `erc20_amount = convert_to_erc20(1, erc_decimals=6, decimals=18)`. Since `6.saturating_sub(18) == 0`, `erc20_amount = 1 * 10^0 = 1` is sent unscaled instead of `1 / 10^12` (which would floor to `0`, i.e. the correct behavior is either revert-on-precision-loss or scale down) — but more critically, for any `amount` large enough to survive scaling, the destination receives the raw local-precision value interpreted at destination's `erc_decimals=6`, over-crediting the destination by `10^12`.
4. The destination `HyperFungibleToken` contract mints/unlocks the unscaled `message.amount` to the recipient, producing a token credit worth `10^12` times more than what was escrowed/burned on the source chain — confirmed by the exponent computation in `convert_to_erc20` at [5](#0-4) .

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
