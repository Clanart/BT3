## Finding

### Title
Excess native-token payments sent to `EvmHost.dispatch`/`fundRequest` are never refunded and become permanently stuck - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native token payment via `msg.value` and swap it for the exact fee amount using `IUniswapV2Router02.swapETHForExactTokens`. None of these functions capture the `amounts` array returned by the swap or refund any unspent native token to the caller, so any overpayment beyond the exact fee is silently absorbed and never returned.

### Finding Description
In `evm/src/core/EvmHost.sol`, `dispatch(DispatchPost)` performs: [1](#0-0) 

`dispatch(DispatchGet)` follows the identical pattern: [2](#0-1) 

and `fundRequest` again repeats the same swap call: [3](#0-2) 

`swapETHForExactTokens(amountOut, path, to, deadline)` only spends as much ETH as needed to obtain exactly `amountOut` tokens; any leftover ETH sent with the call is refunded by the router — but the refund goes to `msg.sender` as seen by the router, which is `EvmHost` itself (since `EvmHost` is the one calling the router), not the original external caller who supplied `msg.value`. `EvmHost` never reads back or forwards this leftover ETH to the actual dispatcher of the request.

This is the identical bug class from the external report: a public payable entrypoint accepts `msg.value` greater than what is strictly required, and the excess is neither computed nor returned, permanently trapping user funds in the contract.

The codebase's own `IntentGatewayV2`/intent-fill contracts demonstrate the correct pattern is well understood elsewhere — they explicitly capture `amounts[0]` from `swapETHForExactTokens` and refund the unspent `msgValue` back to `msg.sender`: [4](#0-3) 

But `EvmHost`, the single production contract through which every POST/GET request and fee-top-up must flow, lacks this same refund logic entirely.

### Impact Explanation
This is a direct, unconditional loss of user funds on the core dispatch path of the protocol. Since Uniswap pool prices fluctuate between the time a user/application estimates the required native amount (via the off-chain `quote()` call, which the docs explicitly warn is only an off-chain estimate subject to sandwich risk) and the time the transaction executes, users are expected to send a buffer above the exact fee. That documented pattern (`msg.value` intentionally generous) guarantees that legitimate protocol usage regularly overpays, and 100% of every such overpayment is stranded inside `EvmHost` with no recovery path for the original payer. Every dispatcher (POST, GET, fundRequest) on every EVM deployment of Hyperbridge is affected — this is not a peripheral utility contract but the host contract itself.

### Likelihood Explanation
High likelihood: this triggers on ordinary, unprivileged use of the primary dispatch entrypoints whenever a caller sends `msg.value` greater than the exact fee token cost — which is the expected/recommended usage pattern documented for native-token fee payment (`docs/content/developers/evm/messaging/post-requests.mdx`, `get-requests.mdx`). No malicious relayer, prover, or admin is required; a normal application integrator calling `dispatch{value: msg.value}(post)` with any safety margin loses the difference every single time.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compute the unspent ETH (`msg.value - amounts[0]`), and refund it to `_msgSender()` (or `post.payer`/`get.payer` as appropriate) before returning, mirroring the pattern already implemented in `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Caller calls `EvmHost.dispatch{value: 2 ether}(post)` where `post.fee` only requires `0.1 ether` worth of ETH to swap for the exact fee-token amount via Uniswap.
2. Inside `dispatch`, `swapETHForExactTokens{value: 2 ether}(post.fee, path, address(this), block.timestamp)` executes, spending only `~0.1 ether` and refunding `~1.9 ether` to `address(this)` (the `EvmHost` contract).
3. `dispatch` returns normally with the correct commitment; the request is dispatched as expected.
4. The `~1.9 ether` refunded by the router is now sitting in `EvmHost`'s native balance, and the function never reads or forwards it back to the caller.
5. The caller has no way to reclaim the `1.9 ether` overpayment — repeated for every dispatch/fundRequest call across the protocol's lifetime, this accumulates unrecoverable user losses inside the host contract. [5](#0-4)

        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
