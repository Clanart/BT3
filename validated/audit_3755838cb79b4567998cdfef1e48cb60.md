### Title
`aptos move verify-package` never compares deployed bytecode to locally-built bytecode, only self-reported metadata - (File: `aptos-move/cli/src/stored_package.rs`)

### Summary
This is the closest local analog to the Fantium bug class ("a check exists but is insufficient to establish the real invariant"). The Aptos CLI's `verify-package` command is documented and named as a bytecode-verification tool ("Downloads the package from onchain and verifies the bytecode matches a local compilation of the Move code" [1](#0-0) , and "checks that on-chain bytecode matches a local source tree" [2](#0-1) ), but its actual implementation only compares `PackageMetadata` struct fields — never the real, executable module bytecode.

### Finding Description
`VerifyPackage::execute` fetches the on-chain `PackageRegistry` with bytecode download explicitly disabled: [3](#0-2) 

It then calls `package.verify(&compiled_metadata)`, whose entire implementation only compares `name`, `deps`, `modules` (source text/source-map metadata, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest`: [4](#0-3) 

None of these fields are the actual compiled bytecode that the Move VM loads and executes. The `ModuleMetadata.source` and `.source_map` fields are optional, gzipped, informational blobs supplied by the publisher at `publish_package` time — the Aptos Move VM's native publish path (`request_publish` / `request_publish_with_allowed_deps`) never checks that these source/source-map fields actually correspond to the bytecode bundle being published: [5](#0-4) [6](#0-5) 

The same applies to `source_digest`, which is computed off the source files locally by the compiler/CLI at build time and simply stored as an opaque string in `PackageMetadata` — there is no on-chain mechanism binding it to the bytecode either.

As a result, a malicious (or compromised) publisher can:
1. Publish a bundle of real, malicious bytecode via `code::publish_package_txn`.
2. Supply crafted `PackageMetadata` whose `modules[i].source`, `source_map`, `manifest`, and `source_digest` describe a benign-looking, different piece of source code (these are attacker-controlled inputs to the transaction and are never cross-checked against the bytecode by the VM).
3. Any downstream user/auditor/exchange who runs `aptos move verify-package` against the "benign" source tree will get `Successfully verified source of package`, even though the deployed, executable bytecode has nothing to do with that source.

This is exactly analogous to the reported bug class: a check exists (`package.verify()`), it's advertised as guaranteeing an invariant (bytecode == source), but it structurally can never observe or validate the field that actually matters (the real bytecode), because `with_bytecode` is hardcoded to `false` and the comparison logic never touches `CachedPackageRegistry.bytecode`/`get_bytecode()` at all — a capability that already exists in the same file: [7](#0-6) [8](#0-7) 

### Impact Explanation
This is a code-safety/verification-integrity bug rather than a permissionless privilege escalation: it does not let an attacker publish to someone else's account (module address must match the signer, enforced separately: [9](#0-8) ). However, it breaks the core trust guarantee that Aptos explicitly advertises for "code review and reproducibility" via `verify-package`. Given mainnet relevance, users, wallets, or auditors that rely on `aptos move verify-package` to confirm that a deployed package (e.g., a DeFi protocol or token contract) matches its published/audited source can be misled into trusting malicious bytecode that was never actually reviewed. This directly matches the "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" impact category in the prompt's Publish Impact Gate.

### Likelihood Explanation
High likelihood of occurrence in practice: the attacker only needs standard, permissionless publish rights to their own account/object (no privileged access required), and the metadata fields used in `verify()` (source, source_map, manifest, source_digest) are all attacker-supplied at publish time with no protocol-level enforcement tying them to the actual bytecode bundle. Any third party relying on `verify-package` as a security signal is affected.

### Recommendation
Fix `CachedPackageMetadata::verify` (and its caller `VerifyPackage::execute`) to perform an actual bytecode comparison instead of (or in addition to) metadata-field comparison:
- Call `CachedPackageRegistry::create(client, self.account, true)` (enable `with_bytecode`) in `VerifyPackage::execute`.
- For each module in the locally-built package, compile it to bytecode with the same `BuildOptions`/bytecode version, fetch the corresponding on-chain bytecode via `registry.get_bytecode(module_name)`, and byte-for-byte (or canonicalized) compare it against the locally compiled bytecode.
- Only report "Successfully verified source of package" if every module's actual deployed bytecode matches the locally compiled bytecode — metadata-only equality (source text, source_digest, manifest) should be treated as a secondary/informational check, not the basis of the verification guarantee.

### Proof of Concept
1. Attacker writes malicious Move module `M_evil` and publishes it under their account via `code::publish_package_txn`, using:
   - `code = [bytecode_of(M_evil)]`
   - `metadata_serialized` containing a `PackageMetadata` whose `modules[0].source` is the gzip of a benign module `M_good`'s source, and `source_digest` computed from `M_good`'s source files.
   - No on-chain check in `code.move`/`request_publish` compares `modules[0].source` to the bytecode bundle, so the transaction succeeds: [10](#0-9) 
2. A reviewer downloads `M_good`'s source, places it in a local package directory, and runs:
   ```
   aptos move verify-package --account <attacker_address>
   ```
3. `VerifyPackage::execute` builds `M_good` locally, extracts its metadata, fetches the on-chain `PackageRegistry` with `with_bytecode=false`, and calls `package.verify(&compiled_metadata)`.
4. Because the on-chain `PackageMetadata` was crafted to match `M_good`'s source/manifest/source_digest exactly, `verify()` succeeds and the CLI prints `Successfully verified source of package` — despite the deployed bytecode actually being `M_evil`, which was never inspected.

Note: I was unable to execute this PoC or fully trace `BuiltPackage::extract_metadata`/`source_digest` computation code (not indexed in the retrieved snippets) to confirm bit-for-bit how `source_digest` is derived; this should be validated by a Devin session with full repository access before treating this as conclusively exploitable end-to-end, though the missing-bytecode-comparison root cause in `stored_package.rs::verify` and `commands.rs::VerifyPackage::execute` is confirmed directly from the code shown above.

    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

fn native_request_publish(
    context: &mut SafeNativeContext,
    _ty_args: &[Type],
    mut args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    debug_assert!(matches!(args.len(), 4 | 5));
    let with_allowed_deps = args.len() == 5;

    context.charge(CODE_REQUEST_PUBLISH_BASE)?;

    let policy = safely_pop_arg!(args, u8);
    let mut code = vec![];
    for module in safely_pop_arg!(args, Vec<Value>) {
        let module_code = module.value_as::<Vec<u8>>()?;

        context.charge(CODE_REQUEST_PUBLISH_PER_BYTE * NumBytes::new(module_code.len() as u64))?;
        code.push(module_code);
    }

    let allowed_deps = if with_allowed_deps {
        let mut allowed_deps: BTreeMap<AccountAddress, BTreeSet<String>> = BTreeMap::new();

        for dep in safely_pop_arg!(args, Vec<Value>) {
            let (account, module_name) = unpack_allowed_dep(dep)?;

            let entry = allowed_deps.entry(account);

            if let Entry::Vacant(_) = &entry {
                // TODO: Is the 32 here supposed to indicate the length of an account address in bytes?
                context.charge(CODE_REQUEST_PUBLISH_PER_BYTE * NumBytes::new(32))?;
            }

            context
                .charge(CODE_REQUEST_PUBLISH_PER_BYTE * NumBytes::new(module_name.len() as u64))?;
            entry.or_default().insert(module_name);
        }

        Some(allowed_deps)
    } else {
        None
    };

    let mut expected_modules = BTreeSet::new();
    for name in safely_pop_arg!(args, Vec<Value>) {
        let str = get_move_string(name)?;

        // TODO(Gas): fine tune the gas formula
        context.charge(CODE_REQUEST_PUBLISH_PER_BYTE * NumBytes::new(str.len() as u64))?;
        expected_modules.insert(str);
    }

    let destination = safely_pop_arg!(args, AccountAddress);

    // Add own modules to allowed deps
    let allowed_deps = allowed_deps.map(|mut allowed| {
        allowed
            .entry(destination)
            .or_default()
            .extend(expected_modules.clone());
        allowed
    });

    let code_context = context.extensions_mut().get_mut::<NativeCodeContext>();
    if code_context.requested_module_bundle.is_some() || !code_context.enabled {
        // Can't request second time or if publish requests are not allowed.
        return Err(SafeNativeError::abort(EALREADY_REQUESTED));
    }
    code_context.requested_module_bundle = Some(PublishRequest {
        destination,
        bundle: ModuleBundle::new(code),
        expected_modules,
        allowed_deps,
        check_compat: policy != ARBITRARY_POLICY,
    });

    Ok(smallvec![])
}
