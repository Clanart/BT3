### Title
Fully-filled same-chain intent orders can be re-processed, re-executing attached calldata and re-emitting `OrderFilled` - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` (and the sibling `_withdraw` guard in `IntentsBase.sol`) mirror the structural flaw in the JBTiered721DelegateStore report: a completion state is inferred from a *derived* quantity (`remaining = totalRequired - alreadyFilled`, and the escrow balance in `_orders`) instead of an authoritative, monotonic "already processed" flag that is checked up front. Once the derived quantity legitimately reaches zero (an order becomes fully filled), a second call into the same function does not revert — it silently treats the order as freshly "fully filled" again, because the `isFullyFilled` boolean defaults to `true` and every token position is skipped via `continue` when `remaining == 0`, never flipping that default to `false`.

### Finding Description
In `_fillSameChain`: [1](#0-0) 

`isFullyFilled` starts `true`. For every output token where the order is *already* completely filled (`alreadyFilled == totalRequired`, so `remaining == 0`), the loop body executes `continue` and never touches `isFullyFilled`. The only path that sets `isFullyFilled = false` requires `remaining > 0`: [2](#0-1) 

Consequently, calling this internal path again for a commitment whose `_partialFills[commitment][outputToken] == totalRequired` for every output token leaves `isFullyFilled == true` at the end of the loop, with `escrowedInputs`/`outputFills` entries left at their zero-initialized default (since the loop body never assigns them for a skipped index).

The function then executes: [3](#0-2) 

Because `isFullyFilled` is `true`, `_execute(order, outputsLen)` runs again — re-dispatching the order's attached calldata through the `CallDispatcher` — and `OrderFilled` is re-emitted. `_withdraw` is called with all-zero token amounts, which is a no-op (`if (amount == 0) continue;` in `_withdraw`), so it does not revert and does not reveal that nothing new was escrowed: [4](#0-3) 

Nothing in `_fillSameChain` itself checks `_filled[commitment] == address(0)` before proceeding — it unconditionally overwrites `_filled[commitment] = msg.sender` at the top: [5](#0-4) 

This is the same bug class as the JBTiered721 report: a completion invariant (`_reserveTokensMinted <= mintable`) is derived from state that independently converges to an edge value (here, `remaining == 0` for every output token) without the function reasoning about *whether it had already reached that state on a prior successful call*. In JB, the divergence produced an underflow/DoS; here it produces the opposite failure mode — a "no-op looking" successful call that still re-triggers privileged side effects (`_execute`) and re-emits a completion event, because the guard silently degrades to a false-positive "fully filled" branch instead of rejecting the call.

### Impact Explanation
`_execute` invokes the configured `CallDispatcher` with `order.output.call`, arbitrary attacker/user-supplied calldata tied to the order. Re-invoking it after the order has already been legitimately and fully settled means the attached call's side effects (e.g., any downstream approvals, swaps, or protocol interactions the call performs) can be replayed an unbounded number of times at zero further cost (all token legs are zero-amount on replay), and `OrderFilled` — an event indexers and solvers rely on as an idempotency/settlement signal — is re-emitted, which can corrupt off-chain accounting or double-trigger integrations that key off that event per commitment. This falls under the bounty's "logic attacks" / "replay/double-claim/double-settlement" categories: a completed cross-chain-adjacent settlement primitive (same-chain intent fill with output execution) is not actually one-time.

### Likelihood Explanation
The defect is reachable by any unprivileged address that can call the public entry point wrapping `_fillSameChain` with the original, already-filled `Order` struct (orders are not secret; they are visible on-chain via `OrderPlaced`/`OrderFilled` events and the commitment is a deterministic hash of public fields). The only way this path is *not* exploitable is if the outer public `fillOrder`-style function (outside the files inspected, in `evm/src/apps/IntentGatewayV2.sol`) independently enforces `_filled[commitment] == address(0)` before dispatching into `_fillSameChain`. That check was not visible in the files retrievable in this session, so it cannot be confirmed to exist; the internal function itself provides no such protection and would misbehave (as described) if invoked a second time for a fully-settled commitment. This uncertainty should be resolved by inspecting the caller.

### Recommendation
Add an explicit, monotonic guard at the top of `_fillSameChain` (and `_fillCrossChain`) that reverts if `_filled[commitment] != address(0)`, rather than relying on the derived `remaining`/`isFullyFilled` values to implicitly encode "already fully settled." Additionally, initialize `isFullyFilled` based on whether *any* progress was made in the current call (e.g., track a `anyProgress` flag) rather than defaulting it to `true`, so a call that makes zero progress on every leg cannot fall through to the "fully filled" branch and re-trigger `_execute`/`OrderFilled`.

### Proof of Concept
1. User places a same-chain order with `output.call` set to some non-trivial calldata (e.g., an approval or transfer routed through the `CallDispatcher`) and a single output asset.
2. A solver calls the public fill entry point with `solverAmount == totalRequired`; `_fillSameChain` runs normally: `alreadyFilled` becomes `totalRequired`, `isFullyFilled` stays `true`, `_execute` runs once, `OrderFilled` is emitted, `_filled[commitment]` is set to the solver.
3. Any address (solver or third party) calls the same public fill entry point again with the identical `order`/`commitment` and any `options.outputs[i].amount` (even `0`, since `solverAmount == 0` combined with `remaining == 0` does not flip `isFullyFilled` to `false` — see lines 76-78).
4. Inside `_fillSameChain`: `alreadyFilled == totalRequired` ⇒ `remaining == 0` ⇒ loop body hits `continue` ⇒ `isFullyFilled` remains `true` ⇒ `_withdraw` is called with all-zero amounts (no-op, no revert) ⇒ `_execute(order, outputsLen)` is invoked a second time ⇒ `OrderFilled` is emitted a second time for the same `commitment`.
5. Repeat step 3 indefinitely — each call re-executes `order.output.call` and re-emits `OrderFilled` at no cost, since all token transfers are skipped as zero-amount.

Note: step 3's reachability from the public API could not be fully confirmed in this session because the outer dispatcher function (`evm/src/apps/IntentGatewayV2.sol`) was not inspected; if that function already enforces `_filled[commitment] == address(0)` before calling `_fillSameChain`, this specific replay is blocked at the wrapper level and only the internal function itself remains unguarded.
