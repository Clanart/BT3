### Title
Webhook HMAC verification does not bind the request body to the `X-Shopify-Shop-Domain` header, allowing cross-shop webhook forgery via signature replay - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates the HMAC over the raw POST body [1](#0-0) , while the shop identity used by the app for tenant-scoping is read separately, unauthenticated, from the `X-Shopify-Shop-Domain` header [2](#0-1) . The HMAC digest, computed in `PayloadVerification#hmac_valid?`, is a function of the raw body only, not the header [3](#0-2) . This is the same root-cause pattern as the referral bug: a security decision (which shop this webhook belongs to) is derived from an attacker-controllable value that is not cryptographically bound to the check that "authenticates" the request (the HMAC).

### Finding Description
The app's client secret used to compute/verify webhook HMACs is shared across every shop that installs the app - it is not per-shop. Any merchant who installs the app on their own store is a valid, "unprivileged" recipient of genuine Shopify webhooks signed with that same shared secret. Such a merchant can:
1. Install the app on their own shop and receive/trigger a legitimate webhook (e.g. `products/update`) whose body+HMAC are valid for the shared secret.
2. Replay that exact body and HMAC signature to the app's webhook endpoint, but alter only the `X-Shopify-Shop-Domain` header to a victim shop's domain.

Because `hmac_valid?(data)` only inspects `request.raw_post`, altering the header has zero effect on the HMAC check [3](#0-2) , so `verify_request` still passes [1](#0-0) . The controller then proceeds to use the forged `shop_domain` value as the trusted tenant identifier. This exact pattern is the one Shopify's own docs recommend building custom webhook controllers around, where `shop_domain` from this same helper is fed directly into a background job for tenant scoping without further validation: [4](#0-3) 

The stock `WebhooksController`, which delegates to `ShopifyAPI::Webhooks::Registry.process`, also passes the shop only through the header-derived request object [5](#0-4) , and its own job templates use `webhook_request.shop` (again header-sourced) for job dispatch [6](#0-5) .

This mirrors the referral bug's root cause precisely: the "referrer" (here, `shop_domain`) is treated as validated because a signature check passed, but the signature never actually covers/binds that value, so an attacker who legitimately controls one signed message can substitute the untrusted field to make the system believe a different, unrelated tenant is the source.

### Impact Explanation
An attacker who is a legitimate but unrelated merchant of the app can forge webhook requests that the app attributes to a victim shop it has no relationship to. Depending on what the app's webhook handlers do with `shop_domain` (e.g. updating shop-scoped records, invalidating sessions, writing to a victim shop's data, or triggering `shop/redact`-style mandatory privacy actions), this enables cross-shop data corruption, spurious/forced actions against a shop the attacker does not control, and denial-of-service or data-integrity issues for the victim tenant.

### Likelihood Explanation
Likelihood is High: the attacker needs no special access — only their own legitimate app installation to obtain a validly-signed webhook body, and standard HTTP tooling to replay it with a modified header. No secrets need to be leaked; the shared app secret is used as designed for the attacker's own shop, and the flaw is purely in the missing binding between signed content and the trust decision made from the header.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` header as trusted on its own. Either:
1. Include the shop domain in the HMAC-covered payload validation (Shopify webhook payloads already contain shop-identifying fields in the JSON body for most topics) and cross-check the header against the body-derived value before use, or
2. Bind webhook processing to a shop that is independently known/expected by the app (e.g., only accept webhooks for shop domains that have an active, previously-established session/installation, and reject/flag mismatches), rather than trusting the header verbatim as the tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., update a product) so Shopify sends a POST to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Capture `B` and `H` (e.g., via a proxy/logging endpoint under the attacker's control, or a webhook debugging tool).
4. Replay the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `PayloadVerification#hmac_valid?(B)` still returns `true` (it never looks at the domain header) [3](#0-2) , so `verify_request` passes [1](#0-0) , and any handler code that calls `shop_domain` receives `"victim.myshopify.com"` [2](#0-1)  despite the payload actually originating from the attacker's own shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```
