### Title
Missing Lockout on Keyring Passphrase Verification RPCs Allows Unlimited Brute-Force of Master Passphrase - ([File: chia/daemon/server.py])

### Summary
The chia daemon's WebSocket RPC handlers `unlock_keyring` and `validate_keyring_passphrase` verify the keyring master passphrase against the encrypted keyring file with no attempt counter, throttling, or lockout of any kind, unlike the CLI-only interactive path which enforces `MAX_RETRIES = 3` with a delay before raising `KeychainMaxUnlockAttempts`. Any caller able to reach these daemon RPC endpoints can attempt the passphrase an unbounded number of times, defeating the purpose of a lockout/anti-brute-force protection — directly analogous to ZITADEL's missing lockout on (T)OTP checks (GHSA-7j7j-66cv-m239), where an authentication-verification endpoint lacked any attempt-limiting mechanism.

### Finding Description
`chia/util/keyring_wrapper.py` defines an interactive CLI helper, `obtain_current_passphrase`, that enforces a maximum of `MAX_RETRIES = 3` attempts with a `FAILED_ATTEMPT_DELAY` and ultimately raises `KeychainMaxUnlockAttempts` (`chia/util/errors.py`) once exhausted: [1](#0-0) 

However, the daemon's programmatic RPC surface bypasses this protection entirely. `WebSocketServer.unlock_keyring` and `WebSocketServer.validate_keyring_passphrase` in `chia/daemon/server.py` call `Keychain.master_passphrase_is_valid(key, force_reload=True)` directly per request with no counter, no delay, and no lockout state tracked across calls: [2](#0-1) [3](#0-2) 

Each failed attempt simply returns `{"success": False, "error": "bad passphrase"}` (or similar), and the caller is free to immediately retry with another guess. There is no `KeychainMaxUnlockAttempts` enforcement, no exponential backoff, and no persistent failed-attempt tracking anywhere in this RPC path — the lockout guard that exists for the interactive terminal prompt (`obtain_current_passphrase`) is not mirrored for the daemon RPC surface that GUI/wallet clients and any other RPC-connected process actually use to unlock the keyring or validate a passphrase.

This mirrors the ZITADEL bug class precisely: a security-critical secret-verification operation (there, OTP/TOTP checks; here, master passphrase checks) is exempted from the lockout policy that protects an analogous, adjacent authentication path (there, password checks; here, the CLI passphrase prompt), enabling unrestricted online guessing against the real gatekeeper of the private keys.

### Impact Explanation
The keyring master passphrase gates access to the encrypted private keys stored in the keyring (`chia/util/file_keyring.py`, `chia/util/keychain.py`). If an attacker who can reach the daemon's WebSocket RPC (e.g., a malicious or compromised local process, browser-based CSRF-style requests if any surface is exposed, or any component granted narrower service scope but reusing the daemon connection) can send unlimited `unlock_keyring`/`validate_keyring_passphrase` requests, they can perform online brute-force or dictionary attacks against the user's master passphrase without any rate limiting. A successful guess unlocks the keyring, exposing all private keys and enabling unauthorized signing/movement of funds — a direct violation of wallet key custody guarantees.

### Likelihood Explanation
Exploitability depends on the attacker already having a live connection to the daemon RPC (which normally requires possession of the daemon's SSL client certificate). Given that constraint, the lack of any lockout is unconditional and trivially exercised by simply looping the RPC call — there is no additional complexity, timing race, or privilege escalation required beyond having RPC connectivity, which multiple local processes (wallet, farmer, harvester, third-party plugins) may possess.

### Recommendation
Track failed passphrase-verification attempts per daemon session (or globally) in `WebSocketServer.unlock_keyring` and `WebSocketServer.validate_keyring_passphrase`, enforcing the same `MAX_RETRIES`/backoff/lockout semantics already implemented for `obtain_current_passphrase`, and raise `KeychainMaxUnlockAttempts` (or an equivalent locked-out response) once the limit is exceeded, requiring an explicit cooldown or daemon restart to reset the counter.

### Proof of Concept
1. Connect to the running chia daemon's WebSocket RPC endpoint (as any client possessing daemon connectivity).
2. Repeatedly send `create_payload("unlock_keyring", {"key": "<guess>"}, ...)` or `create_payload("validate_keyring_passphrase", {"key": "<guess>"}, ...)` with different passphrase guesses in a tight loop, as exercised by the test scaffold in `chia/_tests/core/daemon/test_daemon.py`: [4](#0-3) 
3. Observe that no request is ever rejected due to attempt-count exhaustion — every call is independently evaluated via `Keychain.master_passphrase_is_valid`, confirming the absence of any lockout mechanism on this path.

```python
    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"

        if success and self.run_check_keys_on_unlock:
            try:
                self.log.info("Running check_keys now that the keyring is unlocked")
                check_keys(self.root_path)
                self.run_check_keys_on_unlock = False
            except Exception as e:
                tb = traceback.format_exc()
                self.log.error(f"check_keys failed after unlocking keyring: {e} {tb}")

        response: dict[str, Any] = {"success": success, "error": error}
        return response
```
