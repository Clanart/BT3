### Title
Reward-tier double-dipping in `ArbWomUp3.incentiveDeposit`/`getRewardAmount` via `mWomSV.startUnlock` manipulation - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getRewardAmount(..., _lock=true)` computes the tiered vlMGP reward using the caller-controlled, instantaneously mutable value `mWomSV.getUserTotalLocked(_account)` as the sole proxy for "already rewarded" stake via `calDoubledCounted`. Because `mWomSV.startUnlock` immediately reduces `getUserTotalLocked` (it moves the amount to cooldown before any time delay is required for the accounting change), an attacker can shrink their tracked locked balance between two `incentiveDeposit(_amount,_convertRatio,_bullMode,2)` calls and get the same tier bracket rewarded twice, minting excess vlMGP out of `ArbWomUp3`'s MGP balance.

### Finding Description
`incentiveDeposit` with `_mode == 2` calls: [1](#0-0) 

`getRewardAmount(_amountToConvert, _account, true)` computes `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)`, derives a tiered `rewardAmount`, then subtracts `calDoubledCounted(_account)` which is computed purely from the *current* `mWomSV.getUserTotalLocked(_account)`: [2](#0-1) 

`mWomSV.getUserTotalLocked` is a live, user-mutable value: [3](#0-2) 

Critically, `mWomSV.startUnlock` is a permissionless, unprivileged function callable by the position owner at any time, and it decreases `getUserTotalLocked` *immediately* (by adding the amount to `userUnlockings[...].amountInCoolDown`, which is subtracted in `getUserTotalLocked`) — no cooldown wait is required for the accounting effect to take place: [4](#0-3) 

Exploit flow:
1. Attacker calls `incentiveDeposit(amount1, ratio, bull, 2)`. `_deposit` mode 2 locks `amount1/2` into `mWomSV` for the attacker: [5](#0-4)  `getRewardAmount` computes reward using full `amount1` against tier 0 baseline (locked = 0), and mode-2 doubles it (`rewardToSend * 2`), then locks it into `vlMGP` for the attacker.
2. Attacker immediately calls `mWomSV.startUnlock(x)` to move part of the freshly-locked `mWomSV` balance into cooldown, instantly reducing `getUserTotalLocked(attacker)`.
3. Attacker calls `incentiveDeposit(amount2, ratio, bull, 2)` again. `calDoubledCounted` now uses the *reduced* `getUserTotalLocked`, understating the amount "already rewarded," so the same lower tier bracket is rewarded again on top of the new deposit's tier bracket.

Because `calDoubledCounted`/`getRewardAmount` rely on a spot-checkable, freely decreasable balance instead of a monotonic, persisted "cumulative amount ever rewarded" counter, the reward computation is not conservation-safe across repeated calls interleaved with `startUnlock`. The `whenNotPaused`/`nonReentrant` modifiers on `incentiveDeposit` do not prevent this since the exploit is sequential, not reentrant.

### Impact Explanation
This lets an unprivileged attacker mint more vlMGP reward from `ArbWomUp3`'s MGP balance than the tier configuration entitles them to for their net locked stake, draining the contract's reward reserve intended for other users — a theft of unclaimed vlMGP yield from the reward pool (funds transferred via `vlMGP.lockFor`, capped only by `IERC20(mgp).balanceOf(address(this))` per call, not in aggregate). This matches the Immunefi "theft of unclaimed yield" impact class.

### Likelihood Explanation
The attacker only needs WOM tokens to deposit and no special privileges — `mWomSV.startUnlock` is a normal user function on their own position. The exploit is deterministic, repeatable across many cycles (bounded by `maxSlot` cooldown slots), and does not depend on any admin misconfiguration beyond a normal increasing tier schedule set via `setMultiplier`. Capital requirement is limited to the WOM needed to cross tier boundaries, and gains scale with the number of repetitions.

### Recommendation
Replace the "already rewarded" heuristic (`calDoubledCounted` based on live `mWomSV.getUserTotalLocked`) with a persisted, monotonically-increasing per-account counter (e.g., `cumulativeRewardedMWomSV[account]`) that is only incremented on `incentiveDeposit`/lock and never decreased by unrelated `mWomSV` unlock actions. Reward computation should be based on this persisted counter, not on a balance the user can independently manipulate via `mWomSV.startUnlock`.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `vlMGP`, `mWom`, mock `smartWomConvert`; configure `rewardTier=[0,1000,3000]`, `rewardMultiplier=[100,200,300]`; fund `ArbWomUp3` with MGP.
2. Attacker acquires WOM, calls `incentiveDeposit(2000, ratio, false, 2)`. Record `vlMGPMinted1 = getRewardAmount(...) * 2`.
3. Attacker calls `mWomSV.startUnlock(x)` reducing `getUserTotalLocked(attacker)` by `x`.
4. Attacker calls `incentiveDeposit(2000, ratio, false, 2)` again. Record `vlMGPMinted2`.
5. Assert `vlMGPMinted1 + vlMGPMinted2 > rewardMultiplier[getUserTier(attacker)] * (totalWOMDeposited) / DENOMINATOR` computed against the attacker's actual final `mWomSV.getUserTotalLocked` — demonstrating reward minted exceeds what the final tier/stake would justify, i.e., Conservation is violated.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
    }
