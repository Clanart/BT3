### Title
Missing non-identity check on verification shares allows a zero (identity) group key, making deposited funds publicly spendable — (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes functions that accept a `to` argument without checking it against the zero address, allowing funds to be sent to `address(0)`. The Serai analog of "send funds to the zero value" is constructing a threshold key whose **group key is the identity point**: `ThresholdKeys::new` / `ThresholdKeys::read` accept `verification_shares` deserialized with `Ciphersuite::read_G`, which — unlike `Curve::read_G` — does **not** reject identity points. If the shares for participants `1..=t` are all identity, `group_key` collapses to identity, and the Bitcoin receive address derived from it has a publicly known discrete log (just the registered offset/tweak), so deposited funds are stealable by anyone — the same "funds sent to a known-zero destination" outcome.

### Finding Description
`ThresholdKeys::read` deserializes each verification share with `<C as Ciphersuite>::read_G` (`crypto/dkg/src/lib.rs:622`). `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only enforces a canonical point encoding — it explicitly permits the identity element. The identity-rejecting variant `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) exists but is not used here.

`ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) validates the number of shares, participant indexes (`> n` rejected at line 362), and interpolation consistency, then computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

There is no check that any `verification_shares[i]` is non-identity, and no check that the resulting `group_key` is non-identity. A crafted `ThresholdKeys` serialization containing all-identity verification shares therefore produces `group_key = identity` without error.

Downstream, `bitcoin-serai` derives the spend key for received outputs from the group key plus a registered offset (`processor/src/networks/bitcoin.rs:112-122` shows `key = p2tr_key - G*offset`, i.e., the chain key is `group_key*scalar + G*offset`). With `group_key = identity` and default `scalar = 1` (`crypto/dkg/src/lib.rs:388`), the script key's discrete log is exactly `offset`, a value registered in public `register_offset` protocol data — so the private key to every "received" output is publicly known.

### Impact Explanation
An attacker who supplies crafted serialized `ThresholdKeys` (e.g., via the key-import/recovery path that feeds `ThresholdKeys::read`) causes the validator set to treat `identity` as its group key. The resulting Bitcoin deposit address is spendable by anyone who computes `offset` from on-chain data — the network reports outputs as received while the attacker (or any observer) sweeps them. This is a direct analog of transferring protocol funds to the zero address: value is moved to a destination with a trivially known (zero-base) private key. It also fits the accepted impact class "funds reported received that are not spendable" — not spendable *by the protocol*, spendable by the adversary.

### Likelihood Explanation
Reachability is limited to contexts where serialized `ThresholdKeys` come from untrusted bytes (key recovery/import, validator-set provisioning rather than a locally generated DKG). A normally executed PedPoP/MuSig DKG produces honest verification shares, so exploitation requires the deserialization path to be fed attacker-controlled encodings — the scenario the scan rules explicitly scope in (`ThresholdKeys::read` on untrusted bytes). Given the requirement of reaching that path, Medium severity is appropriate.

### Recommendation
- In `ThresholdKeys::new` (`crypto/dkg/src/lib.rs`), reject identity verification shares and reject an identity `group_key`, e.g., `if bool::from(share.is_identity()) { Err(...) }` per share and for the summed key — mirroring the zero-address check recommended in the report.
- In `ThresholdKeys::read`, use a share-reading helper that rejects identity (equivalent to `Curve::read_G` semantics) rather than raw `Ciphersuite::read_G`.
- Optionally reject `secret_share == 0` for symmetry, since a zero share is never honestly produced (`Curve::random_nonce` already rejects zero).

### Proof of Concept
```rust
use std::{collections::HashMap, io::Cursor};
use ciphersuite::{Ciphersuite, Secp256k1}; // any in-scope suite
use dkg::{ThresholdKeys, ThresholdParams, Participant};

// Build a serialized ThresholdKeys blob where every verification
// share encodes the identity point (canonical 33-byte 0x00.. encoding
// for secp256k1; 32 zero bytes for Ed25519/Ristretto).
let t = 2u16; let n = 3u16; let i = 1u16;
let mut buf = vec![];
buf.extend((Secp256k1::ID.len() as u32).to_le_bytes());
buf.extend(Secp256k1::ID);
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(i.to_le_bytes());
buf.push(1); // Interpolation::Lagrange
buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr()); // secret_share
for _ in 1..=n {
  buf.extend(Secp256k1::G::identity().to_bytes()); // identity shares
}

let keys = ThresholdKeys::<Secp256k1>::read(&mut Cursor::new(buf)).unwrap();
// keys.group_key() == identity; no error was raised.
// With scalar = 1 and a public offset, the Bitcoin script key
// discrete log is `offset` — publicly known → funds stealable.
assert!(bool::from(keys.group_key().is_identity()));
```
