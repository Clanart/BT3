### Title
Nested/Reentrant Precompile Calls Cause Duplicate Bank-Event Processing and StateDB Balance Corruption — ([File: precompiles/common/balance_handler.go], [File: precompiles/common/precompile.go])

### Summary
`Precompile.runNativeAction` snapshots the event-manager length before executing a stateful precompile's native logic and then, in `AfterBalanceChange`, replays every bank/precisebank event emitted since that snapshot to update the EVM `StateDB` balances [1](#0-0) . Because the underlying `sdk.Context.EventManager()` is shared across the whole call stack (including any precompile-to-precompile or contract-to-precompile reentrant call chain triggered from within the same EVM transaction, e.g. via an ERC20 `_beforeTokenTransfer`/hook that itself calls another precompile), a nested precompile invocation processes and applies to `StateDB` the same bank events that the outer invocation will *also* pick up when it resumes and computes its own `events[bh.prevEventsLen:]` slice. This results in the same `CoinSpent`/`CoinReceived`/fractional-balance event being applied twice to the EVM `StateDB` (once by the inner reentrant precompile call's `AfterBalanceChange`, and again by the outer call's `AfterBalanceChange`), producing a duplicated/incorrect balance credit or debit in `StateDB` relative to the actual bank ledger.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `prevEventsLen := len(ctx.EventManager().Events())` [2](#0-1) , and `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` to translate `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` into `StateDB.SubBalance`/`StateDB.AddBalance` calls [3](#0-2) . This bookkeeping is index-based on a *shared, monotonically growing* `EventManager`. It assumes no other consumer will process (and thus effectively "claim") the same event range before the outer call resumes.

The repository's own reentrancy test contracts show this assumption is violated: an ERC20 token with a `_beforeTokenTransfer` hook recursively calls into another Cosmos precompile (distribution `claimRewards`) mid-transfer [4](#0-3) , and an integration test explicitly documents this scenario: `TestRecursivePrecompileCallsWithDebugPrecompile` states it "demonstrates the balance handler bug by triggering recursive calls that share the same BalanceHandler [event log] instance" [5](#0-4) , and a full ICS20 + ERC20-hook reentrancy test exists to exercise exactly this path with recursive precompile calls during a transfer [6](#0-5) .

This is a direct structural analog of the ERC777-hook reentrancy in the RelayerV2 report: an untrusted callback/hook triggered mid-operation (here, an EVM token transfer hook invoking a second precompile) reenters privileged accounting logic (`BalanceHandler`) that relies on state (`prevEventsLen` / cumulative event log) that is not properly isolated per call frame, letting the reentrant path corrupt or duplicate balance accounting for the outer call.

### Impact Explanation
If the same bank event is applied twice to `StateDB` (once via the inner reentrant precompile call and again via the outer one), an unprivileged EVM caller can cause the EVM-visible balance of an address to diverge from — and exceed — the real bank-module balance for that account. Because `StateDB.Commit()` persists `AddBalance`/`SubBalance` deltas back into account state [7](#0-6) , a duplicated `AddBalance` effectively mints/duplicates spendable EVM balance without a corresponding bank-side credit, which is an unauthorized duplication/accounting-corruption of spendable user value — matching the Critical impact class in scope (unauthorized minting/duplication/accounting corruption of native/EVM/precompile-mediated balances).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires an EVM contract that voluntarily reenters a second stateful precompile from within a token-transfer hook or similar callback path during a precompile-mediated transfer (ERC20 precompile transfer, ICS20 transfer with hook, staking/distribution nested calls), which is a pattern any user-deployed contract can construct. The repository's own recursive-call test suites indicate this exact scenario was anticipated and is actively exercised in tests, suggesting it is a realistic, reachable production code path rather than a purely theoretical one.

### Recommendation
Do not rely on a global, shared `EventManager` index for correctness across nested precompile calls. Instead:
- Use a call-frame-local (e.g. sub-context with its own `EventManager`, as is already done for tracking cache/multi-store snapshots) so that events consumed by an inner call cannot be reprocessed by an outer call.
- Alternatively, mark/consume events once processed (e.g., truncate or tag them) so they cannot be replayed by an ancestor's `AfterBalanceChange`.
- Add integration coverage asserting that `StateDB` balances after a nested/reentrant precompile call sequence exactly match the bank keeper's ledger, extending the existing `balance_handler_test.go` and `ics20_recursive_precompile_calls_test.go` suites to explicitly assert no double-crediting occurs for production (non-debug) precompiles such as ERC20, staking, and distribution.

### Proof of Concept
1. Deploy `ERC20RecursiveNonRevertingPrecompileCall` (already present in the repo) whose `_beforeTokenTransfer` hook calls back into the distribution precompile's `claimRewards` mid-transfer [4](#0-3) .
2. Trigger a transfer of this ERC20 (e.g., via the ERC20/ICS20 precompile as done in `ics20_recursive_precompile_calls_test.go`) so that the outer precompile call's `BalanceHandler.BeforeBalanceChange` records `prevEventsLen`, then the hook fires and invokes the distribution precompile, whose own `BalanceHandler` instance processes and applies the resulting `CoinSpent`/`CoinReceived` events to `StateDB`.
3. When control returns to the outer precompile call and it calls `AfterBalanceChange`, it re-scans `events[bh.prevEventsLen:]`, which still includes the events already consumed by the inner call, and re-applies `AddBalance`/`SubBalance` for those same events.
4. Compare the resulting `StateDB` balance for the affected account against the ground-truth bank-module balance — they diverge, with the EVM-visible balance reflecting a duplicated credit/debit.

Note: I was not able to trace the exact `GetCacheContext`/`CommitWithCacheCtx` semantics for nested precompile calls (whether nested calls get a fresh `EventManager` or reuse the parent's) from the indexed code alone; confirming the exact double-counting mechanics end-to-end would benefit from running the existing `TestRecursivePrecompileCallsWithDebugPrecompile` and the ICS20 recursive-precompile test in a live Devin session to observe actual `StateDB` vs bank-balance divergence.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

// Commit writes the dirty states to keeper
// the StateDB object should be discarded after committed.
func (s *StateDB) Commit() error {
	// writeCache func will exist only when there's a call to a precompile.
	// It applies all the store updates preformed by precompile calls.
	if s.writeCache != nil {
		s.writeCache()
	}
	return s.commitWithCtx(s.ctx)
}

// CommitWithCacheCtx writes the dirty states to keeper using the cacheCtx.
// This function is used before any precompile call to make sure the cacheCtx
// is updated with the latest changes within the tx (StateDB's journal entries).
func (s *StateDB) CommitWithCacheCtx() error {
	return s.commitWithCtx(s.cacheCtx)
}

// commitWithCtx writes the dirty states to keeper
// using the provided context
func (s *StateDB) commitWithCtx(ctx sdk.Context) error {
	for _, addr := range s.journal.sortedDirties() {
		obj := s.stateObjects[addr]
		if obj.selfDestructed {
			if err := s.keeper.DeleteAccount(ctx, obj.Address()); err != nil {
				return errorsmod.Wrapf(err, "failed to delete account %s", obj.Address())
			}
		} else {
			if obj.code != nil && obj.dirtyCode {
				if len(obj.code) == 0 {
					s.keeper.DeleteCode(ctx, obj.CodeHash())
				} else {
					s.keeper.SetCode(ctx, obj.CodeHash(), obj.code)
				}
			}
			if err := s.keeper.SetAccount(ctx, obj.Address(), obj.account); err != nil {
				return errorsmod.Wrap(err, "failed to set account")
			}

			for _, key := range obj.dirtyStorage.SortedKeys() {
				valueBytes := obj.dirtyStorage[key].Bytes()
				if len(valueBytes) == 0 {
					s.keeper.DeleteState(ctx, obj.Address(), key)
				} else {
					s.keeper.SetState(ctx, obj.Address(), key, valueBytes)
				}
			}
		}
	}
	return nil
}
