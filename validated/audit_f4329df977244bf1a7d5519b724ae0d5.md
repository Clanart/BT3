### Title
Fee/weight accounting omits the OP_RETURN `data` output already committed to the transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes resources being counted as available while still committed to another use, skewing accounting. The same bug class exists in `SignableTransaction::new`: the OP_RETURN `data` output is pushed onto `tx_outs` (committing the transaction to carrying it) *before* the weight/vbyte calculation, yet `calculate_weight_vbytes` is called with `payments`, not `tx_outs`. The transaction's size accounting therefore never includes the data output it will actually carry, so `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check are computed against a smaller transaction than the one produced.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` first, then the fee math runs over `payments` only:

```rust
// send.rs:194-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (send.rs:62-127) builds a mock transaction solely from `payments` and the optional `change` script; the OP_RETURN output (up to ~80 bytes of data plus output overhead, ≈ 20+ vbytes) is absent. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` under-charges relative to the caller-specified fee rate; the real transaction achieves a lower effective sat/vbyte than requested.
- `if weight > MAX_STANDARD_TX_WEIGHT` can pass for a transaction that actually exceeds the standardness weight limit once the data output is included.
- The change-branch recomputation (`fee_with_change`) inherits the same omission, so `value = input_sat - payment_sat - fee_with_change` can leave a change output that, together with the omitted data output, pushes the tx over weight or below the intended feerate.
- `fee()` reports the true fee, so callers comparing `fee()` vs. `needed_fee()` see a discrepancy rooted in this accounting gap.

The reachable path is public input: `data: Option<Vec<u8>>` supplied to `SignableTransaction::new`, the analog of "available assets" (weight/vbyte budget and input satoshis) being spent against a commitment (the data output) that was never debited.

### Impact Explanation
A produced transaction pays a fee rate below what the caller specified via `fee_per_vbyte`, which can leave it stuck or evicted under mempool pressure, and can emit a transaction that violates `MAX_STANDARD_TX_WEIGHT` and is rejected by standard relay policy. Funds are not directly stealable and the signatures remain correct (the sighash commits to the real transaction via `Prevouts::All`), so impact is a reliable mis-pricing/relayability failure rather than theft: Medium.

### Likelihood Explanation
Any caller supplying `data` triggers the miscalculation; larger `data` values (up to the 80-byte cap enforced at send.rs:171) maximize the error. No adversary is required, though a party controlling the `data` field can deliberately degrade the effective feerate or push the transaction over standard weight.

### Recommendation
Compute weight/vbytes over the final `tx_outs` (or pass `payments` plus the OP_RETURN script) in both the no-change and with-change invocations of `calculate_weight_vbytes`, so `needed_fee`, `NotEnoughFunds`, and the weight check reflect the transaction actually built.

### Proof of Concept
1. Call `SignableTransaction::new` with one input, one payment, `change = None`, `data = Some(vec![0u8; 80])`, and `fee_per_vbyte` chosen so `needed_fee` lands exactly at the desired feerate.
2. Observe `transaction().output` contains the OP_RETURN output while `needed_fee()` was computed on a mock tx without it.
3. Broadcast result: `fee() / vsize(real_tx) < fee_per_vbyte`; with enough inputs plus the data output, the real weight can exceed `MAX_STANDARD_TX_WEIGHT` while the check passed.
