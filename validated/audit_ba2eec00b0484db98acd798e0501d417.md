### Title
Stale positional line-selection is silently reused across diff refresh, causing partial commits to include/exclude the wrong lines - ([File: app/src/lib/stores/app-store.ts])

### Summary
The Beanstalk report's root cause is a broken invariant: a downstream component (`bipSeedGauge`) kept using state computed by an earlier version of dependent code after that code changed, without re-validating that the old state was still meaningful, corrupting accounting. GitHub Desktop has a structurally identical invariant break in its partial-commit ("stage selected lines") pipeline: the user's line selection is stored as a set of *positional indices* into a diff (`hunk.unifiedDiffStart + lineIndex`), and when the working-directory diff is refreshed the app blindly carries the old positional selection forward as long as the indices are still "in range" of the new diff — without checking that those indices still refer to the *same lines of content*.

### Finding Description
Line selection is modeled purely positionally. `DiffSelection` stores selected/deselected lines as a `Set<number>` of absolute indices (`app/src/models/diff/diff-selection.ts:74-84`), and those indices are computed as `hunk.unifiedDiffStart + lineIndex`, i.e., a pure position in the unified diff, not a stable identity tied to the actual line content (`app/src/ui/diff/diff-helpers.tsx:38-53`, `app/src/lib/patch-formatter.ts:143-144,266-267`).

When the working directory diff for the currently selected file is reloaded (e.g., triggered by the file watcher on any change to the file), `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts:3404-3513` recomputes `selectableLines` from the *new* hunks using the same positional scheme, then simply intersects the *old* selection against this new positional set via `withSelectableLines`: [1](#0-0) 

The code comment explicitly acknowledges the limitation: [2](#0-1) 

If the diff hunks shift (lines added/removed above or around the previously-selected hunk, hunks merging/splitting, or line renumbering) between the time the user made a line-level selection and the time the file is subsequently re-diffed, an old absolute index can remain "selectable" in the new diff purely by coincidence of position, while now pointing at a semantically different line. `updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts:32-60`) similarly re-attaches the old `DiffSelection` object to the newly-fetched `WorkingDirectoryFileChange` based only on file `id` (path/status), not diff content: [3](#0-2) 

When the user finally commits, `formatPatch` builds the patch strictly from `file.selection.isSelected(absoluteIndex)` against whatever diff is current at that moment (`app/src/lib/patch-formatter.ts:143-161`), with no re-validation that the index still corresponds to the line the user actually reviewed and checked. The result: the patch handed to `git apply --cached` in `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-81`) can silently include lines the user never intended to commit, or omit lines the user did intend to commit — exactly the "stale-state-used-without-revalidation" failure mode from the Beanstalk report, here corrupting the commit content instead of Stalk accounting.

### Impact Explanation
This breaks the core invariant the report's mitigation calls out — every place that consumes derived/cached state must be updated consistently when the underlying source changes. Here, the "cache" is the user's line-selection bitmap, and the underlying source is the diff; the app does not verify that stale positional indices remain semantically valid before using them to build the commit patch. The outcome is silent corruption of what the user commits: lines the developer deliberately excluded from a partial commit can end up staged and committed (or vice versa), including in shared/collaborative repositories, without any error or warning surfaced to the user. Because commits happen automatically from this state with no diff-content re-confirmation step, this is a genuine "silent corruption of what the user commits or pushes" class issue.

### Likelihood Explanation
The trigger only requires the working-directory diff for the file currently being partially staged to change between the user's selection action and the commit action — e.g., a background formatter/linter/build watcher, an editor autosave, or any other process that touches the file while the user is mid-review in the Changes/commit panel, which is common in real developer workflows in actively-built repositories. No local/physical access, admin rights, or pre-existing malware on the host is required; the only precondition is the ordinary occurrence of the file being modified on disk while a partial-selection commit is in progress, which the code path's own comment (`app-store.ts:3480-3486`) treats as an already-recognized but unresolved edge case rather than a hypothetical.

### Recommendation
Tie diff-line selection to a content-stable identity (e.g., the actual old/new line numbers plus a content hash of the hunk, or by diffing the previous selection against the new diff hunks and dropping/renormalizing any selection whose surrounding context lines no longer match) rather than raw positional indices that are reused across diff refreshes. At minimum, when a refreshed diff structurally differs from the one the current selection was computed against (hunk count/positions changed), clear the partial selection entirely and require the user to re-select, rather than silently carrying forward indices that "still fit." Add regression tests that refresh a file's diff mid-selection (simulating concurrent external modification) and assert that `createCommit`/`formatPatch` never includes/excludes lines other than what the user's original content-based selection intended.

### Proof of Concept
1. Clone/checkout a repository and modify a tracked file so it has two separate hunks: hunk A (lines 5-10) and hunk B (lines 40-45).
2. In GitHub Desktop's Changes view, open the diff and select only specific lines inside hunk B for partial commit (leave hunk A and the rest of hunk B unselected), matching the pattern used in `app/test/unit/git/commit-test.ts:307-365` (`can commit multiple hunks from modified file`) which selects by `unifiedDiffStart`-relative index.
3. Before committing, have an external process (e.g., `git checkout -- <file>` followed by a partial re-edit, or a formatter run) insert/remove lines above hunk A, shifting all subsequent line positions but leaving the file watcher-triggered refresh path (`updateChangesWorkingDirectoryDiff`, `app-store.ts:3404-3513`) to recompute `selectableLines` for the new hunk layout.
4. Observe that the previously computed absolute indices (from the stale hunk B position) are retained as "selected" against the new diff's `selectableLines` set (`app-store.ts:3478-3497`) purely because the numeric index still falls within range — even though the line at that index in the new diff is different content.
5. Commit; inspect the resulting commit via `getChangedFiles` and compare it against the lines the user actually intended to select. The staged content will differ from the user's original selection, demonstrating silent corruption of the commit contents, analogous to the Beanstalk report's stale-facet/stale-library state being used post-upgrade without revalidation.
