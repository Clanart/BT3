Based on my research, I found a direct analog to this bug class in the Kaia auction (KIP-249) module.

### Title
Auction admin can instantly and silently redirect/invalidate all pending bids by changing `AuctionEntryPoint`/`Auctioneer` with no timelock or notice - (File: kaiax/auction/impl/bid_pool.go, kaiax/auction/impl/execution.go)

### Summary
The Kaia auction module re-reads the active `AuctionEntryPoint` address (via `SystemRegistry`), the `Auctioneer` address, and `bidTxGasBuffer`/version parameters from on-chain system-contract state on every single block, and applies any change immediately and unconditionally by wiping the entire bid pool. There is no timelock, no advance-notice mechanism, and no argument validation beyond a zero-address check. This is the same "admin front running / bad timing" class described in the external report: privileged parameters that govern user transaction behavior can change atomically and take effect on the very next block, with no way for an in-flight bidder to know their submitted bid will be silently discarded.

### Finding Description
`AuctionModule.PostInsertBlock` calls `updateAuctionInfo` after every block, which reads the current `AuctionEntryPoint` address, `Auctioneer` address, gas buffer, and version straight from contract state at the just-inserted block: [1](#0-0) 

Whatever is read is unconditionally pushed into the bid pool via `BidPool.updateAuctionInfo`, which — the moment *any* of the four values differs from the previous block — clears every pending bid, including bids that are already valid and scheduled for future blocks (up to `allowFutureBlock = 2`): [2](#0-1) 

Per the module's own documentation, this is by design: "This module reads `SystemRegistry` and `AuctionEntryPoint` to detect any changes... If one of them is changed, the module will clear the existing bids in the bid pool." [3](#0-2) 

The `Auctioneer` and entry-point address are controlled by privileged/admin-level system contracts (`SystemRegistry` for the active `AuctionEntryPoint`, and the entry point contract's own `auctioneer` setter, as reflected in the `ChangeAuctioneer` event in the generated bindings): [4](#0-3) 

There is no time-locked, two-step process for either change — the reference mock demonstrates the unrestricted, immediate-effect pattern (`setAuctioneer` sets state directly with no delay, no old/new validation): [5](#0-4) 

This mirrors exactly the bug pattern from the external report: `zAuctionAccountant.SetZauction()` updates a critical routing address with immediate effect and no warning, causing in-flight user actions (bid acceptance) to unpredictably fail or be redirected. In Kaia's case, a searcher's `BidTx` is generated (`GetBidTxGenerator`) against a specific `auctionEntryPoint`/version snapshot taken from the bid pool at generation time: [6](#0-5) 

If the admin changes the entry point or auctioneer between the time a searcher's bid was accepted/broadcast and the time the block is actually built, the bid pool is wiped for that block cycle, so the previously-accepted, in-flight bid is silently dropped. The searcher's paired target transaction — which reveals their strategy on the public mempool — can still be executed by the proposer, but now unprotected by the searcher's bid/payment commitment, letting third parties or the block proposer itself capture the MEV opportunity for free while the original bidder's protection vanishes without any warning.

### Impact Explanation
Bidders (auction searchers) have no way to know in advance that their accepted bid — covering a target transaction they've already broadcast to the public network — will be invalidated at the next block boundary due to a privileged, single-step, immediate-effect admin change to `AuctionEntryPoint`/`Auctioneer`. This can cause:
- Loss of the intended MEV protection/settlement for bidders whose target transactions are now exposed unprotected.
- Redirection of the entire pending auction workload to a new auctioneer/entry point chosen unilaterally and instantaneously by the admin, which could be timed to specifically exclude or include certain bids (selective censorship), exactly as flagged in the source report's "Examples" section.
- Divergent/unpredictable block-building behavior since the change takes effect the moment it lands on-chain, with no grace window for in-flight bids.

### Likelihood Explanation
The change requires a privileged system-contract call (`SystemRegistry` update or entry-point `auctioneer` change), so it cannot be triggered by an arbitrary unprivileged sender. However, once such a governance/admin transaction is submitted, the effect is deterministic, immediate, and silent to all in-flight bidders — no separate consent or acknowledgment step is required from affected users, matching the report's "unpredictable behavior due to admin front running or bad timing" pattern precisely.

### Recommendation
Introduce a mandatory timelock / two-step announce-then-commit process for changing `AuctionEntryPoint` (in `SystemRegistry`) and `Auctioneer` (in the entry-point contract), so that bidders have a guaranteed grace window (e.g., N blocks) during which either the old configuration remains valid or bid submission is paused, rather than having the bid pool wiped in the same block the change becomes effective. Additionally, consider emitting/consuming the existing `ChangeAuctioneer`-style events proactively in the client to warn/reject bid submissions ahead of a scheduled cutover, and validate that new addresses differ from the current ones and are non-zero before triggering a pool clear.

### Proof of Concept
1. A searcher submits `auction_submitBid` with a valid bid targeting block `N+1`, which is accepted into the bid pool per `AuctionAPI.SubmitBid` and `BidPool.AddBid`.
2. In block `N`, the `SystemRegistry` admin (or `AuctionEntryPoint` admin) submits a transaction changing the active `AuctionEntryPoint` address or `Auctioneer` address — a single, unwarned, immediately-effective call, as modeled in `AuctionEntryPointMock.setAuctioneer`.
3. When block `N` is inserted, `AuctionModule.PostInsertBlock` → `updateAuctionInfo` (kaiax/auction/impl/execution.go:55-109) reads the new values and calls `bidPool.updateAuctionInfo`, which detects the mismatch and calls `clearBidPool()` (kaiax/auction/impl/bid_pool.go:186-213), instantly discarding the searcher's previously accepted bid for block `N+1`.
4. The searcher's already-broadcast target transaction can still be mined in block `N+1`, now without the bid-based MEV protection or settlement the searcher paid/arranged for, while the searcher had no prior signal that this would occur.

// updateAuctionInfo updates the auctioneer address and auction entry point address for the given block number.
// It expects the `num` is after Randao fork.
// It returns true if the non-zero auctioneer address and auction entry point address are set, otherwise false.
func (a *AuctionModule) updateAuctionInfo(num *big.Int) bool {
	auctioneer := common.Address{}
	auctionEntryPointAddr := common.Address{}
	auctionEntryPointVersion := ""
	bidTxGasBuffer := uint64(0)

	defer func() {
		a.bidPool.updateAuctionInfo(auctioneer, auctionEntryPointAddr, auctionEntryPointVersion, bidTxGasBuffer)
	}()

	header := a.Chain.GetHeaderByNumber(num.Uint64())
	if header == nil {
		return false
	}
	_, err := a.Chain.StateAt(header.Root)
	if err != nil {
		return false
	}

	backend := backends.NewBlockchainContractBackend(a.Chain, nil, nil)

	// 1. Read auction entry point address
	auctionEntryPointAddr, err = system.ReadActiveAddressFromRegistry(backend, system.AuctionEntryPointName, num)
	if err != nil {
		return false
	}

	if auctionEntryPointAddr == (common.Address{}) {
		return false
	}

	// 2. Read auctioneer address
	auctioneer, err = system.ReadAuctioneer(backend, auctionEntryPointAddr, num)
	if err != nil {
		return false
	}

	if auctioneer == (common.Address{}) {
		return false
	}

	// 3. Read gas buffer estimate
	bidTxGasBuffer, err = system.ReadGasBufferEstimate(backend, auctionEntryPointAddr, num)
	if err != nil {
		return false
	}

	// 4. Read AUCTION_VERSION to pick the right EIP-712 typehash and ABI for bids targeting this entry point.
	auctionEntryPointVersion, err = system.ReadAuctionVersion(backend, auctionEntryPointAddr, num)
	if err != nil {
		return false
	}

	return true
}

// clearBidPool clears the bid pool.
func (bp *BidPool) clearBidPool() {
	bp.bidMu.Lock()
	defer bp.bidMu.Unlock()

	bp.bidMap = make(map[common.Hash]*auction.Bid)
	bp.bidTargetMap = make(map[uint64]map[common.Hash]*auction.Bid)
	bp.bidWinnerMap = make(map[uint64]map[common.Address]common.Hash)
}

// updateAuctionInfo updates the auction info if the auctioneer or auction entry point address is changed.
func (bp *BidPool) updateAuctionInfo(auctioneer common.Address, auctionEntryPoint common.Address, auctionEntryPointVersion string, bidTxGasBuffer uint64) {
	bp.auctionInfoMu.Lock()
	defer bp.auctionInfoMu.Unlock()

	if bp.auctioneer == auctioneer && bp.auctionEntryPoint == auctionEntryPoint && bp.auctionEntryPointVersion == auctionEntryPointVersion && bp.bidTxGasBuffer == bidTxGasBuffer {
		return
	}

	// Clear the existing auction pool since the auctioneer or auction entry point address is changed.
	bp.clearBidPool()

	bp.auctioneer = auctioneer
	bp.auctionEntryPoint = auctionEntryPoint
	bp.auctionEntryPointVersion = auctionEntryPointVersion
	bp.bidTxGasBuffer = bidTxGasBuffer

	logger.Info("Update auction info", "auctioneer", auctioneer, "auctionEntryPoint", auctionEntryPoint, "auctionEntryPointVersion", auctionEntryPointVersion, "bidTxGasBuffer", bidTxGasBuffer)
}
