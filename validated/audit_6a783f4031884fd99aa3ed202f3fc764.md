### Title
Uncontrolled recursion in `PuzzleWithRestrictions.from_memo()` when parsing attacker-supplied nested `MofN` custody memos - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
CVE-2025-46206 is an uncontrolled-recursion denial of service where `mutool clean` recurses into an attacker-crafted, unbounded self-referential outline structure (`strip_outline()`), crashing the process. The reachable analog in this codebase is `PuzzleWithRestrictions.from_memo()`, which reconstructs a custody-puzzle tree from an on-chain memo by recursively calling itself once per `MofN` branch, with no limit on nesting depth or branching factor. Because this memo originates from `CREATE_COIN` memo data written by whoever created the coin (e.g., a PlotNFT/pooling singleton owner or any custody-architecture user), a malicious counterparty can craft a coin with an arbitrarily deeply nested `MofN` memo. When an honest wallet syncs that coin (e.g., pool/plotnft wallet sync), parsing the memo triggers deep unbounded Python recursion.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is a classmethod used to reconstruct an inner custody puzzle purely from on-chain memo data so that a syncing wallet can recognize an unknown puzzle by its structure: [1](#0-0) 

The critical recursive step is:
```
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
``` [2](#0-1) 

`MofNHint.from_program` places no bound on `member_memos` length, and nothing in `MofN.__post_init__` (or elsewhere) checks nesting depth — it only validates `m <= n`, `m >= 1`, and no duplicate leaf nodes: [3](#0-2) 

Because each `MofN` member is itself a full `PuzzleWithRestrictions`, an attacker can nest `MofN(m=1, members=[MofN(m=1, members=[...])])` to whatever depth Python's call stack allows, entirely inside a single CLVM memo blob that is cheap to construct and attach to a coin.

This memo is parsed automatically during PlotNFT wallet sync, not just via a manual/opt-in API call: `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` whenever it cannot recognize the inner puzzle by direct puzzle-hash comparison, i.e., for any not-already-tracked singleton transition: [4](#0-3) 

This is analogous to `strip_outline()`'s bug class (CWE-674, uncontrolled recursion on attacker-supplied nested/self-referential data): both walk an attacker-controlled tree-like structure recursively with no depth cap, and both are triggered merely by processing untrusted data (a PDF outline vs. a coin's memo) rather than by any privileged access.

### Impact Explanation
A malicious singleton/PlotNFT counterparty can craft a coin whose `CREATE_COIN` memo encodes a deeply nested `MofN` custody memo. Any wallet that syncs and attempts to interpret that coin via `PlotNFT.get_next_from_coin_spend()` (i.e., any node/wallet tracking that PlotNFT/pooling singleton, which is required behavior for pool wallet sync) will recurse through `PuzzleWithRestrictions.from_memo()` proportionally to the attacker-chosen nesting depth. Sufficiently deep nesting causes a Python `RecursionError`, which — if unhandled at the call site — crashes or halts wallet sync processing for that wallet ("spend-triggered transaction-processing halt"), a legitimate Medium-severity DoS analogous to the mupdf bug.

### Likelihood Explanation
Likelihood is Medium: constructing the malicious memo requires no special privilege — any coin owner can memo a `CREATE_COIN` output with an arbitrary CLVM blob shaped like a valid `MofN` memo tree, and the actual custody puzzle behind the memo does not need to be spendable or even consistent with the fake hint tree to trigger `from_memo`'s recursion (the puzzle-hash consistency check happens only after parsing, at `plotnft_puzzle.inner_puzzle_hash() != singleton_create_coin.puzzle_hash`, i.e., after the recursive parse has already occurred). The main uncertainty is exact stack-depth limits under the production Python interpreter/thread stack size in the target deployment, and whether callers of `get_next_from_coin_spend` wrap it in exception handling broad enough to catch `RecursionError` (only `ValueError` is caught around `from_memo`), which would determine whether this becomes an unhandled crash versus a caught, recoverable error.

### Recommendation
- Add an explicit recursion-depth (or total-node-count) limit to `PuzzleWithRestrictions.from_memo()` / `MofN` construction, rejecting memos that exceed a sane bound (mirroring how `strip_outline()` was fixed with a visited/seen-node guard and/or depth cap).
- Convert the recursive `from_memo` parse into an iterative (explicit stack-based) traversal, similar to the non-recursive `sha256_treehash` pattern already used elsewhere in this codebase.
- Ensure callers such as `PlotNFT.get_next_from_coin_spend` catch broader parsing failures (including `RecursionError`) and translate them into `GetNextPlotNFTError` rather than allowing an uncaught exception to propagate and disrupt wallet sync.

### Proof of Concept
1. Construct a `MofNHint` whose `member_memos` list contains a single `PuzzleWithRestrictions` memo which is itself another single-member `MofN` memo, and repeat this nesting N times (e.g., N = 10,000+), each wrapped as `Program.to((PuzzleWithRestrictions.spec_namespace, [nonce, [], 1, MofNHint(m=1, member_memos=[...]).to_program()]))`.
2. Attach this deeply nested memo as the `memo_blob` on a `CREATE_COIN` condition of a singleton spend that otherwise looks like a valid (or invalid, since validation of the parsed hash occurs after parsing) PlotNFT/pooling singleton transition.
3. Have a victim wallet track/sync this singleton so that `PlotNFT.get_next_from_coin_spend()` is invoked and falls through to `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`, per [4](#0-3) .
4. Observe that parsing recurses to depth N via [2](#0-1) , raising `RecursionError` and halting the sync path for that wallet.

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int
    member_memos: list[Program]

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),
        )
