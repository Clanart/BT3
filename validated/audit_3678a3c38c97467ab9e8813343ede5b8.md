### Title
Malformed per-input signature-share vectors panic transaction completion - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`TransactionSignatureMachine::complete` does not validate that each participant supplied one signature share per transaction input before indexing the per-participant vector. A signing participant can provide an empty inner `Vec<SignatureShare<Secp256k1>>` and cause `Vec::remove(0)` to panic during `complete`. [1](#0-0) 

### Finding Description
`TransactionSignatureMachine::complete` accepts a `HashMap<Participant, Vec<SignatureShare<Secp256k1>>>` supplied by counterparties. [2](#0-1)  For every transaction input, it removes index `0` from each participant’s inner vector. [3](#0-2)  Neither the map-level code nor the inner-vector access checks that the vector is non-empty, so an empty vector reaches `Vec::remove` and panics. [3](#0-2) 

This differs from the fixed-length deserialization path: `read_share` parses one scalar share for each signing machine and would produce a correctly sized vector. [4](#0-3)  The public `complete` API itself accepts the structured collection directly and performs no equivalent cardinality check before indexing it. [1](#0-0) 

### Impact Explanation
A participant capable of submitting signature-share data to `complete` can terminate the calling thread or process during transaction finalization. [1](#0-0)  Repeated malformed submissions can prevent the wallet from completing threshold-signed Bitcoin transactions, producing remote denial of service analogous to the reported crafted-packet crash. [1](#0-0) 

### Likelihood Explanation
The trigger only requires a participant to submit an empty inner share vector while satisfying the outer `HashMap` participation mapping. [1](#0-0)  No secret, invalid curve encoding, compromised validator, or control over Serai internals is required. [1](#0-0) 

### Recommendation
Before completing any input, validate every participant’s inner vector length equals `self.sigs.len()` or the transaction input count, and return `FrostError::InvalidShare` for malformed participants. [1](#0-0)  Avoid `remove(0)` on untrusted vectors; consume each vector with an iterator or `get(0).copied()` after validation. [3](#0-2) 

### Proof of Concept
The following demonstrates the reachable panic condition without requiring valid signature values.

```rust
// networks/bitcoin/src/wallet/send.rs
// Given an initialized TransactionSignatureMachine for at least one input:
let mut shares = std::collections::HashMap::new();
shares.insert(participant, Vec::new());

// The outer map contains the participant, but the inner vector is empty.
// Completion reaches shares.remove(0) and panics before signature validation.
let _ = transaction_signature_machine.complete(shares);
```
