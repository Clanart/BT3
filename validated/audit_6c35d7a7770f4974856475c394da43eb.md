Audit Report

## Title
`InitializeNonceAccount` allows unprivileged front-running of a System-Program-created nonce account, letting an attacker seize the nonce authority - ([File: programs/system/src/system_processor.rs])

## Summary
The System Program's `initialize_nonce_account` handler performs no signer check on the target account or on the supplied `authorized` pubkey, unlike `allocate` which explicitly requires `address.is_signer(signers)`. Any account already owned by the System Program, sized/rent-exempt for `nonce::State`, and still `State::Uninitialized`, can be initialized by any unprivileged transaction with an attacker-chosen `authorized` pubkey.

## Finding Description
`initialize_nonce_account` only verifies that the account is writable and in `State::Uninitialized`, then unconditionally writes `State::Initialized(Data::new(*nonce_authority, ...))` using the `nonce_authority` value taken directly from instruction data, with no signer requirement anywhere in the function. [1](#0-0) 

The processor dispatch for `SystemInstruction::InitializeNonceAccount` passes the instruction-supplied `authorized` straight to `initialize_nonce_account` without any additional signer verification. [2](#0-1) 

This is in direct contrast to `allocate`, in the same file, which explicitly requires the target address to be a signer before any state is written to the account. [3](#0-2) 

Because account creation (`CreateAccount`/`Allocate`+`Assign`) and `InitializeNonceAccount` are separate instructions that can be submitted in separate transactions, an account can sit on-chain in `State::Uninitialized`, System-Program-owned, and rent-exempt after creation but before initialization. During that window, nothing in `initialize_nonce_account` or its dispatch path ties the call to the account's creator/owner — any unprivileged party can submit `InitializeNonceAccount` with their own pubkey as `nonce_authority` and win the race.

## Impact Explanation
The nonce authority set by `initialize_nonce_account` is the sole gatekeeper checked by `AdvanceNonceAccount`, `WithdrawNonceAccount`, and `AuthorizeNonceAccount`. An attacker who wins this race becomes the sole controller of the account's `authority` field (the exact corrupted value), and can subsequently withdraw lamports down to the rent-exempt minimum via `WithdrawNonceAccount`, or repeatedly invalidate the durable nonce via `AdvanceNonceAccount`, without ever having signed the original account creation. This is fund theft / unauthorized control of an on-chain account by an unprivileged party, matching the allowed impact category "fund theft/loss" for a built-in program.

## Likelihood Explanation
Exploitability requires an integrator to create and initialize a nonce account in two separate transactions rather than atomically — a known pitfall documented for durable-nonce usage, but not something enforced or prevented by the runtime. Any account creation flow that follows this "create-then-initialize-later" pattern exposes the account to front-running the moment it lands on-chain in `State::Uninitialized`, since transaction visibility (mempool/gossip) lets any unprivileged party race an `InitializeNonceAccount` instruction ahead of the legitimate initialization transaction. This requires only public inputs and no privileged access, satisfying the unprivileged-attacker requirement.

## Recommendation
Require the nonce account (or a payer/authority account established at `CreateAccount` time) to be a signer of `InitializeNonceAccount`, mirroring the `is_signer` check already present in `allocate`, so that an unprivileged third party cannot supply an arbitrary `nonce_authority` for an account it did not create.

## Proof of Concept
1. Victim submits `CreateAccount`/`Allocate`+`Assign` to create account `N`, sized for `nonce::state::State` and owned by the System Program, without yet calling `InitializeNonceAccount`.
2. Attacker observes `N` on-chain in `State::Uninitialized` (or observes the pending creation transaction) and submits `InitializeNonceAccount(attacker_pubkey)` targeting `N` before the victim's initialize transaction lands, per the dispatch at `system_processor.rs` L448-466.
3. `initialize_nonce_account` succeeds because it only checks writability, `State::Uninitialized`, and rent-exemption (`system_instruction.rs` L169-201) — no signer check ties the call to `N`'s creator.
4. The victim's subsequent `InitializeNonceAccount` call fails with `InstructionError::InvalidAccountData` (`system_instruction.rs` L202-209) since the account is now `Initialized`.
5. Attacker, now the recorded nonce authority, calls `WithdrawNonceAccount` or `AdvanceNonceAccount` to drain lamports or deny use of the durable nonce. A Rust unit test can reproduce this by invoking `initialize_nonce_account` twice on the same freshly-created uninitialized account with different `nonce_authority` values and confirming the second call fails while the first attacker call succeeds and sets the attacker's pubkey as authority.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
