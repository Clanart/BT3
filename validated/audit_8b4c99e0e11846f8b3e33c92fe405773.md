### Title
Unvalidated `ReceivedOutput` prevout data loaded during `SignableTransaction` construction produces an unspendable, unfixable signed transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the LineaRollup bug where data loaded during `_submitData` initialization was insufficiently validated, `SignableTransaction::new` and `SignableTransaction::multisig` in `networks/bitcoin/src/wallet/send.rs` load prevout data (`TxOut` value, `script_pubkey`, and `OutPoint`) and a scalar `offset` from `ReceivedOutput` without verifying them against the actual on-chain UTXO. The only consistency check performed is internal — the offset-derived key's script is compared against the attacker-supplied `prevouts[i].script_pubkey` — so fabricated-but-self-consistent data is accepted, and the resulting FROST signature commits to invalid `Prevouts::All` data, producing a transaction that can never be confirmed.

### Finding Description
`ReceivedOutput::read` accepts arbitrary bytes for `offset` (via `Secp256k1::read_F`), `output: TxOut`, and `outpoint: OutPoint` with no validation that the outpoint exists on-chain or that the declared `TxOut` matches the real UTXO (`networks/bitcoin/src/wallet/mod.rs:122-133`). In `SignableTransaction::new`, the claimed `output.value` is summed into `input_sat` and used for fee/change arithmetic (`send.rs:175`, `send.rs:215-234`), and the unverified `TxOut`s are stored into `prevouts` (`send.rs:253`). In `multisig`, the sole check is `p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey` (`send.rs:276-279`) — a check between two attacker-controlled fields. It never checks that `outpoint` resolves to a UTXO with that `script_pubkey`/`value`, nor that `offset` corresponds to the actual registered scanner offset for that script. During signing, `Prevouts::All(&self.tx.prevouts)` commits the sighash to the fabricated prevout set (`send.rs:373-390`).

### Impact Explanation
If a `ReceivedOutput` is supplied with (a) an inflated `output.value`, the change/fee math is corrupted and the signed transaction pays an incorrect fee or nonexistent change; (b) an `outpoint`/`script_pubkey`/`offset` triple that is self-consistent (offset `δ` with `script_pubkey = p2tr(group_key + δG)`) but does not correspond to the real UTXO, the threshold honestly signs a `taproot_key_spend_signature_hash` committing to wrong prevouts. The completed transaction fails Bitcoin's sighash verification and is permanently unbroadcastable — funds reported as spendable inputs cannot move. Like the Linea bug, the corrupted state is not correctable: FROST preprocesses are bound to this transaction (`TransactionSignMachine::cache`/`from_cache` are `unimplemented!`, `send.rs:333-349`), so the signing session's nonces are burned and the attempt cannot be resubmitted with corrected data.

### Likelihood Explanation
Reachable whenever `ReceivedOutput::read` (explicitly in-scope as an untrusted-bytes entry point) or an otherwise-unverified `ReceivedOutput` feeds `SignableTransaction::new`. An attacker controlling the serialized output record — e.g., a relayed or stored scan result tampered before signing — only needs to flip bytes in `output.value` or supply a consistent `(offset, script_pubkey, outpoint)` tuple; no key material or validator collusion is required. In the honest-scan path `Scanner::scan_transaction` always produces correct data, so exploitation requires the read/deserialize path rather than the scanner path.

### Recommendation
In `SignableTransaction::multisig` (or `new`), validate each input's `outpoint` against the chain or a trusted UTXO set and confirm the declared `TxOut` matches the confirmed output before producing `prevouts`. Additionally, verify that each supplied `offset` is one of the offsets legitimately registered for the group key (e.g., recompute the expected script from a trusted registry rather than trusting the serialized `script_pubkey`), so the check at `send.rs:277` binds to ground truth rather than to attacker-supplied data. Consider allowing a corrected `SignableTransaction` to be resubmitted rather than binding preprocesses irrevocably.

### Proof of Concept
1. Obtain a valid `ReceivedOutput` for a UTXO paying to `p2tr(group_key)`, serialize it (`ReceivedOutput::serialize`, `mod.rs:144-148`).
2. Tamper the embedded `TxOut.value` upward (e.g., 1 BTC → 2 BTC) before `ReceivedOutput::read` (`mod.rs:122-133`), which performs no range or existence check.
3. `SignableTransaction::new` computes `input_sat` from the inflated value, allocates excess to the change output, and stores the forged `TxOut` into `prevouts` (`send.rs:175`, `send.rs:230`, `send.rs:253`).
4. `multisig` passes the check at `send.rs:277` because the offset/script are still self-consistent; `TransactionSignMachine::sign` then commits `Prevouts::All` to the forged prevout (`send.rs:375-390`).
5. `complete` yields a fully signed transaction whose Taproot signatures are invalid against the real UTXO — it can never be mined, and since `cache`/`from_cache` panic, the bound preprocesses cannot be reused to sign a corrected transaction. [1](#0-0) [2](#0-1) [3](#0-2)
