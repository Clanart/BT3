### Title

`SchnorrSignature::read` accepts identity nonces, enabling trivial signatures for identity public keys - ([File: crypto/schnorr/src/lib.rs](crypto/schnorr/src/lib.rs))

### Summary

`SchnorrSignature::read` admits a point-at-infinity `R`, and `SchnorrSignature::verify` does not reject either an identity nonce or an identity public key. As a result, the all-identity signature `(R = 0, s = 0)` satisfies the verifier equation for an identity public key under every challenge.

### Finding Description

The decoder only performs two canonical field/point reads and applies no semantic restrictions: [1](#0-0) 

Verification evaluates:

```text
R + cA - sG = 0
```

via `batch_statements` and `multiexp_vartime`: [2](#0-1) 

If `R`, `A`, and `s` are all zero/identity, every term is identity and verification succeeds regardless of the caller-supplied challenge. Other Serai code recognizes that an identity Schnorr nonce is invalid and explicitly rejects it when reading signed Tributary transactions: [3](#0-2) 

The generic `SchnorrSignature` API lacks the same guard.

### Impact Explanation

An unprivileged party can provide untrusted bytes to `SchnorrSignature::read` and then pass the decoded value to `verify`. For an identity public key, they can submit a canonical encoding of `(identity, zero)` and obtain a successful verification without knowing a private key.

This is a forged signature under the API's own verification formula. It affects any integration which treats an identity point as a valid public key or fails to reject identity public keys before calling `SchnorrSignature::verify`.

### Likelihood Explanation

The required input is short, deterministic, and does not depend on the message or challenge. Exploitation only requires reaching a verification path where the public key is attacker-controlled and the identity encoding is accepted by the selected ciphersuite's `read_G`. The separate Tributary parser demonstrates that identity `R` values are representable enough that downstream code had to add an explicit rejection.

### Recommendation

Reject identity nonces and identity public keys in `SchnorrSignature::verify`, and preferably reject identity `R` in `SchnorrSignature::read` as well:

```rust
pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
  if bool::from(self.R.is_identity()) || bool::from(public_key.is_identity()) {
    return false;
  }

  multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
}
```

### Proof of Concept

For any ciphersuite whose `read_G` accepts the canonical identity encoding:

```rust
let sig = SchnorrSignature::<C> {
  R: C::G::identity(),
  s: C::F::ZERO,
};

let public_key = C::G::identity();
let arbitrary_challenge = C::F::ONE;

assert!(sig.verify(public_key, arbitrary_challenge));
```

The verification expansion is:

```text
R + cA - sG
= 0 + 1·0 - 0·G
= 0
```

Therefore `verify` returns `true`.

  /// Return the series of pairs whose products sum to zero for a valid signature.
  /// This is intended to be used with a multiexp.
  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }
