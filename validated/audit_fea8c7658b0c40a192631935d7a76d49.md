## Analysis

The reported bug class describes a swap function that internally calls a liquidity-provision/swap step with **hardcoded 0 slippage tolerance** and `block.timestamp` as the deadline, with the actual slippage check only happening *after* the fact on an aggregated amount — allowing MEV bots to sandwich the internal swap and extract value at the expense of the caller/protocol.

This repo (blackvul/contracts--014, MagpieXYZ / Wombat integration) has a structurally identical pattern in `wombat/SmartWomConvert.sol`.

### Title
Unprotected internal WOM→mWom buyback swap in `SmartWomConvert._convertFor` enables MEV sandwich extraction from harvested/converted yield - (File: wombat/SmartWomConvert.sol)

### Summary
`SmartWomConvert._convertFor` performs a partial buyback swap of WOM for mWom through `IWombatRouter.swapExactTokensForTokens` with a **hardcoded minimum output of `0`** and `block.timestamp` as the deadline, and only validates the final combined output against `_minRec` *after* the swap has executed. [1](#0-0) 

### Finding Description
The internal swap leg of the conversion has zero slippage protection at the point of execution: [2](#0-1) 

The aggregate check `convertAmount + amountRec < _minRec` happens only after the swap returns, comparing the *sum* of the direct-deposit portion and the swapped portion against `_minRec`: [3](#0-2) 

Because `convertAmount` (the non-swapped, 1:1 minted portion) is included in the sum, an attacker can sandwich the AMM swap (front-run to push the WOM→mWom price down, let the swap execute receiving far less than fair value, then back-run to restore price and capture the difference) while the aggregate check still passes as long as `convertAmount + amountRec >= _minRec`. This is the same root cause as the referenced report: an unprotected inner swap step masked by a coarser, post-hoc check, is enough to leak value to MEV searchers.

This function is reachable by ordinary, unprivileged flows:
- Directly via the public `convert`/`convertFor` entry points. [4](#0-3) 
- Via `smartConvert`, which is invoked as part of `WombatStaking`'s reward-harvest flow (`_toMasterWomAndSendReward`), triggered by any unprivileged `deposit`/`withdraw`/`harvest` call, and which forces `_minRec = _amountIn` for the aggregate only, not for the swap leg itself. [5](#0-4) 
- Via `ManualCompound.compound`, where any user compounds claimed WOM rewards through the configured `_convertor` (`SmartWomConvert`) using a caller-supplied `_minRec`. [6](#0-5) 

### Impact Explanation
Because `smartConvert` is exercised automatically as part of the WOM reward harvesting pipeline (triggered by any unprivileged staking action), the buyback swap of pooled WOM protocol rewards into mWom is repeatedly exposed to sandwiching. This results in systematic extraction of value from the yield being distributed to `WombatStaking` depositors/stakers — a direct loss of unclaimed yield to MEV bots at the expense of ordinary users, not an admin or governance actor.

### Likelihood Explanation
Every harvest/deposit/withdraw cycle that triggers `_toMasterWomAndSendReward` → `smartConvert` performs this unprotected swap using public router liquidity, on a predictable pool (`womMWomPool`), with a deterministic, publicly observable transaction — a low-cost, repeatable target for MEV searchers, similar to the original report's sandwich PoC showing ~20% value loss on a single occurrence.

### Recommendation
Add real slippage protection to the intermediate swap itself (e.g., a caller/protocol-supplied minimum output for the `buybackAmount` leg, or split the `_minRec` check across the swap and deposit legs individually) rather than only checking the aggregated total after execution, and consider using a TWAP/oracle-based minimum-out estimate for the automatic `smartConvert` path invoked by staking operations where no user-supplied slippage parameter exists.

### Proof of Concept
1. User (or the `WombatStaking` harvest flow) calls `convert`/`smartConvert`, which routes `buybackAmount` WOM through `IWombatRouter.swapExactTokensForTokens(..., 0, address(this), block.timestamp)`.
2. A searcher observes the pending tx in the mempool, front-runs it by swapping WOM→mWom on `womMWomPool` to move the price unfavorably (since the call enforces no minimum output).
3. The victim's swap executes at the manipulated price, returning a reduced `amountRec`; because `convertAmount` (from the non-swapped mWom minted 1:1) is included in the aggregate, `convertAmount + amountRec` can still clear `_minRec` (which for `smartConvert` is fixed at `_amountIn`).
4. The searcher back-runs, restoring the price and pocketing the spread — mirroring the FlashSwapRouter sandwich PoC in the external report where LP tokens received dropped ~20% due to the same "hardcoded 0 tolerance + deadline = block.timestamp" pattern.
