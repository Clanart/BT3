## Title
Cross-chain escrow release performs external token transfer before decrementing escrow accounting, violating checks-effects-interactions - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the IntentGateway's `withdraw()` function transfers escrowed funds to the beneficiary via a low-level external call *before* decrementing the `_orders[commitment][token]` escrow accounting, mirroring exactly the bug-class in the external report (mutating accounting state after an external call/hook that can re-enter). The EVM version of the same logic (`IntentsBase._withdraw`) was hardened to decrement escrow *before* the external transfer, but the Tron contract still has the unsafe ordering.

### Finding Description
`IntentGatewayV2.withdraw()` on Tron only guards against a completely empty escrow slot and then performs the token/native transfer immediately, updating accounting afterward: [1](#0-0) 

Compare this with the EVM `IntentsBase._withdraw`, which was fixed to decrement `_orders[body.commitment][token]` *before* making the external call, following checks-effects-interactions: [2](#0-1) 

This is the direct structural analog of the FERC1155 `mint`-before-`totalSupply` update bug: an outgoing external call (`beneficiary.call{value: amount}("")` for native assets, which invokes the beneficiary's `receive()`/`fallback()`) executes while `_orders[commitment][token]` still reflects the pre-withdrawal (full) escrow balance. Since `beneficiary` is always attacker-controllable — it is either the `solver` who filled the order (RedeemEscrow) or the `user` who placed/cancelled the order (RefundEscrow), both legitimate participants in the intent lifecycle — an attacker can deploy a malicious contract as beneficiary and reenter during the callback while the escrow ledger for that commitment/token is still stale.

The codebase's own `IntrinsicIntentsReentrancyTest.sol` demonstrates that the project is aware of and actively defends against exactly this class of bug in the EVM contracts (`_filled[commitment] = msg.sender` is set at the top before any external call in `_fillSameChain`/`_fillCrossChain`), but that same discipline was not applied to the Tron `withdraw()` transfer-then-decrement ordering: [3](#0-2) 

### Impact Explanation
While `_filled[commitment]` is set before the token loop (blocking a second full `withdraw()` invocation for the same commitment through `onAccept`/`onGetResponse`, which are `onlyHost`-gated), the escrow decrement for the token currently being transferred remains unprotected during the external call window. For multi-token orders, a malicious beneficiary can reenter during the first token's native transfer and read/act on `_orders[commitment][otherToken]` values that are still pre-decrement, or interact with other contract state that depends on the not-yet-updated escrow ledger before the loop finishes. This falls under the "stealing or loss of funds" / "transaction manipulation" impact categories called out in the bounty scope, since the corrupted value is the escrow accounting map (`_orders`) which gates fund release.

### Likelihood Explanation
The attack requires no compromised relayer, prover, or governance actor — only that the attacker act as a normal solver or order-placing user with a smart-contract beneficiary address, which is a standard, permissionless capability in the intent-fill/cancel flow. The `onAccept`/`onGetResponse` gating limits full re-entry into `withdraw()` itself, so a complete PoC exploiting a concrete double-spend was not fully traced end-to-end within available tool budget; the deviation from the CEI pattern relative to the already-hardened EVM code path is nonetheless a clear, locally-provable regression that the project's own tests classify as a reentrancy risk elsewhere.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to decrement `_orders[body.commitment][token]` (and delete `_orders[body.commitment][TRANSACTION_FEES]`) *before* performing the native/ERC20 external transfer, matching the pattern already applied in `IntentsBase._withdraw` on EVM.

### Proof of Concept
Not fully reproduced with a working exploit transaction within the scope of this analysis — the code-level CEI violation is directly evidenced by the line ordering shown above, but confirming a concrete double-spend requires deeper tracing of all reentrant-reachable entry points in the Tron contract (e.g. `cancelOrder`, `sweep`), which was not completed due to tool-call limits. This should be verified with a Foundry/Tron test analogous to `IntrinsicIntentsReentrancyTest.sol`'s `ReentrantBeneficiary`, targeting `withdraw()`'s native-token branch.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
