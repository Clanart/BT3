### Title
Unchecked uint64 subtraction in EIP-7623 floor-data-gas adjustment can underflow `st.gas` - (File: blockchain/state_transition.go)

### Finding Description
`TransitionDb()` computes the refunded gas and then, for Prague-rules (EIP-7623) transactions, forces `st.gas` down to the floor-data-gas requirement when the actually used gas is below the floor:

```go
gasRefund := st.calcRefund()
st.gas += gasRefund
if rules.IsPrague {
    // After EIP-7623: Data-heavy transactions pay the floor gas.
    if st.gasUsed() < floorDataGas {
        st.gas = st.initialGas - floorDataGas
    }
}
st.returnGas()
``` [2](#0-1) 

`st.gas` is a `uint64`. The subtraction `st.initialGas - floorDataGas` is a raw Go `-` operation with no overflow check, mirroring exactly the bug class described in the external report (Uniswap/Superposition `state.amount_calculated -= ...` without `checked_sub`). The guard condition checked is `st.gasUsed() < floorDataGas`, i.e. `st.initialGas - st.gas < floorDataGas` — this is **not equivalent** to guaranteeing `st.initialGas >= floorDataGas`. `floorDataGas` is derived purely from `msg.Data()` length/zero-byte composition and a token cost multiplier (`params.TxCostFloorPerToken`), independent of `st.gas`/`st.initialGas` (which come from the caller-supplied `Gas()`/tx gas limit minus intrinsic gas already spent). `floorDataGas` is validated only against `msg.Gas()` (the *original* tx gas limit) earlier in `TransitionDb`, not against `st.initialGas` (the *purchased* gas after `buyGas()`), and not against `st.gas` (gas remaining after EVM execution and refund).

If `floorDataGas > st.initialGas` while still satisfying `st.gasUsed() < floorDataGas` (which is easy to arrange since `st.gasUsed() = st.initialGas - st.gas` and `st.gas` includes execution refunds that can be large), the subtraction `st.initialGas - floorDataGas` underflows a `uint64`, silently wrapping to a huge value (near `2^64`) instead of reverting or erroring, exactly as described for the Rust/Solidity case in the report.

`st.gas` is subsequently consumed in `st.returnGas()`:
```go
remaining := new(big.Int).Mul(new(big.Int).SetUint64(st.gas), st.gasPrice)
...
st.state.AddBalance(validatedFeePayer, remaining)
``` [3](#0-2) 

An underflowed `st.gas` (near `math.MaxUint64`) multiplied by `st.gasPrice` produces an enormous refund credited to the fee payer's balance — a direct, unauthorized value-movement / supply-inflation bug reachable purely from a single submitted Prague-rules (EIP-7623) transaction with a low-gas-cost/zero-heavy calldata payload from any unprivileged sender.

### Impact Explanation
If triggered, this allows an attacker-controlled transaction to cause `st.gas` to wrap to a near-`2^64` value, which is then multiplied by `gasPrice` and credited back to the sender/fee-payer via `AddBalance`. This is unauthorized KAIA balance creation (mint-like inflation) directly from a public transaction, and would also cause state divergence between nodes if the condition is reachable and not otherwise guarded elsewhere in gas accounting (e.g., `GasPool.SubGas`/block gas limit checks), since the resulting balance credit exceeds any economically justified refund. This satisfies the "unauthorized value movement / supply inflation" criteria.

### Likelihood Explanation
Likelihood depends on whether `floorDataGas > st.initialGas` is actually reachable given the earlier check `if msg.Gas() < floorDataGas { return ..., ErrFloorDataGas }` (which validates against the *original* `msg.Gas()`, before intrinsic-gas deduction and before `buyGas()`/refund adjustments establish `st.initialGas` and `st.gas`). Because `st.initialGas = msg.Gas()` is set in `buyGas()` [4](#0-3)  and `msg.Gas() >= floorDataGas` was already checked, `st.initialGas - floorDataGas` should not underflow under normal call paths, since `st.initialGas` equals the same `msg.Gas()` value validated against `floorDataGas`. This makes exploitation unlikely under the current code path *unless* `st.initialGas` can diverge from `msg.Gas()` (e.g., via blob-gas-related adjustments, EIP-7702 authorization interactions, or alternate message-construction paths not covered in the audited scope) — an aspect this analysis could not fully verify within the available time/tooling. Given the uncertainty about whether `st.initialGas` can differ from the already-validated `msg.Gas()` in all code paths, the severity should be treated conservatively as Medium pending a concrete PoC, consistent with the judge's guidance in the original report to downgrade absent proof of exploitability.

### Recommendation
Replace the raw subtraction with a checked/guarded operation, e.g.:
```go
if rules.IsPrague {
    if st.gasUsed() < floorDataGas {
        if st.initialGas < floorDataGas {
            return nil, fmt.Errorf("%w: initialGas %d < floorDataGas %d", ErrFloorDataGas, st.initialGas, floorDataGas)
        }
        st.gas = st.initialGas - floorDataGas
    }
}
```
Additionally, audit all other raw `uint64` `+`/`-` gas arithmetic in `blockchain/state_transition.go` (and in `blockchain/gaspool.go`, which already uses guarded `AddGas`/`SubGas`) to ensure every subtraction that feeds into a balance-affecting calculation is bounds-checked, matching the `common/math.SafeSub`/`SafeAdd` helpers already used elsewhere in the codebase (e.g. `blockchain/vm/gas_table.go`).

### Proof of Concept
Not independently verified with a running transaction (limited to static code analysis of the available snippets). Reachability requires confirming, in the full `blockchain/state_transition.go` and `types.Message`/`buyGas()` implementation, whether `st.initialGas` can be set to a value smaller than `floorDataGas` for some valid Prague transaction despite the earlier `msg.Gas() < floorDataGas` check — this needs to be validated with a Devin session that can run the full test suite and construct a concrete Prague/EIP-7623 transaction (e.g., all-zero-byte calldata with minimal non-floor gas limit) and inspect `st.gas` after `TransitionDb()` to confirm or rule out the underflow.
