### Title
Permanent, Path-Keyed `safe.directory` Trust Grant Allows Bypass Of Git's Unsafe-Ownership Protection - (File: app/src/lib/git/config.ts)

### Summary
GitHub Desktop's "unsafe repository" protection is meant to warn the user and require an explicit "Trust Repository" action before operating on a Git repository whose directory is owned by a different user (a scenario Git itself flags as `dubious ownership`, since it can lead to malicious hooks/config being executed). However, the trust decision is recorded as a bare filesystem path in the global `safe.directory` Git config, with no binding to the actual repository's identity (owner, content, or git history). Once trusted, that path is trusted forever, for any content that later occupies it — closely mirroring the reported staking bug where a restriction was keyed to an insufficiently scoped identifier (`msg.sender`) rather than the resource actually needing protection.

### Finding Description
When Desktop detects an unsafe repository, `getRepositoryType` parses Git's `dubious ownership` error and returns `{ kind: 'unsafe', path }` [1](#0-0) . The UI then offers a "Trust Repository" button that calls `addSafeDirectory(path)` [2](#0-1)  and the equivalent flow in `MissingRepository` [3](#0-2) .

`addSafeDirectory` simply appends the raw path string to the **global** `safe.directory` Git config, deduplicated only by exact string match, with no expiration and no binding to the repository's actual identity (owner, root commit, remote URL, etc.):

```
export async function addSafeDirectory(path: string) {
  ...
  await addGlobalConfigValueIfMissing('safe.directory', path)
}
``` [4](#0-3) 

Once a path is in `safe.directory`, Git will never again warn about "dubious ownership" for that exact path, no matter what repository subsequently exists there. There is no `removeSafeDirectory` counterpart in the codebase, and removing a repository from Desktop (`dispatcher.removeRepository`) does not revoke the grant — the trust decision the user made about one specific repository's contents/owner silently persists and is transferred to whatever git repository is later placed at that same path.

This is the same broken-invariant pattern as the report: a security check is scoped to an attacker-influenceable identifier (a filesystem path a user controls, e.g. inside their home directory, a removable drive, a network share, or a temp/build directory) rather than to the resource the check is actually meant to protect (the specific repository and its owner). Just as the staking cooldown could be defeated by moving the "same" tokens to a different `msg.sender`, the ownership-trust protection can be defeated by moving different (attacker-controlled) repository content into the "same" already-trusted path.

### Impact Explanation
An attacker who can predict or influence a path previously trusted by the victim (e.g., a shared/multi-user machine, a network mount that gets reattached to a different backing store, a CI/build directory reused across jobs, or a path the user previously trusted and later deleted/repurposed) can place a malicious Git repository at that exact path. Desktop and the underlying Git binary will treat it as already trusted and skip the ownership warning entirely, silently restoring the exact class of risk the feature exists to prevent — automatic execution of files/hooks from an untrusted, differently-owned repository once the user re-opens or re-adds a repository at that path.

### Likelihood Explanation
Requires a scenario where the same path is reused by different repository owners/content over time (shared machines, mapped network drives, removable media, CI checkout directories) and where the user had previously trusted that path once. This is a realistic occurrence for the exact population of users the feature targets (multi-user/shared systems, corporate machines with roaming profiles or network home directories), since that is precisely the "different owner on this machine" scenario the warning is designed for.

### Recommendation
Do not persist trust decisions keyed solely on filesystem path. Bind the trust grant to something tied to the actual repository content/identity (e.g., re-check ownership at open time regardless of prior config, prompt again if the underlying inode/owner changed, or store trust decisions in Desktop's own repository metadata scoped to the initial commit/remote rather than delegating indefinitely to global Git config), and provide a way to revoke a `safe.directory` entry when a Desktop-tracked repository is removed.

### Proof of Concept
1. On a shared or multi-profile machine, user is prompted about an unsafe repository at `C:\Users\shared\repoA` (owned by another OS user) and clicks "Trust Repository", which calls `addSafeDirectory('C:\Users\shared\repoA')` [2](#0-1) .
2. User later removes that repository from Desktop and deletes the directory; `safe.directory=C:\Users\shared\repoA` remains in the global `~/.gitconfig` (no removal path exists in the codebase).
3. An attacker (another local user, or content later synced to that path via a shared/network mount) creates a new, malicious Git repository at the identical path `C:\Users\shared\repoA`, including malicious hooks/config.
4. Victim later adds/opens `C:\Users\shared\repoA` in Desktop again. `getRepositoryType` runs `git rev-parse` which no longer reports `dubious ownership` because the path is already in `safe.directory` [5](#0-4) , so Desktop shows it as a normal, trusted repository and proceeds to run Git operations against attacker-controlled hooks/config without any warning.

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }
```

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
