### Title
`resolveWithin()` sibling-directory prefix bypass allows deep-link-triggered file disclosure outside the repository - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()`, the function GitHub Desktop uses to keep a deep-link-supplied file path confined to a repository's directory, validates containment with a naive string-prefix check (`realResolved.startsWith(realRoot)`) instead of verifying a path-separator boundary. A repository whose directory name happens to be a prefix of a sibling directory's name (e.g. `my-repo` vs `my-repo-secrets`) lets a crafted `..`-relative `filepath` in an `x-github-client://openRepo` deep link resolve into that sibling directory while still passing the check, exactly mirroring the ACL report's pattern of a validation check being satisfiable by a value that is not actually equal/contained but merely shares a string prefix.

### Finding Description
`_resolveWithin()` normalizes and resolves the caller-supplied path segments against the repository root, then confirms containment purely by string prefix comparison: [1](#0-0) 

Critically, `normalizedRelative` is computed from `join(...pathSegments)` alone — it is never joined with `rootPath` before normalization — so a segment containing `..` sequences is preserved through `resolve()` and can walk out of the root entirely: [2](#0-1) 

The only remaining defense is `realResolved.startsWith(realRoot)`. This check has no path-separator boundary, so any path whose string representation begins with `realRoot` — even a completely different sibling directory such as `realRoot + "-secrets"` — is incorrectly treated as "within" the repository, just as the ACL check in the report accepted a differently-parsed-but-string-distinct value.

The consumer of this function is `Dispatcher.openRepositoryFromUrl()`, reachable from the `x-github-client://openRepo?...&filepath=...` deep link handler. It only rejects absolute paths, then relies entirely on `resolveWithin()` for containment before revealing the resolved file to the user: [3](#0-2) 

Because `filepath` is attacker-controlled (it comes straight from the URL an attacker gets the victim to click) and is only checked for being non-absolute, a relative value like `../my-repo-secrets/token.txt` bypasses the intended root confinement whenever a sibling directory exists whose name is prefixed by the repository directory's name.

### Impact Explanation
A successful bypass causes `shell.showItemInFolder(resolved)` to open/reveal an arbitrary file located outside the repository directory in the victim's file manager — a file read/disclosure outside the repo boundary triggered purely by the user clicking an attacker-supplied link, matching the "link or deep link the user clicks... result is file... read outside the repo" impact category. This is a genuine confinement bypass of a security boundary check, not a hardening gap.

### Likelihood Explanation
Exploitation requires the deep-link handler to be reachable (already the case for GitHub Desktop's registered `x-github-client://openRepo` protocol) and a sibling directory whose name is prefixed by the target repository's directory name. This is a realistic real-world condition: users frequently keep related repos as sibling folders (e.g. `project`, `project-secrets`, `project.bak`, `project-old`, forks named `project-fork`), and on case-insensitive file systems the matching surface is even larger. No local access, admin rights, or prior compromise is needed — only clicking a link.

### Recommendation
Change the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to require a path-separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the report's recommendation of comparing the fully-parsed/normalized value rather than a raw substring/prefix match.

### Proof of Concept
1. Victim has `~/Documents/GitHub/my-repo` open in Desktop, and also has a sibling folder `~/Documents/GitHub/my-repo-secrets/token.txt`.
2. Attacker sends victim a link: `x-github-client://openRepo/<url>?filepath=..%2Fmy-repo-secrets%2Ftoken.txt`.
3. `openRepositoryFromUrl()` passes the `isAbsolute` check (path is relative) and calls `resolveWithin(repository.path, filepath)`.
4. `_resolveWithin()` resolves to `~/Documents/GitHub/my-repo-secrets/token.txt`; `realResolved.startsWith(realRoot)` (`realRoot = ~/Documents/GitHub/my-repo`) evaluates `true` because of the shared string prefix, even though the file lives in a completely separate directory.
5. `shell.showItemInFolder(resolved)` reveals `token.txt` from outside the repository to the user, driven entirely by the attacker-controlled link.
