### Title
`ReceivedOutput::read` accepts unauthenticated serialized outputs, reporting attacker-forged deposits that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to CVE-2017-7480 (rkhunter downloading mirror data over an insecure channel and trusting it), `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` deserializes three fully attacker-controlled fields — `offset`, `output` (a `TxOut`), and `outpoint` — and returns them as a `ReceivedOutput`, the same type produced by trusted `Scanner::scan_transaction`/`scan_block`. No check binds `offset` to `output.script_pubkey`, nor verifies that `outpoint` refers to a real on-chain UTXO paying to the scanner's key. Untrusted bytes read into this function are reported by `value()`/`output()`/`outpoint()` as received wallet funds that cannot actually be spent.

### Finding Description
`Scanner::scan_transaction` only emits a `ReceivedOutput` when `output.script_pubkey` matches a script in `self.scripts`, and it derives `offset` from that map and `outpoint` from the real `tx.compute_txid()` (`networks/bitcoin/src/wallet/mod.rs:199-214`). The deserialized path performs none of these invariants:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    output = TxOut::consensus_decode(&mut buf_r)?;
    outpoint = OutPoint::consensus_decode(&mut buf_r)?;
    Ok(ReceivedOutput { offset, output, outpoint })
}
```
(`networks/bitcoin/src/wallet/mod.rs:122-134`)

There is no re-derivation of `p2tr_script_buf(key + offset*G)` against `output.script_pubkey`, and no linkage of the outpoint to any actual transaction. Any producer of the byte stream can fabricate arbitrary "received" outputs with arbitrary values — exactly the trust violation class of the reference CVE, where bytes obtained over an unauthenticated channel are consumed as authoritative.

The inconsistency is only caught much later: `SignableTransaction::multisig` rejects inputs where `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey` (`networks/bitcoin/src/wallet/send.rs:276-279`). So the forged outputs sit in the wallet's received set, counted by `value()`, until a spend is attempted and silently fails with `None`.

### Impact Explanation
A caller that receives `ReceivedOutput` bytes over a channel (network sync, stored scan results, peer-supplied data — the insecure-mirror analog) will treat forged outputs as received funds. `ReceivedOutput::value()` reports the attacker-chosen `TxOut.value`, inflating reported balance with funds that are not spendable: the fabricated outpoint either doesn't exist, or exists paying a script the claimed `offset` does not unlock, so `SignableTransaction::multisig` returns `None` at signing time. This matches the accepted impact "funds reported received that are not spendable" — a direct availability/integrity failure on the wallet's accounting of its own UTXOs, reachable purely through untrusted bytes to `ReceivedOutput::read`.

### Likelihood Explanation
Any deployment that transports or persists `ReceivedOutput` blobs (the entire reason `read`/`write`/`serialize` exist) exposes this path to whoever controls that channel or store. The attacker needs no private key material and no protocol participation — only the ability to supply bytes. Concrete exploitation does require an integrator to consume serialized outputs from a source the attacker influences, which lowers likelihood relative to a purely on-chain primitive.

Severity assessment: **Medium** — reachable via untrusted input to a public API, causes phantom unspendable funds, but gated by integrator usage of the serialization path and caught (as an opaque `None`) at spend time.

### Recommendation
Have `ReceivedOutput::read` take the scanner key (or a `&Scanner`) and re-derive the expected `script_pubkey` for the claimed `offset` via `p2tr_script_buf(key + GENERATOR * offset)`, rejecting mismatches — mirroring the check already performed in `SignableTransaction::multisig`. Alternatively, bind serialized outputs to their producing transaction/block commitment so fabricated outpoints are detectable at ingest.

### Proof of Concept
```rust
// Given any Secp256k1 scalar `o` and an arbitrary TxOut (e.g. paying
// to a script the wallet does not control, value = 1 BTC) and a fake
// or unrelated OutPoint, serialize:
let mut bytes = o.to_bytes().to_vec();
bytes.extend(bitcoin::consensus::encode::serialize(&forged_txout));
bytes.extend(bitcoin::consensus::encode::serialize(&fake_outpoint));

// This succeeds with no validation:
let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 100_000_000); // phantom funds reported

// Yet spending is impossible:
// SignableTransaction::multisig returns None because
// p2tr_script_buf(keys.offset(o).group_key()) != forged_txout.script_pubkey
```
Contrast with `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:205-211`), which would never emit this output because the script isn't in `self.scripts` and the outpoint isn't bound to a real transaction.
