Based on the investigation, the closest verifiable local analog to the twTAP "reward-token-added-mid-flight causes a stuck cross-chain claim message and fund loss" pattern is in `IntentGatewayV2`'s cross-chain settlement path, specifically the `_withdraw` escrow-release routine that is invoked by an ISMP `onAccept` callback with a token list that is fixed inside the immutable, hashed `Order` struct.

### Title
Duplicate input-token entries in a cross-chain `Order` can make `_withdraw` deterministically revert, permanently locking source-chain escrow after the solver has already paid the user - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The external report's core broken invariant is: a multi-item settlement message is built from state that can diverge from the state actually present when the message is finally executed, and any mismatch causes the settlement handler to revert deterministically — permanently stranding funds because the revert cannot be avoided on retry. The closest structural analog in Hyperbridge's own cross-chain settlement code is `IntentsBase._withdraw`, called from `ExtrinsicIntents.onAccept` when a `RedeemEscrow`/`RefundEscrow` message lands on the source chain.

### Finding Description
`_withdraw` iterates `body.tokens` (which for cross-chain fills is set verbatim to `order.inputs`, see `ExtrinsicIntents.sol:140-147`) and, for each entry, reads and decrements `_orders[commitment][token]`: [1](#0-0) 

The only guard is `if (escrowed == 0) revert UnknownOrder();` — there is no check that `escrowed >= amount`, and the finalize flag (`_filled[body.commitment] = beneficiary`) is only set once, at the top of the function, so any revert inside the loop rolls back the *entire* `onAccept` call atomically, including the escrow bookkeeping decrement from any earlier-processed entry in the same call.

`order.inputs` is not constrained to have unique token addresses anywhere in `placeOrder`/`fillOrder`/`_fillCrossChain`. If an order is placed with two `TokenInfo` entries pointing at the same token address (a state an ordinary, unprivileged user fully controls when constructing and signing their own order), the `WithdrawalRequest.tokens` array carried in the `RedeemEscrow` message will contain that same duplicate. Depending on how the per-commitment escrow map was populated at placement, the second occurrence can end up transferring more than what remains recorded for that token, causing an underflow revert (Solidity 0.8 checked arithmetic) on `_orders[body.commitment][token] = escrowed - amount`. Because the whole call reverts atomically, the escrow storage is restored to its pre-call value on every retry, so the message will revert identically forever — an unrecoverable, deterministic failure exactly analogous to the twTAP `claimedAmount_.length` mismatch that permanently stalls the LayerZero message.

### Impact Explanation
On the destination chain, `_fillCrossChain` has already paid the solver's output tokens to the beneficiary and marked `_filled[commitment] = solver` *before* dispatching `RedeemEscrow` (`ExtrinsicIntents.sol:92, 137-162`). If the corresponding `onAccept` on the source chain reverts forever, the solver never receives the escrowed input tokens they were promised, and the user's original escrow (`_orders[commitment][...]`) remains locked in the source-chain contract indefinitely. Worse, `cancelOrder` from the source chain queries the destination's `_filled[commitment]` via a GET request (`ExtrinsicIntents.sol:319-324`); since the destination already recorded the fill, `onGetResponse` will always see a non-empty slot and revert with `Filled()`, permanently blocking the user's own refund path too. The result is unauthorized fund lock (loss) for both the solver (uncompensated) and the user (un-refundable escrow) — squarely inside the bounty's "loss of funds" and "false state acceptance/stuck settlement" categories, and reachable by an ordinary user crafting their own order, no privileged or malicious-relayer/prover assumption required.

### Likelihood Explanation
Medium — it requires a user (or a buggy/careless order-construction client) to place a cross-chain order whose `inputs` array repeats the same token address, which nothing in `placeOrder` currently rejects. Whether this is exploitable in practice hinges on one detail I could not fully confirm from the available index: whether `placeOrder`'s escrow bookkeeping accumulates (`+=`) or overwrites (`=`) `_orders[commitment][token]` for repeated token entries. If it accumulates correctly, the two duplicate entries' amounts sum cleanly and the underflow does not trigger; if it does not, the shortfall/underflow-revert scenario above applies directly. This ambiguity should be resolved by inspecting the exact escrow-write line in `IntentGatewayV2.sol`'s `placeOrder`, which the current investigation could not conclusively retrieve.

### Recommendation
- Reject orders whose `inputs` (and `output.assets`) contain duplicate token addresses in `placeOrder`, at order-construction time, so the invariant "one entry per token" is enforced before any cross-chain commitment is made.
- In `_withdraw`, clamp/validate `amount <= escrowed` explicitly (rather than relying on the underflow revert) and consider processing per-token withdrawal by aggregating duplicate entries first, so a malformed or adversarial token list cannot cause a permanently non-retriable revert.
- Ensure `onAccept`/`_withdraw` failures on incoming settlement messages do not leave the paired destination-chain state (`_filled`) in a way that also blocks the user's independent cancellation/refund path, e.g. by decoupling "solver already paid" from "user cannot recover escrow if settlement fails."

### Proof of Concept
1. Attacker (an ordinary user) constructs and signs a cross-chain `Order` where `order.inputs = [ {token: T, amount: A1}, {token: T, amount: A2} ]` (same token `T` twice) and destination on another chain.
2. Calls `placeOrder`, escrowing `A1 + A2` of token `T` under commitment `C`.
3. A solver fills the order via `fillOrder` → `_fillCrossChain` on the destination chain: pays output to the user, sets `_filled[C] = solver`, dispatches `RedeemEscrow{ commitment: C, tokens: order.inputs (still duplicated) }` back to the source chain (`ExtrinsicIntents.sol:89-171`).
4. When the message is delivered, `onAccept` → `_withdraw` processes the two duplicate `T` entries against `_orders[C][T]`. If the escrow bookkeeping does not correctly reflect the sum for the duplicate key (or the second entry's `amount` exceeds what remains after the first decrement), the second iteration underflows and reverts the entire `onAccept` call.
5. Because the revert is atomic, `_orders[C][T]` is restored on every retry — the message can never be delivered successfully. The solver's paid-out destination assets are never compensated, and the user's escrow on the source chain is permanently stuck (and `cancelOrder` is separately blocked because the destination already shows `_filled[C] != 0`).

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
