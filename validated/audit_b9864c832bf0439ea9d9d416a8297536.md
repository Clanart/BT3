### Title
Symlink-following arbitrary file read in `getWorkingDirectoryImage` bypasses working-tree containment - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage` builds the file path to read with a plain `Path.join(repository.path, file.path)` and passes it straight to `fs.readFile`. It performs no `lstat`/real-path check and no verification that the resolved path stays inside `repository.path`. Because Node's `fs.readFile` follows symbolic links by default, a symlink checked into a cloned repository (a POSIX symlink object, mode `120000`, which `git checkout` materializes on disk without any elevated privileges on macOS/Linux) can point outside the repository root. When that symlinked path is treated as an image diff, Desktop reads and base64-encodes the symlink target's contents and hands them to the renderer as a `data:` URI.

### Finding Description
`getWorkingDirectoryImage` is the “current” image loader used when Desktop renders an image diff for a working-directory change: [1](#0-0) 

The `file.path` value comes from git's own status/diff output for the cloned repository and is attacker-controlled content (the attacker fully controls what is committed and checked out in the repository being reviewed). No canonicalization (`fs.realpath`) or containment check (`resolvedPath.startsWith(repository.path)`) is performed before the `readFile` call, unlike the path-safety helpers that exist elsewhere in the codebase (e.g. `app/src/lib/path.ts`), which are simply not used here.

The call site that triggers this is `getImageDiff`, which only checks the file status kind and the extension (`.png`, `.jpg`, etc. via `imageFileExtensions`) before invoking `getWorkingDirectoryImage`: [2](#0-1) [3](#0-2) 

Nothing here distinguishes a regular file from a symlink with an image-like name; `git diff --numstat`/binary detection simply reports the path as changed/binary, and `Path.extname(file.path)` is derived purely from the attacker-chosen filename, not from the actual target.

The resulting bytes are surfaced to the renderer as a base64 `data:` URI and set directly into React component state/DOM by `ImageContainer`, then rendered by `TwoUp`/`ModifiedImageDiff`: [4](#0-3) [5](#0-4) 

So the exact wrong value is: `Path.join(repository.path, file.path)` is used as the *effective* file identity for both extension-derived media type and for the `readFile` open call, while the *actual* filesystem object opened by `readFile` (after the OS resolves the symlink) can be any path reachable by the OS user, entirely outside `repository.path`.

### Impact Explanation
This lets a malicious repository, once cloned, cause Desktop to read arbitrary files reachable by the logged-in user's file permissions (e.g. SSH keys, other project source, config files) and load their bytes into the renderer process as a base64 string, bypassing the intended "confined to working tree" model for diff rendering. That matches the "file read outside the repo" impact category, since the untrusted repository (not the user) chooses which file is opened.

### Likelihood Explanation
Requires only: (1) attacker publishes/points the victim to a repository containing a symlink object named with an image extension pointing to `../../../<sensitive file>` or an absolute path outside the repo, and (2) the victim clones it and opens the Changes/History diff view for that path in Desktop. On macOS/Linux, `git checkout` creates a real filesystem symlink for such an entry without any elevated privilege, so the checkout step alone (which Desktop performs automatically on clone/fetch of tracked changes) is sufficient to plant the link; no unnatural additional user action beyond normal "clone and view diff" is needed. (On Windows, `core.symlinks` normally requires Developer Mode or the `SeCreateSymbolicLinkPrivilege`, so this path is primarily exploitable on macOS/Linux by default — this OS-dependent nuance could not be fully re-verified against Desktop's own symlink-handling code such as `app/src/lib/path.ts` in the time available, and should be checked further.)

### Recommendation
Before calling `readFile` in `getWorkingDirectoryImage`, resolve the target with `fs.realpath`/`fs.lstat` and verify the resolved path is still contained within `repository.path` (or refuse to render/treat as binary/unsupported when the entry is a symlink at all, consistent with how git treats symlink blobs). Apply the same containment check anywhere else `file.path` is joined with `repository.path` and handed to filesystem APIs that follow symlinks.

### Proof of Concept
1. Create a repository containing a symlink committed as `evil.png -> ../../outside/secret.bin` (or an absolute path outside the intended clone directory), e.g. `ln -s /etc/passwd evil.png && git add evil.png && git commit`.
2. Clone this repository with GitHub Desktop on macOS/Linux; git checkout creates a real symlink at `evil.png`.
3. Modify `evil.png`'s target file (or just have the target differ from `HEAD`) so Desktop shows it as a working-directory change; select it in Changes.
4. Desktop calls `getWorkingDirectoryDiff` → `convertDiff` → `getImageDiff` → `getWorkingDirectoryImage(repository, file)` at [6](#0-5) , which resolves `Path.join(repository.path, 'evil.png')` and calls `readFile` on it; the OS follows the symlink and returns the contents of the outside-the-repo target instead of failing.
5. The bytes are base64-encoded and passed into `ImageContainer`/`TwoUp`, confirming the outside-tree content reached the renderer (`app/src/ui/diff/image-diffs/image-container.tsx:42`).

```typescript
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
```
