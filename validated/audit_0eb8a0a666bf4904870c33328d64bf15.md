## Title
Argument injection via unsanitized fork clone URL in `git remote add` — ([File: app/src/lib/git/remote.ts])

### Summary
The report's core issue is that a security-relevant identifier (`_chainId`) was trusted from an external/deployer-controlled source instead of being validated/derived safely, and was passed directly into a sensitive operation without a domain-separation guard. The equivalent broken-invariant class in GitHub Desktop is: a remote URL originating from an untrusted, attacker-influenced source (a pull request's fork `clone_url`, retrieved via a "Open in Desktop" deep link) is passed into `git remote add` without the `--` positional-argument separator that Desktop's own `clone()` function uses as a "backstop against ... crafted URL" attacks.

### Finding Description
`addRemote` in `app/src/lib/git/remote.ts` builds the git invocation as: [1](#0-0) 
Note there is no `--` separator between flags and positional arguments, unlike `clone()`: [2](#0-1) 
which explicitly comments that the `--` guard is a "backstop against path traversal attacks where a crafted URL tricks the UI into deriving a clone path outside the intended base directory" — the same defensive pattern is simply missing from `addRemote`.

`addRemote` is invoked with a `headCloneUrl` value that traces back to an attacker-reachable path: the deep-link handler `x-github-client://openRepo/...?pr=NNN` parsed by `parseAppURL` produces an `IOpenRepositoryFromURLAction` with a `pr` field [3](#0-2) 
which `dispatcher.openPullRequestFromUrl` uses to fetch a pull request object and then calls `_checkoutPullRequest` with `pullRequest.head.repo.clone_url`: [4](#0-3) 
That value flows into `_findPullRequestBranch`, which calls `addRemote(repository, forkRemoteName, headCloneUrl)` when no existing remote matches: [5](#0-4) 
and later `_fetchRemote` is invoked on that same remote: [6](#0-5) 

The `head.repo` object in a pull request payload describes the **fork** — a repository that is, by definition, owned/controllable by whoever opened the PR. An attacker who can open a PR (or who controls a GitHub Enterprise-style API server the victim is signed into) chooses their own fork's identity, and — depending on how strictly the API server validates repository/clone-URL fields — this value reaches `git remote add <name> <url>` without the `--` separator that the codebase itself designates as its injection guard elsewhere.

### Impact Explanation
If `headCloneUrl` can be made to start with a `-` (an option-like string) rather than a well-formed `https://`/`git@` URL, `git remote add` would interpret it as a flag instead of a URL argument, which can be leveraged to inject additional git options (e.g. altering remote config, fetch behavior, or in more constrained cases pointing the operation at attacker-controlled config through `-c`-style tricks) — silently corrupting the local repository's remote configuration and the subsequent fetch that Desktop performs automatically as part of "Open PR from Desktop." This matches the requested impact class of "silent corruption of what the user commits or pushes / fetches" since the corrupted remote is fetched automatically without further prompting: `_fetchRemote` runs right after `addRemote`.

### Likelihood Explanation
The likelihood is constrained by two facts I could not fully verify with the available tooling: (1) GitHub.com validates repository owner/name syntax tightly, making it unlikely `clone_url` for a github.com-hosted fork could ever begin with `-`; (2) `parseRemote`/`parseRepositoryIdentifier` (used elsewhere, e.g. in `clone-repository.tsx`) constrain what strings are treated as valid remote URLs before other operations — but I did not find equivalent validation applied to `headCloneUrl` before it reaches `addRemote` in `_findPullRequestBranch`. For a compromised or malicious GitHub Enterprise Server endpoint (which Desktop trusts once the user has signed in), the API is fully attacker-controlled and this constraint would not apply. This is a plausible but not confirmed-exploitable path given index limitations; a full assessment (e.g., of GHE API validation) would need a live investigation.

### Recommendation
Add the `--` separator to `addRemote` (and any other `git remote add`/`set-url` calls that consume API- or deep-link-derived URLs) exactly as already done in `clone()`:
```ts
await git(['remote', 'add', '--', name, url], repository.path, 'addRemote')
```
Additionally, validate `headCloneUrl` (and `fork.clone_url`, `parent.cloneURL`) with `parseRemote`/`parseRepositoryIdentifier` before use, rejecting values that don't parse as well-formed git remote URLs, consistent with the guard pattern GitHub Desktop already applies in `clone.ts`.

### Proof of Concept
Not independently verified end-to-end (would require confirming whether a GitHub Enterprise Server API response's `head.repo.clone_url` field can be forced to begin with `-` and reach `_findPullRequestBranch`); the concrete, verifiable defect is the structural one: `addRemote`'s git invocation omits the `--` separator that the same codebase treats as mandatory in `clone()` for identical untrusted-URL-into-git-argv concerns.
