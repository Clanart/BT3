### Title
Arbitrary file read via symlinked working-directory file in diff/image preview - (File: `app/src/lib/git/diff.ts`)

### Summary
GitHub Desktop reads the content of a working-directory file directly from disk by joining the repository root with the git-reported file path, then calls Node's `readFile`, which transparently follows symlinks. Unlike `app/src/lib/copilot-conflict-context.ts`, which explicitly guards conflict-file reads with `resolveWithin` to reject "path traversal and symlink escapes," the diff-rendering and syntax-highlighting code paths that back the Changes/Diff UI perform no such check. A cloned or fetched repository can contain a symlink (a git blob with mode `120000`, or an untracked symlink written by a build step) whose target points outside the repository (e.g. `~/.ssh/id_rsa`, a browser profile, or an OS credential file). When the user simply views that file in the Changes list, Desktop follows the symlink and loads the target file's bytes into the renderer, displaying them as an "image" or as syntax-highlighted text.

### Finding Description
`getWorkingDirectoryImage` reads the file with no root-containment check: [1](#0-0) 

`getResolutionDiff` similarly reads the on-disk "working-tree" content directly via `Path.join(repository.path, filePath)` and `readFile`, with no symlink/traversal guard: [2](#0-1) 

The syntax-highlighting code path used to render the Changes diff pane does the same for untracked/modified working-directory files: [3](#0-2) 

By contrast, the codebase already recognizes this exact class of bug and has a fix pattern for it: `resolveWithin` in `app/src/lib/path.ts` resolves both the root and the candidate path with `fs.realpath` and rejects the result if it escapes the root, and its own test suite explicitly covers "fails for paths that use a symlink to traverse outside of the root": [4](#0-3) [5](#0-4) 

`buildConflictContext` uses this guard for conflict files: [6](#0-5) 

but the equivalent diff/image/highlighting readers do not call `resolveWithin` (or `lstat` to detect a symlink) before reading — they trust `file.path` as reported by `git status`/diff parsing and simply join it onto `repository.path`.

### Impact Explanation
An attacker who controls the content of a cloned/fetched repository (a very low bar — any public repo a victim clones, or a repo the victim is a collaborator on) can commit a symlink pointing at a sensitive absolute path on the victim's machine (SSH keys, cloud credential files, other repos' `.git/config` with tokens, etc.), possibly with an image-like extension to route through `getWorkingDirectoryImage`. As soon as the victim opens that repository in Desktop and clicks the file in the Changes/History diff view (an entirely ordinary workflow, not a special social-engineering step), the target file's raw bytes are read into the renderer process and displayed (as an "image" or as highlighted source), giving the attacker a way to exfiltrate the confirmation of content indirectly (e.g., via screenshot, copy, or a secondary channel) or, more importantly, to have secret file bytes loaded into the Electron renderer's memory/DOM. This matches the "attacker controls a cloned/fetched repository ... result is file read outside the repo" valid-impact category.

### Likelihood Explanation
Git supports symlink blobs (mode `120000`) cross-platform in the object database; on macOS/Linux the working tree materializes them as real filesystem symlinks (Windows requires special git config, but is still commonly enabled by developer tooling). No special privileges, no local access, and no additional social engineering beyond "open the repo and view the file in Changes" are required, which is a core, expected Desktop interaction. The existing `resolveWithin`/symlink-escape guard being present in one code path (`copilot-conflict-context.ts`) but absent from the older/more central diff and highlighting paths indicates this is a real gap rather than a defended surface.

### Recommendation
Route every working-directory file read that occurs during diff/image rendering and syntax highlighting through `resolveWithin` (as already done in `copilot-conflict-context.ts`), rejecting or flagging any path whose `realpath` escapes `repository.path`. Additionally, `lstat` the target path before treating a working-directory entry as a plain file for image/text rendering, and refuse to follow symlinks (or explicitly display them as "symlink" entries) instead of dereferencing them for content display.

### Proof of Concept
1. Attacker prepares a repo containing a symlink blob: `ln -s /home/victim/.ssh/id_rsa fake.png` and commits it (`git add -A && git commit`), or leaves it untracked.
2. Victim clones this repository with GitHub Desktop and opens the Changes (or Commit history diff) view.
3. Victim clicks `fake.png` in the file list.
4. Desktop calls `getWorkingDirectoryImage`/`getFileContents`, which does `readFile(Path.join(repository.path, 'fake.png'))`; because the OS resolves the symlink, the actual bytes of `/home/victim/.ssh/id_rsa` are read and rendered as an "image"/highlighted text in the diff pane, exposing the private key content to anything that can see the rendered UI (screen sharing, screenshot, or a companion exfiltration bug). export async function getWorkingDirectoryImage(
```typescript
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
```

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
