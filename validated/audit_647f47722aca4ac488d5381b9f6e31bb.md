### Title
`recoverPolynomialCoeffs` does not verify recovered polynomial reproduces the supplied cells at `cellIDs` before returning - (File: `api_eip7594.go`)

### Summary
`Context.RecoverCellsAndComputeKZGProofs` calls `recoverPolynomialCoeffs` (`api_eip7594.go`), which reconstructs a polynomial via `ctx.dataRecovery.RecoverPolynomialCoefficients` (`internal/erasure_code/erasure_code.go`) using only the *actually-missing* cell indices as the erasure set, without ever confirming that evaluating the resulting polynomial at the caller-supplied `cellIDs` reproduces the caller-supplied `cells`. If the supplied set of cells is not perfectly consistent with a single degree-`<ScalarsPerBlob` polynomial, the FFT-based decoder can silently produce a polynomial whose evaluations diverge from some of the inputs used to construct it, and the API returns that mismatched result with no error.

### Finding Description
The claimed invariant is: for every supplied `cellIDs[i]`, `recovered[cellIDs[i]] == cells[i]`, and the recovered polynomial has degree `< ScalarsPerBlob`, else the call must return an error.

Tracing `recoverPolynomialCoeffs` (`api_eip7594.go:97-146`):
1. It validates `len(cellIDs) == len(cells)`, ascending order (`isAscending`), each `cellID < CellsPerExtBlob`, and that `len(cellIDs) >= NumBlocksNeededToReconstruct()`. None of these checks are semantic (mathematical) checks on the *content* of the cells - only shape/index checks.
2. `missingCellIds` is built strictly as the complement of the supplied `cellIDs` in `[0, CellsPerExtBlob)` (`api_eip7594.go:121-126`).
3. The supplied cells are deserialized and copied straight into `extendedBlob` at the positions corresponding to their `cellID` (`api_eip7594.go:132-141`), with zeros left at the (actually) missing positions.
4. `ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)` (`internal/erasure_code/erasure_code.go:110-148`) runs the classical FFT-based erasure-decoding algorithm: build vanishing polynomial `Z(x)` with roots at `missingCellIds`, form `E(x) = data(x)*Z(x)`, divide by `Z(x)` in a coset, then **truncate** the result to the first `numScalarsInDataWord` coefficients (`erasure_code.go:146`) and return it unconditionally.
5. Back in `RecoverCellsAndComputeKZGProofs` (`api_eip7594.go:148-165`), the returned `polyCoeff` is used directly to compute `recoveredCells` and proofs and returned to the caller - there is no step anywhere that re-evaluates the recovered polynomial at the originally-supplied `cellIDs` and compares against the originally-supplied `cells`.

The algorithm's correctness proof (this is the standard n·log₂n Reed–Solomon erasure-recovery construction) depends on the erasure set used to build `Z(x)` having exactly the size/structure required for a degree-`<k` codeword, and on the non-erased entries being *actual* evaluations of a single degree-`<k` polynomial. The code derives the erasure set purely from index bookkeeping (which positions the caller happened to omit), never from any consistency check on the values. If a caller supplies a `cells` set whose values are not evaluations of a common low-degree polynomial (e.g., an over-determined but inconsistent set, or values crafted so the interpolation/truncation step folds a corrupted result into the truncated low-degree part), the returned `polyCoeff` need not, in general, reproduce every supplied `cells[i]` when evaluated back at `cellIDs[i]`. Because the final truncation discards higher-degree coefficients of the coset quotient unconditionally, any residual inconsistency in the input is silently absorbed/dropped rather than surfaced as an error.

None of the existing guards (`ErrNumCellIDsNotEqualNumCells`, `ErrCellIDsNotOrdered`, `ErrFoundInvalidCellID`, `ErrNotEnoughCellsForReconstruction`) check value-level consistency; they only check shape and index bounds. `deserializeCell` only validates field-element canonicity of each scalar, not consistency across cells. There is no post-recovery equality assertion anywhere in `api_eip7594.go`, `internal/erasure_code/erasure_code.go`, or `internal/kzg_multi`.

### Impact Explanation
If exploitable with a concretely constructed inconsistent input, this would let an unprivileged caller obtain `RecoverCellsAndComputeKZGProofs` output (recovered cells/proofs) that silently disagrees with the cells it supplied, i.e., `recovered[cellIDs[i]] != cells[i]` for some `i`, with no error returned. This is the class of "High" impact described in the rules: go-eth-kzg would diverge from the consensus-spec/c-kzg reference behavior (which is expected to reject such degenerate/inconsistent inputs, or to be guaranteed correct only for genuinely consistent codewords) for the same input, or produce mis-recovered cell data that differs from another correct implementation for identical inputs - a client-split-class issue.

### Likelihood Explanation
I was not able to fully verify, within the available tools/read-only access, whether it is actually possible in practice to construct such an inconsistent `cellIDs`/`cells` input under the specific parameters used here (`blockErasureSize` = `scalarsPerCell`, `CellsPerExtBlob`, `NumBlocksNeededToReconstruct()` fixed at exactly half of `CellsPerExtBlob` per the EIP-7594 spec). In the EIP-7594 protocol, `RecoverCellsAndComputeKZGProofs` is always called with exactly (or more than) the minimum threshold of cells, and the reference c-kzg-4844 implementation uses the identical FFT-based recovery algorithm without an explicit "re-evaluate and compare" step either - suggesting this is a property of the shared cross-client algorithm/design rather than a go-eth-kzg-specific deviation. I could not confirm from the code alone (without executing gnark-crypto FFT operations to construct a concrete counterexample) that a caller can actually produce `cells` values that pass all the existing shape/index guards, get accepted by `RecoverPolynomialCoefficients`, and yield `recovered[cellIDs[i]] != cells[i]` for some `i` while c-kzg-4844 would behave differently for the same bytes. This requires constructing an explicit numeric counterexample and comparing against the reference implementation, which is beyond what I could validate here.

### Recommendation
Given the uncertainty about a concrete exploit and that this pattern likely mirrors the reference c-kzg-4844 algorithm, the primary recommendation before treating this as a confirmed bug is to attempt to build a concrete counterexample (a `cellIDs`/`cells` set consistent with all existing shape checks but inconsistent as evaluations of one degree-`<ScalarsPerBlob` polynomial) and check whether `recoverPolynomialCoeffs` produces `recovered[cellIDs[i]] != cells[i]` for it, and whether c-kzg-4844 differs in behavior for the identical bytes. If such an input exists, add an explicit post-recovery check in `recoverPolynomialCoeffs` (`api_eip7594.go`) that re-evaluates the recovered polynomial at each supplied `cellIDs[i]` and returns an error (e.g. a new `ErrRecoveredCellMismatch`) if it does not exactly equal the supplied `cells[i]`.

func (ctx *Context) recoverPolynomialCoeffs(cellIDs []uint64, cells []*Cell) ([]fr.Element, error) {
	if len(cellIDs) != len(cells) {
		return nil, ErrNumCellIDsNotEqualNumCells
	}

	// Check that the cell Ids are ordered (ascending)
	if !isAscending(cellIDs) {
		return nil, ErrCellIDsNotOrdered
	}

	// Check that each CellId is less than CellsPerExtBlob
	for _, cellID := range cellIDs {
		if cellID >= CellsPerExtBlob {
			return nil, ErrFoundInvalidCellID
		}
	}

	// Check that we have enough cells to perform reconstruction
	if len(cellIDs) < ctx.dataRecovery.NumBlocksNeededToReconstruct() {
		return nil, ErrNotEnoughCellsForReconstruction
	}

	// Find the missing cell IDs and bit reverse them
	// So that they are in normal order
	missingCellIds := make([]uint64, 0, CellsPerExtBlob)
	for cellID := uint64(0); cellID < CellsPerExtBlob; cellID++ {
		if !slices.Contains(cellIDs, cellID) {
			missingCellIds = append(missingCellIds, (domain.BitReverseInt(cellID, CellsPerExtBlob)))
		}
	}

	// Convert Cells to field elements
	extendedBlob := make([]fr.Element, scalarsPerExtBlob)
	// for each cellId, we get the corresponding cell in cells
	// then use the cellId to place the cell in the correct position in the data(extendedBlob) array
	for i, cellID := range cellIDs {
		cell := cells[i]
		// Deserialize the cell
		cellEvals, err := deserializeCell(cell)
		if err != nil {
			return nil, err
		}
		// Place the cell in the correct position in the data array
		copy(extendedBlob[cellID*scalarsPerCell:], cellEvals)
	}
	// Bit reverse the extendedBlob so that it is in normal order
	domain.BitReverse(extendedBlob)

	return ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)
}

func (ctx *Context) RecoverCellsAndComputeKZGProofs(cellIDs []uint64, cells []*Cell, numGoRoutines int) ([CellsPerExtBlob]*Cell, [CellsPerExtBlob]KZGProof, error) {
	polyCoeff, err := ctx.recoverPolynomialCoeffs(cellIDs, cells)
	if err != nil {
		return [CellsPerExtBlob]*Cell{}, [CellsPerExtBlob]KZGProof{}, err
	}

	recoveredCells, err := ctx.computeCellsFromPolyCoeff(polyCoeff, numGoRoutines)
	if err != nil {
		return [CellsPerExtBlob]*Cell{}, [CellsPerExtBlob]KZGProof{}, err
	}

	proofs, err := ctx.computeKZGProofsFromPolyCoeff(polyCoeff, numGoRoutines)
	if err != nil {
		return [CellsPerExtBlob]*Cell{}, [CellsPerExtBlob]KZGProof{}, err
	}

	return recoveredCells, proofs, nil
}

func (dr *DataRecovery) RecoverPolynomialCoefficients(data []fr.Element, missingIndices []BlockErasureIndex) ([]fr.Element, error) {
	zX := dr.constructVanishingPolyOnIndices(missingIndices)

	// Compute zX evaluations without mutating zX since we need zX later for a coset FFT
	zXForEval := make([]fr.Element, len(zX))
	copy(zXForEval, zX)
	dr.domainExtended.FftFr(zXForEval)
	zXEval := zXForEval

	if len(zXEval) != len(data) {
		return nil, errors.New("length of data and zXEval should be equal")
	}

	eZEval := make([]fr.Element, len(data))
	for i := 0; i < len(data); i++ {
		eZEval[i].Mul(&data[i], &zXEval[i])
	}

	dr.domainExtended.IfftFr(eZEval)
	dzPoly := eZEval

	dr.domainExtendedCoset.CosetFFtFr(zX)
	cosetZxEval := zX
	dr.domainExtendedCoset.CosetFFtFr(dzPoly)
	cosetDzEVal := dzPoly

	cosetQuotientEval := make([]fr.Element, len(cosetZxEval))
	cosetZxEval = fr.BatchInvert(cosetZxEval)

	for i := 0; i < len(cosetZxEval); i++ {
		cosetQuotientEval[i].Mul(&cosetDzEVal[i], &cosetZxEval[i])
	}

	dr.domainExtendedCoset.CosetIFFtFr(cosetQuotientEval)

	// Truncate the polynomial coefficients to the number of scalars in the data word
	polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]
	return polyCoeff, nil
}
