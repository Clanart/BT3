## Analysis

The external report's broken invariant is: *a function that is supposed to enforce/perform a safety-critical step (staking into the boosted-position contract) silently fails to do so, while downstream code (`claimBoostedPositionRewards`) proceeds as if the invariant held.* The closest structural analog in GitHub Desktop is a boundary-check function that is *called* as if it guarantees "this path stays inside the repository," but its implementation has a logic gap that lets attacker-influenced paths pass the check while actually landing outside the repo — and the caller (a file-write flow) proceeds to write attacker-controlled content there without any further validation.

### Title
Missing path-separator boundary check in `resolveWithin` allows Copilot-driven conflict-resolution writes to escape the repository - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin`/`_resolveWithin` is the sole guard used throughout Desktop to ensure that a path derived from external/attacker-influenced data (conflicted file paths, AI-generated conflict resolutions, deep-link file paths) stays inside a given repository root before it is read from or written to. Its containment check uses `String.prototype.startsWith` without appending a path separator, so a sibling path whose name merely shares the root directory's name as a prefix (e.g. root `/Users/victim/repo` vs. target `/Users/victim/repo-secrets/notes.txt`) incorrectly passes the "inside repo" check. [1](#0-0) 

### Finding Description
`_resolveWithin` computes `realRoot` and `realResolved` via `realpath` and then does:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a classic prefix-match containment bug (CWE-22 variant): it never checks that `realResolved` continues with a path separator (or equals `realRoot` exactly) after the shared prefix. Any path that resolves to a sibling of the intended root whose name begins with the root's name will be treated as "within" the root. [2](#0-1) 

This helper is the guard used by `_applyCopilotConflictResolutions`, which writes AI-suggested conflict resolution content to disk during a merge/rebase and then stages it for commit: [3](#0-2) 

The write path itself relies entirely on `resolveWithin` for safety before calling `writeFile`: [4](#0-3) 

The `resolution.path` values written here originate from Copilot's structured resolution output, which is generated from the *conflicted file content* the attacker controls (a merge/rebase conflict introduced by a crafted, cloned/fetched repository or branch). Because the file content — including any adversarial "resolution" the model is coaxed to emit — is attacker-supplied, `resolution.path` is an attacker-influenced value that only `resolveWithin` stands between it and an arbitrary sibling location.

The same broken primitive is also used to sanitize the `filepath` parameter of the `x-github-client://openRepo` deep link before calling `shell.showItemInFolder`, so the same prefix-bypass affects that attacker-clicked-link surface as well: [5](#0-4) 

and it is also relied upon when reading conflicted file contents to build the Copilot request context: [6](#0-5) 

### Impact Explanation
If the boundary check is bypassed, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` writes attacker-influenced content to a file *outside* the actual repository, guarded only by this flawed prefix check — a direct instance of "file write... outside the repo" and "silent corruption of what the user commits/pushes," since the write happens automatically as part of the normal "Continue Merge" flow and the affected path is then `git add`-ed alongside the legitimate resolutions. The deep-link variant enables `shell.showItemInFolder` to reveal/read a file outside the intended repository directory in response to a link click, matching the "attacker controls a link... deep link the user clicks" primitive.

### Likelihood Explanation
Exploitation requires: (1) a maliciously crafted repository/branch that produces a merge/rebase conflict whose content is engineered (prompt injection) to make the Copilot resolution step return a `path` value targeting a sibling location sharing the repository directory's name prefix, and (2) that sibling path/file already existing on the victim's filesystem (since `resolveWithin` calls `realpath` on the resolved target, which requires it to already exist). This narrows practical exploitation but does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim open/clone the attacker's repository and use the "Resolve with Copilot" feature, or click a crafted deep link. The existing "guard" (`resolveWithin`) is exactly the mechanism the maintainers rely on to prevent this class of issue, and it does not actually stop the path because of the missing separator check.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to require an exact match or a boundary at a path separator, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests covering sibling-directory-with-shared-prefix cases (e.g. root `/tmp/repo` vs. `/tmp/repo-evil`) for both POSIX and Win32 variants, alongside the existing `resolveWithin` test suite.

### Proof of Concept
1. Victim clones an attacker-controlled repository named e.g. `demo` to `~/Documents/GitHub/demo`. A pre-existing sibling directory `~/Documents/GitHub/demo-secrets/token.txt` exists on the victim's machine (e.g., from an unrelated prior clone/project).
2. Attacker crafts a branch/commit that creates a merge/rebase conflict whose content contains a prompt-injection payload designed to make the Copilot conflict-resolution model emit a resolution object with `path: "../demo-secrets/token.txt"` and attacker-chosen `resolvedContent`.
3. Victim triggers "Resolve with Copilot" and clicks "Continue Merge" (`app/src/ui/dispatcher/dispatcher.ts` → `app/src/lib/stores/app-store.ts:_applyCopilotConflictResolutions`).
4. `resolveWithin(repository.path, "../demo-secrets/token.txt")` resolves to `~/Documents/GitHub/demo-secrets/token.txt`; `realRoot` = `.../demo` and `realResolved` = `.../demo-secrets/token.txt`, and `realResolved.startsWith(realRoot)` returns `true` due to the missing separator check, so the path is treated as valid.
5. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` overwrites `token.txt` outside the `demo` repository with attacker-chosen content [7](#0-6) .

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
