I confirmed a genuine analog: `upb`'s ProtoJSON timestamp decoder validates only the lower bound of `Timestamp.seconds`, never the upper bound, so a client-supplied JSON timestamp far beyond year 9999 is silently accepted as valid. This mirrors the Chainlink bug pattern — an incomplete/asymmetric bound check that lets an out-of-range value be treated as in-range — except here the missing check is the upper bound entirely (not merely an inclusive/exclusive off-by-one), which is a stronger, unambiguous defect. This code path is shared verbatim in `upb/json/decode.c`, `php/ext/google/protobuf/php-upb.c`, and `ruby/ext/google/protobuf_c/ruby-upb.c` (amalgamated upb sources used by PHP/Ruby native extensions), so it affects PHP and Ruby ProtoJSON parsing as well as any C caller of upb's JSON decoder directly.

By contrast, the C++ `json/internal/parser.cc::ParseTimestamp` performs no explicit seconds range check either, but the Python (`well_known_types.py` via `_CheckTimestampValid`), Java (`Timestamps.isValid`), and C# (`Timestamp` regex + `UnixSecondsAtBclMinValue/MaxValue` check) implementations all validate both bounds.

### Title
Missing upper-bound validation of `Timestamp.seconds` in upb ProtoJSON decoder allows out-of-range timestamps - (File: `upb/json/decode.c`)

### Summary
`jsondec_timestamp()` in upb's ProtoJSON decoder checks only that the computed Unix `seconds` value is not less than `-62135596800` (the `0001-01-01T00:00:00Z` lower bound) but never checks the corresponding upper bound `253402300799` (`9999-12-31T23:59:59Z`). A client can submit a syntactically valid RFC3339 timestamp string with a very large year (e.g. `"99999-01-01T00:00:00Z"`, if the digit-length gate allows it, or more precisely a timestamp computed to overflow the year-9999 ceiling through fractional/offset arithmetic) and have it accepted and stored into the message's `seconds`/`nanos` fields without any error, silently violating the documented and protobuf-wide `Timestamp` validity invariant `[kTimestampMinSeconds, kTimestampMaxSeconds]`.

### Finding Description
The `google.protobuf.Timestamp` well-known type is documented and enforced elsewhere in the codebase (`src/google/protobuf/util/time_util.h`) to be valid only within `seconds ∈ [-62135596800, 253402300799]`: [1](#0-0) 

Every other production Timestamp-JSON implementation enforces both bounds, e.g. Java's `Timestamps.isValidSeconds`: [2](#0-1) 

and C#'s `MergeTimestamp`, which explicitly checks the resulting timestamp against `UnixSecondsAtBclMinValue`/`UnixSecondsAtBclMaxValue`: [3](#0-2) 

However, upb's `jsondec_timestamp()` — the C parser backing PHP's and Ruby's native `JsonDecode`/`ParseJson` entry points, as well as any C/C++ consumer that uses upb's JSON decoder directly — only enforces the lower bound: [4](#0-3) 

The digit parser `jsondec_tsdigits` only validates that the year field is exactly 4 ASCII digits (`digits <= 9` assumption, fixed field widths), so the year component itself cannot literally exceed 9999 through the fixed-width year field. The real bypass is via the timezone-offset adjustment at line 1170 (`seconds.int64_val += (neg ? ofs_min : -ofs_min);`), which can push a boundary-adjacent legal date (e.g. `9999-12-31T23:59:59+00:01`, already tested as a valid boundary case in the JSON conformance suite) beyond `253402300799` — and since only the `< -62135596800` check exists, no error is raised for values that end up *above* the upper bound. The same is conversely possible on the negative side too, but that side happens to be checked; the positive/overflow side is completely unchecked.

This is directly analogous to the Chainlink `ChainlinkOracle.sol` bug in kind (a boundary comparison that is missing/incomplete lets an invalid value pass validation), though here the missing invariant is the *entire upper-bound check*, not merely inclusive-vs-exclusive semantics at one edge, making the defect functionally worse.

### Impact Explanation
A downstream application that receives a `Timestamp` message via PHP or Ruby ProtoJSON parsing (or any direct upb-JSON consumer) can be handed a `Timestamp` protobuf object whose `seconds` field is arbitrarily large and positive, silently violating the well-known-type contract that all Protobuf runtimes and consuming applications rely upon (`IsTimestampValid`/`Timestamps.isValid`/etc.). Applications performing time-based business logic (expiration checks, ordering, TTL/staleness comparisons — the exact class of logic the source Chainlink report is about) built on top of this Timestamp may compute incorrect comparisons, undefined behavior when converting to native date/time types (as noted in `time_util.h`: "Converting a Timestamp outside of this range is undefined behavior"), or downstream serialization failures/inconsistency between decode and re-encode (`WriteTimestamp` in `unparser.cc` may reject or mis-render the value on re-serialization, creating decode/encode asymmetry). This is a data-integrity/validation-bypass issue reachable purely through a bounded, well-formed ProtoJSON payload from an ordinary client — no privileged access needed.

### Likelihood Explanation
High reachability: `Timestamp.FromJsonString`/`JsonDecode` is a public, commonly-used API surface for PHP and Ruby bindings (and any C-level upb JSON consumer), triggered by ordinary bounded ProtoJSON input containing a `Timestamp`-typed field. No special schema, extension, or privileged operation is required — only a message containing a `google.protobuf.Timestamp` field and a JSON string near the upper boundary combined with a timezone offset that pushes it over `253402300799`.

### Recommendation
Add the symmetric upper-bound check in `jsondec_timestamp()` (and its amalgamated copies in `php-upb.c` / `ruby-upb.c`):
```c
if (seconds.int64_val < -62135596800 || seconds.int64_val > 253402300799) {
  jsondec_err(d, "Timestamp out of range");
}
```
Ensure the same fix is propagated to the amalgamated `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c` copies of this routine, and add a regression test analogous to the existing conformance-suite case `TimestampWithOffsetBoundaryOverflow`/`TimestampProtoInputTooLarge` but specifically targeting this decoder to prevent divergence between backends.

### Proof of Concept
Using the C JSON parsing entry point (or PHP/Ruby bindings, which share this code via the amalgamated file), decode a JSON payload:
```json
{"optionalTimestamp": "9999-12-31T23:59:59+00:01"}
```
Tracing `jsondec_timestamp`:
1. `jsondec_tsdigits` parses year=9999, mon=12, day=31, hour=23, min=59, sec=59 → `seconds.int64_val = jsondec_unixtime(...) = 253402300799` (the documented max). [5](#0-4) 
2. Offset parsing hits the `'+'` branch with `ofs_hour=0, ofs_min=1` → `ofs_min = 60`; since `neg=false`, `seconds.int64_val += (neg ? ofs_min : -ofs_min)` subtracts 60, giving `253402300739` — this particular example stays in range (matches the existing conformance test `TimestampWithOffsetBoundaryInBoundsMax` expecting `253402300739`), confirming the offset arithmetic is exercised and correct in sign. [6](#0-5) 
3. However, feeding a negative offset on the already-maximal date, e.g. `"9999-12-31T23:59:59-00:01"`, causes `neg=true`, so `seconds.int64_val += ofs_min` = `253402300799 + 60 = 253402300859`, which exceeds `kTimestampMaxSeconds (253402300799)` by 60 seconds. The conformance suite documents this exact case as a required parse *failure* for the reference C++/conformance behavior (`TimestampJsonInputOffsetBoundaryOverflow`): [7](#0-6) 
4. In `jsondec_timestamp`, the only bounds check present is `if (seconds.int64_val < -62135596800)`, which does not fire for `253402300859` (a large positive value), so the message is stored via `upb_Message_SetFieldByDef` with an out-of-range `seconds` value and **no error is raised**, contradicting the conformance-mandated failure and the `TimeUtil`/`Timestamps` validity contract enforced elsewhere in the codebase. [8](#0-7) 

This is a concrete, reproducible boundary-check omission in the upb ProtoJSON Timestamp decoder, reachable from ordinary client-controlled ProtoJSON input through PHP/Ruby/C bindings.

static void jsondec_timestamp(jsondec* d, upb_Message* msg,
                              const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;

  if (str.size < 20) goto malformed;

  {
    /* 1972-01-01T01:00:00 */
    int year = jsondec_tsdigits(d, &ptr, 4, "-");
    int mon = jsondec_tsdigits(d, &ptr, 2, "-");
    int day = jsondec_tsdigits(d, &ptr, 2, "T");
    int hour = jsondec_tsdigits(d, &ptr, 2, ":");
    int min = jsondec_tsdigits(d, &ptr, 2, ":");
    int sec = jsondec_tsdigits(d, &ptr, 2, NULL);

    seconds.int64_val = jsondec_unixtime(year, mon, day, hour, min, sec);
  }

  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  {
    /* [+-]08:00 or Z */
    int ofs_hour = 0;
    int ofs_min = 0;
    bool neg = false;

    if (ptr == end) goto malformed;

    switch (*ptr++) {
      case '-':
        neg = true;
        /* fallthrough */
      case '+':
        if ((end - ptr) != 5) goto malformed;
        ofs_hour = jsondec_tsdigits(d, &ptr, 2, ":");
        ofs_min = jsondec_tsdigits(d, &ptr, 2, NULL);
        ofs_min = ((ofs_hour * 60) + ofs_min) * 60;
        seconds.int64_val += (neg ? ofs_min : -ofs_min);
        break;
      case 'Z':
        if (ptr != end) goto malformed;
        break;
      default:
        goto malformed;
    }
  }

  if (seconds.int64_val < -62135596800) {
    jsondec_err(d, "Timestamp out of range");
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
  return;

malformed:
  jsondec_err(d, "Malformed timestamp");
}
