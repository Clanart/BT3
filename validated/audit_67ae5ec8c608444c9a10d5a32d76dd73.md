## Title
Single stale/illegal oracle price for one enabled asset reverts the entire position valuation, freezing withdraw/borrow/repay/liquidation - (`File: mainnet/contracts/market/v0-4-market.clar`)

### Summary
`get-assets` resolves prices for every asset in a user's enabled collateral/debt bitmap by calling `price-multi-resolve`, and then unconditionally unwraps the result with `unwrap-panic`. `price-multi-resolve` folds over the asset list via `iter-price-multi`, and as soon as **any single asset's** `price-resolve` call fails (stale timestamp, non-positive price, or confidence check failure), the whole fold sets `valid: false` and the aggregate call returns `ERR-ORACLE-MULTI`. Because `get-assets` wraps this in `unwrap-panic`, that single bad asset causes the *entire* multi-asset valuation to abort, exactly like the referenced Frax bug where one bad element (`pubKey` already used) in a loop reverted the whole `depositEther()` call rather than being skipped.

### Finding Description
`get-assets` in `mainnet/contracts/market/v0-4-market.clar`: [1](#0-0) 

builds the list of asset oracle configs for the user's enabled mask and calls: [2](#0-1) 

`price-multi-resolve` folds `iter-price-multi` over every asset in the position. `iter-price-multi` propagates failure state (`valid: false`) once any single `price-resolve` call fails: [3](#0-2) 

`price-resolve` itself asserts both price legality and per-asset staleness/monotonicity, reverting with `ERR-ORACLE-INVARIANT` for any single feed that is stale, non-monotonic, or has price ≤ 0: [4](#0-3) 

Because `price-multi-resolve` asserts `(get valid response)` and `get-assets` wraps the whole call in `unwrap-panic`, a single mis-behaving oracle feed (e.g., stale beyond `max-staleness`, or a Pyth confidence-interval failure) for *one* asset in the user's collateral/debt set is enough to make `get-assets`—and therefore any downstream function that depends on it (`get-position`, `get-full-position`, `get-liquidation-position`, and the notional/health-check pipeline used by withdraw, borrow, repay, and liquidate)—unconditionally revert. This is structurally identical to the Frax `getNextValidator()`/`depositEther()` DoS: one bad element in a loop aborts the whole batch operation instead of being isolated or skipped.

### Impact Explanation
If any single enabled asset in a user's position has an oracle whose price becomes stale or fails validation (which can legitimately happen during oracle downtime, network congestion, or Pyth feed staleness, independent of any DAO misconfiguration), the user's entire position becomes unreadable: they cannot withdraw excess healthy collateral of *other* assets, cannot repay debt, and — more importantly — liquidators cannot liquidate the position even though the debt asset and collateral used for liquidation might have perfectly healthy price feeds, because `get-liquidation-position`/`get-assets` reverts for the whole mask rather than the single problematic asset. This matches "temporary freezing of funds" (unclaimed collateral/debt cannot be moved) until the stale feed is refreshed or the DAO manually disables/removes that asset from the user's enabled mask.

### Likelihood Explanation
This is triggerable by ordinary market conditions (an oracle simply going stale for one asset among several in a position) rather than requiring any attacker action or DAO misconfiguration — the same class of "benign-input causes total loop failure" that 0xean judged Medium severity in the Frax report. Any user who deposits multiple enabled collateral types, or any debt asset whose oracle staleness window is exceeded, can trigger this for themselves or, in the liquidation path, for their liquidators.

### Recommendation
Make per-asset oracle failures non-fatal to the aggregate operation: skip/short-circuit only the affected asset (e.g., exclude it from valuation with a safe fallback, or allow liquidation/withdraw of the unaffected assets) instead of using `unwrap-panic`/`asserts!`-based all-or-nothing failure in `price-multi-resolve`/`iter-price-multi`. At minimum, ensure the liquidation path does not depend on pricing of assets outside the ones being liquidated, so one stale feed elsewhere in the position cannot block liquidation of an otherwise-liquidatable position.

### Proof of Concept
1. User has two enabled collateral assets: Asset A (Pyth feed, `max-staleness` 60s) and Asset B (DIA feed, `max-staleness` 300s).
2. Pyth stops publishing updates for Asset A's feed for >60s (network delay, keeper downtime, etc.) while Asset B remains fresh.
3. User (or a liquidator) calls any function that computes the position value — e.g. `withdraw`/`liquidate`, which internally calls `get-assets`/`get-position` → `price-multi-resolve` → `iter-price-multi` → `price-resolve` for Asset A.
4. `price-resolve` for Asset A fails `oracle-timestamp-fresh` → returns `ERR-ORACLE-INVARIANT` (`mainnet/contracts/market/v0-4-market.clar:387-393`).
5. `iter-price-multi` marks the whole fold `valid: false`, causing `price-multi-resolve` to return `ERR-ORACLE-MULTI` (`mainnet/contracts/market/v0-4-market.clar:397-403`).
6. `get-assets`'s `unwrap-panic` on this call aborts the entire transaction (`mainnet/contracts/market/v0-4-market.clar:482-492`), even though Asset B (and the debt asset) are perfectly priceable — blocking withdraw/repay/liquidation for the whole position until Asset A's feed updates or the DAO intervenes.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
