## Title
Shared-Token Escrow Over-Release in Same-Chain Partial Fills Allows Solvers to Drain Other Legs' Escrow - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntentGatewayV2.placeOrder` deduplicates **output** tokens but never enforces uniqueness on **input** tokens [1](#0-0) . Escrow accounting is keyed only by `(commitment, token)`, not by leg index, and multiple input entries of the same token accumulate into a single pooled balance via `_orders[commitment][token] += reducedInputs[i].amount` [2](#0-1) . In `_fillSameChain`, once any single output leg is fully completed, the escrow release for that leg's paired input token is computed as the **entire remaining balance in the shared pool** rather than that leg's proportional share, letting a solver fully deliver the cheapest leg and walk away with escrow that belongs to other, unfilled legs funded by the same token.

### Finding Description
In `_fillSameChain`, per output leg `i`, when the leg becomes fully filled (`amountFilled == totalRequired`), the escrow amount to release is read directly from the token-keyed mapping instead of the leg-specific proportional amount:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

This "release everything remaining" branch is intended only to mop up rounding dust from earlier proportional partial fills of the **same** leg. But because escrow is tracked per `(commitment, token)` and not per `(commitment, leg-index)`, if the order has two distinct output legs (e.g. `output.assets = [DAI, WETH]`, guaranteed unique by the placeOrder dedup check) that are both funded by the **same input token** (e.g. `inputs = [{USDC, 400}, {USDC, 600}]`, which is never checked for uniqueness), then `_orders[commitment][USDC]` holds the combined `1000` for both legs.

A solver can fully fill only the DAI leg (worth 400 USDC of escrow) with a trivial output delivery, triggering the "release all remaining" branch, which reads `_orders[commitment][USDC] == 1000` and releases the **full 1000** to that solver via `_withdraw` [4](#0-3) . The WETH leg remains unfilled and the order stays open (`isFullyFilled == false`, so `_filled[commitment]` is deleted and no execution is finalized) [5](#0-4) , but the escrow that should have paid whoever later fills the WETH leg is already gone. A later filler who genuinely delivers WETH will compute `escrowedAmount = _orders[commitment][USDC] == 0` and receive nothing (`_withdraw` skips zero-amount entries without reverting) [6](#0-5) .

The root cause mirrors the WSHIDO pattern: a check is present (`amountFilled == totalRequired`) that appears to gate the release, but it does not validate the amount against what is actually owed for that specific leg — it releases from an under-specified shared resource instead of a leg-scoped entitlement.

### Impact Explanation
Any unprivileged solver can steal input-token escrow belonging to other legs of the same order by choosing which leg to complete first, whenever an order has multiple output legs sharing an input token. This is direct loss of user funds (the order creator's escrowed tokens) to an unentitled party, with no admin, relayer, or prover collusion required — matching the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" criteria.

### Likelihood Explanation
Exploitation requires only that a user (or an attacker acting as their own "user") place a same-chain order with two or more output legs backed by the same input token — nothing prevents this since only output-token uniqueness is enforced at placement [7](#0-6) . Any solver (including the attacker) can then call `fillOrder`/`_fillSameChain` and choose to complete the cheapest leg first. No special privileges, timing races, or off-chain infrastructure are needed.

### Recommendation
Track escrow per `(commitment, output-leg-index)` rather than pooling by `(commitment, token)` alone, or compute the full-fill release amount as `order.inputs[i].amount - alreadyReleasedForThisLeg` instead of reading the shared token balance. Additionally, enforce uniqueness (or an explicit N:1 allocation rule) for input tokens at `placeOrder` time, symmetric to the existing output-token dedup check.

### Proof of Concept
1. User places a same-chain order with:
   - `inputs = [{token: USDC, amount: 400}, {token: USDC, amount: 600}]`
   - `output.assets = [{token: DAI, amount: 400e18}, {token: WETH, amount: 0.2e18}]`
   Escrow after fee deduction: `_orders[commitment][USDC] == 1000` (combined).
2. Attacker (as solver) calls `fillOrder` supplying `options.outputs = [{DAI, 400e18}, {WETH, 0}]` — fully completing leg 0 only.
3. In `_fillSameChain`, leg 0: `amountFilled == totalRequired` → `escrowedAmount = _orders[commitment][USDC] == 1000` is placed into `escrowedInputs[0]`.
4. `_withdraw` transfers the full `1000` USDC to the attacker while `isFullyFilled == false` (leg 1 unmet), so `_filled[commitment]` is deleted and the order appears still open for leg 1.
5. Any subsequent filler attempting to deliver the WETH leg finds `_orders[commitment][USDC] == 0` and receives no escrow, confirming the 600 USDC meant for that leg was already stolen in step 3.
