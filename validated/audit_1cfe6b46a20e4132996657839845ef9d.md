### Title
Pause flag `_paused` in IntentGatewayV2 is declared but never enforced, leaving all fund-moving intent flows unstoppable - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase.sol` declares a dedicated pause flag but no contract in the `intentsv2` module ever reads it or exposes a `pause()`/`unpause()` setter, so the emergency-stop primitive that the storage layout was clearly designed for is completely inert. This mirrors the LensHub finding's root cause — a state-changing, fund-moving code path that is not gated by the pause mechanism the rest of the system relies on for incident response — except here the gap is total rather than partial: no external entrypoint of the intent gateway (`placeOrder`, `fillOrder`, `_withdraw`/refund/redeem via `onAccept`, `_sweepDust`) can be halted at all.

### Finding Description
`IntentsBase.sol` declares: [1](#0-0) 
with the comment "Appended last to preserve existing storage slots," indicating the flag was added to support pausability. However, a repo-wide search for `whenNotPaused` / `_paused` usage inside `evm/src/apps/intentsv2/**` (`ExtrinsicIntents.sol`, `IntrinsicIntents.sol`, `SolverAccount.sol`, `IntentsBase.sol`) returns only the two occurrences in `IntentsBase.sol` itself — the declaration and its comment. There is no modifier definition, no `pause()`/`unpause()` function, and no conditional check (`if (_paused) revert ...`) anywhere that consumes this variable.

Contrast this with the sibling `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts in the same codebase, which correctly wire `Pausable`/`PausableUpgradeable` into every fund-moving entrypoint: [2](#0-1) [3](#0-2) [4](#0-3) 

These show the intended pattern across the codebase: `send`, `onAccept`, `onPostRequestTimeout`, `transfer`, and `transferFrom` all carry `whenNotPaused`. The IntentGatewayV2 escrow/fill/refund/sweep logic in `IntentsBase.sol` — which moves user funds via `_withdraw` (escrow release/refund), `_execute` (calldata-driven output dispatch), and `_sweepDust` (dust sweep) — has no equivalent guard: [5](#0-4) [6](#0-5) 

Since `_paused` is never toggled or checked, if governance discovers an in-progress exploit against order placement, fill, cancellation, or the `RedeemEscrow`/`RefundEscrow`/`SweepDust` cross-chain message handlers, there is no on-chain mechanism to halt the flow of funds while a fix is prepared — the storage slot exists purely as dead weight.

### Impact Explanation
This is functionally identical to the LensHub gap: an emergency-stop control that the protocol clearly intends to have (evidenced by the reserved storage slot) does not actually block fund movement. In a live incident (e.g., a discovered logic bug enabling wrong-beneficiary fills or double-redemption of escrow), governance has no lever to stop `placeOrder`/`fillOrder`/redeem/refund/sweep execution in the IntentGatewayV2, allowing continued draining of escrowed user funds and dust reserves during the response window. This falls under the accepted "logic attacks / fund loss" category because it removes the only mitigation available once a separate bug is being actively exploited.

### Likelihood Explanation
High confidence that the code lacks the guard (confirmed by exhaustive grep across the `intentsv2` directory), but the severity is conditional — it only becomes actively damaging once another exploitable bug in the intent flow is found and cannot be stopped. It is not itself a directly triggerable fund-theft primitive by an unprivileged attacker in isolation; it is a missing-defense finding that removes a critical circuit breaker, consistent with the original report's own framing ("stopping transferring tokens was actually very helpful").

### Recommendation
Wire `_paused` into an actual `Pausable`-style modifier (or explicit `if (_paused) revert Paused();` checks) and apply it to all fund-moving external entrypoints of the IntentGatewayV2 — order placement, fill, cancel/refund, and the cross-chain `onAccept` handlers for `RedeemEscrow`, `RefundEscrow`, and `SweepDust` — together with owner-only `pause()`/`unpause()` setters, mirroring the pattern already used correctly in `HyperFungibleToken.sol` and `WrappedHyperFungibleToken.sol`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (via `ExtrinsicIntents.sol`/`IntrinsicIntents.sol`, both inheriting `IntentsBase`).
2. Observe that `_paused` is declared at [1](#0-0)  but grep for `_paused` across the whole `intentsv2` directory returns no consuming modifier or setter function.
3. Even if governance sets `_paused = true` via direct storage manipulation (there is no function to do so safely), no code path checks it — `_withdraw`, `_execute`, and `_sweepDust` (called from `placeOrder`/`fillOrder`/`onAccept` handlers) all execute unconditionally regardless of the flag's value, proving the pause mechanism cannot stop fund movement.
