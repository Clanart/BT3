### Title
Panic on identity nonce-sum (NULL-deref analog) reachable via untrusted FROST preprocess bytes aborts Bitcoin signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
CVE-2018-17000 is a NULL-pointer dereference reached by feeding a crafted file to `tiffcp`: attacker-controlled input reaches a code path that dereferences invalid state, causing a denial of service. The Serai analog is a panic on the point-at-infinity reached by feeding crafted nonce commitments through `read_preprocess` into the Bitcoin `Schnorr` algorithm: `x()` calls `encoded.x().expect("point at infinity")` at `networks/bitcoin/src/crypto.rs:15` and is invoked by `Hram::hram` at `networks/bitcoin/src/crypto.rs:65-66` on the aggregate nonce `R` and group key `A`. `R` is computed in `crypto/frost/src/sign.rs:383` as `B.nonces(&nonces)`, a binding-factor-weighted sum of `NonceCommitments` points deserialized from each participant's preprocess bytes (`Commitments::read`, `crypto/frost/src/nonce.rs:133-139`), with no identity check on the resulting sum before it is passed to `sign_share` (`crypto/frost/src/sign.rs:398`) and `verify` (`crypto/frost/src/sign.rs:465`).

### Finding Description
The `Schnorr` algorithm in `networks/bitcoin/src/crypto.rs` is explicitly documented to panic if `R` or `A` is the point at infinity ("This may panic if called with nonces/a group key which are the point at infinity", lines 78-80). `R` is derived entirely from preprocess messages, which are untrusted bytes supplied by other participants via `SignMachine::read_preprocess` (`crypto/frost/src/sign.rs:276-281`, and per-input in `networks/bitcoin/src/wallet/send.rs:351-353`). The pipeline:

1. Attacker sends serialized preprocess bytes → `TransactionSignMachine::read_preprocess` → `Commitments::read` → `NonceCommitments::read` → `Secp256k1::read_G` (group-element bytes the attacker fully controls).
2. `TransactionSignMachine::sign` → `AlgorithmSignMachine::sign` computes `Rs = B.nonces(&nonces)` at `crypto/frost/src/sign.rs:383` — a linear combination `Σ (base_commitment_i + rho_i · actual_commitment_i)` over all included participants.
3. `sign_share` (`crypto/frost/src/sign.rs:398`) and later `verify` inside `complete` (`crypto/frost/src/sign.rs:465`) call `Hram::hram(R, A, msg)`, which calls `x(R)` → `.expect("point at infinity")` → panic if the aggregate commitment sums to identity.
4. `verify` additionally calls `needs_negation(&sig.R)` / `x()` on derived points (`networks/bitcoin/src/crypto.rs:146`).

There is no check that any `NonceCommitments` point, nor the weighted aggregate `R`, is non-identity before it reaches `hram`. Like `_TIFFmemcmp(NULL, ...)`, a value that should never be empty is dereferenced unconditionally on attacker-influenced input.

### Impact Explanation
A panic in `sign_share` or `complete` aborts the signing attempt and, since the panic propagates through `machine.sign(...)`/`machine.complete(...)` in `TransactionSignMachine` (`networks/bitcoin/src/wallet/send.rs:355-398`), can crash the processor task performing the Bitcoin multisig — a denial of service against threshold signing (stuck funds / halted payouts), matching the CVE's availability-only Medium profile. The same panic applies to any `Algorithm` whose `hram`/`verify` touches `R` or the group key without an identity guard, but `networks/bitcoin/src/crypto.rs` makes it concrete for Bitcoin transaction signing.

### Likelihood Explanation
Triggering requires the weighted aggregate `R = Σ (D_i + rho_i·E_i)` to equal the identity. Because `rho_i` is a hash over all preprocesses (`B.calculate_binding_factors`, `crypto/frost/src/sign.rs:362-371`), a malicious participant cannot trivially solve for their commitment in a single-shot round. However, preprocesses are gossiped before `sign` runs, and nothing in `NonceCommitments::read` or `Commitments::read` rejects identity or otherwise degenerate group elements; a participant submitting identity for both commitments contributes exactly `identity` to the sum, and adaptive/repeated-session strategies (or a participant able to see others' preprocesses before finalizing their own, e.g., ordering within the same batch) can target a zero sum. Even absent a deterministic exploit, the code documents the panic condition rather than returning `FrostError`, so any edge case producing an identity `R` (including malformed `ThresholdKeys`/views) is a reachable crash rather than a handled error.

### Recommendation
Reject identity/degenerate points early: in `NonceCommitments::read` (`crypto/frost/src/nonce.rs`) and after computing `Rs`/`B.nonces(...)` in `crypto/frost/src/sign.rs`, return `FrostError::InvalidPreprocess(l)`/`InternalError` instead of allowing the aggregate to reach `hram`. Alternatively, make `x()`/`x_only()`/`Hram::hram` in `networks/bitcoin/src/crypto.rs` total (return `Option`/error) so a point-at-infinity input fails verification rather than panicking, and have `sign_share`/`verify` propagate that failure.

### Proof of Concept
- Supply a preprocess byte stream to `TransactionSignMachine::read_preprocess` (`networks/bitcoin/src/wallet/send.rs:351-353`) whose `NonceCommitments` encode the point at infinity for both the base and actual generator commitments (e.g., the compressed `0x00`/infinity encoding accepted by `Secp256k1::read_G`).
- Contribute commitments such that the binding-weighted sum at `crypto/frost/src/sign.rs:383` is `ProjectivePoint::IDENTITY` (identity contributions cancel; adversarial ordering/ROS-style adaptivity across repeated `attempt`s assists reaching zero).
- `machine.sign(preprocesses, b"")` → `IetfSchnorr::sign_share` → `Hram::hram(&R=∞, &A, msg)` → `x(&R)` → `encoded.x().expect("point at infinity")` (`networks/bitcoin/src/crypto.rs:15`) → panic, aborting the signing task. The same panic is reachable later via `complete` → `Schnorr::verify` (`crypto/frost/src/sign.rs:465`, `networks/bitcoin/src/crypto.rs:145-148`).
