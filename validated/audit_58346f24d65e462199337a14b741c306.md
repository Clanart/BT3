### Title
Hookify rule frontmatter parser silently drops `operator`/`pattern` fields for standard-but-differently-indented YAML condition lists, degrading multi-condition security rules into no-ops - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter`'s hand-rolled YAML parser only recognizes a dict-item continuation line (e.g. `operator:`, `pattern:`) when its indentation is strictly greater than 2 spaces (`indent > 2`). Valid, commonly-used YAML list syntax with the `-` marker at column 0 and continuation keys indented by exactly 2 spaces (the natural indent following `"- "`) falls below this threshold, so those lines are silently discarded instead of being attached to the current condition dict. This causes `Condition.from_dict` to fall back to its defaults (`operator='regex_match'`, `pattern=''`), turning a strict AND-condition security rule into a rule whose conditions effectively always evaluate true/false regardless of the intended pattern.

### Finding Description
In `extract_frontmatter` (`plugins/hookify/core/config_loader.py`), the state machine classifies each line into: top-level key (`indent == 0`), new list item (`stripped.startswith('-')`), or dict-item continuation (`elif indent > 2 and in_dict_item and ':' in line`) [1](#0-0) . Standard YAML permits list dashes at indent 0 with their keys continuing at indent 2 (2 spaces = length of `"- "`). For example:

```
conditions:
- field: command
  operator: regex_match
  pattern: rm -rf
- field: file_path
  operator: not_contains
  pattern: /tmp
```

Here `- field: command` matches the list-item branch and starts `current_dict = {'field': 'command'}` with `in_dict_item = True` [2](#0-1) . The following `  operator: regex_match` line has `indent == 2`, which satisfies none of the three branches (`indent==0` fails, doesn't start with `-`, and `indent > 2` fails), so it is silently skipped along with `  pattern: rm -rf`. The same happens for the second condition's `operator`/`pattern` lines. The resulting parsed `conditions` list becomes `[{'field': 'command'}, {'field': 'file_path'}]`, losing all pattern/operator data.

`Condition.from_dict` then fills in defaults for the missing keys: `operator='regex_match'`, `pattern=''` [3](#0-2) . In `RuleEngine._check_condition`, `regex_match('', field_value)` calls `re.search('', text)`, which matches any non-empty (truthy) string unconditionally [4](#0-3) . `_rule_matches` requires all conditions to pass for the rule to fire [5](#0-4) , so the intended two specific conditions (`command` regex "rm -rf", `file_path not_contains /tmp`) are replaced by two field-presence-only checks with empty patterns — silently changing the rule's actual matching behavior with no error, warning, or exception raised anywhere in `load_rule_file`/`load_rules`.

No schema validation, no YAML library, and no warning path exists for this case — `load_rules` only catches `IOError/OSError/ValueError/...` classes, none of which are triggered since parsing "succeeds" without error [6](#0-5) .

### Impact Explanation
This breaks the rule-integrity invariant that a hookify rule's declared multi-condition AND-logic (e.g., "block `rm -rf` unless under `/tmp`") is what actually gets enforced by `PreToolUse`/`PostToolUse`/`Stop` hooks. `pretooluse.py` and other hook scripts load rules via `load_rules()` and execute `RuleEngine.evaluate_rules` against live tool input with no independent verification [7](#0-6) . A security-critical hookify rule written in valid, semantically-correct YAML (using 0-indent dashes, a common and encouraged style) is silently degraded into a rule that no longer checks the intended dangerous pattern, causing hookify to fail to block/warn on operations it was designed to catch (false negative in the safety control), or to spuriously fire on unrelated operations (false positive/noise that could desensitize users to real warnings). This is a hook-enforcement/trust-boundary bypass in the plugin's own guardrail mechanism.

### Likelihood Explanation
No special privileges are required beyond the ability to introduce or influence content of a `.claude/hookify.*.local.md` file — which is loaded automatically by `load_rules()`/`load_rule_file()` for every file matching that glob in the working directory [8](#0-7) . Such files are commonly generated by the `/hookify:configure`/`/hookify` command flow or copied from documentation/PR suggestions; the vulnerable indentation style (0-indent dash, 2-space continuation) is valid YAML and plausibly produced by an LLM, a copy-pasted example, or repo content (e.g., a PR that "adds a safety rule") without any visual indication that anything is wrong, since no error is ever surfaced. The bug is fully deterministic and 100% reproducible for any condition list using this indentation.

### Recommendation
Replace the hand-rolled state-machine parser with a real YAML parser (e.g., Python's `yaml.safe_load`) for the frontmatter block, eliminating custom indentation-threshold heuristics entirely. If a dependency-free parser must be kept, fix the continuation-detection logic to compare each continuation line's indentation against the indentation of the line that started the current list item (`base_indent`) rather than a hardcoded magic constant (`indent > 2`), and add a validation/assertion step in `Rule.from_dict`/`load_rule_file` that rejects or warns loudly when any parsed `Condition` has an empty `pattern` or missing `field`, rather than silently defaulting.

### Proof of Concept
Add a fuzz/invariant test in a new test module (e.g. `plugins/hookify/core/test_config_loader_fuzz.py`) that generates the same two-condition YAML block under several valid indentation styles and asserts the parsed `Condition` objects are identical (invariant to whitespace-only YAML-equivalent changes):

```python
import itertools
from hookify.core.config_loader import extract_frontmatter, Rule

BASE = """---
name: block-rm-outside-tmp
enabled: true
event: file
action: block
conditions:
{conditions_block}
---
Body
"""

def make_block(dash_indent, cont_indent):
    d = " " * dash_indent
    c = " " * cont_indent
    return (
        f"{d}- field: command\n{c}operator: regex_match\n{c}pattern: rm -rf\n"
        f"{d}- field: file_path\n{c}operator: not_contains\n{c}pattern: /tmp\n"
    )

def test_condition_parsing_invariant_to_valid_yaml_indentation():
    results = []
    for dash_indent, cont_indent in itertools.product([0, 2], [2, 4]):
        content = BASE.format(conditions_block=make_block(dash_indent, cont_indent))
        fm, msg = extract_frontmatter(content)
        rule = Rule.from_dict(fm, msg)
        results.append([(c.field, c.operator, c.pattern) for c in rule.conditions])

    expected = [
        ("command", "regex_match", "rm -rf"),
        ("file_path", "not_contains", "/tmp"),
    ]
    for r in results:
        assert r == expected, f"Parser dropped/mis-attributed fields: got {r}"
```

Expected: with `dash_indent=0, cont_indent=2` the test fails, showing parsed conditions as `[("command", "regex_match", ""), ("file_path", "regex_match", "")]` instead of the expected pattern/operator values — demonstrating the silent field-drop and subsequent security-relevant `Rule` degradation via `RuleEngine._check_condition`'s empty-pattern always-match behavior.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
