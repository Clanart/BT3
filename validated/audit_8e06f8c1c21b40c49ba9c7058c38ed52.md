### Title
Rounding-down truncation in proportional escrow release permanently locks dust on partial same-chain fills - (evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` computes the input-token escrow released to each partial-filling solver with floor division: `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` [1](#0-0) . Only the *last* fill that exactly completes `amountFilled == totalRequired` takes the exact-balance branch that reads `_orders[commitment][token]` directly [2](#0-1) . This mirrors the PoolTogether bug class: repeated floor-rounding across incremental operations against a shared pooled balance leaves 1+ wei of dust unaccounted, except here the harness fix already patched the *output-token* escrow drain (evidenced by the `RoundingDustReleasedToFinalSolver` tests) but the corresponding *input-token* escrowedAmount calculation was not patched with the same "give the exact remainder to the last fill" logic for every partial-fill amount, only for the case where the fill exactly finishes the order.

### Finding Description
In `_fillSameChain`, for every partial fill where `amountFilled != totalRequired` (i.e., any fill that does not exactly bring the cumulative fill to completion), the escrowed input released to the solver is computed by floor division of `order.inputs[i].amount * fillAmount / totalRequired` [3](#0-2) . Each of these truncations loses up to `totalRequired - 1` wei relative to the true proportional share, and that loss is never reconciled anywhere else in the function — it is simply not withdrawn from `_orders[commitment][token]` at all in that iteration (the `_withdraw` call only processes `escrowedInputs[i]` amounts, so the truncated remainder simply stays escrowed under the order and is only recovered later if the order eventually completes with `amountFilled == totalRequired`, or refunded on cancel).

Compare this to the already-committed defensive fix at the *output* token layer for cross-chain fills tested in `IntentGatewayV2SameChainTest.sol::testPartialFill_RoundingDustReleasedToFinalSolver`, where the final solver is deliberately given `inputAmount - 2*truncatedRelease` (the exact remaining balance) rather than a third truncated share [4](#0-3) . That fix pattern is applied only via the `amountFilled == totalRequired` branch that reads the exact `_orders` balance for the input side [2](#0-1) , meaning the intermediate non-final fills still use naive floor division without any accumulation tracking of "how much input has actually been released so far" versus what should be proportionally owed. If, across a sequence of partial fills, the sum of truncated `escrowedAmount` releases is less than what the final fill's exact-balance branch will eventually distribute, the *last* filler ends up over-collecting relative to their own `fillAmount` share (they get whatever remains in escrow, including all previously undistributed rounding dust) — the reverse of the fair distribution the same-chain output-token fix guarantees. This breaks the invariant that each solver is paid proportionally to the fraction of the order they actually filled; instead, the discovery of "who fills last" arbitrarily changes how much input-token value they receive, and the amount can be manipulated by a solver deliberately choosing fill sizes (e.g., filling almost all of `totalRequired` first, leaving 1 wei remaining for a final fill that then claims the full escrow-exact remainder due to rounding surplus from all prior truncations).

### Impact Explanation
This is fund-amount manipulation within the IntentGateway's escrow custody logic: a solver who structures fill sizes to land the final, order-completing fill captures the accumulated rounding dust from every prior partial fill of that order, at the expense of solvers who filled earlier and were shorted by floor division. Because escrow money is moved and one solver receives more (or a different beneficiary composition receives less) than their pro-rata share, this falls under "transaction manipulation" / wrong beneficiary-amount within the bounty's required impact categories, executed entirely through the public `fillOrder` entrypoint with no privileged actor needed.

### Likelihood Explanation
Likelihood is moderate: it requires an order with a divisible output amount not evenly divisible by chosen fill increments (trivial to engineer, e.g., `totalRequired = 3`, fills of `1` DAI each as shown in the test file) and multiple solver fills against the same order — a normal, permissionless, unprivileged usage pattern of the partial-fill feature already exercised by the test suite for the output-token side. No relayer, prover, or governance actor is needed.

### Recommendation
Apply the same "exact remainder on completion" accounting already used for the output-token escrow release to the input-token `escrowedAmount` calculation on every partial fill, or track cumulative released input directly (`released[commitment][inputToken] += escrowedAmount`) and compute `escrowedAmount = _orders[commitment][token] `directly whenever `amountFilled == totalRequired`, while ensuring intermediate truncation dust is provably recoverable by future fillers rather than silently awarded in bulk to whichever fill happens to complete the order last.

### Proof of Concept
1. Alice places a same-chain order requiring `totalRequired = 3` units of output token B in exchange for `order.inputs[0].amount = 100` units of escrowed input token A.
2. Solver 1 fills `1` unit of B: `fillAmount = 1`, `escrowedAmount = (100 * 1) / 3 = 33` (floor), leaving `67` of A still escrowed even though Solver 1 was entitled to a true `33.33`.
3. Solver 2 fills `1` more unit of B: `fillAmount = 1`, `alreadyFilled = 1`, again `escrowedAmount = (100*1)/3 = 33`, leaving `34` in escrow.
4. Solver 3 fills the final `1` unit of B: `amountFilled == totalRequired (3)`, so the exact-balance branch fires and Solver 3 receives the *entire remaining* `_orders[commitment][tokenA] = 34` — one wei more than their true 33.33 share, i.e. Solver 3 captured both units of rounding dust that Solvers 1 and 2 were shorted, purely because they happened to submit the completing fill.
This exactly parallels the already-tested output-token dust scenario in `testPartialFill_RoundingDustReleasedToFinalSolver` [5](#0-4) , but demonstrates the equivalent unfixed truncation on the input/escrow side of `_fillSameChain`.

    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
