### Title
Attacker-controlled threshold parameters cause quadratic Lagrange interpolation blocking in `ThresholdKeys::new` - (File: crypto/dkg/src/lib.rs)

### Summary
The referenced CVE (CVE-2018-15472) describes a worker thread blocking for a long time on adversarial input with no timeout. The same bug class exists in Serai's DKG crate: `ThresholdKeys::read` accepts untrusted `t`/`n` values up to `u16::MAX`, and `ThresholdKeys::new` then computes the group key via Lagrange `interpolation_factor` — an O(t²) field-arithmetic loop plus `t` field inversions — with no bound or timeout. `ThresholdKeys::read` is explicitly a reachable sink for untrusted bytes, so an unprivileged party that can feed serialized `ThresholdKeys` into any `read`/recover/`promote` path forces the host to burn billions of field operations.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from the reader and only bounds them via `ThresholdParams::new`, which merely checks `t <= n` and `i <= n` — both may be as large as 65535 [1](#0-0) [2](#0-1) 

With `Interpolation::Lagrange` (a single `0x01` byte), `ThresholdKeys::new` computes the group key by evaluating `interpolation_factor` for each of the `t` participants `1..=t` [3](#0-2) 

Each `interpolation_factor` call iterates over all `t` included participants performing two field multiplications per element, and finishes with a full field inversion (`denom.invert()`) — the most expensive scalar operation [4](#0-3) 

Total cost is therefore `t` inversions plus `O(t²)` multiplications. At `t = 65535` that is ≈4.3×10⁹ field multiplications and 65535 inversions, blocking the calling thread for a very long time. The deserialization itself supplies the quadratic input cheaply: `n` verification shares of ~32 bytes each means ~2 MB of input triggers the maximum work [5](#0-4) 

The same quadratic pattern is reachable again on any later `ThresholdKeys::view(included)` call, which computes `interpolation_factor` for every member of `included` [6](#0-5) 

### Impact Explanation
An unprivileged party supplying crafted bytes to `ThresholdKeys::read` (or to a recovery/promotion path that internally calls `ThresholdKeys::new`) forces the host into ~4 billion field operations and 65k inversions on a single blocking call — a direct availability denial of the signing/key-management thread, mirroring the CVE's `A:H` impact of a rouge-blocking Sidekiq job. No secret access, malformed curve point, or privileged position is required; only control of the length fields `t` and `n` plus enough share bytes to pass the read stage.

### Likelihood Explanation
Reachability is concrete: `ThresholdKeys::read` is a listed public deserialization entry point, `ThresholdParams` accepts any `t <= n <= 65535`, and `Interpolation::Lagrange` requires no additional validation. The only input requirement is ~2 MB of validly-encoded points, well within typical message size limits. The cost is deterministic and unavoidable once `ThresholdKeys::new` is invoked, since the group key is eagerly interpolated at construction [7](#0-6) 

### Recommendation
Cap `n`/`t` at a sane protocol maximum (e.g., the actual supported multisig size) inside `ThresholdParams::new` or `ThresholdKeys::read` before any interpolation work, and/or defer/cache group-key computation. If arbitrary thresholds must be supported, restructure group-key derivation to O(t) (precomputed prefix products of Lagrange numerators/denominators or a batch inversion via Montgomery's trick) instead of the current per-participant O(t) factorization.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }
