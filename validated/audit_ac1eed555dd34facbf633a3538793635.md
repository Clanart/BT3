### Title
`find-superset` selects an arbitrary (not the tightest) covering egroup among population-equal, mutually-incomparable masks, letting borrowers pick a looser LTV - (File: mainnet/contracts/registry/v0-egroup.clar)

### Summary
`resolve`/`find` walk buckets from the smallest population upward and, within a bucket, return the *first* mask in list order for which the caller's asset mask is a subset, via `find-superset`/`iter-find-superset`. When two egroups of equal population size are supersets of the same borrower mask but are not subsets of each other (e.g. `C=0b1011` and `D=0b1101` both cover `0b1001`), the invariant enforced at insert/update time (`validate-superset-invariant` / `check-egroup-invariant`) does not constrain their relative LTVs because neither is a `subset` of the other. The resolver therefore can return the egroup with the higher `LTV-BORROW`, even though a stricter, equally-specific egroup also legitimately covers the position.

### Finding Description
Tracing the resolution path for a position mask `0b1001` (assets 0 and 3):

- `find` computes `min = population(0b1001) = 2` and calls `active(2)`, which returns bucket indices (population-1) with population ≥ 2 in increasing order via `iter-active`/`ITER-UINT-128` [1](#0-0) .
- No exact 2-population egroup exists, so bucket-2 contributes nothing; the fold proceeds to bucket-3 via `iter-find`, which calls `find-superset` on the population-3 bucket list [2](#0-1) .
- `find-superset`/`iter-find-superset` iterate the bucket's `(list 128 uint)` in *insertion/append order* and return the **first** mask for which `subset target mask` holds, ignoring any other valid covering mask later in the list [3](#0-2) .
- Bucket-3 was populated by `insert-bucket`, which simply appends new masks to the end of the list: `(append bucket mask)` [4](#0-3) . If `D` (mask `0b1101`, LTV-BORROW=9000bps) was inserted before `C` (mask `0b1011`, LTV-BORROW=5000bps), `D` appears earlier in the list and is matched first for a position mask `0b1001`, since both `subset(0b1001, 0b1101)` and `subset(0b1001, 0b1011)` are true.
- The invariant check performed at insert time, `check-egroup-invariant`, only restricts LTV ordering between egroups that are in an actual subset/superset relationship with each other: `(if (subset existing-mask new-mask) ... (if (subset new-mask existing-mask) ... true))` — when neither mask is a subset of the other (as with `C` and `D`, which share bits 0 and 3 but differ on bit 1 vs bit 2), the check trivially returns `true` and imposes no constraint on their relative `LTV-BORROW` values [5](#0-4) .
- Consequently, two equally-specific, mutually-incomparable, but LTV-inconsistent egroups can legitimately coexist in the same bucket, and the resolver's tie-break (first-match-in-list-order) is not based on picking the minimum (safest) `LTV-BORROW`. No later gate in `borrow` re-derives or cross-checks against the alternate covering egroup — the market simply consumes whatever `LTV-BORROW` `resolve` returns for the health check.

The root cause is purely in the resolution/tie-breaking logic of `v0-egroup.clar` (`find-superset`, `iter-find-superset`, bucket append order), not in oracle pricing or DAO misconfiguration — the two egroups themselves can each be a perfectly sensible, independently-approved 3-asset configuration; the bug is that the code has no deterministic "pick lowest LTV among covering supersets" rule when candidate masks are incomparable.

### Impact Explanation
Direction: a borrower's effective `LTV-BORROW` is inflated from the intended tightest bound (5000bps via `C`) to a looser bound (9000bps via `D`) for the identical two-asset composition, purely based on registry insertion order. The borrower profits by extracting the LTV delta (4000bps) in additional borrowable USD against the same collateral, with the shortfall socialized to lenders/vault depositors. This is an on-chain, code-driven mispricing of borrowing capacity (not an oracle issue) and can push positions to be under-margined relative to the safe threshold intended by the tighter egroup, threatening protocol solvency for that debt tranche — matching the Critical / protocol-insolvency category.

### Likelihood Explanation
Exploitability depends entirely on DAO-approved registry state having two equal-population, pairwise-incomparable egroups that both cover the same reduced asset subset with materially different `LTV-BORROW` values, and on their insertion order placing the looser one first in the bucket list. This is plausible in a maturing protocol with many overlapping asset-combination egroups (as the docs' rationale for the bucket system implies), and once such a configuration exists, exploitation requires no privilege — any ordinary user holding just the shared subset of assets (assets 0 and 3) can borrow at the looser LTV by simply calling `borrow`. It is repeatable for any wallet as long as the adverse ordering persists in the bucket list (removal/update via `remove-bucket`/`insert-bucket` could change it, but nothing prevents the adverse ordering from arising or persisting).

### Recommendation
In `find-superset`/`iter-find-superset`, do not return the first matching mask; scan the full bucket (or all buckets with population ≥ min) for **all** masks satisfying `subset target mask`, and select the one with the minimum `LTV-BORROW` (i.e., the strictest/safest covering egroup), or equivalently, extend `check-egroup-invariant`/`validate-superset-invariant` to also compare and reconcile LTV values across incomparable-but-co-covering masks so that resolution is guaranteed order-independent regardless of insertion order.

### Proof of Concept
Clarinet/vitest simnet plan on `mainnet/contracts/registry/v0-egroup.clar` + `mainnet/contracts/market/v0-4-market.clar`:
1. As DAO, `insert` egroup `D`: `MASK=0b1101` (assets 0,2,3), `LTV-BORROW=9000`, `LTV-LIQ-PARTIAL=9200`, `LTV-LIQ-FULL=9500` (satisfying `serialize-and-validate-input` strict ordering).
2. As DAO, `insert` egroup `C`: `MASK=0b1011` (assets 0,1,3), `LTV-BORROW=5000`, `LTV-LIQ-PARTIAL=6000`, `LTV-LIQ-FULL=7000`. Confirm `validate-superset-invariant` passes for both since neither mask is a subset of the other.
3. Call `get-bucket` for popcount buff `0x02` (population 3) and assert the list is `[D-mask, C-mask]` (D appended first).
4. As an attacker principal, open a position using only assets 0 and 3 (`mask=0b1001`), with collateral value normalized appropriately for the two assets' price feeds/decimals.
5. Call `borrow` to push the position to ~89% LTV of the deposited collateral.
6. Assert the call succeeds using the 9000bps threshold from `D`, and would have reverted with `ERR-UNHEALTHY` had `C`'s 5000bps threshold been (correctly) applied, verifying `resolve(0b1001)` returned egroup `D` instead of the stricter `C`.

(define-private (iter-active (pos uint) (acc {bitmap: uint, min: uint, result: (list 128 uint)}))
  ;; abs is the 1-based rep of pos in the bitmap (represents population count)
  ;; pos is the bucket index (0-based)
  (let ((abs (+ pos u1))
        (bmap (get bitmap acc))
        (min (get min acc))
        (actv (> (bit-and bmap (pow u2 pos)) u0))
        (bounds (>= abs min)))
    (if (and actv bounds)
        ;; Bucket exists AND meets population requirement - include it
        ;; Return bucket INDEX (pos), not population count (abs)
        (let ((result (get result acc))
              (new (as-max-len? (append result pos) u128)))
          (merge acc { result: (unwrap-panic new) }))
        ;; Skip this bucket
        acc)))

(define-private (find-superset (target uint) (masks (list 128 uint)))
  (let ((init { target: target, result: none })
        (out (fold iter-find-superset masks init)))
    (get result out)))

(define-private (iter-find-superset (mask uint) (acc {target: uint, result: (optional uint)}))
  (let ((res (get result acc)))
    (if (is-some res)
        ;; Already found a match - return early
        acc
        ;; Check if this mask matches
        (let ((target (get target acc)))
          (if (subset target mask)
              ;; Match found - return egroup ID
              (let ((id (unwrap-panic (map-get? reverse mask))))
                (merge acc { result: (some (buff-to-uint-be id)) }))
              ;; Not a match - skip
              acc)))))
