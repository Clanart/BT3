### Title
OP_RETURN data is excluded from transaction weight and fee calculation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Medium severity: `SignableTransaction::new` adds an optional OP_RETURN output but calculates weight, virtual size, and the required fee using only the payment outputs. A transaction containing `data` therefore pays the fee rate appropriate for a smaller transaction and can be rejected by Bitcoin relay policy despite the caller requesting a valid fee rate. [1](#0-0) 

### Finding Description
When `data` is provided, an additional zero-value OP_RETURN `TxOut` is appended to `tx_outs`. [2](#0-1) 

The subsequent `calculate_weight_vbytes` call is passed `payments`, not `tx_outs`, so the OP_RETURN output is absent from the transaction constructed for measurement. [3](#0-2)  The helper builds its measurement transaction exclusively from `payments` and the optional change script. [4](#0-3) 

The same omission occurs when change is considered because the second measurement is also based on `payments` rather than the complete output list. [5](#0-4)  The final `SignableTransaction` nevertheless contains the enlarged `tx_outs` vector. [6](#0-5) 

### Impact Explanation
`needed_fee` is `fee_per_vbyte * vbytes` for a transaction that excludes the OP_RETURN output, while the signed transaction includes that output and consumes additional block space. [7](#0-6) 

For an 80-byte payload, the actual transaction can be approximately 90 vbytes larger than measured, materially reducing its effective fee rate. If the requested rate is near the minimum relay rate, the generated transaction can fail standard relay even though the constructor's minimum-fee check passed. This can make intended spends unbroadcastable until reconstructed with a higher fee. [8](#0-7) 

### Likelihood Explanation
Any call to `SignableTransaction::new` with `Some(data)` triggers the incorrect calculation unconditionally. The API explicitly supports this input as transaction metadata, so untrusted transaction data that a caller causes Serai to sign can directly reach the affected path. [9](#0-8) 

### Recommendation
Calculate weight from the complete output set, including the OP_RETURN output, before computing `needed_fee`. One approach is to change `calculate_weight_vbytes` to accept the actual `tx_outs` slice or otherwise pass a payment/output representation containing `payments`, `data`, and `change`, then use that same representation for both measurement and final transaction construction. [10](#0-9) 

### Proof of Concept
The following assertion demonstrates that an 80-byte OP_RETURN increases the actual output set and transaction size while leaving the reported required fee unchanged:

```rust
let without_data = SignableTransaction::new(
  inputs.clone(),
  &payments,
  change.clone(),
  None,
  fee_per_vbyte,
).unwrap();

let with_data = SignableTransaction::new(
  inputs,
  &payments,
  change,
  Some(vec![0; 80]),
  fee_per_vbyte,
).unwrap();

assert_eq!(
  without_data.transaction().output.len() + 1,
  with_data.transaction().output.len()
);

// The fee estimate ignores the additional OP_RETURN output.
assert_eq!(without_data.needed_fee(), with_data.needed_fee());

// After signing, with_data.vsize() is larger than without_data.vsize(),
// so its actual fee rate is lower than fee_per_vbyte.
```

The equality holds because both calls calculate fees from the same `payments` slice even though `with_data` contains an extra output. [11](#0-10)
