### Title
Unauthenticated `CallDispatcher.dispatch` allows anyone to drain any native ETH (or token) balance left in the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, permissionless contract used by multiple unrelated protocol flows — `HyperFungibleToken`/`HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`, and `IntentGatewayV2` — to execute arbitrary post-mint/post-unlock/post-fill calldata. Its `dispatch(bytes encoded)` function has no access control (no `onlyHost`, no caller allow-list, no reentrancy/ownership binding) and the contract accepts arbitrary native value via `receive() external payable {}`. Any address can call `dispatch` directly with an arbitrary `Call[]` array to move whatever native ETH balance is currently sitting in the dispatcher to any target of its choosing.

### Finding Description
`dispatch` only checks that each `call.to` has code and reverts the whole batch if any sub-call fails; it performs no check on `msg.sender`, no binding to a specific chain/module/order/payee, and no verification that the value it forwards was intended for the caller: [1](#0-0) 

The dispatcher is designed to *transiently* hold native value/tokens within a single legitimate transaction — e.g. `WrappedHyperFungibleTokenUpgradeable.onAccept` unlocks/unwraps ETH to the dispatcher and immediately invokes `dispatch` so the `Call.value` field can forward it to a router: [2](#0-1) 

Documentation confirms the dispatcher is a single shared deployment referenced across apps and that it can end up holding leftover balances/dust after execution: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution," and for IntentGatewayV2, "any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust." No equivalent sweep/guard exists inside `CallDispatcher.sol` itself, and since `dispatch` is public/unauthenticated, any residual native balance in the dispatcher (from partial swap execution, over-funded `Call.value`, rounding, a reverted/interrupted flow, or a stray direct ETH transfer via `receive()`) is available to be drained by any unprivileged caller who crafts their own `Call[]` targeting themselves.

Because `CallDispatcher` is a shared, stateless-router singleton with no per-flow/per-chain/per-order binding, "reusing data cross module" isn't even needed — the contract simply never authenticates who is entitled to spend value it currently holds. `dispatch` doesn't distinguish a legitimate caller (an HFT/WrappedHFT/IntentGatewayV2 contract acting on behalf of a specific cross-chain message) from an arbitrary EOA.

### Impact Explanation
If native value transiently held by the dispatcher (for example, mid-flow ETH from a `WrappedHyperFungibleToken` unwrap-and-swap, or ETH sent directly via `receive()`) is not fully consumed by the intended `Call[]` in the same transaction, or if it accumulates as dust from partial/failed executions, any external account can call `dispatch` and route that ETH to an address they control. This is a direct, unauthorized movement of protocol/user-escrowed native value out of the shared dispatcher, matching the "wrongful ... withdrawal, redirect of protocol-controlled or user escrowed assets" impact category.

### Likelihood Explanation
Exploitability depends on the dispatcher actually holding a non-zero native balance outside of an atomic, self-contained call sequence. In the reviewed code, the intended use pattern (mint/unlock → immediately `dispatch` within the same `onAccept` transaction) is atomic, so under normal successful execution there is no window for an outside caller to intervene. However, the design provides no defense-in-depth: `dispatch` has no access control at all, so any ETH that does end up resting in the contract (via `receive()`, a partially-consumed `Call.value`, or dust from a swap that doesn't spend 100% of forwarded value) is fully exposed to any caller. Whether a concrete residual-balance scenario is reachable in production (e.g., a swap call that doesn't consume all forwarded ETH, or a legitimate actor mistakenly sending ETH directly to the dispatcher address) needs further verification against the exact `Call[]` payloads used by integrators — I could not fully verify from the indexed code whether `IntentGatewayV2`/`IntentsBase` sweep *native* ETH balance (only ERC-20 "dust" sweeping was documented) after calldata execution.

### Recommendation
- Add access control to `CallDispatcher.dispatch` so only pre-authorized callers (the specific HFT/WrappedHFT/IntentGatewayV2 instances that are meant to use it, or a caller-supplied one-time authorization token bound to a specific message/commitment) may invoke it.
- Ensure `dispatch` never carries a standing balance: require the caller to pre-fund each call exactly (e.g., pass `msg.value` matching total `Call.value` sum) rather than relying on residual contract balance, and sweep any leftover native/token balance back to the invoking contract or a fixed treasury at the end of every `dispatch` call, mirroring the ERC-20 dust-sweep pattern already used in `IntentGatewayV2`.
- Consider making `CallDispatcher` non-custodial by design (e.g., forbid it from retaining a balance across transactions, revert if `address(this).balance` is nonzero after all calls complete for a given `dispatch` invocation, unless the residual is explicitly swept to a known-safe recipient).

### Proof of Concept
1. Deploy `CallDispatcher` (as used on any Hyperbridge EVM chain) and send it native ETH directly (`receive()` accepts arbitrary value) or trigger a legitimate cross-chain flow (e.g., `WrappedHyperFungibleTokenUpgradeable` unwrap-and-swap) where the swap call does not consume 100% of the forwarded `Call.value`, leaving residual ETH in the dispatcher.
2. From an unrelated, unprivileged EOA, call `CallDispatcher.dispatch(encoded)` with a single `Call{ to: attackerContract, value: address(dispatcher).balance, data: "" }`.
3. Observe the call succeeds (no `msg.sender` check exists in `dispatch`), and the attacker-controlled contract receives the dispatcher's native balance, even though that value was intended for a different user's cross-chain settlement flow. [3](#0-2)

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
