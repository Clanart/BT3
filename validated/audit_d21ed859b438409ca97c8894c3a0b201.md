### Title
Vesting Balances Held Under a Direct-Cast EVM Address Become Permanently Frozen After Auto-Association - (File: `utils/helpers/associate.go`)

### Summary
When an EVM address is associated to a Sei (secp256k1) address — either explicitly via the `Associate` precompile/tx or implicitly on the sender's very first ordinary EVM transaction — `AssociationHelper.MigrateBalance` moves only the *spendable* balance of the direct-cast account (`sdk.AccAddress(evmAddr[:])`) to the newly associated Sei address. Any coins still locked under a vesting schedule are left behind at the direct-cast address, and that account is deliberately **not removed** in this case. Because the direct-cast address is derived by truncating a Keccak-256 EVM public key, there is no discoverable secp256k1 private key that authors a valid Cosmos signature for it — once association happens, nobody can ever move the still-vesting coins, even after they fully vest.

### Finding Description
`AssociationHelper.MigrateBalance` is the routine responsible for reconciling balances between the direct-cast Sei address (`castAddr = sdk.AccAddress(evmAddr[:])`) and the real, pubkey-derived Sei address (`seiAddr`) during association: [1](#0-0) 

It only moves `SpendableCoins` (or `usei` only, in the `migrateUseiOnly` case) and the wei balance. It then only removes the `castAddr` account — reclaiming/retiring it — `if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero()`. If the account is a vesting account with any coins still locked, the account is preserved as-is at `castAddr`, but the mapping from `evmAddr` now points to `seiAddr` instead, and the pubkey has already been moved/attached to `seiAddr`: [2](#0-1) 

`AssociateAddresses` is invoked automatically by the EVM ante handler on essentially every transaction path — an explicit `Associate` tx, or, critically, the very first ordinary EVM transaction from an address that isn't yet associated: [3](#0-2) 

The project's own test confirms the residual-lock behavior: a vesting account with 1 `usei` locked keeps that 1 `usei` locked at the direct-cast address after migration, while the 1 spendable `usei` moves to the new `seiAddr`: [4](#0-3) 

And a dedicated unit test documents that vesting accounts at the cast address are explicitly *not* reused/collapsed into the new identity, unlike a plain empty `BaseAccount`: [5](#0-4) 

Because `castAddr` is `sdk.AccAddress(evmAddr[:])` — a hash of an EVM (Keccak-256/secp256k1) public key truncated to 20 bytes and reinterpreted as a Cosmos address — there is no realistic way to construct a Cosmos-native transaction whose signature validates against that address unless the exact same bytes happen to also be a valid secp256k1-derived Cosmos address (astronomically unlikely). Once `SetAddressMapping` reroutes `evmAddr -> seiAddr` and the associated pubkey is attached to `seiAddr`, the `castAddr` vesting account is orphaned: no signer can ever author a transaction from it, so the remaining vesting coins (and any coins that vest afterward) can never be spent, transferred, or withdrawn.

This mirrors the reported bug class precisely: coins that are rightfully owed to a user (unvested-but-committed or eventually-vesting) become permanently frozen because the on-chain state transition (revocation there; association here) severs the user's practical ability to authorize a withdrawal, even though the accounting (locked/vesting balance) still nominally exists.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by an ordinary, unprivileged account holder. Any account that (a) holds a vesting schedule (e.g., team/investor/airdrop vesting grants created via genesis or, historically, `MsgCreateVestingAccount`/`MsgCreatePeriodicVestingAccount`/`MsgCreatePermanentLockedAccount` before the vesting module was deprecated) at the direct-cast address of its EVM public key, and (b) subsequently sends its first plain EVM transaction (a completely routine, expected action) will have any still-locked vesting balance stranded forever at an address no one can sign for. Note that vesting module message handlers are now deprecated and reject new vesting-account creation, but historically created (or genesis-created) vesting accounts remain valid and decodable, and the vulnerability window applies to any address that already holds such a grant.

### Likelihood Explanation
Likelihood is moderate to high in practice: any vested-token holder whose tokens have not yet fully unlocked, and who has not yet interacted with the EVM (a very common flow — many Sei accounts only start using the EVM after already existing on the Cosmos side with genesis/team vesting), will trigger this automatically and silently the first time they send an EVM transaction. No malicious actor is required; the freezing happens as a side effect of the association helper's balance-migration logic, and it happens irrespective of intent.

### Recommendation
`MigrateBalance` should not leave a vesting/locked balance stranded at an address that becomes permanently unspendable once association is performed. Options include:
1. Migrating the entire vesting account (schedule and all) to `seiAddr` instead of only moving the spendable balance, so `seiAddr` inherits the vesting schedule and can claim it as it unlocks.
2. Refusing to associate (or refusing MigrateBalance) while `LockedCoins(castAddr)` is non-zero, until the vesting is fully resolved or explicitly migrated by an admin-controlled path.
3. Alternatively, make the direct-cast address's future signature requirement satisfiable — e.g., allow EVM-signed messages to author transactions on behalf of `castAddr` for as long as it still holds vesting coins.

### Proof of Concept
1. A vesting grant (e.g., `DelayedVestingAccount`/`PeriodicVestingAccount`) is created at `castAddr = sdk.AccAddress(evmAddr[:])` for a user's future EVM address (via genesis or, historically, a vesting-creation message), with `OriginalVesting = 100 usei` and some future `EndTime`.
2. The user later submits any ordinary EVM transaction from the corresponding private key. The `EVMPreprocessDecorator.AnteHandle` path detects the address is not yet associated and calls `AssociateAddresses`, which calls `MigrateBalance` (`utils/helpers/associate.go:57-83`).
3. `MigrateBalance` moves only `SpendableCoins(castAddr)` (0, since all 100 usei are still locked) to `seiAddr`, and because `LockedCoins(castAddr)` is non-zero, does **not** remove the `castAddr` account — the vesting schedule and its 100 usei remain parked there.
4. `evmAddr` is now mapped to `seiAddr`, and the user's pubkey lives on `seiAddr`. No further transaction the user signs can ever originate from `castAddr`.
5. When `EndTime` passes, `LockedCoins(castAddr)` becomes zero and the 100 usei are nominally "spendable," but no one can produce a Cosmos signature that validates against `castAddr` (a Keccak-256-derived EVM address, not a secp256k1-derived Cosmos address), so the 100 usei are permanently unreachable — this is directly demonstrated by `TestMigrateBalance` in `x/evm/ante/preprocess_test.go:423-441`, which shows the locked coin remaining at the EVM cast address after migration.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

func TestMigrateBalance(t *testing.T) {
	k := &testkeeper.EVMTestApp.EvmKeeper
	ctx := testkeeper.EVMTestApp.GetContextForDeliverTx(nil)
	admin, _ := testkeeper.MockAddressPair()
	seiAddr, evmAddr := testkeeper.MockAddressPair()
	k.BankKeeper().AddCoins(ctx, sdk.AccAddress(evmAddr[:]), sdk.NewCoins(sdk.NewCoin("usei", sdk.NewInt(2))), false)
	// set a vesting account of 1
	k.AccountKeeper().SetAccount(ctx, vestingtypes.NewDelayedVestingAccountRaw(
		vestingtypes.NewBaseVestingAccount(
			k.AccountKeeper().NewAccountWithAddress(ctx, sdk.AccAddress(evmAddr[:])).(*authtypes.BaseAccount),
			sdk.NewCoins(sdk.NewCoin("usei", sdk.NewInt(1))), math.MaxInt64, admin),
	))
	associateHelper := helpers.NewAssociationHelper(k, k.BankKeeper(), k.AccountKeeper())
	require.Nil(t, associateHelper.MigrateBalance(ctx, evmAddr, seiAddr, false))
	require.Equal(t, int64(1), k.BankKeeper().SpendableCoins(ctx, seiAddr).AmountOf("usei").Int64())
	require.Equal(t, int64(0), k.BankKeeper().LockedCoins(ctx, seiAddr).AmountOf("usei").Int64())
	require.Equal(t, int64(0), k.BankKeeper().SpendableCoins(ctx, sdk.AccAddress(evmAddr[:])).AmountOf("usei").Int64())
	require.Equal(t, int64(1), k.BankKeeper().LockedCoins(ctx, sdk.AccAddress(evmAddr[:])).AmountOf("usei").Int64())
}

func TestAssociateAddressesDoesNotReuseVestingCastAccount(t *testing.T) {
	ctx := sdk.Context{}
	evmAddr := common.HexToAddress("0x1111111111111111111111111111111111111111")
	castAddr := sdk.AccAddress(evmAddr[:])
	seiAddr := sdk.AccAddress(common.HexToAddress("0x2222222222222222222222222222222222222222").Bytes())
	pubkey := secp256k1.GenPrivKey().PubKey().(*secp256k1.PubKey)

	ak := &mockAccountKeeper{accounts: map[string]authtypes.AccountI{}}
	baseAcc := authtypes.NewBaseAccount(castAddr, nil, 42, 7)
	ak.SetAccount(ctx, vestingtypes.NewDelayedVestingAccount(baseAcc, sdk.NewCoins(sdk.NewInt64Coin("usei", 100)), 123, nil))
	bk := &mockBankKeeper{}
	ek := &mockEVMKeeper{}

	helper := NewAssociationHelper(ek, bk, ak)
	require.NoError(t, helper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false))

	require.Equal(t, 1, ak.newAccountCalls)
	require.Equal(t, evmAddr, ek.mappings[seiAddr.String()])
	acc := ak.GetAccount(ctx, seiAddr)
	require.NotNil(t, acc)
	require.Zero(t, acc.GetAccountNumber())
	require.Zero(t, acc.GetSequence())
	require.Equal(t, pubkey.Bytes(), acc.GetPubKey().Bytes())
}
