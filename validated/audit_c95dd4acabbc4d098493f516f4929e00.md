### Title
Malleable `Payout` tx (SinglePlusAnyoneCanPay covers only input0/output0) lets an attacker mine a garbled-OP_RETURN variant, framing the honest operator as malicious - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds a `Payout` transaction whose sole input is signed by the user with `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . This sighash flag commits only to input0 and output0; it does **not** cover output1 (anchor) or output2 (OP_RETURN with the operator's xonly pubkey), and `ANYONECANPAY` allows arbitrary other inputs to be added. Anyone who observes the mempool/broadcast tx can therefore rebuild a byte-identical-input0/output0 variant with a corrupted or missing OP_RETURN, using the *same* valid witness signature, and get it mined instead of the operator's original.

### Finding Description
Binding claimed broken: `payout_payer_operator_xonly_pk` (recorded by `Verifier::update_finalized_payouts`, core/src/verifier.rs:2319-2328) == the operator that actually fronted `output0` of the mined `Payout` tx.

The user's withdrawal signature is required and verified with `TapSighashType::SinglePlusAnyoneCanPay` both at the operator RPC layer (`core/src/rpc/parser/operator.rs:161-187`, enforced strictly) and at signature-verification time in `Operator::withdraw` (`core/src/operator.rs:630-637`, `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)`). By BIP-341 semantics, `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` commits the signature to exactly one input (the signed one, ignoring all others) and exactly the output at the same index (output0). Outputs at index 1 (anchor, `NON_EPHEMERAL_ANCHOR_AMOUNT`) and index 2 (`op_return_txout(operator_xonly_pk.serialize())`) constructed in `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:418-433) are **not covered** by this sighash. Consequently, once the honest operator's `Payout` tx is broadcast (witness containing the valid `user_sig`), any unprivileged party can extract that witness from the public transaction/mempool and construct an alternate transaction with:
- the same input0 (same outpoint/prevout, same witness/signature — remains valid since the signature does not commit to any other data being unchanged),
- the same output0 (`out_script_pubkey`, `out_amount` as chosen by the withdrawing user — publicly known once the attacker has observed the tx, or even chosen by the attacker itself since the attacker fully controls "the bytes of a withdrawal UTXO"/"an OP_RETURN" per the threat model),
- a garbled or removed OP_RETURN output, and
- extra attacker-funded inputs/outputs (permitted by `ANYONECANPAY`) to raise the fee rate above the honest operator's original.

If this variant is broadcast with a higher fee and confirms before (or replaces via RBF-style race) the honest transaction, it becomes the transaction that actually spends the withdrawal UTXO. `Verifier::update_finalized_payouts` then locates the payout by `bitcoin_syncer_spent_utxos` join on the withdrawal outpoint (`core/src/database/verifier.rs:170-196`) — it identifies the payout purely by *which tx spent the withdrawal UTXO*, not by which tx the honest operator broadcast. It then calls `get_first_op_return_output` and `parse_op_return_data` (circuits-lib/src/bridge_circuit/mod.rs:609-617) on that mined tx; since the OP_RETURN is corrupted/missing, `operator_xonly_pk` parses to `None`, and `update_payout_txs_and_payer_operator_xonly_pk` persists `NULL` (core/src/verifier.rs:2319-2328).

Later, when the honest operator (who genuinely fronted output0) sends its kickoff, `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1859-1915) reads `payout_info` for the deposit's move txid, finds `operator_xonly_pk_opt = None`, logs "assuming malicious", and returns `true` (core/src/verifier.rs:1882-1885) — even though the operator did front the withdrawal. This causes the verifier to treat the honest operator's kickoff as fraudulent, driving a Challenge/Disprove against a legitimate reimbursement claim.

None of the existing guards prevent this: `is_deposit_valid` and `is_profitable` only gate the operator's own decision to send the tx, not what ultimately gets mined; `SECP.verify_schnorr` only checks the (deliberately partial) sighash; there is no on-chain or in-protocol binding tying output2 (OP_RETURN) to output0/input0 beyond the same transaction — and that binding is exactly what `SinglePlusAnyoneCanPay` fails to make cryptographically enforceable.

### Impact Explanation
An honest operator that legitimately fronts a withdrawal can have its later kickoff flagged as malicious by every verifier reading the corrupted payout record, resulting in a Challenge (and potentially Disprove) against that operator's collateral — i.e., an honest operator's collateral is threatened/burned for a payout it did in fact make. This is directly enumerated in the rules as a Critical impact category ("an honest operator's collateral burned"). The attack is repeatable per withdrawal/operator: any withdrawal transaction broadcast by any operator is subject to the same malleability, so the blast radius spans all operators and all deposits using the standard (non-optimistic) `Payout` path.

### Likelihood Explanation
The attacker needs only: (1) observe an operator's broadcast `Payout` transaction (visible in the Bitcoin mempool/P2P network, no privileged access), (2) construct a variant tx with identical input0 witness/signature and identical output0, a corrupted OP_RETURN, and extra self-funded inputs to raise fee/priority, and (3) get it mined first — a purely public, fee-market race requiring no keys, no verifier/operator role, and no majority hashrate (only faster/higher-fee broadcast, which is within normal transaction-relay behavior). This matches the declared unprivileged attacker capabilities exactly ("choose the bytes of a withdrawal UTXO... an OP_RETURN, a script, a witness"). Feasibility depends only on network mempool dynamics/fee bidding, not on any cryptographic break.

### Recommendation
Bind the OP_RETURN (and ideally all outputs) into the signed data actually committed by the withdrawal signature — e.g., require `SIGHASH_ALL` (or a custom commitment covering all outputs) for the payout input signature so any output tampering invalidates the witness, or have the user's off-chain signature/commitment include the operator's xonly pubkey so a garbled OP_RETURN cannot appear in a tx carrying a valid signature. Alternatively, when `update_finalized_payouts` finds no valid OP_RETURN, it should not treat this ambiguously the same as "optimistic payout" for purposes of `is_kickoff_malicious`; instead, cross-check whether an operator later claims/kickoffs for that deposit and require stronger evidence (e.g., verifying the confirmed output0 destination/amount matches a known operator-submitted `withdraw()` request, and only flag malicious if no operator's committed data matches) before assuming maliciousness.

### Proof of Concept
```
cargo test --package clementine-core payout_op_return_malleability_regtest -- --nocapture
```
Test plan (regtest):
1. Set up a deposit/withdrawal as in existing e2e flow (`core/src/test/deposit_and_withdraw_e2e.rs`).
2. Honest operator (`op_pk`) calls `Operator::withdraw` to build/broadcast the real `Payout` tx with `SinglePlusAnyoneCanPay` signature (per `core/src/operator.rs:560-637`), holding the transaction/witness from the RPC layer instead of relying on automatic broadcast.
3. From the same signed witness, construct a second `Payout`-shaped transaction with identical input0 (outpoint + witness) and identical output0, but replace/garble output2's OP_RETURN push (or drop it), add one extra attacker-owned funding input (ANYONECANPAY permits this) and bump the fee.
4. Broadcast the attacker's variant first and mine it (regtest `generate`), asserting it (not the honest tx) is the one confirmed at the withdrawal outpoint via `get_txid_where_utxo_is_spent`.
5. Run `update_finalized_payouts` (via normal verifier sync) and assert, on the DB (`get_payout_info_from_move_txid`), that `operator_xonly_pk_opt == None` for the withdrawal's move txid.
6. Have the honest operator send its kickoff for this deposit; call `Verifier::is_kickoff_malicious` directly and assert it returns `true`.
7. Assert that a `Challenge` transaction is queued/dispatched against `op_pk`'s kickoff despite `op_pk` having genuinely funded `output0`.

Both sides of the binding are checked: before the attack, `payout_payer_operator_xonly_pk == Some(op_pk)` would have matched the actual funder; after the attack, the stored value is `None`, breaking the equality and triggering the false-malicious verdict.
