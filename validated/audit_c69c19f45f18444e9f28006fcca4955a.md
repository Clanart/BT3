### Title
Silent-swallowed reward-processing error lets a relayer double-claim consensus incentive rewards - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` calls `Self::process_message(...)` and discards any error with `let _ = ...` [1](#0-0) . Inside `process_message`, the relayer reward is transferred from the treasury **before** the reputation mint and the `LastRewardedHeight` watermark update [2](#0-1) . If the reputation mint fails (e.g. `T::ReputationAsset::mint_into` returning `BelowMinimum`/frozen-account errors, exactly the "typically a frozen asset" failure mode documented for the sibling pallet), the function returns `Err(ReputationMintFailed)` *after* the currency transfer already executed but *before* `LastRewardedHeight` is advanced. Because the caller discards this error and returns `Ok(...)` unconditionally, the treasury payment is never rolled back and the watermark used to prevent re-paying the same block span is never moved forward. This is the same bug class as the OAppLzReceive report: a downstream failure condition (a frozen/blocked account) is absorbed instead of propagated, letting state advance inconsistently with the actual asset movement.

### Finding Description
`process_message` performs, in order:
1. `T::Currency::transfer(treasury -> relayer, reward, ...)` [3](#0-2) 
2. `Self::deposit_event(RelayerRewarded ...)` [4](#0-3) 
3. `T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into()).map_err(|_| Error::<T>::ReputationMintFailed)?` [5](#0-4) 
4. `LastRewardedHeight::<T>::mutate(...)` — only reached if step 3 succeeds [6](#0-5) 

`on_executed` invokes this per state machine with `let _ = Self::process_message(...)`, discarding the `Result` [1](#0-0) , and always returns `Ok(PostDispatchInfo { ... })` [7](#0-6) . There is no `#[transactional]` wrapper around `process_message`, so an early `?` return there does not undo the storage mutations already committed by earlier steps in the same call (the currency `transfer` and the event deposit are non-reverting once made, since only the *outer* dispatchable's own top-level error would trigger storage rollback, and here the outer `FeeHandler::on_executed` never returns an error).

`calculate_reward` computes the payable block span using the watermark as the baseline: `baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height)`, and `reward = (latest_height - baseline) * block_cost` [8](#0-7) . If the watermark is never advanced (because step 3 kept failing), then on every subsequent consensus proof for that `state_machine_id`, the same relayer is paid again for the same already-rewarded block range — the amount even grows, since `latest_height` keeps increasing while `baseline` is stuck.

The `relayer_account` credited is recovered purely from the sr25519 signature embedded in the consensus message (`Signature::decode(...).verify_and_get_sr25519_pubkey(...)`) [9](#0-8) , i.e. it is whatever account the message signer chose. A relayer can pick a `T::ReputationAsset` account that is guaranteed to fail minting (e.g. a fresh account below the reputation asset's existential/minimum balance, or one that never receives the asset's provider reference), causing `mint_into` to fail deterministically on every reward cycle while `T::Currency::transfer` (the actual treasury payout) continues to succeed every time.

### Impact Explanation
This produces unbounded, repeated payouts from the protocol treasury for the same block span of consensus updates — a direct "double-claim/double-settlement" of relayer rewards, explicitly listed as an in-scope impact. Because the failure condition (mint failure on a chosen/undertfunded reputation account) is fully within the relayer's control and requires no special privilege beyond normal participation in submitting valid consensus proofs, the treasury can be drained over repeated legitimate-looking consensus submissions.

### Likelihood Explanation
The precondition — causing `T::ReputationAsset::mint_into` to fail for a chosen account while `T::Currency::transfer` for the same account succeeds — is realistic and low-cost: it only requires selecting/using an account that does not meet the reputation asset's minimum-balance/creation requirements (a common `pallet-assets` failure mode), which is a normal, permissionless account-selection choice rather than a compromised admin or malicious peer assumption. The bug is deterministic and repeatable on every subsequent consensus message batch.

### Recommendation
- Do not discard the `Result` of `process_message` in `on_executed`; propagate or explicitly handle the failure.
- Perform the reputation mint and watermark update atomically with (or before) the currency transfer, e.g. wrap `process_message` in `#[frame_support::transactional]` so a mint failure rolls back the treasury transfer, or reorder operations so `LastRewardedHeight` is only advanced (and the transfer only executed) after all steps are guaranteed to succeed.
- Alternatively, decouple reward accounting from `ReputationAsset::mint_into` entirely so that a mint failure never blocks or duplicates the currency payout / watermark advance.

### Proof of Concept
1. A relayer prepares consensus messages signed such that the recovered `relayer_account` is an account that is guaranteed to fail `T::ReputationAsset::mint_into` (e.g. an account with zero prior balance in the reputation asset, below its minimum balance / existential deposit).
2. Relayer submits a valid consensus proof advancing `state_machine_id` to `height_1`. `on_executed` → `process_message`: `Currency::transfer` pays the reward to `relayer_account` and emits `RelayerRewarded`; `mint_into` fails with `ReputationMintFailed`; the error is swallowed by `let _ = ...`; `LastRewardedHeight` is **not** updated.
3. Relayer submits another valid consensus proof advancing the same `state_machine_id` to `height_2`. `calculate_reward` again uses the old/unchanged `baseline`, computing a reward covering blocks already paid in step 2 (plus new blocks), and `Currency::transfer` pays it again.
4. Repeating steps 2–3 lets the relayer collect payment for the same historical block span an unbounded number of times, draining `T::TreasuryAccount`.
