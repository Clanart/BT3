### Title
`ReceivedOutput::read` accepts an unbound scalar offset, letting untrusted bytes report funds as received/spendable under the wrong key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The WSHIDO bug class is an authorization check gated on the wrong predicate (`allowance != 0` instead of `allowance >= amount`), so the security-relevant validation is skipped while the state-changing operation proceeds. The Serai analog is in `ReceivedOutput::read`: a `ReceivedOutput` couples a scalar `offset` with a `TxOut`/`OutPoint`, and the whole security model of the scanner/wallet is that `key + G*offset` is the Taproot internal key behind `output.script_pubkey` (this is exactly how `Scanner::scan_transaction` constructs the value legitimately, `networks/bitcoin/src/wallet/mod.rs:205-211`). However, `ReceivedOutput::read` (`mod.rs:122-134`) deserializes the offset, the `TxOut`, and the `OutPoint` as three independent fields and never checks that the offset actually derives the output's `script_pubkey`. Untrusted bytes therefore produce a semantically invalid `ReceivedOutput` that downstream code treats as a spendable received output.

### Finding Description
`Scanner::register_offset`/`scan_transaction` guarantee an invariant: for every `ReceivedOutput` they emit, `p2tr_script_buf(self.key + G*offset) == output.script_pubkey`, i.e. the offset is the HDKD tweak that makes the output spendable by the threshold key (`mod.rs:180-214`). `ReceivedOutput::read` reconstructs the same type from a byte stream with only syntactic checks: `Secp256k1::read_F` for the offset, `TxOut::consensus_decode`, `OutPoint::consensus_decode` — and returns `Ok` unconditionally (`mod.rs:122-134`). There is no verification that `output.script_pubkey == ScriptBuf::new_p2tr_tweaked(key + G*offset)` nor that the `outpoint` actually exists/pays that output. The reader doesn't even take the wallet key, so the binding cannot be recovered post-hoc from the type. Any consumer that receives a serialized `ReceivedOutput` (the type exposes `serialize`/`read` precisely for transport/storage, `mod.rs:120-148`) and feeds it into the spend path (`send.rs` builds transactions/sighashes from `ReceivedOutput`s) will compute the spending key as `group_key + offset` while the actual UTXO pays to a different script — the analog of WSHIDO debiting an arbitrary `src`.

### Impact Explanation
An unprivileged party who can supply `ReceivedOutput` bytes to a wallet/scanner consumer can cause funds to be reported received that are not spendable: the output either isn't ours (wrong script for the claimed offset) or the `outpoint` doesn't reference it. The processor will treat the output as a spendable input — attempting to sign for a nonexistent/incorrectly-keyed UTXO (wasted signing sessions, stalled spends, or accounting an attacker-owed deposit as credited value that can never be moved). Because the offset is fully attacker-chosen and unchecked, the discrepancy is silent: every field is individually well-formed.

### Likelihood Explanation
Reachability is exactly the sanctioned surface: untrusted bytes fed to `ReceivedOutput::read`. Exploitation requires a consumer that accepts externally-supplied serialized `ReceivedOutput`s rather than only self-produced `Scanner` output — a plausible integration pattern given the public read/serialize API — and no consensus on-chain confirms the tuple. It does not require key leakage, collusion, or malformed curve encodings.

### Recommendation
Either bind the offset at deserialization time (change `read` to take the wallet `ProjectivePoint` and reject unless `p2tr_script_buf(key + G*offset) == Some(output.script_pubkey)`), or make the invariant type-level: only `Scanner` may construct `ReceivedOutput` (private fields already enforce this — keep it that way) and document that `read` must only be used on bytes previously produced by `Scanner::scan_*` for the same key; additionally, consumers should confirm the `outpoint`/`TxOut` against chain data before spending.

### Proof of Concept
Conceptual, using the public API:

```rust
// Attacker-controlled bytes: valid encoding, wrong binding
let our_key: ProjectivePoint = ...;            // threshold wallet key (even Y after tweak)
let victim_offset = Scalar::ONE;
// A TxOut paying to a *different* script (e.g. attacker's own address,
// or p2tr(our_key + G*2) while we claim offset 1)
let fake = ReceivedOutput {
    offset: victim_offset,                     // via serialization, not the private field
    output: TxOut { value: Amount::from_sat(100_000), script_pubkey: attacker_script },
    outpoint: OutPoint::null(),
};
let bytes = fake.serialize();
let decoded = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // succeeds
// decoded.offset() == 1, but our_key + G*1 does not match attacker_script:
// downstream spend logic will derive the wrong internal key and produce a
// signature for a UTXO we do not control — reported received, unspendable.
```

Uncertainty note: exploitability hinges on an integration path where serialized `ReceivedOutput`s cross a trust boundary; within `Scanner`-only usage the invariant holds by construction. The code defect (no offset↔script binding in `read`) is verified at `networks/bitcoin/src/wallet/mod.rs:122-134` against the construction invariant at `mod.rs:185-211`.
