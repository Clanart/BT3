### Title
Bank precompile `sendNative` bypasses `SendEnabled` check enforced by native `MsgSend` - (File: precompiles/bank/bank.go)

### Summary
The `MsgSend`/`MsgMultiSend` handlers in `sei-cosmos/x/bank/keeper/msg_server.go` enforce `IsSendEnabledCoins` before moving funds, but the EVM `bank` precompile's `sendNative` method transfers `usei`/`wei` directly through `BankKeeper.SendCoinsAndWei`, which never calls `IsSendEnabledCoins`. This mirrors the reported bug class: a state-gating check (pause/disable) exists on one entry point but is missing on another entry point that reaches the same underlying value-transfer logic.

### Finding Description
`msgServer.Send` explicitly calls `k.IsSendEnabledCoins(ctx, msg.Amount...)` before calling `SendCoins`: [1](#0-0) 

However, the bank precompile's `sendNative` (reachable from any EVM contract call at address `0x...1001`) moves `usei`/`wei` value directly via `p.bankKeeper.SendCoinsAndWei`, with no `IsSendEnabledCoins` check anywhere in the call path: [2](#0-1) 

`SendCoinsAndWei` itself, in `BaseSendKeeper`, only manipulates wei/usei balances via `SubWei`/`AddWei`/`SendCoinsWithoutAccCreation` and never consults `IsSendEnabledCoins`/`GetParams().SendEnabledDenom`: [3](#0-2) 

By contrast, `IsSendEnabledCoins`/`IsSendEnabledCoin` exist specifically to gate transfers per-denom via governance-controlled `SendEnabled`/`DefaultSendEnabled` params: [4](#0-3) 

The precompile's `send` method (ERC20-pointer-gated token sends) *does* go through `bankMsgServer.Send`, which enforces the check: [5](#0-4) 

But `sendNative`, used for native `usei` value transfers attached to EVM calls (`msg.value`), completely skips this gate.

### Impact Explanation
If governance or an operator disables `usei` sends (`SendEnabled=false` for the base denom, e.g., during an incident response or a chain-level "pause" of native transfers), any EVM account can still move `usei`/`wei` value between accounts by calling the `bank` precompile's `sendNative` method with non-zero `msg.value`. This is a real fund-movement bypass of an on-chain compliance/pause control reachable by any unprivileged EVM caller, functionally identical to the reported `OptimismPortal.depositTransaction` bypassing `whenNotPaused`.

### Likelihood Explanation
Requires only a standard EVM transaction/contract call to the bank precompile with a non-zero value — no special privileges, and the precompile is part of the default-configuration public EVM surface. The condition for the impact to matter (base-denom `SendEnabled=false`) is operator/governance-controlled, but once set, the bypass is trivially and immediately exploitable by any user.

### Recommendation
Add an `IsSendEnabledCoins` (or equivalent `IsSendEnabledCoin` for the base denom) check in `PrecompileExecutor.sendNative` before calling `SendCoinsAndWei`, matching the check already performed in `msgServer.Send`. Alternatively, move the enforcement into `BaseSendKeeper.SendCoinsAndWei`/`AddWei`/`SubWei` so all callers (native message server and precompiles alike) are consistently gated.

### Proof of Concept
1. Governance (or default params) sets `SendEnabled=false` (or removes usei from the enabled list) for the base denom `usei` via bank module params.
2. Any EOA submits a normal `MsgSend` transferring `usei` — it fails with `ErrSendDisabled` as expected (`sei-cosmos/x/bank/keeper/msg_server.go` line 29-31).
3. The same EOA instead calls the `bank` precompile at `0x0000000000000000000000000000000000001001`'s `sendNative(receiverAddr)` method with `msg.value` set to the amount of usei/wei to send.
4. `PrecompileExecutor.sendNative` (`precompiles/bank/bank.go` lines 251-309) proceeds to call `p.bankKeeper.SendCoinsAndWei` directly, successfully transferring the funds — bypassing the pause entirely.

// IsSendEnabledCoins checks the coins provide and returns an ErrSendDisabled if
// any of the coins are not configured for sending.  Returns nil if sending is enabled
// for all provided coin
func (k BaseSendKeeper) IsSendEnabledCoins(ctx sdk.Context, coins ...sdk.Coin) error {
	for _, coin := range coins {
		if !k.IsSendEnabledCoin(ctx, coin) {
			return sdkerrors.Wrapf(types.ErrSendDisabled, "%s transfers are currently disabled", coin.Denom)
		}
	}
	return nil
}

// IsSendEnabledCoin returns the current SendEnabled status of the provided coin's denom
func (k BaseSendKeeper) IsSendEnabledCoin(ctx sdk.Context, coin sdk.Coin) bool {
	return k.GetParams(ctx).SendEnabledDenom(coin.Denom)
}

func (k BaseSendKeeper) SendCoinsAndWei(ctx sdk.Context, from sdk.AccAddress, to sdk.AccAddress, amt sdk.Int, wei sdk.Int) error {
	if err := k.SubWei(ctx, from, wei); err != nil {
		return err
	}
	if err := k.AddWei(ctx, to, wei); err != nil {
		return err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeWeiTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, to.String()),
			sdk.NewAttribute(types.AttributeKeySender, from.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, wei.String()),
		),
	})
	if amt.GT(sdk.ZeroInt()) {
		return k.SendCoinsWithoutAccCreation(ctx, from, to, sdk.NewCoins(sdk.NewCoin(sdk.MustGetBaseDenom(), amt)))
	}
	return nil
}
