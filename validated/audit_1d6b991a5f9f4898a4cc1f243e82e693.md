### Title
Unrecovered `Dec.Quo` overflow panic in oracle `MidBlocker` cross-rate finalization causes validator crash / chain halt - (File: `x/oracle/abci.go`)

### Summary
The reported PHP EXIF bug is a classic "unchecked arithmetic operation on attacker-controlled input causes a hard runtime fault." The Sei oracle module has an analogous pattern: `sdk.Dec.Quo` performs a fixed-point division and calls `assertInValidRange()` on the result, which `panic`s if the quotient falls outside the ~256-bit decimal range. Validator-submitted exchange-rate votes flow into this division during every `MidBlocker` cross-rate computation. One call site guards this panic with `recover()`, but a second, later call site in the same code path does not.

### Finding Description
In `x/oracle/types/ballot.go`, `ToCrossRate` explicitly wraps the `Quo` call in a `recover()` because "Quo will panic on overflow": [1](#0-0) 

However, `x/oracle/abci.go`'s `MidBlocker` performs a second, structurally identical `Quo` operation on the **same class of validator-submitted values** — combining the reference-denom weighted median (`exchangeRateRD`, itself an unrecovered vote-derived `sdk.Dec`) with the per-denom tallied `exchangeRate` — with **no recover**: [2](#0-1) 

`Dec.Quo` computes `chopPrecisionAndRound(quo)` and then calls `result.assertInValidRange()`, which panics if the value exceeds the valid Dec bit-length bound (analogous to the EXIF bug's unguarded division producing an out-of-range/trap result): [3](#0-2) 

The existing test `TestOverflowAndDivByZero` only exercises the case where the *reference-denom* ballot itself overflows (via `WeightedMedianWithAssertion`) or where `ToCrossRate`'s protected `Quo` call panics — both of those are wrapped in `defer/recover` blocks already. It does **not** cover the scenario where `Tally()` (called after the recovered `ToCrossRateWithSort`) returns a legitimate, non-overflowing per-denom `exchangeRate`, but the subsequent unprotected `exchangeRateRD.Quo(exchangeRate)` at `x/oracle/abci.go:94` overflows independently — e.g., when `exchangeRateRD` (reference-denom price) is extremely large and `exchangeRate` (target-denom cross rate) is extremely small, driving the quotient beyond `Dec`'s valid range.

### Impact Explanation
`MidBlocker` runs unconditionally for every validator node at the end of each oracle vote period. An unrecovered panic here is not contained by a per-message ante/msg-handler recover; it propagates up through the ABCI `EndBlock`/`MidBlock` call chain and crashes the node process (or, if handled generically by Cosmos SDK's `runTx`-level recover — which does *not* wrap `BeginBlock`/`MidBlocker`/`EndBlocker` — the node halts). Since all honest validators execute `MidBlocker` deterministically on the same votes, a crafted vote set causing this panic would crash **every validator simultaneously**, producing a full chain halt — a High-severity impact analogous to (but worse than, since it's chain-wide instead of single-process) the original EXIF SIGFPE crash.

### Likelihood Explanation
Oracle price votes are periodically submitted by whitelisted validators (`x/oracle` feeder accounts), not arbitrary unprivileged users, so triggering this requires control of (or collusion among) enough voting power to set a denom's aggregate vote to extreme values and get past `pickReferenceDenom`/threshold checks. The `TestOverflowAndDivByZero` test demonstrates the team is aware of and has attempted to guard overflow/divide-by-zero cases in this exact code path, but the guard was applied inconsistently (`ToCrossRate` recovers, the abci.go `Quo` call site does not), suggesting the gap is a genuine oversight rather than an intentionally accepted risk.

### Recommendation
Wrap the `exchangeRateRD.Quo(exchangeRate)` call in `x/oracle/abci.go` (line 94) with the same `defer/recover` pattern already used in `ExchangeRateBallot.ToCrossRate`, treating an overflow result as "skip this denom" (consistent with the existing zero-exchange-rate skip logic), rather than allowing the panic to propagate out of `MidBlocker`.

### Proof of Concept
1. Configure the oracle whitelist with the reference denom and a second denom.
2. Have voting validators submit an aggregate vote for the reference denom with an extremely large (but in-range) `sdk.Dec` value, and for the target denom a value chosen so that `Tally()`'s returned `weightedMedian` for the target denom (after `ToCrossRateWithSort`, which safely recovers from its own internal overflow) is a small nonzero in-range `Dec`.
3. When `MidBlocker` reaches `exchangeRate = exchangeRateRD.Quo(exchangeRate)` (`x/oracle/abci.go:94`), the division of the very large reference rate by the very small target rate overflows `Dec`'s valid range, and `assertInValidRange()` panics without a surrounding recover, crashing `MidBlocker` execution on every validator.

*(Note: exact numeric thresholds needed to overflow `Dec`'s ~2^315-bound while keeping `exchangeRateRD` and post-tally `exchangeRate` individually valid were not empirically re-derived here beyond the pattern already demonstrated by `TestOverflowAndDivByZero`; a background engineer should extend that test to specifically target the `abci.go:94` call site to confirm exploitability precisely.)*

// quotient
func (d Dec) Quo(d2 Dec) Dec {
	// multiply precision twice
	mul := new(big.Int).Mul(d.i, precisionReuse)
	mul.Mul(mul, precisionReuse)

	quo := new(big.Int).Quo(mul, d2.i)
	chopped := chopPrecisionAndRound(quo)
	result := Dec{chopped}
	result.assertInValidRange()
	return result
}
