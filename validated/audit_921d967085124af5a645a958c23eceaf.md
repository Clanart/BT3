## Finding

### Title
Missing duplicate-token validation in Tron `IntentGatewayV2.placeOrder` re-introduces the escrow-bucket-collision bug already patched in the mainline EVM contract - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core invariant break is: when two logically-distinct "slots" (token1/token2) are allowed to alias to the same underlying key, per-slot accounting collapses into a single shared balance and downstream withdraw/refund math becomes wrong, stranding or misdirecting funds. Hyperbridge's `IntentGatewayV2` escrow uses exactly this pattern — a `mapping(bytes32 => mapping(address => uint256)) _orders` keyed by `(commitment, token)` — and the mainline EVM implementation had to add an explicit duplicate-token rejection to `placeOrder` after discovering that repeated token legs in `order.inputs`/`order.output.assets` collapse into one `_orders[commitment][token]` bucket, corrupting per-leg partial-fill and withdrawal accounting. That fix (and its regression tests) exists only in the primary EVM contracts; the separately-maintained Tron fork implements the same bucket pattern without the guard.

### Finding Description
In the mainline EVM `IntentGatewayV2` (`IntrinsicIntents.sol`/`IntentsBase.sol`), the escrow is keyed only by `(commitment, token)`: [1](#0-0) 

Two input or output legs referencing the same token address share one bucket in this mapping. This was a real, exploitable bug — confirmed by dedicated regression tests explicitly describing it as "same-chain partial fills over-release repeated input escrow" and duplicate output legs that "share one `_partialFills` bucket": [2](#0-1) [3](#0-2) 

The fix was to reject any order containing duplicate input or duplicate output token addresses at `placeOrder` time with `IntentsBase.InvalidInput`.

The Tron deployment target, `evm/tron/contracts/apps/IntentGatewayV2.sol`, is a separate, non-inheriting reimplementation of the same escrow model — same `_orders[commitment][token] += ...` accumulation pattern in `placeOrder`: [4](#0-3) 

and the same per-token merged balance decremented on withdrawal: [5](#0-4) 

Unlike the patched mainline `placeOrder`, this loop only checks `order.inputs[i].amount == 0` before accumulating into the shared bucket — there is no check rejecting a repeated `token` address across `order.inputs` (or across `order.output.assets`, consumed elsewhere for fills). This reproduces exactly the class of bug the mainline EVM contract had to add a dedicated guard for.

### Impact Explanation
Because `_orders[commitment][token]` merges amounts across any legs sharing the same token, per-leg proportional accounting (partial fills, per-leg refund/cancel amounts, per-leg withdrawal in `withdraw()`) computed independently for each duplicated leg can diverge from the single merged on-chain balance. This is the same invariant break as `DoubleTokenLexscrow`: distinct logical slots collapsing into one physical balance leads to over-release (attacker/solver extracts more than one leg's true escrow) or under-release/lock (remaining legs can never be redeemed because the shared bucket was already zeroed by an earlier leg's withdrawal), i.e. loss or lock of user funds and incorrect settlement amounts — squarely within the bounty's "stealing or loss of funds" / "transaction manipulation" impact categories.

### Likelihood Explanation
Triggering the condition requires nothing more than an ordinary, unprivileged user placing an order on Tron with two input (or two output) legs that use the same token address — a normal, permissionless call to `placeOrder`. No relayer, prover, admin, or malicious peer is required, matching the "public-entrypoint, unprivileged attacker" requirement. The bug class has already been proven real and worth fixing in the mainline EVM contract (via the referenced regression tests), so the underlying accounting flaw is not hypothetical — only the guard preventing it is missing from the Tron variant.

### Recommendation
Port the same duplicate-token rejection used in the mainline `IntentsBase`/`IntrinsicIntents` `placeOrder` path (reverting with an `InvalidInput`-equivalent error) into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, checking both `order.inputs` and `order.output.assets` for repeated token addresses before any escrow accounting occurs.

### Proof of Concept
1. On the Tron deployment, call `placeOrder` with `order.inputs = [{token: USDC, amount: 700}, {token: USDC, amount: 300}]`.
2. The loop at `evm/tron/contracts/apps/IntentGatewayV2.sol:445-462` accepts both legs (no duplicate check), transferring 1000 USDC total from the user and setting `_orders[commitment][USDC] = 1000`.
3. Any downstream logic that treats the two input legs as independently accounted (e.g., per-leg cancellation/refund amounts, or a withdrawal request whose `body.tokens` array is built per original leg rather than per unique token) operates against a single merged 1000 balance instead of two independent 700/300 balances, allowing a leg's withdrawal to zero out or exceed the balance intended for the other leg — producing either an over-release (fund theft) or a stuck leftover balance (fund lock), depending on the order of leg processing.         address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
