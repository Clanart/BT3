### Title
`resolveWithin` containment check uses an unanchored string prefix, allowing repo-path escape via crafted deep-link `filepath` - ([File: app/src/lib/path.ts])

### Summary
The self-liquidation bug's underlying pattern is a boundary/eligibility check that is computed against a *broader* value than the one that actually defines the safe/allowed range (`getTotalDebt()` instead of `faceValue`), letting an attacker-influenced value slip past a check that looks correct but isn't tight enough. Desktop's `_resolveWithin` helper — the app-wide "is this path still inside the repo root" guard — has the same class of flaw: it verifies containment with a raw string `startsWith(realRoot)` instead of verifying a path-segment boundary, so a resolved path in a sibling directory whose name merely shares the root path as a string prefix passes the check as if it were "inside" the repository.

### Finding Description
`_resolveWithin` computes the real, symlink-resolved root and target paths and then decides containment purely by string prefix: [1](#0-0) 

```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of a path separator boundary. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo` and the resolved target is `/Users/victim/Documents/GitHub/myrepo-secrets/passwords.txt`, the latter string literally starts with the former, so the function returns the escaped path as "safely resolved" even though it is a completely different, sibling directory.

This helper is reused as the app's general-purpose path-containment gate. One reachable, fully attacker-controlled call site is the "Open Repository from URL" deep-link handler: [2](#0-1) 

The `filepath` parameter comes directly from a `x-github-client://` deep link that a user is enticed to click (e.g. embedded in a webpage, README, or crafted "Open in Desktop" link) — the report's "link or deep link the user clicks" category. The code rejects absolute paths (`isAbsolute(filepath)`) but otherwise trusts `resolveWithin(repository.path, filepath)` to keep the result inside the repo:

```
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
}
```

By supplying a relative `filepath` such as `../myrepo-secrets/id_rsa` (where the opened/cloned repository directory is named `myrepo`), an attacker can make the resolved absolute path land in a sibling directory (`myrepo-secrets`) that merely shares the `myrepo` prefix, while `_resolveWithin`'s unanchored `startsWith` check still reports it as contained.

### Impact Explanation
The corrupted value is the boolean containment decision returned by `_resolveWithin` — it is `true` (non-null) for paths that are provably outside the intended root whenever a sibling file/directory name happens to share the root directory's name as a prefix (a common occurrence for project variants like `repo`, `repo-backup`, `repo-old`, `repo2`, cloned forks, etc., or attacker-created directories). The affected call site (`openRepositoryFromUrl`) uses the escaped path to call `shell.showItemInFolder`, which opens the OS file manager and reveals/highlights an arbitrary file elsewhere on disk outside the repository — a "file read/reveal outside the repo" driven entirely by an attacker-controlled deep link, matching the report's valid-impact bar. Because `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are exported as the project's canonical safe-path primitive, any other current or future consumer that trusts it for a write (not just a reveal) would inherit the same escape.

### Likelihood Explanation
The existing regression tests for `resolveWithin` only cover `..` traversal, null bytes, absolute paths, and symlink escapes — none test the "sibling directory with a shared name prefix" case: [3](#0-2) 

so the gap is unnoticed by the current test suite. Triggering it requires no local access, no elevated privileges, and no prior compromise — only that the victim click a specially crafted GitHub Desktop deep link while having (or being tricked into cloning) a repository whose directory name is a prefix of another path on disk, which is a realistic naming pattern (`project`, `project-backup`, `project.wiki`, `project-old`).

### Recommendation
Change the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require a true path-segment boundary, e.g.:
```
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the same `join`/`resolve`/`normalize` implementation's separator (POSIX `/` or Windows `\`), and add a regression test asserting that a sibling path such as `<root>-evil/file` is rejected even though it shares `<root>` as a string prefix.

### Proof of Concept
1. Clone/open a repository at `/Users/victim/Documents/GitHub/myrepo`.
2. Have (or create, e.g. via a separate clone) a sibling directory `/Users/victim/Documents/GitHub/myrepo-secrets/passwords.txt`.
3. Get the victim to click a deep link of the form:
   `x-github-client://openRepo/0/0/0/0?url=<repo-url>&filepath=..%2Fmyrepo-secrets%2Fpasswords.txt`
4. `openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1940-1973`) resolves the repository, rejects the filepath only for being absolute, then calls `resolveWithin(repository.path, filepath)`.
5. Inside `_resolveWithin` (`app/src/lib/path.ts:36-72`), `resolve()` produces `/Users/victim/Documents/GitHub/myrepo-secrets/passwords.txt`; `realResolved.startsWith(realRoot)` evaluates `true` because the string `myrepo-secrets` starts with `myrepo`.
6. `shell.showItemInFolder(resolved)` opens the OS file browser highlighting `passwords.txt`, a file entirely outside `myrepo`, despite the "containment" guard reporting success.

```typescript
  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
```

```typescript
  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
      assert.equal(await resolveWithin(parent, root), root)
    })
```
