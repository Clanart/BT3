### Title
Scanner reports outputs below the spendable threshold as received funds — dust outputs credited but economically unspendable — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
Analogous to the yAxis report where a withdrawal silently returns nothing while consuming the user's shares, `Scanner::scan_transaction` reports every output paying to a registered script as a spendable `ReceivedOutput` with no check on the output's value. An unprivileged sender can pay outputs whose value is below the cost to spend them (below `DUST`/the input's ~57-vbyte spend cost) to a Serai multisig address. The scanner reports these as received funds, yet `SignableTransaction::new` accepts them as inputs and will burn their entire value as fee (or, when change is present but leftover is `< DUST`, silently fold the remainder into the fee). Funds are therefore reported received that are not spendable, exactly the "deposited value that yields zero recoverable value" class from the report.

### Finding Description
`scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` matches solely on `output.script_pubkey` and pushes a `ReceivedOutput` for any matching output, regardless of `output.value`. There is no floor check anywhere in the wallet layer: `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) sums `inputs` blindly, only errors if `input_sat < payment_sat + needed_fee`, and treats any leftover under `DUST` (546) as additional fee without signaling the caller (`send.rs:223-235`). The only `DUST` guard is on *payments* (`send.rs:165-169`), not on received inputs. So a sub-dust or marginally-above-dust output is credited by the scanner yet cannot be spent without losing its full value to fees — economically unspendable while indistinguishable from real balance.

### Impact Explanation
Any Bitcoin user can send a transaction paying a dust-valued output (e.g., a few hundred sats) to the multisig's P2TR script (or any registered offset script). The scanner reports it as a received output; downstream accounting treats it as balance, but spending it requires more fee than it contributes, so including it as an input yields zero net value — the output is consumed while contributing nothing, mirroring the "burn shares, receive nothing" failure. It also enables deposit-of-record inflation: balance is reported that can never be recovered.

### Likelihood Explanation
Reachable by any unprivileged party with public transaction data — no validator key, collusion, or RPC access needed; just a standard Bitcoin payment to a known Serai address/offset script. Cost to the attacker is only the dust amount plus one transaction fee. Constrained to amounts below ~10,000 sats per output, so severity is Medium rather than High.

### Recommendation
Enforce the network `DUST` floor (or the per-input spend cost, ~285 sats at 5 sat/vbyte per the `DUST` rationale in `processor/src/networks/bitcoin.rs`) inside `Scanner::scan_transaction`/`scan_block`, dropping or separately flagging outputs whose value cannot cover their own spend, rather than returning them as spendable `ReceivedOutput`s.
