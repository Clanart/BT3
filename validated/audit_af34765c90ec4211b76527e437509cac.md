## Title
WERC20 precompile permanently locks native tokens sent via `msg.value` on non-deposit calls (`withdraw`, `transfer`, `approve`, `transferFrom`, queries) - (File: precompiles/werc20/werc20.go)

### Summary
The external report describes `TokenVesting`'s naive `payable` `receive`/`fallback` trapping ETH with no withdraw path. The Cosmos EVM analog is the `WERC20` precompile (`precompiles/werc20/werc20.go`), which wraps the base ERC-20 precompile but **overrides `Execute` without the base precompile's value-rejection guard**. Only the `deposit`/`fallback`/`receive` code path routes `contract.Value()` back to the caller; every other method (`withdraw`, `transfer`, `approve`, `transferFrom`, and view methods) silently accepts attached native value and never returns it, permanently locking those funds in the precompile's underlying bank account.

### Finding Description
The base ERC-20 precompile explicitly guards against receiving native value on any method: [1](#0-0) 

This check exists precisely because "ERC20 precompiles cannot receive funds because they are not managed by an EOA and will not be possible to recover funds sent to an instance of them."

However, `WERC20.Execute` completely replaces this logic and only special-cases the `deposit`/`fallback`/`receive` paths; all other methods (including the `withdraw` no-op and the inherited ERC-20 `transfer`/`approve`/`transferFrom`/query methods routed through `HandleMethod`) are dispatched with no check on `contract.Value()`: [2](#0-1) 

`Withdraw` itself never inspects or moves `contract.Value()` — it is documented as a no-op that only validates balance and emits an event: [3](#0-2) 

Only `Deposit` routes the attached native coins back to the caller: [4](#0-3) 

Critically, native value attached to any EVM call to the precompile is applied to the precompile's account balance in `StateDB` (via the ordinary EVM value-transfer mechanism) and is flushed to the real Cosmos SDK bank balance **before** the precompile's native (Go) logic runs: [5](#0-4) 

Because Solidity's `payable` modifier is only a compile-time restriction, an attacker can bypass it entirely with a raw low-level call, e.g. `address(WERC20).call{value: 1 ether}(abi.encodeWithSignature("withdraw(uint256)", 0))` or `...transfer(to, amount)`. The EVM will transfer the value into the precompile's account, `CommitWithCacheCtx` commits that value into the real bank balance of `sdk.AccAddress(precompileAddr.Bytes())`, and then `Withdraw`/`Transfer`/etc. execute without ever moving that attached value anywhere. There is no method that lets anyone sweep the WERC20 precompile account's residual native balance back out — `Deposit` only returns the exact `contract.Value()` of the *current* call, not any pre-existing balance sitting in the precompile's account from a prior mis-attached call.

### Impact Explanation
This meets the Critical "permanent freezing/locking/unauthorized extraction... of user funds... precompile-mediated assets" bar: an unprivileged user (or a contract routing user funds, e.g. a DeFi integrator naively forwarding `msg.value` on a low-level call) can cause native token value to become irrecoverably locked in the WERC20 precompile's backing account, with no code path to reclaim it. Because WERC20 is the standard bridge between native EVM value and ERC-20 semantics used broadly by DeFi integrations (per its own README claiming "No Lock-up" as a security property), this directly contradicts the module's own invariant and destroys real economic value.

### Likelihood Explanation
Low-to-medium in practice for a careful human calling through the standard interface (since the Solidity `IWERC20` interface marks `withdraw`/ERC-20 methods non-payable), but trivially triggerable by anyone using a raw low-level call or by any integrating contract that forwards `msg.value` indiscriminately to a token address it treats as ERC-20-compatible (a very common pattern, e.g. generic multicall/forwarder contracts). No special privileges are required — it is purely an unprivileged EVM call.

### Recommendation
Add the same `contract.Value().Sign() == 1` rejection used by the base ERC-20 precompile to every non-deposit branch of `WERC20.Execute` (i.e., reject value for `withdraw` and anything dispatched to `HandleMethod`), so only `deposit`/`fallback`/`receive` may legitimately carry native value. Alternatively, refund any unexpected `contract.Value()` in `Withdraw`/`HandleMethod` before proceeding.

### Proof of Concept
1. Deploy/call a simple forwarder or use a raw transaction with `to = WERC20_precompile_address`, `data = abi.encodeWithSelector(IWERC20.withdraw.selector, 0)`, `value = X` (X > 0).
2. The EVM call machinery credits `X` to the precompile's `StateDB` balance and, per `runNativeAction`, commits this to the real bank balance of `sdk.AccAddress(werc20Address.Bytes())` before `Execute` runs.
3. `Execute` dispatches to `Withdraw` (see `precompiles/werc20/werc20.go` lines 116-117), which never touches `contract.Value()` and only emits a `Withdrawal` event (`precompiles/werc20/tx.go` lines 62-79).
4. The transaction succeeds; `X` native tokens now sit in the precompile's bank account permanently, since no method returns arbitrary residual balance from that account back to any user — `Deposit` (`precompiles/werc20/tx.go` lines 28-57) only refunds the value of the *current* call.

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	// ERC20 precompiles cannot receive funds because they are not managed by an
	// EOA and will not be possible to recover funds sent to an instance of
	// them.This check is a safety measure because currently funds cannot be
	// received due to the lack of a fallback handler.
	if value := contract.Value(); value.Sign() == 1 {
		return nil, fmt.Errorf(ErrCannotReceiveFunds, contract.Value().String())
	}

	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	return p.HandleMethod(ctx, contract, stateDB, method, args)
}

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch {
	case method.Type == abi.Fallback,
		method.Type == abi.Receive,
		method.Name == DepositMethod:
		bz, err = p.Deposit(ctx, contract, stateDB)
	case method.Name == WithdrawMethod:
		bz, err = p.Withdraw(ctx, contract, stateDB, args)
	default:
		// ERC20 transactions and queries
		bz, err = p.HandleMethod(ctx, contract, stateDB, method, args)
	}

	return bz, err
}

// Deposit handles the payable deposit function. It retrieves the deposited amount
// and sends it back to the sender using the bank keeper.
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}

// Withdraw is a no-op and mock function that provides the same interface as the
// WETH contract to support equality between the native coin and its wrapped
// ERC-20 (e.g. ATOM and WEVMOS).
func (p Precompile) Withdraw(ctx sdk.Context, contract *vm.Contract, stateDB vm.StateDB, args []interface{}) ([]byte, error) {
	amount, ok := args[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("invalid argument type: %T", args[0])
	}
	amountInt := math.NewIntFromBigInt(amount)

	caller := contract.Caller()
	callerAccAddress := sdk.AccAddress(caller.Bytes())
	nativeBalance := p.BankKeeper.SpendableCoin(ctx, callerAccAddress, evmtypes.GetEVMCoinDenom())
	if nativeBalance.Amount.Mul(types.ConversionFactor()).LT(amountInt) {
		return nil, fmt.Errorf("account balance %v is lower than withdraw balance %v", nativeBalance.Amount, amountInt)
	}

	if err := p.EmitWithdrawalEvent(ctx, stateDB, caller, amount); err != nil {
		return nil, err
	}
	return nil, nil
}

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}
