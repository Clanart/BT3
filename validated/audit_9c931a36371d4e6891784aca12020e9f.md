## Finding: Unauthenticated `CallDispatcher.dispatch()` allows anyone to drain leftover ETH/ERC20 balances held by the shared dispatcher

### Title
Unrestricted `CallDispatcher.dispatch()` lets any caller redirect leftover bridged funds to an arbitrary address - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
The external report's root cause is that a shared/trusted execution context (`SignalService`, storing state keyed on `msg.sender`) could be invoked by an unrestricted attacker to make it act with the Bridge's identity, moving funds to an attacker-chosen destination with no restriction on `message.to`/selector. The local analog is `CallDispatcher.dispatch()` [1](#0-0)  — a single, shared, unowned contract reused across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` flows — which has **no access control on the caller and no restriction on the `to`/`value` fields of the `Call[]`** it executes.

### Finding Description
`CallDispatcher` is deployed once and its address is reused by multiple apps: `HyperFungibleToken.onAccept` [2](#0-1) , `WrappedHyperFungibleToken.onAccept` [3](#0-2) , and `IntentGatewayV2` predispatch/postdispatch flows [4](#0-3) . All of these transiently route tokens or native ETH *through* the dispatcher (minting/unlocking bridged funds to the dispatcher address so that attacker-supplied `Call[]` calldata can spend them), then rely on the calldata itself (or, only in `IntentGatewayV2`'s case, an explicit sweep) to move funds back out.

The `dispatch()` function itself performs zero authentication:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [5](#0-4) 

There is no `msg.sender` check restricting who may call `dispatch()`, and no restriction on `to` (other than requiring it be a contract) or `value`. Contrast this with `EvmHost.dispatchIncoming`, which is `restrict(_hostParams.handler)` [6](#0-5)  and always calls a *fixed* selector (`IApp.onAccept`) — exactly the mitigation pattern the external report recommended. `CallDispatcher.dispatch()` implements neither safeguard: any address, any selector, any value, callable by anyone.

Because `dispatch()` can be invoked directly and independently of any bridge message, whenever the shared dispatcher is left holding a balance — e.g. dust from a `Call[]` that doesn't spend 100% of bridged tokens/ETH (acknowledged in docs: *"Token approvals in the Call[] should use exact amounts... since the dispatcher contract holds tokens temporarily during execution"* and *"any tokens remaining in the CallDispatcher are swept back... and collected as dust"* [7](#0-6) ) — that balance is claimable by anyone, not just the app/user that deposited it.

Critically, `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken.onAccept` (unlike `IntentGatewayV2`) never sweep the dispatcher after executing `message.data`:
```solidity
if (message.data.length > 0) {
    ICallDispatcher(_dispatcher).dispatch(message.data);
}
``` [8](#0-7) 
If the bridged amount minted/unlocked to `to = CallDispatcher` (a pattern explicitly documented for compose flows [9](#0-8) ) is not fully consumed by the attacker-supplied `Call[]` (e.g. a swap with slippage, a partial approve, or an intentionally malformed call that only partially executes), the residual ERC20/ETH balance is left sitting in `CallDispatcher` indefinitely.

### Impact Explanation
Any unprivileged, unrelated third party can call `CallDispatcher.dispatch()` directly with a `Call[]` whose `to` is themselves (or any address) and whose `value`/`data` drain the dispatcher's current native or ERC20 balance (e.g. `IERC20.transfer(attacker, dispatcher.balanceOf(token))`, or a plain native transfer). Because the dispatcher's balance at any point in time may hold funds belonging to a bridged transfer that has not yet been fully routed to its rightful beneficiary, this results in loss/theft of bridged user funds to an arbitrary attacker-chosen address — matching the "stealing or loss of funds" / "unauthorized transaction or execution" impact classes in scope.

### Likelihood Explanation
No malicious relayer, prover, or governance actor is required. The attack requires only:
1. A legitimate cross-chain transfer (by any user, including the attacker themselves acting as a normal bridge user) that mints/unlocks funds to the `CallDispatcher` with a `data` payload that leaves any residual balance (easy to engineer deliberately, or simply occurs from routine slippage/dust in swap-composition use cases documented by the protocol itself).
2. A single unauthenticated call to `dispatch()` by anyone monitoring the dispatcher's balance.

Since `dispatch()` is a plain external function with no reentrancy/ownership guard, this is directly and repeatably exploitable by any address, with no dependency on relayer behavior, front-running, or governance compromise.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by the specific app instance that deposited the funds for the current call (e.g., pass an authorized caller allowlist, or deploy a fresh single-use dispatcher/escrow per message instead of a shared singleton).
- Enforce that any residual balance in the dispatcher after executing calls is always swept back to the invoking app (as `IntentGatewayV2` already does) rather than left claimable by any external address — apply the same sweep pattern to `HyperFungibleToken`/`WrappedHyperFungibleToken`.
- At minimum, add a `msg.sender` restriction (e.g. `onlyAuthorizedCaller`) to `dispatch()` so a shared, stateful, unauthenticated contract can never be invoked to move funds it happens to be holding on behalf of an unrelated flow.

### Proof of Concept
1. User bridges tokens via `WrappedHyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` encoding a `Call[]` that swaps only 99% of the delivered amount (e.g. sets `amountOutMin` such that the swap under-consumes input, or simply omits a full-amount `transfer`/`approve`).
2. Relayer delivers the message; `onAccept` unwraps/unlocks the funds into `CallDispatcher`, then executes `dispatch(message.data)`, leaving 1% of the bridged amount sitting in `CallDispatcher`'s balance [3](#0-2) .
3. Attacker (any address, no relation to the transfer) calls `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, leftoverAmount)})]))` directly — succeeds because `dispatch()` has no caller restriction [5](#0-4) .
4. Leftover bridged funds are transferred to the attacker instead of being recoverable by the original sender/beneficiary.

<br>

Note: This finding is derived purely from statically reading the contracts referenced above; I did not execute or test the PoC on-chain.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
