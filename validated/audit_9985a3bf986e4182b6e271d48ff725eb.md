### Title
Git's built-in clone-time code-execution protection is explicitly disabled during recursive clones - (File: `app/src/lib/git/clone.ts`)

### Summary
`app/src/lib/git/clone.ts` runs `git clone --recursive` and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for the clone invocation. [1](#0-0)  `GIT_CLONE_PROTECTION_ACTIVE` is Git's own safety switch (introduced together with the fix for GHSA-vm9j-fq5v-hjp8 / CVE-2024-32004) that detects and refuses to complete a clone (including cloning of nested submodules triggered by `--recursive`) when the repository/submodule tree contains symlinked or otherwise unsafe paths that could cause a hook or config file to be executed or read unexpectedly during the clone. By forcing this variable to `'false'`, GitHub Desktop removes exactly the guard that upstream Git added to stop a maliciously crafted repository from achieving code execution as a side effect of being cloned.

### Finding Description
The clone path is reachable from fully attacker-influenced input: a URL received via the `x-github-client://openrepo/...` deep link (`parseAppURL` → `IOpenRepositoryFromURLAction`) [2](#0-1) , dispatched through `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository`, which shows the "Clone repository" dialog pre-filled with the attacker's URL [3](#0-2) [4](#0-3) , and finally invoked with `clone(url, path, options)` [5](#0-4) .

Inside `clone()`, the only defenses applied are a destination-path sensitivity check (`isClonePathSensitive`, which only blocks a handful of hard-coded home-directory targets) [6](#0-5)  and then `git -c init.defaultBranch=... clone --recursive -- <url> <path>` executed with `GIT_CLONE_PROTECTION_ACTIVE=false` [7](#0-6) . Unlike other git operations in this codebase (commit, merge, push, etc.), the clone call does not pass `interceptHooks`, so it does not get Desktop's own hook-interception/sandbox mechanism (`withHooksEnv`/`getRepoHooks`) either [8](#0-7) . That mechanism is what Desktop otherwise relies on to safely intercept and gate hook execution; during clone, that safety net is absent and the only remaining defense — Git's own built-in clone protection — has been turned off.

The corrupted value/invariant: the environment variable `GIT_CLONE_PROTECTION_ACTIVE`, which Git itself expects to be left enabled to prevent unsafe repository trees from executing code during a recursive clone, is unconditionally forced to `'false'` for every clone Desktop performs, regardless of how untrusted the source URL is.

### Impact Explanation
An attacker who controls a repository (or a fork/submodule reachable from a repo whose URL a victim is lured into opening, e.g. via a crafted "Open in Desktop" link or a shared clone URL) can attempt to exploit the class of clone-time symlink/hook issues that Git's `GIT_CLONE_PROTECTION_ACTIVE` mechanism exists to block. Because Desktop disables that mechanism for every clone and does not substitute its own hook interception for the clone step, a successful payload could result in arbitrary command/hook execution on the victim's machine as soon as they clone the attacker's repository — satisfying the "attacker controls a cloned/fetched repository ... result is code execution" criterion.

### Likelihood Explanation
The clone path is one of Desktop's most common, low-friction user actions (typing/pasting a URL into "Clone repository", or clicking a `x-github-client://openrepo/...` link which pre-fills and can auto-trigger the clone flow). No special local access, admin rights, or pre-existing compromise is required — only that the victim clones a URL supplied by the attacker, which is the exact normal use of the feature. The explicit, unconditional disabling of the protection (`GIT_CLONE_PROTECTION_ACTIVE: 'false'`) applies to 100% of clones performed through the app, not just an edge case.

### Recommendation
- Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` and let Git's built-in clone protection remain active (the default), verifying the bundled `dugite`/Git version is new enough to support it.
- If disabling it was done to work around a specific compatibility issue, gate it behind that specific scenario only, and otherwise route the clone step through the same hook-interception sandbox (`withHooksEnv`/`interceptHooks`) used by other git operations so hook execution during (recursive) clone is mediated by Desktop rather than relying solely on the git binary's own checks.
- Add a regression test asserting that `clone()` never sets `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` (or that it is only disabled in a narrowly justified, documented case).

### Proof of Concept
1. Attacker crafts and hosts a Git repository containing a submodule (or crafted repo layout) that relies on the class of symlink/hook issues `GIT_CLONE_PROTECTION_ACTIVE` is designed to detect and block on clone.
2. Attacker sends the victim a link such as `x-github-client://openrepo/https://evil.example.com/attacker/repo` or simply the clone URL.
3. Victim clicks the link (handled by `handleAppURL`/`parseAppURL`) or pastes the URL into "Clone a repository", triggering `openOrCloneRepository` → `clone()`. [4](#0-3) 
4. `clone()` runs `git clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false`, so Git's own safeguard against the crafted repository layout is bypassed for both the top-level clone and every submodule fetched via `--recursive`. [7](#0-6) 
5. If the crafted repository content is otherwise sufficient to trigger the underlying Git clone-protection scenario, code executes on the victim's machine purely as a result of cloning — with no additional confirmation step in Desktop's UI to catch it.

Note: I could not execute Git locally in this environment to confirm the exact exploit payload/version dependency for the underlying Git clone-protection bypass (this would need to be validated in a sandboxed environment with the specific Git/dugite version Desktop bundles); the finding here is scoped strictly to the fact that Desktop unconditionally disables this named safety mechanism for every clone, which is directly verifiable in `app/src/lib/git/clone.ts`.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
