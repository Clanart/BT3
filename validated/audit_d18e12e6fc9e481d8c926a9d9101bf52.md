### Title
Self-referral sybil loop lets an attacker farm referral MGP rewards via two attacker-controlled wallets - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.useCode` only blocks a user from using their own registered code (`codeOwners[_code] == msg.sender`), but does not verify that the referrer and referee are economically independent parties. An attacker can register a code with wallet A and use it from wallet B (also controlled by the attacker), then repeatedly trigger `trigger()` via genuine but minimal MasterMagpie claims to accumulate `refererInfo.rewardAmount` and `refereeInfo.rewardAmount` for both attacker-controlled addresses.

### Finding Description
`registerCode` [1](#0-0)  lets any address register an arbitrary code with no cost or KYC/anti-sybil check. `useCode` [2](#0-1)  only rejects `codeOwners[_code] == msg.sender` (direct self-referral from the same address), so nothing stops address B from using a code owned by a different address A that the same attacker also controls.

Once `myReferer[B] = A` is set, every time MasterMagpie calls `trigger(B, amount)` upon B's reward claim [3](#0-2) , the contract computes `refererAmount` and `refereeAmount` as percentages of `_amount` (based on tier `basic` percentage plus a boosted factor from vlMGP locking) and credits both `refererInfo.rewardAmount` (A) and `refereeInfo.rewardAmount` (B). Both amounts are later withdrawable in MGP via `claimReward()` [4](#0-3) , which transfers real MGP tokens out of the ReferralStorage contract's balance.

Existing modifiers (`_onlyMasterMagpie` on `trigger`) correctly ensure `_amount` reflects a real, legitimately-earned MasterMagpie reward claim rather than an arbitrary attacker-supplied number — so the attack does not mint unlimited free tokens. However, there is no check preventing the referrer and referee from being sybil identities of the same actor, so any real (even minimal) staking/claiming activity by B is amplified with an extra referral bonus paid to A and B that was intended to reward genuine third-party referral relationships. This diverts the protocol's referral incentive budget (a separately funded pool of MGP held by `ReferralStorage`) to a single actor without providing real referral value, and the attack is fully repeatable at negligible cost (minimal stake, gas only).

### Impact Explanation
This results in "theft of unclaimed yield" — the referral incentive pool (MGP funded into `ReferralStorage` for genuine referral rewards) is diverted to a single attacker acting as both referrer and referee, using two wallets they control and only trivial real stake. The loss is bounded by the size and frequency of B's actual reward claims and the tier/boost percentages, but it is real, repeatable, and drains the protocol's referral budget rather than accruing to legitimate independent referrers.

### Likelihood Explanation
Preconditions are trivial: any EOA can call `registerCode` for free, any second EOA can call `useCode` for free, and then stake the minimum amount and repeatedly claim through MasterMagpie. No privileged role, flash loan, or reentrancy is needed — only two wallets and minimal capital, making this a low-cost, highly repeatable exploit.

### Recommendation
Add anti-sybil safeguards to `useCode`/`registerCode`, such as: preventing a referee from using a code owned by an address linked to the same funding wallet is impractical on-chain, so consider capping total referral reward payout per referrer/referee pair relative to independently-verifiable stake, adding a minimum referee stake/lockup threshold before referral rewards accrue, or requiring a cooldown/vesting on referral rewards proportional to sustained real economic activity rather than raw claim count, to make self-referral farming uneconomical.

### Proof of Concept
Foundry test plan:
1. Deploy `ReferralStorage`, `MasterMagpie`, vlMGP/MGP mocks, and a staking pool.
2. Wallet A calls `registerCode(codeA)`.
3. Wallet B calls `useCode(codeA)`, verify `myReferer[B] == A`.
4. Wallet B stakes minimal principal into a MasterMagpie-tracked pool.
5. Advance time/emission, have B call MasterMagpie's claim function repeatedly, which internally calls `ReferralStorage.trigger(B, amount)`.
6. After N repeated claims, call `ReferralStorage.claimReward()` from A and B.
7. Assert `userInfos[A].rewardAmount` and `userInfos[B].rewardAmount` (and MGP balances after `claimReward`) grow with each claim cycle despite B's negligible staked principal, demonstrating referral-budget siphoning via sybil self-referral with no independent economic counterpart to A's "referral."

        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
