### Title
`SignableTransaction::new` omits the OP_RETURN data output from transaction weight/fee and standard-weight checks - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/blackvul/serai--014/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
Like the Rails bug where the `Permissions-Policy` header is only emitted on HTML `Content-Type` responses, `SignableTransaction::new` applies its security-relevant accounting — virtual-size estimation, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` standardness check — only to `payments` (and optionally `change`). The `OP_RETURN` data output, which is a real output included in the final signed transaction, is never fed into `calculate_weight_vbytes`, so the fee and standardness "policy" silently does not apply to that output type.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

- Lines 193–202 push the `OP_RETURN` output into `tx_outs` before any weight accounting happens.
- Line 204 then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — which reconstructs a template transaction from `payments` only (lines 85–93). The `OP_RETURN` output already present in `tx_outs` is not represented.
- Lines 224–235 recompute weight with `Some(&change)` when change exists — but again only `payments` and `change` are templated; the data output is still missing.

Concretely, `calculate_weight_vbytes` builds `tx.output` solely from `payments` plus the optional change output (lines 85–99), so `weight`, `vbytes`, `needed_fee` (line 206), the `DEFAULT_MIN_RELAY_TX_FEE` floor (line 211), the `NotEnoughFunds` check (line 215), and the `MAX_STANDARD_TX_WEIGHT` check (line 241) are all computed on a transaction that is structurally smaller than the one actually signed and broadcast. ### Impact Explanation
Two concrete consequences:

1. **Underpaid fee / fee-policy bypass.** The signed transaction is ~`10 + data_len` weight-units-heavier (up to ~80 bytes of payload plus output overhead, roughly 30–45 vbytes) than what `needed_fee` was priced for. A caller requesting `fee_per_vbyte` gets a transaction whose effective fee rate is lower — potentially below the mempool minimum relay fee even though `TooLowFee` was checked, or below `needed_fee` semantics such that `fee()` diverges from `needed_fee()`. The transaction can be constructed, fully signed by the FROST multisig (`TransactionSignMachine::sign`, lines 355–398), and then rejected or stuck unconfirmed — outputs it spends are effectively frozen until a replacement is negotiated.

2. **Standard-weight check evasion.** A transaction whose real weight exceeds `MAX_STANDARD_TX_WEIGHT` can pass the line-241 check because the `OP_RETURN` output's weight is never counted, producing a signed transaction that no default-policy node will relay.

This is reachable from public inputs: the `data` field originates from external instruction data supplied in deposits/burns that the processor serializes into the Bitcoin transaction via this constructor.

### Likelihood Explanation
Any transaction built with `data.is_some()` (a normal, supported code path — lines 194–202 exist specifically for it) triggers the miscount. It does not require attacker-crafted exotic inputs; it is a deterministic accounting error present whenever the data output is used. Severity is bounded (fee shortfall is at most ~45 vbytes × rate, and the failure mode is an unrelayable/stuck transaction rather than theft), which is consistent with a Medium finding.

### Recommendation
Include the data output in the weight template. Either pass a fully materialized output list into `calculate_weight_vbytes` (build the template from `tx_outs` after pushing the `OP_RETURN`), or append a `TxOut { value: Amount::ZERO, script_pubkey: <the OP_RETURN script> }` in both the no-change and with-change weight calculations before computing `weight`/`vbytes`/`needed_fee`.

### Proof of Concept
In `SignableTransaction::new`, trace `data = Some(vec![0u8; 80])`:

```rust
// tx_outs gets the OP_RETURN (lines 194-202)
tx_outs.push(TxOut { value: Amount::ZERO,
  script_pubkey: ScriptBuf::new_op_return(...80 bytes...) });

// but the template used for weight has only `payments` (lines 204, 85-93):
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// -> tx.output inside calculate_weight_vbytes = payments only; OP_RETURN absent

let mut needed_fee = fee_per_vbyte * vbytes;   // underpriced
// TooLowFee check (line 211) and MAX_STANDARD_TX_WEIGHT check (line 241)
// both evaluated on the underestimated weight
```

A unit test asserting `SignableTransaction::new(inputs, payments, None, Some(vec![0; 80]), fee_rate)` yields `needed_fee == fee_rate * tx.weight()-derived vbytes` would fail: `tx.weight()` exceeds the counted weight by the size of the OP_RETURN output.
