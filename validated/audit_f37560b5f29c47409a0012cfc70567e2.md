### Title
`RecoverPolynomialCoefficients` truncates the erasure-decoded polynomial without verifying the discarded high-order coefficients are zero, allowing acceptance of cell sets that are not evaluations of a true degree < 4096 polynomial - (File: `internal/erasure_code/erasure_code.go`)

### Summary
`Context.RecoverCellsAndComputeKZGProofs` (the `RecoverCells`-family entrypoint) reconstructs the polynomial coefficients from attacker-supplied cells via `ctx.recoverPolynomialCoeffs` → `DataRecovery.RecoverPolynomialCoefficients`. The latter unconditionally truncates the reconstructed `numScalarsInCodeword`-length coefficient vector to the first `numScalarsInDataWord` (4096) entries and never checks that the discarded coefficients (indices 4096..8191) are zero, nor does the caller verify that recomputed cells at the originally supplied `cellIDs` match the input `cells`.

### Finding Description
The invariant that should hold is: for every supplied `cellIDs[i]`, `recovered[cellIDs[i]] == cells[i]`, and the recovered polynomial has degree < `ScalarsPerBlob` (i.e. all coefficients at index ≥ 4096 are zero).

Tracing the path:
- `Context.RecoverCellsAndComputeKZGProofs` (`api_eip7594.go:148`) calls `ctx.recoverPolynomialCoeffs(cellIDs, cells)` [1](#0-0) .
- `recoverPolynomialCoeffs` places the caller-supplied cell evaluations into `extendedBlob` at the caller-chosen (validated only for ordering/range) `cellID` positions, bit-reverses, and forwards to `ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)` [2](#0-1) .
- Inside `RecoverPolynomialCoefficients`, the algorithm builds the erasure vanishing polynomial `zX` for the missing cells, computes `D(x) = E(x)·Z(x)` via evaluation-domain multiplication and IFFT, divides by `Z(x)` in the coset domain to obtain the quotient `cosetQuotientEval`, and then simply slices: `polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]` [3](#0-2) .

This decoding procedure is only guaranteed correct when the evaluations supplied for the non-missing cells are genuinely consistent with *some* polynomial of degree < `numScalarsInDataWord` (4096). If an attacker supplies cell values (for the cellIDs they choose to submit) that are not evaluations of any such low-degree polynomial, the quotient polynomial computed by the division will generally have nonzero coefficients beyond index 4096. The code discards those coefficients silently instead of detecting and rejecting this case (e.g. by checking they're all zero, or by re-evaluating the truncated `polyCoeff` at the supplied `cellIDs` and comparing to the input `cells`).

Because `recoverPolynomialCoeffs`/`RecoverCellsAndComputeKZGProofs` never performs that check either (no comparison of recomputed cells against the original submitted `cells[i]` for the supplied `cellIDs[i]`), the function returns a `polyCoeff` and downstream `computeCellsFromPolyCoeff`/`computeKZGProofsFromPolyCoeff` produce cells and proofs from this "wrong" degree-4096-truncated polynomial that do not actually reproduce the attacker's original submitted cells at those indices. This breaks `recovered[cellIDs[i]] == cells[i]` for the supplied indices, and produces a polynomial whose "true" (un-truncated) representation has degree ≥ 4096 — inconsistent with what a correct implementation (e.g. c-kzg) would either reject or represent differently.

None of the existing guards prevent this: `isAscending`, the `cellID < CellsPerExtBlob` check, and `NumBlocksNeededToReconstruct` only validate structural/index properties of the input, not the algebraic low-degree consistency of the supplied evaluations [4](#0-3) .

### Impact Explanation
This is a High-severity "client split" scenario: for cell sets crafted to have nonzero degree-4096..8191 coefficients when erasure-decoded, this library will silently truncate and emit a `recovered`/proof set that a spec-compliant implementation such as c-kzg (which would reject such inconsistent inputs, or at minimum produce a self-consistent output that matches the supplied cells) would treat differently. This causes divergence between go-eth-kzg and c-kzg/the consensus spec on the accepted output for identical attacker-supplied bytes, potentially causing nodes running different libraries to disagree on canonical cell/proof data for the same blob reconstruction request.

### Likelihood Explanation
The attacker needs only to submit a cell set (via the public `RecoverCellsAndComputeKZGProofs` API, reachable from any protocol path that performs cell recovery) whose values are not evaluations of a genuine degree<4096 polynomial but pass the basic structural checks (ascending, in-range cell IDs, sufficient count). Constructing such cells requires only linear algebra over the known extended-domain roots of unity (public parameters), with no access to the trusted setup or private keys. This is fully repeatable and inexpensive for an unprivileged attacker.

### Recommendation
After computing `polyCoeff` in `RecoverPolynomialCoefficients` (or in the caller `recoverPolynomialCoeffs`), explicitly verify that the discarded high-order coefficients (`cosetQuotientEval[numScalarsInDataWord:]`) are all zero, and/or re-derive the cells at the original `cellIDs` from the truncated polynomial and assert they equal the caller-supplied `cells[i]` bit-for-bit before returning success; return an error otherwise.
