## Analysis: Unbounded loop in `object::root_owner` reachable from the publish/init path

Tracing the external Karma.sol bug down to its abstract invariant — "a function silently omits a bound/init check that another sibling function in the same trust boundary correctly performs" — I found a direct Aptos analog in `object.move`'s ownership-chain walkers, which are called directly from the code-publishing and lazy-module-initialization paths.

### Title
Unbounded ownership-chain loop in `object::root_owner` allows permanent DoS of code-object publish/upgrade and lazy module self-init — (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`code::publish_package` and `init::assert_may_self_initialize` both call `object::root_owner()` to determine/verify the transitive owner of a code object when the `lazy_module_initialization` feature is enabled [1](#0-0) . Unlike its sibling functions in the same module (`owns` and `verify_ungated_and_descendant`), `root_owner` has **no cycle/nesting bound**, so it loops forever if the object's ownership graph is cyclic.

### Finding Description
`object.move` defines three ownership-chain-walking functions. Two of them explicitly guard against unbounded traversal using `MAXIMUM_OBJECT_NESTING`: [2](#0-1) [3](#0-2) 

But `root_owner` has no such bound: [4](#0-3) 

```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```

A cyclic ownership graph is achievable through fully legitimate, unprivileged use of `object::transfer` / `transfer_raw`. `verify_ungated_and_descendant` only checks that the **current** owner chain from the destination reaches the signer within 8 hops **before** the transfer is applied — it does not prevent the resulting graph from becoming cyclic once the new edge is added: [5](#0-4) 

The existing test only shows a same-transaction self-loop attempt failing on the *second* transfer, but a **two-step, two-object cycle can be built across two separate transactions**, each individually passing `verify_ungated_and_descendant`:
1. Owner `@addr` owns objects `O1` and `O2`.
2. `transfer(@addr, O1, O2_address)` — succeeds (`O2`'s owner is `@addr`, matches immediately).
3. `transfer(@addr, O2, O1_address)` — at check time `O2`'s current owner is still `@addr` (the transfer hasn't happened yet), and `O1`'s owner is `O2`, so the walk from `O1` finds `O2`... actually the check walks from the *destination* `O1_addr`: `O1.owner == O2`, `O2.owner == @addr` → matches within 2 hops. Succeeds.
4. After step 3, `O1.owner == O2` and `O2.owner == O1`: a genuine 2-object ownership cycle now exists, with no code path ever rejecting it.

Once such a cycle exists, calling `root_owner()` on either object index into `address_to_object<ObjectCore>(...).owner()` back and forth forever, since `is_object()` is always true for both addresses and neither ever resolves to a non-object account address.

### Impact Explanation
`root_owner()` is invoked from two protected-state-mutation call sites feature-gated by `is_lazy_module_initialization_enabled`:
- `code::publish_package`, on every (re)publish/upgrade to an object-hosted package, to record the deploy owner used later to authorize self-init [6](#0-5) .
- `init::assert_may_self_initialize`, on every call to `internal_maybe_initialize` for an object-hosted module [7](#0-6) .

If an attacker (or even the object owner unintentionally) maneuvers a code object's ownership into a cycle as shown above, then:
- Any subsequent `code::publish_package`/`object_code_deployment::upgrade` targeting that object address will loop until gas is exhausted, permanently denying upgrade capability for that code object (an availability-affecting "freeze" outcome achieved without the owner's `freeze_code_object` call).
- Any call to `internal_maybe_initialize` for a module hosted at that address will similarly hang/abort on out-of-gas, permanently bricking that module's lazy self-init.

This is a code-safety/publish-path availability bug reachable by an unprivileged object owner manipulating their own object graph, with concrete, reproducible corrupted control flow (infinite loop) in a function directly gating publish/upgrade and module-init state mutation.

### Likelihood Explanation
The precondition (constructing a 2-object ownership cycle) requires only two ordinary `object::transfer` calls by the object's own owner — no special privilege, no VM/verifier bypass. It is easy to trigger accidentally by a package author restructuring nested object ownership, and trivially triggerable adversarially against one's own object to grief future upgrade/init availability, or against integrations that rely on `root_owner`/`owns` semantics elsewhere.

### Recommendation
Add the same bounded-iteration and cycle-detection guard used in `owns`/`verify_ungated_and_descendant` to `root_owner`:
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    let count = 0;
    while (is_object(obj_owner)) {
        count += 1;
        assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Additionally, consider hardening `verify_ungated_and_descendant` (or adding a dedicated acyclicity check) so that `transfer`/`transfer_raw` cannot ever create a cycle in the ownership graph in the first place, since `root_owner` is not the only place a cyclic graph could cause unexpected behavior.

### Proof of Concept
```move
// 1. Create two objects owned by `creator`.
let ref1 = object::create_object(signer::address_of(creator));
let ref2 = object::create_object(signer::address_of(creator));
let obj1 = object::object_from_constructor_ref<ObjectCore>(&ref1);
let obj2 = object::object_from_constructor_ref<ObjectCore>(&ref2);

// 2. O1 -> O2
object::transfer(creator, obj1, object::object_address(&obj2));

// 3. O2 -> O1 (still valid: at check time O2's owner is still `creator`)
object::transfer(creator, obj2, object::object_address(&obj1));

// 4. Cycle now exists: O1.owner == O2, O2.owner == O1.
// Any call that reaches object::root_owner(obj1) or root_owner(obj2)
// (directly, or indirectly via code::publish_package / init::internal_maybe_initialize
// on a module hosted at either address) now loops forever / runs out of gas.
let _ = object::root_owner(obj1); // hangs / OUT_OF_GAS
```

**Note on confidence:** I could not execute this in a live Move VM/e2e test harness to directly confirm the gas-exhaustion behavior or rule out an unseen guard elsewhere in the transfer path; this assessment is based on static reading of `object.move`, `code.move`, and `init.move`. I recommend a Devin session run the above PoC against `aptos-move/e2e-move-tests` to empirically confirm the infinite loop / `OUT_OF_GAS` abort before treating this as fully verified.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.

            assert!(

                error::permission_denied(ENO_UNGATED_TRANSFERS),

        };

    #[view]
    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
