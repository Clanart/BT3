## Analysis: Consensus Incentives Reward Uses Only the *Current* Rate Applied Retroactively

The DIA report's broken invariant — "rewards computed with the *current* rate applied across a stake period during which the rate could have changed" — has a direct analog in `pallet-consensus-incentives`.

### Root cause

`calculate_reward` computes the reward for the *entire* un-rewarded block range `[baseline, latest_height]` using whatever `block_cost` is stored **right now** in `StateMachinesCostPerBlock`, with no accounting for the fact that governance may have changed that rate at some point inside that range: [1](#0-0) 

The reward formula is `Reward = (LatestHeight - PreviousHeight) * CostPerBlock`, documented explicitly: [2](#0-1) 

`baseline` is the pallet's own watermark (`LastRewardedHeight`), which only advances when a reward is actually paid — so unclaimed block ranges can accumulate indefinitely between deliveries: [3](#0-2) 

The rate itself is a single mutable value with no history, updated via the privileged (but routine, non-malicious) `update_cost_per_block` extrinsic: [4](#0-3) 

### Why this reproduces the DIA bug class

The relayer, an unprivileged actor, controls **when** they submit the `ConsensusMessage` that triggers `process_message`/`calculate_reward` via `on_executed`: [5](#0-4) 

Because the reward for the whole backlog `latest_height - baseline` is priced at whatever `CostPerBlock` happens to be in storage at the moment of delivery — not at the rate(s) that were actually in force block-by-block — a relayer can:
1. Withhold delivering consensus updates while `CostPerBlock` is low, letting the un-rewarded block range grow.
2. Deliver right after governance raises `CostPerBlock`, collecting the *entire* accumulated backlog at the new, higher rate — draining more from `TreasuryAccount` than the protocol intended for those older blocks.

Conversely, if the rate is lowered, blocks that accrued under the old higher rate are paid at the new lower rate, silently underpaying relayers who delivered promptly versus those who delay — the same "identical stakes get different rewards depending on timing" unfairness described in the report, but here manifesting as a treasury-drain/timing-arbitrage vector rather than a simple fairness issue.

This is not a niche edge case: `LastRewardedHeight` explicitly exists to prevent double-payment for the *same* blocks, but nothing constrains how large a backlog can accumulate before it's collapsed into a single reward computed with a single point-in-time rate: [6](#0-5) 

### Title
Consensus-Incentives Reward Backlog Priced Entirely at Current Rate Enables Relayer Timing Arbitrage on Treasury Payouts - (File: modules/pallets/consensus-incentives/src/impls.rs)

### Summary
`calculate_reward` multiplies the full un-rewarded block range by the single current `StateMachinesCostPerBlock` value, with no per-period rate history. A relayer who controls submission timing of `ConsensusMessage` proofs can let a reward backlog accumulate and then deliver it immediately after a rate increase, extracting an inflated payout from `TreasuryAccount` for blocks that should have been priced at the lower historical rate.

### Finding Description
`process_message` → `calculate_reward` computes `reward = (latest_height - baseline) * block_cost` using the rate read from storage at call time. `baseline` is `LastRewardedHeight`, which only advances on payment, so the backlog window is attacker-controlled by simply not delivering proofs. There is no accumulator/index tracking rate-weighted accrual per block, unlike what would be required to price each sub-range at the rate that was actually active during it (the exact fix pattern the DIA report recommends).

### Impact Explanation
Treasury funds (`T::Currency::transfer` from `TreasuryAccount`) can be paid out at an amount that does not correspond to the intended reward schedule — an overpayment relative to protocol intent whenever the rate rises during an accumulated backlog, effectively a wrong-amount fund movement out of the treasury to a relayer who exploited submission timing rather than genuine, timely relay work.

### Likelihood Explanation
Requires only a normal, unprivileged relayer choosing when to submit an otherwise-valid `ConsensusMessage`/proof — no collusion with governance, no malicious prover, and no compromised keys. Rate changes via `update_cost_per_block` are a normal, expected governance operation, so the timing window is realistically available.

### Recommendation
Track rate-weighted accrual incrementally (an index/accumulator updated on every `update_cost_per_block` call, analogous to `globalIndex` in the report's recommendation) so a backlog spanning a rate change is paid using the rate(s) actually in effect for each sub-range, not a single current snapshot applied to the whole range.

### Proof of Concept
1. Set `CostPerBlock = X` for a state machine.
2. Do not submit any `ConsensusMessage` for that chain while its height advances by `N` blocks (backlog accrues, `LastRewardedHeight` unchanged).
3. Governance raises `CostPerBlock` to `Y > X` (a routine operational change).
4. Relayer immediately submits the consensus proof covering the full backlog of `N` blocks; `calculate_reward` pays `N * Y` instead of the amount intended under `X` for those blocks, over-draining the treasury relative to the rate that was actually in force when those blocks occurred.

```rust
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
```
