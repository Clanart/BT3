Confirmed critical finding.

### Title
Whichever transaction spends the withdrawal UTXO gets its first-scanned OP_RETURN attributed as payer, letting anyone re-route/forge payout attribution - (File: circuits-lib/src/bridge_circuit/mod.rs, core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
`get_payout_txs_for_withdrawal_utxos` identifies the "payout tx" purely by which transaction spends `withdrawal_utxo_txid:withdrawal_utxo_vout` in a given block — it does not check that this transaction is the specific txid the operator originally built. `update_finalized_payouts` then calls `get_first_op_return_output`, which scans outputs in order and returns the first OP_RETURN, not a fixed vout. Because the payout tx's only signature (`TapSighashType::SinglePlusAnyoneCanPay`) commits solely to input 0 and output 0, an attacker can take operator A's valid, unconfirmed, ANYONECANPAY-signed input+output-0 pair and rebuild a competing, higher-fee transaction that spends the same withdrawal UTXO, keeps output 0 identical (so the signature stays valid), but inserts an extra OP_RETURN before A's real one and reorders/pushes A's own OP_RETURN later.

### Finding Description
Binding claimed broken: `operator_xonly_pk` recorded in `withdrawals.payout_payer_operator_xonly_pk` for withdrawal *i* == the operator whose signed output 0 actually funded the withdrawal for *i*.

Code path:
- `core/src/database/verifier.rs::get_payout_txs_for_withdrawal_utxos` (lines 170-196) joins on `bitcoin_syncer_spent_utxos` keyed by `(withdrawal_utxo_txid, withdrawal_utxo_vout)` — it returns whatever `spending_txid` actually spent that outpoint in the block, with no check that this txid equals a specific expected/registered payout txid. [1](#0-0) 
- `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2354) takes that tx and calls `get_first_op_return_output`, then `parse_op_return_data`, storing whatever xonly pubkey is found as `payer_operator_xonly_pk`. [2](#0-1) 
- `get_first_op_return_output` scans by iteration order and returns the *first* match, not output index 2 as fixed by `create_payout_txhandler`. [3](#0-2) 
- `create_payout_txhandler` places outputs as [user payout(0), anchor(1), OP_RETURN(2)] and signs only input 0 with `set_p2tr_key_spend_witness`, using the user-supplied `TapSighashType::SinglePlusAnyoneCanPay` signature enforced at parse time (`core/src/rpc/parser/operator.rs::parse_withdrawal_sig_params`). [4](#0-3) [5](#0-4) 
- `SinglePlusAnyoneCanPay` commits only to input 0's prevout (via ANYONECANPAY) and to the output at the same index as the input, i.e. output 0 only (Taproot SIGHASH_SINGLE semantics implemented in `calculate_pubkey_spend_sighash`, which uses `Prevouts::One` for this flag). It places no constraint on any other output (count, order, or content) of the transaction. [6](#0-5) 
- Consequently, this signature/output-0 pair is fully reusable in any transaction that (a) spends the same outpoint, (b) keeps output 0 byte-identical, and (c) has any other outputs whatsoever. An attacker can therefore add an earlier OP_RETURN carrying operator B's xonly pk before A's genuine OP_RETURN, and it will still validate.
- Root cause: `get_first_op_return_output`'s "first match wins" semantics combine with (1) `get_payout_txs_for_withdrawal_utxos`'s identification of the payout purely by "spent this outpoint" rather than by exact expected txid, and (2) a SIGHASH_SINGLE|ANYONECANPAY signature that leaves all outputs after index 0 completely unconstrained.
- This directly feeds `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1857-1915), which compares the DB-recorded `payer_operator_xonly_pk` to `kickoff_data.operator_xonly_pk` of whoever kicks off; a mismatch (e.g., A's own honest kickoff vs. a DB-recorded B) causes verifiers to treat A's kickoff as malicious and disprove/challenge it, and a match (attacker/B kicking off with `operator_xonly_pk = B`) lets B pass this check. [7](#0-6) 

Existing guards do not stop this: `Operator::withdraw`'s `SECP.verify_schnorr` only checks the copied signature against the (unchanged) sighash of input 0/output 0 — it says nothing about extra outputs — and no code anywhere validates that the confirmed payout tx has exactly 3 outputs in the canonical order, or that the OP_RETURN used is at a fixed vout.

### Impact Explanation
- Honest operator A: once a substitute/decoy tx with an earlier, attacker/other-operator-controlled OP_RETURN is mined instead of (or as a race against) A's broadcast payout tx, `payer_operator_xonly_pk` for that withdrawal is set to the wrong key. When A later kickoffs (with its own correct `operator_xonly_pk`), `is_kickoff_malicious` sees a mismatch and flags A as malicious, triggering a BitVM disprove against A even though A genuinely and validly funded the withdrawal — A's collateral is burned and A is permanently unable to reach Reimburse for that deposit. This matches "an honest operator's collateral burned" / "an honest operator permanently unable to be reimbursed" (Critical).
- If the inserted xonly pk belongs to an actual colluding/malicious operator B who then submits the matching kickoff, `is_kickoff_malicious` passes (match), and B is reimbursed from the round/reimburse flow for a payout it never funded — "an operator reimbursed for a payout it never funded" (Critical).
- Repeatable across every withdrawal for which the payout tx has not yet confirmed at the moment the attack is executed; blast radius spans all deposits/operators using this codepath, since the flaw is structural (signature scheme + first-match OP_RETURN scan + outpoint-only tx identification), not tied to a specific deposit.

### Likelihood Explanation
Preconditions are modest and attacker-only: the attacker needs (1) visibility of A's broadcast (unconfirmed) payout tx — the SinglePlusAnyoneCanPay witness is public in the mempool, (2) the ability to construct and fee-bump/RBF-replace or race a competing transaction spending the same withdrawal UTXO (standard mempool/replacement mechanics; DEFAULT_SEQUENCE and no additional restriction prevents a conflicting spend from being relayed/mined if it has adequate fee), and (3) basic Bitcoin script construction skill to add another OP_RETURN output. No verifier/operator/aggregator privilege, key share, or collateral is required to perform steps (1)-(3) — griefing operator A requires only fee-paying capability. Reaping the reimbursement benefit as "operator B" additionally requires B to actually be a registered operator able to kick off, but the griefing/DoS harm to A is achievable purely by an unprivileged attacker.

### Recommendation
- In `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts`, do not accept "any tx that spends the withdrawal UTXO" as canonical; require the confirmed txid to structurally match the transaction the operator committed to (fixed output layout/count), or bind the OP_RETURN commitment cryptographically to the signed material.
- Fix `get_first_op_return_output` (and the corresponding circuit logic) to require the OP_RETURN to be at the fixed, protocol-defined output index (index 2, matching `create_payout_txhandler`) rather than the first-scan match, and reject payout txs where the layout deviates.
- Consider having the user's signature cover more of the transaction (e.g., `SIGHASH_ALL|ANYONECANPAY` restricted to a template, or explicitly commit to the full expected output set/order) so that arbitrary extra outputs cannot be spliced in without invalidating the signature.

```rust
fn test_get_first_op_return_picks_attacker_inserted_output_over_real_one() {
    use bitcoin::{Transaction, TxOut, Amount, absolute::LockTime, transaction::Version, ScriptBuf};
    use crate::bridge_circuit::{get_first_op_return_output, parse_op_return_data};

    let real_operator_pk = [0xAAu8; 32];
    let fake_operator_pk = [0xBBu8; 32]; // operator B, attacker-controlled

    let payout_output = TxOut { value: Amount::from_sat(10_000), script_pubkey: ScriptBuf::new() }; // output 0, must stay identical to preserve SIGHASH_SINGLE|ANYONECANPAY
    let injected_op_return = crate::... /* op_return_txout equivalent */ (fake_operator_pk);
    let real_op_return = /* op_return_txout equivalent */ (real_operator_pk);

    let attacker_tx = Transaction {
        version: Version::non_standard(3),
        lock_time: LockTime::ZERO,
        input: vec![/* same input 0 as A's payout tx, ANYONECANPAY sig preserved */],
        output: vec![payout_output.clone(), injected_op_return.clone(), real_op_return.clone()],
    };

    let circuit_tx = attacker_tx.into();
    let first = get_first_op_return_output(&circuit_tx).expect("must find an OP_RETURN");

    assert_eq!(parsed, fake_operator_pk);
```

```rust
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
```
