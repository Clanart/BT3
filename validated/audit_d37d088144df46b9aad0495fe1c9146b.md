Confirmed: `deposit`/`withdraw`/`harvest` on `WombatStaking` have no cooldown or delay — any wallet can call `AnkrBNBPoolHelper.deposit`/`WombatPoolHelper.deposit` and `harvest()` (which is unrestricted besides pool being active) freely, then withdraw immediately after.

### Title
Instantaneous, non-streamed reward crediting in `BaseRewardPool`/`BaseRewardPoolV2` lets a wallet deposit right before harvest and capture a full batch of accumulated rewards, then withdraw immediately - ([File: rewards/BaseRewardPool.sol], [File: rewards/BaseRewardPoolV2.sol], [File: wombat/WombatStaking.sol])

### Summary
`BaseRewardPool._provisionReward` (and the identical logic in `BaseRewardPoolV2` and `mWOMSVBaseRewarder`) credits an entire incoming reward batch to `rewardPerTokenStored` in a single state update, based on whatever `totalStaked()` is at that exact block [1](#0-0) . This mirrors the am-AMM "last-minute deposit" bug class: because the whole accumulated batch (which can represent WOM/bribe rewards accrued over an arbitrarily long period since the last harvest) is distributed atomically to current stakers rather than streamed over time, a wallet can deposit into the pool immediately before a permissionless `harvest()` call and be counted as a full-share holder for the entire batch.

### Finding Description
`WombatStaking.harvest()` is callable by any address (gated only by `_onlyActivePool`, not privileged) and triggers `_toMasterWomAndSendReward`, which ultimately calls `IBaseRewardPool(_rewarder).queueNewRewards(...)` [2](#0-1) [3](#0-2) . `queueNewRewards`/`donateRewards` call `_provisionReward`, which immediately folds the whole `_amountReward` into `rewardInfo.rewardPerTokenStored` divided by the current `totalStaked()`, with no time-weighted vesting: `rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()` [1](#0-0) . Because `earned()`/`_updateFor()` only look at `rewardPerToken()` snapshots (not a per-second stream like `WomUp.sol`'s `rewardRate`/`periodFinish` design [4](#0-3) ), any wallet holding a share at the moment `_provisionReward` runs receives a full pro-rata cut of the entire batch, regardless of how briefly it has been staked.

There is no deposit lock or cooldown in `MasterMagpie._deposit`/`_withdraw` [5](#0-4) , nor in `WombatStaking.deposit`/`withdraw` [6](#0-5)  or the pool helpers' `deposit`/`withdraw` wrappers [7](#0-6) . An attacker can therefore: (1) call `WombatPoolHelper.deposit(...)` to obtain freshly-minted shares immediately before calling the permissionless `harvest()` (or even in the same block via a bundled/multicall pattern, or simply front-running a bot's `harvest()` call), (2) trigger/observe `harvest()` so the newly queued WOM/bribe rewards are instantly baked into `rewardPerTokenStored` for all current stakers including the attacker, and (3) immediately call `withdraw()` to exit, having paid no time cost proportional to the reward earned.

### Impact Explanation
This dilutes honest long-term liquidity providers' share of harvested rewards by allowing a transient depositor to claim a full pro-rata cut of rewards that accrued while they were not staked, i.e., a **theft of unclaimed yield** from other stakers. The magnitude scales with how much time passes between harvests and how large the attacker's deposit is relative to `totalStaked()` at harvest time.

### Likelihood Explanation
`harvest()` is unrestricted (any external wallet can call it) [2](#0-1) , and deposit/withdraw have no lockup, so the attack requires no privileged access and can be executed by any user monitoring pending WOM rewards (`pendingWom()` is even exposed as a view helper) [8](#0-7) , making the attack straightforward to time and repeat across pools/epochs.

### Recommendation
Stream newly queued rewards over time (e.g., a `rewardRate`/`periodFinish` model like the one already used in `WomUp.sol` [4](#0-3) ) instead of crediting the full batch to `rewardPerTokenStored` in one atomic update in `_provisionReward` [1](#0-0) , or introduce a minimum staking duration before a deposit becomes eligible for freshly queued rewards.

### Proof of Concept
1. Attacker monitors `WombatPoolHelper.pendingWom()` and observes a large amount of unharvested WOM/bribe rewards accumulated in `MasterWombat`/`voter` for a given pool.
2. Attacker calls `WombatPoolHelper.deposit(_amount, _minimumLiquidity)`, which flows through `WombatStaking.deposit` → `MasterMagpie.depositFor` [9](#0-8) , minting shares in `BaseRewardPool` with no lockup.
3. Attacker (or anyone) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest(lpToken)` → `_toMasterWomAndSendReward` → `IBaseRewardPool.queueNewRewards` [2](#0-1) , which atomically updates `rewardPerTokenStored` for the whole batch based on current `totalStaked()` [1](#0-0) .
4. Attacker immediately calls `WombatPoolHelper.withdraw(_liquidity, _minAmount)` [10](#0-9) , which internally harvests (crediting `userRewards`) before removing the attacker's stake, letting them claim their full share of the batch's rewards despite having staked for only one transaction.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
