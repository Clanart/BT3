## Analysis

The Arrakis bug's core mechanism was: an arbitrary/attacker-controlled external call executed *between* a "before" state snapshot and an "after" state settlement, where the settlement logic trusted a derived/observed value (pool reserves) that could be manipulated by side effects triggered during that external call — allowing value duplication.

I found a structurally identical pattern in this repo's precompile balance-accounting mechanism, which is explicitly documented as a known bug class in the test suite itself.

### Title
Double-counted bank balance events during nested/recursive precompile calls cause EVM StateDB balance duplication - (File: precompiles/common/precompile.go, precompiles/common/balance_handler.go)

### Summary
The `BalanceHandler` mechanism used by every stateful precompile (`erc20`, `ics20`, `staking`, `distribution`, `bank`, `werc20`) reconciles Cosmos SDK bank events into the EVM `StateDB` by recording an event-index watermark (`prevEventsLen`) before a precompile call and replaying all `CoinSpent`/`CoinReceived` events emitted since that watermark afterward via `stateDB.AddBalance`/`SubBalance`. Because `sdk.Context.EventManager()` accumulates events for the entire transaction and is not scoped per nested call, a precompile call that triggers a **nested precompile call** (e.g., an ERC20 token's `_beforeTokenTransfer`/`transfer` hook calling `STAKING_CONTRACT.delegate()` or `DISTRIBUTION_CONTRACT.claimRewards()`, as demonstrated in `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol`) causes the same bank events to be captured and applied twice: once by the inner precompile's own `AfterBalanceChange` call, and again by the outer precompile's `AfterBalanceChange` call, since the outer call's watermark predates the inner call and its post-execution event slice still includes the events already consumed by the inner call.

### Finding Description
- `runNativeAction` in `precompiles/common/precompile.go` (lines 99-123) creates a fresh `BalanceHandler` per precompile entry via `p.BalanceHandlerFactory.NewBalanceHandler()`, calls `BeforeBalanceChange(ctx)` which stores `prevEventsLen = len(ctx.EventManager().Events())`, executes the action, then calls `AfterBalanceChange(ctx, stateDB)`. [1](#0-0) 
- `AfterBalanceChange` in `precompiles/common/balance_handler.go` iterates `events[bh.prevEventsLen:]` and applies `stateDB.AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived` event found in that slice. [2](#0-1) 
- If, during the outer precompile's `action(ctx)`, an EVM sub-call reaches a *second* precompile (e.g. staking or distribution) whose own `runNativeAction` also runs, that inner call snapshots its own `prevEventsLen` (a later index than the outer's) and applies its own bank-event delta to `stateDB` immediately. When control returns to the outer precompile and it later calls its own `AfterBalanceChange`, its window `events[outerPrevEventsLen:]` still contains those same inner events (since the shared `EventManager` never truncates), so the outer call re-applies the same `AddBalance`/`SubBalance` mutations a second time onto the `StateDB`.
- The repository's own test suites acknowledge and specifically target this mechanism: `evmd/tests/integration/balance_handler/balance_handler_test.go` is explicitly titled to test "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB" [3](#0-2) 
, and `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` is explicitly commented as testing "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated." [4](#0-3) 
- `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol` is a purpose-built PoC contract whose `_beforeTokenTransfer` hook calls `claimRewards()` (which calls `DISTRIBUTION_CONTRACT.claimRewards`) recursively up to 5 times inside a single ERC20 transfer, directly nesting a precompile call inside another precompile-triggered flow. [5](#0-4) 

This is functionally analogous to the Arrakis rebase-token bug: an attacker-reachable, ordinary transaction flow (calling `transfer`/hooks that legitimately call precompiles) causes a derived accounting value (StateDB balance, sourced from replaying bank events) to be updated using stale/already-consumed data, producing value duplication (unauthorized EVM balance minting) rather than requiring any privileged executor role.

### Impact Explanation
If confirmed to duplicate `AddBalance` deltas, this allows an unprivileged EVM contract deployer to construct a token/contract whose transfer hooks make nested precompile calls (staking delegate/undelegate, distribution claimRewards, ICS20 transfer, bank send) that legitimately move value once at the Cosmos SDK bank-keeper level but get credited **twice** to the corresponding address's EVM `StateDB` balance. This directly matches the "Critical unauthorized minting... irreversible accounting corruption of spendable user value across native balances... EVM balances" impact category, since it creates a divergence between actual bank-module-backed value and the EVM-visible balance that can subsequently be spent/transferred within the EVM.

### Likelihood Explanation
The trigger requires only deploying an ordinary Solidity contract (no elevated privileges) that combines an ERC20 transfer hook (or any callable function) with a nested call to a second stateful precompile — a pattern the repo's own maintainers built dedicated test contracts and test suites to reproduce (`ERC20RecursiveNonRevertingPrecompileCall.sol`, `balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`), indicating this is a known, actively-investigated internal concern rather than a theoretical one.

### Recommendation
I was not able to execute these tests or read their assertions to completion within this session, so I cannot confirm from static reading alone whether the currently-committed test assertions demonstrate a passing (bug present) or a corrected/guarded outcome (e.g., an assertion that specifically checks no double-counting occurs). The event-log-diffing approach itself (shared, un-scoped `ctx.EventManager()` combined with a per-call watermark) is structurally fragile for nested precompile calls; a robust fix would scope event capture per nested call (e.g., truncating/consuming processed events, or using a call-depth-aware event cursor) rather than relying on the tail-slice-since-watermark pattern.

### Proof of Concept
I could not produce a working, verified PoC within this session — reproducing this class requires running the existing `TestRecursivePrecompileCallsWithDebugPrecompile` and `ics20_recursive_precompile_calls_test.go` test flows against the actual `x/erc20`/`staking`/`distribution` precompiles (not the test-only debug precompile) and inspecting resulting `StateDB` balances vs. bank-keeper balances, which requires executing the Go test suite — a capability outside the scope of this read-only code search. The repository already contains scaffolding (`ERC20RecursiveNonRevertingPrecompileCall.sol`, `ics20_recursive_precompile_calls_test.go`) that appears purpose-built to exercise exactly this path; running `TestHandleMsgTransfer`/`TestRecursivePrecompileCallsWithDebugPrecompile` and diffing EVM balance vs bank balance after the recursive-hook transfer would confirm or refute duplication.

**Caveat / uncertainty**: I was unable to fully verify whether current guards (e.g., `stateDB.precompileCallsCounter` / `MaxPrecompileCalls` journal limits seen in `x/vm/statedb/statedb.go`, or event-index adjustments) already prevent double-application in the nested-precompile-call scenario, since I did not trace the complete call chain including how `AfterBalanceChange` interacts with `stateDB.CommitWithCacheCtx()`/journal reverts across nested `runNativeAction` invocations. This should be verified by actually running the referenced test suites before treating this as a confirmed, unpatched Critical finding.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
