### Title
Division-by-zero panic in KIP-71 base fee calculation via ungated `GasTarget=0` governance parameter - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `GasTarget` without any zero-guard, while the sibling parameter `BaseFeeDenominator` explicitly has a zero fallback. The governance parameter registry (`kaiax/gov/param.go`) fails to enforce `GasTarget != 0` — it uses `noopFormatChecker` instead of a nonzero check like the one applied to `BaseFeeDenominator`. A governance vote setting `kip71.gastarget` to `0` therefore propagates into every full node's per-block header validation and panics via `math/big` division by zero, crashing block processing chain-wide. This is the direct Kaia analog of the ImageMagick `resize.c` division-by-zero bug class (JLSEC-2026-880): an externally-influenceable numeric input reaches an unguarded division deep in core processing logic, producing an availability-impacting crash.

### Finding Description
`params/kip71_config.go` computes the next Magma-era base fee: [1](#0-0) 

Note the asymmetry: `BaseFeeDenominator == 0` is explicitly guarded and falls back to `64`: [2](#0-1) 

But `gasTarget := kc.GasTarget` has no such guard, and is used directly as a divisor: [3](#0-2) 
and again in the decreasing-base-fee branch: [4](#0-3) 

`x.Div(x, new(big.Int).SetUint64(gasTarget))` calls Go's `math/big.Int.Div`, which panics with "division by zero" when the divisor is zero.

The value of `GasTarget` originates from the governance parameter `kip71.gastarget`, registered in `kaiax/gov/param.go`: [5](#0-4) 

Unlike `Kip71BaseFeeDenominator`, which explicitly rejects zero: [6](#0-5) 

`Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, which accepts any `uint64` value including `0`: [7](#0-6) 

The resulting `ParamSet.GasTarget` is converted straight into a `KIP71Config` via `ToKip71Config`: [8](#0-7) 

`NextMagmaBlockBaseFee` (and thus the unguarded division) is invoked for **every** block, on **every** node, during header validation once the Magma hardfork is active: [9](#0-8) 

Since `parentGasUsed` is derived from `min(parentHeaderGasUsed, upperGasLimit)` and any real block has nonzero gas usage, once `GasTarget` reaches `0`, the `parentGasUsed > gasTarget` branch is taken on essentially every subsequent block, guaranteeing the panic at line 102 (or line 120 in the decrease branch) on all full nodes.

### Impact Explanation
A single successful governance vote setting `kip71.gastarget` to `0` (a value the format checker fails to reject) causes every node that validates block headers after that parameter takes effect to panic in `NextMagmaBlockBaseFee`. Because `blockchain/block_validator.go`'s `validateHeader` calls this on the consensus-critical path for all headers post-Magma, this is a chain-wide, network-availability-impacting bug: nodes crash while validating blocks, matching the "system availability" impact and `A:H` component of the referenced CVSS vector. This satisfies the "state divergence between honest nodes" / "acceptance-of-invalid-parameter causing halt" criteria, since it is the governance-parameter validation path itself that is missing an input-range check present for its sibling parameter.

### Likelihood Explanation
Likelihood is bounded by the fact that changing `kip71.gastarget` requires a governance vote (privileged governing-node action), which is why this maps to the explicitly in-scope "governance parameters" category rather than an anonymous-transaction-sender path. However, within that category there is no additional safeguard: the parameter passes the registry's `FormatChecker` (a no-op) and there is no compensating zero-guard in `NextMagmaBlockBaseFee`, unlike the equivalent `BaseFeeDenominator` case which was clearly hardened against this exact failure mode. This inconsistency strongly suggests the `GasTarget` zero-guard was simply omitted, not intentionally left open, making this a straightforward, single-parameter trigger rather than requiring a complex multi-step chain.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) in `kaiax/gov/param.go`, and/or add a defensive zero-guard fallback for `GasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, consistent with the existing `BaseFeeDenominator == 0` fallback.

### Proof of Concept
1. Submit/pass a governance vote (or malicious/misconfigured governance config) setting `kip71.gastarget = 0`. `PartialParamSet.Add("kip71.gastarget", 0)` succeeds because `Kip71GasTarget.FormatChecker` is `noopFormatChecker` (`kaiax/gov/param.go:324-334`, `160-162`).
2. Once the parameter takes effect at block `N+1` (post-Magma), any node processing block `N+1` calls `govParamSet.ToKip71Config().VerifyMagmaHeader(...)` in `blockchain/block_validator.go:207`.
3. `VerifyMagmaHeader` calls `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` with `kc.GasTarget == 0` (`params/kip71_config.go:50`).
4. Since any real block has `parentGasUsed > 0 = gasTarget`, execution enters the increase branch and executes `x.Div(x, new(big.Int).SetUint64(0))` at `params/kip71_config.go:102`, which panics in Go's `math/big` package with "division by zero", crashing the node's block-processing goroutine chain-wide.
