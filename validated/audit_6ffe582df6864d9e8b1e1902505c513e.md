The reported bug class relies on (1) roles being encoded as raw 4-byte function selectors and (2) an attacker-extensible mechanism (`_moduleCall`) that lets untrusted code register arbitrary new functions whose selector could collide with a privileged constant like `ROOT = 0x00000000`.

Sei-chain's precompile dispatch does not share this structure: precompile executors switch on the ABI-decoded `method.Name` string (not raw 4-byte selectors) [1](#0-0) , and access control for admin-only actions is enforced by keeper/module-level checks (e.g. `x/authz` grants keyed by full Cosmos `MsgTypeURL` strings) rather than by comparing a 4-byte selector to a hardcoded root value [2](#0-1) . The set of custom precompiles is a fixed, compiled-in map built once at startup by `InitializePrecompiles`/`GetCustomPrecompiles`, not something an unprivileged transaction sender, contract deployer, or RPC client can extend or redefine at runtime [3](#0-2) . The only "extensible" precompile registry in the codebase is the `giga/evmonly` custom precompile placeholder, which is explicitly out of scope per the analog-search rules (`giga/` excluded), and it is fail-closed anyway (`ErrCustomPrecompilesOpen` for any registered address) [4](#0-3) .

Since there is no reachable path where an untrusted actor can register a new "module" or function whose selector/identifier collides with a hardcoded privileged constant to escalate to root/admin authority, this bug class does not have a valid analog in the current sei-chain codebase.
