### Title
`depositFor` hardcodes zero slippage protection, enabling sandwich attacks on user deposits - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor` is the only deposit entry point in this contract that does not let the caller specify a minimum-liquidity (slippage) protection value. Unlike `deposit()` and `depositNative()`, which forward a user-supplied `_minimumLiquidity` down to the underlying Wombat pool, `depositFor` unconditionally passes `0`, removing any protection against price manipulation for that specific, publicly-callable path.

### Finding Description
`WombatPoolHelperV2.deposit()` and `depositNative()` both accept a `_minimumLiquidity` parameter from the caller and forward it through `_deposit` → `IWombatStaking.deposit` → `IWombatPool.deposit`, which uses it to revert if the LP minted is below the specified minimum: [1](#0-0) [2](#0-1) 

`depositFor`, however, hardcodes the minimum liquidity to `0` regardless of what value would be appropriate: [3](#0-2) 

This value flows unchanged into `WombatStaking.deposit`, which calls the Wombat AMM pool's `deposit` with `_minimumLiquidity` as the slippage guard: [4](#0-3) 

Because `depositFor` is externally callable by anyone for any `_for` address, and unconditionally supplies `0` as the minimum acceptable LP output, any deposit routed through this function has no protection against the pool's cash/liability ratio (and thus the LP-minting curve) being manipulated immediately before the deposit executes.

### Impact Explanation
An attacker can sandwich a `depositFor` call: front-run it with a large swap that skews the Wombat pool's cash/liability ratio unfavorably for depositors, let the victim's deposit mint a reduced amount of LP/receipt tokens (since `_minimumLiquidity = 0` cannot revert this), then back-run with an opposite trade to restore the pool state and capture the value that would otherwise have gone to the depositor. This is a direct extraction of value from user funds at deposit time, not a gas-only or no-impact issue.

### Likelihood Explanation
`depositFor` is a normal, permissionless external function intended for common use cases (e.g., relayed/gasless deposits, deposit-on-behalf-of flows), so it is realistically reachable by ordinary transactions. The asymmetry with `deposit()`/`depositNative()` (which do accept a caller-supplied minimum) indicates this is an implementation oversight rather than an intentional design choice, mirroring the reported UMA pattern where one code path lost a protective default that a sibling path retained.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (or otherwise compute/require a non-zero minimum) and forward it through `_deposit` the same way `deposit()` and `depositNative()` do, instead of hardcoding `0`.

### Proof of Concept
1. Attacker monitors mempool for a `WombatPoolHelperV2.depositFor(_amount, _for)` transaction.
2. Attacker front-runs with a large swap in the underlying Wombat pool to skew cash/liability, reducing LP minted per unit deposited.
3. Victim's `depositFor` executes with `_minimumLiquidity = 0` at `wombat/WombatPoolHelperV2.sol:106`, so it cannot revert even though LP minted is far below fair value.
4. Attacker back-runs with the reverse swap, restoring the pool and pocketing the value difference extracted from the victim's deposit.
