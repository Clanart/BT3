### Title
Unguarded division by zero in mempool block-building crashes transaction processing on a crafted duplicate-spend bundle - (File: `chia/full_node/mempool.py`)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes a per-item `item_cost = cost - cost_saving` and immediately divides `fee / item_cost` in a logging call, with no zero-check. Under the item-deduplication path (`IdenticalSpendDedup.get_deduplication_info`), `cost_saving` can equal the item's full cost when a mempool item consists solely of coin spend(s) that exactly duplicate a spend already committed earlier in the same block-building pass. This drives `item_cost` to `0`, causing an unguarded `ZeroDivisionError` — the same bug class as CVE-2020-16299 (division by zero from crafted/attacker-influenced input reaching a print/format routine without a zero guard), but here reachable from an ordinary submitted spend bundle rather than a crafted PDF.

### Finding Description
In `chia/full_node/mempool.py`, `create_bundle_from_mempool_items()` iterates mempool items ordered by priority to build a block: [1](#0-0) 
```

                    bundle_coin_spends, ff_state_update = singleton_ff.process_fast_forward_spends(...)
                    (
                        unique_coin_spends, cost_saving, atoms_saving, pairs_saving,
                        unique_additions, dedup_state_update,
```

`fee / item_cost` is a Python expression evaluated eagerly as an argument to `log.info(...)`, regardless of the configured log level — it is not gated by a lazy `%`-style format. If `item_cost == 0`, this raises `ZeroDivisionError` unconditionally.

`item_cost` is derived from `cost_saving`, computed in `IdenticalSpendDedup.get_deduplication_info()`: [2](#0-1) 
For every coin spend in the item that is `eligible_for_dedup` and whose `coin_id` already exists in `self.deduplication_spends` (i.e. an identical spend, with the identical solution, was already committed earlier in this same block-building pass via a different mempool item), `cost_saving` accumulates that spend's isolated cost. If a mempool item is composed entirely of such already-deduplicated coin spends (e.g., a single-coin spend bundle re-asserting the exact same offer/announcement-style coin spend that a previous mempool item already contributed to the block), `cost_saving` can equal `cost` (the item's total `SpendBundleConditions.cost`), driving `item_cost` to exactly `0`.

This dedup mechanism specifically exists to allow multiple independently-submitted spend bundles that spend the identical coin with an identical solution (e.g., competing fulfillments of the same offer/announcement) to coexist in the mempool, per `.cursor/context/mempool.md` and the pipeline notes on FF/DEDUP eligibility: [3](#0-2) 
An unprivileged wallet user/offer counterparty can trivially construct such a duplicate single-coin spend bundle and submit it via the normal `add_transaction` RPC path, which flows into `MempoolManager.validate_spend_bundle` / `add_to_pool`, and later into `create_bundle_from_mempool_items` during block construction: [4](#0-3) 

### Impact Explanation
The crash occurs inside the block-building routine (`create_bundle_from_mempool_items`), which full nodes/farmers call to assemble a transaction block from the mempool. An unhandled `ZeroDivisionError` there halts that block-building call, i.e. it is a spend-triggered transaction-processing halt reachable purely from mempool contents that an attacker fully controls by submitting ordinary spend bundles — matching the "Validate" criterion explicitly permitted in scope ("a spend-triggered transaction-processing halt"). This is analogous to the GhostScript CVE: a crafted, attacker-supplied input (there a PDF; here a spend bundle combination) reaches an unguarded division, causing a denial of service in a routine that must not fail.

### Likelihood Explanation
Reaching `cost_saving == cost` requires crafting a mempool item that: (1) is dedup-eligible (matches the criteria in `eligible_for_dedup`), (2) consists only of coin spend(s) whose costs exactly, cumulatively, equal `item.conds.cost` reported for the item, and (3) has that same coin/solution already committed earlier within the same block-building pass. This is a narrow, timing/ordering-dependent condition (the earlier identical-spend item must have already been selected for the same block being built), making it non-trivial but plausible for an attacker who controls both competing spend bundles (e.g., self-competing offer fulfillments) and observes mempool/block-building behavior. I was not able to fully verify from the available index whether `item.conds.cost` (the whole mempool item's reported cost) can *exactly* equal the sum of per-coin `spend_data.cost` values for single-coin items (i.e., whether there is always some non-per-coin baseline cost component that would prevent `item_cost` reaching precisely 0). This should be independently confirmed against `chia_rs`'s cost accounting (outside the indexed Python code) before treating this as fully proven.

### Recommendation
Guard the division in the log statement, e.g.:
```python
log.info(
    "Cumulative cost: %d, fee per cost: %s, item cost: %d",
    cost_sum, (fee / item_cost if item_cost else "inf"), item_cost,
)
```
and/or treat `item_cost == 0` as a defensive skip-and-continue case (similar to other cost-limit skip logic already present in this loop) before performing any division involving `item_cost`.

### Proof of Concept
Conceptual reproduction (exact per-coin cost accounting in `chia_rs` was not independently verifiable from the indexed code, so this is a hypothesis to validate in a live/test environment):
1. Construct an offer/announcement-style coin `C` whose puzzle can be spent by two independent wallets with the exact same solution (a common offer-settlement pattern).
2. Submit spend bundle `SB1 = {C-spend, feecoin-spend}` (pays fee via a second coin) to the mempool — it is admitted.
3. Have the full node begin block building; `SB1`'s `C`-spend gets recorded in `IdenticalSpendDedup.deduplication_spends` once included in the in-progress block.
4. Submit spend bundle `SB2 = {C-spend only}` with a nonzero fee, spending the same coin `C` with the identical solution (allowed because `eligible_for_dedup` bypasses the normal double-spend rejection for matching solutions) — it is admitted to the mempool as a second, competing item.
5. During the same block-building pass, when `SB2` is processed, `get_deduplication_info` returns `cost_saving == cost` for `SB2` (its only spend already matches the cached dedup entry), making `item_cost = cost - cost_saving = 0`.
6. `log.info("... %0.4f ...", cost_sum, fee / item_cost, item_cost)` raises `ZeroDivisionError`, aborting block construction for that call — repeatable each time an attacker resubmits such a duplicate-only bundle while a matching spend is mid-block. [5](#0-4) [6](#0-5)
