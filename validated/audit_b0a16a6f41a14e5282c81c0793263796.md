### Title
First re-voter after a fully-unvoted pool captures the entire queued bribe reward pool disproportionate to their stake - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2._provisionReward` (inherited by `BribeRewardPool`, the rewarder type used for Wombat bribe pools) queues any incoming reward into `rewardInfo.queuedRewards` whenever `totalStaked() == 0`, and only flushes the *entire* accumulated `queuedRewards` into `rewardPerTokenStored` on the next call where `totalStaked() > 0`. Because the flush divides the whole backlog by whatever the current `totalStaked()` is at that single flush moment (not by stake-time-weighted history), an attacker who is the first to re-stake a dust amount after a pool is fully unvoted can capture nearly 100% of previously queued rewards.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPoolV2.sol`: [1](#0-0) 
queues rewards when `totalStaked() == 0` and, on the very next provisioning call once stake is nonzero, adds the *whole* backlog to the current reward amount and divides by `totalStaked()` at that instant — crediting it entirely to whoever holds stake at that moment, with no accounting for when the reward actually accrued relative to when the staker entered.

`BribeRewardPool.totalStaked()` returns `totalSupply`, which is driven by `WombatBribeManager.vote()`/`unvote()` calling `stakeFor`/`withdrawFor`: [2](#0-1) [3](#0-2) 

Exploit flow:
1. All voters call `unvote()` on a pool, driving `BribeRewardPool.totalSupply` (and thus `totalStaked()`) to 0.
2. A bribe reward arrives for that pool via `WombatStaking.vote()` → `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)` (triggered by anyone calling `castVotes` or the permissionless `harvestSinglePool`): [4](#0-3) [5](#0-4) 
Since `totalStaked() == 0` at this point, the whole reward amount is pushed into `rewardInfo.queuedRewards` and sits there, benefiting no one yet.
3. Attacker (or anyone) can additionally call the fully public `donateRewards(_amountReward, _rewardToken)` on the rewarder to add more to the same queue, since it has no access control beyond `isRewardToken` check: [6](#0-5) 
4. Attacker calls `WombatBribeManager.vote()` with a minimal positive delta for that pool, which calls `BribeRewardPool.stakeFor(attacker, dustAmount)`, making `totalStaked()` nonzero and 100%-owned by the attacker: [7](#0-6) 
5. Attacker (or anyone) triggers `harvestSinglePool([lp])` again (a zero-delta vote that still harvests/queues any new bribe), which invokes `_provisionReward` while `totalStaked()` is now the attacker's dust amount. The entire backlog in `queuedRewards` is flushed into `rewardPerTokenStored`, divided by the tiny `totalStaked()`, producing a huge `rewardPerTokenStored` increase attributable almost entirely to the attacker's dust stake.
6. Attacker calls `claimBribe` → rewarder's `getReward`, capturing nearly the full queued reward.

Existing checks (`onlyManager` on `queueNewRewards`, `onlyOperator` on `stakeFor`/`withdrawFor`, `isRewardToken` on `donateRewards`) do not prevent this because they only gate *who* can call the functions, not *when* relative to `totalStaked() == 0`, and there is no time-weighted or per-epoch accrual mechanism to protect rewards queued while stake is zero.

### Impact Explanation
This results in theft of unclaimed yield that should be distributed pro-rata to all future re-voters of the pool, but is instead scooped almost entirely by whichever address is first to re-stake a dust amount after a full unvote. This matches the "theft of unclaimed yield" impact class specified in the prompt's scope.

### Likelihood Explanation
The precondition (a pool being fully unvoted, `totalSupply == 0`) is a normal, reachable on-chain state — it can happen naturally when governance sentiment shifts, or be induced/observed by a monitoring bot. `vote()`, `unvote()`, `harvestSinglePool()`, and `donateRewards()` are all permissionless/public functions callable by any vlMGP holder or any EOA. The attacker only needs a small amount of vlMGP (from locking a small amount of MGP they purchased) to place a dust vote, and can front-run the re-entry of legitimate voters since they control the timing of the second `harvestSinglePool` flush call. This is fully repeatable each time a pool cycles through zero total stake.

### Recommendation
Track reward accrual per staked amount only while `totalStaked() > 0`; instead of bulk-flushing a queued backlog to whichever staker happens to be present at the next nonzero-stake provisioning, either (a) refuse to queue rewards while `totalStaked() == 0` and instead redirect/hold them at the manager level until a fair distribution point, (b) require a minimum bootstrap stake or timelock before newly staked dust positions can claim from a pre-existing queued backlog, or (c) snapshot/distribute queued rewards proportionally based on stake established over a vesting/streaming window rather than an instantaneous flush.

### Proof of Concept
Foundry test plan:
1. Deploy `BribeRewardPool` (or use existing Wombat bribe rewarder) with `operator = WombatBribeManager` mock, reward token = mock ERC20.
2. Have voter A stake 1000 units via `stakeFor`, then fully `withdrawFor` (simulating full unvote) so `totalStaked() == 0`.
3. Call `queueNewRewards(1000e18, rewardToken)` (simulating a bribe harvest) as `onlyManager` — assert `rewards[rewardToken].queuedRewards == 1000e18` and `rewardPerTokenStored` unchanged.
4. Attacker calls `stakeFor(attacker, 1)` (dust stake, 1 wei unit) via the manager mock.
5. Call `queueNewRewards(0, rewardToken)` or any new small provisioning to trigger the flush — assert `rewardPerTokenStored` increases by `1000e18 * 10**decimals / 1`.
6. Assert `earned(attacker, rewardToken) ≈ 1000e18`, i.e., the attacker with 1 wei of stake captures ~100% of the 1000e18 queued reward, and call `getReward`/`claimBribe` to confirm actual token transfer of the full amount to the attacker despite contributing a negligible (dust) share of stake.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
