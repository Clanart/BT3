## Analog Found: `IntentGatewayV2.instance()` on Tron silently permits self-authentication for unregistered chains

### Title
Unregistered-chain fallback in Tron `IntentGatewayV2.instance()` lets a spoofed CREATE2-cloned contract authenticate as the gateway itself, bypassing peer authentication - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core defect is: multiple parallel implementations are supposed to share one security invariant, but only one implementation is audited/verified, while a sibling implementation quietly diverges and weakens the invariant. The exact same class of bug exists between the canonical EVM `IntentGatewayV2` (`evm/src/apps/intentsv2/IntentsBase.sol`) and its Tron port (`evm/tron/contracts/apps/IntentGatewayV2.sol`): both are meant to authenticate inbound cross-chain `RedeemEscrow`/`RefundEscrow` requests against a registered peer gateway address, but the Tron variant's `instance()` fallback behavior is different and unsafe.

### Finding Description
On the canonical EVM contract, resolving an unregistered state machine reverts: [1](#0-0) 

This is enforced by `_authenticate`, used to gate `RedeemEscrow`/`RefundEscrow` in `onAccept`: [2](#0-1) [3](#0-2) 

On the Tron port, the analogous `instance()` function does **not** revert for an unregistered `stateMachineId` — it silently falls back to `address(this)`: [4](#0-3) 

and `authenticate()` compares the inbound module against that same fallback-tolerant `instance()`: [5](#0-4) 

Because the gateway proxy is deployed deterministically via CREATE2 with a publicly known salt, implementation, and init data — explicitly so that "no peer address is embedded in the init data" and the address is "identical across chains" — the Tron gateway's own address is a public, reproducible value: [6](#0-5)  (same deterministic-CREATE2 design documented for the sibling implementation). An attacker can therefore deploy an identical-bytecode contract at the exact same address on any EVM chain that Hyperbridge can relay messages from but that has **not** been registered as a peer of the Tron gateway (i.e., no entry exists in `_instances` for that chain's hashed state machine id). Any `RedeemEscrow`/`RefundEscrow` `PostRequest` sent `from` that address, with `source` set to the unregistered chain, will pass `authenticate()` because `instance(unregistered_source)` resolves to `address(this)` — which equals `module` by construction — instead of reverting with `UnknownInstance` as the canonical implementation does.

### Impact Explanation
This breaks the "request/response paths must bind module identity and chain id" invariant called out in the pivots. An attacker who can get any Hyperbridge-relayed POST request accepted from an unregistered chain (using a contract deployed at the gateway's own address via the same CREATE2 recipe) can drive `RedeemEscrow`/`RefundEscrow` on the Tron `IntentGatewayV2`, releasing escrowed order funds to an attacker-chosen beneficiary/solver without ever being a legitimately registered peer gateway. This is direct theft/loss of escrowed bridge funds and unauthorized execution of a privileged code path (`onAccept`), not merely a compromised-relayer or malicious-peer scenario — the flaw is in the contract's own authentication logic, reachable by an ordinary unprivileged actor.

### Likelihood Explanation
The precondition (CREATE2-cloning a contract to the gateway's own address on an unpermissioned chain) is fully within an unprivileged attacker's control, since the salt/implementation/init-data are public/documented as identical-everywhere by design. The attack requires no relayer, prover, admin, or governance compromise — only that Hyperbridge can relay a message from the chosen unregistered chain and that the gateway's peer set is incomplete relative to all such chains (verified: `_instances` is populated only for a fixed `peerChains` list at deploy time). Likelihood is Medium-to-High, contingent on confirming the exact `onAccept`/withdrawal wiring in the Tron contract (see caveat below).

### Recommendation
Make `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` revert on an unregistered `stateMachineId`, matching the canonical `_instance()` behavior in `evm/src/apps/intentsv2/IntentsBase.sol` (`UnknownInstance`), instead of defaulting to `address(this)`. Alternatively, remove the fallback and require every chain to be explicitly registered before any inbound authentication can succeed from it.

### Proof of Concept
1. Attacker computes the Tron `IntentGatewayV2` proxy's deterministic CREATE2 address (public: implementation bytecode + `salt` + init data, per `evm/script/DeployIntentGateway.s.sol`).
2. Attacker deploys byte-identical contract to that same address via CREATE2 on an EVM chain reachable by Hyperbridge but **not** present in the Tron gateway's `peerChains`/`_instances` registrations.
3. From that contract, attacker dispatches a Hyperbridge POST request (`RedeemEscrow` or `RefundEscrow`, `WithdrawalRequest` body) targeting the real Tron `IntentGatewayV2`.
4. On relay, `onAccept` → `authenticate(request)` calls `instance(request.source)`; since `request.source` is unregistered, `_instances[...]` is zero and `instance()` returns `address(this)`, which equals `module` (the attacker's contract address). `Unauthorized` is never raised.
5. The withdrawal path executes, releasing escrowed tokens to the attacker-controlled beneficiary.

**Caveat:** I confirmed the vulnerable `instance()`/`authenticate()` logic directly, and confirmed via grep that `onAccept`, `RequestKind.RedeemEscrow`/`RefundEscrow`, and a `_withdraw`-equivalent (`withdraw`) exist in this file, but I did not get to read the full `onAccept` body in `evm/tron/contracts/apps/IntentGatewayV2.sol` (the tool budget ran out before that read completed) to verify line-for-line that `authenticate()` is invoked exactly as in the canonical `ExtrinsicIntents.onAccept`. The structural evidence (identical function names/error types/mapping design copied from the canonical contract, `cancelOrder`'s use of `instance()` and `withdraw()`) strongly supports this being the same call pattern, but this final wiring detail should be confirmed by a follow-up read of the full file before treating this as a fully confirmed exploit chain.
