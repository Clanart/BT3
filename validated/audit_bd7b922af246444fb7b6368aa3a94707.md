### Title
MasterMagpie's `updatePool` permanently loses a pool's MGP allocation whenever the pool's staked supply is temporarily zero - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie.updatePool()` computes each pool's share of the global `mgpPerSec` emission based on elapsed time and `allocPoint`. When a pool's staked supply (`lpSupply`) is zero, the function skips the accrual step entirely but still advances `lastRewardTimestamp` to the current block, discarding that period's emission allocation forever instead of queuing it, unlike the protocol's own reward pools which correctly defer emissions when supply is zero.

### Finding Description
In `updatePool`, if `lpSupply == 0`, the function returns early after only updating `lastRewardTimestamp`, without ever adding the corresponding `mgpReward` to `pool.accMGPPerShare`: [1](#0-0) 

Because `lastRewardTimestamp` is advanced to `block.timestamp` on this early return, the `multiplier = block.timestamp - pool.lastRewardTimestamp` used in the *next* successful update call will only reflect time elapsed after supply returns to non-zero. The MGP that would have been minted/allocated to this pool for `mgpPerSec * pool.allocPoint / totalAllocPoint` during the zero-supply window is never accrued into `accMGPPerShare` and is not queued anywhere for later distribution, unlike `_provisionReward` in `BaseRewardPoolV2` and `vlMGPBaseRewarder`, and `_queueNewRewardsWithoutTransfer` in `DelegateVoteRewardPool`/`mWOMSVBaseRewarder`, which all explicitly accumulate into `rewardInfo.queuedRewards` when `totalStaked() == 0` and later add it back once supply is nonzero: [2](#0-1) 

`_calMGPReward` (used for off-chain/frontend estimation, and mirrored by the on-chain `_calNewMGP`/harvest logic) exhibits the same skip-on-zero-supply behavior, confirming that no MGP is retroactively credited for the period the pool had zero supply: [3](#0-2) 

Since `lpSupply` is derived from users' own staking/withdrawal actions (`_calLpSupply`), an ordinary user can trivially trigger the zero-supply condition simply by withdrawing all staked tokens from a pool (e.g., the sole staker withdrawing), causing subsequent `updatePool`/`deposit`/`withdraw` calls to permanently skip that period's MGP emissions for the pool. This is the same root cause reported in the Blend `do_gulp_emissions` bug: an emission-distribution routine that advances its internal clock/state without accounting for periods when the underlying supply is zero, causing that share of emissions to be unclaimable by anyone forever.

### Impact Explanation
Any MGP emissions allocated to a pool during the period its stake balance is zero are permanently lost - they cannot be claimed by any user, past or future, since `accMGPPerShare` is never incremented for that time window and no queuing mechanism exists (unlike the fixed version used elsewhere in the codebase). This constitutes permanent freezing/loss of unclaimed yield, which affects all future depositors relying on the advertised `mgpPerSec` allocation for that pool.

### Likelihood Explanation
This can be triggered purely by unprivileged wallet activity: any pool that is fully unstaked (e.g., low-TVL pools, or the moment between the last withdrawal and next deposit) will silently lose its proportional MGP emissions for as long as it remains empty. No admin action or special configuration is required beyond the ordinary lifecycle of deposits/withdrawals, and low-liquidity pools transiently reaching zero supply is a realistic occurrence in this protocol's normal operation (similar to the "0 d_supply" scenario judged Medium in the original report).

### Recommendation
Mirror the pattern already used in `BaseRewardPoolV2._provisionReward` / `vlMGPBaseRewarder` / `mWOMSVBaseRewarder` / `DelegateVoteRewardPool`: when `lpSupply == 0` in `updatePool`, accumulate the skipped `mgpReward` into a per-pool `queuedRewards`-style variable instead of discarding it, and add that queued amount into the next successful `accMGPPerShare` accrual once `lpSupply > 0` again.

### Proof of Concept
1. Pool P has `allocPoint > 0` and `lpSupply > 0` with a single staker.
2. The staker calls `withdraw()` for their full balance, making `lpSupply == 0`.
3. Time passes (e.g., 1 day). During this time, `mgpPerSec * P.allocPoint / totalAllocPoint` worth of MGP is "owed" to pool P per the emission schedule.
4. Any call that triggers `updatePool(P)` (deposit, withdraw, `massUpdatePools`, `updateEmissionRate`, `updatePoolsAlloc`) executes the `lpSupply == 0` branch, setting `pool.lastRewardTimestamp = block.timestamp` without adding anything to `accMGPPerShare`.
5. A new staker deposits into pool P. Their rewards, and all future rewards, are computed only from the new `lastRewardTimestamp` forward.
6. The MGP corresponding to the elapsed zero-supply day is never accrued to any user's `rewardDebt`-adjusted balance and cannot be claimed by anyone — it is permanently lost from the pool's effective reward pool.

```text
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }    
```

```text
    function _calMGPReward(address _stakingToken, address _user) internal view returns(uint256 pendingMGP) {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_user];
        uint256 accMGPPerShare = pool.accMGPPerShare;
        uint256 lpSupply = _calLpSupply(_stakingToken);

        if (block.timestamp > pool.lastRewardTimestamp && lpSupply != 0) {
            uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
            uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) /
            totalAllocPoint;
            accMGPPerShare = accMGPPerShare + (mgpReward * 1e12) / lpSupply;
        }

        pendingMGP = (user.amount * accMGPPerShare) / 1e12 - user.rewardDebt;
        pendingMGP += unClaimedMgp[_stakingToken][_user];
    }
```
