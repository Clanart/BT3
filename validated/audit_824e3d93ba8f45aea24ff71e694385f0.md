## Finding: Missing ERC-20 return-value validation in `withdraw()` lets a malicious input token silently "successfully" burn escrow without paying the beneficiary

The reported bug class — comments/docstrings claiming a guarantee ("tokens are burned/withdrawn/sent") that the code doesn't actually enforce — has a direct, exploitable analog in the Tron variant of the IntentGatewayV2 contract, in escrow release for intent settlement.

### Title
Unchecked low-level ERC-20 transfer in `withdraw()` lets a malicious order-input token silently swallow escrow, causing permanent fund loss to the rightful beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, the internal function that releases escrowed order inputs to a filler (on `RedeemEscrow`) or refunds the user (on `RefundEscrow`/cancellation), moves ERC-20 tokens with a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treats the call as successful whenever it does not revert, without decoding the returned boolean. [1](#0-0)  This is the exact "docstring vs. implementation" mismatch pattern from the seed report: the function's own doc says it "Withdraws the escrowed tokens for a request body" [2](#0-1) , but the implementation only guarantees the *call did not revert* — not that tokens actually moved.

### Finding Description
`placeOrder()` lets any caller escrow an arbitrary ERC-20 address as an order input with no allowlist. [3](#0-2)  An attacker can therefore place an order whose input token is a contract they fully control, one that implements `transfer()` to `return false` (a legal, non-reverting ERC-20 failure signal used by several real-world tokens) whenever the recipient is not the attacker.

When the order is later filled and the destination dispatches a `RedeemEscrow` message back to release the escrowed input to the filler, `onAccept` calls `withdraw(body, false)`:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    ...
    _orders[body.commitment][token] -= amount;
``` [4](#0-3) 

`success` only reflects whether the external call reverted, not whether the token actually transferred value; a token returning ABI-encoded `false` makes `success == true`. The code then decrements the internal escrow ledger and emits `EscrowReleased`, permanently finalizing settlement, while the filler receives zero tokens.

This is a real divergence from the canonical EVM implementation, which correctly uses `SafeERC20.safeTransfer`, reverting on a `false` return: [5](#0-4)  The Tron contract dropped that guard in favor of a raw `.call`, which is used identically (with the same flaw) for `SweepDust` and the transaction-fee payout inside the same function. [6](#0-5) [7](#0-6) 

Existing guards do not stop this: `authenticate()` only checks that the incoming message's `from` matches a known peer instance [8](#0-7) , and the escrow existence check `if (_orders[body.commitment][token] == 0) revert UnknownOrder()` only checks the escrow ledger is non-zero, not that a real transfer occurred. [9](#0-8)  None of these validate the semantic outcome of the ERC-20 call.

### Impact Explanation
This directly violates "bridged assets, order escrow, refunds ... must move exactly once and only to the rightful beneficiary and amount." Here escrow is marked settled/refunded and the internal ledger is decremented (`_orders[...] -= amount`, `_filled[commitment] = beneficiary`), but the rightful beneficiary (filler who already delivered the output on the destination chain, or a user awaiting refund) receives nothing. The value is neither returned to escrow nor paid out — it is permanently stuck/lost, and settlement cannot be retried since `_filled`/`_orders` state has already advanced. This is a direct loss-of-funds bug reachable by an unprivileged attacker who simply chooses the input token when placing their own order — no relayer, prover, or admin compromise required.

### Likelihood Explanation
High for any deployment that allows arbitrary ERC-20 addresses as order inputs (which `placeOrder` does, with no allowlist). Non-reverting `false`-returning ERC-20s are a well-documented and common real-world pattern (deliberately or accidentally), and an attacker can trivially deploy a bespoke token that returns `false` selectively based on the recipient address to target fillers while keeping their own deposit path (`transferFrom` during `placeOrder`, which does use `safeTransferFrom` via `IERC20`, not affected) functioning normally.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (and the identical pattern in `onAccept`'s `SweepDust` branch and the fee payout) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the canonical `IntentsBase.sol` implementation, so that a `false` return value causes a revert instead of silently finalizing settlement.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer(to, amount)` returns `false` (without reverting) whenever `to != attacker`, and behaves normally for `transferFrom` during deposit.
2. Attacker calls `placeOrder` on the source chain with `EvilToken` as `order.inputs[0].token`, escrowing `amount` of `EvilToken` into `_orders[commitment][EvilToken]`. [3](#0-2) 
3. A filler fills the order on the destination chain, delivering the promised output to the attacker there.
4. The destination dispatches `RedeemEscrow` back to the source `IntentGatewayV2`; `onAccept` calls `withdraw(body, false)` with `beneficiary = filler`.
5. `EvilToken.transfer(filler, amount)` returns `false` (call succeeds, `success == true`); `_orders[commitment][EvilToken] -= amount` executes and `EscrowReleased` is emitted, finalizing settlement.
6. The filler has delivered the output but received none of the escrowed `EvilToken`; the funds are stuck in the contract, unrecoverable through normal settlement paths.
