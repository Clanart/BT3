### Title
Scanner accepts dust/unspendable outputs as `ReceivedOutput`s, causing Serai to spend inputs worth less than the fee they add - (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_transaction` registers any transaction output whose `script_pubkey` matches a registered script, with no lower bound on the output's value. Outputs at or below the dust threshold (546 sats, or the processor's own 10,000-sat `DUST` constant) — which cost more in fee weight to spend than they contribute — are reported as spendable `ReceivedOutput`s. An unprivileged attacker can send dust-valued P2TR outputs to a Serai multisig address; each such output is later consumed as an input by `SignableTransaction::new`, where it adds ~57 vbytes of fee weight while contributing less value than that fee, silently draining wallet funds. This mirrors the reported bug class: a missing zero/minimum check on a received value lets an attacker extract value by supplying economically-negative "collateral".

### Finding Description
`scan_transaction` pushes a `ReceivedOutput` for every output matching `self.scripts`, inspecting only `output.script_pubkey` and never `output.value` (networks/bitcoin/src/wallet/mod.rs:199-214). `ReceivedOutput` is documented as "A spendable output" (line 88), yet an output worth 1 satoshi is not spendable: Bitcoin Core's dust relay rule (referenced by `DUST` in send.rs:27-32) makes sub-546-sat outputs unspendable in practice, and even outputs in the 546–10,000 sat range are uneconomical per the processor's own `DUST = 10_000` rationale (processor/src/networks/bitcoin.rs:606-638, which computes ~285+ sats of fee per input at 5 sat/vB and requires 10,000 sats minimum).

When such outputs are later passed to `SignableTransaction::new`, each one increases `input_sat` by its dust value but increases `needed_fee` by `fee_per_vbyte * ~57` (the per-input vbyte cost embedded in `calculate_weight_vbytes`, send.rs:68-94 and 204-206). For any input worth less than `fee_per_vbyte * 57`, inclusion is net-negative: the wallet burns more in fees than the input provides, and the `NotEnoughFunds` check at send.rs:215 treats the dust sats as real funds. Neither the scanner nor the transaction builder filters sub-threshold inputs.

### Impact Explanation
Any party that learns a Serai deposit address (public on-chain) can grief the multisig by sending dust outputs to it. Each dust output is scanned, stored, and eventually included as a transaction input, costing the wallet `fee_per_vbyte * 57 - value` sats each — a forced, unbounded economic drain proportional to how many dust outputs the attacker broadcasts. Additionally, outputs below the relay dust limit represent funds "received" (counted in `input_sat`) that are not actually spendable, potentially causing `NotEnoughFunds` accounting to overestimate available balance — the same "credited value without real collateral" shape as the reference bug where `quoteAmount` rounding to 0 credited option tokens for free.

### Likelihood Explanation
Exploitation requires only sending ordinary Bitcoin transactions to a known address — fully unprivileged and cheap (sub-dust outputs cost the attacker <546 sats each). The condition triggers deterministically since scanning has no value check. The constraint is that impact accrues in small units per output (bounded by per-input fee weight), so meaningful drain requires many dust outputs or elevated fee rates; this keeps it below High severity.

### Recommendation
Enforce a minimum value when accepting outputs: either in `Scanner::scan_transaction`/`scan_block` (skip outputs with `output.value.to_sat() < DUST`), or in `SignableTransaction::new` (reject or skip `ReceivedOutput`s whose value is below the per-input fee contribution `fee_per_vbyte * input_vbytes`). The processor-side `DUST = 10_000` threshold is the appropriate bound for "spendable" classification.

### Proof of Concept
1. Obtain the Serai multisig's P2TR `script_pubkey` (public on-chain).
2. Broadcast transactions paying 100 sats each to that script — e.g., 50 outputs, costing the attacker ~5,000 sats.
3. `Scanner::scan_block`/`scan_transaction` returns 50 `ReceivedOutput`s (networks/bitcoin/src/wallet/mod.rs:205-211).
4. `SignableTransaction::new` includes all 50 as inputs: `input_sat` gains 5,000 sats, but `needed_fee` gains `50 * 57 * fee_per_vbyte`. At 10 sat/vB that's 28,500 sats of added fee — a net ~23,500 sat loss to the wallet from the attacker's 5,000-sat spend, and below relay minimums the 100-sat outputs would be reported as spendable funds while being effectively unspendable.
