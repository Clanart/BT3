### Title

Untrusted `ReceivedOutput` deserialization accepts nonexistent outputs as spendable inputs - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

`ReceivedOutput::read` reconstructs a spendable wallet output entirely from attacker-controlled bytes without authenticating that the referenced Bitcoin outpoint exists or belongs to the wallet. The declared `offset`, `TxOut`, and `OutPoint` are trusted verbatim. `SignableTransaction::new` subsequently uses the deserialized value and outpoint to construct a transaction, while `SignableTransaction::multisig` only checks that the embedded `script_pubkey` matches the wallet-derived output script.

An attacker can therefore serialize a `ReceivedOutput` containing the wallet’s public P2TR script, an arbitrary value, and a fake outpoint. Code accepting serialized outputs from an untrusted source can report unavailable funds as received and attempt to sign a transaction spending nonexistent coins.

### Finding Description

`ReceivedOutput::read` performs only decoding:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)?;
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
Ok(ReceivedOutput { offset, output, outpoint })
``` [1](#0-0) 

No chain proof, scanner registration, output-key derivation, or outpoint lookup is performed.

`SignableTransaction::new` trusts the decoded output’s value for fee and balance calculations and uses the decoded outpoint directly as a transaction input. [2](#0-1) 

`SignableTransaction::multisig` verifies only that `prevouts[i].script_pubkey` equals the script produced by tweaking the threshold key with the supplied offset. [3](#0-2) 

Because the script is public and reproducible, this check does not establish that the claimed outpoint exists or contains the encoded amount.

### Impact Explanation

An unprivileged party who can submit serialized `ReceivedOutput`s can cause a wallet to treat arbitrary Bitcoin outputs as spendable funds. The attacker can fabricate:

- an arbitrary input value;
- a nonexistent or spent `OutPoint`;
- a valid-looking P2TR script belonging to the target wallet.

The constructed transaction cannot obtain a valid blockchain UTXO, so the reported funds are not actually spendable. Depending on the caller, this can corrupt balance accounting, reserve unavailable funds, or induce signing and broadcasting transactions that can never confirm. The resulting signature itself is for a transaction generated from fake input data; the more direct wallet impact is falsely recognizing nonexistent received funds.

### Likelihood Explanation

The attack requires an application to deserialize `ReceivedOutput`s supplied by an untrusted party rather than producing them through `Scanner::scan_transaction` or `Scanner::scan_block`. That trust boundary is not enforced by the API: `ReceivedOutput::read` is public and returns an object indistinguishable from one produced by chain scanning.

The attacker needs only know a wallet script/address, which is public, and encode a matching `TxOut` plus a fabricated `OutPoint`. No key compromise, validator collusion, malformed curve encoding, or protocol deviation is required.

### Recommendation

Treat `ReceivedOutput` bytes as a transport encoding for already-authenticated scan results, not as proof of ownership. Before constructing a `SignableTransaction`, verify every decoded output against trusted Bitcoin chain data:

1. Resolve the claimed `OutPoint`.
2. Confirm it is unspent and has required maturity.
3. Confirm the chain `TxOut` exactly equals the deserialized `TxOut`.
4. Confirm the script corresponds to a scanner-registered offset.
5. Persist or transmit an authenticated scanner provenance/tag if deserialized records may cross a trust boundary.

The validation could be integrated into wallet construction or provided by an explicit authenticated-storage reader rather than relying on callers to infer that `ReceivedOutput::read` performs only syntactic decoding.

### Proof of Concept

Conceptually:

1. Obtain the target wallet’s public P2TR `ScriptBuf`.
2. Create a `TxOut` with that script and an arbitrary large value.
3. Create an arbitrary `OutPoint`, such as a random transaction ID and `vout = 0`.
4. Encode a canonical scalar offset appropriate for the script, followed by consensus encodings of the fake `TxOut` and `OutPoint`.
5. Feed those bytes to `ReceivedOutput::read`.
6. Pass the resulting value to `SignableTransaction::new`.
7. Call `SignableTransaction::multisig` with the corresponding wallet keys.

The output passes `ReceivedOutput::read`, is counted as an input, and passes the script check in `multisig`, even though no such spendable output necessarily exists.

  /// Read a ReceivedOutput from a generic satisfying Read.
  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
