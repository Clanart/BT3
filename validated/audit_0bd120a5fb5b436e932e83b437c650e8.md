### Title
Untrusted `ThresholdKeys` fields can bind a victim to an attacker-controlled group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled threshold parameters, interpolation data, secret share, and verification shares, but `ThresholdKeys::new` only validates the participant ranges and derives the group key from the first `t` verification shares. It does not authenticate the serialized key package or prove that all verification shares belong to one threshold polynomial. A crafted package can therefore make participant 2 use an attacker-selected key controlled by participant 1’s verification share. During FROST completion, a valid aggregate signature is returned before individual signature shares are checked, allowing the attacker to supply a compensating scalar share. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The deserializer reads `t`, `n`, `i`, an interpolation selector, one scalar secret share, and `n` verification-share points directly into `ThresholdKeys::new`. For `Interpolation::Lagrange`, `new` computes `group_key` by interpolating only participants `1..=t` over the supplied verification shares; it does not check that the local `secret_share` corresponds to `verification_shares[i]` or that the other verification shares encode the same polynomial. [4](#0-3) [5](#0-4) 

For example, `t=1`, `n=2`, `i=2`, Lagrange interpolation, a chosen victim share `x`, `verification_shares[1]=aG`, and `verification_shares[2]=xG` deserialize successfully and produce `group_key=aG`. In signing set `{1,2}`, participant 2’s Lagrange factor is `-1`, while participant 1’s factor is `2`; these shares are interpolated independently from the attacker-supplied verification-share map. [6](#0-5) [7](#0-6) 

`SignatureMachine::read_share` accepts any canonical scalar as another participant’s response, and `complete` first returns a signature whenever the scalar sum verifies against `view.group_key()`. Per-participant verification-share statements are checked only after that aggregate success path, so an attacker who knows the crafted secret material can calculate the scalar that makes the aggregate valid and bypass individual-share detection. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who supplies the serialized threshold-key package can cause the victim’s FROST machine to emit a valid Schnorr signature under an attacker-selected group key rather than a correctly formed threshold key. The result is a cryptographically valid signature for an unintended public key and constitutes signing-key-context injection through malformed key metadata. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
The attack requires an untrusted party to provide or alter the serialized `ThresholdKeys` consumed by a signer and then participate as one of the declared signing parties. Both prerequisites are within the allowed input surface for `ThresholdKeys::read` and `read_share`; the crafted fields are all canonical and therefore pass the existing encoding checks. The main constraint is that the attacker must know the secret-share scalar encoded in the package to calculate the compensating response. [1](#0-0) [12](#0-11) 

### Recommendation
Do not accept `ThresholdKeys` bytes from an unauthenticated source; serialize them only from a trusted DKG/dealer result or protect them with authentication bound to the expected group key. On deserialization, additionally verify that `C::generator() * secret_share == verification_shares[i]`, and include enough authenticated DKG/VSS data to prove that every verification share belongs to the same threshold polynomial. Individual share verification should also occur before accepting an aggregate signature whenever key material is not trusted. [13](#0-12) [9](#0-8) 

### Proof of Concept
Construct a serialized `ThresholdKeys<C>` record with:

```text
curve-id       = C::ID
t              = 1
n              = 2
i              = 2
interpolation  = 1                    // Lagrange
secret_share   = x                    // scalar known to attacker
vshare[1]      = a*G                  // attacker knows a
vshare[2]      = x*G
```

`ThresholdKeys::read` accepts this object because every participant index and scalar/point encoding is well-formed. `ThresholdKeys::new` derives `group_key` solely from participant 1, so `group_key == a*G`. For signing set `{1,2}`, participant 2 produces `z2 = r2 - c*x`; participant 1 submits `z1 = r1 + c*(a+x)`, where `r1` and `r2` correspond to the bound nonce commitments. The resulting `R=r1G+r2G` and `s=z1+z2=r1+r2+c*a` satisfy `sG=R+c(aG)`, so `complete` returns the signature before checking either share against its declared verification share.
