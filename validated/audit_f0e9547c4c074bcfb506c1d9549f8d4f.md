### Title
`ReceivedOutput::read` deserializes a spendable-output claim without validating the key-derivation checks enforced via `p2tr_script_buf`'s `Option` return — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The original finding is an unchecked boolean return from `transferFrom`: an operation that signals success/failure via its return value is invoked without inspecting that value, so a failure is silently treated as success. The analog in Serai is the Taproot key-parity/script-derivation check. `p2tr_script_buf` returns `Option<ScriptBuf>` — `None` whenever the key is odd-Y or infinity — and every *trusted* construction path (`Scanner::new`, `Scanner::register_offset`, `SignableTransaction::multisig`) is obligated to inspect that `Option`. The untrusted deserialization path, `ReceivedOutput::read`, never performs the check at all: it accepts arbitrary bytes for `offset`, `TxOut`, and `OutPoint` and produces a struct that claims to be a spendable output with no proof that `offset` derives `output.script_pubkey`.

### Finding Description
- `p2tr_script_buf` returns `None` for odd/infinity keys (`networks/bitcoin/src/wallet/mod.rs:80-86`).
- `Scanner::new` (`mod.rs:162-166`) and `Scanner::register_offset` (`mod.rs:180-196`) check the `Option` and even increment the offset until a valid script exists. `register_offset`'s doc notes offsets must be "securely generated" because arbitrary offsets can introduce a spendable script path (`mod.rs:174-179`).
- `SignableTransaction::multisig` re-verifies `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey` before signing (`send.rs:275-281`).
- `ReceivedOutput::read` (`mod.rs:122-134`) performs none of this: `Secp256k1::read_F` for the scalar, then raw consensus decode of `TxOut`/`OutPoint`. A byte string produced by an untrusted writer can encode any offset for any script_pubkey — including an offset that yields an odd-Y key (unspendable under BIP-340), an offset that yields a *different* tweaked key than the script commits to, or an offset that introduces an attacker-known script path.

The Result/`Option` value is effectively "not checked" on this path: the invariant the return value encodes is skipped entirely at the trust boundary where untrusted bytes enter the system.

### Impact Explanation
A `ReceivedOutput` obtained from untrusted bytes represents "funds received and spendable under a known scalar offset." Any consumer that deserializes such records (e.g., persisted or transported scanner output) and treats them as spendable accepts outputs that either (a) cannot be signed for — `multisig` returns `None` / signing fails, making the reported funds unspendable — satisfying "funds reported received that are not spendable"; or (b) embed a script path the offset-holder did not intend, since no derivation check binds `offset` to `output.script_pubkey`. In case (a), a `SignableTransaction` built over the poisoned output fails mid-flow, potentially stalling the signing session for all co-inputs.

### Likelihood Explanation
Reachable by any unprivileged party able to feed bytes to `ReceivedOutput::read` (an explicitly exposed deserialization API on the spendable-output type). Exploitation requires a consumer that acts on deserialized outputs without re-running `scan_transaction`-equivalent validation; the struct provides no marker distinguishing scanner-produced from byte-produced instances, so this is a realistic misuse surface rather than a documented-MUST violation — the type system does not enforce the check.

### Recommendation
At minimum, `ReceivedOutput::read` should validate the deserialized output: reject if `p2tr_script_buf(base_key + G*offset)` is `None` or does not equal `output.script_pubkey`. Since `read` lacks the base key, a cleaner fix is to make `ReceivedOutput` construction private to `Scanner` (i.e., only `scan_transaction`/`scan_block` may create one), and have deserialization take the scanner/key as a parameter so the offset-to-script binding is re-verified on decode — mirroring how `multisig` already re-checks before signing.

### Proof of Concept
```rust
// Crafted bytes: offset=1, a TxOut whose script_pubkey is the P2TR of some
// unrelated key K' (never derived from base+G*1), any OutPoint.
let mut bytes = Vec::new();
bytes.extend(Scalar::ONE.to_bytes());
bytes.extend(serialize(&TxOut { value: Amount::from_sat(100_000), script_pubkey: attacker_script }));
bytes.extend(serialize(&OutPoint::new(txid, 0)));

let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // succeeds — no derivation check
// ro claims spendability; SignableTransaction::new(vec![ro], ...) builds a TX;
// multisig(keys) returns None -> funds reported received but not spendable,
// or an attacker-chosen script path is accepted without detection.
```
Key lines: `mod.rs:122-134` (unchecked `read`), `mod.rs:80-86` (the `Option` return encoding the invariant), `send.rs:275-281` (the check that exists on the signing path but not the decode path).
