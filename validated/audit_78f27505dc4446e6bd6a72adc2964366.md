### Title
ProtoJSON encoder in the upb runtime (used by PHP and Ruby native extensions) omits XSS-hardening escapes for `<`, `>`, `&` that the Java/C++/C# ProtoJSON encoders apply - (File: `upb/json/encode.c`)

### Summary
The Java (`JsonFormat.java`), C++ (`json/internal/writer.cc`), and C# (`JsonFormatter.cs`) ProtoJSON string encoders all escape the characters `<`, `>`, `&`, `=`, `'` (and several Unicode line/format separators) as `\uXXXX` even though they are legal, unescaped JSON characters, specifically to defend against the well-known JSON-embedded-in-`<script>` XSS class (the same bug class as GHSA-9r27-994c-4xch, where a markdown-to-HTML renderer failed to escape `<`/`>`/`&` in one code path while other paths did escape them). The upb C JSON encoder (`upb/json/encode.c`, shared verbatim into `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`) implements only the RFC 8259-mandated escapes and passes `<`, `>`, `&`, `=`, `'` straight through as raw UTF-8 bytes.

### Finding Description
The invariant that fails to transfer uniformly across Protobuf's ProtoJSON implementations is: "string field values must have HTML/JS-significant characters escaped in JSON output, as defense-in-depth against callers who embed protobuf-generated JSON into HTML/`<script>` contexts."

- In Java, `JsonFormat.java`'s `printStringEscapedAndQuoted` builds a `replacementChars` table that explicitly escapes `<>&='` "to prevent XSS risks" [1](#0-0) , and this is regression-tested for exactly the `</script>` injection pattern [2](#0-1) .
- In C++, `json/internal/writer.cc`'s `MustEscape` explicitly escapes `<` and `>` "to prevent security bugs in JavaScript" [3](#0-2) , applied via `WriteEscapedUtf8`'s unsafe-char set which also includes `<`/`>` [4](#0-3) .
- In C#, `JsonFormatter.cs`'s `WriteString` follows the same "prevent security bugs in javascript" comment and escapes a matching set of characters [5](#0-4) .
- In the upb C runtime, however, `jsonenc_put_escaped_char` only implements the JSON-spec-mandated escapes (`\n \r \t \" \f \b \\` and control chars `< 0x20`); every other byte, including `<`, `>`, `&`, `=`, `'`, is written through unmodified via `jsonenc_putbytes` [6](#0-5) . The identical function body is duplicated verbatim in the PHP native extension [7](#0-6)  and the Ruby native extension [8](#0-7) .

This is a straightforward serialization-time missing-escape defect: an attacker-controlled string field value (delivered via a bounded, valid Protobuf binary or JSON parse — trusted schema, no malformed input needed) that contains `</script>` or similar HTML-significant sequences is serialized back to ProtoJSON by the upb-backed PHP/Ruby runtimes without the same escaping that Java/C++/C# apply, while the generated JSON is expected by consuming applications to carry the same "safe to embed in HTML" guarantee that the other language runtimes document and test for.

### Impact Explanation
Applications that trust protobuf's ProtoJSON output as safe for embedding into HTML `<script>` blocks (a documented protobuf design goal, evidenced by the dedicated `testHtmlEscape` regression test tied to bug b/73832901) receive a false safety guarantee when using PHP or Ruby (or any consumer of `upb/json/encode.c`): a string field such as `optional_string = "</script><script>evil()</script>"` will be serialized with the raw `<`/`>` characters intact, enabling script injection/XSS in the consuming web application, exactly mirroring the discord-markdown class of bug (escaping applied inconsistently across code paths that should share one invariant).

### Likelihood Explanation
High likelihood of reachability: the vulnerable code path is the default, un-opted ProtoJSON serialization function (`upb_JsonEncode`/`jsonenc_string`) invoked whenever a PHP or Ruby application calls the standard "to JSON" method on any message containing a `string`/`bytes` field, with no special options required. The only precondition is that the application embeds protobuf's JSON output into an HTML/JS context — a usage pattern protobuf itself anticipates and defends against in its other language runtimes.

### Recommendation
Add the same HTML/JS-unsafe character escaping set used in `src/google/protobuf/json/internal/writer.cc`'s `MustEscape` (and Java's `JsonFormat` / C#'s `JsonFormatter`) to `upb/json/encode.c`'s `jsonenc_put_escaped_char`/`jsonenc_stringbody`, at minimum escaping `<`, `>`, `&`, `=`, `'`, and propagate the fix into the vendored copies in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c` (these appear to be generated/vendored from the upb source, so the generation script should be re-run rather than hand-patched).

    static constexpr absl::CharSet kUnsafeChars =
        ~absl::CharSet::AsciiPrintable() | absl::CharSet("\"\\<>");

    auto [safe_prefix, rest] = SplitAtFirst(str, kUnsafeChars);

      Write(safe_prefix);
      str = rest;

        break;

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
