### Title
Desktop Silently Rewrites a Repository's Git Remote URL Based on an Untrusted GitHub API Response - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` automatically runs `git remote set-url` on a repository's `origin` remote whenever the GitHub API's `clone_url` for the matched repository differs from the locally configured remote, with **no user confirmation, no diff/warning dialog, and no check that the new URL still points to the same repository the user originally added**. Because the owner/name used to query the API is re-derived from the *current* git remote URL on every refresh (via `matchGitHubRepository`), and the update is applied automatically whenever GitHub reports a different `clone_url` for that owner/name, this creates a silent-remote-hijack primitive whenever the value returned by the GitHub API for that repository changes to point somewhere else (e.g. after an ownership transfer, or if the account is talking to a GitHub Enterprise endpoint/on-path server that can shape the API response).

### Finding Description
`repositoryWithRefreshedGitHubRepository` re-resolves the GitHub repository on essentially every refresh cycle (fetch/push/background indicator refresh): [1](#0-0) 

It calls `matchGitHubRepository(accounts, remote)` (via `this.matchGitHubRepository`), which derives `owner`/`name` purely by parsing the repository's **current git remote URL** — not from any immutable GitHub repository ID stored locally: [2](#0-1) 

It then fetches `repos/{owner}/{name}` from the GitHub API and hands the raw API object straight to `updateRemoteUrl`: [3](#0-2) 

`updateRemoteUrl` performs only three checks before rewriting the remote: (1) the URL protocol (`https`/`ssh`) hasn't changed, (2) the current remote still matches the previously cached `cloneURL` (i.e. the user hasn't manually customized it), and (3) the new `clone_url` differs from the current one. If all three hold, it calls `gitStore.setRemoteURL`, which shells out to `git remote set-url`: [4](#0-3) [5](#0-4) 

None of these checks verify that the *identity* of the repository (e.g. a stable numeric GitHub repo id) is preserved — only that the string values are internally consistent. The broken invariant is: **"the remote URL Desktop pushes to/fetches from should only change when the user explicitly configures it, or the on-disk repository is provably the same GitHub repository."** Here, the only source of truth is the API's `clone_url` string for whatever `owner/name` the *current remote* resolves to, which is exactly the kind of externally-controlled value the seed report's `totalBPTSupply`/threshold check represents: a value derived from the current state that an outside party can influence, used to unconditionally drive a state-changing, no-confirmation operation.

### Impact Explanation
If the value returned by the GitHub API for a matched `owner/name` changes to point at a different underlying repository — e.g., the repository is transferred to (or reclaimed/re-registered by) a different, attacker-controlled owner, or a compromised/malicious GitHub Enterprise Server endpoint returns a different `clone_url` for the same query — Desktop will silently repoint the user's local `origin` remote to that URL on the very next background refresh, without any dialog, confirmation, or visible diff. From that point forward:
- All subsequent `git push` operations from Desktop silently upload the user's commits to the new (attacker-controlled) remote.
- All subsequent `git fetch`/`pull` operations silently pull content from the new remote into the user's working copy.

This is a silent corruption of what the user pushes/fetches — the user believes they are still working with the original repository, but Desktop has quietly changed the destination based on an untrusted API response tied to the current remote string.

### Likelihood Explanation
This requires the GitHub API (or GHES endpoint) to return a `clone_url` for the resolved `owner/name` that points to a different actual repository than the one the user originally added — something that is realistically reachable when a repository/organization ownership changes hands, when short-lived name slugs get reclaimed, or when Desktop is pointed at a self-hosted/enterprise endpoint the attacker influences. No local access, malware, or leaked credentials are needed; the trigger is purely the content of an API response for a repository the app already believes it is tracking, consumed during routine automatic background refreshes that happen without explicit user action.

### Recommendation
- Do not automatically rewrite the local remote based solely on a changed `clone_url` string; at minimum, require the GitHub API repository object's persistent numeric `id`/`node_id` to match the previously stored `GitHubRepository` record before treating it as "the same repository that was merely renamed."
- Surface a confirmation dialog (similar to `ConfirmForcePush`/`UntrustedCertificate`) before silently changing `origin`'s URL, showing the old and new URL to the user.
- Consider decoupling remote-URL auto-updates from routine background/indicator refresh paths so this doesn't happen without explicit user awareness.

### Proof of Concept
1. User adds/clones a repository and Desktop associates it with GitHub repo `owner/name` (stores `gitHubRepository.cloneURL` matching the actual `origin` remote).
2. The GitHub API subsequently begins returning a different `clone_url` for a `repos/{owner}/{name}` lookup that still uses the *same owner/name string* Desktop derives from the current remote (e.g. through repository transfer/reclaim, or an attacker-influenced GHES endpoint) — see the query path in [6](#0-5) .
3. On the next automatic refresh (e.g. triggered from `fetchForRepositoryIndicator` or any push/pull flow calling `repositoryWithRefreshedGitHubRepository`), `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true`, `urlsMatch === false`, and calls `gitStore.setRemoteURL('origin', <new-url>)` with no user interaction, as demonstrated by the existing unit test that shows the remote is updated whenever `clone_url` changes: [7](#0-6) .
4. The user's next push/fetch in Desktop silently targets the new remote URL.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
