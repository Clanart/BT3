### Title
Payout attribution forgery via unsigned OP_RETURN lets an unprivileged withdrawer credit a real operator for a payout it never funded - (`core/src/verifier.rs`)

### Summary
`update_finalized_payouts` in `core/src/verifier.rs` derives `payout_payer_operator_xonly_pk` purely from the first OP_RETURN output found in whatever transaction spends the registered withdrawal outpoint, without checking that this content was signed or authorized by the named operator. Because the payout input is spent via `SIGHASH_SINGLE|ANYONECANPAY` (which never covers the OP_RETURN output), the withdrawer — who holds the private key to their own withdrawal UTXO — can construct and broadcast this transaction themselves, appending an OP_RETURN naming any real operator's public x-only key, causing that operator to be falsely credited as payer.

### Finding Description
The broken binding is: `payout_payer_operator_xonly_pk (DB) == party whose BTC funded the payout output`.

Trace:
1. The withdrawer registers a withdrawal UTXO on Citrea that they themselves control the private key of (a self-owned taproot "dust" UTXO), as illustrated by `generate_withdrawal_utxo`/`sign_withdrawal_output` in `core/src/test/common/setup_utils.rs`.
2. `parse_withdrawal_sig_params` enforces the input signature's sighash type must be `SinglePlusAnyoneCanPay` [2](#0-1) . This sighash type commits only to the input and the single output at the same index (the "payout output"); it explicitly excludes the anchor output and, critically, the OP_RETURN output (added at index 2 in `create_payout_txhandler` [3](#0-2) ) from the commitment, and `AnyoneCanPay` allows the signed input to be combined with any other inputs/outputs in any transaction.
3. Since the withdrawer holds the UTXO's private key, they can produce this exact signature themselves and construct/broadcast the "payout" transaction directly — no operator's participation, signature, or consent is required to add an OP_RETURN naming a real operator X's xonly pubkey (public data).
4. `get_payout_txs_for_withdrawal_utxos` in `core/src/database/verifier.rs` joins purely on the withdrawal UTXO's outpoint bytes being spent in a finalized block [4](#0-3) , with no check on who broadcast the spending tx or whose key signed it.
5. `update_finalized_payouts` then extracts the first OP_RETURN's bytes from that spending transaction and parses it as an xonly pubkey, storing it as `payout_payer_operator_xonly_pk`, with no signature or consent check on that field [5](#0-4) .
6. Real operator X's own automated `PayoutCheckerTask` watches for unhandled payouts matching its own key via `get_first_unhandled_payout_by_operator_xonly_pk` [6](#0-5)  and automatically calls `handle_finalized_payout`, which allocates a pre-signed kickoff connector and proceeds through the kickoff/challenge/reimburse flow [7](#0-6) .
7. `is_kickoff_malicious` in `core/src/verifier.rs` only checks that the operator broadcasting the kickoff matches the OP_RETURN-recorded pubkey and that the blockhash commitment matches [8](#0-7)  — it never checks that X actually funded the payout output's value, so this guard does not stop the forgery; it only prevents a *different* operator from stealing X's forged credit.

Since operator X's reimbursement via the `Reimburse` transaction ultimately draws real bridge value tied to that deposit's `MoveToVault` UTXO (see kickoff/reimburse chain in `core/src/builder/transaction/creator.rs` and `operator_reimburse.rs`), X ends up reimbursed for a payout it never funded — while the withdrawer effectively pays themselves via their own self-owned UTXO.

### Impact Explanation
An unprivileged attacker (the withdrawer) can force any specific, real operator to be credited as `payout_payer_operator_xonly_pk` for a payout the operator never broadcast, signed for, or funded, by simply naming that operator's public xonly key in an OP_RETURN output that lies outside the withdrawer's own signature commitment. The named operator's own automation then proceeds to claim reimbursement it did not earn, i.e., "an operator reimbursed for a payout it never funded" — a listed Critical impact. This is repeatable per withdrawal and independent of which operator is targeted, since operator xonly pubkeys are public and every operator's automated `PayoutCheckerTask` reacts purely to the DB-recorded `payout_payer_operator_xonly_pk` field.

### Likelihood Explanation
No privileged access, key compromise, or operator collusion is required — the attacker only needs to be a normal withdrawer: register a withdrawal on Citrea using a self-owned UTXO, produce a `SinglePlusAnyoneCanPay` signature over the fixed input/output pair themselves, and construct/broadcast a transaction with a crafted OP_RETURN naming a real operator. Cost is limited to Bitcoin transaction fees. This is deployable against any live/regtest bridge instance running the automation feature, and is repeatable against every operator and every withdrawal.

### Recommendation
Do not treat the payout tx's OP_RETURN as the source of truth for attribution unless it is cryptographically bound to the named operator. Require the OP_RETURN (or an equivalent operator commitment) to be covered by a signature from the named operator's key (e.g., require the operator to co-sign or use a sighash type that commits to all outputs, or have the operator separately attest to fronting the specific withdrawal index/output before `update_finalized_payouts` records it as `payout_payer_operator_xonly_pk`).

### Proof of Concept
`cargo test` plan in `core/src/test/deposit_and_withdraw_e2e.rs` style:
1. Run a deposit so a `MoveToVault` tx and `deposit_data` exist for a real operator X.
2. As the withdrawer, generate a self-owned dust UTXO (`generate_withdrawal_utxo`), register it as the withdrawal UTXO via Citrea mock (`insert_withdrawal_utxo`).
3. Withdrawer, without calling any operator RPC, builds the payout transaction directly via `create_payout_txhandler` using their own `SinglePlusAnyoneCanPay` signature (`sign_withdrawal_output`) and operator X's real `xonly_public_key` in the OP_RETURN, then broadcasts it via `rpc`.
4. Mine to finality; wait for the verifier's `update_finalized_payouts` to run.
5. Assert `db.get_payout_info_from_move_txid(...)` returns `Some(Some(X.xonly_public_key), ...)` even though operator X's `withdraw`/`internal_withdraw` RPC was never called.
6. Assert operator X's `PayoutCheckerTask` (or `internal_finalized_payout`) proceeds to produce a `kickoff_txid` and eventually a `Reimburse` tx for this withdrawal, demonstrating X is credited/reimbursed for a payout it never funded — binding `payout_payer_operator_xonly_pk == X` while `party who funded output != X` (it was the withdrawer's own self-owned UTXO).
