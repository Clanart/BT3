Audit Report

## Title
Undersized fixed-capacity `OutstandingRequests` LRU (16384 entries) in repair nonce-tracking causes legitimate repair responses to be discarded under high repair load - (File: core/src/repair/outstanding_requests.rs)

## Summary
`OutstandingRequests::default()` hard-codes an LRU capacity of `16 * 1024` entries for tracking repair request nonces, independent of the actual repair request issuance rate (`MAX_REPAIR_LENGTH = 512` per repair pass in `repair_service.rs`) [1](#0-0) [2](#0-1) . When the number of concurrently outstanding, non-expired nonces exceeds this fixed capacity within the 60s `DEFAULT_REQUEST_EXPIRATION_MS` window, the underlying `LruCache::put` silently evicts the least-recently-used entry regardless of whether its own 60s timer has expired [3](#0-2) . A genuine repair response arriving for an evicted-but-still-valid nonce is then indistinguishable from a forged/unmatched-nonce packet and is dropped both in `shred_fetch_stage.rs::verify_repair_nonce` and `turbine/src/sigverify_shreds.rs::extract_shred_and_location`.

## Finding Description
`register_response` looks up the nonce in the LRU; if it is not present (because it was evicted by capacity-based LRU eviction rather than actual timer expiration), it returns `None` with no way to distinguish "never existed / expired" from "valid but evicted" [4](#0-3) . Consumers treat a `None` result as an invalid/unmatched response:

- `shred_fetch_stage.rs::verify_repair_nonce` discards the packet entirely if `register_response` returns `None` (the nonce is not found or already invalidated).
- `turbine/src/sigverify_shreds.rs::extract_shred_and_location` explicitly documents this as "the request entry was evicted before consumption," increments `num_unknown_block_location`, and drops the shred instead of inserting it into blockstore.

The eviction is purely capacity-driven LRU (`LruCache::put`), not tied to the `expire_timestamp` field stored per-entry, so a still-pending, non-expired nonce can be evicted purely because too many *newer* requests were added, breaking the intended invariant that a response should remain acceptable until its own 60-second expiration.

The repair-issuance side confirms the volume mismatch is architecturally possible: `MAX_REPAIR_LENGTH = 512` repairs can be generated per pass in `repair_service.rs`, and the module also defines `REPAIR_REQUEST_TIMEOUT_MS = 150` — the time the service waits before re-requesting an unfulfilled repair for a given shred — meaning the service can be requesting many distinct shreds concurrently during ledger catch-up (e.g., after a large gap, restart, or partition) well beyond the fixed 16384-entry cache within a 60s window. This is a straightforward capacity-vs-throughput mismatch: nothing ties the LRU size to `MAX_REPAIR_LENGTH`/expiration window, so under sufficiently heavy legitimate repair backlog (not requiring any malicious/trusted peer assumption — packet loss, network congestion, or a large ledger gap are enough), the cache evicts still-valid entries and correct responses are dropped.

## Impact Explanation
This matches the "non-RPC remote exhaustion/degradation" impact category: an unprivileged network condition (sustained shred loss/backlog, not requiring a malicious validator or trusted process) causes the victim's own repair-response cache to evict still-valid outstanding request nonces, causing correctly-signed, on-time repair responses to be dropped rather than inserted into blockstore. This degrades — but does not by itself halt — the node's ability to catch up via repair, since it wastes round trips and repeatedly re-requests shreds whose responses were dropped due to cache eviction rather than actual invalidity.

## Likelihood Explanation
Reaching >16384 concurrently outstanding, non-expired nonces requires a sustained, large repair backlog (e.g., large ledger gaps, poor network conditions, or high shred loss) persisting well within the 60-second expiration window. This is architecturally possible given `MAX_REPAIR_LENGTH = 512` per pass and no coupling between issuance rate/cache size, but requires prior degraded state (falling behind) rather than being triggerable purely by a single unprivileged packet from an attacker; it is a resource-bound design mismatch rather than a directly attacker-controlled trigger of a single request.

## Recommendation
Size the `OutstandingRequests` LRU capacity relative to the maximum sustainable in-flight repair volume and the `DEFAULT_REQUEST_EXPIRATION_MS` window (e.g., based on `MAX_REPAIR_LENGTH` and typical repair-pass cadence, with headroom), or change the cache to evict only expired entries (checking `expire_timestamp`) rather than relying purely on capacity-based LRU eviction, so that a still-pending, non-expired nonce is never evicted ahead of a genuinely expired one.

## Proof of Concept
1. Construct a test harness around `OutstandingRequests` that calls `add_request` more than 16384 times within a simulated window smaller than `DEFAULT_REQUEST_EXPIRATION_MS`.
2. Call `register_response` for one of the earliest-inserted (now-evicted) nonces with a valid response and a `now` still less than its original `expire_timestamp`.
3. Observe that `register_response` returns `None` even though the nonce's timer had not actually expired, confirming that capacity-based LRU eviction — not the intended 60s expiration — caused the valid response to be rejected as if unmatched/invalid.
4. Cross-reference with `turbine/src/sigverify_shreds.rs::extract_shred_and_location`'s `num_unknown_block_location` counter and `shred_fetch_stage.rs::verify_repair_nonce`'s discard path to confirm the same effect occurs in the shred-processing pipeline.

```rust
pub const DEFAULT_REQUEST_EXPIRATION_MS: u64 = 60_000;

pub struct OutstandingRequests<T, U = ()> {
    requests: LruCache<Nonce, RequestStatus<T, U>>,
}

impl<T, S: ?Sized, U> OutstandingRequests<T, U>
where
    T: RequestResponse<Response = S>,
{
    /// Add a request to the cache, returns the nonce to be sent with the repair request
    /// and expected on the response.
    pub fn add_request(&mut self, request: T, now: u64) -> Nonce {
        self.add_request_with_metadata(request, now, None)
    }

    /// Similar to `add_request` but additionally specifies an associated metadata
    /// for the nonce that can be fetched with `fetch_metadata_for_nonce`.
    pub fn add_request_with_metadata(
        &mut self,
        request: T,
        now: u64,
        metadata: Option<U>,
    ) -> Nonce {
        let num_expected_responses = request.num_expected_responses();
        let nonce = rng().random_range(0..Nonce::MAX);
        self.requests.put(
            nonce,
            RequestStatus {
                expire_timestamp: now + DEFAULT_REQUEST_EXPIRATION_MS,
                num_expected_responses,
                request,
                metadata,
            },
        );
        nonce
    }
```

```rust
    pub fn register_response<R>(
        &mut self,
        nonce: u32,
        response: &S,
        now: u64,
        success_fn: impl Fn(&T) -> R,
    ) -> Option<R> {
        let mut should_delete = false;
        let response = self.requests.get_mut(&nonce).and_then(|status| {
            if status.num_expected_responses == 0 {
                // No more expected responses
                return None;
            }

            if now >= status.expire_timestamp || !status.request.verify_response(response) {
                // Invalid/expired response should invalidate this nonce.
                should_delete = true;
                return None;
            }

            status.num_expected_responses -= 1;
            if status.num_expected_responses == 0 && status.metadata.is_none() {
                // No metadata, and no more expected responses safe to delete eagerly.
                should_delete = true;
            }
            Some(success_fn(&status.request))
        });

        if should_delete {
            self.requests
                .pop(&nonce)
                .expect("request must exist when marked for deletion");
        }
        response
    }
```
