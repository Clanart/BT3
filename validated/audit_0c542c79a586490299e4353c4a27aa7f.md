## Analysis

The MakerDAO report's core broken invariant: a legitimate, permanent "cage" (halt) mechanism blocks the *exit/refund* path for funds that are already committed, with no separate carve-out for withdrawals and no recovery route.

Hyperbridge's ISMP core has a direct structural analog in the consensus-client freeze mechanism.

### Title
Freezing a consensus client permanently blocks timeout-refund delivery for already-dispatched requests, trapping escrowed funds - (File: `modules/ismp/core/src/handlers.rs`, `modules/ismp/core/src/handlers/consensus.rs`)

### Summary
`freeze_client` is a permissionless, one-way safety action: any party ("fisherman") who submits a valid fraud proof of a consensus fault can freeze a consensus client. Per the protocol docs, "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead." [1](#0-0) 

The same `is_consensus_client_frozen` gate is enforced in `validate_state_machine`, which is the shared precondition used before processing **requests, responses, and timeouts**: [2](#0-1)  This is confirmed by the protocol docs, which list "Assert that the state machine's consensus client is not frozen" as the *first* check performed by the timeout handler, identical to the request/response handlers: [3](#0-2) 

### Finding Description
When an application (e.g. `IntentGatewayV2`/`ExtrinsicIntents`, `WrappedHyperFungibleToken`) escrows a user's funds and dispatches a cross-chain `PostRequest` to a destination whose consensus client is later frozen (because a genuine fault was found on that destination chain), two things become true simultaneously:

1. The request can never be **delivered**, because delivering it requires `validate_state_machine` to pass `is_consensus_client_frozen`, which now permanently errors with `FrozenConsensusClient`. [4](#0-3) 
2. The same request can never be **timed out** either, because `handle_timeouts` uses the exact same `validate_state_machine` precondition against the same frozen consensus client (the destination's state, needed to prove non-membership for the timeout), so the timeout call also reverts with `FrozenConsensusClient` forever. [5](#0-4) 

Unlike a normal DoS, this is unrecoverable: the docs state explicitly that a frozen client cannot be unfrozen, and creating a brand-new client via `create_client` does not restore the ability to timeout/settle messages that were already dispatched under the old, now-permanently-frozen `consensus_state_id`. This exactly reproduces the MakerDAO analog: a legitimate, one-way halt action (`cage`/`freeze_client`) that blocks the specific exit function (`daiJoin.exit`/timeout-refund) needed to return funds already owed to users, with no guard rail carving out the refund/exit path from the halt.

### Impact Explanation
Any application escrowing user funds against a cross-chain request (intent-gateway order inputs, `WrappedHyperFungibleToken` locked collateral, relayer fee withdrawal requests) that targets a state machine whose consensus client is subsequently frozen will have those funds **permanently locked** — neither the success path (delivery) nor the failure/recovery path (timeout refund) can execute. This matches the bounty's "stealing or loss of funds" impact category, since users lose access to funds without any fault of their own.

### Likelihood Explanation
`freeze_client` is a permissionless, publicly-callable safety mechanism intended to be triggered whenever a real byzantine fault (double-signing/eclipse) is detected on a connected chain — it does not require a malicious Hyperbridge admin, relayer, or prover, only an honest fisherman reacting to a genuine external fault. Given Hyperbridge connects to many external consensus systems over time, a consensus fault on any one of them is a plausible, expected event this mechanism is explicitly designed to handle — yet its side effect on pending timeouts appears unaccounted for.

### Recommendation
Separate the "no new consensus/request/response processing" invariant from the "no timeout processing" invariant. Timeout handling should not require the frozen client's liveness — instead, timeouts for requests targeting a frozen consensus client should be unconditionally honorable (e.g., permit timeout dispatch once a client is marked frozen, similar to how a `challenge_period` of `0` bypasses the delay check), or provide a dedicated recovery path that lets applications reclaim escrowed funds tied to commitments referencing a frozen `consensus_state_id`.

### Proof of Concept
1. App on chain B escrows user funds and dispatches `PostRequest` to chain A with `timeout_timestamp = T`.
2. A genuine consensus fault occurs on chain A; a fisherman submits `freeze_client` with a valid `FraudProofMessage` for A's `consensus_state_id` as tracked on B — this succeeds permissionlessly per `docs/content/protocol/ismp/consensus.mdx` lines 188-197.
3. Time passes `T`; a relayer tries to call the timeout handler on B for the escrowed request. `validate_state_machine` on B calls `is_consensus_client_frozen` for A's consensus id, which now always returns `Err(FrozenConsensusClient)` as shown in the `frozen_consensus_client_check` test at `modules/ismp/testsuite/src/lib.rs` lines 176-208.
4. The timeout call reverts forever; the app's `on_timeout` refund logic never executes; escrowed user funds remain locked with no available exit, mirroring the `daiJoin.cage()` scenario exactly.

The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs. This may arise from double signing or eclipse attacks. The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state. In this state it can no longer process new consensus messages as well as new requests & responses. Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead.

```rust
/// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;
```

```text
The timeout `handle` is used to notify onchain `IsmpModule`s of outgoing requests that have now timed out. A relayer will construct the `TimeoutMessage` which holds a batch of these messages, and their relevant proofs. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the messages have indeed timed out
- Assert that the claimed messages are known by the host
- Assert that the relevant state machine's time has advanced past the `timeout_timestamp` of specified messages.
- Assert that the relevant non-membership proofs for the messages are valid
- Finally dispatch the timeouts to the relevant `IsmpModule::on_timeout` and delete the commitments for the outgoing messages.
```

```rust
pub fn frozen_consensus_client_check<H: IsmpHost>(host: &H) -> Result<(), &'static str> {
	let intermediate_state = setup_mock_client(host);
	// Set the previous update time
	let challenge_period = host.challenge_period(intermediate_state.height.id).unwrap();
	let previous_update_time = host.timestamp() - (challenge_period * 2);
	host.store_consensus_update_time(mock_consensus_state_id(), previous_update_time)
		.unwrap();
	host.store_state_machine_update_time(intermediate_state.height, previous_update_time)
		.unwrap();
	host.freeze_consensus_client(mock_consensus_state_id()).unwrap();

	let post = PostRequest {
		source: intermediate_state.height.id.state_id,
		dest: host.host_state_machine(),
		nonce: 0,
		from: vec![0u8; 32],
		to: vec![0u8; 32],
		timeout_timestamp: 0,
		body: vec![0u8; 64],
	};
	let (signature, ..) = create_relayer_signer(vec![post.clone()].encode(), &[1u8; 32]);

	// Request message handling check
	let request_message = Message::Request(RequestMessage {
		requests: vec![post.clone()],
		proof: Proof { height: intermediate_state.height, proof: vec![] },
		signer: signature,
	});

	let res = handle_incoming_message(host, request_message).map_err(|e| e.downcast().unwrap());
	dbg!(&res);
	assert!(matches!(res, Err(ismp::error::Error::FrozenConsensusClient { .. })));
	Ok(())
```
