### Title
Wallet `sign_message_by_address` / `sign_message_by_id` RPC allows blind BLS signing of attacker-controlled raw bytes with the real spend key, enabling forged `AGG_SIG_UNSAFE`/`AGG_SIG_ME` authorizations - (File: chia/wallet/util/signing.py, chia/wallet/wallet_rpc_api.py)

### Summary
The Galleon `Auth.tsx` bug lets a malicious dApp get the wallet to blindly sign an attacker-supplied message and hand the signature back to the attacker, who reuses it to move the victim's funds. Chia's wallet exposes an analogous capability through the `sign_message_by_address`/`sign_message_by_id` RPC endpoints: when a caller sets `safe_mode=False`, the wallet signs the caller-supplied bytes **directly** with `AugSchemeMPL.sign`, without any CHIP-0002 domain-separation prefix, using the same synthetic secret key that authorizes real coin spends.

### Finding Description
`sign_message` in `chia/wallet/util/signing.py` branches on the signing mode: [1](#0-0) 

When `mode` is `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT` or `BLS_MESSAGE_AUGMENTATION_HEX_INPUT` (selected by the RPC caller via `is_hex`/`safe_mode=False`), `hex_message` is set to the raw caller-supplied bytes with **no prefix, no length constant, and no domain separation** — unlike the `CHIP_0002` modes, which wrap the message in `("Chia Signed Message", message)` before hashing. The raw bytes are then signed by `AugSchemeMPL.sign(secret_key, hex_message)` using `secret_key`, which is the wallet's real synthetic secret key for a live coin puzzle hash, exactly the key used to satisfy `AGG_SIG_ME`/`AGG_SIG_UNSAFE` conditions during normal coin spends.

The RPC endpoints `sign_message_by_address` and `sign_message_by_id` in `chia/wallet/wallet_rpc_api.py` derive this `synthetic_secret_key` from the wallet's real puzzle-hash key material and pass the caller's `request.message`/`request.signing_mode_enum` straight through to `sign_message`: [2](#0-1) [3](#0-2) 

The request schema exposes `is_hex` and `safe_mode` directly to the RPC caller: [4](#0-3) 

Because `AGG_SIG_UNSAFE` in CLVM/consensus checks a BLS signature over the raw condition-argument bytes with no coin-specific or transaction-specific salt (unlike `AGG_SIG_ME`, which chia mitigates by appending genesis-challenge + coin-id), any signature the wallet produces via `safe_mode=False` over attacker-chosen bytes is a valid `AGG_SIG_UNSAFE` witness for that exact byte string, signed by the coin's real key. A malicious dApp or local RPC integration (e.g., a "message signing" flow analogous to the reported `galleon://` `Auth.tsx` dialog) can present a plausible-looking string to the user for "authentication," have the wallet sign it with `safe_mode=False`, and then reuse that signature as the `AGG_SIG_UNSAFE` witness in an unrelated spend bundle that unlocks a puzzle requiring exactly that public key/message pair (e.g., a puzzle the attacker constructs specifically so its `AGG_SIG_UNSAFE` condition argument equals the phishing message), enabling unauthorized coin movement without ever going through the wallet's normal, reviewed transaction-construction path.

### Impact Explanation
If an attacker can get the wallet's real key to sign an arbitrary attacker-chosen byte string via `safe_mode=False`, they obtain a valid BLS signature that can be embedded as an `AGG_SIG_UNSAFE` witness in a spend bundle for any coin whose puzzle demands that exact public key and message — the signature is not scoped to any specific coin or spend, so it can be replayed in a completely different, attacker-crafted transaction. This is unsigned/unauthorized coin movement achieved by tricking the signing UX rather than by compromising the transaction-review flow, matching the report's "attacker-controlled message signed and exfiltrated" bug class.

### Likelihood Explanation
This requires convincing a wallet user (or an integration that calls the RPC on the user's behalf, e.g., a browser/dApp bridge) to approve signing a specific string with `safe_mode=False`/raw BLS augmentation mode, and requires the attacker to have pre-built a puzzle whose `AGG_SIG_UNSAFE` condition argument matches that string and public key. This is more constrained than the original browser-URI report (there is no default OS-level `galleon://` handler here), and it depends on how any given wallet UI/dApp-bridge product built on top of this RPC decides to solicit "sign this message" approval from the user — the RPC itself does not enforce any warning or restriction differentiating `safe_mode=True` (CHIP-0002 prefixed, safe) from `safe_mode=False` (raw, dangerous) at the point of call.

### Recommendation
- At minimum, require an explicit, loudly-labeled confirmation (distinct from ordinary message signing) whenever `safe_mode=False` is requested, since this mode removes all domain separation.
- Consider deprecating/removing raw `BLS_MESSAGE_AUGMENTATION_*` signing modes from the public wallet RPC, or restrict them to a build-time/opt-in flag, since `CHIP_0002` modes already provide a safe, prefixed alternative for legitimate message-signing use cases.
- Any wallet/dApp-bridge product exposing this RPC to untrusted callers should never let a remote/URI-triggered flow choose `safe_mode=False`.

### Proof of Concept
1. A dApp bridge (or any RPC caller) invokes `sign_message_by_address` with `SignMessageByAddress(address=<victim address>, message=<attacker-chosen hex/utf8 payload>, is_hex=True, safe_mode=False)`.
2. `chia/wallet/wallet_rpc_api.py:sign_message_by_address` derives the real synthetic secret key for that address and calls `sign_message(secret_key, message, mode=BLS_MESSAGE_AUGMENTATION_HEX_INPUT)`.
3. `chia/wallet/util/signing.py:sign_message` signs the raw bytes with no prefix: `AugSchemeMPL.sign(secret_key, bytes.fromhex(message))`.
4. The attacker takes the returned `(pubkey, signature)` and embeds `signature` as the `AGG_SIG_UNSAFE` witness in a spend bundle for a coin whose puzzle contains `(AGG_SIG_UNSAFE pubkey message)` with the same `message` bytes, allowing that spend to pass condition validation without further authorization from the victim.

Note: I was not able to fully trace, within the available index, the exact mempool/consensus code path that validates `AGG_SIG_UNSAFE` witnesses end-to-end (only reference locations were found in `chia/consensus/condition_tools.py` and test files) to confirm there is no additional mitigating check beyond public-key/message equality; a full Devin session would be needed to inspect `chia/consensus/condition_tools.py` and the CLVM condition-parsing code in detail to fully confirm there are no additional constraints on `AGG_SIG_UNSAFE` reuse.

def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )

    async def sign_message_by_address(self, request: SignMessageByAddress) -> SignMessageByAddressResponse:
        """
        Given a derived P2 address, sign the message by its private key.
        :param request:
        :return:
        """
        synthetic_secret_key = self.service.wallet_state_manager.main_wallet.convert_secret_key_to_synthetic(
            await self.service.wallet_state_manager.get_private_key(decode_puzzle_hash(request.address))
        )
        signing_response = sign_message(
            secret_key=synthetic_secret_key,
            message=request.message,
            mode=request.signing_mode_enum,
        )
        return SignMessageByAddressResponse(
            pubkey=signing_response.pubkey,
            signature=signing_response.signature,
            signing_mode=request.signing_mode_enum.value,
        )

    async def sign_message_by_id(self, request: SignMessageByID) -> SignMessageByIDResponse:
        """
        Given a NFT/DID ID, sign the message by the P2 private key.
        :param request:
        :return:
        """
        entity_id: bytes32 = decode_puzzle_hash(request.id)
        if is_valid_address(request.id, {AddressType.DID}, self.service.config):
            did_wallet: DIDWallet | None = None
            for wallet in self.service.wallet_state_manager.wallets.values():
                if wallet.type() == WalletType.DECENTRALIZED_ID.value:
                    assert isinstance(wallet, DIDWallet)
                    assert wallet.did_info.origin_coin is not None
                    if wallet.did_info.origin_coin.name() == entity_id:
                        did_wallet = wallet
                        break
            if did_wallet is None:
                raise ValueError(f"DID for {entity_id.hex()} doesn't exist.")
            synthetic_secret_key = self.service.wallet_state_manager.main_wallet.convert_secret_key_to_synthetic(
                await self.service.wallet_state_manager.get_private_key(await did_wallet.current_p2_puzzle_hash())
            )
            latest_coin_id = (await did_wallet.get_coin()).name()
            signing_response = sign_message(
                secret_key=synthetic_secret_key,
                message=request.message,
                mode=request.signing_mode_enum,
            )
            return SignMessageByIDResponse(
                pubkey=signing_response.pubkey,
                signature=signing_response.signature,
                signing_mode=request.signing_mode_enum.value,
                latest_coin_id=latest_coin_id,
            )
