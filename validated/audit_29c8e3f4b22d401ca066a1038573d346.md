### Title
Use of `payable.transfer` in the canonical WSEI wrapped-token contract can permanently freeze user funds on withdrawal - (File: `contracts/src/WSEI.sol`)

### Summary
The `WSEI` contract, which is the canonical Wrapped SEI ERC-20 shipped and embedded as chain artifacts for the Sei EVM, implements `withdraw()` using the hard-coded-gas `payable.transfer()` primitive instead of a low-level `call`. Any smart-contract holder of WSEI whose `receive()`/`fallback()` logic costs more than the fixed 2300-gas stipend will have every `withdraw()` call permanently revert, freezing that user's WSEI balance with no way to redeem it for native SEI.

### Finding Description
`WSEI.withdraw()` debits the caller's WSEI balance and then attempts to send native SEI back via `payable(msg.sender).transfer(wad)`: [1](#0-0) 

`transfer()` forwards only a fixed 2300-gas stipend to the recipient. If `msg.sender` is a contract (e.g., a DEX router, vault, multisig, or any smart-contract wallet) whose `receive()`/`fallback()` performs any state-changing logic (event emission bookkeeping, SLOAD/SSTORE, delegatecall forwarding, etc. — all of which routinely exceed 2300 gas, especially post EIP-1884 SLOAD repricing), the internal transfer will run out of gas and revert the entire `withdraw()` transaction.

This `WSEI` bytecode is not a throwaway example: it is embedded directly into the chain binary and exposed through `x/evm/artifacts/wsei/artifacts.go` (`go:embed WSEI.abi` / `WSEI.bin`), and is deployed/used by the EVM module's tx CLI: [2](#0-1) 

Because `WSEI` is the chain's official wrapped-native-token contract (analogous to WETH on Ethereum), it is expected to be integrated into DEXes, routers, and other contracts across the Sei EVM ecosystem — all of which are reachable by any unprivileged EVM transaction sender.

### Impact Explanation
Once a contract account accumulates WSEI balance and its fallback/receive function exceeds the 2300-gas budget, `withdraw()` will always revert for that account, permanently freezing the underlying native SEI backing that balance inside the `WSEI` contract. Since `WSEI` is a system-provided, widely-integrated token wrapper, this can affect any protocol contract (routers, vaults, aggregators) that holds WSEI and attempts to unwrap it, resulting in permanent, unrecoverable loss of access to funds — a legitimate High-severity freezing-of-funds condition.

### Likelihood Explanation
Likelihood is high: this requires no privileged access, no cross-chain component, and no validator collusion — any user can simply deploy or use a contract with a non-trivial `receive()` function and interact with `WSEI`, or an existing integrated protocol contract can unknowingly trigger the condition. This is a well-known, deterministic Solidity gas-stipend pitfall.

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `WSEI.withdraw()` with a low-level call and explicit success check (checks-effects-interactions is already respected since balance is decremented first):
```solidity
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "WSEI: ETH transfer failed");
```
This removes the fixed 2300-gas limitation while preserving reentrancy safety via the existing balance-decrement-before-transfer ordering.

### Proof of Concept
1. Deploy a contract `Victim` with a `receive()` function that writes to storage (e.g., `receive() external payable { lastAmount = msg.value; }`), which costs well over 2300 gas (cold SSTORE ≈ 20000 gas).
2. `Victim` deposits native SEI into `WSEI` via `deposit()`, receiving WSEI tokens.
3. `Victim` calls `WSEI.withdraw(wad)`.
4. The internal `payable(msg.sender).transfer(wad)` call forwards only 2300 gas to `Victim.receive()`, which requires more gas to execute the SSTORE, causing an out-of-gas revert that bubbles up and reverts the entire `withdraw()` transaction.
5. `Victim`'s WSEI balance remains debited-then-reverted (transaction fully reverts), but since the only pathway to redeem WSEI for native SEI is `withdraw()`, and it always reverts for this account, the wrapped balance is permanently unredeemable.
