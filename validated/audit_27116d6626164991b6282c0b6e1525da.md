## Finding: Argument-injection via unsanitized tag names passed to `git push`

### Summary
`getStringArray` only checks that the parsed JSON value is an `Array` whose elements are `string` — it enforces **no length limit** and **no content/format validation** (e.g. it never rejects tag strings that begin with `-`). The resulting array, retrieved via `getTagsToPush`, is spread directly into the `git push` argv in `push.ts` with no `--` end-of-options marker, so a string beginning with a dash is interpreted by `git` as a command-line flag rather than a ref/tag name. [1](#0-0) 

### Finding Description
`getStringArray` validates only that:
1. the parsed value is an `Array`, and
2. every element has `typeof === 'string'`

No check exists for array length or for the shape of each string (e.g., rejecting leading `-`/`--`, which git's `check-ref-format` does **not** forbid for tag/branch names). [2](#0-1) 

`getTagsToPush` is a thin wrapper that reads the `tags-to-push-${repository.id}` key via `getStringArray` with no additional sanitization. [3](#0-2) 

The consumer, `push()` in `push.ts`, builds the `git push` argv and appends every element of `tagsToPush` verbatim, immediately after the refspec and before the `--set-upstream` / `--force-with-lease` / `--no-verify` flags — there is no `--` separator to force git to treat remaining items as positional refnames: [4](#0-3) 

If any tag string begins with `-`, `git` will parse it as an option to `push` instead of a tag refspec. This is a known argument-injection class in git tooling (e.g. `--upload-pack=<cmd>` / `--receive-pack=<cmd>` for altering the invoked helper program, `-o<server-option>`, or forcing `--force`).

### Reachability caveat
I was able to confirm the full sink (`push.ts`) and the insufficient validation in `getStringArray`/`getTagsToPush`, but I was not able to fully trace, within the available tool budget, the exact code in `git-store.ts` that *populates* the `tags-to-push-${id}` entry (i.e., whether the tag names it stores are taken as-is from the local repository's tag list, which could include tag names created via a malicious cloned/fetched repository, or whether they are filtered beforehand). Git's own ref-naming rules (`git check-ref-format`) do not forbid tags from starting with `-`, so if GitHub Desktop enumerates local tags (including ones the user obtained by fetching from an attacker-controlled remote) and stores them unmodified via `storeTagsToPush`, this path would be reachable by "repository content" per the review scope. This last link should be verified directly against `git-store.ts` before treating this as a confirmed, end-to-end exploitable chain.

### Impact Explanation
If reachable, a maliciously-named tag (e.g. `-o<server-option>` or `--force`) fetched from an attacker-controlled remote could be interpreted by `git push` as a command-line flag instead of a ref, resulting in unintended push behavior (silent force-push, server-side option injection) — a "silent corruption of what the user commits or pushes" per the valid-impact criteria. The unbounded array length itself is not exploitable beyond a large but harmless argv (no direct DoS/impact), so the length concern in the question is a minor point compared to the missing content validation.

### Likelihood Explanation
Medium-to-low, contingent on the unverified population path: it requires the user to (1) fetch/clone a repository containing an attacker-crafted tag name beginning with `-`, and (2) have GitHub Desktop compute that tag as one "to push" and persist it unmodified via `storeTagsToPush`, and (3) subsequently perform a push. No `--` separator exists to neutralize the risk regardless of source.

### Recommendation
- In `getStringArray`, add validation appropriate to its use as git refspecs: reject empty strings, strings starting with `-`, and enforce a sane maximum array length.
- In `push.ts`, insert a literal `'--'` argument before appending `tagsToPush` (and before any other list of refnames derived from external/repository data) so git never interprets subsequent items as options.
- Audit `git-store.ts` for where `tagsToPush`/`storeTagsToPush` is populated to confirm whether tag names originate from repository content without sanitization.

### Proof of Concept
1. Clone/fetch a repository containing a tag literally named `--upload-pack=/tmp/evil.sh` (or `-oserver-option-value`, or `--force`) — permitted by git's ref-naming rules.
2. Trigger a flow in GitHub Desktop that computes "tags to push" including this tag, causing `storeTagsToPush` to persist `localStorage["tags-to-push-<id>"] = '["--force"]'` (or similar) unmodified.
3. Perform a push; `push.ts` builds `args = ['push', 'origin', 'branch:branch', '--force', ...]` — git now treats the tag string as a flag, not a ref, corrupting the intended push semantics. [5](#0-4)

```typescript
export function getStringArray(key: string): ReadonlyArray<string> {
  const rawData = localStorage.getItem(key) || '[]'

  try {
    const outputArray = JSON.parse(rawData)

    if (!(outputArray instanceof Array)) {
      return []
    }

    if (outputArray.some(element => typeof element !== 'string')) {
      return []
    }

    return outputArray
  } catch (e) {
    return []
  }
}
```
