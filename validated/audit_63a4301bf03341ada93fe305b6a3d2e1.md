This maps cleanly onto a reachable bug in Serai's Bitcoin scanner: outputs accumulated across transactions in one block all get overwritten with the **last** matching transaction's `presumed_origin` and `data` — so a depositor's funds can be credited under an attacker's instruction, analogous to ZKasino converting user deposits into something else without consent.

### Title
Cross-transaction `presumed_origin`/`data` overwrite in `Bitcoin::get_outputs` misattributes earlier deposits to a later transaction's instruction - (File: processor/src/networks/bitcoin.rs)

### Summary
`get_outputs` in the Bitcoin network driver accumulates scanned outputs in a vector declared **outside** the per-transaction loop, then rewrites `presumed_origin` (all outputs) and `data` (External-kind outputs) for *every* accumulated output using only the most recent transaction's values. An unprivileged user sending a Bitcoin transaction can therefore overwrite the Serai instruction (`InInstruction` data) attached to another user's deposit found earlier in the same block, causing that deposit to be processed under the attacker's instruction instead of the depositor's.

### Finding Description
In `Bitcoin::get_outputs`, the result vector is created once per block:

```rust
// processor/src/networks/bitcoin.rs
let mut outputs = vec![];                       // declared before the tx loop
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    ...
    outputs.push(output);
  }
  if outputs.is_empty() { continue; }

  let presumed_origin = { ... tx.input[0] ... };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {                  // iterates ALL txs' outputs, not just this tx
    if output.kind == OutputType::External {
      output.data.clone_from(&data);            // overwrites earlier txs' InInstruction
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

Because `outputs` is not scoped to `tx`, when block `B` contains transactions `T1` (victim deposit with instruction `D1`) and `T2` (attacker deposit with instruction `D2`, mined later in the same block), the second loop iteration sets the victim's `External` output `data` to `D2` and its `presumed_origin` to `T2`'s first input address. The output is then emitted by the scanner as a legitimately received deposit but carrying the attacker's `InInstruction`.

This is reachable entirely with public inputs: any user can craft and broadcast a Bitcoin transaction paying the Serai external address with a chosen `InInstruction` (embedded via `extract_serai_data`), and ordering of transactions within a block is not something the victim controls.

### Impact Explanation
The `data` field on an `External` output is the `InInstruction` that tells Serai what to do with the deposit (e.g., which Serai address/operation to credit). Overwriting it with the attacker's instruction causes the victim's deposited BTC to be credited/routed according to the attacker's instruction — effectively converting another user's funds to the attacker's benefit, the same trust violation class as the ZKasino deposit conversion. `presumed_origin` misattribution additionally corrupts refund/origin tracking. No threshold collusion, malicious node, or leaked key is needed — just two transactions in one block.

### Likelihood Explanation
Likelihood is moderate-to-high: Bitcoin blocks routinely contain multiple transactions, and an attacker can watch the mempool/blocks for Serai deposits and submit their own deposit with a chosen `InInstruction` targeting the same block. Since `register_offset` offsets and the external address are deterministic/public, crafting a matching deposit is trivial. The attacker only needs their transaction to appear in the same block *after* the victim's (or any later position, since the overwrite applies to all accumulated outputs). Attackers who can get a tx into the same block (e.g., via miner cooperation or simply fee-bumping into the next block with the victim tx unconfirmed-but-eventually-co-mined) trigger this reliably.

### Recommendation
Scope the output vector and the origin/data decoration to the current transaction: either declare `outputs` inside the `for tx` loop (extending a per-block results list), or only mutate outputs produced by `scanner.scan_transaction(tx)` for that iteration. E.g., collect `let mut tx_outputs = ...` per transaction, decorate only `tx_outputs`, then `outputs.extend(tx_outputs)`.

### Proof of Concept
1. Victim broadcasts `T1`: pays `external_address(group_key)` with `InInstruction D1` crediting victim's Serai account.
2. Attacker broadcasts `T2`: pays `external_address(group_key)` with `InInstruction D2` crediting the attacker, arranged to be mined in the same block after `T1` (attacker can simply wait for a block template containing `T1` and ensure `T2` follows it, or both land unconfirmed and are ordered by the miner).
3. `get_outputs(block)` scans `T1`, pushes the victim `External` output with `D1`, then scans `T2`, pushes the attacker output, and overwrites **both** outputs' `data` with `D2` and `presumed_origin` with the attacker's input address.
4. The scanner emits both outputs to the processor; the victim's deposit is processed under `D2`, routing/ crediting it to the attacker.
