### Title
Unadjusted hunk-header line offsets in partial-line staging/discard patches applied with `git apply --unidiff-zero` — silent corruption of staged/committed content - ([File: app/src/lib/patch-formatter.ts])

### Summary
`formatPatch()` and `formatPatchToDiscardChanges()` in `app/src/lib/patch-formatter.ts` build a synthetic unified diff for GitHub Desktop's line/hunk selection features (partial staging and "discard selected lines"). For every hunk they reuse the **original** `hunk.header.oldStartLine` / `hunk.header.newStartLine` values verbatim instead of recomputing them to reflect the fact that earlier hunks may have been partially or entirely deselected: [1](#0-0)  and equivalently in the discard path [2](#0-1) . These synthetic patches are then applied to the index/working tree with `git apply ... --unidiff-zero ...`, a flag that explicitly disables git's normal context-consistency safety checks: [3](#0-2)  and [4](#0-3) .

### Finding Description
`hunk.header.oldStartLine`/`newStartLine` are computed by `git diff` for the **full, unmodified** hunk set — i.e. they assume every preceding hunk's real additions/deletions are applied. When the user deselects a hunk or lines within a hunk (a routine, fully user-controlled action exposed in the diff UI), `formatPatch()` silently drops those lines from the generated patch buffer but never renumbers the `newStartLine`/`oldStartLine` (and only recomputes local `oldCount`/`newCount`) of subsequent hunks to account for the net line-count delta the dropped hunk would have introduced: [5](#0-4) . The same unadjusted-header pattern exists in `formatPatchToDiscardChanges()`: [6](#0-5) .

The resulting patch is fed directly into `git apply` with `--unidiff-zero`, which is documented to disable the sanity checks git normally performs to guard against hunks being located/applied at the wrong place: [3](#0-2) . This mirrors the audited pattern exactly: a position value (`range[0]`/hunk start line) is mutated conceptually (the real file shifts because a preceding hunk is skipped) but the code that performs the actual write (the hunk header handed to `git apply`) keeps using the stale, unadjusted coordinate, while the safety mechanism that would normally catch the mismatch (context validation) has been deliberately turned off.

### Impact Explanation
If a repository an attacker controls (a cloned/fetched branch, PR, or file provided via a git remote) contains content engineered to create ambiguous or repeated context blocks near the affected hunk boundaries, a legitimate user performing ordinary line-level staging or "discard changes" actions in Desktop can have their patch applied at the wrong location in the index/working tree. Because `--unidiff-zero` removes the extra consistency checking, this can result in silent corruption of exactly the kind called out as valid impact: the wrong lines get staged/committed, or the wrong lines get discarded from the working tree, without any user-visible error — i.e. "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This code path is exercised on every partial-hunk/partial-line commit and every "discard selected lines" action, which are core, everyday features of GitHub Desktop, so the trigger conditions are common. The attacker precondition (crafting file content with duplicated/ambiguous line sequences near hunk boundaries in a repository the victim clones/fetches/checks out) is realistic and requires no special privileges — only that the victim opens a diff from that repository and performs a partial selection. I was not able to fully verify from static reading alone whether `git apply`'s underlying placement algorithm uses the pre-image (`oldStartLine`) exclusively for locating hunks (in which case the miscomputed `newStartLine` might be purely cosmetic) or whether inconsistent header metadata combined with `--unidiff-zero` can cause misplacement in practice; this would need to be confirmed empirically against the actual `git apply` behavior for multi-hunk partial selections with duplicate content, which is outside what the static code/index can confirm.

### Recommendation
When building the synthetic patch in `formatPatch()`/`formatPatchToDiscardChanges()`, track a running line-offset delta across hunks and add it to each subsequent hunk's `oldStartLine`/`newStartLine` to reflect the actual effect of previously skipped/altered hunks, rather than reusing the raw `hunk.header` values unmodified [1](#0-0) . Additionally, reconsider or minimize reliance on `--unidiff-zero`, since it removes a safety net that would otherwise catch such offset mismatches [3](#0-2) .

### Proof of Concept
Static evidence only (I could not execute `git apply` to confirm the runtime effect):
1. Take a file with two hunks in its working-tree diff, where hunk 1 nets a line-count change (e.g. old 10 lines → new 6 lines, a −4 delta) and hunk 2 begins shortly after.
2. In the Desktop diff UI, deselect all of hunk 1 and select only hunk 2, then stage (or discard) via the line-selection UI.
3. `formatPatch()` emits hunk 2 using the original `hunk.header.newStartLine` (e.g. `+17`) even though hunk 1's −4 line delta is not present in the emitted patch, so the true post-image position should be `+21` [1](#0-0) . This exact scenario is present in the existing test suite: [7](#0-6) , confirming the header is emitted unadjusted for the dropped hunk.
4. The patch is submitted to `git apply --cached --unidiff-zero --whitespace=nowarn -` (or the non-cached discard variant) [3](#0-2) [4](#0-3) , with the normal context-consistency check disabled.

Given the residual uncertainty about whether `git apply` actually mis-locates the hunk under these conditions in practice, this should be treated as a **credible but not fully confirmed** finding; a background engineering session with access to a real git binary would be needed to construct a concrete duplicated-context repository and demonstrate an actual misapplied/corrupted commit end-to-end.

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

          return
