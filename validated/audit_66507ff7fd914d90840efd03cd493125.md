### Title
OP_RETURN data output excluded from weight/vbytes calculation causes underpriced fee and unchecked transaction size - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` payload, which it commits to an OP_RETURN output (lines 194-202). However, the weight/vbyte computation at line 204 (`calculate_weight_vbytes(tx_ins.len(), payments, None)`) is fed only `payments` — the caller-supplied `(ScriptBuf, u64)` list — and never the OP_RETURN `TxOut` that was just pushed into `tx_outs`. The `change`-branch recomputation at lines 225-226 has the same flaw. As a result, `needed_fee` is computed over a transaction that omits up to ~89 weight units (8-byte amount + script + up to 80 bytes of pushed data), and the `MAX_STANDARD_TX_WEIGHT` check at line 241 also runs against an underestimated `weight`. This is the Serai analog of the report's miscalculated fee: a caller-supplied value (the `data` bytes) is silently miscalculated into the fee/weight accounting.

### Finding Description
The OP_RETURN output is constructed before the fee calculation: [1](#0-0) 

but `calculate_weight_vbytes` only iterates `payments` (and optionally `change`): [2](#0-1) 

so `needed_fee = fee_per_vbyte * vbytes` at line 206 and `fee_with_change` at line 227 both understate the true virtual size. The final `weight > MAX_STANDARD_TX_WEIGHT` rejection at line 241 likewise uses the weight without the OP_RETURN output. Note the assertion in the processor's `plan.rs` (`assert!((new_outputs + total_fee) <= original_outputs)`) only checks that the *target* fee is collected, not that the target fee matches the real serialized size — so the miscalculation propagates through to a broadcast transaction.

### Impact Explanation
Any caller (including an unprivileged user requesting a withdrawal whose plan carries a `data` payload) causes the threshold network to produce a transaction whose actual fee rate is `needed_fee / actual_vbytes` < `fee_per_vbyte`. With a full 80-byte payload the understatement is ~22-25 vbytes (OP_RETURN script + amount + output overhead). Since `needed_fee` is validated against the relay minimum using the same understated `vbytes` (line 211), the resulting transaction can sit below `DEFAULT_MIN_RELAY_TX_FEE`'s *actual* requirement — i.e., it may be constructed, signed, and then rejected by the Bitcoin network as non-relayable, leaving funds committed to an unspendable/unpropagatable transaction. The weight check bypass is bounded (~89 WU) so it cannot push a borderline tx over the 400,000 WU standardness limit by much, but the underpriced-fee outcome is concrete.

### Likelihood Explanation
The `data` parameter is a public input to `SignableTransaction::new` — no privileged position is needed to supply up to 80 bytes. The bug triggers deterministically whenever `data` is `Some`, since the OP_RETURN output is always omitted from both fee-rate and weight accounting. Severity is bounded to Medium: the effect is a fee-rate miscalculation producing potentially non-relayable transactions, not theft or forgery.

### Recommendation
Include the OP_RETURN output in the weight computation: build the full `tx_outs` list (payments + data + optional change) *before* calling `calculate_weight_vbytes`, and pass the complete output set — or pass `data`-bearing `TxOut`s into the function — so `vbytes`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually signed. Add a unit test constructing a `SignableTransaction` with a maximal `data` payload asserting `fee() / real_vsize >= fee_per_vbyte` and `>= DEFAULT_MIN_RELAY_TX_FEE` scaled to the true size.
