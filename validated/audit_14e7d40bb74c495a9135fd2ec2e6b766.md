### Title
Unsafe raw `.call()` for token transfers in Tron IntentGatewayV2 does not check return-data boolean, allowing silent transfer failure while escrow is finalized as paid - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` mixes `SafeERC20` (used for inbound `safeTransferFrom`) with raw, unsafe outbound token payouts in `withdraw()` and in the `SweepDust` branch of `onAccept()`. These outbound paths use `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level call did not revert (`success`), never decoding/checking the ERC20 boolean return value, exactly the bug class from the referenced report.

### Finding Description
In `withdraw()`, escrow release is performed as: [1](#0-0) 

and finalization happens unconditionally alongside it: [2](#0-1) 

`success` from a low-level `.call()` only indicates the callee did not revert; it says nothing about the ERC20 return value. Many tokens (including non-standard TRC20/ERC20 tokens deployed on Tron) signal failure by returning `false` in the ABI-encoded return data instead of reverting — e.g., on insufficient allowance/edge cases, paused/blacklisted transfers, or custom business logic. Because `success` will be `true` in that case, `if (!success) revert TransferFailed();` never triggers, so:
- `_orders[body.commitment][token] -= amount;` decrements the escrow accounting as if the beneficiary was paid.
- `_filled[body.commitment] = beneficiary;` marks the order as finalized/filled.
- `EscrowReleased`/`EscrowRefunded` is emitted, signaling success cross-chain.

Yet the tokens never actually left the contract. The beneficiary receives nothing, and the escrow record no longer reflects the tokens still held by the contract — they become permanently stuck with no remaining accounting path to reclaim them.

The same unsafe pattern is repeated for the fee-token payout and for `SweepDust`: [3](#0-2) [4](#0-3) 

Notably, this contract explicitly imports and uses `SafeERC20` for the inbound leg: [5](#0-4) [6](#0-5) 

demonstrating the fix pattern was known and applied elsewhere in the same file and in the canonical EVM version (`evm/src/apps/intentsv2/IntentsBase.sol`), which correctly uses `safeTransfer`: [7](#0-6) 

but the outbound payout paths in the Tron variant were left with the unsafe raw-call pattern.

`withdraw()` is reached from the normal, non-malicious protocol flow: a solver fills an order and the resulting `RedeemEscrow`/`RefundEscrow` request is delivered via `onAccept`, guarded only by `onlyHost` + `authenticate()` (proof validity, not token behavior): [8](#0-7) 

No relayer/prover misbehavior is required — the vulnerability is purely in how the contract interprets the ERC20 call outcome for whatever `token` is configured in the order's input assets.

### Impact Explanation
This is a direct loss-of-funds bug matching the bounty's "stealing or loss of funds" and "false state acceptance" categories: escrow state is unconditionally marked as released/finalized even when the underlying token transfer silently failed, permanently locking the affected tokens in the contract with no remaining accounting reference, and denying the rightful beneficiary their payout.

### Likelihood Explanation
Likelihood is Medium: the order's input/output token is user/solver-supplied (via `TokenInfo.token` in `Order.inputs`), so any account placing an order can pick a token whose `transfer()` implementation returns `false` under some conditions instead of reverting — this is a well-known real-world ERC20/TRC20 quirk, not a hypothetical. No admin, relayer, or prover compromise is needed; only a specific token behavior on a legitimately settled order.

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` outbound payouts in `withdraw()` and the `SweepDust` handling in `onAccept()` with `SafeERC20.safeTransfer()`, consistent with the inbound leg and with the canonical `IntentsBase.sol` implementation, so both revert-on-failure and false-return-on-failure tokens are handled correctly before escrow/finalization state is mutated.

### Proof of Concept
1. User places an order whose input token is a non-standard ERC20/TRC20 that returns `false` (rather than reverting) on a failed `transfer()` (e.g., due to an internal check like a paused state or blacklist that the token silently enforces).
2. Solver fills the order normally; a `RedeemEscrow` request is dispatched and later delivered to `onAccept` → `withdraw()` on the source chain, per lines 620-626 and 682-705 of `evm/tron/contracts/apps/IntentGatewayV2.sol`.
3. At the moment of payout, the token's internal condition causes `transfer()` to return `false` without reverting.
4. `success` is `true` (external call didn't revert) so `TransferFailed` is not raised; `_orders[...][token] -= amount` and `_filled[commitment] = beneficiary` execute as if payment succeeded, and `EscrowReleased` is emitted.
5. The beneficiary receives zero tokens, while the contract's real token balance still contains the escrowed amount with no order/commitment entry pointing to it — funds are stuck permanently.
