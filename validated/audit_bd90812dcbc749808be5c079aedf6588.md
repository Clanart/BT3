### Title
External payments to the protocol's reserved offset script_pubkeys are misclassified as internal `Change`/`Forwarded`/`Branch` outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` identifies relevant outputs solely by `script_pubkey` equality against every registered offset script (`self.scripts.get(&output.script_pubkey)`, `networks/bitcoin/src/wallet/mod.rs:205`). `Bitcoin::get_outputs` then labels each scanned output with `kinds[offset]`, i.e. `OutputType::{External, Branch, Change, Forwarded}` (`processor/src/networks/bitcoin.rs:686-700`). The `Branch`, `Change`, and `Forwarded` script_pubkeys are pure functions of the public group key (`p2tr_script_buf(key + G*offset)` via `branch_address`/`change_address`/`forward_address`, lines 661-674), so any unprivileged party can compute them and pay to them. There is no authentication that an output paying to an internal script was actually produced by the protocol. This is the direct analog of the reported bug: the external `mintWithId` occupies an id inside the sale's reserved id-range; here an external transaction occupies the protocol's reserved script space, and the protocol cannot distinguish it from its own outputs.

### Finding Description
- `Scanner::new`/`register_offset` build `scripts: HashMap<ScriptBuf, Scalar>` covering the external key plus the three hash-derived offsets registered in `processor/src/networks/bitcoin.rs:313-347`.
- `scan_transaction` returns a `ReceivedOutput` for *any* on-chain output whose `script_pubkey` matches, with no check of provenance.
- `get_outputs` unconditionally assigns `kind = kinds[offset]` and only attaches the parsed `data` (`extract_serai_data`) when `kind == OutputType::External` (lines 731-734); it also unconditionally sets `presumed_origin` from `tx.input[0]` (lines 715-728), indexing `tx.input[0]` on any transaction that touches a scanned script.
- Consequences reachable by an unprivileged sender:
  1. A payment to the `Change`/`Forwarded`/`Branch` address is reported to the scheduler as an internal output type, not a deposit. Funds "received" are handled under change/forward semantics (e.g. fed to the UTXO scheduler's forwarding/aggregation path) rather than credited — deposits to a derivable protocol address silently miscategorized.
  2. An attacker can force the multisig to treat arbitrary attacker-funded outputs as `Forwarded`, driving unintended signing/forwarding work and fee expenditure (griefing of the reserved output pipeline).
  3. The `tx.input[0]` dereference in `get_outputs` presumes a specific transaction shape for anything touching these scripts; attacker transactions of arbitrary shape are processed under this assumption.

### Impact Explanation
Medium. The protocol assumes the Branch/Change/Forwarded script space is exclusively occupied by its own transactions (the comment at line 313, "Always construct the full scanner in order to ensure there's no collisions", guards only internal collisions). An external party intersecting that space causes funds to be classified and routed under the wrong `OutputType`, which corrupts the scanner→scheduler pipeline the same way an intersecting mint corrupts the sale's id range: the operation executes on an identifier the protocol believed it owned.

### Likelihood Explanation
High reachability, moderate impact. Computing the internal addresses requires only the public group key and the public `hash_to_F` offset constants (`KEY_DST`, `"branch"`, `"change"`, `"forward"`), and sending to them is an ordinary Bitcoin payment — no validator status, no collusion, no key material. The cost is only the funding amount, which the attacker may partially recover only if the misclassification is later corrected.

### Recommendation
Bind outputs to protocol intent rather than script alone: e.g. require `Change`/`Forwarded` outputs to originate from a transaction spending a known protocol input (verify against `presumed_origin`/outpoint lineage), or treat payments to internal scripts lacking an InInstruction/plan context as `External` deposits or drop them with an explicit event. Alternatively, embed the output-type tag in committed transaction data the scanner validates, instead of inferring it purely from `script_pubkey`.

### Proof of Concept
1. Observe the multisig group key `K` (public).
2. Compute `change_addr = p2tr_script_buf(K + G * hash_to_F(KEY_DST, "change"))` via the public `Bitcoin::change_address`/`scanner()` path.
3. Broadcast a transaction paying ≥ `DUST` (10,000 sat) to `change_addr` with arbitrary inputs (e.g. any P2PKH/P2TR input) and no Serai OP_RETURN data.
4. `get_outputs` scans the block, finds the matching `script_pubkey`, and emits `Output { kind: OutputType::Change, presumed_origin: <attacker's input[0] address>, data: [] }` — an attacker-created output now occupies the reserved change-output space and is handed to the scheduler as protocol-internal change, while `assert_eq!(output.tx_id(), tx.id())` and the `input[0]` origin fetch run on attacker-shaped data.

Note: I verified the scanner/`get_outputs` path directly; I could not fully trace the scheduler's downstream handling of `OutputType::Change`/`Forwarded` inputs within the available iterations, so the exact end-state (mis-credit vs. forced forward vs. stall) is inferred from the `kind`-based routing design rather than confirmed in the scheduler code.
