### Title
Untrusted `ReceivedOutput` deserialization accepts any offset/output/outpoint triple without verifying the offset derives the output's script - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes a scalar `offset`, an arbitrary `TxOut`, and an arbitrary `OutPoint` from untrusted bytes with no consistency check. The scanner (`Scanner::scan_transaction`) is the only code path that establishes the invariant binding these three fields — it only constructs a `ReceivedOutput` when `output.script_pubkey` equals a registered `p2tr_script_buf(key + G*offset)` and the outpoint refers to a real transaction output. The deserialization path skips this binding entirely, so any unprivileged party that can feed bytes into `ReceivedOutput::read` can fabricate received outputs that were never authorized/derived by the scanner — the analog of a low-privilege actor adding content to a resource they do not control.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping each registered P2TR script to the scalar offset that derives it (`register_offset`, lines 180-196). `scan_transaction`/`scan_block` (lines 199-227) only emit a `ReceivedOutput` when a tx output's `script_pubkey` matches a registered script, and set `outpoint` to the actual `(txid, vout)`.

`ReceivedOutput::read` (lines 122-134) reconstructs the same structure from a byte stream:

- `offset`: any scalar accepted by `Secp256k1::read_F`
- `output`: any `TxOut` decodable by consensus rules
- `outpoint`: any `OutPoint`

There is no check that `p2tr_script_buf(key + G*offset) == output.script_pubkey`, no check that the outpoint exists on chain, and no authentication of the byte source. The `offset` field is exactly what makes the output "spendable" (it is the HDKD scalar needed to produce the spending signature), so a forged `ReceivedOutput` is not merely mislabeled data — it directly feeds the wallet's spendable-set accounting.

### Impact Explanation
A `ReceivedOutput` whose `offset` does not correspond to `output.script_pubkey` describes an output the threshold key cannot sign for: the spendable key would be `key + offset`, while the output locks to a different tweaked key. If the fabricated script isn't even a P2TR output for a derivable key, the funds are unspendable entirely. Consequences depending on how the consumer uses deserialized outputs:

- **Funds reported received that are not spendable**: a fabricated `ReceivedOutput` inflates the reported balance; a subsequent spend constructed over it produces a transaction that can never be signed (or is signed against the wrong key and rejected by the network).
- **Phantom deposits**: pairing a real-looking `outpoint`/`TxOut` belonging to someone else with an arbitrary offset credits the wallet with UTXOs it does not own and cannot spend.
- **Griefing of coin selection**: spendable-set construction that trusts deserialized `ReceivedOutput`s can be forced to select invalid inputs, stalling withdrawals/batches until the bad entries are purged.

This is a Medium-severity analog: integrity impact only (C:N/I:H/A:N profile of the source advisory), reachable purely by supplying bytes to `ReceivedOutput::read` — no key material, collusion, or malformed-curve inputs required.

### Likelihood Explanation
Exploitation requires a path where a serialized `ReceivedOutput` crosses a trust boundary — e.g., outputs persisted to a DB/writeable store, relayed between processor components, or reconstructed from coordinator/RPC-provided data rather than freshly scanned. In those flows, any party able to write or relay the bytes (which the threat model treats as unprivileged — the whole point of deserialization helpers exposed on untrusted input per `read_F`/`read_G` conventions) can inject forged entries. The scanner path itself is safe; the vulnerability is the asymmetric trust between `scan_*` (validating constructor) and `read` (unvalidated constructor). Where callers persist scanner results and reload them, an attacker with write access below the signing layer escalates "data write" into "funds accounting write" — precisely the broken-access-control shape of the reference CVE.

### Recommendation
Bind the deserialization to the validating constructor:

- Make `ReceivedOutput` fields private-constructible only via `Scanner` (expose `read` on `Scanner` instead: `Scanner::read_output` that re-verifies `self.scripts.get(&output.script_pubkey) == Some(&offset)` and rejects otherwise).
- If a standalone `read` must exist, it should take the wallet `key`/registered scripts and perform the same `p2tr_script_buf(key + G*offset)` check before returning `Ok`.
- Consumers should additionally confirm `outpoint` resolves to an on-chain output with matching `TxOut` before treating the entry as spendable.

### Proof of Concept
Conceptual (no code execution):

1. Honest setup: `Scanner::new(key)` registers `scripts[p2tr(key)] = 0`.
2. Attacker crafts bytes: `offset = 0`, `output = TxOut { value: 1_000_000, script_pubkey: <victim's P2TR script or arbitrary script> }`, `outpoint = OutPoint::new(<any txid>, 0)`.
3. `ReceivedOutput::read(&mut bytes)` returns `Ok` — the same structure `scan_transaction` would emit for a genuine deposit, indistinguishable downstream.
4. Wallet marks 1_000_000 sats as received/spendable. Either the outpoint doesn't exist (phantom balance) or it exists but isn't spendable under `key + offset` (unspendable funds; any spend attempt fails at signing or network validation).

Caveat: I could not fully confirm every consumer of `ReceivedOutput::read` in the remaining iteration budget; the finding holds wherever the reader treats deserialized outputs as equivalent to scanner-produced ones, which the `#[derive(PartialEq)]` and identical field semantics encourage.
