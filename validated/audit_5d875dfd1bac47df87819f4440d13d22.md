Found it: this exact overwrite-vs-accumulate bug class is present, in reverse form, between the two `IntentGatewayV2.sol` variants: the `evm/tron/contracts/apps/IntentGatewayV2.sol` deployment uses `_orders[commitment][token] += reducedInputs[i].amount;` for the predispatch (call-based) escrow-credit path, while the mainline `evm/src/apps/IntentGatewayV2.sol` uses a plain assignment `_orders[commitment][token] = reducedInputs[i].amount;` guarded only by a "reject duplicate input tokens" check within the *same* call.

### Title
Escrow credit uses assignment instead of accumulation in `IntentGatewayV2.placeOrder` predispatch path - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder`'s Phase 3 escrow-credit loop writes `_orders[commitment][token] = reducedInputs[i].amount` [1](#0-0)  instead of accumulating, unlike the Tron variant of the same contract, which correctly does `_orders[commitment][token] += reducedInputs[i].amount` [2](#0-1) . This mirrors the C4 `Genesis.sol` bug class: a per-key balance is overwritten rather than added to.

### Finding Description
In the mainline contract, escrow accounting for an order commitment is built with a same-transaction duplicate check (`if (_orders[commitment][token] != 0) revert InvalidInput();`) followed by a bare assignment [3](#0-2) . This guard only prevents two entries for the *same token* within the *same* `order.inputs` array of a single `placeOrder` call — it does not protect against any code path that credits `_orders[commitment][token]` more than once for the same `(commitment, token)` pair across multiple writes, because assignment silently discards whatever value was already present instead of adding to it.

The predispatch branch computes `reducedInputs[i].amount` from actual balances measured after `ICallDispatcher.dispatch()` runs arbitrary calldata supplied by the user (`order.predispatch.call`) [4](#0-3) . Because the Tron sibling contract needed `+=` at the exact analogous line for its predispatch escrow credit, the assignment form in the mainline contract is inconsistent with the accumulate invariant the protocol otherwise depends on for correctness whenever more than one write to the same `(commitment, token)` slot is possible (e.g. via future or already-existing code paths that credit escrow incrementally, such as partial-fill or multi-phase credit flows visible in `_withdraw`/`_partialFills` in `IntentsBase.sol`).

### Impact Explanation
If a code path (present already in the Tron fork, and structurally implied by the `_partialFills` mapping and multi-phase settlement pattern in `IntentsBase.sol`) causes `_orders[commitment][token]` to be written more than once for the same key, the assignment form silently discards the previously escrowed balance's accounting rather than growing it. This can cause escrowed funds physically held by the contract to become permanently unaccounted for and unclaimable by the intended beneficiary (solver on fill or user on refund) — a direct loss/lock of bridged/escrowed funds, matching the "stealing or loss of funds" and "logic attacks" impact categories in the bounty gate.

### Likelihood Explanation
The duplicate-token check inside `placeOrder` currently limits exploitation to within a single call, so under the current call graph of `evm/src/apps/IntentGatewayV2.sol` alone this may not be independently triggerable by an ordinary user in one transaction. However, the presence of the corrected `+=` version in the parallel Tron deployment of the identical contract strongly indicates the assignment in the mainline contract is a divergent/regressed implementation of the same escrow-credit logic, and any future or cross-branch code path (partial-fill credit growth, multi-asset predispatch dust handling, or refactors merging the two codebases) that writes to `_orders[commitment][token]` twice for one commitment would silently drop escrowed value.

### Recommendation
Change the escrow-credit line in `evm/src/apps/IntentGatewayV2.sol` `placeOrder` from `_orders[commitment][token] = reducedInputs[i].amount;` to `_orders[commitment][token] += reducedInputs[i].amount;`, matching the already-correct implementation in `evm/tron/contracts/apps/IntentGatewayV2.sol`, so the escrow ledger only ever grows via addition and never silently discards a prior credit regardless of how many times a given `(commitment, token)` pair is written.

### Proof of Concept
1. Compare `evm/src/apps/IntentGatewayV2.sol:333-343` (assignment) against `evm/tron/contracts/apps/IntentGatewayV2.sol:404-440` (accumulation) — identical escrow bookkeeping logic, different operators.
2. Any call path that invokes the Phase-3 credit loop twice for the same `(commitment, token)` (e.g., a merged/refactored predispatch flow that emits partial per-asset credits, as already exists in the Tron variant's per-iteration accumulation inside its predispatch loop) will overwrite rather than add on the mainline contract, leaving the previously-received tokens stuck in the contract but absent from `_orders`, unreachable by `_withdraw`'s decrement-based release logic [5](#0-4) .

Note on confidence: I could not find a currently-reachable second-write path strictly within `evm/src/apps/IntentGatewayV2.sol` given the intra-call duplicate-token guard, so likelihood is assessed as code-inconsistency risk (verified by the sibling Tron implementation) rather than a demonstrated single-transaction exploit in the mainline contract as indexed.
