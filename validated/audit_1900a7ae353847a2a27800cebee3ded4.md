## Title
Copilot conflict-resolution reassembly silently misattributes/misapplies merged content on diff3 (three-way) conflicts, corrupting committed files - ([File: app/src/lib/copilot-conflict-resolution.ts])

## Summary
The report describes a value-accounting mismatch: one function (`accruePackageReward`) computes an expected amount while the actual transfer mechanism silently delivers less, and a second function (`releaseRewards`) later trusts that mismatched accounting and fails/corrupts state. The Desktop analog is `app/src/lib/copilot-conflict-context.ts`'s `extractConflictHunks` (which decides what conflict content is shown to the Copilot model) versus `app/src/lib/copilot-conflict-resolution.ts`'s `reassembleResolvedFile` (which decides where the model's resolution is spliced back into the file on disk). The two functions use different marker-detection logic and disagree on diff3 (three-way merge) conflicts, so the content sent to the model does not correspond to what actually gets replaced on disk — an attacker-controlled repository file can make Desktop silently corrupt what the user commits.

## Finding Description
`extractConflictHunks` explicitly understands three marker types — `oursMarker` (`<<<<<<<`), `baseMarker` (`|||||||`), and `theirsMarker`/`separatorMarker` — and switches parsing state when it sees `|||||||`: [1](#0-0) [2](#0-1) 

`reassembleResolvedFile`, which later splices the model's per-hunk resolution back into the raw file content, only recognizes two markers — `=======` and `>>>>>>>` — and has **no concept of `|||||||` at all**: [3](#0-2) [4](#0-3) 

Concretely: if the *base* section of a real diff3 conflict (the content between `|||||||` and the real `=======`) happens to contain a line that is exactly seven `=` characters (a common ASCII-art/section-divider convention in text, markdown, changelog, or config-like files — fully attacker-controlled since it's ordinary file content, not a conflict marker), `extractConflictHunks`'s base-collection loop stops at that stray line (it only checks `separatorMarker`, not full context) and misclassifies everything after it — including the true separator and the true "theirs" content — as `theirsContent`: [5](#0-4) 

This corrupted `oursContent`/`baseContent`/`theirsContent` triple is what gets sent to the model (via `formatConflictContextForPrompt`), so Copilot resolves the conflict based on a garbled understanding of which lines belong to which side.

`validateResolutionPaths` only checks that the *number* of hunks returned matches the *number* of hunks extracted — it never re-validates hunk boundaries or content against the original file: [6](#0-5) 

`reassembleResolvedFile` then splices the model's resolution into the file using its own, marker-blind boundary detection, matched "by order, not by line number" as the code comment itself states: [7](#0-6) 

Because `reassembleResolvedFile` still finds the same start/end line indices for this hunk (it keeps scanning past the stray `=======` since `hasSeparator` is a sticky flag, and only breaks on the real `>>>>>>>`), the hunk count and boundary stay superficially consistent, so no error is raised anywhere in the pipeline — the model's answer (produced from corrupted context) is written straight to disk as the "resolved" file.

## Impact Explanation
This breaks the invariant the whole feature depends on: *the text sent to the model for resolution must be the same text that gets replaced on disk*. When it isn't, Copilot can silently discard or misattribute real "theirs"/base content that it never actually saw as distinct — resulting in **silent corruption of what the user commits** during a merge/rebase/cherry-pick conflict resolution, with no warning, no diff review requirement beyond what's already shown, and no re-validation against the original markers. This matches the accepted impact category of "silent corruption of what the user commits or pushes." The corruption is deterministic in terms of which lines are misclassified; the exact resulting file content additionally depends on how the model responds to garbled input, but the *desync itself* is fully attacker-controlled and reproducible without relying on any social engineering, local access, or leaked credentials — only a routine merge against a repository/branch that contains this content.

## Likelihood Explanation
The trigger condition is narrow (diff3 merge is required — `git config merge.conflictstyle diff3` or `merge.conflictstyle merge` with the base marker enabled, plus a base section containing a stray 7-character `=` line) and requires the user to invoke the Copilot conflict-resolution flow rather than resolving manually. Diff3 style is not Desktop's default, so this reduces likelihood; however, it requires no special user action beyond a normal merge with an attacker-influenced file and clicking the existing "Resolve with Copilot" action, so it is Medium likelihood rather than a contrived attack chain.

## Recommendation
Make `reassembleResolvedFile` marker-detection symmetric with `extractConflictHunks`: track `|||||||` and only recognize the closing `=======` that immediately follows base content (or reuse a single shared parsing routine for both extraction and reassembly so they can never disagree). Additionally, `validateResolutionPaths` should validate more than hunk *count* — e.g., re-derive hunk boundaries at reassembly time and diff them against what was sent to the model, or embed a content checksum per hunk in the request/response so any mismatch fails loudly instead of silently splicing based on divergent parses.

## Proof of Concept
```
<<<<<<< HEAD
ours content
||||||| merged common ancestors
some legitimate base text
=======
this is a plain divider used as ordinary content, not a real conflict marker, but it matches /^={7}$/
more base text that should never reach the model as "theirs"
=======
real theirs content
>>>>>>> feature-branch
```
1. Attacker contributes/merges a branch where the base (common ancestor) revision of a tracked file contains a stray line consisting of exactly seven `=` characters within what will become a diff3 base section.
2. Victim merges/rebases against this content with `merge.conflictstyle diff3` (or `merge`) enabled, producing the marker layout above.
3. Victim opens Desktop's "Resolve with Copilot" flow. `extractConflictHunks` [5](#0-4)  misclassifies "more base text that should never reach the model as 'theirs'" plus the real "=======" plus "real theirs content" as a single `theirsContent` blob, while `baseContent` only contains "some legitimate base text".
4. Copilot resolves the conflict based on this corrupted view (it never sees a true separation between base and theirs).
5. `reassembleResolvedFile` [4](#0-3)  still locates the same overall hunk span (line 1 through the real `>>>>>>> feature-branch`), so no count/validation error is raised, and the model's answer — derived from the corrupted context — is written verbatim into the user's working file and offered for commit.

**Uncertainty note**: I was not able to fully trace the exact write-to-disk call site (`copilot-store.ts` / `app-store.ts` consumers of `reassembleResolutions`) within the available search results, so I cannot cite the precise line where the reassembled content is written to disk without markers being re-checked; the finding is based on the parsing/reassembly logic itself, which is fully verified from source.
