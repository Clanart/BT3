### Title
Panic on attacker-controlled participant key list in MuSig key aggregation (`u16::try_from(our_i).expect(...)` before bounds check) - ([File: crypto/dkg/musig/src/lib.rs])

### Summary
`musig()` locates the caller's public key inside a caller-supplied `keys: &[C::G]` list *before* the list length is validated. If the list contains more than `u16::MAX` entries and the caller's key sits at an index `> u16::MAX`, `u16::try_from(our_i).expect(...)` panics instead of returning `MusigError::TooManyKeysProvided`. Analogous to CVE-2022-1183, an unprivileged party supplying a crafted participant set causes an assertion-style abort in production DKG code.

### Finding Description
In `crypto/dkg/musig/src/lib.rs`, `musig()` computes `our_i = keys.iter().position(...)` at line 122, then only afterwards calls `check_keys::<C>(keys)` (line 126), which is what enforces `keys.len() <= u16::MAX`. `ThresholdParams::new` is then built with:

```rust
// crypto/dkg/musig/src/lib.rs:128-135
let params = ThresholdParams::new(
  keys_len,
  keys_len,
  Participant::new(
    u16::try_from(our_i).expect("keys.len() <= u16::MAX yet index of keys > u16::MAX?") + 1,
  )
  .expect("i + 1 != 0"),
)
```

The `expect`'s invariant ("keys.len() <= u16::MAX") is not yet established at the point `u16::try_from(our_i)` runs — `check_keys` has not been called when `position` is computed, and even though `check_keys` runs before the `expect`, nothing constrains `our_i`: `position` was already taken over the unvalidated slice. If `keys.len() > u16::MAX` and the victim's public key is at index `65536` or beyond, `u16::try_from(our_i)` returns `Err` and the `expect` panics. There is also a latent second panic: even after `check_keys` passes, `keys_len` can be `u16::MAX`, in which case a `keys` list of exactly 65535 entries puts `our_i = 65534`, `u16::try_from` succeeds giving `65535`… fine — but with `keys_len = u16::MAX` and `our_i` at the last index, `Participant::new(our_i + 1)` gets `65535`, valid; however a list of length `u16::MAX` where `our_i + 1 == 65536` is impossible since `our_i < len <= 65535`. The primary bug is the missing length check before `position`/`try_from`.

The `keys` slice is public input: in a MuSig-style n-of-n DKG it is assembled from the public keys advertised by all participants, so any participant can inflate it. The same reachable-panic pattern exists conceptually in `ThresholdView::original_verification_share`/`verification_share` (documented panics on out-of-set `Participant`), but those require a caller-supplied index rather than attacker bytes.

### Impact Explanation
A panic in `musig()` aborts the calling thread/process during distributed key setup. If the DKG runs in a validator/coordinator context where any participant may propose or relay a key list, a single malicious participant can crash honest nodes attempting key aggregation — availability loss matching the CVE's "daemon terminates with an assertion failure" class. No secret material is leaked, so this is a pure DoS (Medium severity analog; the CVE itself was rated High for a network-facing daemon).

### Likelihood Explanation
Exploitation requires the victim to run `musig()` over a key list the attacker influences, and the list must exceed 65535 points (~2 MB for 32-byte encodings — cheap to produce) with the victim's key placed at index ≥ 65536. Whether an attacker controls ordering and length depends on the integrator's protocol; where participants contribute keys to a shared aggregation (the design intent of this crate, per `ThresholdKeys`/`Participant` usage in FROST/DKG flows), ordering is attacker-influenceable. It is deterministic once reachable — no probabilistic requirement.

### Recommendation
Run `check_keys::<C>(keys)` before `keys.iter().position(...)`, and return `MusigError::TooManyKeysProvided`/`NotPresent` instead of panicking:

```rust
let keys_len = check_keys::<C>(keys)?;            // validate length + duplicates first
let our_pub_key = C::generator() * private_key.deref();
let Some(our_i) = keys.iter().position(|key| *key == our_pub_key) else {
  Err(MusigError::DkgError(DkgError::NotParticipating))?
};
// now our_i < keys_len <= u16::MAX, and Participant::new(our_i as u16 + 1) cannot fail
```

### Proof of Concept
```rust
// Victim's key
let private_key = Zeroizing::new(<C as Ciphersuite>::F::random(&mut OsRng));
let our_pub = C::generator() * private_key.deref();

// Attacker-supplied key list: > u16::MAX entries, victim's key last
let mut keys = vec![C::generator() * <C as Ciphersuite>::F::from(1u64); 65537];
keys[65536] = our_pub;

// Panics inside musig at:
//   u16::try_from(our_i).expect("keys.len() <= u16::MAX yet index of keys > u16::MAX?")
// instead of returning Err(MusigError::TooManyKeysProvided { max: 65535, provided: 65537 })
let _ = musig::<C>([0u8; 32], private_key, &keys);
```

Root cause: `crypto/dkg/musig/src/lib.rs` lines 122–135 — `position()` over the unvalidated slice, followed by an `expect` whose invariant is only enforced by `check_keys` which is invoked (line 126) after `our_i` is already determined, and which would have rejected the oversized list had ordering been correct.
