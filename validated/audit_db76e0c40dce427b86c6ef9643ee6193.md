### Title
Webhook `shop_domain` Identity Is Not Bound to the HMAC-Verified Payload, Enabling Cross-Shop Webhook Spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only proves that the raw request body was signed with the app's shared client secret; it never proves that the `X-Shopify-Shop-Domain` header actually corresponds to the shop whose data produced that signed body. Any merchant who has installed the app can legitimately obtain a validly-signed webhook for their own shop and then replay that same signed body while substituting a different shop's domain in the (unsigned) header, and the request still passes verification.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes the signature exclusively over `request.raw_post` using the app's shared secret: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` gates on `hmac_valid?(data)` alone: [2](#0-1) 

The concern separately exposes a `shop_domain` accessor that simply reads the unauthenticated `X-Shopify-Shop-Domain` header, with no cryptographic link to the HMAC-covered body: [3](#0-2) 

The gem's own documentation instructs developers building custom webhook controllers to trust this unverified `shop_domain` value directly for job dispatch/tenant scoping: [4](#0-3) 

This is structurally the same bug class as the reported analog: a signature check validates that *some* legitimate party produced the payload (RandaoReveal ⇒ HMAC), but a separate identity field used for authorization/attribution (ProposerIndex ⇒ shop_domain) is never cross-checked against what was actually signed. Since the HMAC secret (`ShopifyApp.configuration.secret`/`old_secret`) is shared across all shops of a given app installation rather than being shop-specific, a malicious merchant who has installed the app can capture their own genuinely-signed webhook body/HMAC pair and re-submit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. The signature still validates (it only covers the body), so the request is accepted and processed as if it originated from the victim shop.

### Impact Explanation
A downstream job keyed on `shop_domain` (as shown in the documented custom-controller pattern) would execute shop-scoped logic (e.g., data updates, redactions, or business logic keyed by shop) attributing an attacker-controlled payload to a victim shop it did not originate from — a cross-shop request-forgery/attribution bypass accepted as an authentic signed request from Shopify.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate (even single, low-trust) merchant of the app who can trigger any webhook topic on their own shop to obtain a valid signature, then replay it with a forged domain header to the public webhook endpoint. No secret leakage or elevated privilege is needed beyond ordinary app installation.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header (or the `shop_domain` convenience accessor) as an authenticated identity. Either include the shop domain in the HMAC-signed material and verify it as part of `hmac_valid?`, or derive/cross-validate the shop identity from data that is itself covered by the signature (e.g., verify the header value against the shop associated with the webhook body's resource, or require it to match a shop with an active, verified session before dispatching shop-scoped jobs).

### Proof of Concept
1. Merchant M installs the app on `m.myshopify.com` and configures a webhook (e.g., `carts/update`).
2. M triggers the topic, receiving from Shopify a POST with `raw_post = B` and header `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`.
3. M replays the exact same body `B` and HMAC header to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `PayloadVerification#hmac_valid?` only checks `HMAC(secret, B)` against the header — it passes. [5](#0-4) 
5. A custom controller following the documented pattern calls `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` using the forged domain, causing the job to run against `victim.myshopify.com`. [6](#0-5)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
