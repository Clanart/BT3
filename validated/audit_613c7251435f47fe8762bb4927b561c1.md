## Title
Stale Line-Selection Indices Reused Against a Freshly Re-Fetched Diff Allow Silent Corruption of Partially Committed Content - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported Solana bug is fundamentally about a state-mutating operation (`process_burn_withdrawal_ticket`) that trusts a caller-supplied value (`min_amount_out`) and an implicit precondition (a prior "state tracker" update) without re-validating that the on-chain state still matches what the caller believed was true when it decided to proceed — letting stale/attacker-influenced state produce a result the user never agreed to. The equivalent broken invariant exists in GitHub Desktop's partial-commit ("stage selected lines") pipeline: the UI computes line-selection indices against one snapshot of a file's diff, but `applyPatchToIndex` re-fetches a brand-new diff from disk at commit time and blindly reapplies those stale indices to it, with no check that the diff hasn't changed underneath the user's selection.

### Finding Description
When a user partially stages a file (checks only some diff lines/hunks for commit), Desktop stores the selection as a set of **absolute line indices** on `WorkingDirectoryFileChange.selection` [1](#0-0) . These indices are computed against the `ITextDiff` that was loaded into the UI at selection time.

At commit time, however, `applyPatchToIndex` does **not** reuse that already-loaded diff. It independently re-invokes `getWorkingDirectoryDiff` to regenerate the diff from the current working directory contents, and then feeds the *old* selection object (with its absolute indices) into `formatPatch` against this *new* diff: [2](#0-1) 

`formatPatch` walks the (potentially different) hunks and simply maps `hunk.unifiedDiffStart + lineIndex` back onto the caller-supplied selection, with no verification that the line at that index still represents the same logical change the user reviewed and checked: [3](#0-2) 

The resulting patch is then applied with `git apply --cached --unidiff-zero`, i.e. **zero context lines**, which removes the one safety net (context-line matching) that could otherwise cause `git apply` to fail loudly if the file had shifted: [4](#0-3) 

The application itself acknowledges this gap in a different code path that reconciles diff and selection after a reload — but explicitly limits the fix to only removing indices for lines that no longer exist, not to verifying that surviving indices still map to equivalent content: [5](#0-4) 

This is the direct analog of the reported vulnerability's broken invariant: exactly as `min_amount_out` is checked against a value the caller decided on earlier without re-validating it against current vault state (and without enforcing the state-refresh instruction), Desktop's partial-commit selection is applied against a re-fetched diff without re-validating that the selection still corresponds to the same content, and without any mechanism (equivalent to `CrankVaultUpdateStateTracker`) that forces the selection to be recomputed from the current state before being trusted.

### Impact Explanation
If the working-directory file changes between the moment the user reviews/selects diff lines in the Changes view and the moment "Commit" actually executes `applyPatchToIndex` — for example due to a file watcher, build tool, linter/formatter, or git hook shipped inside a cloned/fetched malicious repository (e.g. a `post-checkout` hook, an npm `postinstall` script, or an editor task auto-triggered on file open) that rewrites tracked files shortly after the repo is opened — the stale absolute-index selection can silently map onto different hunk content in the freshly recomputed diff. Because `--unidiff-zero` provides no context lines to detect the mismatch, `git apply --cached` can succeed while staging/committing content the user never reviewed or intended to include, i.e. silent corruption of what the user commits (and subsequently pushes). This can be used by a malicious repository to smuggle unreviewed lines into a legitimate-looking partial commit.

### Likelihood Explanation
Exploitation requires only that the victim clone/open an attacker-controlled repository and use Desktop's normal partial-staging workflow (select some lines, then commit) while some repo-provided automation (hook/task/watcher) mutates the file in the narrow window between diff-load and commit-apply. No local/admin access, no leaked credentials, and no unnatural user steps beyond ordinary "clone repo → review diff → commit" usage are required, which is within Desktop's normal trust boundary for untrusted repositories.

### Recommendation
`applyPatchToIndex` (and `discardChangesFromSelection`) should not silently re-fetch and reuse a stale selection against a new diff. Either:
- Reuse the exact `ITextDiff` object that was rendered and selected against in the UI (pass it through instead of recomputing), and reject/re-prompt if the file's content hash on disk differs from when the diff was generated; or
- Recompute the diff immediately before applying, and re-validate that the previously selected lines still correspond byte-for-byte to the same hunk content (not just that the index still exists), aborting the partial-apply with a clear error if content has shifted, similar to how `min_amount_out` should be revalidated against current vault state before allowing the burn to proceed.

### Proof of Concept
1. Clone a malicious repository containing a `post-checkout` (or similarly auto-triggered) hook/script that appends or reorders lines in a tracked file a few seconds after checkout.
2. In Desktop, open the repo, select the modified file, and check only specific lines/hunks in the Changes diff view for partial commit.
3. Before clicking "Commit", let the hook/script fire and mutate the file's on-disk content (shifting hunk boundaries).
4. Click "Commit". `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` [6](#0-5)  and applies the old absolute-index selection to the new hunk layout via `formatPatch` [7](#0-6) , using `--unidiff-zero` (no context) [4](#0-3) .
5. Inspect the resulting commit: it can contain different/additional lines than what was visually checked in the UI, demonstrating silent corruption of the committed content.
