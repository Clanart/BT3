### Title
Joining/switching a pool after earning self-farmed rewards forwards those pre-existing unclaimed rewards to the new pool instead of the user - (File: chia/wallet/plotnft_wallet/plotnft_wallet.py)

### Summary
`PlotNFT2Wallet` tracks all pool-reward coins (both self-farmed and pool-farmed) in a single, undifferentiated table (`pool_reward2s`) keyed only by `singleton_id`, with no record of which `PoolConfig`/pool destination was active when each reward accrued. The only way to redeem a reward once the PlotNFT is in the `pooling` state is `forward_pool_reward()`, which always sends the reward to whatever pool puzzle hash is *currently* configured on the PlotNFT, not to the configuration that existed when the reward was earned. This mirrors the reported Aave/Morpho bug class: switching the "manager" that resolves reward destinations (there, the rewards manager contract; here, the plotnft's pool target/config) silently reroutes or strands rewards that accrued under the previous configuration.

### Finding Description
`PlotNFT2Wallet.claim_rewards()` is gated by `if self.pooling: raise ValueError("Cannot claim rewards while pooling...")`, evaluated only against the *current* on-chain `plotnft.pooling` state [1](#0-0) . Meanwhile `PlotNFT.forward_pool_reward()` is only usable `if self.pooling`, and it always builds a solution sending the reward to the puzzle described by the singleton's current pool configuration [2](#0-1) .

The reward tracking store (`pool_reward2s`) records rewards solely by `singleton_id`/`height`/`spent_height`, with no tag for which pool configuration was active at accrual time [3](#0-2) [4](#0-3) . `PlotNFT2Wallet.coin_added()` overwrites the local `target_puzzle_hash` (the "reward manager" analog) every time the on-chain `pool_config` changes, e.g. on join/leave/switch [5](#0-4) .

Consequently, a user who:
1. Self-farms (no pool_config) and accrues reward coins that are rightfully theirs (destined for their own wallet when claimed), then
2. Calls `join_pool()` (setting a new pool_config, analogous to "setting a new rewards manager"),

can no longer call `claim_rewards()` (blocked by the `self.pooling` gate), and the *only* remaining redemption path, `forward_pool_reward()`, sends those pre-existing, rightfully-self-earned reward coins to the newly joined pool's puzzle hash — not back to the user. The project's own test suite documents and accepts this outcome under the comment `# LOSE REWARDS (while pooling)`, confirming this is a real, reachable behavior rather than a hypothetical [6](#0-5) . The same pattern repeats for rewards earned while pooling but still unclaimed when leaving to a different pool (`# LOSE REWARDS (while leaving)`) [7](#0-6) .

This is directly analogous to the reported bug class: a manager/destination-resolving setter (`join_pool`/pool_config change ≈ `setRewardsManager`) is not reconciled against already-accrued-but-unclaimed rewards before being changed, and the only claim path routes exclusively through the *new* configuration, causing prior rewards to be redirected away from their rightful owner.

### Impact Explanation
This is coin redirection: value that a wallet user legitimately earned (self-farmed block rewards, or pool rewards earned under an old pool relationship) is forwarded, via a spend the user themselves must sign/submit, to a puzzle hash controlled by a different, potentially unrelated third-party pool. Because the plotnft owner is the only one who can construct and sign this spend (it requires the owner's synthetic pubkey via `bls_member`/delegated-puzzle machinery in `claim_pool_rewards`/`forward_pool_reward`), the effect is a self-inflicted, silent loss of funds triggered by ordinary wallet actions (`join_pool`) with no explicit warning that older unclaimed rewards will be swept to the new pool. This is a coin-movement / fund-loss issue reachable by any plotnft wallet user, warranting Medium severity, consistent with the classification of the original report.

### Likelihood Explanation
Likelihood is meaningful because the sequence (accrue self-farmed or old-pool rewards → change pool/join a different pool before claiming) is an entirely normal, expected user workflow with plot-NFTs, not an edge case requiring malicious input. The codebase's own test explicitly exercises and accepts this exact scenario, indicating it is a known, reachable condition rather than a theoretical one.

### Recommendation
- Track, per pending `PoolReward`, which `PoolConfig`/target puzzle hash was in effect when it accrued (extend the `pool_reward2s` schema), and require unclaimed rewards to be claimed to the *matching* destination (or via a dedicated "claim stranded reward" path that pays the original owner) before allowing `join_pool`/`leave_pool` to change the active pool target.
- Alternatively, block `join_pool`/pool-switching operations while unclaimed rewards exist that were accrued under a different configuration, analogous to the "settable only once" / "explicit accrual toggle" mitigation discussed for the Aave rewards manager, and surface an explicit warning/error to the user (similar to Morpho's decision to warn before changing reward managers).
- At minimum, document this behavior prominently in `pw_join_pool`/`leave_pool` RPC docs and CLI so users are not surprised that switching pools forwards outstanding rewards to the new pool.

### Proof of Concept
1. Create a `PlotNFT2Wallet` in self-custody (no `pool_config`) and farm/self-farm several blocks so multiple `PoolReward`s accrue to `pool_reward2s` for the plotnft's `singleton_id` (see `coin_added` reward tracking) [8](#0-7) .
2. Before calling `claim_rewards()`, call `join_pool(pool_config=..., pool_url=...)` to switch the plotnft into `FARMING_TO_POOL` state.
3. Attempt `claim_rewards()` — it raises `"Cannot claim rewards while pooling..."` [9](#0-8) .
4. Call `PlotNFT.forward_pool_reward()` on the pre-existing (pre-join) reward coins — the resulting spend sends them to the new pool's puzzle hash rather than back to the user, exactly as demonstrated in the existing test's `# LOSE REWARDS (while pooling)` section [6](#0-5) .

    async def get_pool_rewards(
        self,
        *,
        plotnft_id: bytes32,
        max: int = DEFAULT_POOL_REWARDS_PER_CLAIM,
        include_spent: bool = False,
    ) -> list[PoolReward]:
        async with self.db_wrapper.reader() as conn:
            rows = await conn.execute_fetchall(
                (
                    "SELECT * from pool_reward2s WHERE singleton_id = ?"
                    + (" AND spent_height IS NULL" if not include_spent else "")
                    + " ORDER BY spent_height ASC LIMIT ?"
                ),
                (plotnft_id, max),
            )
            pool_rewards_selected = [
                PoolReward(
                    coin=Coin(
                        parent_coin_info=bytes32(row[1]), puzzle_hash=bytes32(row[2]), amount=uint64.from_bytes(row[3])
                    ),
                    singleton_id=bytes32(row[4]),
                )
                for row in rows
            ]
            return pool_rewards_selected
