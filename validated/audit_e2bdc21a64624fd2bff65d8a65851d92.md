## Analysis

The Astaria report's core broken invariant is: a narrow, local check (`L0k < A0k`) is substituted for the true aggregate invariant that must hold across all elements of a stack (`o_new + oⱼ ≤ Lⱼ` for every `j`), so an operation on one element silently violates guarantees that depend on the state of *other* elements sharing the same resource.

The same pattern exists in the Intent Gateway's same-chain partial-fill escrow release logic.

### Finding Description

`IntrinsicIntents::_fillSameChain` computes, for each output index `i`, how much escrow to release for the corresponding `order.inputs[i]`: [1](#0-0) 

When the output leg at index `i` is *not yet* fully satisfied, the release is correctly computed proportionally: `(order.inputs[i].amount * fillAmount) / totalRequired`. But when the fill completes that leg (`amountFilled == totalRequired`), the code switches to releasing the **entire remaining balance stored under that token address** in `_orders[commitment][token]`:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
}
```

`_orders` is keyed only by `(commitment, token address)` — not by input index: [2](#0-1) 

If an order's `inputs[]` array contains the **same token address at two or more indices** (e.g. `inputs[0].token == inputs[1].token == USDC`, with different amounts backing two independent output legs), then `_orders[commitment][USDC]` holds the *sum* of both legs' escrow. Completing just one of those output legs causes the "amountFilled == totalRequired" branch to release the **full aggregate balance for that token**, including the escrow that is still meant to back the *other*, unfilled leg.

`_withdraw` then simply decrements and transfers whatever amount it is told, with only a `== 0` guard, not a per-leg accounting check: [3](#0-2) 

This is exactly the Astaria pattern: the invariant "escrow released for leg `i` must never exceed leg `i`'s proportional share" is enforced only in the partial-fill branch, but is silently replaced by "release everything left for this token" in the completion branch — a narrower/wrong local check standing in for the aggregate invariant that must hold across all legs of the order.

### Impact Explanation

A solver who fills only the *cheapest* output leg of a multi-leg order can be paid the escrow backing *all* legs sharing that input token, i.e., far more than the proportional amount owed for the output they actually delivered. This is direct fund loss for the order's user (their escrow, meant to be split across independent legs, is paid out entirely to whichever solver completes the smallest leg first) and a windfall for the filling solver — reachable through the fully permissionless, unprivileged `fillOrder` entrypoint with no relayer, prover, or admin involvement. It also risks bricking the order: the remaining unfilled leg(s) can no longer be paid out (their `_orders` balance is now zero), so `_withdraw` will revert with `UnknownOrder()` on any later attempt to complete or cancel them, permanently locking that portion of accounting.

### Likelihood Explanation

Exploitability hinges entirely on whether `placeOrder` allows duplicate token addresses across `order.inputs[]` — I was not able to inspect the `placeOrder`/order-construction code within the available iterations to confirm or rule out a dedup/uniqueness check on input tokens. If no such check exists (which is typical for permissively-encoded order structs, since inputs and outputs are just parallel arrays matched by index), then any order creator (or an order creator colluding with a solver) can construct this layout at zero extra cost, making the attack trivially reachable by an ordinary user/solver pair with no special privileges.

### Recommendation

Track escrow per `(commitment, input index)` rather than per `(commitment, token address)`, or explicitly reject orders whose `inputs[]` contains duplicate token addresses at `placeOrder` time. In `_fillSameChain`, the completion branch should release exactly the leg's own remaining balance (`order.inputs[i].amount - alreadyReleased[i]`), never a token-keyed aggregate that can be shared with other legs.

### Proof of Concept

1. User places a same-chain order with `inputs = [{USDC, 100}, {USDC, 900}]` and `outputs = [{DAI, 100}, {WETH, w}]` — two legs sharing the USDC token address. `_orders[commitment][USDC] = 1000`.
2. A solver calls `fillOrder` supplying `options.outputs = [{DAI, 100}, {WETH, 0}]` — fully satisfying leg 0, providing nothing for leg 1.
3. In the loop, `i = 0`: `alreadyFilled = 0`, `fillAmount = 100`, `amountFilled = 100 = totalRequired` → `escrowedAmount = _orders[commitment][USDC] = 1000` (not the proportional 100).
4. `i = 1`: `solverAmount == 0` and `remaining > 0` → `isFullyFilled = false`, loop `continue`s without touching escrow for leg 1.
5. `_withdraw` transfers the full 1000 USDC to the solver for having delivered only 100 DAI; `_orders[commitment][USDC]` becomes 0.
6. Any later attempt by another solver to complete leg 1 (WETH for the remaining 900 USDC) triggers `_withdraw` → `escrowed == 0` → reverts with `UnknownOrder()`, permanently stranding leg 1.

Note: this PoC assumes `placeOrder` does not reject duplicate `inputs[].token` entries; I was unable to confirm this within the available exploration budget and flag it as the key open verification item for a follow-up review of the order-placement path.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
