### Title
Self-referral bypass in `useCode()` allows an attacker to fabricate referrer/referee rewards using two self-controlled addresses - (File: rewards/ReferralStorage.sol)

### Summary
`useCode()` in `rewards/ReferralStorage.sol` only blocks binding a code to the exact same address that registered it (`codeOwners[_code] == msg.sender`). It does not prevent an attacker who controls two separate addresses from registering a code on address A and calling `useCode` from address B, creating a fake "referral" relationship between two Sybil addresses that are ultimately the same beneficiary.

### Finding Description
`registerCode()` lets any address claim an arbitrary unused `bytes32` code and become its `codeOwners[_code]` owner with a default tier [1](#0-0) . `useCode()` binds a caller to a referrer via that code, with the only anti-self-referral check being an exact-address match: [2](#0-1) 

Because the check is `codeOwners[_code] == msg.sender` and not any broader Sybil/ownership check, an attacker who controls address A and address B can: (1) call `registerCode` from A, (2) call `useCode` from B using A's code. This is accepted since `codeOwners[_code] (A) != msg.sender (B)`.

Once bound, whenever B's rewards are harvested through `masterMagpie`, `trigger(B, amount)` is invoked, which computes both a referrer share (paid to A) and a referee share (paid to B) based on `tiers[tier].rewardPercentage` plus the boosted percentage derived from `totalBoostFactor`/`BoostPoint`: [3](#0-2) 

Both `refererInfo.rewardAmount` (A) and `refereeInfo.rewardAmount` (B) are credited and later claimable via `claimReward()`, which transfers real MGP tokens out of the contract's balance [4](#0-3) . Since the attacker controls both A and B, they collect a bonus (`basic + boosted` percentage of `_amount`) that is supposed to reward genuine third-party recruitment, but is instead paid entirely to the same actor.

Separately, `totalBoostFactor` is only updated for an address that has itself registered a code (`userInfo.myCode != 0`), using `sqrt(vlMGPLockedAmount)` as the per-account factor [5](#0-4) , and `_calBoosted` allocates a fixed pool `BoostPoint` proportionally to `factor / totalBoostFactor` [6](#0-5) . Because `sqrt` is concave, splitting one large lock across N self-controlled, code-registered addresses (`sqrt(x/N) * N > sqrt(x)`) increases the attacker's aggregate share of the fixed `BoostPoint` pool relative to holding one address, diluting genuine referrers' boosted share — this is a real, additional Sybil incentive compounding the self-referral bypass, though it is a separate mechanism from `useCode`'s same-address check and does not itself break `BoostPoint == totalBoostFactor` bookkeeping (that invariant is maintained correctly by `updateTotalFactor`; the exploit is about *unfair proportional capture*, not a broken accounting invariant).

No modifier, `nonReentrant`, or receipt-token accounting prevents this; `HasReferral` only stops a referee from re-binding once already bound, and `Circled` only blocks the exact-same-address case.

### Impact Explanation
An attacker can capture both the referrer and referee shares of the referral reward pool for their own emissions, paid out in real MGP tokens from `ReferralStorage`'s balance via `claimReward()`, without any genuine third-party recruitment. This directly matches "Theft of unclaimed yield" — MGP tokens intended to reward organic referral growth are instead extracted by a single actor operating multiple addresses. Additionally, splitting locked vlMGP across multiple Sybil addresses that each register a code disproportionately increases the attacker's share of the fixed `BoostPoint` pool at the expense of genuine referrers, due to the concavity of the `sqrt` factor calculation.

### Likelihood Explanation
The attack requires no privileged role — only two or more EOAs/contracts the attacker controls, the ability to call `registerCode`, `useCode`, and normal reward-claiming flows through `masterMagpie`/`vlMGP`. It is fully repeatable and scales with capital splitting (more addresses, more Sybil "referrals"), and costs only gas plus the cost of splitting an existing vlMGP lock across addresses.

### Recommendation
Track and reject self-referral across attacker-linked addresses at a policy/off-chain level is not enforceable on-chain; instead, consider requiring stricter binding rules such as a minimum time-lock/cooldown between `registerCode` and `useCode`, capping referral bonus payouts relative to independently-verifiable external activity, or moving to a design where boosted rewards are capped per unique "cluster" rather than per address. At minimum, review whether `trigger()`'s combined referrer+referee payout should be reduced or removed when referrer and referee share the same underlying vlMGP lock history/funding source, though full mitigation of Sybil self-referral is inherently difficult purely on-chain.

### Proof of Concept
1. Deploy `ReferralStorage`, `vlMGP`, and `MasterMagpie` per test harness; fund `ReferralStorage` with MGP for reward payout.
2. From address A: call `registerCode(codeA)`.
3. From address B (attacker-controlled): call `useCode(codeA)` — assert it succeeds (no `Circled` revert) even though A and B are the same beneficiary.
4. Lock vlMGP from both A and B; call `updateTotalFactor` for A (has `myCode` set) so `totalBoostFactor` includes A's factor.
5. Simulate B claiming a reward through `masterMagpie`, triggering `trigger(B, amount)`.
6. Assert `userInfos[A].rewardAmount > 0` and `userInfos[B].rewardAmount` includes the referee bonus, both claimable via `claimReward()` to addresses controlled by the same attacker — i.e., total MGP claimed by the attacker across A+B exceeds what a non-referred single-address claimant of the same base `amount` would receive.
7. (Sybil boost) Split one large vlMGP lock across N addresses, each calling `registerCode` and locking `X/N`; call `updateTotalFactor` for each; assert the sum of `sqrt(X/N)` factors (and thus the attacker's aggregate `_calBoosted` share of `BoostPoint`) exceeds the single-address `sqrt(X)` case, demonstrating disproportionate capture of the shared `BoostPoint` pool.
