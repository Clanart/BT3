## Analysis: Cross-chain value duplication in `x/erc20` IBC OnRecvPacket middleware

### Mapped invariant
Asset-representation path invariant: ICS20 transfer + `x/erc20` conversion must preserve 1:1 accounting — a packet that is acknowledged as "successful" on the receiving chain must not also trigger a refund on the sending chain, and vice versa. This is the direct analog of the SteadeFi bug class: a multi-step action where step 1 (unescrow to recipient) commits, and a later, separate step (ERC20 re-conversion) fails — but instead of the overall operation staying consistent, the *already-delivered* value from step 1 is not rolled back while the failure of step 2 is reported as a total-packet failure.

### Root cause location [1](#0-0) 

```go
func (im IBCMiddleware) OnRecvPacket(...) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer) // (1) underlying ICS20 transfer runs first
	if !ack.Success() {
		return ack
	}
	return im.keeper.OnRecvPacket(ctx, packet, ack) // (2) erc20 conversion runs on the SAME, uncached ctx
}
```

Step (1), `im.Module.OnRecvPacket`, is the standard ICS20 transfer callback. For a token pair that `IsNativeERC20()` (i.e., the ERC20 originated on this chain, was converted to a bank coin, and sent out over IBC — now returning home), this step **unescrows the coin directly to the recipient's bank balance** and returns a *success* acknowledgement. This state change is written against the same `ctx` used for step (2), not a cached/branched context.

Step (2), `k.OnRecvPacket` in [2](#0-1)  then attempts to convert that already-delivered bank coin into the ERC20 representation:

```go
case found && pair.IsNativeERC20():
    ...
    pair, err := k.MintingEnabled(ctx, recipient, coin.Denom)
    if err != nil {
        ...
        return channeltypes.NewErrorAcknowledgement(err)
    }
    if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(recipient.Bytes()), recipient); err != nil {
        return channeltypes.NewErrorAcknowledgement(err)
    }
```

If `MintingEnabled` ( [3](#0-2) ) or `ConvertCoinNativeERC20` fails — e.g. the token pair was disabled, the recipient is a blocked address, `IsSendEnabledCoin` is false, or the ERC20 contract has been self-destructed (explicitly called out as a real failure mode in the module's own comments, see `OnAcknowledgementPacket` doc at [4](#0-3) ) — the function returns `channeltypes.NewErrorAcknowledgement(err)`.

### The inconsistency
* No Go `error` is returned from the packet-handling path; only an acknowledgement *value* signaling failure is produced. Core IBC's `RecvPacket` message handling does not revert state on an error acknowledgement — it commits whatever the branched multistore already contains and simply writes the error ack bytes to the packet-receipt/ack store for relaying back to the sender chain.
* Consequently the bank-coin unescrow performed in step (1) **remains committed** — the recipient keeps the received value (this is explicitly the documented fallback: "the user will receive the bank token instead").
* But the acknowledgement ultimately delivered to the counterparty chain is an **error**. Standard ICS20 `OnAcknowledgementPacket` logic on the sending chain treats an error acknowledgement as "packet failed" and refunds the original sender (unescrows/mints back the amount that was debited/escrowed when the transfer was sent).

Net effect: the same value now exists **twice** — once already delivered to the recipient on the receiving chain (as the fallback bank coin), and once refunded back to the original sender on the sending chain. This is an unauthorized duplication of spendable user value across chains, triggered purely by an ordinary, unprivileged condition (any factor that makes `MintingEnabled`/`ConvertCoinNativeERC20` fail for a "native ERC20 return" packet, such as a self-destructed pair contract, a since-disabled token pair, or a blocked/paused recipient/denom).

This contrasts with the more careful pattern used elsewhere in the codebase for the same class of risk — the general-purpose IBC callback handler explicitly buffers state in a `cachedCtx` and only commits with `writeFn()` after confirming success, e.g. [5](#0-4) , and the "recipient with callback" flow tested in [6](#0-5)  which traps failed-conversion funds in an isolated address rather than leaving an inconsistent ack. The direct (non-callback) `x/erc20` `OnRecvPacket` path for native-ERC20 return packets lacks this safeguard.

### Confidence / gaps
I was not able to view the full body of `ConvertCoinNativeERC20` (only located it in `x/erc20/keeper/msg_server.go`) before running out of tool calls, so I cannot cite the exact burn/mint sequence inside it or confirm with 100% certainty whether it performs any additional rollback internally beyond what's shown. I also could not trace the exact core IBC `04-channel` `RecvPacket` handler in this repo's IBC-go vendor code to confirm definitively that an error-acknowledgement return does not trigger an automatic state revert (this is standard IBC-go behavior across versions, but I did not find and read that exact function in this repository within budget). These are the two points I'd flag as needing direct confirmation before treating this as fully proven, though the existing code comments (`"If conversion fails, then the user will receive the bank token instead"`) strongly corroborate that state is intentionally retained on error-ack in this exact path.

### Title
Cross-chain double-crediting via inconsistent error-acknowledgement after already-committed unescrow in native-ERC20 IBC return path — (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
When a native-ERC20-backed IBC coin returns to its origin chain, the `x/erc20` IBC middleware runs the ICS20 unescrow (crediting the recipient) before attempting ERC20 re-conversion. If re-conversion fails, an error acknowledgement is returned even though the unescrow already committed, causing the sending chain to also refund the original sender — duplicating the transferred value across both chains.

### Finding Description
See analysis above: `im.Module.OnRecvPacket` unescrows coins to the recipient and returns success; `k.OnRecvPacket`'s native-ERC20 branch then may fail and downgrade the ack to an error, without undoing the unescrow, because both calls operate on the same uncached `ctx`.

### Impact Explanation
Meets the Critical bar for "unauthorized minting, burning, duplication ... of spendable user value across native balances ... or token-pair-backed balances" — the same nominal value becomes simultaneously spendable by the recipient (bank coin) and refunded to the sender on the counterparty chain, effectively creating unbacked supply/duplicated claims relative to the original escrow.

### Likelihood Explanation
Trigger conditions (token-pair disabled, blocked recipient, send-disabled denom, or self-destructed ERC20 contract for the pair) are realistic operational states reachable without validator/governance collusion, and the module's own doc comments acknowledge these failure modes occur in practice (e.g., self-destructed contracts).

### Recommendation
Wrap the erc20 conversion step in a cached context (`ctx.CacheContext()`), and only call `writeFn()` (committing the unescrow/mint/burn effects) when both the underlying transfer callback and the ERC20 conversion succeed; otherwise, discard the cached mutations so that a failing conversion results in a true no-op state on the receiving chain matching the error acknowledgement returned to the sender, consistent with the pattern already used in `x/ibc/callbacks/keeper/keeper.go`.

### Proof of Concept
Conceptual (not fully executed due to tool budget): register a native-ERC20 token pair, send it out over IBC to chain B, then trigger a return transfer while the pair is disabled (or the ERC20 contract self-destructed) on chain A so that `MintingEnabled`/`ConvertCoinNativeERC20` fails inside `x/erc20/keeper/ibc_callbacks.go`'s `OnRecvPacket`. Observe: (1) chain A's recipient balance already reflects the unescrowed bank coin (confirmed by the existing test pattern at [7](#0-6)  for the callback variant), and (2) the packet's final acknowledgement is `NewErrorAcknowledgement`, which chain B's `OnAcknowledgementPacket` would process as a failure and refund the sender — yielding two live copies of the transferred value.

func (k Keeper) MintingEnabled(
	ctx sdk.Context,
	receiver sdk.AccAddress,
	token string,
) (types.TokenPair, error) {
	if !k.IsERC20Enabled(ctx) {
		return types.TokenPair{}, errorsmod.Wrap(
			types.ErrERC20Disabled, "module is currently disabled by governance",
		)
	}

	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	if !pair.Enabled {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrERC20TokenPairDisabled, "minting token '%s' is not enabled by governance", token,
		)
	}

	if k.bankKeeper.BlockedAddr(receiver.Bytes()) {
		return types.TokenPair{}, errorsmod.Wrapf(
			errortypes.ErrUnauthorized, "%s is not allowed to receive transactions", receiver,
		)
	}

	// NOTE: ignore amount as only denom is checked on IsSendEnabledCoin
	coin := sdk.Coin{Denom: pair.Denom}

	// check if minting to a recipient address other than the sender is enabled
	// for for the given coin denom
	if !k.bankKeeper.IsSendEnabledCoin(ctx, coin) {
		return types.TokenPair{}, errorsmod.Wrapf(
			banktypes.ErrSendDisabled, "minting '%s' coins to an external address is currently disabled", token,
		)
	}

	return pair, nil
