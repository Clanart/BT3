Based on my investigation, I found a concrete analog in how GitHub Desktop handles the `filepath` parameter from `x-github-client://openRepo/...` deep links.

### Title
Path Traversal via unsanitized `filepath` query parameter in `x-github-client://openRepo` deep link - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` extracts `filepath` from an attacker-controlled deep-link URL and passes it through unsanitized as part of `IOpenRepositoryFromURLAction`, unlike the `branch` parameter which is validated with `testForInvalidChars`.

### Finding Description
In `parseAppURL`, the `openrepo` action parses several query parameters: `pr`, `branch`, and `filepath`. [1](#0-0) 

Notice that `pr` is validated against `/^\d+$/`, and `branch` is validated with `testForInvalidChars`, but `filepath` receives no validation whatsoever before being placed into the returned action object: [2](#0-1) 

The `IOpenRepositoryFromURLAction.filepath` is explicitly documented as "the file to open after cloning the repository": [3](#0-2) 

This is the exact broken invariant that maps to the Rails `actionpack-page_caching` bug: a URL-derived path component (there, the cache path; here, the post-clone file to open) is not checked for traversal segments (`../`) or absolute-path escapes before being used to construct a filesystem path. Elsewhere in the codebase the project is clearly aware of this exact class of bug and has hardened against it in the clone-destination path (`sanitizeCloneName` in `app/src/lib/remote-parsing.ts`, `isClonePathSensitive` in `app/src/lib/git/clone.ts`) and for file writes originating from Copilot conflict resolution (which uses `resolveWithin` before writing): [4](#0-3) 

However, no equivalent `resolveWithin`-style containment check exists for `filepath` from the `openRepo` deep link.

### Impact Explanation
If the `filepath` value ultimately reaches a `Path.join(repository.path, filepath)` + open-in-editor/open-with-default-application call path (the same pattern used throughout the codebase, e.g. `onOpenInExternalEditor` in `app/src/ui/app.tsx`, `revealInFileManager` in `app/src/lib/app-shell.ts`, and `onOpenItem` in `app/src/ui/changes/sidebar.tsx`), a crafted deep link such as `x-github-client://openRepo/owner/repo?filepath=..%2F..%2F..%2F.ssh%2Fid_rsa` could cause Desktop to open, reveal, or read a file outside of the intended cloned repository directory, potentially exfiltrating sensitive files (SSH keys, credentials, config files) merely by having the user click a malicious link — matching the "attacker controls...a link or deep link the user clicks" impact criteria.

### Likelihood Explanation
I was **not able to fully verify** the sink that ultimately consumes `action.filepath` after `open-repository-from-url` is dispatched — `grep_search` located `filepath` references in `app/src/ui/dispatcher/dispatcher.ts` but I was unable to confirm within the available tool budget whether the dispatcher joins this value with the repository path unsanitized, opens it directly, or passes it only to a UI-only "select this file in the Changes list" flow (which would be lower-severity, limited to file selection rather than an fs read/open). This is a significant gap: the vulnerability's presence depends entirely on how the dispatcher/`open-repository-from-url` handler consumes `filepath`, which the index did not surface for me.

### Recommendation
Regardless of the exact sink, `filepath` should be treated with the same rigor as `branch`: validate it rejects `..` segments and absolute paths, or pass it through `resolveWithin(repository.path, filepath)` (already implemented in `app/src/lib/path.ts`) before it is used to construct any filesystem path, consistent with the mitigation already applied to Copilot conflict resolution writes.

### Proof of Concept
Because I could not confirm the exact consuming code path for `filepath` in the dispatcher within this session, I cannot provide a fully verified end-to-end PoC. The suspected PoC vector is:
1. Attacker hosts a link: `x-github-client://openRepo/owner/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. User has GitHub Desktop registered as the protocol handler and clicks the link.
3. `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'owner/repo', filepath: '../../../../.ssh/id_rsa', ... }` with `filepath` unsanitized.
4. If the dispatcher's post-clone "open file" logic joins this with the cloned repo path without calling `resolveWithin`, the traversal segments would resolve outside the repo.

**Given the unresolved uncertainty about the actual sink**, I recommend this be flagged for follow-up investigation into `app/src/ui/dispatcher/dispatcher.ts`'s handling of `open-repository-from-url` and its `filepath` field before treating this as a confirmed, exploitable finding rather than a strong candidate based on local code evidence.

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {

      }

      // we also expect the branch for a forked PR to be a given ref format

      }

      return unknown
    }

    }
