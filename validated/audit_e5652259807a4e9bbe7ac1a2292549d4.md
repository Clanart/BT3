The xToken incident class is "trusted external input / counterfeit value accepted as authentic." The strongest Serai analog candidate is the forwarded-output flow keyed by `output.balance()`. Let me check `ForwardedOutputDb` and the forward-registration path.### Title
Forwarded-output instruction replay via corrupted DB entry allows duplicate `InInstruction` emission from a single deposit - ([File: processor/src/multisigs/db.rs](processor/src/multisigs/db.rs))

### Summary
`ForwardedOutputDb::take_forwarded_output` pops one `InInstructionWithBalance` from a FIFO queue keyed by `ExternalBalance` (coin + amount), but writes back the *entire original buffer* (`&outputs`) instead of the remainder (`outputs_ref`). The consumed instruction is therefore never removed, and every subsequent scanned `Forwarded` output with the same amount re-emits the same `InInstruction`. Because `Forwarded`-kind outputs can be created by any unprivileged Bitcoin sender paying to the publicly derivable forward address, this is reachable entirely with attacker-crafted on-chain data — the analog of the xToken "counterfeit asset accepted as authentic / oracle keyed on an untrusted value" bug class.

### Finding Description
`ForwardedOutputDb` is keyed only on `ExternalBalance` [1](#0-0) . During `ForwardFromExisting`, a scanned External output's `InInstruction` is saved under the post-fee balance it will be forwarded with [2](#0-1) . Later, any output scanned with `OutputType::Forwarded` triggers `take_forwarded_output(txn, output.balance())` and the returned instruction is pushed as a real instruction [3](#0-2) .

The pop logic decodes one instruction off the front, asserts progress, then stores the wrong slice back [4](#0-3) :

```rust
let outputs = Self::get(txn, balance)?;
let mut outputs_ref = outputs.as_slice();
let res = InInstructionWithBalance::decode(&mut outputs_ref).unwrap();
assert!(outputs_ref.len() < outputs.len());
if outputs_ref.is_empty() {
  txn.del(Self::key(balance));
} else {
  Self::set(txn, balance, &outputs); // BUG: stores the full original buffer, not outputs_ref
}
```

When the queue held more than one instruction, the consumed head is rewritten along with the tail, so the same instruction is returned again for the next `Forwarded` output of that amount — an unbounded replay so long as matching-amount outputs keep arriving.

### Impact Explanation
Each replayed `InInstructionWithBalance` is pushed into `instructions` and treated as a freshly arrived deposit instruction for the new multisig. An attacker can therefore cause the *same* depositor instruction to be emitted N times by sending N `Forwarded`-kind outputs of the matching amount in a single Bitcoin transaction (one tx can carry multiple vouts; `scan_transaction` iterates all outputs [5](#0-4) ). Unless downstream Serai logic deduplicates identical instructions (no such dedup exists at this layer), each replay is an unauthenticated mint/instruction — counterfeit crediting analogous to the xToken incident — plus instruction/queue desynchronization where the wrong instruction gets paired to a real forwarded output, permanently dropping a legitimate depositor's instruction while their coins sit uncredited in the multisig.

### Likelihood Explanation
The forward address is publicly computable: `forward_address(key) = key + G * hash_to_F("Serai Bitcoin Output Offset", "forward")` [6](#0-5) [7](#0-6) . An attacker only needs to know the group key and observe the mempool/chain to learn pending forwarded amounts (the balance is the DB key and equals the forwarded output's value, publicly visible once the forward tx is broadcast). Exploitation requires only a standard Bitcoin transaction during the ~6-hour `ForwardFromExisting` rotation window — no collusion, no invalid curve points, no validator misbehavior.

### Recommendation
Store the remaining slice, not the original buffer:

```rust
Self::set(txn, balance, outputs_ref);
```

(or `&outputs[outputs.len() - outputs_ref.len() ..]`). Additionally, key forwarded-output instructions by output `id`/outpoint (or a hash of the stored instruction) rather than `ExternalBalance` alone, and/or bind the expected forwarded output to the `Plan`'s registered `Eventuality` so only the multisig's own forwarding transaction can satisfy it — preventing any third party from creating "counterfeit" `Forwarded` outputs that consume queued instructions.

### Proof of Concept
1. Rotation reaches `ForwardFromExisting`; victim deposits `V` sats to the old multisig. The processor saves `instruction` under `ForwardedOutputDb` key `ExternalBalance { coin: Bitcoin, amount: V - fee }` (two queued instructions share the key, or one suffices to show replay ordering corruption).
2. Attacker watches for the forwarding plan, computes `forward_address(new_group_key)`, and broadcasts a tx with **two** outputs of exactly `V - fee` sats to that script.
3. `Bitcoin::get_outputs` scans both as `OutputType::Forwarded` [8](#0-7) .
4. First `take_forwarded_output` returns instruction #1 and, because `Self::set(txn, balance, &outputs)` rewrites the full buffer, instruction #1 remains at the head of the queue.
5. Second `take_forwarded_output` decodes instruction #1 again — the same `InInstructionWithBalance` is emitted twice; the tail instruction #2 (a different depositor's) is only reachable after another replay, pairing it to whatever output arrives then or dropping it entirely.
6. Result: duplicate emission of a depositor instruction and permanent loss/misattribution of other queued forwarded instructions, caused solely by attacker-published on-chain data.
