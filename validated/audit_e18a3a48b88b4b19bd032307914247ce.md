### Title
Recursive Clone Disables Git's Submodule Protocol Protection (`GIT_CLONE_PROTECTION_ACTIVE: 'false'`) - ([File: app/src/lib/git/clone.ts])

### Summary
The external report's broken invariant is "anyone can control a resource (a vault) and users trust it implicitly without verification, giving the controller a path to abuse the depositor." The Desktop analog is: anyone can author/publish a Git repository (the untrusted object a user chooses to clone), and Desktop's `clone()` helper unconditionally weakens Git's own submodule-protocol safety check for every clone it performs, trusting the repository's `.gitmodules` content without restriction.

### Finding Description
`clone()` in [1](#0-0)  always passes `--recursive` and explicitly sets:
```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```
for the `git clone` invocation, with no way to opt out per-repository. This environment variable corresponds to the guard Git itself introduced (alongside `protocol.file.allow`/submodule protocol allow-listing) after CVE-2022-39253, whose purpose is to prevent an untrusted repository's `.gitmodules` from silently causing local (`file://`) or otherwise unsafe-protocol submodules to be fetched during a recursive clone. By forcing this protection flag to `'false'` for every clone, Desktop deliberately turns off the very check that stops a malicious repository from directing Git to pull in content from arbitrary local paths on the victim's machine as a "submodule."

The app additionally passes `-c protocol.file.allow=always` explicitly in `updateSubmodulesAfterOperation` (used after `checkout`/`pull`) in [2](#0-1) , but that call is gated by an `allowFileProtocol` boolean that defaults to `false` in `checkoutBranch`/`checkoutCommit` ( [3](#0-2) ). The initial `clone()` path has no such gate at all — the protection is disabled unconditionally for the very first, most attacker-controlled step (cloning a repository the user just discovered, e.g. via a deep link or GitHub API-provided clone URL).

There is a partial mitigation for destination-path traversal (`isClonePathSensitive`, [4](#0-3) ), but that only checks the top-level clone *destination* directory chosen by the user/UI — it does nothing to constrain what a malicious `.gitmodules` inside the cloned repository can reference as a submodule source once `GIT_CLONE_PROTECTION_ACTIVE` is off.

### Impact Explanation
An attacker who controls a repository that a user clones through Desktop (via `Clone repository` dialog, a `x-github-client://openRepo` deep link, or `--cli-clone`, all funneled into `clone()`) can embed a `.gitmodules` file that references a submodule via `file://` (or another otherwise-restricted) URL pointing at a local, unrelated path on the victim's disk (e.g. another checked-out repository, an SSH config directory, etc., subject to normal filesystem permissions). Because `--recursive` is always passed and Git's file-protocol protection is force-disabled, that local content gets copied into the newly cloned working directory without any prompt. This is a "silent corruption of what the user commits/pushes" outcome: the user may then unknowingly `git add`/commit/push files sourced from unrelated local repositories, exfiltrating their contents to the attacker's remote once pushed, or introducing unexpected files that a build/hook step in the *cloned* repo could act on.

### Likelihood Explanation
Likelihood is high for the trigger condition (any public/malicious repo the user clones satisfies "attacker controls a cloned/fetched repository"), but impact is bounded by normal OS file permissions (no privilege escalation) and requires the user to subsequently commit/push the resulting working tree changes for exfiltration to complete, or requires a same-filesystem local target for hardlink/copy content to matter. It is a genuine regression of an upstream Git security fix rather than a theoretical concern, since the disabling flag is hardcoded and unconditional.

### Recommendation
Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`, or restrict it to a narrow, deliberately-opted-in scenario (e.g., "clone again" of a known-good repository the user already trusts). Do not pass `--recursive` blindly; instead, perform the initial clone without submodule recursion, then run `git submodule update --init --recursive` through the existing `updateSubmodulesAfterOperation` path where `allowFileProtocol` is already deliberately gated to `false` by default. This restores parity between the initial-clone code path and the checkout/pull code paths, which already treat file-protocol submodules as untrusted by default.

### Proof of Concept
1. Attacker publishes a public GitHub repository containing a `.gitmodules` entry such as:
   ```
   [submodule "leak"]
     path = leak
     url = file:///home/victim/some-other-project
   ```
2. Victim clones this repository in GitHub Desktop (via UI, deep link, or `--cli-clone`), which calls `clone()` in [5](#0-4) .
3. Because `--recursive` is set and `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, Git clones `file:///home/victim/some-other-project` into the `leak/` directory without any warning, even though upstream Git's protections were specifically designed to block this by default for untrusted repositories.
4. The victim now has unrelated local repository content materialized inside the cloned working tree and may commit/push it, or the attacker's repo can otherwise reference/read the copied files on subsequent operations.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
