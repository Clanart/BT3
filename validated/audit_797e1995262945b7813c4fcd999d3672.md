### Title
Denial of Service via Unbounded Python Recursion in Wallet Outer-Puzzle Driver Matching (`match_puzzle`) - (File: chia/wallet/outer_puzzles.py)

### Summary
`chia.wallet.outer_puzzles.match_puzzle()` and the per-layer `OuterPuzzle.match()` implementations (CAT, singleton, metadata, ownership, credential-restricted/CR) recursively call each other once per curried puzzle layer, with no maximum-depth check. A wallet user who loads an attacker-crafted offer (or otherwise inspects an attacker-supplied puzzle reveal) causes one Python stack frame per nested layer. A puzzle reveal with a few thousand nested layers (e.g. `CAT(CAT(CAT(...ACS...)))`) exhausts the Python recursion limit and crashes the wallet process with an uncaught `RecursionError`, mirroring the unbounded-recursion crash pattern described in the go-attestation `readELAMAggregation` advisory (CVE-2026-19201), but here the recursive "sub-event" is a curried CLVM puzzle layer instead of a Windows event-log sub-record.

### Finding Description
`match_puzzle()` iterates all registered drivers and calls `driver.match(puzzle)`: [1](#0-0) 

Each driver's `match()` uncurries the puzzle, extracts an `inner_puzzle`, and then calls `self._match(UnknownPuzzle(known_program=inner_puzzle))`, which is bound back to the top-level `match_puzzle` function (see `function_args = (match_puzzle, ...)` and `driver_lookup` wiring): [2](#0-1) 

This recursive call pattern appears identically in every outer-puzzle driver, e.g. `CATOuterPuzzle.match`: [3](#0-2) 

`SingletonOuterPuzzle.match`: [4](#0-3) 

`OwnershipOuterPuzzle.match`, `MetadataOuterPuzzle.match`, and `CROuterPuzzle.match` all follow the same self-recursive `self._match(...)` pattern: [5](#0-4) [6](#0-5) [7](#0-6) 

None of these functions enforce a maximum nesting depth or layer count, unlike other recursive tree-walking code in the same codebase (e.g. `chia/data_layer/data_store.py`'s Merkle tree code, which explicitly relies on `chia_rs.datalayer.RecursionDepthExceededError` to bound recursion depth, and `chia/types/blockchain_format/tree_hash.py`, whose docstring explicitly states it is implemented "non-recursive so we don't have to worry about blowing out the python stack").

The attacker-reachable entry point is offer processing. `Offer.from_spend_bundle()` (invoked transitively by `Offer.from_bytes()`, `Offer.from_bech32()`, and `Offer.try_offer_decompression()`) calls `match_puzzle()` directly on every `coin_spend.puzzle_reveal` in an untrusted spend bundle supplied by an offer counterparty: [8](#0-7) 

The same call also occurs when scanning offered coins (`_get_offered_coins`): [9](#0-8) 

A wallet user who receives an offer file/bech32 string from a counterparty and inspects it (`chia wallet take_offer`, `get_offer_summary`, `respond_to_offer` RPC calls, or the `GetOffer`/`GetAllOffers` RPC endpoints which call `Offer.from_bytes` on stored offer bytes) will trigger this recursive matching against attacker-controlled CLVM data before the offer is otherwise validated against consensus rules.

### Impact Explanation
By constructing an offer whose settlement coin spend uses a puzzle reveal with thousands of nested CAT/singleton/ownership/metadata/CR curry layers, a malicious offer counterparty can force the recipient's wallet process to hit Python's recursion limit and raise an uncaught `RecursionError` while simply examining or attempting to take the offer. This halts wallet transaction processing (a spend/offer-triggered processing halt), matching the "Medium" severity DoS class of the reference report: an untrusted, attacker-supplied nested structure drives unbounded recursion in application code with no depth guard, crashing the process handling it.

### Likelihood Explanation
Constructing an offer with a deeply layered puzzle reveal requires no special privileges — any user can build an `Offer`/`WalletSpendBundle` with an arbitrarily curried dummy puzzle and share it as a normal offer file/bech32 string, which is a routine, expected interaction pattern (offers are explicitly designed to be exchanged with untrusted counterparties before being accepted on-chain).

### Recommendation
Add an explicit recursion/nesting-depth limit to `match_puzzle()` and each `OuterPuzzle.match()` implementation (CAT, singleton, ownership, metadata, CR), returning `None`/raising a controlled `ValueError` once a maximum layer count is exceeded, analogous to the `RecursionDepthExceededError` guard already used in `chia/data_layer/data_store.py`. Alternatively, convert the recursive matching walk into an iterative loop that threads layer-construction dictionaries on an explicit stack, mirroring the non-recursive design already used in `chia/types/blockchain_format/tree_hash.py`.

### Proof of Concept
1. Build a CLVM puzzle `P0 = ACS` (accept-everything puzzle).
2. Iteratively wrap it N times (N ≈ 2000–5000) using `construct_cat_puzzle(CAT_MOD, tail, P_i)` (or alternate CAT/singleton/ownership layers) to produce `P_N`.
3. Create a dummy `CoinSpend` with `puzzle_reveal = P_N` and package it into a `WalletSpendBundle`, then build an `Offer` via `Offer.from_spend_bundle(bundle)` or serialize with `Offer(...).to_bech32()`.
4. Send the resulting offer bech32 string to a victim wallet and have it call `Offer.from_bech32(offer_str)` (e.g. via `chia wallet take_offer` or the `get_offer`/`respond_to_offer` RPC).
5. Observe that `match_puzzle()` recurses once per layer through `CATOuterPuzzle.match` → `self._match` → `match_puzzle` → ..., exceeding Python's default recursion limit and raising an unhandled `RecursionError`, terminating offer processing (and, depending on the calling context, the wallet RPC worker/process).
