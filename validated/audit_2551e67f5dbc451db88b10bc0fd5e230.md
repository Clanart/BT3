### Title
Unchecked u64 arithmetic on untrusted payment amounts can overflow, panicking or bypassing the not-enough-funds check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The analog of the USSD finding — multiplication/addition of untrusted magnitudes without overflow guards — exists in `SignableTransaction::new` and `SignableTransaction::fee`. The code sums caller-supplied `u64` payment amounts and input values with `sum::<u64>()` and adds `payment_sat + needed_fee` using plain operators, and multiplies `fee_per_vbyte * vbytes` without checked math, while the change-output path a few lines later correctly uses `checked_sub` — showing the overflow hazard was recognized but only guarded in one branch [1](#0-0) .

### Finding Description
Three sites perform unchecked arithmetic on values an unprivileged party can influence:

1. `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` — `payment.1` values are arbitrary `u64`s in the transaction data fed to the signing path; two payments ≥ `u64::MAX/2 + 1` overflow the sum (each individually only needs to pass the `DUST` check at lines 165–169) [2](#0-1) .
2. `if input_sat < (payment_sat + needed_fee)` — addition can overflow independently of the sum [3](#0-2) .
3. `let mut needed_fee = fee_per_vbyte * vbytes;` — multiplication overflow on an externally-derived fee rate [4](#0-3) .
4. `fee()` subtracts `sum(outputs)` from `sum(inputs)` with a plain `-`, underflowing if a mis-assembled tx is ever queried [5](#0-4) .

On overflow, in debug/`overflow-checks` builds this panics, aborting transaction construction (DoS of the signing flow). With wrapping arithmetic, `payment_sat + needed_fee` wraps to a small value, so the `NotEnoughFunds` check passes and a `SignableTransaction` containing absurd `Amount::from_sat` outputs is returned and handed to FROST signing — producing signatures over a transaction that is invalid on chain (outputs exceed 21M BTC consensus limit), so the intended payment never executes while inputs remain earmarked.

### Impact Explanation
Either a panic crashing the transaction-building path (denial of service, analogous to the USSD revert-DoS), or a wrapped sum that defeats the solvency check and causes the multisig to sign an invalid transaction — the protocol commits signatures and scheduler state (offsets recorded in `SignableTransaction`) to a spend that can never confirm, stalling the affected payments.

### Likelihood Explanation
Requires a payment amount large enough to overflow u64, which presumes amounts near 1.8e19 sats are ever admitted into `payments`; within `networks/bitcoin` itself no bound tighter than `>= DUST` is enforced, so the library-level invariant is unguarded. The `fee_per_vbyte * vbytes` overflow additionally needs an extreme fee rate. Severity is therefore Medium: reachable arithmetic-unsafety of the same class as the report, but conditional on upstream amount validation.

### Recommendation
Mirror the `checked_sub` already used for change across the whole function: accumulate `input_sat`/`payment_sat` with `try_fold`/`checked_add`, compute `fee_per_vbyte.checked_mul(vbytes)`, and compare via `input_sat.checked_sub(payment_sat + needed_fee)`. Alternatively bound each `payment.1` to the Bitcoin `MAX_MONEY` range (21e15 sats) at entry, which makes the sums provably safe.
