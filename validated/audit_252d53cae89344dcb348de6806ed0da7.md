## Finding: Platform-dependent `uint` type for AccountKey multisig `Threshold`/`Weight` causes overflow-detection and consensus divergence between 32-bit and 64-bit nodes

### Title
Weighted-MultiSig AccountKey overflow detection depends on platform int-width (`uint`), enabling state divergence across node architectures - (File: `blockchain/types/accountkey/account_key_weighted_multi_sig.go`)

### Summary
The `AccountKeyWeightedMultiSig` type stores `Threshold` and each `WeightedPublicKey.Weight` as Go's platform-dependent `uint` type instead of a fixed-width type like `uint64`. Overflow protection in `CheckInstallable` relies on wraparound behavior of this same platform-dependent type, so the exact point at which "weighted sum overflow" is detected differs depending on whether the node binary is compiled for a 32-bit or 64-bit architecture. This mirrors the original Monero `round_money_up` bug class, where overflow detection based on `ULONG_MAX` differed from `ULLONG_MAX` on 32-bit systems.

### Finding Description
`AccountKeyWeightedMultiSig` is defined with platform-width integers: [1](#0-0) 

Overflow detection in `CheckInstallable` sums up weights and checks for wraparound only within the bit-width of `uint`: [2](#0-1) 

`Validate`, used during transaction signature verification, also accumulates weights in a platform-dependent `uint`: [3](#0-2) 

Since Go's `uint` is 32 bits on 32-bit architectures and 64 bits on 64-bit architectures, the wraparound boundary for `sum` differs: 2^32 vs 2^64. A test in the codebase explicitly acknowledges this architecture dependence: [4](#0-3) 

An attacker (any transaction sender performing an `AccountUpdate`/account-creation with an `AccountKeyWeightedMultiSig`) can craft `Threshold`/`Weight` values that sum to just above 2^32-1 but well below 2^64-1 (e.g., three weights near `0xFFFFFFFF/... ` summing to ~2^32+k). On a 64-bit node, `sum` is computed in 64-bit arithmetic and no wraparound occurs, so `CheckInstallable`/`Validate` behave as if the sum is a large-but-valid (non-overflowed) value. On a 32-bit node, the identical `uint` additions wrap modulo 2^32, producing a different (smaller) `sum`, changing whether `ErrWeightedSumOverflow` is returned in `CheckInstallable`, and whether `Validate` treats the signature threshold as satisfied.

### Impact Explanation
This causes state/consensus divergence between honest nodes running on different CPU architectures (32-bit vs 64-bit builds) for the exact same block/transaction: one class of nodes accepts the `AccountUpdate` transaction / treats a signature set as satisfying the threshold, while the other rejects it or requires a different weighted sum. This can lead to a chain split, or allow signature-threshold bypass on architectures where the wraparound point is reached differently than intended, directly affecting AccountKey authorization security (which gates all future transactions/fee-delegation signed by that account).

### Likelihood Explanation
Reachable purely via a single submitted `AccountUpdate` (or account creation) transaction containing carefully chosen large `Threshold`/`Weight` values in a `AccountKeyWeightedMultiSig`—no privileged access or special network position required. The trigger values are large but still well within the RLP-encodable range for these fields (up to `uint64` max on 64-bit builds), making this practically constructible by any unprivileged sender.

### Recommendation
Change `AccountKeyWeightedMultiSig.Threshold` and `WeightedPublicKey.Weight` (and all sum accumulators in `Validate`/`CheckInstallable`) from Go's platform-dependent `uint` to a fixed-width type (`uint64`), and use explicit fixed-width overflow-safe arithmetic (e.g. the existing `common/math.SafeAdd` helpers) so overflow detection is architecture-independent and consistent across all node builds.

### Proof of Concept
1. Attacker crafts an `AccountKeyWeightedMultiSig` with `Threshold = T` and three `WeightedPublicKey` entries with weights `w1, w2, w3` such that `w1+w2+w3` is slightly greater than `2^32 - 1` (e.g., `w1=w2=w3 = 0x55555556`, sum ≈ `0x100000002`), but the individual weights and threshold fit comfortably in `uint64`.
2. Submit this key via an `AccountUpdate` transaction (`types.TxTypeAccountUpdate`), analogous to the existing test flow at: [5](#0-4) 
3. On a 64-bit node: `sum` (as 64-bit `uint`) does not overflow; `CheckInstallable` succeeds (assuming `sum >= Threshold`), and the account key is installed.
4. On a 32-bit node: identical additions wrap at `2^32`; `prevSum > sum` triggers, so `CheckInstallable` returns `kerrors.ErrWeightedSumOverflow` and the same transaction is rejected.
5. Result: the two node populations diverge on whether this transaction (and subsequent block containing it) is valid, producing a consensus fork purely from CPU-architecture differences.

func (a *AccountKeyWeightedMultiSig) Validate(currentBlockNumber uint64, r RoleType, recoveredKeys []*ecdsa.PublicKey, from common.Address) bool {
	if a.Threshold == 0 {
		return false
	}
	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul

	// Validation 1. if isIstanbul is true, check whether the signature number exceeds key number
	if isIstanbul && len(recoveredKeys) > len(a.Keys) {
		logger.Debug("AccountKeyWeightedMultiSig validation failed and number of signatures exceeds key number",
			"numSigs", len(recoveredKeys), "numKeys", len(a.Keys))
		return false
	}

	numberOfValidAndUniqueSigs := 0
	weightedSum := uint(0)

	// To prohibit making a signature with the same key, make a map.
	// TODO-Kaia: find another way for better performance
	pMap := make(map[string]*ecdsa.PublicKey)
	for _, bk := range recoveredKeys {
		b, err := rlp.EncodeToBytes((*PublicKeySerializable)(bk))
		if err != nil {
			logger.Warn("Failed to encode recovered public keys of the tx", "recoveredKeys", recoveredKeys)
			continue
		}
		pMap[string(b)] = bk
	}

	for _, k := range a.Keys {
		b, err := rlp.EncodeToBytes(k.Key)
		if err != nil {
			logger.Warn("Failed to encode public keys in the account", "AccountKey", a.String())
			continue
		}

		// if the registered key is included in one of the transaction signatures,
		// update weightedSum and validSigNum
		if _, ok := pMap[string(b)]; ok {
			weightedSum += k.Weight
			numberOfValidAndUniqueSigs++
		}
	}

	// Validation 2. if isIstanbul is true, check whether invalid signature exists
	if isIstanbul && numberOfValidAndUniqueSigs < len(pMap) {
		logger.Debug("AccountKeyWeightedMultiSig validation failed and invalid signature exists",
			"numberOfValidSigs", numberOfValidAndUniqueSigs, "numberOfUniqueSigs", len(pMap))
		return false
	}

	// Validation 3. check whether enough signatures are gathered
	if weightedSum < a.Threshold {
		logger.Debug("AccountKeyWeightedMultiSig validation failed and weightedSum is smaller than threshold",
			"recoveredKeys", recoveredKeys, "accountKeys", a.String(), "threshold", a.Threshold, "weighted sum", weightedSum)
		return false
	}

func (a *AccountKeyWeightedMultiSig) CheckInstallable(currentBlockNumber uint64) error {
	sum := uint(0)
	prevSum := uint(0)
	if len(a.Keys) == 0 {
		return kerrors.ErrZeroLength
	}
	if a.Threshold == 0 {
		return kerrors.ErrZeroThreshold
	}
	if uint64(len(a.Keys)) > MaxNumKeysForMultiSig {
		return kerrors.ErrMaxKeysExceed
	}
	keyMap := make(map[string]bool)
	for _, k := range a.Keys {
		// Do not allow zero weight.
		if k.Weight == 0 {
			return kerrors.ErrZeroKeyWeight
		}
		sum += k.Weight

		b, err := rlp.EncodeToBytes(k.Key)
		if err != nil {
			// Do not allow unserializable keys.
			return kerrors.ErrUnserializableKey
		}
		if _, ok := keyMap[string(b)]; ok {
			// Do not allow duplicated keys.
			return kerrors.ErrDuplicatedKey
		}
		keyMap[string(b)] = true

		// Do not allow overflow of weighted sum.
		if prevSum > sum {
			return kerrors.ErrWeightedSumOverflow
		}
		prevSum = sum
	}
