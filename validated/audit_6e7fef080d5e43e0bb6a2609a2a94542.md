## Title
Attacker-controlled conflict content can desynchronize Copilot's per-hunk resolutions from their conflict blocks, causing silent corruption of committed code - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile()` splices the model's per-hunk conflict resolutions back into the original file **by position order, not by any content or identity binding**, using a hand-rolled line scanner that recognizes conflict markers with a regex tolerant of trailing text after `<<<<<<<`/`>>>>>>>`. [1](#0-0) 
Because the conflicted file content comes from a merge/rebase/cherry-pick against a remote branch (attacker-controlled content in a fetched/pulled repository), an attacker who can influence the "theirs" side of a conflict can craft conflict markers or embedded marker-like lines that shift how `reassembleResolvedFile` counts and matches hunks against the model's ordered `hunkResolutions` array, causing the wrong resolved content to be spliced into the wrong location — with no validation that the reassembled content matches what was actually reviewed.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file with conflict markers line-by-line: [2](#0-1) 
It detects a conflict start with `reassemblyOursMarker = /^<{7}(?:\s|$)/`, looks ahead for a `=======` separator and a `>>>>>>>` closer, and if found, replaces the entire block with `hunkResolutions[hunkIndex]` — advancing `hunkIndex` strictly by encounter order. There is no check that the number of conflict blocks found in `rawContent` at reassembly time matches the number of hunks (`hunks.length`) the model was originally shown, nor that the content between blocks is unchanged from what was sent to the model.

The only cross-check that exists, `validateResolutionPaths`, compares the *expected* hunk count (from `IFileConflictContext.hunks.length`, computed when the prompt was built) against the *model's returned* hunk count: [3](#0-2) 
This check validates the model's response against the context gathered *before* the call, but it never re-validates that `ctx.rawContent` — the file's on-disk content used at reassembly time in `reassembleResolutions` — still contains the same number/shape of conflict blocks as when the context was built: [4](#0-3) 

If the working-directory conflict markers change between context-gathering and reassembly (e.g. because the conflicted file itself, sourced from a merge with attacker-influenced "theirs" content, contains a malformed/extra conflict-marker-like sequence that satisfies `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` but wasn't parsed as a discrete hunk when the prompt context was built), `reassembleResolvedFile`'s position-based counter (`hunkIndex`) desyncs from the model's `hunkResolutions` array. Because both counts can still numerically match `validateResolutionPaths`'s check (which only compares totals, not structural alignment) or the discrepancy can be hidden by matching totals coincidentally, resolved content for one conflict can be spliced onto a different, unrelated conflict block — silently corrupting the merged file. The malformed-marker fallback (`hasSeparator`/`closingIndex` check) only handles the case of *no* match found; it does nothing to protect against a *shifted* match caused by markers that are technically well-formed per the local scan but differ from how the original hunk-extraction logic (which builds `IFileConflictContext.hunks`) segmented the file.

Because this reassembled `resolvedContent` becomes the file written to disk and staged for commit without further diffing against what the reviewer actually saw hunk-by-hunk in the resolution dialog (the UI shows the model's `resolvedContent` per hunk, not a live diff of the final reassembled file against the true positions), a user who approves an AI conflict resolution can end up committing/pushing code whose merged content differs from what they intended to accept — this is "silent corruption of what the user commits or pushes," matching the report's core invariant break (a computed value is not correctly delivered/mapped back to its owner).

### Impact Explanation
This does not require local/physical access, admin rights, or leaked credentials — the trigger is purely the content of a conflicted merge/rebase originating from a git remote (a repository or branch under an attacker's control that the victim merges/rebases/cherry-picks against, then invokes Copilot conflict resolution on). If the desync can be reliably induced, the impact is silent corruption of committed source: reintroduction of removed vulnerable code, dropping of a security fix, or splicing of attacker-chosen content into unrelated file locations, all without any error or diff-mismatch signal shown to the user. This satisfies the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitability depends on being able to reliably craft repository content that produces a conflict-marker sequence which is well-formed by `reassembleResolvedFile`'s local three-marker scan, yet is segmented differently than the hunk boundaries used to build the model context (`IFileConflictContext.hunks`) — I was not able to fully trace the hunk-extraction logic (`copilot-conflict-context.ts`, not covered in this investigation) that produces `IFileConflictContext.hunks`, so I cannot confirm with certainty that such a divergence is reachable versus impossible by construction (e.g., if both code paths use the exact same marker regex and are always computed from the same immutable snapshot of `rawContent`). This is the primary source of uncertainty in this analog and would need verification against `copilot-conflict-context.ts` and the full conflict-resolution flow (where `rawContent` is captured and whether it can change between context capture and reassembly, e.g. via concurrent working-directory edits or multi-file/chunked resolution ordering).

### Recommendation
- Re-derive the hunk count/positions from `rawContent` at reassembly time using the exact same extraction logic used to build `IFileConflictContext.hunks`, and assert structural equality (count and, ideally, content hash of each conflict block) before splicing, failing closed (falling back to manual resolution) on any mismatch.
- After reassembly, generate a diff between `ctx.rawContent`'s conflicted regions and the final `resolvedContent`, and surface it in the resolution-approval UI so users are shown exactly what changed relative to the actual file, not just the model's per-hunk text.
- Ensure `rawContent` is captured and used atomically for both context-building and reassembly (no window where on-disk conflict markers can change between the two).

```typescript
export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
```

```typescript
// Conflict markers used by reassembleResolvedFile to locate marker blocks.
const reassemblyOursMarker = /^<{7}(?:\s|$)/
const reassemblySeparatorMarker = /^={7}$/
const reassemblyTheirsMarker = /^>{7}(?:\s|$)/

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
```

```typescript
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
```

```typescript
export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
```
