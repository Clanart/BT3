### Title
Hardcoded Arbitrum chain-id allowlist causes wrong block-number source (and corrupted order deadlines) on new/unlisted Arbitrum Orbit deployments - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._blockNumber()` decides whether to read `block.number` directly or query the `ArbSys` precompile (`address(100)`) based on a hardcoded, closed set of chain ids: `ARBITRUM_ONE` (42161), `ARBITRUM_NOVA` (42170), `ARBITRUM_SEPOLIA` (421614). [1](#0-0) [2](#0-1) 

This is exactly the "hardcoded value breaks new L2/L3 deployments" pattern described in the external report, applied here to a hardcoded **chain-id list** (rather than a contract address) that governs which block-number source is authoritative for order-lifecycle timing.

### Finding Description
`_blockNumber()` is the single source of truth `IntentGatewayV2` uses for deadline math throughout the order lifecycle (`placeOrder`/deadline validation, fill-window checks, cancel eligibility), as referenced from `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`. [2](#0-1) 

The code comment itself states the invariant being protected: *"Order deadlines are denominated in the block heights Hyperbridge tracks for each state machine — for Arbitrum chains that is the L2 block number, but the `block.number` opcode there returns the approximate L1 block number, so the ArbSys precompile is queried instead."* [3](#0-2) 

Hyperbridge already targets multiple Arbitrum-stack chains and is expanding to more L2s (Base, Unichain, zkSync, Scroll, etc., per the seed report, and the deployment scripts already enumerate 9+ mainnet chains). [4](#0-3) 

Any current or future **Arbitrum Orbit chain** (a first-class, actively marketed Arbitrum deployment model) inherits the same L1/L2 block-number divergence as Arbitrum One/Nova, since Orbit chains are Arbitrum-stack rollups where `block.number` also reflects the parent/settlement chain height rather than the local L2 height. Because the chain-id check in `_blockNumber()` is a hardcoded, closed enumeration, any Orbit chain not in `{42161, 42170, 421614}` silently falls through to the `block.number` branch, returning the wrong (parent-chain) height while the contract's own logic and comments assert this value is the canonical, trusted "L2 block height Hyperbridge tracks" for that state machine. [5](#0-4) 

Unlike the reported Uniswap PositionManager bug (which reverts loudly and is easy to catch pre-launch), this failure mode is **silent** — the contract does not revert, it simply computes deadlines against the wrong clock, with no guard, no `require`, and no way for `_validateParams` or any other check in `IntentsBase` to catch the mismatch. [6](#0-5) 

### Impact Explanation
Because `_blockNumber()` feeds order-deadline enforcement directly, a wrong block-number source desynchronizes the local notion of "expired" from what Hyperbridge's cross-chain proof/verification layer and off-chain relayers/solvers assume for that state machine. Concretely this can:
- Make orders appear expired far earlier or later than intended (since L1 vs. L2 block cadence differs by an order of magnitude), enabling premature `cancelOrder`/refund flows to fire while a solver's fill is still legitimately in flight, or blocking legitimate refunds long past the user's intended deadline.
- Corrupt any cross-chain storage-proof verification that assumes deadline/height consistency between the local and remote gateway instances for cancellation flows built on `_calculateCommitmentSlotHash`. [7](#0-6) 

This directly touches the "timeout paths must bind ... and one-time receipt handling" invariant called out in the task, since deadline correctness underlies whether a fill vs. refund/cancel path is even reachable for a given order.

### Likelihood Explanation
Likelihood depends on whether Hyperbridge actually deploys `IntentGatewayV2`/`IntentsBase` on an Arbitrum Orbit chain (or any future Arbitrum chain id) not already present in the hardcoded triple. Given the project's demonstrated pattern of continuously adding new EVM chains to its `DeployIntentGateway.s.sol` peer list, and Orbit chains being a standard, actively-used Arbitrum deployment path, this is a realistic expansion scenario rather than a hypothetical one. I was not able to fully trace, within the available tool budget, every downstream function in `IntentGatewayV2.sol`/`ExtrinsicIntents.sol` that consumes `_blockNumber()` to confirm the exact fund-movement consequence (e.g., whether it enables a genuine double-claim between fill and refund) — this would need direct review of the `placeOrder`/`fillOrder`/`cancelOrder` deadline comparisons in those two files to fully confirm severity.

### Recommendation
Replace the closed chain-id allowlist with a robust, extensible mechanism:
- Detect Arbitrum-stack chains generically (e.g., attempt an `ArbSys` call and gracefully fall back, or gate via a governance-settable/immutable flag set at deployment/initialization time per state machine) instead of hardcoding `ARBITRUM_ONE`/`NOVA`/`SEPOLIA` chain ids.
- Alternatively, make the block-number source an explicit, validated constructor/initializer parameter (mirroring the seed report's recommendation to parameterize instead of hardcode), so every new Orbit/L2 deployment is forced to make an explicit, auditable choice rather than silently falling through to the wrong default.

### Proof of Concept
1. Deploy `IntentGatewayV2` (which inherits `IntentsBase`) on any Arbitrum Orbit chain whose `block.chainid` is not `42161`, `42170`, or `421614`.
2. Because that chain id fails all three equality checks in `_blockNumber()`, the function returns raw `block.number`. [5](#0-4) 
3. On Arbitrum-stack Orbit chains, `block.number` reflects the parent chain's height (analogous to Arbitrum One returning L1 height), not the local Orbit L2 height that order deadlines are meant to be denominated in per the code's own documented invariant. [3](#0-2) 
4. All deadline-gated order operations (fill window, cancel eligibility, cross-chain cancellation storage-proof checks) now operate against a materially different clock than intended, with no revert or on-chain signal that anything is wrong.

```text
    /**
     * @dev Returns the current block number of the host chain. Order deadlines are
     * denominated in the block heights Hyperbridge tracks for each state machine —
     * for Arbitrum chains that is the L2 block number, but the `block.number` opcode
     * there returns the approximate L1 block number, so the ArbSys precompile is
     * queried instead. The chain id check keeps the bytecode identical across all
     * chains, preserving the deterministic CREATE2 deployment addresses.
     * @return The chain-appropriate current block number.
     */
    function _blockNumber() internal view returns (uint256) {
        if (block.chainid == ARBITRUM_ONE || block.chainid == ARBITRUM_NOVA || block.chainid == ARBITRUM_SEPOLIA) {
            return IArbSys(ARB_SYS).arbBlockNumber();
        }
        return block.number;
    }
```
