### Title
Incorrect index remapping in `threshold_i_map_to_keys_and_musig_i_map` removes the wrong participant's preprocess/share, crashing confirmation signing - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The analog of CVE-2018-19937 (a gate bypassed because state was checked under one representation and consumed under another) is present in the coordinator's MuSig confirmation/signing protocol: `threshold_i_map_to_keys_and_musig_i_map` mixes two distinct index spaces — threshold share indexes (`Participant` values in the `spec.i()` range space) and MuSig participant indexes (position in the sorted signer list + 1) — and removes the local placeholder using the wrong space's key.

### Finding Description

`DkgConfirmer::share`/`complete` (and the equivalent signing paths) receive a `HashMap<Participant, Vec<u8>>` keyed by **threshold share index** of each publishing validator. `threshold_i_map_to_keys_and_musig_i_map` (coordinator/src/tributary/signing_protocol.rs:208-250) does the following:

1. Inserts `our_threshold_i` — `spec.i(removed, our_key).start`, a **share-index** in the `t`-of-`n` threshold space — into the map with an empty value (line 219).
2. Sorts all keys, resolves each to a validator key, and rebuilds a new map keyed by **musig_i** = `enumerate index + 1` over *validators* (lines 231-245). Note this space counts validators, not shares: when any validator has `weight > 1`, or any earlier validator was `removed` (shifting share indexes down per `spec.i`'s shift logic at spec.rs:132-136), `our_threshold_i` ≠ `musig_i`.
3. Removes `our_threshold_i` **from the musig-indexed map** (line 247) and unwraps the result.

Whenever `our_threshold_i` differs from our `musig_i` — i.e., any preceding validator has `weight > 1`, or any earlier validator was fatally slashed (`removed`), which changes `spec.i`'s returned `start` — line 247 either:

- removes a *different* signer's entry (dropping their real preprocess/share while our empty-vec placeholder survives under our own `musig_i`), or
- returns `None` and panics at `.unwrap()`.

In the first case, the surviving map still contains an entry under our own `musig_i`. `share_internal` → `machine.sign(preprocesses, msg)` then pushes `multisig_params.i()` plus all map keys into `included` (crypto/frost/src/sign.rs:290-295), producing a duplicate index → `FrostError::DuplicatedParticipant` → the `unreachable!()` arm at signing_protocol.rs:172-176 → panic.

### Impact Explanation

The coordinator-side `DkgConfirmer::share`/`complete` path (used to produce the MuSig confirmation of generated keys on-chain) panics deterministically for any validator set where the two index spaces diverge — weighted validator sets and, critically, any confirmation `attempt > 0` where an earlier-sorted validator was fatally slashed and `removed` is non-empty. `removed` grows precisely because of adversarial behavior (slashing), so an adversary who gets an earlier-indexed validator removed forces this divergence and crashes every coordinator attempting `share`/`complete` for that attempt — a liveness/availability failure of the DKG-confirmation signing gate, analogous to the VLC bug's bypass of a protective gate via state the gate didn't account for.

### Likelihood Explanation

Triggering conditions are ordinary protocol states (non-unit weights, or a removed validator) rather than malformed bytes, but the `removed` set — the input that shifts `spec.i` results — is influenced by the behavior of validators being slashed. An adversary able to cause an earlier-indexed validator's removal (e.g., by being that validator and equivocating) causes the panic on the next attempt's `share`/`complete`. Medium likelihood: requires specific set composition or a prior slash event.

### Recommendation

In `threshold_i_map_to_keys_and_musig_i_map`, remove the placeholder using the musig-space index, not `our_threshold_i` — e.g., compute `let our_musig_i = Participant::new(u16::try_from(position_of_our_key_in_sorted).unwrap() + 1)` and `map.remove(&our_musig_i)`, or record the musig_i assigned to `our_threshold_i` during the remap loop and remove that key. Also replace `unreachable!` arms in `share_internal`/`complete_internal` with proper error propagation so unexpected `FrostError`s cannot panic the coordinator.
