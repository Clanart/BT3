### Title
Silently-skipped Copilot conflict resolutions get staged with unresolved conflict markers and committed - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` iterates over the AI-generated `copilotResolutions` and writes each resolved file to disk, but several failure paths in that loop `continue` (silently skip a file) without recording that the resolution was **not** applied. The caller (`copilot-conflicts-dialog.tsx`) treats the whole batch as done and immediately proceeds to `onContinueAfterConflicts()`, which stages *all* tracked working-directory files (including the ones Copilot silently skipped) via `stageFiles`/`git add` and then runs `rebase --continue` / `cherry-pick --continue` / `commit`. Because `git add` clears a path's "unmerged" index stage regardless of its content, a file that still contains raw `<<<<<<<`/`=======`/`>>>>>>>` markers gets committed as-is.

### Finding Description
`_applyCopilotConflictResolutions` (app/src/lib/stores/app-store.ts:7169-7269) loops over `copilotResolutions` and, for each entry, either writes the resolved content to disk or applies a manual ours/theirs choice. Multiple branches in this loop `continue` without any error surfaced to the caller: [1](#0-0) 

- `deletedSide === undefined` → `continue` (delete-vs-modify resolution silently dropped)
- `absolutePath === null` (from `resolveWithin` path-containment check) → logs a warning and `continue`
- these skips leave the working-directory file exactly as it was before Copilot ran — i.e. still containing conflict markers for a text conflict, or still in an ambiguous delete/modify state.

The function has no return value and no way to tell the caller that some resolutions were skipped: [2](#0-1) 

The UI simply awaits it and moves on: [3](#0-2) 

`onContinueAfterConflicts` then stages **every** tracked working-directory file — including the one that was never actually rewritten — and calls `git rebase --continue` / `cherry-pick --continue` / creates the merge commit: [4](#0-3) [5](#0-4) 

`stageFiles`/`updateIndex` simply runs `git update-index --add`/`git add`, which clears a path's conflicted ("unmerged") index stage based purely on the caller's request — Git does not inspect file content for leftover conflict markers: [6](#0-5) 

This is the same broken invariant as the SystemReward bug: the "resolved" bookkeeping (staging a resolution as applied) is advanced without confirming the underlying write actually succeeded/happened, so a skipped item is effectively counted as done. Just as `remain` was decremented for a failed `send()`, here the merge/rebase/cherry-pick "continue" step proceeds as if every conflicted file were genuinely resolved by Copilot, when in fact some files were silently left untouched.

### Impact Explanation
If a resolution is skipped, the affected file keeps its raw `<<<<<<<`/`=======`/`>>>>>>>` conflict markers on disk. Because staging clears the conflicted flag independent of content, the subsequent commit created by `createMergeCommit`/`rebase --continue`/`cherry-pick --continue` bakes literal conflict-marker text into the tracked source file. This is silent corruption of what the user commits and, if they push it, what they publish to the remote — potentially breaking builds, leaking both "ours" and "theirs" code side-by-side, or (for source files that are executed, e.g. build scripts) producing syntactically broken/behaviorally wrong code that ships without the user reviewing it, since the result dialog led them to believe Copilot had resolved everything.

### Likelihood Explanation
This path is reachable during any Copilot-assisted merge/rebase/cherry-pick conflict resolution when the working directory state changes between resolution generation and confirmation (e.g. `deletedSide === undefined`), or when `resolveWithin` rejects the returned path. It doesn't require local/physical access, admin rights, or leaked credentials — it's triggered purely by the shape/state of the attacker-influenced conflicting content in a cloned/fetched repository during a normal merge/rebase workflow. However, the exact conditions that make `absolutePath === null` or `deletedSide === undefined` fire in practice weren't fully confirmed from the available code (I could not locate `resolveWithin`'s implementation in the indexed code to verify exactly which inputs it rejects), so likelihood is moderate rather than certain — a background Devin session with full file access would be needed to trace `resolveWithin` and the exact reachability of these skip branches from attacker-controlled conflict content.

### Recommendation
`_applyCopilotConflictResolutions` should return the set of paths it actually wrote/staged (or the paths it skipped) instead of silently continuing. The caller should refuse to proceed with `onContinueAfterConflicts()` (or should re-check `hasUnresolvedConflicts`/scan for leftover conflict markers) for any file that was not successfully rewritten, and should surface a clear error/warning to the user rather than treating a partially-applied resolution set as fully applied.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
