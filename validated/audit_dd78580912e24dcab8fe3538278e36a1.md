### Title
Missing `__ReentrancyGuard_init()` in VLMGP (and mWomSV) breaks reentrancy protection on user lock/unlock functions - ([File: VLMGP.sol])

### Summary
`VLMGP` inherits `ReentrancyGuardUpgradeable` but its initializer `__vlMGP_init_` never calls `__ReentrancyGuard_init()`, leaving the guard's internal `_status` slot at its default value of `0` instead of `NOT_ENTERED` (`1`). The identical omission exists in `mWomSV.__mWOMSV_init_`. Because the `nonReentrant` modifier only reverts when `_status == _ENTERED`, and the check-then-set logic silently behaves incorrectly when starting from `0`, the reentrancy protection guarding user-facing lock/unlock functions is effectively broken. [1](#0-0) [2](#0-1) 

### Finding Description
`VLMGP` declares itself as `ERC20Upgradeable, OwnableUpgradeable, PausableUpgradeable, ReentrancyGuardUpgradeable` and marks several externally callable functions with `nonReentrant`: [3](#0-2) [4](#0-3) [5](#0-4) 

Its initializer only calls `__Ownable_init()`, `__Pausable_init()`, and `__ERC20_init(...)`, never `__ReentrancyGuard_init()`: [1](#0-0) 

The same pattern (inheriting `ReentrancyGuardUpgradeable`, using `nonReentrant` on `lock`/`unlock`/`forceUnLock`-equivalent flows, but never calling `__ReentrancyGuard_init()`) exists in `mWomSV`: [6](#0-5) [2](#0-1) 

Both `unlock` and `forceUnLock` in `VLMGP` follow a checks-external-call-effects pattern rather than checks-effects-interactions: they perform an external call (`IMasterMagpie(masterMagpie).multiclaimFor(...)`) and/or an external token transfer (`IERC20(MGP).safeTransfer(...)`) *before* zeroing `slot.amountInCoolDown`: [7](#0-6) [8](#0-7) 

Because the contract relies on `nonReentrant` to make this ordering safe, and the guard's storage was never initialized, an attacker can re-enter `unlock` (or `forceUnLock`) during the `multiclaimFor` callback (which itself distributes reward tokens and can invoke arbitrary reward-token transfer hooks, e.g. tokens with `ERC777`/callback-style transfer behavior registered as reward tokens) and repeat the transfer of `slot.amountInCoolDown`/`amountToUser` multiple times before the slot is zeroed out, draining MGP tokens held by the contract on behalf of all users.

### Impact Explanation
A broken reentrancy guard on `VLMGP`/`mWomSV` — contracts that custody user-locked MGP/mWOM tokens for an unprivileged, ordinary-wallet-reachable unlock flow — allows direct theft of other users' locked funds via reentrant calls to `unlock`/`forceUnLock`, since the external interaction occurs before the corresponding cooldown-slot state is zeroed. This is a direct theft-of-user-funds / protocol-insolvency-class impact.

### Likelihood Explanation
Any ordinary wallet can call `startUnlock`, wait for the cooldown, and then call `unlock`/`forceUnLock` — no privileged role is required to trigger the vulnerable path. The only precondition is a reentrant callback opportunity during the external calls in `unlock`/`forceUnLock` (e.g., through a reward token distributed via `multiclaimFor`), which is plausible given the contract's use of arbitrary configured reward tokens.

### Recommendation
Add `__ReentrancyGuard_init()` to `VLMGP.__vlMGP_init_` and `mWomSV.__mWOMSV_init_` so the `ReentrancyGuardUpgradeable` storage is properly initialized to `NOT_ENTERED`, restoring the intended protection for all `nonReentrant`-guarded functions.

### Proof of Concept
1. Deploy `VLMGP` behind a proxy and call `__vlMGP_init_`; note that the `ReentrancyGuardStorage._status` slot remains `0` (not `1`) because `__ReentrancyGuard_init()` is never invoked, analogous to the referenced report's `MockedReentrancyGuardView()` test.
2. Register a malicious reward token (or a token with transfer callbacks) with `MasterMagpie` such that `IMasterMagpie(masterMagpie).multiclaimFor` triggers a callback to `msg.sender` during `VLMGP.unlock`.
3. Have the attacker lock MGP, start unlock, wait for cooldown, then call `unlock(_slotIndex)`. Inside `multiclaimFor`'s reward-token transfer callback, re-enter `unlock(_slotIndex)` before `slot.amountInCoolDown` is zeroed in the outer call.
4. Because `_status` was never initialized to `NOT_ENTERED`, the `nonReentrant` check does not correctly block the re-entrant call, allowing `IERC20(MGP).safeTransfer(msg.sender, unlockedAmount)` to execute multiple times for the same cooldown slot, draining MGP from the contract.
