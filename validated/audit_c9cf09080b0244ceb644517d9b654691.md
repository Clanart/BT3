### Title
Checking out a Pull Request resolves the fork's branch by name, not by the reviewed commit SHA — ([File: app/src/lib/stores/app-store.ts])

### Summary
The report's broken invariant is: an amount/state is computed once (before an attacker-influenceable step) and then trusted again later without re-validating that it still matches, letting the attacker cause the two views to diverge. In GitHub Desktop, the analogous invariant is broken in the Pull Request checkout flow: the PR object the user reviews (title, diff, "Files changed") is anchored to a specific `head.sha` returned by the GitHub API, but the actual checkout resolves the fork's branch **by ref name**, never re-checking that the ref still points at the reviewed SHA.

### Finding Description
`PullRequest`/`PullRequestRef` model the head of a PR with both a `ref` (branch name) and a `sha` (the commit hash the API reported at fetch time): [1](#0-0) 

When the user chooses to check out a PR, `Dispatcher.checkoutPullRequest` forwards to `AppStore._checkoutPullRequest`, passing `pullRequest.head.ref` (the branch name) — the `sha` field is dropped entirely: [2](#0-1) [3](#0-2) 

`_findPullRequestBranch` then adds/uses a remote pointing at `headCloneUrl` (the fork, i.e., attacker-controlled if the PR is from an untrusted contributor), fetches it, and resolves the branch purely by `remoteRef = "${remote.name}/${headRefName}"` — a name lookup, with no comparison against any expected SHA: [4](#0-3) 

The resulting `Branch` (whatever the fork's ref currently points to) is what gets checked out via `_checkoutBranch`. Nothing in this path re-fetches or asserts that the branch tip still equals `pullRequest.head.sha`, the value that was used to render the PR's title/diff and that the user based their "review, then checkout" decision on.

This is the same class of bug as the ERC777 report: a value is captured once (the "amount"/SHA at the moment of display) and consumed later (checkout) after an attacker-controlled actor (the fork owner/remote) has had the opportunity to change the underlying state, and the code path that consumes the value never re-validates it against the originally observed value.

### Impact Explanation
A PR author (or anyone able to push to the fork branch — this includes an attacker whose PR the user is reviewing) can force-push new commits to `headRefName` between the time the user reviewed the PR in Desktop (title/diff computed from the stored `head.sha`) and the time the user clicks "Checkout" in the PR list, or even during the fetch step inside `_findPullRequestBranch` itself. Desktop will silently check out and place the user's working directory on the attacker's newest, unreviewed commit — not the commit that was displayed. This can be used to smuggle malicious build scripts, CI configs, dependency manifests, or source changes into what the user believes is a reviewed checkout, which the user may then build, run, commit on top of, merge, or push, i.e., silent corruption of what the user reviews before acting on the branch.

### Likelihood Explanation
This requires no local access, no malware, and no leaked credentials — only that the user is viewing/interacting with an attacker-authored (or attacker-controlled fork of an) open pull request and clicks "Checkout" (a normal, expected user action for reviewing contributions). The attacker fully controls the timing of the force-push to their own fork branch, and Desktop's fetch/checkout window over the network makes the race trivially winnable (the fetch itself in `_findPullRequestBranch` can be timed to occur just after a force-push).

### Recommendation
When checking out a pull request, resolve and validate against `pullRequest.head.sha` rather than the branch name alone:
- After fetching the fork remote in `_findPullRequestBranch`, verify the branch tip SHA matches `pullRequest.head.sha` (or check out the SHA directly, e.g., `pr/<number>` created from the specific commit) before calling `_checkoutBranch`.
- If the tip no longer matches (fast-forwarded, rebased, or force-pushed), warn the user that the PR has changed since it was last reviewed and require an explicit re-confirmation/refresh before checking out.

### Proof of Concept
1. Attacker opens a PR from `fork/feature` with an innocuous commit at SHA `A`. Victim opens the PR in Desktop; Desktop stores `PullRequest.head = { ref: "feature", sha: "A" }` and renders the diff for `A`.
2. Victim reviews the diff for `A`, decides it's safe, and clicks "Checkout branch" in the PR list (`onItemClick` → `dispatcher.checkoutPullRequest`): [5](#0-4) 
3. Immediately before or during Desktop's fetch inside `_findPullRequestBranch`, the attacker force-pushes a malicious commit `B` (e.g., adding a malicious `postinstall` script or altering source) to `fork/feature`.
4. `_findPullRequestBranch` fetches the fork remote and resolves `remoteRef` to whatever `feature` currently points to — commit `B` — with no check against the previously known SHA `A`: [6](#0-5) 
5. `_checkoutBranch` checks out `B`. The victim's working directory now contains unreviewed attacker content, believing it matches the diff they inspected for `A`.

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
