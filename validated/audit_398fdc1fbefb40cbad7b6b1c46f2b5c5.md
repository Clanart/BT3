### Title
`ThresholdKeys::read` accepts a secret share inconsistent with its claimed verification share, so attacker-supplied key bytes let a participant emit shares that never verify and get an honest signer blamed/slashed - (crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` deserializes `secret_share` and the per-participant `verification_shares` map, then calls `ThresholdKeys::new`, which only checks the count of shares and participant index bounds — it never verifies that `C::generator() * secret_share == verification_shares[params.i()]`, nor that the deserialized key belongs to the claimed participant at all. This is the Serai analog of performing a privileged operation (acting as participant `i` of a threshold group) without validating the authentication material (proof that the secret share actually corresponds to participant `i`'s verification share). [1](#0-0) [2](#0-1) 

### Finding Description

In `ThresholdKeys::new`, the only consistency performed is `verification_shares.len() == n` and `participant <= n`; the `group_key` is then derived by interpolating verification shares `1..=t`, entirely trusting the attacker-controlled map. `read` funnels straight into `new` after parsing the ciphersuite ID, `t`, `n`, `i`, interpolation, secret share, and the verification shares — no binding between `secret_share` and `verification_shares[i]` is ever established.

Downstream, `view()` interpolates `secret_share` and the verification shares independently: the node's emitted FROST share is `k + c·λ_i·s_i` (from the attacker-written `s_i`), while blame verification checks it against the attacker-written `verification_shares[i]`. In `AlgorithmSignatureMachine::complete`, a share failing `verify_share` produces `FrostError::InvalidShare(l)`, which the coordinator escalates into participant removal/slashing transactions (`RemoveParticipantDueToDkg` / `InvalidShare` handling in `coordinator/src/tributary/handle.rs` and `processor/src/key_gen.rs`). The code itself acknowledges this hole: `complete` errors with `"everyone had a valid share yet the signature was still invalid"` attributing it to "deserialize a semantically invalid FrostKeys". ### Impact Explanation

Untrusted bytes reaching `ThresholdKeys::read` (a serialized key blob — e.g., supplied via a restore/migration path or any channel where key material is ingested rather than generated by PedPoP/`calculate_share`, which does verify shares) cause the holder to emit signature shares under a key whose claimed identity (`i`, `group_key`, `verification_shares`) is unbound from the embedded secret. Two concrete consequences:

1. An honest node deserializing crafted keys produces shares that fail `verify_share`, deterministically causing `InvalidShare` blame against that participant — aborting signing sessions and triggering coordinator-level removal of a non-faulty participant.
2. Because `group_key` is computed purely from attacker-chosen verification shares `1..=t` and never checked against the secret, two copies of "the same" participant index can carry divergent group keys; `recover_key`'s consistency check on `group_key` then silently partitions, and signing proceeds under a group key other participants do not recognize — shares are valid individually yet the aggregate never verifies, yielding the unreachable-in-honest-operation `InternalError` abort.

### Likelihood Explanation

Reachability requires attacker-controlled bytes to reach `ThresholdKeys::read` — the rules explicitly enumerate `ThresholdKeys::read` as an untrusted-input surface. Within an honest DKG (`calculate_share` → `ThresholdKeys::new` on verified data) this is unreachable, which caps severity below the Strapi critical and at Medium: the impact is denial of signing and wrongful blame/removal of an honest participant rather than key extraction or signature forgery.

### Recommendation

In `ThresholdKeys::new` (or at least in `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Optionally also document/verify that callers obtain `ThresholdKeys` only from `calculate_share`/`complete`, which already perform share verification.

### Proof of Concept

```rust
// For any C: Ciphersuite, build a blob accepted by ThresholdKeys::read
// whose secret_share does not correspond to verification_shares[i].
let real_share = <C as Ciphersuite>::F::random(&mut OsRng);
let foreign_point = <C as Ciphersuite>::generator() *
    <C as Ciphersuite>::F::random(&mut OsRng); // != G * real_share

let mut shares = HashMap::new();
for l in 1 ..= n {
    shares.insert(Participant::new(l).unwrap(),
        if l == i { foreign_point } else { C::generator() * rand });
}

// ThresholdKeys::new succeeds: only count and index bounds are checked,
// never generator * secret_share == verification_shares[i].
let keys = ThresholdKeys::new(
    ThresholdParams::new(t, n, Participant::new(i).unwrap()).unwrap(),
    Interpolation::Lagrange,
    Zeroizing::new(real_share),
    shares,
).unwrap();

// Equivalent bytes pass through ThresholdKeys::read identically.
// When this node signs, complete() hits either InvalidShare(i) —
// blaming this honest participant — or InternalError.
```

```rust
  fn complete(
    self,
    mut shares: HashMap<Participant, SignatureShare<C>>,
  ) -> Result<A::Signature, FrostError> {
    let params = self.params.multisig_params();
    validate_map(&shares, self.view.included(), params.i())?;

    let mut responses = HashMap::new();
    responses.insert(params.i(), self.share);
    let mut sum = self.share;
    for (l, share) in shares.drain() {
      responses.insert(l, share.0);
      sum += share.0;
    }

    // Perform signature validation instead of individual share validation
    // For the success route, which should be much more frequent, this should be faster
    // It also acts as an integrity check of this library's signing function
    if let Some(sig) = self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum) {
      return Ok(sig);
    }

    // We could remove blame_entropy by taking in an RNG here
    // Considering we don't need any RNG for a valid signature, and we only use the RNG here for
    // performance reasons, it doesn't feel worthwhile to include as an argument to every
    // implementor of the trait
    let mut rng = ChaCha20Rng::from_seed(self.blame_entropy);
    let mut batch = BatchVerifier::new(self.view.included().len());
    for l in self.view.included() {
      if let Ok(statements) = self.params.algorithm.verify_share(
        self.view.verification_share(*l),
        &self.B.bound(*l),
        responses[l],
      ) {
        batch.queue(&mut rng, *l, statements);
      } else {
        Err(FrostError::InvalidShare(*l))?;
      }
    }

    if let Err(l) = batch.verify_vartime_with_vartime_blame() {
      Err(FrostError::InvalidShare(l))?;
    }

    // If everyone has a valid share, and there were enough participants, this should've worked
    // The only known way to cause this, for valid parameters/algorithms, is to deserialize a
    // semantically invalid FrostKeys
    Err(FrostError::InternalError("everyone had a valid share yet the signature was still invalid"))
```
