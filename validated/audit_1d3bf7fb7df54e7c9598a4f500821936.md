### Title
Missing default locking around lazy unknown-field-to-extension promotion causes data race / memory corruption in `upb_Message_GetOrPromoteExtension` - (File: `upb/message/promote.c`)

### Summary
The kernel CVE fixes a data race where `mc_ifc_count` is mutated by two code paths (`ipv6_mc_down` and the `mld_ifc_work` workqueue) without both paths holding `mc_lock`. The failed invariant is: "a field that looks read-only/idempotent from the outside is actually mutated, and not all callers acquire the required lock before touching it." The same invariant is violated in upb's extension/unknown-field subsystem: `upb_Message_GetOrPromoteExtension` (and the sibling promotion APIs) perform a **hidden, in-place mutation** of a `upb_Message`'s internal `aux_data` extension table and unknown-field list, but **no lock is held by default** — locking is only installed if the host-language binding opts in via `hpb::internal::upb_extension_locker_global`, which is `nullptr` unless a wrapper deliberately sets it.

### Finding Description
`GetExtension`/`HasExtension`-style calls are documented and used as if they were read-only queries after parsing. Internally, however, for extensions/unknown fields that were not yet linked at parse time, the first access triggers **lazy promotion**: [1](#0-0) 

which walks the unknown-field list, parses matching bytes into a new sub-message, and then calls: [2](#0-1) 

`_upb_Message_GetOrCreateExtension` mutates the message's `aux_data` array (potentially reallocating it via `_upb_Message_ReserveSlot`) and `upb_Message_DeleteUnknown2` mutates/reallocs the unknown-field storage — both are unsynchronized writes to shared, message-owned memory: [3](#0-2) 

Nothing inside `upb_Message_GetOrPromoteExtension`, `_upb_Message_Getext`, `upb_Message_FindUnknown2`, or `upb_Message_DeleteUnknown2` acquires any lock — the core upb runtime is intentionally lock-free/single-writer here. The *only* synchronization mechanism that exists is an **opt-in** hook defined in `hpb/internal/message_lock.h`, explicitly labeled as a stopgap: [4](#0-3) 

and implemented as a no-op unless a locker function pointer is installed: [5](#0-4) 

By default, `upb_extension_locker_global` is a zero-initialized `std::atomic` (`nullptr`), so `MessageLock`'s constructor loads `nullptr`, calls no `locker()`, and `unlocker_` stays `nullptr` — i.e., **no locking occurs at all** unless a host binding explicitly installs a locker (as the C++ test harness does for its own regression test): [6](#0-5) 

This mirrors the kernel bug precisely: `mld_ifc_stop_work`/`mld_ifc_work` are only safe if callers remember to wrap them in `mutex_lock(&idev->mc_lock)`; the fix added that locking centrally. In upb, the analogous "always acquire the lock before touching the shared mutable field" invariant is **not enforced by the core runtime** — it is left to each host language to reimplement correctly, and C++ users of raw `upb_Message`/`upb_MiniTableExtension` APIs (not going through `hpb::internal`) get **zero protection** by default.

### Impact Explanation
If a consuming application shares a single parsed `upb_Message` across threads (a pattern the API superficially invites, since `GetExtension`/`HasExtension` look like const reads) and two threads concurrently trigger extension/unknown-field promotion — e.g., thread A calls `GetOrPromoteExtension` for extension X while thread B calls it for extension Y, or while thread B serializes the message — both threads race on the same `aux_data` array and unknown-field linked storage. Because `_upb_Message_GetOrCreateExtensionWithTag` can reallocate/resize the `aux_data` array via `_upb_Message_ReserveSlot`, and `upb_Message_DeleteUnknown2` mutates/relinks unknown-field storage, concurrent unsynchronized access can produce:
- Lost updates / duplicate extension entries,
- Use of a stale/freed `aux_data` pointer if one thread reads while another reallocates,
- Corrupted unknown-field iterator state read by `upb_Message_FindUnknown2`/`NextUnknown2` while another thread deletes entries.

This is a genuine memory-safety data race (comparable in class, though not necessarily in blast radius, to the KCSAN-detected kernel bug), reachable purely through the C++/upb core APIs with a single crafted-but-valid, bounded Protobuf payload containing extension fields that are not eagerly linked (forcing the lazy-promotion code path) plus an application usage pattern of sharing the parsed message across threads for extension access. Given C/C++ memory corruption potential (heap corruption, UAF on `aux_data`), this can escalate to memory disclosure/integrity failure.

### Likelihood Explanation
Medium-High as an analog, but conditioned on an application-level precondition: the vulnerable path only fires when an application shares a single mutable `upb_Message` object across threads and performs extension access from more than one thread — a documented-as-unsafe-by-default pattern for which upb only provides an *opt-in* fix (`upb_extension_locker_global`). The team's own test suite (`hpb/internal/message_lock_test.cc`) and the explicit "TODO: Fix... will be replaced by a core runtime solution" comment in `message_lock.h` confirm the maintainers are aware this is unresolved in the core runtime and currently pushed onto callers/bindings to fix, exactly like the upstream kernel bug being pushed onto callers of `mld_ifc_stop_work` until the kernel fix centralized locking in `ipv6_mc_down`.

### Recommendation
- Move the required synchronization into the core `upb_Message_GetOrPromoteExtension` / `_upb_Message_GetOrCreateExtension` / `upb_Message_DeleteUnknown2` code paths themselves (e.g., an internal per-message spinlock/mutex or atomic CAS-based promotion, similar to the `PyUpb_LazyPtr` free-threading primitives already used elsewhere in the codebase) rather than relying on an externally-supplied, opt-in locker.
- Document loudly (and ideally `UPB_ASSERT`/instrument in debug/ASan/TSan builds) that `GetExtension`/`HasExtension` are **not** const-safe for concurrent multi-thread access unless a locker is installed, since the API surface currently suggests otherwise.
- Extend the existing `hpb::internal::MessageLock` concept from an opt-in "TODO" hack into a default, always-on internal locking/atomic mechanism at the `upb_Message` level (as the header comment itself proposes for the future).

### Proof of Concept
A minimal reproduction pattern using existing test infrastructure in the checkout:
1. Build a `TestModel` with two extensions not linked at parse time (as done in `hpb/internal/message_lock_test.cc:38-52`, `GenerateTestData()`), producing a bounded serialized payload.
2. Parse it once into a single `TestModel parsed_model` (shared, not per-thread) — same as `message_lock_test.cc:70-76`.
3. **Without** installing `upb_extension_locker_global` (skip line 71's `store(&lock_func...)`, which is precisely the default state for any C++/upb consumer not using the `hpb` locking shim), spawn two threads that both call `hpb::GetExtension(&parsed_model, theme)` and `hpb::GetExtension(&parsed_model, ThemeExtension::theme_extension)` concurrently, as in `TestConcurrentExtensionAccess` (`hpb/internal/message_lock_test.cc:70-118`).
4. Under ThreadSanitizer, this reproduces a data race on the message's internal `aux_data`/unknown-field state inside `upb_Message_GetOrPromoteExtension` (`upb/message/promote.c:118-215`) and `_upb_Message_GetOrCreateExtensionWithTag` (`upb/message/internal/extension.c:41-65`) — the exact scenario the `hpb::internal` locking shim was added to paper over, confirming the core upb runtime has no default protection.

upb_Extension* UPB_PRIVATE(_upb_Message_GetOrCreateExtensionWithTag)(
    struct upb_Message* msg, const upb_MiniTableExtension* e, upb_Arena* a,
    upb_TaggedAuxType tag) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  // For Canonical Extensions, we check whether the extension has already been
  // set. If we find an extension with the same pointer and tag, we reuse it to
  // prevent duplicate entries for the same extension.
  //
  // For Non-Canonical Extensions, we do NOT reuse them, matching the behavior
  // of adding a unknown StringView (through `_upb_Message_AddUnknown`) which
  // accumulates.
  if (tag == kUpb_TaggedAuxType_CanonicalExtension) {
    upb_Extension* ext =
        (upb_Extension*)UPB_PRIVATE(_upb_Message_Getext)(msg, e);
    if (ext) return ext;
  }
  if (!UPB_PRIVATE(_upb_Message_ReserveSlot)(msg, a)) return NULL;
  upb_Message_Internal* in = UPB_PRIVATE(_upb_Message_GetInternal)(msg);
  upb_Extension* ext = upb_Arena_Malloc(a, sizeof(upb_Extension));
  if (!ext) return NULL;
  memset(ext, 0, sizeof(upb_Extension));
  ext->ext = e;
  in->aux_data[in->size++] = upb_TaggedAuxPtr_MakeExtension(ext, tag);
  return ext;
}

class MessageLock {
 public:
  explicit MessageLock(const upb_Message* msg) : msg_(msg) {
    UpbExtensionLocker locker =
        upb_extension_locker_global.load(std::memory_order_acquire);
    unlocker_ = (locker != nullptr) ? locker(msg) : nullptr;
  }
  MessageLock(const MessageLock&) = delete;
  void operator=(const MessageLock&) = delete;
  ~MessageLock() {
    if (unlocker_ != nullptr) {
      unlocker_(msg_);
    }
  }

 private:
  const upb_Message* msg_;
  UpbExtensionUnlocker unlocker_;
};

bool HasExtensionOrUnknown(const upb_Message* msg,
                           const upb_MiniTableExtension* eid) {
  MessageLock msg_lock(msg);
  if (upb_Message_HasExtension(msg, eid)) return true;

  const uint32_t number = upb_MiniTableExtension_Number(eid);
  return upb_Message_FindUnknown2(msg, number, 0).status == kUpb_FindUnknown_Ok;
}

bool GetOrPromoteExtension(const upb_Message* msg,
