### Title
Nil-pointer dereference (chain halt / node crash) via unchecked `AccountKeeper.GetAccount` result in EVM signer-association code - (File: `app/ante/cosmos_checktx.go`)

### Summary
`UpdateSigners()` in `app/ante/cosmos_checktx.go` and the sibling `EVMAddressDecorator.AnteHandle()` in `x/evm/ante/preprocess.go` both call `accountKeeper.GetAccount(ctx, signer)` and immediately dereference the result (`acc.SetSequence(...)`, `acc.GetPubKey()`) without checking `acc == nil`. `AccountKeeper.GetAccount` returns a `nil` interface whenever the address has no stored account — exactly analogous to `k_object_find()` returning `NULL` for an unregistered object in the reported Zephyr CVE. Any signer address that reaches this code path without first having a persisted account causes a Go nil-interface-method-call panic.

### Finding Description
`sei-cosmos/x/auth/keeper/account.go` shows the canonical lookup semantics: [1](#0-0) 
returns `nil` for any address that has never been assigned an account.

`app/ante/cosmos_checktx.go`'s `UpdateSigners` fetches each tx signer's account and unconditionally dereferences it: [2](#0-1) 
There is no `if acc == nil` guard before `acc.SetSequence(...)` — a Go nil-interface call, which panics just like dereferencing the NULL `k_object` pointer in the original report.

The same unguarded pattern appears in `x/evm/ante/preprocess.go`'s `EVMAddressDecorator.AnteHandle`, which is wired into the standard (non-EVM) ante chain in `app/ante.go`: [3](#0-2) [4](#0-3) 
Here `acc := p.accountKeeper.GetAccount(ctx, signer)` is followed directly by `acc.GetPubKey()` with no nil check.

Both call sites are reached for every signer of a submitted Cosmos transaction (via `sigTx.GetSigners()`), after the association-lookup `GetEVMAddress` returns `false` (i.e., the signer is not yet EVM-associated).

### Impact Explanation
A nil-interface dereference panics the goroutine handling the ABCI request. Because this code runs inside the ante-handler / signer-update pipeline that executes for ordinary Cosmos transactions during `CheckTx`/`DeliverTx`, an unprivileged user can trigger a node-level panic by submitting a transaction whose signer set includes an address that has no persisted account. If not recovered by a surrounding `recover()`, this crashes the node process handling the transaction — on a validator this is a consensus-halting DoS; on a public RPC/full node it is a node crash, matching the CVSS 5.5 "AC:L/PR:L/UI:N ... A:H" profile of the original report (kernel/consensus-critical component halted by an unprivileged, syscall/tx-triggerable NULL dereference).

### Likelihood Explanation
The precondition — a transaction signer address with no existing account — is trivially reachable by any external actor: a brand-new (never funded, never seen) `sei1...` address can appear as a non-fee-payer signer (e.g., a co-signer, multisig participant, or authz-related signer) as long as normal signature verification and `SetPubKeyDecorator`/`DeductFeeDecorator` bookkeeping do not already force account creation for every signer before this code runs (only the fee payer is guaranteed to have an account created via `DeductFeeDecorator`/`SetPubKeyDecorator`'s inline-pubkey branch; other signers can skip account creation via the "already omitted pubkey" branch in `SetPubKeyDecorator`). This makes the bug reachable from a single, unprivileged, externally submitted transaction with no special access.

### Recommendation
Add explicit nil checks after every `AccountKeeper.GetAccount` call in `app/ante/cosmos_checktx.go` (`UpdateSigners`) and `x/evm/ante/preprocess.go` (`EVMAddressDecorator.AnteHandle`), mirroring the pattern already used in `sei-cosmos/x/auth/ante/fee.go`'s `checkDeductFee` (`if deductFeesFromAcc == nil { return error }`) and `precompiles/auth/auth.go`'s `account()` handler. When `acc == nil`, either create the account via `accountKeeper.NewAccountWithAddress`+`SetAccount` (consistent with `SetAddressMapping`'s existing "ensure account exists" pattern) or return a descriptive error instead of proceeding to dereference the nil value.

### Proof of Concept
1. Generate a fresh keypair/address `X` that has never sent or received funds on the chain (no account record in the auth store).
2. Construct a Cosmos SDK transaction (e.g., a multisig or authz-composed message) whose `GetSigners()` includes `X` as a secondary signer, structured so that `X`'s `SignerInfo.PublicKey` is omitted (client asserts the chain already knows it) while a primary/fee-payer signer with a valid, funded account supplies the inline pubkey and pays fees.
3. Submit the transaction via `CheckTx`/`DeliverTx` (or the EVM-adjacent checktx path that invokes `UpdateSigners`).
4. Because `X` has no account, `SetPubKeyDecorator` skips the `GetSignerAcc` existence check for `X` (pubkey-omitted branch), and the transaction proceeds to `EVMAddressDecorator`/`UpdateSigners`, where `accountKeeper.GetAccount(ctx, X)` returns `nil` and the subsequent `acc.GetPubKey()`/`acc.SetSequence(...)` call panics the node handling the request.

Note: full confirmation that no other ante decorator forces account creation for *every* signer (not just the fee payer) before this point would require live testing in a running node/CheckTx harness, which is outside the scope of static code review; the code as written unconditionally lacks the nil guard regardless of how reliably the precondition can be forced.
