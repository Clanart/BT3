### Title
Forfeiture bypass via same-transaction `cancelUnlock` before reward claim allows theft of decay-forfeited MGP/rewards - ([File: `VLMGP.sol`], [File: `rewards/vlMGPBaseRewarder.sol`])

### Summary
`vlMGPBaseRewarder._calExpireForfeit` computes the forfeited portion of a reward/MGP payout by reading `vlMGP.getRewardablePercentWAD(_account)` live, at the moment the claim executes. Because `VLMGP.cancelUnlock` has no restriction preventing it from being called on an already-expired ("stale") unlock slot, and simply zeroes out `slot.amountInCoolDown` with no `nonReentrant` guard or reward-settlement side effect, an attacker can call `cancelUnlock` immediately before triggering a claim (via `MasterMagpie.multiclaimFor` → `getReward`/`queueMGP`) in the same transaction. This erases the decayed slot from the percent calculation and restores `getRewardablePercentWAD` to 100%, completely bypassing the intended decay-based forfeiture.

### Finding Description
`VLMGP.getRewardablePercentWAD` (VLMGP.sol:193-218) computes a user's rewardable percentage by iterating `userUnlockings[_user]`. For any slot where `amountInCoolDown > 0` and `block.timestamp > endTime` (i.e., the slot has expired and gone stale without being finalized via `unlock()`), the percentage contribution decays over time: [1](#0-0) 

`vlMGPBaseRewarder._calExpireForfeit` (rewards/vlMGPBaseRewarder.sol:386-400) uses this live value to compute how much of a pending reward/MGP payout is forfeited: [2](#0-1) 

This is invoked both from `queueMGP` (used when unlocking/harvesting MGP) and from `_sendReward` (used by `getReward`/`getRewards`), both of which are only callable through `MasterMagpie` (`onlyManager`/`onlyMasterMagpie`): [3](#0-2) [4](#0-3) 

The critical flaw is that `VLMGP.cancelUnlock` can zero out a stale slot's `amountInCoolDown` with no time restriction and no `nonReentrant` guard, and it performs no reward-settlement call itself: [5](#0-4) 

Because `getRewardablePercentWAD` is a *view* recomputed fresh on every claim (not a value snapshotted/settled at the time the slot went stale), an attacker fully controls its input state right up to the instant of the claim. An attacker (via their own EOA or a helper contract) can, in a single transaction:
1. Call `vlMGP.cancelUnlock(slotIndex)` on their expired, decayed slot — this sets `slot.amountInCoolDown = 0`, removing it entirely from the `getRewardablePercentWAD` decay computation.
2. Immediately trigger `MasterMagpie.multiclaimFor` (which the attacker can call for themselves, or which is invoked internally by `startUnlock`/`unlock`) to reach `vlMGPBaseRewarder.getReward`/`queueMGP`.
3. `_calExpireForfeit` reads `getRewardablePercentWAD` **after** the cancellation, sees 100% rewardable, and forfeits nothing — even though, moments earlier, a portion of the pending reward/MGP was supposed to be forfeited due to the stale, decayed slot.

No existing modifier (`whenNotPaused`, lack of `nonReentrant` on `cancelUnlock`) or accounting mechanism prevents this reordering, since the forfeiture calculation is not based on a state snapshot taken when the slot became stale — it's computed on demand using current, attacker-influenced state.

### Impact Explanation
This is a theft of unclaimed yield: MGP/reward amounts that should be forfeited to other stakers (via `_queueNewRewardsWithoutTransfer`, redistributed as `ForfeitRewardAdded`) are instead retained entirely by the attacker. Every staker with a stale, decayed unlock slot can repeat this before every claim, permanently denying the redistribution pool its expected forfeited yield and unfairly increasing the attacker's payout at the expense of other honest stakers who let their forfeiture apply correctly. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
The precondition (an unlock slot whose `endTime` has passed while `amountInCoolDown > 0`, i.e., the user did not promptly call `unlock()`) is common and entirely attacker-controlled — the attacker can simply choose not to finalize their unlock. `cancelUnlock` and the claim-triggering calls (`getReward`, `startUnlock`, `unlock`, all of which invoke `multiclaimFor`) are public/external functions requiring no special privileges, no capital beyond the attacker's own locked MGP, and can be composed atomically in one transaction via a simple helper contract or even sequential calls within the same block by an EOA using two transactions if same-block ordering is guaranteed (though same-transaction via a contract wrapper is trivial and fully reliable). It is fully repeatable for every stale slot and every claim.

### Recommendation
Decouple forfeiture determination from live, attacker-mutable state at claim time. Options:
- Settle/lock in the forfeiture percentage (or the forfeited amount) at the moment a slot becomes stale (e.g., via a keeper-independent checkpoint), rather than recomputing `getRewardablePercentWAD` from currently-live `userUnlockings` data at claim time.
- Disallow `cancelUnlock` on slots whose `endTime` has already passed (force the user to call `unlock()` instead, which already triggers `multiclaimFor` before consuming the amount, settling rewards under the correct decayed percentage) — i.e., add a check `if (block.timestamp > slot.endTime) revert(...)` in `cancelUnlock`.
- Alternatively, force reward settlement (`multiclaimFor`/`getReward`) as part of `cancelUnlock` itself, using the pre-cancellation `getRewardablePercentWAD`, before the slot's `amountInCoolDown` is zeroed.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` (or `mWomSV`/`mWOMSVBaseRewarder` analog) with a short `coolDownInSecs`.
2. Attacker locks MGP, then calls `startUnlock` to create a slot; warp time past `slot.endTime` without calling `unlock()`, so the slot is stale.
3. Queue a batch of MGP rewards for the attacker such that `earned(attacker, MGP) > 0`.
4. **Baseline run**: call `vlMGPBaseRewarder.getReward(attacker, attacker)` directly (via MasterMagpie) without cancelling — assert `_calExpireForfeit`/emitted `MGPHarvested` shows `forfeitAmount > 0` matching the decayed `getRewardablePercentWAD`.
5. **Exploit run** (fresh state, same setup): deploy a small attacker contract that in one transaction calls `vlMGP.cancelUnlock(slotIndex)` then immediately calls into `MasterMagpie` to trigger `getReward`/`multiclaimFor` for the attacker.
6. Assert that in the exploit run, `forfeitAmount == 0` (or near-zero) and `userReceiveAmount` equals the full pending reward, versus the baseline where forfeiture is non-zero — proving the decay-based forfeiture is bypassable at will.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
