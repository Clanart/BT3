Confirmed: `_params.dispatcher` is a single, globally-shared `CallDispatcher` instance used by *every* order on the gateway (predispatch, output-calldata postdispatch, and same-chain fill sweeps all route through the same `_params.dispatcher` address). `CallDispatcher.dispatch` is a stateless, unauthenticated pass-through — anyone naming `_params.dispatcher` as `to` can push funds into it, and it holds no per-order bookkeeping. This is the load-bearing fact for the finding below.

### Title
Cross-order fund theft via shared-`CallDispatcher` dust sweep using a spot `balanceOf` check - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_execute()` (called from `_fillSameChain` in `IntrinsicIntents.sol`, and from the cross-chain postdispatch path) sweeps *whatever balance the shared `CallDispatcher` happens to hold* for each output token, immediately after running the order's own attacker-supplied `output.call`, and books all of it as "protocol dust" via `IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance`. Just like the Aave `_checkNoLiquidity` bug — which used `IERC20Detailed(asset).balanceOf(aTokenAddress)` (a spot balance) instead of an accounting invariant (scaled total supply / per-order debt) — this sweep uses a spot balance snapshot of a *shared, unscoped* contract instead of a value scoped to the specific order being finalized. Because the dispatcher is one singleton contract shared by all orders and by both the predispatch and postdispatch call paths, any tokens sitting in it at sweep time — including tokens deposited moments earlier by an unrelated order's calldata, or deliberately funneled there by an attacker's own `output.call` — get treated as if they belong to the order currently finishing execution.

### Finding Description
`_execute` in `evm/src/apps/intentsv2/IntentsBase.sol` (lines 438-485):
```solidity
function _execute(Order calldata order, uint256 outputsLen) internal {
    if (order.output.call.length == 0) return;
    address dispatcher = _params.dispatcher;
    ICallDispatcher(dispatcher).dispatch(order.output.call);      // attacker-controlled calls
    ...
    uint256 balance = IERC20(token).balanceOf(dispatcher);         // spot balance, not order-scoped
    if (balance > 0) {
        sweepCalls[...] = Call({to: token, value: 0,
            data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)});
        emit DustCollected(token, balance);
    }
    ...
}
```
`order.output.call` is user-supplied at order-placement time (docs: "Postdispatch... The `call` field in `PaymentInfo` contains calldata to execute after the order is filled"), and `_params.dispatcher` — `CallDispatcher.sol` — is a single stateless forwarder shared across *every* order and *both* predispatch/postdispatch flows [1](#0-0) . It has no concept of which order owns which balance; it just executes whatever `Call[]` it's told and holds whatever tokens end up in it. The predispatch flow independently confirms the same singleton is reused and pulls balances via unscoped `balanceOf(dispatcher)` reads [2](#0-1) .

The vulnerable invariant: "the balance the dispatcher holds when `_execute` runs belongs to *this* order" is never actually enforced — it is inferred from a mutable, shared, externally-influenceable snapshot, exactly the same class of mistake as the reported `_checkNoLiquidity` bug (using `balanceOf` as a stand-in for a scoped accounting value). An attacker who controls `order.output.call` (every order placer does) can:
1. Craft `output.call` so that, as one of its steps, it moves tokens that were *already* escrowed/pending for a *different*, concurrently-processing order (e.g. a same-chain order the attacker also placed, or output tokens a solver transferred to `beneficiary`/dispatcher for another still-in-flight fill) into `dispatcher`.
2. Trigger their own `fillOrder` such that `_execute` runs and sweeps the entire `balanceOf(dispatcher)`, including the diverted funds, into the gateway as "dust" credited to the attacker's own `DustCollected`/`OrderFilled` accounting path, or simply strands another user's in-flight settlement.
3. Because the sweep transfers to `address(this)` (the gateway) rather than to a specific beneficiary, and dust is later drained only through governance `_sweepDust`, this at minimum permanently locks/misattributes another party's funds as protocol dust, and at worst lets a solver/attacker who also controls the dust-sweep beneficiary (or races the predispatch/postdispatch calls of two orders in the same block) redirect real user funds out of the intended settlement path.

The check exists purely to decide "how much do I sweep," and — like `_checkNoLiquidity` — it trusts a balance that can be manipulated within the same transaction/block by the very party whose action the check is supposed to gate.

### Impact Explanation
This falls under "logic attacks" / "unauthorized transaction or execution" / "stealing or loss of funds" per the bounty gate: a single shared, unauthenticated `CallDispatcher` combined with an unscoped `balanceOf` sweep lets order calldata (fully attacker-controlled, no privileged role required) misattribute or strand tokens belonging to a different order as "protocol dust," diverting them from their rightful beneficiary/escrow accounting.

### Likelihood Explanation
Any unprivileged user can place an order with arbitrary `output.call` content (the "Calldata" feature is explicitly designed for composable arbitrary execution), and the `_params.dispatcher` singleton is reused for every order and both predispatch/postdispatch flows, so no relayer, prover, or admin cooperation is needed to reach the vulnerable sweep — only sequencing two orders (or an order plus a solver fill) so that the shared dispatcher briefly holds funds that don't belong to the order currently calling `_execute`.

### Recommendation
Do not infer "how much to sweep" from `balanceOf(dispatcher)`. Either (a) give each order/fill its own ephemeral `CallDispatcher` instance (e.g. deployed via `CREATE2` per commitment and self-destructed/never reused), or (b) snapshot the dispatcher's balance *before* dispatching `order.output.call` and only sweep the delta attributable to that call, or (c) require the dispatcher itself to track balances per caller/commitment rather than being a bare stateless forwarder.

### Proof of Concept
Not independently executable from the indexed code alone — a full PoC requires reproducing the exact sequencing of two concurrent orders' `predispatch`/`postdispatch` calls against the shared `CallDispatcher` in a forked-mainnet Foundry test to demonstrate the cross-order balance leak concretely. I was not able to find (or rule out) an additional reentrancy guard in `IntentGatewayV2.fillOrder`/`placeOrder` that might serialize dispatcher usage across orders within a block; this repo's indexed excerpts show `nonReentrant` on `cancelOrder` but I could not confirm the same modifier is present (or absent) on `fillOrder`/`placeOrder`, which is the deciding factor for whether two orders' dispatcher usage can actually interleave within one transaction or must be sequenced across separate transactions in the same block. A Devin session with full repo/build access should verify `fillOrder`'s reentrancy protection and dispatcher-sharing semantics end-to-end before treating this as conclusively exploitable.
