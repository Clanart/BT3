### Title
`ThresholdKeys::read` deserializes secret share and verification shares without consistency checks, allowing forged group keys / misattributed blame - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reconstructs a threshold keypair entirely from untrusted bytes — `t`, `n`, `i`, a type-tag byte selecting `Interpolation::Constant` vs `Interpolation::Lagrange`, a `secret_share` scalar, and `n` verification-share points. `ThresholdKeys::new` never verifies that `secret_share * generator == verification_shares[i]`, and when `Interpolation::Constant` is chosen the interpolation coefficients themselves come from the untrusted byte stream. The result is a semantically invalid `ThresholdKeys` whose reported `group_key()` is fully attacker-controlled.

### Finding Description
`ThresholdKeys::read` parses the interpolation variant from a single attacker-controlled byte: `0 => Interpolation::Constant` (which then reads `n` arbitrary scalars as coefficients) and `1 => Interpolation::Lagrange` (crypto/dkg/src/lib.rs:604-616). It then reads `secret_share` and `n` verification-share points and passes them to `ThresholdKeys::new` (crypto/dkg/src/lib.rs:618-631).

`ThresholdKeys::new` validates only counts and index bounds, and computes `group_key` as `sum_{i=1..=t} verification_shares[i] * interpolation_factor(i)` (crypto/dkg/src/lib.rs:349-391). Critically, it never checks that the deserialized `secret_share` corresponds to `verification_shares[params.i()]` (`generator * secret_share == verification_shares[i]`). With `Constant` interpolation, the attacker additionally chooses every coefficient, so `group_key` can be set to any target point: set `c[0] = 1`, remaining coefficients `0`, and `verification_shares[Participant(1)] = victim_group_key`.

The FROST code itself acknowledges this class: `AlgorithmSignatureMachine::complete` notes "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494) — i.e., deserialization can produce objects no honest execution creates, the exact CWE-502 shape of the Kredis advisory (untrusted input instantiating an object with an attacker-chosen, semantically invalid state).

### Impact Explanation
An attacker who can feed bytes to `ThresholdKeys::read` can fabricate a `ThresholdKeys` that:
- Claims any `group_key` (e.g., a production validator set's group key) while embedding an unrelated `secret_share` and a forged participant index `i`. Outputs scanned under that `group_key` are unspendable by these keys.
- When used in `view()`/`sign`, produces signature shares under a participant index the holder does not legitimately occupy. Since per-share verification in `complete` (crypto/frost/src/sign.rs:475-489) checks each share against `verification_share(l)`, a forged `i` colliding with an honest participant's index causes that honest participant to be reported as `FrostError::InvalidShare(l)` — misattributed blame that downstream Serai code treats as a slashable fault (`ProcessorMessage::InvalidParticipant` / `InvalidShare` paths).
- Flipping the tag byte on a Lagrange-serialized key (or vice versa) silently changes how `group_key` and per-signer interpolation factors are computed, so two parties reading "the same" logical key from differently-tagged bytes disagree on the group key while both believing their key material is valid.

### Likelihood Explanation
Reachability is by design per the assessed threat model: `ThresholdKeys::read` is an explicitly in-scope deserialization entry point for untrusted bytes. Crafting the payload requires only scalar/point encodings — `read_F`/`read_G` enforce canonicity but not semantic consistency, so the bytes are trivially constructible. Exploiting it requires the attacker to influence the serialized key material consumed by a node (backup/restore, replicated DB, or any path where key blobs transit untrusted channels), which is the standard precondition for CWE-502 findings of this severity class.

### Recommendation
In `ThresholdKeys::new`, reject inputs where `C::generator() * secret_share != verification_shares[params.i()]`. Additionally, for `Interpolation::Constant`, consider committing the coefficients to the expected structure (e.g., recompute/verify them for known schemes such as MuSig's `binding_factor`, which are deterministically derivable from the participant keys rather than trusting the serialized values), or restrict `Constant` deserialization to contexts that expect it.

### Proof of Concept
1. Choose victim group key `G_victim`, and target params `t = n` (required for `Constant` per crypto/dkg/src/lib.rs:368-372).
2. Build serialized bytes: `C::ID` header, `t`, `n`, `i = 1`, tag byte `0`, coefficients `[1, 0, ..., 0]` (n scalars), arbitrary `secret_share`, then verification shares with `verification_shares[1] = G_victim` and arbitrary points for `2..=n`.
3. `ThresholdKeys::<C>::read` succeeds; `keys.group_key() == G_victim` even though `generator * secret_share != verification_shares[1]` and the discrete log of `G_victim` is unknown.
4. Using these keys in FROST `sign` produces a share that either fails verification under an honest participant's index (misattributed `InvalidShare` blame) or reaches the `InternalError("everyone had a valid share yet the signature was still invalid")` path that the code comments can only arise from "a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494).
