## Finding [1](#0-0) 

### Title
Unbounded recursive memo parsing in `PuzzleWithRestrictions.from_memo` allows a spend-triggered stack-exhaustion crash of PlotNFT/pool-tracking clients - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody structure (`MofN` member trees) directly from the attacker-controlled `memo` bytes attached to a `CREATE_COIN` condition, with no depth limit. `PlotNFT.get_next_from_coin_spend()` in `chia/pools/plotnft_drivers.py` calls this parser on the memo of any singleton-created coin it is tracking. A crafted, deeply-nested `MofN` memo causes unbounded Python recursion and a `RecursionError`, crashing whatever client process (pool-operator or wallet plotNFT tracker) is following that singleton's chain state — the same bug class as CVE-2022-42321 (recursive tree deletion in xenstored exhausting the stack from untrusted, attacker-controlled nesting depth).

### Finding Description
`PuzzleWithRestrictions.from_memo()` is defined as: [1](#0-0) 

When `further_branching` is true (derived directly from the memo bytes), it builds an `MofN` object whose `members` are produced by calling `PuzzleWithRestrictions.from_memo(memo)` again for every entry in `m_of_n_hint.member_memos` — and those nested member memos can again set `further_branching`, recursing arbitrarily deep. There is no maximum-nesting check anywhere in this method or its `MofNHint.from_program` counterpart.

This parser is invoked on chain data an attacker fully controls: the `memo_blob`/`memos` field of a `CREATE_COIN` condition is unconstrained bytes chosen by whoever creates the spend. The consuming code path is: [2](#0-1) 

`PlotNFT.get_next_from_coin_spend()` is the routine wallet/pool-operator client code uses to follow a plotNFT/pool singleton's lineage as it advances on-chain (e.g. for `join_pool`, waiting-room transitions, self-custody transitions). It falls into the `PuzzleWithRestrictions.from_memo(...)` branch whenever it cannot otherwise infer the puzzle from the previous known state, which is exactly the case a third-party pool-operator client hits when indexing many farmers' plotNFT singleton coins.

Unlike the rest of the codebase, which explicitly guards against this exact class of bug — e.g. `sha256_treehash()` is deliberately implemented iteratively "so we don't have to worry about blowing out the python stack" [3](#0-2)  and Data Layer's tree writer is likewise "Implemented iteratively to avoid Python recursion limits for deep graphs" [4](#0-3)  — `from_memo` has no such protection despite operating on fully attacker-controlled input.

Because a `CREATE_COIN` condition's CLVM cost only scales with byte size (not nesting depth), an attacker can encode thousands of nesting levels of `MofN` in a very small, cheap memo blob, well under any per-spend or per-block cost limit, and far exceeding Python's default recursion limit (1000).

### Impact Explanation
Any process that calls `PuzzleWithRestrictions.from_memo()` on attacker-influenced memo data — most concretely a pool-operator or plotNFT-tracking wallet service running `PlotNFT.get_next_from_coin_spend()` while syncing singleton state for pooled/self-custody plotNFTs — will raise an unhandled `RecursionError` and crash or abort that processing task. This is a spend-triggered transaction-processing halt of downstream clients that track plotNFT/pool singleton state, achievable by any actor who can produce a coin spend with a crafted memo (including the owner of the singleton itself, targeting a pool operator's indexing service, or any party whose coin creation is being watched by such a client).

### Likelihood Explanation
Likelihood is moderate-to-high for any deployed pool-operator or plotNFT client that calls `get_next_from_coin_spend` while syncing untrusted on-chain singleton history: constructing the malicious memo requires only ordinary spend-bundle construction (no signature bypass, no consensus change), and the payload is small and cheap.

### Recommendation
- Enforce a maximum nesting depth (or maximum total member count) when parsing `MofNHint`/`from_memo`, rejecting memos beyond a sane bound with a `ValueError` instead of recursing.
- Convert `PuzzleWithRestrictions.from_memo()` and `MofNHint`/member parsing to an iterative (stack-based) implementation, consistent with the pattern already used in `sha256_treehash()` and the Data Layer tree writer, so untrusted nesting cannot exhaust the Python call stack.
- Wrap `from_memo` calls in `PlotNFT.get_next_from_coin_spend()` to catch `RecursionError` (in addition to `ValueError`) and treat it as `GetNextPlotNFTError("Invalid memoization of PlotNFT")` as a defense-in-depth measure.

### Proof of Concept
1. Construct a `CREATE_COIN` condition whose memo blob is a deeply nested `MofN` hint structure: `("CHIP-0043", nonce, [], <further_branching=true>, (m, [nested_memo, nested_memo]), ...)`, where `nested_memo` is itself another such structure, repeated ~2000+ levels deep (trivial to build programmatically, and small in serialized size).
2. Submit a spend bundle whose coin spend includes this `CREATE_COIN` condition as the singleton's puzzle-hash-creating output (mirroring the shape expected by `PlotNFT.get_next_from_coin_spend`, i.e. parent memo unresolved from prior state).
3. Any pool-operator/wallet client that calls `PlotNFT.get_next_from_coin_spend()` on this coin spend to follow the singleton lineage triggers `PuzzleWithRestrictions.from_memo()`, which recurses once per nesting level and raises `RecursionError`, terminating that client's sync/processing task.
