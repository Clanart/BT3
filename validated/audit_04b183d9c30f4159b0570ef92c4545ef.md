### Title
Custody `SendMessageBanned` restriction fails to block `RECEIVE_MESSAGE`, allowing message-condition policy bypass - (File: chia/wallet/puzzles/custody/send_message_banned.clsp)

### Summary
The `SendMessageBanned` custody restriction is meant to prevent a delegated puzzle inside a `PuzzleWithRestrictions` custody arrangement from emitting message conditions that communicate off-coin. Its ChiaLisp implementation only checks for the `SEND_MESSAGE` opcode (66) and never checks for `RECEIVE_MESSAGE` (67), so a delegated puzzle can freely emit `RECEIVE_MESSAGE` conditions and bypass the intended restriction.

### Finding Description
`chia/wallet/puzzles/custody/send_message_banned.clsp` implements the restriction logic: [1](#0-0) 

`check_conditions` walks the output condition list and raises (`(x)`) only when `(f (f conditions))` equals `SEND_MESSAGE`. `RECEIVE_MESSAGE` is a distinct opcode (67) defined right alongside `SEND_MESSAGE` (66): [2](#0-1) 

The Python driver wrapping this puzzle, `SendMessageBanned` in `chia/wallet/puzzles/custody/restrictions.py`, has no additional filtering and simply curries/loads the same puzzle: [3](#0-2) 

The existing test suite only validates that `SEND_MESSAGE` is rejected and a "self-destruct" (empty) delegated puzzle is accepted; it never exercises a delegated puzzle that emits `RECEIVE_MESSAGE`: [4](#0-3) 

Because `SEND_MESSAGE`/`RECEIVE_MESSAGE` are a paired, mode-based inter-coin communication primitive (per the project's own testing notes, "Message-condition tests cover the paired `SEND_MESSAGE`/`RECEIVE_MESSAGE` invariant"), an attacker who controls (or is granted use of) the delegated puzzle inside a `SendMessageBanned`-restricted custody arrangement can still emit `RECEIVE_MESSAGE` conditions. Depending on how the surrounding member/mode bits are structured, this lets the coin participate in message exchanges (including coin-id/puzzle/amount commitment modes) that the custody policy was specifically designed to forbid — an intended-only-`SEND_MESSAGE`-capable coin can be coerced into acting as a message receiver, defeating the isolation the restriction is meant to enforce.

### Impact Explanation
This is a policy/authorization bypass within the custody/multisig architecture (`chia.wallet.puzzles.custody`), which end users rely on to restrict what an otherwise-untrusted or lower-privileged delegated puzzle/co-signer can do with a coin. An incomplete restriction lets a party who is only supposed to be constrained from sending messages instead receive them, silently defeating the isolation guarantee that custody designers and downstream integrators (e.g. plotnft/pool flows or other systems built atop this restriction primitive) depend on. This does not, on its own, forge signatures or double-spend, but it is a concrete violation of custody/access-control invariants reachable purely from a submitted spend bundle, matching the High-severity, policy-bypass nature of the reference CVE.

### Likelihood Explanation
Any user of the `SendMessageBanned` restriction (directly, or any wallet/custody configuration built on `chia.wallet.puzzles.custody.restrictions`) is affected the moment a delegated puzzle emits a `RECEIVE_MESSAGE` condition instead of `SEND_MESSAGE`; no privileged access or race condition is required, only crafting the delegated puzzle's output conditions, which is exactly the class of input a restriction like this is meant to constrain.

### Recommendation
Update `check_conditions` in `send_message_banned.clsp` (and the corresponding deployed `.clsp.hex`/`deployed_puzzle_hashes.json` entries) to raise on both `SEND_MESSAGE` and `RECEIVE_MESSAGE` opcodes, then add a regression test analogous to `test_send_message_banned` that asserts a `RECEIVE_MESSAGE`-emitting delegated puzzle is also rejected with `GENERATOR_RUNTIME_ERROR`.

### Proof of Concept
1. Build a `PuzzleWithRestrictions` with `restrictions=[ValidatorStackRestriction(required_wrappers=[SendMessageBanned()])]` and `puzzle=ACSMember()`, as in `chia/_tests/clvm/test_restrictions.py::test_send_message_banned`.
2. Instead of the `SendMessage(...)` delegated puzzle used in that test, construct a delegated puzzle whose output conditions include a `RECEIVE_MESSAGE` condition (opcode 67) built via `chia.wallet.conditions.ReceiveMessage`.
3. Wrap it with `ValidatorStackRestriction.modify_delegated_puzzle_and_solution` exactly as the existing test does for `SendMessage`, and push the resulting `WalletSpendBundle` via `SimClient.push_tx`.
4. Observe that unlike the `SEND_MESSAGE` case (which fails with `Err.GENERATOR_RUNTIME_ERROR`), the spend with `RECEIVE_MESSAGE` succeeds (`MempoolInclusionStatus.SUCCESS`), confirming the restriction is bypassed for the sibling opcode.

@pytest.mark.anyio
async def test_send_message_banned(cost_logger: CostLogger) -> None:
    async with sim_and_client() as (sim, client):
        restriction = ValidatorStackRestriction(required_wrappers=[SendMessageBanned()])
        pwr = PuzzleWithRestrictions(nonce=0, restrictions=[restriction], puzzle=ACSMember())

        # Farm and find coin
        await sim.farm_block(pwr.puzzle_hash())
        coin = (await client.get_coin_records_by_puzzle_hashes([pwr.puzzle_hash()], include_spent_coins=False))[0].coin

        # Attempt to send a message
        send_message_dpuz = DelegatedPuzzleAndSolution(
            puzzle=Program.to(
                (
                    1,
                    [
                        SendMessage(
                            bytes32.zeros,
                            sender=MessageParticipant(parent_id_committed=bytes32.zeros),
                            receiver=MessageParticipant(parent_id_committed=bytes32.zeros),
                        ).to_program()
                    ],
                )
            ),
            solution=Program.to(None),
        )
        wrapped_dpuz = restriction.modify_delegated_puzzle_and_solution(send_message_dpuz, [Program.to(None)])
        escape_attempt = WalletSpendBundle(
            [
                make_spend(
                    coin,
                    pwr.puzzle_reveal(),
                    pwr.solve(
                        [],
                        [Program.to([send_message_dpuz.puzzle.get_tree_hash()])],
                        Program.to(None),
                        wrapped_dpuz,
                    ),
                )
            ],
            G2Element(),
        )
        result = await client.push_tx(escape_attempt)
        assert result == (MempoolInclusionStatus.FAILED, Err.GENERATOR_RUNTIME_ERROR)

        # Now send it to the correct place
        self_destruct_dpuz = DelegatedPuzzleAndSolution(
            puzzle=Program.to(None),
            solution=Program.to(None),
        )
        wrapped_dpuz = restriction.modify_delegated_puzzle_and_solution(self_destruct_dpuz, [Program.to(None)])
        sb = cost_logger.add_cost(
            "Minimal puzzle with restrictions w/ send message banned wrapper",
            WalletSpendBundle(
                [
                    make_spend(
                        coin,
                        pwr.puzzle_reveal(),
                        pwr.solve(
                            [],
                            [Program.to([self_destruct_dpuz.puzzle.get_tree_hash()])],
                            Program.to(None),
                            wrapped_dpuz,
                        ),
                    )
                ],
                G2Element(),
            ),
        )
        result = await client.push_tx(sb)
        assert result == (MempoolInclusionStatus.SUCCESS, None)
