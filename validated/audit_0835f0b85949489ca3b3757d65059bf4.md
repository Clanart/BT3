### Title
Staking/Distribution/Gov precompiles accept `msg.value` without consuming or rejecting it, permanently stranding native coin at an unowned precompile address - (File: precompiles/staking/tx.go, precompiles/distribution/tx.go, precompiles/gov/gov.go)

### Summary
The `x/erc20` ERC20 precompile explicitly guards against exactly the bug class described in the external report: it rejects any call carrying `contract.Value() > 0` because "ERC20 precompiles cannot receive funds ... and will not be possible to recover funds sent to an instance of them" [1](#0-0) . The WERC20 precompile solves the same problem differently: its `Deposit` handler immediately routes the received `contract.Value()` back to the caller via `BankKeeper.SendCoins` so no value is ever retained at the precompile address [2](#0-1) . However, the `staking`, `distribution`, and `gov` precompiles implement neither protection: their `Execute`/`Run` dispatchers call the handler methods directly without any `contract.Value()` check [3](#0-2) [4](#0-3) , and methods like `Delegate` derive the bonded amount solely from the ABI-decoded `amount` argument via `NewMsgDelegate(args, ...)`, never from `contract.Value()` [5](#0-4) .

### Finding Description
In the EVM `CALL` semantics, when a caller invokes a precompile with `msg.value > 0`, go-ethereum's EVM transfers that native value from the caller to the callee address in the state DB *before* the precompiled contract's `Run` is invoked, and only reverts the transfer if the call itself reverts. The ERC20 and WERC20 precompiles are the only ones in this codebase that account for this: ERC20 outright rejects any nonzero value, and WERC20's `deposit` immediately forwards the value to `SendCoins` back to the caller so it is never left "owned" by the precompile.

The staking, distribution, and gov precompiles have no equivalent guard. Their `Execute` functions dispatch directly to the transaction handler based on method name without inspecting `contract.Value()`. For example, `Precompile.Delegate` builds the `MsgDelegate` amount entirely from the ABI-encoded `amount` parameter, not from any native value attached to the call [6](#0-5) . If a caller (an EOA via a wrapper contract, or more realistically a smart contract that also forwards `msg.value` when calling `STAKING_CONTRACT.delegate(...)`) sends native coin along with the call — intentionally or due to an integration bug — that coin is transferred by the EVM to the staking precompile's address (`0x...800`) as part of normal `CALL` value-transfer semantics, while the actual bonding amount is independently debited from the delegator's bank balance inside `stakingMsgServer.Delegate`. The precompile addresses (`0x...800`, `0x...801`, `0x...805`, etc.) are not controlled by any private key and have no code path that sweeps or forwards a stray native balance back out — unlike WERC20's deposit or ERC20's outright rejection. The value credited to the precompile address is therefore permanently locked: it cannot be withdrawn by the depositor, is not tracked by any keeper's accounting, and is not part of any recoverable state.

This exactly mirrors the report's bug class (native coin sent alongside a call to a contract that has no mechanism to receive/forward/reject it, resulting in stuck value) but manifests here as a **native EVM value-transfer semantics gap in precompiles that are payable-callable from Solidity ABI (`StakingI`, `DistributionI`, `GovI`)** rather than a missing `receive()` on a Solidity contract.

### Impact Explanation
Under the required Cosmos EVM impact gate, this qualifies as "permanent freezing, locking ... of user funds ... or unauthorized extraction of user funds" — any native coin an unprivileged caller attaches as `msg.value` to a staking/distribution/gov precompile call becomes permanently unrecoverable, since the precompile's Go implementation does not use, forward, or reject that value, and the precompile addresses have no owner/withdraw path. This is a direct value loss reachable from ordinary (non-privileged) contract/transaction flow, matching the "theft/permanent freezing of user funds" critical-impact category.

### Likelihood Explanation
Likelihood depends on whether wallets/dApps/integrating smart contracts actually attach `msg.value` when calling these precompiles' Solidity interfaces (`StakingI.delegate`, `DistributionI.withdrawDelegatorReward`, `GovI.vote`, etc.). Several of the repo's own test/reverter contracts (`StakingCaller.sol`, `StakingCallerTwo.sol`) declare their wrapper functions as `payable` and forward `msg.value` into `STAKING_CONTRACT.delegate(...)` [7](#0-6) , showing this is a realistic integration pattern developers use. Any real integrator following this pattern (or a user directly calling with value out of confusion, since Solidity `payable` interfaces invite it) would silently lose funds. I could not fully verify at the EVM/statedb layer within this session whether some upstream `RunNativeAction`/`RunSetup` wrapper in `precompiles/common/precompile.go` intercepts and reverts nonzero value uniformly for all precompiles (my last read of that file did not complete due to a tool-call error) — if such a universal check exists there, it would neutralize this finding for all precompiles equally. This should be verified directly in `precompiles/common/precompile.go` before treating this as conclusively exploitable.

### Recommendation
Add a shared, universal `contract.Value().Sign() == 1` rejection (or explicit forwarding, as WERC20 does for deposit) in the common precompile dispatch path (`precompiles/common/precompile.go`) so it applies uniformly to `staking`, `distribution`, `gov`, `bank`, `ics20`, and any other non-payable-by-design precompile, rather than relying on each precompile package to individually replicate the check that currently only exists in `erc20/erc20.go`.

### Proof of Concept
1. Deploy or use a wrapper contract analogous to `StakingCaller.sol`'s `testDelegate` (`payable`, forwarding `msg.value` into `STAKING_CONTRACT.delegate(address(this), validatorAddr, msg.value)`) [7](#0-6) .
2. Call `delegate` with an `amount` argument and also attach `msg.value` equal to that amount (as the sample contracts do).
3. Observe: the staking module debits the delegator's bank balance for the bonded `amount` via `stakingMsgServer.Delegate` (bank-based, independent of `contract.Value()`), while the EVM's native value-transfer mechanics simultaneously move the attached `msg.value` into the precompile address's balance, since `Precompile.Delegate` never checks or consumes `contract.Value()` [5](#0-4) .
4. Query the balance of the staking precompile address (`0x...800`) afterward — the attached value remains there permanently, with no withdraw method on the precompile and no controlling key, unlike WERC20's `deposit`, which explicitly returns the value [8](#0-7) , or ERC20, which rejects it outright [1](#0-0) .

// Deposit handles the payable deposit function. It retrieves the deposited amount
// and sends it back to the sender using the bank keeper.
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}

// Delegate performs a delegation of coins from a delegator to a validator.
func (p *Precompile) Delegate(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
	method *abi.Method,
	args []interface{},
) ([]byte, error) {
	bondDenom, err := p.stakingKeeper.BondDenom(ctx)
	if err != nil {
		return nil, err
	}
	msg, delegatorHexAddr, err := NewMsgDelegate(args, bondDenom, p.addrCdc)
	if err != nil {
		return nil, err
	}

	p.Logger(ctx).Debug(
		"tx called",
		"method", method.Name,
		"args", fmt.Sprintf(
			"{ delegator_address: %s, validator_address: %s, amount: %s }",
			delegatorHexAddr,
			msg.ValidatorAddress,
			msg.Amount.Amount,
		),
	)

	msgSender := contract.Caller()
	if msgSender != delegatorHexAddr {
		return nil, fmt.Errorf(cmn.ErrRequesterIsNotMsgSender, msgSender.String(), delegatorHexAddr.String())
	}

	// Execute the transaction using the message server
	if _, err = p.stakingMsgServer.Delegate(ctx, msg); err != nil {
		return nil, err
	}
