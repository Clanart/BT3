### Title
Unprotected `__WombatStaking_init` initializer can be front-run to hijack ownership of WombatStaking - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking` is deployed as an upgradeable contract behind a `TransparentUpgradeableProxy` (see `ProxyAdmin.sol` / `TransparentUpgradeableProxy.sol`) [1](#0-0)  and initializes its state through the `public` function `__WombatStaking_init`, guarded only by OpenZeppelin's `initializer` modifier and carrying no access-control check on the caller [2](#0-1) . Because proxy deployment and initialization happen as two separate transactions, any unprivileged wallet monitoring the mempool can front-run the deployer's initialization call.

### Finding Description
`__WombatStaking_init` sets critical state — `wom`, `veWom`, `masterWombat`, `masterMagpie`, `lockDays` — and calls `__Ownable_init()`, which sets `msg.sender` as the contract owner: [2](#0-1) 

The `initializer` modifier from OpenZeppelin's `Initializable` only guarantees the function runs once; it performs no `msg.sender` validation. Since `WombatStaking` is deployed as a proxy and initialized in a follow-up transaction, an attacker watching the mempool can submit their own call to `__WombatStaking_init` with higher gas, becoming the owner and setting attacker-controlled addresses for `wom`, `veWom`, `masterWombat`, and `masterMagpie` before the legitimate deployer's transaction lands. This is the exact bug class described in the external report for `PerpOwnable.transferPerpOwner` — a one-time, unauthenticated setup function that can be front-run to seize control of a contract that later custodies user funds.

`WombatStaking` is the contract that custodies user LP tokens deposited via `deposit`/`withdraw` and mints/burns receipt tokens through `WombatPoolHelper`/`AnkrBNBPoolHelper` calls such as `deposit`, `depositLP`, `withdraw`, and `burnReceiptToken`. If an attacker becomes owner of `WombatStaking` before real pools are added, they can subsequently call owner-gated functions (e.g., `setMWom`, `addPool`, `removePool`, pool helper wiring) with attacker-controlled parameters to redirect legitimate user deposits.

### Impact Explanation
Taking ownership of `WombatStaking` before it's properly wired lets the attacker permanently control LP custody configuration (mWom address, pool wiring, masterWombat/masterMagpie references) for the entire Wombat staking integration. Because `WombatStaking` is where deposited LP tokens sit and receipt tokens are minted/burned, an attacker-controlled owner can misconfigure pools/addresses to redirect or freeze deposited LP tokens once real deposits flow in, resulting in theft or permanent freezing of user funds — satisfying the "direct theft of user funds" / "permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood is contingent on the specific deployment sequence: the vulnerability is only exploitable in the narrow window between proxy deployment and the initialization transaction, requiring an attacker to actively monitor the mempool and out-bid the deployer's gas price at that exact moment. This is a real, unprivileged-wallet-reachable path (no special role needed to call `__WombatStaking_init`), but it is a one-time, deployment-window opportunity rather than a persistently exploitable bug against a live, already-initialized contract.

### Recommendation
- Restrict initializer functions like `__WombatStaking_init` (and analogous `__init` functions across `MasterMagpie`, `ReferralStorage`, `vlMGPBaseRewarder`, `mWOMSVBaseRewarder`, `WombatBribeManager`, etc.) so they can only be called by a trusted deployer/factory address, or deploy the proxy and call `initialize` atomically within the same transaction (e.g., via a factory contract or by encoding the `initialize` call as constructor data passed to the proxy).
- Consider using `_disableInitializers()` in constructors of implementation contracts to prevent initialization of the logic contract itself, and ensure proxy deployment scripts always couple proxy creation with initialization in one atomic transaction.

### Proof of Concept
1. Deployer deploys the `WombatStaking` implementation and a `TransparentUpgradeableProxy` pointing to it (two separate transactions).
2. Deployer prepares a transaction calling `__WombatStaking_init(wom, veWom, masterWombat, masterMagpie)` on the proxy address.
3. Attacker observes this pending transaction in the mempool and submits an identical call to `__WombatStaking_init` with attacker-supplied parameters and a higher gas price.
4. Attacker's transaction is mined first; `initializer` marks the contract as initialized, `__Ownable_init()` sets the attacker as `owner()`, and `wom`/`veWom`/`masterWombat`/`masterMagpie` are set to attacker-chosen values.
5. The deployer's original transaction reverts (already initialized). The attacker now owns `WombatStaking` and controls all `onlyOwner` configuration functions (`setMWom`, `addPool`, `removePool`, etc.), which govern LP custody and receipt-token issuance. [2](#0-1)
