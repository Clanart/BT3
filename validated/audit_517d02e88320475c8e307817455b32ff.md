### Title
Governing node can set `reward.mintingamount` (and other reward-distribution governance parameters) to an arbitrarily high value with no upper bound, causing unbounded token supply inflation - (File: kaiax/gov/param.go)

### Summary
The `VaultAdmin` report is about an owner being able to set a fee parameter to an unreasonably high value (up to but excluding 100%) with no sane upper bound, causing griefing/loss for other users. The analogous privileged-parameter-setting path in Kaia is the governance parameter system in `kaiax/gov`, specifically `RewardMintingAmount`, which controls how much new native token is minted every block and has **no upper bound check at all** (`FormatChecker: noopFormatChecker`).

### Finding Description
Governance parameters in Kaia are defined in a table with a `Canonicalizer` and a `FormatChecker` used to validate any vote value before it is accepted into the parameter set: [1](#0-0) 

`RewardMintingAmount` uses `bigIntCanonicalizer` (which only ensures the value parses as a big int) and `noopFormatChecker`, which unconditionally returns `true` regardless of the value: [2](#0-1) 

Contrast this with the `RewardMinimumStake` and `RewardStakingRewardThreshold` parameters just below it, which at least enforce `v.Sign() >= 0`: [3](#0-2) 

Additionally, the `checkConsistency` function in the header-governance implementation, which cross-validates certain vote values against other chain state (e.g., `Kip71LowerBoundBaseFee` vs `Kip71UpperBoundBaseFee`), explicitly treats `RewardMintingAmount` as requiring **no further checks** beyond the basic format check: [4](#0-3) 

Once a `RewardMintingAmount` vote is accepted (via `governance_getParams`/header governance voting mechanism, exercised by the governing node in `single` governance mode), it flows directly into `RewardConfig.MintingAmount` and is minted every block without any sanity bound: [5](#0-4) [6](#0-5) 

This value is added straight into the block reward and distributed to the proposer/stakers/funds every single block: [7](#0-6) 

This is structurally identical to the `VaultAdmin` bug class: a governance-privileged actor (the governing node, analogous to the `VaultAdmin` owner) can set a monetary parameter (minting amount, analogous to performance/withdrawal fee) with no reasonable upper bound, and the parameter is used every "epoch" (in Kaia's case, every block) to move value.

### Impact Explanation
If a governing node casts (or a malicious/compromised governing node is coerced into casting) a `RewardMintingAmount` vote with an extremely large value, every subsequent block would mint that amount of new native KAIA and distribute it to the proposer/reward addresses, causing severe and immediate uncontrolled supply inflation. Unlike `RewardRatio`/`Kip82Ratio`, which are format-checked to sum to 100 (bounding relative distribution), there is no absolute ceiling on the minted amount itself. This is a direct match to the "supply inflation" acceptance criterion.

### Likelihood Explanation
This requires control of the governing node vote (a privileged governance actor), which is analogous to the contract owner in the original report — not an arbitrary unprivileged party. However, per the task's explicit allowed categories, "governance parameters" and "staking and reward distribution" are permitted analog domains, and no code path independently caps the value once voted. The likelihood of triggering the underlying code defect is effectively guaranteed given a single accepted vote, since there is zero validation logic standing between the vote and consensus-wide minting.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` that enforces `v.Sign() >= 0` and a reasonable upper bound (e.g., relative to `DefaultMintingAmount` or a hard cap value), consistent with the bounding pattern already used for `RewardRatio`/`Kip82Ratio` (which must sum to 100) and the cross-parameter consistency checks already implemented for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`. Consider adding an explicit case for `RewardMintingAmount` in `checkConsistency` (in `kaiax/gov/headergov/impl/header.go`) rather than relying purely on the no-op format checker.

### Proof of Concept
1. In `single` governance mode, the governing node (the account identified by `GovernanceGoverningNode`) submits a vote for `gov.RewardMintingAmount` with an arbitrarily large value (e.g. `10^30`).
2. `NewVoteData` accepts it because `RewardMintingAmount`'s `FormatChecker` is `noopFormatChecker`, always returning `true` (`kaiax/gov/param.go:160-162,414-424`).
3. `checkConsistency` in `kaiax/gov/headergov/impl/header.go:214-220` performs no additional validation for `gov.RewardMintingAmount`, so the vote passes header verification (`VerifyVote`/`VerifyGov`).
4. Once the vote takes effect at the next epoch, `reward.NewRewardConfig` populates `RewardConfig.MintingAmount` with the attacker-chosen value.
5. Every subsequent block, `getRewardSummary`/`getDeferredRewardSimple`/`getDeferredRewardFullKore`/`getDeferredRewardFullFlex` in `kaiax/reward/impl/getter.go` mint and distribute this amount to the proposer/stakers/reward funds (`kaiax/reward/impl/getter.go:86-87,225-227,333-368`), producing unbounded token supply inflation with no code-level ceiling.

Note: I could not fully trace the exact contract-governance (`kaiax/gov/contractgov`) code path for parameter updates beyond header-governance voting, since the index did not surface it in these searches; if a Devin session is needed to inspect additional validation possibly present in `contractgov`, that would need to be checked to see if it adds bound-checking not visible here.

// getDeferredRewardFullKore is for non-Simple policy and after Kore.
func getDeferredRewardFullKore(config *reward.RewardConfig, execFee, burntFee, blobFee *big.Int, si *staking.StakingInfo) (*reward.RewardSpec, error) {
	var (
		spec             = reward.NewRewardSpec()
		minted           = new(big.Int).Set(config.MintingAmount)
		distributableFee = new(big.Int).Sub(execFee, burntFee)
	)

	// Distribute using RewardRatio first. Unlike Legacy, fees are not distributed here
	// because fees are exclusively allocated to proposer. By the way, remainder goes to KIF.
	validators, kif, kef := config.RewardRatio.Split(minted)
	proposer, stakers := config.Kip82Ratio.Split(validators)
	ratioRemainder := calcRemainder(minted, proposer, stakers, kif, kef)
	kif.Add(kif, ratioRemainder)

	// Further distribute using Kip82Ratio. By the way, remainder goes to proposer.
	// After Prague, if the CLStaking is not nil, the proposer and staking rewards are proportionally distributed to both CN and CL.
	// For proposer rewards, see `specWithProposerAndFunds`.
	stakersAlloc, kip82Remainder := assignStakingRewards(config, stakers, si)
	proposer.Add(proposer, kip82Remainder)
	stakers.Sub(stakers, kip82Remainder)

	// Proposer gets the fees.
	proposer.Add(proposer, distributableFee)

	spec.Minted = minted
	spec.TotalFee = new(big.Int).Add(execFee, blobFee)
	spec.BurntFee = new(big.Int).Add(burntFee, blobFee)
	spec.Stakers = stakers
	for addr, amount := range stakersAlloc {
		spec.IncRecipient(addr, amount)
	}
	spec = specWithProposerAndFunds(spec, config, proposer, kif, kef, si)
	return spec, nil
}
