I found a strong analog: `app/src/lib/git/clone.ts` explicitly disables git's own clone-time config protection by setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before invoking `git clone --recursive` on an attacker-supplied URL.

### Title
Clone-time disabling of Git's `protected.configuration` safeguard allows a malicious remote/submodule to smuggle dangerous repo config (`core.hooksPath`, `core.fsmonitor`) into a freshly cloned repository - (File: `app/src/lib/git/clone.ts`)

### Summary
Git ships a defense-in-depth mechanism (the "clone protection" that the `GIT_CLONE_PROTECTION_ACTIVE` internal env var gates) intended to prevent a small class of config values considered dangerous (e.g. `core.hooksPath`, `core.fsmonitor`) from being effective when they originate from a repository/config the user did not explicitly opt into (e.g. one just fetched from an untrusted remote, or a bundle/local-clone source). Desktop's `clone()` function [1](#0-0)  unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every clone, which turns this protection off for all clones performed through Desktop, including clones of arbitrary/attacker-controlled remote URLs.

### Finding Description
This mirrors the sudoswap bug's broken invariant: a value that should be validated/trusted only after a specific gate (the router being an approved, non-reentrant caller; here, config coming only from a locally-trusted source) is instead accepted unconditionally because the guard is disabled. Desktop always disables the git-native guard rather than only for trusted, already-vetted repositories.

Once a clone completes, Desktop later reads and *executes* content controlled by that same repository's config: `getRepoHooks` in `app/src/lib/hooks/get-repo-hooks.ts` runs `git config -z --get core.hooksPath` against the freshly cloned repository path with no scope restriction [2](#0-1) , and if that path contains executable files matching a known hook name, `withHooksEnv` proxies and executes them during subsequent commit/push/pull/merge/rebase operations [3](#0-2) . Hook execution is on by default (`enableHooksByDefault`) as shown by the preference default [4](#0-3)  and the changelog entry "Enable hooks support by default" [5](#0-4) .

Normally, Git's clone protection exists specifically because a clone can, through `--recursive` submodule checkout or a crafted `.git/config` obtained via file:// / bundle transports, end up with a `core.hooksPath`/`core.fsmonitor` value pointing at attacker-supplied content in the working tree before the user has had any chance to review it. Disabling `GIT_CLONE_PROTECTION_ACTIVE` for every clone removes that safety net project-wide rather than only where Desktop has already validated the source. Combined with `--recursive` submodule cloning in the same call [6](#0-5) , a malicious top-level repository (or a submodule it references) can carry a config setting `core.hooksPath` into a directory containing attacker-authored "hook" scripts checked out as ordinary tracked files, and Desktop's own hook-interception feature will subsequently execute them as if they were locally-authored, trusted hooks — with no reentrancy-style additional confirmation from the user that a "local" hook is really local.

### Impact Explanation
If exploitable, this yields arbitrary code execution on the victim's machine using the desktop user's own privileges, triggered purely by cloning a malicious public repository and then performing an ordinary commit/push/pull/merge — actions a normal Desktop user routinely performs right after cloning. This satisfies the "attacker controls a cloned/fetched repository ... resulting in code execution" impact criterion.

### Likelihood Explanation
Medium-High. The attack requires only that the victim clone a hostile repository through Desktop and then perform one of the operations for which hooks are intercepted (`pre-commit`, `pre-push`, `post-checkout`, `post-merge`, etc., per `knownHooks` in `get-repo-hooks.ts` [7](#0-6) ). No special privileges or prior compromise are needed. The main uncertainty (not fully verifiable from the indexed code alone) is exactly which config values `GIT_CLONE_PROTECTION_ACTIVE=false` disables in the vendored dugite/git binary version and whether `core.hooksPath` set via a cloned `.git/config`/submodule config survives into the working `.git/config` after `git clone --recursive` completes normally (as opposed to only during the clone subprocess itself). This should be confirmed by a background agent capable of building/running Desktop's vendored git.

### Recommendation
- Only set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for clone sources Desktop has already established as trusted (e.g. re-clones of a repository the user already has an account/relationship with), not for arbitrary URLs entered by the user or reached via "Clone repository" from GitHub.
- After clone (including recursive submodule clones), explicitly re-validate that `core.hooksPath` and `core.fsmonitor` are unset or point only to Desktop's own managed hook proxy directory before allowing `getHooksEnvEnabled()`-gated hook execution to run against a newly cloned repository.
- Treat hook execution as requiring an explicit one-time user confirmation the first time hooks are detected in a freshly cloned (as opposed to pre-existing/relocated) repository, mirroring the "reentrancy guard"-style recommendation in the source report: validate state directly before use rather than trusting a value cached/set earlier in the flow.

### Proof of Concept
1. Attacker creates a public GitHub repo `evil/repo` containing a submodule (or main-repo committed config, if reachable via `--recursive`) that sets `core.hooksPath = .attacker-hooks` and an executable file `.attacker-hooks/post-checkout` (or `pre-commit`) containing an arbitrary payload.
2. Victim uses GitHub Desktop's "Clone a repository" to clone `evil/repo`; Desktop calls `clone()` with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and `--recursive` [8](#0-7) .
3. Victim performs an ordinary follow-up action (checkout, commit, or pull) in Desktop; `withHooksEnv`/`getRepoHooks` detect the (attacker-authored) hook file under the effective `core.hooksPath` and execute it via the hooks proxy [9](#0-8) .
4. The attacker's script runs with the victim's OS-level privileges, achieving code execution without any explicit warning that the hook originated from freshly cloned, untrusted content.

Note: I was not able to fully confirm from the indexed source alone (i) the precise semantics of `GIT_CLONE_PROTECTION_ACTIVE` in the vendored git/dugite build used by this fork, or (ii) whether `core.hooksPath` set inside a submodule's config actually propagates to a location `getRepoHooks` will read for the *superproject* path. Given index-size limits, a full confirmation (e.g., inspecting the vendored git build flags or running an end-to-end clone test) would require a Devin session with full repository/build access.
