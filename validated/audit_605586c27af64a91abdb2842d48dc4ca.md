### Title
Unauthenticated access to `InternalSendTx`/`InternalGetEmergencyStopTx` on the aggregator when `client_verification=false` selects the `Noop` interceptor - (File: `core/src/rpc/interceptors.rs`, `core/src/servers.rs`)

### Summary
`create_grpc_server` picks the interceptor solely from `config.client_verification`: when true it installs `OnlyAggregatorAndSelf`, which enforces `leaf_cert == our_cert` for any method whose gRPC name starts with `Internal`; when false it installs `Noop`, which returns `Ok(req)` unconditionally for every request. Because the aggregator's `client_verification` can legitimately be `false`, the self-only trust boundary that the codebase built specifically for `Internal`-prefixed methods (`internal_send_tx`, `internal_get_emergency_stop_tx`) is not enforced at all in that mode, letting any caller invoke them.

### Finding Description
The claimed binding is: *"a caller reaching an `Internal`-named method" == "that caller possesses the entity's own client certificate (self)"*. This is enforced only inside `only_aggregator_and_self`: [1](#0-0) 

which is reached only through the `OnlyAggregatorAndSelf` variant: [2](#0-1) 

`create_grpc_server` chooses which variant is installed purely based on `config.client_verification`: [3](#0-2) 

When `client_verification` is `false`, `Interceptors::Noop` is installed, and its `call` implementation is `Ok(req)` with no certificate or method-name check whatsoever — `is_internal` is never invoked. This is verified directly in the `Interceptor::call` match arm above. `InternalSendTx`/`InternalGetEmergencyStopTx` are gRPC methods implemented on `AggregatorServer` (`core/src/rpc/aggregator.rs`), reachable at the aggregator's gRPC port. With `client_verification=false`, an attacker with no TLS client certificate at all can open a connection and call these methods directly — the `is_internal` gate that exists specifically to require `leaf_cert == our_cert` is simply never executed because the request never passes through `only_aggregator_and_self`.

### Impact Explanation
If `client_verification=false` is used for the aggregator's deployment, the self-only protection intended for `Internal`-prefixed RPCs collapses entirely, allowing any unauthenticated caller to invoke `internal_send_tx` / `internal_get_emergency_stop_tx`. I was unable to fully verify the exact runtime behavior of `internal_send_tx`/`internal_get_emergency_stop_tx` inside `core/src/rpc/aggregator.rs` because the file (2691 lines) was truncated in my read beyond line 1000, before reaching those method implementations. Based on the visible helper `send_emergency_stop_tx` (which enqueues an attacker/caller-influenced `bitcoin::Transaction` for broadcast via `self.tx_sender.insert_try_to_send`), the risk category matches "an unauthenticated state-changing or broadcasting call," but I cannot confirm with certainty from the code I retrieved whether `internal_send_tx`'s inputs are fully attacker-controlled arbitrary transactions or constrained to system-known transaction types/IDs.

### Likelihood Explanation
This is not merely a documentation statement — `config.client_verification` is a real, code-enforced branch in `core/src/servers.rs` that determines whether `Noop` or `OnlyAggregatorAndSelf` protects the server, and the `is_internal` self-check is completely bypassed under `Noop` for every caller, with no fallback authentication layer visible in `interceptors.rs`. Exploitation requires no cost beyond reaching the aggregator's gRPC port and requires no Bitcoin transaction, deposit, or fee payment.

### Recommendation
Do not let `Internal`-prefixed method protection depend on `client_verification`. Enforce the `is_internal` self-cert check independently of the interceptor variant (e.g., always run `is_internal`/self-cert verification inside `Noop` too, or reject `Internal`-prefixed methods unconditionally unless `client_verification` is enabled), so that disabling general client TLS verification cannot silently remove the self-only boundary for internal RPCs.
