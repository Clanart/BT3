### Title
Unvalidated buffer offset in `is_atom_canonical` causes unhandled `IndexError`, crashing mempool transaction validation - ([File: chia/full_node/mempool_manager.py])

### Summary
`is_atom_canonical()` in `chia/full_node/mempool_manager.py` reads a length-prefix pattern from an attacker-supplied byte buffer and advances `offset` by up to 5 bytes to consume a multi-byte atom-length prefix, but never checks that `offset` stays within the bounds of `clvm_buffer` before indexing into it. [1](#0-0)  This is the direct analog of the xrdp bug class: a missing bounds check on an index derived from untrusted input, used to read/index a buffer. In xrdp the missing check causes a heap out-of-bounds write; in this Python code the same missing-bounds-check pattern instead causes an out-of-bounds read that Python turns into an unhandled `IndexError`, rather than memory corruption.

### Finding Description
`is_clvm_canonical()` walks a raw CLVM-serialized byte buffer (`puzzle_reveal` or `solution` bytes) token by token. For any atom whose length prefix indicates a multi-byte encoding (`0x80 < b < 0xFF`), it calls `is_atom_canonical(clvm_buffer, offset)`: [2](#0-1) 

Inside `is_atom_canonical`, `prefix_len` (0–5) is derived purely from the high bits of the byte at `offset`, and the function then loops `prefix_len` times, incrementing `offset` and indexing `clvm_buffer[offset]` each time — with no check that `offset < len(clvm_buffer)`: [3](#0-2) 

If an attacker crafts a `puzzle_reveal` or `solution` whose last byte encodes a large length-prefix pattern (e.g. `0xFC`–`0xFE` range requiring several trailing bytes) but the buffer ends before all of those trailing bytes exist, `clvm_buffer[offset]` will index past the end of the `bytes` object. In C/xrdp this class of bug is a heap OOB read/write; in Python it raises `IndexError` because `bytes.__getitem__` is bounds-checked at the interpreter level.

This function is reached directly from mempool admission: `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` and `is_clvm_canonical(bytes(coin_spend.solution))` for every coin spend in a submitted `SpendBundle`, before any other well-formedness check on those buffers: [4](#0-3)  This is called from `add_spend_bundle()`, which is the mempool-admission entry point reachable by any unprivileged peer/wallet submitting a spend bundle: [5](#0-4) 

I was unable to fully verify, within the available tooling, whether `add_spend_bundle`/`validate_spend_bundle` (or an even higher-level caller such as the RPC/full-node spend-bundle-submission path) wraps this call in a broad `try/except Exception` that would convert the `IndexError` into a benign `Err.UNKNOWN`-style rejection versus letting it propagate and crash/kill the task/queue processing that transaction. This distinction is important to the exact severity and could not be confirmed with the tools available; a Devin session with full repository access would be needed to trace the exception-handling boundary around `validate_spend_bundle` calls (e.g., in `full_node.py`'s RPC/gossip handlers) to determine whether the unhandled exception is caught generically or escapes and disrupts mempool-manager processing for other transactions.

### Impact Explanation
If the `IndexError` is not caught at some outer boundary, this is a spend-triggered exception in the mempool transaction-validation pipeline, potentially halting/crashing processing of that transaction path (denial of service against mempool admission), reachable by any unauthenticated spend-bundle submitter with a single malformed `puzzle_reveal`/`solution` buffer — no signature or valid coin state is required to reach the vulnerable code, since `is_clvm_canonical` is invoked before other spend validation. This matches the "spend-triggered transaction-processing halt" impact category. It does **not** achieve memory corruption or RCE like the original xrdp CVE, because Python bounds-checks all buffer indexing at the VM level.

### Likelihood Explanation
Likelihood of reaching the vulnerable code is high — any spend bundle submitted to the mempool (via RPC or peer gossip) invokes `is_clvm_canonical` on the raw puzzle reveal and solution bytes early in `validate_spend_bundle`. Crafting the required trailing-byte pattern (a multi-byte atom length-prefix byte placed at the very end of the buffer) is straightforward and requires no privileged access or valid signatures, only a syntactically-parseable-enough CLVM buffer up to that final atom.

### Recommendation
Add an explicit bounds check in `is_atom_canonical` before advancing `offset` and indexing `clvm_buffer`, e.g. raise/return a "not canonical" result if `offset + prefix_len >= len(clvm_buffer)` instead of relying on implicit exceptions, and audit/confirm that `is_clvm_canonical`'s callers (`validate_spend_bundle`, and any RPC ingestion paths) catch `IndexError`/`Exception` and convert it into a normal validation error rather than letting it propagate uncaught.

### Proof of Concept
Construct a `puzzle_reveal` (or `solution`) byte buffer whose CLVM serialization ends with a single byte in the `0xFC`–`0xFE`* multi-byte length-prefix range (e.g. `0xFC` implies `prefix_len = 4`, requiring 4 more trailing bytes) but provide no further bytes after it, then call:
```python
from chia.full_node.mempool_manager import is_clvm_canonical
is_clvm_canonical(b"\xfc")  # or any truncated buffer ending on such a prefix byte
```
This causes `clvm_buffer[offset]` inside `is_atom_canonical` to index past the end of the buffer and raise `IndexError`. Submitting a `SpendBundle` whose `coin_spend.puzzle_reveal` or `coin_spend.solution` bytes end this way and routing it through `MempoolManager.validate_spend_bundle` reaches the same unguarded code path. *(Note: whether this raises out to crash processing of that mempool item, or is caught and merely rejected, could not be confirmed with the tools available in this session.)*

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
