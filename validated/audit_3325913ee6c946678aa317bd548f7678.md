## Analysis

The bug‑report pattern is: an **unbounded, permissionlessly‑growable array** gets fully iterated inside a function that every "session" (epoch) must execute, so an attacker who cheaply grows the array can inflate the cost of that hot‑path function indefinitely.

Agave has a structurally identical primitive: `VoteAccounts::clone_and_filter_for_vat`.

### Title
Unbounded, permissionless growth of the in‑memory vote-accounts map inflates the cost of the mandatory epoch-boundary `clone_and_filter_for_vat` scan — ([File: vote/src/vote_account.rs])

### Summary
Any account owned by the vote program is added to the bank‑wide `Stakes::vote_accounts` map as soon as a transaction successfully writes vote-state data to it, with **no stake or authorization requirement** — only rent exemption for the account's data size. `StakesCache::check_and_store` unconditionally calls `upsert_vote_account` whenever `owner == vote_program` and the data deserializes as a valid `VoteStateVersions`, regardless of delegated stake. [1](#0-0)  At every epoch boundary, `Bank::compute_new_epoch_caches_and_rewards` unconditionally calls `clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, ...)` on the **entire, unfiltered** vote-accounts snapshot. [2](#0-1)  That function loops over `self.vote_accounts.iter()` in full — an O(n) scan over every vote account that has ever been created and not zeroed out — before any truncation to the max-accounts bound is applied. [3](#0-2) 

### Finding Description
The invariant that breaks is: "the size of the vote-accounts collection scanned every epoch is bounded by economically meaningful stake." It is not. Creating a vote account only requires the rent-exempt minimum for `VoteStateV4::size_of()` bytes (a small, fully recoverable deposit via account closure) — there is no minimum-delegation gate like the one enforced for stake accounts (`get_minimum_delegation`, 1 SOL). [4](#0-3)  Any transaction that successfully touches a vote-program account of correct size gets cached into `vote_accounts` regardless of whether stake is ever delegated to it. [1](#0-0) 

Existing guards do not stop this path:
- `clone_and_filter_for_vat` allocates `entries_to_sort` with `capacity = max_vote_accounts.min(self.vote_accounts.len())` (bounded), but the **for-loop that populates it still iterates the full, unbounded `self.vote_accounts`** before any filtering/truncation happens. [5](#0-4) 
- The BLS-pubkey/stake/balance filter inside the loop only decides whether an entry is *kept*, not whether it is *visited* — every entry, staked or not, costs a `vote_state_view()` call and multiple field reads. [6](#0-5) 
- This call is unconditional in the epoch-boundary path (`compute_new_epoch_caches_and_rewards`), i.e. it runs on every bank crossing an epoch boundary on every validator, not just under Alpenglow-specific gating. [7](#0-6) 

This mirrors the reported bug class exactly: cheap, permissionless growth of a collection ("allTokens") that a privileged/critical routine ("withdrawAllIncentives" style function) must fully traverse on a recurring basis, with no cap enforced on the traversal itself.

### Impact Explanation
Each additional junk vote account (zero-stake, no BLS key) adds a fixed per-entry cost to a computation that every validator must perform on every bank that crosses an epoch boundary. If an attacker creates a very large number of cheap, valid-sized vote accounts (bounded only by data-availability/rent cost, not by stake), the O(n) unfiltered scan in `clone_and_filter_for_vat` grows proportionally, adding avoidable latency to epoch-boundary bank creation across the fleet — a non-RPC, network-wide degradation vector that can slow block production at epoch boundaries, distinct from any single malicious peer/node assumption (the attack requires only ordinary permissionless transactions).

### Likelihood Explanation
Likelihood is bounded mainly by the rent cost of creating and maintaining many vote accounts (`VoteStateV4::size_of()` rent-exempt reserve per account), which is far cheaper than the 1 SOL minimum enforced for stake delegation. This capital requirement is recoverable (accounts can be closed), making sustained large-scale creation economically low-cost relative to its network-wide effect, though it does require non-trivial account count and continued account maintenance to keep entries alive across epochs.

### Recommendation
Filter `self.vote_accounts` by a cheap, pre-computed criterion (e.g., only consider entries that already have non-zero delegated stake or a cached "has BLS key" bit maintained incrementally at insert time) before the O(n) loop in `clone_and_filter_for_vat`, or maintain a separate bounded index of "candidate" vote accounts so the per-epoch scan cost does not grow with total vote-account count, only with staked/candidate count.

### Proof of Concept
1. Submit vote-program `CreateAccount`/`InitializeAccount` instructions to create `N` vote accounts, each funded only to the rent-exempt minimum, with no stake ever delegated to them.
2. Each successful transaction causes `Bank::update_stakes_cache` → `StakesCache::check_and_store` → `upsert_vote_account` to add the entry to `Stakes::vote_accounts`, unconditionally on stake. [8](#0-7) [1](#0-0) 
3. At the next epoch boundary, `compute_new_epoch_caches_and_rewards` calls `clone_and_filter_for_vat`, whose `for` loop visits all `N` entries before any truncation. [9](#0-8) 
4. Repeating step 1 across many transactions/epochs lets `N` grow unbounded, linearly inflating the cost of this mandatory per-epoch scan on every validator.
