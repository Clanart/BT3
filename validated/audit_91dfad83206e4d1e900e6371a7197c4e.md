### Title
Allowance wildcard collision lets assets move past `restrict-assets?`/`as-contract?` post-conditions - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`check_allowances` in `clarity/src/vm/functions/post_conditions.rs` enforces the asset-movement limits declared by `with-ft`/`with-nft` allowances inside `restrict-assets?` and `as-contract?`. When checking whether a moved fungible or non-fungible asset is covered, the function unconditionally treats any allowance entry whose `asset_name` field happens to be the literal string `"*"` as a wildcard that covers *every other asset name* under the same contract, in addition to the exact-name match.

### Finding Description
`check_allowances` builds a `ft_allowances` map keyed by the exact `AssetIdentifier` (contract + asset name) supplied to each `with-ft` call: [1](#0-0) 

Then, for every fungible asset actually moved during the protected body, the enforcement code builds a "merged" allowance list consisting of the exact-name match **plus** any allowance whose `asset_name` is the literal `"*"` under the same `contract_identifier`: [2](#0-1) 

The identical pattern is duplicated for NFTs: [3](#0-2) 

`AllowanceWithFt`/`AllowanceWithNft` do not have a distinct "wildcard" variant — the `asset_name` is just whatever ASCII string is passed as an argument to `with-ft`/`with-nft`, evaluated and converted to a `ClarityName` with no special-casing for `"*"`: [4](#0-3) 

Because the wildcard behavior is purely a side effect of matching on the string value `"*"`, and any contract can freely `define-fungible-token`/`define-non-fungible-token` an asset literally named `"*"`, an allowance that a developer writes intending to restrict exactly one asset named `"*"` (a legal, if unusual, Clarity identifier) silently becomes an allowance for **every other fungible/non-fungible asset defined in that same contract**. There is no way for the protected body's caller to declare "I mean this asset name literally, not as a wildcard" — the enforcement logic in `check_allowances` cannot distinguish the two intents.

This breaks the equality that "assets moved during a protected scope only up to the amount explicitly authorized by name." An asset that was never given its own allowance can move past the bound the developer set, purely because a differently-named, unrelated asset in the same contract happened to be allowed with `asset_name = "*"`.

### Impact Explanation
`restrict-assets?`/`as-contract?` allowances are Clarity's contract-level analog to transaction post-conditions — they are the mechanism a contract author relies on to bound how much of which asset can move in a protected scope (e.g., when a contract calls into a possibly-untrusted contract as itself, `as-contract?`). The wildcard collision lets an asset move past the amount/asset scope the post-condition/allowance was written to enforce, which matches the Critical impact category "an asset moving past its post-conditions." Any contract-controlled token contract (which fully controls its own asset names) can define an asset named `"*"` to hijack any allowance entry using that literal name and thereby move unrelated, unauthorized quantities of other tokens defined in the same contract during the protected body's execution.

### Likelihood Explanation
Exploitation requires only that (1) the protected body's asset owner/contract issues an allowance for an asset whose name happens to be `"*"` (a valid but unusual `ClarityName`), and (2) an attacker-influenced contract in the same address space defines another asset under that contract. Given `"*"` is a legal ASCII string for `asset-name`, and contract authors may pick it deliberately or by mistake (e.g. auto-generated tooling, copy-paste), the collision is straightforward to trigger without any privileged access — an ordinary contract deployer/caller can arrange it. No signer, miner, or admin privilege is required, only normal contract-call unprivileged access, matching the required threat model.

### Recommendation
Do not infer wildcard semantics from the literal string `"*"` in `asset_name`. Introduce an explicit `Allowance::FtAll { contract_identifier }` / `Allowance::NftAll { contract_identifier }` variant (analogous to the existing `Allowance::All`), created only via a dedicated native function (e.g. `with-ft-all`), and have `check_allowances` match against that discriminated variant rather than string-matching on `"*"`. This removes the ambiguity between "exact allowance for an asset literally named `*`" and "wildcard allowance for every asset in the contract."

### Proof of Concept
1. Attacker deploys `.attacker-token`, which defines two fungible tokens via `define-fungible-token`: `secret-token` (high value) and one literally named `*`.
2. A victim contract calls:
   `(as-contract? ((with-ft .attacker-token "*" u10)) (contract-call? .attacker-token transfer-both ...))`
   intending only to allow up to 10 units of the token literally named `*` to move.
3. Inside the protected body, `.attacker-token`'s `transfer-both` moves `u1000000` of `secret-token` (which has no allowance of its own) to the attacker.
4. In `check_allowances`, when the FT-movement loop processes the moved asset `secret-token`, it looks up `ft_allowances.get(secret-token)` (empty) and then `ft_allowances.get(AssetIdentifier{contract: attacker-token, asset_name: "*"})`, which returns the `u10` allowance meant only for the literal `*` asset: [5](#0-4) 
   Because `secret-token`'s moved amount is checked against this unrelated allowance entry instead of being flagged as uncovered, the transfer of `1000000` `secret-token` units is (incorrectly) allowed to pass unless it happens to also exceed `u10`, and in the “no allowance present” branch it is entirely skipped once any wildcard entry exists — moving `secret-token` past the scope the victim contract intended to restrict.

        for (asset, amount_moved) in ft_moved {
            // Build merged allowance list: exact-match entries + wildcard entries for the same contract
            let mut merged: Vec<(usize, u128)> = Vec::new();

            if let Some(allowance_vec) = ft_allowances.get(asset) {
                merged.extend(allowance_vec.iter().cloned());
            }

            if let Some(wildcard_vec) = ft_allowances.get(&AssetIdentifier {
                contract_identifier: asset.contract_identifier.clone(),
                asset_name: ClarityName::from_literal("*"),
            }) {
                merged.extend(wildcard_vec.iter().cloned());
            }

            if merged.is_empty() {
                // No allowance for this asset, any movement is a violation
                record_violation(&mut earliest_violation, MAX_ALLOWANCES as u128);
                continue;
            }

            for (index, allowance) in merged {
                if *amount_moved > allowance {
                    record_violation(&mut earliest_violation, index as u128);
                }
            }
        }
