This confirms the analog: any address can call `purchase(app, tier, months, chain)` for **any** `app`/`chain` pair — the function has no check binding the caller to the app being credited. Combined with pallet-bandwidth's hard-capped, evicting FIFO subscription list, this reproduces the OtterSec pool-DoS pattern.

### Title
Bandwidth subscription list can be griefed by third-party dust purchases that evict a victim app's paid allowance - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth` stores each `(app_chain, app)`'s prepaid bandwidth as a `BoundedVec<Subscription, MAX_SUBSCRIPTIONS>` (cap 1024) that evicts the **oldest** entry once full [1](#0-0) . `BandwidthManager.purchase()` on any EVM source chain lets **any caller** credit **any app on any chain** — the `app` and `chain` parameters are attacker-controlled and never checked against `msg.sender` [2](#0-1) . An attacker can therefore buy the cheapest configured tier in bulk against a victim `(chain, app)` key to fill the 1024-slot FIFO with worthless subscriptions, evicting the victim's legitimately purchased, still-unconsumed allowance.

### Finding Description
`push_subscription` appends every new purchase to the FIFO and, once the list is at `MAX_SUBSCRIPTIONS` (1024), unconditionally evicts index 0 (the oldest) to make room, regardless of how much unused `remaining_bytes` that entry still holds [3](#0-2) . The pallet's `on_accept` credits based solely on `request.from` matching the registered `BandwidthManager` for the source chain — it does not check that the payer is the app owner, nor does it enforce any relationship between the buyer and the `app`/`chain` fields decoded from the purchase body (this is the documented "sponsorship" feature) [4](#0-3) .

On the EVM side, `BandwidthManager.purchase()` takes `app` and `chain` as plain calldata arguments with zero ownership check, only requiring `tierPrice[tier] != 0` and `months > 0` [5](#0-4) . This is structurally identical to the reported bug: a hard-capped list (`MAX_NUMBER_OF_DELEGATIONS` ≈ `MAX_SUBSCRIPTIONS`), fillable by anyone with a small qualifying deposit (cheapest tier ≈ dust delegation), used to push out a legitimate, already-committed entry before it is consumed.

### Impact Explanation
An app that has pre-paid for a large tier (e.g., the $1000/8MB tier) can have its remaining, unconsumed byte allowance wiped out before use: an attacker repeatedly calls `purchase()` against that same `(chain, app)` key with the cheapest tier and `months = 1`, appending 1024 low-value entries and evicting the victim's high-value, still-live subscription along with `SubscriptionEvicted { lost_bytes }` [6](#0-5) . This is a direct loss of prepaid funds for the victim app (paid bytes become permanently unusable) and can also be used to fully block a victim app's cross-chain messaging (`GateError::NoAllowance`/`Insufficient`) once its real subscription is evicted, denying the ISMP router's bandwidth check for legitimate traffic.

### Likelihood Explanation
The attack requires only an unprivileged EVM account with fee-token balance for the cheapest tier repeated up to 1024 times — no relayer, prover, admin, or governance role is needed, and the `app`/`chain` fields are fully attacker-chosen calldata. The cost scales with `cheapest_tier_price × 1024`, which is bounded and can be made cheap by governance's own tier pricing (the manager only rejects a zero-priced tier, not a "too cheap" one) [7](#0-6) . Given the sponsorship feature is intentional and documented, this is a realistic griefing vector against any competitor or targeted app whose `(chain, app)` identity is public (it is emitted in `BandwidthCredited`/`BandwidthConsumed` events).

### Recommendation
Do not let an unrelated payer silently displace another payer's live, unconsumed subscription. Options: (1) bound eviction to same-payer entries only, or track `paid_from` and refuse eviction of subscriptions with different payer/tier provenance while the cap is reached from a *different* payer; (2) coalesce/aggregate same-tier repurchases instead of queuing unbounded near-duplicate entries, removing the incentive to spam-buy the cheapest tier; (3) enforce a minimum tier price floor and/or per-caller rate limiting on `purchase()` for a given `(chain, app)` to make dust-filling economically and functionally ineffective; (4) prefer evicting the entry with the least remaining value/soonest expiry rather than strict FIFO-oldest, so a fresh legitimate large purchase cannot be trivially displaced by many cheap ones.

### Proof of Concept
1. Governance configures `Tier::TierOne` with a low price (e.g., $50/100KB) and a larger tier (`TierFour`, $1000/8MB) on `pallet-bandwidth` and registers a `BandwidthManager` for source chain `EVM-X`.
2. Victim's app buys `TierFour` for itself, crediting `(app_chain, app)` with a large `remaining_bytes` entry that is not yet fully drained.
3. Attacker, from any unrelated EOA on `EVM-X`, calls `BandwidthManager.purchase(app = victimAppBytes, tier = TierOne, months = 1, chain = victimAppChain)` 1024 times (`app`/`chain` are free-form calldata, no ownership check) [2](#0-1) .
4. Each purchase message lands on `pallet-bandwidth::on_accept`, which appends a new `Subscription` via `push_subscription`; once the FIFO reaches 1024 entries, the victim's `TierFour` subscription (the oldest, if the attacker starts before other purchases, or simply once it ages to the front) is evicted, emitting `SubscriptionEvicted { lost_bytes }` with the victim's still-large `remaining_bytes` [8](#0-7) .
5. The victim's app now has its prepaid bandwidth destroyed (funds loss) and/or its gate calls start failing with `GateError::Insufficient`/`NoAllowance` [9](#0-8) , denying legitimate message dispatch.

```rust
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
```

```text
### Purchase messages skip the gate

The router uses `Pallet::is_purchase_message(request)` to identify a purchase from a registered manager (`request.source` is managed _and_ `request.from` matches the registered manager address). Purchase messages bypass the gate — otherwise a depleted app couldn't ever recharge.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```
