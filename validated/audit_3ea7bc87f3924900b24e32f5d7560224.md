## Title
Stale `manualResolutions` map survives across unrelated merge/rebase instances, causing silent auto-application of a prior "ours/theirs" choice to attacker-controlled conflict content - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` in `app/src/lib/stores/updates/changes-state.ts` carries forward the entire `manualResolutions: Map<string, ManualConflictResolution>` from the previous `conflictState` into the next one whenever a `conflictState` object already exists, **without verifying that the new conflict is actually a continuation of the same merge/rebase**. The only signal used to decide whether to "reset" anything is a branch-name/tip comparison used purely for **stats counters** (`mergeAbortedAfterConflictsCount` / `mergeSuccessAfterConflictsCount`) - it never clears `manualResolutions`. When the user later finishes the merge, `createMergeCommit` (`app/src/lib/git/commit.ts`) blindly re-applies any resolution keyed by file `path` to whatever file with that path exists in the *current* working directory, regardless of which merge produced it.

### Finding Description
`updateConflictState` computes the resolutions to carry into the new state purely based on whether *any* previous conflict state existed: [1](#0-0) 

`performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange` detect a branch-name change (meaning the prior merge was aborted and a **different** merge/rebase has begun) but only increment a stats counter — they do not clear or invalidate the `manualResolutions` map that was already threaded through `getConflictState`: [2](#0-1) 

This is confirmed by the unit test suite, which explicitly asserts that resolutions are "preserved" across branch changes, only tracking abort/success stats as a side note: [3](#0-2) 

The `manualResolutions` map is keyed **only by file path** — there is no binding to the merge's `currentTip`/`MERGE_HEAD`/source branch. When the merge is eventually finished, `createMergeCommit` looks up each path in this map and unconditionally re-applies the stored resolution to whatever conflicted file currently exists at that path: [4](#0-3) 

`stageManualConflictResolution` then runs `git checkout --theirs/--ours` and `git add`/`git rm` against the **current** conflict markers for that path — i.e. whatever content the new (potentially attacker-controlled) merge introduced — without any fresh user confirmation: [5](#0-4) 

In the UI, the conflicts dialog reads the resolution straight from `manualResolutions.get(f.path)` to render the file as already resolved: [6](#0-5) 

### Impact Explanation
This breaks the invariant that a manual conflict resolution decision only applies to the specific merge/commit pair the user reviewed it for. An attacker who controls a fetched branch/PR (e.g., force-pushes new content to a branch a victim is merging, or supplies a crafted branch with a conflicting path matching one the victim previously resolved in an aborted merge) can cause the victim's earlier "accept theirs" choice to be silently reapplied to the attacker's new content on the next merge attempt involving the same file path. Because the file is displayed as already resolved, the user is not prompted to review the diff again before clicking "Continue merge", so `createMergeCommit` stages and commits the attacker-controlled content without further review — silently corrupting what the user commits/pushes.

### Likelihood Explanation
Requires a specific but realistic sequence: user starts a merge/rebase with conflicts, manually resolves at least one file as "theirs", aborts (or the state otherwise transitions to a different branch/tip while `conflictState` remains non-null), and then starts a new merge/rebase involving the same file path before the state is fully reset (e.g., quickly retrying after `abortMerge`, or resolving conflicts across a rebase spanning multiple commits touching the same path). Because `IRepositoryState` is cached per-repository and `conflictState` is not cleared to `null` in between unless git itself reports no `MERGE_HEAD`/`REBASE_HEAD`, this window is plausible in normal user workflows around iterative rebases and repeated merge attempts against attacker-controlled remotes.

### Recommendation
Bind `manualResolutions` (and any state derived from it) to an identity for the specific merge/rebase instance (e.g., `MERGE_HEAD`/`currentTip` and the `theirBranch`/source commit), and clear the map whenever `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange` detect the branch/tip has changed rather than only incrementing a stats counter. Additionally, `createMergeCommit`/`stageManualConflictResolution` should re-validate that a stored resolution still corresponds to the same conflicting blobs (or at least require the file to still be flagged for the same conflict entry) before silently applying it.

### Proof of Concept
1. Victim starts `git merge attacker-branch` against a repo whose remote is attacker-controlled; file `shared.txt` conflicts.
2. Victim manually resolves `shared.txt` as "theirs" in Desktop's Conflicts dialog (`_updateManualConflictResolution` stores `manualResolutions.set('shared.txt', theirs)`).
3. Victim aborts the merge (`dispatcher.abortMerge`) before continuing — `conflictState` transitions but, per `updateConflictState`, `manualResolutions` for `shared.txt` is retained if a new conflict state is derived before `conflictState` collapses to `null`.
4. Attacker updates `attacker-branch` (force-push) with different, malicious content in `shared.txt`.
5. Victim re-merges `attacker-branch`; `shared.txt` conflicts again. Because `manualResolutions` already contains `shared.txt -> theirs`, the Conflicts dialog shows it as already resolved.
6. Victim clicks "Continue merge" without reviewing `shared.txt` again; `_finishConflictedMerge` → `createMergeCommit` calls `stageManualConflictResolution(repository, file, ManualConflictResolution.theirs)`, running `git checkout --theirs -- shared.txt; git add shared.txt`, silently staging and committing the attacker's new malicious content.

function performEffectsForMergeStateChange(
  prevConflictState: MergeConflictState | null,
  newConflictState: MergeConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
): void {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.currentBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.currentBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the merge must have been aborted
  if (branchNameChanged) {
    statsStore.increment('mergeAbortedAfterConflictsCount')
    return
  }

  const { currentTip } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null
  ) {
    const previousTip = prevConflictState.currentTip

    if (previousTip !== currentTip) {
      statsStore.increment('mergeSuccessAfterConflictsCount')
    } else {
      statsStore.increment('mergeAbortedAfterConflictsCount')
    }
  }
}

export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`

    }
  }

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
