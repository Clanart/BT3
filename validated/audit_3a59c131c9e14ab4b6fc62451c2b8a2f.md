### Title
`ReceivedOutput::read` deserializes unauthenticated output data with no consistency check between the spend-offset, the claimed `TxOut`, and the `OutPoint`, allowing forged "received" outputs that the threshold key cannot spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The report's bug class is trusting bytes obtained from an unauthenticated source without an integrity/authenticity check (an executable downloaded over plaintext HTTP and executed). In `bitcoin-serai`, `ReceivedOutput::read` plays the analogous role: it ingests raw, unauthenticated bytes claiming to represent a spendable received output — a spend-offset scalar, a `TxOut`, and an `OutPoint` — and returns a `ReceivedOutput` that downstream spend logic treats as a real, spendable UTXO. No check binds the offset to the output's script key, or the outpoint to a real chain output, so tampered or fabricated input bytes produce `ReceivedOutput`s that are structurally valid yet unspendable or fraudulent.

### Finding Description
`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` reads three independent, unauthenticated fields:

- `offset` via `Secp256k1::read_F(r)` — the scalar added to the scanner's key to derive the spending key.
- `output` via `TxOut::consensus_decode` — the claimed value and script_pubkey.
- `outpoint` via `OutPoint::consensus_decode` — the claimed funding position.

It then returns `ReceivedOutput { offset, output, outpoint }` unconditionally (`networks/bitcoin/src/wallet/mod.rs`, lines 122-134). There is no verification that `output.script_pubkey` is the P2TR script for `key + offset*G` (the invariant `Scanner::scan_transaction` enforces on the honest path by looking up `self.scripts.get(&output.script_pubkey)`, lines 199-214), and no authenticity tag binds the fields together. An attacker who can supply or modify the serialized bytes — e.g., a man-in-the-middle on the channel carrying scanned outputs, or a hostile data source — can:

1. Swap in a `TxOut` paying to an arbitrary script while keeping a valid offset: the output is reported received at a claimed `value()`, but no key the threshold group holds can spend it.
2. Pair a real script with a mismatched `offset`: the derived signing key does not control the output, so the spend signature is invalid.
3. Inflate `output.value`: downstream fee/change computation in `send.rs` then over-estimates available funds.

This is the Serai-shaped analog of the HTTP-download flaw: unauthenticated fetched data is consumed as authoritative without any integrity binding.

### Impact Explanation
`ReceivedOutput`s feed the spend path (`send.rs`), which selects inputs, computes fees, and produces a transaction the threshold group signs. A forged or tampered `ReceivedOutput` causes funds to be reported as received when they are not spendable by the group's key, or causes the group to sign a transaction spending an outpoint it does not control / with a wrong value, producing an invalid or loss-making transaction. In the inflation case, fee/change math is computed against a fictitious input value. This matches the acceptance criterion "funds reported received that are not spendable" and can deadlock treasury funds until the bad input is identified and excluded.

### Likelihood Explanation
Reachable by any party able to supply the bytes passed to `ReceivedOutput::read` — the deserialization boundary is explicitly an untrusted-input surface (the same class as `read_F`/`ThresholdKeys::read` consumers). Unlike an on-chain path, this requires no mining or consensus influence, only a privileged position over, or compromise of, the channel carrying scanned output data — the same privileged-network-position requirement as the original advisory. Severity Medium: requires that channel position and does not directly leak key material, but reliably misreports funds and DoSes/misdirects the spend pipeline.

### Recommendation
Authenticate `ReceivedOutput` at the read boundary: after `TxOut::consensus_decode`, recompute the expected P2TR script from `key + offset*G` (or store/re-derive via `Scanner`) and reject inputs where `output.script_pubkey` does not match; additionally have the caller verify the `outpoint`/`TxOut` against chain data before use. Where serialized `ReceivedOutput`s cross a trust boundary, wrap them in an authenticated channel (MAC/signature) rather than raw `serialize()`/`read()`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs behavior, attacker-controlled bytes:
let mut forged = Vec::new();
// Offset chosen to be valid scalar, e.g. ZERO (honest-looking)
forged.extend(Scalar::ZERO.to_bytes());
// A TxOut paying to an attacker's script_pubkey with an inflated value
forged.extend(serialize(&TxOut {
    value: Amount::from_sat(1_000_000_000),
    script_pubkey: attacker_script, // not key + offset*G
}));
forged.extend(serialize(&OutPoint::null()));
let ro = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
// read() succeeds; ro.value() reports 10 BTC "received",
// yet no offset-derived key controls attacker_script -> unspendable.
```
`read()` returns `Ok` because lines 122-133 perform no script-vs-offset or chain-membership check; `Scanner::scan_transaction` (lines 199-214) is the only code enforcing the offset↔script binding, and `read()` bypasses it entirely.
