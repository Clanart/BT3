### Title
Unhandled `URI::InvalidURIError` on malformed `host` param crashes public `/auth/shopify/callback` route - (File: `app/controllers/shopify_app/callback_controller.rb`)

### Summary
`CallbackController#redirect_to_app` calls `deduced_phishing_attack?`, which calls `URI(decoded_host).host` on a value derived directly from the attacker-controlled `host` request parameter. Unlike the parallel logic in `ShopifyApp::EmbeddedApp#safe_embedded_app_url`, which explicitly validates the decoded host for unsafe characters (`unsafe_embedded_host_characters?`) before parsing, the callback controller performs no such sanitation, so a malformed `host` value can raise `URI::InvalidURIError` outside of any `rescue` block.

### Finding Description
The OAuth callback flow is:
`callback` → (on success) → `redirect_to_app` → `deduced_phishing_attack?` → `decoded_host` [1](#0-0) 

- `decoded_host` returns `ShopifyAPI::Auth.embedded_app_url(params[:host])` — a value built directly from the attacker-supplied `host` param, with no validation performed inside `shopify_app` itself. [2](#0-1) 
- `deduced_phishing_attack?` then calls Ruby's stdlib `URI(decoded_host).host` directly, with no rescue for `URI::InvalidURIError`. [3](#0-2) 

The only exception handling in the `callback` action wraps `validated_auth_objects` (the OAuth code/state/hmac validation step), not the subsequent `redirect_to_app` call: [4](#0-3) . Once OAuth validation succeeds (which an attacker can trigger themselves for their own shop, controlling all params including `host`), execution reaches `redirect_to_app` unguarded.

By contrast, the sibling implementation in `ShopifyApp::EmbeddedApp#safe_embedded_app_url` explicitly screens the decoded host for empty/invalid encoding, control characters, backslashes, and `@` before treating it as a domain: [5](#0-4) . `CallbackController` has no equivalent screening before calling `URI()`, so it relies entirely on `ShopifyAPI::Auth.embedded_app_url` (external gem, not present in this repo) to produce a URI-parseable string. Whether that external method fully sanitizes all invalid-URI byte sequences (e.g., raw spaces, backslashes, control characters, malformed percent-encoding) cannot be confirmed from this repository's code, since `embedded_app_url` is not implemented here — this is the one point of uncertainty in this analysis.

Existing safeguards (`ShopifyApp::Utils.sanitize_shop_domain`, HMAC/state validation in `validated_auth_objects`) do not protect this specific call site: `sanitize_shop_domain` is only invoked after `URI(decoded_host).host` has already succeeded, and HMAC/state validation has nothing to do with the `host` param's format.

### Impact Explanation
If `URI(decoded_host).host` raises, the exception is unhandled and propagates out of the `callback` action on the public, unauthenticated `/auth/shopify/callback` route, producing a 500 error (and, depending on host app's Rails exception-handling configuration, a stack trace) instead of the intended silent redirect to `ShopifyApp.configuration.root_url`. This is a scoped denial-of-service / error-disclosure issue confined to this single route and request, not a data-access, session, or token compromise — closest match is Shopify's "Denial of Service" impact class, which is typically low severity for single-request crashes.

### Likelihood Explanation
Reaching this code requires only that OAuth validation in `validated_auth_objects` succeed, which an attacker can trivially arrange by running the standard OAuth flow against their own shop/app install and then substituting a malformed `host` value in the final callback request. No victim interaction, secrets, or elevated privileges are needed, making this fully attacker-controlled and repeatable — contingent only on `ShopifyAPI::Auth.embedded_app_url` passing through a string that Ruby's `URI()` parser rejects, which could not be fully verified since that method's implementation is outside this repo.

### Recommendation
Wrap the `URI(decoded_host)` call in `deduced_phishing_attack?` in a rescue for `URI::InvalidURIError` (treating a parse failure the same as `sanitized_host.nil?`, i.e., redirect to root), mirroring the defensive character/encoding checks already present in `ShopifyApp::EmbeddedApp#unsafe_embedded_host?`.

    def safe_embedded_app_url(host)
      decoded_host = Base64.decode64(host.to_s)
      return if deduced_phishing_attack?(decoded_host)

      ShopifyAPI::Auth.embedded_app_url(Base64.strict_encode64(decoded_host))
    end

    def deduced_phishing_attack?(decoded_host)
      sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(decoded_host) unless unsafe_embedded_host?(decoded_host)
      if sanitized_host.nil?
        message = "Host param for redirect to embed app in admin is not from a trusted domain, " \
          "redirecting to root as this is likely a phishing attack."
        ShopifyApp::Logger.info(message)
      end
      sanitized_host.nil?
    end

    def unsafe_embedded_host?(decoded_host)
      return true if decoded_host.empty? || !decoded_host.valid_encoding?
      return true if unsafe_embedded_host_characters?(decoded_host)

      embedded_host_authority(decoded_host).include?("@")
    end

    def unsafe_embedded_host_characters?(decoded_host)
      decoded_host.each_char.any? do |character|
        character_code = character.ord
        character_code <= 0x20 || character_code == 0x7f || character == "\\"
      end
    end
