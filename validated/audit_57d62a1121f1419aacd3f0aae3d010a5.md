### Title
Bridge value transfer permanently stuck if `handleKLAYTransfer`/`handleERC20Transfer` reverts due to attacker-controlled `_to` recipient - (File: contracts/service_chain/bridge/BridgeTransferKLAY.sol)

### Summary
The Kaia service-chain bridge's `_requestKLAYTransfer`/`requestERC20Transfer` functions let an unprivileged caller pick an arbitrary `_to` recipient address on the counterpart chain. The finalization functions `handleKLAYTransfer` and `handleERC20Transfer` push value to `_to` and `require()` the transfer to succeed, with no fallback/refund path if `_to` cannot receive funds. If `_to` is a contract that reverts on receipt (or a token that blocks transfers to `_to`), the finalize call reverts every time it is attempted, permanently locking the user's funds with no recovery mechanism on either chain — the same root cause as the referenced Optimism `finalizeDeposit()` bug.

### Finding Description
`requestKLAYTransfer` accepts a user-supplied `_to` and emits `RequestValueTransfer` after taking custody of the funds/fee on the source-chain bridge: [1](#0-0) 

Bridge operators later call `handleKLAYTransfer` on the counterpart bridge to push the value to `_to`. This call performs a low-level call and reverts the whole finalize transaction if the transfer fails: [2](#0-1) 

Specifically: [3](#0-2) 

The equivalent ERC20 path has the same structure — `_to` is fully attacker-controlled at request time, and `handleERC20Transfer` requires the mint/transfer to succeed or reverts: [4](#0-3) 

If `_to` is:
- a contract with no `payable` fallback or one that unconditionally reverts (KLAY case), or
- an address blacklisted by, or otherwise rejected by, the ERC20 token contract, or a contract that reverts on `mint`/`transfer` (ERC20 case),

then every attempt by every operator to call `handleKLAYTransfer`/`handleERC20Transfer` for that specific `_requestedNonce` will revert. There is no code path anywhere in `BridgeTransfer.sol`, `BridgeTransferKLAY.sol`, or `BridgeTransferERC20.sol` that refunds the request back to the source-chain sender, retries with a different recipient, or allows the stuck request to be skipped and finalized to an alternate address. Once the funds have been burned/locked on the source chain via `_requestKLAYTransfer`/`_requestERC20Transfer` (and burned in mint/burn mode), they cannot be returned.

Additionally, since votes are keyed per nonce with `_voteValueTransfer`/`_lowerHandleNonceCheck`, and `lowerHandleNonce`/`_updateHandleNonce` advance the handled-nonce window contiguously from `lowerHandleNonce`: [5](#0-4) 

a permanently-failing nonce also prevents `lowerHandleNonce` from advancing past it, which can additionally impact bookkeeping/pruning of `handleNoncesToBlockNums` for that nonce and subsequent nonces beyond the 200-nonce window, though the primary and clearest impact is the stuck user funds for that specific request.

### Impact Explanation
An unprivileged transaction sender (any user calling `requestKLAYTransfer`, the bridge's payable fallback, or `requestERC20Transfer`/`onERC20Received`) can, by mistake or intentionally (e.g. to grief themselves or as part of a more complex attack against a service that relies on the bridge), set `_to` to an address that cannot receive the transferred asset. Once the corresponding source-chain deduction has occurred, the funds are permanently unrecoverable, since neither bridge contract provides any mechanism to reclaim or redirect handled-but-failing requests. This is direct, unauthorized-in-effect loss/lock of user value with no way to recover it — matching the "Medium" severity of the original report (funds get stuck in the bridge, not stolen by a third party, but irrecoverably lost to the depositor).

### Likelihood Explanation
Likelihood is moderate: this requires either user error (a mistyped/incompatible `_to`, e.g., pointing to a non-payable contract, a multisig without a receive function, or a token-gated/blacklisted address) or a deliberate griefing setup. Because `_to` is fully user-supplied and unchecked for receive-capability at request time (`_requestKLAYTransfer`/`_requestERC20Transfer` perform no validation of `_to`), this is trivially reachable by any caller in a single transaction, with no special privileges or timing needed.

### Recommendation
Add a callback/refund mechanism analogous to Optimism's `L2StandardBridge`: if `handleKLAYTransfer`/`handleERC20Transfer` fails to deliver funds to `_to`, do not unconditionally revert; instead, either (a) hold the funds in an escrow within the destination-chain bridge that `_to`/`_from` can later `claim()`, or (b) emit a definitive failure event and route the value back to the counterpart bridge/`_from` via a compensating "handle transfer failed" request, so that funds are never left irrecoverably stuck due to a non-receiving `_to`.

### Proof of Concept
1. On the source chain, user (or attacker as their own victim) calls `bridge.requestKLAYTransfer(maliciousContractAddr, value, "0x", {value: value + fee})` where `maliciousContractAddr` is a contract with a `receive`/`fallback` that always reverts (or simply a contract with no payable fallback at all). [6](#0-5) 
2. This deducts KLAY from the sender and (in mint/burn mode) burns it on the source chain; the request emits `RequestValueTransfer` with `to = maliciousContractAddr`.
3. On the destination chain, an operator calls `handleKLAYTransfer(txHash, from, maliciousContractAddr, value, requestedNonce, blockNumber, extraData)`.
4. `_to.call.value(_value)("")` fails because the receiving contract reverts; `require(ok, "handleKLAYTransfer: transfer failed")` reverts the entire finalize transaction. [3](#0-2) 
5. Every operator retry for this same `requestedNonce` reverts identically — there is no alternative code path to redirect or refund the value. The user's KLAY is permanently unrecoverable.

Note: I was not able to fully verify whether the current mainnet/system contracts (as opposed to this `service_chain` bridge module) still actively use this exact bridge contract in production, since the codebase index may not include full deployment/registry wiring for this legacy service-chain bridge; if precise confirmation of current production usage is needed, a full repository clone/build (e.g., via a Devin session) would be required.

        if (_requestedNonce > upperHandleNonce) {

        if (limit > upperHandleNonce) {
