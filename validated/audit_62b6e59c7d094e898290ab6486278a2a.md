### Title
`ReceivedOutput::read` deserializes `offset`, `TxOut`, and `OutPoint` without validating the offset-to-script binding or output authenticity - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` reconstructs a "spendable output" from three attacker-controlled fields — an `offset` scalar, a `TxOut`, and an `OutPoint` — performing only canonical-decoding checks. It never verifies that `output.script_pubkey == p2tr_script_buf(scanner_key + GENERATOR * offset)`, nor that the claimed `outpoint`/`value` correspond to a real, unspent chain output. This is the same class as the referenced finding: a multi-field value returned by an external party is consumed while ignoring the fields that would authenticate it.

### Finding Description
`ReceivedOutput` is the type Serai uses to represent funds belonging to the FROST group key, and its `read` function is a documented sink for untrusted bytes (peer-relayed output claims). The reader does:

```rust
let offset = Secp256k1::read_F(r)?;          // canonical scalar only
output   = TxOut::consensus_decode(...)?;    // well-formedness only
outpoint = OutPoint::consensus_decode(...)?; // well-formedness only
```

(see `networks/bitcoin/src/wallet/mod.rs:122-134`).

By contrast, the trusted producer path `Scanner::scan_transaction` only yields outputs whose `script_pubkey` was found in `self.scripts` (the map keyed by `p2tr_script_buf(key + G*offset)`, `mod.rs:185` and `mod.rs:205`). The `read` path skips this entire binding check and also skips any confirmation that `outpoint` exists or that `output.value` is real.

The only downstream validation is in `SignableTransaction::multisig` (`send.rs:277`), which checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`. An attacker can trivially satisfy this: the group key is public, so for any chosen `offset` they can compute the matching P2TR script themselves and place it in the forged `TxOut`. What cannot be satisfied — but is never checked — is whether the claimed `outpoint` actually exists on-chain carrying that value, because `TransactionSignMachine::sign` commits to `Prevouts::All(&self.tx.prevouts)` (`send.rs:375`), i.e., it signs over the *claimed* prevout amounts.

### Impact Explanation
An unprivileged party able to relay `ReceivedOutput` bytes can cause the signing set to:

1. Treat non-existent or non-spendable outputs as received funds ("funds reported received that are not spendable"), corrupting balance/accounting for the vault.
2. Fabricate an inflated `output.value` on a correctly-scripted (attacker-computed) `TxOut` with a fake `outpoint`. Since the sighash commits to `Prevouts::All`, the group produces a valid BIP-340 signature for a transaction that is invalid on-chain — or, when mixed with real inputs, a transaction whose fee/change math is computed against phantom input value.
3. Point the `outpoint` at a real output that pays to someone else entirely while claiming a matching script in the `TxOut` copy — the signature commits to the supplied `TxOut` value, not the chain truth, producing spends the network rejects or that drain fees.

This matches the accepted impact of reported-but-unspendable funds and incorrect value commitment.

### Likelihood Explanation
Any peer/coordinator component relaying serialized outputs can inject bytes; no key material or collusion is needed. Crafting a passing `TxOut` requires only the public group key (`p2tr_script_buf(key + G*offset)`). The `multisig` check gives a false sense of validation while leaving `value` and `outpoint` unauthenticated.

### Recommendation
Bind `ReceivedOutput` to the scanner's key at deserialization or first use: require the reader to take the base `ProjectivePoint` (or the `Scanner`) and enforce `self.scripts`/`p2tr_script_buf(key + G*offset) == output.script_pubkey`. More importantly, do not treat `read` outputs as confirmed funds — require an RPC/chain lookup that `outpoint` resolves to an unspent output whose `script_pubkey` and `value` equal the claimed `TxOut` before feeding it into `SignableTransaction::new`, mirroring the fix of validating all returned fields rather than trusting them.

### Proof of Concept
```rust
// key: the group's tweaked ThresholdKeys<Secp256k1> group_key (public)
let offset = Scalar::ONE; // any scalar
// Attacker computes a script that WILL pass SignableTransaction::multisig's check
let script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset)).unwrap();

let forged = ReceivedOutput {
    offset,
    output: TxOut {
        value: Amount::from_sat(1_000_000_000), // phantom value
        script_pubkey: script,
    },
    outpoint: OutPoint::null(), // references nothing on-chain
};
let bytes = forged.serialize();

// Deserialization succeeds — no offset/script binding or outpoint check
let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// SignableTransaction::new accepts it, crediting 10 BTC of fake input value;
// multisig()'s script check passes because the attacker derived `script`
// from the public key; the resulting signature commits via Prevouts::All
// to the fabricated prevout amount.
```
