### Title
Out-of-range `sender`/`recipient` indexes cause panic in PedPoP blame evaluation due to missing existence check before map indexing - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame()` / `AdditionalBlameMachine::blame()` accept caller-supplied `sender` and `recipient` `Participant` indexes and pass them to `blame_internal()`, which indexes `self.commitments[&sender]` without first checking that `sender` actually exists in the commitments map. This mirrors the reported bug class: `getWithdrawRequestValue()` iterated all pool tokens and required a withdraw request to exist for each, reverting on the token for which `initiateWithdraw()` had skipped creating one. Here, the commitments map is built only for participants `1..=n`, yet the blame path assumes any supplied `Participant` is present — the same "skip on creation, require on iteration" gap.

### Finding Description
`AdditionalBlameMachine::new` populates `commitments` exclusively for participants `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs:656-660`). `BlameMachine` produced by `KeyMachine::calculate_share` similarly only contains entries for the protocol's participants (`crypto/dkg/pedpop/src/lib.rs:512-521`).

`blame()` forwards attacker-influenced arguments into `blame_internal()` (`crypto/dkg/pedpop/src/lib.rs:623-632`, `674-682`), which executes:

- `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` (`:582`), and
- `&self.commitments[&sender]` inside `share_verification_statements` (`:599`).

`Participant::new` only enforces non-zero; any value `> n` is representable. A `sender` not among `1..=n` causes `HashMap` index panic on `self.commitments[&sender]`. There is no `MissingParticipant`/`InvalidParticipant` check before use — the exact same shape as the LP bug, where a missing entry was only discovered by an unconditional `require(hasRequest)` deep in a later iteration. `validate_map` exists in this crate (`:57-83`) precisely to check existence before iteration, and it is correctly used in `verify_r1` (`:305`) and `calculate_share` (`:468`), but the blame path never validates `sender`/`recipient` membership.

The `AdditionalBlameMachine::new` documentation only states that commitment *messages* must be valid and authenticated; it does not constrain the `sender`/`recipient` indexes passed to `blame()`. In Serai's deployment, blame accusations originate from counterparty messages (the coordinator resolves a `faulty` participant from an `InvalidCommitments`/`InvalidShare` processor message), so the index is influenced by an unprivileged counterparty's claim.

### Impact Explanation
Any node evaluating a blame accusation panics if the accusation references a participant index outside `1..=n`. In an integrated deployment (coordinator/processor evaluating DKG blame over tributary messages), a malicious or malformed accusation referencing an out-of-range `sender` crashes the blame-evaluation path on every honest node that processes it, stalling fault adjudication for the DKG attempt — the analog of `price()` reverting for the affected account and every function depending on it. Severity: Medium (reachable panic/DoS from counterparty-supplied protocol input; no secret leakage or forgery).

### Likelihood Explanation
A `Participant` index is attacker-influenceable: it is derived from the accused party claimed in a blame/share-invalid message. An unprivileged protocol participant can claim fault against a fabricated participant index (e.g., `n + 1`). No cryptographic break is needed — the panic is reachable purely by supplying an index the commitments map never contained, just as the LP report only required a zero exit balance to leave a gap that a later unconditional lookup tripped over.

### Recommendation
In `blame_internal` (and the `AdditionalBlameMachine::blame` wrapper), validate `sender` and `recipient` against the commitments map before use — check `self.commitments.contains_key(&sender)` and that `recipient` is a valid participant index (`<= n`), returning a defined error or identifying the accusing party as faulty rather than panicking on `self.commitments[&sender]`.

### Proof of Concept
```rust
// Build a completed AdditionalBlameMachine for n participants with valid
// commitment messages (as an observer of a real DKG would have).
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// Attacker-controlled accusation referencing a participant that was never in the DKG.
let bogus = Participant::new(n + 1).unwrap();

// Panics at crypto/dkg/pedpop/src/lib.rs:599 on `self.commitments[&sender]`
// after decrypt_with_proof is attempted; with a validly-signed msg for a real
// sender the panic is deterministic. Even the InvalidSignature early-return path
// is unreachable-sender-agnostic once a signed msg exists, and the second
// commitments[&sender] index at :599 panics unconditionally for bogus sender.
machine.blame(bogus, honest_recipient, msg, proof);
```
Note: the `Err(DecryptionError::InvalidSignature) => return sender` early return at `:585` fires first if no validly-signed `EncryptedMessage` can be produced for `bogus`; however any caller that reaches `blame_internal` with a syntactically registered-but-absent sender (or via `BlameMachine` where commitments only cover `1..=n`) hits the unconditional index at `:599`. I was unable to fully trace `decrypt_with_proof`/`encryption.register` in `crypto/dkg/pedpop/src/encryption.rs` within this session, so whether the ECDH step itself dereferences a per-participant key that would panic earlier is unverified — if it does, the same missing-existence-check class applies one step earlier rather than at `:599`.
