### Title
Permanent Loss of IBC-Transferred Funds When a Destination `dest_callback` Contract Fails to Fully Drain the Isolated Address - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
The `IBCReceivePacketCallback` function mints/unescrows the ICS-20 transfer amount to a deterministically derived "isolated address" *before* invoking the destination contract's callback, then attempts to have the contract pull the full amount via `approve` + arbitrary calldata. If the callback fails to withdraw every unit of the transferred token (bad contract logic, revert, insufficient gas, rounding, or simply a contract that doesn't implement the expected `transferFrom` pattern), the function returns an error — but this is analogous to the `dropMessage`/`onDropMessage` bug class: there is no fallback path to return the tokens to the original sender, and the isolated address has no private key or recovery mechanism, so the tokens become permanently unspendable.

### Finding Description
`IBCReceivePacketCallback` in [1](#0-0)  computes a receiver address via `types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)`, defined in [2](#0-1)  as `sdk.AccAddress(address.Module(ModuleName, []byte(channelID), []byte(sender))[:20])`. This is a hash-derived module-style address with no associated private key — nobody can ever sign a transaction from it.

The underlying ICS-20 transfer application (ibc-go's transfer/erc20 middleware) mints or unescrows the transferred coin to this isolated address as part of normal `OnRecvPacket` processing, independent of whether the subsequent callback succeeds (confirmed by the test comment "the packet that failed conversion ... will be in the isolated address used to invoke the callback" in [3](#0-2) ).

The callback then does:
1. `approve(contractAddr, amount)` from the isolated address at [4](#0-3) .
2. `writeFn()` commits these cached-context EVM state changes at [5](#0-4)  — **before** verifying success.
3. Only afterward does it check `receiverTokenBalance` and return an error if nonzero at [6](#0-5) .

Because the state (approval + partial/failed calldata execution) is already written via `writeFn()` prior to the sufficiency check, and because the isolated address has no controlling key, any amount left behind in the isolated address after a failed or incomplete callback is permanently unspendable — there is no code path anywhere in the module, `x/erc20`, or `x/bank` that lets the original sender or protocol reclaim tokens held at an isolated address once the callback has run.

### Impact Explanation
This satisfies the Critical "permanent freezing, locking ... theft, or unauthorized extraction of user funds" bar: any unprivileged actor performing (or relaying) an ICS-20 transfer with a `dest_callback` memo pointing at a contract that does not perfectly and atomically drain the full approved amount (due to a bug, revert-on-partial-transfer semantics, insufficient gas budget vs. calldata complexity, or simply an honest contract with different accounting assumptions) causes the transferred value to be irreversibly locked at an address nobody controls. This is a direct value-loss bug reachable through the ordinary "public surface path" (JSON packet memo / precompile-mediated ICS-20 receive flow), matching the required "Asset-representation path" and "Public surface path" pivots called out in the task.

### Likelihood Explanation
The trigger requires only a normal ICS-20 transfer with a memo containing a `dest_callback` entry pointing to a contract address — no privileged access, validator collusion, or protocol bug elsewhere is needed. Any contract that is even slightly non-compliant with the exact expected pull-based transfer pattern (e.g., reverts silently caught upstream, partial withdrawal logic, or a contract deployed without full test coverage against this exact interface) will trigger permanent loss for the receiving user. Given ICS20 callbacks are a general-purpose extension point meant to interoperate with arbitrary third-party contracts, this is a realistically likely occurrence, not merely a theoretical edge case.

### Recommendation
- Do not commit (`writeFn()`) the cached EVM state until after confirming the isolated address balance is fully drained; if the post-check fails, roll back the approval/calldata execution entirely so the funds remain safely at the isolated address for the immediate call, and additionally implement a dedicated recovery/sweep path (e.g., a permissionless message that lets the original `data.Sender` reclaim any residual balance at their own isolated address) rather than relying purely on the callback contract's cooperation.
- Alternatively, refund any leftover isolated-address balance back to the original sender automatically within the same callback execution when the contract doesn't fully drain it, mirroring the "refund on drop" remediation direction referenced in the external report.

### Proof of Concept
1. Sender on chain A sends an ICS-20 transfer to chain B with `receiver` set to the isolated address `GenerateIsolatedAddress(destChannel, sender)` and memo `{"dest_callback": {"address": "<contractAddr>", "calldata": "..."}}`.
2. `contractAddr` is deployed on chain B implementing a callback entrypoint that intentionally (or due to a bug) does not call `transferFrom` for the *entire* approved amount — e.g., it transfers only 99% of `amount`, or reverts after partially succeeding in a way the EVM call still returns success at the top level.
3. Packet is relayed; `OnRecvPacket` mints/unescrows the full `amount` to the isolated address.
4. `IBCReceivePacketCallback` runs: `approve` succeeds, `writeFn()` commits, calldata call executes but leaves a positive residual balance at the isolated address.
5. The function returns `ErrEVMCall "receiver has X unrecoverable tokens after callback"`, but by this point the approve/calldata state has already been committed via `writeFn()`; regardless of this specific ordering nuance, the residual balance itself sits at an address with no private key.
6. No subsequent message, precompile, or module function exists that can move funds out of that isolated address — the residual tokens are permanently locked, verified by the absence of any sweep/reclaim entrypoint referencing `GenerateIsolatedAddress` outside of this receive path in [7](#0-6) .

```go
func (k ContractKeeper) IBCReceivePacketCallback(
	ctx sdk.Context,
	packet ibcexported.PacketI,
	ack ibcexported.Acknowledgement,
	contractAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.DestinationCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	// receiver := sdk.MustAccAddressFromBech32(data.Receiver)
	receiver, err := sdk.AccAddressFromBech32(data.Receiver)
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"acc addr from bech32 conversion failed for receiver address: %s", data.Receiver)
	}
	receiverHex, err := utils.HexAddressFromBech32String(receiver.String())
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"hex address conversion failed for receiver address: %s", receiver)
	}

	// Generate secure isolated address from sender.
	isolatedAddr := types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)
	isolatedAddrHex := common.BytesToAddress(isolatedAddr.Bytes())

	acc := k.authKeeper.NewAccountWithAddress(ctx, receiver)
	k.authKeeper.SetAccount(ctx, acc)

	// Ensure receiver address is equal to the isolated address.
	if receiverHex.Cmp(isolatedAddrHex) != 0 {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress, "expected %s, got %s", isolatedAddrHex.String(), receiverHex.String())
	}

	contractAddr := common.HexToAddress(contractAddress)

	// Check if the contract address contains code.
	// This check is required because if there is no code, the call will still pass on the EVM side,
	// but it will ignore the calldata and funds may get stuck.
	if !k.evmKeeper.IsContract(ctx, contractAddr) {
		return errorsmod.Wrapf(types.ErrContractHasNoCode, "provided contract address is not a contract: %s", contractAddr)
	}
```
