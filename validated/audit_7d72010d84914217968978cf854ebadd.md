### Title
Non-atomic reward accounting vs. `balanceOf` causes permanent freezing of unclaimed yield across all reward tokens for a user - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.getReward()` (and the equivalent path in `BaseRewardPoolV2.sol`) tracks each user's claimable amount in the `userRewards[rewardToken][account]` mapping and pays it out with an unchecked `safeTransfer`, with no prior verification that the pool's actual token balance still covers the accounted amount. Any registered reward token whose `balanceOf()` can be reduced without a corresponding transfer out of the pool (fee-on-transfer tokens, downward-rebasing tokens, or any token that MasterMagpie/WombatStaking's `queueNewRewards` flow accepts as an arbitrary bribe/reward token) can cause this transfer to revert, exactly mirroring the referenced VTVLVesting `withdraw()` bug where `balanceOf()` diverges from internally tracked entitlement.

### Finding Description
`_provisionReward`/`queueNewRewards` records `historicalRewards`/`rewardPerTokenStored` based on the nominal `_amountReward` passed in [1](#0-0) , without measuring the actual balance change from the `safeTransferFrom` call. The accrued `userRewards[rewardToken][_account]` figure is later paid out unconditionally: [2](#0-1) 

The loop pays every registered reward token for the account in a single transaction. If the actual balance held by the pool for one reward token is smaller than the accounted `reward` value (e.g., because the token has fee-on-transfer or rebase-down characteristics), `safeTransfer` reverts, and because Solidity reverts roll back all state changes in the transaction, the `userRewards[rewardToken][_account] = 0;` reset is undone as well. The user is left in a state where `getReward()` will revert every time it's called for that account — not only for the deficient token, but for the entire batched call encompassing **all** of that user's other, perfectly healthy reward tokens in the same pool, since they are all transferred in the same loop/transaction. The same non-atomic-accounting-vs-actual-balance pattern also exists in `BaseRewardPoolV2._provisionReward`/`_sendReward` [3](#0-2) .

This is functionally identical to the referenced VTVLVesting finding: an internally tracked "entitled" amount silently diverges from the ERC20 contract's real `balanceOf()`, causing `withdraw`/`getReward` calls to permanently revert and lock funds unless someone donates extra tokens to top up the balance (exactly the "send more tokens to unlock" workaround called out in the original report).

### Impact Explanation
Because `getReward()` batches transfers for every reward token registered on a pool in one atomic call, a single problematic reward token permanently blocks claiming of all other legitimate, fully-funded reward tokens for that user in that pool. This constitutes permanent freezing of unclaimed yield for affected users, satisfying the "theft or permanent freezing of unclaimed yield" impact bar, reachable purely through the normal, unprivileged `getReward`/`claim` flow that any staking user calls.

### Likelihood Explanation
Reward tokens flowing into `BaseRewardPool`/`BaseRewardPoolV2` originate from `WombatStaking`'s harvest/bribe pipeline, where reward tokens can be arbitrary ERC20s sourced from Wombat's bribe rewarders (an external, permissionless surface as far as user-facing reachability is concerned) via `queueNewRewards` [4](#0-3) . Any deflationary/fee-on-transfer/rebase-down token entering this path — which is not filtered or validated for balance-integrity anywhere in `_provisionReward` — triggers the freeze the next time an affected user calls `getReward`. No admin/governance action beyond normal protocol operation is required to reach the vulnerable code from an ordinary wallet's `claim` transaction.

### Recommendation
- In `_provisionReward` (both `BaseRewardPool.sol` and `BaseRewardPoolV2.sol`), measure the actual received balance via `balanceOf` before/after `safeTransferFrom` and use the delta to update `rewardPerTokenStored`/`historicalRewards`, rather than trusting the nominal `_amountReward` parameter.
- In `getReward`, cap each per-token transfer to `min(userRewards[token][account], IERC20(token).balanceOf(address(this)))`, carrying forward any shortfall as an "unpaid" balance (similar to the `unpaidRewards` pattern already used in `mocks/wombat/MultiRewarderPerSec.sol#L189-201`), so that a shortfall in one reward token cannot block payout of the others.
- Consider an explicit allow-list check/rejection of tokens with abnormal `balanceOf` behavior when registering new reward tokens.

### Proof of Concept
1. A pool's `BaseRewardPool` is funded via `queueNewRewards`/`donateRewards` with a fee-on-transfer or downward-rebasing token X as a registered reward token.
2. Over time, `X.balanceOf(address(this))` drops below the sum of all `userRewards[X][*]` due to the token's rebasing/fee mechanics, without any transfer having occurred out of the pool.
3. A user with a legitimate claim across multiple reward tokens (including X and a healthy token Y) calls `getReward()`/`claim` via `MasterMagpie`.
4. The loop in `getReward()` [5](#0-4)  reaches token X, `safeTransfer` reverts because actual balance < accounted `reward`, reverting the whole transaction.
5. Every subsequent `getReward()` call for that user reverts identically (accounting for X is never reduced), permanently blocking claim of token Y as well, until someone manually donates extra X tokens to the pool to cover the shortfall.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userShare) internal view returns (uint256) {
        return ((_userShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**stakingTokenDecimals) + userRewards[_rewardToken][_account];
    }

    function _sendReward(address _rewardToken, address _account, address _receiver, uint256 _amount) internal {
        userRewards[_rewardToken][_account] = 0;
        IERC20(_rewardToken).safeTransfer(_receiver, _amount);
        emit RewardPaid(_account, _receiver, _amount, _rewardToken);
    }

    function getReward(address _account, address _receiver)
        override
        public
        onlyMasterMagpie
        updateReward(_account)
        returns (bool)
    {
        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

        return true;
    }
