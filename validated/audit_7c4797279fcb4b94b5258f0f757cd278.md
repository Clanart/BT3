### Title
Attacker-controlled `ThresholdKeys::read` allocates oversized interpolation vector before validating parameters - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` trusts the serialized participant count `n` to preallocate `Interpolation::Constant` before constructing and validating `ThresholdParams`. A minimal malformed payload declaring `n = 65535` can force allocation of roughly 2 MiB before reading fails or invalid parameters are rejected. Repeated or concurrent calls can amplify a small amount of attacker-controlled input into material memory pressure. [1](#0-0) [2](#0-1) 

### Finding Description
The deserializer reads `t`, `n`, and `i`, then immediately handles interpolation type `0` by calling `Vec::with_capacity(usize::from(n))`. No bound is applied to `n`, and the `ThresholdParams::new(t, n, i)` validation that rejects `t > n`, zero values, or an out-of-range participant is not reached until after the oversized allocation and scalar-reading loop. `Participant::new` only rejects zero, so `n` can be as large as `u16::MAX`. [3](#0-2) [4](#0-3) 

### Impact Explanation
An unprivileged party that can submit serialized `ThresholdKeys` bytes can cause disproportionate transient memory allocation with a truncated message. With a typical 32-byte scalar representation, `n = 65535` reserves approximately 2 MiB before any scalar is read. If the reader is paused or the input stream remains open after the allocation, each request can retain that allocation while consuming very little attacker bandwidth; enough concurrent requests can degrade or terminate the process through memory exhaustion. [5](#0-4) 

### Likelihood Explanation
The vulnerable path is directly reachable through the public `ThresholdKeys::read` API and requires only a valid curve identifier followed by attacker-controlled parameter bytes. No valid proof, signature, threshold share, blockchain data, or privileged position is required. The amplification is bounded to `u16::MAX` entries per invocation, but exploiting it only requires repeatedly invoking deserialization or holding allocations open through an incomplete reader. [6](#0-5) 

### Recommendation
Validate `t`, `n`, and `i` by constructing `ThresholdParams` before allocating or reading interpolation coefficients. In addition, replace `Vec::with_capacity(n)` with incremental `Vec::push` growth or impose a protocol-level maximum participant count before allocation. This prevents truncated or delayed inputs from reserving memory proportional to an unvalidated attacker-controlled `n`. [7](#0-6) 

### Proof of Concept
For any `Ciphersuite` `C`, construct the expected `C::ID` prefix, then serialize:

```text
t = 0x0001
n = 0xffff
i = 0x0001
interpolation = 0x00
EOF
```

`ThresholdKeys::<C>::read` reaches `Interpolation::Constant`, executes `Vec::with_capacity(65535)`, and allocates approximately 2 MiB before the subsequent `C::read_F` call fails on EOF. Keeping the reader open after the interpolation tag causes the oversized vector allocation to remain live while no further attacker data is sent. [1](#0-0) [2](#0-1)

impl ThresholdParams {
  /// Create a new set of parameters.
  pub const fn new(t: u16, n: u16, i: Participant) -> Result<ThresholdParams, DkgError> {
    if (t == 0) || (n == 0) {
      return Err(DkgError::ZeroParameter { t, n });
    }

    if t > n {
      return Err(DkgError::InvalidThreshold { t, n });
    }
    if i.0 > n {
      return Err(DkgError::InvalidParticipant { n, participant: i });
    }

    Ok(ThresholdParams { t, n, i })
  }
