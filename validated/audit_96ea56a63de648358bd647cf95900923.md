### Title
`ReceivedOutput::read` accepts attacker-supplied bytes without verifying the offset actually derives the output's key — deserialized outputs can claim to be spendable when they are not - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Like the WinGUp updater executing downloaded installers without integrity verification, `ReceivedOutput::read` reconstructs a spendable-output record entirely from untrusted bytes — an `offset` scalar, a `TxOut`, and an `OutPoint` — without verifying that `offset * G + scanner_key` actually hashes to `output.script_pubkey`, i.e. without verifying the output is spendable by the key the offset implies.

### Finding Description
`Scanner` maintains a map from `script_pubkey` to `offset` and produces `ReceivedOutput`s internally by looking up `self.scripts.get(&output.script_pubkey)` in `scan_transaction` — so every `ReceivedOutput` the scanner emits is guaranteed spendable by `key + offset*G` (modulo the even-Y normalization in `p2tr_script_buf`/`register_offset`).

`ReceivedOutput::read`, however, performs zero consistency checking. From `networks/bitcoin/src/wallet/mod.rs` (lines 122–134):

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Any byte string that decodes produces a structurally valid `ReceivedOutput` whose `offset()` may have no relationship to the `script_pubkey` in `output`. There is no key/offset/script binding — the deserialized object's integrity claim ("this output is spendable via `key + offset*G`") is never re-established.

### Impact Explanation
A `ReceivedOutput` whose `offset` does not correspond to its `output.script_pubkey` is a "funds received that are not spendable" primitive: downstream code treats `offset()` as the scalar tweak needed to sign for the output (`SignableTransaction`/`TransactionMachine` compute signing keys as `key + offset*G`). Consequences include:

- An output reported as received/spendable which cannot actually be signed for, stalling or corrupting the wallet's UTXO set.
- A mismatched offset silently redirecting the derived signing key: the wallet produces a signature for `key + offset*G`, which is not the key committed in `script_pubkey`, yielding an invalid spend and effectively burning the input's fee contribution while the output stays locked.
- The `outpoint` is likewise unbound to the `output`, so a deserialized record can pair a real (attacker-observed) outpoint with a wrong offset, causing the wallet to attempt signing for UTXOs it does not control.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read` — i.e. untrusted serialization rather than in-memory `Scanner` output (which is self-consistent). Where a peer, coordinator message, or untrusted store supplies a serialized `ReceivedOutput`, this is directly reachable with public inputs. Exploitation yields mis-spendable outputs / failed signing rather than direct key recovery, so impact is limited to integrity/availability of funds — Medium.

### Recommendation
Rebind the offset to the output at deserialization, mirroring what `scan_transaction` guarantees:

```rust
let output = ReceivedOutput { offset, output, outpoint };
// Verify offset actually derives this script_pubkey for the known scanner key
if p2tr_script_buf(key + (ProjectivePoint::GENERATOR * output.offset)) !=
   Some(output.output.script_pubkey.clone()) {
  Err(io::Error::other("offset does not match output script_pubkey"))?;
}
```

Since `ReceivedOutput::read` currently has no access to the scanner key, either pass the key/`Scanner` into `read`, or store/serialize the derived `ProjectivePoint` alongside the offset and re-derive `p2tr_script_buf` from it at read time. At minimum, callers must not trust a deserialized `ReceivedOutput` as spendable without re-running the script-derivation check.

### Proof of Concept
1. Construct a `Scanner` for key `K`; register a legitimate offset `o1` producing script `S1`.
2. Attacker serializes a `ReceivedOutput` with `offset = o1` but `output.script_pubkey = S2` (any P2TR script not derived from `K + o1*G`), and any on-chain `outpoint` they do not own.
3. `ReceivedOutput::read` succeeds — no error.
4. Wallet signs the input with key `K + o1*G`; the resulting signature fails BIP-341 verification against `S2`, so the transaction is unspendable/invalid despite the wallet believing it controlled the output.
