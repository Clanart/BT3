### Title
`updateHostParams` lets `challengePeriod` be dropped to any value (including 0) instantly, with no floor and no timelock, retroactively collapsing the fisherman-veto window for state commitments already in flight - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal` validates several `HostParams` fields before accepting an update — e.g. it enforces `params.unStakingPeriod >= 1 days` (`InvalidUnstakingPeriod`) [1](#0-0)  — but it applies **no equivalent floor or timelock to `challengePeriod`**, which is copied straight from the incoming struct into storage: [2](#0-1) . This mirrors the reported `updateA` bug class exactly: a security-critical timing parameter can be changed abruptly, in a single transaction, with no lower bound and no grace period for parties relying on the old value.

### Finding Description
`challengePeriod` is the exact analog of the `A` parameter in the report — it is not just configuration, it is the safety window that lets fishermen catch and veto bad/faulty state commitments before they are actioned. All four ISMP message handlers gate on it using the *current* `challengePeriod` value against the *original* `stateMachineCommitmentUpdateTime` of an already-stored commitment: [3](#0-2) [4](#0-3) [5](#0-4) 

The same design exists in the Substrate ISMP core: `verify_delay_passed` recomputes `current_timestamp - update_time > delay_period` using whatever `challenge_period` is configured *at call time*, not at the time the commitment was stored [6](#0-5) .

Because the check is `current_timestamp - stored_update_time > current_challenge_period` (not the challenge period that was in effect when the commitment landed), a governance-triggered reduction of `challengePeriod` is applied **retroactively** to every state commitment already stored. A commitment that fishermen were relying on a 7‑day window to review/veto (via `deleteStateMachineCommitmentInternal`, which records the vetoing fisherman) [7](#0-6)  can instead be actioned the instant the parameter is lowered — even down to `0`, which explicitly disables the delay check altogether (`if (challengePeriod != 0 && challengePeriod > delay)`).

`unStakingPeriod`, which exists specifically "to prevent long-range attacks" per its own doc comment [8](#0-7) , is protected with an explicit minimum. `challengePeriod`, whose doc comment says it is the "Minimum challenge period for state commitments" [9](#0-8) , has no such protection — the validation block in `updateHostParamsInternal` checks `hostManager`, `handler`, `consensusClient`, `hyperbridge`, `stateMachines.length`, and `unStakingPeriod`, but never `challengePeriod` [10](#0-9) .

Off-chain relayer infrastructure (`tesseract`) treats the challenge period as a stable pre-commitment: it waits for it and races it against a veto-notification stream before treating a state update as final [11](#0-10) , and the SDK's `waitForChallengePeriod` helper reads the challenge period once and sleeps for that duration [12](#0-11) . None of this tooling anticipates the value shrinking mid-flight, so the entire "wait, then act" safety assumption built on top of `challengePeriod` breaks the moment it is retroactively lowered.

### Impact Explanation
This directly threatens the "false proof/state acceptance" and "unauthorized transaction or execution" categories called out in the bounty scope. Any state commitment stored under a longer challenge period can be prematurely finalized as soon as `challengePeriod` is reduced (or zeroed), letting post-requests, get-responses, and timeouts referencing that commitment be dispatched to destination modules before the security window the protocol advertised has actually elapsed. This shrinks or eliminates the window fishermen have to call `deleteStateMachineCommitmentInternal`/veto a faulty commitment stemming from a consensus fault or long-range-style state reorg, risking processing of requests against state that should still have been contestable — i.e. false state acceptance leading to unauthorized execution/fund movement.

### Likelihood Explanation
Reaching the update itself requires a `hostManager` governance call, which is the legitimate cross-chain-governance path (`onAccept`/`SetHostParam` in `HostManager.sol`) [13](#0-12)  — this is not a compromised-actor path, it's ordinary parameter maintenance. The exploitable primitive is available to any unprivileged party once the parameter change lands: no attacker privilege beyond normal permissionless calls into `HandlerV2` (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) is needed to benefit from the collapsed delay window on already-stored commitments. Likelihood is moderate — it requires a governance parameter update that happens to lower `challengePeriod` while commitments are pending, which is plausible for routine protocol tuning but not guaranteed to occur.

### Recommendation
- Add a minimum-floor check on `params.challengePeriod` in `updateHostParamsInternal`, symmetric to the existing `InvalidUnstakingPeriod` check on `unStakingPeriod`.
- More importantly, do not apply challenge-period changes retroactively to already-stored commitments: snapshot the challenge period at the time a state commitment is stored (alongside `_stateCommitmentsUpdateTime`) and use that snapshot in the delay check, or enforce a timelock/grace period before a `challengePeriod` reduction takes effect for pre-existing commitments.
- Apply the equivalent fix in `modules/ismp/core/src/handlers.rs::verify_delay_passed`, which has the same current-value-vs-stored-time pattern.

### Proof of Concept
1. Hyperbridge governance (via `hostManager`) submits a legitimate `updateHostParams` call to tune fees/addresses and, as part of the same struct, reduces `challengePeriod` from `7 days` to `0` — no dedicated check rejects this value: [14](#0-13) .
2. Prior to this update, a state machine commitment was stored at height `H` with `_stateCommitmentsUpdateTime[H] = T0` (e.g., 1 hour before the update), under the assumption fishermen have `7 days` to veto it via `deleteStateMachineCommitmentInternal`.
3. Immediately after the update lands, any relayer calls `handlePostRequests` (or `handleGetResponses`/timeout handlers) referencing proof height `H`. The check `challengePeriod != 0 && challengePeriod > delay` now evaluates `0 > delay` which is always false, so `ChallengePeriodNotElapsed` never reverts: [15](#0-14) .
4. The request is dispatched to the destination module (`host.dispatchIncoming`) using a state commitment that fishermen had a contractual 7‑day review window for but which was never actually vetoed within any meaningful time — the safety property "requests are only processed after `challengePeriod` seconds of scrutiny" is broken for every commitment that predates the parameter change.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

export async function waitForChallengePeriod(chain: IChain, stateMachineHeight: StateMachineHeight): Promise<void> {
	// Get the challenge period for this state machine
	const challengePeriod = await chain.challengePeriod(stateMachineHeight.id)

	if (challengePeriod === BigInt(0)) return

	// Get the state machine update time
	const updateTime = await retryPromise(() => chain.stateMachineUpdateTime(stateMachineHeight), {
		maxRetries: 3,
		backoffMs: 500,
		logMessage: "Fetching consensus update time while waiting for the challenge period",
		shouldRetry: (error) => !MissingConsensusUpdateTimeError.isError(error),
	})
	// Check current timestamp
	let currentTimestamp = await chain.timestamp()
	// Calculate time passed since update
	let timeElapsed = currentTimestamp - updateTime

	if (timeElapsed > challengePeriod) return

	// First sleep for the whole challenge period
	await sleep(Number(challengePeriod) * 1000)
