Based on my investigation, I found a genuine analog: the `OrderIndependentMultisigSpendingCondition::verify` function does not chain the sighash across signature fields, and does not deduplicate signature fields, meaning a single signature can be replayed multiple times within the same `fields` vector to be counted as multiple distinct signatures toward `signatures_required`.

### Title
Duplicate-signature counting bypasses multisig threshold in `OrderIndependentMultisigSpendingCondition::verify` - (File: stacks-codec/src/transaction.rs)

### Summary
`OrderIndependentMultisigSpendingCondition::verify` verifies each `TransactionAuthField::Signature` entry against the *same* `initial_sighash` (not a rolling/chained hash as in the ordered multisig case), and increments `num_sigs` for every valid signature field without checking whether the recovered public key was already counted. [1](#0-0)  This mirrors the `WhitelistRegistry.register` bug: a per-item mutation (`num_sigs += 1`) is performed based on a check that should ensure uniqueness but doesn't, so the same "member" (signature) is effectively counted twice, breaking the equality between "number of counted signatures" and "number of *distinct* keys that actually signed".

### Finding Description
In `MultisigSpendingCondition::verify` (order-dependent), each field's verification uses a rolling `cur_sighash` that is updated by `make_sighash_postsign` after each signature, which binds the signature to its position and to the specific preceding auth fields [2](#0-1) . In contrast, `OrderIndependentMultisigSpendingCondition::verify` calls `next_verification` with the constant `initial_sighash` for every field [3](#0-2) , and `next_verification` simply recovers the pubkey from `sig` against `sighash_presign` computed from that same `initial_sighash`, `cond_code`, `tx_fee`, and `nonce` [4](#0-3) . Because the presign hash is identical for every signature field, the *exact same* `MessageSignature` bytes can be placed into two separate `TransactionAuthField::Signature` entries in `fields`, and each occurrence will independently recover to the same valid public key and increment `num_sigs` by one [5](#0-4) . The loop never checks `pubkeys` for duplicates before comparing `num_sigs` against `self.signatures_required` [6](#0-5) .

The only remaining check is that the reconstructed `pubkeys` list (which now contains a duplicate) must hash, via `StacksAddress::from_public_keys`, to the pre-registered `signer` Hash160 [7](#0-6) . This means the attack only works if the account's address was originally derived from a public-key set that itself contains a duplicate key (e.g., an N-of-M multisig account where the deployer registered the same key twice, intentionally or by mistake, to reduce the real number of distinct signers needed) — in that scenario, `verify` will accept only that one real key signing twice as satisfying a nominally higher `signatures_required` threshold, since nothing prevents the same underlying signature from filling more than one of the "required" signature slots.

This is analogous to the `WhitelistRegistry` bug: a mutation/counter (`_whitelist.add`/`num_sigs`) is advanced based on an implicit uniqueness assumption that is never actually enforced, letting one actor's single action be counted as multiple independent actions.

### Impact Explanation
If exploitable end-to-end, this would let a transaction be treated as satisfying a signature threshold with fewer distinct signing keys than required — i.e., "signatures verified fewer than the threshold" while still passing `verify`. That maps to the High-severity class in scope. However, the practical blast radius is constrained: it requires the target multisig address's public key set to already contain a duplicate entry, which is an unusual (arguably degenerate) account configuration, not something a generic attacker can impose on an arbitrary victim's existing N-of-M account.

### Likelihood Explanation
Low-to-Medium. It requires a specific precondition — an existing multisig account whose registered public-key list has a duplicate key — which is not the normal multisig setup and would typically only arise from user/tooling error. I was not able to fully verify from the available index whether any upstream code path (e.g., account creation, `new_multisig_order_independent_p2sh`) rejects duplicate public keys when constructing such a condition, which would foreclose this path entirely; this is a gap in what I could confirm from the indexed files.

### Recommendation
In `OrderIndependentMultisigSpendingCondition::verify`, deduplicate the recovered `pubkeys` (e.g., collect into a `HashSet`/`BTreeSet` of compressed key bytes) before counting `num_sigs`, or reject the condition outright if two fields recover to the same public key. Additionally, consider rejecting construction of any multisig spending condition (`new_multisig_order_independent_p2sh`/`p2wsh`) whose input public-key list contains duplicates, closing off the precondition entirely.

### Proof of Concept
Not fully constructible from the available index — I could not confirm (within tool budget) whether `new_multisig_order_independent_p2sh`/`p2wsh` construction paths already reject duplicate public keys, which would determine whether this is practically reachable. A concrete PoC would: (1) build an `OrderIndependentMultisig` account with `signatures_required = 2` from a public-key list containing the same key twice plus one other distinct key (3 total slots, one key duplicated); (2) have only the duplicated key sign; (3) submit two `TransactionAuthField::Signature` fields with the identical signature bytes; (4) show `verify` returns `Ok` because `num_sigs == 2` even though only one distinct private key actually signed.
