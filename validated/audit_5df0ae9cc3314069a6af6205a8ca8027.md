### Title
Unzeroized transcript retains the DKG ECDH shared key in freed heap memory, enabling recovery of PedPoP secret shares - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
CVE-2025-36083 is a "sensitive information remains in heap buffers because memory is not cleared before release" bug. Serai's PedPoP DKG encryption derives its per-recipient ChaCha20 key from an ECDH shared secret that is written into a `RecommendedTranscript`, yet the transcript is an ordinary heap-owning object that is dropped without zeroization. The shared key therefore survives in freed heap memory, and whoever recovers it can decrypt the encrypted DKG secret share for that recipient.

### Finding Description
`cipher()` builds the encryption keystream by appending the ECDH shared point into a transcript:

- `crypto/dkg/pedpop/src/encryption.rs:95-97`: `ecdh()` computes `Zeroizing::new(public * private)` — the shared secret is `Zeroizing`.
- `crypto/dkg/pedpop/src/encryption.rs:104-111`: inside `cipher()`, `ecdh.to_bytes()` is appended into `transcript` (`RecommendedTranscript::new(b"DKG Encryption v0.2")`) under `b"shared_key"`. Only the local `ecdh` byte buffer is manually zeroized (`ecdh.as_mut().zeroize()`); the transcript itself is dropped normally at the end of the function.
- The code even acknowledges this gap: `// Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly // TODO: https://github.com/serai-dex/serai/issues/151` (encryption.rs:102-103). `ZAlloc` (`common/zalloc/src/lib.rs:37-46`) zeroizes on dealloc precisely to prevent this, but it is not used here.
- The transcript's internal state (a heap `Vec`/hash state containing `context`, `domain_separate` tag, and the full `shared_key` bytes) is freed without clearing.

This `cipher()` is used for both directions: `Encryption::encrypt()` when generating `EncryptedMessage` secret shares for each counterparty (`crypto/dkg/pedpop/src/lib.rs:366-369`), and the decrypt path when a participant reads `EncryptedMessage::read` / decrypts incoming shares. Every call leaves one copy of a long-term ECDH shared secret in reusable heap memory.

Contrast with the rest of the crate, which is careful: `SecretShare` implements `ZeroizeOnDrop` (pedpop/src/lib.rs:256-261), coefficients are zeroized (pedpop/src/lib.rs:374), and `Encryption::zeroize()` clears `enc_key` (encryption.rs:422-430). The transcript is the one unzeroized container holding equivalent secret material.

### Impact Explanation
A local attacker (the CVE's model: local user, `AV:L`, `C:H`) who can trigger a DKG or decrypt operation and then read freed heap — e.g., a co-resident process, core dump, swap, or a subsequent allocation in the same process after the machine is dropped — recovers the ECDH shared key for a (sender, recipient) pair. With that key and the static IV (`b"DKG IV v0.2\0"`, encryption.rs:124-126), they can re-derive the ChaCha20 keystream and decrypt the corresponding `EncryptedMessage` ciphertext observed on the wire, recovering the FROST secret share `polynomial(coefficients, l)` it carried (pedpop/src/lib.rs:366-367). This is disclosure of threshold-key share material, the exact asset class the rest of the module wraps in `Zeroizing`.

### Likelihood Explanation
Reachability is high: an unprivileged DKG participant supplies their `EncryptionKeyMessage` (with their `enc_pub_key`) via `Commitments::read`/`EncryptionKeyMessage` deserialization, causing the victim to call `ecdh()` and `cipher()` over attacker-controlled inputs during `generate_secret_shares`/`decrypt`. The residual requirement — reading freed heap — matches the CVE's stated local-information-disclosure model, and the buffer deterministically contains the full shared secret since it is appended verbatim (encryption.rs:109-110). The code's own TODO confirms the protection was intended but not applied.

### Recommendation
Zeroize the transcript's internal buffer, or route the shared-key derivation through a zeroizing container: e.g., derive the key via `transcript.challenge()` into a `Zeroizing` buffer without appending the raw `shared_key` bytes to a persistent transcript, or wrap the transcript allocation in `ZeroizingAlloc`/`Zeroizing` once feasible (issue #151). At minimum, after `key.copy_from_slice(...)`, explicitly clear any transcript state containing `shared_key` before the transcript is dropped.

### Proof of Concept
1. Participant `l` runs `KeyGenMachine::generate_coefficients` / `SecretShareMachine::generate_secret_shares`, which calls `self.encryption.encrypt(rng, l, share_bytes)` → `cipher(context, &ecdh(private=enc_key, public=enc_pub_key_l))`.
2. Inside `cipher()`, `transcript.append_message(b"shared_key", ecdh)` copies the 32-byte shared point into the transcript's heap buffer (encryption.rs:104-110).
3. `cipher()` returns `ChaCha20`; `transcript` is dropped without zeroization — the shared key remains at its heap address until reused.
4. A local reader of the process's heap (the CVE's attack surface) finds the shared key bytes, recomputes `ChaCha20` with `key = H_transcript(shared_key)` and `iv = "DKG IV v0.2\0"`, and decrypts the published `EncryptedMessage` for participant `l`, recovering the DKG secret share.
