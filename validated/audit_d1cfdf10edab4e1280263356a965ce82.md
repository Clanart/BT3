### Title
Unprivileged manipulation of the WOM/mWOM Wombat pool price to force unfavorable `smartConvert` buyback decisions and extract value from protocol-harvested yield - (File: wombat/SmartWomConvert.sol)

### Summary
`SmartWomConvert.smartConvert()` decides, on every WOM→mWOM conversion path used by `WombatStaking`, whether harvested WOM should be minted 1:1 into mWOM or partially routed through the on-chain `womMWomPool` AMM. This decision is driven entirely by spot values read from that pool in the same transaction, with no TWAP or manipulation resistance, and the entry point that triggers the conversion (`WombatStaking.harvest`) is callable by any unprivileged wallet.

### Finding Description
`currentRatio()` prices mWOM in WOM by calling `IWombatRouter(router).getAmountOut(...)` against `womMWomPool` for a fixed 1e18 probe amount, and `maxSwapAmount()` derives the swappable cap from that same pool's live `cash()`/`liability()` values: [1](#0-0) 

`smartConvert()` then uses these two spot reads to compute `convertRatio`, i.e., how much of the incoming WOM gets routed through the AMM ("buyback") versus minted 1:1 as mWOM: [2](#0-1) 

Both values are read fresh, in-block, from the same pool that any wallet can also swap against via the Wombat router — there is no oracle, no TWAP, and no slippage/price-impact bound applied to `currentRatio()`/`maxSwapAmount()` themselves (only `_minRec` protects the final `_convertFor` swap output, not the ratio-selection logic).

The trigger for this logic on protocol-held WOM (harvested rewards, not a user's own deposit) is `WombatStaking.harvest()`, which any unprivileged wallet can call for any active pool: [3](#0-2) 

This routes into `_toMasterWomAndSendReward`, which per the comment in `SmartWomConvert` ("should mainly used by wombat staking upon sending wom") is the path that hands harvested WOM to `smartConvert`. Because `harvest`/`deposit`/`withdraw` on `WombatStaking` are all unprivileged-callable and each triggers this same reward-forwarding flow, an attacker can:
1. Swap a large amount into/out of `womMWomPool` (via the public Wombat router) to push `currentRatio()` below `buybackThreshold` and/or skew `cash()`/`liability()` so `maxSwapAmount()` is maximized in the attacker's favor.
2. In the same transaction, call `harvest()` on an active `WombatStaking` pool, forcing the protocol's harvested WOM to be converted using the manipulated `convertRatio`, i.e., forcing a larger portion of protocol WOM to be swapped through the temporarily-distorted AMM rather than minted 1:1.
3. Reverse the initial swap, capturing the AMM's slippage/price-impact as profit extracted directly from the WOM that would otherwise have become mWOM value for stakers (via `_toMasterWomAndSendReward` → base reward pool distribution).

### Impact Explanation
This constitutes theft of unclaimed yield: WOM harvested on behalf of `WombatStaking` depositors is converted at an attacker-manipulated rate instead of the rate that would apply absent manipulation, transferring value from the protocol's reward flow to the attacker. This falls within the accepted impact category of "theft ... of unclaimed yield."

### Likelihood Explanation
Likelihood depends on the depth/liquidity of `womMWomPool` relative to the capital an attacker can mobilize; Wombat's stableswap invariant provides some manipulation resistance for shallow price moves, but pushing `currentRatio()` across the `buybackThreshold` (90%) boundary, or skewing `cash()`/`liability()` to change `maxSwapAmount()`, does not require draining the pool — only shifting it near the threshold for one block. I was not able to fully inspect `_toMasterWomAndSendReward`'s body in this pass to confirm the exact call sequence into `smartConvert`, so the precise magnitude of extractable value per harvest call is unverified and should be confirmed against the live contract before acting on this report.

### Recommendation
- Do not derive `convertRatio` from a single-block spot read of `womMWomPool`; use a TWAP or a governance/keeper-set ratio with bounded deviation checks against a time-weighted reference.
- Add slippage/price-impact bounds on `currentRatio()`/`maxSwapAmount()` themselves (not just on the final swap output `_minRec`), and consider restricting `smartConvert` execution to a trusted keeper role rather than any unprivileged caller of `harvest()`.

### Proof of Concept
Conceptual sequence (not a full Foundry test, since exact pool depth/behavior at a given block was not verified):
1. Attacker swaps WOM→mWOM (or reverse) via the public Wombat router against `womMWomPool` to move `currentRatio()` under `buybackThreshold` and/or skew `cash()`/`liability()`.
2. Attacker calls `WombatStaking.harvest(lpAddress)` on any active pool (unprivileged), which drives protocol-held WOM into `SmartWomConvert.smartConvert`, using the now-manipulated `convertRatio`/`maxSwapAmount`.
3. Attacker reverses step 1's swap, realizing profit from the price-impact extracted from the protocol's harvested WOM conversion. [4](#0-3) [3](#0-2)

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
