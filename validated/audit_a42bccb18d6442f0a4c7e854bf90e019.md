## Finding

### Title
Payout transaction's operator-attribution OP_RETURN is unsigned, allowing anyone to mis-credit reimbursement to an operator who never funded the withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx` that fronts a Citrea withdrawal is signed by the user with `SIGHASH_SINGLE|ANYONECANPAY` [1](#0-0) , which only commits the input to output index 0 (the user's payout amount) and allows arbitrary additional inputs. The OP_RETURN output that records which operator "fronted" the withdrawal (`payout_payer_operator_xonly_pk`) is built with `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))` [2](#0-1)  and is never covered by that signature. The verifier/operator later trust this on-chain OP_RETURN value verbatim as ground truth for "who paid" without any further binding to the actual broadcaster/funder of the transaction.

### Finding Description
`create_payout_txhandler` builds the payout tx with a user-signed input (KeySpend, `SinglePlusAnyoneCanPay`), a payout output, an anchor output, and an OP_RETURN output containing whatever `operator_xonly_pk` the caller passes in [2](#0-1) . Because the sighash type is `SinglePlusAnyoneCanPay`, the user's signature only authenticates input index 0 against output index 0; it places no constraint on the OP_RETURN output's content, nor on any additional inputs used to pay fees (the anchor output pattern is explicitly designed for CPFP fee bumping by any funder). Anyone in possession of the user's off-chain signature (given "off-chain to operators" per the doc comment) can therefore construct and broadcast a variant of this transaction that pays the user correctly but names an arbitrary `operator_xonly_pk` in the OP_RETURN — including the xonly key of an operator who never funded anything.

On the verifier side, `update_finalized_payouts` scans the confirmed block, extracts the OP_RETURN operator pubkey with `parse_op_return_data`, and stores it verbatim as `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` [3](#0-2) . This DB value is later used as the sole source of truth for "who is entitled to reimbursement": `validate_payer_is_operator` checks only that the stored `payer_xonly_pk` equals the calling operator's own key [4](#0-3) , and `is_kickoff_malicious` checks that the stored `operator_xonly_pk` matches the kickoff's `operator_xonly_pk` [5](#0-4) . At no point is there a check that the operator named in the OP_RETURN actually supplied the additional funding input(s) of the payout transaction.

This breaks the custody binding: `party that funded the withdrawal == operator credited for reimbursement`. An attacker (or a party fronting the payout on behalf of one operator) can name a different, unrelated operator in the OP_RETURN. That named operator becomes eligible (via `get_reimbursement_txs`/kickoff flow) to claim the `Reimburse` tx output, which pays out the full vault amount from the `move_to_vault` UTXO [6](#0-5) , even though they never fronted BTC to the user. Simultaneously, the operator who actually did front the funds is permanently unable to claim reimbursement, since `validate_payer_is_operator` will reject them (the DB attributes the payout to someone else).

### Impact Explanation
This is a Critical-class custody/attribution break:
- An operator can be "reimbursed for a payout it never funded" — the named (mis-attributed) operator can walk the normal reimbursement path and drain the `move_to_vault` UTXO via `Reimburse` tx.
- The operator who genuinely fronted the withdrawal becomes "permanently unable to be reimbursed" — `validate_payer_is_operator` will always fail for them for that deposit, since the DB's `payer_xonly_pk` won't match their own signer key.

Both outcomes are explicitly listed Critical impacts (operator reimbursed for payout never funded; honest operator permanently unable to be reimbursed).

### Likelihood Explanation
The attack requires no privileged role: any party that obtains the user's off-chain `SinglePlusAnyoneCanPay` payout signature (given to operators for this exact purpose) can construct their own version of the payout transaction with a different OP_RETURN content and additional funding input, and broadcast it before/instead of the legitimate operator's broadcast. This is a standard consequence of using `SIGHASH_SINGLE|ANYONECANPAY` on a transaction whose unsigned outputs carry security-relevant metadata, and does not require compromising any key, verifier, or aggregator.

### Recommendation
Do not rely on an unauthenticated OP_RETURN for operator attribution. Either:
- Cover the OP_RETURN output (and disallow extra inputs) under the signature scheme used for the payout tx, or
- Require the crediting operator's own signature (e.g., a signed attestation binding operator key to the specific payout txid) before marking `payout_payer_operator_xonly_pk` in the database, or
- Bind attribution to the actual funding input's key (e.g., require the CPFP/fee-paying input to be spendable only by the named operator's key), so that whoever supplies the additional inputs is provably the same party named in the OP_RETURN.

### Proof of Concept
1. User signs a withdrawal input with `SIGHASH_SINGLE|ANYONECANPAY` and shares it off-chain (intended for operator use), per the documented flow [7](#0-6) .
2. Attacker (or a distinct operator A) constructs `create_payout_txhandler` with `operator_xonly_pk = B` (any other operator's key) instead of their own, reusing the same signed input/output0, and adds their own fee-paying input(s)/anchor. [2](#0-1) 
3. The transaction confirms; `update_finalized_payouts` parses the OP_RETURN and stores `operator_xonly_pk = B` as the payer in the DB. [3](#0-2) 
4. Operator B later calls `get_reimbursement_txs`, which succeeds because `validate_payer_is_operator` finds `payer_xonly_pk == B` [4](#0-3) , letting B claim the `Reimburse` tx and drain the vault UTXO, despite never having funded the payout. Meanwhile the actual funder (attacker or operator A) cannot get reimbursed for this deposit at all.

    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())

        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,

        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,

                if payer_xonly_pk != self.signer.xonly_public_key {

                    )
                    .into());

                (payout_blockhash, kickoff_txid)
            }

                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
