### Title
Missing `chain_id` in `CLEMENTINE_EIP712_DOMAIN` Enables Cross-Deployment Replay of Withdrawal Authorization Signatures — (`core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to authenticate both `OptimisticPayoutMessage` and `OperatorWithdrawalMessage` withdrawal authorization signatures omits the `chain_id` and `verifying_contract` fields required by EIP-712 to bind a signature to a specific chain and deployment. This is the direct Clementine analog of the external bug's "signing standard inconsistency": just as `BLUEPRINT_TYPE_HASH` used a wrong field name that broke the binding between the type hash and the actual struct, the incomplete domain here breaks the binding between the signature and the deployment context.

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is declared as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

No `chain_id` or `verifying_contract` is included. The `alloy_sol_types::eip712_domain!` macro only hashes the fields that are present, so the domain separator is identical across every chain and every Clementine deployment that shares the same `name`/`version` string.

This domain is used in both verification paths:

- **Verifier** (`sign_optimistic_payout`): calls `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` with `CLEMENTINE_EIP712_DOMAIN`. [2](#0-1) 

- **Operator** (`withdraw` RPC): calls `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` with the same domain. [3](#0-2) 

Both signing and verification go through `recover_address_from_ecdsa_signature`, which computes `params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)`: [4](#0-3) 

Because the domain carries no `chain_id`, a signature produced for a Citrea testnet Clementine deployment is cryptographically indistinguishable from one produced for mainnet, and vice versa.

### Impact Explanation

If the same `aggregator_verification_address` key is used across two Clementine deployments (e.g., staging and production, or two bridge instances on the same Bitcoin network), an attacker who captures a legitimately-issued `OptimisticPayoutMessage` or `OperatorWithdrawalMessage` signature can submit it verbatim to the other deployment. The verifier/operator will recover the correct aggregator address and accept the request as authorized, potentially triggering an unauthorized optimistic payout or operator withdrawal on the target deployment — draining bridge-controlled BTC from the vault.

The `verification_signature` guard is the only authentication layer protecting these withdrawal endpoints from unauthorized callers: [5](#0-4) [6](#0-5) 

### Likelihood Explanation

The check is opt-in (`if let Some(address_in_config) = self.config.aggregator_verification_address`), so it only applies when the feature is enabled. When enabled, the same aggregator key being reused across deployments is a realistic operational assumption (e.g., a single Citrea-controlled key signing for both testnet and mainnet bridges). The `input_outpoint` field partially limits cross-chain replay (Bitcoin UTXOs differ between mainnet and testnet), but does not prevent replay across two mainnet deployments or two deployments sharing the same Bitcoin regtest/signet environment.

### Recommendation

Add `chain_id` (and optionally `verifying_contract`) to `CLEMENTINE_EIP712_DOMAIN`:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
    chain_id: <CITREA_CHAIN_ID>,          // bind to specific Citrea chain
    verifying_contract: <BRIDGE_ADDRESS>, // bind to specific bridge deployment
};
```

This ensures every signed message is cryptographically bound to a specific chain and contract, making cross-deployment replay impossible even if the same aggregator key is reused.

### Proof of Concept

1. Deployment A (testnet) and Deployment B (mainnet) both configure `aggregator_verification_address = 0xAGGREGATOR`.
2. Aggregator signs a valid `OptimisticPayoutMessage` for Deployment A with `CLEMENTINE_EIP712_DOMAIN` (no `chain_id`).
3. Attacker captures the `verification_signature` string from the gRPC call to Deployment A's aggregator.
4. Attacker submits the identical `OptimisticWithdrawParams` + `verification_signature` to Deployment B's `optimistic_payout` endpoint.
5. Deployment B's verifier calls `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` with the same domain — recovers `0xAGGREGATOR` — and proceeds to sign the optimistic payout MuSig2 partial signature, spending vault BTC on Deployment B without the aggregator ever authorizing it for that deployment. pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
