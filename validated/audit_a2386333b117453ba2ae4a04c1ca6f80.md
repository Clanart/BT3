## Finding: CEI Violation Reintroduced in Tron `IntentGatewayV2.withdraw()` — Read-Only Reentrancy on `_orders` Escrow Accounting

### Title
Escrow accounting updated after external transfer in Tron `IntentGatewayV2.withdraw()`, unlike the fixed EVM `_withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The main EVM implementation of the intents escrow-release logic, `_withdraw` in `IntentsBase.sol`, correctly applies checks-effects-interactions: it decrements `_orders[commitment][token]` *before* making the native/ERC20 transfer [1](#0-0) . The Tron variant of the same contract, `IntentGatewayV2.withdraw()`, reintroduces the exact violation described in the external report: it performs the native/ERC-20 `.call` transfer to `beneficiary` first, and only afterwards decrements `_orders[body.commitment][token]` [2](#0-1) .

### Finding Description
`withdraw()` is invoked from `onAccept` (restricted `onlyHost`, for `RedeemEscrow`/`RefundEscrow` requests) and from `onGetResponse` (also `onlyHost`) [3](#0-2) [4](#0-3) . The `beneficiary` address is attacker-influenceable: it is derived from `body.beneficiary`, which for a `RedeemEscrow` message is the solver that filled the order — and a user is free to act as their own solver, i.e., point the beneficiary at an attacker-controlled contract.

Inside the per-token loop, the flow is:
```
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
(bool sent,) = beneficiary.call{value: amount}("");   // external call FIRST
...
_orders[body.commitment][token] -= amount;             // state updated AFTER
``` [5](#0-4) 

Because `_orders` is a `public` mapping (state getter exposed for reads) [6](#0-5) , any external contract/integrator that reads `_orders(commitment, token)` for this gateway during the callback window (triggered by the native-token `.call` to the malicious beneficiary) observes the pre-decrement (stale) escrow balance for that commitment/token — the same "read-only reentrancy" class flagged in the original Balmy report, where a view of internal accounting is stale relative to an in-flight external call.

Note that `_filled[body.commitment] = beneficiary` *is* set before the loop (correct CEI ordering for that specific variable) [7](#0-6) , and `withdraw()`'s only entrypoints (`onAccept`, `onGetResponse`) are `onlyHost`-gated, so a reentrant call cannot directly re-trigger `withdraw()` or `fillOrder()` to double-spend the escrow itself within this contract. The exposure is specifically to **external readers of `_orders`** during the transfer callback, exactly the risk class the original report calls out ("if there is any external integration that reads share values from the vault, they should be aware of this read-only reentrancy vector").

### Impact Explanation
Any external protocol or contract that integrates with the Tron `IntentGatewayV2` and reads `_orders(commitment, token)` to gate its own logic (e.g., valuing outstanding escrow, computing available liquidity, or deciding whether to extend credit/trust based on "unredeemed" escrow) can be misled during the beneficiary's callback window into treating already-transferred funds as still escrowed. This does not directly steal funds from the gateway itself (the `onlyHost` gate and pre-set `_filled` guard block direct re-entrant double-redemption within this contract), but it reproduces the exact class of vulnerability from the seed report and represents a real divergence from the fixed pattern already applied in the canonical EVM contract.

### Likelihood Explanation
Low-to-medium: exploitation requires (a) an integrator that reads `_orders` mid-transaction and (b) an attacker able to register themselves (or a colluding solver) as the `beneficiary` of a native-token output, which is achievable by any user acting as their own solver on a same-chain order. No relayer, prover, or admin compromise is needed — only a standard user interaction with an ordinary external `.call` to a contract they control.

### Recommendation
Apply the same checks-effects-interactions fix already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` (and delete `TRANSACTION_FEES`) *before* issuing the native/ERC-20 transfer, for every token in the loop, matching the ordering at `evm/src/apps/intentsv2/IntentsBase.sol:403-409`.

### Proof of Concept
1. User places a same-chain-style order where they also act as their own solver, setting `output.beneficiary` to a contract they control with a `receive()` that calls back into any external view/state-reading integration point.
2. Order is filled, generating a `RedeemEscrow` message back to source (Tron) chain.
3. Host calls `onAccept` → `withdraw(body, false)`.
4. During the loop's `beneficiary.call{value: amount}("")`, the attacker's `receive()` fires while `_orders[commitment][token]` still reflects the pre-transfer (undecremented) balance.
5. Any external contract querying `IntentGatewayV2._orders(commitment, token)` at this point (e.g., via a nested call chain the attacker triggers) obtains stale escrow accounting, matching the read-only reentrancy pattern from the seed report. [8](#0-7)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
```
