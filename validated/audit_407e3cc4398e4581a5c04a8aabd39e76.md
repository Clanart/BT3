### Title
Uncontrolled Recursion in `AccountKeyRoleBased` RLP Decoding Leads to Denial of Service - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes nested `AccountKey` values without any depth limit. Because the composite-type / "no nested RoleBased key" restriction (`IsCompositeType`) is enforced only *after* decoding finishes (in `CheckInstallable`/`CheckUpdatable`), a transaction sender or public RPC caller can submit deeply nested RLP-encoded `AccountKey` data that is fully decoded — recursing once per nesting level — before any rejection occurs. This matches CWE-674 Uncontrolled Recursion / CAPEC-130 Excessive Allocation from the referenced Elasticsearch advisory, and can be used to crash or hang a Kaia node.

### Finding Description
`AccountKeyRoleBased` is decoded via: [1](#0-0) 

For each sub-key byte slice `enc[i]`, it calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [2](#0-1) 

`AccountKeySerializer.DecodeRLP` reads the `keyType` first, calls `NewAccountKey(keyType)` to allocate the concrete key (which can itself be `AccountKeyTypeRoleBased`), and then calls `s.Decode(serializer.key)` — which, if the type is `AccountKeyRoleBased` again, re-enters `AccountKeyRoleBased.DecodeRLP` from the top. Nothing in this call chain tracks or limits nesting depth.

The safeguard against nested `RoleBased` keys — `IsCompositeType()` returning `true` and being checked in `CheckInstallable`/`CheckUpdatable` — only runs *after* the entire structure has already been recursively decoded: [3](#0-2) 

The existing regression test only demonstrates that a **single** level of nesting is rejected post-decode (`TestAccountUpdateRoleBasedKeyNested`), not that deep/nested RLP payloads are rejected before or during decoding: [4](#0-3) 

Because the rejection happens after decode, an attacker can construct an RLP blob that nests `AccountKeyRoleBased` inside itself many times (each level only needs the minimal RLP overhead for a list-of-one-byte-string plus a 1-byte key type tag), causing the Go call stack to grow proportionally to the nesting depth during `DecodeRLP`. Two directly reachable entry points exist for an unprivileged actor:

1. **Public RPC** `kaia_decodeAccountKey`, which calls `rlp.DecodeBytes` directly on attacker-supplied bytes with no depth restriction: [5](#0-4) 

2. **Transaction submission** — any `TxTypeAccountUpdate`/`TxTypeAccountCreation`(-family) transaction carrying a crafted `AccountKey` field is RLP-decoded when the raw transaction bytes are unmarshaled (e.g. via `eth_sendRawTransaction`), which happens before `pool.validateTx`/`tx.Validate()` gets a chance to reject nested composite keys.

### Impact Explanation
Excessive/uncontrolled recursion during RLP decoding of the `AccountKey` field can exhaust the goroutine stack or consume excessive CPU/memory while decoding, potentially crashing or hanging the node that processes the request (RPC server goroutine, tx-pool ingestion goroutine, or block-processing goroutine when replaying a mined block containing such a transaction). Because transactions and their fields are also RLP-decoded independently by other nodes when they receive and process gossiped transactions or blocks, a single crafted submission could degrade or crash multiple nodes that decode the same payload — a network-wide availability impact matching the Medium severity of the source advisory.

### Likelihood Explanation
The attack requires only a single self-crafted RLP payload; no privileged access, no cryptographic key, and no coordination is needed. It is reachable via a standard public JSON-RPC call (`kaia_decodeAccountKey`) or via a normally-formatted `AccountUpdate`/`AccountCreation` transaction submitted through the public RPC, making the likelihood of exploitation reasonably high for any node exposing the RPC or accepting transactions from the network. The only bound on nesting depth is the transaction/payload size limit (`MaxTxDataSize`) — for the RPC call path even that ceiling may not apply, since `EncodeAccountKey`/`DecodeAccountKey` do not enforce `MaxTxDataSize`.

### Recommendation
Add an explicit recursion/nesting-depth check in `AccountKeyRoleBased.DecodeRLP` (and ideally in `AccountKeySerializer.DecodeRLP`) that rejects decoding as soon as a nested `AccountKeyTypeRoleBased` (or any composite type) is encountered, mirroring the existing `IsCompositeType` check but applied *during* decode instead of only after. Alternatively, track decode depth through the `rlp.Stream` (or a package-level counter passed through decode context) and abort with an error once a small fixed depth (e.g., 1, since nested RoleBased keys are never valid) is exceeded.

### Proof of Concept
1. Construct an RLP-encoded `AccountKeySerializer` byte string `S0` for an innocuous key type such as `AccountKeyTypeNil`.
2. Wrap `S0` into an `AccountKeyRoleBased` encoding: `L1 = RLP([S0])`, then wrap `L1` as `AccountKeySerializer{keyType: RoleBased, key: L1}` bytes `S1`.
3. Repeat step 2 N times (nest `S_{i}` inside a new `AccountKeyRoleBased` list to produce `S_{i+1}`), for as many iterations as the size budget allows (bounded only by `MaxTxDataSize` for the tx path, or unbounded for the direct RPC path).
4. Call `kaia_decodeAccountKey(S_N)` via JSON-RPC, or submit a `TxTypeAccountUpdate` transaction whose `AccountKey` field RLP-encodes to `S_N`, via `eth_sendRawTransaction`.
5. Observe that `AccountKeyRoleBased.DecodeRLP` recurses N times before any nested-composite-type check occurs, consuming stack/CPU proportional to N and potentially crashing or hanging the node.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}

func (s *KaiaAPI) DecodeAccountKey(encodedAccKey hexutil.Bytes) (*accountkey.AccountKeySerializer, error) {
	dec := accountkey.NewAccountKeySerializer()

		return nil, err
	}
