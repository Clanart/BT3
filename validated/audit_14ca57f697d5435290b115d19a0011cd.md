### Title
Forged aggregate Schnorr signatures from unbound nonce commitments - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary

`SchnorrAggregate::verify` pairs the aggregate's `Rs` array with `keys_and_challenges` solely by index, but the aggregation weight depends only on the ordered challenges. Because the nonce commitments and public keys are not bound into each weight, an unprivileged prover can calculate the weights and construct cancelling nonce commitments for arbitrary public-key/challenge pairs.

### Finding Description

`verify` rejects length mismatches, then initializes a transcript and appends every challenge before deriving a weight for each tuple position. [1](#0-0)  The resulting multi-exponentiation checks `sum_i z_i * R_i + sum_i z_i * c_i * A_i - s * G == 0`, where `R_i` comes from the attacker-controlled aggregate and `(A_i, c_i)` is supplied by index from `keys_and_challenges`. [2](#0-1) 

Neither `A_i` nor `R_i` is incorporated into the transcript used by `weight`; only the challenges are appended before the sequential calls to `weight`. [3](#0-2)  Consequently, all `z_i` values are publicly computable before constructing `R_i` and `s`, despite the aggregate's serialization accepting arbitrary attacker-controlled `R` values and `s`. [4](#0-3) 

### Impact Explanation

An attacker can produce a `SchnorrAggregate` that verifies for public-key/challenge pairs without possessing the corresponding private keys or valid constituent signatures. For each index, they choose a scalar `r_i`, compute its public weight `z_i`, set `R_i = r_i * G - c_i * A_i`, and set `s = sum_i z_i * r_i`. The verification expression then reduces to `s * G`, causing a forged aggregate to pass verification for arbitrary public keys and challenge-bound messages. [2](#0-1) 

### Likelihood Explanation

Any party able to invoke `SchnorrAggregate::verify` with chosen serialized aggregate bytes can perform the attack. `read` accepts an arbitrary vector of nonce points followed by an arbitrary scalar, and `verify` supplies the parallel public-key/challenge tuples used for index pairing. [4](#0-3) [5](#0-4)  The forgery requires only public keys, public challenges, group multiplication, and group addition; no private-key knowledge, malformed encodings, validator misbehavior, or malformed pairing is needed.

### Recommendation

Bind every aggregate component into the weight derivation. In particular, for each index, transcript the tuple position, public key, challenge, and corresponding `R` before deriving that tuple's weight, or derive each weight from a complete digest of the ordered list of `(public_key, R, challenge)` tuples. Ensure the same complete ordering is used by `SchnorrAggregator::aggregate` and `SchnorrAggregate::verify`, and add regression tests showing that permuting `Rs` or replacing them with cancelling values causes verification failure.

### Proof of Concept

Given target pairs `(A_i, c_i)`:

1. Instantiate the same verifier transcript and append every `c_i`, matching `verify`.
2. Derive each public weight `z_i`.
3. For every index, choose random scalar `r_i`.
4. Set `R_i = r_i * G - c_i * A_i`.
5. Set `s = sum_i z_i * r_i`.
6. Submit `SchnorrAggregate { Rs: [R_0, ...], s }`.

Verification computes:

```text
sum_i z_i * R_i + z_i * c_i * A_i - s * G
= sum_i z_i * (r_i * G - c_i * A_i) + z_i * c_i * A_i - s * G
= sum_i z_i * r_i * G - s * G
= 0
```

Thus `multiexp_vartime(&pairs).is_identity()` returns true even though no valid constituent Schnorr signatures or private keys were used. [2](#0-1)
