This confirms the full attack chain. The critical binding is: the withdrawal signature uses `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params` at `core/src/rpc/parser/operator.rs:182-187`, which is a Bitcoin sighash flag that only commits to input index 0 and its corresponding output index 0. It does not cover any other outputs of the transaction, including the OP_RETURN output that identifies the fronting operator.

### Title
Unauthenticated payout-attribution hijack via SIGHASH_SINGLE|ANYONECANPAY malleability of the operator OP_RETURN tag - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx` that an operator broadcasts to front a user withdrawal is signed by the user with `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) , enforced by the RPC layer at `parse_withdrawal_sig_params` [2](#0-1) . This sighash flag commits only to input index 0 and output index 0; it does not cover output index 2, the OP_RETURN output that records the operator's x-only public key used later to attribute the reimbursement [3](#0-2) . Because this OP_RETURN is unauthenticated by the signature, any unprivileged party who observes the broadcast (unconfirmed) `payout_tx` can rebuild an alternative, still-validly-signed transaction spending the same withdrawal UTXO with an arbitrary or garbage OP_RETURN payload, and get it mined instead (e.g. via a higher-fee replacement), before the original confirms.

### Finding Description
Verifiers attribute a confirmed payout to an operator purely by parsing the OP_RETURN of the transaction that actually lands on-chain: `update_finalized_payouts` extracts the x-only pubkey from the first OP_RETURN output of the mined payout tx and stores it as `payout_payer_operator_xonly_pk` [4](#0-3) . This value is later used both to find the next unhandled payout for a specific operator (`get_first_unhandled_payout_by_operator_xonly_pk`) [5](#0-4)  and to gate the operator's own manual reimbursement flow (`validate_payer_is_operator`, which errors if the recorded payer key doesn't equal `self.signer.xonly_public_key`) [6](#0-5) .

The equality this binding is supposed to enforce is:
`operator credited for payout == operator whose BTC actually paid the withdrawal input signature holder`

But the value that decides this equality — the OP_RETURN payload — is not covered by the presigned withdrawal signature's sighash (`SinglePlusAnyoneCanPay` only binds input 0 / output 0) [7](#0-6) . Consequently, once any operator broadcasts a `payout_tx` (visible pre-confirmation in the mempool, since it's a normal Bitcoin transaction with `DEFAULT_SEQUENCE`/RBF-fundable fields via `fund_raw_transaction` with `replaceable` unset which defaults to RBF-signaling in bitcoind) [8](#0-7) , an unprivileged attacker can:
1. Take the same signed key-path witness for input 0 (valid for any output-1/index-1+ modification, since sighash doesn't cover them).
2. Rebuild the transaction with the same output 0 (payout to the user — otherwise the sig is invalid) but a modified anchor (output 1, bumped fee) and a different OP_RETURN payload (output 2) — either garbage bytes (making `parse_op_return_data`/`XOnlyPublicKey::from_slice` fail so `operator_xonly_pk` becomes `None`) or another operator's genuine x-only key.
3. Broadcast this competing, higher-fee transaction so it replaces the original in the mempool/confirms instead.

The result: the true fronting operator's `self.signer.xonly_public_key` never matches the DB-recorded `payout_payer_operator_xonly_pk`, so `validate_payer_is_operator` will error out forever for that deposit [9](#0-8) , and `PayoutCheckerTask::run_once`'s automated lookup `get_first_unhandled_payout_by_operator_xonly_pk` will never surface this withdrawal for the honest operator either [10](#0-9) . If the attacker instead inserts a *different* honest operator's key, that operator (who never funded anything) becomes eligible to claim the kickoff/reimbursement for this deposit, since `is_kickoff_malicious` only checks that `kickoff_data.operator_xonly_pk` equals the DB-recorded payer key, not that this operator's wallet actually paid [11](#0-10) .

### Impact Explanation
This breaks the custody binding "the operator credited versus the party that paid" listed as a Critical impact class. Two concrete outcomes:
- The operator who genuinely fronted the withdrawal loses the ability to ever be reimbursed for the BTC it paid out of pocket — "an honest operator permanently unable to be reimbursed."
- A different, uninvolved operator can be made eligible to claim the reimbursement kickoff for a payout it never funded — "an operator reimbursed for a payout it never funded."

Both are explicitly listed Critical impacts.

### Likelihood Explanation
The only requirement is observing an operator's own broadcast, unconfirmed `payout_tx` in the mempool (a normal, public event) and racing it with a fee-bumped variant — no keys, roles, or privileged access are needed, since the SIGHASH_SINGLE|ANYONECANPAY signature never authenticates the OP_RETURN output. This is a fully unprivileged, network-level manipulation reachable by any observer, making likelihood high whenever an operator's payout transaction sits unconfirmed for even one block.

### Recommendation
Bind the operator-attribution OP_RETURN to the user's signature. Options: change the withdrawal signature's sighash type to cover all outputs (e.g., `SIGHASH_ALL|ANYONECANPAY`, or a per-operator commitment baked into the presigned message itself so the operator identity is fixed at signing time), or otherwise cryptographically commit the fronting operator's identity before broadcast (e.g., require the operator to also provide a signature over the whole transaction template, or use a distinct per-operator UTXO/connector rather than a mutable OP_RETURN as the sole attribution mechanism).

### Proof of Concept
1. Operator A broadcasts `payout_tx` for withdrawal W with witness satisfying `SinglePlusAnyoneCanPay` on input 0 / output 0, and OP_RETURN = A's xonly pk at output 2 [3](#0-2) .
2. Before confirmation, an attacker observes this tx in the mempool, copies input 0's witness (valid regardless of other outputs), and constructs `payout_tx'` spending the same withdrawal UTXO with the identical output 0, but replaces the anchor output with a higher-fee version and the OP_RETURN with either garbage bytes or operator B's xonly pk.
3. Attacker broadcasts `payout_tx'` with a higher fee rate so it replaces A's transaction and confirms.
4. `update_finalized_payouts` parses the mined tx's OP_RETURN and records `payout_payer_operator_xonly_pk` as `None` or B's key, never A's [12](#0-11) .
5. Operator A calls `get_reimbursement_txs`/its automated `PayoutCheckerTask`; both fail to find this payout attributable to A, permanently blocking A's reimbursement for BTC it actually paid out [9](#0-8) [10](#0-9) . If B's key was used, B can instead claim the kickoff/reimbursement for a payout it never funded, since `is_kickoff_malicious` only validates key equality against the DB record [11](#0-10) .
