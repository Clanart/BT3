### Title
Desktop disables Git's CVE-2024-32002 clone-hook protection, enabling hook-based RCE from malicious cloned repositories - ([File: app/src/lib/git/clone.ts])

### Summary
The EigenLayer report's underlying invariant break is: a mechanism meant to protect the trusting party (the staker's funds/shares) is instead disabled/bypassed by the delegated authority, and no compensating guard exists on the affected path. The GitHub Desktop analog: Desktop's `clone()` wrapper explicitly turns **off** a Git-upstream safety control (`GIT_CLONE_PROTECTION_ACTIVE`) that exists specifically to stop malicious repositories from planting executable Git hooks during a recursive clone, while Desktop's own "hooks environment" feature (new in 3.5.5) will happily discover and execute any hook it finds in `.git/hooks` (or `core.hooksPath`) on subsequent commit/pull/merge/push operations — with no separate "trust this repository" prompt for content that arrived via Desktop's own clone.

### Finding Description
`clone()` builds the execution environment for `git clone --recursive` and unconditionally sets: [1](#0-0) 

```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git introduced to enforce the fix for **CVE-2024-32002** — a case-confusable/symlinked submodule path (e.g. `a/.git/hooks/post-checkout` vs `A/.git/hooks/post-checkout` on case-insensitive filesystems, or via nested `.git` symlink tricks) that lets a malicious repository, cloned with `--recurse-submodules`, silently write an executable hook file into the *superproject's* `.git/hooks` directory. Git's protection refuses such clones/checkouts unless the caller explicitly disables it. Desktop disables it for every single clone it performs.

Separately, Desktop ships a first-class "hooks environment" subsystem that actively looks for and executes hooks found in a repository's hooks directory (resolved via `core.hooksPath` or the default git-dir path) as part of ordinary user actions: [2](#0-1) [3](#0-2) 

and hook execution spawns the discovered file directly with the user's shell environment: [4](#0-3) 

Every core Git operation Desktop performs on a freshly cloned repository intercepts one or more of these hook names, e.g. `commit` (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`), `merge` (`pre-merge-commit`, `post-merge`, `commit-msg`), `pull` (`pre-merge-commit`, `post-merge`, `pre-rebase`, `pre-commit`, `post-rewrite`), and `push` (`pre-push`): [5](#0-4) [6](#0-5) [7](#0-6) 

The hooks feature is enabled by default (`enableHooksByDefault()` gates `defaultHooksEnvEnabledValue`, and `getHooksEnvEnabled` is what gates whether `withHooksEnv` intercepts hooks at all): [8](#0-7) 

Existing "untrusted repository" guards in Desktop (`isRepositoryUnsafe` / "The Git repository ... appears to be owned by another user on your machine. Adding untrusted repositories may automatically execute files in the repository.") only apply to *locally discovered* repositories owned by a different OS user — not to a repository that Desktop itself just cloned from an attacker-controlled remote: [9](#0-8) [10](#0-9) 

That check never fires for the clone path in `clone.ts`, so a repository that arrives via `git clone --recursive` (including via the `x-github-client://openrepo/...` deep link handled by `parseAppURL`/`openOrCloneRepository`, or a "Clone repository" action a user performs against an attacker's URL) is never subjected to any "trust" gate, and the one Git-level control that would normally stop hook-planting through a malicious submodule structure has been explicitly turned off by Desktop.

### Impact Explanation
An attacker who controls a cloned/fetched repository (a public repo or fork with a crafted submodule) can plant an executable file at a path that Git's hook loader will treat as `.git/hooks/<hookname>` in the superproject once cloned with `--recurse-submodules` — exactly the class of attack CVE-2024-32002 was designed to stop. Because Desktop disables that stop with `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, and Desktop's own hooks subsystem is on by default and will execute any hook it discovers as soon as the user commits, pulls, merges, or pushes in that repository, the result is silent, unprompted arbitrary code execution in the user's shell environment (`spawn(gitPath, args, { env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' } })`), running with the user's own privileges. This matches the "Valid Impact" bar: attacker-controlled cloned/fetched repository content leading to code execution, achieved purely through Desktop's own default configuration.

### Likelihood Explanation
Every clone Desktop performs goes through this same `clone()` function and therefore always carries `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, so the mitigating Git-side control is unconditionally off — there is no code path where it is re-enabled. The hooks feature is enabled by default as of 3.5.5 per the changelog ("[New] Enable hooks support by default"), and no additional user confirmation/trust dialog exists for repositories obtained via clone. The remaining variable is whether a case-insensitive filesystem or symlink-planting technique against current Git/dugite versions can still successfully write the hook file despite other unrelated hardening in newer Git releases; this could not be independently verified within the available tool budget and would need to be confirmed against the specific `dugite`/git version Desktop bundles.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in `clone()`; let Git's native clone protection run, and only special-case it (if at all) after auditing why it was disabled. If it must remain disabled for compatibility, add an explicit, mandatory equivalent of the "unsafe repository" trust prompt after any recursive clone before Desktop's hooks subsystem is allowed to execute discovered hooks for that repository, and audit `getRepoHooks`/`with-hooks-env.ts` to refuse hooks whose files were introduced by the clone itself in nested/submodule `.git` directories rather than pre-existing local configuration.

### Proof of Concept
1. Attacker crafts a public repository containing a submodule whose path collides (via case-insensitivity or symlink tricks) with the superproject's `.git/hooks` directory, following the pattern of CVE-2024-32002, embedding an executable `post-commit` (or `pre-push`) script.
2. Victim clones the repository through Desktop (Clone dialog, or via the `x-github-client://openrepo/...` deep link handled by `parseAppURL` → `openOrCloneRepository`).
3. Desktop's `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` [11](#0-10) , so Git's built-in defense against the hook-planting submodule trick does not block the write of the malicious hook file.
4. The victim makes a commit, pull, merge, or push in the new repository through Desktop's normal UI. `withHooksEnv`/`getRepoHooks` discover the planted hook (default-enabled hooks environment) [12](#0-11)  and `hooks-proxy.ts` spawns it with the user's shell environment [4](#0-3) , achieving code execution with no trust prompt of any kind.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
