### Title
Coinbase outputs are reported as spendable `ReceivedOutput`s - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching outputs as `ReceivedOutput` values without recording that they are coinbase outputs or enforcing Bitcoin's 100-block maturity rule. [1](#0-0)  A downstream caller can therefore treat an immature coinbase payout to a watched Taproot script as available funds and construct or sign a transaction that Bitcoin consensus will reject until maturity. [2](#0-1) [3](#0-2) 

### Finding Description
`ReceivedOutput` is explicitly represented as "a spendable output" and carries only the scalar offset, `TxOut`, and `OutPoint`; it has no coinbase/maturity flag or block-height context. [4](#0-3)  `Scanner::scan_transaction` converts every matching `script_pubkey` into a `ReceivedOutput` keyed by `(txid, vout)`. [5](#0-4)  `Scanner::scan_block` invokes that routine over all `block.txdata`, including `txdata[0]`, which is the coinbase transaction under Bitcoin's block format. [1](#0-0) 

The spending path does not recover the missing maturity constraint: `SignableTransaction::new` accepts the supplied `ReceivedOutput`s, uses each `outpoint` as a transaction input, and stores the supplied `TxOut`s as Taproot prevouts. [2](#0-1)  The signing machine then commits to `Prevouts::All`, producing signatures for a transaction whose coinbase input is nevertheless invalid before maturity. [3](#0-2) 

### Impact Explanation
A miner or other party capable of supplying an accepted Bitcoin block can pay the monitored script in the coinbase and cause the scanner to report funds that cannot actually be spent for 100 blocks. [1](#0-0)  If those outputs enter a spend pipeline, the result is an incorrectly reported available balance and an invalid threshold-signed transaction, potentially stalling withdrawals or causing repeated signing/broadcast attempts. [6](#0-5)  The impact is bounded to temporary unsatisfiability rather than theft, making it Medium severity. 

### Likelihood Explanation
The vulnerable path is reachable from untrusted Bitcoin block data whenever a caller uses `Scanner::scan_block` to collect spendable wallet outputs. [7](#0-6)  Exploitation requires a block producer to direct a coinbase output to a watched script, which is economically costly but does not require access to Serai key material or validator privileges.  Serai's processor adapter separately skips `block.txdata[0]`, so deployments using that exact adapter avoid this particular path; the exposed wallet-level API remains unsafe for callers that rely on `scan_block`. [8](#0-7) 

### Recommendation
Change `Scanner::scan_block` to skip `block.txdata[0]` by default, matching the processor adapter's behavior. [8](#0-7)  Alternatively, add coinbase metadata and the containing block height to `ReceivedOutput`, and reject immature coinbase inputs in `SignableTransaction::new` or a wallet-level validation API. [9](#0-8) 

### Proof of Concept
A block producer mines a block whose `block.txdata[0]` coinbase transaction contains an output paying `p2tr_script_buf(key)`, where `key` is registered with `Scanner`. [10](#0-9)  Calling `Scanner::scan_block(&block)` returns that coinbase output as a `ReceivedOutput` with `offset == Scalar::ZERO`. [7](#0-6)  Passing that object to `SignableTransaction::new` creates an input referencing the coinbase outpoint and configures signing over it as a normal prevout. [2](#0-1)  The resulting transaction is cryptographically signed but consensus-invalid until the coinbase has matured, so the scanner reported received funds that were not spendable. [3](#0-2)
