### Title
Auctioneer signature is bound only to the raw `SearcherSig` bytes, not to the actual bid content, allowing bid-field substitution after auctioneer approval - ([File: kaiax/auction/bid.go])

### Summary
The Kaia auction (KIP-249) module verifies two signatures on every submitted `Bid`: the searcher's signature over the full EIP-712-encoded bid struct, and the auctioneer's signature. However, the auctioneer's signature is computed over `keccak256("\x19Ethereum Signed Message:\n" + len(SearcherSig) + SearcherSig)` — i.e., it signs the *bytes of the searcher signature*, not a digest of the actual bid parameters (`To`, `CallGasLimit`, `Data`, `MaxGasPrice`, etc.). This is directly analogous to the reported `CredibleAccountModule` bug: a signature (`userOpHash`/auctioneer-hash) is decoupled from the object it is supposed to authorize (`userOp`/bid content), and no code re-derives or cross-checks that the approved hash actually corresponds to the concrete data being executed.

### Finding Description
`Bid.GetEthSignedMessageHash()` in [1](#0-0)  builds the auctioneer digest solely from `b.SearcherSig`:

```go
func (b *Bid) GetEthSignedMessageHash() []byte {
    data := b.SearcherSig
    return crypto.Keccak256(fmt.Appendf(nil, "\x19Ethereum Signed Message:\n%d%s", len(data), data))
}
```

`ValidateAuctioneerSig` then only checks that the recovered signer of this digest equals the configured `auctioneer` address [2](#0-1) . It never re-derives the digest from the bid's actual fields (`TargetTxHash`, `BlockNumber`, `Sender`, `To`, `Nonce`, `Bid`, `CallGasLimit`, `Data`, and — in v2 only — `MaxGasPrice`, which is excluded from `EncodeData()` for the v2 typed-data hash used by `ValidateSearcherSig`, see `EncodeData` at [3](#0-2)  versus `bidV3.EncodeData` at [4](#0-3) ).

The bid-pool validation path (`validateBidSigs` in [5](#0-4) ) calls `ValidateSearcherSig` (binds sender/searcher to the bid struct) and `ValidateAuctioneerSig` (binds only to `SearcherSig` bytes) independently, and never checks that the fields not covered by the searcher's typed-data digest (in v2, `MaxGasPrice`) are consistent with anything the auctioneer actually reviewed.

Because `MaxGasPrice` is not part of `EncodeData()` for `AuctionVersionV2` bids, an attacker who intercepts (or otherwise obtains) a valid `(SearcherSig, AuctioneerSig)` pair for a v2 bid can construct a new `Bid` object with the same `SearcherSig`/`AuctioneerSig` bytes but an arbitrary `MaxGasPrice` value, and it will still pass both `ValidateSearcherSig` (unaffected, since the field isn't in the digest) and `ValidateAuctioneerSig` (unaffected, since it only checks `SearcherSig` bytes) in `bp.validateBid` → `bp.validateBidSigs` [6](#0-5) .

This mirrors the report's root cause exactly: a signature is trusted to authorize an entire payload, but the hash it actually covers omits (or is otherwise decoupled from) part of that payload, and no code enforces that the executed/propagated data matches what was actually signed for that unincluded field.

### Impact Explanation
`MaxGasPrice` from the bid is threaded through `EncodeAuctionCallData` for v3 auctions in [7](#0-6) , and is part of the auction entry-point's on-chain gas price cap enforcement. If an attacker can present a bid with a `MaxGasPrice` that the auctioneer never actually approved (because for v2-format signatures it is never bound into either signature's digest), a malicious bidder/searcher could smuggle a materially different gas-price cap into the bid the block proposer bundles and executes on-chain, potentially bypassing the auctioneer's intended cap and causing fee/economic abuse in the auction settlement (unauthorized value movement relative to what the auctioneer actually authorized). This directly matches the allowed impact categories ("fee ... abuse", "auction settlement theft").

### Likelihood Explanation
Reachable by any bidder/searcher/network peer that can submit bids via the `auction_submitBid` RPC or gossip a bid over the auction bid-pool p2p channel (`BidPool.HandleBid`), i.e., an unprivileged public actor as required by scope. No validator, node-operator, or consensus-message compromise is needed — it only requires reusing a previously observed valid `SearcherSig`/`AuctioneerSig` pair with a substituted `MaxGasPrice` (v2 bids), or more generally exploiting the general design flaw that the auctioneer signs over `SearcherSig` bytes rather than bid content.

### Recommendation
- Have the auctioneer sign a digest computed directly over the bid's EIP-712 struct hash (the same structured data the searcher signs, or a distinct auctioneer-specific typed-data hash that includes every field, including `MaxGasPrice`), instead of signing `keccak256("\x19Ethereum Signed Message:\n"+len(SearcherSig)+SearcherSig)`.
- Ensure the v2 `EncodeData()` includes `MaxGasPrice` (or reject/zero it for v2 bids on-chain) so no bid field can vary independently of what was actually signed by either party.
- Add an explicit check that `ValidateAuctioneerSig`'s covered content is cryptographically tied 1:1 to every field consumed by `EncodeAuctionCallData`/execution.

### Proof of Concept
1. Auctioneer approves a legitimate v2 bid `B` (searcher signs EIP-712 hash of `TargetTxHash, BlockNumber, Sender, To, Nonce, Bid, CallGasLimit, Data`; auctioneer signs `keccak256(EthSignedMessage(B.SearcherSig))`).
2. Attacker constructs `B'` = copy of `B` with `MaxGasPrice` changed to an attacker-favorable value, keeping `SearcherSig` and `AuctioneerSig` unchanged.
3. Submit `B'` via `auction_submitBid` → `ToBid` → `bidPool.AddBid` → `validateBid` → `validateBidSigs`:
   - `ValidateSearcherSig(B')` recomputes the v2 EIP-712 digest, which excludes `MaxGasPrice`, so it is identical to `B`'s digest → passes.
   - `ValidateAuctioneerSig(B')` recomputes the digest from `B'.SearcherSig` (unchanged) → passes.
4. `B'` is accepted into the bid pool with an unauthorized `MaxGasPrice`, and is later bundled/executed via `GetBidTxGenerator`/`EncodeAuctionCallData`, which does include `MaxGasPrice` in the v3 call encoding path used for execution semantics.

Note: full end-to-end confirmation of the exact on-chain gas-price enforcement effect requires inspecting the deployed `AuctionEntryPoint` (v3) contract logic, which is outside the indexed Go/Solidity mock code available here (only `AuctionEntryPointMock.sol` with signature checks commented out was found) — the real KIP-249 contract's enforcement of `MaxGasPrice` could not be directly verified in this codebase and should be confirmed with a full Devin session with complete repository access.

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}

func EncodeAuctionCallData(bid *auction.Bid, version string) ([]byte, error) {
