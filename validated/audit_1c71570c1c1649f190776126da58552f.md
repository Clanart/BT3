## Title
GitHub-host detection regex allows attacker domains to be trusted as GitHub Enterprise, enabling credential-helper OAuth phishing - (File: `app/src/lib/api.ts`)

### Summary
`isGitHubHost()` in `app/src/lib/api.ts` uses a loose regex, `/(^|\.)(github)\./`, to decide whether an arbitrary remote hostname should be treated as a trusted GitHub (Enterprise) host. Because the pattern only checks that the label `github` is followed by a dot and preceded by start-of-string or a dot, any attacker-registered domain such as `github.attacker.com` or `github.example.net` satisfies the match, even though it has no relationship to a real GitHub Enterprise Server deployment. This is the same class of bug as the reported `ZNSRootRegistrar`/`ZNSSubRegistrar` issue: absence of proper boundary validation lets an attacker craft a string that "looks like" a trusted namespace member (a GitHub subdomain) when it is not.

### Finding Description
`isGitHubHost` is used by the git credential-helper trampoline (`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`) to classify the host that git is currently authenticating against: [1](#0-0) 

```ts
// github.example.com,
if (/(^|\.)(github)\./.test(hostname)) {
  return true
}
```

This anchors on the label `github` immediately followed by `.`, and preceded by either the start of the string or a `.`. It does **not** verify that this label is the *last* meaningful part of the domain (i.e., it doesn't check that `github` is a suffix domain owned by GitHub). A hostname like `github.attacker.com` starts with `github.` and therefore matches `^github\.`, causing `isGitHubHost()` to return `true` for a domain fully controlled by an attacker who simply registers it.

`getEndpointKind()` calls `isGitHubHost(endpoint)` as its last-resort fallback classification step whenever a `WWW-Authenticate` header didn't disambiguate the host and no existing account is already stored for it: [2](#0-1) 

If `isGitHubHost` returns `true`, the endpoint is classified as `'enterprise'` rather than `'generic'`. In `getCredential()`: [3](#0-2) 

```ts
if (
  endpointKind !== 'generic' &&
  !accounts.some(a => a.endpoint === apiEndpoint)
) {
  ...
  const account = await ui.promptForGitHubSignIn(endpoint)
  ...
}
```

Because the endpoint is (mis)classified as `'enterprise'` instead of `'generic'`, Desktop skips the neutral "generic git credentials" prompt and instead invokes `promptForGitHubSignIn(endpoint)`, which opens Desktop's built-in GitHub Enterprise **sign-in** dialog for the attacker's hostname: [4](#0-3) 

```ts
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
```

This drives the full GitHub Enterprise OAuth/basic-auth sign-in flow against `origin` (e.g. `https://github.attacker.com`), which the user will see as a legitimate "Sign in to GitHub Enterprise" dialog rather than a benign "enter git credentials for this remote" prompt. Existing guards (`isDotCom`, `isGHE`, `isKnownThirdPartyHost`, the `WWW-Authenticate` realm check) do not catch this case because they run before the vulnerable regex and only rule out `github.com`/`*.ghe.com`/known third-party hosts — none of them reject a spoofed `github.*` prefix domain.

### Impact Explanation
An attacker who controls a git remote (e.g., serves an HTTP(S) git endpoint at `https://github.<attacker-domain>/...` and returns a 401 to the git credential negotiation, or is simply added as a remote/proxy the user fetches/clones from) can cause Desktop's credential-helper trampoline to believe the host is a legitimate GitHub Enterprise instance. This upgrades an ordinary "generic git auth" prompt into Desktop's real sign-in flow (`beginEnterpriseSignIn`/OAuth), tricking the user into completing an authentication ceremony against an attacker-controlled endpoint under the visual guise of "GitHub Enterprise sign-in." Depending on what the attacker's server does during that flow (serve a fake OAuth authorize/token page, or a Basic-Auth-style prompt), this can lead to credential/token phishing, and any GitHub identity/token established through this flow is subsequently trusted and reused for future operations against that same attacker endpoint, since Desktop stores the resulting `Account` keyed to `apiEndpoint`.

### Likelihood Explanation
Exploitation requires only that a victim add/clone/fetch from an attacker-controlled remote whose hostname begins with `github.` followed by any attacker-owned domain (trivial and cheap to register, e.g., `github.some-attacker.io`), and that a git operation triggers the credential helper (typical for any private-looking HTTPS remote that challenges auth). No local access, no prior malware, and no elevated privileges are needed — this fits squarely in the "attacker controls a git remote/proxy response" unprivileged threat model.

### Recommendation
Replace the substring/prefix-style regex with a proper suffix-domain check, e.g. verify `hostname === 'github.<tld>'` is not what's intended — rather, require that `github` appear as an actual owned domain label combined with an allow-list, or (safer) drop this heuristic entirely and rely only on `isDotCom`, `isGHE`, known accounts, and the `WWW-Authenticate` realm check, falling back to `'generic'` by default instead of guessing `'enterprise'` from a loose hostname pattern. If a heuristic must be kept, validate using proper effective-TLD-aware suffix matching (similar to `isKnownThirdPartyHost`'s `hostname.endsWith('.'+knownHost)` pattern) rather than a regex that also matches hosts where `github` is merely the *first* label.

### Proof of Concept
1. Attacker registers `github.attacker.tld` and stands up an HTTPS git server at that host that returns a `401` without a recognizable `WWW-Authenticate: realm="GitHub"` header (or one the attacker can't spoof) but otherwise looks like a plain HTTPS git remote.
2. Victim adds this URL as a GitHub Desktop remote/clone target: `https://github.attacker.tld/org/repo.git`.
3. When Desktop performs a git fetch/clone, `git`'s credential negotiation invokes Desktop's trampoline credential helper (`createCredentialHelperTrampolineHandler` → `getCredential`).
4. `getEndpointKind` fails the `isDotCom`/`isGHE`/known-account/`WWW-Authenticate` checks, then calls `isGitHubHost('https://github.attacker.tld')`.
5. `hostname = 'github.attacker.tld'` matches `/(^|\.)(github)\./` (matches at `^github.`), so `isGitHubHost` returns `true`, and `getEndpointKind` returns `'enterprise'`.
6. `getCredential` calls `ui.promptForGitHubSignIn('https://github.attacker.tld/...')`, which opens Desktop's real Enterprise sign-in dialog pointed at the attacker's origin, `dispatcher.beginEnterpriseSignIn` + `setSignInEndpoint('https://github.attacker.tld')`.
7. The victim, believing they are signing in to a legitimate GitHub Enterprise Server, may enter credentials or complete an OAuth-like flow that the attacker's server can harvest or otherwise abuse.

Note: I could not fully verify server-side behavior of the sign-in flow beyond `setSignInEndpoint`/`validateURL` (i.e., exactly what UI/network request sequence a malicious server can exploit further, such as OAuth authorize/token endpoints), since that depends on runtime behavior not fully covered by the indexed code. Confirming the full phishing surface (e.g., what exactly the enterprise sign-in dialog requests from the attacker server and how failure states are displayed) would benefit from a live/dynamic test in a Devin session.

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)

        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
