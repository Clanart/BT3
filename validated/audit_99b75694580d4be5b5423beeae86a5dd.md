### Title
`ReceivedOutput::read` accepts arbitrary `TxOut`s without verifying the output is spendable via the claimed offset — funds can be recorded as received yet be unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The reported bug class is a caller performing a value-affecting operation that fails silently because the return status is never checked, so state is updated (tokens minted/burned) despite the transfer not occurring. In Serai, the analogous unchecked-status path is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134`, which deserializes a claimed spendable output — a scalar `offset`, a `TxOut`, and an `OutPoint` — from untrusted bytes and returns `Ok` without verifying that the output's `script_pubkey` is a P2TR script that any offset could ever satisfy. The only places this inconsistency could be caught, `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`) and `Scanner`/`p2tr_script_buf` (`networks/bitcoin/src/wallet/mod.rs:80-86`), either return `None` (silently dropping the attempt) or are never invoked on the read path. The result is a "successful" representation of received funds that are cryptographically unspendable — the same "transaction succeeds, funds are lost" shape as the `invokeTransfer` report.

### Finding Description
`ReceivedOutput::read` performs three unchecked decodes:

- `Secp256k1::read_F(r)?` reads the scalar `offset` — no constraint that it is non-zero or that `key + G*offset` yields an even-Y point.
- `TxOut::consensus_decode` accepts *any* `script_pubkey` — it does not require the output to be P2TR, let alone the tweaked P2TR script derived from `offset` via `p2tr_script_buf`.
- `OutPoint::consensus_decode` accepts any outpoint.

Nothing ties the three fields together. `p2tr_script_buf` (`mod.rs:80-86`) returns `None` for odd-Y keys, and `Scanner::register_offset` (`mod.rs:180-196`) only inserts offsets that produce a valid even tweaked script — so for any fixed key there are `TxOut`/`offset` combinations that no legitimate `Scanner::scan_transaction` could ever emit, yet `read` accepts them all.

When such a `ReceivedOutput` is later fed to `SignableTransaction::new` (`send.rs:150-256`), the value is summed into `input_sat` (`send.rs:175`) and the output is spent as an input. Only at `multisig()` time (`send.rs:273-285`) does `p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey` get checked — and the failure mode is `None`, i.e., the spend silently cannot be constructed, exactly mirroring the report's "caller ignores failure status."

### Impact Explanation
A `ReceivedOutput` accepted via `read` is treated downstream as spendable balance: `SignableTransaction::new` adds its value to `input_sat` and builds a transaction consuming it. If the `offset`/`script_pubkey` pair is inconsistent (e.g., a non-P2TR script, or a script whose tweaked key no registered offset produces), `SignableTransaction::multisig` returns `None` and no signature machine can ever be created — the funds counted as inputs are permanently unspendable. This is the Serai analog of the audit finding's "transaction succeeds while the transfer failed": accounting treats value as received/available while it is not spendable, enabling loss of funds and possible over-payment of fees using phantom inputs.

### Likelihood Explanation
Reachability is established by the scope rules: untrusted bytes passed to `ReceivedOutput::read` are a permitted public-input surface. Any attacker who can cause such bytes to be deserialized (e.g., by supplying or corrupting the serialized `ReceivedOutput` stream consumed by the signer/wallet path) can inject an output whose value is credited as an input but can never be signed for. The decode itself always "succeeds" (`Ok`), so no error surfaces until signing silently fails with `None`.

### Recommendation
Either store the base key (or the expected tweaked `script_pubkey`) in `ReceivedOutput` and have `read` verify `p2tr_script_buf(key + G*offset) == Some(output.script_pubkey)`, rejecting any output that is not the exact P2TR script the offset authorizes; or, at minimum, have `read` enforce that `output.script_pubkey` is a v1 P2TR witness program so that only key-spendable outputs are admitted. Correspondingly, `SignableTransaction::new` should validate each input's offset against its prevout script at construction time and return a `TransactionError` rather than deferring the silent `None` to `multisig()`.

### Proof of Concept
Conceptual, using the library API:

```rust
// Deserialize a ReceivedOutput where `offset` is valid but `script_pubkey` is arbitrary
let mut bytes = vec![];
bytes.extend(Scalar::ONE.to_bytes());                  // any scalar
let fake_out = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_p2pkh(&PubkeyHash::all_zeros()), // not P2TR
};
bytes.extend(serialize(&fake_out));
bytes.extend(serialize(&OutPoint::default()));

// Succeeds — no check that script_pubkey matches any derivable tweaked key
let received = ReceivedOutput::read(&mut &bytes[..]).unwrap();

// Treated as a real, spendable input
let stx = SignableTransaction::new(
  vec![received], &payments, None, None, fee_per_vbyte,
).unwrap(); // Ok — value counted in input_sat

// Only here does it fail — and silently, as None
assert!(stx.multisig(&keys).is_none()); // funds "received" but unspendable
```
