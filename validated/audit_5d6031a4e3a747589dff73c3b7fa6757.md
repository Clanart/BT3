## Analysis

The seed report is about **rounding that releases more/less than the entitled share of an escrowed balance**, letting a user walk away with residual value the protocol assumed was accounted for. Hyperbridge's same-chain intent partial-fill path (`_fillSameChain` / `IntrinsicIntents.sol`) already patched the *pure rounding-dust* variant of this bug — the code explicitly hands the **entire remaining `_orders` balance** to the solver that completes the last unit of a given output leg instead of computing a proportional (rounded-down) share, and a dedicated regression test (`testPartialFill_RoundingDustReleasedToFinalSolver`, `IntentGatewayV2SameChainTest.sol:1550`) confirms dust is not stranded.

That very fix, however, introduces a different broken invariant: it releases **the whole `_orders[commitment][token]` bucket** rather than the amount actually earmarked for the specific output leg being completed. [1](#0-0) 

### Title
Full-balance escrow release on per-leg completion allows a solver to drain escrow reserved for other output legs of the same order - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_orders` tracks escrow **only by `(commitment, token)`**, not by output-leg index: [2](#0-1) 

When an order has multiple output legs whose corresponding `order.inputs[i]` entries use the **same token address**, all their escrowed amounts are summed into a single `_orders[commitment][token]` slot at placement time. In `_fillSameChain`, when a solver fully satisfies leg `i` (`amountFilled == totalRequired`), the code releases the *entire current balance* of that token bucket instead of the proportional amount tied to leg `i`:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

### Finding Description
This computation was written to fix leftover-dust rounding for the *last unit of a single leg*, but it silently assumes `_orders[commitment][token]` holds only that leg's escrow. If two (or more) input legs of the same order share a token address, the bucket instead holds the sum of both legs' escrow. Completing the smaller/faster leg first triggers the `amountFilled == totalRequired` branch and hands the solver the **combined balance for both legs**, not just the share belonging to the leg it filled.

`_withdraw` (`IntentsBase.sol:390-410`) then unconditionally decrements `_orders[commitment][token]` by the released amount without any per-leg bookkeeping to prevent this over-release, and `isFullyFilled` for the order overall remains `false` (because the other leg's `_partialFills` is still short), so the order is **not finalized** — leaving the second output leg's beneficiary/solver with an escrow balance of zero when they later attempt to complete it. [4](#0-3) 

### Impact Explanation
A solver can complete the cheapest/smallest leg of a multi-leg order backed by a duplicated input token and receive the **entire pooled escrow** for that token, even though part of it was reserved to pay for a different output leg. The remaining leg's later filler gets nothing (escrow already drained to zero), while the user's order is stuck half-filled with no way to recover the diverted funds through `_cancelSameChain`, since `_orders` for that token now reads zero and cancellation for that token silently skips it. This is a direct, unauthorized reallocation of escrowed value to an unintended party — a "stealing/loss of funds" and "wrong beneficiary or amount" outcome as defined by the bounty scope, reachable by any ordinary, unprivileged solver.

### Likelihood Explanation
Likelihood depends on whether `placeOrder`/order construction permits multiple `inputs[]` entries with the same token address feeding different output legs — nothing in `IntentsBase._validateParams` or the reviewed fill/cancel logic rejects duplicate input token addresses across indices, so this is plausible for legitimate multi-asset intents (e.g., "pay 60 USDC for output A and 40 USDC for output B"). Exploitation requires no relayer, prover, or admin collusion — a normal solver simply chooses to fill the smaller leg first.

### Recommendation
Track escrow per `(commitment, outputIndex)` rather than only per `(commitment, token)`, or explicitly compute the proportional amount still owed for the specific leg being completed (`order.inputs[i].amount - alreadyReleased[i]`) instead of reading the full aggregate `_orders[commitment][token]` balance. If duplicate input tokens across legs are not an intended feature, reject them at order-placement time.

### Proof of Concept
1. User places an order with two output legs both funded from the same input token (e.g. `inputs[0] = 60 USDC` → `output[0]`, `inputs[1] = 40 USDC` → `output[1]`), giving `_orders[commitment][USDC] = 100`.
2. Solver calls `fillOrder` supplying only the tokens required for `output[0]`. Since `amountFilled == totalRequired` for leg 0, `escrowedAmount = _orders[commitment][USDC] = 100` is computed and released in full to the solver via `_withdraw`.
3. `_orders[commitment][USDC]` is now `0`. `isFullyFilled` is `false` (leg 1 still open), so the order is not finalized.
4. Any solver later attempting to complete `output[1]` correctly supplies its output tokens, but the corresponding `escrowedAmount` for leg 1 resolves to `0` (bucket already drained) — they receive no input-token compensation, while the first solver walked away with 40 USDC that belonged to leg 1's escrow.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
