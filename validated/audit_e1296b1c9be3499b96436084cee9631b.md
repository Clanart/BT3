### Title
Live-pruning trie nodes are irrecoverably marked for deletion when a reverted tx-bundle triggers intermediate trie hashing/commit, causing state trie corruption on live-pruning nodes - ([File: work/worker.go])

### Summary
The Xen CVE (ALPINE-CVE-2024-31145) bug class is: flawed error-handling on a mapping-teardown path leaves a resource mapping in place (or, by extension, incorrectly torn down) when it should not be, because the error path does not correctly restore the pre-error state. Kaia has a directly analogous, already-demonstrated flaw in tx-bundle execution combined with live pruning: intermediate trie hashing performed while executing a bundle records nodes as "prunable" in the shared trie `Database`, but bundle failure/revert only restores the `StateDB`'s object-level snapshot — it does not undo the pruning marks that were already recorded against the shared trie database as a side effect of that (ultimately discarded) execution.

### Finding Description
Bundled transactions are executed speculatively and reverted on failure via `commitBundleTransaction`'s `restoreEnv`, which resets only the copied `StateDB` and header/gas bookkeeping: [1](#0-0) 

However, `Database.markPrunableNode`/pruning-mark bookkeeping lives in the shared `storage/statedb.Database`, not in the per-call `StateDB` copy, and is populated whenever a trie is hashed/committed to compute an intermediate root while stepping through the transactions inside the bundle: [2](#0-1) 

Those pruning marks accumulate in `db.pruningMarks`/`db.pruningMarksCache` and get flushed to `MiscDB` whenever `Cap` or `Commit` next runs: [3](#0-2) [4](#0-3) 

Because `restoreEnv()` only reverts `env.state` (the `StateDB` wrapper) and not the shared trie `Database`'s pruning bookkeeping, the marks recorded for nodes made "obsolete" by the reverted bundle sub-transaction survive the revert. Once the block is later committed and `bc.chPrune` triggers `pruneTrieNodeLoop`, those marks cause `PruneTrieNodes` to delete trie nodes that are, in fact, still referenced by the actually-committed (reverted-to) state, because the reverted-to state trie kept the "old" version of those nodes: [5](#0-4) [6](#0-5) 

This is functionally identical to the CVE bug class: an error/rollback path fails to properly reverse a resource-lifecycle side effect (mapping/pruning-mark) established before the error, so that side effect is applied erroneously later — resulting in state that should still be reachable (referenced trie nodes) being deleted, i.e., an "unmapping" that shouldn't have happened.

This exact defect is already reproduced and acknowledged in the test suite: [7](#0-6) [8](#0-7) 

### Impact Explanation
A block producer (miner) running with live pruning enabled that processes a transaction bundle containing a transaction that fails/reverts mid-bundle (e.g., due to `ErrNonceTooHigh`, `ErrRevertedBundleByVmErr`, `ErrTxGeneration`) will have its trie `Database` accumulate stale pruning marks for nodes that remain live in the actually-persisted state. When those marks are later processed by `pruneTrieNodeLoop`, the corresponding trie nodes are deleted from `StateTrieDB` even though the canonical state trie still needs them. This produces:
- State trie corruption / missing nodes on the affected live-pruning node, causing it to be unable to serve state reads, generate proofs, or continue block processing correctly — a state divergence between the affected honest live-pruning node and honest non-pruning/archive nodes.
- Because bundle inclusion and their revert conditions are attacker-influenceable (an unprivileged sender can craft a bundle that predictably reverts partway, e.g. by racing nonces or forcing an EVM revert), this is remotely triggerable by any user able to submit bundles to a live-pruning validator/miner, not merely a resource-only DoS: it can lead to permanent, unrecoverable state store corruption on that node.

### Likelihood Explanation
The trigger conditions are within reach of an ordinary transaction/bundle submitter: craft a bundle of ≥2 transactions where one intentionally fails (nonce-too-high or EVM revert) after a prior transaction in the bundle has already caused an intermediate trie commit. The test `TestTxBundleWithLivePruningByMiner` demonstrates this exact scenario succeeds in corrupting state under live pruning with an ordinary two-tx bundle and default nonce manipulation — no privileged access or consensus-message manipulation required. The main precondition is that the target node/miner has live pruning enabled and processes attacker-influenced bundles, which is an increasingly common node configuration for resource-constrained validators.

### Recommendation
Ensure that any pruning-mark bookkeeping performed against the shared trie `Database` as a side effect of intermediate root computation during bundle execution is scoped to the sub-transaction and rolled back together with `env.state` when a bundle is discarded/reverted (e.g., snapshot/restore `db.pruningMarksCache` alongside `env.state.Copy()`/`Set()`, or defer pruning-mark recording until the bundle is fully accepted). Alternatively, disallow live pruning together with bundle execution until this is fixed, and make `commitBundleTransaction`/`restoreEnv` symmetric with respect to all persistent, non-`StateDB`-scoped side effects of trie hashing.

### Proof of Concept
The codebase's own test reproduces the corruption end-to-end:
1. Enable live pruning (`bcdata.db.WritePruningEnabled()`) and enable the miner. [9](#0-8) 
2. Fund an "anon" account, then submit a 2-tx bundle from `anon` to `validator` where the second tx uses `nonce+100` so it fails with `ErrNonceTooHigh` and the bundle is reverted via `commitBundleTransaction`/`restoreEnv`. [10](#0-9) 
3. With live pruning enabled, `GenABlockWithTransactionsWithBundle` returns an error (state verification failure), confirming the state db becomes broken because pruning marks recorded during the reverted bundle sub-transaction are not rolled back — exactly matching the comment in the test: "State db will be broken because nodes marked as pruning during executing the bundle will be left in state db even though the bundle will be reverted." [11](#0-10) 

Note: I was unable to directly view the `StateDB.IntermediateRoot`/`Finalise` and `Trie.Commit`/`Hash` implementations within the available search results (the grep for those exact signatures returned no matches, likely due to index/formatting differences), so the precise call site that triggers `markPrunableNode` during bundle sub-transaction execution could not be pinpointed beyond the `Trie.markPrunableNode` definition itself. A Devin session with full repository access would be needed to confirm the exact call chain from `ApplyTransaction`/`commitBundleTransaction` into `markPrunableNode` and to implement the fix.

// Mark the node for later pruning by writing PruningMark to database.
func (t *Trie) markPrunableNode(n node) {
	// Mark nodes only if both conditions are met:
	// - t.pruning: database has pruning enabled, i.e. nodes are stored with ExtHash
	// - t.PruningBlockNumber: requested pruning through state.New -> OpenTrie -> NewTrie.
	if !t.pruning || t.PruningBlockNumber == 0 {
		return
	}

	if hn, ok := n.(hashNode); ok {
		// If a node exists as a hashNode, it means the node is either:
		// (1) lives in database but yet to be resolved - subject to pruning,
		// (2) collapsed by Hash or Commit - may or may not be in database, add the mark anyway.
		t.pruningMarksCache[common.BytesToExtHash(hn)] = t.PruningBlockNumber
	} else if hn, _ := n.cache(); hn != nil {
		// If node.flags.hash is nonempty, it means the node is either:
		// (1) loaded from database - subject to pruning,
		// (2) went through hasher by Hash or Commit - may or may not be in database, add the mark anyway.
		t.pruningMarksCache[common.BytesToExtHash(hn)] = t.PruningBlockNumber
	}
}

func (bc *BlockChain) pruneTrieNodeLoop() {
	// ReadPruningMarks(1, limit) is very slow because it iterates over the most of MiscDB.
	// ReadPruningMarks(start, limit) is much faster because it only iterates a small range.
	startNum := uint64(1)

	bc.wg.Go(func() {
		for {
			select {
			case num := <-bc.chPrune:
				if num <= bc.cacheConfig.LivePruningRetention {
					continue
				}
				limit := num - bc.cacheConfig.LivePruningRetention // Prune [1, latest - retention]

				startTime := time.Now()
				marks := bc.db.ReadPruningMarks(startNum, limit+1)
				bc.db.PruneTrieNodes(marks)
				bc.db.DeletePruningMarks(marks)
				bc.db.WriteLastPrunedBlockNumber(limit)

				logger.Info("Pruned trie nodes", "number", num, "start", startNum, "limit", limit,
					"count", len(marks), "elapsed", time.Since(startTime))

				startNum = limit + 1
			case <-bc.quit:
				return
			}
		}
	})

// PruneTrieNodes deletes the trie nodes according to the provided set of pruning marks.
func (dbm *databaseManager) PruneTrieNodes(marks []PruningMark) {
	batch := dbm.NewBatch(StateTrieDB)
	defer batch.Release()
	for _, mark := range marks {
		if err := batch.Delete(TrieNodeKey(mark.Hash)); err != nil {
			logger.Crit("Failed to prune trie node", "err", err)
		}
		if _, err := WriteBatchesOverThreshold(batch); err != nil {
			logger.Crit("Failed to prune trie node", "err", err)
		}
	}
	if err := batch.Write(); err != nil {
		logger.Crit("Failed to batch prune trie node", "err", err)
	}
}
