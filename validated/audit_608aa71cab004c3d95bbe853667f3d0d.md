### Title
`SignableTransaction`/`multisig` trusts the self-reported `ReceivedOutput` value instead of the actual on-chain amount, letting a forged prevout make the multisig sign a transaction that is invalid (or burns funds as fee) on-chain — (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The Maple bug class is "accounted" vs "actual" balance: `triggerDefault` used the loan's internally accounted `collateral()` counter instead of `balanceOf(loan)`, so unaccounted tokens desynchronized accounting and caused a revert/stuck funds. The analog lives in `bitcoin-serai`'s wallet: `ReceivedOutput` carries a `value` that is *claimed* alongside the outpoint, `ReceivedOutput::read` accepts it from raw bytes ( [1](#0-0) ), and `SignableTransaction::new`/`multisig` use that claimed value for input-summation, change, fee, and the Taproot `Prevouts::All` sighash commitment — while `multisig` only validates the `script_pubkey`, never the amount.

### Finding Description
`SignableTransaction::new` computes `input_sat` by summing `input.output.value` from the caller/`read`-supplied `ReceivedOutput`s ( [2](#0-1) ), uses it to pass the `NotEnoughFunds` check and to size the change output ( [3](#0-2) ), and stores the claimed `TxOut`s as `prevouts` ( [4](#0-3) ). At signing time `TransactionSignMachine::sign` commits `Prevouts::All(&self.tx.prevouts)` into every input's `taproot_key_spend_signature_hash` ( [5](#0-4) ). The only integrity check is in `multisig`, which verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — the address — but never compares `prevouts[i].value` to the actual UTXO amount ( [6](#0-5) ).

This mirrors the Maple issue exactly: the code assumes the "accounted" value embedded in the `ReceivedOutput` equals the real balance locked in the referenced outpoint. Bitcoin consensus binds a Taproot key-spend signature to the *actual* prevout amounts, so any divergence between the claimed `value` and the on-chain amount produces a validly-completed FROST signature over a sighash that no node will accept.

### Impact Explanation
An unprivileged party able to feed untrusted bytes into `ReceivedOutput::read` (or otherwise supply a `ReceivedOutput` whose `value` disagrees with the chain, e.g. a stale/conflicting serialized output) can:

- Inflate `value`: `NotEnoughFunds` is bypassed and a change output is computed from phantom satoshis; the multisig signs a transaction committing to amounts that don't exist, so the completed transaction is permanently unbroadcastable — the real UTXOs are not spent and the signing round is wasted (the direct analog of the `_disburseLiquidationFunds` revert / stuck-collateral outcome).
- Deflate `value`: the sighash still commits to the wrong amount → invalid signature on-chain; additionally the change computation subtracts against the understated input, pushing the difference into the declared fee field (`fee()` = `sum(prevouts) - sum(outputs)`, [7](#0-6) ), misreporting the fee the threshold group actually pays.

In both cases the honest participants produce "concrete signing of an unintended message" — a signature share set whose aggregate is worthless — and funds that appear spendable (a completed `Transaction`) are not.

### Likelihood Explanation
Reachability is via the documented untrusted-bytes surface (`ReceivedOutput::read`) or any caller constructing `ReceivedOutput` from data not re-validated against the chain — the struct's `value` is a pure claim with no consensus check anywhere in `send.rs`. The attack requires no key material, no collusion, and no validator misbehavior: a single inconsistent serialized output suffices, and the failure only surfaces after the full threshold protocol completes, making it a reliable griefing/DoS primitive rather than a probabilistic one. Severity Medium: no key leakage, but denial of the signing pipeline and phantom-balance accounting.

### Recommendation
In `SignableTransaction::multisig` (or `new`), bind the claimed amount to reality the same way the script is bound: either fetch each `previous_output`'s on-chain `TxOut` and assert `prevouts[i].value` matches (the `balanceOf` analog), or have `ReceivedOutput` carry a proof/derive its `value` exclusively from `scan_transaction` output observed on-chain and reject deserialized values that differ. At minimum, document and enforce that `ReceivedOutput`s passed to `new` must be freshly produced by `Scanner::scan_transaction`, and add a consensus-independent sanity check that the `outpoint` resolves to a UTXO with the claimed amount before producing shares.

### Proof of Concept
```rust
// networks/bitcoin context (conceptual)
// 1. Honest scanner observes a real UTXO of 100_000 sats to `key`'s p2tr script.
let real: ReceivedOutput = scanner.scan_transaction(&funding_tx).remove(0);
assert_eq!(real.value(), 100_000);

// 2. Attacker deserializes a forged ReceivedOutput: same outpoint/script,
//    but inflated value (read() performs no amount validation).
let mut forged = real.serialize();
// overwrite the TxOut value field inside `forged` bytes, or equivalently:
let forged = ReceivedOutput {
    offset: real.offset(),
    output: TxOut { value: Amount::from_sat(1_000_000), // phantom
                    script_pubkey: real.output().script_pubkey.clone() },
    outpoint: *real.outpoint(),
};

// 3. SignableTransaction::new accepts it; input_sat = 1_000_000 phantom sats,
//    change output sized accordingly.
let tx = SignableTransaction::new(vec![forged], &payments, Some(change_addr), None, fee)
    .unwrap(); // NotEnoughFunds bypassed

// 4. multisig() succeeds: script_pubkey matches; value is never checked.
let machine = tx.clone().multisig(&keys[&Participant::new(1).unwrap()]).unwrap();

// 5. All honest participants complete FROST; the signature commits
//    Prevouts::All with value=1_000_000 while the real UTXO is 100_000.
//    Broadcast fails: sighash prevout-amount mismatch => invalid signature.
//    Signing round is burned; the real funds remain unspent.
```
