### Title
Bank precompile `send` in legacy versions bypasses tokenfactory allow-list access control - (File: `precompiles/bank/legacy/v552/bank.go`, `v555/bank.go`, `v562/bank.go`, `v580/bank.go`, `v600/bank.go`)

### Summary
Multiple legacy versions of the bank precompile's `send` function call `p.bankKeeper.SendCoins(...)` directly instead of routing through the bank module's `MsgSend` handler, bypassing the `IsInDenomAllowList` check that enforces tokenfactory denom allow-lists. This is conceptually the same bug class as CVE-2021-21318: an access-control list associated with an entity (there: series ACL; here: tokenfactory `AllowList`) is not applied/enforced along an alternate code path that mutates or reads the protected resource, allowing the restriction to be silently bypassed.

### Finding Description
The tokenfactory module lets a denom admin restrict transfers of a denom to a specific allow-list of addresses via `MsgUpdateDenom` → `bankKeeper.SetDenomAllowList` [1](#0-0) . This allow-list is intended to be the sole gate for token movement, and it is enforced inside the bank module's `MsgServer.Send`/`MultiSend` handlers via `IsInDenomAllowList` checks on both sender and receiver [2](#0-1) .

However, the EVM bank precompile's `send` method — reachable by any ERC20-native-pointer contract, i.e. by any unprivileged EVM caller that holds the pointer address for a tokenfactory denom — calls `p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, ...)` directly in several legacy precompile implementations, completely skipping the `IsInDenomAllowList` gate: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The `SendKeeper.SendCoins` implementation itself contains no allow-list enforcement — the check lives only in the `msgServer.Send`/`MultiSend` wrapper [7](#0-6) , so calling `SendCoins` directly is equivalent to publishing/removing the resource without re-applying its access rules, exactly mirroring the Opencast ACL-drift bug class.

This was subsequently fixed starting at precompile version v601, where `send` was changed to build a `banktypes.MsgSend` and route it through `p.bankMsgServer.Send(...)`, which does perform the `IsInDenomAllowList` check [8](#0-7) . The current/head bank precompile (`precompiles/bank/bank.go`) also uses `p.bankMsgServer.Send` [9](#0-8) .

### Impact Explanation
If a tokenfactory admin sets an `AllowList` to restrict who can hold/receive/send a denom (e.g., for compliance or KYC purposes), any account holding the denom's ERC20 pointer contract address could still move funds to or from addresses outside that allow-list by invoking the vulnerable legacy precompile `send` path, since `SendCoins` performs no allow-list check on its own. This is an unauthorized-transfer/access-control-bypass bug affecting tokenfactory denoms with restricted allow-lists, reachable purely by a pointer/EVM caller — no privileged role required.

### Likelihood Explanation
Exploitability depends entirely on whether these legacy precompile code paths (`v552`–`v600`) remain reachable at the current chain height/version, i.e., whether the precompile version-dispatch mechanism (`precompiles/bank/setup.go`) still routes calls to these legacy implementations for certain historical EVM block heights (replay) or for contracts pinned to an older precompile ABI/version. I was not able to fully confirm from the indexed code whether these legacy versions are still live/dispatchable on the current running chain or are purely retained for historical block replay/verification purposes (`consensus_config_fuzz_test.go` and `setup.go` reference version-gated dispatch, but I could not trace the exact height-based selection logic within tool-call limits). If the versioned dispatcher only ever calls the current (fixed) implementation for new transactions and legacy code is only used for replaying old blocks, then this issue is not exploitable going forward and is already remediated. If any live-call path can still select `v552`–`v600` (e.g., via explicit version selection, or because upgrade height gating allows temporary reachability), the bug is directly exploitable by any address holding/being sent an ERC20-pointer-wrapped tokenfactory denom.

### Recommendation
- Confirm whether `precompiles/bank/setup.go`'s version-dispatch logic can route any live (non-replay) EVM call to `v552`–`v600` implementations of the bank precompile's `send` function.
- If reachable, patch those legacy implementations to route through `bankMsgServer.Send` (as done in v601+) or explicitly add `IsInDenomAllowList` checks before calling `SendCoins`.
- More generally, add allow-list enforcement inside `BaseSendKeeper.SendCoins`/`InputOutputCoins` themselves (defense-in-depth) rather than relying solely on the `MsgServer` wrapper, so that any current or future caller of the keeper method (precompiles, other modules, IBC, wasm bindings) cannot bypass the tokenfactory allow-list.

### Proof of Concept
1. Tokenfactory admin creates denom `factory/{admin}/foo` and calls `MsgUpdateDenom` with `AllowList{Addresses: [admin]}`, restricting all transfers to only the admin address [10](#0-9) .
2. Admin registers an ERC20 native pointer for `factory/{admin}/foo`.
3. An unprivileged holder of tokens (funded before/legitimately) that also controls the pointer contract calls the bank precompile's `send(sender, receiver, "factory/{admin}/foo", amount)` on a chain height/version dispatching to the vulnerable legacy implementation (`v552`–`v600`), with `receiver` an address NOT in the allow-list.
4. Because the vulnerable `send` invokes `bankKeeper.SendCoins` directly [11](#0-10) , the transfer succeeds to the disallowed receiver, whereas the equivalent `MsgSend` transaction would be rejected with `"is not allowed to receive funds"` as demonstrated in the bank module's own test for the fixed path [12](#0-11) .

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

func (p Precompile) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	// TODO: it's possible to extend evm module's balance to handle non-usei tokens as well
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}

	}

		return nil, 0, err

		return nil, 0, err
