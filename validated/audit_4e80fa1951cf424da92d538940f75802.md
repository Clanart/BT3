## Analysis: Storage/State cache desync analog in Cosmos EVM's `StateDB`

The Stylus bug is about a per-call storage cache accumulating "known values" that can drift from the real backing store when a nested/reentrant call shares storage state through a separate cache. The closest reachable analog in this repository is in the Cosmos EVM `StateDB` implementation, where in-memory `stateObject` balances (a cache of the account's target balance) can diverge from the real `x/bank` balance changed by a precompile call that shares the same account within the same transaction, and where this divergence is deliberately introduced for blocked/module addresses.

### Root cause

`StateDB.getStateObject` lazily loads and then permanently caches account state (including `Balance`) in `s.stateObjects` for the lifetime of the transaction [1](#0-0) . The cached `Balance` is only ever updated by explicit EVM-level `AddBalance`/`SetBalance`/`SubBalance` calls, which append `balanceChange` journal entries [2](#0-1) .

Precompile execution runs in a shared `cacheCtx` created once per StateDB via `GetCacheContext`/`cache()` [3](#0-2) , and directly mutates the real `x/bank` (and other module) state through keeper calls, independent of the `stateObjects` cache. To keep the EVM's cached balances consistent with what the precompile actually did to the bank store, `BalanceHandler.AfterBalanceChange` parses `CoinSpent`/`CoinReceived`/fractional-balance events emitted by the precompile call and pushes matching `AddBalance`/`SubBalance` calls into the StateDB [4](#0-3) .

Critically, this resynchronization is **explicitly skipped for blocked addresses** (module accounts, e.g. the precisebank reserve, staking/distribution/gov module accounts, ICS20 escrow accounts):

> "even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation can emit an x/bank event... To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB. Instead, the state changes... are applied directly via the MultiStore." [5](#0-4) 

So for any blocked/module address touched by a precompile call, the real bank balance is changed but the EVM's cached `stateObject.account.Balance` for that address is left untouched/stale — exactly the "storage cache becomes out of sync" pattern from the Stylus report, transplanted to Cosmos EVM's balance cache.

### Where the stale value gets committed

At the end of the transaction, `Commit()` iterates only the journal's **dirty** addresses and calls `SetAccount`, which calls `SetBalance` [6](#0-5) . `Keeper.SetBalance` does not overwrite the balance directly — it computes a **delta** between the StateDB's cached target `amount` and the *current* real spendable balance, then **mints or burns** that delta to force the real balance to match the stale cached target: [7](#0-6) 

This is the exploitable mechanism: if a blocked/module address (whose real balance was changed by a precompile mid-transaction, bypassing the EVM balance cache) is also marked "dirty" in the StateDB journal by any other EVM-level operation touching that address in the same tx, `Commit()` will forcibly mint or burn the delta between the stale in-memory value and the real (precompile-modified) balance — silently corrupting a module/escrow account's balance (minting spendable value out of thin air, or burning legitimately transferred funds).

### Impact

If reachable with a dirtying operation against a blocked address in the same transaction as a precompile call that moves funds into/out of that same address, this results in unauthorized minting or burning of native/EVM balance — matching the "Critical unauthorized minting, burning ... irreversible accounting corruption of spendable user value" impact class.

### Likelihood / confidence caveat

I was not able to fully trace, within the remaining tool budget, a concrete unprivileged code path that both (a) dirties a blocked/module address's EVM `stateObject` and (b) triggers a precompile call that changes that same address's real balance within one transaction. Blocked addresses (module accounts, escrow addresses) are not normally addressable as EVM `msg.sender`/`CALL` targets from ordinary contract logic, so reachability depends on whether any precompile (staking, distribution, gov, ICS20/IBC, or the `precisebank` reserve) exposes a code path where the EVM's `AddBalance`/`SubBalance` (or a value-bearing `CALL`) touches a blocked address address directly, or whether `SelfDestruct`/`CREATE2` collision tricks could pre-load such an address into `stateObjects` as dirty before a precompile call changes its real balance. This gap in verification means the finding should be treated as a **plausible high-severity design weakness with an explicitly documented sync bypass**, rather than a fully proven end-to-end exploit; further live tracing (ideally with a Devin session that can compile/run the integration test suite, e.g. extending `nested_evm_extension_test_suite.go` or the precompile balance-handler tests) would be needed to confirm concrete reachability and construct a working PoC transaction.

### Title
Stale EVM balance cache for blocked/module addresses causes mint/burn delta corruption on Commit - (File: `x/vm/keeper/statedb.go`, `precompiles/common/balance_handler.go`, `x/vm/statedb/statedb.go`)

### Recommendation
- Do not compute `SetBalance`'s mint/burn delta against a StateDB-cached target value for addresses whose real balance may have been modified out-of-band by a precompile within the same transaction; instead, either (a) refresh `stateObjects[addr].account.Balance` from the keeper immediately after any precompile call for *all* addresses touched by that call's events (including blocked addresses, using a safe non-recursive read-only balance refresh instead of skipping sync entirely), or (b) commit/refresh the affected state object before allowing further EVM-level mutation of it in the same tx.
- Audit all precompiles (staking, distribution, gov, ICS20/IBC, bank, precisebank) for any path where a blocked/module address's EVM state object can become "dirty" in the same transaction that a precompile also changes its real bank balance.

Given the uncertainty on concrete end-to-end reachability, I'm flagging this as requiring further live verification rather than asserting a fully proven Critical exploit.

// cache creates the stateDB cache context
func (s *StateDB) cache() error {
	if s.ctx.MultiStore() == nil {
		return errors.New("ctx has no multi store")
	}
	s.cacheCtx, _ = s.ctx.CacheContext()

	// Get KVStores for modules wired to app
	cms := s.cacheCtx.MultiStore().(storetypes.CacheMultiStore)
	storeKeys := s.keeper.KVStoreKeys()

	// Create and set snapshot store to stateDB
	snapshotStore := snapshotmulti.NewStore(cms, storeKeys)
	s.snapshotter = snapshotStore
	s.cacheCtx = s.cacheCtx.WithMultiStore(snapshotStore)
	s.writeCache = func() {
		s.ctx.EventManager().EmitEvents(s.cacheCtx.EventManager().Events())
		s.cacheCtx.MultiStore().(storetypes.CacheMultiStore).Write()
	}

	return nil
}

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
