### Title
Unrestricted balance sweep in `ManualCompound::compound()` allows theft of other users' pending reward/dust tokens - (File: `rewards/ManualCompound.sol`)

### Summary
`ManualCompound::compound()` computes the amount of each compoundable reward token to convert/lock/forward to the caller by reading the contract's *total* token balance (`IERC20(_tokenAddress).balanceOf(address(this))`) rather than the delta actually produced by the caller's own claim. This mirrors the `BunniHook` bug class described in the report, where a raw `balanceOfSelf()` check (instead of a before/after delta check) allows funds belonging to someone else to be swept into the current operation.

### Finding Description
In `compound()`:
```solidity
function compound(address[] calldata _lps, address[][] calldata _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp) external {
    uint256 rewardTokensLength = rewards.length;        
    IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
    ...
    for (uint256 i; i< rewardTokensLength; i++) {
        address _tokenAddress = rewards[i].tokenAddress;
        ...
        uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));
        if (receivedBalance > 0) {
            ... // convert / lock / transfer receivedBalance to msg.sender
        }
    }
}
``` [1](#0-0) 

`receivedBalance` is read as the entire raw balance of the reward token held by `ManualCompound`, with no snapshot of the balance taken before `multiclaimOnBehalf` is invoked. This is functionally identical to the flagged `BunniHook` bug, where `args.currency.balanceOfSelf() < args.amount` was checked against the raw balance instead of the balance *increase* attributable to the current operation, letting funds meant for someone else (am-AMM fees in the original report) leak into the current caller's flow.

Concretely, any of the following situations leave a non-zero balance of a `rewards[]` token sitting in `ManualCompound` between calls:
- Rounding/dust left over from `IConverter.convertFor`, `ILocker.lockFor`, or `ISimpleHelper.depositFor` in a prior `compound()` call.
- A prior `compound()` call reverting after `multiclaimOnBehalf` succeeded is not possible atomically (the whole tx would revert), but partial consumption inside `convertFor`/`lockFor` (e.g. `_convertRatio` only converts a portion and the converter is expected — but not guaranteed — to forward the remainder back to `msg.sender`) can leave residual balance owned conceptually by the prior caller.
- Because `_lps`/`_rewards` are fully caller-controlled and can be empty arrays, any unrelated wallet can call `compound([], [], 0, 0, false)` at any time; this skips the actual claim but still executes the second loop over the fixed `rewards[]` registry and sweeps whatever token balance currently sits in the contract to `msg.sender`. [2](#0-1) 

Since `compound()` is unauthenticated/unpermissioned (any wallet may call it for itself) and the sweep target (`msg.sender`) is entirely attacker-controlled while the swept amount is the *entire* balance rather than a delta tied to the caller's own claim, an attacker can race legitimate users' `compound()` transactions or exploit any leftover dust to redirect reward tokens that were destined for another user.

### Impact Explanation
Reward tokens (WOM, MGP, etc.) that are transiently held by `ManualCompound` on behalf of a legitimate compounding user — but not fully consumed/forwarded within that same transaction due to converter/locker rounding, or left over from a prior interrupted flow — can be swept by any other unprivileged wallet simply by calling `compound()` with empty/irrelevant `_lps`/`_rewards` arrays. This is a direct theft of another user's unclaimed/pending yield, matching the "theft or permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
Reachable by any ordinary wallet with no special privileges — `compound()` has no access control and accepts arbitrary (including empty) input arrays, while the vulnerable sweep loop over the protocol-defined `rewards[]` registry executes unconditionally on every call. The precondition (non-zero dust/residual balance in the contract) depends on rounding behavior of the configured `IConverter`/`ILocker`/`ISimpleHelper` implementations, which was not verifiable from the indexed contents of `SmartWomConvert.sol` in this session.

### Recommendation
Snapshot each reward token's balance in `ManualCompound` before calling `multiclaimOnBehalf`, and only act on the balance *increase* attributable to the current `compound()` call:
```solidity
uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
...
uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this)) - balanceBefore;
```
This mirrors the recommended fix in the original report (validating the balance delta rather than the raw balance).

### Proof of Concept
1. User A calls `compound()` and, due to `_convertRatio`/rounding inside the configured `_convertor` (`SmartWomConvert`), a small amount of the reward token remains in `ManualCompound` after the call instead of being fully consumed or refunded.
2. Attacker B immediately calls `ManualCompound.compound([], [], 0, 0, false)` (empty `_lps`/`_rewards`).
3. `multiclaimOnBehalf` is a no-op (empty arrays), but the second loop still executes for every token in `rewards[]`, reads `IERC20(_tokenAddress).balanceOf(address(this))` (which still includes User A's leftover dust), and forwards/converts/locks it to `msg.sender` = attacker B.
4. Attacker B receives tokens that were never part of their own claim, at User A's expense. [3](#0-2)

        uint256 rewardTokensLength = rewards.length;

        for(uint256 i; i < _lps.length; i++) {
            uint256 rewardLength = _rewards[i].length;
            if (rewardLength > 0) {
                for (uint j; j < rewardLength; j++) {
                    if (!compoundableRewards[_rewards[i][j]]) {
                        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                        if (rewardBalance > 0)
                            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                    }
                }
            }
        }
        for (uint256 i; i< rewardTokensLength; i++) {
            address _tokenAddress = rewards[i].tokenAddress;
            address _helperAddress = rewards[i].tokenHelper;
            address _convertor = rewards[i].convertor;
            address _locker = rewards[i].locker;
            uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));

            if (receivedBalance > 0) {
                if (_convertor != address(0)) {
                    IERC20(_tokenAddress).safeApprove(_convertor, receivedBalance);
                    IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2);
                } else if (_locker != address(0) && _lockMgp) {
                    IERC20(_tokenAddress).safeApprove(_locker, receivedBalance);
                    ILocker(_locker).lockFor(receivedBalance, msg.sender);                        
                } else if (_helperAddress != address(0)) { 
                    IERC20(_tokenAddress).safeApprove(_helperAddress, receivedBalance);
                    ISimpleHelper(_helperAddress).depositFor(receivedBalance, msg.sender);
                } else {
                    IERC20(_tokenAddress).safeTransfer(msg.sender, receivedBalance);
                }
            }
        }

        emit Compounded(msg.sender, rewardTokensLength, _lockMgp);
    }
