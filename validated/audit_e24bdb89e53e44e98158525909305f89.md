### Title
Front-runnable `registerCode` allows an unprivileged attacker to hijack a referral code before the intended owner, permanently redirecting future referral yield - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.registerCode(bytes32 _code)` assigns `codeOwners[_code]` on a strict first-come-first-served basis with no commit-reveal, reservation, or identity binding. Because the transaction and its `_code` argument are visible in the mempool before inclusion, any unprivileged actor can observe a victim's pending `registerCode` call and resubmit the identical call with higher gas to claim ownership first.

### Finding Description
`registerCode` checks only that the code is unoccupied: [1](#0-0) 
There is no proof-of-intent (e.g., commit-reveal hash, signature from a pre-registered identity, or code tied to `msg.sender`'s address) binding the code to the honest submitter before the code string itself becomes public on-chain/in-mempool. An attacker who sees the victim's pending `registerCode(_code)` transaction in the mempool can submit the same call with a higher gas price; because of standard EVM/mempool ordering by gas price, the attacker's transaction can be mined first, setting `codeOwners[_code] = attacker`. The victim's transaction then reverts with `CodeOccupied()`.

Subsequently, any referee who intends to use the victim's advertised code calls: [2](#0-1) 
`useCode` reads `codeOwners[_code]`, which now resolves to the attacker, so `myReferer[referee] = attacker`, and all future reward routing via `trigger()`: [3](#0-2) 
credits `refererInfo.rewardAmount` (attacker) instead of the intended owner. The only remediation path is `forceSetCodeOwner`, which is `onlyOwner`-gated and thus not something the victim can self-serve: [4](#0-3) 
No modifier, pause, or reentrancy guard addresses this race; the vulnerability is purely a lack of front-running protection in the registration flow.

### Impact Explanation
This matches the "theft of unclaimed yield" impact class: referral rewards (a share of `MGP` accrued via `trigger()`) that would have flowed to the legitimate code owner are instead permanently routed to the attacker for as long as referees keep using that code (and the code cannot be reclaimed by the victim without owner intervention). The loss is proportional to the volume of referee activity attributed to the squatted code.

### Likelihood Explanation
Feasibility is high in principle: no special privileges, capital, or leaked keys are needed — only mempool monitoring and a higher gas bid, both are standard front-running capabilities. However, exploitation requires the code string to already be circulating (e.g., in a not-yet-mined transaction) before the victim's code is registered; if the victim registers a code privately/early and only publicizes it after confirmation, the front-run window disappears. Thus likelihood is conditional on timing/behavior of the victim, not solely on contract logic, but the contract provides zero protection against the case that does occur.

### Recommendation
Add front-running resistance to code registration, e.g.:
- Use a commit-reveal scheme (`commitCode(hash(code, salt, sender))` then `revealCode(code, salt)` after a delay) so the plaintext code is not exposed before ownership is locked in, or
- Bind codes to `msg.sender` deterministically (e.g., derive from the registering address) rather than allowing arbitrary user-chosen bytes32 strings, or
- Allow a self-service dispute/reclaim mechanism (rather than only `onlyOwner` `forceSetCodeOwner`) for cases of clearly evidenced squatting within a short window after registration.

### Proof of Concept
Foundry test plan:
1. Deploy `ReferralStorage`, initialize with mock `vlMGP`/`masterMagpie`.
2. Simulate mempool front-run: have `victim` construct a `registerCode(CODE)` call but do not broadcast/mine it yet; have `attacker` call `registerCode(CODE)` first and mine it — assert `codeOwners[CODE] == attacker`.
3. Now mine victim's queued `registerCode(CODE)` call — assert it reverts with `CodeOccupied()`.
4. Have a `referee` call `useCode(CODE)` — assert `myReferer[referee] == attacker`.
5. Call `trigger(referee, amount)` from `masterMagpie` — assert `userInfos[attacker].rewardAmount` increases and `userInfos[victim].rewardAmount` remains zero, confirming yield diversion.

        if (_code == bytes32(0)) revert InvalidCode();
        if (codeOwners[_code] != address(0)) revert CodeOccupied();

        codeOwners[_code] = msg.sender;
        userInfos[msg.sender].myCode = _code;

        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
