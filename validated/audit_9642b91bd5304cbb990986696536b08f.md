### Title
Unbounded payment amounts produce consensus-invalid transactions that can never confirm, permanently stalling the spend plan — (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` only validates each payment's *lower* bound (`*amount < DUST` at send.rs:165-169) and never checks that individual amounts or their sum are within Bitcoin's `MAX_MONEY` range (21M BTC = 2,100,000,000,000,000 sats) or that `u64` additions don't overflow. A transaction built with an oversized payment is consensus-invalid yet is still fully constructed, signed via FROST (`multisig`/`Prevouts::All` binds prevout values, not output validity), and tracked by eventuality — matching the "duration=0" pattern: an accepted input makes the output permanently unworkable, with the spent inputs locked until manual intervention.

### Finding Description

In `SignableTransaction::new`:

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

- There is no upper bound on `amount`. `TxOut { value: Amount::from_sat(payment.1), ... }` happily accepts values exceeding Bitcoin's 21M-coin supply cap; such an output violates `MoneyRange` and the transaction is consensus-invalid forever.
- `payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` (send.rs:187) and `input_sat < (payment_sat + needed_fee)` (send.rs:215), plus `input_sat.checked_sub(payment_sat + fee_with_change)` (send.rs:228), can wrap/panic on `u64` overflow. In release builds wrapping can let the `NotEnoughFunds` check pass while the produced TX spends far more than its inputs — again permanently invalid.

### Impact Explanation

An unprivileged user who can influence a `Plan`'s payment `amount` (a withdrawal request is a `u64` sat value) causes the multisig to produce and sign a transaction the Bitcoin network will reject at consensus level (output > MAX_MONEY or outputs > inputs). The inputs are consumed/tracked as spent by the eventuality/scheduler layer, the TX can never confirm, and each re-attempt reproduces the same invalid transaction — an identical burn/retry cycle to the auction finding, resolvable only by operator intervention. Alternatively, in debug builds the overflow panics, killing the signing task (DoS).

### Likelihood Explanation

Reachable with public inputs: payment amounts are attacker-influenced `u64` fields; no key compromise, no malicious validator, no collusion required — only a sufficiently large or crafted payment value. The fix mirrors the report's recommendation exactly (a missing bound check on an accepted parameter).

### Recommendation

- In `SignableTransaction::new`, reject any `amount` exceeding Bitcoin's money range (`amount > Amount::MAX_MONEY.to_sat()` → new `TransactionError::PaymentTooLarge`).
- Use `checked_add`/`checked_sum` for `payment_sat` and `payment_sat + needed_fee`/`payment_sat + fee_with_change` arithmetic, erroring on overflow instead of wrapping or panicking.
