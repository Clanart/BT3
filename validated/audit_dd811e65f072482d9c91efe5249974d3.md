Let me examine the actual bounds-checking behavior of `is_atom_canonical`/`is_clvm_canonical` to confirm whether a crafted truncated CLVM buffer can trigger an out-of-bounds read/unhandled exception.### Title
Missing bounds check in `is_atom_canonical`/`is_clvm_canonical` length-prefix parsing allows a crafted spend bundle to trigger an out-of-bounds read (`IndexError`) during mempool admission - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` runs `is_clvm_canonical()` on every coin spend's `puzzle_reveal` and `solution` bytes as the very first admission check for a submitted spend bundle. `is_clvm_canonical()` delegates atom-length decoding to `is_atom_canonical()`, which reads a variable-length size prefix (1–6 bytes) directly out of the raw buffer without ever checking that the buffer actually contains enough bytes for the declared prefix length. This is structurally the same bug class as CVE-2018-19842's `getToken` in radare2: a length/token field controls how many additional bytes are read, and the reader trusts that length without validating it against the remaining buffer size, producing an out-of-bounds read on truncated/crafted input.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the high bits of `clvm_buffer[offset]` to determine `prefix_len` (0 to 5 additional bytes), then loops `prefix_len` times incrementing `offset` and indexing `clvm_buffer[offset]` again: [2](#0-1) 

There is no check anywhere in this function (or in its caller `is_clvm_canonical`) that `offset + prefix_len < len(clvm_buffer)` before dereferencing. If an attacker supplies a buffer whose last byte is a length-prefix marker (e.g., `0xF8`..`0xFF` class bytes) with fewer trailing bytes than the encoding requires, the loop indexes past the end of `clvm_buffer`, causing Python to raise an `IndexError` — the Python-level analog of a stack/heap buffer over-read in the CVE's C parser.

`is_clvm_canonical()` walks the same buffer token-by-token (treating `0xFF` as pair, `<=0x80` as small atom/NIL, else delegating to `is_atom_canonical`) and is invoked unconditionally on attacker-controlled `puzzle_reveal` and `solution` bytes from `validate_spend_bundle()`: [3](#0-2) 

`validate_spend_bundle()` is called from `add_spend_bundle()`, which has no exception handling around the call and is reached directly from spend-bundle submission (RPC `push_tx`, wallet transaction submission, or peer `new_transaction`/`respond_transaction` mempool admission): [4](#0-3) 

### Impact Explanation
An unprivileged spend-bundle submitter can craft a `CoinSpend` whose `puzzle_reveal` or `solution` byte string ends with a truncated multi-byte atom-length prefix. Because `is_clvm_canonical`/`is_atom_canonical` run before signature/condition validation and have no bounds checking, this raises an unhandled `IndexError` inside the mempool admission path instead of returning the expected `Err.INVALID_COIN_SOLUTION`. Depending on how far up the call stack the exception propagates uncaught, this can abort in-flight mempool-item processing for that bundle and, if not isolated per-task, disrupt the full node's transaction-processing pipeline — a spend-triggered processing halt for that code path, matching the "resource" (availability) impact class of the source CVE (CVSS `A:H`).

### Likelihood Explanation
High reachability: this check runs on every coin spend of every submitted spend bundle before any other content validation, and the triggering condition (a short/truncated atom-length prefix at the very end of `puzzle_reveal` or `solution`) is trivial for any wallet user, offer counterparty, or RPC caller to construct. No signature, special permission, or existing coin state is required to reach the vulnerable code — only a syntactically well-formed but truncated CLVM byte string.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access inside the prefix-length loop (and in `is_clvm_canonical`'s main loop before indexing `clvm_buffer[offset]`), returning a definitive non-canonical/invalid result (or raising a caught, well-defined `ValueError`) when the buffer is shorter than the declared prefix length, mirroring the defensive length checks already used elsewhere in the codebase (e.g., `skip_bytes`/`skip_list` in `chia/full_node/full_block_utils.py`, which validate `n > len(buf)` before consuming). Ensure `validate_spend_bundle`/`add_spend_bundle` treat any parsing failure here as `Err.INVALID_COIN_SOLUTION` rather than letting an exception escape.

### Proof of Concept
Submit a `SpendBundle` whose single `CoinSpend` has, e.g., `solution = SerializedProgram.fromhex("f8")` (or any buffer ending in a byte matching the `0b11111000`/`0b11111100`/etc. prefix-length markers with fewer trailing bytes than the declared prefix length). When `MempoolManager.add_spend_bundle()` invokes `validate_spend_bundle()`, the call `is_clvm_canonical(bytes(coin_spend.solution))` reaches `is_atom_canonical`, which increments `offset` past the end of the 1-byte buffer and executes `clvm_buffer[offset]`, raising `IndexError` instead of returning a graceful `Err.INVALID_COIN_SOLUTION` as intended by the code's design (compare with the graceful non-canonical parametrized cases in `chia/_tests/core/mempool/test_mempool_manager.py:130-156`, which only exercise buffers long enough to avoid this edge, not the truncated-prefix case). def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
