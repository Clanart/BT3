## Analysis

The FreshRSS CVE's failed invariant: **request content containing secrets is echoed verbatim into an error path that gets persisted to logs, with no redaction of sensitive values on the parse/auth failure path** — even though the same secret would presumably not be exposed in the normal/success path.

Protobuf has an explicit analog of this invariant: the `debug_redact` field option, whose entire purpose is to guarantee that fields marked sensitive never appear in human/log-visible output such as `DebugString()`. That protection is implemented for the TextFormat/DebugString surface but is **not** implemented for the ProtoJSON parsing surface in Java. [1](#0-0) 

When `com.google.protobuf.util.JsonFormat.Parser.merge()`/`parseFieldValue()` encounters a type mismatch (e.g. the JSON value for a scalar field is a `JsonObject` instead of the expected scalar type), it raises:
```java
throw new InvalidProtocolBufferException(
    "Invalid value: " + json + " for expected type: " + field.getType());
```
This directly serializes the raw, attacker-supplied JSON value — including string/bytes content — into the exception message, with **no check of `field.getOptions().getDebugRedact()`**.

Compare this to `TextFormat.java`, where the exact same class of value (a field's content) is *never* emitted without first consulting redaction state: [2](#0-1) [3](#0-2) 

I confirmed `debug_redact`/`DebugRedact` handling exists only in `TextFormat.java` and its supporting `Descriptors.java` redaction-state logic — `JsonFormat.java` contains zero references to it. That means a field explicitly annotated `[debug_redact = true]` by the schema owner (e.g. an API key, password, or token field) to guarantee it never leaks into debug/log output is **not protected** when parsing fails through the ProtoJSON path; its raw value is placed into the thrown exception's message.

### Why this transfers
- Attacker model matches: an ordinary client sending a bounded ProtoJSON payload through the public `JsonFormat.parser().merge(...)` API, with a trusted, valid schema that already opted into redaction via `debug_redact`.
- Exposure path matches FreshRSS: applications commonly catch `InvalidProtocolBufferException` at their API boundary and log `e.getMessage()` (or equivalent) for diagnostics — exactly analogous to `debugInfo()` being written to `log_api.txt` on `unauthorized()`/`badRequest()`.
- Missing check matches: FreshRSS failed to scrub the request body before logging; `JsonFormat.parseFieldValue` fails to consult the field's `debug_redact` state before embedding it in the exception, unlike its sibling `TextFormat` code path which does.

### Caveat
This is weaker than the original CVE in one respect: the value embedded is one the client itself supplied in the same request, not a separately-scoped secret. It still constitutes a real violation of the schema owner's stated confidentiality intent (`debug_redact`) if the value is a stored/merged field being echoed back during a merge-into-existing-message scenario, or if the JSON payload is proxied/logged by infrastructure with a different trust boundary than the original submitter (e.g., API gateways, WAFs, log aggregation systems, or where the field represents server-issued state the client is echoing back, such as a session/API token field that the app re-serializes and re-parses).

## Answer

### Title
ProtoJSON parser embeds raw field values in exception messages, bypassing `debug_redact` protections applied elsewhere - (File: `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`)

### Summary
`JsonFormat.Parser.parseFieldValue()` throws `InvalidProtocolBufferException` messages that directly interpolate the raw, unredacted JSON value received from the client when a type mismatch occurs. Protobuf's schema-declared `debug_redact` field option — designed specifically to prevent sensitive field contents from appearing in any debug/log-visible string — is honored by `TextFormat`'s `DebugString`/`Printer` machinery but is never consulted anywhere in `JsonFormat.java`. Consuming applications that log parse-failure exception messages (a standard practice, directly analogous to FreshRSS's `debugInfo()`/`log_api.txt` behavior) will leak the contents of fields the schema author explicitly marked as sensitive.

### Finding Description
`parseFieldValue()` builds its type-mismatch error as: [4](#0-3) 
No lookup of `field.getOptions().getDebugRedact()` (or the recursive message-option check implemented for TextFormat in `Descriptors.isOptionSensitive`) occurs before the value is concatenated into the exception message. Contrast this with the TextFormat printer, which memoizes redaction state per field and substitutes a `[REDACTED]` marker whenever `debug_redact` is set: [5](#0-4) 
and the corresponding Java printer, which checks `RedactionState`/`isOptionSensitive` before ever emitting a field's raw value: [3](#0-2) 
The JSON parsing path has no equivalent gate, so any sensitive scalar/message field that is sent with an unexpected JSON shape (e.g., a `string` field marked `debug_redact` sent as `{}` instead of a quoted string) has its value placed verbatim into `InvalidProtocolBufferException.getMessage()`.

### Impact Explanation
Any consuming application that logs, returns, or otherwise surfaces the message of a caught `InvalidProtocolBufferException` from ProtoJSON parsing (a very common error-handling pattern) will disclose the contents of fields the protobuf schema owner explicitly annotated as sensitive via `debug_redact`, undermining the confidentiality guarantee that option is meant to provide across the library. This mirrors the FreshRSS CVE's core issue: a value the application intended to keep out of logs is written to logs on the failure path due to a missing redaction check in exactly the surface designed to prevent it elsewhere.

### Likelihood Explanation
Moderate. It requires (1) a schema that marks a field `debug_redact = true`, and (2) a client/attacker able to submit a malformed ProtoJSON payload for that field (trivial — just send the wrong JSON type), and (3) the consuming application logging or otherwise exposing the raw exception message (common practice for API error diagnostics, though not universal). No privileged access is required beyond being an ordinary caller of the public `JsonFormat.parse()` API.

### Recommendation
In `JsonFormat.java`'s `parseFieldValue()` (and any other error paths in that file that interpolate `json`/field values into exception messages), consult the field's redaction state — reusing or mirroring `Descriptors`' `isOptionSensitive`/`RedactionState` logic already used by `TextFormat` — and substitute a `[REDACTED]` placeholder for fields (or their containing message options) marked `debug_redact` before constructing the exception message.

### Proof of Concept
1. Define a proto message with a sensitive field: `string api_token = 1 [debug_redact = true];`.
2. Call `JsonFormat.parser().merge("{\"apiToken\": {\"nested\":\"secret-token-value\"}}", builder)` — sending an object where a string is expected.
3. `parseFieldValue()` reaches the `json instanceof JsonObject` branch for a non-message field type and throws:
   `InvalidProtocolBufferException("Invalid value: {\"nested\":\"secret-token-value\"} for expected type: STRING")` [4](#0-3) 
4. Any code catching this exception and logging `e.getMessage()` writes the raw payload — including content the schema explicitly marked for redaction — to logs, in contrast to calling `message.toString()`/`DebugString()` on the same field, which would correctly print `[REDACTED]`.
