## Title
Stale rebase `abort`/`continue` race can advance HEAD past a user-requested abort - ([File: app/src/lib/stores/app-store.ts])

### Summary
The Aptos report describes a race where a stale, in-flight "resume" operation completes after a newer "pause" decision was made, allowing state to advance beyond a bound the newer decision was supposed to enforce. GitHub Desktop's rebase-conflict flow has a structurally similar pattern: `_continueRebase` and `_abortRebase` both invoke raw git state-mutating commands directly through `gitStore.performFailableOperation` with no shared "current operation" token, sequence number, or mutual-exclusion lock between them.

### Finding Description
`_continueRebase` (`app/src/lib/stores/app-store.ts:7469-7486`) calls `continueRebase()` and `_abortRebase` (`app/src/lib/stores/app-store.ts:7461-7467`) calls `abortRebase()`, each independently via `gitStore.performFailableOperation`, which is a bare async wrapper (error/retry handling) rather than a queue keyed to a specific in-progress rebase. [1](#0-0) 

The only guard against double-invocation lives in the *UI layer*, not the store: `ContinueRebase` disables its button while `isCommitting` is true, and `ConfirmAbortDialog` tracks a local `isAborting` boolean that disables its own submit button. [2](#0-1) [3](#0-2) 

Unlike the Copilot-conflict-resolution flow, which explicitly documents and guards against this exact class of bug ("Guards against a stale run ... clobbering the controller, progress, or result of the newer run" via an `ownsCurrentRun()` check tied to an `AbortController` identity comparison), no equivalent ownership token exists for rebase continue/abort. [4](#0-3) 

Because `dispatcher.continueRebase` performs `_continueRebase` → `_loadStatus` → `refreshRepository` as a multi-await sequence with no cancellation hook, and `dispatcher.abortRebase` performs `_abortRebase` → `_loadStatus` → `refreshRepository` independently, if a user triggers "Continue rebase" (long-running, e.g. large repo / hook execution via `interceptHooks`) and then, before that promise settles, a way exists to also dispatch "Abort" (e.g. through a race between the `ConfirmAbortDialog`'s `onSubmit` and a stale `ContinueRebase.onSubmit` promise that started before the button became disabled, or through dev-tools/automation bypassing the React state guard), both `git rebase --continue` and `git rebase --abort` end up running against the same on-disk rebase state with unspecified interleaving. [5](#0-4) [6](#0-5) 

The corrupted value is the repository's `HEAD`/working tree: if `continueRebase` finishes advancing HEAD to a new rebased commit *after* `abortRebase` has already run and reported "rebase aborted, back on original branch," the state cache and UI will reflect an aborted rebase while the actual on-disk ref has been moved forward by the stale continue — a silent divergence between what the user believes they committed/aborted and what git actually recorded, matching the "resume can advance state beyond what the pause/abort was supposed to enforce" pattern from the Aptos bug.

### Impact Explanation
If exploitable, this causes silent corruption of what the user believes they aborted — the rebase target branch's tip could be moved by a "ghost" continuation of a rebase the user explicitly asked to cancel, and this could later be pushed, propagating unintended commits to a shared remote.

### Likelihood Explanation
Likelihood is low/uncertain. This requires that a `continueRebase` call already be in flight (already past the UI's disabled-button check) at the exact moment `abortRebase` is also dispatched. React's synchronous state updates typically prevent this in normal UI interaction since both buttons live in mutually exclusive dialog steps (`ShowConflicts` vs `ConfirmAbort`), and I could not find local evidence of a concrete UI path that lets both fire concurrently — I was unable to fully trace whether `switchMultiCommitOperationToShowProgress` (called at the start of `onContinueAfterConflicts`) blocks the `ConfirmAbort` step from being reachable while continue is pending, due to remaining tool-call budget. This is a plausible structural weak point (absence of an ownership/sequence guard analogous to the one deliberately added for Copilot conflict resolution) rather than a confirmed, reproducible exploit path.

### Recommendation
Add the same ownership-token pattern used in `_startCopilotConflictResolution` (`app/src/lib/stores/app-store.ts:6956-6962`) to the rebase continue/abort flow: track an operation identifier/`AbortController` in `multiCommitOperationState` when `_continueRebase` starts, and have both `_continueRebase`'s completion handler and `_abortRebase` check/set that token before mutating state or issuing the next git command, rejecting a stale continue if abort has since taken ownership.

### Proof of Concept
Not independently reproduced. A conceptual repro: 1) start a rebase that hits conflicts and resolve them so "Continue rebase" is enabled, 2) trigger `dispatcher.continueRebase` with a slow `post-rewrite`/`prepare-commit-msg` hook (via `interceptHooks`) to keep the promise pending, 3) concurrently invoke `dispatcher.abortRebase` (e.g., via `Dispatcher` API directly, bypassing UI button disablement), and 4) observe whether `git rebase --continue` completes and advances HEAD after `git rebase --abort` has already reported success and cleared `multiCommitOperationState`.

  public async continueRebase(
    kind: MultiCommitOperationKind,
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    conflictsState: RebaseConflictState
  ): Promise<RebaseResult> {
    const stateBefore = this.repositoryStateManager.get(repository)
    const { manualResolutions } = conflictsState

    const beforeSha = getTipSha(stateBefore.branchesState.tip)

    log.info(`[continueRebase] continuing rebase for ${beforeSha}`)

    const result = await this.appStore._continueRebase(
      repository,
      workingDirectory,
      manualResolutions
    )

    // At this point, given continueRebase was invoked, we can assume that the
    // rebase encountered some conflicts and they have been resolved. Getting
    // now a CompletedWithoutError result means that the rebase has completed
    // successfully and there aren't more conflicts to resolve, therefore we can
    // track this as a successful rebase with conflicts.
    if (result === RebaseResult.CompletedWithoutError) {
      this.statsStore.recordOperationSuccessfulWithConflicts(kind)
    }

    await this.appStore._loadStatus(repository)

    const stateAfter = this.repositoryStateManager.get(repository)
    const { tip } = stateAfter.branchesState
    const afterSha = getTipSha(tip)

    log.info(
      `[continueRebase] completed rebase - got ${result} and on tip ${afterSha} - kind ${tip.kind}`
    )

    return result
  }
