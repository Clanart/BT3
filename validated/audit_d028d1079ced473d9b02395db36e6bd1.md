### Title
Missing per-participant preprocess/share count check causes index panic DoS in `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
Analogous to the `DebitaV3Loan::extendLoan` report — where a stray arithmetic computation reverts an otherwise-valid operation — the Bitcoin `TransactionMachine` pipelines in `networks/bitcoin/src/wallet/send.rs` perform unchecked indexing on attacker-controlled `Vec` lengths. `read_preprocess` deserializes a `Vec<Preprocess>` and `read_share` deserializes a `Vec<SignatureShare>` of arbitrary length per participant, but `sign` indexes `commitments[c]` for `c in 0 .. self.sigs.len()` and `complete` calls `shares.remove(0)`. A participant who supplies fewer preprocesses/shares than there are inputs causes an out-of-bounds panic, aborting signing for the whole transaction.

### Finding Description
`TransactionSignMachine::read_preprocess` builds `self.sigs.iter().map(|sig| sig.read_preprocess(reader)).collect()` yielding `Vec<Preprocess<Secp256k1, ()>>` whose length is entirely determined by the sender — nothing enforces it equals `self.sigs.len()` (the number of transaction inputs). In `sign`, the code then does:

```rust
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
``` [1](#0-0) 

If any participant's preprocess vector has `len() < self.sigs.len()`, `commitments[c]` panics. Symmetrically, `TransactionSignatureMachine::complete` does `shares.remove(0)` per input on each participant's `Vec<SignatureShare>`:

```rust
let sig = schnorr.complete(
  shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
)?;
``` [2](#0-1) 

`read_share` at line 409-411 accepts an empty `Vec`, so `remove(0)` on an empty vector panics during `complete`. These are `Vec` indexing operations — not length checks — gating an otherwise-legitimate signing round, mirroring the unused `extendedTime = maxDeadline - alreadyUsedTime - currentTime` subtraction that reverts valid loan extensions.

### Impact Explanation
Any participant in the threshold signing set can supply a truncated `Vec<Preprocess>` or `Vec<SignatureShare>` (e.g., zero elements) via the authenticated-but-untrusted preprocess/share channels. The honest coordinator/other signers panic mid-`sign`/`complete` rather than returning a `FrostError`, so a valid Bitcoin spend cannot be produced for that session — a forced-abort DoS on signing an otherwise-valid transaction, matching the finding class (legitimate operation fails due to unchecked computation on external input). Severity: Medium — liveness failure only, no secret leakage.

### Likelihood Explanation
Reachable by any unprivileged signing participant with only public inputs: the malicious bytes flow through `read_preprocess` (send.rs:351-353) or `read_share` (send.rs:409-411), both of which impose no length bound relative to `self.sigs.len()`. Multi-input transactions (multiple `AlgorithmMachine`s at send.rs:275-282) make the mismatch trivially triggerable. Panics in Rust abort/unwind the signing thread — whether this halts a coordinator process depends on the integrator, but the documented API returns `Result` and callers will not expect a panic on malformed peer input.

### Recommendation
Validate lengths before indexing: in `sign`, check `commitments.iter().all(|(_, c)| c.len() == self.sigs.len())` and return `FrostError` on mismatch; in `complete`, check each participant's share `Vec` has exactly `self.sigs.len()` elements (or use `Vec::pop`/`drain` with an explicit length check) before calling `shares.remove(0)`. Alternatively, deserialize into a fixed-shape `[Preprocess; N]`/per-input map keyed by input index so length mismatches are impossible by construction.

### Proof of Concept
```rust
// In-scope: networks/bitcoin/src/wallet/send.rs
// Signer builds a 2-input SignableTransaction -> TransactionMachine with sigs.len() == 2.
// Malicious participant P sends a preprocess encoding that reads as vec![], i.e.
// read_preprocess returns an empty Vec<Preprocess<Secp256k1, ()>>.

// sign() then executes:
//   (0 .. 2).map(|c| ... commitments[c].clone() ...)
// For P, commitments[0] indexes an empty Vec -> index out of bounds panic.

// Equivalent panic path in complete():
//   P's read_share returns vec![] (empty Vec<SignatureShare<Secp256k1>>)
//   shares.remove(0) on P's empty Vec -> "removal index ... out of bounds" panic
//   while processing input 0, before any signature share is validated.

// Result: entire signing session for a valid 2-input spend aborts with a panic
// instead of FrostError, even though all honest shares are correct.
```
