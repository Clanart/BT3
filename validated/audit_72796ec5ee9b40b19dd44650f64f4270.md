### Title
Transaction fee is calculated over an output set that excludes the OP_RETURN `data` output, producing an under-priced or unrelayable signed transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the required fee from the transaction's vbytes, but `calculate_weight_vbytes` only models `payments` (and optionally `change`). The OP_RETURN output constructed from the caller-supplied `data` (up to 80 bytes) is pushed onto `tx_outs` after the weight calculation and is never included in the vbyte estimate. The signed transaction therefore pays `needed_fee` computed over a smaller transaction than the one actually broadcast.

### Finding Description
In `SignableTransaction::new`, the `data` argument becomes an OP_RETURN output appended directly to `tx_outs` (send.rs, `if let Some(data) = data { tx_outs.push(...) }`). However, the fee path calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` and later `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`. `calculate_weight_vbytes` builds its model `Transaction` purely from `payments` plus the optional `change` output; it has no `data` parameter at all. The resulting `weight`/`vbytes` (and hence `needed_fee = fee_per_vbyte * vbytes`) omit the ~11–90+ bytes of the OP_RETURN output that is present in the real `tx`.

The change output amount is derived as `input_sat - payment_sat - fee_with_change` using the same underestimated fee, so the transaction is internally consistent but pays `needed_fee` — a fee rate below the requested `fee_per_vbyte` — and the `TooLowFee` minimum-relay check is also evaluated against the underestimated vbytes. With an 80-byte payload, the real vsize exceeds the estimate by roughly 90 vbytes; at `fee_per_vbyte` near the relay minimum the actual fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`.

### Impact Explanation
The vault signs a transaction whose true fee rate is lower than the caller specified, and which can dip below the network minimum relay fee. Inputs are committed to a `Sequence::MAX` (non-RBF) transaction paying `sum(inputs) - sum(outputs)`, so a transaction rejected by relay policy cannot be fee-bumped and must be abandoned and re-signed, leaving the inputs' funds temporarily unspendable. This is the direct analog of computing a charge over a base that omits a component: the fee base omits the `data` output just as the management fee base failed to exclude pending assets.

### Likelihood Explanation
Any caller passing a non-`None` `data` payload to `SignableTransaction::new` triggers the underestimation; 80-byte payloads maximize the error. Reaching the relay-minimum failure additionally requires a low `fee_per_vbyte`, but the under-payment relative to the requested rate occurs for every non-empty `data`.

### Recommendation
Include the data output in the weight model: pass the fully-formed `tx_outs` (or an equivalent `data: Option<&[u8]>` parameter) into `calculate_weight_vbytes` so both the `needed_fee`/`TooLowFee` check and the change-amount computation use the real transaction size.

### Proof of Concept
- `calculate_weight_vbytes` constructs its model transaction from `payments` and `change` only — no `data` field exists in its signature or body: `networks/bitcoin/src/wallet/send.rs` `fn calculate_weight_vbytes(inputs, payments, change)`.
- The OP_RETURN output is appended to `tx_outs` before the fee computation yet never fed into that model: `if let Some(data) = data { tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }) }` in `SignableTransaction::new`.
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None); let mut needed_fee = fee_per_vbyte * vbytes;` — fee derived from the data-less model.
- Change path repeats the omission: `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` then `input_sat.checked_sub(payment_sat + fee_with_change)`, so change is oversized and the actual fee equals the underestimated `needed_fee`.
- The relay-minimum check `if needed_fee < ((DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000)` uses the underestimated `vbytes`, so a transaction that is actually below the minimum relay fee can pass.
