### Title
Relayer fee balance is zeroed on dispatch, not on delivery, while the withdrawal message itself carries zero relayer incentive — ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
The relayer-fee `withdraw()` extrinsic dispatches an ISMP POST request to the destination host manager to disburse the relayer's accumulated fees, then immediately zeroes the on-chain `Fees` balance — before there is any proof that the request was ever delivered. The withdrawal request is itself dispatched with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }`, i.e. zero fee/zero payer, so ordinary Hyperbridge relayers have no economic reason to deliver it. This is the exact same "constant/zero relayer fee" pattern flagged in the external report, but here the consequence is stronger than discouraged participation — the source-side accounting commits to the withdrawal (erasing the balance) before the payout is confirmed on the destination, creating a real fund-loss window if that particular dispatch is never delivered.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  performs, in order: (1) `dispatcher.dispatch_request(...)` with a zero `FeeMetadata`, and (2) `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero())` right after the dispatch call succeeds — not after any destination-side receipt or delivery confirmation.

The dispatch itself is explicitly zero-incentivized: [2](#0-1) 

This zero-fee, zero-payer pattern for Hyperbridge-originated system messages (host-executive, intents-coprocessor, token-governor, and — as named directly — the relayer pallet's own withdrawal path) is independently documented as a known, unresolved incentive gap: [3](#0-2) 

The design doc's own proposed fix (`OutboundRequestDeliveryReward` keyed by `module_id`, claimed via `claim_outbound_request_delivery_reward`) defaults every module to **zero reward** until a governance extrinsic explicitly whitelists it: [4](#0-3) 

So even with the mitigation pallet present, the relayer-withdrawal module id is not incentivized unless and until governance runs `set_outbound_request_delivery_reward` for it (see the manual runbook, which treats this as an explicit, per-module opt-in step: [5](#0-4) ). Absent that governance action, third-party relayers have zero reason to deliver a given relayer's withdrawal POST.

The only thing currently making delivery likely is the withdrawing relayer's own tesseract client self-relaying the request it just submitted: [6](#0-5) 

That self-relay path persists the pending withdrawal to a local DB for crash recovery, but this is off-chain, best-effort resilience layered on top of an on-chain state machine that has *already* committed to zero balance the instant the dispatch call returned `Ok`. If the self-relay never completes — client crash before the DB write, lost/corrupted local DB, insufficient native/fee-token gas on the destination chain to complete delivery, or simply no other altruistic relayer picking it up because the fee is zero — the relayer's `Fees` entry is already zero on Hyperbridge, and no other on-chain record exists that the balance is still owed.

### Impact Explanation
This falls under "loss of funds," which the bounty gate explicitly accepts. A relayer's rightfully earned fees can be erased on Hyperbridge with the payout resting entirely on a zero-incentive ISMP dispatch plus the relayer's own client software behaving reliably. Any interruption between dispatch acceptance and destination delivery — a scenario the code comments themselves acknowledge ("a crash between submit and accumulation doesn't lose the reward" is guarded for accumulation, but no equivalent atomic guarantee exists for the withdrawal-zeroing step) — permanently destroys the relayer's economic claim with no recourse, since `Fees` has already been zeroed and the destination-side credit never materializes.

### Likelihood Explanation
No malicious peer, prover, or governance actor is required. This is triggered by ordinary operational conditions inherent to the current design: the withdrawal dispatch is unconditionally zero-fee, so third-party pickup cannot be relied upon, and the fallback (self-relay by the withdrawing relayer's own tesseract instance) is a single point of failure with no on-chain re-issuance mechanism if it fails. Any relayer running standard tesseract tooling under normal failure modes (process crash, disk loss, destination-chain gas exhaustion) is exposed.

### Recommendation
Do not zero `Fees` synchronously with dispatch acceptance. Either (a) zero the balance only after a destination-side delivery receipt is proven back to Hyperbridge (mirroring the receipt-proof pattern already used by `accumulate_fees` / `OutboundRequestDeliveryClaim`), or (b) keep a recoverable "pending withdrawal" record on-chain keyed by commitment that can be re-dispatched or refunded if the original request is never delivered within a bounded window. Independently, apply the `OutboundRequestDeliveryReward` incentive (already scaffolded in `outbound_request.rs`) to the relayer pallet's own `MODULE_ID` by default, rather than requiring a separate governance opt-in, so third-party relayers have an actual economic reason to deliver these withdrawal messages instead of relying solely on self-relay.

### Proof of Concept
1. Relayer R accumulates fees on Hyperbridge for destination chain D (via `accumulate_fees`), so `Fees::<T>::get(D, R) = X`.
2. R calls `Pallet::withdraw` with a valid signature. `dispatch_request` is called with `FeeMetadata { payer: 0, fee: 0 }` — see [7](#0-6) .
3. Immediately after, `Fees::<T>::insert(D, R, 0)` runs — [8](#0-7) . On-chain, R now shows zero accrued fees for D, regardless of what happens next.
4. R's tesseract process is the only party economically motivated to deliver the resulting POST request (no other relayer earns anything for it, per `docs/outbound-request-incentivization.md`). If that process crashes before writing the pending-withdrawal row to its local DB, or the DB is lost, or the destination submission subsequently fails and is never retried, the POST request is never delivered.
5. R has no on-chain balance (`Fees` is zero) and no destination-side payout — the amount `X` is unrecoverable through the normal flow.

**File:** docs/outbound-request-incentivization.md (L9-11)
```markdown
A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.
```

```markdown
pub fn set_outbound_request_delivery_reward(
    origin: OriginFor<T>,
    module_id: BoundedVec<u8, ModuleIdBound>,
    amount: BalanceOf<T>,
) -> DispatchResult {
    T::RelayerOrigin::ensure_origin(origin)?;
    OutboundRequestDeliveryReward::<T>::insert(&module_id, amount);

        module_id,
        new_reward: amount,
```
