### Title
Deposits to the retiring multisig's external address during `ForwardFromExisting`/`ClosingExisting` are scanned, marked seen, then dropped — funds received but never spendable - (File: processor/src/multisigs/mod.rs)

### Summary
An unprivileged Bitcoin sender can deposit BTC to the retiring multisig's external (offset-zero) P2TR address during the key-rotation window. The output is scanned by `Scanner::scan_transaction`, recorded as `seen`, and emitted in a `ScannerEvent::Block`. During processing, `scanner_event_to_multisig_event` only creates a `Forward` plan for outputs that carry a parseable `InInstruction` (`instruction` is `Some`), and only creates a `Refund` plan when `refund_to` decodes to a valid address. A plain Bitcoin send (no embedded Serai data, or undecodable data with no refund address) produces neither, so the output is retained — and then unconditionally dropped a few lines later because `step` is `ForwardFromExisting`/`ClosingExisting` and `output.key() == existing.key`. The code assumes it "will report it once it hits the new multisig," but no forwarding plan was ever made, so the output never reaches the new multisig, is never credited on-chain, and — because `seen` is already set — is never re-scanned. The scheduler never receives the UTXO, so the funds are permanently unspendable.

### Finding Description
`get_outputs` scans every non-coinbase transaction output matching a registered `script_pubkey` and classifies it via the `kinds` offset map; an external deposit yields `OutputType::External` regardless of whether the sender embedded any Serai data [1](#0-0) . Outputs are then permanently marked `seen`/inserted into `ram_outputs` by the scanner, so a dropped output can never be re-emitted [2](#0-1) . In `scanner_event_to_multisig_event`, forwarding plans are only built when `instruction_from_output::<N>(output)` returns `Some(instruction)` or a consumable `refund_to`; an output with neither is retained [3](#0-2) . Immediately after, every retained output to the existing key is dropped whenever the rotation step is `ForwardFromExisting` or `ClosingExisting`, on the assumption it was already forwarded [4](#0-3) . `PlanFromScanning::Forward`/`Refund` plans are the only mechanisms that would carry the UTXO into the scheduler, so a dropped output is never passed to `scheduler.schedule`/`add_outputs` [5](#0-4) . The on-chain UTXO therefore exists, is spendable cryptographically (P2TR key-path under `key + offset*G`), yet no Plan will ever reference it — it is stranded forever.

### Impact Explanation
A user's deposit to the retiring multisig during the rotation window is burned: confirmed on-chain, acknowledged by the scanner, but never credited, never forwarded, never refunded, and never spendable. This is the direct analog of the report's "liquidator receives vault tokens it cannot redeem": value is received by the vault side but the redemption/spend path is unavailable, and it is irreversible (`seen` prevents reprocessing). Loss of user funds, Medium severity (requires the timing window of multisig rotation, but rotation is a normal, recurring protocol event and the sender needs no privilege — the external address is public).

### Likelihood Explanation
Requires a deposit to land in a block while `step` is `ForwardFromExisting` or `ClosingExisting` with the output addressed to the existing key, and for the deposit to carry no valid `InInstruction` and no decodable refund address (or a refund path that fails `refund_to.consume().try_into()`). This is reachable by any unprivileged sender making a plain Bitcoin transfer to the deposit address at the wrong time — precisely the "time of need"/edge-window shape of the original report, where the receiver holds assets it cannot use.

### Recommendation
In `scanner_event_to_multisig_event` (processor/src/multisigs/mod.rs), do not silently drop retained outputs to the existing key during `ForwardFromExisting`/`ClosingExisting`. For outputs where `instruction_from_output` yields no instruction and no valid refund, either (a) create a forward plan unconditionally when `N::Scheduler::shim_forward_plan` is `Some`, regardless of instruction presence, or (b) route them into the scheduler's normal UTXO pool so they are swept by the closing plan. At minimum, outputs that will be dropped must not be marked `seen`/must be refunded.

### Proof of Concept
1. Multisig rotation begins; `current_rotation_step` returns `ForwardFromExisting` for block `n` (new key activated, existing not yet retired).
2. Attacker/victim broadcasts a Bitcoin transaction paying `X` sats to `p2tr_script_buf(existing_key)` (offset ZERO → `OutputType::External`), with no `InInstruction` data embedded in the inputs.
3. `get_outputs` returns `Output { kind: External, output, .. }`; scanner marks its outpoint `seen` and emits `ScannerEvent::Block`.
4. In `scanner_event_to_multisig_event`: `output.key() == existing.key`, `instruction_from_output` returns `(None, None)` → no `Forward`/`Refund` plan → `should_retain == true`.
5. The drop check at lines 922-929 matches (`step == ForwardFromExisting`, `output.key() == existing.key`) → output removed, never reported, never scheduled.
6. Result: UTXO confirmed on-chain under the multisig's control, absent from every Plan and from `scheduler.utxos`; unspendable and uncreditable forever.

*Note on confidence: the drop path and plan-creation conditions were verified directly; `instruction_from_output`'s exact return for data-less outputs and `shim_forward_plan`'s `Some`/`None` for the UTXO scheduler could not be fully read in available iterations, but the retention-then-drop structure guarantees stranding whenever no `PlanFromScanning` entry is produced for the output.*
