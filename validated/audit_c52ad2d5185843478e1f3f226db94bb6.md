### Title
`ThresholdKeys::read` accepts semantically inconsistent key material (secret share vs. verification shares never validated), letting unauthenticated bytes be treated as authentic keys - (File: crypto/dkg/src/lib.rs)

### Summary
PackageKit 0.6.17 installed unsigned RPMs as though they were signed: unauthenticated input was accepted as authenticated because the authenticity check was skipped. The analog in Serai is `ThresholdKeys::read`, which deserializes `secret_share` and `verification_shares` and passes them to `ThresholdKeys::new`, where only structural properties (share count, participant index bounds, interpolation applicability) are checked — never that `secret_share * G == verification_shares[i]` or that the verification shares form a consistent set for the claimed `group_key`. Attacker-influenced key bytes are therefore accepted as valid keys and used for signing.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation variant, a `secret_share` scalar, and `n` verification shares, then constructs keys via `ThresholdKeys::new` [1](#0-0) . `ThresholdKeys::new` only validates `verification_shares.len() == n`, that participant indexes are `<= n`, the interpolation variant's applicability, and computes `group_key` as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` [2](#0-1) . Nowhere is `secret_share * C::generator() == verification_shares[i]` checked, nor that the shares are mutually consistent.

The consequences materialize downstream. In `view()`, the interpolated secret share and interpolated verification shares are computed independently, so inconsistency silently propagates [3](#0-2) . In FROST `complete`, the aggregate signature fails, the per-share blame batch runs, and the holder's own share fails against the attacker-chosen `verification_share` — the FROST code itself acknowledges this path: "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" [4](#0-3) . The holder's own share is queued for blame like any other share [5](#0-4) .

Additionally, `group_key()` is derived entirely from the (untrusted) verification shares — an attacker can craft bytes whose resulting `group_key` corresponds to a private key nobody holds, so any outputs scanned/attributed to that key are unspendable [6](#0-5) .

### Impact Explanation
An unprivileged party who can influence the bytes fed to `ThresholdKeys::read` obtains keys accepted as authentic while being semantically invalid. Two concrete impacts: (1) the holder is deterministically blamed as faulty during FROST signing (`FrostError::InvalidShare(holder)`), enabling wrongful attribution of fault/slashing to an honest participant; (2) funds sent to the resulting `group_key` may be unspendable, i.e., funds reported received that are not spendable.

### Likelihood Explanation
Exploitation requires attacker control over serialized `ThresholdKeys` bytes (e.g., a compromised or malicious coordinator/peer supplying key material, or tampered storage). The read path is explicitly exposed to untrusted bytes, and no integrity check (MAC, signature, or self-consistency) stands between `read` and signing use. Medium likelihood: it needs a delivery vector for the bytes, but no cryptographic break is required once delivered.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), assert `C::generator() * secret_share == verification_shares[params.i()]`, and optionally verify the verification shares form a consistent polynomial set (e.g., that interpolation over any `t`-subset yields the same `group_key`). At the storage layer, authenticate serialized key material (MAC/signature bound to the session context) so forged bytes are rejected before parsing.

### Proof of Concept
1. Craft serialized bytes for `ThresholdKeys::<C>::read`: valid `C::ID`, `t`, `n`, `i`, `Interpolation::Lagrange` (`0x01`), an arbitrary `secret_share` scalar, then `n` attacker-chosen points as `verification_shares` such that `Σ share_i * λ_i` over `1..=t` equals an attacker-selected `group_key` (e.g., `verification_shares[1] = G*x`, others identity, with `λ_1 = 1` for `t = 1`, or solve for arbitrary `t`).
2. `ThresholdKeys::read` returns `Ok` — no consistency check rejects it.
3. Call `keys.view(included)` and run FROST `sign`/`complete`. The holder signs with `secret_share` but is evaluated against `verification_shares[i]`; the aggregate `verify` fails [7](#0-6) , the blame batch identifies the holder's share as invalid [8](#0-7) , and `Err(FrostError::InvalidShare(holder))` is returned — the honest party is reported faulty.
4. Any funds addressed to the resulting `group_key()` are unspendable since the shares do not interpolate to its discrete log.

Caveat: the concrete channel by which an unprivileged party supplies bytes to `ThresholdKeys::read` depends on integrator plumbing (the sink itself is in-scope); the crypto-layer defect — accepting unauthenticated, internally inconsistent key material as valid — is confirmed in `crypto/dkg/src/lib.rs`.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }

  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<ThresholdKeys<C>> {
    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];
      reader.read_exact(&mut id_len)?;
      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }
