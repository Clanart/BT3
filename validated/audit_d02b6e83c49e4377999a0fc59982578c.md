### Title
Missing length validation on per-participant preprocess/share vectors causes index-out-of-bounds panic (DoS) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` index into per-participant `Vec<Preprocess>` / `Vec<SignatureShare>` values using the number of transaction inputs, without ever checking each participant supplied that many elements. A malicious (or simply desynchronized) participant can send a short/empty vector, read via `read_preprocess`/`read_share`, causing a panic that aborts the signing round. This is the Serai analog of CVE-2022-0998's class: a numeric/index validation flaw reachable from untrusted input that crashes the process.

### Finding Description
In `TransactionSignMachine::sign`, each input index `c` is used to index `commitments[c]` on every participant's preprocess vector:

```rust
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
``` [1](#0-0) 

`read_preprocess` produces `self.sigs.iter().map(|sig| sig.read_preprocess(reader))` for *local* decoding, but the `commitments` map passed to `sign` is keyed by `Participant` and populated by the caller from whatever each peer transmitted — nothing enforces that a peer's `Vec<Preprocess>` has `sigs.len()` elements. If any participant's vector has fewer elements than `self.sigs.len()`, `commitments[c]` panics with an index-out-of-bounds.

The identical pattern exists in `TransactionSignatureMachine::complete`, which calls `shares.remove(0)` per input on each participant's share vector:

```rust
let sig = schnorr.complete(
  shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
)?;
``` [2](#0-1) 

A participant that sends an empty `Vec<SignatureShare>` (a valid `Vec` encoding — `Writable for Vec<T>` writes no length prefix, so zero elements is trivially produced) causes `remove(0)` to panic on the very first input.

Note also that `Writable for Vec<T>` in `crypto/frost/src/sign.rs` writes no element count, so a sender can even *truncate* its serialized preprocess vector and the receiver's `read_preprocess` will silently produce a shorter vector rather than an error, making this reachable purely through untrusted bytes. [3](#0-2) 

### Impact Explanation
An unprivileged signing participant can reliably panic every honest participant's `sign`/`complete` call for a Bitcoin transaction by sending a preprocess or share vector with fewer elements than the transaction has inputs. Since a panic in `sign` consumes/aborts the FROST attempt (and a panicking task typically tears down the signing session), this is a remote, attacker-triggered denial of service against multisig Bitcoin signing — the same impact category (attacker-reachable crash through a length/index validation flaw) as CVE-2022-0998's integer overflow in `vhost_vdpa_config_validate`. Repeated per attempt, an attacker can prevent the threshold wallet from ever completing a multi-input Bitcoin spend.

### Likelihood Explanation
Fully attacker-controlled: the preprocess/share messages are deserialized from peer-provided bytes via `read_preprocess`/`read_share`, and the victim indexes them without a length check. Any participant in the signing set can trigger it deterministically on demand. It is only Medium rather than High because the impact is a crash/DoS of the signing attempt rather than key recovery or forged signatures.

### Recommendation
In `TransactionSignMachine::sign`, validate `commitments.values().all(|v| v.len() == self.sigs.len())` (returning `FrostError::InvalidPreprocess(l)` per offender) before indexing. Similarly, in `TransactionSignatureMachine::complete`, validate each `Vec<SignatureShare>` has `self.tx.input.len()` elements before calling `remove(0)` — or better, drain the vectors once into `VecDeque`/`iter` so a short vector returns a `FrostError::InvalidShare` instead of panicking.

### Proof of Concept
1. Construct a `SignableTransaction` with two inputs (so `self.sigs.len() == 2`) and call `multisig(keys)` then `preprocess(rng)` to obtain a `TransactionSignMachine`.
2. For each peer `l`, obtain a `Vec<Preprocess>` via `read_preprocess` — but provide bytes for only one `Preprocess` (or zero; `Writable for Vec` has no length prefix so truncation is undetectable), yielding `vec![p]` instead of `[p0, p1]`.
3. Call `sign.commitments` map containing that peer's single-element vector. `sign` iterates `c` over `0..2`, evaluates `commitments[1]` on the peer's vector → `index out of bounds` panic.
4. For `complete`: supply a peer's `Vec<SignatureShare>` deserialized as `vec![]`; `shares.remove(0)` panics immediately on the first input.
