### Title
Shallow-copy in `dataCopy` (identity) precompile enables RETURNDATACOPY value mismatch / consensus state divergence - (File: blockchain/vm/contracts.go)

### Summary
Kaia's identity precompile (`0x04`) still implements `Run` by returning the caller-supplied input slice directly instead of a defensive copy, reproducing the exact shallow-copy pattern that caused GHSA-69v6-xc2j-r2jf / CVE-2020-26241 in go-ethereum.

### Finding Description
The `dataCopy` precompile is defined as: [1](#0-0) 

```go
func (c *dataCopy) Run(in []byte, contract *Contract, evm *EVM) ([]byte, error) {
	return in, nil
}
```

`in` is the raw input byte slice handed to the precompile by the EVM call dispatcher; in `run`/`RunPrecompiledContract` this ultimately traces back to a slice view into the calling contract's live memory buffer (the same pattern used across all Kaia forks — see `PrecompiledContractsByzantium` through `PrecompiledContractsOsaka`, which all map `0x04` to this same `dataCopy` type): [2](#0-1) 

Because `Run` returns the slice itself (no `common.CopyBytes`/defensive copy), the bytes referenced by the precompile's return value are the same underlying memory backing array that the *calling* contract can still write to. This is functionally identical to the vulnerable pre-1.9.17 geth `dataCopy.Run` that the advisory patched by making the identity precompile copy its output before returning.

Reachable exploit pattern (per the advisory, applicable verbatim to Kaia's EVM/precompile interpreter):
1. Contract writes value `X` into an EVM memory region `R`.
2. Contract calls precompile `0x04` (`dataCopy`) with `R` as call-data input/output region.
3. Because the returned bytes alias `R`'s backing array rather than being copied, the "return data" set by the call is not independent of subsequent memory writes.
4. Contract then overwrites `R` in memory with value `Y`.
5. Contract executes `RETURNDATACOPY` to pull the previously "returned" bytes onto the stack/memory.

A node whose call/return-data plumbing performs a true copy at the call boundary observes `X`; a node relying on this aliasing slice (as in unfixed geth, and as implemented here) can observe `Y`, because the buffer was mutated after the precompile "returned" it but before `RETURNDATACOPY` reads it.

### Impact Explanation
This is a consensus-critical divergence bug class: if the EVM/memory implementation surrounding this precompile allows the returned slice to alias the caller's mutable memory (rather than the call framework itself performing a safe copy on `RETURNDATACOPY`/call-return handling), different node implementations or different memory-growth/reallocation behavior can compute different `RETURNDATACOPY` results for the same transaction and bytecode. This can be weaponized by any contract deployer / transaction sender to craft a contract whose behavior (and resulting state root) differs between nodes, causing a chain split, exactly as scored Medium/CVE-2020-26241 (C:N/I:H/A:N).

### Likelihood Explanation
Reachable by any unprivileged transaction sender or contract deployer with a single crafted contract and a single transaction invoking precompile `0x04` — no privileged role, validator, or peer compromise required. The `dataCopy` code path is identical across every precompile map/fork in this codebase, so any fork level is affected as long as this `Run` implementation is unpatched.

### Recommendation
Change `dataCopy.Run` to return a defensive copy of the input rather than the input slice itself:
```go
func (c *dataCopy) Run(in []byte, contract *Contract, evm *EVM) ([]byte, error) {
	return common.CopyBytes(in), nil
}
```
Additionally, audit the EVM `run`/`RunPrecompiledContract` call path and `RETURNDATACOPY`/memory-growth handling to confirm no other precompile or call-return path aliases live, mutable EVM memory instead of copying at the return boundary — mirroring the full upstream geth security-release fix (commit 295693759e5ded05fec0b2fb39359965b60da785).

### Proof of Concept
Conceptually (Solidity/inline assembly), matching the pattern already present in this repo's own test helper contract: [3](#0-2) 

```solidity
contract Exploit {
    function attack() external returns (bytes32 stackVal) {
        assembly {
            let R := mload(0x40)
            mstore(R, 0x00000000000000000000000000000000000000000000000000000000000042) // write X
            let ok := call(gas(), 0x04, 0, R, 0x20, R, 0x20) // call identity(R) -> aliases R
            mstore(R, 0x00000000000000000000000000000000000000000000000000000000000099) // overwrite R with Y
            returndatacopy(0x00, 0, 0x20) // reads aliasing buffer
            stackVal := mload(0x00)
        }
    }
}
```
On an implementation where the precompile's returned bytes alias the caller's memory buffer `R` (as with the unpatched `return in, nil` above), `stackVal` can resolve to `Y` (0x99) instead of the consensus-correct `X` (0x42) observed by nodes that copy on return/RETURNDATACOPY, producing divergent execution results/state roots for the same transaction.
