### Title
Unchecked subtraction of attacker-influenced fee causes underflow in output amortization, silently dropping payments - (File: processor/src/multisigs/scheduler/utxo.rs)

### Summary
`Scheduler::created_output` computes `to_amortize = actual - expected` with a plain `u64` subtraction. `actual` is the on-chain value of the branch output the multisig just created; `expected` is the sum of the payments that output was scheduled to cover. The gap between them is the transaction fee, which is derived from `median_fee()` over transactions in a block — data any unprivileged party can influence by broadcasting Bitcoin transactions. When the real fee exceeds the estimate (i.e. `actual < expected`), the subtraction underflows, panicking in debug builds and wrapping to ~`u64::MAX` in release builds. In release, the wrap makes `payments.sum() < to_amortize` true, so the function returns early and silently drops every child payment under that output.

### Finding Description
The analogous bug class to CVE-2017-9106 is "an integer value outside the assumed range is used in arithmetic without a range check, producing incorrect behavior instead of a clean `invaliddata` error."

In `Scheduler::created_output`:

```rust
// processor/src/multisigs/scheduler/utxo.rs:484-489
let mut to_amortize = actual - expected;
// If the payments are worth less than this fee we need to amortize, return, dropping them
if payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>() < to_amortize {
  return;
}
```

`expected` is asserted equal to the sum of the queued payment amounts (`assert_eq!(expected, payments.iter()...sum::<u64>())` at line 474). `actual` is the amount the output was actually created with after the real network fee was deducted (`expected - fee`). The code assumes `actual >= expected` — equivalently, that the actual fee never exceeds the estimate baked into `expected`. That assumption is entirely controlled by the fee market.

The fee itself comes from `Bitcoin::median_fee` (processor/src/networks/bitcoin.rs:388-415), which averages per-vbyte fees of every non-coinbase transaction in the sampled block:

```rust
// processor/src/networks/bitcoin.rs:396-406
in_value += self.rpc.get_transaction(&input_tx).await ... .value.to_sat();
...
fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
```

Any party can publish transactions paying arbitrary fees; if they dominate the sampled block, `fee.0` and hence the actual fee charged to the branch output exceeds what `expected` accounted for, producing `actual < expected`.

There are two consequences depending on build profile:

1. **Debug / panic-on-overflow:** `actual - expected` panics, crashing the processor handling `created_output` — a signing/withdrawal liveness failure reachable purely by sending Bitcoin transactions.
2. **Release (wrapping):** `to_amortize` wraps to ~`u64::MAX`; the guard `payments_sum < to_amortize` is always true, so the function returns early and **drops every payment** under the branch output. No blame, no error — the payments are removed from `queued_plans` at lines 472-478 before the underflow is ever evaluated, so they are permanently lost from the scheduler's perspective. User withdrawals/burns that were confirmed on the Serai side simply never pay out, and the funds remain locked in the multisig's accounting view.

A related unchecked arithmetic site in the same path: `SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes` and `payment_sat + needed_fee` (networks/bitcoin/src/wallet/send.rs:206, 215) with no `checked_*` arithmetic — an attacker-driven extreme `fee_per_vbyte` causes multiplication/addition overflow panics in `make_signable_transaction`, halting transaction construction entirely.

### Impact Explanation
- **Release build:** all payments amortized under a branch output created during a fee spike are silently discarded. Burns/withdrawals that users were told completed are never paid, and the scheduler loses track of them (`queued_plans` entry already removed). This is a funds-accounting integrity failure: value received/recorded that is never spent onward, analogous to "funds reported received that are not spendable."
- **Debug build:** reproducible panic → processor liveness denial of service, stalling all signing for that multisig until restarted.

### Likelihood Explanation
The trigger requires the real fee to exceed the estimated fee used when the plan was scheduled. `median_fee` samples a single block (`get_block(block_number)`, `block.txdata[1..]`), so an attacker who fills more than half the non-coinbase transactions of the sampled block with high-fee transactions directly sets the fee estimate. Fees are attacker-chosen, real Bitcoin transactions — a public input. The cost is the fees paid, but the attack needs only a temporary spike between scheduling and output creation. Organic fee volatility can also trigger the wrap path accidentally, meaning the silent payment-drop path can fire without any adversary.

### Recommendation
- Use `actual.checked_sub(expected)` in `created_output` (processor/src/multisigs/scheduler/utxo.rs:485) and handle the `actual < expected` case explicitly — e.g. treat the deficit as the amount to amortize (`expected - actual`) and drop only payments that individually fall below dust, rather than dropping the entire queue.
- In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:206, 215, 227), use `checked_mul`/`checked_add` for `fee_per_vbyte * vbytes` and `payment_sat + needed_fee`, returning a `TransactionError` instead of panicking.
- In `median_fee` (processor/src/networks/bitcoin.rs), bound the returned fee (e.g. clamp to a sane maximum) and use `checked_sub` for `in_value - out` so a malformed prevout response can't panic.
- Sample the median over multiple blocks, per the existing `TODO2` comment, to reduce single-block manipulation.

Note: I was unable to fully trace the call path feeding `expected` vs `actual` (whether `expected` is always pre-fee and `actual` always post-fee); the underflow requires `actual < expected`, which follows whenever the real fee exceeds what was reserved — that is the attacker-influenced input via `median_fee`.
