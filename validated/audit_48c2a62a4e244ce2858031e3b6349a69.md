### Title
Nested/recursive precompile calls cause bank balance-change events to be double-processed into the EVM `StateDB`, duplicating spendable balance - (File: `precompiles/common/precompile.go`, `precompiles/common/balance_handler.go`)

### Summary
The Cosmos EVM precompile framework tracks bank `EventTypeCoinSpent`/`EventTypeCoinReceived` (and `precisebank` fractional-balance) events emitted during a native precompile call and replays them onto the EVM `StateDB` via `BalanceHandler.AfterBalanceChange`. When a precompile call triggers a *nested* precompile call (e.g. a contract-controlled reentrant call back into a precompile, or a precompile that itself calls back into the EVM), the outer call's recorded event window overlaps with the inner call's window, so the same bank events get applied to the `StateDB` twice - once by the inner handler and again by the outer handler. This mirrors the root cause pattern of the reference report (a critical value used to update/derive account state is read/applied using a stale or already-consumed reference point), except here the corrupted value is the EVM-visible balance rather than a collateral exchange rate.

### Finding Description
Each precompile invocation goes through `Precompile.runNativeAction`: [1](#0-0) 

For every call, a **new** `BalanceHandler` is created and:
1. `BeforeBalanceChange(ctx)` records `prevEventsLen = len(ctx.EventManager().Events())`. [2](#0-1) 
2. The native `action(ctx)` runs (this is where bank `SendCoins`/mint/burn happen and emit events).
3. `AfterBalanceChange(ctx, stateDB)` iterates `events[prevEventsLen:]` and applies `stateDB.AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived`/fractional-balance event found in that slice. [3](#0-2) 

The critical assumption is that the event slice `events[prevEventsLen:]` observed by a given call's `AfterBalanceChange` contains **only** the bank events caused by that call's own logic. This assumption breaks when the native `action` itself triggers another EVM/precompile call that goes through `runNativeAction` again (nested call). Because `ctx.EventManager()` accumulates events across the whole call stack (it is the same context's event manager, not reset per nested call), the sequence is:

- Outer call: `prevEventsLenOuter = N`
- Nested call starts, also captures `prevEventsLenInner = N'` (N' >= N, includes any events emitted by outer before the nested call)
- Nested call emits bank events, then its own `AfterBalanceChange` applies `events[N':]` to `stateDB` (correctly, for its own subset)
- Control returns to outer action; outer action may or may not emit more events
- Outer's `AfterBalanceChange` fires and applies `events[N:]` to `stateDB` — this range **includes** the events already consumed and applied by the nested call's `AfterBalanceChange`

Because `ctx.EventManager().Events()` is a monotonically growing slice sourced from the *same* SDK context propagated down the call chain (only `prevEventsLen` differs between handler instances — not the event manager itself), the outer handler re-parses and re-applies balance-changing events that the inner handler already applied. This results in the `StateDB` being credited/debited twice for a single underlying bank ledger movement, producing a **balance desync between the native bank ledger and the EVM state view** used by that transaction (and, since `StateDB` state is committed at end of tx, persisted into consensus state).

This exact mechanism is already flagged and reproduced by an existing regression test in the repo: [4](#0-3) 
which explicitly documents: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."*

The debug precompile used in that test only emits a custom `debug_precompile` event (not a bank event), so the test measures event-count/desync mechanics rather than directly proving fund duplication, but the same code path (`runNativeAction` / `AfterBalanceChange`) is used by production precompiles that *do* emit `CoinSpent`/`CoinReceived` events and mutate `StateDB` balances — notably the ERC-20 precompile, which wires a `BalanceHandlerFactory` from the real `BankKeeper`: [5](#0-4) 

Any production precompile (ERC20, WERC20, staking, distribution, gov, ics20, slashing) that can be reentered — e.g. by calling a token/precompile method whose execution invokes a callback to an attacker-controlled contract, which then calls back into the same or another balance-changing precompile before the outer call unwinds — is a candidate for triggering this double-application path.

### Impact Explanation
If reachable with an unprivileged, attacker-crafted contract, this would let an attacker artificially inflate their `StateDB`-visible EVM balance for a native/ERC20-represented asset without a corresponding real bank-ledger increase (or conversely cause victims' balances to be doubly debited). Because `StateDB` balance is what backs subsequent EVM transfers/spends within the same transaction and is what is persisted to the account's on-chain state at commit, a duplicated credit is directly spendable value that was never actually escrowed/backed by the bank module — an unauthorized duplication of spendable user value, matching the Critical "unauthorized minting/duplication ... corruption of spendable user value across native balances, EVM balances" impact category.

### Likelihood Explanation
Likelihood depends on whether any in-scope precompile method can be made to reenter the `runNativeAction` path before its own `AfterBalanceChange` runs (classic reentrancy shape). I was not able to fully trace a concrete production call chain (e.g. ERC20 `transfer` → contract callback → nested precompile call using the same `ctx.EventManager()`) within the remaining investigation budget to confirm an end-to-end unprivileged trigger with a real bank event (`CoinSpent`/`CoinReceived`), as opposed to the debug-only reproduction present in the repo's test. The mechanism itself (shared/growing `EventManager` across nested `runNativeAction` calls, combined with non-disjoint `prevEventsLen` windows) is clearly present and already acknowledged by the repository's own test/comment, but I could not verify within this session whether a genuine reentrant call path exists from an unprivileged EVM contract into a bank-event-emitting precompile method (e.g., via `CallEVMWithData` invoked from inside a precompile's native action, as the debug precompile does) with a matching prevention/guard elsewhere (e.g., reentrancy locks) that might already close this gap for real precompiles.

### Recommendation
- Make `AfterBalanceChange` only consume events that have not already been consumed by an inner/nested handler — e.g., track a shared, call-stack-aware cursor (such as storing the "already processed" event index on the `StateDB`/context itself, incremented atomically as each handler processes its slice) rather than each handler independently reading `len(events)` at entry.
- Alternatively, disallow/guard nested precompile calls from reusing the same `ctx.EventManager()` without isolating a fresh event manager per nested `runNativeAction` invocation, and merge/skip already-applied events on unwind.
- Add integration tests using a real bank-event-emitting precompile (not just the debug precompile) in a reentrant call chain, asserting `StateDB` balances match `x/bank`/`x/precisebank` ledger state after the transaction commits.

### Proof of Concept
The repository already contains a partial PoC demonstrating the underlying mechanics: [6](#0-5) 
This test deploys a caller contract that invokes the debug precompile recursively (`callback(0)` → `call1()` chain), and shows that event windows recorded by nested `BalanceHandler` instances overlap (`debug_count == 10` out of `15` total events across the recursive chain). Extending this exact pattern by replacing the debug precompile's custom event with a real `x/bank` `SendCoins` call inside the nested nesting (so that `CoinSpent`/`CoinReceived` events are emitted at each nesting level) would be the next step to directly demonstrate `StateDB.AddBalance`/`SubBalance` being invoked twice for the same underlying transfer — this final confirmation step was not completed in this session due to tool-call limits.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
