### Title
Verifiers Accept Arbitrarily Low `output_amount` in Optimistic Payout, Burning Bridge Vault UTXO as Miner Fees — (`File: core/src/verifier.rs`)

---

### Summary

`sign_optimistic_payout` in `verifier.rs` enforces only an **upper** bound on `output_amount`. There is no lower-bound check. Because the optimistic payout transaction spends the full `bridge_amount` move-to-vault UTXO with no change output, any `output_amount` below `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` silently burns the difference as miner fees. When `aggregator_verification_address` is not configured (it is optional), any mTLS-authenticated actor can trigger this path with `output_amount = 1 sat`, permanently destroying the full deposited BTC.

---

### Finding Description

`create_optimistic_payout_txhandler` constructs a transaction with exactly two inputs and two outputs:

```
Input 0:  user withdrawal dust UTXO (~550 sat)
Input 1:  move-to-vault UTXO  (bridge_amount, e.g. 10 BTC = 1_000_000_000 sat)

Output 0: user payout          (output_amount — caller-supplied)
Output 1: anchor output        (NON_EPHEMERAL_ANCHOR_AMOUNT)
```

There is no change output. [1](#0-0) 

The implicit miner fee is therefore:

```
fee = bridge_amount + dust - output_amount - NON_EPHEMERAL_ANCHOR_AMOUNT
```

Before signing, each verifier runs `sign_optimistic_payout`, which contains the sole amount check:

```rust
// amount in move_tx is exactly the bridge amount
if output_amount
    > self.config.protocol_paramset().bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT
{
    return Err(...)
}
``` [2](#0-1) 

This is a one-sided guard. Any `output_amount` in `[0, bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT]` passes. The verifiers then produce a valid MuSig2 partial signature over the sighash of a transaction that may pay out 1 sat while consuming 10 BTC from the vault.

The aggregator's `optimistic_payout` handler performs no independent amount floor check either; it constructs the same `output_txout` directly from the caller-supplied `output_amount` and forwards it to verifiers. [3](#0-2) 

The only gate that could prevent an unprivileged caller from reaching this path is `aggregator_verification_address`, which is an **optional** config field. [4](#0-3)  When it is absent (the default in the regtest config and not required by the protocol), any mTLS-authenticated actor — operator or verifier — can call the aggregator's `optimistic_payout` RPC with an arbitrary `output_amount`.

---

### Impact Explanation

- **Permanent, total loss of bridged BTC.** The move-to-vault UTXO holding the full `bridge_amount` (10 BTC in the regtest paramset) is irrevocably spent. The difference between `bridge_amount` and the attacker-chosen `output_amount` is paid to Bitcoin miners and is unrecoverable.
- The depositing user receives only `output_amount` (as low as 1 sat) instead of the full bridge amount.
- The bridge state machine marks the deposit as paid out (the move-to-vault UTXO is spent), so no further recovery path exists within the protocol.

---

### Likelihood Explanation

- `aggregator_verification_address` is optional and absent from the regtest environment config. [5](#0-4)  Any deployment that omits it is immediately exploitable by any actor holding a valid mTLS client certificate.
- Even when `aggregator_verification_address` is set, the verification signature commits to the full `WithdrawParams` including the caller-supplied `output_amount`. Verifiers do not independently derive the correct expected amount from on-chain data; they trust whatever amount is presented to them as long as it does not exceed the ceiling.

---

### Recommendation

In `sign_optimistic_payout`, add a strict equality (or tight floor) check alongside the existing ceiling check:

```rust
let expected_amount =
    self.config.protocol_paramset().bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT;

if output_amount != expected_amount {
    return Err(eyre::eyre!(
        "Output amount must equal bridge_amount - anchor: expected {}, got {}",
        expected_amount,
        output_amount
    ).into());
}
```

Alternatively, if a fee deduction is intentional, enforce a tight minimum floor (e.g., `>= bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT - max_allowed_fee`). The same check should be mirrored in the aggregator's `optimistic_payout` handler before verifier signatures are solicited.

Additionally, `aggregator_verification_address` should be made a required field, or the aggregator endpoint should be restricted to a dedicated, non-shared mTLS identity.

---

### Proof of Concept

1. Deploy Clementine without `AGGREGATOR_VERIFICATION_ADDRESS` set (the default regtest config).
2. Complete a normal deposit; the move-to-vault UTXO now holds `bridge_amount` (e.g., 1 000 000 000 sat).
3. As any mTLS-authenticated actor, call the aggregator's `optimistic_payout` gRPC with:
   - `withdrawal_id` = the valid deposit index
   - `input_outpoint` = the registered withdrawal dust UTXO
   - `input_signature` = a valid `SinglePlusAnyoneCanPay` signature over a 1-sat output (the user signs this themselves, or the attacker controls the withdrawal UTXO)
   - `output_amount` = **1** (one satoshi)
   - `output_script_pubkey` = attacker-controlled address
4. Each verifier passes the check `1 > bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` → false, and signs. [6](#0-5) 
5. The aggregator aggregates the MuSig2 signatures, sets the script-spend witness on input 1, and broadcasts the transaction. [7](#0-6) 
6. Bitcoin confirms the transaction: the move-to-vault UTXO (10 BTC) is spent; the user receives 1 sat; ~10 BTC is paid to miners.
