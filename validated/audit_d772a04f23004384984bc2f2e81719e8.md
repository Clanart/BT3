### Title
Unguarded `updateEndRemainingAllocation()` allows re-snapshotting the bonus denominator to steal the shared bonus pool - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is a `public` function with no guard preventing repeated invocation, unlike its guarded internal usage inside `claim()`. Because `totalRemainingAllocation` shrinks every time any user calls `claim()`, an attacker can call `updateEndRemainingAllocation()` directly at any point after `periodsEndTime[4]` — after most other users have already claimed — to collapse `totalEndRemainingAllocation` toward their own remaining allocation, inflating `getBonusAmount(attacker)` at the expense of the shared `totalBonus` pool and other still-unclaimed honest users.

### Finding Description
`claim()` only calls the snapshot helper conditionally: [1](#0-0) 

```solidity
function claim() external {
    if (totalEndRemainingAllocation == 0) {
        updateEndRemainingAllocation();
    }
```

This guard is meant to make the denominator "set once." However, `updateEndRemainingAllocation()` itself has no equivalent internal guard against being re-invoked, and it is `public`: [2](#0-1) 

```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```

Any unprivileged account can call this function directly, bypassing the `claim()`-only "set once" guard, and it will unconditionally overwrite `totalEndRemainingAllocation` with the *current* `totalRemainingAllocation`. Since `totalRemainingAllocation` is decremented by the *entire* forfeited/claimed user's allocation on every `claim()` call: [3](#0-2) 

```solidity
uint256 userAllocation = allocations[msg.sender];
allocations[msg.sender] = 0;
totalRemainingAllocation -= userAllocation;
if (claimableAmount <= userAllocation) {
    uint256 forfeited = userAllocation - claimableAmount;
    totalBonus += forfeited;
}
```

it strictly decreases as more users claim after `periodsEndTime[4]`. `getBonusAmount()` uses this snapshot as the denominator: [4](#0-3) 

An attacker can therefore wait until most honest users have already claimed (shrinking `totalRemainingAllocation` down toward the attacker's own unclaimed allocation), then call `updateEndRemainingAllocation()` directly right before their own `claim()`. This re-snapshots `totalEndRemainingAllocation` to a much smaller value, close to the attacker's own `allocations[attacker]`. The attacker's `getBonusAmount` then approaches `totalBonus` in full (`bonusAmount ≈ userAllocation * totalBonus / userAllocation = totalBonus`), capturing nearly the entire forfeited-bonus pool that was meant to be shared proportionally among all users who wait until the end. Because this manipulated `totalEndRemainingAllocation` value is now permanently fixed for everyone (the `claim()` internal guard `if (totalEndRemainingAllocation == 0)` will no longer fire), the remaining honest users who have not yet claimed will have their own `getBonusAmount` computed against the same collapsed denominator, causing either: (a) `claimableAmount > aidropToken.balanceOf(address(this))` reverts that freeze their funds, or (b) if funds remain, further disproportionate payouts, worsening insolvency — since `withdrawDust` cannot be reached until users are already permanently locked out. This directly matches the audited invariant violation: a participant is able to shrink the denominator that scales their own bonus.

The "pending mempool" precondition described in the prompt is one concrete way to reach the same state (attacker front-runs/repeats calls around the first post-period4 claim), but the root cause is broader: `updateEndRemainingAllocation()` can be invoked by anyone, any number of times, at any point after `periodsEndTime[4]`, with no access control or one-time guard.

### Impact Explanation
This is a direct theft of user funds: the attacker extracts a disproportionate — potentially near-total — share of `totalBonus`, which was contributed by other users who claimed early and forfeited part of their allocation. Remaining honest claimants either receive less than entitled or have their `claim()` revert due to insufficient contract balance, permanently losing access to their allocation/bonus. This matches Immunefi's "Critical - Direct theft of user funds" classification.

### Likelihood Explanation
No privileged role is required — `updateEndRemainingAllocation()` and `claim()` are both `external`/`public` with no access control. The only precondition is waiting until `periodsEndTime[4]` has passed and other users have begun claiming (naturally occurring, or the attacker can simply monitor mempool/chain state and time their own transaction). No capital beyond gas is required, and the attack is trivially repeatable by any registered participant with a non-zero allocation.

### Recommendation
Guard `updateEndRemainingAllocation()` so it can only set the snapshot once, e.g. add `if (totalEndRemainingAllocation != 0) return;` (or a boolean `hasSnapshotted` flag) inside the function itself, mirroring the intent of the check currently only enforced in `claim()`. Alternatively, restrict the function to be called only by the contract itself from `claim()`, or capture the snapshot deterministically at `periodsEndTime[4]` via a scheduled/one-shot mechanism rather than relying on external triggering.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`; `register()` allocations for users A (honest, large allocation), B (honest, large allocation), and M (attacker, small allocation).
2. Warp time past `periodsEndTime[4]`.
3. Have A call `claim()` — assert `totalEndRemainingAllocation` is set to `totalRemainingAllocation` at that time (sum of B + M, since A's own allocation was just subtracted) and A receives `allocation + bonus` proportional to A's share.
4. Have B call `claim()` — assert `totalRemainingAllocation` is now reduced to just M's allocation, but `totalEndRemainingAllocation` remains unchanged (still fixed from step 3) since `claim()`'s guard skips re-triggering.
5. Attacker M directly calls `updateEndRemainingAllocation()` (not through `claim()`), and assert `totalEndRemainingAllocation` is overwritten to now equal `allocations[M]` only (much smaller than in step 3).
6. Attacker M calls `claim()`; assert `getBonusAmount(M)` ≈ `totalBonus` (nearly 100% of the forfeited bonus pool), versus the expected proportional share `allocations[M] * totalBonus / (allocations[A]+allocations[B]+allocations[M])` that should have applied had the denominator not been re-snapshotted.
7. Assert this demonstrates `getBonusAmount(M)` is inconsistent with `allocations[M]`'s fair proportional share, and that the manipulation was only possible via the unguarded public `updateEndRemainingAllocation()` call outside of `claim()`.
