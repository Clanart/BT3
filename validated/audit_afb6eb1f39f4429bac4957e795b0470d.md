### Title
Unsigned OP_RETURN operator-attribution field lets any third party hijack payout credit via `SinglePlusAnyoneCanPay` rebuild - (File: core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
The payout transaction's OP_RETURN operator xonly-pubkey (`core/src/builder/transaction/operator_reimburse.rs:407-436`) is not covered by the withdrawer's `SinglePlusAnyoneCanPay` signature, since that sighash only commits to input 0 and output 0 (`Prevouts::One`, `core/src/builder/transaction/txhandler.rs:222-229`). `Verifier::update_finalized_payouts` then blindly trusts whatever OP_RETURN appears in the transaction that is first found on-chain spending the registered `withdrawal_utxo_txid`/`vout` (`core/src/database/verifier.rs:170-196`, `core/src/verifier.rs:2312-2343`) to decide `payout_payer_operator_xonly_pk`, with no cryptographic binding between the signer and the credited operator.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk (DB) == the party that actually funded/broadcast the withdrawer-committed output`. Trace: the withdrawer signs only input 0 + output 0 (the payout to themselves) under `SinglePlusAnyoneCanPay` (`core/src/test/common/setup_utils.rs:499-543`, `core/src/builder/transaction/txhandler.rs:210-233`). The OP_RETURN naming the crediting operator is added as output 2 by `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) and is *not* part of the signed message. Consequently any party possessing the raw signature (available once any operator broadcasts to the public mempool, or obtainable directly since the aggregator's `withdraw` RPC (`core/src/rpc/aggregator.rs:1811-1888`) and `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-203`) only validate sighash type, not caller identity) can reconstruct a transaction spending the same `withdrawal_utxo` with the same required output-0 payment to the withdrawer, but with an arbitrary OP_RETURN xonly pubkey and their own fee-funding inputs. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) credits whichever version is first mined against that `withdrawal_utxo` — via the DB join in `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) — with zero check that the named pubkey is even a registered operator (`XOnlyPublicKey::from_slice` alone, `core/src/verifier.rs:2319-2321`), nor that it matches the one who funded the transaction inputs. Existing guards (`is_kickoff_malicious`, `core/src/verifier.rs:1857-1915`; `validate_payer_is_operator`, `core/src/operator.rs:1686-1740`) only check that the *kickoff's* operator matches the DB-recorded payer — they cannot detect that the DB-recorded payer was never cryptographically tied to who actually paid, since that binding never existed.

### Impact Explanation
Two concrete outcomes, both matching listed Critical categories:
1. If the attacker's rebuilt transaction confirms before the intended operator's, the honest operator's identical payout transaction becomes an unconfirmable double-spend of the already-spent `withdrawal_utxo`; `validate_payer_is_operator` then rejects that operator's future kickoff attempt ("Payer is not own operator") — an honest operator becomes permanently unable to be reimbursed for a withdrawal it genuinely funded/attempted.
2. If the attacker names a *different, real* operator's public xonly key (these are public via `fetch_operator_keys`) while funding the output themselves, that named operator's `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-111`) will discover the "unhandled payout" under its own key and proceed to kickoff and claim bridge reimbursement for a withdrawal it never funded — an operator reimbursed for a payout it never funded, at the cost of the attacker's own BTC (or, if the attacker is willing to be defrauded of nothing and simply grief, at the cost of permanently blocking the true operator, as in scenario 1). Both are repeatable per-withdrawal and per-operator, since the flaw is structural (unsigned OP_RETURN + first-block-wins attribution) rather than a one-off bug.

### Likelihood Explanation
Preconditions: attacker must observe/obtain the withdrawer's `SinglePlusAnyoneCanPay` signature (trivially available from the mempool once any operator broadcasts, or from any operator willing to relay a withdraw request) and must be able to fund the required output value itself (real BTC cost equal to the withdrawal amount) plus fees to win the race, or must simply be faster/luckier in mempool propagation for scenario 1. No verifier/operator/aggregator privilege, key share, or TLS access is needed — only public gRPC access and normal Bitcoin broadcast capability, consistent with the stated unprivileged threat model. This is deployable on regtest/testnet without live Citrea or mainnet.

### Recommendation
Bind the crediting operator identity into the withdrawer's signed commitment (e.g., require the withdrawer to sign a per-operator commitment via `SIGHASH_ALL` for the operator/OP_RETURN output as well, or have the operator itself co-sign/commit the OP_RETURN pubkey in a way that's verified against the actual funding inputs), and/or have `update_finalized_payouts` validate that the OP_RETURN pubkey belongs to a currently registered operator and cross-check funding provenance before crediting.

### Proof of Concept
`cargo test` outline (regtest, no live Citrea needed — mock/insert withdrawal DB rows directly as existing tests do, e.g. `core/src/test/manual_reimbursement.rs`):
1. Set up two operators (op0, op1) and a deposit/withdrawal as in `core/src/test/common/clementine_utils.rs:42-135`.
2. Have `op0.withdraw(...)` build and broadcast its payout tx (asserting DB shows `withdrawal_utxo` registered).
3. Before confirmation, take the same witness/signature from the mempool tx, and independently build a second raw transaction reusing input 0 (same outpoint + witness) but with attacker-funded fee inputs and an OP_RETURN naming `op1`'s xonly pubkey instead; broadcast it and mine it first.
4. Assert `Database::get_payout_info_from_move_txid` now returns `op1`'s xonly pubkey as `payout_payer_operator_xonly_pk`, and that op0's subsequent kickoff attempt fails `validate_payer_is_operator`, while op1's `PayoutCheckerTask` picks up the payout as its own via `get_first_unhandled_payout_by_operator_xonly_pk` — proving attribution was hijacked with zero involvement from op1.
