### Title
Hookify block rules on `field: new_text`/`content` silently fail to match `Write` tool operations, allowing dangerous file writes to bypass security rules - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._extract_field` extracts the value of a condition's `field` using tool-specific aliasing logic that is inconsistent across `Bash`/`Write`/`Edit`/`MultiEdit`. When a rule's `event` is `file` (which per design and documentation matches `Write`, `Edit`, and `MultiEdit` tools alike) and its `field` is the commonly-used `new_text` (the default field inferred by the legacy `pattern:` shorthand), the extraction path returns an empty string for `Write` tool invocations instead of the actual written content, causing the rule to never match and never block, even though the identical content written via `Edit` would correctly trigger the block.

### Finding Description
`config_loader.Rule.from_dict` converts the simple legacy `pattern:` shorthand into a `Condition` with `field='new_text'` whenever `event == 'file'` [2](#0-1) . Both `pretooluse.py` and `posttooluse.py` route `Write`, `Edit`, and `MultiEdit` tool calls to `event='file'` rules identically, with no `tool_matcher` distinguishing them by default [3](#0-2) .

Inside `_extract_field`, the direct lookup `if field in tool_input: ... return str(value)` is attempted first [4](#0-3) . For `Write`, `tool_input` only contains `file_path` and `content` — there is no `new_text` key, so this direct lookup fails. Execution then falls through to the tool-specific branch:

```
elif tool_name in ['Write', 'Edit']:
    ...
    elif field == 'new_text' or field == 'new_string':
        return tool_input.get('new_string', '')
``` [5](#0-4) 

For `Write`, `tool_input` has no `new_string` key (that key only exists for `Edit`), so `tool_input.get('new_string', '')` returns `''` — a non-`None` empty string. Because `_check_condition` only treats `None` as "no value" and treats an empty string as a valid, checkable value [6](#0-5) , the `regex_match`/`contains` operators are evaluated against `''`, which fails to match any non-empty pattern. The condition silently evaluates to `False`, `_rule_matches` returns `False`, and the block/warn rule never fires — with no error, warning, or log indicating the rule failed to evaluate the intended data.

This is not a contrived edge case: the plugin's own command documentation (`hookify.md`) tells users/agents that `event: file` rules apply uniformly across `Write|Edit|MultiEdit`, and the default field for such rules is `new_text` [7](#0-6) [1](#0-0) . A user (or a Claude agent acting on repository-controlled prompt-injected content) can trivially reach the vulnerable path merely by causing a "sensitive-files"/"secrets" style rule to run against a `Write` tool call instead of `Edit` — the exact same dangerous content (e.g., writing a file containing `API_KEY=...`) that would be blocked via `Edit` passes through undetected via `Write`, because `Write`'s content lives under `content`, not `new_string`, while the extraction alias for `new_text` only checks `new_string`.

A related, analogous gap exists for `MultiEdit`: the tool-specific branch for `MultiEdit` only implements `file_path` and `new_text`/`content` aliases, omitting `old_text`/`old_string` entirely [8](#0-7) , so any rule keyed on `old_text` (valid and documented for `Edit`) silently never matches `MultiEdit` operations.

### Impact Explanation
This is a Security-control bypass: a hookify block rule intended to deny dangerous file-write operations (e.g., leaking secrets, adding backdoor code, writing to sensitive paths) can be silently routed around simply by the acting tool being `Write` rather than `Edit`, without any error or indication to the user that protection failed. Since Claude (potentially influenced by repository-controlled prompt injection) chooses which tool to invoke to accomplish a file modification, an attacker who can influence Claude's tool choice (a very low bar, since `Write` and `Edit` are often interchangeable for creating/overwriting file content) can achieve the exact operation the user configured hookify to block, defeating the security boundary the user relied on.

### Likelihood Explanation
High feasibility, low precondition: any project using the hookify plugin's standard, documented workflow (`/hookify` command with `event: file` and a simple `pattern:`) is affected by default — no unusual configuration is required. The only "attacker action" needed is that the operation is performed via `Write` (create/overwrite a file) instead of `Edit` (modify existing text), which is a normal and expected tool choice for Claude when creating new files or fully rewriting file content, and can be steered by prompt-injected repository content instructing Claude to "create/write a file with X content" rather than "edit."

### Recommendation
In `RuleEngine._extract_field`, normalize field aliasing per-tool independent of the direct `tool_input` key lookup, and make the `Write`/`Edit` branch check the correct underlying key for each tool (e.g., for `Write`, `new_text`/`content` should resolve to `tool_input.get('content')`; for `Edit`, they should resolve to `tool_input.get('new_string')`). Also add the missing `old_text`/`old_string` alias handling for `MultiEdit`. Additionally, treat the absence of a valid tool-specific mapping as `None` (not `''`) so that `_check_condition` can distinguish "field truly not present for this tool" from "field present but empty," preventing rules from silently evaluating against empty strings.
