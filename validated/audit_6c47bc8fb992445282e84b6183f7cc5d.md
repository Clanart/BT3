### Title
Symlink bypass of clone-destination sensitivity check via literal path comparison instead of realpath resolution - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` guards against a crafted clone URL tricking the UI into deriving a destination path inside a sensitive location (`~/.ssh`, `~/.gnupg`, `~/.config`, `~/.gitconfig`, `%APPDATA%`). The guard, `isClonePathSensitive`, identifies the destination solely by its literal, case-lowered resolved path string. Just like the SwapHandler bug where a token could have more than one valid "address" and the address-equality check missed the non-canonical one, a filesystem directory can be reached through more than one path "address" — its canonical path or a symlink/junction pointing at it. `isClonePathSensitive` only recognizes the canonical string form, so a destination that is a symlink pointing at a sensitive directory sails through the check untouched.

### Finding Description
`isClonePathSensitive` computes identity purely with `Path.resolve(unresolvedClonePath).toLowerCase()` and compares it against a fixed list of sensitive absolute paths: [1](#0-0) 

Note that `Path.resolve` never touches the filesystem — it does not dereference symlinks. Elsewhere in the very same codebase, the team explicitly recognized that literal path comparison is insufficient for security-relevant path checks and resolves symlinks via `fs.promises.realpath` before comparing: [2](#0-1) 

`isClonePathSensitive` does not follow that pattern. If the resolved clone destination is (or passes through) a symlink whose target is `~/.ssh`, `~/.gnupg`, `~/.config`, or `%APPDATA%`, the literal string will not equal or start with any entry in `sensitiveLocations`, so the function returns `false` and `clone()` proceeds: [3](#0-2) 

The symlink itself is trivial for an attacker to place: any git repository can contain a checked-out symlink as an ordinary tracked file — no privileges, malware, or leaked credentials are required, only that the victim clone/open an attacker-supplied repository. Once such a symlink exists at the location the victim later selects (or that a crafted `x-github-client://openRepo/...` URL causes Desktop to auto-populate) as their next clone destination, `git clone --recursive ... -- <url> <path>` writes the new repository's contents through the symlink into the real sensitive directory (e.g. `~/.ssh`), because the sensitivity check that was supposed to stop exactly this "crafted-URL-derives-a-dangerous-path" scenario never re-derives the real path.

### Impact Explanation
A successful bypass lets a remote attacker cause GitHub Desktop to write arbitrary git-tracked files into the user's `~/.ssh`, `~/.gnupg`, `~/.config`, `~/.gitconfig`, or `%APPDATA%` locations (e.g., overwriting `authorized_keys`, SSH `config`, or GPG keyrings), which is a file write outside the intended repository directory and can lead to SSH/GPG key exfiltration or execution via `~/.ssh/config` `ProxyCommand`/`.gitconfig` `core.fsmonitor`/hook-like directives. This matches the "file write outside the repo" / "credential exfiltration" impact classes called out as valid.

### Likelihood Explanation
Requires two attacker-influenced conditions that are both achievable without local/physical access or prior malware: (1) the victim at some point checks out an attacker-controlled repository/commit that plants a symlink at a filesystem location, and (2) the victim later performs a Desktop clone/open-in-desktop action whose destination path resolves through that same symlink. This is a rarer, chained scenario (comparable to the original report's "rare but real" multi-address token), which is consistent with the accepted Sherlock precedent of treating such edge-case identity checks as valid Medium severity even when the triggering condition is uncommon.

### Recommendation
Resolve the destination path with `fs.promises.realpath` (following the existing pattern used in `resolveWithin`/`app/src/lib/path.ts`) before comparing against `sensitiveLocations`, and re-validate after directory creation but before invoking `git clone`. Alternatively, reject clone destinations whose immediate parent directory entry is a symlink at all, rather than relying on string identity of the resolved path.

### Proof of Concept
1. Attacker publishes `repo-A` containing a tracked symlink `linkdir -> ../../.ssh` (or an absolute-path symlink to the victim's home `.ssh`), checked in as a normal git object.
2. Victim clones `repo-A` normally into `~/Documents/GitHub/repo-A`; git materializes `~/Documents/GitHub/repo-A/linkdir` as a symlink pointing at `~/.ssh`.
3. Victim later clicks an attacker-supplied `x-github-client://openRepo/https://github.com/attacker/x` link (or types a path) whose sanitized destination resolves to `~/Documents/GitHub/repo-A/linkdir/newclone`.
4. `isClonePathSensitive('~/Documents/GitHub/repo-A/linkdir/newclone')` lower-cases and compares the literal string against `~/.ssh` etc.; it does not match or start with any sensitive entry, so it returns `false`.
5. `clone()` proceeds and `git clone --recursive -- <url> <path>` writes through the symlink, populating/overwriting content inside the victim's real `~/.ssh` directory. [1](#0-0) [4](#0-3) [5](#0-4)

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
