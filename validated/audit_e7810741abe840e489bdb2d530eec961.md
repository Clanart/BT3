## Finding: Valid

### Title
Tag names spread unvalidated into `git push` argv, enabling flag/argument injection - (File: app/src/lib/git/push.ts)

### Summary
`push()` builds the `git push` argument vector and appends `tagsToPush` directly via `args.push(...tagsToPush)` with no validation and, critically, without a `--` separator to force git to treat the following tokens as refspecs rather than options. [1](#0-0) 

### Finding Description
`tagsToPush` is a plain array of tag-name strings surfaced from the git store's `_tagsToPush`, which is populated from local tag refs (created via `createTag`, or materialized locally after fetching a remote — tags fetched from an attacker-controlled repository become ordinary local refs). Nothing in `push.ts`, nor in the surrounding call chain that was inspected (`git-store.ts`, `tags-to-push-storage.ts`, `tag.ts`), validates that a tag name does not start with `-`, nor is a `--` argument separator inserted before the tag list. This differs from other git wrappers in the same codebase (`checkout.ts`, `diff.ts`, `add.ts`, `reset.ts`, `rm.ts`, `stash.ts`, `submodule.ts`, `log.ts`, `clone.ts`, `reflog.ts`, `apply.ts`, `rev-list.ts`) which each explicitly insert a literal `'--'` before pathspec/ref arguments to stop this exact class of injection. [2](#0-1) 

Git ref names are permitted to contain characters such as `-` and `=`; the only characters `git check-ref-format` rejects are things like space, `~`, `^`, `:`, `?`, `*`, `[`, `\`, and ASCII control characters — a leading `-` is not rejected. This means an attacker who controls a public repository can create a tag literally named e.g. `--receive-pack=/tmp/evil.sh` or `--force`. When a victim adds/fetches that repository as a remote (or forks it) and later performs a push through GitHub Desktop with "push tags" enabled, that tag name flows unchanged into `push()`'s `args` array and, because dugite spawns `git` directly with an argv array (no shell), git's own argument parser will interpret the injected string as an option flag rather than as a refspec.

### Impact Explanation
Depending on the injected flag, this can:
- Force `git push` to treat a normal push as `--force` (silently corrupting/overwriting remote history the user did not intend to overwrite, bypassing GitHub Desktop's force-with-lease confirmation UX), or
- Inject `--receive-pack=<path>`/`-o <server-option>`/other option flags recognized by the local git client, which is passed to the underlying transport (impact depends on the transport/server, e.g. self-hosted git servers over SSH accepting a custom `--receive-pack` executable path), or
- Otherwise corrupt the intended argv and change push semantics without any user-visible indication.

This falls squarely within the described valid-impact category: silent corruption of what the user pushes, triggered purely by cloning/fetching an attacker-controlled repository — no local access, credentials, or unusual user steps required beyond normal fetch + push.

### Likelihood Explanation
Moderate-to-high. The only prerequisites are: (1) the victim adds or forks a repository containing a maliciously named tag, (2) the victim fetches it (a completely normal, expected action), and (3) the victim later pushes tags via GitHub Desktop's standard "push" flow, which happens by default whenever unpushed tags exist. No special user interaction beyond ordinary usage is required.

### Recommendation
- Validate each entry of `tagsToPush` against a strict tag-name allow-list (reject any entry starting with `-`) before it reaches `push()`.
- Insert a literal `'--'` separator in `push.ts` immediately before `...tagsToPush` is spread into `args`, consistent with the pattern already used in `checkout.ts`, `diff.ts`, `add.ts`, `reset.ts`, and other git wrappers in this codebase, so git unconditionally treats subsequent tokens as refspecs regardless of their content.

### Proof of Concept
1. Attacker publishes a repository containing a tag named `--receive-pack=/tmp/evil.sh` (or `--force`) pointing at any commit.
2. Victim adds this repository as a remote (or forks it) in GitHub Desktop and fetches it, which creates a local tag ref with that literal name. [3](#0-2) 
3. Victim later pushes their own branch to a different remote (e.g. their own fork/origin) while this malicious tag is still unpushed locally; GitHub Desktop includes it in `tagsToPush`.
4. `push()` executes `git push <remote> <branch> --receive-pack=/tmp/evil.sh ...` (or with `--force`), because `args.push(...tagsToPush)` inserts the raw tag string as a bare argv token with no `--` separator. [1](#0-0)

export async function fetchTagsToPush(
  repository: Repository,
  remote: IRemote,
  branchName: string
): Promise<ReadonlyArray<string>> {
  const args = [
    'push',
    remote.name,
    branchName,
    '--follow-tags',
    '--dry-run',
    '--no-verify',
    '--porcelain',
  ]

  const result = await git(args, repository.path, 'fetchTagsToPush', {
    env: await envForRemoteOperation(remote.url),
    successExitCodes: new Set([0, 1, 128]),
  })

  if (result.exitCode !== 0 && result.exitCode !== 1) {
    // Only when the exit code of git is 0 or 1, its stdout is parseable.
    // In other cases, we just rethrow the error so our memoization layer
    // doesn't cache it indefinitely.
    throw result.gitError
  }

  const lines = result.stdout.split('\n')
  let currentLine = 1
  const unpushedTags = []

  // the last line of this porcelain command is always 'Done'
  while (currentLine < lines.length && lines[currentLine] !== 'Done') {
    const line = lines[currentLine]
    const parts = line.split('\t')

    if (parts[0] === '*' && parts[2] === '[new tag]') {
      const [tagName] = parts[1].split(':')

      if (tagName !== undefined) {
        unpushedTags.push(tagName.replace(/^refs\/tags\//, ''))
      }
    }

    currentLine++
  }

  return unpushedTags
}
