## Title
Commit-time diff re-fetch causes stale line-selection to be applied against different content, silently corrupting partial commits/discards - (File: `app/src/lib/git/apply.ts`)

### Summary
`BaseCustomAccounting`'s bug class is: a security-relevant check (slippage bound) is computed once, but the actual state-changing operation (`modifyLiquidity`) executes later against fresh pool state that can differ from what was checked, and the check is never re-validated against the value that is actually applied. GitHub Desktop has a structurally identical pattern in its partial-commit/partial-discard pipeline: the user's line "selection" (the equivalent of the slippage bound the user consented to) is computed against one snapshot of a file's diff, but the code that actually builds and applies the patch re-reads the diff from disk at execution time and blindly re-uses the old selection's line indices against that fresh diff.

### Finding Description
`applyPatchToIndex` (used for staging partial commits) fetches a brand-new diff at execution time: [1](#0-0) 

and then hands that fresh diff, together with the file's `DiffSelection` (which was computed against whatever diff was rendered earlier in the UI when the user checked/unchecked lines), to `formatPatch`: [2](#0-1) 

`formatPatch` decides what to include in the patch purely by absolute line index into the (possibly stale) selection: [3](#0-2) 

There is no verification that the diff used to build the selection is the same diff being patched. Desktop is aware this class of problem exists — it already has code that reconciles `selectableLines` against a newly-loaded diff for the *UI's* representation of selection state: [4](#0-3) 

but that reconciliation only updates what is *selectable* going forward from a UI reload; it is not run immediately before `applyPatchToIndex`/`discardChangesFromSelection` execute, so if the working-tree file changes between the last diff reconciliation and the moment the user hits "Commit" or "Discard selected lines," the git-level apply step still combines an old selection with a newly fetched diff without any equality/hash check between the two, and without re-deriving the selection against the new hunk layout.

The same shape exists for discard: `discardChangesFromSelection` is called with a `diff` object and a `selection`, and callers are expected to supply a diff that matches the selection, but nothing enforces that the diff passed in is the one the selection was computed from at the moment of application: [5](#0-4) 

This is the direct analog of the reported Uniswap issue: the "check" (what the user visually reviewed and chose to include/exclude) is evaluated against one state snapshot, while the actual mutating operation (`git apply --cached`) is executed against a different, later-fetched state, and the two are combined without re-validation — exactly like combining a stale slippage bound with a live, fee-inflated delta.

### Impact Explanation
If the tracked file's on-disk content changes between the time the diff was rendered/selected in the UI and the time `applyPatchToIndex`/`discardChangesFromSelection` runs (e.g. a format-on-save tool, a build/watch script from the cloned repository's `package.json` scripts, a linter's autofix, or any other background process with write access to the working tree), the hunk boundaries and line indices in the freshly-fetched diff can shift relative to the diff the user actually reviewed. Because the selection is keyed by absolute line index rather than tied to the diff content it was derived from, this can cause:
- Lines the user never selected being silently staged and committed.
- Lines the user did select being silently dropped or, worse, unrelated content at the same index range being committed instead.
- For discard, resurrecting or deleting the wrong hunk of a modified file.

This is a silent corruption of what the user commits/pushes — matching the "silent corruption of what the user commits or pushes" impact class, since Desktop presents no re-confirmation and the mismatch is invisible to the user at commit time.

### Likelihood Explanation
This does not require local/physical access or malware already present beyond what a normal developer workflow already exposes: any cloned repository that ships build tooling, watchers, git hooks, or editor-integrated formatters that write to tracked files while Desktop is open is sufficient to create the race window between diff-rendering and commit/discard execution. Because `getWorkingDirectoryDiff` is unconditionally re-fetched at apply time with no staleness check against the diff the selection was built from, there is no existing guard that closes this window.

### Recommendation
Before applying a patch built from a `DiffSelection`, verify that the diff used to construct the selection is still the current diff for that file (e.g., compare diff text/hash, or the underlying blob OID/mtime) immediately prior to calling `applyPatchToIndex`/`discardChangesFromSelection`, and abort/re-derive the selection (as already partially done in `app-store.ts`'s `selectableLines` reconciliation) rather than silently applying a possibly mismatched selection against a freshly fetched diff.

### Proof of Concept
1. Clone a repository that includes a background write process (e.g. a `postinstall`/watch script, or an editor/format-on-save integration) with write access to a tracked file.
2. In GitHub Desktop, open the Changes view for that file and select only some lines/hunks to commit (this computes a `DiffSelection` against the diff rendered at that moment).
3. Before clicking "Commit", let the background process rewrite/reformat the file (shifting line numbers/hunks) without the user noticing (no forced diff re-render is required for the click to proceed).
4. Click "Commit selected lines." `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` (`app/src/lib/git/apply.ts:60`) and applies the *old* `DiffSelection`'s absolute indices to the *new* hunk layout via `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`), producing a patch that stages content the user never reviewed/selected.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
