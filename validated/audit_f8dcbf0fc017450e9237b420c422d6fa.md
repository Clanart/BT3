## Analysis

I found a concrete structural analog. The Sherlock report's broken invariant is: **an action that depends on a prior state is executed against a freshly-fetched/unverified version of that state instead of the exact state the caller validated against, and the mismatch silently produces an unintended result** (liquidator's repay succeeds/fails independent of the collateral actually seized).

In GitHub Desktop, the same "stale-state re-fetch" pattern exists in the partial-commit staging path: the UI computes a `WorkingDirectoryFileChange.selection` (a `DiffSelection`, storing only line *indices*, not content) against a diff that was rendered and reviewed by the user, but at commit time `applyPatchToIndex` re-fetches a brand-new diff from disk and blindly re-applies those same numeric indices to it.

### Title
Partial-commit staging re-fetches the working-directory diff and reapplies stale line-index selections, allowing silent corruption of committed content - (File: app/src/lib/git/apply.ts)

### Summary
When a user stages a subset of hunks/lines for a commit, Desktop stores the selection as line-index positions (`DiffSelection`, keyed by absolute index into the diff that was displayed) rather than by line content. At commit time, `applyPatchToIndex` does **not** reuse the diff the user reviewed — it calls `getWorkingDirectoryDiff` again to build a fresh diff, then reapplies the old index-based selection to that new diff via `formatPatch`.

### Finding Description
`stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`) fetches the diff at staging time: [1](#0-0) 

`formatPatch` (`app/src/lib/patch-formatter.ts:129-221`) then walks `diff.hunks` and checks `file.selection.isSelected(absoluteIndex)` where `absoluteIndex = hunk.unifiedDiffStart + lineIndex`: [2](#0-1) 

`DiffSelection` is purely index-based, with no association to actual line content: [3](#0-2) 

Desktop is aware that diffs can "change dramatically" between the point the UI computed a selection and later use, and has a mitigation for the *live UI refresh* case (`app-store.ts` recomputes `selectableLines` on `_loadStatus`): [4](#0-3) 

However, that reconciliation only clamps selectable-line *sets* during UI refresh — it does not re-validate that the specific selected indices still correspond to the same textual lines the user reviewed, and it is not invoked on the commit-time path. `applyPatchToIndex` performs its own independent `getWorkingDirectoryDiff` call right before `git apply --cached`, with no re-validation against the diff object the UI last displayed and no check that the file's on-disk content is unchanged since the last render.

If the tracked file's content on disk changes between the moment the user makes their partial selection in the UI and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs (e.g. seconds later when the user clicks "Commit"), the hunk boundaries and `unifiedDiffStart` offsets in the newly-fetched diff shift. The stale absolute-index selection is then reinterpreted against different hunks/lines, so `git apply --cached` stages content the user never selected or reviewed — while the commit dialog still shows the old diff/selection as "what will be committed."

### Impact Explanation
This directly matches the "silent corruption of what the user commits or pushes" impact category. A cloned/fetched repository can legitimately arrange for tracked files to be rewritten between the diff being shown and the commit being executed — for example via a repo-provided file watcher/build task that the editor or IDE the repo targets runs automatically (`.vscode/tasks.json` with `runOptions.runOn: folderOpen`), a `post-checkout`/background git hook triggered by an unrelated Desktop-issued git command, or any tool the repository's tooling instructs the user to run alongside Desktop. None of these require local/admin access or prior malware — they are ordinary side effects of opening/using a repository whose tooling is attacker-controlled. The result is that the user believes they are committing (and possibly pushing) exactly the reviewed hunks, but the actual staged/committed content silently differs — a supply-chain-relevant integrity break, analogous to the liquidation contract committing based on data that no longer matches what was validated.

### Likelihood Explanation
Moderate. It requires a timing window between diff render and click-to-commit, and an external process (which a hostile repository can arrange to run, e.g. via build scripts/tasks/watchers commonly present in real projects) modifying the exact file the user is partially staging. This is a realistic but not attacker-fully-controlled window, and no existing guard (the `selectableLines` reconciliation) covers the commit-time re-fetch path in `apply.ts`.

### Recommendation
`applyPatchToIndex`/`stageFiles`/`createCommit` should either (a) accept and reuse the exact `IDiff` object that was last shown to and reviewed by the user for that file (threading it through from the Changes view rather than re-deriving it), or (b) re-validate at staging time that the on-disk file content/hash matches what the diff was computed against before trusting the stale index-based selection, aborting/re-prompting the user if it has changed.

### Proof of Concept
1. Open a repository in Desktop, modify a tracked file with multiple hunks, and in Changes view select only some lines/hunks for the next commit (leaving other hunks unselected).
2. Before clicking "Commit", have an external process (simulating a repo-provided build/watch task) rewrite the file so that hunk boundaries shift (e.g. insert/remove lines above the hunks the user selected) without Desktop's Changes view being told to refresh in between.
3. Click "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) calls `getWorkingDirectoryDiff` again, producing a diff with different `hunk.unifiedDiffStart` offsets.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:144-157`) reapplies the old `file.selection.isSelected(absoluteIndex)` against the new hunk layout, staging/committing different lines than what was shown in the last-rendered diff and selected by the user, with no error or warning surfaced.
