### Title
Stale line-level diff selections are silently reapplied to a changed working-directory file, corrupting what gets committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
The external report describes a state-ordering bug: a derived accumulator (`lnImpliedRateCumulative`) is updated with a *post-swap* value but treated as if it applied to the *entire prior interval*, so the observation silently misrepresents what actually happened during that window. The Desktop analog is `updateChangedFiles()` in `app/src/lib/stores/updates/changes-state.ts`, which reapplies a file's previously recorded line-level `DiffSelection` onto the *new* `WorkingDirectoryFileChange` object every time git status is refreshed, without validating that the underlying diff/hunks are still the same. The stale selection (which lines are "included") is carried forward as if it still describes the current diff, so a user can end up committing a different set of lines than the ones they actually reviewed and checked.

### Finding Description
`updateChangedFiles` merges the freshly-fetched `status.workingDirectory.files` with the previous in-memory files purely by file ID, and blindly copies over the old `selection` object onto the new file: [1](#0-0) 

This happens on *every* status refresh (`_loadStatus` → `updateChangedFiles`), for *every* file in the working directory — not just the currently-viewed one: [2](#0-1) 

The only place where selectable lines are recomputed against a fresh diff is `updateChangesWorkingDirectoryDiff`, and even there it is scoped to the single file the user currently has open, and it only prunes lines that no longer exist — it doesn't re-validate that a previously "included" line index still corresponds to the same content: [3](#0-2) 

Just like the oracle bug where the post-swap rate is applied over the *whole* interval instead of the *actual* period it was valid for, here a `DiffSelectionType.Partial` selection computed against an *old* diff is carried forward and applied to a *new* diff state whose hunk/line layout may have shifted (e.g., external edits, a hook/pre-commit modification, an autosave, or another process touching the file between two status refreshes). Git commit generation (`patch-formatter.ts` / `apply.ts` / `update-index.ts`) trusts this selection when building the patch that is staged and committed, so the corrupted selection state directly determines what content is written to the repository history.

### Impact Explanation
If the selection is stale relative to the new diff, the set of "included" lines silently no longer corresponds to what the user reviewed in the Changes view before clicking Commit. This is a silent corruption of what the user commits — lines a user intentionally excluded could be included (leaking unintended content, e.g. a debug print or credential a user meant to keep local) or lines a user intended to include could be silently dropped. There is no error, confirmation, or invalidation surfaced to the user; the diff view can also continue displaying a cached diff (`selection.diff` reused when `selectedFileIDs` are unchanged, per the same file) that doesn't match on-disk content by the time the patch is built.

### Likelihood Explanation
Medium: the race window is any background status refresh (Desktop polls/refreshes status frequently — on focus, after fetches, timers, file-watcher events) racing with a file being modified on disk between when the user makes a partial line selection and when they click "Commit." No attacker/local access is required beyond the normal threat model of an untrusted repository triggering hooks or generating file changes (e.g., a pre-commit/post-checkout hook, or a build step configured in the repo) that alter tracked files' content between two status polls while a partial commit is in flight.

### Recommendation
When merging previous file selection state into freshly-fetched status in `updateChangedFiles`, do not unconditionally reuse `existingFile.selection`. Instead, invalidate/clear partial line-level selections whenever the file's diff-affecting attributes have changed (e.g., recorded blob hash/oid, size, or mtime differs from what the selection was computed against), forcing a fresh diff load and re-derivation of selectable lines before allowing commit — mirroring the recommendation to use the pre-swap (i.e., only validated/known-consistent) state rather than blindly propagating potentially stale derived state across an interval where the underlying data may have changed.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt` so it has 10 changed lines.
2. In the Changes view, partially select lines 1–5 only (`DiffSelectionType.Partial`), leaving lines 6–10 unselected.
3. Before committing, have an external process (e.g., a pre-commit-adjacent tool, a build watcher, or simply editing the file in another editor) modify `file.txt` such that the diff hunks shift — e.g., insert 3 new lines at the top so what was "line 5" is now different content, while status still reports the file by the same path/ID.
4. Desktop's periodic `_refreshRepository` → `_loadStatus` → `updateChangedFiles` runs before the user notices, re-applying the old `existingFile.selection` (line indices 1–5) onto the new `WorkingDirectoryFileChange`, per `changes-state.ts:56`.
5. The user, still trusting the (now-stale) view, clicks Commit. The patch is built from the reapplied selection indices against the new file content, and the committed patch includes/excludes different actual lines than what was shown/intended when the selection was made — corrupting the resulting commit without any warning.
