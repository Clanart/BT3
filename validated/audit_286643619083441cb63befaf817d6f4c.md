### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is permanently trapped in the Host contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward it to `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` to buy exactly `fee`/`amount` worth of `feeToken`. None of these three functions capture the return value of `swapETHForExactTokens` or otherwise account for unspent native token, and none of them forward any refund to `_msgSender()`. This exactly mirrors the `forgeWithListed` bug class from the seed report: a caller is allowed (indeed expected, per the docs) to send `msg.value` that only needs to *cover* the fee, but any excess beyond what the swap actually consumes is not returned to the payer.

### Finding Description
Compare the three call sites in `EvmHost.sol`: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three, `swapETHForExactTokens` is invoked with the entire `msg.value`, but the returned `uint256[] memory amounts` (which reports how much native token was actually spent — `amounts[0]`) is discarded. No code path computes `msg.value - amounts[0]` and refunds it to `_msgSender()`.

This is a direct regression relative to the pattern the same codebase correctly implements elsewhere. `IntentGatewayV2.sol` and `ExtrinsicIntents.sol` both capture the swap's spent amount and refund the difference: [4](#0-3) [5](#0-4) 

`EvmHost` itself never does this. Because `EvmHost` is the contract that actually *calls* the router (`address(this)` in `EvmHost` is `msg.sender` from the router's perspective), any leftover ETH that a standard `UniswapV2Router02.swapETHForExactTokens` refunds goes back to `EvmHost`, not to the original transaction sender. That leftover native ETH becomes stranded inside `EvmHost`'s balance with no user-facing mechanism to reclaim it — `EvmHost.sol` exposes no `withdraw`/`sweep`/`receive` function for native ETH; the only asset-recovery path visible is the governance `IHostManager.withdraw` for `feeToken` revenue, not native ETH.

The situation is worse on chains using the custom Gnosis wrapper. `GnosisUniswapV2Wrapper.swapETHForExactTokens` does not perform partial spending logic at all — it wraps the **entire** `msg.value` into WETH/WXDAI and transfers all of it to `msg.sender` (i.e., to `EvmHost`), while only checking `amountOut > msg.value` (revert if insufficient, but never limiting to `amountOut`): [6](#0-5) 

Here `EvmHost` receives (and keeps) fee tokens worth the *entire* overpaid `msg.value`, not just `post.fee`/`get.fee`/`amount`. Since `dispatch()`/`fundRequest()` never use the returned `amounts[0]` to compute a refund, the entire surplus — fee-token equivalent of the excess native ETH — is absorbed by the Host with no accounting entry crediting it back to the payer.

The documentation explicitly instructs integrators to just forward `msg.value` without needing to compute the swap precisely ("User must send enough native tokens to cover fees... The Host will swap native -> feeToken via Uniswap"), which normalizes sending more than the exact fee — exactly the overpayment behavior the seed report flags as dangerous when no refund path exists: [7](#0-6) 

### Impact Explanation
Every unprivileged user or application calling `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with any native-token overpayment (which is the normal/expected usage pattern per the documentation, since exact swap output amounts are impossible to know client-side due to slippage/price movement) permanently loses the excess value into the Host contract. This is a direct value-leak/fund-loss primitive reachable through the most common public entry points of the bridge (dispatching cross-chain requests and topping up relayer fees), matching the "stealing or loss of funds" impact category. Unlike the C4 report's narrow race-condition trigger (fee changed mid-flight), here overpayment occurs on essentially every native-token dispatch because slippage/AMM price movement makes it operationally infeasible to send the exact wei amount the swap will consume.

### Likelihood Explanation
High. No malicious actor, relayer, or governance compromise is required — an honest user following the documented native-payment flow (`dispatch{value: msg.value}(...)`) will routinely send more ETH than the swap consumes (to buffer against price movement), and the excess is silently absorbed with no refund and no recovery function. The bug is triggered by ordinary use, not by an attacker-crafted edge case.

### Recommendation
- Capture the return value of `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.sol`/`ExtrinsicIntents.sol`.
- Fix `GnosisUniswapV2Wrapper.swapETHForExactTokens` to only wrap/transfer `amountOut` worth of native token and refund the remainder to `msg.sender`, rather than converting and forwarding the entire `msg.value`.
- Add a native-ETH sweep/withdraw path if any residual dust is intentionally allowed to remain, ensuring it is governance-controlled and not silently accumulated as an unrecoverable value leak.

### Proof of Concept
1. Deploy `EvmHost` wired to a standard `UniswapV2Router02` (or the `GnosisUniswapV2Wrapper`).
2. Call `dispatch(DispatchPost)` with `post.fee = 1e18` (feeToken units) and `msg.value` set generously above the actual ETH cost of buying `1e18` feeToken (e.g., 2x the expected amount, to account for slippage as the docs suggest).
3. Observe: `swapETHForExactTokens` consumes only `amounts[0]` ETH and (per standard router behavior) refunds `msg.value - amounts[0]` back to `msg.sender` of the swap call, which is `EvmHost`, not the original transaction sender.
4. Check `address(EvmHost).balance` before and after: the leftover ETH remains in `EvmHost` with no event, no accounting record, and no public function to withdraw it back to the original caller.
5. With `GnosisUniswapV2Wrapper`, repeat with `amountOut < msg.value`: observe the wrapper converts and transfers the *entire* `msg.value` to `EvmHost` as feeToken, i.e., `EvmHost` is credited/holds `msg.value` equivalent in feeToken even though only `post.fee` was required — the surplus feeToken is stuck with no user-refund mechanism.

```text
    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
```

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol" icon="solidity"
contract MyApp is HyperApp {
    function readRemoteStateWithNative(
        bytes memory dest,
        bytes[] memory keys
    ) public payable returns (bytes32) {
        bytes memory context = abi.encode(msg.sender, block.timestamp);
        
        DispatchGet memory getRequest = DispatchGet({
            dest: dest,
            height: 0,
            keys: keys,
            timeout: 3600,
            fee: 0,
            context: context
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
```
