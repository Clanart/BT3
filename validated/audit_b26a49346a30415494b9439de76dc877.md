### Title
Reachable panic on untrusted DKG messages in PedPoP encryption layer — duplicate registration and unregistered-decryptor blame crash honest nodes - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The FreeType CVE is a buffer over-read in a parser (`skip_comment` in `psobjs.c`) reachable when untrusted font bytes are processed — i.e., improper handling of attacker-controlled input causes an out-of-bounds access / crash (availability impact, Medium). The Serai analog is improper handling of attacker-controlled DKG messages in the PedPoP encryption layer: `Decryption::register` uses `assert!` on peer-controlled state, and `decrypt_with_proof` indexes a `HashMap` with a peer-derived `Participant` key. Both panic instead of returning an error when fed adversarial inputs, crashing the honest participant processing the messages.

### Finding Description
Two reachable panic sites exist in `crypto/dkg/pedpop/src/encryption.rs`:

1. `Decryption::register` panics if a participant registers an encryption key twice. The set of `EncryptionKeyMessage`s processed is supplied by other DKG participants over the channel — a participant who sends a second registration message (or whose message is replayed/duplicated by a faulty peer path before dedup) triggers `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")`. The library explicitly states it cannot deduplicate conflicting messages itself ("If any participant sends multiple sets of commitments, they are faulty... That responsibility lies with the caller"), so a caller that forwards a duplicate reaches the panic.

   File: `crypto/dkg/pedpop/src/encryption.rs:356-361`
   ```rust
   assert!(
     !self.enc_keys.contains_key(&participant),
     "Re-registering encryption key for a participant"
   );
   self.enc_keys.insert(participant, msg.enc_key);
   ```

2. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly when verifying the accuser's `EncryptionKeyProof`. `decryptor` is a `Participant` derived from the accusation being processed. `Participant` is just a nonzero `u16` wrapper (`Participant::new(u16)`); if the named decryptor never completed registration (e.g., an accusation crafted for an index that isn't in `enc_keys`, or the decryption map was built from a different/ambiguous registration set), the `HashMap` index panics. Note `EncryptedMessage::read`, `EncryptionKeyProof::read`, `Commitments::read` etc. all accept arbitrary attacker bytes and correctly return `io::Error` on malformed input — the panic occurs on *semantically* valid but adversarial inputs, which is exactly the over-read bug class: the parser boundary is fine, but a downstream consumer assumes structure the attacker can violate.

   File: `crypto/dkg/pedpop/src/encryption.rs:383-390`
   ```rust
   proof
     .dleq
     .verify(
       &mut encryption_key_transcript(self.context),
       &[C::generator(), msg.key],
       &[self.enc_keys[&decryptor], *proof.key],
     )
     .map_err(|_| DecryptionError::InvalidProof)?;
   ```

The same unchecked indexing pattern exists at `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, encryption.rs:466), though that path is driven by local participant selection rather than a peer message.

### Impact Explanation
An unprivileged DKG participant can crash every honest participant that processes its messages:

- Sending two `EncryptionKeyMessage`s (or equivocating so different honest nodes see different orderings) causes `Decryption::register` to panic on all nodes that observe the duplicate.
- Submitting a blame/accusation flow that reaches `decrypt_with_proof` naming a `decryptor` not present in `enc_keys` causes a `HashMap` index panic while the honest node is trying to arbitrate the blame.

A panic during DKG execution aborts the key-generation (or resharing) session for that node and, in a coordinator/processor context, can take down the running task — an availability failure matching the CVE's A:H impact class. Because the panic fires inside library code rather than being returned as a `Result`, the caller has no way to attribute blame and retry.

### Likelihood Explanation
Triggering requires only sending protocol messages — no collusion, no leaked keys, no validator compromise:

- Duplicate registration: send two valid `EncryptionKeyMessage`s. Whether every deployment panics depends on caller-side dedup, but the library itself documents that it does not enforce uniqueness, and the `assert!` indicates the author treated it as unreachable rather than handling it gracefully.
- Unregistered decryptor: a faulty participant can be accused before it registers, or an accusation can reference an index whose registration was never processed by the victim node; reaching `decrypt_with_proof` then panics unconditionally.

Both are deterministic crashes reachable with public inputs, so Medium severity (availability-only, no secret leakage) is consistent with the CVE's 6.5 rating.

### Recommendation
- Replace the `assert!` in `Decryption::register` with a fallible check returning an error (e.g., extend `DecryptionError` or return `io::Error`), so duplicate registrations reject the message instead of aborting the process.
- In `decrypt_with_proof`, use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` instead of direct indexing.
- Apply the same treatment to `Encryption::encrypt`'s `enc_keys[&participant]` lookup, or document/enforce via types that only registered participants can be addressed.
- Audit other `assert!`/indexing sites on peer-derived identifiers in `crypto/dkg` (e.g., `included[...]`, `responses[l]` in `crypto/frost/src/sign.rs`) — those specific ones happen to be guarded by `validate_map`/`included` construction, but the pattern of indexing maps with attacker-influenced `Participant` keys should be eliminated in favor of checked lookups.

### Proof of Concept
Conceptual, against `crypto/dkg/pedpop`:

```rust
// Path 1: duplicate registration panic
let mut dec: Decryption<C> = Decryption::new(context);
let msg: EncryptionKeyMessage<C, M> = evil_participant_registration(); // valid message from participant p
dec.register(p, msg.clone()); // ok
dec.register(p, msg);         // PANIC: "Re-registering encryption key for a participant"

// Path 2: unregistered decryptor panic
let mut dec: Decryption<C> = Decryption::new(context);
// register enc keys only for participants 1..=t (honest set)
let msg: EncryptedMessage<C, E> = EncryptedMessage::read(&mut bytes, params)?; // valid PoP from accuser
let proof: EncryptionKeyProof<C> = EncryptionKeyProof::read(&mut proof_bytes)?; // accuser's valid DLEq for msg.key
// accuser names a decryptor index that never registered an encryption key
dec.decrypt_with_proof(accuser, Participant::new(unregistered_index).unwrap(), msg, Some(proof));
// PANIC at encryption.rs:388: self.enc_keys[&decryptor] on absent key
```

In both cases the input messages are well-formed (all `read` calls succeed and signatures/DLEq proofs verify), so error handling at the deserialization boundary cannot prevent the crash — mirroring the FreeType bug where `skip_comment` over-read despite the token parser appearing to bound the input.
