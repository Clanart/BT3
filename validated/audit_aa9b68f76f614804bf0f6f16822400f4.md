### Title
DID recovery attestation uses replayable AGG_SIG_UNSAFE signature not bound to the recovering coin - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
The Chia DID (Decentralized Identifier) recovery mechanism authorizes recovery of a lost/compromised DID by collecting signed "attestation" messages from a threshold of designated backup DIDs. Each attestation is built with `create_recovery_message_puzzle()`, which emits an `AGG_SIG_UNSAFE` condition whose signed message is only the new inner-puzzle hash (`newpuz`) — it is **not** bound to the specific recovering DID coin, its parent, or any nonce. This is the same root cause described in the external report: a signature intended to authorize a single, specific action is not scoped/nonced, so it can be replayed to authorize an unintended, different action.

### Finding Description
`create_recovery_message_puzzle()` produces two conditions when a backup DID spends its "attestation" coin: [1](#0-0) 

- `CREATE_COIN_ANNOUNCEMENT` of `recovering_coin_id` — an **unsigned** condition, freely craftable by whoever assembles the final recovering spend bundle.
- `AGG_SIG_UNSAFE` over `(pubkey, newpuz)` — the only *signed* material, and it contains neither the recovering coin's id, parent, puzzle hash, nor any additional/domain-separation data.

`AGG_SIG_UNSAFE` is documented and enforced in consensus as the one AGG_SIG variant that is *not* bound to a specific coin or spend — it is validated purely as `(pubkey, msg)` pairs collected globally across the whole spend bundle, with no scoping to the announcement, the coin, or any nonce: [2](#0-1) [3](#0-2) 

Because the `AGG_SIG_UNSAFE` message is only `newpuz`, and the DID inner puzzle validates recovery by matching threshold signatures against `pubkey`s in its own `recovery_list` (independent of which specific DID coin produced the attestation), the same on-chain, previously-broadcast attestation signature can be extracted and reused: any other DID that also lists the same backup pubkey as a valid recoverer can be "recovered" to the exact same `newpuz` by pairing the reused signature with a self-crafted `CREATE_COIN_ANNOUNCEMENT` matching that other DID's `recovering_coin_id` — without any new interaction from, or consent of, the backup-DID holder. This mirrors the ERC-4337 report precisely: the signature was meant to authorize one specific recovery event but nothing in the signed payload prevents it from being replayed to authorize recovery of a different coin.

### Impact Explanation
If an organization or protocol reuses one trusted "backup"/recovery DID across multiple child DIDs (a natural pattern for custodial/recovery-as-a-service setups), a single legitimate recovery event's broadcast attestation becomes a reusable credential: an attacker who observes it on-chain can replay the exact `(pubkey, newpuz)` signature against every other DID that lists the same backup pubkey, redirecting control of those DIDs to the `newpuz` puzzle hash without the backup DID owner's participation or consent. This is an unauthorized coin/asset-ownership takeover of DID singleton coins reachable by any observer of public chain data — no privileged position required.

### Likelihood Explanation
Exploitability requires: (1) at least two DIDs configured with the same backup/recoverer pubkey (a common operational pattern), and (2) a legitimate recovery attestation having been broadcast at least once. Given those preconditions, replay is trivial — the attacker only needs to craft their own `CREATE_COIN_ANNOUNCEMENT` and coin spend and reuse the already-public signature bytes; no cryptographic work or private key access is needed.

### Recommendation
Bind the `AGG_SIG_UNSAFE` message in `create_recovery_message_puzzle()` to the specific recovering coin (e.g., include `recovering_coin_id`, or better, use a coin-scoped condition such as `AGG_SIG_ME`/`AGG_SIG_PARENT` with an explicit nonce derived from `recovering_coin_id`, so the signed payload cannot be separated from the specific recovery event it was intended for).

### Proof of Concept
1. DID `A` and DID `B` both list backup DID `R`'s pubkey `pk_R` in their `recovery_list` with `num_of_backup_ids_needed = 1`.
2. DID `A`'s legitimate owner initiates recovery to `newpuz`; backup `R` produces an attestation coin spend per `create_spend_for_message()` (`chia/wallet/did_wallet/did_wallet_puzzles.py:158-172`), broadcasting `AGG_SIG_UNSAFE(pk_R, newpuz)` on-chain.
3. An attacker observes this attestation in the confirmed block/mempool history and extracts `(pk_R, newpuz, signature)`.
4. The attacker crafts a new spend bundle recovering DID `B`, supplying their own `CREATE_COIN_ANNOUNCEMENT(recovering_coin_id_of_B)` and reusing the extracted `AGG_SIG_UNSAFE` signature to satisfy DID `B`'s single-backup-signature recovery requirement, since the DID inner puzzle only checks pubkey membership and AGG_SIG_UNSAFE presence, not attestation-to-coin binding.
5. DID `B` is now recovered/controlled by `newpuz`, without `R`'s consent or awareness for this second recovery.

Note: I was unable to fully trace the DID inner-puzzle CLVM's exact recovery-validation logic (it lives in the compiled `DID_INNERPUZ` chialisp bundled via `chia_puzzles_py`, not in readable Python source available to the index) to confirm there is no additional binding check beyond pubkey/signature-count matching. This should be verified directly against `DID_INNERPUZ` chialisp source before treating this as confirmed exploitable in production.

```python
def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle
```
