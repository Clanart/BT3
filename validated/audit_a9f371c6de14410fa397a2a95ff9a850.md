## Analog Found

### Title
Future-dated oracle publish-time is treated as "fresh" and permanently poisons the per-feed monotonic timestamp, bricking price resolution - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The Salty `DAO._executeApproval`/`_finalizeApprovalBallot` bug shows how an unguarded, one-time bad input can lock a critical state transition forever, with no recovery path short of extraordinary user action. Zest's oracle timestamp-freshness gate contains the same class of "permanent-lock" logic error: a single future-dated `publish-time` accepted from a price feed is written as the new monotonic high-water mark for that feed, after which every subsequent (correct, present-time) update is rejected by the same monotonic check, permanently reverting `price-resolve` for that asset until real time catches up to the erroneous future timestamp.

### Finding Description
`oracle-timestamp-fresh` computes the staleness delta as follows: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

If the feed-reported `ts` (`publish-time` from Pyth, or the converted DIA timestamp) is ever greater than the current `stacks-block-time`, `delta` is forced to `u0`, which trivially satisfies `<= delta max-staleness`. Combined with `(>= ts prev)` (also true, since a future `ts` is by definition `> prev`), this future timestamp is unconditionally accepted as "fresh."

`price-resolve` then persists that accepted timestamp as the new monotonic floor for the `{type, ident}` feed key: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        ...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Once `last-update` for that feed key holds a value in the future, every legitimate, correctly-timestamped subsequent update (`ts` = real, present `publish-time`) will have `ts < prev`, failing `(>= ts prev)` and causing `ERR-ORACLE-INVARIANT` on every call — permanently, until `stacks-block-time` naturally advances past the poisoned future value. There is no admin recovery path exposed for this map entry in the market contract; the `last-update` map has no setter other than `price-resolve` itself, so the invariant remains unrecoverable via any operator action within the market contract.

This is precisely analogous to the Salty `DAO` finding: a single unguarded event (there, a reverting external call; here, one future-dated oracle timestamp) permanently corrupts a piece of protocol state that gatekeeps a core function (there, ballot finalization; here, price resolution used by every borrow/withdraw/liquidate/health check for that asset), with no built-in way to unstick it short of waiting out real time or an emergency contract upgrade.

The `write-feeds`/`write-feed` path lets any caller push arbitrary Pyth VAA/PNAU payloads through `verify-and-update-price-feeds` on `borrow`, `liquidate`, and collateral-mutating entrypoints: [3](#0-2) 

so a single valid Pyth VAA whose `publish-time` is ahead of the current Stacks block time (plausible given Pyth/Stacks clock skew, or a slightly-ahead attestation from Pythnet) is sufficient to trigger the poisoning — no compromise of governance, no bad registry configuration, and no reliance on the oracle actually reporting incorrect price data (only a timestamp slightly ahead of local block time).

### Impact Explanation
Once poisoned, `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for that specific feed on every subsequent call. Because `get-asset-value`, `get-notional-evaluation`, and `is-healthy-with-mask` all depend on `price-resolve` succeeding for every relevant asset in a user's mask, this bricks `borrow`, `withdraw`, and `liquidate` for any position that includes the poisoned asset as collateral or debt, for as long as the injected future timestamp remains ahead of `stacks-block-time`. This is a temporary freezing of user funds/positions (borrowers cannot manage their position, liquidators cannot liquidate unhealthy positions using that asset), matching the in-scope High-impact class "temporary freezing of funds."

### Likelihood Explanation
Likelihood is non-trivial: `write-feeds` accepts arbitrary encoded Pyth payloads from any caller on `borrow`/`liquidate`/collateral operations, and the only requirement to trigger the bug is a `publish-time` that exceeds the current Stacks block's `stacks-block-time` — achievable through normal clock skew between the Pythnet attestation and Stacks block production, or by a caller deliberately supplying a payload with an inflated `publish-time` (still cryptographically valid per Wormhole/Pyth verification, since `publish-time` is not independently bounded against `stacks-block-time` before being accepted here).

### Recommendation
In `oracle-timestamp-fresh`, reject (rather than silently zero-out) timestamps that are ahead of `stacks-block-time`:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)         ;; reject future timestamps outright
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
Additionally, consider bounding how far ahead of the previous accepted timestamp a new timestamp is allowed to be (a maximum forward jump), and/or exposing an authorized-only reset/override for the `last-update` map so a poisoned entry can be corrected without waiting for real time to pass.

### Proof of Concept
1. Attacker (or a legitimate caller with a slightly-skewed clock) obtains a validly-signed Pyth VAA for asset `X`'s feed whose `publish-time` is set some seconds ahead of the current Stacks block's `stacks-block-time` (e.g., +300s).
2. Attacker calls any market entrypoint accepting `price-feeds` (e.g., `borrow`) with this payload, causing `write-feeds` → `write-feed` → Pyth `verify-and-update-price-feeds` to store the future-dated price in `pyth-storage-v4`.
3. In the same or a subsequent call, `price-resolve` for asset `X` resolves this stored feed: `oracle-timestamp-fresh` computes `delta = 0` (since `ts > stacks-block-time`) and accepts it; `price-resolve` then executes `(map-set last-update key timestamp)`, storing the future timestamp as `prev`.
4. On the next legitimate call needing asset `X`'s price (any user's `borrow`/`withdraw`/`liquidate` touching `X`), the real Pyth feed reports the correct, present-time `publish-time`, which is now `< prev` (the poisoned future value). `oracle-timestamp-fresh` returns `false` via `(>= ts prev)`, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for every subsequent call involving asset `X`, until `stacks-block-time` naturally advances past the poisoned value.
