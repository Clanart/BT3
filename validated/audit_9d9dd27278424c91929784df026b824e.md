## Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` causes stack-overflow DoS via a single transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
The `php-svg-lib` bug class is "recursion depth is not bounded during parsing, and the anti-recursion/anti-abuse check only runs *after* parsing has already recursed arbitrarily deep." The same pattern exists in Kaia's `AccountKey` RLP decoding path: `AccountKeyRoleBased.DecodeRLP` recursively re-invokes the top-level `AccountKeySerializer` decoder for each element of the role-based key list, and this recursion has no depth limit. The rule that forbids nesting (`RoleBasedKey cannot contain a roleBasedKey`) is enforced later, in `CheckInstallable`/`checkAccountKeyZeroValues`, i.e. only *after* the recursive decode has already completed. A crafted, deeply self-nested `AccountKey` blob supplied in an ordinary `AccountUpdate`/`AccountCreation` transaction can therefore drive unbounded Go-stack recursion during decoding, before any of the "no nested composite type" checks execute.

### Finding Description
`AccountKeySerializer.DecodeRLP` dispatches based on the decoded `keyType` and, for `AccountKeyTypeRoleBased`, calls `NewAccountKeyRoleBased()` then `s.Decode(serializer.key)`: [1](#0-0) 

`AccountKeyRoleBased.DecodeRLP` decodes a list of raw byte blobs and, for **each** blob, independently RLP-decodes it as a brand-new `AccountKeySerializer` via `rlp.DecodeBytes`: [2](#0-1) 

Because each nested blob is decoded with a fresh call to `rlp.DecodeBytes`/`NewAccountKeySerializer().DecodeRLP`, this is a **direct Go-stack recursion** driven purely by attacker-controlled content: if the byte blob itself again encodes `keyType = AccountKeyTypeRoleBased`, the process recurses into `AccountKeyRoleBased.DecodeRLP` again, and so on. There is no depth counter anywhere in this call chain (`rlp.Stream`'s internal `stack` field only tracks list boundaries within a single `Decode` call, not across the independent, re-entrant `rlp.DecodeBytes` calls made per-blob).

The only defense against nested `RoleBased` keys is `CheckInstallable`, which rejects `IsCompositeType()` sub-keys — but this check only runs *after* the entire structure has already been decoded: [3](#0-2) [4](#0-3) 

This mirrors the CVE-2023-50251 pattern precisely: the "must not self-reference" rule (analogous to SVG's `use` self-reference guard) is a post-hoc semantic check, not a parse-time depth limit, so the recursive parser itself is exploitable before that rule can ever run.

This decode path is reached whenever an `AccountUpdate` or `AccountCreation` transaction is parsed: the account key bytes (`KeyData`) are RLP-decoded via `accountkey.NewAccountKeySerializer()` / `rlp.DecodeBytes`: [5](#0-4) [6](#0-5) 

Any unprivileged sender can submit such a transaction via `eth_sendRawTransaction`/`txpool.AddRemote`, meaning the RLP is decoded on every node/full node/RPC endpoint that receives and validates the transaction, well before signature/nesting checks reject it.

### Impact Explanation
A crafted `AccountKeyRoleBased` blob nested many levels deep (each level only needs the minimal RLP list overhead of a few bytes) can cause the recursive `DecodeRLP` chain to recurse thousands of times per transaction submission. In Go, exceeding the goroutine stack limit results in a fatal, unrecoverable `runtime: goroutine stack exceeds ... stack overflow` process crash — `recover()` cannot catch this, unlike a normal panic. Any node (validator/CN, PN, EN, or public RPC endpoint) that accepts and RLP-decodes the transaction — during tx-pool admission, block validation, or `kaia_decodeAccountKey`/`kaia_encodeAccountKey` API calls — can be crashed by a single submitted transaction or RPC payload from an unprivileged sender. Because the trigger is a normal transaction (not a peer/consensus message), it can propagate through the mempool and potentially crash multiple honest nodes simultaneously, which is a network-wide availability impact, not merely resource exhaustion on one host.

### Likelihood Explanation
High reachability: the crafted payload is just RLP bytes placed in the `AccountKey` field of a standard `AccountUpdate`/`AccountCreation` transaction, requiring no special privileges, only enough balance to pay for the transaction (or even none, if only decode-time crash is targeted via `kaia_decodeAccountKey` RPC, which decodes arbitrary attacker-supplied hex with no gas cost at all). No signature validity is required to trigger the decode-time recursion.

### Recommendation
Add an explicit recursion/nesting depth limit before or during `AccountKeyRoleBased.DecodeRLP` (and generally in `AccountKeySerializer.DecodeRLP`), e.g., threading a depth counter through decoding and rejecting decode once a small maximum depth (1, matching the "no nested composite type" business rule) is exceeded — enforcing the "no nested RoleBased key" rule at parse time rather than only after the fact in `CheckInstallable`. Additionally, expose `kaia_decodeAccountKey`/`kaia_encodeAccountKey` RPCs and transaction ingestion paths to the same guard so unauthenticated RPC calls cannot trigger the same recursion.

### Proof of Concept
Conceptual construction (exact byte-level PoC would need to be built with the `rlp` and `accountkey` packages, but the mechanism is deterministic):
1. Start with `innerKey = RLP(AccountKeyTypeNil)` wrapped as an `AccountKeySerializer` (`keyType || key`).
2. Build level `i+1` as: `AccountKeySerializer{ keyType: AccountKeyTypeRoleBased, key: RLP([ RLP(level_i) ]) }` — i.e., an `AccountKeyRoleBased` whose single list element is the RLP bytes of the previous level's full serializer.
3. Repeat this wrapping N times (N in the thousands is achievable within normal transaction size limits, since each level adds only a few bytes of RLP list/string framing).
4. Submit an `AccountUpdate` transaction (`TxTypeAccountUpdate`) with `TxValueKeyAccountKey` set to the RLP bytes from step 3 (or call `kaia_decodeAccountKey` RPC directly with the encoded hex).
5. On decode (`AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → recursive `rlp.DecodeBytes`), the call stack grows by one full decode stack frame per level; at sufficient N this exceeds the Go runtime's maximum goroutine stack and crashes the process with an unrecoverable stack-overflow fatal error, before `CheckInstallable`'s nested-type rejection ever executes.

**Uncertainty**: I could not fully verify the exact maximum transaction/calldata size limit enforced elsewhere in the codebase (e.g., `TxPool` size caps) that would bound how many nesting levels are practically achievable in a single transaction; this affects the exact depth needed but not the existence of the unbounded-recursion-before-validation flaw itself. I was not able to execute the PoC in this environment; the above is a structural/code-level derivation based on the read code paths cited above.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
}
