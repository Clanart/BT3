### Title
Identity group key / identity verification shares accepted, making any crafted signature verify — ([File: crypto/dkg/src/lib.rs])

### Summary
The Qubit exploit's root cause was that an operation meant to fail on a degenerate input (a `safeTransferFrom` call to the zero address) silently succeeded, letting a deposit be credited with nothing locked. The analog in Serai is that `ThresholdKeys::read` / `ThresholdKeys::new` never reject identity verification shares or an identity `group_key`. If attacker-controlled bytes are fed to `ThresholdKeys::read` (a listed untrusted-bytes sink), the resulting key set has `group_key == identity`, and the FROST signature fast-path in `AlgorithmSignatureMachine::complete` accepts a forgery: `R + c·A − s·G == 0` collapses to `R − s·G == 0` when `A` is the identity point, which any prover satisfies without knowing a discrete log.

### Finding Description
- `ThresholdKeys::read` deserializes each verification share via `<C as Ciphersuite>::read_G(reader)` (`crypto/dkg/src/lib.rs:622`), not `Curve::read_G`. Only `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) performs the identity rejection. The base `Ciphersuite::read_G` accepts canonical identity encodings.
- `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-378`) computes `group_key` as the interpolated sum of `verification_shares[1..=t]` and performs no identity check on either the shares or the resulting `group_key`.
- `SchnorrSignature::verify` (`crypto/schnorr/src/lib.rs:108-110`) checks `multiexp_vartime([R, cA, -sG]).is_identity()`. With `A = identity` the `cA` term vanishes, so `(R = G·x, s = x)` verifies for any `x` the attacker chooses.
- `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:465-467`) trusts `algorithm.verify(self.view.group_key(), &self.Rs, sum)` as the happy path. An attacker supplying all preprocesses can pick nonce commitments `R_i = G·r_i`, so `R = G·Σr_i`, then set the share sum `s = Σr_i` — producing an accepted signature under a "group key" that has no secret.

### Impact Explanation
A serialized `ThresholdKeys` blob with all-identity verification shares deserializes successfully and yields `group_key = identity`. Any signature of the form `(R = G·x, s = x)` verifies against it, so a party able to get a node/coordinator to load such keys (e.g., via `ThresholdKeys::read` on untrusted or corrupted key material) can forge FROST signatures for that key without any discrete-log knowledge — conceptually identical to Qubit crediting xETH collateral for a deposit that never happened: a degenerate input is treated as a success.

### Likelihood Explanation
Requires attacker-controlled bytes to reach `ThresholdKeys::read` and the resulting keys to be used for signing/verification (key restore, import, or deserialization paths). Within the stated threat model `ThresholdKeys::read` is an exposed sink; no cryptographic hardness assumption needs breaking — only the missing identity check. The `sign.rs` comment at `crypto/frost/src/sign.rs:491-494` acknowledges "deserialize a semantically invalid FrostKeys" as a reachable failure mode but does not prevent it.

### Recommendation
In `ThresholdKeys::new` (and/or `read`), reject identity verification shares and reject a computed `group_key` that `is_identity()`. Alternatively, switch deserialization to an identity-rejecting `read_G` for verification shares, matching the strictness `Curve::read_G` already applies elsewhere.

### Proof of Concept
```rust
// crypto/dkg or frost test context; conceptual
// 1) Craft a serialized ThresholdKeys: valid C::ID header, t = 1, n = 1, i = 1,
//    Interpolation::Constant([1]), secret_share = arbitrary, verification share = identity point.
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(0);                    // Interpolation::Constant
buf.extend(C::F::ONE.to_repr().as_ref());
buf.extend(C::F::random(&mut rng).to_repr().as_ref()); // secret share
buf.extend(<C::G as Group>::identity().to_bytes().as_ref()); // identity verification share

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // accepted

// 2) Forged signature for group_key = identity:
//    SchnorrSignature { R: G*x, s: x } satisfies R + c*A - s*G == 0 since A = 0.
let x = C::F::random(&mut rng);
let sig = SchnorrSignature::<C> { R: C::generator() * x, s: x };
assert!(sig.verify(keys.group_key(), arbitrary_challenge));
```

Note: I could not fully verify whether `Ciphersuite::read_G` in `crypto/ciphersuite/src/lib.rs` rejects identity encodings (the final search returned no content); the finding assumes it accepts canonical identity encodings, which is consistent with `Curve::read_G` existing specifically to add that rejection. If the base `read_G` already rejects identity for every ciphersuite, this analog does not hold.
