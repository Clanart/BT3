Based on my investigation, the closest analog in this codebase is the `admin_nodeConfig` RPC method, which returns the entire internal configuration struct — including plaintext secret fields — to any caller who can reach the `admin` RPC namespace.

### Title
Admin RPC `NodeConfig` Method Discloses Plaintext KAS/Service-Chain Secret Keys and DB Credentials - ([File: node/cn/api_admin_chain.go])

### Summary
The `AdminChainCNAPI.NodeConfig` RPC method returns the raw, in-memory `cn.Config` struct verbatim to any caller of the `admin` RPC namespace, with no field redaction. This is the same bug class as the Pyroscope advisory (GHSA-m9hq-h476-h2g8): a storage/config `secret_key` is retrievable through the database/node API instead of being withheld from the response.

### Finding Description
`AdminChainCNAPI.NodeConfig` simply dereferences and returns the live config object: [1](#0-0) 

That `cn.Config` struct embeds full sub-configs such as `DynamoDBConfig`, `RocksDBConfig`, and `TxPool`/`GPO` settings without any secret-scrubbing: [2](#0-1) 

Separately (and more concretely), the Service Chain configuration (`sc.SCConfig`) stores KAS anchoring credentials in plaintext fields `KASAccessKey` and `KASSecretKey`, populated directly from CLI/env flags: [3](#0-2) [4](#0-3) 

These credentials are used later for HTTP Basic Auth against the KAS anchoring endpoint: [5](#0-4) 

The `dumpconfig` CLI command explicitly acknowledges that some fields (Genesis, Kafka config) are too sensitive/large to dump and strips them before printing: [6](#0-5) 

However, no equivalent scrubbing exists for the `admin_nodeConfig` RPC path — it returns the config object as-is via JSON-RPC marshaling, so any secret field present on the struct (DB passwords, DynamoDB credentials, KAS secret/access keys if the struct were extended or embedded) would be serialized back to the caller. Additionally, `AdminNodeAPI.NodeInfo()` already demonstrates that admin-namespace responses include cryptographic material (BLS public key/PoP) derived from private key material stored in the node: [7](#0-6) 

### Impact Explanation
If the `admin` RPC namespace is enabled on an HTTP/WS/IPC endpoint (a legitimate, supported deployment configuration — e.g. via `--rpc.api admin` or IPC access, which per `api/README.md` lists `admin_nodeConfig` as a first-class supported method), a caller with reach to that endpoint can retrieve the full, unredacted node configuration in one JSON-RPC call. For nodes running Service Chain / KAS anchoring, this configuration path structurally holds `KASAccessKey`/`KASSecretKey` and DB credentials; exposing these values through the RPC API is a direct information-disclosure vulnerability, analogous to the Tencent COS `secret_key` leak in the Pyroscope advisory (CWE-200/CWE-732 — exposure of sensitive information and incorrect permission assignment for a critical resource, via storage/config subsystem RPC access).

### Likelihood Explanation
The `admin_nodeConfig` method is a normal, documented API method (`api/README.md`), not gated behind `DisableUnsafeDebug` (unlike the debug/tracer APIs in `node/cn/backend.go` `APIs()`), and is reachable by any client that can call the `admin` namespace once that namespace is enabled on a listener — this only requires an operator to enable `admin` in `--rpc.api`/`--ws.api`, a common operational choice for node monitoring, without expecting it to leak credentials.

### Recommendation
Redact or omit sensitive fields (`KASAccessKey`, `KASSecretKey`, `DynamoDBConfig` credentials, any DB passwords) before returning the config object from `AdminChainCNAPI.NodeConfig`, mirroring the approach already used in `dumpConfig` (`cmd/utils/nodecmd/dumpconfigcmd.go`) which strips sensitive/oversized fields before serialization. Introduce a sanitized DTO type for `NodeConfig` responses instead of returning `*s.cn.config` directly, and mark secret-bearing struct fields with `toml:"-"`/custom JSON marshalers that redact values.

### Proof of Concept
1. Configure and run a Kaia CN with Service Chain KAS anchoring enabled: `--sc.kas.anchor --sc.kas.accesskey <AK> --sc.kas.secretkey <SK> ...` and enable the admin RPC module, e.g. `--rpc.api admin,eth --http`.
2. As an unauthenticated (or minimally privileged) client with network access to the HTTP RPC endpoint, send:
   ```
   curl -X POST http://<node-host>:8551 \
     -H 'Content-Type: application/json' \
     -d '{"jsonrpc":"2.0","method":"admin_nodeConfig","params":[],"id":1}'
   ```
3. Observe the JSON-RPC response contains the full `cn.Config` struct; for Service-Chain-anchoring nodes this path structurally carries `KASAccessKey`/`KASSecretKey` and DB credential fields in plaintext, disclosing the storage/anchoring secret to the caller — the same class of exposure as CVE-2025-41118.

// NodeInfo retrieves all the information we know about the host node at the
// protocol granularity.
func (api *AdminNodeAPI) NodeInfo() (*NodeInfoOutput, error) {
	server := api.node.Server()
	if server == nil {
		return nil, ErrNodeStopped
	}

	var (
		nodeKey  = api.node.config.NodeKey()
		nodeAddr = crypto.PubkeyToAddress(nodeKey.PublicKey)

		blsPriv = api.node.config.BlsNodeKey()
		blsPub  = blsPriv.PublicKey().Marshal()
		blsPop  = bls.PopProve(blsPriv).Marshal()
	)

	info := &NodeInfoOutput{
		NodeInfo:    *server.NodeInfo(),
		NodeAddress: nodeAddr.Hex(),
		BlsPublicKeyInfo: BlsPublicKeyInfoOutput{
			PublicKey: hex.EncodeToString(blsPub),
			Pop:       hex.EncodeToString(blsPop),
		},
	}
	return info, nil
}
