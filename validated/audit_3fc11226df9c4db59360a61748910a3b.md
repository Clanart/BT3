### Title
Malicious FROST preprocess with identity `E` commitment and negated `D` forces aggregate nonce `R` to the point at infinity, panicking `Hram`/`x` during `sign_share` — (File: `networks/bitcoin/src/crypto.rs`, `crypto/frost/src/nonce.rs`, `crypto/frost/src/algorithm.rs`)

### Summary
A co-signer in a FROST signing session sends a preprocess whose nonce commitments are `(D, E) = (-H, G_identity)`, where `H` is the sum of the other participants' bound nonce commitments. Because `read_G` accepts the canonical identity encoding, and `BindingFactor::bound`/`nonces` computes `D + rho * E` with no identity rejection, the aggregate nonce `R` becomes the point at infinity. `IetfSchnorr::sign_share` then calls `H::hram(&nonce_sums[0][0], ...)`, and the Bitcoin `Hram` calls `x(R)`, which does `.expect("point at infinity")` — a panic reachable purely from attacker-supplied preprocess bytes, a direct analog of a malformed telecommand crashing the memory-management module.

### Finding Description
- `GeneratorCommitments::read` accepts any canonical points, including the identity: `crypto/frost/src/nonce.rs:34-36` calls `C::read_G`, which only rejects non-canonical encodings (`crypto/ciphersuite/src/lib.rs:91-100`); the identity is canonical.
- The bound nonce for participant `l` is `generator.0[0] + (generator.0[1] * rho)` (`crypto/frost/src/nonce.rs:187`). With `E = 0`, this is just `D` regardless of `rho`, letting the attacker fully control their contribution despite not knowing `rho` in advance.
- `BindingFactor::nonces` sums contributions into `D += commitments.nonces[n].generators[g].0[0]` plus a multiexp term (`crypto/frost/src/nonce.rs:194-211`) with no identity check, so `Rs[n][g]` can be identity.
- `Schnorr::sign_share` calls `H::hram(&nonce_sums[0][0], &params.group_key(), msg)` (`crypto/frost/src/algorithm.rs:208`). The Bitcoin `Hram::hram` calls `x(R)` (`networks/bitcoin/src/crypto.rs:59-66`), and `x` is `key.to_encoded_point(true)` then `.expect("point at infinity")` (`networks/bitcoin/src/crypto.rs:13-16`). The doc comments explicitly acknowledge "Panics on invalid input" and "may panic if called with nonces … which are the point at infinity", dismissing it as "a negligible probability" — but with `E = identity` it is deterministic, not probabilistic.

### Impact Explanation
Any participant in a threshold signing set can deterministically crash the local signing process of every other participant at `sign()` time, aborting the signing session (and, for a process hosting many sessions or an automated signer, denying availability of the signing service). The crash occurs inside the victim's `sign_share` call, after the victim has already committed its nonce — the attacker needs no private information.

### Likelihood Explanation
Fully deterministic and cheap: the attacker waits for other preprocesses (or goes first with a precomputed `D` chosen to cancel the sum once others arrive — either way `E = identity` removes `rho` from their term), computes `D` as the negation of the summed other bound commitments, serializes it, and broadcasts it via `read_preprocess`. Reachability path: `AlgorithmSignMachine::read_preprocess` → `Commitments::read` → `sign` → `B.nonces` → `algorithm.sign_share` → `Hram::hram` → `x` panic. Only requirement is membership in the signing set, which the in-scope rules permit since preprocess bytes are attacker-controlled input.

### Recommendation
Reject the identity point in `GeneratorCommitments::read`/`Commitments::read` (add `if point.is_identity().into() { Err(...) }` after `read_G`), and/or check `nonce_sums`/`Rs` for identity before calling `hram` in `sign_share`, returning `FrostError` instead of panicking. Belt-and-suspenders: make `x`/`x_only` return `Result` rather than `expect`.

### Proof of Concept
```rust
// Victim runs AlgorithmMachine::<Secp256k1, bitcoin_schnorr::Schnorr> over a 2-of-2 (or t-of-n) set.
// Attacker (Participant 2) waits for the victim's preprocess (D_h, E_h), then computes:
//   rho-independent bound contribution: choose E = identity, D = -(D_h + rho*E_h - rho*E_h)
// More precisely, since attacker cannot know rho, set:
//   E_att = ProjectivePoint::IDENTITY            // kills the rho*E term
//   D_att = -(bound nonce sum of all other signers, where their terms are D_h + rho*E_h)
// For a 2-of-2 the victim's contribution is fixed once their preprocess is broadcast only if
// rho is known; instead the attacker can simply send E_att = identity and D_att chosen after
// the victim's preprocess is received *and* rho is derivable (transcript is public), since
// rho = H(group_key || msg || commitments) — the attacker computes rho locally, then sets
//   D_att = -(D_h + rho * E_h)
// Serializes (D_att, E_att) as the preprocess and sends it.
// Victim: machine.read_preprocess(bytes) -> Ok(Preprocess)
//         machine.sign(map, msg)
//           -> B.nonces() yields R = identity
//           -> Schnorr::sign_share -> Hram::hram(&R_identity, ...) -> x(R)
//           -> encoded.x().expect("point at infinity")  // PANIC
```
Root cause is confirmed at `networks/bitcoin/src/crypto.rs:13-16` (panic on infinity), `crypto/frost/src/nonce.rs:34-36` and `crypto/frost/src/nonce.rs:180-191` (no identity rejection / bound-sum construction), and `crypto/frost/src/algorithm.rs:208` (unconditional `hram` on `nonce_sums[0][0]`).
