### Title
Unbound "custom message" signature in the `addr` precompile's `associate()` lets anyone replay a victim's off-chain signature to force an unwanted, attacker-timed address association - ([File: precompiles/addr/addr.go])

### Summary
The `authz-casdoor` bug lets an attacker authenticate with credentials obtained from a different authorization source because the plugin fails to bind the credential to the intended purpose/session. The `addr` precompile's `associate()` method has the analogous flaw: it recovers an EVM/Sei address pair from an arbitrary, caller-supplied `customMessage` plus a `v/r/s` signature, with no chain-ID or purpose-binding prefix enforced on-chain. Any ECDSA signature the victim has ever produced for any unrelated off-chain purpose (a `personal_sign` on a totally different dApp, a login flow, etc.) is a valid "association credential" on Sei, and it can be submitted by *any* third party, not just the signer.

### Finding Description
`associate()` takes `v`, `r`, `s`, and `customMessage` directly from calldata and recovers the signer via `helpers.GetAddresses`, hashing `customMessage` with no fixed prefix, domain separator, or chain-ID binding enforced by the precompile itself: [1](#0-0) 

The recovered `evmAddr`/`seiAddr`/`pubkey` are then fed straight into `associateAddresses`, which only checks that the target isn't already associated before calling `AssociateAddresses`: [2](#0-1) 

Because `customMessage` is fully attacker/caller-controlled and unconstrained, the "authentication" performed here is not scoped to a Sei-specific association intent. Any signature the victim produced elsewhere for a wholly different context (which is routinely exposed — e.g. `personal_sign` challenges from other dApps, exchanges, or airdrop-claim flows) satisfies the check. This mirrors the authz-casdoor root cause: a credential minted for one authentication context is accepted as proof of authorization in a different context, because the check never verifies the credential was actually issued *for this specific action*.

The consequence is not merely benign "someone associated my address for me" — the code's own comments elsewhere in the ante/EIP-7702 path describe why forced/unexpected association is dangerous: it migrates state created under the EVM-address's *direct-cast* Sei identity to the newly-associated, pubkey-derived Sei identity, and can "orphan any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)": [3](#0-2) [4](#0-3) 

That same `AssociateAddresses` migration path is invoked directly and unconditionally by `addr.associate()`, so any attacker who can replay a victim's stray signature can trigger this migration at a time of their choosing — without the victim ever intending to associate, and potentially while the victim holds direct-cast balances or delegations.

### Impact Explanation
An attacker who obtains any signature a victim produced off-chain for an unrelated purpose can:
1. Force an unwanted, attacker-timed address association for the victim on Sei via a single public precompile call requiring no special privilege.
2. Trigger the direct-cast → pubkey-derived state migration described in the codebase's own risk analysis, which can orphan staking/distribution records tied to the direct-cast identity and — per the code's explicit comment — halt the chain via the distribution validator-removal hook.

This satisfies the "validator halt" / "permanent freezing" impact bar: a third party with no relationship to the victim's Sei activity can unilaterally force a state transition the codebase's own comments identify as chain-halting when it collides with staking/distribution state.

### Likelihood Explanation
Obtaining a usable `v/r/s` + message pair from a victim is low-effort: any `personal_sign`/EIP-191 signature a user has ever produced anywhere (many wallets and dApps request such signatures routinely) is directly reusable here since `customMessage` is not scoped to Sei or to an "I want to associate" intent, and there's no requirement that the message be secret. The precompile call itself is public and unprivileged (any EOA/contract can submit it), and `associateAddresses` only rejects already-associated targets, not un-consented ones.

### Recommendation
Bind the signed message to a fixed, Sei-specific, chain-ID-scoped domain string (or require the message to equal a canonical constant such as `"Associate Sei Address: <chainID>:<nonce>"`) instead of accepting an arbitrary caller-supplied `customMessage`. Additionally consider requiring the association to be self-initiated (caller == recovered signer) rather than allowing any third party to submit someone else's signature on their behalf.

### Proof of Concept
1. Victim signs any off-chain EIP-191 `personal_sign` message on an unrelated site/dApp (e.g., a login challenge) with their EVM key; the `v/r/s` and message text become observable (many dApps display or log these).
2. Attacker extracts `v`, `r`, `s`, and the original message text.
3. Attacker calls `addr.associate(v, r, s, message)` on Sei (a public, unprivileged precompile call) at `precompiles/addr/addr.go:160-203`.
4. `helpers.GetAddresses` recovers the victim's `evmAddr`/`seiAddr`/`pubkey` from the unrelated signature and `associateAddresses` (lines 239-255) immediately performs the association and any accompanying direct-cast → pubkey-derived state migration — all without the victim submitting any transaction or intending to associate on Sei.

```go
func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
```
