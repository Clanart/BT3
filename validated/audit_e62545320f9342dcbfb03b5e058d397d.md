### Title
Untrusted `ReceivedOutput` fields can inject arbitrary prevouts into a threshold-signed Bitcoin transaction - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` without authenticating that the supplied `TxOut` is the actual output referenced by the supplied `OutPoint`. `SignableTransaction::new` then treats these attacker-controlled fields as authoritative wallet inputs, and `TransactionSignMachine::sign` commits them into every Taproot signature through `Prevouts::All`.

### Finding Description
`ReceivedOutput::read` deserializes three independent claims: the scalar offset, the full previous output, and the previous-output reference. The parser only checks that the encodings are structurally valid; it does not bind `output` to `outpoint` or prove that either was produced by `Scanner::scan_transaction`. [1](#0-0) 

The only later consistency check is that `keys + offset` maps to `prevouts[i].script_pubkey`. It does not check that `outpoint` exists, that its value is `prevouts[i].value`, or that the output is unspent. [2](#0-1) 

When signing, all supplied `prevouts` are committed to the Taproot sighash. Consequently, arbitrary bytes accepted through `ReceivedOutput::read` become signing parameters, not merely untrusted serialization data. [3](#0-2) 

### Impact Explanation
If an application accepts a serialized `ReceivedOutput` from an untrusted party and passes it to `SignableTransaction::new`/`multisig`, that party can cause the threshold group to sign a transaction whose declared prevout data was not observed by the wallet scanner.

Where the attacker supplies the real `OutPoint` and real matching script for a wallet-owned UTXO, but substitutes a payment destination chosen by the attacker, the resulting signatures are valid and transfer the wallet funds. Where the pair is inconsistent with chain state, the signed transaction is invalid. In either case, the threshold group signs a sighash over injected prevout metadata that the wallet never authenticated as a received output.

### Likelihood Explanation
The attacker does not need cryptographic capabilities or control of a validator. They need only influence serialized `ReceivedOutput` input and the transaction construction request. Public blockchain data provides the needed wallet script and `OutPoint`; the offset is determined by the public scanner registration.

The issue is conditional on an integration boundary treating `ReceivedOutput` as untrusted input rather than as scanner-authenticated state. The vulnerable library API does not encode or enforce that trust requirement during deserialization.

### Recommendation
Do not expose raw `ReceivedOutput` deserialization as a source of spend authority. Bind each `ReceivedOutput` to authenticated scanner state, or require a trusted outpoint-to-output proof/lookup before signing.

At minimum:

- Make `ReceivedOutput::read` crate-private or clearly separate untrusted wire data from authenticated wallet outputs.
- Re-fetch each `OutPoint` from the Bitcoin RPC and compare its value and `script_pubkey` with the supplied `TxOut`.
- Reject zero-valued or nonexistent prevouts.
- Ensure `SignableTransaction` construction receives only outputs produced by `Scanner::scan_transaction`/`scan_block` or another trusted UTXO database.
- Add a regression test where a serialized `ReceivedOutput` pairs a real wallet script with an unrelated or fabricated `OutPoint` and assert it cannot reach `multisig`/signing.

### Proof of Concept
Conceptually, let `wallet_output` be a real unspent output paying to the threshold wallet, and let `wallet_outpoint` be its transaction position. An attacker supplies:

```text
ReceivedOutput {
  offset: wallet_offset,
  output: TxOut {
    value: wallet_output.value,
    script_pubkey: wallet_output.script_pubkey,
  },
  outpoint: wallet_outpoint,
}
```

along with a payment requesting the wallet value minus fee to an attacker-controlled `script_pubkey`. The offset/script check in `SignableTransaction::multisig` passes because it only compares the declared script to `p2tr_script_buf(keys + offset)`. `TransactionSignMachine::sign` then calls `taproot_key_spend_signature_hash` with `Prevouts::All(&self.tx.prevouts)`, producing threshold signature shares for the attacker-requested spend.
