## Title
Discard/stage-selection patches are formatted from a stale in-memory diff and applied by line offset (`--unidiff-zero`), letting content changed after diff-load (e.g. by an automatically-run Git hook) be silently mis-applied to the tracked file - (File: `app/src/lib/git/apply.ts`)

### Summary
This is the closest structural analog to M-8. The Sherlock bug is that `Auditor::checkLiquidation()` computes the amount to seize from a value (collateral) taken at a point in time, and a subsequent state-changing step (floating-assets accrual in `noTransferRepayAtMaturity`) is not reflected before the seize is executed — an action is carried out using a stale precomputed value, corrupting the intended result. In GitHub Desktop, the "Discard changes"/partial-stage flow has the same shape: the UI computes an `ITextDiff` for a file once (`getWorkingDirectoryDiff`), the user makes a line/hunk selection against that diff, and — potentially much later, after user interaction and any hooks/background processes have run — that same, now-possibly-stale `diff` object is turned into a patch (`formatPatch` / `formatPatchToDiscardChanges`) and applied to the file or index with `git apply --unidiff-zero`, without re-reading or re-diffing the file immediately before applying.

### Finding Description
`discardChangesFromSelection()` and `applyPatchToIndex()` in `app/src/lib/git/apply.ts` both take a caller-supplied `diff`/selection and turn it directly into a unified-diff patch which is fed to `git apply`: [1](#0-0) 

`applyPatchToIndex` similarly re-fetches the diff for staging the index, but `discardChangesFromSelection` accepts the diff as a parameter from the caller rather than recomputing it at apply time: [2](#0-1) 

The `diff` parameter that reaches `discardChangesFromSelection` originates from the UI layer (context-menu / diff viewer state) and is threaded unchanged through `Dispatcher.discardChangesFromSelection` down into the git layer: [3](#0-2) 

The patches are built with `git apply --unidiff-zero --whitespace=nowarn -`, i.e. with zero-context unified hunks that git applies mostly by explicit line numbers rather than by robust context matching: [4](#0-3) 

Both `formatPatch` and `formatPatchToDiscardChanges` build the hunk purely from `hunk.header.oldStartLine`/`newStartLine` recorded in the diff object at the time it was generated, with no verification that these offsets still correspond to the file's current on-disk content: [5](#0-4) [6](#0-5) 

There is one place in `app-store.ts` that explicitly acknowledges diffs can go stale between load and use, but that guard only re-validates *selection line indices*, not the underlying content used to build the patch that is ultimately applied: [7](#0-6) 

Meanwhile, GitHub Desktop's own Git Hooks Subsystem routes hook execution (`post-checkout`, `post-merge`, etc.) through a proxy that runs scripts sourced from the repository itself, which can freely rewrite tracked files in the working directory at any point after a fetch/pull/checkout — i.e. after Desktop has already computed and cached the diff shown to the user, but before the user clicks "Discard"/stage on a partial selection.

**Broken invariant:** the patch applied to the working tree/index is derived from a diff snapshot that is not guaranteed to match the file's current content at apply time, and `--unidiff-zero` makes the apply operation trust stale line offsets rather than fail safely on mismatch.

**Why existing guards don't stop it:** the only staleness guard in the codebase (`app-store.ts:3478-3497`) filters *selectable lines* inside the cached diff object itself when a new diff is loaded through the normal refresh path — it does nothing to protect the `discardChangesFromSelection`/`applyPatchToIndex` code path, which can be invoked with a diff object that was captured before an out-of-band content change (e.g. a repo-provided hook) and is never re-diffed against disk before `git apply` runs.

### Impact Explanation
If a tracked file's content is altered between the moment Desktop's diff/selection UI captures the `ITextDiff` and the moment the user confirms a partial "Discard changes" or partial stage, the generated zero-context patch can be applied against line offsets that no longer correspond to the intended hunks. Because the patch is unidiff-zero (line-number driven, not context-fuzzy), a mismatch may not cleanly fail — it can result in silent corruption of the file: content the user never selected can be deleted/reverted, or content they intended to discard can remain, all without an error surfaced to the user. This corrupts the state of what gets committed/pushed next, mirroring the "silent corruption of what the user commits" impact class.

### Likelihood Explanation
Requires no privileged/local access beyond normal Desktop usage of a cloned/fetched repository: an attacker who controls the repository's hook scripts (post-checkout/post-merge, executed automatically by Desktop's Git Hooks Subsystem) can time a rewrite of a tracked file to land inside the window between diff-load and user-triggered discard/stage — a window that is inherently non-trivial in an interactive GUI application where users read diffs before acting. This does not require social engineering beyond the normal, expected act of cloning/pulling a repository and using the built-in changes UI.

### Recommendation
Before formatting and applying any patch in `applyPatchToIndex` / `discardChangesFromSelection`, re-fetch a fresh diff (or at minimum the current file hash/mtime) immediately prior to constructing the patch, and abort/re-prompt the user if the file has changed since the diff shown to them was generated — analogous to how `Auditor::checkLiquidation()` should account for the floating-assets increase that occurs later in the same call, rather than trusting a value computed earlier in the flow.

### Proof of Concept
Not independently executable from the indexed code alone (would require running the actual Electron app with a crafted repository containing a `post-checkout`/`post-merge` hook that rewrites a tracked file during the interactive window between opening the file's diff and confirming a partial discard). The code-level evidence establishing the vulnerable pattern is cited above (`app/src/lib/git/apply.ts:102-119`, `app/src/lib/patch-formatter.ts:129-145` and `251-270`, and the unit test suite in `app/test/unit/git/apply-test.ts` which only exercises `discardChangesFromSelection` with diffs freshly computed immediately before use, never validating behavior when the on-disk file diverges from the passed-in diff).
