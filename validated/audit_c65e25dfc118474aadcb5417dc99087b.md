### Title
Unauthenticated On-Chain SSRF via DataLayer Mirror URL Injection — ([File: chia/data_layer/data_layer.py])

### Summary
Any party who can submit a spend bundle can create a "mirror" coin that associates arbitrary attacker-chosen URLs with *any* DataLayer store id (launcher id), without owning that store. DataLayer services that subscribe to that store id pull those URLs and later issue outbound HTTP `GET` requests to them without any validation of scheme, host, or destination (no private-network/loopback/link-local blocklist). This is the same bug class as the Flowise APIChain SSRF: attacker-controlled, unvalidated data is trusted to construct an outbound request URL that the server then fetches.

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a standard XCH coin spend to the mirror puzzle hash and stores the target `launcher_id` plus caller-supplied `urls` purely as coin memos, with no check that the sender owns or controls that `launcher_id`/store: [1](#0-0) 

This is exposed directly through the wallet RPC `dl_new_mirror`, which forwards `request.urls` unchanged into `create_new_mirror`: [2](#0-1) 

and through the DataLayer RPC `add_mirror`, which likewise performs no ownership or URL validation before publishing: [3](#0-2) [4](#0-3) 

On the consuming side, any DataLayer service that is subscribed to (or owns/tracks) that store id reads the mirror URLs from the wallet and adds them as subscription servers without filtering: [5](#0-4) 

Those server URLs are later used verbatim to construct an outbound HTTP GET request in `http_download()`, with no scheme allowlist and no check against internal/loopback/link-local/metadata-service addresses: [6](#0-5) 

This call is reached from `fetch_and_validate()`, which is driven purely by wallet-reported singleton/mirror state — i.e., attacker-controlled on-chain data — during the periodic sync loop: [7](#0-6) 

The project's own internal documentation acknowledges mirror/plugin URLs are untrusted inputs, but the stated mitigation is only that *downloaded file content* must be verified against the wallet-advertised root — it does not address the SSRF vector of the request itself being sent to an attacker-chosen destination: [8](#0-7) 

This mirrors the Flowise flaw precisely: in Flowise, prompt-injected "API documentation" (attacker-controlled text) was trusted to produce a URL that the server then fetched with no destination validation; here, an attacker-controlled coin memo (mirror URL, requiring no ownership of the target store) is trusted to produce a URL that the DataLayer service then fetches with no destination validation.

### Impact Explanation
Any user capable of submitting a spend bundle (a `create_new_mirror` transaction can use `amount=uint64(0)`, so cost is only the transaction fee) can force any DataLayer node subscribed to a given store — including community/public store mirrors used by wallet and Data Layer clients — to issue HTTP requests to attacker-chosen destinations: internal services, cloud metadata endpoints, loopback services, or other hosts reachable only from the DataLayer node's network. This enables internal network reconnaissance, potential credential exfiltration via metadata endpoints, and abuse of the node as an SSRF proxy — impacting confidentiality (`C:H`) of the operator's environment, matching the referenced advisory's CVSS profile. This is directly reachable by an unprivileged Data Layer client/wallet user with no special node/peer/farmer privileges, satisfying the scope's "Data Layer client" reachability requirement.

### Likelihood Explanation
High. No coordination with a store owner is required — mirror creation is simply a standard, self-fundable coin spend with memo data; the receiving DataLayer service performs periodic, automatic syncing (`periodically_manage_data()`) that will pick up and dereference newly announced mirror URLs for tracked/subscribed stores without operator interaction.

### Recommendation
- Enforce a strict allowlist of URL schemes (e.g., `http`/`https` only, and restrict `s3://` handling to the existing plugin path).
- Validate resolved hostnames/IPs against RFC1918/loopback/link-local/multicast ranges and known cloud metadata addresses (e.g., `169.254.169.254`) before making any outbound request in `http_download()` and `get_downloader`/plugin dispatch paths.
- Consider requiring/recording proof that a mirror-publishing coin was created by (or authorized by) the actual DataLayer singleton owner before treating its URLs as trusted sync targets, or at minimum surface mirror provenance to operators so unowned/untrusted mirrors can be excluded by policy.
- Apply the same destination validation to plugin `downloader.url`/`uploader.url` POST targets in `chia/data_layer/data_layer.py` (`get_uploaders`, `check_plugins`) and `download_data.py`.

### Proof of Concept
1. Attacker (any wallet with minimal XCH for fees) calls `dl_new_mirror` (or DataLayer RPC `add_mirror`) targeting a `launcher_id` of a store they do not own, with `urls=["http://169.254.169.254/latest/meta-data/", "http://internal-service.local:8080/admin"]` and `amount=0`. [2](#0-1) 
2. The mirror coin is confirmed on-chain; any DataLayer service subscribed to that `launcher_id` reads it via `update_subscriptions_from_wallet()`. [5](#0-4) 
3. During the next `periodically_manage_data()` cycle, `fetch_and_validate()` selects the malicious server URL and `http_download()` issues a real HTTP GET to the attacker-controlled endpoint from the victim DataLayer node. [6](#0-5)

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
