## Title
Checkbox click on one side of a Modified diff row silently fails to (de)select its actual line, corrupting what gets committed - ([File: app/src/ui/diff/side-by-side-diff.tsx])

### Summary
`onLineNumberCheckedChanged` in `side-by-side-diff.tsx` computes `lineBefore` and `lineAfter` by calling `getDiffLineNumber(row, column)` twice with the **same** `column` argument instead of resolving the "before" line with `DiffColumn.Before` and the "after" line with `DiffColumn.After`. [1](#0-0) 

### Finding Description
For a `Modified` diff row (a row that pairs a deleted line and an added line side by side), the row carries two distinct diff line numbers: `row.beforeData.diffLineNumber` and `row.afterData.diffLineNumber`, resolved via `getDiffRowLineNumber` using the `column` parameter (`DiffColumn.Before` or `DiffColumn.After`). [2](#0-1) 

`onLineNumberCheckedChanged` is invoked with the specific `column` the user clicked on, but then does:
```js
const lineBefore = this.getDiffLineNumber(row, column)
const lineAfter = this.getDiffLineNumber(row, column)
```
Both calls pass the *same* `column`, so `lineBefore` and `lineAfter` resolve to the identical diff line number (whichever side was clicked). The code then calls `selection.withLineSelection(lineBefore, isSelected)` and `selection.withLineSelection(lineAfter, isSelected)` — applying the same toggle to the same line number twice, while the opposite line of the pair (the one belonging to the other `DiffColumn`) never has its selection state updated at all. [3](#0-2) 

This is structurally the same bug class as the report: `old_bias` should have been used in place of `old_sum_bias` in one branch, but instead the same (wrong) variable was reused for two computations that were supposed to diverge. Here, `DiffColumn.Before`/`DiffColumn.After` should diverge for the two lookups but instead the same `column` value is reused for both.

### Impact Explanation
When a user views a modified hunk in side-by-side mode and unchecks only the "before" (deleted) or only the "after" (added) line checkbox to partially stage/commit a change, the deleted counterpart line's selection is never updated. The generated commit/patch (built later via `patch-formatter.ts`'s `file.selection.isSelected(absoluteIndex)` checks) will silently include or exclude the wrong line relative to what the UI displayed as checked/unchecked. [4](#0-3) 
This corrupts what the user believes they are committing — the checkbox state shown to the user and the actual staged/committed content diverge, which is a silent-corruption-of-commit-content class issue matching the "Valid Impact" criteria (silent corruption of what the user commits or pushes).

### Likelihood Explanation
This triggers on ordinary, expected user interaction — unchecking/checking an individual line checkbox on a "Modified" row in the side-by-side diff view, which is a core, frequently used Desktop feature (partial-line staging). No attacker-controlled repo content is required to trigger the bug itself, but a malicious repository could be crafted to make diffs that primarily present as Modified rows for sensitive lines (e.g., pairing a benign added line next to a malicious deleted line) to increase the odds that a reviewer excludes the wrong line while believing they excluded the intended one.

### Recommendation
Fix the lookups to use the correct, distinct columns:
```js
const lineBefore = this.getDiffLineNumber(row, DiffColumn.Before)
const lineAfter = this.getDiffLineNumber(row, DiffColumn.After)
```
Add a regression test for `onLineNumberCheckedChanged` on a `Modified` row verifying that toggling the "before" checkbox only changes `beforeData.diffLineNumber`'s selection and leaves `afterData.diffLineNumber`'s selection untouched (and vice versa).

### Proof of Concept
1. Modify a file such that a hunk contains one deleted line immediately followed by one added line (rendered as a single `Modified` row in side-by-side view via `getModifiedRows`). [5](#0-4) 
2. In the Changes view, uncheck only the "before" (deleted-line) checkbox for that row.
3. Because `onLineNumberCheckedChanged` resolves both `lineBefore` and `lineAfter` using the same `column` (here, `DiffColumn.Before`), the deleted line's diff-line-number toggle is applied redundantly, and the added line's diff-line-number is never toggled to match the intended state.
4. Commit the change — the resulting patch (via `formatPatch`) reflects the added line's original selection instead of the user's explicit action on it, producing a commit that differs from what the checkbox UI displayed.

**Uncertainty note**: I was unable to fully trace whether `withLineSelection` treats duplicate calls with the same line number idempotently or whether some other guard in `getSelection()`/`DiffSelection` model compensates for this before it reaches `patch-formatter.ts`; I could not load the full `diff-selection.ts` implementation in the remaining budget. If such a compensating check exists, the practical severity could be lower than described. A Devin session with full file access would be needed to confirm the exact end-to-end effect on `DiffSelection.isSelected()`.

  private getDiffRowLineNumber(row: SimplifiedDiffRow, column: DiffColumn) {
    if (row.type === DiffRowType.Added || row.type === DiffRowType.Deleted) {
      return row.data.diffLineNumber
    }

    if (row.type === DiffRowType.Modified) {
      return column === DiffColumn.After
        ? row.afterData.diffLineNumber
        : row.beforeData.diffLineNumber
    }

    return null
  }
