### Title
`updatePool` in MasterMagpie uses insufficient `accMGPPerShare` precision (1e12), permanently losing MGP yield on frequent permissionless calls - (File: `rewards/MasterMagpie.sol`)

### Summary
`MasterMagpie.updatePool()` accrues rewards into `pool.accMGPPerShare` using a fixed precision multiplier of `1e12`, the exact same class of bug flagged in the referenced report for `secRewardsPerShare` (which used `1e18` against a similarly-scaled supply and was recommended to be raised to `1e27`). Because `updatePool` is a `public`, permissionless function (also callable via `deposit`/`withdraw`/`massUpdatePools` by any wallet), any user can trigger frequent, small-`multiplier` updates that cause the per-call incremental reward to round down to zero, while `lastRewardTimestamp` is still advanced — permanently erasing that slice of yield for all stakers of the pool.

### Finding Description
The pool's accumulator is updated as:

```solidity
uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;

pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
pool.lastRewardTimestamp = block.timestamp;
``` [1](#0-0) 

This mirrors the reported pattern `secRewardsPerShare += (blockDelta * 1e18) / marketSupply`: whenever `mgpReward * 1e12 < lpSupply`, the division truncates to `0`, yet `pool.lastRewardTimestamp` is unconditionally advanced to `block.timestamp`. Since the next call's `multiplier` is computed from the new `lastRewardTimestamp`, the reward accrued during that interval is not carried forward — it is permanently lost, not merely delayed.

`updatePool` is `public` with no access restriction beyond `whenNotPaused`:

```solidity
function updatePool(address _stakingToken) public whenNotPaused {
``` [2](#0-1) 

and it is reachable from unprivileged, permissionless entry points, including the standalone `massUpdatePools()` and via `deposit`/`withdraw` flows:

```solidity
function massUpdatePools() public whenNotPaused {
    for (uint256 pid = 0; pid < registeredToken.length; ++pid) {
        updatePool(registeredToken[pid]);
    }
}
``` [3](#0-2) 

Any ordinary wallet can call `updatePool`/`massUpdatePools` (or simply `deposit`/`withdraw` a dust amount) repeatedly, in every block, shrinking `multiplier` to the minimal block-time gap. With a small enough `multiplier`, or a pool with a small `allocPoint` share, or a large `lpSupply` (staking receipt tokens are typically 18-decimal, and total staked value across a pool can be large), `mgpReward * 1e12` easily falls below `lpSupply`, rounding the accrual to `0` for that call while still consuming the elapsed time window forever.

The identical low-precision pattern (`1e12`) also appears in the mock `MasterWombatMockRewardPersec.sol` `updatePool`, confirming this is a systemic accumulator design used across the reward-distribution codebase, not an isolated typo:

```solidity
pool.accRewardPerShare = pool.accRewardPerShare + ((mgpReward * 1e12) / lpSupply);
``` [4](#0-3) 

### Impact Explanation
Because `updatePool` is callable by any wallet and permanently advances `lastRewardTimestamp` regardless of whether the division underflows to zero, an attacker (or even ordinary high-frequency interaction, e.g., bots calling `massUpdatePools` every block) can cause MGP emissions for a pool to be silently and irrecoverably lost. This is a direct, permanent loss of unclaimed yield owed to all stakers of that pool — MGP that was budgeted/minted for emission per `mgpPerSec` never reaches any user's `accMGPPerShare`/`rewardDebt` accounting and cannot be recovered, since the time window it corresponds to has already been consumed by `lastRewardTimestamp` update.

### Likelihood Explanation
Likelihood is high because:
- `updatePool`/`massUpdatePools` require no privilege and no fee beyond gas.
- Any wallet can force minimal-`multiplier` calls back-to-back (e.g., calling every block).
- Pools with low `allocPoint` relative to `totalAllocPoint`, or with a large `lpSupply` denominator (18-decimal staking tokens with sizable TVL), make the rounding-to-zero condition (`mgpReward * 1e12 < lpSupply`) easy to trigger without needing extreme values — this is the same numeric regime the original report demonstrated (`marketSupply = 10e18`, `blockDelta = 1` → `0`).

### Recommendation
Increase the accumulator precision (e.g., to `1e27` or higher, matching or exceeding the largest expected `lpSupply` scale), and/or track and carry forward any residual/truncated reward instead of discarding it when the division rounds down, so no time-weighted MGP emission is permanently lost due to rounding.

### Proof of Concept
1. Assume a registered pool with `allocPoint` small relative to `totalAllocPoint`, and `lpSupply` (staking token balance, 18 decimals) sufficiently large that `mgpReward * 1e12 < lpSupply` for a 1–2 second `multiplier`.
2. Attacker (any wallet) repeatedly calls `MasterMagpie.massUpdatePools()` (or `updatePool(stakingToken)`) every block.
3. Each call computes `mgpReward = (multiplier * mgpPerSec * allocPoint) / totalAllocPoint`, then `mgpReward * 1e12 / lpSupply` truncates to `0` due to insufficient precision, per [1](#0-0) .
4. `pool.lastRewardTimestamp` is set to `block.timestamp` regardless, so the elapsed interval's reward is never recovered in a subsequent call.
5. Over many blocks, MGP that should have accrued to `accMGPPerShare` for that pool's stakers is permanently forfeited, reducing the yield actually claimable by legitimate stakers.
