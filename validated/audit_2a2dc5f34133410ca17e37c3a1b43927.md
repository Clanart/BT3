### Title
Legacy `pattern`-to-`Condition` field inference silently defeats block rules for non-`bash`/`file` events - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`Rule.from_dict` converts a legacy `pattern:` frontmatter field into a `Condition` by inferring the `field` attribute purely from the `event` value: `command` for `event == 'bash'`, `new_text` for `event == 'file'`, and `content` for every other event value (including `all`, or any other string a rule author writes) [1](#0-0) .

`RuleEngine._extract_field` only recognizes `content` for `tool_name in ['Write', 'Edit']` (mapping it to `tool_input['content']` or `tool_input['new_string']`); for `tool_name == 'Bash'` it only recognizes `command`, and for `MultiEdit` it only recognizes `file_path`/`new_text`/`content` via the edits list [2](#0-1) . When the inferred field is `content` but the invoked tool is `Bash`, `_extract_field` returns `None`, and `_check_condition` immediately returns `False` for a `None` field value [3](#0-2) , so `_rule_matches` always returns `False` regardless of the actual command content [4](#0-3) .

Consequence: a rule file (frontmatter) that looks like a legitimate, broadly-scoped block rule — e.g. `event: all` with `pattern: "rm -rf"` and `action: block` — is silently inert against `Bash` tool invocations, because the legacy inference path chooses `field=content` instead of `field=command`. The exact same intended pattern expressed with the "new style" explicit `conditions:` list (`field: command`) works correctly, exposing a real behavioral differential between legacy and explicit condition parsing driven only by the `event` string, with no warning or error surfaced to the rule author (`load_rule_file` succeeds and returns a `Rule` object normally) [5](#0-4) .

An attacker who can influence a `.claude/hookify.*.local.md` rule file — either by contributing it in a shared/cloned repository (a "repo-shipped rule file", e.g. via PR) or by causing `/hookify` generation to emit a legacy-style `pattern` rule with a non-canonical `event` value — can plant a rule that a maintainer believes blocks dangerous Bash commands (because it has `action: block` and a plausible-looking pattern) but that never actually fires, since no validation checks that the inferred `Condition.field` is actually extractable for the tool the rule targets.

### Impact Explanation
The impact is a false sense of local enforcement: a block rule intended to stop dangerous Bash commands (e.g., `rm -rf`, `curl | sh`, credential exfiltration commands) silently never matches, so the underlying dangerous command executes unblocked while the maintainer believes hookify is protecting the workspace. This is scoped strictly to the hookify plugin's own advisory/blocking hook mechanism (a locally-installed automation feature) rather than Claude Code's core built-in permission/approval system, so it should be understood as "Unauthorized local command execution against hookify's own deny controls," not a bypass of Claude Code's native approval prompts.

### Likelihood Explanation
Requires: (1) hookify plugin installed and relied upon for enforcement, and (2) a legacy-style `pattern` rule file with an `event` value other than exactly `bash` or `file` (a very easy, unremarkable-looking authoring mistake, or an intentional attacker-crafted rule submitted via PR/repo content). No special privileges are needed beyond normal repository contribution, and the failure is completely silent (`load_rule_file` returns a valid `Rule`, and `evaluate_rules` simply returns `{}` for the Bash command in question).

### Recommendation
- In `Rule.from_dict`, validate the inferred `Condition.field` against the rule's `event`/`tool_matcher`, or better, make the legacy-pattern-to-field mapping consistent with `_extract_field`'s actual field/tool coverage (e.g., default to `command` when the rule's `tool_matcher` includes `Bash`, `new_text`/`content` for `Write`/`Edit`/`MultiEdit`, etc., rather than keying only off the raw `event` string).
- Add a startup/self-check in `load_rule_file` (or a `hookify` lint step) that verifies each rule's conditions produce a non-`None` `_extract_field` result for at least one plausible sample input for the declared event/tool_matcher, and warn loudly if a `block` rule can never match.
- Emit an explicit warning when `event` is not one of the recognized values (`bash`, `file`, `stop`, `all`) so silent misclassification is visible to the rule author.

### Proof of Concept
Unit test added to `plugins/hookify/core/config_loader.py`/`rule_engine.py` test suite:
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter = {
    "name": "block-rm-rf",
    "enabled": True,
    "event": "all",          # non-canonical event, legacy pattern path
    "pattern": "rm -rf",
    "action": "block",
}
rule = Rule.from_dict(frontmatter, "Dangerous rm command blocked!")

engine = RuleEngine()
result = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"},
})

# Expected (intended) behavior: result contains permissionDecision "deny"
# Actual behavior: result == {} -- the block rule never fires
assert result == {}, "Block rule silently fails to match dangerous Bash command due to field inference bug"
```
Compare against the equivalent explicit-conditions rule (`conditions: [{field: command, operator: regex_match, pattern: "rm -rf"}]`), which correctly returns a `deny` decision — demonstrating the differential between legacy and explicit condition parsing.
