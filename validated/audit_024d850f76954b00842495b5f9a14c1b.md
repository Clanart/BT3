### Title
`CitreaClient` Ignores Configured `bridge_contract_address` and Uses Hardcoded Compile-Time Constant — (`core/src/citrea.rs`)

### Summary

`CitreaClient::new()` always instantiates the bridge contract and queries storage proofs using the hardcoded compile-time constant `BRIDGE_CONTRACT_ADDRESS`, completely ignoring the operator-configurable `BridgeConfig.bridge_contract_address` field. If the Citrea bridge contract is redeployed at a new address, all deposit collection, withdrawal collection, storage-proof generation, and N-of-N key checks will silently target the stale address, permanently halting bridge liveness.

### Finding Description

`core/src/citrea.rs` declares a compile-time constant:

```rust
pub const BRIDGE_CONTRACT_ADDRESS: &str = "0x3100000000000000000000000000000000000002";
``` [1](#0-0) 

This constant is used in two places inside `CitreaClient`'s implementation:

1. **Contract instantiation** in `CitreaClient::new()`:

```rust
let contract = BRIDGE_CONTRACT::new(
    BRIDGE_CONTRACT_ADDRESS
        .parse()
        .expect("Correct contract address"),
    provider,
);
``` [2](#0-1) 

2. **EIP-1186 storage proof query** in `get_storage_proof()`:

```rust
let response: serde_json::Value = self
    .client
    .get_proof(
        BRIDGE_CONTRACT_ADDRESS,
        ...
    )
``` [3](#0-2) 

Meanwhile, `BridgeConfig` exposes a fully configurable `bridge_contract_address: String` field: [4](#0-3) 

This field is parsed from the environment variable `BRIDGE_CONTRACT_ADDRESS` and from TOML config files: [5](#0-4) 

However, the `CitreaClientT::new()` trait signature does **not** accept a contract address parameter:

```rust
async fn new(
    citrea_rpc_url: String,
    light_client_prover_url: String,
    chain_id: u32,
    secret_key: Option<PrivateKeySigner>,
    timeout: Option<Duration>,
) -> Result<Self, BridgeError>;
``` [6](#0-5) 

Both `Verifier::new()` and `Operator::new()` call `C::new(...)` passing only the five parameters above — `config.bridge_contract_address` is never forwarded: [7](#0-6) [8](#0-7) 

A grep over the entire Rust source confirms `bridge_contract_address` is referenced only in `config/env.rs` (parsing) and `config/mod.rs` (field definition, default, and equality check) — never in `citrea.rs` where the contract is actually used.

### Impact Explanation

Every bridge-critical operation that touches the Citrea L2 state goes through `CitreaClient`:

| Method | Bridge Effect |
|---|---|
| `collect_deposit_move_txids` | Reads deposit txids → drives deposit finalization |
| `collect_withdrawal_utxos` | Reads withdrawal UTXOs → drives operator payout |
| `get_storage_proof` | Generates EIP-1186 proof for assert tx → drives challenge/disprove |
| `check_nofn_correctness` | Validates N-of-N key against contract → guards deposit signing |
| `get_replacement_deposit_move_txids` | Reads replacement deposit events |

If the bridge contract is redeployed at a new address (e.g., for an upgrade or security patch), all of the above will silently query the old, stale address. No deposits or withdrawals will be detected, storage proofs will be generated against the wrong contract state, and the bridge will halt completely. Operators who set the correct new address in their config will receive no benefit — the configured value is silently discarded.

Additionally, the existence of the `bridge_contract_address` config field gives operators false confidence that they can reconfigure the contract address without a code change.

### Likelihood Explanation

The Citrea bridge contract address is currently fixed at `0x3100000000000000000000000000000000000002`. A redeployment is a low-frequency but non-zero event (upgrades, security incidents, chain migrations). The bug is latent and will trigger silently — no error is raised when the configured address differs from the hardcoded constant.

### Recommendation

1. Add `bridge_contract_address: String` as a parameter to `CitreaClientT::new()`.
2. In `CitreaClient::new()`, parse and use the passed address instead of the `BRIDGE_CONTRACT_ADDRESS` constant.
3. In `get_storage_proof()`, use the address stored on `self.contract` (via `self.contract.address()`) rather than the module-level constant.
4. Pass `config.bridge_contract_address` from both `Verifier::new()` and `Operator::new()` call sites.

### Proof of Concept

1. Deploy a new bridge contract at address `0xDEAD...`.
2. Set `BRIDGE_CONTRACT_ADDRESS=DEAD...` in the operator/verifier config.
3. Start Clementine — `CitreaClient::new()` ignores the env var and binds to `0x3100000000000000000000000000000000000002`.
4. All calls to `collect_deposit_move_txids`, `collect_withdrawal_utxos`, and `get_storage_proof` target the old address.
5. No new deposits or withdrawals are ever detected; the bridge is permanently halted from the perspective of the running node. [1](#0-0) [2](#0-1) [4](#0-3)
