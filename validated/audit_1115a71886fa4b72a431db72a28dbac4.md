## Title
`get-asset-price()` misattributes the STX Pyth feed to the `stSTXbtc`/`zstSTXbtc` (BTC-yield) assets, producing a wrong collateral/debt valuation and a wrong health verdict - (File: `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
In `get-asset-price`, the branches for `stSTXbtc` and `zstSTXbtc` are commented as "BTC price" but both call `get-pyth-price PYTH-STX` instead of `PYTH-BTC`, attaching the wrong asset's price feed to these assets when computing USD-denominated collateral/debt values and the resulting health factor / liquidatability flag.

### Finding Description
`v0-1-data.clar` defines distinct Pyth feed identifiers `PYTH-STX` (STX/USD) and `PYTH-BTC` (BTC/USD) [1](#0-0) . `get-asset-price` correctly uses `PYTH-BTC` for `sBTC` and `zsBTC`, but for `stSTXbtc` and `zstSTXbtc` — assets explicitly commented as "BTC price (liquid staked STX with BTC yield)" — it queries `PYTH-STX` instead: [2](#0-1) 

This price is consumed by `sum-collateral-usd` and `sum-debt-usd`, which multiply the (wrong) price by the asset amount/scaled debt to build `coll-usd`/`debt-usd` [3](#0-2) . Those totals then feed directly into `current-ltv`, `health-factor`, and the boolean `is-liquidatable` returned by `get-user-position` [4](#0-3) .

Because STX and BTC prices move independently, substituting the STX feed for the BTC feed produces an incorrect USD value for `stSTXbtc`/`zstSTXbtc` positions whenever the two prices diverge — the direction and magnitude of the error is unbounded and tracks the STX/BTC price ratio drift, not a rounding or decimals artifact.

### Impact Explanation
This is an exponent/price-attached-to-wrong-asset class bug (explicitly in scope per the analog rules) landing on the collateral/debt valuation and health verdict path, analogous to the reentrancy report's underlying concern of state manipulated by/around a "read a field for a purpose it wasn't meant for" flow. If BTC/USD > STX/USD (BTC price higher), `stSTXbtc`/`zstSTXbtc` collateral value is undervalued and debt value using this asset is undervalued — this can misreport a position as `is-liquidatable: false` when it is actually unhealthy under the true BTC price, or vice versa (falsely flag a healthy position as liquidatable). This maps to temporary freezing of funds (positions that should be liquidatable are not flagged, delaying protective liquidation and risking insolvency exposure) — a High-severity impact class.

However, this must be caveated: this data path lives in the standalone `v0-1-data.clar` "read-only utility contract" (explicitly labeled as such in its header comment) [5](#0-4) . Nothing in the codebase indicates that `v0-4-market.clar` (the actual borrow/liquidate/collateral-add path) calls into `v0-1-data.clar` for its authoritative health checks — the market contract instead resolves prices independently via `price-resolve`/`resolve-price-feed` against each asset's registered oracle identifier in the asset registry [6](#0-5) . I could not find any caller of `v0-1-data.clar`'s `get-user-position`/`get-asset-price` from a fund-moving function; it appears to be purely a display/query aggregator.

### Likelihood Explanation
If `get-user-position`/`get-all-assets`/etc. from `v0-1-data.clar` are used by liquidation bots or front-ends to decide when to call `liquidate()`, a bot could skip liquidating an actually-unhealthy `stSTXbtc` position because `is-liquidatable` incorrectly reads `false`, until the real on-chain `liquidate()` health check (in `v0-4-market.clar`, which uses correct per-asset oracle idents from the registry) is separately evaluated. The bug is code-only (not third-party oracle data or a bad registry entry) and is deterministically triggered any time BTC/USD ≠ STX/USD, which is essentially always.

### Recommendation
Change the `stSTXbtc` and `zstSTXbtc` branches in `get-asset-price` (mainnet/contracts/utility/v0-1-data.clar) to call `get-pyth-price PYTH-BTC` instead of `get-pyth-price PYTH-STX`, matching the `sBTC`/`zsBTC` pattern and the asset's documented BTC-denominated nature. Apply the identical fix in the local-testing mirror `local-testing/contracts/utility/protocol-data.clar` (same bug present there).

### Proof of Concept
1. Assume STX/USD = $1.00 and BTC/USD = $60,000.
2. A user holds `stSTXbtc` collateral valued (correctly, per the asset's design) at ~$60,000 per unit.
3. Call `get-user-position` for that account: `sum-collateral-usd` invokes `get-asset-price(stSTXbtc)`, which returns the `PYTH-STX` price (~$1.00) instead of `PYTH-BTC` (~$60,000) [2](#0-1) .
4. `coll-usd` is understated by roughly 60,000x, so `current-ltv` is overstated and `health-factor`/`is-liquidatable` are computed against a grossly wrong denominator, causing the read-only reported health state to diverge sharply from the true, market-contract-verified state.

**Caveat on confidence**: I was unable to confirm from the indexed code whether any privileged off-chain or on-chain component treats `v0-1-data.clar`'s `get-user-position`/`is-liquidatable` as authoritative for triggering fund-moving actions (e.g., automated liquidation bots), versus using it purely for UI display. If it is display-only with no automated consumer, the practical impact is informational rather than a fund-impacting bug. Confirming this would require inspecting off-chain bot/indexer code outside this repository's index, which is out of scope for this scan.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
