### Title
Unauthenticated aggregator gRPC endpoint lets any network caller trigger privileged bridge operations - (File: core/src/servers.rs)

### Summary
The `ClementineAggregator` gRPC service is the single privileged entry point that all verifiers and operators trust for state-changing and broadcast-triggering calls (`NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, `InternalSendTx`, `InternalGetEmergencyStopTx`). Unlike the verifier/operator servers, the aggregator's own gRPC server does not authenticate its callers, so any party that can reach the aggregator's TCP port can invoke these privileged RPCs and have the aggregator forward them to verifiers/operators using the aggregator's own trusted mTLS identity. This mirrors the C4 "Ineffective Whitelist" bug class: the entity that is supposed to be the sole trusted caller (here, "the aggregator identity") can be impersonated/used by anyone reaching that entry point, defeating the intended access boundary — "a caller reaching a signing or state-changing method versus the party it is meant for."

### Finding Description
`create_grpc_server` builds mTLS with an `Interceptors` value that restricts callers to "aggregator or self" for verifier/operator servers, but the aggregator server is explicitly built without that restriction: [1](#0-0) 

`create_aggregator_grpc_server` only warns if `client_verification` is enabled, implying the aggregator is normally deployed with it disabled, and always passes the same `create_grpc_server` path used above: [2](#0-1) 

This is confirmed by the project's own documentation, which states the aggregator intentionally never authenticates its clients: [3](#0-2) 

Meanwhile, the verifier/operator servers only ever check that the caller presented the *aggregator's* certificate (or their own, for internal calls) — they have no way to distinguish "the real aggregator operator" from "anyone who reached the aggregator's unauthenticated port and had the aggregator forward the call for them": [4](#0-3) 

The aggregator exposes exactly the state-changing/broadcast RPCs relevant to bridge custody without any caller check of its own: [5](#0-4) 

Because the aggregator process holds the one credential ("the aggregator's client certificate") that verifiers/operators treat as authoritative, and that process itself does not gate who may drive it, the "whitelist" (mTLS restriction to the aggregator) is rendered ineffective in the same way the C4 report describes: the privileged party (aggregator) can be driven by an unlimited number of unprivileged requesters, each one indistinguishable from a legitimate call once it reaches the aggregator.

### Impact Explanation
This directly matches the "unauthenticated state-changing or broadcasting call" High-severity category: an attacker reaching the aggregator's port can initiate `NewDeposit`/`SendMoveToVaultTx` flows, request `Withdraw`/`OptimisticPayout` reimbursement flows, or force `InternalSendTx` broadcasts, all of which are supposed to only be reachable by "the clementine-backend service" (the trusted aggregator operator), per the RPC docstrings. Even though downstream cryptographic checks (musig2 N-of-N signing, ECDSA verification signatures) still gate final fund movement, this removes the intended access-control layer at the point closest to the caller, and lets anyone drive the aggregator's privileged workflow (nonce generation, deposit/withdrawal orchestration, broadcast triggering) without ever needing to be the aggregator operator.

### Likelihood Explanation
High for a deployment following the documented configuration: the docs explicitly instruct that "the aggregator does not enforce client certificates." Any network path to the aggregator's TCP/gRPC port (which, per its purpose, is intended to be reachable by the "clementine-backend service") is sufficient — no key compromise, no operator/verifier role, no social engineering required, only network reachability, consistent with the report's original "unprivileged attacker" threshold.

### Recommendation
Require the aggregator's gRPC server to authenticate its own callers (e.g., mTLS with a specific backend-service certificate, or an API key/JWT scheme), analogous to how verifier/operator servers restrict inbound calls to "aggregator or self." At minimum, rate-limit and authenticate all state-changing/broadcast RPCs (`NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, `InternalSendTx`) so that the aggregator cannot be driven by arbitrary network clients.

### Proof of Concept
1. Deploy Clementine per the documented configuration (aggregator TLS enabled, `client_verification` left at its aggregator default of not enforcing client certs, per docs/usage.md:203).
2. From any host with network access to the aggregator's exposed port (no certificate needed beyond generic TLS), open a gRPC channel to `ClementineAggregator`.
3. Call `Withdraw`, `OptimisticPayout`, `NewDeposit`, or `InternalSendTx` directly, as shown reachable in [6](#0-5) .
4. The aggregator processes the request and forwards it to verifiers/operators using its own certificate, which those servers accept per the "aggregator or self" check in [7](#0-6) , despite the request never originating from the actual trusted aggregator operator.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}
