## Title
VALIDATE_SENDER precompile accepts signature-malleable (v,s) values, enabling replay-protection bypass for AccountKey-based multisig validation - (File: blockchain/vm/contracts.go)

### Summary
The `VALIDATE_SENDER` precompiled contract (address `0x3ff`), which is used by smart contracts to verify that a set of signatures over an arbitrary message hash was produced by the keys registered in an account's `AccountKey`, recovers signer public keys via `crypto.Ecrecover` without first validating that `r`/`s` are canonical (non-malleable) via `crypto.ValidateSignatureValues`. This allows a caller to submit an alternate, still-valid signature `(r, n-s, 1-v)` for the same message/signer, i.e. classic ECDSA signature malleability.

### Finding Description
`validateSender.validateSender` parses `from`, a 32-byte message, and one or more 65-byte signatures from the precompile input, then recovers a public key for each signature directly with `crypto.Ecrecover`, and finally checks the recovered keys against the account's `AccountKey`: [1](#0-0) 

`crypto.Ecrecover` (both cgo and non-cgo implementations) only rejects a non-canonical recovery id (`v ≥ 2`); it does not reject signatures whose `s` lies in the upper half of the curve order: [2](#0-1) 

This is different from every other signature-recovery path in the codebase, which explicitly calls `crypto.ValidateSignatureValues(v, r, s, homestead)` — rejecting `s` values above `secp256k1halfN` — before calling `Ecrecover`:
- Legacy/typed transaction sender recovery: [3](#0-2) 
- EIP-7702 `SetCodeAuthorization.Authority()`: [4](#0-3) 
- Auction bid signer recovery (`kaiax/auction/bid.go`): [5](#0-4) 
- The `ValidateSignatureValues` implementation itself, which explicitly documents this as an anti-malleability check: [6](#0-5) 

`VALIDATE_SENDER` is the one path that omits this check entirely — it neither calls `ValidateSignatureValues` nor filters on `s`.

### Impact Explanation
`VALIDATE_SENDER` is a general-purpose building block explicitly documented and tested for AccountKey/multisig authorization inside smart contracts (see `contracts/testing/validatesender/validate_sender.sol` and `tests/validate_sender_test.go`, where `ValidateSenderContract.ValidateSender(sender, msgHash, sigs)` is used to authorize actions on behalf of a multisig account key). Because the precompile accepts both the canonical and the malleable counterpart of any valid signature for the same `(from, msgHash)`, any smart contract built on top of `VALIDATE_SENDER` that treats the raw signature bytes (or a hash thereof) as a unique replay-protection nonce — rather than solely relying on the signed message content — can be tricked into accepting a second, "different" but cryptographically equivalent signature for an already-authorized message. This is a well-known ECDSA-malleability replay/authorization-bypass pattern (the exact bug class cited in the report) and directly weakens the AccountKey-authorization guarantee that this precompile is meant to provide to any contract built on it, reachable by any unprivileged transaction sender calling such a contract.

### Likelihood Explanation
Exploitation only requires deriving `s' = secp256k1N - s` and `v' = 1 - v` from an already-observed valid signature (trivial, public-key-agnostic arithmetic) and submitting it as ordinary transaction input to a contract calling `VALIDATE_SENDER`. No privileged access, node compromise, or consensus manipulation is needed — only a standard public transaction/call.

### Recommendation
In `validateSender.validateSender` (blockchain/vm/contracts.go), validate each signature's `r`/`s` with `crypto.ValidateSignatureValues(v, r, s, true)` (rejecting the upper-half `s` range) before calling `crypto.Ecrecover`, mirroring the check already performed in `recoverPlainCommon` and `getSigner` (kaiax/auction/bid.go).

### Proof of Concept
1. Sign a message hash `msg` with a private key belonging to one of the signers configured in `from`'s `AccountKey`, producing canonical signature `(r, s, v)`.
2. Compute the malleable counterpart `(r, secp256k1N - s, 1 - v)`.
3. Call a contract that forwards `(from, msg, sig')` to the `VALIDATE_SENDER` precompile (`blockchain/vm/contracts.go` `validateSender.Run`), e.g. via `ValidateSenderContract.ValidateSender` as exercised in `tests/validate_sender_test.go`.
4. Observe that `sig'` also recovers to the same authorized public key and passes `accountkey.ValidateAccountKey`, i.e. the precompile treats `(r,s,v)` and `(r, n-s, 1-v)` as two distinct "valid" authorizations for the same message — demonstrating the missing malleability check that other recovery paths in the codebase explicitly guard against.

```go
// Ecrecover returns the uncompressed public key that created the given signature.
func Ecrecover(hash, sig []byte) ([]byte, error) {
	if len(sig) != SignatureLength {
		return nil, errors.New("invalid signature")
	}
	if len(hash) != DigestLength {
		return nil, fmt.Errorf("hash is required to be exactly %d bytes (%d)", DigestLength, len(hash))
	}
	// Enforce canonical Ethereum recovery id v ∈ {0, 1}.
	if sig[RecoveryIDOffset] >= 2 {
		return nil, errors.New("invalid signature recovery id")
	}
	return secp256k1.RecoverPubkey(hash, sig)
}
```

```go
// ValidateSignatureValues verifies whether the signature values are valid with
// the given chain rules. The v value is assumed to be either 0 or 1.
func ValidateSignatureValues(v byte, r, s *big.Int, homestead bool) bool {
	if r.Cmp(common.Big1) < 0 || s.Cmp(common.Big1) < 0 {
		return false
	}
	// reject upper range of s values (ECDSA malleability)
	// see discussion in secp256k1/libsecp256k1/include/secp256k1.h
	if homestead && s.Cmp(secp256k1halfN) > 0 {
		return false
	}
	// Frontier: allow s to be in full N range
	return r.Cmp(secp256k1N) < 0 && s.Cmp(secp256k1N) < 0 && (v == 0 || v == 1)
}
```
