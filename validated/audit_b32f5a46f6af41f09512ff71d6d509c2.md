### Title
Missing minimum-bid enforcement allows the auction bid pool to accept near-zero bids, letting searchers win block-position auctions while paying negligible value - (File: kaiax/auction/impl/bid_pool.go)

### Summary
The external report's bug class is a missing lower-bound check on a value that is supposed to compensate the protocol/validator (an off-chain-negotiated `feeRate` with no `minFeeRate` floor). The closest reachable analog in this Kaia repo is the `kaiax/auction` bid pool, which accepts any bid greater than zero (`bid.Bid.Sign() <= 0` is the only floor check) with no protocol-configured minimum bid amount, allowing a searcher to submit and win an auction slot for a nominal amount (e.g., 1 wei) as long as it beats the previous bid for that target tx.

### Finding Description
`BidPool.validateBid` in `kaiax/auction/impl/bid_pool.go` enforces several structural checks on submitted bids (block-number window, data size, gas limit, signature validity) but the only economic constraint is: [1](#0-0) 
This only rejects a zero or negative bid; there is no `minBid`/`minBidRate` configured or enforced anywhere in `AuctionConfig`, `BidPool`, or the bid-replacement logic in `insertBid`: [2](#0-1) 
Because replacement of an existing bid for the same `(blockNumber, targetTxHash)` only requires a strictly higher `bid.Bid` value, a single searcher facing no real competition can submit a bid of 1 wei and it will be accepted, inserted into `bidWinnerMap`, and forwarded via `newBidCh` to be built into a block bundle in `AuctionModule.ExtractTxBundles`: [3](#0-2) 
There is no `AuctionConfig` field or `errors.go` sentinel corresponding to a minimum-bid floor (only `ErrZeroBid`, `ErrLowBid` for being non-strictly-greater than an existing bid): [4](#0-3) 
This mirrors the reported bug class exactly: the on-chain/off-chain value (feeRate in the report, Bid here) that is meant to fund the protocol/proposer has an upper-bound-style adjacent check (`ErrExceedMaxCallGasLimit`/`ErrExceedMaxDataSize`) but no protocol-enforced minimum, so an unprivileged auction participant can pay an arbitrarily small amount and still have their transaction included with priority via `ExtractTxBundles`/`GetBidTxGenerator`.

### Impact Explanation
Auctions (KIP-249) exist so that MEV/priority value is captured for the protocol/validators rather than left on the table. Absent a minimum bid, a searcher (or a sender colluding with themselves across two addresses, since bid pool competition is optional) can win the priority slot for 1 wei whenever no other searcher is actively competing for that specific target transaction in that block window, undermining the intended fee/value capture of the auction mechanism. This is a fee/auction-settlement value-capture issue analogous to the reported "orders settled without paying fees" — value that should go through the auction is bypassed at negligible cost.

### Likelihood Explanation
Any external actor who can reach `auction_submitBid` (an RPC exposed per `kaiax/auction/README.md`, `auction_submitBid`) and has an `Auctioneer`-countersigned bid can trigger this; because `AuctionEntryPointMock`/checks only require `bid > 0`, and there is no market-maker-of-last-resort or reserve price, this is reachable whenever no competing bid exists for that target tx — a very common situation in practice (most transactions won't have multiple competing searchers). No node compromise or validator collusion is required.

### Recommendation
Introduce a protocol-configurable minimum bid (e.g., `AuctionConfig.MinBid` or a value read from `AuctionEntryPoint`/registry) and enforce it in `BidPool.validateBid` alongside the existing zero-bid check, e.g.:
```go
if bid.Bid.Cmp(minBid) < 0 {
    return auction.ErrBidBelowMinimum
}
```
This should be sourced from a governance-controlled parameter (mirrored on the `AuctionEntryPoint` contract, similar to `bidTxGasBuffer`) so it can be tuned per network conditions, consistent with the report's recommendation to introduce and enforce a `minFeeRate`.

### Proof of Concept
1. Deploy/observe an `AuctionEntryPoint` and start the auction module (Randao fork active, auctioneer and entry point configured) so `BidPool.running == 1`.
2. As the `Auctioneer`, sign and submit (via `auction_submitBid` → `AuctionAPI.SubmitBid` → `BidPool.AddBid`) a `Bid` with `Bid = big.NewInt(1)` (1 wei), a valid `TargetTxHash` for an upcoming block, valid searcher/auctioneer signatures, and no other competing bid for that target.
3. `validateBid` only checks `bid.Bid.Sign() <= 0` (fails only for 0 or negative) at [1](#0-0) ; the 1-wei bid passes.
4. The bid is inserted (`insertBid`) and becomes the winner in `bidWinnerMap` since there is no competing bid to beat.
5. When the target transaction is included, `AuctionModule.ExtractTxBundles` (`kaiax/auction/impl/builder.go:31-54`) builds a bundle including the corresponding `BidTx`, granting the searcher's transaction priority execution for a payment of only 1 wei — demonstrating that the auction's value-capture mechanism can be bypassed at negligible cost, analogous to the reported missing `minFeeRate` check.

```go
func (a *AuctionModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	bundles := []*builder.Bundle{}
	curBlock := a.Chain.CurrentBlock()
	if curBlock == nil || atomic.LoadUint32(&a.bidPool.running) == 0 {
		return bundles
	}

	miningBlock := curBlock.NumberU64() + 1
	bidTargetMap := a.bidPool.GetTargetTxMap(miningBlock)
	if len(bidTargetMap) == 0 {
		return bundles
	}

	for _, tx := range txs {
		txHash := tx.Hash()
		bid, ok := bidTargetMap[txHash]
		if !ok {
			continue
		}
		b := builder.NewBundle(
			builder.NewTxOrGenList(a.GetBidTxGenerator(tx, bid)),
			txHash,
			true,
		)
```
