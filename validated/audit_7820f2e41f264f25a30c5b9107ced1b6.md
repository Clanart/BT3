Based on my investigation, I found a strong structural analog: the redirect header-sanitization filter in `same-origin-filter.ts` uses a hardcoded denylist of header names rather than allowlisting only known-safe headers, so a cross-origin redirect from an attacker-controlled server can smuggle a still-sensitive-but-unlisted header past the sanitizer, exactly mirroring the "deny-list omits a live sensitive operation" root cause of the subtensor report.

### Title
Cross-origin redirect header sanitizer uses a hardcoded denylist, letting unlisted sensitive headers (e.g. `X-GitHub-OTP`, custom bearer/session headers) leak to an attacker-controlled redirect target - (File: app/src/main-process/same-origin-filter.ts)

### Summary
`installSameOriginFilter` is Desktop's only defense against a GitHub/GHES API redirect exfiltrating credentials to a different origin, since `fetch()` does not enforce same-origin credential stripping the way browsers with CORS do. [1](#0-0) 
It works by remembering each request's original origin and, on any subsequent cross-origin hop of the same request id, stripping headers that match a small, hardcoded set. [2](#0-1) 

### Finding Description
The sanitization logic is implemented as a denylist:

```ts
const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])
...
for (const [k, v] of Object.entries(details.requestHeaders)) {
  if (!unsafeHeaders.has(k.toLowerCase())) {
    sanitizedHeaders[k] = v
  }
}
``` [3](#0-2) 

Any header not literally named `authentication`, `authorization`, or `cookie` is passed through to the new origin on a cross-origin redirect. This is the same structural flaw as the subtensor bug: the filter's job is authorization/credential-boundary enforcement, but it's built as "block these specific known-sensitive tokens" instead of "only allow these specific known-safe tokens." Any credential-carrying header introduced later, or by a server response, that isn't one of these three exact strings bypasses the boundary entirely — identical in shape to the `deny { swap_coldkey, schedule_swap_coldkey }` list that didn't get updated when `announce_coldkey_swap`/`swap_coldkey_announced` were added.

Concretely, Desktop already uses at least one other credential-relevant header that this denylist does not cover: `X-GitHub-OTP`, which the app inspects on responses and which GitHub Enterprise/GitHub.com 2FA flows use. [4](#0-3)  More generally, `authenticated-image-filter.ts` injects `Authorization: token ${token}` headers for private asset/avatar requests based on origin [5](#0-4) 
— that header name is covered here (`authorization`), but the design pattern shows Desktop is prone to adding new origin-scoped, credential-bearing headers over time, any of which would silently bypass `unsafeHeaders` unless someone remembers to add the exact lowercase string to this one `Set`.

### Impact Explanation
If a GitHub/GHES API endpoint (or any endpoint Desktop calls with `fetch`) is redirected by a malicious or compromised server/proxy to an attacker-controlled origin, any request header not in `{authentication, authorization, cookie}` — including any future or custom bearer/session/API-key style header, `Proxy-Authorization`, or any GHES-specific auth header — is forwarded unstripped to the attacker's server, leaking credentials/tokens. The `installSameOriginFilter` comment explicitly frames this filter's sole purpose as stopping "cross domain leaks of auth headers" [6](#0-5) 
so any gap in the header set directly undermines the one guard meant to prevent this class of leak, satisfying the "credential/token exfiltration via attacker-controlled ... redirect response" impact criteria.

### Likelihood Explanation
The attacker-controlled trigger (an HTTP redirect from a GitHub Enterprise instance, a compromised/malicious API endpoint, or an MITM'd proxy that Desktop's `fetch` requests hit) is exactly the class of input this bug report targets. Exploitability depends on Desktop (now or in the future) sending a credential-bearing header whose name isn't `authorization`/`authentication`/`cookie` — I could not find such a header actively in use beyond the ones already covered by name (`Authorization`), so today's concrete leak surface is narrower than the subtensor case. This is a latent/maintenance-hazard vulnerability (same shape as the report: the mechanism to prevent bypass is a manually maintained list rather than a safe-by-default allowlist) rather than a confirmed exploitable header leak in the current codebase.

### Recommendation
Invert the filter to an allowlist: strip every request header on cross-origin redirect except an explicit, minimal allowlist of headers known to be safe to forward (e.g. `accept`, `content-type`, `user-agent`), so any newly introduced credential header is safe by default instead of requiring developers to remember to add it to `unsafeHeaders`.

### Proof of Concept
Conceptual (cannot be executed without live redirect infrastructure): configure a GHES-like origin that Desktop is authenticated against so that a normal API call (e.g. `ghRequest`) receives an HTTP 3xx redirect to `https://attacker.example`. If the outgoing request carries any custom credential header other than `Authorization`/`Cookie` (e.g. a hypothetical `X-Desktop-Session` or `X-GitHub-OTP` echoed back on the request), `installSameOriginFilter`'s `onBeforeSendHeaders` handler will not remove it because `unsafeHeaders.has(k.toLowerCase())` returns false for anything not in the three-item set, and the header is retransmitted to `attacker.example`.   orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const initialOrigin = requestOrigin.get(details.id)
    const { origin } = new URL(details.url)

    if (initialOrigin === undefined || initialOrigin === origin) {
      return { requestHeaders: details.requestHeaders }
    }

    const sanitizedHeaders: Record<string, string> = {}

    for (const [k, v] of Object.entries(details.requestHeaders)) {
      if (!unsafeHeaders.has(k.toLowerCase())) {
        sanitizedHeaders[k] = v
      }
    }

    log.debug(`Sanitizing cross-origin redirect to ${origin}`)
    return { requestHeaders: sanitizedHeaders }
  })
