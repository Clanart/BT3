## Title
`popStashEntry` silently drops the user's stash based on an unreliable "exit code 1 + empty stderr = safe" heuristic - (File: `app/src/lib/git/stash.ts`)

### Summary
GitHub Desktop's `popStashEntry` treats a `git stash pop` failure that has exit code `1` and *empty* `stderr` as proof that "the stash was popped successfully but exit code 1 reported" and, based on that assumption alone, calls `dropDesktopStashEntry` to permanently delete the stash entry. This mirrors the Reserve `DutchTrade`/`BackingManager` bug class: an ambiguous, empty/negative signal (no error text) is treated as evidence of one specific benign condition, when in fact many other failure modes produce the exact same signature. If the stash pop actually failed for a different reason, Desktop discards the user's stashed changes as if they had already been safely restored.

The code's own comment ("Not the greatest approach but stash isn't very communicative") acknowledges the heuristic is fragile — this is the exact class of bug in the report: using the *absence* of a specific error signal (empty stderr) as a positive proof of a particular benign outcome (resolvable conflict already applied), instead of verifying the actual outcome. `git stash pop` internally performs a merge of the stash tree into the working directory, which can invoke content filters (`clean`/`smudge` defined via `.gitattributes`) and can fail for reasons unrelated to merge conflicts — e.g. a filter command failing, a filesystem error, or any other non-conflict failure that a git version/platform combination happens to report without stderr output. All of these are conditions influenceable by the contents of a cloned/fetched repository (via `.gitattributes` filter definitions checked into the repo), i.e. attacker-controlled input, since Desktop applies whatever filter/attribute configuration is present in the working tree during operations like stash pop/apply and checkout.

There is no verification that the working directory actually received the stashed changes before `dropDesktopStashEntry` runs — the code only checks the shape of the error (`exitCode === 1 && stderr.length === 0`), the same ambiguous-empty-signal pattern flagged in the source report as unsafe (there empty revert data, here empty stderr).

### Impact Explanation
If the heuristic's assumption is wrong, Desktop calls `git stash drop`, which is a destructive, effectively unrecoverable action (the stash commit becomes unreachable and subject to garbage collection). The user's stashed working-directory changes can be silently lost while Desktop reports/behaves as though the pop succeeded (`_popStashEntry` in `app-store.ts` logs "popped stash" and simply refreshes the repository) — matching the "silent corruption of what the user commits or pushes" impact category, since a user who believes their in-progress changes were restored may go on to commit/push a repository state missing that work, with no error surfaced. ### Likelihood Explanation
Exploitation requires only that the attacker control the content of a repository the user clones/fetches/checks out in Desktop (e.g. a `.gitattributes` file with a `filter.<name>.smudge`/`clean` command that fails during the internal merge performed by `stash pop`), which fits the in-scope attacker model (repository content, not local/physical access). Because the exact conditions under which `git` omits stderr text on a given failure are git-version/platform dependent and not something Desktop can fully enumerate, this is a realistic, not purely theoretical, path — directly analogous to the accepted Reserve finding, where the judges upgraded severity despite "low likelihood" because the assumption (empty data ⇒ one specific cause) was demonstrably false in practice (USDT/BNB `approve()` reverting with empty data for unrelated reasons).

### Recommendation
Do not infer success from the absence of an error signal. After a failed `git stash pop`, explicitly verify the actual repository state (e.g., re-check `git status`/whether the stash's changes are present, or check for conflict markers/unmerged paths) before deciding whether it is safe to drop the stash. If verification is inconclusive, surface the error to the user rather than auto-dropping the stash, consistent with how `createDesktopStashEntry`'s own comment already flags this class of "here be dragons" heuristic as needing revisiting.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitattributes` entry that defines a clean/smudge filter for a tracked file, where the filter command exits non-zero under a specific condition (e.g. a size or environment check) but does not print anything to stderr.
2. Victim clones the repository in GitHub Desktop, creates a Desktop-managed stash (e.g. via branch switch with local changes, `createStashAndDropPreviousEntry`/`checkoutAndBringChanges`), and later triggers the pop path (either automatically during a branch switch or via "Restore stash").
3. `git stash pop` invokes the filter during the internal merge; the filter fails, causing `git stash pop` to exit with code `1`; because the filter emitted nothing to stderr, `e.result.stderr.length === 0`.
4. `popStashEntry`'s catch handler matches its heuristic and calls `dropDesktopStashEntry`, permanently deleting the stash even though the victim's changes were never actually restored to the working directory.
5. The victim is left with neither the restored changes nor the stash, and no error is shown to them.

export async function popStashEntry(
  repository: Repository,
  stashSha: string
): Promise<void> {
  // ignoring these git errors for now, this will change when we start
  // implementing the stash conflict flow
  const expectedErrors = new Set<DugiteError>([DugiteError.MergeConflicts])
  const stashToPop = await getStashEntryMatchingSha(repository, stashSha)

  if (stashToPop !== null) {
    const args = ['stash', 'pop', '--quiet', `${stashToPop.name}`]
    await git(args, repository.path, 'popStashEntry', {
      expectedErrors,
    }).catch(e => {
      // popping a stashes that create conflicts in the working directory
      // report an exit code of `1` and are not dropped after being applied.
      // so, we check for this case and drop them manually unless there's
      // anything in stderr as that could have prevented the stash from being
      // popped. Not the greatest approach but stash isn't very communicative
      if (
        e instanceof GitError &&
        e.result.exitCode === 1 &&
        e.result.stderr.length === 0
      ) {
        log.info(
          `[popStashEntry] a stash was popped successfully but exit code ${e.result.exitCode} reported.`
        )
        // bye bye
        return dropDesktopStashEntry(repository, stashSha)
      }
      return Promise.reject(e)
    })
  }
}
