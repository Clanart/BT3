### Title
`GeneratorPromotion::complete` admits proof maps not matching the participant set and panics on `unwrap`, bricking promotion - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to the Hybra gauge bug (an entity admitted without proper provenance/membership validation later bricks a trusted path), `GeneratorPromotion::complete` validates the `proofs` map only by count (`proofs.len() == n - 1`) and per-key upper bound (`u16::from(i) <= n`), but never verifies the map actually contains a `GeneratorProof` for every participant in `1 ..= n` other than the local one. The subsequent per-participant loop indexes the map with `proofs.get(&i).unwrap()`, so a malformed-but-admitted map panics instead of returning an error.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two checks on the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

- `proofs.len() != params.n() - 1` → `IncorrectAmountOfParticipants` [1](#0-0) 
- `u16::from(i) > params.n()` for each key → `InvalidParticipant` [2](#0-1) 

It then iterates `i in 1 ..= params.n()`, skips `params.i()`, and unconditionally unwraps: `let proof = proofs.get(&i).unwrap();` [3](#0-2) 

The checks are insufficient: a map of size `n - 1` may contain an entry keyed to the verifier's own index `params.i()` (a participant that should never appear in the proofs map, since the local proof is supplied separately via `self.proof.share` [4](#0-3) ) while omitting some honest participant `j`. Both validation checks pass (`len == n - 1`, all keys `<= n`), yet `proofs.get(&j).unwrap()` panics.

Contrast with the correct pattern used elsewhere: `ThresholdKeys::new` checks both length and each key's bound [5](#0-4) , and PedPoP's `validate_map` additionally verifies every expected participant is present and that no entry duplicates the local index [6](#0-5) . `complete` omits the equivalent "exact membership" check — the same inconsistency as `GaugeManager` verifying standard pairs via the factory but skipping the check for CL pools.

### Impact Explanation
A `GeneratorProof` map is untrusted bytes/messages supplied by counterparties (`GeneratorProof::read` + `complete` is a listed reachability surface). Supplying a `proofs` map that includes a `Participant` equal to the verifier's own `params.i()` — or otherwise swaps one required key for another in-range key — causes a panic inside `complete`, aborting generator promotion for the honest caller. Since the panic occurs mid-protocol after proofs have already been partially processed, the promotion session is bricked and must be restarted; repeated submissions brick it indefinitely. This mirrors the report's impact: an unvalidated entity admitted into a trusted path halts the protocol for the honest participant.

### Likelihood Explanation
Any party able to feed a `proofs` map to a `complete` call (i.e., provide a `HashMap<Participant, GeneratorProof>` assembled from received proof messages) can trigger it. No valid DLEq proof is needed for the offending entries — the panic happens before `proof.proof.verify` is reached for the missing participant [7](#0-6) . The malformed map can even consist entirely of valid proofs keyed to the wrong participant indices.

### Recommendation
Replace the length/bound checks with exact-set membership validation, mirroring `validate_map`: iterate `1 ..= params.n()`, require `proofs` contains every `i != params.i()` and does not contain `params.i()`, returning `PromotionError::MissingParticipant`/`InvalidParticipant` instead of unwrapping. Alternatively, look up each `proofs.get(&i)` and map `None` to an error rather than panicking.

### Proof of Concept
```rust
// crypto/dkg/promote: panic in complete() via mis-keyed proofs map
let (promotion, _proof) =
  GeneratorPromotion::<Ristretto, AltGenerator<Ristretto>>::promote(&mut OsRng, my_keys);

let n = my_keys.params().n();
let my_i = my_keys.params().i();

// Build a proofs map of size n - 1 that passes both checks:
// include an entry keyed to `my_i` (never queried) and omit honest participant `j`.
let mut proofs: HashMap<Participant, GeneratorProof<Ristretto>> = HashMap::new();
for i in 1 ..= n {
  let i = Participant::new(i).unwrap();
  proofs.insert(i, valid_proof_for(i)); // collect real proofs
}
// Swap one required entry for a self-keyed one
let j = Participant::new(if u16::from(my_i) == 1 { 2 } else { 1 }).unwrap();
proofs.remove(&j);
proofs.insert(my_i, proofs[&other].clone()); // len still n - 1, all keys <= n

// Both validation checks pass; proofs.get(&j).unwrap() panics.
promotion.complete(&proofs);
```
The analogous "quarantine" hardening from the report (never panic on untrusted map shape) applies directly: the fix is to return a typed `PromotionError` so a single malformed proof set cannot abort promotion.
