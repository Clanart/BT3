### Title
Quadratic Lagrange interpolation (O(t²) field ops + t inversions) on deserialization of `ThresholdKeys` and on `ThresholdView` construction - (File: crypto/dkg/src/lib.rs)

### Summary
The pypdf advisory (GHSA-5hgr-hg42-57jg / CWE-407) is an algorithmic-complexity DoS: a small crafted input forces disproportionate decode work. Serai's `Interpolation::interpolation_factor` exhibits the same class: computing a Lagrange factor is O(k) in the size of the participant set, and it is invoked once per participant, making `ThresholdKeys::new` and `ThresholdKeys::view` O(t²)/O(k²) in field multiplications plus one expensive field inversion per participant. `ThresholdKeys::read` is explicitly an untrusted-bytes entry point, so a single ~O(n)-sized serialized blob forces quadratic CPU work.

### Finding Description
`Interpolation::interpolation_factor` iterates the entire `included` slice for a single participant, performing one field multiplication and one subtraction per other participant, and finishing with a field inversion [1](#0-0) .

`ThresholdKeys::new` calls `interpolation_factor` once for each of `1 ..= params.t()` to derive `group_key`, giving O(t²) multiplications and t inversions [2](#0-1) .

`ThresholdKeys::read` deserializes an attacker-controlled `t`, `n` (both u16, so up to 65535), a `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` — O(n) bytes in, O(t²) field work out [3](#0-2) . Validation only checks `t <= n`, `i <= n`, and share count [4](#0-3) .

The same quadratic pattern occurs in `ThresholdKeys::view`, which calls `interpolation_factor` once per included signer (plus one for the local secret share), each O(k) with an inversion, where `k` = `included.len()` up to `n` [5](#0-4) . `view` is reached by FROST signing (`sign`/`complete`) whenever the included set is large, i.e., driven by which participants submit preprocesses/shares — input an unprivileged protocol peer controls.

For `t = n = 65535` with Lagrange interpolation, a single `ThresholdKeys::read` performs ~4.3·10⁹ field multiplications and 65535 field inversions from a ~2–4 MB input — roughly three orders of magnitude more work per input byte than linear decoding.

### Impact Explanation
An unprivileged party supplying serialized `ThresholdKeys` bytes (or, in protocol, driving a large `included` set into `view()` during signing) can stall the victim in a CPU-bound loop of billions of field operations. This is a resource-exhaustion/availability impact on any node processing untrusted `ThresholdKeys` blobs or participating in FROST signing with attacker-influenced signing sets — the same availability-only impact class as the referenced advisory (CVSS VA:L).

### Likelihood Explanation
Reachability is confirmed by the accepted input surface: `ThresholdKeys::read` consumes a `t`/`n` pair chosen by the byte provider and immediately performs the quadratic group-key derivation before any semantic check of share correctness. No secret, no collusion, and no malformed-curve trickery is required — just a large validly-framed `t = n` parameter set. In-protocol, `view()` quadratic cost is triggered whenever a large signing set is assembled, which depends on preprocess submissions from arbitrary participants. Cost is bounded by the u16 parameter range (t, n ≤ 65535), keeping severity Medium rather than Critical/High.

### Recommendation
Cap the Lagrange interpolation cost or avoid the quadratic form:
- Compute `group_key`/verification-share interpolation with the standard O(t) prefix/suffix product trick for the full `1..=t` range, or cache computed Lagrange factors across calls.
- In `interpolation_factor`, batch the inversions (e.g., Montgomery batch inversion) so the O(k) inversions in `view()`/`new()` become one inversion plus O(k) multiplications.
- Alternatively, enforce a sane upper bound on `t`/`n` in `ThresholdKeys::read`/`ThresholdParams::new` consistent with actual validator-set sizes, so deserialization cost is bounded.

```rust
// crypto/dkg/src/lib.rs — concept demonstration over e.g. Ristretto/Ed25519 ciphersuite C
// Build a serialized ThresholdKeys blob with t = n = 65535, Lagrange interpolation.
// Layout per ThresholdKeys::write: [u32 id_len][C::ID][u16 t][u16 n][u16 i][u8 interp=1]
//                                  [F secret_share][G x n verification_shares]

let t: u16 = u16::MAX;
let n: u16 = u16::MAX;
let mut blob = vec![];
blob.extend((C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes());
blob.extend(n.to_le_bytes());
blob.extend(1u16.to_le_bytes());      // i
blob.push(1);                          // Interpolation::Lagrange
blob.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. n {
    blob.extend(C::generator().to_bytes().as_ref()); // verification_shares
}

// ~4 MB of input triggers ~4.3e9 field muls + 65535 inversions inside
// ThresholdKeys::new -> interpolation_factor (crypto/dkg/src/lib.rs:226-248, 376-378)
let _keys = ThresholdKeys::<C>::read(&mut blob.as_slice());
```
Each of the 65535 `interpolation_factor` calls iterates all 65535 participants and inverts a denominator, so CPU time is quadratic in `t` while input size is linear in `n`.

```rust
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
```
