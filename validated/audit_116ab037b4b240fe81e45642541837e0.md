### Title
Missing referral-factor refresh on `unlock`/`forceUnLock`/`cancelUnlock` permanently inflates referral boost after MGP is withdrawn - (File: VLMGP.sol)

### Summary
`VLMGP._lock()` and `VLMGP.startUnlock()` both call `IReferralStorage(referralStorage).updateTotalFactor(user)` to recompute `userInfo.factor = sqrt(getUserTotalLocked(user))` and refresh the global `totalBoostFactor` denominator. `unlock()`, `forceUnLock()`, and `cancelUnlock()` — the three functions that actually change a user's locked balance to a lower (or zero) value — never call this refresh, so a user's stored referral `factor` and the shared `totalBoostFactor` denominator become permanently stale once MGP actually leaves the contract.

### Finding Description
In [1](#0-0)  and [2](#0-1) , `startUnlock()` and `_lock()` call `updateTotalFactor` to sync `userInfo.factor` in `ReferralStorage` with the live value returned by `getUserTotalLocked`. However, [3](#0-2)  shows `unlock()`, `cancelUnlock()`, and `forceUnLock()` perform the actual balance-reducing operations (`_unlock()`, transferring MGP back to the user) without any call into `referralStorage`.

`ReferralStorage.updateTotalFactor` ( [4](#0-3) ) is the only place where `userInfo.factor` is recomputed from `getUserTotalLocked` and where `totalBoostFactor` is adjusted. Since `unlock`/`forceUnLock`/`cancelUnlock` never invoke it, once a user (who has registered a referral code, i.e. `userInfo.myCode != 0`) actually withdraws their MGP via any of these three paths, `userInfo.factor` remains frozen at the value computed the last time `startUnlock`/`_lock` ran (i.e., reflecting a locked balance the user no longer has), and `totalBoostFactor` is never decremented to remove that user's stale contribution.

An unprivileged attacker only needs to:
1. Register a referral code in `ReferralStorage`.
2. Lock a modest amount of MGP (triggers `_lock` → `updateTotalFactor`, setting `factor = sqrt(amount)`).
3. `startUnlock` the full amount, wait out cooldown, then call `unlock()` (or `forceUnLock()` for an immediate exit) to withdraw all MGP.

After step 3, `getUserTotalLocked(attacker) == 0`, but `userInfo.factor` in `ReferralStorage` still reflects the old locked amount, and this stale value remains part of `totalBoostFactor` forever (no further lock/startUnlock call is required by the attacker).

### Impact Explanation
`_calBoosted` (referenced from `trigger()` in [5](#0-4) ) uses `userInfo.factor` relative to `totalBoostFactor` to size the extra "boosted" percentage a referrer earns on top of their base tier reward whenever any of their referees triggers a reward event. Because the attacker's `factor` never decays back down after they withdraw all locked MGP, they continue to receive a boosted referral reward share indefinitely, disproportionate to their actual (zero) stake — this dilutes/distorts rewards owed to other legitimate referrers who still hold locked MGP, matching the "Theft of unclaimed yield" impact class (referral reward yield is misallocated toward a user with no real backing stake).

### Likelihood Explanation
This requires no privileged role — any EOA can register a referral code, lock a small amount of MGP, and then unlock/forceUnLock it through the normal, unprivileged flow. It is fully repeatable and capital-light: the attacker only needs to temporarily hold enough MGP to pump their `factor`, then withdraw it. The bug is a straightforward code-path omission (three of five state-changing entrypoints skip the refresh call that the other two perform), so it will trigger deterministically on every unlock/forceUnLock/cancelUnlock by any referral-code holder.

### Recommendation
Add `if (referralStorage != address(0)) IReferralStorage(referralStorage).updateTotalFactor(msg.sender);` to `unlock()`, `forceUnLock()`, and `cancelUnlock()` in `VLMGP.sol`, mirroring the call already present in `startUnlock()` and `_lock()`, so `userInfo.factor` and `totalBoostFactor` are refreshed on every path that changes a user's locked balance.

### Proof of Concept
Hardhat test plan:
1. Deploy `VLMGP`, `ReferralStorage`, `MasterMagpie` mocks/fixtures with `referralStorage` wired into `VLMGP`.
2. Attacker registers a referral code via `ReferralStorage.setCode` (or equivalent) so `userInfo.myCode != 0`.
3. Attacker calls `VLMGP.lock`/deposit path to lock `X` MGP → assert `ReferralStorage.userInfos[attacker].factor == sqrt(X)` and `totalBoostFactor` includes it.
4. Attacker calls `startUnlock(X)`, waits `coolDownInSecs`, then calls `forceUnLock` (or `unlock` after cooldown) to withdraw all `X` MGP → assert `VLMGP.getUserTotalLocked(attacker) == 0`.
5. Assert `ReferralStorage.userInfos[attacker].factor` is unchanged from step 3 (still `sqrt(X)`, not `0`), and `totalBoostFactor` still includes that stale factor.
6. Trigger a referral reward event (`ReferralStorage.trigger`) for a referee of the attacker and confirm the attacker still receives a boosted percentage based on the stale factor, despite having zero locked MGP — demonstrating unclaimed-yield misallocation.
