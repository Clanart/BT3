### Title
BIP-340 signatures are emitted without negating the secret share for odd-Y group keys, producing signatures no Bitcoin verifier accepts - (File: networks/bitcoin/src/crypto.rs)

### Summary
The `Schnorr` `Algorithm` implementation for `Secp256k1` in `networks/bitcoin/src/crypto.rs` handles BIP-340 parity for the nonce point `R` (negating the challenge in `Hram::hram` and negating the final `s` in `verify`), but never accounts for the parity of the group key `A` / `X`. BIP-340 verifiers always lift the x-only public key to the *even-Y* point. When the aggregate FROST group key (or the TapTweak-offset signing key) has odd Y, the produced `(R_x, s)` fails verification against the even-Y lifted key, so any output controlled by that key is unspendable. Analogous to CVE-2018-1000022 (a signing action produces an output the requester did not intend/cannot use), an unprivileged party who causes funds to be sent to the threshold wallet's script pubkey gets outputs reported as received that the federation can never sign for.

### Finding Description
- `Hram::hram` computes the BIP-340 challenge `c = H(R_x, A_x, m)` and negates it only when `R` has odd Y (`conditional_select(&c, &-c, needs_negation(R))`). There is no adjustment for `A`'s parity. [1](#0-0) 
- `sign_share` delegates to the generic FROST Schnorr share `k_i + c·λ_i·x_i` using `params.secret_share()` unmodified — the share is never conditionally negated when the group key `X = Σ λ_i x_i G` is odd-Y. [2](#0-1) 
- `verify` corrects only `R` parity: it conditionally replaces `s` with `-s` when `sig.R` is odd-Y and emits the 64-byte BIP-340 signature. Nothing negates for key parity. [3](#0-2) 

Verification math: honest signing yields `s = k + c·x` where `X = xG`. A BIP-340 verifier computes `R' = sG − e·P` where `P` is the even-Y lift of `x(X)`, i.e. `P = −X` when `X` is odd. If `X` is odd-Y, the signature satisfies `sG = R + cX`, so `R' = R + 2cX ≠ ±R`, and every signature fails. With `s` negated for odd `R`, the same discrepancy remains. Correct BIP-340 threshold implementations (e.g., MuSig2/FROST-taproot) must negate each signer's effective secret contribution (equivalently use `−x`) when the aggregate/tweaked key is odd-Y; this implementation has no such correction.

### Impact Explanation
Any Bitcoin output whose spend path requires a BIP-340 signature from an odd-Y aggregate or tweaked key is permanently unspendable: the federation will run the full FROST protocol, produce a "valid" 64-byte signature per this code, and have it rejected by every Bitcoin node. An attacker needs only to send Bitcoin to the wallet's published script pubkey — a public input — to lock funds under a key the code cannot correctly sign for. This is a High-severity loss-of-funds condition ("funds reported received that are not spendable") triggered with ~50% probability per key/tweak whenever the effective signing key is odd-Y, unless parity normalization is applied by the caller (see caveat).

### Likelihood Explanation
The parity of an x-only key is random (~1/2) unless upstream code (DKG `promote`/offset construction in `networks/bitcoin/src/wallet/`) forces the effective signing key to even-Y before `sign_share`. I could not confirm within the indexed scope whether `ThresholdKeys`/`ThresholdView` offsets or the wallet's TapTweak construction normalize parity; `crypto.rs` itself (`x_only`, `needs_negation`, `Hram`, `sign_share`, `verify`) demonstrably performs nonce parity handling only, so the defect exists in this crate's algorithm logic. If callers always pre-negate, the finding degrades to a latent trap; if any reachable key is odd-Y, every spend fails deterministically.

### Recommendation
In `sign_share` (or in `ThresholdView` construction for Bitcoin), conditionally negate the secret-share contribution when `needs_negation(&params.group_key())` is true — i.e. compute the share as `k_i + c·λ_i·(−x_i)` for odd-Y `X` — so the signature verifies against the even-Y lift used by BIP-340. Equivalently, normalize keys to even-Y at key-aggregation/offset time and assert the invariant in `Algorithm::verify`/`sign_share`. Add a regression test that completes a FROST signature under an odd-Y group key and checks it with `bitcoin::secp256k1`/BIP-340 verification.

### Proof of Concept
1. Run DKG producing `ThresholdKeys<Secp256k1>` whose `group_key()` has odd Y (resample until `needs_negation(group_key)` is true).
2. Build `Schnorr::new()` `AlgorithmMachine`s for a threshold signing set and run preprocess → `sign(preprocesses, msg)` → `complete`.
3. `verify` returns a `[u8; 64]` signature; feed it and `x_only(group_key)` to a BIP-340 verifier (`secp256k1::schnorr::verify` or `bitcoin`'s `SchnorrSig`): it fails, because the verifier uses the even-Y lift `−X` while the signature embeds `+c·x` for `X = xG` odd. The parity flip of `s` for `R` (`crypto.rs:146`) cannot compensate for the un-negated `x`.
4. Repeat with an even-Y key: signature verifies, confirming the defect is specifically the missing key-parity negation, not general Schnorr correctness.

Note on uncertainty: whether the odd-Y case is reachable in production depends on key normalization in `wallet/mod.rs`/`send.rs` and the DKG offset path, which I could not fully verify within scope. The defect in the `Algorithm` formula itself is confirmed by the cited lines.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
