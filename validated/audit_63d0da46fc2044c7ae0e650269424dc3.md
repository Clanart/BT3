### Title
Webhook HMAC verification does not cover the `X-Shopify-Shop-Domain` header, enabling cross-shop webhook replay - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
This is the same bug class as the external H-14 finding: a signature/HMAC scheme is computed over a subset of the data that is actually acted upon, omitting a routing/tenant-identifying field. In `shopify_app`, `ShopifyApp::WebhookVerification#verify_request` computes the HMAC over `request.raw_post` only, while the shop identifier used to route and attribute the webhook (`shop_domain`, read from the `X-Shopify-Shop-Domain` header) is never included in that HMAC. Any request with a valid `(body, hmac)` pair — including one captured from a legitimate webhook delivered to the attacker's own shop — can be replayed with an arbitrary `X-Shopify-Shop-Domain` header and will still pass verification, exactly as the `from_chain` field could be omitted from `verifySignature` while still being trusted downstream in `processCrossChainCallback`.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes and compares the HMAC using only the request body: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` calls this with `request.raw_post` as the only signed input: [2](#0-1) 

The same module exposes `shop_domain`, sourced directly from the unauthenticated `X-Shopify-Shop-Domain` header: [3](#0-2) 

The gem's own documentation instructs app developers to build custom webhook controllers that dispatch background jobs keyed by this unauthenticated `shop_domain` value, alongside the HMAC-verified body: [4](#0-3) 

Because `shop_domain` (the value that determines *which tenant's* data this webhook belongs to) is never part of the cryptographic message that `hmac_valid?` checks, it is fully attacker-controllable as long as the attacker can obtain any one valid `(raw_post, hmac)` pair — for example by installing the app on their own shop and capturing a real webhook delivery. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value naming a victim merchant. The verification step (`verify_request`) will pass, and the downstream job will process/store the replayed payload under the victim shop's identity — a direct analog of `from_handler`/`from_chain` being trusted post-signature-check in the Solidity finding.

The built-in `ShopifyApp::WebhooksController` delegates to `ShopifyAPI::Webhooks::Registry.process` with `headers: request.headers.to_h`, so the same unauthenticated header is passed along as the source of the `shop` value used for job routing: [5](#0-4) 

### Impact Explanation
An attacker who controls (or can install the app on) any shop can capture one legitimate webhook body + HMAC pair from their own shop and replay it against the app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to name an arbitrary, unrelated victim shop. Because the HMAC never covers this header, the request passes verification, and any consumer that keys job/data processing off `shop_domain` (as the gem's own documentation instructs) will attribute/process the replayed payload as belonging to the victim shop — a cross-shop data confusion/injection, analogous to how the original H-14 issue let attackers sabotage cross-chain transaction state by supplying an unauthenticated routing field.

### Likelihood Explanation
Likelihood is High for apps that follow the documented custom-webhook pattern (or any downstream consumer relying on `shop_domain` from `WebhookVerification`) since: (1) the attacker only needs their own installed shop to generate one valid signed payload, (2) no secret knowledge beyond what's obtainable from a self-owned installation is required, and (3) the vulnerable header-trust pattern is explicitly documented and recommended by the gem itself.

### Recommendation
Bind the shop identity to the signed message rather than trusting an unauthenticated header: verify that the `shop_domain`/`shop` value used for routing matches a shop value embedded in and verified as part of the webhook body (or otherwise cryptographically tie the header to the signature, e.g. include it in the HMAC input), and reject requests where the two disagree. Update `hmac_valid?`/`verify_request` and the documented custom-controller pattern in `docs/shopify_app/webhooks.md` accordingly so `shop_domain` can no longer be supplied independently of the signed payload.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the raw request body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both are legitimately signed by Shopify's shared secret for the attacker's own shop).
2. Send a POST request to the app's webhook endpoint (e.g., `/webhooks/<topic>` handled by `WebhooksController` or a custom controller including `ShopifyApp::WebhookVerification`) with body `B`, header `X-Shopify-Hmac-Sha256: H`, but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` calls `hmac_valid?(request.raw_post)`, which only checks `B` against `H` — this passes because `B`/`H` were never tied to any shop domain.
4. The controller/job (per `docs/shopify_app/webhooks.md`'s documented pattern, e.g. `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`) processes the payload attributed to `victim-shop.myshopify.com`, even though the actual signed content originated from the attacker's own shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
