### Title
Attacker-controlled Git host can spoof `WWW-Authenticate: realm="GitHub"` to trigger OAuth flow (and client_secret exchange) against an arbitrary server - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
When Git needs credentials for a remote (including submodule remotes discovered during clone/fetch), Desktop's credential-helper trampoline decides whether the target host is a "GitHub-like" host (github.com/GHE) or a "generic" Git host. Part of that decision trusts a `WWW-Authenticate` header value returned by the remote server itself, without validating that the host is actually a known/trusted GitHub domain.

### Finding Description
`getEndpointKind` in [1](#0-0)  first checks known domains (`isGist`, `isDotCom`, `isGHE`), then falls back to inspecting `wwwauth[...]` credential fields captured from the server's HTTP response: if the value contains `realm="GitHub"`, the endpoint is classified as `'enterprise'` regardless of the actual hostname. This header is fully attacker-controlled because it is the literal value of the `WWW-Authenticate` response header sent by whatever server Git connected to.

That classification feeds `getCredential` in [2](#0-1) : if the kind is not `'generic'` and there is no existing account for that endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`.

`promptForGitHubSignIn`, in [3](#0-2) , takes the raw `origin` of the attacker-controlled endpoint and, since the hostname isn't `github.com`, calls `dispatcher.beginEnterpriseSignIn(cb)` followed by `dispatcher.setSignInEndpoint(origin)` — driving the sign-in store directly to the `Authentication` step using the attacker's origin, bypassing the normal manual "Enterprise address" entry step (`EndpointEntry`, see [4](#0-3) ) where a user might otherwise notice a suspicious URL.

If the user proceeds through the resulting sign-in popup (presented as "Git requesting credentials to access `<url>`", see [5](#0-4) ), the OAuth authorization URL is built via `getOAuthAuthorizationURL(endpoint, state)` and the resulting code is exchanged with `requestOAuthToken(endpoint, code)`, both in [6](#0-5) . `requestOAuthToken` POSTs `client_id` and the application's `client_secret` directly to `<attacker-endpoint>/login/oauth/access_token`, handing the attacker the Desktop app's OAuth `client_secret` and the authorization `code`.

The root cause is that `getEndpointKind` uses server-supplied, attacker-controllable data (`WWW-Authenticate` realm) as a trust signal to decide the endpoint is a legitimate GitHub host, instead of relying solely on validated domain matching (`isDotCom`/`isGHE`) or an already-established account relationship.

### Impact Explanation
An attacker who controls (or fully controls the responses of) a Git remote — reachable through a top-level remote URL or, more stealthily, a `.gitmodules` submodule URL embedded in an otherwise innocuous public repository that the victim clones or fetches with `--recursive` (see `updateSubmodulesAfterOperation`/`clone` in [7](#0-6)  and [8](#0-7) ) — can cause Desktop to treat their server as a trusted GitHub Enterprise host. This drives the user into an OAuth sign-in flow targeting the attacker's server and leaks the Desktop client's `client_id`/`client_secret` and the OAuth authorization code to the attacker, and can also result in the user being socially engineered into entering GitHub credentials/2FA against what looks like a legitimate "Sign in to GitHub" dialog pointed at the attacker's host (unauthorized OAuth/account-binding flow against an untrusted server).

### Likelihood Explanation
The attacker-controlled input is limited to the `WWW-Authenticate` header of an HTTP 401 response and the remote/submodule URL, both fully within attacker control without requiring local access, admin rights, or prior compromise. It does require the user to interact with the resulting sign-in dialog (click through), which is a plausible normal action since it looks like a standard "authenticate to continue" prompt triggered automatically by the fetch/clone/submodule-update operation. Because Desktop routes straight to the `Authentication` step and shows `credentialHelperUrl` rather than requiring the user to type the enterprise address themselves, the usual human checkpoint for verifying the enterprise URL is weakened.

### Recommendation
Do not trust `WWW-Authenticate` realm values as a signal to classify a host as GitHub/Enterprise. Base the `'enterprise'`/`'github.com'` classification purely on validated domain matching (`isDotCom`, `isGHE`, known configured GHE endpoints) or on an explicit, real network round-trip probe (`isGitHubHost`) rather than a client-supplied claim embedded in a header. At minimum, before initiating the OAuth flow via `promptForGitHubSignIn`, require the user to confirm/enter the enterprise host explicitly (reuse the `EndpointEntry` step) rather than auto-populating and jumping directly to `Authentication` with an unverified attacker-controlled origin.

### Proof of Concept
1. Attacker hosts a public GitHub repository whose `.gitmodules` contains a submodule remote pointing to `https://attacker.example/repo.git`.
2. Attacker's server, when Git attempts HTTPS auth against it (returns 401), sends `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim clones the attacker's repo with submodules (or Desktop's own `--recursive` clone), triggering `git submodule update --init --recursive`, which contacts `attacker.example`.
4. Desktop's trampoline `getCredential` → `getEndpointKind` sees the spoofed `wwwauth[...]` header, classifies `attacker.example` as `'enterprise'` (see [9](#0-8) ).
5. Since no account exists for `attacker.example`, `ui.promptForGitHubSignIn('https://attacker.example/...')` is invoked, calling `dispatcher.setSignInEndpoint('https://attacker.example')` directly (skipping manual endpoint entry) and showing a "Git requesting credentials to access attacker.example" sign-in dialog.
6. If the victim proceeds, `requestOAuthToken` POSTs the Desktop app's `client_id`/`client_secret` and the OAuth code to `https://attacker.example/login/oauth/access_token`, which the attacker fully controls and can log/exfiltrate [10](#0-9) .

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
