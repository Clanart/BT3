Based on my investigation, I found a concrete, locally-provable analog of the fee-on-transfer bug in the `IntentGatewayV2`/`ExtrinsicIntents` fill path.

### Title
Fee-on-transfer output tokens let a solver mark an order "filled" and release full source-chain escrow while the beneficiary receives less than the promised output amount - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2`'s intent-placement path (`placeOrder`) is fee-on-transfer aware: it measures `balanceOf` before/after each `safeTransferFrom` and stores the *actually received* amount as escrow [1](#0-0) . However, the corresponding output/fill path in `ExtrinsicIntents.sol` (part of the same intents system, invoked from `fillOrder`) does the opposite: it transfers the *nominal* `totalRequired` amount to the beneficiary via `safeTransferFrom`, records `outputFills[i].amount = totalRequired` and immediately proceeds to redeem/settle the order, without verifying the beneficiary actually received `totalRequired` [2](#0-1) .

### Finding Description
This is the exact inversion described in the Slingshot report: the amount that is *recorded/committed as delivered* (`totalRequired`, used to build `outputFills` and the `RedeemEscrow` dispatch) is computed and checked *before* the real token transfer's fee-on-transfer effect is realized, rather than being derived from the beneficiary's actual balance delta. If `token` in the output leg is a fee-on-transfer/deflationary ERC20, `beneficiary` receives strictly less than `totalRequired`, yet:
- `outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired})` still reports full delivery [3](#0-2) .
- The `RedeemEscrow` withdrawal request dispatched to the source chain is built from `order.inputs`, unconditionally granting the solver the full escrowed input amount for the order [4](#0-3) .
- The order is marked filled and the `OrderFilled` event reports full outputs delivered [5](#0-4) .

This contrasts directly with the input-side pattern in the same protocol, which the developers clearly recognized needed balance-delta accounting for fee-on-transfer tokens [6](#0-5) , proving the fix pattern was known but not applied symmetrically to the output/settlement leg.

### Impact Explanation
A solver can select a fee-on-transfer token as the output asset (if the order or gateway configuration permits arbitrary output tokens), fill the order, and claim the entirety of the user's escrowed input on the source chain via `RedeemEscrow`, while the user (beneficiary) receives less than `order.output.assets[i].amount` promised in the order. This is a direct "wrong beneficiary amount" / value-leakage bug matching the required impact class (loss of funds to the intended beneficiary, order settled as fully filled when it was not).

### Likelihood Explanation
The path is reachable by any solver calling the public `fillOrder` entrypoint with attacker-chosen output token — no privileged, relayer, or governance role is required. The likelihood is bounded by whether output tokens are restricted to a vetted allowlist elsewhere in order validation; I was not able to confirm within the indexed code whether such an allowlist exists for output tokens (only for the token being escrowed on the input side was balance-delta protection found).

### Recommendation
Mirror the input-side protection: after transferring output tokens to `beneficiary`, measure `balanceOf(beneficiary)` before/after the transfer and use the actual received delta (not `totalRequired`) both for the `outputFills` record and to validate against `order.output.assets[i].amount` before dispatching the `RedeemEscrow` request that pays the solver.

### Proof of Concept
1. User places a cross-chain order requiring `outputToken` amount `X` to `beneficiary`.
2. `outputToken` is a fee-on-transfer ERC20 (e.g. 5% burn on transfer).
3. Solver calls `fillOrder`; `ExtrinsicIntents.sol` executes `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired)` [7](#0-6) , but `beneficiary` only receives `totalRequired * 0.95`.
4. `outputFills[i].amount` is still recorded as `totalRequired` [8](#0-7) , and the `RedeemEscrow` message pays the solver the full input escrow on the source chain [4](#0-3) .
5. User receives less than the agreed output amount while the solver is paid in full, and the order is marked filled, preventing recovery.
