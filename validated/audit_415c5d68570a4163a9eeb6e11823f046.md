### Title
Pointer reverse-registry keyed only by raw 20-byte address with no type scope, allowing cross-pointer-type collision/confusion — ([File: x/evm/keeper/pointer.go])

### Summary
The CW↔EVM pointer subsystem stores every reverse-lookup entry (native→ERC, CW20→ERC20, CW721→ERC721, CW1155→ERC1155, and the three ERC→CW "wrapper" directions) in a single shared KV namespace keyed only by `types.PointerReverseRegistryKey(addr)` — a raw 20-byte `common.Address`, with no discriminator for which of the seven pointer categories the entry belongs to. This mirrors the root cause described in the Blocky DNSSEC advisory: a security-relevant lookup/cache is scoped by an identifier (domain name / address) that is not sufficiently specific to the trust decision being made (proof purpose / pointer type), so state written for one purpose is silently reused for another.

### Finding Description
`x/evm/keeper/pointer.go` writes the reverse-registry entry from all seven `SetXXXPointer` paths into the identical prefix `types.PointerReverseRegistryKey(addr)`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

For the "ERC → native/CW" directions the key is the raw EVM address; for the "CW → ERC" wrapper directions the key is `common.BytesToAddress([]byte(bech32Addr))` — i.e. the first/only 20 bytes of the Sei account address, cast the same way Sei already uses for direct EVM↔Sei address casting elsewhere in the codebase (`x/evm/keeper/address.go` `CanAddressReceive`). Both address spaces (raw EVM addresses and cast Sei bech32 addresses) are 20 bytes, and both `evmAddressIsPointer` and `cwAddressIsPointer` — the guards that enforce the "cannot create a pointer to a pointer" invariant — read from that same unscoped keyspace: [5](#0-4) 

`GetPointerInfo`/`GetAnyPointerInfo` then just walk version numbers 0..max under that key and return whatever is stored, with no verification that the stored entry actually belongs to the pointer category being queried: [6](#0-5) [7](#0-6) 

This is structurally the same defect class as the Blocky bug: a trust/identity decision ("is this address a pointer, and if so of what and to what") is cached/stored under a key (bare address) that is broader than the scope of the fact being recorded (pointer direction/type), so a write made for one purpose (e.g., registering a CW20 wrapper for an ERC20 token) can satisfy, shadow, or be misread by a check made for an entirely different purpose (e.g., the "is this a native/CW20/CW721/CW1155 pointer" checks, or the reverse pointee lookups `GetCW20Pointee`/`GetCW721Pointee`/`GetCW1155Pointee`/`GetNativePointee`/`GetERC20Pointee`/`GetERC721Pointee`/`GetERC1155Pointee`, `GetAnyPointeeInfo`).

### Impact Explanation
If an attacker can cause the 20-byte key derived from an address/contract they control to collide with (or be written before/after) the reverse-registry key of an unrelated, legitimately-registered pointer of a *different* category, the following can occur:
- The `ErrorPointerToPointerNotAllowed` invariant (`evmAddressIsPointer`/`cwAddressIsPointer`) can be bypassed or falsely triggered, since it only checks "does any entry exist at this address" rather than "does an entry of the correct type exist." Bypassing this invariant is exactly the case the check exists to prevent: chaining pointers (pointer-to-a-pointer), which the pointer-precompile tests (`x/evm/keeper/pointer_test.go`) explicitly assert must never be allowed because it breaks the 1:1 accounting between native/CW/EVM token representations.
- Reverse pointee resolution (`GetAnyPointeeInfo`, `GetCW20Pointee`, etc., consumed by `x/evm/keeper/grpc_query.go` and `evmrpc/block.go`) can report the wrong underlying token/contract for a given pointer address, which is the on-chain source of truth other integrations (wallets, bridges, and any contract logic that trusts the pointer registry to route CW↔EVM asset representation) use to decide which token a pointer actually represents.

Because pointer registration is a normal, permissionless, unprivileged transaction path (`RegisterPointer` / the `pointer` precompile, reachable by any contract deployer or EVM caller — see `x/evm/keeper/msg_server_test.go` `TestRegisterPointer`/`TestAssociateContractAddress`), an attacker does not need special privileges to attempt to seed a colliding registry entry.

### Likelihood Explanation
Exploitability hinges on an attacker's ability to control the 20-byte address used as the reverse-registry key for a *different* pointer category than an existing legitimate entry (e.g., choosing/instantiating a CW20/CW721/CW1155 contract address, or controlling an EVM address, whose bytes match an already-registered pointer/pointee of another type), and on the order/overwrite semantics of `setPointerInfo`/`GetPointerInfo` across types not currently being checked anywhere in the codebase. I was not able to fully verify, within the scope of this review, exactly how easily such a same-address, cross-type registration can be forced in practice (e.g., whether wasm contract address allocation or `instantiate2` salts give an attacker enough control over the resulting bech32 address to target a specific 20-byte value), so likelihood should be treated as **uncertain/moderate** pending a directed proof-of-concept — this is presented as a structural root-cause analog to the reported bug class, not a confirmed working exploit.

### Recommendation
Include the pointer category/direction (native, CW20, CW721, CW1155, and which direction) as part of the reverse-registry key, e.g. `PointerReverseRegistryKey(pointerType, addr)`, so that `evmAddressIsPointer`, `cwAddressIsPointer`, `GetAnyPointerInfo`, and all `GetXPointee` lookups can only match entries written for the same pointer category, eliminating the possibility of one registration's proof satisfying an unrelated category's check — analogous to scoping the DNSSEC validation cache by proof purpose/class rather than bare name.

### Proof of Concept
Not independently reproduced. The analysis is based on static review of `x/evm/keeper/pointer.go` showing that all seven pointer-registration paths write to the identical `PointerReverseRegistryKey(addr)` keyspace and that `evmAddressIsPointer`/`cwAddressIsPointer`/`GetAnyPointerInfo` do not check pointer type before trusting a hit at that key. A concrete exploit would require constructing (or finding) a CW contract address / EVM address whose 20 bytes collide with an existing pointer/pointee entry of a different category and then observing that `RegisterPointer`, the `pointer`/`pointerview` precompiles, or the gRPC pointer queries return/accept cross-type results.

	if semver.Compare(ctx.ClosestUpgradeName(), "v6.5") < 0 {
		iter := store.ReverseIterator(nil, nil)
		defer func() { _ = iter.Close() }()
		if iter.Valid() {
			return iter.Value(), binary.BigEndian.Uint16(iter.Key()), true
		}
