## Analysis

`storeCredential()` implements the `store` verb of the git credential-helper protocol: whenever `getEndpointKind()` classifies the target as `'generic'`, it writes the supplied `username`/`password` straight into the OS keychain via `setGenericCredential()`, with no additional confirmation step: [1](#0-0) 

That call is only ever gated by two things: (1) `TrampolineServer.processCommand()` checking that the `trampolineToken` is a currently-live token, and (2) `getEndpointKind()` returning `'generic'`: [2](#0-1) 

`isValidTrampolineToken()` only checks *existence* of the token in a set — it carries no binding to a specific command, a specific git invocation, or a specific verb (`get` vs `store` vs `erase`), and it stays valid for the whole duration of the underlying git operation: [3](#0-2) 

The token (and the trampoline server's TCP port) are delivered to the spawned git process as plain environment variables, `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`: [4](#0-3) 

Git hooks run as **child processes of git**, so by default they inherit the parent process environment — including `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` — unless the optional "hooks environment interception" feature is active. That feature explicitly proxies hook execution and only forwards `GIT_`/`GITHEAD_`-prefixed variables to the real hook, filtering out everything else (which happens to exclude the trampoline vars since they don't match those prefixes): [5](#0-4) [6](#0-5) 

But that sanitizing proxy only engages when `opts?.interceptHooks && getHooksEnvEnabled()` are both true; otherwise `withHooksEnv()` short-circuits to `fn(opts?.env)`, i.e. hooks run with the git process's raw environment (trampoline token included): [7](#0-6) 

Combining these facts: a repository-supplied hook (e.g. `pre-push`, `post-checkout`, `pre-commit`) that runs during a normal GitHub Desktop-initiated git operation can read `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` from its own environment (when hooks-environment interception isn't engaged for that operation/config), open a raw socket to the trampoline server, and speak the trampoline netstring protocol directly — sending a `CREDENTIALHELPER` command with `parameters = ['store']` and a crafted `stdin` credential blob for any host that `getEndpointKind()` classifies as `'generic'` (any non-GitHub HTTPS/HTTP remote, or one whose `WWW-Authenticate` realm matches GitLab/Gitea/Bitbucket). Since the token/handler make no distinction between "git itself, after a real successful auth" and "any process holding the token," `storeCredential()` will silently overwrite the OS keychain entry for that host with attacker-chosen values — no UI prompt, no confirmation that any authentication actually occurred.

## Title
Trampoline credential-store command lacks provenance binding, allowing malicious repo hooks to silently overwrite generic-host credentials - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
`storeCredential()` trusts any holder of a live trampoline token to invoke the `store` verb and persist arbitrary username/password values into the OS credential store for `'generic'` (non-GitHub) hosts, with no check that the command was emitted by git following a genuine, successful authentication.

## Finding Description
`getEndpointKind()` classifies a URL as `generic` for any non-GitHub HTTPS/HTTP remote [8](#0-7) . `storeCredential()` then unconditionally forwards `cred.get('username')`/`cred.get('password')` to `setGenericCredential()` [9](#0-8) . The only gate is `isValidTrampolineToken()`, which merely checks token liveness, not the caller's identity or that a real auth prompt/success preceded the call [2](#0-1) . The trampoline token is exposed to the git process (and, absent active hooks-environment sanitization, to any hook child process it spawns) via plain env vars [4](#0-3) , and the sanitizing proxy that would strip these vars only runs when both `interceptHooks` and `getHooksEnvEnabled()` are true [10](#0-9) .

## Impact Explanation
A malicious repository hook can silently corrupt the OS-level generic credential entry for a host the user legitimately uses, without any user-visible prompt. Depending on how the attacker crafts the injected credentials, this can cause the victim's subsequent `git push`/`pull` operations against that host to send attacker-chosen credentials, breaking authentication or, if the attacker controls the resulting flow, redirecting stored secrets. This matches the "silent corruption" and "credential store" impact categories in scope.

## Likelihood Explanation
Requires the victim to clone/fetch a repository with a hook script and to have GitHub Desktop's hooks-environment-interception protection either disabled or not applicable to the triggering operation, since when that feature is active the trampoline env vars are stripped before reaching the real hook. I was not able to confirm the default state of `getHooksEnvEnabled()` (whether the interception is on-by-default) or which of GitHub Desktop's git operations set `interceptHooks: true`, from the available code — this materially affects how broadly exploitable the issue currently is.

## Recommendation
Bind trampoline `store`/`erase` commands to a specific, previously-issued `get` credential request for the same endpoint/session (e.g. require that a corresponding successful `get` occurred for that URL within the same token's lifetime before honoring `store`), rather than trusting any process holding a live token. Additionally, ensure the trampoline token/port are always excluded from any environment inherited by hook subprocesses regardless of the hooks-environment-interception setting.

## Proof of Concept
1. Create a repository containing a `post-checkout` (or `pre-push`) hook that reads `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` from its own process environment.
2. From the hook, open a TCP socket to `127.0.0.1:$DESKTOP_PORT` and send a trampoline `CREDENTIALHELPER` command with `parameters=['store']`, `trampolineToken=$DESKTOP_TRAMPOLINE_TOKEN`, and stdin containing `url=https://gitlab.example.com`, `username=attacker`, `password=EXACT_VALUE`.
3. Have the victim clone/checkout the repo through GitHub Desktop, triggering the hook.
4. Inspect the OS keychain entry for `gitlab.example.com` and confirm it was overwritten with the attacker-supplied values without any prompt.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
