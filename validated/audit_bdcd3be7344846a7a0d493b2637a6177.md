### Title
`update_access_scopes?` scope-change check keys on unverified `params[:shop]` instead of the authenticated session shop - ([File: lib/shopify_app/access_scopes/shop_strategy.rb])

### Summary
`ShopAccessScopesVerification#current_shopify_domain` derives the shop used for scope-mismatch detection purely from `params[:shop]` (after `ShopifyApp::Utils.sanitize_shop_domain` format-normalizes it), and `ShopStrategy.update_access_scopes?` simply looks up whatever session matches that domain and diffs its `scope` against configured scopes. Neither step ties the compared shop back to the shop actually authenticated for the current request/session, so an attacker who controls the `shop` query param can point the check at any installed shop whose stored scope happens to already match configuration.

### Finding Description
The reauth gate is:
`app/controllers/concerns/shopify_app/shop_access_scopes_verification.rb`
```
def scopes_mismatch?
  ShopifyApp.configuration.shop_access_scopes_strategy.update_access_scopes?(current_shopify_domain)
end

def current_shopify_domain
  return if params[:shop].blank?
  ShopifyApp::Utils.sanitize_shop_domain(params[:shop])
end
``` [1](#0-0) 

and the comparison itself:
```
def update_access_scopes?(shop_domain)
  shop_access_scopes = shop_access_scopes(shop_domain)
  configuration_access_scopes != shop_access_scopes
end

def shop_access_scopes(shop_domain)
  ShopifyApp::SessionRepository.retrieve_shop_session_by_shopify_domain(shop_domain)&.scope
end
``` [2](#0-1) 

`current_shopify_domain` never cross-checks the supplied `shop` against the shop identified by the request's actual authenticated context (session cookie / ID token `dest` claim); it is purely a format-sanitized copy of the raw `params[:shop]` value. `sanitize_shop_domain` (`lib/shopify_app/utils.rb`) only validates that the value resolves to a recognized `*.myshopify.com`/trusted-domain host after `downcase`/`strip` normalization — it performs no session/identity binding. [3](#0-2) 

Because `retrieve_shop_session_by_shopify_domain` is keyed by whatever shop string is passed in, an attacker who supplies a `shop` param naming a different, already-reauthorized installed shop (one whose stored session `scope` matches current configuration) causes `update_access_scopes?` to return `false`, suppressing the `redirect_to(shop_login)` / `redirect_for_embedded` reauth flow in `login_on_scope_changes` for the request — even though the shop actually driving the request may hold a session with stale/insufficient scopes. [4](#0-3) 

Regarding the encoding-fuzzing angle specifically: `sanitize_shop_domain` normalizes case (`downcase`/`strip`) and strictly requires the host to resolve, via `Addressable::URI`, to one of a fixed `TRUSTED_SHOPIFY_DOMAINS` suffixes (`myshopify.com`, `shopify.com`, etc.), returning `nil` for anything that doesn't match. [5](#0-4) 
This defeats naive unicode/punycode/case/delimiter tricks intended to make two *different* shop strings sanitize to the *same* canonical value or to smuggle an untrusted host through as trusted — no such variant is accepted as "trusted" outside the fixed suffix list. The exploitable gap is not an encoding-normalization bug but the architectural one: the check trusts *any* syntactically-valid, differently-named `shop` param (pointing at a genuinely different, attacker-choosable installed shop) rather than requiring it to equal the shop verified by the authenticating session/ID token for the current request.

### Impact Explanation
This allows suppression of a scope-reauthorization redirect that should occur for the shop truly driving the request, by supplying a `shop` param that resolves to a different installed shop whose session scope happens to satisfy the configured scopes. This matches the "scope reauthorization bypass" class: the app will continue serving the request without prompting the merchant/session to re-consent to updated scopes, even though the actual session backing that request may lack them.

### Likelihood Explanation
Exploitability depends on whether the host application's authentication before_actions (session cookie validation / ID token `dest` verification in controllers like `AuthenticatedController`, `EnsureInstalled`, `WithShopifyIdToken`) independently bind `params[:shop]` to the authenticated shop before `login_on_scope_changes` runs. I was not able to fully trace `authenticated_controller.rb`'s before_action ordering and whether it enforces `params[:shop] == authenticated shop` prior to this concern executing, due to running out of tool iterations. If such a binding check exists and runs earlier in the filter chain, this specific gate becomes unreachable with a mismatched `shop`, and the bypass is neutralized upstream.

### Recommendation
Have `scopes_mismatch?` derive the shop from the verified/authenticated session (e.g., the shop already established by `EnsureHasSession`/`current_shopify_session`/ID token `dest`) rather than raw `params[:shop]`, or assert equality between `params[:shop]` (sanitized) and the authenticated shop before using it in `update_access_scopes?`.

### Proof of Concept
Could not be fully validated as a standalone reproducible test within the available exploration — confirming exploitability requires tracing the exact before_action chain of `AuthenticatedController` and related concerns (`EnsureInstalled`, `WithShopifyIdToken`, `EnsureHasSession`) to determine whether `params[:shop]` is bound to the authenticated session shop earlier in the request lifecycle. This should be verified with an integration test that authenticates as Shop A (stale scope) but sends `shop=shop-b.myshopify.com` (Shop B, scope matching config) and asserts whether `login_on_scope_changes` still redirects.

      def sanitize_shop_domain(shop_domain)
        uri = uri_from_shop_domain(shop_domain)
        return if uri.nil? || uri.host.nil?

        trusted_domains.each do |trusted_domain|
          no_shop_name_in_subdomain = uri.host == trusted_domain
          from_trusted_domain = trusted_domain == uri.domain

          return myshopify_domain_from_unified_admin(uri) if unified_admin?(uri) && from_trusted_domain
          return nil if no_shop_name_in_subdomain || uri.host&.empty?
          return uri.host if from_trusted_domain
        end
        nil
      end
