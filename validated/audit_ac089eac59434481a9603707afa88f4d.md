### Title
`ThresholdKeys::read` allocates attacker-sized vector before validating input length - (File: crypto/dkg/src/lib.rs)

### Summary
The NIP-98 advisory describes a parser that performs allocation and parse work proportional to an unauthenticated, attacker-sized input before any validation. The same pattern exists in `ThresholdKeys::read`: after reading only the curve ID, `t`, `n`, and `i` fields (≈15 bytes of input), it trusts the attacker-controlled `n` (`u16`, up to 65535) and calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficients, then performs `n` scalar reads and `n` point reads plus `n` `HashMap` insertions for `verification_shares` — all before `ThresholdParams::new` validates `t`/`n`/`i` at the end of the function [1](#0-0) .

### Finding Description
`ThresholdKeys::read` deserializes `n` as a raw `u16` from the reader [2](#0-1) . If the interpolation tag byte is `0`, it immediately executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
``` [3](#0-2) 

With `n = 0xffff` this allocates `65535 * size_of::<F>()` (≈2 MiB for a 32-byte scalar) after consuming only ~15 bytes of attacker input — an amplification factor of ~10⁵. Even when the subsequent `read_exact` calls fail at end-of-input, the allocation already occurred. The function then attempts `n` `read_G` calls and `n` `HashMap::insert` operations into `verification_shares` [4](#0-3) , and only afterwards calls `ThresholdParams::new(t, n, i)` which rejects invalid parameter combinations [5](#0-4) . Validation happens after the resource consumption, exactly mirroring the advisory's "decode and parse before validate" ordering. By contrast, the sibling structure `Commitments::read` in PedPoP bounds its reads by the locally configured `params.t()` rather than a wire-supplied count [6](#0-5) .

A related but weaker instance exists in `SchnorrAggregate::read`, which loops `u32` times pushing `read_G` results — there the work is bounded by bytes actually present in the stream (each iteration fails at EOF), so amplification is absent [7](#0-6) .

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (e.g., a corrupted or externally supplied keys blob, a peer-delivered serialized key package during recovery/reshare flows using `dkg` recovery/promote code paths) can trigger ~2 MiB of allocation per call with ~15 bytes of input. Repeated calls exhaust host memory — a remote denial of service identical in class to RUSTSEC-2026-0229 (unauthenticated allocation before validation), with no authentication bypass or data disclosure required.

### Likelihood Explanation
Reachability depends on the integrator passing untrusted bytes to `ThresholdKeys::read`; the serialization exists precisely for persistence/transfer of key material between nodes, so untrusted-origin input is plausible in recovery flows. The `n = 0xffff` input is trivially constructible. The alloc is bounded at ~2 MiB per call (u16 max), so exploitation requires repetition, matching the advisory's "repeated requests" model.

### Recommendation
Validate parameters before allocating: parse `t`, `n`, `i` and run `ThresholdParams::new` (plus an application-level cap on `n`) before `Vec::with_capacity` and before any `read_F`/`read_G` loop in `ThresholdKeys::read`. Prefer incremental `Vec::push` over `with_capacity(n)` so allocation stays proportional to bytes actually consumed.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, Participant};
// For any C: Ciphersuite, e.g. ciphersuite_ed25519::Ed25519

fn poc() {
    let mut buf = vec![];
    // curve ID length + ID
    buf.extend(&(Ed25519::ID.len() as u32).to_le_bytes());
    buf.extend(Ed25519::ID);
    // t = 1, n = 0xffff, i = 1
    buf.extend(&1u16.to_le_bytes());
    buf.extend(&u16::MAX.to_le_bytes());
    buf.extend(&1u16.to_le_bytes());
    // interpolation tag 0 => Interpolation::Constant
    buf.push(0u8);
    // ~15 bytes of input; Vec::with_capacity(65535) allocates ~2 MiB
    // before the first read_F hits EOF
    let _ = ThresholdKeys::<Ed25519>::read(&mut Cursor::new(&buf));
}
```

Caveat: I verified the allocation-before-validation ordering in `crypto/dkg/src/lib.rs`; the concrete reachability of `ThresholdKeys::read` from fully untrusted network input depends on integrator usage, which is outside the in-scope crypto crates. If `ThresholdKeys::read` is only ever invoked on locally-generated bytes, this analog reduces to a hardening issue rather than a reachable vulnerability.
