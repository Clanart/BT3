## Analysis Result

The bug-class from the Sherlock report — "an automatic, privileged action fires during a normal update flow, and an attacker-controlled object can turn that action into a failure/execution primitive that blocks or corrupts the operation" — has a direct, concrete analog in GitHub Desktop's clone implementation.

### Title
Git clone protection against malicious recursive-submodule hook execution is explicitly disabled - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while always passing `--recursive` to `git clone`. This environment variable is the exact mechanism Git itself uses to detect whether a wrapping/embedding application (like Desktop) has already applied protections against the CVE-2024-32002-class attack, where a maliciously crafted repository with recursive submodules can get its hook scripts executed during clone on case-insensitive or symlink-capable filesystems. By forcing this flag to `'false'` on every clone, Desktop tells Git "the caller is NOT protected," which — depending on the underlying Git version's exact protection logic — removes or weakens Git's own defense-in-depth check against this attack path, re-exposing users who clone attacker-supplied URLs (e.g. `git clone` initiated from a shared/deep link or a repository picked from the GitHub API) to arbitrary code execution driven purely by repository content.

Every invocation of `clone()` — the function backing Desktop's "Clone repository" flow, driven by `CloningRepositoriesStore.clone` [2](#0-1)  — passes `--recursive` and forces `GIT_CLONE_PROTECTION_ACTIVE=false` unconditionally, for every URL the user (or a deep link / "Clone with Desktop" handler) supplies. This variable exists in upstream Git specifically to let embedding tools assert that they've already mitigated the symlinked/case-colliding submodule-hooks attack that lets a malicious repo run its own hook script during a `--recursive` clone. Explicitly setting it to `'false'` communicates the opposite of Desktop's actual protection state, which either disables an internal safety re-check in Git or causes Git to assume the wrapper already handled the risk when it has not — either way weakening the guard against attacker-supplied clone content.

Unlike the `isClonePathSensitive` check right above it (a genuine, narrowly-scoped guard against path traversal into `~/.ssh`, `~/.gnupg`, etc. — [3](#0-2) ), there is no corresponding validation of submodule content, hook paths, or filesystem case-sensitivity before disabling clone protection. The `--recursive` flag means submodules (whose URLs, paths, and `.gitmodules` entries are all attacker-controlled content inside the top-level repository) are cloned and their hooks paths resolved automatically, with the safety net turned off.

### Impact Explanation
An attacker who controls the content of a repository (a normal, unprivileged capability — anyone can publish a public repo, or send a "Clone with Desktop" deep link / `x-github-client://openRepo` style URL pointing at one) can craft a repository with recursive submodules designed to collide with `.git/hooks` via symlink or case-insensitive path tricks. On a victim's machine (macOS/Windows default case-insensitive filesystems are common), simply cloning that URL via Desktop's normal, expected "Clone repository" UX can result in arbitrary code execution on the user's machine — the outcome explicitly called out as valid impact ("attacker controls a cloned/fetched repository... result is code execution... outside the repo").

### Likelihood Explanation
No local access, no leaked credentials, and no unnatural user steps are required — cloning a URL is the core, expected use of the feature (including via deep links that trigger a clone without much user scrutiny of the underlying repository content). Since the disabling of protection is unconditional and not gated by trust of the source (`origin`, GitHub-owned repos, forks, or arbitrary third-party URLs are all cloned via this same function), any malicious/fork/spoofed repository reaches this path.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or only set it when Desktop has independently implemented and verified equivalent protections against symlinked/case-colliding submodule hook paths before recursing into submodules). At minimum, do not force this flag off for every clone; let Git's own protection remain active, and add pre/post-clone verification that no submodule hook path resolves outside the expected `.git/modules` tree.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` file referencing a submodule whose path/name is crafted to collide (via case-insensitivity or symlink trick) with the parent repository's hooks directory when cloned recursively — following the same structural pattern documented for CVE-2024-32002.
2. Attacker shares the clone URL (e.g. through a "Clone with Desktop" link, or simply as a repository URL the victim pastes into Desktop's clone dialog).
3. Victim clones the repository using Desktop's standard clone flow, which calls `clone()` in `app/src/lib/git/clone.ts`.
4. Because `args` includes `--recursive` and `env.GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, Git proceeds with recursive submodule initialization without the wrapper-asserted protection, allowing the crafted hook to execute during the clone, achieving code execution under the victim's user account outside of any sandbox.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
