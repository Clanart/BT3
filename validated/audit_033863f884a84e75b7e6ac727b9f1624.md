### Title
Path-prefix confusion in `resolveWithin` allows deep-link `filepath` to escape the target repository - (File: `app/src/lib/path.ts`)

### Summary
The report's bug class is "a caller-controlled parameter is trusted without a strict enough boundary check, letting the attacker cross a security boundary that the code believes it is enforcing." The Desktop analog is in the `_resolveWithin` helper used to sandbox the `filepath` parameter of the `x-github-client://openRepo/...` deep link: it validates containment with a plain string `startsWith` comparison instead of a path-segment-aware comparison, so a sibling directory whose name merely begins with the repository's directory name is treated as "inside" the repository.

### Finding Description
`_resolveWithin` in `app/src/lib/path.ts` resolves an attacker-supplied relative path against a trusted root and then performs the containment check: [1](#0-0) 

The check `realResolved.startsWith(realRoot)` is a raw string comparison with no trailing separator enforced. If the repository lives at `/Users/victim/Documents/GitHub/myrepo` and there happens to be a sibling directory whose name has `myrepo` as a prefix (e.g. `myrepo-secret`, `myrepository`, or any folder GitHub Desktop or the user later clones next to it), then a resolved path such as `/Users/victim/Documents/GitHub/myrepo-secret/id_rsa` will pass the check even though it is not actually inside `myrepo`. `realpath` is used to defeat symlink tricks, but it does nothing to defeat this class of prefix confusion because it operates on the already-escaped path.

This helper directly gates the `filepath` deep-link parameter, which is entirely attacker-controlled through a link the victim is asked to click: [2](#0-1) 

The parsed `filepath` field itself is minimally validated in `parseAppURL` — it just needs to be a non-null querystring value; there is no check that it stays within the repo, that check is deferred entirely to `resolveWithin`: [3](#0-2) 

So the only guard preventing an `openrepo://...&filepath=..%2F..%2Fmyrepo-secret%2Fid_rsa` deep link from resolving to a path outside the cloned repository is the flawed `startsWith` check.

### Impact Explanation
A successful bypass causes `dispatcher.ts` to call `shell.showItemInFolder(resolved)` on a path the code believes is safely inside the repository but which is actually a sibling directory/file chosen by the attacker. This directly matches the “file read/exposure outside the repo” impact category: an attacker who controls a link the victim clicks can make Desktop reveal (via the OS file manager) an unintended file/directory located next to the target repository, defeating the sandboxing the `resolveWithin` API is explicitly documented to provide (“guaranteed to reside at, or underneath this path”). The same flawed primitive (`_resolveWithin`) is reused by other call sites (`app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`), so any future or current callers that resolve attacker-influenced relative segments against a directory root inherit the same weakness, and the blast radius depends on what each of those call sites subsequently does with the resolved path.

### Likelihood Explanation
Exploitation requires the victim to click a maliciously crafted `x-github-client://openRepo/...` link (or Desktop being registered for `github-mac://`/`github-windows://` style protocols) pointing at a repository the victim already has cloned, plus the existence of a same-prefixed sibling directory. This is a plausible naming collision in real-world folder layouts (e.g., `project` and `project-notes`, `project` and `project.bak`, or Desktop's own convention of appending `-1`, `-2` suffixes when cloning a repo whose folder name already exists) making the precondition realistic rather than contrived, and requires no admin rights, no local access, and no prior compromise — only clicking a link, matching the "Valid Impact" criteria.

### Recommendation
Change the containment check in `_resolveWithin` (`app/src/lib/path.ts`) from a raw `startsWith` string comparison to a path-boundary-aware comparison, e.g. verify that `realResolved === realRoot` or that `realResolved.startsWith(realRoot + path.sep)`, so that only true descendants of `realRoot` pass. Add a regression test (alongside the existing `app/test/unit/path-test.ts` suite) covering sibling directories that share a name prefix with the root.

### Proof of Concept
1. Victim has cloned a repository to `/Users/victim/Documents/GitHub/myrepo` and separately has (or later creates) a directory `/Users/victim/Documents/GitHub/myrepo-secret` containing a sensitive file `secret.txt`.
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=..%2Fmyrepo-secret%2Fsecret.txt`
3. `parseAppURL` accepts the `filepath` value unchanged (only checks it isn't an absolute path later, in dispatcher.ts) and returns an `open-repository-from-url` action with `filepath: "../myrepo-secret/secret.txt"`.
4. `openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)`, where `repository.path` = `/Users/victim/Documents/GitHub/myrepo`.
5. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/myrepo-secret/secret.txt`, and `realResolved.startsWith(realRoot)` evaluates true because the string `/Users/victim/Documents/GitHub/myrepo-secret/secret.txt` starts with `/Users/victim/Documents/GitHub/myrepo`.
6. The check passes, `resolveWithin` returns the sibling path, and `shell.showItemInFolder(resolved)` is invoked, exposing `secret.txt` outside the intended `myrepo` repository boundary. [4](#0-3) [5](#0-4)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
