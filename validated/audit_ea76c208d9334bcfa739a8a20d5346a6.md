### Title
`ThresholdKeys::new`/`ThresholdKeys::read` accept zero secret shares and attacker-chosen verification shares, yielding a group key with a publicly known discrete log — (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to `transferPosition` accepting `address(0)` (moving a position to a null/uncontrolled address), `ThresholdKeys::new` performs no validation that the resulting `group_key` is non-identity or that the `secret_share`/`verification_shares` are consistent. Combined with `ThresholdKeys::read`, which deserializes these fields from untrusted bytes, an unprivileged party can craft a serialized `ThresholdKeys` whose group key is any point they choose — including the generator itself, whose discrete log (`1`) is public knowledge.

### Finding Description
`ThresholdKeys::new` computes `group_key` as the interpolation of the supplied `verification_shares` over participants `1..=t`: [1](#0-0) 

It checks only the count and upper bound of participant indexes (lines 355–365) and the `Constant`/`t == n` constraint (lines 367–374). It never checks:
- that `secret_share != 0`,
- that any verification share is non-identity,
- that `verification_shares[i]` actually corresponds to `generator() * secret_share`,
- that the resulting `group_key` is not a trivial/known key.

`ThresholdKeys::read` feeds attacker-controlled bytes straight into `read_F`/`read_G` and calls `ThresholdKeys::new`: [2](#0-1) 

Since Lagrange interpolation factors over `1..=t` sum to `1`, an attacker who sets every verification share to `C::generator()` produces `group_key = generator() * (Σ L_i) = generator()`. The secret key of the "threshold" group key is then `1` — known to everyone. Equivalently, setting all shares to identity yields `group_key = identity`, for which Schnorr signatures are trivially forged (`s` arbitrary, `R = s·G`, since `s·G == R + c·identity`).

### Impact Explanation
Any party that deserializes attacker-supplied `ThresholdKeys` bytes (e.g., key material distributed or loaded over an authenticated-but-untrusted channel, the reachable-input class explicitly in scope) ends up with a threshold group whose key the attacker fully controls. Schnorr/FROST signatures under that group key are forgeable by anyone, so funds or authorizations gated on the threshold signature are spendable by the attacker without any honest signature shares — the Serai analog of positions/assets being transferred to a null (here, publicly-known) key.

### Likelihood Explanation
Reachable wherever `ThresholdKeys::read` consumes bytes not fully trusted as locally-generated key material. `Participant::new` already rejects index `0` and `ThresholdParams::new` rejects `t == 0`, showing zero-validation was considered for indexes but not for the key material itself. Severity is Medium: exploitation requires an integrator to deserialize untrusted `ThresholdKeys` rather than self-generated ones, matching the "untrusted bytes fed to `ThresholdKeys::read`" reachability rule.

### Recommendation
In `ThresholdKeys::new`, reject `secret_share == 0`, reject identity verification shares, and verify `verification_shares[params.i()] == C::generator() * secret_share` (or document that callers must only deserialize self-produced bytes). Optionally reject `group_key == identity` / low-order results.

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs context — ThresholdKeys::read path
// Attacker constructs serialized bytes (as produced by ThresholdKeys::write):
//   C::ID, t = 2, n = 3, i = 1, Interpolation::Lagrange,
//   secret_share = arbitrary scalar (e.g., 0),
//   verification_shares[1..=3] = C::generator()  (or C::G::identity())
//
// ThresholdKeys::read -> ThresholdKeys::new computes:
//   group_key = Σ_{i=1}^{2} L_i * verification_shares[i]
//            = (L_1 + L_2) * G = G          // Lagrange factors sum to 1
//
// group_key == C::generator(), whose discrete log is 1.
// A Schnorr signature for any message under this group key is forged as:
//   k = random nonce scalar; R = k * G; c = challenge(R, G, msg);
//   s = k + c * 1   // valid for group key G without any threshold signing
//
// With verification_shares = identity, group_key = identity and any
// (R = s*G, s) pair verifies, since s*G == R + c*identity.
```
The gap is the unchecked computation of `group_key` from fully attacker-controlled `verification_shares` at `ThresholdKeys::new` (crypto/dkg/src/lib.rs:376-378), reachable via `ThresholdKeys::read` (crypto/dkg/src/lib.rs:625-631).
