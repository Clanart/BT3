### Title
`SignableTransaction::new` computes the fee from a stale output set that omits the OP_RETURN data output, underpaying the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds the caller-supplied `data` OP_RETURN output to `tx_outs`, but then computes the transaction weight/vbytes — and therefore `needed_fee`, the minimum-fee check, the not-enough-funds check, and the change amount — from a weight calculation that only accounts for `inputs` and `payments`. The OP_RETURN output (up to 80 bytes of attacker-influenced data plus output overhead) is never included in the size used for fee estimation, analogous to the Yieldoor report where a rate derived from the state at a prior step is applied to a result that has since grown.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is appended to `tx_outs` before the weight is measured:

```solidity
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` rebuilds a transaction from `inputs`, `payments`, and an optional `change` script — it has no parameter for `data`/`tx_outs`, so the OP_RETURN output's size (~10–100 weight units × up to 80-byte payload plus varints) is excluded from both `weight` and `vbytes`. The same omission occurs in the change branch, which again calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`.

Consequences of using this stale (pre-data-output) size:

1. `needed_fee = fee_per_vbyte * vbytes` underprices the real transaction. Since `fee()` returns `sum(inputs) - sum(outputs)`, the actual paid fee equals `needed_fee`, so the effective fee rate of the broadcast transaction is strictly below the caller-requested `fee_per_vbyte`.
2. The `TooLowFee` check (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) is evaluated against the underestimated `vbytes`, so a transaction requested at exactly the minimum relay rate will actually serialize below the minimum and be rejected by default node relay policy.
3. The change output is credited `input_sat - payment_sat - fee_with_change`, i.e., it absorbs the fee that should have paid for the OP_RETURN bytes, making the change output slightly oversized and the fee correspondingly undersized.
4. The `TooLargeTransaction` check uses `weight` that omits the data output, so the max-standard-weight bound is enforced on a stale size.

### Impact Explanation
A transaction built with `data` (e.g., the maximum ~91 extra bytes: 8-byte value + script length + `OP_RETURN`/`OP_PUSHDATA` + 80-byte payload) pays a fee computed as if that output did not exist. If the caller requests a fee rate at or near the 1 sat/vbyte relay minimum — which `SignableTransaction` explicitly permits once `needed_fee` clears `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` — the produced transaction's real fee rate falls below the minimum and is non-standard: default Bitcoin nodes will not relay or mempool-accept it. The transaction's txid is fixed at construction (`Eventuality(signable.txid())` in the processor), so the funds it spends cannot be recovered or re-signed with a higher fee by that flow. This is an availability/loss-of-funds class issue on transaction construction reachable via the public `data` parameter.

### Likelihood Explanation
Any invocation of `SignableTransaction::new` with `data: Some(_)` and a near-minimum `fee_per_vbyte` produces an unrelayable or under-priced transaction deterministically; no adversarial timing is required. For larger requested fee rates the transaction still confirms but at a lower effective rate than requested, bounded by the ~80-byte data cap.

### Recommendation
Include the data output in the size used for fee estimation. Pass `tx_outs` (or `payments` plus a flag/size for the OP_RETURN output) into `calculate_weight_vbytes` so `vbytes`, `weight`, the `TooLowFee` check, the change value, and the `TooLargeTransaction` check all reflect the final transaction, e.g.:

```rust
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, None);
```

where `calculate_weight_vbytes` is refactored to take the actual `TxOut` list rather than rebuilding outputs only from `payments`.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
