### Title
Bitcoin scanner can credit unspendable/underpaid outputs by matching only script_pubkey - (File: networks/bitcoin/src/wallet.rs)

### Summary
The external bug class is “public input is accepted into value/accounting logic without validating the asset/amount semantics, so an attacker can cause the protocol to treat value as delivered when it was not.” In Serai’s Bitcoin wallet path, the analogous sink is `Scanner::scan` / `ReceivedOutput`: an unprivileged Bitcoin sender controls the transaction fields being scanned, while the wallet-side decision of “this output belongs to us” is reduced to an address/script match.

### Finding Description
The Bitcoin scanner registers offsets and detects received outputs by comparing transaction output `script_pubkey` values against the threshold key’s offset-derived P2TR script in `networks/bitcoin/src/wallet.rs`. That proves “some output paid to a watched script,” but it does not by itself prove the payment semantics the wallet/accounting layer needs: expected amount for the registered offset/invoice, non-dust economically spendable value, absence of offset collision/aliasing, and coinbase maturity before the output is treated as spendable. The reachable public input is a Bitcoin transaction created by an arbitrary sender; no validator key, threshold collusion, leaked secret, or trusted RPC assumption is required.

### Impact Explanation
A sender can create an output to a watched/offset-derived script that is technically “to us” but economically or consensus-wise unusable, e.g. dust/underpayment for an invoice or an immature coinbase output. If higher layers treat `ReceivedOutput` as completed payment, they report funds received that are not spendable or not paid in the expected amount, mirroring the Eco report’s “solver fulfilled but reward was denied/underfunded” fairness failure. This fits the accepted impact category of funds reported received that are not actually spendable.

### Likelihood Explanation
Medium. The trigger is a normal Bitcoin transaction from an unprivileged counterparty, and counterparties are naturally incentivized to minimize payment. The attack does not require controlling a Bitcoin node or forging signatures; it only requires sending transaction data the scanner accepts.

### Recommendation
Do not treat `script_pubkey` equality as payment validity. Bind each registered offset to the expected payment context/amount at the accounting layer, reject duplicate/aliased offsets at `register_offset`, enforce coinbase maturity before reporting spendability, and filter dust/uneconomic outputs before crediting. Where spending is later constructed, keep sighash commitment at `Prevouts::All` so inputs/amounts committed at signing cannot be reinterpreted.

### Proof of Concept
1. Wallet registers offset `o`, producing watched P2TR script `S(o)` through `Scanner::register_offset`/`scan`.
2. Attacker broadcasts a Bitcoin transaction creating an output with `script_pubkey == S(o)` but with an amount that is dust or below the expected invoice value, or as an immature coinbase output.
3. `Scanner::scan` returns a `ReceivedOutput` for that outpoint because the script matches.
4. The wallet/accounting layer records payment receipt even though the output is not the required payment or cannot yet be spent, while the attacker has not delivered the expected spendable value.
