### Title
Blame proof leaks the ECDH key before the message PoP is verified, enabling recovery of other participants' secret shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The DKG encryption layer is explicitly designed so that a blame proof (`EncryptionKeyProof`, which contains the ECDH shared key `proof.key`) can only reveal the message it authenticates, because the per-message proof-of-possession (PoP) is supposed to prevent an attacker from co-opting another participant's `msg.key`. In `KeyMachine::calculate_share`, however, the decrypted share's canonicality check (`C::F::from_repr`) is performed and error-returned *before* `batch.verify_with_vartime_blame()` is ever run, so the `EncryptionKeyProof` — containing the raw ECDH shared key — is emitted for a message whose Schnorr PoP was never verified. This re-opens exactly the side-effect attack the code comments describe as mitigated.

### Finding Description
`EncryptedMessage` carries `key` (ephemeral public key), `pop` (Schnorr PoP over `context`, `R`, `key`, `from`, and the ciphertext bytes), and the ChaCha20-encrypted share. The comments in `encryption.rs` spell out the attack: Eve observes Alice encrypt to Bob with key `X`, then sends Bob a message "claiming to use X"; Bob decrypts to gibberish and publishes a blame argument revealing `bX` (the ECDH shared key), which decrypts Alice's real message. The PoP is stated to be the fix. [1](#0-0) 

But in `calculate_share`, `decrypt` only *queues* the PoP into a `BatchVerifier` (it is not checked yet), decrypts the message unconditionally, and returns the `EncryptionKeyProof` containing the ECDH key: [2](#0-1) 

`calculate_share` then checks whether the plaintext is a canonical scalar **before** the batch (and therefore the PoP) is verified; a non-scalar plaintext causes an immediate `PedPoPError::InvalidShare` carrying `blame: Some(...)` — the ECDH key — with the queued PoP never verified: [3](#0-2) 

So Eve can replay Alice's `msg.key` (public on the wire) under Eve's own `from` index with a malleated ciphertext: the PoP will fail (it's bound to `from` and the ciphertext via `pop_challenge`), and the decrypted plaintext will be non-canonical with high probability, but neither matters — the early `from_repr` return leaks `ecdh(bob_enc_key, alice_msg_key)` to Eve before any verification. Eve then uses that key to decrypt Alice's genuine `EncryptedMessage` to Bob, recovering Alice's secret share to Bob.

The processor propagates the serialized blame to the coordinator (`ProcessorMessage::InvalidShare { blame }`), making the leaked key effectively public: [4](#0-3) 

### Impact Explanation
This is a confidentiality break of DKG secret shares reachable by an unprivileged participant using only public protocol data. Repeating the attack against shares addressed to `t` distinct honest recipients lets Eve collect `t` evaluations of a victim dealer's polynomial and interpolate its constant term — that dealer's contributed secret. Applied across enough dealers, this can contribute to reconstruction of the threshold group's secret key material, analogous in class to CVE-2026-15977 (an unauthenticated endpoint returning secret key material): a public protocol message causes the victim to emit secret cryptographic keys it should never reveal.

### Likelihood Explanation
Fully deterministic and attacker-triggered. Eve needs only an honest victim who runs `calculate_share` over a share map containing Eve's forged `EncryptedMessage`. A random malleated ciphertext decrypts to a non-canonical scalar with overwhelming probability (for Ed25519's `l ≈ 2^252`, ~75% per attempt, retryable across DKG attempts). No collusion or privileged position is required.

### Recommendation
Enforce the PoP before any blame material is released: verify `msg.pop` synchronously (or run the batch verification) prior to the `from_repr` canonicality check in `calculate_share`, returning `InvalidShare { blame: None }` (the `BatchId::Decryption` outcome) whenever the PoP fails or is unverified. Alternatively, perform the scalar check inside `decrypt` only after confirming PoP validity, so `EncryptionKeyProof` is only ever emitted for authenticated messages.

### Proof of Concept
1. Alice (participant 1) runs `commit`/`generate_secret_shares`, producing `EncryptedMessage`s for each participant; Eve observes the message `M = secret_shares[ALICE][BOB]` with `M.key = X` (per-message public key) and ciphertext `C_A` (Alice's share to Bob).
2. Eve constructs a forged message `M' = EncryptedMessage { key: X, pop: <anything>, msg: <random bytes same length as C_A> }` and sends it to Bob under `from = EVE`.
3. Bob calls `machine.calculate_share(rng, shares)` where `shares[EVE] = M'` (read via `EncryptedMessage::read`, which performs no validation).
4. In `decrypt`, the PoP is only queued; `cipher(context, ecdh(bob_enc, X)).apply_keystream(M'.msg)` yields pseudorandom bytes, which fail `C::F::from_repr` with high probability.
5. `calculate_share` returns `PedPoPError::InvalidShare { participant: EVE, blame: Some(EncryptionKeyProof { key: ecdh(bob_enc, X), .. }) }` — PoP never verified.
6. Bob broadcasts `blame.serialize()`. Eve reads `proof.key`, computes `cipher(context, proof.key)`, and XORs it against `C_A`, recovering Alice's secret share to Bob.
7. Repeating for `t` victims yields `t` evaluations of Alice's polynomial, recovering her dealt secret.

Contrast with `invalid_encryption_pop_blame` in `tests.rs`, which shows the *intended* behavior (PoP failure → `blame: None`) — a path bypassed by the early `from_repr` return.
