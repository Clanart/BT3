### Title
Cached FROST preprocess is reused whenever a signing context repeats, causing nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

Analogous to a pool "primed" with hidden debt before victims deposit, `SigningProtocol::preprocess_internal` primes each signing context with a persisted deterministic seed (`CachedPreprocesses`). Once a seed is stored for a context, every subsequent signing operation under that same context regenerates the *identical* FROST nonces and commitments. If two distinct messages are ever signed under one context, the two resulting signature shares share the same nonces, and any observer can algebraically recover the signer's MuSig private key share — the trap was set long before the second signature occurred.

### Finding Description

`preprocess_internal` derives an encryption key from `b"Cached Preprocess Encryption Key" || context.encode() || key`, then: if `CachedPreprocesses::get(txn, &context)` is empty it creates a fresh preprocess via `AlgorithmMachine::preprocess(&mut OsRng)` and stores the seed XORed with the encryption key; it *then unconditionally re-loads that stored seed* and reconstructs the machine via `AlgorithmSignMachine::from_cache` [1](#0-0) .

`from_cache` feeds the seed into `ChaCha20Rng::from_seed`, so the nonces, commitments, and addendum are fully determined by the seed [2](#0-1) . The seed is never deleted or rotated after use — it persists in the DB keyed only by `context`.

The only instantiation is `DkgConfirmer`, whose context is `(b"DkgConfirmer", attempt)` [3](#0-2) . Both `share` and `complete` re-enter `preprocess_internal` through `share_internal` [4](#0-3) , and the signed message is `set_keys_message(set, removed, key_pair)` [5](#0-4)  — where `key_pair` is supplied per-call. Two calls in the same `attempt` with different `key_pair` values (e.g., a retried/updated DKG confirmation, or an equivocating confirmation) sign different messages with byte-identical FROST nonces.

This is exactly the failure mode `CachedPreprocess` documents: "A preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share" [6](#0-5) . The DB layer caches the seed indefinitely and reuses it silently, with no binding of the cached entry to the message that will be signed.

### Impact Explanation

FROST shares have the form `z = d + e·ρ + λ·s·c`. With the same nonces `(d, e)` and same signing set, two shares for messages `m1 ≠ m2` differ only in the challenge `c`, yielding `s = (z1 − z2) / (λ·(c1 − c2))`. Signature shares and preprocesses are broadcast to all participants over the tributary protocol, so any validator (or anyone observing the publicized tributary data) recovers the victim validator's MuSig secret share for that set — full compromise of that validator's signing key for the set, enabling forged threshold signatures in combination with other leaked shares, or targeted blame/DoS. Impact: key share recovery → Critical/High class.

### Likelihood Explanation

Reuse requires `share_internal` to run twice under one `(b"DkgConfirmer", attempt)` context with differing `key_pair`. `key_pair` is attacker-influenced data (it is the DKG output being confirmed, produced from validator-submitted messages), and nothing in `preprocess_internal` binds the cached seed to the message. Any code path — restart replay, retry, equivocation handling, or future caller — that signs two distinct confirmations within one attempt triggers the leak. Because the seed is persisted (not in-memory), the reuse window is unbounded.

### Recommendation

Bind the cached preprocess to the message, or burn it on first use:

- Include the message hash (e.g., `set_keys_message` digest) in the `CachedPreprocesses` key, or store `msg_hash` alongside the seed and `assert_eq!` on reuse, refusing to sign a different message with the same seed.
- Alternatively, delete the DB entry after `share_internal` consumes it, regenerating (and republishing) a fresh preprocess on any subsequent call.

### Proof of Concept

Conceptual, based on `DkgConfirmer`:

```rust
// Same attempt -> same context -> same cached seed -> same nonces
let mut confirmer = DkgConfirmer::new(&key, &spec, &mut txn, attempt).unwrap();
let share1 = confirmer.share(preprocesses.clone(), &key_pair_a).unwrap();

// Later in the same attempt (or after reboot), a different KeyPair is confirmed
let mut confirmer2 = DkgConfirmer::new(&key, &spec, &mut txn2, attempt).unwrap();
let share2 = confirmer2.share(preprocesses, &key_pair_b).unwrap();

// share1 and share2 were produced with identical nonces (d, e) and identical
// binding factors; only the Schnorr challenge differs (msg includes key_pair).
// secret_share = (share1 - share2) / (lambda * (c1 - c2))
```

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
