### Title
Webhook HMAC Verification Does Not Bind Signature to Shop Domain, Enabling Cross-Shop Webhook Replay - ([File: lib/shopify_app/controller_concerns/payload_verification.rb])

### Summary
The webhook signature check in `ShopifyApp::PayloadVerification#hmac_valid?` only authenticates the raw request body. It never binds the HMAC to the `X-Shopify-Shop-Domain` header that `ShopifyApp::WebhookVerification#shop_domain` (and the underlying `ShopifyAPI::Webhooks::Registry`) uses to identify which merchant a webhook belongs to. Because the header is not covered by the signature, any party who has obtained one valid `(body, HMAC)` pair for a webhook can replay that exact request to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value, and the request will still pass verification.

### Finding Description
`hmac_valid?` computes the digest strictly over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` calls only this body-based check before allowing the request through, and separately exposes `shop_domain` straight from the (unauthenticated) header: [2](#0-1) 

The built-in `WebhooksController` forwards both the raw body and the full header set (including `X-Shopify-Shop-Domain`) to `ShopifyAPI::Webhooks::Registry.process`, which resolves the shop from the header and dispatches to a job handler: [3](#0-2) 

The generated job templates then use that unauthenticated `shop_domain` to look up a `Shop` record and open an authenticated Shopify session/access-token for that shop before running any webhook logic: [4](#0-3) [5](#0-4) 

This is the same root-cause class as the reported analog: the code trusts an external value (`shop_domain`) that was never actually validated against the cryptographically verified data (`raw_post`), analogous to trusting the swap output amount without checking it matches what was signed for. Since Shopify uses one shared `api_secret_key` per app across all installed shops (not a per-shop secret), any merchant with the app installed can capture a legitimately-signed webhook body for their own shop (e.g. from their own store activity, which they fully control and can trigger repeatedly) and replay `(body, valid HMAC, forged shop header)` directly to the app's public webhook URL, impersonating a different installed shop.

### Impact Explanation
Because the shop-scoping value used by the job layer is not covered by the HMAC, an attacker (any merchant who has the app installed) can cause the app to process attacker-chosen webhook payloads under a victim shop's identity, including mandatory privacy webhooks (`shop/redact`, `customers/redact`, `customers/data_request`). This can trigger unauthorized shop-scoped side effects such as forced data redaction/erasure for a victim shop, or execution of app business logic under `shop.with_shopify_session` using the victim's stored offline access token — a cross-shop access/action impact.

### Likelihood Explanation
Exploitation requires only that the attacker themselves be a legitimate, unrelated merchant using the app (no special access needed), and that they know or can enumerate a target shop's `myshopify.com` domain (public information). Capturing a valid `(body, HMAC)` pair only requires triggering any subscribed webhook topic on the attacker's own shop, which they fully control. The replay is a straightforward direct HTTP POST to the app's `/webhooks` route with a modified header, so likelihood is high wherever webhook handlers use the header-derived `shop_domain` to scope authenticated actions (as in all generator-provided templates and documented custom-controller examples).

### Recommendation
Do not treat `X-Shopify-Shop-Domain` (or any header) as authenticated merely because the body's HMAC validated. Either:
- Include the shop domain (and ideally topic/webhook id) as part of the HMAC-covered material used to look up and enforce the shop context, or
- Cross-check the header-derived shop domain against a shop-independent authenticated fact (e.g., verify the webhook was registered for that exact shop/topic combination via the Shopify webhook ID and topic returned by `ShopifyAPI::Webhooks::Registry`, not solely a client-supplied header), or
- Bind webhook verification to a per-shop secret/session lookup rather than a single global `api_secret_key` shared by all installed shops.
At minimum, document this trust boundary explicitly so app developers scoping data by the webhook's `shop_domain` know it is not itself authenticated by the HMAC and must not be treated as tenant-isolation proof.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled) and Shop B (victim) — both share the app's single `api_secret_key`.
2. On Shop A, trigger any subscribed webhook topic (e.g. update a cart) to receive a genuine webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
3. Replay the captured request directly to the app's public webhook endpoint (`ShopifyApp::WebhooksController#receive` / any controller including `ShopifyApp::WebhookVerification`), keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain` with `shop-b.myshopify.com`.
4. `hmac_valid?` succeeds because it only checks `HMAC(secret, B) == H`, which is unaffected by the header change.
5. The webhook job runs with `shop_domain = "shop-b.myshopify.com"`, loading Shop B's stored session/access token and executing the handler logic with attacker-supplied body `B` attributed to Shop B — e.g., forcing `ShopRedactJob`/`CustomersRedactJob` logic to run against Shop B triggered entirely by Shop A's action.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

module ShopifyApp
  class WebhooksController < ActionController::Base
    include ShopifyApp::WebhookVerification

    def receive
      params.permit!

      ShopifyAPI::Webhooks::Registry.process(

      )
      head(:ok)
    end
