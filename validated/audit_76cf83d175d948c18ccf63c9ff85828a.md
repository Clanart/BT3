### Title
Unauthenticated `signer` field in `RequestMessage`/`ResponseMessage` lets any relayer attribute delivery — and its reward — to an arbitrary account - (File: modules/pallets/ismp/src/host.rs)

### Summary
`pallet-ismp`'s `IsmpHost::store_request_receipt` / `store_response_receipt` write the caller-supplied `signer: Vec<u8>` from the incoming `RequestMessage`/`ResponseMessage` directly into `RequestReceipts`/`ResponseReceipts` after only running it through `extract_signer`, with no check that the bytes are a valid signature over the delivered batch. This receipt value is later trusted by `pallet-relayer` as the ground truth for "who delivered this message" when paying out `accumulate_fees` (`modules/pallets/relayer/src/accumulate.rs`) and `claim_outbound_request_delivery_reward` (`modules/pallets/relayer/src/outbound_request.rs`), via `decode_receipt_relayer`, which for substrate destinations returns the raw bytes as-is when `len <= 32` — i.e. no signature check is even attempted in that branch.

### Finding Description
`handlers/request.rs::handle` calls `host.store_request_receipt(&wrapped_req, &msg.signer)?` for every `PostRequest` in the batch: [1](#0-0) 

The pallet-level implementation stores whatever `extract_signer` extracts from the caller-controlled `signer` bytes, unconditionally: [2](#0-1) 

The doc comment on `RequestMessage`/`ResponseMessage` explicitly signals this is not enforced: "Signer information. **Ideally should be** their account identifier" — i.e. it's advisory, not verified at the point of delivery: [3](#0-2) 

Downstream, both reward paths trust this stored value as the delivering relayer's identity. `decode_receipt_relayer` for substrate destinations returns the raw stored bytes untouched when they are ≤32 bytes long — no signature decode, no verification at all in that branch: [4](#0-3) 

This is structurally identical to the Android bug: a critical authorization decision (which account is credited as "authenticated"/"the delivering relayer") is made by trusting a value the untrusted party supplies at delivery time (`msg.signer`, analogous to the app trusting `onAuthenticationSucceeded` instead of validating a bound `CryptoObject`), instead of requiring a genuine cryptographic signature bound to the delivered request/response at the moment the receipt is created.

### Impact Explanation
Any permissionless relayer can submit a `RequestMessage`/`ResponseMessage` with a valid state/membership proof (which they can construct honestly since they are actually delivering the message) but set `signer` to bytes of their choosing — including bytes that happen to match an account they don't need to prove ownership of at delivery time. Because the receipt is the sole source of truth consumed later by `accumulate_fees` and `claim_outbound_request_delivery_reward` to attribute and pay the relayer reward/fee, this allows redirecting or self-attributing reward payouts (treasury funds and per-request relayer fees) without the destination chain ever validating that the claimed signer actually performed or authorized the delivery. This falls squarely in-scope: unauthorized transaction/execution and wrong-beneficiary fund movement in the reward/fee-accumulation path.

### Likelihood Explanation
High: submitting `RequestMessage`/`ResponseMessage` is a normal, permissionless relayer action already required for protocol operation — no privileged role, prover collusion, or governance action is needed. The attacker only needs to control the `signer` field of a message they are already entitled to submit.

### Recommendation
Require `msg.signer` to be validated as a genuine signature over the delivered batch (using the same `Signature::verify` machinery already used in `outbound_request.rs`/`accumulate.rs`) inside `store_request_receipt`/`store_response_receipt` before persisting it, rather than trusting caller-supplied bytes. Alternatively, derive the stored identity directly from the extrinsic's actual submitter (e.g., `ensure_signed`/transaction origin) instead of an unauthenticated payload field.

### Proof of Concept
1. Relayer constructs a valid `RequestMessage` with a correct membership proof for requests it is legitimately delivering.
2. Instead of putting its own signature/public key in `signer`, it sets `signer` to arbitrary bytes ≤32 bytes (e.g., a victim's or a fresh throwaway account's raw bytes).
3. `handle_incoming_message` → `request::handle` → `host.store_request_receipt(&wrapped_req, &msg.signer)` stores those bytes verbatim in `RequestReceipts[commitment]`.
4. Later, when a state proof of `RequestReceipts[commitment]` is submitted to `pallet-relayer::accumulate` or `claim_outbound_request_delivery_reward`, `decode_receipt_relayer` returns those same unverified bytes as `delivered_by`/`address`, and the reward/fee is credited to that attacker-chosen identity — with no proof the "signer" ever authorized or performed the delivery.

Note: I was not able to fully trace `extract_signer`'s exact validation logic (it wasn't returned in the indexed snippets), so it's possible it performs some additional sanity check I couldn't verify; a Devin session with full repo access should confirm `extract_signer`'s implementation in `modules/pallets/ismp/src/host.rs` to close this gap definitively.
