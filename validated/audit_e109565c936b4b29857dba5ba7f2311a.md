This confirms the mechanism: every EVM `CALL` to a precompile with `value != 0` triggers `TransferWithoutEvents`/`SubBalance`/`AddBalance` in the StateDB, which converts the EVM balance transfer into a real usei/wei bank transfer from the caller to the Sei address bound to the precompile address, via `AddBalance` in `x/evm/state/balance.go` [1](#0-0) . This happens in the EVM/StateDB layer, *before* the precompile's Go `Execute`/`Run` method is even entered — it is unconditional and independent of whether the precompile logic actually needs or moves that value.

The distribution precompile's `rewards()` view method is the one method that is missing the `pcommon.ValidateNonPayable(value)` guard that every other query method in the same `Execute` switch has, as explicitly called out in the test suite comment: *"rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)"* [2](#0-1) . In `Execute`, `RewardsMethod` is dispatched straight to `p.rewards(ctx, method, args)` with no value check, unlike sibling query methods such as `ParamsMethod`, `ValidatorOutstandingRewardsMethod`, etc. that also don't check either, but critically `rewards()` is a read-only accessor with zero code paths that forward, refund, or otherwise account for `value` [3](#0-2) .

Because the value-transfer already happened in the StateDB before `Execute` runs, a transaction/contract that calls `rewards(address)` on the distribution precompile (`0x0000...1007`) with nonzero `msg.value` will have that usei/wei silently and permanently moved from the caller's Sei-mapped balance into the bank balance of the Sei address associated with the distribution precompile's EVM address. There is no withdrawal method, no refund path, and no fallback mechanism for the precompile's own associated account — it is not a normal DAO/module account with any sweep logic, so the funds are stranded exactly as in the reported DAO bug class (funds deposited to an address with no code path to move them back out).

This is a direct match for the report's bug class: "native tokens sent to an address get stuck because there is no function to withdraw them." Here, the "address" is the distribution precompile's associated account, and the "deposit path with no offsetting withdraw" is the missing `ValidateNonPayable` check on `rewards()`.

### Title
Missing non-payable check on distribution precompile `rewards()` permanently strands native tokens sent with the call - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards()` view method of the distribution precompile (address `0x...1007`) is the only query-type method in `PrecompileExecutor.Execute` that does not call `pcommon.ValidateNonPayable(value)`. Because EVM `value` transfers to any precompile address are unconditionally settled into the real usei/wei bank balance of that precompile's associated Sei account before the precompile's Go code ever runs, any caller who sends nonzero `value` alongside a `rewards()` call has those funds moved out of their own balance into the precompile's associated account with no code path to retrieve them.

### Finding Description
Every precompile call with `value != 0` results in an unconditional native-token balance transfer performed by the EVM/StateDB layer (`AddBalance`/`SubBalance` -> `BankKeeper().AddCoins`/`SubUnlockedCoins`) [4](#0-3) . This transfer is independent of whatever the target precompile's Go logic subsequently does with `value`. All other transaction-type methods in the distribution precompile's `Execute` dispatcher explicitly guard against unwanted value with `pcommon.ValidateNonPayable(value)` (e.g. `WithdrawValidatorCommissionMethod`) [5](#0-4) , but `RewardsMethod` is dispatched with no such check and no logic that consumes, forwards, or refunds the value: [6](#0-5) 

The `rewards()` handler itself is a pure read path (it only queries delegation rewards) and never touches `value`, so any usei/wei sent alongside the call is simply left in the precompile's associated Sei account balance with no corresponding accounting, no event, and — crucially — no exposed method anywhere in the precompile to move funds back out of that account. This is functionally identical to the reported DAO issue: native tokens are accepted into an address (here, the precompile's backing account, analogous to the DAO contract) but no withdrawal mechanism exists to recover them.

### Impact Explanation
Any usei/wei value attached to a `rewards()` call is irrecoverably lost from the caller's control and effectively "burned" into the precompile's associated account balance, which has no operator, no owner, and no method to reclaim it. This is a direct, permanent loss of user funds triggerable by any EVM transaction sender or any contract that (mistakenly or via crafted calldata from an integrator) attaches value to this specific call. Because this is reachable by an ordinary EVM transaction against a public precompile address, it meets the "concrete fund loss or permanent freezing" bar.

### Likelihood Explanation
The ABI for the `rewards` method is exposed publicly (used by any dApp integrating rewards queries) and nothing in the transaction submission or wallet flow prevents a caller from attaching `value` to any contract call, especially in generated/batched calls, proxy contracts that forward `msg.value`, or misconfigured integrations that assume all precompile calls are payable-safe. Given the test suite explicitly documents this as a known quirk rather than a reverted/guarded case, any nonzero-value call to `rewards()` will always succeed and always strand the sent value.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used by the other read-only/view methods in `Execute` to the `RewardsMethod` case before dispatching to `p.rewards(...)`, so that a value-bearing call to `rewards()` reverts before the EVM-level value transfer is committed, consistent with all other non-payable precompile methods.

### Proof of Concept
1. From any EVM account associated with a Sei address holding usei, call the distribution precompile at `0x0000000000000000000000000000000000001007` with method selector for `rewards(address)` and set `msg.value` to a nonzero amount (e.g. `1e18` wei).
2. Observe the call succeeds (no `ValidateNonPayable` revert) and returns the delegator's reward data as normal.
3. Query the caller's on-chain usei balance: it is now reduced by the `value` sent.
4. Query the bank balance of the Sei address mapped to the distribution precompile's EVM address (`p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address)`): it has increased by the same amount.
5. There is no method on the distribution precompile, nor any other module, that can move funds out of that account back to the original sender — the value is permanently stranded, mirroring the "Native tokens in the DAOs are stuck" bug class from the external report.
