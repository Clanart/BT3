Based on my investigation, I found a concrete analog of this bug class in the `distribution` precompile.

### Title
Value sent to the non-payable-but-unguarded `rewards()` view method of the distribution precompile is permanently stranded - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile at `0x0000000000000000000000000000000000001007` explicitly guards almost every method against accidental value transfers via `pcommon.ValidateNonPayable(value)`, except for the `rewards()` query method, which is dispatched without any such check [1](#0-0) . This mirrors the InfinityExchange bug class: value/usei sent into a contract or precompile that has no corresponding accounting or retrieval path becomes permanently unreachable.

### Finding Description
In `PrecompileExecutor.Execute`, all state-changing dispatch branches (`WithdrawValidatorCommissionMethod`, etc.) call `pcommon.ValidateNonPayable(value)` to reject any EVM call that attaches `usei`/`wei` value [2](#0-1) . The `RewardsMethod` case, however, dispatches straight to `p.rewards(ctx, method, args)` with no `value` argument passed and no `ValidateNonPayable` check at all [1](#0-0) .

This is corroborated by an integration test comment which explicitly documents the quirk: *"rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds), so this spec deliberately has no 'view rejects value' test."* [3](#0-2) 

Because precompile addresses are backed by a Sei account (`p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address)`), any `usei`/`wei` value attached to an EVM call to the distribution precompile at `0x...1007` is credited to that account balance via the EVM's value-transfer mechanics before/along with the precompile's `Run`. Since `rewards()` is a pure read-only query with no payment-handling logic (unlike `delegate()` in the staking precompile, which explicitly calls `pcommon.HandlePaymentUsei` to refund/process attached value [4](#0-3) ), the value sent along with a `rewards()` call is never returned to the caller and never accounted for by any distribution logic. There is no `rescue`/`sweep` function in the distribution module or precompile to later retrieve it, so it accumulates permanently in the precompile's underlying Sei address.

This is structurally identical to the InfinityExchange bug: a payable entry point accepts value with no corresponding bookkeeping, and there is no mechanism elsewhere in the codebase to reclaim it, resulting in permanent freezing of funds.

### Impact Explanation
Any `usei`/`wei` value mistakenly or intentionally attached to a `rewards()` call against the distribution precompile is irrecoverably lost — permanently frozen at the precompile's backing account with no owner-only or public function able to retrieve it. This is a permanent freezing of user funds triggered by a single, unprivileged EVM transaction (no special privileges needed — any EVM caller can attach value to this call).

### Likelihood Explanation
Likelihood is moderate: this requires a caller to mistakenly (or through a buggy integrating contract) attach a non-zero `value` to what is documented/expected to be a pure view call. Wallets, SDKs, or naively-generated calldata that reuse a generic "send value with call" pattern could easily trigger this, and unlike other view methods in the same precompile, there is no revert to protect the caller.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard to the `RewardsMethod` case in `precompiles/distribution/distribution.go`'s `Execute` dispatch (and any legacy precompile versions still reachable at the currently active height) so calls with non-zero value revert instead of silently stranding funds, consistent with all other query/transaction methods in the same file.

### Proof of Concept
1. Associate an EVM address with a Sei account and ensure it holds `usei`.
2. Call the distribution precompile's `rewards(address)` (or equivalent) function at `0x0000000000000000000000000000000000001007` via a raw EVM transaction, attaching a non-zero `value` field.
3. Observe that the call succeeds (no `ValidateNonPayable` revert), the attached value is transferred to the precompile's backing account, and the query result is returned to the caller.
4. Confirm the value is never returned or credited to the caller's balance, and that no distribution or precompile function exists that can retrieve it — the amount is permanently stuck in the precompile's Sei address balance, corroborated by the deliberate lack of test coverage noted at [5](#0-4) .
