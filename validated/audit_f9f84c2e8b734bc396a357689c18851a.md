### Title
Attacker-controlled remote spam can force silent selection of an untrusted "default remote" - (File: `app/src/lib/stores/helpers/find-default-remote.ts`)

### Summary
The Holograph report describes a broken invariant: when a canonical entry (a filled operator pod) is missing, the system silently falls back to an arbitrary, attacker-influenceable slot (the zero-address pod), and that fallback is then treated as authoritative ("open season"). GitHub Desktop has a structurally identical pattern in how it selects the "default remote" for a repository: if no remote literally named `origin` exists, Desktop falls back to whatever remote happens to be first, with no further validation, and treats that pick as the repository's canonical remote for git operations.

### Finding Description
`findDefaultRemote` implements the selection logic: [1](#0-0) 

If no remote is named `origin`, it returns `remotes[0]` unconditionally — i.e., whichever remote sorts/lists first is silently promoted to "the default remote" for the repository, with no ownership or trust check. `getRemotes` returns remotes sorted alphabetically by name (confirmed by test expectations sorting `A, D, L, T, X`): [2](#0-1) 

An attacker who controls the contents of a repository the victim opens or clones in Desktop (e.g., a repository shipped without an `origin` remote, or one whose `.git/config` the attacker crafted/tampered with — for example a repository obtained via a zip/tarball-with-embedded-.git, a shared network clone, or a submodule/worktree checkout) can simply omit `origin` and add a remote whose name sorts before any legitimate remote (e.g. `0-origin`, `aaa`) pointing at an attacker-controlled URL. `findDefaultRemote` will then pick that attacker remote as "the" default with no signal to the user that anything unusual happened — directly analogous to the empty pod being picked because no real operator filled it.

The resulting value is treated as trustworthy in several downstream code paths in `git-store.ts` and `app-store.ts` (10+ and 9+ references respectively), including deriving `currentRemote`/`defaultRemote` used to resolve git-proxy environment (`envForRemoteOperation`) for push/pull/fetch, and as the fallback source of remote URL when `branch.remote` is unset (explicitly called out as a "critical path" safeguard in `app-store.ts`): [3](#0-2) 

Because `safeRemote` here derives from `remoteName`/`remote.url`, and that remote can trace back to the attacker-chosen "default remote" rather than a name explicitly tied to the branch, an unnoticed swap can route the git proxy/URL resolution to the wrong endpoint. There is no guard in `findDefaultRemote` or its call sites that cross-checks the picked remote's URL against a known-good GitHub repository association before treating it as canonical (unlike `repositoryMatchesRemote`/`urlMatchesRemote` in `repository-matching.ts`, which do exist but are not invoked here to validate the "default remote" pick itself).

### Impact Explanation
If Desktop's notion of "default remote" silently resolves to an attacker-supplied remote instead of the legitimate `origin`, subsequent proxy-configuration/env resolution and remote-URL fallback logic that assumes `defaultRemote`/`currentRemote` is trustworthy can be steered toward it. This does not achieve remote code execution by itself, but it corrupts what the user believes they are pushing to / fetching from, and can be leveraged to redirect network traffic (and by extension credentials sent for auth, e.g. via `envForRemoteOperation`) toward an attacker-controlled host without any explicit UI warning — matching the "silent corruption of what the user commits/pushes" and "credential exfiltration" categories in scope.

### Likelihood Explanation
Moderate. It requires the victim to open/clone a repository that lacks an `origin` remote (not the common case for repos cloned normally through Desktop's own clone flow, which sets `origin`), so the attacker vector is repos obtained through other means (zipped repo drops, `git clone --origin <name>`, tarballs with a pre-populated `.git`, or a maliciously modified `.git/config` in a shared/synced folder). No admin rights, malware, or leaked credentials are required — only that the user opens Desktop against an attacker-prepared repository directory, which is within the documented in-scope attacker capability ("attacker controls a cloned/fetched repository").

### Recommendation
- Do not blindly fall back to `remotes[0]`; require an explicit signal (e.g., only fall back when there is exactly one remote, or validate the candidate remote's URL against the known GitHub repository association via `repositoryMatchesRemote`) before treating it as the canonical default.
- Surface a UI warning when the "default remote" is being inferred from a non-`origin`, unmatched remote so users can catch unexpected redirections.
- Audit all consumers of `findDefaultRemote`/`defaultRemote`/`currentRemote` (`git-store.ts`, `app-store.ts`) to ensure none use it for security-relevant decisions (proxy resolution, credential scoping) without re-validating against the associated `GitHubRepository`.

### Proof of Concept
1. Attacker prepares a git repository directory with no remote named `origin`, but a remote named `0-mirror` (sorts first alphabetically) pointing at `https://attacker.example/evil.git`, plus optionally a legitimately-named-looking remote `zzz-real` pointing at the real GitHub project.
2. Victim obtains this directory (e.g., via a shared archive, synced folder, or any means other than Desktop's own "Clone repository" flow) and opens it in GitHub Desktop ("Add local repository").
3. `getRemotes` returns `[0-mirror, zzz-real]` alphabetically; `findDefaultRemote` finds no `origin` match and returns `remotes[0]` = `0-mirror`. [1](#0-0) 
4. This attacker-controlled remote becomes `gitStore.defaultRemote`/`currentRemote`, used as the fallback remote for push/proxy-env resolution paths in `app-store.ts` whenever a branch lacks its own recorded remote. [3](#0-2) 
5. Without any explicit user confirmation, operations that rely on this fallback resolve against the attacker's host instead of the legitimate one.

  remotes: ReadonlyArray<IRemote>
): IRemote | null {
  return remotes.find(x => x.name === 'origin') || remotes[0] || null
}
