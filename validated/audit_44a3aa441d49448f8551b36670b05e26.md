The CVE's bug class is "prefix/framing mishandling that causes subsequent bytes to be interpreted under the wrong context." I'll check Serai's transcript framing and the in-scope FROST/bitcoin code for a matching pattern.### Title
`SignableTransaction::new` omits the OP_RETURN data output from all fee/vsize calculations, so transactions carrying data under-pay fees and miscompute change - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The zsh CVE's bug class is "the beginning of an input determines how the rest is handled, and later content is processed under the wrong accounting." In `bitcoin-serai`, `SignableTransaction::new` pushes the OP_RETURN data output into `tx_outs` **before** computing the transaction weight and fee, but every call to `calculate_weight_vbytes` is fed only `payments` — the data output is never accounted for. The result is a signed transaction whose fee rate is below the caller-specified `fee_per_vbyte` (and possibly below the relay minimum that was checked against the underestimated vsize), plus a change output computed from the wrong fee.

### Finding Description
`SignableTransaction::new` builds `tx_outs`, including an attacker-influenced OP_RETURN output when `data` is present [1](#0-0) . It then computes the transaction's weight and virtual size via `calculate_weight_vbytes(tx_ins.len(), payments, None)` [2](#0-1) . Inside `calculate_weight_vbytes`, the output list is constructed **only** from `payments` plus an optional `change` output [3](#0-2)  — the already-appended OP_RETURN output is never passed in. The same omission occurs in the change-path recomputation at send.rs:225-227. Consequently `needed_fee = fee_per_vbyte * vbytes` is computed over a vsize missing the OP_RETURN output (~11 + len bytes, up to ~91 vbytes for the 80-byte max data checked at send.rs:171), and the minimum-relay-fee check at send.rs:211 also uses the underestimated `vbytes`.

The deposit/data path is attacker-reachable: `data` on a `SignableTransaction` ultimately originates from depositors' `InInstruction` payloads (`extract_serai_data` pulls up to `MAX_DATA_LEN` bytes from any OP_RETURN or witness push in a deposit transaction [4](#0-3) ), so an unprivileged depositor controls whether this code path runs and how large the unaccounted output is.

### Impact Explanation
Two concrete harms:

1. **Under-priced / unrelayable transactions.** With `fee_per_vbyte` near the minimum and a large `data`, the real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` even though the check at send.rs:211 passes (it divides by the underestimated `vbytes`). The resulting transaction is rejected by Bitcoin mempool policy, so the multisig produces a signed transaction that cannot confirm — funds earmarked for that send are unspendable via it.
2. **Incorrect change and fee accounting.** When a change output exists, its value is `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is too small, so change is inflated and the *actual* paid fee (`fee()`, send.rs:138-141) diverges from both the requested rate and `needed_fee` reported to callers — breaking the coordinator's fee bookkeeping for any data-bearing send.

### Likelihood Explanation
Any transaction constructed with `data.is_some()` triggers it deterministically — no timing or collusion needed. Triggering requires only that a public depositor include data in a deposit such that a refund/forward transaction carries an OP_RETURN payload, which is a normal protocol flow. Severity is bounded (Medium): it does not leak key material or forge signatures, but it deterministically produces transactions violating the specified fee policy, which can stall funds.

### Recommendation
Pass the fully-built `tx_outs` (including the OP_RETURN output) into the weight calculation, or compute vbytes after assembling all outputs. The cleanest fix is to refactor `calculate_weight_vbytes` to take `&[TxOut]` instead of `payments`/`change`, and call it with `&tx_outs` for both the no-change and with-change estimates. The minimum-relay check should then use the true vsize.
