### Title
Payout OP_RETURN operator credit is not covered by the withdrawal signature, allowing false operator-payer attribution - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `withdraw()` payout transaction requires the user to authorize spending their withdrawal UTXO with a `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` signature, which cryptographically binds only input 0 and output 0 of the transaction. The OP_RETURN output that records "which operator fronted this withdrawal" (used later by `update_finalized_payouts` and the bridge circuit to determine who is eligible for BitVM2 reimbursement) is a *third*, uncommitted output. Anyone in possession of a valid withdrawal signature can therefore construct and broadcast a payout transaction that correctly pays the withdrawing user (satisfying the signed output) while writing an arbitrary operator's x-only public key into the OP_RETURN output — attributing payer credit to an operator that never authorized or funded that specific transaction.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user payout (index 0), an anchor (index 1), and an OP_RETURN commit to `operator_xonly_pk` (index 2). [1](#0-0) 

The user's authorization signature is verified against `calculate_sighash_txin(0, in_signature.sighash_type)`, and the accompanying error message explicitly documents that the expected sighash type is `SinglePlusAnyoneCanPay`: [2](#0-1) 

`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` only commits the signer to: (a) the specific input being spent (input 0), and (b) the output at the same index (output 0, the user payout). It places **no** constraint on any other input or output in the final transaction — including the anchor output and, critically, the OP_RETURN output that carries the operator's identity.

Downstream, `update_finalized_payouts` scans the confirmed payout transaction for the first OP_RETURN output and unconditionally records whatever x-only public key it finds as `payout_payer_operator_xonly_pk`: [3](#0-2) 

This same trust assumption is baked into the bridge circuit itself, which parses the first OP_RETURN output of the payout transaction and uses it directly as `operator_xonlypk` to compute the `deposit_constant` used in the reimbursement proof — the circuit performs no check that this key belongs to whoever actually funded the payout inputs: [4](#0-3) 

Because the OP_RETURN content is never covered by any cryptographic commitment from the withdrawing user (or from any of the N-of-N verifiers), any party who obtains a valid withdrawal signature (e.g. captured from a broadcast/mempool transaction, or obtained off-chain per the protocol's documented flow) can:
1. Build a new payout transaction reusing the same signed input/output-0 pair,
2. Add their own funding inputs (needed anyway, since ANYONECANPAY requires the assembler to cover the transaction balance),
3. Substitute the OP_RETURN output with an arbitrary registered operator's x-only public key that had nothing to do with funding this transaction,
4. Broadcast/replace-by-fee this transaction so it confirms.

This breaks the intended binding: *the operator credited (via `payout_payer_operator_xonly_pk` / the circuit's `operator_xonlypk`) == the operator that actually paid.* A colluding party can grant an operator false payer credit for a withdrawal it never fronted, and that operator can later use its own N-of-N pre-signed kickoff/round transactions (tied to its own key from deposit setup) to claim the BitVM2 reimbursement flow, without ever having spent bridge funds.

### Impact Explanation
This maps to the Critical impact category "an operator reimbursed for a payout it never funded." The false-payer attribution is entirely unauthenticated at the Bitcoin-transaction level — the only requirement is possession of a valid, previously-issued withdrawal signature, which is not bound to the OP_RETURN payer field by design.

### Likelihood Explanation
Exploitation requires: (1) access to a valid user withdrawal signature for a specific withdrawal (obtainable once any payout attempt for that withdrawal is visible on the network, since witness data is public, or through any leak of the off-chain-shared signature), and (2) collusion with, or self-registration as, a beneficiary operator that has pre-signed kickoff/round transactions for the relevant deposit. This is a multi-step but fully unprivileged and un-authenticated attack path relative to Bitcoin — no verifier, watchtower, or aggregator role is required to construct or broadcast the malicious payout transaction.

### Recommendation
Bind the operator-identity OP_RETURN output to the same signature that authorizes the withdrawal input, e.g. by switching the user's authorization to `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY` if additional operator-funded inputs must remain flexible) so that all outputs, including the OP_RETURN, are committed. Alternatively, require the operator's own signature/commitment over the OP_RETURN output before it is trusted by `update_finalized_payouts` and by the bridge circuit's `operator_xonlypk` derivation.

### Proof of Concept
1. Wait for (or intercept) a broadcast payout transaction `withdraw()` produces for a withdrawal UTXO; extract the witness signature for input 0, which is `SIGHASH_SINGLE|ANYONECANPAY` per [5](#0-4) .
2. Construct a new transaction with: input 0 = the same withdrawal outpoint with the captured signature; output 0 = identical to the original (script_pubkey/value unchanged, satisfying the SINGLE commitment); additional self-funded input(s) to cover fees/balance (permitted by ANYONECANPAY); an OP_RETURN output containing an arbitrary target operator's x-only public key (per encoding in `create_payout_txhandler`, [6](#0-5) ).
3. Broadcast this transaction (optionally as an RBF replacement of the original) so it confirms instead.
4. Once finalized, `update_finalized_payouts` records the substituted operator's x-only public key as the payer for that withdrawal [7](#0-6) , and the bridge circuit will accept that same key as `operator_xonlypk` when computing the reimbursement `deposit_constant` [8](#0-7) , letting that operator pursue reimbursement for a payout it never funded.

/// Creates a [`TxHandler`] for the `payout_tx`.
///
/// This transaction is sent by the operator to front a peg-out, after which operator will send a kickoff transaction to get reimbursed.
///
/// # Inputs
/// 1. UTXO: User's withdrawal input (committed in Citrea side, with the signature given to operators off-chain)
///
/// # Outputs
/// 1. User payout output
/// 2. OP_RETURN output (with operators x-only pubkey that fronts the peg-out)
///
/// # Arguments
/// * `input_utxo` - The input UTXO for the payout, committed in Citrea side, with the signature given to operators off-chain.
/// * `output_txout` - The output TxOut for the user payout.
/// * `operator_xonly_pk` - The operator's x-only public key that fronts the peg-out.
/// * `user_sig` - The user's signature for the payout, given to operators off-chain.
/// * `network` - The Bitcoin network.
///
/// # Returns
/// A [`TxHandler`] for the payout transaction, or a [`BridgeError`] if construction fails.
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
