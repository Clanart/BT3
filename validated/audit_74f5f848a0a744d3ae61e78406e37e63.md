### Title
`SignableTransaction::new` computes weight/fee on a transaction that omits the `OP_RETURN` data output, so the "needed fee" and standardness weight are calculated against a smaller transaction than the one actually signed - (`networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` builds the real output list (`tx_outs`) including an optional `OP_RETURN` output carrying up to 80 bytes of caller-supplied data, but computes the transaction's weight/vbytes — and therefore `needed_fee`, the minimum-relay-fee check, the change-amount decision, and the `MAX_STANDARD_TX_WEIGHT` check — from a synthetic transaction built only from `payments` and `change`. The fee formula is thus evaluated against parameters that do not match the transaction actually signed and broadcast, directly analogous to a swap-math helper using a hardcoded fee while pools charge a different, per-pool fee.

### Finding Description
`SignableTransaction::new` accepts `data: Option<Vec<u8>>` (≤ 80 bytes) and, when present, pushes an `OP_RETURN` `TxOut` onto `tx_outs` at `send.rs:194-202`. However, both calls to `Self::calculate_weight_vbytes` pass `payments` only:

- `send.rs:204`: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);`
- `send.rs:225-226`: `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`

Inside `calculate_weight_vbytes` (`send.rs:62-127`), the synthetic transaction's `output` is built from `payments` plus the optional `change` — the `OP_RETURN` output is never included. Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`, `send.rs:227`) is priced for a smaller vsize than the real transaction. The actual fee paid is `sum(inputs) - sum(outputs)` (`send.rs:138-141`), which is fixed, so the transaction pays a *lower effective sat/vbyte* than the caller requested.
2. The minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (`send.rs:211`) is evaluated against the understated `vbytes`, so a transaction whose true size pushes its fee rate below the relay minimum is accepted and signed anyway.
3. The change-creation decision (`send.rs:228-234`) uses `fee_with_change` computed without the `OP_RETURN`; more importantly the `weight > MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) uses `weight` that excludes the `OP_RETURN` output, so a borderline transaction can exceed standardness weight in practice.
4. The threshold group then signs this transaction via `TransactionMachine`/`TransactionSignMachine` (`send.rs:273-398`), producing a fully valid but under-priced/non-standard Bitcoin transaction.

### Impact Explanation
When `data` is supplied, the signed transaction's real fee rate is strictly lower than the `fee_per_vbyte` the caller specified, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` while passing the `TooLowFee` check. Such a transaction is validly signed by the FROST threshold group but will not be relayed or mined, leaving the inputs unspendable under that signature until an entirely new signing session is run (inputs use `Sequence::MAX`, so no RBF/CPFP remedy is built in). A caller that supplies `data` and a marginal `fee_per_vbyte` — inputs it fully controls — deterministically obtains a stuck, non-propagating transaction, i.e., a mismatch between the documented parameter (`fee_per_vbyte`) and what the signed bytes actually pay.

### Likelihood Explanation
The bug triggers deterministically whenever `data.is_some()`: every `OP_RETURN`-carrying transaction is mispriced by the size of that output (~9 + len(data) bytes of output, non-witness). Whether the effective fee actually drops below the relay minimum depends on how close `fee_per_vbyte` is to the boundary, but the systematic under-pricing and the unenforced `MAX_STANDARD_TX_WEIGHT` bound occur in all cases. Reachability is limited to whoever legitimately drives `SignableTransaction::new` (the wallet's own transaction construction path), which tempers severity to Medium.

### Recommendation
Include the `OP_RETURN` output in the size calculation. The simplest fix is to move the `data`/`OP_RETURN` push before the weight calculations and pass the full output list (or the data length) into `calculate_weight_vbytes` — e.g., extend `calculate_weight_vbytes` to take the `data` argument and push the same `TxOut` it will actually use, so `vbytes`, `vbytes_with_change`, `needed_fee`, the min-relay check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will be signed.

### Proof of Concept
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

```rust
// tx_outs gets the OP_RETURN output...
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(PushBytesBuf::try_from(data).unwrap()),
  })
}

// ...but the weight/vbytes used for fee, min-relay, change, and
// MAX_STANDARD_TX_WEIGHT are computed from `payments` only:
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds its synthetic `Transaction` with `output` derived solely from `payments` and `change` (`send.rs:85-99`), so `tx.weight()` at `send.rs:101` never accounts for the `OP_RETURN` output that `tx_outs` — and therefore the signed `self.tx` — contains. Construct a `SignableTransaction` with `data = vec![0; 80]`, `change = None`, and `fee_per_vbyte` such that `fee_per_vbyte * vbytes` just exceeds `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`; the call returns `Ok`, yet the real transaction's effective fee rate is below the relay minimum, producing a signed transaction that will not propagate.
