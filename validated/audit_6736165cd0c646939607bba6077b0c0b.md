### Title
Attacker-controlled `ReceivedOutput` binds a wallet script to an unrelated outpoint, bypassing spendability validation - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`ReceivedOutput::read` accepts the scalar `offset`, claimed `TxOut`, and claimed `OutPoint` as three independent attacker-controlled fields, without verifying that the outpoint actually references the decoded output or that the decoded output was produced by the registered scanner. [1](#0-0) 

The later `SignableTransaction::multisig` check only verifies that the supplied `offset` derives a key whose P2TR script equals the attacker-supplied `TxOut.script_pubkey`; it does not authenticate the `OutPoint` or compare the decoded `TxOut` with the output actually stored at that outpoint. [2](#0-1) 

### Finding Description

`Scanner::scan_transaction` safely constructs `ReceivedOutput` by looking up a transaction output's `script_pubkey`, attaching the registered offset, and deriving the outpoint from the containing transaction's actual TXID and output index. [3](#0-2) 

The serialized form loses that provenance: `ReceivedOutput::read` accepts any canonical scalar, any consensus-decodable `TxOut`, and any consensus-decodable `OutPoint`, then returns them as one supposedly spendable output. [1](#0-0) 

This is the same confusion class as the external report: the bytes select the verification context rather than resolving the object and then checking the request against that resolved object. Here, the attacker chooses the scanner-derived equivalent—`offset` and `script_pubkey`—while independently choosing the claimed chain object—the `OutPoint`—instead of deriving both from one authenticated transaction output. [4](#0-3) 

`SignableTransaction::new` trusts the resulting `output.value`, `offset`, and `outpoint` when calculating input value and constructing transaction inputs. [5](#0-4) 

During signing setup, `multisig` checks only that `p2tr_script_buf(keys.offset(offset).group_key())` equals the supplied `prevouts[i].script_pubkey`; a forged `ReceivedOutput` that uses a registered wallet script therefore passes even when its `OutPoint` is unrelated, nonexistent, or belongs to another output. [6](#0-5) 

### Impact Explanation

An unprivileged party who can submit serialized `ReceivedOutput` bytes can cause the wallet to report an arbitrary amount as received and spendable by pairing a registered Serai Taproot script with an unrelated or fabricated `OutPoint`. [7](#0-6) 

The forged record can be used to satisfy `SignableTransaction::new`'s input-value accounting and can proceed through `multisig` because the offset-to-script check passes for the attacker-supplied prevout. [8](#0-7) 

The resulting transaction commits to the fabricated prevout through `Prevouts::All`, so threshold participants can be induced to produce signatures for a transaction whose claimed input does not correspond to the selected on-chain outpoint. [9](#0-8) 

### Likelihood Explanation

The attack requires only public knowledge of a scanner-registered P2TR script and the ability to provide serialized `ReceivedOutput` data to a caller. [1](#0-0) 

No private key, malformed curve encoding, validator compromise, or inconsistent preprocess is needed because both parsed fields are syntactically valid; the vulnerability is the missing semantic binding between the claimed prevout and the actual output. [3](#0-2) 

The forged record passes the only local spendability check when it uses a registered script and its corresponding offset, making this deterministic rather than probabilistic. [10](#0-9) 

### Recommendation

Do not treat `ReceivedOutput::read` as establishing scanner provenance. [1](#0-0) 

Replace it with a contextual API such as `Scanner::read_received_output(reader)` that rejects a decoded `output.script_pubkey` unless `self.scripts.get(&output.script_pubkey) == Some(&offset)`. [11](#0-10) 

Authenticate the `OutPoint` against consensus data by resolving it to the actual transaction output—or preferably reconstruct `ReceivedOutput` only through `scan_transaction`, where the TXID and `vout` are derived from the observed transaction. [3](#0-2) 

If serialized records must cross trust boundaries, include authenticated provenance, such as the containing transaction or a Merkle/block proof, and rebuild the `TxOut` from that authenticated source instead of accepting an independently supplied `TxOut`. [12](#0-11) 

### Proof of Concept

```rust
use bitcoin_serai::{
  bitcoin::{
    consensus::Encodable,
    Amount, OutPoint, TxOut,
  },
  wallet::{p2tr_script_buf, ReceivedOutput, SignableTransaction},
};
use frost::curve::Secp256k1;
use k256::Scalar;

// `registered_script` is any script already registered in Scanner::scripts,
// such as the base tweaked threshold key's P2TR script.
let registered_script = p2tr_script_buf(base_group_key).unwrap();

let forged_output = TxOut {
  value: Amount::from_sat(100_000_000),
  script_pubkey: registered_script,
};

// This can reference a nonexistent output or an output belonging to another
// script. ReceivedOutput::read does not resolve or authenticate it.
let forged_outpoint = OutPoint::null();

let mut encoded = Vec::new();
encoded.extend_from_slice(&Scalar::ZERO.to_bytes());
forged_output.consensus_encode(&mut encoded).unwrap();
forged_outpoint.consensus_encode(&mut encoded).unwrap();

let received = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(received.value(), 100_000_000);

// The fabricated amount is counted as available input.
let signable = SignableTransaction::new(
  vec![received],
  &payments,
  change,
  None,
  fee_per_vbyte,
).unwrap();

// This succeeds because offset ZERO derives the same script that was embedded
// in forged_output, even though forged_outpoint does not identify that output.
let machine = signable.multisig(&threshold_keys).unwrap();
```

`ReceivedOutput::read` accepts this record because it never checks that the offset belongs to the decoded script or that the decoded output exists at the decoded outpoint. [1](#0-0) 

`SignableTransaction::new` then treats `received.output.value` as input value and inserts `received.outpoint` into the spend transaction. [13](#0-12) 

`multisig` accepts the record whenever the supplied offset maps to the supplied script, leaving the claimed outpoint unauthenticated. [2](#0-1)
