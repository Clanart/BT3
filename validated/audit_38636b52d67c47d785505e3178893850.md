### Title
Transaction-level InInstruction data applied to every scanned External output in the same transaction enables cross-output hijacking of a deposit's instruction - (File: processor/src/networks/bitcoin.rs)

### Summary
When the Bitcoin processor scans a block, `get_outputs` extracts the InInstruction payload (`data`) once per *transaction* and then attaches that same payload — plus a `presumed_origin` taken only from `tx.input[0]` — to **every** output in that transaction whose script matches the External offset. The instruction is not bound to a specific output index, amount, or destination identity. In any transaction containing more than one Serai-bound output where the InInstruction was not authored for all of them (e.g., a coinjoin/PayJoin-style transaction, or a batched deposit created by a third party), an unprivileged party who contributes an OP_RETURN InInstruction output can have their instruction (such as a `Refund` to an attacker address) applied to outputs funded by other participants — an improper access control violation where one party's untrusted data governs another party's deposit.

### Finding Description
In `Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-740`), the scan works as follows:

1. Each non-coinbase transaction is scanned; every output matching a registered script becomes an `Output` with a `kind` (`External`, `Branch`, `Change`, `Forwarded`) derived from the script→offset map (`lines 691-700`).
2. If the transaction produced any outputs, `presumed_origin` is computed **once** from `tx.input[0]`'s spent script (`lines 707-729`).
3. `extract_serai_data(tx)` is called **once** and the resulting `data` is cloned into *every* output of `kind == OutputType::External`; `presumed_origin` is likewise cloned into all outputs (`lines 730-735`):

```rust
let data = Self::extract_serai_data(tx);
for output in &mut outputs {
  if output.kind == OutputType::External {
    output.data.clone_from(&data);
  }
  output.presumed_origin.clone_from(&presumed_origin);
}
```

`scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) itself only matches on `output.script_pubkey`; it has no notion of which output an instruction belongs to. The processor then consumes `output.data` to build plans (e.g., `PlanFromScanning::Refund(output, refund_to)` in `processor/src/multisigs/mod.rs:585-596`) and treats `presumed_origin` as the depositor identity.

There is no binding between the InInstruction payload and a specific vout, no requirement that a transaction contain exactly one External output before honoring the instruction, and no check that the instruction author controls the inputs funding each output.

### Impact Explanation
An unprivileged party can cause their InInstruction to be applied to a deposit they did not fund:

- **Coinjoin / multi-party transactions**: In a transaction where a victim's input funds an output to Serai's external address, an attacker co-participating adds their own input/output plus an OP_RETURN-encoded InInstruction (e.g., a `Refund` naming an attacker-controlled Serai address). Because `data` is cloned to all `External` outputs, the victim's output is processed with the attacker's instruction — diverting the refund/credit path to the attacker. This is a theft of the deposit's instructed disposition.
- **Batched deposits**: A service batching deposits to Serai for multiple users in one transaction sees a single instruction govern all External outputs, misattributing data across users.
- **Origin spoofing**: `presumed_origin` is taken solely from `tx.input[0]` and applied to all outputs, so an attacker who controls input position 0 in a multi-party transaction causes every output to be attributed to an address they chose.

The advisory class is "improper access control — a malicious context can access another context's inputs/outputs"; here, attacker-supplied transaction data reaches and governs outputs belonging to a different logical deposit. Impact: funds received by Serai are dispositioned (refunded/credited) according to an instruction authored by an unrelated party — i.e., funds may be sent to an attacker-specified address or credited to the wrong depositor.

### Likelihood Explanation
Likelihood is moderate:

- The attack requires the victim's deposit to be made inside a transaction the attacker can co-author (coinjoin, PayJoin, batching intermediaries). Standard single-party deposits are safe since the depositor controls the whole transaction.
- No cryptographic break, key access, validator collusion, or RPC manipulation is needed — only the ability to add an OP_RETURN InInstruction and place an input early in a shared transaction, both of which are fully permissionless on Bitcoin.
- Coinjoin usage (Wasabi, JoinMarket, PayJoin) is common for Bitcoin; deposit flows routed through batching services are also realistic.

### Recommendation
Bind the InInstruction to the specific output it applies to:

- Associate `data` with exactly one External output (e.g., the first External output, or an output index committed inside the InInstruction itself) rather than cloning it to all External outputs in the transaction.
- Alternatively, reject transactions containing more than one External-kind output when a non-empty instruction is present, or ignore `data` for any transaction with >1 External output.
- Do not derive `presumed_origin` solely from `tx.input[0]`; either iterate inputs or treat multi-party inputs as ambiguous/unknown.
- Document that deposits must be made in dedicated transactions under the depositor's sole control if per-output binding is not implemented.

### Proof of Concept
```
1. Victim V intends to deposit to Serai's external address A_ext = p2tr_script_buf(group_key)
   inside a coinjoin-style transaction T.
2. Attacker M joins T, contributes an input, and adds an OP_RETURN output encoding
   InInstruction::Refund(attacker_serai_address). M also arranges to occupy tx.input[0]
   (or simply relies on data applying regardless of input position).
3. T is mined. Bitcoin::get_outputs scans T:
   - scanner.scan_transaction(T) returns V's output (kind = External) — and any other
     External outputs present.
   - extract_serai_data(T) returns M's Refund instruction.
   - The loop at bitcoin.rs:731-736 clones M's data into V's output and sets its
     presumed_origin to the spender of tx.input[0] (M).
4. The multisig code consumes V's output under PlanFromScanning::Refund(output,
   attacker_serai_address) (multisigs/mod.rs:585), so V's deposit is refunded to M.
   No signature, key, or node compromise was required — only untrusted transaction
   bytes crossing the per-output authorization boundary.
```
