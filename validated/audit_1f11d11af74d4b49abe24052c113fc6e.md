Found the analog: `requestERC20Transfer()` in `BridgeTransferERC20.sol` pulls tokens via `safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then unconditionally proceeds with `_requestERC20Transfer()` which emits `RequestValueTransfer` and credits the exact `_value` requested, without verifying how many tokens the bridge actually received.

### Title
Fee-on-transfer / non-standard ERC20 tokens cause accounting mismatch in Bridge ERC20 deposits - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`requestERC20Transfer()` and the internal `_requestERC20Transfer()` credit the requested `_value` (and fee) as the amount transferred into the Bridge without checking the Bridge's actual token balance delta, so any registered ERC20 token that charges a transfer fee (or otherwise delivers less than the requested amount) causes the Bridge to over-credit the deposit relative to what it actually received.

### Finding Description
`requestERC20Transfer` pulls tokens with: [1](#0-0) 

It performs `IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then immediately calls `_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData)`, which emits `RequestValueTransfer` with the exact `_value` and pays fees via `_payERC20FeeAndRefundChange`: [2](#0-1) 

Nowhere does the code check the Bridge contract's `balanceOf(address(this))` before and after the `safeTransferFrom` call to confirm it actually received `_value.add(_feeLimit)`. If the registered ERC20 token (`onlyRegisteredToken` only checks that the token address is on an allow-list, not that it is a "clean" ERC20, per `onlyRegisteredToken` modifier used here) implements a fee-on-transfer, deflationary, or rebasing mechanism, the Bridge will hold strictly less than `_value + _feeLimit` while still emitting `RequestValueTransfer` for the full `_value`, and (in `modeMintBurn`) burning the full requested `_value` via `ERC20Burnable(_tokenAddress).burn(_value)` even though it never actually held that much.

This mirrors the reported bug class exactly: crediting a deposit based on the caller-supplied amount parameter instead of the measured balance delta after `transferFrom`.

### Impact Explanation
On the counterpart chain, `handleERC20Transfer` will release/mint the full `_value` to the recipient based on the `RequestValueTransfer` event, per: [3](#0-2) 
If the source-side Bridge actually received less than `_value` (fee-on-transfer token) while non-mint-burn mode holds real liquidity, the Bridge's real token reserve is silently drained over repeated deposits/withdrawals — a supply/liquidity accounting divergence that leads to insufficient balance for legitimate later `handleERC20Transfer`/withdraw calls, or (worse) an ability for other depositors to drain the shared reserve since the bridge believes it holds more collateral than it does. In `modeMintBurn` mode, burning the full nominal `_value` from a supply that a fee-on-transfer token never actually delivered can compound the discrepancy between claimed and real balances tracked by the token's own accounting on the two chains.

### Likelihood Explanation
Reachable by any unprivileged caller who calls the public `requestERC20Transfer` (or the ERC20 `onERC20Received` 1-step hook) with an already-`onlyRegisteredToken` token. `onlyRegisteredToken`/`onlyUnlockedToken` only gate on an operator-curated allow-list of token addresses, not on token transfer semantics; an operator could register (intentionally or mistakenly) any ERC20 that later turns on/adds fee-on-transfer, deflationary burn-on-transfer, or rebasing behavior (as USDC itself reserves the right to do), at which point every subsequent deposit through this exact code path silently mis-accounts.

### Recommendation
In `requestERC20Transfer`/`_requestERC20Transfer`, measure the Bridge's token balance before and after the `safeTransferFrom` call and use the actual received delta (rather than the caller-supplied `_value`/`_feeLimit`) for fee computation, the `RequestValueTransfer` event, and (if `modeMintBurn`) the `ERC20Burnable.burn` amount.

### Proof of Concept
1. Operator registers a token via the bridge's token-registration flow that is upgradeable/pausable-fee ERC20 (or any token later modified to add a transfer fee), passing `onlyRegisteredToken`.
2. Token owner turns on a transfer fee (e.g., 1%) — analogous to USDC's fee-on-transfer switch being turned on.
3. User calls `requestERC20Transfer(token, to, value=100, feeLimit=0, extraData)`. `safeTransferFrom` moves `msg.sender -> bridge` for nominal `100`, but bridge actually receives `99` due to the fee.
4. `_requestERC20Transfer` still emits `RequestValueTransfer(..., _value=100, ...)`, and if `modeMintBurn` is true, calls `ERC20Burnable(token).burn(100)` even though bridge only holds `99` (this call could even revert due to insufficient balance, or succeed while draining other users' funds if the bridge holds pooled liquidity).
5. On the target chain, `handleERC20Transfer` releases/mints `100` tokens to `_to`, exceeding what was actually collected on the source chain — demonstrating the accounting divergence and value leakage described in the referenced report's bug class.

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }
