### Title
`SignableTransaction::new` computes the fee from a weight snapshot taken before the OP_RETURN output is added, underpaying the fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is "checkpoint/commit a value derived from state read *before* the mutation that should have been included in it." In `SignableTransaction::new`, the weight/vsize used to derive `needed_fee` is checkpointed from the `payments` slice only, *before* the OP_RETURN `data` output — which is already pushed into `tx_outs` — is accounted for. The transaction is then built with the larger output set while paying the smaller, stale fee.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output carrying the caller-supplied `data` is appended to `tx_outs` at `networks/bitcoin/src/wallet/send.rs:194-202`. Immediately after, at `send.rs:204`, the fee is derived from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which reconstructs a template transaction containing only `payments` (see `send.rs:85-93`) — the `data` output is never included. The same stale template is reused for the change calculation at `send.rs:225-226`. The final `SignableTransaction` is then constructed with `tx_outs` (which includes the OP_RETURN output) at `send.rs:245-255`, so the real transaction is larger than the one the fee was computed for. Every input is also created with `Sequence::MAX` (`send.rs:182`), disabling BIP-125 replace-by-fee, so the underpriced transaction cannot be fee-bumped.

### Impact Explanation
An unprivileged party can supply up to 80 bytes of `data` (checked at `send.rs:171-173`). The OP_RETURN output adds roughly 90+ serialized bytes (~90+ vbytes of weight) that are never priced into `needed_fee`. Since the minimum-relay-fee guard at `send.rs:211` is also evaluated against the stale `vbytes`, a transaction built at `fee_per_vbyte` near the relay minimum will have an effective fee rate well below `DEFAULT_MIN_RELAY_TX_FEE` once the data output is included. The threshold-signed transaction the multisig produces is valid but non-relayable/non-confirmable, locking the referenced UTXOs until a new signing round produces a corrected transaction — an out-payment liveness failure reachable purely through attacker-controlled `data` fed into a public `sign` path.

### Likelihood Explanation
Any code path that constructs a `SignableTransaction` with attacker-influenced `data` and a `fee_per_vbyte` near the minimum triggers it deterministically; it is purely a function of public inputs, requiring no collusion. Severity is Medium: no funds are stolen or signatures forged, but payments are systematically delayed/stuck whenever the data output materially inflates the transaction relative to the priced size.

### Recommendation
Build the full output set (payments + OP_RETURN + potential change) before computing weight, i.e., call `calculate_weight_vbytes` with `tx_outs` (or an equivalent enumeration) rather than the `payments` slice, and compute the change-bearing variant against the same complete output list. Alternatively, drop the template reconstruction and compute `tx.weight()` on the actual candidate `Transaction` before finalizing `needed_fee`.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` is chosen so `needed_fee` just passes the `DEFAULT_MIN_RELAY_TX_FEE` check at `send.rs:211`.
2. The returned transaction's `fee()` (`send.rs:138-141`) equals `input_sat - payment_sat - change`, which equals `needed_fee` priced for a tx *without* the OP_RETURN output.
3. Compute the real `tx.weight()`/vsize of `transaction()` — it exceeds `vbytes` by the OP_RETURN output's serialized size, so `fee() / actual_vbytes < fee_per_vbyte` and potentially `< DEFAULT_MIN_RELAY_TX_FEE / 1000`, yielding a signed transaction Bitcoin nodes will not relay.
