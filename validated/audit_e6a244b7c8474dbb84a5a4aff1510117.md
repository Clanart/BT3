### Title
`ReceivedOutput::read` accepts an arbitrary offset/script_pubkey pair without verifying the offset actually derives the output's key, letting untrusted bytes register unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Liferay advisory (CWE-732, incorrect permission assignment) concerns a resource being exposed because a required authorization/validity check on who may access it was missing. The Serai analog is a missing *binding* check on a critical resource: `ReceivedOutput` couples a `Scalar` offset (which determines the spend key `key + offset*G`) with a `TxOut` and `OutPoint`, yet `ReceivedOutput::read` deserializes all three fields from untrusted bytes with no check that `output.script_pubkey == p2tr_script_buf(key + offset*G)`. Any consumer that credits deposits or reports balances based on deserialized `ReceivedOutput`s can be shown "funds received" which the threshold key cannot actually spend.

### Finding Description
`ReceivedOutput` is defined at `networks/bitcoin/src/wallet/mod.rs:89-97` with three fields: `offset`, `output` (a `TxOut`), and `outpoint`. Its deserializer at `networks/bitcoin/src/wallet/mod.rs:122-134` reads a canonical scalar via `Secp256k1::read_F` and then consensus-decodes an arbitrary `TxOut` and `OutPoint`. It performs no verification that the decoded `script_pubkey` equals `p2tr_script_buf(base_key + GENERATOR * offset)` — it cannot, because the base key is never bound into the object.

The only place the offset-to-script binding is ever enforced is deep in the signing path, in `SignableTransaction::multisig` at `networks/bitcoin/src/wallet/send.rs:276-279`, which returns `None` when `p2tr_script_buf(offset.group_key())` mismatches the claimed `prevouts[i].script_pubkey`. Between deserialization and that late check, the forged `ReceivedOutput` is treated as real: `value()` (mod.rs:116-118) returns the attacker-chosen `TxOut.value`, and `SignableTransaction::new` (send.rs:175-176) sums `input.output.value` directly into `input_sat` for fee and change accounting.

The serializer is symmetric — `write`/`serialize` (mod.rs:137-148) emit exactly the attacker-controlled fields — so a forged `ReceivedOutput` round-trips identically through `ReceivedOutput::read`, matching the untrusted-bytes reachability surface.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (a listed reachability surface for this audit) can fabricate an output crediting any `value` to a `script_pubkey` the group does not control, while attaching an arbitrary `offset`. Downstream accounting observes `value()` and `input_sat` and reports those funds as received; only at `multisig()` time does the transaction fail (returning `None`), meaning the credited balance was never spendable — the exact "funds reported received that are not spendable" acceptance criterion. Additionally, a mismatched `offset`/`outpoint` pair causes the entire `SignableTransaction::multisig` call to abort, so one forged input in a batch DoSes the signing of all genuine inputs alongside it.

### Likelihood Explanation
`ReceivedOutput` is explicitly designed for transport and persistence (`read`/`write`/`serialize` are public, and the processor's `Output::read` at `processor/src/networks/bitcoin.rs:156` embeds it in its own untrusted deserialization). The forgery requires only writing a scalar, a `TxOut`, and an `OutPoint` — no key knowledge, no signature, no collusion. Exploitation requires a consumer that credits balances before the `multisig()` binding check, which is the natural integration pattern; the library itself never warns that `read` yields an unvalidated claim.

### Recommendation
Bind the resource to its claim: either store the base `ProjectivePoint` in `ReceivedOutput` and have `read` (or a separate `verify(key)` method, invoked by all consumers immediately after `read`) assert `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`, or make `read` private and only construct `ReceivedOutput` via `Scanner::scan_transaction`, which already produces correctly-bound instances. Consumers should treat `ReceivedOutput`s not originating from `scan_transaction`/`scan_block` as untrusted until the offset binding is verified, rather than relying on the late `multisig()` check.

### Proof of Concept

// A genuine output: script pays to key + offset*G
let real: ReceivedOutput = scanner.scan_transaction(&tx).remove(0);

// Forgery: keep a valid offset, claim an arbitrary high-value TxOut
// paying to an attacker key, and any outpoint.
let forged_txout = TxOut {
  value: Amount::from_sat(21_000_000_0000_0000), // 21M BTC claimed
  script_pubkey: attacker_p2tr_script,           // key + offset*G does NOT match
};
let forged = ReceivedOutput { /* via read of crafted bytes */
  offset: real.offset(),
  output: forged_txout,
  outpoint: OutPoint::new(attacker_txid, 0),
};

// ReceivedOutput::read accepts it: no binding check at mod.rs:122-134.
// forged.value() reports 21M BTC; SignableTransaction::new counts it in
// input_sat (send.rs:175) for fee/change math.
// Only multisig() (send.rs:277) notices, returning None — the balance was
// already reported, is unspendable, and the abort kills co-batched real inputs.
