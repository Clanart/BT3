### Title
Remote CPU exhaustion via quadratic Lagrange interpolation in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts an attacker-supplied `t`/`n` pair up to `u16::MAX`, deserializes that many verification shares, and then computes the group key with `O(t²)` Lagrange interpolation. A syntactically valid but semantically useless key object can therefore make parsing consume billions of scalar operations before returning.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the input stream, then reads `n` serialized group elements and calls `ThresholdKeys::new` [1](#0-0) . `ThresholdParams::new` permits any `t <= n <= u16::MAX` [2](#0-1) .

For `Interpolation::Lagrange`, `ThresholdKeys::new` computes the group key by iterating over all `t` participants and calling `interpolation_factor` for each one [3](#0-2) . Each `interpolation_factor` call iterates over the same `t`-participant list to build the Lagrange numerator and denominator [4](#0-3) . This produces `t²` field operations during deserialization.

### Impact Explanation
An unprivileged party who can provide serialized threshold keys can set `t = n = 65535`, provide a valid secret-share scalar, and provide 65,535 canonical group encodings. `ThresholdKeys::read` then performs roughly 4.3 billion scalar multiplications while calculating the group key.

The request can repeatedly stall a verification, signing, or key-loading worker, causing availability loss analogous to the source advisory’s complete-DoS condition. The payload remains small because the participant count is capped by a 16-bit field; the vulnerability is computational amplification rather than memory exhaustion.

### Likelihood Explanation
The input only needs a valid curve ID, valid threshold parameters, one canonical scalar, and `n` canonical group elements. Repeated encodings of `C::generator()` are sufficient because the participants—not the point values—populate the verification-share map [5](#0-4) .

The attack does not require invalid signatures, collusion, private material, malformed encodings, or an out-of-range participant. It works whenever the attacker controls the bytes passed to `ThresholdKeys::read`.

### Recommendation
Bound `t` and `n` to a protocol-supported maximum before reading or interpolating verification shares. For Lagrange interpolation, precompute all coefficients in `O(t)` or another sub-quadratic method, or reject threshold configurations for which the required work exceeds a fixed budget. Perform structural parameter validation before allocating maps or calculating the group key.

### Proof of Concept
```rust
// Serialized ThresholdKeys<C> structure:
//   u32 curve-ID length || C::ID || t || n || i || interpolation ||
//   secret_share || verification_shares[n]

let t = u16::MAX;
let n = u16::MAX;
let i = 1u16;

let mut bytes = Vec::new();
bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
bytes.extend(C::ID);
bytes.extend(t.to_le_bytes());
bytes.extend(n.to_le_bytes());
bytes.extend(i.to_le_bytes());
bytes.push(1); // Interpolation::Lagrange
bytes.extend(C::F::ONE.to_repr().as_ref());

let generator = C::generator().to_bytes();
for _ in 0 .. n {
  bytes.extend(generator.as_ref());
}

// Triggers approximately 65,535² scalar operations inside
// Interpolation::Lagrange while constructing the group key.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```
