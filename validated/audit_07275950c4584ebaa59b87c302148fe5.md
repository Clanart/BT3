### Title
User funds sent directly to the pool contract (`p2_singleton`) address are permanently unclaimable via `PoolWallet.claim_pool_rewards` - ([File: chia/pools/pool_wallet.py])

### Summary
`PoolWallet.claim_pool_rewards()` only "absorbs" coins that appear in `coin_to_height_farmed`, a dict built exclusively from confirmed consensus farming-reward transaction records `tx_store.get_farming_rewards()`. Any coin that is sent to the pool's `p2_singleton_puzzle_hash` outside of that exact consensus reward path (e.g. a user or third party mistakenly sending XCH to the pool-contract/plot-NFT reward address, analogous to sending ETH to a payable batch function) is silently skipped forever, and there is no other wallet-exposed function to spend or recover it. This mirrors the reported Solidity bug class: a function accepts value into a contract-controlled address but the codebase provides no path to withdraw/claim that value if it didn't arrive through the expected flow.

### Finding Description
`claim_pool_rewards` retrieves all unspent coin records for the pool wallet and then filters: [1](#0-0) 

```
unspent_coin_records = await self.wallet_state_manager.coin_store.get_unspent_coins_for_wallet(self.wallet_id)
...
farming_rewards: list[TransactionRecord] = await self.wallet_state_manager.tx_store.get_farming_rewards()
coin_to_height_farmed: dict[Coin, uint32] = {}
for tx_record in farming_rewards:
    height_farmed: uint32 | None = tx_record.height_farmed(...)
    assert height_farmed is not None
    coin_to_height_farmed[tx_record.additions[0]] = height_farmed
```

Then, when iterating unspent coins: [2](#0-1) 

```
first_coin_record = None
for coin_record in unspent_coin_records:
    if coin_record.coin not in coin_to_height_farmed:
        continue
```

Any unspent coin at the `p2_singleton_puzzle_hash` that isn't recorded as a farming reward transaction is unconditionally skipped (`continue`) and never included in an absorb spend. The `create_absorb_spend` helper that actually builds the spend for the p2-singleton coin computes the exact coin identity itself from `pool_parent_id(height, genesis_challenge)` and `calculate_pool_reward(height)` rather than from the actual coin record being iterated, so the entire claim path is hard-wired to only recognize genuine consensus block rewards: [3](#0-2) 

There is no wallet RPC, CLI command, or code path (outside of `claim_pool_rewards`) that lets a plot-NFT/pool wallet owner spend an arbitrary coin sitting at their `p2_singleton_puzzle_hash`. This is a known historical hazard: the project's own changelog documents that coins accidentally sent to the pool contract address are "ignored" by the wallet and that a "backup key" mechanism to claim them was only ever planned ("today are just ignored"): [4](#0-3) [5](#0-4) 

The `.cursor/context/pools.md` design notes independently confirm the same restriction, describing claim as scanning only "known farming rewards": [6](#0-5) 

### Impact Explanation
A wallet user, plotter, or any third party who sends XCH directly to a plot NFT's `p2_singleton_puzzle_hash` (the documented "pool contract address" shown by `pw_status`/`get_wallets`, and which end users can trivially obtain and pay to, e.g. through a mistaken transfer, a mis-configured pool payout, or copy-paste error) permanently loses that XCH: the wallet has no exposed function that spends non-farming-reward coins from that address, matching the "user will lose funds sent to X with no withdrawal path" bug class from the report. This is a genuine, unauthorized-in-effect loss of value for the coin owner (their funds become permanently unspendable through official wallet flows), which is the closest reachable analog to the reported Medium severity issue.

### Likelihood Explanation
This requires no privileged access - any user or counterparty who has the `p2_singleton_puzzle_hash` (which is intentionally shown to users, e.g. via `pw_status`) can trigger the condition simply by sending a standard XCH payment to that address instead of, or in addition to, letting it be paid by consensus block rewards. This is a realistic, low-effort mistake (directly analogous to sending ETH to a payable-but-non-refundable contract function), and the project's own changelog shows this has happened in practice historically ("added a warning to user to not send money to the pool contract address").

### Recommendation
Provide a wallet-level recovery path for coins at `p2_singleton_puzzle_hash` that are not recognized consensus farming rewards - e.g., extend `claim_pool_rewards` (or add a dedicated RPC) to also detect and spend arbitrary unspent coins at the pool singleton's `p2_singleton_puzzle_hash` using `singleton_top_layer.claim_p2_singleton`/`pay_to_singleton_or_delay_puzzle`'s generic claim path (which does not require the coin to match the exact reward-coin id), rather than restricting the claimable set to `coin_to_height_farmed`. At minimum, surface a clear, permanent warning/error (not silent skip) when unspent, unrecognized coins exist at that address, and document/implement the "backup key" recovery mechanism referenced in the changelog.

### Proof of Concept
1. Create a plot-NFT/pool wallet in `SELF_POOLING` or `FARMING_TO_POOL` state; note its `p2_singleton_puzzle_hash` from `pw_status`.
2. From an unrelated wallet, send a standard XCH transaction whose puzzle hash is that `p2_singleton_puzzle_hash` (this is a valid, ordinary coin creation - no farming/consensus reward involved).
3. Call `pw_absorb_rewards` (`PoolWallet.claim_pool_rewards`) on the pool wallet.
4. Observe that the manually-sent coin is present in `unspent_coin_records` but is skipped because it is absent from `coin_to_height_farmed` (built only from `tx_store.get_farming_rewards()`), per: [7](#0-6) 
The coin remains unspent indefinitely; no other wallet RPC/CLI command exists to move it, permanently stranding the sender's XCH.
