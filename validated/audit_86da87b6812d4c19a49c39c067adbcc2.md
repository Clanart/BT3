### Title
Fee and weight accounting in `SignableTransaction::new` ignores the OP_RETURN data output, underestimating the signed transaction's fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` measures the transaction's weight/vbytes using only the payment outputs (and optionally the change output), while the actual transaction being signed also contains an OP_RETURN output carrying up to 80 bytes of attacker/caller-controlled `data`. The signed transaction is therefore larger than the measured one, so `fee_per_vbyte * vbytes` under-prices the real transaction — a direct analog of fee amounts being computed/validated against one representation while the transaction is built with another.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs), the OP_RETURN output is pushed into `tx_outs` at lines 194–202, but the fee/weight estimation at line 204 calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which reconstructs a transaction containing only `payments` (lines 85–93) plus an optional `change` output (lines 95–99). The `data` output is never included in the measured transaction. The same omission occurs on the change path at lines 225–227. As a result:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) are computed on a smaller transaction than the one actually assembled at lines 245–251.
- The minimum-relay-fee check at line 211 and the `MAX_STANDARD_TX_WEIGHT` check at line 241 are likewise evaluated against the smaller, unrepresentative transaction.

`calculate_weight_vbytes` builds its `tx.output` solely from `payments` and `change` (lines 85–99), so the OP_RETURN output's ~10–90 bytes are simply never counted. Callers then sign a transaction whose real `sum(inputs) - sum(outputs)` fee is `input_sat - payment_sat - change`, which corresponds to the underestimated `needed_fee` — the transaction pays `fee_per_vbyte * (real_vsize - measured_vsize)` fewer satoshis than the requested rate.

### Impact Explanation
Medium. The produced, threshold-signed Bitcoin transaction pays a lower fee rate than the caller specified via `fee_per_vbyte`. Because `data` can be up to 80 bytes (checked at line 171), the discrepancy reaches roughly `fee_per_vbyte * ~90` satoshis. Two consequences:

1. The transaction pays materially less than the intended fee rate, degrading confirmation reliability and potentially dropping below relay/mempool acceptance in fee-market conditions, stalling the funds the transaction moves.
2. The minimum-fee guard (`TooLowFee`) and the standardness guard (`TooLargeTransaction`) are evaluated on the wrong (smaller) transaction, so a transaction that should have been rejected or priced differently is signed and broadcast.

This mirrors the reported class: the fee validated/computed (over `payments`/`change` only) is inconsistent with the fee applied to the transaction actually built and signed (which includes the OP_RETURN output).

### Likelihood Explanation
Reachable by anyone able to invoke `SignableTransaction::new` with a non-empty `data` argument — `data` is an untrusted public input that flows only into the OP_RETURN output and is excluded from every weight measurement. Any caller relying on `needed_fee`/`fee()` to reflect the requested rate (e.g., amortizing it over payments, as the processor layer does) will systematically under-fee every transaction carrying data, with the error scaling linearly with both `data.len()` and `fee_per_vbyte`.

### Recommendation
Pass the fully assembled output set (including the OP_RETURN output) into `calculate_weight_vbytes`, or add a `data: Option<&[u8]>`/`extra_outputs` parameter so the measured transaction structurally matches the transaction placed in `SignableTransaction`. Apply the same fix on both the no-change path (line 204) and the change path (lines 225–227), so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the final signed transaction.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics:
// SignableTransaction::new(inputs, &payments, None, Some(data), fee_per_vbyte)

// tx_outs = payments + OP_RETURN(data)            // lines 188-202
// but measured tx = payments only                 // lines 85-93, called at line 204

// needed_fee = fee_per_vbyte * vbytes(payments_only_tx)      // line 206
// signed tx  = inputs -> payments + OP_RETURN(data)          // lines 245-251
// real fee   = input_sat - payment_sat  == needed_fee

// For data of 80 bytes, the OP_RETURN output adds ~90 serialized bytes
// (~90 vbytes, no segwit discount on outputs). The transaction therefore
// pays ~90 * fee_per_vbyte fewer satoshis than the specified rate, and a
// large enough `data` can also push the real weight over
// MAX_STANDARD_TX_WEIGHT while `weight` at line 241 still passes.
```

The bug is structural: `calculate_weight_vbytes` is invoked with `payments` (line 204 and 225–226) while `tx_outs` — which additionally contains the OP_RETURN output from lines 195–201 — is what lands in the signed `Transaction` at line 250.
