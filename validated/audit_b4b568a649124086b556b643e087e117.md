### Title
Removed validators retain their key slots in the DKG-confirmation MuSig, causing signature shares to be verified against stale keys and blame to be mis-attributed - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the Freeverse report (a stale operator recorded at initiation retains authority and corrupts finalization), Serai's DKG confirmation protocol builds its MuSig `ThresholdKeys` over the *full* validator list — including validators already removed for that attempt — while the preprocess/share maps are compacted to only non-removed signers. The removed "operator's" key slot is never revoked from the signing context, so every index in the confirmation session is bound to the wrong public key whenever `removed` is non-empty.

### Finding Description
`SigningProtocol::preprocess_internal` constructs the MuSig participant keys via `musig(musig_context(...), self.key.clone(), participants)` where `participants` is supplied by the caller. [1](#0-0) 

Both `DkgConfirmer::preprocess_internal` and `DkgConfirmer::share_internal` pass `self.spec.validators()` — the complete validator set, with no filtering by `self.removed`. [2](#0-1) 

The preprocesses and shares, however, are re-indexed by `threshold_i_map_to_keys_and_musig_i_map`, which resolves each `Participant` through `spec.i(removed, key)` — skipping removed validators — and then compacts the surviving signers to fresh MuSig indices `1..=k`. [3](#0-2) 

Concretely: with validators `[A, B, C]` where `A` was removed during this DKG attempt (`removed_as_of_dkg_attempt` returns `[A]`):

- `musig()` is instantiated with `participants = [A, B, C]`, so `ThresholdKeys` participant 1 is bound to `A`'s verification share, participant 2 to `B`, participant 3 to `C`.
- The preprocess/share maps are compacted: `B → Participant(1)`, `C → Participant(2)` (our own index is inserted and removed the same way). [4](#0-3) 
- Inside `AlgorithmSignMachine::sign`, `included` = our full-list index plus `{1, 2}`, and `self.params.keys.view(included)` interpolates the verification shares of `A` and `B` — not `B` and `C`. [5](#0-4) 

So `B`'s preprocess and signature share are verified against `A`'s (the removed validator's) key material. The removed validator's authority was never revoked from the participant list — exactly the stale-operator class.

### Impact Explanation
Every non-removed validator positioned after a removed one produces a share that fails verification against the wrong verification share, or — if indices happen to still satisfy the threshold — a confirmation signature over a group key that does not match the validator set agreed on-chain. Worse, the error path in `Transaction::DkgConfirmed` handling maps the blamed `Participant` back through `reverse_lookup_i(&removed, p)` and publishes `RemoveParticipantDueToDkg` against that resolved validator — an *innocent* signer, since `p` indexes into the stale full-list ordering, not the submitter who actually sent bad data. [6](#0-5) 

Result: the DKG confirmation MuSig can never complete whenever any validator was removed for that attempt (liveness failure of key confirmation), and fatal-slash votes can be issued against honest validators whose shares were cryptographically valid.

### Likelihood Explanation
Removal during a DKG attempt is an ordinary protocol event — `RemoveParticipantDueToDkg` votes trigger `fatal_slash`, and `removed_as_of_dkg_attempt` exists precisely because the removed set can be non-empty for a given attempt. [7](#0-6)  No malicious action is required to reach the divergence; a validator removed for being offline suffices. Because the mis-indexing is deterministic, the failure occurs on every such attempt.

### Recommendation
Build the MuSig participant list from the same removed-filtered view used for indexing: in `DkgConfirmer::preprocess_internal` and `share_internal`, compute `participants` as `spec.validators().iter().map(|v| v.0).filter(|k| spec.i(&self.removed, *k).is_some()).collect()` (equivalently, derive the participant list inside `threshold_i_map_to_keys_and_musig_i_map` and reuse it for `musig()`), so that `Participant(i)` in the `ThresholdKeys` corresponds to the same key as the compacted `musig_i` in the preprocess/share maps. Alternatively, have `musig()` consume `(Participant, key)` pairs rather than a positional list.

### Proof of Concept
1. Validator set `[A, B, C]` (threshold 2). During DKG attempt `n`, `A` is fatally slashed (`RemoveParticipantDueToDkg`), so `removed_as_of_dkg_attempt(txn, genesis, n) = [A]`.
2. `B` calls `dkg_confirmation_nonces` → `DkgConfirmer::preprocess()` → `musig(ctx, key_B, [A, B, C])`; `B` is `Participant(2)`. `B`'s published preprocess is accumulated under `B`'s threshold index. [8](#0-7) 
3. In `share`/`complete`, `threshold_i_map_to_keys_and_musig_i_map` compacts `{B→1, C→2}` and `share_internal` rebuilds keys over `[A, B, C]`. `B`'s machine has `i=2`; the map labels `B`'s preprocess as participant `1`.
4. `sign()` forms `included = {1, 2}` → `view({1,2})` interpolates verification shares of `A` and `B`. `C`'s share (participant 2) verifies against `B`'s share; `B`'s share (participant 1) verifies against `A`'s — both fail, or produce a signature for the wrong aggregate key. [9](#0-8) 
5. `complete` returns `Err(Participant(1))`; the handler resolves index 1 through the removed-filtered lookup to `B` and publishes `RemoveParticipantDueToDkg { participant: B }` — fatal-slashing an honest validator — while the confirmation signature never finalizes. [10](#0-9) 

Caveat: I verified the indexing mismatch statically; the MuSig `i()` assignment is positional over the passed `participants` list per `musig(...)` usage at line 119, and the compacted remap at lines 241-245. I could not fully trace `dkg_musig::musig`'s internals within the available iterations, so the exact binding of participant index to key relies on the positional convention evident from the call site and the remap helper's design.
