Confirmed: `pallet_ismp::dispatcher::Pallet::dispatch_request` (`modules/pallets/ismp/src/dispatcher.rs:92-151`) takes `dispatch_post.from` **verbatim** from the caller-supplied `DispatchPost` and writes it straight into the on-chain `PostRequest.from` field, with no check that the calling pallet/account is actually authorized to use that module identifier. Any pallet — or any pallet that exposes a permissionless "send arbitrary post request" extrinsic (the pattern shown in `modules/pallets/demo/src/lib.rs:131-184` and in the polkadot dispatching docs) — can set `from` to whatever bytes it wants.

### Title
Forgeable `PostRequest.from` lets any caller impersonate a reward-eligible module and drain the `OutboundRequestDeliveryReward` treasury - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`OutboundRequestDeliveryReward`/`claim_outbound_request_delivery_reward` (`modules/pallets/relayer/src/outbound_request.rs`, `modules/pallets/relayer/src/lib.rs:417-451`) pays a governance-configured BRIDGE reward to whoever proves delivery of a request whose `from` field matches an allowlisted `module_id`. The allowlist is meant to gate only Hyperbridge's own system pallets (host-executive, intents-coprocessor, token-governor, relayer withdrawal, future bandwidth module). But the `from` field is not authenticated at dispatch time: `pallet_ismp::dispatcher::Pallet::dispatch_request` copies `dispatch_post.from` directly onto the committed `PostRequest` with no binding to the caller's actual pallet/account identity.

### Finding Description
The claim's entire security model (`docs/outbound-request-incentivization.md:114-215`, `modules/pallets/relayer/src/outbound_request.rs:107-197`) rests on the assumption that `request.from` faithfully identifies which pallet dispatched the request:

> "The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier."

That assumption is not enforced anywhere in the dispatch path. `dispatch_request` (`modules/pallets/ismp/src/dispatcher.rs:92-151`) builds:
```rust
let post = PostRequest {
    source: self.host_state_machine(),
    dest: dispatch_post.dest,
    nonce: self.next_nonce(),
    from: dispatch_post.from,   // <-- caller-controlled, unchecked
    to: dispatch_post.to,
    ...
};
```
There is no check that `from` corresponds to the pallet/account that invoked `dispatch_request`. Any pallet on the runtime that exposes a user-facing "dispatch a post request" extrinsic (the demo/ping pattern shown in `modules/pallets/demo/src/lib.rs:131-184`, or the equivalent pattern documented for third-party pallets in `docs/content/developers/polkadot/dispatching.mdx`) lets the caller choose `from` freely, then pays for it with `fee.payer = signer` — the fee doesn't constrain `from` at all.

The outbound-request-reward verification pipeline (`process_outbound_request_delivery_claim`, `modules/pallets/relayer/src/outbound_request.rs:119-197`) checks:
1. `request.source == host.host_state_machine()` — trivially true since `dispatch_request` always stamps `source` as the local chain.
2. `RequestCommitments::get(commitment).is_some()` — true for any successfully dispatched request, including one from an unprivileged permissionless pallet call.
3. Not already claimed.
4. `OutboundRequestDeliveryReward[request.from] > 0` — the only real gate, keyed purely on attacker-supplied bytes.
5. State-proof of delivery on the destination and signer match.

None of these checks verify that `request.from` was actually set by the pallet whose module id it claims to be. An attacker only needs `from` bytes equal to any currently-allowlisted `module_id` (these are logged on-chain in `OutboundRequestDeliveryReward` storage and are effectively public — e.g. `b"ismp-ast"`, `b"HYPR-FEE"`, or a real system pallet's id) to have their self-dispatched, free ($0 fee, arbitrary payload) request treated as a genuine hyperbridge-originated system message eligible for the treasury payout.

This is the direct structural analog of the NPM finding: the guarding relationship ("only real system-pallet dispatches earn a reward") is checked only at a shallow level (bytes equality on an unauthenticated field) and is disconnected from the thing it is supposed to prove (that the pallet with that identity actually dispatched it) — exactly like PODs being disconnected from the staked amount, letting an attacker satisfy the surface-level condition without the substance behind it.

### Impact Explanation
This allows unauthorized draining of the `TreasuryPalletId` account (`hb/trsry`) via `claim_outbound_request_delivery_reward` (`modules/pallets/relayer/src/outbound_request.rs:175-184`). An attacker can:
1. Dispatch a free-of-charge request from any permissionless pallet call, setting `from` to a currently allowlisted `module_id`.
2. Deliver it to any destination themselves (trivial and cheap, since the body/timeout are attacker-controlled).
3. Submit `claim_outbound_request_delivery_reward` with a valid state proof and their own signature, and receive `reward` BRIDGE from the treasury for a message that carries no genuine protocol value — repeatable per distinct commitment (different nonce each time), so it can be looped to drain the treasury balance entirely. This is a straightforward loss/theft of protocol funds via unauthorized claim of a reward that should only be payable to legitimate system-message deliveries.

### Likelihood Explanation
High, once any reward is registered for a module id (which is the intended operational state — the whole feature exists to pay these rewards). No relayer, prover, admin, or governance compromise is needed; a single unprivileged account with a permissionless-dispatch pallet call available (any pallet mirroring the documented/demo dispatch pattern) and normal relayer tooling to submit the destination-state proof suffices. The only friction is finding/using an on-chain pallet that lets a user call `dispatch_request` with attacker-chosen `from` bytes — but this is exactly the documented, expected pattern for building ISMP-integrated pallets (see `docs/content/developers/polkadot/dispatching.mdx` and `modules/pallets/demo/src/lib.rs`), so such an avenue is very plausible to exist somewhere in the deployed runtime (any custom/community pallet integrated with `pallet-ismp` on Hyperbridge's own chain, or an intentionally over-permissive future module).

### Recommendation
Bind `request.from` to the caller's real identity at dispatch time rather than trusting the caller-supplied `DispatchPost::from`. Options:
- Change `IsmpDispatcher::dispatch_request` to take the caller's `PalletId`/account and either overwrite `from` with a derived, non-forgeable module id, or verify `from == derive_module_id(caller)` before accepting the dispatch.
- Alternatively, restrict which callers may set `from` values that match entries in `OutboundRequestDeliveryReward` — e.g. maintain an explicit `AllowedDispatchers: BoundedVec<u8, ModuleIdBound> -> CallerOrigin` map and check it inside `dispatch_request`, or require the reward-eligible pallets to dispatch through a privileged wrapper the generic public dispatch path cannot reach.
- At minimum, add a runtime-wide invariant test asserting that no permissionless call path can set `PostRequest.from` to a value present in `OutboundRequestDeliveryReward`.

### Proof of Concept
1. Governance has registered a non-zero reward for module id `M` (e.g. `b"ismp-ast"`), as in the documented Layer-4 runbook (`docs/outbound-request-incentivization.md:317-329`).
2. Attacker calls any permissionless "dispatch" extrinsic on the runtime that forwards user-supplied `from`/`to`/`body` into `T::IsmpDispatcher::dispatch_request(DispatchRequest::Post(post), FeeMetadata { payer: attacker, fee: 0 })` (pattern identical to `modules/pallets/demo/src/lib.rs::transfer`/`dispatch_to_evm`), setting `post.from = M`, `post.to` = attacker-controlled EVM/substrate address, `body` arbitrary, `fee = 0`.
3. This lands in `pallet_ismp::child_trie::RequestCommitments` exactly like a genuine system-pallet dispatch — `dispatch_request` in `modules/pallets/ismp/src/dispatcher.rs` performs no identity check.
4. Attacker (or their own relayer instance) delivers the request to the chosen destination, producing a `RequestReceipts[commitment]` entry attributing delivery to an address they control.
5. Attacker submits `Relayer::claim_outbound_request_delivery_reward` with `request` (matching what was dispatched), a valid destination state proof, `payee = attacker`, and a signature from the address recorded in the receipt.
6. `process_outbound_request_delivery_claim` passes every check (source-is-self, commitment-known, not-claimed, reward-configured, state-proof, signer match) and transfers `reward` BRIDGE from `TreasuryPalletId` to the attacker (`modules/pallets/relayer/src/outbound_request.rs:175-184`), which can be repeated with a fresh nonce each cycle to drain the treasury.
