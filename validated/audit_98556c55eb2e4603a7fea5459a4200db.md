### Title
`IntentGatewayV2.withdraw` (Tron) trusts raw `.call` success instead of checking ERC20 boolean return value, allowing escrow to be silently burned on non-reverting-`false` tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports OpenZeppelin's `SafeERC20` [1](#0-0)  but does **not** use it for the escrow-payout path in `withdraw()`, `onAccept`'s `SweepDust` branch, or the tx-fee payout. Instead it performs a raw low-level `.call` with `IERC20.transfer.selector` and only checks that the call did not revert, never decoding/validating the returned boolean, exactly the ERC20-return-value bug class from the cited report (`enableToken`'s unchecked `approve`).

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

`success` is only `true`/`false` based on whether the external call itself reverted; it says nothing about the ABI-encoded `bool` return data that ERC20 `transfer()` is supposed to return. Any ERC20 implementation that returns `false` on failure (a well-known non-standard-compliant pattern this exact bug class targets) will make `token.call(...)` return `success = true` with returndata `abi.encode(false)`, which this code never inspects. The check therefore always passes even when the transfer silently failed.

The identical pattern also appears in:
- The `SweepDust` branch of `onAccept`: `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount)); if (!success) revert TransferFailed();` [3](#0-2) 
- The transaction-fee payout inside `withdraw()`: `(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees)); if (!success) revert TransferFailed();` [4](#0-3) 

Crucially, after the unchecked "success" the escrow ledger `_orders[body.commitment][token]` is unconditionally decremented (line 701) and, for fees, deleted (line 713), regardless of whether the beneficiary actually received tokens. By contrast, the primary (non-Tron) EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol` correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` [5](#0-4) , which decodes and enforces the boolean return value (or handles no-return tokens) via OpenZeppelin's `SafeERC20`. The Tron file diverges from this pattern and reintroduces the unchecked-return-value class the SafeERC20 usage elsewhere in the codebase was meant to prevent, despite already importing `SafeERC20` at the top of the same file.

### Impact Explanation
For any input/output token used in an intent order that is a non-reverting ERC20 (returns `false` instead of reverting on failed transfer, e.g. due to internal balance/allowance/blacklist checks implemented without `require`), a legitimate `withdraw()` call (triggered by `RedeemEscrow`/`RefundEscrow` cross-chain messages or GET-response timeout path) will:
1. Report success and emit `EscrowReleased`/`EscrowRefunded`.
2. Decrement/delete the internal escrow accounting for that commitment.
3. Never actually deliver the tokens to the beneficiary (filler or user).

The result is silent loss of the escrowed funds — they remain permanently locked in the `IntentGatewayV2` contract's balance while the accounting record that would let anyone claim them has already been wiped, with no revert and no reentry path to retry since `_orders[...]` is already zeroed. This is a direct fund-loss condition matching the "stealing or loss of funds" bounty category, reachable through the standard, unprivileged intent-fill/redeem flow with no malicious relayer, prover, or admin required — only a token contract that is a known non-standard-compliant ERC20 (a common real-world token category, not an "imported dependency bug").

### Likelihood Explanation
Likelihood is moderate to high in practice: many real-world tokens (e.g., legacy/administrative tokens, some stablecoins with denylists) return `false` on failed transfer instead of reverting. Since `IntentGatewayV2` on Tron allows arbitrary ERC20 tokens to be used as order inputs/outputs (`TokenInfo.token` is attacker/user-supplied), any order or dust-sweep involving such a token guarantees silent fund loss on every failed transfer attempt (e.g., beneficiary blacklisted, insufficient token-side balance/logic edge case). No attacker action beyond normal contract usage is needed — this is a straightforward logic defect independent of any adversarial relayer or governance behavior.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` lines 693-699 and 707-713, and in `onAccept`'s `SweepDust` branch lines 661-667) with `IERC20(token).safeTransfer(beneficiary, amount)` using the already-imported `SafeERC20` library, matching the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures the boolean return value is checked (and handles tokens with no return value) before the escrow ledger is decremented, so accounting is only mutated after tokens are provably delivered.

### Proof of Concept
1. Deploy (or use) an ERC20 token `T` whose `transfer()` function returns `false` on failure instead of reverting (e.g., a denylisting stablecoin implementation where the recipient is later added to a denylist, or a mock token built specifically to return `false`).
2. User places an order with `T` as an input token via `placeOrder`, escrowing `_orders[commitment][T] = amount`.
3. Filler fills the order; the counterpart chain (or same-chain path) eventually dispatches a `RedeemEscrow`/`RefundEscrow` request that reaches `onAccept` → `withdraw(body, isRefund)`.
4. Set up `T` so that at the moment of `withdraw`, `transfer(beneficiary, amount)` returns `false` (e.g., beneficiary is now denylisted) rather than reverting.
5. `token.call(...)` succeeds (`success = true`) because the low-level call itself doesn't revert; the `if (!success) revert TransferFailed();` guard passes.
6. `_orders[body.commitment][T] -= amount;` executes, zeroing the escrow record, and `EscrowReleased`/`EscrowRefunded` is emitted — while `beneficiary`'s `T` balance never increased.
7. The `amount` of `T` is now permanently stuck in the `IntentGatewayV2` contract with no ledger entry left to reclaim it.
