### Title
`PoolWallet.claim_pool_rewards()` aborts the entire reward-claim batch on a single bad coin, DoSing pool reward absorption - (File: `chia/pools/pool_wallet.py`)

### Summary
`PoolWallet.claim_pool_rewards()` iterates over every unspent p2-singleton reward coin owned by a pool-wallet singleton and, for each one, calls `create_absorb_spend()` to chain another absorb spend onto a running `last_solution` cursor. This mirrors the Frax `getNextValidator()`/`depositEther()` pattern: a single batch operation loops over N claimable items and builds up cumulative state, but any one item that fails an internal invariant check aborts the whole batch instead of being skipped, taking the entire user-facing operation offline until the bad state is cleared.

### Finding Description
`claim_pool_rewards()` builds `coin_to_height_farmed` from local farming-reward transaction records, then loops over `unspent_coin_records`, calling `create_absorb_spend()` once per matching reward coin and feeding the previous spend's first `CoinSpend` back in as `last_solution` for the next iteration [1](#0-0) . `create_absorb_spend()` itself contains several bare `assert` statements with no exception handling around singleton parent linkage and puzzle-hash matching, e.g. `assert coin is not None`, `assert coin.puzzle_hash == full_puzzle.get_tree_hash()`, and `assert full_puzzle.get_tree_hash() == coin.puzzle_hash` [2](#0-1) . None of these are caught in the caller's loop, so if the local view of the singleton tip (`last_solution` / `current_state`) becomes inconsistent with on-chain state — for example due to a stale `WalletPoolStore` history entry, a reorg that isn't yet reflected in `get_spend_history()`, or any mismatch between `coin_to_height_farmed` and the actual chain-confirmed reward coin — the `assert` raises an unhandled `AssertionError` that propagates out of `claim_pool_rewards()` and aborts the *entire* batch, not just the offending coin. This is functionally identical to the Frax `getNextValidator()` bug: iterating a collection, hitting one bad entry, and reverting work already accumulated for all the good entries in the same call.

### Impact Explanation
This is reachable by any local wallet user via the `pw_absorb_rewards` RPC, which dispatches straight into `claim_pool_rewards()` for `PoolWallet` instances [3](#0-2) . A single inconsistent/malformed reward coin or stale local pool-transition record blocks the wallet from claiming *any* of its otherwise-valid pooled rewards in that call, since the function has an early guard against overlapping unconfirmed transactions (`have_unconfirmed_transaction()`) but no per-coin isolation inside the loop itself [4](#0-3) . Funds are not lost, but legitimate reward claims are denied until the underlying state inconsistency is manually resolved — the same "temporarily inoperable until manual intervention" impact pattern the report describes for `depositEther()`.

### Likelihood Explanation
Triggering requires the wallet's locally reconstructed pool-singleton state (`WalletPoolStore` history / `current_state`) to diverge from the coin actually consumable on-chain, which can occur from reorgs, partial sync, or any parser edge case in `solution_to_pool_state()`/`apply_state_transition()` noted as fragile in the module's own documentation ("Assertions are common around CLVM shape, singleton additions, and reward heights... converting them to recoverable paths can hide state corruption if not paired with explicit rejection semantics") . This makes it a plausible, non-adversarial DoS path for pool-wallet users rather than a routine occurrence.

### Recommendation
Wrap each per-coin `create_absorb_spend()` call in `claim_pool_rewards()`'s loop in a `try`/`except`, log and skip the offending reward coin (similar to the report's recommended `try/catch` mitigation for `getNextValidator()`), and continue accumulating `all_spends` for the remaining valid coins rather than letting one bad entry abort the whole claim.

### Proof of Concept
1. Get a `PoolWallet` into a state where `get_current_state()`/`get_spend_history()` returns a stale or slightly inconsistent `last_solution` relative to the actual on-chain singleton tip (e.g., simulate a reorg that changes the singleton's most recent spend without a matching update in `WalletPoolStore`).
2. Farm additional pool rewards so `unspent_coin_records` contains several claimable p2-singleton coins.
3. Call `pw_absorb_rewards` (→ `claim_pool_rewards()`).
4. Observe that the loop over `unspent_coin_records` reaches `create_absorb_spend()` for the inconsistent coin, hits `assert coin.puzzle_hash == full_puzzle.get_tree_hash()` (or an analogous assert), and raises — aborting `claim_pool_rewards()` for the entire batch even though the other reward coins in `unspent_coin_records` were legitimately claimable.
