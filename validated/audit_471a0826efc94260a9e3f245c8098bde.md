### Title
Blame proof published before PoP verification reveals victim's ECDH key, leaking other participants' secret shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG encrypts each secret share with a per-message ECDH key `enc_key_recipient * msg.key`, and correctness of the ephemeral `msg.key` is enforced by a Schnorr proof-of-possession (`pop`) that is only *queued* into a `BatchVerifier` inside `Encryption::decrypt`, not evaluated there. `KeyMachine::calculate_share` returns `PedPoPError::InvalidShare { blame: Some(blame) }` — containing an `EncryptionKeyProof` that publicly reveals the ECDH shared point — on the `C::F::from_repr` early-error path *before* `batch.verify_with_vartime_blame()` ever runs. A malicious DKG participant can therefore replay an honest sender's `msg.key` (which they do not know the discrete log of), induce the victim to emit a blame proof for it, and recover the cipher key that decrypts the honest sender's real encrypted share to the victim.

### Finding Description
`Encryption::decrypt` queues the per-message `pop` Schnorr signature into the caller's `BatchVerifier` and then immediately computes `ecdh(self.enc_key, msg.key)`, decrypts the ciphertext, and returns a fully-formed `EncryptionKeyProof { key, dleq }` — i.e. the actual ECDH shared point plus a DLEq proving its correctness [1](#0-0) . In `KeyMachine::calculate_share`, the deserialized share is checked with `C::F::from_repr` and, on failure, the function returns `InvalidShare { participant: l, blame: Some(blame.clone()) }` immediately — the batch containing the PoP verification is never executed [2](#0-1) . The PoP exists precisely to stop this: the code comments state that without it, an attacker who copies Alice's per-message key `X` can make "Bob... create a blame argument against Eve... they'd reveal bX, revealing Alice's message to Bob. This is a massive side effect" [3](#0-2) . The early return reintroduces exactly that leak for any message whose decrypted bytes are non-canonical. In production, the processor serializes this blame into `ProcessorMessage::InvalidShare { blame: Some(...) }`, broadcasting the `EncryptionKeyProof` (which contains `key` = `enc_key_victim * msg.key`) [4](#0-3) . Because `cipher()` uses a static IV with a keystream derived solely from `context || shared_key`, publishing `key` is equivalent to publishing the plaintext of every message using that ECDH pair [5](#0-4) .

### Impact Explanation
The attacker crafts an `EncryptedMessage` to victim `B` reusing the `key` field `X` from honest participant `A`'s real encrypted share to `B` (observed on the broadcast/authenticated channel), with arbitrary ciphertext and an arbitrary self-signed PoP. `B`'s `calculate_share` decrypts the message — using the *real* shared key `bX` — and returns the blame proof revealing `bX` before noticing the PoP is invalid. The attacker then XORs the published keystream key against `A`'s original ciphertext, recovering `A`'s secret share to `B`. Repeating per sender recovers `B`'s full incoming share set and hence `B`'s threshold secret share. With `t = 2` (or by corrupting `t - 1` victims this way plus the attacker's own share), the attacker reconstructs the entire group secret key — full key-share recovery from a single crafted DKG message per victim. The victim is slashed-adjacent (the attacker is blamed, since `blame_internal` will flag the invalid signature [6](#0-5) ), but the share is already leaked.

### Likelihood Explanation
Reachable by any participant included in a PedPoP key-generation session: they supply the `shares` map input to `calculate_share` (`CoordinatorMessage::Shares` in the processor [7](#0-6) ). The only probabilistic element is that the decrypted bytes be a non-canonical scalar encoding; for 32-byte fields like ed25519 (`l ≈ 2^252`) a random 32-byte string fails `from_repr` with probability ≈ 15/16, and failed attempts merely abort the DKG attempt, which can be retried on the next attempt/session.

### Recommendation
Do not emit the `EncryptionKeyProof` until the message's PoP has been verified. Concretely: in `calculate_share`, either (a) verify `msg.pop` synchronously inside `Encryption::decrypt` before computing/returning the ECDH proof (returning `blame: None` on failure, matching the `BatchId::Decryption` path), or (b) defer the `from_repr` early-error and the `InvalidShare` blame emission until after `batch.verify_with_vartime_blame()` has run, only attaching `blames[l]` once the PoP for `l` is known-good. The batch-blame mapping already encodes this intent (`BatchId::Decryption(l) → blame: None` [8](#0-7) ); the `from_repr` branch at line 481 bypasses it.

### Proof of Concept
1. Participants `A` (honest), `E` (attacker), `B` (victim) run PedPoP with `t = 2`, `n = 3`. `E` observes the broadcast `EncryptedMessage` `m_AB = { key: X = xG, pop, msg: c }` that `A` sends to `B`.
2. `E` builds `m_EB = { key: X, pop: SchnorrSignature::sign(k_e, r_e, pop_challenge(ctx, R_e, X, E, c')) , msg: c' }` for a fresh key `k_e` and arbitrary ciphertext `c'` (e.g. all `0xff` bytes, non-canonical with high probability). Note `E` reuses `A`'s point `X` but signs the PoP under `from = E`, so the signature itself is self-consistent — it will nonetheless pass/fail batch only later.
3. `E` sends `m_EB` to `B` as its secret share. `B`'s `calculate_share` calls `encryption.decrypt(...)`: it queues the PoP into the batch, computes `key = bX` (the same ECDH key as for `m_AB`), decrypts `c'`, and builds `EncryptionKeyProof { key: bX, dleq }`.
4. `from_repr` on the decrypted bytes fails (≈15/16 per attempt for ed25519/Ristretto; for secp256k1 ≈ 1/2) → `calculate_share` returns `Err(InvalidShare { participant: E, blame: Some(proof) })` **without ever running `batch.verify_with_vartime_blame()`**.
5. The processor emits `ProcessorMessage::InvalidShare` with `blame.serialize()`, publishing `bX`. `E` derives the ChaCha20 key via `cipher(context, bX)` and decrypts `A`'s real ciphertext `c`, obtaining `A`'s share `s_{A→B}` — despite `E` never knowing `x` or `b`.
6. Repeating steps 2–5 for every sender to `B` (all messages are broadcast) yields every `s_{i→B}`, so `E` reconstructs `B`'s secret share `Σ_i s_{i→B}`. With `t = 2`, `E`'s own share plus `B`'s share interpolates the group private key — full threshold key recovery via a yes/no (canonical/non-canonical) decryption oracle.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
