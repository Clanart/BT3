### Title
`ThresholdKeys::read`/`ThresholdKeys::new` never checks the secret share matches the participant's verification share, letting a crafted key file substitute an attacker-chosen group key / unusable share - (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes a load path that accepts untrusted file contents without validating them against the expected security invariant, and then acts on whatever the file says. The Serai analog is `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), which deserializes a serialized threshold key set — `t`, `n`, `i`, the interpolation method, the `secret_share`, and all `n` `verification_shares` — entirely from attacker-supplied bytes, then hands them to `ThresholdKeys::new`. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) validates count/index bounds and derives `group_key` purely by interpolating `verification_shares[1..=t]` (lines 376-378), but never verifies the fundamental invariant `C::generator() * secret_share == verification_shares[params.i()]`, nor that the verification shares are mutually consistent (i.e., lie on a common polynomial). The loaded key is then used to produce signature shares and to derive the group key other components trust.

### Finding Description
- `ThresholdKeys::read` reads `t`, `n`, `i` (lines 591-602), an interpolation tag plus `n` scalars for `Interpolation::Constant` (604-616), an arbitrary `secret_share` (line 618), and `n` arbitrary points as `verification_shares` (620-623), then calls `ThresholdKeys::new`.
- `ThresholdKeys::new` only enforces `verification_shares.len() == n`, `participant <= n`, and `t == n` for constant interpolation (355-374). The `group_key` is computed as `sum(verification_shares[i] * interpolation_factor(i, {1..=t}))` (376-378) — fully determined by bytes the attacker chose.
- No code anywhere in `read`/`new`/`view` checks `generator() * secret_share == verification_shares[i]`. A `view` (463-533) interpolates the mismatched `secret_share` and emits signature shares that will fail FROST verification against `verification_shares[i]`, causing the honest holder to be blamed.
- Because `group_key` is a free function of `verification_shares`, an attacker who supplies a fully self-consistent file (own secret share + own verification shares) causes the node to operate under a group key whose discrete log the attacker knows.

### Impact Explanation
Two concrete impacts, both reachable purely through the deserialized bytes:

1. **Attacker-controlled group key.** If the crafted blob is internally consistent, `group_key()` returns a key the attacker fully knows. Any deposits the scanner attributes to that group key, and any message the node threshold-signs "on behalf of the group," are actually under attacker control — funds reported received are spendable by the attacker, not the group.
2. **Persistent blame/DoS against an honest signer.** If `secret_share` does not match `verification_shares[i]`, every share this participant produces in `AlgorithmSignMachine::sign` fails verification, and the signer is reported as `InvalidShare`/blamed — potentially slashed — for behavior it did not cause.

This matches the CVE's shape exactly: insufficient validation of a loaded object lets the file contents dictate security-relevant behavior (which key is signed under, whether shares verify).

### Likelihood Explanation
`ThresholdKeys` is the canonical serialized form of a DKG result; `read` is the recovery/import path and is explicitly designed to ingest externally-provided bytes. Any flow where a key file is supplied by a third party (key recovery, coordinator/peer-provided backup, restoration from an untrusted store) reaches this code with no authentication of the contents. The attack requires no threshold collusion and no cryptographic break — only the ability to supply the file — matching the report's local-untrusted-input precondition. Requires a deployment that accepts key material from an untrusted source rather than only its own freshly generated DKG output, which is exactly the recovery/restore scenario `read` exists for.

### Recommendation
In `ThresholdKeys::new` (or in `read` before constructing), assert `C::generator() * secret_share == verification_shares[&params.i()]` and return a `DkgError` otherwise. Optionally also verify the verification shares lie on a degree-`t-1` polynomial consistent with the interpolation (or that `group_key` recomputes identically for every `t`-subset), so a crafted `verification_shares` map cannot alias to an attacker-known group key while the share remains honest.

### Proof of Concept
```rust
// Attacker builds a ThresholdKeys blob with a key they fully control:
let params = ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap();
let attacker_secret = Zeroizing::new(C::F::random(&mut OsRng));
let attacker_shares: Vec<C::F> = /* eval poly with p(1) consistent */;
let mut verification_shares = HashMap::new();
for l in 1..=3u16 {
  let l = Participant::new(l).unwrap();
  // attacker-chosen points; group_key = G * known_dl
  verification_shares.insert(l, C::generator() * chosen_share_for(l));
}
let keys = ThresholdKeys::new(params, Interpolation::Lagrange,
                             attacker_secret, verification_shares).unwrap();
// keys.group_key() is attacker-known; serialize -> victim calls
// ThresholdKeys::read -> succeeds with no consistency check.

// Variant 2 (blame): keep honest verification_shares but write a
// different secret_share into the serialized blob.
// read() succeeds; every share the victim emits fails verification
// and they are blamed for an InvalidShare.
```
The check `read` skips (`G * secret_share == verification_shares[i]`) is exactly what would reject both variants.
