## Finding

### Title
Unrestricted brute-force on daemon RPC `unlock_keyring` / `validate_keyring_passphrase` (no rate limiting or lockout) - (File: `chia/daemon/server.py`)

### Summary
The Chia daemon's `unlock_keyring` and `validate_keyring_passphrase` RPC handlers validate the master keyring passphrase with no attempt counter, delay, or lockout, unlike the equivalent CLI passphrase-entry path which enforces `MAX_RETRIES` with a failure delay. Any client capable of reaching the daemon websocket (e.g. GUI, a local RPC caller, or anyone holding a copy of the daemon's client certificate) can send unlimited passphrase guesses to fully brute-force the keyring passphrase that protects all wallet private keys — the same "unbounded verification attempts against a secret that gates access to funds" bug class as the reported Runtipi TOTP issue, just mapped onto Chia's local keychain/RPC authorization boundary instead of a web 2FA endpoint.

### Finding Description
`WebSocketServer.unlock_keyring()` and `WebSocketServer.validate_keyring_passphrase()` call `Keychain.master_passphrase_is_valid(key, force_reload=True)` directly and return a plain success/failure response with no state tracked across calls: [1](#0-0) [2](#0-1) 

There is no per-connection or per-process attempt counter, no exponential backoff, and no lockout after N failed attempts on this code path. Contrast this with the CLI-only helper `obtain_current_passphrase()`, which is the *only* place in the codebase enforcing `MAX_RETRIES = 3` and a `FAILED_ATTEMPT_DELAY` before raising `KeychainMaxUnlockAttempts`: [3](#0-2) 

That protection lives entirely in the interactive prompt loop and is never applied to the daemon websocket commands. `handle_message()` dispatches `unlock_keyring`/`validate_keyring_passphrase` (via `keychain_commands`) or general command mapping on every single incoming message with no throttling at the transport layer either — the daemon docs explicitly note "there is no ... rate limiter here": [4](#0-3) [5](#0-4) 

The only cost imposed on each guess is PBKDF2-SHA256 with 100,000 iterations used to derive the decryption key from the candidate passphrase: [6](#0-5) 

This is a per-guess CPU cost, not an attempt-count or lockout defense — it slows but does not bound the number of guesses a caller may submit over the persistent websocket connection, and provides no protection against a weak/default or dictionary passphrase.

### Impact Explanation
An actor who can open a websocket to the daemon (holder of/compromised holder of the daemon's mTLS client certificate, e.g. a compromised local GUI/service, or any local RPC caller in a multi-tenant/shared-host deployment) can repeatedly call `unlock_keyring` or `validate_keyring_passphrase` with different guesses indefinitely. Successful brute-force yields the master passphrase, which decrypts the on-disk keyring and exposes every mnemonic/private key managed by that node — a direct path to unauthorized coin movement, since those keys sign spend bundles for all wallets under that keychain.

### Likelihood Explanation
Exploitation requires the attacker to already have a channel to the daemon (i.e., already hold a valid daemon TLS client cert or run as a process able to connect locally) — directly analogous to the original report's precondition of "attacker who has obtained a user's valid credentials." Given that precondition, exploitation is trivial: there is no cap on attempts, no session expiry forcing re-authentication, and no lockout, so a weak, default, or previously-leaked-pattern passphrase can be brute-forced over an arbitrarily long window, exactly mirroring the reported issue's 24-hour unrestricted verification window.

### Recommendation
Add attempt tracking (per-connection and/or global), exponential backoff, and a hard lockout (raising `KeychainMaxUnlockAttempts`, which already exists in `chia/util/errors.py`) to the `unlock_keyring` and `validate_keyring_passphrase` daemon RPC handlers, mirroring the protection already present in `obtain_current_passphrase()`. Consider also rate-limiting at the `handle_message()` dispatch layer for these two commands specifically.

### Proof of Concept
1. Connect to the daemon websocket with a valid (attacker-held) client TLS cert.
2. Repeatedly send:
```json
{"command": "unlock_keyring", "data": {"key": "<guess>"}, "request_id": "...", "destination": "daemon", "origin": "poc"}
```
3. Observe that every request — regardless of how many prior failures occurred — returns immediately with `{"success": false, "error": "bad passphrase"}` and no lockout/backoff is ever triggered, allowing the full guess space to be exhausted, as confirmed by the test harness exercising this route with no attempt-limit assertions: [7](#0-6)

    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"

        if success and self.run_check_keys_on_unlock:
            try:
                self.log.info("Running check_keys now that the keyring is unlocked")
                check_keys(self.root_path)
                self.run_check_keys_on_unlock = False
            except Exception as e:
                tb = traceback.format_exc()
                self.log.error(f"check_keys failed after unlocking keyring: {e} {tb}")

        response: dict[str, Any] = {"success": success, "error": error}
        return response

FAILED_ATTEMPT_DELAY = 0.5
MAX_RETRIES = 3


def prompt_for_passphrase(prompt: str) -> str:
    if sys.platform == "win32" or sys.platform == "cygwin":
        print(prompt, end="", flush=True)
        prompt = ""
    return getpass(prompt)


def obtain_current_passphrase(prompt: str = DEFAULT_PASSPHRASE_PROMPT, use_passphrase_cache: bool = False) -> str:
    from chia.util.keyring_wrapper import KeyringWrapper

    """
    Obtains the master passphrase for the keyring, optionally using the cached
    value (if previously set). If the passphrase isn't already cached, the user is
    prompted interactively to enter their passphrase a max of MAX_RETRIES times
    before failing.
    """

    if use_passphrase_cache:
        passphrase, validated = KeyringWrapper.get_shared_instance().get_cached_master_passphrase()
        if passphrase:
            # If the cached passphrase was previously validated, we assume it's... valid
            if validated:
                return passphrase

            # Cached passphrase needs to be validated
            if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
                return passphrase
            else:
                # Cached passphrase is bad, clear the cache
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(None)

    # Prompt interactively with up to MAX_RETRIES attempts
    for i in range(MAX_RETRIES):
        colorama.init()

        passphrase = prompt_for_passphrase(prompt)

        if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
            # If using the passphrase cache, and the user inputted a passphrase, update the cache
            if use_passphrase_cache:
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
            return passphrase

        time.sleep(FAILED_ATTEMPT_DELAY)
        print("Incorrect passphrase\n")
    raise KeychainMaxUnlockAttempts

def generate_nonce() -> bytes:
    """
    Creates a nonce to be used by ChaCha20Poly1305. This should be called each time
    the payload is encrypted.
    """
    return token_bytes(NONCE_BYTES)


def generate_salt() -> bytes:
    """
    Creates a salt to be used in combination with the master passphrase to derive
    a symmetric key using PBKDF2
    """
    return token_bytes(SALT_BYTES)


def symmetric_key_from_passphrase(passphrase: str, salt: bytes) -> bytes:
