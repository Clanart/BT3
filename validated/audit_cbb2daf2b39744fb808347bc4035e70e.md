## Title
Stale line-index diff selection can silently commit unreviewed content when the working tree changes between diff review and commit ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets a user selectively stage/commit individual diff lines via a `DiffSelection` object that records *positional* line indices from the diff that was rendered in the UI. When the user clicks "Commit", Desktop does not re-validate that this selection still corresponds to the same content — it re-fetches a **fresh** `git diff` at staging time and blindly re-applies the old, positionally-indexed selection to it. If the tracked file's content on disk changes between the moment the user reviewed/selected lines and the moment the commit executes, the old line indices map to different lines in the new diff, so Desktop will commit/exclude lines the user never actually approved. This mirrors the report's broken invariant: an authorization (the operator's signature / the user's line selection) is captured against one state of the world but executed against a different, more permissive state, with no binding or re-validation between the two.

### Finding Description
Desktop tracks a per-file `DiffSelection`, which stores selection state purely as a `Set<number>` of diff line indices (`divergingLines`), with no reference to line content: [1](#0-0) 

When the user commits, `_commitIncludedChanges` takes the files whose selection is not `None` straight from the in-memory `changesState.workingDirectory` and passes them to `createCommit`: [2](#0-1) 

`createCommit` stages the files via `stageFiles`, which for any file with a `Partial` selection calls `applyPatchToIndex`: [3](#0-2) 

Critically, `applyPatchToIndex` does **not** reuse the diff that the UI last rendered/that the selection was built against — it fetches a brand-new `git diff` at commit time and formats a patch by indexing into that new diff with the old (stale) selection: [4](#0-3) 

`formatPatch` walks the *new* diff's hunks and simply asks `file.selection.isSelected(absoluteIndex)` for each line's positional index in the new diff, with no comparison against the diff that generated that selection: [5](#0-4) 

Desktop's own code acknowledges this is unresolved: when the diff is refreshed in the Changes view, the comment explicitly states that stale partial-selection validity is not properly checked, and only line-index bookkeeping (not content) is patched up: [6](#0-5) 

That refresh (`updateChangesWorkingDirectoryDiff`) only runs when the Changes view diff is (re)loaded (e.g. background polling or file selection), and there is no guarantee it runs — or that the user notices — immediately before `_commitIncludedChanges` executes. This creates a TOCTOU window: content in the working tree can be mutated (e.g. by a build/watch script, an editor autosave, a git `clean`/`smudge` filter defined in a cloned repository's `.gitattributes`, or any tool triggered while working in a repository the user cloned) between the time the user visually reviewed and selected lines and the time the commit is actually staged.

### Impact Explanation
Because `applyPatchToIndex` re-diffs and re-applies indices without validating them against the diff shown to the user, a shifted/changed file can cause Desktop to silently:
- Commit lines the user explicitly deselected (e.g., accidental debug code, secrets, or lines the user was told/thought were excluded).
- Exclude lines the user explicitly selected, producing an incomplete/corrupted commit.

This directly matches the accepted impact category "silent corruption of what the user commits or pushes" — the user believes they reviewed and approved a specific set of changes, but Desktop stages a different set without any warning, confirmation, or diff-hash binding, exactly as the original bond report describes an operator unknowingly locking more funds than they approved due to a missing binding parameter in the signed authorization.

### Likelihood Explanation
This does not require local/physical access or malware already resident: any process that legitimately modifies a tracked file while Desktop is open and a partial selection is pending (very common with watch-mode build tools, formatters-on-save, linters with `--fix`, or repository-defined git clean/smudge filters that execute automatically on checkout/diff of a cloned/fetched repository) can trigger the race. The window is the time between the last diff render and the user's click on "Commit," which in practice is often several seconds to minutes for a careful reviewer — well within reach of automated tooling.

### Recommendation
Bind the `DiffSelection` to the exact diff it was derived from (e.g., a content hash or the diff object itself) and validate that hash at staging/commit time in `applyPatchToIndex`/`stageFiles`. If the working directory diff has changed since the selection was captured, refuse to commit and force Desktop to re-diff, re-render, and require the user to re-confirm their selection — rather than remapping stale positional indices onto new diff content.

### Proof of Concept
1. In a repository, modify `file.txt` and open Desktop's Changes view; partially select a subset of lines to include in the commit (leave others unselected).
2. While the commit message box is focused (before clicking Commit), have an external process (e.g., a `watch` build script, formatter, or a `.gitattributes` `clean` filter defined by the cloned repo) rewrite `file.txt`, shifting line positions but keeping the file "modified."
3. Click "Commit" without re-opening the diff view.
4. Observe via `git show` on the resulting commit that the staged hunk content does not match the lines the user visually selected in step 1 — `applyPatchToIndex` fetched a new diff (`getWorkingDirectoryDiff`) at `app/src/lib/git/apply.ts:60` and applied the old `DiffSelection`'s indices (`app/src/lib/patch-formatter.ts:157`) to it, producing an unreviewed commit.

      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`

    }
