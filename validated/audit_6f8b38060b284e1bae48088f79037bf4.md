### Title
Nil-pointer dereference crash in `filterTransactions` when an `MsgEVMTransaction` fails `AsTransaction()` unpacking - (File: `evmrpc/utils.go`)

### Summary
`filterTransactions` in `evmrpc/utils.go` calls `m.AsTransaction()` on a `*types.MsgEVMTransaction` decoded from block data and immediately dereferences the returned `*ethtypes.Transaction` (`ethtx.Hash()`, `ethtx.Nonce()`) without checking whether the pointer is `nil`. `MsgEVMTransaction.AsTransaction()` explicitly returns `(nil, nil)` when `UnpackTxData(msg.Data)` fails. This is the same bug class as CVE-2025-57767: a header/field accessor that can legitimately return NULL/nil is used without a nil check before a field access, causing a SEGV/panic.

### Finding Description
`MsgEVMTransaction.AsTransaction()` is defined as:
```go
func (msg *MsgEVMTransaction) AsTransaction() (*ethtypes.Transaction, ethtx.TxData) {
	txData, err := UnpackTxData(msg.Data)
	if err != nil {
		return nil, nil
	}
	return ethtypes.NewTx(txData.AsEthereumData()), txData
}
``` [1](#0-0) 

In `evmrpc/utils.go`, `filterTransactions` (used by every EVM RPC block/tx query path such as `eth_getBlockByNumber`, `eth_getTransactionByBlock*`, receipt/log retrieval) iterates over all messages in a queried block, and for each `*types.MsgEVMTransaction` message calls:
```go
ethtx, _ := m.AsTransaction()
hash := ethtx.Hash()
sender, _ := rpcutils.RecoverEVMSender(ethtx, block.Block.Height, block.Block.Time.Unix())
...
if txCount+startOfBlockNonce[sender.Hex()] != ethtx.Nonce() {
``` [2](#0-1) 

The error return of `AsTransaction()` is discarded (`_`), and `ethtx` is used unconditionally. If `ethtx` is `nil`, calling `ethtx.Hash()` / `ethtx.Nonce()` dereferences a nil `*ethtypes.Transaction`, causing a runtime panic. Note that other call sites in the same package correctly guard against this: `getEthTxForTxBz` checks `etx != nil` before use [3](#0-2) , and `encodeReceipt` checks `etx != nil` before dereferencing [4](#0-3) , confirming that the developers are aware `AsTransaction()`/similar accessors can return nil and that `filterTransactions` is missing this same guard.

### Impact Explanation
A panic inside `filterTransactions` is invoked directly from JSON-RPC handlers that process each of `block.Block.Txs` for any queried block (e.g. `eth_getBlockByNumber`, `eth_getTransactionByBlockNumberAndIndex`, `eth_getTransactionReceipt`-adjacent flows), all of which are on the public EVM JSON-RPC surface reachable by any RPC client. A panic here, if not recovered by the outer RPC handler's `recover()` wrapper for every call path that reaches `filterTransactions` (several call sites do have `recover()` in their own deferred metrics function, but `filterTransactions` is also invoked from helper paths without that specific recover, e.g. through `getFilteredMsgs`/`GetEvmTxIndex`/`encodeReceipt` chains), can crash or degrade the RPC node process, which matches the "crash of default-configuration RPC nodes" acceptance criterion.

### Likelihood Explanation
Reaching this path requires a block to contain a `MsgEVMTransaction` whose `Data` Any cannot be unpacked by `UnpackTxData` at query time. Normally `ValidateBasic()` on `MsgEVMTransaction` also calls `UnpackTxData` and would reject such a message during CheckTx/DeliverTx [5](#0-4) , so under strict ante-handler enforcement, a malformed message should not usually make it into a committed block. However, the vulnerability is a genuine missing-nil-check defect in the RPC decode path that is inconsistent with sibling code (`getEthTxForTxBz`, `encodeReceipt`) that explicitly nil-checks the same style of accessor — indicating that the unpack-failure state is considered reachable/expected by the codebase's own authors, but the guard was omitted at this specific call site. Given the uncertainty over whether a currently-known transaction-crafting path can produce an already-included, unpack-failing `MsgEVMTransaction` in a block, I could not fully confirm an end-to-end unauthenticated trigger from a single external transaction/RPC request within the available tools.

### Recommendation
In `filterTransactions` (`evmrpc/utils.go`), check the returned `*ethtypes.Transaction` for `nil` immediately after calling `m.AsTransaction()` and `continue` to skip the message (mirroring the nil-guard pattern already used in `getEthTxForTxBz` and `encodeReceipt`) instead of unconditionally calling `.Hash()` / `.Nonce()` on it.

### Proof of Concept
Not fully constructible with the available read-only tooling: reproducing the crash requires demonstrating a concrete way to get a `MsgEVMTransaction` with an unpack-failing `Data` field committed into a block despite `ValidateBasic`'s identical `UnpackTxData` check, which could not be confirmed from static code inspection alone.
