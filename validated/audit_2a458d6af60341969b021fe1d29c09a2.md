## Analysis

The strongest local analog to the ERC4626 "guarded one path but not the mirrored one" bug class is in the **Tron build of `IntentGatewayV2`**, specifically the `withdraw()` function that releases/refunds escrowed intent inputs. [1](#0-0) 

Compare this to the canonical EVM implementation, which uses `SafeERC20.safeTransfer` for the same job: [2](#0-1) 

### Title
Unchecked ERC-20 return value in `IntentGatewayV2.withdraw()` lets escrow accounting finalize while token transfer silently fails, permanently losing solver funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder()` on the Tron `IntentGatewayV2` correctly uses `SafeERC20.safeTransferFrom` to pull escrow in [3](#0-2) , but the mirrored payout path, `withdraw()`, uses a raw low-level `.call` and only checks that the *call itself* did not revert — it never inspects the ABI-decoded boolean return value of `transfer()`: [4](#0-3) 

The same unchecked pattern is used for the transaction-fee payout and `SweepDust`: [5](#0-4) [6](#0-5) 

This is the exact bug-class from the report: one leg of a symmetric operation is hardened (deposit uses `SafeERC20`), the other leg is not (withdraw does not verify the ERC-20 success flag), so on-chain bookkeeping (`_filled`, `_orders`) diverges from the true custody of funds.

### Finding Description
`withdraw()` is invoked from three authenticated call sites: `onAccept()` for `RedeemEscrow`/`RefundEscrow` [7](#0-6) , `onGetResponse()` after a source-cancel proof [8](#0-7) , and same-chain `cancelOrder()` [9](#0-8) .

In all cases, `withdraw()` unconditionally:
1. Sets `_filled[body.commitment] = beneficiary` (finalizing settlement state) [10](#0-9) .
2. Decrements `_orders[commitment][token] -= amount` [11](#0-10) .
3. Emits `EscrowReleased`/`EscrowRefunded` [12](#0-11) .

...based solely on `success` from the raw `.call`, which is `true` whenever the target contract *returns normally*, even if it encodes and returns `false` (a legal, non-reverting ERC-20 behavior per EIP-20, and exactly the pattern `SafeERC20` exists to guard against). Since `order.inputs[i].token` is an arbitrary address supplied by the user at `placeOrder()` time [13](#0-12) , an attacker fully controls the token contract's behavior on this call.

### Impact Explanation
An attacker places an order whose input token is a contract that: (a) behaves like a normal ERC-20 during `safeTransferFrom` at placement (so escrow succeeds and the order looks legitimate to solvers/indexers), then (b) returns `false` (without reverting) from `transfer()` when the gateway later tries to pay it out in `withdraw()`.

- A solver fills the order on the destination chain, delivering real value to the beneficiary there, then the source-chain `onAccept(RedeemEscrow)` is triggered.
- `withdraw()` "succeeds": `_filled[commitment]` is set, `_orders[commitment][token]` is zeroed, `EscrowReleased` fires — the protocol's own state says the solver was paid.
- The malicious token never actually transfers anything to the solver.

The solver has permanently lost the value it delivered on the destination chain, and the escrowed input tokens are stuck/unrecoverable in the gateway (the commitment is already marked filled, so no cancel/refund path can retry payout). This is direct loss of funds and false settlement-state acceptance — the contract's authoritative accounting (`_filled`, `_orders`, emitted events) says value moved when it did not.

### Likelihood Explanation
This requires no relayer, prover, admin, or governance compromise — a single unprivileged user places a normal-looking order with a token they fully control. It is triggerable through the standard `placeOrder` → (solver fills) → `onAccept(RedeemEscrow)` flow, which is exactly the intended, public happy path of the Intent Gateway. The only "special" ingredient is a token contract that returns `false` instead of reverting, which is valid ERC-20 behavior and requires no elevated privilege to deploy.

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()` (and the identical pattern in `SweepDust` handling) with `SafeERC20.safeTransfer`, matching the pattern already used for escrow intake (`safeTransferFrom`) and the main EVM `IntentsBase.sol` implementation. This ensures a token that returns `false` reverts the whole state transition instead of letting `_filled`/`_orders` finalize against a transfer that never happened.

### Proof of Concept
1. Deploy `EvilToken`, an ERC-20 whose `transferFrom` behaves normally (returns `true`) but whose `transfer` returns `false` (no revert) when called by the `IntentGatewayV2` contract address.
2. Attacker calls `placeOrder()` with `EvilToken` as `order.inputs[0].token`; `safeTransferFrom` succeeds, escrow recorded in `_orders[commitment][EvilToken]`.
3. A solver, seeing a well-formed order, calls `fillOrder`/equivalent on the destination chain and delivers the requested output assets to the order's beneficiary.
4. Destination gateway dispatches `RedeemEscrow`; source `onAccept` calls `withdraw(body, false)`.
5. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, solver, amount))` returns `(true, abi.encode(false))`; `success` is `true` so the check at line 697-699 passes.
6. `_orders[commitment][EvilToken] -= amount` succeeds (decrements to 0), `_filled[commitment] = solver` is set, `EscrowReleased` is emitted — but `EvilToken.balanceOf(solver)` never increased.
7. The solver has delivered real output value on the destination chain and received nothing on the source chain; the commitment is now permanently marked filled, blocking any retry.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
