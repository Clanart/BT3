### Title
Unvalidated `Participant` indexes in PedPoP blame path cause reachable panic / DoS - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs), [File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Analogous to GHSL-2024-235's null-pointer dereference (a field used without validation → crash), the PedPoP blame-handling path dereferences `HashMap` entries indexed by attacker-controlled `Participant` values without checking they are within `1..=n`. Supplying an out-of-range participant to `BlameMachine::blame` / `AdditionalBlameMachine::blame` panics on `enc_keys[&decryptor]` and `commitments[&sender]`, crashing the process.

### Finding Description
- `Decryption::decrypt_with_proof` dereferences `self.enc_keys[&decryptor]` (encryption.rs:388). `std::collections::HashMap`'s `Index` impl panics when the key is absent.
- `BlameMachine::blame_internal` dereferences `self.commitments[&sender]` (lib.rs:599) and calls `decrypt_with_proof(sender, recipient, msg, proof)` (lib.rs:582) with the caller-supplied `sender`/`recipient`.
- `blame` (lib.rs:623-632) and `AdditionalBlameMachine::blame` (lib.rs:674-682) take `sender: Participant, recipient: Participant` directly from the blame accusation. `Participant` is any non-zero `u16` — nothing in `blame`/`blame_internal` bounds-checks it against `params.n()` or the membership of `enc_keys`/`commitments`.
- Therefore an accusation naming `sender` or `recipient` > n (or any participant not present in the maps) panics instead of returning blame. `EncryptedMessage::read` / `EncryptionKeyProof::read` accept arbitrary bytes for the message/proof, so the whole input set is attacker-controlled.

### Impact Explanation
An unprivileged DKG participant (or any party able to submit a blame accusation with a copy of an encrypted share message) can deterministically panic the verifying node during the blame-resolution phase. In a node process, this is a remote Denial of Service equivalent in severity class to the CVE (SEGV → process abort), and it can also be used to abort blame adjudication, preventing the honest party from cryptographically proving fault.

### Likelihood Explanation
Reachable whenever a node processes blame claims from peers — the inputs (`sender`, `recipient`, `EncryptedMessage`, `EncryptionKeyProof`) are all supplied by the accusing/accused party, and no validation constrains the participant indexes to the DKG's membership set. `AdditionalBlameMachine` is explicitly documented as usable "regardless of if the caller was a member in the DKG protocol" (lib.rs:639-644), widening exposure to any third party adjudicating blame.

### Recommendation
In `blame_internal` (and `decrypt_with_proof`), replace `HashMap` indexing with `.get()` and return a `PedPoPError`/blame result when `sender`/`recipient` is not a registered participant. Alternatively, validate `u16::from(sender) <= n && u16::from(recipient) <= n` at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame` before any map access.

### Proof of Concept
```rust
// Assume a completed 3-of-3 PedPoP DKG producing `keys: ThresholdKeys<C>` and a
// `BlameMachine<C>` (or `AdditionalBlameMachine::new(ctx, 3, commitment_msgs)`).

// Craft a blame accusation where `sender` is outside the participant set.
let malicious_sender = Participant::new(4).unwrap(); // n = 3
let recipient = Participant::new(1).unwrap();

// Any well-formed serialized EncryptedMessage; its contents are irrelevant
// because the panic occurs on the map index before the share is checked.
let msg_bytes = /* serialized EncryptedMessage<C, SecretShare<C::F>> */;
let msg = EncryptedMessage::<C, SecretShare<C::F>>::read(
    &mut msg_bytes.as_slice(),
    ThresholdParams::new(3, 3, Participant::new(1).unwrap()).unwrap(),
).unwrap();

// PANIC: `self.commitments[&sender]` in `blame_internal` (lib.rs:599),
// or `self.enc_keys[&decryptor]` in `decrypt_with_proof` (encryption.rs:388)
// when `recipient` is out of range.
blame_machine.blame(malicious_sender, recipient, msg, None);
```
