### Title
Unchecked ERC-20 `transfer` return value in `IntentGatewayV2.withdraw()`/`SweepDust` lets escrow be zeroed while the actual token transfer silently fails - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` settles escrowed funds using a raw low-level `.call()` to the token's `transfer` selector and only checks that the *call* did not revert (`success`), never decoding/checking the ABI-encoded `bool` the ERC-20 standard requires callers to check. This is the exact analog of the seeded bug class ("the value returned by the function is not being checked"): non-reverting-but-`false`-returning ERC-20 tokens (a well-known non-compliant/paused-token pattern) will report `success = true` at the call level while the transfer itself did nothing, yet the contract proceeds to decrement escrow accounting and permanently mark the order as filled/refunded, causing an irreversible loss of the beneficiary's funds.

### Finding Description
In `withdraw()`, escrow release does: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```

`success` here reflects only whether the external call reverted, not whether the token's own logic actually moved value. Any ERC-20 implementation that returns `false` on failure instead of reverting (a widely documented non-standard-but-common pattern — pausable tokens, blacklist tokens, tokens with insufficient-balance edge cases that return `false`) will make `success == true` even though no tokens moved. The same pattern is repeated in the `SweepDust` handler in the same file: [2](#0-1) 

and again for transaction-fee redemption: [3](#0-2) 

Immediately after the unchecked call, `withdraw()` also sets `_filled[body.commitment] = beneficiary;` at the top of the function, before any transfer is even attempted: [4](#0-3) 

and decrements `_orders[body.commitment][token] -= amount` unconditionally after the unchecked call. Once `_filled` is set and `_orders` decremented, the order can never be retried or refunded — `onGetResponse`'s cancellation path checks `Filled()` and stops.

This deviates from the sibling, non-Tron implementation, which uses OpenZeppelin's `SafeERC20.safeTransfer` (which decodes and requires the returned boolean, and additionally handles tokens that don't return a value at all) for the exact same escrow-release logic: [5](#0-4) 

The Tron contract does correctly use `safeTransferFrom`/`safeTransfer` for the deposit-side and fee-collection paths, showing the withdrawal/sweep path is the outlier where the return-value check was dropped.

### Impact Explanation
This falls under "stealing or loss of funds": for any listed token that can return `false` instead of reverting, `withdraw()` will mark the order filled and delete/decrement escrow bookkeeping while the beneficiary receives nothing. The tokens remain custodied by the contract with no accounting path back to any user, and the withdrawal can't be retried since `_filled`/`_orders` state has already been consumed — a direct, irrecoverable fund loss for the intended beneficiary. The `SweepDust` and fee-redemption paths have the same defect, extending the risk to protocol-fee sweeps as well.

### Likelihood Explanation
This requires only that one of the intent's listed input/output tokens is an ERC-20 that can return `false` on `transfer` failure without reverting — a known, non-exotic real-world token behavior (used by several deployed tokens, and reachable even via edge-case balance/blacklist conditions on otherwise "normal" tokens). No relayer, prover, admin, or governance compromise is needed; the path is reached by the normal `onAccept`/`RedeemEscrow`/`RefundEscrow`/`SweepDust` flow that any user's order naturally exercises once the destination-side host delivers the message. The trigger condition is entirely token-contract-dependent, not attacker-privileged, making it a plausible unprivileged-exploitable condition rather than a hypothetical edge case.

### Recommendation
Replace all three raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` sites in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`'s token loop, `withdraw`'s fee redemption, and the `SweepDust` branch of `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with how the deposit side of this same file and the non-Tron `IntentsBase.sol` already handle it. This ensures both call-revert and returned-boolean-`false` failures abort the transaction before `_filled`/`_orders` state is mutated.

### Proof of Concept
1. Deploy (or select) a destination-chain token `T` that implements `transfer` to return `false` (rather than revert) when, e.g., the recipient is blacklisted, the contract is paused, or another internal condition fails — this is a real pattern used by several production tokens.
2. A user places an order on the source chain with `T` as an output/input token; a solver fills it; escrow for `T` is recorded in `_orders[commitment][T]`.
3. The `RedeemEscrow`/`RefundEscrow` POST request is delivered to `onAccept`, invoking `withdraw(body, ...)`.
4. Because the destination-chain condition causes `T.transfer(beneficiary, amount)` to return `false` without reverting, the low-level `.call` returns `success = true`.
5. `withdraw()` proceeds: `_filled[commitment] = beneficiary` is already set (set unconditionally at function entry) and `_orders[commitment][T] -= amount` executes, permanently closing out the order's escrow accounting.
6. The beneficiary never receives any `T` tokens, and the escrowed amount is now unrecoverable and cannot be re-claimed through any other path, since the order is marked filled/refunded and downstream checks (`onGetResponse`'s `Filled()` guard) block retries. [6](#0-5)
