### Title
Unrecovered type-assertion panic in the Pointer precompile crashes/aborts EVM transaction processing when a malicious CosmWasm contract returns a non-string `name`/`symbol` field - (File: precompiles/pointer/pointer.go)

### Summary
The `addCW20Pointer`, `addCW721Pointer`, and `addCW1155Pointer` methods of the Pointer precompile (`0x000000000000000000000000000000000000100b`) query an arbitrary, caller-supplied CosmWasm contract address for `token_info`/`contract_info` and then decode the JSON response into `map[string]interface{}`, immediately performing unchecked type assertions `formattedRes["name"].(string)` and `formattedRes["symbol"].(string)`.

### Finding Description
Any EVM caller (unprivileged transaction sender or contract) can invoke the Pointer precompile's `AddCW20`, `AddCW721`, or `AddCW1155` functions with an arbitrary bech32 CW contract address they control. That contract's `token_info`/`contract_info` query response is fully attacker-controlled — the caller can deploy a CosmWasm contract (a "pointer user" is explicitly an in-scope actor) whose query handler returns JSON where `name`/`symbol` is missing, `null`, a number, an array, or an object instead of a string: [1](#0-0) [2](#0-1) 

Because `formattedRes["name"]` returns `interface{}(nil)` when the key is absent (or a non-string concrete type when the value is a JSON number/array/object), the unguarded type assertion `.(string)` panics with a runtime "interface conversion" error — this is the same root-cause class as the KubeEdge advisory (CWE-476: crash triggered by processing an untrusted response without validating its shape before dereferencing/asserting on it).

This precompile logic exists in the current version and is duplicated verbatim across the legacy precompile versions (`precompiles/pointer/legacy/v552` through `v67`), all of which are reachable depending on block height via `precompiles/common`'s versioned-precompile dispatch. The `AddNative` variants are safe because they source `name`/`symbol` from bank module metadata (typed Go structs), not from JSON-decoded external contract output — only the CW20/CW721/CW1155 paths are affected because they parse arbitrary contract responses.

### Impact Explanation
A panic inside a precompile's `Execute` is not locally recovered by the Pointer precompile or by `pcommon.NewDynamicGasPrecompile`'s `RunAndCalculateGas` wrapper (only `HandlePrecompileError` runs in the `defer`, which handles returned `err` values, not panics). The panic propagates up through the go-ethereum EVM call stack into `x/evm/keeper/msg_server.go`'s `EVMTransaction` handler, which does have a `recover()` — but it immediately re-panics (`panic(pe)`) unless the panic message matches the OCC read-estimate string, meaning the panic ultimately escapes normal transaction execution and is only caught much higher up (e.g. `ProcessBlock`'s recover, or the giga executor's per-tx recover, which convert it into an `ErrPanic`/500 response rather than crashing the whole node). The net effect for the reachable path is: an unprivileged EVM caller can force a Cosmos-SDK-level panic during ordinary transaction execution by pointing the Pointer precompile at a malicious contract, causing that transaction (and potentially disrupting sibling transaction processing in the batch/goroutine, depending on which panic-recovery layer catches it) to abort with an internal panic rather than a clean revert. This does not appear to escalate to a full node crash/halt given the multiple recovery layers found in `app/app.go` (`ProcessBlock`, `ProcessTxsSynchronousGiga`, `makeGigaDeliverTx`), so the severity is best characterized as a Medium-severity availability/robustness bug (unexpected panic path in production precompile code, degrading gracefully to an aborted transaction rather than a node crash) — the same "malicious response causes nil/invalid-type dereference panic" bug class as the reported advisory, but not a Critical/High halting vulnerability once fully traced through Sei's panic-recovery layers.

### Likelihood Explanation
High likelihood of triggering: any address can deploy a CosmWasm contract with a `token_info`/`contract_info` query handler returning malformed JSON (e.g. `{"name": null}` or `{"name": 5}`), then call `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` on the Pointer precompile against that contract from an EVM transaction. No special privileges or race conditions are required — this is fully attacker-controlled input reachable in a single transaction.

### Recommendation
Replace the unchecked type assertions with checked ones (`name, ok := formattedRes["name"].(string)`) and return a proper `error` (not a panic) when the field is missing or of the wrong type, across `precompiles/pointer/pointer.go`'s `AddCW20`, `AddCW721`, `AddCW1155`, and the equivalent duplicated functions in all `precompiles/pointer/legacy/vXXX/pointer.go` files. Consider unmarshalling into a typed struct instead of `map[string]interface{}` to get compile-time-safe decoding with graceful `json.Unmarshal` error handling.

### Proof of Concept
1. Deploy a CosmWasm contract whose `contract_info`/`token_info` query handler returns `{"symbol": "ok"}` (omitting `name`, or setting `"name": null`).
2. From any EVM account, call the Pointer precompile (`0x000000000000000000000000000000000000100b`) function `addCW721Pointer(contractAddress)` (or `addCW20Pointer`/`addCW1155Pointer`) with the malicious contract's Sei bech32 address.
3. Precompile execution reaches:
```go
formattedRes := map[string]interface{}{}
json.Unmarshal(res, &formattedRes)
name := formattedRes["name"].(string)   // panics: interface conversion: interface {} is nil, not string
``` [3](#0-2) 
4. The resulting runtime panic propagates out of the EVM call and is only caught by higher-level recovery in `x/evm/keeper/msg_server.go` (which re-panics) or `app/app.go` (`ProcessBlock`/giga executor), aborting the transaction with an internal panic response instead of a clean EVM revert.
