### Title
`ReceivedOutput::read` accepts any `TxOut` without verifying it is locked to `key + offset·G`, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the reference report is an unconditional operation on an input that was never validated (`approve()` called on the ETH placeholder address, which is not a contract), causing guaranteed failure at the point of use. `ReceivedOutput::read` exhibits the same shape: it deserializes a scalar `offset`, an arbitrary `TxOut`, and an `OutPoint`, then constructs a `ReceivedOutput` asserting the trio is consistent — without ever checking that `output.script_pubkey` is actually the P2TR script for `key + offset·G`, or even that it is P2TR at all.

### Finding Description
`ReceivedOutput::read` reads three independent fields and returns them as a coherent "spendable output":

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```
(networks/bitcoin/src/wallet/mod.rs:122-134)

The only producer-side guarantee of consistency is `Scanner::scan_transaction`, which looks up `output.script_pubkey` in `self.scripts` and attaches the registered `offset` (wallet/mod.rs:199-214). But `ReceivedOutput::read` is explicitly designed to accept untrusted bytes (it is listed as an untrusted-input reader), and it performs zero validation binding `offset` to `output`:

- No check that `output.script_pubkey.is_p2tr()`.
- No check that the x-only key committed in `script_pubkey` equals `x_only(key + GENERATOR * offset)` for any scanner key.
- No check that the `outpoint` even refers to a real output containing this `TxOut`.

Downstream, this object is treated as a received, spendable output. In `processor/src/networks/bitcoin.rs`, `Output::key()` computes the signing key as `read_G(script_pubkey_xonly) - offset·G` after asserting `script.is_p2tr()` (lines 113-121). For a maliciously crafted `ReceivedOutput`:

1. If `script_pubkey` is not P2TR, `assert!(script.is_p2tr())` panics — a permanent processor crash on attacker-supplied bytes, mirroring the reference bug's guaranteed revert.
2. If `script_pubkey` is P2TR but commits to a key different from `key + offset·G` (trivially constructed by an attacker), the recovered `key` is some unrelated point. The multisig will sign for that computed key, but the actual on-chain UTXO is locked to a different x-only key, so the produced BIP-340 signature will never satisfy the output. The funds are counted as received by Serai yet are cryptographically unspendable.

The constructor is the only place where the `offset ↔ script_pubkey ↔ outpoint` invariant could be enforced for deserialized data, and it is skipped entirely — the exact analog of calling `approve()` without checking `params.fromToken != _ETH_ADDRESS_`.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., outputs relayed through any path that doesn't come from a local `Scanner`) can cause either:

- **Denial of service**: a non-P2TR `script_pubkey` triggers `assert!(script.is_p2tr())` / the `expect` on the last instruction in `Output::key()`, halting processing of the batch containing it — analogous to all Zeta swaps reverting.
- **Unspendable "received" funds**: an output whose script key doesn't match `key + offset·G` is registered as received value, but any spend attempt produces signatures for a key that doesn't control the UTXO. This matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Any integration that serializes/deserializes `ReceivedOutput`s (the API exists for exactly that purpose) and re-imports outputs from untrusted sources exposes this path. Crafting the malicious bytes requires no key knowledge — `offset` is arbitrary, `TxOut`/`OutPoint` are standard consensus encodings. The panic path (non-P2TR script) is deterministic; the unspendable-funds path requires only picking any P2TR script that wasn't derived via `register_offset`.

### Recommendation
Make deserialization enforce the invariant, the same way the reference fix gates `approve()`:

```rust
pub fn read<R: Read>(r: &mut R, key: &ProjectivePoint) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  // ... decode output, outpoint ...
  let expected = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset))
    .ok_or(io::Error::other("offset yields odd/infinity key"))?;
  if output.script_pubkey != expected {
    Err(io::Error::other("output script_pubkey does not match key + offset"))?;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

At minimum, reject non-P2TR `script_pubkey`s and mismatched keys so a `ReceivedOutput` is provably spendable by construction.

### Proof of Concept
1. Build `buf = offset_bytes || serialize(TxOut{ value, script_pubkey: ScriptBuf::new_p2wpkh(...) }) || serialize(outpoint)` — a non-P2TR script.
2. `ReceivedOutput::read(&mut buf.as_slice())` returns `Ok`.
3. Passing it to `Output::key()` panics at `assert!(script.is_p2tr())` (processor/src/networks/bitcoin.rs:114) — deterministic DoS.

Variant: use `ScriptBuf::new_p2tr_tweaked(TweakedPublicKey::dangerous_assume_tweaked(attacker_xonly))` with any `offset`. Deserialization succeeds; `Output::key()` returns `attacker_key - offset·G`, the threshold signs for it, but the UTXO is locked to `attacker_xonly` — funds counted as received are unspendable.
