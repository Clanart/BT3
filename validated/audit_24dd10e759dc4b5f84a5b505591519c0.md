### Title
`IntentGatewayV2.instance()` on TRON silently trusts unregistered source chains as `address(this)`, allowing forged cross-chain messages to drain escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The TRON build of `IntentGatewayV2` resolves an unregistered peer chain's gateway address to `address(this)` instead of reverting, unlike the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`) which reverts with `UnknownInstance` for any chain lacking an explicit `_addDeployment` registration. This mirrors the root cause of the external report: a value that must be explicitly registered during a setup/migration step (there, `historicalRoots`; here, `_instances[chain]`) is instead implicitly treated as valid/trusted by default, so a legitimate authorization check can be satisfied without the corresponding trust ever actually having been established.

### Finding Description
`IntentsBase.sol` (the canonical, audited path) requires every peer chain to be explicitly registered before it is trusted: [1](#0-0) 

By contrast, the TRON contract's `instance()` helper falls back to `address(this)` for any chain that has no explicit entry in `_instances`: [2](#0-1) 

This `instance()` result feeds directly into `authenticate()`, which is the sole gate for accepting `RedeemEscrow`/`RefundEscrow` messages that release escrowed order funds: [3](#0-2) 

Because `address(this)` is a public, known constant (the gateway's own deployed address, intentionally kept identical across chains via CREATE2 per the design notes in the sibling contract), `authenticate()` will accept **any** incoming ISMP `PostRequest` whose `request.from == address(this)`, from **any source chain that has not yet had an explicit `NewDeployment` registration** — even chains where no real `IntentGatewayV2` contract has ever been deployed, or where the deployed contract at that address is not actually this gateway. `onAccept` in the tron contract dispatches straight to withdrawal logic once `authenticate()` passes, releasing whatever tokens are escrowed under the referenced order commitment to an attacker-chosen beneficiary/solver: [4](#0-3) 

The corrupted value is the return of `instance(request.source)` for any chain id not present in `_instances` — it silently resolves to a trusted value (`address(this)`) instead of failing closed. Existing guards do not stop this because (a) `authenticate` never checks whether the chain was actually registered, only whether the resolved address matches `request.from`, and (b) ISMP's cross-chain delivery pipeline only needs a valid consensus/state proof for *some* state machine Hyperbridge already tracks — it does not require that state machine to have ever deployed or interacted with this specific `IntentGatewayV2` instance. Any state machine Hyperbridge supports generically (which is a large, growing set) becomes an implicitly trusted source the moment this contract is deployed, before any `NewDeployment` governance action ever runs — exactly analogous to the zkSync case where the very first legitimate return-trip check failed because the trusted-value registration step was skipped at setup.

### Impact Explanation
This directly enables theft of escrowed order funds (`_orders[commitment][token]`) placed by users on the TRON `IntentGatewayV2` instance: an attacker can construct a `WithdrawalRequest` naming themselves as `beneficiary`/solver for any known order commitment and get it delivered as if it originated from a legitimate, registered peer gateway, simply by dispatching from a not-yet-registered state machine with `from = address(this)`. This matches the bounty's "stealing or loss of funds," "unauthorized transaction or execution," and "false proof/state acceptance" categories, since the authentication check accepts a message from a chain identity that was never actually vetted as hosting this gateway.

### Likelihood Explanation
Likelihood is high for any newly deployed TRON `IntentGatewayV2` (or any instance following this pattern) prior to full peer registration across all Hyperbridge-supported state machines, and it persists indefinitely for any state machine that governance has not yet explicitly added via `add_deployment`/`NewDeployment`. No malicious peer, relayer, or prover behavior is required — only an unprivileged party able to dispatch an ISMP message from an already-Hyperbridge-supported but not-yet-`_addDeployment`-registered chain, which is a normal, permissionless dispatch operation from that chain's own IntentGateway-like contract or any contract at the CREATE2 address.

### Recommendation
Make `instance()` fail closed exactly like the canonical `IntentsBase._instance()` implementation: revert with `UnknownInstance` (or equivalent) when `_instances[keccak256(stateMachineId)] == address(0)`, rather than defaulting to `address(this)`. If the "same address on every chain" convenience is desired, it must be established via an explicit, governance-driven registration (as `initialize()` does in the canonical contract) rather than an implicit fallback trusted by default.

### Proof of Concept
1. Deploy `IntentGatewayV2` (TRON variant) via CREATE2 at address `G` on chain `A`. Do not yet call `NewDeployment`/`add_deployment` for chain `B`, even though Hyperbridge already has a working consensus/state-proof client for `B` (a prerequisite for any ISMP delivery, but independent of this gateway's own peer registry).
2. A user places an order on chain `A` with real escrow recorded in `_orders[commitment][token]`.
3. An attacker (or any contract) on chain `B` dispatches an ISMP `PostRequest` to Hyperbridge targeting `dest = A`, `to = G`, `from = G` (the known, address-identical gateway address), with body `RequestKind.RedeemEscrow` and a `WithdrawalRequest{ commitment, tokens: order.inputs, beneficiary: attacker }`.
4. Once delivered and proven via ordinary Hyperbridge consensus/state proofs for chain `B` (no special privilege needed — `B` is a normal supported chain), `onAccept` on `G` calls `authenticate(request)`: `instance(B)` returns `address(this) == G` (fallback, since `B` was never registered), which equals `module = address(bytes20(request.from)) = G`. Authentication passes.
5. `_withdraw` releases the escrowed tokens for `commitment` to `attacker`, even though chain `B` never had a legitimate `IntentGatewayV2` deployment or any prior trust relationship with `G`.

Note: I could not fully confirm from the index whether `_withdraw`'s internal logic in the TRON contract has any additional chain-binding check beyond `authenticate()` that might mitigate this (the tron file's `_withdraw` body was not fully retrieved within the available context), so this should be verified directly against `evm/tron/contracts/apps/IntentGatewayV2.sol` in a full checkout before remediation.

```text
    /**
     * @dev Fetch the IntentGateway contract instance for a chain.
     */
    function instance(bytes calldata stateMachineId) public view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        return gateway == address(0) ? address(this) : gateway;
    }

    /**
     * @dev Checks that the request originates from a known instance of the IntentGateway.
     */
    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }
```
