### Title
Partial-commit patch construction re-fetches the working-directory diff, letting attacker-controlled file changes between diff-render and commit silently include/exclude unintended lines - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only *some* lines/hunks of a modified file, Desktop does not stage the raw diff the user actually reviewed. Instead, at commit time `stageFiles()` → `applyPatchToIndex()` calls `getWorkingDirectoryDiff()` **again** to obtain a fresh diff from disk, and then reuses the `WorkingDirectoryFileChange.selection` object (a set of *absolute line indices* computed against the diff that was rendered earlier in the UI) to build the patch from this newly fetched diff via `formatPatch()`. [1](#0-0) [2](#0-1) 

### Finding Description
The invariant that is silently violated: "the line-index selection the user made while reviewing hunk N of diff-at-time-T1 still refers to the same content when applied to hunk N of diff-at-time-T2."

The commit flow is:
1. `updateChangesWorkingDirectoryDiff()` loads a diff once for UI rendering and the user selects/deselects lines by *absolute index* (`file.selection.isSelected(absoluteIndex)`), not by content hash. [3](#0-2) 
2. The app itself acknowledges the file can change between renders: `updateChangesWorkingDirectoryDiff` has a follow-up reconciliation step, but it only prunes now-invalid selectable lines when *re-rendering* the Changes view — it does not re-run before a commit is executed. [4](#0-3) 
3. `_commitIncludedChanges()` takes the `WorkingDirectoryFileChange` objects straight out of `repositoryStateCache` (the state computed from whatever diff/selection existed at the last status refresh) and hands them to `createCommit()` → `stageFiles()`. [5](#0-4) 
4. For any file with a partial selection, `stageFiles()` calls `applyPatchToIndex(repository, file)`. [2](#0-1) 
5. `applyPatchToIndex()` does **not** reuse the diff that produced the selection; it calls `getWorkingDirectoryDiff(repository, file)` a second, independent time, right before formatting/applying the patch. [6](#0-5) 
6. `formatPatch()` then walks the **freshly fetched** diff's hunks/lines and decides inclusion purely by `file.selection.isSelected(absoluteIndex)` — an index computed against the *old* diff. [7](#0-6) 

If the on-disk file content changes between the moment the diff was rendered/selected (T1) and the moment `applyPatchToIndex` re-reads it (T2) — e.g., because a git filter/smudge driver, a `post-checkout`/background process, a build tool, an editor auto-format-on-save, or content injected by a cloned/fetched malicious repository (submodule hooks, `.gitattributes`-driven filters, LFS smudge, etc.) rewrites the file — hunk boundaries, line counts, and content at a given absolute index shift. The stale index-based selection is then applied against the new hunk layout, so `git apply --cached` will stage/commit **different lines than the ones the user selected and reviewed in the diff viewer**, with no error (the patch is syntactically valid against the new diff, just semantically wrong versus user intent).

This is the direct structural analog of the Line-of-Credit finding: the app records a "spot" value (line-selection indices tied to diff snapshot A) and later uses it to compute what gets deposited/withdrawn (staged/committed) without re-validating that the underlying value (file content/diff) hasn't moved (rebased) since it was captured, and no before/after equality check is performed.

### Impact Explanation
The corrupted value is **the exact content of the commit that gets created and eventually pushed**. Consequences:
- Silent inclusion of lines the user explicitly deselected (potential inclusion of secrets, unfinished code, or attacker-planted content).
- Silent exclusion of lines the user intended to commit, giving the user false confidence that specific changes were captured.
- Because the commit succeeds with a valid SHA and no visible error, the user has no signal that the staged content diverged from the reviewed diff — this is a "silent corruption of what the user commits" scenario, which is explicitly in-scope per the task's valid-impact criteria.
- If the divergent commit is subsequently pushed, the corruption propagates to the shared remote/history.

### Likelihood Explanation
This requires a real race between diff-load and patch-apply, which in a synchronous UI flow is normally narrow, but Desktop's own codebase acknowledges the file "might have changed dramatically since last we loaded it" as an expected occurrence (see the comment in `app-store.ts`), meaning the window is not merely theoretical — it is wide enough that Desktop already builds partial mitigation for the *viewing* path but not for the *commit* path. Realistic triggers that don't require local/physical access or prior malware: a cloned/fetched repository configured with a smudge/clean filter, a `.gitattributes` filter driver, Git LFS, or a checked-in pre/post hook or background watcher (e.g., an npm `postinstall`/build watcher) that rewrites tracked files shortly after checkout — all of which are attacker-controlled via repository content, matching the "attacker controls a cloned/fetched repository" criterion in the Valid Impact section. No admin rights, no leaked credentials, and no unnatural user steps are needed beyond the ordinary workflow of reviewing a diff, selecting some lines, and clicking Commit.

### Recommendation
- Do not re-fetch the diff in `applyPatchToIndex`; thread through the exact `ITextDiff`/`ILargeTextDiff` object (and ideally a content hash or mtime/size snapshot) that produced the user's selection, and abort/re-prompt the commit if the file has changed since that diff was captured.
- Before calling `stageFiles`/`applyPatchToIndex`, perform the same reconciliation `updateChangesWorkingDirectoryDiff` already does for the UI (recomputing `selectableLines` against the current diff) and refuse to silently apply a selection that no longer maps cleanly, surfacing an error to the user instead.
- Alternatively, capture file hash/mtime at diff-render time and compare against the working tree immediately before invoking `git apply`, failing safely if they differ.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked text file with several distinct hunks.
2. In the Changes view, select only a subset of lines in one hunk (partial selection) — this fixes `file.selection`'s absolute-index bitmap against the diff currently rendered (T1).
3. Before the commit button is pressed, have the working-tree file rewritten by something the app doesn't control synchronously with the UI — e.g., a `.gitattributes` clean/smudge filter, a Git LFS pointer resolution, or a file-watcher/build script bundled with the repository — such that line offsets shift (lines added/removed above the selected hunk) without the Changes view being refreshed (T2).
4. Click Commit. `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-reads the diff at T2 via `getWorkingDirectoryDiff` [6](#0-5)  and `formatPatch` applies the T1 selection indices to the T2 hunks [7](#0-6) .
5. Inspect the resulting commit: it contains different line content than what was highlighted/selected in the diff viewer at the time of selection, with no warning shown to the user.

*Note: I was not able to execute this end-to-end in a live Desktop instance (no filesystem/terminal access in this mode), so the PoC above is derived purely from static code-path analysis; the actual race window and exploitability under a specific filter/hook configuration should be validated empirically before treating this as fully confirmed.*
