### Title
DLEq verifiers accept empty proofs that bind no generator or public point - (File: crypto/dleq/src/lib.rs)

### Summary
`DLEqProof::verify` and `MultiDLEqProof::verify` accept zero-statement inputs. An attacker can produce a purported proof whose challenge is computed over only the domain separator, with no generator, nonce, public point, or discrete-log statement included in the transcript. The resulting proof bytes deserialize and verify successfully, allowing a forged proof to be accepted when an empty proof statement reaches the verifier.

### Finding Description
`DLEqProof::verify` only checks that `generators.len() == points.len()`; it does not require either list to be non-empty. When both are empty, the loop adds no `generator`, `nonce`, or `point` messages to the transcript, so the challenge commits only to the `"dleq"` domain separator and any caller-supplied transcript prefix. [1](#0-0) 

The proof itself consists solely of public scalars `c` and `s`, and `DLEqProof::read` accepts two canonical scalars without checking that the proof will be bound to at least one statement. [2](#0-1) 

`MultiDLEqProof::verify` has the same issue at two levels: it permits an empty outer `generators`/`points` list, and it permits an individual discrete-log entry whose inner generator and point lists are empty. In the latter case, only the numeric index is added to the transcript and no verification statement is evaluated. [3](#0-2) 

The tests explicitly exercise zero-generator and zero-key cases, confirming that this acceptance path is reachable rather than prevented by an undocumented caller invariant. [4](#0-3) [5](#0-4) 

### Impact Explanation
A successful DLEq verification normally establishes that supplied public points share a discrete logarithm across supplied generators. With this bug, verification succeeds while establishing no such relation because there are zero statements to verify.

If a caller derives the generator/point lists from protocol data or permits an empty statement set, an unauthenticated party can submit proof bytes that satisfy the verifier without possessing a secret key or proving equality of public keys. The forged proof can therefore act as a bypass around a cryptographic membership, ownership, promotion, or equality check that relies on `verify` returning `Ok(())`.

### Likelihood Explanation
The attack is deterministic and requires no private state once an empty statement set reaches verification. The attacker only needs to cause the verifier to evaluate `DLEqProof::verify` with empty `generators` and `points`, or `MultiDLEqProof::verify` with an empty outer list or an empty inner series.

This is conditional on a caller accepting a variable-length statement list and failing to enforce a positive length before calling the verifier. Because the verifier’s API accepts slices without documenting or enforcing a non-empty precondition, this is a plausible input-validation bypass rather than a purely theoretical edge case.

### Recommendation
Reject empty proof relations in the verifier:

- In `DLEqProof::verify`, return `DLEqError::InvalidProof` when `generators.is_empty()`.
- In `MultiDLEqProof::verify`, reject `generators.is_empty()` and reject every inner series where `generators[i].is_empty()`.
- Apply the same invariant in `prove` to prevent creation of vacuously valid proofs.
- Add regression tests asserting that empty outer and inner statement lists fail verification and deserialization-driven verification.

### Proof of Concept
```rust
use zeroize::Zeroizing;
use rand_core::OsRng;
use k256::{Scalar, ProjectivePoint};
use transcript::RecommendedTranscript;
use dleq::DLEqProof;

// An attacker chooses any scalar; it is never bound to a public point.
let scalar = Zeroizing::new(Scalar::ZERO);
let generators: &[ProjectivePoint] = &[];
let points: &[ProjectivePoint] = &[];

let proof = DLEqProof::prove(
    &mut OsRng,
    &mut RecommendedTranscript::new(b"proof context"),
    generators,
    &scalar,
);

let encoded = proof.serialize();
let decoded =
    DLEqProof::<ProjectivePoint>::read(&mut encoded.as_slice()).unwrap();

// This succeeds despite proving no discrete-log equality statement.
assert!(
    decoded
        .verify(
            &mut RecommendedTranscript::new(b"proof context"),
            generators,
            points,
        )
        .is_ok()
);
```

For `MultiDLEqProof`, `generators = &[vec![]]`, `points = &[vec![]]`, and one scalar response likewise produce a successful verification while the inner relation contains zero generator/point statements.

  /// Verify the specified points share a discrete logarithm across the specified generators.
  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[G],
    points: &[G],
  ) -> Result<(), DLEqError> {
    if generators.len() != points.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"dleq");
    for (generator, point) in generators.iter().zip(points) {
      Self::verify_statement(transcript, *generator, *point, self.c, self.s);
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }

    Ok(())

  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[Vec<G>],
    points: &[Vec<G>],
  ) -> Result<(), DLEqError> {
    if points.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }
    if self.s.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"multi_dleq");
    for (i, (generators, points)) in generators.iter().zip(points).enumerate() {
      if points.len() != generators.len() {
        Err(DLEqError::InvalidProof)?;
      }

      transcript.append_message(b"discrete_logarithm", i.to_le_bytes());
      for (generator, point) in generators.iter().zip(points) {
        DLEqProof::verify_statement(transcript, *generator, *point, self.c, self.s[i]);
      }
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }

    Ok(())
