Now I have a concrete, verifiable analog. The `CallDispatcher` contract has no access control on its `dispatch()` entry point, and `IntentGatewayV2.placeOrder()` transfers user-owned tokens into that shared, unrestricted contract before invoking `dispatch()` itself as a separate, non-atomic external call.

### Title
Unrestricted `CallDispatcher.dispatch()` allows theft of in-flight predispatch escrow funds - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with **no caller restriction** at all [1](#0-0) . It is meant to be invoked only by `IntentGatewayV2`/`IntentsBase` as an internal orchestration step, but because it is a shared, permissionless singleton, any address can call it directly with an arbitrary `Call[]` payload targeting any contract, exactly mirroring the external report's core flaw: a privileged execution surface (`Emitter`'s `EMITTER` role granted to a caller that can relay arbitrary calldata) that lacks a restriction preventing it from being invoked outside its intended, trusted context.

### Finding Description
In `placeOrder()`, when an order has `predispatch` calldata, the gateway first pushes the user's tokens into the `dispatcher` contract via `safeTransferFrom(msg.sender, dispatcher, amount)` or a raw ETH transfer, in a loop [2](#0-1) . Only **after** all assets have been moved does it call `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [3](#0-2) , followed by a second `dispatch()` call to sweep the resulting balances back to the gateway [4](#0-3) .

Because `CallDispatcher.dispatch()` is a public entrypoint with zero access control [1](#0-0) , and the same `dispatcher` address is a long-lived, shared contract used by every order across the protocol (also invoked from `IntentsBase._execute()` for postdispatch fills [5](#0-4) ), any tokens/ETH the dispatcher is holding at any point in time are exposed to a permissionless "steal it now" call from anyone who front-runs the gateway's own sweep-back transaction. `CallDispatcher` also has a `receive()` function to accept ETH [6](#0-5) , so it accumulates a real balance rather than just relaying calls atomically.

Concretely: `placeOrder()` sends the user's ETH/ERC20 into `dispatcher` (line 216 or 219), then calls `dispatcher.dispatch(order.predispatch.call)` as a **separate transaction step**, not atomically bundled with the deposit at the EVM call-frame level from the user's perspective — an attacker monitoring the mempool can front-run the `placeOrder` transaction's own internal `dispatch()` call, or more directly, can call `CallDispatcher.dispatch()` themselves in a transaction sandwiched between the user's asset transfer and the gateway's own predispatch/sweep calls within the same block (e.g., via same-block MEV/bundle construction), supplying a `Call[]` such as `{to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dispatcher.balanceOf())}` or `{to: attacker, value: dispatcherEthBalance, data: ""}`, draining the escrowed input assets before the gateway's own sweep-back executes.

This directly matches the report's broken invariant: a role/entrypoint intended to be restricted to a single trusted orchestrator (the `EMITTER` role / here, the intended "only-IntentGatewayV2-calls-dispatch" assumption) has **no on-chain enforcement**, so any external actor can invoke the same privileged capability directly.

### Impact Explanation
User funds placed into `CallDispatcher` as part of `placeOrder()`'s predispatch flow (or `IntentsBase._execute()`'s postdispatch flow) can be stolen by any unprivileged address before the gateway retrieves them, resulting in direct loss of escrowed user funds — a fund-theft impact matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories.

### Likelihood Explanation
Likelihood is high for any order that uses `predispatch`/`postdispatch` calldata (a documented, first-class feature of `IntentGatewayV2` [7](#0-6) ): the attack requires only a plain contract call to a public, unauthenticated function (`CallDispatcher.dispatch`) with attacker-controlled calldata — no privileged role, relayer, or prover assumption is needed, and the window is any block in which `CallDispatcher` holds a non-zero balance between the deposit and the gateway's own sweep call.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by authorized orchestrators (e.g., an `onlyAuthorizedCaller` modifier checking `msg.sender` against a stored allowlist of gateway/app addresses), similar to the report's fix of blocking arbitrary target calls. Alternatively, make `CallDispatcher` a per-call, single-use contract (deployed fresh per order via `CREATE2`/`CREATE` and self-destructed or with delegatecall-based execution scoped to the caller) so no shared, externally drainable balance ever exists between the deposit and sweep steps.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder()` with `predispatch.assets` containing 100 USDC and non-empty `predispatch.call`.
2. Inside `placeOrder()`, 100 USDC is transferred from the user to `dispatcher` (line 219) via `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`.
3. Before `placeOrder()`'s own subsequent line `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` executes (or is included in the block), an attacker submits a transaction calling `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 100e6)})]))` directly.
4. `CallDispatcher.dispatch()` has no access-control check [1](#0-0) , so it executes the attacker's call, transferring the escrowed 100 USDC out to the attacker.
5. The user's subsequent `placeOrder()` predispatch/sweep steps see an insufficient dispatcher balance and revert or under-credit escrow (`InsufficientNativeToken`/`InvalidInput` at lines 239/244), while the user's funds are already gone.
