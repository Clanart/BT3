### Title
SchnorrAggregate verification accepts forged aggregates: nonces and keys are not bound, allowing `s = 0`, `R_i = -c_i·A_i` forgery for arbitrary keys/messages - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the Starlay incident — where a flawed index calculation let an attacker withdraw more than they deposited — `SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs` uses an incorrect accumulation formula that lets an unprivileged attacker "claim" valid signatures that were never produced. The aggregate verification equation checks `Σ z_i·(R_i + c_i·A_i) − s·G == 0`, but neither the per-signature weight `z_i` nor anything else in the statement binds the nonces `R_i` or the keys. An attacker can set each `R_i = −c_i·A_i` and `s = 0`, making every term cancel and the multiexp return identity, so `verify` returns `true` for any set of public keys and challenges.

### Finding Description
`SchnorrAggregate::verify` builds a `DigestTranscript` from the caller-supplied `dst` and appends only the challenges (`crypto/schnorr/src/aggregate.rs:132-136`). The weights `z_i` are then squeezed from that digest (`weight`, lines 22–65, called at line 140), and the statement `Σ (z_i·R_i) + (z_i·c_i·A_i) + (−s·G) = 0` is evaluated via `multiexp_vartime` (lines 138–145).

Per the half-aggregation scheme this implements (eprint 2021/350), the aggregation weight must bind the *entire* aggregate: all public keys, all nonces `R_i`, and all messages. Here:

- `R_i` values are never transcripted — they are attacker-controlled inputs read via `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`).
- Public keys are never transcripted either; only the challenges are.
- `s` is a single free scalar.

The verification equation therefore reduces to `Σ z_i·(R_i + c_i·A_i) = s·G` with `z_i`, `c_i`, `A_i` all known to the prover before choosing `R_i` and `s`. The trivial forgery: for every `i`, set `R_i = −c_i·A_i` (a publicly computable point) and set `s = 0`. Each pair `(z_i·(−c_i·A_i)) + (z_i·c_i·A_i)` cancels to the identity, and the generator term vanishes, so `multiexp_vartime(&pairs).is_identity()` is true.

### Impact Explanation
Any verifier relying on `SchnorrAggregate::verify` accepts an aggregate signature over arbitrary public keys and arbitrary challenges (i.e., arbitrary messages, since challenges bind key/nonce/message upstream) produced by someone who knows none of the private keys. This is a universal forgery of the aggregated signature — the strongest possible verification failure, matching the incident class of accounting math that credits more than what exists.

### Likelihood Explanation
The attack requires only public data: the target public keys `A_i` and challenges `c_i`. `SchnorrAggregate` is deserializable from untrusted bytes via `SchnorrAggregate::read`, and `verify` is a public API. No key knowledge, no threshold collusion, no timing, and no malformed-curve inputs are needed; the forgery is deterministic and works on the first attempt.

### Recommendation
Bind the full aggregate into the weight derivation in `SchnorrAggregate::verify` (and symmetrically in `SchnorrAggregator::aggregate`/`complete`): transcript each public key, each `R_i`, and each challenge before squeezing `z_i`, e.g. `digest.append_message(b"key", key.to_bytes())` and `digest.append_message(b"R", self.Rs[i].to_bytes())` inside the loop at `crypto/schnorr/src/aggregate.rs:139-143`, with `SchnorrAggregator::aggregate` updated to commit the same fields in the same order. Alternatively, compute the linear combination as `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G` only after weights commit to the complete `{A_i, R_i, c_i}` set, per eprint 2021/350.

### Proof of Concept
For any `keys_and_challenges = [(A_1, c_1), …, (A_n, c_n)]` with `n ≥ 1`:

1. For each `i`, compute `R_i = −(c_i · A_i)` (pure public-key arithmetic; `c_i` is a public scalar).
2. Set `s = 0`.
3. Construct `SchnorrAggregate { Rs: [R_1, …, R_n], s: 0 }` — deliverable via `SchnorrAggregate::read` as `u32` length, the `R_i` encodings, and a zero `s` encoding.
4. `verify(dst, keys_and_challenges)` computes `pairs = [(z_i, −c_i·A_i), (z_i·c_i, A_i)]` for each `i`, plus `(0, G)`. Every pair sums to identity regardless of the `z_i` values (which depend only on the challenges), so `multiexp_vartime(&pairs).is_identity() == true` and verification succeeds — a valid-looking aggregate signature for keys the attacker does not control.
