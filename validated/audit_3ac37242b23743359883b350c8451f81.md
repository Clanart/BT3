### Title
Cross-shop session hijacking via unauthenticated `shop` parameter in `EnsureInstalled` - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
`ShopifyApp::EnsureInstalled` (the legacy, non-token-exchange authentication concern) derives the "current shop" purely from the unsigned `params[:shop]` query parameter and then loads that shop's stored offline session/access token by domain, with no cryptographic proof (no HMAC, no session-token/JWT, no session cookie) that the requester is actually associated with that shop. This mirrors the RocketStorage pattern of an unauthenticated caller being able to select and act on a "protected" resource belonging to another party simply by supplying the right key/identifier.

### Finding Description
`current_shopify_domain` is computed directly from the request parameter without any signature check: [1](#0-0) 

That attacker-controlled domain is then used to look up and expose the stored offline session (containing the real Shopify access token) for that shop: [2](#0-1) 

`check_shop_known` sets `@shop` to that session if one exists in storage, purely based on the unauthenticated `shop` param match: [3](#0-2) 

For non-embedded (top-level) requests, `validate_non_embedded_session` only checks that the *shop's stored offline token is still valid* (an Admin API call using that token) — it performs no verification that the current HTTP requester is the legitimate merchant or has any session tied to that shop: [4](#0-3) 

There is no `before_action` in this concern that validates an HMAC, a session cookie, or a verified session token against the supplied `shop` domain — unlike the OAuth callback flow (`CallbackController`) or `WebhookVerification`/`PayloadVerification`, which use `hmac_valid?` to cryptographically authenticate a request: [5](#0-4) 

As a result, any controller including `EnsureInstalled` (used when `use_new_embedded_auth_strategy?` is `false`, i.e. the legacy/default OAuth flow) trusts `installed_shop_session`/`@shop` — the victim shop's real offline access token — for any anonymous request that supplies `?shop=<victim-domain>` for a previously-installed shop, as long as that shop's token hasn't been revoked.

### Impact Explanation
Any unauthenticated visitor can force a controller action gated by `EnsureInstalled` to execute using another (unrelated) merchant's real offline Shopify access token, by simply passing that merchant's shop domain in the `shop` query parameter. Since `installed_shop_session` exposes the actual `ShopifyAPI::Auth::Session` (with `access_token`) for that domain, this is a cross-shop authorization bypass: the requester never proves possession of a valid App Bridge session token, OAuth cookie, or HMAC-signed admin redirect — they only need to know (or guess) a `myshopify.com` subdomain that has installed the app. This can lead to unauthorized data access/modification against a merchant's store depending on what the wrapped controller action does with `installed_shop_session`/`@shop`.

### Likelihood Explanation
This code path is reachable by a fully anonymous HTTP request (no cookies, no headers, no token) — an attacker only needs to send a normal top-level GET request with a `shop` parameter set to any myshopify domain that has installed the app (shop domains are often guessable/enumerable, e.g., via storefronts). The legacy flow (`use_new_embedded_auth_strategy? == false`) is still the default/available configuration in this gem version, so likelihood is high for any app still using `EnsureInstalled` for non-embedded pages.

### Recommendation
- Do not derive the acting shop/session solely from the unauthenticated `shop` query parameter for non-embedded requests. Require a verified session (session cookie set only after OAuth, or a verified session token/JWT) before exposing `installed_shop_session`.
- If `shop` must be accepted from the URL, cryptographically bind it (HMAC as Shopify does on admin-initiated requests, or the JWT session-token `dest`/`iss` claim as used in `ShopifyApp::TokenExchange`/`WithShopifyIdToken`) before trusting it to select a stored access token.
- Prefer migrating fully to `use_new_embedded_auth_strategy?` / `EnsureHasSession`, which already derives the shop from a verified ID token (`authenticated_shopify_domain_from_token`) rather than from a bare request parameter, and rejects mismatched requested/authenticated domains (`reject_mismatched_requested_shopify_domain`).

### Proof of Concept
1. Determine or guess a myshopify.com domain that has previously installed the app (e.g., `victim-shop.myshopify.com`), so a shop session already exists in storage.
2. As a completely anonymous user (no cookies, no App Bridge, no HMAC), send: `GET https://app.example.com/some_protected_path?shop=victim-shop.myshopify.com`
3. `check_shop_domain` passes because `current_shopify_domain` resolves via `ShopifyApp::Utils.sanitize_shop_domain(params[:shop])` [1](#0-0) .
4. `check_shop_known` finds the stored session for `victim-shop.myshopify.com` and sets `@shop` to it [3](#0-2) .
5. `validate_non_embedded_session` merely confirms the stored offline token still works against Shopify's Admin API — it does not check the requester's identity [4](#0-3) .
6. The controller action now executes using `installed_shop_session`, i.e., `victim-shop`'s real offline access token, for a request that was never authenticated as belonging to that shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
