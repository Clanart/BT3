### Title
`SyscallGetProcessedSiblingInstruction` charges a flat `syscall_base_cost` regardless of instruction data/account size or trace-scan length, materially underpricing compute - (File: `syscalls/src/lib.rs`)

### Summary
The Float Capital `totalFunding` bug charged a fee based on a fixed/proxy quantity (`overbalancedValue`) instead of the actual amount of work the Float Pool had to do (`overbalancedValue - underbalancedValue`), letting large amounts of real work go essentially unpriced. The Agave analog is `SyscallGetProcessedSiblingInstruction` in `syscalls/src/lib.rs:2009-2107`, which charges only the flat `syscall_base_cost` at the top of the function [1](#0-0) , but then performs work that scales with the size of the instruction trace and the size of the copied instruction (data bytes and account metas) [2](#0-1) [3](#0-2) .

### Finding Description
Every other syscall that copies a variable amount of data out of the VM into caller memory charges compute proportional to the size of that data:
- `SyscallSetReturnData` charges `len / cpi_bytes_per_unit` [4](#0-3) .
- `SyscallGetReturnData` charges `(length + Pubkey size) / cpi_bytes_per_unit` [5](#0-4) .
- `translate_instruction_rust`/`translate_instruction_c` (used for CPI) charge based on `data.len()` and `account_metas.len() * size_of::<AccountMeta>()` [6](#0-5) [7](#0-6) .
- Generic mem-ops (`memcpy`, etc.) charge `n / cpi_bytes_per_unit` [8](#0-7) .

In contrast, `SyscallGetProcessedSiblingInstruction` consumes only `syscall_base_cost` once, up front [1](#0-0) , before it:
1. Scans backwards through the instruction trace to find the requested sibling instruction — a loop over `range.rev()` whose length is bounded only by `MAX_INSTRUCTION_TRACE_LENGTH` [2](#0-1) , and
2. If found, translates/copies the full instruction `data` (`instruction_context.get_instruction_data()`) and builds/copies an `AccountMeta` for every instruction account (`get_number_of_instruction_accounts()`) into caller memory [9](#0-8) .

Neither the trace-length scan nor the per-byte/per-account copy is metered. This is structurally the same defect pattern as the Float Capital bug: the priced quantity (`syscall_base_cost`, a constant) is decoupled from the actual quantity of work performed (trace depth searched, plus instruction data length and account count copied), so a caller that triggers large sibling instructions (large data payloads, many accounts) via CPI trace positioning pays the same fixed price as a caller retrieving a tiny sibling instruction.

### Impact Explanation
Because cost does not scale with the size of the data/accounts copied or with the depth of the trace search, a program can obtain large amounts of "translation" work (data copy + account-meta materialization, one instruction-account lookup and `AccountMeta` construction per account) from the runtime for the same fixed compute-unit price as a single-byte, single-account result. This is a compute-mispricing/underpricing issue rather than a memory-safety or privilege-escalation bug — sizes of `data_len`/`accounts_len` are still checked for equality against the actual sibling instruction (line 2069-2071) so it does not appear to enable out-of-bounds access, but it does let the actual "translate/copy" cost be decoupled from the price paid, matching the report's core complaint that a fee formula fails to correspond to the true magnitude of work being compensated for.

### Likelihood Explanation
This syscall (`sol_get_processed_sibling_instruction`) is available to any unprivileged on-chain program with no special permission, and the instruction data length / number of accounts of a sibling instruction (and CPI trace depth, bounded by `MAX_INSTRUCTION_TRACE_LENGTH`/`MAX_CALL_DEPTH`) are fully attacker-controlled by constructing a transaction with many CPIs carrying large instruction data and many accounts, then calling this syscall repeatedly. This makes the underpricing straightforward to trigger deterministically; the ceiling on the magnitude of impact is limited by other transaction-level limits (max instruction data size, max accounts, max trace length, max compute budget), which reduces — but does not eliminate — the practical severity.

### Recommendation
Meter `SyscallGetProcessedSiblingInstruction` proportionally to the actual work performed, consistent with the rest of the syscalls in this module:
- After locating a sibling instruction, charge for the copied `data_len` and `accounts_len * size_of::<AccountMeta>()` the same way `translate_instruction_rust`/`translate_instruction_c` price CPI instruction translation.
- Consider also charging a per-iteration cost (or capping/pricing) the backward scan over the instruction trace, since trace depth is attacker-influenced.

### Proof of Concept
Not applicable in the traditional sense (no crash/PoC executable was run); the finding is derived directly from reading `SyscallGetProcessedSiblingInstruction`'s implementation and comparing its charging behavior to every other size-dependent syscall in the same file/module [10](#0-9) . A concrete PoC would construct a transaction with a top-level or nested CPI instruction carrying maximal instruction data and maximal account count, then have a callee invoke `sol_get_processed_sibling_instruction` in a loop to observe that compute consumption per call remains flat (`syscall_base_cost`) independent of the size of the copied sibling instruction, unlike equivalent calls to `sol_set_return_data`/`sol_get_return_data` or CPI invocation whose costs scale with size.

declare_builtin_function!(
    /// Get a processed sigling instruction
    SyscallGetProcessedSiblingInstruction,
    fn rust(
        invoke_context: &mut InvokeContext<'_, '_>,
        index: u64,
        meta_addr: u64,
        program_id_addr: u64,
        data_addr: u64,
        accounts_addr: u64,
    ) -> Result<u64, Error> {
        let execution_cost = invoke_context.get_execution_cost();

        invoke_context.compute_meter.consume_checked(execution_cost.syscall_base_cost)?;

        let stack_height = invoke_context.get_stack_height();
        let mut reverse_index_at_stack_height = 0;
        let mut found_instruction_context = None;
        let current_ix_caller = invoke_context.transaction_context.get_current_instruction_context()?.get_index_of_caller();

        // Either we only search for top level instructions or CPIs, depending on the stack height.
        let range = if stack_height == 1 {
            0..invoke_context.transaction_context.next_top_level_instruction_index()
        } else {
            let end = invoke_context.transaction_context.get_instruction_trace_length();
            let start = end.saturating_sub(invoke_context.transaction_context.number_of_cpis_in_trace());
            start..end
        };

        for index_in_trace in range.rev() {
            let instruction_context = invoke_context
                .transaction_context
                .get_instruction_context_at_index_in_trace(index_in_trace)?;
            // If we are searching through CPIs, sibling instructions must have the same caller
            // but instructions from different callers are interspaced in the frame.
            if instruction_context.get_index_of_caller() != current_ix_caller {
                continue;
            }

            if instruction_context.get_stack_height() < stack_height {
                break;
            }
            if instruction_context.get_stack_height() == stack_height {
                if index.saturating_add(1) == reverse_index_at_stack_height {
                    found_instruction_context = Some(instruction_context);
                    break;
                }
                reverse_index_at_stack_height = reverse_index_at_stack_height.saturating_add(1);
            }
        }

        let check_aligned = invoke_context.get_check_aligned();
        let memory_mapping = invoke_context.memory_contexts.memory_mapping_mut()?;
        if let Some(instruction_context) = found_instruction_context {
            translate_mut!(
                memory_mapping,
                check_aligned,
                let result_header: (&mut ProcessedSiblingInstruction) = map(meta_addr)?;
            );

            if result_header.data_len == (instruction_context.get_instruction_data().len() as u64)
                && result_header.accounts_len
                    == (instruction_context.get_number_of_instruction_accounts() as u64)
            {
                translate_mut!(
                    memory_mapping,
                    check_aligned,
                    let program_id: (&mut MaybeUninit<Pubkey>) = map(program_id_addr)?;
                    let data: (&mut [MaybeUninit<u8>]) = map(data_addr, result_header.data_len)?;
                    let accounts: (&mut [MaybeUninit<AccountMeta>]) = map(accounts_addr, result_header.accounts_len)?;
                    let result_header: (&mut ProcessedSiblingInstruction) = map(meta_addr)?;
                );
                // Marks result_header used. It had to be in translate_mut!() for the overlap checks.
                let _ = result_header;

                program_id.write(*instruction_context.get_program_key()?);
                data.write_copy_of_slice(instruction_context.get_instruction_data());
                let account_metas = (0..instruction_context.get_number_of_instruction_accounts())
                    .map(|instruction_account_index| {
                        Ok(AccountMeta {
                            pubkey: *instruction_context.get_key_of_instruction_account(instruction_account_index)?,
                            is_signer: instruction_context
                                .is_instruction_account_signer(instruction_account_index)?,
                            is_writable: instruction_context
                                .is_instruction_account_writable(instruction_account_index)?,
                        })
                    })
                    .collect::<Result<Vec<_>, InstructionError>>()?;
                accounts.write_clone_of_slice(account_metas.as_slice());
            } else {
                result_header.data_len = instruction_context.get_instruction_data().len() as u64;
                result_header.accounts_len =
                    instruction_context.get_number_of_instruction_accounts() as u64;
            }
            return Ok(true as u64);
        }
        Ok(false as u64)
    }
);

use {super::*, crate::translate_mut};

fn mem_op_consume(invoke_context: &mut InvokeContext, n: u64) -> Result<(), Error> {
    let compute_cost = invoke_context.get_execution_cost();
    let cost = compute_cost.mem_op_base_cost.max(
        n.checked_div(compute_cost.cpi_bytes_per_unit)
            .unwrap_or(u64::MAX),
    );
    invoke_context.compute_meter.consume_checked(cost)
}
