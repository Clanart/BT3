### Title
`distribution` precompile's `rewards()` view accepts ETH value without validation, permanently stranding sent funds - ([File: precompiles/distribution/distribution.go])

### Summary
The `distribution` precompile's `rewards(address)` query method is the only view-type method in the file that fails to call `pcommon.ValidateNonPayable(value)` (or the equivalent `p.validateInput`), unlike every sibling view (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`), which all reject non-zero `value`. This is the root cause matched to the reported bug class: a function that should reject/validate an attached fee/value doesn't, so a value-bearing call is processed incorrectly instead of reverting, causing user funds to be silently lost rather than an explicit, safe rejection.

### Finding Description
In `precompiles/distribution/distribution.go`, the `Execute` dispatcher handles the `RewardsMethod` case with no non-payable guard: [1](#0-0) 

Compare this to every other query method in the same file, which explicitly enforces `p.validateInput(value, args, N)` → `pcommon.ValidateNonPayable(value)`, e.g.: [2](#0-1) [3](#0-2) 

The `rewards` function itself only validates argument length, never the value: [4](#0-3) 

`ValidateNonPayable` is the shared safety check used throughout all precompiles to reject value-bearing calls to non-payable functions: [5](#0-4) 

This is confirmed by the test-suite comment describing exactly this gap: [6](#0-5) 

Because the EVM transfers `value` (in wei) to the precompile address (0x…1007) before/along with the call, and `rewards()` neither rejects it (like other views) nor consumes/refunds it via `pcommon.HandlePaymentUsei` (like payable transaction methods e.g. `withdrawDelegationRewardsFor`/wasmd's `executeBatch` pattern), a caller who mistakenly or unknowingly attaches value to a `rewards(address)` call will have that value accepted into the precompile's EVM balance with no code path to reclaim it — the distribution precompile address is not a real Sei account with withdrawal logic tied to arbitrary incoming value.

### Impact Explanation
This directly matches the accepted-fund-loss criteria: any wei sent along with a `rewards()` call is permanently stranded (there is no bank/EVM balance sweep or refund path for value sent to this specific view method), constituting concrete, irreversible loss of user funds for any account that calls this reachable, unprivileged public RPC/precompile endpoint (e.g., wallets/aggregators that always attach `value` for a route, or a user manually including value by mistake).

### Likelihood Explanation
Likelihood is moderate: this requires a caller (user, wallet, dApp integrator) to attach non-zero `value` to a call targeting the `rewards` selector on the distribution precompile (`0x0000000000000000000000000000000000001007`), which is trivially reachable by any EVM transaction sender or contract with no privilege requirements. It is a straightforward, one-transaction fund-loss condition, not requiring adversarial coordination or specific network conditions — but it does depend on the caller supplying value to a call that (per the ABI) is documented/expected to be a view.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` (or route through the existing `p.validateInput(value, args, 1)` helper already used by every sibling view) to the `rewards` method, consistent with all other read-only distribution precompile methods, so value-bearing calls revert instead of silently stranding funds.

### Proof of Concept
1. Caller submits an EVM transaction (or `eth_call`/contract call) to precompile address `0x0000000000000000000000000000000000001007` invoking `rewards(address)` with a non-zero `value` (e.g., 1 usei worth of wei).
2. Dispatch in `Execute` routes to `case RewardsMethod: return p.rewards(ctx, method, args)` with no `ValidateNonPayable` check (contrast with `case WithdrawValidatorCommissionMethod: if err = pcommon.ValidateNonPayable(value); err != nil { ... }` a few lines above).
3. `rewards()` only checks `ValidateArgsLength(args, 1)`, executes the query, and returns success — the call does not revert.
4. The attached value, having already been transferred to the precompile's EVM balance as part of call semantics, is never refunded (no `HandlePaymentUsei` call exists in `rewards()`), and remains stuck at the precompile address with no legitimate withdrawal path, unlike `payablePrecompiles` (bank/staking/gov/wasmd) which have explicit payment-handling and event-suppression logic.
