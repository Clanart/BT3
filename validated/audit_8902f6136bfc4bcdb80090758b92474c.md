### Title
Division by zero in KIP-71 dynamic base fee calculation when governance `Kip71GasTarget` is set to 0 - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter with no zero-check, mirroring the `FractionalAvgPool` bug pattern where a user/governance-controlled divisor can reach zero and crash the process at runtime.

### Finding Description
`NextMagmaBlockBaseFee` computes the new base fee by dividing by `gasTarget` in both the "gas used above target" and "gas used below target" branches: [1](#0-0) 

```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // <-- divide by gasTarget
```
and the symmetric branch below it does the same. `gasTarget` comes directly from `kc.GasTarget`, i.e. the governance parameter `Kip71GasTarget` (`reward.gastarget`), with no guard against zero, unlike `BaseFeeDenominator`, which has an explicit fallback to 64 if it is zero: [2](#0-1) 

Crucially, the parameter's `FormatChecker` in the governance parameter table is `noopFormatChecker` — it accepts any `uint64`, including `0` — whereas the neighboring `Kip71BaseFeeDenominator` parameter explicitly rejects `0`: [3](#0-2) 

Since `GasTarget` is a governance parameter, a validator/governing entity can vote it to `0`. Once enacted, every node computing `NextMagmaBlockBaseFee` for a block with nonzero `parentGasUsed` will hit `parentGasUsed > gasTarget` (0) and execute the `x.Div(x, new(big.Int).SetUint64(0))` call. Go's `big.Int.Div` panics with `"division by zero"` in this situation (there is no software check comparable to TensorFlow's `DCHECK_GT`, which is only a debug-mode assertion in the original CVE).

This function is invoked on the consensus-critical header validation path (`VerifyMagmaHeader`), the block-building/mining path, transaction pool base-fee checks, and the public `eth_feeHistory`/`kaia_feeHistory` RPC path: [4](#0-3) [5](#0-4) 

### Impact Explanation
If `GasTarget` is set to `0` via governance, every honest node computing the next Magma base fee for a block that used any gas will panic inside `big.Int.Div`, causing:
- Block validators to crash when verifying/producing the next block header (`VerifyMagmaHeader` / block assembly), since the base fee must be recomputed every block.
- Public RPC nodes serving `feeHistory` to crash/panic when processing any block after this parameter becomes active, since `processBlock` unconditionally calls `NextMagmaBlockBaseFee` for the next-block computation.

This is a network-wide denial-of-service: a single governance vote that sets `Kip71GasTarget=0` would deterministically crash all conforming nodes on the very next block with nonzero gas usage, since the computation is a required part of consensus (base fee verification) and not merely advisory. This satisfies the "state divergence between honest nodes / acceptance of invalid transaction or block" bar loosely, but more directly it is a network-halting crash — the most severe outcome achievable via a governance parameter.

### Likelihood Explanation
The likelihood of triggering requires a successful governance vote for `Kip71GasTarget=0`, which typically requires validator/governing-node privileges rather than being reachable by an arbitrary unprivileged transaction sender. However, the underlying issue — missing zero-check on a value directly echoed from governance input with a permissive (`noopFormatChecker`) validator — is a real code defect analogous to the reported CVE class, and it is inconsistent with the sibling parameter `Kip71BaseFeeDenominator`, which explicitly guards against `0` at both the parameter-validation layer and inside `NextMagmaBlockBaseFee`. Given that governance parameter changes are an explicitly in-scope reachable path per the review rules, and the fix is trivial/consistent with the existing `BaseFeeDenominator` pattern, this is a legitimate, low-effort-to-trigger (once a vote passes) medium-severity defect.

### Recommendation
Add the same defensive fallback used for `BaseFeeDenominator` for `GasTarget`: if `kc.GasTarget == 0`, use a safe non-zero default (or reject/clamp the value) before performing any division in `NextMagmaBlockBaseFee`. Additionally, tighten the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go` to reject `0`, consistent with `Kip71BaseFeeDenominator`.

### Proof of Concept
1. Governance enacts (or a governing node votes) `Kip71GasTarget = 0` (permitted because its `FormatChecker` is `noopFormatChecker`, allowing any `uint64` including `0`): [6](#0-5) 
2. On the next block whose parent used gas > 0 (i.e., `parentGasUsed > gasTarget(0)`), every node calls `KIP71Config.NextMagmaBlockBaseFee(...)`: [7](#0-6) 
3. `parentGasUsed != gasTarget(0)` and `parentGasUsed > gasTarget(0)`, so the code proceeds to `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, which panics with "division by zero" in Go's `math/big` package, crashing the node process during block verification/production and RPC fee-history serving.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
