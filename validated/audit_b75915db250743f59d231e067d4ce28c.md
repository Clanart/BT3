### Title
Coarse `(filePath, category)` dedup key in `handle_commit_review_posttooluse` lets a new dangerous finding be silently suppressed by an earlier same-category finding on the same file - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
`handle_commit_review_posttooluse` records reviewed findings and deduplicates future findings using only the tuple `(filePath, category)`, not the actual vulnerable code. Because an attacker fully controls the diff content of successive commits/amends on a session, they can get a low-severity finding recorded for a file+category once, after which any subsequent — genuinely different and more dangerous — finding that lands on the same file and the same LLM-assigned category is treated as "already known" and never surfaces via `PostToolUse`, `Stop`, or push-sweep.

### Finding Description
After a commit is analyzed, `handle_commit_review_posttooluse` builds `finding_snapshots` and records them into shared session state keyed only by `(filePath, category)`: [1](#0-0) 

The same coarse key is used for the late-dedup step (`_dedup_against_state`) that filters out `vulns` already present in `previous_findings`, and the Stop hook uses the identical `(filePath, category)` key to record/merge fires: [2](#0-1) [3](#0-2) 

The comments explicitly document this as intentional, to avoid "under-dedupe" from diff-context drift in `vulnerableCode`: [4](#0-3) 

Because the key ignores `vulnerableCode`/line content entirely, an attacker who fully controls the commit/amend diffs (a normal Claude Code user, no elevated privilege needed) can:
1. Commit a trivial or low-risk change that the LLM classifies into some `category` (e.g., "Injection") on file `F`, which gets recorded into `previous_findings` via `_record_findings`.
2. In a later commit or amend, introduce a genuinely new and more dangerous vulnerability in the *same file* `F` that the reviewer LLM classifies under the *same* `category`.
3. `_dedup_against_state` treats the new finding's key `(F, category)` as already present in `prompted = _finding_keys(previous_findings)` and drops it from `new_vulns`, so no stderr guidance is emitted and `sys.exit(2)`/rewake never fires for the new dangerous code: [2](#0-1) 
4. The Stop hook, sharing the same `previous_findings` state and the same `(filePath, category)` key, is equally blind to the new finding.

This breaks the stated invariant that dangerous edits/commands must remain reviewable and blockable across retries/amends, since the review pipeline's memory of "already surfaced" findings is not tied to the actual vulnerable content, only to a coarse classification tuple that is fully attacker-influenced (attacker controls both the file path touched and, indirectly, the category the LLM assigns by choosing the vulnerability pattern).

I was not able to retrieve the exact implementation of `_dedup_against_state` / `_finding_keys` (defined in `plugins/security-guidance/hooks/llm.py`) within the available tool budget, so the precise key-normalization/matching semantics there are inferred from the call-site comments and mirrored Stop-hook logic rather than directly confirmed.

### Impact Explanation
This is a Logic-level guard bypass: a required security control (commit/push/stop review) can be defeated by an attacker-controlled sequence of commits that reuses a previously-seen `(filePath, category)` pair, causing a newly introduced dangerous change to emit no warning and no rewake. This matches "Logic-level service disruption caused by bypassing a required guard or misbinding security state" since the review's state binding (dedup key) is misbound to a coarser identity than the actual finding.

### Likelihood Explanation
Feasible for any unprivileged Claude Code user/session: no special permissions are needed beyond normal edit/commit access, and the attacker fully controls diff content and can choose to commit a "seed" low-severity issue before landing the real dangerous change, or exploit incidental collisions where the LLM classifies unrelated vulnerabilities in the same file under the same category label. It requires the review LLM to assign the same `category` string to two different vulnerabilities in the same file, which is plausible given limited category taxonomies (e.g., "Injection", "Access Control", "Command Execution").

### Recommendation
Tighten the dedup key so it cannot be satisfied by unrelated vulnerabilities: incorporate a stable content fingerprint (e.g., normalized/line-independent hash of the vulnerable code snippet or the specific CWE/rule ID plus a hash of the surrounding function) in addition to `(filePath, category)`, or require an explicit "same root cause" signal from the LLM before suppressing a new finding. At minimum, avoid ever suppressing findings whose severity is higher than the previously recorded finding for that same key.

### Proof of Concept
Integration test plan against `handle_commit_review_posttooluse`:
1. Initialize session state with `previous_findings = [{"filePath": "app.py", "category": "Injection", "vulnerableCode": "os.system(cmd)"}]` (simulating a prior low-severity finding already reviewed).
2. Craft a commit diff to `app.py` that introduces a distinct, high-severity vulnerability that the mocked `analyze_code_security`/agentic reviewer classifies as `category="Injection"` (e.g., `subprocess.run(user_input, shell=True)`), with different `vulnerableCode` text.
3. Invoke `handle_commit_review_posttooluse` with this commit's `input_data` (mocked `git show` output, mocked `analyze_code_security` return).
4. Assert: `sys.exit(2)` is NOT called (no stderr guidance emitted) and `emit_metrics` shows `vulns_found: 0`/`deduped>0`, demonstrating the new dangerous finding was suppressed solely due to the `(filePath, category)` key match — even though `vulnerableCode` differs and the underlying issue is materially different and more severe than the previously recorded one.
5. Repeat via the Stop hook path (`handle_stop_hook`) reading the same `previous_findings` state, confirming the same suppression occurs there too.

    def _record_findings(state):

        for f in finding_snapshots:
            key = (f["filePath"], f["category"])
