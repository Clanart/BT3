## Analysis

CVE‑2021‑44510 describes a size calculation derived from attacker input that becomes an extremely large/invalid value, leading to a `memset` with an out-of-bounds size and a crash. The closest reachable analog in `blackvul/kaia--022` is the Hardhat `console.log` precompiled contract's decoder, which derives a slice `start` offset directly from raw 256-bit call-data words via `big.Int.Int64()`, whose behavior is undefined/uncontrolled when the value does not fit in an `int64` — giving an attacker full control (including negative values) over a Go slice index used without a lower-bound check. [1](#0-0) 

### Title
Attacker-Controlled Negative/Overflowing Slice Offset in `consoleLog.decode` Causes Panic (Node DoS) - (File: blockchain/vm/contracts.go)

### Summary
The `consoleLog` precompiled contract, reachable by any contract or EOA transaction that calls the fixed console-log precompile address with crafted calldata, decodes `String`/`Bytes` typed console.log arguments by reading a raw 32-byte word from `params` and converting it with `big.NewInt(0).SetBytes(...).Int64()` to obtain a slice `start` offset, then bounds-checks only the sum `start+registerSize`/`start+size+registerSize` against `len(params)` before slicing. [2](#0-1) [3](#0-2) 

### Finding Description
`big.Int.Int64()` on a `SetBytes`-derived non-negative 256-bit value that exceeds `int64` range is documented as producing undefined/truncated results, meaning the resulting `int` value that is later used as `start` is effectively attacker-chosen and can be crafted to be **negative** (e.g., by choosing calldata bytes whose low 64 bits form a negative two's-complement pattern). The code only validates `len(params) < start+registerSize` (and similarly for `size`), which is satisfiable even when `start` is negative because the check does not verify `start >= 0`. The subsequent slice expression `params[start : start+registerSize]` (and the analogous `Bytes` branch) then executes with a negative lower bound, which is an immediate Go runtime panic ("slice bounds out of range"), exactly mirroring the CVE's root cause: a size/offset calculation derived from crafted input becomes an out-of-range value that the memory-access primitive (here, Go's slicing, there `memset`) cannot safely handle, producing a crash. [4](#0-3) [5](#0-4) 

The `size` field has the identical issue independently: it is also derived via `Int64()` from an attacker-supplied word and used in the same unchecked-lower-bound arithmetic, so a crafted negative `size` (or a `start`/`size` combination causing signed integer wraparound in `start+size+registerSize`) can likewise defeat the `len(params) <` guard and trigger an out-of-range slice panic.

### Impact Explanation
Because the `consoleLog` precompile is invoked as part of ordinary EVM execution (any `CALL`/`STATICCALL`/transaction to its fixed address), a single crafted transaction from any unprivileged sender can trigger an unrecovered Go runtime panic during EVM interpretation. In a blockchain node, a panic during transaction/block execution is not a benign, isolated failure — it propagates through consensus-critical execution paths (`EVMInterpreter.Run` → `operation.execute` → precompile `Run`), and there is no `recover()` wrapping this call chain in the paths located in the codebase, meaning it can crash the node process executing the transaction. If this is triggerable identically on all nodes processing the same block/transaction, it can cause a network-wide denial of service, which aligns with the "High" (availability-only) severity of CVE-2021-44510 (CVSS 7.5, `A:H`, no confidentiality/integrity impact). [6](#0-5) 

### Likelihood Explanation
Likelihood is high given: (1) the precompile is reachable by any single transaction with no special privileges, (2) no gas/computation cost is charged for calling it (`GetRequiredGasAndComputationCost` returns `0, 0`), making it essentially free to attempt repeatedly, and (3) the crafted 32-byte word needed to produce a negative `Int64()` result is trivially constructible by any caller who controls calldata. [7](#0-6) 

### Recommendation
Validate `start` (and `size`) are non-negative and within `math.MaxInt` bounds before using them as slice indices; prefer decoding these fields as `uint64`/`uint256` and performing overflow-checked arithmetic (similar to `calcMemSize64`/`SafeAdd` patterns already used elsewhere in the VM package) rather than relying on `big.Int.Int64()`'s undefined truncation behavior. Additionally, wrap precompile execution (or `RunPrecompiledContract`) in a `recover()` to prevent any single malformed input from crashing the node. [8](#0-7) 

### Proof of Concept
1. Craft calldata for the `consoleLog` precompile: 4-byte selector matching a `StringTy` signature (e.g., `0x41304fac`), followed by a single register-size word.
2. Set that word's raw bytes such that `big.NewInt(0).SetBytes(word).Int64()` yields a negative `int64` (this is achievable because `Int64()`'s behavior on out-of-range magnitudes is documented as undefined/truncating, letting the attacker pick the low 64 bits directly).
3. Send a transaction (or internal call) invoking the console-log precompile address with this calldata as part of contract execution.
4. `decode()` computes `start` as the crafted negative value; the check `len(params) < start+registerSize` passes since `start+registerSize` is small/positive; the code then executes `params[start : start+registerSize]`, which panics with "slice bounds out of range" due to the negative lower bound, crashing the executing goroutine/node. // Identical to calcMemSize64, but length is a uint64
func calcMemSize64WithUint(off *uint256.Int, length64 uint64) (uint64, bool) {
	// if length is zero, memsize is always zero, regardless of offset
	if length64 == 0 {
		return 0, false
	}
	// Check that offset doesn't overflow
	offset64, overflow := off.Uint64WithOverflow()
	if overflow {
		return 0, true
	}
	val := offset64 + length64
	// if value < either of it's parts, then it overflowed
	return val, val < offset64
}
