### Title
Ed448 `is_torsion_free` is a tautology — every point passes the subgroup check, so crafted small-order encodings bypass `PrimeGroup` validation - (File: crypto/ed448/src/point.rs)

### Summary
The analog of CVE-2021-4140 (crafted markup escaping a security boundary) is a validation-boundary bypass reachable with crafted bytes: `Point::is_torsion_free` in `crypto/ed448/src/point.rs:295-298` computes `((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()` — i.e. `(-P) + P == identity` — which is true for *every* point on the curve, including the low-order (cofactor-4) torsion points it exists to reject. Consequently `GroupEncoding::from_bytes` (line 316) accepts torsion components, and `Ciphersuite::read_G`/`Ed448::read_G` will return non-prime-order points wherever untrusted Ed448 bytes are parsed.

### Finding Description
Ed448 has cofactor 4, so subgroup membership must be explicitly checked. The check implemented is:

```rust
// crypto/ed448/src/point.rs
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

`Scalar::ZERO - Scalar::ONE` is −1 mod the group order, so this computes `self·(-1) + self`, which is the identity for **all** points — the function unconditionally returns `Choice(1)`. It should multiply by the prime subgroup order `l` (or by the cofactor) instead. `from_bytes` then gates acceptance on `not_negative_zero & point.is_torsion_free()`, so the torsion half of the conjunction is vacuous, and a negative-zero/identity-adjacent or order-2/order-4 point serializes through `read_G` as a valid `Point`. The crate's own `torsion` test only asserts that one specific historical point is *detected* as torsion via a manually constructed `Point`, but since `is_torsion_free` is constant-true, that assertion itself cannot distinguish anything.

### Impact Explanation
Any code path that reads an attacker-supplied Ed448 point via `read_G` (explicitly reachable: `SchnorrSignature::read`, `Commitments::read`, `DLEqProof::read`, `EncryptedMessage::read`, etc., for the `Ed448` ciphersuite) accepts small-order points while all downstream verification math assumes a `PrimeGroup`. This is an incorrect verifier formula: the batched Schnorr verification equation `(-s)·G + 1·R + c·A = 0` is only checked modulo the point's actual order. A public key `A = T` of order 4, paired with `R = T` and `s = 0`, satisfies the equation whenever the challenge `c ≡ 3 (mod 4)` — an attacker who controls the message/nonce being verified can grind `c` with ~2 trials to forge a signature that verifies under `A`, with no discrete-log knowledge. More generally, any verification share, proof element, or group key component accepted via `read_G` can carry a hidden order-4 component, breaking the soundness assumption underpinning all Ed448 proof and signature verification in this codebase.

### Likelihood Explanation
An unprivileged party only needs to submit 57 bytes decoding to an Ed448 torsion point (which `from_bytes` now accepts) plus a forged `(R, s)` pair ground on the challenge modulo 4 — pure public input, off-line work. Whether it is exploitable end-to-end depends on an Ed448 deployment accepting attacker-chosen public keys or proof elements, but within the cryptography itself the check provides zero protection where it claims to enforce prime-order membership.

### Recommendation
Fix `is_torsion_free` to multiply by the prime subgroup order, e.g. `(self * Scalar::from(GROUP_ORDER)).is_identity()` using the Ed448 `l` constant, or equivalently `self.mul_by_cofactor()`/multiply by 4 and confirm the result is *not* identity only where appropriate — the correct check is `self * l == identity`. Additionally, keep rejecting the identity and add regression vectors: decode known order-2 and order-4 Ed448 encodings and assert `from_bytes` returns `CtOption::none`.
