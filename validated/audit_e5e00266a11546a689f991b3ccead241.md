## Title
Partial-commit staging silently re-diffs the working file at apply time, letting positional line-selections drift onto different content than what the user reviewed - (File: `app/src/lib/git/apply.ts`)

## Summary
GitHub Desktop's partial-commit ("stage selected lines") feature stores the user's line selection as **positional indices** into a diff, then re-fetches a **fresh** diff of the working file at staging time and reapplies those same indices to it. Nothing ties a selected index back to the specific content the user actually reviewed. If the file's diff shape changes between the moment the user reviews/selects lines and the moment `git commit`/staging actually runs (e.g. because a build step, formatter, git hook, or other tooling shipped in a cloned/fetched repository rewrites the tracked file), the same index numbers can now point at different lines, so Desktop silently stages/commits content the user never selected. This mirrors the reported Caviar `Pair` bug: a value (`price`, here "what will be committed") is derived from **live, attacker-influenceable state** (`balanceOf`, here "current working-tree diff") instead of the validated snapshot the invariant was checked against (the reserves tracked internally / the diff the user actually reviewed), silently bypassing the guarantee the UI implies.

## Finding Description
When staging a partial file, `stageFiles` calls `applyPatchToIndex` for any file with a `Partial` selection: [1](#0-0) 

`applyPatchToIndex` does **not** use the diff object the user actually looked at in the UI. It re-fetches the working-directory diff from disk right before building the patch: [2](#0-1) 

The patch is then built by walking this *freshly fetched* diff's hunks and asking `file.selection.isSelected(absoluteIndex)` for each line: [3](#0-2) 

`DiffSelection` is a purely positional structure - it has no notion of the underlying line content, only a set of numeric indices that diverge from a default state: [4](#0-3) 

The app itself acknowledges this gap: when a new diff is loaded for a file that already has a selection, the code only prunes indices that are no longer "selectable" (e.g. turned into context lines); it explicitly does **not** verify that a still-selectable index still corresponds to the same line content the user selected: [5](#0-4) 

So the "invariant" that ought to hold - *what the user visually selected is what gets committed* - is enforced only against a diff snapshot in the renderer, while the actual commit-time patch is built against a re-derived, currently-live diff, using indices that were validated against a different (potentially now-stale) diff. This is structurally identical to the Caviar bug: the K-invariant/price is supposed to be enforced against tracked reserves, but the contract instead recomputes the price from the *live* balance, so an attacker who can perturb that live state (direct transfer) can make the derived value diverge from what the invariant checks assumed.

## Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user reviewing a diff, deselecting sensitive/unwanted lines (e.g. a secret accidentally added, a debug statement, or lines they intend to keep local), and clicking "Commit selected" can end up committing/pushing content they never intended, without any warning, if the file's tracked content shifts between the review and the staging call. Because commits and pushes are typically not re-diffed against the exact reviewed selection at apply time, a repository shipping automation that mutates a tracked file mid-session (linters/formatters, build scripts, git hooks that run on checkout/merge, watch-mode tooling committed to the repo) can cause Desktop to stage different hunks than the ones the user picked.

## Likelihood Explanation
Exploitation requires only that tracked file content is modified between the time a partial selection is made in the UI and the time staging/commit executes - a window that is trivially widened by any repo-bundled tooling that touches files on disk (format-on-save configs, watch scripts, hooks) combined with normal user latency while composing a commit message. No local/admin access or pre-existing malware is required beyond the victim opening/using a repository that ships such tooling, which is within the stated valid-impact scope (attacker controls a cloned/fetched repository).

## Recommendation
Do not re-derive the patch from a freshly fetched diff at apply time. Either:
- Pass the exact `IDiff` object that was validated/shown to the user (and whose `selectableLines` the current `DiffSelection` was built against) into `applyPatchToIndex`/`stageFiles`, instead of re-fetching it, or
- If a fresh diff must be fetched for correctness (e.g. because the index was reset), compare a content fingerprint (e.g. hash of hunk headers/line text) of the newly fetched diff against the diff the selection was validated against, and refuse/re-prompt instead of silently reapplying stale positional indices when they diverge.

This mirrors the recommended fix for the Caviar report: stop deriving a security-relevant value from live external state and instead validate it against the tracked/reviewed state before acting on it.

## Proof of Concept
1. Open a repository in Desktop that contains a modified tracked file with multiple hunks, and includes a script/hook (e.g. a `post-checkout`/build watcher bundled with the repo) that will insert/remove a line earlier in that same file shortly after it's opened.
2. In the Changes view, review the diff and select only specific lines to include (deselecting others), as shown in `formatPatch`'s per-line `isSelected` check (`app/src/lib/patch-formatter.ts:143-171`).
3. Before clicking "Commit", let the repo's bundled tooling rewrite the file so the hunk boundaries/line offsets shift.
4. Click "Commit". `stageFiles` → `applyPatchToIndex` re-fetches the diff (`getWorkingDirectoryDiff`, `app/src/lib/git/apply.ts:60`) and reuses the old `DiffSelection`'s numeric indices against the new hunks.
5. The resulting commit contains different lines than what was visually selected in step 2, with no warning presented to the user - this can be confirmed by diffing `HEAD` after commit against the selection the user made.
