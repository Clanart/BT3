## Title
`convert_to_balance` fails to scale up amounts when the local asset has more decimals than the ERC20 source, minting near-zero tokens on `on_accept`/`on_timeout` - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` in the `hyper-fungible-token` pallet only ever divides the incoming `U256` ERC20 amount, using `erc_decimals.saturating_sub(local_decimals)` as the exponent. When `local_decimals > erc_decimals`, `saturating_sub` clamps to `0`, so the divisor becomes `10^0 = 1` — the function performs no scaling at all instead of the required upscale by `10^(local_decimals - erc_decimals)`. This mirrors the code-423n4 sfrxEth bug: an arithmetic operation applied in the wrong direction (division that should have been multiplication), silently mispricing an asset conversion. [1](#0-0) 

### Finding Description
`convert_to_balance` is documented to "divide by `10^(erc_decimals - local_decimals)` to scale down from ERC20 precision," which is only correct for the case `erc_decimals >= local_decimals`. The complementary function, `convert_to_erc20`, correctly multiplies by `10^(erc_decimals - local_decimals)` for the opposite direction, but `convert_to_balance` has no corresponding multiply branch:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
``` [2](#0-1) 

This function is called on both the `on_accept` (inbound mint/transfer) and `on_timeout` (refund) paths of the ISMP module handler, using `erc_decimals` read from the governance-configured `Precisions` map and `local_decimals` from the local asset's metadata (or `T::Decimals` for the native asset):

```rust
let decimals = if local_asset_id == T::NativeAssetId::get() {
    T::Decimals::get()
} else {
    <T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(local_asset_id.clone())
};
let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), source)
    .ok_or(HftError::DecimalsNotConfigured(source))?;
let amount = convert_to_balance::<...>(
    U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
    erc_decimals,
    decimals,
)
``` [3](#0-2) 

If a remote ERC20 is registered with fewer decimals than the corresponding local Substrate asset (e.g. a 6-decimal USDC-style token bridged into an 18-decimal local asset, or bridged into the native asset if `T::Decimals` is 18), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the divisor is `1` and the raw ERC20 integer (e.g. `1_000_000` for 1 USDC) is minted/transferred as-is, instead of being scaled up to `1_000_000 * 10^12` local units. The recipient receives `10^12` times fewer tokens than deposited on the source chain. Existing guards (`Precisions` allowlist check, source-contract authentication via `ContractToAsset`) only verify that the mapping is configured — they do nothing to detect or reject a decimals mismatch that triggers this scaling failure.

### Impact Explanation
This is a real fund-loss/mis-mint bug on a live bridging pallet: value that a user legitimately locked/burned on the source EVM chain is credited on Hyperbridge at a fraction (potentially 10^12 or more, depending on configured decimals) of its correct amount, on both the inbound receive path (`on_accept`) and the timeout refund path (`on_timeout`). This falls squarely within the bounty's "transaction manipulation" / "loss of funds" / "wrong beneficiary amount" categories since it moves funds to the rightful beneficiary but in the wrong (drastically understated) amount, with no attacker action required — it fires on every legitimate transfer whenever `local_decimals > erc_decimals` for the registered pair.

### Likelihood Explanation
This does not require a malicious actor, relayer, or governance compromise — it triggers deterministically for any correctly-functioning cross-chain transfer whenever the registered local asset decimals exceed the remote ERC20's decimals (a configuration that is entirely plausible, e.g. bridging a 6-decimal stablecoin into an 18-decimal local asset or the chain's 18-decimal native token). Whether this is currently reachable in production depends on the specific decimals values configured in `Precisions` for deployed asset pairs, which I could not fully verify from the indexed code (governance-set storage values are not visible in this search). The vulnerability is code-level certain; live exploitability depends on current on-chain configuration that I was not able to confirm.

### Recommendation
Fix `convert_to_balance` to branch on the sign of `erc_decimals - local_decimals`, symmetric to `convert_to_erc20`:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
Add a unit test exercising `local_decimals > erc_decimals` (e.g. `erc_decimals = 6`, `local_decimals = 18`) to lock in correct round-trip behavior with `convert_to_erc20`.

### Proof of Concept
1. Governance configures a remote ERC20 with `erc_decimals = 6` (e.g. USDC) mapped to a local asset (or the native asset) with `local_decimals = 18`, via whatever admin call populates `Precisions::<T>::insert(local_asset_id, source, 6)`.
2. A user on the EVM side sends `1_000_000` (1.0 USDC in 6-decimal units) via the HFT bridge contract; this arrives as `message.amount = 1_000_000` in the `PostRequest` body.
3. `on_accept` calls `convert_to_balance::<Balance>(U256::from(1_000_000), erc_decimals=6, decimals=18)`.
4. Inside, `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18u8) = 0`, so divisor `= 10^0 = 1`, and `amount = 1_000_000` is minted/transferred in 18-decimal local units — i.e. `0.000000000001` of a full local token instead of the correct `1_000_000 * 10^12 = 1_000_000_000_000_000_000` (1.0 full local token).
5. The beneficiary receives roughly one-trillionth of the value they deposited; the same shortfall applies to `on_timeout` refunds. [2](#0-1) [4](#0-3) [5](#0-4)
