### Title
Self-referral via Sybil wallets allows fabricating referral rewards - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.useCode()` only blocks a user from using their own code (`codeOwners[_code] == msg.sender`), but does nothing to prevent an attacker from registering a code with one wallet and using it from a second, attacker-controlled wallet. Every time the second wallet claims MGP rewards through `MasterMagpie`, `trigger()` mints extra referral rewards to both the "referrer" and "referee" records, both ultimately controlled by the same attacker, letting them siphon protocol-funded referral incentives with no genuine third-party referral activity.

### Finding Description
`registerCode` lets any address claim an arbitrary unused `bytes32 _code` and become `codeOwners[_code]`: [1](#0-0) 

`useCode` only rejects the case where the caller is the code owner itself; it has no way (and cannot have one, on-chain) to detect that the caller is a second address controlled by the same owner: [2](#0-1) 

When the referred wallet (wallet2) claims rewards through `MasterMagpie.multiClaim`, the accumulated MGP reward it legitimately earned from its own stake (`totalReward`) is first paid out to it via `_sendMGPForVlMGPPool`/`_sendMGP`/`_sendVlMGPFor`, and then `IReferralStorage(referral).trigger(_user, totalReward)` is invoked on top of that: [3](#0-2) 

Inside `trigger`, the referrer (wallet1, `myReferer[wallet2]`) and the referee (wallet2) both get **additional** `rewardAmount` credited, computed as percentages of `totalReward`, on top of what wallet2 already received directly: [4](#0-3) 

This `rewardAmount` is claimable via `claimReward()`, which transfers real MGP tokens out of the `ReferralStorage` contract's own balance (a pool the protocol must fund separately for referral incentives) to the caller: [5](#0-4) 

Because both the referrer and referee are attacker-controlled, the attacker collects `refererAmount + refereeAmount` in MGP for every claim wallet2 makes — bonus tokens that were meant to reward genuine external referral growth — without bringing in any actual third-party user or TVL. The only defense in the code, `codeOwners[_code] == msg.sender`, is trivially bypassed by using two separate EOAs.

### Impact Explanation
This is a theft of protocol-funded referral incentives (unclaimed yield): the attacker extracts real MGP from the `ReferralStorage` contract's reward budget purely by fabricating referral volume between sock-puppet wallets, matching the Immunefi "theft of unclaimed yield" impact class. Every staking/claim cycle by the attacker's own second wallet generates extra, illegitimate MGP payable to the first wallet, diluting the pool of MGP set aside to reward genuine referrers.

### Likelihood Explanation
- Preconditions: only two attacker-controlled EOAs, no privileged role required.
- Capital needed: only whatever the attacker already intends to stake to earn MGP rewards through `MasterMagpie`; the referral bonus is pure upside on top.
- Feasibility/repeatability: the exploit sequence (`registerCode` → `useCode` → stake/claim loop) can be repeated indefinitely with any number of claims, and additional Sybil wallets can be created cheaply to scale the extraction.

### Recommendation
Self-referral via Sybil addresses is a structural limitation of any purely on-chain, code-based referral system and cannot be fully solved on-chain without off-chain identity/KYC or economic disincentives (e.g., requiring the referee to bring net-new, non-trivial locked value before referral rewards accrue, capping total referral payout per code relative to referee's own stake size/duration, or requiring a bond/vesting period for both referrer and referee rewards to filter out short-lived Sybil pairs). At minimum, consider adding rate limits or minimum stake-duration/size thresholds before `trigger()` credits rewards, and monitor/flag codes whose referee wallets share funding sources.

### Proof of Concept
Foundry test outline:
1. Deploy `ReferralStorage`, `MasterMagpie`, `MGP`, `vlMGP` per existing test harness; fund `ReferralStorage` with a MGP incentive balance as the protocol would in production.
2. `vm.prank(wallet1); referralStorage.registerCode(codeA);`
3. `vm.prank(wallet2); referralStorage.useCode(codeA);`
4. `wallet2` stakes MGP into `MasterMagpie` and lets rewards accrue, then calls `multiClaim` (or equivalent) which triggers `IReferralStorage.trigger(wallet2, totalReward)`.
5. Assert `referralStorage.userInfos(wallet1).rewardAmount` increased by `refererAmount = totalReward * refererPercentage / DENOMINATOR` even though wallet1 provided no independent stake/TVL.
6. Have `wallet1` call `claimReward()` and assert MGP balance of wallet1 increases from the `ReferralStorage` contract's balance, confirming real token extraction with no genuine third-party referral source.

        UserInfo storage refereeInfo = userInfos[_referee];

        if (_referer == address(0))
            return;

        uint256 boostesd = _calBoosted(_referer);

        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
