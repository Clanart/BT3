### Title
Cached preprocess seed is reused across every signing attempt for a context, causing deterministic FROST nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the minipool bug where a once-set timestamp (`rewardsStartTime`) was never reset on minipool re-creation — letting a repeated action skip a required freshness check — Serai's signing protocol caches a FROST preprocess seed once per `context` and *never* deletes or rotates it. Every `share` call for the same context deterministically regenerates the *same* nonces via `AlgorithmMachine::seeded_preprocess` (ChaCha20Rng seeded by the cached 32-byte seed). Two signed messages under one context therefore reuse identical nonces, allowing anyone who observes the two signature shares to algebraically recover the signer's secret share — the exact catastrophic consequence the `CachedPreprocess` documentation warns about.

### Finding Description
In `SigningProtocol::preprocess_internal`, the preprocess is stored under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` only `if ...get(...).is_none()`, and is read back on every subsequent call for the same context — it is never cleared after `share_internal` consumes it. [1](#0-0) 

`share_internal` rebuilds the machine via `self.preprocess_internal(participants).0` each time it is invoked, so repeated share generation under one context reuses the same seed. [2](#0-1) 

`AlgorithmMachine::seeded_preprocess` derives both nonces and the addendum purely from the seed (`ChaCha20Rng::from_seed(*seed.0)`), making reuse fully deterministic — identical commitments and identical secret nonces for every signing session. [3](#0-2) 

The share returned by `sign` is `share = nonce_actual + λ·challenge·secret_share`, where `nonce_actual = base + rho·nonce` is fixed per seed while `challenge` varies with `msg`. With two shares `(s1, s2)` for messages `(m1, m2)` and known `λ`, the secret share is `λ·secret = (s1 - s2) / (c1 - c2)`. [4](#0-3) 

The library itself documents that reuse "will enable third-party recovery of your private key share," yet the only production consumer caches per context and never invalidates. [5](#0-4) 

### Impact Explanation
Recovery of a validator's threshold secret share. Observing any two shares signed under the same context (the context is derived from the tributary spec/set, not per message, so every signing job for a validator set shares one seed) yields the private key share via linear equations on the reused nonce. Combined across enough victims, this can collapse the threshold security of the multisig, enabling signature forgery and theft of funds controlled by the group key.

### Likelihood Explanation
Certain upon any second signature under a reused context. The cache is only written when empty (`CachedPreprocesses::get(...).is_none()`), persists in the DB across restarts, and `share_internal` performs no invalidation — so the second, third, and Nth signing attempts for that context all emit shares over identical nonces. An unprivileged party able to cause two distinct messages to be signed for the same validator set (e.g., retry of a signing attempt with altered transaction data) obtains the secret share from the two published shares.

### Recommendation
Delete or overwrite `CachedPreprocesses` for the context the first time `share_internal` produces a share (one-time-use semantics), and/or derive the effective seed as `H(cached_seed || msg || session_nonce)` so that distinct messages cannot share nonces. Alternatively, mix fresh `OsRng` entropy into `seeded_preprocess` at `from_cache` time in `crypto/frost/src/sign.rs` so a cached seed cannot deterministically regenerate identical commitments.

### Proof of Concept
1. Under context C, call `share_internal` for message `m1`: `preprocess_internal` loads seed S, `seeded_preprocess` produces nonces `(d, e)`; emitted share `s1 = d + ρ1·e + λ·c1·x`.
2. Trigger a second `share_internal` for the same context C with message `m2` (e.g., a retried/modified signing job). The cache still holds S → identical `(d, e)` → `s2 = d + ρ2·e + λ·c2·x`.
3. Since `ρ` is public (computed from `hash_binding_factor` over the transcript) and `λ` (Lagrange coefficient) is public, solve the 2×2 linear system in `d + ρ·e` terms: `(s1 − s2) = λ·x·(c1 − c2)` after subtracting the known nonce contribution — more precisely with identical nonce vector `k`, `s1 − s2 = λ·x·(c1 − c2)`, so `x = (s1 − s2)·(λ·(c1 − c2))⁻¹ mod q`.
4. The signer's secret share `x` is recovered from two publicly broadcast signature shares.
