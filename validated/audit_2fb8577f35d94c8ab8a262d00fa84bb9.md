## Finding: Unbounded object-ownership cycle causes infinite loop in `root_owner()`, DoSing code-publish owner recording and lazy module self-init

### Title
Missing nesting-depth guard in `object::root_owner()` allows an ownership cycle (creatable via two ordinary `transfer` calls) to permanently hang `code::publish_package`'s owner recording and `init::assert_may_self_initialize` - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
`aptos_framework::object::root_owner()` walks the object ownership chain with **no depth bound**, unlike its sibling functions `owns()` and `verify_ungated_and_descendant()` in the same module, which both explicitly cap traversal at `MAXIMUM_OBJECT_NESTING`. `root_owner()` is exactly the function the new lazy-module-initialization/publish-ownership-tracking mechanism relies on (`code::publish_package` and `init::assert_may_self_initialize`) to decide who legitimately controls a code object. Because `object::transfer`'s cycle check (`verify_ungated_and_descendant`) only verifies that the *destination* is transitively owned by the caller — it never checks that the object being moved is not itself an ancestor of the destination — two ordinary, individually-authorized transfers by the same owner can create a 2-object ownership cycle. Once a code-hosting object is (or becomes) part of such a cycle, any call into `root_owner()` on it loops forever.

### Finding Description
`code::publish_package` records the object's transitive root owner at every (re)publish for later self-init gating: [1](#0-0) 

That value is later re-derived and compared on every lazy self-init: [2](#0-1) 

Both paths call `object::root_owner()`: [3](#0-2) 

Notice this loop has **no** `MAXIMUM_OBJECT_NESTING` bound, whereas the structurally identical traversal in `owns()` does: [4](#0-3) 

and the transfer-time cycle guard `verify_ungated_and_descendant()` also enforces the same bound, but only checks that the caller (`owner`) is an ancestor of `destination` — it never checks that the object being moved is not itself an ancestor of `destination`: [5](#0-4) 

**Exploit construction (2 ordinary, individually-authorized transfers by the same signer U):**
1. `U` owns object `A` directly, and owns object `B` directly.
2. `U` calls `transfer_to_object(U, B, A)`. `verify_ungated_and_descendant(U, A)` succeeds because `A.owner == U`. Now `B.owner = A`.
3. `U` calls `transfer_to_object(U, A, B)`. `verify_ungated_and_descendant(U, B)` walks `B.owner (=A) -> A.owner (=U)` and succeeds because `U` is reached within the depth bound. Now `A.owner = B`.

Result: `A.owner == B` and `B.owner == A` — a genuine 2-object cycle with no path to any account address, created entirely through legitimate, authorized transfer calls.

If either `A` or `B` (or an address that is transitively parented by them) is a code-deployment object with `OBJECT_CODE_DEPLOYMENT`/`LAZY_MODULE_INITIALIZATION` enabled, then:
- `code::publish_package`'s owner-recording branch (`object::address_to_object<ObjectCore>(addr).root_owner()`) will spin forever on republish/upgrade attempts targeting that object.
- Every call to `init::internal_maybe_initialize` for a module on that object will spin forever in `assert_may_self_initialize` via `recorded_deploy_owner`/`root_owner()`.

### Impact Explanation
This reaches "module-init ... native validation ... reaches protected state mutation" directly in scope of the Publish Impact Gate: the write path for publishing/upgrading code to an object, and the module self-initialization entry point, both become permanently unusable (unbounded loop until gas exhaustion) for any code object caught in such a cycle. Any legitimate owner or third party who wants to publish, upgrade, or trigger lazy self-init on a code object placed into (or made to reference) such a cycle is denied service — the transaction can never complete successfully, only abort on out-of-gas, and the underlying state (`InitializationState`, `PackageRegistry`) can become permanently unreachable through the intended entry points that depend on `root_owner()`. This is a code-safety invariant break in the new lazy-module-initialization ownership-tracking feature, not a generic node/network DoS.

### Likelihood Explanation
The cycle is created using only two ordinary `object::transfer_to_object` calls, both fully authorized under the existing `verify_ungated_and_descendant` check (no privilege escalation needed — the attacker is simply the legitimate owner of both objects at the time of each transfer). No feature flags beyond `OBJECT_CODE_DEPLOYMENT`/`LAZY_MODULE_INITIALIZATION` (both on by default per `types/src/on_chain_config/aptos_features.rs`) are required to trigger the impact. The only uncertainty is whether some other invariant elsewhere in the framework independently prevents such two-hop cycles from ever being constructible in practice (e.g., additional restrictions on `ObjectCore` not visible in the excerpts reviewed) — this was not fully verifiable from the available code, and should be confirmed with a runtime/unit test before treating this as fully proven.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING`-bounded loop guard used in `owns()`/`verify_ungated_and_descendant()` to `root_owner()`, failing with `EMAXIMUM_NESTING` instead of looping unboundedly. Additionally, harden `verify_ungated_and_descendant()` (or `transfer`) to reject transfers where the object being moved is itself found while walking up the destination's ownership chain, closing the two-hop (and N-hop) cycle-creation path at its source.

### Proof of Concept
```
// Pseudocode using aptos_framework::object
let u = create_signer_for_test(@0xCAFE);
let a_ref = object::create_object(@0xCAFE);   // A owned by U
let b_ref = object::create_object(@0xCAFE);   // B owned by U
let a = object::object_from_constructor_ref<ObjectCore>(&a_ref);
let b = object::object_from_constructor_ref<ObjectCore>(&b_ref);

object::transfer_to_object(&u, b, a); // B.owner = A  (verify_ungated_and_descendant(U, A) passes: A.owner == U)
object::transfer_to_object(&u, a, b); // A.owner = B  (verify_ungated_and_descendant(U, B) passes: B.owner(A) -> A.owner(U) == U)

// Now A.owner == B and B.owner == A: a cycle.
// Calling object::root_owner(a) or object::root_owner(b) never terminates.
// If A (or B) hosts published code with LAZY_MODULE_INITIALIZATION enabled,
// code::publish_package's `object::address_to_object<ObjectCore>(addr).root_owner()`
// call, and init::assert_may_self_initialize's equivalent call, will loop indefinitely.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    /// Return true if the provided address has indirect or direct ownership of the provided object.

    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
