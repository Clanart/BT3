## Title
Missing `request.from` validation in `BandwidthManager.onAccept` allows any hyperbridge-chain module to forge governance actions - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.onAccept` only validates that the incoming `PostRequest.source` equals `IDispatcher(_host).hyperbridge()` (the *chain* identifier of the relay chain), but never checks `PostRequest.from` against `PALLET_BANDWIDTH_MODULE_ID`. Since `source` binds only to the origin *chain*, not the origin *module/pallet* on that chain, any module on the hyperbridge chain that can dispatch a `PostRequest` with `to = address(BandwidthManager)` can impersonate `pallet-bandwidth` and execute `SetTiers`/`Withdraw` governance actions.

### Finding Description
`onAccept` performs exactly one authenticity check: [1](#0-0) 

This checks `request.source` — the chain id of the sender — but never checks `request.from`, which is the module identifier of the specific dispatching pallet on that chain. The contract even documents that `PALLET_BANDWIDTH_MODULE_ID = bytes("BWMARKET")` is meant to bind the expected sender module: [2](#0-1) 

...but this constant is never referenced anywhere in `onAccept`'s validation logic — it is dead code from an authentication standpoint (only used as the `to` field when *dispatching outbound* purchase messages, not for validating inbound ones): [3](#0-2) 

This contrasts with the sibling app `ExtrinsicIntents.sol`, which does check `request.from` to bind the specific source module in addition to `source`, confirming that per-module binding is the expected security pattern in this codebase and that its absence here is an oversight, not a deliberate design choice: [4](#0-3) 

Because `onAccept` is gated only by `onlyHost` and the chain-level `source` check, any pallet on the hyperbridge relay chain (not just `pallet-bandwidth`) that can dispatch a `POST` request with `to = address(BandwidthManager)` will have its message accepted as authentic governance. The forged body can:
- Overwrite `tierPrice[tier]` via a forged `SetTiers` payload, corrupting the pricing storefront.
- Trigger a forged `Withdraw`, draining the contract's ERC20/native token treasury to an attacker-chosen `beneficiary`.

### Impact Explanation
This breaks the "Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow" pivot. A forged `Withdraw` message directly steals funds held by `BandwidthManager` (fee tokens collected from `purchase()` calls, and any native token balance), and a forged `SetTiers` corrupts pricing state used by all future purchasers. This is a state-machine/module-binding bypass fitting "false proof/state acceptance" and "unauthorized transaction or execution."

### Likelihood Explanation
Exploitability depends on whether an untrusted/attacker-influenced module on the hyperbridge relay chain can dispatch a `POST` request with an arbitrary `to` address (i.e., addressed to `BandwidthManager` on the destination EVM chain) while consensus/state proofs correctly attest that the request truly originated from the hyperbridge chain. If the relay-chain message-routing layer restricts which pallets can freely choose arbitrary `to`/destination targets, this may be mitigated at the runtime layer rather than in the EVM contract. However, defense-in-depth via `from` binding is the pattern used elsewhere in this codebase, and its absence here is a genuine deviation that removes a layer of authentication that the contract's own naming/documentation implies should exist.

### Recommendation
Add an explicit check binding `request.from` to `PALLET_BANDWIDTH_MODULE_ID` in `onAccept`, mirroring the pattern used in `ExtrinsicIntents.sol`:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge()) || !request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) {
    revert UnauthorizedAction();
}
```

### Proof of Concept
1. Attacker (or any non-`pallet-bandwidth` module on the hyperbridge chain) crafts a `PostRequest` with:
   - `source = IDispatcher(_host).hyperbridge()` (correct chain id)
   - `to = address(BandwidthManager)`
   - `from = <arbitrary bytes, not "BWMARKET">`
   - `body = abi.encode(OnAcceptActions.SetTiers) || abi.encode(Tier[])` with attacker-chosen `tier`/`price`
2. This request is routed through the host to `BandwidthManager.onAccept` (as `IncomingPostRequest`).
3. `onAccept` checks only `request.source.equals(hyperbridge)`, which passes; `request.from` is never inspected.
4. `tierPrice[tier]` is overwritten with the attacker's value (or, using the `Withdraw` action, funds are transferred to an attacker-chosen `beneficiary`), despite the message never having originated from the real `pallet-bandwidth` module.

Note: I could not fully verify within the indexed code whether the relay-chain/runtime message-dispatch layer independently restricts arbitrary modules from setting `to`/destination freely (this would require inspecting the Substrate `pallet-ismp`/dispatch-routing logic, which was not available in the search results reviewed). The EVM-side contract code, however, unambiguously omits the `from` check that the codebase's own conventions (see `ExtrinsicIntents.sol`) and documentation (naming of `PALLET_BANDWIDTH_MODULE_ID`) indicate should be present.
