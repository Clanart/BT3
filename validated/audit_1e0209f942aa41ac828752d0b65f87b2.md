### Title
Bank precompile `send` lacks the anti-delegatecall guard that every other identity-authorizing precompile enforces, enabling caller-identity spoofing - ([File: precompiles/bank/bank.go])

### Summary
`dirty_sock` escalated privileges because a socket API (snapd) trusted a client-supplied identity token without verifying it actually reflected the calling process's real credentials. The sei-chain analog is the EVM bank precompile's `send` method, which authorizes a native-token transfer purely by checking that the passed-in `caller` value equals the registered ERC20 pointer contract for the denom — but, unlike every other stateful precompile in the codebase, it never verifies that `caller` actually corresponds to the contract that is really invoking it (no anti-delegatecall check).

### Finding Description
`precompiles/bank/bank.go`'s `send` performs its entire authorization on the `caller` parameter: [1](#0-0) 
It requires `pointer.Cmp(caller) == 0`, i.e. the EVM `msg.sender`-equivalent must equal the registered native ERC20 pointer contract address for that denom, then it executes a `banktypes.MsgSend` from an arbitrary `senderSeiAddr` (`args[0]`) to an arbitrary `receiverSeiAddr` (`args[1]`) for an attacker-chosen amount: [2](#0-1) 

Every other precompile in this codebase that performs an equivalent caller-identity based authorization explicitly guards against delegatecall spoofing at the top of `Execute`/`Run`, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

These checks exist precisely because, under `DELEGATECALL`, the EVM preserves the *original* caller identity (`CALLER()`/msg.sender) while the *executing* contract address changes to the delegatee. That means a malicious contract `M` that is `DELEGATECALL`ed into by a legitimate contract `P` executes with `callingContract == M` but `caller == P`'s own upstream caller preserved through the frame — the classic "who is really talking to me" identity-spoofing primitive, structurally identical to dirty_sock trusting an unauthenticated identity claim over a socket.

A repo-wide search confirms `precompiles/bank/bank.go` does contain exactly one `"cannot delegatecall"` string, but the excerpted `send` function body (lines 198-249, and specifically the authorization block at 213-216) contains no such check — the guard, if present at all, is scoped to `sendNative`, not to `send`. `send`'s own `Execute` dispatcher likewise applies no `caller.Cmp(callingContract)` gate before routing to `send`: [7](#0-6) 

Because the ERC20 native pointer contract (the only account meant to legitimately hold `caller == pointer`) is an ordinary EVM contract that a user can drive through arbitrary call sequences (e.g. `transfer`/`transferFrom` logic, or any code path where the pointer contract calls out to a user-specified address, such as an approve/allowance callback or reentry point), any sequence in which the pointer contract issues a `CALL` to an attacker-supplied contract, which then itself performs a `DELEGATECALL` to the bank precompile's `send` selector, would present the precompile with `caller == pointer` (satisfying the sole authorization check) while the attacker's contract fully controls the call data — including `senderSeiAddr`, `receiverSeiAddr`, `denom`, and `amount`.

### Impact Explanation
If reachable, this allows unauthorized transfer of native `usei`/bank-module coins from an arbitrary Sei account to an attacker-chosen account, i.e. direct fund theft/unauthorized transfer via a precompile — matching the accepted "unauthorized transfer via precompile" impact class. This would not require compromising any private key or governance path; it only requires driving the legitimate pointer contract into calling attacker-controlled code, then delegatecalling into the bank precompile.

### Likelihood Explanation
Confidence is **moderate, not proven**: I confirmed the structural anomaly (the `send` authorization path and its `Execute` dispatcher lack the `caller.Cmp(callingContract)` guard universally applied elsewhere in the codebase) via direct code reading, but I was unable to fully verify, within the remaining budget, (a) the exact line where `"cannot delegatecall"` appears in `bank.go` (to confirm it truly excludes `send`) and (b) whether the deployed ERC20 native pointer contract bytecode (`native.GetBin()`, referenced in `precompiles/pointer/...`) contains any code path that performs an external `CALL` to an attacker-controllable address during `transfer`/`transferFrom`, which is the precondition needed to make `caller == pointer` while attacker code executes. Without that second confirmation, the exploit chain is architecturally plausible but not fully proven end-to-end from the evidence gathered.

### Recommendation
Add the same `if caller.Cmp(callingContract) != 0 { return nil, 0, errors.New("cannot delegatecall bank") }` guard to the bank precompile's `Execute` dispatcher (or specifically to the `send` method) that is already applied in `precompiles/distribution`, `precompiles/gov`, `precompiles/staking`, and `precompiles/pointer`, so that `send`'s pointer-identity check cannot be satisfied via a delegatecall-preserved caller value. Additionally, audit the native ERC20 pointer contract bytecode/template for any external calls to non-fixed addresses during transfer flows that could be leveraged as the first hop of this chain.

### Proof of Concept
Conceptual (not fully verified against the deployed pointer bytecode):
1. Attacker identifies denom `X` with registered native pointer contract `P` at address `0xP1` (`evmKeeper.GetERC20NativePointer`).
2. Attacker deploys malicious contract `M` and arranges for `P` to issue a `CALL` to `M` during some normal user-triggered operation on `P` (e.g., a transfer/callback code path in the pointer contract).
3. Inside `M`, since `M` was `CALL`ed by `P`, `CALLER()` as seen going forward is `P`. `M` then issues `DELEGATECALL(bankPrecompileAddress, sendCalldata)` where `sendCalldata` encodes `send(senderSeiAddr=<victim>, receiverSeiAddr=<attacker>, denom=X, amount=<victim balance>)`.
4. The bank precompile's `send` sees `caller == P` (satisfying `pointer.Cmp(caller) == 0`) and `callingContract == M`, and, absent the missing guard, executes `MsgSend` from the victim to the attacker for denom `X`. [8](#0-7)

```go
func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		bz, err := method.Outputs.Pack(true)
		return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, 0, err
	}

	msg := &banktypes.MsgSend{
		FromAddress: senderSeiAddr.String(),
		ToAddress:   receiverSeiAddr.String(),
		Amount:      sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount))),
	}

	err = msg.ValidateBasic()
	if err != nil {
		return nil, 0, err
	}

	if _, err = p.bankMsgServer.Send(sdk.WrapSDKContext(ctx), msg); err != nil {
		return nil, 0, err
	}

	bz, err := method.Outputs.Pack(true)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
```
