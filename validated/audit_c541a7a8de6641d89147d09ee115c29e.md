### Title
Path-containment guard `resolveWithin()` uses naive string-prefix comparison, allowing escape into sibling directories - ([File: app/src/lib/path.ts])

### Summary
The report's underlying bug class is a broken boundary/invariant check in security-critical comparison logic that produces an incorrect accept/reject decision (ECDSA384 mishandled point-arithmetic edge cases, causing valid signatures to be wrongly rejected). The Desktop analog is the reverse-polarity version of the same defect class: `_resolveWithin()` in `app/src/lib/path.ts` is the guard that decides whether a resolved path is contained inside a trusted root, and it uses a naive `String.prototype.startsWith` comparison without a path-separator boundary check, causing it to *wrongly accept* paths that merely share a string prefix with the root but live in a completely different, sibling directory.

### Finding Description
`_resolveWithin` computes the final decision as: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`startsWith` treats `realRoot` as an arbitrary character prefix, not a path component boundary. If `realRoot` is `/Users/victim/Documents/GitHub/repo`, then `/Users/victim/Documents/GitHub/repo-2/secret.txt` **also** satisfies `startsWith(realRoot)`, even though `repo-2` is a different directory entirely. The invariant the function is supposed to enforce — "the resolved path must be at or under the root" — is broken exactly the same way the ECDSA384 library broke its "point is on curve / satisfies verification equation" invariant: an edge case in the comparison (prefix vs. exact-boundary) is mishandled, causing the guard to give the wrong answer for a specific input shape.

This directly matters because GitHub Desktop routinely creates sibling directories with numeric suffixes when repo names collide during clone (e.g. `repo`, `repo-1`, `repo-2`), so the "shares-a-prefix-but-is-a-different-directory" scenario is not a contrived edge case — it's a normal, expected directory layout for Desktop users who have cloned repos with colliding names or forks of the same project.

The guard is consumed by attacker-reachable, unprivileged paths:
- `app/src/ui/dispatcher/dispatcher.ts`, `openRepositoryFromUrl`, handling the `filepath` parameter of a GitHub Desktop deep link (`x-github-client://openRepo?...&filepath=...`). It only rejects absolute paths via `isAbsolute(filepath)`; a relative traversal payload (`../repo-1/id_rsa`) is not rejected by that check and is passed straight into `resolveWithin`. [2](#0-1) 
- `app/src/lib/copilot-conflict-context.ts`, which calls `resolveWithin(workingDirectory, file.path)` on conflicted file paths before reading file contents for the Copilot conflict-resolution feature. [3](#0-2) 

Existing tests do not cover this specific boundary condition — they check `..` traversal without a matching back-in path, symlink escapes, and null bytes, but never a sibling directory whose name is a superset string of the root's basename: [4](#0-3) 

### Impact Explanation
If a user clicks a crafted GitHub Desktop deep link (`x-github-client://openRepo?url=...&filepath=../repo-2/.ssh/id_rsa`) that targets a repository located next to another sibling directory sharing a name prefix (a common Desktop-created layout), the `filepath` guard incorrectly accepts the traversal and `shell.showItemInFolder(resolved)` is invoked on a file **outside** the intended repository — this satisfies the "file read/write outside the repo via a link the user clicks" impact criterion. The Copilot conflict-context code path could similarly be used to leak the contents of files outside the working directory into an AI-context payload if conflict file paths can be influenced through a crafted merge/fetch, though this second path is less certain because Git generally restricts tracked path components from containing `..`.

### Likelihood Explanation
Moderate. Exploitation requires: (1) the victim to click a maliciously crafted `x-github-client://` deep link, and (2) a sibling directory that shares the root repository's name as a string prefix to exist at the parent folder level — which happens routinely because Desktop auto-suffixes colliding clone directory names (`repo`, `repo-1`, `repo-2`, etc.), and because users commonly keep multiple related repos/forks under one parent folder with similar names. No admin rights, local access, or prior malware are required — only a single click on an untrusted link, which matches the "attacker controls...a link or deep link the user clicks" valid-impact category.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to enforce a real path-boundary comparison instead of a raw string prefix check, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory whose name extends the root's basename (e.g. root `repo`, target `repo-2/file`) is rejected. Also consider tightening `openRepositoryFromUrl` in `dispatcher.ts` to canonicalize/validate `filepath` independent of the shared root-detection helper, since it is the primary attacker-reachable consumer.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import * as fs from 'fs/promises'
import * as path from 'path'
import * as os from 'os'

// Setup: sibling directories sharing a name prefix, as Desktop creates for
// name-colliding clones (repo, repo-1, repo-2, ...)
const parent = await fs.mkdtemp(path.join(os.tmpdir(), 'gh-desktop-'))
const root = path.join(parent, 'repo')
const sibling = path.join(parent, 'repo-2')
await fs.mkdir(root)
await fs.mkdir(sibling)
await fs.writeFile(path.join(sibling, 'secret.txt'), 'private data')

// Simulates dispatcher.ts openRepositoryFromUrl's filepath handling:
// isAbsolute('../repo-2/secret.txt') === false, so it is not rejected there.
const resolved = await resolveWithin(root, '../repo-2/secret.txt')

console.log(resolved)
// BUG: resolved !== null even though it points to `${parent}/repo-2/secret.txt`,
// which is OUTSIDE `root` (`${parent}/repo`). The `startsWith` check in
// _resolveWithin passes because "repo-2" is a string-prefix superset of "repo".
```
