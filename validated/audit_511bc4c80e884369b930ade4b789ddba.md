### Title
Payout OP_RETURN operator-credit is unauthenticated, allowing a payout to be re-attributed to an operator who never funded it - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The payout transaction that fronts a user's withdrawal is only partially signed by the user (`SIGHASH_SINGLE|ANYONECANPAY`, covering just input[0] and output[0]). The `OP_RETURN` output that records *which operator fronted the payout* (`operator_xonly_pk`), and any additional inputs that actually fund the payment, are outside the signed scope. This is exactly the "AllowedCalldataEnforcer must only be used for static types" bug class translated to this protocol: a value that is intended to be bound to the whole transaction (who really paid) is only bound to a small fixed slice of it (input 0 / output 0), and everything else — including the reimbursement-credit field — remains freely substitutable by any third party who observes the transaction before it confirms.

### Finding Description
`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout transaction with:
- input[0]: the user's withdrawal UTXO, spent via `SpendPath::KeySpend`
- output[0]: the user's requested payout (`output_txout`)
- an anchor output
- an `OP_RETURN` output containing `operator_xonly_pk.serialize()` — the value later used to decide who gets reimbursed [1](#0-0) 

The user's signature is required to be `TapSighashType::SinglePlusAnyoneCanPay` (enforced in `parse_withdrawal_sig_params`): [2](#0-1) 

`SIGHASH_SINGLE|ANYONECANPAY` binds *only* input[0] and the single output at the same index (output[0]). It does **not** bind the OP_RETURN output, the anchor output, or any of the additional funding inputs that `fund_raw_transaction` adds when the operator broadcasts the tx: [3](#0-2) 

Once this transaction is broadcast to the Bitcoin mempool (before confirmation), its witness — including the user's valid signature over input[0]/output[0] — is public. Because that signature does not constrain the OP_RETURN payload or the extra funding inputs, **any observer** can build a competing (higher-fee, RBF-replacing) transaction that:
- reuses the exact same input[0] and the identical witness/signature (still valid, since nothing they change affects the signed message),
- reuses the identical output[0] (required to keep the signature valid),
- supplies its own funding input(s) to cover the withdrawal amount and fee,
- writes an **arbitrary** `operator_xonly_pk` into the OP_RETURN.

When this transaction confirms, `update_finalized_payouts` (verifier) trusts the OP_RETURN value verbatim as "the operator who fronted this payout" and stores it in the DB: [4](#0-3) 

Later, when an operator submits a kickoff to claim reimbursement, `is_kickoff_malicious` only checks that the *claimed* operator's key matches the DB-recorded OP_RETURN value — it never verifies that the funding inputs of the confirmed payout actually belonged to that operator: [5](#0-4) 

The bridge circuit performs the same trust-without-verification step: it parses `operator_xonlypk` straight out of the payout's OP_RETURN and folds it into `deposit_constant` without any check that the operator whose key appears there actually supplied the payout's funding inputs: [6](#0-5) [7](#0-6) 

This breaks exactly the custody-binding the prompt calls out: **"the operator credited versus the party that paid."** The signature that is supposed to authorize/attest the payout only covers a static, fixed slice of the transaction (input 0 / output 0) — analogous to the `AllowedCalldataEnforcer` only correctly restricting static-typed fields — while the semantically important "who paid" attribution (OP_RETURN + funding inputs) is a free-form, unauthenticated field that anyone touching the unconfirmed transaction can rewrite.

### Impact Explanation
This is Critical under the given impact classes: "an operator reimbursed for a payout it never funded." An unprivileged party who observes an operator's broadcast (but unconfirmed, RBF-eligible) payout transaction in the Bitcoin mempool can front-run it with their own funding and redirect the `bridge_amount` reimbursement credit to any operator xonly public key of their choosing (all operator public keys are public, discoverable via `fetch_operator_keys`/aggregator). Whoever's key is written into the OP_RETURN — not the party who actually supplied the payout funds — becomes eligible to claim the full `bridge_amount` reimbursement through their own kickoff. This decouples "the party who custodied/fronted the withdrawal" from "the party who gets reimbursed from the vault," which is the exact custody-attribution invariant the protocol is meant to enforce and that a colluding pair (an unprivileged financier + a registered operator) can exploit to extract `bridge_amount` reimbursement while the operator contributes no capital and takes no custody risk. It can also be used adversarially to deny the true, honest fronting operator their rightful reimbursement by out-bidding their RBF transaction and re-attributing the credit elsewhere.

### Likelihood Explanation
The precondition is simply observing an unconfirmed payout transaction in the Bitcoin mempool (a normal, publicly visible event any time a withdrawal is being processed) and being able to construct/broadcast a standard RBF replacement with a higher fee — no special role, key compromise, or privileged RPC access is required, only capital to cover the withdrawal amount plus a higher fee than the original broadcaster. This is squarely an "unprivileged attacker" scenario as scoped by the task.

### Recommendation
Require the `operator_xonly_pk` OP_RETURN value (and ideally all outputs/other inputs) to be committed by the *user's* signature or otherwise cryptographically bound to whoever is authorized to fund the payout — e.g., have the aggregator/user sign over the intended operator's identity (or, at minimum, use a sighash type that commits to all outputs, such as `SIGHASH_ALL|ANYONECANPAY`, and separately verify that the extra funding inputs of the confirmed payout transaction can be traced to the address(es) registered to the credited `operator_xonly_pk`) before trusting it in `update_finalized_payouts`, `is_kickoff_malicious`, and the bridge circuit's `deposit_constant` computation.

### Proof of Concept
1. User signs a `WithdrawParams` with `TapSighashType::SinglePlusAnyoneCanPay` and submits it via the aggregator; operator A receives it and calls `Operator::withdraw`, which builds and broadcasts a `payout_tx` (input[0]=withdrawal UTXO+user sig, output[0]=user payout, OP_RETURN=operator A's xonly pk), funded/fee-bumped via `fund_raw_transaction`/RBF (`core/src/operator.rs:620-674`).
2. Before confirmation, any third party observes this transaction in the mempool and extracts the witness for input[0] (the valid `SinglePlusAnyoneCanPay` signature).
3. The third party constructs a new transaction reusing input[0] and its unmodified witness, output[0] unmodified (script_pubkey/amount identical, required to keep the signature valid), adds its own funding input(s) to cover the withdrawal amount plus a higher fee, and sets the OP_RETURN to operator B's xonly pk (any registered operator, e.g. a colluding party) instead of operator A's.
4. This transaction wins the RBF race and confirms. `update_finalized_payouts` (`core/src/verifier.rs:2312-2342`) records operator B as the payer.
5. Operator B later submits a kickoff; `is_kickoff_malicious` (`core/src/verifier.rs:1857-1890`) matches operator B's key against the DB record and does not flag it as malicious, and the bridge circuit's `deposit_constant`/`host_deposit_constant` (`circuits-lib/src/bridge_circuit/mod.rs:206-229`, `bridge-circuit-host/src/structs.rs:482-516`) validate using operator B's key parsed from the OP_RETURN — allowing operator B to be reimbursed `bridge_amount` despite having contributed none of the payout funds.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
