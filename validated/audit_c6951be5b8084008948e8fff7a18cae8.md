### Title
Heap Pointer Address Disclosure via `MessageLite::DebugString()` for Lite Messages - (File: `src/google/protobuf/message_lite.cc`)

### Summary
The Linux floppy driver bug (CVE-2018-7273) leaks kernel function/variable addresses through `printk`, defeating KASLR because an unprivileged reader of `dmesg` can recover raw kernel pointers with no sanitization. The invariant that failed there is: *diagnostic/debug output must never embed raw memory addresses that are usable to defeat address-space randomization*. In this checkout, `MessageLite::DebugString()` (and its aliases `ShortFormat`/`Utf8Format`) fails the same invariant for `LITE_RUNTIME` messages: it unconditionally serializes the *heap address of the message object itself* into the returned string, with no redaction and no way for the caller to suppress it.

### Finding Description
`MessageLite::DebugString()` branches on whether the concrete message is a full (reflection-capable) message or a Lite message: [1](#0-0) 

For Lite messages (`is_lite == true`, i.e. any message generated with `optimize_for = LITE_RUNTIME`, which is common on Android/embedded/mobile clients and servers) it returns `absl::StrCat("MessageLite at 0x", absl::Hex(this))` — the literal heap pointer to the object, formatted as hex. This behavior is deliberate and explicitly documented by the test suite, which even asserts the address must vary between instances: [2](#0-1) 

`DebugString()` is not a private/internal helper — it is reachable from two other public free functions used broadly for logging/tracing: [3](#0-2) 

The message object whose address is disclosed is exactly the object populated by parsing attacker-controlled bytes via any of the public parse entry points (`ParseFromString`, `ParseFromArray`, `MergeFromCodedStream`, etc.) defined in the same file. There is no check, flag, or sanitization step comparable to the redaction logic that exists for full/reflective messages (`TextFormat::Printer::SetRedactDebugString`, seen in the sibling `text_format.cc` implementation) — the Lite path bypasses all of that and prints the raw pointer unconditionally: [4](#0-3) 

A structurally identical issue exists for `ClassData::DebugName()`, which embeds the `ClassData*` (essentially a vtable-like descriptor address) when `is_dynamic` is set: [5](#0-4) 

### Impact Explanation
Any application code that logs, traces, or surfaces `DebugString()`/`ShortDebugString()`/`Utf8DebugString()` output of a Lite protobuf message (a very common pattern for error/debug logging of parsed request bodies) will emit a live heap address of a heap object into logs. Like `dmesg` for the kernel bug, an application log sink read by a lower-privileged consumer, forwarded to a monitoring system, or otherwise exposed can act as the disclosure channel, giving an attacker a real, defeat-ASLR heap pointer for the process handling their own request. This is an infoleak, not memory corruption on its own, matching the CVSS profile of the analog (Confidentiality: High, Integrity/Availability: None) — consistent with the medium severity of CVE-2018-7273.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the message type to be `LITE_RUNTIME`-optimized and (2) application code to log/expose `DebugString()`/`ShortFormat()`/`Utf8Format()` output of an attacker-supplied message, which is a common but not universal practice, and the disclosure is incidental rather than attacker-triggered on demand (the attacker can send any payload; they don't control *when* the app logs, only that when it does, the pointer leaks).

### Recommendation
For `LITE_RUNTIME` messages, avoid embedding the raw object address in `DebugString()`/`ShortFormat()`/`Utf8Format()` output. If some non-determinism/uniqueness marker is needed (per the test's stated rationale), use a non-address-derived identifier (e.g., a random per-instance token, or a hash) rather than `absl::Hex(this)`, mirroring the redaction already applied to reflective messages via `TextFormat::Printer::SetRedactDebugString`. Apply the same treatment to `ClassData::DebugName()`'s dynamic-class-data address.

### Proof of Concept
1. Build a `LITE_RUNTIME` message type (any proto compiled with `optimize_for = LITE_RUNTIME`, e.g. `proto2_unittest::TestAllTypesLite` used in the existing test).
2. Parse an attacker-controlled, well-formed payload into it via `ParseFromString`/`ParseFromArray` (any public parse API).
3. Call `message.DebugString()` (or `ShortDebugString()`/`google::protobuf::ShortFormat(message)`), and log/print the result.
4. Observe the output begins with `MessageLite at 0x<heap_address>`, exactly as asserted by the existing unit test `TYPED_TEST(LiteTest, DebugString)`: [2](#0-1) 
The printed hex value is the live heap address of the parsed object in the current process — a raw pointer leak analogous to the kernel's `%p`/`printk` disclosure in `show_floppy`.

std::string MessageLite::DebugString() const {
  auto* data = GetClassData();
  ABSL_DCHECK(data != nullptr);
  if (!data->is_lite) {
    return data->descriptor_methods()->debug_string(*this);
  }

  return absl::StrCat("MessageLite at 0x", absl::Hex(this));
}

TYPED_TEST(LiteTest, DebugString) {
  proto2_unittest::TestAllTypesLite message1, message2;
  EXPECT_TRUE(absl::StartsWith(message1.DebugString(), "MessageLite at 0x"));
  EXPECT_TRUE(absl::StartsWith(message2.DebugString(), "MessageLite at 0x"));

  // DebugString() and ShortDebugString() are the same for now.
  EXPECT_EQ(message1.DebugString(), message1.ShortDebugString());

  // Even identical lite protos should have different DebugString() output. Part
  // of the reason for including the memory address is so that we get some
  // non-determinism, which should make it easier for us to change the output
  // later without breaking any code.
  EXPECT_NE(message1.DebugString(), message2.DebugString());
}
