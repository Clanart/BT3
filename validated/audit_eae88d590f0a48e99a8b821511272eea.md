### Title
Cached FROST preprocess seed is never deleted after consumption, so repeat sign calls under one context reuse nonces and leak the secret share - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The bug class from the Escher report is "a teardown/cancellation primitive that is assumed to destroy state but actually leaves it intact, so the supposedly-dead path keeps operating." Serai's `SigningProtocol` exhibits the same shape: `CachedPreprocesses` stores the deterministic FROST seed in the DB and it is **never deleted** after `from_cache` consumes it. `SignMachine::from_cache` explicitly requires that "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:216-224`), yet `preprocess_internal` only ever calls `CachedPreprocesses::get`/`set` — no removal exists anywhere in the codebase (`coordinator/src/tributary/signing_protocol.rs:123-145`).

### Finding Description
`preprocess_internal` derives a ChaCha20 seed stored at `CachedPreprocesses[context]` where `context` is e.g. `(b"DkgConfirmer", attempt)` (`signing_protocol.rs:275`). Every subsequent call to `preprocess_internal` with the same context reloads the same seed, so `seeded_preprocess` regenerates the identical nonce pair `(d, e)` and identical `Commitments` (`crypto/frost/src/sign.rs:121-144`).

Both `DkgConfirmer::share` and `DkgConfirmer::complete` funnel through `share_internal`, which calls `preprocess_internal` again (`signing_protocol.rs:288-327`). The signed message is `set_keys_message(set, removed, key_pair)`, where `key_pair` is supplied by the caller at each call site (`signing_protocol.rs:296-300`). Therefore:

- `share(preprocesses, key_pair_A)` emits share `s_A = d + e·ρ + λ·x·c_A`
- `complete(preprocesses, key_pair_B)` (or a second `share` call with a different `key_pair` / different signing set, which changes `included`, the binding factors `ρ`, or `c`) emits share `s_B` built from the **same** nonces `d, e`

Two shares with identical `(d, e)` but different challenges/bindings yield two linear equations in the two unknowns `d, e`, and after recovering them the secret share `x` falls out of `s − d − e·ρ = λ·x·c`.

### Impact Explanation
Recovery of the validator's FROST secret share for the MuSig-aggregated tributary confirmation key. Combined with `< t` other compromised/reconstructed shares this enables key reconstruction; even alone, a leaked share undermines the threshold assumption and enables forgery chains in combination with the preprocess-commitment data (which is also broadcast). This is the exact failure mode `crypto/frost/src/sign.rs:85-87` and `spec/cryptography/FROST.md:51-55` warn about: "Reusing preprocesses would enable a third-party to recover your private key share."

### Likelihood Explanation
The seed persists for the entire lifetime of the DB (it is never garbage-collected), so *any* code path that signs two distinct messages — or the same message under two distinct signer sets (different `removed` sets change `threshold_i_map_to_keys_and_musig_i_map` output and hence `included`/binding factors, `signing_protocol.rs:208-250`) — under the same `(domain, attempt)` context triggers reuse. `share` and `complete` are invoked at different times by the tributary handler with independently supplied `key_pair` values, so a single attempt that observes two distinct `KeyPair` candidates (e.g., a re-confirmed or disputed DKG result within the same attempt) is sufficient. This requires only that the coordinator be asked to sign twice for the context — the leaked material is broadcast publicly as signature shares.

### Recommendation
Delete `CachedPreprocesses[context]` inside `preprocess_internal` immediately after `CachedPreprocesses::get` succeeds (or on the transition to `share`), so a second `share`/`complete` under the same context cannot silently regenerate the consumed nonces. Alternatively, mix the message (or a monotonically increasing per-context counter persisted alongside the seed) into the seed derivation so distinct messages can never share a nonce. This mirrors the Escher fix direction: do not rely on a stateful entry persisting while assuming the "used once" invariant holds — enforce consumption at the storage layer.

### Proof of Concept
1. For `context = (b"DkgConfirmer", attempt = k)`, call `DkgConfirmer::share(preprocesses, key_pair_A)` → emits `share_A`.
2. Later, within the same attempt `k`, the handler calls `DkgConfirmer::complete(preprocesses, key_pair_B, shares)` with `key_pair_B ≠ key_pair_A` (or a different `removed` set altering the participant mapping). `share_internal` → `preprocess_internal` reloads the still-present `CachedPreprocesses[context]` seed and rebuilds identical nonces via `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:127-135`).
3. `complete` emits a second share `share_B` over the same `(d, e)`. With both public shares and the known public preprocesses, solve:
   - `s_A = d + e·ρ_A + λ·x·c_A`
   - `s_B = d + e·ρ_B + λ·x·c_B`
   Two equations, two unknowns `(d, e)` → recover `d, e`, then `x = (s_A − d − e·ρ_A) / (λ·c_A)`, the FROST secret share.
