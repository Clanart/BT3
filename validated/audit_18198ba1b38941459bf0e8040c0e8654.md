## Title
Self-attested `signer` field lets an unprivileged submitter redirect relayer rewards to an arbitrary beneficiary — (File: `modules/pallets/messaging-incentives/src/lib.rs`, `modules/ismp/core/src/handlers/request.rs`)

### Summary
The external report's core broken invariant is: **reward attribution is not bound to who actually did the delivery work**, letting a party redirect/duplicate reward credit that should go to the honest, timely actor. Hyperbridge's `pallet-messaging-incentives` (and the `WeightFeeHandler` in `pallet-ismp`) reproduce this exact invariant break: the "relayer" credited with a reward is derived purely from a self-supplied `signer` byte-blob carried inside the `RequestMessage`/`ResponseMessage` payload, verified only as "a signature over the message content by *some* keypair" — never checked against the account that actually assembled/submitted the state proof or paid for delivery.

### Finding Description
When `pallet-ismp` processes an inbound `RequestMessage`, the handler stores the receipt using the caller-supplied `msg.signer` verbatim: [1](#0-0) 

`store_request_receipt` and the emitted `Event::PostRequestHandled` both take this `signer` value directly as the "relayer" of record — there is no check anywhere in `handle()` that ties `msg.signer` to the transaction's actual origin or to any real proof-of-delivery infrastructure.

Downstream, `pallet-messaging-incentives::relayer_for` recovers the credited account purely by decoding `msg.signer` as a `Signature` and verifying it against `keccak_256(&msg.requests.encode())`: [2](#0-1) 

and mints reputation to whatever account that signature resolves to: [3](#0-2) 

The same pattern exists in `pallet-ismp`'s built-in `WeightFeeHandler`, which also decodes `msg.signer` with no origin binding to move funds based on the recovered key: [4](#0-3) 

Because the signature only needs to verify over `msg.requests.encode()` (public message content, not anything unique to the submitter's identity or the extrinsic call itself), **anyone who can construct a valid `RequestMessage` — including by copying the requests/proof payload of a message another relayer has already correctly assembled and broadcast — can swap in their own self-generated `signer` signature** and submit it as their own extrinsic. The state/membership proof verification in `handle()` (lines 86-93) still succeeds because the proof is unrelated to `signer`; only the reward-attribution field is attacker-controlled. This is structurally identical to the reported bug: a party who did not do the genuine, timely relay work "listens" for/observes an already-valid delivery payload and resubmits it, redirecting the reward to itself rather than the honest actor whose infrastructure actually produced the proof.

### Impact Explanation
This breaks the pivot requirement that "relayer rewards ... must move exactly once and only to the rightful beneficiary and amount." An attacker can:
- Reroute reputation/fee-handler payouts (`ReputationMinted`, and the `WeightFeeHandler` fund transfer) away from the relayer who actually incurred the cost of building the state proof, to an arbitrary self-controlled account.
- Farm rewards across many sybil accounts using a single piece of expensively-obtained proof data, diluting/misallocating the incentive pool exactly as described in the external report (dilution of rewards, incentive misalignment, reward farming without proportional real work).

This is a logic flaw in the reward-attribution mechanism itself (not merely "malicious relayer" behavior or front-running), since the protocol claims to identify "the relayer that delivered" via `signer` but never authenticates that claim against the extrinsic origin or any delivery-specific commitment (e.g., a nonce, the submitter's account, or a binding to the actual destination-chain proof).

### Likelihood Explanation
Medium-high: submitting `RequestMessage`/`ResponseMessage` extrinsics is a permissionless, publicly documented relayer operation, and message payloads (requests + proof) are visible on-chain/in the mempool once assembled. Swapping the `signer` field before submission requires no special privilege — just any keypair — and the existing test suite for `pallet-messaging-incentives` confirms the credited account is fully determined by whatever `signer` decodes successfully (`on_executed_mints_reputation_proportional_to_bytes`, `unsigned_message_does_not_mint`), with no cross-check against the submitting account.

### Recommendation
Bind reward attribution to a value that cannot be freely re-signed by an observer: either (a) require `msg.signer` to match the extrinsic's actual signed origin (or be authenticated via `validate_unsigned` against the submitting account), or (b) include something unique to the submission itself (e.g., a nonce tied to the destination-chain relayer that produced the delivery, or the extrinsic sender's `AccountId`) in the signed payload so that a copied message cannot be re-attributed to a different beneficiary without redoing the proof-of-delivery work.

### Proof of Concept
1. Honest relayer B assembles a legitimate `RequestMessage` (`requests`, valid membership `proof`) and signs it with keypair `K_B`, producing `signer_B`, then broadcasts the extrinsic.
2. Attacker A observes the pending/public `RequestMessage` payload (`requests`, `proof` are unrelated to `signer` and reusable), replaces `signer_B` with `signer_A` — a fresh signature over the identical `keccak_256(&requests.encode())` produced with attacker-owned keypair `K_A` — and submits this as their own extrinsic before B's lands (or resubmits after B's fails/gets front-run at the mempool level).
3. `handle()` in `modules/ismp/core/src/handlers/request.rs` verifies the membership proof (unaffected by the signer swap) and stores the receipt/dispatches with `signer_A` as the recorded relayer.
4. `pallet-messaging-incentives::on_executed` (or `WeightFeeHandler::on_executed`) recovers `K_A` from `signer_A`, verifying successfully against the same message content, and mints reputation/transfers reward to attacker A's account instead of B's — despite B having done the actual work of sourcing the state and assembling the proof.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}

impl<T: Config> FeeHandler for Pallet<T>
where
	T::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
}
