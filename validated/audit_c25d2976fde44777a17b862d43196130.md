### Title
`matchGitHubRepository` binds a local repo's GitHub association from an unverified remote URL, letting `updateRemoteUrl` silently rewrite `origin` on refresh - (File: `app/src/lib/repository-matching.ts`, `app/src/lib/stores/app-store.ts`, `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The report's broken invariant is: a registry that is supposed to bind an "owner" to a resource does so without verifying that the caller actually controls/owns that resource, and then lets state be silently overwritten as a result. GitHub Desktop has the same class of flaw in how it associates a local repository folder with a `GitHubRepository` record: `matchGitHubRepository` in `app/src/lib/repository-matching.ts:29-46` resolves the account to use purely by matching the remote URL's **hostname**, with no check that the signed-in account can actually access the specific `owner/name` encoded in that (attacker-controllable) remote URL. This differs from the sibling function `findAccountForRemoteURL` in `app/src/lib/find-account.ts:38-110`, which explicitly calls `canAccessRepositoryUsingAPI` before trusting an owner/name pair. This inconsistency is analogous to the Solidity finding: one code path enforces the "owner must actually own it" invariant, the other silently trusts the value and updates a persisted registry.

### Finding Description
`repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4874-4914`) is the function that keeps a local repository's GitHub association fresh. It calls `matchGitHubRepository(repository)` (`app-store.ts:4964-4977`), which in turn delegates to `matchGitHubRepository(accounts, remote.url)` in `repository-matching.ts:29-46`: [1](#0-0) 

This function takes whatever `remote.url` is configured on the repository's default remote — a value fully controlled by whoever set up the `.git/config` (e.g. a cloned/downloaded repository, or a remote changed via `git remote set-url` outside Desktop) — parses only the hostname/owner/name, and returns the **first account whose endpoint hostname matches**, without ever confirming that account has permission to access `owner/name`. Contrast with `findAccountForRemoteURL` in `app/src/lib/find-account.ts:16-28,93-106`, which requires `canAccessRepositoryUsingAPI` to return `true` before an account is returned.

Once `matchGitHubRepository` returns a match, `repositoryWithRefreshedGitHubRepository` uses the (unverified) `owner`/`name` to call `api.fetchRepository(owner, name)` with the victim's own account credentials, and unconditionally persists the result via `repoStore.upsertGitHubRepository` / `setGitHubRepository` (`app-store.ts:4887-4913`), then feeds the API response into `updateRemoteUrl`: [2](#0-1) 

`updateRemoteUrl` will call `gitStore.setRemoteURL(...)` — i.e., rewrite the actual `origin` remote in `.git/config` on disk — whenever the API's `clone_url` differs from the current remote and the stored `gitHubRepository.cloneURL` still matches the current remote ("unchanged"). This write happens with no user confirmation dialog; it's silent maintenance logic. The code comment in `app-store.ts:4880-4882` further states GitHub Desktop "currently never clear[s] GitHub repository associations" (referencing desktop/desktop#1144), meaning once an association is made it persists and keeps being treated as authoritative on every future refresh — exactly the "sticky, unvalidated ownership record" pattern called out in the original report.

### Impact Explanation
Because the owner/name used to query the API and to decide whether/how to rewrite the local remote is derived from an attacker-influenced remote URL string with no access-control check, an attacker who can get a victim to open a folder/clone with a crafted remote (e.g. a repository zip/clone containing a `.git/config` pointing `origin` at an attacker-chosen `owner/name` on github.com) can cause GitHub Desktop to:
- Silently associate the local repository with a `GitHubRepository` record it never verified belongs to the user, and
- Silently rewrite the user's `origin` remote URL to a URL returned from the API for that association on a later background refresh, without any prompt.

This falls under "silent corruption of what the user commits or pushes": subsequent `git push`/`git fetch` actions performed through Desktop's UI would operate against the rewritten remote instead of the one the user believes is configured, with no explicit change confirmation shown to the user (the confirmation dialog `UpstreamAlreadyExists` in `app/src/ui/upstream-already-exists/upstream-already-exists.tsx` only guards the separate `upstream` remote used for forks, not `origin` updates via `updateRemoteUrl`).

### Likelihood Explanation
This requires the attacker to control the initial remote URL of a repository the victim opens in Desktop (e.g. a distributed/cloned repo, similar to the report's "attacker controls a cloned/fetched repository" precondition) and for the victim to have a GitHub.com account signed in (very common for Desktop users). No admin rights, malware, or leaked credentials are required — only that the victim opens the attacker-supplied repository folder in Desktop, which is a normal, expected user action for this application. The main uncertainty (not fully verifiable from static reading) is exactly how often `repositoryWithRefreshedGitHubRepository` fires automatically (e.g. periodic background refresh vs. only on explicit user actions like publish/refresh); I found it invoked from `_publishRepository` and multiple other call sites in `app-store.ts`, but could not fully confirm all automatic/background trigger paths within the available tool budget.

### Recommendation
- Require an explicit access check (like `canAccessRepositoryUsingAPI`) before `matchGitHubRepository` returns an account/owner/name association, so an unverifiable owner/name from an untrusted remote is never bound to a local repository or used to make follow-up API calls.
- Never silently rewrite `origin` via `updateRemoteUrl` without user confirmation, and clear/invalidate stale `GitHubRepository` associations (addressing the long-standing `desktop/desktop#1144` TODO) rather than treating them as permanently authoritative.
- Surface a confirmation dialog (similar to `UpstreamAlreadyExists`) before any automatic remote URL rewrite of `origin`.

### Proof of Concept
1. Attacker creates a public/accessible repo `attacker/decoy` on github.com.
2. Attacker distributes a git repository (e.g. as a zip or via a "clone this" link) whose `.git/config` `origin` remote is set to `https://github.com/attacker/decoy.git`.
3. Victim, who is signed into a github.com account in GitHub Desktop, opens this folder in Desktop.
4. `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` (`app/src/lib/repository-matching.ts:29-46`) matches the victim's own account purely because the hostname is `github.com`, without checking whether the victim's account should be tied to `attacker/decoy`.
5. `api.fetchRepository('attacker', 'decoy')` succeeds (public repo) and the association is persisted (`app-store.ts:4909-4910`).
6. If the attacker later renames/transfers `attacker/decoy` so its `clone_url` changes, the next automatic refresh's `updateRemoteUrl` call (`app/src/lib/stores/updates/update-remote-url.ts:42-44`) silently rewrites the victim's `origin` remote to the new URL with no prompt, altering where the victim's future pushes/fetches go.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
