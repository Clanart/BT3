## Title
`convert_to_balance` / `convert_to_erc20` silently skip scaling when the local chain has *more* decimals than the remote ERC20, minting/crediting corrupted (over- or under-inflated) amounts on cross-chain transfer - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token` scales amounts between the local asset's decimal precision and the remote ERC20's decimal precision (`Precisions` storage) at every send/receive boundary. The scaling helpers `convert_to_balance` and `convert_to_erc20` [1](#0-0)  only implement the "scale down"/"scale up" case for `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals` (e.g. local asset has 18 decimals, remote ERC20 has 6), `erc_decimals.saturating_sub(local_decimals)` returns `0`, so the helper multiplies/divides by `10^0 = 1` — i.e. it performs **no scaling at all** — instead of dividing/multiplying by `10^(local_decimals - erc_decimals)` as required. This directly mirrors the reported `_slippageTol`/decimal-mismatch bug class: a value computed without accounting for a decimal difference between two assets.

### Finding Description
- `send()` converts the locally-escrowed/burned amount (in local decimals) into the wire amount using `convert_to_erc20(amount, erc_decimals, decimals)` [2](#0-1) .
- `on_accept()` converts the incoming wire amount back into local decimals using `convert_to_balance::<Balance>(value, erc_decimals, decimals)` before minting/unlocking to the beneficiary [3](#0-2) .
- Both helpers compute the scale factor as `10^(erc_decimals.saturating_sub(local_decimals))`, which is correct only when `erc_decimals >= local_decimals` [1](#0-0) .
- When the local asset has *more* decimals than the remote ERC20 (a normal, documented configuration — the pallet explicitly supports "10-decimal DOT on Polkadot vs 18-decimal DOT on Ethereum" style pairs, and `Precisions` is set per `(asset, chain)` via `register_token`/`update_token`) [4](#0-3) :
  - `convert_to_erc20` fails to divide down, so the wire `amount` sent to the destination EVM contract is inflated by `10^(local_decimals - erc_decimals)`. If local_decimals=18 and erc_decimals=6, a user sending 1 local token (raw `1e18`) produces a wire amount of `1e18` instead of the correct `1e6` — a **10^12 amount inflation** delivered to `HyperFungibleTokenImpl.mint()`/unlock on the destination chain.
  - `convert_to_balance` symmetrically fails to multiply up on the inbound side, so an ERC20 amount denominated in fewer decimals is credited to the beneficiary as if it were the same raw integer in the local (higher-decimal) asset — a **10^12 deflation**, effectively destroying value.
- Unlike the `AssetLogic._swapAsset` report (which only caused hitting/missing slippage bounds), here the corrupted value is the **actual settlement amount that gets minted or released from custody** on the counterpart chain — there is no additional check anywhere in `send()`/`on_accept()` that cross-validates the scaled amount against the original escrowed amount.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant:
- **Outbound direction (local decimals > erc decimals):** a user's `send()` call escrows/burns the correct local amount, but the message dispatched to the destination contract carries an amount inflated by `10^(local_decimals - erc_decimals)`. If the destination pallet mints (non-native asset) or releases from an under-collateralized custody account, the destination chain mints/releases far more tokens than were ever locked/burned on the source — a direct value-creation / fund-loss bug for the bridge's custody.
- **Inbound direction:** the beneficiary is credited `10^(erc_decimals - local_decimals)`... actually `10^(local_decimals-erc_decimals)` times *less* than intended, so legitimate transfers can vanish into dust, permanently locking user funds (their EVM-side tokens were burned/escrowed, but they receive a negligible local credit).

Given that `Precisions` is an admin-configured value expected to differ per remote chain (the pallet's entire purpose is to support this), any token registered where the local chain's decimals exceed the remote ERC20's decimals hits this path on every single transfer, not just an edge case.

### Likelihood Explanation
Any unprivileged user can trigger this simply by calling the public `send()` extrinsic once a token pair with `local_decimals > erc_decimals` is registered (e.g. a native Substrate asset with 12/18 decimals bridged to a 6-decimal USDC-style ERC20, which is an explicitly documented supported scenario). No malicious relayer, prover, or governance actor is needed — the corruption happens deterministically in pure arithmetic inside `send`/`on_accept`.

### Recommendation
Fix `convert_to_balance` and `convert_to_erc20` in `modules/pallets/hyper-fungible-token/src/impls.rs` to handle both directions explicitly:
```rust
if erc_decimals >= local_decimals {
    value / 10^(erc_decimals - local_decimals)   // scale down
} else {
    value * 10^(local_decimals - erc_decimals)   // scale up
}
```
(and the mirrored logic for `convert_to_erc20`), matching the pattern already used correctly elsewhere in the repo, e.g. `_normalizeAmount` in `evm/src/utils/VWAPOracle.sol` [5](#0-4)  and `adjustDecimals` in the SDK [6](#0-5) , both of which correctly branch on `fromDecimals < toDecimals` vs. `>`.

### Proof of Concept
1. Governance registers an asset via `register_token` with `local_decimals = 18` (e.g. a `pallet-assets` asset with 18 decimals) and `Precisions[asset_id][EVM-dest] = 6`.
2. A user calls `send(params)` with `amount = 1_000_000_000_000_000_000` (1 token, 18-decimal raw units). The pallet burns/escrows 1 full local token.
3. Inside `send()`, `erc20_amount = convert_to_erc20(1e18, erc_decimals=6, decimals=18)`. Since `6u8.saturating_sub(18u8) == 0`, `erc20_amount = 1e18 * 10^0 = 1e18` instead of the correct `1e18 / 10^12 = 1e6`.
4. The dispatched `Message.amount` field carries `1e18` raw units to the destination `HyperFungibleTokenImpl`/gateway contract, which — treating the ERC20 as having 6 decimals — mints or releases `1,000,000,000,000` (1 trillion) tokens to the recipient instead of `1`.
5. The reverse (`on_accept`/`convert_to_balance`) analogously credits `1e18 / 10^0 = 1e18` raw local units for a genuinely small ERC20 transfer that should have been scaled up, but in the case where local > erc decimals this direction instead **destroys** value rather than inflating it, depending on which leg of the round trip is examined — either way the settlement amount no longer matches the escrowed/burned amount.

**Uncertainty note:** I could not fully confirm from the available index whether the destination-side EVM `onAccept` handler for `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` performs any independent decimal validation before minting (only `HyperFungibleTokenImpl.sol`'s bare `mint`/`burn` primitives were retrieved, not the gateway `onAccept` wiring). Due to index size limits, the full contents of `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` and `WrappedHyperFungibleToken.sol` were not available to verify this end-to-end; a Devin session with full repo access should confirm the destination contract does not re-derive/clamp the amount independently before concluding this is exploitable for outright fund creation versus "only" fund lockup.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}

export function adjustDecimals(feeInFeeToken: bigint, fromDecimals: number, toDecimals: number): bigint {
	if (fromDecimals === toDecimals) return feeInFeeToken
	if (fromDecimals < toDecimals) {
		const scaleFactor = BigInt(10 ** (toDecimals - fromDecimals))
		return feeInFeeToken * scaleFactor
	} else {
		const scaleFactor = BigInt(10 ** (fromDecimals - toDecimals))
		return (feeInFeeToken + scaleFactor - 1n) / scaleFactor
	}
}
