### Title
Path-key mismatch in `git diff --check` conflict-marker parsing can zero out `conflictMarkerCount`, letting files with real merge markers be silently committed - (File: `app/src/lib/git/diff-check.ts`)

### Summary
The external report's broken invariant is: a counter is incremented once per *association* but decremented only once per *entity*, breaking the symmetric relationship the accounting depends on, and steering `canTransfer` down the wrong branch. The closest reachable analog in GitHub Desktop is the `conflictMarkerCount` value that gates whether a conflicted file is treated as "resolved." That count is derived by regex-parsing `git diff --check` output and keying results by a path string [1](#0-0) . If the attacker-controlled repository (from a clone/fetch/checkout of a malicious branch) contains conflicted paths that Git quotes or reformats in `--check` output (paths with special/non-ASCII characters, tabs, quotes — Git's C-style path quoting), the extracted key no longer matches the working-directory file's raw `path`, and the per-file marker count silently resolves to zero even though the file on disk still contains real `<<<<<<<`/`=======`/`>>>>>>>` markers.

### Finding Description
`getFilesWithConflictMarkers` builds a `Map<string, number>` from `git diff --check` stdout using the pattern `^(.+):\d+: leftover conflict marker` [2](#0-1) . This map is later associated (in `getMergeConflictDetails`/`getRebaseConflictDetails`) with the conflicted files enumerated from `git status`, by path [3](#0-2) .

Downstream, the count is the sole signal that decides whether a file "has unresolved conflicts":

```
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  if (manualResolution !== undefined) return false
  if (isConflictWithMarkers(status)) {
    return status.conflictMarkerCount > 0
  }
  return true
}
``` [4](#0-3) 

This single boolean feeds `getConflictedFiles`/`getResolvedFiles`, which in turn gate the Conflicts dialog's "Continue"/commit button and the Copilot conflict-resolution flow's "resolved" state [5](#0-4) [6](#0-5) . The Copilot dialog explicitly treats a marker count of zero as proof the user "resolved it themselves in an editor" and unblocks continuing: `isFileResolvedExternally` returns true purely based on `conflictMarkerCount === 0` [7](#0-6) .

The asymmetry mirrors the report's invariant break: the "increment" side (raw marker occurrences reported by `git diff --check`, one line per marker, potentially with quoted/escaped path text) does not use the same key representation as the "decrement/lookup" side (`file.path` from `git status --porcelain`), so the association silently drops to zero instead of reflecting the true marker count — exactly the kind of "increments correctly, decrements/associates incorrectly" bug that corrupts the accounting used to choose the execution path.

### Impact Explanation
If the count is wiped to zero for a file that still contains real conflict markers, Desktop's UI and commit path treat that file as resolved:
- `createMergeCommit` stages "other files" (non-manually-resolved) via `stageFiles` without re-checking marker counts before committing [8](#0-7) .
- The Conflicts dialog and Copilot dialog will unblock "Continue"/commit once `conflictedFiles.length` reaches 0 [9](#0-8) .

This lets a file with literal `<<<<<<<`/`=======`/`>>>>>>>` markers get committed and pushed by the user without any warning — "silent corruption of what the user commits or pushes," matching the accepted impact category.

### Likelihood Explanation
Exploitation requires only that the victim clone/fetch/checkout a repository or branch containing a path that Git quotes in diff output (e.g. containing a tab, double quote, backslash, or non-ASCII byte with `core.quotepath` defaults) and that this file legitimately conflicts during a merge/rebase/cherry-pick that the user resolves with Desktop's own conflict tooling. No local access, elevated privileges, or pre-existing malware is needed — the attacker only needs to control repository content, which fits the "controls a cloned/fetched repository" precondition explicitly allowed by the Valid Impact criteria. I was not able to directly inspect the exact join code that maps `conflictCountsByPath` back onto the `ConflictedFileStatus.conflictMarkerCount` field (only its call sites), so I cannot fully confirm whether an intermediate normalization step (e.g. unquoting) already exists; this is the main residual uncertainty in this analysis.

### Recommendation
- Normalize/unquote paths returned by `git diff --check` (e.g. run `git status`/`diff --check` with `-z`/`--no-quotepath`, or parse `core.quotepath` C-style quoting) before using them as map keys, ensuring symmetric matching with `git status` paths.
- Add a defensive re-verification step before staging/committing "resolved" conflicted files: re-scan file contents for literal conflict-marker lines rather than trusting a cached count keyed by a possibly-mismatched path.
- Add regression tests with conflicted files whose names require quoting (tabs, quotes, non-ASCII) to ensure `conflictMarkerCount` stays accurate.

### Proof of Concept
1. Attacker creates a branch with a file whose name requires Git path quoting when reported by porcelain/diff tooling, e.g. a filename containing a literal tab character or a double quote, and seeds it with content that will merge-conflict against the victim's branch.
2. Victim clones the repo in GitHub Desktop and starts a merge/rebase against that branch; Desktop detects the conflict via `git status --porcelain` and populates `WorkingDirectoryFileChange` with the raw (unquoted) path.
3. Desktop calls `getFilesWithConflictMarkers`, which parses `git diff --check` output; because Git quotes the special-character path in this output, the regex-extracted key differs from the raw `file.path` used elsewhere [1](#0-0) .
4. The lookup for that file's marker count misses, `conflictMarkerCount` resolves to 0, `hasUnresolvedConflicts` returns false [4](#0-3) , and the Conflicts/Copilot dialog shows the file as resolved.
5. The user clicks "Continue"/commit; `createMergeCommit` stages and commits the file verbatim, including its live `<<<<<<<`/`=======`/`>>>>>>>` markers, and the corrupted commit is pushed [8](#0-7) .

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
