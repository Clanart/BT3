Based on the investigation, the closest reachable analog to the loopfi "partial liquidation delays full correction" bug class is in Kaia's validator-set state machine (`kaiax/valset`), which governs when an under-collateralized (under-staked) validator is actually removed from active duty.

### Title
Under-staked validators can remain `ValActive` and keep earning consensus/reward eligibility due to slot-limited MinStake violation demotion - (File: kaiax/valset/impl/transition_context.go)

### Summary
The `CDPVault` bug allows a position that violates the safety threshold to be shielded from a full corrective action (liquidation) because the enforcement check is re-evaluated fresh each time and a partial, self-triggerable action can flip the "unsafe" flag back to "safe." Kaia's validator-set (`valset`) module has a structurally analogous gate: a validator whose staking amount falls below `MinStake` (the analog of an unsafe collateralization ratio) is supposed to be demoted out of `ValActive`, but the demotion is throttled by a per-block "slot" capacity and an active-count floor, so the violating validator can continue operating as `ValActive` — collecting proposer/committee eligibility and staking rewards — for as long as those capacity constraints remain saturated.

### Finding Description
`applyViolationTransition` in [1](#0-0)  defines `canDemoteActive`, which only allows a `ValActive` node to be demoted to `ValExiting` if there is a free `ValExiting` "slot" (`hasSlot`) *and* demoting it would not push the active validator count below `MinActiveCount`.

The MinStake violation rule itself is applied here: [2](#0-1)  — for every `ValActive` validator whose `StakingAmount < MinStake`, the code only transitions it to `ValExiting` `if canDemoteActive(valset.ValExiting)`; otherwise it logs a trace message and the validator is left untouched in `ValActive`.

Even at the epoch boundary (`applyEpochTransition`), a `ValActive` validator that has fallen below `MinStake` is only demoted if doing so does not empty the active set entirely: [3](#0-2) . The accompanying test explicitly documents this retained-despite-violation behavior: [4](#0-3) , and the slot-exhaustion case is exercised in [5](#0-4) .

This mirrors the loopfi issue's mechanics: the "is this entity currently violating the safety condition" check (`StakingAmount < MinStake` vs. `_isCollateralized`) is gated behind an additional condition (`canDemoteActive`/slot availability vs. temporarily restored collateralization) that can suppress the corrective state transition (demotion vs. liquidation) even though the underlying violation persists.

### Impact Explanation
While a validator cannot single-handedly control how many *other* validators are simultaneously in violation (which determines slot saturation), a validator operator fully controls their own staking amount via public withdrawal transactions against their `CnStaking` contract (e.g., `ApproveStakingWithdrawal`/withdrawal flow, see [6](#0-5) ). By deliberately reducing stake below `MinStake` while relying on the fact that the `ValExiting` slot budget (`maxSlotAvailable`) or the `MinActiveCount` floor is already saturated by other violators, a validator can remain `ValActive` — retaining proposer/committee selection eligibility and reward distribution eligibility (see `kaiax/reward` staking-amount-based reward eligibility) — despite not satisfying the minimum staking safety requirement that other participants are held to. This is a state-divergence/incorrect-enforcement risk: nodes that should be excluded from consensus and reward due to insufficient stake continue to participate, diluting rewards for compliant, fully-staked validators and weakening the security assumption that active validators hold at least `MinStake`.

### Likelihood Explanation
Reaching the violation condition itself only requires a normal, unprivileged staking withdrawal transaction that any validator operator can submit. Whether the demotion actually fires depends on the current slot occupancy and active-count floor, which are network-wide conditions outside a single actor's full control — this bounds the likelihood to scenarios where multiple validators are already near/below `MinStake` (e.g., during price drops of the staked asset or coordinated behavior), which is a plausible, foreseeable condition rather than a contrived one, similar to the loopfi scenario requiring a market price drop.

### Recommendation
Track how long a validator has been in MinStake violation and prioritize/force demotion once a bound is exceeded (or immediately revoke reward/proposer eligibility for violating stake even while state transition is deferred), decoupling "reward and consensus eligibility" from the throttled `ValActive`/`ValExiting` state label. Alternatively, apply the staking-amount check independently at reward-distribution and committee-selection time rather than solely relying on the (rate-limited) state machine.

### Proof of Concept
1. Multiple validators simultaneously drop below `reward.minstake` (e.g., due to a price/stake reduction), filling the `ValExiting`/`ValPaused` slot budget computed by `maxSlotAvailable`/`slotLimitsFor` in [7](#0-6) .
2. A validator operator submits a normal withdrawal transaction against their `CnStakingV4` contract, dropping their own `StakingAmount` below `MinStake`.
3. On the next non-epoch block, `applyViolationTransition` evaluates rule 1 for this validator: `val.StakingAmount < ctx.MinStake` is true, but `canDemoteActive(valset.ValExiting)` returns `false` because `hasSlot(valset.ValExiting)` is already exhausted by the other violators from step 1 (as demonstrated by [5](#0-4) ).
4. The validator remains `ValActive`, keeps being selected for committee/proposer duty, and keeps earning staking rewards despite violating `MinStake`, until a slot frees up — an outcome directly analogous to the loopfi position that stays "safe" and avoids full liquidation due to a partial, gate-suppressing condition.

```go
func (ctx *TransitionContext) applyViolationTransition(m valset.NodeMap) valset.NodeMap {
	var (
		newValidators = m.Copy()
		// Slot/count helpers check the in-progress state of newValidators.
		// Counts change as validators transition within the loop, so these cannot be replaced with a contract call.
		hasSlot = func(state valset.NodeState) bool {
			return newValidators.CountByState(state) < ctx.MaxSlotAvailable
		}
		// canDemoteActive additionally ensures enough ValActive remain for consensus.
		// Used only when transitioning FROM ValActive (reducing active count).
		canDemoteActive = func(targetState valset.NodeState) bool {
			return hasSlot(targetState) && newValidators.CountByState(valset.ValActive) > ctx.MinActiveCount
		}
	)
```

```go
// maxSlotAvailable returns the maximum number of nodes allowed in
// ValPaused or ValExiting state each given epochVACount n.
func maxSlotAvailable(n uint64) uint64 {
	if n < 4 {
		return 0
	}
	return (n/3 + 1) / 2
}

// slotLimitsFor returns (maxSlotAvailable, minActiveCount) for epochVACount n.
func slotLimitsFor(n uint64) (uint64, uint64) {
	return maxSlotAvailable(n), minActiveCount(n)
}
```

```go
func TestApplyViolationTransition_Deterministic(t *testing.T) {
	var firstResult map[common.Address]NodeState
	for i := range 100 {
		m := NodeMap{
			addr1: {State: ValActive, StakingAmount: belowMinStake},
			addr2: {State: ValActive, StakingAmount: belowMinStake},
			addr3: {State: ValActive, StakingAmount: aboveMinStake}, // keeps VA count > minActiveCount
		}
		// maxSlot=1, minActive=2 → only 1 of addr1/addr2 can transition
		ctx := violationCtx(t, ctxOpts{MaxSlotAvailable: 1, MinActiveCount: 2})
		out := ctx.applyViolationTransition(m)
		states := map[common.Address]NodeState{
			addr1: out[addr1].State,
			addr2: out[addr2].State,
			addr3: out[addr3].State,
		}
		if firstResult == nil {
			firstResult = states
		} else {
			require.Equal(t, firstResult, states, "nondeterministic result at iteration %d", i)
		}
	}
}
```
