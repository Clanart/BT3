### Title
Public `updateEndRemainingAllocation()` lacks a "set-once" guard, letting any caller re-snapshot the bonus denominator to inflate their own `getBonusAmount()` share and break the `totalBonus` conservation invariant - (File: rewards/Airdrop.sol)

### Summary
`Airdrop.updateEndRemainingAllocation()` is `public` and unconditionally overwrites `totalEndRemainingAllocation = totalRemainingAllocation` whenever `block.timestamp >= periodsEndTime[4]`, with no check that it has already been set. Because `totalRemainingAllocation` monotonically shrinks as other users `claim()`, any late claimant can call `updateEndRemainingAllocation()` directly (bypassing the once-only `if (totalEndRemainingAllocation == 0)` guard used inside `claim()`) immediately before their own `claim()` to shrink the denominator used in `getBonusAmount()`, inflating their own bonus payout beyond their fair share of the fixed `totalBonus` pool.

### Finding Description
`claim()` only auto-triggers the snapshot the first time, guarded by `if (totalEndRemainingAllocation == 0)`: [1](#0-0) 

But `updateEndRemainingAllocation()` itself has no such guard and can be called by anyone, any number of times, as long as `block.timestamp >= periodsEndTime[4]`: [2](#0-1) 

`getBonusAmount()` divides by whatever `totalEndRemainingAllocation` currently holds: [3](#0-2) 

Since `totalRemainingAllocation` is decremented on every `claim()` (`totalRemainingAllocation -= userAllocation`, `rewards/Airdrop.sol:164`), each honest claimant that goes first (e.g. A, B) reduces the pool used as the shared denominator. `totalBonus` itself stops growing once every user's `claimableAmount` reaches 100% of allocation past `periodsEndTime[4]` (the `forfeited` branch only fires when `claimableAmount <= userAllocation`, i.e. `bonus == 0`), so `totalBonus` is effectively fixed at that point. An attacker who waits for other users to claim first, then calls `updateEndRemainingAllocation()` directly before their own `claim()`, re-snapshots `totalEndRemainingAllocation` down to the now-smaller `totalRemainingAllocation`, which inflates `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation` for themselves. This directly breaks the intended conservation invariant that the sum of all `bonusAmount` payouts should never exceed `totalBonus`.

Numeric example: allocations A=100, B=100, C(attacker)=100, `totalBonus`=30. A claims first (auto-sets snapshot to 300, gets bonus=10). B claims next (snapshot still 300, gets bonus=10). At this point `totalRemainingAllocation` = 100 (only C left). If C had claimed normally with the existing snapshot (300), C would get bonus=10, and 10+10+10=30=`totalBonus` (conserved). Instead, the attacker (C) calls `updateEndRemainingAllocation()` directly beforehand, resetting the snapshot to 100 (current `totalRemainingAllocation`), then calls `claim()`: bonus = 100*30/100 = 30. Total paid out = 10+10+30 = 50, exceeding `totalBonus`=30 by 20 units, stolen from tokens meant for other purposes / the contract's balance.

### Impact Explanation
This is a direct theft of the shared "unclaimed yield" (bonus) pool: an unprivileged claimant can pay themselves more than their proportional share of `totalBonus`, at the expense of the contract's token balance which funds other claimants' principal + bonus. If enough is drained, later legitimate claimants can hit `if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();` (`rewards/Airdrop.sol:160`), freezing their rightful allocation. This matches Immunefi's "theft of unclaimed yield" / "theft of user funds" impact class.

### Likelihood Explanation
No special privileges are required — `updateEndRemainingAllocation()` is `public` and callable by any address, and `claim()` is callable by any registered allocatee. The only precondition is that the attacker waits until `block.timestamp >= periodsEndTime[4]` and until at least one other user has already claimed (shrinking `totalRemainingAllocation`), which is a normal, expected occurrence given many claimants will claim promptly after vesting completes. No capital is needed beyond gas, and the attack is repeatable by any subsequent claimant, worsening the shortfall for whoever claims last.

### Recommendation
Add the same "set-once" guard to `updateEndRemainingAllocation()` that is already used at its call site in `claim()`:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4] && totalEndRemainingAllocation == 0) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```
This ensures the bonus-pool denominator is snapshotted exactly once, immutably, at the first claim after period 4 ends, preserving the conservation invariant.

### Proof of Concept
Hardhat test plan:
1. Deploy `Airdrop` with `startTime` in the near future and a mock ERC20 token; fund the contract with enough tokens to cover principal + `totalBonus`.
2. `register([A, B, C], [100, 100, 100])`.
3. Warp time to before `periodsEndTime[4]`; have A, B, C each partially claim at earlier periods such that some forfeiture accrues into `totalBonus` (e.g. only 2 of 3 users claim at period 0-3, causing the non-claiming behavior to set up a non-zero `totalBonus`), or directly assert a nonzero `totalBonus` state via prior partial claims per the periods table.
4. Warp to `>= periodsEndTime[4]`.
5. Have A call `claim()` (auto-sets `totalEndRemainingAllocation` to full remaining, e.g. 300), then B call `claim()` (uses the same snapshot).
6. Read `totalRemainingAllocation` (now reduced to C's allocation only, e.g. 100).
7. Attacker (C) calls `updateEndRemainingAllocation()` directly, then `claim()`.
8. Assert: `bonusAmount` paid to C (`claimableAmount_C - allocation_C`) plus bonuses already paid to A and B exceeds `totalBonus` recorded before C's claim, i.e. `sum(bonusPaid) > totalBonus`, and/or assert the contract's final token balance goes negative/insufficient for any hypothetical remaining claimant, demonstrating the conservation invariant break.
