### Title
`ThresholdKeys::new`/`read` derives `group_key` from only the first `t` verification shares, letting attacker-supplied key material carry corrupted shares for participants `t+1..=n` that silently break reconstruction — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to the Illuminate `mint()` bug — where anyone could inflate `totalSupply` with unbacked tokens so the pro-rata `redeem()` formula `(amount * holdings) / totalSupply` pays out 0 — `ThresholdKeys::new` computes `group_key` by interpolating **only** `verification_shares[1..=t]` and never validates the remaining `n - t` shares against the polynomial/group key. Untrusted bytes fed to `ThresholdKeys::read` can therefore carry a well-formed-looking `group_key` (matching an already-funded multisig) while the verification shares for participants `t+1..=n` are arbitrary garbage. Any signing set that includes one of those indexes produces a share that fails verification, aborting signing.

### Finding Description
`ThresholdKeys::read` parses attacker-controlled `t`, `n`, `i`, the interpolation method, a secret share, and `n` verification shares, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:574-632). `ThresholdKeys::new` checks only that the map has `n` entries and that every index is `≤ n` — which, combined with `HashMap` deduplication, just forces the index set to be exactly `1..=n` — and then computes the group key:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

(crypto/dkg/src/lib.rs:376-378)

Only participants `1..=t` contribute. Shares for indexes `t+1..=n` are stored verbatim in `ThresholdCore` and are used later in `view()` to build the interpolated `verification_shares` map for whichever signing set is chosen (crypto/dkg/src/lib.rs:500-507). There is no check that all `n` shares lie on the same degree-`(t-1)` polynomial — i.e., no consistency check between the extra shares and `group_key`.

An attacker can thus craft serialized `ThresholdKeys` where:
- the shares for `1..=t` are chosen so their Lagrange combination equals a target (e.g., an existing funded multisig's) group key — all Lagrange factors are public, so e.g. `share_1 = group_key * L_1^{-1}`, `share_2..=t` = identity/arbitrary points compensated accordingly;
- shares for `t+1..=n` are random points not on the polynomial.

`keys.group_key()` returns the expected key, so any consumer (address generation, Scanner, funding) treats the keys as valid. But when `view(included)` is called with an `included` set containing any index `> t` — which is legitimate, since any `t`-of-`n` subset should be able to sign — that participant's interpolated `verification_share` is wrong relative to `group_key`. Their FROST signature share then fails `verify` in `AlgorithmSignatureMachine::complete`, yielding `FrostError::InvalidShare` and aborting the signature.

### Impact Explanation
Funds associated with the reported `group_key` become unspendable whenever the honest signing set drawn by the scheduler includes any participant index `> t` — a griefing/DoS on redemption directly mirroring the Illuminate report's "redeem returns 0 or reverts" outcome. Depending on how `included` is selected, this may deterministically brick signing (if high-index participants are always included) or intermittently fail attempts, each time blamed on honest participants (`InvalidParticipant`/`InvalidShare` is emitted against the victim index, not the attacker). Because `read`/`new` fully "validates" the blob, the corruption surfaces only at signing time, far removed from the malicious input.

### Likelihood Explanation
Requires an attacker to supply the serialized `ThresholdKeys` bytes consumed by a victim (a listed reachable input: `ThresholdKeys::read`). The construction needs no secret knowledge — Lagrange factors and the target group key are public. Medium likelihood conditional on an integrator loading externally-sourced key material; High impact on availability of funds when it occurs.

### Recommendation
In `ThresholdKeys::new`, after computing `group_key` from `1..=t`, verify the remaining shares are consistent: for each `i in (t+1)..=n`, check `verification_shares[i] == Σ_{j=1..=t} verification_shares[j] * λ_j(i)` (Lagrange evaluation at `i`), or equivalently verify the reconstructed view for a set including `i` still interpolates to `group_key`. Alternatively, require callers of `read` to re-derive and cross-check `group_key` against an externally known value, and document that `ThresholdKeys::read` output is not self-authenticating.

### Proof of Concept
Conceptual (Rust, in-scope crates only):

```rust
// Target: an existing funded multisig group key G_target, params t=2, n=3.
// Attacker builds a malicious serialized ThresholdKeys blob.

// Lagrange factor for participant 1 in set {1,2}: L1 = 2 * (2-1)^{-1} = 2
// For set {1,2}: group_key = share1 * 2 + share2 * (-1)  (mod order)
// Pick share2 = identity (or any point); solve share1 = (G_target + share2) * 2^{-1}.

let l1 = F::from(2u64);                    // λ_1 for set {1,2}
let l2 = -F::ONE;                          // λ_2 for set {1,2}
let share2 = G::identity();                // arbitrary
let share1 = (G_target - share2 * l2) * l1.invert().unwrap();
let share3 = G::random(&mut rng);          // NOT on the polynomial — corrupt

// Serialize: C::ID, t=2, n=3, i=1, Interpolation::Lagrange, secret_share=0,
// verification_shares = [share1, share2, share3]
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), G_target);    // looks fully valid

// Victim (participant 3) loads their copy and signs in set {1,2,3} or {2,3}:
let view3 = keys3.view(vec![p2, p3]).unwrap();      // succeeds — no error
// view3.verification_share(p3) is wrong vs group_key, so in
// AlgorithmSignatureMachine::complete the share fails verification:
//   FrostError::InvalidShare(Participant(3))
// Signing aborts; participant 3 (honest) is blamed. Funds at G_target unspendable.
```

Root cause is the partial validation at crypto/dkg/src/lib.rs:355-378: the integrity `group_key` is derived from a `t`-element subset while `n - t` shares are accepted unchecked — the same shape as minting unbacked supply that only the pro-rata consumer later divides by.
