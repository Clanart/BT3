### Title
Pool wallet accepts a zero/burn `target_puzzle_hash` when joining or self-pooling, permanently misdirecting future block rewards - (File: `chia/pools/pool_wallet.py`)

### Summary
`PoolWallet` validates a caller-supplied `PoolState` before committing it on-chain (`_verify_initial_target_state` → `_verify_pool_state`), but none of the validation helpers actually reject an invalid/burn `target_puzzle_hash` such as `bytes32.zeros`. This is the same bug class as the reported `setXProvider` issue: a critical address field that drives future value transfers is never checked against a degenerate/zero value before being persisted into consensus-relevant state.

### Finding Description
`PoolState.target_puzzle_hash` is a non-optional `bytes32` field that determines where pool/self-pool rewards are ultimately paid [1](#0-0) .

Before a `PoolState` is used to create a pool wallet or to join/leave a pool, it is passed through `_verify_initial_target_state`, which calls `_verify_pool_state`: [2](#0-1) 

The only check on `target_puzzle_hash` is `if state.target_puzzle_hash is None`. Because `target_puzzle_hash` is typed as `bytes32` (not `Optional[bytes32]`), this branch can never trigger for any concrete 32-byte value supplied by a caller — including `bytes32.zeros`. Neither `_verify_self_pooled` nor `_verify_pooling_state` add any additional check on the puzzle hash value itself: [3](#0-2) 

`join_pool`, which is reachable from an unprivileged local wallet action (`pw_join_pool` RPC / plotnft CLI on top of it), only re-validates via the same `_verify_initial_target_state` call and otherwise accepts any `target_state` supplied by the caller: [4](#0-3) 

The accepted `target_puzzle_hash` is then baked directly into the pooling/waiting-room inner puzzle via `pool_state_to_inner_puzzle`, which is used both when creating the singleton and when generating the on-chain travel spend: [5](#0-4) 

Because the RPC-level `NewPoolWalletInitialTargetState.__post_init__` only checks that `target_puzzle_hash` is *set* (not `None`) when `FARMING_TO_POOL`, and does not reject `bytes32.zeros`, the zero hash flows unchanged from user input all the way into consensus-committed pool state: [6](#0-5) 

### Impact Explanation
`target_puzzle_hash` is the final payout destination for pool rewards, both for self-pooling and for the pool-declared address in farming-to-pool mode. `PoolWallet.claim_pool_rewards()` and `generate_travel_transactions()` build coin spends that pay claimed/absorbed rewards to the current `target_puzzle_hash`. If this is set (accidentally by a buggy client, or via a malicious/compromised pool response that a wallet blindly accepts as the pool's `target_puzzle_hash`) to `bytes32.zeros` or another unspendable/burn hash, all subsequent farming rewards routed through that singleton become permanently unspendable — a direct, irreversible loss of funds for the plot-NFT owner. This matches the "contract/asset becomes unusable" impact class described in the reference report.

### Likelihood Explanation
Reaching this path requires only a single wallet-level action: creating a pool wallet or calling `join_pool` with an attacker- or bug-supplied `target_puzzle_hash`. No privileged role is required — a local wallet RPC caller (or code path deriving `target_puzzle_hash` from an untrusted pool server response) can trigger it. Since the guard that appears intended to catch this case (`state.target_puzzle_hash is None`) is unreachable due to typing, the vulnerability is a straightforward logic gap rather than a theoretical edge case.

### Recommendation
Add an explicit check in `PoolWallet._verify_pool_state` (or in `NewPoolWalletInitialTargetState.__post_init__` / `initial_pool_state_from_dict`) that rejects `target_puzzle_hash == bytes32.zeros` (and any other well-known burn/unspendable puzzle hash) before the state is used to create a launcher spend or travel spend, e.g.:
```python
if state.target_puzzle_hash == bytes32.zeros:
    return "Invalid target_puzzle_hash: cannot be the zero hash"
```
This should be applied consistently in `_verify_self_pooled`, `_verify_pooling_state`, and the RPC-facing `NewPoolWalletInitialTargetState` validation so that both wallet-initiated and pool-server-supplied puzzle hashes are checked.

### Proof of Concept
1. Call the pool-wallet creation or `pw_join_pool` RPC with `initial_target_state`/`target_state` set to `state="FARMING_TO_POOL"`, `target_puzzle_hash=bytes32.zeros`, a valid `pool_url`, and a valid `relative_lock_height`.
2. `NewPoolWalletInitialTargetState.__post_init__` passes because `target_puzzle_hash` is merely "set" (non-`None`) [7](#0-6) .
3. `PoolWallet._verify_pool_state` passes because `bytes32.zeros is None` is `False` [8](#0-7) .
4. `create_new_pool_wallet_transaction` / `join_pool` proceed, and `pool_state_to_inner_puzzle` curries the zero hash directly into the on-chain singleton's inner puzzle as the reward payout target [5](#0-4) .
5. All future rewards claimed or travelled through this singleton are paid to `bytes32.zeros`, permanently locking those funds.

    def _verify_self_pooled(cls, state: PoolState) -> str | None:

        if state.pool_url not in {None, ""}:
            err += " Unneeded pool_url for self-pooling"

        if state.relative_lock_height != 0:

    @classmethod
    def _verify_pooling_state(cls, state: PoolState) -> str | None:
        err = ""

            err += (
                f" Pool relative_lock_height ({state.relative_lock_height})"
                f"is less than recommended minimum ({cls.MINIMUM_RELATIVE_LOCK_HEIGHT})"
            )

                f" Pool relative_lock_height ({state.relative_lock_height})"
                f"is greater than recommended maximum ({cls.MAXIMUM_RELATIVE_LOCK_HEIGHT})"
            )

        if state.pool_url in {None, ""}:
            err += " Empty pool url in pooling state"
        return err

    @classmethod
    def _verify_pool_state(cls, state: PoolState) -> str | None:
        if state.target_puzzle_hash is None:
            return "Invalid puzzle_hash"

        if state.version > POOL_PROTOCOL_VERSION:
            return (
                f"Detected pool protocol version {state.version}, which is "
                f"newer than this wallet's version ({POOL_PROTOCOL_VERSION}). Please upgrade "
                f"to use this pooling wallet"
            )

        if state.state == PoolSingletonState.SELF_POOLING.value:
            return cls._verify_self_pooled(state)
        elif state.state in {PoolSingletonState.FARMING_TO_POOL.value, PoolSingletonState.LEAVING_POOL.value}:
            return cls._verify_pooling_state(state)
        else:
            return "Internal Error"

    @classmethod
    def _verify_initial_target_state(cls, initial_target_state: PoolState) -> None:
        err = cls._verify_pool_state(initial_target_state)
        if err:
            raise ValueError(f"Invalid internal Pool State: {err}: {initial_target_state}")
