### Title
Unvalidated participant indexes in blame evaluation panic on missing commitments map entry — reachable crash (DoS) in PedPoP blame flow - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame_internal` and the `AdditionalBlameMachine::blame` wrapper index `self.commitments[&sender]` directly (crypto/dkg/pedpop/src/lib.rs:599). The `sender` (accused) and `recipient` (accuser) participants come from attacker-controlled blame material, yet only `Participant::new`'s non-zero check is applied at deserialization (crypto/dkg/src/lib.rs:29-35; coordinator/src/tributary/transaction.rs:348-353). If `sender` is a well-formed `Participant` absent from `commitments` (index `> n`, or a participant removed from the set), the `HashMap` index panics and kills the processing task — a crafted-input crash analog to the CVE-2025-55663 null-deref DoS.

### Finding Description
- `AdditionalBlameMachine::new` builds `commitments` strictly for `1 ..= n` and errors `MissingParticipant` if any index is absent from `commitment_msgs` (crypto/dkg/pedpop/src/lib.rs:654-661). It performs no validation of the *accused/accuser* values later passed to `blame`.
- `blame_internal` then evaluates `self.commitments[&sender]` unconditionally (crypto/dkg/pedpop/src/lib.rs:596-604). `std::collections::HashMap`'s `Index` impl panics on a missing key.
- The upstream caller in `processor/src/key_gen.rs` `VerifyBlame` handler feeds `accuser`/`accused` straight from the coordinator message into `blame(accuser, accused, ...)` (processor/src/key_gen.rs:504-556), and additionally `.unwrap()`s `AdditionalBlameMachine::new` — so a `MissingParticipant` error (accused never submitted commitments / was removed via `RemoveParticipantDueToDkg`) is also an immediate panic.
- The API docs themselves concede this contract fragility: "Usage of invalid commitments is considered undefined behavior, and may cause everything from inaccurate blame to panics" (crypto/dkg/pedpop/src/lib.rs:645-648).

### Impact Explanation
A participant (or anyone able to submit a `Transaction::InvalidDkgShare`/`VerifyBlame` accusation) supplies an `accused`/`faulty` index that parses as `Participant` but is not a key in the commitments map — e.g., an index above `n` that passed `Participant::new`, or a participant whose commitments were never recorded. The node processing the blame hits the `HashMap` index panic (or the `MissingParticipant` `unwrap`) and crashes, denying service during the DKG/blame phase — mirroring the crafted-file segmentation-violation DoS of the reference CVE.

### Likelihood Explanation
The `faulty`/`accuser` fields are read as raw `u16` and only checked for non-zero (`Participant::new`, crypto/dkg/src/lib.rs:29-35; coordinator/src/tributary/transaction.rs:341-353). Reachability requires the blame path to be exercised and no intermediate bound-check of `accused <= n`; I could not fully confirm the absence of such a check in `coordinator/src/tributary/handle.rs` (contents not inspected in this pass), so the trigger may be partially gated by coordinator-side validation. Within the in-scope crate, the panic itself is unconditional once an out-of-map `sender` reaches `blame`.

### Recommendation
- Replace `self.commitments[&sender]` (and the equivalent `[&l]` in `calculate_share`, crypto/dkg/pedpop/src/lib.rs:490) with `.get(&sender)` returning a `PedPoPError::InvalidParticipant`/`MissingParticipant` style error instead of panicking.
- In `AdditionalBlameMachine::blame`/`BlameMachine::blame`, reject `sender`/`recipient` not in `1 ..= n` before evaluating.
- Ensure callers bound-check `accused`/`accuser` against `params.n()` before invoking blame evaluation.

### Proof of Concept
1. DKG attempt with `n` participants; participant `k`'s commitments are never stored (or `k = n + 1` supplied raw).
2. Accuser submits blame naming `sender = Participant::new(k)` (non-zero, so deserialization succeeds).
3. `AdditionalBlameMachine::new` either returns `Err(MissingParticipant(k))` — panicking at the caller's `.unwrap()` (processor/src/key_gen.rs:548) — or succeeds, after which `blame_internal` executes `self.commitments[&k]` on a map keyed only by `1 ..= n` (crypto/dkg/pedpop/src/lib.rs:599, 656-660).
