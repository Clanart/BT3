Confirmed: `ConvertCoinNativeERC20` (called from `ConvertCoinToERC20FromPacket`) performs no `pair.Enabled` check anywhere in its body [1](#0-0) . The disabled-check is only enforced at the `OnRecvPacket` entry point and in `MintingEnabled`/`setAllowance`, but not in the IBC-timeout/error-ack refund path.

### Title
IBC timeout/error-ack refund path bypasses governance-disabled token pair, silently minting ERC20 tokens for a "killed" pair - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
This is the same bug class as the Alchemix `Voter._updateFor` report: an entity that governance has explicitly disabled ("killed") continues to accrue/produce value through a code path that forgot to check the disabled flag. In Cosmos EVM's `x/erc20` module, `ToggleConversion` sets `pair.Enabled = false` to stop ERC20 conversions for a token pair [2](#0-1) . Most conversion entry points respect this flag — `OnRecvPacket` explicitly checks `!pair.Enabled` and returns [3](#0-2) , and `MintingEnabled`/`setAllowance` also check it [4](#0-3) [5](#0-4) . However, `ConvertCoinToERC20FromPacket` — invoked from `OnAcknowledgementPacket` (on error-ack) and `OnTimeoutPacket` — only checks `params.EnableErc20` (the module-wide switch) and `IsDenomRegistered`, never `pair.Enabled` for the individual token pair [6](#0-5) . It then unconditionally calls `ConvertCoinNativeERC20`, which also performs no `Enabled` check [1](#0-0) .

### Finding Description
Once a native-ERC20 token pair is disabled via governance `MsgToggleConversion` (e.g., because the ERC20 contract was found to be malicious, buggy, or is being deprecated), the intent is that no further coin↔ERC20 conversions should occur for that pair. Any ordinary user can trigger the vulnerable path without any governance/relayer privilege: initiate an outbound ICS20 transfer of the pair's registered denom to any chain and let it either time out or receive an error acknowledgement (both are ordinary, permissionless, and often externally influenceable outcomes of IBC transfers, e.g. sending to a channel with no counterparty listener, or a channel that will reject the transfer). This triggers `OnTimeoutPacket`/`OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket`, which re-mints/unescrows the ERC20 representation into the sender's EVM balance for a token pair that governance intentionally disabled.

### Impact Explanation
This breaks the accounting invariant that a disabled token pair cannot produce new ERC20-side value. It results in unauthorized minting/unescrowing of ERC20 balances for an asset that governance froze, effectively bypassing a security control meant to halt a compromised or deprecated ERC20 contract (e.g., a token pair disabled specifically because the ERC20 contract has a reentrancy/inflation exploit). Value could keep flowing into the ERC20 representation of a "killed" pair, corrupting the coin/ERC20 1:1 backing invariant that `x/erc20` is designed to preserve.

### Likelihood Explanation
Any unprivileged user holding the affected native coin can trigger this by sending an ICS20 transfer that will time out or get an error ack (self-controllable in many cases, e.g., targeting a channel/destination configured to reject/timeout). No special permissions or validator collusion are required.

### Recommendation
Add a `pair.Enabled` check inside `ConvertCoinToERC20FromPacket` (mirroring the check in `OnRecvPacket`) before calling `ConvertCoinNativeERC20`, so that timeout/error-ack refund flows no-op (leaving the sender with the bank coin, not the ERC20) when the token pair conversion has been disabled by governance.

### Proof of Concept
1. Governance registers a native ERC20 token pair for denom `atoken` (`RegisterERC20`).
2. Governance later calls `MsgToggleConversion` to disable the pair (`pair.Enabled = false`) due to a discovered ERC20 contract issue.
3. A user holding `atoken` coins initiates an ICS20 transfer (`MsgTransfer`) of `atoken` to a channel/counterparty that will time out (or that returns an error acknowledgement).
4. `OnTimeoutPacket`/`OnAcknowledgementPacket` invokes `ConvertCoinToERC20FromPacket`, which checks only `params.EnableErc20` and `IsDenomRegistered` — not `pair.Enabled` — and calls `ConvertCoinNativeERC20`.
5. The user's EVM account receives newly unescrowed/minted `atoken` ERC20 tokens despite the pair being disabled, which can be verified by querying the ERC20 `balanceOf` for the sender and comparing against the disabled `pair.Enabled` state fetched via `GetTokenPair`.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

// ToggleConversion toggles conversion for a given token pair
func (k Keeper) toggleConversion(
	ctx sdk.Context,
	token string,
) (types.TokenPair, error) {
	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	pair.Enabled = !pair.Enabled
	k.SetTokenPair(ctx, pair)
	return pair, nil
}
