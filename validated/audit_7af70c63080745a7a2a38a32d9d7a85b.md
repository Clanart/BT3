### Title
Cached FROST preprocess seed is keyed only by `("DkgConfirmer", attempt)`, so a validator's nonce seed outlives its validator-set namespace and is reused across DKG confirmations for different sets - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
CVE-2022-24122's bug class is a reference-counted object (`ucounts`) that outlives the namespace which defined it, so a stale object is used in a new security context. The analog in Serai is `CachedPreprocesses`: a persistent store of FROST nonce seeds whose key is an `Encode`-able `context`. `DkgConfirmer` builds that context as `(b"DkgConfirmer", self.attempt)` — omitting the tributary's genesis / validator set — so the nonce seed generated for one validator set's DKG confirmation survives that set ("namespace") and is deterministically reloaded for the next set's confirmation where `attempt` again equals e.g. `0`. `AlgorithmSignMachine::from_cache`/`seeded_preprocess` then re-derives identical nonces, producing nonce reuse across two distinct signed messages — direct private-key-share recovery for anyone observing the on-chain shares.

### Finding Description
`preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs:100-148` fetches `CachedPreprocesses::get(txn, &self.context)`; if absent it generates a fresh `AlgorithmSignMachine`, XORs `machine.cache()` with an encryption key derived from `context || self.key`, and stores it. The seed is never deleted or bound to anything beyond `context`. For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` (line 275) — `DkgConfirmerSigningProtocol<'a, T> = SigningProtocol<'a, T, (&'static [u8; 12], u32)>` (line 252). Neither the tributary genesis (`spec.genesis()`) nor the `ExternalValidatorSet` is part of the key, and the encryption key (`"Cached Preprocess Encryption Key" || context.encode() || key.to_repr()`, lines 107-114) is equally set-agnostic.

`attempt` is a per-tributary counter (`AttemptDb: (genesis, topic) -> u32`, `coordinator/src/tributary/db.rs:66`), so every new validator set starts again at `attempt = 0`. A validator who keeps the same `key` across two sets — the normal case — therefore hits the same `CachedPreprocesses` key twice, once under each set.

The second lookup returns the *old* seed, and `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`) deterministically derives `nonces`/`commitments` from `ChaCha20Rng::from_seed(*seed.0)`, so the identical FROST nonces are used to sign `set_keys_message(set, removed, key_pair)` (line 296) for two different sets — different MuSig participant lists, different messages, different challenges, same nonces. The file's own header (lines 25-48) documents that nonce reuse across signing sessions is fatal, and the FROST spec (`spec/cryptography/FROST.md:51-55`) states reuse enables recovery of the private key share.

### Impact Explanation
Both `Transaction::DkgConfirmed` shares and the published `confirmation_nonces` are consensus data visible on the tributary (handle.rs `Transaction::DkgShares { confirmation_nonces }`, `DkgConfirmed { confirmation_share }`). With two signature shares `s₁, s₂` computed over the same nonce scalar `k` but different challenges `c₁ ≠ c₂` (different `set_keys_message` contents and different MuSig preprocessing), an observer solves `s₁ - s₂ = (c₂ - c₁) · x` for the validator's private key `x` — the Ristretto validator key that is the root of trust for all tributary signatures, not just a threshold share. This is textbook nonce reuse, reachable purely from publicly finalized data.

### Likelihood Explanation
Deterministic: every validator persisting across a validator-set rotation reuses the seed for `("DkgConfirmer", 0)` (and any matching later attempt numbers). No adversarial action is needed beyond observing the two sets' `DkgConfirmed` transactions. The only mitigations would be if a validator changed keys per set (they don't — `key` is the validator's identity key) or if attempts never repeated across sets (they do — the counter is genesis-scoped while the cache key is not). The "ucounts outlives its namespace" shape is exact: the seed's lifetime is the whole DB, its key's namespace is only `attempt`, and the security context (validator set) in which it was minted is not encoded.

### Recommendation
Include the tributary genesis (or `spec.set()`) in the `DkgConfirmer` context — e.g. `let context = (b"DkgConfirmer", self.spec.genesis(), self.attempt)` — so each namespace gets its own seed. Also mix the genesis into the preprocess-encryption-key preimage for defense in depth. Additionally, consider binding `context` inside `SigningProtocol` itself (e.g. always prefix `spec.genesis()`), and add a `CachedPreprocesses::del`/rotation after `complete_internal` succeeds so a confirmed attempt's seed cannot be re-served even if the context repeats.

### Proof of Concept
1. Validator `V` (fixed key `k`) is in validator set `A` (genesis `gA`) and set `B` (genesis `gB`), sequential sessions.
2. During `A`'s DKG, `dkg_confirmation_nonces(k, specA, txn, 0)` → `preprocess_internal` finds no `CachedPreprocesses[("DkgConfirmer", 0)]`, stores `seed XOR enc(k)` where `enc = Blake2s256("Cached Preprocess Encryption Key" || ("DkgConfirmer",0).encode() || k)`.
3. `V` publishes `confirmation_nonces` (commitments derived from `ChaCha20Rng::from_seed(seed)`) in `Transaction::DkgShares`, and its share `s_A` in `DkgConfirmed` for `set_keys_message(setA, removedA, keyPairA)`.
4. During `B`'s DKG, `attempt` is again `0`. `CachedPreprocesses::get(("DkgConfirmer", 0))` returns the same stored bytes; `enc` is identical (same context encoding, same `k`), so the same `seed` is loaded and `from_cache` reproduces the same nonces/commitments — the published `confirmation_nonces` are byte-identical to step 3's.
5. `V`'s share `s_B` for `set_keys_message(setB, removedB, keyPairB)` is published. Observer computes `x = (s_A - s_B) / (c_B - c_A)` using the challenges reconstructed from the public transcripts, recovering `V`'s validator private key.
