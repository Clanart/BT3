### Title
Panic on attacker-controlled participant index in PedPoP blame evaluation enables crash DoS - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
The reference bug class is a remotely-triggered `panic!` on a crafted protocol message that crashes honest participants. The same class is present in Serai's PedPoP DKG: `BlameMachine::blame` / `AdditionalBlameMachine::blame` and the shared `blame_internal` take a `sender: Participant` index that originates from an accusing party's message, and unconditionally index `self.commitments[&sender]` inside `blame_internal` (crypto/dkg/pedpop/src/lib.rs:599) and `share_verification_statements`. `self.commitments` only ever contains keys `1..=n` (inserted in `calculate_share` via `all_participant_indexes()` and in `AdditionalBlameMachine::new` via `for i in 1 ..= n`). An accuser can name any `Participant` value `> n` (or one not present in the map), causing `HashMap`'s `Index` implementation to panic — an unhandled panic reachable purely from attacker-supplied protocol data.

### Finding Description
- `Participant` admits any non-zero `u16` (`Participant::new`, crypto/dkg/src/lib.rs:29-34), so `Participant(n + k)` is a well-formed value a peer can send.
- `blame_internal` at crypto/dkg/pedpop/src/lib.rs:575-609 performs `self.commitments[&sender]` (line 599) with no membership/range check on `sender` or `recipient`. Passing a `sender` not in `1..=n` panics (`index out of bounds` / `no entry found for key`).
- `AdditionalBlameMachine::blame` (line 674-682) exposes the same unchecked path, and `AdditionalBlameMachine` is explicitly designed to be usable "regardless of if the caller was a member" (line 639-640), meaning even non-participating nodes evaluating third-party blame claims can be crashed by a forged accusation naming an out-of-range sender.
- Unlike the FROST signing path, where every attacker-controlled `Participant` is screened by `validate_map`/explicit bounds checks before any indexing (crypto/frost/src/sign.rs:297-313; `complete` at 451-489), the blame path performs no equivalent validation of `sender`/`recipient` before map indexing.
- The same pattern exists in `KeyMachine::calculate_share` via `self.commitments[&l]` (line 490), though there `l` is constrained by `validate_map` to `all_participant_indexes`, so it is safe; the blame path lacks this guard.

### Impact Explanation
A single malicious or Byzantine participant (or any party submitting a blame accusation to a non-member `AdditionalBlameMachine`) can send one crafted blame message naming an out-of-range `sender` index and crash every node that evaluates it. In a threshold DKG this aborts key generation / recovery handling at the blame stage, denying completion of the protocol and, in a deployment, panicking the signing/validator process — directly analogous to the reference "all orderers break down immediately on receiving a constructed message" impact. This is more than a rejected message: it is a process-level panic, so severity is Medium (availability loss requiring restart; no key material is compromised, and only one faulty sender is needed).

### Likelihood Explanation
High reachability: the panic requires no collusion and no valid cryptographic material — only a blame accusation carrying a `Participant` value `> n`, which is trivially constructible since `Participant` accepts any non-zero `u16`. The only preconditions are that the victim runs the PedPoP blame path (during or after a DKG) and that the blame caller passes the peer-supplied `sender`/`recipient` through unchecked, which the API contract invites ("determine the faulty party" for arbitrary accusations). The main caveat is integration-dependent: the library trusts the caller to hand it the indices from an authenticated accusation, so exploitability assumes blame messages are evaluated as received rather than pre-filtered.

### Recommendation
In `blame_internal`, validate `sender` and `recipient` before use: reject/return a deterministic fault outcome (e.g., blame the accuser, or return an error) when either index is not a key of `self.commitments`. Concretely, replace `self.commitments[&sender]` with a `self.commitments.get(&sender)` check, and similarly ensure `decrypt_with_proof` does not index maps by the unvalidated `sender`/`recipient`. Additionally, because `blame` currently returns `Participant` rather than `Result`, consider adding a `try_blame` API returning `Result<Participant, PedPoPError>` so malformed accusations cannot panic at all.

### Proof of Concept
```rust
// crypto/dkg/pedpop context: n participants completed round 2, yielding
// BlameMachine<C> (or a third-party constructs AdditionalBlameMachine::new(context, n, msgs)).
// Attacker submits a blame accusation naming a nonexistent sender:

let evil_sender = Participant::new(n + 1).unwrap(); // valid Participant, not in 1..=n
let recipient   = Participant::new(1).unwrap();

// Any EncryptedMessage bytes; the panic occurs on `self.commitments[&sender]`
// at crypto/dkg/pedpop/src/lib.rs:599 before share validation concludes.
blame_machine.blame(evil_sender, recipient, msg, None);
// => panics: "no entry found for key" (HashMap Index on missing Participant(n+1))
```
The same crash is reachable via `AdditionalBlameMachine::blame` for a non-member evaluator, requiring only the `n` commitment messages plus one crafted accusation.

Note: I did not verify whether `encryption.decrypt_with_proof` (called earlier in `blame_internal`, line 582) also panics on unknown indices; if it does, the crash triggers there first — either way the path is unchecked. I also could not fully trace the Serai coordinator's blame-message plumbing to confirm end-to-end delivery, which is the main open question on real-world reachability.
