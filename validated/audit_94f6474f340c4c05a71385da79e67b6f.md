## Title
Any git remote can spoof a `WWW-Authenticate: realm="GitHub"` header to force GitHub Desktop into an unrequested Enterprise sign-in/OAuth flow bound to an attacker-controlled origin - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The Cally bug let the contract *owner* unilaterally re-classify a security-relevant parameter (`feeRate`) at redemption time, after the counterparty had already committed funds, silently redirecting value that should have gone to the seller. The Desktop analog is `getEndpointKind()` in the credential-helper trampoline: it classifies an arbitrary remote host as a trusted "enterprise" (GitHub) endpoint purely by trusting a `WWW-Authenticate` header value that the *remote server itself* supplies during a routine `fetch`/`clone`/`pull`/`push`/submodule operation. Because the classification decision is made from attacker-controlled response data at request time (analogous to a mutable, unilaterally-set "fee rate" evaluated at settlement), the user's credential-helper flow can be silently redirected toward treating an untrusted host as if it were a legitimate GitHub Enterprise server.

### Finding Description
`getEndpointKind()` decides how the trampoline credential helper should respond to a `git credential fill` request: [1](#0-0) 

```
  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
```

The `wwwauth[...]` entries in `cred` are populated straight from stdin fields that git's credential protocol forwards, which in turn come from the actual HTTP response headers the remote server (or any proxy/MITM sitting on the connection path) chooses to send. Nothing in this code path verifies that the header actually originates from a GitHub product, checks the TLS certificate, or checks against a known/registered GHE hostname — it is a bare substring match on attacker-suppliable text.

This classification directly controls the interactive sign-in behavior in `getCredential()`: [2](#0-1) 

If `endpointKind !== 'generic'` and no existing account matches the URL's endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)` using the **attacker's own host** as `endpoint`: [3](#0-2) 

```
public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
  return new Promise<Account | undefined>(async resolve => {
    ...
    const { hostname, origin } = new URL(endpoint)

`setSignInEndpoint(origin)` binds the global sign-in/OAuth flow to whatever `origin` the remote chose to report, i.e., the attacker's own server, and pops the standard "Sign in to your GitHub Enterprise instance" dialog mid-way through what the user believed was a normal `git fetch`/`clone`/`pull`/`push` or submodule update.

### Impact Explanation
- The corrupted value is the credential-helper's trust classification of the remote endpoint (`endpointKind`), which should only ever be derived from a hostname the user explicitly trusts (an added Account/Enterprise endpoint), not from data returned by the party being authenticated to.
- Existing guards don't stop this: there is no allow-list check, no TLS/host verification, and no requirement that the URL match any previously configured GHE endpoint before triggering `beginEnterpriseSignIn`/`setSignInEndpoint`.
- Practical effect: an attacker who controls a git remote (or sits as a proxy/MITM on the connection, one of the explicitly allowed attacker positions) can force GitHub Desktop to surface an unsolicited GitHub Enterprise sign-in/OAuth dialog bound to the attacker's origin during any routine network git operation, including transparently through a submodule fetch triggered by cloning/pulling someone else's repository (`buildSubmoduleDiff`/`updateSubmodulesAfterOperation` reuse the same `envForRemoteOperation`/trampoline plumbing). This matches the "unauthorized OAuth or account binding" impact category: the user is coaxed into initiating an authentication/OAuth handshake against an origin they never intended to trust, and any credentials or tokens they subsequently enter go directly to the attacker's server.

### Likelihood Explanation
This requires no local access, no admin rights, and no pre-existing malware — only that the user perform an ordinary `fetch`, `clone`, `pull`, `push`, or submodule update against a repository/remote the attacker controls (or a network position that can inject the response header). It fits squarely in the allowed threat model ("attacker controls ... a git remote/proxy response") and needs no unnatural extra steps by the victim beyond normal Desktop usage.

### Recommendation
Do not let a self-reported `WWW-Authenticate` realm string alone elevate an arbitrary host to "enterprise" trust status. At minimum:
- Require the host to match a previously known/added GitHub/GHE endpoint (or a user-approved allow-list) before treating a `realm="GitHub"` response as trustworthy.
- Independently corroborate the claim (e.g., via `isGitHubHost()`'s API probe, which already exists later in the same function) rather than short-circuiting on the header value alone.
- If an unrecognized host claims to be GitHub via headers, surface it as an explicit warning/confirmation ("This unfamiliar server claims to be GitHub Enterprise — do you want to sign in?") instead of silently launching the standard sign-in/OAuth UI.

### Proof of Concept
1. Attacker sets up a git server (e.g., `https://evil.example.com/foo.git`) or a proxy in the request path.
2. Victim adds `https://evil.example.com/foo.git` as a submodule URL in a repository they publish, or victim simply clones/fetches from `evil.example.com` directly.
3. When GitHub Desktop performs the fetch/clone (via `envForRemoteOperation` → trampoline → `git credential fill`), the attacker's server responds to the HTTPS authentication challenge with `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as a `wwwauth[0]=...` field to the credential helper trampoline; `getEndpointKind()` returns `'enterprise'` for `evil.example.com`.
5. Since no account matches `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`, which calls `dispatcher.beginEnterpriseSignIn()` and `dispatcher.setSignInEndpoint('https://evil.example.com')`, opening Desktop's normal Enterprise sign-in dialog pointed at the attacker's origin in the middle of an otherwise ordinary git operation.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }
```
