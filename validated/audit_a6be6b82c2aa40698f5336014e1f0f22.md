### Title
Reward-per-token accounting lets a same-block flash-locker skim a pro-rata share of another user's forfeited MGP - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`_queueNewRewardsWithoutTransfer` distributes `forfeitAmount` across `totalStaked()` (i.e. `vlMGP.totalSupply()`) at the moment the forfeiture is booked, with no time-weighting or vesting for newly added stake. Because `VLMGP._lock` synchronously calls `MasterMagpie.depositVlMGPFor`, which increases `totalStaked()` and syncs `userRewardPerTokenPaid` for the depositor *before* the increase, an attacker can lock immediately ahead of a victim's forfeiting claim (front-run) and then call `getReward`/`getRewards` to harvest a pro-rata share of the forfeited MGP without having accrued any stake-time.

### Finding Description
- `VLMGP._lock` (VLMGP.sol:461-470) calls `MasterMagpie.depositVlMGPFor` synchronously, which in `_deposit` (MasterMagpie.sol:482-505) calls `_harvestBaseRewarder` **before** `user.amount` is incremented. This means the attacker's `userRewardPerTokenPaid` is set to the *pre-forfeiture* `rewardPerTokenStored` value, while their balance becomes visible in `totalStaked()` (`vlMGP.totalSupply()`, vlMGPBaseRewarder.sol:137-139) immediately after (`VLMGP.sol:468`, `totalAmount += _amount`). [1](#0-0) [2](#0-1) 

- When a victim's forfeiting claim is processed shortly after (via `_sendReward` or `queueMGP`), `_queueNewRewardsWithoutTransfer` spreads `forfeitAmount` over the current `totalStaked()`, which now includes the attacker's freshly locked balance: [3](#0-2) 

- The attacker's earned amount is computed purely from current `balanceOf(_account)` and the delta in `rewardPerTokenStored` since their last sync — there is no minimum holding duration or snapshot mechanism: [4](#0-3) [5](#0-4) 

- The forfeited reward token distributed here is the raw MGP token (`address(vlMGP.MGP())`, see `queueMGP`/`_sendReward`), which is sent directly via `IERC20(_rewardToken).safeTransfer` in `_sendReward` — **not** re-locked. So the attacker does not need to wait through the `coolDownInSecs` unlock cycle (`VLMGP.startUnlock`/`unlock`) to realize the gain; they only need to call `getReward`/`getRewards` on `vlMGPBaseRewarder` after the forfeiture event, while their capital can remain locked (or later be unwound through the normal cooldown process independent of the reward capture). [6](#0-5) [7](#0-6) 

No existing modifier prevents this: `nonReentrant` and `whenNotPaused` don't address time-weighting, and `updateReward`/`updateRewards` only sync the accumulator, they don't gate eligibility by holding duration.

### Impact Explanation
This allows an unprivileged attacker to capture unclaimed yield (forfeited MGP) that should accrue to genuine, longer-term lockers, diluting their expected rewards. This matches the Immunefi impact class "theft of unclaimed yield" — a real, quantifiable, repeatable diversion of funds away from legitimate stakers, though it does not cause insolvency or permanently freeze funds (the diluted legitimate stakers still get their MGP-locked/staked capital back; they only lose their expected share of that particular forfeiture event).

### Likelihood Explanation
- Requires only capital to lock MGP (no privileged role), and mempool visibility to front-run a pending claim/forfeiture transaction (e.g., another user's `getReward`, `getRewards`, or a manager's `queueMGP` call) — feasible via standard MEV/front-running techniques on public mempools.
- Repeatable any time a sizeable forfeiture event is anticipated; the larger the attacker's flash-locked stake relative to `totalStaked()`, the larger the skimmed share.
- The attacker's capital is temporarily committed (locked in vlMGP, subject to `coolDownInSecs` before withdrawal of principal), but the *harvested reward* (forfeited MGP) is immediately transferable without any lock, so the exploit's profit is realized instantly while principal risk is limited to a lockup delay, not loss.

### Recommendation
Introduce a minimum holding/vesting period (or a checkpoint prior to the current block) before newly deposited stake becomes eligible for a pro-rata share of already-realized forfeiture/reward events — e.g., snapshot `totalStaked()` and eligible balances prior to the block in which the reward is queued, or apply a time-weighted average balance instead of instantaneous balance when computing `earned()`. Alternatively, require deposits to be synced with a delay (e.g., rewards accrued in the deposit block excluded from the new depositor's earned calculation) similar to a "reward exclusion window" pattern used in other Convex/Synthetix-style forks to block flash-deposit sniping.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, MGP token mocks; set `coolDownInSecs` to a nonzero value.
2. Victim locks a large amount of MGP over time so their `getRewardablePercentWAD` degrades (simulate lock expiry so `_calExpireForfeit` yields a non-trivial `forfeitAmount`).
3. In the same block/tx ordering:
   a. Attacker calls `VLMGP.lock(largeAmount)` (front-run tx) — assert `vlMGPBaseRewarder.userRewardPerTokenPaid(MGP, attacker)` is synced to the pre-event `rewardPerTokenStored`.
   b. Victim (or a manager via `queueMGP`) triggers the forfeiting claim, causing `_queueNewRewardsWithoutTransfer` to increase `rewardPerTokenStored` for the MGP reward token, using `totalStaked()` that includes attacker's new lock.
   c. Attacker immediately calls `getReward`/`getRewards` on `vlMGPBaseRewarder` (back-run tx) and receives MGP.
4. Assert: `attacker's received MGP amount ≈ forfeitAmount * attackerBalance / totalStaked()` at the time of the forfeiture, despite attacker having held stake for effectively zero block-time before the event, and compare to the "fair" outcome where attacker held the position for zero elapsed epochs — demonstrating disproportionate yield capture relative to contribution.

    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }
