### Title
`internal_withdraw` RPC bypasses the aggregator-authorization check enforced by `withdraw`, allowing unauthenticated broadcast of operator-funded payout transactions - (File: core/src/rpc/operator.rs)

### Summary
The gRPC method `withdraw` on the operator requires an aggregator-issued ECDSA verification signature before funding and broadcasting a payout transaction on behalf of a Citrea withdrawal [1](#0-0) . The sibling method `internal_withdraw` performs the exact same privileged action (parsing withdrawal parameters and calling `self.operator.withdraw(...)`, which funds and broadcasts a real Bitcoin payout transaction from the operator's wallet) but has no such check and no test-only guard, unlike other `internal_*` methods in the same file [2](#0-1) .

### Finding Description
`ClementineOperator::withdraw` is the intended entry point for triggering an operator-funded payout. It gates the call behind an aggregator-signed ECDSA verification signature when `aggregator_verification_address` is configured, rejecting the call with `BridgeError::ECDSAVerificationSignatureMissing` or `InvalidECDSAVerificationSignature` otherwise [1](#0-0) .

`internal_withdraw`, defined immediately above it, parses the same `WithdrawParams` and calls the identical `self.operator.withdraw(...)` business logic, but performs none of the verification-signature checks present in `withdraw` [2](#0-1) . Contrast this with `internal_finalized_payout` in the same file, which is explicitly restricted with `if !cfg!(test) { return Err(Status::permission_denied(...)) }` to prevent it from being reachable outside test builds [3](#0-2) . `internal_withdraw` has no equivalent restriction, so in a production (non-test) build it remains a reachable, state-changing/broadcasting RPC that performs the operator's own on-chain fund-fronting action (`Operator::withdraw`, which verifies the user's payout signature, checks profitability, funds the raw tx via the operator's wallet, and returns a signed transaction ready to be broadcast) [4](#0-3) .

This is the reachable analog of the report's underlying "check bypass on privileged action" theme: the `withdraw` binding (aggregator-authorized payout funding == the only sanctioned path to spend the operator's fee/collateral funds fronting a withdrawal) is broken because `internal_withdraw` reaches the same fund-committing logic without the authorization gate that `withdraw` enforces.

### Impact Explanation
Any caller reaching `internal_withdraw` (any party who possesses a valid user withdrawal signature — which per the Citrea withdrawal flow is public/known off-chain to the withdrawing user, not secret to the aggregator) can trigger the operator to fund and sign a payout transaction without the aggregator's verification-signature authorization that is supposed to gate which payouts a given operator instance will front. This matches the impact category of "an unauthenticated state-changing or broadcasting call" (High), since it lets an unprivileged caller invoke the operator's fund-committing withdrawal logic through a side door that skips the deployment's configured authorization control.

### Likelihood Explanation
Likelihood depends on whether `internal_withdraw` is exposed on the same gRPC service surface in production deployments (i.e., not feature-gated at compile time or access-controlled at the network layer). The code as written contains no `cfg!(test)` or similar guard on this specific handler, unlike its neighboring `internal_finalized_payout`, which strongly suggests this is an oversight rather than an intentional test-only method that was simply forgotten to be locked down.

### Recommendation
Add the same authorization check to `internal_withdraw` that exists in `withdraw` (verify the aggregator's ECDSA `verification_signature` against `aggregator_verification_address` before calling `self.operator.withdraw(...)`), or, if `internal_withdraw` is meant to be test-only (as its naming and the pattern of other `internal_*` RPCs suggest), gate it with the same `if !cfg!(test) { return Err(Status::permission_denied(...)) }` check used in `internal_finalized_payout`.

### Proof of Concept
1. Deploy an operator node with `aggregator_verification_address` configured (intended to require aggregator-authorized payouts).
2. Obtain a valid user signature for a pending Citrea withdrawal (obtainable off-chain by the withdrawing user, not secret).
3. Call the operator's `internal_withdraw` gRPC method directly with the withdrawal parameters and user signature, omitting any aggregator verification signature.
4. Observe that `internal_withdraw` succeeds and returns a signed payout transaction — the same result that `withdraw` would only produce after successfully validating the aggregator's verification signature — demonstrating the authorization check is bypassed via the sibling RPC.
