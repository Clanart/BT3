## Finding: Webhook HMAC Verification Does Not Bind the Signed Payload to the `Shop Domain` Header, Enabling Cross-Shop Forged Webhooks

### Summary
This maps to the same bug class as the linked report: a cryptographic authentication step exists, but the signed data does not include the identifier that is later used to decide *whose* account/state is affected. In `hbridge/operations.rell`, the EVM signature didn't bind to the FT4 account. In this repo, the webhook HMAC signature validated by `ShopifyApp::PayloadVerification#hmac_valid?` only covers the raw request body — it never includes the `X-Shopify-Shop-Domain` header that downstream code (`ShopifyApp::WebhookVerification#shop_domain`, and generated jobs like `AppUninstalledJob`) trusts to decide which shop record to mutate.

### Finding Description
`hmac_valid?` computes/validates the HMAC strictly over `request.raw_post`: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` only checks that HMAC, and `shop_domain` is read straight from the unauthenticated header, with no cross-binding to the signed body: [2](#0-1) 

Generated job templates then trust this header-derived value to look up and mutate shop-specific records. For example, `AppUninstalledJob` uses the `shop`/`shop_domain` value (sourced from the webhook headers via `ShopifyAPI::Webhooks::WebhookHandler`) to find and **destroy** a shop record: [3](#0-2) 

Because the HMAC is a function of body content only (`HMAC(secret, raw_post)`), any two requests with the same body and the same app secret produce the same valid HMAC — regardless of which shop's `X-Shopify-Shop-Domain` header accompanies it. This is structurally identical to the reported bug: the signature authenticates the payload/message but never binds it to the specific account (FT4 account there, shop domain here) that authorization decisions are keyed off of.

### Impact Explanation
An attacker who legitimately installs the app on a shop they control (a completely ordinary, unprivileged action — install then uninstall) obtains one authentic `(body, HMAC)` pair for a webhook whose body content is fixed/predictable (e.g., an empty or near-empty payload for `app/uninstalled`, or any webhook topic whose body they fully control/know). They can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `verify_request` will accept it because it never checks the header against the signed body, and the downstream job (`AppUninstalledJob`) will resolve `Shop.find_by(shopify_domain: <victim_domain>)` and destroy the victim's installation record/access token — a cross-shop state change triggered from an unrelated merchant's own valid credentials.

### Likelihood Explanation
Requires only that the attacker be an "unrelated merchant" who can install/uninstall the target app on any shop of their own to harvest one valid signature — no leaked secrets, no host-operator access, and no dependency-only conditions. The vulnerable pattern (`hmac_valid?` / `shop_domain`) is the officially documented way to build custom webhook controllers and is the exact code used by the gem's generators, so it is broadly reachable in any app built on this gem.

### Recommendation
Bind the shop domain (and other routing-relevant headers such as `X-Shopify-Webhook-Id`/topic) into the HMAC-verified data, or otherwise cryptographically tie the `X-Shopify-Shop-Domain` header to the authenticated payload before using it for lookups/mutations — mirroring the report's recommendation to include the linked account identifier inside the signed message rather than relying on out-of-band, unauthenticated context.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggers a webhook topic with a fixed/known body (e.g., an empty-body event), and captures the resulting `X-Shopify-Hmac-Sha256` value from Shopify's legitimate call.
2. Attacker sends a POST to the app's webhook endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` succeeds because only the body is checked.
4. `AppUninstalledJob#perform` (or an app's custom webhook job) is invoked with `shop_domain: "victim-shop.myshopify.com"`, causing `Shop.find_by(shopify_domain: ...).destroy` on the victim's record. [4](#0-3)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
```
