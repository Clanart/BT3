### Title
Unbounded `order.inputs` array lets an order-placer permanently lock their own escrow (and block settlement/refund) via gas-exhausting `_withdraw` loop - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`placeOrder()` accepts an `Order` with an attacker-controlled `inputs` array and enforces no upper bound on its length — the only guard is `if (order.inputs.length == 0) revert InvalidInput()` [1](#0-0) . That same array length propagates unchanged into every downstream settlement/cancellation path (`_withdraw`, `withdraw`) which iterates over `body.tokens` with a plain `for` loop and does one external `.call`/`safeTransfer` per element [2](#0-1)  and equivalently in the Tron/legacy contract [3](#0-2) . This is the same broken invariant as the GTE-perps report: an unbounded, attacker-sized array is looped over in a fund-moving function with no per-call cap or pull-based/paginated design.

### Finding Description
1. A user calls `placeOrder(order, graffiti)` with `order.inputs` containing an arbitrarily large number of distinct token entries (e.g. hundreds/thousands of cheap self-deployed ERC-20s, or even native-token duplicate entries). `placeOrder` only checks `inputs.length == 0`, never an upper bound [1](#0-0) .
2. `placeOrder`'s own escrow-transfer loops over `inputsLen` already spend O(n) gas at order-placement time, so the user can size `n` right up to the source chain's block gas limit for the initial transaction [4](#0-3) .
3. Later, when a solver fills the order (`fillOrder` → `withdraw`/`_withdraw`) or the order is cancelled/refunded, the *same* `inputs` length is looped over again on the source chain to release the escrow, this time inside a settlement transaction that must also decode a cross-chain message, verify a proof/commitment, and perform per-token external transfers [2](#0-1) .
4. Because the additional gas overhead of proof verification, dispatch bookkeeping, and dispatch-context is added on top of the token-transfer loop, the same `inputs.length` that fit inside a plain transfer transaction can push the settlement/cancellation transaction over the block gas limit, making `_withdraw` un-executable in a single transaction forever.
5. Since `_withdraw`/`withdraw` are the *only* code paths that release escrowed input tokens (both the happy-path fill and the refund/cancel paths funnel through them), an order whose `inputs.length` is large enough to blow the gas limit during withdrawal has its escrow permanently stuck — neither the solver can be paid nor the user refunded.

### Impact Explanation
This is not a generic "gas DoS on a shared queue" (which the impact gate explicitly excludes) — it is a fund-lock caused by a single unprivileged user's own order data becoming un-processable by the very custody-release function (`_withdraw`/`withdraw`) that must run to unlock escrowed tokens. Because escrow release, refund, and settlement all share this one gas-unbounded loop, an attacker (or even an honest user misconfiguring their own order) can strand their own escrowed funds irrecoverably, and if the loop bound is close to the destination/source chain gas limit, griefing becomes possible against any order that shares that gas budget with proof verification and dispatch overhead added on top. This matches the "stealing or loss of funds" bounty category because tokens become permanently unrecoverable, not merely delayed.

### Likelihood Explanation
Likelihood is moderate-to-high: `placeOrder` is a fully public, unprivileged entry point, ERC-20 tokens are cheap and trivial to deploy on EVM chains in bulk, and no governance, relayer, or prover assumption is required — the attacker (or unwitting user) only needs to control the `Order.inputs` array they submit themselves. The only friction is that they must pay gas proportional to `inputsLen` at `placeOrder` time as well, but this cost is linear and bounded by the source-chain block gas limit, unlike the downstream `_withdraw` transaction, which layers additional proof-verification/dispatch overhead on top of the same loop, making the crossover point reachable.

### Recommendation
- Enforce a hard cap on `order.inputs.length` (and `output.assets.length`) in `placeOrder`, sized so that `_withdraw`'s per-token transfer loop plus the largest possible calldata/proof-verification overhead in `onAccept`/`fillOrder`/`cancelOrder` cannot approach the block gas limit on any supported destination chain.
- Alternatively, decouple escrow release from a single atomic loop: record per-token withdrawal state and allow `withdraw` to be called incrementally/per-token (or in bounded batches) so that an oversized `inputs` array degrades to multiple cheaper transactions instead of becoming permanently un-executable.

### Proof of Concept
1. Deploy N inexpensive ERC-20 tokens (e.g., N = 300–500, tuned to the target chain's gas limit) and approve `IntentGatewayV2` for each.
2. Call `placeOrder(order, graffiti)` with `order.inputs` containing one `TokenInfo` entry per deployed token, each with a minimal nonzero amount, and a single valid `output` asset — this succeeds because only `inputs.length == 0` is checked [1](#0-0) .
3. A solver calls `fillOrder` on the destination chain (same-chain or cross-chain) providing correct outputs; on the source chain, the settlement path (`onAccept` → `withdraw`/`_withdraw`) attempts to iterate the full `inputs` array plus proof/decoding overhead and runs out of gas / exceeds the block gas limit, causing the transaction to always revert.
4. Because `withdraw`/`_withdraw` is the sole function that decrements `_orders[commitment][token]` and transfers tokens out (for both fill and refund/cancel paths), the escrowed tokens for this order can never be released — the user's funds and the solver's payout are permanently locked in the `IntentGatewayV2` contract.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
