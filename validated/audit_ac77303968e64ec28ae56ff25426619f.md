### Title
Unbounded loop in `object::root_owner()` lets an object-ownership cycle permanently brick code-object publish/upgrade and lazy module self-init - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks an object's ownership chain with no depth bound, unlike every other cycle-aware traversal function in the same file (`owns`, `verify_ungated_and_descendant`), which both cap iterations at `MAXIMUM_OBJECT_NESTING` and abort with `EMAXIMUM_NESTING`. `root_owner()` is used on the publish path: `code::publish_package` calls it to record the deploy owner for lazy self-init, and `init::assert_may_self_initialize` calls it every time an object-hosted module tries to self-initialize. Because ordinary, individually-valid `object::transfer` calls can be used to construct a 2-object ownership cycle, any account can turn its own code object into one whose `root_owner()` never terminates, permanently breaking `code::publish_package` (upgrade/freeze) and `init::internal_maybe_initialize` (module self-init) for that object.

### Finding Description
`root_owner()`: [1](#0-0) 

has no cycle guard, in contrast to `owns()`: [2](#0-1) 

and `verify_ungated_and_descendant()`: [3](#0-2) 

both of which explicitly track `count` against `MAXIMUM_OBJECT_NESTING` because "objects may have cyclic dependencies."

`root_owner()` is invoked directly on the code-publish path in `code::publish_package`: [4](#0-3) 

and on the lazy module self-init gate: [5](#0-4) 

`transfer_raw` (backing entry `transfer`/`transfer_to_object`) only validates that the *acting signer* currently, transitively owns the object being moved at call time; it never checks the resulting ownership graph for cycles: [6](#0-5) 

Because each transfer is validated independently against the *pre-transfer* state, a user who directly owns two objects X and Y can:
1. Transfer X to Y's address (valid: `verify_ungated_and_descendant` trivially passes since X.owner == user).
2. Transfer Y to X's address (valid: same reasoning, Y.owner == user at that time).

After step 2, `ObjectCore[X].owner == Y` and `ObjectCore[Y].owner == X`, forming a 2-cycle. Both `owns()` and `verify_ungated_and_descendant()` would safely detect this and abort with `EMAXIMUM_NESTING`, but `root_owner()` has no such protection and will loop `while (is_object(obj_owner))` forever between X and Y.

### Impact Explanation
Any subsequent call that reaches `root_owner()` for X or Y deterministically runs out of gas rather than returning or aborting cleanly:
- `code::publish_package` (and therefore `object_code_deployment::publish`/`upgrade`) permanently fails whenever `features::is_lazy_module_initialization_enabled()` is on and the target address is one of the cyclic objects — the code object can never again be upgraded, have new packages published, or be frozen.
- `init::internal_maybe_initialize`, used by the compiler-generated lazy self-init pattern, will OOG on every call for any module deployed to that object, bricking every entry function of that module that depends on self-init having run.

This corrupts a code-safety invariant on the publish path: the object-ownership traversal that gates who may (re)publish/upgrade code and who may trigger module self-init is not well-founded, so a reachable, legitimately-constructed state (an ownership cycle) makes the "protected state mutation" (publish/upgrade/freeze/self-init) permanently unreachable for that code object. This is a availability/soundness break specific to the publish/init invariant (not a generic network-level DoS), matching the "module-init... failure that reaches protected state mutation" pivot.

### Likelihood Explanation
The precondition (owning two objects and issuing two ordinary `object::transfer` calls) requires no special privilege beyond owning the objects and is achievable by any account, including on an object it intends to use for code deployment. `LAZY_MODULE_INITIALIZATION` and `OBJECT_CODE_DEPLOYMENT` are both listed as default-enabled feature flags: [7](#0-6) [8](#0-7) 
so the vulnerable code path is live on networks with these flags active. The likelihood of accidental triggering is low, but the likelihood of a deliberate, low-cost griefing/self-DoS (or sabotage of a shared object whose ownership the attacker controls before handing it off) is high given how simple the cycle construction is.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING`-bounded loop guard used in `owns()`/`verify_ungated_and_descendant()` to `root_owner()`, aborting with `EMAXIMUM_NESTING` (or a dedicated error) if the chain exceeds the bound instead of looping unboundedly. Additionally, consider rejecting transfers that would introduce ownership cycles, or bounding cycle depth checks at transfer time so `root_owner()`'s precondition (an acyclic, bounded-depth chain) actually holds.

### Proof of Concept
Move-level pseudocode reproducing the cycle (analogous to existing `object.move` tests, e.g. `verify_ungated_and_descendant`'s nesting tests):
```move
// user owns both X and Y initially
let x_ref = object::create_object(@user);
let y_ref = object::create_object(@user);
let x = object::object_from_constructor_ref<ObjectCore>(&x_ref);
let y = object::object_from_constructor_ref<ObjectCore>(&y_ref);
let x_addr = object::address_from_constructor_ref(&x_ref);
let y_addr = object::address_from_constructor_ref(&y_ref);

// Step 1: X -> owned by Y (valid: user directly owns X)
object::transfer(&user_signer, x, y_addr);

// Step 2: Y -> owned by X (valid: user still directly owns Y)
object::transfer(&user_signer, y, x_addr);

// Now ObjectCore[x_addr].owner == y_addr and ObjectCore[y_addr].owner == x_addr.
// Any subsequent call to object::root_owner(x) or root_owner(y) loops forever
// (bounded only by out-of-gas), e.g. via code::publish_package(x_addr, ...) or
// any entry function on a module at x_addr/y_addr that calls
// init::internal_maybe_initialize.
```
This can be validated against the existing `init.move` test module's `record_current_owner`/`assert_may_init` helpers by first forming this cycle on an object address, then invoking `code::publish_package` or `init::internal_maybe_initialize` against it and observing the transaction fails with `OUT_OF_GAS` instead of a bounded `EMAXIMUM_NESTING`-style abort.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

            return true

            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            current_address = object.owner;
        };
