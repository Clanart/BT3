Confirmed: `filepath` in the `x-github-desktop://openrepo?...&filepath=...` deep link is fully attacker-controlled querystring text, with no path-traversal sanitization applied in `parseAppURL` [1](#0-0) , and is later passed straight into `resolveWithin(repository.path, filepath)` in `dispatcher.ts` [2](#0-1) .

### Title
Directory-boundary check uses unbounded `startsWith` prefix comparison, allowing sibling-directory escape via deep-link `filepath` - (File: app/src/lib/path.ts)

### Summary
`resolveWithin`/`_resolveWithin` is GitHub Desktop's central "stay inside the repository root" guard, used to validate untrusted, attacker-influenced relative paths (deep-link `filepath`, Copilot conflict-resolution paths, conflict-context file paths) before touching the filesystem. Its final containment check is a bare string-prefix test that is not anchored to a path-separator boundary, so it is satisfied by any sibling directory whose name happens to start with the root directory's name — e.g. `/Users/victim/Documents/GitHub/repo-evil` incorrectly passes as "within" `/Users/victim/Documents/GitHub/repo`. This is the same bug class as the reported `lp_value_after_swap_and_fee >= lp_value_before_swap` invariant: a boundary/invariant check that should be strict is implemented as a loose (non-strict) comparison, letting a crafted input slip through a guard that looks correct at a glance.

### Finding Description
The containment check is:
```ts
// app/src/lib/path.ts:66-71
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

`realRoot` has no guaranteed trailing separator, so `String.prototype.startsWith` treats any path whose textual prefix matches `realRoot` as "inside" the root — including a completely different, sibling directory (e.g., `repo` vs `repo-evil`, or `repo` vs `repo2`). Because `resolved` is computed with `path.resolve(root, relative)`, an attacker who controls `relative` (the `pathSegments`) can use `..` traversal to leave `root` and land in a sibling directory whose name is a superstring of `root`'s basename, and the function will still return that path as "resolved"/valid instead of `null`.

This exact function is the sole containment guard used for:
- Deep-link initiated file reveal: `openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)` where `filepath` comes unsanitized from the `x-github-desktop://openrepo` URL query string, then calls `shell.showItemInFolder(resolved)` [2](#0-1) .
- Copilot conflict resolution content writes: `resolveWithin(repository.path, resolution.path)` gates a `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` call [4](#0-3) .
- Copilot conflict context file reads: `resolveWithin(workingDirectory, file.path)` gates `readFile(absolutePath, 'utf8')` [5](#0-4) .

None of these call sites add an extra separator-boundary check on top of `resolveWithin`'s result — they all trust that a non-null return means the path is genuinely inside the repository.

The existing unit tests for `resolveWithin` only cover traversal-then-return-to-root and symlink-escape cases; there is no test for the sibling-directory-name-prefix scenario [6](#0-5) , so this gap is unexercised and unguarded.

### Impact Explanation
If a user has two repositories cloned side by side where one directory name is a prefix of another (a very common layout, e.g. `Documents/GitHub/repo` and `Documents/GitHub/repo-fork`, or Desktop's own default clone naming when a name collision occurs and a suffix like `-1`, `-2` is appended), a malicious deep link (`x-github-desktop://openrepo?url=...&filepath=../repo-fork/secret.txt`) or a crafted Copilot-conflict-resolution/API response path can cause Desktop to:
- Reveal a file outside the intended repository in Explorer/Finder (information disclosure of file existence/location), or
- Silently write attacker-supplied content into a file inside a different repository the user has open, corrupting what that user later commits and pushes — directly matching this bug class's "silent corruption of what the user commits or pushes" impact criterion.

### Likelihood Explanation
The `filepath` deep-link parameter requires only that the user click an attacker-supplied link — no local access, no malware, and no unusual manual steps, matching the "link the user clicks" attacker primitive. The precondition (a sibling directory whose name prefixes the target repository's directory name) is common given Desktop's default clone-to-`~/Documents/GitHub/<name>` behavior and its own collision-suffixing scheme. The Copilot conflict-resolution path is reachable from AI-agent-generated file paths that are used with `resolveWithin` before writes, tightening the practical exploitation surface further if that content can be influenced.

### Recommendation
Make the containment check strict by requiring the resolved path to either equal the root exactly or be nested strictly beneath it via a full path-separator boundary, e.g.:
```ts
const rootWithSep = realRoot.endsWith(Path.sep) ? realRoot : realRoot + Path.sep
return realResolved === realRoot || realResolved.startsWith(rootWithSep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory (`root` vs `root-evil`/`root2`) is correctly rejected by `resolveWithin`.

### Proof of Concept
1. Assume two repositories are cloned: `~/Documents/GitHub/repo` (open in Desktop) and `~/Documents/GitHub/repo-evil` (attacker's or unrelated repo containing `secret.txt`).
2. Attacker sends the victim a link: `x-github-desktop://openrepo?url=https://github.com/owner/repo&filepath=../repo-evil/secret.txt`.
3. User clicks the link; Desktop calls `openRepositoryFromUrl`, which invokes `resolveWithin(repo.path, '../repo-evil/secret.txt')` [7](#0-6) .
4. Inside `_resolveWithin`, `resolved = path.resolve('~/Documents/GitHub/repo', '../repo-evil/secret.txt')` = `~/Documents/GitHub/repo-evil/secret.txt`; `realResolved.startsWith(realRoot)` evaluates `'.../repo-evil/secret.txt'.startsWith('.../repo')` → `true`, so the function returns the path instead of `null` [8](#0-7) .
5. `shell.showItemInFolder(resolved)` reveals `secret.txt` from the unrelated `repo-evil` directory, even though it is outside the cloned repository the link claimed to target.

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
