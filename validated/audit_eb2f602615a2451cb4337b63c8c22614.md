### Title
EvmHost native-fee dispatch/fundRequest paths swallow Uniswap V2 ETH refunds, permanently locking user overpayment - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment and swap it for `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. The real UniswapV2Router02 refunds any unspent ETH (`msg.value - amounts[0]`) to `msg.sender` of the swap call — which is `EvmHost` itself, not the original caller of `dispatch`/`fundRequest`. None of these three functions capture the `amounts` return value or forward the leftover ETH back to `_msgSender()`, so any overpayment is trapped in the `EvmHost` contract with no code path to reclaim it.

### Finding Description
In `dispatch(DispatchPost memory post)`: [1](#0-0) 

the swap result is discarded and no refund logic follows. The identical pattern repeats in the GET variant: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

This is a direct local analog of the reported Sudoswap bug class: an external swap/purchase call that can return unused funds to the caller, but the wrapping function neither captures nor forwards that refund to the actual payer, causing silent fund loss for the end user.

The codebase demonstrates the correct pattern elsewhere, confirming this is an inconsistency/bug rather than intended design. `IntentGatewayV2.placeOrder` captures the swap's `amounts[0]`, decrements the tracked `msgValue` by the actual spend, and explicitly refunds the remainder to `msg.sender`: [4](#0-3) 

Likewise, the custom `UniV3UniswapV2Wrapper.swapETHForExactTokens` and `UniV4UniswapV2Wrapper.swapETHForExactTokens` (used as pluggable `uniswapV2` routers on chains lacking a native V2 deployment) explicitly compute `spent`/`refundETH` and send the difference back to `msg.sender`: [5](#0-4) [6](#0-5) 

But that refund lands on `EvmHost` (the caller of the router), and `EvmHost.dispatch`/`fundRequest` do not relay it onward to the user who supplied `msg.value`. There is no `receive()`/sweep function in `EvmHost` visible in the reviewed sections to let a user or governance reclaim this stranded ETH, so the value is effectively lost to the caller and stuck in the host contract.

### Impact Explanation
Any unprivileged user who calls `dispatch{value: msg.value}(post)`, `dispatch{value: msg.value}(get)`, or `fundRequest{value: msg.value}(...)` with `msg.value` even slightly above the exact amount needed to purchase `post.fee`/`get.fee`/`amount` units of `feeToken()` loses that excess permanently — no revert, no event, no way to recover it. Because the exact ETH cost of a Uniswap swap fluctuates with pool price between quote-time and execution-time, users following the documented "overpay slightly for safety" pattern (as demonstrated safe in `IntentGatewayV2`) will routinely lose funds when calling these `EvmHost` entry points directly. This is unauthorized loss of user funds via a public, permissionless bridge entrypoint.

### Likelihood Explanation
Likelihood is Medium: any direct caller of `IDispatcher(host).dispatch` or `fundRequest` with native payment must estimate the ETH-to-feeToken price off-chain (via `quote()` in `HyperApp.sol`) and typically adds slippage buffer, since `swapETHForExactTokens` reverts if underfunded — pushing users toward overpaying, which triggers the loss on every such call, not just an edge case.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` and refund the difference (`msg.value - amounts[0]`) to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`: [4](#0-3) 

### Proof of Concept
1. Compute `feeToken` cost off-chain via `HyperApp.quote(post)` (returns `getAmountsIn` estimate) and add a safety buffer, e.g. `estimatedEth * 105 / 100`, as is standard practice against price movement.
2. Call `IDispatcher(host).dispatch{value: bufferedEth}(post)` where `post.fee` is the desired relayer fee in `feeToken`.
3. Internally, `swapETHForExactTokens{value: bufferedEth}(post.fee, path, address(this), block.timestamp)` spends only `amounts[0] <= bufferedEth` and the Uniswap router refunds `bufferedEth - amounts[0]` to `EvmHost` (the caller).
4. `EvmHost.dispatch` never reads `amounts` nor forwards any ETH back to the original caller; the transaction completes successfully, `feeToken` fee is escrowed correctly, but the caller's overpaid ETH remains in `EvmHost`'s balance with no accounting or withdrawal path — confirmable by checking `address(host).balance` increased by exactly the unspent amount while the caller's balance decreased by the full `bufferedEth`.
