## Title
Diff shown for renamed files omits already-staged content, causing GitHub Desktop to commit/push content the user never reviewed — (`File: app/src/lib/git/diff.ts`)

### Summary
For files whose status is `AppFileStatusKind.Renamed`, `getWorkingDirectoryDiff` intentionally diffs the working tree against the **index**, not against `HEAD`, and the source comment explicitly documents that this omits "any changes already staged to the renamed file." [1](#0-0)  Despite this known gap in what is *shown*, the commit path for a fully-selected file (`DiffSelectionType.All`) does **not** derive the commit content from the diff the user reviewed — it stages whatever is currently on disk via `git update-index --add --remove`, i.e., the full working-directory content regardless of what the rendered diff displayed. [2](#0-1)  This creates a mismatch: the UI's diff (the artifact the user inspects before deciding to commit) can under-report the actual delta, while the eventual commit faithfully includes the un-shown content.

### Finding Description
`getWorkingDirectoryDiff` branches on file status:
- New/Untracked files: diffed with `--no-index` against `/dev/null`.
- Renamed files: diffed with no base ref (defaults to comparing the working tree file against the **index**), explicitly marked as "incorrect" in the code comment because it "won't show any changes already staged to the renamed file." [3](#0-2) 
- All other files: diffed against `HEAD`. [4](#0-3) 

When the user commits the renamed file with "select all" (`DiffSelectionType.All`), `stageFiles` does not apply the reviewed diff as a patch; it forcefully removes the old path and then runs `update-index --add --remove` on the new path, which stages the file's **current working-tree bytes** verbatim. [5](#0-4)  Only files with a *partial* selection go through `applyPatchToIndex`, which builds a patch from the same diff that was rendered. [6](#0-5) 

Consequently, if a renamed file's index entry already differs from what the rendered diff (index vs. working tree) suggests — for example, if the index for the new path was pre-populated with content different from `HEAD`'s version of the old path — the diff view can under-represent the true delta between `HEAD` and what will land in the commit, while the "commit all" action still commits the full working-directory content. The broken invariant is: *the diff the user reviews is not guaranteed to be the diff of what actually gets committed for renamed files.* Existing guards (the diff rendering, and the partial-selection patch application) do not cover the full-file/"select all" case, which bypasses the diff entirely and stages raw working-tree state.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user relying on the Desktop diff view to review changes to a renamed file before committing can be shown an incomplete or misleading diff (e.g., missing additions that were already staged in the index), yet the "Commit" action for that file will still push the full, unreviewed content upstream. This is particularly dangerous in a scenario where the working copy/`.git` state a user opens (e.g., a shared repository folder, or a repository state produced by tooling/hooks the user does not fully control before opening it in Desktop) has index content diverging from `HEAD` for a renamed path — the user could unknowingly commit and push content they never saw in the diff panel.

### Likelihood Explanation
The mismatch is triggered purely through normal Desktop usage (renaming a tracked file, having staged content differ from what's shown, then using "Select All" to commit) — no privileged access, malware, or unnatural steps are required. The code comment shows the Desktop maintainers were already aware of the discrepancy but treated it as an acceptable rendering limitation rather than a data-integrity issue in the commit path itself. [7](#0-6) 

### Recommendation
For renamed files, either (a) always compute the diff against `HEAD` (using a blob-diff of the old path's blob vs. the new path's working-tree content, as the code comment already suggests was considered), or (b) make the "select all" commit path apply the same diff that was rendered (as is already done for partial selections via `applyPatchToIndex`) so that what's shown and what's committed can never diverge.

### Proof of Concept
1. Create a repo, commit `foo` with content `line1`.
2. `git mv foo bar`.
3. Outside of Desktop, stage extra content into the index for `bar` that differs from the working tree (e.g., via a script/hook run before opening the repository in Desktop) so the index entry for `bar` diverges from `HEAD`'s `foo`.
4. Open the repository in GitHub Desktop; the Renamed file's diff (index vs. working tree, per `getWorkingDirectoryDiff`) does not surface the already-staged divergence from `HEAD`. [1](#0-0) 
5. Select "All" and commit — `stageFiles` stages the full working-directory content via `update-index --add --remove`, producing a commit whose actual diff from `HEAD` includes content never shown in the reviewed diff panel. [8](#0-7) 
6. The user pushes this commit, having reviewed an incomplete diff.

```typescript
export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)
```

```typescript
export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
}
```
