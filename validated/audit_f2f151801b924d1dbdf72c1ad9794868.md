## Title
`_fetchRefspec` bypasses the single-flight network-operation guard, letting a fork PR trigger a fetch that races and corrupts a concurrent push/pull/fetch - ([File: app/src/lib/stores/app-store.ts])

## Summary
GitHub Desktop serializes all network Git operations (`fetch`, `pull`, `push`) on a repository through a single `isPushPullFetchInProgress` flag so only one can run at a time. `_fetchRefspec`, the method used to fetch a pull request's ref when a user views/checks out a PR from a fork, explicitly does **not** go through that guard, so it can execute concurrently with a user-initiated push, pull, or fetch on the same working directory.

## Finding Description
`withPushPullFetch` is the mutual-exclusion mechanism that all push/pull/fetch entry points use to avoid concurrent network Git operations against the same repository: [1](#0-0) 

`_fetch`, `_fetchRemote`, and the pull/push flows all route through `withPushPullFetch`: [2](#0-1) 

However `_fetchRefspec` explicitly opts out of this protection, and the code comment states why: because it must be able to complete even while a PR-from-fork viewing flow needs it, regardless of any in-progress network operation: [3](#0-2) 

The underlying git call simply runs `git fetch <remote> <refspec>` directly against the repository's working directory: [4](#0-3) 

`fetchRefspec` is reachable from the renderer via `Dispatcher.fetchRefspec`: [5](#0-4) 

The attacker-controlled input here is the PR/fork's remote and refspec: PR metadata (head repo clone URL, head ref) comes straight from the GitHub API for a pull request opened by any external contributor to a public repo, and is used to construct the remote and refspec that get fetched, as seen in `_findPullRequestBranch` / `_checkoutPullRequest`: [6](#0-5) [7](#0-6) 

Because `git fetch` writes into the same repository's refs, packed-refs, and object database that a concurrently-running `push`/`pull` is reading from and writing to (`performPush`/`performPull` also call `fastForwardBranches`, `updateRemoteHEAD`, and `_refreshRepository` on the same repository), an attacker who authors a PR against a repository the victim has open in Desktop can cause the victim's own fetch/pull/push to race against the attacker-triggered `fetchRefspec`. This is the direct structural analog of the `Trader` bug: two operations that were designed to be mutually exclusive (matched orders vs. fetch/pull/push single-flight) can be forced to run concurrently by an attacker-influenced trigger, corrupting/interleaving the shared on-disk git state (refs, FETCH_HEAD, packed objects) that the victim's legitimate operation depends on. The `withPushPullFetch` guard exists specifically to prevent this class of interleaving, and `_fetchRefspec` is a documented, intentional gap in it.

## Impact Explanation
Two Git processes running against the same working directory/`.git` folder concurrently (one being `git fetch` on a fork ref, the other being a user's `git pull`/`git push`/`git fetch`) can race on git's own lock files (e.g. `.git/refs`, `packed-refs`, `FETCH_HEAD`), on Desktop-managed state updates (`fastForwardBranches`, `updateRemoteHEAD`, `_refreshRepository`), and on the app's own progress/refresh UI state. Depending on timing, this can silently corrupt what the app subsequently reports as committed/pushed state, cause a legitimate push/pull to fail or be denied (mirroring the "trader denied from trading" impact), or leave the repository's ref/remote-tracking state inconsistent — all triggerable by an attacker who merely opens a pull request against a repository the victim has cloned in Desktop.

## Likelihood Explanation
Exploitation requires: (1) the victim has the target repository open in Desktop and is actively pushing/pulling/fetching, and (2) the victim (or Desktop's own PR-preview UI) is concurrently viewing/checking out the attacker's PR, which triggers `_fetchRefspec`/`_findPullRequestBranch`. Both PR viewing and manual push/pull are common, ordinary Desktop usage patterns (no privileged access, no local file system tricks, no social engineering beyond opening a normal PR), so the precondition is plausible, though the race window is narrow and timing-dependent, making consistent exploitation non-trivial.

## Recommendation
Route `_fetchRefspec` through the same `withPushPullFetch` (or an equivalent per-repository mutex) guard used by `_fetch`/`_fetchRemote`/pull/push, queuing it rather than allowing it to run concurrently, and document/handle the case where a user's PR-view fetch must wait for the current network operation to complete instead of bypassing the lock.

## Proof of Concept
1. Attacker opens a pull request against a public repository that the victim has cloned in GitHub Desktop, with `head.repo`/`head.ref` pointing at attacker's fork.
2. Victim starts a `git push` or `git pull` in Desktop on that repository (`_performPush`/`performPull`, guarded by `withPushPullFetch`).
3. While that operation is in flight, the victim's Desktop UI (or the attacker driving the victim to look at the PR, e.g. via a shared "Open in Desktop" link) triggers `_checkoutPullRequest` → `_findPullRequestBranch` → `_fetchRemote`/`_fetchRefspec` for the attacker's fork ref.
4. Because `_fetchRefspec` does not check/set `isPushPullFetchInProgress`, its `git fetch` runs concurrently with the victim's in-flight push/pull against the same `.git` directory, racing on shared ref/lock state.

Note: I was unable to fully verify from the indexed code exactly which UI component auto-triggers `fetchRefspec`/`_findPullRequestBranch` without explicit user action (e.g. PR preview panel prefetching), since only `app-store.ts`, `git-store.ts`, `fetch.ts`, and `dispatcher.ts` references were indexed. Confirming the exact automatic-trigger UI path would benefit from a full repository checkout via a Devin session rather than the indexed snippets available here.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
