## Analysis

The Solidity report's broken invariant is: **a privileged trust value is hardcoded into the contract with no mechanism to rotate/revoke it if it is later compromised.** The closest real analog in this codebase is not an address, but a hardcoded **SSH host-key fingerprint** used to silently bypass the normal "unknown host" trust prompt for SSH-based git operations.

### Title
Hardcoded, non-revocable GitHub SSH host-key fingerprint silently auto-trusts SSH connections claiming to be `github.com`, bypassing the host-authenticity prompt - (File: `app/src/lib/trampoline/trampoline-askpass-handler.ts`)

### Summary
`handleSSHHostAuthenticity` in the trampoline askpass handler automatically answers `'yes'` (i.e., "trust this host") to SSH's "unknown host" prompt whenever the reported host is `github.com`, the key type is `RSA`, and the fingerprint matches a single string literal baked into the source code. [1](#0-0)  No other code path exists to update, rotate, or disable this hardcoded trust anchor at runtime — the only way to change it is to ship a new application build, exactly mirroring the report's complaint that a privileged value is fixed with "no way to change that address... in case of governance change or compromise."

### Finding Description
For every other SSH host, Desktop safely defers to the user via an interactive prompt: [2](#0-1)  which calls `trampolineUIHelper.promptAddingSSHHost` to show the host/IP/keytype/fingerprint and let the user decide. [3](#0-2) 

The `github.com`/RSA/fingerprint tuple is the single exception carved out of this review process, and it is a compile-time constant rather than something the app can refresh from GitHub or invalidate if that specific RSA key is ever compromised — which has concrete precedent: GitHub has previously had to rotate its RSA SSH host key after private-key exposure. If a build shipped before such a rotation is still in use (which can persist for a meaningful population of users given staged/auto-update rollouts), the hardcoded fingerprint continues to silently authorize any SSH endpoint presenting that specific key material, with **zero user-visible warning**, for as long as that build remains installed.

### Impact Explanation
An attacker capable of intercepting or redirecting SSH traffic to `github.com` (DNS poisoning, malicious network/proxy, or a compromised git remote/host advertised through `parseAddSSHHostPrompt`) who possesses (or obtains, e.g. via a future/past key-exposure incident) the private key matching the hardcoded fingerprint can:
- Have the connection silently marked "known/trusted" with no user prompt, because `handleSSHHostAuthenticity` returns `'yes'` before ever reaching `trampolineUIHelper`. [4](#0-3) 
- Then have the trampoline's credential flow (SSH key passphrase / credential helper) proceed against this now-"trusted" endpoint without any interactive re-confirmation, enabling credential/passphrase exfiltration and silent substitution of git objects served to the victim during clone/fetch/push — i.e., silent corruption of what the user later commits/pushes on top of attacker-supplied history.

This satisfies the allowed impact classes: git remote/proxy-response attacker control leading to credential exfiltration and silent corruption of push/fetch content, without requiring local access, admin rights, prior malware, or leaked user credentials — the only prerequisite is control of the network path plus knowledge of the pinned key material, which is exactly the class of "compromise" the original report warns about for hardcoded privileged trust values.

### Likelihood Explanation
Likelihood is dependent on an external precondition (possession of the private key matching the hardcoded fingerprint, e.g., via a future GitHub key rotation/exposure event) plus network-path control, so this is not exploitable against a healthy, never-compromised key. However, the design itself — a single hardcoded trust bypass with no revocation mechanism embedded in the app, contrasted with the safe, prompted path used for every other host — is a structural weakness identical in shape to the reported bug class, and it has real-world precedent (GitHub's own documented history of RSA host-key rotation following key exposure).

### Recommendation
- Do not hardcode a single fingerprint as an unconditional auto-trust bypass. At minimum, fetch/validate GitHub's current host key set from a source that can be updated independently of app releases (e.g., a versioned, signed config fetched at runtime, similar to how endpoints are resolved in `app/src/lib/api.ts`), or provide an in-app mechanism to invalidate a previously pinned key.
- Alternatively, still show a (lightweight, one-time) confirmation for the `github.com` key the first time it's seen per machine, persisting the accepted fingerprint in the user's own `known_hosts`-equivalent store rather than compiling it permanently into the binary, so a future compromise/rotation can be remediated by an app update revoking the old pin rather than perpetuating silent trust in it.

### Proof of Concept
1. An attacker controls the network path to `github.com` for a victim (e.g., malicious Wi-Fi, DNS poisoning, or a compromising proxy) and possesses a private key matching the fingerprint hardcoded at [5](#0-4) .
2. Victim performs a normal `git fetch`/`clone` over SSH in Desktop against `git@github.com:...`.
3. Git's SSH client emits the "unknown host" authenticity prompt, which is intercepted by `parseAddSSHHostPrompt` and routed to `handleSSHHostAuthenticity`.
4. Because `info.host === 'github.com'`, `info.keyType === 'RSA'`, and `info.fingerprint` matches the hardcoded constant, the function returns `'yes'` immediately — no call to `trampolineUIHelper.promptAddingSSHHost` occurs, so the user sees no warning at all.
5. The connection is now treated as trusted; subsequent credential/passphrase exchange and object transfer occur against the attacker-controlled endpoint, enabling credential capture and/or delivery of tampered repository content.

  public promptAddingSSHHost(
    host: string,
    ip: string,
    keyType: string,
    fingerprint: string
  ): Promise<boolean> {
    return new Promise(resolve => {
      this.dispatcher.showPopup({
        type: PopupType.AddSSHHost,
        host,
        ip,
        keyType,
        fingerprint,
        onSubmit: addHost => resolve(addHost),
      })
    })
  }
