### Title
Zero used as "unset" sentinel for per-destination protocol fee lets governance's explicit 0% fee silently fall back to the (non-zero) default fee, causing unauthorized over-extraction from every order into that destination - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
The bug class in the external report is "a legitimate zero value is treated as invalid/unset, so it can never actually take effect, and the code silently falls back to different (wrong) behavior." `IntentGatewayV2.placeOrder` reproduces this exact pattern for `_destinationProtocolFees`: a governance-configured `0` (explicit "no fee for this destination") is indistinguishable from "never configured," so the contract silently substitutes the global `_params.protocolFeeBps` instead of honoring the intended zero fee.

### Finding Description
`placeOrder` computes the protocol fee to deduct from user inputs as: [1](#0-0) 

```solidity
bytes32 destinationHash = keccak256(order.destination);
uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
if (protocolFeeBps == 0) {
    protocolFeeBps = _params.protocolFeeBps;
}
```

`0` is used both as the storage default (unconfigured mapping slot) and as a legitimate configured value ("no fee for this destination"). Governance sets destination fees via `_updateParams`/`onAccept`, which stores whatever `feeBps` value it is given with no distinction for zero: [2](#0-1) 

The only guard is `feeBps >= 10_000 revert InvalidInput()` — there is no rejection of `feeBps == 0` and no `Option`/sentinel encoding to distinguish "explicitly zero" from "not yet set." Consequently, once governance dispatches a cross-chain `UpdateParams` message intending a 0% fee for a specific destination chain (e.g., to run a fee-free/subsidized corridor), the write to `_destinationProtocolFees[stateMachineId] = 0` is indistinguishable from an unconfigured entry. The very next `placeOrder` call to that destination re-reads `0`, treats it as "not configured," and falls back to `_params.protocolFeeBps` (the global default, which is typically non-zero, e.g. 100 bps in the test fixtures).

The Tron variant of the contract has the identical pattern: [3](#0-2) 

This is a public, unprivileged entrypoint path (`placeOrder` is callable by anyone) whose fee computation is silently manipulated by prior, entirely legitimate governance state — no malicious peer, relayer, or admin action is required beyond a normal, intended governance configuration. Existing guards (`_validateParams`'s `protocolFeeBps >= 10_000` check, and the destination-fee `feeBps >= 10_000` check in `_updateParams`) do nothing to prevent this, because they only bound the *upper* range of the value, not the *ambiguity* at zero.

### Impact Explanation
The corrupted value is `protocolFeeBps` used in `placeOrder`'s fee-reduction loop: [4](#0-3) 

Because the wrong (non-zero, default) fee bps is applied instead of the governance-intended zero, every order routed to that destination has its escrowed/reduced `TokenInfo[]` amounts miscalculated: users are charged a protocol fee they were never supposed to pay, and the order `commitment` (computed via `keccak256(abi.encode(order))` over the wrongly reduced inputs) reflects the wrong amount. This is a direct loss of user funds via a logic flaw in fee accounting/state application on a bridge order-escrow path — the exact "wrong amount" / "logic attack" impact class called for in the bounty scope. It also means any destination that governance intends to be fee-exempt can never actually be fee-exempt through the normal `UpdateParams` flow, silently defeating the protocol's own configuration.

### Likelihood Explanation
High likelihood of triggering in normal operation: this requires no attacker at all — any time governance legitimately wants to zero out a destination-specific fee (a supported, documented use case per `DestinationFee`/`ParamsUpdate`), the very next `placeOrder` call from any ordinary user against that destination will silently overcharge. It reproduces on every order to the affected destination until the bug is fixed, is triggerable by the fully permissionless `placeOrder` function, and does not depend on race conditions, malicious relayers, or compromised keys.

### Recommendation
Distinguish "unset" from "explicitly zero" for `_destinationProtocolFees`, e.g.:
- Use a sentinel that is not a valid bps value (such as `type(uint256).max`) for "unset," reserving `0` as a legitimate configured percentage; or
- Maintain a separate `mapping(bytes32 => bool) hasDestinationFee` alongside the bps mapping and check that flag before falling back to `_params.protocolFeeBps`; or
- Adopt an `Option`-style encoding matching what `pallet-bandwidth`/`intents-coprocessor` already use elsewhere in this codebase (`Option<TierConfig>`, `Option<DestinationFee>`) so "revoke to default" is an explicit action rather than an accidental zero write.

Apply the same fix to the Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) and to the `IntentsBase._updateParams`/`onAccept` code paths that write into `_destinationProtocolFees`.

### Proof of Concept
1. Deploy `IntentGatewayV2` and initialize with `_params.protocolFeeBps = 100` (1%), matching existing test fixtures such as `testPlaceOrderDestinationFeeWithFallback` in `evm/tests/foundry/IntentGatewayV2Test.sol`.
2. Governance dispatches a cross-chain `UpdateParams` message (via `onAccept`) with `destinationFees = [{ chain: "ARBITRUM", destinationFeeBps: 0 }]`, intending Arbitrum orders to pay zero protocol fee.
3. `_updateParams` stores `_destinationProtocolFees[keccak256("ARBITRUM")] = 0` with no error — indistinguishable from an unset slot: [5](#0-4) 
4. A user calls `placeOrder` with `order.destination = "ARBITRUM"`. `placeOrder` reads `_destinationProtocolFees[destinationHash] == 0`, treats it as "not configured," and substitutes `_params.protocolFeeBps = 100`: [6](#0-5) 
5. The user's escrowed input is reduced by 1% (`DustCollected` emitted) even though governance explicitly configured 0% for that destination — demonstrating the fee state can never be honestly set to zero per-destination, and users on that corridor are systematically overcharged.

*Note: I could not execute this against a live Foundry/Hardhat test harness in this environment; the trace above is derived directly from reading the on-chain logic (`IntentGatewayV2.sol` lines 300–331, `IntentsBase.sol` lines 551–568) and the existing test suite pattern (`testPlaceOrderDestinationFeeWithFallback`) that already demonstrates the same zero-fallback code path being exercised, just not with the "explicit zero" governance intent scenario.*
