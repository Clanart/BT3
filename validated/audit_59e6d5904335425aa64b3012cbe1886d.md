## Title
Delimiter-based Git log/ref parsers silently misalign fields on attacker-crafted NUL bytes, corrupting displayed commit/branch data - (File: `app/src/lib/git/git-delimiter-parser.ts`)

### Summary
The smart-contract report is about code that trusts `abi.decode` to always receive well-formed data; when the assumption breaks, the surrounding logic (which assumes the decode step "cannot fail") behaves incorrectly and funds can be misrouted. The equivalent structural pattern in GitHub Desktop is the family of fixed-width, delimiter-based parsers used to turn `git log`/`git for-each-ref` output into structured objects. These parsers assume that Git output is always cleanly split into complete, fixed-size groups of NUL-separated fields. That data, however, originates from a repository the user cloned or fetched — an attacker-controlled artifact — and Git plumbing does not guarantee that commit message content is free of the same `\0` byte used as the field separator.

### Finding Description
`createLogParser` builds the `-z --format=...%x00...` arguments and returns a `parse` function that blindly chunks the split records into fixed-size groups: [1](#0-0) 

`getCommits` uses this parser with `%b` (commit body) as one of the interpolated fields, reading the output as a raw `Buffer` and splitting strictly on `\0`: [2](#0-1) 

The parser has no way to verify that each of the fields it decodes (`sha`, `shortSha`, `summary`, `body`, `author`, `committer`, `parents`, `trailers`, `refs`) came from the commit it thinks it did — it simply assumes `records.length` is a multiple of `keys.length` and walks the buffer in fixed strides: [3](#0-2) 

A commit's free-form message body (`%b`) is fully attacker-controlled content when the commit is crafted with low-level Git plumbing rather than the normal `git commit` CLI (which sanitizes input). If that body contains an embedded literal NUL byte, `splitBuffer` will produce one extra record for that commit's entry. Because the loop advances by a constant `keys.length` per iteration rather than validating record boundaries, every subsequent commit's fields shift by one column for the remainder of the parsed history — SHAs, authors, parents, and trailers end up attributed to the wrong commit entries, with no exception thrown anywhere in the pipeline. This is the direct analog of "`abi.decode`-succeeds-but-produces-wrong-values" rather than the "`abi.decode`-reverts" case discussed in the report — arguably worse, since there is no error signal at all.

The same fixed-stride, unchecked-record-count design exists in `createForEachRefParser`, which is used by `getBranches`/`getBranchesDifferingFromUpstream` to determine upstream tracking relationships used for push targeting: [4](#0-3) 

### Impact Explanation
Downstream, `Commit.sha`/`Commit.parentSHAs` values feed operations the user believes are scoped to a specific, displayed commit — e.g. restoring co-authors on amend via `restoreCoAuthorsFromCommit`/`loadCommitAndCoAuthors`, which trusts `commit.summary`/`commit.body`/parsed trailers to reconstruct the commit that is about to be rewritten: [5](#0-4) 

If the SHA/author/trailers shown for a history entry are silently shifted to belong to a different commit due to the parsing misalignment, a user acting on that entry (amend, revert, cherry-pick, viewing/using the commit identity for co-authoring) can end up operating on or committing metadata for the wrong commit — a silent corruption of what the user commits, with no error surfaced to alert them, mirroring the "tokens sent to unintended place without revert" outcome in the original report.

### Likelihood Explanation
This requires the attacker to control the content of a repository the victim clones or fetches (in scope per the task's valid-impact criteria) and to construct a commit object containing a raw NUL byte in the message body via Git plumbing rather than the ordinary CLI, then get the victim to view that repository's history in Desktop. This is a Git-internals-only step (no local/physical access, no admin rights, no malware) satisfying the "attacker controls a cloned/fetched repository" avenue in the valid-impact list. Note that constructing such an object requires bypassing normal `git commit` sanitization; producing a definitive PoC would require confirming a plumbing path that survives object writing/transport without stripping the NUL, which the guard in this codebase does not attempt to check at parse time regardless of how the object was produced.

### Recommendation
- In `createLogParser`/`createForEachRefParser`, validate that the number of parsed records is an exact multiple of `keys.length` (or use a per-record sentinel/count check) and throw/skip on mismatch instead of silently continuing with a fixed-stride walk.
- Where feasible, prefer parsing strategies that don't rely purely on a byte value (`\0`) that cannot be excluded from attacker-controlled free-form fields (commit messages, ref names) without an explicit length-prefixed or escaped encoding.
- Add defensive validation before using parsed `sha` values for destructive/identity-sensitive operations (amend, revert, cherry-pick) — e.g., cross-check the parsed SHA against `git cat-file`/`git rev-parse` before acting on it.

### Proof of Concept
1. Attacker creates a repository and, using low-level Git plumbing (e.g. `git hash-object -w --stdin -t commit` with a manually constructed commit object body) constructs a commit whose message contains a literal `\0` byte.
2. Attacker pushes/publishes this repository; victim clones/fetches it in Desktop.
3. Desktop calls `getCommits`, which runs `git log -z --format=...%H%x00%h%x00%s%x00%b%x00...` and pipes the buffer through `createLogParser`'s `parse`: [6](#0-5) 
4. Because the crafted commit's `%b` field itself contains an internal `\0`, the fixed-stride record consumption in `parse` misaligns every subsequent commit's fields (SHA, author, parents, trailers) by one column, with no validation or exception raised: [7](#0-6) 
5. The commit list rendered in Desktop (and any action keyed off the parsed `sha`, such as restoring co-authors on amend) now silently reflects incorrect data for one or more commits.

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

export function createForEachRefParser<T extends Record<string, string>>(
  fields: T
) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%00')
  const formatArgs = [`--format=%00${format}%00`]

  const parse = (value: string) => {
    const records = value.split('\0')
    const entries = new Array<{ [K in keyof T]: string }>()

    let entry
    let consumed = 0

    // start at 1 to avoid 0 modulo X problem. The first record is guaranteed
    // to be empty anyway (due to %00 at the start of --format)
    for (let i = 1; i < records.length - 1; i++) {
      if (i % (keys.length + 1) === 0) {
        if (records[i] !== '\n') {
          throw new Error('Expected newline')
        }
        continue
      }

      entry = entry ?? ({} as { [K in keyof T]: string })
      const key = keys[consumed % keys.length]
      entry[key] = records[i]
      consumed++

      if (consumed % keys.length === 0) {
        entries.push(entry)
        entry = undefined
      }
    }

    return entries
  }

  return { formatArgs, parse }
}
