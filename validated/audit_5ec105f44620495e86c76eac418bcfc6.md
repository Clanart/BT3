Based on the collision pattern in the report — where a **shared identifier (function selector)** causes two different entities to be treated as the same one, silently shadowing the trusted one — the closest structural analog in GitHub Desktop is how a GitHub repository's *identity* is re-derived purely from the human-readable `(hostname, owner, name)` triplet rather than an immutable GitHub repository ID, and that weaker "signature" is used to decide whether to silently rewrite the user's configured git remote URL.

### Title
Remote URL Auto-Rewrite Trusts Owner/Name Match Instead of Immutable Repository ID, Enabling Repo-Jacking - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` silently overwrites a repository's git remote URL with whatever `clone_url` the GitHub API now returns for a given owner/name, gated only by a case-insensitive string comparison of `(hostname, owner, name)`. There is no check that the API's stable repository ID still matches the previously cached one, so any GitHub repository that satisfies the same "signature" (same owner login + same repo name on the same host) will silently take over the identity of the previously trusted repository, exactly analogous to a new module's function signature colliding with — and being shadowed/replaced by — an already-registered one.

### Finding Description
`matchGitHubRepository` and `urlMatchesRemote` establish a GitHub repository's identity solely from its hostname, owner login, and repository name, compared case-insensitively: [1](#0-0) 

This "signature" is then used by `updateRemoteUrl` to decide, without any user confirmation, whether to rewrite the locally configured git remote: [2](#0-1) 

The function only checks that (a) the current remote URL still parses to the same owner/name/host as what Desktop last cached (`remoteUrlUnchanged`), and (b) the URL scheme/protocol hasn't changed. If those hold, it calls `gitStore.setRemoteURL(...)` with the API-supplied `clone_url` — no verification that the underlying GitHub repository (by its immutable numeric ID) is still the same repository. GitHub allows repository names and even owner logins to be freed and re-claimed (e.g., after an account is renamed/deleted, or an org repo is renamed and the old owner/name is reused by someone else). An attacker who registers/creates a repository under the exact `owner/name` that a victim previously cloned (on the same host) produces an API object whose owner/name "signature" collides with the cached one, causing Desktop to silently repoint the trusted remote at the attacker's `clone_url`.

This is the same class of bug as the report: a narrower, attacker-influenced identifier (function selector / owner+name pair) collides with an already-established one, and the system silently substitutes behavior/identity without any collision check against a stronger, immutable identifier (DIMORegistry's own selectors / the GitHub repository's numeric ID).

### Impact Explanation
If the local `origin` (or `upstream`) remote is silently rewritten to an attacker-controlled clone URL, all subsequent `git fetch`/`git pull`/`git push` operations issued by Desktop operate against a repository the attacker fully controls. This can lead to:
- Fetching and merging attacker-supplied commits/history into the user's working repository (supply-chain style corruption of what gets pulled).
- Pushing the user's private work (and any credentials sent as part of the push handshake) to an attacker-controlled endpoint if the attacker's `clone_url` uses a host they control.
- Silent, unattended corruption of what the user believes they are syncing with, without any dialog comparable to the existing `UpstreamAlreadyExists` warning that Desktop shows for a related but different scenario: [3](#0-2) 

### Likelihood Explanation
The path requires an attacker to control a GitHub repository whose owner+name (on the same host) matches a repository the victim previously cloned via Desktop — achievable through repo-jacking (claiming a freed username/org or a renamed repository slot) — and requires the API-derived `clone_url` for that identical-looking repo to differ from what's already configured. This is entirely externally triggerable via the GitHub API response and does not require local access, admin rights, or prior malware, matching the "attacker controls a GitHub API object" impact category. Note: I was not able to fully trace every call site that feeds `apiRepo` into `updateRemoteUrl` within the available search budget, so it is uncertain whether an upstream caller already validates the API repository's immutable ID before invoking this function — this should be verified directly in `app/src/lib/stores/app-store.ts` around GitHubRepository refresh logic.

### Recommendation
Before calling `setRemoteURL`, verify that the API repository's immutable numeric `id` matches the previously stored `GitHubRepository`'s ID (the same way Diamond-style selector routers should check against a canonical/immutable set rather than a mutable label). If the ID differs, treat it as a different repository and surface a warning to the user instead of silently rewriting the remote — mirroring the existing `UpstreamAlreadyExists` confirmation flow.

### Proof of Concept
1. Victim clones `https://github.com/alice/tool.git` with Desktop; Desktop caches the `GitHubRepository` record (owner="alice", name="tool", API id=111).
2. `alice` renames her GitHub account or deletes/renames the `tool` repository, freeing the `alice/tool` slug (or an org member removal frees an org-owned slug).
3. Attacker registers/renames an account to `alice` (or creates a repo) and creates a new repository `tool` with a malicious `clone_url`, obtaining a new API id (e.g., 999).
4. On next repository refresh, Desktop's `fetchRepository('alice', 'tool')` returns the attacker's repository object; `updateRemoteUrl` sees hostname/owner/name still match the cached signature and, without checking the API id, calls `gitStore.setRemoteURL('origin', attackerCloneUrl)`.
5. The next `git fetch`/`push` performed by the victim now targets the attacker's repository transparently.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
