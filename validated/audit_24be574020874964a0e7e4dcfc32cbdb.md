### Title
Bitcoin deposits above network dust but below `N::DUST` are silently discarded by the scanner, permanently stranding user funds - ([File: processor/src/multisigs/scanner.rs])

### Summary
Analogous to the external report — where a `MIN_NOTIONAL_WEI` check bricks positions whose value later falls below a fixed minimum — Serai's Bitcoin integration applies a hardcoded minimum-value filter (`N::DUST = 10_000` sats) at intake. Any output sent to a Serai-controlled address whose value is at least Bitcoin's real dust/relay minimum but below Serai's internal `DUST` constant is silently ignored by the scanner: never emitted as a received output, never credited, and unrecoverable since the spending key is threshold-held.

### Finding Description
In `processor/src/multisigs/scanner.rs:562-567`, scanned outputs are only surfaced if `output.balance().amount.0 >= N::DUST`:

```rust
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {
    outputs.push(output);
  }
}
```

For Bitcoin, `DUST` is `10_000` sats (`processor/src/networks/bitcoin.rs:638`), justified by a fee-model comment assuming 5 sat/vbyte. However, Bitcoin's actual output minimum is ~546 sats (`networks/bitcoin/src/wallet/send.rs:32`, `pub const DUST: u64 = 546`), which is what `SignableTransaction::new` itself enforces for outgoing payments (`send.rs:165-169`).

This creates the same asymmetric-minimum bug class as `MIN_NOTIONAL_WEI`: the protocol accepts a wide range of economically valid deposits at the consensus/relay layer but applies a much higher internal minimum when *crediting* them. An unprivileged user sending, e.g., 5,000 sats to a Serai deposit address produces a perfectly valid, spendable output — yet `scan_transaction`/`scan_block` results get filtered out before ever reaching `ReceivedOutput`. The UTXO exists on chain under Serai's tweaked threshold key, but the processor will never schedule it, so it can never be aggregated or spent.

### Impact Explanation
User funds in the range `[546, 10_000)` sats sent to Serai addresses are permanently lost: the deposit confirms on-chain, the protocol never reports it, and no party can unilaterally recover it since the key is FROST-thresholded. This is strictly worse than "funds reported received that are not spendable" — the funds are never even reported. There is no error path, refund, or event emitted; the drop is silent (no log at the `>= DUST` filter site).

### Likelihood Explanation
Any external depositor can reach this with a single ordinary Bitcoin transaction — no protocol access required. Small deposits are plausible: users testing the bridge with small amounts, or dust-sized remainder payments. The gap between 546 and 10,000 sats is nearly a 20x window. Nothing in the deposit flow rejects or warns about sub-`DUST` amounts beforehand; the check only exists inside the scanner loop.

### Recommendation
Either (a) accept all outputs at `>=` Bitcoin's actual dust floor and handle the uneconomical-spend case at scheduling time (e.g., queue them for aggregation only when fee conditions make them spendable), or (b) treat sub-`DUST` outputs as explicitly detected-but-flagged events so the protocol can refund or later recover them, rather than dropping them silently. At minimum, emit a `ScannerEvent`/log for ignored outputs so operators can detect stranded funds.

### Proof of Concept
1. Compute a Serai deposit address for an active threshold key (`p2tr_script_buf(tweaked_key)`, `networks/bitcoin/src/wallet/mod.rs:80-86`).
2. Send a confirmed Bitcoin transaction paying 5,000 sats to that script.
3. `Scanner::scan_transaction` (`mod.rs:199-214`) returns the `ReceivedOutput` — matching `script_pubkey` — but `scanner.rs:564` discards it since `5_000 < N::DUST (10_000)`.
4. No `ScannerEvent::Block`-associated output is emitted; the deposit is never credited and no `ReceivedOutput` is ever constructed for the scheduler — the 5,000 sats sit unspendable under the threshold key indefinitely.
