### Title
Silent remote-URL rewrite based on unauthenticated API `clone_url` comparison, without host allow-listing or user confirmation - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The core invariant broken in the Telepathy report is: *the value used to decide "who is authorized to sign/finalize this state" is not the same value that was actually verified/committed to*. In `updateRemoteUrl`, GitHub Desktop performs an analogous mismatch: it decides whether to overwrite the user's local git `origin` remote URL by comparing structural URL components (hostname/owner/name) rather than verifying the full trust context, and only checks that the URL *protocol* stayed the same — not that the *host* is one the user actually intends to push/pull from.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  fetches `apiRepo.clone_url` from the GitHub/GHE API and compares it against the locally configured remote using `urlMatchesRemote`, which only compares parsed hostname/owner/name components case-insensitively [2](#0-1) . The function then applies a narrow guard — matching protocol scheme only — before calling `gitStore.setRemoteURL` to silently rewrite the remote: [3](#0-2) 

There is no verification that the *host* in the new `clone_url` is the same host the user originally trusted, and there is no user confirmation before the remote is rewritten — unlike the `LightClient` bug, where the wrong sync committee (an unverified value swapped in for the correct verification target) is trusted implicitly. Here, the API response is trusted implicitly to redirect where the local repository will subsequently push/fetch, as long as the URL parses to a "GitHub-repository-shaped" URL, without any explicit binding to the specific instance/host the user originally configured to be immutable.

The codebase itself elsewhere acknowledges the danger of trusting slightly-out-of-sync remote-identity values for critical operations — see the extensive comment in `PushBranch`'s `safeRemote` construction, which was added specifically because relying on a possibly-stale remote name during push was recognized as risky [4](#0-3) . That defensive pattern was not applied to `update-remote-url.ts`, where the actual write of a new remote *URL* (not just name) happens based on trusting an external, per-request API payload.

### Impact Explanation
If a GitHub Enterprise server (or the API endpoint reached through it) that the user has previously authenticated to is compromised or manipulated (a "git remote/proxy response" attacker per the valid-impact scope), it can return a crafted `clone_url` for a repository the victim has already cloned. On the next background refresh, Desktop will silently repoint the user's `origin` remote to the attacker-specified host, provided the URL still parses as `protocol://host/owner/name` with the same scheme. Subsequent pushes/fetches by the user — believing they are talking to the original repository — would silently go to a different host, which matches the report's "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires attacker control of the API server/response the app queries for repository metadata (the enumerated "git remote/proxy response" actor), not local access or leaked credentials. It occurs automatically on normal repository refresh cycles with no user interaction, similar to how the `LightClient` bug is triggered automatically by normal chain progression rather than by any special user action. I was unable to verify, within the remaining tool budget, exactly how frequently `updateRemoteUrl` runs in production refresh cycles or whether any additional guard exists further upstream (e.g., in `refreshGitHubRepositoryInfo`) that might restrict this to first-time-only association — this should be confirmed before treating the likelihood as fully established.

### Recommendation
Before rewriting the local remote URL from an API-provided `clone_url`, require that the hostname (not just protocol) match the previously trusted value, or prompt the user to confirm the change explicitly when the host differs. Treat any observed change to `clone_url`'s host as untrusted input requiring positive user confirmation, analogous to how the Trail of Bits recommendation was to bind the verification input (`attestedSlot`) directly to the finalized value being trusted rather than deriving trust context from an unrelated field.

### Proof of Concept
Conceptual PoC (not fully executable without a live malicious GHE instance):
1. User adds and authenticates to a GitHub Enterprise account, and clones a repo whose origin is `https://ghe.example.com/org/repo.git`.
2. Attacker gains control of `ghe.example.com`'s API responses (e.g., compromises the GHE app server while leaving git protocol/TLS cert intact, or via a malicious reverse proxy in front of the API endpoint only).
3. On the next repository info refresh, the attacker's API returns `clone_url: "https://ghe.example.com/org-evil/repo.git"` (same host, different owner) or a differently-cased/aliased host that still parses with matching hostname per `parseRemote`.
4. `updateRemoteUrl` computes `protocolsMatch = true`, `remoteUrlUnchanged = true` (since the cached `gitHubRepository.cloneURL` still matches the current remote), and `urlsMatch = false` (since owner differs) — triggering `gitStore.setRemoteURL(...)` and silently repointing `origin` [5](#0-4) .
5. The user's next `git push` is sent to `org-evil/repo` without any prompt, matching the "silent corruption of what the user commits or pushes" impact.

Note: I could not, within the current tool budget, confirm whether an additional confirmation dialog exists elsewhere in the refresh pipeline that would block step 4 before `setRemoteURL` executes; a Devin session with full-repo access should verify the call sites of `updateRemoteUrl` (e.g., in the repository/GitHub-repository refresh store logic) to rule this out before treating this as conclusively exploitable.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
