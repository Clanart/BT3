### Title
Oracle timestamp freshness check silently bypassed for future-dated price timestamps, enabling permanent staleness lock or acceptance of manipulated prices - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `oracle-timestamp-fresh` helper used by `price-resolve` in the market contract computes a "not-too-stale" delta that is forced to `u0` (i.e., automatically treated as fresh) whenever the reported feed timestamp is greater than the current `stacks-block-time`. Combined with the monotonic-timestamp rule (`>= ts prev`), this both (a) accepts a price without any real staleness bound whenever its timestamp is in the future, and (b) permanently ratchets the per-feed `last-update` timestamp forward past real time, which can lock out all subsequent legitimate (correctly-timed) price updates for that asset because they will fail the `>= ts prev` monotonicity check indefinitely.

### Finding Description
`oracle-timestamp-fresh` is the sole staleness/monotonicity gate applied to every resolved price before it is used for collateral/debt valuation and liquidation: [1](#0-0) 

```clarity
(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When `ts > stacks-block-time` (the price's reported timestamp is ahead of the chain's current time), `delta` is hard-coded to `u0`, so `(<= delta max-staleness)` is unconditionally true — the per-asset `max-staleness` bound configured in the asset registry is completely bypassed for any future-dated timestamp, no matter how far in the future. The only remaining guard is the monotonic check `(>= ts prev)`.

This is invoked from `price-resolve`, which then commits the (possibly future) timestamp as the new `last-update` value for that feed/type key if it is greater than the previously stored one: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Once any single future-dated timestamp is accepted and persisted to the `last-update` map, `last-update-time` for that feed becomes greater than the real chain time. All subsequent, correctly-timestamped price updates will then have `ts < prev`, which fails `(>= ts prev)` and causes `ERR-ORACLE-INVARIANT`, permanently blocking further price updates for that asset via the normal path until a new timestamp exceeds the artificially advanced watermark.

This is a self-contained logic bug in the market contract's own staleness-gating implementation — not a third-party data-integrity issue — because a correctly functioning freshness check should reject (or clamp to `max-staleness`-worth-of-tolerance) timestamps that are ahead of `stacks-block-time`, rather than special-casing them to "always fresh."

### Impact Explanation
- If the feed's timestamp field can ever be advanced (via clock skew in the upstream data path, a delayed/held VAA replay, or any deviation between the oracle's clock and `stacks-block-time`), the freshness bound configured per-asset (`max-staleness`) is bypassed entirely, meaning a price could be used well beyond its intended staleness window without reverting.
- Once accepted, the stored `last-update` timestamp for that asset is ratcheted into the future, which can cause all further legitimate price updates to be rejected by the monotonicity check, freezing that asset's price feed. Any market action that requires accruing/resolving that asset's price (borrow, withdraw, health checks, liquidation) will use the frozen/stale price indefinitely, or revert entirely if `price-resolve` cannot be satisfied — a temporary freezing of funds for positions collateralized or borrowing in that asset.

### Likelihood Explanation
This requires only a single anomalous timestamp (ahead of `stacks-block-time`) from either oracle path (`resolve-pyth` or `resolve-dia`) to be processed once; no attacker-side computation, governance compromise, or economic capital is required — it is purely a logic defect in how the market contract validates the timestamp it receives.

### Recommendation
Rewrite `oracle-timestamp-fresh` so that a timestamp ahead of `stacks-block-time` is treated as invalid (or bounded by an explicit future-tolerance constant) rather than being coerced to `delta = 0`:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)                       ;; reject future timestamps outright
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This removes the unconditional "fresh" bypass and prevents the `last-update` watermark from being advanced past real time.

### Proof of Concept
1. A price update for asset X is resolved via `resolve-pyth`/`resolve-dia` with `timestamp = T_future`, where `T_future > stacks-block-time` (e.g., due to clock skew between the Pyth/DIA source and the Stacks node, or a delayed relay of an update whose payload timestamp is ahead of the block being processed).
2. `price-resolve` calls `oracle-timestamp-fresh(T_future, last-update-time, max-staleness)`; because `T_future > stacks-block-time`, `delta = u0`, so the staleness bound is bypassed and (assuming `T_future >= last-update-time`) the check passes.
3. `price-resolve` stores `last-update[key] = T_future`, which is now ahead of real chain time.
4. On the next legitimate update with a correct timestamp `T_now <= stacks-block-time` (but `T_now < T_future`), `(>= ts prev)` fails, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT`, freezing all further price updates for asset X until real time catches up to `T_future`.

**Uncertainty:** I could not verify within the available index how far the Pyth/DIA `publish-time`/`timestamp` fields are otherwise sanitized before reaching `resolve-pyth`/`resolve-dia` (e.g., in `pyth-storage-v4` or the DIA oracle client), since those external contracts were not fully indexed. If those upstream contracts already strictly reject timestamps ahead of the current block time, the practical likelihood of reaching this code path would be lower; a Devin session with full repository access would be needed to confirm this.
