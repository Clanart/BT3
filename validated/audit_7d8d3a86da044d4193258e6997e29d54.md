### Title
Flash-loan reward sniping via `donateRewards` instantaneous, non-time-weighted distribution - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`donateRewards` is permissionless and calls `_provisionReward`, which distributes both the newly donated amount and any accumulated `queuedRewards` backlog proportionally to `totalStaked()` measured at the instant of the call. Because `totalStaked()` is simply the live staking-token balance of the `operator` (MasterMagpie) [1](#0-0) , and stake/unstake within MasterMagpie can be done atomically in the same transaction, an attacker can flash-loan the staking token, deposit it into MasterMagpie to inflate `totalStaked()`, trigger `donateRewards` to flush the entire queued backlog against this artificially inflated stake, then immediately withdraw and repay the loan — capturing a share of the backlog reward that was accrued while the attacker held no real economic exposure.

### Finding Description
`_provisionReward` computes the reward increment as a lump-sum split over `totalStaked()` at call time: [2](#0-1) 

Key issues:
1. `totalStaked()` reads `IERC20(stakingToken).balanceOf(operator)` — a spot balance, not a time-weighted or checkpointed value [1](#0-0) .
2. `queuedRewards` accumulates whenever `totalStaked()==0` at donation time and is only folded into `rewardPerTokenStored` the next time `totalStaked() != 0` [3](#0-2) . This backlog can represent rewards that logically belong to a "no active stakers" period, but they are dumped entirely against whichever `totalStaked()` exists at the moment someone (anyone) calls `donateRewards`.
3. `donateRewards` has no access control beyond `isRewardToken` and no floor on `_amountReward` (can be 1 wei) [4](#0-3) .
4. In `MasterMagpie._deposit`, the reward-checkpoint (`_harvestBaseRewarder`, which updates `userRewardPerTokenPaid`) happens **before** `user.amount` is incremented, so a newly-deposited attacker's paid checkpoint is set to the pre-donation `rewardPerTokenStored` [5](#0-4) . Immediately after, the attacker's `balanceOf` (via `stakingInfo`) reflects the full flash-loaned amount, so when the queued backlog/donation is distributed, the attacker's stake captures a share proportional to the artificially inflated balance, diluting genuine stakers' share of the backlog.
5. `MasterMagpie.deposit`/`withdraw` use `nonReentrant`, but this only guards against re-entrant calls, not sequential deposit→donate→withdraw calls within the same transaction by the same caller, so the whole sequence is atomically composable with a flash loan.

No existing check (no cooldown, no minimum holding period, no per-second/streaming vesting of the queued backlog) prevents an attacker from being present only for the single block/transaction in which the backlog is released.

### Impact Explanation
This allows an attacker to steal unclaimed yield: reward tokens accrued during a period when `totalStaked()==0` (queued backlog) or new donations are diverted disproportionately to a flash-loan-funded transient staker instead of the legitimate stakers who held stake historically or hold it afterward, at the direct expense of those stakers. This matches Immunefi's "High - Theft of unclaimed yield" category since real reward-token value (ERC20 assets held by the rewarder contract) is redirected to the attacker with no lasting economic exposure or cost beyond gas and flash-loan fees.

### Likelihood Explanation
The precondition is realistic: any pool that experiences a period of zero `totalStaked()` (e.g., newly created pool, or a pool fully drained then re-seeded) accumulates `queuedRewards`; flash loans of common staking tokens (LP tokens, wrapped assets) are broadly available. The attack requires only: (1) flash-loan the staking token, (2) `MasterMagpie.deposit`, (3) call `donateRewards` with a trivial amount to trigger the flush, (4) `MasterMagpie.withdraw` to harvest and reclaim principal, (5) repay the loan — all within one transaction, repeatable for any pool/token pair with a nonzero `queuedRewards` backlog or ongoing reward stream, requiring no privileged role.

### Recommendation
Do not distribute rewards proportional to an instantaneous, flash-loanable balance. Options:
- Replace the lump-sum "flush on next nonzero totalStaked" model with per-second/streaming accrual (e.g., track `lastUpdateTime` and drip `queuedRewards` over a vesting window) so a single-block stake captures a negligible fraction.
- Add a minimum stake duration/checkpoint delay before a deposit is eligible to receive newly queued rewards (e.g., snapshot balances a block prior, or require rewards to accrue only to balances held before the donation transaction).
- Consider computing `totalStaked()` from an internally tracked, checkpointed sum of `userInfo[...].amount` rather than the live external `balanceOf`, and reject deposit+withdraw pairs within the same transaction/block for reward-eligibility purposes.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPoolV2` for a staking token, register a reward token, and let `queuedRewards` accumulate (call `queueNewRewards` while `totalStaked()==0`, or simply skip staking so no one has deposited).
2. Deploy a `FlashLoanReceiver` attacker contract that, within `executeOperation`:
   a. Approves and calls `MasterMagpie.deposit(stakingToken, flashLoanedAmount)`.
   b. Calls `BaseRewardPoolV2.donateRewards(1, rewardToken)` (or via `queueNewRewards` if manager-gated path not needed — must use `donateRewards` since attacker is unprivileged).
   c. Calls `MasterMagpie.withdraw(stakingToken, flashLoanedAmount)`, which triggers `_harvestBaseRewarder` → `getReward`, sending the attacker the accrued reward tokens.
   d. Repays the flash loan.
3. Assertions:
   - Attacker's reward-token balance increased by a disproportionate share (near-total) of the previously queued backlog, while legitimate stakers (added before the attack, still holding stake after) see their `earned(account, rewardToken)` reduced/diluted versus a baseline scenario without the flash-loan attack.
   - `balanceOf(attacker)` before/after equals `IMasterMagpie(operator).stakingInfo(stakingToken, attacker).staked` at each step (accounting stays "reconciled" per query definition), yet the attacker's net PnL in reward tokens is positive with zero net principal risk — demonstrating value extraction disallowed by the intended distribution invariant (backlog should reward the stake set that earned it over time, not a flash-loan snapshot).

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
