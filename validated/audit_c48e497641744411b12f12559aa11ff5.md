Based on the investigation, the closest local analog to the Arbitrum bug-class ("silently coerce an unhandled/invalid enumerated value into a default instead of failing loudly") is the git status-code mapping fallback in `app/src/lib/status-parser.ts`.

### Title
`mapStatus` silently reclassifies unrecognized/type-change git status codes as ordinary "Modified" instead of failing or flagging them - ([File: app/src/lib/status-parser.ts])

### Summary
`mapStatus` in [1](#0-0)  enumerates a long, explicit list of two-character porcelain v2 status codes (`M.`, `.M`, `A.`, `.A`, `D.`, `.D`, `R.`, `.R`, `C.`, `.C`, `AD`, `AM`, `RM`, `RD`, and the six conflict codes), but any code not on that list — including type-change combinations that use the `T` character (which the parsing regex explicitly allows, see `[MADRCUTX?!.]{2}` at [2](#0-1) ) — falls through to a catch-all default: [3](#0-2) 

This mirrors the exact bug class in the Arbitrum report: an enumerated/validated value space (`preimageType` there, git status XY code here) has an "impossible"/unhandled branch that is silently coerced into a default value (`.unwrap_or(255)` there, `{ kind: 'ordinary', type: 'modified' }` here) instead of raising an error so the caller can react to the anomaly.

### Finding Description
`parseChangedEntry` accepts any two-character status code matching `[MADRCUTX?!.]{2}` from `git status --porcelain=2 -z` output ( [4](#0-3) ), including type-change codes such as `T.`, `.T`, `MT`, `TM`, `AT`, `TA`, `RT`, `TR`, `CT`, `TC`, `DT`, `TD`, and the "unmerged/unknown" `X`/`U` combinations that aren't in the six hardcoded conflict codes. `mapStatus` never checks for these; they all fall through to line 420-425 and are reported as a plain ordinary "modified" file, with no `submoduleStatus`-style flag or warning indicating the entry is actually a type change (e.g., regular file ⇄ symlink) or otherwise unusual.

Git emits a type-change (`T`) status when a tracked path's type differs between index/HEAD and the working tree — most notably when a repository contains a symlink and the checkout environment doesn't preserve symlinks (e.g. `core.symlinks=false`, which is common/default in some Windows configurations), git materializes the symlink as a plain text file containing the target path and reports the discrepancy as a type change. This can happen purely as a side effect of cloning/checking out an attacker-authored repository — no unnatural user action is required.

### Impact Explanation
Because the mapper hides the "type change" nature of the entry and reports it as an ordinary modification, the Changes list/diff UI built downstream (`convertToAppStatus` in [5](#0-4) ) treats it identically to a normal content edit. A user reviewing the diff before committing loses the specific signal that a file's type changed (e.g., a symlink was replaced by a plain file, or vice versa), which is exactly the kind of anomaly a user should be alerted to before staging/committing — this matches the "silent corruption of what the user commits or pushes" impact category, since the semantic nature of the change is misrepresented rather than surfaced.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker-controlled repository containing tracked symlinks (or other type-varying content) and a checkout environment where git doesn't preserve the original type (a realistic, non-default-but-common condition, e.g., Windows without Developer Mode/symlink privilege, or `core.symlinks=false`). No admin rights, local access, or unnatural steps are needed beyond cloning/fetching and viewing the resulting status — actions Desktop performs routinely.

### Recommendation
Explicitly enumerate and label type-change (`T`-containing) and any other unmerged/unknown status codes in `mapStatus`, returning a distinct `FileEntry` kind (e.g. `'typechange'`) or otherwise surfacing them distinctly to the UI, rather than silently defaulting unrecognized codes to `{ kind: 'ordinary', type: 'modified' }`. At minimum, log/telemetry-flag unrecognized codes so silent misclassification can be detected, similar to how the Arbitrum fix replaced a silent `unwrap_or` fallback with an explicit failure for out-of-range/unexpected states.

### Proof of Concept
1. Attacker publishes a public repository containing a tracked symlink file (e.g. `payload -> /some/target`).
2. Victim clones the repository on a system/config where git does not preserve symlinks on checkout (`core.symlinks=false`), which is common on Windows setups without Developer Mode/elevated privileges enabled for symlink creation.
3. `git status --porcelain=2` reports the symlink path with a type-change status code (e.g. `1 .T ...` or similar `T`-inclusive XY code).
4. `parsePorcelainStatus`/`parseChangedEntry` successfully parses this line into an `IStatusEntry` since `T` is in the allowed character class ( [2](#0-1) ).
5. `mapStatus` does not match any of the explicit codes and falls through to the default branch, returning `{ kind: 'ordinary', type: 'modified' }` ( [3](#0-2) ), so the Changes UI shows this as an ordinary modified file rather than flagging the type change, and the user may commit/push the change without realizing the underlying object type was altered.

function parseChangedEntry(field: string): IStatusEntry {
  const match = changedEntryRe.exec(field)

  if (!match) {
    log.debug(`parseChangedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for changed entry`)
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    path: match[8],
  }
}
