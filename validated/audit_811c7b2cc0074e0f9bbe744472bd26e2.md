### Title
Unbounded `io.ReadAll(r.Body)` in NewRelic/Datadog JSON-RPC HTTP tracing wrappers bypasses `MaxRequestContentLength`, enabling memory-exhaustion DoS - ([File: networks/rpc/http_newrelic.go])

### Summary
When Kaia's node operator enables NewRelic APM or Datadog APM tracing for the JSON-RPC HTTP server, every incoming HTTP request is first intercepted by `newNewRelicHTTPHandler` / `newDatadogHTTPHandler`, which call the shared helper `getRPCRequests(r)`. That helper reads the entire request body into memory via `io.ReadAll(r.Body)` with no size cap, before the server's own content-length validation and `io.LimitReader`-bounded codec ever run. A public, unauthenticated RPC caller can therefore force the node to buffer an arbitrarily large (or chunked, unbounded) HTTP body into memory in a single request, exactly the "buffer indefinitely with no size limit before any terminator/validation check" bug class described in the Rack advisory (CVE-2025-61772).

### Finding Description
The vulnerable helper is: [1](#0-0) 

```go
func getRPCRequests(r *http.Request) ([]*jsonrpcMessage, bool, error) {
	reqBody, err := io.ReadAll(r.Body)
	...
}
```

It is invoked unconditionally at the top of both tracing handlers, before any size check: [2](#0-1) [3](#0-2) 

These handlers are wired as the **outermost** layer of the HTTP handler chain in `NewHTTPServer`, wrapping the CORS/vhost/timeout handler and ultimately the `Server` (`srv`) itself: [4](#0-3) 

The size protections that exist for the normal path — the `Content-Length` check in `validateRequest` and the `io.LimitReader(r.Body, common.MaxRequestContentLength)` wrapping performed in `newHTTPServerConn` — only take effect **after** control reaches `srv.ServeHTTP`: [5](#0-4) [6](#0-5) 

Since `getRPCRequests` runs first and reads `r.Body` directly with `io.ReadAll` (no `io.LimitReader`, no `MaxBytesReader`), an attacker can:
- Send a POST to the JSON-RPC HTTP endpoint with `Transfer-Encoding: chunked` (so `r.ContentLength == -1`, defeating the later `r.ContentLength > MaxRequestContentLength` check entirely) and stream an unbounded amount of data, all of which is fully materialized in memory by `io.ReadAll` before any limit is applied.
- Or simply send a body far larger than `common.MaxRequestContentLength`; it will still be fully read into memory by the tracing wrapper before the inner handler ever gets a chance to reject it.

This is reachable by any unauthenticated public JSON-RPC caller — no special privileges are required — and only depends on the node operator having enabled a supported, documented production feature (`NEWRELIC_APP_NAME`/`NEWRELIC_LICENSE` or `DD_TRACE_ENABLED` env vars), which is common in production deployments (the code also parses KAS-specific headers, indicating production/KAS usage of this tracing path).

### Impact Explanation
A remote, unauthenticated attacker can force unbounded memory allocation per request against the node's JSON-RPC HTTP endpoint whenever NewRelic or Datadog tracing is enabled, leading to process OOM/crash or severe slowdown — a denial of service against the public RPC endpoint. This matches the same "unbounded buffering of attacker input with no cap" root cause as the referenced Rack CVE-2025-61772 (CWE-400), and directly affects availability of the RPC service (and potentially the node process itself if OOM-killed).

### Likelihood Explanation
Likelihood is high in any deployment where NewRelic or Datadog APM tracing is turned on for the RPC layer (a normal production observability configuration): the exploit requires only a single crafted HTTP POST request (e.g., large or chunked-encoded body) to the public JSON-RPC HTTP port, with no authentication, no special transaction crafting, and no race conditions.

### Recommendation
Wrap `r.Body` with `io.LimitReader(r.Body, common.MaxRequestContentLength)` (or use `http.MaxBytesReader`) inside `getRPCRequests` before calling `io.ReadAll`, so the tracing wrappers enforce the same size limit as the main codec path regardless of `Content-Length` header presence/correctness. Additionally, reject requests using chunked transfer encoding without an effective bound before any buffering occurs.

### Proof of Concept
1. Start a Kaia node with JSON-RPC HTTP enabled and `NEWRELIC_APP_NAME`/`NEWRELIC_LICENSE` (or `DD_TRACE_ENABLED=true`) set.
2. Send an HTTP POST request to the JSON-RPC endpoint using `Transfer-Encoding: chunked` and stream a very large (multi-GB) body without ever properly terminating a valid JSON-RPC payload.
3. Observe that `getRPCRequests` → `io.ReadAll(r.Body)` in `networks/rpc/http_newrelic.go`/`http_datadog.go` fully buffers the attacker-supplied stream in memory before `validateRequest`'s content-length check or the `io.LimitReader`-bounded codec in `networks/rpc/http.go` ever executes, causing memory usage to grow unbounded with the size of the attacker's stream, leading to OOM/DoS of the node process.

func getRPCRequests(r *http.Request) ([]*jsonrpcMessage, bool, error) {
	reqBody, err := io.ReadAll(r.Body)
	if err != nil {
		logger.Error("cannot read a request body", "err", err)

	codec := NewCodec(conn)

	defer codec.close()

	return codec.readBatch()
}

	if ddTracer != nil {
		handler = newDatadogHTTPHandler(ddTracer, handler)

	return &http.Server{
		Handler:      handler,
		ReadTimeout:  timeouts.ReadTimeout,
		WriteTimeout: timeouts.WriteTimeout,
		IdleTimeout:  timeouts.IdleTimeout,
	}
