### Title
`SignableTransaction::new` computes fee/vbytes without the OP_RETURN data output, producing transactions that underpay the intended fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `USDV.sol` computing minted amounts against the wrong denomination, `SignableTransaction::new` computes the transaction weight/vbytes — and therefore `needed_fee` and the minimum-relay-fee check — using only the `payments` outputs. The OP_RETURN `data` output is pushed onto `tx_outs` after `calculate_weight_vbytes` runs, so every signed transaction carrying `data` is larger than the size the fee was priced for.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at send.rs:194-202, but both weight calculations use the raw `payments` slice, which excludes it:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (send.rs:204)
- `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:225-226)

`calculate_weight_vbytes` (send.rs:62-127) builds a template `Transaction` whose `output` list contains only the `payments` entries plus the optional change output. An up-to-80-byte `data` payload creates an output of roughly `8 (value) + 1 (script len) + 1 (OP_RETURN) + 1..2 (push opcode) + data_len` bytes — up to ~92 bytes that are never priced.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is computed against the underestimated `vbytes`, so the transaction underpays relative to the caller's requested fee rate.
2. The minimum relay check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (send.rs:211) uses the same underestimated `vbytes`, so a transaction can pass `TooLowFee` validation while its *actual* fee rate is below the 1000 sat/kvB relay minimum, making the signed transaction non-relayable.
3. When change is used, `change = input_sat - payment_sat - fee_with_change` (send.rs:228-230) overpays the change output relative to the intended fee budget, distorting the accounting further (the change is still spendable, so this is misattribution rather than theft).
4. The weight-limit check `weight > MAX_STANDARD_TX_WEIGHT` (send.rs:241) also uses the weight without the data output, allowing a `TooLargeTransaction` escape for transactions at the boundary.

The processor path (`Bitcoin::make_signable_transaction` in `processor/src/networks/bitcoin.rs:446-452`) always passes `None` for `data`, so the reachable surface is the wallet API, where an unprivileged caller supplies `data` directly to `SignableTransaction::new`.

### Impact Explanation
Any caller constructing a transaction with a `data` payload produces a signed transaction whose effective fee rate is strictly lower than `fee_per_vbyte`, and can be below the network minimum relay fee despite passing the `TooLowFee` check. Such a transaction is rejected at broadcast, permanently stalling that signing attempt; for a threshold wallet this means the multisig produced a signature on a transaction that cannot confirm, and the fee/change amounts committed to in the sighash do not reflect the real transaction size. Like the USDV finding, the value transferred is computed in the wrong unit basis (vbytes of a transaction that isn't the transaction being built), yielding systematically incorrect amounts.

### Likelihood Explanation
Any `SignableTransaction::new` invocation with `Some(data)` triggers the miscalculation deterministically; the severity scales with payload size and how close `fee_per_vbyte` is to the relay minimum. At `fee_per_vbyte = 1` with an ~80-byte payload, the actual fee rate drops well below 1 sat/vB and the transaction cannot be relayed.

### Recommendation
Include the OP_RETURN data output in the template transaction passed to `calculate_weight_vbytes` — i.e., compute weight/vbytes over the full `tx_outs` (payments + data + optional change) rather than over `payments`. This makes `needed_fee`, the `TooLowFee` check, the change amount, and the `TooLargeTransaction` check all consistent with the transaction actually signed.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs behavior
// Construct a transaction with an 80-byte OP_RETURN payload and fee_per_vbyte = 1
let tx = SignableTransaction::new(
  vec![input],
  &payments,
  Some(change_script),
  Some(vec![0xAA; 80]), // data output
  1,                    // 1 sat/vbyte == minimum relay fee
).unwrap();

// needed_fee was priced on vbytes computed WITHOUT the OP_RETURN output:
//   needed_fee = 1 * vbytes(payments-only-tx)
// The final tx includes the ~92-byte OP_RETURN output, so
//   tx.vsize() > vbytes_used_for_fee
//   effective fee rate = needed_fee / tx.vsize() < 1 sat/vbyte
// => below DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB), so the signed
//    transaction is rejected by relay despite passing the TooLowFee check.
```

```rust
  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
```
