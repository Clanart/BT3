### Title
Cached FROST preprocess reused across distinct `sign()` calls enables validator key recovery via nonce reuse - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The Sparkle bug class — a signature produced/accepted for data other than what was bound — maps onto Serai's coordinator-side MuSig/FROST wrapper, where the *same* private nonces are deterministically reused to sign attacker-influenced inputs. `SigningProtocol::preprocess_internal` caches a 32-byte preprocess seed in the DB keyed solely on `context` (for `DkgConfirmer`, `("DkgConfirmer", attempt)`), and `share_internal` reconstructs the sign machine from that seed on every call, then calls `SignMachine::sign` with attacker-supplied preprocesses and a caller-supplied `msg`. Nothing binds the cached nonce to the preprocess set or message, and the cached seed is never deleted.

### Finding Description

`preprocess_internal` stores `CachedPreprocess` under only `self.context` (signing_protocol.rs:123–145). `share_internal` calls `self.preprocess_internal(participants).0` and then `machine.sign(preprocesses, msg)` with `preprocesses` parsed via `read_preprocess` (untrusted bytes, in-scope) and `msg` = `set_keys_message(...)` influenced by the `key_pair` argument (signing_protocol.rs:150–180, 288–301). `complete` additionally re-invokes `share_internal` to rebuild the machine, signing a second time under the same seed (signing_protocol.rs:312–327).

In `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:385–398), the share is `s = (d + ρ·e) + c·x`, where `d`, `e` come from the cached seed (identical every call), `ρ` is the binding factor over the attacker-influenced commitments/message (sign.rs:361–371, nonce.rs:161–191), `c` is the Schnorrkel HRAm challenge over the message, and `x` is the validator's MuSig secret (derived from `self.key`, its actual validator key). Shares are broadcast publicly.

Two attack shapes, both from public inputs:

- Same preprocess set, different message (`key_pair`/signer-set variation): `s1 − s2 = (c1 − c2)·x` ⇒ `x = (s1−s2)/(c1−c2)`.
- Distinct preprocess sets (distinct ρ) or mixed variations: each share gives one linear equation `s_i = d + ρ_i·e + c_i·x` over the three unknowns `d, e, x`; three signed shares under the same `attempt` fully recover `x`.

The file's own header concedes the hazard — "it is explicitly unsafe to reuse nonces across signing sessions" and "nonce re-use [occurs if] the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — but relies on BFT finality of received messages, which does not constrain *which subsets* of valid preprocesses get aggregated or that `share()` and `complete()` are each invoked exactly once per attempt. It also claims rebuilds "re-decide nonces," which is false: the seed persists in the DB (`CachedPreprocesses`), so a crash/restart reuses the same nonces. This directly violates `SignMachine::from_cache`'s contract that "the preprocess must be deleted so it's never reused" (crypto/frost/src/sign.rs:216–224).

### Impact Explanation

Recovery of `x` — the validator's Ristretto private key behind its MuSig share — from observed public signature shares. This key is the validator's root-of-trust key used to confirm DKG results on-chain; recovering it lets the attacker impersonate the validator in subsequent confirmation/signing protocols (unintended-message signing). Key share recovery from public shares is an accepted impact class.

### Likelihood Explanation

Requires the victim validator's coordinator to execute `sign` more than once under a single `attempt` context with differing preprocesses or message — reachable when `share()`/`complete()` are driven by distinct finalized preprocess submissions or on a mid-attempt restart. Preprocesses are untrusted bytes via `read_preprocess`, so a malicious validator controls ρ directly. Medium-high conditional likelihood; severity of outcome is critical.

### Recommendation

Key the cached preprocess on a hash of the full signing inputs (participants, preprocess commitments, message) or burn the cached seed after first `sign`, re-generating nonces when inputs change; alternatively include the message/signing-set commitment in the `CachedPreprocesses` key so a mismatch errors rather than silently reusing nonces.

### Proof of Concept

1. As a validator, submit preprocess commitments for a DKG-confirmation attempt; victim coordinator calls `DkgConfirmer::share(preprocesses_A, key_pair)` → publishes `s1 = d + ρ1·e + c1·x`.
2. Trigger a second `share()`/`complete()` under the same `attempt` with a different preprocess subset `preprocesses_B` (or a different `key_pair`) → `s2 = d + ρ2·e + c2·x`.
3. Repeat once more for `s3` if needed, then solve the linear system `s_i = d + ρ_i·e + c_i·x` over the Ristretto scalar field for `x` (ρ_i, c_i are publicly computable from the transcript definitions in sign.rs:361–379 and schnorrkel's HRAm).
4. Verify `G·x` equals the victim's MuSig verification share / validator key.

Note: full certainty on step 2's trigger multiplicity would require tracing `handle.rs` call paths, which could not be fully verified; the code path and the unconditional nonce reuse are confirmed.
