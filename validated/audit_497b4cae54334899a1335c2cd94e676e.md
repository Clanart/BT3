### Title
`git clone --recursive` explicitly disables Git's built-in clone-time protection against malicious submodule/hook payloads - (File: `app/src/lib/git/clone.ts`)

### Summary
The reported minievm bug is about a permission check that exists at one call boundary (the `Create`/`Create2` message handlers) but is not enforced at the deeper mechanism (the actual EVM `CREATE` opcode), letting an attacker interpose an intermediary (a factory contract) that inherits trust and re-executes the restricted operation unchecked. The Desktop analog is structurally the same shape: Desktop's `clone()` performs a `git clone --recursive` against an attacker-controlled remote URL, but it explicitly forces off the safety mechanism Git itself added to guard exactly this "trusted top-level operation, untrusted nested object" pattern — the recursive submodule clone protection — by setting `GIT_CLONE_PROTECTION_ACTIVE=false`.

### Finding Description
`clone()` in `app/src/lib/git/clone.ts` builds the environment for the clone process and unconditionally sets: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself uses to re-invoke a nested/recursive `clone` step with hardened checks (the mitigation shipped for the class of clone-time submodule/hook attacks, i.e. CVE-2024-32004-style issues, where a crafted repository can smuggle executable hooks or unsafe symlinked paths through nested clone/checkout of submodules). Setting it to `'false'` tells Git that the protection is "already active" / should be skipped for the nested recursive clone step, which is the opposite of the intended use — it deliberately turns off Git's own guard for the exact code path (`clone --recursive`, i.e., attacker-controlled remote + nested submodules) that the report's underlying invariant is about: *a permission/safety check exists at one layer but a nested, attacker-reachable object can be used to bypass it.*

Here, the "permission check" analog is Git's clone-time protection against unsafe repository content encountered during recursive submodule cloning; the "factory contract" analog is a malicious submodule (or `.gitmodules` entry) inside the attacker's repository that the top-level, trusted `clone --recursive` invocation will process without the hardening that Git would otherwise apply.

Additional evidence that submodule content is treated with elevated trust elsewhere in the codebase reinforces that this is a real, reachable path: `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` can also enable `protocol.file.allow=always` for submodules via an `allowFileProtocol` flag, showing that submodule handling in this codebase already carries known allow-listing/relaxation knobs that are more permissive than top-level operations: [2](#0-1) 

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` actually suppresses Git's hardened re-exec/verification step during the nested submodule clone triggered by `--recursive`, then cloning any attacker-supplied or attacker-linked repository through Desktop's normal "Clone repository" flow (`app/src/ui/clone-repository/clone-repository.tsx` → `dispatcher.clone` → `clone()` in `app/src/lib/git/clone.ts`) could result in unsafe repository content (e.g. crafted submodule paths/symlinks or hook-bearing nested clones) being processed without the protection Git ships specifically to stop this. This maps directly to the "attacker controls a cloned/fetched repository ... resulting in code execution or file write outside the repo" impact category, since it removes a guard rail on precisely the operation (recursive clone of untrusted content) that guard rail exists for.

### Likelihood Explanation
Likelihood is moderate-to-high in terms of reachability: cloning arbitrary/untrusted URLs is a first-class, unprivileged, everyday user action in Desktop (`Clone repository` dialog, `x-github-client://clone` deep links, etc.), and `--recursive` is passed unconditionally on every clone, so every clone of an attacker-controlled repo goes through this weakened code path. The main uncertainty (which I could not fully verify without deeper access to the exact Git version's semantics of `GIT_CLONE_PROTECTION_ACTIVE`) is whether disabling this variable actually reopens a specific known CVE in the bundled `dugite`/Git version, or whether it's a deliberate, already-mitigated compatibility shim (e.g., to avoid Git refusing benign nested clones). This distinction changes the finding from "exploitable regression" to "hardening gap," so it should be confirmed against the exact Git version bundled with Desktop before treating this as confirmed-exploitable.

### Recommendation
- Verify against the bundled Git/dugite version whether `GIT_CLONE_PROTECTION_ACTIVE=false` actually disables the CVE-2024-32004-class protection for `clone --recursive`; if so, remove this override (or replace it with a value that does not defeat the check) so that the same protections applied to a normal `git clone --recursive` from the CLI apply inside Desktop.
- If the override exists to work around Git treating Desktop's own clone invocation as already-protected, that assumption should be re-validated: it must be true for *every* Git version Desktop bundles/supports, not just the one used during implementation.
- Apply the same review to the `allowFileProtocol` knob in `updateSubmodulesAfterOperation` (`app/src/lib/git/submodule.ts`) and confirm which call sites pass `true`, to ensure untrusted submodules cannot use `file://` to read/link arbitrary host paths.

### Proof of Concept
1. Attacker publishes a repository with a submodule (`.gitmodules`) engineered to exploit the class of issue that `GIT_CLONE_PROTECTION_ACTIVE` is designed to prevent (e.g. unsafe nested repository content processed during recursive submodule clone/checkout).
2. Victim uses Desktop's "Clone a repository" flow (or a deep link) to clone the attacker's URL; Desktop calls `clone()` in `app/src/lib/git/clone.ts`, which always sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and always passes `--recursive`. [1](#0-0) 
3. Because the protection variable is forced off, the recursive submodule clone step runs without the hardening Git normally applies to this exact scenario, potentially allowing the malicious submodule content to be written/processed unsafely on the victim's machine.

Note: I was unable to execute this against a live Git binary or confirm the exact CVE/behavior tied to `GIT_CLONE_PROTECTION_ACTIVE` in this sandbox, so step 3's exact exploit mechanics should be validated by a Devin session with terminal access before treating this as a confirmed, weaponizable vulnerability rather than a hardening regression.
