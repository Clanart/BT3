### Title
Missing `request.from` (module identity) check in `ExtrinsicIntents.onAccept` lets any pallet on the Hyperbridge state machine reach privileged upgrade/admin logic - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`ExtrinsicIntents.onAccept` (and the identical logic in `IntentGatewayV2.sol`) branches into privileged administrative actions — `NewDeployment`, `UpdateParams`, `SweepDust`, and critically `UpgradeContract` (an `ERC1967Utils.upgradeToAndCall`) — guarded only by checking that `request.source` equals the configured Hyperbridge state machine identifier. Unlike the `RedeemEscrow`/`RefundEscrow` branch, which calls `_authenticate()` to verify `request.from` against the specific registered gateway module address, the privileged branch never checks `request.from` at all.

### Finding Description
```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        _authenticate(incoming.request);   // checks request.from == registered module
        ...
    }
    // only hyperbridge is permitted to perform these actions
    if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
    if (kind == RequestKind.NewDeployment) { ... }
    else if (kind == RequestKind.UpdateParams) { ... }
    else if (kind == RequestKind.SweepDust) { ... }
    else if (kind == RequestKind.UpgradeContract) {
        (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
        ERC1967Utils.upgradeToAndCall(newImpl, initData);
    }
}
```
`request.source` identifies only the *chain* the message came from (the Hyperbridge/Nexus state machine); it says nothing about *which module/pallet on that chain* originated it. ISMP's own model distinguishes these two fields precisely so that `IsmpModule::on_accept` implementations can bind trust to a specific sender module, not merely a specific chain — this is exactly what `_authenticate()` does for the escrow branch by comparing `request.from` against `_instance(request.source)`.

Because the privileged branch omits this `request.from` check, *any* pallet compiled into the Hyperbridge/Nexus runtime that can call `IsmpDispatcher::dispatch_request` with a `to` targeting this contract's address and attacker-influenced `body` bytes is treated as equally trusted as the intended governance module. The runtime already contains several dispatch primitives of this shape (arbitrary `to`, attacker/pallet-controlled `body`), e.g. `pallet_ismp_demo::dispatch_to_evm` and `pallet-host-executive`/`intents-coprocessor`'s internal `dispatch(state_machine, to, body)` helper, which build a `DispatchPost{ to, body, .. }` and send it via `IsmpDispatcher`: [4](#0-3) [5](#0-4) 

If a body-controlling path exists (or is later added) from an unprivileged/insufficiently-restricted origin into any such dispatcher with `to` = the `ExtrinsicIntents`/`IntentGatewayV2` proxy address, the attacker can construct `body = bytes1(RequestKind.UpgradeContract) ++ abi.encode(maliciousImpl, initData)`. Since only `request.source` is verified, the check passes as long as the message legitimately originates on the Hyperbridge chain — the specific sending pallet is never checked — and `ERC1967Utils.upgradeToAndCall` swaps the proxy's implementation to attacker-controlled code, executing with full control over the contract's storage and any escrowed order funds. This mirrors the Marmo bug precisely: the destination trusts an "implementation" selection (here, effectively "which pallet is authorized to drive privileged logic") without verifying its identity, only its origin chain.

### Impact Explanation
A successful exploitation results in complete takeover of the `ExtrinsicIntents`/`IntentGatewayV2` proxy contract via `UpgradeContract`, or unauthorized `SweepDust`/`UpdateParams`/`NewDeployment` calls that can redirect protocol dust, change fee parameters, or register a fraudulent gateway `Deployment` for another chain. Any of these can lead to loss of escrowed order funds, false gateway-instance trust bindings (enabling forged `RedeemEscrow`/`RefundEscrow` down the line since `_instance()` is used by `_authenticate`), and unauthorized execution — squarely within the "stealing or loss of funds," "unauthorized transaction or execution," and "false proof/state acceptance" impact categories.

### Likelihood Explanation
The vulnerable check is a straightforward code-review finding: the asymmetry between the authenticated escrow branch (`_authenticate` checks `request.from`) and the unauthenticated privileged branch (`request.source` only) is directly visible in the same function. Exploitability at runtime depends on whether any dispatch pathway in the connected Substrate runtime allows a `body`/`to` combination to reach this contract without being restricted to the intended governance pallet — several `dispatch_request`-calling helpers with attacker-adjacent `to`/`body` parameters exist in the codebase (`pallet_ismp_demo::dispatch_to_evm`, `intents-coprocessor::dispatch`), though I was not able to fully trace within budget whether their current callers already restrict origin/body enough to block this specific `RequestKind::UpgradeContract` payload. This should be verified with a background Devin session that traces every `IsmpDispatcher::dispatch_request` caller in the Hyperbridge/Nexus runtime for reachable, attacker/pallet-controlled `body` bytes targeting `IntentGatewayV2`/`ExtrinsicIntents`.

### Recommendation
Add a `request.from` binding check in the privileged branch of `onAccept`, analogous to `_authenticate()`, verifying that `request.from` equals the specific, registered governance/Hyperbridge-core module identifier (not merely that `request.source` equals the Hyperbridge state machine). This closes the module-identity gap and ensures privileged actions (especially `UpgradeContract`) can only be triggered by the one intended sender module.

### Proof of Concept
1. Identify (or introduce, if one doesn't yet exist) any pallet in the Hyperbridge/Nexus runtime that lets a caller (even root or a pallet whose author didn't intend it as "the" governance origin) call `IsmpDispatcher::dispatch_request` with `dest = Evm(<intent gateway chain>)`, `to = <ExtrinsicIntents/IntentGatewayV2 proxy address>`, and a `body` value equal to `bytes1(uint8(RequestKind.UpgradeContract)) ++ abi.encode(maliciousImplementation, initCalldata)`.
2. The message is relayed and delivered to the EVM host, which calls `ExtrinsicIntents.onAccept`.
3. `onAccept` checks only `keccak256(request.source) == keccak256(hyperbridge)` — true, since the message legitimately originated on the Hyperbridge chain — and never checks `request.from`.
4. `ERC1967Utils.upgradeToAndCall(maliciousImplementation, initCalldata)` executes, replacing the proxy's implementation and/or running arbitrary init logic with full control of the contract's storage and escrowed funds.
