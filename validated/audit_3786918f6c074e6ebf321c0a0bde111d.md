### Title
`Scanner::scan_block` credits immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The audit finding's bug class is a cost-bearing restriction (the `LOCKTIME` lock) that is silently bypassed by a condition (`unlockOverride`), letting an actor obtain the benefit (gauge weight) without paying the intended cost. In Serai's Bitcoin scanner, `Scanner::scan_block` iterates over every transaction in a block — including `block.txdata[0]`, the coinbase — and feeds each through `scan_transaction`, which matches only on `output.script_pubkey` and immediately wraps the match in a `ReceivedOutput` marked spendable. There is no check that the matched output comes from a coinbase transaction, which by consensus cannot be spent for 100 blocks. The maturity "cost" exists in the protocol but the crediting path doesn't enforce it, so funds are reported as received-and-spendable when they are not spendable.

### Finding Description
`scan_transaction` at networks/bitcoin/src/wallet/mod.rs:199-214 pushes a `ReceivedOutput` for any output whose `script_pubkey` is registered in `self.scripts`, recording only `offset`, `output`, and `outpoint`. It carries no flag distinguishing coinbase provenance and performs no maturity check. `scan_block` at networks/bitcoin/src/wallet/mod.rs:221-227 calls `scan_transaction` unconditionally on `block.txdata`, including index 0 (the coinbase). A `ReceivedOutput` obtained this way flows into the signing path in `send.rs`, which will attempt to build a transaction spending an outpoint that Bitcoin consensus rejects as immature. The only guard is a doc comment noting "a post-processing pass is needed" — the API itself returns the unspendable output indistinguishably from spendable ones.

### Impact Explanation
An external, unprivileged party (any miner) can craft a coinbase transaction paying to the vault's watched `script_pubkey` (the base address `p2tr_script_buf(key)` is registered automatically by `Scanner::new`, so no offset registration is even required). The scanner then reports this output as received. Any downstream consumer that treats `ReceivedOutput`s as spendable inputs will construct transactions that are invalid by consensus (immature coinbase spend), and worse, a coinbase output can disappear entirely via reorg within the 100-block window — the outpoint is not just locked, it may never exist on the eventual canonical chain. This matches the accepted impact class "funds reported received that are not spendable".

### Likelihood Explanation
Coinbase outputs paying to arbitrary Taproot scripts are trivially constructible by any miner — a coinbase is the one transaction type where the sender pays no fee and no existing UTXO is required. While the doc comment warns about maturity, the default, convenient API (`scan_block`) has the unsafe behavior and the hazard is silent: nothing in `ReceivedOutput` lets a caller detect the case after the fact without re-fetching the block. Any integrator scanning blocks for received outputs hits this path unless they independently reimplement filtering via `scan_transaction(&block.txdata[1..])`.

### Recommendation
`scan_block` should skip `block.txdata[0]`, or return coinbase-derived outputs in a distinct type/flag so callers cannot confuse them with spendable outputs. At minimum, `ReceivedOutput` should carry a `coinbase: bool` (or block-height metadata) so the spend path in `send.rs` can reject immature inputs rather than emitting consensus-invalid transactions.

### Proof of Concept
```rust
// A miner builds a block whose coinbase pays to the scanned key's script.
let mut scanner = Scanner::new(group_key).unwrap();
let coinbase = Transaction {
  // ... coinbase tx with output[0].script_pubkey == p2tr_script_buf(group_key)
};
let block = Block { header, txdata: vec![coinbase] };
let received = scanner.scan_block(&block);
assert_eq!(received.len(), 1); // immature coinbase output reported as ReceivedOutput
// send.rs will now happily spend received[0].outpoint -> consensus-invalid tx
```
The triggering input is entirely under an external miner's control (`block.txdata[0]` fed to `scan_block`), requires no privileges, and the resulting `ReceivedOutput` is indistinguishable from a mature, spendable one.
