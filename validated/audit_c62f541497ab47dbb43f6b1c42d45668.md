### Title
`castVotes` unconditionally harvests ALL pools for the delegate pool, so a single reverting reward-token transfer permanently freezes voting/bribe-harvesting for every user - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.castVotes()` is a public, unprivileged function that already iterates over **every** registered pool (`pools.length`, not a caller-chosen subset) to build the vote deltas and calls `wombatStaking.vote(...)`. It then unconditionally calls `IDelegateVoteRewardPool(delegatedPool).harvestAll()`, which in turn calls `claimAllBribes(address(this))`, looping over **all** pools the delegate has voted in and pushing reward tokens directly to the delegate/rewarder contracts via `safeTransfer`. Because these are push-transfers executed inside a single atomic, shared, protocol-wide function, one reverting transfer anywhere in the loop reverts the entire `castVotes()` call for every caller, not just the account tied to the problematic token.

### Finding Description
`castVotes()` builds vote deltas for all pools and forwards them to `wombatStaking.vote()` [1](#0-0) . Inside `WombatStaking.vote()`, harvested bribe rewards are pushed directly with `safeTransfer` to `bribeFeeCollector` and `bribeManager` for protocol/caller fees, and then queued into each pool's rewarder [2](#0-1) .

After that, if a `delegatedPool` is configured, `castVotes()` unconditionally calls `harvestAll()` [3](#0-2) , which calls `claimAllBribes(address(this))` [4](#0-3) . `claimAllBribes` loops over the **entire global `pools` array** (not a caller-supplied subset) and, for every pool the delegate has voted in, calls `IBribeRewardPool(pool.rewarder).getReward(_for, _for)` [5](#0-4) , which directly `safeTransfer`s reward tokens to the recipient [6](#0-5) .

This mirrors the exact bug class in the external report: a push-based token transfer to a fixed recipient, executed as part of a larger, shared state-transition, that can revert (e.g. a paused/blacklist-capable token, or an ERC-777-style token with a receiver hook that reverts on transfer) and thereby block the whole transaction. The critical difference from a simple self-DoS is that `castVotes()` is not scoped to the caller's own position — it always iterates the full `pools` array and always triggers `harvestAll()` for every pool the delegate has voted in, regardless of which pools the caller cares about. Any ordinary/unprivileged wallet calling `castVotes()` on any pool triggers harvesting for all pools tied to the delegate; if the reward token of just one of those pools reverts on transfer (which can occur without any admin misbehavior — bribe reward tokens can be arbitrary ERC-20/ERC-777 tokens set by the bribe issuers on the underlying Wombat bribe contracts, not by MagpieXYZ's admins), `castVotes()` reverts for every subsequent caller, system-wide, indefinitely.

### Impact Explanation
Because `castVotes()` reverting blocks:
- Vote casting for **all** pools and **all** vlMGP voters (not just the one tied to the bad token),
- Harvesting/distribution of bribe rewards into every pool's rewarder (`queueNewRewards`), freezing unclaimed yield for all voters,
- The delegate pool's own reward accrual and distribution (`harvestAll`/`_manageRewards`),

this is a protocol-wide, permanent (>24h, effectively indefinite until code/contract change) freeze of voting-result-affecting mechanics and of unclaimed bribe yield for every ordinary vlMGP voter — matching the "permanent freezing of unclaimed yield" / "governance voting result manipulation via freeze" impact bar.

### Likelihood Explanation
Likelihood is realistic without any privileged action: bribe reward tokens are token addresses returned by third-party Wombat bribe contracts (`IWombatBribe(bribesContract).rewardTokens()`), which are outside the control of MagpieXYZ's admins and can be arbitrary tokens (including tokens that later become paused/blacklist-capable for the `delegatedPool`/rewarder address, or ERC-777 tokens with reverting hooks). Any single such token appearing among the pools the delegate has voted for is sufficient to permanently break `castVotes()` for the entire system, and the code path (`castVotes → harvestAll → claimAllBribes → getReward → safeTransfer`) is reachable from an ordinary wallet's transaction with no special privileges.

### Recommendation
Decouple the shared, protocol-wide vote-casting/fee-forwarding logic from per-pool reward harvesting/transfers. Use a pull-based pattern for reward claiming (accumulate claimable balances instead of push-transferring during `castVotes`), or wrap each per-pool transfer/harvest in a try/catch so a single failing token cannot revert the entire `castVotes()` call for all pools and all users.

### Proof of Concept
1. A bribe reward token for one of the pools the `delegatedPool` has voted for becomes a token that reverts transfers to the `DelegateVoteRewardPool` contract address (e.g., blacklist-capable stablecoin blacklists the contract, or an ERC-777 token's hook reverts).
2. Any ordinary user calls `WombatBribeManager.castVotes(false)`.
3. `castVotes()` iterates `pools` (all pools) and calls `wombatStaking.vote(...)`, then unconditionally calls `delegatedPool.harvestAll()` [3](#0-2) .
4. `harvestAll()` → `claimAllBribes(address(this))` iterates every pool the delegate voted in and calls `getReward` [7](#0-6) , which performs `IERC20(rewardToken).safeTransfer(_account, reward)` [6](#0-5) .
5. The transfer for the malicious/blacklisted token reverts, bubbling up through `claimAllBribes` → `harvestAll` → `castVotes`, reverting the whole transaction.
6. Every subsequent call to `castVotes()` by any user reverts identically, permanently freezing voting and bribe-reward distribution for the entire protocol until the delegate pool or bribe list is manually remediated by governance.
