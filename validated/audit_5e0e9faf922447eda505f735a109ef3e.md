## Verdict

Confirmed: no `GIT_ALLOW_PROTOCOL` or `protocol.<ext|fd>.allow=never` restriction is set anywhere on the code paths that construct the environment for a clone, and the `clone_url`/`url` string reaches `git`'s argv unfiltered. However, this is only exploitable through an untrusted/attacker-controlled API *server* (i.e., a malicious or compromised GitHub Enterprise endpoint the user has explicitly added), not through GitHub.com itself, since GitHub.com computes `clone_url`/`ssh_url` server-side and never echoes attacker-supplied strings into that field.

### Finding Description
`app/src/lib/git/clone.ts`'s `clone()` builds the argv for `git clone` and appends the caller-supplied `url` verbatim after `--`: [1](#0-0) 

The environment used for the operation is produced by `envForRemoteOperation()`/`envForProxy()` in `app/src/lib/git/environment.ts`, which only deals with authentication headers and http(s) proxy resolution — it never sets `GIT_ALLOW_PROTOCOL` or any `protocol.*.allow` config: [2](#0-1) [3](#0-2) 

`clone.ts`'s only defensive check, `isClonePathSensitive()`, validates the destination *path*, not the *scheme* of `url`: [4](#0-3) 

The `url` value that ultimately reaches `clone()` can originate from `IAPIRepository.clone_url`/`ssh_url`, fetched via `API.fetchRepositoryCloneInfo()`: [5](#0-4) 

For **GitHub.com**, the `repos/{owner}/{name}` endpoint is `api.github.com`, and GitHub.com always computes `clone_url`/`ssh_url` server-side as `https://github.com/...` / `git@github.com:...` — an attacker cannot inject an arbitrary string (e.g. `ext::...`) into that field through any legitimate GitHub.com API response. The endpoint resolution logic confirms `github.com`/`api.github.com` always maps to the fixed dotcom endpoint: [6](#0-5) [7](#0-6) 

For a **GitHub Enterprise (GHES-compatible) account**, however, the endpoint is derived from whatever host the user configured, and the JSON response (including `clone_url`) is fully controlled by that server: [8](#0-7) 

So if a user adds an Enterprise account pointing at an attacker-controlled or compromised "GHES-compatible" server, that server can respond to `GET repos/{owner}/{name}` with `clone_url: "ext::sh -c ..."`, which then flows through `resolveCloneInfo()` → `dispatcher.clone(url, path, ...)` in the Clone dialog to `clone.ts`'s `clone()` unchanged: [9](#0-8) [10](#0-9) 

The same unfiltered pass-through also exists for `updateRemoteUrl()` (used when refreshing repo metadata from the API) and `_convertRepositoryToFork()`, both of which take `apiRepo.clone_url` and feed it to `gitStore.setRemoteURL()`: [11](#0-10) [12](#0-11) 

Git's `ext::`/`fd::` remote helper transports are, by default, permitted at the "user" trust level (`protocol.ext.allow=user`), which git treats as satisfied for any top-level, directly-invoked `git clone <url>` command (i.e., `GIT_PROTOCOL_FROM_USER` is left at its default of allowing user-initiated protocols) — it is not gated by `GIT_ALLOW_PROTOCOL` unless Desktop explicitly restricts it, which it does not.

### Impact Explanation
If reachable, this results in arbitrary command execution when the user clones/refreshes a repository from a malicious or compromised GitHub Enterprise-style endpoint — full RCE on the user's machine.

### Likelihood Explanation
Low-to-moderate. The Proof of Concept requires the victim to have added and be actively using an account pointed at an attacker-controlled or compromised Enterprise/GHES endpoint (the field is never attacker-controllable for real GitHub.com responses, since dotcom computes it server-side). This is a real gap (missing `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow=never` hardening for any remote-URL string sourced from an API object), but the attacker-controlled-API-object precondition here specifically requires a rogue/compromised Enterprise server rather than github.com itself, narrowing the realistic blast radius compared to the "any GitHub API repo object" framing in the question.

### Recommendation
- In `app/src/lib/git/environment.ts`'s `envForRemoteOperation()` (used by `clone.ts`, `checkout.ts`, `push`/`fetch`, etc.), always set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or the equivalent `-c protocol.ext.allow=never -c protocol.fd.allow=never` args) so that any URL sourced from an API object or user input can never invoke local/`ext`/`fd` transport helpers.
- Additionally validate any `clone_url`/`ssh_url` value taken from `IAPIRepository` against the `https|ssh|git` scheme allowlist (e.g., via `parseRemote()`) before it is passed to `clone()`, `setRemoteURL()`, or `updateRemoteUrl()`.

### Proof of Concept
1. Add a GitHub Enterprise account whose endpoint is controlled by the attacker (or a compromised legitimate GHES instance).
2. From that account, respond to `GET repos/{owner}/{name}` with `{"clone_url": "ext::sh -c \"touch /tmp/pwned\"", ...}`.
3. User selects/clones that repository (or Desktop calls `fetchRepositoryCloneInfo`/`updateRemoteUrl`/`_convertRepositoryToFork` for it).
4. `clone()` in `app/src/lib/git/clone.ts` runs `git ... clone --recursive -- ext::sh -c "touch /tmp/pwned" <path>` with no `GIT_ALLOW_PROTOCOL` restriction, and git invokes the attacker's command via the `ext` helper.

```typescript
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```

```typescript
export async function envForProxy(
  remoteUrl: string,
  env: NodeJS.ProcessEnv = process.env,
  resolve: (url: string) => Promise<string | undefined> = resolveGitProxy
): Promise<Record<string, string | undefined> | undefined> {
  const protocolMatch = /^(https?):\/\//i.exec(remoteUrl)

  // We can only resolve and use a proxy for the protocols where cURL
  // would be involved (i.e http and https). git:// relies on ssh.
  if (protocolMatch === null) {
    return
  }

  // Note that HTTPS here doesn't mean that the proxy is HTTPS, only
  // that all requests to HTTPS protocols should be proxied. The
  // proxy protocol is defined by the url returned by `this.resolve()`
  const proto = protocolMatch[1].toLowerCase() // http or https

  // We'll play it safe and say that if the user has configured
  // the ALL_PROXY environment variable they probably know what
  // they're doing and wouldn't want us to override it with a
  // protocol-specific proxy. cURL supports both lower and upper
  // case, see:
  // https://github.com/curl/curl/blob/14916a82e/lib/url.c#L2180-L2185
  if ('ALL_PROXY' in env || 'all_proxy' in env) {
    log.info(`proxy url not resolved, ALL_PROXY already set`)
    return
  }

  // Lower case environment variables due to
  // https://ec.haxx.se/usingcurl/usingcurl-proxies#http_proxy-in-lower-case-only
  const envKey = `${proto}_proxy` // http_proxy or https_proxy

  // If the user has already configured a proxy in the environment
  // for the protocol we're not gonna override it.
  if (envKey in env || (proto === 'https' && 'HTTPS_PROXY' in env)) {
    log.info(`proxy url not resolved, ${envKey} already set`)
    return
  }

  const proxyUrl = await resolve(remoteUrl).catch(err => {
    log.error('Failed resolving Git proxy', err)
    return undefined
  })

  return proxyUrl === undefined ? undefined : { [envKey]: proxyUrl }
}
```
