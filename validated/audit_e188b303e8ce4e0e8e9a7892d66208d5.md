## Analog Found: Stale index-based diff-line selection can silently mis-stage content in Desktop's commit flow

### Title
Positional (index-based) diff-line selection is blindly re-applied to a freshly re-fetched working-directory diff during staging, allowing silent inclusion of unintended lines in a commit - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The C4 report's root cause is a scheme that uses **position** (`tokenId % 100`) as the identity for "which founder owns this slot" instead of a scheme that is robust to how the underlying sequence actually plays out, letting the real-world outcome silently diverge from the user's configured intent. GitHub Desktop has a structurally identical pattern in its partial-commit ("stage some lines") feature: `DiffSelection` records *only positional line indices* (`hunk.unifiedDiffStart + lineIndex`) as the identity of a "selected" line, and that positional selection is re-applied against a diff that is **independently re-fetched at staging time**, not the diff the user actually reviewed.

### Finding Description
`DiffSelection.isSelected(lineIndex)` determines inclusion purely by absolute line index within a diff, with no notion of line content or identity: [1](#0-0) 

This selection object is captured against the diff the user is viewing in the Changes tab. But when the user commits, `createCommit` → `stageFiles` → `applyPatchToIndex` **re-fetches the working directory diff from disk again**, independent of whatever diff was rendered in the UI: [2](#0-1) 

The (old, UI-time) `file.selection.isSelected(absoluteIndex)` is then applied directly against this newly-fetched diff's hunks to build the patch that gets `git apply --cached`'d: [3](#0-2) 

The developers are aware that a diff's line structure can drift and that stale index-based selections stop corresponding to the same semantic lines — but the only place this is defended against is the **UI refresh path** (`updateChangesWorkingDirectoryDiff`), which prunes selection to `selectableLines` computed from a newly loaded diff: [4](#0-3) 

That comment explicitly states: *"The diff might have changed dramatically since last we loaded it... we'll settle on just updating the selectable lines."* Critically, this reconciliation only happens in the Changes-tab diff-loading code path. The commit/staging code path (`_commitIncludedChanges` → `createCommit` → `applyPatchToIndex`) never calls this reconciliation — it passes the working-directory file's selection object straight through and lets `applyPatchToIndex` fetch a *third*, independent copy of the diff at patch-build time: [5](#0-4) 

So there are three points in time where the diff can be computed (initial render, `updateChangesWorkingDirectoryDiff` refresh, and `applyPatchToIndex`'s own re-fetch), and only the middle one revalidates the selection against structural changes. If the working tree changes between the last UI-visible diff and the staging-time diff — e.g., because a git-attribute-driven line-ending normalization, a build/format tool, an editor autosave, or any other process writes to the tracked file after the user made their line selections but before they click "Commit" — the absolute indices in the stale `DiffSelection` will now point at different, unrelated lines in the new hunk layout.

### Impact Explanation
Because the identity of a "selected line" is purely positional and is applied to a diff object different from the one the user visually inspected, Desktop can silently stage/commit lines the user never intended to include (or omit lines the user did select), without any error, warning, or diff re-confirmation. This is a direct analog of the C4 finding's core defect: using positional/sequential identity as a proxy for semantic ownership, which breaks silently whenever the underlying sequence shifts. Here the "broken invariant" is: *what the user visually approved for commit == what actually gets included in the patch applied to the index*. The attacker-controlled surface is the content of a cloned/fetched repository and its working tree state (e.g. via `.gitattributes`-driven normalization behavior that is repo-controlled, or any process racing the commit), which can shift the diff's hunk layout between UI-render time and staging time, causing corruption of what the user actually commits or pushes.

### Likelihood Explanation
This requires no elevated privilege and no unnatural user action beyond the normal "select some lines, then commit" workflow that Desktop explicitly supports. The precondition — that the working directory diff can change between when it is displayed and when `applyPatchToIndex` re-fetches it — is not hypothetical: the codebase itself documents and partially guards against this exact scenario in `updateChangesWorkingDirectoryDiff`, but that guard is not wired into the staging/commit path. The likelihood of the diff drifting during that window scales with how long the user takes between selecting lines and clicking Commit, and with the presence of any other repo-triggered mutator of the working tree (auto-formatters, git attribute filters, git hooks that run before `pre-commit` staging, or background file watchers reacting to repository content).

### Recommendation
- Before building the patch in `applyPatchToIndex`/`formatPatch`, revalidate the caller-supplied `DiffSelection` against the diff that is about to actually be used to build the patch (the same reconciliation logic already implemented in `updateChangesWorkingDirectoryDiff`'s `withSelectableLines` should be applied here too), rather than trusting a selection captured against a potentially stale diff.
- Alternatively, thread through and diff-check the diff object that generated the selection (e.g. compare hunk headers/line counts, or a content hash) at staging time, and abort/re-prompt the user if the working-directory diff has changed since the selection was made, rather than silently applying stale indices to new content.
- Add a regression test that changes the file's diff shape (e.g., inserts unrelated lines) between selection construction and `createCommit`/`applyPatchToIndex` invocation, asserting that either the operation fails safely or the correct semantic lines are staged.

### Proof of Concept
Conceptual reproduction, given local code evidence (not independently executed):
1. User selects specific lines to stage in the Changes tab, producing a `DiffSelection` tied to a diff loaded at time T1 (via `updateChangesWorkingDirectoryDiff`). [6](#0-5) 
2. Before the user clicks "Commit", some other write happens to the same tracked file in the working directory (e.g. by a linter/formatter, or a repo-defined `.gitattributes` normalization triggered on the next `git add`), shifting the hunk/line layout without the Changes tab necessarily re-rendering in time.
3. The user clicks "Commit". `_commitIncludedChanges` passes the (unrevalidated) selected files straight to `createCommit`. [7](#0-6) 
4. `createCommit` → `stageFiles` → `applyPatchToIndex` calls `getWorkingDirectoryDiff(repository, file)` again, fetching the diff at time T2 (post-write), and builds the patch using the T1 `DiffSelection`'s absolute indices against the T2 diff's hunks. [8](#0-7) 
5. Because `isSelected` only checks position, not content, lines at those same absolute indices in the T2 diff — which may now correspond to entirely different content — get included/excluded, and `git apply --cached` stages that patch silently, with no warning that the staged result diverges from what the user selected in the UI.
