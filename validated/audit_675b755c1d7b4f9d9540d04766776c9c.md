### Title
Unauthenticated dust-value donations are credited as spendable balance by `Scanner`, letting a griefer inflate reported funds and force economically-unspendable inputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Arcadia report describes a griefing vector where an attacker donates tokens directly to a pool, corrupting the pool's internal accounting (utilization/interest) because the system cannot distinguish "real" liquidity from unsolicited transfers. The same class exists in `bitcoin-serai`: `Scanner::scan_transaction`/`scan_block` credits *any* on-chain output whose `script_pubkey` matches a registered script — regardless of value or economic spendability — as a `ReceivedOutput` indistinguishable from a legitimate deposit. An unprivileged party can send dust outputs (< `DUST` = 546 sat, or any output whose value is less than the marginal fee cost of spending it) to the multisig's tweaked address, inflating the balance the scanner reports while those outputs can only be spent at a net loss.

### Finding Description
`Scanner` maintains a map of `ScriptBuf -> Scalar` offsets and `scan_transaction` pushes a `ReceivedOutput` for every transaction output matching a registered script, with no filter on `output.value`:

`networks/bitcoin/src/wallet/mod.rs`
```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

Any third party can compute the multisig address (it is a public P2TR key) and craft a transaction paying it dust — e.g. via a miner, or outputs just above relay dust that are still below the fee cost of an added input. These appear in scan results identically to real deposits.

On the spend side, `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`) enforces `DUST` only on *payments* (line 165-169), never on *inputs*. Every `ReceivedOutput` the caller feeds in adds a full Taproot input's weight to `needed_fee` (lines 204-206, via `calculate_weight_vbytes`), while contributing `input.output.value` to `input_sat` (line 175). An input worth less than `fee_per_vbyte * input_vbytes` is net-negative: spending it destroys value relative to leaving it, yet the scanner and wallet surface it as ordinary balance.

### Impact Explanation
- Reported balance is inflated by attacker-controlled, economically-unspendable outputs — the analog of donated "liquidity" corrupting pool accounting. Any downstream consumer that sums `ReceivedOutput::value()` overestimates spendable funds.
- If inputs are selected naively (e.g. sweep-all), griefed dust inputs raise `needed_fee` and can push an otherwise-valid transaction into `NotEnoughFunds`/`TooLargeTransaction` or silently burn treasury value into fees.
- Like the report's mitigation, the attacker's donation is a real cost to them, bounding severity to Medium.

### Likelihood Explanation
Fully reachable by an unprivileged party: the P2TR output key is public, and anyone can broadcast or mine a transaction creating a matching `script_pubkey` output. No validator status, key material, or protocol interaction is required. Impact is bounded because each griefed output costs the attacker its value, and a careful caller can filter inputs — but the library provides no signal (e.g. a value floor or spendability flag) to do so.

### Recommendation
Mirror the report's fix ("do not allow borrowing more than total realised liquidity" → do not count outputs that cannot be net-positive to spend):
- In `Scanner::scan_transaction`, skip (or separately flag) outputs below a configurable economical-spend threshold, or expose `output.value` vs estimated input-fee cost on `ReceivedOutput` so callers can filter.
- In `SignableTransaction::new`, reject or ignore inputs whose `value` is below the marginal fee attributable to that input's weight.

### Proof of Concept
1. Multisig key `K` is tweaked via `tweak_keys`/`p2tr_script_buf` → public address `A`; `Scanner::new(K_tweaked)` registers `A`'s script.
2. Griefer broadcasts a transaction with N outputs paying `A`, each with `value` in `[1, input_fee_cost)` (e.g. 200 sats at prevailing feerates). These can be mined despite being below standard dust relay limits, or set just above `DUST` for relay but below spend cost.
3. `scanner.scan_block(block)` returns N `ReceivedOutput`s; any consumer summing `value()` overcounts spendable balance.
4. A sweep transaction built with `SignableTransaction::new(all_received, payments, change, ...)` now includes the dust inputs: `input_sat` barely rises while `needed_fee` grows by ~`fee_per_vbyte * 58` vbytes per input, either overpaying fees or failing `NotEnoughFunds`/`TooLargeTransaction` — griefing succeeds at cost bounded by the dust amount, exactly paralleling the Arcadia donor-griefing mechanics.
