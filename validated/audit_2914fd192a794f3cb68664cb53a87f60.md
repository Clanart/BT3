### Title
Alternate-spelling JSON key aliasing bypasses ProtoJSON duplicate-field / oneof-conflict rejection - ([File: python/google/protobuf/json_format.py])

### Summary
Caddy's bug is a **name-normalization mismatch**: an exact-string safety check (`http.Header.Del()` on `Remote-Groups`) is bypassed because a differently-spelled but semantically-equivalent client input (`Remote_Groups`) collides with the trusted value only *after* a later normalization step (`-`→`_` for FastCGI). Python's ProtoJSON parser (`google.protobuf.json_format`) has the same class of bug: its duplicate-key/oneof-conflict rejection is enforced on the *exact JSON key string*, but a field can legally be addressed by two different spellings (original `snake_case` name and `lowerCamelCase` `json_name`) that both resolve to the *same* `FieldDescriptor`. The rejection logic never normalizes before comparing, so an attacker-supplied JSON object with two differently-spelled keys for the same field slips past the "no duplicate/no conflicting field" guarantee and silently overwrites the first-parsed value.

### Finding Description
`_ConvertFieldValuePair` resolves each JSON key to a field by trying the `json_name` map first, then falling back to the original snake_case name via `fields_by_name`: [1](#0-0) 

The function tracks "already seen" fields using the **raw JSON key string**, not the resolved field identity, to detect duplicates and to enforce the oneof-exclusivity check: [2](#0-1) 

Because the `names` list stores `name` (the literal key text such as `"int32Value"`), a second key with a different literal spelling of the same field (e.g. `"int32_value"`) is not in `names`, so the duplicate check `if name in names` at line 663 never fires, `names.append(name)` just adds the second spelling, and processing proceeds to overwrite/clear the field a second time. The top-level JSON object parsing also runs `_DuplicateChecker` as an `object_pairs_hook`, but it too only rejects **exact** string key collisions: [3](#0-2) 

This is the direct analog of the Caddy flaw: the "delete/duplicate" defense operates on the untransformed attacker string, while the actual identity used downstream (the resolved `FieldDescriptor`, analogous to Caddy's `HTTP_*` CGI variable) is reached through a normalization (`json_name` ↔ original name mapping) that the defense does not account for. The bug is explicitly acknowledged in upstream tests as a known, unfixed oversight: [4](#0-3) 

The same alternate-name collision is intentionally allowed to persist as legacy/undefined behavior at the schema level (JSON name conflict handling), which is the root enabler: [5](#0-4) 

### Impact Explanation
Any application that calls the public `google.protobuf.json_format.Parse()`/`ParseDict()` API and relies on its documented "duplicate key" or "oneof conflict" rejection as an *integrity guarantee against ambiguous/conflicting untrusted JSON* can be bypassed by an attacker sending the same logical field twice under its two legal spellings (`fooBar` and `foo_bar`). The second occurrence silently wins ("last-value-wins"), clearing/overwriting whatever the first occurrence set — including clearing repeated/map fields and re-populating them, or satisfying a oneof exclusivity check with two different-looking keys that are actually the same field. This mirrors the Caddy CWE-287/290 pattern (trusted value overridden by client-controlled alias) but the confidentiality/integrity impact here is bounded by what the consuming application does with the parsed message; ProtoJSON parsing itself has no privileged/auth semantics. Where an application treats "the parser will reject conflicting/duplicate fields" as a security boundary (e.g., deduplication/anti-smuggling logic before trusting a parsed field), this bypass allows request/field smuggling analogous to the header-smuggling impact in the original report. Severity here is Medium rather than High because Protobuf itself has no authentication surface — the practical exploitation depends entirely on how the embedding application uses the guarantee.

### Likelihood Explanation
High likelihood of reachability: `json_format.Parse`/`ParseDict` is a fully public, documented parsing API taking attacker-controlled JSON text; no privileged access or hostile schema is needed, and the trusted `.proto` schema is unmodified. The bug requires only a normal message with a field whose default `json_name` differs from its declared name (the common case for any snake_case field), which is essentially all generated protobuf messages. The condition is explicitly reproduced by upstream's own regression tests, confirming determinism and confirming it is a genuine, currently-unfixed gap rather than a theoretical one.

### Recommendation
In `_ConvertFieldValuePair`, track "already seen" state by the **resolved `FieldDescriptor` object** (or `field.full_name`/`field.number`) rather than by the raw JSON key string, for both the duplicate-field check (line 663) and the oneof-conflict check (lines 673–682). Apply the same normalization in `_DuplicateChecker`/`object_pairs_hook` is not sufficient alone since it operates before field resolution; the field-identity-based check inside `_ConvertFieldValuePair` is the correct enforcement point. Equivalent per-language implementations (C++ `json/internal/parser.cc`, Java `JsonFormat`) should be audited to confirm whether their `SeenState`/`RecordAsSeen` tracking is keyed on resolved field identity (appears correct in C++, per `Traits::RecordAsSeen(*field, msg)`) versus the Python implementation's string-keyed tracking, which is the outlier.

### Proof of Concept
Using the upstream regression test already present in the codebase, which demonstrates the exact bypass with a non-map field: [6](#0-5) 

```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2

msg = json_format_proto3_pb2.TestMessage()
# Two different spellings of the SAME field, "int32_value" (json_name "int32Value")
json_format.Parse('{"int32Value": 1, "int32_value": 2}', msg)
assert msg.int32_value == 2  # No ParseError raised, despite semantically duplicate key.
```

Expected upstream behavior (per its own "duplicate key" defense in `_DuplicateChecker` at `python/google/protobuf/json_format.py:432-438` and the field-duplicate check at line 663) would be to raise `ParseError` as it does for the exact-spelling duplicate case (`testDuplicateField`), but instead the second alias silently overrides the first — an unauthenticated attacker sending untrusted JSON can smuggle a second, conflicting value for a field that application logic assumed was protected against duplication.

def _DuplicateChecker(js):
  result = {}
  for name, value in js:
    if name in result:
      raise ParseError('Failed to load JSON: duplicate key {0}.'.format(name))
    result[name] = value
  return result

void internal::DescriptorBuilder::CheckFieldJsonNameUniqueness(
    const absl::string_view message_name, const DescriptorProto& message,
    const Descriptor* descriptor, bool use_custom_names) {
  absl::flat_hash_map<std::string, JsonNameDetails> name_to_field;
  for (const FieldDescriptorProto& field : message.field()) {
    JsonNameDetails details = GetJsonNameDetails(&field, use_custom_names);
    if (details.is_custom && JsonNameLooksLikeExtension(details.orig_name)) {
      auto make_error = [&] {
        return absl::StrFormat(
            "The custom JSON name of field \"%s\" (\"%s\") is invalid: "
            "JSON names may not start with '[' and end with ']'.",
            field.name(), details.orig_name);
      };
      AddError(message_name, field, DescriptorPool::ErrorCollector::NAME,
               make_error);
      continue;
    }
    auto it_inserted = name_to_field.try_emplace(details.orig_name, details);
    if (it_inserted.second) {
      continue;
    }
    JsonNameDetails& match = it_inserted.first->second;
    if (use_custom_names && !details.is_custom && !match.is_custom) {
      // if this pass is considering custom JSON names, but neither of the
      // names involved in the conflict are custom, don't bother with a
      // message. That will have been reported from other pass (non-custom
      // JSON names).
      continue;
    }
    auto make_error = [&] {
      absl::string_view this_type = details.is_custom ? "custom" : "default";
      absl::string_view existing_type = match.is_custom ? "custom" : "default";
      // If the matched name differs (which it can only differ in case), include
      // it in the error message, for maximum clarity to user.
      std::string name_suffix = "";
      if (details.orig_name != match.orig_name) {
        name_suffix = absl::StrCat(" (\"", match.orig_name, "\")");
      }
      return absl::StrFormat(
          "The %s JSON name of field \"%s\" (\"%s\") conflicts "
          "with the %s JSON name of field \"%s\"%s.",
          this_type, field.name(), details.orig_name, existing_type,
          match.field->name(), name_suffix);
