## Analysis Summary

I traced the external report's core invariant break — *"a state-locking counter is incremented synchronously, but the fee paid for the message that is supposed to complete/unlock it is validated against only part of the real cost, so the completion message can be silently dropped forever, freezing user funds"* — to Hyperbridge's cross-chain **order cancellation** flow in the Intent Gateway.

### Title
Attacker-controlled relayer fee on destination-side order cancellation can permanently strand a victim's escrowed funds - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, function `_cancelFromDest`; analogous logic in `evm/src/apps/IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol`, `cancelOrder`)

### Summary
Destination-side cancellation of a cross-chain intent order is **permissionless after the order deadline** — anyone, not just the order owner, may call it and pay the ISMP dispatch cost. The call immediately flips the destination-side settlement flag to a terminal, non-reversible value (blocking all future fills *and* the alternative source-side cancellation route), then dispatches a `RefundEscrow` POST message back to the source chain to release the user's escrow. The relayer fee attached to that dispatch is fully attacker-controlled and is never validated against the fee a relayer actually needs to be paid to profitably deliver it. This mirrors the reported bug class exactly: a state lock is set synchronously and irreversibly, while the fee that is supposed to fund the message which clears that lock can be set arbitrarily low, so the unlocking message never gets delivered.

### Finding Description
Per the documented flow [1](#0-0) , destination-side cancellation:
1. Marks the order as settled locally (`_filled[commitment] = user`) to block future fills — this is the "state counter" analog to `state + 1` in the TON bug.
2. Dispatches a cross-chain `RefundEscrow` message to the source chain, which is the *only* mechanism that will ever release the escrowed input tokens back to the user. [2](#0-1)  confirms an unprivileged third party can trigger this after the deadline: *"Before and at the order deadline only the order creator can trigger this path. From the first destination block after the deadline, anyone may call... The caller pays the dispatch cost, but cannot change `WithdrawalRequest.beneficiary`: the refund always goes to `order.user`."*

The dispatch itself is built with an attacker-supplied `options.relayerFee` and `timeout: 0` (no expiry), as shown in the sibling `_cancelFromSource`/fill-order dispatch pattern in the same contract: [3](#0-2) [4](#0-3) 
and the function signature confirming an attacker/anyone-triggerable path exists for the destination-side cancel: [5](#0-4) 

The contract only validates that `msg.value`/token balance covers the *specified* `relayerFee` (a simple balance/allowance check), not that the fee is *sufficient for an honest relayer to profitably deliver it*. Hyperbridge's own relayer network enforces a profitability gate independently and off-chain: [6](#0-5) 
which explicitly skips ("Skipping unprofitable tx") any message whose attached fee is below the computed cost-plus-margin. Because the message never expires (`timeout: 0`, matching the documented "will not timeout" pattern used elsewhere for fee-withdrawal messages: [7](#0-6) ), an underfunded `RefundEscrow` simply sits in the relayer's retry queue forever rather than eventually timing out and being refunded.

The net effect: the attacker's transaction has already flipped `_filled[commitment]` to a non-zero/terminal value on the destination chain, so:
- No solver can ever fill the order (fill is checked against `_filled`).
- The source-side "cancel from source" path, which queries the destination's `_filled` storage slot and requires it to read *empty* to authorize a refund, will instead see a *non-empty* value and revert with `Filled()` (per [1](#0-0) ).
- The only remaining path to recovery is the underfunded `RefundEscrow` message itself, which no profit-seeking relayer will deliver.

### Impact Explanation
This directly matches the bounty's accepted impact classes: **loss/lock of bridged escrow funds** caused by **unauthorized/unprivileged execution** (any address can trigger the destructive state transition on behalf of a victim after deadline) combined with **insufficient fee validation** that lets the completing message be silently starved. The victim's escrowed input tokens (potentially significant value for an intent order) become unrecoverable through any first-class contract path once this is triggered — a state exactly analogous to the reported `state > 0` permanent lock.

### Likelihood Explanation
The attack requires only: (1) waiting for an order's deadline to pass (attacker-observable, no privileged role needed), (2) calling the permissionless `cancelOrder`/`_cancelFromDest` path with a deliberately low `relayerFee`, well under the actual gas+margin cost of delivering the POST to the source chain. No malicious relayer, prover, governance actor, or leaked key is required — the "attacker" is simply an ordinary caller exploiting the permissionless post-deadline cancellation trigger and the lack of a fee floor check.

### Recommendation
- **Short term**: Enforce a minimum relayer fee for the `RefundEscrow`/settlement dispatch in `_cancelFromDest` (and the equivalent `cancelOrder` cross-chain branch), derived from a conservative on-chain gas-cost estimate (mirroring the SDK's own `RELAYER_MESSAGE_GAS`/`CANCEL_MESSAGE_GAS` constants used off-chain in `sdk/packages/sdk/src/protocols/intents/OrderCanceller.ts`), rather than trusting an arbitrary caller-supplied value.
- Alternatively/additionally, restrict the "anyone can cancel after deadline" permission so that only the fee amount computed by the contract itself (not attacker input) is used, or require the caller to attach at least the contract-quoted `quoteCancelOrder` amount.
- **Long term**: Add a generic on-chain recovery/refund path for `_filled`-locked orders whose settlement message has been outstanding and unfunded beyond some threshold, independent of relayer cooperation — e.g., allow anyone to call the existing `fundRequest` top-up mechanism (`docs/content/developers/evm/messaging/post-requests.mdx`, lines 252-274) automatically or make cancellation fee under-payment impossible rather than merely recoverable by a good Samaritan.

### Proof of Concept
1. Alice places a cross-chain intent order with source-chain escrow of token X, destination chain B, deadline `D`.
2. At block `D+1`, attacker Bob (not Alice, not a solver) calls `cancelOrder`/`_cancelFromDest` on the destination `IntentGatewayV2`/`ExtrinsicIntents` for Alice's order, supplying `options.relayerFee = 1` (or any value far below the real delivery cost) and just enough `msg.value`/allowance to satisfy the naive balance check.
3. The call succeeds: `_filled[commitment]` is set to `order.user` (Alice), and a `RefundEscrow` POST with `fee = 1` and `timeout = 0` is dispatched to the source chain.
4. Hyperbridge's relayer profitability check (`tesseract/messaging/messaging/src/events.rs`) perpetually classifies this message as unprofitable and never submits it.
5. Alice's escrowed tokens on the source chain remain locked: solvers can't fill (`_filled` is set), and Alice can't use the source-side cancellation path either, since the destination `_filled` slot now reads non-empty and `onGetResponse` reverts with `Filled()`.

**Caveat/uncertainty**: If Hyperbridge's generic `fundRequest` top-up mechanism (documented in `docs/content/developers/evm/messaging/post-requests.mdx`, lines 252-274) can be called permissionlessly against this specific commitment by any observer to raise the fee post-hoc, the lock could in principle be repaired manually. I was not able to fully verify within the available context whether `fundRequest` is wired to accept top-ups for `IntentGatewayV2`/`ExtrinsicIntents`-originated commitments specifically, so the lock should be treated as "indefinite pending third-party intervention" rather than strictly cryptographically permanent — the underlying fee-validation gap and the unauthorized-trigger primitive remain valid regardless.

### Cancellation

There are two modes for cross-chain cancellation:

**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.

![Cancel from Source Chain](/intent-gateway-cancel-source.svg)

**Cancel from destination chain**: Before the deadline, only the order owner can call `cancelOrder()` on the destination chain. After the deadline, anyone can cancel. The function marks the order as cancelled locally (`_filled[commitment] = user`) to prevent future fills, then dispatches a cross-chain `RefundEscrow` message back to the source chain. When the source chain receives this message via `onAccept()`, it calls `withdraw()` to refund the escrowed tokens to the user and emits `EscrowRefunded(commitment)`.

### Cancel from the Destination Chain

Cancelling from the destination chain is simpler and does not require a storage proof. The destination gateway immediately marks the order as settled, blocking any future fill attempts, and sends a refund message to the source chain via Hyperbridge. When the message arrives, the source chain authenticates it as coming from the registered destination gateway and returns the escrowed tokens to the original user.

Before and **at** the order deadline only the order creator can trigger this path. From the first destination block after the deadline, anyone may call. This lets relayers act on behalf of users whose orders have expired without being filled, providing a recovery mechanism that does not require the user to be online. The caller pays the dispatch cost, but cannot change `WithdrawalRequest.beneficiary`: the refund always goes to `order.user`.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

### Initiating withdrawals

To initiate a withdrawal from hyperbridge, a relayer needs to submit a transaction to hyperbridge which triggers the withdrawal request. This extrinsic is unsigned and will not require any native tokens for execution fees. Once the extrinsic is executed, hyperbridge dispatches a POST request that when executed on its destination, will provide the relayer with the fees they've accrued.
