### Title
Zero-share delegation lets `MsgDelegate` accept a delegator's `usei`/dStable-equivalent tokens while minting no `Delegation.Shares` - (File: sei-cosmos/x/staking/keeper/delegation.go, sei-cosmos/x/staking/types/validator.go)

### Summary
The reported dTRINITY bug is a classic "zero-share deposit" pattern: a vault mints `shares = assets * totalSupply / totalAssets`, the division truncates to `0` for a small enough deposit relative to the exchange rate, and the code proceeds to accept the deposit without reverting on `shares == 0`, causing the depositor's funds to be absorbed with no claim on them. The same arithmetic/validation gap exists in Sei's native `x/staking` module's delegation flow, which is directly reachable by any unprivileged account submitting a `MsgDelegate` transaction (including via the `staking` precompile from EVM).

### Finding Description
`Validator.SharesFromTokens` computes shares using integer (truncating) division: [1](#0-0) 

`Keeper.Delegate` calls this path through `AddValidatorTokensAndShares` (which for a non-first delegation calls `SharesFromTokens`/`AddTokensFromDel`), then unconditionally adds the (possibly zero) result to `delegation.Shares`, transfers the delegator's coins into the module account, and stores the delegation — with no check that `newShares` is non-zero: [2](#0-1) [3](#0-2) 

The public entry point, `msgServer.Delegate`, only validates the coin denom before calling `k.Keeper.Delegate`, and never rejects a zero-share result: [4](#0-3) 

`MsgDelegate.ValidateBasic` only checks that the amount is a valid, positive coin — it has no minimum-delegation check, despite the module's own spec documenting that delegation is "expected to fail if... the amount delegated is less than the minimum allowed delegation": [5](#0-4) [6](#0-5) 

If a validator has accumulated a very high tokens-per-share exchange rate (e.g., after receiving large rewards, or after a slash that heavily reduced `Tokens` relative to `DelegatorShares` without invalidating the exchange rate entirely), a delegator who sends a small-but-nonzero `usei` amount can get `newShares == 0` from `SharesFromTokens`. `DelegateCoinsFromAccountToModule` still moves their tokens into the bonded/not-bonded pool, `validator.Tokens` increases by the full amount, but `delegation.Shares` remains unchanged (0 added), meaning the sender permanently loses claim to those tokens — the tokens are silently redistributed pro-rata to existing shareholders.

This path is reachable by any unprivileged account: directly via a `MsgDelegate` transaction, or indirectly through EVM users calling the `staking` precompile's `delegate`/`delegateFor`, which builds and executes the same `MsgDelegate`: [7](#0-6) 

### Impact Explanation
This is a concrete fund-loss bug: a delegator's tokens are debited from their account and merged into the validator's bonded pool, but they receive zero delegator shares and therefore zero claim on those tokens or resulting rewards/unbonding rights. The lost value is permanently redistributed to other delegators of that validator. Because delegation is a core, frequently used consensus mechanism reachable by any account (and by any EVM caller through the staking precompile), this qualifies as concrete fund loss / permanent freezing of user funds analogous to the original High-severity dTRINITY finding.

### Likelihood Explanation
Exploitability requires a validator whose `Tokens/DelegatorShares` ratio is large enough that a nonzero `bondAmt` truncates to `newShares == 0` (e.g., `bondAmt < DelegatorShares/Tokens` in raw units, i.e., `bondAmt * DelegatorShares < Tokens` given integer division). Such conditions can arise naturally over the life of a long-running, popular validator with a very large existing token/share base, or could be intentionally engineered by a validator/attacker who inflates `Tokens` relative to `DelegatorShares` (e.g., via a slash-then-recover cycle or by controlling deposits) and then induces or waits for a victim to send a small delegation amount. No special privilege is needed by the victim — only an ordinary `MsgDelegate` (or precompile-based EVM delegate call) with a small amount.

### Recommendation
In `Keeper.Delegate` (sei-cosmos/x/staking/keeper/delegation.go) and/or `Validator.AddTokensFromDel` (sei-cosmos/x/staking/types/validator.go), reject the delegation and return an error (e.g., a new `ErrInsufficientShares`/`ErrDelegationTooSmall`) whenever the computed `issuedShares`/`newShares` is zero for a nonzero `bondAmt`, before any coins are moved or state is mutated. Alternatively, enforce a minimum delegation amount scaled to the validator's current exchange rate so that `SharesFromTokens` cannot truncate to zero for any accepted transaction, matching the module's own documented (but unimplemented) invariant in `spec/03_messages.md`.

### Proof of Concept
1. Validator `V` is created and, through the normal `MsgDelegate`/reward/slash lifecycle, ends up with `Tokens = 10_000_000_000usei` and `DelegatorShares = 1usei`-worth of shares (i.e., an extremely high tokens-per-share ratio) — reachable purely through sequences of ordinary delegate/undelegate/slash operations, no privileged access needed.
2. An unrelated user submits `MsgDelegate{DelegatorAddress: victim, ValidatorAddress: V, Amount: 1000usei}` (or calls the `staking` precompile's `delegate(V)` with `value = 1000` wei-equivalent usei) directly against `msgServer.Delegate`.
3. Inside `Keeper.Delegate` → `AddValidatorTokensAndShares` → `Validator.SharesFromTokens(1000)` computes `DelegatorShares.MulInt(1000).QuoInt(Tokens)`, which truncates to `0` because `1000 * DelegatorShares < Tokens`.
4. `k.bankKeeper.DelegateCoinsFromAccountToModule` still transfers the victim's `1000usei` into the bonded pool; `delegation.Shares` is updated by adding `0`; `k.SetDelegation` stores a delegation with unchanged (possibly still-zero) shares.
5. The victim's `MsgDelegate` transaction succeeds (no error returned), their `1000usei` balance decreases, but they hold no additional shares in `V` and cannot recover the tokens via `MsgUndelegate` — the funds are permanently redistributed to `V`'s other delegators.

// SharesFromTokens returns the shares of a delegation given a bond amount. It
// returns an error if the validator has no tokens.
func (v Validator) SharesFromTokens(amt sdk.Int) (sdk.Dec, error) {
	if v.Tokens.IsZero() {
		return sdk.ZeroDec(), ErrInsufficientShares
	}

	return v.GetDelegatorShares().MulInt(amt).QuoInt(v.GetTokens()), nil
}

// AddTokensFromDel adds tokens to a validator
func (v Validator) AddTokensFromDel(amount sdk.Int) (Validator, sdk.Dec) {
	// calculate the shares to issue
	var issuedShares sdk.Dec
	if v.DelegatorShares.IsZero() {
		// the first delegation to a validator sets the exchange rate to one
		issuedShares = amount.ToDec()
	} else {
		shares, err := v.SharesFromTokens(amount)
		if err != nil {
			panic(err)
		}

		issuedShares = shares
	}

	v.Tokens = v.Tokens.Add(amount)
	v.DelegatorShares = v.DelegatorShares.Add(issuedShares)

	return v, issuedShares
}

// Delegate defines a method for performing a delegation of coins from a delegator to a validator
func (k msgServer) Delegate(goCtx context.Context, msg *types.MsgDelegate) (*types.MsgDelegateResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	valAddr, valErr := sdk.ValAddressFromBech32(msg.ValidatorAddress)
	if valErr != nil {
		return nil, valErr
	}

	validator, found := k.GetValidator(ctx, valAddr)
	if !found {
		return nil, types.ErrNoValidatorFound
	}

	delegatorAddress, err := sdk.AccAddressFromBech32(msg.DelegatorAddress)
	if err != nil {
		return nil, err
	}

	bondDenom := k.BondDenom(ctx)
	if msg.Amount.Denom != bondDenom {
		return nil, sdkerrors.Wrapf(
			sdkerrors.ErrInvalidRequest, "invalid coin denomination: got %s, expected %s", msg.Amount.Denom, bondDenom,
		)
	}

	// NOTE: source funds are always unbonded
	newShares, err := k.Keeper.Delegate(ctx, delegatorAddress, msg.Amount.Amount, types.Unbonded, validator, true)
	if err != nil {
		return nil, err
	}

	if msg.Amount.Amount.IsInt64() {
		defer func() {
			stakingMetrics.delegateTotal.Add(goCtx, 1)
			stakingMetrics.delegateAmount.Record(goCtx, msg.Amount.Amount.Int64())
		}()
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeDelegate,
			sdk.NewAttribute(types.AttributeKeyValidator, msg.ValidatorAddress),
			sdk.NewAttribute(sdk.AttributeKeyAmount, msg.Amount.String()),
			sdk.NewAttribute(types.AttributeKeyNewShares, newShares.String()),
		),
		sdk.NewEvent(
			sdk.EventTypeMessage,
			sdk.NewAttribute(sdk.AttributeKeyModule, types.AttributeValueCategory),
			sdk.NewAttribute(sdk.AttributeKeySender, msg.DelegatorAddress),
		),
	})

	return &types.MsgDelegateResponse{}, nil
}

// ValidateBasic implements the sdk.Msg interface.
func (msg MsgDelegate) ValidateBasic() error {
	if msg.DelegatorAddress == "" {
		return ErrEmptyDelegatorAddr
	}

	if msg.ValidatorAddress == "" {
		return ErrEmptyValidatorAddr
	}

	if !msg.Amount.IsValid() || !msg.Amount.Amount.IsPositive() {
		return sdkerrors.Wrap(
			sdkerrors.ErrInvalidRequest,
			"invalid delegation amount",
		)
	}

	return nil
}
