## Title
Missing `_requestCommitments` cleanup after paying the GET relayer fee allows a stale-height timeout proof to trigger a duplicate fee payout and a duplicate app callback — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` pays the relayer fee out of `_requestCommitments[commitment].fee` on a successful response delivery but never deletes that `_requestCommitments[commitment]` entry [1](#0-0) . Both sibling settlement paths — `dispatchTimeOut(GetRequestTimeout, ...)` and `dispatchTimeOut(PostRequestTimeout, ...)` — explicitly `delete _requestCommitments[commitment]` as their very first step, labeled "replay protection" [2](#0-1) [3](#0-2) . The GET-response success path is the only settlement branch that omits this cleanup, leaving the fee metadata live so the same commitment can later be settled a second time via a timeout proof.

### Finding Description
`_requestCommitments[commitment]` (a `FeeMetadata{sender, fee}`) is the single piece of state that both success and timeout paths use to decide "has this request already been paid out" and to know how much to pay. The pattern used everywhere else in the contract is: read/consume the metadata, then delete it before/around the payout so the same commitment cannot be settled twice. `dispatchIncoming(GetResponse, ...)` breaks this pattern [4](#0-3) :

```solidity
// reward the relayer fee
uint256 fee = _requestCommitments[commitment].fee;
if (fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
```

`_requestCommitments[commitment]` is left untouched. Meanwhile, `HandlerV2.handleGetRequestTimeouts` gates dispatch of a timeout solely on `meta.sender == address(0)` (i.e., whether that mapping entry exists) and a non-membership proof of the response receipt at an arbitrary caller-supplied historical `message.height` that only needs to satisfy the challenge period, not be the latest known height [5](#0-4) . Because `meta.sender` was never cleared after the successful response, this check still passes for an already-delivered request, and a non-membership proof against any historical height that predates the response's existence remains a valid proof forever (history doesn't change). `dispatchTimeOut(GetRequestTimeout, ...)` then re-invokes the app's `onGetTimeout` callback and refunds `meta.fee` to `meta.sender` a second time [2](#0-1) .

Net effect for one GET request: the relayer is paid on delivery, the app executes `onGetResponse`, and later the same commitment can also drive `onGetTimeout` on the app plus a second fee-token payout to `meta.sender` — a duplicate settlement causing direct fee-token loss and a corrupted double-completion of app state (success path *and* timeout path both executed for the same request).

### Impact Explanation
This directly matches the bounty's "duplicate settlement/claim" and "loss of funds" categories: the fee token pool pays out twice for a single GET request, and any `IApp` implementing `onGetTimeout` will process a request it already fulfilled via `onGetResponse`, which can corrupt application-level accounting (e.g., double refunds, double state transitions) in addition to the direct token loss on `EvmHost`.

### Likelihood Explanation
The path requires only a permissionless relayer/attacker action: submit `handleGetRequestTimeouts` with a valid non-membership proof at an older, already-finalized height for a request whose response was already delivered. No privileged role, malicious peer, or governance action is needed — any state height whose challenge period has elapsed and which predates the response's existence yields a valid proof. The only friction is timing (the timeout proof must reference a height old enough to predate the response while still satisfying `request.timeout() > state.timestamp`... note the check is `state.timestamp` at the *proof height*, not current time, so an attacker simply needs a historical height where the query looked unanswered and the request already looked timed out relative to that height's timestamp).

### Recommendation
Delete `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse, ...)` immediately after (or as part of) the fee payout, mirroring the cleanup already performed in both `dispatchTimeOut` overloads, so a commitment can only ever be settled once via either the success path or the timeout path.

### Proof of Concept
1. App dispatches a GET request on chain A; `EvmHost.dispatch` records `_requestCommitments[commitment] = FeeMetadata({sender: payer, fee: F})`.
2. A relayer delivers the GET response via `HandlerV2.handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse, relayer)`. The app's `onGetResponse` succeeds; relayer is paid `F` from the fee token. `_requestCommitments[commitment]` is **not** deleted [4](#0-3) .
3. Later, an attacker (or the same relayer) submits `HandlerV2.handleGetRequestTimeouts` for the same `commitment`, using a state height for the destination chain from *before* the response existed there, satisfying both the timeout timestamp check and the non-membership proof of the response receipt at that height [6](#0-5) .
4. `meta = host.requestCommitments(commitment)` still returns the original non-zero `FeeMetadata`, so `UnknownMessage` is not triggered; `dispatchTimeOut` executes, calling `onGetTimeout` on the app (already delivered `onGetResponse`) and transferring `meta.fee = F` again to `meta.sender` [2](#0-1) .
5. Result: `F` was paid out twice from the fee-token balance for a single request, and the app processed conflicting success/timeout callbacks for the same commitment.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
