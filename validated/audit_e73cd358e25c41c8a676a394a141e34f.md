### Title
Unicode Bidirectional Override Characters in File Paths Are Not Sanitized in `PathText`, Enabling Filename Spoofing in the Changes List - (File: `app/src/ui/lib/path-text.tsx`)

### Summary
`PathText.render()` and its state builder `createPathDisplayState` output raw path substrings without stripping Unicode bidi control characters (e.g. U+202E). A repository containing a file whose name embeds such characters will have its status-derived path rendered with reordered characters in the Changes list / commit dialogs (via `PathLabel`), while the underlying path used for git operations remains the real, un-reordered string.

### Finding Description
`createPathDisplayState` only normalizes the path with `Path.normalize()` and slices it by index for directory/filename separation and truncation [6](#0-5) . No pass removes or escapes Unicode format/control characters. `render()` inserts `directoryText`/`fileText` (and the tooltip's `normalizedPath`) directly as React text children [7](#0-6) , which the browser bidi algorithm will visually reorder if a RLO/LRO/PDF character is present. `PathLabel`, used throughout the Changes list, commit/discard dialogs, and conflict UIs, feeds `status.path`/`status.oldPath` (derived from git status of a cloned repo's working tree) into `PathText` unmodified [4](#0-3) .

### Impact Explanation
An attacker who controls repository content (a cloned/fetched repo) can create a file whose real name is, for example, `evil<RLO>gnp.exe` such that it displays as `evilexe.png` in the Changes list, commit summary, or discard-changes dialogs. If the user reviews the list visually and stages/commits believing they are committing a benign file, the actual file staged and committed is the truly-named file — corrupting the user's perception of what they are committing. This falls under "silent corruption of what the user commits/pushes," a valid impact category, since no code execution occurs in Desktop itself but the user's mental model of file identity is deceived.

### Likelihood Explanation
Likelihood is high for the input reaching the render path (any file added to a cloned repo's working directory with a bidi-override character in the name will show up in `git status` and populate the Changes list) since no filtering exists in git-status parsing (`app/src/lib/status-parser.ts` etc., not modified in this file) nor in `PathText`. Actually exploiting the user into misidentifying the file requires that the crafted display convincingly disguises the file (e.g. flipping extension order), which is achievable with standard RTLO tricks and requires no unusual interaction beyond normal repository browsing/staging.

### Recommendation
Sanitize/escape Unicode bidirectional control characters (U+202A–U+202E, U+2066–U+2069, and other Cf category format characters) out of paths before display in `createPathDisplayState`/`extract`, or wrap rendered path segments with CSS `unicode-bidi: plaintext` / explicit `dir="ltr"` isolation combined with visibly rendering control characters as their Unicode replacement glyphs (e.g., via a dedicated escape function similar to how GitHub.com highlights suspicious characters in diffs/filenames).

### Proof of Concept
1. In a repository, create a file with a name containing U+202E, e.g. `touch $'exe.\u202Egnp'` (renders as `exe.png` when the extension bytes are reordered).
2. Clone/open this repository in GitHub Desktop; the file will appear as untracked in the Changes list, rendered via `PathLabel` → `PathText`.
3. Observe that the displayed filename in the Changes list/tooltip visually differs from `git status --porcelain` output for the same entry (diff the DOM text content of the `.path-text-component` span against `state.normalizedPath`), demonstrating the display can no longer be trusted to represent the real path being staged.

export function extract(normalizedPath: string): {
  normalizedFileName: string
  normalizedDirectory: string
} {
  // for untracked submodules the status entry is returned as a path with a
  // trailing path separator which causes the directory to be trimmed in a weird
  // way below. let's try to resolve this here
  normalizedPath = normalizedPath.endsWith(Path.sep)
    ? normalizedPath.substring(0, normalizedPath.length - 1)
    : normalizedPath

  const normalizedFileName = Path.basename(normalizedPath)
  const normalizedDirectory = normalizedPath.substring(
    0,
    normalizedPath.length - normalizedFileName.length
  )

  return { normalizedFileName, normalizedDirectory }
}

function createPathDisplayState(
  normalizedPath: string,
  length?: number
): IPathDisplayState {
  length = length === undefined ? normalizedPath.length : length

  if (length <= 0) {
    return { normalizedPath, directoryText: '', fileText: '', length }
  }

  const { normalizedFileName, normalizedDirectory } = extract(normalizedPath)

  // Happy path when it already fits, we already know the length of the directory
  if (length >= normalizedPath.length) {
    return {
      normalizedPath,
      directoryText: normalizedDirectory,
      fileText: normalizedFileName,
      length,
    }
  }

  const truncatedPath = truncatePath(normalizedPath, length)
  let directoryLength = 0

  // Attempt to determine how much of the truncated path is the directory prefix
  // vs the filename (basename). It does so by comparing each character in the
  // normalized directory prefix to the truncated path, as long as it's a match
  // we know that it's a directory name.
  for (
    let i = 0;
    i < truncatedPath.length && i < normalizedDirectory.length;
    i++
  ) {
    const normalizedChar = normalizedDirectory[i]
    const truncatedChar = truncatedPath[i]

    if (normalizedChar === truncatedChar) {
      directoryLength++
    } else {
      // We're no longer matching the directory prefix but if the following
      // characters is '…' or '…/' we'll count those towards the directory
      // as well, this is purely an aesthetic choice.
      if (truncatedChar === '…') {
        directoryLength++
        const nextTruncatedIx = i + 1

        // Do we have one more character to read? Is is a path separator?
        if (truncatedPath.length > nextTruncatedIx) {
          if (truncatedPath[nextTruncatedIx] === Path.sep) {
            directoryLength++
          }
        }
      }
      break
    }
  }

  const fileText = truncatedPath.substring(directoryLength)
  const directoryText = truncatedPath.substring(0, directoryLength)

  return { normalizedPath, directoryText, fileText, length }
}
