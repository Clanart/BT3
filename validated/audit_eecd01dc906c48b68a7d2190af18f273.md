### Title
Fee/change accounting omits the OP_RETURN data output from the transaction weight, so the required fee is computed against a smaller vsize than the transaction that is actually signed - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Footium distributor computing `value = _amount - totalClaimed` against stale/incomplete accounting state, `SignableTransaction::new` computes the transaction weight — and therefore the required fee and the change amount — from `payments` only, even though an extra `OP_RETURN` output has already been pushed into `tx_outs`. The signed transaction is larger than the size the fee was priced for, so every transaction carrying a `data` payload pays less fee-per-vbyte than requested and can fall below relay minimums, leaving funds locked in an unconfirmable/unbroadcastable transaction.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before any weight calculation:

```rust
// networks/bitcoin/src/wallet/send.rs:193-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

But the weight/vbytes used for the fee calculation are computed with `payments` (which does not contain the data output), not with `tx_outs`:

```rust
// networks/bitcoin/src/wallet/send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds a mock transaction whose outputs are exactly the `payments` slice it is given (send.rs:85-94), so the ~`4 + len(data)`-byte OP_RETURN output (up to ~90 bytes for 80 bytes of data) is missing from the weight. The same omission occurs in the change path:

```rust
// networks/bitcoin/src/wallet/send.rs:225-227
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change;
```

Consequences of the delta between accounted and actual transaction:

1. `needed_fee = fee_per_vbyte * vbytes` and `fee_with_change = fee_per_vbyte * vbytes_with_change` are both underestimates — the real vsize is larger, so the effective fee rate is below the caller's `fee_per_vbyte`.
2. The minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (send.rs:211) uses the underestimated `vbytes`, so a transaction can pass this check while its actual fee rate is below the relay minimum.
3. The change value `input_sat - payment_sat - fee_with_change` (send.rs:228) is *over*credited: the change output receives sats that should have gone to the fee, compounding the effective-fee shortfall — a direct structural analog of the report's `value = _amount - totalClaimed` releasing the wrong residual because one side of the subtraction was stale.

### Impact Explanation
Any `SignableTransaction` built with `data: Some(...)` produces a transaction whose real fee rate is lower than the rate the creator specified and lower than what `needed_fee()`/`fee()` accounting assumed. At fee rates near the mempool minimum, the signed transaction will be rejected by relays or sit unconfirmed; the inputs committed to it (`prevouts` are committed in the sighash via `Prevouts::All`) cannot be spent elsewhere until a replacement is constructed — funds are effectively locked, mirroring the "lock fund / sub-optimal amount" impact of the original report. The change output is additionally overvalued relative to correct accounting.

### Likelihood Explanation
The bug triggers deterministically for every caller that passes `Some(data)`. In Serai's processor flow, OP_RETURN payloads are used to carry instruction/refund metadata in network transactions, some of which embed data derived from externally-supplied `InInstruction`s — i.e., attacker-influenced transaction data feeds directly into the miscounted path. No validator collusion, key compromise, or misuse is required; the arithmetic error is purely internal to `SignableTransaction::new`. Likelihood is moderate (requires data-carrying transactions and low fee margins to manifest as a lock), which keeps this at Medium.

### Recommendation
Compute weight from the actual outputs that will be in the transaction. Either pass the fully-built `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or add a `data_len`/`extra_outputs` parameter accounting for the OP_RETURN output's serialized size in both the no-change and with-change calculations. The change value at send.rs:228 will then automatically use the correct `fee_with_change`. As defense-in-depth, add a post-construction assertion that `tx.weight()` matches the accounted `weight`, and consider checking the effective fee rate against `DEFAULT_MIN_RELAY_TX_FEE` using the final transaction's real vsize.

### Proof of Concept
```rust
// Conceptual, against networks/bitcoin/src/wallet/send.rs
let inputs = vec![received_output]; // value V
let payments = &[(script, payment_amt)];
let data = Some(vec![0u8; 80]); // maximal OP_RETURN payload

let tx = SignableTransaction::new(inputs, payments, Some(change_script), data, fee_rate).unwrap();

// The constructed transaction contains payment + OP_RETURN + change outputs,
// but needed_fee was priced for payment (+change) only.
let real_vsize = tx.transaction().vsize() as u64;
let accounted_vsize = tx.needed_fee() / fee_rate; // vbytes used internally
assert!(real_vsize > accounted_vsize); // OP_RETURN output unaccounted

// Effective fee rate is below what the caller requested:
let real_fee = tx.fee();
assert!(real_fee < fee_rate * real_vsize);
// When fee_rate * accounted_vsize just passed the DEFAULT_MIN_RELAY_TX_FEE
// check at send.rs:211, the real rate can be below the relay minimum,
// producing a signed transaction the network will not accept.
```
