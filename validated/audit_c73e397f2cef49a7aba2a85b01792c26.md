# Title
Payout transaction attribution is malleable via SIGHASH_SINGLE|ANYONECANPAY, letting anyone rewrite the OP_RETURN operator attribution and permanently deny reimbursement — (`core/src/verifier.rs`, `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The user's withdrawal signature is required to use `TapSighashType::SinglePlusAnyoneCanPay`, which only commits to input 0's outpoint and output 0 (the user payout output) — it does not commit to the OP_RETURN output that names the funding operator, nor to any other inputs. Anyone who observes this public signature (submitted as part of the `withdraw()` call on the Citrea Bridge contract) can rebuild a competing, valid, standard, RBF-capable payout transaction that reuses the same signed input/output[0] but substitutes an arbitrary OP_RETURN and fee-paying inputs, then outbid the honest operator's broadcast so only the attacker's version is mined and picked up by `Verifier::update_finalized_payouts`.

### Finding Description
The broken binding: `payout_txid_processed_by_update_finalized_payouts == payout_txid_whose_output_2_names_the_true_funding_operator`.

`create_payout_txhandler` builds the payout tx as `[output0: user payout][output1: anchor][output2: OP_RETURN(operator_xonly_pk)]` and signs input 0 with the user-provided `taproot::Signature`: [1](#0-0) 

Both `parse_withdrawal_sig_params` and `Operator::withdraw` strictly enforce that this user signature use `TapSighashType::SinglePlusAnyoneCanPay`: [2](#0-1) [3](#0-2) 

Per BIP-341, `SINGLE|ANYONECANPAY` only commits to: the signer's own input's outpoint/amount/scriptPubKey, and the single output at the same index (output 0). It does **not** commit to any other input, to output 1 (anchor), to output 2 (OP_RETURN operator attribution), or even to the total output/input count. This signature and the `input_outpoint`/UTXO it applies to are submitted publicly by the withdrawing user via the Citrea Bridge contract's `withdraw()` call (attacker-controlled per the threat model), so anyone can read `in_signature` and `in_outpoint` off-chain before any operator broadcasts a payout tx.

An attacker can therefore independently construct their own transaction: keep input 0 (same outpoint, same valid signature) and output 0 (identical, as required by SIGHASH_SINGLE), but attach arbitrary fee-paying inputs of their own and an arbitrary OP_RETURN payload (garbage bytes, or another operator's public xonly key) at output 2, sign their own added inputs, and broadcast it with a higher feerate/RBF signal than the honest operator's version. Since both transactions spend the same input 0, only one can be mined.

`Verifier::update_finalized_payouts` blindly trusts whichever txid the block_cache confirms was mined and derives the credited operator solely from that transaction's OP_RETURN: [4](#0-3) 

There is no check that the confirmed payout tx is the one the actual funding operator constructed, nor any commitment binding the OP_RETURN to the signed input. The database update is keyed only by the withdrawal index and whichever txid the `bitcoin_syncer_spent_utxos` records for that outpoint: [5](#0-4) [6](#0-5) 

Downstream, `is_kickoff_malicious` compares the DB-recorded `operator_xonly_pk` (derived from whichever tx confirmed) against the actual kickoff sender; a mismatch or `None` value (e.g., garbage OP_RETURN bytes) causes the kickoff to be treated as malicious, permanently blocking the true funding operator's reimbursement path: [7](#0-6) 

No existing guard (`is_deposit_valid`, `SECP.verify_schnorr`, `is_kickoff_malicious`, or a DB uniqueness constraint) prevents this divergence — `verify_schnorr` only validates the user's signature against input 0/output 0, which the attacker's malleated transaction still satisfies unchanged.

### Impact Explanation
The true funding operator can never satisfy `is_kickoff_malicious`'s equality check (their `kickoff_data.operator_xonly_pk` will not match the DB-recorded attribution, which is now `None` or an arbitrary/wrong value), so their `PayoutCheckerTask`/`handle_finalized_payout`/`mark_payout_handled` path is permanently unreachable for that withdrawal — matching the Critical category "an honest operator permanently unable to be reimbursed" — while the operator has already spent real BTC funding the user's payout. If the attacker instead sets the OP_RETURN to a different, non-paying operator's known xonly pubkey, that operator could be credited and eventually reimbursed for a payout it never funded — also Critical. This is repeatable per-withdrawal across any deposit/operator, since it only depends on the publicly-readable `withdraw()` calldata and does not require any privileged capability.

### Likelihood Explanation
The only precondition is that the attacker observes a public Citrea `withdraw()` call (containing `in_signature`, `in_outpoint`, `output_script_pubkey`, `output_amount`) before the corresponding payout transaction confirms — trivially true since this data is on-chain calldata. The attacker needs only enough BTC to fund a competing fee input and outbid the operator's feerate within `TxSenderLimits` bounds, a modest and fully attacker-controlled cost. No key compromise, majority hashrate, or privileged role is required — fully consistent with the unprivileged threat model.

### Recommendation
Bind the OP_RETURN attribution (and ideally the full set of outputs/other inputs) to the same commitment the user signs, e.g. require the user to sign with `SIGHASH_ALL` (or a covenant/OP_RETURN template fixed at withdrawal-request time and validated on confirmation against the value committed on the Citrea side), or have `update_finalized_payouts`/`is_kickoff_malicious` verify the confirmed payout tx's structure (inputs, non-attribution outputs) matches a pre-registered candidate rather than trusting whatever OP_RETURN happens to be present in the mined transaction.

### Proof of Concept
```
cargo test --package clementine-core update_finalized_payouts_op_return_malleability -- --nocapture
```
Plan:
1. Set up regtest bridge with one deposit and one withdrawal (as in `deposit_and_withdraw_e2e.rs`), obtain `in_signature` (`SinglePlusAnyoneCanPay`), `in_outpoint`, `output_script_pubkey`, `output_amount` as would be submitted to Citrea's `withdraw()`.
2. Build the honest operator's payout tx via `Operator::withdraw` (records operator A's xonly pk in output 2 OP_RETURN); do not mine it yet.
3. Independently reconstruct a second payout tx using `create_payout_txhandler` with the same `input_utxo`/`user_sig`/`output_txout`, but attach the attacker's own funding input and a different/garbage OP_RETURN payload, and set a higher feerate; assert `SECP.verify_schnorr` for input 0 still succeeds against the same `user_sig`.
4. Broadcast both; mine one block; assert only the attacker's txid appears in `block_cache.txids`.
5. Call `update_finalized_payouts`; assert `db.get_payout_info_from_move_txid` returns `operator_xonly_pk != operator A`'s key (or `None`).
6. Have operator A send its real kickoff; assert `Verifier::is_kickoff_malicious` returns `true`, proving operator A can never pass `mark_payout_handled`/`PayoutCheckerTask` for this withdrawal — confirming both sides of the binding diverge.

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
