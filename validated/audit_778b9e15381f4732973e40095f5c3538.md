## Title
Tron `IntentGatewayV2.placeOrder` credits escrow with requested amount instead of actual received balance, enabling shared-pool insolvency/drain via non-standard ERC20 inputs - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrowed amount for each input token from the user-supplied `order.inputs[i].amount` (reduced only by the protocol fee) rather than the amount the gateway actually received via `safeTransferFrom`. This is the same broken invariant flagged in the external report for `_safeRewardTransfer`: an outbound/inbound transfer amount is trusted without verifying it against a measured before/after balance delta.

### Finding Description
In the main EVM `IntentGatewayV2.sol`, the non-predispatch branch explicitly measures actual received tokens: [1](#0-0) 
```
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```
This actual-received amount is what feeds into the protocol-fee reduction and the commitment/escrow accounting later in the function, and is covered by dedicated fee-on-transfer regression tests. [2](#0-1) 

The Tron contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) instead computes `reducedInputs` from the *requested* `order.inputs[i].amount` before any transfer occurs: [3](#0-2) 

Then, in the non-predispatch transfer path, it calls `safeTransferFrom` for the full requested amount but never checks the balance actually received, and unconditionally credits the escrow ledger with `reducedInputs[i].amount` (derived from the requested amount, not what arrived): [4](#0-3) 

The predispatch branch has a similar issue: it computes `dust = balance - requiredAmount` and credits `reducedInputs[i].amount` to escrow, but `reducedInputs` was already fixed at commitment-build time from the pre-transfer requested amount, so if the dispatcher's actual balance for that token comes in short (fee-on-transfer, rebasing, or any deflationary ERC20), `balance < requiredAmount` reverts, but if it comes in with a token that transfers a different underlying amount without hitting that specific check path (e.g., due to rounding, or a token whose `balanceOf` return doesn't strictly track `transferFrom` semantics), the escrowed value can still diverge from custody.

Because `_orders[commitment][token]` is a per-commitment ledger backed by one shared token balance in the contract, over-crediting escrow for one order's commitment does not just under-fund that specific order — it consumes real token balance that belongs to other orders' commitments for the same token, since all escrowed balances for a given ERC20 share the same physical `balanceOf(address(this))` pool. When a legitimate later order attempts `fillOrder`/`withdraw` for its own (correctly funded) commitment, the shared token balance may already be depleted by the earlier over-credited commitment, causing loss of funds/insolvency for the correct beneficiary, or letting the attacker who placed the deflationary-token order withdraw more than they deposited by draining the shared pool.

### Impact Explanation
This directly maps to the required impact classes: **stealing or loss of funds** and **transaction manipulation** via escrow amount mismatch, and **false state acceptance** at the commitment level (the on-chain commitment/escrow claims a balance that the contract does not actually hold). It is reachable by any unprivileged user calling `placeOrder` with a non-standard ERC20 token (fee-on-transfer, rebasing, or one with rounding-affecting transfer semantics) — no relayer, prover, or admin compromise is required.

### Likelihood Explanation
Likelihood is **moderate**: it requires the attacker to place an order using a token that does not transfer 1:1 (fee-on-transfer/deflationary/rebasing ERC20), which is common in the wild and not prevented by any token whitelist in this contract (mirroring the exact justification given in the external report: "the system does not currently implement any token white-listing"). The main EVM contract already treats this as a real, tested threat model (see the `FeeOnTransferToken` test suite) but the Tron variant does not carry the same fix.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` (or the dispatcher, for the predispatch path) immediately before and after each `safeTransferFrom`/sweep, mutate `order.inputs[i].amount` to the actual delta, and only then compute `reducedInputs`/`commitment`/escrow credits from that measured amount in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 `FOT` with e.g. 5% transfer fee (analogous to the `FeeOnTransferToken` test contract already in the repo: [5](#0-4) ).
2. Attacker calls `IntentGatewayV2(tron).placeOrder(order, graffiti)` on the Tron variant with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no protocol fee configured.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` is executed, but the gateway contract only receives `950e18` due to the 5% fee.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits `1000e18` (the full requested amount) to escrow — 50e18 more than the contract's actual `FOT` balance increase.
5. A second, legitimate user places a separate order also denominated in `FOT` for `500e18`, correctly transferring `500e18 * 0.95 = 475e18` net into the shared pool.
6. Contract's total `FOT` balance is now `950e18 + 475e18 = 1425e18`, but total escrow ledger claims `1000e18 + 500e18 = 1500e18` (using un-reduced values for simplicity) — a `75e18` shortfall shared across both commitments.
7. When the first (attacker's) order is filled/withdrawn, it can pull the full `1000e18` credited amount from the shared pool (subject to the fee-on-transfer haircut on the way out), depleting balance needed to satisfy the second legitimate order's `500e18` escrow claim, causing the second order's `withdraw`/`fillOrder` call to revert or receive less than owed — a direct loss/lock of the second user's funds caused entirely by the first user's unprivileged `placeOrder` call.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
