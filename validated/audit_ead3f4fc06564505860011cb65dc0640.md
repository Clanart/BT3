### Title
`SignableTransaction` signs fabricated `ReceivedOutput` prevout data without verifying it against the chain - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the reported bug (redeeming against stale oracle prices without freshness validation), `SignableTransaction::new` and `TransactionSignMachine::sign` consume `ReceivedOutput` values — which can be deserialized from untrusted bytes via `ReceivedOutput::read` — and commit to their claimed `TxOut` data through `Prevouts::All` in the BIP-341 sighash, without ever checking that the outpoint exists, is unspent, or that the declared `value`/`script_pubkey` matches the actual UTXO on the chain. The only consistency check performed is that the claimed `script_pubkey` equals `p2tr_script_buf(group_key + offset)`; the outpoint and amount are trusted blindly.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) decodes an attacker-controlled `offset`, `TxOut`, and `OutPoint` with no binding between them and no validation against chain state. `SignableTransaction::new` (`send.rs:150-256`) then:

- treats `input.output.value` as real available funds for fee/change math (`send.rs:175`, `send.rs:215`, `send.rs:228`),
- stores `input.output` verbatim into `prevouts` (`send.rs:253`),
- and only validates `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` in `multisig` (`send.rs:273-285`). The `outpoint` is never checked against the `TxOut`, and the `TxOut` is never checked against the blockchain.

`TransactionSignMachine::sign` (`send.rs:373-390`) then signs `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), ...)`, committing the threshold signature to the fabricated prevout amounts. This is the Serai analog of `_calculateTroveRedemption` trusting stale price data: externally supplied value data is consumed in a signing computation with no freshness/consistency check against the authoritative source (the chain).

### Impact Explanation
Because BIP-341 key-path sighashes commit to the *actual* prevout amounts, any `ReceivedOutput` whose `value` does not equal the real UTXO's value produces a signature that is invalid on-chain while appearing to complete successfully inside the FROST protocol (`complete` only checks the Schnorr equation, `frost/src/sign.rs:465`). An unprivileged party supplying crafted bytes to `ReceivedOutput::read` can therefore cause the validator set to produce a formally "completed" threshold signature over an unspendable transaction — funds are reported as spendable inputs (and change is computed) on phantom value. If the declared amount is deflated, the constructed transaction silently routes the discrepancy into fees/change accounting before failing at broadcast. Each such instance burns a signing plan ID/attempt and causes the honest signing set to endorse a transaction that can never confirm.

### Likelihood Explanation
Any consumer that builds `SignableTransaction`s from serialized `ReceivedOutput`s not freshly produced by `Scanner::scan_transaction`/`scan_block` over a finalized block is exposed: outputs can be replayed after being spent (no spentness check exists anywhere in `send.rs`), corrupted in transit/storage, or supplied by an untrusted peer. The attack requires only control of the bytes fed to `ReceivedOutput::read` — an explicitly in-scope input channel — and no threshold corruption, since `multisig` passes as long as the `script_pubkey` is copied verbatim from a real Serai output.

### Recommendation
Before signing, re-validate each input against chain state: confirm `outpoint` references an existing, unspent UTXO whose `TxOut` (value and `script_pubkey`) exactly equals `input.output`. Equivalently, fetch prevouts via RPC inside `multisig`/`TransactionSignMachine::sign` rather than trusting the serialized `ReceivedOutput`, or hash a commitment to the verified chain state into the signing transcript so participants provably agree on the inputs being spent.

### Proof of Concept
1. Take a real Serai P2TR output: `TxOut { value: 50_000, script_pubkey: p2tr_script_buf(key) }` at outpoint `P`.
2. Construct forged bytes: `offset = Scalar::ZERO`, `output = TxOut { value: 5_000_000, script_pubkey: <same script> }`, `outpoint = P`, and feed them through `ReceivedOutput::read` — it succeeds, since no field is cross-checked (`mod.rs:122-134`).
3. `SignableTransaction::new(vec![forged], payments, change, None, fee)` succeeds; `multisig(keys)` returns `Some` because the `script_pubkey` check passes (`send.rs:277`).
4. `machine.sign(...)` produces shares committing `Prevouts::All` to the claimed `5_000_000` sats; `complete` returns `Ok(tx)` because the Schnorr aggregate verifies against the committed (wrong) message.
5. Broadcasting `tx` fails at every Bitcoin node: the committed prevout amount does not match the real UTXO, so the BIP-341 signature is invalid — a completed threshold signature over an unspendable transaction, constructed entirely from untrusted `ReceivedOutput` bytes.
