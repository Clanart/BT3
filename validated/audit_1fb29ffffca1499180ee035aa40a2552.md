### Title
Self-referral via two colluding EOAs lets an attacker collect both referrer and referee reward shares in `trigger` - ([File: rewards/ReferralStorage.sol])

### Summary
`useCode` only blocks a single address from referring itself (`codeOwners[_code] == msg.sender` check), but it does not prevent two addresses controlled by the same attacker from forming a referrer/referee pair. By registering a code from EOA A and calling `useCode` from EOA B, the same attacker becomes both `_referer` and `_referee` in `myReferer`/`myReferees`, so every subsequent `trigger` call pays both the `refererAmount` and `refereeAmount` bonus to accounts the attacker fully controls.

### Finding Description
`useCode` (rewards/ReferralStorage.sol:134-145) enforces:
```solidity
if (codeOwners[_code] == msg.sender) revert Circled();
if (myReferer[msg.sender] != address(0)) revert HasReferral();
```
This only guards against `msg.sender` referring itself with its own code; it has no mechanism (and cannot have one on-chain) to detect that `codeOwners[_code]` (address A) and `msg.sender` (address B) are economically the same entity. Once B calls `useCode(codeA)`, `myReferer[B] = A` is set permanently (no way to unset), and `myReferees[A]` includes B.

When `masterMagpie` later calls `trigger(_referee, _amount)` (rewards/ReferralStorage.sol:173-195) upon B claiming/harvesting its own MGP reward, the function computes:
```solidity
uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;
refererInfo.rewardAmount += refererAmount;
refereeInfo.rewardAmount += refereeAmount;
```
Both `refererAmount` (credited to A) and `refereeAmount` (credited to B) are additive bonuses on top of B's own base claim, funded from the protocol's referral reward pool (MGP held by `ReferralStorage`, claimable via `claimReward`). Since A and B are both attacker-controlled, the attacker captures the entire `(basic + boosted) * _amount / DENOMINATOR` referral bonus pool for themselves, which is a bonus that is only supposed to exist to reward two *distinct, independent* participants (the referrer bringing new capital and the referee being incentivized to stake). No other check (owner-set tiers, `boosted` factor, `nonReentrant`, etc.) restricts referral relationships to distinct real users — the whole design assumes A and B are unrelated parties, an assumption that cannot be verified on-chain and is trivially defeated by using two wallets.

### Impact Explanation
This causes theft/dilution of the referral reward pool (unclaimed MGP yield held by `ReferralStorage` for `claimReward`): the attacker collects both the referrer share and referee share of every claim `_amount` they route through their own two accounts, whereas a legitimate single staker with equivalent capital (no referral code used) would receive zero referral bonus. This directly reduces the MGP available for genuine referrers/referees and effectively transfers referral-program value to the attacker's own accounts, matching the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Highly likely and cheap to execute. It requires only two ordinary EOAs, one `registerCode` call, one `useCode` call, and then normal staking/harvesting activity through `masterMagpie`. No special privileges, capital, or timing are needed, and it is fully repeatable for every harvest cycle for as long as the attacker keeps staking through account B.

### Recommendation
Referral programs generally cannot cryptographically prove two addresses are unrelated, so full elimination via code review requires either: (1) restricting `useCode`/`registerCode` so that codes can only be linked to KYC'd or otherwise vetted addresses (off-chain control), or (2) capping/removing the referrer-side or referee-side bonus computation to make self-referral economically neutral, e.g. requiring a minimum staking-history / distinctness heuristic, or funding the referral bonus by *diverting* a portion of the referee's own claim (`refererAmount + refereeAmount <= _amount`, i.e., a true split of the referee's yield) rather than adding a bonus on top. If bonuses are meant to come from a separate incentive budget, consider adding governance-controlled per-address/pair anti-Sybil limits (e.g., maximum total referral bonus payable per unique referrer, KYC allowlist, or minimum unlock/lock duration before a referral pair becomes reward-eligible).

### Proof of Concept
Foundry test outline:
1. Deploy `ReferralStorage`, `VLMGP`, `MasterMagpie`, and MGP token in a test harness; set a nonzero `sharePercent` and a tier with `rewardPercentage > 0`.
2. From address A: call `registerCode(codeA)`.
3. From address B (attacker-controlled, no relation to A besides being the same operator's key): call `useCode(codeA)`.
4. Have B stake and accrue a harvestable reward `_amount` through the normal `masterMagpie` flow, then trigger the harvest so `masterMagpie` calls `referralStorage.trigger(B, _amount)`.
5. Assert `userInfos[A].rewardAmount == _amount * refererPercentage / DENOMINATOR` and `userInfos[B].rewardAmount == baseReward + _amount * refereePercentage / DENOMINATOR`.
6. Compare against a control scenario where a non-colluding staker C (same capital as B, no referral code used) harvests the same `_amount`: assert `userInfos[C].rewardAmount == baseReward` only (no referral bonus).
7. Assert `(A.rewardAmount + B.rewardAmount) - C.rewardAmount == _amount * (refererPercentage + refereePercentage) / DENOMINATOR > 0`, demonstrating the attacker-controlled pair captured referral bonus a single non-colluding staker cannot get, drawn from the shared MGP reward pool.
