### Title
Cross-Transaction Output Metadata Overwrite in Bitcoin `get_outputs` Applies a Later Transaction's `data`/`presumed_origin` to Outputs From Earlier Transactions - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
The Pterodactyl advisory describes a missing ownership check: a resource (server) is fetched by UUID without verifying the requesting node owns it, letting one principal's authority operate on another principal's resources. The Serai analog is in `Bitcoin::get_outputs` at `processor/src/networks/bitcoin.rs:686-736`: scanned `ReceivedOutput`s are accumulated into a single `outputs` vector across every transaction in a block, and then the `presumed_origin` and Serai `data` fields — extracted from *one* transaction — are unconditionally written onto **all** accumulated outputs, including outputs produced by earlier, unrelated transactions. The code never verifies that an output's `outpoint().txid` matches the transaction whose metadata is being applied — the exact "resource fetched/annotated without verifying ownership" shape (CWE-639/CWE-283).

### Finding Description
`get_outputs` iterates `for tx in &block.txdata[1 ..]` (coinbase skipped). Inside the loop:

1. `scanner.scan_transaction(tx)` pushes newly matched outputs into `outputs` (line 699). `outputs` is declared **outside** the transaction loop (line 689) and is never drained or scoped per-transaction.
2. After each `tx` that produced at least one *new* output (`if outputs.is_empty() { continue; }`, line 702), `presumed_origin` is derived from `tx.input[0]` (lines 707–729) and `data` from `Self::extract_serai_data(tx)` (line 730).
3. `for output in &mut outputs` (line 731) then writes `output.data = data` (for `OutputType::External`) and `output.presumed_origin = presumed_origin` — for **every element of `outputs`**, not just the ones scanned from `tx`. Outputs from earlier transactions in the same block are re-stamped with this transaction's origin and payload.

The only transaction-identity check present is `assert_eq!(output.tx_id(), tx.id())` at line 698, which runs on the newly pushed outputs *before* the metadata pass and does not constrain which transaction's metadata lands on which output. `Output::key()`/the `assert_eq!(output.key(), key)` in `processor/src/multisigs/scanner.rs:563` validate the key, not the data attribution.

`data` is the Serai `InInstruction` payload carried by the deposit's OP_RETURN-style commitment; downstream logic uses it to determine what the deposited funds are meant to do, and `presumed_origin` is used for refund/attribution purposes. Both are attacker-influenced fields of the attacker's own transaction.

### Impact Explanation
An unprivileged external party sends a Bitcoin transaction paying to Serai's `External` address (script derived deterministically from the group key) with attacker-chosen OP_RETURN data in a block that also contains an earlier legitimate deposit to `External`. Because the metadata pass rewrites `data` and `presumed_origin` on all previously collected outputs, the victim deposit's Serai instruction is replaced by the attacker's payload, and its recorded origin becomes the attacker's input. This yields funds reported received with the wrong instruction/origin — enabling misrouting/misattribution of deposits (value processed under attacker-chosen semantics rather than the depositor's), analogous to the advisory's "information/resources of server A exposed/manipulated under node B's authority."

### Likelihood Explanation
- Reachable entirely with public inputs: the attacker only needs to broadcast a normal Bitcoin transaction to a deterministic, publicly derivable Serai address in the same block as a victim deposit.
- The attacker cannot directly control intra-block ordering; they need their transaction to appear *after* the victim's. This reduces to block-position grinding/relay timing or miner cooperation, so likelihood is moderate rather than certain.
- The victim deposit must be `OutputType::External` for `data` to be overwritten (`presumed_origin` is overwritten for all kinds).

### Recommendation
Scope the metadata assignment to the outputs scanned from the current transaction only. For example, record the length of `outputs` before `scanner.scan_transaction(tx)` and apply `presumed_origin`/`data` only to `outputs[start..]`, or collect per-transaction `Vec`s inside the loop. Additionally (defense in depth), assert `output.tx_id() == tx.id()` inside the `for output in &mut outputs` metadata loop, or store the owning `txid` alongside each output and skip non-matching outputs.
