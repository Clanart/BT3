### Title
`ThresholdKeys::read` deserializes untrusted secret share and verification shares without consistency or identity validation, yielding attacker-controlled group keys - ([File: crypto/dkg/src/lib.rs])

### Summary
The XStream/XML deserialization bug class maps onto Serai's `ThresholdKeys::read`: a security-critical key object is reconstructed from raw bytes without verifying that the deserialized secret share is consistent with the deserialized verification shares, and without rejecting identity verification shares. A crafted blob produces a `ThresholdKeys` whose `group_key` is fully attacker-determined.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation tag, `n` constant-interpolation scalars, a `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` [1](#0-0) . The verification shares are read with `<C as Ciphersuite>::read_G`, which enforces canonical encoding but does **not** reject the identity point (that check only exists in `Curve::read_G` in the FROST crate) [2](#0-1) [3](#0-2) .

`ThresholdKeys::new` checks only that there are `n` verification shares keyed by participants `<= n`, and that constant interpolation implies `t == n`. It then computes `group_key` purely from `verification_shares[1..=t]` [4](#0-3) . It never verifies that `C::generator() * secret_share == verification_shares[i]`, that `secret_share` is non-zero, or that any verification share is non-identity. Consequently a crafted serialization fully determines `group_key` independent of the stored share, or installs an inconsistent share that produces invalid signature shares at signing time.

### Impact Explanation
A `ThresholdKeys` blob is the root of trust for the validator's FROST signing keys. An attacker who can feed crafted bytes to `ThresholdKeys::read` (key backup/import path) can supply `(t, n, i, secret_share = a, verification_shares = {1 => a*G, ...})` for an attacker-known scalar `a`. All nodes accepting the blob agree on `group_key` derived from shares `1..=t`, which is a key the attacker knows outright. Funds reported as received by that multisig are then spendable by the attacker without any threshold signature — or, with inconsistent shares, every signature attempt fails, permanently bricking the key. This is key-share/group-key substitution via deserialization of untrusted data, directly matching the reported bug class.

### Likelihood Explanation
Exploitation requires delivering a crafted serialization to `ThresholdKeys::read` rather than merely sending protocol messages, so it is lower likelihood than a pure network-input bug. However the function is a public deserialization API on a secret-bearing type with no integrity framing (no MAC, no consistency proof), and the code comments acknowledge it is used to reconstruct keys from serialized form in production flows.

### Recommendation
In `ThresholdKeys::new` (or at the end of `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]`, reject identity/non-canonical verification shares, and reject a zero secret share. Optionally authenticate serialized key blobs (e.g., MAC or signature) so untrusted bytes cannot be injected as key material.

### Proof of Concept
```rust
// Craft a ThresholdKeys<Ristretto> blob whose group key is attacker-known
let a = <Ristretto as Ciphersuite>::F::random(&mut OsRng); // attacker's scalar
let mut buf = vec![];
buf.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(1u16.to_le_bytes());            // t = 1
buf.extend(2u16.to_le_bytes());            // n = 2
buf.extend(1u16.to_le_bytes());            // i = 1
buf.push(1);                             // Interpolation::Lagrange
buf.extend(a.to_repr().as_ref());          // secret_share = a
buf.extend((Ristretto::generator() * a).to_bytes().as_ref());  // share 1 -> aG
buf.extend(Ristretto::generator().to_bytes().as_ref());        // share 2 (any point)
let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_ref()).unwrap();
// keys.group_key() == a*G: a key whose discrete log is known only to the attacker
```
`ThresholdKeys::new` succeeds because it never checks that `secret_share` is consistent with the installed verification shares, and accepts identity/arbitrary points for shares `2..=n` [5](#0-4) .

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
