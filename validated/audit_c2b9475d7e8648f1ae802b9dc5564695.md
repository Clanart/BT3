## Title
Attacker-controlled branch name from a fetched/cloned repository can inject a `git checkout` option flag due to misplaced `--` argument terminator - (File: `app/src/lib/git/checkout.ts`)

### Summary
The external report's broken invariant is: a value that is supposed to be constrained to a "safe" role (an *address allowed to manage a Safe*) instead reaches a privileged execution path in the wrong context, because the guard/wiring that should stop it was missing or ineffective. The Desktop analog is structurally the same class of bug: a value that is supposed to be constrained to a "safe" role (a *ref name, treated as a plain positional argument to `git`*) instead reaches `git`'s option parser, because the `--` end-of-options guard that is supposed to stop that was placed **after** the untrusted value instead of before it.

### Finding Description
`getBranchCheckoutArgs()` in [1](#0-0)  builds the argument list for `git checkout` as:

```
[branch.name, ...(remote ? ['-b', branch.nameWithoutRemote] : []), '--']
```

and `checkoutBranch()` combines it with the base args as `[...baseArgs, ...(await getBranchCheckoutArgs(branch))]` in [2](#0-1) , producing a command shaped like:

```
git checkout --progress <branch.name> [-b <nameWithoutRemote>] --
```

`branch.name` is the *first* positional token after `checkout`/`--progress`, and the `--` end-of-options marker is placed at the very *end* of the argument list, i.e. **after** the attacker-influenced value has already been read by Git's option parser. This is the same broken-invariant pattern as the original report: a protection mechanism exists in the code (`--`) but is wired up in a way that never actually intercepts the untrusted value before it reaches the privileged operation, just as `allowSAFE()` existed but was never reachable through the trusted proxy path.

`branch.name` and `branch.nameWithoutRemote` originate from ref names discovered via `for-each-ref` (see `getBranches()`/`app/src/lib/git/for-each-ref.ts`), which enumerates **all local and remote-tracking refs**, including refs created by fetching from a remote the user does not control (e.g. cloning/adding a malicious remote, or a repository containing a crafted `refs/heads/...` or `refs/remotes/<remote>/...` name). Git's `git-check-ref-format` rules used to validate ref names do **not** forbid a ref component from starting with a hyphen (`-`), only leading dots, control characters, `~^:?*[\`, `..`, `@{`, trailing `.lock`, and trailing `/` — see the equivalent allow-list Desktop itself uses for user-typed names in [3](#0-2) . Note that `sanitizedRefName()` *does* strip a leading `-`/`+` for user-entered branch names, but this sanitizer is only applied to names the user types (e.g. create/rename branch dialogs) — it is never applied to ref names discovered from a fetched remote and surfaced through `getBranches()`/the branches list UI, which is exactly the path `checkoutBranch()` consumes.

Because Electron's `git()` wrapper invokes Git via `execFile`-style argv arrays (not a shell), classic shell-metacharacter injection is not possible, but **Git-option injection** is: any ref name beginning with `-` that reaches `git checkout` before the `--` terminator will be parsed as a command-line option rather than a ref, e.g. a remote branch literally named `--orphan`, `-B`, `--detach`, or (more importantly) an option that accepts a following value that can itself be attacker-shaped.

### Impact Explanation
This lets an attacker who controls a remote/repository the victim adds and fetches (unprivileged: no local access needed, just a git remote or a repository link the victim clones) get a chosen `git checkout` flag executed inside the user's working directory the moment the user checks out that branch from Desktop's branch list, silently changing what gets checked out/committed (e.g. via `--orphan`, `-B <existing-branch>` to force-reset an existing local branch pointer, or `--detach`) — matching the "silent corruption of what the user commits or pushes" impact bucket. It does not require admin rights, local/physical access, prior malware, or leaked credentials, and requires only the natural Desktop workflow of adding/fetching a remote and clicking "checkout" on a branch — no unnatural steps.

### Likelihood Explanation
Likelihood is Medium: it requires the victim to add/clone a remote controlled (or influenced, e.g. via a compromised upstream/mirror) by the attacker and then select the maliciously-named branch for checkout in the Desktop UI, which is a common, expected workflow (adding remotes and checking out branches from them). Desktop does not currently filter or warn about ref names beginning with `-` anywhere along this path, unlike the explicit sanitization it performs for user-authored branch names.

### Recommendation
Move the `--` end-of-options terminator to precede all attacker-controllable positional arguments (i.e., emit `git checkout --progress -- <branch.name>` and use `git branch -- <nameWithoutRemote>` semantics, or otherwise place `--` immediately after the subcommand/flags and before any ref name), and/or apply the same `testForInvalidChars`/leading `-`/`+` rejection used in `sanitize-ref-name.ts` to ref names sourced from `for-each-ref` before they are used to build `git` argv, not only to user-typed names.

### Proof of Concept
1. Attacker creates a repository/remote containing a branch literally named `--orphan` (a valid ref name under `git-check-ref-format`, since a leading `-` is not one of the disallowed patterns applied in `sanitize-ref-name.ts`).
2. Victim adds this remote in GitHub Desktop and fetches it, so `for-each-ref`/`getBranches()` returns a `Branch` object with `name`/`nameWithoutRemote` equal to `--orphan`.
3. Victim selects that branch in the branches list and Desktop invokes `checkoutBranch()`, which calls `git(['checkout', '--progress', '--orphan', '--'], ...)` (local-branch case) — the `--orphan` token is consumed as a real Git checkout option instead of a literal ref name, because the `--` terminator is placed after it, not before.
4. Confirm by inspecting `getBranchCheckoutArgs()` output for `branch.name === '--orphan'`: the terminator ordering shows `--` is the last element, so it never precedes/protects the ref-name argument, unlike a defensively-correct build such as `['checkout', '--progress', '--', branch.name]`.

I was unable to fully trace whether `git-check-ref-format`/`for-each-ref` parsing in this fork applies any additional filtering beyond what's shown in `sanitize-ref-name.ts` and `for-each-ref.ts` (only partially indexed), so confirm in a live checkout that a remote-tracking ref literally named `-orphan`/`--orphan` survives unmodified into the `Branch` model before relying on this PoC end-to-end.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
