## Title
`resolveWithin` containment check uses unanchored `String.prototype.startsWith`, allowing sibling-directory path escape from an attacker-controlled deep-link `filepath` - (File: app/src/lib/path.ts)

### Summary
`_resolveWithin` (used by `resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) is the function that guarantees a user-influenced relative path "resides at, or underneath" a given root directory. The final containment check, `realResolved.startsWith(realRoot)`, is a bare string-prefix comparison with no trailing path separator, so any resolved path whose string representation merely begins with `realRoot` — including a sibling directory such as `realRoot + "-evil"` — passes the check even though it is not actually inside the root. This is invoked from the `x-github-client://openRepo/...?filepath=...` deep-link handler, where `filepath` is attacker-supplied.

### Finding Description
`resolveWithin` is documented to guarantee containment: [1](#0-0) 

but the actual boundary test omits the separator: [2](#0-1) 

`realResolved.startsWith(realRoot)` treats `realRoot` as a mere character prefix rather than a path-segment boundary. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and a crafted relative segment resolves to `/Users/victim/Documents/GitHub/repo-secrets/id_rsa` (a sibling directory that just happens to start with the same characters as the root directory name), the check `"...repo-secrets/id_rsa".startsWith("...repo")` is `true`, so the function returns the resolved path as "safe" even though it is a completely different directory tree.

Compare this with the same codebase's own hardened pattern used elsewhere for an analogous containment check, which correctly appends the separator: [3](#0-2) 

The vulnerable function is reachable from the "Open in Desktop" URL handler, which is triggered by a user clicking an attacker-controlled `x-github-client://openRepo/...` link (an unprompted, unprivileged, remote-controlled trust boundary): [4](#0-3) 

`filepath` here comes straight from the URL query string with only an `isAbsolute` check applied before being handed to `resolveWithin`: [5](#0-4) 

Because `repository.path` (the root) is itself derived, in the auto-clone flow, from an attacker-supplied repository name via `sanitizeCloneName`, and because Desktop users routinely clone multiple repositories into the same parent "GitHub" folder, an attacker who knows or can predict a sibling directory name sharing the target directory's name as a prefix (e.g. an already-cloned repo named `desktop-secrets`, `myrepo-old`, `myrepo2`, etc., or one the same deep link causes to be cloned) can construct a `filepath` value such as `../myrepo-secrets/config.json` that resolves outside the intended repository root while still passing the `resolveWithin` guard.

### Impact Explanation
The consumer of the return value, `shell.showItemInFolder(resolved)`, reveals/opens a file outside the cloned repository's working directory in the OS file explorer — a containment/read-outside-repo primitive driven entirely by a link the user clicks, matching the "attacker controls a link/deep link the user clicks... resulting in ... file... read outside the repo" impact category. The same `resolveWithin` primitive is also relied on elsewhere for security-relevant path containment (`app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`), so the missing separator check is a systemic weakness in the app's core "stay inside this directory" guarantee, not isolated to one call site.

### Likelihood Explanation
Exploitation requires: (1) a user clicking a crafted `x-github-client://openRepo/...?filepath=...` link (no other user action needed, matches the "link the user clicks" attacker-controlled vector), and (2) the existence of a sibling directory under the same parent whose name is prefixed by the target repository's directory name. Condition (2) is a real-world common occurrence given Desktop's default behavior of cloning all repositories into one shared parent folder with names like `repo`, `repo-fork`, `repo-old`, `repo2`, etc. This makes the bug practically triggerable without any privileged access, though the specific target file is constrained by what sibling directories exist, moderating (but not eliminating) severity.

### Recommendation
Change the final check in `_resolveWithin` to require a directory-boundary match, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator via the passed-in `options`), mirroring the pattern already used correctly in `isClonePathSensitive` in `app/src/lib/git/clone.ts`.

### Proof of Concept
1. User has previously cloned two repositories into the same parent directory: `~/Documents/GitHub/myrepo` and `~/Documents/GitHub/myrepo-secrets` (the latter could itself be a repo the attacker got the victim to clone earlier, or any coincidentally-named folder, e.g. a personal notes folder).
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Fid_rsa`
3. Desktop resolves the repository to `~/Documents/GitHub/myrepo`, calls `openRepositoryFromUrl`, and invokes `resolveWithin(repository.path, "../myrepo-secrets/id_rsa")`.
4. `resolved` becomes `~/Documents/GitHub/myrepo-secrets/id_rsa`; `realResolved.startsWith(realRoot)` evaluates to `true` because `"myrepo-secrets"` textually starts with `"myrepo"`.
5. `shell.showItemInFolder(resolved)` is called, revealing a file outside the intended repository tree, in violation of the function's documented containment guarantee at [1](#0-0) .
