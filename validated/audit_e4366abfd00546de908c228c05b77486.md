### Title
Deep-link `filepath` parameter is unsanitized while sibling parameters are validated - ([File: app/src/lib/parse-app-url.ts])

### Summary
`parseAppURL()` is the entry point for attacker-controlled deep links (`x-github-client://…`, `github-mac://…`, `x-github-desktop-auth://…`) that any web page or email can invoke via a clicked link, and macOS registers `open-url` to route directly into this parser with no other gate. Within the `openrepo` action, the `branch` and `pr` query parameters are explicitly validated (`testForInvalidChars`, digit-only regex), but the `filepath` parameter is extracted with `getQueryStringValue()` and passed straight through into `IOpenRepositoryFromURLAction` with zero validation.

### Finding Description
`parseAppURL()` builds the `open-repository-from-url` action like this: [1](#0-0) 

Notice `pr` is checked against `/^\d+$/`, `branch` is checked with `testForInvalidChars`, but `filepath` has no equivalent check before being stored on the action object. This asymmetry is the "too open" pattern from the seed report: one caller/parameter path in the routine has restrictions, while a sibling path that reaches the same trust boundary has none.

This action is dispatched to the renderer and consumed by `Dispatcher.dispatchURLAction` → `openRepositoryFromUrl`, and the `filepath` value is threaded through the clone flow (referenced multiple times in `app/src/ui/dispatcher/dispatcher.ts`) to open a specific file once the clone completes. [2](#0-1) 

The application already treats other user-input-derived paths as dangerous — e.g. `sanitizeCloneName()` explicitly guards against `../` traversal segments so a malicious repo name from a URL can't escape the clone base directory, and `resolveWithin()`/`isClonePathSensitive()` exist specifically to stop crafted URLs from writing/reading outside the intended directory. [3](#0-2) [4](#0-3) 

The `filepath` value doesn't benefit from any of these guards at the point it's parsed, which means the "restriction" applied to comparable attacker-controlled strings (branch names, clone destination names) is missing for this one.

### Impact Explanation
If the value that eventually reaches file-open/shell logic is derived by naively joining `filepath` onto the freshly cloned repository path (the standard pattern for this feature), an attacker-crafted deep link such as `x-github-client://openrepo/https://github.com/attacker/repo?filepath=../../../../some/sensitive/file` could cause Desktop to open a file outside the cloned repository once the user clicks the link and the app finishes cloning. This is a "silent" alteration of the file the user ends up viewing/opening — the exact class of impact called out as valid (attacker controls a link the user clicks; the app reads/opens something the user didn't intend, outside the repo boundary).

### Likelihood Explanation
Likelihood is moderate: the trigger requires only a clicked link (no local access, no malware, no admin rights), matching the valid-impact criteria. However, I was not able to retrieve the exact downstream code in `dispatcher.ts`/`app-store.ts` that consumes `action.filepath` to confirm precisely how it is joined to the repository path or whether a later, unseen guard (e.g. a `resolveWithin` check) exists at the consumption site — my tool budget was exhausted before reaching that specific call site. This is a real gap in my verification, and I flag it explicitly rather than asserting the sink is unguarded.

### Recommendation
Apply the same restriction used for `branch` to `filepath` at parse time in `parseAppURL()` (e.g., reject values containing `..`, absolute-path indicators, or drive letters, or route the value through `resolveWithinPosix`/`resolveWithinWin32` before use), and confirm/add a `resolveWithin`-style containment check at the point where `filepath` is joined to the cloned repository path before any open/read attempt.

### Proof of Concept
1. Attacker publishes a link: `x-github-client://openrepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim (with GitHub Desktop registered as the protocol handler) clicks the link.
3. `handleAppURL` → `parseAppURL` accepts the URL and produces `{ name: 'open-repository-from-url', url: '.../attacker/repo', filepath: '../../../../.ssh/id_rsa', branch: null, pr: null }` with no traversal check on `filepath`, unlike the check applied to `branch`. [5](#0-4) [1](#0-0) 
4. This action is dispatched to `openRepositoryFromUrl`, which clones `attacker/repo` and (per the intended feature) opens `filepath` relative to the clone directory — the unresolved consumption code should be reviewed to confirm whether traversal segments are stripped before use.

**Note on confidence:** I confirmed the missing input validation at the parser (`app/src/lib/parse-app-url.ts`), which is a real, verifiable asymmetry versus `branch`/`pr` validation, and confirmed `filepath` propagates into `dispatcher.ts`. I could not confirm within this session whether the actual file-open call at the consumption site already re-validates the path (which would neutralize the issue). If a Devin session is available, the next step should be to locate `openRepositoryFromUrl`'s handling of `filepath` in `app/src/ui/dispatcher/dispatcher.ts` and `app-store.ts` to determine whether a containment check exists before the file is opened.
