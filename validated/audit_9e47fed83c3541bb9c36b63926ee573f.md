## Finding

### Title
IntentGatewayV2 (Tron) escrows and refunds/settles the pre-transfer `amount` instead of the tokens actually received, causing shared-pool insolvency with fee-on-transfer/deflationary tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow with the nominal input amount from the order rather than the tokens actually received by the contract. Unlike the EVM mainline version, it has no fee-on-transfer/deflationary-token accounting.

### Finding Description
In the EVM `IntentGatewayV2.sol`, the non-predispatch escrow path explicitly measures the actual amount received and rewrites `order.inputs[i].amount` to that real balance delta before it is used for the commitment or escrow accounting: [1](#0-0) 

The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, drops this safeguard in its equivalent non-predispatch branch: it calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits escrow with `reducedInputs[i].amount` — a value derived purely from the pre-transfer `order.inputs[i].amount` — with no balance-before/after check: [2](#0-1) 

`reducedInputs` (used to populate `_orders[commitment][token]`) is computed earlier purely from `order.inputs[i].amount`, before any transfer occurs: [3](#0-2) 

If `token` is a fee-on-transfer/deflationary ERC-20, the contract's actual balance increases by less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is still incremented by the full (fee-inclusive) `reducedInputs[i].amount`. `_orders` is a single mapping shared by every order/commitment for that token across the whole contract; it does not track a segregated, per-order token balance in vault form — it is bookkeeping used to authorize later payouts via `withdraw`.

Both settlement paths that eventually call `withdraw` trust the nominal amount recorded in escrow (which equals the deficit-inflated `order.inputs`/`body.tokens[i].amount`), not the contract's real token balance: [4](#0-3) 

`withdraw` only checks `_orders[body.commitment][token] == 0` (i.e., the order exists) — it never validates that `IERC20(token).balanceOf(address(this))` actually holds the amount it is about to pay out, and it unconditionally transfers `amount` (the nominal, pre-fee amount) to `beneficiary`, decrementing the bookkeeping map by that same nominal amount.

### Impact Explanation
Because `_orders` bookkeeping is inflated relative to real custody for every order that uses a deflationary token, the contract's real balance of that token is short by the sum of all transfer fees ever taken. Since the token custody pool is shared across all commitments, later `withdraw` calls (redemptions/refunds/cancellations for *other, unrelated* orders using the same token) can be executed for the full nominal amount even though the pool is undercollateralized — draining tokens that rightfully belong to other users' un-redeemed escrows, and eventually causing `token.call(transfer)` reverts (fund lock) for whichever order is unlucky enough to be redeemed last. This is a direct fund-loss/fund-lock impact on the bridge's custody accounting, matching the "loss of funds to other users" pattern in the original Yieldy report.

### Likelihood Explanation
Any unprivileged user can call `placeOrder` with an arbitrary ERC-20 `token` address of their choosing (there is no allow-list check on `order.inputs[i].token` in this code path), so triggering the deficit requires nothing more than placing an order using any deflationary/fee-on-transfer token. This is a normal, permissionless, public entry point — no relayer, prover, or admin compromise is needed.

### Recommendation
Mirror the mainline EVM fix: measure `IERC20(token).balanceOf(address(this))` before and after the `safeTransferFrom` in the non-predispatch branch of the Tron `placeOrder`, and use the actual received delta (not the nominal `order.inputs[i].amount`) both for computing `reducedInputs`/the commitment hash and for the `_orders[commitment][token]` credit, consistent with the EVM implementation.

### Proof of Concept
1. Attacker deploys or uses an existing fee-on-transfer ERC-20 `token` (e.g., 5% transfer fee).
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [{token, amount: 1000}]` (no predispatch call).
3. `safeTransferFrom(msg.sender, address(this), 1000)` executes; contract actually receives only 950 tokens due to the fee, but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` derived from the original `1000` (minus protocol fee bps, not minus the token's transfer fee).
4. Repeat step 2/3 with several orders using the same deflationary token — each order under-delivers real tokens to the contract while over-crediting the internal `_orders` ledger.
5. When orders are settled/cancelled via `withdraw` (called from `onAccept` `RedeemEscrow`/`RefundEscrow` or the same-chain `cancelOrder` path), each payout transfers the full nominal `amount` recorded in `body.tokens[i].amount`, without checking real balance.
6. Once the accumulated nominal payouts exceed the token's real balance held by the contract (the sum of all transfer fees skimmed), a later legitimate order's `withdraw` call either reverts (fund lock for that user) or, if partial balances allow, effectively pays out tokens belonging to a still-unsettled order, resulting in loss of funds for that order's rightful beneficiary.
