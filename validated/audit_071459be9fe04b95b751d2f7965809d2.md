## Title
Partial-commit line selection is tracked by absolute diff-line index with no content binding, allowing silent inclusion/exclusion of unintended changes when the working file is modified between diff review and commit - (`File: app/src/models/diff/diff-selection.ts`)

### Summary
`DiffSelection`, the model backing GitHub Desktop's line-by-line ("partial") commit feature, records which lines a user wants to commit purely as a set of numeric `unifiedDiffStart`-relative indices, with no association to the actual line content or a hash of the diff it was computed against. When the working-directory diff is recomputed (file watcher-triggered status refresh, whitespace-hide toggle, or the second, independent diff fetch performed at commit time), the old numeric selection is carried forward and reapplied to the new diff by index only. If the underlying file changed between the user's review and the commit, the same indices now point at different hunks/lines, and `formatPatch()` builds the patch to `git apply --cached` from those mismatched indices — silently committing content the user never selected.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `isSelectable(lineIndex)` operate purely on integer indices: [1](#0-0) 

When a new diff is loaded for the currently selected file, Desktop remaps the previous selection state onto the new hunks by simply recomputing which indices are "selectable" and intersecting them with the previously diverging indices — it never re-validates that the same index still represents the same content: [2](#0-1) [3](#0-2) 

Crucially, the diff shown in the Changes view and the diff actually used to build the commit patch are fetched independently, at different times:
- The UI diff is fetched in `updateChangesWorkingDirectoryDiff`: [4](#0-3) 
- The commit-time diff is fetched again, freshly, inside `applyPatchToIndex`: [5](#0-4) 

`formatPatch()` then walks the *freshly fetched* diff's hunks and decides whether to include each line solely by asking `file.selection.isSelected(absoluteIndex)`, i.e. the stale, index-only selection from before: [6](#0-5) 

Because the selection object carries no reference to the diff/content it was derived from, there is no invariant tying "line 42 is selected" to "line 42 is still the change the user reviewed." Any modification to the working file between the last diff render and the `createCommit`/`applyPatchToIndex` call (which is unavoidable async window, and can be caused by build tools, linters/formatters, git hooks, or any other repository-provided tooling that touches tracked files, or simply the file watcher racing a second background status refresh) shifts hunk boundaries. The stale indices then get silently reinterpreted against unrelated lines in the new diff, producing a commit whose staged content differs from what the user selected and visually reviewed — with no error, warning, or diff re-confirmation shown before or after commit.

This is directly analogous to the SushiSwap bug: a derived/cached quantity (`reserve0/1`, here the line-index-based `DiffSelection`) is not kept consistent with the authoritative current state (`balance0/1`, here the live git diff), and is nonetheless used unchanged to drive a critical state-mutating operation (`burn()`, here `git apply --cached` / commit creation), corrupting the result.

### Impact Explanation
The result is silent corruption of what the user commits and subsequently pushes: unintended lines can be included (leaking/committing content the user explicitly deselected) or intended lines can be dropped (silently discarding a fix, e.g. a security patch, from the commit) without any indication to the user. Since Desktop shows no post-commit diff confirmation, the user has no way to detect the discrepancy from the UI alone. This can propagate corrupted/incomplete commits into shared history once pushed.

### Likelihood Explanation
Triggering this requires only that the tracked working-directory file changes after the user forms a partial line selection and before the commit patch is generated — a window that already exists in normal Desktop operation (status/diff are polled/refreshed on file-system events, and the commit-time diff fetch is a second, independent `git diff` call). Any tooling in the repository ecosystem (pre-commit hooks, linters/formatters, build watchers) that touches files during this window turns an otherwise benign flow into silent commit corruption; no elevated privileges, malware, or unnatural user steps are needed beyond the standard "select some lines, then commit" workflow.

### Recommendation
Bind `DiffSelection` state to the diff it was computed from (e.g., a content hash or hunk signature per selectable index) so that when a new diff is loaded, previously diverging indices are only preserved if the corresponding line's content is unchanged; otherwise the affected selection should be reset/cleared and surfaced to the user. Additionally, `applyPatchToIndex`/`createCommit` should validate that the diff used to build the patch matches the diff last presented in the UI (e.g., by re-diffing and comparing content, not just fetching a fresh diff and blindly reapplying old indices) before finalizing the commit.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt` so it has two separate hunks (e.g., changes near line 5 and line 50).
2. In the Changes view, select only the hunk near line 50 for commit (partial selection), leaving line 5's hunk unselected.
3. Before clicking "Commit", have any repo-provided tooling (e.g., a `pre-commit`/`post-checkout` hook, a lint-staged/husky script, or a file watcher such as a bundler) insert/remove a line above line 5, shifting all subsequent line numbers in the file by one or more.
4. Desktop's background status refresh recomputes the diff; the previous partial selection (line indices around 50) is carried over via `withSelectableLines` purely by index, per [2](#0-1) .
5. Click "Commit". `applyPatchToIndex` fetches a brand-new diff and `formatPatch` applies the old numeric selection to it per [6](#0-5) , resulting in a patch built from the wrong hunk/lines relative to what the user actually reviewed and clicked to include.
6. Inspect the resulting commit: it contains content different from the lines the user selected in the UI, with no warning shown.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
