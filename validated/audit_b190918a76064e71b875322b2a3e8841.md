### Title
Type-change (mode) status codes silently collapse to "Modified", hiding symlink/regular-file conversions from review and diff — ([File: app/src/lib/status-parser.ts])

### Summary
GitHub Desktop's porcelain-v2 status classifier `mapStatus` only has explicit branches for `M`/`A`/`D`/`R`/`C`/`??` and the standard conflict codes. [1](#0-0) [2](#0-1)  Any status code it doesn't recognize — including Git's typechange code `T` (e.g. `.T`, `T.`, `MT`, `TM`, produced when a tracked file switches between a regular file, symlink, or submodule gitlink) — falls through to an unconditional default that reports the file as an ordinary "modified" file with no further distinction: [3](#0-2) 

This is the same class of bug as the `extcodehash` report: a state-classification function that special-cases the criteria it explicitly checks for, but silently misclassifies an out-of-band edge case as a "safe/default" state rather than surfacing the true nature of the change.

### Finding Description
`convertToAppStatus` in `app/src/lib/git/status.ts` converts the `FileEntry` produced by `mapStatus` into `AppFileStatusKind`. Because the fallback branch returns `kind: 'ordinary', type: 'modified'`, a typechange entry becomes indistinguishable from a normal content edit and is rendered with `AppFileStatusKind.Modified`: [4](#0-3) 

Desktop's diff parser (`app/src/lib/diff-parser.ts`) has no handling for the `old mode` / `new mode` header lines Git emits on a typechange diff (confirmed: no matches for `old mode`/`new mode` anywhere in that file), so the raw patch is parsed as an ordinary text diff. For a file converted from a regular file to a symlink, the patch content is literally `-<old file contents>` / `+<symlink target path>` — a two-line "text diff" that gives no structural signal that the entry is now a symlink.

Contrast this with how Desktop already treats renames specially in the UI — there is dedicated code to detect and flag "renamed and includes changes" vs. "renamed but not changed": [5](#0-4) 

No equivalent warning path exists for a type change, because the underlying status classification (`mapStatus`) never labels it as anything other than a generic "Modified" — the same "checked the wrong set of criteria and returned the default" pattern the zkSync report describes for `getCodeHash`.

### Impact Explanation
An attacker who controls a repository, branch, or PR that the victim fetches/clones/checks out (a permitted attacker primitive) can craft a commit that converts a tracked file — for example a build script, a `.gitignore`, or a path referenced by tooling — into a symlink pointing outside the working directory (or the reverse, converting a symlink into a plain file to defeat a symlink-based safety check elsewhere in tooling). In Desktop's Changes list and diff view this shows only as an ordinary "Modified" file with a two-line content diff, not as a highlighted type/mode change. A user who reviews the (deceptively small) diff and stages/commits it will silently commit a file-type change they did not knowingly review, which is the "silent corruption of what the user commits or pushes" impact category. It could also be leveraged in combination with any Desktop or downstream tooling behavior that treats symlinked paths specially.

### Likelihood Explanation
Likelihood is low-to-medium: it requires the victim to open a repository containing an attacker-crafted typechange commit, which is a normal, unprompted workflow (fetching a branch/PR) rather than any privileged or local-access step. However, exploitation depends on the user not noticing the tiny diff content itself (the symlink target string), so this is a UI/labeling gap rather than a fully silent corruption — similar to how the zkSync finding was judged medium-impact/low-probability due to being an edge case rather than a directly exploitable primitive.

### Recommendation
Add explicit handling in `mapStatus` (`app/src/lib/status-parser.ts`) for typechange status codes (`.T`, `T.`, `MT`, `TM`, etc.) that returns a distinct `AppFileStatus` kind (e.g. `TypeChanged`) instead of falling through to the generic "modified" default. Extend `convertToAppStatus` and the UI (`app/src/ui/diff/index.tsx`) to surface a clear warning banner analogous to the rename-with-modifications case whenever a file's type changes (especially to/from a symlink), and parse the `old mode`/`new mode` diff headers in `diff-parser.ts` so the mode transition is available to the renderer.

### Proof of Concept
1. In a test repository, commit a regular file `foo.txt`.
2. In a subsequent commit, delete `foo.txt` and recreate it as a symlink (`ln -s /etc/passwd foo.txt`), producing a Git typechange (`git diff --raw` shows status `T`, porcelain v2 shows `.T`/`T.`).
3. Push this as a branch/PR and have the victim fetch/checkout it in Desktop.
4. Observe: `getStatus`/`mapStatus` classify `foo.txt` as ordinary "Modified" (fallback at status-parser.ts:420-426) with no type-change indicator, and the diff view renders a plain two-line text diff rather than a mode-change warning — matching the code paths cited above.

export function mapStatus(
  statusCode: string,
  submoduleStatusCode: string,
  renameOrCopyScore: number | undefined
): FileEntry {
  const submoduleStatus = mapSubmoduleStatus(submoduleStatusCode)

  if (statusCode === '??') {
    return { kind: 'untracked', submoduleStatus }
  }

  if (statusCode === '.M') {
    return {
      kind: 'ordinary',
      type: 'modified',
      index: GitStatusEntry.Unchanged,
      workingTree: GitStatusEntry.Modified,
      submoduleStatus,
    }
  }

  if (statusCode === 'M.') {
    return {
      kind: 'ordinary',
      type: 'modified',
      index: GitStatusEntry.Modified,
      workingTree: GitStatusEntry.Unchanged,
      submoduleStatus,
    }
  }

  if (statusCode === '.A') {
    return {
      kind: 'ordinary',
      type: 'added',
      index: GitStatusEntry.Unchanged,
      workingTree: GitStatusEntry.Added,
      submoduleStatus,
    }
  }

  if (statusCode === 'A.') {
    return {
      kind: 'ordinary',
      type: 'added',
      index: GitStatusEntry.Added,
      workingTree: GitStatusEntry.Unchanged,
      submoduleStatus,
    }

    return {

      type: 'deleted',

  }
