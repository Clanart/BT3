### Title
`ThresholdKeys::read` deserializes an attacker-chosen secret share and verification shares without checking their consistency, yielding a fully attacker-controlled "threshold key" - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary

`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574`) accepts untrusted bytes and reconstructs a `ThresholdKeys` via `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349`). `ThresholdKeys::new` validates only the *count* and *index range* of `verification_shares` and the applicability of the interpolation method — it never verifies that the deserialized `secret_share` satisfies `C::generator() * secret_share == verification_shares[params.i()]`, nor that `verification_shares` are bound to the `secret_share` at all. This is the direct analog of the Ignition flaw (CWE-94: untrusted input passed insecurely to a sensitive operation): untrusted serialized bytes are trusted as a key material object without integrity/consistency checks, giving the supplier of the blob control over the resulting key.

### Finding Description

In the legitimate PedPoP DKG path, consistency between a secret share and its verification share is enforced cryptographically (`share_verification_statements` / batch verification in `crypto/dkg/pedpop/src/lib.rs:487-499`). `ThresholdKeys::read` bypasses all of that: it reads `t`, `n`, `i`, an interpolation method (with `Interpolation::Constant` reading `n` attacker-supplied coefficients at `crypto/dkg/src/lib.rs:607-613`), a raw `secret_share` scalar (`line 618`), and `n` raw `verification_shares` points (`lines 620-623`), then calls `ThresholdKeys::new`. `ThresholdKeys::new` (`lines 349-391`) computes `group_key` as `Σ verification_shares[j] * interpolation_factor(j, [1..=t])` — purely a function of the attacker-supplied points and coefficients — and stores the attacker-supplied `secret_share` alongside it with no consistency check.

An attacker who supplies the serialized blob can therefore craft `ThresholdKeys` where:
- `secret_share` is a scalar `s` known to them,
- `verification_shares[j] = G * s_j` for attacker-known `s_j` for all `j` in `1..=n`,

so that the derived `group_key` equals `G * Σ λ_j s_j` — a key whose entire discrete logarithm is known to the attacker. Alternatively, they can craft a blob where `verification_shares[i] ≠ G * secret_share`, so the victim signs shares under a `group_key` that no consistent quorum actually controls.

The Lagrange path is equally affected: `interpolation_factor` (`crypto/dkg/src/lib.rs:226-249`) operates on whatever participant indexes and points were deserialized, and `view()` (`lines 463-533`) will interpolate and offset the attacker-chosen secret share, emitting signature shares bound to the attacker-chosen verification shares.

### Impact Explanation

Any consumer that feeds untrusted/recovered/imported bytes to `ThresholdKeys::read` and then uses the result for FROST signing or address derivation ends up operating under a key whose group secret the attacker fully knows. Concretely:
- Funds sent to `group_key()` of a maliciously deserialized `ThresholdKeys` are spendable by the attacker alone — funds reported as belonging to the victim's threshold group that are not actually controlled by it.
- Signing with such keys produces shares the attacker can complete into valid signatures for a key they own, while the victim believes a threshold protocol protects it.
- Alternatively, inconsistent `secret_share`/`verification_shares[i]` pairs produce shares that fail verification, permanently bricking the key (DoS on funds) — but the primary impact is full key compromise.

### Likelihood Explanation

The bug requires an integrator to deserialize `ThresholdKeys` from a source an unprivileged party can influence (key import, backup/restore, migration, or replication paths — the format is a self-describing portable serialization including a curve ID check, clearly designed for persistence and transport). `read` is a public API explicitly listed as reachable with untrusted bytes. Since `ThresholdKeys::new` performs zero binding between the scalar and the points, exploitation is deterministic: no race, no brute force, no protocol cooperation needed. Severity: High (critical if a production path loads peer-supplied key blobs).

### Recommendation

In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Additionally, when `Interpolation::Constant` is deserialized, bound-check `c.len() == n` semantics are already implicit via read count, but the consistency check is the essential fix. Document that `ThresholdKeys` blobs are secret-and-integrity-sensitive and must only be loaded from authenticated storage.

### Proof of Concept

```rust
// Attacker crafts a serialized ThresholdKeys blob where they know the entire
// "group secret". For C = a ciphersuite, t = n = 1, i = 1:
let s = <C as Ciphersuite>::F::random(&mut rng);       // attacker-known secret
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes());                        // t = 1
blob.extend(1u16.to_le_bytes());                        // n = 1
blob.extend(1u16.to_le_bytes());                        // i = 1
blob.push(1);                                           // Interpolation::Lagrange
blob.extend(s.to_repr().as_ref());                      // secret_share = s
// verification_shares[1] = G * s  (consistent) -> group_key = G * s, fully known
blob.extend((C::generator() * s).to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut blob.as_ref()).unwrap();
// keys.group_key() == G * s: attacker knows the discrete log of the group's key.
// Any funds/authority the victim associates with keys.group_key() are attacker's.
// A variant blob with verification_shares[1] = G * y (y != s) is also accepted,
// producing keys whose shares can never verify (permanent fund lockup).
assert_eq!(keys.group_key(), C::generator() * s);
```
