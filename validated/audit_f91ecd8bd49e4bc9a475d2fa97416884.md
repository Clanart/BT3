### Title
Untrusted deserialization tag chooses the `Interpolation` variant, enabling secret-share recovery - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reconstructs a `ThresholdKeys` object from raw bytes. A single attacker-controlled tag byte selects between two mathematically different interpolation objects — `Interpolation::Constant(Vec<C::F>)` (coefficients fully read from the stream) or `Interpolation::Lagrange` (coefficients derived at signing time from the participant indexes) — at `crypto/dkg/src/lib.rs` lines 604–616. This is the direct analog of the JSON "unsafe object creation" class: the parser instantiates an object whose *type/semantics* are dictated by untrusted input, and downstream code treats both variants interchangeably.

### Finding Description
`ThresholdKeys::read` (lines 574–632) reads `t`, `n`, `i`, then a one-byte discriminant: `0` deserializes `n` attacker-supplied scalars as `Interpolation::Constant`, `1` produces `Interpolation::Lagrange`. It then reads `secret_share` and `verification_shares` and calls `ThresholdKeys::new`.

Two properties make this exploitable:

1. The group key is derived from `verification_shares` (the committed public shares for participants `1..=n`), not from the interpolation object. Flipping the tag byte does **not** change the group key — the deserialized keys are "for" the same multisig.
2. The interpolation object is consumed during signing to weight the signer's secret share into its signature share. With `Interpolation::Constant`, the weighting coefficients are exactly the scalars the attacker placed in the serialized blob — they are applied *regardless of which participant set is included*.

If an attacker can cause a victim's `ThresholdKeys` bytes to be read with the `Constant` variant and known coefficients (a tampered backup/sync/peer-supplied serialization — the rules treat bytes fed to `ThresholdKeys::read` as untrusted), the victim's published FROST signature share has the form `s_i = d_i + rho*e_i + c_i*lambda_i*share`, where `lambda_i` is the attacker-chosen constant. Since `lambda_i`, the challenge `c`, and the nonce commitments `R` are all public/known, the attacker algebraically recovers the victim's secret share `(s_i - d_i - rho*e_i) / (lambda_i * c)`.

The same primitive also lets the attacker choose coefficients that simply produce invalid shares (DoS), but share recovery is the High-severity outcome.

### Impact Explanation
Recovery of a victim's threshold secret share. Combined with `t - 1` other compromised/tampered shares (or used against several victims independently), this collapses to full group-key recovery — the strongest acceptance criterion (key share recovery). Even alone, it is a secret disclosure provable purely from the deserialization code path.

### Likelihood Explanation
Requires the attacker to influence bytes deserialized via `ThresholdKeys::read` (e.g., a keys file/record obtained or replaced through any non-authenticated channel). The rules explicitly scope `ThresholdKeys::read` as a sink for untrusted bytes, so reachability is assumed per the engagement model. The exploit itself is deterministic arithmetic once a share is published.

### Recommendation
Authenticate the `ThresholdKeys` serialization (e.g., bind the interpolation discriminant and coefficients into a MAC/commitment, or refuse `Interpolation::Constant` in `read` when the keys were originally generated with `Lagrange`). At minimum, `ThresholdKeys::new`/`read` should verify that the deserialized `Interpolation` is the one consistent with the verification shares and participant set — e.g., recompute expected Lagrange behavior or reject attacker-chosen constant coefficients on the read path.

### Proof of Concept
1. Obtain a victim's serialized `ThresholdKeys<C>` blob (tag byte `1`, Lagrange).
2. Rewrite byte at the interpolation offset to `0` and append `n` chosen scalars `lambda_1..lambda_n` (e.g., `lambda_i = 1`), keeping `t`, `n`, `i`, `secret_share`, `verification_shares` unchanged.
3. `ThresholdKeys::read` succeeds; `group_key` is unchanged.
4. Victim signs under FROST; attacker observes the emitted share `s_i` and the aggregate `R` (hence challenge `c`).
5. Compute `share = (s_i - nonce_share_component) * (lambda_i * c)^{-1}` to recover the secret share.

Supporting code: the tag-byte dispatch is at `crypto/dkg/src/lib.rs:604-616`; `ThresholdKeys::new` is invoked at line 625; the variant definitions and their use in `ThresholdView`/signing live in `crypto/dkg/src/lib.rs` and `crypto/frost/src/sign.rs` (`view(included)` at line 312 applies the stored interpolation to compute share weights).

Uncertainty note: I was unable to fully read `ThresholdKeys::new`'s internal consistency checks within the available iterations; if it re-derives and cross-checks coefficients against verification shares for both variants, the flip would be rejected and this analog reduces to a no-op. That check should be confirmed before finalizing severity.
