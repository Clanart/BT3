### Title
Unvalidated slice length in `on_accept` non-EVM calldata-origin branch causes panic on malformed `message.from` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`message.from` is decoded from attacker-controlled ABI-encoded `body` via `Message::abi_decode` [4](#0-3) , and its length is not constrained to 32 bytes by the type system at this point (it is a dynamic `bytes` field, as evidenced by the explicit length checks performed elsewhere for the same field). In `on_accept`'s optional-calldata handling, when `substrate_data.signature` is `None` and `source.is_evm()` is `false`, the code does:

```rust
let mut account = [0u8; 32];
account.copy_from_slice(from_bytes);
account.into()
```

with no length check. `copy_from_slice` panics if `from_bytes.len() != 32`, whereas the sibling `beneficiary_bytes` derivation (lines 63-71) and the `on_timeout` sender derivation (lines 224-232) both check `len() == 32`/`== 20` and return `HftError::InvalidRecipientLength`/`InvalidSenderLength` on mismatch.

### Finding Description
The token mint/transfer to `beneficiary` happens earlier in `on_accept` (lines 93-117), before the optional-calldata block (line 120 onward) that contains the vulnerable slice copy. A crafted `PostRequest` with a non-EVM `source`, no `substrate_data.signature`, and a `message.from` field whose byte length is not 32 (e.g., 19 or 33 bytes) will pass through the mint/transfer logic successfully, then panic at `account.copy_from_slice(from_bytes)` while attempting to derive the calldata-dispatch origin.

### Impact Explanation
A panic here diverges from the pallet's established error-handling convention (`Result::Err` via `HftError`), which is designed so that misbehaving cross-chain messages are rejected gracefully by the ISMP module dispatch machinery. Whether this manifests as an extrinsic-local revert or something more severe (e.g., a wasm runtime trap that aborts message processing/block execution) depends on how `pallet_ismp`'s request handler wraps calls to `IsmpModule::on_accept` (i.e., whether it is executed inside a `#[transactional]`/`with_storage_layer` boundary that reliably unwinds panics and rolls back all storage changes, including the mint/transfer already performed). I was not able to fully trace that wrapping in this session to confirm whether the mint/transfer is guaranteed to be rolled back or could persist while the message is otherwise treated as failed/reprocessed — this should be verified directly against `modules/ismp/core/src/handlers/request.rs` and the pallet's dispatch pathway.

### Likelihood Explanation
High. The attacker only needs control over the `body` payload of a `PostRequest` from a registered non-EVM `source`/`from` contract pairing (i.e., any legitimate registered token bridge configuration), with `substrate_data.signature == None` and a `message.from` of length ≠ 32. No privileged access is required beyond what's needed to route a message through `on_accept`, which is the normal unprivileged ISMP message-delivery path.

### Recommendation
Add the same length validation used for `beneficiary_bytes` (and in `on_timeout`) before this `copy_from_slice`, returning a typed error (e.g., a new `HftError::InvalidFromLength` variant) instead of allowing a panic:
```rust
let from_bytes = message.from.as_ref();
if from_bytes.len() != 32 {
    Err(HftError::InvalidFromLength(from_bytes.len()))?
}
let mut account = [0u8; 32];
account.copy_from_slice(from_bytes);
account.into()
```

### Proof of Concept
1. Register a non-EVM `source`/token mapping via `ContractToAsset`.
2. Craft a `PostRequest` whose `source` is non-EVM and whose `body` ABI-encodes a `Message` where `data` is a non-empty `SubstrateCalldata` with `signature = None`, and `from` is a byte array of length 19 or 33.
3. Deliver the message so it reaches `Pallet::<T>::on_accept`.
4. Observe that the mint/transfer to `beneficiary` (lines 93-117) executes, then execution reaches `account.copy_from_slice(from_bytes)` (line 184) and panics instead of returning `Result::Err`. [5](#0-4)
