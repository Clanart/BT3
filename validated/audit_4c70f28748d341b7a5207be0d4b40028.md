Found a valid analog in the governance vote-consistency logic for KIP-71 base fee bounds.

### Title
KIP-71 LowerBoundBaseFee/UpperBoundBaseFee votes are validated against stale ParamSet, allowing lowerBound > upperBound to be committed - ([File: kaiax/gov/headergov/impl/header.go])

### Summary
The Sherlock report describes a Solidity round-creation function that validates a set of related timestamp fields independently against stale/incorrect reference points instead of validating them against each other consistently, allowing an inconsistent final state (e.g., `roundStartTime < applicationsEndTime`). The kaia governance module has the same class of bug: `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` votes are each checked only against the *current* (pre-vote) `ParamSet`, not against each other or against a vote that is committed in the same epoch, so lowerBound can end up greater than upperBound.

### Finding Description
`checkConsistency` in `kaiax/gov/headergov/impl/header.go` validates a `Kip71LowerBoundBaseFee` vote by comparing the new value only to `params.UpperBoundBaseFee` fetched from `h.GetParamSet(blockNum)` — the current effective parameter set, not the value that would result after applying a `Kip71UpperBoundBaseFee` vote placed earlier in the same epoch: [1](#0-0) 

Each vote is validated independently at the time it is included in the header, against `h.GetParamSet(blockNum)`, which reflects only params already finalized from *previous* epochs (see `getExpectedGovernance`, which aggregates votes only from the previous epoch index): [2](#0-1) 

Because votes accumulated within the current epoch are not yet reflected in `GetParamSet`, if a governing/council voter (or a sequence of validly-authorized proposers across blocks within the same epoch, in "none"/ballot mode) first votes `kip71.lowerboundbasefee = X` (validated against the old, larger `UpperBoundBaseFee`) and then votes `kip71.upperboundbasefee = Y < X` (validated against the old, smaller `LowerBoundBaseFee`), both votes pass `checkConsistency` individually even though together they produce `LowerBoundBaseFee > UpperBoundBaseFee` once both are applied at epoch rollover via `getExpectedGovernance`/`NewGovData`. This mirrors the Sherlock issue where each timestamp field is checked against a stale reference instead of the final, consistently-ordered configuration.

The resulting inconsistent pair is then consumed directly by KIP-71 base-fee computation, which assumes `LowerBoundBaseFee <= UpperBoundBaseFee`: [3](#0-2) 

### Impact Explanation
An inverted `LowerBoundBaseFee > UpperBoundBaseFee` governance parameter pair corrupts `NextMagmaBlockBaseFee`'s clamping logic (`parentBaseFee.Cmp(upperBoundBaseFee) >= 0` vs `.Cmp(lowerBoundBaseFee) <= 0`), producing base-fee values that do not converge to a stable/expected range, or diverge from what honest nodes computing consensus on the header's base fee would expect once the parameters are network-wide agreed. This directly affects `VerifyMagmaHeader`, which all nodes use to validate block base fees — an inconsistent parameter state accepted by one code path but causing another downstream computation to misbehave can lead to acceptance of blocks with an unintended base fee, affecting fee/burn accounting for every transaction in the network (state divergence / incorrect fee enforcement across the network).

### Likelihood Explanation
This requires an authorized voter (governing node in single mode, or any council member able to write `header.Vote` in ballot-style modes) to submit two governance votes for `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` in the same epoch, in the specific order that crosses each other. This is a privileged action gated by council/governing-node status rather than an arbitrary unprivileged transaction, which reduces likelihood relative to a fully permissionless bug, but it is still reachable through the normal vote/header-proposal mechanism without any additional out-of-band trust, and the check-order dependency (stale `GetParamSet` reference) is a genuine logic gap rather than a defense-in-depth control.

### Recommendation
When validating `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` votes in `checkConsistency`, account for any pending vote of the counterpart parameter already accepted within the same (not-yet-finalized) epoch — i.e., compute the vote's effective value against the value that would be in effect after applying all prior votes in the current epoch, not just `h.GetParamSet(blockNum)`. Alternatively, perform a final consistency check at epoch-boundary governance construction (`getExpectedGovernance`) rejecting/clamping any resulting `LowerBoundBaseFee > UpperBoundBaseFee` combination before it is written into `header.Governance`.

### Proof of Concept
1. At epoch start, current params: `LowerBoundBaseFee = 25e9`, `UpperBoundBaseFee = 750e9`.
2. Governing node proposes block N with `Vote = {kip71.lowerboundbasefee: 700e9}`. `checkConsistency` compares `700e9 > params.UpperBoundBaseFee(750e9)`? No → accepted [4](#0-3) .
3. Same epoch, block N+1, governing node proposes `Vote = {kip71.upperboundbasefee: 100e9}`. `checkConsistency` compares `100e9 < params.LowerBoundBaseFee(25e9)`? No (still using stale pre-epoch `LowerBoundBaseFee`) → accepted [5](#0-4) .
4. At next epoch boundary, `getExpectedGovernance` aggregates both votes into the new `GovData`, producing `LowerBoundBaseFee=700e9 > UpperBoundBaseFee=100e9` [2](#0-1) .
5. `NextMagmaBlockBaseFee` now operates with an inverted bound pair, producing incorrect/undefined base-fee clamping behavior [6](#0-5) .

// The blockNum's epoch index must be greater than 0. That is, it must be blockNum >= epoch.
func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}
