### Title
`ThresholdKeys::read` accepts attacker-controlled verification shares without checking consistency with the secret share or rejecting the identity point, yielding a `group_key` corresponding to no valid shared key - ([File: crypto/dkg/src/lib.rs])

### Summary
The bug class in the external report is "missing precondition checks on a function argument causes an invalid input to produce a valid-looking output corresponding to nothing." In Serai, `ThresholdKeys::read` deserializes `t`, `n`, `i`, the secret share, and all `verification_shares` from untrusted bytes, then computes `group_key` purely from the supplied verification shares. It never checks that the supplied `secret_share` is consistent with `verification_shares[i]`, and it uses `Ciphersuite::read_G` — which, unlike `frost::curve::Curve::read_G`, does not reject the identity point.

### Finding Description
- `ThresholdKeys::read` reads an arbitrary point for each of the `n` verification shares via `<C as Ciphersuite>::read_G(reader)?` and passes them straight into `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:620-631`).
- `ThresholdKeys::new` only checks the *count* of shares and that each `Participant` index is `<= n` (`crypto/dkg/src/lib.rs:355-365`). It then computes `group_key = sum(verification_shares[i] * interpolation_factor(i, 1..=t))` (`crypto/dkg/src/lib.rs:376-378`) with no check that `verification_shares[params.i()] == generator() * secret_share`.
- `Ciphersuite::read_G` rejects non-canonical encodings but accepts the identity point (`crypto/ciphersuite/src/lib.rs:91-100`); only the FROST-specific `Curve::read_G` wrapper rejects identity (`crypto/frost/src/curve/mod.rs:125-131`), and `ThresholdKeys::read` uses the former.
- As a result, an unprivileged party supplying bytes to `ThresholdKeys::read` can make `group_key` be any point they choose: e.g., set `verification_shares[1] = G * x_known` and `verification_shares[2..=t] = identity` (all accepted), making `group_key` a key whose discrete log the attacker knows, or make `group_key` a junk point for which no private key exists while the embedded `secret_share` is unrelated.

### Impact Explanation
`ThresholdKeys` is the root object for all FROST signing: `view()` interpolates `secret_share` against `verification_shares` (`crypto/dkg/src/lib.rs:494-521`), and `group_key()` is the address/verification key everything else derives from. Two concrete impacts:

1. If the corrupted `group_key` is used to derive a deposit address (e.g., `Scanner::new(key)` / `p2tr_script_buf(key)` in `networks/bitcoin/src/wallet/mod.rs:80-86,162-165`), funds sent to it are reported received yet are unspendable, because the declared `secret_share`/`verification_shares` do not interpolate to a key under `group_key`.
2. If `group_key` is attacker-chosen with known discrete log (identity shares + one chosen share), the attacker can unilaterally forge signatures that verify under `keys.group_key()`.

This is exactly the reported failure mode — no precondition check lets invalid input produce a key/address "corresponding to no public key" (or worse, to an attacker key) — reached via the explicitly in-scope `ThresholdKeys::read` untrusted-bytes path.

### Likelihood Explanation
Anywhere serialized `ThresholdKeys` cross a trust boundary (disk state, inter-process messages, coordinator-supplied parameters), malformed bytes are reachable. The library's own `write`/`read` round-trip is used for persistence, so a corrupted or maliciously crafted blob is silently accepted; `ThresholdKeys::new`'s only validation is structural (counts, index bounds), not cryptographic consistency. The fix is cheap (one scalar multiplication + comparison, plus an identity rejection), so the missing check is plausibly hit in any integration that doesn't re-verify the key itself.

### Recommendation
In `ThresholdKeys::new` (or in `ThresholdKeys::read`), add precondition checks:
- Reject identity verification shares (or use an identity-rejecting reader).
- Verify `verification_shares[params.i()] == C::generator() * secret_share` and error otherwise, so a deserialized key can never claim a `group_key` inconsistent with the embedded secret share.

### Proof of Concept
```rust
// Attacker crafts bytes for ThresholdKeys::<C>::read:
//   id_len/id = C::ID, t = 1, n = 2, i = 1, interpolation = Lagrange (0x01)
//   secret_share = arbitrary s (e.g., s = 1)
//   verification_shares[1] = G * x_attacker   (attacker knows x_attacker)
//   verification_shares[2] = identity         (accepted: read_G doesn't reject identity)
let keys = ThresholdKeys::<C>::read(&mut crafted_bytes.as_slice()).unwrap();
// group_key = verification_shares[1] * lagrange(1, {1}) = G * x_attacker
// Attacker now knows the discrete log of keys.group_key() and can forge signatures
// under it, while keys.secret_share (s) is unrelated — no error is ever raised.
```
