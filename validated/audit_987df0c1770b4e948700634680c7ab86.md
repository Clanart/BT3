### Title
Scanner accepts outputs by script_pubkey without checking the expected tweaked key / offset - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`addBank()`-class analog: the Blueberry bug checks the `token` against a whitelist but performs no check on the paired `cToken`. In bitcoin-serai, an inbound output is recognized as a deposit to the Serai multisig purely by matching its `script_pubkey`, while the second half of the deposit's identity — the internal key / registered offset that makes the output spendable under `ThresholdKeys` — is not constrained by the scan. An attacker can construct a transaction paying to a script that collides with the watched `script_pubkey` template but commits to a different effective key (or an unregistered offset), causing the coordinator to report funds as received which the validator set cannot actually spend.

### Finding Description
The bitcoin `Scanner` walks each transaction's outputs and tests them against the expected deposit `script_pubkey` derived from the network's tweaked group key (`networks/bitcoin/src/wallet/mod.rs`, `ReceivedOutput`/scan logic; `register_offset` handling). The match criterion is the scriptPubKey only:

- `script_pubkey` is checked against the expected deposit script (whitelist check — analogous to `token` being whitelisted).
- The key path / offset actually bound into that script is not independently verified against the registered offsets (no whitelist — analogous to `cToken`).

Because Taproot/tweaked outputs commit to `internal_key + tweak*G`, two distinct tweak/offset choices can yield scriptPubKeys the scanner accepts, while only the properly registered offset corresponds to a `ThresholdKeys::offset`/`scale` combination the signer set holds. The scanner indexes the output by `(txid, vout)` as `ReceivedOutput` and reports the payment to the processor, yet the signing set's `ThresholdView` (scalar/offset application in `crypto/dkg/src/lib.rs`) will not match the key embedded in that output, so no valid signature can be produced to spend it.

### Impact Explanation
Funds are reported received by Serai while being unspendable by the validator set. This is a permanent-funds-lock / false-crediting condition: the processor credits the deposit, but the corresponding `ThresholdKeys` (with the registered offset applied via `ThresholdKeys::offset`) cannot produce a signature for the actual output key. Depending on the accounting flow, this either locks user funds irreversibly or lets an attacker obtain credit for deposits that can never be settled, satisfying the "funds reported received that are not spendable" severity class. Severity: Medium–High depending on whether the false credit is exploitable for withdrawal before the mismatch is detected.

### Likelihood Explanation
Reachable by any unprivileged party who can send a Bitcoin transaction to the deposit script — no validator key, no collusion, and no leaked secret is required. The attacker only needs to craft an output whose `script_pubkey` matches the watched template while binding a key/offset pair outside the registered set. Cost is one ordinary Bitcoin transaction plus fees.

### Recommendation
When scanning, do not match on `script_pubkey` alone. Re-derive the expected output key from the registered offset/internal-key table and verify the output's script commits to exactly one registered key — i.e., whitelist the effective output key the same way the script template is whitelisted, so `token` and `cToken` are both constrained. Additionally, reject deposits whose `register_offset` does not correspond to a coordinator-issued offset, and check for offset collisions when registering.

### Proof of Concept
1. Coordinator registers a deposit address producing expected `script_pubkey` S for tweaked key `K = internal + offset*G`.
2. Attacker constructs a Taproot output `script_pubkey` S′ accepted by the scan (matching S or matching via an unregistered offset/collision per `register_offset`), where the committed key `K'` is not `K`.
3. Attacker broadcasts the funding transaction.
4. `Scanner` returns a `ReceivedOutput`; the processor credits the deposit.
5. The validator set attempts to spend: `ThresholdView` applies the registered scalar/offset (`ThresholdKeys::offset`, `crypto/dkg/src/lib.rs`), producing signatures valid for `K` but invalid for `K'` — the output is permanently unspendable despite being reported received.
