## Title
Incorrect time-decay formula in `getRewardablePercentWAD` causes indefinite forfeiture of already-unlocked vlMGP rewards - ([File: VLMGP.sol])

### Summary
`VLMGP.getRewardablePercentWAD()` uses `block.timestamp - startTime` (time since the cooldown *started*) as the decay denominator for slots that have already finished cooling down, instead of anchoring the ratio to the moment the slot became unlocked. As a result, the "rewardable" percentage for a fully-unlocked-but-unclaimed cooldown slot keeps shrinking the longer a user waits before calling `unlock()`, even though the tokens are already fully vested. This directly and negatively affects the `forfeitAmount` computed by `vlMGPBaseRewarder._calExpireForfeit`, permanently redirecting a growing share of an ordinary user's already-earned MGP rewards into the pool's forfeit bucket.

### Finding Description
`getRewardablePercentWAD` computes, per user, what fraction of their vlMGP position should be treated as "still locked" (rewardable) vs. "unlocking/forfeitable": [1](#0-0) 

For a cooldown slot that has *not yet* reached `endTime`, the user gets full (100%) credit:
```
percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
```
But once `block.timestamp > endTime` (i.e., the slot is fully vested and ready to be withdrawn via `unlock()`), the code instead applies a decaying weight:
```
percent += userUnlocking[i].amountInCoolDown * 1e18 * (endTime - startTime)
    / userTotalVlmgp / (timeNow - startTime);
```
At the exact moment `endTime` is reached, `(endTime-startTime)/(timeNow-startTime) == 1`, matching the pre-expiry 100% weighting continuously. However, as `timeNow` keeps advancing past `endTime` (i.e., the user simply hasn't called `unlock()` yet), the denominator `(timeNow - startTime)` keeps growing indefinitely while the numerator `(endTime - startTime)` stays fixed, so the weight monotonically decays toward zero. This means tokens that are already fully unlocked/vested are treated as increasingly *less* rewardable the longer the withdrawal transaction is delayed — the opposite of the intended semantics (fully unlocked tokens should retain their maximum weight, not decay further).

This percentage is consumed by `vlMGPBaseRewarder._calExpireForfeit`, which is invoked on every reward claim/harvest path (`getReward`, `getRewards`, `queueMGP`, `_sendReward`): [2](#0-1) [3](#0-2) 

`rewardableAmount = _amount * rewardablePercentWAD / 1e18` shrinks as `rewardablePercentWAD` shrinks, so `forfeitAmount = _amount - rewardableAmount` grows accordingly and is permanently diverted via `_queueNewRewardsWithoutTransfer` to be redistributed among other stakers — it is not returned to the original user.

### Impact Explanation
Any ordinary vlMGP holder who starts an unlock (`startUnlock`), lets the cooldown period complete, and does not immediately call `unlock()` (a completely normal and expected user flow — no requirement exists to call `unlock()` the instant `endTime` passes) will see their `getRewardablePercentWAD` continue to decay the longer they wait. Any MGP reward harvested from `vlMGPBaseRewarder` (including reward flowing through `MasterMagpie._sendMGPForVlMGPPool` → `queueMGP`) during that window is forfeited at an ever-increasing rate that has no relation to the user's actual locked/unlocked status — this is a direct, permanent loss of the user's own earned/unclaimed yield to other participants, without any way for the user to recover it once forfeited.

### Likelihood Explanation
This requires no privileged action and is triggered purely by normal user behavior (waiting more than a few moments after cooldown ends before calling `unlock()`, and separately harvesting/claiming MGP rewards in between). This is a very common real-world pattern (batching transactions, gas optimization, or simple delay), making the bug highly likely to trigger in practice for active vlMGP participants.

### Recommendation
Anchor the decay ratio to the slot's unlock completion rather than its start time, or simply give fully-unlocked slots a fixed maximum weight (matching the "still in cooldown" branch) instead of a formula whose denominator grows unboundedly with wall-clock time. E.g., cap the ratio at 100% and only decay (if intended at all) relative to time elapsed since `endTime`, not since `startTime`.

### Proof of Concept
1. User locks MGP, then calls `startUnlock(100e18)` at `T0`; `coolDownInSecs = 7 days`, so `endTime = T0 + 7 days`.
2. At `T0 + 7 days` (just after `endTime`), `getRewardablePercentWAD` correctly returns 100% for that slot (`(7d)/(7d) = 1`).
3. User does not call `unlock()` immediately (e.g., waits `T0 + 14 days` before harvesting other MGP rewards through `MasterMagpie`/`vlMGPBaseRewarder`).
4. At `T0 + 14 days`, the same slot's weight is now `(7d)/(14d) = 50%`, even though the 100 tokens have been fully vested/unlocked since `T0+7d` and nothing about the user's position has changed.
5. Any MGP reward harvested at this point via `vlMGPBaseRewarder._calExpireForfeit` uses this deflated 50% rewardable percent, forfeiting roughly half of what should be a fully rewardable claim, with the forfeited MGP permanently redistributed to other stakers via `_queueNewRewardsWithoutTransfer` — the affected user can never reclaim it.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
