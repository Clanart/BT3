### Title
Hardcoded `DUST` threshold in `SignableTransaction::new` is output-type agnostic, permitting payments whose scriptPubKey's real dust threshold exceeds 546 sats to be signed into transactions Bitcoin Core rejects as non-standard — ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Annirich/serai--021))

### Summary
`SignableTransaction::new` validates every requested payment against a single hardcoded constant `DUST: u64 = 546` (send.rs:32, send.rs:165-169). Bitcoin's actual dust rule is per-output: `dust = (serialized_output_size + input_spend_size) * dustRelayFee`, which yields ~330 sats for P2TR but grows without bound for large `script_pubkey`s. A payment whose amount passes the 546-sat check yet is below the true dust threshold for its (user-supplied) `script_pubkey` produces a transaction Bitcoin Core will not relay — yet the FROST threshold network will still sign it.

### Finding Description
`DUST` is declared once and applied uniformly:

```rust
// networks/bitcoin/src/wallet/send.rs:32
pub const DUST: u64 = 546;
```

```rust
// networks/bitcoin/src/wallet/send.rs:165-169
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

The code comment (lines 29-31) acknowledges the constant is only an approximation in the *downward* direction (SegWit outputs have a lower dust floor) and accepts that divergence as "marginal". The *upward* direction is unhandled: the dust threshold for an output is `GetDustThreshold = nSize * dustRelayFee` where `nSize` includes `script_pubkey` length plus the cost of the input that would spend it. For a P2TR output it is ~330 sats; for an output with a large `script_pubkey` (e.g., a multi-hundred-byte non-standard script, or a bare multisig/legacy script the user requests payment to), the threshold can exceed 546 — in fact it scales linearly with script size, so any threshold is achievable.

There is no corresponding per-output calculation anywhere; the only other uses of `DUST` are the change-output check at line 229 (`value >= DUST`, where the change script is the wallet's own P2TR and the constant is correct). The payment check is the reachable flaw.

Once the check passes, the payment is committed verbatim into `tx_outs` (lines 187-191) and the transaction is eventually hashed per-input with `Prevouts::All` and signed by the threshold key (lines 373-397). An unprivileged party who can cause the processor to build a withdrawal/payment to an arbitrary `script_pubkey` (e.g., a bridging-out instruction with a user-chosen destination script) controls both the script bytes and the amount.

### Impact Explanation
A transaction containing a dust output is non-standard under Bitcoin Core's `IsStandardTx` (dust check in policy.cpp) and will be rejected by the default mempool. Serai's signing pipeline has no post-signing validity re-check — `SignableTransaction::new` performs all policy validation up front. Result: the threshold multisig produces and signs a transaction committing UTXOs (`Prevouts::All` binds all inputs' values and scripts, lines 373-390) that cannot be broadcast. The selected inputs are consumed by the signing attempt's intent, and any re-sign requires the coordinator to recognize and rebuild — i.e., funds are spent into an unspendable/unrelayable transaction from the network's perspective. This maps directly to the accepted class "funds reported sent that are not spendable".

Additionally, in the benign direction, the same hardcoding wrongly rejects *valid* payments: a 400-sat payment to a P2TR output is standard (dust ≈ 330) yet returns `DustPayment`, a reachability-only DoS on withdrawals — the same two-sided failure mode as the source report's `MINIMUM_AMOUNT`.

### Likelihood Explanation
Low-to-moderate. Exploitation requires the processor path to accept user-chosen `script_pubkey`s for payments, which holds for outbound transfer instructions. It requires no collusion, no privileged access, and no malformed encoding — just a payment whose destination script pushes its dust floor above 546 sats while the requested amount sits in the gap. Each attempt only burns the fee of the re-attempted transaction; the impact is per-transaction liveness/funds-locking rather than key compromise, keeping this at Medium.

### Recommendation
Replace the single constant with a per-output dust computation mirroring Bitcoin Core's `GetDustThreshold`: `dust = (serialized TxOut size + estimated spend-input size) * dustRelayFee`, where the spend-input size for non-SegWit scripts is 148+ bytes and for SegWit uses the discounted witness size. Apply it to each payment's actual `ScriptBuf`, and to the change output using the wallet's own script. Alternatively, restrict payable scripts to known templates (P2TR/P2WPKH/P2PKH) with their exact thresholds instead of a blanket 546.

### Proof of Concept
1. An unprivileged user submits an outbound instruction specifying a destination `script_pubkey` of ~500 bytes of arbitrary opcodes (a valid `ScriptBuf`) and amount `600` sats.
2. `SignableTransaction::new` is invoked; `600 >= DUST` so `DustPayment` is not raised (line 166-168). The TxOut `{ value: 600, script_pubkey: <500 bytes> }` is pushed to `tx_outs` (lines 188-191).
3. Dust for that output per Core ≈ `(8 + 1 + 500 + ~148) * 3 ≈ 1971` sats ≫ 600 → the transaction contains a dust output and is non-standard.
4. `multisig()`/`preprocess()`/`sign()` proceed normally; `taproot_key_spend_signature_hash` commits to all prevouts and outputs (lines 373-390) and the threshold group signs it.
5. `complete()` returns a fully witnessed `Transaction` (lines 413-428) that every default Bitcoin node rejects with `-26: dust` — the multisig's inputs are committed to an unbroadcastable spend, producing a signed output the network cannot use. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
