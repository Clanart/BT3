**Reasoning summary:**

The equality the question claims is broken is: `payout_tx.output[0].script_pubkey/value == out_script_pubkey/out_amount originally authorized by the withdrawer's SinglePlusAnyoneCanPay signature`.

Tracing the code:

1. `create_payout_txhandler` builds the payout tx with the withdrawal UTXO as a **key-spend** input (`SpendPath::KeySpend`), with `output_txout` at index 0 [1](#0-0) .
2. The withdrawer's signature is verified/created against a sighash computed by `calculate_pubkey_spend_sighash` → `taproot_key_spend_signature_hash(txin_index, prevouts, SinglePlusAnyoneCanPay)` [2](#0-1) .
3. Per BIP-341/`SighashType::Single`, this sighash (ANYONECANPAY variant only skips *input* commitments; the `Single` component still commits to the output at the corresponding index) cryptographically **binds the signature to the exact `script_pubkey` and `value` of output[0]** — i.e. exactly `out_script_pubkey`/`out_amount` — as generalized in `taproot_encode_signing_data_to_with_annex_digest` (SIGHASH_SINGLE commits per-output, only ANYONECANPAY relaxes input commitments) [3](#0-2) .
4. `Operator::withdraw` verifies this exact binding via `SECP.verify_schnorr` before ever funding/broadcasting [4](#0-3) .

Because the signature is bound to output[0]'s script_pubkey/value at the Bitcoin-consensus level (BIP-341 taproot key-spend verification, enforced by every full node, not just Clementine's own check), an attacker who reuses a captured signature but substitutes a different `output_txout` produces a transaction with an **invalid witness** — it cannot be confirmed by the Bitcoin network at all, let alone reach `update_finalized_payouts`. Getting such a mismatched tx "confirmed" would require forging a new valid Schnorr signature for the new output, which requires the withdrawer's private key — explicitly out-of-scope key compromise, not something achievable by an unprivileged attacker holding only a leaked signature for a *different* output.

Therefore `update_finalized_payouts`'s failure to re-examine `output[0]` [5](#0-4)  is not an exploitable gap: any transaction that reaches that code path and successfully confirms on Bitcoin is guaranteed by consensus-level Schnorr/Taproot verification to carry the withdrawer-authorized output at index 0. The claimed equality holds both before and after under the attacker model given (no key compromise).

    pub fn calculate_pubkey_spend_sighash(
        &self,
        txin_index: usize,
        sighash_type: TapSighashType,
    ) -> Result<TapSighash, BridgeError> {
        let prevouts_vec: Vec<&TxOut> = self
            .txins
            .iter()
            .map(|s| s.get_spendable().get_prevout())
            .collect();
        let mut sighash_cache: SighashCache<&bitcoin::Transaction> =
            SighashCache::new(&self.cached_tx);
        let prevouts = match sighash_type {
            TapSighashType::SinglePlusAnyoneCanPay
            | TapSighashType::AllPlusAnyoneCanPay
            | TapSighashType::NonePlusAnyoneCanPay => {
                bitcoin::sighash::Prevouts::One(txin_index, prevouts_vec[txin_index])
            }
            _ => bitcoin::sighash::Prevouts::All(&prevouts_vec),
        };

        let sig_hash = sighash_cache
            .taproot_key_spend_signature_hash(txin_index, &prevouts, sighash_type)
            .wrap_err("Failed to calculate taproot sighash for key spend")?;
