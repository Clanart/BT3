### Title
Uncaught panic on HashMap indexing / re-registration assert in PedPoP encryption layer allows unauthenticated crash of DKG participants - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The json-smart advisory (CWE-754) describes a crash class where an exceptional condition raised on attacker-controlled input is never checked or caught. In Rust, the analog is an unhandled panic (`assert!`, `HashMap` `[]` indexing, `unwrap`) reached from untrusted protocol input. `crypto/dkg/pedpop/src/encryption.rs` contains two such reachable panics: a duplicate-registration `assert!` in `Decryption::register` and an unchecked `self.enc_keys[&participant]` / `self.enc_keys[&decryptor]` indexing panic in `Encryption::encrypt` and `Decryption::decrypt_with_proof`. Neither condition is validated against the attacker-controlled `Participant` index before indexing.

### Finding Description
`Decryption::register` panics when a participant submits a second `EncryptionKeyMessage`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:356-358
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
```

More critically, both `Encryption::encrypt` and `Decryption::decrypt_with_proof` index `self.enc_keys` with a `Participant` value using `HashMap`'s `Index` impl, which panics on a missing key:

```rust
// crypto/dkg/pedpop/src/encryption.rs:388
&[self.enc_keys[&decryptor], *proof.key],
```

```rust
// crypto/dkg/pedpop/src/encryption.rs:466
encrypt(rng, self.context, self.i, self.decryption.enc_keys[&participant], msg)
```

`decrypt_with_proof` is invoked on the blame path, where the `from`/`decryptor` indexes derive from an accuser's `InvalidDkgShare`-style claim — attacker-controlled values. `EncryptedMessage::read` (line 171), `EncryptionKeyMessage::read` (line 57), `SchnorrSignature::read`, and `EncryptionKeyProof::read` (line 267) all deserialize arbitrary, structurally-valid messages for any participant index; nothing in this module enforces that `decryptor`/`participant` corresponds to a registered key before the `[]` indexing is evaluated. The result is a `io::Result`-bypassing panic: exactly the "exception thrown but not caught" shape of CVE-2021-27568.

### Impact Explanation
An honest PedPoP participant node can be crashed (panic → abort of the DKG/signing process) by an attacker-controlled message flow: a double registration, or a blame/proof resolution referencing a `decryptor` index that never registered an encryption key. In Rust this is a full process abort (or at minimum a thread panic propagating out of the DKG state machine), denying availability of the threshold-key session. This matches the advisory's impact (uncaught `NumberFormatException` crashing programs using the library).

### Likelihood Explanation
The panic sites are reachable only through the DKG message-handling paths, and reachability depends on the caller (`pedpop`'s protocol logic / coordinator) passing through an attacker-chosen `Participant` index to `register`, `encrypt`, or `decrypt_with_proof` without prior membership checks. A participant who withholds or duplicates their `EncryptionKeyMessage`, or an accuser whose blame proof names an unregistered `decryptor`, are the natural triggers. I was unable to fully trace `crypto/dkg/pedpop/src/lib.rs`'s callers to confirm every guard, so the crash is probable rather than proven end-to-end — hence Medium rather than High.

### Recommendation
Replace panicking accesses with checked lookups returning `Err`:

- In `Decryption::register`, return an error instead of `assert!` on duplicate registration.
- In `decrypt_with_proof` (line 388) and `encrypt` (line 466), use `self.enc_keys.get(&participant).ok_or(...)` / `?` and surface a `DecryptionError`/`io::Error` for unknown participants.
- Add a validation step that rejects `EncryptedMessage`/blame inputs whose participant index was never registered before proof verification runs.

### Proof of Concept
```rust
// Conceptual: any flow that reaches decrypt_with_proof with an unregistered
// decryptor index panics on `self.enc_keys[&decryptor]`.

let mut dec = Decryption::<Secp256k1>::new(context);
// Only participant 1 registers an encryption key.
dec.register(Participant::new(1).unwrap(), key_msg_from_1);

// An accuser submits a blame claim whose decryptor index is 2 (never registered),
// with any structurally valid EncryptedMessage + EncryptionKeyProof whose pop/dleq
// are made to pass for the accuser's own key.
// When the blame path calls:
dec.decrypt_with_proof(accuser, Participant::new(2).unwrap(), msg, Some(proof));
// -> thread panics at encryption.rs:388: `self.enc_keys[&decryptor]`
//    (HashMap Index impl: "no entry found for key"), aborting the DKG.
```

Similarly, calling `register` twice for the same `Participant` hits the `assert!` at line 356 and panics without any `Err` path.
