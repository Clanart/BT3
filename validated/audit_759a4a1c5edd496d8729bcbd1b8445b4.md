### Title
`SignableTransaction` omits the OP_RETURN data output (and overstates change) when computing weight/fee, producing transactions whose effective fee rate falls below the requested and potentially below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends a caller-supplied OP_RETURN output to `tx_outs` (lines 194-202) but then calculates transaction weight and `needed_fee` using the `payments` slice alone (`calculate_weight_vbytes(tx_ins.len(), payments, None)`, line 204). The byte size contributed by the data output — up to 80 bytes of data plus output overhead, per the `data.len() > 80` check at line 171 — is never counted, so `needed_fee` is systematically underestimated whenever `data` is `Some`. The same wrong `payments`-only estimate feeds the change calculation at line 226, so the change output absorbs value that should have funded the fee for the data output.

### Finding Description
The constructor builds `tx_outs` from `payments` and then pushes the OP_RETURN output:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds a template transaction whose `output` list is derived only from `payments` (lines 85-93) plus optional `change`. The OP_RETURN output is therefore invisible to the weight/vbytes calculation. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` is smaller than the fee required for the actual transaction, which includes the extra ~90-byte output.
2. In the change branch, `fee_with_change` is likewise computed without the data output, so `change = input_sat - payment_sat - fee_with_change` is too large — the change output steals sats that should have paid for the OP_RETURN's size.
3. The resulting signed transaction has `actual_fee / actual_vbytes < fee_per_vbyte`. If `fee_per_vbyte` was chosen at or near the minimum relay threshold, the undercounted ~20+ vbytes can push the effective rate below `DEFAULT_MIN_RELAY_TX_FEE`, making the transaction non-standard/unrelayable despite the `TooLowFee` guard at line 211 passing. The weight check at line 241 (`MAX_STANDARD_TX_WEIGHT`) is also computed without the data output, so a borderline-size transaction can exceed the standard weight limit while passing the check.

The test suite only exercises `data` through `TransactionError` checks (`Some(vec![0; 80])` is asserted `is_ok` but never signed or broadcast), so this is not covered.

### Impact Explanation
Any Bitcoin transaction constructed with `data: Some(_)` pays a lower fee rate than the caller explicitly requested, and overpays the change address by `fee_per_vbyte * vbytes(OP_RETURN)`. For fee rates near the relay minimum — exactly the regime guarded by the `TooLowFee` check — the real fee rate can drop below the minimum relay fee, causing the signed transaction to be rejected by peer mempools: funds committed by the threshold signature cannot confirm until the transaction is abandoned and re-signed (a liveness/availability failure for the signing round). In the worst case a near-max-size transaction silently exceeds `MAX_STANDARD_TX_WEIGHT` and is permanently unrelayable. Impact is limited to fee miscalculation and potential transaction relay failure; it does not leak key material. Medium severity.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some` — the miscalculation is unconditional, not attacker-dependent. Exploitability as a *security* issue is moderate: `data` is integrator-supplied rather than controlled by an unprivileged external party, and the concrete harm (unrelayable transaction) requires the requested fee rate to be close to the minimum relay fee or the transaction to be near the standard weight limit. In the common case the result is merely a ~20-30% fee-rate error on small transactions plus inflated change.

### Recommendation
Include the OP_RETURN output in the weight estimate: either push it into the `payments` slice used for `calculate_weight_vbytes` (with a zero amount, since the value field is fixed-size), or compute weight directly from the assembled `tx_outs`. Apply the same fix to the change branch so `fee_with_change` reflects the true output set. Add a test asserting `tx.needed_fee() == tx.vsize() * fee_per_vbyte` for a `SignableTransaction` constructed with `data`.

### Proof of Concept
```rust
// Construct a transaction with data, then compare the implied vs actual fee rate.
let tx = SignableTransaction::new(
  vec![output],
  &payments,
  Some(change_addr),
  Some(vec![0u8; 80]),   // permitted by the <=80 check
  fee_per_vbyte,
).unwrap();

let actual_vbytes = tx.transaction().vsize() as u64; // includes the OP_RETURN output
// needed_fee only paid for vbytes *without* the ~90-byte OP_RETURN output:
assert!(tx.needed_fee() < actual_vbytes * fee_per_vbyte);
// With change set, the actual paid fee equals needed_fee, so:
//   actual_fee_rate = needed_fee / actual_vbytes < fee_per_vbyte
// If fee_per_vbyte * actual_vbytes < DEFAULT_MIN_RELAY_TX_FEE * actual_vbytes / 1000
// the signed TX is below minimum relay fee despite passing the TooLowFee check.
```
