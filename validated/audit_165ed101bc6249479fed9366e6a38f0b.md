### Title
`SchnorrAggregate::verify` returns `true` for an aggregate signature with zero signers - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the CMS `verifySignatures` zero-signer flaw, `SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs` accepts a forged aggregate signature over an empty signer set. When `self.Rs` and `keys_and_challenges` are both empty, the only verification pair remaining is `(-s, G)`, so any caller passing an empty signer list will accept the attacker-supplied signature `Rs = []`, `s = 0` as valid — no party ever signed anything. [1](#0-0) 

### Finding Description
`SchnorrAggregate::verify` performs the following:

1. It only checks that `self.Rs.len() == keys_and_challenges.len()`. Two empty slices satisfy this. [2](#0-1) 
2. It transcripts only the challenges from `keys_and_challenges`; with an empty set, no challenges are appended. [3](#0-2) 
3. The `pairs` loop over `keys_and_challenges` pushes nothing, leaving only the constant pair `(-self.s, C::generator())`. [4](#0-3) 
4. `multiexp_vartime(&pairs).is_identity()` therefore reduces to `s * G == 0`, i.e. `s == 0`. [5](#0-4) 

Additionally, `SchnorrAggregate::read` allows an attacker to deserialize exactly this shape: a length prefix of `0` followed by a zero scalar `s`. [6](#0-5)  There is no check anywhere that at least one signer participated, mirroring the upstream bug where `SignedData` with an empty `SignerInfos` set verified successfully. The test suite even codifies that an empty `BatchVerifier` passes (`multiexp` over zero pairs is identity), confirming the same vacuous-success pattern exists as an assumption in the codebase. [7](#0-6) 

### Impact Explanation
The verifier's formula is incorrect: it accepts `Σ zᵢ·Rᵢ + Σ zᵢ·cᵢ·Pᵢ − s·G = 0` degenerating to `s·G = 0`, which any unprivileged party satisfies with `s = 0`. Any downstream consumer that derives authorization, quorum, or "these validators signed this message" semantics from a successful `SchnorrAggregate::verify` call — without separately enforcing a non-empty signer set — will treat a message as signed by a signer set that does not exist. This is a forged signature on arbitrary `dst`/message context, produced without knowledge of any private key.

### Likelihood Explanation
Exploitation requires a caller to invoke `verify` with an empty `keys_and_challenges` slice, which in turn requires the caller to accept an empty signer list from attacker-influenced input. `verify` itself imposes no minimum signer bound, and `read` produces empty `Rs` from 4 zero bytes, so the vulnerable configuration is fully attacker-reachable wherever signer lists are deserialized or counted from untrusted data rather than a fixed validator set.

### Recommendation
In `SchnorrAggregate::verify`, return `false` early when `keys_and_challenges.is_empty()` (equivalently `self.Rs.is_empty()`), so the vacuous multiexp identity cannot be reached. Defense-in-depth: also reject zero-length `Rs` in `SchnorrAggregate::read`.

### Proof of Concept
```rust
// crypto/schnorr Ed25519 context
let mut bytes = vec![];
bytes.extend_from_slice(&0u32.to_le_bytes());          // len(Rs) = 0
bytes.extend_from_slice(<Ed25519 as Ciphersuite>::F::ZERO.to_repr().as_ref()); // s = 0

let aggregate = SchnorrAggregate::<Ed25519>::read::<&[u8]>(&mut bytes.as_slice()).unwrap();
assert!(aggregate.Rs().is_empty());

// Forged "aggregate signature" verifies over an empty signer set
assert!(aggregate.verify(b"any DST", &[])); // returns true — no one signed
```

```rust
  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
```
