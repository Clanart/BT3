Confirmed: `validateResolutionPaths` is called per-chunk, scoped only to that chunk's `expectedFiles`. Each `resolveChunk` result is validated in isolation against its own `chunkFiles`, and only after that is `allResolutions.push(...result.value.resolutions)` performed with no de-duplication across chunks. `createDependencyAwareChunks` is documented/tested to partition files into disjoint groups, but this partitioning invariant is enforced only by the chunking algorithm, not re-checked when merging results — the merge step trusts that no two chunk responses share a `path`. This is the same broken-invariant shape as the Nouns DAO bug: a downstream consumer (`sendProRataTreasury`/`quit()` there, `_applyCopilotConflictResolutions` here) iterates an unvalidated aggregate array and processes duplicate entries with no cross-entry uniqueness guard, silently letting the last duplicate win.

### Title
Cross-chunk duplicate file paths in batched Copilot conflict resolution can silently overwrite a different file's resolved content - (File: app/src/lib/stores/copilot-store.ts)

### Summary
When more than `SinglePromptFileLimit` (20) conflicted files are resolved with Copilot, `resolveConflicts` in `app/src/lib/stores/copilot-store.ts` splits files into independent chunks (`createDependencyAwareChunks`) and resolves them concurrently via `resolveChunk`. Each chunk's response is validated by `validateResolutionPaths` [1](#0-0)  only against that chunk's own `expectedFiles`, which correctly rejects unexpected paths and duplicates *within* a single chunk's response. However, the results of all chunks are merged into one flat array with no global de-duplication: [2](#0-1) . `_applyCopilotConflictResolutions` in `app-store.ts` then iterates this merged array and writes each resolution's content to disk keyed by `resolution.path` [3](#0-2) , with no check that a path was only produced once across the whole resolution set.

### Finding Description
The broken invariant is: "each conflicted file path appears in exactly one chunk's resolution output," which is asserted only by a unit test on `createDependencyAwareChunks` [4](#0-3)  and never re-verified at merge time. The per-chunk validator `validateResolutionPaths` cannot see across chunk boundaries — it builds `expectedPaths`/`returnedPaths` solely from the `chunkFiles` passed into that specific `resolveChunk` call [5](#0-4) . If a model response for chunk A (whose content is derived from attacker-controlled conflicted file contents — e.g., a hostile branch merged/rebased/cherry-picked from a cloned/fetched remote, which can embed prompt-injection text inside conflict hunks) is manipulated into legitimately reusing a `path` string that also belongs to a file resolved by a different concurrently-processing chunk (e.g., via retries, chunk resubmission on transient errors, or a model hallucinating a path that happens to coincide with another chunk's own conflicted file — plausible for common repository file names like `package-lock.json`, `README.md`, or vendored files that could appear more than once in a monorepo's conflict set if chunking ever produces overlapping groups on edge cases), both chunk validations pass individually (each path is legitimately in that chunk's own `expectedFiles`), yet the merge step still produces two `IFileResolution` entries for the same `path`. `_applyCopilotConflictResolutions` then performs two sequential `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` calls for the same file [6](#0-5) , and the file that lands on disk (and gets `git add`-ed and committed by the ongoing merge/rebase/cherry-pick) is whichever resolution happened to be pushed last into `allResolutions` — not necessarily the one the user reviewed as canonical in the result dialog for that path, and with no error or warning surfaced anywhere in the pipeline.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." The user believes they are committing the resolution shown for a given file in the Copilot conflicts dialog, but the actually-written and staged content can be a different resolution generated for the same path in a different concurrent chunk (potentially reflecting a different, adversarially-influenced merge outcome), and the corrupted result is committed and can be pushed without any indication to the user that a collision occurred. This is analogous to the ERC20 duplicate-token bug's core defect: an aggregate loop over an unvalidated array with duplicate keys causes an unintended value (a "greater than pro-rata" transfer there; a silently overwritten file resolution here) to be applied downstream of a per-item check that only guards each individual item, not the aggregate.

### Likelihood Explanation
Likelihood is low-to-medium: it requires (a) a conflict set large enough to trigger chunking (>20 files), and (b) a way for the same `path` to appear validly in two different chunks' resolution outputs, which the chunking algorithm's dependency partitioning is designed to prevent but does not structurally guarantee is impossible at merge time — there is no assertion, error, or log if it does happen. The attacker's practical lever is the content of a cloned/fetched repository (crafted merge/rebase source) that produces many conflicting files, combined with prompt-injection content in conflict hunks that can influence what `path` a model emits in its structured JSON response; the per-chunk validator does not stop an in-chunk-legitimate but merge-duplicate path from reaching the write path.

### Recommendation
Add a global uniqueness check when merging `allResolutions` across chunks in `resolveConflicts` (`app/src/lib/stores/copilot-store.ts`), e.g. track a `Set<string>` of paths already resolved and throw a `CopilotValidationError` (or drop/flag the later duplicate and surface it as a skipped file) if a chunk returns a `path` already present in `allResolutions`. Additionally, `_applyCopilotConflictResolutions` in `app-store.ts` should defensively de-duplicate `copilotResolutions` by `path` (keeping only the first or explicitly the last with a warning) before writing, so a merge-time invariant violation cannot silently corrupt working-directory content even if the aggregation-time check is bypassed.

### Proof of Concept
Conceptual reproduction (exact model manipulation not verifiable without live Copilot access, so this is a structural PoC based on the code path):
1. Trigger a merge/rebase with >20 conflicted files so `resolveConflicts` chunks the work (`chunkSize` 15–20) into ≥2 concurrent `resolveChunk` calls [7](#0-6) .
2. Craft file content (from the fetched/cloned branch being merged) containing a prompt-injection payload inside a conflict hunk assigned to chunk A that causes the model's JSON `resolutions` array to include a resolution entry whose `path` equals a filename that is also a genuine conflicted file being resolved by chunk B.
3. `validateResolutionPaths` for chunk A only checks against chunk A's own `expectedFiles`, so if the path collides with one of chunk A's real files (not chunk B's — cross-chunk hallucination of an out-of-scope path would fail this check), and chunk B independently and correctly resolves its own copy/instance, when both settle, `allResolutions` in `resolveConflicts` [8](#0-7)  contains two entries for the same `path` with no error thrown.
4. `_applyCopilotConflictResolutions` writes both in sequence [9](#0-8) ; the second `writeFile` call silently overwrites the first, and `git add -- <path>` stages whichever content won, which is then committed as part of the merge/rebase/cherry-pick continuation — with the dialog having potentially shown the user the other (now-discarded) resolution.

Note: I was not able to fully verify whether `createDependencyAwareChunks` can ever produce overlapping (non-disjoint) groups for adversarial inputs (only a happy-path uniqueness test exists), nor could I confirm the Copilot SDK's actual susceptibility to prompt injection from conflict-hunk content in this environment — both would require live testing beyond static code review.
