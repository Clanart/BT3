## Analysis Result

The `get_root_removal()` loop in `chia/wallet/trading/offer.py` is the strongest reachable analog to the HAProxy zero-copy "send loop" DoS: it is an unbounded `while` loop over attacker-controlled offer data that can be made to spin without making forward progress if the coin-lineage graph in an untrusted offer file contains a cycle among "ephemeral" removals.

### Title
Unbounded loop in `Offer.get_root_removal()` allows a malicious offer file to hang the wallet - ([File: chia/wallet/trading/offer.py])

### Summary
`get_root_removal()` walks up parent links among an offer's removals until it reaches a "non-ephemeral" (root) coin, using `while coin not in non_ephemeral_removals: coin = next(...)`. The membership test for "non-ephemeral" is derived purely from data inside the offer bundle (which coin names appear as a parent of another removal in the same set), not from validated on-chain lineage. A crafted offer whose coin-spend set encodes a cycle (e.g., coin A's `parent_coin_info` equals coin B's `name()` and vice versa) makes every coin in the cycle "ephemeral" by this definition, so no coin in the cycle is ever a member of `non_ephemeral_removals`. [1](#0-0) 

### Finding Description
`non_ephemeral_removals` is computed as the set of removals whose `parent_coin_info` is *not* the name of another removal in the same offer bundle: [2](#0-1) 

If the offer's `coin_spends` list is crafted such that two (or more) coins mutually reference each other as parent (a cycle), neither coin satisfies the "non-ephemeral" condition, yet the initial guard only checks that the coin (or its parent) is present *somewhere* in `all_removal_ids`, not that a root actually exists: [3](#0-2) 

The `while` loop then repeatedly calls `next(c for c in all_removals if c.name() == coin.parent_coin_info)`, walking the cycle forever since the exit condition (`coin in non_ephemeral_removals`) can never become true for any coin in the cycle. This is directly analogous to the HAProxy `h2_send` loop bug class: a loop that is supposed to terminate on reaching a "root"/"end" state but can be driven into a state where that terminating condition is permanently unreachable given attacker-supplied input, causing the process to spin.

### Impact Explanation
This function is reachable purely by having a wallet user load/parse an untrusted offer file received from a counterparty (a normal "offer counterparty" interaction, not requiring any privileged access). `get_root_removal()` is called from `get_primary_coins()` and `get_pending_amounts()`: [4](#0-3) [5](#0-4) 

Both of these are used by wallet/trade-manager code when a user inspects, examines, or attempts to take/cancel an offer. Triggering the infinite loop on the calling thread would hang that wallet operation (and, depending on the calling context, block the asyncio event loop or worker thread), constituting a spend/offer-triggered denial of service consistent with the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Constructing such a cyclic `coin_spends` set requires only crafting a `SpendBundle`/offer file with coin data whose `parent_coin_info` fields point at each other — no real on-chain state, valid puzzle execution, or signature is required to enter this code path, since `get_root_removal`/`get_primary_coins`/`get_pending_amounts` operate purely on the SpendBundle structure. This makes the likelihood of an attacker forging such an offer relatively low-effort, though it requires the victim to load/inspect the specific offer object function paths, and I was not able to fully trace how deeply `respond_to_offer`/CLI flows exercise `get_primary_coins()` vs. `get_pending_amounts()` in this indexed snapshot of `trade_manager.py` (matches were found but full call sites were not retrievable in this pass).

### Recommendation
Validate that the offer's removal graph is acyclic before or during root-removal resolution — e.g., track visited coin names in `get_root_removal()`'s loop and raise a `ValueError`/`ValidationError` if a coin is revisited, or bound the loop by `len(all_removals)` iterations and fail if a root has not been found within that bound.

### Proof of Concept
Construct an `Offer` whose `_bundle.coin_spends` contains two `CoinSpend`s, `cs_a` and `cs_b`, where `cs_a.coin.parent_coin_info == cs_b.coin.name()` and `cs_b.coin.parent_coin_info == cs_a.coin.name()`, and neither coin appears in `additions()`. Calling `offer.get_primary_coins()` (or `offer.get_pending_amounts()`) on this offer will invoke `get_root_removal()` on one of these coins, and the `while coin not in non_ephemeral_removals` loop will never terminate because both `cs_a.coin` and `cs_b.coin` are excluded from `non_ephemeral_removals` by construction, causing the calling thread to hang indefinitely.     # This returns the non-ephemeral removal that is an ancestor of the specified coin
```python
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
