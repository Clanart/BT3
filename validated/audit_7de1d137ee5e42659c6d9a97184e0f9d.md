### Title
Unprivileged users can flood the mempool's bounded `ConflictTxCache`/`PendingTxCache` with fee-free, cost-free retries, evicting other users' legitimate pending transactions - ([File: chia/full_node/pending_tx_cache.py])

### Summary
Chia's mempool relies on `MempoolManager.add_spend_bundle()` to route any spend bundle that fails immediate admission into one of two fixed-capacity FIFO caches — `ConflictTxCache` (max 1000 items) or `PendingTxCache` (max 3000 items) — for later retry, with no fee requirement to enter either cache. [1](#0-0) 
Eviction from both caches is strictly oldest-first (FIFO by insertion order), not fee-based, unlike the main mempool pool which evicts by lowest fee-per-cost. [2](#0-1) [3](#0-2) 

### Finding Description
The fee-sufficiency check in `validate_spend_bundle()` only applies when `self.mempool.at_full_capacity(cost)` is true; it is entirely skipped for the common `MEMPOOL_CONFLICT` (double-spend collision with an existing mempool item) and unmet-height-assertion (`PENDING`) outcomes, both of which are checked *after* the fee gate and route the item straight into the corresponding retry cache regardless of fee. [4](#0-3) [1](#0-0) 

An unprivileged user can repeatedly submit spend bundles that:
- spend a coin (owned by them) which they know will conflict with an existing mempool entry (e.g., resubmitting a slightly modified version of their own already-pending spend with insufficient fee increase), guaranteeing `MEMPOOL_CONFLICT`, or
- carry a not-yet-satisfied `ASSERT_HEIGHT`/timelock condition, guaranteeing a `PENDING` classification.

Neither path ever consumes the underlying coin (the transaction is never actually included), so the same coin can be reused to generate an unlimited stream of essentially free cache entries. Because the caches are bounded purely by count/cost and evict the oldest entry first — not the lowest-value or attacker-owned entry — this stream can repeatedly evict *other users'* legitimately pending/conflicting spend bundles from the caches. This directly parallels the Oku bug class: a hard-capped bookkeeping structure (`maxPendingOrders` there; `_cache_max_size` here) that can be refilled at effectively zero net cost after each "cancellation" (here, natural cache eviction/no-op since the coin was never spent), permanently crowding out legitimate users' retry state.

### Impact Explanation
Items evicted from `_conflict_cache`/`_pending_cache` are simply dropped rather than retried on the next matching `new_peak()`/height advance, meaning legitimate users' transactions that were otherwise valid but temporarily blocked (by an honest conflict or unmet timelock) silently lose their automatic retry and must be manually resubmitted by the wallet/client, or otherwise fail to be included when their condition becomes satisfiable. This is a transaction-processing disruption reachable by any unprivileged spend-bundle submitter with no fee requirement, matching the "broken functionality / DoS at low cost, repeatable" class described in the source report. The severity is bounded because it disrupts retry bookkeeping rather than causing outright coin theft or double-spend acceptance, which is why this is assessed as Medium, consistent with the original finding's rating.

### Likelihood Explanation
The attack requires only ordinary wallet capability: the ability to construct and submit a spend bundle of one's own coin repeatedly (e.g., minor solution variation each time to produce a new `spend_name`), with no minimum fee and no successful spend consumption, so the cost of a single attacker is limited to transaction-construction overhead and possibly a small amount of fee-per-cost tuning to guarantee the desired classification. Given Chia's cheap CLVM execution and no fee floor on this specific path, sustained flooding of 1000 (`ConflictTxCache`)/3000 (`PendingTxCache`) slots is straightforward for a single actor running a simple script, similar to the original report's assumption of a cheap L2 chain.

### Recommendation
Apply the same fee-per-cost admission floor used for the full mempool (`nonzero_fee_minimum_fpc` / `at_full_capacity` check) to items entering `ConflictTxCache` and `PendingTxCache`, or change their eviction policy from pure FIFO to fee-aware eviction (similar to `Mempool.add_to_pool()`'s priority-ordered eviction), so that zero/low-fee resubmissions cannot arbitrarily displace higher-value or longer-waiting legitimate entries submitted by other users.

### Proof of Concept
Conceptual reproduction (not executed, based on code paths in `mempool_manager.py` and `pending_tx_cache.py`):
1. Attacker submits `SpendBundle` A spending coin `C` with fee `f` into the mempool; it is accepted.
2. Attacker submits `SpendBundle` A' spending the same coin `C` with a marginally different solution and fee `f' <= f + MEMPOOL_MIN_FEE_INCREASE - 1` (insufficient to replace A). `check_removals()` returns `MEMPOOL_CONFLICT`, and `add_spend_bundle()` unconditionally calls `self._conflict_cache.add(item)` without any fee check. [5](#0-4) 
3. Repeat step 2 with a new `spend_name` (trivial solution tweak) up to 1000+ times; each call to `ConflictTxCache.add()` evicts the oldest cached item (`first_in = next(iter(self._txs.keys()))`), which may belong to any other user's legitimately conflicting transaction. [6](#0-5) 
4. Coin `C` is never actually spent (A never gets replaced/confirmed), so the attacker can repeat indefinitely at negligible marginal cost, continuously crowding out other users' cached pending/conflicting transactions.

    def add(self, item: MempoolItem) -> None:
        """
        Adds SpendBundles that have failed to be added to the pool in potential tx set.
        This is later used to retry to add them.
        """
        name = item.name

        if name in self._txs:
            return None

        self._txs[name] = item
        self._cache_cost += item.cost

        while self._cache_cost > self._cache_max_total_cost or len(self._txs) > self._cache_max_size:
            first_in = next(iter(self._txs.keys()))
            self._cache_cost -= self._txs[first_in].cost
            self._txs.pop(first_in)

    def drain(self) -> dict[bytes32, MempoolItem]:
        ret = self._txs
        self._txs = {}
        self._cache_cost = 0
        return ret

    def add(self, item: MempoolItem) -> None:
        """
        Adds SpendBundles that are not yet valid because of a height assertion.
        They will be re-tried once their height requirement is satisfied
        """
        assert item.assert_height is not None

        name = item.name

        if name in self._txs:
            return None

        self._txs[name] = item
        self._cache_cost += item.cost
        self._by_height.setdefault(item.assert_height, {})[name] = item

        while self._cache_cost > self._cache_max_total_cost or len(self._txs) > self._cache_max_size:
            # we start removing items with the highest assert_height first
            to_evict = self._by_height.items()[-1]
            if to_evict[1] == {}:
                self._by_height.popitem()
                continue

            first_in = next(iter(to_evict[1].keys()))
            removed_item = self._txs.pop(first_in)
            self._cache_cost -= removed_item.cost
            to_evict[1].pop(first_in)
            if to_evict[1] == {}:
                self._by_height.popitem()
