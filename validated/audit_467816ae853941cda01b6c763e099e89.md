### Title
Witness-embedded InInstruction commitment is never verified, letting malformed spends inject arbitrary instruction data - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::extract_serai_data` extracts Serai `InInstruction` data from a transaction input's witness when the final witness item (the redeem script) matches the pattern `OP_SHA256 <push> OP_EQUALVERIFY ...`. The check in `segwit_data_pattern` only verifies the script's *shape* — it never verifies that the pushed 32 bytes actually equal `sha256` of the extracted witness data item, nor that the extracted item is the committed preimage at all. This is a direct analog of the CKEditor paste-injection class: a sanitizer that pattern-matches the container but doesn't validate the payload lets malformed input smuggle arbitrary content into a trusted pipeline (here, `output.data()` → `Shorthand::decode` → `RefundableInInstruction` → credited balance/instruction).

### Finding Description
The data flow is:

1. `get_outputs` scans each non-coinbase tx with `scanner.scan_transaction`, which matches purely on `script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:205`), then calls `extract_serai_data(tx)` and attaches the result to every `OutputType::External` output (`processor/src/networks/bitcoin.rs:692-735`).
2. `extract_serai_data` checks inputs: for each input with `witness.len() >= 2`, it treats `witness.last()` as a redeem script and, if `segwit_data_pattern` returns `Some(true)`, copies `witness[witness.len() - 2]` into `data` (`processor/src/networks/bitcoin.rs:508-519`).
3. `segwit_data_pattern` only checks `OP_SHA256`, then "a data push" (`ins.next()?.ok()?.push_bytes()?` — any length, value ignored), then `OP_EQUALVERIFY` (`processor/src/networks/bitcoin.rs:473-491`).

The intended design (per the test `test_receive_data_from_input` in `processor/src/tests/literal/mod.rs:93-162`) is that the witness item is the *preimage* committed inside the P2WSH script at funding time — i.e., `sha256(witness[len-2]) == <pushed hash>` must hold for the script to even execute. However, `segwit_data_pattern` discards the pushed hash entirely and never hashes the extracted witness item. Two concrete failures result:

- **No preimage binding**: an arbitrary witness item is accepted as the instruction even when it does not hash to the committed value. Any script beginning `OP_SHA256 <anything> OP_EQUALVERIFY` — a ubiquitous pattern (hashlocks, HTLCs) — causes the second-to-last witness element, whatever it is, to be injected as Serai instruction data.
- **Wrong element assumed**: `witness[len-2]` is blindly assumed to be the preimage. For scripts with more stack items (e.g., `<sig> <pubkey> <preimage> <script>` vs. other orderings), whichever element lands at `len-2` is taken.

The injected bytes then flow into `instruction_from_output` (`processor/src/multisigs/mod.rs:55-92`), which SCALE-decodes them as `Shorthand`, converts to `RefundableInInstruction`, and produces an `InInstructionWithBalance` credited with the output's balance — affecting minting, refunds (`instruction.origin.or(presumed_origin)`), and downstream instruction execution.

### Impact Explanation
An unprivileged Bitcoin user sending a transaction that pays a Serai external address can attach instruction data that was never committed to in any script, defeating the purpose of the `OP_SHA256 <hash> OP_EQUALVERIFY` commitment scheme. Because `data` is applied to *all* external outputs found in the tx, and because the hash pattern matches common hashlock scripts, a spend of an unrelated HTLC/hashlock input combined with a payment to Serai causes arbitrary witness stack contents (e.g., a signature, pubkey, or preimage belonging to a different protocol) to be interpreted as a Serai `InInstruction`. Where those bytes decode as a valid `Shorthand`/`RefundableInInstruction` — including an attacker-supplied `origin` — the deposited balance is bound to an instruction the funding output never committed to, enabling late-binding of instructions (chosen at spend time, after the funding tx is confirmed/observed) rather than at funding time as designed. This permits instruction grafting onto deposits, e.g., selecting refund origin or transfer destination after the fact, contrary to the commit-and-reveal security model.

### Likelihood Explanation
Reachable by any unprivileged party able to broadcast a Bitcoin transaction paying a registered Serai external address — no validator key or internal access needed. The trigger conditions are mild: spend any input whose witness script begins `OP_SHA256 <32 bytes> OP_EQUALVERIFY` (standard hashlock/HTLC construction) in the same transaction. The malformed-data injection works deterministically since the hash comparison is simply absent. Severity is medium rather than high because the attacker still funds the deposit with real value and the injected instruction still must decode as a valid `Shorthand` to produce an `InInstructionWithBalance` (invalid data is dropped at `processor/src/multisigs/mod.rs:66-82`).

### Recommendation
In `segwit_data_pattern`/`extract_serai_data`, enforce the commitment: capture the pushed bytes after `OP_SHA256`, require they are exactly 32 bytes, and verify `sha256(witness[witness.len() - 2]) == <pushed hash>` before accepting the witness item as Serai data. Reject the input otherwise. Additionally consider locating the preimage position per the actual script structure rather than assuming `len() - 2`.

### Proof of Concept
```rust
// Conceptual: in Bitcoin::get_outputs, a transaction like this injects
// attacker-chosen bytes as the InInstruction for an External output:

// Redeem script that passes segwit_data_pattern but whose pushed hash
// does NOT correspond to the provided witness data item:
let fake_hash = [0xAA; 32]; // committed hash, never checked
let script = ScriptBuf::builder()
    .push_opcode(OP_SHA256)
    .push_slice(fake_hash)              // any 32 bytes; not sha256(injected_data)
    .push_opcode(OP_EQUALVERIFY)
    // ... remainder of a valid hashlock spend script ...
    .into_script();

// Witness: [sig..., pubkey..., injected_data, script]
let injected_data = Shorthand::transfer(None, attacker_serai_address.into()).encode();
tx.input[0].witness.push(sig);
tx.input[0].witness.push(pubkey);
tx.input[0].witness.push(injected_data); // witness[len-2]: extracted verbatim
tx.input[0].witness.push(script);        // witness[len-1]: redeem script

// tx also contains an output paying Serai's external address.
// extract_serai_data returns injected_data even though
// sha256(injected_data) != fake_hash, because the hash is never compared.
// The External output's `data` is set to injected_data and is decoded as
// a RefundableInInstruction crediting the deposit to the attacker's chosen
// instruction — content that was never committed to on-chain.
```

The root cause is that `segwit_data_pattern` (`processor/src/networks/bitcoin.rs:473-491`) validates only the opcode skeleton and discards the pushed hash, while `extract_serai_data` (`processor/src/networks/bitcoin.rs:513-516`) trusts `witness[len-2]` as the preimage without hashing it — a missing-content-validation bug structurally identical to the CKEditor paste flaw, where a malformed payload passes a shallow structural check and arbitrary content enters a trusted sink.

One caveat worth noting: this analysis is based on the indexed code; whether an attacker gains economically beyond the deposit they must fund depends on downstream `InInstruction` semantics (mint/transfer/refund), which sit outside the in-scope crates, so I did not fully verify the end-to-end profit path.
