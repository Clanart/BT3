### Title
DataLayer Merkle proof verification lacks leaf/internal-node domain separation and proof-depth validation, allowing forged inclusion proofs - (File: chia/data_layer/data_layer_util.py, chia/data_layer/data_layer_wallet.py)

### Summary
Chia's DataLayer inclusion-proof verification (`dl_verify_proof_internal` and `verify_offer`) never checks that a claimed leaf hash actually terminates a subtree of the expected depth, and the hashing scheme uses the same domain tag for leaf and internal nodes. This is the direct analog of the Sablier "Merkle tree inside a Merkle tree" issue: a malicious DataLayer store owner can construct a proof where the "leaf" is really a precomputed internal-node hash of a hidden subtree, letting them forge key/value inclusion proofs that a counterparty will accept as valid.

### Finding Description
DataLayer's node hashing is domain-separated between key and value, but **not** between leaf and internal nodes: `key_hash(key) = sha256(0x01 || key)`, while both `leaf_hash(key, value) = sha256(0x02 || key_hash || value_hash)` and internal-node hashing use the same `0x02` prefix over two 32-byte hashes [1](#0-0) . Because leaf and internal hashes share the same tag, `sha256(0x02 || left || right)` for an internal node is indistinguishable from `sha256(0x02 || key_hash(key) || value_hash(value))` for a terminal node whenever `left == key_hash(key)` and `right == value_hash(value)`.

Verification of an inclusion proof (`dl_verify_proof_internal`) recomputes `leaf_hash` from the supplied `key_clvm_hash`/`value_clvm_hash`, checks it equals the proof's `node_hash`, and then calls `proof.valid()` to confirm the sibling-hash chain (`layers`) reconstructs the asserted root: [2](#0-1) . Nowhere is the proof's `layers` length checked against the real depth of the committed Merkle tree for that root. The same pattern is used for offer verification in `verify_offer()`, which likewise only checks `leaf_hash(...) == proof.node_hash` and `proof.valid()` per reference proof, with no depth check: [3](#0-2) .

Because a DataLayer store owner fully controls the tree contents (`DataStore`/`MerkleBlob` construction) and there is no depth commitment stored alongside the root, a malicious owner can insert a subtree whose "combined_hash" happens to also validate as `leaf_hash(fake_key, fake_value)` for some `fake_key`/`fake_value` they choose (by construction — they pick the two 32-byte children to be `key_hash(fake_key)` and `value_hash(fake_value)`), then hand out a shorter proof (skipping the fabricated subtree's own children) that a verifier will accept as genuine inclusion for `fake_key -> fake_value`.

### Impact Explanation
This directly affects the `get_proof` / `verify_proof` RPC flow used by an unprivileged Data Layer client (`chia/data_layer/data_layer_rpc_api.py:558-599`, `chia/data_layer/data_layer_util.py:924-943`) and the DL-offer verification path used during CAT/NFT/DL atomic-swap trades (`verify_offer` in `data_layer_wallet.py`). A dishonest store owner offering data via a DL offer, or answering `get_proof` requests, could present a forged (key, value) inclusion proof that a taker's `take_offer`/`verify_proof` call would accept as valid for the currently anchored root — deceiving the counterparty into completing an offer or trusting off-chain data that was never actually committed as claimed. This falls into the "offer settlement theft"/forged data-identity category reachable by any unprivileged offer counterparty or RPC caller trusting DataLayer proofs.

### Likelihood Explanation
Exploitation requires the attacker to control (or collude with) the DataLayer store/root being queried — i.e., they are the offer maker or the store's DL wallet owner supplying `get_proof`/offer data. This mirrors Sablier's own assessment ("a team member with malicious intent") — it is a plausible but not fully unprivileged network-wide attack; it requires the victim to trust a party who controls the DataLayer store contents, which is a common trust boundary in DL-offer trading. Likelihood is medium: no cryptographic break is needed, only careful subtree construction, but it requires an actively malicious counterparty rather than a passive attacker.

### Recommendation
Add domain separation between leaf and internal node hashing (e.g., distinct prefix bytes) so a leaf hash can never collide with an internal node hash, and additionally store/verify the expected proof depth (or tree size) bound to each committed root so that `dl_verify_proof_internal`/`verify_offer` reject proofs whose layer count is inconsistent with the tree's committed shape.

### Proof of Concept
1. As a malicious DataLayer store owner, build a tree where some internal node `N` has children `L = key_hash(fake_key)` and `R = value_hash(fake_value)` (attacker freely chooses `fake_key`/`fake_value`, then derives the required sibling values to make `N` match those hashes structurally).
2. Commit and publish the root as usual through normal batch-update/publish flow.
3. When answering a `get_proof` request (or constructing a DL offer), return a `HashOnlyProof`/`Proof` whose `node_hash = N` and whose `layers` only contain siblings from `N` up to the root (skipping `N`'s real children).
4. The victim's `verify_proof` (`dl_verify_proof_internal`, `chia/data_layer/data_layer_util.py:880-921`) or `verify_offer` (`chia/data_layer/data_layer_wallet.py:1253-1296`) recomputes `leaf_hash(fake_key, fake_value) == N` and checks `proof.valid()` against the published root — both checks pass, since neither validates that `N` is truly a terminal at the correct depth nor separates leaf/internal domains, resulting in acceptance of a forged inclusion claim for data that was never actually stored as a leaf.
