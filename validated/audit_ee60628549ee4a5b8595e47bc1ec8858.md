### Title
Ed448 torsion check is vacuous — `Point::is_torsion_free` always returns true, so torsioned points pass `from_bytes`/`read_G` despite claiming rejection - (File: crypto/ed448/src/point.rs)

### Summary
Analogous to CVE-2018-5392 — where binaries set the "Dynamic base" (ASLR-compatible) flag while the relocations table that ASLR actually requires was stripped — `crypto/ed448` declares a torsion-safety guarantee in `GroupEncoding::from_bytes` (gating point acceptance on `point.is_torsion_free()`), but `is_torsion_free` is implemented with a formula that is identically true for every point. The protection is advertised in the API surface yet mathematically absent, so any untrusted bytes fed to `Ed448::read_G`, `SchnorrSignature::read`, `Commitments::read`, `ThresholdKeys::read`, etc. can carry a small-order (torsion) component that the code believes it rejected.

### Finding Description
`Point::is_torsion_free` is defined as:

```rust
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
``` [1](#0-0) 

`Scalar::ZERO - Scalar::ONE` equals `-1` (mod l), so the expression computes `P·(-1) + P = 0`, which is the identity for **every** point `P`, torsion or not. The intended check (multiply by the prime order `l` and test for identity) is nowhere performed. This is the exact shape of the mingw-w64 bug: the flag/check is present and callers rely on it, but the underlying mitigation is void.

The vacuous check is consumed here:

```rust
let point = Point { x, y, z: FieldElement::ONE };
CtOption::new(point, not_negative_zero & point.is_torsion_free())
``` [2](#0-1) 

`from_bytes` therefore accepts points of order 4 (Ed448 cofactor). Every deserialization entry point that trusts `GroupEncoding` — `Ciphersuite::read_G` (which only additionally checks canonical re-encoding via `point.to_bytes() == encoding`), `SchnorrSignature::read`, `DLEqProof::read`, `Commitments::read`, `ThresholdKeys::read` — inherits the hole, since a canonical encoding of a torsioned point still re-encodes to itself and passes the canonicality comparison in `crypto/ciphersuite/src/lib.rs` lines 91-100. [3](#0-2) 

### Impact Explanation
Ed448's `Point` is declared `PrimeGroup`, and downstream verification formulas assume all deserialized points lie in the prime-order subgroup — the same assumption documented in `crypto/schnorr/src/lib.rs` lines 34-41 ("These are intended to be strict... generic over Ciphersuite which is for PrimeGroups"). With torsion accepted:

- A public key or nonce containing a 4-torsion component `T` makes the Schnorr equation `R + c·A − s·G = 0` satisfiable modulo the torsion factor: for `A = T`, `R = identity`, `s = 0`, verification passes whenever `c ≡ 0 (mod 4)` (~25% of challenges), giving a probabilistic forgery path and an incorrect verifier formula for adversary-supplied keys/nonces.
- In FROST/DKG verification (`verify_share` / `batch_statements` in `crypto/frost/src/sign.rs`), a torsioned verification share or commitment is no longer bound to the prime-order subgroup, invalidating the share-validation guarantee.

Accepted impact per scope: an incorrect verifier formula reachable purely through untrusted bytes passed to `read_G`/`verify`.

### Likelihood Explanation
Any protocol path that deserializes an Ed448 point supplied by an untrusted party reaches the bug — no collusion, no leaked keys required; the torsion point is a valid canonical encoding. Exploiting it for signature forgery additionally requires influencing ~2 bits of the challenge (probability 1/4 per attempt for a pure order-4 key), so it is a Medium-severity integrity failure rather than a reliable one-shot forgery. Uncertainty: practical exploitability depends on whether any deployed flow accepts attacker-chosen Ed448 public keys/nonces; the cryptographic defect itself is unconditional.

### Recommendation
Fix `is_torsion_free` to actually test prime-order membership, e.g.:

```rust
fn is_torsion_free(&self) -> Choice {
  (*self * Scalar::from(BASEPOINT_ORDER)).is_identity()
}
```

or clear the cofactor and compare (`(*self * cofactor).mul_by_cofactor`-style check), then add a regression test asserting `from_bytes` rejects known order-2/order-4 Ed448 encodings. Audit `crypto/ed448` for any other place relying on the vacuous check.

### Proof of Concept
```rust
use group::GroupEncoding;
use ed448::Point;

// A canonical encoding of an Ed448 point with a non-trivial torsion
// component (e.g., the order-2 point or any point + order-4 point).
let mut bytes = [0u8; 57];
// ... populate with encoding of T (small-order point) ...
let p = Option::<Point>::from(Point::from_bytes(&bytes.into())).unwrap();
// Expected: None (torsion rejected). Actual: Some(p) — is_torsion_free
// always returns Choice(1) because P*(-1)+P == identity for all P.
```
