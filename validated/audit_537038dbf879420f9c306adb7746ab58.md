### Title
New depositors can retroactively claim historical bonus rewards, diluting/stealing yield from existing stakers - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2` (and its clones `vlMGPBaseRewarder.sol`, `mWOMSVBaseRewarder.sol`, `BaseRewardPool.sol`) track per-user reward checkpoints in `userRewardPerTokenPaid[rewardToken][account]`, which defaults to `0` for any account that has never been checkpointed. `earned()`/`_earned()` compute a user's owed reward as `balanceOf(account) * (rewardPerToken - userRewardPerTokenPaid) / 10**decimals`, using the account's **current, live** stake balance fetched from `MasterMagpie` (`balanceOf` calls `IMasterMagpie(operator).stakingInfo`). Because the pool itself has no `stake()`/`withdraw()` entrypoint of its own to checkpoint balances at the moment they change, and the checkpoint (`updateFor`/`updateReward` modifier) only runs inside `getReward`/`getRewards`/`updateFor()`, a wallet that stakes into a pool with an already-accrued `rewardPerTokenStored` (built up from prior `donateRewards`/`queueNewRewards` calls before they ever staked) will, on first claim, be credited the *entire* historical `rewardPerToken` delta multiplied by their newly-deposited balance — reward that was actually earned by, and intended for, the pool's pre-existing stakers. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
- `rewardPerToken(rewardToken)` is a monotonically-increasing global accumulator, bumped whenever `_provisionReward` runs (via `queueNewRewards`/`donateRewards`), independent of which specific stakers are currently in the pool. [4](#0-3) 
- `_earned`/`earned` multiply the account's **current** `balanceOf(_account)` (a live external read from `MasterMagpie.stakingInfo`) by the *entire* gap between `rewardPerToken` and the account's stored `userRewardPerTokenPaid`. [1](#0-0) 
- For any address that has never interacted with this specific rewarder, `userRewardPerTokenPaid[rewardToken][account]` is the Solidity default of `0`. There is no hook fired at deposit time in this rewarder to set `userRewardPerTokenPaid` to the then-current `rewardPerToken` before the user's stake balance becomes visible via `balanceOf`. The only checkpoint path is `_updateFor`, invoked from `updateReward`/`updateRewards` modifiers, which are only exercised by `getReward`/`getRewards`/`updateFor()` — i.e., at claim time, not necessarily at the moment of deposit. [5](#0-4) [6](#0-5) [2](#0-1) 
- Consequently, an ordinary wallet can: (1) wait for/observe an existing pool with accrued `rewardPerTokenStored` (built from past `donateRewards`/`queueNewRewards` provisioning), (2) deposit into `MasterMagpie` for that staking token, and (3) immediately call `getReward`/`getRewards` through `MasterMagpie.multiclaimSpec`/`multiclaimFor`, which routes to `IBaseRewardPool.getReward`/`getRewards` on the rewarder. [7](#0-6)  Because their `userRewardPerTokenPaid` is `0`, the checkpoint credits them with `balance * rewardPerToken`, i.e., the full historical accumulator applied to a stake they only just acquired.
- The reward token balance actually held by the contract corresponds to rewards accrued by (and owed to) the *previous* stakers who were present while the reward accumulator grew. Since `_sendReward` pays out of the same finite pool of already-transferred-in reward tokens, an attacker draining an inflated `userRewards[...]` entry directly reduces what is available to legitimate, pre-existing stakers — a direct theft of unclaimed yield analogous to the referenced Syndicate.sol H-03 pattern (lazy/late reward checkpointing allowing a new participant to claim rewards accrued before their participation).
- The identical pattern (same `_updateFor`, same `userRewardPerTokenPaid` default-zero baseline, same live `balanceOf`) exists in `vlMGPBaseRewarder.sol` and `mWOMSVBaseRewarder.sol`. [8](#0-7) [9](#0-8) 

### Impact Explanation
This allows an unprivileged wallet to steal unclaimed bonus-reward-token yield that rightfully belongs to earlier, legitimate stakers of a `BaseRewardPoolV2`/`vlMGPBaseRewarder`/`mWOMSVBaseRewarder` pool, by depositing after rewards have accrued and immediately claiming a share proportional to their new balance rather than their time-weighted contribution. This meets the "theft of unclaimed yield" impact bar.

### Likelihood Explanation
Likelihood is high for any pool that receives periodic `donateRewards`/`queueNewRewards` provisioning (bonus reward tokens distributed via these rewarders) and where new deposits can occur between provisioning events — no special privileges, timing races, or governance actions are required; a single wallet performing `deposit` → `multiclaimSpec`/`multiclaimFor` is sufficient once `rewardPerTokenStored > 0`.

### Recommendation
Checkpoint `userRewardPerTokenPaid[rewardToken][account]` to the current `rewardPerToken(rewardToken)` for every reward token at the moment a user's staked balance changes (deposit/withdraw), not only when they claim. This requires either adding an explicit hook that `MasterMagpie` calls into the rewarder before mutating `user.amount` (so the checkpoint captures the pre-change balance and baseline), or maintaining balance/checkpoint state locally inside the rewarder instead of relying on a live, out-of-band `balanceOf` read from `MasterMagpie`.

### Proof of Concept
1. Pool `P` has zero stakers; `rewardPerTokenStored[token] = R0`.
2. Owner/manager calls `donateRewards`/`queueNewRewards` multiple times, causing `rewardPerTokenStored[token]` to increase to `R1 > R0` while stakers who were present at that time never claimed. [10](#0-9) 
3. Attacker calls `MasterMagpie.deposit(stakingToken, largeAmount)`.
4. Attacker calls `MasterMagpie.multiclaimSpec([stakingToken], ...)`, which invokes `rewarder.getReward(attacker, attacker)` on the `BaseRewardPoolV2`, triggering `updateReward(attacker)` → `_updateFor(attacker)` → `earned(attacker, token)` = `largeAmount * (R1 - 0) / 10**decimals`. [11](#0-10) [1](#0-0) 
5. `_sendReward` transfers this inflated amount out of the contract's actual reward-token balance, which was funded to pay the earlier, legitimate stakers — leaving them under-funded when they later attempt to claim. [12](#0-11)

    modifier updateRewards(address _account, address[] memory _rewards) {
        uint256 length = _rewards.length;
        uint256 userShare = balanceOf(_account);
        
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = _rewards[index];
            // if a reward stopped queuing, no need to recalculate to save gas fee
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;
            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userShare);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
        _;
    }

        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =

            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;

                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
