## Title
Clone Operation Explicitly Disables Git's Built-In Clone Protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
The Vault report's core pattern is a security control that exists in the code path but is deliberately hard-coded to the "unprotected" state, so a guard that should be able to be activated by an operator is unconditionally off. The Desktop analog is in `clone()`: for every `git clone --recursive` invocation, Desktop explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the process environment, unconditionally disabling Git's own built-in clone-time protection mechanism for an operation whose entire input (the remote URL/repository content, including nested submodules) is attacker controlled. [1](#0-0) 

### Finding Description
`clone()` builds the execution environment for `git clone --recursive` and merges in `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally, regardless of the source of the URL (API-fetched clone URL, user-typed URL, or deep-link/`open-repository-from-url` action): [2](#0-1) 

This clone path is reachable from multiple attacker-influenced entry points: the "Clone repository" dialog resolves clone info from the GitHub API and from user-supplied URLs, [3](#0-2)  and the `x-github-client://openRepo/...` deep link handler parses a URL supplied entirely by whatever triggered the link and ultimately reaches the same clone flow via `dispatchURLAction`/`openRepositoryFromUrl`. [4](#0-3) [5](#0-4) 

The `--recursive` flag means submodules (each of which can point to arbitrary, attacker-chosen URLs and content) are fetched and checked out as part of the same operation. `GIT_CLONE_PROTECTION_ACTIVE` is the git-side kill switch that governs whether Git's built-in defenses against malicious repository content encountered during clone (case-variant/alternate-data-stream `.git` paths, hook injection through nested/symlinked `.git` directories in submodules, etc.) remain active. By forcing it to `'false'`, Desktop removes this layer of defense on every clone, precisely at the moment the tool is ingesting fully untrusted content from a remote the user does not yet control or trust.

This differs from the codebase's other, deliberate defenses that *are* correctly scoped and opt-in:
- `isClonePathSensitive()` is a genuine, always-on guard against path traversal into sensitive local directories. [6](#0-5) 
- The "unsafe repository" / `safe.directory` trust flow requires explicit user action before treating a differently-owned directory as trusted. [7](#0-6) 
- The Git hooks execution environment is gated by a feature flag and a user-controlled setting (`getHooksEnvEnabled()`), which must both be true. [8](#0-7) 

The clone-protection override has none of that gating — there is no setting, feature flag, or condition; it is a bare string literal disabling a security control for every clone, all the time.

### Impact Explanation
If a cloned or fetched (via `--recursive`, i.e., submodule) repository relies on the specific class of attack that `GIT_CLONE_PROTECTION_ACTIVE` is designed to stop (crafted repository object paths that can plant or overwrite hook files/executables inside `.git` during the clone), Desktop's explicit opt-out removes that mitigation. This can result in attacker-controlled files being written into locations that later get treated as executable Git hooks, i.e., code execution or file write outside the intended working tree — the report's protection-bypass pattern of "the guard exists but is programmatically forced off" reproduced almost exactly, but here the disabled guard is Git's own upstream mitigation rather than an app-level toggle.

### Likelihood Explanation
The disabling code runs unconditionally on every clone, and clone URLs are attacker-influenced in at least two realistic paths: cloning a repository discovered via the GitHub API/clone dialog, and the `x-github-client://openRepo/...` protocol handler which can be triggered by a link the user clicks. `--recursive` further widens the attack surface to any submodule URL embedded in the top-level repository, which the top-level repo author fully controls. No additional local access, admin rights, or social engineering beyond "clone this repo/click this link" is required.

I could not find any commit message, changelog entry, or code comment in the indexed files explaining why `GIT_CLONE_PROTECTION_ACTIVE` was set to `'false'` — this may be intentional (e.g., compatibility workaround) rather than a pure oversight, but no such rationale is present in the code I could retrieve. This should be verified with the Desktop team/commit history, which the indexed search here could not surface.

### Recommendation
Do not unconditionally disable `GIT_CLONE_PROTECTION_ACTIVE`. If there is a compatibility reason (e.g., a known false-positive with legitimate repositories/submodule layouts) it should be scoped as narrowly as possible (only for specific detected legitimate cases) rather than applied to every clone, and the decision should be logged/surfaced, not silently forced off in the environment passed to every `git clone --recursive` call.

### Proof of Concept
1. Author a public repository whose content is structured to trigger the class of issue that Git's clone-time protection (governed by `GIT_CLONE_PROTECTION_ACTIVE`) is designed to reject — e.g., a submodule reference or `.git`-adjacent path crafted to exploit case-insensitive/alternate-path filesystem behavior during a recursive clone.
2. Get a victim to clone this repository in Desktop, either directly via the Clone dialog (URL fetched from the GitHub API or typed manually) [3](#0-2)  or via an `x-github-client://openRepo/<attacker-url>` link. [9](#0-8) 
3. Desktop calls `clone()`, which sets `GIT_CLONE_PROTECTION_ACTIVE=false` in the child process environment before invoking `git clone --recursive -- <url> <path>`. [10](#0-9) 
4. Because the protection is disabled, Git does not apply the corresponding built-in defense that would otherwise reject or sanitize the crafted repository/submodule content, allowing the malicious payload delivered via the attacker-controlled clone/submodule content to land as it would on a vulnerable, unpatched Git installation.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  return unknown
}
