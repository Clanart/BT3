### Title
Attacker-controlled `.gitmodules` `file://` submodule URL can exfiltrate/plant local files during checkout when `protocol.file.allow=always` is re-enabled - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean that, when `true`, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [1](#0-0) . This flag is threaded through from `checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts` [2](#0-1) [3](#0-2) , and is exercised with `true` at least in the checkout test suite when checking out a branch that carries an (uninitialized) submodule [4](#0-3) .

### Finding Description
Git's `protocol.file.allow` setting controls whether local `file://` transports are permitted for submodule clones. This exact control was the security fix that Git shipped for CVE-2022-39253, where a malicious repository could declare a submodule pointing at a `file://` path elsewhere on disk; when a victim recursively clones/checks-out the repo, Git performs a local "clone" that copies the referenced directory's contents into the submodule working tree. Upstream Git changed the default to disallow this for recursive submodule operations precisely because the submodule URL (and therefore the `file://` target path) is fully attacker-controlled content coming from `.gitmodules` inside the cloned/fetched repository — the attacker doesn't need any special access, just a repository the victim opens or checks out branches/commits from in Desktop.

GitHub Desktop's `updateSubmodulesAfterOperation` reintroduces this exposure by explicitly passing `-c protocol.file.allow=always` whenever `allowFileProtocol` is `true` [1](#0-0) . Because `.gitmodules` (and thus the submodule URL for each entry) is part of the repository content that an attacker fully controls in any repo they publish or any branch/PR they push, an attacker can set a submodule URL to `file:///Users/victim/.ssh`, another local repository, or any other path readable by the victim's OS account. When Desktop performs a checkout with `allowFileProtocol=true`, Git will happily "clone" that local path into the submodule directory inside the repository working tree.

### Impact Explanation
This breaks two invariants at once:
1. **File read outside the repo boundary**: local directories unrelated to the repository (e.g., SSH keys, another private git repo, config directories) get copied into the checked-out working tree, i.e., unauthorized read access to host files driven purely by attacker-controlled repository content.
2. **Silent corruption of what the user commits/pushes**: once those files land in the working directory as part of a submodule, the user may unknowingly `git add`/commit/push them to the (attacker-visible) remote, exfiltrating local file contents to a repository the attacker controls.

Both outcomes match the "Valid Impact" criteria — attacker only needs to control a cloned/fetched repository's content (`.gitmodules`) and does not need local/physical access, admin rights, or any assistance from the victim beyond checking out the branch/commit inside Desktop.

### Likelihood Explanation
Likelihood depends entirely on which call sites in Desktop pass `allowFileProtocol: true` to `checkoutBranch`/`checkoutCommit` (e.g., cloning a new repository, checking out a PR branch, or switching branches). The test suite exercises this path with `true` for a submodule checkout scenario [4](#0-3) , and `clone.ts` also runs an initial `git clone --recursive` without any `protocol.file.allow` restriction applied at all [5](#0-4) , meaning any submodule with a `file://` URL is followed unconditionally during the initial clone regardless of the `allowFileProtocol` flag on subsequent checkouts. I was not able to fully enumerate every production call site that sets `allowFileProtocol: true` within the given tool budget — this needs to be verified against `app/src/lib/stores/app-store.ts` (or wherever `checkoutBranch`/`checkoutCommit` are invoked in the app, e.g., branch switching and PR checkout flows) to confirm whether the flag is ever set to `true` for repositories/branches originating from **untrusted forks or PRs**, as opposed to only for repositories the user explicitly trusts (e.g., local file-based clones used in testing/local dev workflows).

### Recommendation
- Verify all production call sites of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` and ensure `allowFileProtocol: true` is never used for branches/commits/repositories originating from a remote or fork that isn't already fully trusted (i.e., never for arbitrary cloned/fetched content, including PR checkouts).
- If `file://` submodule support is required for a legitimate local workflow, gate it behind an explicit, per-repository user opt-in/confirmation rather than passing it implicitly based on checkout type.
- Default `protocol.file.allow` to Git's safer default (unset, or `user`/`deny` for recursive submodule fetches) unless a user has explicitly trusted the specific repository being checked out.

### Proof of Concept
1. Attacker creates a public repository with a `.gitmodules` file containing:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
2. Victim opens/clones the repository in GitHub Desktop, or fetches/checks out a branch/PR from it where `checkoutBranch`/`checkoutCommit` is invoked with `allowFileProtocol: true` (as exercised in `app/test/unit/git/checkout-test.ts:160-166`).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which locally "clones" `/home/victim/.ssh` into the `leak/` submodule directory of the working tree [1](#0-0) .
4. The victim's SSH keys (or any other locally readable directory) now exist inside the repository's working tree and can be committed/pushed by the victim, or read directly from disk by any process with access to the repo folder.

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
```
