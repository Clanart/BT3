### Title
Webhook HMAC verification has no timestamp/replay protection, allowing indefinite reuse of old signed webhook payloads - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only checks that the HMAC-SHA256 signature of the raw request body matches the app secret; it never validates freshness of the request (no timestamp, nonce, or webhook-id replay check). Because the signature is a deterministic function of the (secret, body) pair with no expiry, any previously captured, validly-signed webhook request remains "valid" forever and can be resubmitted by anyone at any later time.

### Finding Description
`verify_request` computes `hmac_valid?(data)` purely from `request.raw_post` and the configured secret(s): [1](#0-0) 

`hmac_valid?` in turn only performs a constant-time comparison of the HMAC digest against the stored `secret`/`old_secret`: [2](#0-1) 

There is no check of a timestamp, delivery/webhook-id, or any freshness window anywhere in the verification path, and the generated webhook controllers simply call the job handler once verification passes: [3](#0-2) [4](#0-3) 

This is the same class of defect as the Tellor oracle bug: a signed message that should only be trusted once/near its original time window can be "played back" by anyone who has previously observed it (e.g., via network capture, logs, proxy, or a malicious insider on the merchant's infrastructure), because the app-side verification treats “correct signature” as sufficient proof of freshness/validity, with no state tracking of what has already been consumed.

### Impact Explanation
An attacker who obtains one legitimately-signed webhook payload (this does not require breaking the HMAC secret — only observing a single valid delivery) can replay it to the app's webhook endpoint at any future time and have it processed as if it were a live, current event. Concretely reachable impacts using the gem's own generated jobs:
- Replaying a captured `app/uninstalled` webhook destroys the shop's session record via `shop.destroy` in the generated job template, even though the merchant is still installed — an unprivileged, unrelated-merchant-triggerable denial of service / forced re-auth against a victim shop. [5](#0-4) 
- Replaying `customers/redact` / `shop/redact` privacy webhooks re-triggers destructive redaction logic against stale/old data long after the original event, which can cause incorrect data loss for a merchant.
- More generally, any shop-specific data-mutating webhook (`orders/*`, `carts/update`, etc.) can be resubmitted to reintroduce stale state into the app, mirroring the "old values reused" impact described in the Tellor finding.

### Likelihood Explanation
Medium: the attacker does not need to know the app's secret, only to have observed one previously-delivered valid webhook (e.g., via shared logging infrastructure, browser devtools on merchant-controlled tooling, a compromised proxy, or misconfigured request logging that many apps have). Given that, replay is trivial and unlimited in time, since neither `WebhookVerification` nor `PayloadVerification` records or checks any per-delivery identifier or timestamp.

### Recommendation
- Track processed webhook deliveries (e.g., by `X-Shopify-Webhook-Id`) and reject duplicates within a retention window.
- Enforce a maximum age for the request based on `X-Shopify-Triggered-At` or `X-Shopify-Webhook-Id`, rejecting significantly stale deliveries.
- Document/require idempotency in generated job handlers so repeated delivery of the same webhook id is a no-op for destructive operations (e.g., `AppUninstalledJob`, `ShopRedactJob`).

### Proof of Concept
1. Register a webhook (e.g., `app/uninstalled`) and capture one legitimate delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` computed as `Base64(HMAC-SHA256(secret, B))`.
2. At any later time (minutes, days, or months after), an attacker with access to `B`/`H` (e.g., from logs, a proxy, or a merchant's own dev tools) issues:
   ```
   POST /webhooks/app_uninstalled
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: <shop>
   Body: B
   ```
3. `verify_request` recomputes the HMAC of `B` with the app secret, matches `H`, and passes: [1](#0-0) 
4. The job runs again (`AppUninstalledJob#perform`), destroying the shop record even though the shop is still installed and using the app: [6](#0-5)

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```text
class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
```
