### Title
Cached FROST preprocess seed is never consumed: re-execution re-derives identical nonces for distinct signing sets/messages, enabling secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug (CVE-2024-56631) is a lifetime-ordering flaw: `kref_put` frees `sfp` while `sg_release` still references it. The Serai analog is the inverse-ordering lifetime flaw in `SigningProtocol::preprocess_internal`: a FROST preprocess seed is persisted in `CachedPreprocesses` under `context` and is **never deleted after the nonce material it produces has been consumed by `sign`**. Every subsequent call with the same context deterministically re-materializes the same `AlgorithmSignMachine` — the same nonces `d, e` — via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`ChaCha20Rng::from_seed(*seed.0)`), so the nonce is "used after free": the seed's single-use lifetime is exhausted at the first `sign`, yet it is resurrected and used again.

### Finding Description
- `preprocess_internal` stores the seed once (`if CachedPreprocesses::get(...).is_none()`) and loads it on *every* call, regenerating identical nonces each time (`signing_protocol.rs:123-145`). There is no delete/rotate anywhere; `CachedPreprocesses` has no removal path.
- `share_internal` calls `preprocess_internal().0` then `machine.sign(preprocesses, msg)` (`signing_protocol.rs:150-180`). The FROST share is `d + e·ρ·λ + secret_share·c`; reusing `(d, e)` with a different `preprocesses` map (different binding factor ρ and/or different included set λ) or a different `msg` (different challenge c) yields a second linear equation in the same nonces, and two shares with different challenges directly recover the secret share: `secret = (s1 − s2) / (λ·(c1 − c2))`.
- Two distinct consumers of the same context exist on the same path: `DkgConfirmer::share` calls `share_internal(preprocesses, key_pair)` once, and `DkgConfirmer::complete` calls `share_internal` **again** (`signing_protocol.rs:312-326`) with caller-supplied `preprocesses` and `key_pair` (which determine `msg = set_keys_message(...)`). Both use context `(b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`), so both derive identical nonces.
- The file's own safety argument concedes the gap: nonce-reuse safety rests entirely on BFT input uniqueness and on a check that "the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (`signing_protocol.rs:34-54`) — i.e., nothing prevents a second `share_internal` execution whose preprocess set or message differs from the first. `share` and `complete` take their `preprocesses`/`key_pair` from externally supplied tributary data, so an attacker-controlled preprocess map that still parses through `read_preprocess` (untrusted bytes → `read_preprocess`, explicitly in scope) produces a distinct ρ/challenge under identical nonces.

### Impact Explanation
Any second `share_internal` execution under an already-used `context` whose preprocess map or `key_pair` differs (even by one participant's commitment bytes) produces a signature share under reused nonces. Two such shares are public outputs (`share` is broadcast; `complete` outputs the aggregate). The attacker solves the two-share linear system and recovers the coordinator's MuSig/FROST secret share for the validator set key — full key-share recovery, the exact consequence the code comments (`signing_protocol.rs:25-27`, `frost/src/sign.rs:85-87`) flag as the failure mode. This maps directly to "signing of an unintended message / key share recovery" in the validation criteria.

### Likelihood Explanation
Reachable by an unprivileged party supplying preprocess bytes and key-pair data that reach `share`/`complete` (both take `HashMap<Participant, Vec<u8>>` parsed via `read_preprocess`). Triggering requires only that two invocations under one context see differing inputs — precisely the case the unimplemented TODO commitment check was meant to exclude. The persistence of the seed across process restarts further widens the window (a rebuilt coordinator re-derives the same nonces for whatever inputs it then sees). Rated High.

### Recommendation
Delete (or rotate) `CachedPreprocesses` entry the first time `share_internal` completes a `sign` for a context, and implement the pending TODO: before publishing a share, verify the on-chain preprocess set corresponds to the commitments derived from the cached seed, aborting if not. Alternatively key the cache by a hash of (context, sorted preprocess commitments, msg) and refuse to serve a second distinct tuple under the same seed.

### Proof of Concept
1. Attempt `a`: coordinator calls `DkgConfirmer::new(key, spec, txn, a)` → context `(b"DkgConfirmer", a)`; seed `S` stored.
2. `share(preprocesses_A, key_pair_A)`: nonces `(d, e)` derived from `S`; share `s1 = d + e·ρ_A·λ + x·c_A` is published.
3. `complete(preprocesses_B, key_pair_B, shares)` where `preprocesses_B` differs from `preprocesses_A` (e.g., an attacker-contributed participant commitment differs) or `key_pair_B ≠ key_pair_A`: `share_internal` reloads `S`, regenerates the same `(d, e)`, and internally produces `s2 = d + e·ρ_B·λ' + x·c_B` feeding the aggregate signature.
4. With `s1` and the aggregated signature (or the second share), solve for the secret share `x` via the standard nonce-reuse linear system over `(ρ_A, c_A, λ)` vs `(ρ_B, c_B, λ')` — all public quantities. Secret share recovered.
