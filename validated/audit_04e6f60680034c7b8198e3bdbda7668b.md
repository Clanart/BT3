### Title
Panic on missing `GeneratorProof` participant index in `GeneratorPromotion::complete` enables remote denial of service - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *count* and *upper bound* of the participant indexes in the caller-supplied `proofs` map, then indexes it with `HashMap::get(...).unwrap()`. A participant who submits their proof under a foreign index (e.g., the recipient's own index) causes a missing-key `unwrap()` panic, crashing the party running key promotion — the same availability-loss class as CVE-2021-2028 (repeatable crash of the server by a network attacker), mapped onto Serai's DKG generator-promotion message flow.

### Finding Description
`GeneratorPromotion::complete` performs two checks on `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

1. `proofs.len() == params.n() - 1` [1](#0-0) 
2. Every key `i` satisfies `u16::from(i) <= params.n()` [2](#0-1) 

It never checks that the key set equals `1..=n \ {params.i()}`. The proof-consumption loop then does `let proof = proofs.get(&i).unwrap()` for every `i != params.i()` [3](#0-2) .

Because `Participant` values in the map are unconstrained other than `<= n`, a single faulty participant can submit their `GeneratorProof` keyed under `params.i()` (the verifier's own index) or under another participant's index while omitting their own. With `n - 1` entries all `<= n`, both checks pass, but at least one required index `j != params.i()` is absent, so `proofs.get(&j)` returns `None` and `.unwrap()` panics. The panic occurs before any DLEq verification for that index, so it requires no valid proof from the attacker — only a syntactically readable `GeneratorProof` message (`GeneratorProof::read` just reads a point and a `DLEqProof` [4](#0-3) ).

### Impact Explanation
Complete loss of availability of the promotion operation, and — since `complete` consumes `self` and libraries in this ecosystem generally do not catch panics — a crash of the hosting process. In a Serai validator/processor context, promotion runs over `ThresholdKeys` produced by the PedPoP DKG (`promote` is used to move keys to a new generator, e.g., for Taproot-style tweaked generators). A crashing promotion aborts the key-rotation/migration for the whole threshold group: no participant can finalize the promoted `ThresholdKeys<C2>` while the attacker keeps sending the malformed map, matching the "frequently repeatable crash" pattern of the MySQL InnoDB DoS. Severity is Medium: high-privileged-ness is not required (any DKG participant can send the malformed message), but impact is limited to availability during the promotion ceremony.

### Likelihood Explanation
Any one of the `n - 1` remote participants in the promotion can trigger it deterministically, at zero computation cost, by transmitting a `GeneratorProof` associated with the wrong `Participant` index (or the caller assembling a map keyed by claimed rather than verified sender). The path is `complete(proofs)` → length/bounds checks pass → `proofs.get(&i).unwrap()` on the missing index. Reachability requires the integrator to build `proofs` from received messages keyed by sender index, which is the natural calling convention given the map type.

### Recommendation
Replace the fallible indexing with an explicit error. For each `i` in `1 ..= params.n()` where `i != params.i()`, use `proofs.get(&i).ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?` (or a dedicated `MissingProof` variant) instead of `.unwrap()`. Optionally also reject `proofs.contains_key(&params.i())` up front so a proof registered under the verifier's own index is blamed on the sender rather than silently counting toward `n - 1`. The final `ThresholdKeys::new(...).unwrap()` [5](#0-4)  is safe since the map it builds is complete by construction, but should still be converted to a propagated error for consistency.

### Proof of Concept
```rust
// n = 3, our participant index i = 1.
// Honest participant 3 sends a valid GeneratorProof.
// Attacker (participant 2) submits their GeneratorProof under index 1
// (the verifier's own index) instead of index 2 — e.g., by sending it
// while claiming/being keyed as participant 1.

let mut proofs: HashMap<Participant, GeneratorProof<C1>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof); // wrong key
proofs.insert(Participant::new(3).unwrap(), honest_proof);

// Checks pass: proofs.len() == 2 == n - 1; all keys <= 3.
promotion.complete(&proofs);
// Loop reaches i = Participant(2); proofs.get(&Participant(2)) == None
// -> .unwrap() panics at crypto/dkg/promote/src/lib.rs:146
```

The same panic occurs if the attacker simply sends a proof keyed under index `j` while the honest `j`'s proof is absent — any multiset of `n - 1` keys within `1..=n` that does not cover `1..=n \ {params.i()}` triggers it.

Caveat: whether this is reachable depends on the integrator keying the `proofs` map by a sender-supplied or misattributed index rather than strictly verifying provenance; the bug itself (a panic on attacker-influenced map contents inside a `complete` API over untrusted messages) is concrete in the in-scope crate. I was not able to inspect the `processor`/`coordinator` call sites of `GeneratorPromotion::complete` within this search to confirm the exact map-construction convention used in production.
