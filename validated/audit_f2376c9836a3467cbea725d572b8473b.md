## Analysis: Stale "prevEventsLen" cursor causes duplicate balance crediting on nested/recursive precompile calls

### Title
Double-application of bank balance-change events to the EVM StateDB during nested precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The reported bug class is: a "last known reference value" used to compute a delta is not kept consistent across independently-triggered updates, so a later update re-applies a delta that has already been accounted for, corrupting a cumulative value. In Cosmos EVM, the analogous mechanism is `BalanceHandler.prevEventsLen`, which is used as a cursor into the SDK `EventManager` event log to decide which bank events to translate into `StateDB.AddBalance`/`SubBalance` calls after a precompile executes. Because this cursor is recorded once at entry (`BeforeBalanceChange`) and consumed as `events[prevEventsLen:]` at exit (`AfterBalanceChange`), any events emitted and *already applied to the StateDB* by an inner/nested precompile invocation that occurs between the outer's `Before`/`After` calls get replayed and re-applied by the outer call as well.

### Finding Description
`RunNativeAction` in [1](#0-0)  wraps every precompile call. Inside `runNativeAction`, a `BalanceHandler` is obtained via `p.BalanceHandlerFactory.NewBalanceHandler()`, `BeforeBalanceChange` snapshots the current event count, the native `action` executes, and `AfterBalanceChange` replays new bank events into the StateDB: [2](#0-1) .

`BeforeBalanceChange`/`AfterBalanceChange` implementation: [3](#0-2) 

The critical issue is that `action(ctx)` can itself trigger a nested EVM call (e.g. an ERC20/bank/ICS20 precompile call that internally calls `CallEVM`/executes a contract which in turn calls back into a precompile). The codebase explicitly supports and tracks recursive/nested precompile calls via `precompileCallsCounter` and `MaxPrecompileCalls`, and journals each nested precompile invocation as a `precompileCallChange`: [4](#0-3) , [5](#0-4) .

When a nested precompile call occurs during the outer call's `action`, that nested call gets its *own* `BalanceHandler` instance and correctly applies its own bank events to the StateDB at `events[nestedPrevEventsLen:nestedEnd]` via its own `AfterBalanceChange`. However, when execution returns to the *outer* precompile call and it finishes, the outer's `AfterBalanceChange` computes `events[bh.prevEventsLen:]` using the **original, pre-nested-call** cursor. This slice necessarily also includes all the bank events that were emitted and already applied to the StateDB by the nested call, because the outer cursor was captured before the nested call ran. The outer handler has no way to know that a sub-range of "new" events was already consumed by an inner handler — it re-parses and re-applies every `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` event in that range, calling `stateDB.AddBalance`/`SubBalance` a second time for the same underlying bank movement.

This is a direct analog of the reported bug: the "last recorded" reference (`lastEthPrice` in the report, `prevEventsLen` here) is not synchronized with intermediate state-changing operations that occur between its capture and its use, so the same delta gets counted twice against a cumulative value (there: `cumulativeValue`; here: the EVM `StateDB` balance of the affected address(es)).

### Impact Explanation
Re-applying the same `AddBalance` delta doubles the EVM-visible balance of the receiver address for that bank transfer, while the underlying `x/bank`/`x/precisebank` balance was only moved once. This directly breaks the 1:1 accounting invariant between native bank balances and EVM StateDB balances that the `x/precisebank`/precompile design depends on (see `x/precisebank/README.md` invariant `aatom` fully backed by `uatom`). Since the corrupted (inflated) balance lives in the StateDB that is committed to the `x/vm` keeper at the end of the transaction (`s.commitWithCtx` writes `obj.account` including balance), the attacker's on-chain EVM balance becomes permanently larger than what is actually backed by escrowed bank coins. That balance can subsequently be spent/transferred/withdrawn (e.g., via WERC20/`werc20.Withdraw`, ERC20 transfer, or conversion back to native coin), constituting unauthorized duplication/minting of spendable value — a Critical impact under the allowed-impact gate ("unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances ... or precompile-mediated assets").

### Likelihood Explanation
This requires an unprivileged user to construct a contract call sequence that triggers a precompile call whose native action itself performs a further EVM call reaching a second (or the same) balance-affecting precompile before the outer one returns — i.e., recursive/nested precompile invocation with bank-balance side effects in between. This is exactly the scenario the repository's own test `evmd/tests/integration/balance_handler/balance_handler_test.go` (`TestRecursivePrecompileCallsWithDebugPrecompile`) is built to exercise, confirming the pattern is reachable and previously identified internally as "the balance handler bug." Note: I was only able to confirm that the *debug* test precompile (`testutil/testdata/debug/debug.go`) uses a **shared/singleton** `BalanceHandler` (`p.GetBalanceHandler()`), which is the clearest reproduction path; production precompiles (erc20, bank, staking, distribution, ics20, gov, slashing) obtain a **fresh** `BalanceHandler` per call via `BalanceHandlerFactory.NewBalanceHandler()`. A fresh handler prevents the "shared instance" variant of the bug, but does **not** prevent the double-application described above, because the vulnerability is about the *event-index window overlap* between an outer and inner call's independently-created handlers, not about instance sharing. I was not able to fully trace, within the tool-call budget, a concrete production precompile-to-precompile call chain (e.g. ICS20 transfer triggering a callback that reaches ERC20/bank precompile) that would reliably reproduce this in mainline (non-debug) code, so this should be verified with a live nested-call trace before treating it as confirmed-exploitable in production precompiles.

### Recommendation
Make the event-window bookkeeping nesting-aware: track a stack/counter of already-consumed event indices, or have `AfterBalanceChange` advance the shared high-water mark that `BeforeBalanceChange` reads, so that an outer call's window excludes any sub-range already consumed and applied by an inner call. Alternatively, only the outermost precompile call in the current transaction should perform event-driven StateDB balance reconciliation, with nested calls suppressing their own re-application (e.g., propagate a "began index" pointer through nested calls and update a single shared cursor after each nested `AfterBalanceChange` completes, rather than each level independently slicing from its own separately captured start index).

### Proof of Concept
Not independently reproduced within the available tool budget beyond the repository's own `TestRecursivePrecompileCallsWithDebugPrecompile` test, which demonstrates the mechanics of nested precompile calls interacting with a `BalanceHandler`'s `prevEventsLen` cursor using the test-only debug precompile: [6](#0-5) . Constructing a concrete exploit chain through *production* precompiles (rather than the debug/test precompile) would require further investigation to confirm a reachable nested-call path that emits bank events between an outer precompile's `Before`/`AfterBalanceChange` calls.

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
