## Title
Wallet raw-message signing modes (`BLS_MESSAGE_AUGMENTATION_HEX_INPUT`/`UTF8_INPUT`) can be tricked into producing valid `AGG_SIG_ME`/`AGG_SIG_UNSAFE` spend-authorization signatures due to unstructured, delimiter-free concatenation of the signed payload - (File: `chia/wallet/util/signing.py`, `chia/consensus/condition_tools.py`)

### Summary
The Gitea advisory's root cause is that a signed payload is built by raw concatenation of fields without delimiters or length prefixes, so a value signed for one semantic context can be replayed/reinterpreted as authorization for a different context. Chia's `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc. conditions have the exact same construction style: `msg + coin_identity_bytes + additional_data`, concatenated with no delimiters and verified as a single opaque BLS-signed byte string [1](#0-0) . Separately, the wallet exposes a "sign arbitrary message" capability (`sign_message`/`sign_message_by_address`/`sign_message_by_id`) that, for `SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT` / `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT`, signs the caller-supplied bytes directly with the same synthetic secret key used to authorize on-chain spends of the user's coin, with no prefix, no domain tag, and no rejection of dangerous content [2](#0-1) .

### Finding Description
For a standard coin, the inner puzzle's `AGG_SIG_ME` condition is satisfied by any BLS signature over `sha256tree(delegated_puzzle) + coin.name() + AGG_SIG_ME_ADDITIONAL_DATA`, produced with the coin's synthetic secret key [3](#0-2) . Consensus validation reconstructs this exact same flat, delimiter-free byte string from the coin's real identity fields and the CLVM-provided `msg`, and hands it to `AugSchemeMPL.verify` [4](#0-3) . BLS signature verification has no notion of "structured fields" — it only sees one flat byte string, so any signature over the identical bytes is accepted, regardless of how or why it was produced.

The wallet RPC's `sign_message` function, when invoked with `SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT` (or `_UTF8_INPUT`), signs exactly the caller-controlled bytes with `AugSchemeMPL.sign(secret_key, hex_message)` — no `CHIP_0002_SIGN_MESSAGE_PREFIX` wrapping, no CLVM tree-hash transform, and no check that the bytes don't end in (or otherwise resemble) a known `AGG_SIG_*_ADDITIONAL_DATA` suffix [2](#0-1) . Contrast this with the AGG_SIG_UNSAFE consensus check, which explicitly walks all `agg_sig_additional_data` values and rejects any `AGG_SIG_UNSAFE` message ending in one of them specifically to prevent this class of cross-domain confusion [5](#0-4) . That guard exists only for the on-chain `AGG_SIG_UNSAFE` condition path; it is not applied to the wallet's raw message-signing RPC surface, so the "hardening" that Chia already recognized as necessary for one code path was never extended to the other, structurally identical, signing surface.

Because `sha256tree(delegated_puzzle)`, `coin.name()`, `AGG_SIG_ME_ADDITIONAL_DATA` (and the analogous fields for `AGG_SIG_PARENT`/`AGG_SIG_PUZZLE`/`AGG_SIG_AMOUNT`/etc.) are all public, deterministic, and computable by anyone who knows the target coin, an attacker who can get a wallet to sign an arbitrary hex/utf8 "message" (e.g., via a malicious dApp's "verify wallet ownership" / "login" flow calling `sign_message_by_address`) can construct that message to be byte-identical to a valid spend-authorization payload for one of the victim's real coins, then reuse the resulting BLS signature inside a `CoinSpend`/`SpendBundle` to satisfy the coin's `AGG_SIG_ME` (or other `AGG_SIG_*`) condition and move funds without the victim ever seeing or approving an actual transaction.

### Impact Explanation
This allows unauthorized, attacker-directed coin movement using a signature the victim believes they issued for an unrelated, non-financial purpose (message signing / login proof). It maps directly to "concrete unsigned or unauthorized coin movement," the strongest listed impact category, and is reachable purely through wallet RPC calls that any dApp/wallet-connected client can trigger — no privileged, network, or node-level access required.

### Likelihood Explanation
Exploitability requires social/UX engineering (getting the user's wallet to sign a specific raw byte string presented as an innocuous message) rather than a pure protocol flaw, and the attacker must know the coin identity and delegated-puzzle tree hash in advance to craft the colliding payload. This is a real, concretely reachable path (the RPC and signing primitives exist exactly as described) but depends on user/wallet interaction, similar in spirit to the Gitea report's requirement that the target task be in a specific state.

### Recommendation
- Apply the same `agg_sig_additional_data` suffix-rejection check used for `AGG_SIG_UNSAFE` (`chia/consensus/condition_tools.py:140-145`) to the raw-message signing paths in `chia/wallet/util/signing.py`'s `sign_message`, for `BLS_MESSAGE_AUGMENTATION_HEX_INPUT`/`UTF8_INPUT` modes.
- Prefer mandating the CHIP-0002 domain-separated prefix/tree-hash wrapping (`("Chia Signed Message", message)`) for all message-signing RPC modes, removing the raw/unwrapped signing modes or gating them behind explicit, prominent warnings distinguishing them from spend-authorization signing.
- More generally, add explicit length-prefixing or canonical structured encoding (not raw concatenation) to the `AGG_SIG_*` message construction in `make_aggsig_final_message` (`chia/consensus/condition_tools.py:73-96`) so that no off-protocol signing surface can ever produce a byte-for-byte-colliding payload.

### Proof of Concept
1. Attacker learns the target coin's `coin.name()` (public) and can construct/predict a delegated puzzle they want executed against that coin (public CLVM construction, e.g., `Program.to((1, malicious_conditions))`), computing `sha256tree(delegated_puzzle)`.
2. Attacker builds `payload = sha256tree(delegated_puzzle) + coin.name() + AGG_SIG_ME_ADDITIONAL_DATA` and hex-encodes it.
3. Attacker's dApp calls the wallet RPC `sign_message_by_address` (or `sign_message_by_id`) with `signing_mode = BLS_MESSAGE_AUGMENTATION_HEX_INPUT` and `message = payload.hex()`, framed to the user as an innocuous "verify ownership"/"login" request [6](#0-5) .
4. The wallet signs `payload` directly with the coin's synthetic secret key via `sign_message` → `AugSchemeMPL.sign(secret_key, hex_message)` [2](#0-1) .
5. Attacker submits a `SpendBundle` containing a `CoinSpend` for the victim's coin, with `delegated_puzzle` producing `(AGG_SIG_ME synthetic_pubkey sha256tree(delegated_puzzle))`, and aggregates the obtained signature. Consensus verification computes the identical `payload` bytes and accepts the signature [1](#0-0) , allowing the malicious conditions (e.g., `CREATE_COIN` to an attacker address) to execute.

```python
def make_aggsig_final_message(
    opcode: ConditionOpcode,
    msg: bytes,
    spend_conditions: Coin | SpendConditions,
    agg_sig_additional_data: dict[ConditionOpcode, bytes],
) -> bytes:
    if isinstance(spend_conditions, Coin):
        coin = spend_conditions
    elif isinstance(spend_conditions, SpendConditions):
        coin = Coin(spend_conditions.parent_id, spend_conditions.puzzle_hash, uint64(spend_conditions.coin_amount))
    else:
        raise ValueError(f"Expected Coin or Spend, got {type(spend_conditions)}")  # pragma: no cover

    COIN_TO_ADDENDUM_F_LOOKUP: dict[ConditionOpcode, Callable[[Coin], bytes]] = {
        ConditionOpcode.AGG_SIG_PARENT: lambda coin: coin.parent_coin_info,
        ConditionOpcode.AGG_SIG_PUZZLE: lambda coin: coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_AMOUNT: lambda coin: int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT: lambda coin: coin.puzzle_hash + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_AMOUNT: lambda coin: coin.parent_coin_info + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_PUZZLE: lambda coin: coin.parent_coin_info + coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_ME: lambda coin: coin.name(),
    }
    addendum = COIN_TO_ADDENDUM_F_LOOKUP[opcode](coin)
    return msg + addendum + agg_sig_additional_data[opcode]
```

```python
def pkm_pairs(conditions: SpendBundleConditions, additional_data: bytes) -> tuple[list[G1Element], list[bytes]]:
    ret: tuple[list[G1Element], list[bytes]] = ([], [])

            (ConditionOpcode.AGG_SIG_PUZZLE, spend.agg_sig_puzzle),
            (ConditionOpcode.AGG_SIG_AMOUNT, spend.agg_sig_amount),
            (ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT, spend.agg_sig_puzzle_amount),
            (ConditionOpcode.AGG_SIG_PARENT_AMOUNT, spend.agg_sig_parent_amount),
            (ConditionOpcode.AGG_SIG_PARENT_PUZZLE, spend.agg_sig_parent_puzzle),
            (ConditionOpcode.AGG_SIG_ME, spend.agg_sig_me),

                ret[0].append(pk)
```

```python
def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )
```

```python
DEFAULT_HIDDEN_PUZZLE_HASH from this puzzle is used with

This is important because it allows sign_coin_spends to function properly via the
following mechanism:

- A 'standard coin' coin exists in the blockchain with some puzzle hash.

- The user's wallet contains a primary sk/pk pair which are used to derive to one
  level a set of auxiliary sk/pk pairs which are used for specific coins. These
  can be used for signing in AGG_SIG_ME, but the standard coin uses a key further
  derived from one of these via calculate_synthetic_secret_key as described in
  https://chialisp.com/docs/standard_transaction. Therefore, when a wallet needs
  to find a secret key for signing based on a public key, it needs to try repeating
  this derivation as well and see if the G1Element (pk) associated with any of the
  derived secret keys matches the pk requested by the coin.

    delegated_puzzle_solution = Program.to((1, condition_args))
    solutions = Program.to([[], delgated_puzzle_solution, []])

  simply quoting a list of conditions, and the following argument is the arguments

  p2_delegated_puzzle_or_hidden_puzzle are given. The first argument determines
  whether a hidden or revealed puzzle is used. If the puzzle is hidden, then what
  is required is a signature given a specific synthetic key since the key cannot be
```
