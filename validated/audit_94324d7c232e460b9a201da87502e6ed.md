### Title
Tokenfactory Denom Allow-List Is Enforced Only in `MsgSend`/`MsgMultiSend`, Bypassable via the EVM Bank Precompile - ([File: sei-cosmos/x/bank/keeper/msg_server.go])

### Summary
`IsInDenomAllowList` restricts transfers of a tokenfactory denom to addresses on an admin-set allow list, but the enforcement is implemented as an explicit check inside the `Send`/`MultiSend` Cosmos message handlers rather than inside the shared `SendCoins`/`SendCoinsAndWei` keeper functions that actually move balances. Any code path that calls the underlying `SendCoins`/`SendCoinsAndWei` keeper methods directly — instead of going through `MsgSend`/`MsgMultiSend` — moves funds without ever consulting the allow list.

### Finding Description
The allow-list check is wired in only at the message-server layer: [1](#0-0) [2](#0-1) 

The actual balance-moving logic lives in `BaseSendKeeper`'s `SendCoins`/`SendCoinsAndWei`, and `IsInDenomAllowList` itself is only a helper the msg server chooses to call — it is not baked into the keeper's transfer primitives: [3](#0-2) 

The EVM bank precompile calls `SendCoins`/`SendCoinsAndWei` on the bank keeper directly (as confirmed by the `SendCoins(ctx`/`SendCoinsAndWei` call sites in `precompiles/bank/bank.go` and its legacy versions across `v552`–`v640`), which is the same keeper method used by the message-server path but reached from an EVM transaction rather than from `MsgSend`. Because the precompile does not itself call `IsInDenomAllowList`, and the keeper-level `SendCoins`/`SendCoinsAndWei` never checks it either, an EVM transaction invoking the bank precompile's send method can move an allow-listed tokenfactory denom to or from an address that is not on that denom's allow list — something explicitly forbidden and tested-for on the Cosmos message path: [4](#0-3) 

This is structurally identical to the reported bug class: a privileged/restricted operation ("only whitelisted addresses may transact") has its authorization check attached to only one caller of the sensitive function, while another externally reachable entry point calls the same sensitive underlying logic and inherits none of the protection.

### Impact Explanation
A tokenfactory denom admin who has set a `DenomAllowList` (via `MsgUpdateDenom`/`SetDenomAllowList`) is relying on the chain to prevent transfers to/from non-allow-listed addresses — this is a compliance/permissioning primitive (e.g., for regulated or KYC-gated tokens). If the EVM bank precompile's transfer entry point does not also enforce `IsInDenomAllowList`, any EVM account holding such a denom (e.g., via the usei/wei bridge or a bank-precompile-facilitated balance) can send it to or receive it from disallowed addresses, defeating the allow-list guarantee entirely. This is an unauthorized-transfer/permission-bypass issue reachable purely from a submitted EVM transaction.

### Likelihood Explanation
Medium-High: any externally-submitted EVM transaction that calls the bank precompile's send functionality with a tokenfactory denom that has an active `DenomAllowList` would trigger this bypass — no special privileges beyond holding the restricted denom are required to attempt the transfer. I was not able to fully verify the exact code of `precompiles/bank/bank.go`'s `send`/`sendNative` handler bodies in this session (only the call-site grep results were confirmed) to check whether the precompile independently re-implements an allow-list check before calling `SendCoins`; that would need to be read directly to close out this analysis with full certainty.

### Recommendation
Move the `IsInDenomAllowList` (and `BlockedAddr`) checks into `BaseSendKeeper.SendCoins` and `SendCoinsAndWei` themselves (or into a shared pre-transfer hook that all callers, including the EVM bank precompile and any CosmWasm bank bindings, must go through), rather than relying on each caller of the keeper method to remember to call the check itself.

### Proof of Concept
1. As the tokenfactory denom creator/admin, create a denom `factory/{admin}/restricted` and call `SetDenomAllowList` (via `MsgUpdateDenom`) restricting transfers to a fixed set of addresses, per [5](#0-4) .
2. Fund an address A that is NOT on the allow list with some of this denom (or associate an EVM address to it).
3. From address A, submit an EVM transaction invoking the bank precompile's send method (`precompiles/bank/bank.go`) to transfer the restricted denom to an arbitrary address B not on the allow list.
4. Because the precompile call path reaches `SendCoins`/`SendCoinsAndWei` directly without going through `sei-cosmos/x/bank/keeper/msg_server.go`'s `Send`/`MultiSend` handlers, the `IsInDenomAllowList` check in [6](#0-5)  is never evaluated, and the transfer succeeds despite both A and B being outside the allow list — contrast with the same attempt via `MsgSend`, which is rejected as shown in [7](#0-6) .

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	err = k.SendCoins(ctx, from, to, msg.Amount)
	if err != nil {
		return nil, err
	}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
