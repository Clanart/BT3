### Title
`ThresholdKeys::read` accepts a self-declared participant index and arbitrary verification shares without binding them to the deserialized secret share — a deserialized key share is "promoted" to any participant role of an attacker-chosen multisig - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `(t, n, i)`, the interpolation method, a secret share, and `n` verification shares entirely from untrusted bytes, then hands them to `ThresholdKeys::new`, which only checks `i <= n` and `verification_shares.len() == n`. Nothing verifies that `verification_shares[i] == C::generator() * secret_share`, i.e. that the credential (the secret share) actually corresponds to the claimed participant index `i`, nor that the claimed index is one the deserializer is authorized to act as. This is the direct analog of CVE-2024-31859: a party supplies input that causes them to assume a role (participant index / multisig membership) without the authorization check that should bind the claimed role to a valid credential.

### Finding Description
`ThresholdKeys::read` parses `i` via `Participant::new(read_u16()?)` which only rejects zero, and reads `n` arbitrary points as `verification_shares` [1](#0-0) . `ThresholdKeys::new` then only bounds checks `participant <= n` and `len == n` [2](#0-1)  before deriving `group_key` purely from the supplied verification shares over participants `1..=t` [3](#0-2) . There is no consistency check between `secret_share`, `verification_shares[i]`, and the resulting `group_key`.

Because `Interpolation::Constant` deserialization also takes `n` arbitrary attacker-controlled scalars as interpolation factors [4](#0-3) , an attacker crafting the byte stream controls every input to the group-key derivation. Concretely, an attacker can construct serialized `ThresholdKeys` where:
- `i` is any participant index `1..=n` (self-promotion to any role),
- `verification_shares` are points whose discrete logs the attacker knows (e.g., `G * s_j` for attacker-chosen `s_j`),
- `secret_share` is consistent with `verification_shares[i]` — or deliberately inconsistent.

In the consistent case, the deserialized keys are a fully valid signer for a multisig whose group key the attacker fully controls (they know every underlying share). In the inconsistent case, the code proceeds to sign and only fails deep inside `AlgorithmSignatureMachine::complete`, where the code itself acknowledges this hole: `"The only known way to cause this ... is to deserialize a semantically invalid FrostKeys"` [5](#0-4)  — i.e., the deserialization is known to admit semantically invalid keys and the failure is deferred to an `InternalError` (or worse, `unreachable!()` in callers such as `share_internal` which treats `InvalidParticipant`/`InvalidSigningSet` as impossible [6](#0-5) ).

By contrast, the legitimate constructors (`dkg_dealer::key_gen`, `pedpop::KeyMachine::calculate_share`, `musig`) all establish `verification_shares` from proven data (committed polynomials, verified shares, or the key list containing `G * private_key`) before calling `ThresholdKeys::new` [7](#0-6) [8](#0-7) . Only the untrusted `read` path skips the credential↔role binding.

### Impact Explanation
Any consumer that loads `ThresholdKeys` (or `FrostKeys`) from a byte source it does not fully control accepts a claimed participant identity and an attacker-composed multisig. The holder of such crafted bytes can make a node believe it is participant `i` of a multisig at an attacker-controlled `group_key`, then produce signature shares that verify under `view.verification_share(i)` since the attacker set that share themselves — i.e., valid partial signatures for a group the node was never authorized into. Even when shares are inconsistent, the node enters a signing session under a forged identity and hits `unreachable!()`/`InternalError` paths, turning a deserialization flaw into a panic (integrity/availability impact). This is precisely the CVE's shape: a missing authorization check on a role claim, escalated through a routine code path.

### Likelihood Explanation
Reachability requires untrusted bytes reaching `ThresholdKeys::read`, which is an explicitly in-scope surface (key material imported from files, peers, or backups — e.g., the vector-import path in `crypto/frost/src/tests/vectors.rs` demonstrates such bytes are a real input format). Crafting the payload is trivial (LE u16s + points). The constraint is that the harm materializes only where an integrator accepts externally supplied serialized keys, which keeps this at Medium, matching the source advisory's severity.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), enforce the role↔credential binding:
- require `verification_shares[i] == C::generator() * secret_share` before constructing the keys;
- for `Interpolation::Constant`, consider validating the factors' consistency with the group key (e.g., `group_key == Σ factors[j] * verification_shares[j+1]`);
- reject identity/torsion verification shares at deserialization.
This ensures the deserialized structure cannot claim a participant index its secret share does not authorize.

### Proof of Concept
```rust
// Conceptual: craft serialized ThresholdKeys claiming participant index `i`
// with a secret share unrelated to verification_shares[i], or with
// verification shares fully controlled by the attacker.

let mut serialized = vec![];
serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
serialized.extend(C::ID);
serialized.extend(1u16.to_le_bytes());            // t = 1
serialized.extend(n_u16.to_le_bytes());           // n
serialized.extend(attacker_chosen_i.to_le_bytes()); // i: arbitrary role claim
serialized.push(1);                               // Interpolation::Lagrange
serialized.extend(attacker_secret.to_repr().as_ref());
for vs in attacker_controlled_verification_shares {
    serialized.extend(vs.to_bytes().as_ref());    // arbitrary points, e.g., G * s_j
}

// Succeeds: only i <= n and len == n are checked. secret_share is never
// bound to verification_shares[i], and group_key is derived from the
// attacker-supplied shares.
let keys = ThresholdKeys::<C>::read(&mut serialized.as_ref()).unwrap();
assert_eq!(keys.params().i(), Participant::new(attacker_chosen_i).unwrap());
// keys.group_key() is whatever the attacker's shares imply; keys will
// sign (and verify shares) under the attacker's chosen multisig, or
// trigger InternalError / unreachable!() deep in complete().
```
