## Analysis

The Code4rena report's core defect is: **a decimals‑scaling computation silently produces the wrong result when the two operands' decimal counts are in the "unexpected" order**, and the bug is hidden because nothing reverts — it just corrupts the number used downstream. Hyperbridge's `hyper-fungible-token` pallet has a direct, more severe analog: the ERC20 ↔ local‑balance conversion helpers use `u8::saturating_sub`, which silently collapses the scaling exponent to zero whenever the assumed decimal ordering is reversed, and this feeds directly into fund-moving `on_accept`/`on_timeout` logic.

### Title
Silent decimal-scaling collapse in `hyper-fungible-token` ERC20↔balance conversion causes fund loss/mispricing on bridge deliveries and timeouts - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance` and `convert_to_erc20` compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)` (or the reverse), which only produces correct results when `erc_decimals >= local_decimals`. When a governance-configured token pair has `erc_decimals < local_decimals` (e.g. a 6-decimal ERC20 bridged against an 18-decimal native/local asset — a completely ordinary configuration), the `saturating_sub` clamps to `0`, so the multiplier/divisor becomes `10^0 = 1` and **no scaling is applied at all**. The raw cross-chain amount is then used unmodified as the local balance (or vice versa), producing amounts that are off by many orders of magnitude, with no error, revert, or event.

### Finding Description [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions assume `erc_decimals >= local_decimals` (exactly the same class of assumption the Malt report flags — a decimals relationship that is only valid in one direction). `saturating_sub` never signals the violated assumption; it just returns `0`.

These helpers are invoked directly in the ISMP message handlers that move real value: [2](#0-1) 

```rust

    T::Decimals::get()
} else {

let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), source)
    .ok_or(HftError::DecimalsNotConfigured(source))?;
let amount = convert_to_balance::<...>(
    U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
    erc_decimals,
    decimals,

```

and identically in `on_timeout`: [3](#0-2) 

If `Precisions::<T>::get(asset, source)` (the per-asset ERC20 decimals recorded for a given EVM contract) is smaller than the local asset's/native's decimals — e.g. a 6-decimal stablecoin ERC20 bridged into an 18-decimal native/local balance, which is an entirely normal, non-adversarial configuration — `erc_decimals.saturating_sub(decimals)` evaluates to `0`. The divisor becomes `1`, so the raw 6-decimal ERC20 amount is minted/transferred **as-is** in 18-decimal terms (i.e. scaled down by 10^12 versus the correct amount). The symmetric `convert_to_erc20` path (used when dispatching outbound messages) has the same flaw in the opposite direction: it multiplies by `1` instead of the required scale-up factor when `local_decimals > erc_decimals`, producing an outbound amount value that is `10^(diff)` too small relative to what was actually escrowed/burned locally, or — depending on which side of the pair falls into the reversed case — too large when interpreted by the peer contract.

Unlike the original Malt finding (an unused, merely mislabeled return value), here the corrupted number **is** the amount actually minted, transferred, or refunded by `on_accept`/`on_timeout`, so the miscalculation is not cosmetic — it directly changes custody outcomes.

### Impact Explanation
This breaks the core Hyperbridge invariant that bridged assets must move "exactly once and only to the rightful beneficiary and amount":
- Inbound delivery (`on_accept`) can under-mint/under-transfer to the beneficiary by orders of magnitude (fund loss for the user, since the sender already paid/escrowed the correct amount on the source chain).
- Timeout refunds (`on_timeout`) use the same helper with the same decimal pair, so refunds are equally corrupted — a user whose message times out can be refunded a negligible fraction of their original escrowed amount, effectively locking/losing funds in `pallet_account()`.
- The outbound conversion (`convert_to_erc20`) has the mirrored failure mode, which can distort amounts dispatched to the EVM side.

No relayer, prover, or governance misbehavior is required — this triggers automatically for any token pair configured (via the normal `Precisions` admin flow, which is a routine setup step, not an attack) where the ERC20 side happens to use fewer decimals than the local/native asset, a configuration that is common in practice (e.g., 6-decimal stablecoins vs. 18/12-decimal native balances).

### Likelihood Explanation
Likelihood is high for any deployment that bridges a lower-decimal ERC20 (6 or 8 decimals, very common for stablecoins/BTC-pegged tokens) against a higher-decimal local/native asset (18 decimals, the Substrate/EVM-wrapped norm). The bug is silent — no revert, no distinguishing error — so it would not be caught by input validation and would likely only surface after funds are already lost or stuck.

### Recommendation
Replace `saturating_sub` with an explicit branch (as done correctly elsewhere in this same codebase, e.g. `_normalizeAmount` in `evm/src/utils/VWAPOracle.sol` and `adjustDecimals` in `sdk/packages/sdk/src/utils.ts`, both of which branch on `<`, `==`, `>` and scale in the correct direction each way):
```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }.to_string();
    dec_str.parse::<B>()
}
```
Apply the symmetric fix to `convert_to_erc20`, and add a test asserting correct round-tripping for `erc_decimals < local_decimals` configurations (the current test suite in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs` should be checked/extended for this case).

### Proof of Concept
1. Governance registers a token pair via `Precisions` where the EVM ERC20 representation has 6 decimals and the local/native asset has 18 decimals (e.g., a USDC-style bridge into a chain with an 18-decimal native currency) — an ordinary, expected configuration, not an attack.
2. A user calls the EVM-side `HyperFungibleToken` `send`/bridge function to bridge `1,000,000` raw units (1.0 token at 6 decimals) to a Substrate beneficiary. This is escrowed/locked correctly on the EVM side.
3. A relayer delivers the ISMP POST request; `on_accept` runs:
   - `decimals = 18` (local), `erc_decimals = 6` (from `Precisions`).
   - `erc_decimals.saturating_sub(decimals) = 6u8.saturating_sub(18u8) = 0`.
   - `amount = value / 10^0 = 1,000,000` (unchanged, still "1,000,000" but now interpreted as an 18-decimal balance, i.e. `0.000000000001` tokens instead of the intended `1.0`).
4. The beneficiary is minted/transferred `0.000000000001` tokens instead of `1.0` — a ~10^12x loss, with no revert, no warning event, and no path to recover the difference (it's not tracked or refundable since the message succeeded).
5. The same defect independently corrupts `on_timeout` refunds for the identical asset pair, and `convert_to_erc20` corrupts outbound amounts when the decimal relationship is reversed on that side.
