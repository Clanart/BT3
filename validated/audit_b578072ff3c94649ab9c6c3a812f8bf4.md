## Analysis

The core broken invariant in the StRSR report is: **a security-relevant value (`domainSeparator`) is derived from a mutable identity field (`name`) at initialization time, but is never recomputed when that identity field is changed later**, so all downstream consumers keep trusting a stale binding between the value and the identity.

The closest analog in GitHub Desktop is the automatic git-remote-URL rewriting logic that fires when Desktop "refreshes" the GitHub metadata for a repository. Desktop re-resolves a locally cloned repository to a GitHub API repository object purely by **owner/name strings**, and if that lookup succeeds it will silently rewrite the user's `origin` remote URL to whatever `clone_url` the API returns — without ever re-validating that the returned repository is *the same* GitHub repository (by immutable numeric id) that was originally associated with the local clone.

### Title
Git remote URL is silently rewritten based on an unverified owner/name lookup, allowing repo-squatting to redirect pushes - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes a repository's GitHub association (e.g. on account refresh, checkout, or periodic repository refresh), it resolves the current git remote to a GitHub API repository purely via the parsed `owner`/`name` of the remote URL, then re-fetches that repository from the API and — if certain URL-shape checks pass — rewrites the local `origin` remote to the API's `clone_url`. Nowhere in this flow is the immutable GitHub repository id compared between the previously-stored `GitHubRepository` record and the freshly-fetched `IAPIRepository`. This is structurally the same class of bug as the StRSR issue: the binding between "trusted identity" (the repository the user originally added) and "value used later" (the URL Desktop pushes/fetches with) is established once by a mutable name and is never re-verified against a stable identifier when it's refreshed.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` resolves the repository via `matchGitHubRepository(repository)`, which is implemented in `repository-matching.ts`: [1](#0-0) 

This function only compares the remote's hostname against known account endpoints and returns the parsed `owner`/`name` strings from the remote URL — it has no notion of the previously known repository identity.

That result is then used to call the GitHub API and, on success, `updateRemoteUrl` is invoked to potentially rewrite the local remote: [2](#0-1) 

`updateRemoteUrl` itself only checks that (a) the protocol hasn't changed, and (b) the *current* remote URL still equals the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited it), before overwriting the remote with the newly fetched `clone_url`: [3](#0-2) 

At no point in this path is `apiRepo.id` (the GitHub API's immutable numeric repository id) compared against the id stored in the local `GitHubRepository` record. The "identity" the code trusts is the mutable `owner/name` pair — exactly analogous to StRSR trusting the mutable `name` field for its domain separator instead of anchoring to something stable.

### Impact Explanation
If the `owner/name` that a locally cloned repository was originally bound to becomes available for reuse on GitHub — e.g. the original repository is renamed/transferred/deleted and an attacker registers a new repository under the vacated `owner/name` (a well-known "repo-jacking" pattern) — the next time Desktop performs a background refresh (account refresh, checkout, periodic repository refresh calling `repositoryWithRefreshedGitHubRepository`/`withRefreshedGitHubRepository`), it will fetch the attacker's repository object by name, and `updateRemoteUrl` will silently repoint the user's `origin` remote to the attacker's `clone_url`, since the URL-shape checks (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) can all be satisfied without any repository-id validation. This causes silent corruption of what the user subsequently pushes to (and potentially pulls/fetches from), fully unattended and without any prompt, which matches the listed valid-impact category of "silent corruption of what the user commits or pushes" driven by an attacker-controlled GitHub API object.

### Likelihood Explanation
This requires no local access, no malware, and no credential leakage — only that an attacker be able to create/rename a GitHub repository to occupy an `owner/name` combination that a victim's existing local clone still references (a scenario GitHub itself has publicly acknowledged as exploitable for renamed/transferred repos). The refresh path is triggered routinely (e.g., `refreshSelectedRepositoryAfterAccountChange`, checkout flows via `withRefreshedGitHubRepository`), so no unusual user action is required beyond normal use of Desktop over time.

### Recommendation
When refreshing GitHub repository metadata, persist and compare the GitHub API's immutable repository `id` (already available on `IAPIRepository`) against the `id`/`dbID` stored on the existing local `GitHubRepository` record before trusting `apiRepo.clone_url` for `updateRemoteUrl`, and before calling `upsertGitHubRepository`. If the id differs from what was previously associated with the repository, treat it as a different repository (surface a warning to the user) rather than silently rewriting the remote.

### Proof of Concept
1. User clones `https://github.com/alice/project` in Desktop; Desktop stores a `GitHubRepository` row with `owner=alice`, `name=project`, and the API-reported `id`.
2. `alice` renames/deletes `project` (or transfers ownership away), freeing the `alice/project` slug.
3. An attacker creates a new repository at `alice/project` (different underlying `id`) with `clone_url` pointing to their own repo.
4. On the next Desktop-triggered refresh (e.g. `_checkoutCommit` → `withRefreshedGitHubRepository`, or an account refresh calling `refreshSelectedRepositoryAfterAccountChange`), `matchGitHubRepository` resolves `owner=alice, name=project` from the still-unchanged local remote URL, `api.fetchRepository('alice','project')` returns the attacker's repository object, and `updateRemoteUrl` rewrites the local `origin` to the attacker's `clone_url` because the protocol and prior-URL checks pass and no `id` check exists to reject the mismatch.
5. The user's next `git push`/`git fetch` silently targets the attacker-controlled repository.

**Uncertainty:** I was not able to fully inspect `upsertGitHubRepository` in `repositories-store.ts` or the full body of `api.fetchRepository`/`IAPIRepository` within the tool-call budget to confirm with 100% certainty that no id-based reconciliation exists anywhere else in the pipeline; the visible code in `update-remote-url.ts` and the relevant slice of `app-store.ts` shows no such check, but a full audit of `repositories-store.ts`'s `upsertGitHubRepository` would be needed to rule out a de-duplication-by-id safeguard elsewhere. I recommend a Devin session with full repo access to verify this end-to-end before treating it as confirmed.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
