## Title
Silent, Attacker-Steerable Rewrite of the `origin` Remote URL via GitHub API `clone_url` — ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The report's broken invariant is: an owner/attacker can silently repoint a trusted identifier→address mapping (`bytes32 currency → token address`) without the affected party's consent, corrupting subsequent transfers. The Desktop analog is `updateRemoteUrl()`, invoked from `AppStore.repositoryWithRefreshedGitHubRepository()`, which silently repoints the local `origin` git remote to whatever `clone_url` the GitHub API (or GHE server) returns for the repository, based on weak heuristics rather than explicit user consent.

### Finding Description
`updateRemoteUrl` is called automatically every time Desktop refreshes a repository's GitHub metadata (on repository selection, background fetch cycles, and account refresh) via `AppStore.repositoryWithRefreshedGitHubRepository`: [1](#0-0) 

The actual rewrite logic only checks three conditions before silently calling `gitStore.setRemoteURL(...)`: [2](#0-1) 

1. `protocolsMatch` — new URL's protocol equals the current remote's protocol.
2. `remoteUrlUnchanged` — the *previously cached* `gitHubRepository.cloneURL` still matches the current git remote (i.e., the user hasn't manually customized `origin`).
3. `!urlsMatch` — the new API-provided `clone_url` differs from the current remote.

None of these checks validate that the *new* `clone_url` still points to the same owner/repo identity the user originally added — only that the protocol family and the previous known value are consistent. `setRemoteURL` itself performs no validation on the destination host: [3](#0-2) 

The `apiRepo` used to feed this function comes straight from `api.fetchRepository(owner, name)` against the account's configured `endpoint` (dotcom or a GitHub Enterprise Server), and the returned `clone_url` field is trusted verbatim: [4](#0-3) 

This exactly mirrors the `TokenVault` bug class: a mapping (`currency → address` / `repository identity → origin URL`) that is supposed to be a stable, user-approved association can be silently reassigned by an externally-controlled data source (`CurrencyController` return value / GitHub API `clone_url` response), and the existing "guards" (zero-address check / protocol+previous-URL-match check) do not verify the *new* value is legitimate — they only gate on incidental properties (non-zero / same-protocol), not on the actual identity being pointed to.

### Impact Explanation
If the attacker controls the API responses observed by Desktop for a given account's endpoint — explicitly in scope per this report's own "Valid Impact" category ("attacker controls ... a GitHub API object ... or a git remote/proxy response") — such as a compromised or malicious GitHub Enterprise Server, or a MITM position on that server's API traffic, they can return an attacker-chosen `clone_url` for the repository the user has open. Desktop will then, with no user prompt or confirmation dialog, run `git remote set-url origin <attacker-url>`. All subsequent user-initiated `git push` and `git fetch` operations on that repository transparently target the attacker's repository instead of the legitimate one. This is "silent corruption of what the user commits or pushes" as explicitly called out in the report's valid-impact list — commits/code the user believes are going to their real repo are pushed to an attacker-controlled destination instead, and future fetches can pull attacker-controlled history/code into the user's working tree without any visible indication that `origin` changed.

### Likelihood Explanation
This code path runs unconditionally and automatically: on every repository selection (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), and periodically for GitHub-Enterprise-backed repositories. It requires no unusual user action beyond normal use of Desktop against an Enterprise or compromised/MITM'd API endpoint. It does not require local access, admin rights, prior malware, or leaked credentials — only that the attacker control the API responses returned to Desktop's fetch of repository metadata for that endpoint, which matches the accepted attacker model in the report ("a git remote/proxy response").

### Recommendation
Before rewriting `origin` in `updateRemoteUrl`, verify that the new `clone_url` still identifies the *same* owner/repository (e.g., matches the `GitHubRepository`'s stable API `id`, not just protocol-family heuristics), and/or surface a confirmation dialog to the user (similar to the existing `UpstreamAlreadyExistsError` / `UpstreamAlreadyExists` dialog pattern already used for the analogous upstream-remote case) whenever the destination host or owner/name actually changes, rather than silently applying the update.

### Proof of Concept
1. User has a repository cloned from a GitHub Enterprise Server, with `origin` pointing to `https://ghe.example.com/org/repo.git`, tracked in Desktop.
2. Attacker compromises or MITMs the GHE server's API responses for `GET /repos/org/repo`.
3. User selects/refreshes the repository in Desktop, or the periodic background fetch cycle runs, triggering `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository('org','repo')`.
4. The attacker-controlled API response returns `clone_url: "https://ghe.example.com/org/repo-evil.git"` (same host/protocol, different repo) — `protocolsMatch` is true, `remoteUrlUnchanged` is true (user never manually changed origin), `urlsMatch` is false.
5. `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com/org/repo-evil.git')` with no prompt.
6. The user's next `git push` silently pushes their commits to `org/repo-evil` instead of `org/repo`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
