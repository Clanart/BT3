### Title
Escrow/fee-accounting collision via attacker-chosen input token colliding with the `TRANSACTION_FEES` sentinel key - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` stores escrowed input amounts in `_orders[commitment][token]`, keyed by the raw `address` derived from the user-supplied `order.inputs[i].token` bytes32. The same mapping is reused, with the reserved key `TRANSACTION_FEES`, to store the order's protocol fee amount. Because the input-token loop only guards against *duplicate* tokens within the inputs array (`if (_orders[commitment][token] != 0) revert InvalidInput()`) and never checks that a user-chosen token address is different from the `TRANSACTION_FEES` sentinel, a user can pick an input token whose address equals `TRANSACTION_FEES`. The fee-write that follows (`_orders[commitment][TRANSACTION_FEES] = order.fees;`) then unconditionally overwrites the escrow amount recorded for that "token," corrupting the record that `withdraw()` later relies on to release exactly the escrowed input amount and, separately, the transaction fee amount to the solver. This is directly analogous to the reported bug class: an unchecked/unvalidated key derived from attacker input aliases into a slot that was meant for something else, letting user input corrupt protocol-controlled accounting.

### Finding Description
In the escrow-crediting phase of `placeOrder`: [1](#0-0) 
each input's `token` (an arbitrary address chosen by the order's `user`, decoded from `bytes32(uint256(uint160(...)))`) is used directly as a mapping key into `_orders[commitment][token]`, with only a same-order duplicate check. Immediately after, if the order carries a fee, the same mapping is written again under the fixed sentinel key `TRANSACTION_FEES`: [2](#0-1) 

Nothing in this path rejects `token == TRANSACTION_FEES`. Since `TRANSACTION_FEES` is just another `address`-typed constant used as a map key (confirmed by its reuse across `IntentsBase.sol` and the Tron variant of `IntentGatewayV2.sol`), an attacker who knows its value can supply it as one of `order.inputs[i].token`. The duplicate-input check only compares against zero, so the first write (the real escrow amount for that "token") succeeds, and the subsequent unconditional fee write (`_orders[commitment][TRANSACTION_FEES] = order.fees;`) silently overwrites it, since it targets the identical storage slot.

On settlement, `withdraw()` (shown for the equivalent Tron-variant contract, same pattern applies to the mainline EVM contract) reads and decrements `_orders[body.commitment][token]` per input, and separately reads/deletes `_orders[body.commitment][TRANSACTION_FEES]` for fee redemption: [3](#0-2) 

Because both the escrowed "colliding" input and the transaction fee were coalesced into one storage slot at placement time, the value redeemed for that input during fill/withdrawal no longer matches the real amount of tokens actually pulled from the user (`safeTransferFrom`d at placement), while the true escrowed balance for that colliding address sits unaccounted for in the contract. Depending on the relative magnitudes of `reducedInputs[i].amount` vs `order.fees`, this can cause: value greater than the tracked accounting entry to be released to the solver (an accounting-driven overpay from the contract's real token balance), an underflow revert that locks the order (and the user's escrowed principal) permanently, or a token balance permanently stuck in the contract because its accounting entry was clobbered and is never independently redeemable.

### Impact Explanation
This lets any unprivileged order-placer corrupt the on-chain accounting Hyperbridge's IntentGateway uses to guarantee "escrow moves exactly once and to the rightful beneficiary." Possible outcomes are fund loss/lock for the user (escrow becomes unredeemable), or a beneficiary/solver receiving an amount unrelated to what was actually escrowed once the fee slot's value substitutes for the real input record. Both map onto the required impact classes: "stealing or loss of funds" and "logic attacks" against escrow/settlement accounting.

### Likelihood Explanation
No privileged actor, relayer, or prover is required — `placeOrder` is a public entry point and the `token` field of each `TokenInfo` is fully attacker-controlled (it's decoded from arbitrary `bytes32` input). The only precondition is knowing the exact value of the `TRANSACTION_FEES` constant, which is a compile-time constant baked into the deployed bytecode and therefore trivially discoverable by inspecting the contract or its ABI/source. Triggering it only requires the order to also carry a non-zero `order.fees`, which is an ordinary, common case.

### Recommendation
Reject any `order.inputs[i].token == TRANSACTION_FEES` (and any other reserved sentinel key) in the input-crediting loop of `placeOrder`, mirroring the existing duplicate-token check. More robustly, use a mapping keyed by a struct/enum discriminant (e.g., `mapping(bytes32 => uint256)` keyed by `keccak256(abi.encode(isFee, token))`) instead of overloading the plain `address` key space shared between real ERC-20 addresses and internal sentinels.

### Proof of Concept
1. Attacker inspects `IntentGatewayV2`/`IntentsBase` to obtain the constant value of `TRANSACTION_FEES`.
2. Attacker calls `placeOrder` with `order.inputs[0].token = bytes32(uint256(uint160(TRANSACTION_FEES)))` and `order.inputs[0].amount = X`, plus `order.fees = Y` (Y != 0).
3. Phase 3 escrow-credit loop runs: `_orders[commitment][TRANSACTION_FEES] = X` is written (since it's the only input and no prior duplicate exists).
4. Immediately after, because `order.fees > 0`, `_orders[commitment][TRANSACTION_FEES] = Y` overwrites the just-written `X`.
5. The contract has pulled `X` real tokens from the attacker via `safeTransferFrom` (as part of normal input handling) plus `Y` fee tokens, but the mapping now only records `Y` under the `TRANSACTION_FEES` key — the record of the `X`-token escrow is gone.
6. On settlement/`withdraw()`, the code that expects to release `X` back out for that "token" instead operates against the corrupted `Y` value, causing either a revert (funds permanently locked in escrow) or an incorrect transfer amount, depending on the relative sizes of `X` and `Y`.

I could not directly view the line where `TRANSACTION_FEES`'s concrete address value is declared (index limits truncated that portion of `IntentsBase.sol`), so the exact numeric value and byte-for-byte reachability of step 2 should be confirmed by reading `evm/src/apps/intentsv2/IntentsBase.sol` in full before treating this as fully proven; the mapping-collision mechanism itself, however, is directly supported by the cited `placeOrder`/`withdraw` code.
