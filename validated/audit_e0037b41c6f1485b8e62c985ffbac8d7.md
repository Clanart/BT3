Confirmed: `placeOrder` never validates that `order.inputs.length == order.output.assets.length`. It only checks `order.inputs.length == 0` and rejects duplicate output tokens [1](#0-0) . Escrow is credited for every entry in `order.inputs` regardless of `outputsLen` [2](#0-1) .

### Title
Same-chain fill releases escrow only up to `output.assets.length`, permanently trapping excess escrowed inputs once the order is marked filled - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` iterates only `outputsLen = order.output.assets.length` entries when building `escrowedInputs`, indexing `order.inputs[i]` by the same loop bound [3](#0-2) . If the user places an order where `order.inputs.length > order.output.assets.length`, only the first `outputsLen` input tokens are ever escrowed-and-released on fill; any input tokens at index `>= outputsLen` remain in `_orders[commitment][token]` forever with `_filled[commitment]` now set, blocking the only other exit path (cancellation).

### Finding Description
`placeOrder` escrows every entry in `order.inputs` and stamps the commitment over the full array [1](#0-0) , with no check that `inputs.length` matches `output.assets.length`. Cross-chain paths (`_fillCrossChain`/`onAccept`) release the full input set via `_withdraw(body, ..., true)` on redemption, since `WithdrawalRequest.tokens` there is built from the full input array. But the same-chain fill path in `_fillSameChain` builds `escrowedInputs`/`outputFills` as arrays sized `outputsLen`, and only ever references `order.inputs[i]` for `i < outputsLen` [4](#0-3) [5](#0-4) .

When every output asset in the (shorter) `output.assets` array reaches `amountFilled == totalRequired`, `isFullyFilled` stays `true` and the order is finalized: `_withdraw(body, false, true)` sets `_filled[commitment] = beneficiary` and transfers only the `outputsLen`-sized `escrowedInputs` [6](#0-5) . The remaining `order.inputs[outputsLen..]` tokens were escrowed at placement but never appear in any withdrawal request, so they stay recorded in `_orders[commitment][token]` at their original (unreduced) amount.

Recovery is blocked: `cancelOrder` → `_cancelSameChain` requires `_filled[commitment] == address(0)`... actually the top-level `cancelOrder` in the docs explicitly checks `_filled[commitment] != address(0)` and reverts with `Filled()` before dispatching to `_cancelSameChain` [7](#0-6) . Once the order is finalized by a normal fill, cancellation is permanently unavailable, and the excess escrow has no other code path that reads `_orders[commitment][token]` for indices beyond `outputsLen`.

This is structurally identical to the reported bug class: a process whose iteration/index bound (here `outputsLen`, there the entropy-slot count) is smaller than the full domain of stored value (here `inputs.length`, there `770*13` slots vs. 10,000 mintable), so a legitimately-created value silently falls outside the reachable range and becomes permanently unrecoverable once the enclosing state is finalized irreversibly (order marked filled / generation incremented).

### Impact Explanation
Direct, permanent loss of the user's own escrowed tokens with no admin, governance, or recovery path once the order fills — the tokens sit in the contract's balance forever, unassignable to any beneficiary, matching "loss of funds" / "permanent lock" impact categories. Because `_filled[commitment]` is a normal user-facing invariant (used everywhere to gate cancel/fill), there is no privileged sweep for surplus locked in `_orders` (the `SweepDust`/dust-sweeping paths only cover explicitly tracked `DustCollected` amounts, not silently-orphaned `_orders[commitment][token]` balances for untouched input indices).

### Likelihood Explanation
Reachable by any ordinary unprivileged user constructing an `Order` with `inputs.length != output.assets.length` (a valid ABI-encodable struct; nothing in `placeOrder` or the `Order` schema enforces equal lengths) and having *any* solver perform a normal same-chain fill that completes every output asset. No malicious relayer, prover, or governance action is required — a solver simply filling the order as designed triggers the loss for the user who placed it (or for a solver who is later shorted if the array-length relationship runs the other way, though the primary victim here is the order owner's excess escrow).

### Recommendation
In `placeOrder`, enforce `order.inputs.length == order.output.assets.length` (reverting with `InvalidInput()` otherwise), matching the 1:1 index correspondence that `_fillSameChain` implicitly assumes. Alternatively, make `_fillSameChain` iterate and release escrow over the full `order.inputs.length` rather than `outputsLen`, and only mark `isFullyFilled` once all output *and* all extra input entries are accounted for.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [TokenInfo(USDC, 1000e6), TokenInfo(DAI, 500e18)]` but `order.output.assets = [TokenInfo(WETH, 1e18)]` (i.e., `inputs.length = 2`, `output.assets.length = 1`). Both USDC and DAI get escrowed under the resulting `commitment` in `_orders[commitment][USDC]` and `_orders[commitment][DAI]`.
2. A solver calls `fillOrder` supplying `outputs = [TokenInfo(WETH, 1e18)]`. `_fillSameChain` loops `i` from `0` to `outputsLen-1 = 0` only, computing `escrowedInputs[0]` from `order.inputs[0]` (USDC) and releasing exactly that to the solver. `isFullyFilled` becomes `true` since the single output asset is fully filled.
3. `_withdraw(body, false, true)` executes: `_filled[commitment] = solver`, USDC escrow decremented and transferred to solver. The DAI entry at `order.inputs[1]` was never referenced.
4. `_orders[commitment][DAI] == 500e18` remains untouched in contract storage. `cancelOrder` now reverts with `Filled()` for this commitment. No function in `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents` ever again reads or transfers `_orders[commitment][DAI]` — the 500 DAI is permanently stranded in the gateway contract.
