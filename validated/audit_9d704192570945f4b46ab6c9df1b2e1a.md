### Title
GitHub Desktop silently repoints a repository's `origin` remote to an attacker-claimed GitHub repo after an owner/name-based (non-ID) re-match - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`repositoryWithRefreshedGitHubRepository` periodically re-resolves the locally-tracked repository against the GitHub API by parsing the current remote URL into `{owner, name}` and calling `api.fetchRepository(owner, name)` — a lookup keyed purely on the mutable owner/name strings, never on the GitHub repository's stable numeric id. Whatever `IAPIRepository` object comes back for that owner/name is then trusted enough to have Desktop rewrite the local git `origin` remote URL to match it, via `updateRemoteUrl`. If the owner/name pair is reclaimed by a different, attacker-controlled repository (GitHub allows username/repo renames, and old names become squattable), Desktop will silently retarget the user's push destination to the attacker's repository without any identity check or user prompt.

### Finding Description
The refresh path is:

- `repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4874-4914`) calls `this.matchGitHubRepository(repository)` to get `{account, owner, name}`, then `api.fetchRepository(owner, name)` (`app/src/lib/api.ts:973-988`, `GET repos/{owner}/{name}`). [1](#0-0) 
- The underlying matcher, `matchGitHubRepository`, derives `owner`/`name` purely by string-parsing the current remote URL and matching the account's hostname — there is no comparison against a persisted repository id. [2](#0-1) 
- If `repository.gitHubRepository` is already set, the freshly fetched `apiRepo` (identified only by owner/name) is handed to `updateRemoteUrl`, which — if the *protocol* of the old and new URL match and the current remote still textually matches the previously cached `gitHubRepository.cloneURL` — calls `gitStore.setRemoteURL(...)` to physically rewrite the on-disk git remote to `apiRepo.clone_url`. [3](#0-2) 

The broken invariant is identity continuity: nothing in this path verifies that the repository object returned for `{owner, name}` today is the *same* repository (by GitHub's immutable numeric id) that Desktop originally associated with this local clone. `urlMatchesRemote`/`urlsMatch` only compare hostname/owner/name strings, which is exactly the attacker-controllable value in a rename/squatting scenario, not a security boundary. [4](#0-3) 

This mirrors the reported bug class precisely: a trusted reference (the delegate contract address / here, the GitHub repository object bound to owner+name) is checked once, then silently substituted by an attacker between checks, and the caller (Desktop) acts on the new, attacker-controlled object without re-verifying its identity — exactly the "verify by address/hash before acting" gap the report calls out.

### Impact Explanation
If a repository or account is renamed on GitHub (a normal, common action) and an attacker registers the vacated `owner/name` with their own repository, any Desktop user whose local clone still has an `origin` remote pointing at the old `owner/name` — and who has Desktop refresh GitHub repo info in the background (this happens periodically via repository indicator refresh, account-change refresh, and pre-push refresh) — will have Desktop **silently rewrite `origin`'s URL** to the attacker's `clone_url`. Subsequent `git push` operations from that user then push their code/history straight into the attacker's repository, i.e., silent corruption of what the user pushes and unauthorized disclosure of code/commits to a third party. It can also poison PR/branch-protection/permission state associated with the local repository, since `repositoryWithRefreshedGitHubRepository` also calls `upsertGitHubRepository`/`refreshBranchProtectionState` using the same misresolved `apiRepo`. [5](#0-4) 

### Likelihood Explanation
This requires no local access, no credentials, and no unusual user action — only that: (1) the user previously had a GitHub remote for an owner/name that later becomes available (a routine consequence of GitHub renames), and (2) the attacker claims that owner/name on GitHub, a normal unprivileged action. Desktop performs this refresh automatically in the background (it's not gated behind an explicit "check for updates" user click), so the substitution happens without any user awareness. The only mitigating factor is `protocolsMatch` and `remoteUrlUnchanged` gating in `updateRemoteUrl`, but both are satisfied by design in the ordinary rename-then-squat sequence, since the stale cached `cloneURL` still textually matches the still-unmodified on-disk remote.

### Recommendation
- Bind the GitHub repository association to the immutable numeric repository `id` returned by the API (already present on `IAPIRepository`/`GitHubRepository` records) rather than re-deriving/re-trusting objects solely from `owner`/`name` string matches.
- In `updateRemoteUrl`, refuse to auto-update the remote URL (or warn the user first) if the newly fetched `apiRepo.id` differs from the previously stored repository id for that association — treat an id mismatch as "this is a different repository," not a rename.
- Short term: add an explicit confirmation prompt before silently rewriting `origin`'s URL, mirroring the report's recommendation to verify the destination's identity before trusting it for an operation with lasting effects (a push).

### Proof of Concept
1. User A has GitHub Desktop tracking a local clone with `origin` = `https://github.com/alice/project.git`, associated with `GitHubRepository{owner: alice, name: project, cloneURL: https://github.com/alice/project.git}`.
2. Alice renames her GitHub account (or the repo) — GitHub frees the `alice/project` slug.
3. Attacker registers a new GitHub account named `alice` (or otherwise reclaims the slug) and creates a repository named `project`.
4. Desktop's background refresh (`repositoryWithRefreshedGitHubRepository`) runs, calls `api.fetchRepository('alice', 'project')`, which now returns the attacker's repository object with `clone_url: https://github.com/alice/project.git` (same string, attacker-owned).
5. `updateRemoteUrl` sees `protocolsMatch === true` and `remoteUrlUnchanged === true` (cached cloneURL textually still equals the on-disk remote) — the branch that actually calls `setRemoteURL` isn't even needed here since the URL text is identical, demonstrating that Desktop has no way to detect the underlying repository identity changed; it will happily continue treating `origin` as authoritative and push there on the user's next `git push`, sending the user's code to the attacker's repository. [6](#0-5)

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
