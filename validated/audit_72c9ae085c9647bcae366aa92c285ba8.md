### Title
`writeFn()` commits approve+calldata state before the post-condition balance check, leaking ERC20 allowance/state on failed IBC callbacks - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
The reported LiFi bug is a class of "cross-chain receiver executes attacker-influenced calldata against a token-holding account without properly reverting/clearing allowances on failure." The Cosmos EVM analog is `ContractKeeper.IBCReceivePacketCallback`, which grants an ERC20 `approve()` to an attacker-supplied `contractAddress` on behalf of a per-sender "isolated address," then executes attacker-supplied `cbData.Calldata` against that contract, and only *afterwards* checks that the isolated address's token balance is zero.

### Finding Description
In `x/ibc/callbacks/keeper/keeper.go`, `IBCReceivePacketCallback`:
1. Derives an isolated address per `(destChannel, sender)` pair [1](#0-0) .
2. Approves the attacker-controlled `contractAddr` (taken directly from the packet memo `dest_callback.address`) to spend the isolated address's ERC20 tokens [2](#0-1) .
3. Executes attacker-controlled `cbData.Calldata` against `contractAddr`, with `msg.sender` = isolated address [3](#0-2) .
4. Calls `writeFn()` to commit the cached context (approve + calldata execution) **before** validating that the isolated address's token balance is zero [4](#0-3) .
5. Only after committing, it checks `receiverTokenBalance != 0` and returns an error if the check fails — but this error can no longer roll back the already-committed `approve()` and calldata execution.

Because the isolated address is deterministic and reused for all packets from the same `(sender, channel)` pair (as seen in test helper `types.GenerateIsolatedAddress(channelID, sender)`), an attacker fully controls both the `contractAddress` and `calldata` fields via IBC packet memo. An attacker can supply a `contractAddress`/`calldata` combination that:
- Deliberately leaves a non-zero allowance for a malicious spender contract (e.g., approves without fully consuming/decreasing it, or triggers a benign no-op call), causing the overall function to return an error (since the balance check fails) — but the `approve()` state change has already been persisted via the premature `writeFn()`.
- On a subsequent legitimate transfer that reuses the same isolated address (same sender/channel), the previously-approved malicious contract retains its allowance and can drain any tokens later deposited into the isolated address without further packet-level authorization, effectively stealing funds analogous to the LiFi `Receiver` "leftover allowance" bug.

### Impact Explanation
This breaks the ERC20 accounting invariant (allowance/balance consistency) for a precompile-mediated/ERC20-representation asset path in `x/erc20`/IBC-callbacks — an attacker-controlled contract can retain unauthorized spending rights over an isolated address that legitimately holds bridged user funds, enabling unauthorized extraction of user funds on a later deposit to the same isolated address. This matches the "Critical … theft or unauthorized extraction of user funds … token-pair-backed balances" allowed impact category.

### Likelihood Explanation
Likelihood requires: (a) the erroring path being reached (attacker's calldata leaves nonzero balance to trigger the failing check while still executing far enough to have `writeFn()` called — which happens whenever the calldata call succeeds but the resulting balance is nonzero); and (b) a second, legitimate deposit later landing in the same isolated address (same sender+channel), which is a normal occurrence for repeat bridge users. Both an attacker-authored memo and a plausible follow-up transfer are unprivileged, ordinary IBC transactions, making this reachable without special privileges. However, exploiting it fully depends on convincing/legitimate future transfers reusing the exact same isolated address, and I was not able to fully confirm within tool budget whether ibc-go's outer `ProcessCallback` wraps this call in its own cache-context that would additionally discard `ctx`'s writes on error return from `IBCReceivePacketCallback` (which could mitigate persistence). This uncertainty should be verified in code (ibc-go's callbacks middleware `ProcessCallback`) before treating this as conclusively exploitable.

### Recommendation
Move the token-balance validation (and any allowance-clearing) before calling `writeFn()`, performing it against `cachedCtx` so a failing post-condition discards all approve/calldata side effects atomically. Additionally, explicitly reset the ERC20 allowance (`approve(contractAddr, 0)`) after the calldata execution regardless of success/failure, before persisting state, so no residual allowance can survive on the isolated address between different packets from a bridge with a compromised/malicious `dest_callback.address` value.

### Proof of Concept
1. Attacker sends an ICS-20 transfer with memo `dest_callback: { address: <MaliciousContract>, calldata: <crafted> }` where `MaliciousContract`'s function, when called, does not transfer the full approved amount out of the isolated address (leaving `receiverTokenBalance != 0`), but performs internal bookkeeping that keeps the allowance non-zero.
2. `IBCReceivePacketCallback` executes `approve()` and the calldata call inside `cachedCtx`, then calls `writeFn()`, committing both to `ctx` (the underlying store).
3. The post-check `receiverTokenBalance.Cmp(big.NewInt(0)) != 0` fails and the function returns an error — but the `approve(MaliciousContract, amount)` granted in step 2 remains persisted in state for the isolated address.
4. On a subsequent bridge transfer from the same sender via the same channel (reusing the same isolated address), `MaliciousContract` calls `transferFrom(isolatedAddress, attacker, amount)` using the still-valid allowance to steal the newly received tokens, without needing the isolated address's holder to authorize anything for that new packet.

(Full confirmation of steps 3–4 requires validating ibc-go's `ProcessCallback` semantics for cache-context handling on `ContractKeeper` errors, which could not be completed within the available tool budget.)
