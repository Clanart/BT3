### Title
Partial-commit line selection is applied against a re-fetched diff, silently corrupting what gets committed - ([File: app/src/lib/git/apply.ts])

### Summary
The bug-class from the report is: a value (yToken `pricePerShare`) is computed against the state of the world *at read time*, but the action that consumes that value (a withdrawal/settlement) is executed against a *later, changed* state, so the value used no longer matches reality and the wrong outcome is silently produced. The Desktop analog is line-based partial-commit selection: the UI computes which lines are "selected for commit" against a diff fetched at time T1, but the staging step recomputes the diff at time T2 and blindly reapplies the same line-index-based selection to it, assuming the two diffs are line-index-compatible.

### Finding Description
When a user stages a subset of lines in a file (a "partial commit"), the selection state is a `DiffSelection` bitmask keyed by absolute line indices into a specific `ITextDiff` (`hunk.unifiedDiffStart + lineIndex`), computed from a diff obtained via `getWorkingDirectoryDiff` when the Changes view loads/refreshes the diff for the selected file [1](#0-0) .

When the user actually commits, `stageFiles` routes partially-selected files to `applyPatchToIndex` [2](#0-1) . That function does **not** reuse the diff/selection pair that was validated/shown to the user — it independently re-invokes `getWorkingDirectoryDiff(repository, file)` at commit time and immediately calls `formatPatch(file, diff)` on this freshly fetched diff using the file's existing `selection` object: [3](#0-2) .

`formatPatch` walks the new diff's hunks/lines and decides inclusion purely via `file.selection.isSelected(absoluteIndex)`, i.e. by numeric line-index lookup, with no check that the new diff's hunk layout/line count/content matches the diff the indices were derived from: [4](#0-3) .

App Store's own comment acknowledges this exact hazard for the *display* path — when a diff reload happens while the Changes view is open, it explicitly recomputes `selectableLines` and drops selections that no longer correspond to real lines, because "the diff might have changed dramatically since last we loaded it": [5](#0-4) . That reconciliation only runs for the UI's own re-render path (`updateChangesWorkingDirectoryDiff`), not for the commit/staging path in `applyPatchToIndex`, which fetches its own independent diff and reuses raw indices without going through this reconciliation.

### Impact Explanation
If the working-directory file content changes between the time the user visually selects lines to include (based on the diff shown) and the moment `_finishCommitCreation`/`createCommit` actually runs `stageFiles` → `applyPatchToIndex` (e.g., an external editor autosave, a pre-commit formatter/linter, a build step, or another process writing to the file while the commit dialog is open), the absolute line indices in the stale `DiffSelection` no longer correspond to the same lines/hunks in the newly fetched diff. Because `formatPatch` trusts the indices without validating hunk shape, this can cause the committed patch to include unintended lines, omit intended lines, or misapply additions/deletions from the wrong hunk — i.e. silent corruption of what the user actually commits and eventually pushes, without any error or user-visible warning. This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires no attacker privilege beyond the normal capability already assumed in scope: the content of a tracked working-directory file changes between diff-render time and stage/commit time. This is a realistic, unprompted condition (auto-formatters, format-on-save, linters, generated files, git hooks, or even a fast typist editing before the async commit resolves) rather than a contrived local-admin scenario, so likelihood is moderate — it depends on timing/race between UI diff render and the async commit execution path, and is more likely with larger diffs (slower fetch/format) or slower disk/CI environments.

### Recommendation
`applyPatchToIndex` should not silently re-fetch and trust a brand-new diff against a possibly-stale `DiffSelection`. Either (a) pass the exact diff object that was used to compute the selection through the commit call chain instead of re-fetching inside `applyPatchToIndex`, or (b) validate that the newly-fetched diff's hunk boundaries/line content are unchanged (or reconcile selection via the same `withSelectableLines`-style logic already used in `app-store.ts`) before calling `formatPatch`, aborting or re-prompting the user if the file changed underneath the pending commit.

### Proof of Concept
1. Open a repo in Desktop with a modified tracked file containing multiple hunks; select only specific lines/hunks for the commit (partial staging) via the diff view (loads diff at T1, `unifiedDiffStart`-indexed selection is stored on `WorkingDirectoryFileChange`).
2. Before clicking "Commit" resolves (or while another process, e.g. a formatter/save action, is writing to the same file), let the file content on disk change such that hunk boundaries shift (add/remove lines above the selected hunk).
3. Trigger the commit: `stageFiles` → `applyPatchToIndex` re-fetches `getWorkingDirectoryDiff` (T2) and calls `formatPatch(file, diffAtT2)` using the selection indices computed from the diff at T1.
4. Inspect the resulting commit: the staged/committed hunk content corresponds to different lines than what the user visually selected, demonstrating silent corruption of the committed content — reproducible by unit-testing `formatPatch` with a `DiffSelection` built from diff A but applied to a structurally different diff B for the same file, as already exercised (without the mismatch scenario) in [6](#0-5) .
