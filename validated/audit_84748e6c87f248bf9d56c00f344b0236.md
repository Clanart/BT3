Confirmed: `AppProxyVerification#query_string_valid?` only verifies the HMAC signature over the query parameters — it never checks that the `timestamp` parameter is fresh or has not been previously consumed.### Title
App Proxy request signature has no timestamp/freshness enforcement, enabling indefinite replay of a signed request - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies only that the `signature` query parameter matches an HMAC of the remaining query parameters. It never checks that the `timestamp` parameter (which Shopify includes in every app-proxy request) is recent or that the signed query string has not already been consumed. This is the same root cause pattern as the reported `emitLoan()` finding: a validly signed payload can be captured once and replayed an unlimited number of times because there is no nonce/one-time-use/expiration enforcement server-side.

### Finding Description
`query_string_valid?` deletes the `signature` param, recomputes the HMAC over the rest of the query string, and compares it with `secure_compare`: [1](#0-0) 

`verify_proxy_request` is wired as a `before_action` for any controller that includes this concern, and is the only gate protecting the endpoint (CSRF protection is explicitly skipped): [2](#0-1) 

The `timestamp` field is present in the query string and is included in the HMAC computation, but its value is never compared against `Time.now` or any expiry window — it is treated as opaque signed data, not as a freshness token. The test suite confirms the verifier accepts a fixed, years-old timestamp (`1466106083`, i.e. 2016) as valid indefinitely as long as the signature matches: [3](#0-2) 

Because app-proxy requests are GET requests forwarded from `https://{shop}/apps/{proxy}` to the app's configured proxy URL, the full signed query string (including `signature` and `timestamp`) is visible to any client that can trigger or observe navigation to that proxied page (e.g. by viewing page source, browser dev tools/network tab, or a shared link containing the same query string). Any such observer can replay the identical URL against the app's `app_proxy` endpoint from outside Shopify's infrastructure, with no time bound, since the code never checks recency.

### Impact Explanation
Any party who captures a legitimately signed app-proxy request (e.g., a customer browsing a merchant's storefront, or anyone with access to the resulting URL) can replay that exact request against the app's proxy controller indefinitely. Depending on what the app-proxy endpoint does (the generator scaffolds a simple render, but real apps commonly perform state-changing or metered actions — e.g., issuing discounts, recording loyalty points, submitting reviews, redeeming a one-time code), a replay can force repeated/duplicate execution of that action under the merchant's authenticated context, exactly mirroring the reused-signature impact described in the report (repeated unintended execution of an operation that should only happen once). This is a forged/accepted-replay-of-signed-request class issue in the app-proxy authentication layer that `shopify_app` ships and documents as the standard verification mechanism for these routes.

### Likelihood Explanation
Reachable by any anonymous or unrelated party who can obtain a valid signed app-proxy URL — no privileged access or leaked secret is required, since query strings sent to app-proxy URLs are visible client-side (unlike server-to-server webhook HMAC payloads). The `timestamp` parameter exists specifically to support freshness checks, but `AppProxyVerification` never uses it that way, so the exploitability depends entirely on how the consuming app's action responds to a duplicate request — some app-proxy actions are idempotent, but nothing in `shopify_app` prevents or warns against building non-idempotent handlers on top of this concern, and the docs/generator do not mention any replay risk.

### Recommendation
Add a freshness check against the `timestamp` parameter (reject requests older than a small delta, similar to the webhook `X-Shopify-Hmac` combined with the mitigation applied for the `emitLoan()` finding — i.e., enforce a short acceptance window), and encourage/support one-time-use tokens or idempotency keys for app-proxy actions that trigger state changes, documenting this expectation in `docs/shopify_app/engine.md`.

### Proof of Concept
1. A merchant's storefront page makes (or a merchant/developer shares) a link to the app's app-proxy path, e.g. `https://shop.myshopify.com/apps/my-app?shop=some-random-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd`.
2. Any observer (customer, anyone who received/inspected the URL) copies this exact query string.
3. They replay the identical request directly to the app's `/app_proxy/...` endpoint at any later time — as shown in the test, `query_string_valid?` accepts this even though `timestamp=1466106083` corresponds to 2016, proving there is no expiry enforcement: [3](#0-2) 
4. `verify_proxy_request` passes, and the controller action executes again, exactly as it did the first time, with no way for the app to distinguish a legitimate fresh request from a replayed one. [4](#0-3)

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
