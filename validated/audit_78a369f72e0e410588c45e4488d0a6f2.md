Audit Report

## Title
Unbounded, unindexed `getProgramAccounts` scan lets a single low-rate RPC client exhaust CPU/memory - ([File: rpc/src/rpc.rs])

## Summary
`get_filtered_program_accounts` in `rpc/src/rpc.rs` takes an unbounded `else` branch whenever the `AccountIndex::ProgramId` secondary index is not enabled (the default validator configuration), scanning every account owned by an arbitrary, caller-supplied `program_id` with no byte/count cap before returning results. This is in direct contrast to its sibling `get_filtered_indexed_accounts`, which passes `self.config.scan_results_limit_bytes` down to bound the scan. A single unauthenticated `getProgramAccounts` RPC call against a program with many owned accounts (e.g., the System Program) can therefore force full materialization of a large in-memory result set, degrading or crashing the RPC node.

## Finding Description
The unindexed path in `get_filtered_program_accounts` explicitly notes it does not enforce a limit ("this path does not need to provide a mb limit because we only want to support secondary indexes") and calls `bank.get_filtered_program_accounts(&program_id, ...)` with only a predicate filter, no size bound. This flows into `Accounts::load_by_program_with_filter`, which calls `AccountsDb::scan_accounts` with `&ScanConfig::default()` — no `byte_limit_for_scan` is threaded through at all. `scan_accounts` walks the entire accounts write-cache plus the entire accounts index for every pubkey visible from the bank's ancestors, cloning each matching account's full data into a `Vec<KeyedAccountSharedData>` collector with no early-abort based on accumulated size. The only existing safeguard, `scan_results_limit_bytes`, is wired solely into the indexed sibling `get_filtered_indexed_accounts`; it is never propagated to the non-indexed path used whenever the operator has not opted into `--account-index program-id`, which is the default state for most validators/RPC nodes due to the extra memory overhead of maintaining secondary indexes.

## Impact Explanation
This matches the "single-client low-rate RPC crash/degradation" impact category: an unprivileged, unauthenticated caller can send one `getProgramAccounts` request naming a program with a large number of owned accounts (trivially satisfied by `system_program::id()` on any populated cluster, or a program the attacker deploys and populates with many accounts at low on-chain cost) and force the node to allocate and return a potentially very large in-memory response inside a `spawn_blocking` task, exhausting memory/CPU and degrading service for other RPC clients on that node.

## Likelihood Explanation
Likelihood is high on RPC nodes without `--account-index program-id` enabled. No stake, signature, or transaction submission is required — only network access to the JSON-RPC endpoint and knowledge of a program with many owned accounts, both trivially available to any unprivileged actor.

## Recommendation
Thread `scan_results_limit_bytes` (or an equivalent limit) into the non-indexed `get_filtered_program_accounts` call path in `rpc/src/rpc.rs`, propagating it through `Bank::get_filtered_program_accounts` → `Accounts::load_by_program_with_filter` → `AccountsDb::scan_accounts`'s `ScanConfig`, so the scan aborts once accumulated result size exceeds a configured maximum regardless of secondary-index configuration. Consider also requiring at least one selective filter or enforcing pagination for unfiltered `getProgramAccounts` calls when no secondary index is enabled.

## Proof of Concept
1. Run an RPC node without `--account-index program-id`.
2. Target `system_program::id()` (or a program owning many accounts).
3. Issue `{"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["<program_id>"]}` with no filters.
4. Trace the call through `get_filtered_program_accounts`'s unindexed `else` branch → `bank.get_filtered_program_accounts` → `Accounts::load_by_program_with_filter` → `AccountsDb::scan_accounts`, observing no byte/count limit is applied before the full result set is materialized and returned, causing memory/CPU exhaustion proportional to the number of accounts owned by the target program.
