### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` enables memory exhaustion DoS - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary

`ThresholdKeys::read` deserializes `n` (a `u16` fully controlled by the input bytes) and immediately performs `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector, plus iterates `1 ..= n` performing `read_G` into a `HashMap`, before `ThresholdParams::new` validates the parameters at the end of the function. A ~11-byte crafted input therefore forces an allocation of up to 65,535 scalars (~2 MiB for 32-byte fields) and drives allocation/parsing work orders of magnitude larger than the input, analogous to the unbound-cardinality memory exhaustion of CVE-2023-45142 (CWE-770).

### Finding Description

In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, and `i` from raw input bytes:

```rust
// crypto/dkg/src/lib.rs:604-623
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  ...
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
```

`n` comes straight from the wire (`u16::from_le_bytes`, up to 65535) and is used to size `Vec::with_capacity` and to bound the scalar/point read loops *before* `ThresholdParams::new(t, n, i)` is invoked at the end of the function to reject inconsistent parameters. There is no early bound check on `n` relative to `t`, the remaining input length, or any protocol maximum (the validator set in Serai is far smaller than 65535). Only after all allocations and reads does `ThresholdKeys::new` validate `verification_shares.len() == n` and `t <= n`.

An untrusted caller feeding bytes to `ThresholdKeys::read` can claim `n = 0xFFFF` with interpolation byte `0` and supply just enough bytes to satisfy a large prefix of the reads: each pushed `C::F` is 32 bytes, each `C::G` 32+ bytes, so a ~2 MiB+ live allocation (plus `HashMap` growth for `verification_shares`) is driven by an input claiming those elements — and even the pure `with_capacity(65535)` case is a ~2 MiB allocation from an 11-byte input. The reader only fails once the byte stream is exhausted, so the attacker controls the amplification factor.

### Impact Explanation

A remote, unprivileged party that can feed crafted bytes to `ThresholdKeys::read` (key-material deserialization is an explicitly in-scope untrusted-byte sink) can force disproportionate heap allocations per request/message. Repeated submissions cause sustained allocator pressure and memory exhaustion of the host process — the same CWE-770 DoS class as the otelhttp advisory — degrading or crashing the node handling threshold-key material (e.g., during key-import/recovery paths where serialized `ThresholdKeys` are consumed).

### Likelihood Explanation

The reachability bar is low: the function is a public deserialization API accepting arbitrary `io::Read` input. The trigger requires only setting `interpolation = 0` and a large `n`; no valid signature, proof, or participant status is needed. The amplification is transient per call (the `Vec` is dropped on the eventual `Err`), but a sustained stream of such inputs yields sustained memory churn and peak RSS far exceeding inbound bandwidth — a practical DoS, though bounded to ~64K elements per message, which caps severity at Medium rather than High.

### Recommendation

Validate `t`, `n`, and `i` via `ThresholdParams::new` *immediately* after reading them, before any allocation, and reject `n` above a protocol-sane maximum. Additionally, avoid `Vec::with_capacity(n)` / pre-counted loops trusting `n`; either cap `n` to the expected participant count or grow vectors incrementally so allocation tracks bytes actually present in the input.

let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
