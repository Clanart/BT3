### Title
`HostManager.onAccept` accepts governance requests from any module on Hyperbridge without checking `request.from` - ([File: evm/src/core/HostManager.sol])

### Summary
`HostManager.onAccept` — the sole gate protecting `EvmHost.withdraw()` (drains bridge revenue) and `EvmHost.updateHostParams()` (rewrites admin, handler, consensusClient, feeToken, etc.) — authenticates an incoming cross-chain message using only the source **chain id**, never the source **module id**. Every other `IApp` implementation in this same codebase authenticates both fields. This is a concrete violation of the stated Hyperbridge invariant that "cross-chain admin or host-management effects must not be reachable through... wrong module bindings."

### Finding Description
`HostManager.onAccept` is: [1](#0-0) 

It checks `request.source.equals(IHost(_params.host).hyperbridge())` — i.e. only that the message originated from the Hyperbridge parachain's state-machine id — and then unconditionally executes whatever `OnAcceptActions` (`Withdraw` or `SetHostParam`) is encoded in `request.body`, calling straight into `IHostManager(_params.host).withdraw(...)` or `updateHostParams(...)`.

It never checks `request.from`, i.e. it never verifies *which module/pallet on the Hyperbridge chain* dispatched the message. Contrast this with every other privileged/asset-moving `IApp` in the same repo, which all validate `request.from` against a registered module address, in addition to the source chain: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The bandwidth-manager documentation independently flags this exact class of gap for its own manager contract ("no module-id lookup"), confirming the pattern is a recognized risk area in this codebase: [6](#0-5) 

On the Substrate side, `from` is not derived or enforced by `pallet-ismp`'s dispatcher — it is whatever byte string the calling pallet chooses to put in `DispatchPost.from`, and it is carried through unchanged into the on-chain `PostRequest`: [7](#0-6) 

Today, the only pallets that target a `host_manager` address (`pallet-host-executive`'s `update_host_params`/`withdraw`, `pallet-bandwidth`'s `dispatch_withdraw`) gate their calls behind `HostExecutiveOrigin`/`AdminOrigin`: [8](#0-7) 

So `EvmHost.withdraw`/`updateHostParams` are *currently* only reachable through those admin-gated extrinsics. But `HostManager.onAccept`'s check has no dependency on that fact — it is structurally missing the module-binding check that the Hyperbridge Pivots require ("Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow"). Any current or future pallet on the Hyperbridge runtime capable of calling the generic `IsmpDispatcher::dispatch_request` with an attacker/caller-influenced `to` (destination module) field — the exact pattern already used by the permissionless, `ensure_signed`-only `pallet_ismp_demo::dispatch_to_evm` extrinsic, which lets any signed account choose an arbitrary destination `module` address on any connected EVM chain — could target `HostManager`'s address. Because the check in `onAccept` is chain-id-only, such a message would pass authentication purely on the basis that it originated from "the Hyperbridge chain," regardless of which module dispatched it or whether that module intended to move host-manager funds.

### Impact Explanation
A successful bypass of module binding on `HostManager.onAccept` reaches `EvmHost.withdraw()` (sends host-held revenue to an attacker-chosen `beneficiary` for an attacker-chosen `amount`/`token`) and `EvmHost.updateHostParams()` (can rewrite `admin`, `handler`, `consensusClient`, `hostManager`, `feeToken` — i.e. full protocol takeover of the EVM host). This falls squarely in "stealing or loss of funds," "unauthorized transaction or execution," and "false state/authorization acceptance" categories the bounty targets, and is a direct architectural analog to the external report's core defect: a single insufficiently-scoped authorization check (there, a single DAO key with no second factor; here, a single source-chain check with no module-id second factor) that lets an unintended party execute privileged, fund-moving, ownership-altering actions.

### Likelihood Explanation
Exploitability today is bounded by the fact that no currently-shipped permissionless pallet lets a caller fully control both the destination `to` address and an arbitrary `body`, aimed specifically at a `HostManager` contract — the closest such permissionless primitive (`pallet_ismp_demo::dispatch_to_evm`) hardcodes its `body`. Likelihood is therefore moderate rather than immediately critical: it is a missing defense-in-depth control on a fund/admin-critical path, matching a documented anti-pattern already called out elsewhere in this codebase's own docs, and it means any future or overlooked pallet capable of steering `to`/`body` on a Hyperbridge-originated dispatch (a common, low-scrutiny pattern in this multi-pallet runtime) instantly becomes a full host-takeover primitive with no additional review of `HostManager.sol` required.

### Recommendation
Add a `request.from` check to `HostManager.onAccept`, mirroring `ExtrinsicIntents`/`IntentGatewayV2`/`HyperFungibleToken`/`HyperbridgeLzEndpoint`: require `request.from` to equal a specifically registered governance module id (e.g. `pallet-host-executive`'s `PALLET_ID`, `hostexec`) rather than accepting any module dispatching from the Hyperbridge chain. This restores the "chain id + module id" dual authentication that the rest of the protocol relies on for cross-chain fund/admin actions.

### Proof of Concept
1. On the Hyperbridge parachain, any pallet capable of calling `T::IsmpDispatcher::dispatch_request` with a caller/attacker-influenced `to` field (structurally identical to the existing permissionless `pallet_ismp_demo::dispatch_to_evm(origin, EvmParams{ module, destination, .. })` shown at `modules/pallets/demo/src/lib.rs:216-239`) sets `to = <HostManager address on target EVM chain>` and `body = abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(WithdrawParams{ beneficiary: attacker, amount: hostBalance, token: feeToken }))`.
2. `pallet-ismp` dispatches the request with `source = host_state_machine()` (Hyperbridge's real chain id) — this field cannot be spoofed by the calling pallet (`modules/pallets/ismp/src/dispatcher.rs:128-146`).
3. On delivery, `EvmHost.dispatchIncoming` calls `HostManager.onAccept(incoming)`.
4. `HostManager.onAccept` checks only `request.source.equals(hyperbridge())` — true, since the message did originate from the real Hyperbridge chain — and never checks `request.from`, so it proceeds to call `IHostManager(_params.host).withdraw(withdrawParams)`, transferring the host's revenue to the attacker's `beneficiary` address (`evm/src/core/HostManager.sol:95-109`, `evm/src/core/EvmHost.sol:651-660`).

```text
    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
```
