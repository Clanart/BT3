### Title
Missing/duplicate DKG messages trigger `HashMap` index and `assert!` panics in PedPoP decryption handling - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2023-37019 (a malformed `S1Setup Request` missing a required field remotely triggers an assertion and crashes the MME), PedPoP's decryption/blame path dereferences `self.enc_keys[...]` and asserts on re-registration without validating that the referenced participant actually registered an encryption key. A DKG participant who sends a blame/accusation naming a `decryptor` that never submitted an `EncryptionKeyMessage`, or who sends a second registration for the same participant, causes a panic rather than an `io::Error`/protocol error, crashing the processing task.

### Finding Description
`Decryption::register` asserts that a participant is not already present, with no graceful error path:

```rust
// crypto/dkg/pedpop/src/encryption.rs:356-360
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

More critically, `Decryption::decrypt_with_proof` — invoked when handling a blame/accusation message — indexes `self.enc_keys` by an attacker-namable `decryptor` participant:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-390
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // panics if decryptor never registered
  )
  .map_err(|_| DecryptionError::InvalidProof)?;
```

`std::collections::HashMap`'s `Index` impl panics on a missing key. The same pattern exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, line 466). None of these paths validate participant membership before indexing; the read side (`EncryptedMessage::read`, `EncryptionKeyMessage::read`, lines 57-59, 171-177) happily parses any well-formed bytes and does not enforce that the sender first registered.

### Impact Explanation
An unprivileged DKG participant can send a malformed protocol sequence — a blame message naming a non-existent `decryptor`, or a duplicated `EncryptionKeyMessage` — causing a panic in the victim's key-generation handling. As in CVE-2023-37019, a missing/duplicated required field reaches an assertion-like path (`HashMap` indexing panics identically to `assert!`), repeatedly crashing the process and aborting the DKG/signing session — denial of service of the signing infrastructure.

### Likelihood Explanation
Reachable entirely from public inputs: the attacker controls the messages they send in the DKG and any blame arguments they raise. `decrypt_with_proof` is a `pub(crate)` handler fed by deserialized `EncryptedMessage`s from peers; there is no prior check that `decryptor` exists in `enc_keys`. No collusion, leaked keys, or integrator misuse is required — just a participant who skips the registration step or references an arbitrary participant index.

### Recommendation
Replace `self.enc_keys[&decryptor]` and `self.decryption.enc_keys[&participant]` with `.get(&p).ok_or(...)` returning `DecryptionError`/`io::Error`, and change `Decryption::register`'s `assert!` into a returned error (`io::Error::other("re-registered encryption key")`) so malformed peer sequences are rejected instead of panicking. Also validate in the DKG driver that every expected participant registered before processing blame or share-encryption steps.

### Proof of Concept
```rust
// Given a Decryption<Ristretto> where only participant 1 registered:
let mut dec = Decryption::<Ristretto>::new(context);
dec.register(Participant::new(1).unwrap(), key_msg_from_p1);

// Attacker (participant 2) sends an EncryptedMessage and raises a blame
// naming decryptor = Participant(9), who never registered:
let blame = EncryptedMessage::<Ristretto, ShareBytes>::read(&mut attacker_bytes, params)?;
let proof = EncryptionKeyProof::read(&mut attacker_proof_bytes)?; // any well-formed proof
// Panics inside HashMap Index on missing key before the DLEq is even verified:
let _ = dec.decrypt_with_proof(Participant::new(2).unwrap(),
                               Participant::new(9).unwrap(), blame, Some(proof));

// Alternatively, re-sending a registration for participant 1 hits:
// assert!(!self.enc_keys.contains_key(&participant)) -> panic
```

Both panics occur after `read` succeeds on attacker-controlled bytes, before any cryptographic verification rejects the input — matching the CVE pattern of an assertion reachable via a message missing required prior state.
