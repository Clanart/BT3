## Finding: Stale working-directory snapshot allows Copilot AI conflict resolution to silently overwrite the user's own conflict fix

### Title
Stale pre-loop `state` snapshot in `_applyCopilotConflictResolutions()` lets AI-resolved content silently overwrite user's manual conflict resolution - (File: `app/src/lib/stores/app-store.ts`)

### Summary
This is a structural analog of the reported bug: a guard check reads a value captured **once, before a sequence of awaited async operations**, and that stale snapshot is then relied upon to decide whether to skip a destructive write, exactly like `totalProfit` being computed against pre-return conditions instead of being refreshed at the point of use.

### Finding Description
`_applyCopilotConflictResolutions()` captures `state = this.repositoryStateCache.get(repository)` a single time at function entry [1](#0-0) . It then iterates over `copilotResolutions` and, for each file, performs two `await`-ed operations — `resolveWithin(...)` and eventually `writeFile(...)` — before moving to the next file [2](#0-1) .

The safety check meant to prevent clobbering a manually-resolved file explicitly documents its intent:

```
// If the user resolved this file externally (e.g. in their editor) while
// the result dialog was open, git status will report it with no remaining
// conflict markers. Overwriting it with Copilot's stored content would
// silently clobber their work, so skip it and let their resolution stand.
``` [3](#0-2) 

However, the check reads `state.changesState.workingDirectory.files` — the **pre-loop snapshot** captured before any `await` — instead of re-fetching `this.repositoryStateCache.get(repository)` for each iteration. Because the loop `await`s I/O for every resolved file (`resolveWithin`, `writeFile`), the event loop yields multiple times, giving ample time for a background status refresh to detect that the user resolved a *later* file in the list externally. That refreshed status is never consulted; the loop keeps consulting the original `state` object, so the "has this been resolved externally" check systematically fails to catch resolutions that happened after function entry but before that particular file's turn in the loop.

This mirrors the `totalProfit` bug precisely: a value (`onDiskFile`/its `status`) that should be re-evaluated at the point of use is instead computed once and reused across a later branch that has already had time to invalidate it.

### Impact Explanation
If the guard misses an externally-resolved file, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` unconditionally overwrites the user's manual fix with Copilot's (potentially attacker-shaped) resolution content, and the file is then staged via `git add` [4](#0-3) . This is silent corruption of what the user is about to commit/push: the user believes their manual edits are preserved (git status showed them as resolved), but the content that lands in the commit is different, unreviewed AI-suggested content — potentially derived from a maliciously crafted merge conflict in an attacker-controlled branch that induces a particular Copilot resolution. There is no re-confirmation step or diff shown before this overwrite for files processed later in the loop.

### Likelihood Explanation
Triggering this requires only ordinary usage: a repository/branch with several conflicting files (easily crafted by an attacker opening a PR/branch with many conflicts), the user invoking Copilot's AI conflict resolution, and resolving one of the later files manually (e.g. in an external editor) while the flow is still processing earlier files — a natural, unprompted-by-the-app workflow that many users would perform during a long multi-file merge. The larger the number of conflicting files an attacker's branch introduces, the wider the race window (more `await` yield points), increasing likelihood.

### Recommendation
Re-fetch `this.repositoryStateCache.get(repository)` (or at least `changesState.workingDirectory.files`) inside the loop, immediately before the "resolved externally" check and the `writeFile` call, rather than relying on the snapshot captured before the loop began. This keeps the check meaningful for every file, regardless of how much async work has already occurred.

### Proof of Concept
1. Attacker pushes a branch containing 5+ files with merge conflicts to a repo the victim will merge/rebase.
2. Victim starts the multi-commit operation and uses "Copilot conflict resolution"; `_applyCopilotConflictResolutions` captures `state` once [5](#0-4) .
3. While the loop is `await`-ing `resolveWithin`/`writeFile` for file #1, the victim manually resolves file #3 in their editor and saves it (git status now shows file #3 with no conflict markers).
4. When the loop reaches file #3, the check at [6](#0-5)  still evaluates against the pre-loop `state`, where file #3 was still flagged as conflicted — so the skip condition is not satisfied.
5. `writeFile` overwrites the victim's manual resolution with Copilot's resolved content, and it's staged, silently corrupting what will be committed.
