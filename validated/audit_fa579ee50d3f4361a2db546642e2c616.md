## Title
Unrestricted URL Scheme Passed to `shell.openExternal` via `open-external` IPC Channel - (File: `app/src/main-process/main.ts`)

### Summary
The external report's core defect pattern is a handler that *looks* like it enforces a safety constraint but doesn't actually gate the dangerous action on it — the `send_farm_tokens`/`add_farm` instructions had authorization-shaped code that never actually restricted the caller, and the account's authority field was set to the wrong value, breaking the invariant other code relied on. The closest verified analog in GitHub Desktop is the `open-external` IPC handler in `app/src/main-process/main.ts`, which performs a scheme check that is used only for logging and never actually restricts what gets passed to `shell.openExternal`.

### Finding Description
The main process registers the `open-external` channel as: [1](#0-0) 

```ts
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```

The `http(s)` check exists purely to decide whether to emit an informational log line — it is never used as a gate. Any string reaching this handler, regardless of scheme (`file:`, a registered OS protocol handler such as `ms-officecmd:`, `search-ms:`, `steam:`, or another app's custom protocol), is forwarded unmodified to Electron's `shell.openExternal`. This mirrors the reported bug class exactly: code that superficially resembles an access/validation control but does not actually enforce it, so the "authorized" path (only http/https should be opened externally) is not what the code actually restricts to.

The renderer side channel type declares `open-external` as a generic `(path: string) => Promise<boolean>` with no scheme constraint either: [2](#0-1) 

The type is unrestricted, and any UI component in the renderer can supply a value — including a URL originating from an attacker-controlled GitHub object (a link in a commit message, PR/issue body, README, or diff rendered from a cloned/fetched repository) — through this pathway without the main process re-validating the scheme.

### Impact Explanation
`shell.openExternal` is documented by Electron as unsafe with untrusted input because many OS URI schemes registered by other installed applications can be abused to achieve code execution, file writes, or arbitrary application invocation outside of Desktop's own sandbox (the well-known "Do not use `shell.openExternal` with untrusted content" guidance). Since the only scheme check present here is decorative (used for a log message, not enforcement), an attacker who controls content that ends up rendered as a clickable link inside Desktop (issue/PR body, commit message, README from a cloned/fetched repository) can supply a non-http(s) URI. If the user clicks it, Desktop calls `shell.openExternal` with that value, handing control to the OS URL-handler subsystem — a path to file write/read or code execution outside the intended scope, and outside Desktop's own process trust boundary.

### Likelihood Explanation
This requires only that a user click a link that Desktop renders from external, attacker-influenced content (a GitHub API object, PR/issue/commit text, or repository content) — squarely within the valid impact category "a link ... the user clicks." No local access, admin rights, or pre-existing malware is needed, and no unnatural workflow beyond a normal click is required.

### Recommendation
Enforce the scheme allowlist as an actual guard rather than a logging-only condition in the `open-external` handler in `app/src/main-process/main.ts`: reject (or explicitly confirm) any URL whose scheme is not `http:`/`https:` (and any other explicitly supported scheme, e.g. `mailto:`) before calling `shell.openExternal`, mirroring the intent already expressed — but not enforced — by the existing `pathLowerCase.startsWith(...)` check.

### Proof of Concept
1. An attacker crafts a GitHub issue/PR body, commit message, or README containing a rendered link such as `search-ms:query=malware&crumb=location:\\attacker-share` (Windows) or a custom-protocol URI registered by another locally installed application.
2. Victim clones/fetches the repository or views the PR/issue in GitHub Desktop, where the text is rendered as a clickable external link.
3. The renderer invokes the `open-external` IPC channel with the attacker-supplied string (`app/src/lib/ipc-shared.ts:113`).
4. The main process handler forwards it unchanged to `shell.openExternal` because the only scheme check present (`app/src/main-process/main.ts:582-588`) merely toggles a log statement and does not block non-http(s) schemes.
5. The OS invokes whatever handler is registered for that scheme with attacker-controlled parameters, outside GitHub Desktop's intended sandboxed action of "open a web link." [1](#0-0) [2](#0-1)
