## Analysis: Root-Cause Analog Found

The Mellow bug pattern — aggregating balances from multiple sources without verifying a per-source restriction/permission, then having a later "pull"/spend operation revert or produce an invalid result because that restriction was silently violated — has a structural analog in the Chia wallet's CR-CAT (Credential-Restricted CAT) coin ingestion and coin-selection code.

### Title
Unchecked CR-CAT restriction parameters during coin ingestion allow a stranger to poison a wallet's spendable coin set and break future composite CAT spends - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
`CRCATWallet.add_crcat_coin` accepts any incoming coin into a wallet's spendable coin set as long as the coin's `inner_puzzle_hash` matches a known derivation record, but it never checks that the coin's actual `authorized_providers`/`proofs_checker` (the CR-layer restriction, i.e. the Mellow "allowedAssets" analog) match the wallet's configured `self.info.authorized_providers` / `self.info.proofs_checker`. Worse, those actual per-coin restriction values are discarded and never persisted — `CRCATMetadata` only stores `lineage_proof` and `inner_puzzle_hash`. When the wallet later needs to reconstruct the coin's puzzle to spend it (`coin_record_to_crcat`), it always uses the wallet's *current* configured restriction values rather than the coin's real ones. `select_coins` (inherited from `CATWallet`) aggregates spendable coins purely by wallet id/amount with no restriction check, so a "poisoned" coin can be silently mixed into a normal outgoing composite CR-CAT spend.

The metadata persisted for the coin drops this restriction information entirely: [2](#0-1) 
Only `lineage_proof` and `inner_puzzle_hash` are stored in `CRCATMetadata`.

When the wallet needs to spend a coin later, it reconstructs the `CRCAT` object using the *wallet's current* `self.info.authorized_providers`/`self.info.proofs_checker`, not the actual values the coin was created with: [3](#0-2) 

Coin selection for building a spend aggregates coins purely by wallet id/amount, with no restriction-consistency check per coin (inherited from `CATWallet.select_coins`, used unmodified by `CRCATWallet`): [4](#0-3) 

`_generate_unsigned_spendbundle` then pulls in whichever coins `select_coins` returned and builds one composite `CRCAT.spend_many` transaction from all of them: [5](#0-4) [6](#0-5) 

If a "poisoned" coin (same TAIL/asset id, but wrapped with different `authorized_providers`/`proofs_checker` than the victim wallet's current configuration) is sent to the victim's known inner puzzle hash, it will be silently accepted as spendable. When the wallet later needs to combine coins to reach a target amount, `select_coins` may include this poisoned coin. `coin_record_to_crcat` then reconstructs it with the *wrong* restriction parameters, producing a puzzle reveal whose hash does not match the coin actually on chain — the resulting `CoinSpend` is invalid for that coin, and because it's bundled together with the legitimate coins in the same `WalletSpendBundle`, the entire composite transaction fails, exactly mirroring the Mellow pattern where one unchecked/unsupported balance inside an aggregation permanently breaks a batched operation on unrelated legitimate funds.

### Impact Explanation
An unprivileged holder of the same underlying CAT asset (same TAIL hash, since the CR layer is just a wrapper any coin holder can apply) can send a small amount to a victim's public receive address with a CR layer that does not match the victim's actual configured `authorized_providers`/`proofs_checker`. The coin is absorbed into the victim's normal spendable balance. Any future spend attempt by the victim that draws on multiple coins to reach the target amount risks including the poisoned coin, producing an invalid puzzle reveal for that coin and causing the entire multi-coin transaction (including the victim's legitimate funds) to fail — a spend-triggered transaction-processing halt for that wallet, analogous to the Mellow `getLiquidAssets()`/`hookPullAssets()` DoS.

### Likelihood Explanation
Requires only that the attacker already holds (or can obtain) some amount of the same TAIL-identified CAT asset and can construct/relay a CR-CAT coin spend with attacker-chosen `authorized_providers`/`proofs_checker`, then send the resulting coin to a victim's known puzzle hash — all doable by any wallet holder with no special privileges, matching the "unprivileged wallet user / offer counterparty" threat model.

### Recommendation
When ingesting a coin in `add_crcat_coin`, additionally verify that `cr_cat.authorized_providers == self.info.authorized_providers` and that `cr_cat.proofs_checker` matches `self.info.proofs_checker.as_program()` before accepting it as spendable `CoinType.CRCAT`; otherwise route it to an "unknown/foreign CR-CAT" bucket that is excluded from `select_coins`. Additionally persist the coin's actual restriction parameters in `CRCATMetadata` so `coin_record_to_crcat` reconstructs the coin using the values it was actually created with, rather than blindly substituting the wallet's current configuration.

### Proof of Concept
1. Victim runs a `CRCATWallet` for CAT with tail hash `T`, configured with `authorized_providers = [P1]`.
2. Attacker holds a plain CAT coin under the same tail `T` (any amount) and wraps it in a CR layer with `authorized_providers = [P2]` (attacker-controlled/irrelevant provider), sending the resulting CR-CAT coin to the victim's known `inner_puzzle_hash`.
3. Victim's `add_crcat_coin` (cr_cat_wallet.py:227) accepts the coin as `CoinType.CRCAT` because the derivation record for `inner_puzzle_hash` matches; no check on `authorized_providers`/`proofs_checker` is performed, and the metadata stored discards them.
4. Victim later attempts to send an amount requiring more than one coin; `select_coins` (cat_wallet.py:654) includes the poisoned coin.
5. `coin_record_to_crcat` (cr_cat_wallet.py:370) reconstructs the poisoned coin using the wallet's `[P1]` provider list instead of the coin's actual `[P2]`, producing a puzzle reveal whose hash diverges from the coin's real on-chain puzzle hash.
6. The resulting composite `WalletSpendBundle` (built in `_generate_unsigned_spendbundle`, cr_cat_wallet.py:398) is invalid for that coin and fails on submission, blocking the transaction that also spends the victim's legitimate coins.

    def coin_record_to_crcat(self, coin_record: WalletCoinRecord) -> CRCAT:
        if coin_record.coin_type not in {CoinType.CRCAT, CoinType.CRCAT_PENDING}:  # pragma: no cover
            raise ValueError(f"Attempting to spend a non-CRCAT coin: {coin_record.coin.name().hex()}")
        if coin_record.metadata is None:  # pragma: no cover
            raise ValueError(f"Attempting to spend a CRCAT coin without metadata: {coin_record.coin.name().hex()}")
        try:
            metadata: CRCATMetadata = CRCATWallet.get_metadata_from_record(coin_record)
            crcat: CRCAT = CRCAT(
                coin_record.coin,
                self.info.limitations_program_hash,
                metadata.lineage_proof,
                self.info.authorized_providers,
                self.info.proofs_checker.as_program(),
                (
                    construct_pending_approval_state(
                        metadata.inner_puzzle_hash, uint64(coin_record.coin.amount)
                    ).get_tree_hash()
                    if coin_record.coin_type == CoinType.CRCAT_PENDING
                    else metadata.inner_puzzle_hash
                ),
            )
            return crcat
        except Exception as e:  # pragma: no cover
            raise ValueError(f"Error parsing CRCAT metadata: {e}")

    async def select_coins(
        self,
        amount: uint64,
        action_scope: WalletActionScope,
    ) -> set[Coin]:
        """
        Returns a set of coins that can be used for generating a new transaction.
        Note: Must be called under wallet state manager lock
        """
        spendable_amount: uint128 = await self.get_spendable_balance()
        spendable_coins: list[WalletCoinRecord] = list(
            await self.wallet_state_manager.get_spendable_coins_for_wallet(self.id(), in_one_block=True)
        )

        # Try to use coins from the store, if there isn't enough of "unused"
        # coins use change coins that are not confirmed yet
        unconfirmed_removals: dict[bytes32, Coin] = await self.wallet_state_manager.unconfirmed_removals_for_wallet(
            self.id()
        )
        async with action_scope.use() as interface:
            coins = await select_coins(
                spendable_amount,
                action_scope.config.adjust_for_side_effects(interface.side_effects).tx_config.coin_selection_config,
                spendable_coins,
                unconfirmed_removals,
                self.log,
                uint128(amount),
            )
            interface.side_effects.selected_coins.extend([*coins])
        assert sum(c.amount for c in coins) >= amount
        return coins
