## Analysis

The CVE describes unbounded/infinite recursion in a data-parsing function causing a stack overflow. The closest analog in this codebase is `PuzzleWithRestrictions.from_memo()` in `chia/wallet/puzzles/custody/custody_architecture.py`, which recursively reconstructs a custody puzzle tree from an on-chain memo with no depth bound, and is invoked on attacker-influenced coin memo data during PlotNFT/pool state sync.

### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` when parsing attacker-controlled coin memos causes wallet stack-overflow / DoS - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody-puzzle tree (`MofN` of `PuzzleWithRestrictions`) directly from a CLVM `Program` memo taken from chain data, recursing once per `MofN` member with no depth limit. Because the memo shape is fully attacker-controlled (it is the memo attached to a `CREATE_COIN` condition, e.g. inside PlotNFT/pool singleton spends), an attacker can craft a coin whose memo encodes a deeply nested `MofN` tree, driving unbounded Python recursion in any wallet that parses it.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is defined as: [1](#0-0) 

When `further_branching` is true, it builds an `MofN` whose `members` are populated by calling `PuzzleWithRestrictions.from_memo(memo)` again for every member memo — a direct, unbounded Python-level recursion driven entirely by attacker-supplied CLVM data, with no maximum-depth check, unlike `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py`, which is deliberately implemented iteratively specifically to avoid "blowing out the python stack": [2](#0-1) 

This parser is reached from consensus-adjacent wallet code that processes coin memos created by an untrusted counterparty. `PlotNFT.get_next_from_coin_spend()` extracts the memo from a `CREATE_COIN` condition's `memo_blob` produced by a singleton spend and feeds it straight into `PuzzleWithRestrictions.from_memo()`: [3](#0-2) 

Because plotnft/pool singleton state transitions are driven by whatever coin spend is observed on chain (i.e., this sync logic runs whenever a wallet is tracking a PlotNFT and encounters a new singleton spend), an attacker who can get a coin spend with a maliciously deep `MofN` memo onto the chain (or crafted and shared as an unconfirmed spend/offer artifact that the victim's wallet inspects) can trigger deep, unguarded Python recursion purely by having the victim wallet parse the memo.

### Impact Explanation
Python has a default recursion limit (typically ~1000 frames); a moderately deep nested `MofN` memo raises an uncaught `RecursionError` inside wallet code that processes chain data. Depending on call context this can crash the wallet sync loop or, if not carefully caught, take down the wallet service processing loop each time it encounters this coin — a spend-triggered halt/DoS of wallet transaction processing (analogous to the GPAC stack-overflow bug class: unbounded self-recursion driven by attacker-controlled nested input). This does not directly cause coin theft or consensus divergence, keeping severity at Medium, matching the CVSS 5.5/local, availability-only profile of the reference CVE.

### Likelihood Explanation
Likelihood is moderate: reaching this code path requires the victim to be running the PlotNFT/pool sync path (`PlotNFT.get_next_from_coin_spend`) and to encounter a coin spend whose memo was crafted with deeply nested `MofN` structure. An attacker only needs to get such a coin spend observed by the target wallet (e.g., by spending a coin the target is watching, or via a shared offer/coin state), no privileged access or malicious peer/node behavior is required.

### Recommendation
Add an explicit maximum recursion/nesting depth check in `PuzzleWithRestrictions.from_memo()` (and correspondingly in `MofNHint.from_program()`), rejecting memos that exceed a safe depth, or reimplement the parse iteratively (mirroring the pattern already used in `sha256_treehash()`) so a `RecursionError` cannot be induced by external memo data. Ensure all call sites that invoke `from_memo()` on chain-derived data (e.g., `plotnft_drivers.py`) catch/convert any resulting exception into `GetNextPlotNFTError` rather than allowing an uncaught `RecursionError` to propagate.

### Proof of Concept
1. Construct a `Program` memo of the form `(spec_namespace, [nonce, [], 1, (m, [member_memo, member_memo, ...])])` where `member_memo` is itself a full nested `PuzzleWithRestrictions` memo with `further_branching=1`, repeated to a depth of several thousand levels (each level trivial to construct programmatically).
2. Attach this memo as the `memo_blob` on the `CREATE_COIN` condition of a PlotNFT/pool singleton coin spend (per the memo format built in `PlotNFT.launch()` / `PlotNFTPuzzle.memo()`), and get this coin spend accepted/observed on chain (or synced by a victim wallet tracking the launcher id).
3. Have the target wallet call `PlotNFT.get_next_from_coin_spend()` on this spend; it calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`, which recurses once per nesting level with no bound, raising `RecursionError` and aborting/crashing the wallet's plotnft sync processing.
