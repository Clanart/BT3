### Title
Spoofed `WWW-Authenticate` realm forces Desktop into an Enterprise OAuth sign-in flow against an attacker-controlled endpoint, leaking Desktop's OAuth `code`/token exchange to that host - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
Desktop's git credential-helper trampoline decides whether an unknown remote host is a GitHub Enterprise instance by trusting the `WWW-Authenticate` header value returned by that remote during a failed HTTP auth attempt. A malicious or compromised git remote/proxy can simply return `WWW-Authenticate: ... realm="GitHub"` on any HTTPS URL to make Desktop treat it as an "enterprise" endpoint, which automatically triggers the GitHub Enterprise sign-in UI pointed at the attacker's own origin.

### Finding Description
`getEndpointKind` in `trampoline-credential-helper.ts` classifies a credential request's host using several checks, one of which trusts `wwwauth[]` values Git forwards from the remote server's HTTP response: [1](#0-0) 

If no existing account matches, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` derived directly from the (attacker-controlled) credential URL: [2](#0-1) 

`promptForGitHubSignIn` then starts the Enterprise sign-in flow and sets the sign-in endpoint to the attacker's own `origin`: [3](#0-2) 

`SignInStore.setEndpoint` validates only URL syntax/protocol (HTTPS), not that the host is an actual GitHub product, and advances straight to the `Authentication` step for any HTTPS URL other than `github.com`: [4](#0-3) 

`authenticateWithBrowser` then opens an OAuth authorization URL built from that attacker-controlled `endpoint`, and on redirect back exchanges the OAuth `code` by POSTing to that same `endpoint`: [5](#0-4) [6](#0-5) 

The broken invariant is analogous to "unlimited allowance without scoping the trustee": Desktop's endpoint-kind classifier grants a remote host the elevated "trusted GitHub Enterprise" status based solely on unauthenticated, attacker-suppliable header text, instead of verifying the endpoint against a real, previously-established GitHub identity (e.g., via `/meta` API validation, TLS pinning, or an explicit user opt-in per host). This "trust token" (the classification result) is then handed to the full OAuth flow, including the client credentials exchange (`requestOAuthToken`, referenced in `app/src/lib/api.ts`) that is supposed to only ever talk to `github.com` or a user-vetted GHE instance.

### Impact Explanation
An attacker who controls a git remote or a MITM/proxy in front of one (e.g., a malicious clone URL, a compromised self-hosted git server, or a network path being fetched from) can trigger this by simply returning a spoofed `WWW-Authenticate: realm="GitHub"` header on an authentication challenge. This forces Desktop to:
1. Open the OAuth authorization flow against the attacker's own origin (browser navigation to attacker-chosen URL, unexpected to the user who did not ask to sign into anything).
2. On the OAuth callback, exchange the authorization `code` with the attacker's server as if it were a genuine GHE `/login/oauth/access_token` endpoint - which, depending on the exact implementation of `requestOAuthToken`, may transmit Desktop's OAuth client identifier/secret and/or the authorization code to the attacker-controlled host.

This can result in credential/OAuth material being sent to a host the user never intended to authenticate with, purely as a side effect of fetching/cloning from that remote - fitting the "unauthorized OAuth" and "credential/token exfiltration" impact categories.

### Likelihood Explanation
The trigger only requires controlling the HTTP response of a git remote the user clones/fetches from (or a proxy in that path) - no local access, no prior compromise, and no unusual user action beyond a normal `git fetch`/`clone`/`push` HTTPS auth attempt. The `wwwauth[]` substring check (`realm="GitHub"`) is trivial to spoof from any HTTP server. The main precondition is that the user does not already have a matching account for that origin, and reaches an authentication attempt against the malicious remote, which is a common flow (e.g., adding a malicious HTTPS remote or being redirected/proxied to one).

### Recommendation
Do not use an easily attacker-suppliable `WWW-Authenticate` header, on its own, as sufficient evidence to classify an arbitrary host as an "enterprise" GitHub endpoint. At minimum:
- Require independent verification (e.g., a successful call to a well-known GitHub API path/`/meta`-style endpoint with expected schema, not just a header string) before elevating trust.
- Never auto-initiate the OAuth sign-in flow, and never open `shell.openExternal`/perform code-for-token exchanges, against a host inferred purely from unauthenticated header content — require explicit user confirmation naming the exact host before starting `beginEnterpriseSignIn`/`setSignInEndpoint` from a credential-helper-triggered path.
- Scope/limit what is sent in the OAuth code exchange to endpoints that have been explicitly added by the user through the normal "Enterprise sign-in" UI, rather than a value derived from the credential request being serviced.

### Proof of Concept
1. Stand up an HTTPS server at `https://evil.example.com` that responds to any Git HTTP request with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add `https://evil.example.com/some/repo.git` as a remote (or clone it) and trigger a fetch/push that requires auth.
3. Git invokes Desktop's credential helper (`trampoline-credential-helper.ts`); `getEndpointKind` sees the spoofed `wwwauth[]` header and returns `'enterprise'`.
4. Since no account matches `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, which calls `beginEnterpriseSignIn` + `setSignInEndpoint('https://evil.example.com')`.
5. Desktop shows the Sign-in dialog and, on proceeding, opens the browser to an OAuth authorize URL built from `https://evil.example.com`, and on callback exchanges the code by POSTing to `https://evil.example.com/login/oauth/access_token` — attacker's server receives this request. (Exact payload of this request should be confirmed by reading `requestOAuthToken`/`getOAuthAuthorizationURL` in `app/src/lib/api.ts`, which I was unable to inspect before running out of tool calls.)

    }

      this.beginDotComSignIn(currentState.resultCallback)
      return

    try {
