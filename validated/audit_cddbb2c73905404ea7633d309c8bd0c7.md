## Title
Fee-on-transfer / deflationary reward tokens break `BaseRewardPool` accounting via public `donateRewards`, causing permanent freezing of yield for late claimants - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool.donateRewards` and `queueNewRewards` credit the entire nominal `_amountReward` argument to `rewardPerTokenStored` without verifying how many reward tokens the contract actually received via `safeTransferFrom`. If the registered reward token is fee-on-transfer/deflationary, the contract's on-chain balance will be lower than the amount it has promised to stakers, causing later claimers' `getReward` calls to be unfulfillable.

### Finding Description
`donateRewards` is a completely permissionless, unprivileged-wallet-reachable function that any user can call for any already-registered reward token: [1](#0-0) 

It calls `_provisionReward`, which pulls tokens with `safeTransferFrom` but then updates `rewardInfo.rewardPerTokenStored` using the raw `_amountReward` parameter, not the actual balance delta received by the contract: [2](#0-1) 

The same pattern exists in `queueNewRewards` (called by managers such as `WombatStaking` when forwarding harvested/bribe rewards) and is duplicated in `rewards/BaseRewardPoolV2.sol`: [3](#0-2) [4](#0-3) 

Because `rewardPerTokenStored` (and therefore every user's `earned()` value via `_earned`/`earned`) is computed from the nominal amount rather than the amount actually transferred in, if the reward token takes a transfer fee or rebases downward, the sum of all users' accrued claimable rewards will exceed the token balance actually held by the `BaseRewardPool` contract. This is in contrast to `WombatStaking.deposit`/`depositLP`, which correctly use before/after balance diffs to account for LP tokens actually received: [5](#0-4) 

`getReward` then pays out `userRewards[rewardToken][_account]` via a plain `safeTransfer` with no balance check: [6](#0-5) 

### Impact Explanation
Once the pool's accounted rewards exceed the actual token balance, `getReward`/`safeTransfer` calls will begin to fail for the last stakers who attempt to claim (insufficient contract balance), while earlier claimants can still withdraw normally. This results in a permanent, protocol-level freezing of unclaimed yield for a subset of stakers — a real accounting insolvency of the reward pool that is not a mere theoretical or gas-only issue, matching the "permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
Likelihood depends on whether any registered reward token for a given `BaseRewardPool`/`BaseRewardPoolV2` instance is deflationary/fee-on-transfer/rebasing. `donateRewards` requires no special privilege — any wallet can trigger the corruption for any already-registered reward token by donating an amount of a fee-on-transfer token, and normal operational flows (`queueNewRewards` invoked by `WombatStaking`) reinforce the same flawed accounting whenever such a token is used as a reward/bribe token.

### Recommendation
In `_provisionReward` (both `BaseRewardPool.sol` and `BaseRewardPoolV2.sol`), measure the actual amount received by comparing the contract's reward-token balance before and after `safeTransferFrom`, and use that measured delta (instead of the caller-supplied `_amountReward`) when updating `historicalRewards` and `rewardPerTokenStored`.

### Proof of Concept
1. Owner/manager registers a fee-on-transfer ERC20 (e.g., a token that burns 2% of every transfer) as a reward token for some `BaseRewardPool`.
2. Any user calls `donateRewards(1000e18, feeToken)`; the pool only actually receives 980e18 tokens (fee taken during `safeTransferFrom`), but `_provisionReward` still increments `rewardPerTokenStored` based on the full 1000e18. [7](#0-6) 
3. As stakers accrue and claim rewards via `getReward`, the cumulative claimable amount computed from `rewardPerTokenStored` (1000e18-equivalent) exceeds the actual token balance held (980e18-equivalent).
4. Eventually a `getReward` call's `safeTransfer` reverts due to insufficient balance, permanently blocking the affected user(s) from claiming their earned share.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
