### Title
Untrusted `ReceivedOutput` deserialization accepts fabricated outputs — phantom funds injected via crafted backup/restore file - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary

The WeGIA bug class is: a "restore" path consumes an attacker-crafted file and trusts its contents without validating them against the system's actual security invariants. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134`. `ReceivedOutput` is the structure a wallet persists and later reloads to know which Bitcoin outputs it can spend. Its security-critical invariant — that `offset` is the scalar which, added to the scanner's key, produces `output.script_pubkey` — is established only at scan time by `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`, via the `scripts` map built in `register_offset`/`Scanner::new`). `read` re-establishes none of this: it accepts any canonical scalar, any `TxOut`, and any `OutPoint` and returns them as a spendable `ReceivedOutput`.

### Finding Description

`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping each expected Taproot `script_pubkey` to the HDKD offset needed to spend it (`networks/bitcoin/src/wallet/mod.rs:153-196`). `scan_transaction` only emits a `ReceivedOutput` when `output.script_pubkey` is found in that map, binding `offset` ↔ `script_pubkey` ↔ `outpoint` together (`mod.rs:205-212`).

`ReceivedOutput::read` deserializes `offset` via `Secp256k1::read_F`, then `TxOut` and `OutPoint` via `consensus_decode`, and returns them unconditionally:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

There is no check that `p2tr_script_buf(scanner_key + G*offset) == output.script_pubkey`, nor that the `outpoint`/`value` were ever observed on-chain. Because `offset` is even stored *inside* the `ReceivedOutput` rather than re-derived from the scanner, a crafted file fully controls every field of the "received" output. The type has no way to re-verify at read time since it doesn't retain the scanner key — the consistency invariant exists only in `Scanner` and is silently dropped across a serialize/read round trip.

### Impact Explanation

Any code path that restores `ReceivedOutput`s from storage or the network and treats them as received funds will report attacker-fabricated outputs as spendable balance: arbitrary `value` (up to 21M BTC worth of satoshis in a `TxOut`), arbitrary `outpoint` (nonexistent or pointing to outputs paying other scripts), and arbitrary `offset`. Spending attempts against these will produce transactions whose sighash commits to a `script_pubkey`/`value` pair that doesn't match the real UTXO — the inputs are unspendable, so the wallet overstates its balance and constructs transactions that can never confirm. This matches the accepted impact class "funds reported received that are not spendable" — the same shape as WeGIA's restore trusting a crafted backup file, here a crafted output file injecting phantom state.

### Likelihood Explanation

Reachability requires an attacker to supply or corrupt the serialized `ReceivedOutput` bytes consumed by `read` — e.g., a wallet backup/import file, or any channel where scanned outputs are persisted and reloaded (the type publicly exposes `read`/`write`/`serialize` precisely for this purpose). That is a weaker precondition than the WeGIA report (which needed admin access plus crafted filename), but it is a real trust boundary: the entire point of serializing `ReceivedOutput` is to move it across storage boundaries where integrity is not guaranteed. If the consumer treats the byte stream as self-authenticating — which `read` invites, since it validates syntax but never semantics — the injection succeeds deterministically.

### Recommendation

- Store the scanner's base public key (or a hash/ID of it) alongside `ReceivedOutput` and, on `read`, recompute `p2tr_script_buf(key + GENERATOR * offset)` and reject inputs whose `output.script_pubkey` does not match — restoring the scan-time invariant.
- Alternatively, have `Scanner` expose a `verify_received(&ReceivedOutput) -> bool` helper that re-checks `self.scripts.get(&output.script_pubkey) == Some(&output.offset)`, and document that restored outputs must pass it.
- Note `offset` also legitimately must account for `register_offset`'s increment-until-even behavior (`mod.rs:180-196`), so verification must use the *used* offset, not merely presence in `scripts` — which the existing map lookup already handles correctly.

### Proof of Concept

```rust
use bitcoin::{
  consensus::encode::serialize, absolute::LockTime, transaction::Version,
  Amount, OutPoint, ScriptBuf, Transaction, TxIn, TxOut, Txid,
};
use bitcoin::hashes::Hash;
use k256::Scalar;
use std::io::Write;

// Attacker crafts a "restored" ReceivedOutput claiming a 100 BTC input at a
// txid/vout that either does not exist or pays a completely different script.
let mut buf = Vec::new();
buf.write_all(&Scalar::ONE.to_bytes()).unwrap();           // arbitrary offset
let fake_txout = TxOut {
  value: Amount::from_sat(100 * 100_000_000),             // arbitrary claimed value
  script_pubkey: ScriptBuf::new(),                        // unrelated to offset·G + key
};
buf.write_all(&serialize(&fake_txout)).unwrap();
let fake_outpoint =
  OutPoint::new(Txid::from_byte_array([0xAA; 32]), 0);    // fabricated outpoint
buf.write_all(&serialize(&fake_outpoint)).unwrap();

// Wallet restore path
let received = bitcoin_serai::wallet::ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(received.value(), 100 * 100_000_000); // accepted as a spendable 100 BTC input
```

`read` returns `Ok` and the wallet now believes it controls a 100 BTC UTXO. Any downstream send logic using `offset()`/`outpoint()`/`output()` will build a transaction spending a nonexistent or foreign-controlled input that can never confirm, while the reported balance is inflated by the fabricated amount.
