## Finding: Unbounded loop in `object::root_owner()` allows a self-referential ownership cycle to permanently brick lazy module self-init and re-publish/upgrade for the affected code object

### Title
`object::root_owner()` lacks the nesting bound enforced elsewhere, letting a self-owned ("cyclic") object permanently DoS `code::publish_package`'s lazy-init owner tracking and `init::internal_maybe_initialize` - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
`object::root_owner()` walks the ownership chain of an object with an unbounded `while` loop, unlike its sibling functions `owns()` and `verify_ungated_and_descendant()`, which both explicitly cap traversal at `MAXIMUM_OBJECT_NESTING` (8) to defend against cyclic ownership. `root_owner()` is invoked from two Aptos-native publish/init-safety code paths: `code::publish_package()` (to record the object's deploy owner for lazy module init) and `init::assert_may_self_initialize()` (the gate that decides whether a module hosted on an object may mint itself a privileged signer via `init::internal_maybe_initialize`). A single, ordinary, permissionless `object::transfer()` call that names the object itself as the destination creates a self-owning cycle (this exact state is demonstrably reachable — see the existing test `test_cyclic_ownership_transfer_should_fail`, whose *first* `transfer(creator, obj1, obj1.object_address())` call succeeds). Once that state exists, every future call into `root_owner()` for that object address never terminates its `while (is_object(obj_owner))` loop, exhausting gas and aborting the transaction, permanently blocking any future package upgrade and any future lazy self-init on that object.

### Finding Description
`aptos-move/framework/aptos-framework/sources/object.move` defines three functions that traverse the ownership chain: [1](#0-0) 
`owns()` bounds the walk with `count < MAXIMUM_OBJECT_NESTING`. [2](#0-1) 
`verify_ungated_and_descendant()` (used during `transfer`) likewise bounds the walk with the same constant, and its doc comment explicitly says: *"objects may have cyclic dependencies"* — acknowledging cycles as an expected, reachable state. [3](#0-2) 
`root_owner()`, however, has **no bound at all**:
```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
If `obj_owner` ever cycles back to an address that is still an object (e.g., the object owns itself), `is_object(obj_owner)` stays `true` forever and the loop never terminates within the function's own logic (only external gas metering stops it, by aborting the whole transaction).

A self-owning cycle is trivially reachable with a single, unprivileged, standard `transfer` call. As shown by `test_cyclic_ownership_transfer_should_fail`: [4](#0-3) 
```
fun test_cyclic_ownership_transfer_should_fail(creator: &signer) {
    let obj1 = create_simple_object(creator, b"1");
    // This creates a cycle (self-loop) in ownership.
    transfer(creator, obj1, obj1.object_address());
    // This should fails as the ownership is cyclic.
    transfer(creator, obj1, obj1.object_address());
}
```
The test's *comment itself* documents that the **first** `transfer` call succeeds in creating the self-loop; only the *second* call fails (because `verify_ungated_and_descendant`'s bounded walk now detects the pre-existing cycle). So a self-owned object with `ObjectCore.owner == self` is a legitimately reachable, permanent on-chain state, produced by one ordinary transfer.

This directly affects two Aptos-native publish/code-safety invariants that call `root_owner()`:

1. `code::publish_package()` records the deploy owner for lazy module init on every (re)publish/upgrade of a package hosted on an object: [5](#0-4) 
This call will loop unboundedly the moment the hosting object is self-owned, so **any future publish/upgrade to that code object aborts on out-of-gas**, permanently disabling the upgrade path for that package (the `PackageRegistry`/`ManagingRefs` state becomes unreachable via the normal publish flow).

2. `init::assert_may_self_initialize()`, the gate inside `init::internal_maybe_initialize()` that mints the module's self-init signer, also calls `root_owner()` on every self-init attempt: [6](#0-5) 
This means **any ordinary user entry-function call** that triggers lazy self-init on a module hosted at the now-cyclically-owned object will also loop unboundedly and abort — a denial-of-service against all callers of that package, not just the object's owner.

### Impact Explanation
Once the cycle exists, the affected code object's package(s) can never be upgraded again through `code::publish_package`/`object_code_deployment::upgrade`, and any lazily-self-initializing module hosted there becomes permanently uncallable by any user who triggers the not-yet-initialized path, because every invocation burns gas in an unbounded loop and the transaction aborts. This is a permanent write-set/publish-path failure ("verifier/module-init/native validation ... reaches protected state mutation" pathway explicitly named in the publish pivots) caused by a missing invariant that the sibling functions `owns()` / `verify_ungated_and_descendant()` correctly enforce. The break is irreversible on-chain (there is no way to "un-cycle" ownership once created without further transfers that hit the same unbounded `root_owner()` traversal in dependent logic), so it constitutes a durable denial of the code-safety machinery for that address.

### Likelihood Explanation
Creating the cyclic state requires only the object's *own owner* to call ordinary `transfer`/`transfer_to_object` naming the object itself (or, more generally, any address in its own ownership ancestry) as the new owner — a completely permissionless, unprivileged operation available to whoever legitimately owns the object (typically the package deployer, not a governance/admin role). No special capability is required beyond normal object ownership, and the reachability of this exact state is already demonstrated by the existing test suite's own setup step. The only mitigating factor is that it is the object owner's own action that produces the self-DoS, and the effect is scoped to that specific object/package rather than the wider chain, which keeps the likelihood of accidental/malicious triggering plausible but the blast radius bounded to that package's users.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING`-bounded traversal (and abort with `EMAXIMUM_NESTING`, or return the address at the bound rather than looping) to `object::root_owner()` that already protects `owns()` and `verify_ungated_and_descendant()`, so that cyclic or excessively deep ownership chains fail deterministically and cheaply instead of looping until gas exhaustion in every downstream caller, including `code::publish_package`'s deploy-owner recording and `init::assert_may_self_initialize`'s self-init gate.

### Proof of Concept
1. Deploy a package to an object address via `object_code_deployment::publish`, with a module using `init::internal_maybe_initialize` (lazy module init feature enabled), e.g. modeled on `OBJECT_MODULE_SRC` in `aptos-move/e2e-move-tests/src/tests/init_module_api.rs`.
2. As the object owner, call `object::transfer(owner, object, object.object_address())` — this is the exact call shown succeeding in `object.move`'s `test_cyclic_ownership_transfer_should_fail` (first invocation), leaving `ObjectCore.owner == object_address` (self-owned).
3. Call the module's entry function that invokes `init::internal_maybe_initialize(...)` (e.g. `test::run`). Observe the transaction aborts on out-of-gas due to the unbounded loop in `root_owner()` reached via `assert_may_self_initialize`.
4. Attempt `object_code_deployment::upgrade` (or `code::publish_package_txn`) on the same object address. Observe the transaction also aborts on out-of-gas via `record_deploy_owner`'s call to `root_owner()` in `code::publish_package`, showing the package can never be upgraded again.     public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

            count += 1;

            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
