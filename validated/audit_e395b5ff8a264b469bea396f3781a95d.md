### Title
Unchecked ERC20 boolean return in escrow payout allows silent transfer failure with state marked as settled - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.sol` (Tron variant) deposits escrow with `SafeERC20.safeTransferFrom` [1](#0-0) , but pays escrow back out in `withdraw()` and in the `SweepDust` admin-request handler using a raw low-level `.call` to the ERC20's `transfer` selector, checking only that the call did not revert and ignoring the ABI-encoded `bool` return value: [2](#0-1)  and [3](#0-2) .

### Finding Description
`withdraw()` treats a token whose `transfer()` returns `false` (without reverting) exactly the same as a successful payment: `_orders[body.commitment][token] -= amount` is decremented, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased`/`EscrowRefunded` is emitted [4](#0-3) , even though the beneficiary never actually received the tokens. The same unchecked pattern appears in the fee payout right below it, and in the governance-triggered `SweepDust` handler inside `onAccept` [5](#0-4) .

The escrowed `token` address in an order is fully attacker-controlled: any order creator can pick an arbitrary ERC20 contract as `order.inputs[i].token` when placing the order (deposit uses `safeTransferFrom`, which will happily accept a compliant "deposit" while the same contract's `transfer()` returns `false` on withdrawal instead of reverting — a trivially crafted "non-standard" or malicious token). Because the payout path only checks `success` of the low-level call (i.e. that the call did not throw) and not the returned data, this bypasses the `SafeERC20`-style protections used everywhere else in the same file, letting escrow accounting finalize (`_filled` set, `_orders` zeroed) while the token balance remains stuck in the contract.

### Impact Explanation
This breaks the core "funds move exactly once and only to the rightful beneficiary" invariant required for intent settlement. A malicious order creator can escrow a custom token that fails silently on `transfer()`, causing solver fill/redeem/refund flows to mark the commitment as settled (`_filled`, decremented `_orders`) without the solver or refund beneficiary ever receiving the funds — a direct loss-of-funds / broken-settlement condition on the intent-gateway's escrow custody logic, matching the bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
High for the specific token class: any unprivileged user can deploy and use a custom ERC20 as an order's input token; no relayer, prover, or admin collusion is required. The only precondition is the attacker's own crafted token, which is entirely within an unprivileged actor's control — this is not a "malicious peer/relayer" scenario, it exploits a code-level unchecked-return bug in the gateway's own payout path.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used elsewhere in this file for deposits) instead of the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()`, the transaction-fee payout, and the `SweepDust` handler, so that both non-reverting `false` returns and non-boolean-returning tokens are handled uniformly and any failure reverts the whole settlement instead of silently finalizing it.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` always returns `false` without reverting (constructor mints attacker a balance and `transferFrom` behaves normally so escrow deposit succeeds).
2. Attacker calls `newOrder` (source-chain deposit path using `safeTransferFrom`, which succeeds) with `order.inputs[0].token = EvilToken`.
3. A solver fills the order on the destination chain; the fill dispatches a `RedeemEscrow` request back to the source chain.
4. `onAccept` → `withdraw(body, false)` executes `EvilToken.transfer(solver, amount)` via the unchecked low-level `.call`; the call returns `(true, abi.encode(false))`. Since only `success` (the outer call-success flag) is checked, the code proceeds as if payment succeeded.
5. `_orders[commitment][EvilToken] -= amount` and `_filled[commitment] = solver` are set, `EscrowReleased` is emitted — the solver never received any `EvilToken`, yet the protocol's state says the escrow was correctly released.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {

        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
