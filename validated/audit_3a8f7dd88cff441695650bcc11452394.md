## Title
NFT royalty fee can be bypassed via integer-division truncation on small trade amounts - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
The Chia wallet computes NFT royalty payments (the "fee" a buyer/seller owes to the NFT creator on every offer that trades the NFT for fungible assets) using integer floor division. When the traded fungible amount times the royalty percentage is smaller than `MAX_ROYALTY_BASIS_POINTS` (10000), the computed royalty truncates to zero. A taker or maker can therefore split what would be one large purchase into many tiny purchases, each below the truncation threshold, and never pay any royalty at all — exactly the same rounding-to-zero fee-bypass bug class described in the external BarnBridge report.

### Finding Description
`compute_royalty_amount` performs the royalty calculation used when constructing NFT offer spend bundles: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

Both divisions truncate towards zero. For any `offered_amount` where `offered_amount * percentage < MAX_ROYALTY_BASIS_POINTS` (e.g. a royalty of 1% = 100 basis points on an offered amount of 99 mojos gives `99 * 100 // 10000 == 0`), the royalty owed is exactly 0, and the function returns without ever raising an error (the only guard is `royalty >= abs(offered_amount)`, which never triggers for a 0 royalty). This same truncating arithmetic is duplicated in the offer-preview helper: [2](#0-1) 

The result is used directly to build the royalty `CreateCoin` payment inside `make_nft1_offer`: [3](#0-2) 

and the offer-building code explicitly skips creating a royalty payout spend entirely once the summed royalty is 0: [4](#0-3) 

Because there is no minimum-purchase or minimum-royalty enforcement anywhere in the offer path, a party can repeatedly create/accept NFT-for-fungible-asset offers using amounts small enough that `compute_royalty_amount` truncates to zero, and the royalty puzzle hash configured by the NFT creator (`royalty_address`/`royalty_percentage` from the transfer program, see `chia/wallet/nft_wallet/transfer_program_puzzle.py`) never receives a payout, even though many small trades in aggregate move the same total value as one large trade that would have paid royalties.

### Impact Explanation
NFT creators rely on royalty percentages embedded in the NFT's ownership/transfer layer to receive a cut on every secondary sale. By structuring trades as a sequence of sub-threshold-amount offers, any wallet user can systematically deny royalty revenue to creators while still transferring the full economic value of the NFT, undermining the guarantee that royalty-enabled NFTs enforce creator payouts on trade. This is a reachable, wallet-only exploitation path (no privileged access, malicious peer, or protocol-layer compromise needed) that falls squarely in the "offers and trades" / "NFT ownership" reachable surface.

### Likelihood Explanation
Any wallet user/offer counterparty can trigger this by simply making or accepting offers with sufficiently small fungible amounts relative to the royalty percentage — this requires no special privileges, and the wallet's own offer creation code (`make_nft1_offer`/`compute_royalty_amount`) computes and accepts a zero royalty without complaint. The likelihood is high for any NFT with a nontrivial but not enormous royalty percentage traded against small fungible amounts (e.g., low-value CATs or fractional XCH amounts), which is a realistic and easily reachable interaction pattern.

### Recommendation
Round royalty calculations in the creator's favor rather than truncating towards zero, e.g., use ceiling division (`-(-numerator // denominator)`), or enforce a minimum non-zero royalty whenever `percentage > 0` and the traded amount is non-zero, raising an error/rejecting trades whose computed royalty would be forced to 0 despite a non-zero configured percentage. This prevents users from bypassing royalty payment by decomposing a purchase into many small transactions.

### Proof of Concept
Using `compute_royalty_amount` directly (as exercised by the existing test `test_small_amount_truncates_to_zero`): [5](#0-4) 

```
compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)  # 1% royalty
# => uint64(0)
```

An attacker repeats an NFT-for-fungible offer/accept cycle using amounts (e.g. `offered_amount=50` at 1% royalty, or any amount where `amount * percentage < 10000`) so that every single trade computes a royalty of `0`, and `make_nft1_offer` skips generating any royalty payout spend at all, allowing the full value of the NFT to be transferred over many small trades while the creator's `royalty_address` puzzle hash never receives payment.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
