### Title
`ReceivedOutput::read` trusts a caller-supplied spend `offset` without binding it to the output's `script_pubkey` - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` is the wallet's record of "funds we can spend": it stores the scalar `offset` needed to derive the spending key alongside the `TxOut`/`OutPoint` being spent. Its deserializer `ReceivedOutput::read` accepts all three fields verbatim from the byte stream, with no check that `group_key + offset * G` (after TapTweak parity handling) actually corresponds to `output.script_pubkey`. The bug class of the reference report — a server accepting a client-supplied privilege parameter without validating it against server-side truth — maps directly onto Serai accepting a client-supplied spend-authority parameter (`offset`) without validating it against chain-side truth (the script actually paid to).

### Finding Description
`Scanner::scan_transaction` is the only legitimate producer of `ReceivedOutput`s: it looks up `output.script_pubkey` in `self.scripts`, a map built exclusively by `Scanner::new` and `Scanner::register_offset`, so the `offset` it stores is guaranteed to derive the exact key the output pays to (`networks/bitcoin/src/wallet/mod.rs:199-214`, `162-196`).

`ReceivedOutput::read` breaks that invariant. It reads `offset` via `Secp256k1::read_F`, then `TxOut` and `OutPoint` via `consensus_decode`, and returns the tuple unchecked (`networks/bitcoin/src/wallet/mod.rs:122-134`). Any party able to feed bytes into `read` (e.g., an untrusted peer or service supplying "received outputs" to a wallet/processor component) can pair an arbitrary `offset` with an arbitrary `output`. The consumer of `ReceivedOutput` treats `offset()` as authoritative spend authority — `TransactionMachine`/send logic offsets the threshold keys by `received.offset()` and signs for the outpoint. Because the offset was never bound to the script, the wallet will:

- report an output as received/spendable when it is not (offset does not derive the paying key, or the outpoint doesn't exist), and/or
- accept an `offset` chosen so the derived key pays to a script path controlled by the attacker — the exact hazard documented in `register_offset`: "Arbitrary offsets may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script" (`networks/bitcoin/src/wallet/mod.rs:177-179`). `read` bypasses every safeguard `register_offset` applies (even-Y enforcement via `p2tr_script_buf`, collision check, `key + offset*G` derivation, `networks/bitcoin/src/wallet/mod.rs:180-195`).

### Impact Explanation
A deserialized `ReceivedOutput` is treated as spendable balance. An attacker-supplied `(offset, output, outpoint)` tuple causes the wallet to construct and sign a spend of an output it does not control (wasting fees, corrupting change/fee math) or to credit funds that are not spendable by the intended key. Where received outputs are serialized/relayed between components before signing, this is an unauthenticated-input-to-privileged-parameter path identical in shape to CVE-2026-31874: a privilege-equivalent field (spend authority) is taken from the wire and never re-derived.

### Likelihood Explanation
Reachable wherever `ReceivedOutput::read` consumes bytes not produced by the local `Scanner`. Severity is bounded by deployment: it requires an integration that round-trips `ReceivedOutput`s through untrusted channels rather than keeping them local. No cryptographic break is needed — only byte manipulation of a serialized struct.

### Recommendation
Either remove the free-standing `read`/`write` on `ReceivedOutput` (forcing construction through `Scanner`), or add a verification step: recompute `p2tr_script_buf(self.key + GENERATOR * offset)` under the owning `Scanner`'s key and reject the `ReceivedOutput` unless it equals `output.script_pubkey`. A `Scanner::verify_received(&ReceivedOutput)` method would preserve the serialization use case while restoring the construction-time invariant.

### Proof of Concept
```rust
// Given Scanner for group key P with registered offsets, an attacker serializes:
//   offset = o (chosen so P + o*G has a script path they control, or arbitrary)
//   output = TxOut { value: 1_000_000, script_pubkey: <attacker-chosen p2tr> }
//   outpoint = <any real or fake outpoint>
// ReceivedOutput::read accepts all three fields with no consistency check
// (mod.rs:122-134). The wallet then treats `offset` as valid spend authority,
// attempting to spend `outpoint` under keys.offset(o) — funds are reported
// received but are not spendable by the threshold key as constructed by
// Scanner::register_offset would have guaranteed.
```

Uncertainty note: I verified `read` performs no offset/script binding and that `register_offset` documents the arbitrary-offset hazard, but I did not fully trace `send.rs`'s consumption of `offset()`; the concrete loss path assumes downstream code spends `outpoint` under `keys.offset(offset)` as the struct's API implies.
