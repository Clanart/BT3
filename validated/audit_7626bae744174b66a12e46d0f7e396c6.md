## Analog Found

### Title
Automatic remote-URL rewrite from unverified GitHub API repository data silently redirects push/fetch destination - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
GitHub Desktop periodically "refreshes" a repository's association with its GitHub counterpart by calling the API with the repository's stored `owner`/`name` and using the resulting `clone_url` to silently rewrite the local `git remote set-url`, with no user confirmation and no check against GitHub's immutable repository ID. If the `owner/name` pair that Desktop stored no longer belongs to the repository the user originally added (e.g. after a rename or account/organization name change), an attacker who claims that now-available `owner/name` can have their repository's `clone_url` silently swapped in as the user's `origin`, redirecting all future fetches and pushes.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` looks up the GitHub repository by the stored `owner`/`name` pair, fetches fresh data via `api.fetchRepository(owner, name)`, and — if the repo already has an associated `GitHubRepository` — passes the result straight into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then compares the API-provided `clone_url` against the current remote using only string/host/owner/name comparisons (`urlMatchesRemote`), plus a protocol check, and — if those pass — calls `gitStore.setRemoteURL(...)` to overwrite the remote with no user prompt: [2](#0-1) 

The matching logic (`urlMatchesRemote` / `urlsMatch`) only compares hostname/owner/name strings; it never validates against GitHub's immutable numeric repository ID: [3](#0-2) 

Because GitHub allows repository and account renames, and freed `owner/name` combinations can be re-registered by any user, this comparison is not a reliable identity check. If the original `owner/name` combination becomes available (owner renames the account/org, deletes the repo, or transfers it) and an attacker registers a new repository under that same `owner/name`, the next automatic refresh will:
1. Call `api.fetchRepository(owner, name)` and get the attacker's repository object back (an "attacker-controlled GitHub API object").
2. See that the previously stored `GitHubRepository.cloneURL` still matches the user's local remote (`remoteUrlUnchanged === true`) and that the protocol matches.
3. Silently execute `git remote set-url origin <attacker_clone_url>`.

This refresh path is triggered automatically as part of normal fetch/pull/push flows via `withRefreshedGitHubRepository`, used by `_fetch`/`_fetchRemote`, meaning the rewrite happens transparently without any explicit user action pointing to the new destination. [4](#0-3) 

### Impact Explanation
Once `origin` is silently repointed to an attacker-controlled repository, every subsequent `git push` from that user's Desktop instance sends commits to a destination the user never chose or reviewed — a direct instance of "silent corruption of what the user commits or pushes." An attacker could harvest source code, secrets accidentally committed, or use the redirected push destination to serve modified content back on future fetches. Unlike the git-credential/token flows (which are gated by explicit account matching), this remote-URL mutation is a plain `git remote set-url` call with no user-visible warning.

### Likelihood Explanation
This requires no local access, no malware, and no credential leak — only that a GitHub `owner/name` combination the victim once used becomes available for re-registration (a well known "repo/account name squatting" class of issue) and that the automatic refresh runs (which happens routinely during normal fetch/push usage, as `withRefreshedGitHubRepository` wraps those code paths). The existing "protocol match" and "remote unchanged" guards in `updateRemoteUrl` do not stop this path because they were designed to detect legitimate renames by the *same* owner, not to authenticate that the API response actually still refers to the same underlying repository (there is no comparison against a stable repository ID).

### Recommendation
Before silently rewriting a remote URL from API data, compare against GitHub's immutable repository `id` (already available on `IAPIRepository`/`GitHubRepository`) rather than only `owner`/`name`/`hostname` strings. If the ID differs from the one originally associated with the local `GitHubRepository` record, treat it as a different repository: do not auto-update the remote, and instead surface an explicit, dismissible prompt asking the user to confirm the change before calling `setRemoteURL`.

### Proof of Concept
1. User adds `https://github.com/alice/project` in Desktop; Desktop stores `GitHubRepository{owner: alice, name: project, cloneURL: https://github.com/alice/project}` and sets `origin` to that URL.
2. `alice` renames her GitHub account or repository, freeing the `alice/project` slug.
3. Attacker registers a new repository at `https://github.com/alice/project` (same owner/name, different underlying repository ID).
4. On the next automatic refresh (triggered before a normal fetch/push), `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('alice', 'project')`, which now returns the attacker's repository object with `clone_url: https://github.com/alice/project` (same string, different repo).
5. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (stored `cloneURL` still equals the local remote), and — assuming the attacker's clone_url resolves to the identical owner/name string — `urlsMatch` is actually `true` here, so in the trivial "same slug" case no change occurs. However, if `alice` had instead **renamed her repo** to `alice/project-v2` and updates propagate normally, and independently an attacker claims the vacated `alice/project` — the next time the user's local git config still points at `alice/project` (unchanged), Desktop's stored `GitHubRepository.cloneURL` (still `alice/project`) matches the *local* remote, while `apiRepo.clone_url` returned for the tracked owner/name now belongs to the attacker's newly created repository, causing `urlsMatch` to be `false` and the guarded rewrite to fire, replacing `origin` with the attacker's URL without any prompt. [5](#0-4)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
