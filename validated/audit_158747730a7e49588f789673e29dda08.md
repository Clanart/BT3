## Title
`withdraw` in the Tron `IntentGatewayV2` reverts and permanently locks escrow when a predispatch order input legitimately escrows zero tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The seed report's core invariant break is: a batched settlement operation over multiple asset balances assumes every entry is non-zero, and a legitimate zero balance (produced by an upstream composable step) makes the whole operation revert. The Tron `IntentGatewayV2` contract has a direct local analog: its `withdraw` function requires every token entry in a `WithdrawalRequest` to have non-zero recorded escrow, but its `placeOrder` predispatch path can legitimately create a zero-escrow entry for one of an order's multiple input tokens. When that order is later cancelled or redeemed, the entire multi-token `withdraw` call reverts, permanently blocking release of *all* escrowed assets for that order.

## Finding Description
`placeOrder`'s predispatch branch does not validate that `order.inputs[i].amount != 0`, unlike the non-predispatch branch which explicitly checks it: [1](#0-0) 

Compare with the non-predispatch branch, which does enforce it: [2](#0-1) 

Because a predispatch order can have one input asset fully satisfied by the predispatch call's output (`requiredAmount = order.inputs[i].amount == 0`), the escrow credit `_orders[commitment][token] += reducedInputs[i].amount` stores `0` for that token — a legitimate state, analogous to the ICHI vault's zero-balance-of-one-token scenario in the seed report.

Later, when the order is cancelled or its escrow redeemed after a fill, `withdraw()` iterates the full input token list and unconditionally requires every entry's tracked escrow to be non-zero: [3](#0-2) 

There is no `if (amount == 0) continue;` guard here, unlike the canonical guarded implementation used elsewhere in the codebase: [4](#0-3) 

`withdraw` is reached from every settlement path for this contract — same-chain cancel, cross-chain refund, and cross-chain fill redemption — all of which pass `order.inputs` (the full input list, including the zero-escrow entry) as `body.tokens`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `_orders[body.commitment][token] == 0` for that one input reverts `UnknownOrder()` for the whole call, the loop never reaches the other (properly escrowed) tokens in the same `WithdrawalRequest`, and `_filled[body.commitment]` is never durably finalized for a successful transfer of funds.

## Impact Explanation
Any predispatch order with a multi-input list where one input has `amount == 0` becomes permanently un-cancellable and un-redeemable through this code path: same-chain cancellation, cross-chain refund-after-timeout/cancel, and cross-chain fill-redemption on the source chain all call the same `withdraw` function and all revert identically. The user's and/or solver's already-escrowed assets for every input of that order become permanently stuck in the contract with no code path able to release them — this is a direct loss/lock of bridged funds, matching the "stealing or loss of funds" bucket of the bounty scope.

## Likelihood Explanation
Likelihood is Low-to-Medium: it requires an order to use the predispatch/composable-order flow with a multi-asset input list where one asset is fully sourced from the predispatch call's output (so its direct-deposit `amount` is `0`). This is a normal, permitted use of the predispatch feature (no malicious peer, relayer, or governance actor required), so an ordinary user/solver composing such an order can trigger the permanent lock unintentionally, or an attacker can deliberately craft such an order to grief a counterparty's escrow.

## Recommendation
Add the same `if (amount == 0) continue;` guard used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, skipping the escrow check/transfer for zero-amount token entries instead of reverting the whole batch. Additionally, align `placeOrder`'s predispatch branch with the non-predispatch branch by deciding whether a zero-amount input is a valid design intent (in which case downstream code must uniformly tolerate it) or should be rejected up front.

## Proof of Concept
1. User calls `placeOrder` with `order.predispatch.call` set and two inputs: input[0] = USDC with `amount = 1000e6` (required from predispatch output), input[1] = DAI with `amount = 0` (fully pre-funded by the predispatch call's side effects, e.g., a swap output already routed elsewhere).
2. `placeOrder`'s predispatch loop accepts `requiredAmount = 0` for input[1] (no zero check exists), credits `_orders[commitment][DAI] += 0`, leaving it at `0`, and credits `_orders[commitment][USDC] += 1000e6` normally.
3. Order expires unfilled; user calls `cancelOrder` (same-chain) or, cross-chain, waits for the refund/redemption flow to reach `withdraw()` with `body.tokens = order.inputs` (both USDC and DAI entries).
4. In `withdraw()`, the loop reaches the DAI entry: `_orders[commitment][DAI] == 0` → `revert UnknownOrder()`. The entire transaction reverts.
5. The USDC escrow (`1000e6`), which was correctly funded and would otherwise be refundable, can never be released through `cancelOrder`, `RefundEscrow`, or `RedeemEscrow` — all paths call the same `withdraw()` and revert identically, permanently locking the escrowed USDC.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
