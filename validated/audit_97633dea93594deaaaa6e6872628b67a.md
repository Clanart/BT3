### Title
`cancelUnlock()` skips `updateTotalFactor`, permanently desyncing `totalBoostFactor` from real locked amounts - (File: `VLMGP.sol` / `rewards/ReferralStorage.sol`)

### Summary
`VLMGP.cancelUnlock()` zeroes out a cooldown slot (`slot.amountInCoolDown = 0`), which immediately raises the caller's `getUserTotalLocked()` value, but unlike `lock`/`lockFor`/`startUnlock` it never calls `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)`. This leaves the account's cached `userInfo.factor` in `ReferralStorage` stale (too low relative to the account's real locked balance), and consequently understates the global `totalBoostFactor` used as the denominator in `_calBoosted`.

### Finding Description
- `startUnlock()` and `_lock()` both call `IReferralStorage(referralStorage).updateTotalFactor(_account)` after changing a user's locked/cooldown state. [1](#0-0) [2](#0-1) 
- `cancelUnlock()` mutates the same state (`slot.amountInCoolDown = 0`, reducing `getUserAmountInCoolDown`, thereby increasing `getUserTotalLocked` since `getUserTotalLocked = amountInMasterMagpie - amountInCoolDown`) but has no such call: [3](#0-2) 
- `getUserTotalLocked` derivation confirming the immediate increase upon cooldown cancellation: [4](#0-3) 
- `ReferralStorage.updateTotalFactor` is the only place that reconciles `userInfo.factor` and `totalBoostFactor` with the real locked amount, and it is restricted to be called only by `vlMGP`: [5](#0-4) 
- `_calBoosted` uses the global `totalBoostFactor` as denominator for every registered referrer's boosted percentage: [6](#0-5) 
- That boosted percentage feeds directly into `trigger()`, which increases `refererInfo.rewardAmount` and `refereeInfo.rewardAmount`, later paid out via `claimReward()`: [7](#0-6) [8](#0-7) 

Because `cancelUnlock` never triggers reconciliation, once a user calls `startUnlock` (their factor drops, `totalBoostFactor` decreases correctly) and then `cancelUnlock` (their real locked balance is restored, but `totalBoostFactor`/`userInfo.factor` stay at the post-`startUnlock` reduced value), `totalBoostFactor` is left permanently understated relative to the true sum of `sqrt(getUserTotalLocked)` across all participants — until any other action on that or another account (a `lock`/`lockFor`/`startUnlock`) happens to touch and re-sync that specific user's factor, which is not guaranteed to occur.

### Impact Explanation
An understated `totalBoostFactor` inflates `_calBoosted(_account) = BoostPoint * factor[_account] / totalBoostFactor` for **every** registered referrer, globally, not just the attacker's own account, because `totalBoostFactor` is a single shared denominator. This causes the protocol to pay out a higher boosted-reward percentage than the true participation level justifies on every subsequent `trigger()` call while the desync persists, which is an over-allocation from the referral reward budget (the `MGP` balance held by `ReferralStorage` and eventually claimed via `claimReward()`). This matches the class of "theft/over-extraction of unclaimed yield" from the referral reward pool, since a finite/allocated reward budget is being distributed based on incorrect, permanently-desynced accounting rather than true current participation, and normal users have no way to detect or correct the stale `userInfo.factor` themselves (only `vlMGP` can call `updateTotalFactor`).

### Likelihood Explanation
The trigger sequence requires only unprivileged actions: `registerCode()` (permissionless), `lockFor`/`lock` (permissionless deposits into `VLMGP`), `startUnlock()`, and `cancelUnlock()` — all callable by any EOA with no special role. [9](#0-8) [3](#0-2)  No flash loan or race condition is needed; a single account performing `startUnlock` then `cancelUnlock` reliably desyncs its own `factor`/`totalBoostFactor` state every time, and it is fully repeatable by any number of accounts.

However, note: the magnitude/duration of the exploitable window depends on whether some other action re-touches that specific account's `updateTotalFactor` afterward (e.g., any subsequent `lock`/`startUnlock` on that account will resync it back using the now-correct `getUserTotalLocked`). The "splits one large lock across many addresses that each register a code" precondition described in the question is a separate concavity-based amplification (`sqrt(a)+sqrt(b) > sqrt(a+b)`) that is not itself caused by `cancelUnlock`, and combining it with the `cancelUnlock` desync does not establish a clean, quantifiable transfer of funds from one specific victim to the attacker — the inflated boosted percentage benefits **all** referrers uniformly for as long as the desync exists, and actual token payout ultimately depends on how/whether `ReferralStorage`'s `MGP` balance is a finite pre-funded pot (this funding mechanism is not shown in the reviewed code, e.g., no `fundReward`/mint call was found in `ReferralStorage.sol`).

### Recommendation
Add `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` at the end of `cancelUnlock()` (mirroring `startUnlock()` and `_lock()`), so that any change to `getUserTotalLocked()` immediately reconciles the cached `userInfo.factor` and `totalBoostFactor`. More robustly, consider deriving `_calBoosted` on-demand from live `getUserTotalLocked()` rather than caching `factor` in storage, to eliminate desync windows entirely.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `ReferralStorage`, wire `VLMGP.setReferralStorage`.
2. Account A: `lock(X)` into `VLMGP`, then `registerCode(codeA)` in `ReferralStorage`. Assert `totalBoostFactor == sqrt(X)`.
3. Account A: `startUnlock(X)` — assert `totalBoostFactor` drops to `sqrt(getUserTotalLocked(A))` (near 0).
4. Account A: `cancelUnlock(0)` — assert `getUserTotalLocked(A)` returns to `X` immediately, but assert `totalBoostFactor` (and `userInfos[A].factor` via `boosted(A)`) remain at the post-`startUnlock` low value, i.e. `totalBoostFactor != sqrt(sum of current getUserTotalLocked across all registered accounts)` — confirming the invariant break.
5. Have a referee claim via `MasterMagpie.multiclaim` triggering `ReferralStorage.trigger`, and record `refererAmount` paid to A's `rewardAmount`.
6. Compare against the `refererAmount` that would result if `totalBoostFactor` were correctly reconciled to `sqrt(X)`, showing A receives a strictly larger boosted percentage than entitled, sourced from `ReferralStorage`'s `MGP` balance.
