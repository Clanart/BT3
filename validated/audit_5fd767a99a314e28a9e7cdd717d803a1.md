### Title
Escrow release permanently reverts and locks user/solver funds when a `WithdrawalRequest` beneficiary is blacklisted by an input token (e.g. USDC) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` — invoked from `ExtrinsicIntents.onAccept()` for `RedeemEscrow`/`RefundEscrow` messages and from `onGetResponse()` for source-side cancellations — transfers each escrowed input token directly to a `beneficiary` address taken from cross-chain message data (the solver's address on `RedeemEscrow`, or `order.user` on `RefundEscrow`/cancel). If any one of these tokens (e.g. USDC) blacklists the beneficiary address, the `safeTransfer` call reverts, and because the destination chain has already irreversibly marked the order as filled, there is no other path to release the source-chain escrow — the funds become permanently locked.

### Finding Description
On a cross-chain fill, `ExtrinsicIntents._fillCrossChain` sets `_filled[commitment] = msg.sender` on the **destination** chain before delivering output tokens and dispatching a `RedeemEscrow` message back to the source chain: [1](#0-0) [2](#0-1) 

That message's beneficiary is unconditionally `msg.sender` (the solver): [3](#0-2) 

When the message arrives on the source chain, `onAccept` authenticates it and calls `_withdraw(body, isRefund, true)`: [4](#0-3) 

`_withdraw` iterates the escrowed input tokens and does a direct `IERC20.safeTransfer(beneficiary, amount)` (or a raw ETH `.call`) for each one, with no try/catch or fallback: [5](#0-4) 

If any input token is USDC (or any other blacklist-capable stablecoin) and the beneficiary address is blacklisted, `safeTransfer` reverts, which reverts the entire `onAccept` call. `EvmHost.dispatchIncoming` catches the failure only to delete the request receipt "so it can be retried": [6](#0-5) 

Retrying does not help: the blacklist condition is persistent, so every retry hits the exact same revert. Meanwhile the escrow can no longer be recovered through the cancellation path either — `_cancelFromSource` dispatches a GET query of the destination's `_filled` slot, and `onGetResponse` reverts with `Filled()` as soon as that slot is non-empty: [7](#0-6) [8](#0-7) 

Since the destination-side fill already set `_filled[commitment] = msg.sender` before the RedeemEscrow message was even dispatched, that slot is permanently non-empty — cancellation is permanently blocked the instant the destination fill succeeds, regardless of whether the source-chain escrow release ever completes. The escrowed input tokens are therefore stuck in the `IntentGatewayV2`/`ExtrinsicIntents` contract with no beneficiary-independent recovery mechanism, and no admin/governance sweep exists for `_orders[commitment][token]` balances (only generic protocol "dust" is sweepable via `SweepDust`, which does not touch per-order escrow).

The exact same unguarded-transfer pattern (no try/catch, no alternate beneficiary/dead-letter path) also affects: the `_orders[...][TRANSACTION_FEES]` payout at the end of `_withdraw` [9](#0-8)  the parallel Tron `withdraw()` implementation [10](#0-9)  and the same-chain fill path's direct transfer to `order.output.beneficiary` in `IntrinsicIntents._fillSameChain` [11](#0-10) .

### Impact Explanation
This causes irrecoverable loss of escrowed user funds. A cross-chain order's input tokens (potentially significant value) become permanently unreleasable once the corresponding beneficiary address is blacklisted for any one of the escrowed tokens — this can be the solver's own address (self-inflicted, but the user's escrowed input is still the asset at risk and is lost from the protocol's perspective) or, on the refund path, the order-placing user's own address. Because the destination-side `_filled` mapping is set unconditionally before settlement completes on the source chain, there is no fallback: cancellation is blocked as soon as fill succeeds on the destination, and the redemption call reverts deterministically forever if the beneficiary is blacklisted. This matches the bounty's "stealing or loss of funds" / permanent lock class of impact, entirely within the local `IntentGatewayV2` settlement logic, requiring no malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood is low-to-moderate but non-zero, consistent with how Sherlock ultimately scored the analogous Sentiment V2 report as Medium: USDC (and similar issuer-controlled stablecoins) blacklisting is rare but real, driven by sanctions/law-enforcement/AML actions independent of on-chain behavior, and can also be triggered by any address that later becomes tied to illicit funds. Any solver or user interacting with the Intent Gateway using USDC (or another blacklist-capable token) as an escrowed asset is exposed for the lifetime of that order.

### Recommendation
Do not let a failing beneficiary transfer block finalization of escrow state. Options:
- Wrap each token transfer in `_withdraw` in a try/catch; on failure, credit the amount to an internal "claimable" balance for the beneficiary (pull-payment pattern) instead of reverting the whole settlement.
- Decouple `_filled` marking (state finalization / replay protection) from the token transfer loop so a stuck transfer cannot prevent commitment/receipt bookkeeping from completing.
- Provide a fallback recovery path (e.g., allow the order owner to redirect unclaimed escrow to an alternate address after a timeout) rather than looping indefinitely on a message that can never succeed.

### Proof of Concept
1. User places a cross-chain order on chain A escrowing USDC as input, expecting DAI as output on chain B.
2. Solver S fills the order on chain B: output DAI is delivered, `_filled[commitment] = S` is set on chain B, and a `RedeemEscrow` message with `beneficiary = S` is dispatched to chain A.
3. Address `S` is (or later becomes) blacklisted by USDC's issuer for any reason unrelated to this protocol.
4. When the `RedeemEscrow` message is delivered on chain A, `onAccept → _withdraw` calls `IERC20(USDC).safeTransfer(S, amount)`, which reverts because `S` is blacklisted. `EvmHost.dispatchIncoming` deletes the request receipt to allow a retry, but every retry hits the identical revert.
5. The user cannot cancel/refund from chain A either: `_cancelFromSource`'s GET query reads `_filled[commitment]` on chain B, which is already non-empty (set in step 2), so `onGetResponse` reverts with `Filled()`.
6. The escrowed USDC is now permanently stuck in the `IntentGatewayV2` contract on chain A — irrecoverable by the solver, the user, or governance.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
