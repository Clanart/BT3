### Title
Unchecked `u64` accumulation of attacker-influenced `ReceivedOutput` values panics in `SignableTransaction::new`/`fee`, permanently poisoning the wallet's spend pipeline - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The OpenQ bug lets an attacker deposit with an extreme `_expiration` (`type(uint256).max`) so that a later aggregate computation (`getLockedFunds`, called by `refundDeposit`) overflows and reverts for *everyone* — one malformed deposit poisons shared accounting. The Serai analog is the unchecked `u64` summation of `ReceivedOutput::output.value` in the Bitcoin wallet: `ReceivedOutput::read` accepts an arbitrary `TxOut` (any `value` up to `u64::MAX`, any `script_pubkey`, any `offset`) from untrusted bytes, and `SignableTransaction::new` then sums those values with `sum::<u64>()` and performs `payment_sat + needed_fee` without checked arithmetic. A single crafted output poisons every transaction-building attempt that touches it, just as the malicious expiration poisons `refundDeposit` for all funders.

### Finding Description
`ReceivedOutput::read` deserializes an offset scalar, a `TxOut`, and an `OutPoint` with no semantic validation of `output.value` — only consensus-decoding is applied, so `value` may be `u64::MAX` (`Amount::from_sat(u64::MAX)` is legal at the type level even though no such output exists on-chain). The rules of this audit explicitly treat untrusted bytes fed to `ReceivedOutput::read` as attacker-reachable input.

Those bytes flow into `SignableTransaction::new`, which executes:

- `let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();` (networks/bitcoin/src/wallet/send.rs:175) — two crafted inputs each `> u64::MAX/2`, or one `u64::MAX` input combined with any legitimate scanned UTXO, overflow `u64`.
- `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` (send.rs:187) and `input_sat < (payment_sat + needed_fee)` (send.rs:215) — the addition `payment_sat + needed_fee` also panics/wraps.
- `fee()` repeats the unchecked pattern: `prevouts.iter().map(|p| p.value.to_sat()).sum::<u64>() - tx.output...` (send.rs:139-140), which both overflows the sum and underflows the subtraction.
- `needed_fee = fee_per_vbyte * vbytes` and `fee_with_change = fee_per_vbyte * vbytes_with_change` (send.rs:206, 227) multiply unchecked.
- The same pattern exists higher in the stack: `prepare_send` computes `inputs.iter().map(|input| input.balance().amount.0).sum::<u64>() - payments...sum::<u64>()` (processor/src/networks/mod.rs:436-437), and the UTXO scheduler sums `utxo.balance().amount.0` (processor/src/multisigs/scheduler/utxo.rs:212, 388) — every aggregate that iterates over the poisoned output.

Unlike Solidity 0.8 (which always reverts), Rust only panics on overflow in debug builds; in release it wraps. Both are exploitable here:

- **Panic path** (any build with `overflow-checks`, e.g. debug/CI or crates that set `overflow-checks = true`): a single poisoned `ReceivedOutput` makes `SignableTransaction::new` panic every time it is included in a Plan. Because the scheduler keeps the output in `self.utxos` and re-attempts it, the panic repeats indefinitely — the exact shape of OpenQ's permanently-reverting `getLockedFunds`.
- **Wrap path** (release): `input_sat` wraps to a small value. If it wraps below `payment_sat + needed_fee`, the function returns `NotEnoughFunds` forever for any plan containing the poisoned input — the same “deposit blocks all withdrawals” effect. If the wraps line up so the check passes, a `SignableTransaction` is produced whose committed `prevouts` contain a fabricated `u64::MAX` value; the resulting sighash (built over `Prevouts::All` at send.rs:375-389) is then signed by the honest threshold network, producing signatures over a transaction whose inputs do not exist — funds the coordinator believes it received and can spend are in fact unspendable, and the UTXO is never dropped.

### Impact Explanation
One malformed input poisons aggregate accounting for the whole wallet: every Plan, `prepare_send`, fee amortization, and branch-execution pass that iterates the poisoned output either panics or computes a wrapped `input_sat`/`fee`. This mirrors the report's “all users blocked from refunding” — here, all payments routed through the affected multisig scheduler stall, and/or the threshold group is induced to sign a transaction referencing a fabricated prevout value. On the wrap path this is additionally a value-integrity break: the transaction commits the group signature to `u64::MAX` in `prevouts`, while the real chain state contains no such output, so reported-received funds are unspendable.

### Likelihood Explanation
The rules treat bytes supplied to `ReceivedOutput::read` as untrusted-reachable. An attacker needs no validator status, no leaked key, and no collusion — only the ability to deliver malformed serialized output records (e.g., via peer/mempool or coordinator channels that deserialize scanner outputs) with `TxOut.value` near `u64::MAX`. The overflow requires only two attacker-controlled inputs, or one maximal input alongside any real scanned UTXO — directly parallel to the OpenQ attacker adding one `type(uint256).max`-expiration deposit on top of honest ones. Exploitation does not depend on debug builds: in release the wrap produces the same functional outcome (reverted/invalid transaction construction) rather than a recoverable error, because no `checked_add`/`checked_sub` converts it into a `TransactionError`.

### Recommendation
Bound and validate `TxOut.value` at the `ReceivedOutput::read` boundary (reject `value` above the maximum plausible spendable amount, e.g. `> 21e6 * 1e8` sats, mirroring “limit the max allowed `_expiration`”), and replace the raw `sum::<u64>()`, `+`, `*` and `-` in `SignableTransaction::new`/`fee`, `prepare_send`, and the UTXO scheduler with `checked_*`/`saturating_*` operations returning `TransactionError`/`NetworkError`. This turns a poisoned input into a dropped, attributable output instead of a panic or a silently wrapped aggregate.

### Proof of Concept
```rust
use bitcoin::{
  consensus::encode::serialize, absolute::LockTime, transaction::Version,
  Amount, OutPoint, ScriptBuf, Sequence, Transaction, TxIn, TxOut, Txid, Witness,
  hashes::Hash,
};
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};
use k256::Scalar;

fn forged_output(value: u64) -> ReceivedOutput {
  // Bytes an attacker supplies to ReceivedOutput::read:
  //   [32-byte scalar][consensus TxOut][consensus OutPoint]
  let mut bytes = Vec::new();
  bytes.extend_from_slice(&Scalar::ZERO.to_bytes()); // offset
  let txout = TxOut {
    value: Amount::from_sat(value),
    script_pubkey: ScriptBuf::new(), // any bytes; value is what matters
  };
  bytes.extend_from_slice(&serialize(&txout));
  let outpoint = OutPoint { txid: Txid::all_zeros(), vout: 0 };
  bytes.extend_from_slice(&serialize(&outpoint));

  ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}

#[test]
fn poisoned_received_output_blocks_all_spends() {
  // One honest-looking input plus one attacker-forged u64::MAX input
  let honest = forged_output(100_000);
  let malicious = forged_output(u64::MAX);

  let payment_script = ScriptBuf::new();
  let payments = vec![(payment_script, 50_000u64)];

  // Panics (debug/overflow-checks) on `sum::<u64>()` of input_sat,
  // or wraps to ~99_999 in release making `input_sat < payment_sat + needed_fee`
  // spuriously report NotEnoughFunds for EVERY transaction containing it —
  // the same permanent DoS as the poisoned `getLockedFunds()` refund path.
  let _ = SignableTransaction::new(
    vec![honest, malicious],
    &payments,
    None,
    None,
    1, // fee_per_vbyte
  );
}
```
