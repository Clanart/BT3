Based on my investigation, I found a concrete signature-malleability gap in Kaia's own transaction-validation code, separate from the vendored (unused) OpenZeppelin `ECDSA.sol` library.

### Title
Ethereum-typed transaction signature sanity check accepts malleable high-`s` signatures, enabling transaction-hash malleability - ([File: blockchain/types/tx_signatures.go])

### Summary
`SanityCheckSignatures`, which validates the raw `(v, r, s)` signature values of a decoded transaction, calls `crypto.ValidateSignatureValues` with `homestead=false` for Ethereum-typed transactions (EIP-1559/EIP-2930/EIP-4844/EIP-7702), which permits `s` values in the *full* secp256k1 order range instead of restricting to the lower half order. [1](#0-0) 

### Finding Description
`crypto.ValidateSignatureValues` explicitly implements the classic ECDSA malleability defense: when `homestead=true` it rejects `s` values greater than `secp256k1halfN`, but when `homestead=false` ("Frontier" mode) it allows the full range of `s`, exactly the condition that permits two valid `(r, s)` and `(r, N-s)` signatures for the same message/private key. [2](#0-1) 

`SanityCheckSignatures` is the general-purpose sanity check for decoded transactions, and for `IsEthTypedTransaction()` it invokes this function with `homestead` hard-coded to `false`: [3](#0-2) 

By contrast, the actual sender-recovery path used during signature validation (`modernSigner.Sender`/`SenderPubkey` → `RecoverTxSender`/`RecoverTxPubkeys` → `recoverPlain`/`recoverPlainCommon`) always calls `crypto.ValidateSignatureValues` with `homestead=true`: [4](#0-3) [5](#0-4) 

This means the low-`s` malleability check is enforced only in the recovery/`ValidateSender` path, not in the general `SanityCheckSignatures` sanity checker for Ethereum-typed transactions. Because Ethereum's transaction hash (`tx.Hash()`) is computed over the full encoded transaction including `(v, r, s)`, an attacker who observes a valid Ethereum-typed transaction in the mempool/gossip/bundle can flip `s → N-s` and `v` (recovery id 0↔1) to derive a *second* valid signature recovering to the exact same sender and same semantic content, but with a **different transaction hash**. Wherever code paths rely on `SanityCheckSignatures` alone (without additionally going through the homestead-true recovery path) to accept/reject or deduplicate transactions by hash — e.g., transaction-pool admission, RLP decoding sanity gates, or any downstream hash-based tracking (gasless bundle building, KIP-71 fee-payer flows, or off-chain services/bridges keyed by `tx.Hash()`) — the malleable duplicate would pass sanity checks yet be treated as a distinct transaction.

### Impact Explanation
This is state divergence / duplicate-acceptance risk: a single logical transaction can exist under two distinct valid hashes that both pass `SanityCheckSignatures`. Any component that treats transaction identity by hash (mempool dedup, replay-protection bookkeeping, gasless/bundle matching in `kaiax/gasless`, or external services watching for a specific `tx.Hash()`) could be tricked into processing the "same" transaction twice under different hashes, or an attacker could front-run/resubmit a malleable variant of someone else's transaction to disrupt hash-based tracking, matching, or fee-delegation bookkeeping. Since the actual sender-recovery logic (`ValidateSender`/`modernSigner.Sender`) does enforce the homestead-true low-s check, the sender itself cannot be spoofed and funds cannot move to an unintended recipient purely from this gap — limiting severity relative to the classic OZ advisory, but it still creates an exploitable message/hash-uniqueness violation reachable from any transaction sender.

### Likelihood Explanation
High: any unprivileged transaction sender or observer can construct the malleable signature variant using only public elliptic-curve arithmetic (no secret key needed) once a valid EIP-1559/2930/4844/7702 transaction is observed on the wire, and `SanityCheckSignatures` is the general sanity gate applied to decoded transactions of these types.

### Recommendation
Change `SanityCheckSignatures` to pass `homestead=true` (or equivalently always enforce the low-`s` malleability check) for `IsEthTypedTransaction()` in `blockchain/types/tx_signatures.go`, aligning it with the recovery path in `transaction_signing.go`, so a single canonical signature/hash is accepted for the same message.

### Proof of Concept
1. Take any valid Ethereum-typed (e.g., EIP-1559) Kaia transaction `tx` with signature `(v, r, s)` where `s` is in the upper half of the curve order (`s > secp256k1halfN`) — such a signature is fully valid ECDSA and recovers to the correct sender.
2. Call `SanityCheckSignatures(sigs, tx.Type())`; because `crypto.ValidateSignatureValues(v, r, s, false)` is used, this check passes even though `s` is in the malleable upper range.
3. Compute the malleable twin: `s' = N - s`, `v' = v XOR 1` (flip recovery bit). `(v', r, s')` recovers to the exact same public key/sender for the exact same signed message hash.
4. Re-encode the transaction with `(v', r, s')` — this produces a second, differently-hashed transaction (`tx2.Hash() != tx.Hash()`) that also passes `SanityCheckSignatures` and recovers to the same sender, demonstrating that hash-based transaction identity is not unique under this check.

// SanityCheckSignatures validates whether the signature values are valid.
// It checks the signatures from the given TxSignatures.
func SanityCheckSignatures(sigs TxSignatures, txType TxType) bool {
	if len(sigs) == 0 {
		return false
	}

	// Legacy and Eth Typed transactions have only one signature.
	sig := sigs[0]

	if txType.IsEthTypedTransaction() {
		v := byte(sig.V.Uint64())
		return crypto.ValidateSignatureValues(v, sig.R, sig.S, false)
	}

	if txType.IsLegacyTransaction() {
		return validateSignature(sig.V, sig.R, sig.S)
	}

	return sigs.ValidateSignature()
}

// ValidateSignatureValues verifies whether the signature values are valid with
// the given chain rules. The v value is assumed to be either 0 or 1.
func ValidateSignatureValues(v byte, r, s *big.Int, homestead bool) bool {
	if r.Cmp(common.Big1) < 0 || s.Cmp(common.Big1) < 0 {
		return false
	}
	// reject upper range of s values (ECDSA malleability)
	// see discussion in secp256k1/libsecp256k1/include/secp256k1.h
	if homestead && s.Cmp(secp256k1halfN) > 0 {
		return false
	}
	// Frontier: allow s to be in full N range
	return r.Cmp(secp256k1N) < 0 && s.Cmp(secp256k1N) < 0 && (v == 0 || v == 1)
}
