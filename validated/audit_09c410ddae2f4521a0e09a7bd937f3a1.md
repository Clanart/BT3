### Title
Withdrawal Signature's `SIGHASH_SINGLE|ANYONECANPAY` Scope Does Not Cover the OP_RETURN Operator-Attribution Output, Allowing Payout Credit Theft/Griefing - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The user's off-chain withdrawal signature is required to use `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . This sighash type commits only to the signer's own input and the output at the same index; it leaves every other output — including the `OP_RETURN` output that records which operator "fronted" the payout — completely unauthenticated and freely rewritable by anyone who obtains the signature.

### Finding Description
`create_payout_txhandler` builds the payout transaction with the user's payout output at index 0, an anchor at index 1, and an `OP_RETURN` containing the calling operator's x-only pubkey at index 2 [2](#0-1) . The operator's `withdraw` RPC handler takes the user-supplied `in_signature` (whose `sighash_type` is trusted from the wire and only checked to equal `SinglePlusAnyoneCanPay`) and verifies it against the computed sighash for that type [3](#0-2) . Because `SIGHASH_SINGLE|ANYONECANPAY` only binds input 0 to output 0, the signature places no constraint on the `OP_RETURN` output's content (the embedded operator pubkey) nor on which operator ultimately broadcasts the transaction.

Downstream, this `OP_RETURN` pubkey is the sole mechanism used to attribute a completed payout to a specific operator: `update_finalized_payouts` parses it directly from the confirmed on-chain payout transaction and persists it as the "payer" for that withdrawal [4](#0-3) ; `is_kickoff_malicious` later requires the kickoff's `operator_xonly_pk` to equal this DB value or the kickoff is flagged malicious [5](#0-4) ; and the bridge circuit binds the same `OP_RETURN` pubkey into `deposit_constant`, which is the on-chain custody/reimbursement binding checked in zero-knowledge [6](#0-5) .

Since the signature never commits to this pubkey, the same valid user signature can be reused to construct a payout transaction with a **different** operator's pubkey in the `OP_RETURN` (or a garbled/invalid one), or `ANYONECANPAY` lets any observer splice in extra inputs and rebroadcast their own competing version first. Whoever gets their version of the payout confirmed on-chain first is the party attributed as having "fronted" the withdrawal and becomes eligible for kickoff/reimbursement — regardless of which operator's funds (input_prevout funding, fee-rate bumping via `fund_raw_transaction`, RBF) actually paid for it in `operator.rs`'s withdrawal flow [7](#0-6) .

### Impact Explanation
This breaks the custody/attribution binding "the operator credited versus the party that paid": an operator (or any party who intercepts the signed withdrawal-input signature, e.g. via the aggregator/verifier RPC surface or gossip between operators) can front-run a legitimate operator's broadcast by substituting their own x-only pubkey into the unsigned `OP_RETURN`, claiming reimbursement rights for a payout actually funded via another operator's `fund_raw_transaction`/RBF machinery, or corrupt the field entirely to force `operator_xonly_pk_opt` to `None` and make the payout's operator unattributable, causing `is_kickoff_malicious` to treat the real fronting operator's honest kickoff as malicious. This can lead to an honest operator being permanently unable to be reimbursed for a payout they actually funded — a Critical-severity outcome per this program's classification — or to griefing/DoS-adjacent misattribution of the reimbursement chain.

### Likelihood Explanation
Exploitation requires obtaining the raw `in_signature`/`input_outpoint`/`output_script_pubkey`/`output_amount` for a pending withdrawal (delivered off-chain to operators per the design intent, and observable in the clear over the operator's gRPC withdraw call or via mempool once first broadcast) and constructing a competing payout transaction with a different `OP_RETURN` payload before/instead of the legitimate one confirms. No signing key, verifier/operator privilege, or protocol secret is needed — only unprivileged access to the already-shared, unauthenticated withdrawal signature data, making this a real unprivileged-attacker path rather than a role-privileged one.

### Recommendation
Require the withdrawal signature to cover the entire transaction (e.g. `SIGHASH_ALL`/`SIGHASH_DEFAULT`) so that the `OP_RETURN` operator-attribution output is committed to at signing time, or otherwise cryptographically bind the operator identity into data the user signs (for instance, requiring the operator's pubkey as part of the message signed off-chain and re-validated on submission), so a party's later choice of which operator gets credited cannot diverge from the transaction the user actually authorized.

### Proof of Concept
1. User signs a withdrawal input with `SIGHASH_SINGLE|ANYONECANPAY` as required by `parse_withdrawal_sig_params` [8](#0-7) , and shares `(withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount)` with operator A off-chain.
2. Operator A calls `withdraw`, which builds a payout tx via `create_payout_txhandler` embedding A's `xonly_public_key` in the `OP_RETURN` output and funds/broadcasts it [9](#0-8) .
3. Because the `OP_RETURN` output is outside the signed scope, operator B (or any party who has seen the signature, e.g. by observing A's unconfirmed transaction in the mempool before it confirms) constructs an equally-valid payout transaction from the same signature, replacing the `OP_RETURN` payload with B's own pubkey, and RBF/CPFP-races it to confirmation first.
4. `update_finalized_payouts` parses B's `OP_RETURN` from the confirmed tx and records B as the payer [4](#0-3) ; when A later sends its kickoff to be reimbursed for the funds it actually paid out, `is_kickoff_malicious` finds a mismatched `operator_xonly_pk` in the DB and flags A's honest kickoff as malicious [5](#0-4) , permanently denying A reimbursement while B (who did not actually front the user's funds via its own payout construction path) is positioned to claim the reimbursement pipeline instead.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
