## Title
Unbounded `GetRequest.keys`/verification cost lets a fee-paying app force out-of-gas batch failures in `handle_get_requests`, permanently blocking its own and co-batched requests from settling — (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
The external Coded Estate report shows that a user-controlled unbounded vector (`cancellation`), later iterated in a "cancel" transaction, can be sized by a privileged owner to force out-of-gas failures that permanently block cancellation. The local analog in Hyperbridge is `GetRequest.keys: Vec<Vec<u8>>`, a field fully controlled by the *dispatching application* (an unprivileged actor) with no length or aggregate-size cap enforced at dispatch time (`modules/ismp/core/src/dispatcher.rs`, `modules/pallets/ismp/src/dispatcher.rs`). This vector is later iterated per-request inside `Pallet::handle_get_requests` (`modules/pallets/state-coprocessor/src/impls.rs:133-155`) to perform `verify_state_proof` over every key, for every `GetRequest` batched together, before any bandwidth/fee gating rejects the caller.

### Finding Description
`DispatchGet.keys` (Substrate: `modules/pallets/ismp/src/dispatcher.rs:109-125`; EVM: `evm/src/core/EvmHost.sol:974-1013`) has no enforced maximum length or aggregate byte size anywhere in the dispatch path. Any application can dispatch a `GetRequest` with an arbitrarily large `keys` array and pay only the (fixed, size-independent at dispatch time) protocol fee.

When the relayer batches these together and submits them to the coprocessor pallet, `Pallet::handle_get_requests` iterates the whole `requests` batch and, for **each** request, calls `dest_state_machine.verify_state_proof(&host, req.keys.clone(), ...)` (line 134-138) which walks every key in that request's `keys` vector performing trie/membership verification work. Only **after** this expensive verification completes does the code call `BandwidthGate::try_consume` (line 146-151) to check/charge the app's bandwidth allowance — i.e., the metering the pallet's own doc-comment claims happens "before any state proof work" (`modules/pallets/state-coprocessor/src/lib.rs:60-64`) actually happens *after* the costly verification in the real implementation.

This inverted ordering means:
1. An app with no bandwidth allowance (or one it doesn't mind losing) can still force the coprocessor to perform unbounded verification work for an unbounded `keys` array before being rejected.
2. Because `handle_get_requests` is invoked as an unsigned inherent-like extrinsic (`pallet::validate_unsigned`) processing an entire relayer-submitted batch, and any single request in that batch causing excessive weight consumption or exceeding block weight limits will fail/abort the whole batch transaction (all-or-nothing extrinsic execution), non-malicious co-batched `GetRequest`s from other apps are also prevented from settling.
3. This is directly analogous to the reported bug class: an actor-controlled vector length with no cap, iterated in a settlement-critical path, causing gas/weight exhaustion that blocks processing — except here the actor is an ordinary unprivileged dispatching app, not a privileged NFT owner, making it a stronger, permissionless DoS/fund-lock primitive.

### Impact Explanation
This falls under "logic attacks" / transaction manipulation and potential fund loss/lock permitted by the bounty scope: fee-paying users whose `GetRequest`s get batched alongside an attacker's oversized request can have their requests fail to be processed by the coprocessor, causing relayer fees already escrowed (`_requestCommitments[commitment] = FeeMetadata(...)` in `EvmHost.sol`) to remain stuck pending eventual timeout, and repeated resubmission attempts of the same batch could keep failing if the relayer keeps re-batching the same set. It also degrades reliability of the GET-request pipeline that other cross-chain applications depend on for correct settlement.

### Likelihood Explanation
Likelihood is moderate-to-high: dispatching a `GetRequest` with a large `keys` array requires no special privilege — any contract/pallet caller can do it via the standard `dispatch(DispatchGet)` / `dispatch_request(DispatchRequest::Get(...))` entry points, and there is no visible cap on `keys.len()` or per-key size enforced in `EvmHost.sol::dispatch(DispatchGet)` or `pallet_ismp::dispatcher::dispatch_request`. The only mitigating factor is that the relayer chooses how to batch requests (`tesseract/messaging/messaging/src/get_requests.rs`) and could choose to isolate suspiciously large requests, but this is an operational/off-chain mitigation, not an enforced protocol invariant.

### Recommendation
- Enforce a hard cap on `keys.len()` (and/or aggregate encoded size of `keys`) at dispatch time in both `EvmHost.sol::dispatch(DispatchGet)` and `pallet_ismp::dispatcher::dispatch_request` for `DispatchRequest::Get`, rejecting oversized requests before they are ever committed.
- Reorder `handle_get_requests` so `BandwidthGate::try_consume` is checked (using request-declared/estimated size, e.g. `sum(keys.len())`) **before** calling `verify_state_proof`, matching the documented intent in `modules/pallets/state-coprocessor/src/lib.rs:60-64`.
- Consider processing/charging weight per-request rather than only at batch level, so a single oversized request cannot cause the entire batch's extrinsic to exceed the block weight limit and abort unrelated requests.

### Proof of Concept
1. An unprivileged contract calls `IDispatcher(host).dispatch(DispatchGet{ keys: <N very large keys>, ... })` — no size validation rejects it (`evm/src/core/EvmHost.sol:974-1013`).
2. The relayer's `process_get_request_events` groups this request together with other pending `GetRequest`s destined for the same `(dest, height)` (`tesseract/messaging/messaging/src/get_requests.rs:52-56`) and submits a single `GetRequestsWithProof` batch to the coprocessor.
3. `Pallet::handle_get_requests` iterates the batch and calls `verify_state_proof(&host, req.keys.clone(), ...)` for the attacker's oversized request (`modules/pallets/state-coprocessor/src/impls.rs:133-138`), consuming excessive weight/gas before `BandwidthGate::try_consume` is ever reached.
4. If this exceeds the extrinsic's allotted weight/gas, the whole unsigned extrinsic — including the co-batched legitimate `GetRequest`s from unrelated apps — fails, leaving their pending fee-escrowed requests unresolved. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

            path[0] = IUniswapV2Router02(uniswapV2).WETH();

            );
        } else if (get.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), get.fee);
        }

        uint64 timeoutTimestamp = get.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(get.timeout);
        GetRequest memory request = GetRequest({
            source: host(),
            dest: get.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            timeoutTimestamp: timeoutTimestamp,
            keys: get.keys,
            height: get.height,
            context: get.context
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: _msgSender(), fee: get.fee});
        emit GetRequestEvent({
            source: string(request.source),
            dest: string(request.dest),
            from: request.from,
            keys: request.keys,
            nonce: request.nonce,
            height: request.height,
            context: request.context,
            timeoutTimestamp: request.timeoutTimestamp,
            fee: get.fee
        });
