### Title
`allowFileProtocol` re-enables `protocol.file.allow=always` for `git submodule update` on every checkout, letting a malicious repository force-clone attacker-chosen local `file://` submodule paths - ([File: app/src/lib/git/submodule.ts])

### Summary
Modern Git disables the `file://` transport for submodules by default (`protocol.file.allow=user`) specifically to stop a cloned/malicious repository from silently pulling in arbitrary local paths as "submodules." `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` re-enables this protection bypass with `-c protocol.file.allow=always` whenever `allowFileProtocol` is `true`, and this flag is threaded through `checkoutBranch`/`checkoutCommit` in `app/src/lib/git/checkout.ts`. [1](#0-0) [2](#0-1) 

### Finding Description
`updateSubmodulesAfterOperation` builds its `git submodule update --init --recursive` argument list based solely on the boolean `allowFileProtocol` passed in by the caller, without any inspection of the `.gitmodules` file content, the submodule URLs, or whether the repository/remote is trusted: [3](#0-2) 

`checkoutBranch` and `checkoutCommit` simply forward whatever `allowFileProtocol` value they receive to this function, and the flag defaults to `false` only when the caller doesn't explicitly opt in — meaning any code path that checks out a branch/commit with `allowFileProtocol = true` re-enables `protocol.file.allow=always` for *that entire repository's submodule tree*, including any `.gitmodules` entries the malicious repository itself defines with `url = file:///…` pointing at arbitrary local paths (e.g. the user's SSH/config directories, or another repository/user's home directory on the same machine). [2](#0-1) 

The invariant Git's own default is protecting is: *a fetched/cloned repository (attacker-controlled) should not be able to specify local filesystem paths as submodule sources and have them silently cloned into the working tree.* By re-adding `protocol.file.allow=always` on a per-operation basis without validating the individual submodule URLs (e.g. rejecting `file://` submodules that point outside a previously known-safe location, or requiring explicit per-submodule user confirmation), the guard is defeated the moment any caller sets `allowFileProtocol = true` for a checkout of attacker-supplied content — the exact same bug class as the referenced report's core problem: a value validated/permitted broadly at one layer is consumed unconditionally at a lower layer without re-checking it against the specific, potentially-changed/attacker-controlled input (submodule URL) at the point of use.

The `test-repo`/fixture code in the repo shows this is a real, exercised code path (`app/test/unit/git/checkout-test.ts:150-189`, `app/test/helpers/repositories.ts:288-321`), confirming `allowFileProtocol=true` is a supported, reachable configuration for `checkoutBranch`. [4](#0-3) 

### Impact Explanation
If a caller invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol = true` against a branch/commit that originates from an untrusted or newly-cloned/fetched repository, `git submodule update --init --recursive` will honor `file://` submodule URLs defined in that repository's `.gitmodules`. This lets the attacker's repository clone arbitrary local filesystem paths into the working directory as a "submodule," effectively performing an unauthorized local file read into the tracked working tree (data that could subsequently be staged/committed/pushed by an unsuspecting user, i.e. silent corruption/exfiltration of local data through the git workflow). Impact classification as High is appropriate if such a call site can be reached against attacker-supplied repository content without a corresponding per-submodule URL trust check.

### Likelihood Explanation
Likelihood is Low/Medium and unverified: I was not able to fully trace, within the available indexed code, every UI call site that decides when `allowFileProtocol=true` is passed to `checkoutBranch`/`checkoutCommit` (e.g. whether it's gated to only locally-created/trusted repositories vs. any freshly cloned/PR-checkout flow). The searchable index shows the flag is plumbed and used in tests/fixtures, but the concrete decision logic for setting it to `true` in the production UI/dispatcher code was not found by the available search tools. This must be confirmed before treating this as a proven, exploitable path.

### Recommendation
- Do not gate `protocol.file.allow` at the whole-checkout-operation level; validate individual submodule URLs before allowing `file://` and restrict them to paths known to be inside the repository's own trusted clone ancestry.
- Require explicit user confirmation before initializing any submodule whose URL uses the `file://` scheme (mirroring Git's own "unsafe repository" prompts already present elsewhere in the codebase, e.g. `app/src/ui/add-repository/add-existing-repository.tsx` and `app/src/ui/missing-repository.tsx`).
- Audit all call sites that pass `allowFileProtocol = true` to confirm none of them are reachable with attacker-supplied/untrusted repository content (freshly cloned repos, PR checkouts, remote branch checkouts).

### Proof of Concept
Conceptual PoC (not fully verified against production call sites due to index limits):
1. Attacker publishes a public repository containing a `.gitmodules` entry: `url = file:///Users/victim/.ssh` (or another sensitive local path).
2. Victim clones/opens this repository in Desktop and checks out a branch/commit through a code path that sets `allowFileProtocol = true` for `checkoutBranch`/`checkoutCommit`.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which (absent the override) Git would normally refuse for `file://` submodules, cloning the victim's local directory into the tracked working tree.
4. The victim may subsequently stage/commit/push this content, exfiltrating local files through their own git history.

Given the index does not expose the exact production call sites that pass `allowFileProtocol=true`, I recommend a Devin session with full repository access to confirm reachability from untrusted repository content before treating this as confirmed-exploitable.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
