### Title
Excess native-token refunds from Uniswap swaps are silently absorbed by `EvmHost` and become unrecoverable by the payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core defect is a static, non-adjustable protocol parameter that causes value to leak out of a custodial pool because no mechanism accounts for the parameter's real-time deviation from market truth. The local analog in Hyperbridge is `EvmHost`'s native-fee-swap path: `dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()` all perform an exact-output Uniswap V2 swap using the caller's full `msg.value`, but the contract never tracks or forwards the router's leftover-ETH refund back to the paying user. That refund is absorbed into `EvmHost`'s undifferentiated native balance and can subsequently be swept by governance's `withdraw()` to an arbitrary beneficiary — i.e., funds belonging to an ordinary unprivileged user are, by design gap, redirected to the wrong beneficiary.

### Finding Description
In `dispatch(DispatchPost memory post)`: [1](#0-0) 
the host calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. This is an identical pattern in `dispatch(DispatchGet memory get)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

The canonical Uniswap V2 Router `swapETHForExactTokens` implementation computes the exact amount of ETH needed (`amounts[0] <= msg.value`) and refunds `msg.value - amounts[0]` to `msg.sender` — which, from the router's perspective, is `EvmHost` (since `EvmHost` is the caller supplying `{value: msg.value}`), not the original transaction sender (`_msgSender()`/`post.payer`). Nowhere in `EvmHost.sol`'s dispatch functions is this refund captured, tracked per-payer, or forwarded onward to the original caller.

The contract has no `receive()`/refund-accounting logic visible in the dispatch flow, so any leftover ETH becomes part of the contract's generic native balance. `IHostManager.withdraw(WithdrawParams)` supports withdrawing the native token to a `beneficiary` chosen by governance: [4](#0-3) 
which is the same pool that absorbs the un-refunded swap dust — there's no separation between "legitimate protocol revenue" and "user overpayment residue."

Because `HyperApp.quote()` — the documented off-chain fee-estimation helper — is explicitly described as producing an *approximate* value "subject to slippage" and sandwich risk: [5](#0-4) 
users/integrators are guided to send a buffer of extra native token above the quoted amount to avoid a revert from price movement between quote-time and dispatch-time. That buffer is exactly the ETH that gets refunded by the router and then trapped/misappropriated inside `EvmHost`.

### Impact Explanation
This is a genuine "loss of funds / wrong beneficiary" bug reachable by any unprivileged user through the public `dispatch()`/`fundRequest()` entry points — no relayer, prover, or admin collusion required. Every native-token payment that overshoots the exact swap cost (a routine occurrence given documented slippage/sandwich risk in fee estimation) permanently strands the excess in the host contract, where it is then indistinguishable from protocol fee revenue and can be moved by governance's `withdraw()` to a beneficiary other than the original payer. This matches the required impact class: stealing/loss of funds and transaction manipulation via lack of per-payer settlement guarantees, directly analogous to the Mantra report's "static parameter → leaked value from the pool to the wrong party under real market deviation."

### Likelihood Explanation
High. Any normal cross-chain dispatch using native-token payment (the documented, user-friendly path recommended in the docs for "one-off transactions, user-facing apps") will produce dust/excess ETH whenever the quoted amount and actual swap price diverge even slightly — which is expected behavior, not an edge case, since `quote()` is explicitly non-exact. No attacker sophistication or timing is needed; a normal user simply loses the difference every time they call `dispatch()` with native token.

### Recommendation
Track the actual amount spent (`amounts[0]` returned by `swapETHForExactTokens`) versus `msg.value`, and immediately refund the difference to `_msgSender()`/`post.payer` within `dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()`. Do not let unspent native token settle into the contract's generic balance where it can later be swept as "revenue" by `withdraw()`.

### Proof of Concept
1. User A calls `dispatch{value: 1.5 ETH}(post)` where `post.fee` requires only `1.0 ETH` worth of swap input at execution time (a routine outcome since `quote()` is approximate, per `HyperApp.sol` L71-80).
2. Inside `dispatch()` (`EvmHost.sol` L921-932), `swapETHForExactTokens{value: 1.5 ether}(post.fee, ...)` executes; the router internally computes `amounts[0] ≈ 1.0 ETH`, performs the swap, and refunds `0.5 ETH` — but refunds it to `EvmHost` (the router's `msg.sender`), not to User A.
3. `EvmHost` has no code path that captures this `0.5 ETH` refund and returns it to User A; it silently becomes part of `address(this).balance`.
4. Governance later calls `withdraw(WithdrawParams{beneficiary: treasury, amount: X, token: address(0)})` via `IHostManager`, sweeping the native balance — including User A's un-refunded `0.5 ETH` — to `treasury`, an address unrelated to User A.
5. User A has permanently lost `0.5 ETH` with no on-chain mechanism to reclaim it.
