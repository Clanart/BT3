### Title
Unbounded Python-level recursion in offer/puzzle-driver matching allows a counterparty-supplied offer to crash a wallet process (stack-overflow DoS) - ([File: chia/wallet/trading/offer.py], [File: chia/wallet/outer_puzzles.py], [File: chia/wallet/nft_wallet/singleton_outer_puzzle.py])

### Summary
The Rhai advisory is a recursive-descent statement evaluator (`eval_stmt`) that overflows the native stack on deeply nested/attacker-controlled script structure with no depth limiting. The closest reachable analog in this codebase is the Python puzzle-driver "outer puzzle" matching logic used by `chia.wallet.trading.offer.Offer` when it inspects an incoming offer's `puzzle_reveal`s. `match_puzzle()` / `SingletonOuterPuzzle.match()` / `OwnershipOuterPuzzle.match()` / `MetadataOuterPuzzle.match()` / `CROuterPuzzle.match()` (and the corresponding `get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` methods) all recurse by calling `self._match(...)` (or `self._get_inner_puzzle`, etc.) on the puzzle's uncurried "inner puzzle" with no depth bound, per `chia/wallet/nft_wallet/singleton_outer_puzzle.py:49` and `chia/wallet/nft_wallet/ownership_outer_puzzle.py:50` and `chia/wallet/vc_wallet/cr_outer_puzzle.py:36`. Because the CLVM `puzzle_reveal` bytes inside a `CoinSpend`/offer file are fully attacker-controlled and only checked structurally by cheap `uncurry()` pattern matching (`chia/wallet/puzzles/singleton_top_layer.py:179` `match_singleton_puzzle`), an attacker can construct a puzzle with an arbitrarily deep chain of nested recognized-layer curries (e.g. thousands of nested `SINGLETON_MOD`/ownership/metadata layers, each wrapping the next as its "inner puzzle"). When a wallet user's client parses such an offer (a normal wallet action reachable by any offer counterparty), `Offer._get_offered_coins()` (`chia/wallet/trading/offer.py:255`, calling `match_puzzle(parent_puzzle)`) or `TradeManager`/RPC "get offer summary" style flows drive the recursive matcher to a depth controlled entirely by the attacker, causing a Python `RecursionError` or, at sufficiently large depth, a genuine C-stack overflow crash of the wallet process — a spend-triggered transaction-processing halt.

### Finding Description
`chia.types.blockchain_format.program.Program` intentionally implements `sha256_treehash()` iteratively "to avoid Python recursion limits on deeply nested CLVM" (`chia/types/blockchain_format/tree_hash.py:1-7`), showing the project is aware that untrusted CLVM trees must not drive unbounded Python recursion. That discipline was not applied to the wallet's puzzle-driver "outer puzzle" abstraction.

`chia/wallet/outer_puzzles.py:49-54` defines `match_puzzle()`, which iterates known drivers (`CAT`, `SINGLETON`, `METADATA`, `OWNERSHIP`, `CR`, `REVOCATION_LAYER`) and calls `driver.match(puzzle)`. Each driver's `match()` implementation:

- Uncurries the outer puzzle (`match_singleton_puzzle`, `match_ownership_layer_puzzle`, `match_metadata_layer_puzzle`, `match_cr_layer`) using only a mod-hash/shape check — cheap and unauthenticated.
- Then recurses on the "inner puzzle" it just extracted by calling `self._match(UnknownPuzzle(known_program=inner_puzzle))` — see `chia/wallet/nft_wallet/singleton_outer_puzzle.py:49`, `chia/wallet/nft_wallet/ownership_outer_puzzle.py:50`, `chia/wallet/nft_wallet/metadata_outer_puzzle.py:48`, `chia/wallet/vc_wallet/cr_outer_puzzle.py:36`.
- `_match` is bound back to `match_puzzle` itself (`function_args = (match_puzzle, ...)` in `chia/wallet/outer_puzzles.py:79`), so this is mutual/self recursion with no depth cap, no cost accounting, and no CLVM execution cost limit protecting it (this is pure Python object traversal, not metered CLVM execution).

The same unbounded-recursion pattern exists in `construct()`, `get_inner_puzzle()`, `get_inner_solution()`, and `solve()` on every one of these driver classes, and in `PuzzleInfo.also()`/`check_type()` (`chia/wallet/puzzle_drivers.py:60-79`), which also recurses through attacker-controlled "also" chains.

An attacker crafts a `puzzle_reveal` that is a chain of `N` nested recognized layers (e.g., `SINGLETON_MOD` curried around another `SINGLETON_MOD`-wrapped puzzle, and so on `N` times), where `N` is large enough to exceed Python's/CPython C-stack recursion budget (a few thousand frames is typically enough; CPython's default `sys.setrecursionlimit` is 1000, but many services raise this limit, and mutually recursive calls through multiple stack frames per layer accelerate stack exhaustion; sufficiently large `N` can exhaust the actual OS thread stack before Python's recursion-limit check even fires, causing a hard interpreter crash rather than a catchable `RecursionError`). This puzzle costs the attacker essentially nothing to construct — it does not need to be a valid, spendable puzzle; it only needs to *uncurry* to the expected shape at each layer so `match()`/`get_inner_puzzle()` keeps recursing before any semantic/consensus check on the inner content ever happens.

The reachable trigger is `Offer` parsing of a received/counterparty-supplied offer file or `CoinSpend`: `chia/wallet/trading/offer.py:255` calls `match_puzzle(parent_puzzle)` on every coin spend's `puzzle_reveal` inside `_get_offered_coins()`, which backs the `_offered_coins` cache computed for any loaded `Offer` (e.g. when a user opens/inspects an offer file, or a wallet queries `get_offer_summary`/`take_offer` style RPCs). `Offer.from_spend_bundle()` (`chia/wallet/trading/offer.py:634`) similarly calls `match_puzzle` on every `coin_spend.puzzle_reveal`. None of these call sites impose a puzzle-depth limit before invoking the recursive matcher.

### Impact Explanation
This is a spend/offer-triggered transaction-processing halt: a wallet process (CLI wallet, GUI wallet backend, or any RPC caller that loads and inspects an untrusted offer file or spend bundle) can be crashed or DoS'd by a single malicious offer/CoinSpend supplied by any offer counterparty or spend-bundle submitter, with no signature or privilege required. This matches the "spend-triggered transaction-processing halt" impact category permitted by the validation rules. It does not by itself enable unauthorized coin movement or supply inflation, so its severity is bounded to availability impact on the wallet component that parses the malicious data (CWE-674/CWE-120 analog: uncontrolled recursion on attacker input, no depth bound).

### Likelihood Explanation
Likelihood is high for reachability (any counterparty can hand a wallet an offer file, and offer inspection/summary is a routine wallet operation performed before any funds are committed), but the exact crash depth/behavior (`RecursionError` exception vs. genuine process-level stack overflow) depends on CPython's configured recursion limit and platform thread-stack size, which I could not verify from the indexed code (no explicit `sys.setrecursionlimit` override was found in the searched files). This is a caveat on severity/likelihood that a background agent or maintainer should confirm empirically.

### Recommendation
- Add an explicit depth/iteration cap when walking "outer puzzle" layers in `match_puzzle()`, `construct_puzzle()`, `get_inner_puzzle()`, `get_inner_solution()`, and `solve_puzzle()` in `chia/wallet/outer_puzzles.py` and each driver class (`SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`, `TransferProgramPuzzle`), converting the recursive `self._match`/`self._construct`/etc. chains into an explicit iterative loop with a bounded maximum layer count (mirroring the non-recursive design already used in `sha256_treehash`).
- Apply the same bound to `PuzzleInfo.also()`-based recursion in `chia/wallet/puzzle_drivers.py`.
- Reject/short-circuit offers or coin spends whose `puzzle_reveal` exceeds a reasonable curry/uncurry nesting depth before invoking `match_puzzle()` in `Offer._get_offered_coins()` and `Offer.from_spend_bundle()`.

### Proof of Concept
Conceptual PoC (structure, not exact bytes):
1. Build `inner = OFFER_MOD` (or any trivial puzzle).
2. Repeat `N` times (e.g. `N = 50_000`): `inner = SINGLETON_MOD.curry((SINGLETON_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_HASH)), inner)` to produce a puzzle with `N` nested singleton-shaped layers, without ever actually laying out a valid singleton lineage/launcher coin (structural shape is enough to satisfy `match_singleton_puzzle`'s `uncurry()`/mod check).
3. Embed this puzzle as the `puzzle_reveal` of a `CoinSpend` inside a `WalletSpendBundle`, and wrap it as an `Offer` (`Offer.from_spend_bundle`) or serialize/send it as a bech32 offer file.
4. Have a victim wallet load the offer (e.g. via `Offer.from_bech32`/`from_spend_bundle` then inspect it, which triggers `_get_offered_coins()` → `match_puzzle()` → `SingletonOuterPuzzle.match()` recursing `N` times).
5. Observe Python raising `RecursionError` (uncaught in some call paths) or, for very large `N`/tight thread stacks, a hard process crash — halting wallet transaction/offer processing.

I was not able to directly execute or observe this in the sandbox (no code execution tool available in ask-only mode); the recursion structure and reachable call chain are confirmed from source, but the exact `N` needed to overflow the process stack versus merely raising a catchable `RecursionError` was not empirically verified.
