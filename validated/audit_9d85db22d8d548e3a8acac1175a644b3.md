## Vulnerability Confirmed

### Title
Attacker-controlled `_convertRatio` with zero slippage protection in `SmartWomConvert.convert` lets flash-loan price manipulation inflate locked mWom balance, which subsequently inflates tiered MGP rewards in `ArbWomUp3.getRewardAmount` - ([File: wombat/ArbWomUp3.sol, wombat/SmartWomConvert.sol])

### Summary
`ArbWomUp3._deposit` (mode 2) calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` with a hardcoded `_minRec = 0`, and the underlying `SmartWomConvert._convertFor` also swaps through the router with `amountOutMin = 0`. Since `_convertRatio` is fully attacker-chosen (unlike the protected `smartConvert()` entrypoint which enforces `buybackThreshold`), an attacker can route the "buyback" portion through a price-manipulated `womMWomPool` to receive an inflated `obtainedmWomAmount`, which is then locked in `mWomSV` under the attacker's own address for less real WOM than it represents.

### Finding Description
In [1](#0-0) , mode-2 deposits split `_amount` into a direct 1:1 mint portion and a `toSwap` portion routed through `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)`. The `_minRec` argument is hardcoded to `0`, so no slippage/backing check is enforced by the caller.

Inside `SmartWomConvert._convertFor`, [2](#0-1) , the caller-supplied `_convertRatio` (checked only for `<= DENOMINATOR`, no threshold enforcement) determines `buybackAmount`, which is swapped through `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, ...)` — also with `amountOutMin = 0`. This is distinct from the protected `smartConvert()` function [3](#0-2) , which computes a safe `convertRatio` based on `currentRatio()` and `buybackThreshold`; `convert`/`convertFor` bypass this safety logic entirely and trust the caller's `_convertRatio` verbatim.

Because both the outer `ArbWomUp3._deposit` call and the inner router swap use zero minimum-output protection, an attacker can flash-loan-manipulate the `womMWomPool` reserves to make the wom→mWom swap leg return an inflated `obtainedmWomAmount` (more mWom out per WOM in than fair value), then reverse the manipulation after the transaction. The inflated `mWomBal` is then locked via `ILocker(mWomSV).lockFor(mWomBal, _account)` — [4](#0-3)  — crediting the attacker's `mWomSV` balance with more mWom than the real economic value of WOM they contributed.

This inflated `mWomSV.getUserTotalLocked(_account)` then feeds `ArbWomUp3.getRewardAmount`'s tiered calculation on *subsequent* `incentiveDeposit` calls: [5](#0-4) . Because `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)` and `calDoubledCounted` only subtracts the tiered value of the prior locked balance, the marginal reward for a new deposit is evaluated starting from an artificially high tier baseline. If reward multipliers increase with tier (progressive schedule), the same real additional WOM contribution lands in a higher-multiplier bracket, yielding a disproportionately larger MGP reward than the attacker's true cumulative WOM contribution justifies.

### Impact Explanation
This is a theft/inflation of unclaimed MGP emissions and a drain of value from the `womMWomPool`/`SmartWomConvert` conversion backing: the attacker extracts more mWom than their WOM is worth (draining pool value from other LPs/backing), and separately parlays the resulting inflated `mWomSV` balance into inflated future MGP locker rewards from `ArbWomUp3`. This matches the "theft of unclaimed yield" / partial protocol insolvency impact class, since MGP reward distribution and mWom/WOM backing no longer correspond to real value contributed.

### Likelihood Explanation
Requires: (1) an attacker able to flash-loan/sandwich the `womMWomPool` liquidity to move its price transiently, (2) calling `ArbWomUp3.incentiveDeposit` with `_mode = 2` and an attacker-chosen `_convertRatio` that routes funds through the manipulated buyback leg, and (3) reversing the price manipulation in the same transaction/block. All of this is achievable by an unprivileged EOA/contract with only flash-loan capital and WOM tokens — no privileged roles required. Feasibility depends on `womMWomPool` liquidity depth being shallow enough to move cheaply within one block, which is plausible for a niche wom↔mWom pool. This is a repeatable pattern each time pool liquidity allows profitable manipulation.

### Recommendation
- Enforce a real slippage/min-output check in `ArbWomUp3._deposit` when calling `convert` (do not hardcode `_minRec = 0`); compute an expected output using `estimateTotalConversion`/`currentRatio` with a bounded tolerance.
- In `SmartWomConvert.convert`/`convertFor`, do not allow arbitrary caller-supplied `_convertRatio`/`_minRec = 0`; require the same `buybackThreshold`-based safety logic used in `smartConvert()`, or use a TWAP/oracle-checked rate rather than instantaneous pool spot price for the router swap's `amountOutMin`.
- Decouple `ArbWomUp3` MGP reward tiering from `mWomSV.getUserTotalLocked` values that can be inflated through a single-block price-manipulated conversion; base tier progression on cumulative WOM actually deposited (tracked internally), not on the downstream mWom balance.

### Proof of Concept
Foundry fork test plan:
1. Fork Arbitrum mainnet at a block with live `SmartWomConvert`/`womMWomPool` state.
2. Deploy/attach `ArbWomUp3`, `SmartWomConvert`, `mWomSV` (`ILocker`), `mgp` token with sufficient balance in `ArbWomUp3`.
3. Attacker contract: flash-loan WOM, dump into `womMWomPool` to depress mWom price relative to WOM (or otherwise skew the pool so wom→mWom swap yields >1:1).
4. Call `ArbWomUp3.incentiveDeposit(amount, favorableConvertRatio, false, 2)` mid-manipulation; assert `mWomSV.getUserTotalLocked(attacker)` increases by more than the fair-value mWom equivalent of `amount` (compare against `estimateTotalConversion` computed pre-manipulation).
5. Reverse the pool manipulation (swap back) within the same transaction, repay flash loan.
6. Call `incentiveDeposit` again with a small additional `_amount` and assert the MGP reward returned by `getRewardAmount` exceeds what a non-manipulated user with the same cumulative real WOM contribution would receive (compare against a baseline user who deposited via `_mode = 2` without manipulation).
7. Assert net attacker profit (mgp reward value + mWom locked value − WOM spent − flash loan fee) > 0. [6](#0-5) [7](#0-6)

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 mWomToWom = currentRatio();

            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
