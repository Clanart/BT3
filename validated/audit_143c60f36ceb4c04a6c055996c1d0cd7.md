### Title
Identity public keys accept universally forgeable zero Schnorr signatures - ([File: crypto/schnorr/src/lib.rs](crypto/schnorr/src/lib.rs))

### Summary
`SchnorrSignature::verify` verifies the equation `R + cA - sG == identity` without rejecting the group identity as either the public key or nonce commitment. Consequently, the signature `(R = identity, s = 0)` verifies for `A = identity` under every challenge. Since `SchnorrSignature::read` only enforces canonical decoding, an attacker can submit those bytes to any caller that admits an identity key as an authorized signer.

### Finding Description
`SchnorrSignature::read` deserializes `R` through `C::read_G` and `s` through `C::read_F`, with no identity rejection for `R` in this generic path. `Ciphersuite::read_G` accepts any canonical `GroupEncoding` result and only rejects invalid or non-canonical encodings; it does not reject the identity point.

Verification constructs the multi-exponentiation:

```text
R + cA - sG = identity
```

For attacker-supplied values:

```text
A = identity
R = identity
s = 0
```

the relation becomes `identity + c*identity - 0*G = identity`, independent of `c`. Therefore a forged signature does not require solving a challenge or finding a zero challenge.

This is the Serai analogue of treating the recovered zero address as a signer: an invalid/default identity credential is accepted by signature verification if the surrounding authorization set contains it.

### Impact Explanation
Any protocol path that stores, derives, decodes, or otherwise authorizes the identity point as a signer key and then calls `SchnorrSignature::verify` can accept a universal forged signature. Depending on the surrounding protocol, this can authorize an unintended message or incorrectly count the identity key as having signed.

This does not compromise normal nonzero signer keys. The attack requires the authorization system to admit the identity public key, analogous to a system accidentally treating `address(0)` as a valid hat wearer.

### Likelihood Explanation
The forge is deterministic once an identity key is admitted. `Ciphersuite::read_G` permits canonical identity encodings, and `SchnorrSignature::verify` has no identity-key guard. The precondition is contextual: systems that reject identity during key establishment are not exposed, while systems that accidentally store or decode identity as a signer can become universally forgeable.

### Recommendation
Treat the identity public key as an invalid signer in signature verification. In `crypto/schnorr/src/lib.rs`, reject `self.R.is_identity()` and `public_key.is_identity()` in `SchnorrSignature::verify`, and preferably reject identity `R` in `SchnorrSignature::read`. Also ensure authorization-facing key decoding uses a point reader that rejects identity rather than the permissive `Ciphersuite::read_G`.

### Proof of Concept
Conceptually, for any ciphersuite `C` and arbitrary challenge `challenge`:

```rust
let public_key = C::G::identity();
let signature = SchnorrSignature::<C> {
  R: C::G::identity(),
  s: C::F::ZERO,
};

assert!(signature.verify(public_key, challenge));
```

The verification equation becomes:

```text
identity + challenge*identity - 0*G == identity
```

so verification succeeds for every challenge and every message represented by that challenge. The relevant code is `SchnorrSignature::verify` and `batch_statements` in `crypto/schnorr/src/lib.rs:88-110`, while permissive canonical point decoding is in `crypto/ciphersuite/src/lib.rs:91-100`.
