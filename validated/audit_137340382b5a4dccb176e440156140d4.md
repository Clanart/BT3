## Title
Stale `GitHubRepository` association is never cleared when a repository's remote changes, causing branch-protection and fork/permission state to silently apply to the wrong upstream - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The audited report's bug class is: a stored struct/mapping tied to an entity is never fully cleared when the entity is "removed" or changed, so stale nested state leaks into future operations. The direct Desktop analog is `repositoryWithRefreshedGitHubRepository()` in `app-store.ts`, which by design **never clears** the `GitHubRepository` association on a local `Repository` once the remote no longer resolves to a GitHub match. The code contains an explicit acknowledgment of this: [1](#0-0) 

### Finding Description
When Desktop tries to refresh a local repository's associated GitHub metadata, it calls `matchGitHubRepository(this.accounts, remote)` [2](#0-1)  against the *current* remote URL. If the match fails (`match` is `null`), the function returns the repository **unchanged**, keeping whatever `gitHubRepository` object (owner, permissions hash, protected-branch cache, fork/parent linkage) was previously persisted: [3](#0-2) 

This is the exact analog of the audited struct-with-mapping problem: the association record is a compound value (owner, permissions, protected branches via `RepositoriesStore.protectionEnabledForBranchCache` / `branchProtectionSettingsFoundCache`, keyed by `GitHubRepository.dbID`) [4](#0-3)  that is never invalidated when the underlying remote it was derived from is swapped for a different (attacker-controlled) one. Only the *reachable via a matched account* path updates the association; when the remote points somewhere Desktop can't match to a signed-in account, the old, previously-trusted repository record is retained indefinitely.

An attacker who controls a fetched/cloned repository's remote configuration (e.g. via a malicious `.git/config`, a submodule, or a script that rewrites `origin` after clone) can rewrite the remote URL after the association was already established with a legitimate GitHub repo. Because the match-fails path bails out early, Desktop continues to use the stale `GitHubRepository` (its cached protected-branch/permission data and endpoint-derived account selection via `getAccountForRepository`) for later decisions - even though the actual git remote the user is fetching/pushing to has changed.

### Impact Explanation
- Branch-protection related UI/logic (`refreshBranchProtectionState`, `protectionEnabledForBranchCache`) keyed by the stale `dbID` may continue to report protections/permissions belonging to the old repository rather than the one Desktop is now actually talking to, silently misleading the user about whether their target branch is protected.
- `getAccountForRepository`/`withRefreshedGitHubRepository` [5](#0-4)  uses the retained `gitHubRepository.endpoint` to decide which authenticated `Account` to associate with the repository for API calls (issues, PRs, fork settings), so operations can keep being attributed to the old, no-longer-relevant upstream even though the local remote has silently diverged.
- This is a silent-corruption-of-trust-state class issue: nothing in the UI signals that the "known" GitHub repository the user sees (name, fork/parent chain, protections) no longer corresponds to where their commits will actually be pushed/fetched.

### Likelihood Explanation
The vulnerable path triggers any time `matchGitHubRepository` fails to resolve the current remote to an account the user is signed into — which is the common/expected condition after a remote is changed to a URL that isn't recognized (e.g., a different host, or a repo not owned by a signed-in account). The comment in the code (`app-store.ts:4880-4882`, referencing `desktop/desktop#1144`) shows the maintainers are aware this is a known, long-standing, deliberate gap rather than a hardened invariant — meaning there is no guard actively preventing exploitation of stale state once a remote is altered.

### Recommendation
Treat a non-matching remote as a signal to actively invalidate (not just skip-refreshing) the existing `GitHubRepository` association and its dependent caches (`protectionEnabledForBranchCache`, `branchProtectionSettingsFoundCache`, `lastStashCheckCache`), rather than silently returning the previously cached repository object. At minimum, re-validate that the persisted `GitHubRepository.cloneURL`/`htmlURL` still matches the live remote (`repositoryMatchesRemote`) before reusing any cached permission/protection state for decisions that affect what/where the user pushes.

### Proof of Concept
Conceptual repro (based on local code paths; not independently executed):
1. Clone/add a repository whose `origin` points to `https://github.com/org/legit-repo`; Desktop calls `repositoryWithRefreshedGitHubRepository` and persists a `GitHubRepository` record with permissions/branch-protection info for `org/legit-repo`.
2. Attacker-controlled content in that repo (e.g. a post-checkout hook, or a submodule init script) rewrites `origin` to `https://attacker-host/other-repo`, an endpoint Desktop has no signed-in account for.
3. On next refresh, `matchGitHubRepository` returns `null` for the new remote [2](#0-1) , so `repositoryWithRefreshedGitHubRepository` bails out and keeps returning the stale `org/legit-repo` `GitHubRepository` [3](#0-2) .
4. The UI continues to show branch protection/permission state and account association for `org/legit-repo` while `git push`/`git fetch` now actually operate against `attacker-host/other-repo`.

**Note on confidence:** I verified the code paths (`matchGitHubRepository`, `repositoryWithRefreshedGitHubRepository`, the caches in `RepositoriesStore`) exist exactly as described and that the "never clear" behavior is explicit and intentional per the inline TODO/issue reference. I was not able to trace the full downstream UI consequences (e.g., exactly which dialogs display the stale protection state, or whether push/fetch credential selection is also affected) within the available tool budget, so the precise blast radius on credential exfiltration versus UI/state misrepresentation should be confirmed by a maintainer or a live session before treating this as a high-severity finding.

    let updatedRepository = repository
    const account: Account | null = getAccountForRepository(
      this.accounts,
      updatedRepository
    )

    // tried to associate the repository with a GitHub repository, or that

        repository

  }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
