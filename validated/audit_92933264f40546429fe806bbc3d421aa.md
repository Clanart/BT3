## Finding Summary

The Vault bug is a classic **check‑then‑settle race**: a withdrawal amount is validated against a balance snapshot taken at *request* time, but the balance/state can be mutated before the deferred *settlement* step consumes it, and the settlement code has no tolerance for that drift — it just reverts (or, in Agave's case, panics) the whole batch.

Agave has a structurally identical two‑phase flow: **partitioned epoch rewards**. At the epoch boundary, `Bank::calculate_rewards_for_partitioning` snapshots every stake account's delegation/lamports and pre‑computes the exact post‑reward `Stake` state that should be written back. That result is cached and only *applied* to the live stake account many blocks later, in `store_stake_accounts_in_partition` / `build_updated_stake_reward`, which loads the account fresh from `stakes_cache` at distribution time.

### Title
Stale-reward assertion panic on stake accounts mutated between epoch‑reward calculation and partitioned distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Finding Description
`build_updated_stake_reward` re-derives the live stake account at distribution time and then hard-asserts that it matches the delegation value computed at the earlier *calculation* phase: [1](#0-0) 

Two invariants are assumed but not actually re-verified against current chain state:

1. `let StakeStateV2::Stake(meta, stake, flags) = stake_state else { unreachable!(...) }` — assumes the stake account can never end up in a non-`Stake` variant (e.g. after being fully merged/emptied) between calculation and distribution.
2. `assert_eq!(expected_delegation, new_stake.delegation.stake, ...)` — assumes the account's `delegation.stake` at distribution time is *exactly* the pre-calculated value plus the pre-calculated reward, whenever the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is inactive: [2](#0-1) 

The surrounding comment openly states the code's reliance on an external guarantee it does not itself enforce: [3](#0-2) 
"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."

This is exactly the Vault pattern: a value is computed once (queued withdrawal / pre-computed reward-adjusted stake), and a *different*, later phase (settlement / distribution) assumes the underlying account hasn't changed in the meantime. Between the calculation block and the last distribution block (`REWARD_CALCULATION_NUM_BLOCKS` plus up to 10% of the epoch's slots — see `get_reward_distribution_num_blocks`), the delegation is fully live and can be mutated by ordinary user transactions: `Split`, `Merge`, `Redelegate`, `Deactivate`+`Withdraw`, or a plain lamport transfer into the stake account changing its rent-adjusted delegation math. During this same window `recalculate_partitioned_rewards_if_active` is used to patch up totals after a *root* change, but it does not protect every intervening delegation mutation, and the assert/`unreachable!` in `build_updated_stake_reward` runs on every distribution block regardless. [4](#0-3) 

I could not, within the available index, locate any stake-program-side enforcement (e.g., an `EpochRewardsActive`-style rejection of stake-mutating instructions while `EpochRewardStatus::Active`) that would actually make the comment's "stake-program restrictions" claim true. `get_reward_interval()`/`is_calculated()`/`is_partitioned()` only exist in `runtime/src/bank/partitioned_epoch_rewards/mod.rs`, and grepping the stake program and SVM callback paths for any interval check returned nothing. This is the key unverified assumption that would need confirmation with full source access (index size limits may be hiding such a check if it exists elsewhere); if it truly does not exist, both the `assert_eq!` and the `unreachable!()` are directly reachable from ordinary, non-malicious user transactions.

### Impact Explanation
`assert_eq!`/`unreachable!()` failures inside `Bank::distribute_partitioned_epoch_rewards` execute deterministically as part of normal block/epoch processing on every validator replaying the same slot. A panic here is not a per-node crash from a bad RPC request — it is triggered by state that is part of the canonical, agreed-upon ledger (the stake account contents at the relevant slot), so *every* validator that processes that block hits the same panic. That is a cluster-wide consensus halt, the most severe impact category listed as valid for this exercise.

### Likelihood Explanation
Reaching this code path only requires a stake authority performing ordinary permitted operations (merge, split, redelegate, or crediting lamports to the stake account) on a delegation that has already been included in the epoch's reward calculation but not yet distributed — a multi-block window that is easily targeted since `distribution_starting_block_height` and `num_partitions` are derivable from the public `EpochRewards` sysvar. No validator/node compromise, leaked keys, or malicious peer assumption is required — only a stake authority acting within its normal privileges during a public, predictable time window. The main open question is whether a stake-program-side interval guard (not found via search) neutralizes this; if that guard is present and effective, the path is not reachable and there is no vulnerability. If absent, the path is trivially reachable.

### Recommendation
`build_updated_stake_reward` should not `assert_eq!`/`unreachable!()` on a live, attacker-influenced delegation value. Instead it should treat any mismatch between the pre-computed reward and the account's actual state at distribution time the same way `AccountNotFound`/`ArithmeticOverflow` are already handled — as a recoverable `DistributionError` that burns/logs the reward for that entry rather than panicking the whole block. Separately, the actual stake-program-side restriction implied by the comment ("further state mutation prevented by stake-program restrictions") should be verified to exist and be enforced for every stake-mutating instruction (`Split`, `Merge`, `Redelegate`, `Withdraw`, `Deactivate`, and lamport transfers) for the full calculation-to-distribution window, not just partial cases.

### Proof of Concept
Conceptual reproduction (would need to be validated on a running localnet, since I cannot execute code):
1. Delegate/keep an active stake account `S` through an epoch boundary so it is included in `calculate_rewards_for_partitioning`'s snapshot, producing a `PartitionedStakeReward` with a fixed `new_stake.delegation.stake`. [5](#0-4) 
2. Before the block at `distribution_starting_block_height + partition_index_of(S)` is produced, submit a normal `Merge` or `Split` transaction that changes `S`'s `delegation.stake` on-chain (assuming no stake-program guard blocks it — unverified in this index).
3. When the distribution block executes `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward`, the live `stake.delegation.stake` no longer equals `expected_delegation`, triggering the `assert_eq!` panic (or the `unreachable!()` if the account's `StakeStateV2` variant changed), and taking down every validator processing that slot. [2](#0-1) 

**Caveat:** I was unable to conclusively confirm or rule out an existing stake-program-level restriction that prevents these mutating instructions from executing while epoch rewards are active for a given account, given the index's coverage limits. Starting a full Devin session with complete repository access would let you grep the entire `programs/stake` and `svm` trees for any `RewardInterval`/`EpochRewardsActive` guard to determine definitively whether this path is reachable in practice.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(

        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }
