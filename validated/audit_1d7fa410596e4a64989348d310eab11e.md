### Title
Zero-cost dedup remainder causes `ZeroDivisionError` in `Mempool.create_bundle_from_mempool_items()` - ([File: chia/full_node/mempool.py])

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `item_cost = cost - cost_saving` for every mempool item considered for block inclusion and then unconditionally divides `fee / item_cost` for logging purposes. If `item_cost` reaches exactly `0`, this raises an unhandled `ZeroDivisionError`, crashing block-template generation — directly analogous to the reported DODO GSP bug where `totalShares == 0` makes a division revert.

### Finding Description
In `chia/full_node/mempool.py`, `create_bundle_from_mempool_items()` iterates mempool items ordered by fee priority and, for each item, computes: [1](#0-0) 

`cost` is `item.conds.cost`, the item's full CLVM execution cost. `cost_saving` is produced by `IdenticalSpendDedup.get_deduplication_info()`, which sums the previously-recorded cost of every coin spend in the current item that is `eligible_for_dedup` and whose identical solution was already included by a higher-priority item earlier in the same block-building pass: [2](#0-1) 

Dedup-eligible spends are settlement/offer completion spends (e.g. `OFFER_MOD` coin spends used to settle CAT/NFT/XCH offers), which characteristically require no signature. A spend bundle can legitimately consist of nothing but such a spend (see how `Offer.to_valid_spend()`/`to_spend_bundle()` build unsigned, dedup-eligible settlement coin spends with `G2Element()`): [3](#0-2) 

If a mempool item's *entire* cost is attributable to a single dedup-eligible coin spend (no other coins, no aggregated-signature overhead), and that exact coin/solution pair was already deduplicated against an earlier, higher-fee-rate item in the same block-building pass, then `cost_saving` becomes exactly equal to `cost`, making `item_cost == 0`. The subsequent `fee / item_cost` at line 668 then raises `ZeroDivisionError`, which propagates out of `create_bundle_from_mempool_items()`.

This directly mirrors the reported bug class: an unguarded division whose divisor (`totalShares` in the original report, `item_cost` here) can become `0` under attacker-influenced/legitimate-but-unchecked conditions, causing the enclosing function to revert/crash.

### Impact Explanation
`create_bundle_from_mempool_items()` is invoked from block-template/farming code paths (`Mempool`'s block-building logic used by the full node to assemble a block from the mempool). An uncaught `ZeroDivisionError` here halts the current block-building attempt, which is a spend-triggered transaction-processing halt — the exact impact category called out as acceptable evidence in this analysis ("a spend-triggered transaction-processing halt"). Because block building is a core, repeatedly-invoked full-node operation, an attacker who can get two conflicting/duplicate dedup-eligible spend bundles admitted to the mempool (which any unprivileged spend-bundle submitter can do, since settlement/offer spends require no private key) can reliably trigger this crash whenever the node attempts to build a block containing both items.

### Likelihood Explanation
Likelihood is moderate-to-high because:
- Dedup eligibility applies to standard, widely-used settlement puzzles (offer completion spends), which are unsigned and can be submitted as free-standing single-coin spend bundles by any wallet user or offer counterparty.
- The mempool's own conflict-resolution logic explicitly permits two mempool items to spend the *same* coin with the *same* solution when both are dedup-eligible (this is the intended optimization), so constructing the triggering scenario does not require breaking any existing admission invariant — it only requires that the isolated single-coin item's total cost equal exactly the dedup-recorded cost of that coin, which is plausible for a minimal item that carries no other coins and no signature overhead.
- No test coverage was found guarding this specific zero-remainder edge case; the division is performed unconditionally purely for a log statement.

### Recommendation
Guard the division before use, e.g.:
```python
item_cost = cost - cost_saving
fee_per_cost = fee / item_cost if item_cost > 0 else float("inf")
log.info("Cumulative cost: %d, fee per cost: %0.4f, item cost: %d", cost_sum, fee_per_cost, item_cost)
```
Additionally consider treating an `item_cost == 0` item as ineligible for inclusion (skip it) rather than including a zero-cost item in the block, since a zero-cost item should not consume `MAX_SPENDS_PER_BLOCK`/other budgets without contributing its own cost.

### Proof of Concept
Conceptual PoC (requires live network/mempool access to fully validate, which is beyond static analysis):
1. Construct a single, unsigned settlement `CoinSpend` (`OFFER_MOD` completion) for a coin `C` with solution `S`, and submit it wrapped in `SpendBundle A` with a modest fee, and admit it to the mempool as an independent mempool item consisting of exactly that one coin spend (no other coins, no signature).
2. Construct a second `SpendBundle B` that also spends coin `C` with the identical solution `S` (dedup-eligible, so admission's `check_removals()` will not flag a conflict) as part of a larger bundle, with a higher fee-rate, so it sorts before `A` in `create_bundle_from_mempool_items()`'s priority ordering.
3. When the node calls `create_bundle_from_mempool_items()`, `B` is processed first and records coin `C`'s dedup cost. When `A` is then processed, `get_deduplication_info()` yields `cost_saving == A.conds.cost` (since `A` consists solely of coin `C`), making `item_cost = cost - cost_saving == 0`, and the `fee / item_cost` logging call raises `ZeroDivisionError`, aborting block-template creation.

Because I could not run this scenario against a live mempool/full node in this analysis (no execution environment available), I could not empirically confirm that `spend_data.cost` for an isolated dedup-eligible coin spend is always exactly equal to the encompassing item's `conds.cost` in all cases (e.g., possible fixed per-item overhead bytes might make `item_cost` land at a small positive number instead of exactly zero in some configurations). This should be verified with an integration test that constructs the minimal single-coin dedup-eligible mempool item described above and asserts whether `item_cost` can reach exactly `0`.
