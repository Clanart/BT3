### Title
Native-Token Overpayment to `EvmHost.dispatch`/`fundRequest` Is Permanently Trapped Instead of Refunded to the Caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all forward the caller's entire `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. Uniswap V2's `swapETHForExactTokens` refunds any unspent ETH to `msg.sender` **of the router call**, which is `EvmHost` itself (`address(this)`), not the original transaction sender. Any native-token overpayment above the exact fee-token amount required is therefore silently absorbed into the Host contract's own balance and never returned to the depositor. This mirrors the reported `StakeUpMessenger::_batchSend` bug class: an incorrect assumption about how leftover `msg.value` is handled by an inner call, leading to funds being misdirected instead of correctly accounted for.

None of these three functions capture or forward back any leftover native balance after the swap call. The Uniswap V2 Router's `swapETHForExactTokens` implementation sends `msg.value - amountIn` back via `TransferHelper.safeTransferETH(msg.sender, ...)`, and in this call context `msg.sender` is `EvmHost`, not the externally-owned account or calling contract that originally supplied the ETH. Consequently, the difference between the ETH sent and the ETH actually needed for the exact fee-token amount is absorbed into `EvmHost`'s own balance.

This is not merely theoretical: downstream code explicitly assumes the opposite behavior. The `HyperbridgeLzEndpoint.quote()` function deliberately applies a "generous 2x buffer" to fee estimates, with a comment claiming the excess will be refunded by the router to the caller: [4](#0-3) 

Similarly, the developer docs advise sending "enough" native tokens without describing any exact-amount requirement, encouraging users/integrators to send buffer amounts: [5](#0-4) 

Because `EvmHost` never reconciles or returns the router's refund to the original caller, every overpayment (whether from a 2x buffer, slippage margin, or simple user error) becomes an unintended, one-way transfer of native tokens into the Host contract, with no recorded beneficiary and no mechanism for the depositor to reclaim it.

### Impact Explanation
This is a direct loss-of-funds condition for any unprivileged caller: an ordinary user or integrating contract (e.g. `HyperFungibleTokenUpgradeable.send`, `WrappedHyperFungibleToken.send`, `IntentGatewayV2` fee-token swap paths, or any `HyperApp`-based contract calling `dispatch{value: msg.value}` or `fundRequest{value: ...}`) who supplies more native token than the exact `swapETHForExactTokens` input requirement permanently loses the difference. Since the LayerZero adapter's own `quote()` function deliberately doubles the estimate ("Apply a generous 2x buffer"), that adapter's users are guaranteed to overpay and lose roughly half of every native-fee payment to this trap, with no path to recovery — matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
Likelihood is high: no attacker collusion, malicious relayer, or privileged actor is required. Overpayment happens naturally any time a caller doesn't send the exact wei-perfect amount matching the AMM's live quote at execution time (which is virtually guaranteed given price movement between quote-time and execution, and given the codebase's own recommendation to send buffer amounts). This is a public, permissionless entrypoint reachable on every `dispatch()`/`fundRequest()` call that pays with native token.

### Recommendation
After calling `swapETHForExactTokens`, compute `msg.value - amounts[0]` (the actual native amount spent) and refund the difference back to `_msgSender()` (or the designated payer) via a low-level call, mirroring the refund pattern already used elsewhere in the codebase (e.g., `ExtrinsicIntents.sol`'s "Refund any unspent native tokens to the solver" logic). Alternatively, capture the router's `amounts` return value and use it to determine the exact `msg.value` to forward to the router, refunding the remainder explicitly within `EvmHost` rather than relying on the router to refund the correct party.

### Proof of Concept
1. Deploy/observe `EvmHost` with a configured Uniswap V2 router and fee token.
2. Caller invokes `IDispatcher(host).dispatch{value: X}(post)` where `X` is intentionally larger than the exact native amount needed to buy `post.fee` units of `feeToken` (e.g., following the LZ adapter's documented "generous 2x buffer" pattern, or simply due to price slippage between quoting and execution).
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes; the router computes `amounts[0] < X` as the exact ETH needed, deposits/swaps that amount, and refunds `X - amounts[0]` via `safeTransferETH(msg.sender, ...)` where `msg.sender` is `EvmHost`.
4. Check `EvmHost`'s ETH balance before and after the call: it increases by `X - amounts[0]`. The original caller's balance decreases by the full `X`, not `amounts[0]`.
5. No function on `EvmHost` allows the original caller to reclaim `X - amounts[0]`; it is permanently stuck in the Host contract's balance.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
