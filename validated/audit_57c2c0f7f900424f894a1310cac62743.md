### Title
Panic in `AddCosmosEventsToEVMReceiptIfApplicable` after `msCache.Write()` lets a fixed-gas post-processing hook mark a transaction as failed while its state mutations remain committed - (File: `app/receipt.go`, `app/legacyabci/deliver_tx.go`)

### Summary
The Sherlock report describes a callback that is invoked with a fixed gas cap to process an amount of work that scales with growing on-chain state, so the callback can permanently run out of gas and revert. sei-chain has an analogous fixed-gas post-processing callback — `AddCosmosEventsToEVMReceiptIfApplicable`, gated by `DeliverTxHookWasmGasLimit` — that runs on every successful Cosmos/EVM transaction *after* the transaction's own message effects have already been committed to the underlying multistore. Because this hook has no rollback and (for CW721/CW1155 event translation) no local panic recovery, an out-of-gas panic inside it is caught by `DeliverTx`'s outer `recover()` and turned into a transaction-level error, but the state changes written moments earlier by `msCache.Write()` are not undone.

### Finding Description
In `app/legacyabci/deliver_tx.go`, `DeliverTx` executes the transaction's messages and immediately persists their effects: [1](#0-0) 

```
runMsgCtx, msCache := contextCacher(ctx)
result, err = msgRunner(runMsgCtx, tx.GetMsgs())
if err == nil {
    msCache.Write()
}
```

Only *after* this unconditional `Write()`, the function invokes the `evmHook` (which is `App.AddCosmosEventsToEVMReceiptIfApplicable`) to synthesize EVM-compatible logs/receipts for wasm (CW20/CW721/CW1155 pointer) events emitted by the just-committed message: [2](#0-1) 

This hook is bounded by a fixed, governance-settable gas cap `DeliverTxHookWasmGasLimit` (default 300,000, tiny relative to normal Cosmos tx gas limits): [3](#0-2) 

```
// Note: txs with a very large number of WASM events may run out of gas due to
// additional gas consumption from EVM receipt generation and event translation
wasmToEvmEventGasLimit := app.EvmKeeper.GetDeliverTxHookWasmGasLimit(...)
wasmToEvmEventCtx := ctx.WithGasMeter(sdk.NewGasMeterWithMultiplier(ctx, wasmToEvmEventGasLimit))
```

The comment at line 49-50 explicitly acknowledges the possibility of exceeding this gas cap. Critically, only the CW20 branch protects itself: [4](#0-3) 

`translateCW721Event` (called at line 89) and `translateCW1155Event` (called at line 98) have **no** panic recovery: [5](#0-4) [6](#0-5) 

An attacker who sends a single Cosmos message (e.g. `MsgExecuteContract`) that operates on a CW721/CW1155 pointer contract and emits enough wasm events/attributes in one execution (batch mint/transfer/approve-all loops, well within ordinary Cosmos SDK gas limits of millions) can exceed the fixed 300,000-gas budget of `wasmToEvmEventCtx`. Each store read inside `GetERC721CW721Pointer`/`GetERC1155CW1155Pointer` and each log construction consumes gas from this small meter; once exhausted, the SDK gas meter panics with `ErrorOutOfGas`.

That panic propagates out of `AddCosmosEventsToEVMReceiptIfApplicable` (uncaught locally for the CW721/CW1155 paths) and is only caught by the top-level `defer recover()` in `DeliverTx`: [7](#0-6) 

```
defer func() {
    if r := recover(); r != nil {
        recoveryMW := newOutOfGasRecoveryMiddleware(gasWanted, ctx, defaultRecoveryMiddleware)
        recoveryMW = newOCCAbortRecoveryMiddleware(recoveryMW)
        err, result = processRecovery(r, recoveryMW), nil
    }
    ...
}()
```

This converts the panic into `err != nil`, `result = nil`, so the caller (block processing / `ExecTxResult`) will mark the transaction as **failed** (non-zero code). But this recovery happens at the outer function scope — it does not, and cannot, undo the `msCache.Write()` that already ran at line 117-118, before the hook was ever invoked. The message's real effects (bank sends, CW20/CW721/CW1155 balance/ownership changes, mints, burns) are already committed into `ctx.MultiStore()` (`ms`), which is shared by both `msCache` and `wasmToEvmEventCtx`.

The net effect: the transaction's underlying state mutation is durably applied to the canonical chain state, while the block/receipt/RPC surface reports the transaction as reverted/failed.

### Impact Explanation
This is a state/receipt integrity break reachable by any unprivileged transaction sender interacting with CosmWasm CW721/CW1155 pointer contracts (or any contract producing many wasm events per tx):
- Downstream systems (exchanges, bridges, wallets, block explorers, other contracts querying tx status via RPC/receipts) that gate crediting/further action on transaction success will incorrectly treat a state-changing transfer/mint/burn as not having happened, while it is in fact permanently applied on-chain. This can be leveraged to defraud counterparties who rely on the reported (false) failure status while the attacker's real transfer/mint has already succeeded — a fund-relevant inconsistency directly reachable from a public RPC/CosmWasm entrypoint.
- Because the corruption is deterministic (same events, same gas params, same code across all validators), it does not itself cause a chain split, but it does create a systemic disagreement between the authoritative state and what every honest observer (including light clients and RPC consumers) is told about that transaction's outcome.

### Likelihood Explanation
The number of wasm events per Cosmos message is entirely attacker-controlled (batch/approve-all/loop operations against CW721/CW1155 pointer contracts), and the fixed `DeliverTxHookWasmGasLimit` (default 300,000) is small relative to ordinary Cosmos SDK gas budgets, making it straightforward to exceed with a single crafted transaction. No special privileges, governance action, or multi-block setup are required — a single `MsgExecuteContract` transaction suffices.

### Recommendation
- Wrap the entire body of `AddCosmosEventsToEVMReceiptIfApplicable` (not just `translateCW20Event`) in panic recovery so an out-of-gas condition in the hook degrades gracefully (e.g., emits a partial/no synthetic receipt) instead of failing the whole transaction.
- Ensure the hook's failure can never flip a transaction's reported result from success to failure once its message effects have been committed via `msCache.Write()`; either move the hook before the write-commit point (and roll back both together on failure), or make hook failures non-fatal to the transaction result.
- Consider decoupling the wasm-to-EVM synthetic receipt/log generation from the deliver-tx critical path (e.g., defer it to end-of-block similar to other deferred EVM info) so a bounded-gas failure there cannot desynchronize reported tx status from actual state.

### Proof of Concept
Not executed (no test/sandbox access in this session). Conceptually:
1. Deploy/reference a CW721 or CW1155 pointer contract.
2. Submit a single `MsgExecuteContract` (Cosmos-native, non-EVM) that triggers a batch operation (e.g., large `approve_all`/`transfer_batch`/mint loop) producing enough `wasm` module events that `GetERC721CW721Pointer`/`translateCW721Event` (or the 1155 equivalent) consumes more than `DeliverTxHookWasmGasLimit` (300,000) gas while iterating.
3. Observe: the CW message's state effects (ownership/balance changes) are applied (verifiable by querying contract state), yet the transaction's `ExecTxResult` reports failure/out-of-gas because the panic in `translateCW721Event`/`translateCW1155Event` is caught only by `DeliverTx`'s outer recovery, after `msCache.Write()` already persisted the message's effects.
