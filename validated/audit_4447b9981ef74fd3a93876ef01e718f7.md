Based on my research, I found a concrete analog: the tokenfactory `AllowList` restriction (analogous to the `PRIVATE` DAO's intended-but-unenforced membership restriction) is checked at the `MsgSend`/`MsgMultiSend` message-server layer, but the underlying `BaseSendKeeper.SendCoins` / `SendCoinsAndWei` primitives that other privileged bank-precompile paths call do **not** re-check it — meaning the restriction can be bypassed through an alternate entry point, exactly like the PRIVATE DAO's `joinDAO` bypassing the intended type-based restriction.

### Title
Denom `AllowList` restriction bypassed via EVM Bank precompile `sendNative`/legacy `send` paths that call `SendCoins`/`SendCoinsAndWei` directly - ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
The tokenfactory `AllowList` feature is meant to restrict who may send/receive a given factory denom, similar to how a `PRIVATE` DAO is meant to restrict membership. The restriction is only enforced in `bank/keeper/msg_server.go`'s `Send`/`MultiSend` handlers, not inside `BaseSendKeeper.SendCoins`/`SendCoinsAndWei` themselves. Any code path that calls these lower-level keeper methods directly bypasses the allowlist entirely.

### Finding Description
`IsInDenomAllowList` is the sole enforcement mechanism for denom allowlisting, and it is invoked explicitly inside the bank `msgServer.Send`/`MultiSend` handlers before calling `SendCoins`/`InputOutputCoins`: [1](#0-0) 

However, `IsInDenomAllowList` is not called from within `BaseSendKeeper.SendCoins` or `SendCoinsAndWei` themselves: [2](#0-1) 

Several legacy EVM Bank precompile versions (`v552`, `v562`, `v580`, `v600`, `v603`, `v65`, `v67`) call `p.bankKeeper.SendCoins(...)` or `p.bankKeeper.SendCoinsAndWei(...)` directly instead of routing through the bank `MsgServer.Send`, which is the only place the allowlist is checked: [3](#0-2) [4](#0-3) 

Later precompile versions (`v601`, `v605`, `v620`, `v630`, `v640`) were changed to call `p.bankMsgServer.Send(...)` for the ERC20-pointer `send` path, which does go through the allowlist check: [5](#0-4) 

But the `sendNative` (usei/wei) path, present in `v603`/`v67` and presumably the current precompile version, still calls `p.bankKeeper.SendCoinsAndWei` directly — bypassing `IsInDenomAllowList` entirely (though native `usei` itself is not tokenfactory-prefixed, so this particular call is not impacted for `usei`; the risk is any direct `SendCoins`/`SendCoinsAndWei` call site elsewhere in the codebase for a tokenfactory-prefixed denom).

I was unable to fully confirm (due to index truncation) whether the *current* (non-legacy) `precompiles/bank/bank.go` `send`/`sendNative` implementation still calls `SendCoins` directly or has been updated to route exclusively through `bankMsgServer.Send`. This determines whether the bypass is live in production or was already fixed in later precompile versions.

### Impact Explanation
If any production code path (a precompile, IBC transfer hook, wasm bank-send binding, or module-to-module transfer) invokes `SendCoins`/`SendCoinsAndWei` directly for a tokenfactory-prefixed denom that has a configured `AllowList`, the allowlist restriction is silently bypassed, and any address — not just allowlisted ones — can send/receive the denom. This is a direct analog of the PRIVATE DAO issue: a restriction is configured by the creator/admin but selectively enforced only at one of several possible entry points.

### Likelihood Explanation
Likelihood depends entirely on whether any currently-active (non-legacy, in-use) code path calls `SendCoins`/`SendCoinsAndWei` directly for tokenfactory-restricted denoms. The legacy precompile files found (`v552` through `v67`) show this pattern was historically present and was fixed in some later versions by switching to `bankMsgServer.Send`, suggesting maintainers were aware of and addressed this class of bug for at least the ERC20 pointer `send` function — but I could not verify with certainty whether `sendNative` or the current active precompile version still has an unguarded direct-`SendCoins` call for a tokenfactory denom.

### Recommendation
Move the `IsInDenomAllowList` check into `BaseSendKeeper.SendCoins` and `SendCoinsAndWei` themselves (the lowest common primitive), rather than duplicating it only in the `MsgServer.Send`/`MultiSend` handlers, so that all callers — precompiles, wasm bindings, IBC hooks, and any future entry points — uniformly enforce the allowlist.

### Proof of Concept
Not independently reproducible from available context: I could not confirm the current (non-legacy) bank precompile source or another live caller that invokes `SendCoins`/`SendCoinsAndWei` directly with a tokenfactory-allowlisted denom, due to index truncation limits. A Devin session with full repository access would be needed to check `precompiles/bank/bank.go` (current version) and any other direct `SendCoins` call sites against tokenfactory-restricted denoms to construct a concrete PoC transaction that bypasses `IsInDenomAllowList`.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
