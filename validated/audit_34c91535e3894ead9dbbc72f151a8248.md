## Analysis

The MetaSwap bug's core invariant: a contract that temporarily custodies user assets during a multi-step operation exposed those assets to unauthorized access because the temporary custodian had no restriction on who could reach it. The local analog in Hyperbridge is the `CallDispatcher` contract, whose `dispatch()` entrypoint has **no caller restriction whatsoever**, combined with the fact that `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept()` callback routes bridged tokens through this same dispatcher for calldata execution but never sweeps back any residual balance.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain residual tokens left behind by HFT/WrappedHFT calldata execution - (File: `evm/src/utils/CallDispatcher.sol`, `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with zero access control — any address can call it and force the dispatcher to execute an arbitrary `Call[]`, using whatever token/ETH balance the dispatcher currently holds. [1](#0-0) 

`HyperFungibleToken.onAccept()` (and the equivalent `WrappedHyperFungibleToken.onAccept()`) mints/unlocks bridged tokens directly to a caller-supplied `to` address — which, per the documented pattern, is set to the `CallDispatcher` address so that attached calldata can spend the freshly bridged tokens — and then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`. Unlike the `IntentGatewayV2` flow (`IntentsBase._execute`), there is **no sweep-back step** here to reclaim unconsumed balances after the dispatched calls finish. [2](#0-1) [3](#0-2) 

### Finding Description
The documented composable-transfer pattern (transfer-and-swap via Uniswap, transfer-and-stake, etc.) works by minting/unlocking bridged tokens straight to the `CallDispatcher` address, then executing attached swap/approve calldata in the dispatcher's own context: [4](#0-3) 

Because real-world swaps have slippage, minimum-out tolerances, or approve-then-spend patterns that don't consume 100% of the transferred amount, some non-zero token/ETH balance routinely remains on the `CallDispatcher` after the dispatched calls complete. The `IntentGatewayV2` flow (`IntentsBase._execute`, `_fillCrossChain`) is aware of this and explicitly sweeps declared-asset balances back to the gateway after every dispatch: [5](#0-4) 

But `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept` perform **no such sweep** — the function returns immediately after `dispatch()` succeeds: [2](#0-1) 

Since `CallDispatcher.dispatch()` checks nothing about `msg.sender`, any balance left sitting on the dispatcher after such a transfer-and-swap operation is a permanent, unauthenticated bounty: an attacker simply calls `dispatch()` themselves with a `Call[]` such as `IERC20(token).transfer(attacker, dispatcher.balanceOf(...))` (or a plain native-ETH `Call` targeting the attacker) to drain it. Existing guards — `onlyHost` on `onAccept`, source-chain authentication in the HFT message, and the `NotContract`/`CallFailed` checks inside `dispatch()` — only protect the *mint/unlock* step and the target-contract-existence check; none of them restrict who may invoke `dispatch()` itself or protect balances the dispatcher already holds.

### Impact Explanation
Any residual token or native-ETH balance stranded on a `CallDispatcher` instance used by `HyperFungibleToken`/`WrappedHyperFungibleToken` for calldata-bearing transfers is directly and unconditionally stealable by any unprivileged address, at any time, with no relayer/prover/admin compromise required. This is a genuine loss-of-funds path matching the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" categories: the corrupted value is the ERC20/native balance of the `CallDispatcher` contract, and the exploit primitive is a bare call to its public `dispatch()` function.

### Likelihood Explanation
Every documented composable transfer that routes tokens "to" the `CallDispatcher` for post-mint calldata execution (approve+swap via Uniswap being the flagship example in the docs) is likely to leave at least dust behind due to slippage/rounding, and that dust accumulates with each use since nothing ever sweeps it. No malicious relayer, prover, or governance actor is needed — a single unprivileged EOA calling `dispatch()` is sufficient, making this trivially and repeatedly exploitable once any balance accrues.

### Recommendation
Add a mandatory sweep step to `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken.onAccept` (mirroring `IntentsBase._execute`) that transfers any post-dispatch residual balance of the relevant token(s) back to a safe, protocol-controlled destination (or the intended beneficiary) before returning. Alternatively/additionally, restrict `CallDispatcher.dispatch()` so it can only be invoked by its registered owning app (e.g., via a constructor-set `owner`/`caller` check), removing the fully-public entrypoint that lets anyone reach whatever balance the dispatcher is currently holding.

### Proof of Concept
1. Bridge USDC cross-chain via `HyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` encoding a `Call[]` that approves and swaps the USDC on a DEX for WETH with a minimum-out below the actual received amount (normal slippage tolerance).
2. On the destination chain, a relayer submits the proof; `onAccept()` mints USDC to the `CallDispatcher`, then executes the swap calldata. The swap consumes the USDC and delivers WETH to the dispatcher — no sweep occurs, so the WETH (and any USDC dust) sits on `CallDispatcher` indefinitely. [2](#0-1) 
3. Any third-party attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: WETH, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, WETH.balanceOf(dispatcher))})]))` directly. [1](#0-0) 
4. `dispatch()` performs no sender check, so the transfer succeeds and the attacker walks away with the stranded WETH belonging to whoever initiated the bridge transfer.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)

                IERC20(_underlying).safeTransfer(beneficiary, message.amount);

        }
