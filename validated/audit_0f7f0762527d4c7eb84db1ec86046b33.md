## Finding [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Path-traversal / symlink-escape via unguarded `Path.join(repository.path, file.path)` in the Pull Request "Files Changed" view, while the equivalent deep-link code path is protected by `resolveWithin` - (File: `app/src/lib/app-shell.ts`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`)

### Summary
The external report's core bug class is that GitHub Desktop's sibling codebase (shardus-core) implements the *same logical operation* twice, in two separate code paths, and only one of the two got a security fix while the other stayed vulnerable. The same structural flaw exists in GitHub Desktop for the operation "resolve a repo-relative file path to an absolute path before touching the filesystem." One implementation (`resolveWithin`, used by the deep-link `filepath` handler) does the safe thing: it normalizes, resolves, and — critically — calls `realpath()` on both the root and the resolved path and verifies containment, which defeats symlink-based escapes. A second, independent implementation used for Pull Request review file actions (`revealInFileManager`, `onOpenFile`, `onOpenBinaryFile`, `onFileContextMenu`) simply does `Path.join(repository.path, path)` with no containment check and no symlink resolution.

### Finding Description
`app/src/lib/path.ts` defines `resolveWithin()`, explicitly documented as returning `null` if the fully resolved path does not reside underneath the root, and it uses `fs.realpath` on both root and target so that a symlink planted inside the repo cannot be used to escape it: [4](#0-3) 

This function is used in `dispatcher.ts`'s handling of the `open-repository-from-url` deep link action (`x-github-client://openRepo/...?filepath=...`), where the filepath comes from an attacker-controlled URL: [5](#0-4) 

However, the Pull Request review UI resolves attacker-controlled file paths (the paths of files changed in a PR, which come from a fetched fork/branch under the PR author's control) using plain, unguarded `Path.join`:
- `revealInFileManager()`: [6](#0-5) 
- `onOpenFile()` / `onOpenBinaryFile()`: [2](#0-1) 
- `onFileContextMenu()`, which builds `fullPath` the same way and offers "Reveal in Finder/Explorer", "Open in external editor", and "Open with default program" menu actions on it: [7](#0-6) 

`app-shell.ts` itself documents the danger in a comment on the interface it implements ("Do not use this method with non-validated paths") right above the function that violates that very warning: [8](#0-7) 

The `file.path` values displayed and acted upon in the Pull Request "Files Changed" pane originate from the diff/changeset of a PR branch that was fetched from a remote the user does not control (a fork opening a PR). If that fork's history introduces a symlink at some path (e.g. `evil -> /Users/victim/.ssh` or `evil -> ..`) and later a "file" appears to exist underneath that symlinked path in the diff, `Path.join(repository.path, file.path)` will produce a path that — when passed to `shell.showItemInFolder`, `shell.openExternal('file://...')`, or the external editor launcher — is resolved by the OS *through* the symlink, landing outside the repository root. `pathExists()` (used to gate menu items) also follows symlinks and returns `true`, so it provides no containment guarantee.

This exactly mirrors the shardus-core bug class: fixing/guarding the "resolve path under repo root" behavior in the deep-link handler (`resolveWithin`) does nothing for the independently-implemented Pull Request file-actions handler, because the two paths never share the safe implementation.

### Impact Explanation
An attacker who opens a pull request against a repository the victim has cloned in GitHub Desktop can plant a symlink in their fork's tree and reference a path "inside" it in a changed file. When the victim reviews the PR in Desktop's "Files Changed" pane and uses "Reveal in Finder/Explorer", "Open with default program", or the external editor action on that entry, Desktop will reveal/open/execute-via-default-handler a file location chosen by the attacker outside of the cloned repository. Depending on the target (e.g. SSH keys, credential files, or an executable/document type that auto-executes via the OS default handler), this results in unintended disclosure of sensitive local files or execution of attacker-influenced content outside the repo boundary — matching the "file write or read outside the repo" / code-execution impact categories via an attacker-controlled fetched repository (PR fork), with no local access, admin rights, or social engineering beyond normal PR review required.

### Likelihood Explanation
Reviewing Pull Requests via Desktop's built-in "Open Pull Request" dialog and inspecting individual changed files (revealing in file manager, opening with default program, or opening in an external editor) is a routine, expected workflow — not an unnatural user step. The attacker only needs to get a PR opened against a repository the victim reviews with Desktop, which is a normal, low-friction action for any contributor/fork. The vulnerable code path (`Path.join` without containment checks) is reached directly by clicks in the file list context menu, so no unusual configuration is needed.

### Recommendation
Route all repo-relative path resolution used for filesystem actions (`revealInFileManager`, `onOpenFile`/`onOpenBinaryFile`, `onFileContextMenu`'s `fullPath`, and the external-editor path) through the same vetted `resolveWithin` (or `resolveWithinPosix`/`resolveWithinWin32`) helper already used by the deep-link handler in `dispatcher.ts`, rejecting the action (and surfacing an error) when the resolved path escapes `repository.path`. Consolidate this into a single shared "resolve repo file path" utility so future call sites cannot bypass the guard the way the PR file-actions path currently does.

### Proof of Concept
1. As an external contributor, create a fork of the target repository.
2. In the fork, commit a symlink at `payload` pointing to a sensitive location outside any repo (e.g. `ln -s /Users/victim/.ssh payload` on macOS/Linux, or a directory junction on Windows), then commit `payload/id_rsa` style content so the diff shows a file that appears "under" `payload/`.
3. Open a Pull Request from the fork against the target repository.
4. Victim, using GitHub Desktop, opens the PR via "Open Pull Request" and views "Files Changed".
5. Victim right-clicks the file entry with path `payload/id_rsa` and selects "Reveal in Finder/Explorer" (`revealInFileManager`, `app/src/lib/app-shell.ts:61-64`) or "Open with default program" (`onOpenFile`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx:86-97`).
6. `Path.join(repository.path, 'payload/id_rsa')` resolves through the attacker-planted symlink to `/Users/victim/.ssh/id_rsa`, which the OS then reveals/opens — outside the cloned repository, with no containment check comparable to `resolveWithin`'s `realpath`-based verification applied.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
