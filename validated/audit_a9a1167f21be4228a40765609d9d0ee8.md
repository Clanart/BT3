I found a directly relevant, already-known bug class in this repository's `BalanceHandler` mechanism, which is the closest analog to the reported "double-counting when returning assets" pattern. Notably, the repo already has a dedicated regression test (`evmd/tests/integration/balance_handler/balance_handler_test.go`) whose comment states: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [1](#0-0) 

### Analysis

`BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` and `AfterBalanceChange` only replays bank/precisebank events emitted *after* that recorded index into `StateDB.AddBalance`/`SubBalance` calls. [2](#0-1) [3](#0-2)  This is precisely analogous to the reported pattern of "credited once via one path, reconciled again via a second path" — here, a native-token bank transfer performed by a precompile (e.g. `werc20.Deposit`, which calls `p.BankKeeper.SendCoins` directly, bypassing the EVM journal) is only reflected into `StateDB` balances by replaying bank events through `AfterBalanceChange`. [4](#0-3) 

The existing test demonstrates that when precompile calls are **recursive/nested**, each nested `RunNativeAction`/`Run` invocation creates a **new** `BalanceHandler` instance via `BalanceHandlerFactory.NewBalanceHandler()` [5](#0-4) , each of which independently calls `BeforeBalanceChange` and records its own `prevEventsLen` against the **same shared `ctx.EventManager()`** event log. Because the outer handler's `prevEventsLen` was recorded before the inner call executed, and the inner call also emits bank events, the outer call's `AfterBalanceChange` will replay events that the inner handler already replayed into `StateDB` — i.e., the same bank-event-driven balance delta gets applied to `StateDB.AddBalance`/`SubBalance` more than once for overlapping event ranges, or conversely some deltas get dropped/overwritten, depending on ordering. This directly matches the reported bug class of "same underlying value counted via two different accounting paths."

### Impact

This produces a genuine divergence between the EVM `StateDB` balance (visible to `eth_getBalance`, EVM `CALL` value semantics, and any contract logic depending on `balanceOf`/native balance) and the actual `x/bank`/`x/precisebank` ledger balance that backs it. Depending on the direction of the duplication, an attacker could construct a contract that makes nested precompile calls (e.g. wrapping/unwrapping via `werc20`, or a contract calling another precompile from within a precompile-invoked callback) to inflate their EVM-visible balance without a corresponding real bank balance, or drain funds by exploiting the desync between the two ledgers. Since `StateDB.Commit()` ultimately persists whatever balance ends up in the dirty state objects to the real account record via `k.keeper.SetAccount` [6](#0-5) , and `SetBalance` mints/burns the delta against the bank keeper to reconcile [7](#0-6) , an inflated `StateDB` balance from double-counted bank events would ultimately cause the keeper to **mint the difference from thin air** to match the erroneous `StateDB` state — this is unauthorized token creation, a Critical accounting-corruption impact.

### Caveat

The repository already contains a test explicitly documenting this as a known/fixed bug pattern (`TestRecursivePrecompileCallsWithDebugPrecompile`), and its final assertions (`s.Require().Equal(10, debug_count, ...)`) suggest the code being tested may have already been patched to correct for this issue, or the test exists specifically to *prevent regression* of a previously fixed bug. [8](#0-7)  I could not fully confirm from the indexed content alone whether the current `BalanceHandler` implementation still exhibits the double-counting/desync behavior in production paths (e.g. whether `prevEventsLen` restoration/nesting is now correctly handled), or whether it was already remediated prior to this snapshot — the index does not show a git history or diff to confirm which state this corresponds to.

### Title
Balance desync/double-counting via shared `BalanceHandler` state across nested precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
Recursive/nested precompile calls each instantiate a fresh `BalanceHandler` operating over the same `ctx.EventManager()` event log. `BeforeBalanceChange`/`AfterBalanceChange` track balance deltas purely via event-list index offsets (`prevEventsLen`), which can cause bank/precisebank events to be replayed into `StateDB.AddBalance`/`SubBalance` more than once (or be missed), analogous to the reported vault bug where the same value was counted in two independent accounting structures.

### Finding Description
`BalanceHandler.BeforeBalanceChange` snapshots the event count, and `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` to translate bank `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events into `StateDB` balance mutations. [2](#0-1) [9](#0-8)  Each precompile invocation via `RunNativeAction` creates its own `BalanceHandler` from the factory [5](#0-4) , but all handlers share the single `ctx.EventManager()`. In nested-call scenarios (a precompile invoking another EVM call that in turn invokes a precompile), inner and outer handlers' recorded index ranges can overlap, causing the same underlying bank-ledger balance change to be applied to the EVM `StateDB` multiple times.

### Impact Explanation
Because `StateDB.Commit()`/`SetBalance` reconciles any discrepancy between the (possibly-corrupted) `StateDB` balance and the real bank balance by minting or burning the delta directly via the bank keeper [7](#0-6) , a double-applied `AddBalance` would cause the keeper to mint new tokens to match the inflated state — an unauthorized, irreversible increase in spendable value, i.e., Critical accounting corruption.

### Likelihood Explanation
Medium: requires an unprivileged user to deploy/call a contract performing nested precompile calls involving native-token bank transfers (e.g., wrapping via `werc20`, transfers via `bank`/`erc20`/`ics20` precompiles) inside recursive or reentrant call paths, which is a straightforward, permissionless action for any EVM user.

### Recommendation
Ensure `BalanceHandler` state (`prevEventsLen`) is correctly scoped/restored per call depth (e.g., save/restore on entry and exit of nested `RunNativeAction` invocations, or track events by absolute range with proper nesting/stack semantics) so overlapping event ranges are never double-processed across nested precompile calls.

### Proof of Concept
Not independently reproduced here — the repository's own `TestRecursivePrecompileCallsWithDebugPrecompile` test (using the `debug` precompile's recursive `callback()`/`Call0` methods calling itself via `CallEVMWithData`) is designed to exercise exactly this nested-call/shared-`BalanceHandler` scenario and should be used/adapted with a bank-balance-affecting precompile (e.g. `werc20.Deposit`) instead of the no-op debug precompile to confirm whether `StateDB` and bank-keeper balances diverge after execution. func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
