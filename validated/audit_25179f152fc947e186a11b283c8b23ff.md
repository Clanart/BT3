### Title
No validation or refund of excess native ETH in `EvmHost.dispatch()` — overpaid swap dust is permanently captured by the protocol instead of the depositor - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept arbitrary `msg.value` and forward the entire amount to `swapETHForExactTokens{value: msg.value}(post.fee, ...)` with no check that `msg.value` equals the amount actually required to acquire `post.fee` fee-tokens. [1](#0-0)  Any ETH the Uniswap router refunds for being unspent is returned to `msg.sender` of the router call — which is `EvmHost` itself, not the original depositor — and is absorbed via the host's dedicated `receive()` function, explicitly documented as collecting "dust" for the protocol. [2](#0-1)  This is the same broken invariant as the external report (`msg.value` accepted without validating it equals the intended payment amount), just relocated from a WETH NFT-sale flow into Hyperbridge's native-fee payment path.

### Finding Description
Callers across the protocol forward native ETH into `EvmHost.dispatch()` to pay dispatch fees, e.g. `IntentGatewayV2`/`ExtrinsicIntents._fillCrossChain` sends `options.nativeDispatchFee` as `msg.value`, [3](#0-2)  and `WrappedHyperFungibleToken.send()` forwards the leftover `msgValue` after a WETH wrap as the native dispatch payment. [4](#0-3) 

Inside `EvmHost.dispatch()`, the amount required to actually pay `post.fee` in fee-token terms is whatever the Uniswap V2 pool needs at execution time — this can be less than the ETH the caller supplied (price movement, over-estimated quote, buffer padding by a solver). The router's `swapETHForExactTokens` only consumes what's needed and refunds the rest to its caller (`EvmHost`), not to the end-user who originally supplied the ETH. [1](#0-0)  `EvmHost` has no bookkeeping that associates this refunded ETH with the original `_msgSender()`/`post.payer`; it is deposited into the host's own balance via the bare `receive()` fallback and treated as generic protocol dust. [2](#0-1) 

The only way this ETH can ever leave the contract again is through `withdraw(WithdrawParams)`, which is restricted to `_hostParams.hostManager` — a privileged, cross-chain-governance-only path — and pays out to whatever `beneficiary` governance chooses, not necessarily the original depositor. [5](#0-4)  There is no self-service reclaim mechanism for the individual user/solver who overpaid.

This mirrors the reported bug class exactly: a public entry point (`dispatch`, reachable indirectly by any unprivileged caller through `IntentGatewayV2`/`ExtrinsicIntents`/`WrappedHyperFungibleToken`) accepts native token payment without verifying `msg.value` matches the exact required amount, and the excess becomes permanently unrecoverable by the payer.

### Impact Explanation
Every unprivileged user or solver who calls a Hyperbridge fee-paying flow with native ETH (order fillers via `nativeDispatchFee`, `HyperFungibleToken`/`WrappedHyperFungibleToken` senders, any `IApp` integrator dispatching with native value) can lose the difference between the ETH supplied and the ETH actually consumed by the swap. Because fee estimates (`quote()`) are computed off-chain/pre-transaction against a Uniswap pool whose price can move by execution time, users are structurally incentivized to send a buffer above the quoted amount to avoid reverts — and that buffer is silently confiscated into host-controlled dust with no route back to the payer except discretionary governance action. This is fund loss for the payer, at protocol scale (every dispatch call using native payment is affected), not merely a rounding edge case.

### Likelihood Explanation
High. This does not require a malicious peer, relayer, or governance actor — a completely ordinary user or solver following the documented usage pattern (sending native ETH slightly above the quoted fee to be safe, or hitting normal price movement between quoting and execution) triggers the loss. No malformed proof or privileged role is needed; the path is reachable through the standard public `fillOrder`/`placeOrder`/`send` entry points that end up calling `EvmHost.dispatch()` with native value.

### Recommendation
Have `EvmHost.dispatch()` (both `DispatchPost` and `DispatchGet` overloads) compute the exact ETH input required for the swap (e.g., via `getAmountsIn`) and only pull/spend that amount, refunding any true excess back to `_msgSender()` (or `post.payer`) rather than letting it default to the host's own balance. Alternatively, require `msg.value == amountInRequired` (or a caller-supplied maximum with explicit refund-to-caller logic) so unspent native tokens never accrue to the host without a self-service reclaim path for the depositor.

### Proof of Concept
1. A solver calls `IntentGatewayV2._fillCrossChain` supplying `options.nativeDispatchFee = X` intending to cover `post.fee` fee-tokens, per `ExtrinsicIntents.sol` lines 157–162.
2. `IDispatcher(hostAddr).dispatch{value: X}(request)` is invoked, landing in `EvmHost.dispatch(DispatchPost)`.
3. `EvmHost` forwards the full `X` ETH to `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` — if the pool needs only `Y < X` ETH to produce `post.fee` tokens, the router refunds `X - Y` to `EvmHost` (the router's caller), not to the solver.
4. The refunded `X - Y` lands in `EvmHost` via `receive()` and becomes indistinguishable "dust," recoverable only by `withdraw()` under `hostManager` governance restriction — the solver has no way to reclaim it.
5. Repeating this for every dispatch call with even a modest ETH buffer accumulates unrecoverable value drained from ordinary users into host-held funds.

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
