### Title
Permissionless ERC20 registration allows malicious "Approval-hijack" tokens to drain the module's escrow account - (File: `x/erc20/keeper/msg_server.go`, `x/erc20/keeper/proposals.go`)

### Summary
`RegisterERC20` supports a `PermissionlessRegistration` mode in which **any account** can register an arbitrary ERC20 contract as a native token pair without any bytecode review, exactly the "attacker deploys the complementary contract" scenario described in the external NFTBridge report. [1](#0-0)  The conversion logic in `convertERC20IntoCoinsForNativeToken` / `ConvertCoinNativeERC20` claims to "check for unexpected `Approval` event in logs" in its doc comment, but the actual implementation never inspects the emitted logs for `Approval` events — it only checks the `transfer` return value/`Transfer` event and the module's own before/after balance. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The repo's own test fixture `ERC20MaliciousDelayed.sol` demonstrates the exact attack primitive: on every `transfer(recipient, amount)` call, the token secretly calls `_approve(recipient, _thief, hugeAmount)` before performing the real transfer, granting a hidden third party (`_thief`) an unlimited allowance over the *recipient's* balance of that token, while still emitting a normal `Transfer` event. [5](#0-4) 

Because `RegisterERC20` can be called permissionlessly (`params.PermissionlessRegistration`) by any user for any ERC20 address, an attacker deploys such a malicious contract and registers it as a token pair. [6](#0-5) [7](#0-6) 

When any honest user later calls `ConvertERC20` to escrow their tokens (bridging ERC20 → native coin), the keeper calls `transfer(ModuleAddress, amount)` on the malicious contract. [8](#0-7)  The malicious contract's overridden `transfer` sets `allowance[ModuleAddress][_thief] = hugeAmount` as a side effect, before performing the actual (correct-amount) transfer. [9](#0-8)  Since the balance-invariance check only validates that `balanceTokenAfter == balanceToken + tokens` (i.e. the transferred amount arrived correctly), and does not scan `res.Logs` for `Approval` events, the transaction passes all checks and the coins are minted normally. [10](#0-9) 

The `types.ModuleAddress` account, however, now holds an outstanding ERC20 allowance to the attacker's `_thief` address for the entire escrowed balance of that token pair. The attacker can subsequently call `transferFrom(ModuleAddress, thief, allowance)` directly on the EVM (bypassing the module keeper entirely, since this is a normal EVM call reachable by any unprivileged externally-owned account) and drain **all tokens escrowed by every user who ever converted through that pair**, not just their own deposit.

This matches the external report's core failure mode 1:1: a registered pair "cannot be modified," a malicious contract can be registered because there is no verification process, and once registered it causes permanent, irreversible loss of user funds with no way to pause the pair.

### Impact Explanation
This is a Critical, permanent theft of escrowed user funds: the module's escrow account balance (backing potentially many users' minted native coins) becomes drainable by an attacker-controlled address via a standard `transferFrom` call, with no admin recourse once the malicious pair is registered (no pause mechanism was found in the reviewed code). This breaks the 1:1 accounting invariant between native coin supply and escrowed ERC20 backing that `x/erc20` is meant to preserve.

### Likelihood Explanation
Likelihood is high wherever `PermissionlessRegistration` is enabled (params flag), since registration requires no privileged signer and the doc comment on `RegisterERC20` explicitly states "Any account can permissionlessly register a native ERC20 contract." [11](#0-10)  Even if governance-only registration is the deployed configuration, the missing `Approval`-log check is a real gap: it means the code's own documented security control ("check for unexpected `Approval` event in logs") is not implemented, so any imperfect due-diligence during a governance-gated registration would also miss this exact attack. I could not verify from the index whether `PermissionlessRegistration` defaults to `true` or `false` in production genesis; this should be confirmed by a developer with full repo access.

### Recommendation
1. Implement the "check for unexpected `Approval` event in logs" that the doc comments describe but the code does not perform — reject the conversion (or fail closed) if the ERC20 call emits any `Approval` event to a third party other than the expected minimal set of storage changes during `convertERC20IntoCoinsForNativeToken` / `ConvertCoinNativeERC20`.
2. Consider requiring registered ERC20 contracts to match a known-safe bytecode template (e.g., a verified minter/burner implementation) for `PermissionlessRegistration`, and/or restrict permissionless registration to non-arbitrary bytecode.
3. Add a governance-controlled mechanism to disable/pause conversions for a specific compromised token pair rather than only a global `IsERC20Enabled` toggle.

### Proof of Concept
1. Attacker deploys `ERC20MaliciousDelayed`-style contract with `_thief` set to an attacker-controlled address. [12](#0-11) 
2. Attacker calls `MsgRegisterERC20` (permissionless registration enabled) to register the malicious contract as a token pair. [13](#0-12) 
3. Victim calls `MsgConvertERC20` to bridge their tokens; keeper calls `transfer(ModuleAddress, amount)` on the malicious contract, which correctly moves `amount` tokens to `ModuleAddress` but also silently sets `allowance[ModuleAddress][_thief] = ~uint256_max`. [8](#0-7) 
4. Balance invariance check passes (correct amount arrived), coins are minted to victim. [14](#0-13) 
5. Attacker calls `transferFrom(ModuleAddress, thief, <escrowed balance>)` directly via EVM using the granted allowance, draining the module's entire escrow of that token, including any other victims' escrowed funds.

// ConvertCoinNativeERC20 handles the coin conversion for a native ERC20 token
// pair:
//   - escrow Coins on module account
//   - unescrow Tokens that have been previously escrowed with ConvertERC20 and send to receiver
//   - burn escrowed Coins
//   - check if token balance increased by amount
//   - check for unexpected `Approval` event in logs
func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
