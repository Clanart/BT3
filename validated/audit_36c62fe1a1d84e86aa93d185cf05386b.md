### Title
Stale line-index diff selection can be applied against a freshly re-fetched diff, silently mis-including/excluding lines in a commit - ([File: app/src/lib/git/apply.ts])

### Summary
`DiffSelection` (the "declared" set of what the user selected to commit) stores only numeric absolute line indices, with no binding to the specific diff content those indices were computed against [1](#0-0) . When staging a partial commit, `applyPatchToIndex` re-fetches a brand-new diff from disk immediately before building the patch from that same (potentially stale) selection object [2](#0-1) . Just like the report's `createDistribution()` trusting a total that isn't validated against the actual leaves, Desktop trusts that the selection's line indices still line up with the fresh diff's lines, without ever checking that assumption.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `withRangeSelection()` operate exclusively on integer "absolute" line numbers (`unifiedDiffStart + lineIndex`) recorded when the user interacted with a previously rendered diff [3](#0-2) . The class has no notion of what content a given index refers to — it is explicitly documented as having "no notion of how many lines exists or what it is that is being selected" [4](#0-3) .

`formatPatch()` then walks the *diff passed to it* and, for every line, asks the selection object whether the `absoluteIndex` computed from that diff's hunks is selected [5](#0-4) . Crucially, in `applyPatchToIndex`, this diff is obtained via a fresh call to `getWorkingDirectoryDiff(repository, file)` executed right before `formatPatch` is invoked [6](#0-5) , not the diff the user was actually looking at when they made their line selections in the UI.

If the working-tree file's diff shape changes between the moment the user's selection (`divergingLines`) was computed against an earlier diff and the moment `stageFiles`/`applyPatchToIndex` re-diffs the file at commit time — e.g., because of a background fetch/fast-forward (`performFetch` → `fastForwardBranches`), a smudge/clean filter, or any process that touches the file in the same repository — the numeric line indices no longer refer to the same logical lines. `formatPatch` has no mechanism to detect this mismatch: it only errors out if the patch ends up completely empty [7](#0-6) . A shift in hunk boundaries (e.g., one more/less context or changed line count) will cause the wrong lines to be silently marked "selected," producing a patch that commits content the user never reviewed or explicitly selected — exactly analogous to the report's core defect: an aggregate/declared value (`_amount`, here "the selection") is used without validating it is still consistent with the actual underlying data (the Merkle leaves / here, the current diff content).

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user could unknowingly commit lines they explicitly deselected (e.g., secrets, debug code, or unrelated changes) or omit lines they meant to include, without any error or warning, because `formatPatch` only guards against an empty patch, not a content/index mismatch.

### Likelihood Explanation
This requires the diff to visibly change shape (added/removed lines, hunk boundary shifts) between the "for review" diff and the "for commit" diff. I could not fully verify the app's logic for invalidating/re-mapping selection state on background refresh (in `app/src/lib/stores/updates/changes-state.ts`) within the remaining investigation budget — it's possible the app resets or remaps selections on every status refresh, which would mitigate this specific TOCTOU window. This uncertainty should be resolved by a deeper trace of `changes-state.ts` and how `WorkingDirectoryFileChange.selection` is preserved/merged across `_refreshRepository` calls that run concurrently with background fetches.

### Recommendation
Bind selection state to diff identity: store a hash or line-content fingerprint alongside `DiffSelection.divergingLines`, and re-validate (or discard/re-map) the selection against the diff fetched in `applyPatchToIndex` before generating the patch, rather than trusting bare integer indices across two independently-fetched diffs.

### Proof of Concept
Conceptual reproduction (not verified end-to-end due to inability to run code in this environment):
1. Open a file with a multi-hunk diff in Desktop and deselect specific lines (recorded as `divergingLines` indices against Diff A).
2. Trigger a background operation that alters file content/line count outside of the direct commit action (e.g., a fetch that fast-forwards and re-checks-out files, or an external process/git filter touching the file) before clicking "Commit."
3. `stageFiles` → `applyPatchToIndex` re-fetches Diff B via `getWorkingDirectoryDiff` and applies the stale index-based selection from Diff A to Diff B via `formatPatch`.
4. Inspect the resulting commit: lines differing from the user's actual intended selection may be included/excluded, with no error surfaced since `formatPatch` only throws on a fully empty patch.

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
