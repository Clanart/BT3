### Title
Race condition in Kaia gasless module's `PreAddTx` allows concurrent unsynchronized writes to shared `knownTxs` map, bypassing the bundle-tx admission limit - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.PreAddTx`, the tx-pool admission hook that gates gasless (KIP-247) approve/swap bundle transactions into the pool, acquires only a **read lock** (`knownTxsMu.RLock()`) while it both reads the queue-count check and then **mutates** the shared `knownTxs` map via `g.knownTxs.add(tx, TxStatusQueue)`. This mirrors the CVE-2024-26578 bug class: a check ("is this within the queue limit / not already known?") and an act (admit/insert) are not executed atomically under a single exclusive critical section, so concurrent submissions can race past the check.

### Finding Description
`PreAddTx` is defined as: [1](#0-0) 

It takes `g.knownTxsMu.RLock()` — a *shared* lock that multiple goroutines can hold concurrently — then reads `g.knownTxs.numQueue()` against `g.GetMaxBundleTxsInQueue()` and, if under the limit, calls `g.knownTxs.add(tx, ...)`, which is a plain Go-map write: [2](#0-1) 

`knownTxs` is a bare `map[common.Hash]*knownTx` with no internal locking of its own; all synchronization is expected to come from the caller-held `knownTxsMu`. Because `PreAddTx` only takes a *read* lock while performing this read-then-write sequence, any two callers invoking `PreAddTx` concurrently (e.g., for two different gasless approve/swap transactions submitted back-to-back to the endpoint node's public RPC, which is the normal path for `eth_sendRawTransaction`/`SendTransaction` from an unprivileged sender) can:
1. Both pass the `numQueue() >= GetMaxBundleTxsInQueue()` check simultaneously (TOCTOU), each seeing the same pre-insert count, and
2. Both concurrently execute the map write path in `knownTxs.add`, which is an unsynchronized concurrent write to the same Go map.

Concurrent, unsynchronized writes to a Go map are undefined behavior and in practice trigger the Go runtime's `fatal error: concurrent map writes`, which crashes the process — this is a public, remotely triggerable node crash from ordinary user-submitted transactions. Even short of a crash, the TOCTOU allows the effective `MaxBundleTxsInQueue` admission control (a resource/DoS-protection guard on the gasless queue, described in the module docs) to be bypassed by simply firing multiple approve/swap tx submissions in parallel — the same "repeated rapid submission defeats the intended uniqueness/limit check" pattern as the Apache Answer registration race.

By contrast, other mutators of the same map (`IsReady`, `PreReset`, `PostReset`) correctly take the **exclusive** `Lock()`: [3](#0-2) [4](#0-3) [5](#0-4) 

`PreAddTx` is the outlier that uses `RLock()` despite writing.

### Impact Explanation
- Denial of service: any endpoint/public-RPC node running the gasless module can be crashed by an unprivileged party submitting concurrent gasless approve/swap transactions, because Go maps panic fatally on concurrent writes.
- Admission-control/queue-limit bypass: even absent an outright crash, the TOCTOU on `numQueue()` vs `GetMaxBundleTxsInQueue()` lets an attacker admit more bundle transactions into `knownTxs`/the tx-pool queue than the configured `MaxBundleTxsInQueue`, i.e., a resource-limit bypass reachable purely from submitted transactions — analogous to the "duplicate registration bypassing the intended one-per-user constraint" in the original report, here manifesting as bypass of the one-per-limit admission gate for gasless bundle transactions.

### Likelihood Explanation
The precondition is that `PreAddTx` can actually be invoked concurrently by two goroutines without an outer exclusive lock already serializing them (e.g., without `TxPool`'s own pool-wide mutex being held across the whole tx-add path for every entrypoint that calls hook functions). I was not able to fully verify, within the available search budget, whether every call site in `blockchain/tx_pool.go` that invokes tx-pool module hooks like `PreAddTx` always holds `TxPool`'s own exclusive `mu` for the whole check-and-insert path; if it does not (e.g., pre-validation performed outside the pool lock, or concurrent `AddRemotes`/batched submission paths), the race is directly and remotely reachable from ordinary submitted transactions. This uncertainty should be resolved by inspecting `blockchain/tx_pool.go`'s call sites of `PreAddTx` (I found only 2 references there but could not view the surrounding lock context before running out of tool iterations).

### Recommendation
Change `PreAddTx` to use `g.knownTxsMu.Lock()` (exclusive) instead of `RLock()`, since it performs a write (`g.knownTxs.add`) after its read-based limit check, matching the locking discipline already used by `IsReady`, `PreReset`, and `PostReset`. Additionally, consider making `knownTxs.add`/`numQueue` internally safe (e.g., via a dedicated sync.Mutex embedded in the type) so that future callers cannot reintroduce this class of bug.

### Proof of Concept

var wg sync.WaitGroup
for i := 0; i < N; i++ {

        defer wg.Done()

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
