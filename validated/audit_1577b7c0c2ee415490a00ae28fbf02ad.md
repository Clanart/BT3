## Finding: Missing negative-length / overflow check in C# wrapper-type fast-path parsers

### Title
Integer-overflow-induced boundary violation in Wrapper-type length parsing — (File: `csharp/src/Google.Protobuf/ParsingPrimitivesWrappers.cs`)

### Summary
The Mongoose CVE-2025-51495 crash stems from an attacker-controlled length field being consumed in arithmetic without validating it can't overflow/underflow, so a downstream bound computed from that field becomes corrupted and the parser walks past its intended boundary, crashing the process. The protobuf C# runtime has a structurally identical pattern: `ParsingPrimitives.ParseLength` blindly casts a 32-bit varint to `int` with no sign/range validation [1](#0-0) , and this unchecked value is fed directly into an arithmetic sum that defines a parse-loop boundary inside the specialized Wrapper-type readers (`ReadUInt32WrapperSlow`, `ReadUInt64WrapperSlow`, `ReadFloatWrapperSlow`, `ReadDoubleWrapperSlow`) — unlike every other consumer of length in the same file, which explicitly checks `length < 0` and calls `ValidateCurrentLimit` before use.

### Finding Description
`ParseLength` reads a raw 32-bit varint and casts it straight to `int`: [1](#0-0) 
A crafted varint (e.g. all 5 bytes with the continuation bit pattern that decodes to a value ≥ 0x80000000) makes this cast produce a negative `int`.

Every "generic" byte-consuming primitive in this file defends against that: `ReadRawBytes`, `SkipRawBytes`, and `ReadRawString` all explicitly check `size/length < 0` and throw `InvalidProtocolBufferException.NegativeSize()`, and the slow paths additionally call `ValidateCurrentLimit` to bound the read against the current message limit: [2](#0-1) [3](#0-2) [4](#0-3) 

The Wrapper-type fast-path readers in `ParsingPrimitivesWrappers.cs`, however, take the raw `length` from `ParseLength` and only check `length == 0`; there is no `length < 0` check and no `ValidateCurrentLimit` call anywhere in these methods: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

In each of these, `finalBufferPos = state.totalBytesRetired + state.bufferPos + length` is computed with unchecked (default) C# integer arithmetic. If `length` is negative (from the sign-overflowed cast) or otherwise crafted, this sum can wrap, producing a `finalBufferPos` that is either far in the past (loop body never executes, silently returning `0`/default without consuming the intended bytes — a mis-parse) or, via further wraparound, a large positive value that keeps the `do { ... } while (... < finalBufferPos)` loop iterating well past the sub-message's real boundary. Because `ParseTag`/`SkipLastField` are only bounded by the physical buffer/stream, not by this corrupted logical limit, the loop keeps consuming subsequent tag/value pairs that belong to sibling/outer fields. Eventually it either hits the real end of input (`ParseTag` returns tag `0`) and calls `SkipLastField`, which explicitly throws `InvalidOperationException("SkipLastField cannot be called at the end of a stream")`: [9](#0-8) 
or it desynchronizes the outer parser's position tracking so that the caller's own limit/position checks (`PopLimit`) subsequently fail with an unexpected exception.

### Impact Explanation
This is a bounded, attacker-supplied-length integer-overflow that corrupts an internally computed parse boundary and lets the parser walk outside the intended sub-message region within an otherwise small, valid-looking Protobuf payload — matching the Mongoose invariant of "attacker-controlled length used unchecked in arithmetic → corrupted bound → parser walks off the intended region → crash." The concrete, reachable outcome here is an unhandled `InvalidOperationException`/`InvalidProtocolBufferException` (denial of service via crash on the parsing thread), not memory corruption, since all raw-byte access in the fallback path stays within `ReadOnlySpan<byte>` bounds. This aligns with a High-severity, availability-only classification (comparable to the reported CVSS `C:N/I:N/A:H`), and is reachable through a normal, public `MessageParser.ParseFrom`/`IMessage.MergeFrom` call on any message that contains a well-known wrapper field (`google.protobuf.{U}Int32Value`, `{U}Int64Value`, `FloatValue`, `DoubleValue`, `BoolValue`).

### Likelihood Explanation
Likelihood is Medium-High: the payload does not require a huge or memory-exhausting input — a handful of bytes forming a malformed varint length inside a wrapper-typed field is sufficient. No special privileges, custom schema, or unusual API are needed; only a schema (trusted, but very commonly used — wrapper types are ubiquitous in real `.proto` files) containing a wrapper-typed field is required, and the attacker only needs to control the serialized bytes passed to the public `ParseFrom` API.

### Recommendation
Add an explicit `length < 0` (or, better, validate against `state.currentLimit`/`ValidateCurrentLimit`) check immediately after each `ParsingPrimitives.ParseLength` call in `ReadUInt32WrapperSlow`, `ReadUInt64WrapperSlow`, `ReadFloatWrapperSlow`, and `ReadDoubleWrapperSlow` in `csharp/src/Google.Protobuf/ParsingPrimitivesWrappers.cs`, mirroring the guard already present in `ReadRawBytes`/`SkipRawBytes`/`ReadRawString`, and use checked/overflow-safe arithmetic (or a `long` intermediate) when computing `finalBufferPos`.

### Proof of Concept
I was not able to execute this in a sandbox (ask-only mode, no terminal access), so this is a source-level reproduction sketch rather than a verified run:
1. Define a message with a field of type `google.protobuf.UInt32Value` (e.g. field 1).
2. Encode the outer field tag/length normally (length-delimited), but inside the embedded bytes, instead of a valid one-byte length, place a 5-byte varint whose decoded 32-bit value has the high bit set (e.g. bytes `FF FF FF FF 0F`, decoding to `0xFFFFFFFF`).
3. Feed this into `SomeMessage.Parser.ParseFrom(bytes)`.
4. Because `ParseLength` casts `0xFFFFFFFF` to `int` → `-1`, and `ReadUInt32WrapperSlow` performs no `length < 0` check, `finalBufferPos` is computed from a negative `length`, corrupting the do-while loop's termination condition and leading to either a silent mis-parse or an unhandled `InvalidOperationException`/`InvalidProtocolBufferException` once the parser runs past the actual end of the buffered data.

Confirming the exact exception path and exploitability at runtime would require compiling and running this against the actual C# runtime, which I could not do in this environment — this should be validated with an actual unit test/fuzz input before treating it as fully confirmed.

        internal static float? ReadFloatWrapperSlow(ref ReadOnlySpan<byte> buffer, ref ParserInternalState state)
        {
            int length = ParsingPrimitives.ParseLength(ref buffer, ref state);
            if (length == 0)
            {
                return 0F;
            }
            int finalBufferPos = state.totalBytesRetired + state.bufferPos + length;
            float result = 0F;
            do
            {
                // field=1, type=32-bit = tag of 13
                if (ParsingPrimitives.ParseTag(ref buffer, ref state) == 13)
                {
                    result = ParsingPrimitives.ParseFloat(ref buffer, ref state);
                }
                else
                {
                    ParsingPrimitivesMessages.SkipLastField(ref buffer, ref state);
                }
            }
            while (state.totalBytesRetired + state.bufferPos < finalBufferPos);
            return result;
        }
