### Title
`SignableTransaction::new` omits the OP_RETURN data output from fee/vbytes calculation, underpaying fees below the intended rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
When `SignableTransaction::new` is called with `data`, it appends an OP_RETURN output carrying up to 80 bytes to `tx_outs` (send.rs:194-202), but then computes the transaction weight and virtual size via `calculate_weight_vbytes(tx_ins.len(), payments, None)` using only the `payments` list — the data output is never included (send.rs:204). Consequently `needed_fee = fee_per_vbyte * vbytes` is computed for a transaction that is ~90-100 weight units smaller than the one actually built. The same omission occurs in the change path, where `fee_with_change` is derived from a transaction containing payments + change but still no data output (send.rs:225-232).

### Finding Description
The external incident (OSN) is a class of "self-referential" bugs: a contract computes rewards/values while ignoring an effect the contract itself creates (paying out its own token as reward). The Serai analog is a transaction builder that prices its own outputs incorrectly: the very output this function adds (`tx_outs.push(TxOut { value: ZERO, OP_RETURN data })`) is excluded from the size model used to price the transaction.

Concretely:

- `data` output appended at send.rs:194-202.
- `calculate_weight_vbytes` at send.rs:62-127 builds a synthetic `Transaction` containing only `payments` (+ optional change) to measure weight; it has no parameter for the data output.
- `needed_fee` and the minimum-relay-fee check at send.rs:206-213 use the underestimated `vbytes`.
- The change amount at send.rs:228 is `input_sat - (payment_sat + fee_with_change)` where `fee_with_change` is too small, so the change output is slightly *overpaid* relative to the requested fee rate, and the real fee rate `fee() / actual_vsize` is strictly below `fee_per_vbyte`. `fee()` at send.rs:138-141 computes the real fee as inputs minus outputs, confirming the divergence.

### Impact Explanation
Any caller using the `data` parameter gets a transaction whose real fee rate is lower than requested — up to ~90+ bytes of weight unpriced. Two concrete harms:

1. The minimum-relay check (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, send.rs:211) validates the underestimated `vbytes`. The actual transaction can therefore fall below the minimum relay fee, causing the signed transaction to be rejected by nodes — outputs intended as payments become unspendable in practice until a new transaction is constructed. This maps to "funds reported sent/received that are not spendable."
2. Even when relayable, the change output is inflated by the underpriced fee, and the transaction confirms more slowly than the caller's fee policy intended — an incorrect verifier/pricing formula reachable purely from public inputs (`data` bytes supplied to `SignableTransaction::new`).

### Likelihood Explanation
Deterministic: any `SignableTransaction::new` call with `data: Some(...)` produces a systematically underpriced transaction. No adversarial setup is needed beyond supplying data (as processor-level `Shorthand`/OP_RETURN flows do). Severity Medium: it produces stuck/rejected transactions and mispriced change rather than direct theft, but it is reachable with untrusted bytes and breaks the documented fee guarantee.

### Recommendation
Include the OP_RETURN data output in the weight/vbytes model: pass `data` (or a pre-built `TxOut` list) into `calculate_weight_vbytes` so the synthetic transaction matches the real one, in both the no-change call at send.rs:204 and the with-change call at send.rs:225-226. Re-run the minimum-relay-fee check against the corrected `vbytes`.

### Proof of Concept
```rust
// SignableTransaction::new(inputs, &payments, change, Some(vec![0; 80]), FEE)
let tx = SignableTransaction::new(
    inputs.clone(), &payments, None, Some(vec![0u8; 80]), fee_per_vbyte,
).unwrap();

// actual vsize exceeds the vbytes used for needed_fee
let actual_vsize = u64::try_from(tx.transaction().vsize()).unwrap();
assert!(tx.needed_fee() < fee_per_vbyte * actual_vsize);
// effective fee rate < requested; may be < min relay for the true size
assert!(tx.fee() * 1000 < u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * actual_vsize);
```

Caveat noted: the finding rests on `calculate_weight_vbytes` modeling only `payments`/`change` (send.rs:85-99) while `tx_outs` additionally contains the data output; I did not fully enumerate every downstream caller, but the miscalculation is present regardless of caller.
