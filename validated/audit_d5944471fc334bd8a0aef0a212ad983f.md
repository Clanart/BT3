Based on the investigation, I found a structural analog to the Fuel Network WDCM/WQCM bug (comparison flags not cleared between operations, causing stale state to influence a later decision).

### Title
Manual conflict resolutions (`manualResolutions`) are not reset when a merge/rebase is aborted and a new conflicting operation starts before the next status refresh - stale "ours/theirs" choices can be silently reapplied to unrelated, attacker-influenced content - (File: app/src/lib/stores/updates/changes-state.ts)

### Summary
`updateConflictState` in `app/src/lib/stores/updates/changes-state.ts` carries forward the `manualResolutions` `Map<string, ManualConflictResolution>` by reference whenever the previous and new conflict states are of the same *kind* (`merge`↔`merge` or `rebase`↔`rebase`), keyed only by file `path` — never by commit SHA, branch tip, or file content hash. [1](#0-0) 

### Finding Description
`getConflictState` builds the new conflict object using whatever `manualResolutions` map is passed in, and `updateConflictState` decides to reuse the *previous* map instead of a fresh one purely based on `prevConflictState`/`newConflictState` both being `null` or of the same conflict kind: [2](#0-1) [1](#0-0) 

The map is keyed solely by `path` string, as seen in `_updateManualConflictResolution`: [3](#0-2) 

There is no check that the underlying merge/rebase is actually the *same* operation (e.g. by comparing `currentTip`/`targetBranch`/base-branch tip against the previous entry) before deciding to keep the map. `abortMerge` in `app/src/lib/git/merge.ts` only runs `git merge --abort`; it does not itself clear `manualResolutions` — that only happens indirectly, later, when a subsequent status poll observes `mergeHeadFound: false` and `getConflictState` returns `null`. [4](#0-3) 

This is directly analogous to the WDCM/WQCM bug: a piece of state ($of/$err flags in the Fuel VM, `manualResolutions` in Desktop) that should be cleared at the boundary of a logically distinct operation is instead preserved because the code path that resets it depends on an intervening event (a fresh instruction that overwrites $of/$err, or a fresh status poll that nulls `conflictState`) rather than being reset atomically when the previous operation ends.

### Impact Explanation
If a user resolves a conflicted file (e.g. `config.json`) as "Theirs" during a merge with a malicious/compromised branch, then aborts, and — before Desktop's next status poll completes — starts a second conflicting operation (merge/rebase/cherry-pick) against a different, attacker-influenced ref that also conflicts on the same path, the stale "Theirs" resolution could be carried into the new operation's `conflictState.manualResolutions`. Combined with the "stage" resolution path (`git checkout --theirs`) used at commit time, this could cause Desktop to silently take content from the *new* attacker-controlled `theirs` side for a file the user never explicitly reviewed in that second operation — i.e., silent corruption of what the user commits, without an explicit re-confirmation, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires a narrow timing window between `git merge --abort` and Desktop's subsequent repository status refresh, plus the user manually starting a second git operation in that window and having a same-path conflict recur. Desktop typically re-runs `_loadStatus` promptly around abort/complete flows, so the window is likely small in normal UI-driven flows, and I was not able to fully trace every call site that clears `multiCommitOperationState`/`changesState.conflictState` on every abort path (e.g. `_abortMerge` in `app-store.ts`) within the available context, so I cannot confirm whether a synchronous state clear already fully mitigates this before any second operation could be started through the UI. This uncertainty means the exploitability is unconfirmed and likely low without further verification of the abort call chain.

### Recommendation
- Bind `manualResolutions` entries to an identifier for the specific operation (e.g. include `currentTip`/`targetBranch`/merge-base in the cache key, or generate a per-operation nonce) rather than reusing the map purely based on conflict `kind` matching.
- Ensure every abort/cancel code path (`_abortMerge`, rebase/cherry-pick abort, multi-commit-operation abort) synchronously clears `changesState.conflictState` (and thus `manualResolutions`) before allowing a new operation to start, instead of relying on the next asynchronous status poll.

### Proof of Concept
Not independently reproducible from available context — this is a code-level structural finding based on `updateConflictState`'s reuse logic and the keying scheme of `manualResolutions`. A concrete PoC would require tracing all UI-triggered abort call sites to confirm whether a race window actually exists in practice, which was not fully verifiable with the tools available in this session.

/**
 * Convert the received status information into a conflict state
 */
function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

    this.updateMultiCommitOperationStateAfterManualResolution(repository)

    this.emitUpdate()
  }
