### Title
Inconsistent `safeApprove()` usage without zero-reset in `WombatStaking._sendRewards()` can permanently brick reward harvesting - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking._sendRewards()` — the internal function that is invoked on every deposit/withdraw/harvest that flows through `_toMasterWomAndSendReward()` — mixes two different `safeApprove()` patterns for the same purpose within a single function, exactly mirroring the root cause identified in the external report (calling `safeApprove()` with a new non-zero value without first resetting the existing allowance to zero).

### Finding Description
In `_sendRewards()`, when a fee tier is configured with `isMWOM = true` and the reward token is `wom`, the code approves `smartWomConverter` or `mWom` directly with the new fee amount, with **no preceding zero-reset**: [1](#0-0) 

Contrast this with the two other approval sites in the very same function, which correctly reset the allowance to zero before setting a new non-zero value: [2](#0-1) 

This is the identical inconsistency pattern described in the report for `PirexGmx.configureGmxState()` vs `setContract()` — one code path resets allowance to 0 before re-approving, a sibling code path in the same contract does not. `SafeERC20.safeApprove()` (OpenZeppelin) reverts when attempting to set a non-zero allowance on top of an already non-zero allowance. If the downstream consumer (`smartWomConverter.smartConvert()` or `mWom.deposit()`) ever leaves any residual allowance from a prior `_sendRewards()` invocation — e.g. because a future/alternate `mWom`/`smartWomConverter` implementation is swapped in via the admin-settable `smartWomConverter` address, an integrated router swap doesn't consume the full approved amount, or a partial/`try/catch`-style external call leaves state uncommitted — the very next `safeApprove(mWom, feeAmount)` or `safeApprove(smartWomConverter, feeAmount)` call reverts.

### Impact Explanation
`_sendRewards()` is reached from `_toMasterWomAndSendReward()`, which is triggered by ordinary, unprivileged user actions (deposit/withdraw/harvest routed through the pool helpers such as `WombatPoolHelperV2`/`AnkrBNBPoolHelper`) rather than by any admin call. Because this is on the LP custody / reward-distribution hot path in `WombatStaking`, a revert here does not just fail one user's transaction — it can permanently DoS the harvesting and reward-queueing path for the affected pool (and hence for all depositors relying on that pool's LP custody/receipt-token and reward flow), since there is no separate way to reset the stuck allowance from inside `WombatStaking` (no `setContract`-style zero-reset admin function targets these two approvals). This can result in the freezing of unclaimed WOM/mWOM yield for all users of the pool for an indefinite period (well over 24 hours) until a contract upgrade is shipped.

### Likelihood Explanation
The likelihood of the residual-allowance precondition being hit depends on the exact behavior of `mWom.deposit()` / `smartWomConverter.smartConvert()`, which currently do call `safeTransferFrom` for the exact approved amount in the code as written, so under the current specific implementations the allowance is normally drained to zero on each call. However, `smartWomConverter` is an admin-configurable external address, and the code itself does not defensively reset allowance to zero as done in the neighboring lines of the same function — this is a code-quality/robustness bug identical in nature and location-pattern to the reported one: any future change to the target contract's consumption behavior (or any edge case where the external call reverts after partial internal state changes, or reenters and issues an approval independently) turns this into a hard DoS with no user-facing recovery path.

### Recommendation
Mirror the pattern already used later in the same function: reset the allowance to zero before setting a new non-zero allowance for both the `smartWomConverter` and `mWom` approval sites:
```solidity
IERC20(wom).safeApprove(smartWomConverter, 0);
IERC20(wom).safeApprove(smartWomConverter, feeAmount);
...
IERC20(wom).safeApprove(mWom, 0);
IERC20(wom).safeApprove(mWom, feeAmount);
```
Alternatively, replace all `safeApprove` calls with `forceApprove` (OpenZeppelin's newer utility) which handles this internally, for consistency across the whole contract.

### Proof of Concept
1. Assume (now or after any future upgrade of `smartWomConverter`/`mWom`, both of which are owner-settable addresses in `WombatStaking`) that a `_sendRewards()` call leaves a non-zero residual `wom` allowance for `mWom` (or `smartWomConverter`) — e.g., due to an external call that doesn't fully drain the approved amount.
2. Any ordinary user calls `deposit`/`withdraw`/`harvest` through a pool helper (e.g. `WombatPoolHelperV2.harvest()`), which routes into `WombatStaking._toMasterWomAndSendReward()` → `_sendRewards()`. [3](#0-2) 
3. `_sendRewards()` executes `IERC20(wom).safeApprove(mWom, feeAmount)` on line 747 while a non-zero allowance already exists — `safeApprove` reverts.
4. Because this line is not preceded by a zero-reset (unlike the pattern at lines 756/767), every subsequent call into this harvest/reward flow for that pool reverts permanently, freezing LP custody's reward distribution and unclaimed yield for all users of that pool.
