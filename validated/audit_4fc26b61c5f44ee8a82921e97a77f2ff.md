## Title
Stale fee-token confusion in `IntentGatewayV2` escrow/withdraw path lets a host fee-token change strand or misallocate escrowed order fees - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`placeOrder()` escrows an order's `fees` amount denominated in whatever `IDispatcher(host).feeToken()` returns *at order-placement time*, storing only the raw amount under `_orders[commitment][TRANSACTION_FEES]` with no record of which ERC-20 token was actually collected. When the order is later settled, `_withdraw()` in `IntentsBase.sol` re-reads `IDispatcher(host()).feeToken()` *at withdrawal time* and pays the beneficiary that many units of whatever token is *currently* configured as the fee token — not the token that was actually escrowed. This mirrors the H-05 pattern: the contract remembers only an amount, not the source/token it was collected from, and pays out of the wrong pool when the underlying source is switched between deposit and withdrawal.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol::placeOrder()`:
```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    ...
    IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    _orders[commitment][TRANSACTION_FEES] = order.fees;   // amount only, no token address recorded
}
``` [1](#0-0) 

Later, in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw()` (shared by fill, cancel, and refund paths):
```solidity
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
    ...
}
``` [2](#0-1) 

`host().feeToken()` is a governance-mutable parameter on `EvmHost` (`updateHostParams`), and the codebase explicitly documents that the fee token can be swapped ("the host occasionally swaps fee tokens"), as seen in the analogous `BandwidthManager.sol` design where `Withdrawal.token` is deliberately named explicitly so stale-token balances remain recoverable. The `IntentGatewayV2` fee-escrow path does not do this — it has no token field at all in the escrow record, only a raw `uint256` amount keyed by `TRANSACTION_FEES`.

The only guard against fee-token churn lives in `EvmHost.updateHostParams()`:
```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
``` [3](#0-2) 
This check only inspects `EvmHost`'s own balance of the old fee token, not any downstream app contract such as `IntentGatewayV2`, which is a separate contract holding its own escrowed balances. It provides zero protection for `IntentGatewayV2`'s stored `TRANSACTION_FEES` amounts.

**Corrupted value**: `_orders[commitment][TRANSACTION_FEES]` — a bare `uint256` amount that is silently reinterpreted against a different ERC‑20 token address once `host().feeToken()` changes between order placement and order settlement (fill/cancel/refund).

### Impact Explanation
If governance rotates the fee token (a normal, documented operational action on this protocol, as evidenced in `BandwidthManager`'s explicit token-field design for exactly this scenario) while `IntentGatewayV2` orders are in flight with unpaid `order.fees`:
- Orders placed under the old fee token have their `fees` amount recorded in old-token units.
- At settlement (`fillOrder`/`cancelOrder`), `_withdraw()` pays out that same numeric amount in the *new* fee token.
- Since the gateway generally does not hold a matching balance of the new fee token sourced from those specific orders, this either (a) reverts (temporary fund lock: the escrowed old fee tokens become permanently stuck, unclaimed, in the contract, since there is no path to redeem `TRANSACTION_FEES` in the original token), or (b) succeeds by draining the gateway's new-fee-token balance — which is actually other users' escrowed principal/fees from unrelated orders — to pay this order's beneficiary an amount unrelated to what was ever collected for it.

Either outcome is a fund-loss/fund-lock condition affecting real user/solver funds held in `IntentGatewayV2`, directly matching the accepted impact categories (loss of funds / wrong beneficiary or amount / logic attack on custody accounting).

### Likelihood Explanation
This does not require a malicious actor — only a normal, permissioned, expected governance action (fee-token migration) combined with in-flight orders, which the protocol's own documentation acknowledges as a supported operational scenario elsewhere (`BandwidthManager`'s `Withdrawal.token` design exists specifically to handle post-swap stale balances). Any order with `order.fees > 0` that remains open across a fee-token change on its host chain is affected. Given that intent orders can have deadlines far in the future and cross-chain fills/cancellations can take arbitrary time to settle, the window for a fee-token change to land mid-flight is realistic in normal operations, not an edge case requiring adversarial coordination.

### Recommendation
Store the fee token address alongside the escrowed fee amount at `placeOrder()` time (e.g. a `_orders[commitment][FEE_TOKEN_SLOT]`-style mapping, or pack `(token, amount)` into the escrow record), and have `_withdraw()` read back that stored token address instead of re-querying `host().feeToken()`. This mirrors the fix pattern already used correctly elsewhere in this codebase (`BandwidthManager.Withdrawal.token`), where the token is explicitly carried through rather than re-derived from a mutable global at a later time.

### Proof of Concept
1. User places `Order` with `order.fees = 100` while `IDispatcher(host).feeToken() == TokenA`. `placeOrder()` pulls 100 `TokenA` from the user and sets `_orders[commitment][TRANSACTION_FEES] = 100` (no token recorded).
2. Before this order is filled or cancelled, governance calls `EvmHost.updateHostParams()` to rotate `feeToken` to `TokenB` (allowed as long as `EvmHost`'s own `TokenA` balance is zero — `IntentGatewayV2`'s escrowed `TokenA` is untouched by that check).
3. A solver fills the order (or the user cancels it). `_withdraw()` executes `IERC20(host().feeToken()).safeTransfer(beneficiary, 100)` — this now transfers 100 units of `TokenB`, not the `TokenA` that was actually escrowed.
4. If the gateway holds `TokenB` balance from other orders' escrows, this beneficiary is paid out of unrelated users' funds; if it does not, the transfer reverts and the original 100 `TokenA` remains permanently stuck in the gateway with no code path to recover it (the `TRANSACTION_FEES` slot is deleted on any successful attempt, but a reverting attempt leaves the order un-settleable).

This confirms the wrong-source-of-funds pattern from the seed report reproduced locally: an amount escrowed against one token is redeemed against a different, unrelated token because the withdrawal path re-resolves a mutable global instead of using the value bound at escrow time.
