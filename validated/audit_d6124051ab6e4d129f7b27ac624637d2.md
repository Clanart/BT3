### Title
Attacker-controlled length prefix in `ThresholdKeys::read` enables unbounded-memory-allocation DoS — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts a 2-byte `n` field from an untrusted reader and calls `Vec::with_capacity(usize::from(n))` before confirming any of the corresponding bytes exist. A 6-byte crafted header can therefore force ~2 MB of heap allocation per call, and repeated calls (or callers holding/pooling the resulting allocation attempts) enable remote memory exhaustion — the analog of CVE-2020-22041's input-triggered memory-growth DoS. [1](#0-0) 

### Finding Description
`ThresholdKeys::read` first validates the ciphersuite ID, then reads `t`, `n`, and `i` — each a 16-bit value under attacker control when the bytes come from an untrusted party (the function's contract is reading serialized key material, and `Participant::new`/`ThresholdParams::new` only validate consistency, not size). For `Interpolation::Constant` it executes `Vec::with_capacity(usize::from(n))` with `n` up to 65535, immediately reserving `65535 × sizeof(F)` (~2 MB for 32-byte scalars) on the heap before a single scalar byte has been verified present. It then reads `n` scalars and `n` verification shares (`read_F`/`read_G` in a `1 ..= n` loop into a `HashMap`), so each element read allocates and inserts a full-size group element even though the claimed `n` need not correspond to actual supplied bytes — the reads fail only one element at a time, after memory is already committed. [2](#0-1) 

Note: `Vec::with_capacity(n)` reserves the full capacity upfront even if `read_exact` fails on the very first scalar — the allocation succeeds regardless of how few bytes the attacker actually supplies. This mirrors the FFmpeg `av_buffersrc_add_frame_flags` pattern where an attacker-triggered path grows memory without bound relative to input actually delivered. Other readers in the codebase explicitly guard against this class (e.g., the Ethereum `Call::read` reads length-prefixed data in 1 KB chunks precisely because "a valid DoS would be to claim a 4 GB data is present for only 4 bytes"), but `ThresholdKeys::read` and related readers (`Commitments::read` in pedpop, driven by `params.t()`; `Transaction::read` variants in the coordinator) do not chunk or cap this allocation. [3](#0-2) [4](#0-3) 

### Impact Explanation
An unprivileged party who can cause a node to deserialize attacker-supplied `ThresholdKeys` bytes (e.g., through any protocol message, RPC payload, or stored blob routed to `ThresholdKeys::read`) can force multi-megabyte allocations per call with a handful of bytes on the wire. Issued repeatedly or against many concurrent sessions, this exhausts process memory and crashes the validator/processor — availability loss matching the CVE's Medium severity (CVSS 6.5, availability-impact only). Because `verify`/`ThresholdParams::new` reject `n == 0` but accept any nonzero `n` consistent with `t`/`i`, no signature or key knowledge is needed to trigger it.

### Likelihood Explanation
Reachability depends on the integrator feeding untrusted bytes to `ThresholdKeys::read`; the rules scope explicitly lists `ThresholdKeys::read` as an untrusted-bytes sink. Where key material is only loaded from trusted local disk, impact is reduced; where any peer-supplied or restore-from-backup path reaches it, exploitation requires only a 6-byte prefix (`id_len`, `id`, `t=1`, `n=65535`, `i=1`) — trivially craftable. Per-call yield is bounded (~2 MB allocation + up to `n` point-decode attempts before EOF failure), so practical exhaustion requires repeated invocations, which is realistic in retry/polling loops but not a single-shot OOM.

### Recommendation
Do not pre-size allocations from untrusted length fields. In `crypto/dkg/src/lib.rs`, replace `Vec::with_capacity(usize::from(n))` with incremental `push`/`insert` only after each element's `read_F`/`read_G` succeeds, so memory committed is proportional to bytes actually supplied. Additionally consider enforcing a sane upper bound on `n` (e.g., reject `n` exceeding a protocol maximum before allocating) and applying the same chunked-read discipline used in `networks/ethereum/src/machine.rs` to all length-prefixed collections read from untrusted readers.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;

// C = any in-scope ciphersuite, e.g. Ed25519 via dalek-ff-group
fn poc() {
    let mut bytes = Vec::new();
    // C::ID length + ID
    bytes.extend(&u32::try_from(C::ID.len()).unwrap().to_le_bytes());
    bytes.extend(C::ID);
    // t = 1, n = 65535, i = 1
    bytes.extend(&1u16.to_le_bytes());
    bytes.extend(&u16::MAX.to_le_bytes());
    bytes.extend(&1u16.to_le_bytes());
    // interpolation = 0 (Constant) -> Vec::with_capacity(65535) immediately
    bytes.push(0u8);
    // no further bytes needed: with_capacity already reserved ~2 MB
    // (read_F will then fail on EOF, but the allocation occurred)
    let _ = ThresholdKeys::<C>::read(&mut Cursor::new(bytes));
}
```

Each invocation commits ~2 MB of heap (plus per-iteration `HashMap` growth) against ~10 bytes of input; a loop over this input exhausts memory proportional to invocation count.
