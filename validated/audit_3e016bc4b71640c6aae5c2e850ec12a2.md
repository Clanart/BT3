### Title
Malicious repo hooks/filters can exfiltrate the signed-in GitHub OAuth token via the trampoline credential helper's over-broad, unrevoked trust - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`, `app/src/lib/trampoline/trampoline-environment.ts`, `app/src/lib/trampoline/find-account.ts`)

### Summary
The Notional bug is about a residual, over-broad `approve()` allowance that lets *any* call from the trusted counterparty pull more than what was needed for the specific operation. The same "broad permission granted for one purpose, usable for anything within its validity window" pattern exists in GitHub Desktop's Git credential trampoline: for the whole duration of a git operation, Desktop grants `credential.helper=desktop` (backed by the real signed-in account's OAuth token) to **every child process Git spawns**, including filters and hooks defined by the repository content itself, not just the one HTTPS request to the actual remote. The trampoline only checks that the token is a *valid, currently-open* trampoline session — it never checks that the credential request being answered corresponds to the remote/host the user actually intended to talk to.

### Finding Description
`withTrampolineEnv` injects `GIT_CONFIG_PARAMETERS: "... 'credential.helper=' 'credential.helper=desktop'"` and `DESKTOP_TRAMPOLINE_TOKEN` into the environment for the whole git invocation: [1](#0-0) 

The code comment explicitly documents that this is done via environment variables *specifically so that child processes spawned by Git — such as Git LFS filters — inherit the credential helper configuration*: [2](#0-1) 

The trampoline token itself is only checked for validity/liveness, not for which host or repository it is scoped to: [3](#0-2) 

When any process (Git itself, a smudge/clean filter, or a hook spawned during clone/fetch/checkout) runs `git credential fill` with `protocol=https` / `host=github.com`, the trampoline's handler resolves it to the real account: [4](#0-3) 

`findGitHubTrampolineAccount` matches purely by **origin** of the requested host, with no verification that this matches the remote actually being operated on, nor any restriction that only Git's own credential subsystem (and not an arbitrary child process) may ask: [5](#0-4) 

So the "allowance" here — the ability to obtain the plaintext OAuth token for `github.com`/GHE via the trampoline — is granted for the entire lifetime of the git operation to anything that can read the inherited environment and speak the Git credential-helper protocol over the trampoline's TCP socket, not scoped to the single legitimate request Git itself would make to authenticate against the actual remote. This mirrors the Notional finding's root cause: a broad, session-lived permission that outlives/outscopes the specific action it was meant to authorize, and can be abused by an untrusted third party (here, attacker-controlled repository content) that gets to run code inside that trust window.

### Impact Explanation
An attacker who controls the content of a repository the user clones/fetches (e.g. via `.gitattributes` filters, `.git/hooks`-installable hooks if `core.hooksPath` or install scripts run, or Git LFS custom filters) can, during any git operation Desktop performs against that repo, spawn a process that queries `git credential fill host=github.com` and receive back the victim's real GitHub OAuth token in plaintext. That token can be used to impersonate the user against the GitHub API (read private repos, push code, modify settings, etc.), which is credential/token exfiltration originating from an attacker-controlled repository — squarely in the "Valid Impact" category (attacker controls a cloned/fetched repo; result is credential/token exfiltration).

### Likelihood Explanation
Requires the victim to clone or fetch/checkout an attacker-controlled repository in GitHub Desktop while already signed in to a GitHub account in the app — a common, unprivileged scenario (no local/physical access, no prior malware, no social engineering beyond "clone this repo," which is the normal, expected Desktop workflow). The attack surface (LFS filters, `.gitattributes`-driven smudge/clean filters, checkout hooks) is exactly what the trampoline-environment.ts comment says is *intentionally* given the credential helper config, so the exposure is a direct, documented consequence of the current design rather than a hypothetical edge case.

### Recommendation
Scope trampoline credential responses to the specific operation/remote they were issued for instead of trusting any process holding the token for the operation's full duration:
- Bind the trampoline token (and the credential answer) to the specific remote URL/host that Desktop's own git invocation is operating against, and reject `get` requests for hosts that don't match the operation's intended remote.
- Avoid exposing the GitHub-account-backed `credential.helper=desktop` to filter/hook subprocesses; only Git's own credential subsystem talking to the actual remote host should be able to redeem it. If filters/hooks must run with network access, do so without the ambient OAuth-token-granting credential helper, or require an explicit, per-remote allowlist.
- Apply the same "expire immediately after single, verified use" principle recommended in the Notional finding: shrink the trust window and the entity set able to redeem it to the minimum necessary for the specific git subcommand talking to the specific remote.

### Proof of Concept
1. Sign in to a GitHub account in GitHub Desktop.
2. Create/host a malicious repository containing a `.gitattributes` entry that routes a tracked file through a custom filter (or an LFS custom transfer/filter, or a hook triggered on checkout) which on invocation runs:
   `printf 'protocol=https\nhost=github.com\n' | git credential fill`
   using the inherited environment (`GIT_CONFIG_PARAMETERS`, `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`) that Desktop set for the current operation, per `withTrampolineEnv`: [1](#0-0) .
3. Have the victim clone/fetch/checkout that repository in Desktop, triggering the filter/hook during the git operation.
4. The trampoline server accepts the request (only checks token validity, not host/remote binding) and `getGitHubCredential`/`findGitHubTrampolineAccount` returns the signed-in account's real `login`/`token` because the requested host origin (`github.com`) matches an account, irrespective of the actual remote being fetched: [4](#0-3) [5](#0-4) .
5. The filter/hook process now has the victim's plaintext GitHub OAuth token, exfiltratable over the network.

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
