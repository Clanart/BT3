### Title
Governance-set `Kip71GasTarget = 0` causes division-by-zero panic in KIP-71 base fee calculation - ([File: params/kip71_config.go])

### Summary
The `Kip71GasTarget` governance parameter has no zero-value format check, unlike `Kip71BaseFeeDenominator`. A vote setting `kip71.gastarget` to `0`, once ratified into `header.Governance`, causes `KIP71Config.NextMagmaBlockBaseFee` to divide by a zero `big.Int`, panicking on every node that validates a header, builds a block, or queries `eth_feeHistory`/gas price after the ratification. This mirrors the ImageMagick `jp2.c` division-by-zero bug class (attacker/authorized-input-controlled value flows unchecked into a divisor), but here the "crafted input" is a governance-parameter vote rather than a file.

### Finding Description
`Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (always returns true), in contrast to `Kip71BaseFeeDenominator`, whose checker explicitly requires `v != 0`: [1](#0-0) 

When a validator council member/proposer casts this vote, `VerifyVote`/`checkConsistency` in the header-governance module performs no additional bound check for `Kip71GasTarget` — it simply falls into the generic "no more checks" branch and is accepted: [2](#0-1) 

Once ratified at an epoch boundary (via `header.Governance`), `GasTarget` becomes `0` in the active `ParamSet`/`KIP71Config` for all subsequent blocks. `NextMagmaBlockBaseFee` then unconditionally uses `gasTarget` as a divisor without any zero-check (only `BaseFeeDenominator` has a zero-guard fallback): [3](#0-2) [4](#0-3) 

Both the gas-used-above-target branch (`y := x.Div(x, new(big.Int).SetUint64(gasTarget))`) and the gas-used-below-target branch (`y := x.Div(x, gasTarget)`) divide by `gasTarget`. Go's `math/big.Int.Div` panics with `"division by zero"` when the divisor is zero. Since `parentGasUsed` will almost always differ from `gasTarget == 0` (any nonzero gas usage), the panic path is reached on essentially every block after the malicious parameter takes effect.

This function is invoked from consensus-critical and RPC-facing paths, e.g. header verification/base-fee calculation in `blockchain/block_validator.go`, block building in `work/worker.go`, chain generation in `blockchain/chain_makers.go`, tx pool base fee checks in `blockchain/tx_pool.go`, and the public `eth_feeHistory`/gas price oracle in `node/cn/gasprice/feehistory.go` and `node/cn/gasprice/gasprice.go`.

### Impact Explanation
Once `GasTarget = 0` is ratified, every node computing the next block's base fee — during block validation, block proposal, or answering `eth_feeHistory`/gas price RPC calls — panics with a division-by-zero runtime error. This is a chain-wide crash/halt (loss of availability for the CN network and public RPC), matching the CVSS 3.1 profile of the referenced ImageMagick bug (`C:N/I:N/A:H`, availability-only). Because the crash occurs deterministically in header/base-fee validation logic shared by all nodes, it can stall block production entirely (all validators panic when trying to build/verify the next block), which is a severe consensus-availability impact even though it does not itself cause value theft or state divergence between honest nodes (they all fail identically).

### Likelihood Explanation
Setting this parameter requires a governance vote, i.e., an authorized council/proposer or (in single-governance mode) the governing node. This is a privileged but legitimate actor path explicitly named in-scope ("governance parameters"). The vote is not rejected by any format check (`noopFormatChecker`) or consistency check, so a single malicious or buggy vote (accidental misconfiguration is also plausible) that gets ratified at an epoch boundary is sufficient to trigger the panic on the very next block after ratification.

### Recommendation
Add a zero-value format check to `Kip71GasTarget` (and defensively to `Kip71MaxBlockGasUsedForBaseFee`/related fields used as divisors) in `kaiax/gov/param.go`, similar to `Kip71BaseFeeDenominator`'s `v != 0` check. Additionally, add a defensive zero-guard in `KIP71Config.NextMagmaBlockBaseFee` (params/kip71_config.go) before dividing by `gasTarget`, mirroring the existing fallback logic already present for `baseFeeDenominator == 0`.

### Proof of Concept
1. As an authorized voter (governing node in single mode, or council member/proposer in multi mode), submit a `governance_vote` for `kip71.gastarget` with value `0`. `NewVoteData`/`FormatChecker` accepts it because `noopFormatChecker` always returns true (`kaiax/gov/param.go:324-333`).
2. The vote passes `VerifyVote`/`checkConsistency` unchanged (`kaiax/gov/headergov/impl/header.go:213-220`), and gets embedded into `header.Vote`, then ratified into `header.Governance` at the next epoch boundary.
3. From the next block after ratification onward, any block with `parentGasUsed != 0` triggers `KIP71Config.NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))` (params/kip71_config.go:100-103) or the symmetric branch at line 118-121, causing a `runtime` panic ("division by zero") in every node that verifies/builds the header, and in every RPC node computing `eth_feeHistory`/`gasprice` (node/cn/gasprice/feehistory.go, node/cn/gasprice/gasprice.go).

Note: I could not fully trace every RPC-facing entry point (e.g., exact `eth_gasPrice`/`eth_feeHistory` handler wiring) within the available index; the citation for `NextMagmaBlockBaseFee`'s call sites in `blockchain/block_validator.go` and `work/worker.go` was located by grep but not read in full detail due to the final-iteration constraint — a full Devin session could confirm the exact panic call stacks in those files.
