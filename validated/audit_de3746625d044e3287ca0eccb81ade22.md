### Title
Escrow balance decremented after external transfer in `withdraw()` allows reentrant double-payout - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` (Tron variant) pays out escrowed order funds to the beneficiary via a raw `.call` **before** decrementing the per-token escrow accounting (`_orders[commitment][token]`), the same checks-effects-interactions violation as the `sponsor()`/`mint()` bug in the reference report: state that gates further payouts is updated only *after* an external call that can trigger a callback.

### Finding Description
In `withdraw()`: [1](#0-0) 

`_filled[body.commitment]` is set up-front (good), but the per-token escrow balance `_orders[body.commitment][token]` is only *checked* to be non-zero before the transfer, and is *decremented only after* the `.call` (native ETH `beneficiary.call{value: amount}("")` or ERC-20 `token.call(...transfer...)`) returns. This is a direct analog of the H-05 pattern: an external call capable of re-entering the contract happens before the accounting state (`totalSponsored`-equivalent, here `_orders[commitment][token]`) is updated.

`withdraw()` is only reachable internally from `onAccept` and `onGetResponse`, both `onlyHost`-gated, and the `EvmHost` layer sets its own replay-protection receipt (`_requestReceipts`/`_responseReceipts`) *before* invoking the app callback, which normally prevents the exact same inbound message from re-triggering `onAccept`/`onGetResponse` twice: [2](#0-1) [3](#0-2) 

However, that host-level replay guard is keyed on the **hash of the whole inbound request/response** (which includes nonce/height/context), not on the order's `body.commitment`. Two distinct, independently-provable messages (e.g. two GET-response proofs at different heights, or a POST delivery plus a GET-response delivery) can both carry a `WithdrawalRequest` referencing the *same* `body.commitment`/token. If the attacker controls (or the order references) a token contract whose `transfer()` — or a malicious `beneficiary` contract's `receive()` for the native-token branch — calls back into the handler to process the second, already-available proof mid-transaction, that second call reaches `withdraw()` again for the same commitment/token *before* the first call's `_orders[commitment][token] -= amount` has executed. The stale, not-yet-decremented balance still passes the `_orders[...][token] == 0` check, so the same escrowed amount is paid out twice.

This mirrors the sandclock finding precisely: the guarding state (`_orders[commitment][token]`) is only mutated after the callback-capable external call, so multiple deliveries of value referencing the same commitment can be honored once the callback is used to interleave a second valid message.

### Impact Explanation
A successful reentrant interleave causes the same escrowed input tokens (or native asset) to be paid out twice to the beneficiary — direct loss of bridge-custodied funds exceeding what was actually escrowed for the order, i.e. fund loss/double-settlement against the escrow custody invariant that Hyperbridge's bounty scope explicitly protects ("Bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount").

### Likelihood Explanation
Moderate: it requires the attacker to be able to get two distinct, independently valid delivery messages for the same order commitment accepted in the same transaction via a reentrant callback (a malicious escrowed token contract or a malicious beneficiary contract triggering a second `handlePostRequests`/`handleGetResponses` call). This is achievable by an unprivileged order creator who chooses the escrowed token contract and beneficiary address themselves and who submits both proofs, without needing a compromised relayer, prover, or admin — it only needs two legitimately provable messages plus a callback hook, both of which are attacker-controlled inputs to `placeOrder`.

### Recommendation
Apply checks-effects-interactions in `withdraw()`: decrement `_orders[body.commitment][token]` (and validate it against `amount`, not just non-zero) *before* performing the native/ERC-20 transfer `.call`, matching the CEI fix already applied to `_fillSameChain`/`_fillCrossChain` in `evm/src/apps/intentsv2/IntrinsicIntents.sol` (per the regression tests in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`). Additionally consider adding a `nonReentrant` guard around the app-level callback entrypoints (`onAccept`, `onGetResponse`).

### Proof of Concept
1. Attacker places a cross-chain order with an input token that is a malicious ERC-20 whose `transfer()` calls back into `HandlerV2`.
2. Attacker independently obtains two valid delivery proofs referencing the same order `commitment` (e.g., a GET-response proof and, separately, a duplicate/alternate proof for the same storage slot at a different finalized height) — both are legitimate, provable messages, not spoofed.
3. Attacker submits the first message; `EvmHost.dispatchIncoming` stores its own message receipt and calls `onGetResponse` → `withdraw()`.
4. Inside `withdraw()`, the malicious token's `transfer()` (or malicious beneficiary's `receive()`) callback re-invokes the handler with the second proof before `_orders[commitment][token] -= amount` runs.
5. The second call reaches `withdraw()` again; `_orders[commitment][token]` is still at its pre-decrement value, so the check passes and the same escrow is paid out a second time.
6. Both calls unwind normally, leaving `_orders[commitment][token]` decremented once but the beneficiary having received the payout twice.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
