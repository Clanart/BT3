## Analysis

Tracing `Context.RecoverCells` → `recoverPolynomialCoeffs` → `DataRecovery.RecoverPolynomialCoefficients`:

The recovery algorithm builds `extendedBlob` with attacker-supplied cell values at the known `cellIDs` positions and zeros at the missing positions [1](#0-0) , then calls `RecoverPolynomialCoefficients`, which computes `gtilde = IFFT(data(x)·z(x))`, divides by `z(x)` on a coset, inverse-transforms, and **unconditionally truncates** the result to the first `numScalarsInDataWord` (4096) coefficients with no check that the discarded high-order coefficients are zero [2](#0-1) .

Mathematically: because `z(x)` is constructed to vanish exactly at the missing indices and the zeroed positions of `data(x)` guarantee `gtilde` vanishes there too, `gtilde` is *always* exactly divisible by `z(x)` — **regardless of whether the supplied cell values are actual evaluations of a degree<4096 polynomial**. The quotient `q = gtilde/z` has degree bound `≤ numScalarsInCodeword-1-deg(z)`. Only when the number of missing points equals exactly `numScalarsInCodeword - numScalarsInDataWord` (i.e., the caller supplies the *bare minimum* number of cells) does this bound force `deg(q) < 4096`. If the caller supplies more cells than the strict minimum (fewer missing blocks, so `deg(z)` is smaller), the bound on `deg(q)` can exceed 4096, and the truncation silently drops nonzero high-order coefficients. This confirms the reported effect: with inconsistent (non-low-degree) cell data plus a "redundant" cell set, `RecoverPolynomialCoefficients` returns a wrong low-degree truncation whose re-evaluation at the supplied `cellIDs` positions does **not** match the originally supplied `cells[i]` values — yet no error is returned.

I verified no length/order/count guard in `recoverPolynomialCoeffs` (`ErrNumCellIDsNotEqualNumCells`, `isAscending`, `ErrFoundInvalidCellID`, `ErrNotEnoughCellsForReconstruction`) checks polynomial consistency or degree [3](#0-2) , and `RecoverPolynomialCoefficients` itself performs no post-hoc check that `cosetQuotientEval[dr.numScalarsInDataWord:]` is all-zero before truncating [4](#0-3) .

I could not access the c-kzg / consensus-specs reference implementation source directly to confirm whether it performs an analogous re-evaluation/consistency check after recovery (e.g., recomputing cells from the truncated polynomial and comparing against the supplied input cells) that this Go implementation lacks. I also could not find in this repo's test files (`consensus_specs_test.go`) any explicit test vector exercising this exact "supplied more than minimum cells with inconsistent data" scenario, so I cannot confirm from the index whether upstream test vectors already cover/reject this case.

Given the missing verification step is real and reachable through an unprivileged, public API (`Context.RecoverCells`, `Context.RecoverCellsAndComputeKZGProofs`) with attacker-fully-controlled cell bytes, and the derived math shows a genuine divergence between the truncated recovered polynomial and the supplied cell values under a specific redundant-cell-count precondition, this appears to be a legitimate finding.

### Title
RecoverPolynomialCoefficients silently truncates without verifying high-order coefficients are zero, breaking the recovered==supplied invariant - (File: internal/erasure_code/erasure_code.go)

### Summary
`DataRecovery.RecoverPolynomialCoefficients` truncates the computed quotient polynomial to `numScalarsInDataWord` (4096) coefficients without verifying that the coefficients beyond index 4095 are zero. When an attacker supplies more than the strict minimum number of cells with values that are not evaluations of any real degree<4096 polynomial, the true quotient's degree bound can exceed 4096, so the truncation discards nonzero terms and the returned "recovered" polynomial no longer reproduces the supplied cell values at their positions.

### Finding Description
The broken equality is: for every `cellIDs[i]`, `recovered(cellIDs[i]) == cells[i]`, where `recovered` is derived by re-evaluating the polynomial coefficients returned from `RecoverPolynomialCoefficients`.

Path: `Context.RecoverCells`/`RecoverCellsAndComputeKZGProofs` (`api_eip7594.go:8`, `148`) → `recoverPolynomialCoeffs` (`api_eip7594.go:97-146`), which deserializes attacker cells into `extendedBlob` (zeros at missing positions) and calls `ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)` (`internal/erasure_code/erasure_code.go:110-148`).

Root cause: the vanishing-polynomial erasure-decoding trick guarantees `gtilde = data(x)·z(x)` is always exactly divisible by `z(x)` (since `z` vanishes at all missing points and `data` is forced to zero there too) — this divisibility holds even when `data` is not a valid low-degree codeword. The resulting quotient `q`'s degree bound is `numScalarsInCodeword-1-deg(z)`. Only at the minimal-cells threshold does this bound guarantee `deg(q) < 4096`; with more supplied cells, `deg(z)` shrinks and the bound can exceed 4096. The code blindly does `polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]` (line 146) with no check that `cosetQuotientEval[4096:]` are zero.

Attacker's exact bytes: a cell set exceeding the reconstruction minimum, where the supplied evaluations are deliberately inconsistent with any real degree<4096 polynomial (e.g., differing from the low-degree extension by a controlled high-degree perturbation). None of the existing guards (`ErrNumCellIDsNotEqualNumCells`, `isAscending`, `ErrFoundInvalidCellID`, `ErrNotEnoughCellsForReconstruction`) check polynomial consistency or degree, so the malformed set passes straight through.

### Impact Explanation
The returned recovered cells/polynomial (and any KZG proofs computed from it via `computeCellsFromPolyCoeff`/`computeKZGProofsFromPolyCoeff`) will not match the client's originally supplied, "known-good" cells, and this Go implementation's output for a given input may diverge from what a stricter/naively-correct implementation would produce or reject. This matches the "High" category: client split on emitted recovered data/cells/proofs for the same input, or acceptance where a correct implementation would detect inconsistency.

### Likelihood Explanation
Requires the caller to invoke `RecoverCells`/`RecoverCellsAndComputeKZGProofs` with a redundant cell set (more than the bare minimum `NumBlocksNeededToReconstruct` blocks) containing crafted, low-degree-inconsistent values. This is fully attacker-controlled and repeatable per call, with no special privileges — any actor authoring cell bytes for a partial-data-recovery protocol path can attempt it.

### Recommendation
After computing `cosetQuotientEval`, verify that all coefficients from index `numScalarsInDataWord` to the end are zero (or equivalently, re-evaluate the truncated polynomial at the supplied `cellIDs` and assert it equals `cells[i]`) before returning success from `RecoverPolynomialCoefficients`; return an error otherwise.
