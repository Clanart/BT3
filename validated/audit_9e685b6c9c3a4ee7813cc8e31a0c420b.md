### Title
Panic via out-of-map `decryptor` index in `Decryption::decrypt_with_proof` — denial of service during DKG blame resolution - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` — a `HashMap` index that panics when the participant isn't registered — before doing anything else with the caller-supplied `decryptor` argument. The analogous panic exists in `Encryption::encrypt` via `self.decryption.enc_keys[&participant]`. An unprivileged counterparty who causes a blame/decryption path to be invoked for a participant that never registered an `EncryptionKeyMessage` crashes the victim's DKG session — a crafted-input memory-safety-style crash, the analog of CVE-2017-7056's "crafted input → application crash".

### Finding Description
`Decryption::new` starts with an empty `enc_keys` map, populated only by `register`, which inserts `msg.enc_key` for a given `Participant` [1](#0-0) . In `decrypt_with_proof`, after verifying the PoP signature, the code evaluates `self.enc_keys[&decryptor]` directly inside the DLEq verify call [2](#0-1) . `HashMap`'s `Index` impl panics on a missing key. There is no `contains_key`/`get` check, and `decryptor` is an arbitrary `Participant` (any non-zero `u16`, per `Participant::new` which only rejects `0` [3](#0-2) ). The same pattern exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]` [4](#0-3) ). By contrast, `register` uses an explicit `assert!` for re-registration [5](#0-4) , showing the authors treated lookup failures as programmer errors rather than attacker-reachable conditions.

### Impact Explanation
A panic in the DKG share-decryption/blame path aborts the victim's threshold key generation. Because PedPoP blame resolution is triggered by accusing/accused parties' messages, an unprivileged participant (or anyone able to feed the decryption path a `decryptor` index that was never registered — e.g., a participant who omitted their `EncryptionKeyMessage`, or an index beyond `n` which `Participant::new` still accepts) causes a hard crash rather than a graceful `DecryptionError`. Across a distributed validator set, repeated triggering is a liveness denial of service on threshold signing setup. Severity: Medium (crash/DoS reachable by a protocol peer's crafted inputs; no secret leakage or forgery).

### Likelihood Explanation
The trigger requires only that `decrypt_with_proof` be invoked with a `decryptor` not present in `enc_keys`. The PoP check at lines 374–379 must pass first, but the PoP is over `from` (the accused sender), not `decryptor`, so the panic condition is independent of the signature verification. Any code path that maps an accusation onto a `decryptor` index — including a malformed or inconsistent accusation, or a `decryptor` whose registration was never received — reaches the unchecked index. Rust panics in a thread handling DKG messages abort that work unit; in a `catch_unwind`-less async executor or FFI context the process dies outright.

### Recommendation
Replace the `HashMap` indexing with fallible lookup: `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` in `decrypt_with_proof` (line 388), and likewise `.get(&participant)` returning an error in `encrypt` (line 466). Also validate that `u16::from(decryptor) <= params.n` before lookup, since `Participant` admits values beyond `n`.

### Proof of Concept
```rust
// crypto/dkg/pedpop context; C = any Ciphersuite (e.g. Ristretto)
let dec: Decryption<C> = Decryption::new([0u8; 32]);
// Attacker-supplied EncryptedMessage with a valid PoP (they control the ephemeral key)
let msg: EncryptedMessage<C, E> = /* crafted, pop valid for `from` */;
// `decryptor` = Participant::new(65535) — never registered, > n
let _ = dec.decrypt_with_proof(from, Participant::new(65535).unwrap(), msg, Some(proof));
// Panics at self.enc_keys[&decryptor] (encryption.rs:388) -> index out of map
```
Note: exact reachability depends on the caller that selects `decryptor` during blame handling (in the coordinator/DKG layer, outside this crate); I could not fully trace that call site within the available search iterations, but the panic itself is unconditional once an unregistered index is passed, and no bounds check ties `decryptor` to `params.n`.
