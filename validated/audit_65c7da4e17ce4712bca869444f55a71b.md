### Title
Unbounded EIP-7702 authorization list processed in `EVMPreprocessDecorator` before any gas/size check, enabling per-block compute DoS - (File: `x/evm/ante/preprocess.go`)

### Summary
`EVMPreprocessDecorator.AnteHandle` iterates over every entry of a `SetCodeTx`'s authorization list via `associateAuthorizationAuthorities`, performing an ECDSA public-key recovery plus a full keeper read/write for each authority, with no cap on the number of authorizations processed. This loop runs under an infinite gas meter and executes *before* `BasicDecorator`'s intrinsic-gas / block-max-gas validation (which only runs later, when `next(ctx, tx, simulate)` is finally invoked). This mirrors the reported `partyAPendingQuotes` class of bug: a user-controlled array is appended/iterated without a length bound check at the point of use, letting an attacker inflate per-transaction work that downstream logic (liquidation loops / here, gas metering) can no longer bound.

### Finding Description
`EVMPreprocessDecorator.AnteHandle` calls `p.associateAuthorizationAuthorities(ctx, msg, associateHelper)` unconditionally for `SetCodeTx` transactions: [1](#0-0) 

That helper loops over *all* `ethTx.SetCodeAuthorizations()` with no length limit, doing ECDSA recovery (`AuthorityToPreAssociate` → `RecoverAddressesFromAuthorization`) and a keeper `AssociateAddresses` call per entry: [2](#0-1) [3](#0-2) 

Critically, this happens *after* the ante decorator switches to an infinite gas meter (line 65) but *before* `next(ctx, tx, simulate)` is invoked, which is where `BasicDecorator` performs the only cap-related check — `core.IntrinsicGas(...)` and the block-max-gas comparison: [4](#0-3) [5](#0-4) 

So the number of authorizations that get individually ECDSA-recovered and keeper-written is bounded only by how many `SetCodeAuthorization` entries an attacker can fit in a transaction under the mempool/tx-size limit — not by any explicit cap on the authorization list itself, and not by real gas metering (the ante-stage loop runs on the infinite gas meter). A single `SetCodeTx` with tens of thousands of authorization entries would force every validating node's DeliverTx (and every node's CheckTx, via the analogous legacy path `AssociateAuthorizationAuthorities` in `app/ante/evm_checktx.go`) to perform that many secp256k1 recoveries and keeper accesses before the transaction is even gas-checked or can be rejected for exceeding gas limits.

### Impact Explanation
Every validator must process this transaction identically during block execution (DeliverTx), and mempool nodes also run the equivalent path in CheckTx. A crafted transaction with a very large authorization list forces disproportionate CPU work (ECDSA recovery is one of the more expensive primitives per-item) network-wide for a single transaction fee, which can materially delay block production/propagation — matching the "block delay beyond 2.5 seconds" impact bar for this program. Because the loop executes under an infinite gas meter, the protocol has no mechanism to charge for or cap this real compute cost proportionally, unlike normal EVM execution gas accounting.

### Likelihood Explanation
Reachable by any unprivileged sender submitting a single standard EIP-7702 `SetCodeTx` transaction through the public RPC — no special privileges, precompile access, or governance action required. The only constraint is transaction byte-size limits, which still permit a large number of ~125-byte authorization tuples per transaction.

### Recommendation
Enforce an explicit maximum authorization-list length (or a cumulative pre-association budget) in `associateAuthorizationAuthorities` / `AssociateAuthorizationAuthorities`, rejecting or truncating processing once exceeded, and move (or duplicate) the intrinsic-gas / authorization-count validation from `BasicDecorator` ahead of the authority pre-association loop in `EVMPreprocessDecorator` so oversized authorization lists are rejected before any per-entry cryptographic work is performed.

### Proof of Concept
1. Attacker generates N (e.g., 20,000) throwaway EOA keys and signs N valid `SetCodeAuthorization`s (chain ID matching, nonce 0, no code) for a `SetCodeTx`.
2. Attacker sets the transaction's `AuthList` to all N authorizations, sets a legitimate sender/nonce, and sets `Gas` high enough to pass `BasicDecorator`'s intrinsic-gas check (which is only evaluated after the loop already ran).
3. Submits the transaction to the network.
4. Every node's `EVMPreprocessDecorator.AnteHandle` → `associateAuthorizationAuthorities` performs N ECDSA recoveries and N keeper reads/writes under the infinite gas meter, all before any gas-based rejection can occur, consuming disproportionate CPU during DeliverTx/CheckTx and slowing block processing chain-wide.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
}
