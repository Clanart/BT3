### Title
Invalid encryption PoP can prematurely reveal a PedPoP ECDH blame key - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
High severity. `KeyMachine::calculate_share` returns a decryption `blame` proof before the batched proof-of-possession for the corresponding `EncryptedMessage` has been verified. A malicious participant can reuse the ephemeral encryption key from another participant’s encrypted share, attach an invalid PoP and ciphertext that probably decrypts to a non-canonical scalar, and cause the victim to emit the ECDH key for the reused message key. Publishing that blame value exposes the cipher key needed to decrypt the observed honest share.

### Finding Description
`Encryption::decrypt` queues the message PoP into `BatchVerifier`, but immediately derives `ecdh`, decrypts the ciphertext, and constructs an `EncryptionKeyProof` containing that ECDH result before the batch is verified. [1](#0-0) 

`calculate_share` then checks whether the decrypted bytes are a canonical scalar and returns `PedPoPError::InvalidShare { blame: Some(blame.clone()) }` before reaching `batch.verify_with_vartime_blame()`. [2](#0-1) [3](#0-2) 

This bypasses the protection described by `EncryptedMessage`: without a PoP bound to the sender and ciphertext, an observer can reuse another sender’s key and induce the recipient to reveal the corresponding ECDH result. [4](#0-3)  The PoP challenge explicitly binds the context, nonce, reused key, sender, and ciphertext, so a copied PoP cannot authenticate the attacker’s modified message. [5](#0-4) 

The returned `EncryptionKeyProof` is not merely an abstract proof: its `key` field is the ECDH group element and is serialized directly, allowing anyone receiving the blame proof to derive the ChaCha20 stream used by the referenced message. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker participating in PedPoP can recover an encrypted `SecretShare` sent by another participant to the victim. The attacker first obtains an honest encrypted share message, extracts its public message key `X`, then submits their own malformed `EncryptedMessage` with `key = X`, an invalid PoP, and attacker-selected ciphertext. The victim derives the shared point `bX`, where `b` is the victim’s registered encryption private key, and includes it in the returned blame proof. [8](#0-7) 

If the application distributes the returned blame proof as intended, the attacker can use `bX` to reconstruct the encryption transcript and decrypt the previously observed honest ciphertext. That reveals the honest participant’s PedPoP `SecretShare`, the exact side effect the PoP is designed to prevent. [4](#0-3) 

### Likelihood Explanation
The attack requires only a malicious DKG participant and an observed encrypted share message. The forged PoP can remain syntactically valid while failing verification because the challenge covers the attacker’s participant ID and modified ciphertext. [5](#0-4) 

The attacker cannot control the decrypted bytes because they do not know the ECDH key, but random plaintext has a high probability of being a non-canonical field encoding for the in-scope prime-field ciphersuites. If the early `from_repr` check fails, the vulnerable `Some(blame)` path is reached before batch verification can classify the PoP as the failure. Retrying across DKG sessions or message attempts makes the attack reliable. [2](#0-1) 

### Recommendation
Do not derive or return an `EncryptionKeyProof` until the message PoP has been verified successfully. In particular:

- Verify the PoP before decrypting, or retain a failure flag and always execute `batch.verify_with_vartime_blame()` before returning an invalid-scalar error.
- If both the PoP and decoded share are invalid, return `InvalidShare` with `blame: None`.
- Delay `DLEqProof::prove` and disclosure of the ECDH point until all authenticity checks for the exact `key`, sender, and ciphertext have passed.
- Add a regression test that reuses an honest message key, invalidates the PoP, mutates the ciphertext until scalar decoding fails, and asserts that `calculate_share` returns `blame: None`.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res

/// A proof that the provided encryption key is a legitimately derived shared key for some message.
#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub struct EncryptionKeyProof<C: Ciphersuite> {
  key: Zeroizing<C::G>,
  dleq: DLEqProof<C::G>,
}

impl<C: Ciphersuite> EncryptionKeyProof<C> {
  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<Self> {
    Ok(Self { key: Zeroizing::new(C::read_G(reader)?), dleq: DLEqProof::read(reader)? })
  }

  pub fn write<W: io::Write>(&self, writer: &mut W) -> io::Result<()> {
    writer.write_all(self.key.to_bytes().as_ref())?;
    self.dleq.write(writer)
  }

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
