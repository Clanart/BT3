### Title
Stale conflicted-files snapshot in `CommitConflictsWarning` allows silent commit of different files than the ones reviewed - (File: `app/src/ui/merge-conflicts/commit-conflicts-warning.tsx`)

### Summary
The confirmation dialog shown before committing files that still contain unresolved conflict markers displays a **snapshot** of the conflicted files at the moment the user clicked "Commit". When the user confirms, the dialog does not re-validate that snapshot against the current working-directory state — it just tells the dispatcher to commit whatever is currently selected. If the working directory changes between the snapshot and the confirmation click (e.g. because of a background status refresh triggered by activity originating from the fetched/cloned repository), the user can end up creating a commit whose contents differ from what they reviewed and approved, without any further warning.

### Finding Description
`ChangesSidebar.onCreateCommit` computes `conflictedFilesSelected` from the current `workingDirectory` state and, if non-empty, opens a popup carrying that exact array as `files`: [1](#0-0) 

This `files` array is a **snapshot**, explicitly documented as "files that were selected for committing that are also conflicted": [2](#0-1) 

`CommitConflictsWarning` renders that snapshot to the user ("you'll be committing the following conflicted files") as the basis for their decision: [3](#0-2) 

But when the user clicks "Yes, Commit Files", `onSubmit` never passes the reviewed `files` list to the commit call — it only forwards `repository` and `context`, letting `commitIncludedChanges` re-derive whatever is currently selected in the live working-directory state at that moment: [4](#0-3) 

This is the same broken invariant as the oracle report: the object the user reviewed (`pendingOracleData` / the snapshotted `files` array) is not the object that is ultimately acted upon (`pendingOracle` on-chain / the live `workingDirectory` selection read at commit time). There is no re-check that the two are still equal before the action (accepting the oracle / creating the commit) executes.

### Impact Explanation
This matches the "silent corruption of what the user commits" impact category. If the file selection or on-disk contents of the conflicted files change during the (however brief) window between the popup being shown and the user clicking confirm — for example due to a filesystem/status refresh triggered by processes reacting to the just-fetched/merged attacker-controlled branch (build tooling, git hooks, editor auto-format, LFS smudge filters, etc. operating on files brought in by the merge) — Desktop will commit a different set of files/content than what the user explicitly reviewed and approved in the warning dialog. Since this dialog exists specifically to give the user a last chance to avoid committing unresolved conflict markers, silently committing a different (possibly still-conflicted or attacker-influenced) file set defeats the purpose of the safeguard.

### Likelihood Explanation
The window is a normal UI round-trip (render popup → user reads it → user clicks OK), during which Desktop's existing status-refresh mechanisms (`_loadStatus`/`refreshChangesSection`) can legitimately fire and mutate `changesState.workingDirectory` in `app-store.ts`. No user action beyond the normal "click confirm" is required, and no elevated privileges are needed — the only external trigger required is content in the fetched/merged repository (e.g. hook scripts, generated files, or LFS objects) that causes working-directory files to change shortly after the merge/conflict state is computed. I was not able to fully trace the internal implementation of `commitIncludedChanges` (its definition was not resolved within the available search budget), so the exact re-computation logic at commit time could not be independently confirmed beyond what is shown in `commit-conflicts-warning.tsx`; this should be verified against the dispatcher/app-store commit path before treating severity as final.

### Recommendation
Have `CommitConflictsWarning.onSubmit` pass the originally reviewed `files` (or a hash/paths+conflict-state fingerprint of them) back into the commit call, and re-diff them against the current `workingDirectory` state immediately before committing. If the set of conflicted/selected files or their conflict-resolution status has changed since the dialog was shown, abort and re-prompt the user with the updated list, mirroring the oracle registry fix pattern of comparing the accepted value against the current on-chain value before proceeding.

### Proof of Concept
1. Stage a merge/rebase that leaves conflict markers in `file.txt`; select `file.txt` for commit while conflict markers remain.
2. Desktop opens `CommitConflictsWarning` showing `file.txt` as the file that will be committed (snapshot taken in `sidebar.tsx#onCreateCommit`).
3. Before clicking "Yes, Commit Files", trigger a status refresh side effect from the merged branch's content (e.g. a script/hook/tool that runs as part of the fetched repository and rewrites `file.txt` or changes which files are selected/conflicted) so that the live `workingDirectory` state diverges from the snapshot shown in step 2.
4. Click "Yes, Commit Files". `onSubmit` in `commit-conflicts-warning.tsx` calls `dispatcher.commitIncludedChanges(repository, context)` without re-validating the `files` prop, committing whatever is currently selected/live rather than what the user reviewed and consented to.
