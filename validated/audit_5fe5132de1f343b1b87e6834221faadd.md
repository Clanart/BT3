### Title
Re-execution of `share_internal`/`complete` reuses a fixed cached FROST nonce seed, leaking the secret key share if the message or preprocess set ever differs - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The kernel bug class is a value that can change between unsynchronized reads (sysctl read twice, may differ). The Serai analog lives in `SigningProtocol::preprocess_internal`: a FROST preprocess *seed* is cached in the DB under a context key `(b"DkgConfirmer", attempt)` and re-read on every signing step for that context, while the *other* inputs to `sign()` (peer preprocesses, message) are supplied per call and can change between re-executions. The nonce is deterministic (fixed), but the values read alongside it are not — the exact inverse of the sysctl race, with the same consequence: an inconsistent (nonce, message/binding-factor) pair.

### Finding Description
`preprocess_internal` loads `CachedPreprocesses::get(txn, &context)`; if absent it generates a fresh preprocess, encrypts the seed, and stores it; otherwise it decrypts and rebuilds the machine via `AlgorithmSignMachine::from_cache`, which deterministically regenerates the *same* nonce pair `(d, e)` from the seed (`seeded_preprocess` → `ChaCha20Rng::from_seed` → `Commitments::new`) [1](#0-0) . The cached entry is never deleted or rotated after use.

`share_internal` calls `preprocess_internal().0` and then `machine.sign(preprocesses, msg)` with caller-supplied `serialized_preprocesses` and `msg` [2](#0-1) . `DkgConfirmer::share` and `DkgConfirmer::complete` both go through `share_internal`, and `complete` re-executes signing with freshly supplied `preprocesses` and `key_pair` (which feeds `set_keys_message`) [3](#0-2) . So `sign()` can run twice under the same context key with the same `(d, e)` but different binding factors `rho` and/or challenge.

In `sign.rs`, the actual nonce is `d + e * rho` where `rho` is bound to the peer preprocesses and message via `calculate_binding_factors`/`hash_binding_factor` [4](#0-3) . Two shares produced with the same `(d, e)` but different `(rho, challenge)` give two linear equations in `d, e`; recovering them then yields the secret share `s` from `share = nonce + challenge * λ * s`. This is the standard FROST nonce-reuse key extraction, and the crate itself states reuse "will enable third-party recovery of your private key share" [5](#0-4) .

The file header concedes the mechanism: "In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — and then lists two unimplemented safeguards as TODO: checking that the node's on-chain commitments match its presumed preprocess, and reviewing Processor preprocess handling [6](#0-5) . Safety currently rests entirely on the assumption that every re-execution observes byte-identical BFT-finalized inputs — the same assumption class as the missing `READ_ONCE()`: nothing enforces that the concurrently-supplied values haven't changed.

### Impact Explanation
If any execution path produces a second `sign()` under the same `(b"DkgConfirmer", attempt)` context with different peer preprocesses or a different `key_pair`/message (e.g., a re-executed `complete` observing different on-chain data than `share`, or a partial DB rebuild — explicitly acknowledged as unguarded), the validator's MuSig secret key is recoverable from its two published signature shares. That key is the validator's root-of-trust key used for DKG confirmation, so recovery compromises the validator set's signing identity — Critical/High impact for key-share recovery.

### Likelihood Explanation
Requires two `sign()` executions on the same context with differing inputs. Normal BFT-finalized flow keeps inputs identical, but the design deliberately re-executes `sign` in `share` *and* `complete`, persists the seed across reboots, and has acknowledged missing checks (TODOs at lines 51–54) plus a known partial-rebuild hazard. An unprivileged DKG participant can influence the preprocesses map and, through the DKG result, the `key_pair` in the message. Medium likelihood — consistent with a Medium analog.

### Recommendation
Bind the cached preprocess entry to the inputs that must be fixed: store the serialized `preprocess` alongside the seed and, before signing, verify the node's on-chain/published preprocess equals the regenerated one (the TODO at line 51). Additionally include a hash of `msg` and the sorted peer preprocess set in the `CachedPreprocesses` key or a stored digest, and refuse to sign on mismatch rather than reusing the nonce. Alternatively rotate/delete the seed after the first `share` is produced and persist the produced share for `complete` instead of re-signing.

### Proof of Concept
1. `DkgConfirmer::share(preprocesses_A, key_pair)` executes `preprocess_internal` (context `(b"DkgConfirmer", 0)`), creating/loading seed S → nonces `(d, e)`; `sign()` computes `rho_1` from `preprocesses_A` and emits share `σ_1 = d + e·rho_1 + c_1·λ·s`.
2. `DkgConfirmer::complete(preprocesses_B, key_pair', shares)` re-executes `share_internal`; the cached seed S again yields `(d, e)` but `preprocesses_B` (distinct peer commitments supplied in the call) produce `rho_2 ≠ rho_1`, emitting `σ_2 = d + e·rho_2 + c_2·λ·s`.
3. From `σ_1, σ_2`: `e = (σ_1 − σ_2 − (c_1 − c_2)·λ·s…)` — solve the 2×2 system for `d, e` treating `s` symbolically, or use the standard two-nonce FROST extraction to recover `s` directly since `d + e·rho` is known-structure. Either way the validator's `self.key` share is recovered, per the crate's own warning that cached-preprocess reuse "will presumably cause the signer to leak their secret share" [7](#0-6) .
