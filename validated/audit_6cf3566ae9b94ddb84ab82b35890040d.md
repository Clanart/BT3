## Title
`CW721ERC721Pointer` does not override `safeTransferFrom`, causing inherited OpenZeppelin `ERC721.safeTransferFrom` to bypass the CW721 wasm bridge - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer` overrides `transferFrom` to route ownership transfer through the CW721 CosmWasm contract via the wasmd precompile, but it never overrides `safeTransferFrom`. [1](#0-0) 

### Finding Description
`CW721ERC721Pointer` is a pointer contract that lets EVM callers interact with a CW721 CosmWasm NFT contract as if it were a standard ERC721 token. All read functions (`ownerOf`, `balanceOf`, `getApproved`, etc.) are overridden to query the underlying CW721 contract via the wasmd precompile rather than any local OpenZeppelin storage, and `transferFrom` is overridden to submit a `transfer_nft` execute message to the wasm contract. [2](#0-1) [3](#0-2) 

However, `safeTransferFrom(address,address,uint256)` and `safeTransferFrom(address,address,uint256,bytes)` are not present anywhere in `CW721ERC721Pointer.sol`. [4](#0-3) 

Because the contract extends OpenZeppelin's `ERC721`, callers can still invoke `safeTransferFrom` since it is inherited and public. The report's underlying bug class ("use safeTransferFrom instead of transferFrom" / inconsistent use of the two functions) maps here to the inverse and more severe problem: the pointer's *own* state (the inherited OZ `_owners`/`_balances`/`_tokenApprovals` mappings) is never populated by any of the overridden functions, since ownership is tracked exclusively on the CosmWasm side and queried live through `WasmdPrecompile`/`JsonPrecompile`. If the inherited `safeTransferFrom` executes against this empty/never-synced local storage instead of being routed to the wasm bridge like `transferFrom` is, the two entry points into "the same conceptual transfer" behave inconsistently: one moves the real underlying CW721 token ownership, the other operates (or fails) against uninitialized local bookkeeping that has no relationship to actual token custody.

### Impact Explanation
I was not able to fully confirm at the OpenZeppelin bytecode/dispatch level (due to tool/iteration limits) whether the specific OZ version used here dispatches `safeTransferFrom` through the overridden `transferFrom`/`_update` (which would make it merely a functional/no-op-safety-check issue) or through independent internal state that was never initialized (which would make calls unconditionally revert, or — worse — succeed against phantom local state disconnected from the real CW721 owner records, letting the caller in the failing case observe reverts and in the worse case desynchronize the pointer's notion of ownership from the underlying CW721 contract's ground truth). This uncertainty is a **hard blocker** to confirming concrete fund loss/freezing per the validation rubric.

### Likelihood Explanation
Any EVM user holding (or believing they hold) a CW721-backed NFT through this pointer contract could trigger this simply by calling `safeTransferFrom`, which is part of the standard `IERC721` interface that off-the-shelf marketplaces and wallets call by default in preference to bare `transferFrom`. No special privilege is required — this is reachable by any public RPC/contract-call transaction.

### Recommendation
Override both `safeTransferFrom(address,address,uint256)` and `safeTransferFrom(address,address,uint256,bytes)` in `CW721ERC721Pointer` (mirroring the pattern already used in `CW1155ERC1155Pointer.safeTransferFrom`, which correctly routes the transfer through `_execute` against the wasm contract and then performs the `onERC721Received` callback check) so that both transfer entry points consistently move real CW721 ownership through the wasmd precompile. [5](#0-4) 

### Proof of Concept
Not fully constructible without confirming OZ's ERC721 version-specific dispatch behavior for `safeTransferFrom` in this codebase (the relevant `node_modules`/vendored OpenZeppelin `ERC721.sol` source was not retrievable through the available search tools within the iteration budget). A concrete PoC would need to: deploy `CW721ERC721Pointer`, mint/transfer a token so a CW721-side owner exists, then call `pointer.safeTransferFrom(owner, recipient, tokenId)` and observe whether it (a) reverts unexpectedly for a legitimate owner, or (b) succeeds while leaving the real CW721 contract's `owner_of` unchanged — either of which would need direct testing/tracing to confirm before this can be escalated with certainty.

    function transferFrom(address from, address to, uint256 tokenId) public override {
        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }

    function safeTransferFrom(
        address from,
        address to,
        uint256 id,
        uint256 amount,
        bytes memory data
    ) public override {
        require(to != address(0), "ERC1155: transfer to the zero address");
        require(balanceOf(from, id) >= amount, "ERC1155: insufficient balance for transfer");
        require(
            msg.sender == from || isApprovedForAll(from, msg.sender),
            "ERC1155: caller is not approved to transfer"
        );
    
        string memory f = _formatPayload("from", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory t = _formatPayload("to", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(id)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));

        string memory req = _curlyBrace(
            _formatPayload("send", _curlyBrace(_join(f, ",", _join(t, ",", _join(tId, ",", amt)))))
        );
        _execute(bytes(req));
        if (to.code.length > 0) {
            require(
                IERC1155Receiver(to).onERC1155Received(
                    msg.sender,
                    from,
                    id,
                    amount,
                    data
                ) == IERC1155Receiver.onERC1155Received.selector,
                "unsafe transfer"
            );
        }
    }
