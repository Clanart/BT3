### Title
Quadratic Lagrange interpolation on attacker-controlled threshold parameters enables CPU denial of service in `ThresholdKeys::read` / `ThresholdKeys::new` — (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is algorithmic-complexity denial of service: a small attacker-controlled input triggers superlinear computation. Serai's DKG crate exhibits the same class in `ThresholdKeys::new`, which computes the group key via Lagrange interpolation with cost O(t²) in field operations, where `t` is a `u16` supplied by untrusted bytes in `ThresholdKeys::read`. A crafted serialized `ThresholdKeys` blob forces billions of field multiplications and tens of thousands of field inversions before any validation-dependent early-exit can occur.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses `t`, `n`, `i` directly from the byte stream as `u16` values, then calls `ThresholdKeys::new`. `ThresholdParams::new` (lib.rs:166-179) only checks `t <= n <= 65535`. Inside `ThresholdKeys::new` (lib.rs:376-378):

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

`interpolation_factor` for `Interpolation::Lagrange` (lib.rs:229-247) iterates over all of `included` performing a field multiplication for numerator and denominator per element, plus a field inversion per call. So `new` performs `t` calls each costing O(t) field multiplications plus one inversion — total O(t²) multiplications and O(t) inversions, plus `t` point multiplications.

With `t = n = 65535` (all valid per `ThresholdParams::new`), an input of roughly `n * 32` bytes (~4 MB) of points/scalars triggers ~4.3·10⁹ field multiplications and 65535 modular inversions — a quadratic blowup in computation relative to input size, the exact shape of the ReDoS class (small input → superlinear CPU burn).

The same O(|included|²) factorization appears in `ThresholdKeys::view` (lib.rs:494-507) where `interpolation_factor` is invoked once per included signer, and `included` is populated from the attacker-influenced preprocess map in `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:290-312), bounded only by `n`.

### Impact Explanation
An unprivileged party that can cause a node to deserialize a `ThresholdKeys` blob (e.g., during DKG re-sharing, key recovery, or any protocol step that feeds peer-supplied bytes into `ThresholdKeys::read`) can burn CPU quadratic in `t`/`n`. Since `t` and `n` are unrestricted up to 65535, a ~4 MB payload can occupy a CPU core for orders of magnitude longer than the payload size suggests, stalling signing/verification pipelines — an availability attack matching the advisory's `A:H` impact.

### Likelihood Explanation
`ThresholdKeys::read` is a listed reachable deserialization path in scope. The quadratic loop is unconditional once `t <= n` is satisfied; no invalid-input rejection precedes the interpolation. The only mitigating factor is that the expensive path requires the reader to actually reach `ThresholdKeys::new`, and deployments may impose external limits on `n` before deserialization — but the library itself enforces none.

### Recommendation
Cap `t`/`n` to a protocol-meaningful bound (e.g., a few hundred) inside `ThresholdParams::new` or `ThresholdKeys::read` before any O(t²) work. Alternatively, compute the group key incrementally or reject `Constant`/`Lagrange` interpolation sizes above the bound at the deserialization boundary so attacker-controlled bytes cannot dictate quadratic work.

### Proof of Concept
```rust
// Craft a ThresholdKeys blob with t = n = u16::MAX.
// Header: C::ID, then t = 65535, n = 65535, i = 1,
// interpolation = Lagrange (0x01), one scalar, then 65535 point encodings.
let mut buf = vec![];
buf.extend(&(Ed25519::ID.len() as u32).to_le_bytes());
buf.extend(Ed25519::ID);
buf.extend(&65535u16.to_le_bytes()); // t
buf.extend(&65535u16.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(1);                          // Lagrange
buf.extend(Ed25519::F::ONE.to_repr());
for _ in 0 .. 65535 { buf.extend(Ed25519::generator().to_bytes()); }
// ~4 MB input -> ~4.3e9 field muls + 65535 inversions inside ThresholdKeys::new
let _ = ThresholdKeys::<Ed25519>::read(&mut &buf[..]);
```
Each of the 65535 `interpolation_factor` calls at lib.rs:229-247 loops over all 65535 elements, yielding quadratic work per lib.rs:376-378 before any meaningful bound is applied.
