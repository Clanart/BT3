### Title
Assertion-failure DoS: identity points parsed by `ThresholdKeys::read` / sign paths panic in Bitcoin BIP-340 `Hram` - ([File: networks/bitcoin/src/crypto.rs])

### Summary
CVE-2016-7540 is an assertion-failure denial of service reachable by feeding crafted input to a library routine. The Serai analog is a panic on the point at infinity inside the BIP-340 challenge routine `Hram::hram` and its helpers `x()`/`x_only()`, reachable when the group key `A` or the aggregate nonce `R` supplied to `Schnorr::verify`/`sign_share` is the identity point. Identity-carrying verification shares can enter through `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), which deserializes shares with `Ciphersuite::read_G` — a parser that explicitly accepts identity encodings — instead of the identity-rejecting `Curve::read_G`.

### Finding Description
- `x()` calls `key.to_encoded_point(true)` and then `encoded.x().expect("point at infinity")`, panicking on the identity point (`networks/bitcoin/src/crypto.rs:13-16`).
- `x_only()` similarly `expect`s and panics on infinity (`crypto.rs:21-23`).
- `Hram::hram` feeds both `R` and `A` through `x()` (`crypto.rs:59-67`), and its own doc comment states: "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`).
- `Schnorr::verify` invokes the inner FROST verify, which computes `hram(R, group_key, msg)`; a panic there aborts the calling thread during threshold signature completion (`crypto.rs:139-149`).
- On the input side, `ThresholdKeys::read` deserializes `verification_shares` for all `n` participants with `<C as Ciphersuite>::read_G` (`crypto/dkg/src/lib.rs:620-623`). Unlike `Curve::read_G`, which rejects identity (`crypto/frost/src/curve/mod.rs:125-131`), `Ciphersuite::read_G` accepts any canonical encoding, including the identity (`crypto/ciphersuite/src/lib.rs:91-101`). Interpolating verification shares containing identity points can yield an identity `group_key` inside `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:625-631`).
- A second reachability concern is `BatchVerifier::verify_with_vartime_blame`, which `unwrap`s `blame_vartime()` (`crypto/multiexp/src/batch.rs:131`); this is safe only under the invariant that a failed batch implies a locatable culprit, but combined with first-weight-`ONE` weighting in `queue` (`batch.rs:46-48`) it deserves review.

### Impact Explanation
Any code path that calls `Schnorr::verify` / `verify_share` / `sign_share` with an identity group key or identity aggregate nonce aborts via `expect`/`panic` rather than returning an error. If key material or verification shares are ever deserialized from bytes influenced by an unprivileged party (e.g., `ThresholdKeys::read`, DKG output derived from other participants' `Commitments::read` contributions), that party can crash the signer/verifier process. This matches the CVE class: assertion failure on untrusted input, medium-severity availability loss of the signing/verification service.

### Likelihood Explanation
The panic requires `R` or `A` to be the point at infinity. `A` (group key) can become identity if `ThresholdKeys::new` accepts verification shares interpolating to identity — the `Ciphersuite::read_G` parser does not prevent this, and I could not confirm a non-identity check inside `ThresholdKeys::new`. For `R`, each nonce commitment is forced non-identity by `Curve::read_G` in `read_preprocess`, but the weighted sum `Σ ρᵢ(Dᵢ + Eᵢ)` can still be identity; forcing this adaptively is difficult because `ρ` binds the attacker's commitments, making the `R` path impractical. The `A` path via deserialized key material is the realistic vector, and likelihood is moderate because the panic is acknowledged in the API contract ("MAY panic" for a caller that doesn't guard), which integrators must currently discover rather than handle as an error.

### Recommendation
- In `ThresholdKeys::read` and `ThresholdKeys::new`, reject identity verification shares and an identity interpolated `group_key` (use `Curve::read_G` semantics or an explicit `is_identity` check), returning `io::Error` instead of constructing a key that will panic downstream.
- In `Hram::hram` / `x()` / `x_only()`, return a `Result` or define a documented non-panicking behavior (e.g., reject the signature/share) rather than `expect("point at infinity")`.
- Ensure `Schnorr::verify` returns `None` for identity `R`/`A` instead of panicking.

### Proof of Concept
1. Serialize a `ThresholdKeys<Secp256k1>` blob where the `verification_shares` for `l = 1..=n` are chosen so the Lagrange/`Constant` interpolation of shares at indexes `1..=t` yields the identity point (e.g., all shares identity, which `Ciphersuite::read_G` accepts canonically).
2. `ThresholdKeys::read(&mut bytes)` succeeds, producing a key whose `group_key()` is identity.
3. Call `bitcoin_serai::crypto::Schnorr::new()` machine signing/verify with that key; `IetfSchnorr` computes `hram(R, group_key, msg)` → `x(A)` → `encoded.x().expect("point at infinity")` panics, aborting the process — an assertion-failure DoS driven entirely by attacker-supplied bytes, mirroring the RGF-coder assertion in CVE-2016-7540.

Relevant code: `x`/`x_only`/`Hram::hram`/`Schnorr::verify` at `networks/bitcoin/src/crypto.rs:13-23, 59-73, 139-149`; identity-accepting `read_G` at `crypto/ciphersuite/src/lib.rs:91-101`; identity-accepting share parse at `crypto/dkg/src/lib.rs:620-623`; identity-rejecting contrast at `crypto/frost/src/curve/mod.rs:125-131`.

Caveat: I could not verify whether `ThresholdKeys::new` already validates that the interpolated `group_key` is non-identity (that portion of `crypto/dkg/src/lib.rs` was not surfaced by the index). If it does, the `A` path is blocked and only the negligible `R`-sum-to-identity panic remains, which is documented behavior — in that case this would reduce to a no-finding.
