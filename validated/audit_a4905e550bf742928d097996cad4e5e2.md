## Finding: Escrow settlement uses pre-fee order amounts against fee-reduced escrow records, causing a permanent revert-lock of escrowed funds

### Title
Refund/Redeem withdrawal amount mismatch vs. escrowed (fee-reduced) record causes permanent fund lock via underflow revert - (File: evm/tron/contracts/apps/IntentGatewayV2.sol, evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`IntentGatewayV2.placeOrder` escrows and records the **protocol-fee-reduced** amount per token, but the cancellation/refund code paths build the `WithdrawalRequest` using the **original, unreduced** `order.inputs` amount. `withdraw()` then attempts to subtract this larger amount from the smaller recorded value, which underflows and reverts under Solidity 0.8 checked arithmetic — permanently blocking the user from ever reclaiming their escrowed tokens. This is the direct structural analog of the zkSync "Fragile Deposit Limit" bug: a value used to clear/rewind an accounting record does not match what was actually recorded, so the legitimate claim path fails forever.

### Finding Description
In `placeOrder`, when a destination-specific or default protocol fee is configured (`protocolFeeBps > 0`), the amount actually pulled into escrow and recorded per `(commitment, token)` is the **reduced** amount, not the original order amount: [1](#0-0) [2](#0-1) [3](#0-2) 

`_orders[commitment][token]` therefore holds `reducedInputs[i].amount`, strictly less than `order.inputs[i].amount` whenever a fee applies.

The same-chain cancellation path, however, builds the withdrawal request from the **original, unreduced** `order.inputs`, not `reducedInputs`: [4](#0-3) 

The cross-chain destination-side cancellation path in the main EVM implementation does the same — it dispatches a `RefundEscrow` message whose `WithdrawalRequest.tokens` is `order.inputs` (unreduced): [5](#0-4) 

`withdraw()` on the source chain then validates only that a record *exists* (`== 0` check), not that the requested `amount` is `<=` the recorded value, and unconditionally subtracts the (too-large) `amount` from the record: [6](#0-5) 

Because Solidity 0.8.24 uses checked arithmetic outside `unchecked` blocks, `_orders[body.commitment][token] -= amount` reverts on underflow whenever `amount > _orders[body.commitment][token]` — exactly the "attempt to rewind a smaller-than-claimed record" pattern from the original report. Unlike the original bug (missing record entirely), here the record exists but is smaller than the claim amount, producing the identical symptom: the withdrawal transaction can never succeed.

### Impact Explanation
Any order placed while a nonzero protocol fee (`_params.protocolFeeBps` or `_destinationProtocolFees[dest]`) is configured, when cancelled, hits this mismatch and its escrow becomes permanently unrecoverable — the tokens are locked in the `IntentGatewayV2` contract forever, satisfying "loss of funds" under the bounty's impact gate. This is triggerable by any ordinary user (the order creator) simply by calling the public `cancelOrder` entrypoint; it requires no malicious relayer, prover, or admin action.

### Likelihood Explanation
Likelihood is high for any deployment where protocol fees are enabled (a normal, intended configuration, not an edge/testnet-only case): every cancellation of a fee-bearing order deterministically reverts, since the mismatch is baked into the code paths, not a race condition or rare timing window.

### Recommendation
Build all `WithdrawalRequest.tokens` amounts from the same `reducedInputs`/escrowed record used at `placeOrder` time (not the raw `order.inputs`), or have `withdraw()` clamp/read the amount directly from `_orders[commitment][token]` instead of trusting the amount embedded in the incoming request body. Additionally, `withdraw()`'s existence check should be `amount > _orders[...][token]` (insufficient-balance guard) rather than `== 0`, mirroring the original report's suggested fix of clearing/bounding the record instead of reverting on a raw subtraction.

### Proof of Concept
1. Governance/admin sets `_params.protocolFeeBps = 100` (1%) via `UpdateParams`.
2. User calls `placeOrder` with `order.inputs = [{token: USDC, amount: 1000e6}]`. `reducedInputs[0].amount = 990e6` is escrowed and recorded: `_orders[commitment][USDC] = 990e6`.
3. Order goes unfilled; user calls `cancelOrder` (same-chain path) before/at the point cancellation is triggered.
4. `withdraw()` is invoked with `body.tokens[0].amount = 1000e6` (from unreduced `order.inputs`), while `_orders[commitment][USDC] == 990e6`.
5. Token transfer of `1000e6` may succeed (funded from the contract's pooled token balance across multiple orders), but the subsequent `_orders[commitment][USDC] -= 1000e6` underflows and reverts, rolling back the entire transaction.
6. The user can never successfully cancel/withdraw this order — the escrowed `990e6 USDC` is permanently stuck in the contract.

        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

                if (!success) revert TransferFailed();
            }
