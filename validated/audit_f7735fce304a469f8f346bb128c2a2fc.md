### Title
`ThresholdKeys::read` enables quadratic Lagrange interpolation denial of service - (File: crypto/dkg/src/lib.rs)

### Summary
An attacker-controlled serialized `ThresholdKeys` with `t = n = 65535` and `Interpolation::Lagrange` causes `ThresholdKeys::read` to perform billions of field operations while deriving the group key. The input itself is only a few megabytes for 32-byte field/point encodings, creating a substantial CPU amplification from public bytes. [1](#0-0) 

### Finding Description
`ThresholdKeys::read` accepts attacker-supplied `t`, `n`, participant index, interpolation mode, secret share, and `n` verification shares without imposing a practical threshold bound. [2](#0-1) 

After deserialization, it calls `ThresholdKeys::new`. [3](#0-2)  For Lagrange interpolation, `ThresholdKeys::new` computes every participant’s interpolation factor over the set `1..=t`. [4](#0-3)  Each factor calculation loops over all `t` included participants and performs an inversion. [5](#0-4) 

With the maximum encodable `t = n = 65535`, deserialization completes after reading about `n` group elements, but initialization then evaluates roughly `65535²` field operations and `65535` inversions. [6](#0-5) [4](#0-3) [5](#0-4) 

### Impact Explanation
A service that accepts serialized threshold keys can be forced into prolonged CPU consumption by a syntactically valid input of only a few megabytes. Repeated submissions can exhaust CPU capacity and delay unrelated signing or key-processing work. [7](#0-6) [4](#0-3) 

### Likelihood Explanation
The trigger only requires control of bytes passed to `ThresholdKeys::read`; no malformed scalar, invalid point, leaked key, malicious validator, or threshold collusion is needed. `t = n = i = 65535`-bounded parameters pass the explicit `t <= n` and participant checks. [2](#0-1) [8](#0-7) 

### Recommendation
Bound accepted `t`/`n` to the deployment’s supported maximum before allocating or reading participant-dependent data. Preferably compute the group key with an incremental product for Lagrange coefficients rather than independently recalculating each participant’s factor in `O(t²)` time. [4](#0-3) [5](#0-4) 

### Proof of Concept
Construct a Lagrange `ThresholdKeys` encoding with `t = n = 65535`, `i = 1`, one canonical secret scalar, and `65535` canonical verification-share encodings. For a 32-byte group encoding, the participant-dependent payload is approximately 2 MiB, while the read path performs billions of field multiplications.

```rust
use std::io;
use frost::{Participant, ThresholdKeys};
use ciphersuite::Ciphersuite;

fn malicious_threshold_keys<C: Ciphersuite>() -> io::Result<ThresholdKeys<C>> {
    let mut serialized = Vec::new();

    serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
    serialized.extend(C::ID);

    serialized.extend(u16::MAX.to_le_bytes()); // t = 65535
    serialized.extend(u16::MAX.to_le_bytes()); // n = 65535
    serialized.extend(1u16.to_le_bytes());     // i = 1
    serialized.push(1);                        // Interpolation::Lagrange

    serialized.extend(C::F::ONE.to_repr().as_ref());

    let verification_share = C::generator().to_bytes();
    for _ in 0 .. u16::MAX {
        serialized.extend(verification_share.as_ref());
    }

    ThresholdKeys::<C>::read(&mut serialized.as_slice())
}
```

The call reaches the quadratic group-key derivation at `ThresholdKeys::new` after successfully reading `65535` verification shares. [9](#0-8)
