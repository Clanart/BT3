## Finding: Unbounded Python recursion in outer-puzzle driver matching triggers a wallet DoS via a crafted Offer file

The `justhtml` report is about attacker-controlled selector strings causing unbounded CPU/recursion during structural matching (deeply nested pseudo-classes, cyclic graphs). The `chia-blockchain` analog is the outer-puzzle driver matching system used to parse `Offer` files and coin spends: it recursively matches curried puzzle layers with no depth limit, and the recursion cost is *not* metered by CLVM cost accounting (it's plain Python pattern matching on the uncurried CLVM tree, done before any CLVM execution).

### Title
Unbounded recursive outer-puzzle matching in Offer parsing enables a spend-triggered wallet DoS - (File: chia/wallet/outer_puzzles.py)

### Summary
`match_puzzle()` and each outer-puzzle driver's `match()` method recurse into `self._match(inner_puzzle)` for every curried layer of a puzzle reveal, and `PuzzleInfo.also()`/`check_type()` mirror this recursion on the resulting driver dictionary. None of these functions bound recursion depth. Because `Program.uncurry()` is a structural pattern match (not a CLVM execution), an attacker can construct a coin spend / Offer whose puzzle reveal has thousands of nested curry layers cheaply, well under any CLVM cost limit, and cause unbounded Python-stack recursion when a wallet parses it.

### Finding Description
`match_puzzle()` loops over all registered drivers and returns the first non-`None` match: [1](#0-0) 

Each driver in `driver_lookup` is constructed with `function_args = (match_puzzle, ...)`, so a driver's `self._match` **is** `match_puzzle` itself, creating mutual recursion between `match_puzzle` and driver `.match()` methods: [2](#0-1) 

For example, `SingletonOuterPuzzle.match()` unconditionally recurses into `self._match(UnknownPuzzle(known_program=inner_puzzle))` for the inner puzzle of every singleton layer it sees: [3](#0-2) 

`CROuterPuzzle.match()` does the same for CR (credential-restricted) layers: [4](#0-3) 

The resulting `PuzzleInfo` tree is itself walked recursively without a depth guard via `also()`/`check_type()`: [5](#0-4) 

Crucially, `Program.uncurry()` performs no CLVM execution and is not charged against `max_tx_clvm_cost`/`MAX_BLOCK_COST_CLVM` — it is a cheap structural pattern match on `(a (q . MOD) ENV)` shapes. An attacker can therefore nest an arbitrary number of singleton/CR/metadata/ownership curry layers (each adding only a small, fixed number of bytes) inside a single coin's puzzle reveal, producing a deeply nested tree that is cheap in CLVM-cost terms but drives one Python stack frame of recursion per layer in `match_puzzle`.

This matching path is reached by parsing any untrusted `Offer`:
- `Offer._get_offered_coins()` calls `match_puzzle(parent_puzzle)` for every coin spend in the bundle: [6](#0-5) 
- `Offer.from_spend_bundle()` (invoked from `Offer.from_bytes()`/`Offer.from_bech32()`, used by `TakeOffer` and offer-summary RPCs) calls `match_puzzle` per coin spend embedded in the offer bytes: [7](#0-6) 

### Impact Explanation
A wallet user (or offer counterparty) receiving a maliciously crafted `.offer` file / offer bech32 string and calling standard flows such as `get_offer_summary`, `TakeOffer`, or previewing an offer in the GUI can trigger deep, unbounded Python recursion while the wallet parses the embedded coin spends. This can raise `RecursionError` or, depending on interpreter stack limits, crash the wallet/RPC process outright — a spend-triggered halt of wallet transaction processing that requires no signature and no on-chain broadcast, only that the victim process the offer bytes.

### Likelihood Explanation
Medium. Constructing nested singleton/CR/metadata layers is straightforward CLVM construction (curry a mod around another mod repeatedly) and does not require a valid signature, a broadcastable spend bundle, or exceeding any CLVM cost limit, since `uncurry()` matching is unmetered. The main uncertainty is exactly how many layers are needed to exhaust the interpreter's recursion budget in a given deployment, but this is a fixed, attacker-computable constant, not a variable defense.

### Recommendation
- Add an explicit maximum recursion/nesting depth to `match_puzzle()`/driver `.match()` chains and to `PuzzleInfo.also()`/`check_type()`, rejecting or short-circuiting once exceeded.
- Convert the recursive matching loop into an iterative one (mirroring the non-recursive `sha256_treehash()` pattern already used elsewhere in this codebase) so puzzle depth cannot exhaust the Python call stack: [8](#0-7) 
- Bound the number of curry layers considered when parsing untrusted `Offer` bytes before invoking `match_puzzle`.

### Proof of Concept
1. Build an innermost puzzle `P0` (e.g., `(q . 1)`).
2. Repeatedly wrap it N times (e.g., N = 5,000) alternating `SINGLETON_MOD.curry(SINGLETON_STRUCT, Pi)` and a CR-layer curry, producing `PN`.
3. Construct a `CoinSpend` with `puzzle_reveal = PN` and embed it as an offered coin's parent spend inside an `Offer`/`WalletSpendBundle` (no valid signature required to merely parse/summarize the offer).
4. Serialize via `Offer.to_bech32()` (or hand-construct the equivalent bytes) and send it to a victim wallet.
5. Victim calls `get_offer_summary`/`TakeOffer`/GUI offer preview → `Offer.from_bech32()` → `Offer.from_spend_bundle()` → `match_puzzle(PN)` recurses N times through `match_puzzle` ↔ `SingletonOuterPuzzle.match`/`CROuterPuzzle.match`, exceeding Python's default recursion limit and raising `RecursionError`, halting the offer-processing code path.

def sha256_treehash(sexp: CLVMStorage, precalculated: set[bytes32] | None = None) -> bytes32:
    """
    Hash values in `precalculated` are presumed to have been hashed already.
    """

    if precalculated is None:
        precalculated = set()

    def handle_sexp(sexp_stack: ValueStackType, op_stack: OpStackType, precalculated: set[bytes32]) -> None:
        # just trusting it is right, otherwise we get an attribute error
        sexp: SExp = sexp_stack.pop()  # type: ignore[assignment]
        if sexp.pair:
            p0, p1 = sexp.pair
            sexp_stack.append(p0)
            sexp_stack.append(p1)
            op_stack.append(handle_pair)
            op_stack.append(handle_sexp)
            op_stack.append(roll)
            op_stack.append(handle_sexp)
        else:
            # not a pair, so an atom
            atom: bytes = sexp.atom  # type: ignore[assignment]
            if atom in precalculated:
                r = atom
            else:
                r = std_hash(b"\1" + atom)
            sexp_stack.append(r)

    def handle_pair(sexp_stack: ValueStackType, op_stack: OpStackType, precalculated: set[bytes32]) -> None:
        # just trusting it is right, otherwise we get a type error
        p0: bytes = sexp_stack.pop()  # type: ignore[assignment]
        p1: bytes = sexp_stack.pop()  # type: ignore[assignment]
        sexp_stack.append(std_hash(b"\2" + p0 + p1))

    def roll(sexp_stack: ValueStackType, op_stack: OpStackType, precalculated: set[bytes32]) -> None:
        p0 = sexp_stack.pop()
        p1 = sexp_stack.pop()
        sexp_stack.append(p0)
        sexp_stack.append(p1)

    sexp_stack: ValueStackType = [sexp]
    op_stack: list[Op] = [handle_sexp]
    while len(op_stack) > 0:
        op = op_stack.pop()
        op(sexp_stack, op_stack, precalculated)
    # just trusting it is right, otherwise we get some error, probably
    result: bytes = sexp_stack[0]  # type: ignore[assignment]
    return bytes32(result)
