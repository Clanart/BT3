### Title
Attacker-controlled `payments` script_pubkey is never validated for standardness/spendability, so a single unreceivable output makes the entire batched multisig transaction unbroadcastable (or provably burns funds) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` validates only the *amount* of each payment (`>= DUST`) and copies each payment's `ScriptBuf` verbatim into the transaction outputs. There is no check that the destination script is a standard, spendable output type. This is the direct analog of the PartyDAO finding: an irreversible/committed spend depends on a recipient that cannot receive, and the failure of that one output dooms the entire transaction carrying all other payments and inputs.

### Finding Description
`SignableTransaction::new` iterates `payments: &[(ScriptBuf, u64)]` and only rejects amounts below `DUST` (546 sats):

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

The `ScriptBuf` is never inspected. It is then embedded directly:

```rust
let mut tx_outs = payments
  .iter()
  .map(|payment| TxOut { value: Amount::from_sat(payment.1), script_pubkey: payment.0.clone() })
  .collect::<Vec<_>>();
```

The only global checks afterwards are `MAX_STANDARD_TX_WEIGHT` and the fee-rate floor — neither catches a non-standard or provably unspendable script_pubkey.

These payment scripts originate from untrusted user input (the external `address` of an `OutInstruction` / refund `origin`), converted into `ScriptBuf` by the processor (`processor/src/networks/bitcoin.rs::make_signable_transaction` maps `payment.address.clone().into()` with no further validation). Two failure modes result:

1. **Non-standard script** (e.g., an unrecognized bare script, malformed witness program): the signed transaction fails Bitcoin Core's `IsStandardTx` policy and is rejected by every relay. Because plans batch multiple payments and multiple inputs, one attacker's bad output stalls the *entire* transaction — every other user's payment in the plan and all consumed UTXOs are stuck behind a transaction that can never confirm. This mirrors the original bug: the spend cannot complete because one recipient "cannot receive."

2. **Provably unspendable but standard script** (e.g., a value-bearing `OP_RETURN` script or a burn script): the transaction *does* broadcast, but the sats sent to that output are permanently destroyed — funds reported as paid that no one can ever spend.

### Impact Explanation
- Griefing: an unprivileged user submits an out/refund instruction whose address encodes a non-standard script. The resulting `SignableTransaction` is signed by the whole FROST multisig and can never enter the mempool, indefinitely blocking all payments bundled in the same plan and pinning the plan's inputs.
- Fund loss: a payment to an unspendable-but-relayable script burns the value outright — the network records the output as paid while it is unspendable, analogous to the crowdfund fees/ETH being irrecoverable.

### Likelihood Explanation
Medium. No secret knowledge, collusion, or validator compromise is required — only a crafted `ScriptBuf` supplied through the normal public path for specifying destination addresses. The constructor performs zero script validation, so the attack succeeds deterministically whenever such an instruction is scheduled into a plan.

### Recommendation
Validate each payment `ScriptBuf` in `SignableTransaction::new` before constructing the transaction: reject non-standard output types using `bitcoin::policy`/script classification (accept only recognized standard types — P2PKH, P2SH, P2WPKH, P2WSH, P2TR — or explicitly reject `script.is_unspendable()`/nonstandard witness programs), and/or drop only the offending payment rather than failing the whole transaction, mirroring the recommendation to isolate the faulty transfer from the state transition.

### Proof of Concept
```rust
use bitcoin::script::{ScriptBuf, Builder};
use bitcoin::opcodes::all::*;

// A non-standard, meaningless script_pubkey — accepted by SignableTransaction::new
let bad_script = ScriptBuf::from_bytes(vec![0xff, 0xfe, 0xfd; 100]);

// Any valid input set works; payments carry a >= dust amount
let payments = vec![(bad_script, 10_000u64)];
let tx = SignableTransaction::new(inputs, &payments, change, None, fee_per_vbyte);
// tx is Ok(...): the transaction is built and signed by the multisig,
// but every Bitcoin Core relay rejects it as non-standard (bad-tx-nonstandard),
// permanently stalling all payments and inputs in the same plan.
```

Alternatively, `ScriptBuf::new_op_return(...)` with a non-zero amount produces a broadcastable transaction whose payment output is provably unspendable, silently burning the funds.
