### Title
Concurrent auction Stop() and SubmitBid RPC causes panic via send-on-closed-channel in `BidPool` - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool.AddBid` (reachable from the public `auction_submitBid` RPC endpoint) checks the `running` flag and then, after taking a lock and inserting the bid, unconditionally sends the bid on `bp.newBidCh`. `BidPool.stop()` (invoked from `AuctionModule.Stop()`, which is called during chain-rewind restarts per `kaiax/README.md`) concurrently flips `running` to 0, clears the pool, and then closes `bp.newBidCh`/`bp.bidMsgCh`. There is a check-then-act race: `AddBid` can pass its “running” check before `stop()` runs, then proceed to send on the channel after `stop()` has already closed it, causing a `send on closed channel` panic that crashes the whole node process.

### Finding Description
`AddBid` performs a non-atomic sequence of operations without holding the same synchronization primitive that guards channel closing: [1](#0-0) 

`stop()` closes the channels that `AddBid` writes to, and does so without any handshake with in-flight `AddBid` calls other than the best-effort atomic `running` flag, which `AddBid` only checks once at the very start: [2](#0-1) 

Because `AddBid`'s `atomic.LoadUint32(&bp.running)` check at line 253 and its later `bp.newBidCh <- bid` send at line 271 are not atomic with respect to each other, a goroutine can observe `running == 1`, proceed through `validateBid`/`insertBid` (which take time and involve signature verification), and then attempt to send to `newBidCh` exactly as another goroutine executing `stop()` sets `running = 0` and closes `newBidCh`. This causes a panic in Go when sending to a closed channel, crashing the process. `stop()` is documented to be invoked when the auction module is restarted after a chain rewind: [3](#0-2) 
and concretely wired to `AuctionModule.Stop()` → `bidPool.stop()`: [4](#0-3) 

The RPC entrypoint that lets an unprivileged external caller (an auction bidder) trigger `AddBid` is `AuctionAPI.SubmitBid`: [5](#0-4) 

This mirrors the hns3 bug class (CVE-2024-39507): a fast-path check ("is roce registered?" / "is running?") is not synchronized with the teardown path ("roce uninit" / "stop() closing channels"), so a legitimate concurrent operation (link status notify / bid submission) races the teardown and dereferences/uses a resource that has just been torn down, crashing the process.

### Impact Explanation
A crash of the auction/bid-pool goroutine set is a process-wide panic in Go (an unrecovered panic on an unbuffered/normal channel send crashes the entire node), not just the module. Any external actor able to call the `auction_submitBid` RPC (even though the API is marked `Public: false`, it is reachable to any client with access to that RPC namespace, e.g. auctioneers/bidders using the intended feature) can send bids concurrently with a chain-rewind event (`SetHead`) that triggers `AuctionModule.Stop()`/`Start()`, potentially crashing a CN node. This is a denial-of-service against consensus/producing nodes, which is a High severity impact given repeated crash-restart cycles can degrade or bring down block production.

### Likelihood Explanation
The race window requires a bid submission to be in-flight (past the `running` check, inside `insertBid`) at the exact moment `Stop()`/`stop()` executes. `Stop()`/`Start()` are invoked during chain rewinds (`SetHead`), which, while not attacker-triggerable directly, can occur during normal chain reorgs on a CN, and an active bidder submitting bids at high frequency (as auction bidders are expected to do, given the 300 bids/sec/peer rate limiter) increases the probability of hitting this window. The likelihood is Medium: it requires a specific timing coincidence with a node-internal event, but is not implausible under normal auction module operation combined with routine reorgs.

### Recommendation
Synchronize `AddBid`'s send to `newBidCh` with `stop()`'s channel close, e.g., by guarding the channel send with the same `bidMu`/`running` check performed under a lock (re-check `running` right before sending, using `select` with a `default`/`done` case), or by using a `sync.RWMutex` held across both the running-check and the channel send in `AddBid`, paired with `stop()` acquiring the write-lock before closing channels. Alternatively, replace closing `newBidCh`/`bidMsgCh` with a separate `done`/`quit` channel signal and never close channels that producers write to, having `AddBid` select on `case bp.newBidCh <- bid: / case <-bp.quit: return`.

### Proof of Concept
Not independently reproducible without running the full node/RPC stack in this environment. Conceptually:
1. Start an auction module with `Start()`.
2. Concurrently loop calling `AuctionAPI.SubmitBid` with valid bids (goroutine A) while calling `AuctionModule.Stop()` (goroutine B) repeatedly, simulating repeated `SetHead` rewinds.
3. Because `AddBid` (kaiax/auction/impl/bid_pool.go:252-274) checks `running` once and then sends to `newBidCh` after variable-length lock-protected work, while `stop()` (kaiax/auction/impl/bid_pool.go:127-138) can close `newBidCh` in between, a `panic: send on closed channel` is expected under sufficient iteration/timing, matching the "concurrent scenario kernel/process crash" bug class of CVE-2024-39507.

```go
func (bp *BidPool) stop() {
	// Stop the bid pool.
	atomic.CompareAndSwapUint32(&bp.running, 1, 0)
	bp.clearBidPool()

	// Only close channels if they haven't been closed before
	if atomic.CompareAndSwapUint32(&bp.stopped, 0, 1) {
		close(bp.bidMsgCh)
		close(bp.newBidCh)
	}
	bp.wg.Wait()
}
```

```go
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}
```

```go
func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}
```
