### Title
Unauthenticated payout OP_RETURN lets anyone attribute a self-funded withdrawal to an operator who never fronted it, draining the vault via that operator's reimbursement - ([File: core/src/database/verifier.rs])

### Summary
`payout_payer_operator_xonly_pk` is populated purely from the payout transaction's OP_RETURN output, which is *not* covered by the payout's `SinglePlusAnyoneCanPay` signature and can therefore be set to any operator's key by whoever broadcasts the payout tx. `get_first_unhandled_payout_by_operator_xonly_pk` and `is_kickoff_malicious` both trust this unauthenticated value, so any unprivileged bridge user can make a withdrawal that credits operator X without X ever funding it, causing X's own automated `PayoutCheckerTask` to claim a real reimbursement from the vault.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk(idx) == the operator that actually broadcast/funded the payout for withdrawal idx`.

`create_payout_txhandler` builds the payout tx with the user's withdrawal-dust input signed with `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . `SinglePlusAnyoneCanPay` only commits to the input being spent and the output at the *same index* (output 0, the user payout). The OP_RETURN output that carries the operator's x-only pubkey is output index 2 and is completely outside the signed message — anyone in possession of the user's dust-UTXO signature (which is exactly what the withdrawer/attacker supplies to `Operator::withdraw`) can build and broadcast their own payout transaction, funding the real payout amount from their own wallet via `fund_raw_transaction`, while attaching an arbitrary OP_RETURN xonly-pubkey [2](#0-1) .

When the payout confirms, `update_finalized_payouts` blindly parses this OP_RETURN and writes it into the `withdrawals` table with no check that the named operator broadcast, signed, or funded any part of the transaction: [3](#0-2) .

Operator X's own `PayoutCheckerTask` polls `get_first_unhandled_payout_by_operator_xonly_pk(X)` — the query in question, `WHERE payout_payer_operator_xonly_pk = $1 ORDER BY w.idx ASC LIMIT 1` — with no constraint tying the row to a kickoff or funding proof for X [4](#0-3) . Whenever it finds such a row it automatically calls `handle_finalized_payout`, which only checks that X has an *unused, signed kickoff connector* for that deposit — not that X funded the payout — and proceeds to broadcast a kickoff to start reimbursement: [5](#0-4) .

The only later cross-check, `is_kickoff_malicious`, re-reads the same forged `operator_xonly_pk` from the DB and compares it against `kickoff_data.operator_xonly_pk` (the actual kickoff sender) — since both are X, the check passes and the kickoff is accepted as legitimate: [6](#0-5) . Nothing in this path verifies that the funds paid to the user actually came from operator X's wallet or that X ever broadcast the transaction.

### Impact Explanation
An attacker who withdraws twice — once genuinely fronted by honest operator Y, once self-funded by the attacker themselves but with X's pubkey forged into the OP_RETURN — causes X's own automation to detect a second "unhandled payout" and issue a kickoff/reimbursement for a withdrawal X never funded. The reimburse transaction pays X the full deposited `bridge_amount` from the vault's move-to-vault UTXO for that deposit [7](#0-6) , i.e. real bridge value leaves the vault to X with no matching payment fronted by X — matching the Critical category "an operator reimbursed for a payout it never funded, draining vault value with no matching fronted withdrawal." This is repeatable across every withdrawal index and every operator xonly pubkey known to the attacker (all operator keys are public).

### Likelihood Explanation
No privileged role is required: the attacker only needs to be a bridge user who deposits, calls Citrea's `withdraw`, supplies their own signature over their own dust UTXO, and broadcasts a raw Bitcoin transaction (adding their own funding inputs and a forged OP_RETURN) — all actions explicitly listed as available to an unprivileged attacker. Cost is limited to normal withdrawal fronting cost plus fees; no key compromise, majority hashrate, or insider access is needed. The forged OP_RETURN survives unmodified through `update_finalized_payouts` and `is_kickoff_malicious` because neither validates its authenticity.

### Recommendation
Do not derive the reimbursement-eligible operator solely from unauthenticated OP_RETURN bytes. Either (a) require the operator to co-sign the payout transaction (e.g., via an aggregated/N-of-N signature or an operator-specific script path) so the OP_RETURN/payer identity is cryptographically bound to the payout tx, or (b) bind reimbursement eligibility to proof that the operator's own known UTXO(s) funded the payout (e.g., verify the additional payout tx inputs are spendable only by that operator's registered key), rather than trusting `parse_op_return_data` output as sufficient attribution.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
