### Title
Truncated preprocess/share vectors cause out-of-bounds panic, permanently stalling a multisig spend — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class in the report — an accounting/validation gap that lets one participant's state make a later operation underflow and permanently block it — maps onto `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` in bitcoin-serai. Each participant's preprocess/share is deserialized as a bare `Vec<Preprocess>`/`Vec<SignatureShare>` via `read_preprocess`/`read_share`, and its length is never checked against the number of transaction inputs. `sign` then indexes `commitments[c]` for every input `c`, and `complete` calls `shares.remove(0)` on each participant's vector. A signer who supplies a truncated (or empty) vector causes an index-out-of-bounds / `remove(0)`-on-empty panic in honest validators' signing code, aborting the spend.

### Finding Description
`read_preprocess` collects `self.sigs.iter().map(|sig| sig.read_preprocess(reader))`, i.e. it reads however many bytes the peer sent into a `Vec` with no enforced relationship to `tx.input.len()` [1](#0-0) . In `sign`, the per-input commitment map is built by indexing `commitments[c]` for `c in 0..self.sigs.len()`; a short vector panics [2](#0-1) . The same gap exists in `complete`, which pops `shares.remove(0)` per input — an empty share vector panics [3](#0-2) .

### Impact Explanation
An unprivileged FROST participant (or anyone who can feed bytes to `read_preprocess`/`read_share` on a validator's machine, since these are raw `Read` deserializers of untrusted network data) submits a syntactically valid but too-short preprocess/share vector. Honest signers panic mid-signing instead of returning a `FrostError`, crashing the processor's signing task. Because the panic occurs inside `sign`/`complete` after preprocesses were already consumed, the multisig transaction cannot be produced in that session — analogous to the reference issue's "position that cannot be closed": UTXOs earmarked for the spend remain unspendable until out-of-band recovery, and a persistent adversary can repeat this every round to keep funds locked.

### Likelihood Explanation
Requires only that the attacker be a participant (or peer feeding data) in one signing session — no validator compromise, no external-system failure. The missing length check is unconditional, so the trigger is deterministic whenever a short vector is supplied. It does not steal funds or forge signatures; impact is a repeatable liveness DoS against a specific spend, matching Medium severity.

### Recommendation
Validate in `SignableTransaction`/`TransactionSignMachine` that every participant's `Preprocess`/`SignatureShare` vector length equals `self.tx.input.len()` (or at least `self.sigs.len()`) before indexing; return `FrostError`/identify the offending participant for blame instead of panicking. Prefer `get(c)`/`pop_front`-style access with explicit error mapping over direct indexing and `remove(0)`.

### Proof of Concept
```
// Attacker is participant i in a TransactionSignMachine for a TX with 2 inputs.
// Instead of sending Vec<Preprocess> of length 2, they send a Vec of length 1
// (or length 0 for shares in `complete`), serialized normally.
// Honest node's read_preprocess succeeds -> Ok(vec![p0]).
// sign() then does commitments[1] on that participant's map entry ->
// index out of bounds panic, aborting the session.
// Equivalently, a 0-length SignatureShare vec makes complete() panic at
// shares.remove(0) in networks/bitcoin/src/wallet/send.rs.
// No malformed bytes are needed: the vector deserializes cleanly; only the
// length is inconsistent with tx.input.len().
```
