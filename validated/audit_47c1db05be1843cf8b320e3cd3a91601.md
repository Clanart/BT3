### Title
Unbounded length-prefixed deserialization in `SchnorrAggregate::read` enables memory-exhaustion denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the Valine DoS (attacker-controlled input causing application outage), `SchnorrAggregate::read` trusts an attacker-supplied 32-bit element count and deserializes that many group elements into a `Vec` with no bound check, allowing unbounded memory growth / abort on untrusted bytes.

### Finding Description
`SchnorrAggregate::read` reads a little-endian `u32` from the reader and then loops `0 .. count` pushing the result of `C::read_G(reader)` into `Rs` with no limit on `count`: [1](#0-0) 

```rust
// crypto/schnorr/src/aggregate.rs
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

There is no sanity cap comparing `count` against remaining input length or a protocol maximum. The same unbounded-prefix pattern is avoided elsewhere only accidentally — e.g. `ThresholdKeys::read` bounds its vector allocations by a `u16` `n` it then validates through `ThresholdParams::new` [2](#0-1) , while `SchnorrAggregate::read` has no such bound (a `u32` max of 4,294,967,295 elements, ~137 GiB of encoded points for a 32-byte encoding).

### Impact Explanation
Any consumer that feeds untrusted bytes to `SchnorrAggregate::read` over a real `io::Read` (network stream, file, or length-delimited message channel where the reader keeps producing data) lets an unprivileged party drive `Rs` to grow up to 4 billion entries — each a decoded group element stored in memory — exhausting process memory and killing the node. Even for a fixed buffer, an attacker can still force a `count` of `u32::MAX` requiring 4 billion `read_G` calls; while each eventually fails at EOF, the loop only terminates after the input is drained, and on a streaming reader the attacker controls how much is ever "drained". This is a remotely-triggered application outage, matching the accepted impact class of a denial of service from public input bytes.

### Likelihood Explanation
`SchnorrAggregate` is the public type for aggregated Schnorr signatures in `crypto/schnorr`; its `read`/`serialize` pair is designed precisely for deserializing signatures received over the wire. An attacker who can submit a serialized aggregate signature (or any embedding structure that transitively calls `SchnorrAggregate::read`) fully controls the `len` field — a single 4-byte write of `0xFFFFFFFF` is sufficient to trigger the pathological allocation. No key material, validator status, or collusion is required; only the ability to supply bytes to the `read` API.

### Recommendation
Bound the declared element count before allocating/reading:
- Enforce a protocol-level maximum (e.g. reject `count > MAX_AGGREGATE`), or
- Where the reader is a `&[u8]`/`BufReader`, reject `count` larger than `remaining_len / G::Repr::LEN` up front.
Additionally, `SchnorrAggregate::verify` already rejects `self.Rs.len() != keys_and_challenges.len()` [3](#0-2) , so `read` could take the expected count as a parameter (mirroring how `Commitments::read` in `crypto/frost/src/nonce.rs` derives its element count from the caller's `generators` argument rather than from the untrusted stream [4](#0-3) ), eliminating the length field's authority entirely.

### Proof of Concept
```rust
// Any ciphersuite C with 32-byte points, e.g. a dalek-ff-group Curve.
// Feed bytes: len = u32::MAX followed by valid (or even padding) point encodings.
let mut bytes = vec![];
bytes.extend(u32::MAX.to_le_bytes());        // attacker-controlled count
// Attacker then streams 32-byte point encodings indefinitely;
// Rs grows by one C::G per 32 bytes supplied, with no cap.
bytes.extend(std::iter::repeat(0u8).take(1 << 20));

let res = SchnorrAggregate::<C>::read(&mut bytes.as_slice());
// On a streaming reader: unbounded memory growth -> OOM abort.
// On a fixed reader: loop performs up to 4 billion read_G attempts.
```

Caveat: the exact severity depends on whether a production caller exposes `SchnorrAggregate::read` to unauthenticated network input; within `crypto/schnorr` itself the function is public and performs no bounds checking, so any such caller inherits the vulnerability.
