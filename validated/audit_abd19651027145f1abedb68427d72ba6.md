### Title
DL singleton batch updates in `dl_update_multiple` lack cross-spend announcement linking, allowing signature subtraction to strip individual root updates from a submitted spend bundle - (File: `chia/wallet/wallet_rpc_api.py`)

### Summary
`WalletRpcApi.dl_update_multiple` builds one `WalletSpendBundle` containing an independent Data Layer singleton update coin spend per launcher, generated by `DataLayerWallet.create_update_state_spend`, and relies purely on BLS signature aggregation to bind them together instead of `AssertCoinAnnouncement`/`AssertPuzzleAnnouncement` conditions linking the spends. The code explicitly acknowledges this: [1](#0-0)  This is analogous to Cooler's `rollLoan`: the wallet owner authorizes what they believe is one atomic multi-root update transaction, but any party who relays/mempool-processes the resulting spend bundle can unilaterally re-derive a *subset* of it (dropping some singleton updates while keeping others) without the owner's renewed consent, because each per-launcher `CoinSpend` in the bundle is independently valid and not tied to the others via an announcement condition.

### Finding Description
`dl_update_multiple` splits the requested fee evenly across all launcher/root pairs (`fee_per_launcher = uint64(request.fee // len(...))`) and calls `create_update_state_spend` once per pair inside the same `action_scope`, producing one spend per DL singleton: [2](#0-1) 

Each of these spends is signed independently (per-coin `AGG_SIG_ME`), and the resulting bundle is only combined by BLS signature aggregation, not by any on-chain announcement that makes the coins mutually dependent, as the TODO states: [3](#0-2) 

`create_update_state_spend` itself only optionally emits an announcement for the `announce_new_state` ephemeral-coin case (single-singleton use, not used by `dl_update_multiple`) and for the fee-linkage assertion; it never links one singleton's spend to another singleton's spend: [4](#0-3) [5](#0-4) 

Because BLS signatures are aggregated (summed) rather than each coin spend individually re-verified against a single joint signature, any full-node/mempool participant who observes this spend bundle (e.g., before final block inclusion, or via a peer relaying an unconfirmed transaction) can reconstruct a spend bundle containing only a subset of the coin spends together with only that subset's corresponding signature contribution split out of the aggregate, provided they can determine the individual signature shares (which is possible when a per-coin `AGG_SIG_ME` signature is not entangled cryptographically with the others beyond simple summation, and especially trivial for any spend in the set that carries no `AGG_SIG` requirement of its own and thus needs no real signature at all). Such a stripped-down bundle spends only some of the DL singletons the owner intended to update together, while the wallet has no on-chain assertion forcing all launcher updates (and the associated fee, which was pre-split across all of them) to land as a single unit.

### Impact Explanation
This breaks the atomicity the RPC caller/DL operator relies on: they believe they are submitting one transaction that updates N DataLayer store roots together (e.g., to keep a set of related stores mutually consistent, or to only pay fee once for a set of updates). A third party who can manipulate the mempool/spend-bundle propagation can cause only a subset of those root transitions to be confirmed, or cause the owner's fee to be spent servicing fewer updates than authorized, without the DL operator’s renewed agreement — mirroring the Cooler bug class where "anyone can call and change terms without the affected party agreeing." Because each `create_update_state_spend` mutates on-chain singleton state (the DL Merkle root committed into the singleton, consumed for later proof verification via `dl_verify_proof_internal`), a partial/rearranged confirmation can silently desynchronize the wallet-tracked `SingletonRecord`s from what the operator intended to publish atomically, producing an inconsistent/incomplete DataLayer root set that downstream `verify_proof`/offer consumers may treat as valid current state.

### Likelihood Explanation
Exploitation requires the attacker to have visibility into an unconfirmed/broadcast spend bundle (a normal mempool observer role) and be able to isolate signature contributions per coin spend — which the code's own TODO calls out as a known, unaddressed weakness ("vulnerable to signature subtraction"). This does not require any special privilege beyond normal network/mempool access, matching the "single submitted spend bundle" reachability bar for this analog scan. The precondition of being able to actually split out individual signature shares depends on implementation specifics of how each spend's `AGG_SIG_ME` is combined (BLS aggregate signatures generally cannot be losslessly "subtracted" without knowing the discarded party's own signature component, unless that spend required no signature at all or the attacker independently possesses it), so likelihood is Medium rather than High/Critical, but it is a genuine, source-acknowledged design gap.

### Recommendation
Link every `create_update_state_spend` call inside `dl_update_multiple` with `CreateCoinAnnouncement`/`AssertCoinAnnouncement` (or puzzle announcements) so that all N DL singleton updates and the associated fee spend must be included together or the whole bundle fails; alternatively, aggregate the fee into a single fee-paying coin spend cross-linked by announcement to every launcher update, as the second TODO already recommends ("This method should natively support spending many and attaching one fee"). This removes the ability for any relaying party to confirm a strict subset of the originally-authorized multi-root update.

### Proof of Concept
Not independently reproduced in this review (no test/PoC execution tools available in ask-only mode); the vulnerability is derived directly from the in-source acknowledgment and structural analysis of `dl_update_multiple` and `create_update_state_spend`:
1. Caller invokes `dl_update_multiple` RPC with N `launcher_root_pairs` and a total `fee`.
2. `fee_per_launcher = fee // N` is computed and each singleton update spend is generated independently with no cross-spend announcement, per [2](#0-1) .
3. The resulting `WalletSpendBundle` aggregates BLS signatures across all N independent coin spends with no on-chain condition forcing them to be spent jointly.
4. A party observing the unconfirmed bundle can, in principle, remove one or more of the independent per-launcher coin spends (and the fee obligation was already split per-launcher, so removing one does not orphan the rest), producing a still-valid partial spend bundle that confirms fewer DL root updates than the operator authorized as one action — with no mechanism in the puzzle layer to reject the partial set.
