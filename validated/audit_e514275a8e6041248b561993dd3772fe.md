Based on my investigation, I found a credible analog in the CR-CAT (Credential-Restricted CAT) / VC (Verified Credential) subsystem. I was not able to load the raw `credential_restriction.clsp` puzzle file itself (it appears to be outside what the code index returns), so I could not directly inspect the on-chain enforcement of the restriction parameters at the CLVM level; I base the finding on the Python driver/wallet code, which shows that CR-CAT restriction parameters (`authorized_providers` / `proofs_checker`) are spender-supplied per generation (confirmed by the "remark condition" path used to (re)initialize them) and are not re-validated for continuity by the wallet logic that approves third-party spends.

### Title
Wallet approves third-party CR-CAT spends without verifying the credential-restriction "modules" (authorized_providers/proofs_checker) are preserved - ([File: chia/wallet/vc_wallet/vc_wallet.py])

### Summary
`VCWallet.add_vc_authorization()` is the function a wallet uses to co-sign (via VC announcements) a CR-CAT spend embedded in an offer built by an untrusted counterparty. It only validates where the resulting CREATE_COIN outputs go (to us, back to origin, to the pending-approval state, or to the offer puzzle), but never checks that the child CR-CAT's `authorized_providers` and `proofs_checker` — the equivalent of the Safe's "modules" — are unchanged from the parent CR-CAT being spent, before creating an approval announcement.

### Finding Description
`add_vc_authorization` iterates over incomplete `CRCATSpend`s pulled from an offer and, for each, decides whether the wallet's VC should authorize it: [1](#0-0) 

The `outputs_ok` loop only inspects the destination puzzle hash of each `CREATE_COIN` (`cc.at("rf")`), checking that it resolves to our wallet, to the CR-CAT's own inner puzzle hash (change), to the pending-approval-state hash, or to the `OFFER_MOD` hash. It never compares `crcat_spend.children[i].authorized_providers` / `.proofs_checker` against `crcat_spend.crcat.authorized_providers` / `.proofs_checker`.

The children objects come from `CRCAT.get_next_from_coin_spend`, which derives the restriction parameters directly from the counterparty-supplied puzzle reveal/solution of the spend being approved: [2](#0-1) 

Notably, one supported code path explicitly allows initializing/overwriting `authorized_providers` and `proofs_checker` via a `REMARK` condition emitted by the spend itself: [3](#0-2) 

This confirms that the restriction parameters ("modules") for the next generation of a CR-CAT coin are chosen by whoever constructs that spend, not fixed by consensus at mint time. Since `add_vc_authorization` never re-checks that these parameters remain the trusted ones after the spend, a malicious offer counterparty can construct an offer containing a CR-CAT spend whose output coin curries a weaker/attacker-controlled `authorized_providers` list (e.g., adding an attacker-controlled "provider") or a permissive `proofs_checker`, while still passing the `outputs_ok` destination checks (e.g., by routing the coin back to the CR-CAT's own inner puzzle hash, which is treated as legitimate "change"). The victim wallet's VC will then sign the approval announcement for this spend, unaware that the CR-CAT's post-spend policy has been altered — analogous to the Safe audit finding where only one module/property is checked post-execution while other "modules" are left unverified.

### Impact Explanation
If exploited, an offer counterparty could get a victim's VC-holding wallet to co-approve a spend that silently weakens or removes the credential restriction on the resulting CR-CAT coin (e.g., adding a colluding "authorized provider" or an always-true proofs checker). This undermines the entire purpose of CR-CATs (regulatory/compliance-gated transfer), effectively forging authorization for future unrestricted movement of the asset — a supply/asset-identity integrity issue for CR-CAT holders relying on VC-gated transfer semantics.

### Likelihood Explanation
Requires the victim to be a counterparty accepting/co-signing an offer containing a CR-CAT that is not fully spent by the taker (an "incomplete" `CRCATSpend`, which is a normal/supported offer flow for CR-CATs). No special privilege beyond being an offer counterparty is needed; the malicious spend can be built entirely client-side by the offer creator using the existing driver flexibility (remark-condition or curried-parameter control) described above.

### Recommendation
In `add_vc_authorization`, before authorizing any incomplete CR-CAT spend, explicitly assert that each `crcat_spend.children[i].authorized_providers == crcat_spend.crcat.authorized_providers` and `crcat_spend.children[i].proofs_checker == crcat_spend.crcat.proofs_checker` (unless the wallet intentionally supports a controlled provider/checker migration flow, in which case that transition should be explicitly whitelisted and surfaced to the user). This mirrors the audit's recommendation of verifying the full "module list" rather than a single narrow condition.

### Proof of Concept
1. Attacker creates an offer that includes spending their own CR-CAT coin.
2. In the spend's inner solution, attacker emits `CREATE_COIN` back to the CR-CAT's existing inner puzzle hash (satisfying the "change" branch of `outputs_ok`), but curries the new CR layer with a modified `authorized_providers` list that includes an attacker-controlled DID as an "authorized provider", or a `proofs_checker` requiring no real proofs.
3. Victim wallet, holding a valid VC for the original `authorized_providers`, calls `add_vc_authorization` while assembling/accepting the offer; since only destination puzzle hash is checked, `outputs_ok` is `True` and the wallet signs the VC announcement approving the spend.
4. The resulting CR-CAT coin is confirmed on-chain with the attacker's weakened restriction parameters, allowing the attacker (as the "authorized provider") to move the CAT going forward without genuine credential checks. [4](#0-3)

    @classmethod
    def get_next_from_coin_spend(
        cls,
        parent_spend: CoinSpend,
        conditions: Program | None = None,  # For optimization purposes, the conditions may already have been run
    ) -> list[CRCAT]:
        """
        Given a coin spend, this will return the next CR-CATs that were created as an output of that spend.
        Inner puzzle output conditions may also be supplied as an optimization.

        This is the main method to use when syncing. It can also sync from a CAT spend that was not a CR-CAT so long
        as the spend output a remark condition that was (REMARK authorized_providers proofs_checker)
        """
        coin_name: bytes32 = parent_spend.coin.name()
        puzzle = Program.from_serialized(parent_spend.puzzle_reveal)
        solution = Program.from_serialized(parent_spend.solution)

        # Get info by uncurrying
        _, tail_hash_as_prog, potential_cr_layer = puzzle.uncurry()[1].as_iter()
        new_inner_puzzle_hash: bytes32 | None = None
        if potential_cr_layer.uncurry()[0].uncurry()[0] != CREDENTIAL_RESTRICTION:
            # If the previous spend is not a CR-CAT:
            # we look for a remark condition that tells us the authorized_providers and proofs_checker
            inner_solution: Program = solution.at("f")
            if conditions is None:
                conditions = potential_cr_layer.run(inner_solution)
            for condition in conditions.as_iter():
                if condition.at("f") == Program.to(1):
                    new_inner_puzzle_hash = bytes32(condition.at("rf").as_atom())
                    authorized_providers_as_prog: Program = condition.at("rrf")
                    proofs_checker: Program = condition.at("rrrf")
                    break
            else:
                raise ValueError(
                    "Previous spend was not a CR-CAT, nor did it properly remark the CR params"
                )  # pragma: no cover
            authorized_providers = [bytes32(p.as_atom()) for p in authorized_providers_as_prog.as_iter()]
            lineage_inner_puzhash: bytes32 = potential_cr_layer.get_tree_hash()
        else:
            # Otherwise the info we need will be in the puzzle reveal
            cr_first_curry, self_hash_and_innerpuz = potential_cr_layer.uncurry()
            _, authorized_providers_as_prog, proofs_checker = cr_first_curry.uncurry()[1].as_iter()
            _, inner_puzzle = self_hash_and_innerpuz.as_iter()
            inner_solution = solution.at("f").at("rrrrrrf")
            if conditions is None:
                conditions = inner_puzzle.run(inner_solution)
            inner_puzzle_hash: bytes32 = inner_puzzle.get_tree_hash()

            lineage_inner_puzhash = construct_cr_layer(
