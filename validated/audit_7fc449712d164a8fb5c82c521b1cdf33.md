### Title
Payout OP_RETURN operator-credit is not covered by the user's SIGHASH_SINGLE|ANYONECANPAY signature, allowing the fronting operator's identity to be rewritten before confirmation - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds the payout transaction with the user's authorization covering only the withdrawal input/output (`SinglePlusAnyoneCanPay`), while the OP_RETURN output that records "which operator fronted this withdrawal" is appended afterward and is not bound by that signature. Downstream, verifiers derive operator credit/reimbursement rights solely from whatever OP_RETURN ends up in the confirmed transaction.

### Finding Description
`Operator::withdraw` verifies the user's signature only against the payout input/output using `SinglePlusAnyoneCanPay` sighash: [1](#0-0) 
The OP_RETURN carrying `operator_xonly_pk` (the credited "fronting" operator) is added to the transaction by `create_payout_txhandler` as output index 2, outside of what `SIGHASH_SINGLE|ANYONECANPAY` commits to: [2](#0-1) 
Because `SIGHASH_SINGLE` only commits to input 0 and output 0, and `ANYONECANPAY` allows arbitrary other inputs, any party that observes the signed input/output pair (once the operator funds and broadcasts the transaction with `fund_raw_transaction`, which does not lock the added inputs and leaves `replaceable` unspecified) can reconstruct a transaction that spends the *same* withdrawal input with the *same* signature and output-0 payment, but substitutes a different OP_RETURN naming a different operator, then get that variant mined instead (e.g., via RBF/fee bump).

The verifier's Bitcoin-sync logic then trusts whatever OP_RETURN ends up on-chain as ground truth for "who paid": [3](#0-2) 
This is persisted and later used both to determine which operator is entitled to reimbursement (`get_first_unhandled_payout_by_operator_xonly_pk`, feeding `PayoutCheckerTask`) and to judge whether a kickoff from the *true* funding operator is malicious: [4](#0-3) [5](#0-4) 

The binding the protocol relies on is: `operator credited via OP_RETURN == operator that actually funded the withdrawal`. Since the OP_RETURN is not signed by the user and is mutable prior to confirmation, an attacker can break this equality by mining a variant of the pending payout transaction with an OP_RETURN naming an operator who did not fund the withdrawal.

### Impact Explanation
If the OP_RETURN is rewritten to name an operator who did not actually front the payout:
- That falsely-named operator's `PayoutCheckerTask` will pick up the withdrawal as "its own unhandled payout" and initiate `handle_finalized_payout`/kickoff to claim reimbursement for a payout it never funded (Critical: "an operator reimbursed for a payout it never funded").
- Conversely, the operator that actually funded the withdrawal (and expects to be reimbursed) will find that `is_kickoff_malicious` / `send_asserts` reject its kickoff because `payout_op_xonly_pk != kickoff_data.operator_xonly_pk`, leaving the true funder permanently unable to be reimbursed for a real, on-chain payment it made (Critical: "an honest operator permanently unable to be reimbursed").

### Likelihood Explanation
Exploitation requires only the ability to observe the pending payout transaction in the mempool (an unprivileged network participant/mempool watcher) and to broadcast a fee-bumped variant before the original confirms. No verifier, operator, watchtower, or key-compromise privilege is needed — the user's own signature legitimately permits appending/altering outputs beyond output 0 and adding new inputs under `SIGHASH_SINGLE|ANYONECANPAY`. Whether the mempool relay/RBF policy in the deployed configuration actually allows such a replacement to propagate and confirm before the original is fully verified was not confirmed in this review (I could not inspect `crates/clementine-tx-sender/src/rbf.rs` in this pass), so the practical window and reliability of the replacement race is not fully established.

### Recommendation
Bind the operator-credit OP_RETURN into the portion of the transaction that is cryptographically authorized, e.g. by having the aggregator/verifiers require the withdrawal authorization (or a separate commitment signed by the fronting operator) to explicitly include the operator's xonly public key, so the OP_RETURN content cannot be altered without invalidating the authorization. Alternatively, require verifiers to independently confirm (e.g., via the operator's own signed announcement or the transaction's funding inputs, which are under sole control of the actual funder) which operator actually funded the payout, rather than trusting an unsigned OP_RETURN field alone.

### Proof of Concept
1. Operator A calls `Withdraw`/`InternalWithdraw`; `Operator::withdraw` builds and broadcasts a payout transaction with output 0 paying the user, OP_RETURN naming Operator A's xonly pk, signed by the user with `SIGHASH_SINGLE|ANYONECANPAY`.
2. Before confirmation, an attacker observes the transaction, extracts input 0 (withdrawal outpoint + valid user signature) and output 0 (user payment), and constructs a new transaction reusing them but replacing the OP_RETURN with Operator B's xonly pk and adding higher-fee inputs/outputs of their own.
3. Attacker broadcasts the replacement with higher fee; it is mined instead of (or as a replacement for) A's original transaction.
4. Verifiers' `update_finalized_payouts` records Operator B as `payout_payer_operator_xonly_pk` for this withdrawal.
5. Operator B's `PayoutCheckerTask` sees an unhandled payout attributed to itself and calls `handle_finalized_payout`, initiating reimbursement it never funded; meanwhile Operator A's later kickoff for the same deposit fails `is_kickoff_malicious`'s operator-match check, permanently blocking A's legitimate reimbursement.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
