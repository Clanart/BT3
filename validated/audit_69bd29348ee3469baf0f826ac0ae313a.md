### Title
Deterministic FROST/MuSig nonce reuse across divergent signing contexts enables key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a single `CachedPreprocess` seed keyed only by a fixed `context` (`(b"DkgConfirmer", attempt)`) in `CachedPreprocesses`. Every subsequent call — `preprocess`, `share`, and the `share_internal` re-execution inside `complete` — reads that same seed and deterministically regenerates identical FROST nonces via `ChaCha20Rng::from_seed` in `seeded_preprocess`. The seed is never rotated, deleted, or checked against the commitments actually published on-chain. The file's own header admits the safety argument requires that `sign` never run on "distinct received messages," and flags the needed check — that the regenerated commitments match the on-chain commitments — as a `TODO` that is not implemented.

### Finding Description
In `crypto/frost/src/sign.rs:121-144`, `seeded_preprocess` derives the signing nonces `(d, e)` entirely from the 32-byte seed: `ChaCha20Rng::from_seed(*seed.0)` feeds `Commitments::new`. Same seed ⇒ same nonces, always.

In `coordinator/src/tributary/signing_protocol.rs:123-145`, the seed is created once per `context` and stored via `CachedPreprocesses::set`. On every later call, `CachedPreprocesses::get` returns the identical seed, which is decrypted and passed to `AlgorithmSignMachine::from_cache`. There is no `del`/`remove` call on `CachedPreprocesses` anywhere — the seed persists for the lifetime of the attempt and is reused on every re-execution of `share_internal`.

The safety comment at lines 25-48 states nonce reuse is "explicitly unsafe" and claims safety because distinct inputs would require a BFT violation — but lines 50-54 contain an unimplemented `TODO`: verifying "the commitments generated from the decided nonces are in fact its commitments on-chain" and doing the same "before publishing shares." Without that check, a coordinator that re-executes `share_internal` over a different effective signing set (different participant membership in `threshold_i_map_to_keys_and_musig_i_map`, different preprocess bytes from untrusted validators, or a rebuild that re-decides on a divergent view) produces a second signature share under the *same* `(d, e)` but a different binding factor ρ and challenge c.

A FROST share has the form `s = d + e·ρ + λ·x·c`. Two shares `s₁`, `s₂` with identical `(d, e)` but distinct public `(ρ₁, c₁)` and `(ρ₂, c₂)` yield `x` by solving the 2×2 linear system — full private key-share recovery by an unprivileged observer of public tributary data (shares and preprocesses are published on-chain).

### Impact Explanation
`DkgConfirmer` signs `set_keys_message` with the validator set's MuSig-aggregated Ristretto key — explicitly described as "the root of trust." Recovering a validator's key share undermines the supermajority confirmation of DKG results on Substrate, and the same `SigningProtocol` machinery is the template for coordinator-side threshold signing. The leaked share, combined with threshold-many compromised or subsequently recoverable shares, permits forging on-chain key confirmations. This is the ROS-style / parallel-session nonce-reuse class applied through deterministic caching rather than concurrency.

### Likelihood Explanation
The seed-reuse mechanism itself is unconditional — same `context` always yields same nonces. Exploitation requires `share_internal` to execute twice over divergent preprocess/message inputs. The code explicitly acknowledges this precondition is only guarded by an unimplemented `TODO`: any partial rebuild, re-execution over a different finalized preprocess set, or a validator that causes the preprocess map presented to `complete` to differ from the one used at `share` time triggers the reuse. An unprivileged validator fully controls the preprocess bytes it submits, and `read_preprocess` accepts arbitrary bytes, so divergent binding-factor transcripts are directly attacker-influenced.

### Recommendation
- After consuming a cached preprocess in `share_internal`, delete it (`CachedPreprocesses` removal) so any re-execution regenerates fresh nonces, or derive the seed as `H(seed || H(preprocesses || msg))` so the nonce is bound to the exact signing inputs.
- Implement the flagged check before publishing a share: verify the commitments regenerated from the cached seed equal the commitments this validator already published on-chain for this context; abort rather than emit a share on mismatch.
- Persist the published preprocess/commitments alongside the seed so re-executions can detect divergence deterministically.

### Proof of Concept
1. Attempt `a` begins; `preprocess_internal` stores seed `S` under `("DkgConfirmer", a)` and emits commitments `D, E` derived from nonces `(d, e)`.
2. `share()` runs with preprocess set `P₁` (participant set/bytes chosen by submitted tributary messages) → publishes `s₁ = d + e·ρ₁ + λ·x·c₁`.
3. A re-execution path (`complete` at line 321-324, or a rebuild that re-decides over a divergent preprocess map `P₂ ≠ P₁` — possible because the commitment-consistency check at lines 50-54 is `TODO`) reruns `share_internal`, reloads the same `S`, regenerates the same `(d, e)`, and emits `s₂ = d + e·ρ₂ + λ·x·c₂` where `ρ₂, c₂` are publicly computable from the on-chain transcripts.
4. Solve `s₂ - s₁ = e·(ρ₂ - ρ₁) + λ·x·(c₂ - c₁)` together with the public aggregate-key equation for `x` — validator key share recovered from public data only.
