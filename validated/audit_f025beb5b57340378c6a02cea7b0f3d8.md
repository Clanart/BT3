### Title
Gasless module blindly trusts an owner-controlled `GaslessSwapRouter` token/dex whitelist for real KAIA fee-lending decisions - (File: kaiax/gasless/impl/getter.go, kaiax/gasless/impl/tx_pool.go)

### Summary
The `kaiax/gasless` module lends real KAIA gas fees to users via `GetLendTxGenerator`/`LendTxGenerator`, expecting them to be repaid by a `swapForGas` call routed through the on-chain `GaslessSwapRouter` (GSR) contract. The set of "allowed" tokens and the single trusted `swapRouter` address are read directly from GSR contract state each block via `updateAddresses`/`getGaslessInfo`, and the pre-lending economic check (`checkBalanceForSwap`) relies entirely on that same contract's `getAmountIn` price quote. [1](#0-0) [2](#0-1)  The GSR contract itself exposes an owner-gated `addToken(token, factory, router)` function that can register arbitrary token/factory/router triples. [3](#0-2) 

### Finding Description
This mirrors the reported bug class: a privileged, trusted party (the GSR "owner", analogous to the Astaria "vault owner") can unilaterally register a worthless/malicious asset (token + factory + router triple) into a system that other unprivileged parties (block proposers acting through the `kaiax/gasless` module, and end users) rely on to make real value-transfer decisions. Once registered, `updateAddresses` pulls this token into `g.allowedTokens` and the malicious router becomes `g.swapRouter`, causing `IsApproveTx`/`IsSwapTx` to classify swaps against it as legitimate gasless transactions eligible for fee lending. [4](#0-3)  The only economic sanity check performed by the node, `checkBalanceForSwap`, queries `getAmountIn` on the very same (potentially owner-controlled/malicious) router contract to validate that the swap amount is fair, and checks ERC20 `balanceOf`/`allowance` on the (potentially owner-controlled/malicious) token contract. [5](#0-4)  There is no independent, node-side verification of the token's real value or the router's real liquidity; the module's only defense is that the declared `amountRepay` must equal the tx-fee-derived `repayAmount` formula, but this comparison only checks the *declared* repay parameter, not that the swap will actually deliver equivalent value. [6](#0-5) 

Because the GSR contract's Solidity implementation is not present in this repository (only generated bindings exist), I cannot fully confirm whether `swapForGas`'s internal accounting enforces atomic, trustless repayment regardless of the token/factory/router registered, or whether an owner-added malicious factory/router pair could cause the contract to report a successful "swap" without real value moving to repay the lent KAIA. This is the key unverified link in the chain.

### Impact Explanation
If the GSR owner can add a token/factory/router combination that satisfies the module's `isApproveTx`/`isSwapTx`/`checkBalanceForSwap` checks without providing genuine economic value, the owner (or any user colluding with the owner) could repeatedly trigger the block proposer's `LendTxGenerator` to advance real KAIA gas fees that are never genuinely repaid, draining proposer funds transaction by transaction. This is a fee-delegation/gasless settlement theft scenario within the explicitly in-scope "gasless and auction modules" category.

### Likelihood Explanation
Likelihood is Medium: it requires control of the GSR contract's owner key (a privileged but application-level role, not a network validator/operator), and the exact severity depends on GSR's internal Solidity logic which is not available in this repo for full verification. If the owner key is compromised or malicious by design (exactly the "public vault owner can rug" scenario in the source report), the attack is straightforward and repeatable for as long as the malicious token remains in `g.allowedTokens`.

### Recommendation
- Have the `kaiax/gasless` module independently verify the economic legitimacy of a token/router before trusting it for fee lending (e.g., cross-check against a governance-approved allowlist stored outside the mutable GSR contract, or require a minimum on-chain liquidity/TWAP check independent of the router being priced).
- Ensure `swapForGas` settlement is fully atomic at the EVM level so that if genuine repayment value is not produced, the entire bundle (lend tx + approve/swap tx) reverts, and audit this invariant explicitly for owner-added token/factory/router combinations.
- Consider requiring governance (not a single EOA owner) to add tokens/routers to GSR, and add monitoring/alerts for `AddToken` events combined with anomalous gasless-lending volume for newly added tokens.

### Proof of Concept
Not fully constructible from this repository alone, since the `GaslessSwapRouter.sol` source (specifically `addToken`'s access control and `swapForGas`'s internal settlement logic) is not indexed here — only Go bindings are available. func (g *GaslessModule) updateAddresses(header *types.Header) error {
	g.gaslessInfoMu.Lock()
	defer g.gaslessInfoMu.Unlock()

	swapRouter, tokens, err := getGaslessInfo(g.Chain, header)
	// proceed even if there is something wrong with multicall contract
	if err != nil {
		g.swapRouter = common.Address{}
		g.allowedTokens = map[common.Address]bool{}
		logger.Warn("there is something wrong with multicall contract", "err", err.Error())
		return nil
	}

	g.swapRouter = swapRouter

	g.allowedTokens = map[common.Address]bool{}
	for _, addr := range tokens {
		// all tokens are allowed if nil
		if g.GaslessConfig.AllowedTokens == nil {
			g.allowedTokens[addr] = true
		}
		for _, allowed := range g.GaslessConfig.AllowedTokens {
			if addr == allowed {
				g.allowedTokens[addr] = true
			}
		}
	}

	return nil
}
