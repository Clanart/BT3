## Finding: Unsigned OP_RETURN operator attribution in payout transactions allows misattribution of reimbursement credit

### Title
Payout transaction's operator attribution (OP_RETURN) is not covered by the user's signature, allowing an unprivileged party to front a withdrawal while attributing the reimbursement credit to an arbitrary operator - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The user's withdrawal authorization signature uses `SIGHASH_SINGLE | ANYONECANPAY`, which only binds the signed input to its own indexed output (the user payout, output 0). The OP_RETURN output that identifies *which operator fronted the payout* (and therefore which operator gets credited for later reimbursement) is added at output index 2 and is **not covered by any signature at all**. Any party who possesses the withdrawal's `input_signature` (visible once a payout tx referencing it hits the mempool, or otherwise obtained) can construct a competing transaction that reuses the same signed input/output, adds their own fee-paying input, and writes an arbitrary xonly-pubkey into the OP_RETURN — including the pubkey of an operator who never built, signed, or funded that transaction.

### Finding Description
`create_payout_txhandler` builds the payout transaction with the operator's xonly pubkey placed in a plain OP_RETURN output, independent of any signature: [1](#0-0) 

The only cryptographic check performed on the withdrawal is `SECP.verify_schnorr` against the *user's* key over the sighash for the *user's own input*, using `in_signature.sighash_type` which is enforced to be `SinglePlusAnyoneCanPay`: [2](#0-1) [3](#0-2) 

Because the sighash type is `SIGHASH_SINGLE | ANYONECANPAY`, the signature commits only to the single signed input and the correspondingly-indexed output (output 0, the user payout). It does **not** commit to the OP_RETURN output (output 2, holding the "fronting operator" xonly pubkey) or to whichever additional fee-paying inputs get added. Consequently, whoever ultimately assembles and broadcasts the confirmed transaction fully controls the OP_RETURN content.

Downstream, the verifier's chain-sync logic trusts this OP_RETURN blindly to determine who gets credited as the payer/operator for the withdrawal: [4](#0-3) 

This attribution is then persisted and later relied upon by the credited operator's own node to trigger the kickoff/reimbursement flow: [5](#0-4) [6](#0-5) 

The same unauthenticated OP_RETURN value is also what the bridge circuit trusts to bind the reimbursement claim to an operator identity (`operator_xonlypk`), with no verification that the named operator actually produced or funded the transaction: [7](#0-6) 

### Impact Explanation
An unprivileged attacker can observe a legitimate operator's unconfirmed payout transaction (or otherwise obtain the withdrawal `input_signature`), then build and broadcast — with a higher fee — a competing transaction that: (a) spends the same user-signed withdrawal input and pays the same user output (satisfying the only signature check that exists), (b) supplies its own funding input, and (c) writes a different operator's xonly pubkey (or its own, if targeting a registered operator) into the OP_RETURN output.

If the attacker's transaction confirms first:
- The genuine fronting operator's own payout transaction becomes a conflicting/double-spend and can never confirm, permanently preventing that operator from establishing itself as payer in the database (`validate_payer_is_operator` requires an exact match with `self.signer.xonly_public_key`), meaning the honest operator is **permanently unable to be reimbursed** for a withdrawal it legitimately intended to front.
- The verifier database instead attributes payer status to whatever operator the attacker chose. That named operator's own node will pick up the "unhandled payout" and proceed through the kickoff/reimbursement flow for a payout it never authorized or funded, receiving vault reimbursement it did not earn, or — if the attacker names an operator not equipped to properly answer challenges — that operator can be pushed into a kickoff/challenge cycle it did not initiate.

This breaks the "operator credited versus the party that paid" custody binding explicitly called out as in scope, and results in a Critical-class outcome (an honest operator permanently unable to be reimbursed / a misattributed reimbursement).

### Likelihood Explanation
This requires no special role, key, or privilege — only observing a broadcast (unconfirmed) payout transaction or otherwise learning the withdrawal signature, and the ability to broadcast a bitcoin transaction with a competitive fee. Since payout transactions are explicitly designed to be fee-bumped via `fund_raw_transaction`/RBF (implying they sit in the mempool for some time), the window for an attacker to race a replacement transaction is realistic.

### Recommendation
Bind the operator attribution to the transaction with a signature the circuit and verifier can authenticate, rather than trusting an unsigned OP_RETURN:
- Require the operator to sign the OP_RETURN commitment (e.g., include the operator xonly pubkey inside data that is covered by a signature verifiable on-chain or by the bridge circuit), or
- Change the sighash type/commit structure so the OP_RETURN output is covered by a signature from the party being credited (the operator), so a third party cannot rewrite the attribution while merely reusing the user's signed input/output.

### Proof of Concept
1. Operator O1 receives the user's `WithdrawParams` (with `input_signature` using `SIGHASH_SINGLE|ANYONECANPAY` over input 0 / output 0) and constructs+broadcasts `payout_tx_1` via `Operator::withdraw` → `create_payout_txhandler`, with OP_RETURN = O1's xonly pubkey, funded by O1's own wallet input.
2. Attacker A observes `payout_tx_1` in the mempool (or otherwise learns `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`).
3. A constructs `payout_tx_2` reusing the same signed input 0 and output 0 (this passes `SECP.verify_schnorr`, since the signature only commits to that input/output pair), adds their own funding input, and sets OP_RETURN = O2's (a different, registered operator's) xonly pubkey. A broadcasts `payout_tx_2` with a higher fee.
4. `payout_tx_2` confirms first; `payout_tx_1` is invalidated (conflicting spend of the same withdrawal UTXO).
5. `update_finalized_payouts` parses the confirmed `payout_tx_2`'s OP_RETURN and records O2 as `payout_payer_operator_xonly_pk` for that withdrawal.
6. O1's `validate_payer_is_operator` check now fails (payer is O2, not O1) — O1 can never get reimbursed for the funds it sent to the user. O2's `PayoutCheckerTask` instead picks up the "unhandled payout" and proceeds to claim reimbursement it never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
