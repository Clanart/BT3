### Title
Reducing `challengePeriod` via `updateHostParams` retroactively shortens the veto window for already-submitted state commitments, allowing early acceptance of unvetoed (potentially fraudulent) state - (File: evm/src/core/EvmHost.sol, evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2` validates the fisherman-veto safety window for a state commitment by comparing `block.timestamp - host.stateMachineCommitmentUpdateTime(height)` against the **current** `host.challengePeriod()`, not the challenge period that was in effect when the commitment was stored. Because `updateHostParams` (the exact analog of `_configureRegistry`/`setRegistry` in the report) can change `challengePeriod` at any time without inspecting or re-validating already-pending state commitments, shortening this parameter instantly and retroactively finalizes commitments that were still inside their intended fisherman-veto window.

### Finding Description
`storeStateMachineCommitment` records only the commitment and `block.timestamp` — it never snapshots the challenge period that applied at submission time: [1](#0-0) 

Every message handler (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) re-reads the challenge period live from host state at call time and compares it to the stored update timestamp: [2](#0-1) [3](#0-2) 

The same pattern exists in the substrate ISMP core (`verify_delay_passed` reads `host.challenge_period(...)` live against the stored `state_machine_update_time`): [4](#0-3) 

`updateHostParams` is the direct analog of the reported `_configureRegistry`/`setRegistry`: it is the single entrypoint that mutates `challengePeriod` (along with `consensusClient`, `stateMachines`, etc.), and it performs no check of currently pending/unvetoed state commitments before applying the new value: [5](#0-4) 

The fisherman veto mechanism (`deleteStateMachineCommitmentInternal`) is precisely the security control the challenge period is meant to protect — fishermen have exactly `challengePeriod` seconds after `storeStateMachineCommitment` to detect and veto a fraudulent state commitment before it can be relied upon: [6](#0-5) 

Because the check is always evaluated against the *current* parameter rather than the parameter in force when the commitment was written, any reduction of `challengePeriod` (e.g. from 7 days to 1 hour) instantly moves every already-stored, still-pending state commitment past its check — even ones submitted seconds earlier that fishermen had not yet had a fair opportunity to inspect under the original window.

### Impact Explanation
If a malicious or faulty state commitment was stored just before a legitimate parameter update shortens `challengePeriod`, relayers can immediately submit post requests, get responses, or timeouts referencing that commitment without waiting out the fisherman-review period the submitter and downstream applications were relying on. This can result in false state (and therefore false proof) acceptance and downstream execution of requests/timeouts derived from unverified state — directly matching the bounty's "false proof/state acceptance" and "unauthorized transaction or execution" categories, since dispatched requests can move funds or trigger app logic (e.g. bandwidth accounting, paymaster, intent settlement) based on state that had not completed its intended veto window.

### Likelihood Explanation
`updateHostParams` is gated by `hostManager` (cross-chain governance), so the parameter change itself is a legitimate governance action, not an attacker action. However, once such a change occurs (which is an expected, documented, and repeatedly-tested operational path — see `testCanAddwhitelistedStateMachines` and `test_host_manager_set_host_params`), the exploitation of the resulting window is fully permissionless: any relayer can call `handlePostRequests`/`handleGetResponses`/etc. against the pre-existing commitment the instant the new (shorter) period is satisfied, with no additional privilege required. The bug is exactly the analog described in the report: the config-update function never iterates/re-checks existing dependent state (here, pending state commitments) before applying a change that alters their trust status.

### Recommendation
Snapshot the effective challenge period alongside `_stateCommitmentsUpdateTime` at the moment `storeStateMachineCommitment` is called (or store a `(updateTime, challengePeriodAtSubmission)` tuple), and have `HandlerV2` compare elapsed time against the snapshotted period rather than the live `host.challengePeriod()`. Alternatively, when `updateHostParams` lowers `challengePeriod`, enforce that the new (lower) value only applies to state commitments stored after the update, preserving the original window for all commitments already pending.

### Proof of Concept
1. Governance calls `updateHostParams` with `challengePeriod = 7 days` (long veto window), consistent with production configuration.
2. A relayer submits a consensus/state proof; `HandlerV2.handleConsensusUpdate` (or equivalent) calls `host.storeStateMachineCommitment(height, maliciousCommitment)`, recording `_stateCommitmentsUpdateTime[height] = block.timestamp` — see [1](#0-0) . Fishermen expect 7 days to inspect and veto.
3. Minutes later, governance legitimately (or under compromised/rushed process) calls `updateHostParams` again, this time setting `challengePeriod = 1 hours` for unrelated operational reasons — allowed unconditionally by `updateHostParamsInternal`, see [7](#0-6) .
4. One hour later (far short of the original 7-day fisherman window), any relayer calls `handlePostRequests` with a proof anchored at `height`. The check `challengePeriod > delay` now uses the new 1-hour value against the same stored timestamp and passes, see [8](#0-7) .
5. Requests/responses/timeouts derived from the still-unvetoed (potentially fraudulent) `maliciousCommitment` are dispatched to destination modules before fishermen had their originally-promised opportunity to call `deleteStateMachineCommitment` and veto it, see [6](#0-5) .

    /**
     * @dev Updates the HostParams. Will reset all fishermen accounts and initialize any new state machines.
     * @param params, the new host params.
     */
    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;

        // add whitelisted state machines
        for (uint256 i = 0; i < stateMachinesLen; ++i) {
            // create if it doesn't already exist
            if (_latestStateMachineHeight[params.stateMachines[i]] == 0) {
                _latestStateMachineHeight[params.stateMachines[i]] = 1;
            }
        }
    }

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
