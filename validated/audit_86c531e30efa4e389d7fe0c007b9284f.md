### Title
FieldMaskUtil::MergeMessageTo logs attacker-controlled FieldMask path segments unescaped, enabling log injection/forgery - ([File: src/google/protobuf/util/field_mask_util.cc])

### Summary
`FieldMaskUtil::MergeMessageTo` (and the underlying `FieldMaskTree::MergeMessage`) writes raw, attacker-supplied `FieldMask.paths` segments directly into `ABSL_LOG(ERROR)` statements with no escaping of control characters (CR/LF, ANSI escapes, etc.), mirroring the Django `request.path`-in-logs issue (CVE-2025-48432 / CWE-117): an untrusted string reaches an internal log sink without neutralization, allowing forged/injected log lines.

### Finding Description
`google.protobuf.FieldMask` is a `repeated string paths` well-known type with no character restrictions on its entries — any consuming application can populate it directly from a client request (the common `UpdateFooRequest { Foo foo; FieldMask update_mask; }` pattern used pervasively in protobuf-based RPC/REST APIs), via `ParseFromString`/`ParseFromArray` or ProtoJSON.

`FieldMaskUtil::MergeMessageTo(source, mask, options, destination)` is a public API declared at [1](#0-0) . Internally it builds/traverses a `FieldMaskTree` whose nodes are keyed by path segments split from the (attacker-controlled) mask strings, and `FieldMaskTree::MergeMessage` walks those segments against the destination message's `Descriptor`: [2](#0-1) 

When a path segment does not resolve to a known field, or resolves to a field that cannot have sub-paths, the raw segment `field_name` (a `absl::string_view` taken verbatim from the wire/JSON-supplied `FieldMask.paths` entry) is streamed directly into `ABSL_LOG(ERROR)` with no escaping:
```
ABSL_LOG(ERROR) << "Cannot find field \"" << field_name << "\" in message "
                << descriptor->full_name();
...
ABSL_LOG(ERROR) << "Field \"" << field_name << "\" in message "
                << descriptor->full_name()
                << " is not a singular message field and cannot "
                << "have sub-fields.";
```
This is the exact failed invariant from the Django report transplanted to Protobuf: an attacker-controlled value (`FieldMask` path segment, analogous to `request.path`) is written into an internal log line (analogous to Django's internal HTTP response logger) with no neutralization of characters that have special meaning to log viewers/terminals/aggregators.

Unlike the `TextFormat` parser's error/warning messages, where the offending "field name" strings originate from the *trusted schema* (`descriptor->full_name()`, `field->name()`), here the logged string is a substring taken directly out of parsed/attacker-supplied message content (`FieldMask.paths`), which is the class of untrusted-data-into-logs the Django advisory addresses. There is no upstream sanitization step in `FieldMaskUtil` before this log call — `IsValidFieldMask<T>` is an optional, application-invoked pre-check that most callers skip before calling `MergeMessageTo`/`TrimMessage` directly.

### Impact Explanation
Because `field_name` can contain arbitrary bytes (newlines, carriage returns, ANSI/VT100 escape sequences, log-format delimiters such as JSON/CSV structural characters used by log pipelines), an attacker can:
- Inject fabricated log lines/records (log forgery) that appear to come from a different, legitimate event.
- Corrupt structured/machine-parsed log output (e.g., if downstream tooling naively appends this line into JSON/CSV logs), potentially causing log-injection-based deception of SOC/monitoring tooling.
- Inject terminal escape sequences that manipulate the terminal of an operator tailing raw logs (a well-documented log-injection risk category, matching CWE-117 and the CVSS vector of the source advisory: `AV:N/AC:H/PR:N/UI:N/S:C/C:N/I:L/A:N`).

There is no memory corruption, RCE, or resource exhaustion — impact is confined to integrity of log records (`I:L`), matching the severity profile of the original Django CVE.

### Likelihood Explanation
Reaching this code path requires: an application that (a) exposes an update/patch-style RPC that accepts a client-supplied `FieldMask` (extremely common pattern in gRPC/REST-to-gRPC transcoded services), and (b) calls `FieldMaskUtil::MergeMessageTo`/`TrimMessage` without first calling `IsValidFieldMask`. Since `FieldMaskUtil` is documented/intended precisely for this "apply a client-specified partial update" use case, and validation is optional, this is a realistic and likely-triggered condition — an attacker only needs to supply a mask path segment containing an unknown/invalid field name (trivial, no parsing tricks needed) with embedded control characters.

### Recommendation
- Escape/neutralize the logged `field_name` (and similarly `descriptor->full_name()` is safe since schema-derived, but the untrusted `field_name` is not) before writing it into `ABSL_LOG(ERROR)` in `FieldMaskTree::MergeMessage`, e.g., via `absl::CEscape`/`absl::CHexEscape` as is already done elsewhere in the codebase for untrusted data (e.g., `src/google/protobuf/compiler/subprocess.cc:270-271` escapes unparseable plugin output with `absl::CEscape`, and `json/internal/lexer.cc` explicitly discusses hardening error text against log-hostile content).
- Consider making `IsValidFieldMask` validation mandatory (or offering a "safe" merge/trim variant) before any field-mask-driven merge/trim proceeds on untrusted input.

### Proof of Concept
1. Define a trusted schema message `Foo` with a normal field `bar`.
2. Attacker crafts an `UpdateFooRequest`-style wire payload (or, for a minimal repro, directly constructs a `FieldMask`) whose `paths` entry is:
   `"\r\n[FORGED] admin_login_success user=attacker\r\n"`
   (or containing ANSI escape sequences), i.e. `mask.add_paths("\r\n[FORGED] admin_login_success user=attacker\r\n")`.
3. Call `FieldMaskUtil::MergeMessageTo(source, mask, MergeOptions(), &destination)` where `destination` is a `Foo` instance — the descriptor lookup `descriptor->FindFieldByName(field_name)` at [3](#0-2)  fails (no such field), and the raw string is written verbatim via `ABSL_LOG(ERROR)`.
4. Inspect stderr/log sink: the injected `\r\n[FORGED] admin_login_success user=attacker\r\n` text appears as a fabricated, independent log line, demonstrating log forgery — the exact class of impact described in the Django advisory (CVE-2025-48432 / CWE-117).

Note: I was unable to further trace every call site that constructs `FieldMaskTree` nodes (e.g., the exact `AddPath`/tree-construction helper) within the tool budget, so I could not fully confirm whether any earlier code path trims/validates characters in path segments before they reach `MergeMessage`; based on the `AddPath`/`IntersectPath` code reviewed (`field_mask_util.cc:435-458`), no such sanitization is present, only structural `.`-splitting.
