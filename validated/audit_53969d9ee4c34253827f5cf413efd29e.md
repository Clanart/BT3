### Title
`GeneratorPromotion::complete` panics when a proof is submitted under the completer's own participant index, letting one participant abort (cancel) every other party's key promotion — ([File: crypto/dkg/promote/src/lib.rs](https://github.com))

### Summary
Analogous to the Vader `cancelProposal(id, id)` bug — where supplying the same ID twice bypassed the check meant to guard a destructive operation — `GeneratorPromotion::complete` only validates `proofs.len() == n - 1` and `i <= n`, but never checks that `proofs` actually excludes the caller's own index `params.i()`. A participant can submit their `GeneratorProof` keyed under the *victim's* `Participant` index (an "old == new" style self-substitution). The length and bound checks still pass, yet when `complete` iterates `1 ..= n` it skips the victim's index and hits `proofs.get(&j).unwrap()` on a genuinely missing participant, panicking. The promotion — the only mechanism to migrate a key set to a new generator — is irrecoverably aborted for that completer.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` verifies:

1. `proofs.len() == n - 1` (lines 125–131)
2. every key `i` satisfies `u16::from(i) <= params.n()` (lines 132–136)

Then it loops `for i in 1 ..= params.n()`, `continue`s when `i == params.i()`, and unconditionally unwraps `proofs.get(&i)` for every other index (lines 140–146).

A `HashMap` of size `n - 1` whose keys are all `<= n` is not guaranteed to be the exact set `{1..=n} \ {params.i()}`. An attacker substitutes the completer's index for some other participant's index: the map still has `n - 1` entries, all in range, so both checks pass — exactly mirroring how `cancelProposal(id, id)` passed the minority check because the same value was accepted where two distinct values were required. When iteration reaches the displaced participant, `proofs.get(&i).unwrap()` panics instead of returning a `PromotionError`.

### Impact Explanation
`complete` is part of a `verify`-class API reachable with untrusted `GeneratorProof` bytes deserialized via `GeneratorProof::read` and collected into the `proofs` map by an integrator. Any participant (or anyone who can inject a proof into the collection) can deterministically crash the promotion of every honest completer, permanently preventing the key set from being promoted to the new generator — a denial of service on a key-management operation, matching the original report's "anyone can cancel" DoS class. Severity: Medium (panic/DoS on attacker-controlled input; no secret or forgery impact).

### Likelihood Explanation
Requires only that a participant's proof be registered under the wrong `Participant` key — trivially done by whoever relays proofs, or by a participant mislabeling its own submission. The vulnerable `unwrap` is hit on the first missing index.

### Recommendation
Validate the key set explicitly before iterating: after the length check, require `proofs.keys()` to be exactly `{1..=params.n()} \ {params.i()}` — i.e., reject any map containing `params.i()` — and replace `proofs.get(&i).unwrap()` with a checked lookup returning `PromotionError::InvalidParticipant`/a missing-participant error instead of panicking.

### Proof of Concept
Conceptual, for a `t = n = 3` set where victim has `params.i() == 1`:

```rust
// proofs collected by victim (Participant 1)
// Attacker (or relay) registers a proof under key 1 instead of its real index 3.
let mut proofs: HashMap<Participant, GeneratorProof<Ristretto>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), malicious_proof); // victim's own index!
proofs.insert(Participant::new(2).unwrap(), honest_proof_p2);
// proofs.len() == 2 == n - 1   -> passes
// all keys <= n                -> passes
// loop: i=1 skipped (params.i()), i=2 ok, i=3 -> proofs.get(&3).unwrap() PANICS
let _ = promotion.complete(&proofs); // thread panics; promotion aborted
```

Root cause confirmed at `crypto/dkg/promote/src/lib.rs:132-146`: no exclusion check for `params.i()` in `proofs`, and an `unwrap()` on the per-index lookup.
