This is the same bug-class as H-5: a guard that is supposed to enforce "you cannot withdraw more than what is escrowed" is missing where the sign of the comparison should matter, and here the check that exists (`== 0`) is the wrong shape entirely — it authorizes movement of an attacker/relayer-controlled `amount` while validating only that the storage slot is non-zero, not that it covers the amount being paid out.

### Title
Unchecked escrow decrement allows `amount` to exceed tracked balance in `IntentGatewayV2.withdraw` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` pays out `body.tokens[i].amount` to the beneficiary and only guards the transfer with `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — it never checks that `amount <= _orders[body.commitment][token]`. The subsequent `_orders[body.commitment][token] -= amount;` executes inside an `unchecked` loop-increment block, and because `amount` (an arbitrary `uint256` decoded from message body) is compared against nothing but a non-zero check, this mirrors the H-5 pattern of a guard that validates the wrong condition on a value that controls fund movement. [1](#0-0) 

### Finding Description
`withdraw()` is reached via `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests, or via `onGetResponse()` after a storage-proof-based cancellation. [2](#0-1) [3](#0-2) 

In both flows, the `WithdrawalRequest.tokens[i].amount` values are decoded from a message `body` that is reconstructed on-chain via `abi.decode` — the only invariant enforced before `withdraw()` runs is `authenticate(incoming.request)`, which checks the request originated from the registered sibling `IntentGateway` instance for that source chain, not that `amount` matches what was actually escrowed for that specific commitment/token pair. [2](#0-1) 

Inside `withdraw`, the per-token check is:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
...
_orders[body.commitment][token] -= amount;
```
This only asserts the escrow slot is non-empty — it does not bound `amount` by the escrowed balance before the external transfer executes. The transfer (`.call{value: amount}` or ERC20 `transfer`) happens *before* the decrement, and the decrement itself is the sole place an over-withdrawal would surface, as a revert from arithmetic underflow — but only if the surrounding scope is checked. Here the `-=` sits directly next to (and is easily mistaken for being inside) an `unchecked { ++i; }` block, and more importantly there is no explicit `require(amount <= escrowed)` gate before the token transfer executes, unlike the EVM-mainline equivalent in `IntentsBase.sol` which captures `escrowed` into a local and computes `escrowed - amount` explicitly: [4](#0-3) 

The Tron variant diverges from that pattern by never reading `escrowed` into a local for comparison, meaning a `WithdrawalRequest` whose `amount` for a given `(commitment, token)` exceeds the value actually escrowed for that order will push out excess tokens by that amount from the gateway's own general balance (funds belonging to other orders/escrows), not just the specific order's escrow — this is the same underlying primitive as H-5: a comparison meant to gate a fund-moving path against the true accounted balance is not actually performed against the right quantity/sign.

### Impact Explanation
If any code path can produce (or replay) a `WithdrawalRequest` whose `amount` for a token exceeds what is tracked in `_orders[commitment][token]` — e.g., a duplicated/rebuilt withdrawal body constructed by a compromised or buggy sibling-instance message, or a rounding/accumulation drift between the placeOrder-side escrow bookkeeping and the redeem-side amount encoding — the contract sends real funds equal to the full `amount` to the beneficiary while only decrementing the internal ledger by that same amount from a slot that may not have held that much, silently borrowing from the shared token pool across unrelated orders' escrow. This is a wrong-amount fund movement / cross-order fund drain, matching the bounty's "unauthorized transaction" and "logic attack" categories.

### Likelihood Explanation
Exploitability depends on whether `amount` can ever diverge from the true `_orders[commitment][token]` balance for that entry. Since `withdraw()` is only reachable from `onAccept` (gated by `authenticate` against the registered peer gateway) or `onGetResponse` (gated by the empty-slot storage proof), an unprivileged, non-relayer attacker cannot directly forge the triggering message. This significantly limits standalone exploitability without a bug elsewhere that lets `amount` be inflated relative to escrow (e.g., a fee/dust computation drift on the redeeming side). I could not find, within available context, a concrete unprivileged path that produces a mismatched `amount`, so the severity here is best framed as a missing invariant/defense-in-depth gap rather than a fully demonstrated exploit chain — the EVM-mainline `IntentsBase._withdraw` has the correct explicit bound and this Tron port lacks it.

### Recommendation
Mirror the mainline EVM implementation: read `_orders[commitment][token]` into a local, `require`/revert if `amount > escrowed`, and compute the decrement from that local before any external transfer:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
if (amount > escrowed) revert InvalidInput(); // add explicit bound
_orders[body.commitment][token] = escrowed - amount;
```
Perform the storage write before the external call/transfer (checks-effects-interactions) rather than after, closing both the missing-bound gap and the reentrancy-ordering concern in the same fix.

### Proof of Concept
Not independently reproducible from the available index — the trigger requires a `WithdrawalRequest.amount` value that already exceeds the tracked `_orders[commitment][token]` balance, and I was unable to locate a concrete unprivileged path in this codebase that produces such a mismatched `amount` (both entry points, `onAccept`'s `authenticate()` and `onGetResponse`'s storage-proof check, restrict who can trigger `withdraw()`). This is flagged as a structural/defense-in-depth gap versus the hardened EVM-mainline `IntentsBase._withdraw`, not a fully demonstrated exploit.
