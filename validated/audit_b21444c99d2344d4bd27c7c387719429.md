## Title
Silent, unconfirmed rewrite of a repository's git remote URL from an untrusted GitHub API field can redirect future pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` compares the `clone_url` field of a `IAPIRepository` object (data fetched from a GitHub/GHES API) against the locally configured git remote, and if a narrow set of structural checks pass, it silently rewrites the local `origin` remote URL via `gitStore.setRemoteURL`, with no user confirmation. The equality check used to decide "has the API's clone_url actually changed" (`urlMatchesRemote`) only compares hostname, owner and name (case-insensitively), not the full URL. This mirrors the CometBFT bug class: two representations of the same object are compared for consistency, but the comparison is incomplete, so a value that should have been rejected/flagged is instead silently adopted into critical state (here, the git remote that drives future push/fetch targets) — exactly the "invalid state adopted because the equality check was too narrow" pattern from ASA-2024-009.

### Finding Description
`updateRemoteUrl` is invoked with a `GitHubRepository` and the corresponding `IAPIRepository` returned by the API: [1](#0-0) 

The logic:
1. Reads `apiRepo.clone_url` (`updatedRemoteUrl`) — a value that originates entirely from the API response, i.e. from the GitHub/GHES server.
2. Confirms the *scheme* hasn't changed (`protocolsMatch`).
3. Confirms the *previously cached* `gitHubRepository.cloneURL` still structurally matches the *current* local remote (`remoteUrlUnchanged`), using `urlMatchesRemote`.
4. If both hold and the new `updatedRemoteUrl` doesn't already match the local remote, it calls `gitStore.setRemoteURL(...)`, writing the new URL into `.git/config` for that remote — with no dialog, no diff shown to the user, and no way to decline.

The consistency check `urlMatchesRemote`/`repositoryMatchesRemote` only validates hostname + owner + name, not the full URL (path, credentials, query, or subgroup segments): [2](#0-1) 

This is structurally identical to the CometBFT flaw: a "trusted enough" comparison between two representations of state (there: two RPC endpoints' validator sets; here: cached vs. freshly-fetched API repo data) is used to gate acceptance of new state, but the comparison omits fields/structure that matter for the value actually being adopted. In CometBFT, `ProposerPriority` wasn't checked even though it's part of the accepted `State`. Here, only hostname/owner/name are checked even though the full `clone_url` string (which may include host aliases, different casing normalized, or, on GHES with custom domains, effectively different endpoints) is what actually gets written to the git config and used for all subsequent `push`/`fetch`/`pull` operations.

The code comment in `performPush`/`app-store.ts` around `safeRemote` explicitly acknowledges the sensitivity and fragility of remote-name/URL consistency in this codebase, underscoring that a mismatch here is a recognized risk class, not a hypothetical one: [3](#0-2) 

### Impact Explanation
If the GitHub API/GHES response (`IAPIRepository.clone_url`) can be influenced by an attacker-controlled server (e.g. a rogue/compromised GHES instance, or a request answered by a malicious proxy sitting in front of the API endpoint the user has configured Desktop to trust), Desktop will automatically rewrite the user's `origin` remote to a URL that still passes the coarse hostname/owner/name check yet differs from what the user configured. Because the write happens silently, the user has no signal that their next `git push` may go to a different destination than they believe, or that fetched refs originate elsewhere — matching the "silent corruption of what the user commits or pushes" impact category. This is a medium-severity issue because exploitation depends on control over the API response Desktop trusts (e.g., GHES instance compromise or MITM of the API channel), similar to ASA-2024-009 requiring control of RPC endpoints used for state sync.

### Likelihood Explanation
Likelihood is limited because it requires the attacker to control or corrupt the API response used to populate `IAPIRepository`, not merely a git remote or clone content — narrower than the "attacker controls a cloned repo" case, but squarely within "attacker controls a GitHub API object." For GitHub Enterprise Server users pointed at a compromised/malicious instance, or any MITM position on the API traffic, this path executes automatically during a normal repository refresh with no user interaction beyond having the repository open, which is the same "used to be safe, but a subtly incomplete validation of remote server data now silently mutates trusted local state" profile in the original report.

### Recommendation
Do not silently persist `apiRepo.clone_url` into the local git config. At minimum:
- Require full-string (not just hostname/owner/name) comparison before treating the API-provided URL as "the same" as the previously cached one, and only rewrite when that full match indicates the API URL genuinely changed.
- Surface the change to the user (similar to the existing `UpstreamAlreadyExists` dialog pattern) before mutating the remote, rather than applying it automatically via `gitStore.setRemoteURL`.

### Proof of Concept
1. User has GitHub Desktop connected to a GHES instance (or an API endpoint reachable via an attacker-controlled network position).
2. Attacker causes the `/repos/:owner/:name` API response's `clone_url` field to point at attacker infrastructure while keeping the same hostname/owner/name segments Desktop checks (e.g. by altering only the path suffix, credentials, or an equivalent hostname alias not distinguished by `parseRemote`).
3. On the next repository refresh, `updateRemoteUrl` treats this as a legitimate "clone URL changed on GitHub, update local remote" event because `urlMatchesRemote` passes and `protocolsMatch` passes.
4. `gitStore.setRemoteURL` silently rewrites `origin` in `.git/config`.
5. Subsequent `git push`/`fetch` operations from Desktop are redirected without any user-visible confirmation.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
