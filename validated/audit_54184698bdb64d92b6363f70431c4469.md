Found it: `fillOrder` checks `_params.solverSelection` — a mutable, gateway-wide governance flag read fresh at fill time — rather than a per-order flag fixed at `placeOrder` time. This is the same broken-invariant class as the Llama report: an action's security-critical execution semantics (there: call vs delegatecall; here: whether solver-authorization is enforced) is not fixed at commitment time but is determined by a separate mutable global state that can be flipped by an unrelated governance action (`UpdateParams`) after the order has already been placed/committed.

### Title
Order execution authorization (`solverSelection`) is a mutable global flag, not bound to the order at placement time - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`Order.session` is set by the user at `placeOrder` time expecting solver-authorization enforcement, but whether that enforcement is actually applied at `fillOrder` time depends entirely on the current value of `_params.solverSelection`, a single governance-controlled flag shared by every order on the gateway.

### Finding Description
When a user calls `placeOrder`, they can set `order.session` to a disposable session-key address, intending that only a solver they explicitly authorize via `select()` can fill the order [1](#0-0) . However, `fillOrder` only enforces this binding when `_params.solverSelection` is `true` at the moment of the fill call: [2](#0-1) 

`_params.solverSelection` is not part of the order struct and is not fixed at `placeOrder` time — it is read live from mutable gateway-wide storage. It can be changed at any time via `onAccept`'s `UpdateParams` request kind, which is a cross-chain governance action driven by Hyperbridge/its governance signers, entirely independent of the individual order and its user-chosen `session` key: [3](#0-2) 

This mirrors the Llama bug precisely: the user "approved" (placed) an order under the assumption that a specific security property (`session`-key-gated fills) would hold, but that property is actually controlled by unrelated global state that a different action (a governance `UpdateParams` message, with a completely different signer/authorization path than the order itself) can flip after the order is already resting in escrow. If `solverSelection` is turned off after orders were placed with the expectation of solver gating (e.g. temporarily toggled off for a migration, a misconfiguration, or a benign parameter update that also happens to include this field per the `ParamsUpdate` struct), any solver — not just the one authorized via `select()`/session-key signature — can call `fillOrder` directly and claim the order's output/beneficiary role, or race the intended solver.

### Impact Explanation
This can result in unauthorized execution/claiming of an order that the user explicitly restricted to a session-key-selected solver, since the intended protection is bypassed entirely once the flag is off, regardless of the order's own `session` field. Because `ParamsUpdate.params` is a wholesale struct replacement of `_params` (see `onAccept`), any governance update that doesn't carefully preserve `solverSelection` silently disables solver-authorization protection for all in-flight, already-placed orders relying on it — not just newly placed ones.

### Likelihood Explanation
This requires a legitimate `UpdateParams` governance message to be relayed with `solverSelection=false` (or any params struct that resets it), which is a normal, expected operational path (params updates happen for fee changes, dispatcher upgrades, etc. and reconstruct the entire `Params` struct). Since `ParamsUpdate` bundles unrelated fields (protocol fee, destination fees, dispatcher, price oracle) together with `solverSelection`, any operator/governance action targeting one field risks silently toggling this security-relevant flag for all pending orders, making accidental exposure plausible without any malicious relayer or prover assumption.

### Recommendation
Bind solver-selection enforcement to the order at `placeOrder` time (e.g., snapshot `_params.solverSelection` into the order/commitment, or make enforcement conditional on `order.session != address(0)` rather than the mutable gateway-wide flag) so that a later `UpdateParams` cannot retroactively change the authorization semantics of orders that are already escrowed and committed.

### Proof of Concept
1. Gateway is deployed with `_params.solverSelection = true`.
2. User calls `placeOrder` with `order.session = sessionKeyAddress`, escrowing input tokens, expecting only the solver they select via `select()` to be able to call `fillOrder`.
3. Before the order is filled, a governance `UpdateParams` request is processed via `onAccept`, replacing `_params` with a new `Params` struct where `solverSelection = false` (this can happen inadvertently as part of an unrelated fee/dispatcher update since `ParamsUpdate.params` fully overwrites `_params`) [3](#0-2) .
4. Any address can now call `fillOrder(order, options)` directly — the `_params.solverSelection` check in `fillOrder` is skipped entirely, bypassing the session-key authorization the user relied on when placing the order [4](#0-3) .
5. The order is filled by an unauthorized/unselected solver, defeating the protection the user assumed was locked in at order placement.
