### Title
Unauthenticated cross-chain bandwidth sponsorship allows an attacker to grief/evict a victim app's paid bandwidth via FIFO eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s purchase-credit path keys the `Allowance` FIFO subscription list by `(msg.chain, msg.app)` taken entirely from the attacker-supplied `BandwidthPurchaseMsg` body, not by `request.source` or any caller identity. Combined with the hard 1024-entry cap and unconditional oldest-first eviction in `push_subscription`, an unprivileged attacker can spam cheap Tier-1 purchases targeting any victim `(chain, app)` pair to evict that victim's already-paid, higher-value subscriptions, permanently destroying bandwidth the victim paid for and, once evicted subscriptions are gone, potentially throttling the victim to `GateError::Insufficient`/`NoAllowance` for legitimate cross-chain messages.

### Finding Description
`BandwidthManager.purchase()` in `evm/src/apps/BandwidthManager.sol` (lines 148-193) accepts arbitrary `app` and `chain` parameters from `msg.sender` with zero validation that the caller has any relationship to that app/chain — this is intentional to support "sponsorship" (buyer on chain A funding an app on chain B), as documented in `docs/content/developers/evm/bandwidth/overview.mdx` lines 108-114.

On the pallet side, `on_accept` in `modules/pallets/bandwidth/src/lib.rs` (lines 455-489) only validates that `request.from` matches the registered `BandwidthManager` for `request.source` [1](#0-0) . It never checks that `msg.chain`/`msg.app` (decoded from the attacker-controlled body) correspond to the actual payer or the actual source chain [2](#0-1) . The credited subscription is then pushed into the shared `Allowance` FIFO list keyed by that attacker-chosen `(chain, app)` via `push_subscription` [3](#0-2) .

`push_subscription` enforces a hard cap of 1024 entries (`MAX_SUBSCRIPTIONS`), and once the cap is hit, every new push unconditionally evicts index `0` — the oldest entry, in FIFO/insertion order — regardless of how much `remaining_bytes` it holds or who paid for it [4](#0-3) . This is exactly the "no on-chain validation of the write target + shared bounded accounting structure that silently discards old state" pattern from the external report's `Counter` bug: an unprivileged actor performs a low-cost operation (a single cheap Tier-1, 1-month purchase, priced independently of the victim's tier) that mutates shared state belonging to a different, unrelated party, and the existing bound/overflow-style guard (the 1024 cap) is what actually causes the loss, rather than preventing it.

An attacker who wants to grief a specific victim `(app_chain, app)` pair only needs to:
1. Call `purchase()` on any already-deployed, already-registered `BandwidthManager` (no attacker deployment or governance action required — these contracts are public storefronts by design) with `app = victim_app`, `chain = victim_chain`, `tier = TierOne` (cheapest configured SKU), `months = 1`.
2. Repeat until the victim's bucket reaches the 1024 cap and then keep pushing until every subscription the victim actually paid for (inserted earlier, hence at the front of the FIFO) has been evicted.

Each eviction emits `SubscriptionEvicted { lost_bytes, ... }` [5](#0-4)  — the code even self-documents that this is "what the user paid for and won't get to use," but nothing prevents an unrelated third party from being the one who triggers it against someone else's bucket.

### Impact Explanation
This is a loss-of-funds / logic attack against a live, in-scope pallet: it lets any unprivileged EVM account permanently destroy bandwidth another app already paid real fee-token money for (`Loss of funds`), and — once bandwidth is drained below what the app needs — causes legitimate ISMP messages from that app to be rejected by `BandwidthGate::try_consume` (`GateError::NoAllowance`/`Insufficient`) [6](#0-5) , i.e., denial of service on the victim's cross-chain message flow, which is functionally equivalent to the DoS described in the source report. No malicious relayer, prover, admin, or governance actor is needed — only an unprivileged attacker interacting with public, permissionless `purchase()` entrypoints.

### Likelihood Explanation
High. `purchase()` is a public, permissionless entrypoint on an already-deployed contract; the attacker pays only the cheapest configured tier price per call and needs no special privileges, keys, or off-chain trust assumptions. The cost scales linearly with the number of pushes needed to overtake the victim's existing subscription count, which is bounded and knowable on-chain (`Pallet::allowances`/`remaining` are public read functions), making the attack fully plannable and executable by any address holding the fee token.

### Recommendation
Bind the credited bucket to the paying identity or otherwise authenticate `msg.chain`/`msg.app` before allowing a write into another party's `Allowance` entry, e.g.:
- Require `msg.chain == request.source` unless the caller supplies a governance/allowlisted "sponsor" flag, restricting arbitrary cross-chain crediting to an explicit opt-in relationship (e.g., only the app owner or a registered sponsor list can top up a given `(chain, app)`).
- Alternatively, evict by `remaining_bytes`/value-at-risk instead of strict insertion order, or size/weight the eviction cost so that displacing already-paid-for capacity costs the attacker at least as much as the value destroyed (e.g., reject a push if it would evict a subscription with more remaining bytes than the new one grants), closing the low-cost-griefs-high-value gap.

### Proof of Concept
1. Governance configures `TierOne` with a small `(bytes, duration_secs)` and a nonzero but cheap price; `TierFour` (or any tier) is used by the victim to buy substantial bandwidth for `app = VICTIM_APP` on `chain = "EVM-X"`.
2. Attacker (unprivileged, holding the fee token) repeatedly calls `BandwidthManager.purchase(app: VICTIM_APP, tier: TierOne, months: 1, chain: "EVM-X")` from the manager registered on any source chain that talks to the same `pallet-bandwidth` instance.
3. Each relayed purchase message passes `on_accept`'s only check (`request.from == registered manager`) and calls `push_subscription(&"EVM-X", &VICTIM_APP, TierOne, ...)` [7](#0-6) .
4. Once `Allowance::<T>::get("EVM-X", VICTIM_APP).len() == 1024`, each subsequent attacker purchase evicts index `0` [4](#0-3) ; enough repetitions evict all of the victim's real, paid-for subscriptions, emitting `SubscriptionEvicted` for each with the victim's `lost_bytes`.
5. Subsequent legitimate ISMP dispatches from `VICTIM_APP` on `"EVM-X"` fail the gate (`GateError::NoAllowance`) at `BandwidthGate::try_consume` [8](#0-7) , denying the victim's cross-chain messaging despite having paid for bandwidth.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}

/// Why the gate refused a request. Surfaces back to the ISMP router.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum GateError {
	/// The app has no live subscriptions on `(chain, app)`.
	NoAllowance,
	/// Live subscriptions exist but the sum of `remaining_bytes` is
	/// short of what the message needs. The gate makes no mutation in
	/// this case — the caller can retry after a top-up.
	Insufficient { remaining: u128, required: u128 },
}

impl core::fmt::Display for GateError {
	fn fmt(&self, f: &mut core::fmt::Formatter<'_>) -> core::fmt::Result {
		match self {
			GateError::NoAllowance => f.write_str("no bandwidth allowance"),
			GateError::Insufficient { remaining, required } => {
				write!(f, "insufficient bandwidth: have {remaining} bytes, needed {required}")
			},
		}
	}
}
