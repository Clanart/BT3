### Title
Native token value sent to non-payable Staking/Distribution/Gov precompile methods is permanently stranded with no recovery path - (File: precompiles/staking/staking.go, precompiles/distribution/distribution.go, precompiles/common/precompile.go)

### Summary
The `ArmadaTreasuryGov` report describes funds that become permanently unrecoverable because the contract has no function to move out a specific asset (ETH) and, being non-upgradeable, can never gain one. The Cosmos EVM analog is that several stateful precompiles (staking, distribution, gov, slashing, bank) expose non-payable transaction methods but do not reject `msg.value`, unlike the `erc20` precompile, which explicitly does. Native coin sent alongside a call to one of these non-payable methods is absorbed into the EVM/state balance of the fixed precompile address, but none of these precompiles implement any method that can move that balance back out. Because precompile addresses are fixed, code-less, and cannot be upgraded like a normal contract, any coin that lands there is permanently frozen.

### Finding Description
The `erc20` precompile explicitly guards against this class of bug: [1](#0-0) 

The comment makes the invariant explicit: "ERC20 precompiles cannot receive funds because they are not managed by an EOA and will not be possible to recover funds sent to an instance of them."

However, other stateful precompiles that share the exact same `RunNativeAction`/`Execute` dispatch pattern do not have this guard. The `staking` precompile's `Execute` dispatches to methods like `EditValidator`, `Undelegate`, `Redelegate`, and `CancelUnbondingDelegation` without any check on `contract.Value()`: [2](#0-1) 

Only `Delegate` and `CreateValidator` are designed to consume `contract.Value()`; the rest do not. Similarly, `distribution` precompile methods such as `SetWithdrawAddress`, `WithdrawDelegatorReward`, `WithdrawValidatorCommission`, and `ClaimRewards` are not designed to accept `msg.value` at all.

In the shared dispatch path `precompiles/common/precompile.go`, `SetupABI`/`emptyCallData`/`standardCallData` only branch on calldata length and whether a receive/fallback exists in the ABI — they place no restriction on `contract.Value()` for named-method calls: [3](#0-2) 

Under normal go-ethereum `Call` semantics, a `CALL` with `value > 0` and calldata (e.g., `abi.encodeWithSelector(Staking.editValidator.selector, ...)`) transfers native coin into the callee's account balance before the precompile's `Run` executes, regardless of whether that callee is a precompile. For precompiles like `werc20`/`erc20` there is explicit logic to reject or forward the value back (`Deposit` sends coins back via bank keeper). For `staking`'s non-payable methods, `distribution`, `gov`, `slashing`, and `bank` precompiles, no such counter-transfer or rejection exists, so the value silently remains credited to the fixed precompile address in the EVM/bank-synchronized balance.

Since precompile contract addresses (e.g. `0x...800`-series `StakingPrecompileAddress`, `DistributionPrecompileAddress`) have no associated Solidity code and are wired directly into the EVM's native precompile registry rather than being deployed/upgradeable contracts, there is no governance or user action that can later add a "sweep"/"withdraw" method for coins accidentally routed there — mirroring the `ArmadaTreasuryGov` situation of a non-upgradeable contract lacking a distribution path for an asset it can passively receive.

### Impact Explanation
Any unprivileged user (or a malicious/naively-written contract forwarding `msg.value` while making a staking/distribution call) can cause native coin to be irreversibly locked at a fixed, code-less precompile address. This is a permanent freezing/locking of user funds with no possible recovery — matching the Critical impact class of "permanent freezing, locking, theft, or unauthorized extraction of user funds... or token-pair-backed balances" defined in the allowed impact gate. Because the precompile is a protocol-level fixed address rather than an upgradeable contract, there is no governance-only remediation path (a hard fork/binary upgrade would be required), which is a stronger version of the non-upgradeability problem cited in the original report.

### Likelihood Explanation
Triggering this requires only an ordinary EVM transaction/contract call with a nonzero `value` field targeting a non-payable-designed method on one of the affected precompiles — no privileged role, validator, or relayer involvement is needed. The likelihood of accidental triggering is non-trivial (e.g., a wallet/dApp that reuses a "send value with call" pattern for staking helper contracts), and it is trivially triggerable intentionally by any user wanting to demonstrate the bug.

### Recommendation
Add the same guard used in `precompiles/erc20/erc20.go` (`Execute` rejecting `contract.Value().Sign() == 1`) to every precompile method that is not explicitly designed to consume `contract.Value()` (i.e., all `staking` methods except `Delegate`/`CreateValidator`, and all `distribution`, `gov`, `slashing`, and `bank` precompile methods). Alternatively, add a global check in `precompiles/common/precompile.go`'s dispatch path that rejects any call carrying `value > 0` unless the specific method opts in, so the omission can't recur for new precompiles.

### Proof of Concept
1. Deploy or use an existing contract, or send an EVM transaction directly, that calls the `distribution` precompile's `setWithdrawAddress(address, string)` (or `staking`'s `editValidator`, `undelegate`, `redelegate`, `cancelUnbondingDelegation`) while attaching `value > 0` (e.g. `distribution.call{value: 1 ether}(abi.encodeWithSelector(SET_WITHDRAW_ADDRESS_SELECTOR, ...))`).
2. Observe that the call succeeds (the method logic does not reference or reject `contract.Value()`).
3. Query the native balance of the precompile's fixed address (`DistributionPrecompileAddress`/`StakingPrecompileAddress`) after the call — the sent value is now credited there.
4. Confirm no existing precompile method (staking, distribution, gov, slashing, bank) can withdraw/sweep balance held at these fixed precompile addresses, and that these addresses cannot be redeployed or upgraded to add such logic without a chain-wide binary upgrade.

Note: I was not able to fully inspect `precompiles/common/balance_handler.go` (`BeforeBalanceChange`/`AfterBalanceChange`) before running out of tool calls, which is the component responsible for reconciling EVM `stateDB` balance mutations with the Cosmos `x/bank` balances after a precompile call. It is possible (though not confirmed) that this handler contains logic that reverts or redirects unexpected balance deltas on the precompile's own address, which would mitigate or fully prevent the scenario described above. This should be verified against `precompiles/common/balance_handler.go` before treating this finding as fully confirmed.

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch method.Name {
	// Staking transactions
	case CreateValidatorMethod:
		bz, err = p.CreateValidator(ctx, contract, stateDB, method, args)
	case EditValidatorMethod:
		bz, err = p.EditValidator(ctx, contract, stateDB, method, args)
	case DelegateMethod:
		bz, err = p.Delegate(ctx, contract, stateDB, method, args)
	case UndelegateMethod:
		bz, err = p.Undelegate(ctx, contract, stateDB, method, args)
	case RedelegateMethod:
		bz, err = p.Redelegate(ctx, contract, stateDB, method, args)
	case CancelUnbondingDelegationMethod:
		bz, err = p.CancelUnbondingDelegation(ctx, contract, stateDB, method, args)
	// Staking queries
	case DelegationMethod:
		bz, err = p.Delegation(ctx, contract, method, args)
	case UnbondingDelegationMethod:
		bz, err = p.UnbondingDelegation(ctx, contract, method, args)
	case ValidatorMethod:
		bz, err = p.Validator(ctx, method, contract, args)
	case ValidatorsMethod:
		bz, err = p.Validators(ctx, method, contract, args)
	case RedelegationMethod:
		bz, err = p.Redelegation(ctx, method, contract, args)
	case RedelegationsMethod:
		bz, err = p.Redelegations(ctx, method, contract, args)
	default:
		return nil, fmt.Errorf(cmn.ErrUnknownMethod, method.Name)
	}

	return bz, err
}

// emptyCallData is a helper function that returns the method to be called when the calldata is empty.
func emptyCallData(api abi.ABI, contract *vm.Contract) (method *abi.Method, err error) {
	switch {
	// Case 1.1: Send call or transfer tx - 'receive' is called if present and value is transferred
	case contract.Value().Sign() > 0 && api.HasReceive():
		return &api.Receive, nil
	// Case 1.2: Either 'receive' is not present, or no value is transferred - call 'fallback' if present
	case api.HasFallback():
		return &api.Fallback, nil
	// Case 1.3: Neither 'receive' nor 'fallback' are present - return error
	default:
		return nil, vm.ErrExecutionReverted
	}
}

// methodIDCallData is a helper function that returns the method to be called when the calldata is less than 4 bytes.
func methodIDCallData(api abi.ABI) (method *abi.Method, err error) {
	// Case 2.2: calldata contains less than 4 bytes needed for a method and 'fallback' is not present - return error
	if !api.HasFallback() {
		return nil, vm.ErrExecutionReverted
	}
	// Case 2.1: calldata contains less than 4 bytes needed for a method - 'fallback' is called if present
	return &api.Fallback, nil
}

// standardCallData is a helper function that returns the method to be called when the calldata is 4 bytes or more.
func standardCallData(api abi.ABI, contract *vm.Contract) (method *abi.Method, err error) {
	methodID := contract.Input[:4]
	// NOTE: this function iterates over the method map and returns
	// the method with the given ID
	method, err = api.MethodById(methodID)

	// Case 3.1 calldata contains a non-existing method ID, and `fallback` is not present - return error
	if err != nil && !api.HasFallback() {
		return nil, err
	}

	// Case 3.2: calldata contains a non-existing method ID - 'fallback' is called if present
	if err != nil && api.HasFallback() {
		return &api.Fallback, nil
	}

	return method, nil
}
