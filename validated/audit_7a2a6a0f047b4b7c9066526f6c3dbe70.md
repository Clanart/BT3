### Title
Unhandled `IndexError` from malformed length-prefix parsing during mempool canonical-CLVM check crashes spend-bundle validation - (File: chia/full_node/mempool_manager.py)

### Summary
`MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical()` on the raw, attacker-supplied `puzzle_reveal` and `solution` bytes of every coin spend in a submitted `SpendBundle`, before any other structural validation of those bytes has occurred beyond what the Rust CLVM runner already accepted. `is_clvm_canonical()` in turn calls `is_atom_canonical()`, which manually decodes CLVM atom length-prefixes by indexing into the raw `bytes` buffer without ever checking that enough bytes remain in the buffer to satisfy the prefix length it just read. [1](#0-0) [2](#0-1) 

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the atom-length prefix byte at `offset`, determines a `prefix_len` of 0–5 additional bytes based on the top bits of that byte, then unconditionally loops `prefix_len` times doing `offset += 1; atom_len |= clvm_buffer[offset]` with no bounds check against `len(clvm_buffer)`. [3](#0-2) 

`is_clvm_canonical(clvm_buffer)` walks the buffer token by token and, whenever it encounters a byte `> 0x80` (a long-form atom), calls `is_atom_canonical(clvm_buffer, offset)` at the last possible offset in the buffer — i.e., the length-prefix byte can legitimately be the very last byte of the buffer. [4](#0-3) 

If an attacker crafts a `puzzle_reveal` or `solution` whose bytes end exactly on (or just short of) a multi-byte atom length-prefix header — e.g. a trailing `0xC0` byte (5+8 bit prefix, `prefix_len=1`) with no following byte — `clvm_buffer[offset]` raises a Python `IndexError` instead of returning a controlled `False`/`ValueError`. This is the direct Python analog of the CVE's C/C++ integer-overflow-driven out-of-bounds read: the code computes a length/offset from attacker data and reads past the buffer without a bounds check, only here Python's runtime turns the out-of-bounds access into an uncaught exception rather than silent heap corruption.

This is reachable by any unprivileged party who can submit a spend bundle to the mempool: `validate_spend_bundle()` invokes `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` / `is_clvm_canonical(bytes(coin_spend.solution))` directly on the submitted spend's byte content before catching such an error. [5](#0-4) 

`validate_spend_bundle()` is called from `add_spend_bundle()`, which has no `try/except` around the call — any exception raised inside `validate_spend_bundle()` (including this `IndexError`) propagates uncaught out of `add_spend_bundle()`. [6](#0-5) 

The project's own test suite documents that `is_clvm_canonical`/`is_atom_canonical` are directly exercised by malformed/non-canonical CLVM buffers as part of mempool admission validation, and that malformed canonical-encoding inputs are expected to be turned into a controlled `Err.INVALID_COIN_SOLUTION`, not an unhandled exception — confirming this code path is a designed validation gate for untrusted input, not a defensive-only internal helper. [7](#0-6) 

### Impact Explanation
An attacker who can submit a spend bundle to a full node's mempool (a completely unprivileged action, e.g. via the RPC/wallet-protocol `send_transaction` or gossip) can trigger an uncaught `IndexError` deep in `MempoolManager.validate_spend_bundle()` by crafting a `puzzle_reveal` or `solution` whose bytes truncate exactly inside a multi-byte CLVM atom length prefix. Because `add_spend_bundle()` has no exception guard around `validate_spend_bundle()`, this propagates upward through the mempool admission pipeline. Depending on how the calling task/coroutine handles unexpected exceptions (e.g., background task exception swallowing vs. crashing the full-node event loop or admission task), this can at minimum cause a transaction-processing halt for that spend bundle path and, in the worst case if unhandled at a higher level, disrupt block-building/mempool processing — a spend-triggered denial-of-service, matching the "crash an application" impact of the original OpenEXR CVE.

### Likelihood Explanation
Likelihood is high for reachability: any wallet user or spend-bundle submitter fully controls the bytes of `puzzle_reveal` and `solution`, and constructing a buffer that ends exactly on a multi-byte atom-length prefix byte (e.g., a trailing `0xC0`, `0xE0`, `0xF0`, `0xF8`, or `0xFC` byte with insufficient trailing bytes) is trivial and requires no special privileges, cryptographic material, or race condition.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access in the prefix-reading loop (and before the initial `clvm_buffer[offset]` read in `is_clvm_canonical()`'s loop as well), raising a handled `ValueError`/returning `False` when the buffer is too short, mirroring the defensive bounds checks already used in `chia/full_node/full_block_utils.py` (`skip_bytes`, `skip_list`, `generator_from_block`, etc.). Additionally, wrap the call to `is_clvm_canonical()` in `validate_spend_bundle()` (or catch broadly around `validate_spend_bundle()` in `add_spend_bundle()`) so any parsing exception is converted into a normal `Err.INVALID_COIN_SOLUTION` rejection rather than an unhandled exception.

### Proof of Concept
1. Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) serialized bytes end with a truncated multi-byte atom header, e.g. append a single trailing byte `0xC0` (indicating a 5+8-bit length prefix, requiring one more byte that is absent) as the final byte of an otherwise valid list-terminated CLVM buffer.
2. Submit a `SpendBundle` containing this `CoinSpend` to a full node (e.g., via `send_transaction`/gossip so it reaches `MempoolManager.add_spend_bundle()` → `validate_spend_bundle()`).
3. During iteration, `is_clvm_canonical()` reaches offset pointing at the trailing `0xC0` byte and calls `is_atom_canonical(clvm_buffer, offset)`; inside the `prefix_len` loop, `offset += 1; atom_len |= clvm_buffer[offset]` indexes one byte past the end of the buffer, raising `IndexError: index out of range`, uncaught by `validate_spend_bundle()`/`add_spend_bundle()`. [3](#0-2) 

Note: I was not able to trace the exact top-level exception handling of the full-node message-processing task that invokes `add_spend_bundle()` (e.g., whether an outer generic `try/except` in RPC/protocol handling code catches and logs all exceptions, which would reduce this to a per-request failure rather than a broader halt) within the available indexed context; this would need to be confirmed with a live Devin session tracing the full call chain from the wallet-protocol/RPC entry point through to `add_spend_bundle()`.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
