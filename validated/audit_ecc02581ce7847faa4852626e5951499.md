### Title
Post-transfer ERC20 conversion failure returns Error Acknowledgement after coins already committed, causing double-credit across chains - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
The ERC20 IBC middleware performs ERC20 auto-conversion as a *post-processing* step that runs **after** the base ICS20 transfer application has already committed the coin mint/unescrow to the recipient's bank balance on the uncached `ctx`. If the post-processing conversion step (`MintingEnabled` or `ConvertCoinNativeERC20`) fails, the middleware returns an `ErrorAcknowledgement`, signaling packet failure to the relayer/source chain. Because the failure occurs strictly after the coin credit was already committed to state (not inside a cached/reverted context), the destination chain retains the credited bank coin balance for the recipient while the source chain, upon receiving the error acknowledgement, will refund/un-escrow the same amount back to the original sender. This produces two spendable balances from a single transfer.

### Finding Description
The transfer stack composition is: `channel.RecvPacket -> callbacks.OnRecvPacket -> erc20.OnRecvPacket -> transfer.OnRecvPacket` [3](#0-2) . `erc20.IBCMiddleware.OnRecvPacket` first calls the inner transfer app's `OnRecvPacket` (which performs the actual ICS20 mint/unescrow into the recipient's bank account, using the normal, non-cached `ctx`), and only proceeds to `im.keeper.OnRecvPacket` if that inner call succeeded [1](#0-0) .

`Keeper.OnRecvPacket` in `x/erc20/keeper/ibc_callbacks.go` then attempts to auto-convert the just-credited bank coin into its ERC20 representation via `MintingEnabled` and `ConvertCoinNativeERC20`. Both of these can fail for reasons unrelated to the validity of the transfer itself — e.g. a self-destructed/invalid ERC20 contract behind the token pair, minting restrictions, or any EVM execution failure inside `ConvertCoinNativeERC20`. When either fails, the function returns `channeltypes.NewErrorAcknowledgement(err)` [4](#0-3) .

This differs qualitatively from the analogous send-side function `ConvertCoinToERC20FromPacket`, whose doc comment explicitly acknowledges that a conversion failure must NOT fail the overall operation, instead leaving the user with the bank token: *"If the ERC20 conversion fails for whatever reason ... OnAcknowledgementPacket/OnTimeoutPacket still succeeds, but the user receives the corresponding bank token from the TokenPair instead."* [5](#0-4)  — and indeed that function swallows the conversion error and returns `nil` rather than propagating an acknowledgement failure [6](#0-5) .

`OnRecvPacket`, however, does not follow this same safe pattern for two of its failure branches (`MintingEnabled` error and `ConvertCoinNativeERC20` error): it returns an error acknowledgement instead of falling back to leaving the recipient with the bank coin, even though the bank coin has *already* been irreversibly credited by the inner transfer call that ran before it in the same, uncached context.

This exactly mirrors the `onERC721Received` bug class: an asset (the NFT / here, the IBC coin) is already transferred/credited to the recipient by the time a subsequent "did this succeed" decision point is reached, but that later decision (revert due to bad `data.length` / conversion failure) does not — and structurally cannot — undo the earlier state change, since it's not wrapped in a cached context that gets rolled back before the acknowledgement is decided.

### Impact Explanation
This causes unauthorized duplication of spendable value across chains: the destination chain keeps the newly-minted/unescrowed bank coin balance for the recipient (since that commit happened in the base uncached `ctx` before the erc20 middleware ran), while the source chain, upon receiving the resulting error acknowledgement, will refund the sender by un-escrowing (source-native) or minting back (source-voucher) the same amount. The net effect is that the same value exists as spendable balance on both chains simultaneously — a duplication/accounting-corruption of user value across native balances and IBC escrows, matching the Critical impact category for "unauthorized minting, burning, duplication ... of spendable user value ... across native balances ... [or] IBC escrows."

### Likelihood Explanation
Triggering `MintingEnabled` or `ConvertCoinNativeERC20` failure is plausible and partly attacker-controllable: any user can cause `ConvertCoinNativeERC20` to fail post-hoc (e.g. by having previously self-destructed/broken behavior in a native ERC20 contract used as the counterparty of a registered token pair, by exhausting the EVM call in some contract-specific way, or via any of the various EVM-call failure conditions already documented in that function, such as unexpected `Approval` events or balance-invariance mismatches). Because a relayer/receiver does not control which token pairs exist or their underlying contract's behavior, and the conversion step runs unconditionally for every registered native-ERC20-denominated inbound transfer, this is reachable through ordinary transaction flow without any privileged access.

### Recommendation
`Keeper.OnRecvPacket` should never return an error acknowledgement once the underlying transfer's coin credit has already been committed to `ctx`. For the failure branches currently returning `channeltypes.NewErrorAcknowledgement(err)` (the `MintingEnabled` error and the `ConvertCoinNativeERC20` error in the "native ERC20" case), the function should instead emit a failure event and return the original success `ack` unmodified — exactly as `ConvertCoinToERC20FromPacket` already does for equivalent failures — leaving the recipient with the bank-denominated coin instead of attempting (and failing) the ERC20 conversion. Alternatively, perform the entire mint + conversion sequence inside a single cached context that is only written back atomically if conversion succeeds, and only return the ordinary success acknowledgement in the fallback (unconverted) case.

### Proof of Concept
1. Register a native ERC20 token pair for a Cosmos SDK denom, where the ERC20 contract can be made to fail on `transfer` calls post-registration (e.g., self-destructed, or the token pair address code changes such that `ConvertCoinNativeERC20`'s expected-balance invariance check at `x/erc20/keeper/msg_server.go:290-297` fails).
2. Initiate an ICS20 transfer of that denom from a counterparty chain to a recipient on the EVM chain.
3. `transfer.OnRecvPacket` runs first via the middleware stack and credits the recipient's bank balance for the denom (committed to the non-cached `ctx`) [7](#0-6) .
4. `erc20.Keeper.OnRecvPacket` then calls `ConvertCoinNativeERC20`, which fails due to the broken contract; `OnRecvPacket` returns `channeltypes.NewErrorAcknowledgement(err)` [8](#0-7) .
5. The relayer submits this error acknowledgement to the source chain, causing the source chain to refund/un-escrow the sender's original amount.
6. Result: the recipient on the destination chain retains the bank coin balance credited in step 3, and the sender on the source chain also regains their original balance — the same value now exists on both chains.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
