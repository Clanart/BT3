### Title
`ReceivedOutput::read` accepts outputs whose script cannot be spent with the encoded offset - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
**Medium severity.** `ReceivedOutput` is documented as “a spendable output,” but `ReceivedOutput::read` decodes an offset, `TxOut`, and `OutPoint` without verifying that the offset actually unlocks the output’s `script_pubkey`. [1](#0-0) [2](#0-1) 

### Finding Description
Legitimate `ReceivedOutput` values are produced by `Scanner::scan_transaction`, which first matches `output.script_pubkey` against the scanner’s registered script/offset map. [3](#0-2)  The deserializer does not preserve that invariant: it accepts any canonical scalar followed by any consensus-decodable `TxOut` and `OutPoint`, returning them as a valid `ReceivedOutput`. [2](#0-1)  Because `ReceivedOutput` does not serialize the base key needed to check the offset/script relationship, standalone deserialization cannot detect inconsistent encodings.

### Impact Explanation
`ReceivedOutput::value` reports the attacker-chosen Bitcoin amount even when the attached script is unspendable or belongs to a different key. [4](#0-3)  When the output is later used for signing, `SignableTransaction::multisig` derives `keys.clone().offset(offset).group_key()`, builds its expected P2TR script, and returns `None` when it does not equal the encoded output’s `script_pubkey`. [5](#0-4)  The result is funds reported as received that cannot actually be spent through the expected wallet path.

### Likelihood Explanation
Any path that feeds attacker-controlled serialized data to `ReceivedOutput::read` can trigger this with a consensus-valid transaction output. [2](#0-1)  The malformed object can enter balance, accounting, or transaction-construction logic before the later signing-time script check rejects it. [5](#0-4) 

### Recommendation
Do not expose a standalone `ReceivedOutput::read` for untrusted data unless the expected wallet key or script context is also supplied. Add a checked API such as `ReceivedOutput::read_for_key` or `Scanner::read_output` that rejects values where `p2tr_script_buf(key + GENERATOR * offset) != output.script_pubkey`. [6](#0-5) [2](#0-1) 

### Proof of Concept
The following encoding contains scalar `0`, a 50,000-sat `TxOut` with an unspendable `OP_RETURN` script, and an arbitrary `OutPoint`:

```text
00 * 32                                   # offset = 0
50 c3 00 00 00 00 00 00                   # TxOut.value = 50,000
01                                        # script length
6a                                        # OP_RETURN
11 * 32                                   # arbitrary txid
00 00 00 00                               # vout = 0
```

`ReceivedOutput::read` accepts it because it only decodes the three fields and performs no offset/script validation. [2](#0-1)  Consequently, `value()` reports `50_000`, while the non-P2TR `OP_RETURN` script cannot satisfy the signing path’s expected-script comparison. [4](#0-3) [5](#0-4)
