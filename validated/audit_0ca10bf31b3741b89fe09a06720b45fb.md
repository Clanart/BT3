### Title
Nil-pointer panic when converting an unsigned/malformed EIP-7702 `SetCodeTx` with empty `To` to Ethereum transaction data - ([File: x/evm/types/ethtx/set_code_tx.go])

### Summary
`SetCodeTx.Validate()` never enforces that the `To` field is non-empty, but `SetCodeTx.AsEthereumData()` unconditionally dereferences `tx.GetTo()`, which returns `nil` when `To == ""`. This mirrors the CVE-2016-3071 bug class: a specific, syntactically-valid-but-semantically-invalid transform/field combination sails through validation and later crashes the parser/daemon when it is processed.

### Finding Description
`SetCodeTx.Validate()` only checks the address format *if* `tx.To` is non-empty: [1](#0-0) 
It never rejects an empty `To`, unlike EIP-7702's real-world semantics (a `SetCodeTx`/type-4 transaction must always specify a `to` address; it cannot be a contract-creation transaction).

`GetTo()` correctly returns `nil` for an empty `To`: [2](#0-1) 

But `AsEthereumData()` unconditionally dereferences that pointer: [3](#0-2) 
specifically `To: *tx.GetTo()` at line 133 — a nil-pointer dereference panic if `To` is empty.

Because `SetCodeTx` is a registered `ethtx.TxData` interface implementation and `MsgEVMTransaction.Data` is a protobuf `Any`, a transaction sender does **not** need to go through `NewSetCodeTx(tx *ethtypes.Transaction)` (which is only used when converting from a real `go-ethereum` `Transaction` object, and where `tx.To()` for a `SetCodeTx` type is enforced upstream by go-ethereum's own tx constructors). Instead, an attacker can hand-craft a `MsgEVMTransaction` whose `Data` Any directly wraps a `SetCodeTx` protobuf message with `To=""`, `GasTipCap`/`GasFeeCap` set, and a non-nil `AuthList`, and submit it as a raw Cosmos tx (or via the EVM JSON-RPC path that also constructs/parses `ethtx.TxData`).

`MsgEVMTransaction.ValidateBasic()` calls `txData.Validate()`, which — as shown above — accepts an empty `To`: [4](#0-3) 

`AsTransaction()` then calls `UnpackTxData` followed by `txData.AsEthereumData()`, triggering the panic: [5](#0-4) 

This method (`AsTransaction`) is invoked directly from the EVM ante `BasicDecorator`, which every EVM transaction passes through in the ante pipeline (both `CheckTx`/`DeliverTx` router and tracer paths): [6](#0-5) [7](#0-6) 

### Impact Explanation
`baseapp.runTx` in `sei-cosmos` wraps ante/message execution with a `recover()` (in `baseapp.go`/`abci.go`), so a panic hit during ordinary `CheckTx`/`DeliverTx` processing is typically converted into a failed-tx error rather than crashing the whole node. However, the same `AsTransaction()`/`AsEthereumData()` code path is also reachable from EVM RPC code (`evmrpc/tx.go`, `evmrpc/block.go`, `evmrpc/simulate.go`, `evmrpc/utils.go`) and from the mempool/prioritizer (`app/prioritizer.go`), which unpack and process `MsgEVMTransaction`/`ethtx.TxData` outside of `baseapp.runTx`'s panic-recovery boundary. If any of those call sites process a crafted `SetCodeTx` with an empty `To` without their own recovery, the resulting nil-pointer panic can propagate up through goroutines that are not gated by baseapp's recovery, which can crash the process serving CheckTx/mempool or a public RPC node.

I was not able to fully verify, given the remaining tool budget, whether every one of these call sites (`evmrpc/*`, `giga/deps/xevm/keeper/deferred.go`, `x/evm/keeper/deferred.go`, `x/evm/keeper/msg_server.go`) individually wraps this operation in its own `recover()`. This uncertainty is the main gap in confirming full node-crash severity vs. a merely-failed transaction; the vulnerable root cause (missing `To` validation + unconditional pointer dereference) is however clearly proven in `x/evm/types/ethtx/set_code_tx.go`.

### Likelihood Explanation
Trivial and fully attacker-controlled: any unprivileged party can construct a `MsgEVMTransaction` whose `Data` field directly encodes a `SetCodeTx` with `To=""` (bypassing go-ethereum's own transaction constructors) and submit it to any public RPC endpoint or directly as a Cosmos tx. No special privileges, signatures matching a real state, or preconditions are required beyond passing `ValidateBasic()`, which this input does.

### Recommendation
In `x/evm/types/ethtx/set_code_tx.go`, make `SetCodeTx.Validate()` reject an empty `To` (EIP-7702 requires `to != nil`), e.g.:
```go
if tx.To == "" {
    return errors.New("to address cannot be empty for a SetCodeTx")
}
```
Additionally, harden `AsEthereumData()` to avoid a raw pointer dereference regardless of validation (defense in depth), e.g. by checking `GetTo()` for nil and returning/erroring instead of panicking.

### Proof of Concept
1. Construct a `SetCodeTx` protobuf message with: `To: ""`, `GasTipCap`/`GasFeeCap` set to valid non-negative `sdk.Int`s, `ChainID` set, and a non-nil `AuthList`/`Accesses` (or nil, which also passes `validateAccessList`/`validateAuthList` if they allow nil).
2. Wrap it in `codectypes.Any` and set it as `MsgEVMTransaction.Data`.
3. Submit the resulting `MsgEVMTransaction` as a Cosmos transaction (or via the EVM JSON-RPC submission path that constructs/decodes `ethtx.TxData` directly).
4. `ValidateBasic()`/`SetCodeTx.Validate()` passes because `To == ""` is not rejected (`x/evm/types/ethtx/set_code_tx.go:214-218`).
5. When `msg.AsTransaction()` is invoked (e.g., from `x/evm/ante/basic.go:26-27`, or from RPC/mempool code paths outside `baseapp.runTx`'s recovery), `SetCodeTx.AsEthereumData()` executes `To: *tx.GetTo()` at `x/evm/types/ethtx/set_code_tx.go:133`, where `GetTo()` returns `nil`, causing a nil-pointer dereference panic.
