## Analysis Summary

Applying the bug-class seed (a component that is documented/expected to deliver one artifact but actually delivers/verifies something else, so the recipient ends up trusting the wrong object) to Aptos's publish path, I traced the `aptos move verify-package` CLI flow, which is explicitly documented as the mechanism for trusting deployed bytecode: *"For code review and reproducibility, `verify-package` checks that on-chain bytecode matches a local source tree."* [1](#0-0) 

I evaluated several publish-safety candidates (lazy module init ownership gating in `init.move`, `object_code_deployment` upgrade/freeze ownership checks, `large_packages` chunked staging) and all of these enforce owner/compat invariants correctly and are covered by targeted unit tests [2](#0-1) [3](#0-2) . The strongest independent local finding is in the `VerifyPackage` CLI command itself.

### Title
`aptos move verify-package` never fetches or compares on-chain module bytecode, only self-declared metadata — ([File: aptos-move/cli/src/commands.rs])

### Summary
`VerifyPackage`, documented as verifying "that on-chain bytecode matches a local source tree," never downloads the on-chain bytecode and its underlying `verify()` routine only compares `PackageMetadata` struct fields, none of which is cryptographically bound to the actually-deployed module bytes.

### Finding Description
`VerifyPackage::execute` builds the registry with bytecode fetching disabled: [4](#0-3) 

It then calls `package.verify(&compiled_metadata)`: [5](#0-4) 

`CachedPackageMetadata::verify` only compares `name`, `deps`, `modules` (which is `ModuleMetadata` — name + gzip source text only, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest`: [6](#0-5) 

Every one of these fields is **self-declared by the publisher** inside `PackageMetadata` and is never validated on-chain against the actual compiled module bytes at publish time — `code::publish_package` stores `pack: PackageMetadata` verbatim alongside the separately-supplied `code: vector<vector<u8>>` bundle, with no linkage assertion between metadata's `source`/`source_digest` and the bytecode that is actually verified/loaded by the VM: [7](#0-6) [8](#0-7) 

Because `CachedPackageRegistry::create(... , false)` never populates `bytecode`, and `verify()` never inspects it either, `VerifyPackage` can only ever detect metadata forgery (e.g. a wrong name or mismatched manifest text), never bytecode forgery. A malicious publisher can supply legitimate-looking metadata (matching source text and its digest) while publishing an unrelated, malicious `code` bundle. Anyone who runs `aptos move verify-package` against the legitimate source tree gets `"Successfully verified source of package"`, a false attestation that the deployed bytecode matches the reviewed source, when in fact the deployed bytecode has never been examined.

### Impact Explanation
This breaks the "mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" invariant explicitly called out in the publish impact gate. `verify-package` is the tool users, integrators, exchanges, and auditors are told to rely on for code-review/reproducibility assurance before trusting a deployed contract; a false-positive verification directly enables unauthorized/undetected code substitution to reach production trust decisions (e.g., approving token spend, granting admin roles, or listing a contract) based on code that was never actually checked.

### Likelihood Explanation
High likelihood of exploitation impact once discovered: no special privilege is needed by the attacker beyond normal permissionless publish rights (any account/object owner can publish arbitrary metadata alongside arbitrary bytecode), and the mismatch requires no race condition or timing — it is deterministic and reproducible on every invocation of `verify-package` against such a package.

### Recommendation
`VerifyPackage::execute` should call `CachedPackageRegistry::create(client, self.account, true)` (fetch bytecode), and `verify()` should additionally recompile the local package to bytecode (`pack.extract_code()`) and byte-for-byte compare each module against `registry.get_bytecode(module_name)`, failing verification on any mismatch — in addition to (not instead of) the existing metadata field checks.

### Proof of Concept
1. Build a legitimate Move package `pkg_good` with known source `m.move`.
2. Compute its metadata (`name`, `deps`, `manifest`, `source_digest`, `modules[].source`) via `BuiltPackage::extract_metadata()`.
3. Separately compile a malicious module (e.g., one adding an unauthorized admin backdoor) with the *same module name*, and manually construct a `PackageMetadata` whose non-bytecode fields are copied verbatim from step 2 (attacker fully controls both `metadata_serialized` and `code` in the entry function call, they need not match).
4. Publish via `code::publish_package_txn(owner, metadata_serialized, malicious_code)` — the framework never checks bytecode-to-metadata correspondence, so this succeeds: [9](#0-8) 
5. Run `aptos move verify-package --account <attacker_addr>` against the *original, benign* `pkg_good` source tree. Because `VerifyPackage` never fetches or compares bytecode, and only checks the (attacker-copied) metadata fields, the command prints `"Successfully verified source of package"` despite the deployed module being the malicious one.

**Uncertainty note:** I was not able to fully trace whether any downstream consumer (indexer, explorer trust badge, governance tooling) treats a successful `verify-package` run as an authoritative on-chain attestation versus purely a local developer convenience; this affects severity classification but not the existence of the underlying verification gap. Given index size limits, I could not locate every caller of `CachedPackageRegistry`/`verify()` across the whole monorepo — a full audit session would be needed to confirm there is no additional bytecode check elsewhere in the CLI pipeline that I missed.

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
