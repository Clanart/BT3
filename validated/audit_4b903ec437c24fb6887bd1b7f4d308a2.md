### Title
Unbounded oracle timestamp permanently locks price resolution via the monotonic per-feed check - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` enforces a monotonic per-feed oracle timestamp invariant (`oracle-timestamp-fresh`) that permanently rejects any subsequent price with a lower timestamp than the highest one ever recorded for that `{type, ident}` key. Because there is no upper bound anywhere in the pipeline on how far in the future a recorded `publish-time`/timestamp can be relative to real time, a single anomalous update can wedge the `last-update` map at an unreachable maximum, after which every legitimate future price update fails `oracle-timestamp-fresh` and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` forever for that asset — mirroring the reported `tickBin` griefing pattern where a boundary value makes a required check permanently unsatisfiable.

### Finding Description
`price-resolve` fetches a price/timestamp pair, resolves callcodes, then gates it: [1](#0-0) [2](#0-1) 

`oracle-timestamp-fresh` requires both a staleness bound *and* `(>= ts prev)` — the new timestamp must never be lower than the highest previously recorded timestamp for that feed key. `price-resolve` then persists the max timestamp seen into the `last-update` map (`(if (> timestamp last-update-time) (map-set last-update key timestamp) false)`), and there is no code path in the contract to lower or reset this stored value.

The upstream source of `timestamp` for Pyth feeds is `publish-time`, taken from `pyth-storage-v4.clar`'s `write-batch-entry`, which only enforces a *lower* staleness bound and rejects only *older*-than-previous updates — it never enforces an *upper* bound (i.e., it never checks that `publish-time` is not implausibly far in the future): [3](#0-2) [4](#0-3) 

`resolve-dia` has an analogous unmonitored transform, dividing the DIA timestamp by 1000 assuming it is milliseconds, with no independent sanity check that the resulting value is close to `stacks-block-time`: [5](#0-4) 

Once any single feed update (Pyth or DIA) is recorded with a timestamp far beyond real time — whether due to an off-by-1000 unit mismatch, an upstream relay error, or any other anomaly — the `last-update` map for that `{type, ident}` key is permanently pinned at that value. From that point forward, `(>= ts prev)` in `oracle-timestamp-fresh` can never be satisfied by any real, monotonically-increasing future timestamp lower than the wedged value, so `price-resolve` unconditionally reverts with `ERR-ORACLE-INVARIANT` for that asset's oracle key. This is structurally identical to the reported `EraBoxcarMidSum.sol` bug: a check tied to a value that only moves in one direction, with no mechanism to correct it once it saturates, permanently breaking every operation gated by that check.

`price-resolve`/`price-multi-resolve`/`get-asset-value` are invoked from every state-changing market function that needs a price for health checks, e.g. borrow, collateral-add/remove, and liquidation flows, since `get-assets`, `get-notional-evaluation`, and `is-healthy*` all depend on price resolution: [6](#0-5) [7](#0-6) 

There is no admin/DAO function in `v0-4-market.clar` to reset or lower `last-update` for a feed key once it is wedged — I searched the market contract for any such reset entrypoint and found none among all `last-update`-referencing code, meaning the effect, absent a full contract upgrade/migration, is not self-healing within the current logic (I could not verify whether a DAO-controlled upgrade path exists to redeploy `market.clar` with a cleared `last-update` map, as that would require examining the DAO/proposal machinery, which is outside the scope granted here).

### Impact Explanation
For the affected asset, all operations requiring its price (borrowing against it, withdrawing/removing it as collateral while debt exists, repaying debt in it, liquidating positions holding it, and general health checks) permanently revert with `ERR-ORACLE-INVARIANT`. Users' collateral and any interest/yield accruing on the affected asset become inaccessible through normal market flows because every code path that must price the asset first fails. This lands on **temporary freezing of funds** (temporary in the sense that it persists until a contract-level fix/upgrade, since no in-contract remediation exists), matching the same "griefing → DoS on an entire pool/asset" impact class as the reported analog.

### Likelihood Explanation
The wedge only requires one anomalous timestamp to be recorded once for a given oracle feed key — after which the condition is permanent and self-reinforcing (every legitimate subsequent timestamp is, by definition, not higher than a wedged max-future value). No attacker capital or repeated transactions are needed once the anomalous value is recorded; the difficulty lies entirely in whether an out-of-range `publish-time`/DIA timestamp can ever reach `price-resolve` in practice (e.g., through a relay bug, unit-conversion edge case, or a temporarily misbehaving oracle publisher passing existing lower-bound-only staleness checks). I was not able to fully verify from the available contract code whether Pyth's/DIA's off-chain publishers or the Wormhole bridge component enforce their own upper-bound sanity checks before `write-batch-entry` is called, which would affect the real-world likelihood; this uncertainty stems from those components being partially out of the indexed scope.

### Recommendation
- Add an explicit upper bound check on any timestamp accepted into `last-update`/`prices`, e.g. reject `publish-time`/converted DIA timestamps that exceed `stacks-block-time` (or `stacks-block-time + small buffer`) both in `pyth-storage-v4.clar`'s `write-batch-entry` and in `market.clar`'s `price-resolve`, so a single erroneous future timestamp can never be persisted.
- Decouple the "no older than previous" monotonic guard from being unconditionally permanent: consider bounding how far `prev` can legitimately drift ahead of `stacks-block-time`, or provide a DAO-gated recovery function to correct/reset a wedged `last-update` entry for a specific `{type, ident}` key without requiring a full contract migration.
- Add unit tests asserting that a single out-of-range (future) timestamp cannot permanently DoS subsequent legitimate price resolutions for the same feed.

### Proof of Concept
Conceptual reproduction (Clarinet/Clarity test), analogous to the referenced PoC pattern:
1. Register an asset (e.g. USDH via DIA, or any Pyth-backed asset) with oracle config `{type, ident, max-staleness}`.
2. Push one legitimate-looking price update whose `publish-time` (Pyth) or `timestamp` (DIA, pre-division) is set far in the future relative to `stacks-block-time` — this passes `write-batch-entry`'s lower-bound-only staleness check and `is-price-update-more-recent`, and is accepted by `pyth-storage-v4.clar`/DIA's oracle without any upper-bound rejection.
3. Call any market function that triggers `price-resolve` for that asset (e.g. `collateral-add`, `borrow`) — it succeeds once, and `last-update` for that `{type, ident}` is set to the anomalous max timestamp.
4. Advance the chain and push subsequent legitimate price updates with correct (lower, real-time) timestamps.
5. Call `price-resolve` again for the same asset — `oracle-timestamp-fresh`'s `(>= ts prev)` now fails permanently since `prev` is pinned at the anomalous future value, so every call reverts with `ERR-ORACLE-INVARIANT`, freezing all market operations dependent on that asset's price.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
