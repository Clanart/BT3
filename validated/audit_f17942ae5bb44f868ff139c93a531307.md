### Title
OP_RETURN outputs are excluded from fee and weight accounting - (`networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` appends a caller-supplied `OP_RETURN` output to `tx_outs`, but calculates the transaction’s virtual size and weight from only the inputs and payment outputs. The omitted `OP_RETURN` output therefore makes the signed transaction larger than accounted for, while its fee remains based on the smaller transaction.

### Finding Description
`SignableTransaction::new` accepts up to 80 bytes of public transaction data and appends it as an `OP_RETURN` output. [1](#0-0) [2](#0-1) 

However, both weight calculations call `calculate_weight_vbytes` with only `tx_ins.len()`, `payments`, and an optional change script. The `data` output is never represented in the synthetic transaction used for measurement. [3](#0-2) 

Consequently, `needed_fee = fee_per_vbyte * vbytes` uses a virtual size smaller than the transaction ultimately signed and returned. [4](#0-3)  The maximum-standard-weight check has the same issue because it evaluates the weight calculated without the `OP_RETURN`. [5](#0-4) 

### Impact Explanation
An unprivileged caller controlling the public `data`, payment, input, change, and fee-rate arguments can cause the wallet to construct and sign a transaction whose actual fee rate is below the requested fee rate and potentially below Bitcoin’s minimum relay fee. For an 80-byte payload, the omitted output contributes roughly ninety serialized bytes, all counted at full weight.

This is not merely an inaccurate accessor: `needed_fee` determines affordability, change amount, and minimum-fee validation before the transaction is passed to the threshold signing machine. [6](#0-5)  The resulting transaction can be non-relayable or remain unconfirmed even though the API reports that it meets the requested fee rate.

### Likelihood Explanation
The issue is deterministic whenever `data` is supplied. It is reachable through the public `SignableTransaction::new` API and does not require control of validators, peers, private keys, RPC nodes, or consensus rules. A near-minimum fee rate makes the signed transaction fall below relay policy; larger requested fee rates only produce a proportional underpayment.

### Recommendation
Pass the complete output set—including the `OP_RETURN` output—to `calculate_weight_vbytes`. The cleanest fix is to perform fee/size calculation after constructing all outputs, or extend `calculate_weight_vbytes` to accept the data payload and add an equivalent `TxOut` to its synthetic transaction. Recalculate both the no-change and with-change cases using the actual final outputs, and add tests asserting `tx.weight()` equals the internally calculated weight for every supported output combination.

### Proof of Concept
Conceptually:

```rust
let tx = SignableTransaction::new(
  vec![input],
  &[],
  Some(change_script),
  Some(vec![0u8; 80]),
  1, // sat/vbyte
)?;
```

The constructor calculates `vbytes` without the `OP_RETURN` output, while the returned `tx.transaction()` contains that output. For a sufficiently small base transaction, the added `OP_RETURN` output increases the real virtual size enough that `tx.fee() / actual_vbytes` is below the minimum relay rate, despite `new` accepting the transaction and reporting the smaller `needed_fee`.
