### Title
`SchnorrAggregate::verify` accepts trivial forgeries — attacker sets `R_i = -c_i·key_i`, `s = 0` - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
The analog of the CVE-2017-5609 class (untrusted input reaching a security-critical operation without proper binding, allowing the attacker to alter the operation's semantics) maps onto `SchnorrAggregate::verify`. Its verification equation is linear in every attacker-supplied component — the `Rs` points and the scalar `s` are taken verbatim from `SchnorrAggregate::read` — and nothing in the check binds them to the secret keys. An unprivileged party can serialize a forgery that verifies for arbitrary public keys and challenges.

### Finding Description
`SchnorrAggregate::read` accepts an attacker-controlled length-prefixed list of points `Rs` plus a scalar `s` [1](#0-0) . `verify` then queues the multiexp pairs `(z_i, R_i)`, `(z_i·c_i, key_i)`, `(-s, G)` and requires the sum to be identity [2](#0-1) . The check is

`Σ z_i·R_i + Σ z_i·c_i·key_i − s·G == 0`.

The weights `z_i` are derived only from the challenges via `weight(&mut digest)` — the `Rs` and keys are never digested [3](#0-2)  — but even that is irrelevant: because `R_i` is fully attacker-chosen and appears linearly, the adversary simply sets each `R_i = −c_i·key_i` and `s = 0`. Each summand `z_i·(−c_i·key_i) + z_i·c_i·key_i` cancels to identity for **any** weights, so the aggregate "signature" verifies for any set of `(key, challenge)` pairs without knowledge of any discrete log.

The doc-comment acknowledges the challenges must be "binding to the public key, nonce, and any message" [4](#0-3) , but even perfectly binding challenges do not help: the verifier computes `z·R + z·c·key` directly on attacker-supplied `R`, so challenge binding cannot prevent `R = −c·key`.

### Impact Explanation
Concrete forged signature: any consumer that parses an aggregate signature via `SchnorrAggregate::read` (fully unauthenticated bytes, matching the `read_*` reachability surface) and calls `verify` will accept a signature over arbitrary public keys/messages produced by an attacker who knows no private key. This defeats the entire purpose of the aggregation verifier — a single forged `(Rs, s)` pair batch validates as if every listed key had signed.

### Likelihood Explanation
Reachable by any unprivileged party able to submit signature bytes to a verifying component; forgery requires only public keys and the public challenges (which the verifier itself can publish or which are derivable). The computation `R_i = −c_i·key_i` is one scalar multiplication per entry — trivial. Exploitation is deterministic, not probabilistic.

### Recommendation
Do not verify aggregate Schnorr signatures via a multiexp equation linear in attacker-supplied `R`s. Require the aggregated form `Σ z_i·s_i·G = Σ z_i·(R_i + c_i·key_i)` where each `s_i` is supplied per-signer, or switch to an interactive/rogue-proof aggregation (e.g., proper MuSig-style key aggregation with the nonce committed inside the challenge). At minimum, individual `R_i` must be bound into each per-signature challenge `c_i` and `s` must be decomposable to per-signer scalars so a cancellation like `R_i = −c_i·key_i` yields an `s_i` that fails the Schnorr relation `s_i·G = R_i + c_i·key_i` — note that with `s_i = 0` it does not fail here, which is exactly the flaw.

### Proof of Concept
1. Attacker obtains target public key `A` and the challenge `c` (any value; the attack needs no control over `c`).
2. Attacker computes `R = A·(−c)` (a pure public-key operation), sets `s = 0`, and serializes `SchnorrAggregate { Rs: [R], s: 0 }` via `write`.
3. Victim parses it with `SchnorrAggregate::read` (canonical encoding checks pass since `R` is a valid point) and calls `verify(dst, &[(A, c)])`.
4. The multiexp evaluates `z·(−c·A) + z·c·A − 0·G = 0`, `is_identity()` returns true, and `verify` returns `true` — a valid signature under `A` for a challenge `c` the attacker never satisfied, with zero knowledge of `A`'s discrete log. The same construction extends to `n` entries by setting every `R_i = −c_i·key_i`.
