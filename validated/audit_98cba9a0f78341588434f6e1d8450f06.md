### Title
Empty aggregate Schnorr signatures verify as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts the degenerate case where the aggregate contains zero `R` values and `s = 0`. Because the verification equation reduces to `0 * G == identity`, an attacker can provide an empty aggregate encoding that verifies without any signer authorization.

### Finding Description
`SchnorrAggregate::read` permits a zero-length `Rs` vector and then reads a scalar without requiring at least one signature [1](#0-0) . `SchnorrAggregate::verify` only checks that `self.Rs.len() == keys_and_challenges.len()`, so both being empty passes validation [2](#0-1) . For an empty aggregate, the loop queues no weighted `R`/public-key statements, and the only remaining statement is `-self.s * G`; when `s = 0`, this is the identity point [3](#0-2) . Although `SchnorrAggregator::complete` refuses to locally produce an empty aggregate, the public deserializer can still produce one from untrusted bytes [4](#0-3) .

This is the same bug class as the reported zero-reserve swap: an otherwise meaningful verification formula degenerates when a required non-empty reserve/input set reaches zero.

### Impact Explanation
An unprivileged party can forge a serialized aggregate signature for the empty signer set. Any caller that uses `SchnorrAggregate::verify` with a caller-supplied aggregate and an empty authorized signer list will accept it as valid, despite no private key holder participating.

### Likelihood Explanation
The exploit requires only public input bytes and does not require malformed encodings, invalid points, leaked keys, or protocol misbehavior by validators. It affects integrations or verifier paths where an empty signer set is reachable; the cryptographic API itself should reject this vacuous case rather than relying on every caller to do so.

### Recommendation
Reject zero-length aggregates in `SchnorrAggregate::read` or at the start of `SchnorrAggregate::verify`. If deserialization must remain structurally permissive, `verify` should still return `false` when `keys_and_challenges` or `Rs` is empty.

### Proof of Concept
For any ciphersuite `C`, the serialized payload is:

```text
00 00 00 00 || encode_scalar(0)
```

This decodes as `Rs = []` and `s = 0`. Calling:

```rust
aggregate.verify(dst, &[])
```

constructs only the statement `-0 * G`, evaluates it to the identity, and returns `true` [3](#0-2) .
