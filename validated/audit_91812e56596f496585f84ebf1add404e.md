I found a genuine, unprivileged-exploitable analog in `IntrinsicIntents._fillSameChain`, distinct from a front-running-only scenario: the "surplus overpayment" branch is only reachable on the *first* fill of an output pair (`alreadyFilled == 0`), which lets a solver structure a sequence of same-block/same-transaction-adjacent partial fills to bypass the intended surplus split with the protocol/beneficiary, unlike Curve's bug this is a state-transition/branch-selection defect rather than pure front-running.

### Title
Surplus-split bypass via forced partial fill before overpayment - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` only computes and distributes solver "surplus" (`dust`, split between `beneficiaryShare` and `protocolShare`) when `alreadyFilled == 0 && solverAmount > totalRequired`, i.e. only on a single-shot fill of a virgin (unfilled) output pair. [1](#0-0)  If any prior partial fill has touched that output token (`alreadyFilled != 0`), the branch is skipped entirely and `fillAmount` is simply capped at `remaining` with no surplus computed: `fillAmount = solverAmount > remaining ? remaining : solverAmount;`. [2](#0-1) 

### Finding Description
A solver (or a colluding pair of addresses) who wants to overpay in order to manipulate escrow release timing or avoid ever paying the protocol/beneficiary surplus share can do so by never triggering the `alreadyFilled == 0 && solverAmount > totalRequired` condition:

1. Send a first, trivial partial fill (e.g. `solverAmount = 1 wei`) for the output token. This sets `_partialFills[commitment][outputToken] = 1`, so `alreadyFilled` becomes non-zero.
2. Any subsequent fill by the same or a different solver for that pair is now permanently routed through the `else` branch (line 93-95), which only ever caps `fillAmount` at `remaining` — it can never exceed `remaining`, so `solverAmount` in excess of `remaining` is silently discarded from the transferred amount (the solver approves/transfers `beneficiaryTotal = fillAmount`, i.e. never more than `remaining`). No `DustCollected` event, no `protocolShare`, no `beneficiaryShare` is ever computed again for that output token for the rest of the order's lifetime, since `alreadyFilled` never resets to 0 once incremented.

This is the same class of defect as the Curve bug: a single state field (`_partialFills[commitment][outputToken]`, analogous to `initial_debt`/underwater band state) permanently gates which code path future actions take, and a cheap, one-time action (a 1-wei partial fill) by any unprivileged party — the order's own creator selecting a bid, a solver, or literally anyone who can call `fillOrder` on a same-chain order before the "real" solver fills — locks the surplus-collection logic off for the remainder of the order. The guard that would normally split solver overpayment between the protocol treasury and the beneficiary is bypassed for the rest of the order's life, and the fix path (there is no `repay(0)`-style analog here) provides no way to "resync" or recover surplus once the first partial fill has landed. [3](#0-2) 

### Impact Explanation
This falls under "logic attacks" / transaction manipulation in the bounty scope: the protocol's designed fee/surplus-collection invariant ("surplus is split between the beneficiary and protocol according to `surplusShareBps`") is permanently defeated for any output pair that has already received a nonzero partial fill, without needing a malicious relayer, prover, or admin — any address able to call `fillOrder` (unprivileged, public entrypoint) can trigger it. [4](#0-3)  The protocol treasury (`DustCollected` sink) permanently loses its cut of any subsequent overpayment/surplus on that output pair, and no governance or user action can restore the surplus split once the sentinel field is nonzero.

### Likelihood Explanation
High for anyone motivated to avoid the protocol fee share on overpay: the attack requires only a single cheap partial fill (as small as 1 wei of the output token, well below `remaining`) before performing the "real" fill, and same-chain fills are single-transaction/atomic, so this needs no relayer, prover, or race condition — it is fully deterministic and repeatable per order.

### Recommendation
Compute and enforce the surplus split whenever `solverAmount > remaining` (i.e., whenever this specific fill call would overpay the *remaining* amount), rather than gating it on `alreadyFilled == 0`. The surplus (`solverAmount - remaining`) should always be split per `surplusShareBps` regardless of whether prior partial fills exist for that output token.

### Proof of Concept
1. Place a same-chain order with `output.assets[0].amount = 1000` DAI, no calldata, `surplusShareBps` configured non-zero.
2. Attacker (any address) calls `fillOrder` with `outputs[0].amount = 1` — a trivial partial fill. This sets `_partialFills[commitment][DAI] = 1`, transferring 1 wei DAI to the beneficiary and releasing negligible escrow, leaving the order "PartialFill".
3. The intended solver now calls `fillOrder` with `outputs[0].amount = 2000` (double the remaining `999`), intending/expecting the normal overpay/surplus rules to apply.
4. Because `alreadyFilled = 1 != 0`, the surplus branch (lines 84-92) is skipped; `fillAmount = min(2000, 999) = 999`. The solver's `beneficiaryTotal = 999` is transferred (no surplus computed), and any surplus economics designed to fund the protocol (`DustCollected` event) never fire for this fill, even though the solver "overpaid" by 1001 DAI in `solverAmount`. No `protocolShare` is ever deducted, and the solver's excess intention is simply discarded server-side without the intended fee split logic ever executing again for that output token. [5](#0-4)
