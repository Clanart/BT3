### Title
Path-containment check in `resolveWithin` uses a bare string-prefix comparison, allowing sandbox escape via a similarly-named sibling directory or symlink - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin`/`_resolveWithin` is Desktop's central guard for "is this path inside the repository root," used to sanitize attacker-influenced paths (conflicted file paths read from a cloned repo, and `filepath` from `x-github-client://` deep links) before reading files or opening them in the OS shell. The final containment check is a raw string `startsWith` comparison with no path-separator boundary check, so a resolved real path whose directory name merely has the root's name as a *string prefix* (e.g. `/home/user/repo-secrets` vs root `/home/user/repo`) is incorrectly treated as "inside" the root. This mirrors the LSP6 report's root cause exactly: an insufficiently strict boundary/length check on a prefix comparison silently widens the set of values that are treated as "allowed."

### Finding Description
`_resolveWithin` computes the final decision with: [1](#0-0) 

```
  const resolved = resolve(normalizedRoot, normalizedRelative)
  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)
  return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a pure character-prefix test, not a path-segment test. If `realRoot` is `/Users/x/repo`, then `/Users/x/repo-evil/secret.txt` also satisfies `startsWith(realRoot)`, even though `repo-evil` is a completely different, sibling directory. The function's own JSDoc promises the resolved path "resides underneath the root path," which this check does not actually guarantee.

An attacker who controls the content of a cloned/fetched repository can place a symlink whose target real path is a sibling directory sharing the root's name as a prefix (e.g. a directory created next to the clone, or any other directory on disk that happens to start with the same characters as the repo's folder name). When `realpath()` is called on the joined path, the symlink is resolved to that sibling location, and the buggy `startsWith` check accepts it as "inside" the repository.

The unit tests for this function only cover `..` traversal and symlinks pointing to unrelated, differently-named directories: [2](#0-1) 

None of the existing tests exercise the "sibling directory with a shared name prefix" case, so this boundary bug is unguarded by tests and unnoticed by review.

### Impact Explanation
Two attacker-reachable call sites rely on `resolveWithin` for its safety guarantee:

1. `buildConflictContext` reads conflicted file contents from the working directory and forwards them to the Copilot SDK: [3](#0-2) 
`file.path` values originate from git-reported conflict paths in a cloned/fetched, attacker-influenced repository. A crafted symlink whose real target is a same-prefix sibling directory bypasses the guard, causing Desktop to read a file outside the repository and exfiltrate its contents to an external LLM service — a read-outside-repo plus data-exfiltration primitive.

2. `openRepositoryFromUrl`, reachable via GitHub Desktop's `x-github-client://` deep-link handler, uses the same guard before acting on a `filepath`: [4](#0-3) 
A malicious link crafted to reference a path that, after resolution, lands in a same-prefix sibling directory would cause `shell.showItemInFolder` to reveal/open a file outside the intended repository, defeating the explicit "Prevented attempt to open path outside of the repository root" protection that the code believes it enforces.

Both cases satisfy the required threat model: the attacker controls a cloned/fetched repository object or a link the user clicks, and the outcome is file access outside the intended directory boundary — exactly the class of unprivileged, remotely-triggerable issue in scope.

### Likelihood Explanation
Exploitation requires only that a real filesystem path exists whose name is root-name-prefixed (this is plausible on real user machines — sibling folders like `repo`, `repo-old`, `repo2`, `repository`, `repo.bak` are common), and that the attacker can place a symlink inside the cloned repository pointing at such a target (or, on the deep-link path, simply reference a path that resolves that way). No admin rights, local access, or pre-existing malware are needed — the attacker only needs to control repository content or craft a link, both of which are in-scope, unprivileged capabilities. The bug is a straightforward comparison logic error, not a probabilistic condition, so once the naming collision exists, the bypass is deterministic.

### Recommendation
Replace the raw prefix check with a segment-aware comparison, e.g. require that `realResolved === realRoot` or `realResolved.startsWith(realRoot + path.sep)`, ensuring the character immediately following the root path is a path separator (or nothing). This closes the sibling-directory bypass while preserving the "at or underneath root" semantics documented in the function's own comments.

### Proof of Concept
```ts
// Illustrative scenario (mirrors the missing boundary check in resolveWithin):
// Attacker-controlled repo cloned at:
const root = '/home/user/repo'
// A sibling directory that happens to exist / can be created outside the repo:
const secretDir = '/home/user/repo-secrets'

// Inside the cloned repository, attacker adds a symlink:
//   /home/user/repo/link -> /home/user/repo-secrets
// and references it as a conflicted file path: "link/secret.txt"

// _resolveWithin's real check becomes:
const realRoot = '/home/user/repo'
const realResolved = '/home/user/repo-secrets/secret.txt'
console.log(realResolved.startsWith(realRoot)) // true -- INCORRECTLY treated as "inside root"
```
Adding this test case to `app/test/unit/path-test.ts` (analogous to the existing symlink tests) demonstrates that `resolveWithin(root, 'link/secret.txt')` returns a non-null resolved path even though `secret.txt` lives in an unrelated sibling directory, confirming the sandbox-escape via the missing separator boundary in the `startsWith` check at [5](#0-4) .
