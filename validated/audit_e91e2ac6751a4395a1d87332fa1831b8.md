## Analysis

The Overlay bug class is: a function uses one formula/state to **gate/determine eligibility** for an action, but a **different, disconnected formula** is used to actually **compute the resulting amount**, so the two don't stay consistent — silently breaking the intended economic guarantee.

I found a direct structural analog in `rewards/mWOMSVBaseRewarder.sol`. This contract is a near-identical copy of `rewards/vlMGPBaseRewarder.sol` (a rewarder for time-locked/cooldown-based governance tokens), but its forfeit-calculation logic was copy-pasted incorrectly, permanently disabling the intended penalty logic.

### Title
Broken forfeiture calculation in mWOMSVBaseRewarder permanently prevents recapture of unclaimed yield from early-exiting mWomSV holders - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`vlMGPBaseRewarder._calExpireForfeit()` correctly determines how much of a user's accrued reward should be forfeited (and redistributed to remaining stakers) based on the user's actual "rewardable" cooldown state, obtained from `vlMGP.getRewardablePercentWAD(_account)`: [1](#0-0) 

`mWOMSVBaseRewarder._calExpireForfeit()` is meant to do the same for `mWomSV` (which, per `wombat/mWomSV.sol`, implements the same cooldown/unlock-slot mechanism — confirmed by ~100 matches for `amountInCoolDown`/`coolDown`/`getRewardablePercentWAD` in that file), but instead of calling the equivalent "rewardable percent" check, it sets `rewardableAmount = _amount` directly: [2](#0-1) 

### Finding Description
In `vlMGPBaseRewarder`, the eligibility check (`getRewardablePercentWAD`, driven by `VLMGP`'s cooldown/unlock-slot state) and the forfeit amount computation are tied together correctly: users who have started unlocking (moved tokens into cooldown) become only partially "rewardable," and the unclaimed/forfeited portion is queued back into the pool via `_queueNewRewardsWithoutTransfer` for remaining stakers: [3](#0-2) 

In `mWOMSVBaseRewarder`, the same `_sendReward` → `_calExpireForfeit` → `_queueNewRewardsWithoutTransfer` flow exists: [4](#0-3) 

but `_calExpireForfeit` is broken: `rewardableAmount` is assigned `_amount` before the `if` check, so `rewardableAmount > _amount` can never be true, and `forfeitAmount = _amount - rewardableAmount` always evaluates to `0`: [2](#0-1) 

This is exactly the Overlay-style mismatch: the "is this user eligible for full rewards" determination (which should depend on `mWomSV`'s cooldown state, mirroring `VLMGP.getRewardablePercentWAD`) is completely disconnected from the amount actually paid out — the forfeiture mechanism silently never fires, regardless of a user's actual lock/cooldown state.

### Impact Explanation
The forfeiture mechanism exists specifically to recapture unclaimed yield from users who exit early (start unlocking mWomSV) and redistribute it to loyal, still-locked stakers via `rewardInfo.rewardPerTokenStored` updates in `_queueNewRewardsWithoutTransfer`. Because `forfeitAmount` is always `0` in `mWOMSVBaseRewarder`, that redistribution never occurs: every user who initiates or completes an mWomSV unlock still receives 100% of their accrued bonus-token rewards regardless of their cooldown status, and the pool of "clawed-back" unclaimed yield that should accrue to remaining long-term stakers is permanently forfeited (never queued, never distributed). This is a direct, protocol-wide loss of unclaimed yield that should belong to remaining stakers — it is silently and permanently misallocated from the reward pool.

### Likelihood Explanation
This triggers unconditionally on every `_sendReward`/claim call in `mWOMSVBaseRewarder` for any account with any cooldown/unlocking history — no special conditions, privileges, or attacker action required. Any ordinary wallet holding mWomSV and interacting with normal claim/unlock flows benefits from (and remaining stakers are harmed by) this defect on every reward claim.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit()` to mirror `vlMGPBaseRewarder._calExpireForfeit()` by querying the actual rewardable percentage from `mWomSV` (e.g., an equivalent `getRewardablePercentWAD(_account)` call), rather than defaulting `rewardableAmount` to the full `_amount`.

### Proof of Concept
1. User A locks `mWomSV` and starts an unlock/cooldown (analogous to `VLMGP.startUnlock`), which per `mWomSV.sol`'s cooldown design should reduce their "rewardable percent" going forward.
2. Rewards continue to accrue and are queued into `mWOMSVBaseRewarder` via `queueNewRewards`/`_queueNewRewardsWithoutTransfer`.
3. User A calls the claim path leading to `_sendReward`, which invokes `_calExpireForfeit(_account, userRewards[...])`: [5](#0-4) 
4. Inside `_calExpireForfeit`, `rewardableAmount` is set equal to `_amount` unconditionally, so `forfeitAmount` computes to `0`: [2](#0-1) 
5. User A receives the entire `userRewards[...]` amount despite being in cooldown/having exited, and `_queueNewRewardsWithoutTransfer` is never invoked with a nonzero forfeit amount — the redistribution to remaining stakers (the core purpose of the forfeiture mechanism, as implemented correctly in `vlMGPBaseRewarder`) never happens, for any user, ever.

**Note on scope/confidence**: I was unable to pull the full body of `wombat/mWomSV.sol` (only confirmed via grep that it contains the same `amountInCoolDown`/`coolDown`/`getRewardablePercentWAD` keywords as `VLMGP.sol`, ~100 matches), so I could not directly view its `getRewardablePercentWAD` implementation to fully confirm parity with `VLMGP`. If the file contents needed for full verification are required, a Devin session with full repository access would be needed to inspect `wombat/mWomSV.sol` in its entirety.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
```
