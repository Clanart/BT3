### Title
Permissionless, unvalidated `RegisterERC20` lets a malicious contract owner permanently freeze escrowed user funds - (File: x/erc20/keeper/proposals.go, x/erc20/keeper/msg_server.go)

### Summary
`RegisterERC20` is permissionless by default and performs no validation of the registered ERC20 contract's transfer/admin logic [1](#0-0) . The resulting `TokenPair` is marked `OWNER_EXTERNAL` [2](#0-1) , meaning the contract's original deployer retains unilateral, instantaneous control (pause/blacklist/upgrade) over a token that other users are encouraged to trust and convert native coins into. This is the direct Cosmos EVM analog of the NFTX "vault manager can grief users" pattern: an unprivileged actor creates an on-chain trust object (vault / token pair) that other users deposit value into, then unilaterally and instantly changes contract behavior to trap that value, with no timelock or verification-status gate to protect users.

### Finding Description
The conversion flow works as follows:
1. Any user calls `ConvertERC20` to deposit their genuine ERC20 tokens into the `erc20` module's escrow account and receive an equivalent, module-minted native coin (`convertERC20IntoCoinsForNativeToken`, `x/erc20/keeper/msg_server.go:71-188`). This performs a `transfer` EVM call from the user to `types.ModuleAddress` and mints coins 1:1.
2. To redeem, the user calls `ConvertCoin`, which burns their native coin and has the `erc20` module attempt to `transfer` the previously escrowed ERC20 tokens back to them out of the module's balance (`ConvertCoinNativeERC20`, `x/erc20/keeper/msg_server.go:237-306`, specifically the `CallEVM(..., "transfer", receiver, ...)` at line 263).

Because the token pair's contract owner is an arbitrary EOA (`OWNER_EXTERNAL`), and nothing in `registerERC20`/`CreateCoinMetadata` inspects contract logic beyond name/symbol/decimals (`x/erc20/keeper/proposals.go:44-114`), the owner can at any time call an admin-only `pause()`, add the `erc20` module address (or specific victim addresses) to a `blacklist`, or otherwise make `transfer` revert. Since `ConvertCoinNativeERC20`'s escrow-then-unescrow logic depends on that `transfer` succeeding, a paused/blacklisted contract makes redemption permanently impossible: the native coin that was minted to depositors becomes unbacked/unredeemable, and the real ERC20 tokens sitting in the module's escrow account become permanently unreachable by the depositors who already burned their coin claim, or the coin holder is left holding value that can never be turned back into the underlying asset.

Unlike NFTX's optional "finalizeVault" verification status, there is no analogous "verified"/renounced-ownership signal or waiting period surfaced by this module before other users can convert into an `OWNER_EXTERNAL` pair, and `PermissionlessRegistration` is `true` by default (`x/erc20/types/params.go:24-29`), so no governance gate is required to create such a pair.

### Impact Explanation
This falls under "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds... escrowed assets... or token-pair-backed balances." Once users have escrowed real ERC20 value into the module account trusting a registered pair, the contract owner (an unprivileged, non-governance actor) can unilaterally and instantly freeze that escrow, permanently locking user funds with no on-chain recourse, mirroring the NFTX "vault manager griefs users" bug class exactly, but landing on Critical severity here because it corrupts the accounting/redeemability of module-escrowed, token-pair-backed balances rather than merely raising fees.

### Likelihood Explanation
High likelihood: `RegisterERC20` requires no privileged role by default (`PermissionlessRegistration = true`), any standard "admin/pausable/blacklist" OpenZeppelin-style ERC20 contract is trivial to deploy and register, and ordinary users have no way to distinguish a benign `OWNER_EXTERNAL` pair from a malicious one before converting funds into it.

### Recommendation
- Require token pairs registered from externally-owned contracts to prove the contract has renounced administrative control (e.g., verifiably no owner/pauser/blacklist role) before allowing conversions, or restrict `ConvertCoin`/`ConvertERC20` for `OWNER_EXTERNAL` pairs behind an explicit, documented "unverified" warning surfaced at the protocol level (not just a UI convention as in NFTX).
- Consider disabling `PermissionlessRegistration` by default, or requiring a governance/allowlist step before a pair becomes convertible with real user funds.
- Add a mechanism analogous to NFTX's `finalizeVault` at the protocol layer, and/or a timelock on the effect of any change detected in contract behavior (e.g., quarantine period after first registration before large-scale conversions are permitted).

### Proof of Concept
1. Attacker deploys a standard `ERC20Pausable`/blacklist-capable contract, keeping `owner = attacker`.
2. Attacker calls `MsgRegisterERC20` (permissionless, no governance needed since `PermissionlessRegistration` defaults to `true`) to register the contract as a `TokenPair` with `ContractOwner = OWNER_EXTERNAL` (`x/erc20/keeper/proposals.go:36`).
3. Victims acquire the ERC20 token (e.g., via a legitimate use case, airdrop, or DEX) and call `MsgConvertERC20` to deposit tokens into the module escrow and receive the paired native coin (`x/erc20/keeper/msg_server.go:71-188`).
4. Attacker calls `pause()` (or blacklists `types.ModuleAddress`) on their contract.
5. Any victim who still holds the paired coin now calls `MsgConvertCoin` to redeem; the internal `CallEVM(..., "transfer", ...)` in `ConvertCoinNativeERC20` (`x/erc20/keeper/msg_server.go:263`) reverts because the contract is paused/the module is blacklisted, so `ConvertCoin` fails permanently — the victim's coin is stuck, un-redeemable, for as long as the attacker keeps the contract paused (indefinitely). // RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
