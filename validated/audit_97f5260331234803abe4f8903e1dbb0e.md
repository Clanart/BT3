Based on my investigation, I found a concrete file-protocol re-enablement pattern in the submodule-update code path that is a real analog to the report's "attacker-controlled callback silently overrides safety checks" pattern — here the attacker-controlled repository content (`.gitmodules`) can steer Desktop into disabling Git's own submodule-URL protocol hardening.

### Title
Submodule update re-enables `protocol.file.allow=always`, letting a malicious repo's `.gitmodules` pull arbitrary local file-system paths into the working copy - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  accepts an `allowFileProtocol` flag that, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. Modern Git defaults `protocol.file.allow` to `user` (disabled for automated/recursive operations) specifically to stop a cloned/fetched repository's `.gitmodules` from redirecting a submodule fetch to a local `file://` path, which is the exact vector behind past submodule/file-protocol advisories. By passing `-c protocol.file.allow=always` for this invocation, Desktop deliberately unsets that protection for the submodule step.

### Finding Description
The broken invariant is: *a repository the victim clones/fetches must not be able to make Git read from arbitrary local paths on the victim's machine during an automatic (non-interactively-confirmed) submodule update.* Git's own default of `protocol.file.allow=user` exists to enforce this invariant against untrusted repo content (`.gitmodules` is fully attacker-controlled once the victim clones or fetches a malicious repo). Desktop's `updateSubmodulesAfterOperation` function overrides this default per-invocation via `-c protocol.file.allow=always` whenever it is called with `allowFileProtocol: true`: [2](#0-1) . This is analogous to the report's core issue — an attacker-supplied object (there, the ERC20/ERC777 token; here, the `.gitmodules` file inside the cloned repo) is trusted to drive a security-relevant code path (there, `safeTransfer`'s callback; here, `git submodule update`'s protocol negotiation), and the surrounding code's own safety check (`safeTransferFrom`/`safeTransfer` return-value check in Solidity; `protocol.file.allow=user` in Git) is bypassed by design in this call path.

### Impact Explanation
If `allowFileProtocol` is passed as `true` on a code path that runs during an ordinary user action (e.g. checking out a branch that has a new/updated submodule pointing to `file:///some/local/path`), the attacker's `.gitmodules`/submodule URL can direct Git to copy the contents of an arbitrary local directory into the submodule's working-tree path inside the repository — a file read outside the intended repository boundary. Because the copied content then lands inside a Desktop-managed working directory, it can be surfaced in the Changes view and, if the user commits/pushes, transmitted to a remote the attacker controls — turning a local read primitive into credential/file exfiltration (e.g. SSH keys, other local git configs, cloud credential files) without the user knowingly choosing to expose that path.

### Likelihood Explanation
I was only able to confirm the mechanism inside `submodule.ts`; I could not fully trace every call site to `updateSubmodulesAfterOperation` in `app/src/lib/git/checkout.ts` in the time available (`grep_search` showed it referenced 7 times there) to verify under exactly which user-triggered flows (checkout, pull, clone) `allowFileProtocol: true` is actually passed versus gated behind an explicit user prompt. This materially affects likelihood: if the flag is only ever set to `true` after an explicit, informed user confirmation dialog, the practical exploitability is low; if it is set unconditionally (or based on a heuristic the attacker can satisfy, such as the submodule already existing locally), the path is directly reachable by simply cloning or pulling a malicious repository with unprivileged, unmodified user actions — matching the "unprivileged, attacker controls a cloned/fetched repository" criteria.

### Recommendation
- Do not allow `protocol.file.allow=always` to be set automatically based on repository content; require an explicit, per-submodule user confirmation before enabling `file://` submodule fetches, and default to Git's `user`/`never` protection otherwise.
- If `allowFileProtocol` exists to support legitimate local-monorepo workflows, scope it narrowly (e.g., only for submodule URLs the user has manually configured as remotes previously, not URLs freshly introduced by a fetched `.gitmodules`).
- Audit all callers in `app/src/lib/git/checkout.ts` to confirm `allowFileProtocol` is never derived purely from untrusted repository content without a user gate.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` entry such as `url = file:///Users/victim/.ssh` (or any sensitive local path) with a submodule path like `payload/`.
2. Victim uses GitHub Desktop to clone or fetch/checkout the branch containing this `.gitmodules` change.
3. Desktop calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)` (per the call sites in `checkout.ts`), which runs `git -c protocol.file.allow=always submodule update --init --recursive` per [3](#0-2) .
4. Because `protocol.file.allow` is forced to `always`, Git honors the `file://` URL and copies the local directory's contents into `payload/` inside the victim's working tree, bypassing Git's own default protection against exactly this scenario.
5. The copied files now appear as trackable changes in Desktop's Changes view; if the victim commits and pushes (or the attacker socially engineers a "please push this fix" follow-up, which is out of scope but not required for the initial read), the sensitive local content is exposed inside the repository history.

**Caveat:** I could not verify from the index alone the exact conditions under which `checkout.ts` passes `allowFileProtocol: true` (whether gated by a user prompt or automatic). This should be confirmed in a full checkout via a Devin session/local clone before treating this as a fully confirmed high-severity finding, since that gating determines whether this is directly attacker-reachable or requires an extra confirmation step from the user.
