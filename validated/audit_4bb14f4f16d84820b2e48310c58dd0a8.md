### Title
Cross-Cluster CRDS Signature Replay via Missing Shred-Version/Cluster Binding in `CrdsValue::signable_data` - (File: `gossip/src/crds_value.rs`)

### Summary
Analogous to the missing-`chainId` flaw in `VerifyingSingletonPaymaster.getHash`, Agave's gossip layer signs `CrdsValue`s over `CrdsData` alone, with no cluster-identifying value (shred-version, genesis hash) included in the signed payload. Cluster separation is enforced only as an unauthenticated, best-effort transport filter that is bypassed for every non-`ContactInfo` CRDS type whenever the origin pubkey already has *any* record in the local table. A signature legitimately produced on one cluster is therefore valid, verifiable data on any other cluster, and can be replayed by an unprivileged network observer without cooperation from the signer.

### Finding Description
`CrdsValue::signable_data()` returns only the serialized `CrdsData`, never any shred-version or genesis-hash value: [1](#0-0) 

Cluster separation is instead enforced out-of-band, in `cluster_info.rs`, via `discard_different_shred_version`, which is applied to `PushMessage`/`PullResponse` payloads: [2](#0-1) 

Crucially, this filter only strictly checks shred-version for `CrdsData::ContactInfo`. For every other `CrdsData` variant (`Vote`, `LowestSlot`, `EpochSlots`, `DuplicateShred`, `SnapshotHashes`, `RestartLastVotedForkSlots`, `RestartHeaviestFork`), the check degenerates to `crds.get_records(&value.pubkey()).next().is_some()` — i.e. "does this pubkey have *any* existing record at all," irrespective of that record's shred-version or cluster origin (line 2541). Once that bypass condition is met, the value proceeds to `verify_gossip_addr`/CRDS signature verification, which only checks the ed25519 signature against `signable_data()` — again, cluster-agnostic: [3](#0-2) 

Because the signed payload never encodes which cluster it was produced for, any packet capturer on Cluster A can re-transmit a validator's legitimately signed `CrdsValue` (e.g. `Vote`, `EpochSlots`, `RestartHeaviestFork`, `RestartLastVotedForkSlots`) into Cluster B's gossip network. It is not necessary for the validator to act maliciously or for the attacker to hold any key — the attacker is a plain, unprivileged network relay. The only requirement is that the target cluster's CRDS table already holds *some* record for that pubkey (e.g. a `ContactInfo` entry, which is routinely present for any validator whose identity key is reused/observed across networks, as is common for test/dev clusters spun from shared tooling or during coordinated multi-network operations).

This mirrors the audited defect precisely: the "chainId" analog here is `shred_version`/genesis hash, and it is absent from the cryptographically bound payload while present only as an easily-bypassed transport heuristic.

### Impact Explanation
Successful replay lets an unprivileged attacker inject cross-cluster CRDS entries that a receiving validator will treat as authentic first-party gossip from a real, staked identity. The most consequential targets are `RestartHeaviestFork` and `RestartLastVotedForkSlots`, which drive the wen-restart cluster-recovery protocol: a replayed stale/foreign restart vote from a real validator identity can corrupt the aggregated restart-fork picture other validators build during a live restart coordination, i.e., degrade/corrupt cluster-halt recovery consensus. Replayed `Vote`/`EpochSlots`/`DuplicateShred` CRDS entries can likewise poison a validator's view of another validator's real-time state (stale duplicate-shred claims, stale epoch slots) causing false state acceptance/consensus confusion. This does not directly move funds but corrupts consensus-relevant state that the SVM/runtime and restart tooling depend on, consistent with the "false execution/rooting/acceptance, consensus halt" impact categories.

### Likelihood Explanation
No trust or privileged access is required by the attacker beyond ordinary gossip network participation (packet capture/relay), and no cooperation of the signer is needed — this exactly matches the "unprivileged... gossip" scope and explicitly excludes "malicious validator" assumptions, since the signer's original message was entirely legitimate. The main precondition — the target CRDS table already having a record for the replayed pubkey — is a low bar because `ContactInfo` records for known identities persist and are commonly present, and identity-key reuse across Agave test/dev networks (testnet/devnet forks, local clusters bootstrapped from shared configs) is a routine operational occurrence rather than a rare edge case.

### Recommendation
Bind the CRDS signature to the cluster: include the cluster's `shred_version` (or a stable genesis-hash-derived value) inside `CrdsValue::signable_data()` so verification inherently fails for values signed under a different cluster context, mirroring the approach `votor-messages/src/wire.rs` documents for Alpenglow's `get_vote_payload_to_sign()`. Additionally, `discard_different_shred_version` should require the shred-version match for all CRDS variants (not only `ContactInfo`), rather than falling back to "any record exists for this pubkey."

### Proof of Concept
1. Attacker passively observes gossip traffic on Cluster A (shred_version = X) and captures a validator V's signed `CrdsValue` carrying `CrdsData::RestartHeaviestFork` (or `Vote`/`EpochSlots`) — `signature = Ed25519_Sign(V_priv, wincode::serialize(CrdsData))`, per `CrdsValue::new` [4](#0-3) .
2. Attacker connects to Cluster B (shred_version = Y ≠ X), where V's identity pubkey already has a `ContactInfo` (or any) record in the local CRDS table — e.g. because V also runs (or previously ran) on Cluster B, or its pubkey was seen there for any reason.
3. Attacker wraps the captured bytes in a `Protocol::PushMessage(V_pubkey, [captured_value])` and sends it to a Cluster B node.
4. In `process_packets`, `discard_different_shred_version` inspects the payload: since the variant is not `ContactInfo`, it falls through to `crds.get_records(&value.pubkey()).next().is_some()` [5](#0-4) , which is `true` due to the precondition, so the value is *not* discarded despite the shred-version mismatch.
5. `verify_gossip_addr`/CRDS signature verification succeeds because the ed25519 signature is valid over `signable_data()`, which never encoded shred_version X — the check has no way to detect the value was produced for a different cluster.
6. The foreign, stale `RestartHeaviestFork`/`Vote`/`EpochSlots` entry is inserted into Cluster B's CRDS table under V's real pubkey, polluting Cluster B's view of V's state without V's participation or knowledge.

        self.get_signature()
            .verify(self.pubkey().as_ref(), self.signable_data().borrow())
    }

// Discards CrdsValues in PushMessages and PullResponses from nodes with
// different shred-version.
fn discard_different_shred_version(
    msg: &mut Protocol,
    self_shred_version: u16,
    crds: &Crds,
    stats: &GossipStats,
) {
    let (values, skip_shred_version_counter) = match msg {
        Protocol::PullResponse(_, values) => (values, &stats.skip_pull_response_shred_version),
        Protocol::PushMessage(_, values) => (values, &stats.skip_push_message_shred_version),
        // Shred-version on pull-request callers can be checked without a lock
        // on CRDS table and is so verified separately (by
        // check_pull_request_shred_version).
        Protocol::PullRequest(..) => return,
        // No CRDS values in Prune, Ping and Pong messages.
        Protocol::PruneMessage(_, _) | Protocol::PingMessage(_) | Protocol::PongMessage(_) => {
            return;
        }
    };
    let num_values = values.len();
    values.retain(|value| match value.data() {
        CrdsData::ContactInfo(ci) => ci.shred_version() == self_shred_version,
        // for any other CRDS types we check if we store anything already
        // for this pubkey, if we do we allow more values in
        _ => crds.get_records(&value.pubkey()).next().is_some(),
    });
    let num_skipped = num_values - values.len();
    if num_skipped != 0 {
        skip_shred_version_counter.add_relaxed(num_skipped as u64);
    }
}
