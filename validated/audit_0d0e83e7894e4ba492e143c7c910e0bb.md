## Analysis: Inconsistent/incomplete "HTML-unsafe character" escaping in ProtoJSON writers across language implementations

The SiYuan bug's core pattern is: a security-relevant character denylist that is incomplete relative to what actually reaches an unguarded HTML sink, so attacker-controlled content flows through unescaped into `innerHTML`. The closest verifiable analog in this Protobuf checkout is in the ProtoJSON *serialization* (writer) code: several officially supported per-language JSON writers implement a denylist of "characters unsafe to leave unescaped when the JSON output is embedded in HTML/JS," and that denylist is inconsistent and, in some backends, entirely absent, even though the code's own comments document the HTML-embedding threat model it is meant to defend.

### Evidence
- Java's `JsonFormat.java` explicitly escapes `<`, `>`, `&`, `=`, `'` in addition to the characters required by the JSON spec, with an explicit comment: "These characters are fully legal in JSON, but are escaped to prevent XSS risks." [1](#0-0) 
- The C++ core writer (`src/google/protobuf/json/internal/writer.cc`) only escapes `<` and `>` (plus some zero-width/bidi characters) — it never escapes `&`, `=`, or `'`. [2](#0-1) 
- C#'s `JsonFormatter.cs` `CommonRepresentations` table likewise escapes only `"`, `\`, `<`, `>` — no entries exist for `&`, `=`, or `'`. [3](#0-2) 
- PHP's `GPBJsonWire.php::escapedJson` escapes only JSON-mandated control chars, `"`, and `\` — none of `<`, `>`, `&`, `=`, `'`. [4](#0-3) 
- upb's `jsonenc_put_escaped_char` (the shared C JSON encoder backing Python's/Ruby's/PHP's native-extension protobuf implementations) escapes only the JSON-spec-mandated characters and raw control bytes — it has **no** HTML-safety escaping at all, not even `<`/`>`. [5](#0-4) 

### Consuming-application exposure assumption
Protobuf has no public network endpoint itself. The exposure model is: (1) a trusted consuming application parses an attacker-controlled Protobuf/ProtoJSON payload through a supported public parse API (e.g., `ParseFromString`, `MergeFrom`, `JsonFormat.parser().merge()`), populating a string field with attacker-chosen bytes; (2) that same application later re-serializes the message via the public JSON printer API (`JsonFormat.printer().print()`, `JsonFormatter.Format()`, `google::protobuf::json::MessageToJsonString`, upb's json encoder used by Python/Ruby/PHP) and embeds the resulting JSON text directly into an HTML document or inline `<script>` block — a documented, intended use case, since the writer code itself carries comments about "HTML security" and "prevent[ing] XSS risks."

### Why the check fails
The escaping logic in each backend acts as a denylist of "characters unsafe outside pure-JSON contexts." Java's denylist is the most complete (`< > & = '`), but the C++ core writer, C#, and PHP omit `&`, `=`, and `'`, and upb (shared by Python/Ruby/PHP native bindings) omits the entire HTML-safety set including `<`/`>`. An attacker who controls a string field can therefore produce values such as `</script><script>alert(document.domain)</script>` or `'; alert(document.domain); //` that pass through `upb`'s or C++'s/C#'s/PHP's JSON writer completely (or partially) unescaped, while the same value would be safely encoded by Java's writer. A consuming application that trusts the protobuf JSON writer's documented "HTML security" behavior — reasonably, given the comments in `writer.cc` and `JsonFormatter.cs` — and skips its own HTML-context escaping is exposed to injection when running on any backend other than Java (and even Java's own list omits e.g. backtick or other characters relevant in some embedding contexts).

### Impact
If a consuming application (built on the C++/C#/PHP/Python/Ruby ProtoJSON writers) serializes an attacker-influenced message directly into an HTML/`<script>` context without its own escaping, an attacker-controlled protobuf string field reaches the DOM unescaped, enabling script injection in that application's origin — the same end-state (attacker string reaching a live HTML/script sink due to an incomplete denylist) as the SiYuan report, just via a different producer/consumer pair.

### Likelihood
Requires: (1) an application accepting attacker-controlled Protobuf/ProtoJSON input into a message string field, and (2) that application re-serializing the message to JSON via a non-Java protobuf JSON writer and embedding the result in HTML/JS without its own output encoding. This is a plausible but not universal consuming-application pattern (SSR "embed initial state as JSON" is common); it is not exploitable purely within protobuf itself, since protobuf has no HTML rendering surface.

### Recommendation
Align all per-language ProtoJSON writers (`writer.cc`, `JsonFormatter.cs`, `GPBJsonWire.php`, `upb/json/encode.c`) to escape the same "HTML-unsafe" character set that `JsonFormat.java` already escapes (`<`, `>`, `&`, `=`, `'`), and clearly document in `SECURITY.md`/API docs that this escaping is a best-effort defense-in-depth measure, not a substitute for context-appropriate output encoding by the consuming application when embedding protobuf-generated JSON into HTML.

### Proof of Concept
Given a `TestAllTypes` message with `optional_string = "'; alert(document.domain); //"`:
- Java `JsonFormat.printer().print(message)` yields `\u0027; alert(document.domain); \/\/` (escaped, matching `testHtmlEscapeAllGsonCharacters`). [6](#0-5) 
- The equivalent message serialized via upb's JSON encoder (Python/Ruby/PHP native bindings) or via C++'s `JsonWriter::WriteEscapedUtf8` emits the literal, unescaped `'` character in the output, because neither `jsonenc_put_escaped_char` nor `MustEscape` treats `'` as requiring escaping. [5](#0-4) [7](#0-6) 
- If a consuming application embeds that JSON as `<script>var msg = '<%= json %>';</script>`, the unescaped `'` breaks out of the JS string literal, allowing the trailing `alert(document.domain);` to execute — an XSS outcome directly analogous to the SiYuan report's incomplete-denylist-into-unguarded-`innerHTML` chain.

static bool MustEscape(uint32_t scalar, absl::string_view& custom_escape) {
  switch (scalar) {
    // These escapes are defined by the JSON spec. We do not escape /.
    case '\n':
      custom_escape = R"(\n)";
      return true;
    case '\r':
      custom_escape = R"(\r)";
      return true;
    case '\t':
      custom_escape = R"(\t)";
      return true;
    case '\"':
      custom_escape = R"(\")";
      return true;
    case '\f':
      custom_escape = R"(\f)";
      return true;
    case '\b':
      custom_escape = R"(\b)";
      return true;
    case '\\':
      custom_escape = R"(\\)";
      return true;

    case kErrorSentinel:
      // Decoding failure turns into spaces, *not* replacement characters. We
      // handle this separately from "normal" spaces so that it follows the
      // escaping code-path.
      //
      // Note that literal replacement characters in the input string DO NOT
      // get turned into spaces; this is only for decoding failures!
      custom_escape = " ";
      return true;

    // These are not required by the JSON spec, but help
    // to prevent security bugs in JavaScript.
    //
    // These were originally present in the ESF parser, so they are kept for
    // legacy compatibility (and because escaping most of these is in good
    // taste, regardless).
    case '<':
    case '>':
    case 0xfeff:      // Zero width no-break space.
    case 0xfff9:      // Interlinear annotation anchor.
    case 0xfffa:      // Interlinear annotation separator.
    case 0xfffb:      // Interlinear annotation terminator.
    case 0x00ad:      // Soft-hyphen.
    case 0x06dd:      // Arabic end of ayah.
    case 0x070f:      // Syriac abbreviation mark.
    case 0x17b4:      // Khmer vowel inherent Aq.
    case 0x17b5:      // Khmer vowel inherent Aa.
    case 0x000e0001:  // Language tag.
      return true;

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
