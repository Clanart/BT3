### Title
Manipulable WOM/mWOM pool price makes `smartConvert`'s strict `_minRec` check revert, blocking `withdraw`/`deposit`/`depositLP` - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._sendRewards` unconditionally calls `SmartWomConvert.smartConvert(feeAmount, 0)` for any active fee with `isMWOM == true` whenever WOM rewards are harvested, and `smartConvert` self-imposes `_minRec = _amountIn` (the full input amount) as the success bound for the buyback+deposit conversion. Because `_sendRewards` runs inside `_toMasterWomAndSendReward`, which is invoked from `deposit`, `depositLP` and `withdraw` for every interaction with a pool, a revert inside `smartConvert` propagates all the way up and reverts the caller's principal deposit or withdrawal, even though the harvested reward is a small, secondary side-effect of the call.

### Finding Description
In `wombat/WombatStaking.sol`, `withdraw` (and `deposit`/`depositLP`) call `_toMasterWomAndSendReward`: [1](#0-0) 

which computes `womRewards` from the WOM balance delta of a `MasterWombat` harvest and forwards it, unconditionally and without try/catch, into `_sendRewards`: [2](#0-1) 

Inside `_sendRewards`, for every active fee entry with `isMWOM && rewardToken == wom` and `smartWomConverter != address(0)`, the WOM fee slice is sent through `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`: [3](#0-2) 

`SmartWomConvert.smartConvert` computes a `convertRatio` based on the live `currentRatio()` (an on-chain AMM quote from `womMWomPool`) and `maxSwapAmount()` (cash/liability skew of the WOM asset), then calls `_convertFor` with `_minRec` hardcoded to the *full* `_amountIn`: [4](#0-3) 

`_convertFor` performs an actual AMM swap for the buyback portion and reverts with `MinRecNotMatch` unless `convertAmount + amountRec >= _minRec`: [5](#0-4) 

Because `womMWomPool` is a standard, permissionlessly tradable Wombat pool, its exchange rate (used both in `currentRatio()` and in the actual swap executed by `_convertFor`) can be pushed by anyone via ordinary swaps or front-running the harvest-triggering transaction. Since the success bound is the *entire* `_amountIn` rather than a rate-derived tolerance, any adverse price movement/slippage/fee on the buyback swap (including trivial rounding-to-zero for small harvested amounts) is enough to make `convertAmount + amountRec < _amountIn` and revert `smartConvert`. There is no try/catch anywhere between `smartConvert` and `withdraw`/`deposit`/`depositLP`, so this revert unwinds the whole outer transaction, including the user's principal transfer/receipt-token burn/mint logic in `withdraw`: [6](#0-5) 

`nonReentrant`/`whenNotPaused`/`_onlyPoolHelper` modifiers do not mitigate this — they only gate *who* can call `withdraw`, not the internal revert caused by the harvest-and-convert side effect that is inseparable from the withdraw path.

### Impact Explanation
Once the WOM/mWOM pool ratio is pushed (by anyone, including an attacker who front-runs a victim's withdrawal, or simply by ambient market conditions) to a point where the buyback swap output cannot cover the strict full-amount `_minRec`, every subsequent `deposit`, `depositLP`, and `withdraw` call for that pool reverts, because they all route through `_toMasterWomAndSendReward` → `_sendRewards` → `smartConvert`. This blocks legitimate users from withdrawing or depositing principal into a pool that is otherwise fully solvent — a temporary freezing of funds driven entirely by a manipulable external AMM price, matching the "High – Temporary freezing of funds for at least 24 hours" impact class if the attacker sustains the unfavorable price (or repeatedly front-runs) for that duration.

### Likelihood Explanation
Preconditions: `smartWomConverter` must be configured (owner action, standard operational state for this feature) and at least one `feeInfos` entry with `isMWOM = true` and `isActive = true` must exist — this is the intended fee configuration for buybacks, not a misconfiguration. Given that, the exploit only requires an unprivileged actor able to trade on the public `womMWomPool` (no special role needed) to move `currentRatio()`/swap execution price unfavorably immediately before or during a legitimate `withdraw`/`deposit` call, or to exploit the case where a small harvested WOM amount rounds the buyback swap output to less than the buyback input. This is repeatable and does not require compromising any privileged role.

### Recommendation
- Do not let `smartConvert`'s internal buyback slippage protection use the entire `_amountIn` as `_minRec`; compute a rate-derived, slippage-tolerant minimum instead.
- Wrap the `smartConvert` call in `_sendRewards` in a try/catch (or otherwise isolate reward-forwarding failures) so a revert in the optional MWOM-conversion fee path cannot block the queuing of the remaining rewards or, more importantly, the caller's principal deposit/withdraw logic in `WombatStaking.deposit`/`depositLP`/`withdraw`.
- Alternatively, decouple harvesting/fee-forwarding from the principal deposit/withdraw code path (e.g., make harvest failures degrade gracefully by falling back to the non-swap `mWom.deposit` path, or defer to a separate `harvest()` call that can fail independently).

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatStaking`, a mock `MasterWombat`, mock `IWombatPool`, `SmartWomConvert` wired to a mock `IWombatRouter`/`womMWomPool`/`womAsset` whose `cash()`/`liability()` and swap output are test-controllable.
2. Register a pool, add a fee entry with `isMWOM = true, isActive = true`, set `smartWomConverter`.
3. Seed the mock `MasterWombat` to emit a small WOM harvest amount on `withdraw`/`deposit` calls.
4. Table-test over boundary values of `_liquidity`/`_minAmount` (0, 1, typical, max uint) forwarded from a pool-helper-simulating caller to `WombatStaking.withdraw`, while configuring the mock router/asset such that:
   - Row A: `mWomToWom >= buybackThreshold` → `convertRatio = DENOMINATOR`, no swap, `smartConvert` succeeds, `withdraw` succeeds.
   - Row B: `mWomToWom < buybackThreshold` and mock router returns `amountRec < buybackAmount` (simulating adverse price/slippage) → assert `withdraw` reverts with `MinRecNotMatch` bubbled up, and assert the user's principal (`depositToken`) was NOT transferred out (i.e., `beforeWithdraw` balance unchanged), demonstrating principal withdrawal is blocked by the reward-conversion path regardless of `_liquidity`/`_minAmount` values.
   - Row C: harvested amount is set to 1 wei so that `buybackAmount` rounds any swap output to 0 while `buybackAmount > 0` → assert revert on every row of `_liquidity`/`_minAmount`.
5. Assert in all reverting rows that no funds were queued into `poolInfo.rewarder` (reconciliation invariant broken — the whole harvested `womRewards` is lost/blocked, not just the mWOM-fee slice) and that the withdraw's underlying `IWombatPool.withdraw` was never reached.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
