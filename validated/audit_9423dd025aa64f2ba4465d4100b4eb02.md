### Title
Arbitrary file read via tracked symlink in working-directory changes bypasses `resolveWithin` symlink guard - ([File: app/src/lib/git/diff.ts])

### Summary
GitHub Desktop already contains a hardened path-resolution helper, `resolveWithin` (`app/src/lib/path.ts:36-99`), which resolves a repo-relative path with `fs.realpath` and rejects any result that escapes the repository root via a symlink. It is correctly used in a few call sites, e.g. `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:390-407`) and `openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1957-1972`). However, several other code paths that turn a **repository-relative path taken from a cloned/fetched repository's working tree** into a filesystem path still use plain `Path.join(repository.path, file.path)` and then read the file directly with `fs`, with no symlink/traversal check at all.

The clearest instance is `getWorkingDirectoryImage`: [1](#0-0) 

### Finding Description
`getWorkingDirectoryImage` is invoked when the Changes view renders an image preview for a working-directory file whose extension is in `imageFileExtensions` (`.png`, `.jpg`, etc., see `app/src/lib/git/diff.ts:94-107`). It builds the on-disk path with `Path.join(repository.path, file.path)` and calls `readFile()` directly — this follows OS-level symlinks, unlike `git diff`/`git show`, which treat a symlink entry (mode `120000`) as a text blob containing only the link target string.

Git fully supports committing symlinks. An attacker who controls a repository the victim clones or pulls (a public/malicious repo, or a coworker/CI pushing to a shared repo) can commit a tracked symlink, e.g. `logo.png -> ../../../../.ssh/id_ed25519` (or, on Windows, a symlink into `%USERPROFILE%\.aws\credentials`, provided Developer Mode/symlink support is enabled so `git checkout` materializes it). When the victim opens the Changes tab or reviews the commit, GitHub Desktop detects the file by extension and calls `getWorkingDirectoryImage`, which reads through the symlink and returns the target file's raw bytes as a base64 data URI that gets rendered/stored in the renderer process — i.e., the *actual contents of a file outside the repository* are read and surfaced in the UI, not the symlink's target string that `git` itself would show.

The same missing-guard pattern (plain `Path.join` + direct `fs` read/open, no `resolveWithin`) also appears in:
- `getNewFileContent` in the syntax highlighter, which calls `readPartialFile(Path.join(repository.path, file.path), ...)` for `WorkingDirectoryFileChange` and feeds the bytes into the diff view as text [2](#0-1) 
- `revealInFileManager`, which reveals `Path.join(repository.path, path)` in Finder/Explorer [3](#0-2) 
- `getLargeFilePaths`, which `stat()`s `join(repository.path, file.path)` for every staged file [4](#0-3) 
- `onOpenInExternalEditor` in the main UI, which opens `Path.join(repository.path, path)` in the user's configured external editor [5](#0-4) 

None of these validate that the resolved real path stays inside `repository.path`, unlike the `resolveWithin`-based call sites.

### Impact Explanation
This is a direct analog of the reported bug class: a directory entry that is actually a symlink lets the application escape the intended root and disclose file contents outside it. Here the "web root" is the repository working directory, and the untrusted content is fully attacker-controlled (a cloned/pulled/fetched repository). The most severe path — `getWorkingDirectoryImage` and `getNewFileContent`/`readPartialFile` — causes GitHub Desktop to read and display the contents of an arbitrary file the victim's OS user can access (SSH keys, cloud credential files, browser profile files, etc.) purely as a side effect of normal repository review (opening the Changes tab or a commit diff), with no explicit "open file" action required. This matches the report's "Medium" impact class (unauthorized read outside intended root) and is worse than a UI action like "reveal in Finder" because it happens implicitly during diff rendering.

### Likelihood Explanation
Likelihood is high for the specific primitive (any repository can carry a tracked symlink; `git checkout`/`clone` materializes it on macOS/Linux by default, and on Windows when symlink support is enabled), and the trigger (viewing the Changes/diff view) is normal, expected user behavior — it requires no unusual steps, admin rights, or pre-existing compromise, consistent with the "unprivileged, attacker-controlled repo content" impact criteria.

### Recommendation
Route every path derived from `file.path` (or any other repository-relative, attacker-influenced path) through `resolveWithin` (`app/src/lib/path.ts`) before using it with `fs`/`shell` APIs, mirroring the pattern already used in `buildConflictContext` and `openRepositoryFromUrl`. At minimum, add this guard to `getWorkingDirectoryImage`, `getNewFileContent`/`readPartialFile`, `revealInFileManager`, `getLargeFilePaths`, and `onOpenInExternalEditor`, and reject (or flag as "outside repository") any path whose real, symlink-resolved target does not stay within `repository.path`.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink: `git symlink logo.png -> ../../../../.ssh/id_ed25519` (relative symlink chosen so it escapes an arbitrary clone location), commits and pushes it.
2. Victim clones or pulls the repository with GitHub Desktop on macOS/Linux (or Windows with symlink support enabled); `git checkout` creates `logo.png` as a real OS symlink pointing at the victim's SSH private key.
3. Victim opens the repository in GitHub Desktop and views the commit/diff containing `logo.png` (or it appears as a working-directory change).
4. Because `logo.png` matches `imageFileExtensions`, GitHub Desktop calls `getWorkingDirectoryImage(repository, file)`, which does `readFile(Path.join(repository.path, 'logo.png'))` — following the symlink — and returns the private key bytes base64-encoded for rendering as an image, without ever checking that the resolved real path stays inside the repository (contrast with `resolveWithin`'s explicit `realpath` check at `app/src/lib/path.ts:64-71`).

export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
