# CEI Violation in `IntentGatewayV2.withdraw()` Enables Escrow Over-Redemption on Duplicate Token Entries - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in the Tron `IntentGatewayV2` sends escrowed tokens to the beneficiary via low-level `.call` **before** decrementing the corresponding `_orders[commitment][token]` accounting slot, the same check-effects-interactions violation described in the external report. Unlike the main EVM `IntentGatewayV2`/`IntrinsicIntents` implementation — which was already hardened by setting `_filled[commitment]` at the very top of the fill functions (see `IntrinsicIntentsReentrancyTest.sol`) — the per-token escrow balance in this `withdraw()` loop is still only updated *after* the external transfer completes for each token. [1](#0-0) 

### Finding Description
`withdraw()` is invoked from `onAccept()` (RedeemEscrow / RefundEscrow) and from `onGetResponse()`, both restricted with `onlyHost`. [2](#0-1) 

Inside the token loop:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
// external call happens here (ETH .call or ERC20 .call transfer)
_orders[body.commitment][token] -= amount;   // decrement happens AFTER the call
```
The guard tests only `== 0` (an existence check), not `>= amount` (a sufficiency check), and the balance is not zeroed/decremented until after the interaction. `body` (the `WithdrawalRequest`, including its `tokens` array) is decoded from a cross-chain message whose contents ultimately trace back to the order's `inputs`, which are supplied by the order creator at placement time. If the token list for a given commitment contains the same token address more than once with amounts that individually are smaller than the total escrowed balance, each duplicate entry passes the `== 0` check (since the balance is only reduced by `amount`, not zeroed, after each iteration) and triggers another external transfer before the balance is fully drained — allowing repeated redemption of the same escrow slot in a single `withdraw()` execution, driven entirely by the interaction-before-effect ordering that the check-effects-interactions pattern is meant to prevent.

While `_filled[body.commitment] = beneficiary` is set at the top of `withdraw()` (guarding against replay across *separate* `onAccept`/`onGetResponse` invocations), that guard does nothing to protect the per-token accounting mutated *inside* the very call where the external transfers occur — it does not stop over-redemption arising from within the same loop.

### Impact Explanation
A successful over-redemption results in transfer of more escrowed tokens (native or ERC20) than were legitimately deposited for an order, directly draining the gateway's escrow balance — matching the "stealing or loss of funds" and "logic attacks / duplicate settlement" bounty categories. This affects the intent-settlement/escrow custody path, which holds user and solver funds across chains.

### Likelihood Explanation
The order creator (an unprivileged, permissionless actor placing intents) fully controls the `inputs`/token list encoded into the order and consequently into the eventual `WithdrawalRequest.tokens` array processed by `withdraw()`. No relayer, prover, or governance collusion is required — only that duplicate token entries with amounts below the true escrowed total are accepted upstream when the order is placed and mirrored through to the redeem/refund message. This is a structural weakness in the balance-check design (`== 0` instead of comparing consumed amount to remaining balance) compounded by performing the transfer before updating that same balance.

### Recommendation
Change the per-token guard to `require(_orders[body.commitment][token] >= amount, UnknownOrder())` and move the state update (`_orders[body.commitment][token] -= amount`) to occur **before** the external `.call` transfer in each loop iteration, mirroring the CEI fix already applied to `_filled[commitment]` at the top of the function and to `IntrinsicIntents._fillSameChain`/`_fillCrossChain` on the main EVM contract. Apply the same effects-before-interaction ordering to the transaction-fee redemption block that follows.

### Proof of Concept
1. Place an order whose `inputs` include the same token address twice, e.g. `[{token: T, amount: X}, {token: T, amount: X}]`, with the gateway escrowing `2X` of `T` in `_orders[commitment][T]`.
2. Trigger settlement so the destination gateway dispatches a `RedeemEscrow`/`RefundEscrow` message whose `WithdrawalRequest.tokens` mirrors the duplicated entries `[{T, X}, {T, X}]`.
3. On the source chain, `onAccept()` → `withdraw()` executes the loop:
   - i=0: `_orders[commitment][T] == 2X` (nonzero) → transfer `X` to beneficiary → decrement to `X`.
   - i=1: `_orders[commitment][T] == X` (still nonzero, passes the `==0` check though only `X` remains and `X` is being requested again) → transfer another `X` to beneficiary → decrement to `0`.
4. Beneficiary receives `2X` total from an order that should have paid out `X` for token `T` combined with any other legitimately escrowed amount, evidencing over-redemption enabled by checking token-transfer eligibility with a weak `==0` test performed around an external call rather than a strict pre-decrement sufficiency check.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
