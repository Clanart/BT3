### Title
Attacker-controlled participant count in `ThresholdKeys::read` causes disproportionate memory allocation (uncontrolled resource consumption) - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::<C>::read` deserializes a `n: u16` field directly from the reader and immediately uses it to pre-size `Vec::with_capacity(n)` for `Interpolation::Constant`, and to drive a `read_G` loop over `1 ..= n` for the verification-share `HashMap`. An unprivileged party supplying untrusted bytes to `ThresholdKeys::read` (one of the sanctioned reachable read entry points) controls `n` up to `u16::MAX` (65535), causing a multi-megabyte allocation — and up to 65535 point-deserialization attempts — from a 2-byte length prefix, before `ThresholdParams::new` validates `n` against `t`/`i` at the end of the function. This is the same bug class as CVE-2020-14340: attacker-reachable resource growth (memory/handles) divorced from actual input size, enabling denial of service.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` as raw u16s from the wire, then:

- `Interpolation::Constant` branch: `let mut res = Vec::with_capacity(usize::from(n))` followed by `for _ in 0 .. n { res.push(C::read_F(reader)?) }` — [1](#0-0) 
- Verification shares: `for l in (1 ..= n).map(Participant) { verification_shares.insert(l, C::read_G(reader)?) }` — [2](#0-1) 
- Only afterwards does `ThresholdParams::new(t, n, i)` validate consistency — [3](#0-2) 

Two resource issues result:

1. **Pre-allocation amplification**: `Vec::with_capacity(65535)` allocates capacity for 65535 field elements (~2 MB for 32-byte fields, ~3.7 MB for ed448's 56-byte `F`) triggered by a 2-byte wire value. Nothing bounds `n` to the actual multisig's expected size, and the check `ThresholdParams::new` runs only *after* the allocation and read loop have already consumed resources.

2. **Bounded-but-large work loop**: the `read_G`/`read_F` loops attempt up to 65535 cryptographic deserializations (point decompression is non-trivial per element) driven entirely by the attacker's claimed `n`. While the stream ends early, each supplied point is fully processed (subgroup-checked decompression) before any consistency check rejects the message.

`ThresholdKeys::read` is explicitly in the allowed reachable-surface list (untrusted bytes fed to `ThresholdKeys::read`), and the file/function are inside in-scope `crypto/dkg`.

### Impact Explanation
Repeated submissions of crafted `ThresholdKeys` blobs with `n = 0xFFFF` cause the deserializer to allocate ~2–4 MB per call (plus HashMap growth and up to 65535 decompression attempts where bytes are supplied) purely from attacker-controlled header fields. This is a denial of service vector against any node/coordinator/processor that ingests serialized `ThresholdKeys` from untrusted input — matching the CWE-400 uncontrolled-resource-consumption class of the XNIO advisory. No secret material is needed; the amplification ratio (2 bytes → megabytes of allocation) makes sustained memory pressure cheap to mount.

### Likelihood Explanation
Reachability requires an integration that calls `ThresholdKeys::read` on peer-supplied bytes before authentication — plausible wherever serialized keys are exchanged or recovered. The cost to the attacker is minimal (a handful of bytes per attempt); the victim cost is an allocation two orders of magnitude larger plus deserialization work. Impact is availability-only (Medium), consistent with the source advisory's severity.

### Recommendation
Validate `n` *before* allocating: call `ThresholdParams::new(t, n, i)` (or at minimum bounds-check `n` against a protocol maximum and against `t`) immediately after reading the header, and reject messages whose claimed sizes exceed the remaining input length. Avoid `Vec::with_capacity(n)` with untrusted `n`; either cap it or let the vector grow as elements are actually read. Optionally reject trailing/oversized encodings once the expected participant count is known.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, Participant};
use dkg::tests::*; // curve fixture

// Construct a minimal malicious ThresholdKeys blob for curve C (e.g. Ristretto):
// [C::ID len (u32 LE)] [C::ID bytes] [t: u16 LE] [n: u16 LE] [i: u16 LE] [interpolation: u8]
// Set t = 1, n = 0xFFFF, i = 1, interpolation = 0 (Constant).
// ThresholdKeys::<C>::read will execute Vec::with_capacity(65535) for the
// Interpolation::Constant arm — a ~2-4 MB allocation — before ever touching
// ThresholdParams::new, and will then attempt 65535 read_F calls against the
// (short) stream. Repeating with fresh blobs yields steady memory churn and
// pressure with attacker cost of ~10 bytes per attempt.
```
The amplification is visible directly at `crypto/dkg/src/lib.rs:608` (`Vec::with_capacity(usize::from(n))`) and `crypto/dkg/src/lib.rs:621` (`for l in (1 ..= n)`), with the consistency check deferred to `crypto/dkg/src/lib.rs:625`.

Note: I verified the read paths in `crypto/schnorr` (`SchnorrAggregate::read` grows incrementally with actual input — no amplification), `crypto/dleq` (`MultiDLEqProof::read` takes `discrete_logs` as a caller param, not wire data), `crypto/dkg/pedpop` (`Commitments::read` bounded by local `params.t()`), and `crypto/dkg/musig` (`check_keys` caps at u16 and dedups). The `ThresholdKeys::read` path is the strongest in-scope analog; a larger unbounded `Vec::with_capacity(u32)` exists at `coordinator/tributary/src/block.rs:92` but that crate is outside the permitted scope.
