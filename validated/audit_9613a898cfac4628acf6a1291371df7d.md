### Title
Cross-chain `UpdateParams` governance requests to IntentGatewayV2 never expire and can silently revert live protocol parameters - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._updateParams` (called from `IntentGatewayV2.onAccept` when `RequestKind.UpdateParams` arrives) unconditionally overwrites `_params` and `_destinationProtocolFees` with whatever payload is in the delivered ISMP request, with no timestamp/version/freshness check against the parameters currently in effect. Because the outbound governance `PostRequest` that carries this payload is dispatched once from Hyperbridge and then simply sits as an unexecuted commitment until *any* relayer chooses to deliver it — with no expiry — a stale `UpdateParams` message that governance intended to be superseded (e.g. it was queued, then a corrected/newer update was issued before the first was ever relayed) can still be delivered and applied at an arbitrary point in the future, clobbering the live configuration. This is the same broken invariant as the reported `pendingChanges` issue: a delayed, non-expiring privileged change that "becomes irrelevant… but is executed by any user in any order."

### Finding Description
`IntentGatewayV2`/`IntentsBase` receives governance instructions exclusively through `onAccept`, gated only by `request.source == hyperbridge` [1](#0-0) . The `UpdateParams` handler, `_updateParams`, does the following with zero ordering/freshness protection: [2](#0-1) 

It validates only structural bounds (`_validateParams`) — never a monotonic nonce, a version number, or a "not older than currently applied" timestamp — before blindly overwriting `_params` (host, dispatcher, priceOracle, protocolFeeBps, surplusShareBps) and `_destinationProtocolFees`.

Hyperbridge's ISMP layer treats these governance-originated dispatches as ordinary requests: `dispatch_request` records a commitment and puts the request into an off-chain queue keyed only by content hash, with no ordering guarantee across multiple governance dispatches to the same module [3](#0-2) . Delivery is entirely relayer-driven and permissionless — any relayer can deliver any still-undelivered commitment whenever it wants, and other parts of the codebase explicitly document the "timeout = 0 → no expiry" pattern used for governance/system messages (see the LZ endpoint's `dispatch` with `timeout: 0` and its own comment "no expiry") [4](#0-3) . The host-executive and relayer withdrawal pallets likewise dispatch with `timeout: 0` for cross-chain governance/withdraw payloads [5](#0-4) .

So: Hyperbridge governance can dispatch `UpdateParams(A)`, then later (because A was wrong, is now stale, or was meant to be replaced) dispatch `UpdateParams(B)` which gets delivered and applied first. `UpdateParams(A)`'s commitment is still sitting, undelivered, in the request queue with no expiry. Any relayer — an unprivileged, permissionless actor — can later deliver `UpdateParams(A)`, and `onAccept`/`_updateParams` will happily apply it, reverting `_params` (fee rates, dispatcher address, price oracle, host address) back to the stale values with no check that a newer configuration already superseded it.

### Impact Explanation
`_params.protocolFeeBps`, `_params.surplusShareBps`, `_params.dispatcher`, and `_params.priceOracle` directly control fee extraction and calldata routing for every subsequent order filled through the gateway (`_execute` dispatches to `_params.dispatcher`, `_withdraw`/fee accounting use `_params.protocolFeeBps`/`surplusShareBps`). Reverting to a stale, lower/zero fee or an old dispatcher/oracle address changes how much protocol revenue is collected and which contract executes solver calldata for every order until someone notices and reissues the fix — a stale, unauthenticated-by-freshness configuration is fully able to move funds incorrectly (misrouted protocol fees, wrong surplus split, stale price oracle mispricing outputs). This satisfies the "logic attack / transaction manipulation" bucket in the bounty scope: production, unprivileged (any relayer), and it corrupts financial state (`_params`) that gates real fund flows.

### Likelihood Explanation
Requires only that Hyperbridge governance issue two `UpdateParams` dispatches for the same gateway before the first is delivered (a realistic operational sequence — e.g. correcting a misconfigured fee shortly after dispatch, or governance changing its mind before relayers act), and that any relayer subsequently delivers the older, undelivered commitment. No relayer collusion or compromise is needed — relayers are simply doing their normal, permissionless job of delivering any pending commitment they can prove; delivering the "wrong" (older) one is indistinguishable from delivering the "right" one from the contract's point of view because there is no ordering check.

### Recommendation
Add a monotonically increasing version/nonce (or a `lastUpdated` timestamp compared against `block.timestamp`/an included timestamp field) to `Params`/`ParamsUpdate`, and have `_updateParams` reject any update whose version/timestamp is not strictly greater than the one currently stored. Alternatively, give governance-originated `PostRequest`s a bounded `timeoutTimestamp` so stale configuration changes cannot be delivered indefinitely, and/or require the coprocessor pallet to track and only allow the latest dispatched params commitment to be applied (invalidating/removing superseded ones from `RequestCommitments` when a newer update is dispatched).

### Proof of Concept
1. Governance dispatches `UpdateParams(A)` (e.g., `protocolFeeBps = 500`) from the intents-coprocessor pallet targeting `IntentGatewayV2` on chain X. This creates commitment `cA` in `RequestCommitments` with no timeout.
2. Before any relayer delivers `cA`, governance realizes 500bps is wrong and dispatches `UpdateParams(B)` (`protocolFeeBps = 50`), commitment `cB`. A relayer delivers `cB` first; `_params.protocolFeeBps` becomes 50 and users/solvers begin transacting under this rate.
3. Weeks later, an ordinary relayer (looking for any undelivered commitment to earn delivery rewards) finds `cA` still un-delivered in the ISMP request trie and submits the state/consensus proof to deliver it to `IntentGatewayV2.onAccept`.
4. `onAccept` decodes `RequestKind.UpdateParams`, calls `_updateParams(A)`, which passes `_validateParams` (structurally valid) and overwrites `_params.protocolFeeBps` back to 500 — silently reverting governance's corrected configuration with no error, no revert, and no way for the contract to detect that `A` was stale relative to `B`.

    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }

	/// Dispatch an outgoing request, returns the request commitment
	pub fn dispatch_request(request: Request, meta: FeeMetadata<T>) -> Result<H256, ismp::Error> {
		let commitment = hash_request::<Pallet<T>>(&request);

		if RequestCommitments::<T>::contains_key(commitment) {
			Err(ismp::Error::Custom("Duplicate request".to_string()))?
		}

		let (dest_chain, source_chain, nonce) =
			(request.dest_chain(), request.source_chain(), request.nonce());
		let leaf_index_and_pos = T::OffchainDB::push(Leaf::Request(request));
		// Deposit Event
		Pallet::<T>::deposit_event(Event::Request {
			request_nonce: nonce,
			source_chain,
			dest_chain,
			commitment,
		});

		RequestCommitments::<T>::insert(
			commitment,
			RequestMetadata {
				offchain: LeafIndexAndPos {
					leaf_index: leaf_index_and_pos.index,
					pos: leaf_index_and_pos.position,
				},
				fee: meta,
				claimed: false,
			},
		);

		Ok(commitment)
	}
