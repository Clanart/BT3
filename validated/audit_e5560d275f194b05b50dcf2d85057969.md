Based on my investigation, the strongest analog is in `InternalLazyField.java`, where the double-checked-locking pattern for lazy message parsing is missing its in-lock re-check — the same class of bug as the nearcore issue (checking shared state without re-verifying it once the lock is held, allowing duplicate processing of the same data).

### Title
Missing double-check inside lock in `InternalLazyField.ensureInitialized()` allows duplicate/racy re-parsing and violates the "value set once" invariant - (File: `java/core/src/main/java/com/google/protobuf/InternalLazyField.java`)

### Summary
`InternalLazyField` documents that "once `value` ... is set, [it] will not be changed" [1](#0-0)  and its `ensureInitialized()` method is meant to be the thread-safe gate that lazily parses a submessage's bytes exactly once. It performs the classic double-checked-locking pattern: check `value != null` outside the lock, then acquire `synchronized (this)`. However, unlike the closely related `LazyFieldLite.ensureInitialized()`, which re-checks `value != null` a second time immediately after acquiring the lock [2](#0-1) , `InternalLazyField.ensureInitialized()` omits this second check [3](#0-2) .

### Finding Description
`ensureInitialized()` is:
```
private void ensureInitialized() throws InvalidProtocolBufferException {
  if (value != null) {
    return;
  }
  synchronized (this) {
    if (corrupted) {
      throw new InvalidProtocolBufferException("Repeat access to corrupted lazy field");
    }
    ... parse bytes, assign value ...
  }
}
``` [4](#0-3) 

If two threads call `getValue()`/`ensureInitialized()` concurrently while `value == null`, both pass the unsynchronized fast-path check and both enter the `synchronized` block sequentially (mutual exclusion serializes them, but does not prevent redundant work). The first thread parses `bytes` and assigns `value`. Because the second thread never re-checks `value != null` after acquiring the lock, it unconditionally re-parses the same `bytes` via a fresh `CodedInputStream` and reassigns `value` to a brand-new `MessageLite` instance, silently discarding the first thread's parsed object. This directly violates the class's own documented invariant that `value`, once set, "will not be changed" [1](#0-0) .

This is structurally the same defect class as the NEAR nearcore bug: a shared piece of state (`processed_witnesses` there, `value`/lazy-parse-once semantics here) is checked outside the lock, but the check is not repeated once the lock is actually held, so the same unit of work (processing a state witness / parsing the lazy bytes) can be performed twice by racing threads even though the code intends "process once."

The consuming application is any multi-threaded Java service that shares a parsed `Message` containing a lazily-parsed submessage/extension (`[lazy=true]` field or lazily-parsed extension) across threads and calls accessors (`getValue()`, `hashCode()`, `equals()`, `toString()`) concurrently before the field has been touched — a supported public API usage pattern that requires no privileged access.

### Impact Explanation
The observable effect is a benign-looking silent replacement of the cached `value` reference with a second, independently parsed instance:
- Any thread that has already captured a reference to the first parsed `MessageLite` continues to safely use it (Java object references are stable, and reads/writes to `value` are `volatile`), so there's no classic UAF/memory-safety issue.
- However, the object-identity guarantee implied by the "set once" invariant is broken. Downstream code within the class (e.g., `mergeFrom(InternalLazyField, InternalLazyField)` reading `other.value`) or code outside the class that relies on this class's contract of single-assignment for equality/caching/memoization purposes can observe two different `MessageLite` instances for the same field across calls, which can produce subtle behavioral inconsistencies (e.g., double reference-identity caches, extra recursive re-parsing cost for lazy fields containing nested lazy fields/extensions, doubled work in extension registries touched during parsing).
- Because a full second parse is triggered, any registry/extension-resolution side effects performed during parsing (e.g., extension lookups) are executed twice, redundantly.

This is lower severity than the near case (which affected actual protocol state-witness processing), since no confidentiality/integrity boundary of the wire format itself is crossed and no memory corruption occurs — but it is a genuine, reproducible violation of a documented thread-safety/idempotency invariant reachable from ordinary concurrent parsing/access of untrusted-but-valid bounded protobuf data.

### Likelihood Explanation
Triggering requires only:
1. A message with a lazily-parsed field/extension containing attacker-controlled (but validly-encoded, bounded) bytes.
2. Two or more application threads accessing that field concurrently before it has been parsed once (a supported, common pattern — the library's own `InternalLazyField`/`LazyFieldLite` distinction and the project's `thread_safe_test.py` / `message_lock_test.cc` files show this exact concurrency scenario is explicitly tested for other lazy-init code paths in the codebase, confirming it's a recognized class of hazard).

The race window is real but narrow (bounded by parse duration), so it requires genuine concurrent access timed closely, similar to the near report's own caveat that the race "happens only if ... multiple parts are delivered ... at very low latencies."

### Recommendation
Add the missing double-check immediately after acquiring the lock in `InternalLazyField.ensureInitialized()`, mirroring `LazyFieldLite.ensureInitialized()`:
```java
synchronized (this) {
  if (value != null) {
    return;
  }
  if (corrupted) {
    throw new InvalidProtocolBufferException("Repeat access to corrupted lazy field");
  }
  ...
}
``` [5](#0-4) 

### Proof of Concept
Conceptually (mirroring the existing `testConcurrentLazyUnpackAndRead`/`testConcurrentGetFieldValueRace` style tests already present in the repo [6](#0-5) , but for the Java `InternalLazyField` class):
1. Construct an `InternalLazyField` with a valid, bounded serialized submessage in `bytes` and `value == null`.
2. Spawn two threads that both call `getValue()` (which calls `ensureInitialized()`) using a `CyclicBarrier`/`Barrier` to maximize the chance both threads pass the `if (value != null) return;` fast-path check before either enters the `synchronized` block.
3. Instrument/spy on `defaultInstance.getParserForType().parsePartialFrom(...)` (or count invocations) to observe that it is invoked twice for the same `InternalLazyField` instance and that the final `value` reference differs from the first parsed object that a racing thread might have already returned to its caller — demonstrating the invariant violation and duplicated parse work described in `ensureInitialized()` [4](#0-3) .

  private void ensureInitialized() throws InvalidProtocolBufferException {
    if (value != null) {
      return;
    }

    synchronized (this) {
      if (corrupted) {
        throw new InvalidProtocolBufferException("Repeat access to corrupted lazy field");
      }
      try {
        // `bytes` is guaranteed to be non-null since `value` was null.
        CodedInputStream input = bytes.newCodedInput();
        input.enableAliasing(/* enabled= */ true);
        // When lazyExtensionEnabled() returns true, it means all extensions including MessageSet's
        // will be fully parsed. When it returns false, it basically implies this can only be a
        // MessageSet extension, and we should fall back to the old behavior of silently returning
        // the default instance on corrupted extensions i.e. a full parse.
        value =
            extensionRegistry.lazyExtensionEnabled()
                ? defaultInstance.getParserForType().parsePartialFrom(input, extensionRegistry)
                : defaultInstance.getParserForType().parseFrom(input, extensionRegistry);
        input.checkLastTagWas(0);
      } catch (InvalidProtocolBufferException e) {
        corrupted = true;
        throw e;
      }
    }
  }
