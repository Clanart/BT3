### Title
Refunds of unparseable deposits are sent to the owner of `tx.input[0]`, losing user funds for multi-input transactions - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
When an external user deposits BTC to a multisig's External address but the transaction carries no parseable InInstruction, the processor refunds the output to a `presumed_origin` computed solely from the transaction's first input (`tx.input[0]`). For transactions with multiple inputs (batched withdrawals, CoinJoin, PayJoin, consolidation spends), `input[0]` need not belong to the depositor, so the refund is routed to a third party and the depositor's funds are lost — the direct analog of receiving `msg.value` alongside a mismatched parameter instead of rejecting.

### Finding Description
`get_outputs` scans every non-coinbase transaction and, for each matched output, sets `presumed_origin` by resolving only `tx.input[0]`'s previous output script_pubkey [1](#0-0) . All outputs of that transaction get this same origin [2](#0-1) . Downstream, when `instruction_from_output` fails to parse an instruction for an External output, the output is queued as `PlanFromScanning::Refund(output, refund_to)` [3](#0-2) . Nothing validates that `input[0]` corresponds to the party that funded the matched output, that it is the only input, or even that the depositor controls it.

### Impact Explanation
A depositor whose transaction lacks a parseable instruction (or who deposits via a wallet/exchange that batches inputs) has their funds refunded to whoever owns `tx.input[0]`. In CoinJoin/PayJoin flows the coordinator or counterparty typically controls earlier inputs; in batched exchange withdrawals `input[0]` is the exchange's wallet, which is at best custodial recovery, at worst credits a random co-spender. The multisig spends the output to that script_pubkey, so the depositor's BTC is irrecoverably sent to the wrong party. This is permanent fund loss reachable entirely by an unprivileged user broadcasting a transaction.

### Likelihood Explanation
Medium likelihood: it requires a deposit transaction with ≥2 inputs (or a PayJoin where the receiver inserts inputs) plus an absent/malformed instruction — both realistic with modern wallets and batching services. `Prevouts::All` signing commits to all inputs, but no check anywhere ties `presumed_origin` to the actual funder of the scanned output.

### Recommendation
Only assign `presumed_origin` when `tx.input.len() == 1`, and refund to that single input's source. For multi-input transactions without a parseable instruction, either skip the refund (hold the output for manual resolution) or require an explicit instruction/output-derived refund path rather than guessing a funder from input ordering.

### Proof of Concept
1. Multisig `key` activates; `scanner()` registers External/Branch/Change/Forwarded offsets [4](#0-3) .
2. Attacker-adjacent user (or honest depositor via a batching wallet) broadcasts a tx with `input[0]` owned by a third party and `input[1]` funding an output paying `p2tr_script_buf(key)`.
3. `get_outputs` matches the output via `self.scripts.get(&output.script_pubkey)` [5](#0-4) , sets `kind = External`, then computes `presumed_origin` from `tx.input[0]` only [6](#0-5) .
4. `instruction_from_output` returns `None` (no InInstruction), so the plan becomes `Refund(output, third_party_script)` [7](#0-6) .
5. The threshold network signs a spend of the user's deposit to the third party's address; the depositor's funds are lost.
