### Title
Attacker-controlled `recipient`/`sender` indexes in PedPoP blame evaluation panic on `HashMap` indexing, crashing the host process - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept attacker-supplied `Participant` values for `sender` and `recipient` and pass `recipient` into `Decryption::decrypt_with_proof`, which indexes `self.enc_keys[&decryptor]` without a membership check. Any participant index that was never registered (e.g., the local party's own index `i`, which is deliberately excluded from `enc_keys`, or any out-of-range nonzero index) causes a panic — a remotely triggerable denial of service, directly analogous to the reported attacker-triggerable crash/hang class.

### Finding Description
`Decryption::register` only inserts keys for participants that registered an `EncryptionKeyMessage`: [1](#0-0) 

In `verify_r1`, registration is performed for every participant in `all_participant_indexes()` except the local `i` (the loop `remove(&l)` skips `i` because our own commitments message is not in `commitment_msgs`), so `enc_keys` never contains `self.params.i()`: [2](#0-1) 

`decrypt_with_proof` then unconditionally indexes the map with the caller-supplied `decryptor` whenever a `proof` is provided (and the accuser always provides `Some(EncryptionKeyProof)`, since it is deserialized from untrusted bytes via `EncryptionKeyProof::read`): [3](#0-2) 

`blame` forwards the accusation's `sender`/`recipient` straight into `blame_internal` → `decrypt_with_proof` with no bounds or membership validation: [4](#0-3) [5](#0-4) 

`AdditionalBlameMachine` is explicitly documented as usable by parties who were not DKG members for evaluating arbitrary blame statements, so these indexes are fully attacker-controlled public inputs: [6](#0-5) [7](#0-6) 

There is a second symmetric panic at `self.commitments[&sender]` for an out-of-set `sender`: [8](#0-7) 

### Impact Explanation
An unprivileged participant (or, for `AdditionalBlameMachine`, any external evaluator input) submits a blame accusation naming a `recipient` that has no registered encryption key — most trivially the local node's own index `i`, which is structurally guaranteed absent from `enc_keys` — together with any `EncryptionKeyProof` bytes. `self.enc_keys[&decryptor]` panics before any verification occurs, crashing the thread/process evaluating blame. Since blame evaluation gates DKG completion, a single crafted accusation aborts the key-generation ceremony and can repeatedly crash every honest node that processes it — a complete, repeatable availability loss matching the report's DOS class.

### Likelihood Explanation
Reachability requires only that the attacker can get a blame accusation containing chosen `(sender, recipient, msg, proof)` fields evaluated — exactly the inputs `blame` is designed to accept over authenticated-but-untrusted channels. No secret knowledge, valid proof, or collusion is needed; the panic precedes all cryptographic checks. The only mitigation is whether the caller pre-validates participant indexes, which the library does not require or document.

### Recommendation
Replace map indexing with checked lookups: in `decrypt_with_proof`, use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`; in `blame_internal`, use `self.commitments.get(&sender)` and return a defined blame result (or an error) when absent. `blame` should also validate that `sender`/`recipient` are within `1..=n` before evaluation.

### Proof of Concept
```rust
// Setup: t-of-n PedPoP DKG completes; local party index i produces a BlameMachine.
// enc_keys contains every participant EXCEPT i.

// Attacker crafts an accusation with recipient = i (the local evaluator's own index,
// guaranteed absent from enc_keys) and any syntactically valid EncryptionKeyProof.
let sender: Participant = attacker_index;
let recipient: Participant = keys.params().i(); // <-- not in enc_keys
let proof_bytes: Vec<u8> = valid_serialization_of_any_dleq_proof;
let proof = Some(EncryptionKeyProof::<C>::read(&mut proof_bytes.as_slice()).unwrap());
let msg: EncryptedMessage<C, SecretShare<C::F>> = /* any readable msg */;

// Panics at crypto/dkg/pedpop/src/encryption.rs:388:
//   self.enc_keys[&decryptor]  -> HashMap index out of bounds
let (_machine, _faulty) = blame_machine.blame(sender, recipient, msg, proof);
```

Variants: `recipient = n + 1` (never registered) panics identically; `sender = n + 1` panics later at `self.commitments[&sender]` in `blame_internal` when reached via a path where the proof/decryptor lookups succeed (e.g., `AdditionalBlameMachine` where all `1..=n` are registered but `n + 1` is not).

  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }
