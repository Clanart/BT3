## Analysis

The external report's core broken invariant is: **a value-accounting entry point accepts a caller-supplied amount of `0` because the guard only checks "balance ≥ amount" instead of "amount > 0"**, letting an attacker create low-cost, unbacked accounting records (`Operator` structs with `0` stake) that pollute a critical mapping.

The closest local analog is in the Tron deployment of the intent-settlement contract, where the escrow-crediting loop reachable from the `predispatch` code path in `placeOrder` omits the zero-amount guard that exists everywhere else in the codebase for the exact same operation.

### Title
Missing zero-amount check in `IntentGatewayV2.placeOrder` predispatch escrow path allows unbacked order commitments - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2`, the escrow-crediting loop for orders that use a `predispatch` call never validates `order.inputs[i].amount != 0` before sweeping the dispatcher's balance and crediting escrow. Every other equivalent code path in the codebase (the non-predispatch branch of the same function, and the canonical EVM `IntentGatewayV2.sol`) enforces this check explicitly.

### Finding Description
`placeOrder`'s non-predispatch branch enforces the invariant directly: [1](#0-0) 

But the predispatch branch, which runs the sweep-and-credit loop over `order.inputs`, has no equivalent check: [2](#0-1) 

`requiredAmount = order.inputs[i].amount` can be `0`, which makes `balance < requiredAmount` trivially false for any balance (including `0`), so the loop proceeds regardless of whether any value was ever escrowed for that token. The credited escrow is `_orders[commitment][token] += reducedInputs[i].amount`, which equals the caller-declared (and possibly zero) amount rather than anything derived from an actual balance delta.

The canonical, audited version of this same contract explicitly guards against this in its predispatch branch: [3](#0-2) 

This is the same missing-invariant pattern as the external report: a balance-sufficiency check (`balance < requiredAmount`) is used as a substitute for an explicit `amount != 0` check, and it silently degrades to a no-op when the caller-supplied amount is zero.

### Impact Explanation
An attacker can call `placeOrder` on the Tron `IntentGatewayV2` with a `predispatch` payload and one or more `order.inputs[i].amount == 0` entries. This produces a fully valid `OrderPlaced` event and order commitment that appears to represent an escrowed, fillable order to off-chain indexers/solver bots, while zero (or attacker-controlled, non-delta-verified) value actually backs that input slot. This directly weakens the "escrow moves exactly once and only to the rightful beneficiary and amount" invariant called out for intent settlement: a solver or bot that trusts the order's declared `TokenInfo.amount` fields (rather than independently re-deriving escrow from a verified balance delta) can be induced into servicing an order that is not actually fully collateralized, mirroring the front-run/zero-stake griefing vector in the source report (creating cheap, real-looking accounting entries that others must interact with).

### Likelihood Explanation
This is reachable by any unprivileged account calling the public `placeOrder` entrypoint with attacker-chosen `order.inputs` — no relayer, prover, admin, or governance actor is required. The only precondition is supplying a non-empty `predispatch.call`/`predispatch.assets`, which is a normal, documented usage path (e.g., unwrapping LP tokens) rather than a privileged or unusual one.

### Recommendation
Add the same guard used in the non-predispatch branch and in the canonical EVM contract to the predispatch escrow-crediting loop:
```solidity
if (order.inputs[i].amount == 0) revert InvalidInput();
```
Additionally, align the Tron contract's predispatch sweep with the canonical version's before/after balance snapshot pattern (`balancesBefore[i]`) so escrowed amounts are derived from an actual measured delta rather than trusting the caller-declared `order.inputs[i].amount`.

### Proof of Concept
1. Attacker builds an `Order` with `inputs = [{token: <anyERC20>, amount: 0}]` and a non-empty `predispatch.call` / `predispatch.assets` (e.g., a no-op call to a token contract or trivial dispatcher call).
2. Attacker calls `placeOrder(order, graffiti)`.
3. In the predispatch branch, `requiredAmount = 0`; the check `if (balance < requiredAmount) revert InvalidInput();` at line 423 never reverts regardless of `dispatcher`'s actual balance of that token.
4. `_orders[commitment][token] += reducedInputs[i].amount` credits `0`, and the transaction succeeds, emitting a fully valid `OrderPlaced` event and consuming a nonce — an order commitment now exists in storage and in off-chain indexes with a declared, uncollateralized input. [4](#0-3)
