### Title
Unconditional state-transfer overwrites an unrelated repository's uncommitted changes/commit-message state during worktree recovery - ([File: app/src/lib/stores/repository-state-cache.ts])

### Summary
`RepositoryStateCache.transferState()` moves the entire in-memory UI/git state (staged-file selection, commit message draft, `commitToAmend`, conflict state, etc.) from one repository identity to another with no check that the destination already has its own independent state. It is invoked from `_refreshRepository()`'s worktree-recovery path, which derives the "recovered" target `Repository` from data read out of the cloned repository's own `.git/worktrees/*` administrative files (via `resolveMainWorktreePath` / `listWorktreesFromGitDir`). This mirrors the go-ethereum flaw where `createObject` silently let a new object inherit a stale `balance` from a semantically distinct prior object, corrupting state without the caller validating that inheritance was safe.

### Finding Description
`transferState` blindly overwrites whatever is keyed at `target.hash`: [1](#0-0) 

There is no check for a pre-existing entry at `target.hash` (the equivalent of Geth's missing `prev != nil` differentiation) — if state already exists for the target identity, it is unconditionally clobbered by `this.repositoryState.set(target.hash, sourceState)`.

This is reached from `_refreshRepository()` when a tracked repository's working directory has vanished and a worktree is "recovered": [2](#0-1) 

The recovery path resolves the "main worktree" location using data read from the repository's own on-disk git metadata: [3](#0-2) [4](#0-3) 

`resolveMainWorktreePath` explicitly falls back to `listWorktreesFromGitDir`, which runs `git --git-dir <gitDir> worktree list --porcelain` and trusts whatever `worktree <path>` line git reports from the repository's `.git/worktrees/<name>/gitdir` admin files — content that lives inside a repository an attacker fully controls via a crafted clone/fetch. `Repository.hash` is derived only from `path`, `id`, `gitHubRepository?.hash`, `missing`, `alias`, and a couple of workflow flags, not from `gitDir`/`mainWorktreePath`: [5](#0-4) 

So if the path reported for the "main worktree" resolves to a path that is already tracked in Desktop as a distinct repository entry (its own id, its own accumulated `IRepositoryState` — an in-progress commit message, staged file selection, active conflict-resolution state, `commitToAmend`), `transferState` will silently stomp that unrelated repository's state with the stale state carried over from the missing/attacker-influenced worktree, with no user-visible warning.

### Impact Explanation
The corrupted value is the victim repository's `IRepositoryState` (specifically `changesState.workingDirectory` selection/inclusion flags, `changesState.commitMessage`, `commitToAmend`, and `changesState.conflictState`) for a repository the attacker does not directly control the git object database of, but whose selection is silently replaced. Because Desktop's commit/push flow reads what's included/excluded and the commit message straight out of this cached state, this can cause the user to commit or push different content than what they believe they selected — matching the "silent corruption of what the user commits or pushes" impact class. It requires no admin rights, no local access beyond normal Desktop usage, and is triggered purely by opening/refreshing a maliciously-crafted cloned repository whose worktree admin metadata happens to alias an existing tracked repository path.

### Likelihood Explanation
Exploitation requires: (1) the victim already has some other repository open in Desktop whose path can be inferred/guessed or is well-known (e.g. a monorepo checkout path convention), and (2) the attacker's repository going "missing" (a state Desktop itself can enter on stale/relocated repos) and being refreshed while its `.git/worktrees` metadata claims that colliding path as its main worktree. This is a narrow but plausible path rather than trivially triggerable on every clone, so likelihood is moderate — it depends on repository/worktree bookkeeping edge cases that are not exhaustively covered by this local-code review; the exact body of the caller that constructs the "recovered worktree" `Repository` object (referenced only by name, `recoverMissingWorktree`) could not be retrieved in full from the index, so the precise preconditions for reaching a hash collision with an existing tracked repository are not fully confirmed.

### Recommendation
In `transferState`, refuse to overwrite an existing non-initial state at `target.hash` (or merge only specific fields) and require the caller to prove `target` and `source` refer to the same underlying git repository (e.g. compare resolved `.git` common-dir) before transferring UI state such as commit message, staged selection, or conflict state.

### Proof of Concept
Conceptual reproduction (not fully verified end-to-end due to missing source for `recoverMissingWorktree`):
1. Victim has Repository `B` open in Desktop at path `/Users/victim/projects/shared`, with an in-progress commit (files staged, commit message typed, `commitToAmend` set).
2. Victim clones an attacker-supplied repository `A` at a different path; `A`'s `.git/worktrees/x/gitdir` metadata is crafted so `git worktree list --porcelain` (via `listWorktreesFromGitDir`, [4](#0-3) ) reports its "main" worktree path as `/Users/victim/projects/shared`.
3. `A`'s working directory is later reported missing (e.g. user renames/moves it), triggering `_refreshRepository` → `recoverMissingWorktree` → `RepositoryStateCache.transferState(A, recoveredWorktreeForSharedPath)` [6](#0-5) .
4. `transferState` overwrites `B`'s cached `IRepositoryState` with `A`'s stale state [7](#0-6) , silently changing what files/commit message are staged for `B` without victim's awareness.

  public transferState(source: Repository, target: Repository) {
    if (source.hash === target.hash) {
      return
    }

    const sourceState = this.repositoryState.get(source.hash)
    if (sourceState === undefined) {
      return
    }

    this.repositoryState.set(target.hash, sourceState)
    this.repositoryState.delete(source.hash)
  }

export async function resolveMainWorktreePath(
  repository: Repository
): Promise<string | null> {
  const { mainWorktreePath, gitDir, path } = repository

  if (mainWorktreePath === path) {
    return null
  }

  // A recorded path can outlive the location it names, so treat it as a hint
  // rather than the answer — otherwise a stale one would suppress the lookup
  // below, which may well still work.
  if (mainWorktreePath !== undefined && (await pathExists(mainWorktreePath))) {
    return mainWorktreePath
  }

  if (gitDir === undefined) {
    return null
  }

  const mainWorktree = (await listWorktreesFromGitDir(gitDir)).find(
    wt => wt.type === 'main'
  )

  return mainWorktree === undefined || mainWorktree.path === path
    ? null
    : mainWorktree.path
}
