Confirmed: `Bridge` inherits both `BridgeTransferERC20` and `BridgeTransferERC721` (and `BridgeTransferKLAY`), and they all share the single `registeredTokens` mapping from `BridgeTokens` [1](#0-0) . `registerToken` records only `token => counterpart token` with no token-type/kind field [2](#0-1) , and the `onlyRegisteredToken` modifier only checks that the mapping is non-zero, regardless of whether the token was intended to be an ERC20 or an ERC721 [3](#0-2) . Because of this shared, type-agnostic registry, any unprivileged address can call the public `requestERC721Transfer(_tokenAddress, ...)` on a token address that the bridge owner registered as an ERC20 counterpart, or call `requestERC20Transfer` against a registered ERC721 address [4](#0-3) [5](#0-4) .

### Title
Bridge's shared token registry lacks type enforcement, allowing ERC20/ERC721 confusion between `requestERC20Transfer`/`requestERC721Transfer` - (File: contracts/service_chain/bridge/BridgeTokens.sol)

### Summary
The `Bridge` contract combines `BridgeTransferKLAY`, `BridgeTransferERC20`, and `BridgeTransferERC721` on top of a single, common `registeredTokens` mapping inherited from `BridgeTokens`. That mapping never records whether a registered token is meant to be handled through the ERC20 or the ERC721 path. Any unprivileged caller can therefore invoke the public, permissionless `requestERC20Transfer` or `requestERC721Transfer` entry points against a token address that was registered for the *other* asset type, because both functions' only gating check (`onlyRegisteredToken`) is satisfied as long as the address exists in the shared mapping at all.

### Finding Description
`Bridge` is composed as:
```solidity
contract Bridge is BridgeCounterPart, BridgeTransferKLAY, BridgeTransferERC20, BridgeTransferERC721
``` [6](#0-5) 

`BridgeTokens` (inherited into all of `BridgeTransferERC20`/`BridgeTransferERC721`) stores registration in a single mapping keyed only by token address:
```solidity
mapping(address => address) public registeredTokens; // <token, counterpart token>
...
function registerToken(address _token, address _cToken) external onlyOwner onlyNotRegisteredToken(_token) {
    require(_cToken != address(0), "counterpart token address is zero");
    registeredTokens[_token] = _cToken;
    ...
}
``` [7](#0-6) 

There is no `TokenType` field stored per registered token — `TokenType` (`KLAY`/`ERC20`/`ERC721`) exists only as an event-log enum in `BridgeTransfer.sol`, used purely for `emit`, not for access control [8](#0-7) .

The public, unprivileged entry points then only gate on `onlyRegisteredToken(_tokenAddress)`:
```solidity
function requestERC20Transfer(address _tokenAddress, address _to, uint256 _value, uint256 _feeLimit, bytes memory _extraData) public {
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
``` [5](#0-4) 
```solidity
function requestERC721Transfer(address _tokenAddress, address _to, uint256 _tokenId, bytes memory _extraData) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
}
``` [4](#0-3) 

Since `registeredTokens[_token]` is true for a token regardless of what asset kind the operator intended, an unprivileged caller can invoke the wrong transfer path against any registered address. In mint/burn mode, `_requestERC20Transfer` unconditionally calls `ERC20Burnable(_tokenAddress).burn(_value)` on whatever address is supplied [9](#0-8) , and `_requestERC721Transfer` unconditionally calls `ERC721Burnable(_tokenAddress).burn(_tokenId)` [10](#0-9) . If a value happens to satisfy the wrong interface's calldata layout (e.g., an ERC721 contract that also happens to expose a `transferFrom(address,address,uint256)`-compatible selector, which is the case for both ERC20 and ERC721 since the ABI selector is identical: `transferFrom(address,address,uint256)`), the call can succeed against the counterpart bridge/handler logic that assumes a different semantic (amount vs tokenId), producing a `RequestValueTransfer`/`RequestValueTransferEncoded` event with a `TokenType` tag that does not match how the tokens were actually registered/handled and how the counterpart bridge operator will interpret and settle the request on the other chain (mint/burn or release), risking loss or a stuck/irreversible state on the counterpart side.

### Impact Explanation
Because `requestERC20Transfer` and `requestERC721Transfer` are both directly callable by any unprivileged externally-owned account against any address present in the shared `registeredTokens` map, this can produce mismatched `TokenType` events relative to the operator's actual configuration/intent for a given token pair, potentially causing the counterpart-chain operators to mint/burn or release the wrong asset semantics (value vs tokenId), leading to fund loss, stuck tokens in the bridge/escrow, or an un-recoverable settlement on the counterpart chain — directly analogous to the reported "un-liquidatable" outcome caused by asset-type confusion in an unauthenticated, permissionless collateral/token flow.

### Likelihood Explanation
The registration itself is `onlyOwner`-gated (medium barrier), but the actual mistaken-type call is fully reachable by any unprivileged transaction sender once at least one token of each kind has been registered on the bridge, requiring no special privilege, and can be triggered by a single transaction (`requestERC20Transfer`/`requestERC721Transfer`) that any account can submit. Exploitability further requires that the mis-typed calldata does not simply revert (both ERC20 and ERC721 use the identical function selector for `transferFrom(address,address,uint256)`, so the call passes at the Solidity function-dispatch level), making confusion realistic without any code-level workaround by the caller.

### Recommendation
Store an explicit `TokenType` (or separate registries) per registered token in `BridgeTokens`, and enforce it in `_requestERC20Transfer`/`_requestERC721Transfer` (and the corresponding `handleERC20Transfer`/`handleERC721Transfer`) so that a token registered as ERC20 cannot be routed through the ERC721 path and vice versa.

### Proof of Concept
1. Bridge owner calls `registerToken(nftAddress, cNftAddress)` intending `nftAddress` to be handled as ERC721 [2](#0-1) .
2. An unprivileged user calls `requestERC20Transfer(nftAddress, to, value, feeLimit, extraData)` on the `Bridge` contract; `onlyRegisteredToken(nftAddress)` passes because the address is present in `registeredTokens`, with no type check [11](#0-10) .
3. The call attempts `IERC20(nftAddress).safeTransferFrom(msg.sender, address(this), value.add(feeLimit))`, which resolves to the same 4-byte selector as `IERC721.transferFrom`, and emits a `RequestValueTransfer` event tagged `TokenType.ERC20` for an asset that is actually an NFT registered for ERC721 handling [5](#0-4) .
4. The counterpart-chain operator, trusting the `TokenType.ERC20` tag, processes `handleERC20Transfer` (mint/burn semantics for a "value"), producing a mismatch against the NFT's actual `tokenId` semantics — mirroring the reported bug class of type-confused collateral leading to stuck/un-recoverable assets.

    event TokenRegistered(address indexed token);
    event TokenDeregistered(address indexed token);
    event TokenLocked(address indexed token);

    modifier onlyRegisteredToken(address _token) {
        require(registeredTokens[_token] != address(0), "not allowed token");
        _;

    modifier onlyNotRegisteredToken(address _token) {
        require(registeredTokens[_token] == address(0), "allowed token");
        _;
    }

    modifier onlyLockedToken(address _token) {
        require(lockedTokens[_token], "unlocked token");
        _;
    }

    modifier onlyUnlockedToken(address _token) {
        require(!lockedTokens[_token], "locked token");
        _;
    }

    function getRegisteredTokenList() external view returns(address[] memory) {
        return registeredTokenList;
    }

    // registerToken can update the allowed token with the counterpart token.

        onlyOwner
