### Title
Panic on out-of-range participant index during DKG blame evaluation causes remotely triggerable crash - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept attacker-chosen `sender` and `recipient` `Participant` indexes plus untrusted `EncryptedMessage`/`EncryptionKeyProof` bytes. During evaluation, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `blame_internal` indexes `self.commitments[&sender]` directly. `HashMap`'s `Index` impl panics on a missing key, so any accusation naming a `Participant` outside the registered set `1..=n` aborts the process — a repeatable crash DoS analogous to the InnoDB hang/crash class (CVSS 4.9, availability-only impact).

### Finding Description
`Participant` is only constrained to be a non-zero `u16`; it is not bounded by `n`. The blame path never validates that `sender`/`recipient` were actual DKG participants before indexing:

- `crypto/dkg/pedpop/src/encryption.rs:388`: `&[self.enc_keys[&decryptor], *proof.key]` inside `decrypt_with_proof` panics if `decryptor` was never registered.
- `crypto/dkg/pedpop/src/lib.rs:599`: `&self.commitments[&sender]` inside `blame_internal` panics if `sender` is not a registered participant.
- `crypto/dkg/pedpop/src/lib.rs:623-632` (`BlameMachine::blame`) and `crypto/dkg/pedpop/src/lib.rs:674-682` (`AdditionalBlameMachine::blame`) expose this to any caller-supplied accusation: `sender`, `recipient`, the `EncryptedMessage<C, SecretShare>` bytes (parsed via `EncryptedMessage::read` at `encryption.rs:171-177`) and the `EncryptionKeyProof` are all attacker-controlled.

To reach the indexing panic, the attacker only needs the PoP Schnorr signature over `msg.key` to verify (`encryption.rs:374-379`), which is trivial since they choose `key` and sign with a scalar they know. Then either `self.enc_keys[&decryptor]` (when a `proof` is supplied and the DLEq check is reached — actually indexing occurs inside the `verify` argument construction at line 388 before/while verifying) or `self.commitments[&sender]` at `lib.rs:599` fires.

`AdditionalBlameMachine` is explicitly designed for third parties evaluating blame (`lib.rs:638-648`), so these accusations are exactly the untrusted, unauthenticated-by-construction inputs the API is meant to consume — yet `new`/`blame` never bound-check `sender`/`recipient` against `1..=n`.

### Impact Explanation
A single crafted blame accusation (or a blame re-evaluation request to an `AdditionalBlameMachine`) referencing a `Participant` index not in the DKG set (e.g., `n+1` or any `u16 > n`) panics the executing thread. In Serai's deployment these machines run inside processors/coordinator components that install fatal panic hooks (e.g., `std::process::exit(1)` on task panic), so the panic is a complete, repeatable crash — denying service to the key-generation/blame pipeline. This matches the referenced CVE's class: low-complexity network-reachable input causing a hang or repeatable crash with availability-only impact.

### Likelihood Explanation
Exploitation requires the attacker to be able to submit a blame accusation or an `EncryptedMessage`+`EncryptionKeyProof` to a party evaluating blame, and to pick the `sender`/`recipient` indexes. In the DKG blame flow these indexes come from the accusation itself, not from a trusted registry, so any participant (or anyone whose accusations are relayed, since `AdditionalBlameMachine` is explicitly for non-participants evaluating blame) can choose an out-of-range index. No secret knowledge is needed: the PoP is over a key the attacker generates, so building a passing `msg` is trivial. The only gate is whether the surrounding system routes blame evaluations — an inherent part of the protocol's fault-attribution design.

### Recommendation
Bound-check `sender` and `recipient` against the registered participant set before indexing. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get(...)` returning a `DecryptionError`/blame-result or an explicit error for unknown participants (e.g., treat an out-of-range `sender`/`recipient` as the accuser being faulty, or return an `InvalidParticipant` error). Similarly, `AdditionalBlameMachine::blame` should reject indexes outside `1..=n` before calling `blame_internal`.

Equivalently, `blame(sender = Participant(4), recipient = valid, ...)` panics at `crypto/dkg/pedpop/src/lib.rs:599` on `self.commitments[&sender]` once decryption succeeds.

Note: full confirmation that a specific in-scope caller routes unbounded attacker-chosen indexes into `blame` was not verified end-to-end (consumers live outside the in-scope crates), but `AdditionalBlameMachine` is documented for third-party blame evaluation over attacker-supplied accusation fields, making this panic reachable with public inputs in the intended usage.
