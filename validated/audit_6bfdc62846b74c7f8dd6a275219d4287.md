### Title
Silent remote-URL takeover via unpinned owner/name GitHub repository re-match — ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
When Desktop refreshes the GitHub metadata for an existing repository, it re-derives the associated GitHub repository purely by parsing the *current* remote URL for `owner`/`name` strings, fetches "the" repository from the API using only those strings, and — if certain heuristics hold — silently rewrites the local `origin` remote URL to whatever `clone_url` the API returns. There is no check that the API result actually corresponds to the same repository identity (e.g. a stable numeric id) the user originally added. This lets an attacker who can register/control an `owner/name` pair (e.g. because the original owner renamed or deleted the account/repo) get the user's Desktop to silently repoint their `origin` remote to the attacker's clone URL, corrupting where the user's future `fetch`/`push` operations go, without any prompt.

### Finding Description
`matchGitHubRepository()` computes an `IMatchedGitHubRepository` (`owner`, `name`, `account`) solely by string-parsing the *current* git remote URL against each known account's hostname — it does not use any previously stored, stable repository id: [1](#0-0) 

`repositoryWithRefreshedGitHubRepository()` uses that owner/name to call the GitHub API (`api.fetchRepository(owner, name)`), and if it succeeds, feeds the result straight into `updateRemoteUrl()`: [2](#0-1) 

`updateRemoteUrl()` then compares the *previously cached* `GitHubRepository.cloneURL` against the current git remote (to confirm the user hasn't manually customized it) and, if the scheme (http/https/ssh) matches and the URL differs from the freshly fetched `apiRepo.clone_url`, calls `gitStore.setRemoteURL()` to rewrite the remote — with no repository-id pinning and no user confirmation: [3](#0-2) 

`setRemoteURL()` executes `git remote set-url` directly against the working copy: [4](#0-3) 

The broken invariant: Desktop's association between a local repository and a "GitHub repository" is supposed to be a persistent, id-based identity (the DB schema even stores a `gitHubRepositoryID`) [5](#0-4) , but the *refresh* path that keeps that association current re-derives it from mutable owner/name strings rather than the previously stored numeric repository id, and then uses whatever is returned to overwrite git state on disk. If the owner/name namespace is later reused by a different repository (owner renames away/deletes the repo, and someone else creates a new repository at the same owner/name, or the user's account itself is later associated with a different, similarly-named repo on refresh), the app will silently accept the new API object as "the same" repository and push the corresponding `clone_url` into the user's `origin` remote.

This refresh path (`withRefreshedGitHubRepository` / `repositoryWithRefreshedGitHubRepository`) is invoked automatically and without user interaction, e.g. before every fetch: [6](#0-5)  and [7](#0-6) .

### Impact Explanation
If the remote is silently rewritten to an attacker-controlled clone URL, all subsequent `fetch`/`pull` operations pull attacker-controlled history into the user's local clone, and — more importantly — subsequent `push` operations from the user send their code/credentials-bearing HTTPS requests to the attacker's repository/host instead of the legitimate one. This is a silent corruption of what the user fetches/pushes to, matching the "silent corruption of what the user commits or pushes" impact category, and can also be leveraged for credential exfiltration if the rewritten URL points to an attacker-controlled HTTP(S) endpoint that captures Basic-auth/token headers during a push.

### Likelihood Explanation
Likelihood is constrained by real-world preconditions: the attacker must be able to make `owner/name` resolve, via the GitHub API, to a repository they control at exactly the point Desktop performs a background refresh (e.g., after the legitimate repo is renamed, transferred, or deleted and the name is squatted). This is a realistic but not trivial scenario (repo/organization renames and account deletions happen regularly on GitHub, and username/reponame squatting is a known technique), and the rewrite is unprompted and silent, which increases severity once the precondition is met. It also requires the local remote to not have been "manually" customized away from what's cached (the `remoteUrlUnchanged` check), which is the common case for most users who never touch remote settings.

### Recommendation
Pin the GitHub-repository association to the API's immutable repository `id` (already available on `IAPIRepository`/`IAPIFullRepository` and used elsewhere for GitHubRepository dedup) rather than re-deriving it from parsed owner/name strings on every refresh. `repositoryWithRefreshedGitHubRepository()` should re-fetch by the previously stored `GitHubRepository` id (e.g. via a `GET /repositories/:id` style call) when one exists, and only fall back to owner/name matching for repositories that have never been associated with a GitHub id. `updateRemoteUrl()` should additionally require that the fetched `apiRepo.id` matches the previously stored `GitHubRepository`'s id before silently rewriting `origin`; if the id differs, the app should prompt the user rather than silently calling `setRemoteURL()`.

### Proof of Concept
1. User adds/clones `https://github.com/alice/project` in Desktop; Desktop persists a `GitHubRepository` row with `cloneURL = https://github.com/alice/project.git` and the corresponding numeric GitHub id, associated with the local `Repository` via `gitHubRepositoryID` (`repositories-store.ts` `_upsertGitHubRepository`).
2. Alice later renames her account, transfers, or deletes `alice/project`. An attacker registers the `alice` account/organization slot (or otherwise creates a new repo at the same `owner/name`) and creates a new repository `alice/project` with a different id and a `clone_url` under the attacker's control (or a same-looking URL pointing to a malicious proxy/host if using a GHES-style endpoint).
3. On the victim's next background refresh (`_fetch` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository`), Desktop calls `matchGitHubRepository()` which returns `{owner: "alice", name: "project"}` purely from parsing the *current* remote string, then `api.fetchRepository("alice", "project")` returns the attacker's new repository object with the same owner/name but a different id and `clone_url`.
4. Because the user never manually edited the remote (`remoteUrlUnchanged` is true against the previously cached legit `cloneURL`) and the URL protocol (https) is unchanged, `updateRemoteUrl()` calls `gitStore.setRemoteURL(defaultRemoteName, attackerCloneUrl)`, executing `git remote set-url origin <attacker-url>` with no prompt (`app/src/lib/stores/updates/update-remote-url.ts:42-44`, `app/src/lib/git/remote.ts:56-64`).
5. The user's next `git push` now targets the attacker's clone URL, silently exfiltrating code/credentials or letting the attacker serve poisoned history on the next fetch.

Note: I was not able to fully trace whether `IAPIRepository`/`IAPIFullRepository` always exposes a stable `id` field usable for this exact re-pinning fix, nor whether GitHub's API guarantees id reuse cannot occur; that would need to be verified against `app/src/lib/api.ts` in a full session, as the index truncated that file's contents.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  public async setGitHubRepository(repo: Repository, ghRepo: GitHubRepository) {
    // If nothing has changed we can skip writing to the database and (more
    // importantly) avoid telling store consumers that the repo store has
    // changed and just return the repo that was given to us.
    if (isRepositoryWithGitHubRepository(repo)) {
      if (repo.gitHubRepository.hash === ghRepo.hash) {
        return repo
      }
    }

    await this.db.transaction('rw', this.db.repositories, () =>
      this.db.repositories.update(repo.id, { gitHubRepositoryID: ghRepo.dbID })
    )
    this.emitUpdatedRepositories()

    const updatedRepo = new Repository(
      repo.path,
      repo.id,
      ghRepo,
      repo.missing,
      repo.alias,
      repo.workflowPreferences,
      repo.isTutorialRepository,
      repo.gitDir,
      repo.mainWorktreePath
    )

    assertIsRepositoryWithGitHubRepository(updatedRepo)
    return updatedRepo
  }
