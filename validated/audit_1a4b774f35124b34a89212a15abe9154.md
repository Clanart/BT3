### Title
Arbitrary attacker-controlled calldata executed through the shared `CallDispatcher` can plant standing ERC-20 approvals that later drain tokens left behind by unrelated orders - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The C4 report's core broken invariant is: an under-privileged, non-owner-controlled path can grant arbitrary ERC-20 approvals and execute arbitrary calls against protocol-held tokens, with no verification that the intended swap actually happened correctly. Hyperbridge's Intent Gateway V2 reproduces this exact primitive through the permissionless `placeOrder` → `order.output.call` → `CallDispatcher.dispatch()` path: any user can encode arbitrary `Call{to, value, data}` entries that execute from the shared `CallDispatcher`'s context, including unrestricted `approve()` calls, and the post-execution sweep only recovers tokens that are explicitly listed as that order's own output assets.

### Finding Description
`CallDispatcher.dispatch()` blindly executes every `Call` in an ABI-encoded array against any target with any calldata and any forwarded value, the only guard being that the target has code: [1](#0-0) 

This is invoked from `IntentsBase._execute()`, which dispatches `order.output.call` — a field fully authored by the order creator at `placeOrder` time (a permissionless entrypoint) and hashed into the order commitment — and afterwards sweeps back only the balances of the tokens explicitly listed in that order's `output.assets`: [2](#0-1) 

The `Call` struct itself has no restriction on `to` or `data`: [3](#0-2) 

The documentation confirms `approve()` calls routed through the dispatcher are an intended, supported pattern (e.g. `approve` to a router before a swap), and that the dispatcher is a single shared contract reused across every order and every user/solver: [4](#0-3) 

Because `CallDispatcher` never revokes approvals it grants, and `_execute`'s sweep loop only iterates over `order.output.assets[i]` for the *current* order, any ERC-20 approval an attacker plants via their own order's `output.call` (e.g. `token.approve(attacker, type(uint256).max)`) persists indefinitely in storage on that token contract, keyed by `owner = CallDispatcher`. If, in any later, unrelated order/fill, that same token ends up sitting in the `CallDispatcher` and is *not* part of that later order's declared `output.assets` list (for example: an intermediate token from a predispatch swap, dust from a multi-hop route, or any token whose presence isn't anticipated by the sweep set), it is never swept back to the gateway and remains stranded in the dispatcher. The attacker can then call `token.transferFrom(dispatcher, attacker, amount)` directly and permissionlessly — completely outside of Hyperbridge's dispatch/sweep logic — to steal it.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant. An unprivileged attacker (any user who can call `placeOrder`) can pre-position unlimited-approval backdoors on arbitrary ERC-20 tokens against the shared `CallDispatcher`, then later sweep any of that token's balance the dispatcher accumulates outside the narrow per-order sweep set — resulting in theft of funds belonging to other users/solvers that transiently pass through the dispatcher.

### Likelihood Explanation
The attack requires only two ordinary, permissionless actions: (1) place an order whose `output.call` includes an `approve(attacker, max)` Call targeting a token of interest, and (2) wait for/trigger a scenario where that same token lands in the `CallDispatcher` without being listed in a subsequent order's `output.assets` sweep set (readily achievable via predispatch/postdispatch swap routes that produce intermediate or byproduct tokens, as shown in the gateway's own documented and tested swap patterns). No relayer, prover, admin, or governance compromise is needed.

### Recommendation
- Do not reuse a single long-lived `CallDispatcher` across unrelated orders; deploy an ephemeral, single-use dispatcher (or clone) per order/fill so no approval state can outlive the transaction.
- Alternatively, have `_execute` explicitly revoke (`approve(spender, 0)`) any approvals it granted at the end of the same transaction, and sweep the dispatcher's balance of *every* token touched by the call, not just the order's declared `output.assets`.
- Restrict the targets/selectors callable via `CallDispatcher.dispatch` to an allowlist of vetted DEX routers, rather than allowing arbitrary `to`/`data`.

### Proof of Concept
1. Attacker calls `placeOrder` with an order whose `output.call` (or `predispatch`) encodes: `Call({to: TOKEN_X, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})`. This is executed by `_execute` via `ICallDispatcher(dispatcher).dispatch(order.output.call)` (`IntentsBase.sol:442`). `TOKEN_X` is not necessarily part of this order's `output.assets`, so the standing approval is never revoked and the sweep loop (`IntentsBase.sol:444-473`) does not touch it.
2. At any later time, a legitimate, unrelated order routes `TOKEN_X` through the same `CallDispatcher` as an intermediate/byproduct of a predispatch or postdispatch swap (per the documented swap-then-escrow / fill-then-act patterns) without listing `TOKEN_X` in that order's `output.assets`.
3. Attacker calls `TOKEN_X.transferFrom(CallDispatcher, attacker, balance)` directly, using the standing approval from step 1, draining the token before any future sweep or order can recover it. [2](#0-1) [1](#0-0)

        if (order.output.call.length == 0) return;

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {

## Calldata

Orders support arbitrary calldata execution at two points in the lifecycle — before escrow (predispatch) and after fill (postdispatch). Both are executed through the `CallDispatcher` contract, which takes an ABI-encoded `Call[]` array:

```solidity
struct Call {
    address to;      // Target contract (must have code, reverts with NotContract otherwise)
    uint256 value;   // ETH to send with call
    bytes data;      // Calldata to execute
}
```

The `CallDispatcher` executes each call sequentially and reverts the entire batch if any call fails.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.
