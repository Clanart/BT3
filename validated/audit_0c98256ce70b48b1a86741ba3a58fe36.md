## Title
Missing timestamp freshness/replay-window validation in HMAC verification for webhooks and app proxy requests - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb], [File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
The reported bug class centers on missing freshness/staleness validation of externally-supplied signed data (Chainlink oracle rounds) — specifically the absence of any check ensuring a signed payload is not outdated before it is trusted and consumed. The direct analog in `shopify_app` is in `ShopifyApp::WebhookVerification` and `ShopifyApp::AppProxyVerification`: both validate only that an HMAC/signature is cryptographically valid, but neither module checks the `timestamp` parameter (present in app-proxy signed query strings, and implicit in webhook delivery) against a freshness window, so a validly-signed request/payload can be replayed indefinitely.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` computes `hmac_valid?(request.raw_post)` and accepts the request purely based on HMAC match, with no expiry or freshness check on the payload: [1](#0-0) 

`ShopifyApp::PayloadVerification#hmac_valid?` only performs `ActiveSupport::SecurityUtils.secure_compare` against the computed digest, with no timestamp/nonce/replay component considered: [2](#0-1) 

Similarly, `ShopifyApp::AppProxyVerification#query_string_valid?` validates the `signature` parameter against a computed HMAC over the sorted query params (which includes `timestamp` as an opaque signed field), but it never asserts that this `timestamp` is recent — it treats the signature as valid regardless of how old the request is: [3](#0-2) 

This mirrors the reported issue's core defect class: consuming externally-supplied, nominally-signed/validated data without checking that it is fresh (`require(latestTimestamp > baseTimestamp)` in the oracle case). Here, once a webhook payload or app-proxy query string (with its valid `signature`) is observed by any party with network visibility (e.g., via browser history, shared logs, proxy caches, or a passive network observer for non-TLS-terminated hops), it remains a validly-accepted request forever, because there is no server-side check that the signed `timestamp` falls within an acceptable window.

### Impact Explanation
An attacker who obtains a previously valid, signed app-proxy URL or webhook payload can replay it to the app's endpoints at any point in the future and have it accepted as authentic, since the only validation performed is signature/HMAC correctness. This can result in the app service performing actions (e.g., triggering job processing pinned to `shop_domain` and webhook body) based on stale/replayed data. For app proxy specifically, since `shop` is one of the signed parameters passed straight into application logic without a freshness bound, a captured signed proxy request could be resubmitted at will.

### Likelihood Explanation
The likelihood depends on an attacker's ability to intercept or otherwise obtain a previously valid signed webhook/app-proxy request. This is not always trivial to achieve (it is not a pure unauthenticated bypass against a random target), but it is a well-known class of weakness in HMAC-based endpoint verification where the signed timestamp is not actually enforced, and both the webhook and app-proxy signing schemes in this codebase include a `timestamp`-bearing parameter that is signed but never checked for freshness.

### Recommendation
Enforce a maximum age window on the signed `timestamp` for both `ShopifyApp::AppProxyVerification#query_string_valid?` (reject if the `timestamp` query param is not present or is older than a small tolerance, e.g., a few minutes) and consider adding an analogous replay-protection mechanism (e.g., checking `X-Shopify-Webhook-Id` or delivery timestamp header against a freshness window, or maintaining a short-lived seen-ID cache) in `ShopifyApp::WebhookVerification`/`ShopifyApp::PayloadVerification`.

### Proof of Concept
1. Capture a valid, previously-issued app proxy request URL, e.g. `shop=some-store.myshopify.com&path_prefix=/apps/my-app&timestamp=1466106083&signature=<valid>` as validated in the existing test suite: [4](#0-3) 
2. Replay the exact same query string against the app-proxy endpoint at any later time — `query_string_valid?` performs no check on how old `timestamp` is, only on whether the `signature` matches the sorted params, so the replayed request is accepted identically to the original as long as the underlying HMAC secret hasn't rotated: [5](#0-4)

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
