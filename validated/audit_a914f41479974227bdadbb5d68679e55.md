### Title
Shared `BalanceHandler` instance causes `prevEventsLen` overwrite on recursive precompile calls, desyncing EVM `StateDB` balances from bank keeper - ([File: precompiles/common/balance_handler.go])

### Summary
`BalanceHandler` uses a single mutable field `prevEventsLen` to remember the event-log cursor between `BeforeBalanceChange` and `AfterBalanceChange` [1](#0-0) . This is the same "two different values under one name" bug class as the `PoolFactory.deployPool()` `invariantCheck` shadowing issue: a single stateful variable is expected to hold one consistent value across a call, but nested/recursive invocation paths reuse the *same* instance and clobber that value mid-flight, so a later read observes the wrong version of the state.

### Finding Description
`BeforeBalanceChange` snapshots the current event-manager length into `bh.prevEventsLen`, and `AfterBalanceChange` later replays events *after* that recorded index to update the EVM `StateDB` via `AddBalance`/`SubBalance` [2](#0-1) . If a precompile call recurses (e.g., a contract calls a precompile, whose EVM call triggers another call back into the same or another precompile that shares the same `BalanceHandler` instance), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` with a later index. When the outer call's `AfterBalanceChange` subsequently executes, it now slices events from the wrong (larger) index, silently dropping bank events that should have been applied to the `StateDB`, or double counting events, depending on call ordering.

This exact bug is already reproduced in-repo by a dedicated regression test that documents it verbatim: "tests the balance handler bug where recursive precompile calls share the same `BalanceHandler` instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM `stateDB`" [3](#0-2) . The test drives this through a debug precompile invoked recursively via a caller contract and asserts on the resulting number of `debug_precompile` events, confirming the recursive-call/shared-instance scenario is reachable through ordinary contract execution [4](#0-3) .

The `AfterBalanceChange` logic is precisely the code path responsible for keeping the EVM `StateDB` balance in sync with bank-keeper-driven balance changes (`CoinSpent`, `CoinReceived`, and precisebank fractional-balance events) whenever a precompile (ERC20, staking, distribution, gov, slashing, ICS20, etc.) performs a bank operation [5](#0-4) . Any miscalculation of the event window directly corrupts the derived `StateDB` balance for the addresses involved, while the actual bank-keeper balance (source of truth) remains correct — creating a discrepancy between what the EVM believes an account's spendable balance is and what the bank module actually holds.

### Impact Explanation
Because `StateDB.AddBalance`/`SubBalance` calls are what the EVM uses for all in-transaction balance accounting (gas refunds, subsequent transfers, `balanceOf`-precompile reads within the same call context), an incorrectly windowed event replay can:
- Skip applying a legitimate `CoinReceived`/`CoinSpent` event to `StateDB`, causing an account's EVM-visible balance to diverge from its real bank balance (permanent desync until corrected by an unrelated full balance write), effectively freezing or hiding user funds from EVM-level accounting, or
- Reapply/duplicate an event window against `StateDB`, causing an account's EVM balance to be credited or debited a value it should not have received — an accounting corruption of spendable value across native/EVM balance representations, which is the exact class of impact called out in scope (unauthorized minting/duplication/accounting corruption across native and EVM balances).

Given `BalanceHandler` sits underneath multiple precompiles (ERC20, staking, distribution, gov, slashing, ICS20), this is reachable from many contract flows that make precompile calls with reentrant/nested structure, not just a synthetic debug precompile.

### Likelihood Explanation
Triggering requires only an ordinary, unprivileged smart contract that performs a nested/recursive precompile call sequence (e.g., a contract calling a precompile whose execution path re-enters into another precompile call before the outer call's post-processing runs). The repository already contains a working end-to-end regression test demonstrating this exact recursive trigger via a deployed caller contract and a precompile, confirming it is reachable through standard EVM transaction execution without any privileged access [6](#0-5) .

### Recommendation
- Do not share a single `BalanceHandler` (and its `prevEventsLen` field) across nested/recursive precompile invocations. Each precompile call context should either create its own `BalanceHandler` instance, or `BeforeBalanceChange`/`AfterBalanceChange` should be implemented with a stack/counter (push/pop) of previous event-length markers instead of a single scalar field, so nested calls cannot clobber the outer call's marker.
- Add an invariant check in `AfterBalanceChange` that asserts the recorded `prevEventsLen` is monotonically consistent with the call nesting depth, and fail closed (revert) rather than silently mis-slicing events if an inconsistency is detected.
- Extend the existing regression test in `evmd/tests/integration/balance_handler/balance_handler_test.go` to assert on actual `StateDB` balances (not just event counts) before/after recursive calls, to directly catch the balance desync rather than only counting `debug_precompile` events.

### Proof of Concept
The existing test `TestRecursivePrecompileCallsWithDebugPrecompile` is a working PoC: it registers a debug precompile sharing a `BalanceHandler`, deploys a caller contract that invokes `callback(0)` which recursively calls the precompile, and shows the event/state bookkeeping is affected by the shared `prevEventsLen` field [4](#0-3) . To turn this into a funds-impact PoC, replace the debug precompile calls with real bank-moving precompile calls (e.g., ERC20 `transfer` precompile) nested inside each other and assert `StateDB` balance of the affected account against the bank keeper's balance after execution — the two are expected to diverge due to the `prevEventsLen` overwrite described above.

```go
// BalanceHandler is a struct that handles balance changes in the Cosmos SDK context.
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int
}

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```

```go
// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")
```
