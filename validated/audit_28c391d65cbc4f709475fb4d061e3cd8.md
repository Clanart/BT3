### Title
Native ERC20 pointer contract reports attacker-controlled `decimals()` while `balanceOf`/`transfer` move raw un-scaled integer amounts — (File: `contracts/src/NativeSeiTokensERC20.sol`)

### Summary
The `NativeSeiTokensERC20` contract, generated for every native/tokenfactory denom's ERC20 pointer, exposes `decimals()` as an arbitrary value taken from bank denom metadata, while `balanceOf`, `totalSupply`, and `transfer` operate on raw integer coin amounts from the Bank precompile with no scaling applied. Any tokenfactory denom creator (an unprivileged account, since denom creation and denom-admin rights are permissionless) can set `DenomUnit.Exponent` to any value via `MsgSetDenomMetadata`, then register (or have anyone register) an ERC20 native pointer for that denom. The resulting pointer contract will present an ERC20 whose `decimals()` value is completely decoupled from the actual granularity of the values returned by `balanceOf`/moved by `transfer`, exactly the same class of bug as the referenced ClearingHouse report: a hard-coded/assumed precision that silently diverges from the actual value scale returned by a pluggable, less-trusted component.

### Finding Description
Bank-precompile code explicitly documents that native Cosmos denoms are integer-based and always reports `decimals() == 0` for direct bank/EVM balance queries: [1](#0-0) 

However, when a native ERC20 pointer contract is created, `AddNative` derives `decimals` from the denom's bank `Metadata.DenomUnits[].Exponent` instead of using the fixed value 0, and this value is caller/creator supplied via the metadata: [2](#0-1) 

That `decimals` value is passed straight into the constructor of the generated ERC20 pointer: [3](#0-2) 

The pointer contract itself simply echoes back this metadata-derived value from `decimals()`: [4](#0-3) 

Meanwhile `balanceOf`, `totalSupply` and `_update` (used by `transfer`/`transferFrom`) forward the exact raw integer `amount`/`value` to the Bank precompile with no rescaling by `10**decimals`: [5](#0-4) 

The `DenomUnit.Exponent` used to compute `decimals` is fully attacker-controlled: tokenfactory denom creation is permissionless (`CreateDenom` sets the creator as denom admin automatically): [6](#0-5) 

And the denom admin (the creator) can subsequently call `MsgSetDenomMetadata` to set an arbitrary `Exponent`, with the only check being that the sender is the denom's own admin: [7](#0-6) 

So an ordinary user can: (1) create a tokenfactory denom (`factory/<creator>/<subdenom>`), (2) mint/burn/transfer it freely as its own admin, (3) call `MsgSetDenomMetadata` setting `DenomUnits[].Exponent = 18` (or any value), and (4) register/upsert the ERC20 native pointer for that denom via the pointer precompile's `AddNative`. The resulting pointer contract will report `decimals() == 18` while every `balanceOf`/`transfer` amount is still a raw integer unit of the underlying coin (i.e., effectively decimals 0 semantics, as the bank precompile's own hard-coded `decimals()` comment states). This is precisely the bug pattern in the referenced report: a component (the AMM/VAMM in the original report, the tokenfactory-metadata-driven native pointer here) is allowed to supply/imply a precision that a fixed downstream assumption (`PRECISION = 1e6` in ClearingHouse; "native tokens are integer-based" in Sei's bank precompile / pointer decimals plumbing) does not reconcile against the actual value scale used elsewhere in the same interface.

### Impact Explanation
Any EVM-native protocol (DEX/AMM pools, lending markets, aggregators, price oracles) that treats this pointer contract as a standard ERC20 and uses `decimals()` to interpret `balanceOf`/transferred amounts will be off by a factor of `10^decimals`. For example, pairing this pointer token in a constant-product AMM against a real 18-decimal token: the attacker mints/holds a tiny raw integer balance (e.g. `1000`), which the pool interprets as `1000` "whole units" scaled by the claimed 18 decimals (i.e. `1000 * 10^-18` real tokens) — or the reverse, depending on how the integrating contract normalizes decimals — either direction lets the attacker manipulate pricing/liquidity ratios and drain the paired real asset from any pool or lending market that onboards the pointer token, since the token's own contract asserts a false precision. This is a direct, permissionless fund-loss vector rooted in the pointer/precompile layer, not merely an integration mistake by a downstream dApp, because the sei-chain code itself derives an unchecked `decimals()` value from user-controlled tokenfactory metadata and mismatches it against the un-scaled raw balance semantics baked into the same pointer contract and the bank precompile.

### Likelihood Explanation
High. No privileged access is required: tokenfactory denom creation, denom-admin metadata updates, and native ERC20 pointer registration are all permissionless operations reachable from a single EVM/Cosmos transaction sequence by any account. The only prerequisite for actual loss is that some third-party DeFi contract integrates the pointer token trusting its `decimals()`, which is a normal and expected usage pattern for ERC20 pointer tokens (the whole purpose of the pointer mechanism is EVM-side interoperability).

### Recommendation
Do not derive the ERC20 pointer's `decimals()` from user/creator-supplied `DenomUnit.Exponent` for native/tokenfactory denoms. Either:
- Hard-code `decimals()` to `0` for all native pointer contracts (consistent with the bank precompile's own documented invariant that "all native tokens are integer-based"), or
- If a non-zero decimals value is desired for display purposes, actually rescale `balanceOf`, `totalSupply`, and the amounts moved by `transfer`/`transferFrom` by `10**decimals` so the ERC20 interface's numeric semantics are internally consistent, exactly as the original report recommends removing decimals-related hard-coding and ensuring scaling is applied consistently everywhere a precision assumption is made.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/<attacker>/evil`, becoming its admin (`x/tokenfactory/keeper/createdenom.go`).
2. Attacker calls `MsgSetDenomMetadata` on `factory/<attacker>/evil` with `DenomUnits = [{Denom: "evil", Exponent: 18}]` (`x/tokenfactory/keeper/msg_server.go:188-217`, only requires sender == admin, which the attacker is).
3. Attacker mints a tiny amount, e.g. `1000` raw units, via `MsgMint`.
4. Attacker (or anyone) calls the pointer precompile's `addNativePointer("factory/<attacker>/evil")`, which reads the metadata, picks `Exponent=18` as `decimals`, and deploys `NativeSeiTokensERC20` with `decimals_=18` (`precompiles/pointer/pointer.go:99-132`, `x/evm/keeper/pointer_upgrade.go:49-57`).
5. The deployed pointer's `decimals()` returns `18`, but `balanceOf(attacker)` returns the raw `1000` (not `1000 * 10^18` nor any different scaled representation) because `balanceOf`/`_update` pass amounts straight through to the Bank precompile (`contracts/src/NativeSeiTokensERC20.sol:33-49`).
6. Attacker supplies this pointer token to any AMM pool/lending market alongside a genuine 18-decimal ERC20, exploiting the mismatch between the claimed 18-decimal precision and the actual integer-unit balance semantics to extract value from the pool.

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {IBank} from "./precompiles/IBank.sol";

contract NativeSeiTokensERC20 is ERC20 {

    address constant BANK_PRECOMPILE_ADDRESS = 0x0000000000000000000000000000000000001001;

    string public denom;
    string public nname;
    string public ssymbol;
    uint8 public ddecimals;
    IBank public BankPrecompile;

    constructor(string memory denom_, string memory name_, string memory symbol_, uint8 decimals_) ERC20("", "") {
        BankPrecompile = IBank(BANK_PRECOMPILE_ADDRESS);
        denom = denom_;
        nname = name_;
        ssymbol = symbol_;
        ddecimals = decimals_;
    }

    function name() public view override returns (string memory) {
        return nname;
    }

    function symbol() public view override returns (string memory) {
        return ssymbol;
    }

    function balanceOf(address account) public view override returns (uint256) {
        return BankPrecompile.balance(account, denom);
    }

    function decimals() public view override returns (uint8) {
        return ddecimals;
    }

    function totalSupply() public view override returns (uint256) {
        return BankPrecompile.supply(denom);
    }

    function _update(address from, address to, uint256 value) internal override {
        bool success = BankPrecompile.send(from, to, denom, value);
        require(success, "NativeSeiTokensERC20: transfer failed");
        emit Transfer(from, to, value);
    }
}

func (k Keeper) CreateDenom(ctx sdk.Context, creatorAddr string, subdenom string) (newTokenDenom string, err error) {

// Runs CreateDenom logic after the charge and all denom validation has been handled.
// Made into a second function for genesis initialization.
func (k Keeper) createDenomAfterValidation(ctx sdk.Context, creatorAddr string, denom string) (err error) {
	denomMetaData := banktypes.Metadata{
		DenomUnits: []*banktypes.DenomUnit{{
			Denom:    denom,
			Exponent: 0,
		}},
		Base: denom,
		// The following is necessary for x/bank denom validation
		Display: denom,
		Name:    denom,
		Symbol:  denom,
	}

	k.bankKeeper.SetDenomMetaData(ctx, denomMetaData)

	authorityMetadata := types.DenomAuthorityMetadata{
		Admin: creatorAddr,
	}
	err = k.setAuthorityMetadata(ctx, denom, authorityMetadata)
	if err != nil {
		return err
	}

	k.addDenomFromCreator(ctx, creatorAddr, denom)
	return nil
}

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
