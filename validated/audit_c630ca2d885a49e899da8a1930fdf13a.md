## Analysis

`cap_diff_for_prompt` truncates from the **end** of each file's diff content once it exceeds `DIFF_PER_FILE_BYTES` (80,000 bytes) or once the running total exceeds `DIFF_TOTAL_BYTES` (400,000 bytes), keeping `content[:cap]` and appending a truncation marker. [1](#0-0) 

This means an attacker who authors a commit/PR diff controls exactly where in that byte stream the dangerous change lands. By padding a file's diff with a large amount of low-risk content (e.g., generated-looking code, long comments, whitespace, or bulk boilerplate) **before** the malicious change, or by adding enough other files/content ahead of the malicious file so the running `total` in the total-byte accumulator is already exhausted, the attacker can push the truly dangerous lines past the truncation cutoff — silently dropping them from what the review LLM ever sees. `cap_diff_for_prompt` has no line/hunk-aware logic and no prioritization of `+`-added or security-relevant lines within a file's content; it operates purely on raw byte offsets.

However, this specific function (`cap_diff_for_prompt` in `review_api.py`) is one path used by `build_investigate_prompt`, but the primary/actual CC-hook pipeline (`security_reminder_hook.py`) applies an upstream, security-aware prioritization step, `_prioritize_diff_files` in `gitutil.py`, which ranks files by `(risk_tokens_in_path, not_low_priority, added_lines)` before capping the *file count*, specifically to keep dangerous files (auth/exec/subprocess/deserialize paths) prioritized when a diff has too many files. [2](#0-1) 
That mitigates the file-selection risk, but it does **not** mitigate `cap_diff_for_prompt`'s per-file byte truncation — that step still blindly truncates from the end regardless of where the security-relevant `+` lines are located inside an individual file's diff content, and no evidence in the code shows hunk-level content is prioritized before the byte cap is applied. I could not find (within the accessible index) any call site that reorders lines within a single file's diff content by risk before invoking `cap_diff_for_prompt`, nor any test asserting that dangerous lines survive truncation.

Given the tool budget is exhausted, I could not fully trace whether `security_reminder_hook.py`'s actual production path calls `cap_diff_for_prompt` directly (it wasn't found via grep in that file, suggesting the two-stage `review_api.py` module may be used by external/agentic callers rather than the main CC hook itself) — this is an area of residual uncertainty that would need further reading of `security_reminder_hook.py` in full to confirm the exact call graph.

### Title
Per-file byte truncation in `cap_diff_for_prompt` can silently drop attacker-placed high-risk diff lines from security review - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`cap_diff_for_prompt` truncates each file's diff content and the total diff by raw byte offset from the start, keeping only `content[:cap]`, with no awareness of which lines are security-relevant. An attacker who authors the diff being reviewed (e.g., in a PR or commit fed into the agentic reviewer) can pad content ahead of a malicious change so the change is truncated out of the prompt sent to the review LLM.

### Finding Description
`cap_diff_for_prompt` (lines 31-64) enforces `DIFF_PER_FILE_BYTES` and `DIFF_TOTAL_BYTES` caps by slicing `content[:DIFF_PER_FILE_BYTES]` / `content[:room]`, i.e., truncating whatever comes after the cap boundary, regardless of whether that discarded region contains newly added (`+`) lines, sinks, or the attacker's actual payload. `build_investigate_prompt` (lines 156-176) calls this function directly on `diff_files` without first re-ordering hunks/lines by risk, then feeds the resulting `diff_text` to the investigate-stage LLM as the sole diff evidence. An attacker who controls the diff content (e.g., a large auto-generated-looking prologue, verbose boilerplate, or repeated near-duplicate content within the same file) can position the actually dangerous edit past the 80,000-byte per-file boundary or past the 400,000-byte total boundary, so it is replaced by a generic `"... [truncated by security-guidance...]"` marker and never reaches the review model's context.

### Impact Explanation
If the malicious lines are truncated out, the two-stage investigate → self-refute review pipeline never analyzes them, so a genuinely dangerous change (e.g., a backdoor, disabled auth check, injected command) can pass through the security-guidance review silently. This matches "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries," since the review's entire evidentiary basis for a truncated file is the byte-limited prefix.

### Likelihood Explanation
Feasibility depends on the attacker being able to control diff size and ordering of hunks within a file (true for anyone authoring a commit/PR that will be reviewed) and on there being no separate mitigating step between diff extraction and `cap_diff_for_prompt` that reorders content by risk. `gitutil.py`'s `_prioritize_diff_files` mitigates file-level selection under `MAX_DIFF_FILES`, but does not address in-file byte truncation, so a single large file (or several) with an early-truncated dangerous line is a plausible and repeatable path. I was not able to confirm, within the available tool budget, whether the primary CC hook path (`security_reminder_hook.py`) invokes `cap_diff_for_prompt` at all versus only external/agentic-harness callers of `review_api.py` — this affects real-world reachability and should be verified before treating this as confirmed in the main hook flow.

### Recommendation
Make truncation risk-aware: before truncating, prioritize/keep hunks or lines matching `_SECURITY_RISK_PATH_TOKENS`-style heuristics (or simply prioritize `+`-added lines and lines containing sink-like keywords) instead of naive prefix truncation; alternatively, truncate context (unchanged) lines first and preserve all `+`/`-` diff lines up to the cap, only dropping less-security-relevant content last. At minimum, sample/rotate truncation across the file (e.g., keep both head and tail, or keep a proportional sample of hunks) rather than always dropping the tail.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py::cap_diff_for_prompt`:
1. Construct a synthetic diff for one file where the first ~79,900 bytes are innocuous filler lines (e.g., repeated comment lines) and the final lines (after byte 80,000) contain a clearly dangerous `+` line, e.g. `+ os.system(user_input)` or `+ verify_signature = lambda *a: True`.
2. Call `cap_diff_for_prompt([("app/auth.py", crafted_diff)])`.
3. Assert that the dangerous line (`os.system(user_input)` / the disabled `verify_signature`) is **not** present in the returned capped content, and that `dropped > 0`.
4. Repeat with multiple files summing past `DIFF_TOTAL_BYTES` where the dangerous file is ordered last, and assert its content is entirely replaced with `"[omitted by security-guidance: total diff byte cap reached]"`.
5. Assertions should fail today (confirming the vulnerability) because the current implementation performs prefix-only truncation with no risk-based line retention.

def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
