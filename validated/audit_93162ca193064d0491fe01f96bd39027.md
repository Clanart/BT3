### Title
Unbounded attacker-controlled length prefix causes endless-data DoS in `SchnorrAggregate::read` - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` reads a `u32` count of aggregated nonces directly from an untrusted byte stream and then loops that many times pushing deserialized group elements into an unbounded `Vec`. There is no upper bound on the count and no check that the declared count matches the caller's expected number of signatures, so a malicious byte stream can force up to ~4 billion point deserializations and unbounded memory growth — the same "endless data" denial-of-service class as CVE-2023-46737.

### Finding Description
The deserialization at `crypto/schnorr/src/aggregate.rs:77-88` is:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;

#[allow(non_snake_case)]
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}

Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
```

The attacker fully controls `len` (4 bytes, up to `u32::MAX`). For each iteration, `C::read_G` performs a full point decompression/canonicity check and the result is appended to `Rs` with no capacity limit. Unlike `MultiDLEqProof::read` (`crypto/dleq/src/lib.rs:308-315`), which takes a caller-specified `discrete_logs` bound, and unlike the coordinator's transaction parser which enforces `TRANSACTION_SIZE_LIMIT` (`coordinator/src/tributary/transaction.rs:286`), `SchnorrAggregate::read` has no semantic bound derived from expected signer counts.

Every iteration requires only `C::G::Repr` bytes of input (e.g., 32 bytes for Ristretto/ed25519). An attacker supplying ~128 GiB-equivalent of trailing data is not needed to cause harm: even a modest payload declares `u32::MAX`, and the loop will perform decompression work for every byte provided, and if backed by a streaming `io::Read` (network source) the loop continues as long as the attacker keeps feeding bytes — a true endless-data loop. Additionally, `Rs` grows linearly, so a ~137 GB stream or repeated calls can exhaust memory (OOM) before `read` ever returns.

### Impact Explanation
An unprivileged party who can get a verifier/aggregator node to deserialize an attacker-supplied `SchnorrAggregate` (the aggregate signature message circulated among signers/coordinators) can stall that node in a long loop of point deserializations and grow its heap without bound. This denies service to all other signing/verification work on that node, matching the impact of the cosign advisory: verification throughput is monopolized by junk data, blocking legitimate signatures. Severity: Medium (availability only, no secret leakage).

### Likelihood Explanation
The path is reachable with purely public input: the attacker only needs to hand a crafted byte buffer/stream to any component calling `SchnorrAggregate::read`. The cost is asymmetric — 4 bytes control up to ~4 billion iterations, each costing a curve decompression plus a heap push. No cryptographic validity, key knowledge, or privileged position is required; malformed `Rs` never need to pass `verify`, since the cost is incurred inside `read` before verification.

### Recommendation
Cap the deserialized count before looping, e.g.:

```rust
let len = u32::from_le_bytes(len);
if len > MAX_AGGREGATED_SIGNATURES { // e.g. MAX_KEY_SHARES_PER_SET or expected signer count
  Err(io::Error::other("excessive signatures in aggregate"))?;
}
```

Prefer passing the expected signature count into `read` (as `MultiDLEqProof::read` does with `discrete_logs`) so the bound is semantic rather than a global constant, and reject early without allocating.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ed25519;
use schnorr::SchnorrAggregate;

// 4-byte length prefix = u32::MAX, followed by a large (or endlessly-produced)
// stream of 32-byte point encodings.
let mut data = Vec::new();
data.extend(u32::MAX.to_le_bytes());
// Attacker keeps appending bytes; each 32-byte chunk costs a full
// Ed25519 decompression + Vec push inside `read`.
data.extend(std::iter::repeat(1u8).take(32 * 1_000_000)); // example slice

let mut cursor = Cursor::new(data);
// Loops up to u32::MAX times; memory grows per valid point; with a streaming
// reader it never terminates while the attacker supplies data.
let _ = SchnorrAggregate::<Ed25519>::read(&mut cursor);
```

The root cause is `crypto/schnorr/src/aggregate.rs:78-85`: the loop bound is entirely attacker-controlled with no maximum, directly mirroring `FetchAttestations` looping over attacker-supplied attestations in the cosign advisory.
