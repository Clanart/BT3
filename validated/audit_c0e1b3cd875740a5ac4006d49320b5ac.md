## Title
Per-transaction Coinbase Surplus Sweep Failure Silently Ignored in EVM `EndBlock`, Leading to Fund Freezing and Divergent Surplus Accounting - (File: `x/evm/keeper/abci.go`)

## Summary
This is a structural analog of the reported bug class: a loop that accumulates a running total across multiple sub-operations without accounting for the possibility that an individual sub-operation fails. In the Rio report, `queueTokenWithdrawalFromOperatorsForUserSettlement` accumulates `sharesQueued` while assuming every per-delegator withdrawal call succeeds. The same pattern exists in Sei's EVM `EndBlock`, where per-transaction coinbase balances are supposed to be swept to the fee collector, but a failed sweep is merely logged and the loop continues, while a separate `surplus` accumulator keeps growing regardless of the sweep outcome.

## Finding Description
Every EVM transaction on Sei collects its fees/refunds into a deterministic, per-tx-index ephemeral address (`state.GetCoinbaseAddress(idx)`), and at `EndBlock` these balances are meant to be swept to the real fee collector [1](#0-0) .

The sweep loop in `Keeper.EndBlock` iterates over `evmTxDeferredInfoList`, reads the actual `usei`/`wei` balance sitting in each per-tx coinbase address, and attempts `SendCoinsAndWei` to move it to the block's `coinbase` (normally the fee collector module account). If that call returns an error, the code only logs the error and continues the loop — the balance is left untouched at the ephemeral address, but the loop unconditionally still adds `deferredInfo.Surplus` (a separate, already-computed value from `stateDB.Finalize()`) into the block-level `surplus` accumulator: [2](#0-1) 

That accumulated `surplus` is then minted into the EVM module account via `AddCoins`/`AddWei` unconditionally at the end of the function: [3](#0-2) 

`SendCoinsAndWei` itself can fail for reasons other than insufficient funds: `AddWei`/`AddCoins` on the destination call `k.CanSendTo(ctx, addr)`, which consults a list of registered `RecipientChecker`s and rejects the transfer with `sdkerrors.ErrInvalidRecipient` if any checker vetoes the recipient: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

`RecipientChecker`s are registered in `app.go` via `RegisterRecipientChecker` [8](#0-7) , and can cause `CanSendTo` to reject a recipient under conditions unrelated to per-tx coinbase logic (e.g., denylisted/blocked destinations for other subsystems). Because the destination of the sweep (the fee collector, or in replay/blocktest configurations, an externally supplied coinbase Sei address) is not specially exempted, any registered checker rejecting that destination for any reason will cause the per-tx sweep to fail for every transaction in every block from that point forward, while `EndBlock` keeps proceeding as if nothing happened.

## Impact Explanation
If the sweep to the block-level `coinbase` starts failing (deterministically, for every validator, since `CanSendTo` and the checkers are pure state-derived logic run identically on all nodes), the consequence is:
1. **Permanent freezing of funds** — every EVM transaction's fee/refund balance accumulates forever at its per-tx-index ephemeral coinbase address (`state.GetCoinbaseAddress(idx)` is deterministic and reused every block at the same index) and is never reachable by users, since these addresses are not owned by any actor and the sweep never succeeds.
2. **Accounting divergence** — the `surplus` value used to mint into the EVM module account is computed independently of whether the underlying coinbase balance was actually moved. This decouples the "surplus" bookkeeping from the real distribution of funds, meaning the EVM module account can receive minted supply while the corresponding real balance is stuck at the ephemeral coinbase address — an analog to the report's core issue of a loop's running total no longer reflecting the actual state of per-item operations after a silent failure.

The severity depends on whether a concrete `CanSendTo`/`RecipientChecker` condition can be made to reject the fee collector or replay/blocktest coinbase address as the destination; I was not able to fully enumerate every registered `RecipientChecker` and its exact trigger condition to confirm this is remotely triggerable by an unprivileged actor in production configuration before running out of investigation budget. This is a genuine gap in my verification.

## Likelihood Explanation
The loop structure itself (accumulate `surplus` unconditionally; only log-and-continue on `SendCoinsAndWei` failure) is confirmed and is a deterministic code path executed on every block's `EndBlock`, so if any `CanSendTo` condition can reject the destination, the bug triggers with certainty and repeatedly (not a one-off race). The main uncertainty is exclusively about what conditions cause `CanSendTo` to reject the specific fee-collector/coinbase recipient in production — I could not confirm a concrete unprivileged trigger for that precondition within the remaining budget.

## Recommendation
- In `x/evm/keeper/abci.go`'s `EndBlock`, do not add `deferredInfo.Surplus` to the aggregate `surplus` (and thus do not mint it into the module account) for a transaction whose coinbase sweep (`SendCoinsAndWei`) failed; instead track/skip or retry that transaction's surplus separately so minted supply always corresponds to funds that were actually moved.
- Ensure the block-level `coinbase`/fee collector destination can never be rejected by `CanSendTo`/`RecipientChecker`s (e.g., exempt fee-collector-bound EVM sweeps from those checks, since fee settlement is a protocol invariant, not a discretionary transfer).
- Add an invariant/metric alert when `SendCoinsAndWei` fails in `EndBlock` so stuck ephemeral coinbase balances are detected and can be recovered via a migration rather than silently accumulating.

## Proof of Concept
Deterministic PoC sketch (illustrative, pending confirmation of a concrete `CanSendTo` veto path):
1. Register or trigger a `RecipientChecker` condition (via whatever unprivileged mechanism causes `CanSendTo` to return `false`) that rejects the fee-collector module address as a recipient.
2. Submit any EVM transaction; its fee ends up in `state.GetCoinbaseAddress(idx)`.
3. At `EndBlock`, `k.BankKeeper().SendCoinsAndWei(ctx, coinbaseAddress, coinbase, balance, weiBalance)` fails and is logged, but `surplus = surplus.Add(deferredInfo.Surplus)` still executes [9](#0-8) .
4. Repeat across blocks: the per-tx-index coinbase addresses keep accumulating unswept balances indefinitely (permanent freeze), while the EVM module account keeps receiving `surplus` mints independent of whether the corresponding real funds were ever moved.

// AddCoins increase the addr balance by the given amt. Fails if the provided amt is invalid.
// It emits a coin received event.
func (k BaseSendKeeper) AddCoins(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Coins, checkNeg bool) error {
	if !k.CanSendTo(ctx, addr) {
		return sdkerrors.ErrInvalidRecipient
	}
	if !amt.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, amt.String())
	}

	for _, coin := range amt {
		balance := k.GetBalance(ctx, addr, coin.Denom)
		newBalance := balance.Add(coin)

		err := k.setBalance(ctx, addr, newBalance, checkNeg)
		if err != nil {
			return err
		}
	}

	// emit coin received event
	ctx.EventManager().EmitEvent(
		types.NewCoinReceivedEvent(addr, amt),
	)

	return nil
}

func (k BaseSendKeeper) AddWei(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Int) (err error) {
	if !k.CanSendTo(ctx, addr) {
		return sdkerrors.ErrInvalidRecipient
	}
	if amt.Equal(sdk.ZeroInt()) {
		return nil
	}
	defer func() {
		if err == nil {
			ctx.EventManager().EmitEvent(
				types.NewWeiReceivedEvent(addr, amt),
			)
		}
	}()
	currentWeiBalance := k.GetWeiBalance(ctx, addr)
	postWeiBalance := currentWeiBalance.Add(amt)
	if postWeiBalance.LT(OneUseiInWei) {
		// no need to change usei balance
		return k.setWeiBalance(ctx, addr, postWeiBalance)
	}
	currentUseiBalance := k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount
	useiCredit, weiBalance := SplitUseiWeiAmount(postWeiBalance)
	if err := k.setBalance(ctx, addr, sdk.NewCoin(sdk.MustGetBaseDenom(), currentUseiBalance.Add(useiCredit)), true); err != nil {
		return err
	}
	return k.setWeiBalance(ctx, addr, weiBalance)
}

func (k BaseSendKeeper) SendCoinsAndWei(ctx sdk.Context, from sdk.AccAddress, to sdk.AccAddress, amt sdk.Int, wei sdk.Int) error {
	if err := k.SubWei(ctx, from, wei); err != nil {
		return err
	}
	if err := k.AddWei(ctx, to, wei); err != nil {
		return err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeWeiTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, to.String()),
			sdk.NewAttribute(types.AttributeKeySender, from.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, wei.String()),
		),
	})
	if amt.GT(sdk.ZeroInt()) {
		return k.SendCoinsWithoutAccCreation(ctx, from, to, sdk.NewCoins(sdk.NewCoin(sdk.MustGetBaseDenom(), amt)))
	}
	return nil
}

func (k BaseSendKeeper) CanSendTo(ctx sdk.Context, recipient sdk.AccAddress) bool {
	for _, rc := range *k.recipientCheckers {
		if !rc(ctx, recipient) {

		}
	}
