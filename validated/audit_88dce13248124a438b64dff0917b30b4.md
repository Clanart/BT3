### Title
`ReceivedOutput::read` accepts an unbound scalar `offset`, letting an output be recorded under the wrong spend key — funds reported received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Putty bug class is "identical wire format / call signature lets the wrong type be supplied where another is expected, so assets flow in but can never flow out." In bitcoin-serai, `ReceivedOutput` serializes an `offset` scalar alongside a `TxOut`/`OutPoint` with no binding between them. `ReceivedOutput::read` accepts any canonical scalar, and downstream `Output::key()` recomputes the spend key as `x_only_pubkey − G·offset`, trusting the deserialized offset. A `ReceivedOutput` pairing a real output's script_pubkey with a mismatched offset deserializes cleanly (the offset has the "right shape" — a canonical `Secp256k1` scalar — exactly like an ERC721 address has the right shape for an ERC20 `transferFrom`), but the resulting key does not control the output.

### Finding Description
`Scanner::scan_transaction` correctly derives `offset` from its `scripts: HashMap<ScriptBuf, Scalar>` map, so scanner-produced `ReceivedOutput`s are consistent. However, `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) reads `offset` via `Secp256k1::read_F` and `output`/`outpoint` via consensus decode independently — there is no check that `p2tr_script_buf(key + G·offset) == output.script_pubkey`. Downstream, `Output::key()` (processor/src/networks/bitcoin.rs:112-122) extracts the x-only pubkey from the script_pubkey and subtracts `G·offset` to recover the key believed to control the funds. Because `x_only` drops the sign bit, and because any scalar deserializes, an attacker-supplied or corrupted `ReceivedOutput` encoding produces a syntactically valid object whose spend key is wrong.

### Impact Explanation
Analogous to ERC721 tokens entering via `transferFrom` but being unretrievable by `transfer`, a Bitcoin output recorded with a mismatched offset is counted as received balance (`Output::balance()` returns `self.output.value()` unconditionally) while the FROST signing path derives a key/share for `key − G·offset_wrong`, which does not match the output's actual pubkey. The funds are reported received but are not spendable — signatures will not validate against the output's script_pubkey, permanently or until manual intervention.

### Likelihood Explanation
Requires untrusted bytes to reach `ReceivedOutput::read` (an entry point exercised wherever serialized outputs cross a boundary — e.g., outputs relayed between processor instances or read from shared storage). Under honest internal serialization it cannot trigger, which limits likelihood, but the format itself provides no defense and no caller-side revalidation exists in `Output::read` (processor/src/networks/bitcoin.rs:145-166).

### Recommendation
On deserialization (or before crediting), recompute `p2tr_script_buf(scanner_key + GENERATOR·offset)` and reject the `ReceivedOutput` if it does not equal `output.script_pubkey`. Alternatively, store the derived script or key instead of the raw offset, mirroring the report's recommendation of enforcing that the supplied asset is of the expected category rather than merely the expected shape.

### Proof of Concept
```text
Let key K be the scanner key and offset o1 such that
  script1 = p2tr_script_buf(K + G·o1)  (registered via Scanner::register_offset)

Attacker crafts bytes for ReceivedOutput::read:
  offset = o2  (o2 != o1, any canonical scalar, e.g. o1 + 1 adjusted for parity)
  output = TxOut { value: V, script_pubkey: script1 }   // a real, payable script
  outpoint = real outpoint

ReceivedOutput::read succeeds — o2 is a valid Secp256k1 scalar.
Output::key() computes:
  key' = point(x_only(script1)) − G·o2 = (K + G·o1) − G·o2 = K + G·(o1 − o2)  ≠ K + G·o1

The output is counted as V satoshis received, but the threshold key share for key'
cannot produce a valid BIP-340 signature for script1. Funds are stuck.
```

Note: exploitability depends on `ReceivedOutput::read` being fed attacker-influenced bytes; if it is only ever re-read from self-written, integrity-protected storage, this degrades to a defense-in-depth gap rather than a live vulnerability.
