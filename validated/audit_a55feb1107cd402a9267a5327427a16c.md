### Title
Payout attribution (`OP_RETURN` operator pubkey) is not covered by the user's `SIGHASH_SINGLE|ANYONECANPAY` signature, decoupling reimbursement credit from the actual fronting party - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction that fronts a user withdrawal, and encodes the "fronting operator" identity in an `OP_RETURN` output that is used later by verifiers to decide who gets credited (and eventually reimbursed) for the withdrawal. The only cryptographic authorization present on this transaction is the user's `SIGHASH_SINGLE|ANYONECANPAY` signature over input 0/output 0. That sighash type does **not** cover output 1 (anchor) or output 2 (`OP_RETURN`), so the operator-attribution field can be freely set by whoever completes and broadcasts the transaction, independent of who actually supplied the value being spent.

### Finding Description
`create_payout_txhandler` constructs the payout tx with three outputs: the user payout output (index 0, committed by sighash), the anchor (index 1, **not** committed), and the `OP_RETURN` carrying `operator_xonly_pk` (index 2, **not** committed): [1](#0-0) 

The comment in the test helper confirms the user signs with `SinglePlusAnyoneCanPay`: [2](#0-1) 

Because `SIGHASH_SINGLE` only binds input `i` to output `i`, and `ANYONECANPAY` only binds that single input, the witness produced by `set_p2tr_key_spend_witness(&user_sig, 0)` leaves outputs 1 and 2 completely unauthenticated — anyone in possession of the presigned input (`in_outpoint`, `output_txout`, `in_signature`) can rebuild the same transaction with a **different** `operator_xonly_pk` in the `OP_RETURN` and broadcast it, without invalidating the user's signature.

This `OP_RETURN` field is exactly what the verifier's block-processing logic uses to determine who "paid" the withdrawal: [3](#0-2) [4](#0-3) 

And this DB-recorded attribution (`payout_payer_operator_xonly_pk`) is what gates the reimbursement/kickoff flow: an operator's own node checks that the recorded payer matches its own key before proceeding to spend the round/kickoff/reimburse chain and claim funds out of the move-to-vault UTXO: [5](#0-4) [6](#0-5) 

The `withdraw()` handler that actually builds/signs this transaction only checks that the *input* UTXO value is profitable relative to the *output* amount — it performs no check that the `OP_RETURN`/attribution matches the party who created or funded the input UTXO: [7](#0-6) 

**Root cause**: the equality the protocol needs to hold is `payout_payer_operator_xonly_pk == identity of whoever actually funded/broadcast the payout UTXO`. Because the `OP_RETURN` output is outside the coverage of the only signature present on the transaction, this equality is not enforced by anything on-chain — it is simply whatever value the last-to-confirm broadcaster chose to write.

### Impact Explanation
Because the payout tx's input UTXO must already exist on-chain with sufficient value (independently funded by whoever intends to front the withdrawal) before it can be completed, "fronting" the withdrawal is really the act of funding that specific UTXO. The `OP_RETURN` is supposed to record who did that. Since it isn't bound by any signature, whoever completes/broadcasts the transaction can attach an arbitrary `operator_xonly_pk`:
- A different, uninvolved operator can be recorded in the `withdrawals` table as the payer for a withdrawal it never funded. Its own node's `validate_payer_is_operator` check will then treat that assignment as authoritative and proceed with the kickoff/round/reimburse chain, eventually spending the move-to-vault UTXO reimbursement path for a payout that operator did not actually front.
- Conversely, the operator that genuinely funded the payout UTXO can be denied credit if a rival, unsigned-field-substituted version of the same transaction confirms first (the two versions double-spend the same input, so only one can land on-chain).

This breaks the binding called out explicitly in scope: "the operator credited versus the party that paid," and maps to the Critical impact categories "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
The mechanical exploit (rebuilding the tx with a different `OP_RETURN` value while reusing the same presigned input) requires no signing key and no privileged role — it is a pure Bitcoin-transaction-construction issue rooted in the sighash flags chosen in `create_payout_txhandler`. However, I was not able to fully confirm, within the scope of code I reviewed, how broadly the presigned withdrawal parameters (`in_outpoint`, `output_txout`, `in_signature`) are exposed prior to confirmation — the `Aggregator::withdraw` RPC fans this data out to all operators simultaneously (core/src/rpc/aggregator.rs), which is the protocol's own intended distribution to the pool of eligible fronting operators, but I did not verify whether this data is otherwise reachable by a party outside that eligible set without network interception. This affects likelihood but not the underlying root-cause defect, which is real and independent of how the data reaches an attacker.

### Recommendation
Change the sighash type (or transaction structure) so that the `OP_RETURN` attribution output is covered by the same signature that authorizes spending the input, e.g. by having the user sign with `SIGHASH_ALL` (or a taproot-appropriate equivalent that commits to all outputs), or by moving the attribution off the unauthenticated part of the transaction entirely (e.g., deriving payer identity solely from which key spends a script path that only the legitimate fronting operator controls, rather than from an `OP_RETURN` that any broadcaster can set).

### Proof of Concept
1. Obtain a valid, not-yet-confirmed set of payout parameters: `in_outpoint`, `output_txout`, `in_signature` (as accepted by `create_payout_txhandler`), corresponding to a withdrawal whose input UTXO has already been funded on-chain by operator A.
2. Call `create_payout_txhandler` (or replicate its construction) with the same `input_utxo`/`output_txout`/`user_sig`, but substitute `operator_xonly_pk` with operator B's xonly public key in place of A's: [1](#0-0) 
3. Broadcast this alternate transaction so it confirms before operator A's original transaction (both spend the same input, so only one can land).
4. When the verifier processes the confirming block, `update_finalized_payouts` parses the `OP_RETURN` and records operator B as `payout_payer_operator_xonly_pk` for this withdrawal: [8](#0-7) 
5. Operator B's node, running `validate_payer_is_operator`/`get_reimbursement_txs`, will now see itself recorded as the payer and proceed through the kickoff/reimburse flow to claim reimbursement for a withdrawal it never funded, while operator A (the real funder) can no longer be credited since its version of the transaction was double-spent out: [5](#0-4)

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };

        tracing::info!(
            "Payer xonly pk, payout blockhash and kickoff txid found and valid for own operator for the requested deposit id: {}, payer xonly pk: {:?}, payout blockhash: {:?}, kickoff txid: {:?}",
            deposit_id,
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid
        );

        Ok((payout_blockhash, kickoff_txid))
    }
