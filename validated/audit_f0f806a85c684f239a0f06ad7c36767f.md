Confirmed: `Branch` objects come from `getBranches` in `for-each-ref.ts`, which populates `name` directly from git's `%(refname:short)` output for any ref under `refs/heads` / `refs/remotes` — including refs fetched from an attacker-controlled remote. [1](#0-0) 

### Title
Argument injection into `git rebase` via unsanitized branch names lacking `--` end-of-options marker - (File: app/src/lib/git/rebase.ts)

### Summary
`rebase()` builds its argv as `[...gitRebaseArguments(), 'rebase', baseBranch.name, targetBranch.name]` and passes `baseBranch.name`/`targetBranch.name` directly as positional operands to `git rebase`, with no `--` end-of-options marker separating them from option parsing. [2](#0-1) 

### Finding Description
`baseBranch` and `targetBranch` are `Branch` objects whose `name` field is taken verbatim from `%(refname:short)` when Desktop enumerates refs via `getBranches`. [3](#0-2) [4](#0-3)  These refs can originate from a remote (e.g. `refs/remotes/origin/<branch>`) that the attacker fully controls, since ref names allow any character except ASCII control chars, space, DEL, and `~^:?*[\|"<>` — notably `-`, `$`, `(`, `)`, `` ` ``, `;` remain valid ref-name characters, as encoded in Desktop's own sanitizer regex. [5](#0-4) 

Unlike other git wrappers in this codebase — e.g. `checkoutBranch`, which explicitly appends a `--` end-of-options terminator after the ref name before invoking `git checkout` — `rebase()` places the raw ref strings as the first positional arguments right after the `rebase` subcommand, with no such terminator. [6](#0-5) [7](#0-6) 

If a branch fetched from a malicious remote were named beginning with `-` (e.g. via an option that implies `-x`/`--exec`, or other rebase/merge-strategy flags that accept an attached value like `-x<cmd>`), that single argv token would be parsed by git's option parser as a flag+attached-value rather than as a ref, because dugite/Node's `spawn` passes argv arrays directly (no shell parsing splits it), but git's own getopt-style parsing of a single token like `-xtouch$IFS/tmp/pwned` still treats `-x` as the option and the remainder as its attached argument.

### Impact Explanation
If exploitable, this allows attacker-controlled ref names (reachable purely by getting a victim to fetch/clone a repository containing a maliciously-named branch, then trigger a rebase involving it through Desktop's UI) to inject git options instead of being treated as inert ref operands. Depending on the option smuggled in (e.g. an `--exec`/`-x`-style command execution primitive, or a custom merge `--strategy` resolving to an attacker-supplied helper on `PATH`), this could result in arbitrary command execution on the victim's machine — a Critical-impact issue per the program's stated scope.

### Likelihood Explanation
Exploitability is not fully confirmed from static review alone and carries meaningful caveats I could not verify without running git:
- `git rebase -x`/`--exec` implies `-i` and would trigger interactive-mode todo/sequence-editor handling; `rebase()` does not set `GIT_SEQUENCE_EDITOR`/`GIT_EDITOR` overrides (unlike `continueRebase`/`rebaseInteractive`, which do), so behavior in a non-TTY spawned process is uncertain and might fail rather than silently execute.
- Whether current git versions still allow a ref name that is itself a bare `check-ref-format`-valid string beginning with `-` to be created/fetched at all (some git versions/hosts reject `-`-prefixed refs at `branch`/`update-ref`/`receive-pack` level) was not verified in this review.
- These uncertainties mean the concrete PoC command needs empirical validation against a live git binary before treating this as confirmed RCE; what is confirmed by code inspection is the structural flaw (missing `--` separator / lack of leading-`-` rejection) that is otherwise defended against elsewhere in the codebase.

### Recommendation
Add a `--` end-of-options marker before `baseBranch.name`/`targetBranch.name` in the `rebase()` argv (mirroring the pattern already used in `checkout.ts`), and/or reject branch/ref names beginning with `-` before they are used as git command arguments anywhere refs are sourced from untrusted (remote) data.

### Proof of Concept
Not independently verified end-to-end (requires confirming that a `-`-prefixed ref can be created/fetched by a real git server/client and that `-x`/`--exec` or another attached-value option executes without an interactive TTY). Suggested validation: in a test harness, create a local branch literally named `-x` + `touch /tmp/pwned` variant (no space, e.g. using `$IFS`), call `rebase(repository, thatBranch, targetBranch)`, and assert whether git treats it as a ref (fails to resolve) versus as an option (differing error/behavior), then compare against the same test performed through `checkoutBranch` (which uses `--`) to demonstrate the differential handling.

export async function rebase(
  repository: Repository,
  baseBranch: Branch,
  targetBranch: Branch,
  progressCallback?: (progress: IMultiCommitOperationProgress) => void
): Promise<RebaseResult> {
  const baseOptions: IGitStringExecutionOptions = {
    expectedErrors: new Set([GitError.RebaseConflicts]),
  }

  let options = baseOptions

  if (progressCallback !== undefined) {
    const commits = await getCommitsBetweenCommits(
      repository,
      baseBranch.tip.sha,
      targetBranch.tip.sha
    )

    if (commits === null) {
      // BadRevision can be raised here if git rev-list is unable to resolve a
      // ref to a commit ID, so we need to signal to the caller that this rebase
      // is not possible to perform
      log.warn(
        'Unable to rebase these branches because one or both of the refs do not exist in the repository'
      )
      return RebaseResult.Error
    }

    options = configureOptionsForRebase(baseOptions, {
      commits,
      progressCallback,
    })
  }

  const result = await git(
    [...gitRebaseArguments(), 'rebase', baseBranch.name, targetBranch.name],
    repository.path,
    'rebase',
    options
  )

  return parseRebaseResult(result)
}

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}
