### Title
Cross-chain order cancellation races destination fill, allowing double release of escrowed funds - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The External report's core broken invariant is: two independent chains each locally compute a delta/state change and then "sync" that change to the other chain via an async message, without any lock or ordering guarantee — so late-arriving cross-chain messages can overwrite or duplicate state that has since moved on. The Hyperbridge Intent Gateway's cross-chain cancel/fill flow reproduces the same broken invariant: the source chain's "cancel" decision is based on a **stale snapshot** (a GET proof of `_filled[commitment]` on the destination taken at a fixed historical height), while the destination chain can independently accept a fill or process the cancellation at a different real-time point, with no shared lock between the two chains' escrow state.

### Finding Description
`IntentGatewayV2.cancelOrder` on the source chain (`_cancelFromSource` in [1](#0-0) ) requires only that `options.height > order.deadline` and dispatches a `DispatchGet` to read the destination's `_filled[commitment]` storage slot **at that specific height**. If the response proves the slot was empty at that height, `onGetResponse` calls `withdraw()` and releases the escrow to the user on the source chain.

Separately, `_cancelFromDest` (same file, lines 240-267) lets anyone mark the order filled/cancelled locally on the destination and dispatch a `RefundEscrow` POST back to source — which independently triggers `withdraw()` on the source chain.

Because these are two independent, asynchronously-delivered cross-chain messages targeting the same `withdraw()` entrypoint and the same escrow accounting (`_orders[commitment][token]`), the correctness of "exactly-once settlement" depends entirely on `_filled[commitment]` being set atomically and consistently *before* either message is dispatched. The GET-based cancel path explicitly reads a **past** state (at `options.height`, which must simply be greater than `order.deadline` — not the *current* head), meaning the proof does not certify "no fill has ever happened since then," only "no fill had happened at that historical height." A fill that lands on the destination chain in the window between the queried height and the actual GET-response delivery would not be reflected in that proof, yet the proof would still be accepted as authorization to release escrow via `withdraw()` on the source chain — mirroring the LayerZero bug's core defect: consuming a stale snapshot from another chain as if it were current truth, with no cross-chain lock preventing the two settlement paths from targeting the same escrow.

I was not able to confirm within the available tool budget whether `fillOrder`/`_fillCrossChain` on the destination independently enforces `order.deadline >= block.number` as a hard gate (this check is documented for `_cancelFromDest`, but I did not verify the same guard exists inside the fill path itself). If no deadline gate exists on fill, the race window is trivially reachable by any solver.

### Impact Explanation
If exploitable, this allows either double-settlement of the same escrowed funds (fill pays out on destination via `RedeemEscrow`→`withdraw`, while a source-side cancel triggered by a stale GET proof also pays out via `withdraw`) or a wrongful refund to the user after a legitimate fill has already delivered the destination-side payout to a solver — i.e., loss of solver funds or double payment of the same escrow, matching the bounty's "stealing or loss of funds" and "double-settlement" categories.

### Likelihood Explanation
This requires only unprivileged actors: a solver filling an order and the order's own user (or, post-deadline, anyone) triggering `cancelOrder` from the source chain — no relayer collusion, admin action, or leaked keys are needed to *initiate* the race, only the natural asynchrony of cross-chain proof delivery and the challenge-period-based finality window that Hyperbridge already requires for state proofs. This makes exploitation plausible under normal operating conditions rather than requiring an adversarial relayer.

### Recommendation
The GET-based cancel-from-source path should not accept a historical height >`order.deadline` as sufficient proof of non-fill; it must additionally verify that the destination height queried is the latest finalized height at time of response delivery (or otherwise pin the query to a height at/after the response's actual delivery time), and/or `withdraw()` should treat any conflicting cross-chain settlement message for the same commitment as a hard double-spend guard by re-checking on-chain that `_filled[commitment]` (or an equivalent settlement flag) has not been set by a concurrently-delivered fill/refund message before executing the token transfer.

### Proof of Concept
Not independently reproduced — this is a structural race-condition analysis based on the documented control flow (`ExtrinsicIntents.sol` lines 173-267, `docs/content/developers/evm/intent-gateway/cancelling-orders.mdx` lines 59-76) and the shared `withdraw()` settlement entrypoint. A concrete PoC would need to confirm (1) the exact fill-side deadline enforcement and (2) whether `withdraw()` re-validates the `_filled` flag atomically against both message types before disbursing funds — both of which require deeper reading of `withdraw()` and `_fillCrossChain` in `ExtrinsicIntents.sol` / `IntentsBase.sol` than was possible in the remaining tool budget.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
