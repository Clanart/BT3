### Title
Duplicate/unauthorized minting of IBC-transferred value via erc20 middleware overriding a successful acknowledgement with an error acknowledgement after state has already been committed - (File: x/erc20/ibc_middleware.go, x/erc20/keeper/ibc_callbacks.go)

### Summary
The reported LP-token bug is a case of asset value and its associated protocol bookkeeping becoming decoupled: the underlying value moves (tokens transferred) but the bookkeeping used to authorize further movement (the lock/redeem record) is not updated atomically with it, permanently corrupting accounting. The reachable analog in this repository is in the `x/erc20` IBC middleware's `OnRecvPacket` flow: the underlying ICS-20 transfer application commits its balance-affecting state changes (crediting the receiver's bank balance) before the `x/erc20` middleware decides the final acknowledgement, and when the middleware subsequently fails to convert the coin to its ERC-20 representation, it returns a **new error acknowledgement** to the core IBC channel handler. That error acknowledgement causes the *source* chain to run its refund path (unlocking/re-minting the sender's original coins) even though the *destination* chain has already durably credited the receiver with the same value.

### Finding Description
`IBCMiddleware.OnRecvPacket` in `x/erc20/ibc_middleware.go` first calls the wrapped ICS-20 transfer application's `OnRecvPacket`: [1](#0-0) 

This call executes against the live, non-cached `ctx`. The core transfer app's `OnRecvPacket` immediately performs the bank-level state mutation for the packet (minting a voucher or unescrowing native coins to the receiver, here the isolated callback address or hex-mapped recipient) and returns a success acknowledgement, which is then committed.

Only after that state mutation has already occurred does `IBCMiddleware.OnRecvPacket` call `im.keeper.OnRecvPacket`, i.e. `Keeper.OnRecvPacket` in `x/erc20/keeper/ibc_callbacks.go`: [2](#0-1) 

For a registered native-ERC20 token pair, this function calls `MintingEnabled`, which can fail for several unprivileged/ordinary reasons — the ERC20 module being disabled, the token pair being disabled, the receiver being blocked, or bank `SendEnabled` being false for the denom: [3](#0-2) 

If `MintingEnabled` or the subsequent `ConvertCoinNativeERC20` call fails, `Keeper.OnRecvPacket` returns a brand-new `channeltypes.NewErrorAcknowledgement(err)`: [4](#0-3) 

This error acknowledgement replaces the success acknowledgement that the underlying transfer application already returned — **after** that application had already committed its balance change to the receiver on the destination chain. Because the acknowledgement, not any state rollback, is what is relayed back to the source chain, the source chain will interpret the packet as failed and execute its standard ICS-20 failure path (refunding/unlocking the sender's original coins), while the destination chain retains the coins it already credited to the receiver in the same `OnRecvPacket` execution.

The project's own integration test acknowledges this exact scenario: a packet whose ERC20 conversion fails (there, due to `SendEnabled=false`) still results in the transferred amount being durably credited as a bank balance to the receiver (the isolated address) even though the erc20 middleware converts that failure into a returned acknowledgement: [5](#0-4) 

Because this failure path (`MintingEnabled` returning an error, e.g. via bank `SendEnabled` toggling, blocked-address status, or a disabled token pair — all of which can also transiently apply to ordinary users, not just admins) triggers an already-committed credit on the destination combined with a refund-triggering error acknowledgement, the same nominal value can end up available on both sides of the channel, which is a duplication of spendable user value across an IBC-mediated asset representation.

### Impact Explanation
If the sending chain, upon receiving the returned error acknowledgement, refunds/unlocks the original sender's tokens (standard ICS-20 `OnAcknowledgementPacket` failure behavior), then the total circulating value across both chains increases by the amount of every recv-packet whose erc20 conversion step fails after the transfer application has already credited the receiver. This is unauthorized duplication of spendable value across native balances / IBC escrows, matching the Critical impact category for accounting corruption and duplication of user value.

### Likelihood Explanation
The trigger conditions for `MintingEnabled` failure are reachable without any privileged actor: a receiver on the bank `BlockedAddr` list, a token pair that becomes disabled via governance, the ERC20 module toggle, or `SendEnabledCoin` being false for the denom (a parameter that can be legitimately toggled during normal chain operation, or hit for tokens that are send-disabled by default policy). Any relayer delivering a normal ICS-20 packet during such a window triggers this code path deterministically; no malicious relayer collusion is strictly required for the destination-side credit and source-side refund to both occur.

### Recommendation
Ensure the erc20 middleware's failure-to-convert path does not overturn an already-committed successful transfer acknowledgement. Either:
- Perform the `MintingEnabled` / conversion attempt via a branched (cached) context prior to committing the coin transfer, only writing state once the final acknowledgement is determined, or
- If conversion fails, leave the original success acknowledgement intact (since the coin has already legitimately reached the receiver as a bank-denominated token, as the code comments intend) rather than returning a new error acknowledgement that will cause the source chain to also refund the sender.

### Proof of Concept
1. Register a native ERC20 token pair and set the bank module to `SendEnabled=false` for its denom (or otherwise cause `MintingEnabled` to fail) as demonstrated in `TestOnRecvPacketNativeErc20` at [6](#0-5) .
2. Relay an ICS-20 transfer packet for that denom to the EVM chain. The core transfer app's `OnRecvPacket` credits the receiver's bank balance with the packet amount and returns success.
3. `x/erc20` `Keeper.OnRecvPacket`'s `MintingEnabled` check fails, and a new error acknowledgement is returned and relayed back to the source chain.
4. The source chain, upon receiving the error acknowledgement, executes its standard ICS-20 refund logic and returns the original amount to the sender.
5. The destination chain still holds the bank-credited balance for the receiver (demonstrated by `trappedBal` assertions in the test at [7](#0-6) ), resulting in the same value existing on both chains simultaneously.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

func (k Keeper) OnRecvPacket(
	ctx sdk.Context,
	packet channeltypes.Packet,
	ack exported.Acknowledgement,
) exported.Acknowledgement {
	// If ERC20 module is disabled no-op
	if !k.IsERC20Enabled(ctx) {
		return ack
	}

	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		// NOTE: shouldn't happen as the packet has already
		// been decoded on ICS20 transfer logic
		err = errorsmod.Wrapf(errortypes.ErrInvalidType, "cannot unmarshal ICS-20 transfer packet data")
		return channeltypes.NewErrorAcknowledgement(err)
	}

	// use a zero gas config to avoid extra costs for the relayers
	ctx = ctx.
		WithKVGasConfig(storetypes.GasConfig{}).
		WithTransientKVGasConfig(storetypes.GasConfig{})

	// recipient (local chain address): accept hex or local bech32
	recipientBz, err := k.addrCodec.StringToBytes(data.Receiver)
	if err != nil {
		return channeltypes.NewErrorAcknowledgement(errorsmod.Wrap(err, "invalid recipient"))
	}
	recipient := sdk.AccAddress(recipientBz)

	receiverAcc := k.accountKeeper.GetAccount(ctx, recipient)

	// return acknowledgement without conversion if receiver is a module account
	if types.IsModuleAccount(receiverAcc) {
		return ack
	}

func (k Keeper) MintingEnabled(
	ctx sdk.Context,
	receiver sdk.AccAddress,
	token string,
) (types.TokenPair, error) {
	if !k.IsERC20Enabled(ctx) {
		return types.TokenPair{}, errorsmod.Wrap(
			types.ErrERC20Disabled, "module is currently disabled by governance",
		)
	}

	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	if !pair.Enabled {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrERC20TokenPairDisabled, "minting token '%s' is not enabled by governance", token,
		)
	}

	if k.bankKeeper.BlockedAddr(receiver.Bytes()) {
		return types.TokenPair{}, errorsmod.Wrapf(
			errortypes.ErrUnauthorized, "%s is not allowed to receive transactions", receiver,
		)
	}

	// NOTE: ignore amount as only denom is checked on IsSendEnabledCoin
	coin := sdk.Coin{Denom: pair.Denom}

	// check if minting to a recipient address other than the sender is enabled
	// for for the given coin denom
	if !k.bankKeeper.IsSendEnabledCoin(ctx, coin) {
		return types.TokenPair{}, errorsmod.Wrapf(
			banktypes.ErrSendDisabled, "minting '%s' coins to an external address is currently disabled", token,
		)
	}

	return pair, nil
