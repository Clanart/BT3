### Title
`send()` in the Bank precompile trusts caller-supplied `fromAddress` without verifying it belongs to the calling ERC20 pointer's own EVM msg.sender - (File: `precompiles/bank/bank.go`)

### Summary
The `send` handler of the native Bank precompile (`0x0000000000000000000000000000000000001001`) authenticates only that the immediate EVM `caller` is the registered ERC20-native pointer for the given `denom`, then uses an entirely separate, attacker-controlled `args[0]` (`fromAddress`) as the account whose funds are moved via `MsgSend`. This mirrors the CVE-2026-72045 pattern: the mailbox dispatcher authenticated `req.hdr.pcifunc` (the IRQ source) but a *different* unauthenticated payload field, `req.base_pcifunc`, was used as the actual resource index. Here, the precompile authenticates the *caller* (the pointer contract address) but a *different* unauthenticated payload field, `fromAddress`, is used as the actual account whose balance is drained.

### Finding Description
`PrecompileExecutor.send` in `precompiles/bank/bank.go` validates only that `caller == pointer` for the given `denom`: [1](#0-0) 

It then takes `senderSeiAddr` directly from `args[0]` (the `fromAddress` parameter) with no requirement that it equals the actual originating EOA/user that triggered the pointer's ERC20 `transfer`/`transferFrom`: [2](#0-1) 

The only ERC20-native pointer contract shipped in the repo, `NativeSeiTokensERC20`, forwards OpenZeppelin's `_update(from, to, value)` hook directly into `BankPrecompile.send(from, to, denom, value)`: [3](#0-2) 

In OpenZeppelin's ERC20, `_update` is called from `transfer` (with `from = msg.sender`) but also from `transferFrom`, where `from` is the caller-supplied `owner`/`from` argument gated only by an ERC20 allowance check performed in Solidity storage local to the pointer contract, not by the Bank precompile. If `NativeSeiTokensERC20` (or any custom-deployed native-token ERC20 pointer contract, since deployment of arbitrary contracts is permitted on EVM) fails to correctly enforce/decrement the allowance before invoking `_update`/`send`, or if the pointer contract has any logic bug in its allowance bookkeeping, the Bank precompile provides no second line of defense: it will move funds from any `fromAddress` supplied, as long as the call is routed through that specific pointer contract's own EVM call. The precompile's sole authorization check is "is the immediate caller the registered pointer for this denom", which says nothing about who authorized moving `fromAddress`'s coins specifically.

This is structurally identical to the CVE: `is_pf_func_valid()`/similar ownership checks bound the *index field* to the caller's own scope in the fixed kernel code, whereas `rvu_mbox_handler_lmtst_tbl_setup` trusted `base_pcifunc` post-authenticating only the IRQ-derived caller identity. `send()` authenticates the calling contract address but never binds `fromAddress` to any authenticated identity of the actual transaction sender or to an allowance check enforced at the precompile/keeper layer.

### Impact Explanation
If exploitable, this allows unauthorized transfer of native Sei bank-module funds (`usei` and any other denom that has a registered ERC20-native pointer) out of arbitrary victim accounts, i.e., direct fund loss for any address holding tokens through a native-token ERC20 pointer. This matches the "unauthorized transfer via precompile or pointer" and "concrete fund loss" impact categories.

### Likelihood Explanation
Exploitability is contingent on there existing (or a user/attacker being able to deploy) a pointer/proxy contract registered as `GetERC20NativePointer` for some denom whose `transferFrom`/allowance enforcement can be bypassed or is buggy — the shipped `NativeSeiTokensERC20` implementation is a thin wrapper over OpenZeppelin's audited `ERC20._update`/`transferFrom`, which does perform allowance decrement correctly in the reference implementation reviewed. I was not able to fully confirm within this session whether: (a) native ERC20 pointer registration is restricted to a governance/whitelisted set of audited contracts (which would make this unexploitable in practice), or (b) any additional pointer address whitelist/immutability check exists elsewhere in `x/evm/keeper/pointer.go` restricting which contracts can become `GetERC20NativePointer`. This uncertainty affects whether the bug is practically reachable by an unprivileged actor or is only a defense-in-depth gap behind an already-trusted pointer contract.

### Recommendation
Add a second authorization boundary at the Bank precompile itself, independent of the calling contract's own bookkeeping: require that `fromAddress` (or its Sei equivalent) be cryptographically tied to the actual EVM transaction origin/sender for non-pointer-mediated transfers, or require pointer contracts to only ever call `send` with `from == caller`'s associated address for `transfer`, and require an explicit, precompile-tracked allowance record (verified by the precompile itself, not delegated to the pointer contract's Solidity state) for `transferFrom`-style calls. Alternatively, restrict `GetERC20NativePointer` registration to an immutable, protocol-controlled bytecode template that is guaranteed to gate `from` by `msg.sender`/allowance correctly, and add an explicit code hash/audit check before honoring the pointer.

### Proof of Concept
Not able to construct a concrete on-chain PoC within this session: exploitation requires either (1) deploying/registering a custom malicious "pointer" contract for some denom that calls `BankPrecompile.send(victim, attacker, denom, amount)` without any allowance check, and confirming registration of arbitrary pointer contracts is permitted for an unprivileged deployer, or (2) finding a logic flaw in the shipped `NativeSeiTokensERC20`'s `transferFrom`/allowance path itself. I could not verify which pointer-registration model sei-chain enforces (governance-gated vs. permissionless) within the available search results, so likelihood/exploitability of this specific analog is uncertain and should be validated against `x/evm/keeper/pointer.go` (`RegisterPointer`/`GetERC20NativePointer` set-up logic) before treating this as confirmed.

```go
func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
```
