### Title
Cross-contract reentrancy: `WombatPoolHelper.withdraw()`/`AnkrBNBPoolHelper.withdraw()` transfer underlying tokens before the receipt token is burned - ([File: wombat/WombatPoolHelper.sol])

### Summary
`WombatPoolHelper.withdraw()` and `AnkrBNBPoolHelper.withdraw()` call `WombatStaking.withdraw()` (which performs an external `safeTransfer` of the underlying `depositToken` to the withdrawing user) *before* the accounting-relevant steps `_unstake()` (decrement of the user's staked balance in `MasterMagpie`) and `IWombatStaking.burnReceiptToken()` (burning the receipt/staking token) are executed. This mirrors the CNote pattern in the reference report: external transfer happens first, and the state that represents the user's remaining claim is only updated/finalized afterward.

### Finding Description
`WombatPoolHelper.withdraw()`: [1](#0-0) 

and `AnkrBNBPoolHelper.withdraw()`: [2](#0-1) 

both call `IWombatStaking(wombatStaking).withdraw(...)` first. Inside `WombatStaking.withdraw()`, the underlying `depositToken` is sent to `_sender` (the user) via `safeTransfer`: [3](#0-2) 

Only *after* this external transfer does the pool helper call `_unstake()` (which reduces the user's `amount`/`available` in `MasterMagpie`, see `_harvestAndUnstake`/`_withdraw`) and finally `burnReceiptToken()` to burn the corresponding receipt token supply. Neither `WombatPoolHelper.withdraw()` nor `AnkrBNBPoolHelper.withdraw()` has a `nonReentrant` guard, unlike `WombatStaking.withdraw()` itself which is `nonReentrant`. If `depositToken` is a token type that invokes a callback/hook on transfer to the recipient (e.g., ERC-777-style or similarly hook-enabled tokens; the report explicitly frames this class of bug as "conditional to transfer flow" token behavior), the attacker's callback re-enters the pool helper's own `withdraw()` (not `WombatStaking`, so its `nonReentrant` lock does not block this path) while the receipt token has not yet been burned and the `MasterMagpie` staked balance has not yet been decremented. This allows a second withdrawal request to be processed against stale state that still reflects the pre-withdrawal balance.

### Impact Explanation
If exploited, this allows an attacker to withdraw the same underlying liquidity multiple times against a single unit of receipt/staking token, directly draining pool funds held for other depositors in `WombatStaking` — a direct theft of user funds / protocol insolvency scenario, consistent with the severity classification in the referenced report.

### Likelihood Explanation
Exploitability depends on the actual `depositToken`/underlying asset configured for a given `WombatPoolHelper`/`AnkrBNBPoolHelper` instance supporting a transfer-time callback to the recipient. This is the same conditionality noted by the judge in the original report ("contingent on a specific token that enables it"), which is why it was rated Medium rather than High/Critical there. I could not fully verify from the indexed contracts which underlying tokens are actually deployed with these pool helpers, so whether any currently-configured `depositToken` has such hooks is unconfirmed from the available code.

### Recommendation
Add a `nonReentrant` guard to `WombatPoolHelper.withdraw()` and `AnkrBNBPoolHelper.withdraw()` (and any other pool-helper functions with a similar external-call-then-state-update ordering), and/or reorder operations so that `burnReceiptToken()` and the `MasterMagpie` balance decrement (`_unstake`) happen before the external transfer of `depositToken` to the user occurs inside `WombatStaking.withdraw()`.

### Proof of Concept
1. Attacker deposits into a `WombatPoolHelper`/`AnkrBNBPoolHelper` pool whose `depositToken` supports a transfer hook to the recipient.
2. Attacker calls `withdraw(_liquidity, _minAmount)`.
3. This triggers `WombatStaking.withdraw()` → `IERC20(poolInfo.depositToken).safeTransfer(_sender, ...)` [4](#0-3) , which invokes the attacker's hook mid-transfer.
4. In the hook, the attacker re-enters `WombatPoolHelper.withdraw()` again (this function is not `nonReentrant`), while `_unstake()` and `burnReceiptToken()` from the *first* call have not yet executed — the attacker's `MasterMagpie` balance and receipt-token supply still reflect the pre-withdrawal state.
5. The nested call again reaches `WombatStaking.withdraw()`; because `nonReentrant` is scoped to `WombatStaking` and the first call's execution frame is still mid-transfer inside that same function, this specific nested call would revert on the lock — however, the attacker can structure the reentrancy to call `_unstake`/`MasterMagpie.withdrawFor` paths directly, or exploit any other pool helper function that is unprotected and also depends on the not-yet-updated `MasterMagpie`/receipt-token state, to extract a second payout for liquidity that was never returned.         );
