### Title
Desktop silently rewrites the local git remote URL from an untrusted GitHub API `clone_url` field, redirecting future pushes/fetches without user confirmation - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Malt finding is about a privileged component (`timekeeper`) being swapped for a new one whose internal state (`epoch`) is blindly trusted, letting the new state silently override invariants the rest of the system depends on (accumulated `rewarded` amounts), with no re-validation against the previous trusted state. The GitHub Desktop analog is `updateRemoteUrl()`, which blindly trusts a mutable field (`clone_url`) coming from a GitHub API response object and uses it to silently reconfigure the git remote that all future `push`/`pull`/`fetch` operations target, with the only "guard" being a string comparison against previously cached (also API-sourced) data rather than explicit, fresh user confirmation.

### Finding Description
`updateRemoteUrl` decides whether to rewrite the repository's `origin` remote based purely on data returned from the GitHub API: [1](#0-0) 

The only checks performed before calling `git remote set-url` are:
- `protocolsMatch` – the scheme of the old and new URL is the same,
- `remoteUrlUnchanged` – the *current* local remote still matches the *previously cached* `gitHubRepository.cloneURL` (itself populated from a prior API response, not from anything the user typed or confirmed),
- `!urlsMatch` – the API's new `clone_url` differs from what's currently configured. [2](#0-1) 

If all three hold, Desktop calls `gitStore.setRemoteURL(...)`, which runs `git remote set-url <name> <url>` directly against the repository's git config: [3](#0-2) 

This function is invoked from `repositoryWithRefreshedGitHubRepository`, a path that is exercised automatically and frequently — on repository selection, after every push/pull/fetch, and via background fetch/indicator refresh — with no user prompt or diff shown: [4](#0-3) 

`apiRepo` is obtained straight from `api.fetchRepository(owner, name)`, i.e., it is the "GitHub API object" category called out in the valid-impact list — its `clone_url` field is fully attacker-influenceable by anyone who can rename or transfer the underlying GitHub-side repository (repo rename, ownership transfer, or a compromised/malicious org-repo admin on a shared repository), or by a malicious/compromised GHES server for enterprise accounts. Neither `updateRemoteUrl` nor its caller re-validates that the new `clone_url` still refers to the same repository identity the user originally trusted (e.g., by pinned repository ID) — it only checks that the *string* differs from the last cached value, which is itself derived from the same untrusted source. This mirrors the Malt bug's broken invariant: a downstream component blindly consumes a new state value from an "authoritative" source without confirming it against the actual trust boundary (the user's original consent), enabling silent state corruption.

### Impact Explanation
Because the rewrite happens transparently as part of routine refresh operations (not a dedicated "Repository Settings → remote" action the user explicitly approves), a user who clicks "Fetch" or "Push" can have those operations silently redirected to a different remote URL than the one they set up, without ever seeing a diff or confirmation dialog. This falls squarely into "silent corruption of what the user commits or pushes": commits/pushes end up going to an unintended destination determined entirely by content returned from the network/API layer.

### Likelihood Explanation
Likelihood is moderate: the attacker must have the ability to influence the `clone_url` reported by the GitHub API for a repository the victim has cloned (e.g., by renaming/transferring a repo they administer, or via a malicious/compromised GHES instance for enterprise users). No local access, malware, or credential theft is required from the victim's side — the trigger is a normal Desktop background/foreground refresh cycle that already runs automatically. The `sendNonFatalException` guard nearby in `performPush` (for `remoteNameMismatch`) shows the team is aware that remote-identity mismatches are a live concern in this codebase, but that guard only covers remote *name* vs. branch-remote mismatch, not the automatic *URL* rewrite from API data.

### Recommendation
- Do not auto-rewrite the git remote URL purely from API `clone_url` string comparison. Require explicit user confirmation (a dialog showing old vs. new URL) before calling `setRemoteURL`.
- Anchor the "same repository" check to a stable identifier (e.g., API repository `id`/`dbID`) rather than string-matching mutable `clone_url`/name/owner fields, so a rename/transfer to an attacker-controlled destination with a different ID cannot pass as "unchanged."
- Log/audit remote URL changes driven by background refreshes distinctly from user-initiated changes.

### Proof of Concept
1. Victim clones `https://github.com/victim-org/example` in GitHub Desktop; Desktop caches the associated `GitHubRepository` with `cloneURL = https://github.com/victim-org/example`.
2. An attacker with rename/transfer rights on that GitHub-side repository (e.g., a malicious or compromised collaborator with admin rights, or org owner) renames/transfers it so the GitHub API now reports `clone_url = https://github.com/attacker-org/example` for the same repository match key used by Desktop (`owner`/`name`/`account` from `matchGitHubRepository`, see `app/src/lib/repository-matching.ts` lines 28-46).
3. On the victim's next automatic refresh (repository selection, background fetch, or right after any push/pull — see `app/src/lib/stores/app-store.ts` lines 4890-4913), `api.fetchRepository(owner, name)` returns the new `clone_url`.
4. `updateRemoteUrl` sees `protocolsMatch = true`, `remoteUrlUnchanged = true` (local remote still equals last cached `cloneURL`), `urlsMatch = false`, and silently calls `gitStore.setRemoteURL('origin', 'https://github.com/attacker-org/example')` (`app/src/lib/stores/updates/update-remote-url.ts` lines 42-44; `app/src/lib/git/remote.ts` lines 56-64).
5. The victim's next `git push`/`git fetch` from Desktop now targets `attacker-org/example` without any prompt, confirming silent redirection of push/fetch destination.

Note: I was not able to fully trace `matchGitHubRepository` (the `app-store.ts` private method) and `RepositoriesStore.setGitHubRepository`/`upsertGitHubRepositoryFromMatch` end-to-end within the tool budget to confirm the exact identity key (owner/name vs. stable repo ID) used across a rename/transfer; if Desktop instead re-resolves by a stable numeric ID that never changes across renames, the practical exploitability could be narrower than described. Starting a Devin session to read `app/src/lib/stores/repositories-store.ts` and `app/src/lib/stores/app-store.ts`'s `matchGitHubRepository` in full would confirm this end-to-end.

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
