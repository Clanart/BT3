### Title
Keychain namespace parameter (`kc_user`/`kc_service`) is attacker-selectable, allowing any local daemon-authenticated caller to read another local Chia user's private keys - (File: chia/daemon/keychain_server.py)

### Summary
The GitLab advisory (BIT-gitlab-2025-6195 / CVE-2025-6195) is a broken-access-control ("forced browsing") bug where an authenticated user could reach security-report data outside their authorization scope by manipulating request parameters instead of relying on the intended access path. The analogous condition in this codebase is in `KeychainServer.get_keychain_for_request()`, which selects the keychain *namespace* to operate on purely from attacker-supplied `kc_user`/`kc_service` fields in the request body, with no verification that the calling connection is entitled to that namespace.

### Finding Description
`KeychainServer.get_keychain_for_request()` builds/returns a `Keychain` instance keyed only by the `kc_user`/`kc_service` strings taken directly from the incoming request dict: [1](#0-0) 

Every keychain command (`get_key`, `get_keys`, `get_all_private_keys`, `get_first_private_key`, `get_key_for_fingerprint`, `add_key`, `delete_key_by_fingerprint`, `delete_all_keys`, `set_label`, `delete_label`) is dispatched through this function without any authorization check tying the caller's identity/session to the `kc_user`/`kc_service` pair it is requesting: [2](#0-1) 

The only gate applied is whether the *targeted* keychain (not the caller) is unlocked: [3](#0-2) 

Since the daemon's keychain backend partitions private-key storage by `user`/`service` strings (each OS-level login/service getting its own logical keychain), and the daemon dispatches keychain commands to whichever `Keychain(user=…, service=…)` the request names, any client that can open a daemon websocket connection and issue a `get_key`/`get_keys`/`get_all_private_keys` command with a *different* `kc_user`/`kc_service` value than its own can read private key material (mnemonic entropy, per `get_all_private_keys`) belonging to another local partition, as long as that other keychain happens to be unlocked at the time. This mirrors the GitLab bug class: the intended access boundary (each service/user should only reach its own keychain) is enforced only by which namespace string is provided in the request, not by verifying the caller's actual identity/session — i.e., the equivalent of GitLab's "forced browsing" into another project's report by supplying a different identifier.

Confirming that private-key material, not just public data, is exposed via this path: [4](#0-3) [5](#0-4) 

### Impact Explanation
If exploited, this allows a local RPC/daemon caller (who is authorized to talk to the daemon, e.g., any local service or GUI client holding the private daemon TLS cert, but who is not the owner of a different `kc_user`/`kc_service` namespace) to enumerate and extract mnemonic entropy and derive private keys belonging to another local user/service's wallet. That directly yields unauthorized spend authority over another user's coins on a shared machine/daemon deployment — a leaked-key-equivalent outcome reached purely through parameter manipulation of an already-permitted RPC call, not through any separately privileged access.

### Likelihood Explanation
Exploitation requires only the ability to open a connection to the local daemon websocket and send a `get_key`/`get_all_private_keys` command with an alternate `kc_user`/`kc_service` value — no additional secrets, no knowledge of the target's passphrase, and no cryptographic breakage. Any process on the machine already permitted to talk to the daemon (which is the normal access model for wallet/farmer/plotter clients) can attempt this cross-namespace read. The main mitigating factor is that this requires a multi-user/multi-keychain-namespace deployment on the same daemon and that the target namespace's keyring be unlocked, which the code review here could not fully verify is a common real-world daemon configuration.

### Recommendation
Bind the keychain namespace to the authenticated connection/service registration rather than trusting client-supplied `kc_user`/`kc_service` fields; if multiple namespaces must be supported, require that the caller's own authenticated identity match the requested namespace, or restrict `kc_user`/`kc_service` overrides to an explicit, cert-verified admin channel.

### Proof of Concept
Conceptual PoC (not fully verified against production configuration, since determining whether a specific real deployment runs multiple `kc_user`/`kc_service` keychains on one daemon requires runtime access this review could not exercise):
1. Attacker process, holding the standard daemon client certificate used by any local Chia service, connects to the local daemon websocket.
2. It sends `{"command": "get_all_private_keys", "data": {"kc_user": "<victim_user>", "kc_service": "<victim_service>"}, "destination": "daemon"}`.
3. `get_keychain_for_request()` resolves this to the victim's `Keychain` instance and, if unlocked, `KeychainServer.get_all_private_keys()` returns the victim's mnemonic entropy for every stored key, as shown in [4](#0-3) , letting the attacker reconstruct the victim's private keys and spend their coins.

    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

    async def get_all_private_keys(self, request: dict[str, Any]) -> dict[str, Any]:
        all_keys: list[dict[str, Any]] = []
        if self.get_keychain_for_request(request).is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private_keys = self.get_keychain_for_request(request).get_all_private_keys()
        for sk, entropy in private_keys:
            all_keys.append({"pk": bytes(sk.get_g1()).hex(), "entropy": entropy.hex()})

        return {"success": True, "private_keys": all_keys}
```
