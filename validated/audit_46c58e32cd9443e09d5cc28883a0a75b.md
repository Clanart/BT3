### Title
Missing digit-count validation in `TimeUtil::FromString` fraction-scaling `Pow()` allows integer corruption in `Duration` parsing - ([File: src/google/protobuf/util/time_util.cc])

### Summary
`google::protobuf::util::TimeUtil::FromString(absl::string_view, Duration*)` scales the fractional-seconds substring by a locally defined helper `static int64_t Pow(int64_t x, int y)` that has no overflow/negative-exponent protection, exactly analogous to the Sway `pow()` bug: an attacker-controlled magnitude (`nanos_part.length()`) is fed into an unguarded exponent calculation, and the resulting corrupted value is silently accepted rather than rejected.

### Finding Description
`TimeUtil::FromString` for `Duration` extracts `nanos_part` as the substring after `.` and before the trailing `s` directly from the untrusted input string, with no length check: [1](#0-0) 

The scaling helper: [2](#0-1) 

`Pow(10, y)` is called with `y = 9 - nanos_part.length()`. If an attacker supplies more than 9 fractional digits (e.g. `"0.1234567890123s"`), `y` becomes **negative**. Because the loop condition is `i < y`, a negative `y` causes the loop to never execute, so `Pow` returns `1` instead of failing or clamping — the "overflow protection" that exists for the normal case (`y >= 0`, where the loop can already silently wrap on `int64_t` multiplication overflow for large `x`/`y`, since `result *= x` has no overflow check either) is completely bypassed for the more dangerous negative-exponent case. The raw, unscaled (and already `strtoll`-parsed, oversized) `nanos` value is then narrowed with `static_cast<int32_t>(nanos)` before being stored: [3](#0-2) 

This mirrors the Sway `pow()` invariant failure precisely: (1) an attacker-controlled input value (digit-string length / magnitude) drives an arithmetic function, (2) the function has no bounds/overflow check for out-of-range exponents, (3) the miscomputed result is silently truncated/narrowed to a smaller type (`u8`/`u32` in Sway, `int32_t` here) rather than rejected, and (4) the corrupted value is used to populate a value (coin amount in Sway; `Duration.nanos` here) that downstream logic treats as valid. The final `IsDurationValid()` check operates only on the **already-truncated** `nanos` value, so it cannot detect that the original computed value was out of range — the same "post-corruption validation is too late" failure pattern as the Sway PoC where `result_u8 > u8::max()` is checked only after the wraparound already occurred.

By contrast, the modern ProtoJSON binary/JSON parsers used for public wire/JSON parsing (`upb/json/decode.c: jsondec_nanos`, `src/google/protobuf/json/internal/parser.cc: ParseDuration`/`TakeNanosAndAdvance`) explicitly reject `digits > 9` before scaling: [4](#0-3) 
This confirms the invariant ("fractional digits must be ≤ 9, else reject") is the correct fix, and that `TimeUtil::FromString`'s C++ well-known-types helper independently reimplements the same parsing task without that guard.

### Impact Explanation
`google::protobuf::util::TimeUtil::FromString` is a public, documented API (`time_util.h`) intended for parsing RFC3339/Duration text directly supplied by applications (e.g. from user input, config, or untrusted RPC payloads that embed a duration string outside the ProtoJSON WKT codec). A crafted string with >9 fractional digits produces a `Duration.nanos` value derived from silent `int64_t`→`int32_t` truncation of an unscaled magnitude, which can differ arbitrarily (including sign) from the value the input text represents. If application logic uses this `Duration` for billing, rate limiting, timeouts, or similar business logic, this is a data-integrity/logic-corruption issue — the parsed value is wrong but not flagged as invalid, since validation runs post-truncation. This does not cause memory corruption or crash by itself (bounded to a well-defined narrowing conversion), so it is best characterized as a **Medium** severity logic/integrity issue rather than memory safety, but it is a real production analog of the reported bug class (no overflow guard on an arithmetic scaling function acting on attacker-controlled magnitude, silently truncated instead of rejected).

### Likelihood Explanation
Likelihood is moderate: the vulnerable path is only reached via the direct C++ `TimeUtil::FromString(str, Duration*)` API when applications choose to parse duration strings themselves rather than through the JSON/ProtoJSON codec (which does perform the `digits > 9` check). Any application that exposes duration text to end users and forwards it to `TimeUtil::FromString` is exposed. It requires no privileged access — an ordinary bounded string (`"0." + N digits + "s"`) is sufficient to trigger the negative-exponent path.

### Recommendation
Add an explicit bound check in `TimeUtil::FromString(absl::string_view, Duration*)` rejecting `nanos_part.length() > 9` before calling `Pow`, mirroring the guard already present in `upb/json/decode.c: jsondec_nanos` and `src/google/protobuf/json/internal/parser.cc`. Additionally, harden the local `Pow` helper to reject/clamp negative exponents and detect `int64_t` multiplication overflow (e.g. via `absl::CheckedMul` or `__builtin_mul_overflow`), consistent with the general overflow-checking pattern used elsewhere in the codebase, e.g. `upb/port/overflow.h`.

### Proof of Concept
Given the trusted `Duration` schema and the public `TimeUtil::FromString` API:
```cpp
google::protobuf::Duration d;
bool ok = google::protobuf::util::TimeUtil::FromString("0.1234567890123s", &d);
// ok == true (should be rejected: 13 fractional digits > 9 allowed)
// nanos_part = "1234567890123" (13 digits)
// y = 9 - 13 = -4  -> Pow(10, -4) loop `for (i=0;i<-4;...)` never runs -> returns 1
// nanos = strtoll("1234567890123") * 1 = 1234567890123 (int64_t)
// static_cast<int32_t>(1234567890123) truncates to an arbitrary 32-bit value
//   unrelated to the intended fractional value, e.g. 1912276617 on typical two's-complement narrowing
// d.nanos() now holds this corrupted, silently-accepted value if it happens to
// fall within [-999999999, 999999999] after truncation, or is rejected only
// by coincidence otherwise -- IsDurationValid() cannot recover the true value.
```

static int jsondec_nanos(jsondec* d, const char** ptr, const char* end) {
  uint64_t nanos = 0;
  const char* p = *ptr;

  if (p != end && *p == '.') {
    const char* nano_end = jsondec_buftouint64(d, p + 1, end, &nanos);
    int digits = (int)(nano_end - p - 1);
    int exp_lg10 = 9 - digits;
    if (digits > 9) {
      jsondec_err(d, "Too many digits for partial seconds");
    }
    while (exp_lg10--) nanos *= 10;
    *ptr = nano_end;
  }

  UPB_ASSERT(nanos < INT_MAX);

  return (int)nanos;
}
