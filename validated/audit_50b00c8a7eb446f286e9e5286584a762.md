## Unsafe low-level ERC20 transfer checks don't verify return data in `IntentGatewayV2.sol` (Tron) — silent transfer failures cause escrow accounting to advance without funds moving

### Title
Escrow `withdraw()`/dust-sweep use `.call` + success-only checks instead of `SafeERC20`, letting non-reverting `transfer()` failures mark escrow as paid while funds stay locked - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and declares `using SafeERC20 for IERC20;` [1](#0-0)  but its escrow-release and dust-sweep paths bypass `SafeERC20` entirely and instead perform raw low-level calls, checking only that the call itself did not revert — never decoding/validating the returned boolean: [2](#0-1) 

This is the exact bug class in the referenced report: relying on `IERC20.transfer`/`transferFrom` semantics that assume revert-on-failure, when many real ERC20s (including some deployed on TRON/EVM-compatible chains) return `false` on failure instead of reverting.

### Finding Description
In `withdraw()`, the internal function that releases escrowed order funds to a beneficiary (used both for successful fills and for refunds on timeout), the contract:
1. Sets `_filled[body.commitment] = beneficiary` **before** attempting any transfer [3](#0-2) .
2. For each escrowed token, performs `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks `success` (i.e., that the low-level call did not revert) — it never inspects the ABI-decoded boolean return value [4](#0-3) .
3. Regardless of whether the token actually moved value, it unconditionally decrements the escrow accounting: `_orders[body.commitment][token] -= amount;` [5](#0-4) .
4. It emits `EscrowReleased`/`EscrowRefunded` as if settlement succeeded [6](#0-5) .

The same unsafe pattern appears in the dust-sweep path, which also uses `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and checks only `success` [7](#0-6) .

For an ERC20 that returns `false` instead of reverting on a failed transfer (e.g. due to a blacklist, paused state, or non-standard implementation), `success` will be `true` (the low-level call itself did not throw), so the code proceeds as though the transfer succeeded: `_filled` is set, escrow accounting is decremented, and events are emitted — but the beneficiary never actually received the tokens. Because `_orders[body.commitment][token]` reaches zero and `_filled[body.commitment]` is already populated, there is no remaining code path to re-attempt or reclaim that transfer: the tokens become permanently stuck in the contract while the protocol's internal state says the order was settled.

This directly parallels the referenced Sherlock finding (`FeeBuyback.sol` using raw `IERC20.transfer`/`transferFrom` instead of `SafeERC20`, causing reverts/silent failures for non-conforming tokens), except here the effect is worse: instead of reverting the whole transaction (fail-safe), the contract's `.call`+`success`-only check makes it fail silently and finalize accounting anyway (fail-unsafe), resulting in fund loss for the legitimate beneficiary (solver on fill, or user on refund).

### Impact Explanation
This is a direct loss-of-funds bug reachable via the normal, unprivileged `onGetResponse`/withdraw flow that any user or solver relies on to receive their escrowed tokens or refunds. If the escrowed/output token has any non-standard `transfer` behavior (returns `false` rather than reverting on failure — a known "weird ERC20" pattern), the beneficiary permanently loses the funds while the contract's bookkeeping (`_orders`, `_filled`) reflects a completed settlement, with no recovery path. This matches the required impact category of "stealing or loss of funds" through normal-looking transaction flow with no reliance on a malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood depends on which ERC20 tokens are actually configured as intent input/output/fee tokens for the Tron deployment; if any token in use can return `false` on failure (rather than always reverting) under conditions like temporary pausing, blacklist, or insufficient balance in edge cases, the bug triggers deterministically on that transfer, with no attacker action needed beyond the fill/refund the protocol already expects.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the dust-sweep function with `IERC20(token).safeTransfer(beneficiary, amount)` from the already-imported `SafeERC20` library (already used elsewhere via `using SafeERC20 for IERC20;`), and only update `_filled`/`_orders` state after the safe transfer succeeds (or accept that `safeTransfer` will revert on failure, preventing state from being finalized).

### Proof of Concept
1. Configure (or have solvers/users use) an order whose output/escrowed token is an ERC20 that returns `false` on a failed `transfer` (e.g. a blacklist-style token) instead of reverting.
2. Trigger a refund via timeout (`onGetResponse` → `withdraw(body, true)`) or a normal escrow release, where the beneficiary is temporarily unable to receive the token (e.g. blacklisted).
3. In `withdraw()`, `token.call(...)` returns `success = true` (the call itself doesn't revert) even though the token's internal logic returned `false` and did not move balance [8](#0-7) .
4. `_orders[body.commitment][token] -= amount` executes, `_filled[body.commitment]` is already set, and `EscrowRefunded`/`EscrowReleased` fires — the order is now considered fully settled by the contract, but the beneficiary's balance never increased.
5. There is no remaining function that allows the beneficiary to reclaim the now-orphaned escrow, since `_orders[...]` was already zeroed and `_filled` marks the commitment consumed.
