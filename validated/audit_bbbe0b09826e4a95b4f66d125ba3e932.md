### Title
Unbounded buffer indexing in CLVM-canonical-serialization check can raise an unhandled `IndexError` on a crafted spend bundle - ([File: chia/full_node/mempool_manager.py])

### Summary
`is_clvm_canonical()` / `is_atom_canonical()` in `chia/full_node/mempool_manager.py` parse the raw CLVM byte serialization of a spend bundle's generator/puzzle-reveal to determine whether the encoding uses the canonical (shortest) atom-length prefix. Both functions trust the attacker-supplied length-prefix bytes and advance a byte offset based on them without first checking that the offset stays within `len(clvm_buffer)`, unlike the sibling parsing helpers elsewhere in the codebase (e.g. `chia/full_node/full_block_utils.py`) that explicitly bounds-check every length field before use.

### Finding Description
`is_atom_canonical()` reads the atom's leading byte, decides a `prefix_len` (0–5) based on the high bits, and then loops `prefix_len` times doing: [1](#0-0) 
On each iteration it does `offset += 1; atom_len |= clvm_buffer[offset]` with no check that `offset < len(clvm_buffer)`. If the buffer is truncated right after a multi-byte length-prefix marker (e.g. `0xFC`, `0xF8`, `0xF0`, `0xE0`, `0xC0` at the very end of the buffer), indexing `clvm_buffer[offset]` beyond the buffer's length raises an unhandled `IndexError`.

The caller, `is_clvm_canonical()`, compounds this: after computing `atom_len` (which is fully attacker controlled and can be declared arbitrarily large while the actual buffer is short), it does `offset += atom_len` and loops back to `b = clvm_buffer[offset]`: [2](#0-1) 
Because `offset` can now be far past `len(clvm_buffer)`, this second indexing also raises `IndexError` — the only bounds check in the whole routine is the final `return offset == len(clvm_buffer)`, which is never reached in these truncated/oversized cases. This mirrors the underlying bug class of CVE-2017-3599 (an integer-length-driven overflow/under-check in packet parsing that leads to a crash rather than a caught error), except here the "packet" is the CLVM-serialized generator/puzzle bytes carried inside a spend bundle rather than an authentication packet.

### Impact Explanation
If this code path is reached with a raw, unauthenticated-input CLVM buffer taken from a spend bundle submitted via the wallet RPC or peer `NewTransaction`/`RespondTransaction` protocol, an attacker who crafts a spend bundle whose generator bytes end with a dangling multi-byte atom-length marker (or an atom-length field claiming a length far larger than the remaining buffer) can trigger an unhandled `IndexError` inside mempool processing. Depending on whether the call site wraps this helper in a broad exception handler, this can crash the mempool manager task/worker process, causing a denial of service for that full node — a spend-triggered transaction-processing halt, which matches the "Accept" criteria for this analog category.

### Likelihood Explanation
The check operates directly on the un-validated CLVM byte layout of spend-bundle content, which is exactly the kind of data any unprivileged spend-bundle submitter (wallet user or mempool peer) fully controls. Constructing a buffer with a truncated multi-byte atom header is a simple, deterministic, single-attempt operation requiring no race condition or privileged access, making exploitation straightforward if this function is on the mempool-admission path for untrusted input.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before every `clvm_buffer[offset]` access (verifying `offset < len(clvm_buffer)` for each of the `prefix_len` reads) and in `is_clvm_canonical()` before dereferencing `clvm_buffer[offset]` after advancing by `atom_len`, returning `False` (not raising) whenever the buffer is exhausted early — consistent with the pattern already used in `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list` helpers, which raise well-defined `ValueError`s only after explicit remaining-length checks rather than allowing raw `IndexError`s to propagate.

### Proof of Concept
Conceptually: submit a spend bundle whose serialized generator/puzzle bytes are `b"\xfc"` (a 5-byte-length-prefix marker) with no trailing bytes, or `b"\xc0\xff"` claiming length `0xff` while the buffer contains only 2 bytes total, then invoke `is_clvm_canonical()` on that buffer — the function raises `IndexError` instead of returning `False`, because neither `is_atom_canonical` nor `is_clvm_canonical` checks `offset` against `len(clvm_buffer)` before indexing.

I was not able to fully confirm the exact call site(s) that feed unauthenticated/untrusted spend-bundle bytes into `is_clvm_canonical()` (e.g. whether it's always applied after `SerializedProgram.from_bytes()` has already validated the buffer structure, which could make an out-of-bounds atom header unreachable in practice, or whether a broad `try/except` around mempool admission would swallow the resulting `IndexError` before it can crash a worker). Confirming this requires tracing every caller of `is_clvm_canonical`/`is_atom_canonical` in `chia/full_node/mempool_manager.py` and its surrounding exception handling, which the available index snippets did not fully expose.
