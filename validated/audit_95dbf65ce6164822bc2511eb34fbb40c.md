### Title
OP_RETURN data is excluded from transaction weight and fee calculations - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts caller-provided `data` and adds it to the signed transaction as an `OP_RETURN` output, but calculates both the required fee and maximum transaction weight using only the inputs, payments, and optional change output. The resulting transaction can therefore commit to a fee below the caller-specified sat/vbyte rate and below Bitcoin's minimum relay fee.

### Finding Description
The `data` argument is converted into a zero-valued `OP_RETURN` output and appended to `tx_outs` before fee estimation. [1](#0-0)  However, `calculate_weight_vbytes` is invoked with only `tx_ins.len()`, `payments`, and `None`, without passing the constructed data output. [2](#0-1) 

The estimation function itself builds the weight only from the provided payments and optional change output; it has no parameter representing `data`. [3](#0-2)  The change-aware recalculation has the same omission because it also receives only the inputs, payments, and change script. [4](#0-3)  The final transaction nevertheless contains the additional `OP_RETURN` output, and the signature commits to that enlarged transaction. [5](#0-4) [6](#0-5) 

### Impact Explanation
A transaction constructed with up to 80 bytes of public `data` is larger than the transaction used for fee estimation, so `needed_fee` is too low. [7](#0-6)  The minimum-relay check is also performed against the underestimated `vbytes`, allowing a transaction that passes `TooLowFee` internally while paying less than one sat/vbyte on-chain. [2](#0-1) 

The resulting transaction is validly signed but can be rejected by standard Bitcoin relay policy and remain unpublished. Because signatures commit to the complete transaction, including the omitted-from-estimation output, the signed transaction cannot be repaired by merely increasing its fee without producing new signatures. This can delay or prevent spending of the selected UTXOs and make the exposed `needed_fee`/`fee` contract inaccurate. [8](#0-7) 

### Likelihood Explanation
Any caller able to cause a `SignableTransaction` to be produced with attacker-controlled `data` can trigger the discrepancy. The public constructor explicitly supports `data` of up to 80 bytes, and the incorrect calculation is deterministic rather than dependent on validator misbehavior, private state, or malformed encodings. [9](#0-8) [7](#0-6) 

The issue is most readily reached when no change output is created or when input selection leaves little excess value, because the difference between estimated and actual transaction size is then directly reflected in the effective fee rate. If substantial excess input value is burned as fee anyway, the transaction may still satisfy relay policy despite `needed_fee` being understated.

### Recommendation
Pass the complete output set—including the zero-valued `OP_RETURN` output—to the transaction-weight estimator. `calculate_weight_vbytes` should accept the final `tx_outs` shape, or a separate data-output parameter, for both the initial estimate and the change-aware estimate. Recompute the minimum relay threshold and maximum-standard-weight check from the same output set that will actually be signed.

### Proof of Concept
1. Construct a transaction with one spendable input, one ordinary payment of `DUST`, `data = vec![0; 80]`, no change output, and `fee_per_vbyte = 1`.
2. `SignableTransaction::new` appends an approximately 92-byte serialized `OP_RETURN` output to `tx_outs`. [10](#0-9) 
3. Fee estimation calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which excludes that `OP_RETURN` output. [11](#0-10) 
4. Choose `input_sat = DUST + estimated_vbytes`. The funding check succeeds because it compares `input_sat` only against `payment_sat + needed_fee`, where `needed_fee` is `estimated_vbytes`. [12](#0-11) 
5. The actual transaction retains the extra `OP_RETURN` output, so its true vsize is approximately `estimated_vbytes + 92`, while its fee remains `estimated_vbytes` sats. Its effective fee rate is therefore below the requested `1 sat/vbyte` and below the default minimum relay rate checked by the constructor. [5](#0-4)
