### Title
Unchecked KIP-71 `GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee`, crashing every node validating a block - (File: params/kip71_config.go)

### Summary
`params/kip71_config.go`'s `NextMagmaBlockBaseFee` explicitly guards against `BaseFeeDenominator == 0` ("To avoid panic, set the fluctuation range small") but performs **no equivalent guard for `GasTarget == 0`**. When `GasTarget` is 0 and any gas is used in the parent block, the function divides by a zero-valued `big.Int`, which panics in Go's `math/big` package. This is directly analogous to CVE-2023-46849, where an unchecked/unvalidated configuration parameter (`--fragment`) leads to an unguarded divide-by-zero causing a crash/DoS.

### Finding Description
In `NextMagmaBlockBaseFee`: [1](#0-0) 
`BaseFeeDenominator` is defensively checked and defaulted to 64 if zero. However `gasTarget := kc.GasTarget` at line 77 has no such protection: [2](#0-1) [3](#0-2) 

If `gasTarget == 0` and `parentGasUsed > 0` (i.e. `parentGasUsed > gasTarget`), execution reaches `x.Div(x, new(big.Int).SetUint64(gasTarget))` with divisor `0`, which panics (Go's `big.Int.Div` panics on division by zero, unlike a silent return like float division).

The root cause is that the `Kip71GasTarget` governance parameter has no format validation preventing zero, unlike its sibling `Kip71BaseFeeDenominator`, which explicitly rejects zero: [4](#0-3) 
`Kip71GasTarget` uses `noopFormatChecker`, so a governance vote/parameter update setting `GasTarget = 0` will be accepted into the `ParamSet` and subsequently flow into `KIP71Config` via `ToKip71Config()`: [5](#0-4) 

This `KIP71Config` (derived from the governance parameter set for the relevant block) is used both to compute the expected base fee for block building and to **verify** the base fee of every incoming block header (`VerifyMagmaHeader` calls `NextMagmaBlockBaseFee`). Since header/base-fee verification runs on every full node for every block after the Magma fork, a `GasTarget = 0` governance state causes **all nodes** (not just the proposer) to panic during block validation as soon as a block with nonzero gas usage is produced — a full network liveness/availability failure, not merely a single node crash.

### Impact Explanation
This is a Denial-of-Service vulnerability affecting availability of the entire network, matching the impact profile of the referenced CVE (CVSS 3.1: C:N/I:N/A:H). Because `NextMagmaBlockBaseFee` is invoked from block validation logic (`blockchain/block_validator.go`), transaction pool gas-price computations (`blockchain/tx_pool.go`), block building (`work/worker.go`), and fee-history/gas-price-oracle RPC paths (`node/cn/gasprice/*.go`), a single misconfigured/zero `GasTarget` governance value halts consensus-critical processing across the fleet of nodes simultaneously — every node attempting to compute or verify the next base fee panics.

### Likelihood Explanation
Reaching this state requires a governance parameter change setting `Kip71GasTarget` to `0`. This is not directly reachable from an ordinary unprivileged transaction sender's transaction content; it requires that a governance-parameter-set transaction (in "single" governance mode, by the governing node, or via DAO-mode voting) sets this value. The code accepts the value without validation, so the vulnerability is latent and would trigger as soon as governance approves (intentionally or by mistake) a `GasTarget` of `0` and any subsequent block uses gas. This significantly weakens confidence that it is reachable by a fully unprivileged actor in the strict sense requested (single tx/bid/RPC from any address) — it depends on the governance/voting path, which the "Rules" section also generally treats with caution ("operator-only" paths are excluded). I flag this uncertainty explicitly: I could not verify within the available tools whether the governance-parameter-set/vote submission itself can be triggered by a fully unprivileged address in any governance mode, or whether it is strictly gated to the governing/validator node. This is the key open question for confirming full reachability from an unprivileged actor.

### Recommendation
Add an explicit `GasTarget != 0` (and ideally `GasTarget <= MaxBlockGasUsedForBaseFee`) format check to the `Kip71GasTarget` parameter definition in `kaiax/gov/param.go`, mirroring the existing `Kip71BaseFeeDenominator` check. Additionally, harden `NextMagmaBlockBaseFee` in `params/kip71_config.go` with the same defensive default used for `baseFeeDenominator` (e.g., substitute a safe non-zero fallback, or early-return the current/lower-bound base fee) whenever `kc.GasTarget == 0`, so that malformed or historically-persisted zero values cannot cause a runtime panic during consensus-critical header verification.

### Proof of Concept
Given the existing test harness in `params/kip71_config_test.go`, the panic can be reproduced by constructing a `KIP71Config{GasTarget: 0, BaseFeeDenominator: 20, LowerBoundBaseFee: 25000000000, UpperBoundBaseFee: 750000000000, MaxBlockGasUsedForBaseFee: 60000000}` and calling:
```go
cfg.NextMagmaBlockBaseFee(common.Big3, big.NewInt(30000000000), /*parentGasUsed=*/ 1)
```
Since `parentGasUsed(1) > gasTarget(0)`, execution reaches `x.Div(x, new(big.Int).SetUint64(0))`, which panics with `division by zero`, crashing the calling goroutine (block validator / worker / gas price oracle) on every node that processes this configuration and any block with `GasUsed > 0`.
