## Analysis

The external report's core broken invariant: **treating a low-level ERC20 call as successful based only on the call not reverting, without verifying the actual boolean return value of `transfer`/`transferFrom`.** Weird-ERC20 tokens (paused, blacklist-gated, non-compliant) can return `false` instead of reverting on failure, so code that checks only `success` (call didn't revert) rather than decoding `success` will silently accept a failed transfer as successful.

I found this exact pattern reproduced in the escrow-redemption path of `IntentGatewayV2.sol` (Tron variant), even though the same file correctly uses `SafeERC20.safeTransferFrom` for inbound token pulls. The outbound escrow-release path (`withdraw`) and the admin `SweepDust` handling use raw `.call` with a manually encoded `transfer` selector, checking only that the call itself succeeded — not that the token actually reports a truthy return value. Compare with `placeOrder`, which correctly uses `safeTransferFrom` (via `SafeERC20`) for inbound escrow funding: [3](#0-2)  — confirming the developers are aware of the weird-ERC20 risk and mitigate it on the inbound path, but not on the outbound `withdraw`/`SweepDust` path.

### Title
Escrow redemption in `IntentGatewayV2.sol` (Tron) accepts failed ERC20 transfers as successful, finalizing settlement without delivering funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed order tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level call did not revert (`success`), never decoding/validating the ERC20 boolean return value. For any input/output token used in an order that is a non-standard ERC20 returning `false` on failure instead of reverting, the contract will mark the order as filled/refunded and decrement escrow accounting even though the beneficiary never received the tokens.

### Finding Description
`withdraw()` is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` request kinds after `authenticate()` on the incoming cross-chain message: [4](#0-3) . Inside `withdraw`, escrowed tokens are transferred with: [5](#0-4) 
and unconditionally, regardless of whether the underlying `transfer` actually moved value, `_filled[body.commitment] = beneficiary` is set before the loop and `_orders[body.commitment][token] -= amount` is decremented inside it, followed by `emit EscrowReleased(...)`. `success` here reflects only that the target contract did not revert; a token contract that implements `transfer` to `return false` (rather than revert) on a failed transfer — e.g. paused state, blacklist, insufficient allowance edge-case, or a token deliberately crafted by the order creator/solver — will pass this check.

The same unchecked pattern exists in the `SweepDust` handler: [6](#0-5) .

Because order tokens (`order.inputs`, `order.output.assets`) are arbitrary attacker-supplied addresses chosen by the order creator when calling `placeOrder`, an order creator can pick a token whose `transfer` function returns `false` under conditions they control (e.g., a custom token that returns `false` once a certain balance/flag state is met, without reverting). When a solver later fills the order cross-chain and the redemption request comes back to `withdraw()`, the escrow "release" to the solver's beneficiary address silently fails while the contract's internal accounting and finality state (`_filled`, `_orders[...] -= amount`, `EscrowReleased` event) proceed as if the payout succeeded.

### Impact Explanation
This is a false-state-acceptance / fund-loss bug in the intent settlement path: the protocol finalizes settlement (`_filled` set, escrow decremented, event emitted) for a transfer that never actually happened. The rightful beneficiary (solver filling an order, or a user being refunded via `RefundEscrow`) permanently loses the expected payout, while the token remains stuck in the `IntentGatewayV2` contract's balance with no accounting path pointing back to it (the escrow ledger for that commitment/token has already been zeroed/decremented). This matches the bounty's "stealing or loss of funds" and "false proof/state acceptance" impact categories directly in the cross-chain intent/escrow settlement flow.

### Likelihood Explanation
The order creator fully controls which ERC20 token address is used for `order.inputs`/`order.output.assets` in `placeOrder` — no allowlist is enforced in the escrow/withdraw path shown. Since `safeTransferFrom` is already used elsewhere in the very same file for inbound transfers, this indicates awareness of the ERC20 weirdness risk, but the outbound `withdraw`/`SweepDust` path was not updated to match, making this a straightforward, unprivileged, single-transaction trigger: place an order with a crafted token, let it get filled, and the redemption path silently loses funds.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, which is already imported and used (`using SafeERC20 for IERC20;`) elsewhere in the same contract, ensuring both call-success and boolean-return-value are validated before finalizing escrow/settlement state.

### Proof of Concept
1. Order creator deploys a custom ERC20 `token` whose `transfer` function returns `false` (without reverting) whenever called by the `IntentGatewayV2` contract address under a condition the creator controls (e.g., a toggle they flip after the order is placed, or a balance threshold).
2. Order creator calls `placeOrder` using `token` as an input asset; tokens are pulled in via `safeTransferFrom` (succeeds normally) and escrowed under `_orders[commitment][token]`.
3. A solver fills the order on the destination chain; a `RedeemEscrow` request is dispatched back to the source chain.
4. Before/at the time `onAccept` processes `RedeemEscrow`, the creator flips the token's internal condition so `transfer` returns `false`.
5. `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; the call itself does not revert (`success == true`) even though no tokens moved.
6. `_filled[commitment]` is set, `_orders[commitment][token]` is decremented to zero, and `EscrowReleased` is emitted — the solver's beneficiary balance is unchanged, but the protocol considers the order fully and successfully settled, with no remaining accounting path to recover the tokens for the solver.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
