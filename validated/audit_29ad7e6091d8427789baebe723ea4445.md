## Finding: Unbounded recursive puzzle-layer matching on attacker-controlled offer/spend data causes wallet-side resource exhaustion

### Title
Unbounded recursion in wallet outer-puzzle "also" chain matching allows an offer counterparty to trigger CPU/stack exhaustion - (File: `chia/wallet/outer_puzzles.py`)

### Summary
The reported Undici bug class is "an attacker-controlled chain of transformations that is processed without any depth/length bound, driving unbounded CPU/memory work." The reachable analog in this codebase is the wallet's outer-puzzle driver system (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`), which recursively "also"-chains through an attacker-supplied `puzzle_reveal` with **no depth limit and no CLVM cost accounting**, unlike normal puzzle execution.

### Finding Description
`match_puzzle()` in `chia/wallet/outer_puzzles.py` iterates over `driver_lookup` and calls each driver's `.match()`. Every driver (`CATOuterPuzzle.match`, `SingletonOuterPuzzle.match`, `MetadataOuterPuzzle.match`, `OwnershipOuterPuzzle.match`, `CROuterPuzzle.match`) recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` on the puzzle's inner layer and stores the result under `also`, forming an unbounded recursive "layer chain": [1](#0-0) [2](#0-1) 

This recursion is driven purely by how many times a puzzle is curried inside another matching outer-puzzle type (e.g. CAT-in-CAT, singleton-in-singleton, metadata-in-metadata), which the test suite explicitly demonstrates is a supported/legal nesting pattern: [3](#0-2) 

Each layer also triggers `UnknownPuzzle.mod`/`.curried_args`, which perform a CLVM `uncurry()` call via `uncurry_puzzle()`: [4](#0-3) [5](#0-4) 

Unlike condition/CLVM execution in the mempool (which is bounded by `max_tx_clvm_cost`, atom/pair caps, and a >2s validation duration guard — see `chia/full_node/mempool_manager.py:530-598,814-845`), this puzzle-matching recursion runs in **pure Python on the wallet side**, with no cost metering and no depth cap. It is triggered when a wallet inspects an `Offer`'s `puzzle_reveal`s to identify offered coins, via `Offer._get_offered_coins()` calling `match_puzzle(parent_puzzle)` for every coin spend in the bundle: [6](#0-5) 

`Offer` objects are attacker-controlled data received directly from an untrusted offer counterparty (e.g. via `trade_manager.respond_to_offer` / `check_for_final_modifications` / offer file parsing), and are also consulted from `TradeManager.calculate_tx_records_for_offer`.

### Impact Explanation
An offer counterparty can craft a `puzzle_reveal` with tens of thousands of nested matching outer-puzzle layers (e.g., CAT wrapped inside CAT, or singleton wrapped inside singleton via NFT-style layering) at negligible construction cost (each `curry()` call is cheap and does not need to be executed via CLVM to build the reveal). When the victim wallet processes this offer (to display, validate, or respond to it), `match_puzzle`/`also()` recurse once per layer with no bound, causing:
- Excessive CPU consumption processing the layer chain, and/or
- A Python `RecursionError` (stack exhaustion) once the recursion exceeds the interpreter's recursion limit,

halting or significantly degrading the wallet's transaction-processing/offer-handling path. This is a wallet-side denial-of-service condition triggered purely by receiving/handling an untrusted offer, matching the "spend/offer-triggered transaction-processing halt" impact class analogous to the Undici unbounded-decompression-chain resource exhaustion.

### Likelihood Explanation
Likelihood is moderate-to-high: constructing a deeply nested, self-consistent curried puzzle reveal that repeatedly matches a driver's `match()` predicate (e.g., stacking `CAT_MOD` curries, or `SINGLETON_TOP_LAYER_MOD` curries) is straightforward with the existing puzzle-construction helpers already used in tests (`construct_cat_puzzle`, `puzzle_for_singleton`, etc.), and no validation step in the offer-acceptance flow bounds the "also"-chain depth before invoking `match_puzzle`.

### Recommendation
Add an explicit maximum recursion/nesting depth (and/or an iterative implementation with an explicit stack and depth counter) to `match_puzzle` and each outer-puzzle driver's `match`/`get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` methods in `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/singleton_outer_puzzle.py`, `chia/wallet/nft_wallet/metadata_outer_puzzle.py`, `chia/wallet/nft_wallet/ownership_outer_puzzle.py`, and `chia/wallet/vc_wallet/cr_outer_puzzle.py`. Reject or safely bail out (returning `None`/raising a handled error) once a sane depth limit (e.g., matching the maximum realistically-used puzzle nesting, such as 10) is exceeded, before further attempting to process an untrusted `Offer`'s `puzzle_reveal`s.

### Proof of Concept
1. Build a puzzle `P0 = ACS` (accept-any-conditions puzzle).
2. Repeat N times (N = 50,000): `P_{i+1} = construct_cat_puzzle(CAT_MOD, tail_hash, P_i)` (or equivalently nest `puzzle_for_singleton`, chaining an arbitrary number of matching outer-puzzle layers), as already demonstrated feasible for two layers in [3](#0-2) .
3. Embed `P_N` as the `puzzle_reveal` of a `CoinSpend` inside a crafted `Offer`/`TradingOffer` sent to a victim.
4. When the victim wallet calls `Offer._get_offered_coins()` (or any code path invoking `match_puzzle`/`.also()` on this puzzle) as part of viewing, validating, or responding to the offer, the recursive `also`-chain in `chia/wallet/outer_puzzles.py` and the CAT/singleton/metadata/ownership/CR outer-puzzle drivers will recurse N times with no bound, exhausting CPU or hitting Python's recursion limit and halting offer processing.

    def uncurry(self) -> tuple[Program, Program]:
        def match(o: CLVMStorage, expected: bytes) -> None:
            if o.atom != expected:
                raise ValueError(f"expected: {expected.hex()}")

        try:
            # (2 (1 . <mod>) <args>)
            ev, quoted_inner, args_list = self.as_iter()
            match(ev, b"\x02")
            if TYPE_CHECKING:
                # this being False is presently handled in the TypeError exception handler below
                assert quoted_inner.pair is not None
            match(quoted_inner.pair[0], b"\x01")
            mod = quoted_inner.pair[1]
            args = []
            while args_list.pair is not None:
                # (4 (1 . <arg>) <rest>)
                cons, quoted_arg, rest = args_list.as_iter()
                match(cons, b"\x04")
                if TYPE_CHECKING:
                    # this being False is presently handled in the TypeError exception handler below
                    assert quoted_arg.pair is not None
                match(quoted_arg.pair[0], b"\x01")
                args.append(quoted_arg.pair[1])
                args_list = rest
            match(args_list, b"\x01")
            return Program.to(mod), Program.to(args)
        except ValueError:  # too many values to unpack
            # when unpacking as_iter()
            # or when a match() fails
            return self, self.to(0)
