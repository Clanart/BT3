### Title
Griefing/theft of queued bribe rewards via first-staker `donateRewards()` flush in `_provisionReward` - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`_provisionReward` in `BribeRewardPool`/`BaseRewardPoolV2` distributes rewards using `rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()`, and any rewards received while `totalStaked() == 0` are parked in `rewardInfo.queuedRewards` rather than distributed. An unprivileged attacker who becomes the first (and only) voter for a pool with 1 wei of vote weight can call the fully permissionless `donateRewards()` (even with `_amountReward = 0`) to flush all previously queued third-party bribe funds into `rewardPerTokenStored` using a denominator of 1 wei, capturing essentially 100% of that reward for themselves.

### Finding Description
`donateRewards` is external and unguarded except for the reward-token whitelist check, and forwards directly to `_provisionReward`: [1](#0-0) . Inside `_provisionReward`, when `totalStaked() == 0`, incoming rewards are queued instead of distributed; the queue is only flushed on the next call where `totalStaked() != 0`, at which point the entire queued amount is divided by the current (potentially tiny) `totalStaked()`: [2](#0-1) .

`BribeRewardPool.totalStaked()` returns `totalSupply`, which is only mutated via `stakeFor`/`withdrawFor`, callable only by the `onlyOperator` (the `WombatBribeManager`) when a vlMGP holder votes: [3](#0-2) . A holder of a trivial amount of locked vlMGP (obtainable by locking a dust amount of MGP) can permissionlessly cast the very first vote for a pool that currently has `totalSupply == 0` but already has queued bribe rewards (from a legitimate `queueNewRewards` call by a briber while nobody had voted yet). Because `stakeFor`'s `updateRewards` modifier snapshots the attacker's `userRewardPerTokenPaid` at the pre-inflation value (0) before `totalSupply` is incremented, the attacker's account is perfectly positioned to capture the full inflation.

The attacker then calls `donateRewards(0, _rewardToken)` (or any dust amount). Since `totalStaked()` is now 1 wei (nonzero), the branch flushes `rewardInfo.queuedRewards` (which may contain a large, real bribe balance from third-party callers of `queueNewRewards`) into `rewardPerTokenStored`, dividing by `totalStaked() == 1`. This produces a massive `rewardPerTokenStored` increase attributable almost entirely to the attacker's 1-wei balance. Because per-account reward accounting (`userRewardPerTokenPaid`) is captured at the time each user stakes, any depositor who joins *after* this flush is not retroactively diluted — they only accrue future deltas — so the "future depositor dilution" framing in the question is not accurate. However, the attacker does obtain a disproportionate, quantifiable claim on the previously **queued, real** reward balance that rightfully belonged to the pool's future voters (i.e., the reward that should have been shared among all voters once real staking began), by exploiting the trivial 1-wei denominator at the exact moment of first stake.

No modifier, minimum-share requirement, or virtual-offset protects `_provisionReward`'s share calculation, and `donateRewards` has no minimum amount or access restriction beyond the reward-token whitelist.

### Impact Explanation
This is theft of unclaimed yield: real bribe funds queued by third parties (or by `queueNewRewards`) are captured almost entirely by an attacker holding a negligible (1 wei) vote weight, at the expense of the legitimate voters who should have shared that reward once real voting began. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Preconditions: a pool must exist with `totalStaked() == 0` (no votes yet) and nonzero `rewardInfo.queuedRewards` (a briber/`queueNewRewards` already funded it before anyone voted) — a realistic state for newly-added or currently unpopular bribe pools. Capital required is minimal (dust vlMGP lock, gas, and possibly 0 tokens for the triggering `donateRewards` call). The attack is repeatable across any pool matching these preconditions and requires no special privileges — any EOA can lock a trivial amount of MGP and vote.

### Recommendation
Protect `_provisionReward`'s reward-per-token computation against tiny-denominator manipulation: enforce a minimum `totalStaked()` (or minimum vote weight) before allowing reward distribution/flush, use virtual/dead shares (as in ERC4626 inflation-attack mitigations), or require that `queuedRewards` only flush proportionally to genuine, matured stake rather than immediately upon the first nonzero `totalStaked()`.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatBribeManager`/`BribeRewardPool` for a pool with `totalStaked() == 0`.
2. Have a "briber" call `queueNewRewards(largeAmount, rewardToken)` while `totalStaked() == 0` — confirm it lands in `rewardInfo.queuedRewards`, not distributed.
3. Attacker locks a dust amount of MGP to get 1 wei of vlMGP, then calls `vote()` targeting the pool, causing `stakeFor(attacker, 1)` → `totalStaked() == 1`.
4. Attacker calls `donateRewards(0, rewardToken)` (or 1 wei) on the `BribeRewardPool`.
5. Assert `rewardInfo.rewardPerTokenStored` jumped by `largeAmount * 1e18 / 1`.
6. Assert `earned(attacker, rewardToken)` ≈ `largeAmount`, i.e., attacker can claim (via `getReward`) nearly the entire briber-funded reward pot despite holding only 1 wei of vote weight.
7. Have a legitimate voter subsequently vote a large amount and confirm their `earned()` only reflects rewards accrued after their entry, confirming the loss is concentrated as attacker-captured theft of the pre-existing queued reward rather than retroactive dilution of the new voter.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
