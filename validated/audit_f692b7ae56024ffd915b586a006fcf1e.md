## Title
Unchecked ERC20 `transfer` Return Value in Tron `IntentGatewayV2` Escrow Withdrawal — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds and swept dust using a raw low-level `.call()` to the ERC20 `transfer` selector, and only checks that the *call itself did not revert* — it never decodes/validates the boolean return value the ERC20 standard uses to signal transfer failure. Escrow accounting (`_orders[commitment][token]`) is decremented unconditionally as soon as the call does not revert, regardless of whether the token actually moved.

### Finding Description
In `withdraw()`, `IntentGatewayV2.sol` (Tron) releases escrowed tokens like this: [1](#0-0) 

and settles protocol fees the same way: [2](#0-1) 

The dust-sweeping path (`SweepDust` request kind, reachable via an authenticated cross-chain admin message but processed the same insecure way) has the identical pattern: [3](#0-2) 

In all three spots, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` returns `(bool success, bytes memory data)`. `success` only reflects whether the *external call reverted* — it is `true` even when the callee is a non-reverting, non-standard ERC20 that returns `false` in its ABI-encoded return data to signal a failed transfer (a known and common pattern on TRC20/ERC20-like tokens, especially in the Tron/TRC20 ecosystem this file specifically targets). The code never inspects the returned `bytes` to confirm the boolean is `true`. Compare this to the canonical, non-Tron `IntentGatewayV2`/`IntentsBase.sol` implementation, which uses OpenZeppelin's `SafeERC20.safeTransfer`, correctly reverting on a `false` return: [4](#0-3) 

Because the Tron file re-implements this transfer using a manual low-level call instead of `SafeERC20`, it reintroduces exactly the "unchecked return value" class from the seed report: a call whose success is misinterpreted because the return payload (the actual success/failure signal) is discarded.

### Impact Explanation
When `withdraw()` is invoked (from `fillOrder`/`_execute` flows or from `onGetResponse` refund flow) with an order input/output token that silently returns `false` on failure instead of reverting, the contract:
1. Decrements `_orders[body.commitment][token]` as if the beneficiary was paid.
2. Emits `EscrowReleased`/`EscrowRefunded` as if settlement succeeded.
3. Never actually delivers the tokens to the beneficiary.

This is a direct violation of the required invariant that "bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount" — here the escrow state is finalized (one-time, non-retryable, since the accounting is already zeroed and `UnknownOrder` would trip on any second attempt) while the actual asset movement silently fails, producing genuine fund loss for the beneficiary (solver or user, depending on flow) with no recovery path.

### Likelihood Explanation
This is reachable by any unprivileged actor who creates or fills an order using a token contract with this non-reverting-false-return behavior (a pattern common enough among ERC20/TRC20 tokens that OpenZeppelin's `SafeERC20` exists specifically to guard against it). No relayer, prover, or admin collusion is required — only an order using such a token, and the escrow release/refund/sweep flow executing normally through legitimate `fillOrder`/`onGetResponse`/host-authenticated cross-chain paths.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, matching the already-correct implementation in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both call-revert failures and ABI-encoded `false` returns cause the transaction (and therefore the escrow decrement) to revert together, keeping accounting and actual asset movement atomic.

### Proof of Concept
1. Deploy a minimal ERC20-like token whose `transfer` function returns `false` on failure (e.g., insufficient contract-held balance due to a rug/pause condition) instead of reverting.
2. Create an order in `IntentGatewayV2` (Tron) using this token as an input or output asset; escrow it normally via `fillOrder`.
3. Trigger the token's failure condition, then invoke the refund path (`onGetResponse` → `withdraw(body, true)`) or fill/settlement path so `withdraw()` executes.
4. Observe: `token.call(...)` returns `success = true` (call didn't revert) even though the encoded return data is `false`; `_orders[commitment][token]` is decremented and `EscrowRefunded`/`EscrowReleased` is emitted, but the beneficiary's token balance is unchanged — funds are permanently unrecoverable from escrow accounting's perspective.
