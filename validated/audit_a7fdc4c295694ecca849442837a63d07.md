## Analysis

The referenced Wenwin bug (rewards permanently lost because `rewardPerTokenStored` isn't updated while `totalSupply == 0`, so time/tickets that pass during that window are never credited to any staker) has a direct analog in `wombat/WomUp.sol`, which is a Synthetix-style reward-streaming "pool helper" that locks MGP for users staking WOM (converted to mWom). [1](#0-0) 

`rewardPerToken()` returns the stored value unchanged whenever `totalSupply() == 0`, but the `updateReward` modifier still advances `lastUpdateTime` to `lastTimeRewardApplicable()` on every state-changing call: [2](#0-1) 

Unlike `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder`, which explicitly queue undistributed rewards into `rewardInfo.queuedRewards` when `totalStaked() == 0` and replay them into the next distribution once stakers exist (mitigating exactly this class of bug), `WomUp.sol` has no such queuing mechanism: [3](#0-2) 

### Title
Streamed MGP rewards permanently lost in `WomUp` when `totalSupply() == 0` during the reward period - (File: `wombat/WomUp.sol`)

### Summary
`WomUp.stake`/`withdraw`/`migrate`/`getReward` all use the `updateReward` modifier, which advances `lastUpdateTime` to `lastTimeRewardApplicable()` regardless of whether `totalSupply()` is zero. Because `rewardPerToken()` simply returns the stale `rewardPerTokenStored` when `totalSupply() == 0` instead of accruing anything, any reward-rate-seconds that elapse while there are zero stakers are silently dropped and can never be recovered by any staker.

### Finding Description
`initializeRewards()` sets `rewardRate = balance/duration` and starts a 7-day streaming window (`periodFinish`), transferring the entire MGP reward balance into the contract up front. During that window, `rewardPerToken()` is computed as:
```
rewardPerTokenStored + (lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 / totalSupply()
```
but if `totalSupply() == 0` it just returns `rewardPerTokenStored` unchanged, at [4](#0-3) . Every user-triggered call (`stake`, `withdraw`, `migrate`, `getReward`) runs the `updateReward` modifier which sets `lastUpdateTime = lastTimeRewardApplicable()` at [5](#0-4)  — this happens even when `totalSupply()` is (or was) zero. Because `lastUpdateTime` jumps forward without `rewardPerTokenStored` being incremented for that elapsed interval, the MGP corresponding to `rewardRate * elapsedZeroSupplySeconds` is permanently excluded from all future `earned()` calculations, yet those MGP tokens are already held by the contract with no other exit path. `rescueReward()` can only be used before the stream starts (`rewardRate == 0`), so once `initializeRewards()` has run, this portion of tokens is unrecoverable by anyone. [6](#0-5) 

### Impact Explanation
This causes a permanent freezing of MGP reward tokens that ordinary users can never claim: (1) if `initializeRewards()` is called before the first staker arrives (a routine sequence, not an admin exploit — anyone can simply be slow to stake), all reward-seconds up to the first `stake()` call are lost; or (2) if all stakers later call `withdraw`/`migrate` for their full balance, `totalSupply()` returns to zero and every subsequent reward-second elapsing before a new staker arrives is likewise lost. This satisfies the "permanent freezing of unclaimed yield" bar.

### Likelihood Explanation
Reachable purely via ordinary unprivileged wallet actions (`stake`, `withdraw`, `migrate`) that are part of normal expected usage of the contract; no privileged role is required to trigger the loss condition once the (normal, non-malicious) admin call to `initializeRewards()` has occurred. The scenario of a delay before the first staker, or a temporary full-withdrawal gap, is realistic for any staking pool with a fixed distribution duration.

### Recommendation
Mirror the `queuedRewards` pattern already used in `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder`: when `totalSupply() == 0`, do not advance `lastUpdateTime`/consume `rewardRate` seconds, or alternatively track and re-queue the reward amount corresponding to zero-supply periods so it can be redistributed once a new staker appears, rather than allowing it to be silently and permanently excluded from `rewardPerTokenStored`.

### Proof of Concept
1. Owner calls `initializeRewards()` while `_totalSupply == 0` (no stakers yet) — `rewardRate` and `periodFinish` are set at [7](#0-6) .
2. Time passes (e.g., 1 day) with zero stakers.
3. A user calls `stake()`. The `updateReward` modifier runs first: `rewardPerToken()` returns unchanged `rewardPerTokenStored` (since `totalSupply()==0` at this point), then `lastUpdateTime` is set to `lastTimeRewardApplicable()` (now 1 day later) at [2](#0-1) . The `_totalSupply` is only incremented after the modifier executes, at [8](#0-7) .
4. One day's worth of `rewardRate`-denominated MGP is now permanently unaccounted for — it was already transferred into the contract, but no `earned()` calculation for any user will ever include it, and `rescueReward()` is blocked once `rewardRate > 0`.

        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();

        rewardRate = rewardsAvailable / (duration);

        lastUpdateTime = block.timestamp;
        periodFinish = block.timestamp + (duration);
