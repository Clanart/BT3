## Title
`safe.directory` trust exception added via "Trust Repository" never expires or is scoped - permanent path-based code-execution trust ([File: app/src/lib/git/config.ts])

### Summary
The report describes an Olympus governance flaw where an "active" state (a proposal), once created, has no expiration and remains exploitable indefinitely, since no mechanism revokes or re-validates it as time passes and circumstances change. The GitHub Desktop analog is the `addSafeDirectory` trust mechanism: when Desktop encounters a repository path that Git considers "unsafe" (owned by a different user), the user can click "Trust Repository", which permanently whitelists that exact path in the global `safe.directory` Git config [1](#0-0) . Like the un-expiring proposal, this trust decision never expires, is never re-validated, and is never revoked, even though the underlying resource (the directory at that path) can change ownership or content later.

### Finding Description
`addSafeDirectory` appends the given path to the global `safe.directory` git config value if not already present, with no timestamp, no scope limitation, and no corresponding removal API anywhere in the codebase [2](#0-1) . This trust exception is surfaced to the user through `MissingRepository.onTrustDirectory` [3](#0-2)  and `AddExistingRepository`'s unsafe-repository warning flow [4](#0-3) , both of which warn that "Adding untrusted repositories may automatically execute files in the repository."

Once trust is granted, `getRepositoryType` will subsequently treat the same path as `kind: 'regular'` rather than `kind: 'unsafe'` forever [5](#0-4) , and Desktop will freely run Git commands (and any commands relying on repo-controlled config/hooks) against whatever content later resides at that path. There is no code anywhere in the repository that removes an entry from `safe.directory` once added — searching the codebase for a corresponding "remove"/"revoke" of `safe.directory` returns no results, confirming the exception is permanent.

This mirrors the governance bug's broken invariant precisely: a one-time authorization decision ("trust this path" / "activate this proposal") is treated as eternally valid, with no re-check of whether the conditions that justified the original decision still hold.

### Impact Explanation
Git treats "dubious ownership" (an unexpected owner on the path) as a signal of potential attacker control, since a repository at that path can auto-execute code via hooks, `core.fsmonitor`, `core.pager`, or similar config-driven mechanisms. Desktop's guard against this is entirely path-based and time-unbounded: once a user trusts `C:\shared\some-repo` (e.g., a shared drive, removable media, container mount, or a path previously used for a repo that was later deleted and removed from Desktop), any future content — potentially attacker-controlled — placed at that exact path will be treated as trusted and Desktop will run Git operations against it without ever re-surfacing the unsafe-ownership warning. This can lead to execution of attacker-supplied repository configuration/hooks, i.e., code execution outside the user's expectation, sourced entirely from an attacker who gains control of a path the user trusted at some point in the past.

### Likelihood Explanation
This requires a plausible sequence: (1) the user encounters an "unsafe" repository at some path and clicks "Trust Repository" once, and (2) at a later time, an attacker manages to place a different Git repository (with malicious hooks/config) at that same path — realistic on shared machines, mounted/removable drives with reused mount points, multi-user network shares, or after a repository is removed from Desktop and its old path is reused. Because the trust exception is permanent and un-scoped to the specific repository's identity (only the path string), Desktop provides no additional friction or re-confirmation for this scenario.

### Recommendation
Do not treat `safe.directory` trust as permanent within Desktop's own bookkeeping. Options include: prompting for re-confirmation if the repository's Git history/first-commit fingerprint changes unexpectedly at a trusted path, exposing a UI to review and revoke previously trusted paths, or scoping trust decisions with additional integrity checks (e.g., binding to a stable repository identity rather than a bare filesystem path) so a reused path does not silently inherit stale trust.

### Proof of Concept
1. User adds/opens a directory Desktop reports as unsafe (`getRepositoryType` returns `kind: 'unsafe'`) and clicks "Trust repository", calling `addSafeDirectory(path)` [3](#0-2) . This permanently adds `path` to the user's global `safe.directory` Git config.
2. Later, the repository is removed from Desktop, or the underlying volume/mount is detached (e.g., USB drive, network share, container volume).
3. An attacker gains control of a filesystem location matching that same `path` string (e.g., by mounting their own drive at the same mount point, or by another user on a shared machine creating a directory at that path) and places a malicious Git repository there with attacker-controlled hooks/config.
4. The user re-adds/reopens that path in Desktop. `getRepositoryType` no longer reports it as unsafe (because the path is in `safe.directory`), so Desktop silently runs Git operations against the attacker-controlled repository without any warning, exactly as if it were still the originally-trusted repository.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
