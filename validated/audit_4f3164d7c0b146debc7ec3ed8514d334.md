Found it — this is exactly the analog bug class. `ServeHTTP` at [1](#0-0) routes non-POST requests (including WebSocket `Upgrade` requests, which use GET) straight through `r.liveProxy`, an `httputil.ReverseProxy` created with `httputil.NewSingleHostReverseProxy(liveURL)` sharing the router's own `client.Transport` [2](#0-1) . `httputil.ReverseProxy` reuses the shared `http.Transport`'s pooled/keep-alive connections for every proxied request on that transport, and only strips the classic hop-by-hop headers listed in RFC 7230 automatically for non-Upgrade requests — for an `Upgrade: websocket` request, `ReverseProxy` intentionally *keeps* the `Upgrade`/`Connection: Upgrade` headers so it can hijack and tunnel the WS connection. If a client sends a GET with both `Upgrade: websocket` and a `Content-Length` (or a `Transfer-Encoding` framing ambiguity) header, that request is forwarded on a connection drawn from the same shared keep-alive pool used for ordinary POST JSON-RPC proxying via `r.proxy`/`r.newUpstreamRequest` (which explicitly strips `Upgrade`/`Connection` via `removeHopByHopHeaders`, [3](#0-2)  — but that stripping path is *not* used for the `r.liveProxy` GET/Upgrade path). This is structurally the same ambiguity nghttpx had: an Upgrade+Content-Length request forwarded verbatim onto a connection-pool that is also used for ordinary keep-alive requests, letting the backend's parsing of the smuggled trailing bytes desynchronize the connection and let a subsequent, unrelated client's response be paired with the attacker's dangling body — i.e., cross-client response-queue poisoning at the `frozen-rpc-router` proxy layer.

If keep-alives are disabled on that transport, this analog collapses to a non-issue. I was not able to verify this within the given tool budget.

### Title
Frozen-RPC-Router forwards WebSocket Upgrade GET requests through a shared keep-alive `ReverseProxy` transport without hop-by-hop header stripping, enabling request/response smuggling analogous to the nghttpx Upgrade+Content-Length bug - (File: cmd/frozen-rpc-router/router.go)

### Summary
`cmd/frozen-rpc-router/router.go`'s `ServeHTTP` dispatches any non-POST request — including a GET carrying `Upgrade`/`Connection: Upgrade` plus an attacker-controlled `Content-Length` — directly to `r.liveProxy`, a `net/http/httputil.ReverseProxy` that shares the router's own connection-pooling `http.Client.Transport`. Unlike the JSON-RPC POST path (which calls `removeHopByHopHeaders` before forwarding), this Upgrade path does not sanitize the request before it is placed on the same keep-alive connection pool used for regular proxied traffic.

### Finding Description
`ServeHTTP` routes on HTTP method only: `if request.Method != http.MethodPost { r.liveProxy.ServeHTTP(w, request); return }` [1](#0-0) . `r.liveProxy` is built once in `newRouter` via `httputil.NewSingleHostReverseProxy(liveURL)` and explicitly assigned `liveProxy.Transport = client.Transport` [2](#0-1)  — the same `*http.Client` used for the ordinary JSON-RPC proxy calls in `r.proxy`/`r.callUpstream` [4](#0-3) . Go's standard `ReverseProxy` forwards `Upgrade`/`Connection: Upgrade` headers verbatim (it needs them to hijack the tunnel), while any `Content-Length` supplied by the client is also carried through unmodified since no `removeHopByHopHeaders`-style sanitization runs on this code path, unlike the POST path at lines 634–636 which strips `Connection`, `Upgrade`, `Transfer-Encoding`, etc. before building `upstreamRequest` [5](#0-4) . This mirrors the nghttpx flaw precisely: an Upgrade request bearing a body-framing header is relayed onto a connection-reusing transport shared with unrelated traffic, so if the backend does not immediately reject or fully consume the declared body before reusing the socket for the next pipelined message, the smuggled bytes desynchronize the stream and get attributed to a different client's subsequent request/response on that pooled connection.

### Impact Explanation
If exploitable end-to-end (dependent on backend `live` node behavior on the ambiguous Upgrade+Content-Length combination), an unauthenticated public-RPC client could poison the response stream/queue shared with other clients hitting the same `frozen-rpc-router` instance, potentially causing a client to receive a response intended for a different client (cross-client data leakage) or causing malformed backend state that disrupts RPC availability for all users behind that router — a public-RPC-surface integrity/availability issue reachable purely from crafted HTTP requests.

### Likelihood Explanation
Reaching this path requires only sending a single GET request with `Upgrade: websocket`, a spoofed `Connection: Upgrade`, and a `Content-Length` header to the router's listening port — no authentication, wallet, or special client capability is needed, matching the "attacker-favorable ambiguous message" precondition of the original advisory. The remaining variable is whether the specific backend (the `live` full node's RPC server) resolves the resulting ambiguous framing in the attacker's favor, which I could not verify from the indexed code for the backend HTTP/WS server implementation.

### Recommendation
Apply the same hop-by-hop sanitization used in `newUpstreamRequest`/`removeHopByHopHeaders` to the Upgrade/WebSocket forwarding path, or explicitly reject any Upgrade request that also carries a `Content-Length`/`Transfer-Encoding` header before handing it to `r.liveProxy`. Additionally, ensure `liveProxy`'s transport either disables connection reuse or is isolated per-connection so a malformed Upgrade exchange cannot desynchronize traffic belonging to other clients.

### Proof of Concept
1. Send: `GET / HTTP/1.1\r\nHost: <router>\r\nConnection: Upgrade\r\nUpgrade: websocket\r\nContent-Length: 40\r\n\r\n<40 bytes forming a smuggled second HTTP request>`.
2. The router's `ServeHTTP` sees `Method != POST` and forwards the raw request headers/body untouched to `r.liveProxy`, which uses the shared pooled `Transport` to talk to the `live` backend.
3. If the backend keeps the connection alive after handling (or misinterpreting) the Upgrade attempt and then reads the smuggled trailing bytes as a new pipelined request, the attacker's injected request is answered on the same backend connection that will next be reused for another legitimate proxied client request, causing response-queue desynchronization between the attacker and the next client sharing that pooled connection.

func (r *router) newUpstreamRequest(request *http.Request, target *upstream, body []byte) (*http.Request, error) {
	endpoint := joinedURL(target.endpoint, request.URL)
	upstreamRequest, err := http.NewRequestWithContext(request.Context(), request.Method, endpoint.String(), bytes.NewReader(body)) //nolint:gosec // endpoint is rooted at an operator-configured upstream URL.
	if err != nil {
		return nil, err
	}
	upstreamRequest.Header = request.Header.Clone()
	removeHopByHopHeaders(upstreamRequest.Header)
	upstreamRequest.Header.Del("Accept-Encoding")
	if host := clientIP(request.RemoteAddr); host != "" {
		prior := upstreamRequest.Header.Get("X-Forwarded-For")
		if prior != "" {
			host = prior + ", " + host
		}
		upstreamRequest.Header.Set("X-Forwarded-For", host)
	}
	return upstreamRequest, nil
}

func removeHopByHopHeaders(header http.Header) {
	for _, name := range strings.Split(header.Get("Connection"), ",") {
		header.Del(strings.TrimSpace(name))
	}
	for _, name := range []string{
		"Connection",
		"Keep-Alive",
		"Proxy-Authenticate",
		"Proxy-Authorization",
		"Te",
		"Trailer",
		"Transfer-Encoding",
		"Upgrade",
	} {
		header.Del(name)
	}
}
