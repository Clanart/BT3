Based on my investigation, the strongest analog is in `upb`'s wire decoder, specifically the intentionally garbage-tolerant string-read helper `upb_EpsCopyInputStream_ReadStringEphemeral`.

### Title
Deferred bounds validation in `upb_EpsCopyInputStream_ReadStringEphemeral` can expose adjacent patch-buffer memory before the overrun is detected - ([File: upb/wire/internal/eps_copy_input_stream.h])

### Summary
`upb`'s C wire decoder implements an "eps-copy" (end-plus-slop) input stream that intentionally allows reads to run past the logical end of a chunk into a fixed-size `kUpb_EpsCopyInputStream_SlopBytes`-sized `patch` buffer, deferring a definitive bounds error until a later `upb_EpsCopyInputStream_IsDone()` call [1](#0-0) . The helper `upb_EpsCopyInputStream_ReadStringEphemeral` explicitly documents that if the attacker-controlled length prefix `size` extends beyond the real input but still within the slop region, the returned `upb_StringView` "may contain garbage bytes from the patch buffer... it may result in nonsense bytes ending up in the output," with the inconsistency "detected later" via `IsDone()` [2](#0-1) [3](#0-2) .

### Finding Description
The failed invariant mirrors the SQLite report: a length/size value taken from attacker-controlled wire data ("record length") is used to bound a read region, but the check only guarantees the read stays within an over-allocated slop region rather than within the actual valid record/input boundary. In SQLite, a crafted record header lets a query read bytes past the record's real extent, disclosing adjacent heap memory. In `upb`, `size` is read from the untrusted length-delimited tag (`upb_DecodeFast_DecodeSize`/`ReadSize`-equivalent) and passed to `ReadStringEphemeral`; the only check performed is `size <= (e->end + kUpb_EpsCopyInputStream_SlopBytes) - ptr` [4](#0-3) . That check passes even when `size` exceeds the field's real extent (or the stream's actual `limit`), because the slop bytes physically exist in the `patch` buffer/original buffer tail but do not belong to the field being read. The resulting `upb_StringView` therefore can point at bytes that are logically "beyond the record" — either leftover data from a previous buffer refill or uninitialized `patch` contents — the same "read subsequent bytes of memory that extend beyond the record" pattern in the SQLite CVE.

### Impact Explanation
If the value produced by `ReadStringEphemeral` is consumed (e.g., copied into a message field, used in a UTF-8/validation decision, or otherwise observed) before the deferred `IsDone()` check runs and rejects the parse, an attacker sending a bounded, otherwise well-formed Protobuf payload through a public parse API could cause adjacent-buffer bytes (potentially previous message data, stack/heap remnants in the `patch` array, or the tail of the real input buffer) to be exposed. This is a memory-disclosure class issue (Medium), not memory corruption/RCE — consistent with the SQLite report's own severity and the developer's framing of the class as a leak of "bytes that extend beyond the record" rather than corruption.

### Likelihood Explanation
This is Medium/uncertain rather than confirmed High-confidence, because I could not fully trace, within the available tool budget, whether the call sites of `ReadStringEphemeral` in `upb/wire/decode.c` ever surface the ephemeral view to caller-visible state (e.g., copied into a returned message, or into error/UTF-8 diagnostics) before the overrun is caught, or whether it is used purely as an internal peek that is always discarded on the subsequent failed `IsDone()`/limit check. The function's own doc comment strongly suggests the former ("nonsense bytes ending up in the output"), which is why I treat this as the strongest available analog, but this specific call-site behavior (in `upb/wire/decode.c`) needs direct verification I was unable to complete in this session [5](#0-4) .

### Recommendation
- Verify all call sites of `upb_EpsCopyInputStream_ReadStringEphemeral` (in `upb/wire/decode.c`) to confirm whether the returned `upb_StringView` can ever be copied into a message field, returned from a public parse call, or included in diagnostics before the deferred limit/`IsDone()` check runs.
- If any such path exists, either zero/poison the unused tail of the `patch` buffer before use, or move the overrun check to happen before the ephemeral view is handed to any consumer that might retain/copy it, rather than deferring it to `IsDone()`.
- Add a fuzz/unit regression test with a trusted schema and a length-delimited field whose declared size is crafted to land inside the slop region but past the real record boundary, asserting that no `patch` buffer content is observable in the final parsed message when the parse ultimately fails.

UPB_INLINE const char* upb_EpsCopyInputStream_ReadStringEphemeral(
    struct upb_EpsCopyInputStream* e, const char* ptr, size_t size,
    upb_StringView* sv) {
  UPB_ASSERT(size <= PTRDIFF_MAX);
  // Size must be within the current buffer (including slop bytes).
  const char* limit = e->end + kUpb_EpsCopyInputStream_SlopBytes;
  if ((ptrdiff_t)size > limit - ptr) {
    // For the moment, we consider this an error.  In a multi-buffer world,
    // it could be that the requested string extends into the next buffer, which
    // is not an error and should be recoverable.
    return UPB_PRIVATE(upb_EpsCopyInputStream_ReturnError)(e);
  }
  *sv = upb_StringView_FromDataAndSize(ptr, size);
  return ptr + size;
}
