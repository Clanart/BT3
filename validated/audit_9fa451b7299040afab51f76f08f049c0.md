## Analog Found: `LastRewardedHeight` watermark skip on zero-reward payouts

### Title
Zero-reward consensus incentive payouts skip advancing `LastRewardedHeight`, causing retroactive overpayment of relayer rewards from the treasury - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`Pallet::process_message` in `pallet-consensus-incentives` computes a relayer reward as `blocks_since_watermark × block_cost` and only advances the `LastRewardedHeight` watermark for a state machine when the computed `reward` is non-zero. When `reward` is zero — most notably when `StateMachinesCostPerBlock` is set to `0` rather than removed — the watermark is never advanced even though blocks keep being finalized and relayers keep submitting consensus proofs. This is the exact analog of the Ribbon `lastLockedAmount` bug: skipping the recording of a baseline/"last state" value whenever the current value evaluates to zero corrupts a later delta-based calculation.

### Finding Description
In `process_message`: [1](#0-0) 

`calculate_reward` derives `reward = (latest_height - baseline) * block_cost`, where `baseline` is `LastRewardedHeight` (falling back to `previous_commitment_height`): [2](#0-1) 

If `reward.is_zero()` — which happens whenever `block_cost == 0` for that state machine (a value governance can set explicitly via `update_cost_per_block`, distinct from removing the entry entirely) — `process_message` returns early *before* the `LastRewardedHeight::mutate` call that advances the watermark: [3](#0-2) [4](#0-3) 

`update_cost_per_block` is the only governance call that can set the cost, and it accepts any value including `0`: [5](#0-4) 

Because the watermark is not advanced while `block_cost == 0`, every consensus update processed during that window is silently "not recorded" against `LastRewardedHeight` — mirroring the Ribbon report's skipped `lastLockedAmount` update for empty rounds. Once governance later restores a non-zero `block_cost`, the very next `process_message` call computes `blocks = latest_height - baseline`, where `baseline` is still the stale watermark from *before* the zero-cost period. The entire span of blocks that elapsed during the zero-cost window is paid out at the newly restored (non-zero) rate to whichever relayer happens to deliver the next consensus update — an ordinary, unprivileged relayer, requiring no compromise, malicious peer, or malicious governance action. The `existing "reward.is_zero() → skip"` guard was clearly meant only to avoid a no-op transfer/mint/event for a genuinely zero-block span, but it conflates "no reward owed" with "no state to record," exactly like the original Ribbon bug conflated "no locked asset" with "no round to record."

### Impact Explanation
This causes the treasury (`T::TreasuryAccount`) to pay out a lump-sum reward sized by the entire dormant span at the reactivated cost rate, to a single relayer, rather than either (a) zero reward for the dormant window as governance intended when it set `block_cost = 0`, or (b) the correct incremental accounting. This is a direct loss/miscalculation of treasury funds tied to a state-tracking bug — fitting the "stealing or loss of funds" / "logic attack" impact categories, achieved purely by an unprivileged relayer submitting a consensus message after a benign governance parameter change, not by any admin/governance malice, compromised relayer, or front-running.

### Likelihood Explanation
Requires only a routine, foreseeable governance operation (temporarily zeroing `StateMachinesCostPerBlock` for a state machine, e.g., to pause incentives without removing the mapping via `remove_incentives`) followed by ordinary relayer activity restoring a non-zero cost. No attacker collusion, leaked keys, or malicious actors are needed — the "attacker" is simply the relayer who happens to deliver the next consensus proof after cost is restored.

### Recommendation
Advance `LastRewardedHeight` to `state_machine_height.height` unconditionally whenever a message is processed for that state machine, regardless of whether `reward` is zero — mirroring the fix applied for the Ribbon Finance issue (always record the current state as the new baseline, only skip the transfer/event/mint when `reward == 0`).

### Proof of Concept
1. Governance calls `update_cost_per_block(state_machine_id, 0)`.
2. Chain advances from height H0 to H_n over many consensus updates; each `on_executed` call computes `reward = blocks * 0 = 0`, so `LastRewardedHeight` stays at its pre-existing value (or unset).
3. Governance calls `update_cost_per_block(state_machine_id, COST)` with `COST > 0`.
4. Any relayer submits the next consensus message advancing the state machine to height H_n+1. `calculate_reward` computes `blocks = H_n+1 - baseline` where `baseline` is still the height from before step 1 (or older), multiplying the entire accumulated span by `COST` and transferring that full amount from the treasury to the relayer in one payout — far beyond what governance intended to pay for the window it deliberately zero-costed. [6](#0-5) 
The existing test `skip_incentivizing_of_relayer_when_cost_per_block_is_not_set` only covers the case where the map entry is entirely absent (`None`), not the `Some(0)` case, confirming this path is untested.
