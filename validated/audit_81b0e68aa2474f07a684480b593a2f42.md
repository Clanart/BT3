### Title
Unbounded atom-length parsing in `is_atom_canonical`/`is_clvm_canonical` can crash on crafted spend-bundle CLVM data - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical` and `is_clvm_canonical` in `chia/full_node/mempool_manager.py` parse a raw, attacker-supplied serialized CLVM buffer (a submitted coin spend's puzzle reveal/solution) byte by byte to determine DEDUP eligibility. The atom length is computed directly from attacker-controlled length-prefix bytes and is never validated against the remaining buffer size before it is used to index into the buffer, mirroring the binutils `display_debug_ranges` bug class where an unchecked length/offset computed from crafted input overruns the buffer and crashes the parser.

### Finding Description
`is_atom_canonical` reads up to `prefix_len` (0–5) additional bytes to build `atom_len`, indexing `clvm_buffer[offset]` after each increment without checking `offset < len(clvm_buffer)`: [1](#0-0) 

If a submitted spend's puzzle reveal/solution buffer is truncated right at a multi-byte length-prefix boundary, this indexing raises an uncaught `IndexError`.

Even when the prefix bytes are present, `atom_len` (attacker-controlled, up to roughly 2^40 for the longest prefix form) is never checked against the remaining buffer length. The caller, `is_clvm_canonical`, blindly advances `offset += atom_len`: [2](#0-1) 

On the next loop iteration, `b = clvm_buffer[offset]` again indexes past the end of the buffer, raising an unhandled `IndexError` instead of returning `False`/rejecting the input gracefully: [3](#0-2) 

Per the repository's own context notes, this canonical-serialization check is invoked during the "Coin spend processing" step of the mempool's `validate_spend_bundle()` admission pipeline to determine DEDUP eligibility for a submitted spend bundle: [4](#0-3) 

This is directly analogous to the reported CVE class: an integer/length value derived from untrusted, crafted input is used to index/advance through a buffer without bounds validation, causing a crash when parsing malformed data (ELF debug-info length fields in the CVE vs. CLVM atom length-prefix bytes here).

### Impact Explanation
If an unhandled `IndexError` from this canonical-serialization check escapes any surrounding `try/except`, a single crafted (truncated or malformed) coin-spend buffer submitted in a normal spend bundle could crash mempool item processing for that submission, resulting in a spend-triggered transaction-processing halt — one of the accepted High-impact analog categories. I was not able to fully confirm, within the remaining investigation budget, whether an enclosing exception handler in `validate_spend_bundle()`/`pre_validate_spendbundle()` catches bare `IndexError` (as opposed to `ValueError`, which is explicitly caught in `pre_validate_spendbundle`), so the exact blast radius (single-item rejection vs. broader mempool-manager disruption) is uncertain and should be confirmed by tracing all callers and their exception handling.

### Likelihood Explanation
Reachable by any unprivileged spend-bundle submitter: DEDUP eligibility is evaluated for every coin spend processed by `validate_spend_bundle()`, so an attacker only needs to submit a spend bundle whose puzzle reveal or solution buffer is a crafted/truncated multi-byte-atom encoding — no special permissions or peer trust are required.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` before each `clvm_buffer[offset]` access (verify `offset < len(clvm_buffer)`), and validate that the computed `atom_len` does not exceed the remaining buffer length before `is_clvm_canonical` advances `offset` by it — returning `False` (non-canonical/invalid) instead of raising an uncaught exception, consistent with the defensive bounds-checking pattern already used in `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list` helpers.

### Proof of Concept
Construct a spend bundle whose coin spend `solution` (or puzzle reveal) bytes end in a truncated multi-byte atom length prefix, e.g. a buffer ending in byte `0xF8` (5-byte length-prefix marker) with fewer than 5 trailing bytes, or a valid short atom encoding whose declared `atom_len` exceeds the remaining buffer. Submitting this spend bundle to the mempool causes `is_clvm_canonical()`/`is_atom_canonical()` to index past the end of `clvm_buffer`, raising an `IndexError` during the DEDUP-eligibility check inside `validate_spend_bundle()`'s coin-spend processing step.

**Caveat:** This analog is offered with moderate confidence. I confirmed the vulnerable parsing logic and its documented call site in the admission pipeline, but I could not fully trace every exception-handling layer around the call site within the available tool-call budget, so the precise scope of the resulting halt (single spend-bundle rejection vs. a wider processing disruption) is not fully verified.
