Confirmed: `Kip71BaseFeeDenominator` has a `FormatChecker` rejecting zero (`v != 0`) [1](#0-0) , but `Kip71GasTarget` uses `noopFormatChecker`, meaning governance can set `kip71.gastarget` to `0` without any validation [2](#0-1) . This value flows unguarded into `KIP71Config.GasTarget` via `ParamSet.ToKip71Config()` [3](#0-2) , and then into `NextMagmaBlockBaseFee`, where, unlike `BaseFeeDenominator` (which has an explicit zero-guard defaulting to 64), `GasTarget` is used directly as a divisor with no zero-check: `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` in both the "usage above target" and "usage below target" branches [4](#0-3) . Go's `big.Int.Div` panics on division by zero, so this is a real analog to the reported bug class (an unguarded governance-configurable divisor left at its zero default/set-to-zero value breaking a core function), but I could not fully verify within the remaining budget whether this is reachable purely by an "unprivileged" party (it requires a governance vote to set `kip71.gastarget=0`, which is a `governance parameters` path explicitly allowed by the rules) or whether some earlier validation elsewhere in the governance-vote-acceptance pipeline (e.g. `kaiax/gov/headergov`) blocks zero values before they reach `ChainConfig`/`ParamSet`. Given the explicit contrast with the `Kip71BaseFeeDenominator` checker in the same file, this looks like an intentional omission/bug rather than a defense-in-depth elsewhere, but I flag this uncertainty.

### Title
Missing zero-value validation for `kip71.gastarget` governance parameter causes panic in base fee calculation - (File: params/kip71_config.go)

### Summary
The KIP-71 dynamic base fee formula (`NextMagmaBlockBaseFee`) divides by the governance-configurable `GasTarget` parameter without any zero-guard, while the analogous `BaseFeeDenominator` parameter has both a format-checker rejecting zero and a runtime zero-guard. If `kip71.gastarget` is ever `0` (e.g. governance-set default of `0` before initialization, or a governance vote sets it to `0`), every subsequent block whose gas usage differs from the target will trigger a division by zero in `math/big`, which panics.

### Finding Description
`Kip71GasTarget`'s governance parameter definition uses `noopFormatChecker`, allowing any `uint64` value including `0` to be accepted as a valid governance value [2](#0-1) . Contrast this with `Kip71BaseFeeDenominator`, whose checker explicitly requires `v != 0` [1](#0-0) .

The resulting `ParamSet.GasTarget` is passed unmodified into `params.KIP71Config.GasTarget` via `ToKip71Config()` [3](#0-2) .

In `NextMagmaBlockBaseFee`, `BaseFeeDenominator` is defensively checked for zero and replaced with `64` if so ("To avoid panic, set the fluctuation range small") [5](#0-4) , but `gasTarget := kc.GasTarget` has no equivalent guard [6](#0-5) . When `parentGasUsed != gasTarget` (essentially every block once `gasTarget == 0`, since any nonzero gas usage is "above target"), the code computes:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
```
in both the "above target" and "below target" branches [7](#0-6) . `big.Int.Div(x, 0)` panics in Go's standard library.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked during header validation (`VerifyMagmaHeader`) and fee-history/base-fee RPC estimation (`node/cn/gasprice/feehistory.go`), both consensus-critical and RPC-reachable paths [8](#0-7) [9](#0-8) . A panic here in block processing halts every node computing the next block's base fee, i.e., a chain-wide denial of service, satisfying "acceptance of an invalid transaction or block" / state-transition halt criteria.

### Likelihood Explanation
This requires the `kip71.gastarget` governance parameter to become `0`, which is only possible through a governance vote given the current codebase's `noopFormatChecker`. This is a `governance parameters` path explicitly in scope. Given that the sibling parameter `BaseFeeDenominator` was deliberately hardened against zero both at admission (`FormatChecker`) and at use (`kc.BaseFeeDenominator == 0` check), the omission for `GasTarget` appears to be an unintentional gap rather than an accepted risk.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` rejecting `0` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-guard in `NextMagmaBlockBaseFee` analogous to the existing `BaseFeeDenominator == 0` fallback, before using `gasTarget` as a divisor.

### Proof of Concept
1. Submit/pass a governance vote setting `kip71.gastarget = 0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` [2](#0-1) ).
2. Once the parameter takes effect at the relevant block, any block whose `GasUsed` differs from `0` (virtually all blocks) causes `NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))` in the "above target" branch [10](#0-9) .
3. `big.Int.Div` panics on division by zero, crashing the node process during block header verification / base fee computation, halting chain progress network-wide.
