## Title
DataLayer wallet trusts unverified hint memo for singleton root/inner-puzzle-hash during sync, causing state-corruption / sync halt for DL store owners and subscribers - (File: chia/data_layer/data_layer_wallet.py)

## Summary
`DataLayerWallet.singleton_removed()` reconstructs the next `SingletonRecord` (including the DataLayer Merkle `root` and `inner_puzzle_hash`) directly from the `CREATE_COIN` condition's memo/hint field, without cryptographically verifying that those hinted values actually correspond to the puzzle hash of the coin that was created. This mirrors the Phoenix SDK bug class: data extracted from a transaction's execution trace is trusted and persisted as authoritative state without validating it against the actual/ground-truth outcome of that execution.

## Finding Description
When a DataLayer singleton spend is observed during wallet sync, `singleton_removed()` runs the spend's puzzle/solution and scans the resulting conditions for the `CREATE_COIN` that creates the next (odd-amount) singleton coin: [1](#0-0) 

The `full_puzzle_hash` and `amount` are taken from the actual `CREATE_COIN` condition (`condition[1]`, `condition[2]`), which is trustworthy because it is literally the puzzle hash of the coin that gets created on-chain. However, `root` and `inner_puzzle_hash` are taken straight from the CREATE_COIN memo/hint field (`condition[3][1]`, `condition[3][2]`) with **no verification** that:

```
create_host_fullpuz(inner_puzzle_hash, root, launcher_id).get_tree_hash_precalc(inner_puzzle_hash) == full_puzzle_hash
```

This is exactly the check that IS performed for the initial launcher spend, in `match_dl_launcher()`: [2](#0-1) 

So the trust anchor (launch) is cryptographically validated, but every subsequent state-update spend synced via `singleton_removed()` is not. The mismatched `root`/`inner_puzzle_hash` is then persisted into the `SingletonRecord`, including a `LineageProof` built from the unverified `inner_puzzle_hash`/`root`: [3](#0-2) 

## Impact Explanation
Any party who can produce (or influence) a DataLayer singleton spend — the store owner themselves, or anyone able to get a spend for that singleton included on-chain — can put a hint memo whose `root`/`inner_puzzle_hash` do not match the real puzzle structure of the coin actually created. Every wallet syncing that launcher id (the owner's own wallet on resync, and any wallet/subscriber tracking the store for proofs/offers) will:
- Record an incorrect current `root` for the store (`SingletonRecord.root`), which is read by `DataLayer`/`DataStore` reconciliation logic (`_update_confirmation_status()`) and by proof verification paths that ultimately trust wallet-reported root state.
- Build a `LineageProof`/`create_host_layer_puzzle(inner_puzzle_hash, root)` that does not match the true on-chain coin's puzzle hash, so the next attempt to spend this singleton (`create_update_state_spend`, which curries `current_full_puz` from `singleton_record.lineage_proof`/`root`) will produce a puzzle reveal whose tree hash mismatches the real coin, causing the spend to be rejected by the mempool/consensus.

This is a spend-triggered halt to further DataLayer transaction processing for the affected launcher id (subsequent state updates fail to construct valid spends), and it corrupts the wallet-reported root that downstream DataLayer proof/offer logic treats as ground truth — directly analogous to the Phoenix SDK issue where unvalidated/failed-transaction data is processed as if it reflects real on-chain state, leading to a denial-of-service condition for consumers of that data.

## Likelihood Explanation
The DL singleton owner (or anyone who can get a spend accepted for that puzzle) fully controls the memo/hint arguments of the `CREATE_COIN` condition emitted by the state-update solution; there is no additional signature/authorization needed beyond spending the singleton normally through `create_update_state_spend`, whose solution path allows an arbitrary root hash to be hinted. Since `singleton_removed()` is the standard sync path invoked from `WalletStateManager._add_coin_state()` for every DL wallet observing a spend of a tracked launcher, this is reachable by any spend of that singleton, including a spend intentionally crafted with mismatched hints.

## Recommendation
In `singleton_removed()`, after extracting `full_puzzle_hash`, `root`, and `inner_puzzle_hash` from the memo, verify (as `match_dl_launcher()` already does for the launcher spend):
```
create_host_fullpuz(inner_puzzle_hash, root, singleton_record.launcher_id).get_tree_hash_precalc(inner_puzzle_hash) == full_puzzle_hash
```
If the check fails, treat the singleton as melted/invalid (log and `return`) rather than persisting an unverified `SingletonRecord`.

## Proof of Concept
1. Create a DataLayer store/singleton normally (launch verified via `match_dl_launcher`).
2. Craft a state-update spend for that singleton whose delegated puzzle emits `CREATE_COIN <real_next_full_puzzle_hash> <amount> (<launcher_id> <bogus_root> <real_inner_puzzle_hash>)` — i.e., a `CREATE_COIN` whose actual puzzle hash is correct/spendable, but whose hint's `root` value does not correspond to that puzzle hash (attacker picks any `bogus_root != real_root`).
3. Push this spend; it is accepted by consensus because CREATE_COIN/consensus validation never checks the memo/hint contents.
4. Any wallet tracking this launcher id (owner's own wallet re-syncing from scratch, or a subscriber) calls `singleton_removed()`, which records `SingletonRecord(root=bogus_root, inner_puzzle_hash=real_inner_puzzle_hash, ...)` without checking `create_host_fullpuz(real_inner_puzzle_hash, bogus_root, launcher_id).get_tree_hash() == real_next_full_puzzle_hash` (which is false).
5. The next call to `create_update_state_spend()` for this launcher id builds `current_full_puz = create_host_fullpuz(current_inner_puzzle, singleton_record.root, launcher_id)` using the corrupted `bogus_root`, producing a puzzle reveal whose tree hash does not match the real on-chain coin's puzzle hash — the resulting spend bundle fails mempool/consensus validation, halting further DataLayer transaction processing for that store until the corrupted record is manually corrected.
