### Title
Cached FROST preprocess seed is never retired, causing nonce reuse and secret-share recovery when `sign()` runs a second time with different inputs - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` persists a deterministic preprocess seed in `CachedPreprocesses` keyed only by `context` (e.g. `(b"DkgConfirmer", attempt)`), and `AlgorithmSignMachine::from_cache` re-derives the *identical* FROST nonces `(d, e)` from that seed every time it is called. The entry is `set` once and `get` on every subsequent invocation — it is never deleted or invalidated. Because `share_internal` (line 156) re-enters `preprocess_internal`, and `DkgConfirmer::complete` (line 321-324) calls `share_internal` *again* after `DkgConfirmer::share` already did, `machine.sign(...)` is executed twice on the same nonce seed. If the second call's preprocess set or message differs from the first, the same nonce pair is consumed under different binding factors/challenges — the classic nonce-reuse condition that leaks the MuSig/FROST secret share.

### Finding Description
- `preprocess_internal` writes the seed once (`CachedPreprocesses::set`, line 134) but on every later call takes the `from_cache` path (lines 137-145), reconstructing `AlgorithmSignMachine` with the same `seed`, hence the same `nonces: Vec<Nonce<C>>` (crypto/frost/src/sign.rs, `AlgorithmSignMachine`, line 250).
- No code anywhere deletes the `CachedPreprocesses` entry after use; it survives for the lifetime of the DB.
- `DkgConfirmer::share` (line 304) → `share_internal` → `preprocess_internal` → `sign`. `DkgConfirmer::complete` (line 312) → `share_internal` again → `preprocess_internal` (same seed) → `sign` again, with a caller-supplied `preprocesses` map and a `key_pair`-dependent message (`set_keys_message`, line 296).
- The `preprocesses` argument to both calls is built from serialized preprocess bytes read via `read_preprocess` (line 165), i.e. untrusted per-participant data. The included-participant set and their commitments determine the per-participant binding factor `rho` and the challenge `c`. A FROST share is `z = d + e·rho + λ·s·c`; two shares computed over the same `(d, e)` but different `rho`/`c` yield linear equations in the secret share `s`.

This is the exact analog of the kernel bug: an operation (queueing delayed work / re-signing from a cached seed) that races past a teardown boundary (cancel_delayed_work_sync / first consumption of a one-time preprocess) because no "removing/used" flag invalidates the resource. The `SignMachine::from_cache` documentation (crypto/frost/src/sign.rs:218) explicitly warns "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" — the deletion is never performed.

### Impact Explanation
Recovery of the validator's MuSig secret share for the tributary's validator-set key (`musig(musig_context(set), key, participants)`). That share signs `set_keys` confirmations authorizing new threshold key pairs on Serai; share compromise enables forging the validator's contribution to set-keys signatures — consensus-critical key-control impact.

### Likelihood Explanation
The double-`sign` on one seed happens unconditionally — `share()` and `complete()` both drive `share_internal`. Exploitation requires the second `sign` to observe different binding inputs than the first: a different included-participant set in the `preprocesses` map (a peer-controlled preprocess can be valid in one collection and absent/altered in the other, e.g. across retries, reordered tributary message delivery, or a participant that submits preprocess bytes in the share phase but is excluded at complete time), or a different `key_pair` producing a different message/challenge. Both inputs are externally supplied message data, not locally fixed. Note: if `share` and `complete` are always invoked with byte-identical preprocess maps and identical `key_pair`, the second `sign` is deterministic and reproduces the same share (no leak); the leak requires input divergence between the two calls, which is reachable but depends on the coordinator's message flow in `handle.rs` that I could not fully trace within the available analysis.

### Recommendation
- Delete the `CachedPreprocesses` entry (`del`/`remove` on the DB) the first time it is consumed for signing, or gate re-use with an explicit `consumed` flag checked under the same write transaction — the direct analog of the kernel's `xd->removing` flag set under `xd->lock`.
- Alternatively, persist the `AlgorithmSignatureMachine` state (or the emitted share) after `share()` so `complete()` never re-executes `sign` on a re-derived seed.
- At minimum, assert in `share_internal`/`complete` that the reconstructed machine's `preprocess` and the `included` set match the ones used for the share that was actually broadcast.

### Proof of Concept
Conceptual derivation (in-scope crates only):

1. Attempt `a`: `DkgConfirmer::new(key, spec, txn, a)`; `share(preprocesses_A, kp)` stores/loads seed `s`, calls `sign` over included set `I_A` with binding factors `rho_A` and challenge `c_A` over `msg = set_keys_message(set, removed, kp)`, emitting `z_1 = d + e·rho_i,A + λ·x·c_A`.
2. `complete(preprocesses_B, kp', shares)` where `preprocesses_B` differs from `preprocesses_A` (different participant subset or different commitment bytes — both are attacker-supplied `read_preprocess` input) or `kp' ≠ kp`. `share_internal` reloads the same seed → same `(d, e)` → `sign` produces `z_2 = d + e·rho_i,B + λ·x·c_B`.
3. With `z_1`, `z_2`, known `rho_i,A`, `rho_i,B`, `c_A`, `c_B`: subtract to eliminate `d` (or solve the 2×2 system in `d, e·rho` when `rho` matches and `c` differs): `x = (z_1 − z_2 − e·(rho_A − rho_B)) / (λ·(c_A − c_B))` — recovery of the secret share `x`.
