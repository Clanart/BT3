### Title
Bridge value-transfer finalization can be permanently blocked by a blacklistable ERC20 token, permanently locking user funds - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`BridgeTransferERC20.handleERC20Transfer()` unconditionally sends the bridged ERC20 amount to the destination address `_to` supplied by the original requester on the source chain, via `IERC20(_tokenAddress).safeTransfer(_to, _value)` (or `ERC20Mintable.mint`). If the underlying token implements an address blacklist (e.g. USDC, USDT) and `_to` is or becomes blacklisted, this call always reverts, and there is no fallback mechanism to redirect or recover the funds. [1](#0-0) 

### Finding Description
`handleERC20Transfer` is invoked by bridge operators to finalize a cross-chain value transfer that was requested on the counterpart chain via `requestERC20Transfer`/`onERC20Received`. [2](#0-1)  The state bookkeeping (`_setHandledRequestTxHash`, `handleNoncesToBlockNums[...]`, `_updateHandleNonce`) and the token transfer/mint both occur inside the same function call/transaction. [3](#0-2) 

Because Solidity reverts unwind all state changes within a failed transaction, if the terminal `safeTransfer`/`mint` call fails (which is guaranteed for a blacklisted `_to` on tokens like USDC/USDT), the entire `handleERC20Transfer` call reverts — including the nonce bookkeeping. This is directly analogous to the reported Teller Protocol issue: a forced token transfer to a specific address inside a critical settlement path (there, `CollateralManager.withdraw` inside `repayLoanFull`; here, `safeTransfer`/`mint` inside `handleERC20Transfer`) can never succeed once that recipient is blacklisted, and there is no alternate-address recovery path, as recommended in the original report ("Allow borrower to withdraw collateral to any address, if there is no debt").

Unlike the KLAY-only path (`_payKLAYFeeAndRefundChange`, which uses raw ETH `.call`), the ERC20 path is uniquely exposed to token-level blacklists because ERC20 transfer/mint calls into token logic that can unconditionally block specific addresses. [4](#0-3) 

### Impact Explanation
Because the destination `_to` is chosen by the (untrusted) requester on the origin chain when calling `requestERC20Transfer`, an attacker/griefer can request a transfer to an address that is already blacklisted by the bridged token, or a user's own destination address can later become blacklisted before finalization. In either case, the value transfer request can never be successfully finalized by operators — the tokens already escrowed/burned on the source chain, and the corresponding mint/transfer on the destination chain being permanently blocked, results in funds being permanently locked/unspendable with no recovery mechanism in the contract. This constitutes concrete unauthorized loss of value availability (locked user funds) rather than a mere inconvenience.

### Likelihood Explanation
Reaching this state requires only a single externally-triggered `requestERC20Transfer`/`onERC20Received` call by any unprivileged bridge user specifying (or later becoming) a blacklisted `_to`; no privileged access or malicious operator/validator collusion is needed to trigger the condition. The condition depends on the bridged ERC20 token supporting a blacklist (USDC/USDT-style tokens), which are common bridge assets, making this a realistic and low-effort scenario for token-holders or griefers to trigger.

### Recommendation
Decouple the state-finalization bookkeeping from the token delivery step, or implement a pull-based claim pattern (e.g., escrow the amount for `_to` and let any address trigger/redirect withdrawal, or allow governance/operators to redirect funds to an alternate address after a timeout) so that a single blacklisted recipient cannot permanently block nonce processing or lock the transferred value. At minimum, wrap the `safeTransfer`/`mint` call so failures do not revert the entire nonce-processing transaction, and record the failure so funds can later be reclaimed to a non-blacklisted address.

### Proof of Concept
1. A user (or attacker) calls `requestERC20Transfer(tokenAddress, to, value, feeLimit, extraData)` on the source-chain bridge, specifying `to` as an address already blacklisted by `tokenAddress` (e.g. USDC). [5](#0-4) 
2. Tokens are pulled from `msg.sender` into the bridge and (if `modeMintBurn`) burned; a `RequestValueTransfer` event is emitted with nonce `N`. [6](#0-5) 
3. On the destination chain, operators call `handleERC20Transfer(...)` for nonce `N` with `_to` = the blacklisted address. The final `IERC20(_tokenAddress).safeTransfer(_to, _value)` (or `mint`) reverts because the token blocks the blacklisted recipient. [1](#0-0) 
4. Because the revert unwinds the entire call, `_updateHandleNonce`/`_setHandledRequestTxHash` never persist, so nonce `N` can never be marked handled, and the tokens already burned/escrowed on the source side cannot be recovered — there is no code path in `BridgeTransferERC20.sol` to redirect the payout to a different address.

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
