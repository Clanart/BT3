### Title
Unchecked Bitcoin amount arithmetic allows panic and malformed transaction creation - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` uses unchecked `u64` addition and multiplication when calculating payment totals and fees from attacker-influenced transaction parameters. [1](#0-0)  A serialized `ReceivedOutput` can also provide an arbitrary `TxOut` value because `ReceivedOutput::read` consensus-decodes the output without enforcing Bitcoin's maximum-money bound. [2](#0-1) 

### Finding Description
The vulnerable expression is `payment_sat + needed_fee`, where `payment_sat` is the unchecked sum of requested output amounts and `needed_fee` is calculated as `fee_per_vbyte * vbytes`. [3](#0-2)  Supplying `u64::MAX` as a payment amount makes this addition overflow: it panics when overflow checks are enabled and wraps to a small value when they are disabled. [4](#0-3)  In wrapping builds, the insufficient-funds check can pass even though the requested output cannot be funded, after which the resulting transaction is used for Taproot sighash signing. [5](#0-4) 

### Impact Explanation
An unprivileged party who can submit a payment amount or serialized `ReceivedOutput` can crash transaction construction or cause creation and signing of an invalid Bitcoin transaction containing an impossible output value. [6](#0-5)  The malformed transaction is rejected by Bitcoin consensus because its declared outputs exceed its real inputs, so any reported or locally tracked spendable result is unusable. [7](#0-6) 

### Likelihood Explanation
Only one `u64::MAX` payment amount is required; the code rejects only dust lower bounds and does not perform an upper-bound or checked-total check before adding the fee. [8](#0-7)  `fee_per_vbyte` multiplication is additionally unchecked, giving another direct overflow trigger through a public transaction-construction parameter. [9](#0-8) 

### Recommendation
Use `checked_add`, `checked_mul`, and `checked_sub` for all input, output, payment, and fee totals, and reject `TxOut` values or payment amounts exceeding `bitcoin::Amount::MAX_MONEY` before constructing `SignableTransaction`. [10](#0-9) 

### Proof of Concept
```rust
use bitcoin::{Amount, OutPoint, ScriptBuf, TxOut};
use bitcoin::consensus::encode::serialize;
use serai_bitcoin::wallet::{ReceivedOutput, SignableTransaction};

fn received_output(value: u64) -> ReceivedOutput {
    let mut bytes = vec![0; 32]; // zero scalar offset
    bytes.extend(serialize(&TxOut {
        value: Amount::from_sat(value),
        script_pubkey: ScriptBuf::new(),
    }));
    bytes.extend(serialize(&OutPoint::default()));

    ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}

// With overflow checks enabled, this panics at `payment_sat + needed_fee`.
// With wrapping arithmetic, `u64::MAX + needed_fee` wraps to a small value,
// allowing the insufficient-funds check to pass with a 1,000-sat input.
let tx = SignableTransaction::new(
    vec![received_output(1_000)],
    &[(ScriptBuf::new_op_return(&[]), u64::MAX)],
    None,
    None,
    1,
);
```
