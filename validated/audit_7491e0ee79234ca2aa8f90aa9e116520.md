### Title
Copilot conflict resolution splices AI hunk resolutions into the wrong conflict marker block due to mismatched hunk-boundary parsers, silently corrupting committed code - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot conflict-resolution feature uses **two independently implemented parsers** over the same untrusted, attacker-influenced file content (a file with Git conflict markers, produced by merging/rebasing a branch or PR the attacker controls): `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` (used to build the per-hunk prompt sent to the model and to validate the model's response), and `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` (used to splice the model's ordered resolutions back into the file on disk). These two functions define "what counts as a conflict block" differently and are not required to agree. When the conflicted file contains content that makes the two definitions diverge, `reassembleResolvedFile` will splice `hunkResolutions[i]` into the wrong marker block (or the wrong number of blocks), producing a file that looks fully resolved but contains silently swapped/misapplied code — exactly analogous to the Aloe `Oracle.observe` bug, where data was matched to the wrong array slot because index bookkeeping wasn't validated against the underlying data's real boundaries.

### Finding Description
The two relevant parsers:

`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file, and for each `<<<<<<<` marker:
- Collects "ours" lines until the **first** `|||||||` or `=======` line.
- If diff3, collects "base" lines until the next `=======`.
- Collects "theirs" lines until the **first** `>>>>>>>` line.

This produces `N` hunks, which are sent to the model as "Conflict 1 of N", "Conflict 2 of N", etc., and the count is enforced by `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`), which throws only if the *count* of returned hunks doesn't match `expectedHunkCounts` — it does not (and cannot) verify hunk *boundaries* match.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) re-scans the same raw file content independently:
```javascript

  ...
  const resolved = hunkResolutions[hunkIndex].resolvedContent

This function has **no knowledge of diff3 `|||||||` markers, no protection against extra `=======`/`>>>>>>>`-shaped lines that are ordinary file content, and stops scanning at the very first line matching `^>{7}(?:\s|$)`**, regardless of whether a real separator was seen before it. `extractConflictHunks` has different (and more permissive/robust) boundary logic (e.g., it explicitly breaks on the *first* `======= `/`|||||||` for the "ours" section, tracks diff3, and skips genuinely malformed unterminated hunks) [2](#0-1) [3](#0-2) .

Because both functions run over file content that originates from the *incoming* (attacker-controlled) side of a merge/rebase, a crafted file can be built so that:
1. `extractConflictHunks` correctly finds `N` well-formed conflict hunks (so the model is asked for, and returns, `N` resolutions, passing `validateResolutionPaths`'s count check), while
2. `reassembleResolvedFile`'s independent, cruder scan finds a *different* set of block boundaries for the same raw text — e.g. because the "theirs" or "ours" content of one hunk itself contains a line that happens to match `^>{7}(?:\s|$)` (seven `>` characters) or `^={7}$` (seven `=` characters). Such lines are entirely plausible as legitimate file content (ASCII-art dividers, changelog underlines, ownership banners, minified diff-like fixtures, `git diff` example content, README sections, etc.) and are trivial for the attacker to insert deliberately into their branch/PR.

When the two counts/boundaries diverge, `hunkIndex` in `reassembleResolvedFile` drifts out of sync with the model's actual per-hunk intent, so `hunkResolutions[hunkIndex].resolvedContent` — text the model wrote to resolve *conflict K* — gets spliced into the location of a *different* conflict block (or a block that shouldn't be replaced at all), or a genuine conflict block is left with an out-of-range `hunkIndex` and silently dropped (`if (hunkIndex < hunkResolutions.length)` — no error is thrown, the block is just left empty) [4](#0-3) .

No existing guard checks that the reassembled file corresponds to the intended resolutions: `validateResolutionPaths` only validates counts against `extractConflictHunks`'s count, never against `reassembleResolvedFile`'s independent count [5](#0-4) . The only sanity check on resolved content is a regex rejecting *literal, unmodified* conflict markers in the model's own output [6](#0-5)  — it does nothing to verify that the LLM output was spliced into the *correct* location.

### Impact Explanation
This is a silent corruption of what the user commits — the most severe listed impact category. The user runs "Resolve with Copilot" on a merge/rebase involving a branch or PR they don't fully control (e.g., a contributor's PR, a dependency's fork, an upstream branch), reviews a "resolved" file that appears syntactically plausible, and commits/pushes it. In reality, code intended for one conflict block has been written into another location, or a real conflict's resolution has been silently dropped, without any error, warning, or diff mismatch surfaced to the user — the reassembled file is presented as final content ready to write to disk (`IFileResolution.resolvedContent`) [7](#0-6) . Depending on which lines are swapped this can range from broken/wrong logic (e.g. a permission check moved to the wrong function) to reintroducing code the resolution was supposed to remove, all committed and pushed without the user's knowledge.

### Likelihood Explanation
The attacker only needs to control the content of one side of a merge (a PR branch, a fork, or an upstream repo file) that a Desktop user later merges/rebases and resolves via Copilot — no local access, no credentials, and no unnatural user steps beyond the normal "resolve conflicts with AI" workflow the feature is designed for. Crafting a file whose legitimate-looking content contains a line of exactly seven `>` or `=` characters is trivial and stealthy (e.g., burying it in a comment banner, table separator, or changelog entry far from the actual conflicting code), so it does not require the user to notice anything unusual before triggering the bug.

### Recommendation
Make `reassembleResolvedFile` share the exact same boundary-detection logic as `extractConflictHunks` (ideally have both derive from a single shared parser), including diff3 (`|||||||`) awareness and identical first-match semantics for `=======`/`>>>>>>>`. After reassembly, re-run the shared hunk detector over the final reassembled content and assert that (a) the number of conflict blocks found by `reassembleResolvedFile` equals the number originally extracted by `extractConflictHunks`, and (b) zero conflict-marker patterns remain in the final output; throw `CopilotValidationError` and fall back to marking the file as skipped/manual-resolution if either check fails, rather than silently writing a possibly-misassembled file.

### Proof of Concept
1. Attacker pushes a branch/PR containing a file, e.g. `notes.md`, with two real conflicts and, inside the "theirs" section of conflict #1, an innocuous-looking line consisting of exactly seven `>` characters (e.g. a markdown blockquote artifact or divider: `>>>>>>>` with no trailing text after the required whitespace, or with trailing text matching `^>{7}(?:\s|$)`):
```
<<<<<<< HEAD
ours-1
=======
theirs-1
>>>>>>>  spurious-marker-like-content
still theirs-1
>>>>>>> feature
middle
<<<<<<< HEAD
ours-2
=======
theirs-2
>>>>>>> feature
```
2. `extractConflictHunks` sees the first `<<<<<<<`, collects ours until the real `=======`, then collects theirs until the **first** line matching `theirsMarker` — the spurious `>>>>>>>  spurious-marker-like-content` line — ending hunk 1 early and leaving `still theirs-1` / `>>>>>>> feature` as unmatched trailing content that gets re-scanned as the start of a new (malformed, no `<<<<<<<`) region, then correctly finds hunk 2. Net effect: `extractConflictHunks` returns 2 hunks but with hunk 1's `theirsContent` truncated, or (depending on exact spacing) returns a count that still matches the naive expectation while boundaries are shifted.
3. The model is asked for exactly 2 resolutions matching "Conflict 1 of 2" / "Conflict 2 of 2", and returns 2 valid resolutions — passing `validateResolutionPaths`'s count check.
4. `reassembleResolvedFile` performs its own independent scan (no diff3 knowledge, no special-casing) and, hitting the same spurious `>>>>>>>` line first, closes hunk 1's marker block there too, but at a *different absolute line offset* than what `extractConflictHunks` sent to the model — so the "ours"/"theirs" text `hunkResolutions[0].resolvedContent` was written against does not correspond to the text actually spliced out at that location, and everything from `still theirs-1` onward is now copied through as literal orphaned file content (including the leftover `>>>>>>> feature` marker) instead of being replaced, while hunk 2's resolution shifts into place around a different set of surrounding lines than the model believed it was editing.
5. The final `resolvedContent` is written to disk and can be committed as-is; the file is not guaranteed to be free of conflict markers or to reflect the model's intended edits, and no error is raised anywhere in this pipeline.

I was not able to execute this end-to-end in a live Desktop build (no filesystem/runtime access in this mode), so the exact drift amount depends on precise spacing of the crafted trigger line; the structural mismatch between the two independent parsers over the same untrusted input, and the absence of any cross-check between them, is confirmed directly from the source shown above.
