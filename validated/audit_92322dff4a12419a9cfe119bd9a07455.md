### Title
Hookify plugin hooks fail open on any parsing/runtime error, silently bypassing configured `block` rules for dangerous Bash/file operations - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The Asymmetry `SafEth` bug class ("a malfunctioning/untrusted component that is looped over during a critical operation cannot be removed, so the whole operation fails or behaves unexpectedly, harming the user") maps onto the `hookify` plugin's `PreToolUse`/`PostToolUse`/`Stop` hook executors. Instead of DoS'ing the operation when a rule malfunctions, these hooks do the opposite and more dangerous thing: they **fail open**, silently allowing the tool call to proceed whenever the rule engine or config loader throws any exception, or whenever the rule file becomes unparsable — even though the user configured a `block` rule specifically to deny that exact operation.

### Finding Description
`hookify` is a bundled Claude Code plugin that lets an unprivileged project user define `PreToolUse` block/warn rules in `.claude/hookify.*.local.md` files (e.g., "block `rm -rf`", "block edits to `.env`"). These rules are the analog of the `SafEth` "derivative": individually addable/toggleable but with no safe way to quarantine a single malfunctioning rule without silently affecting the security guarantee of the whole set.

The `PreToolUse` executor wraps rule loading and evaluation in a blanket `try/except Exception`, and unconditionally exits `0` (meaning "allow") in the `finally` block, regardless of whether an exception occurred: [1](#0-0) 

The comment even states the intent explicitly: *"On any error, allow the operation"* / *"ALWAYS exit 0 - never block operations due to hook errors."* The same fail-open pattern exists in `posttooluse.py` and `stop.py`.

This means any of the following malfunctions in a *single* rule file silently disables **all** configured deny/block protections for that hook event, with no way for a user to detect it happened at tool-call time:
- A malformed regex pattern that raises `re.error` outside the guarded path (config parsing in `config_loader.py` is guarded per-file, but the `RuleEngine` itself only guards `_regex_match`; other unexpected exceptions inside `evaluate_rules`/`_rule_matches`/`_extract_field`/`_check_condition` propagate up to `main()` in `pretooluse.py` and hit the blanket `except Exception` → allow).
- A `.local.md` file with unusual encoding, a corrupted transcript path, or any dependency import failure (`ImportError` at module load time also exits 0 and allows).
- Any future bug in the hand-rolled YAML-like frontmatter parser (`extract_frontmatter` in `config_loader.py`, lines 87–195) that throws an uncaught type not in the guarded exception list at line 232/236 of `config_loader.py` isn't actually a total bypass since that's guarded — but the equivalent unguarded exceptions in `rule_engine.py`'s `evaluate_rules` flow are not caught anywhere except by the outer blanket handler that resolves to "allow."

There is no mechanism analogous to disabling/removing a single malfunctioning derivative while keeping the others active: a broken rule doesn't just fail to enforce itself — it takes down enforcement for the entire tool call, and does so by defaulting to **allow** rather than deny.

### Impact Explanation
This is a concrete approval-bypass vulnerability, not merely a DoS/availability bug. A user relies on `hookify` `block`-type `PreToolUse` rules as a safety net (e.g., "always block writes to `.env`", "always block `rm -rf`" — these are the exact example rules shipped in the plugin's own docs, see [2](#0-1)  and [3](#0-2) ). If any single rule file becomes malformed or triggers an unhandled exception in the rule engine, the deny decision that should have blocked a dangerous Bash command or sensitive file edit is silently skipped, and the tool call is allowed to execute — directly resulting in unauthorized shell/file actions that the user explicitly configured to be blocked. Because failures are only logged to `systemMessage`/stderr (not surfaced as a hard error), the user may not notice their safety rule silently stopped protecting them.

### Likelihood Explanation
Likelihood is moderate-to-high: the loader's own hand-rolled YAML-subset parser (`extract_frontmatter`) is fragile (manual indentation/state-machine parsing, no real YAML/JSON schema validation), so a user or malicious contributor lightly editing a `.local.md` rule file (e.g., unusual quoting, nested list edge case, invalid regex passed through untested paths in `_extract_field`) can trigger the fail-open path without any special privilege — this exactly parallels the external report's "external dependency malfunctions/is compromised" trigger for the `WstEth` derivative, except here the "untrusted" component is a user-authored config file processed by a fail-open hook.

### Recommendation
Change the fail-safe behavior for hookify's `PreToolUse` (and ideally `PostToolUse`/`Stop`) executors so that any rule-loading or rule-evaluation error that could affect a `block`-type rule **denies** (or at minimum, `ask`s for confirmation) rather than silently allowing the tool call, and surfaces a hard, visible warning distinguishing "no rules matched" from "rule evaluation failed." Additionally, provide per-rule isolation so a parsing failure in one `.claude/hookify.*.local.md` file does not suppress evaluation of the other valid rules (analogous to being able to disable a single malfunctioning derivative without disabling the whole set), and add stricter validation/linting of rule files at write time (`/hookify:configure`) to reduce the chance of malformed rules reaching the fail-open hook path at runtime.

### Proof of Concept
1. Create a hookify block rule intended to prevent destructive commands, e.g. `.claude/hookify.warn-dangerous-rm.local.md` with `action: block`, `event: bash`, `pattern: rm\s+-rf` (as shown in the plugin's own examples, [4](#0-3) ).
2. Introduce a malfunction that causes an unguarded exception during rule evaluation (e.g., a crafted `tool_input` field value or edge case in `_extract_field`/`_check_condition` in `rule_engine.py` that raises `AttributeError`/`TypeError` not caught by the narrow `except re.error` in `_regex_match`), or corrupt the rule file so `config_loader.load_rule_file` raises inside a code path not covered by its guarded exception types.
3. Run a Bash tool call containing `rm -rf <target>`. The `PreToolUse` hook (`plugins/hookify/hooks/pretooluse.py`) catches the resulting exception in its blanket `except Exception` handler, prints only a `systemMessage`, and unconditionally `sys.exit(0)`, which is interpreted as "allow" by Claude Code's hook contract — the destructive command executes despite the configured `block` rule. def main():
```python
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

## Troubleshooting

**Rule not triggering:**
1. Check rule file exists in `.claude/` directory (in project root, not plugin directory)
2. Verify `enabled: true` in frontmatter
3. Test regex pattern separately
4. Rules should work immediately - no restart needed
5. Try `/hookify:list` to see if rule is loaded

**Import errors:**
- Ensure Python 3 is available: `python3 --version`
- Check hookify plugin is installed

**Pattern not matching:**
- Test regex: `python3 -c "import re; print(re.search(r'pattern', 'text'))"`
- Use unquoted patterns in YAML to avoid escaping issues
- Start simple, then add complexity

**Hook seems slow:**
- Keep patterns simple (avoid complex regex)
- Use specific event types (bash, file) instead of "all"
- Limit number of active rules

## Pattern Syntax

Use Python regex syntax:
- `\s` - whitespace
- `\.` - literal dot
- `|` - OR
- `+` - one or more
- `*` - zero or more
- `\d` - digit
- `[abc]` - character class

**Examples:**
- `rm\s+-rf` - matches "rm -rf"
- `console\.log\(` - matches "console.log("
- `(eval|exec)\(` - matches "eval(" or "exec("
- `\.env$` - matches files ending in .env

## Important Notes

**No Restart Needed**: Hookify rules (`.local.md` files) take effect immediately on the next tool use. The hookify hooks are already loaded and read your rules dynamically.

**Block or Warn**: Rules can either `block` operations (prevent execution) or `warn` (show message but allow). Set `action: block` or `action: warn` in the rule's frontmatter.

**Rule Files**: Keep rules in `.claude/hookify.*.local.md` - they should be git-ignored (add to .gitignore if needed).

**Disable Rules**: Set `enabled: false` in frontmatter or delete the file.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)

            return bool(regex.search(text))
```
