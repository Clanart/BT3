## Title
Renamed-file diff view compares against the index instead of HEAD, silently hiding staged changes from the commit preview — ([File: app/src/lib/git/diff.ts])

### Summary
This is a direct structural analog of the reported bug class: one code path (the diff *shown to the user*) reads its "reference point" from the git index, while the code path that actually determines the *committed content* (full working-directory content for "select all" files) is effectively benchmarked against `HEAD`. For renamed files, Desktop's own developers flagged this discrepancy in-line but shipped it anyway, exactly mirroring the "acknowledged, will refactor later" disposition in the original report.

### Finding Description
`getWorkingDirectoryDiff` in [1](#0-0)  branches on file status to decide what to diff the working tree against:

- New/untracked files: `git diff --no-index /dev/null <file>` (correct baseline: nothing).
- Renamed files: `git diff -- <file>` with **no ref**, which diffs the working tree against the **index**, not `HEAD`.
- Everything else: `git diff HEAD -- <file>` (correct baseline: last commit).

The code explicitly documents why the renamed-file case is wrong: [2](#0-1) 

That is, if the index already contains staged bytes for the renamed path that differ from `HEAD` (added outside of the diff-rendering flow — e.g. leftover state from an interrupted rebase/merge, a `git add` run outside Desktop, or any git plumbing operation that leaves the index ahead of `HEAD` for that path), the Changes view will compute "working tree vs index" and can show little or no diff, even though the true delta relative to `HEAD` (what will land in the next commit) is large.

Meanwhile, the actual commit path uses a completely different, unrelated reference: `stageFiles` in [3](#0-2)  stages files whose selection is `DiffSelectionType.All` by running `update-index` on the full **working-directory** file content — not the index snapshot the diff was computed against. `createCommit` in [4](#0-3)  first calls `unstageAll`, then `stageFiles`, so the commit that is produced reflects the on-disk working-directory content compared against `HEAD` — a different comparison than the one the user was shown in the Changes pane before clicking "Commit".

This is structurally identical to the reported contract bug: a validation/preview step (`getMarkPrice` using the on-chain index price / here, the diff view using the index) is computed from a different reference than the step that actually executes/settles (the keeper-supplied fill price / here, the working-directory content compared to `HEAD` at commit time).

### Impact Explanation
If exploited, this causes **silent corruption of what the user believes they are committing**: a user reviewing a renamed file in the Changes pane can see "no changes" or a small, benign diff while the resulting commit (and any subsequent push) actually contains unreviewed content diverging from `HEAD`. This falls squarely within the "silent corruption of what the user commits or pushes" impact category, since the user has no visual indication that the committed diff differs from what they approved.

### Likelihood Explanation
The likelihood is constrained by how an attacker can get the local index into a stale/ahead-of-HEAD state for a renamed path without local/physical access or prior malware — the report does not establish a concrete, remotely-triggerable way (e.g., via a crafted cloned repository or fetch response) to pre-seed the git index in this exact way through normal Desktop operations alone. This is a real, developer-acknowledged inconsistency in the diff-vs-commit reference point, but a fully attacker-controlled remote trigger path (matching the "Valid Impact" bar) is not established from local code alone.

### Recommendation
For renamed files, compute the working-directory diff against the blob at `HEAD:<oldPath>` (as the code comment itself suggests, e.g., via `hash-object`/`git diff <blob> <blob>`) rather than against the current index, so the diff shown to the user always matches what a "select all" commit will actually produce.

### Proof of Concept
Not constructable purely from local code without an established attacker-controlled trigger for pre-staging index content ahead of `HEAD`; the discrepancy itself is directly demonstrable by inspecting [2](#0-1)  and comparing it against the commit staging logic in [3](#0-2)  and [5](#0-4) .

/**
 * Render the diff for a file within the repository working directory. The file will be
 * compared against HEAD if it's tracked, if not it'll be compared to an empty file meaning
 * that all content in the file will be treated as additions.
 */
export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
