### Title
Missing zero/invalid-beneficiary validation in `IntentGatewayV2.withdraw()` allows escrowed funds to be sent to `address(0)` on refund/redeem settlement - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirrored in `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The Intent Gateway's internal `withdraw()` function, which is the single execution path for both order **fills** (`RedeemEscrow`) and order **refunds/cancellations** (`RefundEscrow`), decodes a `beneficiary` address from an ISMP message and immediately transfers escrowed native/ERC-20 tokens to it with no check that `beneficiary != address(0)`. This is the exact bug class from the referenced FETH.sol report: a withdrawal/settlement path that trusts a caller/message-encoded recipient address without validating it isn't the zero address.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is called from `onAccept()` (for `RedeemEscrow`/`RefundEscrow`) and from `onGetResponse()` (for source-chain cancellation): [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
```

There is no `if (beneficiary == address(0)) revert ...` guard, unlike the pattern applied elsewhere in the same codebase for administrative fund flows (e.g. `SimplexPaymaster._setParams` explicitly checks `treasury == address(0)`) [2](#0-1) , and unlike the bandwidth-manager withdrawal docs, which explicitly name the beneficiary as validated input.

The non-EVM-standard low-level `.call{value: amount}("")` to `address(0)` **succeeds** (returns `sent = true`), so a native-token refund/redeem to a zero beneficiary silently burns the funds rather than reverting. For ERC-20 tokens, behavior depends on the token (many revert on transfer-to-zero, but this uses raw `.call` + generic success check, not `safeTransfer`, so any token that permits a zero-address transfer will also silently burn funds).

`beneficiary` in `WithdrawalRequest` originates from `order.user` (set once at `placeOrder` time by the order creator) for the `RefundEscrow`/cancel paths: [3](#0-2) 

The escrow-release invariant stated in the docs — "the refund always goes to `order.user`" — is enforced against redirection by third parties, but nothing in the reviewed code path enforces that `order.user` (and therefore the eventual `beneficiary`) is non-zero at either `placeOrder` or at settlement time.

### Impact Explanation
If an order is created (or a fill/cancel message is otherwise produced) with a zero-value `beneficiary`/`order.user`, the corresponding escrowed principal, transaction fees, and/or fill proceeds are transferred to `address(0)` and permanently lost — matching the "loss of funds" impact class explicitly called out by the Hyperbridge Pivots ("Bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount"). This affects the same `withdraw()` code path used by both cross-chain fill settlement and cross-chain cancellation/refund, so it can burn either solver proceeds or user refunds.

### Likelihood Explanation
Likelihood depends on whether `placeOrder()` validates `order.user != address(0)` before escrowing funds; within the available search budget I was not able to locate or rule out such a check in `placeOrder()` (the grep for `placeOrder`/zero-address validation in `evm/src/apps/IntentGatewayV2.sol` did not return the function body before the tool budget was exhausted). If no such upstream check exists, the class of user error is directly analogous to the original FETH `withdrawFrom` finding (self-inflicted or accidental zero address, still judged medium severity and fixed). This should be treated as **unconfirmed pending verification** of `placeOrder()`'s input validation — a Devin session with full file access should read `evm/src/apps/IntentGatewayV2.sol::placeOrder` and `IntentsBase.sol` in full to confirm whether `order.user == address(0)` is currently reachable.

### Recommendation
Add an explicit guard in `withdraw()` (and any other beneficiary-consuming settlement path) so that a decoded zero-address beneficiary reverts before transferring value, e.g.:
```solidity
if (beneficiary == address(0)) revert InvalidBeneficiary();
```
Additionally validate `order.user != address(0)` (and any `msg.sender` used as `beneficiary` in fill paths) at `placeOrder()` so that a malformed order can never enter escrow in the first place.

### Proof of Concept
Conceptual PoC (requires confirming `placeOrder` does not already rejects `order.user == 0`):
1. User calls `placeOrder()` with `order.user = bytes32(0)` and valid `inputs` (escrow accepted since no explicit check was found blocking this).
2. After `order.deadline`, anyone calls `cancelOrder()` on the destination chain (`_cancelFromDest` permits any caller post-deadline).
3. This dispatches a `RefundEscrow` message with `beneficiary = order.user = bytes32(0)`.
4. On the source chain, `onAccept()` → `withdraw()` transfers the escrowed native/ERC-20 tokens to `address(0)`, permanently burning them. [4](#0-3)
