## Title
Stale line-selection reused against a freshly re-fetched diff can silently stage/commit different content than the user selected - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop's partial-commit ("stage selected lines") feature separates *when the user selects lines to commit* from *when the patch is actually built and applied*. The line selection (`DiffSelection`) is captured against a diff shown earlier in the UI, but `applyPatchToIndex` re-reads the diff from disk at staging time and blindly re-applies the old, index-based selection to it, using a context-free (`--unidiff-zero`) patch. If the tracked file's on-disk content changes between the moment the user reviews/selects lines and the moment Desktop stages the commit — something a hostile repository can trigger via a git hook or a build/watch tool it ships — Desktop will silently stage and commit different lines than what the user actually reviewed and approved, with no error surfaced.

### Finding Description
`applyPatchToIndex` re-fetches the diff from the working directory at staging time: [1](#0-0) 

That freshly fetched `diff` is then combined with the file's *pre-existing* `DiffSelection` object (captured earlier, when the user interacted with the Changes/diff view) to build the patch: [2](#0-1) 

`formatPatch` walks `diff.hunks` (the new diff) and calls `file.selection.isSelected(absoluteIndex)` (the old selection) purely by numeric line index — there is no check that the content at that index still corresponds to what the user actually saw and selected. The resulting patch is applied with `git apply --cached --unidiff-zero --whitespace=nowarn -`, i.e. a **zero-context** patch that git will place using line numbers alone rather than verifying surrounding context, and warnings about mismatches are actively suppressed by `--whitespace=nowarn`.

This is invoked from `stageFiles` for every partially-selected file right before `createCommit` calls `git commit`: [3](#0-2) [4](#0-3) 

The files/selections passed into this pipeline come from the in-memory `repositoryStateCache`, which is only reconciled with a new diff when the user is actively viewing that file and Desktop pushes a refresh — not guaranteed to happen atomically right before commit: [5](#0-4) [6](#0-5) 

The broken invariant mirrors the report's core issue: Desktop *assumes* that a successful, exit-code-0 `git apply` means "the patch that was applied is the patch the user intended," the same way the Cairo contract assumed a non-reverting `transfer`/`transferFrom` meant "the transfer that happened is the transfer that was requested." Neither system validates that the semantic effect of the operation matches the caller's expectation — only that the syscall/RPC didn't hard-fail.

### Impact Explanation
Because `git apply` with `--unidiff-zero`/`--whitespace=nowarn` will succeed as long as the target line numbers exist in the file, a shifted or altered file will still apply cleanly — just against the wrong lines. The user could review a diff, deliberately exclude a sensitive line (e.g. a secret, a debug flag, or a malicious payload injected by the attacker), click Commit, and unknowingly commit and push exactly the line they thought they excluded (or vice versa — include a line they didn't intend), because the file content moved between review and staging. This is a silent corruption of what the user commits, with no error dialog, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitation requires only that the user open a repository under attacker influence (cloned/fetched, containing hooks/build tooling) and use Desktop's line/hunk partial-staging UI, which is a normal, expected workflow (no privileged/local/physical access, no malware, no credentials needed). The attacker-controlled trigger is a git hook (e.g. `post-checkout`, `post-merge`) or a background tool the repository instructs the user to run (already a hooks execution path Desktop explicitly intercepts, e.g. in `createCommit`'s `interceptHooks`), giving the attacker a natural window to mutate a tracked file's content between diff display and staging without any unnatural steps from the user.

### Recommendation
Before building the patch in `applyPatchToIndex`, verify that the diff used to derive the selection is still valid for the file being staged (e.g., compare a content hash/mtime captured when the selection was made, or re-diff and reject/re-prompt if hunks changed) instead of blindly trusting that a zero-exit-code `git apply` implies correctness. At minimum, drop `--whitespace=nowarn`/`--unidiff-zero` in favor of a context-bearing patch and surface any apply anomalies to the user rather than silently proceeding, so the effect of the operation is validated rather than merely its exit status.

### Proof of Concept
1. Clone a hostile repository containing a `post-checkout` hook (or a background watcher script referenced in its README/build instructions) that rewrites a tracked file's content shortly after checkout.
2. In Desktop, open the file's diff, deselect a specific line (e.g., a line containing `DEBUG=true`) intending to keep it out of the commit.
3. Before clicking "Commit," let the attacker's hook/process rewrite the file so the line the user deselected shifts position or is duplicated elsewhere in the file.
4. Click "Commit to <branch>" — `stageFiles` → `applyPatchToIndex` re-fetches the diff (now different from what was shown), reuses the stale `DiffSelection` indices, and `git apply --cached --unidiff-zero --whitespace=nowarn` succeeds.
5. Inspect the resulting commit: it contains the line the user explicitly excluded (or omits content the user intended to include), with no error shown to the user.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
