### Title
Malicious FROST preprocess forces the Bitcoin `Schnorr` algorithm's `hram` to panic on an identity aggregate nonce, aborting signing — (File: networks/bitcoin/src/crypto.rs)

### Summary
The tonic advisory is a remotely-triggered denial of service: an attacker-controlled input drives the server into an error path that terminates the process. The analog in Serai is a panic reachable from attacker-controlled FROST preprocess bytes. `Hram::hram` (BIP-340) in `networks/bitcoin/src/crypto.rs` calls `x(&R)` and `x(&A)`, which `expect("point at infinity")` if the aggregate nonce `R` is the point at infinity. Although `Curve::read_G` rejects identity for each *individual* commitment point, nothing prevents the *sum* of binding-factor-weighted commitments from being identity, so a malicious participant can craft a preprocess that makes the aggregate nonce identity and crashes every signer's machine when `sign_share` is invoked.

### Finding Description
`TransactionSignMachine::sign` in `networks/bitcoin/src/wallet/send.rs` (lines 355–398) reads each participant's `Preprocess` via `read_preprocess` (line 351–353), which deserializes attacker-controlled commitment points with `Secp256k1::read_G`. `Curve::read_G` (crypto/frost/src/curve/mod.rs lines 125–131) rejects identity only per-point. During `sign_share`, `Schnorr::sign_share` in crypto/frost/src/algorithm.rs (line 208) computes `c = H::hram(&nonce_sums[0][0], &params.group_key(), msg)`, where `nonce_sums[0][0]` is `Σ_i (D_i + ρ_i·E_i)` over all included participants. `Hram::hram` (networks/bitcoin/src/crypto.rs lines 59–73) calls `x(R)` (lines 13–16), which does `encoded.x().expect("point at infinity")` — a panic when `R` is identity. The doc comments on `Hram` (line 54) and `Schnorr` (line 78) acknowledge the panic but assume negligible probability for "a well-reasoned caller" — however, the aggregate nonce is attacker-influenceable, not random.

An attacker computes their preprocess after seeing all other preprocesses (they are broadcast). They fix arbitrary non-identity `E_i`, compute their binding factor `ρ_i` over the full commitment set, and set `D_i = −(S_others + ρ_i·E_i)`, where `S_others` is the sum of all other participants' weighted contributions. Both `D_i` and `E_i` are non-identity (so they pass `read_G`), but the aggregate `R` is identity. `x(R)` then panics inside `Sha256` challenge computation, unwinding through `sign` — a clean, remotely-triggered DoS of the transaction-signing protocol on every honest participant's processor.

### Impact Explanation
Any signer set containing one malicious participant can deterministically crash `TransactionSignMachine::sign` on all honest processors attempting a Bitcoin spend. This halts all withdrawals/payments for that multisig session — a permanent, repeatable liveness failure triggered purely by bytes sent to `read_preprocess`, directly analogous to tonic's accept-loop exit on a hostile stream.

### Likelihood Explanation
Deterministic: the attacker fully controls their two commitment points, sees all other commitments before `sign` is called (commitments are exchanged before signing), and can compute `ρ_i` locally since `hash_binding_factor` binds the full serialized commitment set. No probabilistic element is involved, unlike the identity-individual-commitment case which is rejected by `read_G`.

### Recommendation
In `Hram::hram` (or the `Schnorr` `Algorithm` impl), return an error/`None` when `R` or `A` is identity instead of panicking; alternatively, have `AlgorithmSignMachine::sign`/`complete` check `nonce_sums[0][0].is_identity()` and return `FrostError` before invoking `hram`. More broadly, the signing machine should reject preprocess sets whose binding-factor-weighted nonce sum is identity.

### Proof of Concept
1. Honest signers broadcast `Preprocess` values `(D_j, E_j)`; attacker receives them via `read_preprocess`.
2. Attacker picks any non-identity `E_a`, serializes the full commitment set, computes `ρ_a = Secp256k1::hash_binding_factor(binding)` per the FROST binding-factor transcript, then sets `D_a = −(Σ_j (D_j + ρ_j·E_j) + ρ_a·E_a)`.
3. Attacker broadcasts `(D_a, E_a)`. `Curve::read_G` accepts both (non-identity).
4. On `TransactionSignMachine::sign`, `nonce_sums[0][0] = identity`, `Hram::hram` calls `x(&identity)`, `to_encoded_point(true).x()` returns `None`, and `expect("point at infinity")` at `networks/bitcoin/src/crypto.rs:15` panics, aborting signing on every honest participant's node.

Caveat: I verified the panic path at `crypto.rs:13–22`, `algorithm.rs:208`, and the preprocess-read path at `send.rs:351–353`, but did not exhaustively confirm that `sign` performs no upstream identity check on the summed nonce — I saw none in the files read; if one exists in `crypto/frost/src/sign.rs`, this reduces to a no-impact rejection.
