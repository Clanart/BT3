### Title
Malicious git server can spoof GitHub Enterprise via forged `WWW-Authenticate` header to trigger a phishing sign-in prompt and steal OAuth/PAT credentials - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Fei Protocol bug is a case of a component (`FlywheelCore`) trusting a new dependent object (`newFlywheelRewards`) without verifying it actually points back to the caller, silently redirecting fund access to an unverified destination. The Desktop analog is in the git credential-helper trampoline: it classifies a remote endpoint as a legitimate GitHub/Enterprise host based on an **unauthenticated, attacker-controlled `WWW-Authenticate` header** returned by the git server itself, and on that basis triggers a "Sign in to GitHub Enterprise" dialog pointed at the attacker's own host — without ever verifying that the host is actually GitHub.

### Finding Description
When Desktop performs a git HTTP operation and the remote requires authentication, it forwards any `WWW-Authenticate` header(s) to the credential helper as `wwwauth[]` fields. `getEndpointKind` uses this attacker-supplied value as a trust decision: [1](#0-0) 

```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host without
// having to resort to making a request ourselves.
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
```

This value comes directly from the HTTP response of whatever server the remote URL points to — i.e., it is fully attacker-controlled (a malicious clone/fetch remote, a compromised proxy, or a MITM on an `http://` remote). No network round-trip or certificate/identity check is performed for this branch; the comment itself says this bypasses the "real" verification via `isGitHubHost()`.

Once classified `enterprise`, `getCredential` checks whether an account already exists for that endpoint. If not, it calls `promptForGitHubSignIn(endpoint)`: [2](#0-1) 

`promptForGitHubSignIn` then drives the real sign-in flow using the **attacker-controlled `endpoint`**: [3](#0-2) 

```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
this.dispatcher.showPopup({ type: PopupType.SignIn, isCredentialHelperSignIn: true, credentialHelperUrl: endpoint })
```

`setSignInEndpoint`/`setEndpoint` only validate that the URL is syntactically HTTPS (`validateURL`), not that it is actually a GitHub/GHE instance: [4](#0-3) 

If the user proceeds with browser-based OAuth, `getOAuthAuthorizationURL` and `requestOAuthToken` both operate against the attacker's `endpoint`, sending Desktop's static `ClientID`/`ClientSecret` and the authorization code directly to the attacker's server: [5](#0-4) 

The broken invariant is the same class as the Solidity report: a security-relevant "pointer" (which endpoint should be trusted as a GitHub host) is swapped based on an object the attacker fully controls (`WWW-Authenticate` response), without verifying the new value maintains the intended relationship (that it is genuinely a GitHub/GHE server) before wiring it into the trust/credential flow.

### Impact Explanation
A malicious or compromised git remote (or a MITM proxy on a plain-HTTP git operation) can, with zero user action beyond a normal `fetch`/`clone`/`push` that Desktop performs automatically (e.g. background fetching), cause Desktop to pop up an "official-looking" GitHub Enterprise sign-in dialog whose underlying network endpoint is the attacker's own server. If the user completes sign-in (browser OAuth or otherwise), the OAuth code exchange and/or resulting account/token retrieval happens against the attacker's endpoint, resulting in credential/token exfiltration and an account being bound in Desktop under attacker's control assumptions. This matches the "unauthorized OAuth or account binding" / "credential exfiltration" impact category.

### Likelihood Explanation
Any git server the user clones or fetches from — including one added later as an additional remote, or an existing `http://` remote intercepted by a network-level MITM — can trigger this by simply including a `WWW-Authenticate: Basic realm="GitHub"` header in its 401 response, which is trivial to add to any git-http-backend or reverse proxy. Desktop performs fetches automatically in the background for tracked repositories, so no explicit user click is required to reach the vulnerable code path; only completing the resulting sign-in prompt requires user interaction, which is the expected phishing step.

### Recommendation
Do not use the unauthenticated `WWW-Authenticate` header value alone to elevate trust to `enterprise`/GitHub classification. At minimum:
- Require corroboration via the existing network-verified `isGitHubHost()` check before trusting `realm="GitHub"` from a header.
- When routing into `promptForGitHubSignIn`, clearly and non-dismissably surface the exact host being contacted, and/or restrict the auto-suggested "GitHub sign-in" flow to hosts previously known/allow-listed by the user.
- Treat the `wwwauth[]` heuristic as a hint only, not sufficient by itself to switch behavior into the credential-issuing sign-in flow, mirroring the recommended fix pattern of validating that a swapped-in trusted reference genuinely corresponds back to the expected identity (as recommended for `FlywheelCore.setFlywheelRewards`).

### Proof of Concept
1. Attacker sets up a git-over-HTTP server (or a MITM proxy for a plain `http://` remote) serving any repository content.
2. On any authenticated git operation (`fetch`, `push`, or background fetch that Desktop performs automatically for a tracked repository whose remote points at this server), the server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Desktop's askpass/credential trampoline invokes `createCredentialHelperTrampolineHandler`, which parses this into `wwwauth[]=Basic realm="GitHub"` and calls `getEndpointKind`, returning `'enterprise'` purely from this header. [1](#0-0) 
4. Since no account exists for the attacker's endpoint, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)` with the attacker's own URL. [2](#0-1) 
5. `promptForGitHubSignIn` starts an Enterprise sign-in flow bound to the attacker's origin and shows the standard Desktop "Sign in" dialog. [6](#0-5) 
6. If the user proceeds (browser OAuth or credential entry), the resulting token exchange (`requestOAuthToken`) is sent to the attacker's server, exfiltrating the OAuth code/client secret and ultimately any token issued. [7](#0-6)

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }

export function getOAuthAuthorizationURL(
  endpoint: string,
  state: string
): string {
  const urlBase = getHTMLURL(endpoint)
  const scope = encodeURIComponent(oauthScopes.join(' '))

  return new window.URL(
    `/login/oauth/authorize?client_id=${ClientID}&scope=${scope}&state=${state}`,
    urlBase
  ).toString()
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
