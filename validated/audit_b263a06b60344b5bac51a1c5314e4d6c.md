### Title
Unchecked `payment_sat + needed_fee` overflow in `SignableTransaction::new` silently bypasses the `NotEnoughFunds` check, producing a signed transaction that spends more than its inputs - (networks/bitcoin/src/wallet/send.rs)

### Summary
The analog of the reported bug — an overflow guard that checks the wrong bound (or no bound at all), letting a wrapping/silent overflow defeat the intended safety check — exists in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`. The funding check `input_sat < (payment_sat + needed_fee)` and the fee multiplication `fee_per_vbyte * vbytes` are plain u64 arithmetic on values that include attacker-influenced `payments` amounts. Just as `timeBucket * timeCoefficient` could exceed `type(int256).max` while passing the `type(uint256).max` bound check, `payment_sat + needed_fee` can exceed `u64::MAX` and wrap to a small value, passing the insufficient-funds check entirely.

### Finding Description
In `SignableTransaction::new`:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
...
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
...
let mut needed_fee = fee_per_vbyte * vbytes;
...
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

- `payment_sat` is an unchecked `sum::<u64>()` of all `payments[i].1` (line 187); `input_sat` is similarly summed (line 175). Neither uses `checked_add`/`checked_sum`.
- `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change = fee_per_vbyte * vbytes_with_change` (line 227) are unchecked multiplications of caller-supplied `fee_per_vbyte` with computed vbytes.
- The guard `input_sat < (payment_sat + needed_fee)` (line 215) adds before comparing — the exact same shape as `timeBucket > type(uint256).max / timeCoefficient` guarding a product that still overflows downstream. If `payment_sat` is near `u64::MAX`, `payment_sat + needed_fee` wraps (release) or panics (debug); in the wrapping case the comparison is evaluated against the wrapped (small) value, so the `NotEnoughFunds` rejection is skipped.
- The change path (line 228) does use `input_sat.checked_sub(payment_sat + fee_with_change)` — but the inner `payment_sat + fee_with_change` itself can wrap *before* `checked_sub` runs, making the checked subtraction meaningless: `input_sat - wrapped_small` succeeds and produces a "change" output of `input_sat - small`, while `tx_outs` still contains the huge payment.
- The resulting `SignableTransaction` is passed to `multisig()` and `TransactionSignMachine::sign`, where each input's taproot sighash is signed via `sig.sign(...)` (lines 383–391). The multisig will faithfully threshold-sign a transaction whose outputs exceed its inputs — an invalid transaction that can never confirm, yet consumes a signing session and the `SignCompleted`/plan flow downstream.

`payments` and `fee_per_vbyte` are derived from spend instructions (InInstruction-style data flowing through the processor), so an unprivileged party who can cause a spend with crafted large amounts or a crafted fee rate reaches this path with public inputs.

### Impact Explanation
- With wrapping arithmetic (release build): the `NotEnoughFunds` guard is bypassed, producing a `SignableTransaction` whose `tx.output` values exceed `tx.input` prevout values. The threshold group then produces valid Schnorr signatures over the sighashes of a transaction that is structurally invalid — a burned signing attempt, griefing of the coordinator's signing pipeline, and a `SignCompleted` event for a TX that can never be broadcast. Since `inputs` are real UTXOs belonging to the multisig, repeated triggering forces useless signature ceremonies and can wedge retries of a plan.
- With panic-on-overflow (debug or any path where the wrap panics): the node constructing the transaction crashes, a reachable DoS from attacker-supplied payment/fee values — mirroring the reported "revert almost all the time" impact.
- The class matches Medium severity of the source finding: pricing/fee/funds math defeated by an overflow the guard was meant to prevent.

### Likelihood Explanation
Reaching it requires a spend instruction whose cumulative `payments` or `fee_per_vbyte` is large enough to overflow u64 when summed/multiplied — economically absurd values (~1.8e19 sats ≫ 21M BTC), but the code performs no sanity bound on payment amounts other than the `DUST` lower bound (line 166) and the wrapping sum check itself. If any upstream layer fails to bound the total payment amount against actual balances before constructing `SignableTransaction`, a single crafted instruction triggers it. Debug builds panic deterministically; release builds silently accept. Likelihood is moderate: it depends on upstream amount validation, which is not enforced inside this function.

### Recommendation
Apply the same fix pattern as the report recommends — bound the operands *before* the arithmetic, or use checked arithmetic on the arithmetic itself:

```rust
let payment_sat = payments
  .iter()
  .try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: u64::MAX, fee: needed_fee })?;
let needed_fee = fee_per_vbyte.checked_mul(vbytes).ok_or(TransactionError::TooLowFee)?;
let total = payment_sat.checked_add(needed_fee).ok_or(TransactionError::NotEnoughFunds { ... })?;
if input_sat < total { ... }
// and inside the change branch:
let total_with_change = payment_sat.checked_add(fee_with_change).ok_or(...)?;
if let Some(value) = input_sat.checked_sub(total_with_change) { ... }
```

Also cap per-payment and total amounts against `bitcoin::policy`/`MAX_MONEY` (21M BTC) rather than relying solely on the funds comparison.

### Proof of Concept
```rust
// Release build (wrapping arithmetic):
let inputs = vec![received_output_with_value(1_000_000)]; // 0.01 BTC, real UTXO
let payments = &[
  (script_a, u64::MAX - 100), // huge crafted amount
  (script_b, u64::MAX - 100), // payment_sat wraps to ~u64::MAX - 200... 
];
// Even simpler: single payment where payment_sat + needed_fee wraps.
// Choose payment = u64::MAX - needed_fee + 1 so payment_sat + needed_fee == 0.
let payments = &[(script_a, u64::MAX - needed_fee + 1)];
// input_sat < (payment_sat + needed_fee)  =>  1_000_000 < 0  => false
// NotEnoughFunds is NOT raised; tx_outs contains a ~u64::MAX output.
// multisig() → TransactionSignMachine::sign produces valid FROST/Schnorr
// signatures over sighashes of a transaction that can never confirm.
```

Debug build instead panics on the same expression, giving a reachable crash. In both cases the guard intended to reject the spend is defeated by the overflow — the identical bug class as the `type(uint256).max` bound check in `BoundedStepwiseLogarithmicPriceAdapter::getPrice`.

Note: the exploitability ceiling depends on whether upstream callers (processor/coordinator) bound payment totals before constructing `SignableTransaction`; I was unable to fully trace those call sites within the in-scope files, so this is asserted at the `SignableTransaction::new` boundary where the unguarded arithmetic demonstrably lives.
