### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes speculative multi-megabyte allocation per call → memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts the serialized participant count `n` (a `u16` read straight from the input) and uses it to pre-allocate `Vec::with_capacity(n)` for `Interpolation::Constant` coefficients before validating `n` against `ThresholdParams` and before confirming the bytes actually exist. Each 8-byte header can therefore force an allocation of up to `65535 * size_of::<C::F>()` (~2–4 MB), enabling memory-exhaustion DoS analogous to the CVE-2021-42859 class (resource exhaustion via untrusted input).

### Finding Description
In `ThresholdKeys::read`, the reader pulls `t`, `n`, and `i` from the stream, then branches on the interpolation tag. For tag `0` (`Constant`), it does `Vec::with_capacity(usize::from(n))` and then reads `n` scalars [1](#0-0) . Crucially, `ThresholdParams::new(t, n, i)` — which would reject `t > n` or an out-of-range participant — is only invoked at the end via `ThresholdKeys::new` [2](#0-1) . So a crafted buffer with `n = 0xFFFF` and interpolation byte `0` immediately reserves ~2 MB (32-byte fields) to ~3.7 MB (ed448's 56-byte field) of heap before `read_F` even runs. The subsequent `read_F` failures free that allocation, but a caller reading many attacker-supplied key blobs (the listed `ThresholdKeys::read` sink) can be driven into repeated large transient allocations, and if the caller retains partially-read state or the input supplies the bytes, the memory is fully materialized with no upper bound other than the attacker's bandwidth.

### Impact Explanation
This is a direct memory-amplification primitive: ~10 input bytes force a multi-megabyte `Vec` reservation. An unprivileged party feeding untrusted bytes to `ThresholdKeys::read` (an explicitly in-scope sink) can repeat this in a loop to exhaust memory and crash the process, denying service — the same availability-impact class as the Mini-XML leak, realized here as untrusted-length-driven over-allocation rather than a slow leak.

### Likelihood Explanation
Reachability requires an integrator to deserialize `ThresholdKeys` from attacker-controlled bytes, which is the stated threat model for these `read_*` APIs. The amplification factor is large and constant-cost for the attacker. Since DoS-without-secret-leakage caps at Medium, this is a Medium severity analog.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new` *before* any allocation driven by `n`, replace `Vec::with_capacity(n)` with incremental `Vec::push` (allocation then tracks bytes actually present), and/or cap `n` at a protocol maximum. The same "don't pre-allocate from untrusted lengths" pattern already used in `coordinator/src/p2p.rs` (length check before `vec![0; len]`) [3](#0-2)  should be applied here.

### Proof of Concept
```rust
// For any C: Ciphersuite, e.g. C = dalek_ff_group::Ed25519
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);            // matching curve ID passes the check
buf.extend(1u16.to_le_bytes()); // t = 1
buf.extend(0xFFFFu16.to_le_bytes()); // n = 65535
buf.extend(1u16.to_le_bytes()); // i = 1
buf.push(0u8);                // Interpolation::Constant

// Vec::with_capacity(65535) is executed here before read_F ever fails:
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
// Repeat in a loop -> ~2-4 MB reserved per ~10-byte input -> OOM.
```
