### Title
Stale diff-selection indices re-applied to a freshly re-fetched diff during commit, silently including/excluding unintended lines - ([File: app/src/lib/git/apply.ts])

### Summary
`getLastMarketState`'s bug class — using state that can drift between "when selection/decision is made" and "when the calculation actually runs," without revalidating that state before performing the ordered computation — has a direct analog in GitHub Desktop's partial-commit (line/hunk selection) staging path. `WorkingDirectoryFileChange.selection` stores line inclusion decisions as *absolute line indices* computed against the diff that was rendered to the user. When the user commits, `applyPatchToIndex` re-fetches a brand-new diff from disk/git rather than reusing the diff the selection was built against, and then blindly re-applies the old absolute-index selection to the new diff's line layout.

### Finding Description
`WorkingDirectoryFileChange.selection.isSelected(absoluteIndex)` is evaluated purely by numeric line position, not by any content-anchored identity. The commit path is:

1. UI renders a diff and the user selects/deselects specific lines/hunks, producing a `DiffSelection` keyed by `absoluteIndex` positions from *that* diff.
2. On "Commit", `stageFiles` is called, which for any file with a partial selection calls `applyPatchToIndex`: [1](#0-0) 
3. `applyPatchToIndex` does **not** reuse the diff that was shown to the user. It re-runs `getWorkingDirectoryDiff` at commit time to obtain a fresh diff from the current working-tree file: [2](#0-1) 
4. That freshly fetched diff is then formatted into a patch using the *old* selection object, matching by absolute line index: [3](#0-2) 

If the file's on-disk content changes between the moment the user made their line selection in the UI and the moment `applyPatchToIndex` executes (e.g. line count/position shift caused by an auto-formatter run, a build/watch task, a git clean/smudge filter, or any other process that rewrites the tracked file), the hunk/line layout of the newly fetched diff no longer matches the layout the selection indices were computed against. `formatPatch` will then honor/deny inclusion of *different* lines than the ones the user actually reviewed and clicked, because it only checks `absoluteIndex` membership, with no revalidation that the diff is still the same one the user selected against.

There is a similar re-fetch-and-reconcile step elsewhere in the app (`selectableLines` recomputation in `app-store.ts`), but that only prunes selections against a re-rendered diff *for UI purposes when the Changes panel diff is reloaded* — it does not run in, or gate, the `stageFiles`/`applyPatchToIndex` commit path itself: [4](#0-3) 
So no guard exists on the actual staging/commit code path to detect "the diff changed since the user made this selection" before generating and applying the patch.

### Impact Explanation
This allows silent corruption of what the user actually commits and pushes — one of the explicitly valid impact categories. A user who explicitly deselects a suspicious/malicious line (e.g. from a diff introduced by a cloned/fetched repository, or content rewritten by a repo-provided auto-format-on-save/build task) can still end up including that content in the commit, or excluding content they intended to keep, without any indication in the UI that their selection no longer corresponds to the file's actual current diff layout. Since Desktop shows no re-confirmation of the patch that is about to be applied, the user has no way to notice the discrepancy before the commit (and potential push) completes.

### Likelihood Explanation
The race window is realistic in normal developer workflows: editors/IDEs with format-on-save, linters with `--fix` on save, file watchers (webpack/babel/tsc `--watch`), or repo-provided hooks/tasks (e.g. a repo shipping `.vscode/settings.json` with an auto-formatter) commonly rewrite files shortly after they are saved. An attacker who controls a fetched/cloned repository can ship such repo-level tooling config to increase the odds that a file is rewritten between the time a contributor reviews/selects diff lines in Desktop and the time they press Commit, without requiring any unnatural or out-of-band user action — editing and saving files during a review/commit is a normal step.

### Recommendation
Before generating/applying a partial-commit patch in `applyPatchToIndex`, revalidate that the freshly fetched diff (`getWorkingDirectoryDiff`) still matches the diff the `file.selection` was computed against (e.g., by comparing diff hash/line content, not just count of lines, or by anchoring `DiffSelection` to content-based identifiers instead of absolute indices). If the diff has changed, refuse to stage/commit that file's partial selection and force the UI to re-render the diff and require the user to re-confirm their selection, mirroring the "if state changed since selection began, bail out" pattern already used for the UI-facing diff reconciliation in `app-store.ts` but applying it to the commit/staging pipeline itself.

### Proof of Concept
1. Clone an attacker-controlled repository that includes a workspace/task config causing an installed editor or watch process to reformat a tracked file shortly after save (e.g. a `.vscode/settings.json` enabling `editor.formatOnSave` with a custom formatter, or an npm `watch` script the README instructs the victim to run).
2. In GitHub Desktop, open the file's diff, and deselect a specific suspicious added line (e.g. an added backdoor line) via the line-level selection UI, building a `DiffSelection` with absolute indices against the currently rendered diff.
3. Before clicking "Commit", allow the format-on-save/watch task to rewrite the file (shifting line numbers/hunks) without reopening the diff view.
4. Click "Commit". `stageFiles` → `applyPatchToIndex` re-fetches the diff (`getWorkingDirectoryDiff`, `app/src/lib/git/apply.ts:60`) and calls `formatPatch` (`app/src/lib/patch-formatter.ts:129`) using the stale `DiffSelection`'s absolute indices against the new hunk layout.
5. Inspect the resulting commit: the previously deselected malicious line (or another unintended line) is included (or an intended line is excluded), despite the UI never showing this final diff to the user for confirmation.
