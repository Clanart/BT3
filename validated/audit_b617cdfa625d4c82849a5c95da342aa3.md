Based on the evidence gathered, I found a strong local analog in `pallet-hyper-fungible-token`'s decimal-scaling helpers.

### Title
Decimal-scaling helper amplifies bridged amounts when the destination has fewer decimals than the local asset - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_erc20()` is meant to rescale a local balance into the destination ERC-20's decimal precision before it is embedded in the outbound ISMP `Message.amount`. It computes the scaling exponent with `erc_decimals.saturating_sub(local_decimals)` and only ever **multiplies**: [1](#0-0) 

If `local_decimals > erc_decimals` (local asset has more precision than the destination contract's token), `saturating_sub` clamps to `0`, so the multiplier becomes `10^0 = 1` — no down-scaling occurs at all, even though one is required.

### Finding Description
The `send()` extrinsic burns/escrows `params.amount` in local-asset units, then calls `convert_to_erc20(amount, erc_decimals, decimals)` to build the cross-chain `Message.amount` that the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint verbatim to the beneficiary: [2](#0-1) 

The benchmarking module's own comment confirms the implicit precondition this function relies on but does not enforce in the runtime path: *"`register_token` rejects an evm side with fewer decimals than the local asset, so this must stay at or below `EVM_DECIMALS`."* [3](#0-2) 

That precondition is asserted only in a benchmarking comment. Nothing in the search results shows a hard runtime check inside `register_token`/`update_token` enforcing `erc_decimals >= local_decimals` for every configured chain, and the conversion helper itself has no defensive assertion — it silently no-ops the scale-down via `saturating_sub` instead of reverting or dividing. If governance (via `CreateOrigin`, which is a privileged but not necessarily infallible or well-audited path across every chain/asset registration) ever registers a chain/asset pair where the destination ERC-20 has fewer decimals than the local Substrate asset — or if a future asset with higher local decimals is added without updating this invariant — every `send()` for that pair will emit an unscaled `amount` that is `10^(local_decimals - erc_decimals)` times too large. The destination contract's `onAccept` decodes `message.amount` and mints it directly with no independent sanity check against what was escrowed: [4](#0-3) 

This is a false-state/wrong-amount acceptance: the destination chain trusts the encoded `amount` field as authoritative, and the encoding logic is the only guard against a magnitude error. The symmetric counterpart, `convert_to_balance()`, uses the same `saturating_sub` pattern on `on_accept`/`on_timeout`, so under the same misconfiguration a mismatched direction would under-credit locally-minted amounts, compounding accounting corruption across both message directions. [5](#0-4) [6](#0-5) 

### Impact Explanation
If this decimal-ordering invariant is ever violated for any registered `(asset, chain)` pair — a plausible configuration mistake given it is enforced only by a doc comment on a benchmark helper, not a runtime assertion in the conversion functions themselves — a user's ordinary `send()` call would cause the destination `HyperFungibleToken` contract to mint an amount inflated by a power of ten relative to what was actually escrowed/burned on the source chain. This is a direct fund-creation/loss-of-peg bug: the destination-side supply becomes uncollateralized, and whoever controls the recipient address of that transfer effectively mints value out of thin air relative to the locked/burned local collateral.

### Likelihood Explanation
Medium: exploitation depends on a registration-time misconfiguration (an asset/chain pair where the EVM contract's decimals are lower than the local Substrate asset's decimals) rather than a flaw reachable purely by an unprivileged attacker manipulating dispatch inputs directly. However, unlike the original report's simple constant typo, this is a structural gap — the enforcement of the required decimal ordering lives only in a code comment for benchmarking, not as a `Result`-returning check inside `register_token`/`update_token` or inside `convert_to_erc20`/`convert_to_balance` themselves, so a single governance misstep (e.g., onboarding a 6-decimal remote token while the local asset uses 12 or 18 decimals) silently causes systematic overminting for every subsequent transfer on that route, with no in-band way for the runtime to detect or reject it.

### Recommendation
Add an explicit runtime-enforced invariant in `register_token`/`update_token` requiring `erc_decimals >= local_decimals` for every chain in a token's configuration, returning an `Error` otherwise, rather than relying on documentation. Additionally, harden `convert_to_erc20`/`convert_to_balance` to `checked_sub` (returning an error on underflow) instead of `saturating_sub`, so any future misconfiguration fails closed (dispatch/on_accept errors out) rather than silently emitting an unscaled amount.

### Proof of Concept
1. Governance registers asset `X` with `local_decimals = 18` and, for `StateMachine::Evm(N)`, sets `Precisions::<T>::insert(X, Evm(N), 6)` (a 6-decimal ERC-20 destination token) — no runtime check currently blocks this combination.
2. A user calls `send(SendParams { asset_id: X, amount: 1_000_000_000_000_000_000 /* 1.0 token, 18 decimals */, destination: Evm(N), .. })`.
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18u8) as u32)` = `10u128.pow(0)` = `1`, so `erc20_amount = 1e18` (unchanged) — instead of the correct `1e18 / 10^12 = 1_000_000` (1.0 token at 6 decimals). [1](#0-0) 
4. The outbound `Message.amount` field carries `1e18`, which the destination `HyperFungibleToken.onAccept` mints verbatim to the beneficiary — 10^12 times the intended amount for a 6-decimal token, i.e., far in excess of the 1.0 token actually escrowed/burned on the source chain.

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
