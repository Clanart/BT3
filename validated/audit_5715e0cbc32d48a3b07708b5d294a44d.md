## Finding: Unchecked ERC20 `transfer()` Boolean Return in Tron `IntentGatewayV2.withdraw()` / `SweepDust`

### Title
Unchecked ERC20 `transfer()` return value in escrow settlement causes permanent silent loss of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles cross-chain intent escrow (`withdraw()`) and dust sweeps (`SweepDust` handling in `onAccept`) using raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls, checking only that the call did not revert (`success`) but never decoding/validating the ERC20 boolean return value itself.

### Finding Description
Throughout most of the codebase, ERC20 transfers in escrow-critical paths use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which reverts on both call failure and a `false` boolean return. Examples: [1](#0-0)  and [2](#0-1) .

However, in `evm/tron/contracts/apps/IntentGatewayV2.sol` — despite importing and using `SafeERC20` elsewhere in the same file for `safeTransferFrom` calls — the escrow-redeeming `withdraw()` function and the `SweepDust` branch of `onAccept()` bypass `SafeERC20` and instead use a manual low-level call that only checks `success` (i.e. the call did not revert), not the ABI-decoded boolean payload: [3](#0-2) [4](#0-3) [5](#0-4) 

For any TRC20/ERC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (a well-documented non-conformance class, including several tokens deployed on Tron), the `success` flag from the low-level `.call` will be `true` even though no tokens were actually moved, because the call itself did not throw — only the encoded return payload signals failure.

Despite this, `withdraw()` unconditionally proceeds to finalize state:
- `_filled[body.commitment] = beneficiary;` is set unconditionally at the top of `withdraw()`.
- `_orders[body.commitment][token] -= amount;` decrements the escrow accounting right after the unchecked transfer.
- `EscrowRefunded`/`EscrowReleased` events fire as if settlement succeeded.

Because `_filled` and `_orders` are now updated to reflect a "successful" settlement, there is no path to retry or recover — the tokens remain trapped in the contract balance while the internal accounting says they were paid out, and the beneficiary can never claim them through this or any other function, since `_filled` and `_orders` are now considered up to date.

### Impact Explanation
This is a direct, code-local analog of the reported bug class ("unchecked return values of ERC20 `transfer()`"), applied to escrow settlement rather than an auction. It results in permanent, unrecoverable loss of user/solver funds escrowed in the Intent Gateway on Tron: the contract's internal state marks the order as filled/refunded and decrements escrow, while the actual token balance backing that escrow never leaves the contract and can never be re-claimed by the rightful beneficiary. This matches the required impact class "stealing or loss of funds" / "logic attacks" without requiring any malicious relayer, prover, or governance actor — it is triggered purely by ordinary settlement of an order denominated in a non-reverting, boolean-returning ERC20/TRC20 token.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: intents can be denominated in arbitrary ERC20/TRC20 tokens chosen by ordinary users placing orders (see `Order.inputs`/`Order.output.assets` token fields used throughout `fillOrder`/`withdraw`), and Tron's TRC20 ecosystem includes tokens that do not strictly follow the "revert-on-failure" convention assumed by a bare `success` check. No privileged actor, malicious relayer, or compromised prover is needed — the condition is purely a property of the token contract used in the escrowed order, combined with ordinary balance/allowance edge cases (e.g., a compromised/blacklisted token account, paused token, or partial-failure token logic) that legitimately cause `transfer()` to return `false` rather than revert.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with the rest of the file's `safeTransferFrom` usage and with the main-chain `IntentsBase.sol` implementation, so that both call failure and a `false` boolean return revert the transaction before `_filled`/`_orders` state is mutated.

### Proof of Concept
1. A user places a cross-chain order on the source chain with `order.inputs[0].token` set to a TRC20 token `T` whose `transfer()` implementation can return `false` (e.g. due to a blacklist/pause flag) without reverting.
2. The order is filled/escrowed normally; `_orders[commitment][T]` is credited with the escrowed amount as in the deposit path (`IERC20(token).safeTransferFrom(...)`, which correctly enforces success).
3. On settlement, `onAccept` dispatches to `withdraw(body, isRefund)`. Inside, for token `T`:
   ```solidity
   (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
   if (!success) revert TransferFailed();
   ```
   If `T.transfer()` returns `false` due to the beneficiary being blacklisted/paused (a valid, non-reverting outcome under many token implementations) — Ethereum call succeeds (`success == true`), the `if (!success)` guard does not trigger.
4. `_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` are committed, and `EscrowReleased`/`EscrowRefunded` is emitted.
5. The tokens `amount` of `T` remain in the `IntentGatewayV2` contract's balance, but there is no remaining code path to claim them: `_orders[commitment][token]` is already zeroed and `_filled[commitment]` is already set, so any retry attempt (`UnknownOrder`/`Filled` checks) will reject further withdrawal attempts, permanently locking the escrowed funds.
