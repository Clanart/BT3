### Title
OP_RETURN data output is omitted from fee/weight accounting, producing transactions that fail relay policy and brick the spend - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` to `tx_outs`, but then computes `weight`, `vbytes`, `needed_fee`, the `TooLowFee` floor, the `NotEnoughFunds` check, the change-amount computation, and the `MAX_STANDARD_TX_WEIGHT` bound using `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only accounts for the payment outputs and the optional change output. Analogous to the audit finding where a fixed 10,000 gas stipend was insufficient for the real execution path and permanently bricked ETH forwarding, here the transaction's resource footprint is under-provisioned by a fixed amount (the entire data output), so the constructed and FROST-signed transaction can be unbroadcastable.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed to `tx_outs` before the weight/fee math runs:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds the estimation transaction from `payments` only (plus optional `change`), never including the `OP_RETURN` output already committed to `tx_outs` (`send.rs:85-99`). The same omission occurs in the change path (`send.rs:225-234`), where `fee_with_change` and the change output's value are computed from `vbytes_with_change` that excludes the data output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is short by the data output's full weight (an 80-byte OP_RETURN output contributes roughly 90 non-witness bytes ≈ 360 weight units ≈ 90 vbytes).
- The `TooLowFee` check (`send.rs:211`) and the `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) are evaluated against a smaller transaction than the one actually produced by `TransactionSignatureMachine::complete`, which serializes `self.tx` including the data output (`send.rs:417-427`).
- The `NotEnoughFunds` check (`send.rs:215`) may pass when the true fee requirement isn't met.

A reachable path exists for any party supplying `data` (e.g., instruction payloads embedded into transactions), since `data` is a public caller-supplied argument to `SignableTransaction::new` and propagates verbatim into the signed transaction. The resulting signed transaction's actual vsize exceeds the estimated `vbytes` by the data output's size, so its effective fee rate is lower than requested and can fall below `DEFAULT_MIN_RELAY_TX_FEE`, or its weight can exceed `MAX_STANDARD_TX_WEIGHT` when near the boundary — in both cases the fully signed transaction is rejected by relay/mempool policy and the inputs cannot be moved through it.

### Impact Explanation
A successfully completed FROST signing session yields a transaction that nodes refuse to relay/accept: with `fee_per_vbyte` at or near the minimum, the unaccounted ~90 vbytes push the realized fee rate below the relay floor; near the size boundary, actual weight exceeds `MAX_STANDARD_TX_WEIGHT` despite the `TooLargeTransaction` guard passing. The spent inputs remain locked behind a transaction that can never confirm, and the threshold signing ceremony (which consumed preprocesses bound to this exact transaction, since caching is unsupported — `send.rs:333-349`) must be abandoned and re-run. This is a permanent-for-that-transaction DoS of fund movement caused directly by under-provisioned resource accounting, matching the bug class of the source report (a fixed gas limit below the true cost bricking value transfer).

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data: Some(_)` undercounts the transaction size; whether the signed TX becomes unbroadcastable depends on fee rate proximity to the relay minimum and on proximity to the weight cap. The `data` field is attacker-influencable transaction data (instruction data is an external, unprivileged input in this codebase's usage), and low-fee-period or large-transaction conditions are normal operating regimes, so the failure is plausibly triggered rather than exceptional.

### Recommendation
Include the `OP_RETURN` data output in `calculate_weight_vbytes` — e.g., pass the fully assembled output list (or the data payload length) into the estimator so `weight`, `vbytes`, `needed_fee`, the `TooLowFee`/`NotEnoughFunds` checks, the change-amount calculation, and the `MAX_STANDARD_TX_WEIGHT` bound all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
Construct a `SignableTransaction` with a data payload and compare `needed_fee`/weight accounting against the real signed transaction:

```rust
// In a test with a funded ReceivedOutput `output` and script `addr`:
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![output],
  &[(addr(), 1000)],
  None,
  Some(data.clone()),
  fee_per_vbyte, // e.g., 1 sat/vbyte
).unwrap();

// The estimation used `payments` only; the actual tx includes the OP_RETURN.
let real_vsize = tx.transaction().vsize() as u64;           // includes data output
let estimated_vbytes = tx.needed_fee() / fee_per_vbyte;      // excludes data output
assert!(real_vsize > estimated_vbytes);                      // underpaid by ~90 vbytes

// With fee_per_vbyte = 1 sat/vbyte (DEFAULT_MIN_RELAY_TX_FEE = 1000 sat/kvb):
// needed_fee passed the TooLowFee check against the smaller estimate, but the
// real transaction's fee rate = needed_fee / real_vsize < 1 sat/vbyte,
// so the signed TX is rejected from the mempool -> inputs cannot be spent via it.
```

Relevant lines: `send.rs:194-204` (data output pushed, then weight computed from `payments` only), `send.rs:62-99` (`calculate_weight_vbytes` builds the dummy TX without the data output), `send.rs:211,241` (policy checks on the underestimated weight), `send.rs:417-427` (`complete` serializes the real transaction including the data output).
