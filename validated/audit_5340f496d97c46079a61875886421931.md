### Title
Unbounded attacker-declared signature count in `SchnorrAggregate::read` enables denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to CVE-2018-5784 (declared entry count not validated against actual data), `SchnorrAggregate::read` deserializes a `u32` length prefix and loops that many times calling `C::read_G`, with no bound on the declared count and no check that the declared count is consistent with the actual data available. A 4-byte prefix of `0xFFFFFFFF` drives up to ~4.29 billion group-element decodings from an untrusted `Read` stream.

### Finding Description
`SchnorrAggregate::read` reads a little-endian `u32` into `len` and then iterates `0 .. u32::from_le_bytes(len)`, pushing a decoded `C::G` per iteration ( [1](#0-0) ). The declared count is never validated against any protocol bound (e.g., the number of participants, `u16::MAX`, or the remaining input length). Over a `Read` implementation backed by a stream (rather than an in-memory slice, where it fails fast at EOF), the loop continues consuming bytes as long as the peer sends them — exactly the uncontrolled-resource-consumption shape of the LibTIFF bug, where a declared directory-entry count drives processing independent of actual data. The same untrusted `u32` then feeds `SchnorrAggregate::verify`, which allocates `Vec::with_capacity((2 * keys_and_challenges.len()) + 1)` and performs a multiexp over `Rs` ( [2](#0-1) ), amplifying per-element work after parsing.

Contrast with in-repo defensive practice: `Transaction::read` for `DkgCommitments` caps `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` before allocating ( [3](#0-2) ), showing the expected pattern of validating declared counts before acting on them.

### Impact Explanation
An unprivileged party who can deliver bytes to a deserialization/verification path that accepts a `SchnorrAggregate` (an aggregate-signature verify API consuming attacker-controlled encodings) can cause sustained CPU and memory consumption — billions of point-decoding attempts over a streaming reader, or a `Vec` of up to 4 billion `C::G` elements — denying service to the verifying process. This is availability-only; no signature forgery or key disclosure results.

### Likelihood Explanation
Reachability requires an integration that feeds externally supplied bytes to `SchnorrAggregate::read`/`verify` over a non-length-bounded reader. Within this codebase, the read functions used by the signing flows (e.g., `read_preprocess`, `read_share`) are fixed-size and the coordinator `Transaction` parser bounds counts, so exploitation depends on the aggregate verifier being exposed to untrusted streams — plausible for any batch/aggregate signature verification endpoint, but not demonstrated inside the in-repo call sites.

### Recommendation
Enforce a protocol-level maximum on `len` before the loop (e.g., `len > MAX_AGGREGATE` → error, or derive the count from the expected number of signers rather than from the wire), and where the reader is a byte slice, compare `len` against `reader.len()` up front. Prefer `Vec::with_capacity` only after the bound check.

### Proof of Concept

use std::io::Read;
use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;

// A reader that never ends (models a peer streaming data).
struct Endless;
impl Read for Endless {
  fn read(&mut self, buf: &mut [u8]) -> std::io::Result<usize> {
    buf.fill(0);
    Ok(buf.len())
  }
}

fn dos<C: Ciphersuite>() {
  // Wire prefix declares u32::MAX signatures; the parser loops 4_294_967_295
  // times calling C::read_G against the (endless) stream.
  let prefix = u32::MAX.to_le_bytes();
  let mut chained = std::io::Read::chain(&prefix[..], Endless);
  // Hangs / burns CPU and memory indefinitely:
  let _ = SchnorrAggregate::<C>::read(&mut chained);
}
