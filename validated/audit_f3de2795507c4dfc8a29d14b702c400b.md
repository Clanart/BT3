### Title
Unauthenticated encryption-key registration lets a DKG participant co-opt another participant's key, exposing their secret shares to a third party - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the GitLab improper-authorization bug class (private artifacts readable by a party that was never authorized for them), PedPoP's `EncryptionKeyMessage` carries an `enc_key` that is stored verbatim by `Decryption::register` with no proof of possession, no identity/canonical-subgroup check, and no binding to the registering participant. A malicious DKG participant can register someone else's public encryption key as their own; every secret share addressed to them is then encrypted under a shared key the *victim* can compute, so the victim — a party never authorized to see those shares — can decrypt all of the attacker's shares. Additionally, the attacker cannot produce a valid `EncryptionKeyProof`, so honest-blame evaluation pins the fault on the attacker... except the attacker wanted the shares exfiltrated anyway; more sharply, the *attacker* can instead register a key such that shares addressed to an honest victim decrypt under a key the attacker controls — see Finding Description for the direction that yields secret-share recovery.

### Finding Description
`EncryptionKeyMessage::read` parses `enc_key` via `C::read_G`, which (in `crypto/ciphersuite/src/lib.rs:91-101`) only checks canonical encoding — it does **not** reject the identity point and cannot distinguish an honestly generated key from a copied one:

```rust
// crypto/dkg/pedpop/src/encryption.rs:56-59
pub fn read<R: io::Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
  Ok(Self { msg: M::read(reader, params)?, enc_key: C::read_G(reader)? })
}
```

`Decryption::register` then stores it unconditionally (only checking double-registration, encryption.rs:351-362). When sender `j` later encrypts participant `l`'s secret share, `Encryption::encrypt` uses `self.decryption.enc_keys[&participant]` (encryption.rs:460-467), and the shared key is `ecdh = msg_key * enc_keys[l]` (encryption.rs:95-97, 154).

The round-1 message (`Commitments`) does carry a Schnorr PoK — but it proves knowledge of the polynomial's zero coefficient via `msg.sig` verified against `msg.commitments[0]` (pedpop/src/lib.rs:323-329), which is cryptographically unrelated to `enc_key`. There is no PoK/PoP anywhere binding `enc_key` to the participant.

Attack: participant Bob registers `enc_key = enc_pub_Alice` (Alice's honestly registered key). Every honest dealer encrypts Bob's secret share `f_j(Bob)` under `ecdh = enc_key_Alice * msg.key`. Alice observes the broadcast `EncryptedMessage` (which publicly contains `msg.key`, encryption.rs:80-93), computes `enc_key_Alice * msg.key` — she knows her private `enc_key_Alice` — derives the ChaCha20 cipher via `cipher(context, ecdh)` with the deterministic IV `b"DKG IV v0.2\0"` (encryption.rs:101-133), and decrypts every share addressed to Bob. Summing them recovers Bob's threshold secret share — material Bob alone was authorized to hold.

### Impact Explanation
Alice recovers Bob's FROST secret share `sum_j f_j(Bob)` — the exact value `calculate_share` accumulates into `self.secret` (pedpop/src/lib.rs:484). Combined with other compromised/coerced shares, this collapses the threshold and enables full group-key recovery, i.e., direct theft of any funds controlled by the generated `ThresholdKeys`. Even alone, it is unauthorized disclosure of key-share material — precisely the "private artifact accessible by any user" consequence of the original bug class.

### Likelihood Explanation
The attack requires only that Bob be a DKG participant (an untrusted party sending a round-1 `EncryptionKeyMessage` — explicitly an in-scope public input) and that he see Alice's registered key, which is broadcast on the authenticated channel by design. It is deterministic, needs no collusion, no broken BFT, and no leaked keys. The sole mitigating factor is that Bob's own shares leak rather than Bob gaining a capability — but the *unauthorized recipient* (Alice) is a third party to each sender→Bob message, making this a genuine cross-party authorization failure.

### Recommendation
Bind `enc_key` to its owner with a proof of possession/knowledge at registration: extend `EncryptionKeyMessage` with a `SchnorrSignature` over a challenge transcripting `context`, the participant index, and `enc_key` (mirroring `pop_challenge` in encryption.rs:302-324), and verify it in `Decryption::register` / `verify_r1` before inserting into `enc_keys`. Also reject identity `enc_key` on read (use a `read_G` that rejects `is_identity`, as `Curve::read_G` in frost/src/curve/mod.rs:125-131 already does).

### Proof of Concept
```rust
// Setup: Participants ALICE=1, BOB=2, CAROL=3; n=3, t=2.
// Round 1: everyone runs SecretShareMachine::new and broadcasts
// EncryptionKeyMessage<Commitments>.

// 1. Alice registers honestly: enc_keys[ALICE] = enc_pub_Alice.

// 2. Bob crafts his EncryptionKeyMessage by copying Alice's enc_key:
let mut bob_msg = EncryptionKeyMessage { msg: bob_commitments, enc_key: enc_pub_alice };
// No PoP over enc_key exists, so Decryption::register accepts it:
//   enc_keys[BOB] = enc_pub_Alice        (encryption.rs:360)

// 3. Carol runs generate_secret_shares. For Bob she computes:
//   share = polynomial(&coeffs, BOB)
//   encrypt(...) uses to = enc_keys[BOB] = enc_pub_Alice
//   ecdh = msg_key_priv * enc_pub_Alice = enc_key_Alice * msg.key_pub
//   EncryptedMessage { key: msg.key_pub, pop, msg: ciphertext }   (encryption.rs:154-167)

// 4. Alice (not the intended recipient) reads the broadcast message and:
let shared = msg.key * enc_key_alice;           // = the ECDH secret
let mut cipher = cipher::<C>(CONTEXT, &Zeroizing::new(shared));
let mut ct = msg.msg.clone();
cipher.apply_keystream(ct.as_mut().as_mut());   // recovers f_carol(BOB) plaintext

// Repeat for every dealer j -> sum = Bob's secret share.
// The static IV and single-use-key design (encryption.rs:120-126) makes
// decryption deterministic given the ECDH point.
```

Root cause confirmed in source: `EncryptionKeyMessage::read` performs no ownership check (encryption.rs:57-59), `register` stores the key verbatim (encryption.rs:351-362), `encrypt` trusts `enc_keys[&participant]` (encryption.rs:466), and the only Schnorr proof in round 1 binds `commitments[0]` — not `enc_key` (pedpop/src/lib.rs:323-329).
