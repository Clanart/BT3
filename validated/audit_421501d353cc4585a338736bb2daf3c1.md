### Title
Unauthenticated scalar offsets allow forged unspendable received outputs - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

`ReceivedOutput::read` accepts an arbitrary scalar offset, transaction output, and outpoint without verifying that the offset controls the output’s `script_pubkey`. [1](#0-0)  An attacker who can supply serialized `ReceivedOutput` bytes can therefore make a wallet report funds as received even though the associated offset cannot spend them. [2](#0-1) 

### Finding Description

A legitimate `ReceivedOutput` produced by `Scanner::scan_transaction` couples an existing transaction output with an offset previously mapped to that output’s `script_pubkey`. [3](#0-2)  That mapping is created by `register_offset`, which derives `key + offset * G`, converts it to a P2TR script, and stores the offset under that script. [4](#0-3) 

`ReceivedOutput::read` does not perform the corresponding validation. [1](#0-0)  It checks only that the scalar, `TxOut`, and `OutPoint` deserialize successfully, then constructs the object directly. [5](#0-4)  Because the key or expected script is absent from the type and not re-derived during deserialization, the returned object preserves a syntactically valid but semantically false pairing. [6](#0-5) 

This is analogous to using a validated price with attacker-manipulated token amounts: the individual serialized fields are well formed, but the security-critical relation between the spend offset and the output script is never validated. [1](#0-0) 

### Impact Explanation

A caller can receive a `ReceivedOutput` whose `value()` and `output()` report arbitrary attacker-selected funds. [7](#0-6)  Since the output script need not equal `p2tr_script_buf(key + offset * G)`, attempting to spend the claimed UTXO with the supplied offset produces a signature for the wrong Taproot key and cannot authorize the claimed output. [8](#0-7) 

This can corrupt balance accounting, cause acceptance of non-spendable deposits, or make downstream transaction construction repeatedly attempt to spend an invalid outpoint. [2](#0-1) 

### Likelihood Explanation

The issue is reachable whenever serialized `ReceivedOutput` bytes originate from an untrusted peer, remote service, or mutable storage rather than only from local `Scanner` output. [1](#0-0)  No cryptographic break or malformed encoding is needed because the parser accepts unrelated field values. [5](#0-4) 

The impact is bounded by the need for an integrator to trust these bytes as evidence of received funds, so Medium severity is appropriate rather than a direct remote theft primitive. [3](#0-2) 

### Recommendation

Do not expose standalone `ReceivedOutput` deserialization as an authenticated source of received funds. [1](#0-0)  Instead, deserialize through the owning `Scanner` and require `output.script_pubkey` to equal the script generated for `self.key + offset * G`, rejecting otherwise. [4](#0-3) 

Alternatively, store and authenticate a scanner/session binding alongside the record, then make `ReceivedOutput::read` fail unless the serialized output matches the registered script-to-offset mapping. [9](#0-8) 

### Proof of Concept

An attacker can serialize any scalar together with an unrelated `TxOut` and `OutPoint`:

```rust
let forged = ReceivedOutput {
    offset: Scalar::ONE,
    output: TxOut {
        value: Amount::from_sat(100_000),
        script_pubkey: attacker_controlled_script,
    },
    outpoint: attacker_controlled_outpoint,
}
.serialize();
```

`ReceivedOutput::read(&mut forged.as_slice())` succeeds because it only parses the three independent fields. [5](#0-4)  The returned object then reports `value() == 100_000`, even though `Scalar::ONE` was never registered as controlling `attacker_controlled_script`. [7](#0-6)  By contrast, scanner-created outputs are only accepted after `scripts.get(&output.script_pubkey)` finds a registered offset. [3](#0-2)

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;

          return Some(offset);
