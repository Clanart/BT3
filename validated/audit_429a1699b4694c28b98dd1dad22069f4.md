### Title
Prefix-only root check in `resolveWithin()` lets a crafted deep-link `filepath` escape the intended repository directory into a same‑prefix sibling folder - (File: `app/src/lib/path.ts`)

### Summary
The Uniswap report's root cause is a boundary check that is supposed to keep a value strictly inside an intended range, but the check is implemented with a subtly wrong comparison (mismatched `MIN_TICK`/`MAX_TICK` constants), so a value that lies just outside the intended range is still treated as valid. GitHub Desktop has the same structural flaw in its "stay inside the repository root" boundary check: `resolveWithin()` validates containment with `realResolved.startsWith(realRoot)`, a plain string-prefix test with no path-separator boundary. A sibling directory whose name is a superstring of the repository folder name (e.g. `myrepo-secrets` vs `myrepo`) satisfies `startsWith(realRoot)` even though it is a completely different directory. This function is the explicit "backstop" used when handling a user-clicked deep link (`x-github-client://openRepo/...&filepath=...`), so an attacker-controlled `filepath` query parameter can escape the repository root.

### Finding Description
`_resolveWithin()` in `app/src/lib/path.ts:36-72` computes the real, resolved path and then validates containment like this: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of path components: `"/Users/victim/Documents/GitHub/myrepo-secrets/token.txt".startsWith("/Users/victim/Documents/GitHub/myrepo")` is `true`. There is no check that the next character after the matched prefix is a path separator (or that the strings are exactly equal), so any sibling directory whose name begins with the root directory's name is treated as "inside" the root.

This exact function is invoked as the sole guard before revealing a file that comes from a user-clicked deep link: [2](#0-1) 

```
if (filepath !== null) {
  if (isAbsolute(filepath)) {
    log.error(`Refusing to open absolute path: ${filepath}`)
    return
  }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } else {
    log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
  }
}
```

The only pre-check is `isAbsolute(filepath)`, which rejects absolute paths but does nothing to stop relative traversal (`../`). `filepath` originates directly from the `openrepo` URL action's query string, which is attacker-controlled content in a link the victim clicks: [3](#0-2) 

The comment on `isClonePathSensitive` in `clone.ts` shows the project is aware traversal via crafted URLs is a real class of bug that needs a "backstop," but that hardening was only applied to clone-path derivation (`sanitizeCloneName`), not to `resolveWithin`'s containment check: [4](#0-3) 

Same as the Uniswap report - where two boundary constants (`MIN_TICK`/`MAX_TICK` vs `TickMath.MIN_TICK`/`MAX_TICK`) diverge just enough to let price slip "just outside" the intended liquidity range while the rest of the code still assumes it's inside - here the containment test diverges just enough (missing separator boundary) to let a resolved path slip "just outside" the intended repository directory while the calling code (`dispatcher.ts`) still assumes `resolveWithin` guarantees containment.

### Impact Explanation
An attacker who gets a victim to click a `x-github-client://openRepo/<repo-url>?filepath=<traversal>` deep link (e.g. embedded in a webpage, README, or chat message) can cause Desktop to resolve and reveal (`shell.showItemInFolder`) a file located outside the target repository, in any sibling directory whose name is a prefix-match of the repository's folder name. This is a file-path-boundary escape ("read outside the repo" primitive called out as in-scope), and because `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are the app's general-purpose "stay inside root" primitive, any other current or future caller relying on it inherits the same silent bypass.

### Likelihood Explanation
Users routinely clone multiple related repositories with overlapping name prefixes into the same parent folder (e.g. `GitHub/vscode` and `GitHub/vscode-docs`, or `GitHub/api` and `GitHub/api-internal`), so the "prefix collision" precondition is common in real developer setups, not a contrived edge case. The vulnerable code path only requires the victim to click a link - no local access, no admin rights, and no prior compromise - matching the "attacker controls ... a link or deep link the user clicks" scope. The `isAbsolute()` guard gives a false sense of safety while leaving relative traversal completely open, making this an easy, low-effort trigger once the target's directory layout is known or guessed.

### Recommendation
Fix `_resolveWithin` to require an exact match or a proper path-separator boundary after the root, e.g.:

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate `sep` from the injected `options`). Add regression tests with sibling directories that share a name prefix (e.g. root `.../myrepo` vs `.../myrepo-secrets`) to `path.ts`'s test suite, mirroring the existing traversal tests in `clone-path-safety-test.ts`.

### Proof of Concept
1. Victim has previously cloned two repos side by side:
   - `~/Documents/GitHub/myrepo` (the target repo, opened via the deep link)
   - `~/Documents/GitHub/myrepo-secrets` (an unrelated folder containing a sensitive file, `token.txt`)
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=../myrepo-secrets/token.txt`
3. `parseAppURL` parses this into `{ name: 'open-repository-from-url', url: 'https://github.com/owner/myrepo', filepath: '../myrepo-secrets/token.txt' }` (see `app/src/lib/parse-app-url.ts:98-124`).
4. `openRepositoryFromUrl` in `dispatcher.ts` opens `myrepo`, then calls `isAbsolute(filepath)` → `false` (passes), then `resolveWithin(repository.path, filepath)` with `repository.path = '.../myrepo'`.
5. Inside `_resolveWithin`, `resolved` = `.../myrepo-secrets/token.txt`; `realRoot` = `.../myrepo`; `realResolved.startsWith(realRoot)` evaluates `true` because `"myrepo-secrets"` starts with `"myrepo"`.
6. `resolveWithin` returns the out-of-root path instead of `null`, and `shell.showItemInFolder(resolved)` reveals `token.txt` from the sibling `myrepo-secrets` directory - a directory never intended to be reachable from the `myrepo` repository root.
