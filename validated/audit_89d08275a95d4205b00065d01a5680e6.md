### Title
Blame proof reveals the ECDH shared key for a message whose proof-of-possession was never verified, letting a participant decrypt a victim's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

In `KeyMachine::calculate_share`, the per-message `EncryptionKeyProof` (which contains the ECDH shared key `b * msg.key`) is computed inside `Encryption::decrypt` and attached to `PedPoPError::InvalidShare` **before** the batch verification that actually checks the message's Schnorr proof-of-possession (`msg.pop`) runs. An unprivileged participant can therefore force an honest participant to publish the ECDH key for an attacker-supplied `msg.key` — including a `msg.key` copied from another participant's `EncryptedMessage` — thereby decrypting the victim's message and recovering the secret share it carries.

### Finding Description

`Encryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:469-501`) queues the PoP check into a `BatchVerifier` (`msg.pop.batch_verify(...)`, lines 479-485), but returns the `EncryptionKeyProof` containing `key = ecdh(enc_key, msg.key)` immediately (lines 487-500). In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-499`):

1. If the decrypted bytes are not a canonical scalar, the function early-returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` (lines 479-482) — `batch.verify_with_vartime_blame()` is never executed, so the invalid PoP is never detected, yet the blame proof revealing the ECDH key is emitted.
2. Even if the bytes happen to decode as a scalar, the garbage share fails the `BatchId::Share(l)` verification; when the blame search attributes failure to the share statement rather than the decryption statement, `blames.remove(&l)` again returns `Some(proof)` revealing the key.

The PoP exists precisely to prevent this: the comment at `encryption.rs:83-90` explains that without it, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X... Bob would then use this to create a blame argument against Eve... they'd reveal bX, revealing Alice's message to Bob." Because the PoP is only checked inside the batch — which is skipped by the early return, or attributed to a different batch ID — the protection is bypassed. The `Decryption::decrypt_with_proof` path used by `AdditionalBlameMachine` does check `msg.pop.verify` first (`encryption.rs:374-378`), so the leaked proof is only discovered to have a bad signature *after* it has already been published via `ProcessorMessage::InvalidShare { ..., blame }` (processor/src/key_gen.rs:419-425).

### Impact Explanation

The attacker copies victim Alice's per-message public key `X` from Alice's `EncryptedMessage` to Bob, sets `msg.key = X`, attaches an invalid PoP and arbitrary ciphertext bytes, and sends it to Bob. Bob's `calculate_share` emits an `EncryptionKeyProof` revealing `bX` — the exact ChaCha20 input (`cipher(context, ecdh)`) protecting Alice's real ciphertext to Bob. Anyone observing the blame can now decrypt Alice's secret share addressed to Bob. Repeating for `t` senders' shares to the same recipient recovers that participant's secret key share — a key share recovery primitive, reachable entirely with attacker-crafted bytes fed through `EncryptedMessage::read` → `calculate_share`.

### Likelihood Explanation

The attacker is an ordinary DKG participant sending a malformed round-2 message — no special privileges needed. The only requirement is that the attacker observes the victim's `EncryptedMessage` (its `key` field), which is transmitted to the coordinator and gossiped for blame evaluation. Triggering the non-canonical-scalar early return succeeds with high probability per attempt (a random 32-byte string fails `F::from_repr` for Ristretto with probability ~15/16) and is freely retryable across DKG attempts; the scalar-valid case still leaks the key whenever the blame search resolves the share-statement failure.

### Recommendation

In `KeyMachine::calculate_share`, do not release the `EncryptionKeyProof` until the PoP has been verified. Concretely: run `batch.verify_with_vartime_blame()` on the decryption batch IDs *before* treating any decrypted share as invalid, or only attach `blame` after a successful PoP check. Alternatively, restructure `Encryption::decrypt` to return the proof only upon confirmed PoP validity, or store pending proofs and release them solely for failures attributable to `BatchId::Share` *after* confirming the corresponding `BatchId::Decryption` passed — which requires checking the PoP synchronously for each message rather than relying on a single aggregated batch outcome.
