### Title
Time-of-check/time-of-use gap between reviewed diff and re-fetched diff allows attacker-controlled working-directory content to be silently staged into a partial commit - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks of a file to include in a commit. The selection the user makes is recorded as a set of *absolute line indices* against the diff that was rendered in the Changes view [1](#0-0) . When the user actually commits, `applyPatchToIndex` does not reuse that reviewed diff — it re-fetches a brand-new diff from disk (`getWorkingDirectoryDiff`) and then feeds the *old* selection indices into `formatPatch` against this new diff [2](#0-1) . If the file's on-disk content changes between the moment the user reviewed/selected lines and the moment `stageFiles`/`applyPatchToIndex` runs, the same numeric line indices can now point at different content, so the patch applied to the index (and therefore the commit) can silently differ from what the user actually reviewed and approved.

### Finding Description
The invariant that should hold is: "the bytes staged/committed for a partially-selected file are exactly the bytes the user visually selected in the diff viewer." This bug class mirrors the Elfi Protocol report's core flaw — a value (available liquidity / here, "the diff the selection refers to") is computed once and then used later without re-validating it against the current, possibly-changed state, letting a stale calculation silently produce an incorrect and larger-than-expected effect (fund payout / here, committed content).

Concretely:
- `_changeFileLineSelection` stores line-index based `DiffSelection` computed against the diff object currently held in `IChangesState` [3](#0-2) .
- When the diff is refreshed in the background (`updateChangesWorkingDirectoryDiff`), the app explicitly acknowledges that "the diff might have changed dramatically since last we loaded it" and only prunes indices that no longer exist as "includeable" lines — it does **not** revalidate that surviving indices still refer to the same textual content [4](#0-3) .
- At commit time, `stageFiles` calls `applyPatchToIndex` for every partially-selected file [5](#0-4) .
- `applyPatchToIndex` re-derives the diff straight from the working directory (`getWorkingDirectoryDiff(repository, file)`), independent of whatever diff object the UI last displayed to the user, and then calls `formatPatch(file, diff)` using the file's stored `selection`, whose absolute indices were computed against the earlier diff [2](#0-1) .
- `formatPatch` blindly trusts `file.selection.isSelected(absoluteIndex)` against the hunks of the freshly-fetched diff, with no check that the file content, hunk boundaries, or line offsets match what was originally reviewed [6](#0-5) . The code comment even flags the risk generically ("Someone gave us a faulty diff and/or faulty selection state") but the only guard is a bare non-empty check, not a content-equivalence check [7](#0-6) .

An attacker who can influence the working-directory file between "diff shown to user" and "user clicks Commit" — e.g., through a build tool, watch script, editor plugin, LFS/clean-smudge filter, or any other automated process that runs against the cloned repository the victim is actively working in — can shift the file content so the same absolute-index selection now silently maps onto attacker-inserted lines, without the user re-reviewing the diff.

### Impact Explanation
This causes silent corruption of what the user commits: content the user never saw or approved can end up staged and committed under their identity/authorship, then pushed to the remote. Because Desktop shows no re-confirmation dialog before staging partial selections (only the previously-rendered diff and checkbox), the victim has no visual indication a mismatch occurred. This matches the "silent corruption of what the user commits or pushes" impact category explicitly called out as valid.

### Likelihood Explanation
The trigger condition — the working-directory file changing between diff render and clicking Commit — is common in normal developer workflows (auto-formatters, linters running on save, build watchers, git filters, LFS smudge, IDE auto-save with format-on-save, pre-existing background scripts within the repo). Any of these can be an "attacker-controlled" vector if the repository itself ships a script/hook/tool that runs during the developer's normal editing session, which is within the stated threat model (attacker controls a cloned/fetched repository). No admin rights, local physical access, or leaked credentials are required — only that the app is actively displaying a partial selection while the file is externally modified.

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-fetch the diff and verify it is unchanged (e.g., via a hash of the diff text or the underlying file content) relative to the diff the user's `DiffSelection` was made against; if it has changed, abort the partial-stage of that file and force the UI to re-render the diff and require the user to re-select/re-confirm before committing, rather than silently remapping stale indices onto new content.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks.
2. In the Changes view, select only specific lines to include, leaving the rest unstaged (`DiffSelection` recorded with absolute indices against the current diff, as tested in `app/test/unit/patch-formatter-test.ts:41-249`, which shows this exact selected-line-to-patch flow) [8](#0-7) .
3. Before clicking "Commit", have an external process (e.g., a script the repository configures to run, a save-hook, or a filter) rewrite the file so the number of context/insert lines above the target hunk changes, shifting line offsets, while leaving the diff superficially plausible.
4. Click Commit. `stageFiles` → `applyPatchToIndex` re-fetches the diff fresh from disk and applies the old absolute-index selection to it [2](#0-1) ; because indices are unchanged but now refer to different hunk lines, the resulting commit contains different content than what was visually approved, with no re-prompt to the user.

I was unable to fully inspect `app/src/lib/git/commit.ts` (`createCommit`) due to a tool error in the final iteration, so I could not directly confirm the exact call chain from `_commitIncludedChanges` into `stageFiles`/`applyPatchToIndex` line-by-line beyond what is shown in `update-index.ts`; this should be verified in a follow-up review of `app/src/lib/git/commit.ts`.
