### Title
CR-CAT Coins Can Be Permanently Trapped When No Valid VC Exists to Authorize Their Spend - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
Credential-Restricted CATs (CR-CATs) require every spend — including the recipient's own claim of already-received funds — to be co-signed/authorized by a Verified Credential (VC) that satisfies the CR-CAT's `authorized_providers`/`proofs_checker` requirements. If the address that ends up owning a CR-CAT (either directly, or via the "pending approval" holding state used during offers) never has access to such a valid VC, the coin cannot be spent or reclaimed by any path in the wallet code, mirroring the reported Vault issue where a user removed from the whitelist could neither transfer their tokens nor call the escape-hatch `requestWithdraw()`.

### Finding Description
CR-CATs wrap a normal CAT inner puzzle with a credential-restriction layer (`construct_cr_layer`) that is curried with `authorized_providers` and a `proofs_checker` [1](#0-0) . Every spend of the coin, via `CRCAT.do_spend`/`spend_many`, must supply `proof_of_inclusions`, a `provider_id`, and a `vc_launcher_id` derived from a valid VC [2](#0-1) .

On the wallet side, both normal transfers and the "claim pending approval" recovery flow first look up a VC that satisfies the CR-CAT's authorized providers:
- `_generate_unsigned_spendbundle` calls `vc_wallet.get_vc_with_provider_in_and_proofs(self.info.authorized_providers, self.info.proofs_checker.flags)`; if none is found, it raises `RuntimeError("Spending no cat coins is not an appropriate use of _generate_unsigned_spendbundle")` [3](#0-2) , so a normal `cat_spend`/transfer is impossible without a qualifying VC.
- `claim_pending_approval_balance` — the function used to pull CR-CATs out of the intermediate "pending approval" state created when an offer counterparty could not immediately authorize the transfer — performs the same lookup and raises `RuntimeError(f"No VC exists that can approve spends for CR-CAT wallet {self.id()}")` if `vc is None` [4](#0-3) .

There is no alternate/unrestricted exit path in these drivers analogous to allowing a transfer "to `address(this)`" bypassing the check in the reported Vault bug. Once a CR-CAT coin (or a coin sitting in the `construct_pending_approval_state` puzzle hash awaiting a VC-authorized claim) belongs to an address whose owner cannot obtain/retain a satisfying VC — e.g., because the DID/provider revokes or never issues the required VC, or the recipient is simply not a party the `authorized_providers` list recognizes — that coin's balance becomes permanently unspendable by the wallet software, exactly as described in the report where a whitelist removal blocks both regular transfer and the internal `requestWithdraw()` self-transfer.

### Impact Explanation
Coins whose only spend path requires a VC satisfying `authorized_providers` become permanently locked for their nominal owner if such a VC can never be obtained (revocation via `activate_backdoor`, DID never issuing proofs, or provider list simply not covering the recipient). This is a concrete, spend-triggered fund lock reachable purely from normal wallet operations (accepting a CR-CAT offer, or being sent a CR-CAT whose providers don't include a VC you can get). Funds trapped in the `pending_approval` state (created automatically by `check_for_requested_payment_modifications` during offer construction [5](#0-4) ) are especially exposed since `claim_pending_approval_balance` is the *only* code path to release them and it unconditionally requires a matching VC.

### Likelihood Explanation
Any wallet user receiving CR-CATs (common in credential-restricted CAT trading covered extensively by `chia/_tests/wallet/cat_wallet/test_trades.py` and `chia/_tests/wallet/vc_wallet/test_vc_wallet.py`) is exposed if they do not hold, or later lose (via DID-side `revoke_vc`/`activate_backdoor` [6](#0-5) ), a VC satisfying the asset's `authorized_providers`/`proofs_checker`. Because CR-CAT issuers control `authorized_providers` at mint time and providers can revoke VCs at will, this is readily triggerable without any malicious peer/node behavior — purely by ordinary CR-CAT circulation and credential lifecycle events.

### Recommendation
Provide an explicit, credential-independent recovery/exit mechanism for CR-CAT holders who can no longer obtain a satisfying VC — for example, a melt-back-to-issuer path, a time-locked escape clause, or clearly documenting that CR-CAT issuers must guarantee recipients retain valid VCs before accepting such assets, and that wallets should refuse to accept a CR-CAT payment (or auto-warn) when the `authorized_providers` set doesn't include a currently held/obtainable VC. At minimum, the `claim_pending_approval_balance` pending-approval intermediate state should not depend on a VC that the ultimate recipient can't provide; consider adding a way for the original sender to reclaim/refund pending-approval CR-CATs that are never claimed within a bounded time or admit alternate authorization.

### Proof of Concept
1. Mint a CR-CAT with `authorized_providers = [did_id_A]` and send it, via an offer, to a wallet whose only DID/VC is `did_id_B` (not in `authorized_providers`), following the same offer flow exercised in `chia/_tests/wallet/cat_wallet/test_trades.py` (`credential_restricted=True` path) [7](#0-6) .
2. The taker wallet cannot self-authorize (no matching VC), so the payment lands in the `pending approval` state via `construct_pending_approval_state` [8](#0-7) .
3. Attempt to call `CRCATWallet.claim_pending_approval_balance` from the taker's wallet — it raises `RuntimeError(f"No VC exists that can approve spends for CR-CAT wallet {self.id()}")` [9](#0-8)  because no VC with `did_id_A` as provider is available, and there is no other function in `CRCATWallet` to move or reclaim these coins.
4. The CR-CAT balance is now permanently stuck in `pending_approval` with no way for the taker (or the original sender) to release it, matching the "trapped tokens due to whitelist/authorization mismatch" bug class from the report.

def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,

    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)
