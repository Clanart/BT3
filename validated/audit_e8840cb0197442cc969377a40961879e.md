### Title
Empty aggregate signature deserializes and verifies successfully - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary

`SchnorrAggregate::read` accepts an aggregate containing zero nonces, bypassing `SchnorrAggregator::complete`, which explicitly refuses to construct an empty aggregate. When paired with an empty signer list, `SchnorrAggregate::verify` accepts the encoded aggregate if `s = 0`.

### Finding Description

`SchnorrAggregator::complete` establishes the intended invariant that an aggregate must contain at least one signature by returning `None` when no signatures were aggregated. [1](#0-0) 

The deserializer does not enforce that invariant. It accepts a zero-length `Rs` vector and then reads a scalar directly from untrusted input. [2](#0-1) 

During verification, `Rs.len()` is only compared against the supplied `keys_and_challenges.len()`. [3](#0-2)  If both lists are empty, no weighted nonce/public-key statements are added; verification reduces to checking `-s * G == identity`. [4](#0-3)  An attacker can therefore provide `s = 0`, making the empty statement evaluate to identity and verification return `true`.

This is the Serai analog of dereferencing/using a result without checking for the empty/`None` case: the infallible deserialization path reconstructs a value which the normal constructor explicitly refuses to create.

### Impact Explanation

An unprivileged party can produce an aggregate signature accepted for an empty signer set. Any caller which treats a successful `SchnorrAggregate::verify` result as sufficient authorization, while independently allowing an empty signer list, accepts a forged aggregate signature without any private key.

The attack bytes are compact and deterministic: a four-byte little-endian count of zero followed by the canonical scalar encoding of zero.

### Likelihood Explanation

The input is completely attacker-controlled and requires no malformed encodings, invalid points, secret knowledge, race conditions, or protocol participation. Exploitation requires the caller to invoke verification with an empty `keys_and_challenges` slice; the API itself does not reject that state.

### Recommendation

Reject empty aggregates in `SchnorrAggregate::read`, matching `SchnorrAggregator::complete`. Additionally, defensively reject empty `keys_and_challenges` in `SchnorrAggregate::verify` so deserialization and verification independently preserve the non-empty aggregate invariant.

### Proof of Concept

```rust
use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;

fn forged_empty_aggregate<C: Ciphersuite>() {
  // Proof encoding:
  // - 0u32: zero R values
  // - C::F::ZERO: canonical zero scalar
  let mut bytes = Vec::new();
  bytes.extend(0u32.to_le_bytes());
  bytes.extend(C::F::ZERO.to_repr().as_ref());

  let aggregate = SchnorrAggregate::<C>::read(&mut bytes.as_slice()).unwrap();

  // The signer list is empty, matching the zero encoded nonces.
  assert!(aggregate.verify(b"application-specific-dst", &[]));
}
```

The forged object could not be produced through `SchnorrAggregator::complete`, since that constructor returns `None` for an empty aggregation set. [5](#0-4)
