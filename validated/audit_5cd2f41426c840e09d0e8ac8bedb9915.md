### Title
Wallet Signer Protocol Executes Arbitrary Caller-Supplied Signing Instructions Without Binding to a Real Spend — Blind Signing Oracle Enables Unauthorized Coin Movement (`chia/wallet/wallet_signer.py`)

### Summary
The CVE-2021-25312 bug class is "a caller with limited standing (IDTOKENS) can obtain an authorization that lets it act as another identity" because the target system trusted a caller-supplied identity claim without verifying it was correctly bound/derived. The reachable chia analog is `WalletSigner.execute_signing_instructions`, exposed at the wallet RPC endpoint `execute_signing_instructions` (`chia/wallet/wallet_rpc_api.py:3513-3521`), which signs whatever `(fingerprint, message)` targets and `SumHint`/`PathHint` key hints a caller supplies, without verifying that the hints or messages correspond to an actual, real, user-approved coin spend.

### Finding Description
`WalletSigner.execute_signing_instructions` (`chia/wallet/wallet_signer.py:140-253`) is designed for the CHIP-0029 blind-signer protocol: it takes `SigningInstructions` (arbitrary `SigningTarget(fingerprint, message, hook)` entries plus `SumHint`/`PathHint` key hints) and returns BLS signature shares.

Two properties combine into a signing oracle:

1. The wallet's own root key is always available for direct signing: `sk_lookup` is seeded with `{root_pubkey.get_fingerprint(): root_private_key}` (`chia/wallet/wallet_signer.py:143-148`). If a `SigningTarget.fingerprint` matches the root fingerprint, the code signs the caller-supplied `target.message` verbatim with the wallet's real private key with no relation check to any coin, puzzle, or pending transaction: [1](#0-0) 

2. For `SumHint`-based signing (used for synthetic/hidden-puzzle keys), the caller supplies `final_pubkey` and `synthetic_offset` directly, and the code never verifies that `final_pubkey == component_pubkey + offset_pubkey*G`. It simply trusts the caller's claim, derives `offset_sk = PrivateKey.from_bytes(sum_hint.synthetic_offset)` (fully attacker-controlled), and signs the caller's `message` using `AugSchemeMPL.sign(sk, message, final_pubkey)` where `final_pubkey` is the caller's claimed (unverified) identity: [2](#0-1) [3](#0-2) 

The RPC endpoint that exposes this directly to any local RPC caller is: [4](#0-3) 

Nowhere in this path is `signing_instructions` cross-checked against a real `CoinSpend`/`SpendBundle` that the wallet itself constructed via `gather_signing_info` from an actual owned coin (that check only happens in the separate `gather_signing_info` path, `chia/wallet/wallet_signer.py:94-117`, which is not enforced as a precondition for `execute_signing_instructions`). Any caller who can reach the wallet RPC can submit hand-crafted `SigningInstructions` and receive a valid signature over an arbitrary message, augmented under an arbitrary (unverified) claimed pubkey — analogous to HTCondor's IDTOKENS flaw of accepting a claimed identity without validating its binding, "signing" as an identity/spend the wallet never legitimately reviewed or intended to authorize.

### Impact Explanation
A malicious local RPC caller (e.g. a compromised or unauthorized local application, browser-based dApp with RPC access, or CHIP-0029 external tooling integration) can obtain the wallet's actual private-key signature over an attacker-chosen message (e.g. `delegated_puzzle_hash + coin.name() + AGG_SIG_ME_ADDITIONAL_DATA` for any coin controlled by the user's root key/derived keys), without the wallet's normal transaction-construction, review, or `push_tx`/`select_coins` flow ever validating what is being authorized. This signature share can then be combined into a full `SpendBundle` and submitted to the mempool, resulting in unauthorized/unsigned-looking coin movement executed under the guise of the legitimate owner's key — i.e., concrete unauthorized coin movement satisfying the "Validate" criteria (unauthorized coin movement via a spend-triggered path).

### Likelihood Explanation
The `execute_signing_instructions` RPC endpoint is reachable by any local caller with wallet RPC access — the same trust boundary explicitly listed as in-scope ("local RPC caller"). No additional privileges beyond RPC access are required; the endpoint performs no validation binding the supplied `SigningInstructions` to a real, wallet-tracked coin spend, making exploitation straightforward for any caller that can reach the wallet RPC surface (including third-party software integrating with the CHIP-0029 blind-signer flow).

### Recommendation
`execute_signing_instructions` (and the underlying `WalletSigner.execute_signing_instructions`) should not blindly sign caller-supplied messages/targets. At minimum:
- Verify that `SumHint.final_pubkey` is mathematically consistent (`final_pubkey == Σ component_pubkeys + offset_pubkey*G`) before using it as the augmentation key.
- Cross-check that each `SigningTarget.message`/`fingerprint` actually derives from a `CoinSpend`/AGG_SIG condition the wallet independently computed (e.g., only accept `SigningInstructions` previously produced by `gather_signing_info` for coins actually owned/tracked by this wallet, or re-derive expected messages server-side and reject mismatches).
- Consider requiring explicit user confirmation/audit trail before signing instructions not derived from the wallet's own `gather_signing_info` output.

### Proof of Concept
1. As a local caller with wallet RPC access, call `execute_signing_instructions` with:
   - `SigningInstructions(key_hints=KeyHints(sum_hints=[], path_hints=[]), targets=[SigningTarget(fingerprint=root_pubkey_fingerprint_bytes, message=<attacker_chosen_bytes>, hook=<any_bytes32>)])`
2. Per `chia/wallet/wallet_signer.py:206-212`, the wallet signs `<attacker_chosen_bytes>` directly with the wallet's root private key and returns the signature, with no verification that this message corresponds to any real transaction.
3. Alternatively, supply a `SumHint(fingerprints=[root_pubkey_fingerprint], synthetic_offset=<attacker_chosen_32_bytes>, final_pubkey=<attacker_chosen_pubkey_bytes>)` plus a matching `SigningTarget` — per `chia/wallet/wallet_signer.py:188-218`, the wallet returns a signature share bound to the attacker's own chosen `final_pubkey`/message, which the attacker can complete since they know `offset_sk` themselves.
4. The resulting signature(s) can be assembled into a `SpendBundle` and pushed via `submit_transactions`/`push_tx`, moving coins without having gone through the wallet's normal transaction validation/review flow.
