### Title
Recursive `git clone` explicitly disables Git's built-in clone-protection hardening, re-enabling hook-based RCE from a malicious repository - (File: `app/src/lib/git/clone.ts`)

### Summary
Git added `GIT_CLONE_PROTECTION_ACTIVE` as an internal hardening flag (following the 2024 Git security advisories, e.g. CVE-2024-32002/32004, about `git clone --recursive` allowing embedded/nested repositories or symlinked `.git` directories to smuggle hooks that get executed automatically during clone). Git's own clone implementation refuses (or protects against) these unsafe recursive-clone scenarios unless this protection has been explicitly deactivated. GitHub Desktop's `clone()` function unconditionally sets this variable to `'false'` for every clone, i.e. it deliberately turns Git's own anti-RCE hardening off for every recursive clone it performs.

### Finding Description
`clone()` in `app/src/lib/git/clone.ts` builds the environment for the `git clone --recursive` invocation and explicitly forces: [1](#0-0) 

This happens for every single clone performed through Desktop's UI (New/Clone repository, "Clone Again", "Open in Desktop" deep links, opening a PR from a URL, etc.), with no user prompt and no way to opt back into Git's own protection. The `clone()` function does not pass `interceptHooks` at all, so this clone path is also *not* covered by Desktop's own hooks-interception/sandbox mechanism (`withHooksEnv` / `hooks-proxy.ts`) that is used for other operations like `push`, `pull`, `merge`, and `commit`: [2](#0-1) [3](#0-2) 

That interception mechanism runs hooks through a controlled `process-proxy` and surfaces `onHookFailure`/`onHookProgress` to the UI: [4](#0-3) 

Clone bypasses both layers of defense at once: (1) it disables Git's own upstream hardening against hook execution from nested/symlinked submodules during recursive clone, and (2) it never routes through Desktop's hook proxy that could otherwise intercept or gate hook execution. The only guard present in `clone()` is `isClonePathSensitive()`, which only checks the *destination path* on disk (e.g. not `$HOME`, `.ssh`, `.gnupg`) — it does nothing to validate the *contents* of the remote repository being cloned, which is exactly what `GIT_CLONE_PROTECTION_ACTIVE` was designed to police: [5](#0-4) 

### Impact Explanation
An attacker who controls a public/shared Git repository (the untrusted, attacker-controlled artifact required by the report's valid-impact scope) can craft a repository containing a submodule or nested `.git` directory structure that would normally be rejected or neutralized by Git's clone-protection checks. Because Desktop forces `GIT_CLONE_PROTECTION_ACTIVE=false` on every `git clone --recursive` it runs, the underlying `git` binary proceeds as if that hardening were absent, allowing an embedded hook (e.g. `post-checkout`) placed via the crafted submodule structure to execute arbitrary code as soon as the victim clicks "Clone" in GitHub Desktop (or opens an `x-github-client://` clone/PR deep link that routes through `openOrCloneRepository`/`clone()`). This is code execution outside of any expected sandbox, triggered purely by the victim cloning a repository they were led to open — matching the report's "attacker controls a cloned repository → code execution" impact class exactly.

### Likelihood Explanation
Every clone performed by Desktop takes this code path unconditionally — there is no feature flag, setting, or fallback that re-enables the upstream protection, and no interactive warning is shown to the user (unlike the "unsafe directory" warnings shown elsewhere, e.g. `app/src/ui/add-repository/add-existing-repository.tsx` and `app/src/ui/missing-repository.tsx`, which explicitly warn about "adding untrusted repositories may automatically execute files"). Because `--recursive` is always passed, the attack surface is any repository with attacker-controlled submodules, which is trivial to construct and requires zero additional user interaction beyond a normal "Clone repository" action or clicking a clone/"Open in Desktop" link — well within the required unprivileged-attacker/no-local-access constraints.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE=false`. Rely on Git's own default (protection-active) behavior for `git clone --recursive`, and if a legitimate reason exists to disable it (e.g. compatibility with older Git builds or specific workflows), gate that behind an explicit, narrowly-scoped condition with a corresponding UI warning to the user, consistent with the existing "untrusted/unsafe repository" warnings already used elsewhere in Desktop. Route clone through the same `interceptHooks`/hook-proxy machinery used by `push`/`pull`/`merge`/`commit` so hook execution during clone can at minimum be observed, gated, or disabled consistently with the rest of the app.

### Proof of Concept
1. Attacker publishes a Git repository containing a submodule (or nested `.git` layout) crafted to exploit the recursive-clone hook-execution weakness that `GIT_CLONE_PROTECTION_ACTIVE` is designed to prevent (e.g. a `post-checkout`/similar hook reachable via the nested/symlinked structure).
2. Attacker shares the repository URL, a GitHub Desktop clone deep link, or a PR link.
3. Victim opens GitHub Desktop and clicks "Clone" (or clicks the deep link, which flows through `dispatcher.ts`'s `openOrCloneRepository`/`openPullRequestFromUrl` into `clone()`).
4. `clone()` executes `git -c init.defaultBranch=... clone --recursive ... -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment: [6](#0-5) 
5. Because Git's clone-protection hardening is disabled, the embedded hook executes automatically during the recursive clone/checkout, running attacker-controlled code on the victim's machine with no prompt or warning from Desktop.

Note: I could not execute Git itself to empirically reproduce the exact upstream CVE trigger conditions (this is a static code-review finding based on the presence and unconditional use of `GIT_CLONE_PROTECTION_ACTIVE=false`); a background agent with a full checkout and ability to run `git`/`dugite` locally would be needed to build a concrete crafted-submodule repository and confirm hook execution end-to-end.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
