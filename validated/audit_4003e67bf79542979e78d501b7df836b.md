### Title
`distribution.rewards()` accepts `msg.value` with no non-payable guard and no refund, permanently stranding sent ETH/usei/wei - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile's `rewards(address)` view method is dispatched without any payability check, unlike every other guarded method in the same `Execute` switch. If a caller sends non-zero `value` alongside a call to `rewards`, the EVM will have already credited that value to the precompile's account balance as part of standard `CALL` value-transfer semantics before the precompile logic runs, and `rewards()` never refunds it (unlike other payable precompile methods that explicitly call `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` to route received value back to the payer). The result is a fund-loss bug analogous to the `Starklane::depositTokens` report: value sent by an unprivileged EVM caller is silently accepted and never returned.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches all view/query methods through a `switch` on `method.Name`. Every other guarded state-changing/payable method either validates non-payability (`pcommon.ValidateNonPayable(value)`) or explicitly processes `value` via `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` (which both debit and then refund the payer, since the precompile's Sei account was already credited by the EVM's native value-transfer): [1](#0-0) 

The `RewardsMethod` case, however, dispatches directly to `p.rewards(ctx, method, args)` with no `value` parameter at all and no `pcommon.ValidateNonPayable` call: [2](#0-1) 

This is explicitly documented as a known guard gap in the integration test suite: [3](#0-2) [4](#0-3) 

Contrast with `pcommon.HandlePaymentUsei`, used by every properly-guarded payable method, which explicitly refunds the payer because "the following precompile logic will debit the payments from payer's account" — confirming that value sent to a precompile call is first credited to the precompile's own account by EVM CALL-value semantics and must be manually routed back: [5](#0-4) 

Since `rewards()` performs no such refund, and the distribution precompile address (`0x...1007`) is not an address any user or process can withdraw from via a normal transaction (it is a fixed precompile/module address, not an EOA or a contract with a withdrawal function), any wei sent alongside a `rewards()` call is permanently stuck.

### Impact Explanation
This causes direct, permanent, and unrecoverable loss of user funds (ETH/usei/wei) for any unprivileged EVM caller who sends `msg.value` while calling `distribution.rewards()`, whether directly via `eth_call`/a mined tx, or unintentionally via a naive integrating contract that forwards `msg.value` to every external call. There is no path to reclaim the stranded balance — it sits on the precompile's underlying Sei account with no owner key and no withdrawal method. This matches the "Medium/High: concrete fund loss or permanent freezing" acceptance bar.

### Likelihood Explanation
Likelihood is moderate: it requires the caller to deliberately (or by integration bug) attach non-zero `value` to a `rewards()` call, which is a low-value view function that a rational caller wouldn't normally pay ETH for. However, since it's directly reachable by any public RPC client or contract with a single transaction/eth_call and no privilege, and the test suite itself flags it as a known guard-table gap ("Don't generalize dispatch tests; copy the per-method guards from the Go source"), it's a real, exploitable/inadvertent-loss surface rather than theoretical.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check for the `RewardsMethod` case in `Execute` (as done for `WithdrawValidatorCommissionMethod` and other view methods), rejecting any call to `rewards()` that carries non-zero `value`, consistent with the guard pattern used by all other Cosmos precompile view methods in this codebase.

### Proof of Concept
1. From an unprivileged EVM account, associate a Sei address and call `distribution.rewards(delegatorAddress)` on the distribution precompile at `0x0000000000000000000000000000000000001007`, attaching a non-zero `value` (e.g., 1 wei or 1 ether) to the call via a standard `LegacyTx`/`eth_call`.
2. Observe that the call succeeds and returns reward data, unlike every other view method in the suite (e.g., `params`, `validatorOutstandingRewards`) which revert with `execution reverted` when `value` is non-zero (per `pcommon.ValidateNonPayable`).
3. Query the caller's post-tx EVM balance: it is reduced by the `value` sent (standard EVM CALL semantics debit the caller and credit the callee/precompile address).
4. There is no function on the distribution precompile, nor any other module, that allows recovering funds credited to the precompile's account address — the value is permanently stranded, analogous to the underpaid/overpaid `msg.value` being lost in the `Starklane::depositTokens` report. func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
}
