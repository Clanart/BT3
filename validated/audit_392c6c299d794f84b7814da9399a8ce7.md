### Title
Unvalidated `kip71.gastarget` governance parameter allows division-by-zero panic in KIP-71 base fee calculation - ([File: params/kip71_config.go])

### Summary
`Kip71GasTarget` is a mutable governance parameter that can be updated via the governance voting mechanism, but its `FormatChecker` performs no validation at all, unlike its sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero.

### Finding Description
In the governance parameter table, `Kip71GasTarget` uses `noopFormatChecker`, which accepts any `uint64` value including `0`: [1](#0-0) 

Compare this to `Kip71BaseFeeDenominator`, which the codebase explicitly guards against a zero value because it is used as a divisor: [2](#0-1) 

`GasTarget` is however also used as a divisor in `NextMagmaBlockBaseFee`, the KIP-71 base-fee update formula: [3](#0-2) 

Specifically, when `parentGasUsed != gasTarget`, the code computes `x.Div(x, new(big.Int).SetUint64(gasTarget))` in both the "increase" and "decrease" branches. If `gasTarget == 0`, this is a division by zero, which causes `math/big.Int.Div` to panic. This function is invoked on every block by block builders/validators (worker header preparation, tx pool base-fee-dependent logic, block validation, gas price oracle) to compute or verify the base fee: [4](#0-3) 

### Impact Explanation
If `kip71.gastarget` is ever set to `0` (no validation prevents this), every node that reaches this code path while preparing or validating the next block's base fee will panic, crashing the node process. Because `NextMagmaBlockBaseFee` is called from multiple locations that participate in ordinary block production and validation, transaction fee estimation (`gasprice` package), and mempool processing (`blockchain/tx_pool.go`), this is reachable by the normal flow of processing any subsequent block/transaction once the parameter takes effect — it is not limited to a malicious validator or peer message. A chain-wide crash of full/consensus nodes is a severe availability impact (chain halt), which is a valid Medium/High severity analog of the original bug class (an unvalidated administrative/governance parameter creating a state that breaks normal, unprivileged transaction processing).

### Likelihood Explanation
Likelihood is low-to-moderate: setting `kip71.gastarget` requires governance-level authority (the governing node or contract governance), which is a privileged action analogous to the `auth`-gated `setStakedAmountLimit` in the original report. However, exactly like the original bug, the actual damage (panic/DoS) is triggered passively by ordinary subsequent block processing without requiring any additional unprivileged transaction — making it comparable in likelihood/impact shape to the reported issue (privileged misconfiguration silently breaking normal operation for everyone).

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects zero (and any other value that would make the KIP-71 base fee formula ill-defined), mirroring the existing check on `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, consider adding a defensive zero-check inside `NextMagmaBlockBaseFee` itself (similar to the existing `BaseFeeDenominator == 0` fallback) so that even a pre-existing genesis/chain-config value of zero cannot crash the node.

### Proof of Concept
1. As the governing node (or via contract governance), submit a vote/transaction setting `kip71.gastarget` to `0`. No validation in `Params[Kip71GasTarget].FormatChecker` rejects this value [1](#0-0) .
2. Once this parameter takes effect at the target block, any node computing the next block's base fee via `NextMagmaBlockBaseFee` with `parentHeaderGasUsed != 0` enters the `parentGasUsed > gasTarget` (or `<`) branch [5](#0-4) .
3. The line `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` executes `big.Int.Div` with a zero divisor, which panics.
4. Because this function is called from block production/validation and fee-estimation code paths reachable during normal (unprivileged) block/transaction processing, all nodes reaching this code panic, resulting in a chain-wide denial of service.
