### Title
`Verifier::is_deposit_valid` accepts a self-funded ReplacementDeposit output that merely copies an honest `old_move_txid` without any check that the funds actually derive from spending that MoveToVault UTXO - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` (core/src/verifier.rs:541-732) validates a `ReplacementDeposit` purely by recomputing the expected Taproot output script from `ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid)` <cite repo="Kirstentat/clementine--008" path="core/src/verifier.rs" start="659="672" end="672" /> and checking that the on-chain `deposit_outpoint` UTXO matches that script/amount and is confirmed above `start_height`. It never verifies that the UTXO funding `deposit_outpoint` is the actual output of a transaction that spent the real `old_move_txid` MoveToVault output — the check is address-format equality, not spend-provenance equality.

### Finding Description
The binding the protocol needs is: `deposit_outpoint` (the UTXO backing a `ReplacementDeposit`) == the direct output of a transaction that consumed the honest `old_move_txid`'s MoveToVault output under the N-of-N + security-council script (i.e. `create_replacement_deposit_txhandler`'s input is that exact UTXO, see core/src/builder/transaction/mod.rs:404-446). What `is_deposit_valid` actually checks is a weaker equality: `deposit_txout_in_chain.script_pubkey == expected_scriptpubkey` where `expected_scriptpubkey` is deterministically derived only from `(nofn_xonly_pk, old_move_txid, security_council)` via `generate_replacement_deposit_address`/`get_deposit_scripts` [1](#0-0) , plus amount and confirmation depth [2](#0-1) .

Because `nofn_xonly_pk`, `old_move_txid`, and `security_council` are all public, anyone can compute this exact Taproot address offline (`generate_replacement_deposit_address`, core/src/builder/address.rs:89-103) and pay into it from their own self-funded UTXO. `is_deposit_valid` never inspects the *inputs* of the transaction that created `deposit_outpoint`, so it cannot distinguish "output produced by spending the real old_move_txid vault" from "output produced by a random third party funding the same address independently." There is also no DB uniqueness constraint tying one `old_move_txid` to at most one deposit: `insert_deposit_data_if_not_exists` only enforces `ON CONFLICT (deposit_outpoint) DO NOTHING` [3](#0-2) , not on `move_to_vault_txid`/`old_move_txid`. `get_deposit_data_with_move_tx` (core/src/database/operator.rs:432-454) only looks up by the *new* deposit's own computed `move_to_vault_txid`, never by `old_move_txid`, so it provides no cross-check either.

Exploit flow: attacker computes `TX_H` (an honest, confirmed, completed BaseDeposit→MoveToVault txid), derives `addr = generate_replacement_deposit_address(TX_H, nofn_xonly_pk, network, security_council)`, funds `addr` from their own wallet, then calls the aggregator's public `new_deposit`/`deposit_sign` gRPC path with `DepositType::ReplacementDeposit{old_move_txid: TX_H}` and `deposit_outpoint` pointing at their self-funded UTXO. `is_deposit_valid` passes all checks and each verifier proceeds to `deposit_sign`, producing N-of-N partial signatures for a brand-new move-to-vault transaction that carries `TX_H` in its committed script data as "the vault it replaces," even though nothing was ever spent from `TX_H`.

### Impact Explanation
This produces N-of-N partial signatures over a move-to-vault spend that is not authorized by any actual consumption of the honest depositor's `TX_H` UTXO, and it lets an attacker cheaply mint a second, self-funded deposit that *claims* the lineage of another depositor's already-finalized vault. However, the real bridge value transfer requires the attacker's own self-funded UTXO of `bridge_amount` — the attacker is not able to move TX_H's actual BTC out (that would still require signing an input locked by the real nofn key, which needs verifier cooperation on that specific input, not merely matching a script template). The demonstrable, in-scope damage is limited to: verifiers being tricked into presigning a deposit/move-to-vault referencing a false `old_move_txid` predecessor, i.e. "N-of-N partial signatures for a spend no Citrea withdrawal authorises" over the *attacker's own funded UTXO* — not a drain of the honest depositor's TX_H funds, since `TX_H`'s output is never touched by the crafted transaction.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: they need only broadcast a standard transaction paying `bridge_amount` into a publicly-derivable Taproot address, then call the aggregator's public gRPC endpoints (`new_deposit`, `deposit_sign`) as an unprivileged user — no verifier keys, no security-council cooperation, and no interaction with the honest depositor are required. Cost is one on-chain transaction plus bridge_amount of attacker's own BTC (recoverable since it's the attacker's UTXO backing the new deposit). This is repeatable against any confirmed `old_move_txid`, honest or otherwise.

### Recommendation
`is_deposit_valid` must verify spend provenance, not just script-template equality, for `ReplacementDeposit`: fetch the actual transaction that created `deposit_outpoint`, confirm its single input directly spends the real `old_move_txid` MoveToVault output (correct previous txid/vout, correct witness/script path proving the CheckSig(old_nofn_xonly_pk)+security-council script was used), and enforce a DB/consensus-level uniqueness constraint so a given `old_move_txid` can back at most one accepted `ReplacementDeposit`.
