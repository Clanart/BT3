### Title
Overpaid native-token dispatch fees are permanently stranded in `EvmHost` instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all forward the caller's entire `msg.value` into a Uniswap-style `swapETHForExactTokens` call, even though only the exact `fee`/`amount` argument is required. Just like the CBridge finding — where sending more native token than required left the surplus stuck in the facet — any native-token surplus here is refunded by the swap router back to `msg.sender` of that internal call, which is `EvmHost` itself, not the original dApp/user who overpaid. There is no accounting or recovery path for this stranded ETH.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

Each of these functions does `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`, sending the *entire* `msg.value` even though the swap only needs enough ETH to produce `fee`/`amount` units of `feeToken`. Standard `UniswapV2Router02.swapETHForExactTokens` (and the project's own custom wrapper, which explicitly mimics this behavior) refunds any unused ETH to `msg.sender` of the swap call: [4](#0-3) 

Because `EvmHost` itself is the caller of the router/wrapper (not the original transaction sender), this refund lands in `EvmHost`'s own balance. The functions that call `dispatch`/`fundRequest` upstream — e.g. `WrappedHyperFungibleToken.send`, `HyperFungibleToken.send`, `ExtrinsicIntents` fill/cancel flows, and any third-party `IApp` calling `IDispatcher(host).dispatch{value: msg.value}(...)` per the documented pattern — assume the Host will only consume what it needs and are not written to recover a refund from the Host, since the Host provides no such refund mechanism to callers: [5](#0-4) 

There is no `receive()`/withdraw path visible for arbitrary native ETH balance in `EvmHost` other than fee-token revenue withdrawal reachable by the `hostManager` governance actor — meaning any ETH overpayment beyond the exact swap requirement becomes permanently non-recoverable protocol-held ETH, unless a future host-manager governance action happens to sweep it (which is not guaranteed and out of the caller's control).

### Impact Explanation
Any unprivileged user or contract that dispatches a POST/GET request or funds a request while paying with native tokens and supplies `msg.value` even slightly above the exact amount required for the fee-token swap (a common and easy-to-make mistake, since callers typically add slippage buffer when quoting Uniswap swaps) will have the surplus permanently trapped in `EvmHost`. This is a direct loss-of-funds bug for end users interacting with a core, always-reachable public entrypoint (`dispatch`, `fundRequest`), matching the required impact category "stealing or loss of funds."

### Likelihood Explanation
High likelihood: `dispatch{value: msg.value}` and `fundRequest{value: msg.value}` are the documented, expected way for applications to pay native-token fees (see `docs/content/developers/evm/messaging/post-requests.mdx`), and slippage/quote buffers make exact-value payments unlikely in practice. No malicious peer, relayer, or admin action is needed — a normal user transaction triggers the loss.

### Recommendation
After the Uniswap swap, compute the actual ETH consumed (`amounts[0]` returned by `swapETHForExactTokens`) and refund `msg.value - amounts[0]` back to `_msgSender()` (the original caller), rather than allowing the swap router to return the excess to `EvmHost` itself. Alternatively, quote the exact input amount before swapping and require `msg.value == requiredAmount`, reverting otherwise, matching the fix pattern from the CBridge report (`>=` → `==`).

### Proof of Concept
1. A user calls `WrappedHyperFungibleToken.send{value: quotedFee + buffer}(params)` with a small buffer over the quoted fee (common practice to avoid revert on slippage).
2. `send()` forwards the entire remaining `msgValue` to `IDispatcher(_host).dispatch{value: msgValue}(request)`. [6](#0-5) 
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, ...)` is called; only `post.fee` worth of ETH is consumed by the swap. [1](#0-0) 
4. The router/wrapper refunds the unused ETH to its `msg.sender`, which is `EvmHost`, not the original user. [4](#0-3) 
5. The buffer ETH is now permanently held by `EvmHost` with no code path returning it to the user.
