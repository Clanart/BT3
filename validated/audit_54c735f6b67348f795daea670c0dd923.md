### Title
Insufficient Gas for State Persistence in IBC Callbacks - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
The `x/ibc/callbacks` module is vulnerable to a gas-depletion attack that prevents the persistence of failed IBC packet execution state. When an IBC callback is executed, the system uses a cached context with a gas limit specified in the packet's `memo`. If the EVM execution consumes nearly all of this allocated gas (e.g., through a malicious `onERC721Received` hook or expensive computation), the remaining gas is insufficient to complete the Cosmos SDK's mandatory state updates or to properly record the failure. Because the system relies on the `63/64` rule and a manual gas consumption model, an attacker can cause the entire `OnRecvPacket` flow to revert at the SDK level, leading to blocked IBC channels or inconsistent accounting between the EVM and the bank module.

### Finding Description
In `x/ibc/callbacks/keeper/keeper.go`, the `IBCReceivePacketCallback` function executes EVM calls using a `cachedCtx` with a gas limit derived from `cbData.CommitGasLimit` [1](#0-0) . 

The vulnerability manifests in two ways:
1. **Gas Limit Enforcement:** The code retrieves the remaining gas from the `cachedCtx` and passes it as the `gasCap` to `CallEVM` [2](#0-1) . If the EVM execution uses almost all the provided gas, the subsequent call to `ctx.GasMeter().ConsumeGas(res.GasUsed, ...)` might succeed, but the remaining gas in the original `ctx` becomes negligible [3](#0-2) .
2. **Post-Execution Invariants:** After the EVM call, the keeper performs a balance check to ensure the "isolated address" has no remaining tokens [4](#0-3) . If the attacker crafts a contract that consumes gas until only a few hundred units remain, this balance check (which involves a `StateDB` read or bank query) will trigger an "Out of Gas" panic in the base context.

Unlike standard Ethereum where the `63/64` rule (EIP-150) ensures 1/64th of gas remains for the caller to handle reverts, the Cosmos SDK `GasMeter` will panic immediately if `ConsumeGas` exceeds the limit. If this happens during the callback execution in `OnRecvPacket`, the entire transaction reverts, preventing the IBC module from writing the `ErrorAcknowledgement`. This results in the packet being retriable indefinitely (blocking the channel) or failing to settle correctly.

### Impact Explanation
**Critical.** An unprivileged user can send a specially crafted IBC packet that:
- **Blocks IBC Channels:** By causing a revert in the `OnRecvPacket` logic instead of returning an `ErrAck`, the packet is never "processed," effectively halting the channel.
- **Accounting Corruption:** If tokens were minted/un-escrowed before the callback but the final state persistence fails due to OOG, it can lead to discrepancies between the `x/erc20` and `x/bank` modules.
- **Chain Halt:** If triggered in a high-throughput environment, it can be used to DoS specific bridge pathways.

### Likelihood Explanation
**Medium.** It requires the attacker to deploy a contract on the destination chain (or use an existing one with hooks like `onERC721Received`) and send an IBC transfer to it with a specific `gas_limit` in the `memo`.

### Recommendation
1. **Gas Reserve:** Implement a minimum gas reserve (e.g., 50,000 gas) that must remain after the EVM execution to ensure Cosmos-side state cleanup and acknowledgement writing can complete.
2. **Safe Minting:** Use `mint` instead of `safeMint` in internal bridge logic to avoid triggering external contract hooks during the sensitive callback execution phase.
3. **Graceful Failure:** Ensure that "Out of Gas" during the callback is caught and converted into an `ErrorAcknowledgement` rather than allowing the panic to bubble up to the IBC handler.

### Proof of Concept
1. Attacker deploys a contract `MaliciousReceiver` on Chain B.
2. `MaliciousReceiver` implements a function that runs a loop until `gasleft() < 2000`.
3. Attacker sends an IBC transfer from Chain A to Chain B with a `memo` containing:
   ```json
   {
     "dest_callback": {
       "address": "MaliciousReceiverAddr",
       "gas_limit": "200000",
       "calldata": "0x..."
     }
   }
   ```
4. Chain B receives the packet. `IBCReceivePacketCallback` is called.
5. The EVM call executes the malicious loop, leaving only 1,500 gas.
6. `IBCReceivePacketCallback` attempts to call `k.erc20Keeper.BalanceOf(...)` [5](#0-4) .
7. The `BalanceOf` call (requiring ~2,500+ gas for KVStore access) triggers an SDK panic.
8. The entire IBC `OnRecvPacket` reverts; no acknowledgement is written; the channel is blocked.
