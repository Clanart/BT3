### Title
Unchecked amount arithmetic lets crafted payment data produce an invalid signed transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` performs unchecked `u64` summation, multiplication, and addition over attacker-influenced input values, payment amounts, and fee rates. A crafted payment set can wrap `payment_sat + needed_fee` below `input_sat`, bypassing the insufficient-funds check and producing a transaction whose outputs exceed its inputs. In debug builds the arithmetic may panic; in release builds it wraps and the resulting invalid transaction is passed to the Taproot signing machines. [1](#0-0) 

### Finding Description
The analogous integer-mishandling flaw exists in Bitcoin transaction construction. `input_sat` and `payment_sat` are accumulated with `sum::<u64>()`, `needed_fee` is computed with unchecked multiplication, and the balance test uses unchecked addition. None of these operations use `checked_*`, despite the source values being serialized Bitcoin amounts or externally supplied payment parameters. [2](#0-1) [3](#0-2) 

For example, a single requested payment of `u64::MAX` satoshis makes `payment_sat` itself valid as a `u64`, while `payment_sat + needed_fee` wraps to `needed_fee - 1`. If the claimed input total is greater than that wrapped value, `NotEnoughFunds` is not raised and a `TxOut` worth `u64::MAX` satoshis is installed. [4](#0-3) [5](#0-4) 

The transaction is then used to generate Taproot signature hashes, one for each input, and those hashes are signed by the FROST machines. [6](#0-5) 

### Impact Explanation
An attacker who can cause an integrator to construct a transaction from crafted payment data can make Serai sign an unintended Bitcoin transaction that cannot be validly accepted by the network. In debug or overflow-checking builds, the same arithmetic can panic before signing, creating denial of service. In release builds, the signing machines commit to sighashes for a malformed transaction whose declared output set was not properly constrained by the available inputs. This is a reachable arithmetic-integrity failure rather than a cryptographic break. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
The vulnerable path is exposed through the public `SignableTransaction::new` API and requires only control over payment/output parameters or fee rate, together with a selected `ReceivedOutput` set. It does not require compromising validators, peers, secret shares, RPC, or consensus. The strongest impact is limited to signing an invalid transaction or crashing under checked arithmetic; it does not by itself create spendable Bitcoin. [9](#0-8) [7](#0-6) 

### Recommendation
Use checked arithmetic for every monetary total and fee computation in `SignableTransaction::new` and `fee`. In particular:

- Replace both `sum::<u64>()` calls with `try_fold`/`checked_add`.
- Compute `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change` with `checked_mul`.
- Compute `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`.
- Reject overflow with a distinct `TransactionError` instead of wrapping or panicking.
- Optionally enforce Bitcoin's consensus maximum money supply on each `TxOut` and on aggregate inputs/outputs before constructing the transaction.
