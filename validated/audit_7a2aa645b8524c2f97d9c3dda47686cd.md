### Title
`fetchPushControl` fails open to "fully pushable" on API/network error, silently hiding branch-protection warnings - (File: `app/src/lib/api.ts`)

### Summary
The Sherlock report's broken invariant is: *when a security-relevant computation cannot be performed, the code silently falls back to the most permissive/cheapest outcome instead of the most conservative one.* The direct analog in GitHub Desktop is `API.fetchPushControl` in `app/src/lib/api.ts`, whose doc comment explicitly states: "Note: if request fails, the default returned value assumes full access for the user." [1](#0-0)  This value feeds directly into `isBranchPushable`, which drives whether Desktop shows the user a "this branch is protected" warning before they commit/push. [2](#0-1) [3](#0-2) 

### Finding Description
`refreshBranchProtectionState` in `app-store.ts` calls `api.fetchPushControl(owner, name, branchName)` and treats the response as authoritative for `currentBranchProtected = !isBranchPushable(pushControl)`. [3](#0-2) 

`fetchPushControl` wraps the GitHub API request in a try/catch. On *any* failure — a network blip, a transient 5xx, rate limiting, a malformed/attacker-influenced response from a MITM/rogue GitHub Enterprise-style endpoint, or the GHE server simply not supporting the endpoint — it does not propagate the failure or mark the state as "unknown." Instead it returns a hard-coded object where every restriction is disabled:

```
required_signatures: false,
required_status_checks: [],
required_approving_review_count: 0,
allow_actor: true,
allow_deletions: true,
allow_force_pushes: true,
``` [4](#0-3) 

Feeding this into `isBranchPushable` yields `allow_actor !== false && noMergeRequirements === true`, i.e., the branch is reported as fully pushable and unprotected. [5](#0-4) 

Compare this to the sibling function `fetchProtectedBranches`, only a few lines below in the same file, which correctly fails closed by returning `null` (an explicit "unknown" sentinel) on error rather than an empty/permissive array. [6](#0-5)  `fetchPushControl` does not follow this pattern — it manufactures a concrete "everything allowed" object instead of signaling failure, so downstream code has no way to distinguish "confirmed unprotected" from "we couldn't check."

This is structurally identical to the Sherlock bug: when the real value (protection status / risk factor) cannot be determined, the code substitutes the cheapest/most-permissive default instead of refusing the action or defaulting to the safe/conservative state.

### Impact Explanation
`currentBranchProtected` is the value used to decide whether Desktop shows the branch-protection warning banner in the commit box (`showNoWriteAccess` / branch-protection warning path referenced in the surrounding comment). [7](#0-6)  If the push-control request transiently fails (e.g., flaky corporate network, a compromised/incorrect intermediary proxy, or a GitHub Enterprise Server that errors on this endpoint) while the user is working on a genuinely protected branch, Desktop silently drops the protection warning and treats the branch as freely pushable. A user who would normally be stopped and warned before committing to/force-pushing a protected `main`/`release` branch instead gets no warning at all, and the corrupted `currentBranchProtected = false` state can persist until the next successful refresh. This is a silent-corruption-of-what-the-user-commits-and-pushes class issue: it doesn't grant unauthorized server-side push rights (GitHub's server still enforces branch protection rules independently), but it removes Desktop's client-side guardrail exactly when it's most likely needed (transient failures, hostile proxies, or malformed API responses), causing users to attempt actions they believe are safe and be surprised by a rejected/failed push, or in the worst case to bypass a warning that would have prevented an unwanted force-push attempt on a branch they didn't realize was protected.

### Likelihood Explanation
The failure path is reached on any thrown error from `ghRequest`/`parsedResponse`, which is a broad catch (network errors, non-2xx status codes, JSON parse errors) — this is not a rare edge case in real-world usage (corporate proxies, VPNs, GHE outages, rate limiting all trigger it). No local access, admin rights, or social engineering is required; a normal user on a normal connection experiencing a transient blip or working against a non-standard GHE deployment/proxy is enough to hit it.

### Recommendation
Change `fetchPushControl` to fail closed (or fail "unknown") rather than fail open:
- Return `null` (mirroring `fetchProtectedBranches`) on error, and have `refreshBranchProtectionState` treat `null` as "protection status unknown → preserve previous state / assume protected" rather than defaulting `currentBranchProtected` to `false`.
- At minimum, do not synthesize `allow_actor: true` / `allow_force_pushes: true` / empty required-checks as the error fallback; use the most conservative values (`allow_actor: false` or a distinct "unknown" flag) so the UI can either keep showing a warning or clearly indicate the check could not be performed.

### Proof of Concept
1. Configure Desktop against a repository whose default branch has protection rules requiring reviews (so `isBranchPushable` should normally return `false`).
2. Simulate a transient failure of the push_control endpoint only (e.g., intercept/throttle that specific request via a proxy, or trigger a GHE instance that 404s/500s on `/branches/:branch/push_control` while other endpoints succeed) — this is directly analogous to the "hostile/faulty proxy response" attacker primitive in the acceptance criteria.
3. Observe in `app/src/lib/stores/app-store.ts:refreshBranchProtectionState` that `api.fetchPushControl` throws internally, is caught in `app/src/lib/api.ts`, and returns the hard-coded fully-permissive object at lines 1657-1666.
4. Observe `isBranchPushable` returns `true`, `currentBranchProtected` is set to `false`, and the commit/push UI shows no branch-protection warning despite the branch being protected server-side. [8](#0-7) [9](#0-8)

  /**
   * Get branch protection info to determine if a user can push to a given branch.
   *
   * Note: if request fails, the default returned value assumes full access for the user
   */
  public async fetchPushControl(
    owner: string,
    name: string,
    branch: string
  ): Promise<IAPIPushControl> {
    const path = `repos/${owner}/${name}/branches/${encodeURIComponent(
      branch
    )}/push_control`

    const headers: any = {
      Accept: 'application/vnd.github.phandalin-preview',
    }

    try {
      const response = await this.ghRequest('GET', path, {
        customHeaders: headers,
      })
      return await parsedResponse<IAPIPushControl>(response)
    } catch (err) {
      log.info(
        `[fetchPushControl] unable to check if branch is potentially pushable`,
        err
      )
      return {
        pattern: null,
        required_signatures: false,
        required_status_checks: [],
        required_approving_review_count: 0,
        required_linear_history: false,
        allow_actor: true,
        allow_deletions: true,
        allow_force_pushes: true,
      }
    }

export function isBranchPushable(pushControl: IAPIPushControl) {
  const {
    allow_actor,
    required_status_checks,
    required_approving_review_count,
  } = pushControl

  // See https://github.com/desktop/desktop/issues/9054#issuecomment-582768322
  // We'll guard against this being undefined until we can determine the
  // root cause and fix that.
  const requiredStatusCheckCount = Array.isArray(required_status_checks)
    ? required_status_checks.length
    : 0

  // If user is admin and branch is not admin-enforced,
  // required status checks and reviews get zeroed out in API response (no merge requirements).
  // If user is admin and branch is admin-enforced,
  // required status checks and reviews do NOT get zeroed out in API response.
  // If user is allowed to push based on `Restrict who can push` setting, they must still
  // respect the merge requirements, and can't push if checks or reviews are required for merging
  const noMergeRequirements =
    requiredStatusCheckCount === 0 && required_approving_review_count === 0

  // We check for !== false so that if a future version of the API decides to
  // remove or rename that property we'll revert to assuming that the user
  // _does_ have access rather than assuming that they _don't_.
  return allow_actor !== false && noMergeRequirements
```
