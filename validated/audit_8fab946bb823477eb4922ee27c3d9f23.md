### Title
`ThresholdView` Debug implementation leaks secret scalar and offset key-tweak material - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdView<C>` implements `fmt::Debug` and prints the `scalar` and `offset` fields verbatim. These fields are secret, ephemeral key-tweak material applied to the threshold private key (added to `included[0]`'s share). Any code path that Debug-formats a `ThresholdView` — error wrappers, `{:?}` logging, panic messages, `assert!`/`debug_assert!` output — writes the secret scalar/offset to logs, recovering the discrete-log relation between the base group key and the tweaked group key.

### Finding Description
In `crypto/dkg/src/lib.rs`, most secret-bearing structures are carefully redacted in their `Debug` impls via `finish_non_exhaustive()`:

- `ThresholdCore` prints only `params`, `group_key`, `verification_shares`, `interpolation` — `secret_share` is omitted (lines 266–276).
- `SecretShareMachine` and `KeyMachine` in `crypto/dkg/pedpop/src/lib.rs` omit `coefficients` and `secret` respectively.
- `SecretShare` prints nothing but the type name (pedpop/src/lib.rs:242–246).
- `Encryption` prints only `context`, `i`, `enc_pub_key`, and `decryption` — `enc_key` is omitted (encryption.rs:410–420).

`ThresholdView` breaks this pattern. Its manual `Debug` impl prints `scalar` and `offset` (crypto/dkg/src/lib.rs:316–328):

```rust
impl<C: Ciphersuite> fmt::Debug for ThresholdView<C> {
  fn fmt(&self, fmt: &mut fmt::Formatter<'_>) -> fmt::Result {
    fmt
      .debug_struct("ThresholdView")
      .field("interpolation", &self.interpolation)
      .field("scalar", &self.scalar)
      .field("offset", &self.offset)
      ...
```

For `C::F` types such as `dalek_ff_group::FieldElement`, `Debug` renders the canonical field element, so the raw scalar bytes are emitted. These are not public values: `ThresholdKeys::scale` / `ThresholdKeys::offset` are documented as ephemeral secrets "to allow for various account and privacy schemes" (crypto/dkg/src/lib.rs:393–417), and `offset` is summed into the first included participant's signing share inside `ThresholdKeys::view`. Anyone holding `scalar`/`offset` plus the public base `group_key` can compute the tweaked group's effective private-key correction, defeating the privacy property the scalar/offset exists to provide (e.g., unlinkable derived accounts).

### Impact Explanation
The bug class is CWE-532: insertion of sensitive information into log output. If a `ThresholdView` (or any error/path formatting it with `{:?}`) is ever logged, the secret tweak material is written to durable log storage, CI output, or aggregated logging — places an authenticated reader can extract it from. Knowledge of the scalar/offset reveals the secret correction applied to the threshold key, breaking unlinkability of tweaked keys and, for offset-only tweaks, exposing the discrete-log delta needed to reason about the effective private key. Severity is Medium because, like the referenced advisory, exposure requires a debug/log path that formats the value and an observer with log access; the crypto protocols themselves are unaffected.

### Likelihood Explanation
`Debug` is implemented precisely so callers can format the object. Rust code routinely bubbles values through `?`-returned errors, `expect`/`unwrap` panic payloads, `assert_eq!` diffs, or `format!("{view:?}")` diagnostics — all of which invoke this impl. `ThresholdView` is returned by `ThresholdKeys::view` inside `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:312) and stored in `AlgorithmSignatureMachine` (crypto/frost/src/sign.rs:433), so any generic debugging of the signing pipeline can reach it. The design intent elsewhere (consistent `finish_non_exhaustive` redaction) shows secrets were meant to be excluded; scalar/offset are simply oversights.

### Recommendation
Remove `scalar` and `offset` from the `Debug` impl of `ThresholdView` in `crypto/dkg/src/lib.rs` (lines 321–322), keeping only non-sensitive metadata (`interpolation` shape, `group_key`, `included`, `original_verification_shares`/`verification_shares` which are public group elements), and terminate with `finish_non_exhaustive()`. Audit `derive(Debug)` across in-scope crates for other secret wrappers (e.g., `EncryptionKeyMessage`, `EncryptionKeyProof` — the latter intentionally reveals an ECDH key as a blame proof, which is documented behavior and acceptable).

### Proof of Concept
```rust
use std::collections::HashMap;
use zeroize::Zeroizing;
use dkg::{ThresholdParams, ThresholdKeys, Interpolation, Participant};
use ciphersuite::Ciphersuite;
use dalek_ff_group::{Ristretto, Scalar, FieldElement, EdwardsPoint};

let params = ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap();
let mut shares = HashMap::new();
shares.insert(Participant::new(1).unwrap(), EdwardsPoint::generator() * Scalar::from(5u64));
shares.insert(Participant::new(2).unwrap(), EdwardsPoint::generator() * Scalar::from(7u64));
let keys = ThresholdKeys::<Ristretto>::new(
  params,
  Interpolation::Lagrange,
  Zeroizing::new(Scalar::from(5u64)),
  shares,
).unwrap();

// Secret offset for a privacy-preserving tweaked key
let secret_offset = Scalar::from(0xdeadbeefu64);
let keys = keys.offset(secret_offset);

let view = keys.view(vec![Participant::new(1).unwrap(), Participant::new(2).unwrap()]).unwrap();
let dbg = format!("{view:?}");
// Leaks the secret: the offset scalar is printed verbatim
assert!(dbg.contains("offset"));
```
