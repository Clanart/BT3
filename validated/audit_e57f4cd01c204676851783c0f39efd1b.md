## Title
Non-compliant ERC20 (USDT-style) reward transfer in `ArbWomUp.incentiveDeposit` uses raw `.transfer()` instead of `SafeERC20`, permanently reverting reward payouts - (File: `wombat/ArbWomUp.sol`)

### Summary
`ArbWomUp.sol` mixes `SafeERC20`-wrapped calls with a raw, non-wrapped ERC20 `.transfer()` call in the same user-facing function. The unwrapped call is made against the `usdt` token, which — like real Tether USDT — does not conform to the ERC20 standard's requirement to return a `bool` on `transfer()`. Solidity's high-level call decoding will revert whenever the token doesn't return the expected `RETURNDATASIZE`, causing every call to the reward-paying function to fail.

### Finding Description
`incentiveDeposit()` is an unprivileged, user-callable entry point that lets any wallet deposit WOM and atomically receive a USDT-denominated reward: [1](#0-0) 

Note that the contract already imports and uses `SafeERC20`/`safeTransferFrom` for the WOM deposit leg: [2](#0-1) [3](#0-2) 

but the reward payout at line 76 calls `IERC20(usdt).transfer(msg.sender, rewardToSend)` directly, bypassing `SafeERC20`. If `usdt` is (or is later configured/upgraded to) a non-compliant ERC20 like mainnet-style Tether — which returns no data on `transfer()` — Solidity will attempt to decode a `bool` from empty return data and revert the entire transaction, exactly matching the bug class described in the external report (RETURNDATASIZE mismatch reverting on successful, non-compliant transfers).

### Impact Explanation
Because the WOM deposit (`_deposit`) and the USDT reward transfer happen in the same atomic call, a non-compliant `usdt` token causes `incentiveDeposit()` to unconditionally revert on every invocation. This permanently and completely denies all unprivileged users the ability to use the incentive-deposit path: no user can ever deposit WOM for the promised USDT reward, and the USDT reward pool held by the contract becomes permanently unusable/inaccessible through the intended mechanism (no `SafeERC20`-covered path exists to release it to users). This is a permanent freezing of both the reward funds and the deposit functionality, not a temporary/gas-only issue.

### Likelihood Explanation
High, if `usdt` is configured to the real, widely-known non-compliant Tether-style token (as its very name implies). Since the failure occurs on every single call with no workaround, the DoS/freeze is deterministic and total rather than probabilistic.

### Recommendation
Replace the raw `IERC20(usdt).transfer(msg.sender, rewardToSend);` call with `IERC20(usdt).safeTransfer(msg.sender, rewardToSend);` using the already-imported `SafeERC20` library, consistent with the `safeTransferFrom` usage elsewhere in the same contract. Also audit `transferToAdmin()` at line 140, which has the same raw `.transfer()` pattern on the `wom` token.

### Proof of Concept
1. Deploy `ArbWomUp` and initialize with `_usdt` set to a token contract that mimics real USDT's `transfer()` (returns no data, e.g. a minimal contract with `function transfer(address,uint256) external {}` and no `returns (bool)`).
2. Set up `rewardMultiplier`/`rewardTier` via `setMultiplier` so `getRewardAmount` returns a non-zero value, and fund the contract with `usdt` balance.
3. Any unprivileged wallet calls `incentiveDeposit(_amount)` after approving WOM.
4. The internal `_deposit` succeeds via `safeTransferFrom`, but the subsequent `IERC20(usdt).transfer(msg.sender, rewardToSend)` at [4](#0-3)  reverts because Solidity cannot decode the missing return data as `bool`, reverting the whole transaction and permanently blocking the incentive-deposit flow for all users.
