### Title
Unbounded flood of minimum-cost bandwidth purchases evicts a victim's paid subscription before it can be consumed - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores each `(app_chain, app)`'s prepaid bandwidth as a FIFO `BoundedVec<Subscription, 1024>` (`Allowance` storage). Any unprivileged account can call `BandwidthManager.purchase()` on any source chain for any `app`/`chain` pair, at any tier, with no rate limit or per-purchase minimum relative to the list size. When the list is full, the oldest entry — regardless of its remaining, still-useful byte balance — is silently evicted (`push_subscription`, [1](#0-0) ). This is structurally the same broken invariant as the reported `stake`/`unstake` flood: an attacker can pad a bounded, FIFO/queue-like accounting structure with many low-value entries to force eviction/blocking of another party's already-paid-for value.

### Finding Description
`Allowance::<T>` keys subscriptions by `(app_chain, app)` taken from the purchase message body — not `request.source` — explicitly to let "any deployment... sponsor any app on any chain" [2](#0-1) . There is no check that only the app itself, or a privileged party, can push into this list. `on_accept` for a purchase message only validates that `request.from` matches the registered `BandwidthManager` for the request's `source` chain [3](#0-2)  — any external caller of `BandwidthManager.purchase()` can trigger a credit to an arbitrary `(chain, app)` pair as long as they pay the tier price [4](#0-3) .

`push_subscription` unconditionally evicts index 0 (the oldest, i.e., the subscription furthest along in being consumed / likely with a smaller "cheap" tier or the entry a victim is relying on) once the list hits `MAX_SUBSCRIPTIONS = 1024`: [1](#0-0) 

Nothing prevents an attacker from repeatedly purchasing the cheapest configured tier (`TierIndex` with the lowest `tierPrice`) for `months = 1` against the exact same `(chain, app)` key that a victim already funded with a large, long-duration subscription. Once 1024 attacker entries have queued up ahead of consumption, the victim's paid, unconsumed subscription is evicted and its bytes are permanently lost — `SubscriptionEvicted` is emitted, but the funds already paid for that tier are gone with no refund path. This directly mirrors the reported bug's mechanism: flood a bounded/queued accounting structure with minimal-cost entries to force out (or block confirmation of) another party's legitimately committed value.

Unlike the validator stake/unstake report where entries are near-free (1 wei), bandwidth purchases cost real money (cheapest configured tier price), so the attack is not "free," but it is still an unprivileged, single-transaction-type primitive: no protocol control ties the number of entries in the FIFO to the app's own purchasing behavior, and the eviction target (oldest = victim's still-live purchase) is deterministic and attacker-predictable.

### Impact Explanation
A successful flood causes the targeted app's already-paid bandwidth subscription to be evicted from the FIFO list before it is consumed, resulting in **loss of funds** for the victim (the fee token paid at purchase is non-refundable, and the bytes are unusable once evicted) — this matches the bounty's "loss of funds" / "logic attack" categories. Because eviction is oldest-first and unconditional, and the `Allowance` key is attacker-writable via a permissionless purchase, any third party (not the app owner, not a validator/relayer/prover) can grief a specific app's paid allowance.

### Likelihood Explanation
Likelihood is capped by economic cost: an attacker must pay `1024 × cheapest_tier_price` (potentially significant) to guarantee eviction of a specific victim entry, and must know/target the exact `(app_chain, app)` pair, which is public on-chain via `BandwidthCredited` events. This is more expensive than the original 1-wei stake/unstake flood, so likelihood is moderate rather than trivial, but the underlying protocol has zero mitigations (no per-app purchase cap, no minimum relative sizing, no protection of "large" subscriptions from small ones) — the only defense is cost, which scales linearly and predictably with the attacker's budget.

### Recommendation
- Do not evict FIFO entries purely by insertion order; consider evicting only entries that are close to expiry or below a materiality threshold, or reject new purchases while the list is full rather than silently evicting a live, materially-sized subscription.
- Add a minimum purchase-size floor relative to existing entries, or require the caller crediting an `(chain, app)` pair to be either the app itself or an allowlisted sponsor, closing the "anyone can grief any app's queue" surface.
- Alternatively, aggregate/merge subscriptions of the same tier instead of queuing unboundedly many rows, removing the incentive to spam minimum-tier purchases.

### Proof of Concept
1. Victim purchases a high-value, long-duration bandwidth tier for `app` on `chain` via `BandwidthManager.purchase()`, landing as the sole/near-sole entry in `Allowance[chain][app]`.
2. Attacker repeatedly calls `purchase(app, cheapest_tier, 1, chain)` from any account, each call dispatching a `BandwidthPurchaseMsg` that is accepted by `pallet-bandwidth::on_accept` (`modules/pallets/bandwidth/src/lib.rs` lines 454-465) since only `request.from == registered manager` is checked, not the caller of `purchase()`.
3. After 1024 attacker purchases queue ahead of/alongside the victim's entry, the next purchase's `push_subscription` call evicts index 0 — the victim's subscription — emitting `SubscriptionEvicted { lost_bytes: <victim's remaining> }` (`modules/pallets/bandwidth/src/lib.rs` lines 416-425).
4. Victim's paid-for bandwidth is permanently lost; the app is now dependent on the attacker's minimal-tier entries or has no allowance left, and the ISMP `BandwidthGate` will reject its future messages (`NoAllowance`/`Insufficient`) until it repurchases.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

        emit BandwidthPurchased({
            payer: msg.sender,
            feeToken: feeToken,
            tier: tier,
            months: months,
            amountPaid: amount,
            app: app,
            chain: chain,
            commitment: commitment
        });
    }
