### Title
Zero-share deposit due to missing output-floor check in `convert-to-shares-preview` rounding - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The vault `deposit` function computes minted shares via `convert-to-shares-preview`, which uses `mul-div-down` (round-down) with no floor-protection against a `u0` result, unlike `redeem`, which explicitly asserts `(> inkind u0) ERR-OUTPUT-ZERO`. When the share price is greater than 1 underlying-unit-per-share (i.e., `total-supply-preview < total-assets-preview`), a sufficiently small deposit rounds the minted-shares calculation down to zero, letting a depositor's funds enter the vault while they receive no zTokens, transferring value to existing shareholders.

### Finding Description
`convert-to-shares-preview` is defined identically across all vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`): [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

`mul-div-down` truncates: `(/ (* x y) z)`. When `ts < ta` (each share is worth more than one unit of underlying, e.g. after interest accrual increases `ta` relative to `ts`), a small enough `amount` produces `amount * ts / ta = 0` due to integer truncation.

The `deposit` entrypoint uses this value directly as `inkind` (shares to mint) and only checks that the *input* amount is non-zero and satisfies slippage against `min-out`, but never checks that the *output* (`inkind`) is non-zero: [2](#0-1) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
    (ok inkind)))
```

By contrast, `redeem` in the same contract explicitly guards against a zero-value conversion result: [3](#0-2) 

```
  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
```

This is the exact bug class from the external report: `to_shares` rounds an amount-to-shares conversion, and a missing/incorrect zero-output guard lets a nonzero input produce a zero output that silently transfers value instead of reverting. Here, if `min-out` defaults to `u0` (a caller can pass `min-out = 0`), `(>= inkind min-out)` is trivially satisfied even when `inkind = 0`, so a deposit of a small `amount` succeeds, `receive-underlying` pulls the caller's tokens into the vault, `(var-set assets (+ current-assets amount))` increases the vault's tracked assets, but `(ft-mint? zft 0 recipient)` mints zero zTokens. The depositor's underlying is absorbed into `assets` (raising `total-assets-preview` for everyone) while they get nothing in return — a direct transfer of value to existing zToken holders.

### Impact Explanation
This is a direct theft of user funds at rest: a depositor's underlying tokens are taken into the vault permanently while they receive zero shares, and the value is redistributed to existing shareholders through the increased `total-assets-preview` backing the same `total-supply-preview`. This satisfies the Critical impact bucket (direct theft of user funds) even though it is likely most exploitable/observable as an accidental griefing vector against unaware or naive callers who submit `min-out = 0` and a very small `amount` relative to the vault's asset-per-share ratio.

### Likelihood Explanation
Exploitability requires the vault's `total-assets-preview / total-supply-preview` ratio to be sufficiently above `1` (which naturally occurs as interest accrues and `assets` grows faster than `total-supply` since `total-supply-preview` also includes a `treasury-lp` add-on, but the ratio can still exceed 1 significantly over time) and the depositor to submit a small enough `amount` and `min-out = 0`. Since `min-out` is caller-supplied and not enforced to be `> 0`, and since the frontend or an attacker crafting a transaction for a victim (e.g., a contract auto-depositing dust) could trigger this, likelihood is plausible but depends on the ratio drifting enough for a realistic `amount` (e.g., 1 unit of the underlying's smallest denomination) to round to zero.

### Recommendation
Add an explicit `ERR-OUTPUT-ZERO`-style assertion in `deposit` (mirroring `redeem`) requiring `(> inkind u0)` before minting, in all vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`), so any deposit whose conversion rounds down to zero shares reverts instead of silently consuming the depositor's funds.

### Proof of Concept
1. Let the vault reach a state where `total-assets-preview() = TA` and `total-supply-preview() = TS` with `TS < TA` (share value > 1 underlying unit per share, e.g., `TA = 2,000,000`, `TS = 1,000,000`).
2. Caller invokes `deposit(amount = 1, min-out = 0, recipient = attacker-or-victim)`.
3. `convert-to-shares-preview(1)` computes `mul-div-down(1, 1,000,000, 2,000,000) = 0` (integer truncation).
4. `(>= inkind min-out)` → `(>= 0 0)` passes; no other check blocks `inkind = 0`.
5. `receive-underlying` transfers the depositor's `1` unit into the vault; `assets` increases by `1`; `ft-mint? zft 0 recipient` mints zero shares.
6. The depositor's `1` unit is now backing existing shareholders' redemption value with no corresponding shares issued to the depositor — fund loss for the depositor / gain for existing shareholders.
