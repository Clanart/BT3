## Title
Deterministic ProgramData PDA can be pre-funded by an attacker to permanently block program deployment via `AccountAlreadyInUse` griefing - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The external report describes a griefing pattern where a contract compares a token balance to an expected amount with strict semantics (rather than "at least"), so an attacker who sends extra funds to the relevant account can make legitimate calls permanently revert. The closest reachable analog in agave is the `UpgradeableLoaderInstruction::DeployWithMaxDataLen` handler in the BPF Loader Upgradeable program, which creates the ProgramData account at a deterministic PDA via a CPI to the System program's `CreateAccount` instruction — and `CreateAccount` rejects the call outright if the destination account already holds any lamports.

### Finding Description
When a program is deployed for the first time, `process_loader_upgradeable_instruction` handles `DeployWithMaxDataLen` by deriving the ProgramData address deterministically with `Pubkey::find_program_address(&[new_program_id.as_ref()], program_id)` [1](#0-0) , then invoking the System program via `native_invoke_signed` with a `system_instruction::create_account(...)` instruction to fund and allocate that PDA [2](#0-1) .

The System program's `create_account` implementation contains a strict check that fails the whole instruction if the destination account already has a nonzero lamport balance:
```
if to.get_lamports() > 0 {
    ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
    return Err(SystemError::AccountAlreadyInUse.into());
}
``` [3](#0-2) 

Because the ProgramData address is fully deterministic (derived only from the program's public key and the loader program ID), anyone can compute it in advance and transfer even 1 lamport to it before the legitimate deployer submits the `DeployWithMaxDataLen` transaction. This is directly analogous to the `SingleTokenJoin` bug: the check is an exact/strict comparison ("must be exactly 0 lamports") rather than a tolerant one, and an attacker can externally manipulate the account's balance to trigger the failure path, causing every subsequent deploy attempt to that program's ProgramData address to revert with `AccountAlreadyInUse`.

Notably, the codebase already recognizes this general problem class: a newer instruction, `SystemInstruction::CreateAccountAllowPrefund` (`create_account_allow_prefund`), was added specifically to support accounts that were "already had rent paid in whole or in part before creation" without failing [4](#0-3) . However, the BPF Loader's `DeployWithMaxDataLen` path still uses the older, strict `create_account` CPI rather than the prefund-tolerant variant, so it remains exposed to this griefing pattern.

### Impact Explanation
An attacker who front-runs (or simply pre-emptively funds) a program's ProgramData PDA can permanently prevent that program from ever being deployed via `DeployWithMaxDataLen`, since the derived address cannot be changed and the deployer cannot "reclaim" the lamports before their own creation instruction runs the check. This is a denial-of-service/griefing vector against any unprivileged user attempting first-time deployment of a program to a specific address, imposing negligible cost (a single lamport transfer) on the attacker versus a permanent block on the victim's deployment for that program id. It does not lead to memory corruption or privilege escalation, but it is a concrete, reachable, low-cost, high-asymmetry DoS against an unprivileged BPF Loader Upgradeable program-deployment operation.

### Likelihood Explanation
Likelihood is high for any targeted griefing scenario: the ProgramData PDA is deterministically computable off-chain by anyone from the to-be-deployed program's public key before the deploy transaction lands, so an attacker can simply send 1 lamport to it ahead of time. No special privileges, races, or validator cooperation are required — a single ordinary system transfer suffices.

### Recommendation
Change the BPF Loader's `DeployWithMaxDataLen` CPI to use the balance-tolerant creation path (e.g., `CreateAccountAllowPrefund`, mirroring the fix already implemented in `create_account_allow_prefund`) instead of the strict `system_instruction::create_account`, so that pre-existing lamports on the ProgramData address are absorbed into the resulting balance rather than causing `AccountAlreadyInUse`. Alternatively, have the loader itself pre-check/handle nonzero-but-otherwise-uninitialized destination accounts before invoking System program creation, consistent with how `create_account_allow_prefund` already tolerates prefunding elsewhere in the codebase.

### Proof of Concept
1. Compute the deterministic ProgramData PDA for a not-yet-deployed program: `Pubkey::find_program_address(&[program_id.as_ref()], &bpf_loader_upgradeable::id())` [1](#0-0) .
2. Attacker sends 1 lamport to that PDA via an ordinary System `Transfer`.
3. Victim submits `DeployWithMaxDataLen` for `program_id`; the loader CPIs into `system_instruction::create_account` for the PDA [2](#0-1) .
4. `system_processor::create_account` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse` [3](#0-2) , causing the entire deploy transaction to fail, permanently (the address cannot be changed).

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
