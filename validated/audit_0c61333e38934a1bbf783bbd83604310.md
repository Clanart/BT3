### Title
Prompt-injection-driven completion bypass via naive first-match `<promise>` tag extraction – premature/false Ralph-loop termination ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Finding Description
The stop hook determines loop completion purely from substring pattern matching against the assistant's own generated text, with no provenance/context check: [1](#0-0) 
extracts and joins all `text`-type content blocks of the last assistant message, then: [2](#0-1) 
uses a non-greedy Perl regex `s/.*?<promise>(.*?)<\/promise>.*/$1/s` to grab the content of the **first** `<promise>...</promise>` occurrence anywhere in the concatenated text, whitespace-normalizes it, and compares it literally to `COMPLETION_PROMISE` from `.claude/ralph-loop.local.md`.

`COMPLETION_PROMISE` is not a secret: it is echoed in plaintext to the model every iteration in `SYSTEM_MSG` (`plugins/ralph-wiggum/hooks/stop-hook.sh` line 160) and persisted in plaintext in the repo-local state file (`plugins/ralph-wiggum/scripts/setup-ralph-loop.sh` lines 140-150). Any content the model reads (files, tool/MCP responses) can therefore contain instructions telling the model to reproduce that exact phrase.

Because the extraction takes the **first** `<promise>` tag in the entire assistant turn without regard to surrounding context (quoting, negation, code blocks, error explanations, or prompt-injected instructions), an attacker who controls content the model reads/echoes (e.g., a compromised MCP tool response, malicious file content, or crafted repo/issue text) can embed a prompt-injection payload instructing the model to print `<promise>EXACT_PROMISE_TEXT</promise>` — even while the model is explaining that the real task is *not* done, or while merely quoting/relaying the malicious content. The hook has no mechanism to distinguish a genuine self-attested completion from an injected/echoed occurrence of the tag, so it will treat the match as authoritative and immediately delete the state file and stop the loop (`rm "$RALPH_STATE_FILE"; exit 0`), bypassing the intended "genuinely true" completion gate described in the setup script's own warnings (`plugins/ralph-wiggum/scripts/setup-ralph-loop.sh` lines 188-201).

### Impact Explanation
This is a stop-control/deny-means-deny invariant bypass: an unprivileged attacker who can influence any content the agent reads during a Ralph-loop session (MCP tool output, repository files, command output) can force premature termination of an automated iterative task by tricking the model into emitting the exact completion phrase, even though the underlying task remains incomplete or unsafe. In automation contexts where loop completion gates downstream actions (e.g., signaling "done" to a CI pipeline or a human operator), this results in an incomplete/unsafe task being falsely reported as successfully completed — a control-flow/trust-boundary bypass of the stop hook's enforcement logic.

### Likelihood Explanation
Preconditions: (1) a Ralph loop is active with a `--completion-promise` set, (2) the model at some point reads or is exposed to attacker-influenceable content (tool response, file, MCP output) during the loop, and (3) that content contains a prompt-injection instruction that causes the model to emit the tag in its own text output. Given that the exact promise text is broadcast in plaintext every iteration and stored unprotected in the state file, an attacker does not need to guess it — only to get the model to reproduce it via a successful prompt injection, which is a realistic and repeatable technique against LLM agents processing untrusted tool/file content. No allowlist, nonce, or context validation in `stop-hook.sh` prevents this.

### Recommendation
- Require the promise tag to be the sole/primary content of the assistant's final message (or appear in a dedicated, non-echoable structured field) rather than matching the first occurrence anywhere in free-form text.
- Bind the completion promise to a per-session random nonce not previously visible to any tool output, so a static, previously-disclosed phrase cannot be replayed via echoed/injected content.
- Add provenance/context checks (e.g., reject matches inside quoted/code-block sections, or immediately following tool-result echoes) before treating a match as authoritative.
- Consider requiring an explicit non-text confirmation channel (e.g., a hook-only marker) instead of relying on free-text pattern matching for security-relevant control decisions.

### Proof of Concept
Unit/integration test plan for `stop-hook.sh`:
1. Craft a transcript JSONL whose last assistant message text is: `"Tool said: <promise>DONE</promise> but the task is NOT actually finished."` where `DONE` equals the session's `completion_promise`.
2. Run `stop-hook.sh` with `HOOK_INPUT` pointing `transcript_path` at this file and a state file with `completion_promise: "DONE"`.
3. Assert the hook incorrectly outputs no `decision: block` JSON and removes `RALPH_STATE_FILE` (i.e., treats the loop as complete), despite the assistant's own text stating the task is unfinished — demonstrating the false-positive completion bypass.
4. Fuzz variant: embed the promise inside a quoted/injected block sourced from a simulated "MCP tool response" content type, confirming the same false completion trigger across whitespace/unicode-normalized variants, contrasted against a strict oracle that requires the promise to be an unquoted, standalone statement of genuine completion.

  # -0777 slurps entire input, s flag makes . match newlines
  # .*? is non-greedy (takes FIRST tag), whitespace normalized
  PROMISE_TEXT=$(echo "$LAST_OUTPUT" | perl -0777 -pe 's/.*?<promise>(.*?)<\/promise>.*/$1/s; s/^\s+|\s+$//g; s/\s+/ /g' 2>/dev/null || echo "")

  # Use = for literal string comparison (not pattern matching)
  # == in [[ ]] does glob pattern matching which breaks with *, ?, [ characters
  if [[ -n "$PROMISE_TEXT" ]] && [[ "$PROMISE_TEXT" = "$COMPLETION_PROMISE" ]]; then
    echo "✅ Ralph loop: Detected <promise>$COMPLETION_PROMISE</promise>"
    rm "$RALPH_STATE_FILE"
    exit 0
  fi
