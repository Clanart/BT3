### Title
Stale line-index diff selection is applied against a freshly re-fetched diff during commit, silently corrupting partial-commit contents - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop lets users stage a subset of lines/hunks from a file for a commit. The line selection (`WorkingDirectoryFileChange.selection`, a `DiffSelection` of absolute line indices) is computed by the renderer against a specific diff snapshot rendered in the Changes view. When the user commits, `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches a brand-new diff of the file from disk/index (`getWorkingDirectoryDiff`) instead of reusing the diff the selection indices were computed against, then blindly applies the old index-based selection to the new diff's hunks via `formatPatch`.

### Finding Description
In `app/src/lib/git/apply.ts`, `applyPatchToIndex` does: [1](#0-0) 
```
const applyArgs...
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
```
`formatPatch` (`app/src/lib/patch-formatter.ts:129-152`) walks `diff.hunks`, computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` for the *newly fetched* `diff`, and asks `file.selection.isSelected(absoluteIndex)` — but `file.selection` was populated by the UI against a *different, earlier* diff snapshot (see `_changeFileSelection`/`updateChangesWorkingDirectoryDiff` in `app-store.ts`, which explicitly acknowledge this risk): [2](#0-1) 

That mitigation only patches the *displayed* selectable-lines set in the Changes list UI state; it is not propagated to, or enforced by, the actual commit path. `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681-3699`) passes the working-directory `WorkingDirectoryFileChange` objects — carrying whatever `selection` is currently cached in `IChangesState` — straight into `createCommit`, which unconditionally re-diffs and re-applies that selection with no equality/version check between the diff used to build the selection and the diff used to build the patch.

The broken invariant: **the identity/version of the diff a `DiffSelection`'s absolute line indices refer to is never validated against the diff actually used at apply time.** Nothing ties a `DiffSelection` to a diff hash/snapshot id; `isSelected(absoluteIndex)` is purely positional.

This is attacker-reachable because the working directory of a repository the user has cloned/fetched can be mutated between the moment the user visually selects lines and the moment they click "Commit": e.g. a slow background operation, a `post-checkout`/`post-merge`/watchman-style file-system event triggered by content in a malicious clone, or simply the file being touched by another concurrent Desktop operation (fetch/pull/checkout) that races with the commit click. If the file's line count/hunk boundaries shift by even one line between the two diffs, `absoluteIndex` no longer identifies the same logical line, so `formatPatch` will silently select/deselect the wrong lines when building the `git apply --cached` patch.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user who has reviewed and selected only specific benign lines to stage can end up committing different lines than what they saw and approved — including lines they explicitly *deselected* (e.g., secrets, debug code, or content injected by a malicious repository/hook running concurrently). Since the corrupted commit is created and can subsequently be pushed, this can leak content the user never intended to commit, or drop code the user meant to include, without any warning.

### Likelihood Explanation
The window is narrow (requires a working-directory mutation between diff-selection and commit), but Desktop performs many concurrent background git operations against the same working directory (background fetch/status polling in `refreshIndicatorForRepository`, `_loadStatus`, hooks such as `post-checkout`), and a malicious/fetched repository can register hooks or use tricks (e.g., `.gitattributes` filters, smudge/clean filters, or a symlinked working file) to alter file content on disk asynchronously. No privilege beyond normal repo cloning/usage is required, and no existing guard in the commit path re-validates the selection against the diff actually used to build the patch — the only mitigation code (`app-store.ts:3479-3493`) only recomputes selectable lines for the *UI*, not for the commit operation itself.

### Recommendation
Bind a `DiffSelection` to the diff snapshot it was computed from (e.g., a content hash or the exact hunk boundaries) and re-validate/re-map that selection against the diff fetched inside `applyPatchToIndex` before calling `formatPatch`; if the diffs disagree, abort the partial-commit for that file and surface an error to the user (similar to how the report's remediation is to keep the state consistent rather than trusting a possibly-stale value at the moment it's consumed).

### Proof of Concept
1. Open a repository in GitHub Desktop, modify a tracked file with two separate line changes far apart.
2. In the Changes view, deselect the second change's lines (partial selection), which computes `DiffSelection` indices against the diff shown at that moment.
3. Before clicking "Commit", trigger a background/concurrent modification of the same file on disk that shifts line offsets before the first hunk (e.g., another process, a `post-checkout` hook from a hostile clone, or a race with an in-flight `git pull`/`checkout` operation Desktop itself issued).
4. Click "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now with different `unifiedDiffStart` offsets) and applies the old `DiffSelection` indices via `formatPatch`, producing a patch that includes/excludes different lines than what the user selected in the UI, with no error shown.
