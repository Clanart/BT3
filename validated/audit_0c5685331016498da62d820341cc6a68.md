## Analysis

`mWomSV.getUserTotalLocked()` is computed as `stakingInfo(masterMagpie) - getUserAmountInCoolDown()` [1](#0-0) , meaning `startUnlock`/`cancelUnlock` only toggle bookkeeping in `mWomSV` — they never actually withdraw the underlying stake from `masterMagpie` [2](#0-1) . `cancelUnlock` can be called back-to-back with `startUnlock` in the same block, since it only requires `slot.endTime > block.timestamp`, which is guaranteed right after `startUnlock` sets `endTime = block.timestamp + coolDownInSecs` [3](#0-2) . This makes `getUserTotalLocked` a costlessly, instantly, and reversibly manipulable value with no penalty and no meaningful time cost.

`ArbWomUp3.getRewardAmount` and `getUserTier` both read this manipulable value directly: the mode=false branch uses `rewardMultiplier[getUserTier(_account)]` off the pre-deposit balance [4](#0-3) [5](#0-4) , and the `_lock`/mode=2 branch computes a marginal tiered reward as `accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)` minus `calDoubledCounted(_account)` (reward computed on the pre-existing `getUserTotalLocked`) [6](#0-5) . Neither function enforces that the tier/multiplier schedule set via `setMultiplier` be monotonically increasing [7](#0-6) , nor does it use any monotonic "cumulative ever locked" ledger — it always uses the live, attacker-toggleable `getUserTotalLocked`.

Because `startUnlock` can only *decrease* the reported locked balance (never inflate it beyond the real stake), the attack is only profitable if the reward-per-token schedule is declining as tier/cumulative-lock increases (e.g., an early-adopter bonus that decays with size, plausible for a "wom up" migration incentive program per the contract's own comment) [8](#0-7) . In that configuration, temporarily hiding the pre-existing locked balance in cooldown makes the marginal-reward integral (or the flat tier lookup) evaluate against a lower base, yielding a materially larger reward than the true, non-gamed history would produce — after which `cancelUnlock` restores the full principal with zero cost.

### Title
Reward-tier calculation in ArbWomUp3 uses instantly/costlessly gameable mWomSV.getUserTotalLocked, enabling cooldown-cycling to distort tiered MGP rewards - ([File: wombat/ArbWomUp3.sol], [File: wombat/mWomSV.sol])

### Summary
`ArbWomUp3.getRewardAmount`/`getUserTier` derive the caller's tier/marginal-reward position from `mWomSV.getUserTotalLocked`, a value any user can instantly and costlessly lower via `startUnlock` and fully restore via `cancelUnlock` in the same block (no actual withdrawal from `masterMagpie` occurs, no penalty applies). This lets an attacker manipulate their apparent locked balance immediately before an `incentiveDeposit` call, then restore it right after, distorting the tiered MGP reward computation relative to what a true, monotonic lock history would produce.

### Finding Description
`getUserTotalLocked` is `stakingInfo - amountInCoolDown` [1](#0-0) . `startUnlock` moves an arbitrary user-chosen amount into a cooldown slot with no fee/penalty [2](#0-1) , and `cancelUnlock` immediately reverses this as long as `block.timestamp < endTime`, which is true right after `startUnlock` executes [3](#0-2) . No underlying `masterMagpie` stake ever moves during this cycle, so it is entirely free and reversible within a single block/atomic sequence.

`ArbWomUp3.incentiveDeposit` computes `rewardToSend` via `getRewardAmount` before performing the actual deposit [9](#0-8) . Both reward paths key off `mWomSV.getUserTotalLocked(_account)`:
- mode=false path: flat multiplier keyed by current `getUserTier` [4](#0-3) .
- mode=2 (`_lock=true`) path: marginal reward computed as integral over tier brackets from the (manipulable) pre-existing locked amount to `+_amountToConvert`, minus `calDoubledCounted` (reward on the same manipulable base) [6](#0-5) .

Since `setMultiplier` places no constraint requiring `rewardMultiplier` to be monotonically non-decreasing with tier [7](#0-6) , any declining segment in the configured schedule (plausible for an "early-bird"/early-adopter migration bonus, consistent with the contract's stated purpose) is directly exploitable: the attacker temporarily reports a lower `getUserTotalLocked` via `startUnlock`, so the marginal/base tier used in the reward math is artificially lower, causing the computation to apply higher-value (lower-tier) brackets that should already have been "used up" by their true existing balance. Immediately after `incentiveDeposit` completes and MGP has been sent to `vlMGP.lockFor(rewardToSend, msg.sender)`, the attacker calls `cancelUnlock` to restore their full principal at zero cost. `nonReentrant` on `incentiveDeposit` and `startUnlock` does not prevent this because the three calls are sequential, separate top-level transactions/calls, not reentrant into each other.

### Impact Explanation
This allows theft of unclaimed MGP incentive yield from `ArbWomUp3`'s MGP balance: attackers can extract a larger `rewardToSend` (locked into `vlMGP` on their behalf) than their genuine, non-gamed lock history warrants, at the expense of the protocol's incentive pool — matching "theft of unclaimed yield."

### Likelihood Explanation
No special privileges are required — `startUnlock`, `cancelUnlock`, and `incentiveDeposit` are all public/external functions callable by any EOA holding WOM/mWOM. The cooldown cycle is free (no penalty, no waiting period needed to cancel) and repeatable for every `incentiveDeposit` call, so it is fully feasible and can be repeated to compound gains, contingent only on the deployed `rewardMultiplier`/`rewardTier` schedule containing a declining segment (a real, plausible configuration for this type of migration-incentive contract, not a misconfiguration).

### Recommendation
Base tier/reward eligibility on a monotonically non-decreasing, non-gameable ledger (e.g., a `maxEverLocked` high-water-mark per user, or the raw `masterMagpie` stake amount unaffected by cooldown bookkeeping) instead of `getUserTotalLocked`, which excludes cooldown amounts. Additionally, enforce monotonic ordering of `rewardMultiplier` relative to `rewardTier` in `setMultiplier`, or at minimum, snapshot the user's locked balance immediately before allowing any `startUnlock` within a cooldown window that touches an in-flight `incentiveDeposit`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `ArbWomUp3` with `setMultiplier` configured with a declining schedule (`rewardMultiplier[0] > rewardMultiplier[1] > ...`).
2. Fund attacker with WOM; have attacker `lockFor`/`lock` a base amount into `mWomSV` so `getUserTotalLocked` sits above `rewardTier[1]`.
3. Attacker calls `mWomSV.startUnlock(largePortionOfLocked)` to push `getUserTotalLocked` below `rewardTier[1]`.
4. Attacker calls `ArbWomUp3.incentiveDeposit(smallAmount, ratio, false, 2)`; record `rewardToSend` via `getRewardAmount`.
5. Attacker calls `mWomSV.cancelUnlock(slotIndex)` to restore full principal, same block.
6. Compare `rewardToSend` against the reward `getRewardAmount` would have returned had `startUnlock` not been called (i.e., using the true, un-gamed `getUserTotalLocked`). Assert the gamed reward is strictly greater, demonstrating extraction of excess MGP with zero net change to attacker's locked mWOM principal.
