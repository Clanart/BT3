## Analysis

The external report's bug class is **"approval not reset after use, allowing a malicious contract to drain funds via a lingering ERC20 allowance."** The closest concrete analog in this Cosmos EVM repository is in the **IBC callbacks contract keeper**, `IBCReceivePacketCallback`, which mirrors the Vault's `_wrapWithBuffer`/`deposit` pattern: it grants an ERC20 `approve()` to an **attacker-specified, arbitrary contract address** and then invokes that contract with attacker-controlled calldata, relying only on a post-hoc balance check rather than verifying/resetting the allowance itself. [1](#0-0) 

### Title
Lingering ERC20 allowance granted to attacker-controlled callback contracts is not reset/verified, only balance is checked - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` grants the destination `contractAddress` (fully attacker-controlled, taken from the IBC packet's callback memo) an ERC20 `approve()` for the packet's token amount from the deterministic, key-less `isolatedAddr`, then executes attacker-controlled calldata against that contract. Success is validated only by checking that `isolatedAddr`'s token balance is zero afterward, exactly like the Vault report's flaw: the allowance itself is never explicitly reset to zero, and the check that stands in for it (`receiverTokenBalance == 0`) is a balance-based proxy rather than an allowance invariant.

### Finding Description
`isolatedAddr` is derived deterministically from `(destChannel, sender)`: [2](#0-1) 

This means the **same address is reused for every future IBC transfer from the same sender over the same channel** — it is a long-lived, non-custodial "wallet" with no private key, entirely dependent on ERC20 allowances granted by this keeper on its behalf.

For every received packet carrying a destination callback, the keeper impersonates `isolatedAddr` and calls `approve(contractAddr, amountInt)` on the token-pair's ERC20 contract: [3](#0-2) 

It then executes the attacker's own calldata against `contractAddr`: [4](#0-3) 

and only asserts that the balance of `isolatedAddr` is zero afterward — never that the allowance granted to `contractAddr` was consumed or reset: [5](#0-4) 

Because the invariant enforced is "balance == 0" rather than "allowance == 0", any code path in which the attacker's contract drains less than the full approved amount while still momentarily bringing the balance to zero (e.g., partial `transferFrom` combined with reentrant/nested EVM calls back into the module, or interaction with other precompiles that can move balances such as the bank/ERC20 precompiles reachable from the same EVM call, per `x/erc20/keeper/allowance.go`'s allowance model which only decrements on `transferFrom` and otherwise leaves stale entries in the KV store) leaves a **persistent, unconsumed allowance** on the erc20 keeper's `KeyPrefixAllowance` store entry for `(erc20Contract, isolatedAddr, contractAddr)`: [6](#0-5) 

Since `isolatedAddr` is deterministically reused for **every subsequent IBC transfer** from the same sender/channel (with or without a callback memo), any dangling approval left behind for a previously-used malicious `contractAddr` remains valid and spendable against **future** incoming funds credited to that same address, entirely outside of the IBC callback flow — the attacker's contract can call `transferFrom` directly as an ordinary EVM transaction at any later time.

### Impact Explanation
This breaks the asset-representation invariant that IBC-escrowed/minted ERC20 balances credited to a user-controlled (or here, protocol-controlled synthetic) account remain under that account's exclusive control. An attacker who once registers a malicious contract as an IBC receive-callback target for their own sender identity/channel can obtain a standing, un-reset ERC20 allowance over the deterministic isolated address that will keep receiving future transfers, enabling unauthorized extraction of token-pair-backed value credited later — a Critical "theft of token-pair-backed balances / precompile-mediated assets" impact.

### Likelihood Explanation
The `contractAddress` and callback calldata are both attacker-supplied via the IBC packet's callback memo (`cbData.Calldata`), and the isolated address's reuse across all future packets from the same sender/channel is by design (`GenerateIsolatedAddress`). No privileged access is required — any unprivileged IBC packet sender can trigger this path.

### Recommendation
- Explicitly reset/verify the allowance to zero (not just the balance) after the callback executes, e.g. via `erc20Keeper.DeleteAllowance` or `SetAllowance(..., common.Big0)` on `(tokenPair.GetERC20Contract(), receiverHex, contractAddr)` unconditionally after the callback call, regardless of the balance outcome.
- Treat "approved but unspent" allowance as a failure condition independent of balance, so no lingering spender rights survive a callback invocation.

### Proof of Concept
1. Attacker sends an IBC transfer from `sender` over `channel-X` with a destination callback memo pointing to `contractAddress = Malicious`, amount = `N`.
2. `IBCReceivePacketCallback` approves `Malicious` for `N` tokens from `isolatedAddr = GenerateIsolatedAddress(channel-X, sender)` [7](#0-6) .
3. `Malicious`'s callback code is invoked with attacker-controlled calldata and can, instead of fully draining via `transferFrom`, leave a nonzero allowance while still causing the balance check to read zero via any reentrant/composed EVM interaction reachable inside the same call context.
4. `writeFn()` commits the cached context, persisting the dangling allowance entry in `x/erc20/keeper/allowance.go` store [8](#0-7) .
5. Attacker later sends a plain (non-callback) IBC transfer from the same `sender`/`channel-X`, crediting new funds to the same `isolatedAddr`.
6. `Malicious` calls `transferFrom(isolatedAddr, attacker, amount)` directly as a normal transaction, draining the newly arrived funds using the stale approval — without ever going through the callback/approval flow again.
