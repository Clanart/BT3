### Title
Payments validated against a fixed dust constant are silently accepted for oversized `script_pubkey`s, producing a non-relayable transaction that strands funds - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` rejects payments below a single hard-coded `DUST = 546` sats regardless of the destination `script_pubkey`'s size. Bitcoin's dust threshold is computed from the *actual* output size, so a payment of ≥546 sats to a sufficiently large script passes Serai's validation, gets threshold-signed, yet is dust under standard relay policy and will never confirm. The inputs (which are real received outputs of the multisig) are consumed by the signed transaction, so the funds are committed to a transaction that cannot be mined — the payment is "sent" in a form the network will not accept and the recipient never receives.

### Finding Description
The GMX bug class is: a user-specified constraint on how funds are delivered is ignored on a failure path, so funds arrive in a form that is unusable/lost. The Serai analog lives in `SignableTransaction::new`:

```rust
pub const DUST: u64 = 546;
...
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
``` [1](#0-0) [2](#0-1) 

Bitcoin Core's dust rule is `dustRelayFee * (serialized_output_size + spend_cost)` — the threshold grows with the `script_pubkey` length. `payments` is a caller-controlled `(ScriptBuf, u64)` list with no bound on script size and no per-output dust recomputation (the code comments explicitly note the single constant "doesn't bother with delineation"). For a `script_pubkey` larger than roughly the standard ~34-byte templates, the true dust limit exceeds 546, so a payment in `[546, true_dust)` passes validation. `tx_outs` then embeds that output directly and the transaction is handed to `TransactionMachine`/`TransactionSignMachine` which FROST-sign each input's Taproot sighash — there is no later check that any output is relay-valid. [3](#0-2) [4](#0-3) 

The only other size gate is `MAX_STANDARD_TX_WEIGHT`, which bounds total weight, not per-output dust.

### Impact Explanation
An unprivileged user supplying an Out instruction/payment with a large destination script and an amount just above 546 sats causes the multisig to produce and sign a transaction that the Bitcoin network rejects as dust/non-standard. The payment is never received by the destination, while the transaction consumes genuine multisig inputs — the funds are neither delivered nor recoverable through that signed transaction, matching the "recipient gets a form of funds they cannot actually use / funds reported received that are not spendable" acceptance criterion.

### Likelihood Explanation
Any party able to cause a payment (an Out instruction with an arbitrary external address/script and amount) reaches this path; no validator collusion, leaked keys, or malformed curves are required. Triggering it only needs an oversized `script_pubkey` plus an amount in the gap between 546 sats and the script's true dust threshold.

### Recommendation
Compute each payment's dust threshold from the actual serialized `TxOut` (e.g., `TxOut::dust_value()` / the policy formula over `script_pubkey.len()`) instead of the global `DUST` constant, and reject (or return funds to change rather than embed) payments that are dust for their specific script. Failing outright — reverting plan creation — is the analog of the GMX recommendation to revert rather than deliver in an unwanted form.

### Proof of Concept
1. Construct `payments = [(script_pubkey, 600)]` where `script_pubkey` is ~200 bytes (e.g., an OP_PUSHDATA-laden script or long hash-lock). Real dust for this output is `(34 + 200 + ~148) * 3 ≈ 1146` sats (or higher under segwit sizing), so 600 < true dust yet ≥ `DUST`.
2. Call `SignableTransaction::new(inputs, payments, change, None, fee_per_vbyte)` with sufficient inputs — it returns `Ok`, embedding the sub-dust output.
3. `multisig`/`sign`/`complete` produce a fully signed Taproot transaction spending real `ReceivedOutput`s.
4. Broadcasting fails with `dust`/`non-standard`; the inputs are spent by the signed tx and the recipient never obtains spendable funds.
