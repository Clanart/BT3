### Title
ERC20-to-CW20 pointer's `transfer`/`transfer_from` ignore the wrapped ERC20's boolean return value, allowing "successful" CW20 transfers that move no tokens - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The CW20 pointer contract that wraps an arbitrary ERC20 token (deployed via the ERC20-to-CW20 pointer flow, e.g. `deployErc20PointerForCw20` in the test suite) forwards `transfer`/`transfer_from` calls to the underlying ERC20 as a `DelegateCallEvm` message but never inspects the ABI-decoded boolean return value of the ERC20's `transfer`/`transferFrom` functions. It only checks whether the EVM call reverted.

### Finding Description
`transfer()` and `transfer_from()` in [1](#0-0)  build an `EvmMsg::DelegateCallEvm` from `querier.erc20_transfer_payload` / `erc20_transfer_from_payload` and simply `add_message(msg)` to the `Response`, attaching `from`/`to`/`amount` attributes and emitting a success result unconditionally, with no branch that checks the actual `bool` returned by the wrapped ERC20's `transfer`/`transferFrom`.

The `DelegateCallEvm` custom message is routed to `HandleInternalEVMDelegateCall` → `CallEVM` in [2](#0-1) , which treats the call as failed only when `res.Err != nil` (i.e., the EVM execution reverted). If the target ERC20 is a non-compliant token that returns `false` instead of reverting on a failed transfer (the same class of token cited in the original Frax report, e.g. BAT-style tokens), `res.Err` is `nil`, `CallEVM` returns success, and the CosmWasm message handler in `wasmbinding/message_plugin.go` treats the whole `MsgExecuteContract` as successful — even though no tokens were actually moved on the EVM side.

This exactly mirrors the original bug class: a contract wraps external ERC20 token transfers without validating the boolean success flag, so a token that "fails silently" causes the wrapping contract to believe a transfer succeeded when it did not.

### Impact Explanation
Any CosmWasm contract or user that treats a successful `Ok` response (and accompanying `Transfer`-like attributes) from this CW20 pointer's `transfer`/`transfer_from` as proof that value was actually moved can be defrauded: a caller can invoke `transfer_from` (spending an owner's approved allowance) against a wrapped, non-standard ERC20 and receive a "successful" execution result with no actual balance movement on the EVM side. Any downstream logic (e.g., a DEX, escrow, or payment-gated CosmWasm contract) that releases funds/goods based on this apparent success can be tricked into releasing value for a payment that never happened — a direct fund-loss vector, analogous to the original Frax exploit scenario where a user could "pay" with a token that reports success without transferring anything.

Note that the pointer's own `balanceOf`/`allowance` are read live from the ERC20 via `query_balance`/`query_allowance` ( [3](#0-2) ), so the pointer's own state doesn't get corrupted; the loss is realized by any external party that relies on the transaction's success/attributes as a settlement signal rather than re-querying balances.

### Likelihood Explanation
This requires: (1) the ERC20 token being wrapped by the pointer to be a non-standard token that returns `false` on failure instead of reverting (not universal, but a well-known and common pattern in the wild), and (2) a downstream consumer that trusts the CW `transfer_from` success rather than independently verifying balances. Both preconditions are plausible for any permissionless ERC20-to-CW20 pointer creation flow, since pointer creation for arbitrary ERC20 contracts is user-triggered and not restricted to vetted, standards-compliant tokens.

### Recommendation
- Short term: After issuing the `DelegateCallEvm` for `transfer`/`transferFrom`/`approve`, decode the returned data (or use a synchronous check pattern) and explicitly fail the CosmWasm execution if the ERC20 call returns `false`, mirroring the effect of `SafeERC20.safeTransfer`/`safeTransferFrom`. Since `CosmosMsg` submessages here are fire-and-forget (`add_message`, not `add_submessage`+`reply`), consider switching to `add_submessage` with a `reply` handler that inspects the EVM call's `ReturnData` for a `false` boolean and reverts the whole CW20 message if so.
- Long term: Maintain an allow-list / compliance check for ERC20 tokens eligible for CW20-pointer wrapping, or document and warn integrators that pointer-wrapped ERC20 transfers must not be trusted without independently re-querying balances after the call.

### Proof of Concept
1. Deploy a non-standard ERC20 contract `T` whose `transferFrom` returns `false` (does not revert) when the transfer condition fails (e.g., insufficient balance/allowance), similar to BAT.
2. Create an ERC20-to-CW20 pointer for `T` (as in `deployErc20PointerForCw20`, exercised in `contracts/test/ERC20toCW20PointerTest.js`).
3. Have an attacker-controlled CosmWasm contract call `transfer_from` on the pointer, specifying an `owner` whose real allowance/balance in `T` is insufficient.
4. `T.transferFrom` returns `false`; `CallEVM` sees no revert (`res.Err == nil`) and returns success; `transfer_from` in `contract.rs` returns `Response::Ok` with `action=transfer_from` attributes.
5. Any contract downstream that gated an action (e.g., releasing a paid CW20 asset) on the success of step 4 releases value despite the ERC20 balance of `owner`/`recipient` in `T` being unchanged — confirmable by querying `query_balance` before/after.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

	if ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile() {
		return nil, errors.New("sei does not support EVM->CW->EVM call pattern")
	}
	if to == nil && len(data) > params.MaxInitCodeSize {
		return nil, fmt.Errorf("%w: code size %v, limit %v", core.ErrMaxInitCodeSizeExceeded, len(data), params.MaxInitCodeSize)
	}
	if to != nil && to.Cmp(common.HexToAddress(solo.SoloAddress)) == 0 {
		return nil, errors.New("cannot call Solo precompile via CosmWasm")
	}
	value := utils.Big0
	if val != nil {
		if val.IsNegative() {
			return nil, sdkerrors.ErrInvalidCoins
		}
		value = val.BigInt()
	}
	// This call was not part of an existing StateTransition, so it should trigger one
	executionCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx)).WithEVMEntryViaWasmdPrecompile(false)
	stateDB := state.NewDBImpl(executionCtx, k, false)
	gp := k.GetGasPool()
	evmMsg := &core.Message{
		Nonce:     stateDB.GetNonce(from), // replay attack is prevented by the AccountSequence number set on the CW transaction that triggered this call
		GasLimit:  k.getEvmGasLimitFromCtx(ctx),
		GasPrice:  utils.Big0, // fees are already paid on the CW transaction
		GasFeeCap: utils.Big0,
		GasTipCap: utils.Big0,
		To:        to,
		Value:     value,
		Data:      data,
		From:      from,
	}
	// should not increment nonce since this isn't a transaction
	res, err := k.applyEVMMessage(ctx, evmMsg, stateDB, gp, false)
	if err != nil {
		return nil, err
	}
	k.consumeEvmGas(ctx, res.UsedGas)
	if res.Err != nil {
		return nil, res.Err
	}
	surplus, err := stateDB.Finalize()
	if err != nil {
		return nil, err
