### Title
Unsanitized `filepath` parameter in `openrepo` deep link allows path traversal outside cloned repository - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` validates and sanitizes the `branch` parameter of an `openrepo` deep link via `testForInvalidChars`, but performs **no validation whatsoever** on the `filepath` query parameter before returning it as part of the `IOpenRepositoryFromURLAction`.

### Finding Description
In `parseAppURL`, the `openrepo` action branch extracts three query parameters — `pr`, `branch`, and `filepath` — and only `branch` is checked against `testForInvalidChars` before being accepted: [1](#0-0) 

`filepath` is read straight out of the untrusted URL querystring via `getQueryStringValue` and returned unmodified as `IOpenRepositoryFromURLAction.filepath`: [2](#0-1) 

This means an attacker who crafts a deep link such as `x-github-client://openrepo/<repo-url>?filepath=../../../../.ssh/authorized_keys` (or any relative path with `../` segments, or an absolute path) can cause `filepath` to hold a value that escapes the intended repository directory once it reaches the consumer of `IOpenRepositoryFromURLAction.filepath` (the `open-repository-from-url` handling code that opens the file after cloning, in `app/src/ui/dispatcher/dispatcher.ts`).

I was not able to fully retrieve the exact sink code in `dispatcher.ts` that consumes `filepath` (this is `open-repository-from-url` handling) before running out of tool iterations, so I cannot confirm with certainty the exact join/API used downstream (e.g. `Path.join(repository.path, filepath)` followed by a shell "open file" call). This is a material gap: the severity and exploitability of this issue depend entirely on how that downstream code combines `filepath` with the repository path and what OS-level action it performs with the result.

### Impact Explanation
If the downstream sink joins `filepath` with the repository's local path without normalizing/validating that the resulting path remains inside the repository (e.g. `path.join(repoPath, filepath)` and then handing that path to a "reveal in Finder/Explorer" or "open with default application" call), an attacker-controlled deep link could cause Desktop to act on a path outside the cloned repository — potentially disclosing the existence of/opening arbitrary files on the victim's filesystem (e.g. SSH keys, config files), which the bounty scope treats as file read outside the repo. Depending on the OS "open file" behavior, opening an attacker-chosen file with a dangerous extension could also have code-execution implications.

### Likelihood Explanation
Likelihood is contingent on unverified downstream code. `branch` is explicitly sanitized in the same function while `filepath` is not, which is a strong signal of an inconsistent trust boundary, but I could not confirm within the allotted searches whether the actual consumer in `dispatcher.ts` performs its own path containment check before acting on `filepath`. If such a check exists downstream, this finding would be mitigated/invalid.

### Recommendation
Apply the same (or equivalent, path-specific) validation to `filepath` as is applied to `branch` in `parseAppURL`, and additionally, wherever `filepath` is consumed, resolve it against the repository root and verify the resolved path is still contained within that root before performing any file-system operation.

### Proof of Concept
1. Register/trigger the `x-github-client` protocol handler with a URL such as:
   `x-github-client://openrepo/https://github.com/some/repo?filepath=../../../../.ssh/authorized_keys`
2. `parseAppURL` accepts this `filepath` value unchanged (no `testForInvalidChars` or path-containment check is applied), unlike the sibling `branch` parameter.
3. Further confirmation of user-visible impact requires inspecting the exact `open-repository-from-url` consumer logic in `app/src/ui/dispatcher/dispatcher.ts`, which I was unable to fully retrieve before running out of tool calls.

**Note on confidence**: Because I could not confirm the downstream sink code that actually consumes `IOpenRepositoryFromURLAction.filepath`, I cannot state with full certainty whether an exploitable path-traversal file read/open occurs, or whether the sink independently sanitizes the value. The asymmetry between `branch` sanitization and the complete absence of `filepath` sanitization in `parseAppURL` itself is confirmed and is a legitimate defect regardless of downstream mitigations.

      if (!/^\d+$/.test(pr)) {
