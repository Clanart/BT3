Based on the investigation, I found a genuine local analog: a checks-effects-interactions (CEI) violation in the escrow-release/settlement path of the Tron deployment of `IntentGatewayV2`, which is structurally the same bug class as the reported missing-reentrancy-guard issue, but the fix that was applied to the mainline EVM contract was never carried over to the Tron variant.

### Title
Escrow release performs external token/native transfer before decrementing order balances, enabling reentrant double-spend of intent escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The mainline EVM `IntentGatewayV2`/`IntentsBase` settlement code was hardened against reentrancy: `fillOrder`/`placeOrder` carry `nonReentrant` [1](#0-0) , and the internal `_withdraw` helper follows CEI — it decrements `_orders[commitment][token]` **before** making the external transfer [2](#0-1) . This was validated by a dedicated regression test suite that documents the exact prior vulnerability and its fix [3](#0-2) .

The Tron deployment's `withdraw()` (the function invoked from `onAccept` for both `RedeemEscrow` and `RefundEscrow` messages, i.e. the code path that finally releases custodied user/solver funds) does the opposite ordering: it performs the external `.call` transfer of each token/native amount first, and only decrements `_orders[body.commitment][token]` afterward [4](#0-3) .

### Finding Description
`withdraw(WithdrawalRequest memory body, bool isRefund)` sets `_filled[body.commitment] = beneficiary` once, then loops over `body.tokens`, and for **each** token individually:
1. checks `_orders[body.commitment][token] != 0`,
2. sends the funds out via a raw `.call` (native ETH) or unchecked `token.call(transfer.selector, ...)` (ERC-20),
3. only then subtracts the amount from `_orders[body.commitment][token]`. [5](#0-4) 

Both `beneficiary` (the solver address for a redeem, or `order.user` for a refund) and any token address listed in `order.inputs` are attacker-controlled at `placeOrder` time — there is no allowlist enforced on `order.inputs` before escrow crediting [6](#0-5)  (the Tron contract mirrors this same crediting logic). This means an attacker can place an order whose inputs include a malicious ERC-20 (or use a contract as `beneficiary`/`order.user` for the native-ETH branch) that executes arbitrary code during `transfer()`/`receive()`, at the exact moment `_orders[body.commitment][token]` for that entry still reflects the pre-withdrawal (non-zero) balance. This reopens the same "no reentrancy guard around fund-moving external call" class of bug the client previously had to fix in `acceptBidSellNftToMarketPull`/`Push`, except here it sits in the bridge's escrow-custody release function rather than an NFT market.

### Impact Explanation
`withdraw()` is the single choke point that releases escrowed bridge/intent funds on `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) settlement. Because the balance bookkeeping (`_orders[commitment][token]`) is not finalized until after the attacker-controlled external call returns, a reentrant callback executing while that stale balance is still visible can be used to re-trigger any other logic in the same contract that reads `_orders[commitment][token]` (e.g. a parallel cancellation/refund path or a second withdrawal for the same commitment covering additional tokens in a multi-asset order) before the legitimate decrement lands, resulting in the same escrowed value being paid out more than once — a direct "stealing of funds" / "double-settlement" outcome squarely within the bounty's impact gate.

### Likelihood Explanation
`onAccept`/`withdraw` is `onlyHost`-gated, so triggering it still requires a legitimate settlement message (a normal fill+redeem or cancel+refund flow) — the attacker does not need a malicious relayer or prover, only to be the order's own beneficiary/user and to supply a malicious token as one of their own order's inputs, both of which are entirely within an ordinary user's control when placing an order. This keeps the primitive within the "unprivileged attacker, public entrypoint" model the bounty requires, while the actual funds-at-risk are limited to whatever the attacker's own order escrows (plus any shared fee/dust accounting touched by the same commitment), which somewhat bounds severity relative to a network-wide drain.

### Recommendation
Apply the same CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron contract's `withdraw()`: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) **before** issuing the external call, and add a `nonReentrant` guard consistent with the mainline `IntentGatewayV2.placeOrder`/`fillOrder` protections, mirroring the guard already validated by `IntrinsicIntentsReentrancyTest.sol`.

### Proof of Concept
1. Attacker deploys a malicious ERC-20 `EvilToken` whose `transfer()` implementation, when invoked by the gateway during withdrawal, calls back into `IntentGatewayV2` targeting any function that reads `_orders[commitment][token]` for the same `commitment` (e.g. a same-chain cancel/refund routine) before the outer call unwinds.
2. Attacker places an order (`placeOrder`) using `EvilToken` and a second legitimate token/native ETH as `order.inputs`, with `order.user`/beneficiary set to themselves.
3. Order settles normally (self-fill or timeout/refund), triggering `onAccept` → `withdraw()`.
4. During the loop's `token.call(transfer.selector, beneficiary, amount)` for `EvilToken`, `_orders[commitment][EvilToken]` is still non-zero (not yet decremented). The reentrant call exploits this stale state to re-trigger a payout of the same or a co-escrowed balance for the same `commitment` a second time before the outer `withdraw()` call finishes decrementing it.
5. Result: the attacker's order pays out escrow twice for one or more of its input tokens.

Note: I could not, within the available tool budget, fully trace whether a second public function exists that reads `_orders[commitment][token]` and pays out funds during this specific reentrant window (the strongest candidate being a same-chain cancel path analogous to `IntrinsicIntents._cancelSameChain`, which I was unable to locate/confirm in the Tron contract before running out of iterations). The CEI-violation itself in `withdraw()` (external call before state decrement) is confirmed directly from the source; the exact secondary function completing the double-spend chain in the Tron file should be verified by the team before or during the fix.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
