Based on my investigation, I found the exact mechanism now: the `input_utxo` in the payout flow is a **dust UTXO** (only 550 sats, see `generate_withdrawal_utxo` in `core/src/test/common/setup_utils.rs:480-497`) that the user creates purely to carry their `SinglePlusAnyoneCanPay` signature — it does **not** fund the payout amount. The `output_txout` (the actual withdrawal payment) is funded by whoever broadcasts the transaction, via `fund_raw_transaction`/`add_inputs: true` in `core/src/operator.rs:652-674`. The user's signature (`SinglePlusAnyoneCanPay`) only commits to input index 0 and output index 0 (the payout amount+script) — it does **not** cover the OP_RETURN output (index 2) that records `operator_xonly_pk`, per `create_payout_txhandler` in `core/src/builder/transaction/operator_reimburse.rs:407-436`.

### Title
Unsigned OP_RETURN operator-attribution output allows misattributing a payout to an operator who never funded it - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the `payout_tx` with a `SinglePlusAnyoneCanPay` signature that the user provides only over the withdrawal input and the single corresponding output (the payment to the user). The OP_RETURN output that records which operator "fronted" the peg-out (`operator_xonly_pk`) is a third, unsigned output added by whoever constructs and broadcasts the raw transaction. Any party who obtains the user's `WithdrawParamsWithSig` (given to potentially many operators off-chain, or observable once a payout tx enters the mempool) can build their own version of the same transaction, satisfy the committed input/output, but stamp an **arbitrary operator's** xonly pubkey into the OP_RETURN field. [1](#0-0) 

### Finding Description
`Operator::withdraw` verifies only that the sighash over input 0 (using `SinglePlusAnyoneCanPay`) matches the user's signature [2](#0-1) . Because of `ANYONECANPAY`, other inputs added later (the actual BTC-funding inputs from `fund_raw_transaction`) are not committed, and because of `SIGHASH_SINGLE`, only output index 0 is committed. The anchor output (index 1) and the OP_RETURN output carrying `operator_xonly_pk` (index 2) added in `create_payout_txhandler` are entirely outside the signature's scope [3](#0-2) .

Downstream, `update_finalized_payouts` in `verifier.rs` scans confirmed blocks, reads the OP_RETURN of whatever payout tx spent the withdrawal UTXO, and persists it as `payout_payer_operator_xonly_pk` [4](#0-3) . This attribution is later used by `is_kickoff_malicious` to decide whether a kickoff by that named operator is legitimate (i.e., whether they may proceed to reimbursement) [5](#0-4) , and by `validate_payer_is_operator` on the operator side to gate `get_reimbursement_txs` [6](#0-5) .

Because the OP_RETURN is never covered by the user's signature, the equality the protocol relies on — "operator named in OP_RETURN == operator who actually funded/broadcast the payout" — is not enforced by any cryptographic commitment. An unprivileged party who possesses a valid `WithdrawParamsWithSig` (which per the RPC's doc/proto is sent to potentially all operators, and once broadcast is visible in the mempool) can build a payout transaction that correctly pays the user (satisfying the signed constraint) but writes ANY chosen operator's `xonly_pk` into the OP_RETURN, and fund/broadcast it themselves.

### Impact Explanation
If this transaction confirms, the database will record that the named operator "fronted" a withdrawal that operator never authorized, funded, or even knew about. That operator will subsequently be treated by `is_kickoff_malicious`/`validate_payer_is_operator` as the legitimate payer for that deposit, letting them (or an attacker impersonating a kickoff for them) attempt to claim reimbursement from the vault/collateral for money they never spent — an operator reimbursed for a payout it never funded. Conversely, this also lets an attacker deny/confuse the legitimate operator's future `get_reimbursement_txs` flow, since `validate_payer_is_operator` will reject reimbursement attempts by the operator that actually paid if the payer field is set to someone else's key.

### Likelihood Explanation
Exploitability depends on an attacker being able to (a) obtain a valid `WithdrawParamsWithSig` (achievable by any operator recipient, or by observing the mempool before confirmation), and (b) win the race to have their own variant of the payout tx confirm first, while still funding the correct user-facing payment out of pocket. This requires real capital outlay by the attacker (they must pay the user's output) and a race against the legitimate operator's broadcast, so it is not free, but it requires no privileged role — it only needs mempool visibility/access to the params, which the protocol already shares "off-chain to operators" broadly.

### Recommendation
Cover the operator-attribution output in the user's commitment, e.g. by using a sighash type that also commits to the OP_RETURN output, or by deriving/enforcing the OP_RETURN operator key server-side against the account that actually funds the transaction (e.g., have the RPC that broadcasts also require a signature from `operator_xonly_pk` binding it to that specific unsigned raw transaction, or use `SIGHASH_ALL`-style commitments over all outputs before the tx is accepted downstream in `update_finalized_payouts`).

### Proof of Concept
1. Wait for a `WithdrawParamsWithSig` request to reach the mempool (or be shared with multiple operators) for withdrawal index `N` targeting user output `(script_pubkey, amount)`.
2. Build a new `payout_tx` using the same `input_utxo`/`in_signature` (`SinglePlusAnyoneCanPay`), the same output index 0 (paying the user exactly as signed), but set the OP_RETURN (`create_payout_txhandler`'s `operator_xonly_pk` argument) to Operator V's xonly pubkey instead of your own.
3. Fund the extra input(s) needed to cover the payout amount yourself and broadcast this transaction ahead of Operator V's (or the legitimate payer's) transaction.
4. Once confirmed, `update_finalized_payouts` records `payout_payer_operator_xonly_pk = V` for withdrawal `N` [7](#0-6) , even though V never constructed, signed off on, or funded this transaction.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
