### Title
Empty aggregate signature is accepted as valid - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::read` accepts an encoded aggregate with zero nonces, while `SchnorrAggregator::complete` refuses to produce an empty aggregate. [1](#0-0) [2](#0-1) 

An attacker can therefore deserialize a proof object that no legitimate aggregation path can emit. [1](#0-0) 

### Finding Description
`SchnorrAggregate::read` reads a little-endian `u32` count and permits it to be zero, then reads only the scalar `s`. [1](#0-0) 

`SchnorrAggregate::verify` only checks that the number of nonces equals the number of supplied keys/challenges, then verifies the multiexponentiation `sum(z_i R_i) + sum(z_i c_i A_i) - sG == 0`. [3](#0-2) 

For an empty `keys_and_challenges` slice and `s == 0`, there are no signature terms and the final statement is `-0 * G == identity`, which succeeds. [4](#0-3) 

This is analogous to accepting a range smaller than the operation’s minimum unit: the encoding layer admits a zero-length aggregate, while the producing API explicitly treats zero signatures as unrepresentable by returning `None`. [5](#0-4) 

### Impact Explanation
A verifier caller that treats `verify(dst, keys_and_challenges)` as evidence that the listed signers produced signatures can accept a forged aggregate containing no signer authorization at all when the expected signer list is empty or independently reduced to empty. [3](#0-2) 

The forged object is only 36 bytes for a typical 32-byte scalar: `u32(0)` followed by the canonical encoding of scalar zero. [1](#0-0) 

### Likelihood Explanation
Exploitation requires an application to invoke verification with an empty signer/challenge list without separately enforcing a nonzero signer threshold. [3](#0-2) 

Where that can happen through policy-driven or dynamically selected signer sets, the library accepts cryptographically unauthenticated bytes as a successful verification. [6](#0-5) 

### Recommendation
Reject `Rs.len() == 0` in `SchnorrAggregate::read`, matching `SchnorrAggregator::complete`’s refusal to produce empty aggregates. [1](#0-0) [2](#0-1) 

`verify` should also return `false` when `keys_and_challenges` is empty so directly constructed invalid objects cannot bypass the encoder check. [3](#0-2) 

### Proof of Concept
```rust
// crypto/schnorr/src/aggregate.rs
let mut encoded = vec![0, 0, 0, 0];
encoded.extend_from_slice(<C as Ciphersuite>::F::ZERO.to_repr().as_ref());

let aggregate =
  SchnorrAggregate::<C>::read(&mut encoded.as_slice()).unwrap();

assert!(aggregate.verify(b"domain-separator", &[]));
```

The `u32` count of zero is accepted, `s = 0` is read, and verification succeeds because the single checked statement is `-0 * G`, which is the group identity. [1](#0-0) [4](#0-3)
