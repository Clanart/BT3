### Title
Quadratic Lagrange interpolation in `ThresholdKeys` deserialization and signing-set view enables CPU denial of service from untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`Interpolation::interpolation_factor` computes a Lagrange coefficient in `O(|included|)` field operations, and both `ThresholdKeys::new` and `ThresholdKeys::view` call it once per participant in the set, yielding `O(n²)` scalar multiplications plus `n` field inversions. `n` is an attacker-controlled `u16` (up to 65535) parsed directly from the byte stream in `ThresholdKeys::read`, so a few megabytes of crafted input force billions of field multiplications and tens of thousands of inversions. The same quadratic blowup is reachable in the FROST `sign` path via `view`.

### Finding Description
`interpolation_factor` iterates over every member of `included` for each queried participant (`crypto/dkg/src/lib.rs:226-249`):

```rust
for l in included {
  if i == *l { continue; }
  let share = F::from(u64::from(u16::from(*l)));
  num *= share;
  denom *= share - i_f;
}
num * denom.invert().unwrap()
```

`ThresholdKeys::new` invokes it inside the `group_key` computation for every `i` in `1..=t` (`crypto/dkg/src/lib.rs:376-378`), and `ThresholdKeys::view` invokes it for every element of the caller-supplied `included` vector (`crypto/dkg/src/lib.rs:500-507`). `ThresholdKeys::read` accepts `t`, `n`, and `i` from the stream, reads `n` points, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:591-631`), which immediately performs the `O(t²)` Lagrange evaluation with `t` inversions. With `t = n = 65535` and interpolation tag `1` (Lagrange), deserialization performs ~4.3×10⁹ field multiplications and 65535 field inversions before returning — all driven by a ~2 MB input.

In the FROST path, `AlgorithmSignMachine::sign` builds `included` from the keys of the attacker-influenced `preprocesses` map and calls `self.params.keys.view(included.clone())` (`crypto/frost/src/sign.rs:290-313`), reproducing the quadratic cost in `view`. `included` is bounded only by `n` (`crypto/dkg/src/lib.rs:464-491`).

### Impact Explanation
An unprivileged party who can supply bytes to `ThresholdKeys::read` (an in-scope `read` API) — e.g., serialized threshold keys shipped between services or loaded from untrusted storage — can stall the deserializing node for a computation proportional to `n²`, with `n` fully attacker-controlled up to 65535. Each participant index also costs a field inversion (`denom.invert().unwrap()`, `crypto/dkg/src/lib.rs:246`), which is roughly two orders of magnitude more expensive than a multiplication. In the signing path, a counterparty able to dictate the `preprocesses`/`included` set forces each honest signer into the same `O(k²)` interpolation inside `view` before any signature share is produced, grinding FROST sessions to a halt for large validator sets. This is a deterministic-algorithmic-complexity DoS, the direct analog of the ReDoS class (attacker-chosen input size squared in cryptographic work).

### Likelihood Explanation
The cost is fully determined by a `u16` (`n`) the attacker writes into the serialized blob — no probabilistic or cryptographic work is required. Triggering requires only that the victim deserialize attacker-influenced `ThresholdKeys` bytes or accept a signing set the attacker influences. No key material, collusion, or privileged position beyond being a protocol counterparty is needed. Mitigating factor: participants/validators are semi-trusted in some call paths, and practical multisig sizes are small, so exploitation requires either a large legitimately-registered set or an untrusted-bytes path into `read`.

### Recommendation
- Cache interpolation factors: compute each `i`'s Lagrange factor once, or use the standard `O(n)` prefix/suffix-product formulation for Lagrange coefficients over the x-coordinates `1..=n`.
- In `view`, compute the factor for `self.params().i()` once (the only share needed for signing) and compute verification-share factors lazily or via the linear-time formulation.
- Enforce a sane upper bound on `n` in `ThresholdKeys::read` before allocating or interpolating, independent of `u16::MAX`.

### Proof of Concept
Conceptual Rust pseudocode against the in-scope crate:

```rust
// Craft a ThresholdKeys blob with t = n = 65535, Lagrange interpolation.
let mut buf = vec![];
buf.extend(4u32.to_le_bytes());            // C::ID len
buf.extend(C::ID);
buf.extend(65535u16.to_le_bytes());        // t
buf.extend(65535u16.to_le_bytes());        // n
buf.extend(1u16.to_le_bytes());            // i
buf.push(1u8);                             // Interpolation::Lagrange
buf.extend(scalar_repr);                   // secret_share
for _ in 0 .. 65535 { buf.extend(point_bytes); } // verification_shares

// Triggers 65535 calls to interpolation_factor, each looping 65535 times
// with a field inversion per call, inside ThresholdKeys::new's group_key sum.
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```

Equivalent trigger in signing: supply a `preprocesses` map covering all `n` participant indexes to `AlgorithmSignMachine::sign`, forcing `view` (`crypto/frost/src/sign.rs:312`) to run the same `O(n²)` loop at `crypto/dkg/src/lib.rs:500-507`.
