### Title
Unauthenticated dust/false outputs to the multisig address are scanned as spendable and accepted as transaction inputs - (File: networks/bitcoin/src/wallet/mod.rs, networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the `checkTransaction` report — where any actor can poke a publicly reachable function and poison the state a later guarded operation depends on — the Bitcoin wallet's `Scanner` accepts any on-chain output paying to a registered `script_pubkey` as a spendable `ReceivedOutput`, with no minimum-value check, and `SignableTransaction::new` accepts such outputs as inputs without verifying the input's value can cover the marginal cost of spending it. Any unprivileged party can send a Bitcoin transaction creating dust outputs to the multisig's external or offset addresses; those outputs are then reported as funds and can be folded into every subsequent spending transaction.

### Finding Description
`Scanner::scan_transaction` matches outputs purely on `output.script_pubkey` being present in `self.scripts`, and unconditionally constructs a `ReceivedOutput` for each match. There is no lower bound on `output.value` — a 1-satoshi (or otherwise uneconomical/nonstandard) output is reported identically to a real deposit.

`SignableTransaction::new` treats every entry of `inputs: Vec<ReceivedOutput>` as spendable value. It checks `payment` amounts against `DUST` (546 sat) but performs **no** analogous check on input amounts, and `multisig` only verifies `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey` — i.e., that the multisig *could* spend it, not that spending it is rational or that the value is above dust. Each injected input inflates `tx_ins`, `weight`, and hence `needed_fee`, and adds a full FROST signing machine (`self.sigs.push(...)` per input) to every signing attempt.

A transaction spending a sub-dust P2TR input is non-standard under `MAX_STANDARD_TX_WEIGHT`/dust relay rules and cannot be relayed at all: the change/output leg may be valid, but the input itself being dust doesn't make the tx invalid — rather, the input's value (e.g., 546 sat) is less than the fee it adds (~vbytes-per-input × fee rate). So each poisoned input is a net-negative input: it consumes more in fee than it contributes, silently inflating `needed_fee` and forcing the multisig to burn additional funds from its other inputs — or, if the wallet aggregates dust inputs without change, the whole leftover becomes fee.

Relevant code:
- `networks/bitcoin/src/wallet/mod.rs` — `scan_transaction` pushes `ReceivedOutput` for any script match with no amount check (lines 199–214).
- `networks/bitcoin/src/wallet/send.rs` — `DUST` constant and `DustPayment` check applied only to `payments` (lines 32, 165–169); inputs summed and consumed unconditionally (lines 175–185); per-input signing machine construction gated only by script match (lines 273–285).

### Impact Explanation
An unprivileged attacker can, at a one-time cost of ~546 sat per output, permanently pollute the multisig's spendable-output set. Every transaction that sweeps or aggregates these inputs pays more in fees than the inputs are worth, draining the wallet's balance over time, and each poisoned input forces an extra Schnorr/FROST signature instance per signing attempt (adding an extra `AlgorithmSignMachine` round and preprocessing cost for every participant). If the coordinator auto-aggregates scanned outputs, this is an ongoing, externally-triggerable fee burn / signing DoS requiring no privileged position — directly parallel to front-running `checkTransaction` to sabotage a guarded operation.

### Likelihood Explanation
Triggering requires only sending ordinary Bitcoin transactions to a publicly known multisig address — fully within the allowed reachability model ("Bitcoin transactions they send"). The only mitigating factor is that downstream consumers may impose their own minimum (`N::DUST = 10_000` in the processor's scanner loop, `output.balance().amount.0 >= N::DUST`), so the vulnerability is at the wallet-library layer: any consumer that trusts `scan_transaction` results directly, or whose dust threshold is below the per-input fee cost, is affected. Medium severity: persistent fee drain and signing-round amplification, bounded by the attacker's per-output cost.

### Recommendation
- Enforce a minimum value in `Scanner::scan_transaction` (or `ReceivedOutput` construction) — reject outputs below a dust/economic-spendability threshold so untrusted sends cannot enter the spendable set.
- In `SignableTransaction::new`, validate that each input's value exceeds the marginal fee it adds (`fee_per_vbyte * per-input vbytes`), or provide a separate aggregation path that drops economically irrational inputs.
- Document that `scan_transaction`/`scan_block` results are unauthenticated reports requiring value-based filtering before use as inputs.

### Proof of Concept
1. Build a `Scanner` for a multisig key and register offsets (`scanner(key)` registers External/Branch/Change/Forwarded scripts).
2. Attacker broadcasts a transaction containing an output `TxOut { value: 546, script_pubkey: <external address> }` to the multisig's external script (any value ≥ 1 works on-chain; the scanner does not distinguish).
3. `scanner.scan_transaction(&tx)` returns a `ReceivedOutput` indistinguishable from a legitimate deposit.
4. `SignableTransaction::new(vec![poisoned, legit_input], payments, change, None, fee)` accepts the poisoned input; `needed_fee` rises by ~`fee * input_vbytes` while `input_sat` rises by only 546 sat. If 546 < marginal fee, the transaction pays a net-negative input — burning the multisig's other inputs' value as excess fee, and forcing all signers through an additional FROST signing machine for the attacker's input.

Note: the processor-side scanner (`processor/src/multisigs/scanner.rs`, `>= N::DUST`) partially compensates for this in that specific consumer, but that file is outside the in-scope crates; the wallet library itself (`networks/bitcoin/src/wallet/`) exposes the unfiltered path.
