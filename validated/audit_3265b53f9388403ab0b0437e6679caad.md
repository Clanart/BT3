### Title
Uncontrolled recursion in wallet outer-puzzle driver matching (`match_puzzle`/`get_inner_puzzle` `also()` chains) enables stack-overflow DoS from an attacker-crafted offer - (File: `chia/wallet/outer_puzzles.py`)

### Summary
`chia/wallet/outer_puzzles.py`'s `match_puzzle()` and the corresponding `get_inner_puzzle()`, `get_inner_solution()`, `construct()`, and `solve()` methods on `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `SingletonOuterPuzzle`, and `CROuterPuzzle` recurse through the `PuzzleInfo.also()` chain with plain Python function calls and no depth limit. `Offer.from_spend_bundle()` calls `match_puzzle()` on every coin spend's `puzzle_reveal` when parsing an untrusted offer file via `Offer.from_bech32()`, so a wallet or RPC caller that loads a maliciously crafted offer (or a spend bundle taken from one) drives this unbounded recursion directly from external, untrusted data. ### Finding Description
`match_puzzle()` walks `driver_lookup` and calls `driver.match(puzzle)` for each `AssetType`; every implementation (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) that finds a matching curried mod recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` to build a nested `PuzzleInfo` via the `"also"` key [5](#0-4) . This recursion depth is bounded only by how many outer-puzzle layers are curried into the on-chain puzzle reveal being examined, which an offer creator fully controls (e.g. nesting CAT-in-CAT, as already demonstrated with two layers in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py:17-33`). Because there is no maximum-depth check anywhere in `outer_puzzles.py`, `cat_outer_puzzle.py`, `singleton_outer_puzzle.py`, `metadata_outer_puzzle.py`, `ownership_outer_puzzle.py`, or `cr_outer_puzzle.py`, an attacker can construct a puzzle reveal with an arbitrarily deep nested-curry chain (each layer only costs a bit more CLVM curry bytes, no CLVM execution is required to trigger the match) and place it in a `CoinSpend` inside an `Offer`.

When any wallet loads that offer through `Offer.from_bech32()` → `Offer.try_offer_decompression()` → `Offer.from_bytes()` → `Offer.from_spend_bundle()`, the code calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every coin spend before any cost or size limiting is applied [6](#0-5) . This is invoked from `TakeOffer.parsed_offer` for the `take_offer` RPC and from the `take_offer`/`get_offers` CLI commands parsing user-supplied offer files, i.e. reachable by any offer counterparty or local operator loading an untrusted `.offer` file/bech32m string, well before signature/mempool validation would reject the spend bundle. `PuzzleInfo.check_type()` on the same object is similarly recursive without a bound [7](#0-6) .

Because CPython's default recursion limit (and native stack) is a fixed, comparatively small threshold, a puzzle reveal with a few hundred to a couple thousand nested matchable layers is enough to raise `RecursionError` or, more critically since each level calls into `.get_tree_hash()`/`.as_iter()`/dataclass constructors, to overflow the native C stack and crash the wallet process outright (a hard process abort is not always caught by Python `except RecursionError`, exactly matching the rulex advisory's described failure mode).

### Impact Explanation
This is a Medium-severity denial-of-service: any wallet process (via RPC `take_offer`/`create_offer_for_ids` or CLI `chia wallet take_offer`) that opens an untrust offer supplied by an unprivileged offer counterparty can be crashed or hung on recursion before any consensus-level validation (signature checks, CLVM execution cost limits, mempool admission) has a chance to reject the malformed offer. This does not by itself lead to fund loss or forged asset identity, but it is a spend/offer-triggered halt of wallet transaction processing, matching the accepted impact category of a "spend-triggered transaction-processing halt."

### Likelihood Explanation
Likelihood is high for exposed wallet RPC/CLI operators who routinely accept offers from third parties (a core, expected chia wallet workflow), since constructing a puzzle reveal with deeply nested curried outer-puzzle layers requires no special privileges, no valid signature, and no real assets — only crafting `CoinSpend.puzzle_reveal` bytes that satisfy the shallow `uncurry()`/mod-hash matching used by each outer-puzzle driver.

### Recommendation
Add an explicit maximum recursion/nesting depth check in `match_puzzle()` (and `PuzzleInfo.also()`/`check_type()`), rejecting or treating as `UnknownPuzzle` any puzzle reveal whose "also" chain exceeds a small fixed bound (e.g. the maximum number of outer-puzzle layers ever legitimately produced by the wallet, plus margin). Alternatively, convert the recursive matching in `outer_puzzles.py`, `ownership_outer_puzzle.py`, `metadata_outer_puzzle.py`, `singleton_outer_puzzle.py`, and `cr_outer_puzzle.py` to an iterative loop with an explicit depth counter, mirroring the non-recursive approach already used in `chia/types/blockchain_format/tree_hash.py`'s `sha256_treehash()` for the same class of untrusted-depth concern.

### Proof of Concept
1. Build a base puzzle `P0 = Program.to(1)`.
2. Repeatedly wrap it N times (N ≈ 2,000–5,000) using `construct_cat_puzzle(CAT_MOD, tail, P_{i-1})` (as in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py:17-33`, but looped instead of twice) to produce `P_N`, a puzzle reveal with N nested CAT outer-puzzle layers.
3. Construct a `CoinSpend` whose `puzzle_reveal` is `P_N`, embed it into a minimal offer's `WalletSpendBundle`, and serialize/bech32-encode it via `Offer(..., WalletSpendBundle([coin_spend], G2Element()), {}).to_bech32()`.
4. Feed the resulting bech32 string to `Offer.from_bech32()` (as `take_offer` does for `TakeOffer.parsed_offer` or the CLI `take_offer` command).
5. Observe `match_puzzle()`/`CATOuterPuzzle.match()` recursing N times through `self._match(UnknownPuzzle(known_program=inner_puzzle))`, exhausting the Python recursion limit or the native stack and crashing/hanging the wallet process before any CLVM execution or signature check occurs.
