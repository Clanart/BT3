### Title
`getReward()` approves vlMGP without resetting stale allowance, permanently freezing yield claims for all users - (File: wombat/WomUp.sol)

### Summary
`WomUp.getReward()` calls `IERC20(mgp).safeApprove(address(vlMGP), reward)` on every claim without first resetting the allowance to zero [1](#0-0) . Because this allowance is set from the shared `WomUp` contract address to `vlMGP` (not per-user), a single call where `vlMGP.lockFor()` does not fully consume the newly approved `reward` amount leaves a nonzero residual allowance that will cause every subsequent `getReward()` call from any user to revert.

### Finding Description
`getReward()` computes `reward = rewards[msg.sender]` and then unconditionally calls:
```solidity
IERC20(mgp).safeApprove(address(vlMGP), reward);
vlMGP.lockFor(reward, msg.sender);
``` [1](#0-0) 

OpenZeppelin's `SafeERC20.safeApprove` reverts whenever an approval is changed from one nonzero value directly to another nonzero value, requiring `approve(0)` in between as a defense against the classic ERC20 approve race condition. `WomUp` never resets to zero before re-approving. The allowance from `mgp` to `vlMGP` is scoped to `address(this)` (the `WomUp` contract), which is shared across **all** callers of `getReward()` — it is not per-user. If `vlMGP.lockFor(reward, msg.sender)` ever consumes less than the full `reward` amount that was just approved (e.g., due to internal caps, slot limits, or partial-lock logic in `VLMGP.sol`), a residual nonzero allowance remains on the `mgp` token from `WomUp` to `vlMGP`. The very next user (or the same user) calling `getReward()` with any `reward > 0` will have their `safeApprove` call revert, since the current allowance is already nonzero. Since `getReward()` is invoked internally by `withdraw(..., claim=true)` and `migrate(..., _claim=true)` as well as directly, this bricks the entire reward-claiming path contract-wide, not just for one account.

### Impact Explanation
Once the allowance desync occurs, `getReward()` reverts for every account holding a nonzero `rewards[account]` balance, and cannot self-heal because there is no function to reset the allowance to zero. Users' accrued MGP rewards remain stuck inside `WomUp` and can never be locked into `vlMGP`, permanently freezing unclaimed yield for the entire pool of stakers — matching Immunefi's "High – Permanent freezing of unclaimed yield" class.

### Likelihood Explanation
No privileged role is required; any unprivileged staker who has accrued rewards can trigger `getReward()`. Exploitability hinges entirely on whether `VLMGP.lockFor()` can under-consume the approved amount in some code path (e.g., due to lock-slot limits, penalties, or a lock cap) — this is asserted as a precondition in the question. Given that precondition, the bug is deterministic and trivially repeatable (a single call sequence), requiring no capital and no special timing beyond the reward period having accrued and been claimed once.

### Recommendation
Reset the allowance before setting a new one, or switch to `forceApprove`/`safeIncreaseAllowance` patterns that don't require a zero-allowance precondition:
```solidity
IERC20(mgp).safeApprove(address(vlMGP), 0);
IERC20(mgp).safeApprove(address(vlMGP), reward);
```
or use `SafeERC20.forceApprove` (OZ ≥4.8) which handles the reset internally. Additionally, verify/guarantee that `VLMGP.lockFor()` fully consumes the passed-in amount via `transferFrom`, so no residual allowance can accumulate.

### Proof of Concept
Hardhat test plan:
1. Deploy `WomUp`, `VLMGP`, mock `mWom`/`wom`/`mgp` tokens.
2. Configure `VLMGP.lockFor` (or a mock implementing `IVLMGP`) to intentionally consume less than the full approved amount for at least one call (representing a real-world under-consumption path in `VLMGP.sol`).
3. Have User A stake, accrue rewards, call `getReward()` successfully once (leaving residual allowance due to under-consumption).
4. Have User B stake, accrue rewards, call `getReward()` — assert this reverts with `SafeERC20: approve from non-zero to non-zero allowance`.
5. Assert `rewards[UserB]` is unchanged and no state exists to reset the stuck allowance, demonstrating permanent freezing of UserB's unclaimed yield.

Note: This finding assumes `VLMGP.lockFor()` can under-consume the approved `reward` amount, as stated in the question's preconditions; the exact internal logic of `lockFor` in `VLMGP.sol` that would cause under-consumption was not fully retrievable in this session, so this precondition should be independently verified against `VLMGP.sol`'s full implementation before treating this as confirmed rather than conditional.
