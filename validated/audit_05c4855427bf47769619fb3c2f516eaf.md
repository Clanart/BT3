### Title
SignableTransaction fee/weight computed on a transaction that omits the OP_RETURN data output, mis-measuring the signed transaction - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` pushes a caller-supplied `OP_RETURN` data output into `tx_outs`, but then computes the transaction's weight and vbytes via `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a fresh transaction containing only the payment outputs. Both the `needed_fee` (satoshis, derived from vbytes) and the `MAX_STANDARD_TX_WEIGHT` check are therefore evaluated against a *different, smaller* transaction than the one actually assembled and signed — the same class of bug as the WithdrawProxy report, where a quantity measured at one scale is applied to a value expressed at another, corrupting accounting.

### Finding Description
The `data` argument is validated only for length (≤ 80 bytes) and then unconditionally appended as an output:

```rust
// networks/bitcoin/src/wallet/send.rs
if data.as_ref().map_or(0, Vec::len) > 80 {
  Err(TransactionError::TooMuchData)?;
}
...
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` constructs `tx.output` solely from `payments` (plus optional `change`); the OP_RETURN output is never included in the measured transaction. The change path (`calculate_weight_vbytes(..., Some(&change))`) has the same omission. Consequently:

1. `needed_fee` is `fee_per_vbyte * vbytes` where `vbytes` excludes the OP_RETURN output (~`amount` + `script_pubkey` ≈ up to ~95 WU for max-size data). The signed transaction's *actual* fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`.
2. The `TooLowFee` check (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the same under-measured `vbytes`, so a transaction can pass the check yet fall below the default minimum relay fee once the data output is counted.
3. The final `weight > MAX_STANDARD_TX_WEIGHT` check likewise omits the data output, so a transaction that is genuinely non-standard (too heavy to relay) can be accepted.

An unprivileged caller controls `data`, `payments`, `change`, and `fee_per_vbyte`, so this is fully reachable from public inputs — the resulting `SignableTransaction` is what gets routed into FROST signing.

### Impact Explanation
A Bitcoin transaction can be constructed and signed that pays a lower effective fee rate than requested, potentially below the minimum relay fee, or that exceeds the maximum standard weight — in both cases producing a signed transaction that the Bitcoin network will not relay/mine. For an integrator sweeping or paying out scanned outputs (the only use of this module), funds are committed to a transaction that is not spendable/confirmable as intended: the inputs' offsets were already consumed by constructing the plan. The fee shortfall is bounded by the size of the OP_RETURN output (≤ ~80 bytes payload + overhead), which keeps this below "arbitrary theft" but makes it a concrete correctness/availability failure: the vault-equivalent accounting (`needed_fee`) is measured at the wrong scale relative to the transaction actually produced.

### Likelihood Explanation
Any caller that supplies `data` (e.g., embedding an `InInstruction` hash or other metadata, which the codebase's comments indicate is the intended use of the OP_RETURN field) triggers the mis-measurement. It is deterministic — no adversarial timing needed — and requires only passing a non-`None` `data` argument. The discrepancy is largest when `data` is near the 80-byte limit and `fee_per_vbyte` is at the minimum, exactly the regime where relay acceptance matters most.

### Recommendation
Include the data output in the measured transaction. The cleanest fix is to make `calculate_weight_vbytes` take the final `tx_outs` (or an explicit `data` length/serialized output) rather than only `payments`, so `weight`, `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all evaluate the same transaction that is returned in `SignableTransaction`. As a defense-in-depth measure, `fee()`/`needed_fee()` could be sanity-checked against the real `tx`'s weight at construction time.

### Proof of Concept
```rust
// Conceptual PoC against SignableTransaction::new
let data = vec![0u8; 80]; // max allowed
let st = SignableTransaction::new(
    inputs,                 // e.g. one ReceivedOutput
    &payments,              // one payment above DUST
    None,                   // no change
    Some(data.clone()),     // attacker-controlled OP_RETURN
    1,                      // fee_per_vbyte = minimum
).unwrap();

// needed_fee was computed as 1 * vbytes(tx without the OP_RETURN output)
// The actual tx includes the OP_RETURN output (~89 extra bytes of base size),
// so the effective fee rate is:
//   st.needed_fee() / actual_vbytes  <  1 sat/vB
// i.e. below DEFAULT_MIN_RELAY_TX_FEE once the data output is serialized,
// even though the internal TooLowFee check passed.
```
