### Title
Aggregator's `Setup` RPC is reachable by unauthenticated callers when `client_verification=false` - ([File: core/src/servers.rs])

### Summary
`create_grpc_server` only enforces `.client_ca_root(...)` and swaps in the `OnlyAggregatorAndSelf` interceptor when `config.client_verification` is `true`; otherwise it builds a `ServerTlsConfig` with no client CA and wraps the aggregator service in the `Noop` interceptor, which unconditionally returns `Ok(req)`. In the documented aggregator deployment profile (`client_verification=false`), any TCP client that completes a plain server-authenticated TLS handshake—no client certificate required—can call `ClementineAggregator::Setup(Empty{})` and trigger a full protocol re-setup.

### Finding Description
The intended binding is: **CALLER_AUTHORITY == self.aggregator_cert peer identity** for privileged aggregator methods, enforced via the `Interceptors::OnlyAggregatorAndSelf::call` path in `core/src/rpc/interceptors.rs:36-77`, which checks `req.peer_certs()` against `aggregator_cert`/`our_cert`.

In `core/src/servers.rs:106-139` (`create_grpc_server`), this check is gated entirely by `config.client_verification`:
```
let tls_config = if config.client_verification {
    ServerTlsConfig::new().identity(server_identity).client_ca_root(client_ca)
} else {
    ServerTlsConfig::new().identity(server_identity)
};
let service = InterceptedService::new(service, if config.client_verification { OnlyAggregatorAndSelf {...} } else { Noop });
```
`Interceptors::Noop::call` (`core/src/rpc/interceptors.rs:30`) returns `Ok(req)` unconditionally—no certificate or identity check of any kind. `create_aggregator_grpc_server` (`core/src/servers.rs:293-317`) passes the operator-supplied `config` straight into `create_grpc_server`, and merely logs a warning if `client_verification` is `true` (implying `false` is the expected/normal aggregator posture, matching the `bridge_config.toml` aggregator profile).

Consequently, when the aggregator runs with `client_verification=false`, an attacker who opens a bare TLS connection to the aggregator's public port—presenting no client certificate at all—reaches `AggregatorServer::setup` (`core/src/rpc/aggregator.rs`) exactly as an authorized aggregator peer would. The `only_aggregator_and_self` equality check is never evaluated, so it is vacuously "satisfied" by skipping it entirely rather than by the caller proving the right identity.

### Impact Explanation
`Setup` re-runs aggregator-driven protocol setup, redistributing verifier/operator configuration to the connected verifier/operator servers and mutating aggregator-held protocol state on demand. This is an unauthenticated, state-changing gRPC call reachable directly from the internet by any unprivileged attacker with just a TCP connection and TLS client (no certificate, no key share, no collateral)—matching the "High: an unauthenticated state-changing or broadcasting call" category. It is repeatable indefinitely and affects the whole deployment (all verifiers/operators managed by that aggregator instance), since `Setup` is a global, not per-deposit, operation.

### Likelihood Explanation
The only precondition is that the aggregator is deployed with `client_verification=false`, which the question states (and the toml layout suggests) is the documented/expected profile for the aggregator service specifically (as opposed to verifier/operator servers, which use `client_verification=true`). If that is indeed the shipped default aggregator posture, exploitation costs nothing beyond opening a TLS connection to the public aggregator port—no BTC, no fees, no prior relationship with the protocol. This is fully consistent with the attacker capability model (arbitrary requests to the aggregator's public gRPC port).

### Recommendation
Do not tie authentication of the aggregator's own privileged RPCs (`Setup` and any other state-mutating aggregator methods) solely to `config.client_verification`. Either (a) always require mTLS with a client CA on the aggregator's listening port regardless of the `client_verification` flag, or (b) apply a dedicated interceptor/allowlist for `Setup`-class methods that authenticates the caller independent of the general client-verification toggle, so that disabling generic client verification cannot silently disable authorization on privileged aggregator endpoints.
