### Title
Shared `BalanceHandler` instance in stateful precompiles causes bank/StateDB balance desynchronization on reentrant precompile calls - ([File: precompiles/common/balance_handler.go], [File: testutil/testdata/debug/debug.go])

### Summary
This is the Cosmos EVM analog of the Cap `Delegation.distributeRewards` bug: a piece of state that is meant to track "what has already been swept/processed" is shared and mutated across nested/recursive calls, so a later invocation silently consumes or skips the accounting window intended for an earlier one. In Cap this was `IERC20.balanceOf(address(this))` and a coverage=0 skip; in Cosmos EVM the analogous artifact is the `BalanceHandler.prevEventsLen` cursor that is reused by nested calls to the same precompile instance, causing `x/bank` CoinSpent/CoinReceived events to be double-processed or dropped when reconciling with the EVM `StateDB`.

### Finding Description
`BalanceHandler` records an event-log cursor (`prevEventsLen`) in `BeforeBalanceChange` and uses it in `AfterBalanceChange` to slice out only the bank events emitted during the current precompile invocation, translating them into `StateDB.AddBalance`/`SubBalance` calls: [1](#0-0) [2](#0-1) 

The "safe" pattern, used in `precompiles/common/precompile.go`'s `runNativeAction`, creates a **fresh** `BalanceHandler` per call via the factory: [3](#0-2) 

However, other precompile entry points (e.g. the debug/test precompile, which mirrors real precompiles such as staking/distribution/gov/ics20/slashing/erc20 that also reference `GetBalanceHandler()`) instead call `p.GetBalanceHandler()` directly on the `Run` path: [4](#0-3) 

If `GetBalanceHandler()` returns a handler tied to the `Precompile` struct instance rather than one freshly instantiated per call, then any reentrant/nested invocation of the same precompile instance within a single EVM call tree (e.g., a precompile call that itself triggers a Cosmos SDK hook or an EVM sub-call that re-enters the same precompile address) causes the inner call's `BeforeBalanceChange` to overwrite `prevEventsLen`. When the outer call resumes and invokes `AfterBalanceChange`, it slices events starting at the *inner* call's cursor instead of its own, so the balance-changing events emitted by the outer call's own bank transfer(s) are silently skipped from `StateDB` reconciliation (or, in the opposite ordering, events get double counted). This is exactly the class of bug in the report: a distribution/accounting mechanism that depends on a single mutable "last processed marker" being clobbered by a subsequent/nested operation, causing funds transferred at the `x/bank` layer to never be (or be incorrectly) reflected in the EVM-visible balance.

This repository's own integration test explicitly documents this as a known defect: [5](#0-4) 

### Impact Explanation
If `StateDB` balances diverge from the true `x/bank` balances for accounts involved in a precompile-triggered transfer (e.g., distribution `withdrawDelegatorRewards`/`claimRewards`, staking, gov, ICS-20, or ERC20 precompiles, all of which use `GetBalanceHandler()`), an unprivileged caller could construct a reentrant call sequence such that:
- a real bank-level credit/debit occurs, but the EVM `StateDB` never receives the corresponding `AddBalance`/`SubBalance` call, breaking 1:1 accounting between `x/bank` and EVM-visible balances, or
- the same event window is applied twice, duplicating spendable value in the EVM state.

Either outcome is an unauthorized corruption of spendable balance accounting across the native/EVM boundary, matching the "Critical unauthorized minting/duplication/irreversible accounting corruption" impact category.

### Likelihood Explanation
Triggering requires only an ordinary, unprivileged EVM transaction that causes a nested/reentrant call into a stateful precompile that shares state through `GetBalanceHandler()` instead of instantiating a handler per call via the factory pattern used in `runNativeAction`. The repository's own test suite reproduces this reentrancy scenario (`TestRecursivePrecompileCallsWithDebugPrecompile`) and states the bug outright, indicating the trigger condition (recursive/nested precompile calls) is reachable through normal contract composition, not a privileged or contrived path.

### Recommendation
Ensure every precompile execution path (not just `runNativeAction`) always instantiates a **new** `BalanceHandler` per call via `BalanceHandlerFactory.NewBalanceHandler()`, scoped to the local call frame, rather than retrieving/reusing an instance-level handler through `GetBalanceHandler()`. Alternatively, make `prevEventsLen` (and any equivalent cursor) part of a call-stack-aware structure (e.g., a stack pushed/popped per nested call) so that inner calls cannot clobber an outer call's bookkeeping. Add regression tests asserting that `x/bank` balances and `StateDB` balances remain equal after nested/reentrant precompile calls, not just that event counts match.

### Proof of Concept
The existing test `evmd/tests/integration/balance_handler/balance_handler_test.go` (`TestRecursivePrecompileCallsWithDebugPrecompile`) already demonstrates the mechanical trigger (a contract that recursively calls back into a precompile via `callback`), producing an unexpected event count relative to what naive per-call accounting would predict — evidence that `prevEventsLen` is being shared/overwritten across nested calls rather than scoped per invocation. A full weaponized PoC that quantifies the exact stolen/duplicated balance on a production precompile (e.g., distribution `claimRewards` re-entering itself or another balance-affecting precompile within the same EVM call) was not constructed here and would require additional tracing of `GetBalanceHandler()`'s definition (not located in the indexed files) to confirm it is instance-shared rather than per-call; this should be verified directly in a Devin session with full repository access before finalizing severity.
