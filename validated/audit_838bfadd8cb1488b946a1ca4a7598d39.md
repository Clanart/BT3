## Finding: Positional (not semantic) hunk-to-conflict-block matching allows silent misplacement of AI-resolved content into the wrong conflict block

### Title
Count-only validation of Copilot conflict-resolution hunks allows silent misalignment/corruption of committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The external Ion Protocol report is about an *aggregation* routine that only checks a total (quorum count) and blindly divides by it, so a missing individual feed silently drops the result to a fraction of the true value with no error raised. The structural analog in GitHub Desktop is `reassembleResolvedFile`/`reassembleResolutions` in the Copilot merge-conflict-resolution pipeline: the guard `validateResolutionPaths` only checks that the *total number* of hunks returned by the model equals the *total number* of conflict blocks expected for a file, but the actual splicing performed by `reassembleResolvedFile` pairs each hunk to a conflict block purely by array index/order, not by any semantic or positional identity check [1](#0-0) .

### Finding Description
`reassembleResolvedFile` walks the on-disk file with conflict markers and, for each well-formed `<<<<<<< / ======= / >>>>>>>` block found, splices in `hunkResolutions[hunkIndex]` where `hunkIndex` is simply incremented for every block encountered [2](#0-1) . There is no verification that hunk `i` in the model's JSON response actually corresponds to conflict block `i` in the file — the mapping is "matched by order, not by line number," as literally documented [3](#0-2) .

The only defense, `validateResolutionPaths`, checks aggregate counts:
```
const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
if (resolution.hunks.length !== expectedCount) { throw ... }
``` [4](#0-3) 

This is a "quorum-count-satisfied" check exactly like the Ion Protocol `QUORUM` divisor: it confirms the *number* of contributing elements is correct but never validates that each element maps to the *correct* underlying slot. Just as `(feed0 + feed1)/QUORUM` silently halves the value when one feed defaults to `0` while the count still "looks right," a model response that returns the right *number* of hunks but in the wrong *order* (e.g., because it merged two adjacent conflict regions into one hunk while padding the tail with an extra empty hunk, or reordered hunks during JSON generation) will pass `validateResolutionPaths` and then get silently spliced into the wrong conflict blocks by `reassembleResolvedFile`.

Additionally, if `hunkIndex` ever exceeds `hunkResolutions.length` for any reason, the code silently drops the block's content entirely (`if (hunkIndex < hunkResolutions.length) { ... }`, else nothing is pushed) [5](#0-4)  — a direct parallel to the oracle's "defaults to 0" silent-failure mode.

The model's input (conflict hunks, surrounding context, commit messages, PR titles) is derived from attacker-influenced content: an attacker who controls one side of a merge (a branch/PR merged into the repo, or a crafted upstream commit that the victim pulls/rebases) fully controls the conflict markers and context text fed into the LLM prompt [6](#0-5) . Prompt-injection-style content (e.g., text resembling additional JSON hunks, or conflict blocks engineered to produce ambiguous boundaries) can influence how many/which hunks the model emits without violating the count check.

### Impact Explanation
Once resolutions pass validation, they are written directly to disk and staged for commit with no further correctness check:
```
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
...
await git(['add', '--', ...pathsToStage], repository.path, 'copilotConflictResolution')
``` [7](#0-6) 

If content is spliced into the wrong conflict block, the user sees a "resolved" file with no remaining conflict markers, accepts it via "Continue Merge," and silently commits/pushes code that does not match what was actually reviewed — the corrupted value is the *reassembled file content* (`resolvedContent`) that the app treats as validated, mirroring the Ion Protocol case where a structurally-valid-looking aggregate (`val`) is actually corrupted. This is a silent corruption of what the user commits/pushes, sourced from attacker-influenced repository/merge content.

### Likelihood Explanation
This requires no local access, admin rights, or prior malware: it only requires the victim to merge/rebase/cherry-pick against a branch or PR whose content an attacker controls (a normal, expected Desktop workflow) and to use the "Resolve with Copilot" feature. The count-based validation is a real, narrow gap — LLM outputs are known to be inconsistent in exact ordering/boundary segmentation for closely-spaced or nested conflict markers, which is a realistic (not purely theoretical) failure mode for `hunks` ordering, especially across chunked/batched requests where each chunk is resolved somewhat independently [8](#0-7) .

### Recommendation
Replace positional-only hunk matching with an explicit, verifiable identity for each conflict block (e.g., include the original block's start-line index or a content hash of the "ours"/"theirs" markers in the prompt and require the model to echo it back per hunk), and validate that identity in `validateResolutionPaths`/`reassembleResolvedFile` rather than relying solely on total hunk count. Additionally, treat any hunk-index overflow in `reassembleResolvedFile` as a hard validation failure rather than silently omitting content, and surface a diff/preview of the reassembled file for user confirmation before staging, rather than trusting `resolvedContent` as fully "resolved."

### Proof of Concept
1. Set up a repo and trigger a merge conflict where two closely-spaced conflict blocks exist in a single file (e.g., adjacent `<<<<<<<...>>>>>>>` blocks separated by only 1–2 lines of context).
2. Use "Resolve with Copilot"; because the model returns the correct total hunk count (2) but internally treats the two adjacent blocks as one logical change and emits its resolutions in a different order/segmentation (still 2 entries, satisfying `validateResolutionPaths`), `reassembleResolvedFile` splices hunk[0]'s content into block A's position and hunk[1]'s content into block B's position, but the model's content was written assuming the opposite grouping.
3. `_applyCopilotConflictResolutions` writes the reassembled content directly to disk and `git add`s it with no further validation [9](#0-8) , so the user commits a file where code intended for block A ends up in block B (or vice versa), with no conflict markers remaining to alert them.

**Caveat:** I could not fully trace the exact call path in `app/src/lib/stores/copilot-store.ts` (large file, chunk-resolution internals were only partially visible) to confirm with 100% certainty that no additional per-hunk semantic check exists beyond `validateResolutionPaths` before `reassembleResolutions` is invoked. Given index size limits, some file contents may not be available — a Devin session with full file access would be needed to verify the exact call sequence in `copilot-store.ts` around `resolveChunk`/`resolveConflicts` before treating this as fully confirmed.
