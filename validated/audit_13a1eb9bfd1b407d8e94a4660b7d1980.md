## Title
Reward-Sniping via Instantaneous `rewardPerTokenStored` Update Lets Flash-Deposits Steal Pending WOM/MGP Yield - ([File: rewards/BaseRewardPool.sol], [File: wombat/WombatStaking.sol], [File: rewards/MasterMagpie.sol])

## Summary
Analogous to the VAIVault MEV bug, the Magpie reward system distributes accrued yield in a single instantaneous jump (proportional to the pool's *current* `totalStaked()`) whenever `harvest()`/`queueNewRewards()` fires, rather than streaming it continuously over the accrual period. Because deposits and withdrawals through `MasterMagpie`/`WombatPoolHelper` have no lock-up or vesting, any unprivileged wallet can flash-deposit right before a permissionless `harvest()` call and withdraw immediately after, capturing a disproportionate share of rewards that accrued to long-term stakers.

## Finding Description
`BaseRewardPool._provisionReward` (called by `queueNewRewards`/`donateRewards`) increases `rewardPerTokenStored` all at once based on the pool's `totalStaked()` at the moment of the call: [1](#0-0) 

`WombatStaking.harvest()` is a **permissionless** entry point (gated only by `_onlyActivePool`, not by owner/manager) that pulls pending WOM emissions from the underlying Wombat MasterWombat and immediately forwards them into the rewarder via `_toMasterWomAndSendReward` → `queueNewRewards`: [2](#0-1) [3](#0-2) 

`WombatPoolHelper.harvest()` exposes the same call to any wallet with no access control: [4](#0-3) 

Deposits and withdrawals in `MasterMagpie._deposit`/`_withdraw`/`_harvestAndUnstake` have no cooldown or time-weighting — a user's `user.amount` is immediately counted toward `totalStaked()` on deposit and can be withdrawn in the very next call: [5](#0-4) 

Because `rewardPerTokenStored` is bumped by `(_amountReward * 10**decimals) / totalStaked()` at the instant `queueNewRewards` runs, whoever holds the largest share of `totalStaked()` at that instant claims the largest share of the entire pending reward batch — regardless of how briefly they've actually been staked. This mirrors the VAIVault flaw exactly: pending rewards accumulate off-chain/in the external protocol (Wombat's MasterWombat) until someone triggers the harvest, and the accounting has no protection against last-second deposits capturing that pending pot.

## Impact Explanation
An attacker can:
1. Flash-loan or otherwise acquire a large amount of the pool's deposit token.
2. Call `WombatPoolHelper.deposit()` to stake a large position (registered instantly in `MasterMagpie`, no vesting).
3. Call `WombatPoolHelper.harvest()` (or directly `WombatStaking.harvest(lpToken)`), which pulls all pending WOM emissions and instantly inflates `rewardPerTokenStored` proportional to the now-inflated `totalStaked()`.
4. Call `WombatPoolHelper.withdraw()` to unstake, which triggers `_harvestBaseRewarder`/`updateFor`, crediting the attacker their (now large) share of `userRewards`.
5. Claim the harvested WOM/MGP via `MasterMagpie` claim functions and repay the flash loan.

This results in theft of unclaimed yield that rightfully belongs to legitimate long-term stakers — the larger the pending reward batch (e.g., after a long gap since the last harvest), the larger the theft, satisfying the "theft of unclaimed yield" impact criterion.

## Likelihood Explanation
`harvest()`, `deposit()`, and `withdraw()` are all unprivileged, externally callable functions reachable from an ordinary wallet in a single transaction (optionally using a flash loan for capital). No governance, oracle, or admin interaction is required, and the exploit is economically rational whenever the pending reward batch is large relative to the pool's steady-state stake (e.g., after periods of low activity where nobody has called `harvest()`).

## Recommendation
- Stream rewards over time (e.g., a rate-based `rewardRate`/`periodFinish` model like Synthetix `StakingRewards`) instead of crediting the full batch to `rewardPerTokenStored` in one shot at `queueNewRewards` time.
- Alternatively, snapshot `totalStaked()` and reward eligibility prior to the block in which `queueNewRewards`/`harvest` executes, or impose a minimum staking duration before a deposit is eligible for freshly queued rewards.
- Consider calling `harvest()`/`updateFor` and settling all pending rewards at the very start of `deposit`/`withdraw`, before any balance changes are applied, so new deposits cannot retroactively claim rewards accrued before they staked.

## Proof of Concept
```
Pre-condition: Pool P has 1,000,000 staked, 100 WOM pending in MasterWombat (unharvested).

1. attacker calls WombatPoolHelper(P).deposit(9,000,000 stable, minLP)
   -> MasterMagpie._deposit stakes 9,000,000 for attacker (now 10,000,000 total staked)

2. attacker calls WombatPoolHelper(P).harvest()
   -> WombatStaking.harvest(lpToken) -> _toMasterWomAndSendReward(..., true)
   -> pulls 100 WOM from MasterWombat, calls BaseRewardPool.queueNewRewards(100, WOM)
   -> rewardPerTokenStored += 100 * 1e18 / 10,000,000  (attacker now owns 90% of totalStaked)

3. attacker calls WombatPoolHelper(P).withdraw(9,000,000, minOut)
   -> MasterMagpie._withdraw -> _harvestBaseRewarder -> rewarder.updateFor(attacker)
   -> userRewards[WOM][attacker] credited ~90 WOM

4. attacker claims ~90 WOM via MasterMagpie multiclaim, despite staking for only 2 transactions.
```
This is the same pattern described in the VAIVault report: pending emissions accounted for in a lump sum at harvest time, exploitable by a last-second large deposit followed by an immediate withdrawal.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

        if (user.amount > 0) {

        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;

        if (_amount > 0)

                emit Deposit(_account, _stakingToken, _amount);
            else

    }

    /// @notice internal function to deal with withdraw staking token
    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
        emit Withdraw(_account, _stakingToken, _amount);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
