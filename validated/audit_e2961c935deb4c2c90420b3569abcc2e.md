### Title
Use of unsafe `transfer` for USDT reward payout causes permanent DoS of `ArbWomUp.incentiveDeposit` - ([File: wombat/ArbWomUp.sol])

### Summary
`ArbWomUp.incentiveDeposit` pays a USDT-denominated incentive reward to any caller who deposits WOM, using the raw `IERC20(usdt).transfer(...)` call instead of `safeTransfer`. If `usdt` is set to the real USDT token (which does not return a `bool` from `transfer`), every call to `incentiveDeposit` that computes a non-zero reward will revert, permanently blocking unprivileged users from participating in this incentive/distribution mechanism.

### Finding Description
`incentiveDeposit` is an unprivileged, user-facing function that lets any wallet deposit WOM and receive a USDT reward based on their deposit tier: [1](#0-0) 

The reward payout uses the plain ERC20 `transfer` function rather than OpenZeppelin's `safeTransfer`, even though the contract already imports and uses `SafeERC20` elsewhere in the same file (`safeTransferFrom` in `_deposit`): [2](#0-1) 

Real USDT on Ethereum does not return a `bool` on `transfer`/`transferFrom`. When the Solidity ABI decoder for a call declared with the standard `IERC20` interface (which expects a `bool` return) receives no return data of the expected size in certain compiler/interaction paths, or more critically, existing tooling wraps raw `.transfer()` calls in a way that reverts on missing/incompatible return data, the call fails. This is the same root cause identified in the referenced report for `ZappingProxy.sol`: any raw, unwrapped `.transfer` call on a token with non-standard return behavior (like USDT) will unconditionally revert.

Since `_checkAmount`, `_deposit`, and the reward `transfer` all execute in a single atomic transaction with `nonReentrant`, a revert in the final `transfer` call rolls back the entire transaction — including the WOM deposit that had already succeeded via `safeTransferFrom`.

### Impact Explanation
Any unprivileged user calling `incentiveDeposit` for an amount that yields `rewardToSend > 0` will have their entire transaction revert once `usdt` is configured to a USDT-like token with non-standard return semantics. This permanently and unconditionally denies ordinary users the ability to use this deposit/incentive path — there is no workaround, since the revert is deterministic for every call with `rewardToSend > 0`. This constitutes a permanent denial of service of a core, unprivileged user-facing function of the protocol's distribution mechanism, matching the accepted "24-hour-plus freeze" / permanent-DoS impact class (the deposit path becomes unusable indefinitely until an admin redeploys/reconfigures the contract).

### Likelihood Explanation
Likelihood is high whenever `usdt` is set to the real USDT token address (the state variable and reward-naming convention in the contract strongly suggest this is the intent, mirroring the exact bug class from the external report). Because `getRewardAmount` returns a non-zero value for essentially any tiered deposit, the vast majority of ordinary calls to `incentiveDeposit` would trigger the revert, not just edge cases.

### Recommendation
Replace the raw `transfer` call with `safeTransfer` from OpenZeppelin's `SafeERC20` library, which is already imported and used elsewhere in this same contract:
```solidity
IERC20(usdt).safeTransfer(msg.sender, rewardToSend);
```

### Proof of Concept
1. Deploy `ArbWomUp` and initialize with `wom` = a standard WOM token and `usdt` = the real USDT contract address (or any mock ERC20 that does not return a `bool` on `transfer`, replicating USDT's behavior).
2. Configure `setMultiplier` so that any deposit produces `rewardToSend > 0` in `getRewardAmount`.
3. Have an ordinary wallet approve WOM to `ArbWomUp` and call `incentiveDeposit(amount)`.
4. Observe that the transaction reverts at `IERC20(usdt).transfer(msg.sender, rewardToSend)` because the low-level call does not return the expected `bool`, rolling back the WOM deposit as well — the user cannot use `incentiveDeposit` at all as long as `usdt` behaves like real USDT. [3](#0-2)
