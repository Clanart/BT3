### Title
Fixed 8,000-char diff truncation in `build_refute_prompt` lets attacker-padded diffs push a genuinely new dangerous change out of the self-refute context, causing it to be misclassified as "PRE-EXISTING" and refuted - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` truncates the diff shown to the adversarial "refute" stage with a raw `diff_text[:8000]` slice, unlike stage-1's `build_investigate_prompt`, which uses `cap_diff_for_prompt` to cap and clearly mark truncation per file. Because the refute stage's own "PRE-EXISTING" rule tells the model to refute a candidate if its vulnerable code "does NOT appear on any + line in the DIFF block above," an attacker who controls the diff (e.g., a normal PR/commit author) can pad earlier hunks so the actually dangerous `+` line falls past byte 8000 and is invisible to the model, causing a real, newly-introduced vulnerability to be refuted as pre-existing.

### Finding Description
`build_investigate_prompt` builds diff text via `cap_diff_for_prompt`, which caps bytes per-file and in total while inserting explicit `"[truncated by security-guidance: ...]"` markers so the model always knows a file's content is incomplete [1](#0-0) .

`build_refute_prompt`, by contrast, takes the raw, uncapped `diff_text` argument and blindly slices the first 8000 characters with no per-file boundary handling and no truncation marker: `"\n\nDIFF:\n" + diff_text[:8000]` [2](#0-1) . For a multi-file diff, any content after the 8000th character (which can easily be exceeded by a single moderately sized file, given the 80,000-byte per-file cap and 400,000-byte total cap used elsewhere) is silently dropped from the model's view with no indication that truncation occurred.

The refute stage's own instructions then make this omission dangerous: the model is told to REFUTE a candidate if "the cited vulnerableCode does NOT appear on any + line in the DIFF block above — it is unchanged context in a touched file" [3](#0-2) . The model's only tools in this stage are Read/Grep against the *current* filesystem state [4](#0-3)  — it has no way to independently query the actual git diff or line-attribution to check whether code is new. It must rely entirely on whether the text is visible in the "DIFF:" block it was given.

An attacker who submits the reviewed commit/PR fully controls diff content and ordering. By padding earlier files/hunks in the diff so the truncation boundary (8000 chars) lands just before the genuinely dangerous `+` line, the attacker can make that dangerous addition invisible to the refute prompt. Since the model still sees the corresponding finding surfaced by stage 1 (`candidates`) referencing that vulnerable code, but cannot find it in the truncated "DIFF:" block, the PRE-EXISTING heuristic fires and the model refutes a real, newly-introduced vulnerability — defeating the "Default = SURVIVES" fallback the prompt otherwise relies on [5](#0-4) . This breaks the stated invariant that prompt assembly must not let untrusted repo content (the diff itself) suppress review of dangerous changes.

### Impact Explanation
This is a logic-level bypass of the security-review guard: a crafted, attacker-authored diff can suppress the automated self-refute pipeline's ability to keep (i.e., surface) a genuine vulnerability finding, effectively laundering a dangerous change through the review pipeline as "refuted"/pre-existing. This matches "Logic-level service disruption caused by bypassing a required guard" — the required review guard (adversarial refute pass) is defeated by input the attacker fully controls (diff padding), without needing any elevated privilege.

### Likelihood Explanation
- Preconditions: the attacker only needs to be able to author a diff/commit that is fed into this review pipeline (a normal cloned-repo/PR contribution flow) — no elevated privilege, keys, or social engineering required.
- Feasibility: padding a diff with filler content before the malicious hunk is trivial and does not require any special crafting beyond size/ordering, since `cap_diff_for_prompt` caps allow per-file diffs up to 80,000 bytes and total up to 400,000 bytes, far exceeding the 8,000-char window used by `build_refute_prompt`.
- Repeatability: deterministic — the same truncation boundary applies on every invocation given the same diff size/order, so the bypass is reliably reproducible via a unit test on `build_refute_prompt` output.

### Recommendation
Route `diff_text` in `build_refute_prompt` through the same `cap_diff_for_prompt` diff-anchored capping/truncation-marking logic used by `build_investigate_prompt` (per-file caps with explicit truncation markers, prioritizing the files/hunks referenced by the candidate findings so the cited `vulnerableCode` and its surrounding `+`/`-` lines are guaranteed to remain in-window), rather than a flat `[:8000]` slice on the concatenated diff. Additionally, when truncation is unavoidable, ensure the hunks corresponding to each candidate's `filePath`/`vulnerableCode` are prioritized/anchored ahead of unrelated hunks so the PRE-EXISTING check can never fire due to truncation rather than genuine absence from the diff.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py::build_refute_prompt`:
1. Construct a synthetic `diff_text` consisting of a large, benign filler file diff (~9000 chars) followed by a small hunk containing a clearly dangerous `+` line (e.g. `+subprocess.run(user_input, shell=True)`) tagged to a `candidates` entry citing that exact `vulnerableCode`.
2. Call `build_refute_prompt(candidates, diff_text)` and assert that the resulting prompt's `"DIFF:\n..."` section (i.e., `diff_text[:8000]`) does NOT contain the dangerous `+` line — demonstrating the anchor is lost.
3. Assert (fast validation per the target) that after applying the intended fix (diff-anchored capping via `cap_diff_for_prompt`-style logic), the dangerous `+` line remains present in the DIFF block regardless of preceding filler size, i.e., `dangerous_line in prompt_after_fix` is `True` while `dangerous_line in prompt_before_fix` is `False`.
4. Optionally simulate the model-facing consequence: assert that a rule-based re-implementation of the "PRE-EXISTING" check (`vulnerableCode not in diff_block`) evaluates to `True` (i.e., would incorrectly refute) under the current implementation and `False` after the fix.

def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",

    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped

    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
