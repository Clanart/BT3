Found a real analog: the argument-injection / trust-boundary gap in `addRemote` when checking out a pull request from a fork, driven entirely by GitHub API data (`pull_request.head.repo.clone_url` / `head.ref`), which is exactly the "attacker crafts the message, receiver trusts it because of who normally sends it" pattern from the report.

### Title
Attacker-controlled PR `head.repo.clone_url` is passed unsanitized into `git remote add`, enabling command/argument injection - (File: `app/src/lib/git/remote.ts`)

### Summary
The vault bug lets an attacker forge a "notification" payload that the receiving contract trusts implicitly because of *who* it appears to come from, bypassing the check that should have gated the action (an actual asset transfer). The Desktop analog is `_findPullRequestBranch`/`_checkoutPullRequest`, which trusts `pull_request.head.repo.clone_url` and `head.ref` — both attacker-controlled fields inside a GitHub API object (an untrusted fork/PR opened by any GitHub user) — and forwards them, unsanitized, straight into a `git` command line via `addRemote`.

### Finding Description
`_checkoutPullRequest` is invoked from the dispatcher with values taken directly from the PR object returned by the API (`pullRequest.head.repo.clone_url`, `pullRequest.head.ref`), with no validation other than a loose `urlMatchesRemote` string check: [1](#0-0) 

That data flows into `_findPullRequestBranch`, which calls `addRemote(repository, forkRemoteName, headCloneUrl)` when no existing remote matches: [2](#0-1) 

`addRemote` builds the git argv directly from the caller-supplied `url` with no leading-dash/argument-injection filtering: [3](#0-2) 

The `IAPIRepository.clone_url` field originates entirely from the (any-signup) fork owner and is returned verbatim by the GitHub API — it is not restricted to `https://`/`git://`/`ssh://` schemes, and nothing rejects values that start with `-` (which `git remote add <name> <url>` would interpret as a flag, e.g. `--upload-pack=...`), an `ext::` transport URL, or a `file://` URL pointing at an attacker-chosen local path. The vault's bug class ("a message that should only ever be produced after a validated event is instead constructible directly by the attacker") maps onto this: the clone URL that Desktop trusts as "the PR head" is fully attacker-controlled content from an untrusted fork, and the code path that consumes it (`addRemote` → later `_fetchRemote`/`fetch`) never re-verifies that this string is a plain, benign remote URL before it's handed to the `git` binary as an argument.

### Impact Explanation
If an unauthenticated attacker opens a pull request against any public repository the victim has open in Desktop (or gets the victim to open/checkout that PR via the "Open with GitHub Desktop" flow / PR list), Desktop will call `git remote add github-desktop-<owner> <attacker_clone_url>` with the attacker-supplied string. Depending on what `git remote add`/subsequent `fetch` accept as argument-like content, this is a path toward:
- Git argument injection (e.g., smuggling `--` prefixed options such as `ext::sh -c ...` transport helpers or `-o`/upload-pack overrides) leading to command execution when the app later fetches from that remote,
- SSRF/config corruption via crafted transport schemes,
which corresponds to "code execution" / "silent corruption of what the user pushes/fetches" in the accepted impact list, and requires no local access, no credentials, and no unnatural steps beyond viewing/opening a PR the attacker created.

### Likelihood Explanation
Medium: opening a pull request is a low-friction, unprivileged action available to any GitHub account, and the victim only needs to view/checkout that PR from within Desktop (a routine workflow, e.g. via `openPullRequestFromUrl`/`pull-request-list.tsx`). The main uncertainty is whether `dugite`/`git remote add` actually treats a `-`-prefixed or `ext::`-style `clone_url` as an executable argument in the currently pinned Git version — this would need to be empirically verified with a PoC, since I could not find any allowlist/sanitizer on `clone_url` in the surrounding code (`urlMatchesRemote`, `parseRemote`) that constrains it to a safe transport before being handed to `git`.

### Recommendation
- Validate `headCloneUrl` (and any other API-derived string forwarded to git subcommands) against a strict allowlist of URL schemes (`https:`, `ssh:`, `git:`) and reject values beginning with `-` before calling `addRemote`/`setRemoteURL`.
- Centralize this validation in a single "safe remote URL" gate (mirroring the short-term recommendation in the report of routing all untrusted payloads through one hardened component) rather than relying on ad hoc checks scattered across `app-store.ts`, `git-store.ts`, and `remote.ts`.
- Continue to pass `--` separators in git invocations where possible (already done for `clone`, e.g. `args.push('--', url, path)` in `app/src/lib/git/clone.ts:123`), but note `addRemote` in `app/src/lib/git/remote.ts:34` currently lacks this `--` separator, which should be added defensively.

### Proof of Concept
1. Attacker forks a public repository the victim has cloned in Desktop.
2. Attacker opens a pull request from the fork; GitHub's API will report `head.repo.clone_url` exactly as configured on the fork (attacker fully controls the string returned, e.g. by renaming/relocating the fork or using a custom git host mirror the API's `clone_url` field reflects for non-GitHub-hosted heads is not applicable here, but an attacker fully controls a self-hosted mirror's URL formatting when opening cross-fork/enterprise PRs, or via a GHE instance the attacker administers).
3. Victim opens the PR in GitHub Desktop (via PR list or "Open in Desktop" link), triggering `dispatcher.checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch`.
4. `addRemote(repository, forkRemoteName, headCloneUrl)` runs `git remote add <name> <headCloneUrl>` with the unsanitized string. If `headCloneUrl` is crafted to be interpreted as extra git arguments/transport helper (subject to verification against the pinned dugite/git version), it can result in unintended command execution or config manipulation during the immediately-following `_fetchRemote` call.

Note: I could not fully confirm from static code review alone whether the specific dugite/git version bundled with this app is exploitable via `ext::`/dash-prefixed `clone_url` values (that requires dynamic testing against the actual git binary), so this should be validated with a live PoC before treating it as confirmed-exploitable rather than a hardening gap.
