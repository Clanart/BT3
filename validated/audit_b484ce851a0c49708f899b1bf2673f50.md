### Title
Attacker-supplied participant indexes in `GeneratorPromotion::complete` cause panic DoS via missing-key `unwrap` - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to CVE-2024-6428 (the application trusts caller-supplied identifiers instead of enforcing the canonical set), `GeneratorPromotion::complete` accepts a `HashMap<Participant, GeneratorProof>` keyed by caller-chosen `Participant` indexes and only validates the map's length and that each key is `<= n`. It never verifies the keys are exactly the expected set `1..=n` minus the local participant. An unexpected key (e.g., the victim's own index `i`, or any index that displaces another participant) leaves some `i` in `1 ..= params.n()` without an entry, and `proofs.get(&i).unwrap()` panics, aborting the promotion — a limited denial of service caused purely by peer-supplied "user-defined IDs". [1](#0-0) 

### Finding Description
In `complete`, the only validation of `proofs` is:

- `proofs.len() == params.n() - 1` (line 125), and
- every key satisfies `u16::from(i) <= params.n()` (line 133). [2](#0-1) 

The function then iterates `i in 1 ..= params.n()`, skips the local index `params.i()`, and unconditionally unwraps `proofs.get(&i)` (line 146). Because `Participant` indexes are attacker-chosen map keys, a participant can submit a map containing the victim's own index `params.i()` (which is skipped in the loop) plus `n-2` other valid indexes. The length check passes (`n-1` entries), all keys are `<= n`, yet some legitimate participant `j` is missing, so `proofs.get(&j).unwrap()` panics before any proof verification occurs. Compare with `frost::validate_map` and PedPoP's `validate_map`, which correctly check that a peer-supplied map's keys equal the expected participant set (missing and duplicated participants are rejected). [3](#0-2) [4](#0-3) 

### Impact Explanation
A single malicious participant in a generator-promotion session can crash the victim's `complete` call (panic → thread/task abort), denying completion of the promotion for that participant. Since promotion is a O(n) substitute for re-running key generation, repeatedly disrupting it prevents key migration to the new generator. This mirrors the Mattermost impact profile: user-controlled IDs accepted without set-membership validation break administrative operations — here, an unprivileged peer's chosen `Participant` keys break the protocol flow. No secret leakage or forgery results, matching Medium severity.

### Likelihood Explanation
Reachability requires only that the victim runs `GeneratorPromotion::complete` with a `proofs` map containing attacker-influenced keys — the normal protocol flow where each participant broadcasts a `GeneratorProof` tagged with its index. The attacker just mislabels their proof (or a relay/indexing layer maps it to the wrong `Participant`), which needs no cryptographic capability. The panic happens before any proof is verified, so the malicious input needs no valid DLEq proof. Likelihood is moderate: it needs an active participant in the session, but any single participant suffices.

### Recommendation
Replace the length/bounds checks with an exact set-membership validation, matching the `validate_map` pattern used elsewhere: require `proofs.len() == n - 1`, reject any key equal to `params.i()` (`DuplicatedParticipant`/invalid index), and for every `i in 1..=n` with `i != params.i()` return a `MissingParticipant`-style error instead of unwrapping. Concretely, change line 146 to `let proof = proofs.get(&i).ok_or(PromotionError::MissingParticipant(i))?;` and add a check rejecting `proofs.contains_key(&params.i())`. [5](#0-4)

```rust
// Attacker (participant 3) submits their proof under the victim's index 1
// (or the integration layer keys the map by attacker-supplied indexes).

proofs.insert(Participant::new(1).unwrap(), attacker_proof); // victim's own index
proofs.insert(Participant::new(2).unwrap(), honest_proof);   // participant 3 missing

// proofs.len() == 2 == n - 1  -> passes
// all keys (1, 2) <= n = 3    -> passes
// Loop: i=1 skipped (self), i=2 ok, i=3 -> proofs.get(&3).unwrap() -> PANIC
promoting.complete(&proofs); // thread panics at crypto/dkg/promote/src/lib.rs:146
```

The panic occurs on line 146 (`proofs.get(&i).unwrap()`) before any DLEq verification, so the attacker's `GeneratorProof` can be arbitrary bytes that parse, requiring zero valid-secret knowledge.
