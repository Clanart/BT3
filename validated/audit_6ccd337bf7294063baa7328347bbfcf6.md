### Title
Field-extraction ambiguity in `_extract_field` allows attacker-controlled `tool_input` keys to shadow the intended content field, bypassing content-scoped block rules - ([File: plugins/hookify/core/rule_engine.py])

### Summary
The specific mechanism described in the question (line 238's `tool_input.get('content') or tool_input.get('new_string', '')`) is not actually reachable in the scenario proposed, because the generic direct-field lookup earlier in the same function intercepts the key first. However, that earlier lookup is itself the real source of the ambiguity the question is probing for, and it does allow an attacker-shaped `tool_input` to make a rule scoped to `field: "content"` inspect the wrong data.

### Finding Description
`_extract_field` first performs a generic, tool-agnostic lookup: `if field in tool_input: ... return value` [1](#0-0) . Only if that check misses does it fall through to the tool-specific branch that contains the `tool_input.get('content') or tool_input.get('new_string', '')` fallback for Write/Edit [2](#0-1) .

Because the generic check tests key *presence*, not truthiness, an attacker-shaped `tool_input` for an `Edit` call such as `{"content": "", "old_string": "...", "new_string": "<malicious payload>"}` causes line 196 to match on `"content"` and return the empty string immediately — the code never reaches the Write/Edit branch or the `or` fallback at line 238 at all. A rule such as `field: content, operator: contains, pattern: "<malicious payload>"` is evaluated against `''` instead of `new_string`, silently missing the payload that is actually written to disk via the `Edit` tool's `new_string`.

So the exploit is real, but the root cause is the *generic* `if field in tool_input` short-circuit at line 196, not the `or` operator at line 238 as described in the question. The `or` fallback at 238 is only ever reached when the `content` key is completely absent from `tool_input`, in which case `.get('content')` returns `None` (not `''`), so the described "falsy empty string silently falling through" scenario at line 238 specifically does not occur — line 196 always wins first when a `content` key of any value (including `''`) is present.

### Impact Explanation
If exploitable, this would let an attacker whose payload flows into `Edit`/`Write` `tool_input` (e.g., via an untrusted MCP tool response or a manipulated tool call) suppress detection by hookify content-inspection block rules, allowing an unauthorized/malicious file write to proceed. This matches "unauthorized file/action bypass of hook enforcement" impact class.

### Likelihood Explanation
This requires attacker control over the exact shape of `tool_input` passed to the `Edit`/`Write` tool call (i.e., ability to inject an extra `content: ""` key alongside real `old_string`/`new_string` keys) before it reaches the hook's `PreToolUse` input. Whether Claude Code's tool-calling layer would actually pass through such an out-of-schema extra key to the hook's `tool_input` is not verifiable from this repository, since that enforcement (if any) lives in Claude Code core, not in this plugin. This repo only contains the hookify plugin's rule engine, and the hook receives whatever `tool_input` JSON is on stdin, `plugins/hookify/core/rule_engine.py` [3](#0-2)  — there is no independent validation elsewhere in this file that a `tool_name`-appropriate key set is enforced before extraction. Because of this, likelihood is uncertain/unconfirmed rather than proven.

### Recommendation
Remove the generic tool-agnostic `if field in tool_input` short-circuit for tool-specific field names (`content`, `new_text`, `new_string`, `old_text`, `old_string`), and dispatch strictly by `tool_name` first so extraneous/attacker-supplied keys cannot shadow the tool's canonical field. For the `content` alias, explicitly define per-tool authoritative sources (`Write` → `content` only, `Edit`/`MultiEdit` → `new_string`/`edits[].new_string` only) rather than falling back generically.

### Proof of Concept
Unit test in a differential-test style against `RuleEngine._extract_field` / `evaluate_rules`:
1. Construct a `Condition(field="content", operator="contains", pattern="MALICIOUS")` wrapped in a blocking `Rule` with `tool_matcher="Edit"`.
2. Case A: `tool_input = {"file_path": "f.py", "old_string": "x", "new_string": "MALICIOUS"}` (no `content` key) → assert `evaluate_rules` returns a block (detects payload via line 238 fallback).
3. Case B: `tool_input = {"file_path": "f.py", "content": "", "old_string": "x", "new_string": "MALICIOUS"}` → assert `evaluate_rules` returns `{}` (no block), demonstrating the payload in `new_string` is missed because `_extract_field` returns `''` from the direct `content` key match at line 196 before line 238 is ever reached.
4. Assert the two cases produce different outcomes despite the same actual payload being written via `new_string`, confirming the field-extraction ambiguity — but with the caveat above that the mechanism is the line-196 generic lookup, not the line-238 `or` fallback as originally hypothesized.

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)
