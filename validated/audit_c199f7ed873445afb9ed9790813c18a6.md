### Title
Missing zero-check on `Kip71GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`)

### Summary
`params.KIP71Config.NextMagmaBlockBaseFee` uses `kc.GasTarget` as a divisor when computing the base fee delta, but the governance format checker for this parameter (`Kip71GasTarget` in `kaiax/gov/param.go`) never rejects a value of `0`, unlike the sibling parameter `Kip71BaseFeeDenominator` which explicitly enforces `v != 0`. This is the same bug class as the reported `_validateFeeFraction` issue: a fraction/ratio denominator that can legally be validated as `0`, later causing an undefined division.

### Finding Description
`NextMagmaBlockBaseFee` divides by `gasTarget` twice, in both the "increase" and "decrease" base-fee branches: [1](#0-0) [2](#0-1) 

`gasTarget := kc.GasTarget` is taken directly from the governance-controlled `KIP71Config` without any local zero-guard (contrast with `BaseFeeDenominator`, which is explicitly defaulted to `64` if zero): [3](#0-2) 

The governance parameter framework only validates `Kip71GasTarget` with a `noopFormatChecker` that accepts any `uint64`, including `0`: [4](#0-3) 

Compare this to the properly-guarded `Kip71BaseFeeDenominator` parameter, which requires a nonzero value at the governance layer: [5](#0-4) 

If `Kip71GasTarget` is ever set to `0` via a governance vote, then for any block where `parentGasUsed != gasTarget` (i.e. almost every block, since `parentGasUsed > 0 = gasTarget`), the code enters the "increase" branch and computes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor. Go's `math/big.Int.Div` panics on division by zero, so this call panics deterministically on every full node computing `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` for the next block header.

### Impact Explanation
This is reachable purely through the standard, in-scope governance-parameter path (no p2p, consensus-message, or validator-key compromise required). Once `Kip71GasTarget=0` is adopted as the active parameter set, `NextMagmaBlockBaseFee` panics deterministically for essentially every subsequent block on every node that computes header verification or fee estimation (block validators, fee-history RPC handlers such as `node/cn/gasprice/feehistory.go`, and the child-chain fee sync handler in `node/sc/main_bridge_handler.go`, all of which call into `KIP71Config`/`NextMagmaBlockBaseFee`). This halts block production/verification network-wide — a chain-halting denial of service, not a mere resource-only bug — which satisfies the High/Critical bar (acceptance/rejection of blocks breaks and nodes crash instead of reaching consensus).

### Likelihood Explanation
Likelihood depends on a governance parameter update reaching `Kip71GasTarget = 0`, which the code's own `FormatChecker` fails to reject (unlike the analogous `BaseFeeDenominator` check that was correctly hardened). Any governance proposal/vote flow that sets this parameter to zero — whether by misconfiguration, tooling bug, or malicious proposal — will pass validation and only fail catastrophically once applied at the next block boundary.

### Recommendation
Add an explicit nonzero check to the `Kip71GasTarget` `FormatChecker` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) in `kaiax/gov/param.go`, and additionally add a defensive zero-guard for `gasTarget` in `NextMagmaBlockBaseFee` (`params/kip71_config.go`) analogous to the existing `BaseFeeDenominator == 0` fallback, to prevent any legacy/mis-set configuration from causing a division-by-zero panic.

### Proof of Concept
1. Submit/apply a governance parameter update setting `governance.kip71gastarget = 0`; `Kip71GasTarget`'s `FormatChecker` (`noopFormatChecker`) accepts it (`kaiax/gov/param.go:324-333`).
2. Once this parameter set becomes active, at the next block whose parent used any gas (`parentGasUsed > 0 = gasTarget`), `NextMagmaBlockBaseFee` enters the "increase" branch (`params/kip71_config.go:92-109`).
3. `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` executes with `gasTarget == 0`, and `math/big.Int.Div` panics.
4. Every node computing this function (header verification, fee history RPC, etc.) panics, producing a chain-wide denial of service.
