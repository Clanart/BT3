### Title
Bull-mode MGP lock reward is computed from a manipulable spot AMM swap output, allowing an attacker to inflate `mgpAmountToLcok` via price-impact sandwiching - (File: wombat/ArbWomUp2.sol)

### Summary
`incentiveDeposit(_amount, _minMGPRec, true)` routes the BUSD reward through `_bullMGP`, which swaps BUSD for MGP via `ROUTER.swapExactTokensForTokens` and then locks `amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR` MGP into `vlMGP.lockFor` on behalf of the caller. Because `_minMGPRec` is fully attacker-controlled (can be set to `0`) and `amounts[1]` is the *actual, manipulable* on-chain swap output rather than a fixed/fair-value conversion of the BUSD reward, an attacker who can move the BUSD/MGP pool price within the same transaction (flash loan or self-sandwich) can inflate `amounts[1]` and thus receive a disproportionately large vlMGP lock for a fixed BUSD-tier entitlement.

### Finding Description
- `incentiveDeposit` computes `rewardToSend` (a BUSD amount) purely from the WOM-deposit tier tables, independent of any market price: [1](#0-0) .
- When `_bullMode` is true, `_bullMGP` performs a live AMM swap and uses its literal output `amounts[1]` — not a fair/expected conversion of `_busdAmount` — to compute the amount of MGP to lock, then applies the bonus multiplier on top of that manipulable value: [2](#0-1) .
- There is no TWAP, oracle check, or bound on acceptable slippage other than the caller-supplied `_minRec`, and the caller (attacker) chooses `_minMGPRec` themselves, so they can set it to `0` and accept any swap outcome — including one they've engineered to be unusually favorable.
- Since `swapExactTokensForTokens` reads the router's current pool reserves at execution time, an attacker who can shift the pool price immediately before this call (e.g., via a flash-loaned swap in the same transaction, since `ArbWomUp2` itself has no protection preventing composed/atomic calls) can cause `amounts[1]` to be higher than the BUSD reward is fairly worth, inflating `mgpAmountToLcok` beyond what the BUSD-tier reward is supposed to convert to.
- The extra MGP locked comes from whatever MGP balance the swap yields plus the bonus multiplier; the vlMGP/MasterMagpie system does not re-validate that the locked amount corresponds to fair USD value of the reward, so this "backing" invariant (locked vlMGP should map to the BUSD reward, not a manipulated swap rate) is broken.
- Neither `nonReentrant`, `whenNotPaused`, nor any modifier on `incentiveDeposit`/`_bullMGP` addresses this — those guards prevent reentrancy/pausing, not price manipulation of the swap used for reward conversion.

### Impact Explanation
An unprivileged attacker can obtain more locked vlMGP (and consequently a larger share of future MGP emissions distributed through MasterMagpie's staking/voting mechanics) than their WOM-deposit tier and BUSD reward entitle them to. This is a form of value extraction from the protocol's reward/incentive pool (over-issuance of vlMGP relative to backing), and can also permanently skew governance/emission-share proportions in the attacker's favor. This maps to an Immunefi "theft of unclaimed yield / protocol insolvency (partial)" impact class, since the excess MGP locked is not backed by the corresponding BUSD-equivalent value the reward-tier system intended.

### Likelihood Explanation
Exploitability depends entirely on: (1) `ArbWomUp2`/`ROUTER` using a simple constant-product AMM pool for BUSD/MGP with no oracle or TWAP safeguard, and (2) the attacker being able to move that pool's price meaningfully within a single atomic transaction (flash loan of BUSD or MGP, or existing large token holdings) and reverse it afterward. If the BUSD/MGP pool has deep liquidity or the router path uses a TWAP-resistant pricing mechanism, the achievable price impact — and therefore the attacker's gain — may be small relative to gas/slippage/arbitrage costs, making the attack only marginally profitable or unprofitable in practice. I was unable to verify from the indexed code the actual liquidity depth of the deployed BUSD/MGP pool or whether `IPancakeRouter02`/`ROUTER` points to a pool with sufficient depth to make this attack net-profitable; this must be validated on a mainnet fork before treating the impact as material.

### Recommendation
- Do not use the raw, caller-influenced swap output (`amounts[1]`) as the basis for the bonus lock amount. Instead, compute the bonus based on the known `_busdAmount` reward (i.e., multiply and use a fixed/oracle-based conversion rate, or cap `mgpAmountToLcok` using `_busdAmount` converted via a trusted price feed / TWAP), then use the router swap merely to source the MGP tokens.
- Enforce a maximum-allowed deviation between the swap's realized rate and a governance-set/TWAP-based reference rate; revert if the realized price is out of bounds regardless of `_minMGPRec` supplied by the caller.
- Consider removing the ability for the caller to fully control `_minMGPRec` (e.g. enforce a minimum computed server-side/on-chain from a fair-value oracle) so the swap itself cannot be exploited for outsized output even before the bonus multiplier is applied.

### Proof of Concept
Foundry fork test plan:
1. Fork BSC (or the relevant chain) at a block where the BUSD/MGP pancake-style pool used by `ROUTER` exists; deploy/point `ArbWomUp2` at the real `ROUTER`, `busd`, `mgp`, `vlMGP` addresses and set `bullBonusRatio` via `setup`.
2. Baseline: call `incentiveDeposit(amount, minRec=fairMinOut, true)` with the pool at its normal reserve ratio; record `mgpAmountToLcok_baseline` from the `VLMGPRewarded` event.
3. Attack: in the same transaction (via an attacker contract), flash-loan a large amount of BUSD (or MGP), swap it into the BUSD/MGP pool to shift the price so that a subsequent `busd->mgp` swap yields abnormally more MGP; then call `ArbWomUp2.incentiveDeposit(amount, 0, true)`; then swap back to restore the pool and repay the flash loan.
4. Assert `mgpAmountToLcok_attack > mgpAmountToLcok_baseline` by a material margin, and that the attacker's net cost (flash loan fee + slippage on manipulation swaps) is less than the value of the extra vlMGP received, demonstrating net profit.
5. Assert the invariant violation: the BUSD reward consumed (`rewardToSend`) is identical in both cases, but the resulting locked MGP amount differs — showing that locked vlMGP is not properly backed by the intended BUSD reward value.

    function incentiveDeposit(
        uint256 _amount, uint256 _minMGPRec, bool _bullMode
    ) external _checkAmount(_amount) whenNotPaused nonReentrant {
        if (_amount == 0) return;

        uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender);
        _deposit(_amount);
        claimedReward[msg.sender] += rewardToSend;
        
        if (_bullMode) {
            _bullMGP(rewardToSend, _minMGPRec, msg.sender);
        } else {
            IERC20(busd).transfer(msg.sender, rewardToSend);
            emit BUSDRewarded(msg.sender, rewardToSend);
        }
    }

    function _bullMGP(uint256 _busdAmount, uint256 _minRec, address _account) internal {
        IERC20(busd).safeApprove(address(ROUTER), _busdAmount);
        
        address[] memory path = new address[](2);
        path[0] = busd;
        path[1] = mgp;
        uint256[] memory amounts = ROUTER.swapExactTokensForTokens(
            _busdAmount,
            _minRec,
            path,
            address(this),
            block.timestamp
        );

        uint256 mgpAmountToLcok = amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR; // get bull mode bonus
        IERC20(mgp).approve(address(vlMGP), mgpAmountToLcok);
        vlMGP.lockFor(mgpAmountToLcok, _account);

        emit VLMGPRewarded(_account, _busdAmount, mgpAmountToLcok);
    }
