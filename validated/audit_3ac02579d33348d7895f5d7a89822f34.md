### Title
Bridge circuit never validates the payout transaction's output value/script paid to the withdrawer, allowing reimbursement without a genuine payout - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` proves that `payout_input_index` spends the correct withdrawal outpoint recorded on Citrea, but it never inspects `input.payout_spv.transaction.output` to confirm that the withdrawer actually received `output_amount` at `output_script_pubkey` for that withdrawal. Because the only Bitcoin-consensus binding between the withdrawer's key and any output is the sighash type/flag chosen when the withdrawal input was signed — a value the attacker fully controls — a colluding withdrawer/operator pair can produce a Bitcoin-valid payout transaction that consumes the recorded withdrawal UTXO but pays the withdrawer nothing, while a `bridge_circuit` proof over that transaction is still accepted and used to justify full operator reimbursement.

### Finding Description
The claimed binding is:
`value_received_by_withdrawer_address == amount_Citrea_Bridge_recorded_for_that_withdrawal`

In `circuits-lib/src/bridge_circuit/mod.rs`, after `verify_storage_proofs` returns `(user_wd_outpoint, vout, move_txid)` from the Citrea Bridge contract's storage, the circuit only checks: [1](#0-0) 

i.e. it asserts `input.payout_spv.transaction.input[payout_input_index].previous_output == (user_wd_txid, vout)`. It never reads `input.payout_spv.transaction.output` to check that any output pays the withdrawer's script pubkey the correct amount. `verify_storage_proofs` (`circuits-lib/src/bridge_circuit/storage_proof.rs`) only recovers the withdrawal outpoint/vout and move txid from EVM storage proofs — it carries no output-amount/script commitment either.

The only place in the codebase that ties a payout output to the withdrawer's recorded amount/script is the honest-path signature check in `core/src/operator.rs::withdraw` and `core/src/rpc/aggregator.rs` (optimistic payout), where the withdrawer's `taproot::Signature` must use `TapSighashType::SinglePlusAnyoneCanPay`, enforced only in `parse_withdrawal_sig_params`: [2](#0-1) 

This check exists only in the gRPC parsing layer of the *honest* operator RPC path. It is not part of the on-chain consensus rules, not re-verified by `bridge_circuit`, and not something an unprivileged withdrawer is forced to comply with when they sign their own withdrawal UTXO input directly. Nothing in Bitcoin consensus or in `bridge_circuit` prevents the withdrawal input from being signed with a sighash flag that does not commit to any output (e.g. `SIGHASH_NONE|ANYONECANPAY`), or, if `SIGHASH_SINGLE|ANYONECANPAY` is used, from placing the withdrawer's real UTXO at some index whose paired output has already been signed to be worthless while a second, unrelated, operator-funded input/output pair moves the real value to the operator.

Exploit flow:
1. A withdrawer with a valid, already-recorded Citrea withdrawal signs their withdrawal UTXO input using a sighash flag that does not bind it to a specific output value (or colludes so the "real" payout output pays them nothing) and hands this signature directly to a cooperating operator, bypassing `parse_withdrawal_sig_params`/`operator.rs::withdraw` entirely (this call path is not required — anyone can broadcast a validly-signed Bitcoin transaction).
2. The operator constructs and broadcasts a transaction with N inputs: input `payout_input_index` = the recorded withdrawal outpoint (spent per step 1), plus a second, larger input funded from the operator's own vault/change. Outputs pay the withdrawer nothing and pay an operator-controlled address the full value.
3. This transaction confirms on Bitcoin (Bitcoin consensus only requires the signature to be valid for whatever sighash flag was chosen — it does not require any particular output).
4. The operator (or, in a dispute, the operator defending a challenge) builds a `BridgeCircuitInput` with `payout_input_index` pointing at that input. `bridge_circuit` verifies SPV inclusion and `input[payout_input_index].previous_output == (user_wd_outpoint, vout)`, which both hold, and never checks the outputs, so the journal/proof is accepted.
5. The accepted journal is used by the BitVM2 disprove/assert path to justify the operator's reimbursement of `bridge_amount` from the presigned kickoff/round transaction graph, even though the withdrawer received nothing.

Existing guards do not catch this: `Verifier::is_deposit_valid`, `verify_storage_proofs`, and `SPV::verify` all check different things (deposit/withdrawal *outpoint* existence and inclusion), none of them check the payout transaction's output value/address against the Citrea-recorded amount. `Operator::is_profitable` and the sighash-type enforcement in `parse_withdrawal_sig_params` are only exercised in the cooperative, honest-operator RPC path (`core/src/operator.rs::withdraw`, `core/src/rpc/aggregator.rs`) and are trivially bypassed by directly broadcasting a hand-crafted transaction to Bitcoin.

### Impact Explanation
A colluding withdrawer/operator pair can cause the move-to-vault-funded reimbursement mechanism to pay the operator the full `bridge_amount` for a payout transaction that delivers zero (or arbitrarily little) value to the actual withdrawer. This is BTC leaving the bridge's collateral/reimbursement path without a matching fronted withdrawal — a Critical impact ("an operator reimbursed for a payout it never funded"). The attack is repeatable across any withdrawal and any operator willing to collude with a withdrawer, since nothing in `bridge_circuit` or the presigned transaction graph ties the reimbursement amount to value actually delivered to the withdrawer's address.

### Likelihood Explanation
Preconditions: a valid, Citrea-registered withdrawal (attacker-controlled, since the attacker can call `withdraw` and choose the withdrawal UTXO bytes and signature/sighash flag per the threat model), and a willing counterpart with spendable BTC to co-fund the transaction and later run the kickoff/reimbursement flow. The attacker's cost is limited to Bitcoin transaction fees; no majority hashrate, key compromise, or privileged access is required to broadcast the crafted transaction, since sighash flag choice for one's own UTXO is a normal, unprivileged Bitcoin capability explicitly granted in the threat model. The only additional requirement is a cooperating operator to actually complete the reimbursement claim, making this a collusion-based but fully reproducible protocol-level gap rather than a purely single-actor exploit.

### Recommendation
Have `bridge_circuit` (in `circuits-lib/src/bridge_circuit/mod.rs`) explicitly validate the payout transaction's output(s) against the Citrea-recorded withdrawal data: extend the storage-proof/withdrawal commitment on the Citrea Bridge contract to include the expected output script pubkey and amount, and add an assertion in `bridge_circuit` that some output of `input.payout_spv.transaction` (ideally the one paired by index with `payout_input_index`, matching the sighash-committed output) matches that script pubkey and amount exactly. Additionally, enforce/verify that the withdrawal input was spent using a sighash type that commits to that output (e.g. require and check `SinglePlusAnyoneCanPay` semantics are structurally implied by the recorded commitment), so the circuit does not rely solely on an off-chain, unenforced convention.

### Proof of Concept
`cargo test` plan (circuits-lib):
1. Build a `StorageProof`/`BridgeCircuitInput` fixture (reusing the existing `circuits-lib/src/bridge_circuit/storage_proof.rs` test fixtures/`test_data/storage_proof.bin`) that records a withdrawal outpoint/vout and a known bridge amount `X`.
2. Construct a synthetic `payout_spv.transaction` with:
   - `input[0]` = the recorded withdrawal outpoint (satisfying `previous_output` check),
   - `input[1]` = an arbitrary second input (simulating operator vault change),
   - `output[0]` = pays an operator-controlled script pubkey the full value,
   - no output paying the withdrawer's script pubkey any of amount `X` (or a zero-value withdrawer output).
3. Set `payout_input_index = 0` and run `bridge_circuit` (or directly call the storage/output-checking logic path) with a mocked/guest harness.
4. Assert (documenting the current bug) that execution succeeds and would emit a journal hash, i.e. `input[0].previous_output == (user_wd_outpoint, vout)` passes and no assertion ever checks `output_amount`/`output_script_pubkey` against `X` — proving `value_received_by_withdrawer_address (0) != amount_Citrea_Bridge_recorded_for_that_withdrawal (X)` while the circuit still accepts.
5. After applying the recommended fix (checking output value/script against the recorded commitment), assert the same fixture now causes a panic/assertion failure.
