### Title
Permissionless `compound()` sweeps any ERC20 balance held by `ManualCompound`, not just claimed rewards - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` is an unrestricted, externally callable function [1](#0-0) . For any reward token address the caller passes in `_rewards[i][j]` that is not registered as a "compoundable" reward, the function transfers the entire raw `balanceOf(address(this))` of that token to `msg.sender`, with no accounting of what was actually just claimed via `multiclaimOnBehalf` [2](#0-1) .

### Finding Description
The function first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` to pull the caller's claimable rewards into the `ManualCompound` contract [1](#0-0) . It then loops over the caller-supplied `_rewards[i][j]` token addresses and, for any token not in `compoundableRewards`, transfers out `IERC20(_rewards[i][j]).balanceOf(address(this))` in full to the caller [3](#0-2) .

Because this check uses the contract's total token balance rather than a delta/amount actually attributable to the caller's claim, any ERC20 tokens that end up sitting in the `ManualCompound` contract for any reason (e.g. accidental direct transfers, dust left over from prior partial fee/convert operations, or rounding remainders from the second loop's convertor/locker/helper calls) can be swept out by the very next unprivileged caller of `compound()`, simply by naming that token in `_rewards`. This is structurally the same bug class as the reported `claimFees` issue: a function intended only to forward "just claimed" funds instead forwards the contract's entire balance, letting an ordinary caller claim funds that were never theirs.

### Impact Explanation
Any wallet can call `compound()` and specify an arbitrary token address in `_rewards` to drain that token's full balance from `ManualCompound` to itself, as long as the token is not on the `compoundableRewards` allow-list [4](#0-3) . This is a direct theft of funds vector against any tokens (accidentally sent, leftover dust, or otherwise) held by the contract, satisfying the "direct theft of user funds" bar.

### Likelihood Explanation
`compound()` has no access control (no `onlyOwner`/`onlyCompounder` restriction on the external entry point itself) [5](#0-4) , and the attacker fully controls the `_rewards` parameter contents, making exploitation straightforward for any wallet that notices the contract holding a stray balance.

### Recommendation
Track claimed amounts explicitly (e.g., record `balanceBefore`/`balanceAfter` deltas around the `multiclaimOnBehalf` call, or have `MasterMagpie`/the rewarder report the exact amount claimed per token) and only forward that delta to the caller, instead of sweeping `IERC20(token).balanceOf(address(this))` wholesale in both the non-compoundable-reward loop and the main compounding loop.

### Proof of Concept
1. Some ERC20 token `X` (not registered via `addReward`, so `compoundableRewards[X] == false`) ends up held by `ManualCompound` — e.g. via an accidental direct `transfer` from any external actor.
2. Any wallet calls `compound(_lps, _rewards, _convertRatio, _minRec, _lockMgp)` where `_lps` contains any valid registered pool, and `_rewards[i]` includes token `X`'s address.
3. Inside the loop at [3](#0-2) , since `compoundableRewards[X]` is `false`, the code reads `IERC20(X).balanceOf(address(this))` (the entire balance, unrelated to any actual claim) and transfers it to `msg.sender`.
4. The caller receives token `X`'s full balance from the contract with no relation to rewards they actually earned.
