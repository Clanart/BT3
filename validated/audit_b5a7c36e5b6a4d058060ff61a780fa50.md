## Title
Division-by-zero panic in `consolidatedNode.Split()` can brick block finalization when a proposer's combined CN+CL stake is zero - (File: `kaiax/staking/staking_info.go`)

### Summary
The `consolidatedNode.Split()` function divides the proposer's reward between the CN (staking-only) and CL (consensus-liquidity) pools using `totalAmount = StakingAmount + CLStakingAmount` as the denominator. When this total is zero, `big.Int.Div` panics, and because this function is invoked unconditionally from `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` during `FinalizeState()` for every block's proposer, a single validator reaching a zero combined stake can crash reward distribution for the entire network on every node that processes that block — directly analogous to the reported `FeeSplitter.addFees()` bug where a `totalSupply() == 0` denominator bricks a user action, except here the blast radius is a chain-wide halt rather than a single user's transaction.

### Finding Description
`consolidatedNode.Split()` is defined as: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)  // panics if totalAmount == 0
	...
}
```

It is called for the block proposer's own reward split in `specWithProposerAndFunds` / `specWithProposerAndFundsFlex`, guarded only by `cn.CLStakingInfo != nil` — **not** by any minimum-stake check: [2](#0-1) 

By contrast, the other two call sites (`assignStakingRewards`, `assignStakingRewardsFlex`) only invoke `Split()` after confirming `cnTotalStakingAmount > minStake` (or `> threshold`), guaranteeing a strictly positive denominator: [3](#0-2) [4](#0-3) 

The proposer-path call site has no such guard. If the elected proposer for a block is a `consolidatedNode` whose `StakingAmount` (CNStaking) is `0` and whose associated `CLStakingInfo.CLStakingAmount` is also `0` (e.g., the validator fully unstaked from CNStaking while still listed in the AddressBook/committee, and the associated consensus-liquidity pool concurrently has zero staked amount), `totalAmount` becomes `0`, and `clAmount.Div(clAmount, totalAmount)` panics.

### Impact Explanation
This code path executes inside `FinalizeState()`, which runs deterministically on every full node while processing every block (not just the proposer). A panic here does not merely revert one transaction — it crashes the state-transition function that every honest node must execute, halting block finalization network-wide. This is a direct analog of the reported class ("a computed total becomes zero, bricking downstream distribution logic"), but elevated from "one user's sell reverts" to "chain-wide denial of service," since staking amounts and consensus-liquidity balances are attacker/staker-controllable through ordinary CNStaking/CLStaking withdrawal transactions — no privileged access required.

### Likelihood Explanation
Reaching `StakingAmount == 0` requires only ordinary CNStaking withdrawal by a validator operator; reaching `CLStakingAmount == 0` for the same validator's consensus-liquidity pool requires ordinary staker withdrawal from a CL pool (both are user/staker-initiated actions on public system contracts). The validator's AddressBook entry may not be immediately purged after unstaking, so a window exists where the node still participates in proposer selection with `StakingAmount = 0` and a linked `CLStakingInfo` whose `CLStakingAmount` has also drained to `0`. This can occur incidentally (uncoordinated withdrawals) or be deliberately engineered by a validator operator to time their own full CNStaking withdrawal with the CL pool's staker exodus immediately before their proposer turn.

### Recommendation
Guard `consolidatedNode.Split()` against a zero denominator, mirroring the pattern already used at the other two call sites: if `totalAmount.Sign() == 0`, short-circuit and return the full amount to the CN side (or to the proposer/burn destination per policy) instead of dividing, e.g.:
```go
if totalAmount.Sign() == 0 {
    return amount, big.NewInt(0)
}
```
Apply the same defensive check anywhere `Split()` is invoked without a pre-existing `StakingAmount > minStake` guard, i.e., in `specWithProposerAndFunds` and `specWithProposerAndFundsFlex`.

### Proof of Concept
1. A validator `V` registers `CLStakingInfo` for a consensus-liquidity pool with initial nonzero `CLStakingAmount`, and holds nonzero `StakingAmount` in CNStaking — `V` becomes/remains an eligible council member.
2. All liquidity providers withdraw from `V`'s CL pool, driving `CLStakingAmount` to `0` at the next `StakingInfo` snapshot (per the interval defined by `reward.stakingupdateinterval`).
3. `V`'s operator withdraws its entire CNStaking balance, driving `StakingAmount` to `0`, while `V` is still present in the AddressBook/committee for the current staking interval.
4. `V` is selected as proposer for a subsequent block (Prague/KIP-226 rules active, i.e., `istanbul.policy == 2`, `reward.deferredtxfee = true`).
5. During `FinalizeState()`, `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` calls `cn.Split(proposer)` for `V`'s consolidated node; `totalAmount = 0 + 0 = 0`, and `big.Int.Div` panics, crashing state-transition processing for that block on every node.
