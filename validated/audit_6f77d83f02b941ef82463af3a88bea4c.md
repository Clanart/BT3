### Title
Unchecked subtraction in mempool fee calculation can raise an unhandled exception on a minting spend bundle - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle` computes the fee of an incoming spend bundle as `fees = uint64(removal_amount - addition_amount)` without first checking that `removal_amount >= addition_amount`. This is the same bug class as the reported `BurnContract.burn()` underflow: a subtraction that can go negative is fed directly into an unsigned/bounded type constructor with no `require`/explicit check and no dedicated error path, relying implicitly on the subtraction never producing a negative value.

There is no prior guard equivalent to the one used at block-validation time. Compare this to `chia/consensus/block_body_validation.py`, where the exact same computation is explicitly guarded: [4](#0-3) 

The block-level code checks `if removed < added: return Err.MINTING_COIN` *before* subtracting, and only then asserts `fees >= 0`. The mempool-level code has no analogous check anywhere in `validate_spend_bundle` before line 814 — a full review of the function body from the peak check through the fee computation shows no `MINTING_COIN`-equivalent guard [5](#0-4) .

Because a spend bundle submitter fully controls the puzzle reveal/solution for the coins they spend, they can trivially construct a puzzle that emits a `CREATE_COIN` condition for an amount greater than the coin's own value (there is no consensus rule preventing a coin's *puzzle* from emitting such a condition — this is precisely what the `MINTING_COIN` check at block-validation time is designed to catch). Submitting such a spend bundle directly to the mempool causes `addition_amount > removal_amount`, so `removal_amount - addition_amount` is negative, and `uint64(...)` on a negative value is expected to raise (uint64 is a bounded unsigned integer type from `chia_rs.sized_ints`).

### Impact Explanation
An attacker-crafted spend bundle that "mints" coins can throw an unhandled exception inside `validate_spend_bundle`, which is called from `add_spend_bundle` on the transaction-admission path used for every incoming spend bundle (from peers or a local wallet/RPC submitter). If this exception is not caught by an outer handler in this call chain, it results in a spend-triggered failure of transaction processing for that bundle (and potentially for the async task/coroutine handling it), which qualifies as a spend-triggered transaction-processing disruption rather than the intended, clean rejection (`Err.MINTING_COIN`/`FAILED` status) that the equivalent block-level code path produces.

### Likelihood Explanation
Any unprivileged spend-bundle submitter can construct this input: it only requires spending a coin they own with a custom puzzle that unconditionally creates an over-large `CREATE_COIN` output. No cooperation from other peers, farmers, or timelords is needed, and no signature bypass is required (AGG_SIG is independent of coin value). This makes the bug trivially and repeatably reachable from the standard mempool-admission entry point.

### Recommendation
Mirror the guard used in `chia/consensus/block_body_validation.py`: before computing `fees = uint64(removal_amount - addition_amount)` in `chia/full_node/mempool_manager.py`, explicitly check `if removal_amount < addition_amount: return Err.MINTING_COIN, None, []` (or an equivalent dedicated error), so that minting spend bundles are cleanly rejected with a proper error code instead of relying on the implicit behavior of the `uint64` constructor on a negative subtraction result.

### Proof of Concept
1. Select an owned, unspent coin `C` with amount `X` and a custom puzzle `P` such that `P(solution)` returns `[[CREATE_COIN, some_ph, X + 1]]` (no other value-consuming conditions).
2. Build a `SpendBundle` spending `C` with `P`/`solution` (with a valid, or even absent/ACS, signature requirement depending on `P`).
3. Submit the spend bundle to the node (e.g., via `respond_transaction`/RPC `push_tx`), which routes to `MempoolManager.add_spend_bundle` → `validate_spend_bundle`.
4. Since `addition_amount = X + 1 > removal_amount = X`, the line `fees = uint64(removal_amount - addition_amount)` at `chia/full_node/mempool_manager.py:814` attempts to construct `uint64(-1)`, which raises, instead of returning the intended `Err.MINTING_COIN` failure path used at block-validation time. [6](#0-5) 

Note: I could not fully trace, within the available search budget, whether every caller in the chain from the peer message handler down to `add_spend_bundle` wraps this call in a broad try/except that would fully absorb the exception without any denial-of-service effect; this is the main remaining uncertainty in assessing exact blast radius, and would benefit from direct execution/testing in a Devin session to confirm the runtime behavior (exception type raised by `uint64(negative)` and how far it propagates).

        spend_name, and the current mempool. The mempool should

        Args:
            new_spend: spend bundle to validate

            Optional[MempoolItem]: the item to add (to mempool or pending pool)

        if self.peak is None:

        assert len(new_spend.coin_spends) == len(spend_conditions)

        bundle_coin_spends: dict[bytes32, BundleCoinSpend] = {}

            # if this coin_id isn't found, the SpendBundle doesn't match the

            if not is_clvm_canonical(bytes(coin_spend.puzzle_reveal)) or not is_clvm_canonical(
                bytes(coin_spend.solution)

                return Err.INVALID_COIN_SOLUTION, None, []

            lineage_info = None
            if bool(spend_conds.flags & ELIGIBLE_FOR_FF) and supports_fast_forward(coin_spend):
                # Make sure the fast forward spend still has a version that is
                # still unspent, because if the singleton has been spent in a
                # non-FF spend, this fast forward spend will never become valid.
                # So treat this as a normal spend, which requires the exact coin

                    # spend can never be fast forwarded onto it. Fall back to
                    # treating it as a normal spend.

                spend_additions.append(child_coin)

        for coin_id, spend_data in bundle_coin_spends.items():
            if spend_data.latest_singleton_lineage is None:
                non_ff_spend_ids.add(coin_id)
                effective_spend_id = coin_id
            else:
                effective_spend_id = spend_data.latest_singleton_lineage.coin_id
            # Fast forward spends are only allowed to be spent once in a spend bundle
            if effective_spend_id in effective_spend_ids:
                return Err.INVALID_SPEND_BUNDLE, None, []
            effective_spend_ids.add(effective_spend_id)

        # spends in order to evict an FF spend, it must be associated with a
        # normal spend that can be included in a block or invalidated some
        # other way.
        if len(non_ff_spend_ids) == 0:
            return Err.INVALID_SPEND_BUNDLE, None, []

        removal_amount: int = 0
        removal_records = await get_coin_records(removal_names)
        for record in removal_records:
            removal_record_dict[record.coin.name()] = record

        for name in removal_names:

                return Err.UNKNOWN_UNSPENT, None, []
            if name in additions_dict:

                # The timestamp and block-height of this coin being spent needs
                # to be consistent with what we use to check time-lock
                # conditions (below). All spends (including ephemeral coins) are
                # spent simultaneously. Ephemeral coins with an

                removal_record = CoinRecord(
                    removal_coin,
                    uint32(self.peak.height + 1),
                    uint32(0),
                    False,
                    self.peak.timestamp,
                )
                removal_record_dict[name] = removal_record
            else:
                removal_record = removal_record_dict[name]
            removal_amount += removal_record.coin.amount
