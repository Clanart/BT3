This confirms the vulnerability. The codebase already has an established mitigation pattern for exactly this class of bug — `resolveWithin` in `app/src/lib/path.ts`, which resolves symlinks via `realpath` and rejects any path that escapes the root [1](#0-0) , and it's used in `buildConflictContext` specifically to "Guard against path traversal and symlink escapes" for repository-relative conflict file paths [2](#0-1) . `getWorkingDirectoryImage`, however, does not use this helper.

### Title
Working-directory image diff reads files outside the repository via symlinked path components (missing `resolveWithin` check) - (File: app/src/lib/git/diff.ts)

### Summary
`getWorkingDirectoryImage` joins `repository.path` with the attacker-influenced `file.path` from a working-directory status entry and passes the result directly to `readFile`, without any containment check against the repository root.

### Finding Description
`getWorkingDirectoryImage` computes `Path.join(repository.path, file.path)` and reads it with `readFile` [3](#0-2) . `file.path` originates from git status parsing of the working tree and is repository-relative, but `Path.join`/`readFile` do not resolve symlinks before deciding what to read — Node's `fs.readFile` follows symlinks transparently. If the attacker-controlled repository content (e.g. a cloned/fetched repo) contains a symlink as an intermediate path component or as the leaf itself, pointing outside the repository (e.g. `evil-dir -> /etc` or `image.png -> /home/user/.ssh/id_rsa`), the resolved real path escapes `repository.path` even though `file.path` itself contains no `..` traversal segments.

This function is reached from `getImageDiff`, which is invoked when rendering an image diff for a working-directory file with an image extension and non-`Deleted`/non-`Conflicted` status [4](#0-3) , i.e., simply by the user viewing the "Changes" diff for a new/modified image file in a repository that was cloned or fetched from an attacker-controlled remote.

The codebase already recognizes this exact risk pattern and has a fix for it: `resolveWithin` normalizes the path, resolves it and the root via `realpath` (following symlinks), and returns `null` if the real resolved path is not under the real root [1](#0-0) . This helper is explicitly used elsewhere in the codebase to guard file reads of repository-relative, attacker-influenced paths against "path traversal and symlink escapes" [5](#0-4) . `getWorkingDirectoryImage` lacks this check entirely, and no other code path enforces it before the `readFile` call at line 930.

### Impact Explanation
An attacker who controls the content of a repository the victim clones/fetches (or who can influence the working tree, e.g. via a malicious submodule or archive extraction that creates a symlink) can cause Desktop to read and base64-encode arbitrary files reachable from the process's file permissions, then render them as an "image" inside the diff view. This discloses local file contents (potentially credentials, SSH keys, other repos, etc.) to whoever can observe the rendered UI — and if the diff/image is subsequently shared, exported, or included in generated context (e.g. Copilot conflict prompts, error reports), the disclosure could propagate further.

### Likelihood Explanation
Requires the victim to open Desktop's changes/diff view for a file with an image extension inside a repository whose working tree contains an attacker-planted symlink; this is a realistic scenario after cloning a malicious repo, checking out an attacker's branch, or updating a compromised submodule — no unusual user action beyond normal repository browsing is needed. Symlink creation in a git working tree from a clone is standard git behavior (git supports symlink blobs), so the attacker does not need any special local privileges.

### Recommendation
In `getWorkingDirectoryImage`, resolve `file.path` against `repository.path` using `resolveWithin` (as already done in `buildConflictContext`) before calling `readFile`, and treat a `null` result (or a thrown error from `realpath`) as a fatal condition rather than falling through to reading the resolved path. The same containment check should be applied anywhere else in `diff.ts` (and related code) that joins `repository.path` with untrusted `file.path`/`oldPath` values sourced from git status or diff output.

### Proof of Concept
1. Attacker publishes a repository containing, as a tracked or untracked file, a symlink `img.png -> ../../../../etc/passwd` (or on the victim's machine, a symlink pointing to a sensitive absolute path such as the user's SSH private key), plus a real `img.png`-adjacent parent directory symlink escape as an alternative technique (e.g. a tracked symlinked directory `assets -> /Users/victim/.ssh`, containing a file with an image-like extension, e.g. `assets/id_rsa.png`).
2. Victim clones the repository with GitHub Desktop.
3. Victim opens the Changes view; the new/untracked file `assets/id_rsa.png` (or similar) is listed with an image extension, so `getImageDiff` calls `getWorkingDirectoryImage(repository, file)`.
4. `Path.join(repository.path, file.path)` resolves through the symlink to the target outside the repository; `readFile` reads it and the contents are base64-encoded and rendered as an `<img>` data URI in the diff pane, disclosing file contents that the "image" preview should never have exposed.

export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
