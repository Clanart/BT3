### Title
Unbounded allocation when deserializing `ReceivedOutput` via `TxOut::consensus_decode` — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` reads an attacker-controlled Bitcoin `TxOut` using rust-bitcoin's `consensus_decode`, with no size limit applied to the serialized `script_pubkey`. A hostile length prefix (VarInt) causes the decoder to allocate memory proportional to the claimed length before any actual bytes are available, enabling a remote unprivileged party to force an arbitrarily large allocation and abort the process. This is the direct analog of CVE-2023-24603 (missing size limit on downloaded/ingested data) in Serai's own code.

### Finding Description
In `ReceivedOutput::read`, the `output` field is populated via `TxOut::consensus_decode` on a `BufReader` with capacity `0` wrapping the caller-provided reader [1](#0-0) . `TxOut` serialization is `amount (8 bytes) || VarInt(script_len) || script`. rust-bitcoin's consensus decoding of the script allocates a `Vec` sized by the decoded `VarInt` before reading the payload, so a `VarInt` claiming e.g. `u32::MAX`/`u64`-scale length triggers a multi-gigabyte allocation (or immediate allocation abort) with only a handful of real input bytes. Neither `ReceivedOutput::read` nor its callers impose a maximum on the `TxOut` length — contrast with the explicit `TRANSACTION_SIZE_LIMIT` check used for `DkgCommitments` deserialization elsewhere in the codebase [2](#0-1)  and the `MAX_LIBP2P_REQRES_MESSAGE_SIZE` bound on p2p frames [3](#0-2) , showing the codebase otherwise enforces such limits and this path lacks one.

Reachability: `ReceivedOutput::read` is explicitly among the deserialization sinks reachable with untrusted bytes (it is invoked when processor/scanning artifacts — e.g. `Plan`/output records — are deserialized, and `Plan::read` iterates a `u32` count of `N::Output::read` which bottoms out in `ReceivedOutput::read` for Bitcoin [4](#0-3) [5](#0-4) ). A malformed length field anywhere in that byte stream triggers the oversized allocation before the reader's actual content is consulted.

### Impact Explanation
A single small crafted input (on the order of ~20 bytes: 32-byte scalar + 8-byte amount + max VarInt) causes the node to attempt an allocation of up to ~4 GiB (or `u64`-scale if the VarInt permits), resulting in OOM kill or abort of the signing/processor process. Repeated deliveries yield a persistent denial of service against threshold signing — availability loss equivalent to the Medium severity class of the reference CVE (CVSS 6.5, A:H). No secret leakage is required for the impact.

### Likelihood Explanation
The sink is a public deserialization API explicitly designated as reachable with untrusted bytes; triggering it requires no authentication, stake, or collusion — only a length-prefixed byte string. The allocation happens before content validation, so the attack cost is negligible and reliably repeatable.

### Recommendation
Bound the script size before consensus decoding: either length-prefix `TxOut` with a sanity-checked `u16`/`u32` (as done for `SignData` pieces capped at `u16::MAX` [6](#0-5) ), or wrap the reader in `io::Read::take(MAX_SCRIPT_SIZE)` and reject if decoding needs more. A bound on the order of Bitcoin's consensus standardness limits (e.g. 10 KB) is far above any legitimate P2TR script.

### Proof of Concept
```rust
use std::io::Cursor;
// Secp256k1 scalar (offset) = 0x01 serialized, then TxOut:
// amount = 0 (8 bytes LE), script VarInt = 0xffffffff (claims ~4 GiB script)
let mut bytes = vec![0u8; 32];
bytes[0] = 1; // valid scalar repr for read_F
bytes.extend_from_slice(&0u64.to_le_bytes());       // TxOut.amount
bytes.extend_from_slice(&[0xff]);                    // VarInt marker for u32
bytes.extend_from_slice(&u32::MAX.to_le_bytes());    // claimed script length
// ReceivedOutput::read(&mut Cursor::new(bytes)) -> TxOut::consensus_decode
// allocates vec![0; u32::MAX] before reading => OOM/abort with <50 input bytes
```
The same payload embedded in a `Plan`'s inputs (after a nonzero `u32` input count [7](#0-6) ) reaches it through `Plan::read` → `Output::read` → `ReceivedOutput::read`.

Note: the exact allocation behavior depends on the rust-bitcoin version pinned (older `consensus_decode` implementations pre-allocate to the claimed VarInt length; newer versions may grow incrementally, in which case the bound is still missing but realized memory is capped by bytes actually delivered — either way the missing size check on the read path stands).
