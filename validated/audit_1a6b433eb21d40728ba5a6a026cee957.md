### Title
`get_payout_txs_for_withdrawal_utxos` joins on `(txid, vout)` with no uniqueness guarantee, letting one Bitcoin spend credit multiple withdrawal indices - ([File: core/src/database/verifier.rs])

### Summary
`bitcoin_syncer_spent_utxos` is keyed by `(block_id, spending_txid, txid, vout)` and records a spend event for an outpoint with no back-reference to a specific `withdrawals.idx`. `Database::get_payout_txs_for_withdrawal_utxos` re-derives the idx by joining on `(bsu.txid, bsu.vout) = (w.withdrawal_utxo_txid, w.withdrawal_utxo_vout)`, so if two `withdrawals` rows are ever populated with the same `withdrawal_utxo_txid/vout`, a single real Bitcoin spend of that outpoint is reported as a payout for every matching idx.

### Finding Description
Binding claimed to hold: for a given `(txid, vout)` spend recorded in `bitcoin_syncer_spent_utxos`, `{ idx : withdrawals.withdrawal_utxo_txid = txid ∧ withdrawals.withdrawal_utxo_vout = vout }` has cardinality ≤ 1.

Code path:
- `bitcoin_syncer_spent_utxos` schema: primary key `(block_id, spending_txid, txid, vout)`, no reference to `withdrawals.idx` [1](#0-0) .
- `Database::insert_spent_utxo` inserts one row per spent outpoint per block with no linkage to any withdrawal record [2](#0-1) .
- `withdrawal_utxo_txid`/`withdrawal_utxo_vout` per `idx` is set by `update_withdrawal_utxo_from_citrea_withdrawal`, driven purely by whatever bytes the Citrea contract reports for that `idx` via `collect_withdrawal_utxos`, with no uniqueness check against other `idx` values in this repo [3](#0-2) [4](#0-3) .
- `get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` solely on `(txid, vout)`, filtered by `block_id`, and returns every matching `idx`: [5](#0-4) .
- The verifier's block-processing pipeline feeds this result directly into `update_payout_txs_and_payer_operator_xonly_pk`, writing the same `payout_txid` and `payout_payer_operator_xonly_pk` into every returned idx's row [6](#0-5) .
- Reimbursement eligibility for an operator is later looked up per-idx via `get_first_unhandled_payout_by_operator_xonly_pk`, which reads exactly `payout_txid`/`payout_payer_operator_xonly_pk` set above [7](#0-6) .

Exploit flow: An unprivileged user (per the threat model) calls Citrea's `withdraw` twice, choosing the identical outpoint bytes as the `input_outpoint`/withdrawal UTXO for two distinct withdrawal indices idx1 and idx2. Nothing inside this repository detects or blocks the duplicate — `update_withdrawal_utxo_from_citrea_withdrawal` blindly writes whatever the contract returns, per idx, with no uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in `withdrawals`. When an operator later actually funds and broadcasts a real payout for idx1 (spending that shared outpoint once), the bitcoin syncer records a single spend event. `get_payout_txs_for_withdrawal_utxos` then returns `[(idx1, payout_txid), (idx2, payout_txid)]` because both idx rows match the outpoint, and both get the same `payout_txid` and the operator's xonly pk written into their `withdrawals` row — even though the operator never funded a payout for idx2.

Existing guards that fail: `Operator::is_profitable` and deposit/withdraw validation logic all operate off the `withdrawals` table state, which has already been silently corrupted at this point; no DB uniqueness constraint exists on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, and the join key itself has no idx back-reference to disambiguate.

### Impact Explanation
An operator can be credited with a valid, unhandled payout entry (`payout_txid`, `payout_payer_operator_xonly_pk`) for a withdrawal idx it never funded, enabling it to later claim reimbursement (kickoff/collateral payout) for that idx — an operator reimbursed for a payout it never funded. This is repeatable per attacker-chosen duplicate outpoint and is not bound to a single deposit; it silently corrupts the reimbursement bookkeeping keyed by `idx` for any pair of withdrawals sharing a UTXO, blast radius scaling with however many withdrawal indices the attacker chooses to alias to the same outpoint.

### Likelihood Explanation
Requires only the ability to call Citrea's `withdraw` twice with attacker-chosen identical outpoint bytes (explicitly within the stated attacker capabilities) and requires no verifier/operator/aggregator privilege, no key compromise, and no majority hashrate. Whether Citrea's Bridge contract itself deduplicates `withdrawalUTXOs` bytes across indices is outside this repository and could not be verified here; if the contract does enforce such uniqueness, this specific attack path is not reachable, but the underlying DB-layer/join design flaw (no uniqueness constraint, join keyed only on `(txid,vout)`) is independently demonstrable purely at the database layer as requested in the proof idea, without needing a live Citrea node.

### Recommendation
Add a uniqueness constraint on `withdrawals(withdrawal_utxo_txid, withdrawal_utxo_vout)` (or reject/flag duplicate registrations when populating this table from Citrea data), and change `get_payout_txs_for_withdrawal_utxos`'s join to also require the spend event maps to exactly one withdrawal idx (e.g., via a unique constraint plus explicit `HAVING COUNT(*) = 1` per outpoint, or by storing a direct idx reference on the spent-utxo write path rather than re-deriving via `(txid, vout)`).

### Proof of Concept
`cargo test` in `core/src/database/verifier.rs`:
1. Insert one block via `insert_block_info`, `insert_txid_to_block` for a `spending_txid`.
2. Call `insert_spent_utxo(dbtx, block_id, &spending_txid, &shared_utxo.txid, shared_utxo.vout)` once.
3. Call `upsert_move_to_vault_txid_from_citrea_deposit` and `update_withdrawal_utxo_from_citrea_withdrawal` for `idx1` with `shared_utxo`.
4. Repeat step 3 for `idx2` with the same `shared_utxo`.
5. Call `get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id)`.
6. Assert `result.len() == 2` and both `idx1` and `idx2` appear mapped to the same `spending_txid`, proving the one-spend-to-many-idx join behavior against the claimed one-to-one binding.

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }

    async fn collect_withdrawal_utxos(
        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let withdrawal_utxo = self
                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;
