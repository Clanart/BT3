## Title
Governance-settable `GasTarget = 0` causes a division-by-zero panic in KIP-71 base fee calculation, halting block processing on every node - (File: `params/kip71_config.go`)

## Summary

## Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the next block's base fee based on governance-controlled parameters `GasTarget`, `BaseFeeDenominator`, `LowerBoundBaseFee`, and `UpperBoundBaseFee`. The function explicitly guards against `BaseFeeDenominator == 0` ("To avoid panic, set the fluctuation range small") but performs **no equivalent guard for `GasTarget == 0`**: [1](#0-0) 

When `parentGasUsed > gasTarget` (true for any nonzero `parentGasUsed` if `gasTarget == 0`), the code divides by `gasTarget` directly: [2](#0-1) 

`x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0` triggers a Go `big.Int` "division by zero" runtime panic (the same class of bug as the referenced report's Solidity `division or modulo by zero`, mapped here to `panicReasons[0x12]` handling elsewhere in the codebase, confirming this exact error class is recognized in the codebase: [3](#0-2) ).

Crucially, the governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, i.e., **no validation preventing zero**, unlike the sibling parameter `Kip71BaseFeeDenominator` which explicitly rejects zero: [4](#0-3) 

Any governance proposal/vote that sets `kip71.gastarget` to `0` will be accepted by the format checker, get applied to the chain config, and then be used unconditionally by every node computing the next block's base fee in `NextMagmaBlockBaseFee`, which is invoked during header verification (`VerifyMagmaHeader`) and fee history processing (`node/cn/gasprice/feehistory.go`) for every single block once the Magma fork is active.

## Impact Explanation
Once a `GasTarget = 0` governance change takes effect, **every node** on the network that verifies or builds the next block (i.e., every honest full node, CN, and RPC node computing `NextMagmaBlockBaseFee`) will panic identically on `parentGasUsed > 0`, which is the case as soon as a single transaction is included in the parent block. This is a network-wide, deterministic crash of block processing (`VerifyMagmaHeader`) — effectively halting the chain, since no honest node can produce or validate a subsequent block without hitting the same panic. This is not merely a resource-exhaustion or local-node issue; it is a consensus-critical parameter path that all Kaia nodes execute identically for block validation, so its impact meets the required threshold of causing state divergence / consensus failure across honest nodes.

## Likelihood Explanation
`kip71.gastarget` is a normal, voteable governance parameter (see `Kip71GasTarget` in `kaiax/gov/param.go`) reachable via the standard governance voting mechanism (single or DAO governance mode). No format check rejects zero, unlike its sibling `BaseFeeDenominator`. Any party with governance voting rights (e.g., governing node in single mode, or the DAO in the on-chain governance mode) can propose and enact `GasTarget = 0`, triggering the panic at the very next Magma-forked block.

## Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `v == 0`, matching the existing check for `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should apply the same zero-fallback protection to `GasTarget` that it already applies to `BaseFeeDenominator`, to prevent a panic even if a zero value reaches this function through any other path (e.g., stale/legacy chain config, genesis misconfiguration).

## Proof of Concept
1. Via governance voting (single mode: governing node casts the vote; DAO mode: proposal passes), set `kip71.gastarget` to `0`. The vote is accepted because `Kip71GasTarget.FormatChecker` is `noopFormatChecker` and always returns `true`.
2. Once the parameter takes effect at block N, any subsequent block N+1 with `parentGasUsed > 0` (i.e., contains at least one transaction) causes every node calling `NextMagmaBlockBaseFee(header.Number, parentBaseFee, parentGasUsed)` — from `VerifyMagmaHeader` during block validation — to execute:
   - `parentGasUsed(min(gasUsed, upperGasLimit)) > gasTarget(0)` → true
   - `gasUsedDelta := parentGasUsed - 0`
   - `x := parentBaseFee * gasUsedDelta`
   - `y := x.Div(x, big.NewInt(0))` → **panic: division by zero**
3. All nodes computing this (proposers building blocks and validators verifying them) panic simultaneously, halting chain progress network-wide.
