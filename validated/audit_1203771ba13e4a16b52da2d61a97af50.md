## Analysis

The external report's bug class — a security check (`inputValidatorMiddleware`) wired into some route groups but silently missing from others that carry the same class of untrusted input — has a direct, provable analog in Hyperbridge's **bandwidth accounting gate**, not in an off-repo Hono service.

### Title
Bandwidth Gate Only Enforced on `on_accept` (POST requests) — `on_response` (GET responses) Never Debits Bandwidth - (File: `parachain/runtimes/nexus/src/ismp.rs`, `parachain/runtimes/gargantua/src/ismp.rs`)

### Summary
Both the Nexus and Gargantua `ProxyModule::on_accept` implementations invoke `pallet_bandwidth::BandwidthGate::try_consume` to debit a `(source, app)` bandwidth subscription before dispatching a POST request to its destination module. The sibling `on_response` implementation, which delivers GET-response payloads through the exact same router and to the exact same class of destination modules, never calls `try_consume` at all — despite the Gargantua code carrying a comment claiming it does ("Bandwidth gate. Mirrors the request path in `on_accept`").

### Finding Description
In `parachain/runtimes/gargantua/src/ismp.rs`, `on_accept` gates dispatch: [1](#0-0) 

`on_response` in the same file carries a comment describing a bandwidth gate but contains no `try_consume` call whatsoever — it only checks the destination chain and routes to the callback: [2](#0-1) 

The same asymmetry exists in `parachain/runtimes/nexus/src/ismp.rs`: `on_accept` calls `try_consume`, but `on_response` does not: [3](#0-2) 

`pallet_bandwidth::Pallet::<T>` itself confirms this is by design of the pallet's own `IsmpModule` implementation: `on_accept` decodes and processes purchase messages, but `on_response` simply returns an error and never touches `Allowance` storage: [4](#0-3) 

The only place `try_consume`/`BandwidthGate` is invoked anywhere in the codebase is inside the two runtimes' `on_accept` paths (confirmed by `grep` — no other call site of `try_consume` exists outside `gargantua/src/ismp.rs`, `nexus/src/ismp.rs`, and the pallet's own trait implementation). GET responses carry an arbitrary-size `values: Vec<StorageValue>` payload that is dispatched to destination modules identically to how POST request bodies are, yet no byte-size accounting or debit ever occurs for that path.

### Impact Explanation
The bandwidth pallet's model is: `(chain, app)` pairs prepay for byte-throughput via `BandwidthManager.sol` purchases, and the gate is supposed to be "the hook the runtime's ISMP router consults for every message" per the pallet's own module doc: [5](#0-4) 

Because `try_consume` is never called on the response path, any app/chain pair can receive unlimited-size GET-response traffic without ever depleting or even touching its bandwidth subscription — completely bypassing the accounting invariant that "bandwidth balances must move exactly once and only to the rightful beneficiary and amount." This is a logic/accounting-integrity break in a metered resource that the protocol explicitly monetizes (subscriptions purchased via `BandwidthManager.sol`), reachable by any unprivileged party who can cause a GET request/response round-trip to be delivered to a Nexus/Gargantua-hosted app.

### Likelihood Explanation
High likelihood: no privileged role, relayer collusion, or malformed proof is required. Any account can dispatch a GET request from an app it controls (paying nothing extra beyond the normal request), have the counterparty state machine answer it, and the response — regardless of payload size — is delivered through `on_response` with zero bandwidth debit, every single time, deterministically, because the code path structurally omits the `try_consume` call rather than merely mis-computing it under an edge case.

### Recommendation
Add a `try_consume` (or equivalent explicit byte-size gate) call inside `on_response` in both `parachain/runtimes/gargantua/src/ismp.rs` and `parachain/runtimes/nexus/src/ismp.rs`, mirroring the `on_accept` logic (compute payload size via an appropriate encode/size function for `GetResponse`, skip only for pallet-internal/allowlisted flows), so that response delivery is metered the same as request delivery. Remove or correct the misleading "mirrors the request path" comment until the gate is actually implemented.

### Proof of Concept
1. Register a `BandwidthManager` for chain `A` and purchase a small tier for `(chain A, app X)` via the normal purchase flow (`on_accept` handles `PurchaseMessage`, debiting nothing extra here).
2. From `app X` on chain `A`, dispatch a `GET` request to a remote chain.
3. Have the remote chain answer with a `GetResponse` carrying an arbitrarily large `values` payload.
4. Deliver the response through the standard ISMP response handler; the router calls `ProxyModule::on_response`, which checks only `dest_chain` and forwards to the destination module's `on_response` — `pallet_bandwidth::BandwidthGate::try_consume` is never invoked (confirmed absent in `on_response` bodies in both `parachain/runtimes/gargantua/src/ismp.rs:424-441` and `parachain/runtimes/nexus/src/ismp.rs:412-418`).
5. Repeat step 2-4 indefinitely: `Allowance::<T>` for `(A, X)` is never decremented for response traffic, regardless of how many or how large the responses are, permanently bypassing the protocol's bandwidth-purchase monetization for all response-side traffic.

		// Bandwidth gate. Mirrors the request path in `on_accept`: the chain
