## Analysis

The external report's core broken invariant: two components disagree on what a shared "membership list" must contain, and the actual deployed configuration only satisfies one side — so the check that's supposed to gate value release silently fails open (or closed) instead of reverting on unregistered/untrusted state.

The local analog is in the Tron build of `IntentGatewayV2`. There are two different implementations of essentially the same "resolve peer gateway for a chain" function across the codebase, and they disagree on unknown-chain behavior:

**Main EVM contract** (`evm/src/apps/intentsv2/IntentsBase.sol`) reverts when a chain isn't registered: [1](#0-0) 

**Tron contract** (`evm/tron/contracts/apps/IntentGatewayV2.sol`) silently falls back to `address(this)`: [2](#0-1) 

This `instance()` function is the sole gate used by `authenticate()`, which in turn is the only check protecting fund-releasing `RedeemEscrow`/`RefundEscrow` handling in `onAccept`: [3](#0-2) 

The gateway is deployed with an address that's identical across chains by design (deterministic CREATE2, documented explicitly for the peer-registration flow): [4](#0-3) 

### Title
Unregistered-chain fallback in `instance()` lets `authenticate()` accept forged settlement messages from any unregistered peer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.instance()` on Tron returns `address(this)` instead of reverting when a state machine has no registered gateway. Since the gateway's own address is deterministic and identical across every chain it's deployed to (by design, for peer bootstrapping), `authenticate()` — the only defense on `RedeemEscrow`/`RefundEscrow` — will accept a `PostRequest` whose `from` equals that shared deterministic address for *any* `source` chain that has not yet had `NewDeployment` applied to it, because both sides of the `instance(source) != module` comparison resolve to the same self-address.

### Finding Description
`authenticate()` is designed to ensure incoming settlement messages originate only from a gateway explicitly registered as a trusted peer for the claimed source chain: [5](#0-4) 

The security property this relies on is: an unregistered chain must be rejected. But `instance()` implements the opposite behavior — instead of reverting for an unregistered `stateMachineId`, it returns `address(this)`: [6](#0-5) 

Because the contract is deployed with the same address on every chain (a property the protocol relies on and documents elsewhere to avoid carrying peer addresses in init data), `request.from` decoded from a message dispatched by *any* copy of this same contract on *any* chain will also equal `address(this)`. So for any `source` chain the target gateway hasn't yet called `add_deployment`/`NewDeployment` for, `instance(source)` resolves to the local self-address, `module` (derived from `request.from`) also resolves to the same self-address, and the check `instance(request.source) != module` passes — even though the source chain was never trusted.

This directly mirrors the KeroseneManager contradiction: one code path needs a registry to reject unlisted entries, another silently treats "not listed" as "trusted", and the deployed configuration guarantees the mismatch is reachable (new chains are added to Hyperbridge/ISMP routing before every existing gateway's `_instances` map is updated for that pair — the same "deployment script only wires part of the picture" gap called out in the seed report).

### Impact Explanation
An attacker who can get a `PostRequest` accepted by Hyperbridge's routing from *some* chain not yet registered as a peer on the target `IntentGatewayV2` (e.g. a newly supported chain, or any chain where the peer registration lags real deployments — which the codebase's own governance flow makes routine, since `add_deployment` is called incrementally per pair) can trigger `_authenticate` to pass and reach `_withdraw`, releasing escrowed input tokens (`RedeemEscrow`) or refunding to an attacker-chosen `beneficiary` field inside a forged `WithdrawalRequest` (`RefundEscrow`) — unauthorized transaction execution and fund loss/wrong-beneficiary payout on escrowed order inputs.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin — only an unprivileged actor able to dispatch a message from a chain currently unregistered as a peer on the specific target gateway, which is an expected, routine state during phased chain rollout (the same operational gap the external report flags: deployment scripts/configuration steps land asynchronously across contracts).

### Recommendation
Make `instance()` revert on an unregistered `stateMachineId` (matching `IntentsBase._instance` in the main EVM contracts) rather than defaulting to `address(this)`, so `authenticate()` fails closed for any chain that hasn't been explicitly onboarded via `NewDeployment`/`add_deployment`.

### Proof of Concept
1. Deploy/observe that `IntentGatewayV2` (Tron variant) exists at the same address `G` on chain `A` (registered, real escrow) and is never explicitly registered as a peer for chain `B` on chain `A`'s `_instances` map (`_instances[keccak256(B)] == address(0)`).
2. From chain `B` (any chain Hyperbridge routes for, where the same bytecode/address `G` is deployed, e.g. via the same CREATE2 factory), have `G` on `B` dispatch a `PostRequest` with `from = G`, `source = B`, `to = G`, `body = [RedeemEscrow, WithdrawalRequest{commitment: <existing order's commitment on A>, tokens: <its escrowed tokens>, beneficiary: attacker}]`.
3. On chain `A`, `onAccept` calls `authenticate()`: `module = address(bytes20(request.from)) = G`; `instance(B)` on `A` returns `address(this) = G` (fallback, since `B` unregistered) → check passes.
4. `_withdraw` executes, transferring `A`'s escrowed tokens to the attacker-controlled `beneficiary`. [7](#0-6)

        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
