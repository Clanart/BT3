### Title
Path traversal via commit/PR-diff file paths in `revealInFileManager` bypasses the repo's own `resolveWithin` containment guard - (File: app/src/lib/app-shell.ts)

### Summary
`revealInFileManager` joins an attacker-influenced `file.path` string (taken from a commit's or PR's diff/tree listing) directly onto the repository root with `Path.join`, with no containment check. This is inconsistent with the rest of the codebase, which treats file paths that originate from untrusted repository/API content as dangerous and explicitly re-validates them with `resolveWithin` before touching the filesystem (e.g. `openRepositoryFromUrl`'s `filepath` handling and the Copilot conflict-resolution writer).

### Finding Description
`revealInFileManager` is defined as: [1](#0-0) 

It performs `Path.join(repository.path, path)` and passes the result straight to `shell.showItemInFolder`, without ever calling `resolveWithin` (the project's own path-containment primitive defined in `app/src/lib/path.ts`) [2](#0-1) .

This function is invoked with `file.path` values coming from `CommittedFileChange` objects built from a specific commit's or pull request's diff (i.e., from repository content that a remote/fork owner controls), for example in:
- The commit history file-context menu: [3](#0-2) 
- The "Open PR from Desktop" files-changed view: [4](#0-3) 

Notably, both call sites first check `pathExists(Path.join(repository.path, file.path))` to decide whether to enable the menu item, but that existence check does not stop `Path.join` from resolving `..` segments to a location outside the repo if it *does* happen to exist on disk (e.g. a crafted relative path such as `../../.ssh/known_hosts` that exists on the victim's machine) — `pathExists` and `Path.join` here provide no traversal containment, they only check whether *some* resolved path (possibly outside the repo) exists.

This is directly comparable to a pattern the codebase has *already recognized and fixed* elsewhere:
- `openRepositoryFromUrl` explicitly rejects absolute paths and calls `resolveWithin(repository.path, filepath)` before calling `shell.showItemInFolder`, logging and refusing when the path escapes the repo root: [5](#0-4) 
- The Copilot conflict-resolution file writer does the same before calling `writeFile`: [6](#0-5) 

`revealInFileManager` is the one filesystem-facing sink in this family that never received the equivalent `resolveWithin` guard, even though its own JSDoc explicitly warns "Do not use this method with non-validated paths" in the neighboring `IAppShell` interface comment [7](#0-6) .

### Impact Explanation
An attacker who controls a repository, fork, or pull request that a victim opens or reviews in Desktop can supply commit content whose recorded file path contains directory-traversal segments. When the victim views that commit/PR in the History or "Open PR" file list and selects "Show in Finder/Explorer" (or "Open in external editor"/"Open with default program", which route through the same unguarded `Path.join`), Desktop will reveal or open a file outside the repository's working directory. This is a file-read/disclosure primitive outside the intended repo sandbox and directly matches the "file write or read outside the repo" impact class the task calls for. The severity is bounded by whether the OS/git object model actually permits such path strings to survive into a diff/log entry, which is uncertain (see Likelihood).

### Likelihood Explanation
Likelihood is moderate-to-uncertain rather than confirmed. Modern Git enforces `verify_path()`/fsck checks against `..`-containing tree entries during checkout and index operations, which is why ordinary working-directory `git status` entries (parsed in `app/src/lib/status-parser.ts`) cannot realistically contain traversal segments — those paths correspond to files git has already safely checked out. However, `CommittedFileChange` paths shown in History/PR views are derived from `git log`/`git diff --raw`/`--numstat` output for commits that are **not necessarily checked out** (e.g., a fork's PR head that has only been fetched, not checked out into the working tree). Whether Git's raw/numstat diff machinery applies the same `..`-rejection to path strings it merely *prints* (as opposed to paths it *writes to disk*) was not something I could confirm from the indexed source (`app/src/lib/git/log.ts`'s `parseRawLogWithNumstat` content was not available in the index). This is the key open question: if Git's diff/log output can surface such a path string for an unchecked-out commit, the guard gap in `revealInFileManager` becomes directly exploitable; if Git's object-store/fsck layer always blocks such tree entries regardless of context, this finding is a defense-in-depth gap rather than a directly reachable bug.

### Recommendation
Route `revealInFileManager` (and the equivalent `Path.join(repository.path, path)` call sites in `pull-request-files-changed.tsx`'s `onOpenFile`, `filter-changes-list.tsx`, and `app.tsx`'s `onOpenInExternalEditor`) through `resolveWithin`/`resolveWithinPosix`, mirroring the pattern already used in `dispatcher.ts`'s `openRepositoryFromUrl` and `app-store.ts`'s Copilot conflict resolution, and refuse the action (with a log message) when the resolved path escapes the repository root. Additionally, verify (or add a regression test similar to `app/test/unit/status-parser-test.ts`) confirming whether `git log --numstat`/`git diff --raw` can ever emit a path containing `..` for a fetched-but-not-checked-out commit, to determine whether this is directly reachable or defense-in-depth only.

### Proof of Concept
Not independently reproducible from the indexed source alone, because confirming exploitability requires demonstrating that a crafted commit/tree object can produce a `..`-containing path in `git log --numstat`/`git diff --raw` output without ever passing through git's checkout-time path validation. Conceptually:
1. Attacker creates a fork/PR whose head commit's tree contains a blob recorded under a path such as `../../../../.ssh/known_hosts` (requires confirming Git's low-level plumbing permits writing such a tree entry and that `git diff --raw`/`--numstat` prints it verbatim for an unchecked-out ref).
2. Victim opens the PR in Desktop's "Open PR from Desktop" view (`pull-request-files-changed.tsx`), which lists files via `CommittedFileChange` built from that diff.
3. Victim right-clicks the file and selects "Show in Finder"/"Show in Explorer", invoking `revealInFileManager(repository, file.path)` [4](#0-3) .
4. `Path.join(repository.path, file.path)` resolves outside the repo, and `shell.showItemInFolder` reveals/opens the out-of-repo file, with no `resolveWithin` check to stop it, unlike the equivalent deep-link and Copilot-resolution code paths.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
