### Title
Rewards distributed during zero-total-supply periods in `WomUp` are permanently lost - (File: `wombat/WomUp.sol`)

### Summary
`WomUp.sol` implements a Synthetix-style linear reward-streaming mechanism (`rewardRate`/`rewardPerTokenStored`/`lastUpdateTime`) for MGP rewards distributed to `mWom` stakers. The `updateReward` modifier always advances `lastUpdateTime` to `lastTimeRewardApplicable()` regardless of whether `_totalSupply` is zero, while `rewardPerToken()` skips accruing anything when `totalSupply() == 0`. Any elapsed reward-emission time that occurs while nobody is staked is silently discarded and can never be claimed by anyone, permanently trapping the corresponding MGP tokens in the contract.

### Finding Description
The reward accounting lives in `rewardPerToken()` and the `updateReward` modifier: [1](#0-0) 

- `rewardPerToken()` explicitly returns the stale `rewardPerTokenStored` unchanged when `totalSupply() == 0`, meaning no rewards are credited to `rewardPerTokenStored` for any elapsed time during that window.
- However, `updateReward(account)` unconditionally sets `lastUpdateTime = lastTimeRewardApplicable()` on every call, including calls made while `_totalSupply == 0`.

Because `lastUpdateTime` is the anchor used by `rewardPerToken()` to compute `(lastTimeRewardApplicable() - lastUpdateTime) * rewardRate`, once `lastUpdateTime` is forced forward past a zero-supply interval, that interval's `rewardRate`-denominated MGP emission is permanently skipped — it is neither credited to any staker nor recoverable by anyone afterward.

This can be reached with an ordinary sequence of unprivileged transactions:
1. Owner calls `initializeRewards()` to start the 7-day stream — no requirement that anyone has already staked. [2](#0-1) 
2. If no user calls `stake()` immediately, `_totalSupply` stays 0. Any subsequent call that hits the `updateReward` modifier (e.g., the very first user calling `stake()`) fast-forwards `lastUpdateTime`, discarding all the reward stream time elapsed before that first deposit. [3](#0-2) 
3. Equally, mid-stream, if all stakers fully withdraw via `withdraw()`/`migrate()` (which is a purely user-driven, unprivileged action reducing `_totalSupply` to 0), any window until the next `stake()`/`getReward()` call similarly loses the emitted rewards for that duration. [4](#0-3) 

The MGP earmarked for that skipped interval remains stuck in the `WomUp` contract with no owner-claim mechanism: `rescueReward()` can only run before the stream starts (`rewardRate == 0` check), so once `initializeRewards()` has fired it can never be used to recover the lost tokens. [5](#0-4) 

### Impact Explanation
Reward tokens (MGP, ultimately intended to be locked into `vlMGP` for stakers) corresponding to any zero-total-supply interval become permanently unclaimable and irrecoverable — no user can claim them (they were never counted into anyone's `earned()`), and the owner cannot reclaim them either since `rescueReward()` is gated by `rewardRate == 0`. This is a permanent freeze of unclaimed yield/protocol funds, reachable purely through unprivileged user actions (deposit timing, or full withdrawal causing a temporary zero-supply gap).

### Likelihood Explanation
This does not require any malicious actor — it can occur through entirely ordinary usage: the reward stream can be initialized before the first depositor arrives, or all depositors can withdraw/migrate at some point during the 7-day period, both of which are normal, permissionless flows. Given no special conditions or race timing precision is needed (any nonzero gap suffices), the likelihood of this occurring in practice is high.

### Recommendation
Mirror the pattern already used correctly elsewhere in this codebase (e.g. `BaseRewardPool._provisionReward`, `vlMGPBaseRewarder`, `mWOMSVBaseRewarder`), where rewards issued while `totalStaked() == 0` are queued (`queuedRewards`) and only folded into `rewardPerTokenStored` once a nonzero supply exists again, instead of being silently dropped. For `WomUp.sol`, either:
- Only advance `lastUpdateTime` when `totalSupply() > 0` (skip the update while zero-supply, leaving `lastUpdateTime` as-is so the elapsed emission is preserved rather than discarded), or
- Track and queue the reward amount accrued during zero-supply windows and inject it back into the stream once staking resumes, and/or allow the owner to reclaim MGP corresponding to any provably undistributed zero-supply interval.

### Proof of Concept
1. Owner funds `WomUp` with MGP and calls `initializeRewards()`, setting `rewardRate = balance / 7 days`, `lastUpdateTime = block.timestamp`, `periodFinish = block.timestamp + 7 days`. `_totalSupply` is 0 (no one has staked yet).
2. 2 days pass with no calls to the contract (`_totalSupply` still 0).
3. User A calls `stake(amount)`. The `updateReward(msg.sender)` modifier runs: `rewardPerToken()` sees `totalSupply() == 0` and returns the stale `rewardPerTokenStored` (0), so `rewardPerTokenStored` stays 0; then `lastUpdateTime` is set to `block.timestamp` (i.e., day 2), permanently skipping the 2 days worth of `rewardRate` emission — those tokens are never credited to `rewardPerTokenStored` for any subsequent staker.
4. Over the remaining 5 days, only 5/7 of the funded MGP is ever distributable via `earned()`; the 2/7 portion remains stuck as an ERC20 balance in `WomUp` with no function able to withdraw it (`rescueReward()` requires `rewardRate == 0`, which is no longer true).

    function rewardPerToken() public view returns (uint256) {
        if (totalSupply() == 0) {
            return rewardPerTokenStored;
        }
        return
            rewardPerTokenStored + (
                (lastTimeRewardApplicable() - (lastUpdateTime)) * rewardRate * (1e18) / (totalSupply())
            );
    }

    function initializeRewards() external onlyOwner returns (bool) {
        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();

        rewardRate = rewardsAvailable / (duration);

        lastUpdateTime = block.timestamp;
        periodFinish = block.timestamp + (duration);

        emit RewardAdded(rewardsAvailable);

        return true;
