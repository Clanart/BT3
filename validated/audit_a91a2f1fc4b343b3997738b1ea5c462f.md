## Title
Missing predecessor/state check in `_applyCopilotConflictResolutions()` allows stale, unverified content to be written and staged for commit — ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions()` writes AI-generated conflict-resolution content to disk and stages it when the user clicks "Continue Merge." Like the reported `executeEmergencyAction()`, it acts on previously computed state (`copilotResolutions`) without re-validating that the *predecessor* condition — that the repository is still in the same conflict/merge state for which those resolutions were computed — still holds at execution time.

### Finding Description
The function reads `copilotResolutions` from `multiCommitOperationState` and immediately writes each resolution's `resolvedContent` to disk and `git add`s it: [1](#0-0) 

It gates on `manualResolutions` only when `step.kind === MultiCommitOperationStepKind.ShowCopilotConflicts`, but otherwise defaults to an empty map — it never actually asserts that the current step, or the underlying git conflict state, corresponds to the merge for which `copilotResolutions` were generated: [2](#0-1) 

The only "freshness" check performed is a check for *manually and completely resolved* files (no remaining conflict markers) — it does not check whether the on-disk file still belongs to the same conflict/commit context the resolution was computed for, nor does it verify `MERGE_HEAD`/`isCherryPickHeadFound`/`REBASE_HEAD` state is unchanged since resolution generation: [3](#0-2) 

This mirrors the reported bug class exactly: `copilotResolutions` (analogous to a scheduled "action") is applied without checking that its "predecessor" — the specific conflict context that was live when the AI resolution was requested — is still the one currently in effect. The comment at line 7074 even states resolutions are stored and "NOT written to disk yet," which explicitly defers execution to a later click, creating the same time-of-check/time-of-use gap that the report describes for `executeEmergencyAction`.

By contrast, Desktop's own git-level continuation operations for rebase/cherry-pick do check their session predecessor before continuing (e.g. `continueCherryPick` calls `isCherryPickHeadFound()` and `continueRebase` calls `readRebaseHead()` before proceeding): [4](#0-3) [5](#0-4) 
`_applyCopilotConflictResolutions` has no equivalent guard verifying the multi-commit-operation/conflict session is still the one the resolutions were derived from.

### Impact Explanation
If the underlying conflict/merge session changes between when Copilot generates resolutions and when the user clicks "Continue Merge" (e.g. the multi-commit operation is aborted and a different operation with same file paths is started, or paths shift across operations), stale AI-generated content — potentially derived from attacker-authored (prompt-injection) content in the merged branches — could be written to files and staged silently, without git ever confirming those resolutions still correspond to a real, current conflict. This is a "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories, since the write bypasses the normal git conflict-resolution invariant that written content must match currently-conflicted paths in the active merge session.

### Likelihood Explanation
This requires the user to be using the Copilot conflict resolution feature and for the repository/session state to change during the window between resolution generation and confirmation (feasible given the async Copilot request, abort-and-restart affordances, and multi-step navigation such as `ConfirmAbort` visible in the surrounding code). It does not require local/admin access, prior malware, or leaked credentials — only an attacker-controlled repository whose conflicting content/prompt influences the AI's resolution and normal UI navigation by the victim.

### Recommendation
Before writing/staging any `copilotResolutions`, re-verify the "predecessor" condition: confirm the repository's current conflict state (`MERGE_HEAD`/`REBASE_HEAD`/`CHERRY_PICK_HEAD` as appropriate, or a stored session identifier) still matches the one active when the resolutions were generated, and reject/re-derive resolutions if it does not — mirroring the `isCherryPickHeadFound`/`readRebaseHead` guards used elsewhere in the git operation flow.

### Proof of Concept
1. Attacker crafts a branch whose merge conflict content contains prompt-injection text designed to manipulate the Copilot resolution engine's output for a given path.
2. Victim merges/cherry-picks the attacker branch; conflicts are detected and Copilot resolution is requested, storing `copilotResolutions` in `multiCommitOperationState` per lines 7076-7089.
3. While the async resolution is pending or displayed, the victim navigates away (e.g., `ConfirmAbort` flow) or the underlying session state changes without the stored `copilotResolutions` being invalidated.
4. Victim clicks "Continue Merge"; `_applyCopilotConflictResolutions` (lines 7169-7269) writes the stale/attacker-influenced content to the matching path and stages it via `git add`, without ever re-validating that the current git conflict session matches the one for which the resolution was generated.
5. The corrupted content is committed and pushed by the victim, believing it reflects legitimate conflict resolution.

**Uncertainty note:** I could not fully trace how `multiCommitOperationState`/`step` transitions are invalidated across abort/restart flows (e.g., whether some other code path clears `copilotResolutions` on session change) since that logic spans UI dialog components (`copilot-conflicts-dialog.tsx`, `base-multi-commit-operation.tsx`) not fully retrieved in this session. A full confirmation of exploitability would require tracing all callers/dispatchers of `_applyCopilotConflictResolutions` and the state-reset logic for `copilotResolutions` across every abort/step transition — I'd recommend a Devin session with full repo access to verify this end-to-end if a definitive PoC is required.
