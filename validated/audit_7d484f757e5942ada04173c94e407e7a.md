## Title
Missing Timestamp/Deadline Check in App Proxy Signature Verification Allows Indefinite Replay of Forged Signed Requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates only that the HMAC signature over the query parameters matches, but it never checks the `timestamp` query parameter (which Shopify includes in every App Proxy request specifically to allow staleness detection) against the current time. [1](#0-0) 

### Finding Description
Shopify signs every App Proxy request forwarded to the app with a `signature` computed over the full query string, including a `timestamp` parameter that records when Shopify generated the proxied request. `verify_proxy_request` only calls `query_string_valid?`, which recomputes the HMAC and does a `secure_compare` against the supplied signature — there is no check that `timestamp` (or any other freshness marker) is within an acceptable window. [2](#0-1) [3](#0-2) 

Because the signature is a deterministic function purely of the query parameters and the shared secret, any App Proxy URL (including its `signature` and `timestamp`) that is ever captured — via browser history, logs, proxies, referrer headers, or network capture — remains a validly "signed" request forever. This is functionally the same class of bug as the reported GluexRouter issue: a timestamp/deadline value is present specifically to bound validity, but the code path that authorizes the operation never checks it, so an action intended to be time-bound can be executed (or replayed) at any point in the future.

The test suite confirms this design gap: fixed, hardcoded old timestamps (e.g. `"timestamp": "1466106083"`, from 2016) are accepted as valid signed requests without any freshness check. [4](#0-3) 

### Impact Explanation
Any controller that includes `ShopifyApp::AppProxyVerification` (e.g. the generated `AppProxyController`) treats a valid signature as proof the request currently originates from Shopify's App Proxy layer. [5](#0-4) 
Shopify forwards storefront-context parameters through the App Proxy query string (such as `shop`, `path_prefix`, and, when a customer is logged in, `logged_in_customer_id`), all covered by the same signature. If any such signed URL is captured once, it can be replayed indefinitely to re-invoke the app-proxy endpoint under that same "authenticated" context (e.g. as a specific shop or logged-in customer), because there is nothing in the code to reject stale signatures. This is a cross-shop/cross-user forged-request-acceptance issue: an attacker who obtains one historical signed request (not requiring any secret) can resubmit it at will, long after the original request's legitimate time window.

### Likelihood Explanation
Exploitation only requires access to one previously-issued App Proxy URL (via logs, browser history/cache, referrer leakage, shared links, or a compromised intermediary) — no knowledge of `ShopifyApp.configuration.secret` is needed. Since there is no expiry enforcement anywhere in `verify_proxy_request` / `query_string_valid?`, replay works at any time in the future, making this readily exploitable once a single valid URL has leaked.

### Recommendation
Add an explicit freshness check on the `timestamp` parameter in `query_string_valid?`/`verify_proxy_request`, rejecting requests whose `timestamp` is older than a configurable threshold (e.g. a few minutes), mirroring the "deadline passed" style check recommended in the analog report:

```diff
 def verify_proxy_request
-  head(:forbidden) unless query_string_valid?(request.query_string)
+  head(:forbidden) unless query_string_valid?(request.query_string) && timestamp_fresh?(request.query_string)
 end
```

### Proof of Concept
1. Capture any legitimate App Proxy request URL sent to an app (e.g. from server logs), including its `timestamp` and `signature` query parameters.
2. At any later time (minutes, days, or years later), replay the exact same query string against the app's App Proxy endpoint.
3. `query_string_valid?` recomputes the same HMAC over the same parameters and returns `true`, since the signature is deterministic and no timestamp-freshness check exists, as shown by the passing test using a 2016-era `timestamp` value. [4](#0-3) 
4. The controller proceeds as if this were a fresh, legitimate request from Shopify.

```ruby
    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
```

```ruby
    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
