### Title
Attacker-controlled `n`/`t` in `ThresholdKeys::read` triggers quadratic Lagrange interpolation work (CPU exhaustion DoS) - (File: crypto/dkg/src/lib.rs)

### Summary
The rsync bug class — an attacker-supplied numeric parameter driving disproportionate, uncapped resource consumption while passing the existing sanity checks — maps onto `ThresholdKeys::<C>::read`. The serialized format lets an untrusted byte stream choose `t` and `n` up to `u16::MAX`; when the interpolation tag is `1` (`Lagrange`), `ThresholdKeys::new` computes the group key by evaluating `interpolation_factor` for each of `t` participants, and each evaluation is itself an `O(t)` loop of field multiplications plus an inversion. The result is `O(t²)` field operations — ≈4.3·10⁹ scalar multiplications and ≈65 535 field inversions for `t = n = 65535` — from a serialized input of only ~2 MB, with no bound on `t`/`n` other than `t <= n`.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s from the reader [1](#0-0) , then selects `Interpolation::Lagrange` on tag `1` without reading any per-participant coefficient data [2](#0-1) . It then reads `n` group elements and calls `ThresholdKeys::new` [3](#0-2) . `ThresholdParams::new` only enforces `t != 0`, `n != 0`, `t <= n`, `i <= n` — no magnitude cap [4](#0-3) . `ThresholdKeys::new` then builds `t = 1..=t` and computes `group_key` as a sum of `verification_shares[i] * interpolation_factor(i, &t)` [5](#0-4) . `Interpolation::Lagrange::interpolation_factor` performs a full loop over `included` (length `t`) of field multiplications and a field inversion per call [6](#0-5) , making `new` cost `O(t²)` multiplications plus `t` inversions.

The same quadratic behavior is reachable a second time via `ThresholdKeys::view`, which calls `interpolation_factor` once per `included` member over the full `included` list [7](#0-6) , so every subsequent `view` over a large `included` set repeats the `O(n²)` work — and deserialization of such keys is one of the sanctioned untrusted-byte entry points (`ThresholdKeys::read`).

By contrast, other length-prefixed readers in scope are proportional to input size or fail fast at EOF: `SchnorrAggregate::read` loops a `u32` count but performs a fixed-size `read_G` per element, so a truncated stream errors on the first missing point with no pre-allocation [8](#0-7) , and `Commitments::read` iterates `params.t()` which is local configuration, not attacker-controlled [9](#0-8) . The `ThresholdKeys` path is the outlier where the byte stream itself sets the work factor.

### Impact Explanation
A single serialized `ThresholdKeys` blob of ~2 MB (65 535 compressed points) can pin a CPU core for an extended period inside `ThresholdKeys::new`'s Lagrange evaluation (~4.3·10⁹ field multiplications plus 65 535 inversions). If this read is invoked on bytes received over a channel where the attacker can cause a processor/coordinator to deserialize keys (e.g., re-share/promotion flows that route serialized `ThresholdKeys` through `read`), an unprivileged party can stall the victim's processing loop — a medium-severity availability loss analogous to the reference DoS.

### Likelihood Explanation
Likelihood hinges on deployment: `ThresholdKeys::read` must be reachable on untrusted bytes (the scan rules admit it as such an entry point, e.g., key material passed through recover/promote flows). `t`/`n` are raw `u16`s, so hitting the maximum requires only setting four bytes and supplying `n` valid point encodings — trivial to construct. The cost is deterministic and single-shot; no race or special position is needed. Note the amplification is bounded (worst case fixed at `u16::MAX`), keeping this at Medium rather than High.

### Recommendation
- Enforce a hard protocol-level maximum for `t`/`n` (e.g., the deployment's real validator bound) inside `ThresholdKeys::read`/`ThresholdParams::new` rather than allowing the full `u16` range.
- Alternatively, compute the group key with an `O(t)` aggregate evaluation (e.g., evaluate the committed polynomial via the verification-share sum using incremental product trees / prefix-suffix products) so deserialization cost stays linear in input size.
- Reject `Interpolation::Lagrange` blobs whose `t` exceeds the expected participant bound before performing interpolation.

```rust
// Conceptual PoC against Ristretto keys.
// Layout per ThresholdKeys::write (crypto/dkg/src/lib.rs:538-562):
//   u32 ID_len || C::ID || u16 t || u16 n || u16 i || u8 interp || F secret || n * G
let mut buf = vec![];
buf.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(&u16::MAX.to_le_bytes()); // t = 65535
buf.extend(&u16::MAX.to_le_bytes()); // n = 65535
buf.extend(&1u16.to_le_bytes());     // i = 1
buf.push(1);                         // Interpolation::Lagrange -> no coefficient data needed
buf.extend(Scalar::ONE.to_repr());   // secret_share
for _ in 0..u16::MAX {
    buf.extend((Ristretto::generator() * Scalar::ONE).to_bytes()); // verification shares
}
// O(t^2) work happens inside ThresholdKeys::new during this call:
let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
// ~4.3e9 field muls + 65535 inversions for a ~2 MB input.
```

Uncertainty: I did not fully trace which production call site feeds purely attacker-controlled bytes into `ThresholdKeys::read`; the reachability claim rests on the scan rules designating `ThresholdKeys::read` as an accepted untrusted-bytes entry point. If in practice it is only called on locally stored keys, the practical exploitability drops and this reduces to a hardening issue in the deserializer.
