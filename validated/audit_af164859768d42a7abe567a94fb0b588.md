### Title
`SignableTransaction::new` uses a hardcoded dust threshold of 546 sats regardless of the actual output's serialized size — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The analog of the oracle's hardcoded `/100` scaling is `pub const DUST: u64 = 546` in `SignableTransaction::new`. Just as the Hubble code assumed a fixed 8-decimal feed instead of querying the real parameter, `SignableTransaction::new` assumes a fixed dust boundary instead of computing it from the actual `script_pubkey` size of each output it creates. The result is a transaction construction that passes all local validation yet produces an output Bitcoin Core's `IsDust` policy rejects as dust, yielding a signed transaction that cannot be relayed.

### Finding Description
Bitcoin Core's dust rule is not a constant: `IsDust` multiplies `dustRelayFee` by `(GetSerializeSize(txout) + spend_input_size)`, so the true minimum value scales with the destination script's size and type. The code acknowledges this and deliberately collapses it into one number:

```rust
// networks/bitcoin/src/wallet/send.rs:27-32
// https://github.com/bitcoin/bitcoin/blob/.../src/policy/policy.cpp#L26-L63
// As the above notes, a lower amount may not be considered dust if contained in a SegWit output
// This doesn't bother with delineation due to how marginal these values are...
pub const DUST: u64 = 546;
```

`SignableTransaction::new` then applies this single constant to arbitrary caller-supplied `payments: &[(ScriptBuf, u64)]`:

```rust
// networks/bitcoin/src/wallet/send.rs:165-169
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

The `ScriptBuf` is fully attacker-influenced in the upstream flow (a withdrawal/burn specifies the destination address/script). 546 sats is only sufficient for small outputs; for a payment to a large `script_pubkey` — e.g. a bare script, or any non-Taproot spend template whose `(output_size + input_size) * 3 sat/vB` exceeds 546 — a payment of 546 sats or slightly more is below the real dust floor. The same constant is reused for the change-output check at `send.rs:229`, which is safe only because change is a fixed-size P2TR script.

`calculate_weight_vbytes` then builds the transaction, `needed_fee`/balance checks pass, `multisig()` produces FROST signature machines over each input, and the validators sign a transaction that default Bitcoin policy will never relay or mine.

### Impact Explanation
Once signed, the transaction is a validly authorized spend of the multisig's inputs but is non-standard and unbroadcastable. The scheduled plan consumes the payments and the key holds inputs it can no longer spend via that plan without manual recovery; the recipient never receives spendable funds despite the signature being produced. This is directly analogous to the oracle returning a price in the wrong units: the code validates against a constant that does not reflect the actual domain parameter, so it approves a value that the real system (mempool policy vs. price consumers) rejects.

### Likelihood Explanation
Reachable by an unprivileged user: they choose the destination script and amount of a payment. Constructing a payment with amount in `[546, actual_dust_threshold)` requires only a `script_pubkey` large enough that `3 sat/vB * (txout_size + ~180)` exceeds 546, which is roughly an extra ~60+ bytes of script — entirely plausible for non-P2TR destinations. No malicious validator, collusion, or leaked key is needed.

### Recommendation
Compute the dust bound per output rather than per constant: use `bitcoin`'s dust-check helpers (or replicate `IsDust`) over the actual `TxOut { value, script_pubkey }` being created — including the change output — instead of comparing `amount`/`value` against the flat `DUST` constant. If a conservative fixed bound is kept for simplicity, it must be sized for the maximum accepted `script_pubkey` length, and `script_pubkey` length should itself be bounded.

### Proof of Concept
1. An external user submits a payment instruction whose destination resolves to a `ScriptBuf` of ~100+ bytes (e.g., a bare `OP_CHECKMULTISIG`-style or hash-locked script) and an amount of `600` sats.
2. `SignableTransaction::new` executes `send.rs:165-169`: `600 >= 546`, so `DustPayment` is not raised. Weight/fee/balance checks pass and `Ok(SignableTransaction)` is returned.
3. `SignableTransaction::multisig` (`send.rs:273-285`) creates `AlgorithmMachine`s and the threshold validators produce a valid transaction containing the 600-sat output.
4. Under Bitcoin Core's `IsDust` (`3 * (output_serialized_size + spend_template_size)` at the default `dustRelayFee`), the output's true dust floor exceeds 600 sats, so `testmempoolaccept`/`sendrawtransaction` rejects it as `dust`. The multisig signed a spend that can never confirm.

Caveat: severity hinges on whether integrators ever route attacker-chosen non-Taproot scripts through `SignableTransaction::new`; for a pure-P2TR-only caller the constant is conservative and this degrades to a hardening issue.
