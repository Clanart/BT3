## Analog Found: Missing Sufficiency Check Before Escrow Decrement in `IntentGatewayV2.withdraw`

### Title
Escrow withdrawal only checks non-zero balance, not sufficiency, before subtracting — underflow-revert bricks legitimate redeem/refund paths - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The seed report's core defect is a comparison guard that checks the wrong condition before an arithmetic subtraction on a value that tracks "how much has already been consumed against a cap" — allowing the subsequent subtraction to underflow and revert instead of being caught by an explicit sufficiency check. The same defect class exists in Hyperbridge's intent-settlement escrow accounting.

### Finding Description
In `withdraw()` (Tron `IntentGatewayV2`), the guard before decrementing per-token escrow is: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
        _orders[body.commitment][token] -= amount;
        ...
    }
```

Exactly like the vesting bug's `claimedAmount < newAmount` check (which should have been `claimedAmount > newAmount`), this guard tests the wrong invariant: it verifies the escrow slot is merely *non-zero*, not that it is **≥ `amount`**. The equivalent, corrected guard used elsewhere in the codebase for the same operation still has the identical gap — the mainline `IntentsBase._withdraw` also only checks `escrowed == 0` before computing `escrowed - amount`: [2](#0-1) 

Because Solidity ≥0.8 arithmetic is checked, any call path where `body.tokens[i].amount` exceeds the live `_orders[commitment][token]` balance causes the whole `withdraw`/`_withdraw` call to revert on underflow rather than failing with a clear, catchable error — mirroring the vesting bug's "wrong comparison → underflow → always reverts" failure mode.

### Impact Explanation
`withdraw` is the function invoked from `onAccept` for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user cancellation refund) cross-chain messages, and from `onGetResponse` for source-chain cancellation: [3](#0-2) [4](#0-3) 

If the amount carried in the `WithdrawalRequest` ever diverges from the escrow slot's true balance (e.g. due to a partial-fill/full-fill sequencing edge case, a stale/duplicated redeem message, or a message replay after escrow has already been partially drained), the redeem or refund reverts on arithmetic underflow instead of failing gracefully. Because ISMP `RedeemEscrow`/`RefundEscrow` are typically one-shot dispatches tied to a specific commitment, a persistent revert here can permanently strand the escrowed user/solver funds in the contract with no code path left to release them — a fund-lock outcome, not merely a DoS.

### Likelihood Explanation
I could not fully verify the `authenticate()` gating logic in the Tron contract (the tool budget was exhausted before I could read its body), so I cannot confirm whether an unprivileged relayer/attacker can craft an arbitrary `WithdrawalRequest.tokens[i].amount` value that diverges from the true escrow balance, or whether `amount` is always derived server-side to exactly match `_orders[...]`. In the honest same-chain partial-fill flow (`IntrinsicIntents._fillSameChain`), the escrow amount passed to `_withdraw` is computed proportionally and should stay within bounds. The residual risk is in the cross-chain path where the withdrawal amount is decoded from a message body rather than recomputed locally — if any duplicate delivery, retry, or double dispatch of a `RedeemEscrow`/`RefundEscrow` message occurs (e.g., a source-chain GET response landing after a POST-based redeem already drained the same commitment), the second call's `amount` would no longer match the reduced escrow, triggering the underflow revert and stranding whatever remains.

### Recommendation
Replace the existence check with a sufficiency check in both `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) and `_withdraw()` (`evm/src/apps/intentsv2/IntentsBase.sol`):
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed < amount) revert UnknownOrder(); // or a new InsufficientEscrow error
_orders[body.commitment][token] = escrowed - amount;
```
This converts the failure into a clean, auditable revert reason rather than a silent underflow-panic, and — more importantly — makes it possible to add idempotency/replay handling around double-delivered redeem/refund messages instead of letting funds become permanently unwithdrawable.

### Proof of Concept
Conceptual repro (requires confirming reachability of a divergent `amount` via the message-authentication path, which I was unable to fully verify given tool budget):
1. Place a cross-chain order that escrows `X` tokens under `commitment`.
2. Trigger a first `RedeemEscrow`/`RefundEscrow` delivery that withdraws the full `X` (escrow now `0`).
3. Deliver a second message for the same `commitment` (duplicate/retry/race with a GET-response-based cancellation) carrying a non-zero `amount`.
4. `_orders[commitment][token] == 0` check fails via `revert UnknownOrder()` in the current code for `amount == escrowed == 0` case — but if the first withdrawal was partial (escrow `> 0`, `< amount`), the `== 0` guard passes and `escrowed - amount` underflows, reverting the transaction and leaving the remaining escrow permanently stuck since no further redeem/refund message will be dispatched for an already-`_filled` commitment.
