### Title
Missing fractional-digit-count validation causes silent integer overflow / mis-scaled `nanos` in `TimeUtil::FromString(Duration)` - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
`TimeUtil::FromString` for `google::protobuf::Duration` parses a string such as `"1.123456789012s"` by splitting it into `seconds_part` and `nanos_part` and then scaling the fractional digits up to 9-digit nanosecond precision via `nanos = nanos * Pow(10, 9 - nanos_part.length())` [1](#0-0) . There is no check that `nanos_part.length() <= 9` before this scaling, and the helper `Pow` returns `1` for negative exponents rather than performing a division, so any input with more than 9 fractional digits silently escapes correct scaling and is later truncated via a raw `int32_t` cast [2](#0-1) [3](#0-2) .

### Finding Description
The invariant that fails here is the same one described in the external report: a scaling/normalization step is applied assuming a single fixed precision (there, 18 decimals; here, 9 nanosecond digits), and when the actual precision differs, the "scaling factor" ends up being wrong (there, an unnecessary division; here, a `Pow(10, negative)` call that degenerates to identity instead of dividing), causing the calculated numeric value to be corrupted rather than correctly represented.

Specifically:
- `nanos_part` is derived directly from the client-controlled string after the last `.` and before the trailing `s`, with no upper bound on its length [4](#0-3) .
- `nanos = std::strtoll(nanos_part.c_str(), &end, 10)` parses the entire fractional string as an integer, which for a many-digit string can be an arbitrarily large `int64_t` value (bounded only by 64-bit overflow behavior of `strtoll`, i.e. clamped to `LLONG_MAX`) [5](#0-4) .
- The scaling step `nanos = nanos * Pow(10, static_cast<int>(9 - nanos_part.length()))` is meant to left-pad the digits to full nanosecond precision when there are fewer than 9 digits (e.g., `"1.5s"` → `nanos_part="5"`, exponent `8`, correctly scaled to `500000000`). When `nanos_part.length() > 9`, the exponent becomes negative; `Pow` is a simple `for (i = 0; i < y; ++i) result *= x;` loop that never executes for negative `y`, returning `1` [2](#0-1) . The code needed to *divide* by `10^(len-9)` (truncate excess digits) but instead multiplies by `1`, leaving `nanos` as the raw over-long integer.
- That raw value is then narrowed with `static_cast<int32_t>(nanos)`, which is implementation-defined/undefined-behavior-adjacent truncation that can wrap into an arbitrary, unrelated 32-bit value [3](#0-2) .
- `IsDurationValid` only range-checks `nanos` against `[-999999999, 999999999]` [6](#0-5) ; it has no way to detect that the value was derived from a corrupted/truncated intermediate, so a wrapped value that happens to land in range is accepted as a "valid" `Duration` even though it does not correspond to the digits the caller supplied.

This is the direct structural analog of the report's invariant failure: "assumes a fixed scale, applies (or fails to apply) a scaling operation blindly, and produces silently wrong values instead of rejecting or correctly normalizing out-of-range precision."

### Impact Explanation
Any consuming application that calls `google::protobuf::util::TimeUtil::FromString(text, &duration)` on attacker-influenced duration strings (e.g., parsing durations embedded in text configs, logs, or any text protocol where duration strings are user-supplied) can be made to silently accept a `Duration` whose `nanos` field is a wrapped/corrupted integer bearing no correct relationship to the input digits. Depending on how the resulting `Duration` is used downstream (timers, rate limits, billing windows, TTLs), this is an integrity/correctness impact similar in kind (though not identical in severity) to the mis-pricing impact in the original report: attacker-influenced input silently produces a materially wrong numeric result that passes validation. This is not a memory-safety or RCE issue, and severity is bounded by how the consuming application interprets `Duration.nanos`.

### Likelihood Explanation
Likelihood is moderate: `TimeUtil::FromString` is a public, documented API intended for parsing bounded, attacker-controllable text (`"1.010s"`-style strings) [7](#0-6) , so no privileged access or hostile schema is required — this matches the "ordinary client sending bounded input through a supported public parse API" threat model. The trigger condition (more than 9 digits after the decimal point in a duration string) is trivial to construct and requires no malformed wire data, just an ordinary text string.

### Recommendation
Reject (or explicitly truncate with correct rounding) fractional parts longer than 9 digits before the scaling multiplication, e.g. `if (nanos_part.length() > 9) return false;`, and change `Pow` usage (or add an explicit branch) so that over-long fractional strings are divided down rather than silently left unscaled. This mirrors the report's remediation of removing the erroneous scaling operation — here the fix is to validate precision and only apply the multiply-based scaling within its valid (non-negative exponent) domain.

### Proof of Concept
Given the code at [8](#0-7) :
1. Call `TimeUtil::FromString("1.1234567890s", &duration)` (10 fractional digits).
2. `nanos_part = "1234567890"`, `nanos_part.length() = 10`.
3. `nanos = strtoll("1234567890") = 1234567890`.
4. `Pow(10, 9 - 10) = Pow(10, -1)` → loop body never runs → returns `1`.
5. `nanos = 1234567890 * 1 = 1234567890`.
6. `static_cast<int32_t>(1234567890)` happens to fit in `int32_t` (max ~2.147e9), so no wraparound occurs in this particular example, but note `nanos=1234567890 > kDurationMaxNanoseconds (999999999)`, so `IsDurationValid` will reject it — meaning shorter overflows near the `int32_t` boundary (e.g., a fractional part crafted to overflow past `INT32_MAX` and wrap into the valid `[0, 999999999]` range, such as digit strings around `2^31 + small_valid_value`) are the ones that would silently pass validation with a corrupted value.

I was not able to fully brute-force a concrete digit string that (a) overflows the `int64_t`→`int32_t` cast and (b) lands back inside `[-999999999, 999999999]` without executing the actual `strtoll`/cast arithmetic in a compiler, so I cannot claim a verified end-to-end "passes validation with wrong value" repro without running the code. The missing length check and the negative-exponent `Pow` degeneration are confirmed directly from the source; a background engineering session with compiler/test access would be needed to confirm the exact wraparound input and produce an assertion-backed PoC.

bool TimeUtil::FromString(absl::string_view value, Duration* duration) {
  if (value.length() <= 1 || value[value.length() - 1] != 's') {
    return false;
  }
  bool negative = (value[0] == '-');
  size_t sign_length = (negative ? 1 : 0);
  // Parse the duration value as two integers rather than a float value
  // to avoid precision loss.
  std::string seconds_part, nanos_part;
  size_t pos = value.find_last_of('.');
  if (pos == std::string::npos) {
    seconds_part = std::string(
        value.substr(sign_length, value.length() - 1 - sign_length));
    nanos_part = "0";
  } else {
    seconds_part = std::string(value.substr(sign_length, pos - sign_length));
    nanos_part = std::string(value.substr(pos + 1, value.length() - pos - 2));
  }
  char* end;
  static_assert(sizeof(int64_t) == sizeof(long long),
                "sizeof int64_t is not sizeof long long");
  int64_t seconds = std::strtoll(seconds_part.c_str(), &end, 10);
  if (end != seconds_part.c_str() + seconds_part.length()) {
    return false;
  }
  int64_t nanos = std::strtoll(nanos_part.c_str(), &end, 10);
  if (end != nanos_part.c_str() + nanos_part.length()) {
    return false;
  }
  nanos = nanos * Pow(10, static_cast<int>(9 - nanos_part.length()));
  if (negative) {
    // If a Duration is negative, both seconds and nanos should be negative.
    seconds = -seconds;
    nanos = -nanos;
  }
  duration->set_seconds(seconds);
  duration->set_nanos(static_cast<int32_t>(nanos));
  if (!IsDurationValid(*duration)) {
    duration->Clear();
    return false;
  }
  return true;
}
