### Title
`SignableTransaction::new` computes `needed_fee` and the max-weight check on an output set that excludes the `OP_RETURN` data output - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The external finding's class is a quantity computed under one accounting basis being consumed as if it were computed under another, so the result silently diverges once the real base differs. In `SignableTransaction::new`, the transaction's fee and weight are computed from the `payments` list only, while the actual signed transaction additionally contains the attacker-influenced `OP_RETURN` output built from `data`. The signed transaction is therefore larger than what `needed_fee` was priced for.

### Finding Description
`SignableTransaction::new` pushes the `OP_RETURN` output into `tx_outs` before estimating the transaction's size:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds the model transaction's outputs exclusively from `payments`; the `data` output is never passed to it. The same omission exists in the change path, which again calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` on `payments` without the `OP_RETURN`. As a result:

- `needed_fee = fee_per_vbyte * vbytes` underprices the real transaction by the full weight of the `OP_RETURN` output (roughly `data.len() + ~11` bytes, up to ~91 bytes for the 80-byte data cap).
- When change exists, the change amount is set to `input_sat - payment_sat - fee_with_change`, so the *actual* fee paid equals the underestimated `fee_with_change`. The effective fee rate is lower than the caller requested and can fall below the network's minimum relay fee.
- The `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` check is evaluated against the underestimated `vbytes`, so it does not catch this.
- The `weight > MAX_STANDARD_TX_WEIGHT` check also uses the underestimated `weight`, allowing a transaction that exceeds the standardness limit to be produced.

This is the same structural bug as the report: a computed quantity (`vbytes`/`needed_fee`, analogous to `share`) is derived from a partial base (`payments` only, analogous to YieldBox shares) and then treated as if it describes the real, larger base (the final transaction including `OP_RETURN`, analogous to Singularity's `elastic + borrow` denominator). The two values are only coincidentally equal when `data` is `None`, just as `fraction == share` only before interest accrues.

### Impact Explanation
An attacker who can cause an `OP_RETURN` `data` payload to be included in a transaction built by this API makes the signed transaction carry a fee below the requested `fee_per_vbyte`, and potentially below the relay minimum. The transaction is then rejected by relay or left stranded in mempools while its inputs (Serai-controlled UTXOs) are committed to the spend, i.e., funds reported as sent that are not actually spendable/settling — a liveness/funds-lockup impact on the threshold wallet. The oversized-weight path additionally permits emitting a non-standard transaction that Bitcoin Core will refuse to relay.

### Likelihood Explanation
The trigger requires the `data: Option<Vec<u8>>` argument to be `Some`, which is an external, untrusted input to `SignableTransaction::new`. In Serai's own processor flow (`processor/src/networks/bitcoin.rs`), `None` is always passed, so the bug does not fire on the current production call path; however, `Payment.data` is a per-payment attacker-controlled field elsewhere in the processor, and the `data` parameter is public API surface intended for caller-supplied payloads. Reachability therefore depends on any caller (present or future integration) wiring data through — the defect is deterministic whenever that happens, requiring no races or privileged position.

### Recommendation
Include the `OP_RETURN` output in the size model: pass the final `tx_outs` (or `payments` plus the serialized `data` output) into `calculate_weight_vbytes` at both call sites, so `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check are all evaluated against the exact output set that will be signed. Alternatively, make `calculate_weight_vbytes` take the constructed `Transaction`/output list directly to eliminate the dual-source divergence.

### Proof of Concept
```rust
// Conceptual reproduction against networks/bitcoin/src/wallet/send.rs
let data = vec![0xaa; 80];
let tx_with_data = SignableTransaction::new(
    inputs.clone(), &payments, Some(change.clone()), Some(data.clone()), FEE,
).unwrap();
let tx_without = SignableTransaction::new(
    inputs.clone(), &payments, Some(change.clone()), None, FEE,
).unwrap();

// The signed tx carrying the OP_RETURN is larger, yet is priced identically:
assert!(tx_with_data.tx().vsize() > tx_without.tx().vsize());
assert_eq!(tx_with_data.needed_fee(), tx_without.needed_fee());
// => effective fee rate of tx_with_data < FEE, possibly < min relay fee,
//    so the signed transaction can be unrelayable while consuming inputs.
```

Caveat: this analog is a liveness/fee-correctness bug, not secret leakage or signature forgery, and its reachability hinges on `data` being attacker-influenced; within the current processor it is hard-coded to `None`. If the scan's scope requires production-reachable paths only (processor call sites), this may not qualify.
