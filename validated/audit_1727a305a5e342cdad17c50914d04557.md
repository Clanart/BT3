## Analysis

`FeeHandler::on_executed` in `impls.rs` derives a single `relayer_account` by decoding and verifying the signature *only from `messages[0]`*, then applies that one account to reward **every** `StateMachineUpdated` event present in the batch, with no per-event linkage back to the message that produced it. [1](#0-0) 

The reward loop then iterates the entire `events` vector (aggregated across *all* messages in the batch), collapses per-`state_machine_id` events to their highest height, and pays out to `relayer_account` — the identity taken solely from `messages[0]` — regardless of which message in the batch actually caused that state machine's advance: [2](#0-1) 

Contrast this with the sibling `WeightFeeHandler` in `pallet-ismp`, which correctly derives the originator/signer **per message** inside its loop rather than using a single global signer for the whole batch: [3](#0-2) 

Batches are submitted via the unpermissioned `handle_unsigned` extrinsic (`RuntimeOrigin::none()`), as shown in the pallet's own test harness, and the caller fully controls the `Vec<Message>` contents, including the `signer` byte field of each `ConsensusMessage`, which is unrelated to the extrinsic origin and unrelated to the actual consensus-proof verification that determines whether the message is accepted: [4](#0-3) [5](#0-4) 

Since `signer` is just an arbitrary field embedded in the message payload (self-signed over `keccak_256(consensus_proof)`, unrelated to who actually relayed/verified the underlying light-client update for a *different* `state_machine_id`), an unprivileged caller can construct a batch where `messages[0]` is a self-authored/self-signed `Consensus` message (for any state machine they have a valid proof for) and pack additional, independently-valid `Consensus` messages for other state machines into the same `handle_unsigned` call. All messages are still verified individually and correctly by the ISMP host (the vulnerability is not in proof verification), but the reward attribution collapses to whoever occupies index 0.

## Verdict

This is a real wrong-beneficiary accounting bug reachable via unprivileged input (an unpermissioned `handle_unsigned` batch), matching the "wrong beneficiary" and "reward accounting" impact categories in the decision standard. It is not excluded by the "front-run-only" or "malicious relayer" carve-outs, because the flaw exists independent of whether the second message was copied from another relayer's broadcast — it is a batch-aggregation/index-0 assumption bug in the reward code itself, not an infrastructure or relayer-honesty assumption.

### Title
Wrong relayer credited for all state-machine reward events in a batch — only `messages[0]`'s signer is used - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`FeeHandler::on_executed` extracts a single relayer identity from only the first message of a batch and then pays that one account for every `StateMachineUpdated` event in the batch, even for state machines whose update was produced by a different `Consensus` message (with a different, legitimate signer) later in the same batch.

### Finding Description
`on_executed` computes `maybe_relayer_account` solely from `messages.get(0)` [6](#0-5) . It then builds `highest_per_state_machine` from the full `events` vector without any correlation to which message emitted which event, and pays every entry to that single `relayer_account` [7](#0-6) . The `signer` field used for identity is attacker-controlled message content (self-signed over the message's own `consensus_proof`), decoupled from the actual submitter/extrinsic origin, and batches are submitted through the unpermissioned `handle_unsigned` call [4](#0-3) .

### Impact Explanation
An attacker who crafts `messages[0]` as a self-signed `Consensus` message can be credited for the treasury-funded rewards belonging to any other, unrelated `StateMachineUpdated` events that occur later in the same batch — diverting the correct relayer's reward to themselves. This corrupts the reward beneficiary and drains treasury funds intended for the actual relayer that produced the other state machine's consensus update.

### Likelihood Explanation
Requires only the ability to submit an unsigned `handle_unsigned` extrinsic with a multi-message batch where the attacker controls the first message — no privileged access or compromised infrastructure needed. Likelihood depends on batching being used in practice (multiple `Consensus` messages processed together), which the code explicitly supports and is exercised by the reward-collapsing logic for "sequential consensus updates."

### Recommendation
Attribute rewards per originating message: iterate `messages`, extract each `Consensus` message's own verified signer, and only credit that signer for the `StateMachineUpdated` events causally tied to its own `consensus_state_id`/`state_machine_id`, rather than deriving one global relayer from `messages[0]` and applying it to the union of all events in the batch.

### Proof of Concept
1. Attacker (key `A`) crafts `Message::Consensus` #1 with `consensus_proof` for state machine `X`, `signer` = attacker's own signature over `keccak_256(consensus_proof)`.
2. Attacker appends a second, independently valid `Message::Consensus` #2 for state machine `Y`, whose `signer` field is a genuine relayer key `B`'s signature (obtained from a legitimately broadcast/pending message).
3. Attacker submits both via `pallet_ismp::handle_unsigned(RuntimeOrigin::none(), vec![msg1, msg2])`.
4. Both messages independently pass ISMP proof verification and emit `StateMachineUpdated` for `X` and `Y` respectively.
5. `FeeHandler::on_executed` decodes only `msg1`'s signer → account `A`, then pays `A` for both the `X` and `Y` reward entries in `highest_per_state_machine`, per [2](#0-1) , instead of paying `B` for the `Y` update — confirmed by comparison with the existing single-message tests in `pallet_consensus_incentives.rs`, which only cover the single-message case and do not assert per-message attribution in multi-message batches [8](#0-7) .
