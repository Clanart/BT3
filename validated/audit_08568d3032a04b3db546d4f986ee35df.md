### Title
Unsafe `transferFrom` used to release bridged ERC721 tokens, permanently locking user assets on release - (File: contracts/service_chain/bridge/BridgeTransferERC721.sol)

### Summary
`BridgeTransferERC721.handleERC721Transfer` uses `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` to release a bridged NFT to its final recipient instead of `safeTransferFrom`. The `_to` address is fully controlled by the original, unprivileged caller of `requestERC721Transfer` (or `onERC721Received`) on the counterpart chain, so a mistaken or unaware contract destination will accept the transfer without knowing it received an ERC721, permanently locking the asset.

### Finding Description
`requestERC721Transfer` and the 1-step deposit path `onERC721Received` let any unprivileged caller specify an arbitrary `_to` recipient address that is forwarded to the counterpart chain via `RequestValueTransferEncoded`/`RequestValueTransfer` events. [3](#0-2) [4](#0-3) 
When the operator relays this request on the counterpart chain via `handleERC721Transfer`, and the bridge is not in mint/burn mode, the token is released to `_to` using the non-safe `transferFrom`, which does not check whether `_to` implements `onERC721Received`: [1](#0-0) 
Because `transferFrom` performs no receiver-acceptance check (unlike `safeTransferFrom`, which invokes `onERC721Received` and reverts on rejection/incompatibility), if `_to` is a smart contract that is not designed to receive or was never notified it received an ERC721 (e.g., an exchange deposit contract, a multisig without NFT-handling logic, or any contract lacking a recovery mechanism for stray tokens), the transferred token becomes irrecoverably stuck in that contract with no path to move it out.

### Impact Explanation
The bridge is the final custodian action for a cross-chain NFT transfer; once `handleERC721Transfer` executes `transferFrom`, there is no further check or rollback. Tokens sent to a non-compliant/unaware contract address are permanently locked, representing an unrecoverable loss of the user's bridged asset (in non-mint-burn mode this is the actual underlying NFT being released from bridge custody). This is a concrete asset-loss condition reachable purely through normal, unprivileged bridge usage (choosing a destination address), not requiring any privileged or malicious-operator behavior beyond the operator performing its normal designated relaying duty.

### Likelihood Explanation
Likelihood is realistic: any user bridging an NFT to a contract-controlled address on the destination chain (e.g., a wallet contract, custodial deposit address, or any contract not implementing `IERC721Receiver`) will trigger this path without any special conditions or attacker coordination — it's a routine cross-chain NFT transfer where the destination happens to be a smart contract.

### Recommendation
Use `safeTransferFrom` in `handleERC721Transfer` when releasing tokens in non-mint-burn mode, similar to the referenced report's proposed fix for `PrizePool.awardExternalERC721`. To avoid a DoS on the handling/voting mechanism if the recipient reverts, wrap the safe transfer in a `try/catch` (or low-level call) and, on failure, retain the token in a recoverable escrow state (e.g., allow `_to` or the owner to later claim it) rather than reverting the entire handle transaction and blocking nonce processing.

### Proof of Concept
1. On chain A, Alice (unprivileged) calls `requestERC721Transfer(tokenAddress, contractC, tokenId, extraData)` where `contractC` is a contract on chain B that does not implement `onERC721Received` (e.g., a simple multisig or vault contract with no NFT-recovery function).
2. The request emits `RequestValueTransferEncoded` with `_to = contractC`. [5](#0-4) 
3. The bridge operator on chain B observes the event and calls `handleERC721Transfer(..., _to = contractC, ...)`.
4. Since `modeMintBurn` is false, the bridge executes `IERC721(_tokenAddress).transferFrom(address(this), contractC, _tokenId)`, which succeeds because `transferFrom` performs no receiver check. [1](#0-0) 
5. `contractC` now owns `tokenId` but has no logic to transfer it out, permanently locking the NFT with no recovery path.
