### Title
Integer overflow in `SignableTransaction::new` produces a consensus-invalid spend the signer set will still sign - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Bitcoin send path (`SignableTransaction::new`, `networks/bitcoin/src/wallet/send.rs`) performs unchecked `u64` arithmetic over attacker-influenced payment amounts. `payment_sat` (line 187), `payment_sat + needed_fee` (line 215), and `fee_per_vbyte * vbytes` (lines 206, 227) can all overflow. In debug builds these panic — the direct analog of the CVE's null-pointer crash. In release builds they wrap, which defeats the `NotEnoughFunds` sanity check and yields a `SignableTransaction` whose declared outputs exceed its inputs. The downstream FROST `TransactionSignMachine` will still generate a valid BIP-340 signature for this consensus-invalid transaction.

### Finding Description
`SignableTransaction::new` sums payments with `payments.iter().map(|payment| payment.1).sum::<u64>()` and then checks funds with `input_sat < (payment_sat + needed_fee)`. Neither the `sum` nor the addition is checked. Because each payment amount is only lower-bounded by the `DUST` check (line 166-169) and has no upper bound, two payments each near `u64::MAX` overflow both the sum and the addition.

Reachability: the amounts flow from externally supplied payment data (the `payments: &[(ScriptBuf, u64)]` argument, populated from plan/scheduler instructions) into `SignableTransaction::new`, then into `TransactionSignMachine::sign` (`send.rs` lines 355-397), which computes `taproot_key_spend_signature_hash` and calls `sig.sign(...)` — i.e., the threshold set signs a sighash for a transaction whose outputs exceed its inputs. Such a transaction can never be confirmed; the inputs it names become unusable by that plan instance, and `fee()` (lines 138-141, `prevouts sum - output sum`) additionally underflows on the wrapped result.

This mirrors the CVE pattern: hostile input values reach a code path that aborts (panic on overflow in debug builds) or produces corrupt state (wrapped arithmetic bypassing the `NotEnoughFunds` guard in release builds), whereas a correct implementation would reject the inputs.

### Impact Explanation
- Debug builds / `overflow-checks = on`: immediate panic, crashing the signing process — denial of service of the threshold signing flow, matching the CVE's DoS primitive.
- Release builds: `input_sat < (payment_sat + needed_fee)` wraps to a small value, so `NotEnoughFunds` is skipped and a transaction assigning more value to outputs than the inputs contain is constructed. The multisig still produces a valid Schnorr signature over its sighash. The transaction is permanently unbroadcastable, and `fee()` underflow-wraps to a meaningless value, so the plan's funds cannot be spent via this constructed spend — funds are effectively stuck behind an invalid transaction until the plan is rebuilt.

### Likelihood Explanation
The bug requires payment amounts near `u64::MAX`, which are unrealistic for genuine Bitcoin transfers (21M BTC = 2.1e15 sat). Exploitability therefore depends on whether an unprivileged party can inject arbitrary `u64` payment amounts into the scheduler/plan pipeline. If payment amounts originate from untrusted instruction data (e.g., arbitrary `OutInstruction` payloads), the overflow is trivially triggered. If amounts are already range-validated upstream against real coin amounts, the practical risk drops to the debug-build panic path. I could not confirm the upstream validation within the in-scope files.

### Recommendation
Use checked/saturating arithmetic throughout `SignableTransaction::new`:
- `payments.iter().try_fold(0u64, |a, p| a.checked_add(p.1))` for `payment_sat` (same for `input_sat` and `fee()`).
- `payment_sat.checked_add(needed_fee)` and `fee_per_vbyte.checked_mul(vbytes)`, mapping `None` to a `TransactionError` variant.
- Consider an upper bound on individual payment amounts (e.g., `<= MAX_MONEY` = 21e14 sat) in addition to the `DUST` lower bound.
