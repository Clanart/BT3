## Title
Silent deletion of unresolved merge-conflict content when Copilot conflict resolution encounters a malformed conflict-marker decoy — (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Sherlock report flags a missing `if (fee > 0)` check that lets a rounding-to-zero value slip through unvalidated, silently bypassing a fee. GitHub Desktop's Copilot-assisted merge-conflict resolution feature has the same class of bug: `reassembleResolvedFile` relies on an implicit array-bounds check (`hunkIndex < hunkResolutions.length`) instead of an explicit validation/error, so when the count of parsed conflict blocks in the on-disk file diverges from the count of hunks the model actually resolved, the excess conflict block — including all of the user's "ours"/"theirs" code — is silently dropped from the file that gets written to disk, staged, and committed.

### Finding Description
Two independent regex-based scanners walk the same raw conflicted file but handle malformed/unclosed conflict markers differently:

- `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts`, lines 179-279) collects `theirs` content by scanning forward until it finds a closing `>>>>>>>` marker. If it never finds one, the inner loop has already consumed every remaining line up to EOF, and the hunk is discarded via `continue` [1](#0-0)  — this means **any well-formed real conflict marker located after an unclosed decoy marker is never extracted, never sent to Copilot, and never counted**.

- `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts`, lines 549-599), by contrast, treats an unclosed/malformed marker as a single line to copy through and only advances `i` by one, continuing to scan the rest of the file: [2](#0-1)  — so it *will* find and try to splice a resolution into any real, well-formed conflict block that appears after the decoy.

The splice step never validates that the number of well-formed blocks it finds matches `hunkResolutions.length`; it only guards the array access: [3](#0-2) 

When `hunkIndex >= hunkResolutions.length` (i.e., a real conflict block exists that the model was never asked about, because `extractConflictHunks` bailed out early on an earlier decoy marker), the block is **skipped entirely with no replacement and no error** — the entire `<<<<<<< / ======= / >>>>>>>` region, including both sides' real code, disappears from the reassembled content.

That reassembled content is then written directly to disk and staged without further review: [4](#0-3) 

### Impact Explanation
A remote branch/PR (attacker-controlled, fetched/merged by the victim in a normal collaborative workflow) can be crafted so that one of its files contains an unclosed conflict-marker-like sequence (e.g., a string literal or comment beginning with 7+ `<` characters) positioned before a real merge conflict region in that same file. When the victim merges/rebases against this branch and uses "Resolve with Copilot":
- `extractConflictHunks` silently truncates hunk extraction at the decoy, so Copilot is never shown (and never resolves) the trailing real conflict.
- `reassembleResolvedFile` still walks past the decoy and finds the real, well-formed trailing conflict block, but since it has no resolution for it (`hunkIndex >= hunkResolutions.length`), that entire block of code (both "ours" and "theirs" content) is dropped from the file with no warning, no error, and no entry in the "skipped files" list shown to the user.
- The truncated file is written to disk, `git add`ed, and committed as if the merge conflict were correctly and completely resolved — i.e., attacker-controlled input causes silent corruption of what the user commits, which is squarely inside the stated valid-impact class ("silent corruption of what the user commits or pushes").

### Likelihood Explanation
This requires only that the victim merge/rebase an untrusted branch and click "Resolve with Copilot" — a normal supported workflow with no unusual user action, no local/physical access, and no prior compromise. The trigger condition (a decoy unclosed marker positioned before a genuine conflict in the same file) is fully attacker-controlled content in a fetched branch. It does depend on the file actually being edited on both sides at the point after the decoy, which is a reasonably contrivable but not trivial-to-hit scenario, and requires the user to accept the AI resolution without manually diffing every line of every file — plausible given the feature is designed to let users trust and accept the generated resolution.

### Recommendation
- Make the two parsers consistent: `extractConflictHunks` and `reassembleResolvedFile` must apply identical rules for malformed/unclosed markers (ideally by sharing one scanning implementation), so hunk counts derived for the prompt always match what reassembly will encounter.
- In `reassembleResolvedFile`, explicitly validate that the number of well-formed conflict blocks found equals `hunkResolutions.length`; if not, throw (as is already done elsewhere via `CopilotValidationError`) instead of silently omitting content when `hunkIndex >= hunkResolutions.length`.
- Never silently drop a real conflict block's content — if a resolution is missing, fail the whole-file reassembly and force the file into the "skipped, needs manual resolution" path.

### Proof of Concept
1. Attacker prepares a branch where `file.txt` contains, before an actual conflicting hunk, a line matching the "ours" opening marker regex (`/^<{7}(?:\s|$)/`) but with no corresponding `=======`/`>>>>>>>` before EOF is unrealistic in the same file if there's a later real conflict — the realistic construction is a file where an *earlier* real conflict's closing marker text is subtly malformed (e.g. trailing content after `>>>>>>>` prevents the regex match at a boundary chosen by the attacker), causing `extractConflictHunks`'s inner "collect theirs" loop to run to EOF without matching `theirsMarker`, discarding that hunk and all following content from the hunk list per [5](#0-4) .
2. Victim merges/rebases the attacker's branch, gets real merge conflicts in `file.txt` (including a second, well-formed conflict after the malformed one), and clicks "Resolve with Copilot".
3. Copilot only receives/resolves the first hunk (`hunks.length === 1`), because `buildConflictContext` only forwards what `extractConflictHunks` returned [6](#0-5) .
4. On "Continue Merge", `_applyCopilotConflictResolutions` calls `reassembleResolvedFile` with `rawContent` (still containing both conflict blocks) and `hunkResolutions` of length 1.
5. `reassembleResolvedFile` walks past the malformed first block (copied through per its own rule) and finds the real second, well-formed conflict block; since `hunkIndex (1) < hunkResolutions.length (1)` is false, nothing is spliced in for it — the second conflict's code (both sides) vanishes from the output.
6. The truncated file is written and staged; the merge is completed and committed with silently missing code and no indication to the user that anything was skipped.
