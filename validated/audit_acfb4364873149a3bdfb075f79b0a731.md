### Title
Scanner credits attacker-created dust outputs as spendable multisig funds, forcing fee burn greater than their value - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Pareto report — where `requestRedeem` recorded a withdrawal claim without checking that the system actually had collateral backing it — Serai's Bitcoin `Scanner::scan_transaction` credits **any** transaction output whose `script_pubkey` matches a registered script as a fully spendable `ReceivedOutput`, without checking that the output's value can economically be spent. `SignableTransaction::new` then aggregates all supplied `ReceivedOutput`s as inputs without checking that each input's value exceeds the fee cost it adds. An unprivileged party can send sub-dust (e.g. 1 sat) outputs to the multisig's known Taproot address; the scanner reports them as received funds, and any spend that includes them burns more in fees than they contribute — a loss absorbed by the honest depositors, exactly the "obligation recorded without backing, loss socialized" shape of the original bug.

### Finding Description
`Scanner::scan_transaction` matches only `output.script_pubkey` against the registered `scripts` map and pushes a `ReceivedOutput` unconditionally, with no check on `output.value` (networks/bitcoin/src/wallet/mod.rs, lines 199-214). Anyone can create such an output on-chain — the P2TR script of the group key (and of every registered offset) is public.

On the spend side, `SignableTransaction::new` sums `input_sat` from all provided inputs and performs a single aggregate check `input_sat < payment_sat + needed_fee` (send.rs, lines 175-221), but never checks that each individual input is net-positive. A Taproot key-path input adds a fixed ~57.75 vbytes (the code itself assumes a fixed-size input in `calculate_weight_vbytes`, lines 71-83). At fee rate `f` sats/vbyte, an input is only net-positive if `value > ~58*f`. A 1-sat output is consensus-valid yet always net-negative, and can even make the whole transaction non-standard (many nodes reject transactions spending outputs worth less than the incremental relay cost, and if the constructed tx can't meet `TooLowFee`/weight limits, `new` errors out — liveness impact on withdrawals).

The result mirrors the audit finding: value is *accounted* (reported received, `epochPending`-equivalent `input_sat`) that does not reflect spendable backing, and the difference is paid by the other participants whose legitimate inputs subsidize the fee for the attacker's garbage outputs.

### Impact Explanation
- An attacker sends N tiny outputs (down to 1 sat each, ~N sats total cost) to the multisig address or any registered offset address.
- Each such output, once scanned, is indistinguishable from a real deposit. When included as an input, it adds ~58 vbytes of fee cost while contributing ~1 sat — a net loss of ~58·f − 1 sats per input charged to the multisig.
- At scale, forced inclusion of these outputs can also push the transaction over `MAX_STANDARD_TX_WEIGHT` or trigger `NotEnoughFunds`/`TooLowFee`, preventing any spend (griefing / withdrawal liveness), analogous to the report's second impact where `epochPending != 0` permanently blocked withdrawals.

### Likelihood Explanation
Creating matching outputs requires only knowing the public Taproot script — no key material, no validator collusion, no privileged position. Cost to the attacker is only the dust value itself plus their own (small, batched) funding transaction fees. Exploitation depends on the downstream wallet/processor including all scanned outputs as inputs, which is the natural usage of this API (`Scanner` returns `Vec<ReceivedOutput>` specifically shaped to feed `SignableTransaction::new`). Severity is Medium: bounded but repeatable loss plus a liveness vector, reachable entirely from public on-chain data.

### Recommendation
Filter sub-economic outputs at scan time or at transaction construction:

```rust
// in scan_transaction: skip outputs below the economic threshold
if output.value.to_sat() < MIN_SPENDABLE { continue }
```

or in `SignableTransaction::new`, drop/reject inputs where `input.value < INPUT_VBYTES * fee_per_vbyte` (~58·f sats), so that recorded obligations (`input_sat`) reflect only genuinely spendable collateral — the same fix class as the Pareto mitigation (scale the recorded amount to actual backing).

### Proof of Concept
1. Obtain the multisig's P2TR `script_pubkey` (public: derived from `tweak_keys(keys).group_key()` via `p2tr_script_buf`).
2. Broadcast a transaction with 100 outputs of 1 sat each to that script. Cost: 100 sats + fees.
3. `Scanner::scan_transaction` returns 100 `ReceivedOutput`s — reported as received funds (mod.rs:205-211).
4. Any wallet logic that spends all received outputs calls `SignableTransaction::new` with these inputs. Each adds ~57.75 vbytes; at 10 sat/vbyte the fee impact is ~57,750 sats while contributing only 100 sats — a ~57,650-sat loss paid from honest inputs' aggregate (`input_sat` check passes because the loss is socialized across all inputs), or the transaction fails `TooLowFee`/`TooLargeTransaction`, blocking spends entirely.

Note: the scan-time coinbase-maturity caveat (mod.rs:216-220) is documented behavior and excluded; this finding concerns consensus-valid, permanently-uneconomic outputs that the code neither documents nor guards against.
