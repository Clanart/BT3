### Title
`MsgChangeAdmin` transfers TokenFactory denom admin rights in a single irreversible step with no confirmation - ([File: x/tokenfactory/keeper/admins.go])

### Summary
The TokenFactory module's admin-transfer mechanism, `k.setAdmin`, overwrites `DenomAuthorityMetadata.Admin` unconditionally in a single message, with no two-step handshake or acceptance from the new admin.

### Finding Description
`setAdmin` loads the current `DenomAuthorityMetadata`, sets `metadata.Admin = admin`, and persists it immediately: [1](#0-0) . This is invoked from `msg_server.go`'s `ChangeAdmin` handler in response to a single `MsgChangeAdmin` transaction from the current admin, with no subsequent step required from the new admin to accept the role. The module's own documentation confirms this includes the ability to set the admin to `""` (an intentional "burn admin rights" feature), and explicitly states "this is only allowed to be called by the current admin of the denom" [2](#0-1) [3](#0-2) . If the current admin submits `MsgChangeAdmin` with a mistyped or unintended address (e.g., an address they do not control, or a bech32 string that is valid but not the intended recipient), admin rights over the denom (mint, burn, further admin changes) are transferred/relinquished in one atomic, unconfirmed step — exactly the bug class described in the reference report (`transferOwnership()` with no confirmation step).

### Impact Explanation
Because TokenFactory admin rights govern minting and burning of a specific `factory/{creator}/{subdenom}` denom, an erroneous single-step admin change permanently and irreversibly locks the original creator out of managing that denom's supply. This is a permanent freezing of a critical protocol capability (future minting/burning of that tokenfactory-issued asset) reachable purely by an unprivileged tokenfactory denom creator's own transaction, with no built-in safety net (no propose/accept flow, no ability to revert if the new admin address was a typo).

### Likelihood Explanation
Likelihood is bounded by the fact that this action can only be triggered by the current denom admin acting on their own transaction (not exploitable by a third party against another account) — this matches the exact risk profile of the referenced report, where the vulnerability is the absence of a confirmation mechanism rather than a third-party attack vector. Any tokenfactory admin performing a routine admin rotation (e.g., migrating to a new governance/multisig address) is exposed to this risk.

### Recommendation
Implement a two-step admin transfer for TokenFactory denoms: `ProposeChangeAdmin(denom, newAdmin)` sets a pending-admin field, and a follow-up `AcceptAdmin(denom)` message signed by `newAdmin` finalizes the transfer, mirroring the "propose/accept" pattern already used elsewhere in the codebase (e.g., the Gringotts contract's `propose_update_admin`/`vote_proposal`/`process_proposal` flow) [4](#0-3) .

### Proof of Concept
1. Account `A` creates a tokenfactory denom `factory/A/mycoin` via `MsgCreateDenom`, becoming its admin.
2. `A` intends to rotate admin to a new multisig address `B`, but submits `MsgChangeAdmin{Denom: "factory/A/mycoin", NewAdmin: "sei1<typo-address>"}`.
3. `msg_server.go`'s `ChangeAdmin` handler calls `k.setAdmin`, which immediately overwrites `metadata.Admin` to the typo'd address with no further confirmation [1](#0-0) .
4. Neither `A` nor the intended `B` can ever mint/burn/further-administer `factory/A/mycoin` again; the denom's admin capability is permanently and irreversibly lost to a random/unowned address.

func (k Keeper) setAdmin(ctx sdk.Context, denom string, admin string) error {
	metadata, err := k.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return err
	}

	metadata.Admin = admin

	return k.setAuthorityMetadata(ctx, denom, metadata)
