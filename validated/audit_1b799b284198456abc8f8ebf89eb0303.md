### Title
`core.hooksPath` is trusted from a cloned repository's own config, letting a malicious repo redirect Desktop's hooks-interception feature to execute attacker-controlled binaries - (`File: app/src/lib/hooks/get-repo-hooks.ts`)

### Summary
This is the git-native (JS/Electron) analog of the Trail of Bits finding: a security-relevant decision (which hook binaries Desktop will treat as "the repository's hooks" and later invoke via its proxy mechanism) is derived from a value that is not owned/verified by Desktop but is instead read straight out of data the git object model considers attacker-influenced — Git configuration values resolvable within the target repository's path.

### Finding Description
`getRepoHooks` computes `hooksPath` by first asking Git for `core.hooksPath` scoped to the repository path, and only falling back to the default `.git/hooks` location if that lookup fails: [1](#0-0) 

That resolved directory is then scanned for files whose names match Desktop's `knownHooks` allow-list, and any executable match is `yield`ed as a legitimate hook to intercept: [2](#0-1) 

`withHooksEnv` (invoked from `commit.ts`, `merge.ts`, `rebase.ts`, `pull.ts`, `push.ts`) uses this list to decide which hooks to proxy, and unconditionally overrides `core.hooksPath` for the *real* git invocation to point at a temp directory containing Desktop's `process-proxy` binaries, one per discovered hook name: [3](#0-2) 

The actual work happens in `createHooksProxy` (`hooks-proxy.ts`), which, for every intercepted hook invocation, shells out via `git hook run <hookName>` with the user's real environment merged with `GITHUB_DESKTOP=1` and any `GIT_`/`GITHEAD_` prefixed variables from the git-invoked environment: [4](#0-3) 

The broken invariant: Desktop treats `core.hooksPath` (and by extension the executable files found there) as *the user's own trusted local configuration*, the same class of assumption the Trail of Bits report calls out — trusting a value whose provenance is not verified to belong to the trusted party (the user/Desktop) rather than to an untrusted input (a cloned/fetched repository). `git config` without `--local`/`--global` restriction resolves configuration from every scope Git considers, including any config file reachable from the repository's git directory resolution (e.g. `.git/config`, `include`/`includeIf` directives, or a `.git` file redirecting into a worktree/submodule metadata directory supplied as part of the cloned content). Nothing in `getRepoHooks` or `withHooksEnv` verifies that the `hooksPath` value — or the hook files subsequently found and marked executable — originates from a location the user (rather than the repository being opened) actually controls.

### Impact Explanation
If an attacker can get their crafted `core.hooksPath` config and adjacent hook binaries into a directory that Desktop resolves against when opening/interacting with a repository (e.g., a shared/zipped repository dropped in via "Add Existing Repository", a repository whose `.git` metadata directory content is attacker-supplied, or a submodule/worktree layout that lets an attacker-controlled path be resolved as `core.hooksPath`), then every subsequent commit/merge/rebase/pull/push Desktop performs on that repository will run "hooks" discovered from that attacker-chosen path with `GITHUB_DESKTOP=1`, the user's real shell environment, and `GIT_`/`GITHEAD_` variables — i.e., arbitrary code execution under the user's account, entirely inside the Desktop-managed workflow the user believes is safe. This mirrors the ABC Labs finding's core lesson: a value used for a privileged decision must be owned/verified by the trusted component, not sourced from something the lower-trust party (in Desktop's case, the repository content/layout) can manipulate.

### Likelihood Explanation
Moderate-to-low, matching the report's own "Low" difficulty rating for the analogous Solana issue. Git itself already treats "dubious ownership"/unsafe repositories specially (Desktop surfaces this via `getRepositoryType`'s `unsafe` kind and the "Trust Repository" prompts in `add-existing-repository.tsx` / `missing-repository.tsx`), which mitigates the most obvious "just clone a malicious repo and its `.git/config` takes effect" scenario for directories owned by another user. However, `getConfigValue`'s underlying `git config -z --get core.hooksPath` call in `get-repo-hooks.ts` is not restricted with `--local` and does not go through the same "unsafe repository" gate used elsewhere in the codebase (compare `getRepositoryType`'s explicit dubious-ownership handling vs. `getRepoHooks`'s bare `git config` lookup), so any repository-adjacent config source that resolves without tripping the ownership check (e.g., repos the user owns but whose `.git` state was populated by extracting an archive, syncing over a network share, or restoring from an untrusted backup) can still redirect hook execution.

### Recommendation
**Short term:** Restrict the `core.hooksPath` lookup in `get-repo-hooks.ts` to `--local` scope explicitly relative to a git-directory that has already passed Desktop's dubious-ownership/"unsafe repository" check, and refuse to honor `core.hooksPath` values that resolve outside of the repository's own `.git` directory tree unless the user has explicitly trusted that repository (reusing the existing `addSafeDirectory`/`isRepositoryUnsafe` trust gate already implemented in `add-existing-repository.tsx` and `missing-repository.tsx`).

**Long term:** Treat any git-configuration-derived path used to decide what code Desktop will execute as an untrusted input by default; require it to flow through the same trust boundary/allow-list mechanism Desktop uses for "unsafe" repositories, rather than a bare `git config`/`getConfigValue` call, consistent with the general principle in the original report of not letting a lower-trust surface control values that drive privileged program behavior.

### Proof of Concept
1. Obtain or construct a repository directory whose `.git` metadata (not necessarily owned by another OS user, so it doesn't trip the `unsafe` dubious-ownership check) contains a config setting `core.hooksPath = <attacker-dir>`, where `<attacker-dir>` contains an executable file named after a hook Desktop intercepts (e.g., `pre-commit`), per the allow-list in `app/src/lib/hooks/get-repo-hooks.ts`.
2. Have the victim add this repository to GitHub Desktop (e.g., via "Add Existing Repository", extracting a shared archive, or restoring from backup/sync) — no elevated privileges or existing compromise of the host are required, only that the directory's ownership doesn't trigger Git's separate `dubious ownership` unsafe-repo detection.
3. Enable Desktop's hooks-interception feature (`getHooksEnvEnabled()`), which is gated by `enableHooksEnvironment()`/`git-hooks-env-enabled`.
4. Trigger any intercepted git operation (commit, merge, rebase, pull, or push) from Desktop's UI.
5. Observe that `getRepoHooks` resolves `core.hooksPath` to the attacker directory, `withHooksEnv` sets up proxies for the discovered hook name(s), and `createHooksProxy` in `hooks-proxy.ts` executes `git hook run <hookName>` against that path — running the attacker's binary with `GITHUB_DESKTOP=1` and the real environment, under the victim's account, silently as part of what the user believes is a normal Desktop git action.

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
}
