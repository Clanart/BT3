## Title
Signed 64-bit integer overflow in `TimeUtil::TimestampToNanoseconds`/`DurationToNanoseconds` (and Micros/Millis variants) - (File: `src/google/protobuf/util/time_util.cc`)

## Summary
`google::protobuf::util::TimeUtil` exposes conversion helpers that turn a `Timestamp`/`Duration` well-known-type message into a scalar nanosecond/microsecond/millisecond count by multiplying the `seconds()` field by a fixed constant (`1e9`, `1e6`, `1e3`) using plain `int64_t` arithmetic. The only guard is `ABSL_DCHECK(IsTimestampValid(...))`, which (a) is compiled out entirely in release/NDEBUG builds, and (b) even when active, only checks that `seconds`/`nanos` are within the *Timestamp*/*Duration* value range — it does not check whether `seconds * kNanosPerSecond` actually fits in `int64_t`. This is the same bug class as CVE-2025-47268 in `iputils` ping: an attacker-influenced timestamp value is multiplied by a fixed scale factor without an overflow-safe check, producing a signed integer overflow (undefined behavior) and silently wrong/garbage data instead of a controlled error.

## Finding Description
`TimeUtil::TimestampToNanoseconds` computes: [1](#0-0) 

and `TimeUtil::DurationToNanoseconds` does the analogous thing: [2](#0-1) 

Both only assert validity via `ABSL_DCHECK(IsTimestampValid(...))`/`IsDurationValid(...)`, and `IsTimestampValid`/`IsDurationValid` merely bound `seconds`/`nanos` to the documented `Timestamp`/`Duration` ranges: [3](#0-2) 

Those ranges themselves are far larger than what fits after multiplying by `kNanosPerSecond` (1,000,000,000): `kTimestampMaxSeconds = 253402300799` (year 9999) and `kDurationMaxSeconds = 315576000000`, both of which, multiplied by 1e9, exceed `INT64_MAX` (~9.223372e18) by more than an order of magnitude. So a fully "valid" `Timestamp`/`Duration` (as accepted by binary/ProtoJSON parsing and passing `IsTimestampValid`) still overflows in `TimestampToNanoseconds`/`DurationToNanoseconds` — the existing check is necessary but not sufficient, exactly mirroring the ping issue where the timestamp arithmetic lacked an overflow-safe check before multiplying attacker-influenced 64-bit values.

By contrast, other conversion sites in this same file are overflow-safe: the `Duration operator*=(Duration&, int64_t)` path explicitly widens to `absl::uint128` before multiplying to avoid this exact overflow: [4](#0-3) 
demonstrating the project is aware of this arithmetic hazard elsewhere but did not apply the same protection to `TimestampToNanoseconds`/`DurationToNanoseconds`/`TimestampToMicroseconds`/`DurationToMicroseconds`/etc.

Java's equivalent utility (`Timestamps`/`Durations`) uses `Math.multiplyExact`/`addExact`, which throw `ArithmeticException` on overflow instead of silently wrapping: [5](#0-4) [6](#0-5) 
confirming that C++ `TimeUtil` is the outlier lacking an overflow-safe multiply, while Python's implementation is immune because Python integers are arbitrary precision: [7](#0-6) 

## Impact Explanation
A trusted application that parses an attacker-supplied `Timestamp`/`Duration` (binary or ProtoJSON) via the standard `ParseFrom*`/JSON parse APIs, and then calls `TimeUtil::TimestampToNanoseconds`/`DurationToNanoseconds` (or the Micros/Millis variants) on that message in a release build, gets a silently wrapped, semantically wrong int64 value rather than an error — this is a data-integrity failure (incorrect data collection), directly analogous to the "application error or incorrect data collection" impact described in CVE-2025-47268. Because `ABSL_DCHECK` compiles to nothing outside debug builds, production binaries have no diagnostic at all; in debug builds the `ABSL_DCHECK` also wouldn't catch it because `IsTimestampValid` doesn't check the multiplication result, only field ranges — so even a debug assertion failure does not occur, the overflow is truly silent in both modes.

## Likelihood Explanation
Any C++ consumer that calls `TimeUtil::TimestampToNanoseconds`/`DurationToNanoseconds`/`TimestampToMicroseconds`/`DurationToMicroseconds` on a message field populated from untrusted binary or JSON input (a common pattern for well-known-type `Timestamp`/`Duration` fields) reaches this path with a value it fully controls, well within the documented valid range for the type (e.g., a date past ~2262 for nanoseconds, or a large but legal `Duration`). No malformed/oversized wire data, no schema tampering, and no privileged access are needed — a bounded, otherwise-valid message suffices.

## Recommendation
Change `TimeUtil::TimestampToNanoseconds`, `DurationToNanoseconds`, `TimestampToMicroseconds`, `DurationToMicroseconds`, `TimestampToMilliseconds`, and `DurationToMilliseconds` to use overflow-checked arithmetic (e.g., widen to `absl::int128`/`absl::uint128` as already done in `operator*=`, or use `absl::CheckedAdd`/saturating-multiply helpers) and return an explicit error/failure instead of relying on `ABSL_DCHECK`, which is compiled out in release builds and does not validate the post-multiplication range in any build mode.

## Proof of Concept
```cpp
#include "google/protobuf/util/time_util.h"
using google::protobuf::Timestamp;
using google::protobuf::util::TimeUtil;

Timestamp t;
// Fully valid per IsTimestampValid: seconds within
// [kTimestampMinSeconds, kTimestampMaxSeconds] = [-62135596800, 253402300799]
t.set_seconds(253402300799LL);  // 9999-12-31T23:59:59Z, a legal Timestamp
t.set_nanos(0);

int64_t nanos = TimeUtil::TimestampToNanoseconds(t);
// Expected mathematically: 253402300799 * 1'000'000'000 = 253402300799000000000
// which does not fit in int64_t (max ~9.223e18). In a release build
// (NDEBUG, ABSL_DCHECK compiled out) this silently wraps to a
// nonsensical negative/garbage value with no error signal, since
// IsTimestampValid() only bounds seconds/nanos fields, not the
// multiplication result.
```
This reproduces with a message produced from ordinary, schema-valid binary or ProtoJSON parsing of a `Timestamp`, requiring no malformed wire data.

  static constexpr int64_t kTimestampMinSeconds = -62135596800LL;
  // For "9999-12-31T23:59:59.999999999Z".
  static constexpr int64_t kTimestampMaxSeconds = 253402300799LL;
  static constexpr int32_t kTimestampMinNanoseconds = 0;
  static constexpr int32_t kTimestampMaxNanoseconds = 999999999;
  static constexpr int64_t kDurationMinSeconds = -315576000000LL;
  static constexpr int64_t kDurationMaxSeconds = 315576000000LL;
  static constexpr int32_t kDurationMinNanoseconds = -999999999;
  static constexpr int32_t kDurationMaxNanoseconds = 999999999;

  static bool IsTimestampValid(const Timestamp& timestamp) {
    return timestamp.seconds() <= kTimestampMaxSeconds &&
           timestamp.seconds() >= kTimestampMinSeconds &&
           timestamp.nanos() <= kTimestampMaxNanoseconds &&
           timestamp.nanos() >= kTimestampMinNanoseconds;
  }

  static bool IsDurationValid(const Duration& duration) {
    return duration.seconds() <= kDurationMaxSeconds &&
           duration.seconds() >= kDurationMinSeconds &&
           duration.nanos() <= kDurationMaxNanoseconds &&
           duration.nanos() >= kDurationMinNanoseconds &&
           !(duration.seconds() >= 1 && duration.nanos() < 0) &&
           !(duration.seconds() <= -1 && duration.nanos() > 0);
  }
