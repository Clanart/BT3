### Title
Native SEI value sent to the distribution precompile's `rewards()` query is permanently stranded - (File: `precompiles/distribution/distribution.go`)

### Summary
The Sei EVM distribution precompile at `0x0000000000000000000000000000000000001007` exposes a `rewards()` view method that, unlike every other transaction method on the precompile, never validates that the call is non-payable. Because the distribution precompile is not registered in the `payablePrecompiles` allow-list that suppresses native EVM value transfers, any `usei`/wei sent along with a call to `rewards()` is moved by the ordinary EVM value-transfer mechanism into the precompile's underlying account balance — and the distribution precompile has no code path that ever spends from its own balance. This is directly analogous to the `VotingPool` bug class: a token/value receiving surface exists, but there is no mechanism to reclaim or route out value that lands there, so it is permanently locked.

### Finding Description
Every state-changing method on the distribution precompile calls `pcommon.ValidateNonPayable(value)` to reject value-bearing calls, e.g. `withdrawValidatorCommission` [1](#0-0) . The `rewards` method, however, is dispatched with no payability check at all: [2](#0-1) 

This gap is explicitly called out in the integration test suite as a known quirk: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)" [3](#0-2) .

Whether attaching value to a precompile call actually transfers native balance to the precompile address is controlled by `IsPayablePrecompile`, which only whitelists `bank`, `staking`, `gov`, and `wasmd` — precompiles that explicitly move funds via `HandlePaymentUsei`/`SendCoins` as part of their own logic: [4](#0-3) 

Because `distribution` is absent from this list, the EVM's standard value-transfer semantics are **not** suppressed for it, meaning a call with non-zero `value` credits the distribution precompile's account with that `usei`/wei at the EVM/StateDB level, independent of what `PrecompileExecutor.Execute` does. Since the distribution executor's `rewards` handler only performs a read-only query (`p.distrKeeper.DelegationTotalRewards`) and never sends coins out, and since `rewards` is reachable outside `readOnly`/staticcall restriction, any caller can trivially call `rewards(address)` with attached value in a normal (non-static) transaction, and that value is absorbed by the precompile's account with no way to recover it — there is no withdrawal, sweep, or refund mechanism anywhere in the distribution precompile for its own native balance.

This mirrors the reported `VotingPool` root cause precisely: a contract/precompile can receive value as a side effect of an otherwise normal operation, but the code was never designed to hold or redistribute that value, so it becomes permanently locked.

### Impact Explanation
Any unprivileged EVM transaction sender can send `usei` to the distribution precompile via `rewards(address)` and have those funds permanently locked with no recovery path, since:
- The distribution precompile is not in `payablePrecompiles`, so the native transfer happens automatically at the EVM layer.
- `rewards()` never validates non-payability nor moves the received value anywhere.
- No other precompile method or governance-controlled account can withdraw arbitrary native balance credited to the distribution precompile's Sei-mapped address.

This is a permanent freezing of user funds (the exact class of impact required: concrete fund loss / permanent freezing), reachable by any public transaction sender with no special privileges.

### Likelihood Explanation
High likelihood: the vulnerable method is a public, non-owner-gated EVM entry point (`rewards(address)`); no special preconditions are needed beyond attaching non-zero `value` to the call. The behavior is already documented internally as a known quirk in the test suite, confirming the code path is real and reachable.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `rewards` method (and audit all other query/view methods on the distribution precompile and any other non-payable-listed precompiles for the same gap), or alternatively add `distribution` to `payablePrecompiles` and implement an explicit refund/handling path (as `HandlePaymentUsei` does for `bank`/`staking`/`gov`/`wasmd`) so that any received value is either rejected or properly routed back to the caller.

### Proof of Concept
1. An unprivileged EVM account calls the distribution precompile at `0x0000000000000000000000000000000000001007` with method `rewards(address)` (any delegator address, including the caller itself) as a normal (non-static) transaction, attaching `value > 0`.
2. Because `distribution` is not in `payablePrecompiles` [5](#0-4) , the EVM's built-in value-transfer path credits the sent `usei`/wei to the distribution precompile's underlying account balance.
3. `PrecompileExecutor.Execute` dispatches to `rewards`, which performs no `ValidateNonPayable` check [2](#0-1)  and only returns query data; it never touches the credited balance.
4. The transaction succeeds; the sent value is now held at the distribution precompile's account with no method in the distribution precompile (or elsewhere) capable of withdrawing it — the funds are permanently locked.
