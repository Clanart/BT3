### Title
Security-review hooks keyed on `tool_name == "Bash"` silently skip the same git-commit/push actions executed via the PowerShell tool - (File: plugins/security-guidance/hooks/hooks.json)

### Summary
The `security-guidance` plugin's commit/push security review is wired to fire only when `tool_name` is `"Bash"`. On Windows, Claude Code also ships a separate, first-class **PowerShell tool** that executes the exact same class of commands (including `git commit`/`git push`) but reports a different `tool_name`. Because the plugin's `PostToolUse` matcher is `"Bash"` only, and the Python dispatcher additionally gates on `tool_name == "Bash" and hook_event_name == "PostToolUse"`, a commit or push made through the PowerShell tool produces the identical repository state change (new commit, updated ref, pushed history) without ever invoking the security reviewer — mirroring the reported bug class where an alternate code path reaches the same state-changing outcome while skipping the event/telemetry that a downstream control depends on.

### Finding Description
`plugins/security-guidance/hooks/hooks.json` registers the commit/push review hooks under `"matcher": "Bash"` with `"if": "Bash(git commit:*)"` / `"if": "Bash(git push:*)"`: [1](#0-0) 

The Python entry point re-derives the same gate independently, keyed strictly on the literal tool name `"Bash"`: [2](#0-1) 

`handle_commit_review_posttooluse` itself is documented as a "PostToolUse handler for Bash", and its defensive re-check only inspects `tool_input.get("command")`, which is populated for the Bash tool's schema: [3](#0-2) 

Separately, the CHANGELOG confirms Claude Code ships a distinct, first-class **PowerShell tool** for Windows that is functionally parallel to Bash for running shell commands (including `git`), and can even become the *primary* shell: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the plugin's detection logic only recognizes `tool_name == "Bash"`, invoking `git commit`/`git push` via the PowerShell tool changes the same underlying git state (creates commits, pushes refs) that the commit-review/push-sweep logic exists to police, but never triggers `handle_commit_review_posttooluse` or `handle_push_sweep_posttooluse`. This is directly analogous to `[M02] Bypassing token events`: `burn()` (Bash-tool commit) emits the controlling event, while `withdraw()` (PowerShell-tool commit) reaches the same effective state change through a code path that the control never instruments.

### Impact Explanation
On any Windows session with the PowerShell tool enabled (opt-in today via `CLAUDE_CODE_USE_POWERSHELL_TOOL`, and already promoted to the *default*/primary shell in some configurations per the changelog entries above), a user or an automated/compromised workflow can commit and push code containing secrets, injected vulnerabilities, or malicious changes while completely bypassing the security-guidance plugin's LLM-based commit/push review, its `previous_findings` dedup bookkeeping, and its `_append_reviewed_shas` tracking. This silently defeats the security control's entire threat model for any Windows user relying on the PowerShell tool, without any error, warning, or trace indicating the review was skipped — the plugin's telemetry (`commit_review`, `commit_review_on`, `skip_reason`) never even fires, so there is no observability signal that reviews are being missed.

### Likelihood Explanation
Likelihood is moderate-to-high wherever the PowerShell tool is enabled: Windows users using `git` from the PowerShell tool (the increasingly-default shell on Windows per the changelog) will trigger this gap on every single commit/push, with no special attacker action required — it happens as a natural consequence of normal workflow, not a crafted exploit.

### Recommendation
Broaden the `security-guidance` plugin's `PostToolUse` matcher and the `tool_name` check in `security_reminder_hook.py`'s `main()` to also cover `"PowerShell"` (e.g. `"matcher": "Bash|PowerShell"` and `tool_name in ("Bash", "PowerShell")`), and confirm `tool_input.get("command")` is populated consistently for the PowerShell tool's schema so `_GIT_COMMIT_RE`/`_GIT_PUSH_RE` detection and stdout/stderr-based success heuristics keep working. More generally, any hook or plugin that gates state-changing security review on a specific `tool_name` string should be audited for every tool capable of producing the same effect (Bash, PowerShell, and any future shell-equivalent tool).

### Proof of Concept
1. On Windows with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` (or PowerShell as the default shell), have Claude run a normal Bash-tool `git commit -m "..."` once — observe `handle_commit_review_posttooluse` fire (visible via `debug_log`/`emit_metrics` output or the asyncRewake review message).
2. Repeat the same commit content, but have Claude issue the command through the PowerShell tool instead (e.g. `pwsh -c "git commit -m '...'"` equivalent invocation, or simply operate in a session where PowerShell is the active shell tool).
3. Observe that no `commit_review` metric, no `_append_reviewed_shas` entry, and no asyncRewake security-review message is produced for step 2's commit, confirming the review is silently skipped despite the identical git state change. [2](#0-1)

    analyze_code_security, and exits with code 2 (stderr findings) to wake
    the model. Deduplicates against the shared previous_findings state so

    session_id = input_data.get("session_id", "default")
