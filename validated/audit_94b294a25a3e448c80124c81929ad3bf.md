### Title
`safe.directory` trust entries are never revoked, silently bypassing GitHub Desktop's "unsafe repository" ownership protection - (File: `app/src/lib/git/config.ts`)

### Summary
GitHub Desktop protects users from Git's "dubious ownership" attack by refusing to operate on a repository whose directory is owned by a different user, and only proceeding once the user explicitly clicks "Trust Repository." That decision is persisted by adding the path to the global `safe.directory` Git config via `addSafeDirectory`. Nothing in the codebase ever removes a path from `safe.directory`, including when the corresponding repository is removed from Desktop (`_removeRepository`) or relocated. As a result, trust granted for a specific directory persists indefinitely and is silently re-applied to *any future content* that later occupies that same path, without re-prompting the user.

### Finding Description
`addSafeDirectory` adds a path to the global `safe.directory` allowlist the first time a user clicks "Trust Repository" in `MissingRepository` or `AddExistingRepository`: [1](#0-0) 

This call is triggered from `onTrustDirectory` handlers: [2](#0-1) [3](#0-2) 

The underlying ownership check that this trust bypasses is purely path-based, implemented in `getRepositoryType`, which asks Git whether the directory is "unsafe" (owned by another user) and only reports `{ kind: 'unsafe', path }`: [4](#0-3) 

Once a path is added to `safe.directory`, Git will always treat that literal path as trusted — even if the directory's contents or ownership change later — because `safe.directory` entries are keyed purely on path, not on any content/ownership fingerprint. GitHub Desktop never calls anything analogous to a "removeSafeDirectory" — a full repo-wide search confirms there is no code path that ever deletes or resets an entry from `safe.directory`. In particular, `_removeRepository`, which is the normal way a user detaches a repository from Desktop, only removes the local database record and does not revoke the Git-level trust: [5](#0-4) 

This is structurally identical to the `TapiocaOptionLiquidityProvision` bug: a security-relevant piece of state (`sglRescueRequest[...]` timestamp / here, the `safe.directory` trust entry) is set once to gate a protected action, but is never cleared when the protected object is "removed" (the rescued asset / here, the repository is removed from Desktop). If the same identity (asset ID / directory path) is reintroduced later under attacker control, the stale state causes the protection to be silently skipped.

### Impact Explanation
On a machine where paths can be reused by different owners — shared workstations, CI/build agents, restored VM snapshots, re-mounted network shares, or simply a user deleting a repo folder and having another user (or a malicious installer/archive) recreate a directory at the same path — GitHub Desktop will not show the "This directory appears to be owned by another user… may automatically execute files" warning again for that path, because Git itself will consider it safe due to the un-revoked `safe.directory` entry. Git's own dubious-ownership check exists specifically to prevent execution of repository-controlled hooks/config (e.g. `core.fsmonitor`, `.git/hooks`, working-tree scripts) planted by another user; bypassing it via a stale trust entry allows an attacker who gains write access to a previously-trusted path to have their planted repository run without the user ever being warned, leading to code execution under the victim's Desktop process.

### Likelihood Explanation
This requires a somewhat specific but realistic condition: the victim must have previously trusted a directory path and later removed that repository (or the path must be reused, e.g. shared runner directories, ephemeral containers/VMs reused across users, or `/tmp`-style shared paths), and an attacker must then be able to place a Git repository at that exact path before the user re-adds/re-opens it in Desktop. This does not require local/physical access to the victim's already-open session or any credential theft — only the ability to write to a directory path the victim previously trusted (a scenario common in shared/multi-tenant build or lab machines). Likelihood is moderate: it depends on path reuse, but the protection is bypassed completely and silently once that condition is met, with no additional user interaction beyond opening/adding the repository as usual.

### Recommendation
Revoke the `safe.directory` trust when a repository is removed from Desktop (mirroring the "delete the rescue request entry" fix suggested in the original report): add a `removeSafeDirectory`/`git config --global --unset-all safe.directory <path>` call inside `_removeRepository` (and any other path where Desktop forgets a repository, e.g. `_relocateRepository`'s stale-path branch). Additionally, consider binding trust decisions to more than just the path — e.g., re-validate directory ownership/identity at open time rather than relying solely on Git's persistent global allowlist — so that reusing a previously-trusted path with new, differently-owned content still triggers the warning.

### Proof of Concept
1. On a shared machine, User A clones/opens a repository at `C:\shared\project` (or `/shared/project`), triggers the "unsafe repository" prompt (e.g., directory owned by a different user), and clicks "Trust Repository." This calls `addSafeDirectory('/shared/project')`, permanently adding the path to the global `safe.directory` config (`app/src/lib/git/config.ts:181-189`).
2. User A later removes the repository from GitHub Desktop via `_removeRepository` (`app/src/lib/stores/app-store.ts:8210-8235`) and deletes the directory. Note that this code path never removes the `safe.directory` entry.
3. An attacker (a different OS user with write access to `/shared`, or a script executed under a different account) recreates `/shared/project` as a malicious Git repository containing crafted hooks/config designed to execute on Git invocation.
4. User A (or another Desktop user on the shared machine) adds `/shared/project` again via "Add Existing Repository" (`app/src/ui/add-repository/add-existing-repository.tsx`). `getRepositoryType` calls Git, which — because the path is still listed in `safe.directory` — reports it as `regular` rather than `unsafe`, so `isRepositoryUnsafe` is never set and the "Adding untrusted repositories may automatically execute files" warning never appears.
5. Desktop proceeds to run normal Git operations (`loadRemotes`, LFS checks, etc.) against the attacker-controlled repository without any user consent step, despite the directory now being genuinely untrusted content.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
