I found a concrete analog: a boundary-check flaw in the path-containment helper `_resolveWithin` used to validate that a deep-link-supplied file path stays inside the target repository.### Title
Deep-link `filepath` parameter can escape the target repository due to a missing path-separator boundary check in `_resolveWithin` - ([File: app/src/lib/path.ts])

### Summary
GitHub Desktop's `x-github-client://openRepo` deep link accepts a `filepath` parameter that is later resolved against the repository root and revealed to the user via `shell.showItemInFolder`. The containment check used to guarantee the resolved path stays inside the repository, `_resolveWithin`, uses a raw string `startsWith` comparison between the resolved real path and the repository's real root path. Because this check does not verify a path-separator boundary, a sibling directory or file whose name starts with the repository's directory name (e.g. `repo` vs `repo-evil`) is incorrectly treated as being "inside" the repository, allowing a crafted deep link to reference files outside the cloned repository.

### Finding Description
`parseAppURL` builds an `IOpenRepositoryFromURLAction` directly from attacker-controlled URL query parameters, including `filepath`, with only a check that it isn't URL-invalid: [1](#0-0) 

`Dispatcher.openRepositoryFromUrl` takes that `filepath`, rejects only absolute paths, and then relies entirely on `resolveWithin` to keep the path inside the repository before revealing it in the file explorer: [2](#0-1) 

The containment logic itself is in `_resolveWithin`: [3](#0-2) 

The final guard, `realResolved.startsWith(realRoot)`, is a plain string prefix comparison. It never checks for a trailing path separator (or exact equality) after the prefix match. This means any resolved path whose string representation happens to start with the exact characters of `realRoot` — even if it's a completely different, sibling directory — passes the check as "inside" the repository. For example, if the repository lives at `/Users/victim/repo`, a `filepath` value of `../repo-secrets/id_rsa` resolves to `/Users/victim/repo-secrets/id_rsa`, and `'/Users/victim/repo-secrets/id_rsa'.startsWith('/Users/victim/repo')` evaluates to `true`, even though `repo-secrets` is an entirely different directory.

The existing unit tests only exercise cases where the traversal goes fully outside any shared prefix (`join('..')`, `join('..','..')`) or symlink cases that resolve back within the true root; none test the sibling-prefix collision case, so the flaw is not caught: [4](#0-3) 

This is a direct analog of the report's broken-invariant class: a security check performs a coarse/loose identity comparison (string owner equality vs. approved-address delegation in the original report) instead of the precise boundary/identity check the invariant actually requires (path containment vs. string prefix), letting an unintended entity be treated as "trusted."

### Impact Explanation
An attacker who can get a victim to click a crafted `x-github-client://openrepo?...&filepath=...` link can cause Desktop to resolve and reveal (via `shell.showItemInFolder`) a file located outside the intended repository directory, provided a same-prefixed sibling path exists (e.g., another cloned repo, a backup folder, or an attacker-plantable directory name adjacent to the repo). This is a file-read/disclosure outside the repo boundary — the exact "silent corruption/escape of what should stay confined to the repo" class called out as valid impact, reached purely through a link the user clicks, with no local access or malware required.

### Likelihood Explanation
Exploitation requires only that the victim click a specially crafted deep link (Desktop registers `x-github-client://` and platform-legacy schemes as default protocol handlers) and that a directory sharing the repository's name as a prefix exists on disk — a scenario an attacker can increase the odds of (e.g., by naming the malicious/target sibling directory, or via typical developer directory layouts like `repo`, `repo-old`, `repo-backup`). No authentication, admin rights, or prior compromise is needed, only the existing protocol-handler registration and the flawed boundary check.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to check for an exact match or a proper separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator from the `options` parameter passed to `_resolveWithin`). Add regression tests covering sibling directories whose names share a prefix with the repository root.

### Proof of Concept
1. Victim has a repository cloned at `/Users/victim/Documents/repo` and, elsewhere on disk, a differently-named directory sharing the prefix, e.g. `/Users/victim/Documents/repo-secrets/id_rsa`.
2. Attacker sends the victim a link:
   `x-github-client://openrepo?url=https://github.com/owner/repo&filepath=../repo-secrets/id_rsa`
3. Victim clicks the link; `parseAppURL` returns `{ name: 'open-repository-from-url', url, filepath: '../repo-secrets/id_rsa', ... }` (app/src/lib/parse-app-url.ts:98-124).
4. `Dispatcher.openRepositoryFromUrl` (app/src/ui/dispatcher/dispatcher.ts:1957-1972) passes the repo path and `filepath` to `resolveWithin`.
5. In `_resolveWithin` (app/src/lib/path.ts:64-72), `resolved`/`realResolved` becomes `/Users/victim/Documents/repo-secrets/id_rsa`, and `realResolved.startsWith(realRoot)` (`realRoot = /Users/victim/Documents/repo`) evaluates `true` due to the shared string prefix, so the function returns the path instead of `null`.
6. `shell.showItemInFolder(resolved)` reveals `id_rsa` from outside the repository to the user/attacker-directed flow, confirming the boundary bypass.
