### Title
Shared `BalanceHandler` instance across recursive/nested precompile calls corrupts EVM `StateDB` balances relative to the bank keeper - (File: precompiles/common/precompile.go, precompiles/common/balance_handler.go)

### Summary
The reported TribalChief bug is a class of "cached/stale local state used for a later critical operation, causing divergence from the authoritative source of truth." The Cosmos EVM analog is the `BalanceHandler.prevEventsLen` bookmark used to translate x/bank events into `StateDB` balance mutations for stateful precompiles. This repository already contains an integration test explicitly describing this as a bug: [1](#0-0) .

### Finding Description
`BalanceHandler` records `prevEventsLen = len(ctx.EventManager().Events())` in `BeforeBalanceChange`, then on `AfterBalanceChange` replays only the bank events emitted after that index to apply corresponding `StateDB.AddBalance`/`SubBalance` calls [2](#0-1) .

The correctness of this mechanism depends on `prevEventsLen` accurately bookmarking "the event count immediately before this specific precompile call's native action starts." When a precompile call triggers another precompile call recursively (e.g., a contract calling into a precompile method which itself performs an EVM call back into a precompile, or a precompile method invoking `CallEVM`/nested precompile logic), if the same `BalanceHandler` instance is reused across the outer and inner calls, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, discarding the outer call's original bookmark. This is functionally identical to TribalChief's bug: a value captured at one point in time (`currentMultiplier`/`prevEventsLen`) is later invalidated by an intervening state change, but the consuming logic still trusts the stale/overwritten local value instead of re-deriving it from ground truth per call-frame.

The test explicitly documents this: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [1](#0-0) . The test uses a debug precompile that calls `p.GetBalanceHandler()` rather than obtaining a freshly-scoped handler per invocation [3](#0-2) , and the reproduction triggers a `callback` re-entrant call pattern via a caller contract [4](#0-3) .

By contrast, `RunNativeAction`/`runNativeAction` in the common precompile scaffolding creates a brand-new `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` [5](#0-4) , which is the correct pattern (each call frame gets its own bookmark). Whether every production precompile (`staking`, `distribution`, `gov`, `ics20`, `slashing`, `erc20`) consistently obtains a fresh handler per call, versus caching/reusing one on the `Precompile` struct across nested/re-entrant invocations, is the exact question this analog hinges on — the debug precompile's `GetBalanceHandler()` naming strongly suggests a getter for a *stored* field rather than a factory call, which is the vulnerable pattern being demonstrated.

### Impact Explanation
If `prevEventsLen` is silently overwritten by an inner/nested precompile call:
- When the inner call returns and the outer call's `AfterBalanceChange` runs, it will replay events starting from the *inner* call's later bookmark, causing bank-emitted `coin_spent`/`coin_received`/fractional-balance events belonging to the outer call to be **skipped entirely** (never applied to `StateDB`), or conversely cause double-application/duplication of events already consumed by the inner call, depending on ordering.
- This produces a durable divergence between the x/bank ledger (source of truth for native coin balances) and the EVM `StateDB` balance view exposed to `eth_call`/`eth_getBalance`/contract `SELFBALANCE`/subsequent EVM transfers within the same or later transactions, since `StateDB` balances feed directly into subsequent EVM balance checks and transfers.
- This is an unauthorized/incorrect balance-accounting divergence for spendable user value across native and EVM-visible balances — matching the "Critical unauthorized... duplication... accounting corruption of spendable user value across native balances, EVM balances... precompile-mediated assets" impact category, reachable by an ordinary unprivileged user simply calling a contract that makes a nested/recursive precompile call (a pattern achievable via any contract wrapper calling a precompile that itself performs another CallEVM/precompile invocation, e.g. staking/distribution/ERC20 precompiles called from within one another or via a proxy contract).

### Likelihood Explanation
The bug is triggered purely by ordinary, permissionless transaction flow — any user deploying a contract that performs recursive/nested precompile calls (a common pattern for contracts wrapping precompile calls, e.g., calling ERC20 precompile from within a staking/distribution precompile flow, or a caller contract invoking a precompile method twice within one call frame) can trigger it. The presence of a dedicated integration test reproducing exactly this scenario with a debug precompile and a "callback" caller contract [6](#0-5)  indicates the maintainers are aware of and actively verifying this exact class of bug, suggesting either a very real historical vulnerability or an in-progress fix under test.

### Recommendation
Ensure every precompile obtains a `BalanceHandler` scoped strictly to its own call frame (never sharing/caching one across nested/recursive precompile invocations) — e.g. always use `BalanceHandlerFactory.NewBalanceHandler()` fresh per `Run`/native-action invocation as done in `precompiles/common/precompile.go`, and audit/remove any pattern where a `Precompile` struct stores and reuses a single `BalanceHandler` instance (as the `GetBalanceHandler()` naming in the debug precompile suggests) across potentially re-entrant or nested calls. Consider stacking/pushing bookmarks (a stack of `prevEventsLen` values) rather than a single overwritable field, so nested calls cannot clobber the outer frame's bookmark.

### Proof of Concept
The repository's own test is the reproduction: `TestRecursivePrecompileCallsWithDebugPrecompile` deploys a debug precompile and a caller contract that invokes `callback(0)`, triggering nested precompile calls through the same `BalanceHandler` instance, and asserts on the resulting event/debug-count invariants [6](#0-5) . A full exploit against a production precompile (e.g., ERC20 or staking precompile with nested calls) could not be fully verified in this pass because I was unable to inspect `precompiles/{staking,distribution,gov,ics20,slashing,erc20}/*.go`'s exact `GetBalanceHandler` implementation before the session ended; this should be verified directly by inspecting how each precompile constructs/caches its `BalanceHandler` versus the factory-based pattern in `precompiles/common/precompile.go`.

// It records the current number of events in the context to later process balance changes

	bh.prevEventsLen = len(ctx.EventManager().Events())
}
