## Analysis

The seed report's core broken invariant is: an authorization check meant to bind a privileged action to *one specific identity* (`msg.sender == txn.sender`) was replaced by an overly-broad check (`txnSender == sender || txnSender == address(this)`), letting anyone impersonate the trusted identity as long as they hit the *coarser* branch of the condition.

Searching Hyperbridge's cross-chain message-authentication code for the same shape of bug — a privileged-message path that checks only the **coarse** identity (source chain) and omits the **fine-grained** identity (sender module/pallet address) — turns up an exact analog in `ExtrinsicIntents.onAccept`.

### Title
Governance/admin request kinds in IntentGatewayV2 are authenticated only by source chain id, not by sender module — allowing any module on the coprocessor chain to trigger `UpgradeContract`, `SweepDust`, `UpdateParams`, or `NewDeployment` - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept` authenticates `RedeemEscrow`/`RefundEscrow` requests by checking **both** the source chain and the specific sender module address (`_authenticate`), but for the privileged branch (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`) it checks **only** that `incoming.request.source == hyperbridge()`, never verifying `incoming.request.from`. Any entity capable of dispatching an ISMP POST request whose `source` equals the Hyperbridge coprocessor chain id and whose `to` targets this gateway's address is treated as trusted governance.

### Finding Description
`_authenticate` demonstrates the correct pattern used elsewhere in the codebase — checking the specific peer module address, not just the chain: [1](#0-0) 

The privileged branch of `onAccept`, however, drops the module-level check and authenticates solely on chain identity: [2](#0-1) 

Compare this to `HyperFungibleToken.onAccept`, which correctly checks both the registered chain **and** `request.from` before minting: [3](#0-2) 

In `ExtrinsicIntents.onAccept`, `keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())` only proves the message originated from *some* module on the Hyperbridge coprocessor chain — it does not prove the message came from the specific trusted governance/admin module on that chain. This is structurally identical to the reported bug: the guard collapses to a broader-than-intended equivalence class (`sender == expected` broadened to `sender == anything from expected chain`), just as `validateSender` broadened `txSender == sender` to also accept `txSender == address(this)`.

The four request kinds gated only by this weak check are severe:
- `NewDeployment` → overwrites `_instances[keccak256(chain)]`, i.e., the trusted peer-gateway address used by `_authenticate` for `RedeemEscrow`/`RefundEscrow` on that chain — see `_addDeployment`: [4](#0-3) 
- `UpdateParams` → rewrites `host`, `dispatcher`, `priceOracle`, `surplusShareBps`, `protocolFeeBps`: [5](#0-4) 
- `SweepDust` → transfers arbitrary ERC20/native amounts to an attacker-chosen `beneficiary`: [6](#0-5) 
- `UpgradeContract` → full proxy takeover via `ERC1967Utils.upgradeToAndCall` with attacker-supplied `initData`: [7](#0-6) 

### Impact Explanation
If any module/pallet on the Hyperbridge coprocessor chain other than the intended governance module can cause an ISMP POST request to be dispatched with `source = hyperbridge()` and `to = <this gateway's address>`, that message is accepted as authoritative governance by every deployed `IntentGatewayV2` instance across all connected EVM chains. This directly satisfies the bounty's "false state acceptance" / "unauthorized transaction or execution" impact class: it allows redirecting escrow custody (`NewDeployment`), draining protocol dust to an attacker (`SweepDust`), altering fee/dispatcher parameters (`UpdateParams`), or replacing the entire contract implementation (`UpgradeContract`) — a complete loss-of-funds / loss-of-control scenario for every order routed through the gateway.

### Likelihood Explanation
The likelihood hinges on whether any Hyperbridge-chain-side actor other than the dedicated governance module can dispatch a POST request with `source == hyperbridge()` and an attacker-chosen `to`/`body`. The codebase already shows a `HyperbridgeWithdrawalModule` pallet that accepts messages *from* the coprocessor and forwards funds based on decoded instructions, confirming that generic message dispatch from the coprocessor chain to arbitrary `to` addresses is a supported, exercised code path in this system: [8](#0-7) . Because `onAccept` never verifies `request.from` for the privileged branch, the security of every `IntentGatewayV2` deployment collapses to "trust any module capable of posting from the Hyperbridge chain," which is a materially weaker guarantee than intended and inconsistent with the stronger check already used in the sibling `HyperFungibleToken` app and in `_authenticate` itself.

### Recommendation
Add an explicit `from`-address check to the privileged branch of `onAccept`, mirroring `_authenticate`, e.g. store a `governanceModule` (or dedicated `ModuleId`) bound to the Hyperbridge chain and require `keccak256(incoming.request.from) == keccak256(governanceModule)` in addition to the `source == hyperbridge()` check, for `NewDeployment`, `UpdateParams`, `SweepDust`, and `UpgradeContract`.

### Proof of Concept
1. Any pallet/module on the Hyperbridge coprocessor chain (state machine id equal to `IDispatcher(host()).hyperbridge()`) dispatches an ISMP POST request with `to = <IntentGatewayV2 address>` and `body = bytes1(uint8(RequestKind.UpgradeContract)) || abi.encode(maliciousImpl, initData)`.
2. The message passes standard ISMP proof verification (it is a real, correctly-proven message from the Hyperbridge chain — no relayer/prover collusion needed, only that *some* module on that chain, not necessarily the intended governance one, can post an arbitrary message).
3. On delivery, `EvmHost` calls `IntentGatewayV2.onAccept`, which reaches the branch at `evm/src/apps/intentsv2/ExtrinsicIntents.sol:289-309`.
4. The check `keccak256(incoming.request.source) == keccak256(hyperbridge())` passes (true — it did originate from that chain).
5. `kind == RequestKind.UpgradeContract` executes `ERC1967Utils.upgradeToAndCall(maliciousImpl, initData)`, handing full control of the gateway (and all escrowed funds) to the attacker's implementation — without ever having validated which module on the Hyperbridge chain actually authored the message.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}
