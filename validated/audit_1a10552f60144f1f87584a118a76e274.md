### Title
Operator reimbursement can be reassigned by mutating unsigned outputs of the payout tx (SIGHASH_SINGLE|ANYONECANPAY leaves outputs 1+ unauthenticated) - (File: core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the payout transaction's single input with a `SinglePlusAnyoneCanPay` (BIP341 SIGHASH_SINGLE|ANYONECANPAY) signature that only commits to input 0 and output 0 (the user payout). Outputs 1 (anchor) and 2 (OP_RETURN with the fronting operator's x-only pubkey) are not covered by the sighash, so anyone observing the unconfirmed transaction can rebroadcast a byte-identical input/output0 transaction with a different set of trailing outputs while reusing the same valid witness. `Verifier::update_finalized_payouts` then trusts `get_first_op_return_output`, which just returns the first `is_op_return()` output in iteration order with no check that there is exactly one OP_RETURN or that it sits at the canonical index 2.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk[idx] == operator_xonly_pk that actually funded output0 of the mined payout_tx for withdrawal idx`. This should hold because `create_payout_txhandler` ( [1](#0-0) ) deterministically places exactly one OP_RETURN at output index 2, but nothing enforces that invariant when the chain is read back.

Root cause 1 — signature does not cover outputs 1/2: The witness set by `set_p2tr_key_spend_witness(&user_sig, 0)` is a Schnorr signature computed over the taproot sighash for `SinglePlusAnyoneCanPay`, which the aggregator explicitly requires: [2](#0-1) . Per BIP341, SIGHASH_SINGLE only commits to the input being spent (via ANYONECANPAY: outpoint/amount/scriptPubKey/sequence of just that input) and to the single output at the same index as the input (index 0 here). It does not commit to the total output count or to any other output content. Consequently, output 1 (anchor) and output 2 (OP_RETURN with the operator pubkey) can be freely replaced, reordered, duplicated, or padded with an extra decoy OP_RETURN by anyone holding the broadcast transaction, and the same witness remains a valid signature.

Root cause 2 — unchecked OP_RETURN scan on read-back: `get_first_op_return_output` performs an unguarded linear scan for the first OP_RETURN-shaped script: [3](#0-2) . `Verifier::update_finalized_payouts` uses exactly this function on the mined transaction to determine and persist `payout_payer_operator_xonly_pk`: [4](#0-3) . There is no check that the payout transaction contains exactly one OP_RETURN or that it is at output index 2 as `create_payout_txhandler` intends.

Exploit flow: Operator A builds and broadcasts the legitimate payout tx (output0=payout to user, output1=anchor, output2=OP_RETURN(A)). An attacker (no privileges required — anyone who can observe the mempool and broadcast transactions) copies the transaction, keeps input 0 and output 0 byte-identical (required because SIGHASH_SINGLE commits to it), and constructs a competing transaction spending the same withdrawal UTXO with a new output ordering: output1 = OP_RETURN(G) (an honest operator's pubkey), output2 = anchor, output3 = OP_RETURN(A) (decoy). The witness copied from A's broadcast tx remains a valid Schnorr signature for this new transaction because the ANYONECANPAY+SINGLE sighash never covered outputs 1..n. If the attacker's version gets mined instead of (or in place of) A's original — e.g., via a higher-fee replacement or a mempool race, since nothing marks the transaction non-replaceable at the Bitcoin-consensus level for this purpose — `get_first_op_return_output` picks OP_RETURN(G) first, and `update_finalized_payouts` persists `payout_payer_operator_xonly_pk = G` for withdrawal idx i, even though G never funded it.

Downstream, `PayoutCheckerTask`/`Operator::handle_finalized_payout` for operator G's own node (polling `get_first_unhandled_payout_by_operator_xonly_pk`) will find this withdrawal registered under G and proceed with kickoff/asserts to claim reimbursement from the deposit's move-to-vault UTXO, even though G never funded the payout. Operator A, the true funder, is not recorded and cannot claim reimbursement for its own broadcast BTC spend on that withdrawal.

No existing guard blocks this: `is_kickoff_malicious` only compares `kickoff_data.operator_xonly_pk` against whatever `payout_payer_operator_xonly_pk` was stored in the DB ( [5](#0-4) ) — it trusts the same tainted value produced by `update_finalized_payouts` and does not re-derive/re-validate the canonical output-2/single-OP_RETURN structure.

### Impact Explanation
This is a fund-diversion / mis-attribution bug: an honest operator (G) can be recorded as the funder of a payout it never paid, allowing G's node to later claim reimbursement (BTC) from the deposit's move-to-vault UTXO for a withdrawal it did not front, while the operator that actually paid (A) is left with no recorded credit for that withdrawal and cannot be reimbursed for BTC it already sent to the user. This matches the Critical categories "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed." The attack is repeatable across any withdrawal whose payout tx is still unconfirmed/replaceable in the mempool, and across any pair of operators, since the bug lies in generic sighash/parsing logic, not in per-deposit state.

### Likelihood Explanation
Preconditions: a payout tx must be observable pre-confirmation (public mempool data, no special access needed) and the attacker must be able to get their modified/competing transaction mined instead of (or before) the original — via fee bump/RBF or a propagation race. The attacker pays normal Bitcoin fees; no operator credentials, verifier keys, or collateral are required to build and broadcast the competing transaction. The one nontrivial constraint is winning the race/replacement against the original broadcaster, which depends on mempool/miner policy (full-RBF adoption, propagation timing) rather than any cryptographic or protocol defense in Clementine — i.e., the codebase itself provides no defense at all, so likelihood is governed purely by Bitcoin-network conditions outside this repo's control.

### Recommendation
Do not rely on a bare `SinglePlusAnyoneCanPay` signature plus unauthenticated output scanning to attribute payout funding. Options: (1) Commit to the OP_RETURN/operator pubkey inside the signed message, e.g. by using `SIGHASH_ALL` (or otherwise covering all outputs) for the payout input so the operator identity output is authenticated by the user's signature or by an operator-provided co-signature; (2) When reading the payout tx back on-chain in `update_finalized_payouts`, enforce the canonical structure produced by `create_payout_txhandler` exactly — require exactly one OP_RETURN output and require it at the fixed index (2), rejecting/ignoring txs that don't match, instead of taking the first OP_RETURN found; (3) Additionally verify output1/anchor and overall output count/order match the expected template before trusting the parsed operator pubkey.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
