## Title
Tokenfactory `DenomAllowList` restriction can be bypassed by routing transfers of restricted denoms through CosmWasm `BankMsg::Send`, since `wasmkeeper.BankCoinTransferrer` calls `bank.SendCoins` directly instead of the `x/bank` `MsgSend` handler - (File: `sei-wasmd/x/wasm/keeper/keeper.go`)

### Summary
This mirrors the THORWallet finding: a transfer restriction (`isBridgedTokensTransferLocked`) is enforced only in the `transfer`/`transferFrom` entry points, while an alternate value-moving path (bridge `send`, which internally does `mint`/`burn`) skips the check entirely. On Sei, the analogous restriction is the tokenfactory `DenomAllowList`, which gates who may send/receive a given `factory/...` denom. That restriction is enforced in `x/bank`'s `MsgSend`/`MsgMultiSend` handlers, but the underlying `BaseSendKeeper.SendCoins` primitive does **not** enforce it itself. CosmWasm contracts move bank coins through `wasmkeeper.BankCoinTransferrer.TransferCoins`, which calls `SendCoins` directly and only checks `IsSendEnabledCoins`/`BlockedAddr` - never `IsInDenomAllowList`.

### Finding Description
The allow-list check for tokenfactory denoms is implemented as `IsInDenomAllowList` [1](#0-0)  and is only invoked from the `x/bank` message server's `Send` and `MultiSend` handlers: [2](#0-1) 

The underlying keeper primitive that actually moves the balances, `BaseSendKeeper.SendCoins`, performs no allow-list or restriction check of its own - it only calls `SendCoinsWithoutAccCreation`: [3](#0-2) 

CosmWasm contracts that emit `BankMsg::Send` submessages are routed through `wasmkeeper.BankCoinTransferrer.TransferCoins`, which replicates only part of the `MsgSend` handler's checks (`IsSendEnabledCoins` and `BlockedAddr`) and calls `SendCoins` directly - it never calls `IsInDenomAllowList`: [4](#0-3) 

This transferrer is wired into the wasm message dispatcher/bank handler used for every CosmWasm contract execution (`sei-wasmd/x/wasm/keeper/msg_dispatcher.go`, `sei-wasmd/x/wasm/keeper/options.go`), so any CosmWasm contract can trigger a `BankMsg::Send` of a restricted tokenfactory denom on behalf of the contract's own balance, bypassing the sender/receiver allow-list check that `MsgSend` enforces.

### Impact Explanation
Tokenfactory admins configure `DenomAllowList` specifically to restrict who may hold/transfer a given denom (analogous to THORWallet's `transferAllowedContract`/`isBridgedTokensTransferLocked` invariant intended to block speculative trading pre-TGE or otherwise segregate token movement). By depositing the restricted denom into a simple CosmWasm contract (e.g., a generic escrow/vault/AMM-like contract that does `BankMsg::Send` on request) and having the contract forward it to an arbitrary, non-allow-listed address, a user can move restricted-denom balances to addresses that `MsgSend` would have rejected. This breaks the same invariant class as the original report: "unless explicitly permitted, holders of a restricted denom should not be able to move it to arbitrary addresses." It does not create new supply, but it defeats an admin-configured transfer control that projects may rely on to prevent unauthorized distribution or premature liquidity/trading of a token.

### Likelihood Explanation
Reaching this path requires only: (1) a token factory admin has set a `DenomAllowList` for their denom (a normal admin operation via `MsgSetDenomMetadata`/allow-list message), and (2) any user instantiates or uses an existing CosmWasm contract that sends bank coins via `BankMsg::Send` (no special privilege needed - any address can instantiate/execute a wasm contract on Sei, and many generic vault/escrow contract patterns exist). This makes it reachable by an ordinary CosmWasm user/public-RPC client without validator or governance involvement, satisfying the "confirmed root cause + concrete unauthorized transfer" bar, though it depends on a project having actually configured a `DenomAllowList` for a live denom.

### Recommendation
Update `wasmkeeper.BankCoinTransferrer.TransferCoins` (and any other direct `SendCoins` call sites reachable from unprivileged execution, e.g. IBC transfer keeper if applicable) to also call `IsInDenomAllowList` for both the sender and recipient, mirroring the checks performed in `x/bank`'s `MsgSend`/`MultiSend` handlers, or refactor `BaseSendKeeper.SendCoins` itself to perform the allow-list check so all callers are covered uniformly.

### Proof of Concept
1. Tokenfactory admin creates denom `factory/{admin}/RESTRICTED` and sets a `DenomAllowList` containing only `{admin, contractA}` via the tokenfactory/bank allow-list mechanism.
2. Admin funds `contractA` (a simple CosmWasm contract capable of issuing `BankMsg::Send`, e.g., a generic forwarder/vault) with `factory/{admin}/RESTRICTED` coins.
3. Attempt to `MsgSend` the restricted coins directly from `contractA`'s owner-controlled EOA to `userB` (not in allow list) - this is rejected by `msgServer.Send`'s `IsInDenomAllowList` check, confirming the restriction is active.
4. Instead, call `contractA`'s execute entrypoint to have it emit `BankMsg::Send{ to_address: userB, amount: [restricted_coin] }`.
5. This message is processed by `wasmkeeper`'s bank handler via `BankCoinTransferrer.TransferCoins`, which only checks `IsSendEnabledCoins`/`BlockedAddr` and calls `SendCoins` directly - the transfer succeeds and `userB` (not on the allow list) receives the restricted denom, confirming the bypass.

*(Note: I was unable to execute this scenario against a live node/test harness in this environment; the analysis is based on static code tracing of `msg_server.go`, `send.go`, and `keeper.go` as cited above. A Devin session with repository/test access would be needed to confirm end-to-end via an actual wasm contract execution test.)*

```go
// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
```

```go
func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}
```

```go
// TransferCoins transfers coins from source to destination account when coin send was enabled for them and the recipient
// is not in the blocked address list.
func (c BankCoinTransferrer) TransferCoins(parentCtx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amount sdk.Coins) error {
	em := sdk.NewEventManager()
	ctx := parentCtx.WithEventManager(em)
	if err := c.keeper.IsSendEnabledCoins(ctx, amount...); err != nil {
		return err
	}
	if c.keeper.BlockedAddr(toAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", toAddr.String())
	}

	sdkerr := c.keeper.SendCoins(ctx, fromAddr, toAddr, amount)
	if sdkerr != nil {
		return sdkerr
	}
	for _, e := range em.Events() {
		if e.Type == sdk.EventTypeMessage { // skip messages as we talk to the keeper directly
			continue
		}
		parentCtx.EventManager().EmitEvent(e)
	}
	return nil
}
```
