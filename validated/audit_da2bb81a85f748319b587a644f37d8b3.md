### Title
Nested/Reentrant Precompile Calls Cause `BalanceHandler` to Double-Apply Bank Events to StateDB, Corrupting EVM Balances - (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` records a snapshot of the event-manager length (`prevEventsLen`) at the start of a precompile call and, after execution, replays `ctx.EventManager().Events()[prevEventsLen:]` to apply bank `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` deltas onto the EVM `StateDB` [1](#0-0) . This is the exact structural analog of the LivenessGuard `ownersBefore` bug: a "before" snapshot is captured once at call entry, but if a nested/reentrant precompile call occurs during execution of the outer call's native action, the nested call's own `AfterBalanceChange` already consumes and applies the events it produced. Because the outer call's snapshot index (`prevEventsLen`) predates the entire nested execution, the outer call's `AfterBalanceChange` later re-slices `events[outerPrevEventsLen:]`, which still includes all events already consumed and applied by the inner call — causing those bank balance deltas to be applied to `StateDB` a second time.

### Finding Description
`Precompile.runNativeAction` creates a fresh `BalanceHandler` per precompile invocation via the factory and calls `BeforeBalanceChange` immediately before invoking the native action, then `AfterBalanceChange` immediately after [2](#0-1) . `BeforeBalanceChange` stores `len(ctx.EventManager().Events())` at that instant [3](#0-2) , and `AfterBalanceChange` slices the *global, monotonically growing* event list from that stored index to the current length to determine which events to translate into `StateDB.AddBalance`/`SubBalance` calls [4](#0-3) .

The problem: the event manager's event slice is shared and cumulative across the entire EVM call stack for the transaction. If, while executing the outer precompile's native action, a **nested** precompile call occurs (e.g., an ERC-20 `_beforeTokenTransfer` hook that calls the distribution precompile's `claimRewards`, or an ICS-20 transfer whose execution triggers another precompile call — both patterns are exercised in this repo's own reentrancy test contracts, e.g. `contracts/solidity/ERC20RecursiveRevertingPrecompileCall.sol` and `InterchainSenderCaller.sol`) [5](#0-4) [6](#0-5) , that inner call gets its own fresh `BalanceHandler`, records its own (later) `prevEventsLen`, and on completion applies (and effectively "consumes") the bank events produced during its own execution to `StateDB`.

When control returns to the outer call and its native action finishes, the outer `BalanceHandler.AfterBalanceChange` slices from the *outer's* earlier `prevEventsLen` to the current event count. This range still contains the events that were already processed and applied by the inner call's `AfterBalanceChange`. The outer handler therefore re-parses and re-applies those same `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events onto `StateDB`, resulting in balances being incremented/decremented a second time for value that was already reflected in `StateDB` by the inner call.

The project's own integration tests demonstrate awareness of exactly this recursive-precompile-call hazard (`evmd/tests/integration/balance_handler/balance_handler_test.go`, explicitly commented as testing "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB") [7](#0-6) , and the recursive ICS-20/ERC-20 precompile-call test suites confirm that nested precompile calls (staking → distribution, ERC20 hooks → distribution/staking, ICS-20 → internal transfers) are a real, reachable execution path in production precompiles, not merely test-only constructs [8](#0-7) .

### Impact Explanation
`StateDB.AddBalance`/`SubBalance` calls driven by double-applied bank events directly desynchronize the EVM-visible balance from the actual `x/bank` (and `x/precisebank`) ledger balance within the same transaction. Because `StateDB` is authoritative for subsequent balance checks and transfers within the same EVM execution (and its resulting balance changes are what get committed/journaled for the transaction), an attacker who orchestrates a nested/reentrant precompile call sequence can cause `StateDB` to register more (or less) balance than what was actually moved in the bank keeper. This is an accounting-corruption / duplication-of-spendable-value bug: EVM-visible balances can be artificially inflated relative to real bank balances, which can subsequently be spent via ordinary EVM transfers/ERC-20 precompile calls, extracting value that was never actually escrowed/backed — a critical, irreversible accounting-corruption issue between native balances and EVM balances.

### Likelihood Explanation
The repository's own reentrancy test contracts (`StakingReverter.sol`, `ERC20RecursiveRevertingPrecompileCall.sol`, `InterchainSenderCaller.sol`, `ICS20Caller.sol`) and integration test suites (`ics20_recursive_precompile_calls_test.go`, `balance_handler_test.go`) all already exercise nested/recursive precompile call patterns as normal, unprivileged, user-triggerable contract behavior (deploy a contract, have its token hooks or callback logic re-enter a precompile). No reentrancy guard around `BalanceHandler`/`prevEventsLen` or around nested `runNativeAction` invocations was found in the reviewed code. This makes the vulnerable path realistically reachable by any user deploying a contract that chains precompile calls (staking/distribution/gov/ics20/erc20) inside a hook or callback triggered by an outer precompile call.

### Recommendation
Do not rely on a single mutable `prevEventsLen` snapshot that spans potentially nested precompile executions. Options:
- Maintain a stack of `prevEventsLen` values (one per nesting depth), analogous to the LivenessGuard fix of "keep a separate list of ownersBefore for each level of reentrancy," so each call only ever processes the events it itself produced, and nested calls "consume" their event range before returning control to the outer handler's slice.
- Alternatively, have inner precompile calls "advance" the outer handler's `prevEventsLen` when they finish consuming a sub-range of events, so ranges never overlap.
- Add an explicit non-reentrancy guard on `runNativeAction`/`BalanceHandler` to detect and reject nested precompile-triggered balance-changing calls within the same StateDB call.

### Proof of Concept
1. Deploy an ERC-20-like contract analogous to `ERC20RecursiveRevertingPrecompileCall.sol`/`ICS20Caller.sol` whose transfer hook or callback invokes a second stateful precompile (e.g., distribution `claimRewards`, or a second ICS-20 transfer) while the outer precompile call (e.g., staking `delegate` or the first ICS-20 `transfer`) is still executing (`Precompile.runNativeAction` has not yet returned) [5](#0-4) .
2. The inner precompile call gets a fresh `BalanceHandler`, records `prevEventsLen = M`, executes, and its `AfterBalanceChange` applies bank events `[M:M+k]` to `StateDB` [4](#0-3) .
3. Control returns to the outer call's native action, which continues and finishes; its `AfterBalanceChange` (with `prevEventsLen = N < M`) processes `events[N:]`, which still includes the `[M:M+k]` events already applied in step 2, re-applying the same `AddBalance`/`SubBalance` deltas to `StateDB` a second time [9](#0-8) .
4. Compare the resulting `StateDB` balance for the involved address against the actual `x/bank`/`x/precisebank` balance after the transaction commits — the values will diverge, demonstrating the duplication of the bank-event-driven balance delta on the EVM side.

Note: I could not fully trace whether every production precompile (staking, distribution, gov, ics20, slashing, erc20) reaches this exact double-apply path in a single transaction versus only the test/debug precompile scaffolding due to tool-call limits; the underlying `prevEventsLen`/event-slicing mechanism in `precompiles/common/balance_handler.go` and `precompiles/common/precompile.go` is however confirmed and is shared by all of them [2](#0-1) .
