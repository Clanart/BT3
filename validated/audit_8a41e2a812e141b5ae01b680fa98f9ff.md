This confirms the pattern: `Wallet._generate_unsigned_transaction` (and `CATWallet.generate_unsigned_spendbundle`) fetch a supplied `coin`/`coins` set and directly call `puzzle_for_puzzle_hash`/`inner_puzzle_for_cat_puzhash` to sign it — the puzzle derivation itself will simply fail if the puzzle hash isn't derivable by that wallet's keys, so cross-wallet coin selection is self-limiting for signing. The clearer BOLA analog is in `split_coins`, where `target_coin_id` is resolved via a global, wallet-unscoped lookup.

### Title
Missing object-level authorization on `target_coin_id` in `split_coins` allows spending/selecting coins from any wallet via wallet-scoped RPC endpoint - (File: chia/wallet/fungibility_manager.py)

### Summary
The `split_coins` RPC endpoint accepts a `wallet_id` and a `target_coin_id`, but `FungibilityManager.split_coins` resolves `target_coin_id` through a coin lookup that is not scoped to the specified `wallet_id`, and never validates that the fetched coin actually belongs to that wallet before folding it into the outgoing transaction.

### Finding Description
`WalletRpcApi.split_coins` passes the caller-supplied `wallet_id` and `target_coin_id` straight to `FungibilityManager.split_coins`: [1](#0-0) 

Inside `FungibilityManager.split_coins`, the target coin is looked up purely by coin id from the global `WalletCoinStore`, with no `wallet_id` filter and no check that `optional_coin.wallet_id == wallet.id()`: [2](#0-1) 

The fetched `coin` (which may belong to a *different* wallet than the one specified by `wallet_id`, e.g. another CAT wallet, a DID wallet, or a clawback coin) is then added directly to the `coins` set passed to `wallet.generate_signed_transaction`: [3](#0-2) 

`get_coin_record` in `WalletCoinStore` performs a bare `coin_name` lookup across the entire `coin_record` table, with no `wallet_id` predicate: [4](#0-3) 

This is the same bug class as the CVE: an endpoint that is supposed to operate only on objects owned by/scoped to the caller's specified context (`wallet_id`) instead accepts an arbitrary object id (`target_coin_id`) and performs the operation on whatever object that id resolves to globally, without an ownership/scope check.

### Impact Explanation
The wallet daemon manages multiple wallets (XCH, CAT, DID, etc.) under one key. Because `get_fungible_wallet` only checks that the target `wallet_id` is a `Wallet`/`CATWallet` type (not that the coin belongs to it), an RPC caller can request `split_coins` for `wallet_id=<CAT wallet A>` while supplying `target_coin_id` for a coin actually tracked under a completely different wallet (e.g. a different CAT wallet, a coin under a wallet with a different `coin_type`, or one whose `wallet_id` differs from the one specified). Downstream code path (e.g. `CATWallet.generate_unsigned_spendbundle`) treats every coin in the `coins` set as belonging to the target asset type, potentially melting/misinterpreting the wrong asset's coin, causing unintended spends, incorrect change/asset accounting, or loss of coins from the unintended wallet. Because signing still depends on being able to derive a puzzle for that coin's puzzle hash, actual fund loss is limited to cases where the caller (or the local wallet daemon) can derive/spend the puzzle hash of the "other" wallet's coin — but the core defect (unauthorized cross-wallet object selection without an ownership check) is confirmed and matches the reported BOLA bug class (CWE-639) precisely: the endpoint trusts a caller-supplied object id without verifying it is scoped to the object's asserted owner (`wallet_id`).

### Likelihood Explanation
Any local wallet RPC caller who can invoke `split_coins` (a standard wallet RPC command usable via CLI/RPC as shown by `chia/cmds/coins.py` `SplitCMD`) can supply an arbitrary `target_coin_id`; no additional privilege beyond normal wallet RPC access is required, and the test suite (`chia/_tests/wallet/rpc/test_wallet_rpc.py::test_split_coins`) demonstrates the endpoint is reachable and unauthenticated at the object level (only wallet-type is checked, not coin ownership).

### Recommendation
In `FungibilityManager.split_coins`, after fetching `optional_coin`, verify `optional_coin.wallet_id == wallet.id()` (and matching `wallet_type`/`coin_type` as appropriate) before using the coin; raise a `ValueError` (mirroring the existing "Could not find coin with ID" error) if the coin does not belong to the specified wallet, and audit `combine_coins`' `target_coin_ids` path (`chia/wallet/fungibility_manager.py` lines around 100-111) for the same missing ownership check.

### Proof of Concept
1. Create two wallets under the same key: a CAT wallet A (id=2) and CAT wallet B (id=3), each with unspent coins.
2. Note a coin id belonging to CAT wallet B, `coin_B`.
3. Call `split_coins` RPC with `wallet_id=2` (CAT wallet A) and `target_coin_id=coin_B.name()`.
4. Observe that `FungibilityManager.split_coins` (`chia/wallet/fungibility_manager.py:47`) successfully resolves `coin_B` via `coin_store.get_coin_record(target_coin_id)` without checking it belongs to wallet 2, and proceeds to build a transaction using `coin_B` as if it were wallet A's coin — demonstrating the missing object-level authorization check between `wallet_id` and `target_coin_id`.
