### Title
`gasBufferEstimate` (bidTxGasBuffer) misconfiguration can make the auction BidTx generator produce an under-funded gas limit, causing the winning bid's settlement transaction to revert - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
The KIP-249 auction module computes the gas limit for the `BidTx` that settles a winning auction bid using a single governance/contract-controlled numeric parameter, `gasBufferEstimate` (called `bidTxGasBuffer` in the Go code), read directly from the on-chain `AuctionEntryPoint` system contract. This is structurally the same bug class as the reported Morpho `maxGas` issue: an operator/contract-settable numeric "budget" parameter directly drives whether a critical multi-step transaction (match/settle) succeeds or reverts, with no client-side sanity bound, and it can be changed by whoever controls the `AuctionEntryPoint` contract (analogous to "governance").

### Finding Description
`BidPool.getBidTxGasLimit` computes the gas limit of the generated `BidTx` as:
```
gasLimit = max(intrinsicGas + bid.CallGasLimit + buffer, floorDataGas)
``` [1](#0-0) 

`buffer` here is `bp.bidTxGasBuffer`, which is populated purely from an on-chain read of the `AuctionEntryPoint` contract's `gasBufferEstimate()` view function: [2](#0-1) 

This value is refreshed every block via `updateAuctionInfo`, with no minimum/maximum sanity check performed by the client: [3](#0-2) 

The buffer is meant to cover the entry point contract's own overhead beyond the forwarded `callGasLimit` (input verification, signature checks, bid-taking accounting, gas refund to proposer) as shown in the reference/mock implementation: [4](#0-3) 

Exactly like Morpho's `maxGas`:
- If `gasBufferEstimate` is set too low, the `BidTx`'s total gas limit will be insufficient to cover the entry point's bid-taking/settlement/refund bookkeeping that runs *after* the forwarded call, causing the entire `BidTx` (and the atomically-bundled searcher payment) to run out of gas and revert.
- If it is set too high, the resulting `BidTx.Gas()` could approach or exceed practical block gas limits, or simply waste block space, but more importantly a too-low value is the exploitable direction here.
- There is only one hard cap enforced client-side — `BidTxMaxCallGasLimit` on `bid.CallGasLimit` — but no lower/upper bound check on `bidTxGasBuffer` itself, and no verification that `intrinsicGas + CallGasLimit + buffer` is actually sufficient for the entry point contract's real execution path: [5](#0-4) [6](#0-5) 

### Impact Explanation
Because `gasBufferEstimate` is a single contract-read numeric parameter with no client-side floor/ceiling validation, an under-estimated value systematically causes winning `BidTx`s to run out of gas inside the `AuctionEntryPoint.call()` execution after the forwarded call has already spent its `callGasLimit`. Depending on the entry-point contract's exact ordering of bid-taking vs. call-forwarding vs. refund, this can result in:
- Searcher's target call executing without the bid amount actually being collected/settled (fee/auction-settlement abuse), or
- The winning bid transaction reverting entirely, so the auction winner never gets their transaction included/settled despite paying gas, degrading the auction subsystem's core guarantee.

This matches the "gasless or auction settlement theft" / "state divergence" categories called out as in-scope impact for this analog search.

### Likelihood Explanation
`gasBufferEstimate` is read from the `AuctionEntryPoint` contract on every block by `updateAuctionInfo`, and the value flows unchecked into `getBidTxGasLimit`, which is invoked both when a bid is added to the pool (`AddBid`) and when the bid transaction is generated at block-building time (`GetBidTxGenerator`): [7](#0-6) [8](#0-7) 
Any legitimate governance/admin update to `AuctionEntryPoint` (or a bug in the constant chosen there) that under-estimates the true overhead will deterministically and repeatedly trigger this failure mode for every subsequent winning bid until corrected — no attacker action beyond normal bid submission is required.

### Recommendation
- Enforce a sane minimum and maximum bound on `bidTxGasBuffer` read from the entry point contract before using it in `getBidTxGasLimit`, rather than trusting the on-chain value unconditionally.
- Add monitoring/alerting when the computed `BidTx` gas limit is close to known execution costs of the entry point's bid-taking/refund logic, and consider a client-side floor derived from measured contract overhead rather than purely from the on-chain-configurable value.
- Ensure the actual `AuctionEntryPoint.call()` implementation performs bid-taking either atomically with, or safely rolled back alongside, the forwarded call, so that an out-of-gas in the post-call accounting cannot separate "searcher's call executed" from "bid collected."

### Proof of Concept
Not directly executable from static review alone — the exploitability depends on the exact bytecode of the deployed (non-mock) `AuctionEntryPoint` contract's `call()` function, which was not available in the indexed codebase (the only implementation shown, `AuctionEntryPointMock.sol`, has its bid-taking/refund logic commented out). Conceptually:
1. `AuctionEntryPoint.setGasBufferEstimate` (or equivalent governance action) sets `gasBufferEstimate` too low relative to the real cost of `_checkAndTakeBid` + refund logic.
2. A searcher submits a valid bid with `CallGasLimit` at or near `BidTxMaxCallGasLimit`.
3. `BidPool.getBidTxGasLimit` computes `gasLimit = intrinsicGas + CallGasLimit + buffer`, which is insufficient once the forwarded call actually consumes close to `CallGasLimit` gas, leaving too little gas for the post-call bid-taking/refund logic.
4. The generated `BidTx` executes the forwarded call successfully but then runs out of gas in post-call bookkeeping, reverting the whole transaction (or, if bid-taking happens before the forwarded call and isn't rolled back atomically, the target call may still execute without gas being fully accounted/refunded).

Given the uncertainty about the exact production `AuctionEntryPoint` bytecode (only the mock is indexed), I recommend verifying this against the actual deployed contract logic before treating this as confirmed exploitable; the underlying client-side pattern (unchecked, contract-supplied gas parameter feeding a critical settlement transaction's gas limit) is confirmed present in the code reviewed.

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) getBidTxGasLimit(bid *auction.Bid) (uint64, error) {
	bp.auctionInfoMu.RLock()
	buffer := bp.bidTxGasBuffer
	bp.auctionInfoMu.RUnlock()

	data, err := system.EncodeAuctionCallData(bid, bp.auctionEntryPointVersion)
	if err != nil {
		return 0, err
	}

	rules := bp.ChainConfig.Rules(big.NewInt(int64(bid.BlockNumber)))
	intrinsicGas, err := types.IntrinsicGas(data, nil, nil, false, rules)
	if err != nil {
		return 0, err
	}
	floorDataGas := uint64(0)
	if rules.IsPrague {
		floorDataGas, err = blockchain.FloorDataGas(types.TxTypeEthereumDynamicFee, data, 0)
		if err != nil {
			return 0, err
		}
	}

	return max(intrinsicGas+bid.CallGasLimit+buffer, floorDataGas), nil
```

func (a *AuctionModule) updateAuctionInfo(num *big.Int) bool {
	auctioneer := common.Address{}
	auctionEntryPointAddr := common.Address{}
	auctionEntryPointVersion := ""
	bidTxGasBuffer := uint64(0)

	defer func() {
		a.bidPool.updateAuctionInfo(auctioneer, auctionEntryPointAddr, auctionEntryPointVersion, bidTxGasBuffer)
	}()

	header := a.Chain.GetHeaderByNumber(num.Uint64())
	if header == nil {
		return false
	}
	_, err := a.Chain.StateAt(header.Root)
	if err != nil {
		return false
	}

	backend := backends.NewBlockchainContractBackend(a.Chain, nil, nil)

	// 1. Read auction entry point address
	auctionEntryPointAddr, err = system.ReadActiveAddressFromRegistry(backend, system.AuctionEntryPointName, num)
	if err != nil {
		return false
	}

	if auctionEntryPointAddr == (common.Address{}) {
		return false
	}

	// 2. Read auctioneer address
	auctioneer, err = system.ReadAuctioneer(backend, auctionEntryPointAddr, num)
	if err != nil {
		return false
	}

	if auctioneer == (common.Address{}) {
		return false
	}

	// 3. Read gas buffer estimate
	bidTxGasBuffer, err = system.ReadGasBufferEstimate(backend, auctionEntryPointAddr, num)
	if err != nil {
		return false
	}

	// 4. Read AUCTION_VERSION to pick the right EIP-712 typehash and ABI for bids targeting this entry point.
	auctionEntryPointVersion, err = system.ReadAuctionVersion(backend, auctionEntryPointAddr, num)
	if err != nil {
		return false
	}

	return true
