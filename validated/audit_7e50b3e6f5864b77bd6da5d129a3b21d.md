### Title
Path-containment check uses substring comparison instead of boundary-aware check, allowing sibling-directory escape in `resolveWithin` - (File: `app/src/lib/path.ts`)

### Summary
The reported Frax bug is a broken formula invariant: a multiply/divide inversion that only "happens" to be safe because a scaling factor is currently fixed at `1`. The GitHub Desktop analog is the same class of bug — a security check whose correctness silently depends on an assumption that isn't actually enforced. In `_resolveWithin`, the containment invariant ("resolved path must be inside root") is implemented with a raw string `startsWith()` comparison instead of a path-boundary-aware comparison (i.e. comparing against `root + path.sep`). This is the classic "prefix path traversal" bug: it happens to work for paths that end up as true subdirectories, but silently breaks — exactly like multiplying instead of dividing "breaks" once the price stops being 1 — whenever the resolved path lands in a sibling directory whose name happens to share the root directory name as a string prefix (e.g. `repo` vs `repo-evil`, `repo.bak`, `repo-old`).

### Finding Description
`resolveWithin` / `_resolveWithin` is Desktop's canonical helper for making sure a user- or remote-supplied relative path can't escape a given root directory: [1](#0-0) 

The final check is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
`String.prototype.startsWith` performs a raw character comparison with no awareness of path segment boundaries. If `realRoot` is `/Users/victim/Documents/GitHub/reponame` and an input path segment causes `resolved` to walk up and back down into a sibling directory such as `/Users/victim/Documents/GitHub/reponame-evil/payload`, the check still returns `true`, because the string `"reponame-evil/payload"` starts with `"reponame"`.

This is directly analogous to the audited invariant violation: a correctness property ("A is contained in B") that is implemented with an operation that is only correct under an unstated extra condition (here: that no sibling directory shares the root's name as a prefix; in the Frax report: that price == 1). The function's own doc comment claims a stronger guarantee than the code delivers: "the resolved path does not reside underneath the root path this method will return null" — but a same-string-prefix sibling is not underneath the root, and the function fails to reject it.

`resolveWithin` is used to gate access to the filesystem from attacker-influenced input, most notably in the `x-github-client://openRepo` / `github-desktop://` deep-link handler: [2](#0-1) 

Here `filepath` comes straight from a URL that a remote page or link can construct (`openRepositoryFromUrl`). The code rejects absolute paths, then relies entirely on `resolveWithin(repository.path, filepath)` to keep the final path inside the repository before calling `shell.showItemInFolder(resolved)`. Because the containment check can be defeated by a `..`-based path landing on a same-prefixed sibling directory, a crafted deep link can cause Desktop to open the OS file browser targeting a file outside the intended repository.

### Impact Explanation
This does not require local/physical access, admin rights, or pre-existing malware — the only attacker requirement is that the victim click a `github-desktop://` / `x-github-client://` deep link (an explicitly in-scope vector: "a link or deep link the user clicks"). The corrupted value is the boolean containment decision produced by `_resolveWithin`, which downstream code treats as a hard security guarantee ("this path is safe, it's inside the repo"). Any consumer of `resolveWithin` that performs a filesystem operation (read, reveal, or write) based on that boolean inherits the flaw. In the confirmed dispatcher path this results in the file-explorer being pointed at a location outside the repository root chosen by the attacker (subject to a naming coincidence with an existing sibling directory), which is a "read/access outside the repo" primitive of exactly the category called out as valid impact.

### Likelihood Explanation
Exploitability depends on the existence of a sibling directory whose name is a superstring-prefix of the cloned repository's directory name (e.g. `repo`, `repo-backup`, `repo.old`, `repo2`) — a very common real-world pattern for developers who keep backups or forks side-by-side. Given that, the rest of the chain (crafting a `..`-relative `filepath` query parameter in a deep link) is fully attacker-controlled and requires no unusual victim behavior beyond the normal, documented deep-link click flow that Desktop already supports.

### Recommendation
- Fix `_resolveWithin` in `app/src/lib/path.ts` to use a boundary-aware comparison, e.g.:
  ```
  const rootWithSep = realRoot.endsWith(path.sep) ? realRoot : realRoot + path.sep
  return realResolved === realRoot || realResolved.startsWith(rootWithSep) ? resolved : null
  ```
- Audit every call site of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` (`dispatcher.ts`, `app-store.ts`, `copilot-conflict-context.ts`) to confirm none of them assume containment based on the current substring semantics.
- Add regression tests (mirroring the existing `clone-path-safety-test.ts` style) specifically for sibling-directory-prefix escapes, not just `..`/absolute-path escapes.

### Proof of Concept
1. Victim has previously cloned a repo to `/Users/victim/Documents/GitHub/reponame` and, independently, has an unrelated folder `/Users/victim/Documents/GitHub/reponame-secrets` (a very plausible naming pattern, e.g. a manual backup).
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/owner/reponame?filepath=..%2Freponame-secrets%2Fid_rsa`
3. `openRepositoryFromUrl` resolves the repository, sees `filepath = "../reponame-secrets/id_rsa"`, confirms it is not absolute, then calls `resolveWithin(repository.path, filepath)`.
4. Inside `_resolveWithin`, `resolve(root, "../reponame-secrets/id_rsa")` yields `/Users/victim/Documents/GitHub/reponame-secrets/id_rsa`, and `realResolved.startsWith(realRoot)` evaluates `true` because the string `"reponame-secrets/id_rsa"` starts with `"reponame"`.
5. `shell.showItemInFolder(resolved)` opens the OS file browser pointed at `id_rsa` inside the sibling directory — a location the containment check was supposed to prevent access to.

**Confidence note:** I verified the flawed `startsWith` check and its use in `dispatcher.ts` directly. I identified two additional call sites (`app-store.ts`, `copilot-conflict-context.ts`) via `grep_search` but was not able to read their surrounding code before running out of tool calls, so I cannot confirm whether those paths lead to a write (rather than just read/reveal) primitive; that should be verified in a follow-up review.

    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
