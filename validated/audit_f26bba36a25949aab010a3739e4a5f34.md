### Title
`ThresholdKeys::read` deserializes attacker-supplied secret shares and verification shares without any consistency check, embedding an attacker-known group key - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the picklescan report — where deserializing attacker bytes silently embeds a malicious payload that executes later — `ThresholdKeys::<C>::read` reconstructs full signing key material from raw bytes while performing only structural checks. It never verifies that `secret_share` is consistent with `verification_shares[i]` (i.e. `C::generator() * secret_share == verification_shares[&i]`), and it derives `group_key` purely from the attacker-controlled verification shares. A crafted blob therefore yields a fully operational `ThresholdKeys` whose group private key is known to the attacker.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i`, an interpolation selector, a `secret_share` scalar, and `n` verification shares, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) only checks:
- `verification_shares.len() == n` (line 355),
- every participant index `<= n` (lines 361-365),
- `t == n` for `Interpolation::Constant` (lines 367-373),

then computes `group_key` as the Lagrange/Constant-interpolated sum of `verification_shares[1..=t]` (lines 376-378) and stores `secret_share` verbatim.

There is no check that `secret_share` is the evaluation of the shared polynomial at `i` — i.e. that `generator() * secret_share` relates to `verification_shares`. Additionally, the shares are read with `Ciphersuite::read_G` (line 622), which does not reject the identity point (unlike `Curve::read_G` in crypto/frost/src/curve/mod.rs:125-131).

An attacker who supplies these bytes constructs a polynomial `f` with a known secret `x = f(0)`, sets `verification_shares[j] = generator() * f(j)` for `j = 1..=n` and `secret_share = f(i)` for the victim's index `i`. Deserialization succeeds and returns valid-looking `ThresholdKeys` with `group_key = generator() * x`.

### Impact Explanation
The deserialized keys are used directly for FROST signing (`ThresholdKeys` is the input to `ThresholdView`/`sign`). Since the attacker chose the underlying polynomial, they know the group private key `x` corresponding to the victim's `group_key`. They can:
- forge arbitrary signatures under the victim's threshold group key,
- spend any funds controlled by that key,

while the victim believes the key material is legitimate. This satisfies "concrete signing of an unintended message / forged signature" — the malicious payload (an attacker-known key) is smuggled in through deserialization and only "detonates" when the keys are later used.

### Likelihood Explanation
The serialized form is self-describing (curve ID, t, n, i, interpolation, secret share, verification shares) with no MAC, checksum of consistency, or binding to how the keys were produced. Anywhere serialized `ThresholdKeys` cross a trust boundary — restored from an untrusted backup, received from a peer, or loaded from attacker-writable storage — an unprivileged party can substitute a blob they fully control. Deserialization succeeds silently; there is no signature or proof-of-origin on the key blob.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify consistency of the private and public halves:

```rust
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::...)?;
}
```

For `Interpolation::Constant`, also verify the reconstructed secret: the constant-interpolated group key implies a group secret derivable from the coefficient list, so `generator() * secret_share` should equal the per-participant share implied by those coefficients. Optionally reject identity verification shares via `Curve::read_G`-style checks for the first `t` shares that determine `group_key`.

### Proof of Concept
```rust
// Attacker: pick a known polynomial over C::F
let x = /* attacker-known scalar */;
// degree t-1 polynomial f with f(0) = x; compute shares s_j = f(j)
for j in 1..=n { shares.push(f(j)); }
let vshares: Vec<C::G> = shares.iter().map(|s| C::generator() * s).collect();

// Serialize a ThresholdKeys blob for victim index i
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes());
blob.extend(n.to_le_bytes());
blob.extend(i.to_le_bytes());
blob.push(1); // Interpolation::Lagrange
blob.extend(shares[i - 1].to_repr().as_ref());
for v in &vshares { blob.extend(v.to_bytes().as_ref()); }

// Victim deserializes — succeeds despite attacker origin
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::generator() * x); // attacker knows x
// keys.sign(...) produces signatures under group_key; attacker can forge any
// signature under it independently of the victim.
```

Root cause: `ThresholdKeys::read`/`ThresholdKeys::new` treat the `secret_share` ↔ `verification_shares` relationship as trusted, so a deserialization input can carry a hidden attacker-chosen key payload that is later "executed" by the signing protocol.
