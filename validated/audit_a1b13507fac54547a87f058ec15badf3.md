### Title
Overpaid native-token fee on `EvmHost.dispatch`/`fundRequest` is silently trapped in the Host, never refunded to the sender - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept `msg.value` and forward the *entire* amount into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. `swapETHForExactTokens` only consumes the ETH needed to buy the exact `fee`/`amount` output and refunds the remainder — but the refund target is `msg.sender` of the router call, i.e. the `EvmHost` contract itself, not the original caller who supplied the ETH. `EvmHost` never re-forwards that leftover ETH to the user. This is the direct analog of the reported `_depositToBentoBox` bug: a function that receives native token for a computed/variable amount, uses only what's needed, but has no closing "refundETH" step, so the unused portion is stranded in the contract instead of returned to the depositor.

### Finding Description
In the reported Sushi Trident bug, ETH sent by the user is either under- or over-used relative to a dynamically computed `underlyingAmount`, and any unused ETH is not returned because there is no `refundETH()` call at the end of the batch. The Hyperbridge analog is structurally identical: any caller of `dispatch()` or `fundRequest()` who overestimates the ETH needed to cover `post.fee`/`get.fee`/`amount` (e.g., due to slippage buffer, price movement between quote and execution, or simply rounding up) has their entire `msg.value` sent into the router call. The router uses only `amounts[0] <= msg.value` and returns `msg.value - amounts[0]` back to `msg.sender`, which in this call context is `EvmHost`, not the user. There is no code afterward in `dispatch`/`fundRequest` that checks `address(this).balance` or forwards leftover ETH back to `_msgSender()`/`post.payer`. [1](#0-0) [3](#0-2) 

The only exit valve for native ETH sitting in `EvmHost` is `withdraw()`, restricted to `_hostParams.hostManager` (cross-chain governance only): [4](#0-3) 

So any accidental overpayment permanently becomes host revenue, extractable only by governance, not the original payer.

### Impact Explanation
Every `dispatch()`/`fundRequest()` caller who pays with native token and supplies more `msg.value` than the router needs for the exact fee swap loses the difference — it is neither refunded to them nor tracked as owed to them. Since `getAmountsIn` (used internally by the router) reflects the live AMM price at execution time, any caller who pads `msg.value` for slippage safety (a normal, recommended practice, as advised in the docs for GET/POST dispatch) will systematically overpay and lose the excess on every call. This is direct, immediate loss of user funds with no recovery path other than governance discretion.

### Likelihood Explanation
High. Any application built on `HyperApp.dispatchWithFeeToken`/direct `dispatch{value: ...}()` (as documented for both POST and GET messaging) that pads `msg.value` above the exact quoted fee — standard defensive practice given AMM price volatility — will trigger this on essentially every call. No malicious relayer, prover, or governance actor is required; it is triggered purely by a normal unprivileged user/app calling a public entrypoint with a conservative `msg.value`.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compute the leftover native balance received back from the router (or use `amounts[0]` return value) and forward it back to `_msgSender()` via a low-level call, reverting on failure — mirroring the recommended `refundETH` pattern from the cited report.

### Proof of Concept
1. Attacker/normal user calls `EvmHost.dispatch{value: X}(post)` where `post.fee = F` and `X > amountIn` required by the router to buy `F` fee tokens at the current AMM price (e.g., user pads 20% for slippage protection, or price moves favorably between quote and inclusion).
2. Inside `dispatch`, `swapETHForExactTokens{value: X}(F, path, address(this), ...)` consumes only `amounts[0] < X` ETH, and the router refunds `X - amounts[0]` ETH to `msg.sender` of the swap call, which is `EvmHost`.
3. `dispatch()` returns without forwarding any ETH back to the caller; the leftover `X - amounts[0]` remains in `EvmHost`'s balance.
4. The user has no function to reclaim this amount; only cross-chain governance via `HostManager`/`withdraw()` can move it out, and only to a beneficiary of governance's choosing. [5](#0-4)

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
