### Title
Type confusion in `ThresholdKeys` deserialization: attacker-controlled interpolation tag and unbound secret share produce semantically different key material from identical byte streams - (File: crypto/dkg/src/lib.rs)

### Summary

The external report describes type confusion (CWE-843): a tag determines how subsequent bytes are interpreted, and misinterpretation corrupts state. Serai's `ThresholdKeys::read` in `crypto/dkg/src/lib.rs` exhibits the same bug shape: a single attacker-controlled tag byte (`interpolation[0]`) selects between two incompatible interpretations of the remaining bytes (`Interpolation::Constant(Vec<F>)` vs `Interpolation::Lagrange`), and the deserializer never cryptographically binds the deserialized `secret_share` to the participant's `verification_shares[i]` or to the resulting `group_key`. An unprivileged party able to feed bytes to `ThresholdKeys::read` (listed as an in-scope entry point) can install key material whose mathematical meaning — interpolation factors, group key, and effective share — differs from what the honest key-generation protocol produced, causing the victim to sign under a group key the attacker controls. [1](#0-0) 

### Finding Description

`ThresholdKeys::read` parses, in order: a curve ID, `t`, `n`, participant index `i`, a one-byte interpolation discriminant, then (for `Constant`) `n` scalars, then `secret_share`, then `n` verification-share points. It delegates to `ThresholdKeys::new`, which only checks structural constraints (`verification_shares.len() == n`, participant indices `<= n`, `t == n` for `Constant`) and recomputes `group_key` as `sum(verification_shares[l] * interpolation_factor(l))` over participants `1..=t`. [2](#0-1) 

Two distinct gaps create the confusion:

1. **Tag-based reinterpretation**: The identical tail of scalar bytes means `Interpolation::Constant`'s coefficient vector under tag `0`, versus nothing (stateless Lagrange) under tag `1`. For `t == n` sets (where `Constant` is legal, enforced at crypto/dkg/src/lib.rs:368-371), flipping or crafting the tag changes `interpolation_factor(i, included)` from the canonical Lagrange coefficient to an arbitrary attacker-chosen coefficient `c[i-1]`. The same key share is therefore *mathematically reinterpreted* as a different share of a different polynomial — the exact "same bytes, different type/meaning" confusion of the libxslt bug, transposed onto scalar-vs-coefficient interpretation.

2. **No secret-share ↔ verification-share binding**: Nothing in `read`/`new` verifies `C::generator() * secret_share == verification_shares[i]`. `group_key` is derived solely from the attacker-controlled `verification_shares`. A fully crafted serialization therefore yields a `ThresholdKeys` where `secret_share` and `verification_shares` are mutually consistent (attacker sets `verification_shares[i] = G * secret_share`) and consistent under whichever interpolation interpretation the tag selects — but correspond to no honestly generated key. The code itself acknowledges this failure mode in FROST: `crypto/frost/src/sign.rs:492-494` notes the only way to reach "everyone had a valid share yet the signature was still invalid" is "to deserialize a semantically invalid FrostKeys", i.e., inconsistent deserializations are anticipated but not prevented. [3](#0-2) 

### Impact Explanation

An attacker who can cause a participant to load crafted bytes through `ThresholdKeys::read` (serialized key backups, key-recovery/migration inputs, or any integrator path that round-trips keys) obtains a working threshold key whose `group_key` is fully attacker-determined: the attacker chooses `secret_share` and all `verification_shares` to be a consistent sharing of a known secret `s'`, so `group_key = G * s'`. When the victim's FROST `AlgorithmMachine` signs with these keys, `view()` interpolates the attacker-known `secret_share` and produces signature shares that *do* verify — the victim has become a co-signer for a group key the attacker fully controls. Because the attacker also knows `s'` outright, they can forge the complete threshold signature alone or coerce the victim into producing valid partial signatures for transactions under an attacker-owned key (e.g., a multisig registering an attacker-controlled Bitcoin address via the `networks/bitcoin` wallet path). This satisfies the "concrete signing of an unintended message" acceptance criterion: the victim signs shares for a group key that is not the DKG-generated key they believe they hold.

The Constant/Lagrange tag confusion additionally permits mutating an honest serialization (tag `1` → tag `0` plus appended coefficient list, for `t == n` sets) so the victim's share is interpolated by attacker-chosen coefficients, silently changing the effective key without any integrity check catching it — `write`/`serialize` emit no MAC or commitment over the key material.

### Likelihood Explanation

Medium. Exploitation requires attacker influence over bytes passed to `ThresholdKeys::read` — the prompt explicitly designates this entry point as reachable from untrusted input. Within Serai's architecture, threshold keys are serialized/deserialized for storage, recovery, and migration (`serialize()`/`read()` exist precisely for round-tripping key material to untrusted media such as coordinator storage or backup channels). The attack requires no DKG participation, no threshold collusion, and no cryptographic breaks — only byte-level control of one deserialization. Downstream, `recover_key` (`crypto/dkg/recovery/src/lib.rs:37-84`) and FROST signing both trust the loaded structure; the only mitigation is `complete()`'s share verification, which passes when the attacker crafts self-consistent key material. The impact ceiling is signing under an attacker-controlled group key rather than exfiltrating the honest share, which keeps this below High.

### Recommendation

- In `ThresholdKeys::read`, after constructing the keys, verify `C::generator() * secret_share == verification_shares[i]` (applying `interpolation_factor` is unnecessary since `i`'s raw share should equal its verification share before view-time interpolation — verify `G * secret_share * interpolation_factor(i, 1..=t)` consistency or, minimally, the raw share/point binding) and reject on mismatch.
- Authenticate serialized `ThresholdKeys` (MAC or signature keyed by an export secret) so the interpolation tag and all fields are integrity-protected.
- Consider making the interpolation method a parameter of `read` (expected-type argument) rather than an embedded tag, eliminating the reinterpretation entirely.

### Proof of Concept

```rust
// Victim deserializes attacker-supplied ThresholdKeys (e.g., from a restored backup)
let t: u16 = 2; let n: u16 = 3; let i = Participant::new(1).unwrap();

// Attacker crafts a fully self-consistent but attacker-known key
let s_attacker = Secp256k1::random_nonzero_F(&mut OsRng); // attacker knows this
let mut shares = HashMap::new();
// Lagrange interpolation factors for the t-subset {1,2} evaluated publicly
for l in 1..=n { shares.insert(Participant::new(l).unwrap(), G * attacker_chosen_share(l)); }
shares.insert(i, G * s_attacker);

// Serialized: ID || t || n || i || tag=1 (Lagrange) || s_attacker || verification_shares
let keys = ThresholdKeys::<Secp256k1>::read(&mut crafted_bytes).unwrap();
assert_eq!(keys.group_key(), G * attacker_known_secret); // attacker-controlled group key

// Victim signs; share verifies against verification_shares[i] == G*s_attacker
let (machine, pp) = AlgorithmMachine::new(Schnorr::new(...), keys).preprocess(&mut OsRng);
// ... victim emits a valid FROST share under group_key the attacker controls,
// enabling the attacker to assemble a signature for an address they own.
// Alternatively, flipping tag 1 -> 0 on an honest t==n serialization reinterprets
// the share under attacker-chosen Constant coefficients without detection.
```
