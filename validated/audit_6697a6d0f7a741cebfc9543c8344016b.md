### Title
Path-containment check in `resolveWithin()` uses unanchored `String.startsWith()`, allowing sibling-directory escape via a crafted `x-github-client://openRepo` deep link - ([File: app/src/lib/path.ts])

### Summary
The bug pattern in the Native report is a *broken boundary check*: a per-item guard (`exchange rate must not increase by more than 1%`) is evaluated in a way that can be satisfied for each individual entry while the check is silently bypassed in aggregate (duplicate assets). The GitHub Desktop analog is structurally identical in spirit: a boundary/containment check (`resolved path must be inside the repository root`) is implemented with a comparison that is *satisfied on paper* (string prefix match) while the semantic invariant ("strictly inside the directory") is not actually enforced, because the check does not require a path separator (or equality) after the shared prefix.

### Finding Description
`_resolveWithin()` in `app/src/lib/path.ts` computes the canonical (symlink-resolved) forms of the root and the target path and then validates containment purely with a string prefix comparison: [1](#0-0) 

```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of path segments. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo` and an attacker can make `resolved` point at `/Users/victim/Documents/GitHub/myrepo-secrets/...`, the check passes (`"...myrepo-secrets"` *starts with* `"...myrepo"`) even though `myrepo-secrets` is a completely different, sibling directory, not a subdirectory of `myrepo`. This is the exact same class of failure as the reported bug: the invariant that is supposed to be enforced ("no duplicate/aliased item can slip past the per-item gate") is not actually what the comparison implements ("string containment" ≠ "directory containment").

This helper is the single security gate reused across several attacker-reachable call sites:

- `app/src/ui/dispatcher/dispatcher.ts:1940-1973` — `openRepositoryFromUrl()` handles the `x-github-client://openRepo/...` custom protocol handler (a deep link the user clicks). It extracts an untrusted `filepath` from the URL/query string (parsed in `app/src/lib/parse-app-url.ts`), calls `resolveWithin(repository.path, filepath)` and, if not `null`, calls `shell.showItemInFolder(resolved)`: [2](#0-1) 

- `app/src/lib/copilot-conflict-context.ts:390-407` and `app/src/lib/stores/app-store.ts:7233-7259` reuse the same `resolveWithin()` gate to decide whether it is safe to read (or, in the app-store case, **write** LLM-generated conflict-resolution content) to a file path.

Because the containment check can be satisfied for a path that resolves into a *sibling* directory of the repository (e.g. `../<repoName>-something/...`), an attacker who controls the `filepath` query parameter of a deep link — or, in the Copilot flow, the `path` returned in a conflict-resolution response — can make Desktop operate on a file outside of the actual repository working directory while the code believes the "no path escapes the repo" invariant was verified.

### Impact Explanation
- Via the `x-github-client://openRepo` deep link, `filepath` is fully attacker-controlled (crafted link that the user is enticed to click, matching the "link/deep link" attacker-control primitive). A crafted `filepath` such as `../<reponame>-important/id_rsa` (or any sibling of the repo folder present on disk, e.g. another cloned repo, a build/output directory, or a folder created by a previous clone with a longer name) bypasses `resolveWithin()`'s containment check and causes Desktop to call `shell.showItemInFolder()` on a location outside the intended repository — a file-path disclosure/reveal outside the repo boundary that the code explicitly tries to prevent (`log.error('Prevented attempt to open path outside of the repository root...')` is the intended behavior, but the guard is bypassable).
- In `app-store.ts`'s Copilot conflict-resolution flow, the same helper gates a `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` call. If the `path` field returned by the conflict-resolution engine (derived from repository content, which can be adversarially crafted by a malicious repository/PR through prompt-injection in conflicted file content) names a sibling directory of the repo, this becomes a **file write outside the repository** with attacker-influenced content — a stronger, corruption-class impact than the deep-link case, though it depends on the Copilot resolution pipeline actually emitting attacker-influenced paths, which is a secondary, less-verified dependency (the write path was not fully traced during this review because tool budget was exhausted; treat this part as a hypothesis, not a confirmed exploit chain).

### Likelihood Explanation
The deep-link path is the most directly exploitable and lowest-effort: it requires no repository content manipulation, only a URL the victim clicks, and the sibling-directory precondition (a directory on disk whose name has the repo's folder name as a literal prefix) is common in real-world GitHub Desktop usage (e.g. `Documents/GitHub/desktop` next to `Documents/GitHub/desktop-old`, `desktop-backup`, `desktop-fork`, etc., or an attacker luring the victim into first creating such a folder as part of a multi-step social-engineering-free setup, e.g. by having the victim clone the malicious repo under a name that is a prefix of an existing folder). No admin rights, local access, or leaked credentials are required — only the deep-link click and normal Desktop file-open handling, satisfying the "unprivileged... deep link... file read outside the repo" acceptance criteria.

### Recommendation
Fix the containment predicate in `_resolveWithin()` (`app/src/lib/path.ts`) to require an actual path-segment boundary, not just a string prefix, e.g.:
```ts
return (
  realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
) ? resolved : null
```
(using the platform-appropriate separator for the win32/posix variants). This mirrors the report's own recommendation of "don't rely on a loosely-defined equivalence (duplicate assets) — enforce the actual uniqueness/boundary invariant (sorted, deduplicated address set)"; here the fix is to enforce the actual directory-boundary invariant instead of a raw string-prefix comparison.

### Proof of Concept
1. Victim has an existing folder `~/Documents/GitHub/example` (a normal, unrelated Desktop repository) alongside a legitimately cloned/attacker-supplied repository at `~/Documents/GitHub/example-evil` that contains a sensitive file, e.g. `~/Documents/GitHub/example-evil/notes.txt` (or the attacker arranges for the victim's own sibling folder/file to be the target, e.g. `~/Documents/GitHub/example-secrets/id_rsa` created by some other legitimate workflow).
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/someorg/example?filepath=..%2Fexample-evil%2Fnotes.txt`
3. Desktop's protocol handler parses the URL (`app/src/lib/parse-app-url.ts`) and calls `dispatcher.openRepositoryFromUrl()`, which opens/selects the `example` repository and then calls:
   `resolveWithin(repository.path /* .../example */, '../example-evil/notes.txt')`
4. Inside `_resolveWithin`, `resolved` becomes `.../GitHub/example-evil/notes.txt`; `realRoot` = `.../GitHub/example`; `realResolved` = `.../GitHub/example-evil/notes.txt`. Because `"...GitHub/example-evil/notes.txt".startsWith("...GitHub/example")` is `true`, the function returns the resolved path instead of `null`.
5. `shell.showItemInFolder(resolved)` is invoked, revealing/opening a file that resides entirely outside the `example` repository — demonstrating the escape of the intended containment boundary via a link the user clicked, with no local access or malware required. [3](#0-2) [4](#0-3)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
