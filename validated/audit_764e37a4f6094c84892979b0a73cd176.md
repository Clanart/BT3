### Title
Blame proof ECDH key is emitted for messages whose proof-of-possession was never verified, leaking the decryption key for a victim's encrypted share — ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary

Analogous to GHSA-vx3h-qwqw-r2wq (a crafted input causes a server-side operation whose error path reflects sensitive internal information), `KeyMachine::calculate_share` returns an `EncryptionKeyProof` — containing the ECDH shared key that decrypts the offending ciphertext — inside `PedPoPError::InvalidShare` *before* the message's proof-of-possession (PoP) has been verified. The code's own comments state that a failed PoP must yield `blame: None` ("if this batch verifier is reused, we know its the PoP aspect which failed, and therefore to use None for the blame"), yet the scalar-canonicality check short-circuits with `blame: Some(...)` first. [1](#0-0) 

### Finding Description

In `Encryption::decrypt`, the ECDH shared key and a DLEq proof binding it are computed unconditionally, before the queued PoP batch verification ever runs: [2](#0-1) 

In `calculate_share`, the decrypted bytes are checked for scalar canonicality and, on failure, the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` immediately — while `msg.pop.batch_verify(...)` results are only consumed later by `batch.verify_with_vartime_blame()`: [3](#0-2) 

The PoP exists precisely to stop this class of leak, per the code's own threat analysis: without it, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X... Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob." The mitigation fails because the `from_repr` error path publishes `bX` without waiting for the PoP check that would have rejected Eve's forged message. [4](#0-3) 

Attack (Eve is a DKG participant — the protocol's intended adversary, and needs no secret knowledge):

1. Alice publishes `EncryptedMessage` `{ key: Ka, pop: sig_A, msg: C }` encrypting her share `f_Alice(Bob)` to Bob. `pop_challenge` binds `from = Alice`, `Ka`, and `C`. [5](#0-4) 
2. Eve submits to Bob, as *her* share slot, the forged message `{ key: Ka, pop: <garbage>, msg: C XOR δ }` where `δ` is chosen so the decrypted plaintext is a non-canonical scalar encoding.
3. `Decryption::decrypt` computes `blame.key = ECDH(bob_enc_priv, Ka)` — identical to the key protecting Alice's real message — then `from_repr` fails on the mangled plaintext, returning `blame: Some(...)` before the batched PoP (which would have failed, yielding `blame: None`) is ever evaluated.
4. Bob returns/publishes the blame proof per the blame protocol (`EncryptionKeyProof::read`/`AdditionalBlameMachine` consumption in `processor/src/key_gen.rs`). Anyone holding Alice's ciphertext `C` (transmitted on authenticated-but-broadcast channels) now holds the keystream key and recovers Alice's share `f_Alice(Bob)`. [6](#0-5) 

### Impact Explanation

Confidential DKG share disclosure. `f_Alice(Bob)` is secret material: it is Bob's share contribution from dealer Alice, and PedPoP encrypts per-(sender,recipient) precisely to keep these shares private. Leaking one share of one dealer's polynomial reduces the hiding bound on Bob's aggregate secret share and, repeated across dealers (Eve can replay every victim's ciphertext in her own slot), exposes each honest dealer's contribution to Bob. If Bob's key share is ever partially exposed, or combined with threshold-adjacent leaks, this materially weakens the resulting `ThresholdKeys` — matching the report's class of "internal request details leaked through the error path." Severity Medium: requires a protocol participant slot and leaks one share per message rather than the full key.

### Likelihood Explanation

Deterministic: Eve fully controls `δ` and her slot's `pop`, needs only Alice's public ciphertext, and the `from_repr` failure at `crypto/dkg/pedpop/src/lib.rs:480` fires unconditionally before the PoP batch check at line 493. No races, no collusion, no leaked keys required.

### Recommendation

Verify the PoP before returning any blame material. Options:

- Evaluate the PoP for each message before decrypting/`from_repr` checks in `calculate_share` (e.g., a small `BatchVerifier` pass on PoPs first, or per-message `pop.verify` on the error path), and only attach `blame: Some(...)` to errors raised after a confirmed-valid PoP.
- Alternatively, defer construction of `EncryptionKeyProof` in `Encryption::decrypt` until after batch verification succeeds, or re-check the specific message's PoP inside the `InvalidShare`/`from_repr` error branch before including the proof.

### Proof of Concept

```rust
// Eve is participant E; Alice is participant A; victim Bob runs calculate_share.
// Alice's honest message to Bob:
let alice_msg: EncryptedMessage<C, SecretShare<C::F>> = /* key = Ka, pop = PoP_A, msg = C */;

// Eve crafts her slot's message: reuse Ka, garbage PoP, malleated ciphertext.
let mut forged = alice_msg.clone();
forged.msg.as_mut()[0] ^= 0x80; // flip high bit so decoded scalar is non-canonical
forged.pop = SchnorrSignature::read(&mut &[0u8; 64][..]).unwrap(); // invalid PoP

let mut shares: HashMap<Participant, _> = /* other honest shares */;
shares.insert(EVE, forged);

// Bob:
match bob_key_machine.calculate_share(&mut OsRng, shares) {
    // Returns here: from_repr fails BEFORE PoP batch verification runs.
    Err(PedPoPError::InvalidShare { participant: EVE, blame: Some(proof) }) => {
        // proof.key == ECDH(bob_enc_priv, Ka) — the keystream key for Alice's real
        // ciphertext C. Publishing `proof` (as the blame flow requires) lets anyone
        // decrypt Alice's share: plaintext = ChaCha20(cipher(context, proof.key)) ^ C
    }
    _ => unreachable!(),
}
```

Note on scope/certainty: this assumes a malicious DKG participant is an acceptable adversary (the PedPoP threat model explicitly designs blame and the PoP around malicious participants, and the prompt lists "blame proofs revealing ECDH keys" as in-scope). I was unable to inspect `BatchVerifier::verify_with_vartime_blame`'s blame-selection order to rule out that a simultaneous `BatchId::Decryption` failure could additionally mask this; however, the `from_repr` early-return at line 480 is unconditional and does not depend on batch behavior, so the finding stands on the ordering bug alone.
