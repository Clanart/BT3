## Title
Unsafe raw ERC20 `.call` transfer without return-value validation in `IntentGatewayV2.withdraw` / `SweepDust` permanently locks escrowed funds while marking orders as settled - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed intent tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level call did not revert (`success`), never decoding/validating the ERC20 `transfer` boolean return value. This is the exact bug class from the external report (unsafeguarded transfer, no return-value validation, recommendation to use `safeTransfer`) reproduced locally in the bridge's escrow-settlement path, whereas the sibling non-Tron contract correctly uses `safeTransfer`.

### Finding Description
`withdraw()` releases escrow to the beneficiary and finalizes order state using an unchecked-return transfer pattern: [1](#0-0) 

Specifically, for ERC20 tokens:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
and for the fee-token payout in the same function, and again in the `SweepDust` handler in `onAccept`: [2](#0-1) 

`success` here only reflects whether the target contract's code executed without reverting — it does not decode the returned `bool` from `IERC20.transfer`. Many ERC20/TRC20 tokens (a category explicitly relevant on Tron, which is why this contract exists as a Tron-specific fork) return `false` on a failed transfer (e.g., insufficient contract balance, blacklisted/paused recipient) instead of reverting. In that case the low-level `.call` succeeds (`success == true`), `TransferFailed` is never raised, yet no tokens actually moved.

Despite the failed transfer, `withdraw()` still:
- decrements `_orders[body.commitment][token] -= amount;` (escrow accounting treats the funds as paid out),
- sets `_filled[body.commitment] = beneficiary;` (finalizes/closes the order), and
- emits `EscrowReleased`/`EscrowRefunded`.

This is a direct structural analog of the reported `SEuroOffering.transferCollateral` bug: transferring assets "without safeguarding that transfer and not validating return." The contract even imports and uses `SafeERC20`/`safeTransferFrom` for *inbound* transfers (`IERC20(token).safeTransferFrom(...)` at lines 399, 453, 478) but drops to the unsafe raw-call pattern for *outbound* settlement transfers, unlike the canonical EVM contract's `IntentsBase._withdraw`, which correctly calls `IERC20(token).safeTransfer(beneficiary, amount)`: [3](#0-2) 

### Impact Explanation
This is a fund-loss bug in bridge custody/intent settlement: once `withdraw()` runs, the protocol's internal accounting (`_orders`, `_filled`) irreversibly treats the order as settled/refunded regardless of whether the beneficiary actually received tokens. If the input/output token used in an order is a non-reverting-on-failure ERC20 (a real, non-exotic category, especially relevant to TRC20 tokens on Tron), the beneficiary's tokens remain stuck in the `IntentGatewayV2` contract with no remaining code path to reclaim them — `_orders[commitment][token]` has already been decremented and `_filled[commitment]` already set, so any retry is rejected (`UnknownOrder`/already-filled checks). This is a direct "loss of funds" outcome for the intent-settlement custody flow, matching the bounty's required impact category.

### Likelihood Explanation
No malicious relayer, prover, or admin is required. The order's input token is attacker/user-selectable at order placement (`order.inputs[i].token`), so a user (or an attacker crafting an order to grief another beneficiary/solver) simply needs to reference an ERC20 contract that returns `false` on failed transfer instead of reverting — a legitimate, common token behavior, not a custom malicious contract requirement. Any real-world transient failure condition on such a token (temporary insufficient balance in the gateway due to race with concurrent partial fills/sweeps, a paused or blacklisted state) silently converts into a permanent loss rather than a revert, making this reachable under ordinary operating conditions on the Tron deployment.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;`), consistent with the non-Tron `IntentsBase._withdraw` implementation, so both call-success and ERC20 return-value semantics are enforced before mutating escrow/finalization state.

### Proof of Concept
1. Deploy a TRC20/ERC20 token `T` whose `transfer(to, amount)` returns `false` (does not revert) when, e.g., `to` is blacklisted or the contract's balance of `T` is momentarily insufficient (simulate by having the gateway's `T` balance drop below `amount` right before `withdraw` is invoked, e.g. via a race with `SweepDust`/dust collection, or simply use a token whose `transfer` is written to return false on any failure condition).
2. User places an order on the source chain escrowing `amount` of `T` via `placeOrder`.
3. Order is filled/cancelled on the destination chain; a `RedeemEscrow`/`RefundEscrow` cross-chain message is dispatched back and delivered through `onAccept` → `withdraw(body, isRefund)`.
4. Inside `withdraw`, `token.call(...)` succeeds (`success == true`) but `T.transfer` internally returns `false` and moves no tokens.
5. `_orders[commitment][T] -= amount` executes anyway; `_filled[commitment] = beneficiary` is set; `EscrowReleased`/`EscrowRefunded` is emitted.
6. Beneficiary's `T` balance is unchanged — the escrowed tokens remain in the `IntentGatewayV2` contract — but the order is now permanently marked filled/refunded, so no further withdrawal attempt for this commitment is possible.
