## Analysis

The external report's core issue is a **broken invariant between what a party is shown/reviews and what actually gets recorded as the trusted result**, exploited via timing: a relayer can act *after* observing state, and the system accepts stale/late input as if it were current, corrupting the final recorded value (rewards).

The closest verifiable analog in GitHub Desktop is a **TOCTOU (time-of-check/time-of-use) gap between the diff a user reviews/selects lines from, and the diff actually used to build the patch that gets committed**, allowing an attacker who can modify tracked working-directory content mid-review (e.g. via a script/hook shipped inside a cloned/fetched repository) to cause Desktop to silently commit different content than the user reviewed and explicitly selected.

### Title
Stale line-selection indices are silently reapplied to a freshly-regenerated diff at commit time, allowing corruption of partially-committed content - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop's partial-commit feature lets a user review a diff, select individual lines/hunks to include, and commit only that subset. The line selection (`DiffSelection`) is stored as a set of **absolute line indices** relative to whatever diff was last rendered in the UI. When the user actually commits, `applyPatchToIndex` re-fetches a brand-new diff via `getWorkingDirectoryDiff` and blindly re-applies those old absolute indices to the new diff's hunks/lines to build the patch. If the file content changed between the time the diff was rendered/lines were selected and the moment "Commit" is pressed, the indices now point at different lines than what the user reviewed, and Desktop stages/commits content the user never approved.

### Finding Description
The selection-to-content binding is index-based, not content-based: [1](#0-0) 

`formatPatch` decides whether to include a line purely via `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is computed from whatever diff is passed in — there is no check that this diff is the same one the index positions were derived from.

At commit time, `applyPatchToIndex` re-derives that diff independently, from the current on-disk state, immediately before formatting the patch: [2](#0-1) 

`createCommit` drives this whole path (`unstageAll` → `stageFiles` → `applyPatchToIndex`) using whatever `WorkingDirectoryFileChange[]` (with their `selection`) is currently held in application state: [3](#0-2) [4](#0-3) 

The only mechanism that keeps a selection's indices in sync with the actual current diff is `updateChangesWorkingDirectoryDiff`, and it is a **best-effort, asynchronous refresh**, not a synchronous pre-commit validation: [5](#0-4) 

That function only prunes indices that are no longer "includeable" (e.g., turned into context lines); it does not re-validate selection correctness against content, and — critically — it is not invoked as part of `_commitIncludedChanges`. It runs on its own schedule (file selection changes / periodic status refresh), so there is a window between the last diff render and the click of "Commit" during which on-disk content can change without Desktop's selection state being reconciled.

### Impact Explanation
An attacker who controls content inside a repository the victim has cloned or fetched (e.g., via a script invoked by a build tool, editor extension, or Git hook that runs as part of the victim's normal workflow while the repository is open) can rewrite a tracked file's lines after the user has opened its diff in the Changes view and begun selecting specific lines/hunks for a partial commit, but before the user presses "Commit". Because the commit path recomputes the diff fresh and reuses stale absolute-index selection state, the resulting commit can silently:
- include attacker-injected content the user never reviewed or intended to commit, and/or
- drop content the user explicitly selected for inclusion,

while the UI has already shown the user a "successful" commit of what they believe they selected. This is a silent corruption of what the user commits (and subsequently pushes), matching the valid-impact category of "silent corruption of what the user commits or pushes," without requiring local/physical access, elevated privileges, or leaked credentials — only attacker-controlled content flowing through a normal clone/fetch/checkout workflow.

### Likelihood Explanation
This requires a specific timing window (content must change between diff review and the "Commit" click) and a means for the attacker's content to be modified during that window without the user noticing — realistic in cases involving auto-formatters, watch-mode build tools, linters with autofix-on-save, or Git hooks triggered by other Desktop operations happening concurrently on the same repository. It does not require any DoS, malware already on the host, or social engineering step beyond the user performing routine partial-commit review of an untrusted repository's changes, which is a core supported Desktop workflow.

### Recommendation
Bind the selection to content, not to positional indices: before staging/patching at commit time, re-diff the file and verify that the previously selected lines still have matching content (e.g., via a content hash or line-text comparison) rather than reusing raw absolute indices from a possibly stale diff. If a mismatch is detected, abort the commit for that file, refresh the diff, and require the user to re-confirm their selection rather than silently proceeding with mismatched indices. This mirrors making `updateChangesWorkingDirectoryDiff`'s invalidation logic authoritative and synchronous at commit time instead of applying only to UI display state.

### Proof of Concept
1. Attacker-controlled repository ships a script/hook (e.g., invoked by an npm `postinstall`/watch task, or a Git hook triggered by a routine Desktop operation) that appends/removes lines from a tracked file some seconds after checkout.
2. Victim opens the file's diff in Changes and marks a partial line selection (e.g., excluding a specific suspicious line) via `Changes.onDiffLineIncludeChanged` / `DiffSelection`.
3. Before the victim clicks Commit, the attacker's script rewrites the file, shifting line numbers by inserting/removing lines above the reviewed region — this does not necessarily trigger, or race ahead of, `updateChangesWorkingDirectoryDiff`.
4. Victim clicks Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` and applies the stale `DiffSelection` indices against it via `formatPatch`'s `file.selection.isSelected(absoluteIndex)` check.
5. The produced patch/commit no longer matches the content the victim reviewed and approved; a later `push` propagates this silently-corrupted content upstream. [6](#0-5) [7](#0-6)
