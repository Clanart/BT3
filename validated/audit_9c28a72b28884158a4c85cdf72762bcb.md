### Title
`DLEqProof::verify` accepts a proof over an empty statement list, letting an attacker forge a "valid" DLEq proof proving nothing - ([File: crypto/dleq/src/lib.rs](crypto/dleq/src/lib.rs))

### Summary
The CVE class is a missing server-side emptiness check that lets an attacker supply an empty credential and have it accepted as valid. The direct analog in Serai is `DLEqProof::verify` (and identically `MultiDLEqProof::verify`) in `crypto/dleq`: the only input validation is a length-equality check between `generators` and `points`. When both slices are empty, the verification body degenerates to comparing the attacker-supplied scalar `c` against a publicly computable transcript challenge — so anyone can produce a `DLEqProof` that verifies successfully without knowing any discrete logarithm and without any statement actually being proven.

### Finding Description
In `crypto/dleq/src/lib.rs`, `DLEqProof::verify` performs the following:

- Checks only `generators.len() != points.len()` — an equality check, not a non-emptiness check (line 166). Two empty slices satisfy it.
- Applies `transcript.domain_separate(b"dleq")` and iterates `generators.iter().zip(points)` to append `(generator, R, point)` statements via `verify_statement` (lines 170–173). With empty slices, zero statements are ever bound to the transcript.
- Compares `self.c != challenge(transcript)` (line 175). The challenge is therefore a pure function of the domain separator plus whatever the caller transcripted beforehand — fully predictable to anyone.

An attacker computes `c = challenge(transcript)` locally (the transcript is deterministic given the caller's context), picks any `s`, serializes `c || s`, and hands it to a verifier via `DLEqProof::read` (line 191, which imposes only canonical-scalar checks via `read_scalar`, line 89). `verify` returns `Ok(())`.

The same flaw exists in `MultiDLEqProof::verify` (lines 264–293): `points.len() != generators.len()` and `self.s.len() != generators.len()` are the only checks, so `generators = []`, `points = []`, `s = []` with `c` set to the transcripted challenge verifies. Note `MultiDLEqProof::read` takes a caller-supplied `discrete_logs` count (line 308), which can be `0`.

The crate's own test suite demonstrates this degenerate case is silently accepted: `test_dleq` loops `i` from `0` and calls `DLEqProof::prove(..., &generators[..0], ...)` / `verify(..., &generators[..0], &keys[..0])` successfully (`crypto/dleq/src/tests/mod.rs:49-57`), confirming the empty-statement path returns `Ok` rather than erroring.

### Impact Explanation
A DLEq proof that verifies over an empty statement set is a forged proof: the verifier is told "these points share a discrete logarithm" when nothing was proven at all. Wherever a verifier's statement list is derived — directly or by length — from prover-controlled data, an attacker who drives the list to zero bypasses the proof requirement entirely, mirroring how an empty `password` parameter bypassed credential validation in the CVE. The `verify` API is the exact public entry point the audit scope designates as attacker-reachable (`untrusted bytes fed to ... DLEqProof::read ... or to a verify ... API`); the proof bytes are fully attacker-controlled, and the emptiness of the statement list is the missing-validation condition.

Severity is bounded because in-scope callers (`GeneratorPromotion::complete` in `crypto/dkg/promote/src/lib.rs:149-153`, `EncryptionKeyProof` verification in `crypto/dkg/pedpop/src/encryption.rs`) hardcode two generators, so no in-scope production caller currently reaches the degenerate path — the vulnerability is in the `verify` primitive itself, exploitable by any consumer whose statement list can be empty.

### Likelihood Explanation
Triggering the bug requires a verifier calling `DLEqProof::verify` / `MultiDLEqProof::verify` with an attacker-influenced, zero-length statement list. That condition is structurally available wherever the generator/point set is enumerated from untrusted input (e.g., a protocol admitting variable numbers of points). No in-scope Serai caller passes a variable-length list today, so exploitability is contingent on integrator usage — which is precisely why the missing check is dangerous: the API gives no indication that empty input is invalid, and `prove`/`verify`/`read` all round-trip the empty case without error (proven by the existing test).

### Recommendation
Reject empty statements in both verifiers. In `DLEqProof::verify` (`crypto/dleq/src/lib.rs:165-168`), change the guard to also require `!generators.is_empty()`. In `MultiDLEqProof::verify` (`crypto/dleq/src/lib.rs:270-275`), require `generators` non-empty and additionally that each inner `generators`/`points` pair is non-empty (an empty inner series currently binds only the `discrete_logarithm` index message). Optionally also make `DLEqProof::prove` and `MultiDLEqProof::prove` panic/error on empty input so a vacuous proof cannot even be constructed by mistake.

### Proof of Concept
```rust
// Any ciphersuite with PrimeFieldBits; k256 shown per existing tests.
use dleq::DLEqProof; // conceptual; adjust to crate paths
use zeroize::Zeroizing;
use transcript::{Transcript, RecommendedTranscript};
use k256::{Scalar, ProjectivePoint};

// Attacker side: compute the challenge the verifier will derive for an
// EMPTY statement list — only the "dleq" domain separator is transcripted.
fn forged_proof(context: &[u8]) -> DLEqProof<ProjectivePoint> {
    let mut transcript = RecommendedTranscript::new(context);
    transcript.domain_separate(b"dleq");
    // challenge() is pub(crate); reproduce its wide-reduction of
    // transcript.challenge(b"challenge") here, or equivalently call
    // DLEqProof::prove(rng, &mut t, &[], &Zeroizing::new(Scalar::ZERO))
    // which produces a proof that trivially verifies for empty inputs.
    let c: Scalar = /* dleq::challenge of the transcript above */;
    let s = Scalar::ZERO; // arbitrary — s is never used with no statements
    // serialize c || s and feed it to the verifier via DLEqProof::read
    DLEqProof::read(&mut [c.to_repr(), s.to_repr()].concat().as_slice()).unwrap()
}

// Verifier side: statement lists derived from attacker data came back empty.
let proof = forged_proof(b"Some Verifier Context");
let generators: &[ProjectivePoint] = &[];
let points: &[ProjectivePoint] = &[];
assert!(
    proof
        .verify(&mut RecommendedTranscript::new(b"Some Verifier Context"), generators, points)
        .is_ok()
); // forged "proof" accepted — nothing was proven
```

The root cause is `crypto/dleq/src/lib.rs:166-168` checking only `generators.len() != points.len()` (satisfied by two empty slices) and `crypto/dleq/src/lib.rs:170-176` binding zero statements while still requiring `self.c == challenge(transcript)`, a value the attacker fully controls. The identical pattern in `MultiDLEqProof::verify` at `crypto/dleq/src/lib.rs:270-275` is equally affected.
