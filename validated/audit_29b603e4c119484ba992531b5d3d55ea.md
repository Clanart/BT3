### Title
Unauthenticated party can force Serai's Bitcoin scanner to report immature coinbase outputs as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block — including `txdata[0]`, the coinbase — and returns any outputs paying to a registered `script_pubkey` as `ReceivedOutput`s indistinguishable from normal, immediately-spendable outputs. Coinbase outputs are unspendable for 100 blocks under Bitcoin consensus rules. Any miner (an unprivileged external party who controls coinbase contents) can direct the coinbase reward to one of Serai's watched addresses, causing the scanner to report funds as received that cannot actually be spent.

### Finding Description
`scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, with no checks on the transaction type or its spendability [1](#0-0) . `scan_block` then applies this to *all* transactions in the block, explicitly including the coinbase [2](#0-1) . A `ReceivedOutput` exposes only `offset`, `output`, `outpoint`, and `value` [3](#0-2)  — nothing marks an output as immature, so downstream scheduling code cannot distinguish it from a spendable UTXO.

This mirrors the reported bug class: a function performing a privileged effect (crediting funds to the wallet) reachable by an unauthenticated party, where authentication/validation of the input is absent. Here the "call" is any Bitcoin transaction — including a miner-crafted coinbase — paying to Serai's publicly known `p2tr_script_buf(key)` address [4](#0-3) .

Notably, the sibling function that skips the coinbase exists only implicitly: the downstream processor manually slices `block.txdata[1 ..]` when scanning [5](#0-4) , proving the authors recognize coinbase outputs as invalid for crediting, yet `scan_block` — the natural API for block scanning, exercised in the crate's own test via `scanner.scan_block(&block)` [6](#0-5)  — performs no such exclusion. Any caller using the library's own advertised `scan_block` API receives poisoned output.

### Impact Explanation
Any `ReceivedOutput` returned flows into wallet code that treats it as a spendable input (e.g., `SignableTransaction::new` consumes `ReceivedOutput`s directly [7](#0-6) ). A coinbase output reported as received is consensus-immature for 100 blocks: any signed transaction spending it is rejected by the network, and the wallet's balance accounting overstates spendable funds. An attacker who mines even a single block (feasible for any miner; mining pools and even small miners periodically win blocks) can force Serai's wallet to (a) credit phantom liquidity and (b) generate signing plans that can never confirm, halting payouts until the poisoned output is filtered out. This is "funds reported received that are not spendable" — an accepted impact class.

### Likelihood Explanation
No authentication, signature, or special permission is required: the trigger is a standard Bitcoin transaction paying to a publicly known address, which the rules explicitly classify as reachable public input. The only requirement is that the attacker mines a block — routinely achieved by any mining participant, and the coinbase reward itself subsidizes the attack. Integration risk is high because `scan_block` is the documented, test-exercised entry point for block scanning; only callers that happen to replicate the processor's manual `txdata[1 ..]` slice avoid the bug.

### Recommendation
In `Scanner::scan_block`, skip `block.txdata[0]` (or filter by `tx.is_coinbase()`), or annotate `ReceivedOutput` with a maturity flag so callers cannot mistake immature coinbase outputs for spendable funds. Alternatively, perform the coinbase exclusion inside `scan_block` and remove the implicit requirement that callers slice `txdata` themselves.

### Proof of Concept
```rust
// A miner crafts a coinbase whose reward output pays to Serai's P2TR script.
let block: Block = /* block whose txdata[0] is a coinbase paying to
    p2tr_script_buf(group_key).unwrap() */;

let scanner = Scanner::new(group_key).unwrap();
let outputs = scanner.scan_block(&block);

// The immature coinbase output is reported identically to a spendable UTXO:
assert_eq!(outputs.len(), 1);
let coinbase_outpoint = OutPoint::new(block.txdata[0].compute_txid(), 0);
assert_eq!(outputs[0].outpoint(), &coinbase_outpoint);

// Downstream, ReceivedOutput is consumed as a spendable input
// (e.g., SignableTransaction::new(vec![outputs[0].clone()], ...)), yet any
// transaction spending it violates BIP-34 coinbase maturity and is rejected.
```

The contrast with the processor's own workaround — `for tx in &block.txdata[1 ..]` [5](#0-4)  — demonstrates the missing validation inside the in-scope `scan_block` API rather than a caller-side assumption.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
