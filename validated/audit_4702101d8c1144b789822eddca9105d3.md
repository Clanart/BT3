## Title
Fixed `config.DefaultGasCap` (25,000,000) charged in `CallEVM`/`CallEVMWithData` regardless of remaining caller gas, breaking the 63/64 anti-recursion invariant for module-triggered ERC20 calls - (File: `x/vm/keeper/call_evm.go`)

### Summary
`Keeper.CallEVM`/`CallEVMWithData` in `x/vm/keeper/call_evm.go` hardcode `GasLimit: config.DefaultGasCap` (25,000,000 gas, see `server/config/toml.go` / `server/config/migration/v0.50-app.toml`) for every nested EVM call it makes, completely decoupled from the gas actually remaining in the calling context. [1](#0-0) [2](#0-1) 

This is the exact same anti-pattern as the Nibiru H-06 finding: a hardcoded gas budget for a "sub-call" that ignores the EIP-150 63/64 rule, which is precisely what protects the EVM from unbounded recursive-call gas amplification.

### Finding Description
`CallEVM`/`CallEVMWithData` is used pervasively by native Cosmos modules to invoke arbitrary ERC20 contract bytecode on behalf of users, e.g.:
- `x/erc20/keeper/evm.go` `BalanceOf` — calls an arbitrary ERC20's `balanceOf` with `CallEVM(..., false, nil, "balanceOf", account)`, which resolves to `GasLimit: config.DefaultGasCap` inside `CallEVMWithData`. [3](#0-2) 
- `x/erc20/keeper/msg_server.go` `ConvertCoinNativeERC20` — calls `k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())` to unescrow tokens from an arbitrary, user-registered ERC20 contract. [4](#0-3) 
- `x/erc20/keeper/msg_server.go` `convertERC20IntoCoinsForNativeToken` — calls `k.evmKeeper.CallEVMWithData(...)` for `transfer` with `nil` gas cap. [5](#0-4) 

Because none of these callers pass a gas cap, `CallEVMWithData` always sets a **fixed** `GasLimit: config.DefaultGasCap` (25,000,000) for the inner EVM call: [6](#0-5) 

If an attacker registers a malicious ERC20 token pair (via `RegisterERC20` — a permissionless, fee-gated operation like Nibiru's funtoken registration) whose `transfer`/`balanceOf` implementation recursively calls back into `ConvertCoin`/`ConvertERC20` (a precompile is not even required — the ERC20 bytecode itself can call the `0x0000...0800`-style native precompiles, or simply re-enter via a `transferFrom` hook/`_beforeTokenTransfer` calling back into the erc20 module through a precompile bridge such as `bank`/`erc20` precompile), each level of the call stack is re-granted the *full* 25,000,000 gas budget rather than 63/64 of the *parent's remaining* gas. This defeats the EIP-150 guarantee that recursion depth is bounded logarithmically by available gas, allowing an attacker to construct a call chain whose total gas consumption/CPU work is a large multiple of the outer transaction's gas limit — the same failure mode documented in the Nibiru report, which caused unbounded memory growth and consensus-timeout-driven block-production halt.

The repository's own test suite (`ERC20RecursiveRevertingPrecompileCall.sol`, `ERC20RecursiveNonRevertingPrecompileCall.sol`, `ics20_recursive_precompile_calls_test.go`) demonstrates the team is aware recursive precompile calls from ERC20 hooks are a live pattern, but those tests bound the recursion to a small fixed loop (`for(uint256 i=0; i < 5; i++)`) rather than proving termination under adversarial, self-referential recursion through `CallEVM`/`CallEVMWithData`. [7](#0-6) 

By contrast, `x/ibc/callbacks/keeper/keeper.go` explicitly threads `remainingGas`/`cachedCtx.GasMeter().GasRemaining()` into `CallEVM` calls, showing the module authors elsewhere understand the need to bound nested gas by the caller's remaining budget — but this discipline was not applied to `x/erc20`'s `CallEVM`/`CallEVMWithData` default path. [8](#0-7) 

### Impact Explanation
If exploitable, this maps to the "Critical chain halt … that an unprivileged user can trigger through ordinary transaction … flow" impact: an attacker can register a malicious ERC20 token pair and submit a single `MsgConvertCoin`/`MsgConvertERC20` transaction whose nested `transfer`/`balanceOf` calls recurse, each level being granted a fresh 25M-gas allowance disconnected from EIP-150 accounting, multiplying total EVM work far beyond the paying transaction's gas limit and risking block-production stalls/OOM on validators.

### Likelihood Explanation
**Uncertain / not fully confirmed.** I could not fully verify within the available tool budget whether:
1. `ConvertCoin`/`ConvertERC20` can be invoked with a token pair whose contract is fully attacker-controlled bytecode (vs. requiring the pair to be a pre-vetted "native ERC20" deployed through governance) — this gates whether the attacker truly controls the `transfer`/`balanceOf` implementation.
2. There is an outer gas-meter check (e.g., `ctx.GasMeter().ConsumeGas` after each `CallEVM`, visible at `x/vm/keeper/call_evm.go:90`) that, combined with the ante-handler's overall block gas limit, sufficiently bounds total recursion depth even though each individual `CallEVM` call is granted a fixed 25M budget — since the *outer* Cosmos gas meter (fed by the original tx's gas limit) still charges `res.GasUsed` back up the call chain, the "amplification" may be capped by the original tx's gas limit rather than truly unbounded, unlike Nibiru's precompile-only recursion where the hardcoded 100k was *not* charged against the outer meter until return. This significantly reduces confidence that this is a genuine unbounded-recursion primitive versus the original Nibiru bug.
3. Whether `RegisterERC20`/token-pair registration for a "native ERC20" pair is genuinely permissionless in this codebase, and whether recursive re-entry into `ConvertCoin`/`ConvertERC20` from within an ERC20's own `transfer` hook is reachable at all (I found only test fixtures recursing into staking/distribution precompiles, not into `x/erc20` itself).

Given these unresolved reachability and boundedness questions, I cannot confirm this analog reaches the same catastrophic, EIP-150-violating unbounded recursion as the Nibiru report with the confidence required for a Critical finding.

### Recommendation
- Thread the caller's actual remaining gas (as done in `x/ibc/callbacks/keeper/keeper.go`) into `CallEVM`/`CallEVMWithData` instead of defaulting to the fixed `config.DefaultGasCap`, and enforce a 63/64 sub-call gas cap consistent with EIP-150.
- Audit all `CallEVM`/`CallEVMWithData` call sites in `x/erc20` for `nil` gas caps and require an explicit, gas-meter-derived cap.
- Add fuzzing/adversarial tests where a registered ERC20 token pair's `transfer`/`balanceOf` recursively triggers `ConvertCoin`/`ConvertERC20` (not just precompile calls) to confirm whether total gas/CPU work is properly bounded by the outer transaction's gas limit.

### Proof of Concept
Not constructed — reachability of recursive re-entry from an ERC20 `transfer`/`balanceOf` hook back into `x/erc20`'s `ConvertCoin`/`ConvertERC20` message handlers, and confirmation that the outer Cosmos gas meter does not already bound total work, could not be verified with the available tools/time. A concrete PoC would require: (1) confirming `RegisterERC20`/native-ERC20 pair creation is permissionless for attacker-supplied bytecode, (2) deploying an ERC20 whose `transfer` override calls back into the erc20 precompile/module, and (3) measuring whether cumulative EVM gas consumption across the recursive chain exceeds the originating transaction's declared gas limit.
