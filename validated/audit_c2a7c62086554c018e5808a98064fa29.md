## Finding

### Title
Oracle freshness check clamps delta to zero for future-dated feed timestamps, permanently "fresh-washing" stale prices - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` is the sole staleness gate for every price used by Zest's health checks, borrow/withdraw simulations, and liquidations. Instead of bounding the *distance* between the feed timestamp and the chain's current time in both directions, it special-cases any timestamp that is ahead of `stacks-block-time` by forcing `delta = u0`, i.e., "instantly fresh," no matter how far in the future that timestamp is. [1](#0-0) 

### Finding Description
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```
This function is invoked from `price-resolve`, which is the only path that validates a fetched price before it is used anywhere in the protocol: [2](#0-1) 

`ts` (the feed's `publish-time`) comes straight from `resolve-pyth`/`resolve-dia`, which read whatever value is currently stored in `pyth-storage-v4`/DIA: [3](#0-2) 

Neither `pyth-storage-v4`'s `write-batch-entry` nor Zest's own code enforces any *upper* bound on `publish-time` relative to the real/chain clock — the storage contract only rejects prices that are too *old* (`ERR_STALE_PRICE`), never ones with a timestamp set ahead of the current block time: [4](#0-3) 

The consequence: if a feed's `publish-time` is ever ahead of `stacks-block-time` — whether from normal publisher clock skew, chain time lag, or a relayer bug — `oracle-timestamp-fresh` computes `delta = u0` and reports the price as maximally fresh, bypassing the entire `max-staleness` protection defined per-asset in the asset registry. The price stays "fresh" for as long as `ts > stacks-block-time` holds, which can be an unbounded window if the future offset is large, since Stacks block time only advances at real time.

This is structurally the same bug class as the reported `updateWeightsGradually` issue: the code fails to clamp a time-derived value with a `min`/`max` against the current reference time before using it in a downstream calculation, allowing an out-of-range input (a timestamp in the "wrong" temporal direction) to produce an unintended, unbounded result (delta pinned at 0 instead of being measured/rejected).

### Impact Explanation
`price-resolve`/`price-multi-resolve` feed every collateral and debt valuation used in `process-collateral-asset`/`process-debt-asset` for health checks, borrow/withdraw simulation, and liquidation eligibility. If a stale/incorrect price is locked in as "fresh" via a future-dated timestamp, borrowers can be under-collateralized against real market value (protocol insolvency risk) or liquidators can be blocked from liquidating truly undercollateralized positions because the frozen price still shows a passing health ratio (temporary freezing of funds owed to liquidators/lenders). This lands on the in-scope **Critical (protocol insolvency)** / **High (temporary freezing of funds)** impact classes.

### Likelihood Explanation
Exploitability depends on a feed timestamp ending up ahead of `stacks-block-time`, which does not require compromising Pyth's signing keys — clock drift between publishers and the Stacks chain's block-time reference, or any relayer/write-path irregularity that is not gated by an upper timestamp bound in `pyth-storage-v4`, is sufficient to trigger the always-fresh state. Because there is no upper-bound check anywhere in the write or read path, this can occur without any protocol/DAO misconfiguration — the flaw is fully contained in Zest's own freshness arithmetic.

### Recommendation
Compute the staleness delta as an absolute/symmetric distance and reject (rather than zero out) timestamps that are unreasonably ahead of `stacks-block-time`:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   (- ts stacks-block-time)   ;; treat future skew as staleness too
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```
Additionally, `pyth-storage-v4`'s `write-batch-entry`/`set-price-testnet` should reject `publish-time` values beyond a small allowed clock-skew window ahead of the chain's own time.

### Proof of Concept
1. A Pyth (or DIA) update is written/observed with `publish-time` set even slightly ahead of `stacks-block-time` (feasible via normal publisher/chain clock drift, or any relayer irregularity not bounded by an upper-time check).
2. `resolve-pyth`/`resolve-dia` returns this `timestamp` to `price-resolve`.
3. `oracle-timestamp-fresh` computes `delta = u0` because `ts > stacks-block-time`, so `(<= delta max-staleness)` is trivially true regardless of `max-staleness`.
4. The price is accepted as fresh and cached into `last-update`, and remains "fresh" on every subsequent call as long as `ts` stays ahead of the chain's advancing `stacks-block-time` — i.e., a genuinely stale/incorrect price can be used for health checks, borrows, and liquidation decisions for an unbounded period.
