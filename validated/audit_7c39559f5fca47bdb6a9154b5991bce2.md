### Title
CW20ERC20Pointer's delta-based `approve()` allows a spender to front-run allowance changes to double-spend beyond the amount the owner intended - ([File: contracts/src/CW20ERC20Pointer.sol])

### Summary
`CW20ERC20Pointer.approve()` does not directly set the target allowance on the underlying CW20 contract. Instead it queries the current on-chain allowance and computes an `increase_allowance`/`decrease_allowance` delta to reach the caller's requested target amount. Because this delta is computed against a freshly-queried, mutable value rather than being applied atomically against the caller's known prior state, a spender who observes a pending `approve()` transaction in the mempool can front-run it by first draining the existing allowance via `transferFrom`, then let the owner's transaction execute — which will now compute a delta from an allowance of `0` and unconditionally top the spender back up to the newly requested amount. This lets the spender receive both the fully-spent old allowance and the full new allowance, i.e. it can be forced/tricked into transferring more total value than the token owner ever intended to authorize in a single approval update.

### Finding Description
`approve()` in `CW20ERC20Pointer` is implemented as: [1](#0-0) 

Rather than calling the CW20 `set_allowance`-style overwrite, it reads `allowance(msg.sender, spender)` live and issues an `increase_allowance` or `decrease_allowance` CosmWasm message for the difference between the current allowance and the desired target amount: [2](#0-1) 

This is the classic ERC-20 "approve race condition" (SWC-114) pattern, but made strictly worse here: because the contract computes the new allowance relative to whatever the allowance happens to be *at execution time* (not what the owner observed when they signed the transaction), a malicious/compromised spender can:
1. Observe the owner's pending `approve(spender, newAmount)` transaction (e.g., lowering allowance from 100 to 50, or simply refreshing it).
2. Front-run with `transferFrom(owner, spender, 100)` to fully drain the existing 100 allowance.
3. Let the owner's `approve()` transaction land afterward; it now reads `currentAllowance == 0` and issues `increase_allowance(spender, 50)` to reach the owner's intended target of 50.
4. The spender ends up having extracted the full original 100 tokens **and** still holds a fresh allowance of 50 — a strictly larger total draw than the owner ever authorized in either the old or new state.

This mirrors the Tapioca finding's root cause: an amount/authorization boundary that is not atomically bound to the specific approval a user believes they are granting, letting a third party (the approved spender) extract more value than intended by manipulating transaction ordering around the approval update. `CW20toERC20Pointer` similarly implements standard OpenZeppelin approve/transferFrom semantics (subject to the same class of front-running), but `CW20ERC20Pointer`'s relative delta computation is the more directly analogous and more severe variant since it computes a fresh top-up rather than simply overwriting.

### Impact Explanation
A spender who has been granted any allowance on a `CW20ERC20Pointer` token can, by front-running the owner's routine allowance updates, extract tokens beyond what any single approval state (old or new) ever authorized — a direct fund-loss scenario for the token owner attributable to the pointer contract's own allowance-management logic, not to CW20/ERC20 semantics generally.

### Likelihood Explanation
Exploitation requires only that the attacker already holds (or is about to receive) a nonzero allowance from the victim and can observe/front-run the victim's subsequent `approve()` call in the public mempool — a capability any unprivileged EVM transaction sender has. Owners who periodically adjust (rather than fully revoke-then-reset) allowances on `CW20ERC20Pointer` tokens are exposed on every such update.

### Recommendation
Change `approve()` to set the allowance atomically and unconditionally to the caller-specified target (e.g. always issue a full reset via `decrease_allowance` to zero followed by `increase_allowance` to the target, or expose/ use a native "set_allowance" CW20 message if available) rather than computing a delta from a freshly queried, attacker-influenceable current allowance. Alternatively, follow the standard mitigation of requiring the allowance to be set to zero before it can be changed to a new nonzero value, and document/encourage this pattern to callers.

### Proof of Concept
1. Owner has approved `spender` for `100` tokens on a `CW20ERC20Pointer` instance.
2. Owner submits `approve(spender, 50)` intending to reduce the allowance to 50.
3. `spender` sees this transaction in the mempool and front-runs with `transferFrom(owner, spender, 100)`, draining the full existing allowance (allowance becomes 0).
4. Owner's `approve(spender, 50)` executes: `currentAllowance` is now `0`, so per `contracts/src/CW20ERC20Pointer.sol:70-74` the contract issues `increase_allowance(spender, 50)`.
5. Final state: `spender` has already received 100 tokens from step 3 and now holds a fresh allowance of 50 — a total exposure of 150 against an owner who only ever intended a maximum concurrent exposure of 100 (the pre-existing allowance) or 50 (the newly requested one).

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
