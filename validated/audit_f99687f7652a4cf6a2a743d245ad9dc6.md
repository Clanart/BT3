### Title
Hardcoded zero slippage protection in `_sendRewards` swap-to-mWOM conversion enables sandwich attacks on user-triggered stake/unstake operations - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.sol`'s `_sendRewards` function converts harvested WOM fee tokens into mWOM via `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`, hardcoding the minimum-received parameter to `0` regardless of the amount being converted. This mirrors the reported Bitscrunch `swapStableToBCUT()` flaw where `amountOutMinimum` was hardcoded to `1`.

### Finding Description
`_sendRewards` is invoked from `_toMasterWomAndSendReward`, which fires on every stake/unstake action against the Wombat master pool (triggered by ordinary user deposit/withdraw flows through `WombatStaking`). When the harvested WOM fee is designated `isMWOM`, the code path performs: [1](#0-0) 
Here `smartConvert(feeAmount, 0)` sets the minimum acceptable mWOM output to zero, no matter how large `feeAmount` is. `smartConvert` internally swaps a portion of WOM through a router pool (as seen in the sibling `convertFor`/`convert` function using `swapExactTokensForTokens` with a caller-controlled `_minRec` in normal flows) [2](#0-1) , but this internal auto-triggered call path bypasses any minRec protection by passing `0` directly.

Because `_toMasterWomAndSendReward` is invoked as a side effect of ordinary, unprivileged user stake/withdraw transactions (deposit/withdraw against `masterWombat`), an attacker monitoring the mempool can sandwich the resulting on-chain swap inside `smartConvert`, manipulating the WOM→mWOM pool price and causing the protocol to receive far fewer mWOM tokens than expected for the given fee amount. [3](#0-2) 

### Impact Explanation
The mis-converted value is protocol/user-fee-derived mWOM inventory that funds rewards; the shortfall is a direct value loss extracted by the sandwiching attacker at the expense of the protocol's converted balance, which ultimately reduces yield available to stakers. This is a genuine, reachable-by-unprivileged-wallet loss within the explicitly in-scope "WombatStaking LP custody" / "mWOM/SmartWomConvert minting" surfaces.

### Likelihood Explanation
Any user calling stake/unstake functions on `WombatStaking` triggers this path whenever WOM rewards are harvested and the `isMWOM` fee flag is active, making the vulnerable code frequently and predictably reachable; an attacker only needs to watch the mempool for such transactions and sandwich the resulting swap, exactly as described in the original report's attack pattern.

### Recommendation
Do not hardcode `0` for the `smartConvert` call inside `_sendRewards`. Compute an acceptable minimum output off-chain/via a TWAP-based oracle check, or expose a slippage-bounded parameter threaded through from the stake/withdraw call, similar to how `SmartWomConvert.convertFor`/`convert` accept and enforce a caller-supplied `_minRec` that reverts via `MinRecNotMatch()` if unmet.

### Proof of Concept
1. Attacker observes a pending user transaction that calls `WombatStaking`'s deposit/withdraw function for a pool with `isPoolFeeFree == false` and `isMWOM == true`.
2. Attacker front-runs by swapping a large amount into the WOM/mWOM pool used by `smartWomConverter`, skewing the price.
3. The victim transaction executes, `_sendRewards` calls `smartConvert(feeAmount, 0)`, executing the swap at the manipulated price and accepting any nonzero output.
4. Attacker back-runs, swapping back and extracting the price-impact difference as profit, mirroring the reference `PoC.sol` sandwich pattern (front-run swap → victim's `amountOutMinimum=1`/`0` swap → back-run swap) shown in the original report.
