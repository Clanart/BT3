### Title
Cached FROST preprocess seed is reused deterministically per-context, enabling nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a `CachedPreprocess` seed keyed only by `self.context.encode()`. On every subsequent call for a context that already has a cached entry, the same seed is decrypted and passed to `AlgorithmSignMachine::from_cache`, which regenerates bit-for-bit identical FROST nonces and commitments. If two distinct signing operations ever share a context encoding while differing in message or signer set, the same nonce is used to produce two different signature shares, allowing an unprivileged counterparty to recover this validator's private key share.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs`, `preprocess_internal` (lines 100–148):

- Derives an XOR encryption key from `b"Cached Preprocess Encryption Key" || context.encode() || key.to_repr()`.
- If `CachedPreprocesses::get(self.txn, &self.context)` is `None`, generates a fresh preprocess and stores the seed.
- Otherwise loads the stored seed, decrypts it, and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`.

In `crypto/frost/src/sign.rs` (lines 121–144, 268–274), `from_cache` calls `seeded_preprocess(seed)`, which seeds `ChaCha20Rng::from_seed(*seed.0)` and derives the nonces and commitments purely deterministically from that seed. There is no per-invocation entropy and, critically, no consumption or deletion of the cached seed — `CachedPreprocesses::get` will return the identical seed for every call with an equal `context` encoding.

The FROST spec in `spec/cryptography/FROST.md` states explicitly: "Reusing preprocesses would enable a third-party to recover your private key share." The signature share produced in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs` lines 382–398) is of the form `share = base + rho * actual + challenge_share`, where `base + rho * actual` is the nonce combination. The binding factor `rho` depends on the `rho_transcript` (group key, `hash_msg(msg)`, and the `preprocesses` challenge over the full participant/commitment set), so two calls over the same context that differ in `msg` or in the set of submitted preprocesses produce shares `s1 = n + f1(x)` and `s2 = n + f2(x)` with the identical nonce `n`. Solving the two linear equations recovers the secret share `x` (and the nonce).

`share_internal` itself calls `preprocess_internal` again (line 156) rather than consuming the cache, so any retry, re-execution, or second signing request under an equal `context` encoding silently re-derives the same nonces.

### Impact Explanation
An unprivileged participant in the signing set who receives two signature shares produced under the same cached context — e.g., by causing a session to be re-run with a different `serialized_preprocesses` set or different message under an equal `context` — obtains two equations sharing the same nonce term and recovers this validator's MuSig/FROST private key share via `x = (s1 - s2) / (f1 - f2)`. With the share recovered, threshold security is degraded; combined with other shares this enables forgery of Schnorrkel signatures authorizing validator-set key operations and fund movements.

### Likelihood Explanation
Triggering requires two signing operations whose `context.encode()` collides while the signed payload or signer set differs. Contexts are supplied by callers as `Encode` types; any retry path, re-oraclization, or distinct message type whose encoding collides with a prior context reaches this unconditionally — the cache lookup is keyed solely on context and is never invalidated in the shown code path. No cryptographic assumption-breaking is needed; exploitation is linear algebra over public signature shares.

### Recommendation
- Delete the `CachedPreprocesses` entry (`remove`) as soon as a signing session completes or aborts, so a seed can never seed two sessions.
- Bind the cache key to the full session instance (e.g., a monotonically increasing attempt counter or the complete message/participant set) rather than a reusable context.
- Prefer not caching preprocess seeds across protocol invocations at all; FROST preprocesses must be single-use.

### Proof of Concept
1. Observe a signing session under context `C` where this validator emits preprocess `P` and share `s1` for message `m1` (or signer set `S1`).
2. Cause a second signing operation under the same context encoding `C` — e.g., a retried signing round with a different participant subset or a different message — via `share_internal`.
3. `preprocess_internal` finds `CachedPreprocesses::get(txn, C)` non-empty, re-derives identical nonces via `from_cache`/`ChaCha20Rng::from_seed`, and emits share `s2` over the same nonce `n` but a different binding/challenge factor.
4. Solve `x = (s1 - s2) · (λ1·c1 - λ2·c2)⁻¹` over the scalar field to recover the private key share `x`.
