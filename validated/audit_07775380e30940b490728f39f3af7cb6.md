### Title
SSRF via untrusted Data Layer mirror URLs fetched without network destination restrictions - (File: chia/data_layer/download_data.py)

### Summary
Any wallet user can publish an on-chain "mirror" record for **any** Data Layer store (including stores they do not own) containing arbitrary attacker-chosen URLs. When another node subscribes to that store, its Data Layer service pulls those URLs and issues outbound HTTP requests to them with no validation against internal/private network destinations — the same bug class as CVE-2019-15730 (GitLab Jira SSRF: server-side code fetching an attacker-supplied URL from within the operator's network).

### Finding Description
`DataLayerWallet.create_new_mirror()` creates a mirror coin whose puzzle hash is `create_mirror_puzzle()` and whose memo simply encodes `[launcher_id, *urls]` — there is no on-chain or wallet-side check that the caller actually owns/controls that `launcher_id`/store: [1](#0-0) 

The corresponding wallet RPC endpoint `dl_new_mirror` likewise performs no ownership validation on `request.launcher_id` before publishing the mirror: [2](#0-1) 

A victim node that tracks/subscribes to that store pulls these attacker-controlled URLs directly from wallet mirror records into its local subscription list: [3](#0-2) 

During the periodic sync loop, `fetch_and_validate()` iterates these server URLs and passes them into `insert_from_delta_file()`/`download_file()`: [4](#0-3) 

`download_file()` (no plugin downloader configured) calls `http_download()`, which performs an `aiohttp` GET directly against `server_info.url` — a string that originated entirely from the untrusted on-chain mirror record — with no restriction on scheme, host, or IP range (no blocking of loopback, link-local, RFC1918, or cloud metadata addresses): [5](#0-4) [6](#0-5) 

When a plugin downloader is configured, `download_file()` also issues a `POST` to `downloader.url + "/download"` with a JSON body containing `server_info.url` verbatim, meaning the attacker-controlled URL is forwarded to a second, plugin-hosted service as well: [7](#0-6) 

Because Data Layer store creation and mirror publication are both unprivileged, permissionless actions (any wallet holder can create a store and publish mirrors for any `launcher_id` by paying a fee), an attacker only needs a victim's Data Layer client to subscribe to (track) their store — a normal, expected Data Layer usage pattern (e.g., discovering/consuming a public dataset, or as part of resolving a Data Layer offer dependency) — to get the victim's node to issue outbound requests to attacker-chosen destinations.

### Impact Explanation
This is a server-side request forgery: the victim's Data Layer service (running on the node's host, often colocated with other local-only services and cloud infrastructure) becomes a proxy for probing/interacting with resources on its local network or loopback interface that are not otherwise externally reachable (internal RPC ports, cloud metadata endpoints, other local daemons). While downloaded delta-file content is subsequently validated against the wallet-confirmed Merkle root before being trusted as store data, the outbound request itself — and any side effects it triggers on the internal target (e.g., a GET or POST reaching an internal management endpoint) — occurs regardless of that later validation. This can enable internal network reconnaissance, interaction with internal-only HTTP services, or exfiltration of response timing/size information, matching a Medium-severity SSRF impact profile.

### Likelihood Explanation
High likelihood of reachability: creating a store and publishing a mirror requires no special privilege beyond paying a small on-chain fee, and there is no ownership check tying a mirror's `launcher_id` to the creator. Any Data Layer participant that subscribes to or tracks an attacker's store (a normal operation) will have their node's background sync loop (`periodically_manage_data` → `update_subscription` → `fetch_and_validate`) automatically fetch from the attacker-supplied URL without user interaction beyond the initial subscribe.

### Recommendation
- Validate mirror/server URLs before use in `download_file`/`http_download`: reject non-http(s) schemes, and resolve/deny requests to loopback, link-local, private (RFC1918), and known cloud-metadata IP ranges unless explicitly allowlisted by the node operator.
- Consider requiring proof of `launcher_id` ownership (or at least warning/flagging) before accepting or displaying mirror URLs coming from `dl_new_mirror`/`create_new_mirror` for stores the wallet doesn't own.
- Apply the same destination validation to the plugin-downloader POST path (`downloader.url + "/download"`), since it forwards the untrusted URL to a second network-reachable service.

### Proof of Concept
1. Attacker creates a Data Layer store (`chia data create_data_store`) or targets an arbitrary existing `launcher_id`.
2. Attacker calls `dl_new_mirror` (via wallet RPC/CLI `chia data add_mirror`) for that `launcher_id` with `urls=["http://127.0.0.1:<internal-port>/", "http://169.254.169.254/latest/meta-data/"]` and a small fee; the transaction confirms on-chain with no ownership enforcement. [1](#0-0) 
3. Victim node's owner runs `chia data subscribe -i <launcher_id>` (or otherwise tracks the store as part of normal Data Layer consumption).
4. Victim's `DataLayer.update_subscriptions_from_wallet()` ingests the attacker's mirror URLs into local subscriptions. [3](#0-2) 
5. On the next sync cycle, `fetch_and_validate()`/`download_file()`/`http_download()` issues an outbound `GET` from the victim's node to the attacker-chosen internal/loopback URL. [6](#0-5)

```python
async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
