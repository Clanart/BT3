### Title
Batch-abort in `handlers::response::handle` lets a single already-answered/duplicate `GetResponse` in a relayed batch revert all other legitimate responses bundled with it - ([File: modules/ismp/core/src/handlers/response.rs])

### Summary
The externally reported bug's core invariant is: a shared, depletable resource is checked for availability at *request* time, but the actual consumption happens later in an *async batch operation*; if a second party's action already consumed the resource by the time that batch operation executes, the whole batch call reverts, denying delivery to items that were otherwise perfectly valid. The Hyperbridge ISMP GET-response handler, `modules/ismp/core/src/handlers/response.rs`, reproduces the same "single bad item aborts the whole batch" pattern for a different resource: response receipts and request commitments, in a permissionless, concurrently-racing relayer network.

### Finding Description
`handle()` in `response.rs` first runs an up-front validation loop over every `GetResponse` in the incoming `ResponseMessage` batch (lines 47-68): [1](#0-0) 

For each `get` in the batch it checks timeout, destination chain match, existence of the request commitment, and finally whether a `response_receipt` already exists for that response:

```rust
if host.response_receipt(&res).is_some() {
    Err(Error::DuplicateResponse { meta: (&res).into() })?
}
```

Because this loop uses the `?` operator, the very first failing item propagates an `Err` out of the *entire* `handle()` function via the outer `-> Result<MessageResult, anyhow::Error>` signature — before any of the batch's other (unrelated, still-valid) `GetResponse`s reach the second loop (lines 78-114) that actually verifies state proofs and invokes `cb.on_response(...)`.

This is the direct structural analog of the report's `selectRandomCards`/`fulfillRandomWords` flaw: multiple relayers can legitimately race to deliver responses for the same set of outstanding GET requests (this is the expected "relay race" model documented for Hyperbridge relayers, e.g. `docs/content/developers/explore/nexus/relayer.mdx`, which explicitly rewards whichever relayer "wins the relay race"). If Relayer A's transaction, that answers response `X`, lands in the same block/near-simultaneously as Relayer B's larger batch transaction that *also* includes `X` bundled together with `Y`, `Z`, ... (still-unanswered, fully valid) responses, then when B's transaction executes:
- `host.response_receipt(X)` now returns `Some(...)` (A got there first),
- the loop hits `Err(Error::DuplicateResponse)?` on `X`,
- the whole `handle()` call reverts,
- `Y` and `Z`'s valid, correctly proven responses are **not** recorded even though B paid gas and held valid proofs for them.

By contrast, the request handler (`modules/ismp/core/src/handlers/request.rs`) does **not** have this defect: its per-item processing is done inside a `.map(...).collect::<Vec<_>>()` that returns a per-item `Result` without an early `?` that aborts the whole batch (line 132), so one bad request in a batch does not sink the others.

### Impact Explanation
This lets an unprivileged party (a competing relayer, or the original relayer's own retry race, or even the responder submitting overlapping batches by accident) grief the delivery of legitimate, already-proven `GetResponse`s that are bundled together with one duplicate/timed-out entry. Since `GET` requests carry a `timeout`, a party repeatedly front-running one entry of a resubmitted batch can indefinitely stall delivery of the surviving entries until the GET requests time out. This is exactly the failure Hyperbridge's own timeout-handling architecture must guard against per the stated pivot: "Request, response, and timeout paths must bind chain id, module/app identity, commitment uniqueness, and one-time receipt handling on both Substrate and EVM." Concrete downstream consequences of a stalled GET response include stalled fund-recovery paths that rely on GET responses, such as the Intent Gateway's source-chain cancellation flow, which dispatches a `DispatchGet` and only refunds escrow via `withdraw()` once the empty-proof `GetResponse` lands (`docs/content/developers/evm/intent-gateway/overview.mdx`).

### Likelihood Explanation
High — this requires no malicious relayer, prover, or admin, only two independent relayers (or one relayer resubmitting an overlapping batch after a race) operating under the protocol's own permissionless, incentivized "relay race" model. No signature forgery, no consensus assumption compromise, and no special timing beyond ordinary block-inclusion races is needed.

### Recommendation
Process each `GetResponse` independently, the same way `request.rs` already does: instead of an up-front loop that returns `Err(...)?` on the first duplicate/timed-out/unknown item (aborting the whole message), collect per-item results (e.g. via `.map(...).collect::<Vec<_>>()`) so a duplicate or stale entry in the batch is skipped/recorded as an error for that entry only, while the remaining valid `GetResponse`s in the same message are still verified and dispatched to `on_response`.

### Proof of Concept
1. Two GET requests `R1` and `R2` are outstanding on Hyperbridge, both destined for the same state machine at the same proof height.
2. Relayer A submits a `ResponseMessage` containing only `R1`'s response; it lands first and calls `store_response_receipt` for `R1`.
3. Relayer B, who built its batch before observing A's inclusion, submits a `ResponseMessage` containing `{R1, R2}` (bundled for gas efficiency), with valid state proofs for both.
4. In `handle()`, the up-front loop (lines 47-68) iterates `R1` first: `host.response_receipt(R1)` is now `Some(...)` (set by A), so `Err(Error::DuplicateResponse)?` fires immediately.
5. The entire `handle()` call returns `Err`, so `R2`'s valid, correctly proven response is never verified or dispatched to its module's `on_response`, even though B held a fully valid proof for it and paid gas for the attempt.
6. If `R2` is time-critical (e.g., an Intent Gateway cancellation GET), B must detect the specific failure, remove `R1`, and resubmit `{R2}` alone before `R2`'s timeout elapses, or the underlying flow it triggers is delayed until the request times out.
