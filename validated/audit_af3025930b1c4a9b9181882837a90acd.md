### Title
Unchecked ERC20 `transfer` in `incentiveDeposit` allows silent reward-payment failure while user's WOM deposit is irreversibly taken - ([File: wombat/ArbWomUp.sol], [File: wombat/ArbWomUp2.sol])

### Summary
`ArbWomUp.incentiveDeposit()` and `ArbWomUp2.incentiveDeposit()` take a user's WOM deposit via `safeTransferFrom` (which reverts on failure), but then pay the promised USDT/BUSD reward using a raw, unchecked `IERC20(...).transfer(...)` call whose boolean return value is never checked. Because `claimedReward[msg.sender]` and `userWOMDeposited[msg.sender]` are updated unconditionally regardless of whether the reward transfer actually succeeded, a token that returns `false` on failure (rather than reverting) lets the contract silently record the user as "paid" while the WOM they deposited is permanently retained by the contract, with no user-facing way to reclaim it.

### Finding Description
In `wombat/ArbWomUp.sol`: [1](#0-0) 
the function computes `rewardToSend`, calls `_deposit(_amount)` (which does `IERC20(wom).safeTransferFrom(msg.sender, address(this), _amount)` and is state-changing and irreversible from the user's perspective — there is no user withdrawal function for `wom`), increments `claimedReward[msg.sender]`, and only then attempts to pay the reward with a bare `IERC20(usdt).transfer(msg.sender, rewardToSend)` whose return value is discarded.

The same pattern exists in `wombat/ArbWomUp2.sol`: [2](#0-1) 
where the non-bull-mode branch pays with an unchecked `IERC20(busd).transfer(msg.sender, rewardToSend)` after `claimedReward` has already been incremented.

If the reward token (`usdt`/`busd`, which per the code comments are 18-decimal tokens rather than canonical mainnet Tether) is any non-standard ERC20 implementation that returns `false` on failure instead of reverting (e.g., due to an internal pause/blacklist/allowance quirk), the `transfer` call does not revert, so the whole transaction (including the WOM deposit and the `claimedReward` bookkeeping) completes successfully and emits `USDTRewarded`/`BUSDRewarded` events despite the user never receiving the reward token. Because `claimedReward` is already incremented, the user cannot re-claim the missed reward, and because `_deposit` already recorded `userWOMDeposited` and moved the WOM into the contract (only retrievable by the owner via `transferToAdmin`), the user's WOM is irrecoverable from the user side.

This is the exact bug class from the external report: a token transfer whose success is never validated, letting the protocol emit a "successful payment" event and advance accounting state while the actual transfer silently fails.

### Impact Explanation
An ordinary user who calls `incentiveDeposit` deposits real WOM tokens (correctly enforced via `safeTransferFrom`) in exchange for a USDT/BUSD reward. If the reward-side transfer silently fails, the user's WOM is retained by the contract with no path to recovery (only the contract owner can move the WOM out via `transferToAdmin`), while `claimedReward` has already been marked as paid, permanently barring any renewed reward claim for the same WOM amount. This is a direct loss of user funds caused purely by an unprivileged user's own transaction, not by any admin action.

### Likelihood Explanation
The trigger condition (reward token returning `false` instead of reverting) depends on the specific ERC20 implementation deployed at the `usdt`/`busd` address, which is set once via `__arbWomUp_init`/`setup`. Any token behaving in a non-strict-revert manner on failed transfers (a well-documented category of "unsafe" ERC20 behavior, which is precisely why `SafeERC20.safeTransfer` exists and is already used elsewhere in this same contract for the deposit leg) would trigger this on every affected call, and the code path is reachable by any unprivileged wallet simply by calling `incentiveDeposit`.

### Recommendation
Replace the raw `IERC20(usdt).transfer(...)` / `IERC20(busd).transfer(...)` calls with `SafeERC20.safeTransfer` (the library is already imported and used via `using SafeERC20 for IERC20;` and `safeTransferFrom`/`safeApprove` elsewhere in the same contracts), or explicitly `require()` the boolean return value, so that a failed reward transfer reverts the entire deposit transaction instead of silently completing it.

### Proof of Concept
1. Deploy `ArbWomUp` (or `ArbWomUp2`) with `usdt`/`busd` pointed at an ERC20 implementation that returns `false` on a failed `transfer` (e.g., due to insufficient allowance-independent internal restriction, pause flag, or blacklist) rather than reverting.
2. A user calls `incentiveDeposit(amount)`. `_deposit` succeeds via `safeTransferFrom`, taking the user's WOM.
3. `claimedReward[msg.sender] += rewardToSend` executes unconditionally.
4. `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` (no revert); the `USDTRewarded` event is still emitted.
5. The transaction completes successfully: the user's WOM is now locked in the contract, `claimedReward` reflects a reward the user never received, and the user has no built-in mechanism to reclaim either the WOM or the missed reward.

    function incentiveDeposit(
        uint256 _amount, uint256 _minMGPRec, bool _bullMode
    ) external _checkAmount(_amount) whenNotPaused nonReentrant {
        if (_amount == 0) return;

        uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender);
        _deposit(_amount);
        claimedReward[msg.sender] += rewardToSend;
        
        if (_bullMode) {
            _bullMGP(rewardToSend, _minMGPRec, msg.sender);
        } else {
            IERC20(busd).transfer(msg.sender, rewardToSend);
            emit BUSDRewarded(msg.sender, rewardToSend);
        }
    }
