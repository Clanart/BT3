### Title
Copilot conflict resolution overwrites externally-edited files using a stale in-memory working-directory snapshot - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions` decides whether to overwrite a conflicted file with Copilot's stored resolution based on an in-memory `state.changesState.workingDirectory.files` snapshot fetched once at function entry, rather than re-reading live git status right before each write. This mirrors the Deriverse pattern: a safety decision (skip overwrite / don't liquidate) is made from a stale cached value while the actual mutating action (`writeFile`) happens afterward without re-validating against current on-disk state.

### Finding Description
In `_applyCopilotConflictResolutions`, the function grabs `state` once via `this.repositoryStateCache.get(repository)` at the top [1](#0-0) , and then loops over `copilotResolutions`, using that same stale `state.changesState.workingDirectory.files` snapshot to decide whether a file was "resolved externally" and should be skipped, before writing Copilot's content to disk with `writeFile` [2](#0-1) .

The code comment explicitly states the intended invariant: "If the user resolved this file externally (e.g. in their editor) while the result dialog was open, git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work, so skip it..." [3](#0-2) . However, the check uses `state.changesState.workingDirectory.files`, a cached snapshot captured when the function started — not a fresh `getStatus()`/`_loadStatus()` call taken immediately before each write. This snapshot can be arbitrarily old relative to the moment the user clicks "Continue" in `CopilotConflictsDialog.onContinue`, which calls `dispatcher.applyCopilotConflictResolutions(repository)` directly without triggering any status refresh beforehand [4](#0-3) .

Because the dialog itself can remain open for an extended period while the user reviews/edits files in an external editor, and the loop iterates through multiple files performing async `resolveWithin`/`writeFile` operations without ever re-querying git status between iterations, the guard is checking against data that may not reflect the true current on-disk conflict-resolution state at write time. This is the same broken invariant as the reported bug: a protective decision is made using a value captured before the state-changing action, instead of the value valid at the time of the action.

### Impact Explanation
If a user resolves a conflicted file externally (in an editor, removing markers) between when the stale `state` snapshot was captured and the moment `_applyCopilotConflictResolutions` runs the write, the stale check can fail to detect that the file is already resolved, causing Copilot's stored `resolution.resolvedContent` to overwrite the user's manual resolution — silently clobbering their work, exactly the scenario the code comment says it is trying to prevent. This results in silent corruption of what the user is about to commit, matching the "silent corruption of what the user commits" impact category.

### Likelihood Explanation
The likelihood depends on timing between the in-memory `state` snapshot being taken and the async write loop executing, and on the dialog remaining open long enough for the user (or an external process/tool touching the working directory) to modify the file. Since the resolution loop does multiple awaited I/O operations (`resolveWithin`, `writeFile`, final `git add`) without refreshing status in between, and the entry snapshot is taken once regardless of how long the dialog was open, there is a plausible window for staleness, though exploiting it requires the user to actively edit the file in an editor while the dialog is open — a normal, expected workflow this feature explicitly claims to support safely.

### Recommendation
Before writing each Copilot resolution to disk, re-fetch current git status (e.g., via `getStatus`) rather than relying on the `state` snapshot captured at function entry, and use that fresh result to decide whether the file's conflict markers have already been resolved externally. This mirrors the mitigation recommended in the original report: perform the state-affecting checks (`check_funding_rate`/`check_soc_loss` equivalent — here, refreshing working directory status) immediately before the decision is used, not before it becomes stale.

### Proof of Concept
1. Start a merge/rebase/cherry-pick with conflicts and enable Copilot conflict resolution so `copilotResolutions` is populated and the `CopilotConflictsDialog` is shown.
2. While the dialog is open, manually resolve one of the conflicted files in an external editor (remove all conflict markers) — but do not close the dialog.
3. Click "Continue" quickly enough that the app's cached `state.changesState.workingDirectory.files` (captured before or at dialog-open time) still reports the file as conflicted with markers, i.e. before any refresh cycle updates it.
4. `_applyCopilotConflictResolutions` evaluates `onDiskFile` from the stale `state` and finds `isConflictedFileStatus(...) && !hasUnresolvedConflicts(...)` false (since the cached entry still shows unresolved markers), so it does **not** skip the file.
5. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` executes, overwriting the user's manual edits with Copilot's resolution, and the file is staged and committed with the wrong content — silently discarding the user's actual fix.

Note: I was unable to fully trace every intermediate refresh point (e.g., whether some other code path forces a `_loadStatus` call between dialog-open and `onContinue` that would narrow the staleness window) due to index size limits on cross-file event wiring; a Devin session with full repository access would allow tracing all call sites of `_loadStatus`/`emitUpdate` relative to `CopilotConflictsDialog` lifecycle to precisely bound the exploitable window.
