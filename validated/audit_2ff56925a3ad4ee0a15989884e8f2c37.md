### Title
Permanent freezing of escrowed native coins when a native-ERC20 `TokenPair`'s backing contract self-destructs - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`x/erc20` lets a native Cosmos coin be escrowed in the module account in exchange for an EOA-owned ("native ERC20"/`OWNER_EXTERNAL`) ERC20 token via `ConvertCoin` → `ConvertCoinNativeERC20`. The only way to reclaim the escrowed coin is `ConvertERC20`, which requires the `TokenPair` to still exist and be enabled. Both `ConvertERC20` and `ConvertCoin` contain "lazy cleanup" logic that deletes the `TokenPair` entirely (`DeleteTokenPair`) the moment the backing ERC20 contract is found to have no code (i.e., it self-destructed). Once deleted, `GetTokenPairID` returns nothing and any future `ConvertERC20` call for the same denom/contract fails with `ErrTokenPairNotFound` — permanently orphaning any native coin still escrowed in the `erc20` module account for that pair.

### Finding Description
`ConvertCoinNativeERC20` escrows native coins in the `erc20` module account and unescrows the equivalent ERC20 balance to the receiver: [1](#0-0) 

The reverse path, `ConvertERC20`, is gated by `MintingEnabled`, which requires the `TokenPair` to exist and be `Enabled`: [2](#0-1) 

Both `ConvertERC20` and `ConvertCoin` contain identical "cleanup" logic: if the ERC20 contract account has no code hash (self-destructed), the `TokenPair` is deleted outright, and the call returns `nil, nil` (no conversion performed): [3](#0-2) [4](#0-3) 

`DeleteTokenPair` removes the pair from every index (`ERC20Map`, `DenomMap`, `Allowances`): [5](#0-4) 

For an `OWNER_EXTERNAL` (native ERC20) pair, the ERC20 contract is an ordinary EOA-deployed contract, not module-owned. Its deployer/owner can call `selfdestruct` at any time via a normal EVM transaction — no privileged or governance action is required. Once the contract is destroyed:
1. Any subsequent `ConvertERC20`/`ConvertCoin` call for that denom/contract hits the `!acc.HasCodeHash()` branch and permanently deletes the `TokenPair`.
2. There is no other keeper method that recreates a `TokenPair` for the same denom pointing at a live contract, and the coins previously escrowed via `ConvertCoinNativeERC20` remain sitting in the `erc20` module account (`types.ModuleName`) indefinitely, with no `MsgServer` entrypoint left that can reference them (both `GetTokenPairID` and `GetTokenPair` return not-found for the deleted mapping).

This mirrors the reNFT bug's root cause exactly: a mutable "enablement" record (hook status / token-pair existence) is checked at the *closing/reverse* leg of a two-step flow, and an ordinary, non-privileged action (disabling the hook / destroying the backing contract) that occurs *after* the first leg already escrowed value makes the reverse leg permanently unreachable, leaving user value stuck.

### Impact Explanation
Native coins that were legitimately escrowed by users during `ConvertCoin` become permanently unrecoverable once the paired ERC20 contract self-destructs and any actor (including the attacker who owns the contract, or even an unrelated caller attempting a conversion) triggers the lazy-delete path. This is an irreversible freezing/loss of user funds held in the `erc20` module escrow account, matching the "Critical permanent freezing … of … escrowed assets" impact class.

### Likelihood Explanation
Likelihood is meaningful but bounded: it requires (a) an `OWNER_EXTERNAL` token pair to exist (native-ERC20 pairs are registered — permissionless registration is supported via the `permissionless_registration` param, or via governance `RegisterERC20`), (b) at least one user having escrowed native coin via `ConvertCoin` against that pair, and (c) the pair's ERC20 contract owner deliberately or accidentally self-destructing the contract. The self-destruct step is fully unprivileged — it's an ordinary EVM transaction the contract's deployer (or the contract logic itself) can execute — so a malicious contract owner can intentionally rug users who converted coins into their token, or the loss can occur unintentionally on legitimate contract upgrades/kills.

### Recommendation
Do not silently delete the `TokenPair` and forfeit the escrow relationship on self-destruct detection. Instead:
- Keep the `TokenPair` (or a tombstoned record of it) so escrowed native coins can still be refunded/burned/redeemed by their original converters, or
- Before deleting the pair, sweep/burn any coins currently escrowed under that denom in the module account and only then delete the mapping, or
- Track escrowed amounts per (address, pair) so that even after contract self-destruction, `ConvertERC20`-equivalent refund logic can restore the caller's native coin without depending on the destroyed contract's liveness.

### Proof of Concept
1. Register a native-ERC20 `TokenPair` for an EOA-deployed ERC20 contract `C` (denom `X`, `OWNER_EXTERNAL`) via `RegisterERC20`.
2. Alice calls `ConvertCoin` with coin `X`, escrowing her native coins into the `erc20` module account and receiving ERC20 balance on contract `C` (`ConvertCoinNativeERC20`, `x/erc20/keeper/msg_server.go:237-306`).
3. The owner of `C` calls `selfdestruct` on the contract via a standard EVM transaction.
4. Anyone submits `ConvertERC20` (or `ConvertCoin`) referencing contract `C`/denom `X`. `MintingEnabled` still finds the (not-yet-deleted) pair, so the check passes, then the `!acc.HasCodeHash()` branch fires, `DeleteTokenPair` is called, and the request returns `nil, nil` with no conversion executed.
5. `GetTokenPairID(ctx, "X")` and `GetTokenPairID(ctx, C.Hex())` now return empty, so no future `ConvertERC20` call can reference the denom/contract again.
6. Alice's native coins deposited in step 2 remain in the `erc20` module account balance with no `MsgServer` method able to reference the now-deleted pair to redeem them — permanently frozen.

func (k Keeper) MintingEnabled(
	ctx sdk.Context,
	receiver sdk.AccAddress,
	token string,
) (types.TokenPair, error) {
	if !k.IsERC20Enabled(ctx) {
		return types.TokenPair{}, errorsmod.Wrap(
			types.ErrERC20Disabled, "module is currently disabled by governance",
		)
	}

	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	if !pair.Enabled {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrERC20TokenPairDisabled, "minting token '%s' is not enabled by governance", token,
		)
	}

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}
