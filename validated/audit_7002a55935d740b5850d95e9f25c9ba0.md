### Title
Gasless bundle-queue admission uses a shared `RLock` while mutating `knownTxs`, allowing raced tx submissions to exceed `MaxBundleTxsInQueue` - (File: `kaiax/gasless/impl/tx_pool.go`)

### Summary
`GaslessModule.PreAddTx` is the admission hook invoked by the tx pool for every incoming gasless approve/swap transaction to enforce the configured queue-size cap (`MaxBundleTxsInQueue`). It reads the current queue count and then inserts the new transaction into the shared `knownTxs` map, but does so entirely under a **read lock** (`g.knownTxsMu.RLock()`), even though the insertion path mutates the map.

### Finding Description
`PreAddTx` acquires `g.knownTxsMu.RLock()` (a shared/read lock) and, while holding only this shared lock, both reads the current queue size via `g.knownTxs.numQueue()` and mutates the map via `g.knownTxs.add(tx, TxStatusQueue)`: [1](#0-0) 

Because `RLock` allows multiple goroutines to hold the lock concurrently, two or more concurrent calls to `PreAddTx` (triggered by concurrent gasless-bundle tx submissions to the node, e.g. via RPC `eth_sendRawTransaction`/`sendRawTransaction` racing against each other) can each observe `g.knownTxs.numQueue() < MaxBundleTxsInQueue` before any of them has inserted its transaction, and each then proceeds to call `g.knownTxs.add(...)`. This is a direct TOCTOU (check-then-act) race identical in structure to the Pterodactyl advisory: the limit check happens without holding an exclusive lock over the resource being created, so a burst of concurrent requests all pass validation and all commit, pushing the queue past its configured cap.

Separately, `knownTxs.add` itself performs unsynchronized read-then-write map operations (`k.get`, then `k[tx.Hash()] = ...`, then `updateMetrics`) — concurrent execution of this function from multiple `RLock` holders is also a Go map data race (undefined behavior / possible panic on concurrent map writes), compounding the severity beyond a pure logical race. [2](#0-1) 

By contrast, the corresponding promotion/eviction path (`IsReady`, `PreReset`, `PostReset`) correctly takes the **exclusive** `Lock()` before mutating the same `knownTxs` map, confirming that `PreAddTx`'s use of `RLock()` is the outlier/bug: [3](#0-2) [4](#0-3) 

The existing unit test only exercises `PreAddTx` sequentially and does not catch the race: [5](#0-4) 

### Impact Explanation
`MaxBundleTxsInQueue` is meant to bound the number of gasless (approve/swap) transactions the node will hold in `txpool.queue`, protecting the pool from being flooded and from unbounded gasless-lending exposure (each bundle tx is later serviced by the fee-payer/lending mechanism in `GetLendTxGenerator`/`builder.go`). An attacker who submits a large burst of concurrently-processed gasless transactions can bypass this admission control and force the node to admit and track more queued gasless bundle transactions than configured, similarly to how the Pterodactyl bug allowed exceeding per-server resource caps. This can be used to exhaust queue/memory resources reserved for gasless transactions and to increase the node's/fee-payer's exposure beyond the operator-configured safety limit. Because the underlying map access is also unsynchronized under concurrent `RLock` holders, the impact can extend to node crashes (concurrent map write panic) in addition to resource-limit bypass.

### Likelihood Explanation
Any unprivileged party can submit raw transactions concurrently to a node's RPC endpoint (gasless approve/swap transactions require no special privilege). Because Go RPC handlers for transaction submission commonly run on separate goroutines, achieving concurrent invocation of `PreAddTx` for distinct transaction hashes is straightforward — no precise timing tricks beyond ordinary concurrent request submission are needed. This makes the race easily reachable by an external actor without any privileged access.

### Recommendation
Change `PreAddTx` to acquire the exclusive write lock (`g.knownTxsMu.Lock()`) instead of `RLock()`, since it both reads (`numQueue`) and writes (`add`) the shared `knownTxs` map within the same check-then-act sequence. This restores atomicity of the check-and-insert operation and removes the underlying data race on the map.

### Proof of Concept
1. Configure a `GaslessModule` with a small `MaxBundleTxsInQueue` (e.g. `1`).
2. From N goroutines, concurrently construct N distinct valid gasless approve transactions (different senders, each a valid `IsBundleTx`) and call `g.PreAddTx(txN, false)` simultaneously (mirroring how the tx pool would invoke this hook for concurrently-arriving RPC transactions).
3. Because `RLock()` permits concurrent readers, several goroutines can pass the `numQueue() >= MaxBundleTxsInQueue` check before any of them completes `knownTxs.add`, resulting in `g.knownTxs.numQueue()` ending up greater than the configured `MaxBundleTxsInQueue` (observable via `require.LessOrEqual(t, g.knownTxs.numQueue(), maxQueue)` failing under `go test -race`, which will also likely report a concurrent map read/write race in `knownTxs.add`/`knownTxs.get`).

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}

func TestPreAddTxQueueLimit(t *testing.T) {
	log.EnableLogForTest(log.LvlError, log.LvlTrace)

	newModule := func(maxQueue uint) *GaslessModule {
		cfg := *gasless.DefaultGaslessConfig()
		cfg.MaxBundleTxsInQueue = maxQueue
		g := NewGaslessModule()
		dbm := database.NewMemoryDBManager()
		backend := backends.NewSimulatedBackendWithDatabase(dbm, testAllocStorage(), testChainConfig)
		nodekey, _ := crypto.GenerateKey()
		require.NoError(t, g.Init(&InitOpts{
			ChainConfig:   testChainConfig,
			GaslessConfig: &cfg,
			NodeKey:       nodekey,
			Chain:         backend.BlockChain(),
			NodeType:      common.ENDPOINTNODE,
		}))
		return g
	}

	bundleTx := func() *types.Transaction {
		privkey, _ := crypto.GenerateKey()
		return makeApproveTx(t, privkey, 0, ApproveArgs{Spender: common.HexToAddress("0x1234"), Amount: abi.MaxUint256})
	}

	// --gasless.max-bundle-txs-in-queue <= 0 maps to the math.MaxUint64 "no limit"
	// sentinel (config.go).
	t.Run("no limit sentinel accepts on empty queue", func(t *testing.T) {
		g := newModule(math.MaxUint64)
		tx := bundleTx()
		require.True(t, g.IsBundleTx(tx))
		require.NoError(t, g.PreAddTx(tx, false))
		require.Equal(t, 1, g.knownTxs.numQueue())
	})

	t.Run("finite limit still enforced", func(t *testing.T) {
		g := newModule(1)
		require.NoError(t, g.PreAddTx(bundleTx(), false))
		require.ErrorIs(t, g.PreAddTx(bundleTx(), false), ErrBundleTxQueueFull)
	})
}
