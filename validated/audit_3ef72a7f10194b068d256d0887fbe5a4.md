## Analog Found: Stale line-index diff selection is silently re-applied against a freshly re-diffed file, corrupting partial commits

### Title
Partial-commit line selection is validated against line *position*, not line *content*, letting a changing working file corrupt what actually gets committed - ([File: app/src/lib/git/apply.ts])

### Summary
The reported bug is a classic TOCTOU/front-run: state the user reviewed (the vault's mintable amount) is silently changed before the state-changing action (the sale) completes, and the system has no mechanism to detect or block that the reviewed state and the acted-upon state diverged. The Desktop analog is the "partial commit" (line-by-line staging) feature. When a user checks/unchecks individual diff lines to build a commit, the app stores only line *indices* in a `DiffSelection`. When the commit is actually created, Desktop re-reads the file from disk and regenerates the diff, then blindly reapplies the old index-based selection to the new diff's hunk layout via `formatPatch`. If the file content shifts between the moment the user made a selection and the moment the commit is executed (e.g. because a git clean/smudge filter or other repository-defined hook shipped in a cloned/fetched repository transforms the file on access), the indices no longer point at the same logical lines, and the wrong content is silently committed - with no user-visible warning that the request "diverged" from what was reviewed.

### Finding Description
`DiffSelection` records selected lines as an index/bitmap over the diff's hunk structure, keyed by `hunk.unifiedDiffStart + lineIndex`, not by line content or a content hash. `app-store.ts` explicitly acknowledges the underlying race but only handles it defensively for *display* purposes: [1](#0-0) 
This comment shows the app is aware that "the diff might have changed dramatically since last we loaded it," yet the fix applied only prunes now-invalid indices — it does nothing to guarantee that a still-valid index refers to the *same* line the user actually selected.

The dangerous path is at commit time. `applyPatchToIndex` re-fetches a brand-new diff straight from the working directory right before staging: [2](#0-1) 
It then hands this freshly computed diff, together with the *old* `file.selection` (built by the UI against a possibly older diff), to `formatPatch`. `formatPatch` determines what to include purely by `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is derived from the new diff's hunk layout: [3](#0-2) 
There is no check anywhere in this pipeline that the line at a given index in the new diff has the same text as the line at that index in the diff the user actually looked at when selecting lines. `stageFiles` in `update-index.ts` is the caller that invokes `applyPatchToIndex` for every partially-selected file during commit, confirming this is the real commit path (not just a preview path): [4](#0-3) 

The corrupted value is the index-based `DiffSelection` bitmap: it is trusted as a proxy for "the content the user reviewed and approved," but it is only ever validated against hunk indices, never against content, across a window where the working file can change (e.g. via repository-provided clean/smudge filters declared in a cloned repo's `.gitattributes`, or any other process that rewrites the file between the UI diff load and the commit). Because both `updateChangesWorkingDirectoryDiff` (display refresh) and `applyPatchToIndex` (commit-time patch build) independently regenerate the diff at different times, there are at least two points where content can drift out from under a stable index-based selection with no reconciliation.

### Impact Explanation
If the underlying file content shifts between the time the user reviews/selects diff lines and the time Desktop stages the commit, the user can end up committing or pushing content they never selected — silently. This maps directly to the "silent corruption of what the user commits or pushes" impact category: a user could believe they excluded a sensitive line (e.g. a credential accidentally pasted into a file, or a debug statement) while the line that actually gets included/excluded is determined by stale positional bookkeeping rather than the reviewed content, and vice versa (an intended change could be silently dropped or a stray line silently added). The failure mode is invisible in the UI because no error is raised — `git apply` will happily apply a valid-looking patch to the new content as long as indices line up structurally.

### Likelihood Explanation
This requires an attacker-influenced repository that can change file content between the two diff computations — for example via `.gitattributes`-declared clean/smudge filters, or repository content that triggers slow/asynchronous background reprocessing of a working file after it's fetched/checked out. This is within the accepted attacker model ("attacker controls a cloned/fetched repository"). However, the window is narrow (between UI diff refresh and the user clicking Commit) and depends on the victim doing line-by-line partial commits rather than "select all," which somewhat limits real-world frequency. I was not able to fully confirm from the available code whether Desktop disables/sandboxes git clean/smudge filters or other content-mutating repo configuration during diff generation and staging — that would need to be verified in a live Desktop session, since I only have index-limited visibility into the full `diff.ts` / filter-related code paths.

### Recommendation
- Bind `DiffSelection` to line content (e.g., hash the selected line text, not just its index) so that a re-diff after content drift can detect that a previously-selected index no longer corresponds to the same content and either re-map the selection safely or fail loudly instead of silently committing mismatched content.
- Before calling `applyPatchToIndex`, compare the diff the UI last showed the user against the diff about to be used for staging; if they differ in a way that could shift line indices, abort the commit and force the user to re-review the diff before proceeding, similar to the guard rail suggested in the original report for the smart-contract sale flow (i.e., "freeze" the reviewed state until the action is confirmed).
- Consider disabling or sandboxing repository-defined content filters (`clean`/`smudge`, other attribute-driven transforms) during the window between diff display and commit staging for untrusted/newly cloned repositories.

### Proof of Concept
Conceptual reproduction (exact filter-triggering mechanism would need to be validated in a live Desktop instance):
1. Clone a malicious repository that declares a `clean`/`smudge` filter (or otherwise triggers a background file rewrite) on a tracked file, via `.gitattributes`. [5](#0-4) 
2. Modify the tracked file locally; Desktop loads and displays a diff, and the user selects a subset of lines via `changeFileLineSelection`, which stores index-based selection. [6](#0-5) 
3. Before the user clicks "Commit," the repository-controlled filter/background process rewrites the file, shifting line offsets.
4. The user clicks Commit; `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff and applies the old index-based selection against the new hunk layout via `formatPatch`, silently including/excluding different lines than what the user actually reviewed. export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
