### Title
DID recovery attestation uses AGG_SIG_UNSAFE without binding `recovering_coin_id`, enabling signature replay to hijack backup-DID endorsements - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
`create_recovery_message_puzzle()` builds the "attestment" puzzle that a backup DID spends to vouch for a lost DID's recovery. The puzzle emits two conditions: `CREATE_COIN_ANNOUNCEMENT recovering_coin_id` and `AGG_SIG_UNSAFE pubkey newpuz`. The signed message for the `AGG_SIG_UNSAFE` condition is only `newpuz` — it never includes `recovering_coin_id` (the DID coin being recovered). Because `AGG_SIG_UNSAFE` has no domain separation (no coin id/parent/puzzle-hash binding, unlike `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc., see `chia/consensus/condition_tools.py:56-96`), a signature produced for one recovery attempt is a valid signature for *any* message equal to that exact `newpuz` bytestring, regardless of which DID coin it is attached to. ### Finding Description
The backup DID's private key signs only `newpuz` via `AGG_SIG_UNSAFE`: [2](#0-1) 

The `recovering_coin_id` parameter is embedded only in the unsigned `CREATE_COIN_ANNOUNCEMENT` condition and in the puzzle's tree hash (which determines the attestation coin's `puzzle_hash`), not in the signed payload itself. Compare this to the consensus-level AGG_SIG variants, where every opcode except `AGG_SIG_UNSAFE` deterministically appends coin-identity data (`coin.name()`, `parent_coin_info`, `puzzle_hash`, `amount`) plus opcode-specific `additional_data` before signing, precisely to prevent this kind of cross-context replay: [3](#0-2) 

Once a legitimate recovery attestation signature (`sig` over `newpuz`, from `pubkey`) has ever appeared on-chain or in the mempool (which it must, to be broadcast as part of a valid spend bundle), any attacker can:
1. Create their own coin (any amount, e.g. via a `CREATE_COIN` condition in their own spend — permissionless) whose puzzle hash equals `create_recovery_message_puzzle(malicious_recovering_coin_id, newpuz, pubkey).get_tree_hash()`, i.e. the *same* `newpuz`/`pubkey` pair but an attacker-chosen `recovering_coin_id` (any other DID that lists the same backup DID `pubkey` in its `recovery_list`).
2. Spend that coin with an empty solution and the previously observed/leaked signature (no private key needed) to produce a valid `AGG_SIG_UNSAFE` message match plus a `CREATE_COIN_ANNOUNCEMENT` for the attacker's chosen `recovering_coin_id`.
3. Combine this forged attestation with the attacker's own DID recovery spend, since the DID inner puzzle's recovery-mode logic checks for matching backup-DID pubkeys/attestations and their `AGG_SIG_UNSAFE(pubkey, newpuz)` signatures, without any cryptographic binding to which DID coin the backup DID actually intended to endorse.

This is architecturally identical to the reported bug class: a signature scheme omits binding parameters (`recovering_coin_id`, analogous to `tokenId`/`privateWorkerAddress` in the Crestal report) that are used elsewhere in the same protocol flow, letting an attacker splice a legitimately-obtained signature with maliciously chosen out-of-band parameters.

### Impact Explanation
A backup DID's honest endorsement (intended for one specific lost DID's recovery to a specific `newpuz`) can be replayed to complete an unauthorized recovery of a *different* DID coin that lists the same backup pubkey, redirecting control of that DID to `newpuz` (an address the attacker/original recoverer controls) without the second DID owner's consent. This is an unauthorized coin/identity-control theft via forged multisig-like endorsement — a concrete instance of "forged asset identity" / unauthorized coin movement reachable from a single crafted spend bundle by an unprivileged submitter who merely observes a previously-broadcast signature.

### Likelihood Explanation
Exploitability requires: (a) the target DID(s) use the legacy `num_of_backup_ids_needed`/`recovery_list` DID recovery feature with overlapping backup DID pubkeys, and (b) a legitimate attestation signature for that pubkey/`newpuz` pair has been broadcast at least once (observable on-chain or in the mempool by anyone). Given that recovery attestations are inherently broadcast (they must be included in a spend bundle to take effect), condition (b) is trivially satisfied for any DID that has ever performed a recovery. This is a real, low-effort attack path for wallets that still rely on the (deprecated but still consensus-supported) DID `recovery_list` mechanism, though its practical scope is limited to DID configurations that opt into shared backup DIDs across multiple recoverable DIDs.

### Recommendation
Bind the `AGG_SIG_UNSAFE` message to the specific recovery context, e.g. sign `recovering_coin_id + newpuz` (or better, use `AGG_SIG_ME`/coin-bound variants tied to the attestation coin itself) so a signature cannot be reused across different `recovering_coin_id` values. This mirrors the mitigation already applied elsewhere in Chia's condition set (`AGG_SIG_PARENT`, `AGG_SIG_PUZZLE`, etc., all of which bind to coin-specific data before signing).

### Proof of Concept
1. DID `A` and DID `B` both list backup DID pubkey `PK` in their `recovery_list`.
2. Owner of `PK`'s wallet legitimately spends an attestment coin for DID `A`'s recovery, producing `sig = AugSchemeMPL.sign(sk, newpuz_A)` via the `AGG_SIG_UNSAFE` condition from `create_recovery_message_puzzle(A_coin_id, newpuz_A, PK)` (see `chia/wallet/did_wallet/did_wallet_puzzles.py:138-155`). This spend bundle is broadcast/confirmed.
3. Attacker (who does not control `PK`'s private key) observes `sig` on-chain, and wants to redirect DID `B`'s recovery to the same `newpuz_A` address.
4. Attacker sends any amount of XCH to a coin whose puzzle is `create_recovery_message_puzzle(B_coin_id, newpuz_A, PK)` — a permissionless action.
5. Attacker spends that coin with an empty solution, attaching the reused `sig`; the `AGG_SIG_UNSAFE` check passes because the signed message (`newpuz_A`) is identical, and the resulting `CREATE_COIN_ANNOUNCEMENT(B_coin_id)` satisfies DID `B`'s recovery-mode assertion, completing DID `B`'s recovery to `newpuz_A` without any actual authorization from `PK`'s owner for DID `B`.

```python
def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle
```

```python
def make_aggsig_final_message(
    opcode: ConditionOpcode,
    msg: bytes,
    spend_conditions: Coin | SpendConditions,
    agg_sig_additional_data: dict[ConditionOpcode, bytes],
) -> bytes:
    if isinstance(spend_conditions, Coin):
        coin = spend_conditions
    elif isinstance(spend_conditions, SpendConditions):
        coin = Coin(spend_conditions.parent_id, spend_conditions.puzzle_hash, uint64(spend_conditions.coin_amount))
    else:
        raise ValueError(f"Expected Coin or Spend, got {type(spend_conditions)}")  # pragma: no cover

    COIN_TO_ADDENDUM_F_LOOKUP: dict[ConditionOpcode, Callable[[Coin], bytes]] = {
        ConditionOpcode.AGG_SIG_PARENT: lambda coin: coin.parent_coin_info,
        ConditionOpcode.AGG_SIG_PUZZLE: lambda coin: coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_AMOUNT: lambda coin: int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT: lambda coin: coin.puzzle_hash + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_AMOUNT: lambda coin: coin.parent_coin_info + int_to_bytes(coin.amount),
        ConditionOpcode.AGG_SIG_PARENT_PUZZLE: lambda coin: coin.parent_coin_info + coin.puzzle_hash,
        ConditionOpcode.AGG_SIG_ME: lambda coin: coin.name(),
    }
    addendum = COIN_TO_ADDENDUM_F_LOOKUP[opcode](coin)
    return msg + addendum + agg_sig_additional_data[opcode]
```
