### Title
Length-mismatched `Vec<Preprocess>`/`Vec<SignatureShare>` from a peer causes an index out-of-bounds panic in the Bitcoin signing machine - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
CVE-2023-35788 is an out-of-bounds write caused by inconsistent handling of attacker-controlled length fields inside `TCA_FLOWER_KEY_ENC_OPTS_GENEVE` options in `fl_set_geneve_opt`. The analogous flaw in Serai is a length/index trust violation reachable from untrusted peer bytes: `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` index attacker-supplied vectors (`commitments[c]`, `shares.remove(0)`) without ever checking that the per-signer `Vec` produced by `read_preprocess`/`read_share` has the expected length.

### Finding Description
`TransactionMachine::read_preprocess` reads one `Preprocess` per input signature machine, returning a `Vec<Preprocess>` whose length is entirely determined by the *peer's* serialized bytes — there is no check that `preprocess.len() == self.sigs.len()`:

- `read_preprocess` (networks/bitcoin/src/wallet/send.rs:351-353) collects whatever the peer encoded.
- `sign` (send.rs:364-371) then does `commitments[c].clone()` for `c` in `0 .. self.sigs.len()`. If a participant sends a `Vec<Preprocess>` shorter than the number of inputs, indexing `commitments[c]` panics with an out-of-bounds access.
- `read_share`/`complete` (send.rs:409-410, 417-419) has the same shape: `shares.remove(0)` is called once per input on a peer-supplied `Vec<SignatureShare>`; an empty or short vector panics.

These bytes come straight off the wire from the other multisig participants (`read_preprocess`/`read_share` are exactly the untrusted-input sinks enumerated for this audit), so the length field inside the serialized vector is attacker-controlled, exactly as the `geneve_opt` length was attacker-controlled in the CVE.

### Impact Explanation
An out-of-bounds index in safe Rust manifests as a panic rather than memory corruption, but the effect is still an abort of the signing flow at a point where the attacker chose the trigger. Any multisig participant can send a truncated `Vec<Preprocess>` (or `Vec<SignatureShare>`) and panic the victim's `TransactionSignMachine::sign`/`complete` mid-protocol, deterministically killing the signing attempt and liveness of the spend. Since the panic occurs inside `map` over `self.sigs.drain(..)`, the machine is consumed and cannot retry with corrected data.

### Likelihood Explanation
Requires being one of the threshold signers for the Bitcoin multisig — i.e., a participant able to deliver a serialized preprocess/share to the victim. That is precisely the reachable-input class allowed by scope: untrusted bytes fed to `read_preprocess`/`read_share`. No collusion, leaked key, or honest-misuse assumption is needed; one malformed vector suffices.

### Recommendation
Validate the deserialized vector length before indexing: in `sign`, reject (`FrostError::InvalidPreprocess(l)`) when `commitments.len() != self.sigs.len()`; in `complete`, check `shares.len() == number_of_inputs` or return `FrostError::InvalidShare(l)` instead of `remove(0)` on a possibly empty vector.

### Proof of Concept
```rust
// In TransactionSignMachine::sign (send.rs:364-371):
let commitments = (0 .. self.sigs.len())      // e.g. 2 inputs
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone())) // peer sent vec of len 1 -> OOB panic at c == 1
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
```
A malicious participant calls `write` on a `Vec<Preprocess>` containing a single element while the transaction has two inputs; the victim's `read_preprocess` accepts it (no length check), and `commitments[1]` panics with `index out of bounds`. The symmetric trigger is an empty `Vec<SignatureShare>` into `complete`, hitting `shares.remove(0)` on an empty vec.
