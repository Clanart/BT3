### Title
Integer-division rounding in NFT royalty calculation can be exploited to reduce or eliminate royalty payments to zero via trade splitting - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount` and `NFTWallet.royalty_calculation` compute royalties using floor integer division (`//`), analogous to the rounding-down conversion (`_tokensToShares`) flagged in the OperationalStaking report. Because both the maker-side (`royalty_calculation`, used only for UI/summary and taker verification) and offer-construction path (`make_nft1_offer`) use truncating division at multiple points — `amount // offer_side_royalty_split` for `trade_prices`, and `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` in `compute_royalty_amount` — a counterparty crafting/accepting an offer can choose amounts and NFT counts (`royalty_split`, `offer_side_royalty_split`) that drive the computed royalty toward zero, systematically underpaying the royalty recipient just as the audit report describes tokens being "transferred more than it should be" due to rounding.

### Finding Description
`compute_royalty_amount` at [1](#0-0)  computes `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`, performing two successive floor divisions. `royalty_calculation` at [2](#0-1)  performs the same pattern (`abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`). In `make_nft1_offer`, `trade_prices` per-item price is computed as `amount // offer_side_royalty_split` at [3](#0-2)  and later fed into `compute_royalty_amount` to build `royalty_payments` at [4](#0-3) . Since an offer creator (maker) fully controls `offer_dict` (amounts and how many NFTs/fungible assets are bundled into one offer, i.e., `royalty_split`/`offer_side_royalty_split`), they can select amounts such that `abs(offered_amount) // royalty_split` truncates to a value whose `* percentage // 10000` rounds to a smaller-than-intended (or exactly zero) royalty — e.g., `test_small_amount_truncates_to_zero` at [5](#0-4)  already documents a case producing a royalty of `0` from a nonzero offered amount. By splitting a single large trade into several smaller trades (each individually rounding to 0 or a smaller royalty) instead of one large trade, a taker/maker pair can pay materially less cumulative royalty than the NFT creator's configured `royalty_percentage` intends, since each independent settlement's rounding loss is bounded by `royalty_split`/percentage granularity and compounds across trades.

### Impact Explanation
This is a value-extraction bug reachable purely through wallet-level offer construction (`make_nft1_offer`) and offer acceptance — no privileged access, malicious peer, or protocol-level compromise required. It results in systematic underpayment to royalty-enabled NFT creators/royalty addresses, i.e., reward/royalty redirection away from the intended recipient toward the trade counterparties. Because the CLVM enforcement in the ownership-layer transfer program checks against the wallet-supplied `trade_prices_list`/royalty amounts (constructed with this same rounding), an attacker who controls both sides of a trade (or colludes as a counterparty) can structure many small trades to drain royalty income essentially to zero over time, unlike a single one-off rounding error.

### Likelihood Explanation
Medium likelihood: any wallet user creating or accepting NFT offers with royalty-enabled NFTs already goes through this exact code path. Exploitation requires deliberately choosing offer amounts/splits to maximize rounding loss (e.g., many small-amount trades), which is straightforward for a sophisticated trader but not the default behavior of the GUI/CLI, which typically constructs one royalty payment per full trade.

### Recommendation
Round royalty amounts up (ceiling division) or accumulate fractional remainders across split payments in `compute_royalty_amount` and `royalty_calculation`, analogous to the OperationalStaking fix of adjusting `sharesToBurn` upward when truncation occurs, e.g.:
```python
amount = -(-abs(offered_amount) // royalty_split) * percentage
royalty = -(-amount // MAX_ROYALTY_BASIS_POINTS)
```
Ensure the same ceiling/remainder-tracking logic is applied consistently in `make_nft1_offer`'s `trade_prices` computation so the aggregate royalty paid across any offer matches (or exceeds) `percentage` of the total offered value, and cannot be minimized by adjusting `royalty_split`/`offer_side_royalty_split` or trade granularity.

### Proof of Concept
1. NFT creator sets `royalty_percentage = 100` (1%) on an NFT.
2. Maker/taker construct an offer for that NFT with `offered_amount = 50` mojo XCH and `royalty_split = 1`: `compute_royalty_amount(-50, 1, 100)` returns `0` (see `test_small_amount_truncates_to_zero` at [5](#0-4) ), so no royalty is paid despite a nonzero trade value.
3. Repeating this pattern across many small trades (instead of one large trade) lets the pair transfer arbitrarily large cumulative value while paying negligible/zero royalty overall, versus the intended `percentage` cut on the full value — mirroring the reported staking bug where floor-division on a shares/amount conversion under-charges the party that should bear the cost.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
    def royalty_calculation(
        royalty_assets_dict: dict[Any, tuple[Any, uint16]],
        fungible_asset_dict: dict[Any, uint64],
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():
            address, percentage = royalty_info
            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():

                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
```
