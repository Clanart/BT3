### Title
Front-runnable instant reward injection lets an attacker snipe undeserved yield via `BaseRewardPool._provisionReward` - (File: `rewards/BaseRewardPool.sol`)

### Summary
The external report's root cause is that a Curated Vault immediately folds a lump sum of assets into a share-price-determining accumulator (`totalAssets`) the moment a market is (re-)added, letting a sandwiching depositor buy shares cheaply right before the jump and redeem them right after for a disproportionate profit, at existing holders' expense. `BaseRewardPool` in this codebase has the same structural flaw applied to reward accounting: `_provisionReward` immediately folds an entire reward payment into `rewardPerTokenStored` in one shot, weighted only by whoever is currently staked (`totalStaked()`), with no time-vesting or streaming of the reward.

### Finding Description
`_provisionReward` computes the reward-per-token delta and adds it to `rewardInfo.rewardPerTokenStored` in a single, instantaneous step, based on the staked balance at the moment the transaction executes: [1](#0-0) 

This function is reachable from two paths:
- `queueNewRewards`, callable by any `onlyManager` address (typically the operator/manager infra) [2](#0-1) 
- `donateRewards`, which is **fully permissionless** — any unprivileged wallet can call it directly to inject rewards for an already-registered reward token [3](#0-2) 

A user's accrued reward is computed from the delta between the current `rewardPerTokenStored` and the value recorded at the time they last staked/claimed (`userRewardPerTokenPaid`): [4](#0-3) [5](#0-4) 

Because staking/unstaking (via `MasterMagpie` deposit/withdraw, which any unprivileged wallet can call for any registered pool) immediately updates `userRewardPerTokenPaid` to the pre-injection value, an attacker can:
1. Watch the mempool for an upcoming `queueNewRewards`/`donateRewards` call carrying a large reward payment.
2. Front-run it by staking a large amount of the pool's staking token via `MasterMagpie`, which registers `userRewardPerTokenPaid` at the pre-injection level.
3. Let the reward-injection transaction land — `rewardPerTokenStored` jumps instantly based on `totalStaked()` at that moment, which now includes the attacker's freshly deposited stake.
4. Immediately call `getReward`/withdraw to claim a share of the reward proportional to the attacker's stake, despite having contributed none of the time/liquidity that "earned" the reward, and immediately unstake.

This dilutes the reward genuinely due to long-term stakers, exactly mirroring the vault bug class: an atomic, lump-sum update to a per-share/per-token accounting value is exploitable via a stake-before/unstake-after sandwich because the protocol has no mechanism (streaming/vesting, deposit lockups, or minimum holding period) to prevent instantaneous capture of value added in a single block.

### Impact Explanation
This results in direct theft of unclaimed yield from legitimate long-term stakers to the sandwiching attacker, proportional to the size of the reward injection relative to total staked amount at the time — matching the "theft of unclaimed yield" impact category. Every `queueNewRewards` (recurring, e.g., per harvest/emission cycle) and every `donateRewards` call is an attack opportunity, and `donateRewards` requires no privilege at all to trigger (an attacker can even self-trigger the donation as part of the same block/transaction bundle, guaranteeing exploitation reliability rather than depending on mempool visibility of a third-party call).

### Likelihood Explanation
Likelihood is high: the attack requires only standard staking/unstaking calls and, in the `donateRewards` case, the attacker can originate the reward injection itself in the same transaction bundle (flash-stake, self-donate, claim, unstake), removing any dependency on observing another party's mempool transaction. No special permissions, governance action, or oracle manipulation is needed — only capital to stake temporarily (or a flash loan of the staking token, subject to whether the staking token is flash-loanable).

### Recommendation
Stream reward injections over time instead of applying them as an instantaneous lump-sum update to `rewardPerTokenStored` (e.g., a `rewardRate`/`periodFinish` model as used in Synthetix's `StakingRewards`), and/or enforce a minimum staking duration or a cooldown between deposit and reward-eligibility/withdrawal to prevent same-block or same-transaction sandwich extraction of freshly injected rewards.

### Proof of Concept
Conceptual PoC (pattern mirrors the analog report's PoC):
1. Pool currently has `totalStaked() = 100e18`, `rewardPerTokenStored = R0`.
2. Attacker calls `MasterMagpie.deposit(pool, 900e18)` for themselves — `totalStaked()` becomes `1000e18`; attacker's `userRewardPerTokenPaid = R0`.
3. Attacker calls `BaseRewardPool.donateRewards(rewardAmount, rewardToken)` (permissionless) with `rewardAmount = 1000e18` of the reward token.
   - `_provisionReward` executes: `rewardPerTokenStored += (1000e18 * 10**decimals) / 1000e18` → jumps by `1 * 10**decimals` instantly.
4. Attacker calls `getReward` — `earned = balanceOf(attacker) * (rewardPerToken - userRewardPerTokenPaid) / 10**decimals = 900e18 * 1 = 900e18` reward tokens, i.e. 90% of the donated reward, despite having staked for zero elapsed time.
5. Attacker calls `withdraw` to unstake the principal, keeping the 900e18 reward tokens as pure profit, funded by the donation itself and diluting whatever share the pre-existing 100e18 of long-term stakers would otherwise have accrued from future/legitimate emissions using the same accumulator.     function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
