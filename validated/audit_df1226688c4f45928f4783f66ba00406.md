## Analysis

The Init Capital bug is fundamentally a **TOCTOU (time-of-check/time-of-use) value-substitution flaw**: a value (`limitPrice_e36`) is reviewed/relied upon at one point, but the code re-derives/re-uses it at execution time without re-validating it matches what was approved, letting an attacker swap the value in between and corrupt the outcome for the party who didn't get a final say.

GitHub Desktop has a structurally identical pattern in its **partial-commit ("select lines to commit") pipeline**.

### The corrupted value: line-index-based `DiffSelection`

When a user views a file's changes, the diff is loaded and each diff line gets a stable **absolute index** (`hunk.unifiedDiffStart + index`), and the user's checkbox selections are stored against these indices, not against line content: [1](#0-0) 

Note the comment acknowledging that content can shift: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines."* This only prunes indices that no longer exist as includeable lines — it does **not** verify that a still-valid index still refers to the same content the user actually reviewed.

### The re-check happens too late, against fresh data

When the user commits, `stageFiles` → `applyPatchToIndex` is invoked, which **re-fetches a brand-new diff from disk/git** at that moment: [2](#0-1) 

That fresh diff is then fed into `formatPatch`, which blindly re-applies the *stale* `file.selection.isSelected(absoluteIndex)` decisions from the earlier review against the *new* hunk structure: [3](#0-2) 

### Why this is the same bug class

- In the Solidity report, `limitPrice_e36` is checked/displayed once but re-read at fill time, so a front-run mutation between review and execution silently changes the payout.
- In Desktop, the user's line selection is computed against diff hunk indices captured at review time, but `applyPatchToIndex` recomputes the diff at commit time and reapplies the old index-based selection to it. If the tracked file's content/line offsets change between the moment the user reviews the diff and clicks "Commit" (e.g., a build tool, git hook, file watcher, or any process bundled in/triggered by a freshly cloned malicious repository rewrites the file during that window), the absolute indices no longer correspond to the same lines. The result: `formatPatch` can stage/commit content the user never selected/reviewed — a **silent corruption of what the user commits**, one of the explicitly valid impact classes.
- Existing guards don't stop this: `updateChangesWorkingDirectoryDiff` only prunes indices no longer valid; `applyPatchToIndex` has no check that the newly-fetched diff's hunks are unchanged from what the user last saw before it re-applies the stale selection.

### Title
Stale index-based diff selection is silently re-applied to a freshly-fetched diff at commit time, allowing unreviewed content to be committed - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` re-fetches the working directory diff for a file at commit time and reuses the `WorkingDirectoryFileChange.selection` object — whose selections are keyed by absolute diff-line index, not content — that was computed when the user last reviewed the diff in the Changes view. If the file's on-disk content changes between the user's review/selection and the commit action, the line indices no longer map to the same content, and `formatPatch` will include/exclude the wrong lines without the user's knowledge.

### Finding Description
`WorkingDirectoryFileChange.selection` (a `DiffSelection`) records which diff lines the user checked, addressed purely by `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [4](#0-3) . This selection is computed against a diff snapshot loaded into the Changes view, and when the diff is reloaded (e.g. after a status refresh) Desktop only prunes indices that are no longer "includeable," it never re-validates that surviving indices still refer to the same content [1](#0-0) .

At commit time, `applyPatchToIndex` independently re-fetches the diff via `getWorkingDirectoryDiff` [2](#0-1)  and feeds it, together with the stale `selection`, into `formatPatch`, which decides what to include using `file.selection.isSelected(absoluteIndex)` against the newly fetched hunks [3](#0-2) . There is no re-diffing/re-confirmation step comparing the diff the user actually reviewed to the diff being committed against.

### Impact Explanation
If a tracked file's content or line offsets shift between the time the user selects specific lines to stage and the time they click commit (e.g. because a build script, background formatter, git hook, or any file-mutating process bundled with a freshly cloned/fetched malicious repository runs in that window), the stale selection indices can now line up with different content. `git apply --cached` will then stage lines the user never opted into (or drop lines they wanted included), and `createCommit` will commit that patch [5](#0-4) . This is a silent corruption of what the user commits, potentially pushing unreviewed/attacker-influenced content upstream.

### Likelihood Explanation
The window between diff-load and commit is user-controlled but commonly non-trivial (reviewing a large diff, writing a commit message). A malicious repository can ship tooling (npm scripts, git hooks such as `post-checkout`/`post-merge`, editor/formatter integrations) that rewrites tracked files shortly after clone/fetch without any unusual user action beyond opening/using the repo in Desktop, which is within the accepted attacker model ("attacker controls a cloned/fetched repository").

### Recommendation
Before applying the stale selection in `applyPatchToIndex`, compare the newly-fetched diff's hunks against the diff the selection was computed from (e.g. by hashing hunk content or by keeping the original diff alongside the selection object and diffing it against the fresh one). If the content underlying any selected index has changed, refuse to commit that file (or reset its selection) and force Desktop to reload the diff and require the user to reconfirm before staging/committing.

### Proof of Concept
1. Clone a malicious repository containing a tracked file `foo.txt` and a git hook (e.g. `post-checkout`) or background process that, shortly after checkout, rewrites `foo.txt`'s content while preserving similar line counts/positions.
2. In Desktop, open the Changes view for `foo.txt`; a diff is loaded and the user selects specific lines/hunks to stage for a partial commit — this selection is recorded as absolute line indices via `DiffSelection`.
3. Before the user clicks "Commit," the hook/background process rewrites the file's content at those same line positions with different content.
4. The user clicks "Commit." `applyPatchToIndex` re-fetches the diff fresh from disk (now reflecting the rewritten content) and reapplies the old index-based `selection` via `formatPatch`, producing a patch that stages the new, unreviewed content at those indices.
5. `createCommit` commits this patch — the resulting commit silently differs from what the user reviewed and approved on screen.
