## Analysis

The seed bug (`ChiefTrader.sol`) is fundamentally about an intermediary component trusting attacker/controllable input to determine which "identity" (address) a sensitive operation should be executed as, without verifying that identity actually corresponds to what was authorized. The broken invariant is: *"the entity being trusted for a privileged operation is not actually verified to be the one it's assumed to be."*

I found a structurally identical invariant break in GitHub Desktop's credential-helper trampoline, where the "is this host actually GitHub?" classification is derived from attacker-controllable HTTP response content rather than a cryptographic or allow-listed check, and that classification decides whether Desktop auto-launches its "Sign in to GitHub Enterprise" flow against an arbitrary, attacker-chosen origin.

### Title
Credential-helper trusts attacker-supplied `WWW-Authenticate` realm to classify a remote as GitHub, causing GitHub Enterprise sign-in flow to be launched against an attacker-controlled origin - (`app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git performs HTTPS authentication, it forwards any `WWW-Authenticate` response headers from the remote server to Desktop's credential helper as `wwwauth[]` fields. `getEndpointKind()` inspects these attacker-controlled header values and, if any contains `realm="GitHub"`, unconditionally classifies the remote as an `'enterprise'` GitHub host [1](#0-0) . This classification then drives `getCredential()` to automatically invoke the GitHub sign-in UI, pointed at that remote's own origin, whenever no existing account matches it [2](#0-1) .

### Finding Description
`getEndpointKind()` first checks `isGist`, `isDotCom`, `isGHE` (all safe, hostname-based checks), then falls back to inspecting the `wwwauth[]` credential fields, which are populated by Git directly from the HTTP response headers returned by whatever server the git operation happened to contact:

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
``` [3](#0-2) 

There is no verification that the host is actually a GitHub Enterprise server (no TLS pinning, no API probe at this branch, no allow-list) — any HTTPS git server can return `WWW-Authenticate: Basic realm="GitHub"` on a 401 and be classified as `'enterprise'`.

This classification feeds directly into `getCredential()`:
```
if (endpointKind !== 'generic' && !accounts.some(a => a.endpoint === apiEndpoint)) {
  ...
  const account = await ui.promptForGitHubSignIn(endpoint)
``` [4](#0-3) 

`promptForGitHubSignIn(endpoint)` then drives the real GitHub Enterprise sign-in flow against the attacker's own origin (parsed straight from the malicious remote URL):
```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
``` [5](#0-4) 

`setEndpoint()` in `SignInStore` accepts any HTTPS URL (only rejecting non-HTTPS and redirecting `github.com`/`api.github.com` to the dotcom flow), then transitions straight to the `Authentication` step for that attacker-chosen endpoint: [6](#0-5) . From there the user is shown a "Sign in to your GitHub Enterprise" dialog (`app/src/ui/welcome/sign-in-enterprise.tsx`, `app/src/ui/sign-in/sign-in.tsx`) that is functionally identical to a legitimate Enterprise sign-in, but is bound to the attacker's server. Completing sign-in (basic auth or browser/OAuth flow) sends the user's real GitHub credentials/OAuth code directly to that attacker-controlled origin via `requestOAuthToken(endpoint, action.code)` / basic-auth POST at that endpoint [7](#0-6) .

Existing guards do not stop this: `getEndpointKind` only checks hostname equality for `github.com`/`*.ghe.com` in the early branches, but the `wwwauth[]` fallback branch has no hostname/TLS validation at all — it trusts a free-form string from the response body/headers of the very server being connected to. There is also no display, in the sign-in dialog, warning the user "this is not a known/verified GitHub Enterprise instance" versus a normal manual GHE sign-in.

### Impact Explanation
This allows an attacker who controls a git remote (e.g., a URL added by the user by pasting from an issue/PR, a `x-github-client://` deep link, a malicious mirror/proxy, or a compromised/spoofed remote) to make Desktop autonomously launch its trusted "Sign in to GitHub Enterprise" UI pointed at the attacker's server. If the user completes the flow (which they are primed to do, since Desktop itself surfaced the prompt as part of a normal git operation), their GitHub Enterprise credentials or OAuth authorization code are sent directly to the attacker's server — i.e., credential/OAuth token exfiltration and unauthorized account binding, matching the "unprivileged... credential/token exfiltration... unauthorized OAuth or account binding" impact categories.

### Likelihood Explanation
The trigger is a single natural user action (performing a fetch/push/pull/clone against an attacker-supplied HTTPS remote) plus a server response fully controlled by the attacker (`WWW-Authenticate: realm="GitHub"`) — no local access, no malware, no unnatural steps are required. The prompt appears as an ordinary part of Desktop's authentication UX, so a user has no strong reason for suspicion when accepting the "sign in" request.

### Recommendation
Do not classify a host as GitHub/enterprise based solely on the `WWW-Authenticate` realm string returned by that same untrusted host. At minimum:
- Require the `wwwauth[]`-based classification to be corroborated by an actual API probe (`isGitHubHost`) rather than trusting the realm string alone, or drop this heuristic entirely.
- Before launching `promptForGitHubSignIn`/`beginEnterpriseSignIn`, surface the literal endpoint origin prominently in the dialog and require explicit user confirmation that this is an expected Enterprise server, rather than silently pre-filling and advancing past the `EndpointEntry` step.
- Consider gating this auto-launch behind an explicit allow-list or requiring the user to have manually added the enterprise account beforehand.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a malicious proxy/MITM-able mirror) at `https://evil.example.com/repo.git`.
2. Server is configured so that on any unauthenticated Git-over-HTTP request it returns `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim adds this URL as a remote in GitHub Desktop (e.g., pasted from an issue, README, or a crafted "Open in Desktop" link) and performs a `fetch`/`push`.
4. Git invokes Desktop's credential helper trampoline; `getCredential()` → `getEndpointKind()` sees the `wwwauth[]` entry containing `realm="GitHub"` and returns `'enterprise'` [3](#0-2) .
5. Since no existing account matches `apiEndpoint` for `evil.example.com`, `ui.promptForGitHubSignIn('https://evil.example.com')` is called [4](#0-3) .
6. This calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint('https://evil.example.com')` [5](#0-4) , which transitions straight to the `Authentication` step for that origin [8](#0-7) .
7. Desktop shows its standard "Sign in to your GitHub Enterprise" dialog. If the victim completes it (basic auth or browser OAuth), their credentials/OAuth code are sent to `evil.example.com`.

    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }

  public async setEndpoint(url: string): Promise<void> {
    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.EndpointEntry &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with endpoint entry`
      )
    }

    /**
     * If the user enters a github.com url in the GitHub Enterprise sign-in
     * flow we'll redirect them to the GitHub.com sign-in flow.
     */
    if (/^(?:https:\/\/)?(?:api\.)?github\.com($|\/)/.test(url)) {
      this.beginDotComSignIn(currentState.resultCallback)
      return
    }

    this.setState({ ...currentState, loading: true })

    let validUrl: string
    try {
      validUrl = validateURL(url)
    } catch (e) {
      let error = e
      if (e.name === InvalidURLErrorName) {
        error = new Error(
          `The GitHub Enterprise instance address doesn't appear to be a valid URL. We're expecting something like https://example.ghe.com.`
        )
      } else if (e.name === InvalidProtocolErrorName) {
        error = new Error(
          'Unsupported protocol. Only https is supported when authenticating with GitHub Enterprise instances.'
        )
      }

      this.setState({ ...currentState, loading: false, error })
      return
    }

    const endpoint = getEnterpriseAPIURL(validUrl)

    const existingAccount = this.accounts.find(x => x.endpoint === endpoint)

    if (existingAccount) {
      this.setState({
        kind: SignInStep.ExistingAccountWarning,
        endpoint,
        existingAccount,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    } else {
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    }
