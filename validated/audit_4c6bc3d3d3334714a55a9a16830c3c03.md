I found a strong analog to the LUP-ordering bug: `_applyCopilotConflictResolutions` in `app-store.ts` explicitly guards against exactly this class of bug for files the *user* edits externally, but the equivalent staleness check is missing for the reassembly step itself, which is keyed on `resolution.path` matching an earlier-fetched `rawContent` snapshot rather than the file's current on-disk content at write time.

### Title
Copilot conflict resolution reassembles and writes resolved files against a stale `rawContent` snapshot instead of the file's current on-disk state - ([File: app/src/lib/stores/app-store.ts])

### Summary
The Copilot-assisted conflict resolution flow snapshots each conflicted file's content (`rawContent`) once, when building the conflict context sent to the model (`app/src/lib/copilot-conflict-context.ts`). The model's per-hunk resolutions are later spliced back into that *original snapshot*, not into the file's content at the time the user clicks "Continue Merge" (`app/src/lib/copilot-conflict-resolution.ts:609-642`, `reassembleResolvedFile`). `_applyCopilotConflictResolutions` in `app/src/lib/stores/app-store.ts:7169-7269` only checks whether a file has *no remaining conflict markers* (i.e., was fully resolved externally) before skipping the overwrite; it does not detect the case where the file was *partially* edited (e.g., the user tweaked one hunk, added an unrelated line, or a background process/hook touched the file) while still containing conflict markers. In that case the write path still calls `reassembleResolvedFile(ctx.rawContent, ...)` using the stale snapshot and overwrites the current file, silently discarding the user's in-between edits. ### Finding Description
This mirrors the Ajna bug's structure precisely: an operation captures an intermediate state (`rawContent` at context-build time, analogous to the LUP computed after removal but before addition), and a later step treats that intermediate snapshot as if it were the final/current state when committing an update (`reassembleResolvedFile` splicing into `ctx.rawContent`, analogous to `_updateInterestState(poolState, newLup)` using the stale `newLup`). The only staleness guard present, in `_applyCopilotConflictResolutions`:

```
const onDiskFile = state.changesState.workingDirectory.files.find(...)
if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
  continue
}
``` [4](#0-3) 

only fires when conflict markers are fully gone. It provides no protection when the file still nominally "has conflict markers" (so the guard doesn't skip it) but its content has diverged from the `rawContent` that was captured minutes earlier while the model was processing (the model call is asynchronous and can run for a while, per the `abortController`/`progress` plumbing in `app-store.ts:6967-7086`). Any concurrent modification of the working tree during that window — from an editor autosave, a build tool, a git hook, or content pulled in via a stash/second fetch — is invisible to the write path, which unconditionally reassembles from the old snapshot and calls `writeFile`, then `git add`. [5](#0-4) 

### Impact Explanation
This results in silent corruption of what the user ultimately commits: a write that discards the user's most recent, unsaved-to-Desktop-state changes to a conflicted file without any warning, error, or diff review — the exact "silent corruption of what the user commits or pushes" impact class. Because the file still shows as conflicted at the time of the check, the app proceeds to overwrite and stage it, and the corrupted content becomes part of the merge/rebase/cherry-pick commit that gets created and potentially pushed.

### Likelihood Explanation
The window is realistic: model resolution runs asynchronously over potentially many files/hunks (batched, `SinglePromptFileLimit`/`MaxConcurrentChunks`), during which the result dialog is shown and the user can freely edit files with markers still present in an external editor before clicking "Continue Merge". No re-read of the file or diff against the snapshot occurs before the overwrite — only the marker-count-zero fast path is checked.

### Recommendation
Before writing each resolution, re-read the file's current on-disk content and compare it against `ctx.rawContent` (or otherwise detect that the file was modified since the snapshot was taken, e.g. via mtime/hash). If it differs, skip the overwrite (or re-run reassembly against the fresh content) the same way the existing "resolved externally" check does, instead of only checking for zero remaining conflict markers.

### Proof of Concept
1. Start a merge/rebase with multiple conflicted files and trigger "Resolve with Copilot".
2. While the model is processing (loading dialog visible), open one of the still-conflicted files in an external editor and manually resolve just one of its several conflict hunks, leaving other `<<<<<<<`/`>>>>>>>` markers in place, then save.
3. Wait for the Copilot result dialog and click "Continue Merge".
4. Observe that `_applyCopilotConflictResolutions` still finds the file `isConflictedFileStatus` with `hasUnresolvedConflicts` true, so it does not skip it; it writes `reassembleResolvedFile(ctx.rawContent, ...)` — the pre-edit snapshot — overwriting the user's manual edit to that hunk without any prompt, and stages the result for commit.

/**
 * Combine raw per-hunk model resolutions with original file contexts to
 * produce the final {@link IFileResolution} array that the rest of the app
 * expects (each entry has the complete reassembled file content).
 *
 * This is the bridge between the model's lightweight per-hunk output and
 * the existing UI and write path which need full file content.
 */
export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
