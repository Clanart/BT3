### Title
Unauthenticated ReceivedOutput deserialization permits fabricated Bitcoin deposits - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts an offset, complete `TxOut`, and `OutPoint` from an unauthenticated byte stream without proving that the `OutPoint` exists or that its on-chain output matches the supplied `TxOut`. Downstream transaction construction trusts the claimed value and `SignableTransaction::multisig` authenticates only the claimed `script_pubkey`. An attacker who knows the wallet's public Taproot script can therefore submit serialized bytes for a nonexistent, unrelated, or inflated output that the library treats as spendable.

### Finding Description
`ReceivedOutput` is documented as “a spendable output,” but `ReceivedOutput::read` reconstructs all three spendability fields directly from attacker-controlled bytes: the scalar offset, the claimed output, and the claimed UTXO reference. No transaction lookup, Merkle proof, confirmed block check, output-index validation, or equivalence check between `outpoint` and `output` is performed.

The issue is reachable when untrusted bytes are passed to `ReceivedOutput::read` directly or through `processor/src/networks/bitcoin.rs`’s `Output::read`, which deserializes `output` using `ReceivedOutput::read`.

The strongest practical case uses:

- `offset = Scalar::ZERO`
- `output.script_pubkey = p2tr_script_buf(victim_group_key)`
- `output.value = attacker-chosen amount`
- `outpoint = nonexistent UTXO`, an unrelated UTXO, or a real wallet UTXO with a forged value

`SignableTransaction::new` then trusts `output.value` in `input_sat` and stores the forged `TxOut` in `prevouts`. `SignableTransaction::multisig` checks only that `p2tr_script_buf(keys.offset(offset).group_key())` equals the claimed `script_pubkey`; it does not validate the `OutPoint` or its actual on-chain `TxOut`.

During signing, `TransactionSignMachine::sign` commits to `Prevouts::All(&self.tx.prevouts)`. If the `OutPoint` is real but the claimed amount or script differs from the chain UTXO, the generated Taproot signature is invalid because the sighash commits to the forged prevout data. If the `OutPoint` does not exist or is not spendable by the wallet, the transaction cannot spend it at all.

### Impact Explanation
An unprivileged party can cause Serai-derived software to report and account for funds that are not spendable. The fabricated `ReceivedOutput` exposes the forged amount through `value()`, is serialized/deserialized as a normal spendable output, and can be selected as an input by `SignableTransaction::new`.

If callers persist or exchange `ReceivedOutput`/`Output` values across an untrusted boundary, this bypasses the chain-provenance check that `Scanner::scan_transaction` normally provides. Consequences include inflated balances, allocation of nonexistent inputs, transactions rejected by Bitcoin consensus or Taproot signature verification, and incorrect accounting before broadcast.

This is a Medium-severity integrity issue: it does not give the attacker a valid signature for a different spendable output, but it does cause funds to be reported as received and spendable when they are not.

### Likelihood Explanation
The attacker needs only public knowledge of the victim’s Taproot script or group key and a path that feeds attacker-controlled serialized data to `ReceivedOutput::read` or `Output::read`. The prompt’s reachable-input model explicitly includes untrusted bytes supplied to `ReceivedOutput::read`.

The forged object survives the later ownership check because a zero offset and the wallet’s known P2TR script satisfy `SignableTransaction::multisig`’s sole script comparison. The attack fails only if the surrounding application independently authenticates the output against the blockchain or never deserializes wallet outputs from untrusted input; neither check exists in the affected API itself.

### Recommendation
Do not expose `ReceivedOutput::read` as a way to establish a spendable output. Keep deserialization limited to a trusted internal record format, or make the type explicitly unverified until authenticated.

Prefer a verification step before accounting or spending that:

1. Fetches the transaction identified by `outpoint.txid` from a trusted Bitcoin RPC.
2. Confirms `outpoint.vout` is in range.
3. Compares the complete on-chain `TxOut` to the deserialized `output`.
4. Confirms the transaction is confirmed and the output remains unspent.
5. Rechecks `p2tr_script_buf(derived_key(offset)) == output.script_pubkey`.

Alternatively, store only the `OutPoint` and offset in the serialized object and load the authoritative `TxOut` from the chain during verification. For untrusted wire data, require a proof/authenticated source rather than accepting the claimed `TxOut` and `OutPoint` pairing.

### Proof of Concept
Conceptual Rust reproducer for the in-scope API:

```rust
use bitcoin::{
  Amount, OutPoint, ScriptBuf, TxOut, Txid, hashes::Hash,
};
use k256::Scalar;
use bitcoin_serai::wallet::{
  p2tr_script_buf, ReceivedOutput, SignableTransaction,
};

let group_key = victim_threshold_keys.group_key();
let script: ScriptBuf = p2tr_script_buf(group_key).unwrap();

let mut bytes = Vec::new();

// Use offset zero so SignableTransaction::multisig accepts the claimed script.
bytes.extend(Scalar::ZERO.to_bytes());

// Claim a large amount payable to the victim's known Taproot script.
bitcoin::consensus::Encodable::consensus_encode(
  &TxOut {
    value: Amount::from_sat(1_000_000_000),
    script_pubkey: script,
  },
  &mut bytes,
)
.unwrap();

// Reference a nonexistent or unrelated UTXO.
bitcoin::consensus::Encodable::consensus_encode(
  &OutPoint {
    txid: Txid::from_raw_hash(
      bitcoin::hashes::sha256d::Hash::from_byte_array([0x42; 32]).into()
    ),
    vout: 0,
  },
  &mut bytes,
)
.unwrap();

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// The forged value is now reported as spendable.
assert_eq!(forged.value(), 1_000_000_000);

// Transaction construction trusts the fabricated output.
let signable = SignableTransaction::new(
  vec![forged],
  &[(payment_script, 10_000)],
  None,
  None,
  20,
)
.unwrap();

// This passes because only the script is compared to keys.offset(0).
let machine = signable.multisig(&victim_threshold_keys).unwrap();
```

The resulting machine either references a nonexistent/unspendable UTXO or, if the `OutPoint` names a real wallet UTXO while `TxOut.value` was altered, produces signatures over forged `Prevouts::All` data that fail Bitcoin Taproot verification.
