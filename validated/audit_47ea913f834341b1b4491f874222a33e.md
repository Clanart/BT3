### Title
Fee-on-transfer / deflationary ERC-20 inputs break escrow accounting in the Tron `IntentGatewayV2.placeOrder` (unlike the audited EVM version) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core invariant is: *when a token charges a transfer fee, the amount actually received by a contract can be less than the nominal amount specified in a transfer call; any downstream accounting/repayment logic that assumes "received == requested" will desync and later revert or misallocate funds.* The main EVM `IntentGatewayV2` at `evm/src/apps/IntentGatewayV2.sol` already defends against exactly this class of bug by measuring `balanceOf` before/after every `safeTransferFrom` and mutating `order.inputs[i].amount` to the *actually received* value before computing the commitment/escrow [1](#0-0) . The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not carry this fix.

### Finding Description
In `IntentGatewayV2.placeOrder` (Tron), the commitment and the `reducedInputs` (escrow bookkeeping amounts) are computed from the *nominal* `order.inputs[i].amount` supplied by the caller, before any token transfer occurs: [2](#0-1) 

The subsequent token-transfer loop then does a plain `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and unconditionally credits the escrow map with the pre-computed `reducedInputs[i].amount`, with no balance-before/after check to detect fee-on-transfer shortfall: [3](#0-2) 

The predispatch path has the same defect — it forwards the nominal `amount` to the dispatcher and then unconditionally adds `reducedInputs[i].amount` to `_orders[commitment][token]`, only emitting `DustCollected` for the difference between the dispatcher's *pre-required* balance and the required amount, not for a token that also charges a fee on the second (dispatcher→gateway) leg: [4](#0-3) 

Compare this to the corrected EVM version, which records `balancesBefore[i]`, sweeps, and computes `received = balanceOf(after) - balancesBefore[i]`, only then writing `order.inputs[i].amount = received` before the commitment/fee math runs — the Tron contract skips this entirely: [5](#0-4) 

Later, `withdraw()` pays out `body.tokens[i].amount` (which for a filled order traces back to the nominal/reduced amount recorded in `_orders[commitment][token]`, not the gateway's real balance) via a raw `token.call(transfer, beneficiary, amount)`: [6](#0-5) 

For a deflationary/fee-on-transfer ERC-20 (the same token class as USDT-style fees named in the report), the gateway's actual token balance after `placeOrder` is strictly less than the sum recorded in `_orders[...][token]` for that token across all outstanding orders. `_orders` becomes an IOU ledger that is no longer backed 1:1 by the contract's real balance.

### Impact Explanation
Because multiple unrelated orders share the same token balance in the same gateway contract, this is not merely a self-inflicted loss to the order placer — it is a shared-pool insolvency bug:
- Solvers/beneficiaries who withdraw first can drain the gateway's real balance using escrow entries that were inflated relative to what was actually deposited, leaving later, legitimately-filled orders under-collateralized.
- `withdraw()`'s raw `token.call` swallows failures silently in some paths only via explicit `TransferFailed()` revert, but by the time a later beneficiary tries to redeem, the token transfer will simply fail/revert because the contract lacks the real balance — funds get locked, and/or earlier claimants effectively receive more than their fair share of the shared token float, meeting the bounty's "stealing or loss of funds" and "logic attack" criteria without requiring any privileged, colluding, or malicious relayer/solver — an ordinary user placing an order with a standard fee-on-transfer token triggers the desync.

### Likelihood Explanation
This is reachable by any unprivileged user calling the public `placeOrder` entrypoint with a deflationary ERC-20 as an input asset — no admin, relayer, or prover involvement is needed, matching the "public-entrypoint, unprivileged attacker" requirement. The only precondition is that the deployment accepts a fee-on-transfer token as an input asset, which the existing EVM-side test suite explicitly anticipates and defends against (`FeeOnTransferToken` test contract and `testPlaceOrder_FeeOnTransferToken_*` tests exist for the main EVM contract but there is no equivalent hardening or test coverage for the Tron contract) [7](#0-6) .

### Recommendation
Port the balance-diff pattern from `evm/src/apps/IntentGatewayV2.sol` (`balancesBefore`/`received` measurement before mutating `order.inputs[i].amount`, and before computing `reducedInputs`/commitment) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, for both the direct-transfer and predispatch code paths, so that escrow bookkeeping in `_orders[commitment][token]` always reflects the amount actually held by the contract, never the nominal caller-specified amount.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a deflationary ERC-20 (1% fee on transfer, fee burned) as a supported input token.
2. User calls `placeOrder` with `order.inputs[0].amount = 1000e18` of the fee-on-transfer token, having approved the gateway for `1000e18`.
3. `placeOrder` computes `reducedInputs[0].amount` from the nominal `1000e18` (minus protocol fee if any) and derives `commitment` from that value, then calls `safeTransferFrom(msg.sender, address(this), 1000e18)` — the gateway actually receives only `990e18` due to the 1% transfer fee.
4. `_orders[commitment][token]` is credited with the reduced amount computed from `1000e18` (e.g. `1000e18` if no protocol fee), while `IERC20(token).balanceOf(gateway) == 990e18`.
5. When the order is filled/withdrawn, `withdraw()` attempts `token.call(transfer, beneficiary, 1000e18)` — this either reverts (locking the order) once the gateway has no other same-token orders to cover the shortfall, or succeeds by consuming balance escrowed for other unrelated orders in the same token, causing those other orders' withdrawals to subsequently fail/underpay — reproducing the exact "amount minus fee causes accounting to break and the transaction to be reverted / funds to be misallocated" pattern described in the external report.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
