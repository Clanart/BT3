## Title
`applyPatchToIndex()` re-fetches a fresh diff but applies a line-selection bitmap computed against a stale diff, silently corrupting partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
The Yieldoor report describes a stale-state bug: `_updateIndexes()` mixes a previously-cached rate with newly changed inputs and computes an incorrect result because the two values no longer correspond to the same point in time. The same *class* of bug (combining a stale snapshot with fresh state that has since diverged, with no revalidation) exists in GitHub Desktop's partial-commit ("stage selected lines") pipeline.

### Finding Description
When a user selects individual lines of a file to commit, the UI builds a `DiffSelection` bitmap keyed by absolute line indices computed from the diff that was rendered at selection time (`file.selection`, populated via `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts`). That selection object is stored on the `WorkingDirectoryFileChange` and carried forward, unrevalidated, to the commit path.

At commit time, `stageFiles()` (`app/src/lib/git/update-index.ts:109-168`) calls `applyPatchToIndex()` for every file with a partial selection. Crucially, `applyPatchToIndex()` does **not** reuse the diff that produced the selection indices — it fetches a brand-new diff right before applying: [1](#0-0) 

```
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })
```

`formatPatch()` then maps the *old* selection bitmap onto the *newly fetched* hunks purely by absolute index arithmetic: [2](#0-1) 

```

  const absoluteIndex = hunk.unifiedDiffStart + lineIndex
  ...
  } else if (file.selection.isSelected(absoluteIndex)) {
```

`hunk.unifiedDiffStart` and the line ordering come from whatever diff `getWorkingDirectoryDiff` happens to return at apply time (`app/src/lib/diff-parser.ts:292-390` computes these offsets fresh on every parse). If the working-tree content of the file changed between the moment the user made their line selection (diff A) and the moment `applyPatchToIndex` re-diffs the file (diff B) — e.g. hunks shifted, merged, or split due to intervening writes — `file.selection.isSelected(absoluteIndex)` is evaluated against index positions that no longer correspond to the same lines the user actually looked at and checked/unchecked. There is no check anywhere in `applyPatchToIndex`, `stageFiles`, or `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3680-3760`) that the diff used to build the selection is still the diff being staged.

This mirrors the audited bug precisely: `_updateIndexes()` combines `reserve.currentBorrowingRate` (computed against an old utilization snapshot) with `reserve.totalBorrows` that has since changed, producing an inconsistent result because the two values aren't from the same point-in-time state. Here, a line-selection bitmap computed against diff-snapshot A is combined with hunk offsets from diff-snapshot B, with the code implicitly (and incorrectly) assuming the two are still aligned.

### Impact Explanation
If exploited (e.g. by a repository whose build/clean-filter/editor tooling rewrites tracked files asynchronously, or simply an external process/tool that touches a file while the user is reviewing/selecting diff lines in Desktop), the resulting patch built by `formatPatch` can include lines the user explicitly deselected, or omit lines the user selected, without any error or warning. This is a silent corruption of what the user commits — content the user believed was excluded from the commit is committed anyway (or vice versa), which is exactly the class of impact called out as valid ("silent corruption of what the user commits or pushes").

### Likelihood Explanation
Likelihood is constrained: it requires the working-tree file to be mutated between the diff render used for line selection and the moment `applyPatchToIndex` re-fetches the diff for staging (a window that exists for every partial commit, since Desktop always re-diffs rather than reusing the exact diff object tied to the selection). This is analogous to the "usually measured daily" caveat in the original report — the window is normally short, but any external tool, format-on-save, git filter, or slow user review increases exposure. I could not find any guard (hash/oid comparison, diff generation revalidation, or hunk count/id check) in `apply.ts`, `update-index.ts`, or `patch-formatter.ts` that detects the mismatch, so nothing currently prevents a corrupted patch from being silently applied.

### Recommendation
Before calling `formatPatch`/`git apply` in `applyPatchToIndex`, revalidate that the diff used to build `file.selection` is still representative of the on-disk file — e.g. compare the diff/blob signature captured when the selection was made against a freshly computed one, and if they differ, abort staging that file and force the UI to refresh the diff/selection rather than silently applying a patch built from mismatched offsets.

### Proof of Concept
Conceptual reproduction (not executed, since this analysis is derived from static code review only):
1. Open a modified file in Desktop's Changes view; the diff is rendered and the user selects a subset of lines (line-selection bitmap built against diff-snapshot A's hunk offsets).
2. Before clicking "Commit", an external process (editor autosave, formatter, git clean filter, build step) rewrites the file, shifting or restructuring the hunks (diff-snapshot B).
3. User clicks "Commit". `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-fetches diff B via `getWorkingDirectoryDiff`, then calls `formatPatch(file, diffB)`, which evaluates `file.selection.isSelected(absoluteIndex)` against diff B's (shifted) hunk offsets.
4. The generated patch stages a different set of lines than what the user visually selected against diff A, and `git commit` records it — with no warning shown to the user.

Note: I was not able to execute a live reproduction or confirm exact trigger timing/window in this environment; this is a static-analysis-based finding based on the absence of any diff/selection-consistency check in the cited code paths.
