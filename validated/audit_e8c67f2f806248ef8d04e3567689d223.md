### Title
`open-external` IPC handler checks the URL scheme but never enforces it before calling `shell.openExternal` - (File: `app/src/main-process/main.ts`)

### Summary
The main-process IPC handler for `open-external` inspects the target string to see if it looks like an `http(s)://` URL, but that check is only used to decide whether to write a log line — the result is never used to reject or sanitize the value before it is handed to Electron's `shell.openExternal`. This mirrors the report's core defect pattern: a spec-relevant validation exists in the code but is not actually used to gate the sensitive operation.

### Finding Description
`ipcMain.handle('open-external', ...)` computes `pathLowerCase` and checks `startsWith('http://')`/`startsWith('https://')` purely to log `opening in browser: ${path}`. Regardless of the outcome of that check, the handler unconditionally calls `shell.openExternal(path)`: [1](#0-0) 

The renderer-facing wrapper (`openExternal` in `app/src/ui/main-process-proxy.ts`, used by `app-shell.ts`) forwards whatever string it is given straight to this IPC channel: [2](#0-1) 

`LinkButton`, a generic UI component reused across the renderer (including notification/PR-related surfaces such as `pull-request-comment.tsx`, `pull-request-review.tsx`, `pull-request-comment-like.tsx`), calls `shell.openExternal(uri)` directly on click with no protocol allow-list of its own: [3](#0-2) 

This is structurally the same bug shape as `RCNftHubL2.safeTransferFrom`: a spec-required validation (checking the receiver / checking the scheme) is computed but its result is discarded instead of being used to block the unsafe path forward. By contrast, the markdown link interceptor used for rendering GitHub-sourced PR/comment bodies *does* correctly gate on the check result (`if (/^https?:/.test(a.protocol)) { onMarkdownLinkClicked }`), showing the project is aware such gating is needed elsewhere: [4](#0-3) 

### Impact Explanation
`shell.openExternal` on Windows/macOS invokes whatever handler is registered for the URL's scheme (browser, mail client, custom protocol handlers registered by other installed applications). Passing a non-`http(s)` scheme (e.g. `file:`, a custom app protocol, or an OS-specific handler URL) through unchecked can lead to unexpected local application invocation, and historically this class of "unchecked `shell.openExternal`" issue in Electron apps has been used for local code execution via crafted URIs and command-injection-style argument smuggling into vulnerable third-party protocol handlers.

### Likelihood Explanation
The scheme check exists in `main.ts`, so a reviewer could reasonably (incorrectly) assume it also gates the call — the same false sense of safety noted in the original ERC721 report ("it just drops the argument"). I was not able to fully confirm, within the available tool budget, that a fully unprivileged attacker (e.g. a malicious PR/comment author or a malicious remote/proxy) can supply an arbitrary, non-`http(s)` `uri` value into a `LinkButton` that a user would click, since most `LinkButton` call sites I inspected use static/hardcoded URIs (about, terms, preferences); the notification components (`pull-request-comment.tsx`, `pull-request-review.tsx`) reference GitHub API PR/comment data but I could not verify their exact `uri` construction before the tool budget ran out. This uncertainty should be resolved before treating this as a confirmed remotely-triggerable issue.

### Recommendation
In `app/src/main-process/main.ts`'s `open-external` handler, use the computed `pathLowerCase` scheme check to actually reject (return `false`/throw) any URL that isn't `http:`/`https:` (and any other explicitly allow-listed schemes, e.g. `mailto:`), instead of only using it for logging. Apply the same allow-list check inside `LinkButton.onClick` before calling `shell.openExternal`, consistent with the existing gating already implemented in `sandboxed-markdown.tsx`'s link interceptor.

### Proof of Concept
Not independently verified end-to-end due to the caveat above. The reachable code path, if a caller can be found to pass a non-`http(s)` string as `uri`, is:
1. Renderer calls `shell.openExternal(uri)` (`app/src/ui/lib/link-button.tsx:85`) or another `app-shell.ts` consumer with `uri = "customscheme://..."`.
2. This is proxied to the main process via `openExternal` in `app/src/ui/main-process-proxy.ts`.
3. `ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts:581-597` sees the scheme isn't `http(s)`, skips only the `log.info` call, and still executes `await shell.openExternal(path)`, invoking whatever OS handler is registered for that scheme.

Given the unresolved question of concrete attacker control over the `uri` reaching `LinkButton`/`app-shell.openExternal`, this should be treated as a **pattern match with partial verification** rather than a fully confirmed end-to-end exploit — I recommend a follow-up session with fuller repo access to trace all `LinkButton uri=` call sites back to their data sources to confirm reachability from PR/comment/remote-controlled content.

```typescript
  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
```
