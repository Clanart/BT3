### Title
Unchecked u64 additions in `SignableTransaction::new` allow overflow past the funds and fee checks, producing a signed transaction that is invalid and unbroadcastable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

The LibFixedMath bug class is "arithmetic code that validates most cases but misses a specific overflow boundary, silently returning a wrong value instead of reverting." `SignableTransaction::new` performs bounds validation on caller-supplied payment amounts using plain `u64` addition and multiplication (`payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, `payment_sat + fee_with_change`). In a release build, these wrap on overflow rather than panic, so the `NotEnoughFunds` / `TooLowFee` checks can be bypassed and a `TxOut` carrying an invalid (wrapped) value is appended to the transaction that the FROST threshold group then signs.

### Finding Description

`payment_sat` is the unbounded sum of attacker-influenceable `u64` payment amounts:

`networks/bitcoin/src/wallet/send.rs` line 187: `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();`

Three unchecked arithmetic sites then gate correctness:

- Line 206: `let mut needed_fee = fee_per_vbyte * vbytes;` — wrap produces a near-zero fee, bypassing the `TooLowFee` check on line 211.
- Line 215: `if input_sat < (payment_sat + needed_fee)` — if `payment_sat + needed_fee` wraps below `input_sat`, the `NotEnoughFunds` check passes even though the declared outputs far exceed the inputs.
- Line 228: `input_sat.checked_sub(payment_sat + fee_with_change)` — the inner `payment_sat + fee_with_change` add is itself unchecked; if it wraps to a small value, `checked_sub` returns `Some(huge_value)`, and since `huge_value >= DUST`, a change `TxOut` with `Amount::from_sat(huge_value)` is pushed (line 230).

The result is a `SignableTransaction` whose outputs sum to more than its inputs. `TransactionSignMachine::sign` (lines 373–397) then computes the Taproot sighash over this malformed transaction and produces FROST signature shares for it; `complete` (lines 413–428) assembles the fully signed invalid transaction. Additionally, `fee()` (lines 138–141) computes `sum(inputs) - sum(outputs)` with an unchecked subtraction, which panics in debug builds and wraps to a nonsensical `u64` in release.

### Impact Explanation

An unprivileged party who can cause a payment (e.g., a withdrawal/burn instruction carrying a large declared amount, reflected into `payments`) can get the threshold signer group to produce a validly-FROST-signed Bitcoin transaction that consensus rejects outright (`bad-txns-out-*` / value-in < value-out). Consequences:

- A completed signing ceremony produces a transaction that cannot be broadcast; the referenced UTXOs must be re-scheduled and re-signed (a wasted signing round and, depending on session bookkeeping, potential nonce-scheduling disruption).
- `fee()` underflow wrap/panic corrupts fee accounting for any caller that computes the effective fee of such a transaction.
- If downstream code trusts `needed_fee` or the constructed outputs for accounting (e.g., crediting a withdrawal as sent), a wrapped `payment_sat` could make accounting inconsistent with what was actually signable/spendable — the "funds handled inconsistently" analog of the report's silently-wrong arithmetic result.

### Likelihood Explanation

Reaching this requires `payments` entries whose amounts sum past `u64::MAX` (or `fee_per_vbyte * vbytes` overflowing), i.e., the caller must supply payment amounts that are individually ≥ `DUST` but collectively wrap, or an extreme `fee_per_vbyte`. Where the payment list is derived from user-submitted withdrawal requests, an attacker who can register multiple large outputs controls `payment_sat`. The bug requires a release (wrapping) build to bypass the checks silently; in debug builds it is a panic (DoS). Severity is Medium: the forged-looking output set is signed but is rejected by consensus, so no funds are stolen; the impact is signing-oracle/DoS and accounting inconsistency rather than theft.

### Recommendation

Use checked arithmetic consistently, mirroring the audited fix (explicit boundary checks instead of relying on the common case):

- Compute `payment_sat` with `checked_add`/`try_fold` and return `NotEnoughFunds`/`Overflow` on failure.
- Compute `needed_fee` and `fee_with_change` with `fee_per_vbyte.checked_mul(vbytes)`.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`, treating overflow as `NotEnoughFunds` (inputs can never cover a wrapped total).
- Compute `fee()` with `checked_sub` and return `Option<u64>`/`Result`, since a malformed transaction should error rather than panic or wrap.
