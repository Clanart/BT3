## Finding

### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is silently captured by the host instead of refunded to the caller — (File: `evm/src/core/EvmHost.sol`)

### Summary
The `EvmHost` contract exposes three payable entry points — `dispatch(DispatchPost memory post)`, `dispatch(DispatchGet memory get)`, and `fundRequest(bytes32 commitment, uint256 amount)` — that accept native ETH and swap it through the local Uniswap V2-style router for an *exact* amount of fee token. All three call `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` and none of them forward any unspent native ETH back to `_msgSender()` afterward, unlike the sibling application logic in `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents`, which explicitly tracks and refunds leftover `msgValue`.

### Finding Description
`dispatch(DispatchPost)` swaps the entire `msg.value`: [1](#0-0) 

`dispatch(DispatchGet)` does the same: [2](#0-1) 

`fundRequest` also does the same: [3](#0-2) 

In each case, `swapETHForExactTokens` is called with `recipient = address(this)` (the EvmHost) and `msg.sender` (from the wrapper's perspective) is EvmHost itself, not the original dispatch caller. The wrapper implementations refund any unspent input strictly to their own `msg.sender`: [4](#0-3) 

That refund therefore lands back in `EvmHost`'s own balance — none of the three EvmHost functions read a returned `amounts[0]`/leftover value or forward it to `_msgSender()` after the swap call, unlike the analogous fee-swap logic in `IntentGatewayV2`, which explicitly computes and refunds the delta: [5](#0-4) 

and in `ExtrinsicIntents`: [6](#0-5) 

So any caller who sends more native ETH than the swap consumes (e.g. because the fee-token/ETH price moved between the estimate and mining, or slippage is smaller than assumed) permanently loses the difference: it becomes part of `EvmHost`'s own ETH balance and is only recoverable by the privileged `hostManager` via cross-chain governance's `withdraw()`: [7](#0-6) 

The unprivileged caller has no path to reclaim their own overpaid ETH — it is unilaterally converted into host/protocol revenue.

### Impact Explanation
This is a direct, unprivileged loss-of-funds bug: any ordinary user calling `dispatch()`/`fundRequest()` with `msg.value` slightly above the exact swap requirement (a very common and expected occurrence, since callers cannot know the router's exact required input at call time) has the surplus swept into host custody with no self-service refund path — only `hostManager`-gated governance can move it out, and it is not automatically attributed back to the depositor. This matches the report's "excess/locked balance never returned to rightful party" theme, but here the loss falls on an ordinary end user rather than being merely inert protocol yield.

### Likelihood Explanation
High likelihood: any caller invoking `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native ETH and even a small overestimate of the required fee amount will trigger this path — no attacker collusion, malicious relayer, or special conditions are required. It happens under completely normal usage whenever the ETH amount sent exceeds the AMM's exact-output requirement.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents`: capture the `amounts` array returned by `swapETHForExactTokens`, compute `refund = msg.value - amounts[0]`, and forward it back to `_msgSender()` (reverting on failed transfer) in all three EvmHost functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`).

### Proof of Concept
1. Caller estimates the required ETH for a fee of `X` fee-tokens and calls `EvmHost.dispatch{value: Y}(post)` where `Y > actual amount consumed by swapETHForExactTokens` (e.g. due to price movement between quote and execution, or simply over-padding for safety).
2. Inside `dispatch`, `swapETHForExactTokens{value: Y}(post.fee, path, address(this), block.timestamp)` executes; the wrapper spends only `amountIn < Y` and refunds `Y - amountIn` to its caller, which is `EvmHost` (`address(this)`), not the original transaction sender.
3. `dispatch` returns without forwarding this leftover ETH anywhere; it now permanently sits in `EvmHost`'s balance.
4. The original caller has irrecoverably lost `Y - amountIn` ETH; only `hostManager`-authorized cross-chain governance can later extract it via `withdraw()`, and there is no accounting that ties it back to the original depositor for reimbursement.

     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
