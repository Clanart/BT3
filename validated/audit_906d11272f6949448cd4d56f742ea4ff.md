### Title
Re-associating an EVM address permanently blocks the pre-existing direct-cast Sei address from receiving further funds, mirroring the "delisted collateral" freeze pattern - (File: `x/evm/keeper/address.go`)

### Summary
The JOJO finding is about an admin/permission-state change (delisting collateral) retroactively making a user's already-held asset unmovable, because a receivability/valuation check that was meant to gate *new* actions ends up blocking access to *existing* funds. Sei-chain has a structurally identical primitive: `CanAddressReceive` in `x/evm/keeper/address.go` (and its `giga/deps/xevm` duplicate), which permanently flips a direct-cast Sei address from "receivable" to "not receivable" the moment its underlying EVM address becomes associated with a different, pubkey-derived Sei address.

### Finding Description
`CanAddressReceive` implements the rule: a direct-cast address (an `sdk.AccAddress` obtained by truncating/casting an EVM address) may not receive bank funds once the corresponding EVM address has been associated (via `SetAddressMapping`) with a *different* true Sei address. [1](#0-0) 

This check is consulted from the distribution module's `AfterValidatorRemoved` hook and other bank flows via `RegisterRecipientChecker`/`CanSendTo`, and is enforced by `BaseSendKeeper.CanSendTo` at send time. [2](#0-1) 

Analogous to the JOJO bug — where `reserve.isBorrowAllowed = false` zeroes out the *value* of an asset a user already deposited, without providing a path to withdraw it — this mechanism zeroes out the *receivability* of an address after the fact. Any bank-coin balance sitting in the direct-cast address before the re-association becomes unrecoverable through the normal `SendCoinsFromModuleToAccount` / `CanSendTo`-gated paths, because the address permanently fails the receivability check going forward. The tests around `AfterValidatorRemoved`/`canReceiveWithdrawAddr` explicitly document that once `CanSendTo` returns false for such an address, the affected module (distribution) reroutes commission to the community pool rather than lose it — but this is a module-specific mitigation, not a general fix, and it exists precisely because the underlying address can no longer be paid. [3](#0-2) 

The core parallel: a state transition intended to protect the protocol/route funds correctly for *future* transfers (re-association pointing an EVM identity to its real owner) silently and permanently disables receipt of coins for an address that may still be the destination of value already in flight or held by third parties expecting to pay it — exactly like delisting collateral silently zeroing a value that was previously counted as backing a position.

### Impact Explanation
Funds already sent to, or expected by, a direct-cast address before re-association become undeliverable/frozen for as long as that mapping exists — validators' commission is diverted to the community pool instead of the rightful (mis-associated) recipient, and any other module relying on `CanSendTo`/`BlockedAddr`-style checks for that address will likewise refuse to pay it. This is a fund-freezing condition reachable purely through the public `MsgAssociate`/EVM tx flow (any account can trigger `SetAddressMapping` for its own EVM key), matching the required "permanent freezing of funds" bar.

### Likelihood Explanation
Re-association is a normal, permissionless user action (associating an EVM key to its real Sei account), not a privileged operator action, so the precondition is trivially reachable by any user. The scenario requires a party (e.g., a validator, or anyone with a stake/reward due) to be using the pre-association direct-cast address as their receiving address at the time of re-association — a realistic and previously-hit scenario, as shown by the existing regression tests for `AfterValidatorRemoved`.

### Recommendation
Provide an explicit rescue/withdrawal path for balances stranded in a direct-cast address after re-association (e.g., allow the newly associated true Sei address, or a governance/admin-gated sweep, to claim residual balances left in the direct-cast address), rather than silently diverting funds to the community pool or leaving them stuck. At minimum, audit all `CanSendTo`/`BlockedAddr`/`CanAddressReceive` consumers to ensure none of them can strand pre-existing balances without a recovery mechanism.

### Proof of Concept
1. An EVM address `E` has not yet been associated; its direct-cast Sei address `castAddr = sdk.AccAddress(E)` can freely receive and hold `usei` (e.g., as a validator operator address or plain recipient). [4](#0-3) 
2. A third party (owner of the EVM private key for `E`) associates `E` with a different, pubkey-derived Sei address via `SetAddressMapping`. [5](#0-4) 
3. `CanAddressReceive(ctx, castAddr)` now returns `false` for `castAddr`, and `BankKeeper.CanSendTo`-gated payouts destined for `castAddr` (e.g., validator commission via `AfterValidatorRemoved`) can no longer be delivered to it. [6](#0-5) [7](#0-6) 
4. Any usei balance previously credited to `castAddr` (or owed to it) has no defined recovery path other than the ad hoc community-pool diversion implemented specifically for the distribution module's commission flow — other modules paying out to such an address have no equivalent safety net documented in the codebase context examined.

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

// TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator covers the
// case where the validator operator address itself cannot receive funds — its EVM
// address was re-associated (e.g. via associatePubKey) away from the direct-cast Sei
// address it was created under. The withdraw-address fallback in GetDelegatorWithdrawAddr
// resolves back to that same unreceivable operator address, so the commission
// force-withdraw fails. AfterValidatorRemoved runs during EndBlock, so it must not panic:
// the commission is routed to the community pool instead, which conserves value because
// the coins already back the distribution module account.
func TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	// The validator operator is the direct-cast Sei address of an EVM address.
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	castAddr := sdk.AccAddress(evmAddr[:])
	valAddr := sdk.ValAddress(castAddr)
	valAccAddr := sdk.AccAddress(valAddr) // == castAddr

	require.True(t, app.BankKeeper.CanSendTo(ctx, castAddr))

	// Re-associate the EVM address to a different true Sei address, mirroring
	// associatePubKey after a validator was created under the direct-cast address.
	associatedAddr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))[0]
	app.EvmKeeper.SetAddressMapping(ctx, associatedAddr, evmAddr)

	// The operator/delegator address can no longer receive funds, and the
	// withdraw-address fallback resolves back to that same unreceivable address.
	require.False(t, app.BankKeeper.CanSendTo(ctx, castAddr))
	require.Equal(t, valAccAddr.String(), app.DistrKeeper.GetDelegatorWithdrawAddr(ctx, valAccAddr).String())

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := k.GetKVStore(ctx)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}
