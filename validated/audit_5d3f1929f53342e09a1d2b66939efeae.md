### Title
Deterministic CachedPreprocess reuse across multiple `sign` invocations enables nonce reuse and private key share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates the identical FROST nonces from a single cached seed (`CachedPreprocesses`, keyed by `("DkgConfirmer", attempt)`) every time it is invoked. Both `DkgConfirmer::share` and `DkgConfirmer::complete` independently call `share_internal` → `preprocess_internal` → `AlgorithmSignMachine::sign`, so the same consumed preprocess — which per `crypto/frost/src/sign.rs` "MUST only be used once" — is used multiple times. If the set of peer preprocesses (attacker-influenced inputs) differs between any of these invocations, the victim signs with the same binomial nonces `(d, e)` under different binding factors/challenges. Three such shares yield three linear equations in three unknowns `(d, e, λ·x)`, recovering the victim's private key share. This is a use-after-free analog: a cryptographic object whose security depends on single-use lifetime is reused after being consumed.

### Finding Description
- `crypto/frost/src/sign.rs:83-92` documents that a `CachedPreprocess` must be used exactly once; reuse enables third-party recovery of the private key share. `from_cache` → `seeded_preprocess` at `crypto/frost/src/sign.rs:121-144` regenerates identical nonces deterministically via `ChaCha20Rng::from_seed`.
- `coordinator/src/tributary/signing_protocol.rs:123-145` stores the seed in the DB keyed by `context` and re-derives the identical sign machine on every call; the seed is never deleted, rotated, or marked consumed after `sign` runs.
- `DkgConfirmer::share` (`signing_protocol.rs:304-310`) and `DkgConfirmer::complete` (`signing_protocol.rs:312-327`) each call `share_internal`, each calling `preprocess_internal` again — `sign` is executed at least twice on the same nonces within the normal flow.
- The peer `preprocesses` map passed into `share`/`complete` originates from on-chain messages from other validators and is not checked against the set used previously (the file's own header comment at `signing_protocol.rs:50-54` lists this "on-chain-preprocess-matches-presumed-preprocess" check as an unimplemented TODO). Any variation — e.g., `complete` receiving a different/superset preprocess map than `share`, or a re-execution after reboot with a different finalized set — changes the `rho_transcript` at `crypto/frost/src/sign.rs:362-371`, producing distinct binding factors `ρ` and challenges `c` for the *same* nonces.
- The resulting share equation is `s = d + e·ρ_i + λ_i·x·c` (`crypto/frost/src/sign.rs:385-398`). With ρ_i and c computable by the attacker from public data, three shares from three distinct preprocess-sets under one `context` solve for `(d, e, λ·x)`, and `x` follows from the known Lagrange coefficient.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret share, which is the validator's root-of-trust key used for DKG confirmation. Combined with other shares (or used to forge that validator's participation), this enables forging `set_keys` confirmations and compromise of the validator set's signing authority. Equivalent to High severity key-share recovery.

### Likelihood Explanation
The deterministic-reuse design is intentional and defended only by the assumption that BFT finalization guarantees identical preprocess sets across every re-execution — an assumption the code itself flags as an unenforced TODO (`signing_protocol.rs:50-54`). A single participating validator publishing its preprocess, plus normal re-execution paths (reboots, `share` then `complete` with differing inputs, retries under the same `attempt` context), can produce multiple `sign` calls over the same nonces with attacker-influenced peer inputs. No broken-BFT or collusion is required — only variation in the delivered preprocess map between invocations.

### Recommendation
Bind the cached preprocess to a single signing session: record alongside `CachedPreprocesses` the exact peer preprocess set and message hash used on first `sign`, and abort if a subsequent `share_internal`/`complete` for the same `context` is invoked with different inputs (implementing the TODO check). Alternatively, build `AlgorithmSignatureMachine` once and persist/restore it rather than re-running `preprocess_internal`, so `sign` can never execute twice on the same nonces.

### Proof of Concept
1. Victim coordinator runs `DkgConfirmer::preprocess()` for context `("DkgConfirmer", attempt)`; seed `S` is stored.
2. `share(preprocesses_A, key_pair)` runs `sign` producing share `s1 = d + e·ρ1 + λ·x·c1` over nonce seed `S` and peer set A.
3. `complete(preprocesses_B, key_pair, shares)` is invoked with `preprocesses_B ≠ preprocesses_A` (e.g., a different subset/superset of validator preprocesses, or after reboot re-execution); it re-derives the same `(d, e)` from `S` and computes `s2 = d + e·ρ2 + λ·x·c2` with `ρ2 ≠ ρ1`, `c2 ≠ c1`.
4. A third invocation (e.g., another `complete`/re-execution with preprocess set C) yields `s3`. All `ρ`, `c`, `λ` are publicly computable from on-chain data.
5. Solve the 3×3 linear system in `(d, e, λ·x)` over the Ristretto scalar field; divide by `λ` to recover the victim's private key share `x`.
