### Title
`SignableTransaction::new` excludes the user-controlled OP_RETURN output from fee/weight estimation, underpaying the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class is "cost estimation omits a user-controlled component of the work" — in GMX, `estimateExecuteWithdrawalGasLimit` forgot the optional swap; here, `SignableTransaction::new` builds the transaction's OP_RETURN data output into `tx_outs` but computes `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check from `calculate_weight_vbytes`, which is only given `payments` and `change`, never `data`. An unprivileged caller passing `data` (up to 80 bytes) gets a transaction whose real vsize exceeds the estimated one, so the paid fee falls below the requested `fee_per_vbyte` (or the tx silently exceeds standard weight).

### Finding Description
`SignableTransaction::new` accepts a public `data: Option<Vec<u8>>` parameter, bounded only to 80 bytes (line 171). When set, it pushes an additional OP_RETURN output onto `tx_outs` at lines 194–202. However, the fee estimation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` and the change-path estimation at lines 225–226 calls it with `payments, Some(&change)` — neither passes `data`. `calculate_weight_vbytes` (lines 62–127) constructs the mock `Transaction` solely from `payments` plus the optional change output, so the OP_RETURN output's weight (~8 bytes value + script length + up to ~83 script bytes ≈ 90+ vbytes) is never counted.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (line 206, and `fee_with_change` at line 227) is computed on an undersized vbytes, so `needed_fee` under-reports the fee required to hit `fee_per_vbyte`.
- When a `change` output exists, the change amount is set to `input_sat - payment_sat - fee_with_change` (line 230), so the *actual* fee equals the underestimated `fee_with_change`: the final transaction pays a lower effective sat/vbyte than the caller specified and can fall below relay/mempool acceptance or just confirm much later.
- The `weight` variable compared against `MAX_STANDARD_TX_WEIGHT` (line 241) is the mock weight without the data output, so a transaction can pass the size check while the real signed transaction exceeds standard weight and is rejected by the network.
- The minimum-fee check at line 211 also uses the underestimated `vbytes`, so the `TooLowFee` guard is weaker than intended.

### Impact Explanation
An attacker or any caller supplying `data` obtains a transaction that pays less than the requested fee rate — the same economic shape as the GMX report (order creator underpays for execution). In Serai's wallet this means change-bearing transactions with `data` broadcast at a lower feerate than requested, risking stuck/non-relayed transactions, and the weight bound can be bypassed, producing transactions above `MAX_STANDARD_TX_WEIGHT` that nodes will reject. The underestimation is deterministic and fully controlled by the caller through `data` and `change`.

### Likelihood Explanation
Any caller of `SignableTransaction::new` who supplies `data` and a `change` script triggers the undercount; both are public, untrusted inputs to the constructor. The miscalculation occurs on every such call — no race or special state needed — though exploitation only degrades the transaction's effective feerate rather than stealing funds, consistent with Medium severity.

### Recommendation
Include the OP_RETURN output in the estimation: pass the data (or the fully-built output list, including the OP_RETURN `TxOut`) into `calculate_weight_vbytes` for both the change and no-change paths, so `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all account for the actual transaction contents.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// In SignableTransaction::new, data is added to tx_outs (lines 194-202) but
// calculate_weight_vbytes only receives `payments` and `change` (lines 204, 225-226).

let inputs = vec![received_output];            // 1 input
let payments = vec![(payment_script, 10_000)]; // 1 payment
let change = Some(change_script);
let data = Some(vec![0u8; 80]);                // 80-byte OP_RETURN payload

let tx = SignableTransaction::new(inputs, &payments, change, data, fee_per_vbyte).unwrap();

// Actual signed tx has 3 outputs (payment, OP_RETURN, change).
// tx.needed_fee() == fee_per_vbyte * vsize(tx WITHOUT the ~90-vbyte OP_RETURN output)
// tx.fee() == needed_fee (change absorbs the rest), so:
//   tx.fee() / tx.vsize() < fee_per_vbyte
// i.e., the effective feerate is strictly below the caller's request, and the
// MAX_STANDARD_TX_WEIGHT check was evaluated on the smaller, data-less mock tx.
```
