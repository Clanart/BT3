### Title
Partial-commit patch is built from a re-fetched, potentially stale diff — silent commit corruption via TOCTOU on line-selection indices - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets users stage a subset of lines/hunks in a file ("partial commit") by selecting lines in a previously rendered diff. When the commit is actually executed, `applyPatchToIndex` does **not** reuse the diff the user visually reviewed — it re-fetches a brand-new diff from disk at commit time and reapplies the old line-index-based selection to it. If the tracked file's on-disk content changes between the moment the user made their line selection and the moment "Commit" is pressed, the selection indices silently map onto different content, producing a commit/push that does not match what the user reviewed and approved.

### Finding Description
The UI review flow (`updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts`) loads a diff for the selected file and stores a `DiffSelection` keyed by line index/hunk offsets (`file.selection`) [1](#0-0) . The code even acknowledges that "the diff might have changed dramatically since last we loaded it" and only prunes indices that no longer exist, without invalidating the underlying data correspondence [2](#0-1) .

When the commit actually happens, `_commitIncludedChanges` takes `selectedFiles` straight from the cached `state.changesState.workingDirectory.files` (captured potentially long before the click) [3](#0-2)  and calls `createCommit`, which calls `stageFiles`, which for any file with a partial `DiffSelectionType.Partial` selection calls `applyPatchToIndex` [4](#0-3) .

Inside `applyPatchToIndex`, the diff used to build the actual patch is fetched **fresh, live, at commit time** — not the diff object the user looked at in the UI:

```
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
``` [5](#0-4) 

`formatPatch` walks the *new* diff's hunks and lines and decides what to include purely by absolute line index via `file.selection.isSelected(absoluteIndex)` [6](#0-5) . There is no check that the new diff is structurally/content-identical to the diff the selection was computed against. If the file content changed (added/removed lines, reordered hunks) between the time selection indices were recorded and the time `applyPatchToIndex` runs, the same numeric indices now point at different lines. Git then happily applies (`git apply --cached --unidiff-zero`) whatever hunk that mismatch produces to the index, and it becomes part of the commit.

### Impact Explanation
This breaks the fundamental invariant of Desktop's partial-staging feature: "what the user visually selected is what gets committed." The corrupted value here is the **selected line/hunk indices in `DiffSelection`**, which are validated/consumed against a diff snapshot different from the one they were computed from. Existing guards (`updateChangesWorkingDirectoryDiff`'s selectable-line pruning) only remove indices that no longer exist as lines at all — they do nothing to detect that the meaning of a still-valid index has shifted. Any process capable of modifying tracked working-directory content between the user's line selection and the commit click (e.g. a clean/smudge filter, a `post-checkout`/`post-merge`/background tool run as part of the repository's configured hooks/filters, or any other file-touching automation triggered while Desktop is idle on the Changes tab) can cause the user to unknowingly commit and push content they never selected/reviewed — a silent corruption of what the user commits, matching the "unprivileged, attacker-controlled repository object leads to corrupted commit" impact class.

### Likelihood Explanation
Requires no special privileges beyond what an attacker already has when they control a cloned/fetched repository's content or its git filter/hook configuration (a `.gitattributes`-declared clean/smudge filter or standard hook is not "local/physical access" — it's part of the repo the victim opened in Desktop) and some natural delay between the user selecting lines and clicking "Commit" (typical for larger diffs, review time, or waiting on other operations). No unnatural user steps are required — this is the app's normal partial-commit review-then-commit workflow.

### Recommendation
`applyPatchToIndex` (and `stageFiles`/`_commitIncludedChanges`) should not silently re-fetch a new diff and apply cached selection indices to it. Instead:
- Cache and reuse the exact diff object the selection was computed against (already available on `IChangesState.selection.diff`), or
- Before applying the patch, re-diff and compare against the diff the selection was derived from; if they differ, abort staging that file and force the UI to re-render the diff / re-request user confirmation.

### Proof of Concept
1. Clone/open a repository in Desktop that has (or the attacker controls, e.g. via a malicious `clean`/`smudge` filter or hook configured in the repo) a mechanism that rewrites a tracked file's content shortly after checkout/on interval.
2. User modifies `file.md`, opens the Changes tab, Desktop calls `updateChangesWorkingDirectoryDiff` and renders the diff; user selects only specific benign lines to commit (partial selection), leaving the message box open while reviewing.
3. Before the user clicks "Commit", the attacker-controlled filter/hook rewrites `file.md` on disk, shifting hunk/line positions but keeping the file in a state where the same indices are still "selectable" lines (so the stale-selection-pruning in `updateChangesWorkingDirectoryDiff` does not clear them, and the UI may not even re-run this until another interaction).
4. User clicks "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches the diff freshly from the now-modified file and applies the stale index-based selection via `formatPatch`, producing a patch that includes attacker-injected content at those indices.
5. The resulting commit (and any subsequent push) contains content the user never saw or approved, silently corrupting what the user pushes to the remote.
