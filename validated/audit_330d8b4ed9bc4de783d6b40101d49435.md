### Title
Wasmd precompile swallows OCC-abort panics as ordinary execution errors - (File: precompiles/wasmd/wasmd.go)

### Summary
`VersionIndexedStore.Get` and `ValidateReadset` in the multiversion store signal an optimistic-concurrency-control (OCC) conflict by writing to an abort channel and then `panic(abort)`, relying on that panic to unwind all the way to the scheduler's `occ.Abort`-aware recovery middleware (`app.makeGigaDeliverTx` in `app/app.go` and `newOCCAbortRecoveryMiddleware` in `sei-cosmos/baseapp/recovery.go` / `app/legacyabci/recovery.go`). [1](#0-0) [2](#0-1) 

### Finding Description
When a transaction hits an `IsEstimate()` value while running under the OCC scheduler, `WriteAbort` is called and then `panic(abort)` is raised so that the surrounding recovery middleware can detect an `occ.Abort` type and reschedule the transaction instead of treating it as a real error. [3](#0-2) 

However, the `wasmd` precompile — reachable from any EVM transaction that calls into `WasmdAddress` (`0x...1002`) via `instantiate`, `execute`, or `query` — installs its own unconditional `recover()` in each handler:
```go
defer func() {
    if err := recover(); err != nil {
        ret = nil
        remainingGas = 0
        rerr = fmt.Errorf("%s", err)
        return
    }
}()
``` [4](#0-3) [5](#0-4) [6](#0-5) 

If the CosmWasm keeper call underneath (`p.wasmdKeeper.Instantiate`, `p.wasmdKeeper.Execute`, `p.wasmdViewKeeper.QuerySmartSafe`) reads/iterates a KV store key that is backed by a `VersionIndexedStore` and encounters an `Estimate` value written by a still-in-flight higher-index transaction, the resulting `panic(occ.Abort{...})` is caught by this `recover()` and converted into a generic `error` (`fmt.Errorf("%s", err)`), rather than being allowed to propagate to the scheduler's `occ.Abort`-aware recovery middleware in `makeGigaDeliverTx`/`runTx`. This exactly matches the reported bug class: the panic is intercepted before reaching the OCC-abort recovery layer, so the scheduler cannot distinguish an abort from a genuine contract failure.

### Impact Explanation
Because the type information is erased (`occ.Abort` → plain `error`), the calling EVM message treats the wasmd call as a normal revert/failure rather than an abort-and-retry signal:
- The transaction is not correctly re-scheduled/re-executed with fresh dependency data; instead it commits a result (e.g., a reverted call or `VmError`) computed from a transient, undefined intermediate state (the value seen right before the panic point may be a torn/half-computed read).
- This can lead to non-deterministic or incorrect execution outcomes for wasm-pointer-invoking EVM transactions under OCC parallel execution, potentially causing wrong contract state commits, incorrect fund transfers through the wasmd precompile (e.g. `execute`/`instantiate` sending native coin value via `pcommon.HandlePaymentUsei`), or a consensus-relevant apphash mismatch across nodes with different OCC scheduling/interleaving (since the outcome now depends on execution timing/estimate presence rather than being deterministic). Given the wasmd precompile handles token transfers as part of `instantiate`/`execute`, an incorrectly-swallowed abort could result in fund loss/inconsistent balances or a permanent chain split if different validators observe different interleavings of the same block's OCC execution.

### Likelihood Explanation
Reaching this code path requires only a normal EVM transaction that calls the `wasmd` precompile (`instantiate`/`execute`/`query`) while OCC parallel execution is enabled (`ProcessTXsWithOCCGiga`/`ProcessTXsWithOCCV2`), which is the default block-execution mode. Any unprivileged transaction sender or CW/pointer user invoking wasmd from EVM can trigger it; no validator or governance privilege is required. The condition (an in-flight `Estimate` write on a key touched by the wasmd call) depends on natural transaction ordering/conflicts within a block, which is common under concurrent OCC scheduling, especially for popular contracts.

### Recommendation
In each `wasmd` precompile handler's `recover()` block (and the analogous pattern used in `precompiles/distribution` and other precompiles), check whether the recovered value is an `occ.Abort` (or any sentinel abort type) and, if so, re-panic it immediately instead of converting it to an `rerr`. Per the referenced fix, do not rely on panic type-switching alone anywhere in the call chain between `mvkv::Get`/`ValidateReadset` and the top-level scheduler recovery middleware — every intermediate `recover()` (precompiles, wasmd keeper wrappers, EVM call/create wrappers) must explicitly detect and re-throw `occ.Abort` panics rather than swallowing them as generic errors.

### Proof of Concept
1. Enable OCC parallel execution (default in `ProcessTXsWithOCCGiga`/`ProcessTXsWithOCCV2`).
2. Submit a block containing two EVM transactions at increasing tx indices where transaction A (lower index) writes to a CosmWasm contract state key, and transaction B (higher index, executed speculatively in parallel) calls the `wasmd` precompile's `execute`/`query` targeting the same contract/state key before A's real write is finalized (so B sees an `Estimate` placeholder).
3. During B's execution, `wasmdKeeper.Execute`/`QuerySmartSafe` performs a `Get` on the estimated key via a `VersionIndexedStore`, triggering `panic(occ.Abort{...})` inside `sei-cosmos/store/multiversion/mvkv.go`.
4. The panic unwinds into the `wasmd` precompile's `defer func() { if err := recover(); ... rerr = fmt.Errorf("%s", err) }()`, which converts it into a plain error instead of letting it reach `makeGigaDeliverTx`'s `if abort, isOCCAbort := r.(occ.Abort); isOCCAbort` check.
5. Transaction B commits an `ExecTxResult` reflecting a spurious revert/error (based on a torn intermediate read) instead of being correctly retried by the OCC scheduler, producing an incorrect/non-deterministic block result. [7](#0-6)

// newOCCAbortRecoveryMiddleware creates a standard OCC Abort recovery middleware for app.runTx method.
func newOCCAbortRecoveryMiddleware(next recoveryMiddleware) recoveryMiddleware {
	handler := func(recoveryObj interface{}) error {
		abort, ok := recoveryObj.(scheduler.Abort)
		if !ok {
			return nil
		}

		return sdkerrors.Wrap(
			sdkerrors.ErrOCCAbort, fmt.Sprintf(
				"occ abort occurred with dependent index %d and error: %v",
				abort.DependentTxIdx, abort.Err,
			),
		)
	}

	return newRecoveryMiddleware(handler, next)
