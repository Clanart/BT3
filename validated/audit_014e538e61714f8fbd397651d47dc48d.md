Based on the investigation, the strongest and most concrete Desktop analog to the Yeetback "wrong trusted address" bug class is a **hostname-classification bypass in `isGitHubHost`** that is used to decide whether a remote host should be treated as a trusted GitHub endpoint (i.e., whether Desktop's real OAuth/PAT credentials should be handed to it) — the "wrong provider treated as trusted authority" pattern, but here the trust decision is fooled by attacker-controlled input rather than a hard-coded constructor mistake.

### Title
Weak Regex-Based GitHub Host Detection in `isGitHubHost` Enables Credential Disclosure to Attacker-Controlled Hosts - (File: app/src/lib/api.ts)

### Summary
`isGitHubHost` is a "best-effort" heuristic used to decide whether an arbitrary git remote host should be treated as a genuine GitHub/GHE endpoint. Part of that heuristic uses the regex `/(^|\.)(github)\./.test(hostname)` [1](#0-0)  which incorrectly matches any hostname that merely *starts with or contains* the literal substring `github.` (e.g. `github.attacker.com`), not just genuine `*.github.com`/GHE domains. This is analogous to the Yeetback bug: instead of validating the real trusted "provider" (a specific known GitHub/GHE endpoint), the function accepts any attacker-chosen host that superficially resembles one.

### Finding Description
`isGitHubHost` is documented as best-effort [2](#0-1) . Its decision chain is:
```
if (isDotCom(endpoint) || isGHE(endpoint)) return true
if (isKnownThirdPartyHost(hostname)) return false
if (/(^|\.)(github)\./.test(hostname)) return true
``` [3](#0-2) 

The regex requires only that the string `github.` appear at the start of the hostname or immediately after a dot. A domain such as `github.evil-attacker.com` or `sub.github.evil-attacker.com` satisfies `(^|\.)(github)\.` and is therefore classified as a trusted GitHub host without any further verification (no TLD/eTLD+1 check, no exact suffix match against `github.com`/`*.ghe.com`). This function is consumed by `trampoline-credential-helper.ts` [4](#0-3) , the module responsible for deciding whether Desktop's stored git credentials (OAuth tokens / PATs) should be supplied to git for a given remote host during fetch/push/clone/submodule operations.

The invariant that should hold — "only hand real GitHub credentials to a verified, trusted GitHub/GHE endpoint" — is broken by a substring-based hostname check that an attacker fully controls simply by registering a domain containing `github.` as a label.

### Impact Explanation
If the credential helper relies on `isGitHubHost` to gate credential disclosure, an attacker can craft a git remote/submodule URL (e.g. `https://github.malicious-domain.com/x.git`) that a victim clones, fetches from, or that gets pulled in transitively via a submodule inside an otherwise legitimate-looking repository. When git invokes Desktop's credential helper for that host, the flawed classifier may cause the user's real GitHub token to be sent to the attacker's server — i.e., **credential/token exfiltration**, one of the explicitly in-scope impacts for this analysis.

### Likelihood Explanation
The attacker only needs to control a repository (or a submodule reference within a repository) that the victim clones or fetches — no local access, no admin rights, and no social engineering beyond a normal "clone this repo" action, which is squarely within Desktop's unprivileged threat model (attacker controls a cloned/fetched repository or a git remote).

### Recommendation
Replace the substring regex with a strict eTLD+1/suffix match against the exact expected domains (`github.com`, `*.ghe.com`, and the specific configured Enterprise host), and ensure the credential helper never releases a token to a host that hasn't been strictly matched against a known, previously-authenticated endpoint stored in `Account`/`EndpointToken` records rather than a heuristic pattern match.

### Proof of Concept
1. Attacker creates a repository containing a `.gitmodules` entry (or simply asks the victim to add a remote) pointing to `https://github.attacker-domain.com/repo.git`.
2. Victim clones/fetches the parent repository in GitHub Desktop, triggering a submodule/remote operation against `github.attacker-domain.com`.
3. Git invokes Desktop's trampoline credential helper for that host; `isGitHubHost('https://github.attacker-domain.com/...')` evaluates `/(^|\.)(github)\./.test('github.attacker-domain.com')`, which is `true`.
4. If the helper treats this as a verified GitHub host, it releases the user's stored token to the git operation against the attacker's server, which can log the Basic/Bearer credential from the HTTP request.
