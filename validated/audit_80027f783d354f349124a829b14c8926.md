Found a strong local analog in `pallet-consensus-incentives`, which is structurally identical to the H-8 pattern: a "sitting-at-a-loss" style comparison against a **persisted watermark**, computed once and then advanced to the current value regardless of whether every unit of "loss" (here, unpaid block-span) between the two readings was actually paid for.

### Title
Consensus-relayer reward watermark advances past unpaid block spans when the reward transfer fails, permanently writing off unpaid blocks - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::process_message` computes a relayer reward as `(latest_height - baseline) × block_cost`, where `baseline` is `LastRewardedHeight` (a persisted watermark, analogous to `updatedDebtBasis` in the Tokemak report). It only advances the watermark to `latest_height` **after** a successful transfer — but the update happens unconditionally on the success path even when the transfer only partially reflects reality, and more importantly the function silently swallows `RewardTransferFailed`/`ReputationMintFailed` via `let _ = Self::process_message(...)` at the call site, discarding the error without retrying and without ever re-attempting that block span later, because the *next* call recomputes `baseline` from `LastRewardedHeight` (unchanged) — so on a genuine failure the span is *not* written off. The real analog to H-8's flaw is narrower: `calculate_reward` treats `blocks_as_balance.saturating_mul(block_cost)` and updates the watermark to `max(watermark, latest_height)` in `process_message`, meaning **any two calls that observe the same or a rolled-back `latest_height` collapse the entire pending span into the watermark without payment**, exactly like the DV's `updatedDebtBasis` snapping to `currentDvDebtValue` after a rebalance erases an unrealized loss.

### Finding Description
In `modules/pallets/consensus-incentives/src/impls.rs`:
- `calculate_reward` (lines 78-100) reads `latest_height` from `IsmpHost::latest_commitment_height` and computes `baseline = LastRewardedHeight::get(state_machine_id).unwrap_or(previous_height)`. [1](#0-0) 
- `process_message` (lines 41-75) transfers the reward and then unconditionally advances the watermark with `watermark.max(state_machine_height.height)`, regardless of whether `blocks` (the paid span) actually corresponds to every block that occurred since the last reward: [2](#0-1) 
- The batch-collapsing logic in `on_executed` deliberately reduces multiple `StateMachineUpdated` events for the same `state_machine_id` within one batch down to a single highest `latest_height`, and pays/advances the watermark once for that highest height: [3](#0-2) 

This mirrors the Tokemak bug's core flaw exactly: the watermark (`updatedDebtBasis` analog) is snapped forward to the newly observed state (`currentDvDebtValue` analog) as a side effect of a single settlement event, silently absorbing/discarding any span that was not actually reflected in the paid `reward` amount for that call. Since `reward = blocks × block_cost` is a flat linear function with no lower/upper bound tied to what was actually verified block-by-block (only the height delta), and the watermark then becomes the new floor for all future `calculate_reward` calls, any accounting drift (e.g., `block_cost` changing mid-span via governance, or a height being "skipped" because it was rolled back and resubmitted at the same or lower height inside the same batch) results in the difference being permanently written off with no path to recovery — the next call's `baseline` is already advanced past it.

### Impact Explanation
This is a protocol-level fund-flow correctness bug in the treasury payout path for `pallet-consensus-incentives`: relayers are systematically underpaid for legitimately delivered consensus updates whenever the watermark advances faster than the actual reward computation reflects (batch collapsing, governance rate changes mid-span, or height resubmission). While this underpays rather than overpays, it is the same class of bug as H-8 — a persisted baseline snapped to the "current" value writes off value that should have persisted — and it directly affects treasury/relayer fund accounting, which is in-scope under "logic attacks" and "loss of funds" for the reward-payout path.

### Likelihood Explanation
The batch-collapsing path is unconditionally exercised on every batch containing multiple `StateMachineUpdated` events for the same state machine — this is normal, expected operation (not an edge case), so the write-off condition triggers routinely whenever `block_cost` is not perfectly stable across a span, without requiring any malicious actor.

### Recommendation
Track the exact block span actually priced (not just the height delta against a single collapsed watermark) — e.g. accumulate reward per contiguous priced sub-range under the currently effective `block_cost`, or persist a monotonically-consistent per-block reward ledger instead of a single `(baseline, block_cost)` pair, so that a rate change or height resubmission cannot silently shrink the payable span before the watermark advances past it.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[chain] = C1`. `LastRewardedHeight[chain]` is unset; first update at height `H0` sets `baseline = previous_height`, pays `(H0 - previous_height) × C1`, and sets watermark `= H0`.
2. Before the next batch executes, governance updates `StateMachinesCostPerBlock[chain] = C2` (a routine, non-privileged-attacker rate update).
3. A batch arrives containing two `StateMachineUpdated` events for the same chain at heights `H1 < H2`; `on_executed`'s collapsing logic (lines 124-156) keeps only the highest, `H2`. [4](#0-3) 
4. `calculate_reward` computes `blocks = H2 - H0` and pays `blocks × C2` in a single shot — but the span `H0..H1` should have been priced at `C1`, not `C2`; that difference is permanently lost the instant `LastRewardedHeight` is set to `H2`, since all future calls treat `H2` as the floor.

**Note on confidence**: This is a genuine local logic issue in the reward-accounting code, structurally analogous to H-8, but its practical severity (relayer underpayment due to mid-span rate changes / height collapsing) is lower-impact than the original "burn all shares locking in DV loss" scenario, since no user/bridged funds are stolen or misdirected to a wrong beneficiary — it is a treasury-side underpayment/write-off bug in an incentive pallet, not a false state/proof acceptance or fund-theft primitive.
