### Title
Unsigned OP_RETURN payer attribution allows theft of reimbursement credit via signature reuse - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
The payout transaction's OP_RETURN output, which `Verifier::update_finalized_payouts` trusts as the sole record of which operator "paid" a withdrawal, is not covered by the user's `SinglePlusAnyoneCanPay` signature. Because BIP341 SIGHASH_SINGLE only commits to the output at the same index as the signed input (index 0), the OP_RETURN at index 2 and the anchor at index 1 can be freely altered without invalidating the signature, letting an unprivileged attacker rebroadcast operator A's legitimate payout with a swapped OP_RETURN naming a different operator E.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk` recorded in the `withdrawals` table for a `deposit_id` should equal the xonly public key of the operator who actually funded/broadcast the payout transaction that spends the user's withdrawal UTXO. In practice `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) sets this value purely from parsing the mined transaction's OP_RETURN via `parse_op_return_data`/`get_first_op_return_output`, with no cryptographic tie to whoever actually signed or funded the transaction.

`Operator::withdraw` (`core/src/operator.rs:560-637`) builds the payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which places outputs as `[user_output, anchor, OP_RETURN(operator_xonly_pk)]` and signs only input 0 with the withdrawing user's `SinglePlusAnyoneCanPay` signature (`payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` in `core/src/operator.rs:630`). `calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-233`) uses `Prevouts::One` for this sighash type, which per BIP341 only commits the single output at the signed input's index (output 0). Outputs 1 and 2 (anchor, OP_RETURN) are entirely unsigned.

Exploit flow: operator A funds/broadcasts its payout tx for withdrawal `idx`, consuming the user's UTXO with a valid `SinglePlusAnyoneCanPay` witness on input 0. Before it confirms, an attacker observing the unconfirmed transaction copies input 0's witness (the valid signature) and constructs a variant transaction spending the same UTXO, keeping output 0 identical (required for signature validity) but replacing the OP_RETURN with operator E's xonly pubkey, then broadcasts it with a higher fee/RBF to win the race. Once mined, `update_finalized_payouts` parses this variant and stores `payout_payer_operator_xonly_pk = E`. `Operator::validate_payer_is_operator` (`core/src/operator.rs:1687-1740`) on E's own node subsequently succeeds because `payer_xonly_pk == self.signer.xonly_public_key`, and E's `PayoutCheckerTask` (`core/src/task/payout_checker.rs:31-111`) treats this as a legitimate payout it fronted, triggering `handle_finalized_payout` to consume one of E's kickoff/round slots and eventually claim `Reimburse` funds from the shared move-to-vault UTXO — for a withdrawal E never actually paid.

No existing guard checks that the OP_RETURN pubkey corresponds to whoever funded/signed the transaction; `update_finalized_payouts` performs no such verification, and `validate_payer_is_operator` only checks self-consistency, not actual payment provenance.

### Impact Explanation
BTC leaves the shared move-to-vault UTXO to operator E via the Reimburse transaction for a payout E never funded, while operator A — who genuinely paid the user — is permanently unable to be reimbursed because the double-spend orphans A's broadcast and the DB attributes the payout to E. This matches the Critical category directly: "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed." The attack is repeatable across any withdrawal/deposit as long as an attacker can win a fee race against the legitimate payout broadcast, and does not require E's cooperation or awareness — only knowledge of E's public xonly pubkey.

### Likelihood Explanation
The attacker only needs to observe an operator's unconfirmed payout transaction (via mempool/P2P, a normal capability) and win a fee-based race to get their OP_RETURN-swapped variant mined first — standard RBF/CPFP fee-bumping is sufficient since the swapped output isn't part of consensus-invalid changes. No key compromise, no privileged access, and no cooperation from any operator or verifier is required; the attacker merely reuses a signature they observed and controls unsigned bytes (OP_RETURN, other outputs) exactly as permitted by the threat model. This is highly feasible and repeatable for every withdrawal processed by any operator.

### Recommendation
Bind the payout's payer attribution to a value that is cryptographically committed within the signed scope, e.g., have the OP_RETURN operator commitment covered by an `AllPlusAnyoneCanPay`/`All` sighash (or a separate operator-signed commitment) so that changing the OP_RETURN invalidates the user's signature, or otherwise require the fronting operator to itself sign/commit to the OP_RETURN content (e.g., via an additional operator signature over the full transaction, verified in `update_finalized_payouts` before recording `payout_payer_operator_xonly_pk`).
