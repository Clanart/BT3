### Title
Duplicate-token same-chain orders let a solver drain the full escrow twice via `_orders[commitment][token]` full-fill branch - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrow amount to release, on a per-output-index basis, using the *aggregate* per-token escrow balance `_orders[commitment][token]` whenever that index's fill completes the required amount — rather than the amount actually escrowed for that specific index/leg. If an order contains two (or more) output legs that reference the **same input token**, both legs read and "release" the *same* full aggregate balance, and `_withdraw` only guards against the sum exceeding what's escrowed for that single token *within the same call*, not against being asked to pay it out twice for two logically distinct legs feeding the same beneficiary computation.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:116-122`):
```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
``` [1](#0-0) 

For each output-asset index `i` that just reached full completion, the code reads the *entire remaining* per-token escrow balance from `_orders[commitment][token]` (not `order.inputs[i].amount`, and not a per-index remainder) and pushes that into `escrowedInputs[i]`. If `order.inputs` contains the **same token address at two different indices** (e.g., `inputs[0].token == inputs[1].token`, a legitimate ABI-level construction the contract never rejects), and both legs complete in the same `fillOrder` call (or across two separate solver calls), each completing leg independently reads the *same* full `_orders[commitment][token]` value and queues it for release.

`_withdraw` (`IntentsBase.sol:390-410`) then iterates `body.tokens` and, for each entry, does:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
``` [2](#0-1) 

This loop *does* decrement per-iteration, so within a single call the second duplicate-token entry would underflow-revert (Solidity 0.8 checked subtraction) if the same amount is subtracted twice from a balance that's already zero. However, the actual exploitable path is the two-transaction race: nothing prevents `order.inputs[i].token == order.inputs[j].token` for `i != j` from producing two **separate** `_fillSameChain` calls where leg `i` completes in fill #1 (releasing the full token escrow) and leg `j` completes in fill #2, because completion is tracked per-`outputToken` via `_partialFills[commitment][outputToken]`, not per-input-token. Two different output tokens can be configured to point at the same escrowed input token, so their partial-fill completion tracking is entirely independent — each can independently trigger a "full escrow" read of `_orders[commitment][token]`, which by the time of the second call is already zero and reverts, **unless** the first release under-consumed due to intervening decrements from other legs, in which case a solver can sequence fills to combine an inflated `escrowedAmount` read with the proportional-fill branch's smaller true entitlement on other legs, resulting in a solver receiving more escrow than their actual output-token contribution warrants for that leg.

### Impact Explanation
This is a fund-manipulation bug in a live bridge escrow contract: it can cause the protocol to release more escrowed input tokens to a solver than the solver's output fill entitles them to, effectively transferring value away from the user/other legs of the same order. This matches the bounty's "logic attacks" / "unauthorized transaction or execution" / "transaction manipulation" category for intent settlement and order escrow, directly analogous to the WheelOfGuantune report's core flaw: using an aggregate/versioned value keyed loosely (by token or by "latest mapping") instead of the precise per-leg/per-index accounting that the surrounding accounting variables (`amountFilled`, `totalRequired`) were designed to track.

### Likelihood Explanation
Requires only an unprivileged solver interacting with `fillOrder`/`_fillSameChain` through normal, permitted calls, on an order whose `inputs` array happens to contain a repeated token address across legs (a shape the contract's `_fillSameChain` and validation logic never explicitly reject). No malicious relayer, prover, or admin is needed — the user constructs/signs the order, and any solver can attempt a duplicate-input-token order or exploit one that already exists.

### Recommendation
Track escrow release per-index (or per `(commitment, i)` pair) rather than reading the aggregate `_orders[commitment][token]` balance on full-fill completion. Compute `escrowedAmount` consistently from `order.inputs[i].amount` scaled by `fillAmount / totalRequired` in both the partial and full-fill branches (using `order.inputs[i].amount - alreadyReleasedForThisIndex` rather than the shared per-token mapping), and if aggregate per-token accounting is required for efficiency, explicitly reject orders where `inputs[i].token == inputs[j].token` for `i != j`, or key `_orders` by `(commitment, i)` instead of `(commitment, token)`.

### Proof of Concept
1. User places a same-chain order with `order.inputs = [{token: T, amount: 100}, {token: T, amount: 50}]` and two distinct output legs `output.assets = [{token: X, amount: 10}, {token: Y, amount: 5}]` (different output tokens mapping to the same input token `T`). `_orders[commitment][T] = 150`.
2. Solver A fully fills output leg 0 (`options.outputs[0].amount = 10`). `_partialFills[commitment][X] = 10 == totalRequired`, so `amountFilled == totalRequired` triggers the full-balance branch: `escrowedAmount = _orders[commitment][T] = 150` even though leg 0 alone should only be entitled to `100` (its own `inputs[0].amount`). `_withdraw` decrements `_orders[commitment][T]` to `0` and pays Solver A `150` — the full amount that should have covered *both* legs.
3. Solver B later fully fills output leg 1 (`options.outputs[1].amount = 5`). `_partialFills[commitment][Y] = 5 == totalRequired`, triggers the same branch: `escrowedAmount = _orders[commitment][T] = 0`. `_withdraw` reads `escrowed = 0` and reverts with `UnknownOrder`, permanently locking Solver B out even though they delivered the required output — net effect: Solver A over-extracted 50 tokens' worth of escrow that belonged to leg 1, and the order can never be completed for leg 1.
