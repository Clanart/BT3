### Title
Deterministic re-execution of the DKG confirmation MuSig reuses FROST nonces, enabling private key share recovery if a second distinct `set_keys` message is ever signed for the same attempt - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
CVE-2022-2609 is a use-after-free: state consumed by one operation is later used again after its lifetime ended. The direct analog in Serai is the consumption of FROST nonces: `DkgConfirmer` derives its signing nonces deterministically from a `CachedPreprocess` seed stored in `CachedPreprocesses` keyed only by `(b"DkgConfirmer", attempt)`, and every call to `preprocess_internal`/`share_internal` re-materializes the *same* nonces via `AlgorithmSignMachine::from_cache` (`seeded_preprocess` uses `ChaCha20Rng::from_seed(*seed.0)`). The file's own header states safety depends on the nonces only ever signing one message, and explicitly notes the check that the on-chain commitments match the presumed preprocess is a TODO that is not implemented (`signing_protocol.rs:50-54`).

### Finding Description
- `SigningProtocol::preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:100-148`) loads (or creates once) a 32-byte seed from the DB and deterministically regenerates identical nonce scalars `d, e` and identical commitments each time it runs.
- `DkgConfirmer::share` (`signing_protocol.rs:304-310`) calls `share_internal`, which calls `machine.sign(preprocesses, msg)` producing a signature share `s = d + b·e + c·x_i` where `c` binds the message and signing set.
- In `generated_key_pair` (`coordinator/src/tributary/handle.rs:47-60`), `DkgKeyPair::set` unconditionally overwrites the stored key pair for `(genesis, attempt)` and `share()` is then invoked. Nothing deduplicates invocations of this function per attempt, and `msg = set_keys_message(set, removed, key_pair)` varies with `key_pair`.
- Later, `DkgConfirmed` handling calls `confirmer.complete(preprocesses, &key_pair, shares)` (`handle.rs:533-535`), which internally calls `share_internal` again — a second `sign()` under the same nonces.
- If the coordinator's `share()`/`complete()` path is ever driven over a *distinct* `key_pair` or distinct stored `ConfirmationNonces` for the same `attempt` — e.g., a second processor key-pair report overwriting `DkgKeyPair` before `complete`, since `DkgKeyPair::set` and `KeyToDkgAttempt::set` (`handle.rs:54-55`) blindly overwrite — two shares under identical nonces but different challenges are produced. Two such shares yield the secret share by linear algebra: `x_i = (s₁ − s₂) / (c₁ − c₂)` (adjusting for the binding factor), compromising the validator's root MuSig key share.
- The safety argument in the header (`signing_protocol.rs:25-55`) relies on BFT ordering ensuring identical received messages and on complete rebuilds re-deciding nonces; but the seed is persisted in `CachedPreprocesses` across restarts, so a rebuild re-decides nothing — it reuses the same seed. The acknowledged missing verification that the signed-over preprocesses match what is on-chain is exactly the guard that would catch divergence, and it is absent.

### Impact Explanation
Recovery of a coordinator validator's private key share for the DKG-confirmation MuSig. That key is the validator's root-of-trust key used to authorize `set_keys` on Substrate; its compromise combined with threshold cooperation (or if it is a full key under the MuSig structure of the validator set) enables forging confirmations/signatures. Severity: High if reachable; at minimum Medium given the precondition.

### Likelihood Explanation
The nonce reuse fires whenever `share_internal` executes twice with differing `(preprocesses, msg)` under the same `(context, attempt)`. Within the fully-honest single-flow this does not happen (`share` and `complete` use identical inputs, yielding an identical discarded share). The exposure exists because `generated_key_pair` overwrites `DkgKeyPair` without checking for a prior, different pair and the documented on-chain commitment-vs-preprocess consistency check is unimplemented; any path that mutates the stored key pair or preprocesses for an in-flight attempt (re-report after blame, reorg-adjacent re-execution, processor retry emitting a distinct pair) turns the deterministic-nonce design into key-share disclosure. The authors clearly recognized the risk — the header calls reuse "explicitly unsafe" — but left the enforcement as a TODO.

### Recommendation
- Before signing in `share_internal`, verify the locally presumed preprocess/commitments equal the ones actually published on-chain for this `(context, attempt)` (the existing TODO at `signing_protocol.rs:50-54`), and abort if not.
- Make `generated_key_pair`/`DkgKeyPair::set` idempotent: reject a differing `key_pair` for an attempt that already has one.
- Record in the DB that a context's seed has produced a share over a given `(preprocesses_hash, msg_hash)` and refuse to sign differing inputs under the same seed.

### Proof of Concept
Conceptual: run the coordinator's `DkgConfirmer` flow for attempt `a`; observe published share `s₁` over `msg₁ = set_keys_message(set, removed, kp₁)`. Cause `generated_key_pair` to run again for `a` with a distinct `kp₂` (accepted unconditionally at `handle.rs:54-59`), yielding `s₂` over `msg₂` with identical `(d, e)` because `CachedPreprocesses` still holds the same seed (`signing_protocol.rs:123-145`). Solve `x_i = (s₁ − s₂)·(c₁ − c₂)⁻¹` where `cᵢ` are the per-message binding challenges, recovering the validator's Ristretto secret share.
