Regular `withdraw`/`withdrawFor` in `MasterMagpie` are protected by `nonReentrant` [1](#0-0) . However, `emergencyWithdraw` is **not** guarded by `nonReentrant` and violates the Checks-Effects-Interactions pattern in the same way as the reported `finalizeGrant` bug: it performs the external token transfer before fully updating the user's accounting state.

### Title
Checks-Effects-Interactions violation in `emergencyWithdraw` allows stale `user.amount` during reentrant callback - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.emergencyWithdraw` zeroes `user.available` and transfers the staking token to the caller before decrementing `user.amount` and recalculating `user.rewardDebt`, and the function lacks a `nonReentrant` guard.

### Finding Description
```solidity
function emergencyWithdraw(address _stakingToken) external whenPaused {
    PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
    UserInfo storage user = userInfo[_stakingToken][msg.sender];
    uint256 availableaAmount = user.available;
    user.available = 0;
    IERC20(pool.stakingToken).safeTransfer(address(msg.sender), availableaAmount);
    emit EmergencyWithdraw(msg.sender, _stakingToken, availableaAmount);
    user.amount = user.amount - availableaAmount;
    user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;
}
``` [2](#0-1) 

`safeTransfer` is called with `user.amount` still holding its pre-withdrawal (stale, inflated) value, exactly mirroring the `finalizeGrant`/`transfer`-before-`grant.complete` pattern described in the report: state effects (`user.amount`, `user.rewardDebt`) are applied *after* the external interaction, and no reentrancy guard is present on this particular function (unlike `deposit`/`withdraw`/`withdrawFor`, which are all marked `nonReentrant`) [1](#0-0) .

### Impact Explanation
If the staking token registered for a given pool has any transfer-hook/callback semantics (e.g. an ERC-777-style or otherwise hook-enabled token used as `pool.stakingToken`), a reentrant call during `safeTransfer` would observe `user.amount` still at its pre-withdraw value while `user.available` is already zero. Depending on which other pool/helper functions are reachable while the contract is `whenPaused` (note most functions require `whenNotPaused`, sharply limiting the attack surface during the paused emergency window), this stale `user.amount` could be leveraged by any code path that reads `user.amount` without also checking `user.available`, potentially miscalculating rewards or unlock amounts for that user.

### Likelihood Explanation
Likelihood is low. `emergencyWithdraw` is only callable `whenPaused`, which is an unusual and short-lived project state, and nearly all other unprivileged entry points into `MasterMagpie` are gated by `whenNotPaused`, so there is very limited functionality reachable to actually leverage the stale `user.amount` mid-call. Additionally, I was not able to confirm in the indexed code that any of the staking tokens actually registered in the deployed pools (WombatStaking receipt tokens, vlMGP, mWomSV) implement hooks capable of reentering during a standard `IERC20.transfer`/`safeTransfer` call — these appear to be plain mintable ERC20 receipt tokens [3](#0-2) , not ERC-777 or hook-enabled tokens. Without a hook-capable token, this CEI violation is not concretely exploitable, which is why I present the finding as a defensive/best-practice gap rather than a confirmed exploitable path.

### Recommendation
Reorder `emergencyWithdraw` to fully update all state (`user.available`, `user.amount`, `user.rewardDebt`) before performing the external `safeTransfer` call, and add a `nonReentrant` modifier consistent with the other state-mutating entry points (`deposit`, `withdraw`, `withdrawFor`) in the contract.

### Proof of Concept
Concrete end-to-end exploitation could not be demonstrated from the indexed code because none of the staking tokens actually wired into `MasterMagpie` (vlMGP, mWomSV, Wombat receipt tokens) appear to support transfer callbacks/hooks needed to reenter during `safeTransfer` [3](#0-2) . The finding is a genuine CEI-pattern deviation matching the report's bug class, but I cannot confirm it meets the bar of "concrete direct theft of user funds" without a hook-enabled staking token being registered, which would itself require a privileged pool-registration action outside the unprivileged-wallet threat model.
