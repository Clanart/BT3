### Title
Unprivileged participant triggers panic (abort) in PedPoP blame adjudication via out-of-range recipient index - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The FreePBX bug class is: an unauthenticated request reaches a state-changing/destructive operation (module uninstall) instead of being rejected, yielding a denial of service. The analog in Serai's in-scope code is `Decryption::decrypt_with_proof`, which indexes `self.enc_keys[&decryptor]` without a membership check. `Decryption::enc_keys` is only populated for participants `1..=n`, but `AdditionalBlameMachine::blame` / `BlameMachine::blame` accept an attacker-influenced `recipient: Participant` (any nonzero `u16`). Supplying a recipient index `> n` causes an unconditional panic while adjudicating blame, instead of cleanly identifying the faulty party — aborting the DKG/fault-resolution path for every node that evaluates the blame.

### Finding Description
`AdditionalBlameMachine::new` registers exactly the participants `1..=n` into `Decryption.enc_keys` via `encryption.register(i, msg)`. [1](#0-0) 

`blame` then forwards the caller-supplied `sender`/`recipient` pair, unchecked against `1..=n`, into `blame_internal` → `decrypt_with_proof`. [2](#0-1) 

Inside `decrypt_with_proof`, once the per-message PoP verifies, the DLEq proof verification evaluates `self.enc_keys[&decryptor]` as an argument — a `HashMap` index that panics if `decryptor` was never registered. [3](#0-2) 

`Participant` is a plain nonzero `u16` newtype (constructed via `Participant::new`, which only rejects 0), so `recipient = Participant::new(n + 1)` is well-formed but unregistered. There is no `get`/error path — the `HashMap` `Index` impl panics. The processor's `VerifyBlame` handler routes attacker-originated `accuser`/`accused` fields from coordinator messages directly into this API (`blame(accuser, accused, ...)`), making the panic reachable from externally supplied indices during a DKG dispute. [4](#0-3) 

### Impact Explanation
Any party able to submit or trigger a blame adjudication can force an immediate panic (`HashMap` index on a missing key) in every machine that evaluates the blame statement with a forged recipient index, rather than the machine returning the honest `Participant` result it is documented to return. This aborts the DKG/validator process mid-fault-resolution — the exact analog of "unauthenticated request triggers a destructive action": an operation intended to merely *classify* fault instead *crashes* the adjudicator, denying service and preventing the guilty party from being slashed. Since the panic occurs inside the crypto library (`#![no_std]`-compatible panic = abort/unwrap in calling process), it propagates as a process crash for callers that invoke `blame` on untrusted indices.

### Likelihood Explanation
Triggering requires only that an accuser/attacker control the `recipient`/`accused` index passed to `blame` — a field drawn from the accusation message — plus a message carrying a valid per-message PoP (trivially produced by the sender role, or any `EncryptedMessage` whose PoP verifies under its own key). No threshold collusion, no leaked keys, and no broken BFT are required; a single participant-level fault-dispute suffices. The failure mode is deterministic: `enc_keys` provably contains only `1..=n`, so any out-of-range index panics every time it is evaluated.

### Recommendation
Replace the panicking index with a checked lookup in `decrypt_with_proof`: `let Some(enc_key) = self.enc_keys.get(&decryptor) else { return Err(DecryptionError::InvalidProof) };`. Additionally, validate `sender`/`recipient` against `1..=n` (or the registered set) at the top of `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and `blame_internal`, returning a defined error/`PedPoPError` rather than indexing. The same audit should apply to `self.commitments[&sender]` in `blame_internal` (`crypto/dkg/pedpop/src/lib.rs` ~line 599), which has the same unguarded `HashMap` index over attacker-influenced `sender`.

### Proof of Concept
```rust
// crypto/dkg/pedpop: construct an AdditionalBlameMachine over n participants,
// then adjudicate blame with a recipient index > n.
let n: u16 = 4;
// commitment_msgs contains valid EncryptionKeyMessages for participants 1..=n
let machine = AdditionalBlameMachine::<Ristretto>::new(CONTEXT, n, commitment_msgs).unwrap();

// Attacker-controlled accusation fields: sender in-range, recipient out-of-range
let sender = Participant::new(1).unwrap();
let recipient = Participant::new(n + 1).unwrap(); // never registered in enc_keys

// msg is any EncryptedMessage whose PoP verifies (e.g. a share honestly
// encrypted to anyone, or crafted with a known key so pop.verify passes).
// When proof.is_some(), decrypt_with_proof evaluates:
//   self.enc_keys[&decryptor]  // HashMap index -> PANIC
machine.blame(sender, recipient, msg, Some(proof)); // thread panics, no blame returned
```
For `BlameMachine::blame` (the participant's own machine), the same panic is reachable even with an in-range recipient: `verify_r1` registers `enc_keys` only for *other* participants (`commitment_msgs` excludes `i` via `validate_map`), so `recipient == self.params.i()` indexes a key that was never inserted.
