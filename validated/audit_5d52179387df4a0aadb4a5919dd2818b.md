### Title
Missing EVM→CW→EVM re-entrancy guard on `StaticCallEVM` allows unbounded nested EVM execution via CosmWasm `evm_query_static_call`/ERC-pointer query bindings - ([File: x/evm/keeper/evm.go])

### Summary
The sudo report describes a policy engine that enforces an access-control check on one entry point (`execve`) but omits the equivalent check on an alternate, functionally-equivalent entry point (`execveat`/`fexecve`), letting a permitted caller reach forbidden behavior through the unguarded path. Sei-chain's EVM↔CosmWasm bridge has the same class of gap: `CallEVM` (the state-changing "EVM→CW→EVM" entry) explicitly enforces `if ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile() { return errors.New("sei does not support EVM->CW->EVM call pattern") }`, but its sibling entry point `StaticCallEVM` — reached whenever a CosmWasm contract issues an `evm_query_static_call` or any ERC20/721/1155 pointer query binding — has no such guard. [1](#0-0) [2](#0-1) 

### Finding Description
`CallEVM` is Sei's canonical guard against EVM contracts recursing into the EVM through a CosmWasm hop (EVM → wasmd precompile `execute`/`instantiate` → CW contract → `MsgInternalEVMCall`/`MsgInternalEVMDelegateCall` → back into EVM). It rejects the pattern unless the current EVM entry came in through the wasmd precompile itself: [3](#0-2) 

The wasmd precompile's dispatcher deliberately allows the `query` method to run regardless of `ctx.IsEVM()`, i.e., a CosmWasm `query()` call is reachable from an EVM context: [4](#0-3) 

Inside a CosmWasm smart query, a contract can invoke the `evm_query_static_call` custom query (or any of the ERC20/721/1155 "read" bindings, all of which funnel into `StaticCallEVM`): [5](#0-4) [6](#0-5) 

`StaticCallEVM` builds a brand-new EVM instance and issues an independent `StaticCall` — but, unlike `CallEVM`, it never checks `ctx.IsEVM()` / `ctx.EVMEntryViaWasmdPrecompile()` before doing so, and each invocation pulls a fresh gas budget from `k.getEvmGasLimitFromCtx(ctx)` rather than being metered against the calling (outer) EVM's remaining gas: [7](#0-6) 

This makes an EVM→CW→EVM chain fully reachable through the "read" path that the "write" path (`CallEVM`) explicitly forbids: an EVM contract calls the wasmd precompile's `query` method, which invokes a CosmWasm contract, which issues `evm_query_static_call` (or an ERC-pointer query binding) back into `StaticCallEVM`, entering a second, independently-gas-metered EVM. Because a CosmWasm contract's query handler itself can be invoked recursively (a CW contract can query another CW contract, which can again call `StaticCallEVM`), and each `StaticCallEVM` hop mints its own fresh EVM gas limit from context rather than deducting from a shared budget, an attacker-controlled EVM contract + CosmWasm contract pair can chain many such nested static calls within a single transaction, each getting its own full EVM gas allotment on top of the metering already paid for by the outer transaction's gas limit.

### Impact Explanation
This does not enable fund theft directly (the nested execution is read-only), but it breaks the gas-accounting invariant that a single transaction's declared gas limit bounds total EVM computation. Because every `StaticCallEVM` hop reachable through this unguarded CW↔EVM recursion re-derives its gas budget from `k.getEvmGasLimitFromCtx(ctx)` instead of being deducted from the parent EVM call's remaining gas, a moderately deep chain of CW query hops (each re-entering the EVM) can multiply the actual computation performed well beyond what the transaction's gas limit and fee should have purchased. This is a compute-amplification / resource-exhaustion vector: it can be used to make a single, cheaply-metered transaction consume disproportionate validator CPU time during `DeliverTx`, directly threatening the "block delay beyond 2.5 seconds" impact bar, and in the worst case could be tuned to exhaust node resources during block processing (in-scope: EndBlock/DeliverTx path reachable from a public transaction, not p2p/consensus-message related).

### Likelihood Explanation
Reachability requires no special privilege: any address can deploy an EVM contract that calls the wasmd precompile's `query()` method and a CosmWasm contract that recursively issues `evm_query_static_call`/ERC pointer-query bindings, then submit a normal transaction. All of the pieces used (`wasmd.query`, CW `SmartQuery`, `evm_query_static_call`, ERC20/721/1155 pointer query bindings) are documented, user-reachable public interfaces with no wasm-gating beyond "is wasm enabled," which the repo's own test README notes is planned but not yet fully covered for CW-gated flows.

### Recommendation
Apply the same EVM re-entrancy guard used in `CallEVM` to `StaticCallEVM`: reject (or, at minimum, meter against the caller's remaining EVM gas rather than a freshly-derived context gas limit) any `StaticCallEVM` invocation where `ctx.IsEVM()` is true and the entry did not originate via the wasmd precompile (mirroring `if ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile() { return error }` from `CallEVM`). Additionally, thread the parent EVM's remaining gas (or the outer transaction's overall gas budget) through nested `StaticCallEVM` invocations instead of calling `k.getEvmGasLimitFromCtx(ctx)` fresh on each hop, so recursive CW↔EVM query chains cannot multiply metered computation.

### Proof of Concept
1. Deploy CosmWasm contract `A` whose `query` handler issues `evm_query_static_call` (via `x/evm/client/wasm/bindings`) targeting an EVM contract, or simply an ERC20/721/1155 "read" binding (`HandleERC20TokenInfo`, etc.), which internally recurses into `StaticCallEVM`.
2. Deploy EVM contract `B` that calls the wasmd precompile's `query(address, req)` method against contract `A`.
3. Have contract `A`'s query handler itself call another CosmWasm contract's `SmartQuery`, which again issues `evm_query_static_call`, chaining N levels deep.
4. Submit an EVM transaction from any unprivileged account calling `B`. Each level of the EVM→CW→EVM chain re-enters `StaticCallEVM`, and because [8](#0-7)  derives `evmGasLimit` fresh from context on every call rather than deducting from a bounded outer budget, the total EVM computation performed by the single transaction scales with N independently of the transaction's declared gas limit, unlike the equivalent write path which `CallEVM` blocks outright at [9](#0-8) .

Note: I was unable to fully trace `getEvmGasLimitFromCtx`'s exact source (only located it via grep in `giga/deps/xevm/keeper/params.go`, not inspected due to the final-iteration limit) to confirm the precise per-call gas derivation formula; this should be verified in a live Devin session before treating the gas-amplification magnitude as fully proven.

	// when entered from an ABCI query or historical RPC context.

		return nil, err

	})
}

func (k *Keeper) callEVM(ctx sdk.Context, from common.Address, to *common.Address, val *sdk.Int, data []byte, f EVMCallFunc) ([]byte, error) {
	evmGasLimit := k.getEvmGasLimitFromCtx(ctx)
	value := utils.Big0
	if val != nil {
		value = val.BigInt()
	}
	ret, leftoverGas, err := f(from, to, data, evmGasLimit, value)
	k.consumeEvmGas(ctx, evmGasLimit-leftoverGas)
	if err != nil {
		return nil, err
	}
	return ret, nil
