### Title
Off-chain-facing `v0-1-data.clar` bypasses Pyth staleness/monotonic checks and returns stale-price health verdicts - (File: `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
`get-asset-price` in `mainnet/contracts/utility/v0-1-data.clar` fetches Pyth prices by calling the raw `get-price` read-only function on `pyth-storage-v4` directly, instead of going through `pyth-oracle-v4::get-price` (which forwards to `read-price-with-staleness-check`) and instead of Market's own `price-resolve` staleness/monotonicity/confidence gate. This is the exact "improper price validation → stale price used" bug class from the Compound Connector report, reproduced in Zest's own read-utility contract.

### Finding Description
`v0-1-data.clar::get-pyth-price` does:
```
(contract-call? 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4 get-price feed-id)
``` [1](#0-0) 

`pyth-storage-v4::get-price` is a bare map read with **no staleness enforcement**:
```
(define-read-only (get-price (price-identifier (buff 32)))
	(let ((entry (unwrap! (map-get? prices price-identifier) ERR_PRICE_FEED_NOT_FOUND)))
		(ok entry)))
``` [2](#0-1) 

Staleness is only enforced in the sibling function `read-price-with-staleness-check`, which `pyth-oracle-v4::get-price` calls:
```
(define-read-only (read-price-with-staleness-check (price-identifier (buff 32)))
	(let (... (stale-price-threshold (contract-call? .pyth-governance-v3 get-stale-price-threshold)) ...)
		(asserts! (>= (get publish-time entry) (+ (- latest-stacks-timestamp stale-price-threshold) STACKS_BLOCK_TIME)) ERR_STALE_PRICE)
		(ok entry)))
``` [3](#0-2) [4](#0-3) 

By contrast, the market's own `price-resolve` path (used for actual borrow/withdraw/liquidate accounting) calls `pyth-oracle-v4` (the staleness-checked entry point) and additionally applies its own confidence check, monotonic per-feed timestamp tracking (`last-update` map), and `max-staleness` gate:
```
(define-private (call-pyth (ident (buff 32)))
  (let ((res (unwrap! (contract-call? 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-oracle-v4 get-price ident) ERR-ORACLE-PYTH)))
    (ok res)))
...
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness)) ERR-ORACLE-INVARIANT)
``` [5](#0-4) [6](#0-5) 

`v0-1-data.clar` reuses this raw price in `get-asset-price`, which feeds `sum-collateral-usd` / `sum-debt-usd` and the `is-liquidatable` verdict returned by `get-user-position`:
```
(define-private (get-asset-price (aid uint))
  (if (is-eq aid STX) (default-to u0 (get-pyth-price PYTH-STX)) ...
``` [7](#0-6) 
```
is-liquidatable: (>= current-ltv ltv-liq-partial)
``` [8](#0-7) 

None of this path checks Zest's own `max-staleness`/monotonic timestamp invariant, and it also skips the confidence-interval check (`check-confidence`) that Market applies to every Pyth read.

### Impact Explanation
`v0-1-data.clar` is explicitly a "read-only utility contract" providing "optimized read-only functions to query protocol state" for dashboards/liquidator bots, and no state-changing on-chain function in `mainnet/**` was found calling into `v0-1-data.clar` — the actual custody-affecting logic (borrow, withdraw, liquidate) in `v0-4-market.clar` uses its own properly-gated `price-resolve`. This limits the practical blast radius: this contract cannot itself misprice a loan or unlock funds on-chain, because real settlement always re-derives price via Market's gated `price-resolve`.

However, this utility is the documented interface intended for third parties (liquidators, front-ends) to determine `is-liquidatable`/health-factor. A stale/frozen Pyth price (feed halted, price stuck) would make `get-user-position` return an incorrect (stale) `is-liquidatable`/`health-factor` value indefinitely, with no error and no staleness signal, silently misleading anyone relying on it to trigger liquidations — this can cause **temporary freezing of funds** in the practical sense that legitimately liquidatable/undercollateralized positions are not flagged and thus not liquidated in time, while borrowers relying on the same data to avoid liquidation could also be given false assurance. Because the Market's real enforcement path is separately protected, I cannot substantiate a Critical/direct-theft or insolvency claim purely from this contract; the concretely provable impact is limited to serving stale/wrong pricing data from a protocol-provided read interface, which sits at the boundary of the in-scope "temporary freezing of funds" category, contingent on downstream consumers (liquidator bots) trusting this endpoint over Market's own state.

### Likelihood Explanation
High likelihood of occurrence given normal Pyth feed staleness (feed not updated within governance's `stale-price-threshold`) — no attacker action is required; the bug manifests automatically whenever the underlying Pyth price in storage goes stale, since `get-price` unconditionally returns the last stored value regardless of age.

### Recommendation
Change `get-pyth-price` in `v0-1-data.clar` to call `pyth-oracle-v4::get-price` (or otherwise `pyth-storage-v4::read-price-with-staleness-check`) instead of the unchecked `pyth-storage-v4::get-price`, and mirror Market's `oracle-timestamp-fresh`/confidence checks so this reporting utility cannot silently diverge from the protocol's own price-validity guarantees.

### Proof of Concept
1. Pyth stops publishing updates for the STX/USD feed for longer than the configured `stale-price-threshold` in `pyth-governance-v3`.
2. Calling `v0-1-data.clar::get-user-position` (or `get-asset-apys`/`get-all-reserves`) still returns a computed `health-factor`/`is-liquidatable` using the last stored (now stale) price via `get-pyth-price` → `pyth-storage-v4::get-price`, with no error and no indication of staleness.
3. Meanwhile, any attempt to actually borrow/withdraw/liquidate through `v0-4-market.clar` would correctly revert with `ERR-ORACLE-INVARIANT` because its `price-resolve` calls `pyth-oracle-v4::get-price` → `read-price-with-staleness-check`, which reverts on stale data.
4. Result: external consumers of the read-only reporting interface (liquidator bots, dashboards) observe an incorrect/frozen health snapshot that never signals staleness, diverging from the protocol's actual, correctly-gated on-chain state.
