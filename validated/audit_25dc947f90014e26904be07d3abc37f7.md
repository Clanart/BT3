### Title
Unbounded attacker-controlled median fee causes multisig transactions to overpay miners - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
`Bitcoin::median_fee` derives the transaction fee rate directly from the median fee rate of non-coinbase transactions in the selected block, without applying an upper bound. An unprivileged Bitcoin user can include a transaction paying an extreme fee in that block and cause Serai’s next multisig transaction to consume an equally extreme amount as miner fees.

### Finding Description
`make_signable_transaction` obtains `fee.0` from `median_fee` and passes it into `BSignableTransaction::new`. `median_fee` iterates over `block.txdata[1 ..]`, computes each transaction’s fee rate as `(sum(inputs) - sum(outputs)) / tx.vsize()`, sorts the results, and returns the middle value, clamped only to a minimum of `1` sat/vbyte. No maximum, sanity cap, or outlier filtering is applied.

The wallet then treats the resulting value as authoritative:

- `SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes`.
- If change exists, it calculates `fee_with_change = fee_per_vbyte * vbytes_with_change` and subtracts that amount from the change output.
- `prepare_send` amortizes the resulting `tx_fee` across scheduled payments before creating the signable transaction.
- The final signer commits to the resulting Bitcoin transaction through `taproot_key_spend_signature_hash` with `Prevouts::All`.

Therefore, the attacker does not need access to Serai keys, validator inputs, or internal state. They only need their transaction to be included in the block sampled by `median_fee`.

### Impact Explanation
A sufficiently large fee-rate value causes Serai to sign a transaction whose miner fee is much larger than economically necessary or intended. Depending on the available inputs and scheduled payments, the excess is either deducted from payment amounts during fee amortization or taken from change in `SignableTransaction::new`.

This is a concrete loss-of-funds condition: the signed transaction commits to output values that leave the excessive input/output difference as a miner fee. Since the signature commits to all outputs and prevouts, the fee cannot be reduced after signing without restarting signing with a new transaction.

For a single-payment transaction, the effect is bounded by the payment amount after amortization and dust filtering. For transactions with change or larger input sets, the excessive fee can consume substantially more value, potentially up to `sum(inputs) - sum(payments)` when the resulting change is at least the wallet dust threshold, or the entire remainder when no usable change output is produced.

### Likelihood Explanation
An attacker must have a transaction included in the exact block sampled by `make_signable_transaction`, and the manipulation is most reliable when the attacker controls the median position. If the attacker’s transaction is the only non-coinbase transaction in the sampled block, its fee rate directly becomes the returned median.

Executing the attack costs the attacker the inflated fee on their own transaction, so it is not free. However, the cost can be rational if the Serai multisig is expected to create a high-value transaction, if the attacker profits from delayed or reduced payouts, or if the attacker can arrange inclusion during low-activity blocks. No validator compromise, malformed cryptographic message, leaked secret, or invalid chain data is required.

### Recommendation
Do not use an unbounded median of public transaction fees as the sole fee-rate input.

At minimum:

1. Clamp `median_fee` to a protocol-defined maximum sat/vbyte.
2. Prefer a bounded fee estimator backed by multiple recent blocks rather than a single block’s transaction set.
3. Reject or fall back when the sampled block has too few non-coinbase transactions.
4. Add an explicit maximum total fee or maximum fee-to-payment ratio in `prepare_send`, returning `None` instead of producing an economically unreasonable transaction.
5. Include the OP_RETURN output in `calculate_weight_vbytes` when `data` is present, since the current size estimate omits it and therefore misprices data-bearing transactions.

### Proof of Concept
The reachable path is:

```text
public Bitcoin transaction with inflated fee
        |
        v
Bitcoin::median_fee(block)
        |
        v
Bitcoin::make_signable_transaction(..., fee.0)
        |
        v
BSignableTransaction::new(..., fee_per_vbyte = fee.0)
        |
        v
needed_fee / fee_with_change and signed sighash
```

Relevant code:

`processor/src/networks/bitcoin.rs` computes the unbounded public median:

```rust
for tx in &block.txdata[1 ..] {
  // ...
  fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
}
fees.sort();
let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);
Ok(Fee(fee.max(1)))
```

`processor/src/networks/bitcoin.rs` uses it directly for transaction construction:

```rust
let fee = self.median_fee(&block_for_fee).await?;
BSignableTransaction::new(
  inputs.iter().map(|input| input.output.clone()).collect(),
  &payments,
  change.clone().map(Into::into),
  None,
  fee.0,
)
```

`networks/bitcoin/src/wallet/send.rs` converts the supplied rate into the actual residual fee:

```rust
let mut needed_fee = fee_per_vbyte * vbytes;
// ...
let fee_with_change = fee_per_vbyte * vbytes_with_change;
let value = input_sat - (payment_sat + fee_with_change);
```

A concrete scenario is:

- Attacker submits the sole non-coinbase transaction in the sampled block with a fee rate of `1_000_000` sat/vbyte.
- `median_fee` returns `Fee(1_000_000)` because it applies only `max(1)`.
- `make_signable_transaction` passes `1_000_000` as `fee_per_vbyte`.
- `SignableTransaction::new` charges approximately `1_000_000 * transaction_vbytes` as the fee.
- The signer commits to the resulting transaction with `Prevouts::All`, making the excessive input/output difference a valid miner fee.
