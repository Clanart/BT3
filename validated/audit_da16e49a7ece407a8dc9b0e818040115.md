### Title
PedPoP share-deserialization failure returns blame proof revealing an honest party's ECDH key before the PoP is verified - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` (which publicly reveals the ECDH shared key for a message) on the secret-share deserialization error path without ever verifying the message's proof-of-possession. The PoP was added specifically to prevent Eve from copying Alice's per-message encryption key to trick Bob into publishing a blame proof that decrypts Alice's message; the early `?` on `C::F::from_repr` at `crypto/dkg/pedpop/src/lib.rs:480-482` bypasses `batch.verify_with_vartime_blame()` entirely, re-enabling exactly that attack.

### Finding Description
`EncryptedMessage` carries `key`, `pop` (a `SchnorrSignature` PoP), and the ciphertext. The code comments explain why the PoP exists: if Eve copies Alice's key `X`, Bob's blame would reveal `bX`, decrypting Alice's message to Bob (`crypto/dkg/pedpop/src/encryption.rs:84-91`).

In `Encryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:469-501`), the PoP is only *queued* into a `BatchVerifier` (`batch_id` = `BatchId::Decryption(l)`); decryption and generation of the blame `EncryptionKeyProof` (`key = ecdh(enc_key, msg.key)` plus a DLEq) happen unconditionally and are returned immediately.

In `calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-499`):

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

If the decrypted share bytes fail `from_repr` (which attacker-chosen garbage does with overwhelming probability), the function returns early with `blame: Some(...)`. `batch.verify_with_vartime_blame()` at line 493 is never reached, so the queued `BatchId::Decryption(l)` PoP check — the mechanism that would map a bad PoP to `blame: None` — is silently skipped. The `Some(blame)` is then treated as a publishable blame proof.

### Impact Explanation
Any unprivileged DKG participant (or anyone able to feed an `EncryptedMessage` to a victim's `calculate_share`) can:

1. Observe honest Alice's `EncryptedMessage` to Bob and copy its `key` (`X`).
2. Send Bob a forged `EncryptedMessage` `{ key: X, pop: <invalid>, msg: <garbage> }`.
3. Bob's `calculate_share` decrypts with `bX`, gets garbage, `from_repr` fails, and returns `InvalidShare { blame: Some(EncryptionKeyProof { key: bX, dleq }) }` — a valid, publishable proof revealing `bX`.
4. Once Bob publishes the blame (the protocol's intended response), anyone computes `cipher(context, bX)` and decrypts *Alice's genuine ciphertext*, exposing the secret share Alice sent to Bob.

This is a confidentiality leak of DKG secret-share material reachable purely from attacker-supplied bytes to `EncryptedMessage::read` / `calculate_share`, matching the external report's signature-computation secret-leak class.

### Likelihood Explanation
Requires an attacker who can observe a ciphertext in transit and inject a message to the recipient — standard for the DKG's threat model (messages are explicitly not assumed authenticated beyond the PoP). The attack always succeeds: an invalid PoP is never checked on this path, and garbage ciphertext fails `from_repr` with probability ≈ 1. Cost is one forged message per leaked share.

### Recommendation
Do not return the blame proof before the PoP is verified. Options:

- Restructure `calculate_share` so the `from_repr` failure still runs `batch.verify_with_vartime_blame()` first, mapping a `BatchId::Decryption(l)` failure to `blame: None` and only attaching `Some(blame)` when the PoP verifies.
- Alternatively, verify the PoP synchronously (non-batched) inside `decrypt` before producing `EncryptionKeyProof`, or have `decrypt` return the proof only after PoP confirmation.

### Proof of Concept
1. Run a PedPoP DKG with n ≥ 2. Alice (`l = 1`) produces `EncryptedMessage` to Bob (`i = 2`) with per-message key `X` and valid PoP.
2. Eve copies `X`, builds `EncryptedMessage { key: X, pop: <any bytes/invalid SchnorrSignature>, msg: <garbage non-canonical scalar bytes> }`, sends to Bob.
3. Bob calls `KeyMachine::calculate_share(rng, shares)` including Eve's forged message.
4. `decrypt` queues the invalid PoP into the batch, decrypts garbage, and produces `EncryptionKeyProof { key: bX, dleq }`.
5. `from_repr` fails → `calculate_share` returns `Err(InvalidShare { participant: Eve, blame: Some(proof) })` — `batch.verify_with_vartime_blame()` is never executed, so the invalid PoP goes undetected.
6. Bob publishes `proof`. Anyone verifies the DLEq against `[G, X]` / `[B_enc, bX]` (`decrypt_with_proof`, `encryption.rs:366-397`), derives `cipher(context, bX)`, and decrypts Alice's original ciphertext, recovering her secret share to Bob.
