## Bug-class reduction

The Plaza bug's core primitive: an unprivileged caller can permissionlessly push a shared, unbounded-looking accumulator (`totalSellReserveAmount`) with a single call that costs them nothing, and that accumulator directly gates a state transition another party depends on — causing legitimate value to be destroyed/blocked with no real cost to the attacker.

## Title
Permissionless cross-app bandwidth sponsorship lets an attacker force-evict a victim's paid, unconsumed subscription via FIFO-cap eviction - (File: `modules/pallets/bandwidth/src/lib.rs`, `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` is a fully public entrypoint that lets *anyone* credit bandwidth to *any* `(chain, app)` pair — this cross-chain "sponsorship" is an intentional feature. Each purchase appends to a FIFO list capped at `MAX_SUBSCRIPTIONS = 1024`; when the cap is hit, `push_subscription` evicts the list head unconditionally, regardless of how many bytes remain unconsumed on that entry. An attacker can therefore repeatedly purchase the cheapest tier against the exact same `(chain, app)` key a victim already funded, pushing the FIFO length past 1024 and evicting the victim's still-largely-unused (and possibly much larger/more expensive) subscription before it is ever drained by the gate.

### Finding Description
- `purchase()` takes attacker-controlled `app` and `chain` parameters with no ownership check tying the payer to the app being credited: [1](#0-0) 
- The pallet's `on_accept` only checks that the *sender* is the registered `BandwidthManager` for the source chain — it never restricts which `(app_chain, app)` a purchase is allowed to credit: [2](#0-1) 
- `push_subscription` evicts `list[0]` (the oldest entry) purely because the list is at capacity, with no check on `remaining_bytes` of the evicted entry: [3](#0-2) 
- The cap is a fixed, chain-wide-per-app constant of 1024, independent of purchase size or price: [4](#0-3) 
- The gate drains strictly from the FIFO head in insertion order, so an evicted-but-unconsumed entry's bytes are simply gone — the "no mutation on insufficient" safety property only covers drains, not evictions: [5](#0-4) 

This is the same broken invariant as the external report: a shared accounting structure (`totalSellReserveAmount` / the FIFO subscription list) can be inflated by an unprivileged, unrelated party through a normal, valid call, and that inflation directly destroys value/blocks progress for someone else, with the guard (`poolSaleLimit` check / `MAX_SUBSCRIPTIONS` cap) providing no protection against exactly this abuse.

### Impact Explanation
A victim who legitimately pays for a large tier (e.g. the $1000/8MB plan) can have that entire unconsumed allowance evicted and permanently lost by an attacker who targets the same `(chain, app)` key with a sequence of cheap `TierOne` purchases. This is a direct loss of funds for the victim (paid-for bandwidth is destroyed before use) and can be repeated against every `(chain, app)` pair on the network, since sponsorship is deliberately open to any payer/chain combination — no relayer, prover, admin, or governance compromise is required, only the public `purchase()` entrypoint.

### Likelihood Explanation
The attack requires no privileged role and no proof forgery — just calling `purchase()` (a plain public Solidity function) enough times against the target `(chain, app)` key to push the FIFO list past its 1024-entry cap. The cost is bounded by `1024 × cheapest tier price`, which can be far less than the value of the victim's subscription being destroyed (e.g., evicting an $1000/8MB purchase by spending on ~1024 minimal $50/100KB purchases, or fewer if the queue already has other entries). This asymmetry — cheap, permissionless griefing destroying disproportionately larger locked value — mirrors the "extremely cheap attack, attacker loses nothing meaningful" profile of the original finding.

### Recommendation
- Restrict who may credit a given `(app_chain, app)` bucket (e.g., require the purchasing manager/source chain to be on an app-specific allowlist, or require the `payer` on the source chain to match a registered relationship with the app), rather than allowing arbitrary permissionless sponsorship of any target.
- When evicting on a full FIFO list, prefer evicting entries with the least remaining value (e.g., soonest-to-expire or smallest `remaining_bytes`) instead of unconditionally evicting the head, or reject/queue the new purchase instead of silently destroying an existing paid entry.
- Consider raising `MAX_SUBSCRIPTIONS` or making it a function of total bytes committed rather than a fixed entry count, and emit a pre-emptive warning/event before an entry with significant `remaining_bytes` is evicted.

### Proof of Concept
1. Victim calls `BandwidthManager.purchase(app=X, tier=TierFour, months=1, chain=Y)`, crediting `(Y, X)` with 8MB of bandwidth via `pallet-bandwidth`'s `on_accept` → `push_subscription`.
2. Attacker calls `BandwidthManager.purchase(app=X, tier=TierOne, months=1, chain=Y)` repeatedly (no relationship to X or Y required) until the `(Y, X)` FIFO list length reaches `MAX_SUBSCRIPTIONS` (1024) and one more push occurs.
3. `push_subscription` (`modules/pallets/bandwidth/src/lib.rs:404-425`) evicts `list[0]` — the victim's 8MB subscription, regardless of `remaining_bytes` — and emits `SubscriptionEvicted` with the lost bytes.
4. The victim's app can no longer draw on the paid-for allowance; the attacker has destroyed the victim's purchase by spending only on cheap `TierOne` purchases.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
