### Title
Tokenfactory denom-admin can permanently freeze existing holders' funds by narrowing a denom's `AllowList` via `MsgUpdateDenom` - ([File: sei-cosmos/x/bank/keeper/msg_server.go])

### Summary
The bank module's `Send`/`MultiSend` message handlers gate transfers of tokenfactory (`factory/...`) denoms through `IsInDenomAllowList`, which checks the *current* on-chain allow list for that denom. A tokenfactory denom's `admin` can call `MsgUpdateDenom` at any time to replace the allow list, and this new (potentially narrower) list is enforced immediately against **all** existing holders, including those who acquired their balance while unrestricted or while allow-listed. This is analogous to the Tokemak `perWalletLimit` issue: a mutable, admin-controlled gate is checked against present holdings/would-be recipients rather than being scoped only to new inflows, so a later restriction can strand funds already held by users who are excluded from the new list.

### Finding Description
`MsgSend` and `MsgMultiSend` in [1](#0-0)  require both the sender and the recipient to be present in the denom's allow list (when one is set) before allowing a transfer of a `factory/` denom, via `IsInDenomAllowList`: [2](#0-1) 

The allow list is fully mutable post-creation. `x/tokenfactory`'s `MsgUpdateDenom` handler lets the denom's admin overwrite the allow list at will, with no restriction preventing removal of addresses that already hold a balance of the denom: [3](#0-2) 

Because `IsInDenomAllowList` is evaluated against the *current* balance-holder's address for every subsequent `Send`/`MultiSend`, once the admin narrows the list to exclude an address, that address can no longer send (as sender) or receive (as recipient, if sending to itself/others) that denom, even though it already legitimately holds a balance. There is no distinction in the check between "new inflow" and "existing balance already held" — the same mechanism flagged in the Tokemak report (`_beforeTokenTransfer` checking `balanceOf` against a mutable limit for every operation, not just increases). The equivalent gap here is the identical `SubKeeper`/`giga` implementation of `IsInDenomAllowList` used by the Giga EVM-parallel bank keeper: [4](#0-3) .

### Impact Explanation
Any holder of a tokenfactory denom who is dropped from that denom's allow list becomes permanently unable to move their existing balance out via `MsgSend`/`MsgMultiSend` — the funds are frozen at the protocol layer. Because tokenfactory denom creation/administration is reachable by any unprivileged account (any account can create a tokenfactory denom and become its admin, then distribute the token and later restrict the allow list against holders), this meets the "permanent freezing of funds" impact bar even without any governance or validator compromise. Denom admins already have significant control (mint/burn/allow-list) by design, but the specific bug here is that removing an address from the allow list retroactively blocks movement of *already-held* balances rather than only gating new transfers into that address, which is a foreseeable griefing/self-lock vector consistent with the audit finding's root cause.

### Likelihood Explanation
Likelihood is moderate: it requires the denom admin (who could be any account that created the denom) to update the allow list to exclude a prior holder — an ordinary, permitted `MsgUpdateDenom` call, not requiring any privileged or governance access. This can happen unintentionally (an admin narrowing a list without realizing existing holders will be locked out) or intentionally (a malicious/compromised denom admin freezing user funds), matching the exact scenario described in the referenced report.

### Recommendation
When enforcing `IsInDenomAllowList` in `MsgSend`/`MsgMultiSend` (and the Giga equivalent), only apply the allow-list check to the *recipient* accumulating new balance from outside the current holder set, or exempt "send/withdraw" operations by an address that already held the denom balance prior to the list update — mirroring the audit's recommendation to only check the limit on inflow (`mint`), not on outflow (`withdraw`/`transfer`) for balances already held. At minimum, document that admins must not remove addresses that currently hold balances, or add a check in `MsgUpdateDenom` that prevents removing an address with a nonzero balance from the allow list.

### Proof of Concept
1. Attacker/admin account `A` creates tokenfactory denom `factory/A/token` via `MsgCreateDenom` (no initial allow list, or a permissive one).
2. `A` mints and sends tokens to user `B` via `MsgSend`, which succeeds since there is no restrictive allow list yet.
3. `A` calls `MsgUpdateDenom` with a new `AllowList` that does not include `B`, per [5](#0-4) .
4. `B` attempts `MsgSend` to transfer their existing `factory/A/token` balance to any address (including back to `A`, or to a wallet under their own control) — the handler calls `IsInDenomAllowList(ctx, B, ...)` and returns `false`, so the call fails with `"%s is not allowed to send funds"` as seen in [6](#0-5) .
5. `B`'s balance of `factory/A/token` is now permanently frozen — no `MsgSend`/`MsgMultiSend` from `B` for that denom can ever succeed unless `A` chooses to re-add `B` to the allow list.

		return types.AllowList{}

	k.cdc.MustUnmarshal(bz, &allowList)

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
