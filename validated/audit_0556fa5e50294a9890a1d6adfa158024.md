### Title
Spoofed `WWW-Authenticate` realm header from a malicious git remote/proxy triggers an unwarranted "Enterprise GitHub sign-in" prompt for an attacker-controlled host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` in the trampoline credential helper classifies an unknown Git remote host as `'enterprise'` (i.e. "this is a GitHub Enterprise Server") purely based on a `WWW-Authenticate` header value that the remote server itself supplied, without any cryptographic or otherwise verified indication that the host is actually a GitHub product. [1](#0-0) 

### Finding Description
This is the closest analog to the Olympus bug: a value (here, the *trust classification of an endpoint*) is derived from attacker-influenced input and then used to drive a security-relevant decision, without any independent re-validation ("regeneration") — mirroring how `reserveFactor` changed the market's true capacity threshold but the code kept using stale/unchecked state to decide when to act.

When Git authenticates against a remote, it forwards any `WWW-Authenticate` headers returned by the server to Desktop's credential helper via the `cred` map. `getEndpointKind` explicitly treats this as a trusted "happy path" to avoid a real network check: [2](#0-1) 

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
```

A hostile git remote, or a MITM/malicious proxy sitting between Desktop and any remote (an attacker-controlled server that the user cloned/fetched/pushed to, or a git host reachable via a spoofable proxy), can simply respond to the auth challenge with a header such as `WWW-Authenticate: Basic realm="GitHub"`. Nothing about this string is signed or otherwise verifiable — it is fully attacker-controlled data forwarded straight from the wire into a trust decision.

This classification then feeds directly into `getCredential`: [3](#0-2) 

Because the attacker's host is not yet a known account endpoint (`!accounts.some(a => a.endpoint === apiEndpoint)`), and `endpointKind !== 'generic'`, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which is implemented in `trampoline-ui-helper.ts`: [4](#0-3) 

Since `hostname !== 'github.com'` (it's the attacker's own domain), Desktop calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` **using the attacker's origin as the GitHub Enterprise Server endpoint**, then shows the standard GitHub Enterprise sign-in dialog to the user, labeled with the attacker's hostname baked into the flow.

### Impact Explanation
This is not a benign UX glitch — it manufactures unauthorized OAuth/account-binding flow: the user is shown a legitimate-looking "Sign in to GitHub Enterprise" dialog whose target endpoint is entirely attacker-controlled. If the user completes the flow (PAT entry or OAuth device/browser flow against that endpoint), their GitHub personal access token or OAuth code/credentials get sent to the attacker-controlled server, and/or a new `Account` gets bound to that server as if it were a legitimate GHE instance. That satisfies the "unauthorized OAuth or account binding" / "credential/token exfiltration" impact bucket: the attacker (who fully controls a remote/proxy the victim is interacting with) can turn a routine `git fetch`/`push` 401 response into a credential-phishing primitive embedded inside Desktop's own trusted UI.

### Likelihood Explanation
The trigger requires nothing beyond what's explicitly in-scope: the attacker must control a git remote or a proxy sitting in front of one that the victim has added (e.g., a malicious/compromised self-hosted git server, or a MITM on an unauthenticated/downgraded connection). No local access, no prior credential leak, and no unnatural user action beyond a normal `fetch`/`push`/`clone` against a repository followed by responding to the resulting sign-in prompt (the same interaction users are trained to expect for legitimate GHE repos). The check is explicitly designed as a shortcut/"happy path" precisely to *avoid* a verifying network call, which is what removes the safety net that would otherwise catch a spoofed realm value.

### Recommendation
Do not trust the `WWW-Authenticate: realm="GitHub"` header as sufficient proof of a GitHub/GHE endpoint. At minimum, require the network-based `isGitHubHost(endpoint)` check (already present later in the function) to run before ever offering the "GitHub Enterprise sign-in" UI when the endpoint is not already a known account, or otherwise surface the target hostname clearly and require explicit user confirmation that includes the raw hostname, treating a mismatch between the "GitHub" self-declared realm and independent verification as untrusted/`generic`.

### Proof of Concept
1. Attacker stands up a git-over-HTTPS server (or a MITM proxy in front of a git server the victim uses) that always responds to unauthenticated requests with `401` plus header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this remote in Desktop (e.g. `git remote add evil https://attacker.example/org/repo.git`) and performs a `fetch`/`push`.
3. Git invokes the trampoline credential helper; `getCredential` → `getEndpointKind` scans the forwarded `wwwauth[...]` header, matches `realm="GitHub"`, and returns `'enterprise'` without any real verification. [5](#0-4) 
4. Since `attacker.example` is not a known account endpoint, `ui.promptForGitHubSignIn('https://attacker.example')` is invoked. [6](#0-5) 
5. Desktop shows a "Sign in to GitHub Enterprise" dialog bound to `https://attacker.example` as the sign-in endpoint; any credentials/PAT/OAuth exchange the user completes goes to the attacker's server.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
