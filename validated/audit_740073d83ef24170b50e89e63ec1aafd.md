### Title
Merge/rebase/cherry-pick operations act on branch name instead of the reviewed commit SHA, letting a stale or attacker-updated branch tip be silently merged - (File: `app/src/lib/git/merge.ts`)

### Summary
GitHub Desktop lets a user preview what a merge (or rebase/cherry-pick) will do — commit count, "ahead/behind" numbers, and mergeability — based on a `Branch` object captured at a point in time, whose identity is really `branch.tip.sha` [1](#0-0) . When the user actually confirms the merge, however, Desktop invokes `git merge <branch-name>` using only the branch **name**, never re-validating that the name still resolves to the previously-reviewed `tip.sha` [2](#0-1) . Because Desktop also fetches remotes automatically in the background at a fixed interval [3](#0-2) , the remote-tracking branch's tip can silently change between the moment the user reviewed the commits/merge-preview and the moment they click "Merge" — with no re-confirmation step, exactly mirroring the Canto Tray `buy()` bug where the precomputed value (tiles/hash) that the user reviewed no longer matches what is actually consumed at execution time.

### Finding Description
The invariant the UI implies to the user is: "the commits you reviewed in the merge/rebase/cherry-pick dialog are the commits that will be applied." That invariant is enforced only up to the point where the *preview* is displayed — `MergeChooseBranchDialog.updateStatus` explicitly guards against showing a stale preview by comparing `this.state.selectedBranch?.tip.sha !== branch.tip.sha` [4](#0-3) . But once the user clicks "Merge", `start()` passes the previously-selected `Branch` object straight to `dispatcher.mergeBranch` [5](#0-4) , which eventually reaches `GitStore.merge()` and then `merge(repository, branch.name, ...)` [6](#0-5) [2](#0-1) . At no point is `branch.tip.sha` passed to git or checked against the current ref value before the merge executes — the operation is performed purely by ref/branch name, so `git merge` will merge whatever commit that name currently points to at execution time, regardless of what was shown in the "This will merge N commits from X into Y" preview.

Because `BackgroundFetcher` runs automatically for the selected repository (default interval up to one hour, with a random skew) and silently updates remote-tracking refs without any user interaction [7](#0-6) , an attacker who controls the head of a branch/fork the user is comparing against (e.g. a PR from an external contributor) can push new/different commits to that ref at any time. If this happens between the user's review of the merge dialog and their click on "Merge", Desktop will silently merge the new, unreviewed commits into the user's branch — an exact structural analog of the Canto bug, where the client precomputed and displayed a value (tray tiles / merge preview) derived from a mutable, attacker-influenced chain (`lastHash` / remote branch tip), but the state-changing action (`buy()` / `git merge`) never re-validates that the precomputed value still matches current state before proceeding.

### Impact Explanation
A user reviewing a PR/branch merge in Desktop can be shown a clean, reviewed set of commits, but the code that is actually merged into their branch and later pushed can be entirely different and attacker-controlled, without any warning, revert, or confirmation. This can result in unreviewed/malicious commits (e.g. containing backdoors, secrets exfiltration code, or build-script tampering) silently becoming part of the user's branch history and potentially being pushed upstream — corrupting what the user believes they are committing/pushing, matching the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
Exploitation requires an attacker who controls (or force-pushes to) the remote branch/fork being merged, combined with normal timing where Desktop's automatic background fetch (or even a manual fetch/pull the user performs for unrelated reasons) updates the ref between review and merge confirmation — a window that commonly spans user think-time (reading the diff, writing the merge commit message, etc.). This does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the attacker can push to the branch being compared/merged, which is the normal capability of a PR author/fork owner.

### Recommendation
Before executing `git merge` (and similarly for rebase/cherry-pick "start" actions), re-resolve the target branch name to its current tip SHA and compare it to the `tip.sha` that was used to generate the displayed preview/commit list. If they differ, abort with an error/refresh prompt instead of silently merging the new state, analogous to checking `lastHash` before `buy()` in the referenced report. Alternatively, pass the previously-reviewed SHA explicitly to `merge`/`rebase` (e.g., `git merge <sha>` instead of `git merge <branch-name>`) so the operation is pinned to what the user actually reviewed.

### Proof of Concept
1. In Desktop, open the "Compare" / merge dialog against a branch/fork owned by another (potentially malicious) collaborator; Desktop computes and shows `mergeStatus`/commit count for `comparisonBranch.tip.sha` = `A` [1](#0-0) .
2. Before the user clicks "Merge", the attacker force-pushes new commits to that branch, or Desktop's `BackgroundFetcher` performs its scheduled fetch and updates the local remote-tracking ref to tip `B` [8](#0-7) .
3. The user clicks "Merge into `<currentBranch>`"; `start()` sends the stale `Branch` object (still labeled with sha `A` in the UI state) to `dispatcher.mergeBranch` → `_mergeBranch` → `gitStore.merge(sourceBranch, ...)` → `merge(repository, branch.name, ...)` [9](#0-8) [2](#0-1) .
4. `git merge <branch-name>` merges the actual current tip `B` (attacker's new commits), not the previously reviewed tip `A`, with no warning that the reviewed content differs from what was just merged.
