### Title
Unrecovered panics in OCC parallel-execution worker goroutines can crash the whole sei-chain process - ([File: giga/deps/tasks/scheduler.go])

### Summary
The IoTeX report fixes a class of bug where a goroutine spawned to do speculative/parallel work (`mint`) had no `defer/recover`, so any panic inside it (triggered by a legitimate race, not a crafted input) took down the entire process instead of just failing that unit of work. Sei's OCC (optimistic-concurrency-control) transaction scheduler in `giga/deps/tasks/scheduler.go` (and its twin `sei-cosmos/tasks/scheduler.go`) has the same architectural gap: the persistent worker goroutines that execute and validate transactions concurrently are started with **no panic recovery at all**, unlike every other goroutine-spawning helper in the codebase (`evmrpc/utils.go`'s `ParallelRunner`, `sei-tendermint/internal/libs/async/async.go`'s `Parallel`, and the app-level `makeGigaDeliverTx`/`legacyabci.DeliverTx`/`BaseApp.runTx`, all of which do wrap their goroutines/call sites in `recover()`).

### Finding Description
`ProcessAll` starts fixed pools of long-lived worker goroutines for both execution and validation via `start()`: [1](#0-0) 

Each worker simply calls `work()` pulled off a channel with **no `defer recover()`**. These closures are `s.prepareAndRunTask` (wraps `executeTask`) and the validation closure built in `validateAll`: [2](#0-1) [3](#0-2) 

`prepareAndRunTask` only defers `wg.Done()` "to prevent deadlock on panic" — it explicitly acknowledges panics can happen but only protects the wait-group bookkeeping, not the process. The scheduler's own state-machine code contains an outright unguarded `panic(...)` call reachable from the validation goroutine path (`DoValidate` → `validateTask` → `shouldRerun`): [4](#0-3) 

Note that `app.DeliverTx`/`makeGigaDeliverTx` (the actual tx-execution entry point invoked from inside `executeTask`) does have its own internal `recover()` block, matching the "block-apply path stays fatal, mint path gets recovered" split described in the IoTeX fix: [5](#0-4) 

However, that recover only shields the deliverTxFunc call itself. Everything the scheduler does *around* it inside the same worker goroutine — `prepareTask`'s multi-version store wiring (`cms.SetKVStores`, `SetGigaKVStores` type assertions), `invalidateTask`'s `mv.InvalidateWriteset/ClearReadset/ClearIterateset`, `findConflicts`'s `mv.ValidateTransactionStateWithKeys`, and `shouldRerun`'s explicit `panic("unexpected status: ...")` — runs with zero recovery. In Go, an unrecovered panic in *any* goroutine terminates the entire process immediately, independent of whatever other goroutines (including the main ABCI goroutine) are doing. This is precisely the bug class in the IoTeX report: a goroutine doing concurrent/speculative work panics on an unexpected internal invariant and brings the whole node down instead of just failing the transaction/task.

By contrast, the codebase already knows how to defend against this pattern elsewhere: [6](#0-5) [7](#0-6) [8](#0-7) 

These show the project's own established fix pattern (`defer recover()` per goroutine) that the OCC scheduler's `start()`/`executeAll`/`validateAll` workers do not follow.

### Impact Explanation
An unrecovered panic in any of the OCC scheduler's worker goroutines crashes the entire `seid` process on every validator/full node processing that block, i.e., a chain-wide halt (all nodes running the OCC/giga path panic identically on the same block and die), which meets the "validator halt" bar. This is worse than a single-node crash because OCC/parallel execution is deterministic across all nodes validating the same block, so a triggering condition reproduces network-wide simultaneously.

### Likelihood Explanation
I could not, within the scope of what I retrieved, pin down a concrete external-transaction-triggerable input that forces the scheduler's task-status state machine into the `shouldRerun`'s `panic("unexpected status: ...")` branch, nor a specific crafted payload that panics inside `prepareTask`'s store-wrapping type assertions or `multiversion.Store`'s writeset/iterateset bookkeeping outside of the `DeliverTx`-scoped recover. The IoTeX bug itself was triggered by a genuine internal race condition (block-sync commit vs. in-flight mint), not a crafted external input — the fix was defensive hardening, not a response to a directly reachable exploit. The sei-chain analog here is the same class of defensive gap (missing recover around a background/worker goroutine doing speculative concurrent work), but I do not have proof of a concrete transaction-triggerable path to reach the unguarded panic sites, only proof that the unguarded panic sites exist and are reachable in principle from concurrent execution.

### Recommendation
Wrap the worker loop in `start()` (and the `executeAll`/`validateAll` per-task closures) with `defer recover()` that logs the panic, marks the affected task as aborted/failed, and lets `wg.Done()`/channel semantics continue, mirroring the pattern already used in `evmrpc/utils.go`'s `ParallelRunner` and `sei-cosmos/store/multiversion/store.go`'s `validateIterator`. Replace the bare `panic("unexpected status: ...")` in `shouldRerun` with a recoverable error return, and add a Prometheus counter for scheduler-goroutine panics for operator visibility, matching the IoTeX hotfix approach.

### Proof of Concept
Not applicable — I could not identify or confirm a concrete external transaction/message sequence that drives the OCC scheduler into one of the unguarded panic sites (this would require internal state-machine corruption or a race condition analogous to IoTeX's, which I could not confirm is reachable from a single submitted transaction/contract call within the scope of this review). This finding documents a structural defensive gap (missing per-goroutine recover in the OCC scheduler, exact locations cited above) rather than a proven, externally-triggerable exploit chain.

// ExecuteAll executes all tasks concurrently
func (s *scheduler) executeAll(ctx sdk.Context, tasks []*deliverTxTask) error {
	if len(tasks) == 0 {
		return nil
	}
	ctx, span := s.traceSpan(ctx, "SchedulerExecuteAll", nil)
	span.SetAttributes(attribute.Bool("synchronous", s.synchronous))
	defer span.End()

	// validationWg waits for all validations to complete
	// validations happen in separate goroutines in order to wait on previous index
	wg := &sync.WaitGroup{}
	wg.Add(len(tasks))

	for _, task := range tasks {
		t := task
		s.DoExecute(func() {
			s.prepareAndRunTask(wg, ctx, t)
		})
	}

	wg.Wait()

	return nil
}

func (s *scheduler) prepareAndRunTask(wg *sync.WaitGroup, ctx sdk.Context, task *deliverTxTask) {
	defer wg.Done() // Must be deferred to prevent deadlock on panic

	eCtx, eSpan := s.traceSpan(ctx, "SchedulerExecute", task)
	defer eSpan.End()

	task.Ctx = eCtx
	s.executeTask(task)
}
