### Title
Payout tx OP_RETURN operator attribution is unauthenticated malleable data, allowing third-party attribution hijacking of a withdrawal to an arbitrary registered operator - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` places `operator_xonly_pk` into an OP_RETURN output that is not covered by the mandatory `SinglePlusAnyoneCanPay` user signature. Because that sighash flag only commits to input 0 and the matching-index output 0, any party observing the broadcast/mempool payout transaction can rebuild a variant with the same signed input/output but a different OP_RETURN naming a different registered operator, and get it confirmed instead (via opt-in RBF or race), corrupting the DB attribution consumed by `Verifier::update_finalized_payouts`.

### Finding Description
The binding claimed by the protocol is: `payout_payer_operator_xonly_pk` recorded in `withdrawals` for `citrea_idx` == the operator that actually funded `output[0]` of the confirmed payout transaction.

- `create_payout_txhandler` builds the OP_RETURN purely as `PushBytesBuf::from(operator_xonly_pk.serialize())` [1](#0-0)  with no signature or hash tying it to input 0 or output 0.
- The withdrawal's user signature is required to use `TapSighashType::SinglePlusAnyoneCanPay`, enforced at parse time [2](#0-1) , and `calculate_pubkey_spend_sighash` computes the sighash using `Prevouts::One` for this flag [3](#0-2) . Per BIP-341/342, `SIGHASH_SINGLE|ANYONECANPAY` commits only to input 0's outpoint/value/script and to output 0; it does **not** commit to output 1 (anchor) or output 2 (OP_RETURN with `operator_xonly_pk`).
- The operator sends this payout via the RBF fee-paying path (`TransactionType::Payout => FeePayingType::RBF`) [4](#0-3) , and `Operator::withdraw` funds/broadcasts it through `fund_raw_transaction`/RBF [5](#0-4) .
- On confirmation, `Verifier::update_finalized_payouts` blindly trusts whatever OP_RETURN ends up in the confirmed transaction: it parses `get_first_op_return_output`, extracts the pubkey bytes, and writes them as `payout_payer_operator_xonly_pk` for that withdrawal index [6](#0-5) [7](#0-6) .
- This attribution is later relied upon in `is_kickoff_malicious`, which requires `kickoff_data.operator_xonly_pk == payout_info.operator_xonly_pk` or marks the kickoff malicious [8](#0-7) , and in `validate_payer_is_operator` / `PayoutCheckerTask`, which gate reimbursement processing on the recorded payer pubkey matching the operator's own key [9](#0-8) [10](#0-9) .

**Exploit flow**: An unprivileged attacker observes the operator's (or any user-authorized) payout transaction broadcast to the network/mempool for a withdrawal. Since input 0's witness (a valid Schnorr signature over the fixed sighash) is public once broadcast, and since it only commits to input 0 + output 0, the attacker constructs a new transaction that: reuses input 0 with the same witness, keeps output 0 (the user payout) unchanged, but sets output 2's OP_RETURN to any other publicly-known registered operator's xonly pubkey, and adds their own extra input to raise the fee. Because the original transaction is fee-payable/RBF, standard Bitcoin relay policy (BIP125 opt-in RBF, since `fund_raw_transaction` is used for funding/replaceable transactions) allows a higher-fee conflicting transaction from any sender to evict and replace the original in miners' mempools, so this attacker-modified variant confirms in place of the genuine one.

**Why existing guards fail**: None of the mentioned checks (`is_deposit_valid`, `SECP.verify_schnorr`, `is_kickoff_malicious`, DB uniqueness, etc.) validate that the OP_RETURN pubkey is cryptographically bound to the signed spend of output 0 — the signature verification only ever checks input 0/output 0 under the SinglePlusAnyoneCanPay sighash, and the OP_RETURN is trusted verbatim from whatever transaction happens to confirm.

### Impact Explanation
The confirmed payout's `payout_payer_operator_xonly_pk` can be attributed to an operator (call it B) who never funded output 0. Consequences:
- If the real funder (operator A) later sends a kickoff for the same deposit, `is_kickoff_malicious` compares A's `kickoff_data.operator_xonly_pk` to the DB-recorded B and returns `true` (malicious), so A is denied reimbursement despite having genuinely fronted the withdrawal — "an honest operator permanently unable to be reimbursed."
- Operator B, who never fronted anything, may be non-consensually implicated; `PayoutCheckerTask`/`validate_payer_is_operator` for B will treat this withdrawal as B's obligation, potentially causing B's automation to attempt handling a payout it has no `move_to_vault` record for in its own state.
- This is repeatable per attacker-observed payout broadcast and is not limited to one deposit/operator pair — any withdrawal whose payout tx is still unconfirmed/in mempool is a target, and any registered operator (publicly known xonly pubkey) can be named.

This matches the Critical category "an honest operator permanently unable to be reimbursed" / "an operator reimbursed for a payout it never funded" (attribution swap), depending on which side is examined.

### Likelihood Explanation
Preconditions: registered operators' xonly pubkeys are public (published at registration, as stated in the prompt); an unprivileged attacker only needs to observe a broadcast/mempool payout transaction and be able to fund a small additional fee to build a higher-fee, opt-in-RBF-replacing transaction. This requires no key compromise, no majority hashrate, and no privileged role — only mempool visibility and normal fee-paying capability, matching the stated attacker model exactly. The likelihood is moderated only by the race window (the attacker must act before the original payout confirms, i.e., before finality), which is realistically achievable since Bitcoin blocks average ~10 minutes and mempool propagation is near-instant; this is a standard opt-in RBF replacement, not exotic.

One caveat I could not fully verify from the index within available iterations: whether `DEFAULT_SEQUENCE` used for the payout tx's input signals BIP125 opt-in RBF (`sequence < 0xfffffffe`) is set explicitly to a value that would prevent third-party replacement, and whether `fund_raw_transaction`'s `replaceable` option (left as `None`/wallet default) actually results in a replaceable transaction on the specific bitcoind version deployed. If replacement is disabled at the mempool-policy level for this exact transaction (e.g., sequence set to `0xffffffff`/final, and no replaceable flag), the RBF-based race is blocked, but the underlying signature-does-not-cover-OP_RETURN weakness itself remains present and could still be exploited via first-seen mempool propagation racing (broadcasting the attacker's variant before the operator's own tx propagates) in less strict relay/miner policy environments. This nuance should be confirmed with a live `cargo test`/regtest reproduction before finalizing severity.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the same signature that authorizes spending input 0, e.g., by requiring the user's payout signature to use `TapSighashType::All` (or `AllPlusAnyoneCanPay`) instead of `SinglePlusAnyoneCanPay` so that all outputs (including the OP_RETURN) are committed by the signature, or by having the operator additionally co-sign/commit to the OP_RETURN value out-of-band (e.g., verified against the operator's registered pubkey via a Schnorr signature check before recording `update_payout_txs_and_payer_operator_xonly_pk`). At minimum, mark the transaction non-replaceable (finalized sequence) and treat any confirmed payout tx whose txid differs from the operator's originally-broadcast txid as suspect, cross-checking it against the operator's own tx-sender records before crediting attribution.

### Proof of Concept
```
cargo test proof plan (regtest, no mainnet, no live Citrea):
1. Set up two operators A and B with distinct xonly_pks (test harness in core/src/test/common).
2. Have operator A build and broadcast a genuine create_payout_txhandler payout tx for a withdrawal (SinglePlusAnyoneCanPay signature over input0/output0), do NOT mine it yet.
3. As the "attacker" (no operator keys), construct a new transaction reusing:
   - input[0] = same outpoint + same witness (valid under SinglePlusAnyoneCanPay)
   - output[0] = identical user payout output
   - output[2] (OP_RETURN) = B's xonly_pk instead of A's
   - an extra attacker-funded input to raise fee, signaling RBF
   Assert this transaction passes `test_mempool_accept` and can replace A's tx in the mempool (bumpfee/replace-by-fee semantics).
4. Mine the attacker's variant.
5. Run Verifier::update_finalized_payouts on the block; assert
   db.get_payout_info_from_move_txid(...) returns operator_xonly_pk == Some(B.xonly_pk), NOT A.
6. Simulate A's kickoff for this deposit; assert `is_kickoff_malicious` returns true (A wrongly flagged malicious) — i.e. operator_xonly_pk_recorded_for_withdrawal_i (B) != xonly_pk_of_party_who_funded_output_0 (A).
```

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
