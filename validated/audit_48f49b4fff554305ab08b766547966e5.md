### Title
Distribution precompile `rewards()` view method accepts and strands `value` (usei) sent with the call - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards` view method of the Distribution precompile (`0x0000000000000000000000000000000000001007`) is reachable via an EVM `CALL` carrying non-zero `msg.value`, but unlike every other method in the same precompile it never validates or refunds that value. Because a `CALL` to a precompile address unconditionally credits the transferred usei/wei to the precompile's EVM balance before the precompile logic runs, any value sent alongside a `rewards()` call is permanently stranded at the precompile address rather than reaching the caller, being refunded, or being applied to a state change.

### Finding Description
The Distribution precompile dispatch table protects almost all of its query/tx methods against unexpected value: state-changing methods call `p.validateInput(value, ...)` which internally calls `pcommon.ValidateNonPayable(value)` and rejects the call if `value.Sign() != 0` [2](#0-1) , and even other read-only queries like `params`, `validatorOutstandingRewards`, `validatorCommission`, etc. take `value *big.Int` as a parameter for the same validation purpose [5](#0-4) . The `rewards` method, however, is dispatched from `Execute` as `return p.rewards(ctx, method, args)` — omitting `value` from the call entirely [3](#0-2) , and its signature `func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{})` has no `value` parameter and performs no non-payable check [1](#0-0) . This precise defect is acknowledged in the repository's own e2e test comments as a known guard gap [4](#0-3) .

Because EVM `CALL` semantics transfer `msg.value` to the callee address (the precompile's mapped EVM/Sei account) as part of the underlying state-transition bridge before the precompile logic even executes, any usei sent with a `rewards()` call becomes balance held by the Distribution precompile module account in EVM state, with no code path in `rewards()` (or elsewhere) that refunds it to the sender or applies it to any distribution logic.

### Impact Explanation
Funds (usei) sent by any unprivileged EVM caller alongside a `rewards()` call are permanently locked at the precompile's address — they are not refunded, not credited to the caller's expected reward, and not recoverable through any documented precompile method, since `rewards` has no side effects that could disburse them. This constitutes a fund-freezing defect reachable by any external account or contract simply crafting a `CALL` with non-zero value to the Distribution precompile's `rewards(address)` selector.

### Likelihood Explanation
Likelihood is low-to-moderate: the interface exposed to callers (e.g., ethers.js `Contract` wrappers, `viewFunction` semantics) does not normally attach value to view/read-only calls, so accidental triggering by well-behaved clients is unlikely. However, any raw/low-level `CALL` (from a contract, a manually crafted transaction, or a misconfigured integrator) that mistakenly or deliberately attaches value to a `rewards()` invocation will trigger permanent loss with no error and no revert, since the call otherwise succeeds normally.

### Recommendation
Add the same guard used elsewhere in the precompile: thread `value` into `rewards()` and call `pcommon.ValidateNonPayable(value)` (or `p.validateInput(value, args, 1)`) before executing the query, so that any non-zero value sent causes the call to revert instead of stranding funds.

### Proof of Concept
1. Associate an EVM address with a Sei address and call the Distribution precompile's `rewards(delegatorAddress)` selector via a raw `CALL` with non-zero `value` (e.g., using `eth_sendTransaction` with `to: 0x...1007`, `data: <rewards selector + args>`, `value: <nonzero>`).
2. Observe the transaction succeeds (status 1) and returns the expected reward data, exactly as if `value` were zero.
3. Query the Distribution precompile's EVM balance (`eth_getBalance` on `0x0000000000000000000000000000000000001007`) before and after: the sent `value` increases the precompile's balance permanently, with no corresponding usei returned to the caller and no state change elsewhere that consumes it — confirming the funds are stranded, consistent with the test-suite comment noting this exact behavior [4](#0-3) .
