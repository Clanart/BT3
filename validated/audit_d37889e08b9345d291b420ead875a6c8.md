### Title
`Scanner::scan_block`/`scan_transaction` report immature coinbase outputs as spendable `ReceivedOutput`s, leading to consensus-invalid spends - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Serai Bitcoin wallet's `Scanner` credits any transaction output whose `script_pubkey` matches a registered key — including the block's coinbase transaction. Coinbase outputs are bound by a 100-block maturity rule (a consensus rule, not policy), so a `ReceivedOutput` produced from `block.txdata[0]` is reported as received funds yet is not spendable. `SignableTransaction::new`/`multisig` will happily consume such an output and produce a fully signed transaction that the Bitcoin network rejects as consensus-invalid.

### Finding Description
The upstream bug class: a contract accepts user funds without crediting anything back — value is received but the depositor gains nothing usable. The Serai analog: the wallet reports value as received/owned while the funds are not actually spendable.

`Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output matching a registered script, with no check on which transaction in the block it came from (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` calls it on `block.txdata` including `txdata[0]`, the coinbase (`mod.rs:221-227`). The only mitigation is a doc comment: "If received outputs must be immediately spendable, a post-processing pass is needed" — the API itself performs no filtering, and a caller using `scan_transaction` directly on a coinbase transaction gets the same unspendable result.

Downstream, `SignableTransaction::new` accepts any `ReceivedOutput` as an input (`wallet/send.rs:150-185`) and `TransactionSignMachine::sign` produces BIP-340 signatures committing to `Prevouts::All` (`send.rs:373-397`). Nothing anywhere checks coinbase maturity. The resulting signed transaction spends an immature coinbase output and is consensus-invalid; bitcoind rejects it at mempool acceptance and it can never confirm. Until the 100-block window passes the funds are effectively locked, and if the scanning/monitoring logic treats the output as immediately spendable balance, every spend attempt including it deterministically fails.

### Impact Explanation
- Funds are reported as received wallet balance while being unspendable: a miner (or anyone mining a block) paying to a Serai P2TR address produces a `ReceivedOutput` indistinguishable from a normal payment.
- Any `SignableTransaction` built over such an output wastes a full FROST signing ceremony and yields a transaction that can never be broadcast successfully — the inputs remain unusable until manually filtered.
- Reachable by an unprivileged party: anyone who can get a coinbase payout to the watched script (a miner, or a mining pool payout address) triggers it via ordinary on-chain data the scanner consumes.

### Likelihood Explanation
Medium. It requires a coinbase paying a watched script — uncommon but entirely possible (pool payouts, miner donations). The API contract makes it easy to hit: `scan_block` is the natural entry point and includes `txdata[0]` unconditionally; only callers who read the doc comment and implement their own maturity filter are safe. The processor-side code skips `block.txdata[1 ..]` for exactly this reason, confirming the hazard is real rather than theoretical — but the in-scope wallet library exposes the unsafe behavior unconditionally.

### Recommendation
In `Scanner::scan_transaction`, accept a flag or, in `scan_block`, skip `block.txdata[0]`; alternatively record coinbase outputs with a maturity height on `ReceivedOutput` and have `SignableTransaction::new` reject immature inputs. At minimum, make the maturity burden a type/API-level property rather than a doc comment.

### Proof of Concept
1. `let mut scanner = Scanner::new(even_key).unwrap();`
2. Mine a block whose coinbase (`block.txdata[0]`) pays `p2tr_script_buf(key)` — e.g., `generatetoaddress` to that address on regtest.
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` with `offset == Scalar::ZERO` for the coinbase output.
4. Build `SignableTransaction::new(vec![output], &payments, ...)` and run the FROST ceremony via `multisig`/`preprocess`/`sign`/`complete` — a fully valid-looking signed `Transaction` is produced.
5. `send_raw_transaction` fails with `bad-txns-premature-spend-of-coinbase` (consensus rejection): the reported funds are not spendable.
