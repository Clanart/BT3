## Title
Fee-on-transfer input tokens create phantom escrow on the Tron `IntentGatewayV2.placeOrder` — real balance shortfall permanently locks solver payouts - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
The H-06 report's core defect is a **balance-sheet mismatch**: one part of the system credits a ledger based on a nominal/expected amount while the actual custodied balance is something else, so accounting drifts from reality and later claimants can't be paid. Hyperbridge's Tron `IntentGatewayV2` contract reproduces exactly this pattern in `placeOrder`, while the canonical EVM contract explicitly fixed it.

## Finding Description
In the canonical EVM contract `evm/src/apps/IntentGatewayV2.sol`, `placeOrder` deliberately measures the **actual token balance delta** after `safeTransferFrom` and mutates `order.inputs[i].amount` to that measured value before computing the protocol fee and escrow record: [1](#0-0) 

The comment is explicit about why: "For fee-on-transfer tokens, the gateway receives less than the requested amount. We mutate `order.inputs` to reflect actual received so the commitment and escrow are consistent with what the gateway holds."

The Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does **not** do this. It transfers using the nominal, user-supplied `order.inputs[i].amount`, and separately computes `reducedInputs[i].amount` (protocol-fee-reduced) from that same nominal amount — never checking what the contract actually received: [2](#0-1) [3](#0-2) 

`_orders[commitment][token]` is then credited with `reducedInputs[i].amount`, an amount derived entirely from the nominal input, with no verification that the contract's real token balance increased by at least that much: [4](#0-3) 

If the input token skims any amount on transfer (a fee-on-transfer / rebasing / deflationary ERC-20 — the exact category the mainline contract explicitly guards against), the gateway's real balance is strictly less than what `_orders[commitment][token]` claims across all outstanding orders using that token. The escrow ledger becomes structurally overstated relative to custody, i.e. the corrupted value is `_orders[commitment][token]`, which no longer represents "amount of `token` this contract actually holds for this order."

This shortfall surfaces later at settlement. `withdraw()` releases `body.tokens[i].amount` (an escrow-ledger amount) via plain ERC20 `transfer`, checking only that the ledger entry is non-zero, not that the contract's real balance covers it: [5](#0-4) 

Because it is a shared token balance across many orders, whichever `withdraw()` calls land first drain the (now insufficient) real balance; subsequent legitimate `withdraw()` calls for other orders using the same token revert on the underlying `transfer` for lack of funds, even though `_orders[commitment][token]` still shows a nonzero "escrowed" balance for them.

## Impact Explanation
This is a direct loss/lock of funds through the public, unprivileged `placeOrder` entrypoint — no malicious peer, relayer, or admin needed. Any user placing an order with a fee-on-transfer input token understates the gateway's true balance versus its ledger. On a cross-chain order, the solver has already delivered output tokens on the destination chain before the source-chain `withdraw()` runs; if the source-chain balance shortfall means `withdraw()` reverts (insufficient real balance) for that or an unrelated order sharing the token, the solver's (or user's) rightful escrow becomes permanently unpayable/locked, i.e. the solver loses the value already delivered and the user's remaining escrow is stuck. This matches the bounty's "stealing or loss of funds" / "unauthorized transaction manipulation" impact class, mirroring the yEarn vault's "balance sheet doesn't reflect true value" bug that silently drained shareholders.

## Likelihood Explanation
Fee-on-transfer/deflationary tokens are a well-known, common ERC-20 category (and the presence of the exact fix in the sibling EVM contract, plus dedicated `FeeOnTransferToken` foundry tests for the mainline contract, confirms the Hyperbridge team is already aware this token class is expected to be supported as gateway input). The Tron contract's omission of the same guard means the bug triggers under completely ordinary usage — no attacker sophistication required, just placing an order with such a token as input.

## Recommendation
Port the mainline EVM fix to the Tron contract: measure the actual pre/post balance delta on every ERC20 `safeTransferFrom` (and native transfer) in `placeOrder`, mutate `order.inputs[i].amount` to the measured value, and derive `reducedInputs`/`_orders[commitment][token]` from that measured amount rather than the caller-supplied nominal amount. Additionally, `withdraw()` should validate `_orders[commitment][token] >= amount` (not just `!= 0`) before transferring, and ideally assert the token's real balance can cover the release.

## Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee on transfer) as an input token, `protocolFeeBps = 0` for simplicity.
2. User calls `placeOrder` with `inputs[0].amount = 1000`. `safeTransferFrom` pulls 1000 nominal, but the contract actually receives only 990 (1% skimmed). `_orders[commitment][token] += reducedInputs[0].amount` credits 1000 (no fee configured, so `reducedInputs == order.inputs`), even though real balance increase was only 990.
3. Repeat with a second, unrelated order using the same token, again crediting the full nominal amount to `_orders`.
4. Aggregate `_orders[...][token]` across both orders now exceeds the gateway's actual token balance by the cumulative transfer-fee skim.
5. First solver fill/settlement calls `withdraw()` and successfully drains close to the full real balance.
6. Second solver's/`withdraw()` call for the other order reverts on the ERC20 `transfer` inside `withdraw()` (insufficient real balance), even though `_orders[commitment][token]` still shows the escrow as fully funded — that solver's already-delivered output tokens (cross-chain case) or the user's escrow (refund case) are now permanently stuck.
