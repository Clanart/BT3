I have sufficient evidence now to state the finding: the `HasCodeHash()` check used to detect a "self-destructed" `TokenPair.Erc20Address` is a mere non-empty-codehash check, not a check that the *originally registered* bytecode is still present. This exactly mirrors the external report's bug class — a resurrection/re-mint hazard from lazily-cleared "locked/registered" state that does not survive a destroy-then-recreate cycle at the same identity (token id ↔ tokenId; contract address ↔ token pair address).

### Title
Stale TokenPair survives self-destruct + address resurrection, enabling unauthorized native-coin minting via a spoofed ERC20 contract - (File: x/erc20/keeper/msg_server.go)

### Summary
`ConvertERC20`/`ConvertCoin` only invalidate a registered `TokenPair` when the EVM account at the paired ERC20 address has `acc == nil || !acc.HasCodeHash()` [1](#0-0) [2](#0-1) . `HasCodeHash()` only tests that *some* code hash is present on the account, it does not verify that the code hash matches the originally registered ERC20MinterBurnerDecimals bytecode [3](#0-2) . This is the same class of bug as the reported "burned but not re-locked" NFT: a piece of state (whether a token is "live"/backed by real logic) is inferred from a coarse boolean (code exists) instead of being reset/pinned at the moment the underlying asset is destroyed.

### Finding Description
When a native ERC20 contract backing a `TokenPair` self-destructs, `k.evmKeeper.DeleteAccount` clears its code, and the token pair is only removed lazily the next time `ConvertERC20`/`ConvertCoin` is invoked and observes an empty code hash [1](#0-0) . Nothing prevents a new contract from being deployed at that exact address before that lazy check runs (e.g., via `CREATE2` with an attacker-chosen salt, a well known "metamorphic contract" pattern). Once any code is present again, `acc.HasCodeHash()` returns `true`, so the module treats the stale `TokenPair` mapping (`Erc20Address -> Denom`) as still valid and forwards `transfer`/`balanceOf` EVM calls to whatever bytecode is now living at that address [4](#0-3) [5](#0-4) .

Because `convertERC20IntoCoinsForNativeToken` and `ConvertCoinNativeERC20` validate the "transfer" outcome purely by re-querying `balanceOf`/return values on that same contract address [6](#0-5) [7](#0-6) , an attacker who controls the redeployed bytecode fully controls both the "transfer" call and the balance invariance check used to authorize it. This lets the caller satisfy `ConvertERC20`'s internal consistency checks without any real ERC20 value existing, while `k.bankKeeper.MintCoins` mints genuine native Cosmos coins backed by nothing [8](#0-7) .

### Impact Explanation
This breaks the erc20-module's core 1:1 accounting invariant between native coins and their locked/escrowed ERC20 backing. An attacker can mint unbacked native Cosmos coins for the `TokenPair.Denom`, directly matching the "Critical unauthorized minting… of spendable user value across native balances … ERC20 representations" impact class.

### Likelihood Explanation
Exploitation requires: (1) registering/owning a native ERC20 token pair (permissionless registration is supported per `TestRegisterERC20`'s "ok - non-governance, permissionless true" case) [9](#0-8) , (2) self-destructing the contract, and (3) redeploying attacker-controlled bytecode at the identical address via `CREATE2` before any user triggers the lazy cleanup. All three steps are achievable by an ordinary unprivileged EVM user with no special permissions, making this realistically triggerable, though it requires deliberate multi-step setup.

### Recommendation
Do not rely on `HasCodeHash()` alone to detect a "live" token-pair contract. Either:
- Pin and compare the original `codeHash` recorded at registration time against the current account's code hash before permitting any `ConvertERC20`/`ConvertCoin` operation, deleting/blocking the pair on mismatch, or
- Immediately (synchronously) delete the `TokenPair` mapping in the same state transition that destroys the contract (e.g., in the `SELFDESTRUCT`/`DeleteAccount` path), rather than deferring cleanup to the next conversion call.

### Proof of Concept
1. Deploy `ERC20MinterBurnerDecimals` at address `A` via a `CREATE2` factory with salt `S`; register it as a native `TokenPair` (permissionless registration).
2. Convert some ERC20 balance to native coin via `MsgConvertERC20` normally to prove the pair is legitimate, then trigger the contract to self-destruct, clearing its code at `A`.
3. Before anyone calls `ConvertERC20`/`ConvertCoin` again (which would lazily delete the stale pair), redeploy a new, attacker-authored contract to the same address `A` using the same factory/salt `S`, implementing `transfer(...)` to always return `true` and `balanceOf(...)` to return whatever value the caller wants.
4. Call `MsgConvertERC20` for `TokenPair` at `A`: `k.evmKeeper.GetAccountWithoutBalance` sees a non-empty code hash, so the pair is not deleted; `convertERC20IntoCoinsForNativeToken` calls the attacker's fake `transfer`/`balanceOf`, all invariance checks pass trivially, and `k.bankKeeper.MintCoins` mints real native coins to the attacker with no genuine ERC20 backing.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}
