### Title
Unrecognized packed-enum value causes `CodedInputStream` limit to leak, corrupting subsequent field parsing - (File: `java/core/src/main/java/com/google/protobuf/GeneratedMessageLite.java`)

### Summary
`GeneratedMessageLite.ExtensionSchema` (the reflection-based, generic extension-parsing path used by `parseExtension`) pushes a length limit onto the `CodedInputStream` before scanning a packed enum field, but on encountering the *first* unrecognized enum value it `return`s immediately from inside the `while (input.getBytesUntilLimit() > 0)` loop **without calling `input.popLimit(limit)`**. This mirrors the reported ETH-bridge bug: a precondition/edge-case branch inside a routine that owns a resource (`msg.value` / the pushed parsing "limit") takes an early `return` that bypasses the mandatory cleanup step, silently leaving that resource in a bad state instead of failing loudly.

### Finding Description
In `GeneratedMessageLite.java`, `parseExtension()` handles packed fields like this:

```java
if (packed) {
  int length = input.readRawVarint32();
  int limit = input.pushLimit(length);
  if (extension.descriptor.getLiteType() == WireFormat.FieldType.ENUM) {
    while (input.getBytesUntilLimit() > 0) {
      int rawValue = input.readEnum();
      Object value = extension.descriptor.getEnumType().findValueByNumber(rawValue);
      if (value == null) {
        // If the number isn't recognized as a valid value for this
        // enum, drop it (don't even add it to unknownFields).
        return true;                    // <-- early return, no popLimit()
      }
      extensions.addRepeatedField(...);
    }
  } else {
    while (input.getBytesUntilLimit() > 0) { ... }
  }
  input.popLimit(limit);                // <-- only reached on the "all values recognized" path
}
``` [1](#0-0) 

Compare this with the equivalent, correctly-written non-lite path in `MessageReflection.mergeFieldFrom`, which *always* falls through to `input.popLimit(limit)` after the packed-enum loop regardless of whether an unrecognized value is found:

```java

            unknownFields.mergeVarintField(fieldNumber, rawValue);
          }
        } else {
          target.addRepeatedField(field, value);
        }
      } else { ... }
    }
  } else { ... }
  input.popLimit(limit);   // always executed
}
``` [2](#0-1) 

The invariant that fails is the same one guaranteed by every other packed-field parsing site in the codebase (see the generated non-lite code, `input.popLimit(limit)`/`input.popLimit(oldLimit)` unconditionally executed after every packed loop) [3](#0-2) : every `pushLimit()` on a `CodedInputStream` must be matched by exactly one `popLimit()` before parsing continues, because `pushLimit`/`popLimit` mutate the stream's internal `currentLimit` state that all subsequent reads (`refillBuffer`, `isAtEnd`, `skipRawBytes`, etc.) rely on to know where the "virtual end of message" is [4](#0-3) . The attacker-controlled value here is the wire-encoded packed field's raw enum value (any int not present in the target enum's `Descriptor`) inside a schema that declares an extension of `ENUM` type used through `GeneratedMessageLite`'s generic extension path — this is fully reachable from an ordinary bounded `parseFrom()`/`mergeFrom()` call on trusted proto2 Lite schemas that use extensions, with no privileged access required.

Because the limit is never popped, the `CodedInputStream`'s `currentLimit` remains pinned at the boundary of the (now partially-consumed) packed field instead of being restored to the outer message's limit. Every subsequent read on that stream is bounded by the stale, smaller limit rather than the true remaining message size. This will manifest as spuriously truncated parsing of the *rest* of the message (fields after the packed extension silently disappear, or the parser throws a premature `truncatedMessage()`), i.e., a parsing integrity failure that is silent from the caller's point of view — directly analogous to the ETH bridge's silent, unrecoverable loss of the caller's asset when the early-return path skips the mandatory bookkeeping step.

### Impact Explanation
This is a parsing-correctness / integrity bug, not a crash or memory-safety bug: a message containing a packed extension enum field with even a single unknown enum value will have all of its remaining fields misparsed (dropped or reported as truncated) whenever the affected `ExtensionSchema.parseExtension` path is exercised (proto2 Lite generated code with extensions, or any code that walks `GeneratedMessageLite`'s extension parsing table directly). Applications that depend on `mergeFrom`/`parseFrom` faithfully reconstructing all message fields could silently lose data placed after the affected extension, which can translate into security-relevant consuming-application bugs (e.g., a policy or permission field located after the packed enum extension being silently dropped/defaulted). This is a legitimate Medium-severity correctness/integrity issue, matching the severity class of the original ETH report (silent, unrecoverable loss of caller-supplied state due to a missing "close the resource" step on an early-return branch), but it is not a crash, RCE, or resource-exhaustion issue and does not violate any "no unbounded-allocation" exclusion.

### Likelihood Explanation
Likelihood is limited to the specific combination of: (1) a proto2 schema with an `ENUM`-typed, packable extension field, (2) generic (non-tail-call, Lite) extension parsing path (`ExtensionSchema`/`parseExtension` in `GeneratedMessageLite`) being invoked, and (3) the packed payload containing at least one enum raw value absent from the extension's enum type. All three conditions are attacker-controllable from a bounded, well-formed wire payload sent to any public `parseFrom`/`mergeFrom` entry point on such a schema — no malformed varints, no huge allocations, and no privileged state are required, so the bug is readily triggerable by an ordinary client. It is, however, narrow in scope (proto2 Lite + extensions + packed enum), so it does not affect the majority of parse call sites (tail-call parser, `MessageReflection`, upb, C++, Python, etc., which correctly balance `pushLimit`/`popLimit`).

### Recommendation
In `GeneratedMessageLite.parseExtension`, restructure the packed-ENUM branch so that `input.popLimit(limit)` is always executed regardless of whether an unrecognized enum value is encountered — e.g., mirror `MessageReflection.mergeFieldFrom`'s pattern by continuing the loop (dropping the unrecognized value without discarding the pending stream state) and moving `popLimit` after the loop unconditionally, or by wrapping the loop body in a `try/finally` that guarantees `popLimit(limit)` runs before any `return`.

### Proof of Concept
Conceptual reproduction (not run in this environment, described precisely for verification by a Devin agent with build/test tooling):
1. Define a proto2 message with a repeated, packed extension field of an `enum` type with a limited value set (e.g., only `A=0`, `B=1`).
2. Hand-craft (or synthesize via `CodedOutputStream`) a serialized extension payload: a length-delimited packed field whose first varint value is `2` (not a defined enum value: `A`/`B`), followed by a second field in the *same outer message* with a distinguishing value (e.g., a required string field set to a known marker `"AFTER"`).
3. Call `SomeMessageLite.parseFrom(bytes, extensionRegistry)` (with the extension registered) on the generated Lite message.
4. Observe that the field encoded after the packed extension (`"AFTER"`) is missing/empty or that parsing throws `InvalidProtocolBufferException` for a truncated message, even though the input bytes for that field are present and well-formed — demonstrating that `parseExtension`'s early `return true;` on line 720 left the stream's `currentLimit` pinned to the packed-field boundary instead of restoring it via `input.popLimit(limit)` [5](#0-4) .
