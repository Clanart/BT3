The Tron `IntentGatewayV2` contract's `withdraw()` function silently accepts a "successful" low-level ERC20 `.call()` without checking the token's returned boolean, mirroring the report's "Depth 2" case (successful call, unaffected operation) — leading to permanent, unrecoverable loss of escrowed funds.

### Title
Unchecked ERC20 return-value in `withdraw()` permanently destroys escrow accounting on failed-but-non-reverting transfers - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary

### Finding Description
`withdraw()` releases escrowed order funds to a beneficiary using a raw low-level `.call()` for ERC20 tokens, checking only the outer call's `success` flag and ignoring the token's actual returned boolean: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    _orders[body.commitment][token] -= amount;
    ...
}
```

Per the ERC20 spec, `transfer()` is permitted to *return `false`* instead of reverting when the transfer cannot be completed (e.g., due to insufficient contract balance from rounding/fee-on-transfer tokens, blacklist logic, or paused state). A low-level `.call()` to such a token returns `success == true` (the call itself didn't revert) with returndata encoding `false`. Because the code never decodes/checks that returned boolean, the guard `if (!success) revert TransferFailed();` never fires, and execution proceeds to:
- Set `_filled[body.commitment] = beneficiary` (irreversibly marks the order as settled), at [2](#0-1) 
- Decrement `_orders[body.commitment][token] -= amount` (irreversibly destroys the escrow record), at [3](#0-2) 

No tokens actually leave the contract to the beneficiary, but the contract's internal state says the order is filled and the escrow is spent. This is the exact "Depth 2" failure mode from the external report: `bool success == true` is a dummy signal that does not guarantee the intended transfer effect.

This is inconsistent with the sibling EVM implementation of the same app, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer` (which decodes and validates the returned boolean) for the identical withdrawal logic: [4](#0-3) 

The vulnerable `withdraw()` is reachable from two unprivileged/host-triggered paths:
- `onAccept` for `RedeemEscrow`/`RefundEscrow` request kinds (host-delivered cross-chain settlement), at [5](#0-4) 
- `onGetResponse` for order cancellation, at [6](#0-5) 

The same unchecked-return pattern also appears in `SweepDust` handling: [7](#0-6) .

### Impact Explanation
Any order that escrows a token which returns `false` (rather than reverting) on a failed `transfer()` will have its funds permanently locked and unrecoverable: the escrow ledger (`_orders[commitment][token]`) is zeroed and the order is marked `_filled`, so there is no code path to retry or reclaim the funds — a subsequent `cancelOrder`/withdrawal attempt reverts with `Filled` or `UnknownOrder`. This constitutes a direct, unauthorized permanent loss of bridged/escrowed user funds, matching the bounty's "stealing or loss of funds" and "false ... acceptance" categories, without requiring any malicious relayer, prover, or admin — only a token contract exhibiting standard-compliant (if unusual) return-false-on-failure behavior, or a transient condition (e.g., paused token, blacklist, rounding dust below the transfer amount) at the moment of settlement.

### Likelihood Explanation
The path is reachable through normal, permissionless flows: `cancelOrder` → GET response settlement, and standard cross-chain `RedeemEscrow`/`RefundEscrow` settlement via `onAccept`, both driven by legitimate host-verified messages rather than attacker-crafted proofs. The trigger condition (a token whose `transfer` returns `false` instead of reverting) is common enough among real ERC20/TRC20 tokens that the codebase's own `SafeERC20` usage elsewhere demonstrates the team is aware of and defends against it — except in this one function.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this same contract (`using SafeERC20 for IERC20;`), ensuring both call success and the token's returned boolean (or absence of returndata, per EIP-20/no-return-token conventions) are validated before mutating `_filled`/`_orders` state.

### Proof of Concept
1. Deploy a minimal ERC20-like token whose `transfer()` returns `false` when `amount > balanceOf(address(this))` instead of reverting (this is valid ERC20 behavior, seen in real-world tokens).
2. `placeOrder` escrowing this token via `IntentGatewayV2` on Tron.
3. Arrange (e.g., via a fee-on-transfer quirk, partial balance drain from `SweepDust`/dust collection, or direct token behavior) for the contract's balance of that token to be less than the `amount` recorded in `_orders[commitment][token]` at settlement time.
4. Trigger settlement via `onAccept(RedeemEscrow)` or `onGetResponse` (cancellation).
5. `token.call(...)` returns `success == true` with encoded `false`; the `if (!success) revert` guard does not fire.
6. Observe: `_filled[commitment]` is set, `_orders[commitment][token]` is decremented to zero, `EscrowReleased`/`EscrowRefunded` is emitted — yet `token.balanceOf(beneficiary)` did not increase. The order can never be re-settled; funds are permanently stuck in the `IntentGatewayV2` contract.
