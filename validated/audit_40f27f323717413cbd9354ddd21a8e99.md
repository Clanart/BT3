Based on the code I examined, there is a genuine "score computed against one state but applied to a different state" pattern in Desktop's partial-commit (line-level staging) code path, structurally identical to the Venus bug: a value (line-index-based selection) is computed against one snapshot of data and then blindly reapplied against a different, later-fetched snapshot without re-validating that the two are in sync.

### Title
Stale line-based `DiffSelection` is reapplied against a freshly re-fetched diff during partial-file staging, silently corrupting what gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines/hunks of a file, GitHub Desktop stores the user's choice as a `DiffSelection` — a set of *absolute line indices* into the diff that was rendered in the Changes view. When the user clicks Commit, `applyPatchToIndex` does not reuse that already-rendered diff; it re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` [1](#0-0)  and then calls `formatPatch(file, diff)`, which walks the **new** diff's lines and asks the **old** selection object whether each `absoluteIndex` `isSelected` [2](#0-1) . There is no check that the new diff's hunk layout still matches the layout the selection was built against.

### Finding Description
The invariant the app relies on is: "the line indices recorded in `file.selection` correspond to the same lines in the diff used to build the patch." This invariant is normally close-to-true because the UI keeps `selection` roughly reconciled with the diff on every background status refresh via `withSelectableLines`, which only prunes indices that no longer exist but does not detect that surviving indices may now point at *different* content because of a shifted hunk offset [3](#0-2) .

Crucially, at the moment of commit, the invariant is broken again in a way the reconciliation logic never sees: `applyPatchToIndex` performs its own independent `getWorkingDirectoryDiff` call at staging time, completely decoupled from whatever diff/selection reconciliation last ran in the UI [1](#0-0) . If the working tree content for that file changes in the window between the last UI diff reconciliation and this staging call (extra/removed lines elsewhere in the file shift the hunk's `unifiedDiffStart`/line numbering), `formatPatch` will include/exclude lines based on stale absolute indices that now point at unrelated content [4](#0-3) . `stageFiles` then applies this mis-derived patch straight to the index without any secondary validation [5](#0-4) , and `createCommit` commits it [6](#0-5) .

This is the same bug class as `updateAlpha`/`updateMultipliers`: a derived value (score / line-selection) is computed against state S0, the underlying state moves to S1, and the derived value is applied to S1 as if it were still valid, with no re-synchronization step guarding the application point.

### Impact Explanation
If triggered, the user can end up committing lines they explicitly deselected, or omitting lines they explicitly selected — a silent corruption of what the user commits/pushes, which is in-scope for "silent corruption of what the user commits or pushes." In the worst case this could cause partially-redacted secrets/credentials to be committed anyway, or cause code the user intended to exclude to be pushed.

### Likelihood Explanation
This requires the working-tree file content to change (line-count/offset shifting) in the narrow window between the diff the user based their line selection on and the `applyPatchToIndex` staging call — I could not confirm from local code alone a fully remote-triggerable path (e.g. a filter/hook automatically mutating tracked file content at exactly that moment) that a malicious cloned/fetched repository could exploit without some local component (autosave, build watcher, concurrent git operation) actually rewriting the file. This weakens confidence that the "attacker controls a cloned/fetched repository" bar is met purely remotely; I'm flagging this uncertainty explicitly rather than asserting a fully remote PoC.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, re-validate that the freshly fetched diff's hunk structure matches the one the `DiffSelection` was computed against (e.g., by comparing a content hash/hunk signature captured at selection time), and abort/re-prompt the user if it has changed instead of silently reapplying stale indices.

### Proof of Concept
Not fully demonstrable as a remote-only exploit from local code alone. Locally reproducible sequence:
1. Modify a tracked file and view its diff in Desktop; select only specific lines to commit (partial `DiffSelection`).
2. Before clicking Commit, have another process (editor autosave, background script, or a second concurrent git operation) modify the same file so line offsets shift, without Desktop's Changes view refreshing/reconciling selection in time.
3. Click Commit — `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches the new diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) reapplies the stale selection indices against it, producing a patch that includes/excludes different lines than the user intended. export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
