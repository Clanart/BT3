### Title
Deserialization of untrusted `ThresholdKeys` accepts identity/zero verification shares and unvalidated secret share, yielding an attacker-controlled or trivially-forgeable group key - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) deserializes `t`, `n`, `i`, the interpolation method, the secret share, and all `verification_shares` directly from attacker-supplied bytes. It uses `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101), which enforces only canonical encodings — it does *not* reject identity points (contrast `Curve::read_G` in crypto/frost/src/curve/mod.rs:125-131, which does). `ThresholdKeys::new` (lib.rs:349-391) then only checks share count and participant index bounds; it never verifies `secret_share * G == verification_shares[i]`, never rejects identity verification shares, and never rejects an identity `group_key` computed at line 377-378.

### Finding Description
The bug class from CVE-2020-26207 is "trusting a deserialized file whose internal consistency is not validated." The Serai analog is `ThresholdKeys::read`: a crafted blob can set:

- `secret_share = 0` and every `verification_shares[l] = identity` (both canonical and accepted by `read_F`/`read_G`).
- `ThresholdKeys::new` then computes `group_key = Σ verification_shares[i] * λ_i = identity`, and returns `Ok`.

Any downstream FROST usage over these keys signs under `group_key() = identity` (lib.rs:445-447). A Schnorr/FROST signature verifies as `s*G == R + c*A`; with `A = identity`, anyone can produce valid signatures for arbitrary messages with `c = 0, s` chosen freely — the "threshold key" provides zero security. In the bitcoin-serai wallet path, deposit addresses derived from this group key are spendable by anyone, so funds reported as received are not actually secured.

Alternatively, the attacker sets `verification_shares` to a fully consistent set they generated themselves (they know the underlying polynomial), while the victim's `secret_share` is arbitrary: `SecretShareMachine`/`calculate_share`-style consistency between the secret share and `verification_shares[i]` is never checked, so the node produces shares that fail per-share verification and the honest node is blamed via `FrostError::InvalidShare` (crypto/frost/src/sign.rs:483-488), while the attacker can unilaterally sign under the group key.

The codebase itself acknowledges this gap at sign.rs:492-494 ("The only known way to cause this ... is to deserialize a semantically invalid FrostKeys") — invalid keys are detectable only after a failed signing session, not at load time.

### Impact Explanation
- Identity or attacker-known `group_key`: forged signatures and theft of all funds addressed to the threshold key (funds reported received that are not spendable by the honest set).
- Inconsistent `secret_share`/`verification_shares[i]`: the honest node's shares always fail verification; the honest node is mis-attributed blame and the multisig is unusable.

### Likelihood Explanation
Requires feeding a crafted `ThresholdKeys` blob to `ThresholdKeys::read` — the same trust assumption as the `.dbschema` file in the CVE. Where key material is loaded from disk or transported between components without an integrity layer, a tampered or substituted file fully compromises the key. There is no MAC, checksum, or PoK in the serialized format (lib.rs:538-562).

### Recommendation
In `ThresholdKeys::read` / `ThresholdKeys::new`:
- Reject identity verification shares and identity/zero `group_key` (use `Curve::read_G`-style identity rejection).
- Verify `C::generator() * secret_share == verification_shares[i]` for the local participant `i`.
- Reject `secret_share = 0`.
- Consider authenticating serialized keys (e.g., MAC or signature over the blob) since the format carries no integrity protection.

### Proof of Concept
```rust
// Build a ThresholdKeys blob with a zero group key, accepted by ::read
let t: u16 = 1; let n: u16 = 1; let i: u16 = 1;
let mut blob = vec![];
blob.extend((C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes());
blob.extend(n.to_le_bytes());
blob.extend(i.to_le_bytes());
blob.push(1); // Interpolation::Lagrange
blob.extend(C::F::ZERO.to_repr().as_ref());          // secret_share = 0
blob.extend(C::G::identity().to_bytes().as_ref());   // verification_shares[1] = identity

let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));
// group_key == identity => signature equation s*G == R + c*A is satisfiable
// by anyone (e.g., c = 0): the key provides no security, and any deposit
// address derived from it is spendable by an arbitrary party.
```
