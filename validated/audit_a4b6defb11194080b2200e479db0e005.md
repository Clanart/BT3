### Title
Automatic remote URL rewrite based on untrusted GitHub API `clone_url` can silently redirect future pushes - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically refreshes cached GitHub API repository metadata and uses `updateRemoteUrl` to reconcile the local git remote with the API's reported `clone_url`. This mirrors the `ReserveSwapper` pattern of "trust a value derived from external, attacker-influenced state, then act on it without re-verifying that the underlying assumption still holds." Here, the "order accounting balance" is the local `origin` remote URL, and the "external actor who can zero it out" is whoever controls the `IAPIRepository` object returned by the GitHub API for that repo (e.g., an org owner/repo admin who renames/transfers a repository, or a compromised/malicious GitHub Enterprise Server endpoint).

### Finding Description
`updateRemoteUrl` decides whether to silently overwrite the user's configured git remote URL: [1](#0-0) 

The core invariant check is: [2](#0-1) 

The function only compares URLs structurally (`hostname`/`owner`/`name`) via `urlMatchesRemote`/`parseRemote`: [3](#0-2) 

It never verifies that the *target host itself* is still one the user trusts beyond a previously cached `GitHubRepository.cloneURL`, nor does it require any user confirmation before calling `gitStore.setRemoteURL(...)`. The guard rails (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) are purely a TOCTOU-style "did the remote's owner/name change from what we last knew" check — they do not validate that the *new* value came from a trustworthy source, only that it's structurally well-formed and consistent with the previous API snapshot. Since `apiRepo` is sourced from a live GitHub API response, whoever controls that response (a malicious/compromised endpoint, or — for repos the user doesn't administer but still has this cached — a repository owner who changes visibility/ownership metadata) can cause Desktop to overwrite `origin`'s URL to point somewhere else, with no user-visible action or confirmation. This is functionally identical to the reported invariant break: an external actor mutates backing state between the time the app "checked" (cached `gitHubRepository.cloneURL`) and "acted" (rewrote the remote), and the code trusts the post-mutation external value without re-confirming user intent.

### Impact Explanation
If the remote URL is silently rewritten to an attacker-controlled endpoint, subsequent `git push` operations performed by the user through Desktop will transparently send commits/branches to a destination the user did not knowingly choose — a silent corruption of "what the user pushes." Because `push.ts` computes `envForRemoteOperation(remote.url)` from the (now attacker-controlled) URL for credential-helper/proxy resolution, this can also affect what credential context is used for the operation: [4](#0-3) 

The user is never shown a confirmation dialog for this remote-URL change, unlike other divergence-prone flows in the app that do require confirmation (e.g., force push): [5](#0-4) 

### Likelihood Explanation
This requires the attacker to control the GitHub API's reported repository data for a repo the victim has cloned (e.g., a malicious GHES/API-compatible endpoint, or being able to influence the API-returned metadata for a shared/forked repo the victim tracks). The `remoteUrlUnchanged` gate limits this to cases where the user hasn't manually customized their remote, narrowing but not eliminating the window — this is the same "acknowledged, narrow, holdover mechanism" character as the original `ReserveSwapper` report, which was also accepted as a known limitation rather than an exploit with unconditional reach.

### Recommendation
Require explicit user confirmation (a dialog, similar to the force-push confirmation) before silently rewriting a configured remote URL based on GitHub API data, and/or pin trust to the account's already-verified endpoint/hostname rather than accepting any `clone_url` value returned for a given `dbID`.

### Proof of Concept
1. Victim clones a GitHub repository through Desktop; `gitHubRepository.cloneURL` is cached matching `origin`.
2. The repository's owner (or a compromised/malicious API endpoint the account is configured against) causes the GitHub API to report a different `clone_url` for the same repo record (e.g. via a redirect or a manipulated GHES response) while keeping the record otherwise consistent enough to pass `protocolsMatch` and `remoteUrlUnchanged`.
3. On the next background refresh, `updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts:42-44` calls `gitStore.setRemoteURL(...)` and silently repoints `origin` to the new URL.
4. The victim's next `git push` (`app/src/lib/git/push.ts:48-118`) is sent to the attacker-influenced remote without any warning being shown.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
