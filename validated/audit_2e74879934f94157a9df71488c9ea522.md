### Title
Unhandled `IndexError` in `is_atom_canonical()` / `is_clvm_canonical()` allows a single crafted spend bundle to raise an uncaught exception during mempool admission - (File: chia/full_node/mempool_manager.py)

### Summary
`validate_spend_bundle()` calls `is_clvm_canonical()` on every `coin_spend.puzzle_reveal` and `coin_spend.solution` in a submitted `SpendBundle` before any other bounds-checking is performed. [1](#0-0)  Both `is_clvm_canonical()` and its helper `is_atom_canonical()` walk the CLVM byte buffer using an atom's self-declared length-prefix size without ever validating that the declared prefix bytes or atom length actually exist within the buffer, mirroring the `rtw_get_ie()` bug class (trusting a length byte without checking it against the remaining buffer size).

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` decodes the CLVM length-prefix encoding from the leading byte and then reads `prefix_len` (0-5) additional bytes by repeatedly incrementing `offset` and indexing `clvm_buffer[offset]`, with no check that `offset < len(clvm_buffer)`: [2](#0-1) 

`is_clvm_canonical(clvm_buffer)` similarly loops indexing `clvm_buffer[offset]` and advancing `offset` by the atom length returned from `is_atom_canonical`, again without checking that `offset` stays inside the buffer bounds before dereferencing: [3](#0-2) 

Because CPython bounds-checks `bytes` indexing, an out-of-range read raises `IndexError` rather than a raw memory read — but this still means a crafted, truncated CLVM byte string (e.g., a lead byte indicating a 5-byte length prefix such as `0xFC` followed by fewer than 5 remaining bytes, or an atom length that runs past the end of the buffer) triggers an unhandled Python exception deep inside `validate_spend_bundle()`.

This function is reached directly from `MempoolManager.validate_spend_bundle()`, which is invoked from `add_spend_bundle()` — the core mempool admission path taken for every spend bundle submitted by any unprivileged peer/wallet/RPC caller. [4](#0-3)  The call site has no `try/except` around the `is_clvm_canonical` calls, unlike the CLVM-execution failure path a few lines above which is wrapped in `try/except ValueError`. [5](#0-4) 

### Impact Explanation
An unhandled `IndexError` raised from `is_clvm_canonical`/`is_atom_canonical` during `add_spend_bundle` propagates up through the mempool-admission call chain. Since this code path is not guarded by exception handling at the point of the call (only `validate_clvm_and_signature`'s `ValueError` is caught), the exception is not converted into a normal `Err.INVALID_COIN_SOLUTION` rejection; it surfaces as an unexpected exception in whatever task/RPC handler drives spend-bundle admission. This is a spend-triggered disruption to transaction processing reachable by any single crafted spend bundle from an unprivileged submitter — matching the "spend-triggered transaction-processing halt" impact category. It is not a memory-corruption OOB read (Python bounds-checks), so the impact is bounded to exception/DoS rather than data disclosure or memory corruption, unlike the original kernel CVE.

### Likelihood Explanation
High likelihood of triggering the exception: constructing a `CoinSpend` with a `puzzle_reveal` or `solution` whose trailing bytes end mid-atom (e.g., an atom lead byte requiring more length bytes than remain, or a length prefix declaring more payload than remains) is trivial for any wallet-side or RPC caller building a `SpendBundle`, since `puzzle_reveal`/`solution` bytes are attacker-controlled and are only run through `is_clvm_canonical` inside `validate_spend_bundle`, prior to any other structural validation of that specific buffer's own bounds.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (verify `offset < len(clvm_buffer)` prior to reading the length-prefix continuation bytes and before validating the computed atom length against `len(clvm_buffer)`), and equivalently guard the `offset` dereference inside the `is_clvm_canonical()` loop. Alternatively/additionally, wrap the `is_clvm_canonical` calls in `validate_spend_bundle()` in a `try/except` that maps any parsing exception (including `IndexError`) to `Err.INVALID_COIN_SOLUTION`, consistent with how malformed CLVM already returns a controlled `Err` rather than propagating a raw exception.

### Proof of Concept
1. Craft a `solution` (or `puzzle_reveal`) byte string whose final byte is a multi-byte atom length-prefix lead byte requiring additional bytes that are absent from the buffer, e.g. bytes ending in `0xfc` (declares 5 additional length bytes) with fewer than 5 bytes remaining, or a byte sequence where the declared atom length exceeds the remaining buffer size.
2. Build a `SpendBundle` with a `CoinSpend` using this crafted `solution`/`puzzle_reveal` and submit it via the standard spend-bundle submission RPC/peer path so it reaches `MempoolManager.add_spend_bundle()`.
3. Observe that `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))` / `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` [6](#0-5) , which raises an unhandled `IndexError` inside `is_atom_canonical` when it dereferences `clvm_buffer[offset]` past the buffer's end [7](#0-6) , rather than returning a clean `Err.INVALID_COIN_SOLUTION` as intended for malformed CLVM.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
