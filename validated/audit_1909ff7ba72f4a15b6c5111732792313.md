### Title
Stale/superseded state commitment can be re-accepted as canonical after a fisherman veto, due to broken monotonicity reset - (File: evm/src/core/EvmHost.sol / evm/src/core/HandlerV2.sol)

### Summary
This is the local analog of the "stale price accepted as fresh" bug class: instead of a stale oracle price being usable for redemption, a **stale/vetoed state commitment height** can be re-accepted as the *latest* verified state for a state machine after a legitimate fisherman veto, because `deleteStateMachineCommitmentInternal` resets `_latestStateMachineHeight` to a hardcoded `1` rather than to the correct prior canonical height (or `0`). Any subsequent (unprivileged) consensus-proof submission for that chain only needs to beat `height > 1` to be accepted as the new "latest" commitment, allowing an old/replayed proof to be treated as fresh and trusted.

### Finding Description
When a fisherman successfully vetoes a state commitment via `freeze_client`-style proof handling, `EvmHost.deleteStateMachineCommitmentInternal` runs: [1](#0-0) 

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    ...
}
```

If the vetoed height happens to be the current `_latestStateMachineHeight` for that `stateMachineId`, the height tracker is force-reset to the constant `1`, not to the last-known-good height below it, and not to `0` (which would at least be treated specially, since `storeStateMachineCommitment`'s consumer in `HandlerV2.handleConsensus` only guards against overwriting via `latestHeight != 0`): [2](#0-1) 

```solidity
for (uint256 i = 0; i < intermediatesLen; i++) {
    IntermediateState memory intermediate = intermediates[i];
    uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
    if (latestHeight != 0 && intermediate.height > latestHeight) {
        StateMachineHeight memory stateMachineHeight =
            StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
        host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
    }
}
```

`storeStateMachineCommitment` itself blindly overwrites `_latestStateMachineHeight[height.stateMachineId] = height.height` for whatever height clears the `> latestHeight` bar, with the explicit assumption documented in its own comment: "Assumes the state commitment is of the latest height." [3](#0-2) 

Because the reset value is a low, fixed constant (`1`) instead of the actual immediately-preceding, still-valid height, the monotonicity guard is effectively disabled for the entire range `(1, previous_latest]`. Any consensus proof — including one that was already processed/finalized before, or one describing a height that is objectively behind the network's real current head — will pass `intermediate.height > latestHeight` as long as `intermediate.height > 1`, and will be written as the new canonical `latestStateMachineHeight`/commitment for that state machine. Since request/response/timeout handling (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) all key off `host.stateMachineCommitment(height)` and `host.stateMachineCommitmentUpdateTime(height)` for whichever height a relayer chooses to reference in their proof, an old/stale-but-since-vetoed-context state can be reintroduced as trusted truth without re-establishing the previously-enforced strictly-increasing height invariant.

This mirrors the audit's root cause exactly: the system fails to prevent acceptance of **stale, already-superseded data** as current truth, because the recency/monotonicity check (`intermediate.height > latestHeight`) is trivially satisfiable once the tracked "latest" baseline has been corrupted to an artificially low sentinel value.

### Impact Explanation
False state acceptance for a state machine directly undermines the trust model of ISMP: `handlePostRequests`/`handleGetResponses`/timeout handlers all rely on `stateMachineCommitment(height)` being the honest, most-recent, non-superseded view of the counterparty chain. If an old/replayed height can be re-promoted to "latest" after a veto, this can be leveraged to:
- Re-validate or re-process previously-vetoed/invalid state data as legitimate, potentially enabling dispatch of requests/responses/timeouts based on stale state.
- Allow a relayer to pick and "freshen" an old, already-superseded commitment for a given `stateMachineId`, undermining the challenge-period/fraud-proof security model that exists specifically to prevent stale/fraudulent state from being trusted.

This falls squarely under "false proof/state acceptance," one of the explicitly in-scope impact categories.

### Likelihood Explanation
The trigger condition (a fisherman veto of the currently-latest commitment for a given `stateMachineId`) is a normal, expected part of the protocol's fraud-detection lifecycle — not a contrived or adversarial precondition. Once that occurs, the exploit path requires only a normal, permissionless `handleConsensus` call with any legitimately-decodable proof whose derived intermediate height is `> 1`; no malicious relayer, prover, or admin collusion is needed to trigger the broken guard, only the pre-existing veto event plus a subsequent, otherwise-ordinary consensus submission.

### Recommendation
On veto, reset `_latestStateMachineHeight[stateMachineId]` to the actual highest remaining valid height below the vetoed one (tracked via a sorted structure or explicit "previous latest" bookkeeping), or to `0` combined with fixing `storeStateMachineCommitment`/`HandlerV2` to treat `0` as "no commitment yet" rather than skip-guard bypass. Do not use a magic constant (`1`) as a stand-in for "unknown latest height," since it silently reopens the height range to acceptance of old/stale proofs.

### Proof of Concept
1. State machine `X` has `_latestStateMachineHeight[X] = 100` with a valid, trusted commitment.
2. A fisherman submits a valid fraud proof; the handler calls `deleteStateMachineCommitment(height=100, fisherman)`, which deletes commitment 100 and, per the vetoed-is-latest branch, sets `_latestStateMachineHeight[X] = 1`.
3. Any party now calls `handleConsensus` with a decodable proof yielding an intermediate state for `X` at height `50` (an old height that was already superseded before the veto, e.g., a previously-processed but stale proof, or a proof for a chain fork segment lower than 100).
4. `HandlerV2.handleConsensus` checks `latestHeight(=1) != 0 && 50 > 1` → true, so `storeStateMachineCommitment` is called, setting commitment at height 50 as canonical and `_latestStateMachineHeight[X] = 50`.
5. Downstream handlers (`handlePostRequests`, etc.) now trust this stale height-50 commitment as the state machine's latest verified state, even though it predates and is inconsistent with the actually-current, more-advanced chain state that should have superseded it.

    /**
     * @dev Store the state commitment at given state height alongside relevant metadata.
     * Assumes the state commitment is of the latest height.
     */
    function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
        external
        restrict(_hostParams.handler)
    {
        _stateCommitments[height.stateMachineId][height.height] = commitment;
        _stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
        _latestStateMachineHeight[height.stateMachineId] = height.height;

        emit StateMachineUpdated({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId), 
            height: height.height
        });
    }
