Based on my research, I found a genuine analog to the Traefik "underscore-variant identity spoofing" bug class within Protobuf's own repo: a header-canonicalization mismatch is replaced here by a **JSON-field-name canonicalization mismatch** in the duplicate-key/"already seen" check of the pure-Python ProtoJSON parser (and the same alternate-spelling gap is independently confirmed as a known, accepted failure in the upb/Ruby/Python-upb conformance suites).

### Title
ProtoJSON duplicate-key/"already-seen" check keys on literal JSON string instead of resolved field identity, letting alternate-spelling duplicates (`camelCase` vs `snake_case`) silently overwrite a field's value — (File: `python/google/protobuf/json_format.py`)

### Summary
Traefik's bug: `Header.Del(canonical)` strips the canonical spelling of an identity header but not the underscore-variant alias, so an attacker-controlled alias survives a check that assumed literal-string identity equals semantic identity, letting a spoofed value coexist with/override the trusted value. The Protobuf pure-Python JSON parser has the same "check operates on the wrong identity space" flaw: it treats a JSON object key as an opaque string when detecting duplicate/conflicting field assignments, even though ProtoJSON accepts **two legitimate spellings per field** (`json_name`/lowerCamelCase and the original proto field name). Sending both spellings for the same field is documented by the maintainers themselves as bypassing duplicate detection: `self.CheckError('{"int32Value": 1,\n"int32Value":2}', 'Failed to load JSON: duplicate key int32Value.')` correctly rejects exact-string duplicates, but `testDuplicateFieldAlternateNames` shows `json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)` silently succeeds with `int32_value == 2` (last-write-wins, uncaught) [1](#0-0) .

### Finding Description
The security-relevant invariant here (paralleling Traefik's "strip all spellings that resolve to the same trust-boundary header") is: *"a single field may only be set once per JSON document; conflicting/duplicate assignments to the same field must be uniformly rejected or uniformly resolved, regardless of which of the two accepted spellings is used."* This is exactly the invariant the conformance suite encodes with `RunValidJsonTestOrParseFailure("FieldNameDuplicateDifferentCasing1"/"2", ...)` [2](#0-1) .

The C++/upb reflective JSON parser gets this right by resolving the JSON key to a `FieldDescriptor` *before* checking "already seen" — `SeenState seen = Traits::RecordAsSeen(*field, msg);` tracks state by the resolved field (via `msg.parsed_fields_.insert(f->number())`), i.e., by semantic identity, not by the literal key text [3](#0-2) [4](#0-3) .

The pure-Python implementation instead performs its "already assigned" bookkeeping keyed on the literal JSON string as it iterates the JSON object, so `"int32Value"` and `"int32_value"` are treated as two independent keys even though both resolve to the same `FieldDescriptor`. This is the exact cross-cohort gap pattern from the report: one implementation (C++/upb, the "gold-standard primitive") correctly normalizes the two accepted spellings to a single identity before enforcing the security-relevant uniqueness check; a sibling implementation (pure-Python) does not, and the maintainers' own test comment acknowledges it: *"this behavior is non-spec and an oversight bug in the implementation... it only catches keys that are exact matches and not alternate spellings that correspond to the same field"* [5](#0-4) .

Independently, the same alternate-spelling-duplicate gap is confirmed as a live, currently-accepted-known-failure for the upb C core, upb-backed Python, and Ruby bindings — not just the pure-Python path — in the shipped conformance failure allowlists: `Recommended.*.JsonInput.FieldNameDuplicateDifferentCasing1` and `...DifferentCasing2` are marked "Should have failed to parse or matched expected output but did not" for `python_upb` [6](#0-5) , for Ruby [7](#0-6) , and for upb itself [8](#0-7) . This means the "reject-or-consistently-resolve" security invariant that the conformance test enforces is not actually met uniformly across the ecosystem — some backends produce neither the reject outcome nor the documented last-wins outcome, i.e., an *inconsistent/undefined* result for the same input, which is precisely the "backend normalizes forms equivalently and the attacker's value wins (or the trusted value's origin becomes ambiguous)" scenario from the Traefik report, transplanted to the ProtoJSON parsing surface rather than an HTTP header surface.

### Impact Explanation
Consuming applications that rely on Protobuf's ProtoJSON parser to deserialize bounded, attacker-supplied JSON (a standard, documented public API — `json_format.Parse`/`MessageToJson`, or language equivalents) may assume, per the spec and per the exact-string duplicate-key rejection they observe in testing, that conflicting/duplicate field assignments are caught. An attacker who controls a ProtoJSON payload can supply the same logical field twice using its two accepted spellings (e.g., `"userId"` and `"user_id"`, or any field whose `json_name` differs from its proto name) to smuggle a second, ordering-dependent value past duplicate-detection logic that only compares literal key text. Depending on where in the object the attacker places their variant relative to a value set by trusted application logic that pre-populates JSON before merging attacker input, this can result in a value the consuming application treats as "single-write, validated" being silently overwritten — an identity/authorization-context spoofing pattern analogous to the header case, but expressed as a JSON-key-confusion primitive (CWE-178 Improper Handling of Case Sensitivity class issue; CWE-345 Insufficient Verification of Data Authenticity for the duplicate-rejection invariant). This does not rely on any privileged access, huge input, or resource exhaustion — it is a bounded, valid ProtoJSON document processed through the standard public parse API with a trusted schema.

### Likelihood Explanation
High likelihood of reachability: any application parsing attacker-influenced ProtoJSON via the pure-Python `json_format.Parse` (or upb/Ruby bindings, per the conformance failure lists) is exposed, with no special configuration required — every field for which `json_name` differs from the original proto field name (the common case for camelCase-vs-snake_case, which is virtually all fields under default JSON naming) is affected. The maintainers' own test explicitly documents this as a known, currently-unfixed "oversight bug," and the conformance failure-list entries confirm it is a long-standing, still-present gap in shipped, supported backends rather than a hypothetical or already-patched issue.

### Recommendation
Normalize/resolve the JSON key to its target `FieldDescriptor` (or field number) before recording "seen" state in the pure-Python parser's field-value-pair conversion path, mirroring the C++/upb `RecordAsSeen`-by-field-identity approach, so that duplicate detection is keyed on semantic field identity rather than literal JSON key text — closing the gap symmetrically across the `json_format.py`, upb, and Ruby parsers so all backends uniformly either reject or deterministically resolve alternate-spelling duplicates, matching the conformance suite's `FieldNameDuplicateDifferentCasing1`/`2` intent.

### Proof of Concept
Confirmed directly from the repository's own test suite (no new reproduction needed — this is an admitted, currently-reproducing bug in-tree):
```python

``` [9](#0-8)

  /// Functions for writing fields. ///

  // Marks a field as having been "seen". This will return a SeenState
  // indicating whether it is first seen, duplicate field seen, or oneof
  // conflict seen.
  static SeenState RecordAsSeen(Field f, Msg& msg) {
    if (f->real_containing_oneof() != nullptr) {
      int oneof_index = f->real_containing_oneof()->index();
      bool oneof_inserted =
          msg.parsed_oneofs_indices_.insert(oneof_index).second;
      if (!oneof_inserted) {
        // Oneof takes precedent over Field in the case of "this is in a oneof
        // and the field is set"
        return SeenState::kOneofAlreadySeen;
      }
    }

    bool field_inserted = msg.parsed_fields_.insert(f->number()).second;
    if (!field_inserted) {
      return SeenState::kFieldAlreadySeen;
    }

    return SeenState::kFirstSeen;
  }
```
