### Title
Hidden bidirectional-Unicode warning is silently skipped for large diffs, allowing Trojan-Source-style content to be staged/committed unnoticed - (File: app/src/ui/diff/index.tsx)

### Summary
Desktop detects invisible Unicode bidi control characters (`HiddenBidiCharsRegex`) in a diff and surfaces a warning banner (`DiffContentsWarning`) so a reviewer knows the rendered text may not match what's actually in the file. This warning is only wired into the code path that renders a regular text diff. When the diff is classified as `DiffType.LargeText` (diff/file too large to render by default), Desktop shows a placeholder ("The diff is too large to be displayed by default... Show Diff") and does not render `DiffContentsWarning` unless the user explicitly opts to expand it. A user can therefore stage and commit a file containing hidden bidi characters — content that visually appears reordered/misleading in an external editor or GitHub's own PR UI — without ever seeing Desktop's warning, if the file/diff happens to be large.

### Finding Description
`DiffParser.parse()` computes `hasHiddenBidiChars` via `HiddenBidiCharsRegex.test(text)` for every diff, and `buildDiff()` propagates this flag into both `ITextDiff` and `ILargeTextDiff`. [5](#0-4)  However, the flag is only surfaced to the user through `DiffContentsWarning`, which is instantiated inside `side-by-side-diff.tsx`, itself only reached via `Diff.renderText()`/`renderLargeText()`. For a `DiffType.LargeText` diff, `Diff.render()` unconditionally calls `renderLargeTextDiff()` (a collapsed placeholder with a "Show Diff" button) unless `state.forceShowLargeDiff` is already `true`. [6](#0-5) [2](#0-1)  This means the warning banner that is supposed to protect against "content committed differs from what visually appears" is conditioned on diff size, an attacker-influenced property (an attacker who controls the file/patch content in a fork/PR/fetched branch can simply make the diff large enough to trip the "too large to render" threshold), fully bypassing the safeguard by default.

This directly parallels M-12/M-related class of finding: a protective check exists (`hasHiddenBidiChars` / `DiffContentsWarning`) but does not cover every path the corrupted value can travel through before being committed — analogous to slippage protection existing in `stake()`/`unstake()` but not on every derivative path.

### Impact Explanation
A crafted large file/diff (e.g., from a cloned/fetched malicious repository, or a file changed via a merge/rebase from an untrusted remote) can carry hidden bidi-reordering characters (Trojan Source class attack) that make reviewed code appear different from what is actually staged and committed by the Desktop user. Since Desktop's only mitigation for this is the collapsed banner, and that banner is skipped by default for large diffs, the user's commit can silently include logic-altering hidden characters they never saw, with no additional step required beyond opening a large file in the normal commit flow.

### Likelihood Explanation
Any file or diff exceeding Desktop's large-diff threshold trivially triggers this path — no privileged access, malware, or unnatural interaction is required beyond a user reviewing/staging a legitimately large changed file that originated from an external/fetched source. Since large diffs are common (generated files, vendored code, minified assets, or simply padded content by an attacker to cross the threshold), the likelihood that the mitigating banner is skipped is not marginal.

### Recommendation
Compute and surface the `hasHiddenBidiChars` warning independently of the `forceShowLargeDiff` state — i.e., show the `DiffContentsWarning` banner (or block staging with an explicit confirmation) in `renderLargeTextDiff()` itself whenever `diff.hasHiddenBidiChars` is `true`, rather than only after the user opts into rendering the full diff.

### Proof of Concept
1. In a remote/fork repository, create or modify a file so that the corresponding diff exceeds Desktop's large-diff rendering threshold (e.g., a large text file with many changed lines) and include invisible bidi control characters (e.g., U+202E) in one of the added lines to reorder visually displayed code.
2. Fetch/pull this branch into Desktop and open the Changes view for that file.
3. Because the diff is classified `DiffType.LargeText`, Desktop shows the "diff too large to be displayed by default" placeholder (`renderLargeTextDiff()`), and `DiffContentsWarning` is never rendered.
4. The user stages/commits the file via Desktop's normal commit flow without ever seeing the bidi-character warning, even though `diff.hasHiddenBidiChars` is `true` internally. [7](#0-6)

    if (diff.hasHiddenBidiChars) {
      items.push({
        type: DiffContentsWarningType.UnicodeBidiCharacters,
      })
    }

    if (diff.lineEndingsChange) {
      items.push({
        type: DiffContentsWarningType.LineEndingsChange,
        lineEndingsChange: diff.lineEndingsChange,
      })
    }
