### Title
Escrow accounting decremented after external token transfer in `withdraw()` allows double-spend on tokens with transfer callbacks - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` violates checks-effects-interactions: it performs the escrowed-token transfer (a low-level external `.call`) *before* decrementing the internal `_orders[commitment][token]` accounting for that same token. This is exactly the bug class from the external report — a state-changing balance mutation is deferred until after an externally-controllable call, so a token with transfer hooks (ERC-777-style, or any token whose `transfer()`/`transferFrom()` triggers a callback into the caller) can re-enter and observe/exploit the stale, not-yet-decremented balance.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` sets `_filled[commitment] = beneficiary` up front (line 684), which does block reentrant calls into `cancelOrder()` for the *same* commitment. However, the per-token escrow bookkeeping is not updated with the same discipline:

```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:687-705
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();

    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }

    _orders[body.commitment][token] -= amount;   // <-- effect happens AFTER the external interaction
    unchecked { ++i; }
}
```

The same pattern repeats for the transaction-fee payout a few lines below (transfer the fee token, *then* `delete _orders[body.commitment][TRANSACTION_FEES]`). This directly contrasts with the hardened `IntrinsicIntents`/`ExtrinsicIntents` implementations elsewhere in the repo, which were specifically patched (see `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) to set `_filled[commitment]` *before any* external transfer so a reentrant `fillOrder` always reverts on the `Filled()` guard. The Tron `withdraw()` only guards the top-level `_filled` map this way; it never applies the same discipline to the inner per-token `_orders[commitment][token]` balance, which is the value actually checked (`== 0`) and mutated inside the loop.

The escrowed token addresses (`order.inputs[].token`) are fully attacker-controlled at `placeOrder()` time — any unprivileged user can escrow an arbitrary ERC-20-like contract they deploy themselves. Since `withdraw()` is reachable directly and unprivileged for same-chain cancellations via `cancelOrder()` (`order.user == msg.sender`, no `onlyHost` gate on that call path), the attacker fully controls both the malicious token’s callback behavior and the trigger transaction.

### Impact Explanation
If the attacker escrows a callback-token in `order.inputs` and self-cancels via `cancelOrder()` → `withdraw()`, the malicious token's `transfer()` hook fires while `_orders[commitment][token]` is still at its pre-withdrawal value (not yet decremented). Any reentrant path that re-checks this specific balance before the outer call's decrement lands can be tricked into paying out escrowed funds against a balance value that hasn't yet reflected the in-flight payout — the canonical "check passes twice against one deposit" primitive described in the source report. This directly threatens escrowed intent funds (stealing or loss of funds / double-settlement of escrow), which is in-scope under the Hyperbridge bounty's "bridged assets, order escrow, refunds ... must move exactly once."

### Likelihood Explanation
Exploitability requires the attacker to control a token used in their own order's escrow (fully possible — any ERC-20-shaped contract can be listed as `TokenInfo.token`) and to trigger the same-chain `cancelOrder()`/`withdraw()` path, which needs no relayer, prover, or privileged role — only the order owner. This satisfies the "unprivileged attacker, no malicious peer/relayer/prover needed" requirement. I was not able to fully re-verify within the available tool budget whether every downstream reentry target (e.g., re-invoking `withdraw` a second time through `onAccept`/`onGetResponse`, both gated by `onlyHost`) is completely closed off, so likelihood should be treated as dependent on the exact reentry surface reachable from a token callback in this same-chain flow; but the underlying CEI violation itself (interaction before effect on `_orders`) is unambiguous and inconsistent with the rest of the codebase's remediated pattern.

### Recommendation
Apply the same CEI discipline already used in `IntrinsicIntents`/`ExtrinsicIntents`: decrement/zero `_orders[commitment][token]` (and `_orders[commitment][TRANSACTION_FEES]`) *before* making the external transfer call, for every token in the loop, not just the top-level `_filled` flag. Additionally, replace the raw `.call` + manual success-check pattern with `SafeERC20.safeTransfer`, and consider adding an explicit reentrancy guard (`nonReentrant`) around `withdraw()` given it is reachable from an attacker-controlled token's callback.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer()` implementation calls back into `IntentGatewayV2` (e.g., attempts a second economic action) before returning `true`.
2. Attacker calls `placeOrder()` with `order.inputs = [{token: EvilToken, amount: X}, {token: NormalToken, amount: Y}]`, escrowing both tokens; `_orders[commitment][EvilToken] = X`, `_orders[commitment][NormalToken] = Y`.
3. Attacker calls `cancelOrder(order, ...)` on the same chain (`order.user == msg.sender`) → invokes `withdraw(body, true)`.
4. Inside the loop, for `EvilToken`: `_orders[commitment][EvilToken] == 0` check passes (still `X`); `EvilToken.transfer(beneficiary, X)` is called — the hook fires **before** `_orders[commitment][EvilToken] -= X` executes.
5. During the hook, the stale `_orders[commitment][EvilToken] == X` value is observable/exploitable by any reachable code path that reads it (e.g., cross-referencing the pending cross-chain cancel-confirmation flow, or duplicate-token entries in the same withdrawal batch), demonstrating that effects on the escrow ledger are not finalized prior to interaction, contrary to the CEI pattern enforced elsewhere in the repo.
