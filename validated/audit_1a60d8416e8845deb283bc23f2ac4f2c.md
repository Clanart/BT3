### Title
Missing `Approval`-event guard in `convertERC20IntoCoinsForNativeToken` allows a malicious native-ERC20 contract to duplicate escrowed value - (File: `x/erc20/keeper/msg_server.go`)

### Summary
The docstring on `Keeper.convertERC20IntoCoinsForNativeToken` states the function must "check for unexpected `Approval` event in logs," and the helper `validateApprovalEventDoesNotExist` exists precisely for that purpose, but the function's implementation never calls it. The same omission exists in `ConvertCoinNativeERC20`. As a result, a token contract that emits/sets an `Approval` (allowance) as a side effect of `transfer` is never rejected.

### Finding Description
`convertERC20IntoCoinsForNativeToken` escrows tokens by calling `transfer(ModuleAddress, amount)` on the registered ERC20 contract via `k.evmKeeper.CallEVMWithData` [1](#0-0) . After the call it only validates the `Transfer` event or boolean return value and the raw balance delta [2](#0-1) , then mints and sends coins [3](#0-2) . `validateApprovalEventDoesNotExist` is defined in `x/erc20/keeper/util.go` [4](#0-3)  but a repo-wide search shows it is referenced only in its own definition and its unit test [5](#0-4)  — it is never invoked from `msg_server.go`. This means a malicious ERC20 contract's `transfer()` implementation can, as a side effect, grant an allowance (emit `Approval`) to the attacker over the module account's newly escrowed balance, and the conversion will still succeed because nothing checks for that event.

Combined with `RegisterERC20`, which explicitly allows "Any account [to] permissionlessly register a native ERC20 contract to map to a Cosmos Coin" when `PermissionlessRegistration` is enabled [6](#0-5) , an attacker can:
1. Deploy a malicious ERC20 whose `transfer()` performs the normal balance move but also self-approves the attacker over the recipient's (module account's) balance.
2. Register it as a native token pair via `MsgRegisterERC20`.
3. Call `MsgConvertERC20`, triggering `convertERC20IntoCoinsForNativeToken`, which escrows tokens to `types.ModuleAddress` and mints/sends the attacker equivalent native coins [7](#0-6) .
4. Because the missing check never inspects the logs for `Approval`, the hidden allowance persists.
5. The attacker then calls `transferFrom(ModuleAddress, attacker, amount)` directly on the ERC20 contract (an ordinary, unprivileged EVM call outside the module) to reclaim the "escrowed" tokens.

Net effect: the attacker ends up holding both the newly minted native coins and the original ERC20 tokens — a duplication of value backed 1:1 by nothing, corrupting the erc20↔coin accounting invariant that the whole `x/erc20` module is designed to preserve.

### Impact Explanation
This breaks the core 1:1 backing invariant between native coins and native-ERC20-token escrow that `x/erc20` is supposed to guarantee, allowing an unprivileged attacker to duplicate spendable value (mint native coins while also reclaiming the "escrowed" tokens). This matches the allowed "Critical unauthorized minting/duplication ... across native balances, EVM balances, ERC20 representations" impact.

### Likelihood Explanation
The attack requires only ordinary, unprivileged actions: deploying a contract, and calling `MsgRegisterERC20` (contingent on `PermissionlessRegistration` being enabled — this is a governance-configurable parameter, not attacker-controlled, so if it is disabled the registration step would require a privileged/governance action instead). Given that constraint, likelihood is conditional: fully exploitable and permissionless when `PermissionlessRegistration=true`, otherwise requires governance approval of a malicious token pair, which is outside the "unprivileged" threat model. I could not verify the default value of this parameter within the scope of this review, so this dependency should be highlighted to the auditee.

### Recommendation
Call `validateApprovalEventDoesNotExist(res.Logs)` immediately after the `transfer` call inside `convertERC20IntoCoinsForNativeToken` (and likewise in `ConvertCoinNativeERC20`'s `transfer` call), matching the behavior already documented in the function's own comment, and return `types.ErrUnexpectedEvent` if an `Approval` event is present.

    pair := s.setupNativeTokenPairWithMaliciousContract(maliciousBytecode)

    msg := &types.MsgConvertERC20{
        ContractAddress: pair.Erc20Address,
        Amount:          math.NewInt(1000),
        Receiver:        s.receiverAddr.String(),
        Sender:          s.attackerHexAddr.Hex(),
    }

    _, err := s.app.Erc20Keeper.ConvertERC20(s.ctx, msg)

    // Current (buggy) behavior: err is nil, coins are minted, and the
    // attacker can subsequently call transferFrom() on the malicious
    // contract to reclaim the escrowed tokens.
    //
    // Expected behavior after fix:
    s.Require().ErrorIs(err, types.ErrUnexpectedEvent)

// validateApprovalEventDoesNotExist returns an error if the given transactions logs include
// an unexpected `Approval` event
func validateApprovalEventDoesNotExist(logs []*types.Log) error {
	for _, log := range logs {
		if log.Topics[0] == logApprovalSigHash.Hex() {
			return errors.Wrapf(
				types2.ErrUnexpectedEvent, "unexpected Approval event",
			)
		}
	}

	return nil
}

func TestValidateApprovalEventDoesNotExist(t *testing.T) {
	tests := []struct {
		name        string
		res         *types.MsgEthereumTxResponse
		expectError bool
	}{
		{
			name: "empty logs",
			res: &types.MsgEthereumTxResponse{
				Logs: []*types.Log{},
			},
			expectError: false,
		},
		{
			name: "no approval event",
			res: &types.MsgEthereumTxResponse{
				Logs: []*types.Log{
					{
						Topics: []string{"0x1234567890abcdef"},
					},
				},
			},
			expectError: false,
		},
		{
			name: "has approval event",
			res: &types.MsgEthereumTxResponse{
				Logs: []*types.Log{
					{
						Topics: []string{logApprovalSigHash.Hex()},
					},
				},
			},
			expectError: true,
		},
		{
			name: "approval event among others",
			res: &types.MsgEthereumTxResponse{
				Logs: []*types.Log{
					{
						Topics: []string{"0x1234567890abcdef"},
					},
					{
						Topics: []string{logApprovalSigHash.Hex()},
					},
				},

		},

				require.NoError(t, err)
