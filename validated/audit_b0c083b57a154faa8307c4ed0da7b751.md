Confirmed: `unlock()` in `VLMGP.sol` (and analogously `mWomSV.sol`) always invokes `IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender)` with an empty reward-token array *before* releasing the unlocked principal [1](#0-0) . Because the array is empty, `_claimBaseRewarder` falls into the `getReward(_account, _receiver)` branch, which claims **all** registered reward tokens for that pool in one loop [2](#0-1) . The underlying `BaseRewardPool`/`BaseRewardPoolV2`/`vlMGPBaseRewarder` `getReward` implementations iterate over `rewardTokens` and perform an unconditional `IERC20(rewardToken).safeTransfer(...)` for every token with a nonzero balance, with no per-token try/catch [3](#0-2) [4](#0-3) [5](#0-4) .

### Title
Unlock of vested vlMGP/mWomSV can be permanently DoS'd by a single failing reward token in the pool's BaseRewarder - (File: VLMGP.sol / mWomSV.sol / rewards/MasterMagpie.sol)

### Summary
`unlock()` (VLMGP) and the analogous unlock function in `mWomSV.sol` unconditionally trigger a full reward claim across every registered reward token in the pool's base rewarder before releasing the user's already-cooled-down principal. If any single reward token in that loop reverts on transfer (e.g., a paused/blacklist-capable token, a token that later becomes non-transferable, or one that runs out of allowance/liquidity for any legitimate reason), the entire `unlock()` transaction reverts, permanently blocking the user from ever retrieving MGP that has already finished its cooldown period.

### Finding Description
`unlock()` requires `slot.endTime <= block.timestamp` (cooldown finished) then performs, in order: (1) a full-pool reward claim via `multiclaimFor` with an empty reward-token list, (2) `_unlock()` accounting, and (3) the `IERC20(MGP).safeTransfer` of the unlocked principal [6](#0-5) . Step (1) routes through `_multiClaim` → `_claimBaseRewarder` → `rewarder.getReward(_account, _receiver)` since the caller passes an empty reward-token array [7](#0-6) [2](#0-1) . `getReward` loops over every token in `rewardTokens` and does a bare `safeTransfer` for any nonzero pending amount, with no skip/try-catch mechanism analogous to EigenLayer's `indicesToSkip` [3](#0-2) . Since `rewardTokens` accumulates every distinct token ever queued via `queueNewRewards` for that pool [8](#0-7) , a single reward token that starts reverting on transfer for any reason (paused, blacklisted user, non-standard/broken ERC20 behavior) makes `getReward` revert for every account holding a claim, and thus makes `unlock()` unconditionally revert for that account, forever (there is no bypass path or "skip this token" option, and unlike `MasterMagpie.multiclaim`, the user does not control which tokens are included — `unlock()` always calls the "claim all" branch).

### Impact Explanation
This is a direct, unprivileged-user-reachable freeze of principal funds: MGP that has already completed the mandatory cooldown period and is contractually "unlockable" becomes permanently stuck in the `VLMGP`/`mWomSV` contract, because the withdrawal path is hard-coupled to an unrelated reward-distribution side effect that has no isolation or fallback. This matches the accepted "permanent freezing of funds" / "24-hour-plus freeze" impact category, since the funds are frozen indefinitely (until/unless an admin intervenes to fix or remove the bad reward token, which is outside the affected user's control).

### Likelihood Explanation
Likelihood is non-trivial: reward tokens are added over the life of the pool via `queueNewRewards`/`donateRewards`, and any one of them permanently poisons every future `unlock()` call for every user with unlocked principal in that pool. Real-world triggers include token blacklisting (e.g., USDC/USDT-style freezes) of the pool or a specific user, a reward token contract being paused, or a bug/edge case in a reward token's `transfer` function — none of which require any privileged/malicious actor in the Magpie protocol itself, mirroring the "revert for some reason (paused, bug, lack of liquidity)" scenario that the referenced report was ultimately judged on.

### Recommendation
Decouple the mandatory reward claim from the principal unlock: either (a) wrap the `multiclaimFor` call in `unlock()`/`mWomSV` unlock in a try/catch so a reverting reward transfer cannot block release of already-vested principal, or (b) add a reward-token skip-list mechanism to `getReward`/`getRewards` (similar to EigenLayer's `indicesToSkip`) so that a single bad token can be bypassed while still paying out the rest, or (c) make the reward claim on unlock optional/separate from the principal transfer so users can call `unlock()` without triggering `getReward` at all.

### Proof of Concept
1. Protocol/manager queues a new reward token `T` into the vlMGP (or mWomSV) pool's `BaseRewarder` via `queueNewRewards` [9](#0-8) .
2. User A locks MGP, then calls `startUnlock` and waits out the cooldown.
3. Token `T` becomes non-transferable to user A for any reason (blacklist, pause, or contract bug) after having accrued a nonzero pending balance for user A in the rewarder.
4. User A calls `unlock(_slotIndex)`. `unlock()` calls `multiclaimFor` → `_claimBaseRewarder` → `getReward(A, A)`, which loops through `rewardTokens` and attempts `safeTransfer` of token `T`'s pending amount to A, reverting the whole `unlock()` call [10](#0-9) [11](#0-10) .
5. User A's already-cooled-down MGP (`slot.amountInCoolDown`) can never be withdrawn via `unlock()` as long as token `T` keeps reverting, and there is no alternative function to bypass the reward claim.

    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
