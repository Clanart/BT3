### Title
Missing exact-boundary check when reading packed primitive fields lets element decoding silently overrun the declared field length - (File: `src/google/protobuf/wire_format_lite.h`)

### Summary
The PoolTogether report's failed invariant is: a length/quantity value declared by a trusted-but-bounded actor (the promotion's allotted balance) is supposed to strictly bound what can be consumed in a loop, but the consuming loop (`claimRewards`) never re-validates that cumulative consumption stays `<=` the declared allotment, so an inaccurate per-iteration computation can consume more than was allotted and bleed into resources that belong to a different allotment. The transferable Protobuf analog is `WireFormatLite::ReadPackedPrimitive` in `src/google/protobuf/wire_format_lite.h`, which reads a length-delimited packed field by looping `while (input->BytesUntilLimit() > 0)` and calling `ReadPrimitive` each iteration, but never checks that the final read landed exactly on the declared limit rather than overrunning past it.

### Finding Description
`WireFormatLite::ReadPackedPrimitive` (used by the reflection/dynamic-message and non-tctable parsing paths for packed varint fields) is: [1](#0-0) 
```
template <typename CType, enum WireFormatLite::FieldType DeclaredType>
inline bool WireFormatLite::ReadPackedPrimitive(io::CodedInputStream* input,
                                                RepeatedField<CType>* values) {
  int length;
  if (!input->ReadVarintSizeAsInt(&length)) return false;
  io::CodedInputStream::Limit limit = input->PushLimit(length);
  while (input->BytesUntilLimit() > 0) {
    CType value;
    if (!ReadPrimitive<CType, DeclaredType>(input, &value)) return false;
    values->Add(value);
  }
  input->PopLimit(limit);
  return true;
}
```
The declared `length` establishes a "budget" for how many bytes belong to this packed field — the invariant is exactly analogous to a promotion's "allotted balance." The loop condition `BytesUntilLimit() > 0` is checked only *before* each element read, not after. A varint element can be encoded to consume more bytes than remain within the budget while still being fully present in the underlying buffer (i.e., it overruns into the *next* field's bytes but not past the physical buffer). When this happens:
- `BytesUntilLimit()` becomes negative after the read, so the loop correctly stops.
- But there is no check that the position landed *exactly* on the limit (no `ConsumedEntireMessage`-style assertion), so the function returns `true` (success) with a `value` that was decoded from bytes straddling the field boundary, and parsing resumes from a byte offset that has silently skewed past the declared field length.

This is precisely the missing "total consumed `<=` allotted budget" check called out in the PoolTogether report, transplanted to a length-delimited byte budget instead of a token balance. A regression test in the repository explicitly documents this exact hazard for packed varint fields: [2](#0-1) 
```
public void testParsePackedFieldsWithIncorrectLength() throws Exception {
    // Set the length-prefix to 1 with a 4-bytes payload to test what happens when reading a packed
    // element moves the reading position past the given length limit. It should result in an
    // InvalidProtocolBufferException but an implementation may forget to check it especially for
    // packed varint fields.
```
That test confirms the Java implementation (`ArrayDecoders.decodePackedVarint64List`) was hardened to explicitly compare the final position against the computed `fieldLimit` and throw `truncatedMessage()` if they don't match exactly: [3](#0-2) 
The C++ fast-table parser path (`EpsCopyInputStream::ReadPackedVarintWithField`/`ReadPackedVarintArrayWithField` in `parse_context.h`) similarly enforces exact matching (`return end == ptr ? ptr : nullptr;`): [4](#0-3) 

By contrast, the legacy `WireFormatLite::ReadPackedPrimitive` template (reached via reflection-based parsing, e.g. `Message::MergeFromCodedStream` on non-generated/dynamic messages, or `MergeFrom` overrides that dispatch through `WireFormat`/`WireFormatLite` rather than the generated tctable fast path) has no equivalent exact-boundary check.

### Impact Explanation
If a client sends a bounded, well-formed-looking binary Protobuf payload where a packed field's declared byte length is deliberately short relative to the encoding of its last varint element, `ReadPackedPrimitive` will:
1. Decode a value using bytes that logically belong to the *next* field in the message (an integrity failure — a value is fabricated from bytes that were never intended to represent this field), and
2. Leave the input stream's read position advanced past the declared field boundary without error, causing subsequent field parsing to desynchronize from the sender's intended layout.

This is a parsing-correctness/integrity violation on the binary wire-format parsing surface reachable by any client sending Protobuf bytes to a supported public parse API that ends up exercising this code path (dynamic message parsing / reflection-based `MergeFrom`), analogous to the PoolTogether bug where a flawed per-iteration calculation bleeds resources across a boundary that was supposed to strictly cap consumption. It does not by itself cause memory corruption (bounds are still enforced against the physical buffer via `CodedInputStream`'s own limit machinery further up), so severity should be scoped to data-integrity / parser-desync rather than memory safety.

### Likelihood Explanation
Exploitability depends on reaching `WireFormatLite::ReadPackedPrimitive` specifically — this requires a code path that doesn't go through the generated tctable/`ParseContext` fast parser (which has the exact-match check verified above), such as reflection-based dynamic message parsing. I was not able to fully confirm, within the available tooling, whether any currently-shipped generated-code or public API (e.g. `DynamicMessage::ParseFromArray`) still routes packed-varint parsing through this exact template versus always using the hardened `ParseContext` path. This uncertainty should be resolved by tracing `WireFormatLite::ReadPackedPrimitive`'s callers in `wire_format.cc`/reflection ops.

### Recommendation
Add an explicit boundary check after the loop (or after each element read) in `WireFormatLite::ReadPackedPrimitive`, mirroring the fix already applied in `ArrayDecoders.decodePackedVarint64List` and `EpsCopyInputStream::ReadPackedVarintWithField`: verify `input->BytesUntilLimit() == 0` (not merely `<= 0`) before returning `true`, and return `false` (triggering `InvalidProtocolBufferException`/truncated-message handling) otherwise.

### Proof of Concept
Using the same byte layout documented in the existing regression test (length-prefix `1` followed by a 4-byte varint payload) against a message type whose field is parsed via the legacy `WireFormatLite::ReadPackedPrimitive` path (e.g., via `DynamicMessage`/reflection-based `MergeFrom` rather than generated tctable code) would need to be constructed and run to confirm whether this specific template lacks the same exact-boundary enforcement that the Java (`ArrayDecoders`) and fast C++ (`ParseContext`) implementations already have. I did not execute this reproduction — it should be validated by a follow-up engineer with build/test access, since I could not confirm from static inspection alone which public parsing entry points still route through this specific template versus the hardened `ParseContext`/tctable path.

  static int decodePackedVarint64List(
      byte[] data, int position, ProtobufList<?> list, Registers registers) throws IOException {
    final LongArrayList output = (LongArrayList) list;
    position = decodeLengthPrefixVarint(data, position, data.length, registers);
    final int packedDataByteSize = registers.int1;
    final int fieldLimit = position + packedDataByteSize;
    while (position < fieldLimit) {
      position = decodeVarint64(data, position, registers);
      output.addLong(registers.long1);
    }
    if (position != fieldLimit) {
