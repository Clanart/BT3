### Title
Fee and weight accounting ignores the OP_RETURN data output, so `needed_fee` and the standardness check are computed for a smaller transaction than the one actually signed - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the audited issue where internal accounting is updated from a declared amount rather than the amount that actually moves, `SignableTransaction::new` computes `needed_fee`, the minimum-relay-fee check, the change amount, and the `MAX_STANDARD_TX_WEIGHT` check against a transaction that *excludes* the OP_RETURN data output that is actually added to `tx_outs`.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

1. The OP_RETURN output is pushed into `tx_outs` when `data` is present (lines 194-202).
2. `calculate_weight_vbytes` is then called with only `payments` and `change` (lines 204 and 226). The `data` output is never included in the reconstructed transaction used to compute `weight` and `vbytes`.
3. Consequently `needed_fee = fee_per_vbyte * vbytes` (line 206/227) is priced for a transaction missing up to ~90 vbytes of OP_RETURN output (`data` may be up to 80 bytes, checked at line 171).
4. The change output value is computed as `input_sat - payment_sat - fee_with_change` (line 228), so the leftover after outputs equals `needed_fee`, but the real transaction's vsize is larger than the `vbytes` used, meaning the *effective* fee rate is strictly lower than the caller-specified `fee_per_vbyte`.
5. The minimum-relay-fee check (line 211) and the `MAX_STANDARD_TX_WEIGHT` check (line 241) are also evaluated against the underestimated `weight`/`vbytes`, so both can pass for a transaction that is actually under-priced or non-standard.

### Impact Explanation
- Any `SignableTransaction` built with a `data` payload (Serai's `OutInstruction`/`InInstruction` OP_RETURN path) silently pays a lower fee rate than requested, by `fee_per_vbyte * (OP_RETURN output vsize)` satoshis. With a marginal `fee_per_vbyte` this produces a transaction that can fail relay/minimum-fee policy or sit unconfirmed, stalling protocol payouts/rotations that require timeliness.
- A transaction can pass the `TooLowFee` and `TooLargeTransaction` checks while the real signed transaction violates them, producing an invalid or non-standard transaction after the threshold signature completes — a wasted signing round and an unusable transaction.
- The accounting invariant `sum(inputs) - sum(outputs) == needed_fee` holds only for the *intended* fee, not the intended *rate*; the recorded/assumed transaction does not match the transaction actually signed.

### Likelihood Explanation
Deterministic whenever `data` is `Some` — the miscalculation is unconditional on that path, no adversary needed. The severity of the outcome depends on how close `fee_per_vbyte` is to relay minimums and how large the data payload is, so exploitation is environmental rather than attacker-crafted, consistent with a Medium.

### Recommendation
Include the OP_RETURN output in the transaction reconstructed inside `calculate_weight_vbytes` (pass the data/data-length through, or build the weight estimate from the actual `tx_ins`/`tx_outs` after all outputs — including data and change — are known). Alternatively, compute `needed_fee` and the weight/standardness checks over the final `tx` before returning the `SignableTransaction`, so the accounting always reflects the transaction that will actually be signed.

### Proof of Concept
```rust
// networks/bitcoin — conceptual PoC against SignableTransaction::new
let data = vec![0u8; 80]; // max allowed
let tx = SignableTransaction::new(inputs, &payments, change.clone(), Some(data.clone()), FEE).unwrap();

// Recompute the real vsize of tx.transaction() (includes the OP_RETURN output)
let actual_vbytes = tx.transaction().vsize() as u64;
// needed_fee was priced without the OP_RETURN output:
// actual_vbytes > needed_fee / FEE
assert!(tx.needed_fee() < actual_vbytes * FEE); // effective rate < FEE
```

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
