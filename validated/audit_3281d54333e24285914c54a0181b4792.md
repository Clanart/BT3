### Title
GitHub repository identity is bound by mutable `owner login + repo name` instead of GitHub's immutable repository ID, allowing a renamed/transferred/attacker-claimed repository to silently take over a tracked local repository's association - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
The Nested report's broken invariant is: a bookkeeping value (portfolio "power") is *credited* using one key (the depositor's chosen `ptf`) and later *debited* using a different, unverified key, because the code never confirms both operations refer to the same underlying entity. The Desktop analog of this pattern is in the code that "credits" (associates) a local `Repository` with a `GitHubRepository` record: the association is looked up and written using a mutable string pair, `(ownerID, name)` derived purely from parsing a remote URL, rather than GitHub's immutable numeric repository ID. Anyone can cause that pair to point at a different repository than the one the user originally trusted.

### Finding Description
`matchGitHubRepository` derives `owner`/`name` by parsing the remote URL string with no server-side verification beyond a hostname match: [1](#0-0) 

`repositoryWithRefreshedGitHubRepository` (app-store.ts) uses that match to call the GitHub API; if the lookup fails it falls back to `upsertGitHubRepositoryFromMatch`, which binds the local repository to whatever `GitHubRepository` DB row currently matches `(owner, name)`: [2](#0-1) 

The actual database write/lookup is keyed by `[ownerID+name]`, not by GitHub's immutable numeric repository id: [3](#0-2) 

There is no check anywhere in this path that the `GitHubRepository` row being reused/created still refers to the same underlying GitHub repository that the local `Repository` was originally cloned from — exactly the missing "same portfolio" check in the Bribes.sol report. GitHub allows repository renames, transfers, deletion, and re-creation, all of which change the "real" repository behind an `(owner, name)` pair while leaving that pair reusable by a different actor. Because Desktop's local cache is a long-lived Dexie DB (`RepositoriesDatabase`) that is never invalidated by repository ID (`// TODO: We currently never clear GitHub repository associations` at app-store.ts:4880-4882), and lookups are opportunistically keyed by the mutable pair, a `GitHubRepository` record can end up bound to a different real repository than the one that originally created it.

Downstream consumers trust this association without re-validating the numeric id:
- `findRepositoriesForGitHubRepository` matches repositories to pull-request data purely by the local `dbID` of the (possibly mis-bound) `GitHubRepository` row: [4](#0-3) 
- Branch-protection state, fork/parent target, and PR association are all derived from this same `GitHubRepository` identity, feeding into push/force-push guidance (`getNonForkGitHubRepository`, `getForkContributionTarget` in `app/src/models/repository.ts:189-221`).

### Impact Explanation
If the `(owner, name)` pair a user's local repository is bound to comes to refer to a different, attacker-controlled GitHub repository (e.g. via GitHub's own repo-transfer/rename/deletion lifecycle, or a spoofed remote/proxy response that causes `matchGitHubRepository` to resolve to attacker-chosen owner/name strings), Desktop will silently reassociate cached permissions, fork/parent relationships, and pull-request/branch-protection state with the wrong repository. This can cause Desktop to present incorrect force-push/protection warnings and misdirect fork-contribution behavior (which determines the upstream target used when creating pull requests) — i.e., silent corruption of what the app believes about where the user's work is going, without any git-level ownership check comparable to server-side push ACLs.

### Likelihood Explanation
Moderate-to-low confidence. Triggering this requires a real-world condition on the GitHub side (rename/transfer/delete-then-recreate of a repository by a different owner, sometimes called "repo-jacking") or a git remote/proxy that can influence the parsed `owner`/`name` string, both of which are attacker-influenceable but not fully attacker-controlled from a single click. The exact severity of the downstream effect (UI/permission confusion vs. a stronger primitive like credential exfiltration or arbitrary file write) could not be fully confirmed within the available code; I was not able to trace a path from this mis-association directly to code execution or token theft, only to metadata/permission-state corruption.

### Recommendation
- **Short term:** Key `GitHubRepository` lookups/upserts by GitHub's immutable numeric repository `id` (already present in `IAPIRepository`/`IAPIFullRepository`) instead of, or in addition to, `(ownerID, name)`. Detect and handle the case where an existing `(owner, name)` row's stored numeric id no longer matches the freshly-fetched API repository id, and treat that as a new repository rather than silently reusing the row.
- **Long term:** Document the assumption that `(owner, name)` is not a stable identity for a GitHub repository, add regression tests around rename/transfer scenarios, and periodically revalidate/expire stale `GitHubRepository` associations (tracked separately as desktop/desktop#1144) instead of never invalidating them.

### Proof of Concept
1. Victim clones/adds a repository `acme/widgets`; Desktop stores a `GitHubRepository` row keyed by `(ownerID for acme, "widgets")` via `upsertGitHubRepository`/`upsertGitHubRepositoryFromMatch` (`app/src/lib/stores/repositories-store.ts:530-562`).
2. The `acme/widgets` repository is later deleted or renamed on GitHub (or the remote is swapped via a compromised/misbehaving proxy), and an attacker creates a new repository at the same `owner/name` pair, or the parsed remote string otherwise coincides with a previously-tracked `(owner, name)` pair (`app/src/lib/repository-matching.ts:28-46`).
3. On the next refresh, `repositoryWithRefreshedGitHubRepository` fails to fetch by the old id/URL, falls back to `upsertGitHubRepositoryFromMatch`, finds the existing DB row for `(owner, name)`, and rebinds the victim's local `Repository` to it (`app/src/lib/stores/app-store.ts:4890-4913`).
4. Pull-request, branch-protection, and fork-contribution state now reflect the attacker's repository under the victim's local repository entry, with no numeric-id cross-check anywhere in the path.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  public async upsertGitHubRepositoryFromMatch(
    match: IMatchedGitHubRepository
  ) {
    return await this.db.transaction(
      'rw',
      this.db.gitHubRepositories,
      this.db.owners,
      async () => {
        const { account } = match
        const owner = await this.putOwner(account.endpoint, match.owner)
        const existingRepo = await this.db.gitHubRepositories
          .where('[ownerID+name]')
          .equals([owner.id, match.name])
          .first()

        if (existingRepo) {
          return this.toGitHubRepository(existingRepo, owner)
        }

        const skeletonRepo: IDatabaseGitHubRepository = {
          cloneURL: null,
          htmlURL: null,
          lastPruneDate: null,
          name: match.name,
          ownerID: owner.id,
          parentID: null,
          private: null,
        }

        const id = await this.db.gitHubRepositories.put(skeletonRepo)
        return this.toGitHubRepository({ ...skeletonRepo, id }, owner, null)
      }
    )

function findRepositoriesForGitHubRepository(
  gitHubRepository: GitHubRepository,
  repositories: ReadonlyArray<RepositoryWithGitHubRepository>
): ReadonlyArray<RepositoryWithGitHubRepository> {
  const { dbID } = gitHubRepository

  return repositories.filter(
    repository => getNonForkGitHubRepository(repository).dbID === dbID
  )
}
