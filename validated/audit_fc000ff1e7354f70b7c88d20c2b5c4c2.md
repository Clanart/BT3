### Title
OP_RETURN data output bypasses weight/vbyte accounting, defeating `TooLowFee` and `TooLargeTransaction` checks - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` appends the caller-supplied `OP_RETURN` output to `tx_outs` but computes `weight`/`vbytes` — and therefore `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` standardness check — from `calculate_weight_vbytes(inputs, payments, None)`, which only accounts for `payments` and never the data output.

### Finding Description

In `networks/bitcoin/src/wallet/send.rs`, the `OP_RETURN` output is pushed to `tx_outs` (lines 193–202) *before* the weight is calculated, yet `calculate_weight_vbytes` is invoked with only `payments` (line 204):

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds a template transaction whose `output` vector is derived solely from `payments` plus an optional change output — the `data`/`OP_RETURN` output is absent (lines 85–99). Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is underpriced by the vbytes of the omitted output (~`data.len() + 11` vbytes, up to ~91 vbytes for the allowed 80 bytes of data).
- The `TooLowFee` guard (line 211) compares against `vbytes` that excludes the data output, so a transaction whose *real* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` passes validation.
- The `TooLargeTransaction` guard (line 241) compares `weight` that likewise excludes the data output, so a transaction whose real weight exceeds `MAX_STANDARD_TX_WEIGHT` passes validation.

This is the same shape as the Carousel bug: a privileged check applied on the normal path (fee charged proportional to transaction size) is silently skipped for inputs arriving via the alternate `data` path.

### Impact Explanation

The signed transaction is committed to by all signers via `taproot_key_spend_signature_hash` with `Prevouts::All` (lines 373–390), so once completed it cannot be altered. The resulting transaction either (a) pays a fee rate lower than the rate `fee_per_vbyte` promised, potentially below the minimum relay fee, or (b) exceeds the standard weight limit. In both cases Bitcoin nodes will reject it from relay/mempool acceptance, producing a signed, unbroadcastable transaction while the scheduler has consumed those `ReceivedOutput`s — funds locked in a non-propagating spend until a replacement plan is constructed. Unlike a low-fee tx that merely confirms slowly, a sub-minimum-fee or non-standard-weight tx will never propagate.

### Likelihood Explanation

Any caller supplying `data` (the intended use is an `OP_RETURN` payload attached to a batch/plan) with a `fee_per_vbyte` near the minimum, or a payment set whose weight is near `MAX_STANDARD_TX_WEIGHT`, deterministically produces an invalid/uneconomical transaction. The `data` path is the documented mechanism for attaching out-metadata, so it is exercised by normal operation, not adversarial-only input.

### Recommendation

Include the `OP_RETURN` output (and its size) in the template transaction inside `calculate_weight_vbytes`, e.g. by passing the already-built `tx_outs` (or `data.len()`) into the weight calculation performed at line 204 and again at line 226 for the change variant, so `needed_fee`, `TooLowFee`, and `TooLargeTransaction` are evaluated against the true serialized transaction.

### Proof of Concept

```rust
// Construct payments whose weight is just below MAX_STANDARD_TX_WEIGHT,
// then pass data = Some(vec![0u8; 80]).
let stx = SignableTransaction::new(
  inputs,
  &payments,
  Some(change_script),
  Some(vec![0u8; 80]),
  fee_per_vbyte,
).unwrap();
// stx.transaction() serializes to a real transaction whose weight is
// ~89 WU higher than the `weight` used for the MAX_STANDARD_TX_WEIGHT
// check, and whose actual fee rate is ~fee_per_vbyte * real_vbytes
// worth more than `needed_fee` accounted for.
```

`fee()` (lines 138–141) still returns `needed_fee` since the fee is defined as `sum(inputs) - sum(outputs)`; the discrepancy is that the per-vbyte rate and the standardness bounds were computed for a transaction smaller than the one actually signed.
