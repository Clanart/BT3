## Binding under test

Broken binding claimed: `credited_operator(withdrawal i) == funder(payout_tx input, i.e. the operator who broadcast/fee-funded the tx that spends withdrawal_utxo i)`.

This is checked against `Verifier::update_finalized_payouts`, which sets `payout_payer_operator_xonly_pk` purely from whatever OP_RETURN data happens to be embedded in the on-chain transaction that spends the recorded withdrawal UTXO: [1](#0-0) 

## Root cause: OP_RETURN is outside the signed message

`create_payout_txhandler` builds output 0 (user payout), output 1 (anchor), output 2 (OP_RETURN with `operator_xonly_pk`), and signs input 0 with the **user's** signature via key-spend only: [2](#0-1) 

The user's signature is required (and enforced) to use `TapSighashType::SinglePlusAnyoneCanPay`: [3](#0-2) [4](#0-3) 

Per BIP-341, `SIGHASH_SINGLE | ANYONECANPAY` only commits to: the spent input's own outpoint/value/script (ANYONECANPAY), and the single output at the *same index* as that input (SIGHASH_SINGLE) — all other inputs and outputs, including the OP_RETURN output that names the credited operator, are **not covered by the signature at all**. This is confirmed by the sighash construction logic (outputs are only hashed for non-`None`/non-`Single` types, and ANYONECANPAY skips hashing all-prevouts/sequences): [5](#0-4) 

Given this, any party who observes a validly signed `input0`/`output0` pair (e.g. in the mempool once operator A broadcasts its Payout tx) can construct an entirely new transaction that:
- reuses input 0 (the withdrawal UTXO) and its existing valid witness unchanged,
- reuses output 0 (the exact signed user payout) unchanged,
- adds its own fee-paying inputs (ANYONECANPAY permits arbitrary extra inputs),
- adds an arbitrary OP_RETURN naming any real registered operator B instead of A,

and broadcast it with a higher fee to get mined first (classic SIGHASH_SINGLE|ANYONECANPAY malleability/RBF race). The signature remains valid because none of these changes touch the signed message.

## Downstream effect

`get_payout_txs_for_withdrawal_utxos` finds "the" spending tx for the recorded withdrawal UTXO purely by outpoint match, so it happily picks up the attacker's malleated tx once mined: [6](#0-5) 

`update_finalized_payouts` then stores operator B's xonly_pk as `payout_payer_operator_xonly_pk` for withdrawal `i`. Each operator's `PayoutCheckerTask` polls strictly by its own key: [7](#0-6) 

so operator B's task now sees the payout as its own and calls `Operator::handle_finalized_payout`, which creates and broadcasts a real kickoff seeking reimbursement: [8](#0-7) 

`is_kickoff_malicious` accepts B's kickoff as legitimate because it only compares the kickoff's operator key against the (already-poisoned) DB value, not against who actually funded the payout: [9](#0-8) 

Meanwhile operator A's `PayoutCheckerTask` (filtered on A's own pk) never finds this withdrawal (`payout_payer_operator_xonly_pk` is B, not A), so A can never call `handle_finalized_payout` for it — A permanently loses its Reimburse, having actually funded a transaction that got double-spent/replaced by the attacker's variant, while B is now on a false claim path exposing it to Disprove/Challenge for a payout it never made.

## Verdict

### Title
Payout OP_RETURN operator attribution is unsigned and malleable via SIGHASH_SINGLE|ANYONECANPAY, allowing credit theft/false attribution between operators - ([File: core/src/verifier.rs], [File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The Payout transaction's OP_RETURN output (which names the operator to be credited/reimbursed) is not covered by the user's `SinglePlusAnyoneCanPay` signature, so anyone observing a broadcast/mempool Payout transaction can rebuild it with the same input 0/output 0 but an arbitrary OP_RETURN naming a different, real operator, and get it mined first with a higher fee. `Verifier::update_finalized_payouts` then attributes the withdrawal to whichever operator's key appears in the winning transaction's OP_RETURN, independent of who actually funded/broadcast it.

### Finding Description
Binding claimed: `credited_operator(withdrawal i) == funder(payout tx i)`. The Payout transaction is built with 1 signed input (user's withdrawal UTXO, key-spend, `SinglePlusAnyoneCanPay`) and 3 outputs: user payout (0), anchor (1), OP_RETURN with `operator_xonly_pk` (2) — [2](#0-1) . Because the sighash flag is `SinglePlusAnyoneCanPay` — enforced by `parse_withdrawal_sig_params` — [10](#0-9)  and verified the same way by the operator — [4](#0-3)  — the signature commits only to input 0's own outpoint/value/script and to output 0; the anchor and OP_RETURN outputs, and any additional inputs, are outside the signed message. Verifiers determine the credited operator purely from parsing the OP_RETURN of the transaction that ends up on-chain spending the recorded withdrawal UTXO — [1](#0-0)  — with no cross-check to who funded/broadcast the winning transaction. An attacker who sees operator A's Payout tx (mempool, or via any other channel that leaks the signed witness) reuses input 0 + output 0 verbatim, adds their own fee input(s)/change, and substitutes an OP_RETURN naming operator B, then gets it mined first (RBF/fee race). `get_payout_txs_for_withdrawal_utxos` matches by outpoint only, so it returns the attacker's transaction as the payout for withdrawal i — [6](#0-5) . Operator B's `PayoutCheckerTask`, which filters strictly by its own xonly_pk, now finds and processes withdrawal i as its own — [7](#0-6)  — invoking `handle_finalized_payout` to build and broadcast a real kickoff — [8](#0-7) . `is_kickoff_malicious` only compares the kickoff's operator key to the DB value (which is already poisoned), not to who actually funded the spend — [9](#0-8)  — so B's kickoff is accepted as legitimate. Operator A's own `PayoutCheckerTask` never matches this withdrawal (DB row now points to B), so A can never claim it, and the withdrawal UTXO A actually paid for was consumed by the attacker's transaction, not A's.

### Impact Explanation
Operator A permanently loses its Reimburse for a payout it genuinely funded (honest operator unable to be reimbursed). Operator B is put on a false claim path: a kickoff is opened and a Reimburse pursued for a withdrawal B never funded (operator reimbursed for a payout it never made), and it also becomes exposed to Disprove/Challenge scrutiny it cannot legitimately defend since it never made the underlying payout. The attack costs the attacker only normal Bitcoin transaction fees plus an RBF fee bump, and is repeatable per withdrawal as long as at least two registered operators exist and the attacker can observe/replace a broadcast payout transaction before confirmation. This matches the Critical severity bar ("an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed").

### Likelihood Explanation
Preconditions are modest: ≥2 registered operators, and the attacker needs visibility into a not-yet-confirmed Payout transaction (trivially available via mempool monitoring) plus the ability to outbid its fee. No verifier/operator/aggregator privilege, key share, or collateral is required — only standard Bitcoin fee-market access, matching the defined unprivileged attacker capabilities exactly (broadcast transactions, choose signature/sighash flag/OP_RETURN bytes). This is a deterministic, repeatable exploit for every Payout transaction observed in the mempool prior to confirmation.

### Recommendation
Bind the operator-credit commitment to the signed message. Options: (a) require the user signature to use `AllPlusAnyoneCanPay` (or `Default`) so all outputs, including the OP_RETURN, are covered, at the cost of losing flexibility to append arbitrary fee outputs/change positions relative to that output; or (b) keep `SinglePlusAnyoneCanPay` but move the operator-attribution commitment into a value that IS covered by the SIGHASH_SINGLE-selected output (e.g., encode the operator pk as part of output 0's value/script commitment via a covenant, or require the OP_RETURN output to be exactly at index 0 co-mingled with the SIGHASH_SINGLE-committed output using an OP_RETURN+payout combined structure), or (c) require operators to pre-register the specific `(withdrawal_id, operator_xonly_pk)` intent (e.g., via an authenticated gRPC/DB commitment prior to broadcast) and have `update_finalized_payouts`/`is_kickoff_malicious` validate the on-chain OP_RETURN against that pre-registered commitment rather than trusting the mined OP_RETURN blindly.

### Proof of Concept
`cargo test` plan (mirrors the two-`MockCitreaClient`-operator scenario):
1. Set up two operators A and B backed by `MockCitreaClient`, register a deposit and withdrawal index `i`, and let operator A build and sign a valid Payout tx for its own `operator_xonly_pk` (per `create_payout_txhandler`/`Operator::withdraw`), but do not let A's tx confirm yet.
2. As the "attacker," construct a second transaction reusing A's tx `input[0]` (same outpoint + witness, unchanged) and `output[0]` (identical payout output), but with a different OP_RETURN embedding operator B's `xonly_pk`, funded by attacker-owned extra inputs/fees; broadcast it with a higher fee so it confirms first.
3. Run block sync so `Verifier::update_finalized_payouts` processes the block containing the attacker's tx.
4. Assert `db.get_first_unhandled_payout_by_operator_xonly_pk(B_pk)` returns `Some((i, ...))` and `db.get_first_unhandled_payout_by_operator_xonly_pk(A_pk)` returns `None`.
5. Assert that `PayoutCheckerTask::run_once` for operator B succeeds and calls `handle_finalized_payout`/`mark_payout_handled` for withdrawal `i`, while operator A's task returns `false` (no unhandled payout) — demonstrating credit went to B despite A having funded the original payout, and A can never reclaim it.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }
