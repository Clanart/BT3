### Title
`Scanner::scan_block` reports immature (coinbase) outputs as spendable funds — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The original bug class: a contract receives user funds but never credits/transfers them back, leaving value stranded and recoverable by unrelated parties. In Serai's Bitcoin wallet the equivalent shape is `Scanner::scan_block`, which reports *received* funds that are not actually spendable. It scans every transaction in a block including the coinbase (`block.txdata[0]`), and any miner — an unprivileged external party sending a Bitcoin transaction — can direct a coinbase output to a script the Scanner has registered. The resulting `ReceivedOutput` is indistinguishable from a normal output and is fed straight into `SignableTransaction::new`, which builds a transaction spending it. Consensus rejects spending coinbase outputs until they reach 100-block maturity, and a coinbase output orphaned before maturity never becomes spendable at all — yet it was already reported as received value.

### Finding Description
- `Scanner::scan_block` iterates `block.txdata` with no special-casing of the coinbase transaction and no maturity/confirmation tracking: `networks/bitcoin/src/wallet/mod.rs:221-227`.
- `scan_transaction` matches purely on `script_pubkey` membership in `self.scripts` (`mod.rs:199-214`), so a coinbase output paying to the Serai key (or any registered offset) yields a `ReceivedOutput` carrying `offset`, `TxOut`, and `OutPoint`.
- `ReceivedOutput` exposes `value()` and is the exact input type of `SignableTransaction::new` (`send.rs:150-156`), which validates only amounts/dust/fees — never input maturity. A `SignableTransaction` built over an immature coinbase will be signed by the FROST flow and broadcast, then rejected by the network (`bad-txns-premature-spend-of-coinbase`).
- The only mitigation is a doc comment on `scan_block` stating a "post-processing pass is needed" — the API itself provides no flag distinguishing coinbase outputs, so every consumer of `scan_block` receives them as ordinary spendable inputs. If the block is orphaned before maturity, the reported output is destroyed entirely: funds were reported received that can never be spent.

### Impact Explanation
Funds are credited as received (`ReceivedOutput` produced by the scanner) that are not spendable: spending a coinbase before 100 confirmations is a consensus violation, and an orphaned coinbase never exists. Downstream scheduling treats these as valid inputs, producing transactions that can never confirm — the value is effectively stranded exactly as in the reference bug, where tokens sit in the contract uncredited. A miner can trigger this deliberately by pointing a coinbase payout at a registered script.

### Likelihood Explanation
Reachable by any unprivileged miner who can observe Serai's script (all received outputs are to publicly known script_pubkeys) and wins a block. Probability of an organic miner paying a random external script is low, but a motivated miner can do it deterministically whenever they mine a block, making exploitation reliable for them though opportunistic.

### Recommendation
In `Scanner::scan_block`, either skip `block.txdata[0]` or mark coinbase-derived `ReceivedOutput`s so consumers can require 100 confirmations before scheduling them as inputs to `SignableTransaction::new`. Alternatively add a maturity check at input-selection time using the output's block height.

### Proof of Concept
1. A miner registers knowledge of Serai's scanned `script_pubkey` (public on-chain).
2. The miner constructs a block whose coinbase pays `x` sats to that script and broadcasts it.
3. `Scanner::scan_block(&block)` returns a `ReceivedOutput` for the coinbase output (`mod.rs:221-227`, via `scan_transaction` at `mod.rs:199-214`).
4. `SignableTransaction::new(vec![received], &payments, change, None, fee)` succeeds — there is no maturity check (`send.rs:150-256`).
5. The threshold-signed transaction is rejected by consensus for spending an immature coinbase; if the block is orphaned, the reported funds vanish entirely despite having been credited as received.

Note: the doc comment on `scan_block` (`mod.rs:216-220`) acknowledges that coinbase outputs "are bound by maturity" and need post-processing — this documents the hazard but does not enforce it; whether downstream consumers (out of in-scope code) perform that pass could not be fully verified within available iterations, which is the main residual uncertainty in this finding.
