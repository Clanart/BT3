### Title
Unauthenticated blame lets any party mark an innocent DKG recipient as faulty, aborting the protocol - (File: crypto/dkg/pedpop/src/lib.rs + crypto/dkg/pedpop/src/encryption.rs)

### Summary
The InLong issue (CWE-552, canceling an object that doesn't belong to the caller) maps onto Serai as **performing a blame accusation on a sender→recipient relationship the accuser is not part of**. `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept a caller-chosen `(sender, recipient, EncryptedMessage, Option<EncryptionKeyProof>)` tuple with no binding of the accusation to the actual recipient. Whenever the message's proof-of-possession is valid and `proof` is `None`, `blame_internal` unconditionally returns the `recipient` as the faulty party — so any observer can "file" someone else's accusation and have an honest participant declared faulty.

### Finding Description
`BlameMachine::blame` delegates to `blame_internal`, which calls `Decryption::decrypt_with_proof` [1](#0-0) . In `decrypt_with_proof`, a valid `msg.pop` Schnorr signature (verified against a challenge that binds only `sender`, the ephemeral key, and the ciphertext — never `recipient`) is followed by: if `proof` is `Some`, verify the DLEq and decrypt; if `proof` is `None`, return `Err(DecryptionError::InvalidProof)` [2](#0-1) . `blame_internal` maps `InvalidProof` to `return recipient`, i.e., the *recipient* is declared the faulty party whenever the accusation lacks a valid key proof [3](#0-2) .

Two injection paths exist for an unprivileged accuser:

1. **Replayed message**: any `EncryptedMessage` observed on the wire (an encrypted secret share is broadcast/routed publicly) has a valid `pop` for its true `sender`. Passing it to `blame(sender, recipient, msg, None)` instantly pins blame on `recipient`, since `proof = None` → `InvalidProof` → `recipient`.
2. **Forged message**: the `pop` challenge binds only `sender`, `key`, `nonce`, `msg` [4](#0-3) . The `pop` is a Schnorr signature under the *ephemeral* `msg.key`, which the creator knows. An attacker can mint a fresh `EncryptedMessage` whose PoP verifies while claiming an arbitrary `from` — there is no check that `sender` actually produced the message, and no check that the *caller* of `blame` is `recipient` (the only legitimate accuser). `blame` takes all four arguments verbatim [5](#0-4) .

Either way, `blame` returns an arbitrary honest `recipient` as faulty — performing a destructive action (an accusation that forces protocol abort) on a sender/recipient pairing the caller does not own, exactly the "act on another user's application" class from the InLong report.

### Impact Explanation
`blame`'s result is a `Participant` returned to the integrator as the faulty party; per its docs the protocol must abort on any blame [6](#0-5) . In the Serai deployment, DKG blame feeds validator-fault reporting (the same processor stack produces `SignSlashReport` slash requests). A false accusation therefore:

- marks an honest participant as the faulty/lying party, potentially getting them excluded from the produced multisig or slashed;
- aborts key generation/rotation at will (liveness), attributable to victims rather than the attacker — a framing attack, not just DoS.

This is "key share recovery / forged claim against a participant" severity: **Medium–High**. It is not a no-impact DoS because blame is the mechanism that decides who is punished.

### Likelihood Explanation
The attacker needs only (a) a copy of any `EncryptedMessage` — these travel between participants and are observable, or the attacker can forge one since the PoP key is self-generated — and (b) the ability to submit a blame accusation, which is exactly what `blame` exists to process from untrusted input (`EncryptedMessage::read` bytes). No secret knowledge, valid shares, or collusion is required; the code path deterministically returns `recipient` whenever the PoP verifies and `proof` is `None` [7](#0-6) . Likelihood: high, gated only by the deployment's ability to route an accusation.

### Recommendation
Bind the accusation to the accuser and the message to its intended recipient:

1. In `pop_challenge` / `encrypt`, also append `b"recipient"` (`to`) so the PoP commits to the intended decryptor; then `decrypt_with_proof`/`blame` must reject messages whose `recipient` field doesn't match the accused pair.
2. Require `blame` to authenticate that the accuser *is* `recipient` — e.g., accept only a `proof`/`EncryptionKeyProof` produced by `recipient`'s `decrypt` (which is bound to `recipient`'s registered `enc_key` via `self.enc_keys[&decryptor]` [8](#0-7) ), and treat `proof = None` accusations about a well-formed message as *accuser-faulty*, not `recipient`-faulty. Today `None` provably yields `recipient`, which inverts blame onto an innocent party.
3. Alternatively, refuse `blame` for messages where `sender`/`recipient` were not authenticated by the caller as a genuine pair in this session.

### Proof of Concept
```rust
// 5-of-3 PedPoP. Alice=1 sends Bob=2 a valid encrypted share.
// Mallory (any observer / participant) observed the wire bytes.
let msg_bytes: Vec<u8> = /* observed or attacker-constructed EncryptedMessage bytes */;
let msg = EncryptedMessage::<Ristretto, SecretShare<_>>::read(
  &mut msg_bytes.as_slice(),
  ThresholdParams::new(3, 5, Participant::new(2).unwrap()).unwrap(),
).unwrap();

// Mallory submits an accusation naming Bob as accuser, with NO key proof.
// pop.verify succeeds (valid ephemeral-key sig, binds only `sender`).
// proof = None => DecryptionError::InvalidProof => blamed = recipient (Bob).
let (_additional, blamed) =
  blame_machine.blame(Participant::new(1).unwrap(), Participant::new(2).unwrap(), msg, None);
assert_eq!(blamed, Participant::new(2).unwrap()); // innocent Bob blamed

// Even a fabricated message works: attacker picks k, sets msg.key = k*G,
// signs pop_challenge(context, R, msg.key, /*from=*/ Alice, msg) with k —
// the challenge never authenticates `sender` against a long-lived key.
```
Root cause: `blame` consumes attacker-supplied `(sender, recipient, msg, proof)` and maps the `proof: None` branch to `recipient`-faulty without any proof the accuser is `recipient` or that `msg` was addressed to them [1](#0-0) [2](#0-1) .

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
