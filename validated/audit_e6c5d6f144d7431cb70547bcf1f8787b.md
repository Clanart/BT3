## Analysis

The Trader Joe bug's core invariant is: **when a function accepts more native value than required for an internal operation, the excess must be returned to the original sender — if the refund path is broken or missing, user funds get trapped/lost.**

Searching Hyperbridge's EVM contracts for the equivalent "accept native value → perform internal cost calculation → refund excess" pattern turned up multiple correctly-guarded implementations in `IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, `IntrinsicIntents.sol`, and the Uniswap wrapper contracts — all of which capture the swap's actual spend and explicitly forward the remainder back to `msg.sender`. However, `EvmHost.sol`'s own fee-payment swap calls do **not** follow this pattern.

### Title
Native token overpayment on `EvmHost.dispatch()`/`fundRequest()` is silently trapped instead of refunded to the payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all let a caller pay the protocol fee in native token by internally swapping via Uniswap V2's `swapETHForExactTokens`. Unlike every other native-fee-swap call site in this codebase (`IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, `IntrinsicIntents.sol`), these three functions discard the swap's return value and contain no logic to return unspent native token to the caller. ### Finding Description
Uniswap V2's `swapETHForExactTokens` internally refunds any unused `msg.value` (dust ETH beyond the exact amount needed) back to the immediate caller of the router — which in this call chain is `EvmHost` itself (`address(this)` is passed as `to`, but the ETH dust refund goes to `msg.sender` of the router call, i.e. `EvmHost`). None of the three `EvmHost` functions capture the swap's `amounts` return value or use it to compute and forward any leftover `msg.value` back to `_msgSender()`.

Contrast this with the correct pattern used elsewhere in the same codebase, where the actual amount spent is captured and the true leftover balance is explicitly sent back to the original payer: [4](#0-3) 

In `EvmHost.sol`, any native token sent by a user in excess of `post.fee`/`get.fee`/`amount` is swapped away as dust, refunded by the router into `EvmHost`'s own contract balance, and then never returned to the caller — the excess balance sits in the contract with no corresponding accounting/withdrawal path back to that specific user.

### Impact Explanation
This matches the "Bridged assets ... must move exactly once and only to the rightful beneficiary and amount" pivot. Any user calling `dispatch()` or `fundRequest()` with `msg.value` greater than the swap's actual cost permanently loses that excess — it becomes untracked ETH sitting in the `EvmHost` contract, unattributed to any specific depositor and with no self-service reclaim mechanism visible in this function. This is a direct fund-loss condition reachable by any unprivileged caller through a normal public entrypoint, exactly the pattern the external Trader Joe report flags (excess-value handling on a payable swap-wrapping function is broken), except here the failure mode is silent fund loss rather than a revert.

### Likelihood Explanation
High likelihood of accidental triggering: any front-end or integrator that (reasonably, given the docstring "Payment for the request can be made with either the native token or the feeToken") pads `msg.value` for slippage/safety margin when funding a POST/GET request or topping up a fee via `fundRequest` will lose the padding amount with no error or revert to warn them, since the call succeeds. No malicious relayer, prover, or governance actor is required — an ordinary user overpaying will trigger the loss.

### Recommendation
Capture the return value of `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund the difference between `msg.value` and the actual amount spent back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: 2 ether}(post)` where `post.fee` only requires the ETH-equivalent of 0.1 ether worth of `feeToken`.
2. `swapETHForExactTokens{value: 2 ether}(post.fee, path, address(this), block.timestamp)` executes; the router spends ~0.1 ether swapping for the exact fee token amount and refunds the ~1.9 ether dust back to `msg.sender` of the router call, i.e. `EvmHost` itself.
3. `dispatch()` returns normally, the request commitment is recorded, and the 1.9 ether dust remains stuck in `EvmHost`'s balance — it is never sent back to the original caller, and there is no per-user accounting of it in `_requestCommitments` or any other mapping that would let that specific user reclaim it.
