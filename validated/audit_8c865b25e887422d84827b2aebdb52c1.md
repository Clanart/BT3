Based on my investigation, I found a concrete local analog: `_paused` is declared in `IntentsBase.sol` but is never checked anywhere in the entire IntentGateway/intentsv2 codebase — neither `placeOrder`, `fillOrder`, `select`, `cancelOrder`, nor `onAccept`/`onGetResponse` gate on it. [1](#0-0) 

### Title
`_paused` state variable in IntentGatewayV2 is never enforced, making the pause kill-switch a no-op — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase` declares a `bool public _paused` storage slot, explicitly appended "to preserve existing storage slots," implying it was intended to gate order lifecycle functions (`placeOrder`, `select`, `fillOrder`, `cancelOrder`) during an incident. However, no function in `IntentsBase.sol`, `IntrinsicIntents.sol`, or `ExtrinsicIntents.sol` reads `_paused`. Every fund-moving entrypoint remains fully callable regardless of its value.

### Finding Description
`_paused` is declared as a state variable at [1](#0-0)  with a comment indicating it was appended to an existing struct layout for a future/emergency pause mechanism, analogous to `notSuspended`/`whenNotPaused` guards used elsewhere in the codebase (e.g., `HyperFungibleTokenUpgradeable.transfer`/`transferFrom` use `whenNotPaused` at [2](#0-1) , and `EvmHost` has an equivalent `notFrozen`/`FrozenStatus` guard at [3](#0-2) ).

A full grep across the repo confirms `_paused` is referenced only in its declaration — it is never read in any modifier, `require`, or conditional in `IntentGatewayV2.sol`, `IntrinsicIntents.sol`, or `ExtrinsicIntents.sol`. Concretely:
- `placeOrder` in `IntentGatewayV2.sol` escrows user funds unconditionally.
- `_fillSameChain` and `_fillCrossChain` release escrow and transfer solver/user funds unconditionally [4](#0-3) [5](#0-4) .
- `onAccept` processes `RedeemEscrow`/`RefundEscrow`/`SweepDust`/`UpgradeContract` messages unconditionally [6](#0-5) .

This is the direct structural analog of the Symmetrical bug: a suspension/pause flag exists to restrict fund movement in an emergency, but the enforcement was only wired into some paths (or, here, into none at all), so the "restricted" state can be bypassed entirely via the normal, unprivileged entrypoints.

### Impact Explanation
If governance (Hyperbridge, via `UpdateParams`/future logic) or an operator ever sets `_paused = true` — whether manually via a storage write during an incident response, via a future upgrade that adds a setter, or if it's simply assumed by monitoring/ops tooling to be an effective circuit breaker — the flag provides no actual protection. An attacker exploiting a live incident (e.g., a compromised price oracle, a bug in fill/settlement logic, or a malicious call dispatched through `postdispatch`) could continue to `placeOrder`/`fillOrder`/trigger `onAccept` withdrawals and drain escrowed funds even while the protocol believes the gateway is paused. This maps to "unauthorized transaction/execution" and "stealing or loss of funds" under the bounty's impact gate, since the broken invariant is that a declared circuit-breaker fails to stop fund movement through the public entrypoints.

### Likelihood Explanation
The variable's very existence and its comment ("Appended last to preserve existing storage slots") strongly imply an intended enforcement that is currently missing from the deployed/reviewed code — this is a real code defect, not a hypothetical. Any unprivileged user can continue calling `placeOrder`/`fillOrder`/`cancelOrder`/`select` regardless of the pause flag's value, with zero additional preconditions (no malicious relayer, prover, or admin needed).

### Recommendation
Add an explicit `whenNotPaused` modifier (checking `_paused`) to all fund-moving IntentGateway entrypoints — `placeOrder`, `select`, `fillOrder` (same-chain and cross-chain), `cancelOrder`, and the `onAccept`/`onGetResponse` withdrawal paths — mirroring the pattern already used in `HyperFungibleTokenUpgradeable`. Also add the corresponding governance-gated setter (`RequestKind.SetPaused` or similar) if one does not already exist elsewhere in the deployed contract, and add regression tests asserting reverts on all lifecycle functions when `_paused == true`.

### Proof of Concept
1. Assume governance (or an emergency ops process) sets `_paused = true` on a deployed `IntentGatewayV2` proxy, believing this halts new orders/fills during an active incident (e.g., a compromised price oracle skewing surplus calculations, or a discovered bug in escrow accounting).
2. An attacker (or any unaffected user) calls `placeOrder(...)` — succeeds, funds are escrowed, because no function checks `_paused`.
3. A colluding/attacker-controlled solver calls `fillOrder(...)` — succeeds, escrow is released and cross-chain `RedeemEscrow`/`RefundEscrow` messages are dispatched, because `_fillSameChain`/`_fillCrossChain` and `onAccept` never check `_paused`.
4. Funds move through the gateway exactly as in normal operation, defeating the intended emergency stop and enabling continued exploitation of whatever incident prompted the pause.
