### Title
Copilot conflict-resolution apply path writes a stale content snapshot, silently discarding edits made to a conflicted file while resolution is in flight - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes `resolution.resolvedContent` to disk for every conflicted file the user hasn't manually overridden. `resolvedContent` is produced earlier by `reassembleResolutions`/`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` by splicing the model's per-hunk output into `ctx.rawContent` — a one-time snapshot of the file taken when Copilot's context was gathered, *not* the file content at the moment the user clicks "Continue Merge". The only staleness guard before writing is "is this file still reported as conflicted with unresolved markers", which does not detect a file that a user partially edited but that git still reports as conflicted. [1](#0-0) [2](#0-1) 

### Finding Description
The broken invariant mirrors the external report exactly: an internally cached/derived value (`resolvedContent`, computed from a point-in-time snapshot, analogous to the contract's internally tracked balances) is applied against the *real*, potentially-changed state (the on-disk conflicted file, analogous to the real Curve LP balances after a trade) without re-validating that the snapshot still matches reality.

Concretely:
- `reassembleResolutions` builds the final `resolvedContent` from `ctx.rawContent`, the file content captured when the AI gathering step ran [3](#0-2) .
- Resolution generation is asynchronous and can take a while — the code itself tracks and reports elapsed time over 60s/120s [4](#0-3) , i.e., the window between snapshot and apply is expected to be non-trivial.
- When the user finally clicks "Continue Merge", `_applyCopilotConflictResolutions` only skips writing if the file is *no longer* reported as conflicted at all (`isConflictedFileStatus && !hasUnresolvedConflicts`) [5](#0-4) . If the user (or a tool, editor auto-format, another git operation, or a colliding rebase/cherry-pick step) modifies the file's content *within* the still-present conflict markers — or otherwise touches the file while it's still flagged conflicted — the guard does not fire, and the stale `resolvedContent` from the earlier snapshot is written verbatim over the current file [6](#0-5) .
- The write path then unconditionally stages the file with `git add` [7](#0-6) , so the stale content flows directly into what gets committed.

This is structurally identical to the `USDMPegRecovery` bug: a value computed once (deposit accounting / resolved file content) is trusted at a later point in time without re-deriving it against the authoritative live state (real LP balances / real on-disk file), and the only check performed (balance non-negativity / "no remaining conflict markers") is too coarse to catch the actual divergence.

### Impact Explanation
This results in silent corruption of what the user commits — one of the explicitly valid impact classes. A user's legitimate in-progress edits to a conflicted file (made while Copilot's multi-file/multi-chunk resolution run, which can take over two minutes per the app's own instrumentation, is still executing or awaiting confirmation) can be silently overwritten and then staged and committed, without any warning that their edit was discarded. Because the overwrite happens right before `git add` in the same flow that finalizes the merge/rebase/cherry-pick step, the corrupted content becomes part of the resulting commit, and by the time the user notices (if ever), the merge operation has already completed.

### Likelihood Explanation
No unnatural steps or elevated privileges are required: any user who enables Copilot conflict resolution during a merge/rebase and edits a still-conflicted file in an external editor while the (multi-second-to-multi-minute) resolution run is in progress — a normal, foreseeable workflow the code's own comments anticipate ("If the user resolved this file externally... while the result dialog was open") — hits this path. The guard was clearly written with exactly this scenario in mind but only covers the "fully resolved" case, not "partially edited but still marked conflicted," leaving a gap in the same class of race the comment tries to close.

### Recommendation
Before writing `resolution.resolvedContent`, re-read the current on-disk file and compare it (e.g., via hash) against the `rawContent` snapshot that was used to generate the resolution. If the current content differs from the snapshot in any way — not just "conflicts fully resolved" — skip the write (or re-prompt the user) exactly as is already done for the fully-resolved case, so any user modification made after the snapshot was taken is never silently discarded.

### Proof of Concept
1. Start a merge/rebase with conflicts in a repository; enable Copilot conflict resolution (`useCopilotConflictResolution`).
2. While Copilot is generating resolutions (observably slow for larger diffs — the app tracks and reports resolution times over 60–120s), open the still-conflicted file in an external editor and manually adjust content inside the conflict markers (leave the markers in place, or otherwise leave the file in a state git still reports as conflicted).
3. Wait for Copilot's result dialog and click "Continue Merge" without further edits in Desktop.
4. `_applyCopilotConflictResolutions` finds the file still `isConflictedFileStatus` with `hasUnresolvedConflicts` true (guard does not trigger), and writes the stale `resolution.resolvedContent` computed from the pre-edit snapshot, discarding the manual edit, then stages it with `git add` [8](#0-7) .
5. The subsequent commit contains the stale, AI-generated content instead of the user's actual intended edit, with no error or warning surfaced.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
