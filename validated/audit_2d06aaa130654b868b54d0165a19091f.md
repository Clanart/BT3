### Title
Permissionless `IMasterWombat.depositFor` front-run drains WOM rewards before `WombatStaking._toMasterWomAndSendReward` diff-check, permanently stranding rewards - (`wombat/WombatStaking.sol`)

### Summary
`WombatStaking._toMasterWomAndSendReward` uses a balance-before/balance-after pattern to determine how much WOM (and bonus tokens) were harvested from MasterWombat, exactly like the ConvexRewardsAdapter pattern described in H-16. Because `IMasterWombat` exposes `depositFor(uint256 pid, uint256 amount, address account)`, which lets **any address** trigger a deposit/harvest for **any account** (including `WombatStaking` itself), an attacker can call it with `amount = 0` to force MasterWombat to pay out `WombatStaking`'s pending WOM rewards directly to the `WombatStaking` contract address, outside of the accounted flow. The legitimate flow (`depositLP`, `withdraw`, `harvest`) will then measure a `womBeforeBalance`/`womRewards` diff of (near) zero for that portion, so the harvested tokens never reach `_sendRewards` and stay stuck in the contract forever.

### Finding Description
`_toMasterWomAndSendReward` computes the harvested WOM/bonus amounts purely from balance deltas taken immediately before invoking MasterWombat: [1](#0-0) 

```solidity
function _toMasterWomAndSendReward(address _lpToken, uint256 lpAmount, bool _isStake) internal {
    ...
    uint256 womBeforeBalance = IERC20(wom).balanceOf(address(this));
    uint256[] memory beforeBalances = _rewardBeforeBalances(_lpToken);

    if(_isStake)
        _stakeToWombatMaster(_lpToken, lpAmount); // triggers harvest from wombat exchange
    else
        IMasterWombat(masterWombat).withdraw(poolInfo.pid, lpAmount); // triggers harvest from wombat exchange
    uint256 womRewards = IERC20(wom).balanceOf(address(this)) - womBeforeBalance;
    _sendRewards(_lpToken, wom, poolInfo.rewarder, womRewards);
    ...
}
```

This code assumes the only way WOM lands on the `WombatStaking` contract's balance is through the `deposit`/`withdraw` call it just made. However, `IMasterWombat` also exposes `depositFor`, which lets any external caller deposit (even zero amount) on behalf of an arbitrary `account`, and MasterWombat-style contracts pay out pending rewards to that account as part of the deposit/withdraw flow: [2](#0-1) 

```solidity
function depositFor(uint256 pid, uint256 amount, address account) external;

function deposit(uint256 _pid, uint256 _amount) external returns (uint256, uint256);

function withdraw(uint256 _pid, uint256 _amount) external returns (uint256, uint256);
```

Because `depositFor` takes an explicit `account` argument rather than implicitly using `msg.sender`, any unprivileged wallet can call `masterWombat.depositFor(pid, 0, address(WombatStaking))` at any time. This causes MasterWombat to flush `WombatStaking`'s pending WOM reward directly into the `WombatStaking` contract's own token balance, completely bypassing `_sendRewards`/`_toMasterWomAndSendReward`'s accounting. When `WombatStaking` itself later calls `depositLP`, `withdraw`, or `harvest` (which invoke `_toMasterWomAndSendReward`), the `womBeforeBalance` snapshot already includes the attacker-injected tokens, so `womRewards` (the diff) is at or near zero for the amount that was front-run, and those WOM tokens are never routed to `poolInfo.rewarder` via `_sendRewards`.

### Impact Explanation
The stranded WOM tokens sit in the `WombatStaking` contract balance permanently: they were never credited to `_sendRewards`, so they can never be pulled out through the pool's rewarder to user stakers, matching the "rewards stuck" impact described in H-16. Because MasterWombat has already recorded the reward as paid to the `WombatStaking` position, no future harvest call will re-surface this amount — it is a permanent freeze of unclaimed yield belonging to LP stakers in the affected Wombat pool(s), reachable by any ordinary wallet with no special privileges.

### Likelihood Explanation
Any unprivileged address can call `depositFor` on the public MasterWombat contract for the known `WombatStaking` address and any registered `pid`, at zero cost beyond gas, with no requirement to hold a position or authorization check restricting the `account` parameter to `msg.sender`. This can be repeated for every pool/asset harvested by `WombatStaking`, making the DOS trivially and repeatedly executable.

### Recommendation
Do not rely on `balanceOf` deltas taken only around the specific `deposit`/`withdraw` call in `_toMasterWomAndSendReward`/`_sendRewards`. Instead, track rewards using MasterWombat's `pendingTokens`/harvested-amount return values (e.g., use the returned amounts from `deposit`/`withdraw` calls, which report harvested rewards directly) rather than pre/post balance snapshots, or reconcile the full current `balanceOf(address(this))` each harvest so any externally injected balance is still routed to `_sendRewards` instead of being silently absorbed into the "before" baseline.

### Proof of Concept
1. `WombatStaking` holds a staked LP position in MasterWombat for `_lpToken` with `poolInfo.pid`, accruing pending WOM rewards.
2. Attacker (any wallet) calls `IMasterWombat(masterWombat).depositFor(poolInfo.pid, 0, address(WombatStaking))`. MasterWombat harvests the pending WOM for that position and transfers it to `WombatStaking`'s token balance directly (bypassing `WombatStaking`'s own code path).
3. Later, a legitimate user interaction triggers `WombatStaking.depositLP`/`withdraw`/`harvest`, which calls `_toMasterWomAndSendReward`. It snapshots `womBeforeBalance` (already including the attacker-injected WOM from step 2) then calls `deposit`/`withdraw` on MasterWombat again.
4. Since the position's pending WOM was already paid out in step 2, the new call yields little or no additional WOM, so `womRewards = balanceAfter - womBeforeBalance` is ~0, and `_sendRewards` forwards ~0 to `poolInfo.rewarder`.
5. The WOM tokens injected in step 2 remain in `WombatStaking`'s balance indefinitely, never reaching the rewarder or stakers — a permanent freeze of protocol yield, repeatable by the attacker for every pool.
