### Title
DataLayer Mirror URLs Enable Semi-Blind SSRF via Unvalidated HTTP Fetch in `http_download` - (File: chia/data_layer/download_data.py)

### Summary
Chia's DataLayer subscription/sync mechanism fetches store delta files from mirror server URLs that are supplied by the store owner (and propagated on-chain as coin data), and any DataLayer node that subscribes to that store id will download from those URLs with no validation of scheme, host, or destination network. This mirrors the OpenCTI SSRF bug class: an unvalidated, user-controlled URL is fed to an HTTP client with default behavior of following/accepting arbitrary absolute URLs, letting a wallet/DataLayer participant coerce another node into issuing requests to arbitrary internal or cloud-metadata endpoints.

### Finding Description
DataLayer's periodic sync loop calls `fetch_and_validate()` on `DataLayer`, which iterates `servers_info` (mirror URLs discovered via wallet mirror coins/subscription entries) and calls `insert_from_delta_file()` → `download_file()` → `http_download()`.

`http_download()` builds a request directly from `server_info.url` with no allow-list/deny-list, no scheme restriction, and no check against private/link-local/metadata address ranges: [1](#0-0) 

The URL that ends up in `server_info.url` is sourced from mirror subscriptions synced from wallet state (`update_subscriptions_from_wallet`), which stores whatever URL string is associated with a mirror coin for a given store id, with no host/format validation beyond DB persistence: [2](#0-1) 

`fetch_and_validate()` picks a random eligible server and triggers the download without any host restriction: [3](#0-2) 

The context doc for this module explicitly documents that "Plugin and mirror URLs are external trust inputs," and only the *downloaded data* is verified against the wallet-advertised Merkle root — the network destination of the request itself is never validated: [4](#0-3) [5](#0-4) 

Since mirror coins are created on-chain by any DataLayer store owner (a store creator who wants replication publishes a mirror URL that becomes visible to and consumed by any peer/subscriber node's `DataLayer` service), an attacker who controls a store (any unprivileged wallet user can create a DataLayer store/singleton) can set the mirror URL to point at internal infrastructure (e.g. `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:6379/`, or an internal RabbitMQ/Elasticsearch-style admin endpoint reachable from the victim's host) and wait for victim nodes to subscribe to that store id and run their normal sync loop.

### Impact Explanation
Any node running the DataLayer service that subscribes to (or auto-syncs) a store controlled by an attacker will have its `DataLayer` process issue outbound HTTP(S) `GET` requests to an attacker-chosen URL/host — including internal-only services or cloud metadata endpoints — as part of routine, unattended background sync (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`). This is a semi-blind SSRF: the victim process does not directly return response bodies to the attacker, but any observable side effect (timing, error class differences from `MaxDeltaFileSizeExceededError`/`ClientError`/timeout, subsequent behavior, or file content when the "response" happens to look like a valid delta file) leaks information about reachability/availability of internal endpoints, and, depending on internal service behavior (e.g., unauthenticated internal admin APIs), can enable further compromise. This lines up with the CWE-918/CWE-20 class in the reported advisory and matches the "Data Layer client" reachable analog explicitly listed as in-scope.

### Likelihood Explanation
Likelihood is high for a determined attacker: creating a DataLayer store and mirror coin is a normal, unprivileged wallet-user action; no special permissions or network position are required. The victim side effect (background sync fetching mirror URLs) is fully automatic once a node subscribes to (or is auto-subscribed via mirror discovery for) the malicious store id — no additional user interaction is required beyond normal DataLayer usage patterns (subscribing to a store id, which is a standard workflow for DataLayer consumers).

### Recommendation
Validate and restrict mirror/server URLs before they are used for outbound HTTP requests in `http_download()`/`download_file()`/`get_downloader()`: enforce an allow-list of schemes (`https`/`http` only, ideally requiring TLS), resolve and reject requests to private/loopback/link-local/multicast/reserved IP ranges and known cloud metadata addresses (defense against DNS rebinding by re-checking the resolved IP at connect time, not just the hostname), and consider making SSRF protections configurable (e.g. via a strict egress proxy) similar to hardened HTTP client configurations recommended for the analogous OpenCTI fix (disable `allowAbsoluteUrls`-equivalent unrestricted absolute URL handling; add explicit destination validation instead of relying solely on post-download content/root verification).

### Proof of Concept
1. As an unprivileged wallet user, create a DataLayer store (`create_new_dl`) and commit a batch with `submit_on_chain=True`.
2. Use the DataLayer mirror-creation RPC flow to associate a mirror URL with the store's launcher id, setting the URL to an internal/target address, e.g. `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://<victim-internal-host>:<port>/`.
3. Get a victim DataLayer node to subscribe to the store id (`subscribe`), which is standard DataLayer client behavior for anyone wanting to replicate/read that store's data.
4. Observe that the victim's `DataLayer.fetch_and_validate()` → `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py:298-319`) issues an HTTP GET to the attacker-controlled URL with no host validation, as part of its normal, unattended `periodically_manage_data()` sync loop — this can be confirmed by pointing the mirror URL at a controlled listener and observing the inbound request originating from the victim node's IP.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()

                "SELECT * FROM subscriptions WHERE from_wallet == 0 AND tree_id == :tree_id",
                {
                    "tree_id": store_id,
                },
            )
            from_subscriptions_urls = {row["url"] async for row in cursor}
            additions = {url for url in new_urls if url not in old_urls}
            removals = [url for url in old_urls if url not in new_urls]
            for url in removals:
                await writer.execute(
                    "DELETE FROM subscriptions WHERE url == :url AND tree_id == :tree_id",
                    {
                        "url": url,
                        "tree_id": store_id,
                    },
                )

                    await writer.execute(
