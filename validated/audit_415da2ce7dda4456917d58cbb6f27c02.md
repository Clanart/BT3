### Title
Unrestricted slippage tolerance in `WombatPoolHelperV2.depositFor()` enables sandwich-attack theft of depositor funds - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2.depositFor(uint256 _amount, address _for)` pulls `depositToken` from `msg.sender` and deposits it into the Wombat AMM pool via `WombatStaking.deposit()`, but hardcodes the slippage-protection parameter `_minimumLiquidity` to `0` instead of exposing it as a caller-supplied argument, unlike the sibling `deposit()` function.

### Finding Description
`deposit(uint256 _amount, uint256 _minimumLiquidity)` lets the caller specify a minimum LP amount they are willing to accept: [1](#0-0) 

But `depositFor`, which performs the identical underlying operation (pulling ERC20 tokens and depositing them via `WombatStaking.deposit`), forces `_minimumLiquidity` to `0`: [2](#0-1) 

This `0` is passed straight through the internal helper into `WombatStaking.deposit`, which forwards it unmodified as `minimumLiquidity` to the external `IWombatPool.deposit()` call: [3](#0-2) [4](#0-3) 

Because the Wombat stableswap pool's minted-liquidity amount depends on the pool's current cash/liability ratio (an AMM invariant that any unprivileged address can move by swapping against the pool), an MEV searcher can front-run a `depositFor` call by skewing the pool ratio unfavorably, let the victim's deposit mint an amount of LP/receipt tokens far below fair value (since `minimumLiquidity = 0` can never revert), and then back-run to restore the ratio, capturing the difference as arbitrage profit extracted directly from the depositor's principal. This directly matches the "unrestricted slippage tolerance" bug class from the external report, except here the parameter isn't merely missing from the ABI — it is silently zeroed inside the contract even though the underlying primitives fully support user-supplied slippage bounds.

### Impact Explanation
Any wallet calling `depositFor` (e.g., integrators, contracts and users who deposit "for" another beneficiary address) can have its deposited principal partially stolen via a sandwich attack because the contract offers no way to bound the acceptable minted-LP amount. This is a direct, concrete loss of user funds executable by any unprivileged address that can submit adjacent transactions (front-run/back-run), which satisfies the "direct theft of user funds" impact bar.

### Likelihood Explanation
Wombat pools are stableswap AMMs whose cash/liability ratio can be moved by ordinary swap transactions from any address, and MEV infrastructure for sandwiching mempool transactions is commonplace; `depositFor` is a normal `external` function with no access control restricting who may call it, so the attack requires no special privilege — only observing a pending `depositFor` transaction and having capital to swap in the target pool.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`) and forward the caller-supplied value into `_deposit` instead of hardcoding `0`, so callers can set a slippage bound just as they can with the regular `deposit` path.

### Proof of Concept
1. Attacker monitors mempool for a pending `WombatPoolHelperV2.depositFor(amount, victimBeneficiary)` transaction (e.g., a bot or integrator depositing on behalf of a user).
2. Attacker front-runs with a large swap into the target Wombat pool that skews `cash`/`liability`, temporarily reducing the LP-per-token mint rate.
3. Victim's `depositFor` transaction executes; since `_minimumLiquidity` is hardcoded to `0`, the call cannot revert even though the minted LP amount (and thus staked value credited to `_for`) is far below fair value, per [2](#0-1) .
4. Attacker back-runs by reversing the initial swap, restoring the pool ratio and pocketing the difference, which was effectively transferred out of the deposited principal.
