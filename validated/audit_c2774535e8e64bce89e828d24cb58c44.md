### Title
`KeyMachine::calculate_share` reveals the ECDH blame key for shares failing canonicality before the message's proof-of-possession is verified — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to the Nginx-UI flaw (a sensitive operation returning a decryption key for an unauthenticated request), PedPoP's `calculate_share` returns an `EncryptionKeyProof` — which discloses the ECDH shared key for a message — whenever the decrypted share bytes are non-canonical. This early error path returns the blame proof *before* the queued batch verification of the message's Schnorr proof-of-possession ever runs. A participant who replays another party's ephemeral encryption key with a forged (non-verifying) PoP can therefore still cause the victim to emit a valid `EncryptionKeyProof`, revealing the shared key that protects the honest party's encrypted secret share.

### Finding Description
`calculate_share` iterates over received `EncryptedMessage`s. For each, `Encryption::decrypt` (1) queues the per-message PoP (`msg.pop.batch_verify`) into `batch` under `BatchId::Decryption(l)`, and (2) immediately computes `ecdh(enc_key, msg.key)`, decrypts the ciphertext, and returns an `EncryptionKeyProof` containing that shared key. [1](#0-0) 

Back in `calculate_share`, the decrypted bytes are canonicality-checked **synchronously**, and on failure the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` via `?` — before `batch.verify_with_vartime_blame()` at line 493 is reached: [2](#0-1) 

The PoP exists precisely to prevent this disclosure. The comment on `EncryptedMessage` states that without it, an attacker who reuses victim-observed keys can induce blame proofs that reveal `bX`, leaking the honest sender's message: [3](#0-2) 

`blame_internal` enforces the correct ordering — it verifies the PoP first and blames the sender with no key disclosure on `InvalidSignature` — but `calculate_share`'s early `from_repr` error path bypasses that ordering entirely: [4](#0-3) 

### Impact Explanation
A malicious participant `l` captures an honest sender `a`'s `EncryptedMessage` addressed to victim `b` (broadcast/relay channel), takes `msg.key` = `a`'s ephemeral public key `A_msg`, and sends `b` a new `EncryptedMessage { key: A_msg, pop: <invalid>, msg: <garbage> }` in their own slot. `b`'s `decrypt` computes `shared = b_enc * A_msg` — identical to the ECDH key encrypting `a`'s real share to `b` — and returns it inside an `EncryptionKeyProof`. The garbage plaintext fails `C::F::from_repr` with overwhelming probability (for a ~252-bit field, random 32-byte strings are non-canonical ~15/16 of the time), so `calculate_share` returns `blame: Some(proof)` before the invalid PoP is ever checked. When `b` publishes the blame proof (the protocol's intended dispute mechanism), `l` obtains `b_enc * A_msg` and decrypts `a`'s previously captured ciphertext, recovering `a`'s secret-share contribution to `b`. The PoP — the only "authentication" on the per-message key — is nullified because the blame key is disclosed on an unauthenticated message.

### Likelihood Explanation
The attacker must be a DKG participant (the `shares` map is validated against the participant set via `validate_map`) and must observe a victim-bound `EncryptedMessage`. No cryptographic break is needed: any ciphertext works, since non-canonical plaintext is the overwhelmingly common case and triggers the early return regardless of PoP validity. Impact is partial (one share contribution per replayed key), keeping this below full key recovery, but it is a concrete secret disclosure enabled solely by attacker-supplied bytes to `calculate_share`.

### Recommendation
Do not attach the `EncryptionKeyProof` to the canonicality-failure error until the batched PoP verification has confirmed the message's authenticity. Either run `batch.verify_with_vartime_blame()` for the `BatchId::Decryption` statements before canonicality-checking each decrypted share, or re-verify `msg.pop` in isolation on this error path and return `blame: None` (blaming the sender) when it fails — mirroring `blame_internal`'s ordering.

// Eve constructs in her own slot:

  key: alice_msg.key,            // replayed ephemeral key
  pop: SchnorrSignature { R: random_point, s: random_scalar }, // invalid PoP

// Bob:
//   decrypt() queues bad PoP into `batch`, computes shared = b_enc * A_msg,
//   produces EncryptionKeyProof { key: shared, dleq }.
//   from_repr(garbage) fails (~15/16 for a 252-bit field)
//   → calculate_share returns InvalidShare { participant: eve, blame: Some(proof) }
//     WITHOUT batch.verify_with_vartime_blame() ever checking the forged PoP.
// Bob publishes `proof` for blame arbitration → Eve learns shared
//   = b_enc * A_msg = the ECDH key for Alice's real message,
//   → Eve decrypts Alice's captured ciphertext → Alice's share to Bob.
