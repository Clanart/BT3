## Analysis

The 1inch `FarmAccounting` bug is: rewards are tracked as a **fixed distributed amount** while the underlying token balance can independently float (rebase), so the ledger and the real balance diverge and payouts become wrong. The Hyperbridge analog is the Intent Gateway's escrow ledger, which has exactly the same fixed-vs-floating mismatch, but on the deposit/withdrawal side instead of a rewards side.

`IntentGatewayV2` pools **every order's escrowed input tokens together** in one contract balance, keyed only by a per-order accounting map `_orders[commitment][token]`, filled at `placeOrder()` time with the balance-diffed received amount: [1](#0-0) 

Deposits are careful to record the *actual* amount received (handling fee-on-transfer correctly via before/after `balanceOf`): [2](#0-1) 

But settlement (`_withdraw`) pays out the **frozen ledger amount**, not a value re-derived from the contract's current balance: [3](#0-2) 

Because all orders for a given token share the same contract balance, this is structurally identical to the `FarmAccounting` flaw: the contract assumes `Σ _orders[*][token] == balanceOf(token)` holds forever between `placeOrder` and settlement (`fillOrder`/`cancelOrder`/cross-chain `onAccept`/`onGetResponse`), which is exactly what breaks for a rebasing token.

### Title
Shared escrow pool for rebasing input tokens allows early settlers to lock/steal later orders' funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` escrows every order's input tokens in one shared contract balance per token, tracked only via the `_orders[commitment][token]` ledger recorded at `placeOrder` time. `_withdraw` (called from `fillOrder`, `cancelOrder`, and the cross-chain `onAccept`/`onGetResponse` handlers) always transfers the *ledger* amount, never re-derived from the live `balanceOf`. If the escrowed input token is a rebasing asset (balance changes independent of transfers, e.g. negative rebase/interest-bearing tokens), the sum of all outstanding `_orders` entries can exceed the contract's actual token balance. Settlement order then determines who gets paid: whichever orders settle first drain the reduced pool at their full recorded amount, and later orders' `safeTransfer` calls revert, permanently locking those users' escrowed funds.

### Finding Description
- `placeOrder` credits `_orders[commitment][token]` with the amount actually received at deposit time: [4](#0-3) 
- All orders sharing a token sit in the same pooled contract balance — there is no per-order vault or balance segregation.
- `_withdraw` decrements the ledger and pays out the recorded `amount` from the pooled balance without checking that the pool still actually holds that much for this specific order: [5](#0-4) 
- This path is reached from unprivileged, public entry points: same-chain `fillOrder`/`cancelOrder` [6](#0-5) , and the cross-chain settlement callbacks `onAccept`/`onGetResponse` that both call `withdraw`/`_withdraw` unconditionally once a valid proof/message arrives.
- Nothing in the codebase checks token rebase behavior before accepting it as an order input; any ERC20 address can be used as `order.inputs[i].token`.
- The invariant `Σ _orders[*][token] == balanceOf(gateway, token)` is required for every order to be redeemable in full, but a negative rebase (or any independent balance shrink of the escrowed token) breaks it identically to how `FarmAccounting` breaks when the reward balance floats independently of the recorded distributed amount.

### Impact Explanation
When the invariant breaks:
- Orders that settle (fill/cancel/refund) earlier drain the shared pool at their full recorded amount, unaffected by the rebase.
- Orders that settle later find the pool short: `safeTransfer` reverts, and because `_withdraw`/`withdraw` is invoked deterministically from `onAccept`/`onGetResponse`/`fillOrder`/`cancelOrder` with no fallback, those users' escrow becomes **permanently locked** (loss of funds) purely based on settlement ordering — not by anyone's malice, misconfiguration, or admin action, satisfying the "stealing or loss of funds" / "logic attack" bar without requiring a malicious relayer, prover, or governance actor.
- This also applies across the cross-chain cancel/refund and cross-chain fill/redeem paths identically, since they funnel through the same `_withdraw`.

### Likelihood Explanation
Any user (or an integrator building on top of the SDK) can place an order whose input token is a rebasing ERC20; nothing in `placeOrder` restricts token type beyond the fee-on-transfer balance-diff handling already implemented for deposits. Given the multi-day cross-chain settlement windows (deadline-based cancel/fill flows), a negative rebase during that window is a realistic real-world event for known rebasing token classes. No relayer/prover/admin collusion is needed — the break is purely a function of shared-pool accounting plus normal user-triggered settlement calls.

### Recommendation
Either (a) explicitly disallow/flag rebasing tokens as intent-gateway inputs (documentation + an allowlist check, mirroring the FarmAccounting report's own recommendation to avoid rebasable tokens in strict-ledger designs), or (b) remove the shared-pool assumption by re-deriving payout amounts from live `balanceOf` deltas at withdrawal time (the same technique already used correctly on the deposit side for fee-on-transfer tokens), and/or by isolating escrow per commitment (e.g., a sub-vault) so one order's shortfall can never come from another order's balance.

### Proof of Concept
1. User A places order with input token `RBT` (a rebasing ERC20), depositing 1,000 `RBT`; `_orders[commitmentA][RBT] = 1000`.
2. User B places a second order with the same `RBT`, depositing 1,000 `RBT`; `_orders[commitmentB][RBT] = 1000`. Gateway now holds 2,000 `RBT`.
3. `RBT` undergoes a negative rebase of 30%; gateway's actual `balanceOf(RBT)` drops to 1,400, while `_orders` ledger still totals 2,000.
4. User A cancels (same-chain) or the cross-chain solver fills order A first: `_withdraw` calls `safeTransfer(beneficiary, 1000)` — succeeds, leaving 400 `RBT` in the gateway.
5. User B attempts to cancel/settle: `_withdraw` calls `safeTransfer(beneficiary, 1000)` against a balance of only 400 — reverts. `_orders[commitmentB][RBT]` is never decremented (revert rolls back), so User B's 1,000 `RBT` are permanently unredeemable through the normal path, while User A benefited from settling first.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
