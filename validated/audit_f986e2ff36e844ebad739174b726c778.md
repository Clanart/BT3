### Title
CW20-to-ERC20 pointer treats non-standard ERC20 tokens (e.g. USDT) as successfully transferred even when transfer() returns false, causing accounting desync between CW20 pointer balances and actual EVM token balances - ([File: example/cosmwasm/cw20/src/contract.rs])

### Summary
The CW20-to-ERC20 pointer contract wraps an arbitrary ERC20 token so it can be used from the Cosmos/wasm side. When `transfer`/`transfer_from` are executed, the contract builds an ABI-encoded `transfer`/`transferFrom` payload and dispatches it via `EvmMsg::DelegateCallEvm` [1](#0-0) , but it never inspects the boolean return value of the underlying ERC20 call — it unconditionally returns a success `Response`.

### Finding Description
`transfer()` and `transfer_from()` in the CW20 pointer contract fetch the ABI payload from `EvmQuerier` and attach a `DelegateCallEvm` custom message to the response, then immediately build a successful `Response` without any reply handling or return-data check: [2](#0-1) [3](#0-2) .

On the Go side, `HandleInternalEVMDelegateCall` → `CallEVM` only fails the wasm execution when the EVM call itself reverts (`res.Err != nil`); it does not decode/verify the ABI return payload of the delegatecall: [4](#0-3) .

This means that for a non-standard ERC20 token (like USDT) whose `transfer`/`transferFrom` implementation does not revert on failure and simply returns `false` (or omits the boolean return entirely, similar to USDT's non-conforming ABI), the EVM call succeeds without reverting, so `CallEVM` returns no error, and the CW20 pointer contract emits a successful `Transfer` response — even though the actual ERC20 token balance was never moved. This directly parallels the reported bug class: code paths that assume a truthy/successful return from `transfer()`/`transferFrom()` without verifying it, but manifests here as a false-positive success (accounting desync) rather than a DoS, because the pointer's success/failure signal is derived purely from EVM-call revert status, not from the packed boolean.

Contrast this with the reverse-direction pointer, `CW20ERC20Pointer.sol` (ERC20-wrapping-a-CW20), which relies on `require(success, ...)` from a delegatecall into the wasmd precompile [5](#0-4)  — that path is safe because CW20 execute messages always error out (non-2xx) on failure rather than silently returning false, so this asymmetry means the risk is specific to the CW20→ERC20 direction.

### Impact Explanation
If the pointer's owning CW20 contract is pointed at a non-standard ERC20 token that does not revert on transfer failure (e.g. insufficient allowance/balance edge cases in tokens that return `false` instead of reverting, or truncate/omit the boolean), any Cosmos-side actor (wasm message sender) invoking `transfer`/`transfer_from`/`send`/`send_from` on the CW20 pointer will receive a successful transaction result and emitted attributes/events indicating funds moved, while the underlying ERC20 balance is unchanged. Downstream systems, contracts, or users relying on the CW20 pointer's reported success (e.g. marketplaces, escrows, bridges built on top of the pointer) can be tricked into believing a transfer succeeded, leading to fund loss for the recipient-dependent logic or double-spend-like behavior when the sender later relies on both "transfer succeeded" and "balance unchanged" facts.

### Likelihood Explanation
This requires a CW20 pointer to be registered against a non-standard ERC20 token whose transfer function doesn't revert on failure. Pointer registration is permissionless (any user can register an ERC20 for a CW20 pointer), so an attacker or unwitting integrator could point at such a token and then rely on the mismatch. The likelihood of hitting the buggy branch specifically (return `false` without reverting) depends on the target token's implementation, which is plausible for a subset of non-standard tokens, but not as universally triggered as tokens that outright omit the return value (USDT's classic missing-return case, which would actually still not revert here since Sei's Go-level ABI packing of the outgoing calldata doesn't force a return-value check either).

### Recommendation
In `CallEVM`/`HandleInternalEVMDelegateCall` (or specifically in the ERC20 pointer transfer/transferFrom/approve code paths), decode the ABI return data of `transfer`/`transferFrom` calls and treat a `false` boolean return the same as a revert, propagating an error back to the CW20 message handler. Alternatively, harden the CW20 pointer's Rust contract (or the underlying `HandleERC20TransferPayload`/`HandleERC20TransferFromPayload` handlers) to require a submessage reply that decodes and enforces the returned boolean equals `true` before returning a success `Response`.

### Proof of Concept
1. Deploy a mock ERC20 contract whose `transfer(address,uint256)` and `transferFrom` never revert but return `false` on failure conditions (e.g., insufficient balance simply returns `false` without a `require`).
2. Register a CW20 pointer for this ERC20 via the standard pointer-registration flow (as in `contracts/test/CW20toERC20PointerTest.js`).
3. Attempt a `transfer`/`transfer_from` wasm execute call on the pointer for an amount that the underlying `transfer` will fail on (returns `false`).
4. Observe the wasm execute transaction succeeds (`tx.code == 0`, `Transfer` attributes emitted) via `executeWasm(pointer, {transfer: {...}})`, matching the pattern used in `contracts/test/CW20toERC20PointerTest.js` lines 97-116, yet querying the underlying ERC20/CW20 pointer balance afterward shows no balance change — demonstrating the accounting desync caused by the unchecked boolean return.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
