Based on my investigation of the Aptos-native publish and code-ownership pathways, I found a genuine local issue in the object-ownership root-resolution logic that gates the new lazy module self-initialization / object-code-deployment flow.

### Title
Unbounded loop in `object::root_owner` allows ownership-cycle DoS against object-code publish/self-init gating - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks the object-ownership chain to find the transitive top-level owner, but unlike its sibling traversal functions (`owns`, `verify_ungated_and_descendant`), it has **no depth bound**. `root_owner()` is now security-critical: it is invoked by `code::publish_package` (via `init::record_deploy_owner`) and by `init::assert_may_self_initialize` to gate the new lazy-module-initialization/object-code-deployment feature, deciding who may (re)publish or self-initialize code on an object.

### Finding Description
`root_owner` is defined as: [1](#0-0) 
with no `MAXIMUM_OBJECT_NESTING` check, in contrast to `owns` and `verify_ungated_and_descendant`, which explicitly bound their ownership-chain walks: [2](#0-1) [3](#0-2) 

Critically, `transfer_raw` only authorizes the *caller* by walking from the object being moved up to the signer (bounded to 8 hops); it never checks whether the *destination* (`to`) is itself a descendant of the object being moved: [4](#0-3) 

This means an account that directly owns two objects `A` and `B` can legally perform `transfer(A → B)` then `transfer(B → A)`, each individually passing `verify_ungated_and_descendant` (since the signer directly owns the object being transferred each time), producing a 2-cycle `A.owner == B`, `B.owner == A`. Any subsequent call to `root_owner()` on `A` or `B` loops forever (bounded only by gas).

This function was recently wired into the new lazy-init/publish path: [5](#0-4) [6](#0-5) 

### Impact Explanation
Once a code-deployment object's ownership graph contains such a cycle, every future call to `code::publish_package` for that object (upgrade path, gated by `features::is_lazy_module_initialization_enabled() && object::is_object(addr)`) and every `init::internal_maybe_initialize`/`assert_may_self_initialize` check for modules on that object will hit the unbounded loop and abort on out-of-gas instead of a clean, cheap check. This permanently bricks the ability to upgrade or self-initialize the affected code object — a denial-of-service against the object-code-deployment/upgrade flow, which is an in-scope publish-path safety property (object code deployment/upgrade authority must remain functional and not be silently disabled).

### Likelihood Explanation
Creating the cycle requires only ordinary, permissionless `object::transfer` calls by an account that owns both objects in the cycle at the time of transfer — no special privilege is needed, and `allow_ungated_transfer` objects (the default) permit this without any owner-side restriction. The condition is reachable by any object owner, including one who later transfers/nests the poisoned object under a victim's hierarchy.

### Recommendation
Bound `root_owner`'s traversal the same way `owns`/`verify_ungated_and_descendant` are bounded (loop counter capped at `MAXIMUM_OBJECT_NESTING`, aborting with `EMAXIMUM_NESTING` instead of looping unboundedly). Additionally, consider preventing cycle creation directly in `transfer_raw`/`verify_ungated_and_descendant` by also checking that `to` is not a descendant of `object`.

### Proof of Concept
1. Account `attacker` creates two ungated-transfer objects `A` and `B` (`object::create_object`), both directly owned by `attacker`.
2. `attacker` calls `object::transfer(attacker, A, B_address)` — passes `verify_ungated_and_descendant` since `A.owner == attacker`. Now `A.owner == B`.
3. `attacker` calls `object::transfer(attacker, B, A_address)` — passes `verify_ungated_and_descendant` since `B.owner == attacker` (unchanged). Now `B.owner == A`.
4. `A` and `B` now form a 2-cycle.
5. If `A` (or an ancestor object in `A`'s never-terminating chain) hosts code published via `code::publish_package` with `LAZY_MODULE_INITIALIZATION` enabled, any subsequent `publish_package` (upgrade) or `init::internal_maybe_initialize` call on that object invokes `object::root_owner`, which now loops until gas is exhausted, aborting the transaction and permanently blocking legitimate upgrade/self-init.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    #[view]
    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
