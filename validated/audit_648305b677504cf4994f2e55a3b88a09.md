## Finding

The Clementine payout mechanism binds "the operator who gets reimbursed" to "the party that actually funded the payout" purely through an unauthenticated `OP_RETURN` field, which is exactly the class of bug described in the report (an identity field the wrong party can set to redirect economic benefit).

### Title
Payout tx `OP_RETURN` operator attribution is forgeable, letting an operator be credited/reimbursed for a payout it never funded - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the `payout_tx` with the user's withdrawal output at index 0 and an `OP_RETURN` at index 2 naming the operator who is supposed to have fronted the withdrawal. [1](#0-0)  The only cryptographic authorization on this transaction is the user's `SinglePlusAnyoneCanPay` signature, which is verified against input/output **index 0 only**. [2](#0-1)  Because of `SIGHASH_SINGLE|ANYONECANPAY`, the anchor output and the `OP_RETURN` (indices 1 and 2) are not committed to by any signature, and the tx-sender funding code explicitly relies on this to append extra inputs/outputs while keeping the original signature valid. [3](#0-2)  Later, the verifier's chain-sync logic determines who gets credited as the "payer" purely by reading this `OP_RETURN` field out of the confirmed on-chain payout transaction, with no check that the named operator actually supplied the funding inputs. [4](#0-3) 

### Finding Description
`create_payout_txhandler` sets the witness only on input 0 (`set_p2tr_key_spend_witness(&user_sig, 0)`), and the `output_script_pubkey`/`output_amount` supplied by the user's signature only fixes output 0. [5](#0-4)  The `withdraw()` RPC path also only checks this same sighash before broadcasting. [6](#0-5) 

Funding of the transaction (needed because the input UTXO is a small dust UTXO while the payout output is the full withdrawal amount) is done by the tx-sender wallet, which explicitly appends its own inputs and a change output *after* the existing outputs specifically "so that SinglePlusAnyoneCanPay signatures stay valid" - i.e., by design, anyone who can supply the funding inputs can reconstruct this transaction with a different set of trailing outputs (including the `OP_RETURN`). [7](#0-6) 

Once mined, `update_finalized_payouts` scans the confirmed `payout_tx`, extracts the first `OP_RETURN` output, parses the operator x-only pubkey out of it, and stores that as `payout_payer_operator_xonly_pk` for the withdrawal — with no validation that this pubkey corresponds to whoever actually supplied the funding inputs of the transaction. [8](#0-7)  `PayoutCheckerTask` then looks up "the first unhandled payout" keyed by `operator_xonly_pk` and, for the operator matching that key, calls `handle_finalized_payout`, which consumes one of that operator's kickoff connectors and starts the on-chain reimbursement flow for it. [9](#0-8)  The only downstream sanity check, `is_kickoff_malicious`, merely verifies that the operator who eventually sends the kickoff matches the `operator_xonly_pk` recorded from the `OP_RETURN` — it never checks that this operator actually paid for the payout. [10](#0-9) 

This breaks the intended binding:

```
operator credited with reimbursement == party that funded the payout output
```

Concretely: whoever funds the extra inputs required to complete the `payout_tx` (which can be anyone, since it just requires spendable BTC and knowledge of the user's public `SinglePlusAnyoneCanPay` signature/outpoint once any operator has broadcast it into the mempool) can set the `OP_RETURN` to name an arbitrary — including a completely uninvolved — operator's x-only pubkey. That named operator will subsequently be credited by `update_finalized_payouts`/`PayoutCheckerTask` and can go through the kickoff/reimburse flow and be reimbursed from the shared N-of-N collateral for a withdrawal it never funded.

### Impact Explanation
This matches the Critical bucket "an operator reimbursed for a payout it never funded." The party who actually pays out BTC to the withdrawing user gets nothing back, while an arbitrary named operator (who paid nothing) can walk through the kickoff/`ReadyToReimburse`/`Reimburse` flow and legitimately claim reimbursement, since `is_kickoff_malicious` only compares the `OP_RETURN` pubkey to the kickoff sender's pubkey — both of which the attacker/funder controls by choosing whose pubkey to embed. [11](#0-10) 

### Likelihood Explanation
No privileged role (operator, verifier, aggregator, etc.) is required to exploit this — funding a transaction just requires owning spendable BTC and observing/obtaining a broadcast (unconfirmed, RBF-enabled) `payout_tx` or the underlying signed withdrawal data, then constructing/rebroadcasting a variant with a different `OP_RETURN` and one's own funding inputs, exactly as the tx-sender's own funding logic is designed to permit. [7](#0-6) 

### Recommendation
Bind the operator attribution cryptographically to whoever funds the transaction, e.g., require the funding operator to sign the `OP_RETURN` output (or the whole transaction) with `SIGHASH_ALL`/`SIGHASH_DEFAULT` covering all outputs instead of leaving it uncommitted, or otherwise verify during `update_finalized_payouts`/`handle_finalized_payout` that the named operator's own key/signature authorized the specific funding inputs of the confirmed `payout_tx`.

### Proof of Concept
1. Operator A (or the user's designated recipient list) receives a valid withdrawal request and broadcasts `payout_tx_A` (input 0 = user's dust UTXO + `SinglePlusAnyoneCanPay` signature covering output 0 only, plus A's own funding inputs, `OP_RETURN` = A's xonly pubkey), per `create_payout_txhandler`. [1](#0-0) 
2. Before `payout_tx_A` confirms, an unprivileged party observes it in the mempool, reuses input 0 with its still-valid signature (only output 0 is committed), replaces A's funding inputs with its own UTXOs of equal or greater value, keeps output 0 unchanged, and sets the `OP_RETURN` to operator B's xonly pubkey — exactly the malleability the funding code is written to tolerate. [7](#0-6) 
3. This replacement `payout_tx_B` gets mined instead (e.g., via RBF/higher fee).
4. `update_finalized_payouts` parses the `OP_RETURN`, records `payout_payer_operator_xonly_pk = B`. [8](#0-7) 
5. Operator B's `PayoutCheckerTask` sees an unhandled payout attributed to itself and calls `handle_finalized_payout`, consuming a kickoff connector and entering the reimbursement flow, even though B never funded any part of the payout. [9](#0-8) 
6. `is_kickoff_malicious` finds `operator_xonly_pk == kickoff_data.operator_xonly_pk` (both B) and does not flag it, so B is honestly reimbursed for a withdrawal it never paid. [10](#0-9)

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
