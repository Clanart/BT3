### Title
Unsanitized "unsafe repository" path from Git stderr can be written verbatim into global `safe.directory`, allowing a single "Trust Repository" click to silently disable Git's ownership guard for the entire machine - ([File: app/src/lib/git/rev-parse.ts])

### Summary
Just as the Vercel WAF binds its "verified browser" decision to a weak, attacker-influenceable identifier (the browser profile/cookie) instead of the real attacker identity (the IP), GitHub Desktop's "Trust Repository" flow binds a security decision (adding an entry to Git's global `safe.directory` allowlist) to a raw string parsed out of Git's own stderr output, without validating that string before persisting it. Because that string is not re-derived from a trusted, canonicalized value, a directory/path name chosen by the *content the user is opening* can smuggle in Git's special `*` wildcard value, turning a single, narrowly-worded consent ("trust this one folder") into a machine-wide disablement of the ownership check that exists specifically to prevent hook-based code execution from untrusted repositories.

### Finding Description
When Desktop opens a folder that Git considers to have "dubious ownership" (owned by a different user than the current one - Git's mitigation for CVE-2022-24765-class hook execution attacks), `getRepositoryType` extracts the path directly from Git's stderr with a permissive regex and returns it as-is: [4](#0-3) 

This `unsafeMatch[1]` value flows, unmodified and unvalidated, into the UI state (`repositoryUnsafePath` / `unsafePath`) shown in `add-existing-repository.tsx` and `missing-repository.tsx`, and when the user clicks "Trust Repository", it is passed straight to `addSafeDirectory`: [5](#0-4) 

`addSafeDirectory` performs no allow-listing, canonicalization, or rejection of special/wildcard values before calling `addGlobalConfigValueIfMissing('safe.directory', path)`, which runs `git config --global --add safe.directory <path>`: [6](#0-5) 

Git's `safe.directory` mechanism treats the literal value `*` as "trust every directory on this machine, forever" - a special sentinel, not a normal path. Because the value that ends up on disk in the user's global `.gitconfig` is exactly the string Git printed for "repository at '...'" - a string that is effectively controlled by the name of the top-level directory being opened - a directory (or a `.git` file's `gitdir:` target, or a submodule working directory) literally named `*` (or containing other config-breaking characters) results in Desktop writing `safe.directory = *` to the user's global Git configuration instead of the single path the user believed they were approving. The UI's own display of the "unsafe path" comes from the same untrusted string, so the confirmation dialog itself doesn't protect against this - it will happily render "The Git repository at `*` appears to be owned by another user..." without the user recognizing that clicking "Trust" globally disables the safeguard.

Unlike the deep-link path-traversal handling elsewhere in the codebase, which explicitly canonicalizes and bounds paths via `resolveWithin`/`realpath` before trusting them, this Git-stderr-derived path receives no equivalent defense-in-depth: [7](#0-6) 

### Impact Explanation
`safe.directory` exists to stop Git from executing repository-controlled hooks/config for directories owned by someone other than the current user - the exact mitigation for arbitrary code execution via untrusted repositories (network shares, extracted archives, shared/synced folders, cloned or fetched content from an attacker). A single user click intended to trust one specific folder can instead globally disable this protection for every current and future repository on the machine, including any subsequently cloned, fetched, or opened attacker-controlled repository - directly enabling the code-execution-from-untrusted-repository class of attack the check was designed to prevent.

### Likelihood Explanation
The attacker-controlled surface is a directory/working-tree name (or `gitdir:`/submodule path) that an attacker fully controls when distributing a repository, archive, or synced folder for the victim to open via "Add Existing Repository" or the "repository is missing, locate it" flow. Naming a directory `*` (or otherwise embedding characters Git's config parser treats specially) is trivial and requires no local/privileged access beyond the victim opening/adding the attacker-supplied folder - a normal, expected Desktop workflow. The main constraint is that the victim must click "Trust Repository," so this is a one-click deceptive-consent bug rather than a zero-click exploit, but the dialog text itself does not clearly warn the user that the underlying config write can be global-wildcard rather than path-scoped.

### Recommendation
- Validate the path captured from Git's stderr (`rev-parse.ts`) before ever surfacing it in UI or persisting it: reject/escape the literal `*` sentinel and any value that doesn't resolve, via `realpath`, to an actual existing directory equal to the path Desktop asked Git to inspect.
- In `addSafeDirectory`, only accept a path that has been independently derived from Desktop's own known repository path (not re-trusting Git's echoed string), and explicitly disallow the bare `*` value or any value not exactly matching the resolved repository directory.
- Show the fully resolved, canonical path in the "Trust Repository" dialog and require it to match byte-for-byte what will be written to `safe.directory`.

### Proof of Concept
1. Attacker creates a repository/archive whose top-level directory (or a `.git` file's `gitdir:` target, or a submodule checkout path) is named `*`, and distributes it (zip, network share, or a cloned/fetched remote).
2. Victim uses "Add Existing Repository" (or has an existing repository in Desktop that becomes "missing" and is relocated) to point Desktop at this folder.
3. `getRepositoryType` runs `git rev-parse ...` in that folder; Git detects dubious ownership and prints `fatal: detected dubious ownership in repository at '*'`; the regex in `rev-parse.ts` captures `path = '*'` unchanged.
4. Desktop's UI shows the "Trust repository" prompt with this unsanitized path; the victim, believing they are scoping trust to the one folder they just opened, clicks "Trust Repository."
5. `addSafeDirectory('*')` executes `git config --global --add safe.directory *`, disabling Git's ownership check machine-wide for all present and future repositories, silently removing protection against hook-based code execution from any subsequently opened untrusted repository.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
