### Title
`updateRemoteUrl()` silently rewrites a repository's git remote using an unvalidated GitHub API `clone_url`, without verifying repository identity - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
This is the closest local analog to the `bumpTransfer()` bug class: a write path that mutates security-relevant state keyed by an *external, unvalidated identifier* — here, GitHub Desktop automatically rewrites the local git remote URL (the destination for future `fetch`/`push`) based on `clone_url` returned by a GitHub/GHE API call, without ever confirming that the API response actually refers to the *same underlying repository* the user originally added. Just as `bumpTransfer()` trusted a caller-supplied `transferId` and let a later `xcall()` overwrite `s.relayerFees` without checking the ID's provenance, `updateRemoteUrl()`/`_upsertGitHubRepository()` trust an owner+name-keyed API response and overwrite the trusted `cloneURL`/remote without checking the repository's stable numeric API id.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` resolves the repository's owner/name from the *current git remote* via `matchGitHubRepository()`, then calls `api.fetchRepository(owner, name)` and feeds the result into `updateRemoteUrl()`: [1](#0-0) 

`updateRemoteUrl()` then decides to silently repoint the local remote to the API's `clone_url` whenever the protocol matches and the "old" clone URL text still equals what is locally cached (`remoteUrlUnchanged`) but no longer equals the API's current answer (`!urlsMatch`): [2](#0-1) 

The equality checks (`urlMatchesRemote`, `urlsMatch`) only compare **hostname/owner/name strings** parsed out of URLs — never a stable repository identifier: [3](#0-2) 

And the underlying database upsert (`_upsertGitHubRepository`) keys its lookup purely on `[ownerID+name]`, overwriting `cloneURL`/`htmlURL`/permissions for whatever record already exists at that owner+name — again, no comparison against the API repository's numeric `id`: [4](#0-3) 

The broken invariant: nothing in this chain confirms that "the repository living at `owner/name` today" is "the same repository the user originally trusted." Renames are the only case this is *designed* for, but the code path has no cryptographic/id-based binding to the original repository — it is purely name/path based, exactly like `bumpTransfer()` accepting any `transferId` without checking it corresponds to a real, existing transfer.

### Impact Explanation
If the API endpoint queried for `fetchRepository(owner, name)` — a self-hosted GitHub Enterprise server, or any network path the user's client trusts (matching the Valid Impact category "a GitHub API object" / "a git remote/proxy response") — returns repository data whose `clone_url` differs from the previously known one while its `owner`/`name` text still lines up with the locally cached value, GitHub Desktop will **automatically and silently** call `gitStore.setRemoteURL()` and repoint the user's default remote: [5](#0-4) 

This is a direct "silent corruption of what the user commits or pushes" scenario: the user's next `git push` (and any subsequent `git fetch`) transparently targets a different, attacker-influenced repository/server, with no confirmation dialog, diff, or identity check shown to the user.

### Likelihood Explanation
The refresh path is not a rare, user-triggered action — it runs automatically on account-switch and repository refresh (`refreshSelectedRepositoryAfterAccountChange`), so the rewrite can happen without any explicit user interaction beyond normal app usage. The only real precondition is that the queried API endpoint can, for the same `owner/name` textual path, return a different `clone_url` than what Desktop cached — which is squarely possible for GitHub Enterprise/self-hosted endpoints or any environment where the API response is not what the user actually intends (e.g., a compromised/misconfigured GHE instance, or a proxy in the request path). Existing guards (`protocolsMatch`, `remoteUrlUnchanged`, `urlsMatch`) only protect against *user-initiated* protocol changes and don't validate repository identity at all, so they do not stop this path.

### Recommendation
Bind the update to a stable, non-spoofable identifier rather than owner+name text:
- Store and check the API repository's numeric `id` (as returned by the API) alongside `ownerID+name` in `_upsertGitHubRepository`, and refuse to overwrite `cloneURL`/`htmlURL`/permissions if the `id` differs from what's already recorded — treat an id mismatch as "this is a different repository," not "this repository was renamed."
- In `updateRemoteUrl()`, only auto-rewrite the remote when the API-confirmed `id` matches the previously known repository id; otherwise, surface the change to the user for confirmation instead of silently calling `setRemoteURL()`.
- Mirror the same protection Connext applied for `bumpTransfer()`/`PromiseRouter.bumpCallbackFee()`: validate that the identifier (`transferId` there, repository `id` here) actually corresponds to an existing, previously-known entity before allowing an overwrite of trusted state.

### Proof of Concept
1. Victim adds a repository whose GitHub API endpoint is a GitHub Enterprise (or otherwise attacker-influenceable) server; Desktop stores `GitHubRepository{owner, name, cloneURL: "https://ghe.example.com/acme/project.git", id: 101}` and the local git remote is set to that same URL.
2. The GHE server (compromised, misconfigured proxy, or a malicious admin) later serves, for `GET /repos/acme/project`, a response with the same `owner`/`name` text but `clone_url: "https://ghe.example.com/acme/project-attacker-fork.git"` and a different repository `id`.
3. On the next account-change refresh, `repositoryWithRefreshedGitHubRepository()` → `updateRemoteUrl()` sees `remoteUrlUnchanged === true` (matches previously cached `cloneURL`) and `urlsMatch === false` (new clone_url differs) and `protocolsMatch === true`, so it calls `gitStore.setRemoteURL(...)` and silently repoints the user's default remote.
4. The user's next `git push` sends commits to the attacker-influenced destination without any prompt, diff, or warning — exactly the "silent corruption of what the user commits or pushes" impact class, arising because no step validated that the API response referred to the same repository identity as before.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

/**
 * Match a URL-like string to the Clone URL of a GitHub Repository
 *
 * @param url A remote-like URL to verify against the existing information
 * @param gitHubRepository GitHub API details for a repository
 */
export function urlMatchesCloneURL(
  url: string,
  gitHubRepository: GitHubRepository
): boolean {
  if (gitHubRepository.cloneURL === null) {
    return false
  }

  return urlsMatch(gitHubRepository.cloneURL, url)
}

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}

  private async _upsertGitHubRepository(
    endpoint: string,
    gitHubRepository: IAPIRepository | IAPIFullRepository,
    ignoreParent = false
  ): Promise<GitHubRepository> {
    const parent =
      'parent' in gitHubRepository && gitHubRepository.parent !== undefined
        ? await this._upsertGitHubRepository(
            endpoint,
            gitHubRepository.parent,
            true
          )
        : await Promise.resolve(null) // Dexie gets confused if we return null

    const { login, type } = gitHubRepository.owner
    const owner = await this.putOwner(endpoint, login, type)

    const existingRepo = await this.db.gitHubRepositories
      .where('[ownerID+name]')
      .equals([owner.id, gitHubRepository.name])
      .first()

    // If we can't resolve permissions for the current repository chances are
    // that it's because it's the parent repository of another repository and we
    // ended up here because the "actual" repository is trying to upsert its
    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }

    if (existingRepo !== undefined) {
      // If nothing has changed since the last time we persisted the API info
      // we can skip writing to the database and (more importantly) avoid
      // telling store consumers that the repo store has changed.
      if (shallowEquals(existingRepo, updatedGitHubRepo)) {
        return this.toGitHubRepository(existingRepo, owner, parent)
      }
    }

    const id = await this.db.gitHubRepositories.put(updatedGitHubRepo)
    this.emitUpdatedRepositories()
    return this.toGitHubRepository({ ...updatedGitHubRepo, id }, owner, parent)
