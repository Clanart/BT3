### Title
Attacker-controlled `WWW-Authenticate` response spoofs a GitHub Enterprise sign-in flow, exfiltrating the OAuth client secret / auth code to a malicious host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's git credential helper decides whether a remote host is "GitHub" based on the `WWW-Authenticate` header returned by the git server during authentication, with no verification against a real GitHub/GHE instance. A malicious remote (or a MITM/proxy sitting in front of a remote the user has added) can set `realm="GitHub"` on this header to make Desktop treat an arbitrary attacker-controlled host as a GitHub Enterprise endpoint, automatically triggering the enterprise sign-in flow pointed at that host.

### Finding Description
In `getEndpointKind`, Desktop inspects the `wwwauth[...]` credential fields (which are populated straight from the server's `WWW-Authenticate` response headers captured by git) and classifies the endpoint as `'enterprise'` purely because the header contains `realm="GitHub"`: [1](#0-0) 

This classification feeds directly into `getCredential`, which — if no existing account matches the (attacker) endpoint — calls `ui.promptForGitHubSignIn(endpoint)` without any further validation that the host is actually GitHub/GHE: [2](#0-1) 

`promptForGitHubSignIn` then drives the enterprise sign-in flow using the attacker-supplied `endpoint`/`origin`: [3](#0-2) 

Once the user proceeds (clicking "Continue" in what looks like a normal Enterprise sign-in dialog), `authenticateWithBrowser` opens the system browser to an OAuth authorization URL built from that same attacker endpoint: [4](#0-3) 

and later exchanges the OAuth code by making a token request to that same untrusted `endpoint`: [5](#0-4) 

Desktop's OAuth token exchange requests (as seen in the analogous `deleteToken`/token-endpoint calls in `api.ts`) are built with the app's embedded `ClientID`/`ClientSecret` sent to whatever `endpoint` value is passed in: [6](#0-5) 

Because `endpoint` in the whole chain above originates from the credential helper's classification of the *remote's own response*, an attacker-controlled git server can set the process in motion entirely by responding to a fetch/push/clone attempt with a crafted `WWW-Authenticate: realm="GitHub"` header — no prior GHE account, no local/admin access, and no unnatural user action beyond the normal "sign in" click that Desktop already prompts users to do routinely.

### Impact Explanation
If the OAuth request is sent to the attacker's endpoint, the client secret and/or authorization code used to complete the OAuth handshake is delivered to attacker infrastructure instead of GitHub, which the report's "unauthorized OAuth" / "credential/token exfiltration" impact class covers directly. Depending on how the attacker's fake `/login/oauth/access_token` endpoint responds, this can also be leveraged to phish the user (who is shown a legitimate-looking Desktop sign-in UI) or to capture the authorization `code`, which combined with the exfiltrated client secret could be replayed against the real GitHub API.

### Likelihood Explanation
The trigger requires only that the user has added or cloned a repository whose remote is (or is later proxied/MITM'd to be) attacker-controlled, and that a normal git network operation (fetch/push) prompts for credentials — a routine event, not a special user action. The header-based heuristic in `getEndpointKind` is a "happy path" shortcut explicitly designed to avoid extra network calls, and it has no allowlist or TLS/host validation beyond the presence of the string `realm="GitHub"` in the header.

### Recommendation
Do not classify a host as GitHub/enterprise solely from a self-reported `WWW-Authenticate` realm string. Corroborate with an actual capability check (e.g., the existing `isGitHubHost` request that checks for `x-github-request-id`) before allowing this classification to trigger `promptForGitHubSignIn`, and/or require the user to explicitly confirm/select a previously-configured enterprise endpoint before initiating an OAuth flow that transmits the client secret.

### Proof of Concept
1. Attacker controls (or MITMs) a git remote, e.g. `https://evil.example.com/repo.git`, which the victim has cloned or added.
2. Victim performs a `git fetch`/`push`; git asks for credentials, and the remote responds with `WWW-Authenticate: Basic realm="GitHub"`.
3. `getEndpointKind` (`trampoline-credential-helper.ts:153-165`) classifies `evil.example.com` as `'enterprise'`.
4. No account matches this endpoint, so `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')` (`trampoline-credential-helper.ts:107-125`), which shows Desktop's normal "Sign in to GitHub Enterprise" dialog for that host (`trampoline-ui-helper.ts:80-104`).
5. Victim clicks "Continue with browser"; Desktop opens `getOAuthAuthorizationURL('https://evil.example.com', csrfToken)` and later POSTs the OAuth code/`ClientID`/`ClientSecret` to `evil.example.com` to exchange for a token (`sign-in-store.ts:284-359`, exchange pattern shown at `api.ts:2214-2231`).

I was not able to inspect the exact body of `requestOAuthToken`/`getOAuthAuthorizationURL` in `api.ts` within the available tool budget (only confirmed via `grep` that both are defined there and via the sibling `deleteToken` function that endpoint-parameterized requests embed `ClientID`/`ClientSecret`); a Devin session with full file access should verify these two functions directly to confirm the exact fields sent to the attacker-controlled `endpoint`.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }

export async function deleteToken(account: Account) {
  try {
    const creds = Buffer.from(`${ClientID}:${ClientSecret}`).toString('base64')
    const response = await request(
      account.endpoint,
      null,
      'DELETE',
      `applications/${ClientID}/token`,
      { access_token: account.token },
      { Authorization: `Basic ${creds}` }
    )

    return response.status === 204
  } catch (e) {
    log.error(`deleteToken: failed with endpoint ${account.endpoint}`, e)
    return false
  }
}
