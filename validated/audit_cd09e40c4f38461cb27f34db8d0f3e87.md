## Title
Unbounded recursion in wallet-side puzzle/offer matching (`match_puzzle` / `PuzzleInfo.also()` chains) allows a crafted Offer or spend bundle to crash a wallet via CLVM-nested-fragment-style stack exhaustion - (File: `chia/wallet/outer_puzzles.py`, `chia/wallet/trading/offer.py`, `chia/wallet/puzzle_drivers.py`)

### Summary
The Juniper GraphQL advisory is a CWE-400/CWE-674 uncontrolled-recursion DoS: a small attacker-supplied payload causes deeply nested language-level recursion in a trusted-but-unbounded parser, exhausting memory/stack before any cost/size accounting applies. Chia's wallet has a structurally analogous path: `Offer.from_spend_bundle()` / `Offer.from_bytes()` calls `match_puzzle()` for every `CoinSpend.puzzle_reveal` in an untrusted offer/spend bundle [1](#0-0) , and `match_puzzle` recurses through the "outer puzzle" driver chain (CAT → Singleton → Metadata → Ownership → CR → …) with no depth limit, driven purely by attacker-controlled curry nesting in the puzzle reveal [2](#0-1) .

### Finding Description
`Offer.from_spend_bundle()` runs `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` on *every* coin spend in an arbitrary, attacker-supplied `WalletSpendBundle`/offer file, independent of whether that spend is a genuine "dummy" settlement coin spend [3](#0-2) .

`match_puzzle` calls `driver.match(puzzle)` for each registered outer-puzzle driver (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`, …) [2](#0-1) . Each of these `match()` implementations, upon a structural match, uncurries one layer and then recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` to build the nested `"also"` chain, e.g. in `CATOuterPuzzle.match()` [4](#0-3) , `MetadataOuterPuzzle.match()` [5](#0-4) , `OwnershipOuterPuzzle.match()` [6](#0-5) , and `SingletonOuterPuzzle.match()` [7](#0-6) .

Each recursion step also calls `UnknownPuzzle.mod`/`curried_args`, which lazily uncurries the program via `uncurry_puzzle()` → `uncurry()` → `Program.uncurry()` [8](#0-7) [9](#0-8) . `Program.uncurry()` itself recognizes only the canonical CLVM curry shape `(2 (1 . mod) args)` and returns cleanly for anything else [10](#0-9) , so an attacker who wants deep recursion must construct a puzzle reveal with N layers of a driver-recognized curry shape (e.g. N nested `SingletonOuterPuzzle`/`CATOuterPuzzle` wrappers). This is purely a Python-side, CPU-cheap tree construction (no CLVM execution, no mempool cost accounting) — nothing in `match_puzzle`, `PuzzleInfo.also()` [11](#0-10) , `get_inner_puzzle`, `get_inner_solution`, or `construct_puzzle` enforces a maximum "also" depth. Symmetric recursion also exists on the wallet's own `also().also()...` chains used in `TradeManager.check_for_owner_change_in_drivers()` and `get_dl_offer_summary()` [12](#0-11) .

This is the same bug class as the Juniper advisory: an attacker submits a small, cheaply constructed input (nested fragments / nested curry layers) whose recursive-descent handling in the receiving process has no depth cap, consuming the Python call stack (or process memory building `UncurriedPuzzle`/`PuzzleInfo` objects) until a `RecursionError`/`MemoryError` crashes the wallet process, or until `sys.setrecursionlimit`/interpreter recursion protection kills the coroutine handling RPC/offer-file parsing.

Unlike the deliberately-hardened CLVM tree-hash code (`sha256_treehash` is explicitly iterative "so we don't have to worry about blowing out the python stack" [13](#0-12) ) and unlike raw CLVM execution (bounded by `MAX_BLOCK_COST_CLVM`/`max_tx_clvm_cost` cost accounting enforced in `pre_validate_spendbundle()` [14](#0-13) ), the wallet's puzzle-driver matching layer has neither an iterative implementation nor a cost/size gate, and it runs unconditionally when a wallet parses any offer file (`Offer.from_bytes`) or displays/validates any received spend bundle, before signature or full CLVM validation occurs.

### Impact Explanation
A wallet user who opens/loads a maliciously crafted offer file, or a wallet-facing RPC/service that parses an untrusted `Offer`/`SpendBundle` (e.g. `take_offer`, `get_offer_summary`, `check_offer_validity`, offer-file display in a GUI), can have that parsing call crash with a Python `RecursionError` or exhaust memory, denying wallet service (CWE-400/CWE-674, analogous to CVE-2022-31173). Because this executes before puzzle-hash verification against the real coin and before signature checks, the attacker needs no valid coins, keys, or CLVM cost budget — only a syntactically valid but semantically bogus curried puzzle reveal.

### Likelihood Explanation
Medium-High: constructing N nested curry wrappers that match a driver's recognized shape (e.g. `SingletonOuterPuzzle`/`CATOuterPuzzle`, which only need to match the launcher/tail-hash curry pattern) is cheap and can be automated; no coin ownership, signature, or CLVM execution cost is required to trigger `match_puzzle` recursion, and offer files are explicitly designed to be shared with counterparties/wallet users before any validation.

### Recommendation
Impose an explicit maximum nesting depth (or iterative rewrite) for `match_puzzle`/`construct_puzzle`/`get_inner_puzzle`/`get_inner_solution`/`solve_puzzle` in `chia/wallet/outer_puzzles.py` and each outer-puzzle driver's `match()`/`get_inner_puzzle()`/`get_inner_solution()`/`solve()` implementations, and for `PuzzleInfo.also()`-chain consumers in `TradeManager`. Reject/park offers whose driver chain exceeds a small bound (e.g. 32) before recursing further, mirroring the non-recursive design already used for `sha256_treehash`.

### Proof of Concept
Conceptual construction (cannot be executed in this environment):
1. Build a puzzle reveal `P_0 = SETTLEMENT_PAYMENT` (or any innermost puzzle).
2. For `i` in `1..N` (e.g. N = 50,000), wrap: `P_i = SINGLETON_MOD.curry(launcher_struct_i, P_{i-1})` (or alternate between `CAT_MOD.curry(...)`, singleton, ownership, metadata layers) so each layer matches the corresponding driver's `match()` uncurry pattern.
3. Construct a dummy `CoinSpend(coin=Coin(bytes32.zeros, P_N.get_tree_hash(), 0), puzzle_reveal=P_N, solution=<anything>)` and wrap it (with a genuine settlement-style dummy coin per `Offer.from_spend_bundle` expectations) into a `WalletSpendBundle`, then serialize via `Offer(...).to_bech32()`/`bytes()`.
4. Send this offer file to a victim wallet user or feed it to `Offer.from_bytes()` / `take_offer` RPC.
5. `Offer.from_spend_bundle()` calls `match_puzzle()` on `P_N`, which recurses N times through `CATOuterPuzzle.match`/`SingletonOuterPuzzle.match`/etc., each calling `self._match` on the next inner layer, exhausting the Python call stack and crashing/hanging the wallet process before any signature or coin-existence check occurs.

```python
    def uncurry(self) -> tuple[Program, Program]:
        def match(o: CLVMStorage, expected: bytes) -> None:
            if o.atom != expected:
                raise ValueError(f"expected: {expected.hex()}")

        try:
            # (2 (1 . <mod>) <args>)
            ev, quoted_inner, args_list = self.as_iter()
            match(ev, b"\x02")
            if TYPE_CHECKING:
                # this being False is presently handled in the TypeError exception handler below
                assert quoted_inner.pair is not None
            match(quoted_inner.pair[0], b"\x01")
            mod = quoted_inner.pair[1]
            args = []
            while args_list.pair is not None:
                # (4 (1 . <arg>) <rest>)
                cons, quoted_arg, rest = args_list.as_iter()
                match(cons, b"\x04")
                if TYPE_CHECKING:
                    # this being False is presently handled in the TypeError exception handler below
                    assert quoted_arg.pair is not None
                match(quoted_arg.pair[0], b"\x01")
                args.append(quoted_arg.pair[1])
                args_list = rest
            match(args_list, b"\x01")
            return Program.to(mod), Program.to(args)
        except ValueError:  # too many values to unpack
            # when unpacking as_iter()
            # or when a match() fails
            return self, self.to(0)
        except TypeError:  # NoneType not subscriptable
            # when an object is not a pair or atom as expected
            return self, self.to(0)
        except EvalError:  # first of non-cons
            # when as_iter() fails
            return self, self.to(0)
```
