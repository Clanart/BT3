### Title
Rewards continue to accrue against a zero total supply in `WomUp`, permanently locking distributed MGP rewards - (File: `wombat/WomUp.sol`)

### Summary
`WomUp` implements a Synthetix-style staking-rewards accounting scheme (`rewardPerTokenStored`, `lastUpdateTime`, `rewardRate`) for users who stake WOM (converted to mWOM) in order to earn MGP rewards that get locked into `vlMGP`. Like the `ZivoeRewards` bug referenced in the report, the `rewardPerToken()` function special-cases `totalSupply() == 0` by simply returning the stored value without accruing anything, but the `updateReward` modifier always advances `lastUpdateTime` to `lastTimeRewardApplicable()` regardless of whether `totalSupply()` was zero. Because `rewardRate` and `periodFinish` are fixed once at `initializeRewards()` and never adjusted afterward, any period during which `totalSupply()` is zero (e.g., because all stakers withdrew their mWOM) causes the reward that would have accrued during that period to be silently skipped and never re-attributed to anyone, permanently locking those MGP tokens in the contract.

### Finding Description
In `wombat/WomUp.sol`: [1](#0-0) 
`rewardPerToken()` returns the unchanged `rewardPerTokenStored` whenever `totalSupply() == 0`, meaning no reward accrues for that time window. [2](#0-1) 
The `updateReward` modifier unconditionally sets `lastUpdateTime = lastTimeRewardApplicable()` on every `stake`/`withdraw`/`migrate`/`getReward` call, with no branch to preserve the old `lastUpdateTime` when `totalSupply()` was zero. This means the time window during which no one was staked is treated as "already accounted for" once the next `stake`/`withdraw` call occurs, permanently skipping the reward that should have accrued for that window. [3](#0-2) 
`withdraw()` is a fully unprivileged function: any staker can withdraw their entire stake at any time. If the last remaining staker withdraws before `periodFinish`, `_totalSupply` becomes `0` mid-period. Since `rewardRate` is fixed for the entire `duration` (set once in `initializeRewards()`, which reverts if already set) and there is no mechanism to top-up/re-queue skipped rewards later (unlike `BaseRewardPool`/`BaseRewardPoolV2`/`vlMGPBaseRewarder`/`mWOMSVBaseRewarder` in this same codebase, which explicitly track `queuedRewards` for the `totalStaked() == 0` case), any reward corresponding to the zero-supply interval is lost forever. `rescueReward()` cannot recover this because it only works before `startTime`/before `rewardRate` is set: [4](#0-3) 

### Impact Explanation
MGP tokens deposited as rewards for the 7-day period become permanently unclaimable once a "no staker" window occurs mid-period, since:
- There is no code path to re-queue or redistribute the skipped rewards to later stakers (unlike the other reward pools in this repo, which explicitly implement `queuedRewards`).
- `rescueReward()` only functions prior to `rewardRate` being set, so the admin cannot recover the stuck MGP once the reward period is active.
- The tokens sit in the contract forever, unclaimable by any account, constituting a permanent freezing of user-directed yield (MGP tokens meant for stakers).

### Likelihood Explanation
Triggering the bug requires only ordinary, unprivileged wallet actions: any staker(s) can call `withdraw()` to fully exit their position at any point during the active `duration`. If this results in `_totalSupply == 0` before `periodFinish`, the reward-skipping condition is triggered automatically the next time `stake`/`withdraw`/`migrate`/`getReward` is called, with no admin or privileged interaction needed. Because `WomUp` is a bridging/migration-style contract (WOM → mWOM → MGP unlock reward), it is plausible for total supply to legitimately drop to zero at some point in its life (e.g., near the end of the migration incentive period when depositors move to other options), especially compared to larger, more continuously-active pools.

### Recommendation
Follow the same fix pattern already used elsewhere in this codebase (e.g., `BaseRewardPoolV2._provisionReward`): track a `queuedRewards`/leftover concept, or alternatively guard the `lastUpdateTime` update so that it does not advance while `totalSupply() == 0`, e.g.:
```solidity
modifier updateReward(address account) {
    rewardPerTokenStored = rewardPerToken();
    if (totalSupply() != 0) {
        lastUpdateTime = lastTimeRewardApplicable();
    }
    ...
}
```
so that the reward corresponding to the zero-supply window remains available to be earned once staking resumes, rather than being silently skipped and permanently stuck.

### Proof of Concept
1. Owner calls `initializeRewards()`, funding the contract with MGP and setting `rewardRate = rewardsAvailable / duration` and `periodFinish = block.timestamp + duration` (`wombat/WomUp.sol:200-214`).
2. Alice calls `stake(amount)`.
3. Time passes (e.g., 1 day of the 7-day duration).
4. Alice calls `withdraw(amount, false)`, fully exiting; `_totalSupply` becomes `0`. `lastUpdateTime` is updated to the current timestamp in the `updateReward` modifier (`wombat/WomUp.sol:134-148`, `76-84`).
5. No one stakes for e.g. 3 days.
6. Bob calls `stake(newAmount)`. In the `updateReward` modifier, `rewardPerToken()` is evaluated while `totalSupply() == 0` (pre-increment), returning the stale `rewardPerTokenStored` (no accrual for the elapsed 3 days), and then `lastUpdateTime` jumps to the current timestamp, permanently skipping that period's rewards (`wombat/WomUp.sol:100-108`, `76-84`).
7. The MGP reward corresponding to those 3 idle days remains in the contract balance but is never attributed to `rewardPerTokenStored`, so it can never be claimed via `getReward()`, and `rescueReward()` cannot be used since `rewardRate > 0` already (`wombat/WomUp.sol:187-194`). The tokens are permanently locked.

    function rewardPerToken() public view returns (uint256) {
        if (totalSupply() == 0) {
            return rewardPerTokenStored;
        }
        return
            rewardPerTokenStored + (
                (lastTimeRewardApplicable() - (lastUpdateTime)) * rewardRate * (1e18) / (totalSupply())
            );
    }
