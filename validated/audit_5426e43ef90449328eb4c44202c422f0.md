## Analysis

The core broken invariant in the external report is: **a routing identifier (`uniswap://`) is scoped too coarsely** — the receiving app trusts *any* sender that can claim the scheme, instead of binding to a specific, uniquely-verified sender identity. The Hyperbridge analog of this pattern shows up in `ExtrinsicIntents.sol`'s `onAccept` handler, where privileged administrative actions are authenticated against the **source chain** only, not the **specific module** on that chain that produced the message.

### Title
Privileged gateway operations (`UpgradeContract`, `NewDeployment`, `UpdateParams`, `SweepDust`) are authenticated only by source-chain identity, not by sender module id - (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept` dispatches privileged, protocol-critical `RequestKind`s (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`) whenever the incoming request's `source` chain equals the configured Hyperbridge coprocessor id: [1](#0-0) 

Unlike the `RedeemEscrow`/`RefundEscrow` path, which calls `_authenticate(incoming.request)` to verify that `request.from` matches the specific registered gateway instance for that chain: [2](#0-1) 

the privileged branch never checks `request.from` at all — it only checks `request.source`. This is structurally identical to the report's flaw: the "scheme" (source chain identity) is checked, but the specific "app" (module id) that is supposed to be the sole trusted publisher of governance instructions is not pinned down anywhere in this contract.

### Finding Description
`IntentsBase._instances` binds *destination-chain* gateway addresses per state machine, and `_authenticate` uses it to verify `request.from` for user-facing escrow flows. But there is no equivalent registry or check constraining *which module on the Hyperbridge coprocessor chain* is allowed to originate `NewDeployment` / `UpdateParams` / `SweepDust` / `UpgradeContract` instructions. The only gate is:

```solidity
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
```

`request.source` is authenticated by ISMP's consensus/state proof machinery (it genuinely came from the Hyperbridge coprocessor chain), but `request.from` — the module id of the pallet/account that dispatched the request from that chain — is attacker-influenceable data chosen by whatever code calls `dispatch_request` on the Substrate side, exactly as the ISMP router docs describe (`from` is set by the dispatching module, not cryptographically tied to a fixed governance authority): [3](#0-2) 

Any pallet on the Hyperbridge coprocessor chain capable of calling `dispatch_request`/`dispatch_to_evm` with a chosen destination `module` address and body content would produce a request whose `source` legitimately equals Hyperbridge's own state machine id, yet whose `from` is *not* the intended governance/admin module. Because `ExtrinsicIntents.onAccept` never checks `request.from` in this branch, that message is accepted as an authentic protocol-governance instruction.

This mirrors the report's exploit precisely: Alice does not need to break consensus or forge chain identity (the equivalent of getting a message "from Bob's OS"); she only needs to register/use the same coarse scope (here, "any module on the Hyperbridge chain") that the vulnerable receiver treats as fully trusted.

### Impact Explanation
If a module id other than the intended governance module can reach this code path, an attacker gains:
- `UpgradeContract`: arbitrary implementation swap on the ERC-1967 proxy → full contract takeover, including all escrowed user funds (`_orders`).
- `NewDeployment`: overwrite `_instances[keccak256(chain)]`, redirecting `_authenticate`'s trusted peer address for a chain to an attacker-controlled address, which then lets the attacker forge `RedeemEscrow`/`RefundEscrow` messages and drain all escrow for that route.
- `SweepDust` / `UpdateParams`: direct theft of protocol-held dust and redirection of fee/host parameters.

These map directly to "stealing or loss of funds," "unauthorized transaction or execution," and "false proof/state acceptance" in the bounty's impact gate.

### Likelihood Explanation
Exploitability hinges on whether any pallet on the Hyperbridge coprocessor chain lets an unprivileged/attacker-influenced caller pick both the destination contract address (`to`) and body content for a dispatched POST request. I confirmed the pattern exists in principle — the demo pallet's `dispatch_to_evm` is callable via `ensure_signed(origin)` with a user-supplied destination `module` address: [4](#0-3) 

but its body is hardcoded, so it does not by itself weaponize this specific gap. I was not able to fully verify, within the available files, whether any *production* pallet on the Hyperbridge coprocessor chain exposes a fully attacker-controlled `(to, body)` dispatch path that would let someone forge the `RequestKind` byte for `UpgradeContract`/`NewDeployment`/etc. This is the key open question and should be checked directly against Hyperbridge's coprocessor-side pallets before treating this as fully weaponized.

### Recommendation
Regardless of whether a current dispatch path is user-controlled, the contract should not rely solely on `request.source` for governance-critical actions. Introduce an explicit, immutable "authorized governance module id" constant (analogous to `HYPERBRIDGE_MODULE_ID`/`HyperbridgeWithdrawalModule`'s `Coprocessor` check pattern used in `modules/pallets/ismp/src/dispatcher.rs`) and require both `request.source == hyperbridge` **and** `request.from == GOVERNANCE_MODULE_ID` before executing `NewDeployment`, `UpdateParams`, `SweepDust`, or `UpgradeContract`. [5](#0-4) 

### Proof of Concept
1. Identify (or assume, pending verification) a pallet on the Hyperbridge coprocessor chain reachable by an unprivileged signed account that calls `pallet_ismp::dispatch_request` with an attacker-chosen destination address (`to`) and attacker-chosen `body`.
2. Attacker crafts `body = abi.encodePacked(uint8(RequestKind.UpgradeContract), abi.encode(maliciousImpl, initCalldata))` and sets `to = <ExtrinsicIntents/IntentGatewayV2 address>`.
3. The message traverses ISMP with `source = HostStateMachine (Hyperbridge)` genuinely verified by consensus proofs; `from` is set to the calling pallet's own module id (not the intended governance module).
4. On the destination chain, `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` is invoked; the check at line 298 only compares `request.source` to `hyperbridge()` and passes, since `request.from` is never validated for this branch.
5. `ERC1967Utils.upgradeToAndCall(maliciousImpl, initData)` executes, giving the attacker full control of the gateway contract and all escrowed funds.

**Caveat:** Step 1's precondition (an unprivileged, fully attacker-controlled `(to, body)` dispatch path on the Hyperbridge coprocessor chain) could not be conclusively confirmed from the files retrieved in this session; only a hardcoded-body example (`dispatch_to_evm` in the docs) was found. Confirming or ruling out such a pathway in the actual coprocessor-side pallets is necessary to establish full end-to-end exploitability, but the missing `request.from` check in `ExtrinsicIntents.onAccept`'s governance branch is a real, code-verified gap independent of that precondition.
