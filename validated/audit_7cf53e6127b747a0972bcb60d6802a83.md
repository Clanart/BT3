## Title
`aptos move verify-package` reports success without ever comparing on-chain bytecode to locally compiled bytecode - ([File: aptos-move/cli/src/stored_package.rs])

### Summary
The Aptos CLI's `VerifyPackage` command is meant to give users/auditors confidence that the bytecode published on-chain at an account matches a given source tree. In practice, `CachedPackageMetadata::verify()` only diffs the self-declared `PackageMetadata` fields (`name`, `deps`, `modules` metadata, `manifest`, `upgrade_policy`, `extension`, `source_digest`) and never fetches or compares the actual deployed module bytecode. Because nothing on-chain cryptographically binds `PackageMetadata` (source, source_digest, manifest) to the `code: vector<vector<u8>>` bundle that is actually executed, a malicious or compromised publisher can publish benign-looking metadata (matching legitimate source) alongside a different, malicious bytecode bundle, and `verify-package` will still print "Successfully verified source of package."

### Finding Description
On-chain, `code::publish_package` stores `PackageMetadata` (including `ModuleMetadata.source`/`source_map` and `source_digest`) and separately forwards the raw `code: vector<vector<u8>>` bundle to the native `request_publish`/`request_publish_with_allowed_deps` functions: [1](#0-0) [2](#0-1) 

The only linkage between the metadata and the actual bytecode enforced on-chain is module *names* (`expected_modules`) and, if enabled, allowed dependency addresses/names - checked in `validate_publish_request`: [3](#0-2) 

Nothing verifies that `pack.modules[i].source`, `pack.source_digest`, or `pack.manifest` actually correspond to the compiled bytes in `code[i]`. These fields are free-form, publisher-supplied metadata used purely for off-chain tooling/documentation (e.g. `aptos move download`, `aptos move verify-package`), as also documented in `built_package.rs::extract_metadata`, which independently computes `source_digest` from local source files at build time, with no relation enforced by the VM: [4](#0-3) 

The CLI's `VerifyPackage::execute` fetches the on-chain `PackageRegistry` via `CachedPackageRegistry::create(client, self.account, false)` — note the `with_bytecode: false` argument, meaning the actual on-chain module bytecode is never downloaded: [5](#0-4) 

`CachedPackageRegistry::create` only populates its `bytecode: BTreeMap<String, Vec<u8>>` cache `if with_bytecode` is true; with `false` it stays empty and is simply unused for the rest of the flow: [6](#0-5) 

`verify()` then compares only metadata-level struct fields — never actual module bytecode — and returns `Ok(())` (interpreted by the caller as a full success message) as long as all these self-reported metadata fields match: [7](#0-6) 

Because `source_digest` is computed purely from the *source text* the publisher chooses to embed in `ModuleMetadata.source` (itself just a gzipped blob supplied by the publisher, not derived from the compiled module), and because the actual bytecode bundle is a completely separate, unchecked input to `code::publish_package`/`request_publish`, an attacker who controls what is published can:
1. Compile and publish a legitimate-looking `PackageMetadata` (correct `name`, `manifest`, `deps`, `source`, and a `source_digest` matching that source) for public review, while
2. Passing an entirely different, malicious `code: vector<vector<u8>>` bundle for the same module names in the same transaction.

The VM only checks that module names in `code` match `expected_modules` in the metadata and (if dependency check is enabled) that dependency addresses/names are declared — it performs no verification that the bytecode is the compiled result of the declared source or digest.

### Impact Explanation
This breaks a core code-safety expectation: that `aptos move verify-package`'s "Successfully verified source of package" result implies the on-chain executable bytecode matches the reviewed/audited source. Users, auditors, exchanges, or automated tooling that rely on this CLI command to attest to the integrity of a deployed Move package can be misled into trusting malicious bytecode as if it were the reviewed source, enabling supply-chain-style code substitution attacks with no cryptographic or on-chain enforcement to catch the mismatch. This matches the "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" impact category and can lead to high-impact consequences (users interacting with what they believe is audited code while actually executing arbitrary attacker-controlled logic).

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any account owner (including a malicious package publisher, or one whose publishing pipeline is compromised) can trivially construct a publish transaction where the metadata's declared source/digest diverges from the actual bytecode, since the framework's `code::publish_package` and native `request_publish*` functions never cross-check these two independent inputs. No special privilege beyond being the package owner (which is required anyway to publish) is needed — the bug lies entirely in the verification tool's blind trust of self-reported metadata, not in an authorization bypass of publishing itself.

### Recommendation
- In `CachedPackageRegistry::create`/`VerifyPackage::execute`, always fetch actual on-chain module bytecode (`with_bytecode: true`) and compare it byte-for-byte (or via hash) against the bytecode produced by locally compiling the declared manifest/source, in addition to the existing metadata field comparisons in `verify()`.
- Consider having the framework itself bind `source_digest`/`ModuleMetadata.source` to the actual compiled bytecode (e.g., by having `request_publish` recompute or hash-check bytecode against a digest recorded in `PackageMetadata`), so that on-chain state itself cannot present mismatched metadata and bytecode as consistent.
- At minimum, update `verify-package`'s success message and documentation to clarify that it currently only validates metadata self-consistency, not that on-chain bytecode matches the declared/reviewed source, until byte-level verification is implemented.

### Proof of Concept
Conceptual PoC (not a full working script, since it requires a live network/CLI environment):
1. Compile a benign Move package `M` locally; capture its `PackageMetadata` (with correct `source`, `manifest`, `source_digest`).
2. Hand-craft a `code_publish_package_txn` payload using the benign `PackageMetadata` bytes (`metadata_serialized`) but substitute the `code: vector<vector<u8>>` bundle with the bytecode of a malicious module `M` (same module name, e.g. containing a backdoored `entry fun` or altered logic), keeping the same public function signatures so `check_upgradability`/compatibility checks (if any) still pass.
3. Submit this transaction; `code::publish_package` accepts it because module names match `expected_modules` and structural compatibility checks pass — nothing checks the metadata's `source`/`source_digest` against the actual `code` bytes.
4. Run `aptos move verify-package --account <addr>` pointed at the original benign source tree. Because `CachedPackageRegistry::create(..., false)` never downloads bytecode, and `verify()` only compares metadata fields (which match, since the attacker reused the legitimate metadata), the command prints "Successfully verified source of package" even though the deployed bytecode is malicious.

Note: I was not able to execute this against a live network within this environment; the analysis is based on static code review of `stored_package.rs`, `commands.rs`, `code.move`, `built_package.rs`, and `aptos_vm.rs::validate_publish_request`, all cited above, which together demonstrate the missing bytecode-to-metadata binding both on-chain and in the CLI verification tool.

impl CachedPackageRegistry {
    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(

        } else if self_metadata.modules != package_metadata.modules {
            bail!(

                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )

            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
