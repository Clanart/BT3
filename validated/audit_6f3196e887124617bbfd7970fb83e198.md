### Title

OP_RETURN data is omitted from transaction weight and fee accounting, producing underpaid or oversized Bitcoin transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` accepts up to 80 bytes of caller-controlled data and appends it to the transaction as an `OP_RETURN` output, but `calculate_weight_vbytes` only reconstructs payment and optional change outputs. Consequently, the calculated virtual size, required fee, and maximum-standard-weight check exclude the data output actually placed into the signed transaction. A caller can therefore cause the signing flow to produce a transaction whose effective fee rate is below the intended rate or the Bitcoin minimum relay fee, or whose actual weight exceeds the checked limit. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description

The fee estimator builds a transaction containing only payment outputs and an optional change output, with no parameter or branch representing the OP_RETURN data output. [5](#0-4) 

`SignableTransaction::new` validates `data` to be at most 80 bytes and appends it as a zero-value `OP_RETURN` output before calculating weight and fees. [2](#0-1) 

Both weight calculations pass only `payments` and optional `change`; neither communicates `data` to `calculate_weight_vbytes`. [6](#0-5) 

The resulting `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check are therefore computed for a transaction that lacks an output present in the final `SignableTransaction`. [4](#0-3) 

### Impact Explanation

An 80-byte payload creates a serialized output of roughly 92 vbytes, but the estimator accounts for none of it. If `fee_per_vbyte` is selected near the minimum relay boundary, the transaction can pass `TooLowFee` validation while its actual effective fee rate is substantially below the minimum, causing relay or acceptance failure. If the estimated transaction is already close to `MAX_STANDARD_TX_WEIGHT`, the omitted output can also make the final transaction exceed the checked limit after approval. The threshold participants then spend a signing round authorizing a transaction that cannot be published as intended, delaying or preventing movement of the selected inputs. [7](#0-6) [4](#0-3) [8](#0-7) 

### Likelihood Explanation

The vulnerable path is reached whenever a public caller causes a non-empty `data` value to be signed through `SignableTransaction::new`. The implementation explicitly permits payloads as large as 80 bytes, so no malformed encoding or internal state corruption is required. The issue is deterministic: every non-empty `data` payload contributes to the real transaction's size while contributing nothing to either fee estimate or the final weight check. [1](#0-0) [2](#0-1) [6](#0-5) 

### Recommendation

Include the OP_RETURN output in `calculate_weight_vbytes`, either by passing the validated `data` into that function or by calculating weight directly from the final `tx_outs`. After constructing the complete transaction, recalculate its actual weight and enforce both the requested fee rate and `MAX_STANDARD_TX_WEIGHT` against that final transaction rather than the partial reconstruction. [5](#0-4) [9](#0-8) 

### Proof of Concept

1. Create a valid `ReceivedOutput` whose script belongs to the threshold key.
2. Call `SignableTransaction::new` with one dust-compliant payment, no change, an 80-byte `data` payload, and the minimum fee rate that just satisfies the existing `TooLowFee` check.
3. The estimator calculates `needed_fee` from only the inputs and payment output because `calculate_weight_vbytes` receives no representation of `data`.
4. The constructor nevertheless inserts a 92-vbyte-scale OP_RETURN output into `tx_outs` and stores that larger transaction in `SignableTransaction`.
5. `TransactionSignMachine::sign` signs the complete transaction, while `needed_fee` and the standard-weight result remain based on the smaller transaction lacking the OP_RETURN output. Broadcasting the signed transaction can consequently fail minimum-relay or standard-weight validation despite constructor checks succeeding. [10](#0-9) [4](#0-3) [8](#0-7)

impl SignableTransaction {
  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
