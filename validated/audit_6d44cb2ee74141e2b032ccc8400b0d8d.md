### Title
Hand-rolled YAML parser in `extract_frontmatter` diverges from real YAML on duplicate keys/tab indentation, silently downgrading declared `action`/`event`/`tool_matcher` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` (plugins/hookify/core/config_loader.py:87) implements a line-by-line, hand-rolled YAML subset instead of using a real YAML parser. On adversarial but plausible-looking frontmatter (duplicate top-level keys, tab-indented lines), it produces a different `frontmatter` dict than a real YAML parser (e.g. PyYAML's `safe_load`) would produce or than a human/Claude visually scanning the file would infer, causing `Rule.from_dict` to build a `Rule` whose `action`/`event`/`tool_matcher` do not match the value that "looks" authoritative in the file.

### Finding Description
The top-level key/value branch only fires when `indent == 0` (config_loader.py:125):
```
if indent == 0 and ':' in line and not line.strip().startswith('-'):
    ...
    frontmatter[key] = value
``` [1](#0-0) 

Two concrete divergences from a spec-compliant YAML parser:

1. **Duplicate keys silently overwrite (last wins), with no warning** — e.g. a frontmatter block that a reviewer skims and sees `action: block` near the top, followed later (e.g. hidden below a long `message`/`conditions` block, or after a decoy comment) by a second `action: warn` line. The custom parser just does `frontmatter[key] = value` each time it sees a top-level `key: value` line, so the final dict silently ends up with `action: 'warn'`, while a human/Claude skimming the file sees the first, prominent `action: block` declaration and believes the rule is a blocking guard. `Rule.from_dict` then builds a `Rule` with `action='warn'`, and `RuleEngine.evaluate_rules` treats it as a non-blocking warning rule instead of denying the tool call. [2](#0-1) [3](#0-2) 

2. **Tab-indented lines are silently dropped, not errored** — Standard YAML forbids tabs for indentation and a compliant parser (PyYAML) raises a `ScannerError`, causing the whole document to fail to load — a fail-closed behavior. Here, a line such as `\taction: block` has `indent == 1` (tabs counted as width-1), so it fails the `indent == 0` top-level check, fails the `stripped.startswith('-')` list-item check, and fails the `indent > 2 and in_dict_item` continuation check — it is simply ignored with no error, warning, or exception. The field silently falls back to `frontmatter.get('action', 'warn')` default in `Rule.from_dict`, i.e. `warn`, even though the file visually declares `action: block`. [4](#0-3) [5](#0-4) 

The load path is: `load_rule_file` → `extract_frontmatter` → `Rule.from_dict` → consumed directly by `RuleEngine.evaluate_rules`, which is the actual enforcement point deciding `block` vs `warn` and thus whether a tool call is denied (`permissionDecision: deny`) or merely a `systemMessage` is shown. [6](#0-5) [7](#0-6) 

No allowlist, schema validation, or cross-check against a real YAML parser exists anywhere in this pipeline to catch the divergence.

### Impact Explanation
This is a parser-differential trust-boundary bypass on security-policy content: a `hookify.*.local.md` rule file that visually/declaratively appears to `block` a dangerous `Bash`/`Edit`/`Write` operation (matching the described "block `rm -rf`" style rules already shipped as examples in this plugin) can be crafted so the actually-loaded `Rule.action` is `warn` (or `tool_matcher`/`event` differ), silently weakening the enforcement guard while still reading as a strict blocking rule to a human reviewer or to Claude previewing/summarizing the file. This matches the scoped impact described: "a rule intended to 'block' Bash commands is parsed as 'warn' ... bypassing the intended guard" — an approval/review bypass reachable purely through checked-in repository content (no admin privilege, keys, or social engineering needed).

### Likelihood Explanation
Feasible and deterministic: the attacker only needs write access to a `.claude/hookify.*.local.md` file within the repo (the explicitly allowed precondition "checked-in plugin/rule content"). Duplicate-key overwrite and tab-indentation line-dropping are simple, reproducible string patterns, not timing- or environment-dependent, so the divergence is 100% repeatable given the crafted input.

### Recommendation
Replace the hand-rolled parser with a real, strict YAML parser (e.g. `yaml.safe_load`) with `allow_duplicate_keys=False`/duplicate-key rejection enabled and tabs-in-indentation left to raise as YAML already does, so any adversarial/malformed frontmatter fails closed (file rejected, rule not loaded) rather than silently producing a semantically different, weaker rule. At minimum, add explicit duplicate-key detection and tab-character detection in `extract_frontmatter` that raise/skip-the-whole-file instead of silently overwriting or dropping lines.

### Proof of Concept
Differential/unit test in `plugins/hookify/core/config_loader.py`'s test suite:
```python
import yaml
from hookify.core.config_loader import extract_frontmatter, Rule

def test_duplicate_action_key_diverges_from_pyyaml():
    content = """---
name: block-rm
event: bash
action: block
action: warn
---
Dangerous rm command!
"""
    fm, _ = extract_frontmatter(content)
    rule = Rule.from_dict(fm, "")
    # Hand-rolled parser silently downgrades to 'warn'
    assert rule.action == 'warn'
    # A strict YAML loader would reject duplicate keys outright
    import pytest
    with pytest.raises(yaml.YAMLError):
        yaml.load(content.split('---')[1], Loader=yaml.loader.FullLoader)  # or a duplicate-key-checking loader

def test_tab_indented_action_silently_ignored():
    content = "---\nname: block-rm\nevent: bash\n\taction: block\n---\nmsg\n"
    fm, _ = extract_frontmatter(content)
    rule = Rule.from_dict(fm, "")
    # 'action' line was silently dropped; falls back to default 'warn'
    assert 'action' not in fm
    assert rule.action == 'warn'
```
Expected assertions: both tests demonstrate that the file's visually-declared `action: block` is not what `Rule.from_dict` ultimately produces, confirming the parser differential and its downstream effect on `RuleEngine.evaluate_rules`'s block/warn decision.
