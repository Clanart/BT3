### Title
Cross-chain escrow withdrawal reverts entirely if any single input token's escrow was already zeroed, permanently locking multi-token orders on the Tron `IntentGatewayV2` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` reverts the whole withdrawal (fill-release or refund) if `_orders[commitment][token] == 0` for *any* input token in the order, instead of skipping tokens with no remaining escrow. This is the exact `poke()`-class bug: a legitimate, unprivileged state-transition function (`onAccept`/`onGetResponse` → `withdraw()`) that should tolerate a zero-balance entry instead unconditionally reverts, permanently blocking settlement/refund of a multi-input order whenever one of its input tokens has already been reduced to zero escrow (e.g. via a fee-on-transfer token that nets to 0, or any other legitimate path that drives one leg's escrow to zero while others remain funded).

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` iterates every token in `body.tokens` (which is `order.inputs`, the full input list for the order) and does: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
        _orders[body.commitment][token] -= amount;
        ...
    }
```

Compare this to the maintained EVM `IntentsBase._withdraw()`, which explicitly guards against this exact class of zero-balance revert by skipping the token instead of reverting: [2](#0-1) 

```solidity
for (uint256 i; i < len; i++) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) continue;

    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();
```

The main EVM path was hardened (`if (amount == 0) continue;`) — this is direct evidence that the project already recognizes "revert on a zero-value leg instead of skipping it" as a bug class worth fixing (the same repo's `IntentGatewayV2SameChainTest.sol` even has an entire section titled "ROUNDING DUST IN PARTIAL FILLS (Finding #4)" documenting this exact pattern being fixed for partial-fill dust). The Tron contract, however, still contains the unguarded, revert-on-zero version.

`withdraw()` is called from every settlement/cancellation entrypoint on this contract: `onAccept` for `RedeemEscrow`/`RefundEscrow` (destination proving fill/cancel), and `onGetResponse` for source-chain cancellation after querying destination fill status. All of these paths pass the order's full `order.inputs` array (multi-token orders are supported — see `TokenInfo[] inputs` in `Order`). If any one of the multiple input tokens for an order ends up with `_orders[commitment][token] == 0` (achievable, for instance, via a fee-on-transfer token whose net-received amount rounds to zero, or any other flow that zeroes one leg's escrow while other legs remain funded), the *entire* withdrawal call reverts — not just for that token. This means:

- A legitimate solver cannot claim escrow for the still-funded legs of the order after delivering the required outputs (`onAccept`/`RedeemEscrow` reverts entirely).
- A legitimate user cannot get their refund for the still-funded legs (`RefundEscrow`/`onGetResponse` reverts entirely).

Both entrypoints are only reachable once, driven by an authenticated cross-chain message (`onAccept`) or a verified GET response (`onGetResponse`) — they are not gated by any additional retry-with-skip mechanism, so a revert here means the order's remaining escrow is permanently stuck, exactly mirroring how `poke()`'s revert-on-zero-weight permanently prevented voting-power updates.

### Impact Explanation
This is a fund-lock / stuck-escrow bug, not just gas waste: once a single input leg of a multi-token order has zero escrow (whether by design, by fee-on-transfer edge cases, or by an intentionally crafted order), the entire settlement/refund transaction for that order permanently reverts on the Tron gateway, and the remaining escrowed tokens for the other legs can never be released to either the solver or the user through the normal flow. This matches the bounty's "loss of funds"/"logic attack" categories: legitimate value becomes unrecoverable through the contract's own intended state-transition function.

### Likelihood Explanation
Likelihood is Medium: it requires an order with multiple input tokens where one input's escrowed amount reaches exactly zero (e.g., because the token is fee-on-transfer and its net-received amount underflows to zero and is not filtered by an equivalent zero-check on this Tron contract's `placeOrder`, or via any code path that decrements the per-token escrow to exactly zero before the other legs are released). Any unprivileged user who structures such a multi-input order can trigger this without needing a malicious relayer, prover, or admin — it is exercised purely through the standard place/fill/cancel flow.

### Recommendation
Mirror the fix already applied to the primary EVM `IntentsBase._withdraw()`: skip tokens whose withdrawal amount (or existing escrow) is zero instead of reverting the whole batch.

```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) { unchecked { ++i; } continue; }
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
}
```
Also add a matching zero-amount guard to the Tron contract's `placeOrder` (as already present in the current EVM `IntentGatewayV2.sol`) so that dust/fee-on-transfer inputs cannot silently create a zero-escrow leg in the first place.

### Proof of Concept
Conceptual PoC (cannot be run without full Tron test harness in this session, but the trigger conditions are directly derivable from the code):
1. User places a multi-input order on the Tron `IntentGatewayV2` with two input tokens: Token A (a fee-on-transfer token whose received amount rounds to 0 for a chosen amount) and Token B (a normal ERC-20 with non-zero escrow).
2. `_orders[commitment][TokenA] == 0` while `_orders[commitment][TokenB] > 0`.
3. Solver fills the order on the destination chain and the settlement `RedeemEscrow` message arrives via `onAccept` → `withdraw(body, false)`, where `body.tokens` includes both Token A and Token B.
4. The loop reaches Token A, evaluates `_orders[commitment][TokenA] == 0`, and reverts with `UnknownOrder()` — the solver never receives Token B's escrow either, and the transaction cannot be retried through any alternate skip path, permanently stranding Token B's escrow in the contract. [1](#0-0)
