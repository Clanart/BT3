This confirms the differential exploit is real and matches the documented `stop`-event usage pattern in `plugins/hookify/skills/writing-rules/SKILL.md:182-196`.

### Title
Legacy `pattern:` rules for `stop`/`prompt` events silently never match, bypassing block/warn enforcement - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` infers a hard-coded target `field` for legacy (`pattern:`) rules based on `event`, mapping any event other than `bash`/`file` (including `stop` and `prompt`) to `field='content'`. `RuleEngine._extract_field` in `plugins/hookify/core/rule_engine.py` never recognizes `'content'` as a valid field for `stop`/`prompt` events (it only resolves `reason`, `transcript`, `user_prompt` for those, or tool-specific fields for `Bash`/`Write`/`Edit`/`MultiEdit`). As a result, any legacy-style rule targeting `stop` or `prompt` events—exactly the format documented and encouraged in the plugin's own `SKILL.md`—will never match, silently disabling any `action: block` or `action: warn` enforcement for that rule, while the equivalent explicit `conditions:` form (using `field: reason`/`field: transcript`/`field: user_prompt`) works correctly.

### Finding Description
`Rule.from_dict` in `plugins/hookify/core/config_loader.py:56-73` converts a legacy `pattern:` field into a `Condition` by inferring `field` from `event`:
```
if event == 'bash': field = 'command'
elif event == 'file': field = 'new_text'
else: field = 'content'
```
`stop` and `prompt` fall into the `else` branch and get `field='content'`.

In `plugins/hookify/core/rule_engine.py`, `_check_condition` calls `_extract_field(condition.field, tool_name, tool_input, input_data)` (`rule_engine.py:158`). For `Stop`/`UserPromptSubmit` events, `tool_name` is empty and `tool_input` is `{}`, so the only paths that can resolve a value are the `input_data` branch checking `field in ('reason', 'transcript', 'user_prompt')` (`rule_engine.py:203-228`), or the `Write`/`Edit` tool-specific branch that handles `'content'` (`rule_engine.py:235-238`) — which never executes because `tool_name` isn't `Write`/`Edit` for these events. Since `condition.field == 'content'` matches none of these branches, `_extract_field` returns `None`, and `_check_condition` immediately returns `False` (`rule_engine.py:159-160`). Consequently `_rule_matches` returns `False` for the rule regardless of the actual stop-reason, transcript content, or user prompt text.

This exact legacy pattern is the one documented in `plugins/hookify/skills/writing-rules/SKILL.md:182-196` (`event: stop`, `pattern: .*`) as the recommended way to enforce completion checklists via `action: block`. Because `/hookify` command generation (`plugins/hookify/commands/hookify.md:82-102`) and repo-shipped `.claude/hookify.*.local.md` files both commonly use this simple/legacy form, any author (including an attacker who can add or influence a repo-shipped rule file, e.g., via a shared/cloned repository) who follows the documented, simplest syntax for a `stop` or `prompt` blocking rule produces a rule object that is syntactically valid, loads without error, and appears in rule listings as enabled — yet can never actually fire. There is no validation in `load_rule_file`/`Rule.from_dict` that flags a `field`/`event` combination that is structurally guaranteed to never match, so this silent no-op is indistinguishable from a working rule to the person deploying it.

### Impact Explanation
This breaks the invariant that legacy and explicit rule forms produce the same effective security semantics: the explicit form (`conditions: [{field: reason|transcript|user_prompt, ...}]`) works as intended for `stop`/`prompt` events, while the legacy/simple form silently fails to enforce for the exact same events. Any `stop`-event `action: block` rule intended to prevent an agent from stopping before required steps are completed (tests run, docs updated, etc.) — the primary documented use case — is completely inert. This is a Security-control bypass that silently disables a blocking boundary without any error, warning, or feedback to the rule author, matching "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries."

### Likelihood Explanation
High feasibility and fully repeatable: it requires no special privilege — a normal contributor, repo-shipped `.claude/hookify.*.local.md` file, or the `/hookify` LLM-driven generation process following the documented simple syntax in `SKILL.md`/`README.md` for `stop`/`prompt` events will deterministically produce this broken rule every time. It doesn't depend on malformed YAML, edge-case parsing quirks, or race conditions — it's a straightforward logic mismatch between `Rule.from_dict`'s field-inference table and `RuleEngine._extract_field`'s supported field names for non-tool events.

### Recommendation
Fix the field inference in `Rule.from_dict` (`plugins/hookify/core/config_loader.py:60-67`) to map `stop`→`reason` (or `transcript`) and `prompt`→`user_prompt` instead of the generic `'content'`, matching what `RuleEngine._extract_field` actually supports for those events. Additionally, add a validation step in `load_rule_file`/`Rule.from_dict` that verifies the resolved `field` for a given `event` is one `_extract_field` can actually resolve, and log/reject rules where this is not the case, so silently-dead rules cannot be shipped undetected.

### Proof of Concept
Unit test in `plugins/hookify` test suite:
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter = {
    "name": "block-stop-without-tests",
    "enabled": True,
    "event": "stop",
    "pattern": ".*",
    "action": "block",
}
rule = Rule.from_dict(frontmatter, "Tests must pass before stopping!")

engine = RuleEngine()
input_data = {
    "hook_event_name": "Stop",
    "reason": "I am done, tests were not run",
}

result = engine.evaluate_rules([rule], input_data)

# Expected (per documented intent): rule should block since pattern ".*" should always match
assert result.get("decision") == "block", (
    "Legacy stop-event rule silently failed to block; "
    f"got {result!r} instead of a block decision"
)
```
Running this against the current code shows `result == {}` (no block, no warning) because `rule.conditions[0].field == 'content'`, which `_extract_field` cannot resolve for a `Stop` event, causing `_check_condition` to return `False`. Comparing this against an equivalent explicit-conditions rule (`conditions: [{field: reason, operator: regex_match, pattern: ".*"}]`) demonstrates the explicit form correctly blocks, confirming the legacy/explicit semantic divergence.
