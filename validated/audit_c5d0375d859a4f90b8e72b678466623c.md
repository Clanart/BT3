## Analysis

The Tron-specific EVM contract `evm/tron/contracts/apps/IntentGatewayV2.sol` contains the exact analog of the Frax bug: several token payout paths use a raw low-level `.call()` to invoke `IERC20.transfer` and only check that the *call itself* didn't revert (`success`), never decoding/checking the ABI-encoded boolean return value. [1](#0-0) [2](#0-1) [3](#0-2) 

Note the sibling mainline EVM contract `evm/src/apps/intentsv2/IntentsBase.sol` correctly uses `SafeERC20.safeTransfer`, which reverts on a false return: [4](#0-3)  — confirming the Tron variant is the outlier/local analog, not intended behavior.

### Title
Escrow settlement accounting finalizes even when TRC20/ERC20 `transfer` silently fails (returns `false`) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` (reached via `onAccept` for `RedeemEscrow`/`RefundEscrow` and via `onGetResponse`) and the `SweepDust` handler in `IntentGatewayV2.sol` (Tron variant) pay out escrowed tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level call succeeded, never inspecting the returned boolean. Any ERC20/TRC20-style token that returns `false` on a failed transfer instead of reverting (blacklist tokens, legacy tokens, tokens with recipient allowlists, paused tokens, etc.) will cause `success == true` while no tokens actually move.

### Finding Description
In `withdraw()`, escrow accounting is decremented (`_orders[body.commitment][token] -= amount;`) and the order is marked filled (`_filled[body.commitment] = beneficiary;`) unconditionally after the `.call()` "succeeds," regardless of whether the token's internal transfer logic actually moved funds: [1](#0-0) 

The same pattern repeats for transaction-fee payout: [2](#0-1) 

and for the `SweepDust` protocol path invoked from `onAccept`: [5](#0-4) 

Because `withdraw` is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` bodies and from `onGetResponse` for cancellation refunds, this is the terminal settlement step for both successful order fills and refunds: [6](#0-5) [7](#0-6) 

Existing guards do not stop this: `if (!success) revert TransferFailed();` only catches reverts/out-of-gas/no-code failures at the call level. It does not decode `returndata` to check the boolean the ERC20/TRC20 standard defines for a failed-but-non-reverting transfer, so a token that deliberately returns `false` (e.g., to signal a blacklisted recipient or paused state) passes this check while leaving the tokens in the contract.

### Impact Explanation
Once `withdraw()` runs, the escrow ledger (`_orders[commitment][token]`) is permanently decremented and `_filled[commitment]` is set, marking the order/refund as settled. If the token silently no-ops the transfer, the corresponding value stays locked inside `IntentGatewayV2` with no accounting entry pointing back to the rightful beneficiary — the funds are lost to the intended recipient (solver expecting escrow release, or user expecting a refund) while the protocol state believes settlement is complete. This is a direct, permanent loss-of-funds condition and a false-settlement-acceptance analog to the original Frax bug (accounting says "paid," reality says "not paid").

### Likelihood Explanation
This triggers deterministically for any collateral/output token integrated into intents that implements a non-reverting failure mode on `transfer` (a known, common real-world ERC20/TRC20 pattern — blacklist tokens, upgradeable/pausable tokens, tokens with transfer allowlists). No malicious relayer, prover, or governance action is required; the condition is purely a property of the token contract used in an order, combined with normal, authenticated protocol flow (`onAccept`/`onGetResponse` after legitimate ISMP proof verification). Any order denominated in such a token that later becomes blacklisted/paused for the beneficiary, or any newly-added token with this behavior, hits this path.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `SafeERC20.safeTransfer`, consistent with the mainline `IntentsBase.sol` implementation, so that a `false` return value reverts the transaction and escrow/fee accounting is only mutated on a proven successful transfer. Apply this to `withdraw()`'s escrow loop, the transaction-fee payout, and the `SweepDust` handler.

### Proof of Concept
1. Add a pool/order input using a TRC20/ERC20 token `T` whose `transfer(to, amount)` returns `false` (instead of reverting) when `to` is blacklisted or the contract is paused — a documented real-world token behavior.
2. Create and fill/escrow an order with token `T` normally via the standard intent flow.
3. Cause the beneficiary address to become blacklisted/paused on token `T` (a token-level condition, not requiring any privileged Hyperbridge role).
4. Trigger settlement: hyperbridge delivers a legitimate `RedeemEscrow`/`RefundEscrow` message (or the GET-response cancellation path), invoking `withdraw()`.
5. `token.call(...)` succeeds (`success == true`) because the token contract executes normally and just returns `false`; no funds move to `beneficiary`.
6. `_orders[commitment][token] -= amount` still executes and `_filled[commitment]` is set — the order is now permanently marked as settled, and the escrowed `T` tokens remain stuck in `IntentGatewayV2` with no beneficiary able to reclaim them.
