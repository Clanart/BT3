### Title
Unvalidated ECDH public keys in PedPoP allow forcing a publicly-known cipher key, leaking DKG secret shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the ZimaOS report (a user-supplied parameter is used to reach data outside the intended trust boundary without validation), PedPoP accepts attacker-supplied points used as ECDH inputs without rejecting the identity element. A malicious participant can register the identity point as their encryption key, or set the per-message `key` of an `EncryptedMessage` to identity, causing the ECDH shared point — and therefore the ChaCha20 keystream key — to be the publicly computable identity encoding. Secret-share ciphertexts then decrypt for any observer, not just the intended recipient.

### Finding Description
`EncryptionKeyMessage::read` deserializes `enc_key` via `C::read_G`, the base `Ciphersuite::read_G`, which only enforces canonical encoding — it does not reject the identity point (crypto/dkg/pedpop/src/encryption.rs:57-59, crypto/ciphersuite/src/lib.rs:91-101). Likewise `EncryptedMessage::read` accepts an identity `key` (crypto/dkg/pedpop/src/encryption.rs:171-177). Contrast with FROST's `Curve::read_G`, which explicitly rejects identity (crypto/frost/src/curve/mod.rs:125-131); PedPoP is generic over `Ciphersuite`, not `Curve`, so that check does not apply.

Encryption computes `ecdh(private, public) = public * private` (encryption.rs:95-97) and derives the ChaCha20 key solely from `context` and the shared point's public encoding (encryption.rs:101-118). If `enc_key` (or `msg.key`) is the identity, the shared point is the identity, whose bytes are fixed and public. `Decryption::register` stores the key with no validity check (encryption.rs:351-362), and `encrypt` uses it directly (encryption.rs:466).

### Impact Explanation
In a PedPoP session, a malicious participant registering `enc_key = identity` makes every encrypted secret share addressed to them decryptable by anyone who observes the ciphertext (e.g., on the broadcast channel). Alternatively, a malicious sender sets `msg.key = identity` so the share they transmit to an honest victim is world-readable while still passing the Schnorr PoP. In either case, `f_j(i)` values — secret key shares, the protected resource "outside the intended directory" — are disclosed publicly, degrading the threshold assumption: an attacker who additionally controls t-1 shares (or later compromises them) recovers the key. This is a concrete secret-leakage path reachable purely with attacker-chosen bytes fed to `EncryptionKeyMessage::read` / `EncryptedMessage::read` and then `calculate_share`.

### Likelihood Explanation
Requires a malicious DKG participant (or malicious sender) — within scope since shares/messages are attacker-influenced public inputs. No colluding-threshold assumption is needed for the leak itself; impact is partial share disclosure, which is why this maps to Medium rather than High.

### Recommendation
Reject the identity point when reading `enc_key` and `EncryptedMessage::key`, e.g., check `point.is_identity()` after `C::read_G` in `EncryptionKeyMessage::read` (encryption.rs:58) and `EncryptedMessage::read` (encryption.rs:173), mirroring `Curve::read_G`'s identity rejection.

### Proof of Concept
```rust
// Attacker's EncryptionKeyMessage: msg || enc_key where enc_key is the
// canonical identity encoding
let mut bytes = commitments.serialize();
bytes.extend(C::G::identity().to_bytes().as_ref());
let msg = EncryptionKeyMessage::<C, Commitments<C>>::read(&mut bytes.as_slice(), params).unwrap();
// msg.enc_key == identity; accepted with no error
// Every encrypt() to this participant produces ecdh = identity, so the
// ChaCha20 keystream is derivable by any observer from context alone.
```
