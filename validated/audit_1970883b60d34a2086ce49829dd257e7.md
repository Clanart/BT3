### Title
Incomplete BIP-340 parity handling — only the nonce `R` is normalized, never the group key `A`, producing consensus-invalid signatures for odd-Y aggregate keys - (File: networks/bitcoin/src/crypto.rs)

### Summary
CVE-2016-9936 is an *incomplete fix*: the PHP `unserialize` path was patched for CVE-2015-6834 but a residual path still allowed a use-after-free. The analog in Serai is the BIP-340 compatibility layer in `networks/bitcoin/src/crypto.rs`: it correctly normalizes the *nonce* parity (negating the challenge when `R` is odd, negating `s` when `R` is odd), but never normalizes the *group key* `A` to its even-Y form. BIP-340 requires verification against the even-Y lift `P = lift_x(x(A))`, which equals `-A` when `A` has odd Y. Since `ThresholdKeys` group keys have ~50% probability of odd Y, and nothing in `Hram`, `sign_share`, or `verify` negates the effective secret share / challenge for odd `A`, any `SignableTransaction` spend from such a key produces a signature that fails Bitcoin consensus verification — funds the `Scanner` reports as received are permanently unspendable.

### Finding Description
`Hram::hram` (`networks/bitcoin/src/crypto.rs:59-73`) computes the BIP-340 challenge `c = H(R.x || A.x || m)` and applies `conditional_select(&c, &-c, needs_negation(R))` — negating `c` when `R` is odd so the final `s` can be negated. `Schnorr::verify` (`networks/bitcoin/src/crypto.rs:139-150`) internally verifies `sum·G == R + c·A` via `FrostSchnorr::verify`, then emits `s' = -s` iff `R` is odd (equivalently `R' = -R` even).

The math only works when `A` is already even-Y:

- `R` odd, `A` even: signed share is `s = r − c·a`, output `s' = −s`, giving `s'·G = R' + c·A = R' + c·A_even`. Valid.
- `A` odd (`A_even = −A`): consensus requires `s'·G = R' + c·(−A)`. The code produces `s'·G = R' + c·A` — off by `2c·A`. **Always invalid.**

There is no `needs_negation(A)`-based normalization anywhere: `sign_share` (`crypto.rs:128-136`) delegates verbatim to the inner algorithm using `params.secret_share()` unmodified, and `TransactionMachine`/`TransactionSignMachine` (`networks/bitcoin/src/wallet/send.rs:273-398`) feed `keys.clone().offset(self.offsets[i])` straight into `AlgorithmMachine::new(Schnorr::new(), ...)` with no parity fix-up. Meanwhile `p2tr_script_buf` / `x_only` (`crypto.rs:13-23`) drop the sign bit, so the output script commits only to `x(A)` — the parity mismatch is invisible at receive time. The `Scanner` will happily report outputs to `x(A)` as received, yet `multisig()`/`sign`/`complete` can never emit a consensus-valid witness for them when `A` is odd.

### Impact Explanation
**Funds reported received that are not spendable** — an explicitly accepted impact class. For any threshold key whose `group_key` (after offsets) has odd Y coordinate — probability ~1/2 for an unbiased key — every Taproot key-spend signature produced by `TransactionMachine` is mathematically guaranteed to fail BIP-340 verification (`sG = R + c·A` vs. required `sG = R + c·(−A)`). Bitcoin nodes reject the transaction; the UTXOs are unspendable through this code path with no recovery mechanism in-crate. Unlike a probabilistic exploit, this is deterministic per key.

### Likelihood Explanation
Not attacker-steerable (DKG commitments prevent biasing parity), but unconditional once an odd-Y key exists: every spend attempt fails 100% of the time regardless of retries, preprocesses, or signing sets, since parity of `A` is fixed by the key itself.

### Recommendation
When `needs_negation(group_key)` is true, treat the effective secret share as `−a`: equivalently, negate the challenge contribution for the key (in `Hram` or in `sign_share`/`verify_share` via `params.secret_share()`/`verification_share`), so the produced `s` satisfies `s·G = R + c·A_even`. Standard fix: in `Schnorr::sign_share`, pass `params` with the secret share negated when `A` is odd (and likewise negate `verification_share` in `verify_share`), keeping the existing `R`-parity handling unchanged. Alternatively, offset all keys to even-Y at `multisig()`/`ThresholdKeys` construction time and require it as an invariant.

2. Build a `SignableTransaction` spending a `p2tr_script_buf(x_only(group_key))` output; `Scanner`/`multisig()` accept it since parity is dropped.
3. Complete FROST signing via `TransactionMachine` → `TransactionSignMachine::sign` → `TransactionSignatureMachine::complete`.
4. The emitted 64-byte witness `s'` satisfies `s'·G = R' + c·A` internally (`FrostSchnorr::verify` passes at `crypto.rs:145`), but consensus checks `s'·G == R' + c·lift_x(x(A))` where `lift_x = −A`; fails for every input. `bitcoinconsensus`/BIP-340 `Verify` rejects → transaction invalid, UTXO unspendable.
