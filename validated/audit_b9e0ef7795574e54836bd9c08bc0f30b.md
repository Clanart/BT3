### Title
`ReceivedOutput::read` accepts attacker-crafted bytes pairing an arbitrary scalar offset with an arbitrary `TxOut`, yielding "received" outputs that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to CVE-2017-6820 (a parser/sanitizer accepting a crafted token sequence that violates the expected structure), `ReceivedOutput::read` deserializes its three fields independently — `offset`, `output`, `outpoint` — and never validates the core invariant of the type: that `output.script_pubkey` equals `p2tr_script_buf(key + G * offset)` for the scanner's key, and that `outpoint` actually references `output`. An unprivileged party who can feed bytes into `ReceivedOutput::read` (e.g., via relayed/persisted output records) can fabricate a `ReceivedOutput` claiming spendability by the group key when the underlying UTXO is anyone's — or nonexistent.

### Finding Description
`Scanner::scan_transaction` is the honest producer: it only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` matches a script derived from the registered key plus offset, and it binds the real `OutPoint` from `tx.compute_txid()` (`mod.rs:199-214`). The deserializer performs no such binding: [1](#0-0) 

`read` accepts:
1. Any canonical scalar as `offset` (`Secp256k1::read_F`).
2. Any consensus-valid `TxOut` — including a script_pubkey that is not a P2TR output of `key + G*offset`, an attacker-owned address, or dust.
3. Any `OutPoint` — including one referencing a transaction that never contained this output.

Every accessor (`offset()`, `output()`, `outpoint()`, `value()`) then faithfully reports the fabricated claims (`mod.rs:99-118`), and downstream signing code would construct a `SignableTransaction` over an outpoint/spend-key pair that cannot authorize the spend.

### Impact Explanation
Funds reported received that are not spendable: a forged `ReceivedOutput` reports `value()` and an outpoint that the multisig cannot sign for (the derived tweak `key + G*offset` does not correspond to the script_pubkey, or the UTXO doesn't exist / is already spent). If an integrator persists or relays scanner results through this deserialization path — which the API explicitly supports via `serialize`/`read` round-trips (`mod.rs:120-148`) — an attacker who supplies or tampers with these bytes causes incorrect accounting and failed/griefed spends, matching the Medium-severity, low-integrity-impact profile of the source CVE.

### Likelihood Explanation
Exploitation requires the attacker to control bytes later deserialized via `ReceivedOutput::read`. The type is a public serialization format (`serialize`, `write`, `read` are all public), so any storage, message-queue, or RPC handoff of outputs between components exposes the path. No key material or collusion is needed; crafting the bytes is trivial since all three fields are unconstrained attacker input. It is less reachable than a pure on-chain attack (which is why the scanner path is safe but the read path is not), consistent with Medium severity / UI:R-style interaction.

### Recommendation
Make `ReceivedOutput::read` (or a required post-read validation) verify the invariant: recompute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` and reject inputs whose `output.script_pubkey` differs. Since `read` doesn't know the scanner key, add a `verify(&self, key: &ProjectivePoint) -> bool` method and/or have `Scanner` expose a `validate_output` helper that integrators must call after deserialization. The outpoint cannot be self-validated, so documentation should also require confirming the outpoint on-chain before treating the output as spendable.

### Proof of Concept
```rust
// Attacker crafts bytes: valid scalar + their own P2PKH TxOut + fake outpoint
let mut buf = Vec::new();
buf.extend(Scalar::ZERO.to_bytes()); // claims "no offset needed"
let attacker_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: ScriptBuf::new_p2pkh(&attacker_pubkey_hash), // not spendable by group key
};
buf.extend(serialize(&attacker_txout));
buf.extend(serialize(&OutPoint::new(attacker_txid, 0)));

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted
assert_eq!(forged.value(), 1_000_000); // reports funds "received"
// forged.output().script_pubkey != p2tr_script_buf(key + G*offset)
// -> any spend attempt using offset() fails script verification
```
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) returns `Ok` despite the output violating the key/offset/script binding that `Scanner::scan_transaction` enforces at production time (`mod.rs:199-214`).

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
