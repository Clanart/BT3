### Title
Attacker-controlled length in `ThresholdKeys::read` causes large up-front allocation (memory DoS) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts a u16 `n` field from untrusted bytes and immediately performs `Vec::with_capacity(usize::from(n))` when the interpolation tag selects `Constant`. A ~10-byte input therefore forces an allocation of `65535 * size_of::<C::F>()` (~2 MiB for 32-byte scalar types, ~4 MiB for 64-byte `ed448` scalars) before any payload is actually validated. Repeated or concurrent calls let an unauthenticated sender amplify a tiny message into large transient heap allocations, exhausting memory — the same CWE-770 class as GHSA-v42f-hq78-8c5m.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` as raw u16s, then a one-byte interpolation selector. For selector `0` it does:

```rust
// crypto/dkg/src/lib.rs ~604-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

`n` is fully attacker-controlled (0..=65535) and is not bounds-checked against `t`, the remaining input length, or any protocol maximum before `Vec::with_capacity` runs. `ThresholdParams::new` validation happens only afterward, inside `ThresholdKeys::new`, so the allocation occurs before parameter sanity checks. The same `n` also drives a `HashMap` fill loop reading `n` group elements for `verification_shares`, but that path fails fast; the `with_capacity` call is the amplification primitive: it allocates `n * size_of::<F>()` from a 2-byte length field with zero bytes of backing data required.

Reachability is explicit per the allowed surface: `ThresholdKeys::read` is a listed public deserialization entry point for untrusted bytes, and `EncryptedMessage::read`/`read_share` paths in the DKG (`crypto/dkg/src/lib.rs`, `crypto/dkg/pedpop/src/encryption.rs`) similarly hand attacker-controlled streams into these readers.

### Impact Explanation
- 2-byte `n` → up to ~2–4 MiB heap allocation per call with no data needing to exist afterward.
- Memory is dropped when `read_F` hits EOF, but allocations are transient only per-call; an attacker issuing many concurrent `ThresholdKeys::read` invocations (or embedding this read inside higher-level message handling that retains the `Vec`) can multiply memory pressure by ~10^5x input size, crashing the process (OOM) — matching the CWE-770 DoS pattern of the reference advisory.

### Likelihood Explanation
The reader is reachable wherever untrusted bytes are deserialized into `ThresholdKeys` (explicitly in scope). No authentication, proof, or correct `t`/`n` relationship is needed to trigger the allocation — the check ordering means even a 10-byte truncated input triggers `with_capacity(65535)`. Exploitation requires only repeated/concurrent submissions.

### Recommendation
- Remove `Vec::with_capacity(n)` and instead grow incrementally (`res.push` without pre-reservation), so allocation tracks bytes actually present.
- Alternatively, before allocating, cap `n` against a protocol maximum and/or verify `reader` has at least `n * F::Repr::SIZE` bytes available, and validate `ThresholdParams`-style constraints (`t <= n`, `i <= n`) prior to any length-proportional allocation.

### Proof of Concept
```rust
use std::io;
// bytes: ID(len+bytes matching C::ID) || t=1 || n=0xFFFF || i=1 || interp=0
let mut bytes = vec![];
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(1u16.to_le_bytes());      // t
bytes.extend(0xFFFFu16.to_le_bytes()); // n = 65535
bytes.extend(1u16.to_le_bytes());      // i
bytes.push(0);                         // Interpolation::Constant
// No further bytes: still allocates ~65535 * size_of::<C::F>() before failing
let res = ThresholdKeys::<C>::read(&mut bytes.as_slice());
assert!(res.is_err()); // fails — but only after the multi-MiB with_capacity
```
