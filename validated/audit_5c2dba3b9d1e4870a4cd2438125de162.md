### Title
ProtoJSON key-cloaking via alternate field-name spellings bypasses duplicate-key rejection — ([File: python/google/protobuf/json_format.py])

### Summary
Python's ProtoJSON parser (`json_format.Parse`) enforces a "duplicate key" check on the raw JSON object using `json.loads(text, object_pairs_hook=_DuplicateChecker)`, which rejects only *exact string* duplicates of a JSON key. [1](#0-0)  However, field resolution afterward accepts multiple textual spellings that alias to the *same* protobuf field — the canonical `json_name` (lowerCamelCase) and the raw proto `name` (snake_case) — via `fields_by_json_name` and a fallback to `fields_by_name`. [2](#0-1)  Because the duplicate-key checker never normalizes these aliases, a JSON object containing two differently-spelled keys that both resolve to the same field (e.g. `"int32Value"` and `"int32_value"`) passes the uniqueness check untouched, and the second occurrence silently overwrites the first with "last-one-wins" semantics — with no error raised.

### Finding Description
This is the direct Protobuf analog of CVE-2021-23336 (parameter cloaking): the external CVE showed that `urllib.parse.parse_qsl`/`parse_qs` allowed two different query-parameter delimiter conventions (`&` vs `;`) to represent "the same" logical parameter set differently across a proxy and an application, so a value could be smuggled past a cache-key/validation layer that only understood one delimiter convention, while the backend interpreted the differently-delimited/duplicated parameter.

The Protobuf analog: ProtoJSON allows the *same logical field* to be addressed by two textually distinct JSON key spellings (`json_name` lowerCamelCase, and the proto field's own `name` in snake_case, or `json_name` overrides). The invariant that "duplicate JSON keys are rejected to guarantee deterministic, unambiguous parsing" is implemented as a raw-string equality check performed **before** field-name resolution, so it never sees the two spellings as duplicates of the same field. [1](#0-0)  The Protobuf project itself acknowledges this exact class of ambiguity as a known, documented problem in the JSON/Editions design docs: "Conflicting mappings lead to undefined behavior... inconsistent across runtimes and unexpected." [3](#0-2)  The bug is explicitly reproduced and labeled "non-spec... oversight bug" in the Python conformance test suite itself:

```python
def testDuplicateFieldAlternateNames(self):
    # Note: this behavior is non-spec and an oversight bug in the
    # implementation, but would be a breaking change to fix. The duplicate field
    # checker intends reject inputs with duplicate key names, but it only
    # catches keys that are exact matches and not alternate spellings that
    # correspond to the same field.
    parsed_message = json_format_proto3_pb2.TestMessage()
    json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
    self.assertEqual(parsed_message.int32_value, 2)
``` [4](#0-3) 

The same holds for map fields, giving the same cloaking effect for map keys:
```python
def testDuplicateFieldAlternateNamesMap(self):
    ...
    json_format.Parse('{"int32Map": {"1": 2}, "int32_map": {"3": 4}}', parsed_message)
    self.assertEqual(parsed_message.int32_map, {3: 4})
``` [5](#0-4) 

Note this differential also exists between backends: the C++/upb `internal/parser.cc` implementation performs duplicate detection on the *resolved* `Field<Traits>` object (`RecordAsSeen(*field, msg)`, `SeenState::kFieldAlreadySeen`) rather than on the raw text key, so cloaking via alternate spellings is caught there in strict (non-legacy) mode — meaning behavior genuinely diverges between the Python pure implementation and the C++/upb JSON parser for the same bytes. [6](#0-5) 

### Impact Explanation
The invariant broken is "ProtoJSON parsing of a message from a single JSON payload must be deterministic and free of key ambiguity" (the same invariant that CVE-2021-23336's ecosystem relies on for consistent parameter interpretation across components). In a consuming application, this enables a parameter/field-cloaking attack: if a policy/validation/logging layer inspects the JSON payload's canonical field name (e.g. `int32Value`) to make a security decision (e.g. a value range check, an authorization amount, a routing key) while the actual `json_format.Parse()` result silently takes the value from the alternate spelling key that appears later in the object, the validated value and the value that ends up in the parsed protobuf message can differ. This is a value-integrity/logic-bypass class impact (not memory-safety), directly analogous to the "safe request gets cached, malicious differently-keyed parameter gets served" pattern in the CVE. Impact is bounded by application-level trust in JSON key uniqueness for security decisions; it does not by itself grant memory corruption, RCE, or disclosure.

### Likelihood Explanation
Reaching this requires only calling the public `json_format.Parse()` API (pure-Python backend) with a bounded, attacker-supplied JSON string containing a schema-valid field addressed by two spellings — trivial for any external client sending ProtoJSON to a service using this code path. No privileged access, malicious schema, or unusual configuration is needed; it triggers for singular fields and map fields alike, and is already codified/reproduced in the project's own test suite as expected ("non-spec... oversight") behavior, confirming it is real and currently present.

### Recommendation
Perform duplicate/ambiguity detection in `_ConvertFieldValuePair` (or in the JSON loader) on the *resolved field* rather than (or in addition to) the raw JSON key string — i.e., track a `seen_fields` set keyed by `FieldDescriptor` (or field number) as each `name` is resolved to a field, and raise `ParseError` when a field is seen a second time, mirroring the `SeenState`-based approach already used in `src/google/protobuf/json/internal/parser.cc`. This closes the alias-based duplicate bypass and brings the Python pure implementation's semantics in line with the upb/C++ JSON parser, eliminating the cross-backend interpretation differential.

### Proof of Concept
Using the existing, already-checked-in Python conformance test as the concrete reproduction (pure-Python backend, trusted schema, bounded 40-byte payload):
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2

msg = json_format_proto3_pb2.TestMessage()
# "int32Value" (json_name) and "int32_value" (proto name) alias the same field.
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2  # No ParseError raised despite two keys for one field.
```
This matches `testDuplicateFieldAlternateNames` verbatim. [4](#0-3)  Contrast with the exact-duplicate case, which correctly raises:
```python
json_format.Parse('{"int32Value": 1,\n"int32Value":2}', msg)  # raises ParseError: duplicate key int32Value
``` [7](#0-6) 

**Uncertainty note:** I could not trace whether the C++ CPP-backed Python implementation (`pyext`) or the Ruby/PHP upb JSON decoders share this exact raw-key duplicate-check placement (only the pure-Python `json_format.py` and the `internal/parser.cc` Traits-based implementation were directly inspected within the given tool budget); the failure_list files (`failure_list_python*.txt`) reference related `FieldNameDuplicate*` conformance test names but not this specific alternate-name variant, suggesting it is not yet tracked as a known conformance failure outside this test file. A full multi-backend confirmation would need further inspection of `pyext`/upb Python binding code paths.

def _DuplicateChecker(js):
  result = {}
  for name, value in js:
    if name in result:
      raise ParseError('Failed to load JSON: duplicate key {0}.'.format(name))
    result[name] = value
  return result
```
