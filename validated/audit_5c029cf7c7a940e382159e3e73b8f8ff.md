### Title
Discard Selection uses a stale diff snapshot with `git apply --unidiff-zero`, allowing silent working-tree corruption on a TOCTOU race - ([File: app/src/lib/git/apply.ts])

### Summary
`discardChangesFromSelection` reverses only the lines picked by the user in the Changes view by re-serializing a **previously captured** `ITextDiff` + `DiffSelection` into a unified patch and feeding it to `git apply --unidiff-zero`. Unlike its sibling `applyPatchToIndex`, which re-fetches a **fresh** diff immediately before building the patch, `discardChangesFromSelection` never re-reads the working-directory file or re-diffs it — it trusts the diff object that was computed when the UI rendered the file, which can be arbitrarily older than the moment the user actually confirms the discard (there is a full popup/dialog round-trip in between via `DiscardSelection`). If the on-disk file changes in that window, the line offsets encoded in the patch no longer correspond to the current file content, and because the patch is built to accept reduced/zero context (`--unidiff-zero`), `git apply` can still succeed by applying the reversed hunk to the wrong location instead of failing outright.

### Finding Description
- `applyPatchToIndex` (staging) calls `getWorkingDirectoryDiff(repository, file)` right before building the patch, i.e., it always operates on a fresh diff: [1](#0-0) 
- `discardChangesFromSelection` (discarding) has no such re-fetch — it takes the `diff` argument as-is and formats/applies it directly: [2](#0-1) 
- The `diff` and `selection` reach this call only after passing through a confirmation dialog (`DiscardSelection`), which stores them as React props from the moment the popup was opened and only invokes the dispatcher when the user clicks "Discard Changes": [3](#0-2) 
- The same stale `diff` object also originates from `Changes`/`SeamlessDiffSwitcher`'s render-time state, which is snapshotted while `isLoadingDiff` and can lag behind the true working directory state during background refreshes: [4](#0-3) [5](#0-4) 
- `formatPatchToDiscardChanges` builds the hunk by dropping unselected "delete" lines and reversing selected add/delete lines, producing a hunk with reduced context around the target lines, then the caller sends it through `git apply --unidiff-zero --whitespace=nowarn`, a mode explicitly meant to tolerate low/zero-context unified diffs: [6](#0-5) [7](#0-6) 

The broken invariant: the code assumes the diff captured at render time still matches the file on disk at apply time. Nothing in the discard path revalidates that assumption (no re-diff, no hash/mtime check) before invoking `git apply`. This mirrors the report's pattern — a security-relevant decision (which bytes get overwritten) is made against a value (`msg_asset_id()`/here, the captured diff) that the very workflow itself can invalidate before the action executes.

### Impact Explanation
If the working tree is modified between diff capture and the user's click — e.g., by a git hook shipped in a cloned/fetched malicious repository (`post-checkout`, `post-merge`, smudge/clean filters), or any other process that appends/edits the same file while GitHub Desktop's status refresh is in flight — `git apply --unidiff-zero` can apply the low-context reversed hunk against the *new* file content at an offset that only loosely (or coincidentally) matches, rather than failing loudly. This silently corrupts the working copy: lines the user never intended to touch can be deleted/altered, and if the user subsequently commits and pushes, that corrupted content becomes part of the repository history without any error being surfaced. This satisfies the "silent corruption of what the user commits or pushes" impact class and requires only a malicious repo/hook the user has cloned/fetched — no local/admin access or pre-existing malware.

### Likelihood Explanation
Requires precise timing (repo-controlled hook or filter firing during the render→confirm window) and a file whose content is being actively concurrently modified, so it is not trivially reliable, but the attacker fully controls the trigger (hooks execute automatically on checkout/merge/fetch operations Desktop itself performs) and the confirmation dialog intentionally introduces a delay that widens the race window. No user action beyond the normal "select lines → discard → confirm" flow is needed.

### Recommendation
Re-fetch the working-directory diff for the file immediately before formatting/applying the discard patch (mirroring `applyPatchToIndex`'s pattern), and validate that the current diff for the affected hunks is unchanged (or re-map the selection against the fresh diff) before calling `git apply`. Consider avoiding `--unidiff-zero` for user-facing discard operations or requiring full context validation so `git apply` fails safely instead of applying to the wrong offset when the file has drifted from the captured diff.

### Proof of Concept
1. Attacker ships a repo with a `post-checkout`/`post-merge` hook (or a smudge filter) that appends/edits a tracked file shortly after checkout completes.
2. User opens the file in the Changes view (diff/selection captured), selects some lines to discard, and the "confirm discard" dialog opens (`askForConfirmationOnDiscardChanges` is Desktop's default).
3. While the dialog is open, Desktop's background status refresh or the malicious hook rewrites the file on disk, shifting line offsets.
4. User confirms discard; `discardChangesFromSelection` builds the patch from the now-stale `diff`/`selection` and applies it via `git apply --unidiff-zero` against the mutated file — the reduced-context hunk applies at an unintended offset instead of erroring, silently corrupting content the user did not intend to discard, which can then be committed/pushed. export async function discardChangesFromSelection(
```typescript
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
```

```typescript
export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}
```
