Based on my investigation, I found a direct structural analog to the TurboSafe `less()` bug in the EVM Intent Gateway's same-chain fill logic.

### Title
Escrow-release shortcut in `_fillSameChain` can release funds reserved for a different order leg, causing wrong-beneficiary payout and locked/unredeemable escrow - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
Just like `TurboSafe.less()` substituted `feiDebt` (an unrelated live balance) for "the actual amount withdrawn" and let that wrong number update a shared accounting map, `_fillSameChain` in `IntrinsicIntents.sol` substitutes `_orders[commitment][token]` — the *entire current escrow balance for a token address* — for "the proportional escrow owed to this specific output leg" whenever a single output leg reaches its `totalRequired`. `_orders` is keyed only by `(commitment, tokenAddress)`, not by output index, so if two output legs of the same order share an input token address, finishing one leg first drains escrow that was reserved for the other leg.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:116-121`):

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

When a given output index `i` is fully satisfied (`amountFilled == totalRequired`), the code does not compute the proportional/remaining share owed for *that specific leg*; instead it reads the whole current balance stored at `_orders[commitment][token]`. That storage slot is shared across every `order.inputs[j]` entry that happens to reference the same token address, keyed only by `(commitment, token)`:

```solidity
mapping(bytes32 => mapping(address => uint256)) public _orders;
``` [2](#0-1) 

`_withdraw` then decrements exactly that computed `escrowedAmount` from the shared slot and transfers it out:

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
``` [3](#0-2) 

If an order has two output legs whose `order.inputs[i].token` is the same address (e.g., one input asset backing two separate output legs/beneficiaries, or two legs of the same asset with different output tokens), and leg A is completed in a fill before leg B, leg A's "full release" branch grabs the *entire remaining* `_orders[commitment][token]` balance — including the portion that was escrowed to fund leg B — not just leg A's proportional share. This mirrors the TurboSafe pattern exactly: a value meant to represent "amount attributable to this specific unit of work" is replaced by an unrelated aggregate/live value, and that wrong value is fed into the accounting/transfer path.

### Impact Explanation
Two concrete Impact-Gate-eligible outcomes follow:
1. **Wrong beneficiary/amount payout** — the solver filling leg A first receives tokens that were escrowed to satisfy leg B, an unauthorized transfer of value away from its rightful destination.
2. **Fund lock / broken settlement** — leg B's subsequent fill calls `_withdraw` for the same token, finds `_orders[commitment][token] == 0` (or under-funded), and reverts with `UnknownOrder` (`IntentsBase.sol:401`), permanently stranding the user's order in a partially-filled, unresolvable state — the same "permanently occupied/broken invariant" class judged Medium in the source report.

### Likelihood Explanation
This is reachable by any unprivileged solver simply by choosing fill amounts/order such that one output leg completes before another sharing an input token — no malicious relayer, prover, or governance actor is required, and no order-construction check was found in `IntentsBase.sol`/`IntrinsicIntents.sol` that forbids two `order.inputs[]` entries from sharing a token address. The condition only requires an order whose inputs contain a repeated token across indices, which is a normal, permitted intent shape (e.g., splitting one input asset across multiple output beneficiaries/calls).

### Recommendation
Track escrow release per output-leg index rather than by raw token balance: introduce a `_partialEscrowReleased[commitment][i]` (or track remaining amount per leg explicitly) so the "full release" branch computes `orderInputAmount[i] - alreadyReleased[i]` instead of reading the shared `_orders[commitment][token]` slot. Alternatively, disallow orders whose `inputs[]` contain duplicate token addresses at `placeOrder` time, or aggregate/validate that the sum of per-leg releases can never exceed each leg's own entitlement independent of sibling legs sharing the same token.

### Proof of Concept
1. User places a same-chain order with `inputs = [ {token: T, amount: 100}, {token: T, amount: 50} ]` (same token `T` funding two separate output legs, e.g. two different beneficiaries or two different output assets both requiring token `T` as source funding), escrowing a total of `150 T` into `_orders[commitment][T] = 150`.
2. Solver calls `fillOrder` providing `solverAmount` that exactly satisfies output leg `0` only (`totalRequired = 100`, `fillAmount = 100`). Since `amountFilled == totalRequired`, the code sets `escrowedAmount = _orders[commitment][T] = 150` (the full remaining balance, not `100`).
3. `_withdraw` decrements `_orders[commitment][T]` to `0` and transfers `150 T` to the leg-0 solver — `50 T` more than leg 0 was entitled to.
4. A second solver later attempts to fill leg `1` (`totalRequired = 50`). `_withdraw` reads `_orders[commitment][T] == 0` and reverts with `UnknownOrder`, permanently stranding leg 1 — the user's remaining intended output never gets filled, and the first solver received escrow belonging to the second leg.
