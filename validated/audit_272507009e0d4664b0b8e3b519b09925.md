### Title
`GeneratorPromotion::complete` panics on a missing participant's proof when the `proofs` map contains a superfluous key (e.g. the caller's own index) — ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary

Analogous to CVE-2023-3316 — where failing to acquire a resource (an output file handle) leads to a NULL dereference at use time inside `TIFFClose()` — `GeneratorPromotion::complete` fails to acquire a required resource (the `GeneratorProof` for each participant `i ∈ 1..=n, i != self`) and then dereferences it unconditionally via `HashMap::get(...).unwrap()`. The validation only checks the map's *length* and that no key exceeds `n`; it never verifies that every required participant index is actually present, nor that the caller's own index `params.i()` is absent. A panic in Rust is the direct equivalent of the NULL-deref crash: an attacker who can influence which `Participant` keys populate the `proofs` map causes an abort instead of a clean `PromotionError`.

### Finding Description

`complete` performs two checks before consuming proofs:

- `proofs.len() != n - 1` → `IncorrectAmountOfParticipants` (line 125)
- `u16::from(i) > params.n()` → `InvalidParticipant` (line 133) [1](#0-0) 

It then iterates every required index and does `let proof = proofs.get(&i).unwrap();` [2](#0-1) 

Because the length check counts `n - 1` entries but the key check only enforces `key <= n`, the following malicious map satisfies all checks:

- includes a key equal to `params.i()` (the verifying participant's own index — skipped by the `continue` at line 143, never dereferenced), and
- omits the key of one legitimate participant `i*`.

The map still has `n - 1` entries and all keys `<= n`, so validation passes, and `proofs.get(&i*).unwrap()` at line 146 panics. Compare with `validate_map` in `crypto/dkg/pedpop/src/lib.rs`, which correctly rejects both a map containing `ours` (`DuplicatedParticipant`) and a map missing an `included` entry (`MissingParticipant`) — the exact checks absent here. [3](#0-2) 

`GeneratorProof` messages themselves carry no participant index (`read` parses only `share` and `proof`), so the map key is assigned by the caller from whatever participant label accompanied the message on the wire — a value a malicious co-participant controls or can induce by, e.g., submitting a proof under the victim's index or equivocating labels. [4](#0-3) 

### Impact Explanation

Any participant in a generator-promotion session can crash the local promotion of every other participant by causing a `proofs` map that passes both validation checks while omitting a required index. This kills the affected process/task mid-protocol (denial of service), matching the medium-severity availability impact of the source CVE. Since promotion is a one-shot ceremony (`self` is consumed), a panic also forces a full ceremony restart for the victim.

### Likelihood Explanation

A single malicious participant suffices — no collusion or threshold of attackers is needed. Reaching the panic requires the attacker's proof (or absence thereof) to leave exactly one required index missing while keeping `len == n - 1`, which is achievable whenever a participant can have their message keyed under an index that isn't iterated (the verifier's own `i`, the only `<= n` key skipped). The flaw is a deterministic logic gap, not a race or probabilistic condition.

### Recommendation

In `GeneratorPromotion::complete`, replace the length+range checks with a membership-driven validation mirroring `pedpop::validate_map`: reject if `proofs` contains `params.i()` (`DkgError::DuplicatedParticipant`/new variant) and reject with `InvalidParticipant`/`MissingParticipant` for every `i in 1..=n, i != params.i()` absent from `proofs`, before indexing. Then replace `proofs.get(&i).unwrap()` with `proofs[&i]` (now infallible) or a checked access.

### Proof of Concept

```rust
// crypto/dkg/promote: params: t = 2, n = 3, self i = 1
// Honest completion needs proofs for {2, 3}.
// Malicious participant 3 withholds their proof; participant 2's (or a replayed)
// message is keyed under Participant(1) — the caller's own index.
let mut proofs: HashMap<Participant, GeneratorProof<C>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof); // self-index key
proofs.insert(Participant::new(2).unwrap(), honest_proof);   // key 3 missing

// proofs.len() == 2 == n - 1  → passes line 125
// all keys (1, 2) <= n = 3     → passes line 133
// loop: i=1 skipped (continue), i=2 found, i=3 → proofs.get(&3).unwrap() PANICS
promotion.complete(&proofs); // thread panics; no PromotionError returned
```
