## Title
GitHub repository identity is keyed by mutable `(owner, name)` instead of GitHub's immutable repository ID, allowing silent overwrite of cached permissions/fork lineage/branch-protection state — ([File: app/src/lib/stores/repositories-store.ts])

### Summary
The external report's broken invariant is: an operation "transfers"/reassigns an identity-bearing record without checking whether the destination already holds a different value, silently destroying it. The Desktop analog is `RepositoriesStore`'s GitHub-repository cache: local records are looked up and overwritten solely by the `[ownerID+name]` composite key, never by GitHub's immutable numeric repository id. If a repository is deleted and a different repository is created under the exact same `owner/name` (fully within the repo owner's control), Desktop silently overwrites the existing cached identity (permissions, private flag, fork/parent chain, htmlURL/cloneURL) and re-associates it with the user's already-cloned local repository — with no check and no user-facing warning.

### Finding Description
`IDatabaseGitHubRepository` has no field for GitHub's immutable numeric repo id — only a mutable `name` and `ownerID`: [1](#0-0) 

The Dexie schema enforces this pair as the sole unique key for a GitHub repository record: [2](#0-1) 

`RepositoriesStore._upsertGitHubRepository` looks up the *existing* record purely by `[ownerID+name]` and, when found, overwrites its `private`, `htmlURL`, `cloneURL`, `parentID`, `permissions`, `issuesEnabled`, `isArchived` fields with whatever the API currently reports for that owner/name — there is no comparison against a stable repo id to confirm it's still the *same* repository: [3](#0-2) 

`upsertGitHubRepositoryFromMatch` (used as a fallback when the API fetch for a repo fails, e.g. because it was deleted) has the same identity assumption — it reuses any existing DB row matching `[ownerID+name]`: [4](#0-3) 

This record is then attached to the user's actual local, already-cloned working copy via `setGitHubRepository`, which persists the new `gitHubRepositoryID` on the local `Repository` row and returns an updated `Repository` object trusted by the rest of the app for permission/branch-protection decisions: [5](#0-4) 

This overwrite path is triggered automatically and silently during routine background refresh, via `repositoryWithRefreshedGitHubRepository`, which re-derives the match from the local git remote, fetches fresh data from the API, and calls `upsertGitHubRepository`/`setGitHubRepository` without ever checking whether the previously-known repository (by id) is still the one being returned: [6](#0-5) 

The companion `updateRemoteUrl` helper likewise reasons only about `owner`+`name` equality (via `urlMatchesRemote`), not repository identity, when deciding whether to leave the local remote alone: [7](#0-6) [8](#0-7) 

The same lookup-by-name reuse pattern also affects pull-request/fork ingestion, where `head`/`base` repos returned by the API are upserted through `upsertGitHubRepositoryLight`, keyed the same way: [9](#0-8) 

### Impact Explanation
Because the cached `GitHubRepository` record is keyed only by mutable `(owner, name)`, an attacker who fully controls a repository (owner of a fork the victim cloned, a collaborator repo, or an org repo) can:
1. Delete the repository the victim has locally cloned/associated in Desktop.
2. Create a brand-new, unrelated repository under the exact same `owner/name` with different `private`, `permissions`, or fork/`parent` metadata.

On the victim's next background refresh (`withRefreshedGitHubRepository`, triggered routinely on fetch/push/pull/selection), Desktop silently overwrites the cached identity for the victim's *existing, still-checked-out* local repository with the new repo's metadata — without any prompt, diff, or warning that the underlying GitHub-side identity changed. This corrupts the trust signals the app relies on (cached branch-protection state, permission level shown to the user, fork/parent lineage used to compute upstream relationships), and can misattribute pull-request/fork records tied to that database id. This matches the report's impact class: unprivileged, attacker-controlled repository/API data silently overwrites previously-trusted state that governs what the user believes about push/permission safety, with no documentation or confirmation of the behavior.

### Likelihood Explanation
The precondition — an attacker deleting and recreating a repository under the same owner/name — is entirely within the control of any GitHub account owner (no admin rights, no local access, no leaked credentials needed), and Desktop's refresh logic runs automatically and unattended in the background, so no unusual user action is required beyond normal use of Desktop against a repository controlled by an untrusted third party (a fork, an org repo, or a collaborator-shared repo).

### Recommendation
Store and key `GitHubRepository` records by GitHub's immutable numeric repository `id` (already present in `IAPIRepository`/`IAPIFullRepository` responses) rather than `[ownerID+name]`. When upserting, detect an id mismatch against the existing record for a given owner/name and treat it as a *new* repository (creating a new local record and, optionally, prompting the user) instead of overwriting the old one's cached permissions/fork lineage in place. At minimum, document that Desktop's repository-identity cache is name-based and can be invalidated by delete+recreate under the same name.

### Proof of Concept
1. Attacker creates `attacker/demo`, grants themselves collaborator "write" access, victim clones it and adds it to Desktop (creating a `GitHubRepository` DB row keyed `[ownerID(attacker), "demo"]` with `permissions: 'write'`, `parentID: null`).
2. Attacker deletes `attacker/demo`, then immediately creates a new, unrelated repository also named `attacker/demo` (e.g. private, or with a `parent` pointing at some other repository, or with `permissions: 'admin'`/`'read'` differing from before).
3. Victim's Desktop performs a routine background refresh; `matchGitHubRepository` re-derives `owner="attacker", name="demo"` from the unchanged local remote, `api.fetchRepository('attacker','demo')` returns the new repository's data, and `repositoryWithRefreshedGitHubRepository` calls `upsertGitHubRepository` → `_upsertGitHubRepository`, which matches the existing DB row by `[ownerID+name]` and overwrites `private`/`permissions`/`parentID`/`cloneURL` in place — then `setGitHubRepository` re-attaches this changed identity to the victim's still-checked-out local repository, with no warning shown to the victim that the underlying GitHub repository changed.

  public async setGitHubRepository(repo: Repository, ghRepo: GitHubRepository) {
    // If nothing has changed we can skip writing to the database and (more
    // importantly) avoid telling store consumers that the repo store has
    // changed and just return the repo that was given to us.
    if (isRepositoryWithGitHubRepository(repo)) {
      if (repo.gitHubRepository.hash === ghRepo.hash) {
        return repo
      }
    }

    await this.db.transaction('rw', this.db.repositories, () =>
      this.db.repositories.update(repo.id, { gitHubRepositoryID: ghRepo.dbID })
    )
    this.emitUpdatedRepositories()

    const updatedRepo = new Repository(
      repo.path,
      repo.id,
      ghRepo,
      repo.missing,
      repo.alias,
      repo.workflowPreferences,
      repo.isTutorialRepository,
      repo.gitDir,
      repo.mainWorktreePath
    )

    assertIsRepositoryWithGitHubRepository(updatedRepo)
    return updatedRepo
  }

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
