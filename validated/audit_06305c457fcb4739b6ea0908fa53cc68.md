### Title
Ed448 `is_torsion_free` always returns success, so `read_G` accepts torsion-bearing points - (File: crypto/ed448/src/point.rs)

### Summary
Analogous to the `bnxt_qplib_alloc_dpi` bug — where a failed `ioremap` was masked and success returned so callers proceeded with an invalid resource — `Point::is_torsion_free` in the Ed448 backend is a validation routine whose check can never fail. `Ed448::read_G` (via `Ciphersuite::read_G` in `crypto/ciphersuite/src/lib.rs`) relies on `Point::from_bytes`, which gates acceptance on `is_torsion_free`; that check unconditionally produces `Choice` true, so arbitrary 4-torsion components pass as valid, canonical points fed by untrusted bytes.

### Finding Description
`is_torsion_free` is implemented as [1](#0-0) :

```rust
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

`Scalar::ZERO - Scalar::ONE` is `-1`, so the expression computes `(-P) + P = identity` for **every** point — the check is a tautology. It was presumably intended to multiply by the cofactor (4) or test membership in the prime-order subgroup. `Point::from_bytes` calls it as the final validation gate [2](#0-1) , and the generic `Ciphersuite::read_G` used by `Ed448` performs only decompression plus a re-encode canonicality check — it does not re-check torsion [3](#0-2) . For Ed448 (cofactor 4), an encoding like `P + T` with `T` a low-order point decompresses, survives the canonical round-trip, and is accepted exactly as if the torsion "validation" had succeeded — the same failure-masked-as-success shape as the kernel bug.

Reachability: `Ed448::read_G` is invoked on untrusted bytes by `Commitments::read`, `DLEqProof::read`, `SchnorrSignature::read`, `ThresholdKeys::read`, and the PedPoP `EncryptedMessage::read` paths listed in scope — any peer-supplied point (verification share, nonce commitment, DLEq/PoK transcript element) can carry a torsion component.

### Impact Explanation
Because the torsion check is a no-op, the "prime-order group" contract of `PrimeGroup` is violated for Ed448:

- **Incorrect verifier formula / proof ambiguity.** `SchnorrSignature::verify` uses `sG == R + cA` via `batch_statements` [4](#0-3) . With `R = R' + T` (torsion `T`), distinct `(R, s)` encodings for the same logical signature validate, and a party can equivocate on the subgroup component of a commitment while the equations remain satisfiable — a forger has extra degrees of freedom the verifier formula was designed to exclude.
- **Small-subgroup leakage.** In PedPoP-style flows, a peer who submits a torsion-bearing public key/commitment causes the honest party's scalar multiplication (`our_secret * their_point`) to expose `our_secret mod 4` through the torsion component of the resulting ECDH/DLEq relation, leaking low-order bits of key material.
- **FROST blame corruption.** A torsion-bearing nonce commitment in `Commitments::read` produces `Rs` values whose low-order component makes honest-looking shares fail aggregate verification, letting a signer misdirect `InvalidShare` blame in `AlgorithmSignatureMachine::complete`.

The net effect matches the advisory's structure: a mandatory validation is evaluated, discarded, and success is returned, letting downstream cryptographic consumers operate on a resource (group element) that never actually passed validation.

### Likelihood Explanation
Any unprivileged counterparty able to send serialized points to an Ed448 deployment can trigger it: `DLEqProof::read`, `SchnorrSignature::read`, `Commitments::read`/`read_preprocess`, and PedPoP message reads all route through `read_G` → `Point::from_bytes` → the vacuous `is_torsion_free`. No threshold collusion, BFT assumption, or leaked key is needed — only the ability to supply crafted encodings. Exploitation severity is bounded by the small cofactor (2 leaked bits per ECDH, signature-malleability/equivocation leverage rather than full forgery), so it does not reach Critical, but it is a real, reachable integrity/verification failure.

### Recommendation
Replace the tautological check with a genuine subgroup-membership test. The minimal fix:

```rust
fn is_torsion_free(&self) -> Choice {
  // Multiply by the cofactor-independent subgroup order, or equivalently
  // verify the cofactor-cleared point scaled back equals self.
  // Cheapest correct form for cofactor 4: check 4*self has no torsion residual
  // by validating self equals an element of the prime-order subgroup, e.g.
  // via scalar multiplication by the group order or a dedicated cofactor test.
}
```

Concretely, either compute `self * group_order == identity` (using the scalar-field modulus, not `-1`), or implement `mul_by_cofactor` on `Point` and accept only points that decompress as torsion-free. Additionally, add a test asserting that `Point::from_bytes` rejects a generator-plus-torsion encoding (e.g., generator plus a known order-2 point `(0, -1)`-equivalent for Ed448), so the tautology cannot regress.
