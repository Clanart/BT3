### Title
Hookify rule loader resolves `.claude/hookify.*.local.md` relative to process CWD instead of a validated project root, allowing untrusted nested directories to inject enforcement rules - (File: plugins/hookify/core/config_loader.py)

### Summary
`load_rules()` builds its glob pattern with a bare relative path `os.path.join('.claude', 'hookify.*.local.md')` and resolves it via `glob.glob()` against whatever the process's current working directory happens to be, with no anchoring to a trusted/validated project root. Because every hookify hook (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules()` directly without passing or validating a root path, any mechanism that changes the hook subprocess's CWD to a nested, repo-controlled directory causes rules from that directory's `.claude/` folder to be loaded and enforced instead of (or in addition to) the top-level trusted rules.

### Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` does: [1](#0-0) 
This is a relative glob with no `os.getcwd()` validation, no anchoring to `CLAUDE_PROJECT_ROOT`/`CLAUDE_PLUGIN_ROOT`-derived project root, and no check that the resolved directory is the trusted top-level `.claude/`. Every hook entry point simply calls `load_rules(event=...)` and feeds the returned rules straight into `RuleEngine.evaluate_rules()`: [2](#0-1) 

The plugin's own documentation confirms the design assumes CWD equals "the project's .claude directory... current working directory (where Claude Code was started)" but never enforces that invariant in code: [3](#0-2) 

If a repository contains a nested subdirectory with its own `.claude/hookify.*.local.md` file, and the hook subprocess is executed with that subdirectory as CWD (e.g., because the user or an automated flow changed directories, or the session/tool was invoked from within a nested checkout), `glob.glob('.claude/hookify.*.local.md')` will pick up that nested, attacker-controlled rule file instead of (or in addition to) the top-level trusted rule set. Since rules can specify `action: block` and arbitrary regex-based conditions on `command`, `new_text`, etc., this grants untrusted repo content the ability to silently redefine what commands/edits are blocked or allowed for unrelated project directories/sessions — a workspace-confinement/target-binding violation. No allowlist, path canonicalization, or root-scoping check exists anywhere in `config_loader.py` to prevent this.

### Impact Explanation
Untrusted content checked into a nested directory of a repository can gain enforcement authority over hook decisions (`warn`/`block`) intended to apply only to the trusted top-level project, by exploiting an ambient-authority (CWD-based) resolution instead of a validated, session-bound project root. This is a workspace-confinement / trust-boundary violation: rule files are meant to be an explicit, reviewed opt-in mechanism placed in the top-level `.claude/`, but the loader's CWD-relative glob means nested/attacker-controlled `.claude/` folders can override or add enforcement policy without the user ever placing or reviewing those files at the trusted location.

### Likelihood Explanation
Exploitability depends on the hook subprocess's CWD actually diverging from the trusted top-level project root during a session (e.g., a Bash tool invocation changing directories, or a workflow that starts Claude Code from within a nested checkout containing its own `.claude/` rules). This is a plausible but non-default condition, not a directly attacker-triggered CWD change from pure repository content alone; it requires an external factor to alter the process CWD before/during a hook invocation. Given that requirement, the bug is real and reproducible whenever that precondition holds — the vulnerability is a genuine confinement gap, though it should be validated end-to-end against the actual hook invocation mechanism (e.g., how Claude Code sets CWD for hook subprocesses across tool calls) before assuming an ordinary session naturally reaches this precondition.

### Recommendation
Anchor rule loading to a validated project root rather than the ambient CWD: resolve the root via an explicit, trusted source (e.g., `CLAUDE_PROJECT_ROOT` env var set by Claude Code, or the initial session CWD captured once at session start) and use `os.path.join(validated_root, '.claude', 'hookify.*.local.md')`. Additionally, canonicalize the resolved rule directory with `os.path.realpath` and verify it equals the trusted project root before globbing, rejecting or ignoring any `.claude` directories discovered outside that root.

### Proof of Concept
Integration test plan:
1. Create a temporary directory tree: `top/.claude/hookify.top.local.md` (rule A, `action: warn`) and `top/nested/.claude/hookify.nested.local.md` (rule B, `action: block`, planted by "attacker" content checked into `nested/`).
2. Invoke `pretooluse.py` (or directly call `config_loader.load_rules()`) twice: once with `cwd=top`, once with `cwd=top/nested`.
3. Assert that when `cwd=top`, only rule A is loaded/enforced.
4. Assert that when `cwd=top/nested`, rule B (the nested/attacker rule) is loaded and enforced — demonstrating that CWD, not the top-level trusted root, determines which rules gain enforcement authority.
5. After the fix, re-run step 4 with `CLAUDE_PROJECT_ROOT=top` set, and assert only rule A loads regardless of process CWD.
