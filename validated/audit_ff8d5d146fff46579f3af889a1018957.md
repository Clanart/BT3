## Analysis

I traced the report's broken invariant — *"an attacker can manipulate untrusted external state that a privileged decision depends on, and the value is only checked lazily/without protection against attacker-controlled sources"* — into GitHub Desktop's credential‑helper trust logic.

### Title
Attacker-controlled server response can make GitHub Desktop's credential helper treat an arbitrary git host as a trusted "GitHub Enterprise" endpoint, triggering the real OAuth sign-in flow (and OAuth `client_secret` disclosure) against attacker infrastructure — (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's git credential helper (`getEndpointKind`) classifies a remote host as a trusted GitHub/GHE endpoint using several heuristics, one of which is simply reading the `WWW-Authenticate` HTTP header that the remote git server itself returned on a 401. If that header contains `realm="GitHub"`, Desktop immediately classifies the host as `'enterprise'` — with **no verification that the host is an actual GitHub Enterprise instance**. This is the exact analog of the `YAxisVotePower.balanceOf` issue: a value fully controlled by an untrusted counterparty (Uniswap reserves / here, an arbitrary git server's HTTP response header) is trusted directly for a decision with real consequences (voting power / here, "is this a GitHub host that deserves credentials and sign-in prompts").

The `realm="GitHub"` string is copied verbatim from the response the remote server sent to Git — it is fully attacker-controlled if the attacker runs the git server (e.g. a malicious `git remote`, a spoofed HTTP proxy in front of a legitimate remote, or a MITM on a plain-HTTP fallback). This bypasses the only real trust anchors available (`isDotCom`, `isGHE`, matching an existing `Account`).

The fallback path, `isGitHubHost` (`app/src/lib/api.ts:2429-2491`), has an additional weakness on its own: it treats *any hostname containing the label `github`* as a real GitHub host via a naive regex: [2](#0-1)

None of the app's existing guards stop this: `isDotCom`/`isGHE` only check `github.com`/`.ghe.com`, and there is no verification (e.g. TLS certificate pinning, or a check that the reported `realm` actually matches an already-known/allow-listed enterprise endpoint) before trusting either the `WWW-Authenticate` header or the `github.` regex.

### Impact Explanation
- The Desktop app's shared OAuth `client_secret` (baked into every installed build, see `docs/contributing/github-enterprise-auth-from-dev-build.md`) can be sent to an attacker-controlled server, since `requestOAuthToken` posts it to whatever `endpoint` the attacker's response steered the app toward.
- The user is shown Desktop's native "Sign in to GitHub" dialog while actually authenticating toward attacker infrastructure — a strong phishing primitive that borrows the app's own trusted chrome (unauthorized OAuth flow initiation, matching the allowed impact category "unauthorized OAuth or account binding").
- Because `getEndpointKind` short-circuits to `'enterprise'` purely from a response header, the attacker doesn't need to spoof `github.com`'s DNS or TLS cert at all — a benign-looking git remote is enough.

### Likelihood Explanation
This requires only that the victim add or use a git remote (or push/fetch/clone) pointing at a server the attacker controls or can MITM (e.g. a plain-HTTP git URL, a compromised proxy, or a deliberately shared malicious remote), which is a normal, unprivileged Desktop workflow (adding a remote / cloning a repo). No local access, no prior malware, and no leaked credentials are required — this matches the report's valid-impact criteria ("attacker controls...a git remote/proxy response").

### Recommendation
- Never derive trust ("enterprise"/GitHub classification) purely from an unauthenticated `WWW-Authenticate` header or from a loose hostname regex. Require the endpoint to be independently verified (e.g. only trust it if it matches an already-configured/allow-listed Enterprise `Account.endpoint`, or perform the same certificate/identity validation used for `isDotCom`/`isGHE`).
- Before invoking `promptForGitHubSignIn`/starting an OAuth flow, warn the user explicitly that they are about to authenticate against a *new, unverified* host derived from the git remote, and never auto-populate/auto-trigger sign-in silently from credential-helper heuristics.
- Consider not sending `client_secret` to enterprise endpoints that were only ever inferred by heuristics rather than explicitly confirmed via the manual "Add Enterprise account" endpoint-entry+validation flow (`_setSignInEndpoint`).

### Proof of Concept
1. Attacker stands up an HTTP(S) git server at `https://git.attacker.example/foo.git` that, on any credential-required request, returns `401` with header `WWW-Authenticate: Basic realm="GitHub"` (trivial to implement; no TLS trust to `github.com` needed).
2. Victim adds this as a remote (or clones it) in GitHub Desktop and performs a fetch/push.
3. Git invokes Desktop's trampoline credential helper `get` command with this URL; `getEndpointKind` sees the `wwwauth[...]` entry containing `realm="GitHub"` and returns `'enterprise'` (`trampoline-credential-helper.ts:157-165`).
4. Since no existing `Account` has `endpoint === apiEndpoint` for `git.attacker.example`, Desktop calls `ui.promptForGitHubSignIn('https://git.attacker.example')`, presenting the native GitHub sign-in dialog to the user.
5. If the user proceeds (a normal, expected action when prompted to "sign in to GitHub" by the app they trust), the browser is opened to `https://git.attacker.example/login/oauth/authorize?client_id=...`, and upon completion `requestOAuthToken` POSTs `client_id`/`client_secret`/`code` to `https://git.attacker.example/login/oauth/access_token` — both attacker-observable.

Note: I was not able to fully trace `trampolineUIHelper.promptForGitHubSignIn` → `SignInStore` wiring within the available index (only `dispatcher.beginEnterpriseSignIn`/`_setSignInEndpoint` and the OAuth token exchange functions were directly inspected), so the exact intermediate validation performed by `_setSignInEndpoint` (which may attempt a `/meta` connectivity check before allowing sign-in) is not fully confirmed here. Since that file's full contents were not returned by search, I recommend a Devin session with full repo access to confirm whether `_setSignInEndpoint`'s connectivity check meaningfully blocks a cooperating attacker server (which can trivially forge any expected response) before treating this as fully proven end-to-end.

export function getOAuthAuthorizationURL(
  endpoint: string,
  state: string
): string {
  const urlBase = getHTMLURL(endpoint)
  const scope = encodeURIComponent(oauthScopes.join(' '))

  return new window.URL(
    `/login/oauth/authorize?client_id=${ClientID}&scope=${scope}&state=${state}`,
    urlBase
  ).toString()
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
