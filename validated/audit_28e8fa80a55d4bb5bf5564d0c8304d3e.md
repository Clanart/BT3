### Title
OP_RETURN `data` output is excluded from the weight/vbytes used to compute `needed_fee`, letting its cost bypass the fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` computes `needed_fee` as `fee_per_vbyte * vbytes`, but the vbytes are measured on a transaction that contains only the payment outputs (and optionally change). When `data` is supplied, an OP_RETURN output is pushed into `tx_outs` before the weight calculation, yet `calculate_weight_vbytes` is called with `payments` only — the data output is never included in the measured transaction, so its weight is never paid for.

### Finding Description
The Vault bug class is "a proportional fee rounds down / is skipped because the charged base doesn't cover the full operation." In Serai's Bitcoin wallet, the fee is proportional to transaction vbytes, but the measured vbytes omit one entire output:

- `calculate_weight_vbytes` builds a `Transaction` whose outputs come solely from `payments` (plus optional `change`) [1](#0-0) 
- `SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` carrying up to 80 bytes of user-controlled data [2](#0-1) 
- The weight/vbytes and `needed_fee` are then computed *without* that output [3](#0-2) 

`weight` is only ever replaced by the change-inclusive variant; there is no path that re-measures with the data output [4](#0-3) . The actual fee paid is `sum(inputs) - sum(outputs)` — exactly `needed_fee` when there is no change [5](#0-4)  — so the ~83–90 extra vbytes of the OP_RETURN output (80-byte push + script/key overhead) are broadcast but never charged.

The minimum-relay-fee check is also run against the underestimated `vbytes`, so a `fee_per_vbyte` exactly at the relay minimum passes the check while the real transaction is below the node's minimum feerate [6](#0-5) .

### Impact Explanation
Any caller of `SignableTransaction::new` (or integrators embedding data in Serai-built transactions) pays zero fee for up to ~90 vbytes of transaction size — the fee-rate guarantee `fee_per_vbyte` is silently violated, and a transaction constructed at the minimum relay fee is actually under the relay minimum, risking non-propagation or eviction under mempool pressure. This is the same economic flaw as the Vault finding: an operation (the data output) whose cost base is omitted from the proportional fee, reached with purely public inputs (`data` bytes chosen by the caller).

### Likelihood Explanation
The bypass is unconditional whenever `data` is `Some` — no edge cases or adversarial ordering required. The magnitude is bounded (~90 vbytes per transaction), keeping this at Medium rather than High.

### Recommendation
Include the OP_RETURN output in the size estimate: pass the data script (e.g., extend `payments` with `(op_return_script, 0)` or add a `data` parameter) into `calculate_weight_vbytes` so `vbytes`/`weight` reflect the final transaction, including for the change-inclusive variant.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, &payments, change, Some(vec![0u8; 80]), fee_per_vbyte)`.
2. Compare `signable.needed_fee()` against `fee_per_vbyte * actual_tx_vbytes`: the serialized `tx` contains the extra `TxOut` with the 80-byte `ScriptBuf::new_op_return`, yet `needed_fee` equals `fee_per_vbyte` times the size *without* it.
3. `signable.fee()` (inputs − outputs, with no change) equals `needed_fee`, confirming the data output's weight is never paid for.
