## Analog Found

### Title
Tokenfactory admin authorization and per-denom `AllowList` are independently managed, causing `Mint`/`Burn`/transfer operations to silently fail for a validly-authorized admin - (File: x/tokenfactory/keeper/msg_server.go)

### Summary
The reported bug class is that two independent access-control mechanisms (blacklist and minter-role) are administered without cross-validation, so a legitimately privileged actor can become unable to perform mint/burn/transfer operations. The same structural flaw exists in `x/tokenfactory`: the module's admin-authorization check (`authorityMetadata.GetAdmin()`) is completely decoupled from the per-denom `AllowList` mechanism enforced by the bank keeper.

### Finding Description
`x/tokenfactory` denoms can optionally have an `AllowList` set via `MsgCreateDenom` or `MsgUpdateDenom`, stored through `bankKeeper.SetDenomAllowList` [1](#0-0)  and [2](#0-1) . Separately, `Mint`, `Burn`, and `ChangeAdmin` are authorized purely by comparing `msg.Sender` to `authorityMetadata.GetAdmin()` [3](#0-2) [4](#0-3) [5](#0-4) .

These two systems are never reconciled: nothing in `CreateDenom`, `UpdateDenom`, or `ChangeAdmin` checks whether the (new) admin address is a member of the denom's `AllowList`, and nothing in `SetDenomAllowList` checks whether the current admin is being excluded. When a `Mint` succeeds at the msg-server authorization layer, `mintTo` still routes funds through `bankKeeper.SendCoinsFromModuleToAccount` [6](#0-5) , and the bank `SendKeeper` enforces `IsInDenomAllowList` for tokenfactory-prefixed denoms whenever an `AllowList` is set for that denom [7](#0-6) . If the admin (or the mint-to recipient) is not present in that allow list, the mint reverts even though the tokenfactory-layer authorization check passed — exactly mirroring the reported ERC20Token pattern where `onlyMinter` and `notBlacklisted` are independently administered but jointly enforced at the operational function.

This can be reached by an ordinary, unprivileged transaction flow: any account can call `MsgCreateDenom` (permissionless denom creation) and set an `AllowList` that omits itself, or later call `MsgUpdateDenom`/`ChangeAdmin` to move admin rights to an address never added to the list, or narrow the allow list after the fact via `UpdateDenom`. Because `SetDenomAllowList` is not cross-checked against the current admin address in `x/tokenfactory/keeper/msg_server.go`, this is achievable purely through public `tokenfactory` `MsgUpdateDenom` transactions without any privileged/governance action.

### Impact Explanation
Once the current admin address is excluded from the denom's `AllowList` (by their own `UpdateDenom` call, by a `ChangeAdmin` to a not-allow-listed address, or by any subsequent `UpdateDenom` narrowing the list), all further `Mint` operations for that denom permanently fail with an allow-list rejection, even though the tokenfactory admin-authorization check passes. Since `ChangeAdmin` also requires being the current admin, and the denom has no admin-recovery or allow-list bypass path, the denom's supply becomes frozen from any further minting — a form of permanent, self-inflicted supply freeze for that denom that is indistinguishable in cause from the reported ERC20 issue (independently administered access-control lists whose intersection is never validated).

### Likelihood Explanation
Any account can create a tokenfactory denom with an `AllowList` via a single public `MsgCreateDenom`/`MsgUpdateDenom` transaction, and nothing prevents omitting the (current or future) admin address from that list. No special privileges, precompile access, or governance action are required to trigger the state — it purely requires the accountable admin to interact with the two independently-validated fields (`AuthorityMetadata.Admin` vs. bank `AllowList`) without them being cross-checked, exactly as flagged in the source report.

### Recommendation
In `x/tokenfactory/keeper/msg_server.go`, when setting or updating a denom's `AllowList` (`CreateDenom`, `UpdateDenom`) or changing the admin (`ChangeAdmin`), validate that the resulting admin address is present in (or implicitly exempt from) the denom's `AllowList`, or explicitly always exempt the current admin from allow-list enforcement in the bank keeper's `IsInDenomAllowList`/`SendCoins` path used by `mintTo`/`burnFrom`, so admin-driven mint/burn operations cannot be blocked by a stale or misconfigured allow list.

### Proof of Concept
1. Account `A` submits `MsgCreateDenom` for `factory/A/foo` with an `AllowList` that does not include `A` (or later submits `MsgUpdateDenom` setting an `AllowList` that excludes `A`) — [1](#0-0) .
2. `A` remains the admin (`AuthorityMetadata.Admin == A`) since nothing validates the allow list against the admin.
3. `A` submits `MsgMint` for `factory/A/foo`; the msg-server admin check passes (`msg.Sender == authorityMetadata.GetAdmin()`) [8](#0-7) .
4. `mintTo` calls `bankKeeper.SendCoinsFromModuleToAccount` to deliver the minted coins to `A` [9](#0-8) , which is rejected by `IsInDenomAllowList` because `A` is not in the denom's allow list [7](#0-6) .
5. The mint transaction fails, and since `A` is the only account authorized to call `ChangeAdmin`/`UpdateDenom` for this denom, and `A` itself is excluded from the allow list it controls, the denom's mint capability is permanently disabled with no recovery path.

**Note:** I was not able to fully trace the exact call site inside `SendCoins`/`SendCoinsFromModuleToAccount` where `IsInDenomAllowList` is invoked (the tool budget ran out before reading that section of `sei-cosmos/x/bank/keeper/send.go` in full), so the precise line enforcing this check during `SendCoinsFromModuleToAccount` could not be pinpointed with full certainty — a Devin session with file access would be needed to confirm that exact call path end-to-end.

func (server msgServer) Mint(goCtx context.Context, msg *types.MsgMint) (*types.MsgMintResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// pay some extra gas cost to give a better error here.
	_, denomExists := server.bankKeeper.GetDenomMetaData(ctx, msg.Amount.Denom)
	if !denomExists {
		return nil, types.ErrDenomDoesNotExist.Wrapf("denom: %s", msg.Amount.Denom)
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Amount.GetDenom())
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	err = server.mintTo(ctx, msg.Amount, msg.Sender)
	if err != nil {
		return nil, err
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgMint,
			sdk.NewAttribute(types.AttributeMintToAddress, msg.Sender),
			sdk.NewAttribute(types.AttributeAmount, msg.Amount.String()),
		),
	})

	return &types.MsgMintResponse{}, nil
}

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgChangeAdmin,
			sdk.NewAttribute(types.AttributeDenom, msg.GetDenom()),
			sdk.NewAttribute(types.AttributeNewAdmin, msg.NewAdmin),
		),
	})

	return &types.MsgChangeAdminResponse{}, nil
}

func (k Keeper) mintTo(ctx sdk.Context, amount sdk.Coin, mintTo string) error {
	// verify that denom is an x/tokenfactory denom
	_, _, err := types.DeconstructDenom(amount.Denom)
	if err != nil {
		return err
	}

	logger.Info("Minting amount for module", "amount", amount, "module", types.ModuleName)
	err = k.bankKeeper.MintCoins(ctx, types.ModuleName, sdk.NewCoins(amount))
	if err != nil {
		return err
	}

	addr, err := sdk.AccAddressFromBech32(mintTo)
	if err != nil {
		return err
	}

	logger.Info("Sending minted amount to addr", "amount", amount, "addr", addr)
	return k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName,
		addr,
		sdk.NewCoins(amount))
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
