### Title
Hardcoded zero slippage protection in `ArbWomUp3` WOM conversion enables MEV/sandwich loss of user funds - (File: `wombat/ArbWomUp3.sol`)

### Summary
`ArbWomUp3.incentiveDeposit()` with `_mode == 2` routes half of a user's deposited WOM through `SmartWomConvert.convert()` with a hardcoded `_minRec` of `0`, removing any slippage protection on the underlying Wombat pool swap. This mirrors the reported `CvxCrvRewardsLocker` issue where a swap is executed with `minOut = 0`, making it trivially sandwichable.

### Finding Description
Any unprivileged wallet can call the external, non-privileged function `incentiveDeposit(_amount, _convertRatio, _bullMode, _mode)` with `_mode == 2`: [1](#0-0) 

This calls `_deposit`, which for `_mode == 2` splits the user's WOM and forwards half to `SmartWomConvert.convert()` with the minimum-received parameter hardcoded to `0`: [2](#0-1) 

Inside `SmartWomConvert._convertFor`, that `_minRec = 0` is used directly to gate the swap outcome, and the swap call itself also passes `0` as its own `minimumToAmount` to `IWombatRouter.swapExactTokensForTokens`: [3](#0-2) 

Because both the router-level `minOut` and the outer `_minRec` check are `0`, there is no meaningful slippage protection anywhere in this call path — the `convertAmount + amountRec < _minRec` check can never revert since `_minRec` is `0`. This is functionally identical to the reported `CvxCrvRewardsLocker` swap that used `minOut = 0`, except here it is embedded directly in production code rather than being a caller-supplied parameter defaulted incorrectly.

Contrast this with `SmartWomConvert.smartConvert()` (used internally by `WombatStaking._sendRewards`), which computes `_minRec` as the full input amount before calling `_convertFor`, providing actual protection: [4](#0-3) 
No equivalent protection exists for the `ArbWomUp3` path.

### Impact Explanation
A user calling `incentiveDeposit` with `_mode == 2` has half of their deposited WOM swapped through the WOM/mWOM Wombat pool with zero minimum output enforced. An MEV searcher can sandwich this swap (front-run to move the pool price unfavorably, let the victim's swap execute at a poor rate, then back-run), extracting value directly from the depositing user's funds. The resulting `mWom` (already reduced by the sandwich) is then permanently locked via `mWomSV.lockFor`, so the loss is not recoverable by the user. This is a direct theft of user funds via MEV that the contract's own hardcoded parameter enables.

### Likelihood Explanation
Any caller of `incentiveDeposit` with `_mode == 2` and a nonzero `_convertRatio` (which is a normal supported code path, not an edge case) is exposed. WOM/mWOM pool liquidity/pricing conditions and normal MEV bot monitoring of mempools make sandwiching this call straightforward and economically attractive whenever deposit sizes are non-trivial.

### Recommendation
Do not hardcode `_minRec` to `0` in `ArbWomUp3._deposit`. Either expose a user-supplied `_minRec`/slippage parameter for the `_mode == 2` path that is propagated to `SmartWomConvert.convert()`, or compute an on-chain minimum (e.g., via `getAmountOut`) with an acceptable slippage tolerance before calling `convert`. Additionally, `SmartWomConvert._convertFor` should not pass a hardcoded `0` directly to `IWombatRouter.swapExactTokensForTokens`; it should derive a real minimum from `_minRec`/expected rate.

### Proof of Concept
1. User calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, bullMode, 2)` with `convertRatio < DENOMINATOR` so `toSwap > 0`.
2. `_deposit` computes `toSwap` and calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` — note the hardcoded `0` for `_minRec`.
3. Inside `SmartWomConvert._convertFor`, the swap `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` also uses `0` for its minimum output.
4. An attacker observing the pending transaction front-runs it with a large WOM→mWOM swap to depress the exchange rate, lets the victim's swap execute at the degraded rate, then back-runs to restore the price and capture the difference.
5. `convertAmount + amountRec < _minRec` never reverts because `_minRec == 0`, so the undervalued `mWom` is locked into `mWomSV` for the victim, permanently realizing the loss. [5](#0-4) [6](#0-5)
