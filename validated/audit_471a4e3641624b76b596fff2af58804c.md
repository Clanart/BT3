### Title
Unprivileged attacker can evict another payer's paid bandwidth subscription via spam sponsorship purchases - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` maintains a shared, FIFO-capped (1024 entries) `Allowance<T>` list per `(app_chain, app)` pair [1](#0-0) . Any address on any registered source chain can call `BandwidthManager.purchase()` and credit *any* `(app_chain, app)` pair — the payload's `chain`/`app` fields are attacker-controlled and independent of the caller's identity [2](#0-1) , and the pallet only checks that `request.from` matches the registered manager, not who paid [3](#0-2) . When the shared list is at its 1024 cap, a new credit evicts the **oldest** entry regardless of its remaining byte value [4](#0-3) . This is the same broken invariant as the reported Insurance Fund issue: a shared pool whose "share value" for one honest party can be reduced to zero by another unprivileged party's cheap action against the same shared resource.

### Finding Description
`Allowance<T>` is a `StorageDoubleMap<StateMachine, AppKey, SubscriptionList>` — one shared bounded FIFO queue per `(app_chain, app)` [1](#0-0) . The docs explicitly confirm the design is sponsorship-friendly: "a treasury on a single chain can sponsor bandwidth for an app deployed across many chains" and the pallet "keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`" [3](#0-2) . This means *anyone* holding the (cheap) fee token can dispatch a purchase crediting an arbitrary victim `(app_chain, app)` pair — there is no requirement that the caller be the app owner or any authorized entity.

Once a legitimate, high-value purchase (e.g. the $1000/8MB tier) is queued for `(app_chain, app)`, an attacker can repeatedly call `purchase()` with the cheapest tier for the exact same `(app_chain, app)` pair. Each purchase appends to the tail of the FIFO list [5](#0-4) . Once the list reaches the 1024-entry cap, every subsequent purchase pushes out the **oldest** entry — irrespective of its size or remaining value — and emits `SubscriptionEvicted` with the lost bytes [4](#0-3) . Because eviction is strictly FIFO-by-insertion-order and not by value, an attacker paying only the minimum aggregate fee across 1024 cheap purchases can force-evict a legitimate purchaser's large, unexpired, unconsumed subscription — destroying value the victim paid for without any compensation.

The gate's "no mutation on insufficient" safety property protects the *consumption* path [6](#0-5) , but it does nothing to protect against this *credit-side* griefing, because the eviction happens at push time, not consume time, and is keyed by insertion order rather than by payer or remaining value.

### Impact Explanation
This is a direct, permanent loss of paid-for value for the rightful beneficiary (the app operator whose bandwidth was legitimately purchased) — the exact bounty class of "stealing or loss of funds" via a public entrypoint reachable by any unprivileged attacker. It requires no malicious relayer, prover, admin, or governance actor: purchase() is a fully permissionless EVM entrypoint, and the pallet's `on_accept` credit logic performs no authorization check tying the payer to the app being credited beyond validating the manager address.

### Likelihood Explanation
The attack only costs 1024 minimum-tier purchases (the cheapest published tier is $50 for 100KB) targeted at a specific victim `(app_chain, app)`, which is economically feasible for an attacker wishing to grief a competitor's app or extract value via repeated targeted denial of paid bandwidth. No race condition or privileged timing is needed beyond simply outpacing/outlasting normal purchase cadence for that pair — an attacker fully controls when and how many cheap purchases they submit.

### Recommendation
Do not evict FIFO-blindly by insertion order. Either (a) evict by smallest-remaining-value first rather than oldest, (b) cap or throttle per-payer/per-purchase-tier pushes into another party's `(app_chain, app)` bucket, or (c) increase/bound the list size dynamically and refund/alert affected parties via an explicit sponsor allowlist requiring the app owner's opt-in for third-party sponsorship, rather than allowing unrestricted anonymous crediting of arbitrary `(app_chain, app)` pairs.

### Proof of Concept
1. App `X` on chain `A` legitimately purchases the $1000/8MB tier; the subscription is inserted into `Allowance::<T>::get(A, X)` at some FIFO position.
2. Attacker repeatedly calls `BandwidthManager.purchase()` on any registered source chain with `app = X`, `chain = A`, `tier = TierOne` (cheapest, $50/100KB), driving the shared FIFO list for `(A, X)` to the 1024-entry cap [7](#0-6) .
3. Continuing purchases beyond the cap evict the oldest entries in the queue one by one; once eviction reaches app `X`'s legitimate $1000 subscription, it is silently dropped and `SubscriptionEvicted` fires with the lost bytes, even though `X`'s subscription had far more remaining value than the attacker's spam entries [4](#0-3) .
4. App `X` has permanently lost the bandwidth it paid for, with no recourse, while the attacker spent comparatively little relative to the value destroyed.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

```text
## Subscription Lifecycle

Each `(chain, app)` row holds a FIFO list of subscriptions, capped at **1024** entries. Every purchase appends a new subscription — same-tier repurchases don't stack, they queue.

A subscription is immutable across its lifetime:

| Field             | Behavior                                                                       |
| ----------------- | ------------------------------------------------------------------------------ |
| `tier`            | Recorded at purchase time. Used for events and analytics, not for gating.      |
| `remaining_bytes` | Drains as the gate consumes messages. Pops once it hits zero.                  |
| `expires_at`      | Fixed at purchase. Never extends — a repurchase is a _new_ row, not a renewal. |
| `purchased_at`    | Insertion timestamp. Fixes FIFO order under same-block buys.                   |

### Drain order

The gate drains from the **head** of the list. Once the head is fully consumed it pops and continues into the next. If the next entry is expired it's swept silently — what you paid for is yours only until it expires.

This matters when you queue multiple tiers: the cheapest/oldest entry is consumed first regardless of which tier it came from. Plan top-ups so a higher tier doesn't sit behind a soon-to-expire lower tier you'd rather burn last.

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.
```

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
