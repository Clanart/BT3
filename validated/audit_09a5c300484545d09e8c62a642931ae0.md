### Title
Unbounded recursive expansion in `PuzzleWithRestrictions.from_memo()` allows memory/stack exhaustion when parsing untrusted CHIP-0043 custody memos - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody puzzle tree (member/restriction hierarchy) from an on-chain memo `Program` supplied by whoever created the coin. When the memo encodes an `MofN` node, the function recurses once per member with no limit on branching factor or nesting depth, mirroring the Hono `parseBody()` bug class: a bounded-size input can be crafted so that a small serialized CLVM program expands into an unbounded object graph during pure Python-side parsing, with no cost metering (unlike CLVM execution, which is metered by `run_chia_program`/`run_with_cost`).

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses the `spec_namespace` memo tuple and, when `further_branching` is true, builds an `MofN` whose `members` are populated via a **recursive** call: [1](#0-0) 

```python
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```

`MofNHint.from_program()` extracts `member_memos` as an arbitrary-length list straight from the CLVM `Program` structure with no cap: [2](#0-1) 

Because CLVM lists/pairs can be constructed compactly (sharing sub-structure via `Program.to()`/CLVM serialization) and each `MofN` node can itself contain nested `MofN` nodes as its own members, an attacker who controls a custody memo can encode many nesting levels or a wide fan-out of member memos in a relatively small serialized program. Unlike `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py`, which the codebase explicitly rewrote as an iterative (stack-based) algorithm "so we don't have to worry about blowing out the python stack" [3](#0-2) , `from_memo()` uses plain Python recursion with unbounded depth and unbounded per-node fan-out, and no depth/count guard exists anywhere in `custody_architecture.py`.

There is no cost accounting for this Python-side reconstruction (the CLVM cost/mempool metering in `chia/full_node/mempool_manager.py` only governs CLVM execution, not this wallet-side memo parsing), so a single crafted coin/memo can force disproportionate CPU/heap/stack consumption in whatever process parses it (wallet sync, offer/lineage recognition using this custody format).

### Impact Explanation
If/when `PuzzleWithRestrictions.from_memo()` is invoked on attacker/counterparty-controlled memo data (e.g., during wallet sync of a coin using the CHIP-0043 custody puzzle format, or when importing an offer/coin that hints this puzzle type), a malicious memo can:
- Trigger deep Python recursion, risking a `RecursionError`/crash of the wallet process (denial of service), and
- Amplify a small serialized memo into a very large in-memory `PuzzleWithRestrictions`/`MofN` object graph, consuming excessive memory.

This matches a spend-triggered transaction-processing halt / DoS class: a single submitted coin/memo can degrade or crash a wallet client that attempts to recognize/sync it.

### Likelihood Explanation
Currently, `PuzzleWithRestrictions`/`from_memo()` in the searched codebase is only exercised by tests (`chia/_tests/clvm/test_custody_architecture.py`) and by `chia/pools/plotnft_drivers.py`. I could not confirm within the indexed code that `from_memo()` is yet wired into general wallet coin-sync/hint-recognition logic that runs automatically over arbitrary incoming coins reachable by an unauthenticated wallet-state-loading path; the tool index only shows `plotnft_drivers.py` as a caller outside tests. This uncertainty (whether the custody architecture is already reachable from untrusted wallet-sync code, or is still a not-yet-integrated framework) limits confidence in real-world exploitability today. Given the explicit "no depth/count limit" root cause is real and demonstrable via unit-level reproduction, likelihood is assessed as medium pending confirmation of the exact production call path.

### Recommendation
- Add explicit bounds in `PuzzleWithRestrictions.from_memo()` / `MofNHint.from_program()`: cap recursion depth and the number of `member_memos` per `MofN` node, rejecting memos that exceed a sane maximum (mirroring the non-recursive, bounded-traversal pattern already used in `sha256_treehash()`).
- Convert the recursive reconstruction into an iterative, explicitly stack-bounded algorithm, or enforce a hard recursion-depth ceiling with a clear error before recursing.
- Audit and gate all call sites that will feed untrusted, attacker-supplied `Program` memos into `from_memo()` (wallet sync/hint recognition, offer parsing, DID/NFT/CAT recognition using this custody format) to ensure size/nesting limits are enforced before parsing.

### Proof of Concept
Not independently executed against a live process (no runtime access in this environment); the code-level PoC path is:
1. Build a memo `Program` for `PuzzleWithRestrictions` where `puzzle` is `MofN(m=1, members=[...])` and each member's own `puzzle` is again `MofN(m=1, members=[...])`, repeated to a large nesting depth N (e.g., tens of thousands), using `PuzzleWithRestrictions.memo()` to serialize it — CLVM allows this structure to be compact due to shared/curried sub-programs.
2. Call `PuzzleWithRestrictions.from_memo(memo)` on the resulting `Program`.
3. Observe Python recursion depth growth proportional to N in `from_memo()`'s list comprehension `[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]` at [4](#0-3) , leading to `RecursionError` or excessive memory allocation well before any CLVM cost limit would apply, since no cost/limit check exists in this Python-side reconstruction path.

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int
    member_memos: list[Program]

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),
        )
