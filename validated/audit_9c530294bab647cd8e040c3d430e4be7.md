### Title
`rewards()` view in the distribution precompile omits the non-payable guard, permanently stranding any ETH-style value sent with the call - ([File: precompiles/distribution/distribution.go])

### Summary
The distribution precompile (`0x0000000000000000000000000000000000001007`) enforces `pcommon.ValidateNonPayable(value)` on essentially every other entrypoint that does not itself consume the attached value (e.g. `setWithdrawAddress`), rejecting any call that carries `msg.value`. The `rewards()` view method skips this check entirely, so a value-bearing call to `rewards(address)` is accepted rather than reverted, and the transferred usei/wei is never used, refunded, or otherwise accounted for by the precompile logic.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute()` dispatches `RewardsMethod` directly to `p.rewards(ctx, method, args)` without any `pcommon.ValidateNonPayable(value)` guard, unlike `SetWithdrawAddressMethod` and `WithdrawValidatorCommissionMethod`, which both call `pcommon.ValidateNonPayable(value)` before proceeding: [1](#0-0) [2](#0-1) 

`rewards()` itself only performs a read-only `DelegationTotalRewards` query and packs the response; it never touches `value` at all: [3](#0-2) 

This gap is explicitly called out in the precompile's own integration-test suite as a known quirk: [4](#0-3) 

Because EVM value transfer for a `CALL` to a precompile address is performed by the EVM's account-balance machinery before the precompiled `Run`/`Execute` function is even invoked, the caller's usei/wei balance is debited and credited to the precompile's associated account regardless of what the precompile's Go logic does with `value`. Every other stateful entrypoint in this precompile either rejects non-zero value outright (`ValidateNonPayable`) or explicitly consumes it via `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` (see the bank precompile's `sendNative`, which immediately refunds/redirects the payer's value: [5](#0-4) ). `rewards()` does neither — it is a pure query but is reachable with attached value, and that value has no code path back to the caller. The precompile address is not a controllable contract or module account with a withdrawal message; there's no mechanism (analogous to the reported "missing emergency withdraw" gap) to recover funds credited to it this way.

### Impact Explanation
Any unprivileged EVM caller (a plain wallet, a CosmWasm-deployed EVM caller contract, or any public JSON-RPC client) can send `rewards(address)` with non-zero `value`. That value is silently debited from the caller and credited to the distribution precompile's address, with no logic in the codebase that ever debits it back out — a concrete, permanent loss of user funds through a validated, reachable code path in a core Cosmos precompile that the "Missing Mechanism for Managing Strategy Funds" report class is directly analogous to (funds parked at an address with no withdraw/refund mechanism).

### Likelihood Explanation
Likelihood is high: `rewards()` is a normal, publicly documented view method on a widely used precompile; the only trigger needed is constructing the call with a non-zero `value` field, something a naive integrator or wallet could do accidentally (e.g., copy-pasting a payable call pattern from `withdrawDelegationRewards`), or an attacker could exploit deliberately to grief users by tricking them into a "boosted" reward-claim call.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` (or equivalent payment handling via `pcommon.HandlePaymentUsei`) at the start of `rewards()` in `precompiles/distribution/distribution.go`, mirroring `setWithdrawAddress` and `withdrawValidatorCommission`, and apply the same fix to the legacy versioned copies of the distribution precompile (`precompiles/distribution/legacy/v580,v605,v606,v610,v614,v620,v630,v640,v65,v66,v67/distribution.go`) that contain the identical `rewards()` implementation.

### Proof of Concept
1. An EVM-associated account calls the distribution precompile at `0x0000000000000000000000000000000000001007` with method `rewards(address)` and a non-zero `value` (e.g., `{value: parseEther("1")}`), as opposed to the "view rejects value" pattern used for all other queries.
2. The EVM's `Call` semantics debit `value` from the caller's balance and credit it to the precompile address before `Execute` runs.
3. `Execute` routes to `p.rewards(ctx, method, args)` at [6](#0-5) , which never inspects `value`, never calls `ValidateNonPayable`, and never refunds/uses it, unlike `setWithdrawAddress` at [7](#0-6) .
4. The call succeeds (transaction status 1) and returns the rewards data, but the attached usei/wei now sits at the precompile's address with no reachable withdrawal path — permanently stranded.

Note: I could not locate and directly inspect `withdrawDelegationRewards`'s full body in the time available (the function reference did not resolve via the exact search patterns tried), so I cannot fully confirm whether that specific payable-looking method independently handles/refunds `value` correctly; this does not affect the `rewards()` finding, which is independently confirmed by direct code reading and by the codebase's own test-comment acknowledgment of the missing guard.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		bz, err := method.Outputs.Pack(true)
		return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, 0, err
	}

	msg := &banktypes.MsgSend{
		FromAddress: senderSeiAddr.String(),
		ToAddress:   receiverSeiAddr.String(),
		Amount:      sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount))),
	}

	err = msg.ValidateBasic()
	if err != nil {
		return nil, 0, err
	}

	if _, err = p.bankMsgServer.Send(sdk.WrapSDKContext(ctx), msg); err != nil {
		return nil, 0, err
	}

	bz, err := method.Outputs.Pack(true)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
