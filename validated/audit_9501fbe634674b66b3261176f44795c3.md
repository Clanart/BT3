### Title
`SchnorrAggregate::verify` accepts an empty aggregate (no minimum on statement count) — forged signatures verify (`crypto/schnorr/src/aggregate.rs`)

### Summary
`SchnorrAggregate::verify` performs `multiexp_vartime(pairs).is_identity()` where `pairs` consists of one term per `(key, challenge)` plus the mandatory `(-s, G)` term. When `keys_and_challenges` is empty and `Rs` is empty, the only term is `(-s, G)`; an attacker-supplied `s = 0` makes the entire sum the identity, so `verify` returns `true` for a signature that attests to nothing.

### Finding Description
The bug class from the external report is an operation that accepts an unbounded/minimum-zero result: `swapExactTokensForTokens(amount, 0, ...)` accepts any output. The Serai analog is `SchnorrAggregate::verify`, which accepts an aggregate over zero statements — the cryptographic equivalent of `amountOutMin = 0`.

- `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`) reads a 4-byte count, then that many `C::read_G` points, then a scalar `s`. A count of `0` is accepted, yielding `SchnorrAggregate { Rs: [], s }` entirely from untrusted bytes.
- `verify` (`crypto/schnorr/src/aggregate.rs:127-146`) checks `self.Rs.len() == keys_and_challenges.len()` (0 == 0 passes), builds `pairs` containing only `(-self.s, C::generator())`, and returns `multiexp_vartime(&pairs).is_identity()`.
- With `s = 0`, `-0 * G = identity`, so verification succeeds.

The honest aggregator path is guarded — `SchnorrAggregator::complete` (`crypto/schnorr/src/aggregate.rs:175-178`) returns `None` when nothing was aggregated — but `verify` imposes no corresponding lower bound on attacker-controlled input. Any verifier code that calls `SchnorrAggregate::read` on untrusted bytes and then `verify(dst, &[])` (or where the challenge list is derived from the same attacker-controlled transcript and can be empty) will accept a forgery: `aggregate.verify(dst, &[]) == true` for `Rs = [], s = 0`.

### Impact Explanation
An unprivileged party can forge an aggregate Schnorr signature over an empty statement set that passes verification. Depending on the calling protocol, this lets an attacker present a "valid" aggregate where zero signatures were actually verified — e.g., a verifier that iterates attacker-supplied statements and finds none still accepts the aggregate. This is a forged signature/proof accepted by the verifier formula, with no secret knowledge required.

### Likelihood Explanation
Exploitation requires a caller that invokes `verify` with an empty `keys_and_challenges` list on an attacker-parsed `SchnorrAggregate`. The aggregation half-API already treats empty aggregates as invalid (`complete` returns `None`), so callers that round-trip honestly produced aggregates are safe; the exposure exists wherever the two halves are decoupled and the verify side can be reached with a zero-length statement list. Reachability is real but caller-dependent, justifying Medium rather than High.

### Recommendation
In `SchnorrAggregate::verify`, reject empty statement lists:

```rust
if self.Rs.is_empty() || (self.Rs.len() != keys_and_challenges.len()) {
  return false;
}
```

Additionally, `SchnorrAggregate::read` could reject a zero length at parse time, mirroring `SchnorrAggregator::complete`'s `None` return for the empty case.

### Proof of Concept
```rust
// For any Ciphersuite C, dst, and message context:
let agg = SchnorrAggregate::<C> { Rs: vec![], s: C::F::ZERO };
// Or equivalently via untrusted bytes: u32 len = 0 followed by a zero scalar
// passed to SchnorrAggregate::read.

// pairs = [(-0, G)] -> multiexp_vartime -> identity -> true
assert!(agg.verify(b"any_dst", &[]));
```
The forger supplies only public bytes; no key or valid signature is involved.
