### Title
Just-in-time deposit before harvest allows flash-loan-style theft of Stability-Pool-equivalent yield in Wombat reward pools - ([File: wombat/WombatPoolHelper.sol], [File: wombat/WombatStaking.sol], [File: rewards/BaseRewardPoolV2.sol])

### Summary
The reported bug class is a flash-loan attack where an actor buys into a pooled-reward mechanism immediately before a profit-generating event (liquidation) is processed, captures a pro-rata share of the freshly generated profit, then exits immediately — diluting long-term depositors. The same mechanical weakness exists in this codebase's Wombat/Magpie liquidity-mining flow: `WombatPoolHelper.deposit()`/`depositLP()` stake funds and simultaneously trigger a harvest that instantly credits pending rewards into `accRewardPerShare` (in `BaseRewardPoolV2`), based on `totalStaked()` at the moment of the call, with no vesting or time-weighting. An attacker can deposit right before/at the harvest, obtain a share of the reward distribution proportional to their (temporary) stake, and immediately withdraw — capturing yield that should have accrued to the pool's existing, long-term stakers.

### Finding Description
`WombatPoolHelper._deposit()` calls `WombatStaking.deposit()`, which internally calls `_toMasterWomAndSendReward(_lpAddress, lpReceived, true)` — this triggers a harvest from the underlying Wombat pool "to trigger harvest from wombat exchange" [1](#0-0) . The harvested reward tokens are forwarded to the corresponding `BaseRewardPoolV2`/`BaseRewardPool` via `queueNewRewards`/`_provisionReward`, which immediately updates `rewardPerTokenStored` using the *current* `totalStaked()` value: [2](#0-1) 

Because the attacker's freshly-staked deposit is already reflected in `totalStaked()` at the exact moment this update runs (the deposit function stakes into `MasterMagpie` via `_stake` right after the Wombat-side deposit/harvest completes [3](#0-2) ), the attacker's shares participate in the reward split for a batch of rewards they did nothing to earn.

`WombatPoolHelper.withdraw()` and the underlying `WombatStaking.withdraw()` have no cooldown, minimum holding period, or time-based vesting — a user can unstake in the very same transaction/block after depositing and harvesting: [4](#0-3) [5](#0-4) 

`harvest()` on both `WombatPoolHelper` and `WombatStaking` is a fully permissionless, unprivileged-wallet call gated only by pool-active checks, not caller identity: [6](#0-5) 

This mirrors the report's root cause exactly: a pooled reward-per-share accounting scheme that distributes profit instantly and pro-rata to whatever is staked at the moment of distribution, combined with unrestricted, uncool-downed deposit/withdraw, lets an attacker briefly "front-run" the reward event with borrowed or idle capital and extract value meant for long-term depositors.

### Impact Explanation
This constitutes theft of unclaimed yield from legitimate long-term stakers of the Wombat LP / receipt-token pools managed through `MasterMagpie`/`BaseRewardPoolV2`. Each time a harvest occurs (which any user can trigger via `WombatPoolHelper.harvest()` or implicitly via `deposit()`), an attacker who deposits immediately beforehand siphons a share of freshly harvested rewards proportional to their transient stake, diluting the rewards that should accrue to existing depositors who bore the risk/duration of staking.

### Likelihood Explanation
High. No privileged role, oracle, or governance action is required — deposit, harvest, and withdraw are all standard unprivileged-wallet calls, executable atomically in a single transaction (deposit → harvest triggers reward queuing → withdraw). Given available LP tokens/flash-loan liquidity, the attack can be repeated whenever the harvestable reward relative to `totalStaked()` is large enough to be profitable net of any small trading/slippage costs from the wombat pool deposit/withdraw round trip.

### Recommendation
Introduce time-weighting or vesting for reward distribution (e.g., checkpoint-based streaming reward release rather than instantaneous `rewardPerTokenStored` updates), and/or enforce a minimum staking duration or withdrawal cooldown in `MasterMagpie`/`WombatPoolHelper` so that a single-block deposit cannot capture a pro-rata share of a harvest that occurs in the same transaction. Alternatively, decouple the harvest trigger from the deposit path so that new deposits do not immediately participate in a reward batch that was already pending at deposit time (e.g., checkpoint `totalStaked` immediately before adding the new deposit and only allow newly deposited shares to accrue rewards distributed after their checkpoint).

### Proof of Concept
1. Attacker observes pending Wombat rewards are large relative to current `totalStaked()` for a given LP pool (e.g., via `pendingWom()`).
2. Attacker calls `WombatPoolHelper.deposit(_amount, _minimumLiquidity)` with a large amount (potentially flash-loaned depositToken). This internally calls `WombatStaking.deposit()`, which calls `_toMasterWomAndSendReward(_lpAddress, lpReceived, true)`, harvesting Wombat rewards and calling `queueNewRewards` on the `BaseRewardPoolV2`, updating `rewardPerTokenStored` using `totalStaked()` that now includes the attacker's new stake [3](#0-2) [7](#0-6) .
3. In the same transaction, attacker calls `MasterMagpie` claim/harvest (`getReward`/`multiclaim`) to realize their pro-rata share of the just-queued rewards.
4. Attacker calls `WombatPoolHelper.withdraw(_liquidity, _minAmount)` to exit immediately, with no cooldown enforced [4](#0-3) .
5. Attacker repays any flash loan, having captured a portion of the harvest's yield that would otherwise have gone entirely to the pool's existing long-term stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
