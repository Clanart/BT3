This confirms the bug clearly. `mWomSV.getRewardablePercentWAD` at [1](#0-0)  implements the exact same forfeit-percentage logic as `VLMGP.getRewardablePercentWAD`, but `mWOMSVBaseRewarder._calExpireForfeit` never calls it — it hardcodes `rewardableAmount = _amount`, unlike `vlMGPBaseRewarder._calExpireForfeit` which correctly calls `vlMGP.getRewardablePercentWAD(_account)`.

### Title
Unprivileged users can claim full mWOMSV bonus rewards with zero forfeiture due to hard-coded `rewardableAmount` in `mWOMSVBaseRewarder._calExpireForfeit` - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` ignores `mWomSV.getRewardablePercentWAD(_account)` and instead hard-codes `rewardableAmount = _amount`, making `forfeitAmount` always `0` regardless of how much of a user's mWOMSV balance sits in an unlocked/expired cool-down slot. Any staker can call the reachable `getReward`/`getRewards` path via `MasterMagpie.multiclaim`/`multiclaimFor` and receive 100% of bonus rewards attributable to their expired-cooldown balance instead of having that share forfeited and redistributed to remaining lockers.

### Finding Description
`mWOMSVBaseRewarder._sendReward` computes `forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account])` and sends `userRewards - forfeitAmount` to the user, queuing `forfeitAmount` back into the pool via `_queueNewRewardsWithoutTransfer` [2](#0-1) . The intended design (mirrored exactly in `vlMGPBaseRewarder._calExpireForfeit`, which calls `vlMGP.getRewardablePercentWAD(_account)` to scale down the rewardable amount for balances sitting in expired cool-down) is to forfeit the share of rewards belonging to mWOM that is fully unlocked/expired but not yet withdrawn, since that mWOM should no longer be "actively earning" for the depositor [3](#0-2) .

However, `mWOMSVBaseRewarder._calExpireForfeit` never queries `mWomSV.getRewardablePercentWAD`; it sets `rewardableAmount = _amount` directly, so `forfeitAmount = _amount - rewardableAmount` is always `0`: [4](#0-3) 

Meanwhile `mWomSV.sol` itself implements the exact same `getRewardablePercentWAD` logic used by VLMGP, distinguishing "fully in lock", "still in cooldown", and "fully unlocked/expired" cooldown slots and reducing the rewardable percent for expired slots proportionally to elapsed time past cooldown expiry [1](#0-0) . This function is defined but never consumed by `mWOMSVBaseRewarder`.

Exploit path: an attacker (or any regular staker) calls `mWomSV.lock`, then `startUnlock` to begin cooldown, waits for `coolDownInSecs` to fully elapse (the mWOM remains counted in `balanceOf` and continues to accrue rewards via `MasterMagpie` since withdrawal hasn't happened), and then calls `MasterMagpie.multiclaim`/`multiclaimFor` which is publicly callable and routes to `_claimBaseRewarder` → `rewarder.getReward(_account, _receiver)` → `mWOMSVBaseRewarder.getReward` → `_sendReward` [5](#0-4) [6](#0-5) . Because `_calExpireForfeit` always returns `forfeitAmount = 0`, the user receives 100% of `earned()` bonus tokens even though a portion (or all) of their staked balance is expired cooldown mWOM that should have had its share forfeited to remaining lockers, exactly as VLMGP does correctly for vlMGP holders. No modifier, `nonReentrant`, or reward-index update in the call path prevents this, since the vulnerability is a logic omission, not an access-control gap.

### Impact Explanation
This is theft of unclaimed yield: bonus reward tokens that should be forfeited from stale/expired-cooldown mWOMSV balances and redistributed (`ForfeitRewardAdded`) to actively-locked stakers are instead fully captured by the account holding the expired position. This directly reduces the yield available to other mWOMSV lockers and can be repeated by any/every staker who lets their cooldown expire before claiming, since doing so costs nothing and yields strictly more rewards than an honest claim would under the intended design.

### Likelihood Explanation
No special capital or privilege is required — any address that already stakes mWOM via `mWomSV.lock` can trigger this by simply calling `startUnlock`, waiting past `coolDownInSecs`, and calling `multiclaim`/`multiclaimFor` (both are `whenNotPaused`, publicly callable, no allowlist) [6](#0-5) . It is deterministic and repeatable for every mWOMSV staker on every claim.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: query `mWomSV.getRewardablePercentWAD(_account)` and scale `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before computing `forfeitAmount`, ensuring expired-cooldown balances have their reward share correctly forfeited and requeued via `_queueNewRewardsWithoutTransfer`.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder`, mWOM token, and a bonus reward token; register the mWOMSV pool in `MasterMagpie` with the rewarder.
2. User A locks mWOM via `mWomSV.lock(amount)`, which routes through `MasterMagpie.depositMWomSVFor`.
3. Fund the rewarder with bonus reward tokens via `queueNewRewards`, letting `rewardPerTokenStored` accrue for User A's full balance.
4. User A calls `mWomSV.startUnlock(amount)` to put their entire balance into a cooldown slot; warp `block.timestamp` past `coolDownInSecs` so the slot is fully expired (per `mWomSV.getFullyUnlock`), but do not call `unlock` (balance remains counted, `mWomSV.getRewardablePercentWAD(userA)` returns a value < 1e18 reflecting the expired share).
5. Accrue additional bonus rewards after expiry (or use rewards already accrued while the position was expired) and call `MasterMagpie.multiclaim` as User A (unprivileged), routing to `mWOMSVBaseRewarder.getReward`.
6. Assert: `userRewards` paid out via `RewardPaid` equals full `earned()` amount with `forfeitAmount == 0` and no `ForfeitRewardAdded` event ever emitted, even though `mWomSV.getRewardablePercentWAD(userA) < 1e18` — demonstrating the forfeiture that should have occurred (per the VLMGP analog) never happens, violating conservation of unclaimed yield across lockers.

        uint256 fullyInLock = getUserTotalLocked(_user);

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
