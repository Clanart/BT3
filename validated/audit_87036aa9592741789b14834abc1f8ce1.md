### Title
Escrow release/refund logic in `IntentGatewayV2.withdraw()` treats non-standard ERC20 `transfer()` return values as success, permanently locking bridged funds while marking orders as settled - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core defect is: code assumes an external contract's call return semantics without validating what the deployed contract actually returns, causing incorrect success/failure handling. The local Hyperbridge analog is in `IntentGatewayV2.withdraw()` on the Tron gateway, where escrow token transfers are performed via raw low-level `.call()` to `IERC20.transfer` but only the call's `success` flag (i.e. "did not revert") is checked — the actual returned boolean payload from the token is never decoded or checked. Because ERC20 explicitly permits `transfer()` to return `false` on failure instead of reverting, this contract will treat a failed token transfer as a successful one, finalize escrow accounting, and permanently mark the cross-chain order as filled/refunded even though the beneficiary received nothing.

Only `success` (the low-level call did not revert) gates the `TransferFailed()` revert; the returned `bytes` (the ERC20 boolean result) is discarded via `(bool success,) = token.call(...)`. Standard-conformant ERC20 semantics explicitly allow implementations to return `false` on a failed transfer rather than reverting (e.g. blacklist checks, paused tokens, insufficient allowance/balance edge cases in some custom tokens). In that case:
- `success == true` (the call itself executed without reverting).
- The actual transfer did not occur.
- The code proceeds to `_filled[body.commitment] = beneficiary`, decrements `_orders[body.commitment][token] -= amount`, and emits `EscrowReleased`/`EscrowRefunded`.

This is the same class of defect as the reported bug: the contract's consumption of an external call's result does not match the real behavior of that external contract's interface, and the mismatch is silently absorbed instead of causing a controlled failure. Note that elsewhere in the same file the contract already imports and aliases `SafeERC20` (`using SafeERC20 for IERC20;`), which correctly decodes and enforces the boolean return value — but the escrow settlement path deliberately bypasses this protection with raw calls.

### Impact Explanation
This falls under bridge custody / fund loss: escrowed order inputs and relayer/tx fee tokens can become permanently stuck in `IntentGatewayV2` while the protocol's own state (`_filled`, `_orders`, and the `EscrowReleased`/`EscrowRefunded` events consumed by off-chain solvers/relayers/indexers) reports the order as successfully settled. Once `_filled[commitment]` is set, the `UnknownOrder`/already-filled guards prevent any retry or recovery path for the legitimate beneficiary, so the loss is not merely transient — it is permanent for that commitment. This directly matches the bounty's "loss of funds" and "false state acceptance" categories, since on-chain settlement state diverges from actual custody of funds without any attacker-controlled relayer, prover, or admin action required — it is triggered purely by the token's standard-permitted return semantics.

### Likelihood Explanation
The path is reached automatically whenever the Hyperbridge host relays a legitimate `RedeemEscrow`/`RefundEscrow`/`SweepDust` message — no malicious actor, front-running, or compromised relayer is required. Any ERC20 token integrated into this Tron gateway that follows the fully-standard-compliant pattern of returning `false` instead of reverting on failure (a valid and documented ERC20 behavior, distinct from purely non-standard "no return value" tokens like USDT) will trigger this silently. Given IntentGatewayV2 is designed to be generic across arbitrary tokens configured by governance/integrators, this is a realistic production condition rather than a contrived edge case.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()`, `sweepDust`, and the fee redemption block with `SafeERC20.safeTransfer`, which is already imported and used elsewhere via `using SafeERC20 for IERC20;`. This correctly reverts on both call failure and `false` boolean returns, ensuring escrow state is only finalized when the token transfer genuinely succeeds.

### Proof of Concept
1. Configure (or have a user create) an order whose input/fee token is an ERC20 contract that, per spec, returns `false` on a failed `transfer` instead of reverting (e.g. a token with a blacklist/pause check that returns `false` for a blacklisted `beneficiary`, or any custom token following this valid ERC20 pattern).
2. A solver fills the order and the host relays a legitimate `RedeemEscrow` (or `RefundEscrow`) message to `onAccept` → `withdraw()`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting but returns `abi.encode(false)`.
4. `success` is `true`, so `TransferFailed()` is not triggered; `_filled[commitment]` is set, `_orders[...][token]` is decremented, and `EscrowReleased`/`EscrowRefunded` is emitted — while the beneficiary's token balance is unchanged and the tokens remain stuck inside `IntentGatewayV2`.
5. Because `_filled[commitment]` is now non-zero, no future `withdraw()` call for this commitment can succeed, permanently locking the escrowed funds.
