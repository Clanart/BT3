Based on my investigation, I found a real analog to the Tap.sol bug class: an on-chain accounting entry is fully cleared/marked-paid while the corresponding cross-chain payout that should back it can silently deliver less than the recorded amount, permanently losing the difference — exactly the "capped payout but tracker reset to zero" pattern from the report.

### Title
Relayer fee withdrawal zeroes `Fees` for the full amount before the destination payout is guaranteed to succeed for that amount, permanently losing the remainder on partial/failed disbursement - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads `available_amount` from `Fees::<T>::get(...)`, dispatches a single one-shot, `timeout: 0` ISMP POST instructing the destination `HostManager`/`BandwidthManager`-style contract (or `HYPERBRIDGE_MODULE_ID` on substrate) to pay that whole amount, and then unconditionally zeroes `Fees` for that relayer/chain — before the destination-side payout has executed, and with no reconciliation path if the destination-side transfer pays out less than `available_amount` or fails outright for a non-reverting reason.

### Finding Description
The doc comment on the module states the intended invariant plainly: [1](#0-0) 

The implementation reads the balance, dispatches, then immediately zeroes it on the same call, with no proof-of-delivery gate between dispatch and zeroing: [2](#0-1) 

This mirrors the Tap.sol structure precisely: a stateful "amount owed" value (`tapped` in Tap.sol / `Fees[chain][relayer]` here) is computed, an attempt is made to disburse it, and the tracking value is reset to zero regardless of whether the disbursed amount actually matched what was recorded. In Tap.sol, the truncation happened locally (`balance - minimum`); here it happens on the destination chain's execution of the withdrawal message, which the source pallet cannot observe before it clears its own ledger.

On the EVM side, the destination contracts that actually move funds have no allowance/insufficiency guard consistent with the pallet's optimistic accounting: [3](#0-2) 
`IERC20(params.token).safeTransfer(...)` for ERC-20 reverts the whole request on insufficient balance (via `SafeERC20`), which would surface as a failed ISMP delivery, but since `timeout: 0` is set on the withdrawal dispatch: [4](#0-3) 
the request never times out and can be resubmitted/re-delivered indefinitely by any relayer — yet the pallet has already zeroed `Fees` on the source (Hyperbridge) side at dispatch time, not at successful delivery time. If a relayer resubmission ever succeeds later, the relayer already lost the accounting record that would let them prove entitlement to the amount, and there is no `PendingWithdrawal`-equivalent retained anywhere in `pallet-ismp-relayer`'s storage (unlike Tesseract's own client-side DB, which persists pending withdrawals defensively — see `tesseract/messaging/messaging/src/fees.rs` — but that is an off-chain relayer safety net, not an on-chain guarantee, and does not protect the on-chain `Fees` ledger itself).

### Impact Explanation
If the destination-chain payout for a withdrawal request under-delivers or is delivered against a stale/insufficient balance state (e.g., the `HostManager`/fee-token balance on the destination host is temporarily below `available_amount` at delivery time, or the withdrawal message is delivered out-of-order relative to other withdrawals draining the same balance), the relayer's recorded `Fees` balance is already zero on Hyperbridge with no mechanism to reclaim the shortfall — the money is neither on the source ledger nor (fully) at the destination. This is a direct "loss of funds" condition matching the bounty's stated impact class, arising from unprivileged, ordinary relayer withdrawal activity (no malicious peer, relayer, or admin required).

### Likelihood Explanation
Moderate. Relayers withdraw routinely (Tesseract runs `withdraw_once`/`auto_withdraw` on a timer per `tesseract/messaging/messaging/src/fees.rs`), and any transient shortfall in the destination-side custody balance (e.g., concurrent withdrawals racing against `HostManager`/`BandwidthManager` funding, or reliance on `timeout: 0` non-expiring requests that can be delivered much later against a different balance state) is enough to trigger permanent loss of the difference, without any attacker action.

### Recommendation
Do not zero `Fees` at dispatch time. Either (a) zero it only after an on-chain proof of successful destination delivery/execution is verified (mirroring the deliver-then-clear ordering used for `RequestCommitments[...].claimed` in `accumulate`), or (b) retain a recoverable record of the dispatched-but-unconfirmed amount (a pending-withdrawal map keyed by request commitment) so that if the destination-side transfer under-delivers or fails, the relayer can re-claim the exact outstanding remainder rather than having it silently and permanently written off.

### Proof of Concept
1. Relayer accumulates `Fees[dest_chain][relayer] = X` via `accumulate_fees`.
2. Relayer calls `withdraw_fees` with `dest_chain`; `withdraw()` reads `available_amount = X`, dispatches a `timeout: 0` POST instructing the destination `HostManager`/fee-token contract to pay `X` to the beneficiary, and immediately sets `Fees[dest_chain][relayer] = 0` (`withdrawal.rs:177`) in the same extrinsic — before any confirmation that the destination transfer for the full `X` succeeded.
3. If the destination-side transfer (`EvmHost.withdraw` → `safeTransfer`/native `call`) is delivered against a balance state where less than `X` is available, or the message is delivered late/out-of-order due to `timeout: 0` allowing indefinite redelivery, the relayer receives less than `X` (or nothing, pending retry) while `Fees` on Hyperbridge already reads zero — with no on-chain record of the shortfall to reclaim.

**Uncertainty note:** I was not able to fully trace whether `BandwidthManager`/`HostManager` withdrawal-style transfers used by `pallet-ismp-relayer::withdraw` on the EVM destination ever partially succeed (vs. always fully reverting on insufficient balance) in the current implementation — the visible code paths (`SafeERC20.safeTransfer`, `call{value}`) revert on failure rather than truncate. The core, verifiable defect is the ordering/atomicity gap itself: `Fees` is cleared for the full amount at dispatch time rather than at confirmed-delivery time, which is the same class of premature accounting reset as the Tap.sol bug, and is exploitable by any transient destination-balance shortfall or non-reverting under-delivery path a background engineer should audit further (especially any legacy/alternate destination withdrawal handlers reachable via `dest_chain.is_substrate()` vs EVM branches in `withdrawal.rs:134-158`).

//! Relayer fee withdrawal.
//!
//! Once fees have been accumulated into [`crate::pallet::Fees`] by
//! [`crate::accumulate`], relayers withdraw them via [`Pallet::withdraw`].
//! The flow:
//!
//! 1. The relayer signs a `(nonce, dest_chain, beneficiary?)` payload with their per-chain key (EVM
//!    secp256k1 / sr25519 / ed25519).
//! 2. The pallet verifies the signature, increments the per-relayer nonce, and dispatches an ISMP
//!    POST request to the destination's host manager (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate)
//!    instructing it to disburse `available_amount` of the fee token to the beneficiary.
//! 3. The `Fees` entry is zeroed so the same balance cannot be withdrawn twice.
//!
//! The on-chain effect is just dispatching the message; the destination chain settles the
//! payout when the ISMP request is delivered there.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
