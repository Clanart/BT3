### Title
lpSupply used in `updatePool` reward accounting can be inflated by direct token donation, permanently diluting unclaimed MGP yield - (File: rewards/MasterMagpie.sol)

### Summary
`_calLpSupply()` computes the reward-accounting denominator for every pool other than `vlmgp`/`mWomSV` as `IERC20(_stakingToken).balanceOf(address(this))` instead of tracking a pool's actual staked-and-credited supply. Any unprivileged party can transfer the staking token directly to `MasterMagpie` (bypassing `deposit()`), inflating this balance without incrementing any `UserInfo.amount`, which permanently dilutes `accMGPPerShare` and reduces the MGP rewards credited to legitimate stakers for the affected interval.

### Finding Description
`updatePool()` computes emissions as:
```
uint256 lpSupply = _calLpSupply(_stakingToken);
...
pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
``` [1](#0-0) 

and `_calLpSupply` for any non-`vlmgp`/non-`mWomSV` pool simply reads the raw token balance held by the contract:
```
return IERC20(_stakingToken).balanceOf(address(this));
``` [2](#0-1) 

`UserInfo.amount` is only incremented through `_deposit()`, which pulls tokens via `safeTransferFrom` [3](#0-2) . There is no internal bookkeeping variable (e.g., a `totalStaked` counter incremented/decremented on deposit/withdraw) that is used instead of `balanceOf`. An attacker can therefore call `ERC20(stakingToken).transfer(masterMagpie, X)` directly, which raises `_calLpSupply()`'s result without crediting any `UserInfo.amount`.

Because `mgpReward` for the interval is fixed (`multiplier * mgpPerSec * pool.allocPoint / totalAllocPoint`, independent of `lpSupply`) but is divided by an artificially inflated `lpSupply` when incrementing `accMGPPerShare`, the per-share value credited to all stakers of that pool is permanently reduced. Since each user's claimable MGP is `user.amount * accMGPPerShare / 1e12 - user.rewardDebt` (see `_calNewMGP` [4](#0-3) ), the MGP that would have accrued to `accMGPPerShare` above the diluted value is never credited to any `UserInfo` and is unrecoverable — it is not stored per-pool as a residual to be redistributed later. This is reachable through `multiclaim()`, which calls `updatePool()` for every staking token passed in as part of `_multiClaim` [5](#0-4) , or via the standalone public `updatePool()`/`massUpdatePools()`. None of `whenNotPaused`, `nonReentrant`, or the pool-manager modifiers protect against this because `updatePool` and `multiclaim` are intentionally open to any caller and only gate write access to `PoolInfo`/`UserInfo`, not the lpSupply computation itself.

### Impact Explanation
Every unit of directly-donated token permanently and irreversibly lowers the `accMGPPerShare` increment for that interval relative to what legitimate stakers should have received, since the shortfall is not tracked or reimbursed elsewhere. This is a permanent freezing/loss of a portion of unclaimed MGP yield for all stakers of the targeted pool, proportional to `donatedAmount / (creditedSupply + donatedAmount)`. The attack scales with the ratio of donation size to actual staked supply, and is most severe for low-TVL pools.

### Likelihood Explanation
The precondition is trivial: the attacker only needs 1 wei of legitimately staked balance (so `lpSupply != 0` and the pool remains "active"), plus capital to acquire and donate the staking token via a plain ERC20 `transfer`. No special role is required — any EOA can call this at any time, and it is repeatable each time new rewards accrue (each `updatePool` call while the donated balance remains dilutes further intervals too). The attacker's donated tokens are not recoverable (griefing has a real cost to the attacker), which somewhat limits the incentive to attack purely for profit, but it still constitutes a feasible, permanent, and quantifiable degradation of yield accounting caused entirely by an unprivileged actor's public-function calls.

### Recommendation
Track staked supply internally per pool (e.g., a `pool.totalStaked` counter incremented on `_deposit` and decremented on `_withdraw`/`emergencyWithdraw`) and use that value in `_calLpSupply()` instead of the raw `IERC20(_stakingToken).balanceOf(address(this))`, so that reward-per-share accounting is immune to unsolicited token transfers into the contract.

### Proof of Concept
Hardhat/Foundry test outline:
1. Deploy `MasterMagpie`, `MGP`, and a mock ERC20 `stakingToken`; register the pool via `add()`.
2. Attacker deposits 1 wei of `stakingToken` via `deposit()` so `UserInfo.amount = 1` and `_calLpSupply == 1`.
3. Advance time, call `updatePool(stakingToken)`, record `accMGPPerShare_A`.
4. Attacker transfers a large amount (e.g., 1e18) of `stakingToken` directly to `MasterMagpie` (no `deposit()` call), inflating `balanceOf(MasterMagpie)` to `1e18 + 1` while `UserInfo.amount` stays at 1.
5. Advance the same amount of time again, call `updatePool(stakingToken)` (or `multiclaim([stakingToken])`), record `accMGPPerShare_B`.
6. Assert `(accMGPPerShare_B - accMGPPerShare_A)` for step 5 is far smaller than for step 3 despite identical `multiplier`, `mgpPerSec`, and `allocPoint` — demonstrating the dilution.
7. Assert that `_calLpSupply(stakingToken)` (now inflated) no longer reconciles with the sum of all `UserInfo.amount` for that pool, and that the difference between the "expected" accMGPPerShare (using pre-donation supply) and the actual accMGPPerShare represents unclaimed MGP yield that is permanently unrecoverable by any staker.
