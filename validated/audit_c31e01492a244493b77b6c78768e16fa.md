### Title
Attacker-chosen participant index in `blame` causes panic via indexing of unregistered `enc_keys` entry — ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
CVE-2021-3608 is a guest-controlled write reaching a code path that dereferences uninitialized state, crashing QEMU. The Serai analog lives in the PedPoP blame path: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a `decryptor` participant index supplied by the accuser, and `HashMap`'s `Index` impl panics on missing keys. Registered `enc_keys` only exist for participants `1..=n`, but `Participant` accepts any nonzero `u16`, so an accuser can name a `recipient` outside the registered set and crash the process.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` take `sender` and `recipient` as free `Participant` arguments and forward them to `blame_internal`, which calls `decrypt_with_proof(sender, recipient, msg, proof)`. Inside `decrypt_with_proof`, the DLEq verification uses `self.enc_keys[&decryptor]` — a panicking `HashMap` index — without checking that `decryptor` was ever registered. In `AdditionalBlameMachine::new`, keys are only registered for `i in 1..=n`, so any `recipient` greater than `n` (or any `sender`/`recipient` not present) hits an uninitialized map entry. A symmetric panic exists at `self.commitments[&sender]` in `blame_internal` for an unregistered `sender`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
A remote crash of any validator/node evaluating blame: `HashMap::index` on a missing key panics, unwinding or aborting the process handling the DKG/blame protocol. This mirrors the CVE's availability impact — untrusted input steers execution into access of state that was never populated.

### Likelihood Explanation
Reachable by an unprivileged party: blame accusations are submitted with attacker-controlled `sender`/`recipient` fields and a copy of an `EncryptedMessage`. To reach the panicking line, the message's `pop` Schnorr signature must verify for `from` — an attacker can trivially construct a valid `EncryptedMessage` (they choose `key` and sign the PoP themselves) and supply a valid-looking `EncryptionKeyProof`. `AdditionalBlameMachine` is explicitly designed for use by non-participants evaluating blame, so this is a publicly reachable surface, not a malicious-validator-only path.

### Recommendation
Replace the indexing accesses `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` and return `DecryptionError::InvalidProof` / blame the appropriate party when the participant was never registered; alternatively validate `sender` and `recipient` against `params`/the registered set at the top of `blame`/`blame_internal`.

### Proof of Concept
