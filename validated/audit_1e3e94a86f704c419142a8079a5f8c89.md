### Title
`incentiveDeposit()` uses non-standard `IERC20.transfer()` to pay USDT rewards, permanently freezing the WOM incentive-deposit mechanism and any USDT reward balance - (File: wombat/ArbWomUp.sol)

### Summary
`ArbWomUp.incentiveDeposit()` rewards WOM depositors with USDT using the raw `IERC20(usdt).transfer(msg.sender, rewardToSend)` call instead of `SafeERC20.safeTransfer()`. Real USDT does not return a `bool` from `transfer()`, so any call through the `IERC20` interface (which expects a `bool` return value) will revert on mainnet/L2 deployments where `usdt` is the genuine Tether token, permanently bricking the only external deposit entrypoint of the contract.

### Finding Description
`incentiveDeposit()` is the sole external, unprivileged entrypoint for users to deposit WOM and receive a USDT incentive as part of the "arbitrum airdrop" migration flow: [1](#0-0) 

The function first transfers the user's WOM in via `_deposit()` (which correctly uses `safeTransferFrom`), then attempts to pay the USDT reward with a bare `.transfer()` call rather than `SafeERC20.safeTransfer()`: [2](#0-1) 

The contract already imports and uses `SafeERC20` elsewhere (`using SafeERC20 for IERC20;`, and `_deposit()` uses `safeTransferFrom`) [3](#0-2) , showing the raw `.transfer()` on `usdt` is an inconsistent, unsafe usage. Because `usdt` is documented and named as USDT (a token that famously omits the `bool` return value on `transfer`/`transferFrom`), decoding the call through the standard `IERC20` interface — which declares `transfer` as returning `bool` — will cause the EVM call to revert whenever the low-level return data does not match the expected ABI-encoded `bool`, i.e., on every invocation.

This is the same root cause identified in the referenced Sherlock report for `SecondaryRewarder.recover()`: using `IERC20.transfer()` instead of a safe-transfer wrapper breaks compatibility with USDT-like tokens and causes the call to always revert.

### Impact Explanation
Because the USDT payout happens inside the same transaction as the WOM deposit and the reward computation, a reverting `transfer()` call reverts the *entire* `incentiveDeposit()` transaction. Since this is the only external function used to perform incentivized deposits in this contract, the vulnerability:
- Permanently disables the whole incentive-deposit feature (no user can ever successfully call `incentiveDeposit()` once `usdt` is a real USDT-like non-standard token), a freeze exceeding 24 hours since there is no code path to fix it without an upgrade/redeploy.
- Permanently locks any USDT balance already funded into the contract as reward reserve, since the only mechanism to pay it out (`incentiveDeposit`) is unusable; `transferToAdmin()` only rescues the `wom` token balance, not `usdt` [4](#0-3) , so there is no other admin recovery path for the stuck USDT.

This matches the "permanent freezing of funds" / "24-hour-plus freeze" impact bar, mirroring the medium-severity classification given to the original `SecondaryRewarder.recover()` report.

### Likelihood Explanation
Likelihood is high: this code path is triggered by any ordinary user simply calling `incentiveDeposit()` with a nonzero amount whenever the pool is unpaused, and it will deterministically revert every single time as long as `usdt` points to a real, non-standard-compliant USDT token, requiring no special conditions or attacker setup.

### Recommendation
Replace the raw `IERC20(usdt).transfer(msg.sender, rewardToSend)` call with `IERC20(usdt).safeTransfer(msg.sender, rewardToSend)` (the contract already has `using SafeERC20 for IERC20;` in scope), consistent with the `safeTransferFrom` already used in `_deposit()`.

### Proof of Concept
1. Deploy/point `ArbWomUp.usdt` to a token implementing the real USDT ABI (`transfer` with no return value).
2. Fund the contract with USDT and set up `rewardMultiplier`/`rewardTier` via `setMultiplier()`.
3. Any user approves WOM and calls `incentiveDeposit(amount)`.
4. `_deposit()` succeeds, `rewardToSend` is computed, then `IERC20(usdt).transfer(msg.sender, rewardToSend)` at line 76 reverts because the ABI-decoded `bool` return value does not match the token's actual (empty) return data, reverting the whole transaction — the deposit never completes and the pre-funded USDT reward balance can never be paid out through this contract.
