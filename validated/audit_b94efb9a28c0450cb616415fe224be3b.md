### Title
Attacker-crafted offer removals can force an unbounded loop in `Offer.get_root_removal()` when a wallet cancels/inspects an offer - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_root_removal()` walks a coin's ancestry inside a `SpendBundle` by repeatedly matching `coin.parent_coin_info` against the `name()` of another coin in the same `removals()` set, using an unconditioned `while coin not in non_ephemeral_removals:` loop with no cycle detection or iteration bound. Because the coins inside an untrusted, not-yet-chain-validated offer bundle are attacker-supplied Python objects (not proven-real chain coins), an attacker can construct a set of removals whose `parent_coin_info` fields form a cycle that never resolves to a coin in `non_ephemeral_removals`, causing this loop to spin forever.

### Finding Description
`get_root_removal()`: [1](#0-0) 

```
def get_root_removal(self, coin: Coin) -> Coin:
    all_removals: set[Coin] = set(self.removals())
    all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
    non_ephemeral_removals: set[Coin] = {
        c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
    }
    if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
        raise ValueError("The specified coin is not a coin in this bundle")

    while coin not in non_ephemeral_removals:
        coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

    return coin
```

The termination guarantee assumed by this code is that following `parent_coin_info` links among the bundle's `removals()` set eventually reaches a coin whose parent isn't itself in the removal set (a "root"/non-ephemeral removal). That assumption only holds for real coins whose lineage is anchored to a chain-validated, acyclic parent history. An `Offer` object, however, is built directly from an untrusted `SpendBundle` supplied in an offer file (`Offer.from_bytes`/`from_bech32`) *before* any consensus validation of coin identities occurs. A malicious offer author can hand-craft `CoinSpend`s whose `Coin.parent_coin_info` values point to each other in a cycle (e.g., coin A's parent id equals coin B's `name()`, and coin B's parent id equals coin A's `name()`), so that no member of the removal set is ever the "non-ephemeral" root. The `while` loop's `next(...)` call will always find a match and reassign `coin`, looping indefinitely and never raising `StopIteration` or breaking, hanging the calling thread.

This is the direct analog of CVE-2017-12990: the ISAKMP parser looped forever on malformed/malicious attacker-controlled input because loop-termination logic assumed well-formed structure. Here, the "parser" is the offer/lineage-walking logic, and the malformed input is a cyclic parent-coin graph inside an attacker-supplied offer bundle.

`get_root_removal()` is used by `get_primary_coins()`, which is called by the trade manager: [2](#0-1) 

### Impact Explanation
A counterparty who shares a malicious offer file with a victim wallet can cause the victim's wallet process (or any RPC caller) to hang the calling task/thread indefinitely while examining or attempting to act on the offer (e.g., during trade-manager processing that calls `get_primary_coins()`/`get_root_removal()`). This is a spend/offer-triggered transaction-processing halt reachable purely by delivering crafted offer data to an unprivileged wallet user, matching the "spend-triggered transaction-processing halt" impact category in scope.

### Likelihood Explanation
Likelihood is high for any user who loads/processes an untrusted offer file from a counterparty, since offer parsing paths are explicitly designed to accept CoinSpends/`Coin` objects that have not yet been checked against real chain state at this stage. Constructing two or more `CoinSpend`s with `parent_coin_info` fields cross-referencing each other's `name()` is trivial and requires no signature validity, no real blockchain state, and no elevated privileges — only the ability to produce coin/puzzle/solution byte tuples serialized into an offer.

### Recommendation
Add cycle detection (e.g., a visited-set bound by `len(all_removals)`) or an explicit iteration cap in `get_root_removal()`, and raise a `ValueError`/`ValidationError` if no non-ephemeral ancestor is found within that bound rather than looping unconditionally. The same lineage-walk pattern (`while ... : coin = next(...)`) should be audited elsewhere the same helper is reused (`get_primary_coins`, and callers in `chia/wallet/trade_manager.py`).

### Proof of Concept
1. Craft two `Coin` objects: `coin_a = Coin(parent_coin_info=coin_b.name(), puzzle_hash=ph_a, amount=amt_a)` and `coin_b = Coin(parent_coin_info=coin_a.name(), puzzle_hash=ph_b, amount=amt_b)`.
2. Build corresponding `CoinSpend`s for `coin_a` and `coin_b` (with arbitrary puzzle reveal/solution suitable to pass CLVM execution used elsewhere in `Offer` construction) and place them, plus any settlement-payment spends required to make the bundle look like a valid offer, into a `SpendBundle`.
3. Construct an `Offer` from this bundle and call `offer.get_primary_coins()` (or any path leading to `get_root_removal(coin_a)`).
4. Observe that `get_root_removal` never returns: `coin` cycles between `coin_a` and `coin_b` forever, since neither is in `non_ephemeral_removals` (each one's parent is the other, which is itself in `all_removals`).

Note: I was not able to fully trace every call site in `chia/wallet/trade_manager.py` that reaches `get_primary_coins()`/`get_cancellation_coins()` due to tool-call limits; confirming the exact externally-triggerable RPC/CLI entry point(s) that invoke this code on attacker-supplied offer data would benefit from a full Devin session with repository access to trace `trade_manager.py` call graph end-to-end.
