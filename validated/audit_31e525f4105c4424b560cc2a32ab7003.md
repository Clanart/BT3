### Title
Blame proof leaks the ECDH key for messages whose PoP was never verified, enabling cross-message share disclosure - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` (which publicly reveals the ECDH shared key `enc_key * msg.key`) for any share that fails scalar deserialization, even though the message's proof-of-possession (PoP) signature was only *queued* into the batch verifier and is never verified on that early-return path. A malicious participant can copy the per-message encryption key `X` from an honest participant's encrypted share, attach a garbage PoP and a garbage ciphertext, and cause the victim to emit a blame proof revealing `b·X` — which also decrypts the honest participant's message, disclosing their secret share. This is exactly the attack the code comments say the PoP exists to prevent.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` loops over each received `EncryptedMessage` and calls `self.encryption.decrypt`, which:

1. Queues the PoP `SchnorrSignature` into the `BatchVerifier` under `BatchId::Decryption(l)` — no verification yet (`crypto/dkg/pedpop/src/encryption.rs:479-485`).
2. Computes `key = ecdh(&self.enc_key, msg.key)` and returns an `EncryptionKeyProof { key, dleq }` unconditionally (`encryption.rs:487-500`).

Back in `calculate_share`, if the decrypted bytes fail `C::F::from_repr`, the function immediately returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` (`lib.rs:480-482`). This return happens **before** `batch.verify_with_vartime_blame()` at `lib.rs:493`, so the PoP of that message is never checked. The resulting blame proof is intended to be published (e.g., through `CoordinatorMessage::VerifyBlame` in `processor/src/key_gen.rs:504-549`), and `AdditionalBlameMachine::blame` does verify the PoP — but by then the `EncryptionKeyProof.key` (the raw ECDH point) is already emitted in the error and, in the Serai protocol, broadcast for blame adjudication.

The PoP exists specifically so an attacker cannot co-opt another party's per-message key `X`: `encryption.rs:84-91` documents that without it, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X … Bob would then use this to create a blame argument against Eve … they'd reveal bX, revealing Alice's message to Bob." Because `msg.key` is read directly from untrusted bytes via `EncryptedMessage::read` (`encryption.rs:171-177`) and used verbatim in `ecdh` (`encryption.rs:95-97`), Eve only needs to:

- Set `msg.key = X` copied from Alice's `EncryptedMessage` to the victim Bob.
- Set `msg.pop` to any bytes forming a syntactically valid `SchnorrSignature` (it never needs to verify on this path).
- Set `msg.msg` to arbitrary ciphertext. Eve cannot compute the keystream under `bX`, but she doesn't need to: decrypted output of random garbage is non-canonical under `C::F::from_repr` with high probability (for Ristretto/ed25519-class fields, a random 32-byte string is ≥ the group order roughly 7/8 of the time).

When Bob calls `calculate_share`, decryption succeeds (ECDH is computable regardless of PoP validity), `from_repr` fails, and `Some(blame)` carrying `bX` is returned. Publishing it reveals Alice's share-encryption key.

### Impact Explanation
The blame mechanism's confidentiality guarantee — "it's possible to reveal the shared key for a specific message without revealing any other message's decryption keys" (`spec/cryptography/Distributed Key Generation.md`) — is broken: revealing `bX` for Eve's fake message simultaneously reveals the shared key of *Alice's real message* to Bob, since both use `X`. Anyone who observes the published `EncryptionKeyProof` can run `cipher(context, proof.key)` and decrypt Alice's ciphertext, recovering the FROST secret share Alice sent to Bob. Repeating across `t` victims of the same sender recovers that sender's full DKG polynomial secret; combined with other leaked shares this enables threshold key share recovery. This is a sensitive-information-disclosure primitive reachable entirely from attacker-controlled `EncryptedMessage` bytes fed into `EncryptedMessage::read` / `calculate_share`, matching the CVE class of sensitive data exposure through hazardous (missing) input validation.

### Likelihood Explanation
The attacker must be a DKG participant able to send a secret-share message to an honest participant and observe another sender's ciphertext to that victim (both are normal protocol traffic). No collusion, leaked keys, or privileged access is required. The triggering condition (decrypted bytes non-canonical) succeeds with overwhelming probability per attempt, and the attacker can retry across attempts/sessions since each failure merely aborts that DKG attempt. The only requirement is that the blaming party's error handling surfaces `blame` — which is precisely what `PedPoPError::InvalidShare { blame: Some(..) }` is designed to do.

### Recommendation
Do not emit the `EncryptionKeyProof` until the message's PoP has been verified. Concretely:

- In `Encryption::decrypt` (`encryption.rs:469-501`), verify `msg.pop` eagerly (or at least before constructing the proof), returning a variant that yields `blame: None` on PoP failure; or
- In `calculate_share` (`lib.rs:476-491`), verify the PoP signature for share `l` before converting the decrypted bytes — e.g., perform a single-statement `msg.pop.verify(...)` before the `from_repr` early return, or restructure so deserialization failures are collected and only reported after `batch.verify_with_vartime_blame()` confirms the `BatchId::Decryption` statements.

The second option preserves batching efficiency for the common case while ensuring no blame proof is released for a message whose per-message key the sender did not prove possession of.

### Proof of Concept
1. Run a PedPoP session with participants `{Alice=1, Eve=2, Bob=3}` over `Ristretto`. Alice and Bob behave honestly; Eve is malicious.
2. Eve observes Alice's `EncryptedMessage` to Bob and copies its `key` field `X`.
3. Eve constructs her own message to Bob: `EncryptedMessage { key: X, pop: <any SchnorrSignature-shaped bytes>, msg: <random 32-byte ciphertext> }` and sends it in the share round.
4. Bob's `KeyMachine::calculate_share` calls `encryption.decrypt(...)`: the invalid PoP is queued (never verified), `ecdh(b, X)` is computed, and the garbage ciphertext decrypts to bytes that fail `C::F::from_repr` with ~7/8 probability.
5. `calculate_share` returns `PedPoPError::InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key: b·X, dleq }) }`.
6. Per the protocol, Bob publishes the blame (mirroring `CoordinatorMessage::VerifyBlame` handling). Anyone holding Alice's ciphertext to Bob computes `cipher(context, b·X).apply_keystream(alice_msg)` and recovers Alice's secret share — without Eve ever knowing `x` or `b`, and despite `AdditionalBlameMachine::blame` later (correctly) blaming Eve, the share is already disclosed.

```text
// crypto/dkg/pedpop/src/lib.rs
let (mut share_bytes, blame) =

let share =

    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) } // ECDH key released, PoP unverified
  })?);

batch.verify_with_vartime_blame() // never reached on the early return above
```
