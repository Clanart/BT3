### Title
Permanent loss of MGP emissions via frequent `updatePool()` calls causing rounding-down of the reward multiplier - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie.updatePool()` is a public, unrestricted function that computes a time-elapsed reward multiplier and then permanently advances `pool.lastRewardTimestamp` to `block.timestamp`, regardless of whether the computed reward rounded down to a smaller value (or zero) due to integer division. An unprivileged wallet can call `updatePool()` (or trigger it via zero-effect actions) at very short intervals to force the elapsed-time window to be small on every call, causing `mgpReward` to round down repeatedly and never accumulate the true emission owed for that time, permanently forfeiting MGP rewards that should have accrued to stakers. [1](#0-0) 

### Finding Description
`updatePool()` computes:
```
uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
pool.lastRewardTimestamp = block.timestamp;
``` [2](#0-1) 

This is structurally the same bug class as the VaultAdapter M-2 finding: a state variable (`accMGPPerShare`, gated by `lastRewardTimestamp`) that accrues based on `elapsed = now - lastUpdate`, where the elapsed window is unconditionally reset (`pool.lastRewardTimestamp = block.timestamp`) after every consultation — even if the reward computed for that window rounded down to (or toward) zero because of integer division (`mgpReward * 1e12 / lpSupply`, and the nested `multiplier * mgpPerSec * allocPoint / totalAllocPoint`). Because `lastRewardTimestamp` always advances forward regardless of the outcome of the division, any elapsed time whose corresponding reward rounds to a value lost in integer truncation is **never** recovered on a subsequent call — the window that would have contributed that fractional amount is gone.

`updatePool` is `public` with only a `whenNotPaused` modifier — no access control restricts who can call it: [3](#0-2) 

Any unprivileged wallet can therefore call `updatePool(_stakingToken)` on a very tight cadence (e.g. every block) for a pool with a small `allocPoint`/`totalAllocPoint` ratio or low `lpSupply`, forcing `multiplier` to be minimal on each call. Each call's `mgpReward` (and the derived `accMGPPerShare` increment) is more susceptible to truncation than if the elapsed time were allowed to accumulate before a single settlement, and each truncated remainder is permanently discarded because `lastRewardTimestamp` is unconditionally reset.

This mirrors the reported root cause: rounding in a time-multiplied accrual value combined with unconditional timestamp advancement enables a caller to strip value out of the accrual mechanism by consulting/settling frequently.

### Impact Explanation
Every truncated fraction of `mgpReward` is a permanent loss of MGP emissions that would otherwise be distributed to stakers of that pool via `accMGPPerShare`. Because `updatePool` is callable by anyone with no cooldown or minimum-elapsed-time gate, an attacker (or even unintentional high-frequency callers, e.g., bots/integrators triggering deposits/withdrawals of that pool) can grief the pool over time, causing cumulative, unrecoverable underpayment of the intended emission schedule. This is a permanent freezing/loss of unclaimed yield owed to legitimate stakers in `MasterMagpie`'s emission accounting, an explicitly in-scope contract per the target rules.

### Likelihood Explanation
The precondition is minimal: `updatePool()` has no access control, and any pool with a modest `allocPoint`/`totalAllocPoint` ratio, low `lpSupply`, or low `mgpPerSec` makes the rounding loss per call meaningful. Frequent calling costs only gas, and gas cost is a normal, expected cost for a griefing attacker; the likelihood of a real attacker (or even innocuous frequent interaction patterns) triggering this repeatedly over the life of a pool is high, and the effect compounds over time.

### Recommendation
Refactor the reward computation to avoid discarding un-realized reward remainders when the timestamp advances, e.g., by tracking any truncated remainder in storage and carrying it forward to the next `updatePool()` call (similar to how the Sherlock-reported fix reorders operations to preserve precision), or by combining the multiplication so no term is divided out before being multiplied by the full precision factor:
```solidity
uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
```
should retain a remainder carry-forward (e.g., store `pool.rewardRemainder` and add it back on the next computation) so that no accrual is permanently lost due to truncation regardless of how frequently `updatePool()` is invoked.

### Proof of Concept
1. Deploy `MasterMagpie` with a pool having `allocPoint` such that `mgpPerSec * allocPoint / totalAllocPoint` is small relative to 1 (e.g., a low-alloc pool).
2. Attacker (unprivileged EOA) calls `updatePool(_stakingToken)` every block (`multiplier = 1`), causing `mgpReward = (1 * mgpPerSec * allocPoint) / totalAllocPoint` to truncate to 0 (or a value smaller than it would be if elapsed time accumulated over a longer window before settlement).
3. `pool.lastRewardTimestamp` is set to `block.timestamp` on every call regardless, per [2](#0-1) , permanently discarding the un-accrued remainder for that 1-second window.
4. Repeating over many blocks causes cumulative, unrecoverable loss of `accMGPPerShare` growth compared to the case where `updatePool()` is called only once after a long elapsed period, directly reducing the MGP yield ultimately claimable by legitimate stakers of that pool.

Note: I was unable to execute this PoC directly in this environment (no test harness access); the analysis is based on static review of the exact arithmetic and control flow shown above in `rewards/MasterMagpie.sol`.

```text
    /// @notice Update reward variables of the given pool to be up-to-date.
    /// @param _stakingToken Staking token of the pool
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }    
```
