### Title
Debug-Mode `OP_TRUE` Disprove Scripts Bypass ZK Proof Requirement, Enabling Unauthorized Operator Collateral Slashing — (`File: core/src/bitvm_client.rs`)

---

### Summary

`ClementineBitVMPublicKeys::get_g16_verifier_disprove_scripts` returns a single `OP_TRUE` script (`0x51`) when compiled with debug assertions enabled (`cfg!(debug_assertions)`). This compile-time flag is silently active in any non-`--release` build. The mainnet safety gate (`check_mainnet_requirements`) checks `RISC0_DEV_MODE`, `DISABLE_NOFN_CHECK`, and the `use-test-vk` feature flag, but never checks whether the binary was compiled in debug mode. A debug binary deployed on mainnet causes every verifier to (a) store a wrong taproot root hash for the disprove UTXO during deposit setup, and (b) always find a "disprove" condition during the challenge flow — allowing any verifier to slash the operator's collateral without a valid Groth16 proof.

---

### Finding Description

**Root cause — `core/src/bitvm_client.rs:624-630`:**

```rust
pub fn get_g16_verifier_disprove_scripts(&self) -> Result<Vec<ScriptBuf>, BridgeError> {
    if cfg!(debug_assertions) {
        Ok(vec![ScriptBuf::from_bytes(vec![0x51])]) // OP_TRUE
    } else {
        Ok(replace_disprove_scripts(self)?)
    }
}
``` [1](#0-0) 

`cfg!(debug_assertions)` is `true` for every `cargo build` invocation that omits `--release`. The `scripts/run.sh` deployment script does exactly this:

```bash
cargo build --package clementine-core --all-features --bin clementine-core
``` [2](#0-1) 

**Gap in the safety gate — `core/src/config/mod.rs:291-333`:**

`check_mainnet_requirements` guards against `RISC0_DEV_MODE`, `DISABLE_NOFN_CHECK`, and `use-test-vk`, but has no check for whether `debug_assertions` is active:

```rust
check_env_var("DISABLE_NOFN_CHECK", &mut misconfigs);
if is_dev_mode() { ... }   // RISC0_DEV_MODE
if is_test_vk()  { ... }   // use-test-vk feature
// ← no check for cfg!(debug_assertions)
``` [3](#0-2) 

**Call site 1 — deposit setup (`core/src/verifier.rs:1803-1811`):**

During `set_operator_keys`, the disprove scripts are used to compute the taproot root hash that is persisted to the database and later embedded in the kickoff transaction's disprove UTXO:

```rust
let scripts: Vec<ScriptBuf> = bitvm_pks.get_g16_verifier_disprove_scripts()?;
let taproot_builder = taproot_builder_with_scripts(scripts);
let root_hash = taproot_builder
    .try_into_taptree()
    ...
    .root_hash()
    .to_byte_array();
``` [4](#0-3) 

In a debug build this root hash is derived from a single `OP_TRUE` leaf, not from the real Groth16 verifier scripts. All N verifiers must agree on this hash for the deposit to succeed; if all run debug builds they will agree on the wrong hash.

**Call site 2 — challenge flow (`core/src/verifier.rs:2785-2786`):**

During `verify_disprove_conditions`, the same function is called to obtain the scripts used to evaluate the operator's assertions:

```rust
let bitvm_pks = db_cache.get_operator_bitvm_keys().await?.clone();
let disprove_scripts = bitvm_pks.get_g16_verifier_disprove_scripts()?;
``` [5](#0-4) 

With `OP_TRUE` as the only disprove script, the BitVM assertion-validation step trivially succeeds for any operator input, so the verifier always concludes the operator is faulty and proceeds to broadcast the disprove transaction.

---

### Impact Explanation

When all verifiers run a debug build:

1. **Deposit phase**: The kickoff transaction's disprove UTXO is constructed with an `OP_TRUE` taproot leaf instead of the real Groth16 verifier scripts. The UTXO is spendable by anyone who can provide the control block (trivially computable from the public `OP_TRUE` leaf).
2. **Challenge phase**: Any verifier calling `verify_disprove_conditions` will always receive a "disprove" result and will sign and broadcast the disprove transaction, slashing the operator's collateral without the operator having committed any fraud.
3. **Collateral loss**: The operator's collateral UTXO — a bridge-controlled fund — is burned or transferred to the challenger without a legitimate ZK proof of misbehaviour.

This breaks the core BitVM2 safety invariant: the disprove path must only be executable when the operator's Groth16 proof is actually invalid.

---

### Likelihood Explanation

The `scripts/run.sh` reference deployment script builds in debug mode. Any operator or verifier who follows this script for a non-regtest deployment, or who forgets `--release`, silently activates the vulnerable path. Because `check_mainnet_requirements` does not detect debug builds, no startup-time warning is emitted. The N-of-N model means the attack requires all verifiers to be running debug builds simultaneously, which is plausible in a coordinated or accidental misconfiguration scenario (e.g., a team deploying from the same CI artifact built without `--release`).

---

### Recommendation

1. **Add a compile-time guard** in `get_g16_verifier_disprove_scripts`: emit a `compile_error!` or at minimum a `#[cfg(debug_assertions)] compile_error!(...)` if the function is reachable in a non-test context.
2. **Extend `check_mainnet_requirements`** to detect and reject debug builds at startup:
   ```rust
   if cfg!(debug_assertions) {
       misconfigs.push("Binary compiled with debug_assertions (non-release build)".to_string());
   }
   ```
3. **Update `scripts/run.sh`** to use `cargo build --release` for any deployment that is not explicitly local regtest.
4. **Separate the debug shortcut** into a `#[cfg(test)]`-only code path so it cannot be compiled into a production binary.

---

### Proof of Concept

1. Build without `--release` (as `scripts/run.sh` does):
   ```bash
   cargo build --package clementine-core --all-features --bin clementine-core
   ```
2. Start all verifiers from this binary on `Network::Bitcoin`. `check_mainnet_requirements` passes because `RISC0_DEV_MODE` is unset and `client_verification` is true.
3. Initiate a deposit. During `set_operator_keys`, each verifier calls `get_g16_verifier_disprove_scripts`, receives `[OP_TRUE]`, computes a root hash from that single leaf, and stores it. The kickoff transaction is pre-signed with this root hash embedded in the disprove UTXO's taproot tree.
4. The operator broadcasts the kickoff transaction. The disprove UTXO is now on-chain with `OP_TRUE` as its only script-path leaf.
5. Any verifier (or any party who can construct the control block) calls `verify_disprove_conditions`. The function retrieves `[OP_TRUE]` from `get_g16_verifier_disprove_scripts`, the BitVM assertion check trivially succeeds, and the verifier signs and broadcasts the disprove transaction.
6. The operator's collateral is slashed with no valid ZK proof of fraud.
