### Title
Reused cached FROST preprocess enables secret-share recovery across repeated `share_internal` calls - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` loads a `CachedPreprocess` from the DB, decrypts it, and passes it to `AlgorithmSignMachine::from_cache` — but never deletes it. The `SignMachine::from_cache` contract explicitly requires the caller to delete the cached preprocess after use, because reuse leaks the private key share. Each call to `share_internal` therefore re-derives the same nonce seed for the same `context`, and an attacker who can cause a second signing round over a different message/preprocess set (a retry, or participation in a differently-composed signing set) obtains two shares built on the same seed, enabling ROS-style/key-share recovery.

### Finding Description
In `crypto/frost/src/sign.rs:216-224`, `from_cache` is documented with an explicit MUST:

> "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share."

`coordinator/src/tributary/signing_protocol.rs:123-145` implements the caching layer: it writes `CachedPreprocesses::set` once, then on every subsequent `share_internal`/`preprocess_internal` call reads the same `CachedPreprocess` back (`CachedPreprocesses::get` at line 137) and constructs a fresh `AlgorithmSignMachine` via `from_cache` (line 145). No deletion occurs after `machine.sign(...)` at line 170 succeeds or fails.

Because `seeded_preprocess` deterministically expands the seed into the nonces `D, E`, two invocations produce identical base commitments. In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:386-395`), the effective nonce is `base + rho * actual`, where `rho` is the per-participant binding factor over `group_key || hash_msg(msg) || hash_commitments(preprocesses transcript)`. A second invocation with either a different `msg` or a different set of participant preprocesses yields a different `rho` — and a malicious coparticipant choosing their preprocess can force a collision of the aggregate `R` or otherwise grind `rho`, yielding two shares `s1 = d + rho1*e + c1*share`, `s2 = d + rho2*e + c2*share` on the same `(d, e)`. This is exactly the parallel-session/ROS precondition, and with `rho1 == rho2` (attacker replays their preprocess while msg changes) the secret share is recovered directly by linear algebra.

### Impact Explanation
Recovery of a validator's threshold secret share. Combined with shares for the same participant indexes obtained elsewhere, this enables reconstruction/forge of the group's signing capability — i.e., signing arbitrary messages (Bitcoin spends) the victim never agreed to. This matches the "key share recovery / concrete signing of an unintended message" acceptance bar.

### Likelihood Explanation
The triggering condition is simply that `share_internal` runs more than once for the same `context` — e.g., a failed `complete` round retried, or the attacker submitting a different preprocess across two rounds within one session context. `context` is used only to derive the XOR "encryption key" (lines 107-115), not the nonce seed, so any repeat under the same context reuses identical nonces. An unprivileged threshold participant supplies the untrusted preprocess bytes (`read_preprocess`) and observes the victim's broadcast share, satisfying the reachability rules.

### Recommendation
Delete the cached preprocess from `CachedPreprocesses` immediately after `from_cache` consumes it (before `sign`), and key the cache by a value that includes the attempt index so retries generate a fresh seed rather than reusing the same one.

### Proof of Concept
1. As a threshold participant, send preprocess `P1` in round 1; victim signs `msg1` producing share `s1 = d + rho1*e + c1*share` (seed loaded from `CachedPreprocesses`).
2. Force a second call to `share_internal` under the same `context` (retry after a failed `complete`, or second attempt with same context), again submitting `P1` so the binding-factor transcript commits to identical preprocess bytes; arrange `msg2 != msg1` via the protocol's message selection.
3. Since `d`, `e`, and `rho` are identical but `c` differs (`c` binds `msg` via `hram`), `s1 - s2 = (c1 - c2)*share` → `share = (s1 - s2)/(c1 - c2)` mod q. Victim's secret share is recovered.
