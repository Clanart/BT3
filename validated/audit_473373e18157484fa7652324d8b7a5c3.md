## Title
Missing zero-shares check in vault `deposit` allows silent loss of depositor funds via share-rounding (inflation-style drip attack) - (`File: mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Every Zest v0 vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) computes minted shares in `deposit` via `convert-to-shares-preview`, which floors the result of `amount * total-supply / total-assets`. Unlike `redeem`, which explicitly guards against a zero output with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, `deposit` never checks that the computed share amount (`inkind`) is non-zero before transferring the underlying asset in and minting. This is the exact bug class described in the `wxETH::stake` first-1-wei report: a depositor can transfer real underlying assets into the vault and receive 0 shares in return, permanently losing those funds to existing shareholders.

### Finding Description
In `deposit`, shares are computed and then only checked against a slippage bound supplied by the caller: [1](#0-0) 

```
(inkind (convert-to-shares-preview amount)))
...
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
...
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
```

If `min-out` is `0` (the natural default whenever a caller doesn't specify slippage protection), `inkind == 0` satisfies `(>= 0 0)` and the transaction proceeds: the underlying is pulled from the depositor and zero `zft` shares are minted to them.

`convert-to-shares-preview` performs floor division: [2](#0-1) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

Once `ts` is non-zero (true after `initialize`, since it seeds `MINIMUM-LIQUIDITY` shares to `NULL-ADDRESS`), any deposit satisfying `amount * ts < ta` mints `0` shares: [3](#0-2) 

The vault's exchange rate (`ta/ts`, i.e., price per share) is not static — `total-assets-preview` grows as lending interest accrues via the index mechanism (`debt-preview`, `total-borrowed`), exactly analogous to the "dripping" mechanism in the referenced xETH report: [4](#0-3) 

As the price-per-share index climbs above `1.0` over time, the minimum deposit amount required to round to a non-zero share count increases proportionally (`amount < ta/ts`). Any depositor whose amount falls below that threshold — whether through simple error, a low-decimal asset (`DECIMALS u6` for STX/sBTC vaults), or being targeted by a front-running attacker who first inflates `ta/ts` — loses their entire deposited amount: assets increase, no shares are minted to them, and their funds are irrecoverably captured by existing shareholders' share price.

By contrast, `redeem` in the same contracts explicitly guards the analogous zero-output case: [5](#0-4) 

The asymmetry (guard on withdraw, no guard on deposit) confirms the omission is a genuine gap rather than an intentional design choice.

### Impact Explanation
This lands squarely in the **Critical** impact class — direct theft/permanent loss of user funds at rest. A depositor's underlying tokens (STX, sBTC, stSTX, stSTXbtc, USDC, or USDH) are transferred into the vault (`receive-underlying`) with **zero** shares minted back, meaning the deposited value is permanently and irreversibly transferred to the rest of the shareholder pool with no compensation and no path to recovery for the victim. Because the deposit function is shared verbatim across all six mainnet vaults, the flaw is systemic across the whole lending pool suite, not isolated to one asset.

### Likelihood Explanation
Likelihood is elevated relative to the classic ERC-4626 "first depositor" inflation attack because `MINIMUM-LIQUIDITY` seeding at `initialize` already fixes that specific vector — but it does **nothing** to prevent this variant, since the exploitable condition (`amount * ts < ta`) recurs continuously as the lending index accrues interest over time, not just at pool genesis. An attacker only needs to observe or nudge the vault's price-per-share above `1.0` (which happens naturally through normal protocol operation as borrowers pay interest) and then either wait for, or front-run, a small deposit (including their own, to force a subsequent victim's deposit to round to zero) — mirroring the exact "drip" mechanic and timing analysis (1 minute to 1 week windows) demonstrated in the referenced xETH PoC.

### Recommendation
Add an explicit non-zero check on `inkind` in every vault's `deposit` function, mirroring the existing `redeem` guard:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `ERR-AMOUNT-ZERO` / `ERR-SLIPPAGE` assertions in `deposit`, applied uniformly to `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, and `v0-vault-usdh.clar`.

### Proof of Concept
1. Vault is initialized: `initialize` seeds `MINIMUM-LIQUIDITY` (`u1000`) shares to `NULL-ADDRESS`, so `total-supply = 1000`, `total-assets = 1000` (price/share = 1.0).
2. Time passes and borrowers accrue interest; `total-assets-preview` grows (via `debt-preview`/`total-borrowed`) to, say, `2,000,000`, while `total-supply` remains `1000` (price/share = 2000).
3. Victim calls `deposit` with `amount = 1000` (or any `amount < 2000`) and `min-out = 0`.
4. `convert-to-shares-preview` computes `mul-div-down(1000, 1000, 2000000) = 0`.
5. `(asserts! (>= 0 0) ERR-SLIPPAGE)` passes; `receive-underlying` pulls the victim's `1000` underlying units into the vault; `ft-mint?` mints `0` shares to the victim.
6. Victim's underlying is now permanently part of `total-assets`, increasing the value of all other shareholders' shares, while the victim holds zero `zft` and has no claim to redeem any of the deposited funds.
