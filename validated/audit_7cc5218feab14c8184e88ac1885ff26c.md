### Title
Cross-transaction output metadata contamination in `Bitcoin::get_outputs` lets an attacker overwrite the InInstruction data and presumed origin of unrelated deposits in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates matched `Output`s from every transaction in a block into a single `outputs` vector, but then, inside the per-transaction loop, computes `presumed_origin` and `extract_serai_data(tx)` for the *current* transaction and applies them to **all** outputs collected so far — not just the outputs found in the current transaction. Any transaction later in the block (even one with no Serai outputs at all, as long as an earlier tx produced one) rewrites the `data`/`presumed_origin` of every earlier output. An unprivileged party who gets any transaction mined in the same block as a victim deposit can graft their own OP_RETURN / witness-embedded InInstruction `data` and origin onto that victim's External output.

### Finding Description
In `get_outputs`, the result vector is declared before the transaction loop:

```rust
let mut outputs = vec![];
// Skip the coinbase transaction which is burdened by maturity
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { ... outputs.push(output); }

  if outputs.is_empty() {
    continue;
  }
  // populate the outputs with the origin and data
  let presumed_origin = { let input = &tx.input[0]; ... };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {
    if output.kind == OutputType::External {
      output.data.clone_from(&data);
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```
processor/src/networks/bitcoin.rs:686-740

Two scoping errors follow from this structure:

1. `outputs.is_empty()` is checked against the cumulative vector, so once any earlier transaction produced an output, the origin/data population runs for *every* subsequent transaction — including transactions containing zero Serai outputs.
2. `for output in &mut outputs` iterates the cumulative vector, so each subsequent transaction unconditionally overwrites `presumed_origin` on all previously collected outputs, and overwrites `data` on all previously collected `OutputType::External` outputs with `extract_serai_data(tx)` of the *current* tx.

`extract_serai_data` pulls attacker-controlled bytes from any `OP_RETURN` output in the transaction, or from the witness of any input matching the `SHA256 <push> OP_EQUALVERIFY` pattern, truncated to `MAX_DATA_LEN` (processor/src/networks/bitcoin.rs:473-524). `presumed_origin` is derived from whatever `tx.input[0]` spends. Neither is bound to the transaction that actually paid the Serai address.

### Impact Explanation
The processor treats `Output::data()` on `OutputType::External` outputs as the InInstruction accompanying a deposit, and `presumed_origin` for refund/attribution purposes. Because block transaction ordering is influenced by miners/fees and attacker transactions are trivially crafted, an attacker can:

- Place a transaction in the same block, *after* a victim's deposit to a Serai external address, embedding a chosen InInstruction payload via OP_RETURN or the witness pattern. Since the mutation loop runs for the attacker's tx (outputs is non-empty) and iterates all outputs, the victim's External output's `data` is replaced with the attacker's instruction bytes — an instruction the depositor never authored gets associated with real received funds.
- Rewrite `presumed_origin` of every earlier output in the block to an address derived from the attacker's own input, corrupting refund attribution.

This maps the reported "attacker causes a Bitcoin payment/message to be attributed incorrectly for extortion" class onto Serai: untrusted on-chain transaction bytes contaminate the instruction data of unrelated deposits, a form of forged-instruction injection reachable purely with public inputs (sending a Bitcoin transaction).

### Likelihood Explanation
- Requires only that the attacker's transaction appear in the same block after the victim's deposit — achievable via mempool timing/fee bidding; no key material, no validator status, no collusion needed.
- The overwrite is deterministic: every later tx in the block overwrites all accumulated outputs, so the *last* tx's data/origin always wins for the whole block's External outputs.
- Even without matching outputs, an attacker's tx triggers the overwrite path, widening the window to any block containing at least one Serai-bound output anywhere earlier.

### Recommendation
Scope the origin/data population to only the outputs found in the current transaction. Collect per-tx results first, and only run the `presumed_origin`/`extract_serai_data` work when that per-tx set is non-empty, mutating only that set:

```rust
for tx in &block.txdata[1 ..] {
  let scanned: Vec<_> = scanner.scan_transaction(tx).into_iter().map(|output| {
    let kind = kinds[output.offset().to_repr().as_ref()];
    Output { kind, presumed_origin: None, output, data: vec![] }
  }).collect();
  if scanned.is_empty() { continue; }
  let presumed_origin = ...;
  let data = Self::extract_serai_data(tx);
  for output in scanned.iter_mut() { ... }
  outputs.extend(scanned);
}
```
Additionally, guard `tx.input[0]` with a check that the tx actually has inputs before indexing.

### Proof of Concept
1. Victim broadcasts tx A paying the Serai external address (`key + offsets[&OutputType::External]` script), with their own OP_RETURN InInstruction `data_A`. Tx A lands in block B at index i.
2. Attacker crafts tx B with no Serai outputs, containing an OP_RETURN output carrying `data_B` (an arbitrary InInstruction payload), and gets it mined at index j > i in block B.
3. `get_outputs(B, key)`: iteration for tx A pushes the External output and sets `data = data_A`, `presumed_origin = origin_A`. Iteration for tx B: `scanner.scan_transaction(tx B)` returns nothing, but `outputs` is non-empty so the `continue` is skipped; the loop then sets every accumulated output's `data` to `data_B` and `presumed_origin` to `Address::new(attacker's spent output script_pubkey)`.
4. Result: the scanner-reported External output for the victim's deposit carries `data_B` and the attacker's origin — the emitted `Output` pairs real received funds with instruction bytes and origin attribution the depositor never created.
