### Title
SignableTransaction trusts serialized `ReceivedOutput` values/scripts over on-chain truth, producing invalid spends - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction` treats the metadata inside a `ReceivedOutput` — `output.value`, `output.script_pubkey`, `outpoint`, and `offset` — as authoritative accounting of what the multisig owns, yet the only consistency check performed before signing (`multisig`) verifies that `offset.group_key()` maps to `prevouts[i].script_pubkey`. The *value* and *outpoint* fields are never validated against anything. This mirrors the vault bug's shape: two sources of truth (recorded metadata vs. actual chain state / physical tokens vs. `totalSupplies`), where only one is checked and the other is blindly consumed. Because `ReceivedOutput::read` accepts fully attacker-controlled bytes, an unprivileged party can supply a forged output whose script genuinely matches the scanner key while claiming a fabricated amount. The resulting FROST signature commits (via BIP-341 `Prevouts::All`) to the forged amounts, yielding a deterministically invalid transaction and permanently jamming any spend attempted with the forged input.

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `output: TxOut`, and `outpoint` with no validation that the outpoint exists on chain, is unspent, or that `value`/`script_pubkey` match the real UTXO (`networks/bitcoin/src/wallet/mod.rs:120-134`). `SignableTransaction::new` then uses `input.output.value` as `input_sat` for the funds/fee/change computation and stores the `TxOut` verbatim in `prevouts` (`send.rs:175-176`, `send.rs:253`). The lone verification in `multisig` (`send.rs:273-282`) only checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — i.e., it validates the *script* half of the accounting but not the *amount* or *existence* half. At signing time, `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), ...)` commits every participant's signature share to the attacker-chosen amounts (`send.rs:373-390`).

An attacker therefore crafts `ReceivedOutput` bytes with a real-looking `script_pubkey` equal to the vault's P2TR script (so the `multisig` check passes) but an arbitrary `value` or bogus `outpoint` — e.g., an already-spent outpoint, or a higher/lower amount than the chain holds. `SignableTransaction::new` succeeds, `needed_fee` and the change output are computed from the phantom balance, all honest signers produce valid FROST shares for that sighash, and `complete` returns a transaction that any Bitcoin node rejects because the committed prevout amounts (or the outpoint itself) do not match the UTXO set. This is the direct analog of the vault's "physical tokens sufficient but accounting inconsistent" flaw: the script/key check passes (the "physical" claim), while the recorded accounting (value/outpoint) diverges from reality and is never reconciled.

### Impact Explanation
Every signing session built on a forged `ReceivedOutput` is wasted and its output is an unbroadcastable transaction — a denial of service on spending for the affected inputs, analogous to `availableBalance` going negative and bricking borrows. Additionally, `fee()` and change computation derive from the phantom `input_sat`, so fee/change accounting is corrupted whenever it doesn't outright fail. Because the forged bytes only need to pass a public `read`/constructor path, any component that ingests serialized outputs from untrusted peers, queues, or storage inherits the vulnerability.

### Likelihood Explanation
Triggering requires only that an attacker feed crafted bytes to `ReceivedOutput::read` (explicitly an untrusted-input surface) or otherwise inject a forged output into the input-selection path — no key material, validator status, or collusion is needed. The failure is deterministic: BIP-341 commits to all prevout amounts, so any `value` mismatch guarantees an invalid signature, not a probabilistic one. The main mitigation is that an integrator sourcing `ReceivedOutput`s exclusively from its own `Scanner` over a trusted node is not exposed, which caps severity at Medium.

### Recommendation
Short term: in `SignableTransaction::new` or `multisig`, re-derive and verify the full UTXO claim — at minimum verify `script_pubkey` against every registered scanner script (as `multisig` already does) and document that `value`/`outpoint` must be confirmed against a trusted node before signing; prefer constructor APIs that take only an `OutPoint` and fetch the `TxOut` from the node's UTXO set. Long term: adopt a single source of truth — make `ReceivedOutput` construction impossible except via `Scanner::scan_transaction` (seal `offset`/`output`/`outpoint` fields and make `read` produce an unverified marker type that cannot be passed to `SignableTransaction::new`), and add invariant tests asserting signed prevouts match confirmed chain state.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read
let mut forged = Vec::new();
// offset: any scalar; ZERO targets the vault's root script
forged.extend(Scalar::ZERO.to_bytes());
// TxOut: script_pubkey = vault's real P2TR script (passes multisig check),
// value = inflated amount the vault does not actually hold
TxOut {
  value: Amount::from_sat(1_000_000_000),          // phantom balance
  script_pubkey: p2tr_script_buf(vault_key).unwrap(), // passes send.rs:277 check
}.consensus_encode(&mut forged).unwrap();
// OutPoint: a real-looking but worthless/nonexistent outpoint
OutPoint::new(real_txid, 7).consensus_encode(&mut forged).unwrap();

let input = ReceivedOutput::read(&mut forged.as_slice()).unwrap();

// Succeeds: input_sat accounting uses the forged 1 BTC
let tx = SignableTransaction::new(vec![input], &payments, Some(change), None, FEE).unwrap();
// Succeeds: only script-vs-key is checked, never value-vs-chain
let machine = tx.multisig(&keys[&Participant::new(1).unwrap()]).unwrap();
// All honest signers sign a sighash committing to phantom prevout amounts;
// complete() yields a transaction every node rejects as invalid — DoS.
```
