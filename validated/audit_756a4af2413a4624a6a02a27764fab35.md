### Title
Git's built-in clone-time code-execution protection (`GIT_CLONE_PROTECTION_ACTIVE`) is explicitly disabled during every clone - (File: app/src/lib/git/clone.ts)

### Summary
Upstream Git (2.45.1+) introduced the `GIT_CLONE_PROTECTION_ACTIVE` safety mechanism as part of the fix for the recursive-clone/`.gitmodules`+hooks remote-code-execution class of vulnerabilities (the CVE-2024-32004/32020-series issues), which let a maliciously crafted repository execute arbitrary hooks/commands on the victim's machine during `git clone --recursive`. This check is meant to detect and abort clone/checkout sequences where a hook is unexpectedly triggered mid-clone (a state that should never legitimately occur). Desktop's `clone()` function explicitly forces this protection **off** on every single clone, exactly the operation where a hostile, attacker-hosted repository is first ingested.

### Finding Description
`clone()` builds the execution environment for every "Clone repository" action and unconditionally injects: [1](#0-0) 

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```

and then invokes `git clone --recursive ... -- <url> <path>`: [2](#0-1) [3](#0-2) 

This is structurally the same class of bug as the SIZE report: a security-critical **state flag** (`atState`'s reliance on `a.data.lowestQuote == type(uint128).max`, vs. here Git's internal invariant "no hook may run while this clone-protection sentinel is active") is overridden by the caller using attacker-reachable input as the trigger. In the SIZE contract, the attacker crafts bid/finalize parameters so the "not finalized" sentinel is written even though the auction *is* finalized, letting cancel logic run in a state it was never meant to run in. Here, Desktop hard-codes the git-side safety sentinel to the disabled value on the very command (`clone --recursive`) that ingests untrusted, attacker-controlled repository content (submodule URLs/paths, `.gitmodules`, and hook templates delivered via nested repositories) — the exact path this git-side protection exists to guard.

Because `--recursive` is always passed, this affects every clone including forks and third-party remotes that a user opens via "Clone Repository" or via the `x-github-client://openRepo/...` deep link (parsed in `parseAppURL`/`dispatchURLAction`, which flows into a clone). An attacker who controls the cloned/fetched repository (its submodule graph, refs, and `.gitmodules`) can craft it so the recursive submodule clone step would normally trip the upstream protection (e.g. a submodule path colliding with `.git`, or triggering a hook invocation mid-clone) — but with `GIT_CLONE_PROTECTION_ACTIVE=false`, git will not raise the corresponding fatal error and abort, effectively re-opening the RCE window that this git release specifically closed.

### Impact Explanation
If exploitable end-to-end, this reintroduces the impact of the underlying git CVE class: arbitrary code execution on the victim's machine as soon as they clone or fetch a maliciously crafted remote repository through Desktop — no additional user action beyond "Clone repository" (or clicking a deep link that triggers a clone) is required. This satisfies the in-scope impact bar (code execution triggered by an attacker-controlled fetched repository).

### Likelihood Explanation
Likelihood is high in terms of reachability: `clone()` is the single, unconditional code path for all Desktop clone operations (UI "Clone repository", CLI `--cli-clone`, and `open-repository-from-url` deep links), and the disabling flag is set unconditionally rather than only for known-safe/local flows. The residual uncertainty is git's exact patched behavior in the specific dugite/git version bundled with this build (i.e., whether the specific attack primitives the protection blocks are otherwise mitigated at a different layer) — this could not be fully confirmed from the available index, but the code explicitly and deliberately turns off a named upstream security control on the untrusted-input path, which is inherently high risk and warrants investigation/removal.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Let git's default (enabled) protection remain active during `clone --recursive` against untrusted remotes. If the override was added to work around a legitimate false positive (e.g., Desktop's own hook interception/trampoline mechanism from `withHooksEnv/withTrampolineEnv` tripping the check), scope the override narrowly (only for verified same-origin/local/test clones) rather than disabling it globally for every remote clone, and add a regression test cloning a crafted repository designed to trip the upstream protection to confirm git still aborts as intended.

### Proof of Concept
Conceptual reproduction (exact crafted payload requires matching the specific git version's protection trigger, which could not be fully derived from the index):
1. Attacker hosts a repository with a submodule/`.gitmodules` configuration engineered to trigger the scenario that `GIT_CLONE_PROTECTION_ACTIVE` is designed to catch during `git clone --recursive` (e.g., a submodule hook or config injection during recursive checkout).
2. Victim uses Desktop's "Clone repository" (or clicks a `x-github-client://openRepo/<attacker-url>` link) to clone the attacker's repository.
3. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment (`app/src/lib/git/clone.ts:81-93,119-125`).
4. Because the protection is disabled, git does not abort on the crafted condition, and the attacker's payload executes/behaves as it would have prior to the upstream fix, instead of the clone failing safely as git intends.
