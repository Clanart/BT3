### Title
Spoofed `WWW-Authenticate` `realm="GitHub"` Header Tricks Desktop into Launching an Enterprise Sign-In Flow Against an Attacker-Controlled Host - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
`getEndpointKind()` classifies a git remote as GitHub `enterprise` purely by string-matching `realm="GitHub"` inside a `WWW-Authenticate` header value that Git forwards verbatim from the remote server's HTTP response into the credential-helper protocol. This value is fully attacker-controlled by any git server the user fetches/pushes/clones from, and is treated as authoritative without any corroborating check (e.g. actually contacting the host's API to confirm it's a genuine GHE instance).

### Finding Description
When Git performs HTTP(S) authentication against a remote, it captures any `WWW-Authenticate` response headers and passes them to the configured credential helper as `wwwauth[]=...` fields [1](#0-0) . Desktop's `getEndpointKind()` uses these attacker-supplied header values as a "happy path" to decide the endpoint is a GitHub Enterprise server if the string `realm="GitHub"` is present, with no fallback verification unless that substring is absent [2](#0-1) .

`parseCredential()` parses this header text directly out of the credential-helper stdin protocol, imposing no restriction on its content beyond the `key=value` line format [3](#0-2) . Because the header originates from the remote server the user is talking to (any URL added as a remote, or reached via a redirect/proxy), an attacker fully controls this value.

Once `getEndpointKind()` returns `'enterprise'` for a completely arbitrary host, `getCredential()` finds no matching stored account for that host's endpoint (correctly, since it's not a real GHE the user has an account for) and calls `ui.promptForGitHubSignIn(endpoint)` [4](#0-3) . `promptForGitHubSignIn()` then explicitly starts the **Enterprise** sign-in flow and sets the sign-in endpoint to the attacker's own origin: `this.dispatcher.beginEnterpriseSignIn(cb); await this.dispatcher.setSignInEndpoint(origin)` [5](#0-4) .

The broken invariant: Desktop assumes that a self-reported `realm="GitHub"` string in an HTTP auth challenge is proof the target is a legitimate GitHub Enterprise deployment, and uses that unverified claim to drive a trust decision (which sign-in/OAuth flow to launch, and against which origin). No existing guard (TLS, hostname allowlist, or an actual API probe) corroborates the claim before `setSignInEndpoint(origin)` is invoked — the code path that does perform a real check, `isGitHubHost(endpoint)` at the bottom of `getEndpointKind()`, is only reached if the header did *not* match, i.e., the vulnerable branch specifically bypasses verification [6](#0-5) .

### Impact Explanation
A malicious or compromised git server (any remote the victim clones/fetches/pushes to, including one reached through a MITM'd proxy or a redirected URL) can present an HTTP `401` response with `WWW-Authenticate: Basic realm="GitHub"`. This causes GitHub Desktop to present the user with what looks like a normal "Sign in to GitHub Enterprise" dialog, pre-populated with the attacker's origin as the enterprise endpoint. A user who completes this flow will be directing their enterprise/OAuth sign-in interaction (and any resulting credentials Desktop obtains) at the attacker's server rather than a real GitHub instance — enabling credential/token capture without any unusual user action beyond the ordinary "fetch/clone from a remote and enter your credentials when prompted" flow that Desktop treats as normal.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs to control (or MITM) the HTTP responses from a remote the victim adds/uses in Desktop, which is squarely within the accepted threat model ("attacker controls a git remote/proxy response"). No local access, admin rights, or pre-existing malware is required — only that the victim performs a normal git operation (fetch/push/clone) against the attacker's remote, which is a very common and expected action in Desktop's workflow.

### Recommendation
- Do not use the raw `WWW-Authenticate` realm string as sole proof of GitHub/Enterprise identity in `getEndpointKind()`; always corroborate with an actual `isGitHubHost()` (or equivalent authoritative) check to that specific origin before classifying it as `enterprise`, regardless of what the header claims.
- If the header-based heuristic is kept for UX speed, at minimum require it be confirmed via a live probe before calling `dispatcher.setSignInEndpoint(origin)` / `beginEnterpriseSignIn`.
- Surface the resolved origin clearly in the sign-in dialog so users can visually verify what host they are authenticating against.

### Proof of Concept
1. Attacker stands up a plain HTTP(S) git server (or a MITM proxy in front of any git URL) at `https://evil.example.com/some/repo.git`.
2. Victim adds this URL as a remote in GitHub Desktop and performs a `fetch`/`push`.
3. Git attempts HTTP Basic auth; the server responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as `wwwauth[0]=Basic realm="GitHub"` to Desktop's credential-helper trampoline via stdin, parsed by `parseCredential()` [7](#0-6) .
5. `getEndpointKind()` matches `realm="GitHub"` and returns `'enterprise'` for `evil.example.com` [8](#0-7) .
6. `getCredential()` finds no existing account for that endpoint and calls `ui.promptForGitHubSignIn('https://evil.example.com')`.
7. `promptForGitHubSignIn()` calls `beginEnterpriseSignIn` and `setSignInEndpoint('https://evil.example.com')`, presenting the user a GitHub Enterprise sign-in UI pointed at the attacker's server [9](#0-8) .

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}
