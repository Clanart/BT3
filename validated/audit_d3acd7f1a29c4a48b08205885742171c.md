## Analysis

The report's broken invariant is: a state-mutating path that anyone/anything can trigger updates *part* of dependent state (timestamps/balances) while leaving a *derived value other code paths rely on* (`rewardPerTokenStored`) stale — causing silent loss for the victim. The closest structural analog in GitHub Desktop is not a smart-contract style access-control bug (there is no such trust boundary in a desktop app) but the same "partial update, stale derived value used elsewhere" pattern applied to **partial-commit line selection versus refreshed diff content**, where the content is attacker-influenced through a fetched/cloned repository.

### Title
Stale line-indexed partial-commit selection is not revalidated against refreshed diff content for non-focused files, causing silent corruption of committed hunks - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
When GitHub Desktop refreshes working-directory status (`_loadStatus`), `updateChangedFiles` merges the new file list with the previous `DiffSelection` for any file that still exists, but for files with a `Partial` selection it simply reattaches the *old* `DiffSelection` object (holding absolute line indices from the previous diff) onto the *new* file entry, without recomputing which line indices are still valid for the new content. Revalidation of `selectableLines` against a fresh diff only happens for the single file that is currently selected/rendered in the Changes view. If tracked-file content changes on disk between two status refreshes for a file that is *not* the actively viewed file (e.g. due to a smudge/clean filter, submodule checkout, or any background operation that rewrites a tracked file after a `fetch`/`pull` from an attacker-controlled remote), the stale line-index set is carried forward untouched and later used by `formatPatch`/`applyPatchToIndex` to build the commit patch.

### Finding Description
`updateChangedFiles` preserves `existingFile.selection` verbatim for files with a partial selection unless `clearPartialState` is explicitly requested: [1](#0-0) 

The only place that reconciles a `DiffSelection`'s `selectableLines` against a freshly loaded diff is `updateChangesWorkingDirectoryDiff`, and it is scoped strictly to the single currently-selected file: [2](#0-1) [3](#0-2) 

`_loadStatus` — which is invoked repeatedly in the background (e.g. via `refreshIndicatorForRepository`) — calls `updateChangedFiles` on every refresh regardless of which file is selected, but only calls `updateChangesWorkingDirectoryDiff` afterward, which bails out immediately unless exactly one file is selected: [4](#0-3) [5](#0-4) 

The patch-building code, which decides what actually goes into the commit, trusts the `DiffSelection`'s absolute line indices without any check that they still correspond to the same underlying content: [6](#0-5) 

`DiffSelection` itself is a pure line-index bitset with no notion of content hashing/versioning, so once `selectableLines`/`divergingLines` are stale they are silently reused: [7](#0-6) 

The code comment for the (correctly-guarded) selected-file path explicitly acknowledges the underlying risk without treating it as a security boundary: "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines" — but this remediation is applied only to the actively selected file, not to every file whose partial selection is preserved by `updateChangedFiles`.

### Impact Explanation
**Impact: Medium-High.** If a background status refresh (which runs periodically and after fetches, independent of what the user is looking at) picks up new content for a file with a pre-existing partial selection that is not the currently open file, the old line indices get silently reattached to the new content. When the user later commits with "include selected lines," `applyPatchToIndex`/`formatPatch` will select/deselect lines by index against the new hunk structure, potentially staging attacker-influenced additions the user never reviewed, or dropping lines the user intended to include — a silent corruption of what gets committed and possibly pushed.

### Likelihood Explanation
**Likelihood: Medium.** It requires: (1) the user has a file with a partial (line-level) selection pending, (2) that file is not the one currently displayed in the Changes diff view, and (3) the on-disk content of that file changes as a side effect of repository operations sourced from an attacker-influenced remote (e.g. a fetch/pull/checkout that runs a smudge filter, submodule update, or LFS pointer resolution) before the user commits. These are plausible but not one-click conditions, and Desktop already partially mitigates the single-selected-file case, suggesting the multi-file gap may be an oversight rather than an intentionally accepted risk.

### Recommendation
Recompute (or at minimum invalidate) `selectableLines`/`divergingLines` for *every* file whose diff has structurally changed during `updateChangedFiles`, not only for the currently selected file, or force `clearPartialState` semantics whenever the underlying blob/oid for a partially-selected file differs from what was used to establish that partial selection. Alternatively, track a content fingerprint (blob SHA) alongside `DiffSelection` and refuse to apply it as-is if the fingerprint no longer matches before formatting a patch.

### Proof of Concept
Conceptual PoC (unverified end-to-end due to index limitations, but each step is backed by cited code):
1. User opens a repo, selects file `bar` (not the currently displayed file `foo`), and sets a partial line selection on `bar` (some lines staged, some not) — this creates a `DiffSelection` with `selectableLines` bound to `bar`'s current diff.
2. User keeps `foo` open in the Changes view (so `updateChangesWorkingDirectoryDiff`'s revalidation only touches `foo`).
3. A `git pull`/fetch from a remote under attacker control (or a checkout/merge with a malicious `.gitattributes` smudge filter) rewrites `bar`'s working-tree content, changing hunk boundaries/line counts, while `bar` remains "modified."
4. The next periodic `_loadStatus`/`refreshIndicatorForRepository` call runs `updateChangedFiles`, which reattaches `bar`'s old `DiffSelection` to the new file object per `app/src/lib/stores/updates/changes-state.ts:43-60`, without recomputing `selectableLines` (that only happens for `foo` per `app/src/lib/stores/app-store.ts:3404-3497`).
5. User commits including `bar`; `formatPatch` uses the stale absolute line indices against `bar`'s new hunks (`app/src/lib/patch-formatter.ts:143-161`), silently including/excluding different content than the user intended to review and stage. [8](#0-7) [9](#0-8)

export function updateChangedFiles(
  state: IChangesState,
  status: IStatusResult,
  clearPartialState: boolean
): ChangedFilesResult {
  // Populate a map for all files in the current working directory state
  const filesByID = new Map<string, WorkingDirectoryFileChange>()
  state.workingDirectory.files.forEach(f => filesByID.set(f.id, f))

  // Attempt to preserve the selection state for each file in the new
  // working directory state by looking at the current files
  const mergedFiles = status.workingDirectory.files
    .map(file => {
      const existingFile = filesByID.get(file.id)
      if (existingFile) {
        if (clearPartialState) {
          if (
            existingFile.selection.getSelectionType() ===
            DiffSelectionType.Partial
          ) {
            return file.withIncludeAll(false)
          }
        }

        return file.withSelection(existingFile.selection)
      } else {
        return file
      }
    })
