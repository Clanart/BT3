### Title
Malicious self-reporting ERC20 contract can mint unbacked Cosmos coins via `ConvertERC20` invariant bypass - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`convertERC20IntoCoinsForNativeToken` validates the "escrow" step of a native ERC20→coin conversion entirely by querying the same untrusted contract's `balanceOf(module)` before and after the `transfer` call, and by trusting the contract's own `transfer` return value. Because `RegisterERC20` is permissionless by default, an attacker can register a fully malicious ERC20 contract and mint arbitrary bank coins with no real token backing.

### Finding Description
`RegisterERC20` allows any signer to register an arbitrary ERC20 contract as `OWNER_EXTERNAL` (native ERC20 pair) as long as `params.PermissionlessRegistration` is true, which is the default value [1](#0-0) [3](#0-2) . `registerERC20` only checks the contract isn't already registered and reads name/symbol/decimals metadata via `QueryERC20` — it does not verify real transfer semantics [4](#0-3) .

In `convertERC20IntoCoinsForNativeToken`, the pre-transfer balance (`balanceToken`) and post-transfer balance (`balanceTokenAfter`) are both obtained via `k.BalanceOf`, which just calls the target contract's own `balanceOf` view function [5](#0-4) [6](#0-5) . The `transfer` call's success is validated only by unpacking the ABI-encoded boolean return value, and the "invariant" check just compares `balanceTokenAfter` to `balanceToken + amount` — both self-reported by the same attacker-controlled contract [7](#0-6) . There is no independent verification (e.g., checking actual EVM storage slots, an event log for `Transfer`, or comparing against a trusted state) unless `res.Ret` is empty, in which case the code falls back to checking for a `Transfer` event in logs — but a malicious contract can still choose to return non-empty ABI data and skip this check.

An attacker can therefore:
1. Deploy a fake "ERC20" contract whose `transfer()` always ABI-encodes `true` (no real balance mutation for the sender or module), and whose `balanceOf(module)` returns an internally-tracked, ever-increasing counter that increments by exactly the requested `amount` on each call (so the self-consistency check trivially passes).
2. Call `MsgRegisterERC20` (permissionless by default) to register this contract as a native ERC20 token pair.
3. Repeatedly call `MsgConvertERC20`, which will pass all checks and call `k.bankKeeper.MintCoins` for the requested amount, then send it to the receiver [8](#0-7) .

No real ERC20 tokens are ever escrowed; the attacker mints arbitrary Cosmos-native coins under `pair.Denom` backed by nothing.

### Impact Explanation
This results in unauthorized minting of native bank coins with no real economic backing, corrupting total spendable-value accounting for `pair.Denom`. If those coins are later transferred via IBC or through the bank precompile, this constitutes fully unbacked value creation/duplication of spendable user value — a Critical unauthorized-minting impact under the Allowed Impact Gate.

### Likelihood Explanation
This requires no privileged role: `PermissionlessRegistration=true` by default enables any EOA to register any contract they deploy as a native ERC20 pair, and then to invoke `MsgConvertERC20` themselves. The only skill required is writing a malicious Solidity contract that returns fabricated `balanceOf`/`transfer` values — a standard and easily reproducible technique (this is the well-known "fake/self-reporting balance" ERC20 pattern). This is a systemic design property of "native ERC20" token pairs across Cosmos EVM/Evmos-derived codebases: the module inherently trusts the registered contract to behave honestly, since a native ERC20 pair by definition wraps an externally-owned contract not minted by the module itself.

### Recommendation
Given this appears to be an accepted, well-known design tradeoff of "native ERC20" (`OWNER_EXTERNAL`) token pairs shared across Cosmos EVM/Evmos-style implementations (the entire point of `convertERC20IntoCoinsForNativeToken`'s balance-invariant checks is to detect *honest but deflationary/fee-on-transfer* tokens, not to defend against fully malicious contracts), the practical mitigations would be: disable `PermissionlessRegistration` by default so only governance can register native ERC20 pairs after due diligence, and/or require additional bytecode/behavior validation (e.g., verifying the contract is not proxy-upgradeable, or restricting native pairs to well-audited, immutable, non-mintable-by-owner tokens) before allowing conversion.

### Proof of Concept
1. Deploy `FakeERC20` with:
   - `transfer(address,uint256) returns (bool)` that always returns `true` without any storage write to a real balance mapping.
   - `balanceOf(address account) returns (uint256)` that returns a value from an internal counter incremented by the attacker on each call (or hardcoded to track expected `moduleBalance + amount`).
2. As an unprivileged account, submit `MsgRegisterERC20{Erc20Addresses: [FakeERC20]}` — succeeds because `PermissionlessRegistration=true` by default [1](#0-0) .
3. Submit `MsgConvertERC20{ContractAddress: FakeERC20, Amount: X, ...}` repeatedly.
4. Observe `k.bankKeeper.MintCoins` executes each time and the receiver's bank balance in `pair.Denom` increases by `X`, while `FakeERC20` never held or transferred any genuinely escrowed value — confirmed by inspecting that `convertERC20IntoCoinsForNativeToken`'s only balance checks are `k.BalanceOf` calls back into the same malicious contract [9](#0-8) .

func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil

// BalanceOf queries an account's balance for a given ERC20 contract
func (k Keeper) BalanceOf(
	ctx sdk.Context,
	abi abi.ABI,
	contract, account common.Address,
) *big.Int {
	res, err := k.evmKeeper.CallEVM(ctx, abi, types.ModuleAddress, contract, false, nil, "balanceOf", account)
	if err != nil {
		return nil
	}

	unpacked, err := abi.Unpack("balanceOf", res.Ret)
	if err != nil || len(unpacked) == 0 {
		return nil
	}

	balance, ok := unpacked[0].(*big.Int)
	if !ok {
		return nil
	}

	return balance
}
