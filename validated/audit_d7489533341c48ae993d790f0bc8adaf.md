### Title
`SignableTransaction::new` creates change outputs below the system's spendable/dust floor, causing received change to be silently discarded - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The external report describes a contract that is designed to hold a balance yet cannot receive funds because its `receive()` path was disabled. The analog in Serai's Bitcoin wallet is the inverse direction of the same class: `SignableTransaction::new` emits an on-chain change output that the rest of the system defines as unspendable dust, so the change is technically "received" but is never credited and can never be spent.

### Finding Description
`SignableTransaction::new` decides whether to append a change output by comparing the leftover value against the wallet-local constant `DUST`, defined in `networks/bitcoin/src/wallet/send.rs:32` as `546` sats (Bitcoin's bare relay limit). If `input_sat - (payment_sat + fee_with_change) >= 546`, a change output paying a Serai-owned P2TR script is pushed into the transaction (`send.rs:224-235`).

However, the threshold at which Serai treats a received output as real is `Bitcoin::DUST = 10_000` sats, applied in the processor's scanner (`processor/src/multisigs/scanner.rs:564`, `output.balance().amount.0 >= N::DUST`) and justified in `processor/src/networks/bitcoin.rs:606-638` by the fee cost of spending an input (285+ sats under a 5 sat/vbyte assumption, padded to 10,000). The change address used is a registered scanner offset (`processor/src/networks/bitcoin.rs:666-669`), so the output is detected by `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-213`) and then dropped by the `>= N::DUST` filter.

Any transaction whose leftover lands in the band `[546, 10_000)` therefore produces a change output that:
- is created and confirmed on-chain, paying to a key Serai controls,
- is scanned and then discarded as dust,
- is never tracked as a spendable input, permanently stranding those funds.

An unprivileged depositor can influence this band: by choosing the size and count of deposits to the external address (plain Bitcoin transactions they send, which are in-scope public inputs), they shape which inputs the scheduler aggregates and hence the resulting leftover amount.

### Impact Explanation
Direct, irreversible loss of funds. Each affected transaction burns between 546 and 9,999 sats of the multisig's balance into an output the system structurally ignores. The output is not spendable through any Serai path: `ReceivedOutput`s are only produced by `Scanner`, the processor only surfaces outputs ≥ `N::DUST`, and `SignableTransaction::new` refuses to build transactions from inputs it never sees. This matches the accepted impact class "funds reported received that are not spendable" (here: received on-chain, never spendable). Loss is bounded per occurrence but repeatable.

### Likelihood Explanation
The vulnerable band is ~9,454 sats wide and is hit whenever `input_sat - payment_sat - fee_with_change ∈ [546, 10_000)`. Change is only appended when the leftover is non-trivial, so this occurs on a meaningful fraction of ordinary spends, and is deterministic once inputs, payments, and fee rate are fixed. No malicious validator, key material, or off-protocol behavior is required.

### Recommendation
Use a single dust/spendability definition for both creation and acceptance. In `SignableTransaction::new` (`send.rs:224-235`), compare the leftover against the spendable threshold the consumer enforces (i.e., raise the change cutoff to the processor's `N::DUST`, or route change only when it exceeds that threshold), letting sub-threshold leftovers become fee instead of stranded outputs. Alternatively, lower the processor-side filter to match, though the fee-cost rationale in `bitcoin.rs:622-637` argues for raising the wallet cutoff.

### Proof of Concept
```rust
// Conceptual, against networks/bitcoin/src/wallet/send.rs
// Inputs: a single ReceivedOutput worth 100_000 sats.
// Payments: 95_000 sats to some external script.
// fee_per_vbyte chosen s.t. fee_with_change ~= 4_000..9_000 sats
// (e.g., a high quoted median fee), leaving leftover in [546, 10_000).

let tx = SignableTransaction::new(
  vec![input],            // ReceivedOutput { offset, output: 100_000 sats, ... }
  &[(payment_script, 95_000)],
  Some(change_script),    // registered scanner offset, key we control
  None,
  fee_per_vbyte,          // tuned so leftover = 5_000 sats
).unwrap();

// tx.transaction().output contains a change output of 5_000 sats to
// `change_script`. Once broadcast and confirmed:
// - Scanner::scan_transaction returns it as a ReceivedOutput (mod.rs:205-211)
// - processor scanner drops it: 5_000 < N::DUST (10_000) (scanner.rs:564)
// - The 5_000 sats are permanently stranded; no scheduler plan will ever
//   include this UTXO, yet it was never paid as fee either.
```

The asymmetry is the bug class: the "receive" acceptance threshold (10,000) is strictly higher than the "send" creation threshold (546), so the wallet can fabricate outputs that its own pipeline defines as nonexistent — the exact shape of the reference issue (a balance path that exists on one side but not the other).
