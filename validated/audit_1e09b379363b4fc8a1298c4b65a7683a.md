### Title
Commit message trailer injection via unsanitized co-author name/email from GitHub API - (File: `app/src/lib/git/interpret-trailers.ts`)

### Summary
Co-author trailers built from GitHub API-derived user profile fields (`name`, `email`) are interpolated into a single `--trailer token=value` git argument without checking for embedded newlines. Because `git interpret-trailers` writes the trailer value verbatim into the resulting commit message, an embedded newline in the value can produce a second line in the message that itself matches trailer syntax, making it appear (and later parse) as an independently injected trailer.

### Finding Description
`mergeTrailers` builds one `--trailer` argument per trailer directly from attacker-influenceable strings without escaping or rejecting newline characters: [1](#0-0) 

These trailers originate, for co-authors, from `AuthorInput`/`commit-message.tsx`, which formats `${a.name} <${a.email}>` as the trailer value: [2](#0-1) 

The `name`/`email` fields come from `authorFromUserHit`, which is fed by `IMentionableUser`/API responses (`apiUser.name`, `apiUser.email`, or the mentionables list fetched from `fetchMentionables`): [3](#0-2) [4](#0-3) [5](#0-4) 

None of these steps validate or strip control characters (e.g. `\n`) from `name` or `email` before they reach `mergeTrailers`. The underlying git invocation goes through dugite's `exec`, which spawns git directly (no shell), so this is **not** a shell/argv injection — the whole string (including any newline) is passed as a single argv value to `--trailer`. The actual risk is at the git-semantics layer: `git interpret-trailers` writes `token: value` into the message verbatim; if `value` contains a literal `\n` followed by text resembling `Key: Value`, that second line becomes part of the commit message body and matches trailer syntax when later parsed (e.g. by `parseTrailers`/`%(trailers)`), effectively appearing as an attacker-chosen second trailer.

### Impact Explanation
If exploitable, this would let a malicious GitHub account (whose profile `name`/`email` fields are attacker-controlled) — once surfaced as a mentionable/collaborator and selected as a co-author by a victim — inject additional, forged-looking trailer lines (e.g. a bogus `Signed-off-by:`, another `Co-Authored-By:`, or arbitrary custom trailer) into commits the victim creates. This falls under "silent corruption of what the user commits" if realized, since the victim did not intend to add that second trailer.

### Likelihood Explanation
This depends entirely on two unverified preconditions I could not confirm from the code alone:
1. Whether GitHub's API actually permits a user's public `name` or public `email` profile fields to contain a raw `\n` (or other line-breaking control character). GitHub's account settings typically enforce email format validation server-side, and the profile "name" field, while permissive, is commonly stripped of newlines by GitHub's own backend — I did not find and cannot verify this from the client-side repo alone.
2. Whether `git interpret-trailers` itself treats an embedded newline in a `--trailer` value as literal output (creating a second line) or whether it folds/escapes it — I did not find test coverage in this repo confirming git's exact behavior for a newline-containing `--trailer` value.

Both of these are outside GitHub Desktop's codebase and would need to be validated against live GitHub API behavior and actual git binary behavior (as the PoC in the question suggests) before concluding the vulnerability is practically exploitable end-to-end.

### Recommendation
Regardless of whether GitHub's API currently blocks newlines, GitHub Desktop should defensively reject or sanitize (strip/replace `\n`, `\r`, and other control characters) in `trailer.token`/`trailer.value` — particularly for values sourced from co-author name/email — before constructing the `--trailer` argument in `mergeTrailers`, since this function has no guarantee about the origin of its inputs.

### Proof of Concept
Not independently verified. The suggested PoC (craft a co-author whose API-provided email is `"attacker@example.com\nSigned-off-by: attacker@example.com"`, select them as co-author, commit, then run `git log --format='%(trailers)'`) would need to be run against the real GitHub API and a real git binary to confirm both preconditions above hold. I could not execute this in the available tooling.

Given the two open, unverifiable preconditions (GitHub API field validation and git's exact `--trailer` newline handling), I cannot confirm this is definitively exploitable end-to-end from the code alone — this is a plausible defense-in-depth gap rather than a confirmed vulnerability. If the review process requires certainty rather than well-reasoned suspicion, treat this as **not confirmed** pending the PoC being actually run.
