The bug class here is a security-relevant total computed over an incomplete set of inputs, so the check passes when it shouldn't. The analog in Serai's in-scope code is in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`, where the fee/weight calculation omits the OP_RETURN `data` output entirely.

### Title
`SignableTransaction::new` excludes the OP_RETURN data output from the transaction weight, undercalculating `needed_fee` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a caller-supplied `data` parameter of up to 80 bytes which is pushed onto `tx_outs` as an OP_RETURN output (lines 194-202), but the fee is computed by `calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, which reconstructs a transaction containing only `payments` and the optional `change` output. The OP_RETURN output is never included in the weight estimation, so `needed_fee = fee_per_vbyte * vbytes` is computed for a transaction that is smaller than the one actually built and signed.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-206`:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (lines 62-127) builds a dummy `Transaction` whose outputs are `payments` plus at most `change` — `data` is not a parameter and cannot be passed in. The same omission occurs in the change path at lines 224-235, where `fee_with_change` is computed from the same incomplete output set. Consequently:

- `needed_fee` undervalues the true required fee by `fee_per_vbyte * vbytes(op_return_output)` (~90+ weight units / ~23+ vbytes for a full 80-byte payload, plus fixed output overhead of ~34 vbytes).
- The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so it can pass while the actual transaction is below the node's minimum relay fee.
- The change amount at line 228 (`input_sat - payment_sat - fee_with_change`) is computed with the under-estimated fee, so the change output absorbs the shortfall and the final signed transaction pays an effective feerate below `fee_per_vbyte`, potentially below relay minimums.

### Impact Explanation
A `SignableTransaction` built with `data` produces a transaction that underpays its fee relative to the requested rate. When the requested rate is near the relay minimum, the resulting transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` and will be rejected by Bitcoin nodes on broadcast, leaving the inputs unspendable by that transaction and requiring the signing round to be re-run. This is analogous to the external report: an economically meaningful total (`totalUSDborrowed` / `needed_fee`) is computed from a subset of the value it should cover, so a safety check passes when it shouldn't.

### Likelihood Explanation
The defect is deterministic: every call to `SignableTransaction::new` with `data: Some(...)` produces an underestimated `needed_fee` and an overvalued change output. Severity is bounded because the discrepancy is capped at the size of a ≤80-byte OP_RETURN output (~34-100 vbytes), and Serai's own processor always passes `data: None` (`processor/src/networks/bitcoin.rs:450`), so the bug only affects consumers of the wallet API who use the data field — but `data` is a documented, attacker/integrator-controllable public input to the function.

### Recommendation
Include the OP_RETURN output in the weight estimation. Either pass the fully-constructed `tx_outs` (or the `data` payload) into `calculate_weight_vbytes`, or compute the weight after `tx_outs` is finalized. For example, change the signature to accept the final output list and the change flag, and call it after the OP_RETURN push:

```rust
fn calculate_weight_vbytes(
  inputs: usize,
  outputs: &[TxOut],        // final outputs including OP_RETURN, change excluded/pending
  change: Option<&ScriptBuf>,
) -> (u64, u64)
```

and recompute `fee_with_change` against the same complete output set plus the change output.

### Proof of Concept
```rust
// Conceptual: any call with data set undercalculates the fee
let payments = vec![(p2tr_script_buf(key).unwrap(), 10_000)];
let data = Some(vec![0u8; 80]);

let tx = SignableTransaction::new(inputs, &payments, None, data, FEE).unwrap();

// tx.needed_fee() == FEE * vbytes(tx without the OP_RETURN output)
// but tx.fee() == needed_fee while tx.vsize() includes the OP_RETURN output,
// so actual feerate = needed_fee / actual_vsize < FEE
assert!(
  tx.fee() < u64::try_from(tx.vsize()).unwrap() * FEE
);
```

With `FEE = 1` sat/vbyte the check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` passes using the smaller `vbytes`, yet the broadcasted transaction's real feerate is below the relay minimum and will be rejected.
