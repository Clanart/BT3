### Title
Hookify `new_text`/`new_string` field extraction silently returns empty for Write tool, causing block rules to miss dangerous content - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` documents and is used with `field: new_text` as a generic alias that should work for both `Edit` and `Write` under `event: file` rules, but the implementation only reads `tool_input.get('new_string', '')`, a key that never exists on `Write` tool calls (which use `content` instead). A user-authored block rule targeting `new_text` (per the plugin's own README/SKILL guidance) reliably catches `Edit` but silently evaluates to an empty string for `Write`, causing the condition (and thus the block) to never match for `Write` operations with identical dangerous content.

### Finding Description
`_extract_field` in `plugins/hookify/core/rule_engine.py:182-254` first checks `if field in tool_input` (line 196); since `new_text` is never a literal key in any tool's `tool_input`, this fast path never fires for that field. Control falls to the per-tool special case:

```
elif tool_name in ['Write', 'Edit']:
    ...
    elif field == 'new_text' or field == 'new_string':
        return tool_input.get('new_string', '')
``` [1](#0-0) 

For `Write` tool calls, `tool_input` contains `content`, not `new_string` [2](#0-1) . Consequently, `tool_input.get('new_string', '')` always returns `''` for `Write`, whereas for `Edit` it correctly returns the actual new content. `_check_condition` treats a non-`None` empty string as a normal field value and applies the operator (`contains`, `regex_match`, etc.) against `''`, which will not match any non-empty pattern — so the condition silently evaluates false and the rule does not fire, at `plugins/hookify/core/rule_engine.py:157-180`.

The plugin's own documentation instructs users to write exactly this kind of rule: `new_text: New content being added (Edit, Write)` [3](#0-2) , and the skill guide's example rule uses `field: new_text` under `event: file` (which maps to `Edit`, `Write`, `MultiEdit` per `pretooluse.py:48-49`) [4](#0-3) . A rule author (or Claude itself, auto-generating a rule via `/hookify`) following this documented guidance to block dangerous content (e.g., hardcoded API keys, `eval(`, etc.) across both `Edit` and `Write` will unknowingly create a rule that is completely bypassed whenever the operation is performed via `Write` instead of `Edit`.

An attacker who can influence Claude's tool choice through prompt injection (e.g., malicious instructions embedded in repository content, an issue, or a PR that Claude reads) can steer the agent to use `Write` (e.g., overwrite/create a file with the full dangerous content) rather than `Edit`, evading a user's `action: block` rule intended to reliably deny that content, and achieving an unauthorized/unintended file write. Since `pretooluse.py` always exits 0 regardless of hook outcome and only blocks via the `hookSpecificOutput`/`permissionDecision: deny` response derived from `evaluate_rules` [5](#0-4) , a missed match means no deny signal is ever emitted — the write proceeds unblocked.

### Impact Explanation
This breaks the stated invariant that "a matching block rule must reliably deny the protected operation." A user who configures a `block` rule with `field: new_text` to prevent sensitive content (secrets, dangerous code patterns, destructive edits) from being written to disk gets protection against `Edit` but not `Write`, despite documentation explicitly claiming `new_text` applies to both. This can result in unauthorized file writes containing content the user explicitly tried to block, when the responsible tool call is `Write` rather than `Edit` — matching the "Unauthorized file read or write outside the user-approved workspace or target scope" impact category, since the security control the user relies on (`hookify` block rules) is bypassed for one of the two documented tool paths.

### Likelihood Explanation
High feasibility: this is not a contrived edge case — it is the exact usage pattern the plugin's own README and SKILL.md documentation teach users to write. No special privileges beyond normal Claude Code plugin usage are required; only need `hookify` block rule using `new_text`/`content` mismatches and any mechanism (prompt injection, agent's own tool-selection heuristics, or user simply asking Claude to "write" instead of "edit" a file) that causes a `Write` call instead of an `Edit` call with equivalent dangerous content. This is fully deterministic and repeatable given the code logic.

### Recommendation
In `_extract_field`, for `field in ('new_text', 'new_string')` when `tool_name == 'Write'`, fall back to `tool_input.get('content', '')` the same way the `content` field case already does (`tool_input.get('content') or tool_input.get('new_string', '')`). Concretely, unify the alias handling: for `Write`, both `content` and `new_text`/`new_string` should resolve to `tool_input.get('content', '')`; for `Edit`, they should resolve to `tool_input.get('new_string', '')`. Add unit tests asserting that a rule with `field: new_text` matches dangerous content for both `Edit` and `Write` tool calls with equivalent payloads.

### Proof of Concept
Unit test to add to `rule_engine.py` test suite:
```python
def test_new_text_field_matches_write_and_edit_equally():
    rule = Rule(
        name="block-api-key",
        enabled=True,
        event="file",
        action="block",
        conditions=[
            Condition(field="new_text", operator="contains", pattern="API_KEY")
        ],
        message="Blocked!"
    )
    engine = RuleEngine()

    edit_input = {
        "tool_name": "Edit",
        "tool_input": {"file_path": "a.ts", "old_string": "", "new_string": "API_KEY=xxx"}
    }
    write_input = {
        "tool_name": "Write",
        "tool_input": {"file_path": "a.ts", "content": "API_KEY=xxx"}
    }

    edit_result = engine.evaluate_rules([rule], edit_input)
    write_result = engine.evaluate_rules([rule], write_input)

    # Expected: BOTH should be denied since both write identical dangerous content
    assert edit_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
    assert write_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"  # FAILS currently — write_result == {}
```
Running this against the current implementation shows `edit_result` denies as expected, while `write_result` returns `{}` (no match, operation allowed), confirming the bypass.
