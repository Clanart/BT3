### Title
CR-CAT wallet identity resolution keyed only on TAIL hash, ignoring `authorized_providers`/`proofs_checker` "issuer" context - ([File: chia/wallet/cat_wallet/cat_wallet.py])

### Summary
n8n's advisory describes account binding collapsing to a single identity field (`sub`) while ignoring the issuer (`iss`) context that should have scoped it, letting two different issuers' tokens map to one local account. The Chia analog is in `CATWallet.identify()`, where an incoming CR-CAT coin is attributed to an existing local `CRCATWallet` purely by matching `CRCATInfo.limitations_program_hash` (the CAT TAIL hash — the "sub"), while completely ignoring `CRCATInfo.authorized_providers` and `CRCATInfo.proofs_checker` (the "issuer"/policy context that differentiates otherwise-identical-TAIL CR-CATs).

### Finding Description
In `chia/wallet/cat_wallet/cat_wallet.py`, `CATWallet.identify()` handles a newly-seen coin that has been recognized as a CR-CAT (`wallet_type is CRCATWallet`), and searches existing wallet entries for a match: [1](#0-0) 
```
for wallet_info in await wallet_state_manager.get_all_wallet_info_entries(wallet_type=WalletType.CRCAT):
    crcat_info: CRCATInfo = CRCATInfo.from_bytes(bytes.fromhex(wallet_info.data))
    if crcat_info.limitations_program_hash == asset_id:
        return WalletIdentifier(wallet_info.id, WalletType(wallet_info.type))
```
This comparison uses only `limitations_program_hash` (the CAT TAIL hash) to decide that the incoming CR-CAT belongs to an already-existing local CR-CAT wallet. It never checks whether the incoming coin's actual `authorized_providers` list or `proofs_checker` (captured from the coin's own puzzle via `CRCAT.get_next_from_coin_spend`, see `crcat.authorized_providers` used earlier in the same function) matches the `authorized_providers`/`proofs_checker` stored in that wallet's `CRCATInfo`.

Compare this to `CRCATWallet.match_puzzle_info()`, which — for a different code path (offer/puzzle-driver matching) — correctly requires both the TAIL *and* `authorized_providers` *and* `proofs_checker` to match: [2](#0-1) 

The `identify()` path lacks this full comparison, so a CR-CAT with the same TAIL hash but a *different* authorized-provider set (i.e., a different "issuer" of the credential-restriction policy) is folded into the same local wallet identity as an existing, unrelated CR-CAT wallet.

Downstream, `CRCATWallet.coin_record_to_crcat()` reconstructs the `CRCAT` object using the *wallet's* stored `self.info.authorized_providers` / `self.info.proofs_checker`, not the actual policy embedded in that specific coin: [3](#0-2) 
Likewise, spend construction (`_generate_unsigned_spendbundle`, `claim_pending_approval_balance`) selects the VC to authorize the spend using `self.info.authorized_providers` (the wallet's stored provider set) via `vc_wallet.get_vc_with_provider_in_and_proofs`: [4](#0-3) [5](#0-4) 

Because the reconstructed policy no longer matches what was actually curried into the coin's on-chain puzzle at creation time, any subsequent attempt to spend that misattributed coin builds a puzzle reveal that does not hash to the coin's real `puzzle_hash`.

### Impact Explanation
This does not directly enable theft of another party's funds (the puzzle-hash mismatch will cause the constructed spend to fail on-chain validation, since a full/consensus node will reject a `CoinSpend` whose puzzle reveal doesn't hash to the coin's puzzle hash). However, it does cause:
- Silent misattribution of a differently-policied CR-CAT coin to the wrong local wallet record, corrupting the wallet's coin-set/balance bookkeeping (a coin store state divergence from the wallet's own true entitlement).
- A spend-triggered transaction-processing failure/halt for that wallet: once the wallet attempts to include the misattributed coin in a spend bundle (balance selection, `claim_pending_approval_balance`, or offer construction), it will build an invalid spend using the wrong `authorized_providers`/`proofs_checker`, which either fails locally or is rejected by the mempool, and can also entangle honestly-owned coins bundled in the same transaction (e.g., change coins, fee coins) into a failed push.
- If the attacker (any party who can construct a spend bundle producing a CR-CAT with the victim's TAIL hash but a different provider list) sends such a coin to a wallet hinted to the victim, they can force this corrupted state without any privileged access — purely from a submitted spend bundle/wallet-observed coin.

This satisfies the "coin-set divergence between honest nodes/wallet" and "spend-triggered transaction-processing halt" impact classes called out in scope, though it stops short of unauthorized coin movement or theft.

### Likelihood Explanation
Reachable by any wallet user or counterparty who can construct and get accepted a spend bundle creating a CR-CAT coin with a TAIL hash colliding with an existing CR-CAT asset the victim already tracks, but with a different `authorized_providers` set (e.g., by re-deriving a new CR layer over the same TAIL with attacker-chosen providers, or simply if two independent CR-CAT issuances happen to reuse a TAIL). No special privileges, signing keys, or protocol-level trust are required beyond the normal ability to mint/transfer a CAT-like asset with a chosen TAIL/CR configuration and have it hinted to a target wallet's puzzle hash. This makes it a fairly reachable data-integrity bug for any wallet that has previously created a CR-CAT wallet for a given TAIL.

### Recommendation
In `CATWallet.identify()`, when matching against existing `WalletType.CRCAT` wallet entries, require full equality of the CR-CAT identity — TAIL hash **and** `authorized_providers` **and** `proofs_checker` — mirroring the check already implemented in `CRCATWallet.match_puzzle_info()`, instead of matching on `limitations_program_hash` alone. If no wallet matches on all three fields, treat the coin as belonging to a new/different CR-CAT wallet (or as an "unacknowledged" CAT) rather than folding it into an existing, policy-mismatched wallet.

### Proof of Concept
Conceptual walkthrough (based on code inspection; not independently executed against a running node):
1. A victim wallet already owns a CR-CAT with TAIL `T` and `authorized_providers = [P1]`, tracked as `CRCATWallet` with `CRCATInfo(T, ..., [P1], checker1)`.
2. An attacker (or unrelated party) creates and pushes a CAT-issuance/CR-CAT spend bundle for the same TAIL `T` but with `authorized_providers = [P2]` (a different DID/provider), sending an output hinted to the victim's puzzle hash — this is a normal, unprivileged spend-bundle submission.
3. When the victim's wallet syncs this new coin, `CATWallet.identify()` uncurries it, extracts the actual `crcat.authorized_providers = [P2]`, but then matches wallet identity solely via `crcat_info.limitations_program_hash == asset_id` in the loop over existing `WalletType.CRCAT` wallet entries — returning the *existing* wallet (`CRCATInfo` with `[P1]`) rather than creating a distinct wallet or flagging it unrecognized.
4. The coin is stored under the existing CR-CAT wallet. Any later spend attempt via `_generate_unsigned_spendbundle`/`claim_pending_approval_balance` reconstructs the coin's puzzle using `self.info.authorized_providers = [P1]` and fetches a VC authorized for `[P1]`, producing a puzzle reveal that does not match the coin's actual on-chain puzzle hash (which was built with `[P2]`), causing the spend to fail and potentially dragging in other legitimately-owned coins bundled in the same transaction.

    def coin_record_to_crcat(self, coin_record: WalletCoinRecord) -> CRCAT:
        if coin_record.coin_type not in {CoinType.CRCAT, CoinType.CRCAT_PENDING}:  # pragma: no cover
            raise ValueError(f"Attempting to spend a non-CRCAT coin: {coin_record.coin.name().hex()}")
        if coin_record.metadata is None:  # pragma: no cover
            raise ValueError(f"Attempting to spend a CRCAT coin without metadata: {coin_record.coin.name().hex()}")
        try:
            metadata: CRCATMetadata = CRCATWallet.get_metadata_from_record(coin_record)
            crcat: CRCAT = CRCAT(
                coin_record.coin,
                self.info.limitations_program_hash,
                metadata.lineage_proof,
                self.info.authorized_providers,
                self.info.proofs_checker.as_program(),
                (
                    construct_pending_approval_state(
                        metadata.inner_puzzle_hash, uint64(coin_record.coin.amount)
                    ).get_tree_hash()
                    if coin_record.coin_type == CoinType.CRCAT_PENDING
                    else metadata.inner_puzzle_hash
                ),
            )
            return crcat
        except Exception as e:  # pragma: no cover
            raise ValueError(f"Error parsing CRCAT metadata: {e}")

    async def match_puzzle_info(self, puzzle_driver: PuzzleInfo) -> bool:
        if (
            AssetType(puzzle_driver.type()) == AssetType.CAT
            and puzzle_driver["tail"] == self.info.limitations_program_hash
        ):
            inner_puzzle_driver: PuzzleInfo | None = puzzle_driver.also()
            if inner_puzzle_driver is None:
                raise ValueError("Malformed puzzle driver passed to CRCATWallet.match_puzzle_info")  # pragma: no cover
            return (
                AssetType(inner_puzzle_driver.type()) == AssetType.CR
                and [bytes32(provider) for provider in inner_puzzle_driver["authorized_providers"]]
                == self.info.authorized_providers
                and ProofsChecker.from_program(UnknownPuzzle(known_program=inner_puzzle_driver["proofs_checker"]))
                == self.info.proofs_checker
            )
        return False
