### Title
Incomplete "sensitive location" blocklist in `isClonePathSensitive` allows cloning into unprotected credential/config directories - (File: `app/src/lib/git/clone.ts`)

### Summary
The Pendle report's root cause is a safety check (`_isEnoughIMStrict`) that *looks* sufficient but omits terms needed to cover all real-world configurations, so the invariant it is supposed to guarantee can still be violated. The GitHub Desktop analog is `isClonePathSensitive()` in `app/src/lib/git/clone.ts`, a backstop added specifically to stop crafted-URL clone-path-traversal from landing in sensitive locations. It enumerates a fixed, incomplete list of "sensitive" directories and lets everything else through, giving the same false sense of completeness as the flawed margin check.

### Finding Description
`clone()` calls `isClonePathSensitive(path)` before running `git clone`, and blocks only: [1](#0-0) 

The enumerated set is `home` root, `~/.ssh`, `~/.gnupg`, `~/.config`, `~/.config/git`, `~/.gitconfig`, and on Windows `%APPDATA%` / `%APPDATA%\gnupg`. The comment on the function explicitly frames it as "a backstop against path traversal attacks where a crafted URL tricks the UI into deriving a clone path outside the intended base directory," confirming attacker-controlled repository names/URLs are the assumed threat model.

The destination directory name itself comes from `sanitizeCloneName()`, which derives a single path component from the attacker-controlled repo URL/name (last path segment, `.git` suffix stripped, traversal segments rejected): [2](#0-1) 

Because `sanitizeCloneName` only strips traversal but freely allows dotfile-style names (the project's own test confirms `x..\..\..\../.ssh` sanitizes to `.ssh`), an attacker who controls the repository name (via a crafted `owner/name` clone shortcut, a crafted clone URL, or a link the user clicks that pre-fills the Clone dialog) fully controls the final path component that gets joined to whatever base directory the user has selected: [3](#0-2) 

`isClonePathSensitive` only catches the case where that resulting path collides with its five hardcoded entries. It does **not** cover other well-known, equally sensitive per-tool credential/config directories that live directly under the home directory, e.g. `~/.aws`, `~/.docker`, `~/.kube`, `~/.npmrc`'s containing directory, `~/.netrc`'s directory, `~/.git-credentials`'s directory, cloud CLI config folders, etc. Any of these can be produced by an attacker-chosen repo name (e.g. a clone shortcut `evil/. docker`-style name resolving to `.docker`) whenever the user's configured clone base path is the home directory itself — which Desktop allows the user to select via the "Local Path" save dialog: [4](#0-3) 

The UI's `validateEmptyFolder` check that would otherwise stop overwriting existing content is a **separate, UI-only** guard, not enforced inside `clone()` itself: [5](#0-4) [6](#0-5) 

So exactly as in the Pendle finding — where the check needed an additional `max(Hf, Hc)` term to be sufficient — `isClonePathSensitive` needs the full set of security-relevant directories, not just five, to actually guarantee "never write into a sensitive location."

### Impact Explanation
If a target directory such as `~/.docker`, `~/.aws`, or `~/.kube` does not already exist (common for users without those CLIs installed), Desktop will happily create it and populate it with attacker-controlled files from the cloned repository, because the blocklist doesn't recognize it as sensitive. Files placed there are not inert: e.g. a `~/.docker/config.json` with a `credHelpers`/`credsStore` entry pointing to an attacker-named helper binary will cause arbitrary code execution the next time the victim runs `docker login`/`docker pull`; a planted `~/.kube/config` can redirect `kubectl` to an attacker-controlled cluster; a planted `~/.aws/credentials` can result in the victim's AWS CLI using attacker-supplied (or exfiltrating) credentials. This satisfies the "file write outside the repo" / "credential exfiltration" / "code execution" impact classes from a purely repository-content-controlled input.

### Likelihood Explanation
Exploitation requires that the user's configured clone base directory be the home directory (a supported, user-selectable configuration, not the default), and that the attacker can get the victim to clone a maliciously-named repository (via a shortcut like `owner/name`, a crafted clone URL, or a link/deep-link that pre-fills the Clone dialog) whose sanitized name collides with an unprotected but security-relevant folder name. This is a narrower precondition than the original home-root/`~/.ssh` bypass this function was built to fix, but it demonstrates the same underlying flaw: the check is an enumerated blocklist rather than a principled boundary (e.g. "any resolved path outside the user-approved base directory" or an allowlist), so its coverage is inherently incomplete and any directory name not thought of by the original author remains exploitable.

### Recommendation
Replace the enumerated blocklist in `isClonePathSensitive` with a structural guarantee instead of a fixed list, mirroring the Pendle report's fix of replacing an incomplete bound with a mathematically sufficient one:
1. Require that the resolved clone path is a descendant of the user-selected base directory that existed *before* URL-derived name expansion (i.e., verify `resolvedPath.startsWith(chosenBaseDir)` using the pre-sanitized base, not just blocklist a handful of home-relative names).
2. If a "sensitive-directories" blocklist must remain as a defense-in-depth backstop, expand it to a maintained, documented list of all common credential/config directories (`.aws`, `.docker`, `.kube`, `.npm`, `.netrc`, `.git-credentials`'s directory, cloud-vendor config dirs, etc.) rather than only the five currently hardcoded, and enforce the same "empty directory" check inside `clone()` itself (not only in the UI) so it cannot be bypassed by any caller.

### Proof of Concept
1. Configure Desktop's default clone location to the home directory (User Preferences → local clone path, or via the "Choose..." save dialog when initiating a clone).
2. Have the victim clone a repository referenced as `evil/docker` (or a crafted URL such as `https://evil.com/evil/docker.git`) via a link/shortcut.
3. `parseRepositoryIdentifier` extracts `name = "docker"`; `sanitizeCloneName` returns `"docker"`, unmodified — not `.docker`, but demonstrate with a hidden-dir name variant, e.g. a repo named literally `.docker` (`evil/.docker`), which `sanitizeCloneName` preserves as `.docker` (confirmed by the existing test asserting `.ssh`-style names pass through unchanged).
4. `clone()` computes `path = Path.join(homeDir, '.docker')`; `isClonePathSensitive` checks it against `{home, .ssh, .gnupg, .config, .config/git, .gitconfig}` — `.docker` is not in this list, so the check returns `false` and cloning proceeds.
5. Git creates `~/.docker/` populated with the attacker's repository content, including a crafted `config.json` with a malicious `credHelpers` entry, which executes attacker code on the victim's next `docker` invocation. [7](#0-6)

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

  private async validateEmptyFolder(
    path: string | null
  ): Promise<null | Error> {
    if (path === null) {
      return new Error(
        'Unable to read path on disk. Please check the path and try again.'
      )
    }

    try {
      const directoryFiles = await readdir(path)

      if (directoryFiles.length === 0) {
        return null
      } else {
        return new Error(
          'This folder contains files. Git can only clone to empty folders.'
        )
      }
    } catch (error) {
      if (error.code === 'ENOTDIR') {
        // path refers to a file or other file system entry
        return new Error(
          'There is already a file with this name. Git can only clone to a folder.'
        )
      }

      if (error.code === 'ENOENT') {
        // Folder does not exist
        return null
      }

      log.error(
        'CloneRepository: Path validation failed. Error: ' + error.message
      )
      return new Error(
        'Unable to read path on disk. Please check the path and try again.'
      )
    }
  }
