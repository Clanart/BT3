### Title
`post-checkout` hook runs with full trampoline/credential environment because `checkoutBranch`/`checkoutCommit` never populate `interceptHooks` - ([File: app/src/lib/git/checkout.ts])

### Summary
GitHub Desktop's hook-interception system (`app/src/lib/hooks/with-hooks-env.ts`) is designed to run a repo's git hooks through a sandboxed proxy (`createHooksProxy` in `app/src/lib/hooks/hooks-proxy.ts`) that strips sensitive variables such as `GIT_ASKPASS`, `GIT_SSH_COMMAND`, and other credential/exec-path variables before invoking a hook script. This sandboxing is opt-in per Git operation via the `interceptHooks` array passed to `git()`. `pull()`, `push()`, `commit()`, and `merge()` explicitly declare which hooks they intercept, but `checkoutBranch()` / `checkoutCommit()` in `app/src/lib/git/checkout.ts` never set `interceptHooks` at all. As a result, when a cloned/fetched repository contains a `post-checkout` hook, it is executed by real Git with the same environment `core.ts`'s `git()` builds via `withTrampolineEnv` (`app/src/lib/git/core.ts:276-296`), unfiltered by the sanitization applied in `hooks-proxy.ts:166-176`.

### Finding Description
`withHooksEnv()` only substitutes `core.hooksPath` (and thus routes hook execution through the sandboxed proxy) when the caller supplies `opts?.interceptHooks` and at least one matching executable hook is found: [1](#0-0) 

Both `pull()` and `push()` correctly whitelist the hooks that can fire for those operations: [2](#0-1) [3](#0-2) 

But `checkoutBranch()` / `checkoutCommit()` build their `IGitStringExecutionOptions` via `getCheckoutOpts()`, which sets only `env` and `expectedErrors` — no `interceptHooks`: [4](#0-3) [5](#0-4) 

`post-checkout` is a real, well-known Git hook and is present in the app's own `knownHooks` list, showing it is expected to run as part of checkout flows: [6](#0-5) 

Because `interceptHooks` is empty for checkout, `withHooksEnv` short-circuits to `fn(opts?.env)` without ever proxying, so Git invokes `.git/hooks/post-checkout` directly using the environment assembled by `core.ts`'s `git()` — which layers in `withTrampolineEnv` output (containing the trampoline token/credential-helper wiring used for authentication) on top of `opts.env`: [7](#0-6) 

Compare this to the sandboxed path, where `hooks-proxy.ts` deliberately filters the environment down to a safe allowlist and explicitly excludes `GIT_ASKPASS`, `GIT_SSH_COMMAND`, and other exec-path/config variables before a hook subprocess is spawned: [8](#0-7) [9](#0-8) 

The broken invariant: the app's threat model (as expressed by `hooks-proxy.ts`'s exclusion list and the "Adding untrusted repositories may automatically execute files" warning shown in `app/src/ui/missing-repository.tsx` and `app/src/ui/add-repository/add-existing-repository.tsx`) assumes repository-controlled hook scripts must never see the trampoline/credential environment. That invariant is only enforced when `interceptHooks` is populated for the Git subcommand being run. Since `checkout` operations never populate it, an attacker-controlled `post-checkout` hook committed to a cloned/fetched repository executes with the full unfiltered environment, including whatever `GIT_ASKPASS`/trampoline variables `withTrampolineEnv` injects for that operation.

### Impact Explanation
A malicious `post-checkout` hook shipped in a cloned or fetched repository (an attacker fully controls this, no local access needed) can read the process environment it's spawned with and, if it contains `GIT_ASKPASS` pointing at the trampoline binary or the trampoline token, invoke the trampoline itself or exfiltrate the token to talk to Desktop's local credential-serving mechanism, potentially retrieving stored GitHub credentials/tokens for the account performing the checkout. This matches the "credential/token exfiltration" and "unprompted... code execution" impact classes for an attacker who controls a cloned/fetched repository.

### Likelihood Explanation
Likelihood is Medium: `post-checkout` fires automatically on ordinary branch/commit checkout — one of the most common Desktop operations — and requires no special user action beyond checking out a branch/commit from an already-added malicious repository (e.g. after cloning a public repo or opening a PR branch). The existing "unsafe directory" ownership check (`addSafeDirectory`/`getRepositoryType` in `app/src/ui/missing-repository.tsx`, `app/src/ui/add-repository/add-existing-repository.tsx`) only protects against repositories owned by a different local user — it does not gate hook execution for repositories the user has already added/cloned themselves, which is the normal GitHub Desktop workflow.

### Recommendation
Add `interceptHooks: ['post-checkout']` (and any other checkout-triggered hooks, e.g. none currently intercepted) to the `IGitStringExecutionOptions` built in `getCheckoutOpts()` in `app/src/lib/git/checkout.ts`, mirroring the pattern already used in `pull.ts`, `push.ts`, `commit.ts`, and `merge.ts`, so that `post-checkout` is always routed through `withHooksEnv`/`createHooksProxy` and has the trampoline/credential-sensitive environment variables stripped before execution.

### Proof of Concept
1. Attacker publishes a public repository containing `.git/hooks/post-checkout` (executable) that reads `process.env` (e.g. via a shell script dumping env, or attempting to invoke `$GIT_ASKPASS`) and sends it to an attacker server.
2. Victim clones the repository in GitHub Desktop and checks out any branch/commit (`checkoutBranch`/`checkoutCommit` in `app/src/lib/git/checkout.ts`).
3. Because `getCheckoutOpts()` never sets `interceptHooks`, `withHooksEnv` (`app/src/lib/hooks/with-hooks-env.ts:34-36`) returns `fn(opts?.env)` immediately, skipping the sandboxed hooks proxy.
4. Git invokes `post-checkout` directly with the environment built in `core.ts`'s `git()` (`TERM`, `opts.env`, `hooksEnv` (empty), and `env` from `withTrampolineEnv`), none of which has been filtered by the `excludedEnvVars`/`safePrefixes` logic used in `hooks-proxy.ts`.
5. The hook script exfiltrates any credential-relevant environment variables it finds to the attacker. [4](#0-3) [1](#0-0)

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
