### Title
Duplicate withdrawal-UTXO registration lets a single fronted payout be attributed to two vaults - ([File: core/src/database/verifier.rs, core/src/citrea.rs])

### Summary
`collect_withdrawal_utxos` in `core/src/citrea.rs` blindly copies whatever `(txid, vout)` bytes the Citrea Bridge contract stored at each withdrawal index into a per-index row of the `withdrawals` table, with no check that the outpoint is unique across withdrawal indices. Because a withdrawer fully controls the bytes passed to `withdraw()`, the same physical UTXO can be registered under two different withdrawal indices (two different vaults), and `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` in `core/src/verifier.rs` + `core/src/database/verifier.rs` then join the single real Bitcoin spend of that UTXO to *both* rows, letting a single genuine payout be recorded as the fronted payout for two withdrawals/vaults.

### Finding Description
The invariant that should hold is: `withdrawal_utxo_txid‖vout` uniquely identifies at most one row of `withdrawals` (one vault/withdrawal pairing), so that `payout_txid` derived from a Bitcoin spend of that outpoint is attributed to exactly one `idx`.

- `collect_withdrawal_utxos` (`core/src/citrea.rs:458-496`) iterates the contract's `withdrawalUTXOs(idx)` mapping and returns `(idx, OutPoint)` pairs with no uniqueness check across `idx`.
- `update_withdrawal_utxo_from_citrea_withdrawal` (`core/src/database/verifier.rs:108-135`) stores this per-`idx` outpoint into the `withdrawals` table (`idx` is the primary key, but `withdrawal_utxo_txid`/`withdrawal_utxo_vout` have no uniqueness constraint - see `core/src/database/schema.sql:269-281`).
- `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` **on `(txid, vout)`**, not on `idx`. If two rows (`idx=X`, `idx=Y`) share the same `withdrawal_utxo_txid/vout`, a single spend event of that outpoint produces two result rows: `(X, spending_txid)` and `(Y, spending_txid)`.
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) then calls `update_payout_txs_and_payer_operator_xonly_pk` with both `(X, payout_txid, operator_pk, blockhash)` and `(Y, payout_txid, operator_pk, blockhash)`, populating `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` for **both** withdrawal rows from the **one** real payout transaction.
- `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) and `get_payout_info_from_move_txid` (`core/src/database/verifier.rs:253-280`) look up payout info by `move_to_vault_txid` (i.e., by vault), find the falsely-populated row for vault `Y`, see `operator_xonly_pk` matching the operator who actually fronted vault `X`'s withdrawal, and see a blockhash the operator can trivially reconstruct (it's the real block of their own real payout tx). The check therefore returns `false` (not malicious) for a kickoff on vault `Y`, even though that operator never signed or broadcast a payout for vault `Y`'s withdrawer.

Attacker flow: an unprivileged withdrawer calls Citrea's `withdraw()` twice against two different deposits/vaults, both times supplying the **same** self-constructed L1 outpoint (only requiring the attacker to hold a valid signature over one UTXO and burn `bridge_amount` cBTC per call). Two indices `X` and `Y` are created on-chain, each independently collected by `collect_withdrawal_utxos`, both pointing at the identical outpoint. An operator legitimately fronts the payout once (spending that single outpoint, satisfying `withdraw()`'s outpoint-match and RPC-input checks in `core/src/operator.rs:588-596`); the bookkeeping bug then double-attributes that one payout to both vaults, letting the operator additionally submit a kickoff for vault `Y` that `is_kickoff_malicious` will not flag, ultimately allowing reimbursement from vault `Y`'s move-to-vault UTXO without ever having funded a payout for it.

None of the existing guards catch this: `Operator::withdraw`'s outpoint match check (`core/src/operator.rs:594-596`) only verifies against the *one* `idx` being processed, not cross-`idx` uniqueness; `is_kickoff_malicious` trusts DB-stored payout info keyed by `move_to_vault_txid`, which is exactly the value corrupted by the duplicate join; and there is no DB uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in `schema.sql`.

### Impact Explanation
An operator can be reimbursed from a second vault's move-to-vault UTXO for a payout it never separately funded - this is the explicitly listed Critical impact "an operator reimbursed for a payout it never funded." The blast radius scales with the number of withdrawal indices the attacker links to the same outpoint (in principle N indices could all resolve to one real payout, letting an operator drain N vaults with a single real payout). This is repeatable across any pair (or more) of deposits/withdrawals as long as the attacker is willing to pay `bridge_amount` cBTC per extra withdrawal registration.

### Likelihood Explanation
Preconditions are modest: the attacker needs at least two open deposits (vaults) to target and must burn `bridge_amount` cBTC on Citrea for each duplicate withdrawal registration (a real, non-trivial but bounded cost, and possibly recoupable since the attacker directly benefits or can collude with the receiving operator). No verifier, aggregator, or operator key/role is required from the attacker; the divergence is created purely by the attacker's choice of identical outpoint bytes across two `withdraw()` calls, entirely legal inputs to `collect_withdrawal_utxos`. The remaining step (an operator submitting the second kickoff) requires an operator to act, but that operator does not need to be malicious in an unusual way - it only needs to follow the normal kickoff/reimbursement flow using DB state corrupted by the attacker, and this is only possible because the aggregator's bookkeeping does not enforce the uniqueness invariant. This makes it a realistic Critical-severity bug rather than a purely theoretical one; I was not able to fully trace/confirm downstream round-machine acceptance of the “not malicious” kickoff verdict into the final reimbursement-connector spend inside the time available, so the last hop (verifier round-state machine → Reimburse transaction confirmation) should be validated end-to-end with an integration test before treating this as fully proven.

### Recommendation
Enforce uniqueness of the physical withdrawal UTXO across all withdrawal indices before they are considered valid:
- Add a DB uniqueness/partial-unique constraint on `withdrawals(withdrawal_utxo_txid, withdrawal_utxo_vout)` in `core/src/database/schema.sql`, and reject/flag any later `collect_withdrawal_utxos` entry that reuses an outpoint already bound to a different `idx`.
- Change `get_payout_txs_for_withdrawal_utxos`'s join in `core/src/database/verifier.rs` to be scoped so that a given spent outpoint can only satisfy the first (or the one-and-only permitted) withdrawal `idx` it was registered under, e.g., by additionally joining/filtering on a per-outpoint "claimed idx" state, or by having `update_withdrawal_utxo_from_citrea_withdrawal` reject (mark invalid) duplicate outpoints observed for a later `idx`.
- In `is_kickoff_malicious`, additionally verify that the payout transaction's spent input outpoint textually matches the specific `withdrawal_utxo` recorded for the `idx` associated with `move_to_vault_txid` being checked, not merely that some row in `withdrawals` happens to share `payout_txid`.

// core/src/test/withdraw.rs (new test, integration-tests feature, regtest, no mainnet/live Citrea)
#[tokio::test]
async fn duplicate_withdrawal_utxo_registration_double_attributes_payout() {
    // 1. Set up two deposits (vault X, vault Y) via run_multiple_deposits.
    // 2. Construct a single valid withdrawal outpoint + signature (attacker-owned UTXO).
    // 3. Call citrea_client.contract.withdraw(txid, vout) twice, once assigned idx X
    //    and once assigned idx Y (two separate calls with identical (txid, vout) bytes).
    // 4. Mine + sync so verifier's update_citrea_deposit_and_withdrawals runs
    //    collect_withdrawal_utxos and stores both rows.
    // 5. Have one operator front the payout once (operator.withdraw for idx X),
    //    spending the shared outpoint on L1; mine to finality so
    //    update_finalized_payouts/get_payout_txs_for_withdrawal_utxos runs.
    // 6. Assert the invariant violation:
    let info_x = db.get_payout_info_from_move_txid(None, move_txid_x).await.unwrap();
    let info_y = db.get_payout_info_from_move_txid(None, move_txid_y).await.unwrap();
    assert!(info_x.is_some());
    // BUG: info_y should be None (vault Y was never fronted), but it is Some(..)
    // with the same payout_txid/operator_xonly_pk/blockhash as vault X.
    assert_eq!(info_x.unwrap().2, info_y.unwrap().2, "same payout_txid attributed to two vaults");
    // 7. Additionally show is_kickoff_malicious(vault_y_deposit_data, operator_a_kickoff) == false,
    //    i.e. the fronting operator is not flagged malicious for a kickoff on vault Y
    //    despite never funding vault Y's withdrawer.
}
