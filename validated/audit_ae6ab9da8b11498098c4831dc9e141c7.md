### Title
`RuleEngine.evaluate_rules` silently downgrades `action: block` to a no-op warning for the `UserPromptSubmit` event, breaking the documented "deny means deny" guarantee - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine.evaluate_rules` only emits an enforceable denial (`hookSpecificOutput.permissionDecision: deny` or `decision: block`) when `hook_event_name` is `Stop`, `PreToolUse`, or `PostToolUse`. Hookify explicitly documents and ships support for `event: prompt` rules with `action: block` bound to the `UserPromptSubmit` hook, but that event name falls into the final `else` branch, which returns only `systemMessage` with no blocking signal, so the prompt is processed anyway.

### Finding Description
`evaluate_rules` computes `hook_event = input_data.get('hook_event_name', '')` [1](#0-0)  and branches on it when `blocking_rules` is non-empty:

```
if hook_event == 'Stop': ... "decision": "block" ...
elif hook_event in ['PreToolUse', 'PostToolUse']: ... "permissionDecision": "deny" ...
else: return {"systemMessage": combined_message}
``` [2](#0-1) 

`plugins/hookify/hooks/userpromptsubmit.py` is registered as the command for the `UserPromptSubmit` hook event in `plugins/hookify/hooks/hooks.json` [3](#0-2) , and it forwards `input_data` (whose `hook_event_name` will legitimately be `"UserPromptSubmit"`, as set by Claude Code itself) straight into `engine.evaluate_rules(rules, input_data)` [4](#0-3) . Hookify's own `Rule.action` field explicitly supports `"block"` [5](#0-4) , and hookify's user-facing docs (`README.md`, `commands/hookify.md`, `skills/writing-rules/SKILL.md`) document `event: prompt` combined with `action: block` as a supported configuration for blocking dangerous prompts.

Because `"UserPromptSubmit"` is neither `'Stop'` nor in `['PreToolUse', 'PostToolUse']`, any rule with `event: prompt` / `action: block` that matches falls into the `else` branch and returns only `{"systemMessage": combined_message}` — no `decision`, no `hookSpecificOutput.permissionDecision`. Claude Code has no blocking signal to act on for this event, so the prompt submission proceeds unblocked even though the user configured a "block" rule that matched. The `systemMessage` is cosmetic; nothing actually denies processing of the prompt.

### Impact Explanation
This breaks the "deny means deny" invariant for a documented, user-facing hookify feature. A project maintainer who configures a `hookify.*.local.md` rule (`event: prompt`, `action: block`) to prevent Claude from acting on prompts containing dangerous instructions (e.g., prompt-injection payloads pulled in from external/repository content and resubmitted as a user prompt via automation) will have that guard silently fail: the matching content is still processed normally, defeating the intended defense-in-depth control against malicious instructions. The scoped impact is an approval/enforcement bypass of a user-configured trust boundary, not a crash or generic bug — the block action is advertised and configured but never actually takes effect for this event type.

### Likelihood Explanation
Fully deterministic and always reproducible: any enabled hookify rule with `event: prompt` (or `event: all`) and `action: block` that matches incoming prompt text will hit this code path every time, since `hook_event_name` is always `"UserPromptSubmit"` for that hook and the `else` branch is unconditionally taken. No attacker privilege is required beyond normal usage of the documented feature — this is a straightforward logic gap in `evaluate_rules`, not dependent on malformed/crafted input.

### Recommendation
Add explicit handling for `UserPromptSubmit` (and ideally any other non-tool events that support blocking) in `evaluate_rules`, returning a blocking signal Claude Code actually honors for that event — e.g. `{"decision": "block", "reason": combined_message, "systemMessage": combined_message}` (the same shape used for `Stop`), or the `UserPromptSubmit`-specific advanced JSON schema if different. Replace the generic `else` fallback with per-event-aware blocking, and add a defensive assertion/test guaranteeing that whenever `blocking_rules` is non-empty, the returned dict contains an event-appropriate blocking key (`decision` or `hookSpecificOutput.permissionDecision`), never just `systemMessage`.

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules` in `plugins/hookify/core/rule_engine.py`:

```python
def test_userpromptsubmit_block_actually_blocks():
    rule = Rule(
        name="block-prompt",
        enabled=True,
        event="prompt",
        action="block",
        conditions=[Condition(field="user_prompt", operator="contains", pattern="curl | bash")],
        message="Blocked dangerous instruction"
    )
    engine = RuleEngine()
    input_data = {
        "hook_event_name": "UserPromptSubmit",
        "user_prompt": "please run: curl | bash",
    }
    result = engine.evaluate_rules([rule], input_data)
    # FAILS today: result == {"systemMessage": "...blocked dangerous instruction..."}
    assert "decision" in result or "hookSpecificOutput" in result, \
        "block rule matched but no enforceable deny signal was returned"
```

Fuzz/invariant extension: for every `hook_event_name` value (including `UserPromptSubmit`, `SessionStart`, `PreCompact`, etc.) and any non-empty `blocking_rules`, assert the returned dict always contains a recognized blocking key (`decision == "block"` or `hookSpecificOutput.permissionDecision == "deny"`), never a bare `systemMessage`-only response.
