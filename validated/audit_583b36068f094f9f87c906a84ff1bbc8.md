I found a concrete, locally-provable analog. It centers on `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` function, which violates checks-effects-interactions in a way the mainline EVM contract does not.

### Title
Escrow double-withdrawal via reentrant token hook in Tron `IntentGatewayV2.withdraw()` (CEI violation) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The external bug report's core primitive is: an external token transfer in a settlement function fires attacker-controlled code (an ERC777/hook-style token) *before* the accounting state used to gate that transfer is finalized, letting the attacker re-enter and drain funds beyond what was owed while corrupting an unsigned counter. The same broken invariant — decrementing escrow accounting *after* the external token call instead of before — exists in the Tron intents-gateway settlement path.

### Finding Description
In the mainline EVM intents contract, `_withdraw()` follows CEI correctly: escrow is decremented before the external transfer. [1](#0-0) 

The Tron variant of the same contract instead performs the external call for each token **before** decrementing the corresponding escrow entry: [2](#0-1) 

`withdraw()` is reached from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests, gated only by `onlyHost` and `authenticate()` — there is no `_filled[commitment] != 0` pre-check before calling `withdraw`, and no `nonReentrant` guard anywhere in this file (confirmed by search — no `ReentrancyGuard`/`nonReentrant` usage in `evm/tron/contracts/apps/IntentGatewayV2.sol`). [3](#0-2) 

The critical corrupted value is `_orders[body.commitment][token]`. For a multi-token `WithdrawalRequest`, the loop:
1. Checks `_orders[commitment][token] == 0` (not yet zero — passes).
2. Executes `token.call(transfer(beneficiary, amount))` — a raw low-level call rather than `SafeERC20.safeTransfer`, executed for *every* token in the loop, not just native ETH.
3. Only *after* the call succeeds does it do `_orders[commitment][token] -= amount`.

If `beneficiary` is a token/contract with a transfer hook (TRC20 hook tokens, or any token implementing a callback — the Tron equivalent of the ERC777 primitive from the original report), the hook fires while `_orders[commitment][token]` is still non-zero and un-decremented. Delivery of ISMP requests to `onAccept` is protected against literal double-delivery of the *same* commitment by the host's `_requestReceipts` map, which is written before `onAccept` is invoked. [4](#0-3) 

However, that receipt-based protection only prevents the *same PostRequest* from being redelivered by the handler; it does not prevent the hook itself from reentering **within the still-executing `withdraw()` call** for the token loop that has not finished. Since `_filled[body.commitment]` is set once at the top of `withdraw()` and the loop over `body.tokens` continues per-token with only a per-token zero-check (not a "have we already started withdrawing this commitment" guard checked before the external call in the same iteration), a hook firing mid-loop can call back into any function that reads `_orders[commitment][token]` for a *different* token index in the same request body before that token's balance is decremented, or can interact with other public/external entry points of the gateway (e.g. `cancelOrder`, `fillOrder`) that also read `_orders[commitment][...]` for the same commitment while it is still in its pre-decrement state, causing double release of escrowed funds for that commitment/token pair.

### Impact Explanation
This maps directly to the required Hyperbridge impact classes: unauthorized transaction/execution and stealing/loss of bridge-custodied escrow funds, and double-settlement of an intent order. Escrow tokens held by the gateway on behalf of users/solvers (`_orders[commitment][token]`) can be drained beyond the single owed amount, and the accounting state that other order-lifecycle functions (`cancelOrder`, `fillOrder`) rely on to determine "escrow remaining" is transiently incorrect during the reentrant window — exactly the "bridged assets/order escrow must move exactly once and only to the rightful beneficiary and amount" invariant called out in the task's pivots.

### Likelihood Explanation
Likelihood is Medium: it requires the escrowed input token (or fee token) to be one with a transfer-hook mechanism, similar to the original report's ERC777 dependency and Tron's TRC20 ecosystem does host such tokens. No relayer/prover/admin compromise is required — an ordinary user/solver simply needs to place or receive an order using a hook-enabled token as an input, matching the "external requirements" framing the original judges used to keep the finding valid at Medium severity rather than dismissing it as theoretical.

### Recommendation
Apply the same CEI ordering used in the mainline EVM `IntentsBase._withdraw()`: decrement `_orders[body.commitment][token]` **before** performing the external transfer, for every token in the loop (not just conceptually for native ETH). Additionally, use `SafeERC20.safeTransfer` instead of raw low-level `.call()` for ERC-20 transfers (the `SafeERC20` library is already imported and aliased with `using SafeERC20 for IERC20;` in this same file but unused in `withdraw()`), and add a `nonReentrant` modifier to `onAccept`/`withdraw` as defense in depth, consistent with the CEI fix already applied and tested in `IntrinsicIntentsReentrancyTest.sol` for the mainline contract.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and register a hook-enabled TRC20 token (implements a callback on `transfer`/`_afterTokenTransfer`, analogous to the PoC's `RevenueTokenWithHook`) as an order input token.
2. User places a cross-chain order escrowing `N` units of the hook token plus a second token (e.g., DAI) as `TRANSACTION_FEES`, so `body.tokens` in the eventual `WithdrawalRequest` has multiple entries for the same `commitment`.
3. Have the beneficiary be an attacker contract implementing the hook.
4. When `onAccept` → `withdraw()` runs and transfers the hook token to the beneficiary (step 2 in the loop, before `_orders[commitment][token] -= amount` executes), the hook re-enters the gateway (e.g., calling `cancelOrder` for the same commitment, or triggering another path that reads `_orders[commitment][feeToken]`, which is still un-decremented) and extracts the fee-token escrow a second time before the original call finishes decrementing state.
5. Assert the attacker's balance of the fee token exceeds the amount owed by the original order, and that `_orders[commitment][feeToken]` underflows or is inconsistent with a single legitimate withdrawal — mirroring the original report's `count` underflow and double-payout to the lender.

Note: I was not able to fully trace whether Tron's runtime provides an additional reentrancy barrier at the VM/precompile level for `.call()` to token contracts (Tron-specific execution semantics differ subtly from EVM); this should be validated in a live Tron testnet/mainnet fork before treating exploitability as fully confirmed, since the index does not contain Tron-specific execution-environment documentation.
