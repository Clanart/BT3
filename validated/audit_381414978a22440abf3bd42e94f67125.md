App Proxy request signatures have no timestamp/nonce freshness check, permitting indefinite replay of captured requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` accepts any request whose `signature` query parameter matches an HMAC-SHA256 computed over the *other* query parameters (including a `timestamp` parameter), using the app's shared secret. [1](#0-0)  The `timestamp` value is treated as ordinary signed data, not as a freshness/expiry check — there is no logic anywhere in the concern (or elsewhere in the gem) that compares it to the current time or rejects stale requests. [2](#0-1)  This mirrors the reported bug class: a signed authorization (here, a signed HTTP request) that lacks any nonce/expiry-based replay protection, so a captured valid signature can be resubmitted arbitrarily many times to re-trigger the guarded action.

### Finding Description
`AppProxyVerification` is the mixin the gem recommends developers use to protect any custom controller action reachable through an app proxy path (e.g. `AppProxyController#index`, or custom actions like `ReviewsController` shown in the docs). [3](#0-2)  Verification consists solely of recomputing the HMAC over the sorted query parameters (excluding `signature`) and comparing it against the supplied `signature` using a constant-time compare:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)
  signature = query_hash.delete("signature")
  return false if signature.nil?
  ActiveSupport::SecurityUtils.secure_compare(calculated_signature(query_hash), signature)
end
``` [4](#0-3) 

`calculated_signature` simply serializes and HMACs every parameter, including `timestamp`, but the result of that HMAC check says nothing about *when* the request was made — it only proves the parameter set (including whatever timestamp value happens to be in it) hasn't been tampered with. [5](#0-4)  No comparison against `Time.now` or any expiry window exists in this file, and a grep across the whole repository shows no other code path that enforces app-proxy timestamp freshness. As a result, a validly-signed app proxy query string captured once (e.g., via network observation, logs, browser history, a shared/cached URL, or a referrer leak from the storefront) remains fully valid and replayable to the app's backend forever, since the app's shared secret used for signing is static and not tied to a session, order, or one-time nonce.

This is architecturally analogous to the Taiko `TimelockTokenPool.withdraw()` finding: a signature intended to authorize one specific action, verified without any replay-prevention mechanism (nonce, expiry, or single-use marker), thus can be resubmitted to repeatedly trigger the guarded action.

### Impact Explanation
Any controller action that is protected only by `ShopifyApp::AppProxyVerification` and performs a state-changing or resource-consuming operation (which the docs explicitly encourage developers to build, e.g., write actions under an app-proxy namespace) is vulnerable to unlimited replay by anyone who has ever observed one legitimate signed proxy request — including unrelated visitors to the storefront, or anyone with access to browser history/logs/referrers/caches, none of whom need to be an authenticated merchant or need the app secret. Depending on what the guarded action does, this can result in repeated/duplicated writes, resource exhaustion, or business-logic abuse (analogous to "using up more than intended" in the original report) purely through replay of a single captured request, with no time bound on the attack window.

### Likelihood Explanation
Likelihood is moderate: successful exploitation requires the attacker to first obtain one valid, fully-signed app-proxy query string (via network capture, browser history, logs, or a leaked/cached URL), which is a realistic scenario for storefront-facing endpoints. Once obtained, replay is trivial — an anonymous HTTP client can resend the exact query string directly to the app's endpoint (bypassing Shopify's proxy) indefinitely, since neither Shopify nor the gem enforces freshness of the `timestamp` field.

### Recommendation
Add explicit freshness enforcement in `ShopifyApp::AppProxyVerification#verify_proxy_request`/`query_string_valid?`: parse the `timestamp` parameter and reject the request if `Time.now.to_i - timestamp.to_i` exceeds a small tolerance window (e.g., a few minutes), in addition to the existing HMAC check. For state-changing app-proxy actions, additionally recommend/require application-level single-use nonces or idempotency keys, similar to the mitigation applied for the referenced `TimelockTokenPool` bug.

### Proof of Concept
1. A merchant's storefront visitor triggers a legitimate app-proxy request, e.g.:
   `GET /apps/my-app/some_write_action?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1700000000&signature=<valid_hmac>`
2. An attacker captures this full URL (browser history, proxy/log access, shared link, etc.).
3. At any later time — hours, days, or years later — the attacker sends this exact same query string directly to the app's backend (bypassing Shopify's app-proxy front end entirely, since the destination host is just the app's own server).
4. `AppProxyVerification#query_string_valid?` recomputes the HMAC over the same parameters (including the stale `timestamp`) and it matches, so `verify_proxy_request` allows the request through: [6](#0-5) 
5. The guarded action executes again exactly as it did originally, with no distinction between the original and replayed request — demonstrated by the existing test suite itself, which shows the same static query string being validated as `true` repeatedly with no time-based state: [7](#0-6)

# frozen_string_literal: true

module ShopifyApp
  module AppProxyVerification
    extend ActiveSupport::Concern
    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_proxy_request
    end

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```

## Verify HTTP requests sent via an app proxy

See [`ShopifyApp::AppProxyVerification`](/lib/shopify_app/controller_concerns/app_proxy_verification.rb).

The engine provides a mixin for verifying incoming HTTP requests sent via an App Proxy. Any controller that `include`s `ShopifyApp::AppProxyVerification` will verify that each request has a valid `signature` query parameter that is calculated using the other query parameters and the app's shared secret.

### Recommended usage of `ShopifyApp::AppProxyVerification`

The App Proxy Controller Generator automatically adds the mixin to the generated app_proxy_controller.rb
Additional controllers for resources within the App_Proxy namespace, will need to include the mixin like so:

```ruby
# app/controllers/app_proxy/reviews_controller.rb
class ReviewsController < ApplicationController
  include ShopifyApp::AppProxyVerification
  # ...
end
```
