### Title
`dl_verify_proof_internal` returns `success=True` with zero cryptographic verification when a `DLProof`'s `store_proofs.proofs` list is empty - ([File: chia/data_layer/data_layer_util.py])

### Summary
`dl_verify_proof_internal` iterates `dl_proof.store_proofs.proofs` and performs the puzzle-hash/leaf-hash/`ProofOfInclusion.valid()` checks only inside that loop. If an attacker submits a `DLProof` whose `store_proofs.proofs` list is empty, the loop body never executes, no hash or Merkle check is ever performed, and the function returns normally with an empty `verified_keys` list. The caller then reports `VerifyProofResponse(success=True, verified_clvm_hashes=ProofResultInclusions(store_id, []), ...)`, i.e. a "successful" verification result despite zero cryptographic checks having taken place — structurally the same vacuous-pass logic flaw as the Nimiq `BlockInclusionProof::is_block_proven` advisory (empty input list ⇒ trivially "proven" with no crypto verification).

All authenticity checks — puzzle-hash reconstruction/comparison, leaf-hash-matches-key/value, and `ProofOfInclusion.valid()` — live strictly inside the `for` loop over `dl_proof.store_proofs.proofs`. `StoreProofsHashes.proofs` is a plain `list[HashOnlyProof]` field on a `Streamable` dataclass with no minimum-length constraint: [2](#0-1)

Any external caller building a `DLProof` for `dl_verify_proof` — via the wallet RPC endpoint `WalletRpcApi.dl_verify_proof` — can set `proofs = []`: [3](#0-2)

and: [4](#0-3)

The only mandatory check before returning `success=True` is that `coin_id` corresponds to a real DL singleton coin (unrelated to the claimed key/value data). Nothing requires `verified_clvm_hashes.inclusions` to be non-empty, and nothing prevents `success=True` from being returned when zero key/value pairs were actually cryptographically verified. This is functionally identical to the reported class of bug: an empty list that should gate verification instead causes the verification routine to vacuously "pass."

### Impact Explanation
The `verify_proof`/`dl_verify_proof` RPC and CLI command exist specifically so a user (e.g. a Data Layer client, offer counterparty, or marketplace buyer) can independently confirm that specific key/value data is present under a given DataLayer singleton root before trusting/paying for it. If a malicious counterparty crafts a `DLProof` referencing a real, valid DL singleton `coin_id`/`inner_puzzle_hash` but supplies an empty `store_proofs.proofs` list, the verifier receives `success: true` with an empty `verified_clvm_hashes.inclusions` and a `current_root` flag — a response that superficially resembles a "verified, current" result. Any caller/integration that checks `success` (or otherwise fails to strictly validate that `inclusions` contains every expected key/value hash) can be misled into believing claimed data was cryptographically proven when it was not, enabling social-engineering-style data authenticity fraud around DataLayer-backed offers/trades. This matches CWE-345 (Insufficient Verification of Data Authenticity), mirroring the referenced Nimiq advisory's severity class (Medium).

### Likelihood Explanation
Likelihood is moderate: the attacker fully controls the `DLProof` payload passed to `verify_proof`/`dl_verify_proof` and needs only a legitimate `coin_id` (any known/public DL singleton) and matching `inner_puzzle_hash` — both public/discoverable — to make `dl_verify_proof` return `success=True` for zero actual proofs. No signature, key, or privileged access is required. Exploitation depends on a downstream consumer trusting `success` without independently checking that `inclusions` matches all requested keys, which is a plausible integration mistake given the API's naming and shape.

### Recommendation
In `dl_verify_proof_internal` (and/or `dl_verify_proof`), explicitly reject empty `store_proofs.proofs` lists, and/or have `dl_verify_proof` return `success=False` (or raise) whenever `verified_keys` does not cover the full set of keys the caller expected/requested. At minimum, add a guard such as:
```
if len(dl_proof.store_proofs.proofs) == 0:
    raise ProofIntegrityError("Invalid Proof: no key/value proofs supplied")
```
so that an empty proof list can never produce a `success=True` response.

### Proof of Concept
1. Identify any live DataLayer singleton coin: obtain its `coin_id` and current `inner_puzzle_hash`/`puzzle_hash` (both are public chain data, no privilege required).
2. Construct a `DLProof`:
   ```
   DLProof(
       store_proofs=StoreProofsHashes(store_id=<real store id>, proofs=[]),
       coin_id=<real DL singleton coin id>,
       inner_puzzle_hash=<real inner puzzle hash>,
   )
   ```
3. Call the wallet RPC `dl_verify_proof` (or CLI `chia data verify_proof`) with this payload.
4. Observe `dl_verify_proof_internal` returns `[]` without raising (loop body never runs), and the RPC responds with `VerifyProofResponse(success=True, verified_clvm_hashes=ProofResultInclusions(store_id, inclusions=[]), current_root=...)` — a "successful" verification despite zero key/value hashes having been cryptographically checked.

Note: I was not able to inspect the Rust implementation of `ProofOfInclusion.valid()` (bound via `chia_rs`) directly in this index, since it lives outside the Python source tree; the analysis above relies on the observable Python-level control flow in `dl_verify_proof_internal`, which is confirmed to only invoke `proof.valid()` inside the loop over `store_proofs.proofs`.

```python
def dl_verify_proof_internal(dl_proof: DLProof, puzzle_hash: bytes32) -> list[KeyValueHashes]:
    """Verify a proof of inclusion for a DL singleton"""

    verified_keys: list[KeyValueHashes] = []

    for reference_proof in dl_proof.store_proofs.proofs:
        inner_puz_hash = dl_proof.inner_puzzle_hash
        host_fullpuz_program = create_host_fullpuz(
            inner_puz_hash, reference_proof.root(), dl_proof.store_proofs.store_id
        )
        expected_puzzle_hash = host_fullpuz_program.get_tree_hash_precalc(inner_puz_hash)

        if puzzle_hash != expected_puzzle_hash:
            raise ProofIntegrityError(
                "Invalid Proof: incorrect puzzle hash: expected:"
                f"{expected_puzzle_hash.hex()} received: {puzzle_hash.hex()}"
            )

        proof = ProofOfInclusion(
            node_hash=reference_proof.node_hash,
            layers=[
                ProofOfInclusionLayer(
                    other_hash_side=Side(layer.other_hash_side),
                    other_hash=layer.other_hash,
                    combined_hash=layer.combined_hash,
                )
                for layer in reference_proof.layers
            ],
        )

        leaf_hash = internal_hash(left_hash=reference_proof.key_clvm_hash, right_hash=reference_proof.value_clvm_hash)
        if leaf_hash != proof.node_hash:
            raise ProofIntegrityError("Invalid Proof: node hash does not match key and value")

        if not proof.valid():
            raise ProofIntegrityError("Invalid Proof: invalid proof of inclusion found")

        verified_keys.append(
            KeyValueHashes(key_clvm_hash=reference_proof.key_clvm_hash, value_clvm_hash=reference_proof.value_clvm_hash)
        )

    return verified_keys
```

```python
async def dl_verify_proof(
    dlproof: DLProof,
    wallet_node: WalletNode,
    peer: WSChiaConnection,
) -> VerifyProofResponse:
    """Verify a proof of inclusion for a DL singleton"""

    coin_id = dlproof.coin_id
    coin_states = await wallet_node.get_coin_state([coin_id], peer=peer)
    if len(coin_states) == 0:
        raise ProofIntegrityError(f"Invalid Proof: No DL singleton found at coin id: {coin_id.hex()}")

    verified_keys = dl_verify_proof_internal(dlproof, coin_states[0].coin.puzzle_hash)

    response = VerifyProofResponse(
        verified_clvm_hashes=ProofResultInclusions(dlproof.store_proofs.store_id, verified_keys),
        success=True,
        current_root=coin_states[0].spent_height is None,
    )
    return response
```
