### Title
Double-truncating integer division in NFT royalty calculation systematically underpays royalties - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`compute_royalty_amount` in `chia/wallet/nft_wallet/nft_wallet.py` computes the royalty owed to an NFT creator using two sequential truncating integer divisions instead of performing the truncation once at the end. This is the exact bug class described in the external report: `twoThirdsRoot`/`threeHalfsRoot` truncate intermediate results before completing the arithmetic, producing a value biased downward from the mathematically correct result. The Fei fix was to "combine the arithmetic functions and change the order of operations such that truncating steps are performed last." `compute_royalty_amount` does the opposite: it truncates after the first division, then truncates again after the second.

### Finding Description [1](#0-0) 

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

The single line `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` performs two separate truncating (floor) integer divisions:
1. `abs(offered_amount) // royalty_split` truncates first.
2. The truncated quotient is multiplied by `percentage`, then divided by `MAX_ROYALTY_BASIS_POINTS` (10000), truncating a second time.

The mathematically correct (minimal-error) computation is a single combined division performed last, e.g. `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`. Performing the split-division before the percentage multiplication discards fractional remainder information early, which the second truncation compounds. This is structurally identical to the reported `twoThirdsRoot(x) = cubeRoot(x) ** 2` pattern, where truncating the intermediate `cubeRoot` result before squaring loses precision that a combined, single-truncation formula would have preserved.

Concretely: for `offered_amount=5`, `royalty_split=3`, `percentage=9999` (99.99%):
- Current code: `5 // 3 = 1` → `1 * 9999 // 10000 = 0` → royalty = 0.
- Correct order: `5 * 9999 // (3 * 10000) = 49995 // 30000 = 1` → royalty = 1.

The same double-truncation pattern also appears in the sibling helper `NFTWallet.royalty_calculation`: [2](#0-1) 
```
"amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
```

`compute_royalty_amount` feeds directly into offer construction: `make_nft1_offer` calls it to size the `CreateCoin` output paid to the royalty address when an NFT-triggering fungible asset is offered. [3](#0-2) 

### Impact Explanation
Every NFT trade that goes through offer creation with a `royalty_split > 1` (multiple royalty-bearing NFTs in the same offer) and a percentage that does not divide evenly is systematically underpaid relative to the creator-specified royalty percentage. The magnitude is bounded by rounding error, so for any single trade this is small, but it is deterministic and reproducible across every trade meeting the split/percentage conditions, meaning NFT creators receive persistently less royalty than the percentage they configured entitles them to. I was not able to fully verify within this investigation whether an independent CLVM-level check (e.g., inside the ownership/transfer-program puzzle enforcing `trade_price * percentage / 10000`) cross-validates the wallet-computed royalty amount and would reject a mismatched/underpaid spend; my searches for `royalty`/`trade_price` in `.clsp`/`.clvm` puzzle sources did not return results, likely due to index coverage limits on binary/compiled puzzle files, and I could not confirm the on-chain enforcement logic's own arithmetic order. If such enforcement is loose or performs the same style of division, this is a straightforward, wallet-side value leak against royalty recipients baked into every affected offer, with no way for the creator to detect or contest it after the fact (they are not a party to computing the offer terms).

### Likelihood Explanation
This code path executes on every call to `make_nft1_offer`/`compute_royalty_amount` whenever `royalty_split > 1` (an offer bundling multiple royalty-eligible NFTs on the same side) or when `offered_amount * percentage` does not divide evenly by `royalty_split * MAX_ROYALTY_BASIS_POINTS`, which is the common case for arbitrary trade amounts and non-round percentages. No malicious actor is required — a normal wallet user creating or accepting an NFT offer triggers it. `royalty_calculation`, used by the RPC endpoint `nft_calculate_royalties` (called by both CLI and GUI to preview/summarize royalties before confirming an offer), is even simpler to hit since it only requires `len(royalty_assets_dict) > 1`.

### Recommendation
Rewrite `compute_royalty_amount` to perform the multiplication before any truncating division, and to truncate only once at the end, mirroring the Fei fix's guidance ("combining the arithmetic functions and changing the order of operations such that truncating steps are performed last while being mindful of potential overflows"):

```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```//using Python's arbitrary-precision ints there is no overflow risk here, unlike Solidity's fixed-width EVM integers, but the ordering should still be corrected for correctness/fairness.

Apply the same fix to `NFTWallet.royalty_calculation`'s amount computation for consistency between the estimate returned by `nft_calculate_royalties` and the amount actually paid by `compute_royalty_amount`. Additionally, verify (in a Devin session with full repository/CLVM access) whether the on-chain ownership/transfer-program puzzle that ultimately enforces the royalty payment performs its own division in a similarly lossy order, since that is the actual consensus-enforced guarantee to NFT creators, and any mismatch between wallet-computed and puzzle-enforced amounts should be reconciled.

### Proof of Concept
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount

# royalty_split=3, percentage=99.99%, offered_amount=5
result = compute_royalty_amount(offered_amount=-5, royalty_split=3, percentage=9999)
print(result)  # current behavior: 0

# mathematically correct value using combined division:
correct = abs(-5) * 9999 // (3 * 10000)
print(correct)  # 1

assert result != correct  # demonstrates the rounding-order bug reduces the royalty paid
```
