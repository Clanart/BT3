### Title
Schnorr proof verification accepts the identity public key, enabling forged proofs of possession - ([File: crypto/schnorr/src/lib.rs](crypto/schnorr/src/lib.rs))

### Summary

`SchnorrSignature::verify` does not reject the identity point as a public key. For an identity public key, the verification equation degenerates from `sG == R + cA` to `sG == R`, allowing anyone to choose `s`, set `R = sG`, and produce a universally valid signature/proof under that key. Untrusted `EncryptedMessage` values can reach this path because `EncryptedMessage::read` accepts a canonical identity point for `key`, and its proof-of-possession is then checked with that attacker-controlled key. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

The Schnorr verifier constructs the multiexp statement `R + cA - sG == 0` and accepts when the result is the identity. [4](#0-3)  When `A` is the identity point, `cA` is always the identity, so any scalar `s` with `R = sG` satisfies the equation for every challenge `c`. [5](#0-4) 

The generic `Ciphersuite::read_G` validates canonicity but permits the identity point; identity rejection exists only in the separate FROST `Curve::read_G` implementation. [6](#0-5) [7](#0-6)  `EncryptedMessage<C, E>::read` uses the generic `C::read_G`, so an attacker can encode the message key as the identity point. [2](#0-1)  The message PoP is subsequently verified directly against that point. [3](#0-2) 

### Impact Explanation

An unprivileged party can create an encrypted DKG message claiming an identity encryption key and attach a valid-looking Schnorr proof without possessing a corresponding secret key. This bypasses the PoP mechanism intended to bind possession of the message key and can cause downstream validation or blame logic to operate on a proof that does not establish possession. The accepted object is a forged Schnorr proof for a malformed public key. [8](#0-7) [9](#0-8) 

### Likelihood Explanation

The attack requires no secret material, collision, timing advantage, or control over another participant. The attacker only supplies canonical encodings for `key = identity`, `R = sG`, and `s`, where `s` is an arbitrary scalar. The encoded message reaches verification through `EncryptedMessage::read` and `msg.pop.verify`. [2](#0-1) [3](#0-2) 

### Recommendation

Reject the identity point for any group element used as a Schnorr public key or proof-of-possession key. This should occur before `SchnorrSignature::verify`, including inside `EncryptedMessage::read` or immediately before `msg.pop.verify`. The same restriction should be applied consistently to DKG encryption registration keys and decryption proof keys. [2](#0-1) [10](#0-9) [7](#0-6) 

### Proof of Concept

Conceptually, for any ciphersuite `C` and arbitrary challenge `c`:

```rust
use ciphersuite::{Ciphersuite, group::Group};
use schnorr::SchnorrSignature;

fn forged_identity_signature<C: Ciphersuite>(s: C::F, challenge: C::F) -> bool {
    let public_key = C::G::identity();
    let signature = SchnorrSignature::<C> {
        R: C::generator() * s,
        s,
    };

    signature.verify(public_key, challenge)
}
```

Because the public key is the identity, verification evaluates `sG + c*identity - sG`, which always equals the identity. To attack the PedPoP message path, serialize `EncryptedMessage` with `key` set to the canonical identity encoding, `pop.R` set to the canonical encoding of `sG`, `pop.s` set to `s`, and an arbitrary correctly sized encrypted payload; the internally computed challenge cannot prevent the degenerate equation from succeeding.   /// Return the series of pairs whose products sum to zero for a valid signature.
  /// This is intended to be used with a multiexp.
  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }
