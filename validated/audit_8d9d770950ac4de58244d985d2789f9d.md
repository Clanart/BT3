Based on my investigation, the strongest analog I found is in the clone path, where GitHub Desktop explicitly disables a git security control that was added specifically to stop malicious repositories from achieving code execution during `--recursive` clones.

### Title
Cloning explicitly disables Git's clone-time protection against malicious submodules (`GIT_CLONE_PROTECTION_ACTIVE=false`) - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` always sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` before invoking `git clone --recursive`. `GIT_CLONE_PROTECTION_ACTIVE` is the upstream Git safety flag that Git itself sets to `true` by default (as part of the fix for CVE-2024-32002) specifically to prevent maliciously crafted repositories with submodules/symlinks from writing hook files or other executable content into a location that gets executed during (or immediately after) the clone. GitHub Desktop is unconditionally forcing this protection off for every clone, including clones of attacker-controlled/untrusted URLs (e.g. via "Open in Desktop" deep links, `git clone` CLI action, or cloning a repository a user was linked to). [1](#0-0) 

### Finding Description
GitHub upstream's `GIT_CLONE_PROTECTION_ACTIVE` mechanism exists because `git clone --recursive` on a case-insensitive or symlink-supporting filesystem can be tricked (via crafted `.gitmodules`/submodule paths that collide with `.git`) into placing attacker-controlled files inside the clone's own `.git` directory — including hook scripts — which are then executed by Git itself during the same clone operation, without any further user action. Git's fix requires the invoking tool to either not disable the protection, or take on the responsibility of preventing the collision itself. `clone.ts` does neither: it forces `GIT_CLONE_PROTECTION_ACTIVE=false` unconditionally for every clone, and there is no compensating symlink/hooks-path sanitization logic surrounding the `git clone --recursive` invocation in this file. [2](#0-1) 

The attacker primitive matches the "valid impact" criteria exactly: the attacker fully controls the repository being cloned (a git remote/URL the user is enticed to open via "Open in Desktop" link, CLI `--cli-clone`, or manually pasted URL), and no local/physical access, admin rights, or pre-existing malware is required. The corrupted invariant is: *Git's own guarantee that clone-time submodule checkout cannot write into `.git/hooks` (or similar sensitive paths) is turned off by the host application*, so whatever protection the pinned Git version provides against this exact scenario is not in effect for GitHub Desktop users.

Existing guards elsewhere in the codebase do not stop this path:
- `isClonePathSensitive()` only checks the destination directory (e.g. rejects cloning into `~/.ssh`); it does nothing about the internal structure of the repository being cloned. [3](#0-2) 
- `sanitizeCloneName()` and `resolveWithin()` protect against path traversal in destination naming and file-open flows, not against submodule/hook collision during the recursive clone itself. [4](#0-3) [5](#0-4) 
- `interceptHooks`/hook-proxy sandboxing (`withHooksEnv`, `createHooksProxy`) only applies to explicit Desktop-invoked operations like commit/push/pull; `clone()` passes no `interceptHooks` at all, and by disabling `GIT_CLONE_PROTECTION_ACTIVE` it also removes Git's own built-in defense against the underlying primitive that Desktop's hook sandboxing was never designed to cover for the clone step. [6](#0-5) 

### Impact Explanation
If exploitable against the pinned dugite/Git version, cloning a malicious repository (via a link, PR checkout flow, or manual clone) could lead to arbitrary file write into the local `.git` directory and potentially hook execution during the clone itself — i.e., code execution outside of any explicit user consent to run code, satisfying the "code execution" and "silent corruption of repository state" impact categories in scope. This is comparable in nature to the referenced report's core flaw: a required protective/completion mechanism is missing (there, the HyperCore-side crediting logic; here, the clone-time collision protection), causing an unsafe state to persist silently.

### Likelihood Explanation
Likelihood depends on whether the specific Git version bundled with dugite is vulnerable to the underlying case-folding/symlink collision that `GIT_CLONE_PROTECTION_ACTIVE` guards against, and on the target filesystem (case-insensitive filesystems, e.g. default macOS/Windows, are the primary risk surface for the original CVE class). I was not able to verify from local code alone which dugite/git version is bundled, so I cannot confirm the vulnerability is currently reachable — this is a hardening regression at minimum, and a full RCE vector at worst, depending on the underlying Git binary's behavior.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally. Investigate why this override was added (likely to work around a clone failure on some legitimate submodule layout) and instead fix the underlying compatibility issue, or scope the override narrowly with explicit sanitization of submodule paths before disabling the protection. At minimum, verify against the currently bundled Git/dugite version whether disabling this flag reintroduces the CVE-2024-32002 class of vulnerability, and add a regression test cloning a repository with a submodule path crafted to collide with `.git`/`.git/hooks` on a case-insensitive filesystem.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

/**
 * Extracts a safe single-component directory name from a URL-derived repo name.
 *
 * Mirrors the approach of git's `git_url_basename()` in `dir.c`: treat `/`,
 * `\`, and `:` as path separators, take the last non-empty component, strip a
 * trailing `.git` suffix, and reject traversal segments. This ensures the
 * result is always a single path component that cannot escape the parent
 * directory when passed to `Path.join()`.
 *
 * Examples:
 *  - `"Hello-World"` → `"Hello-World"` (unchanged)
 *  - `"desktop.git/../../otherdir"` → `"otherdir"` (last component, traversal segments skipped)
 *  - `".."` → `null` (traversal-only name rejected)
 *
 * See: https://github.com/git/git/blob/master/dir.c (`git_url_basename`)
 */
export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
