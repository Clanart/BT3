## Title
IBC-received value is duplicated when the ERC-20 middleware overrides a successful transfer ack with an error ack after the underlying transfer already mutated bank state — ([File: x/erc20/keeper/ibc_callbacks.go], [File: x/erc20/ibc_middleware.go])

### Summary
This is the same failure-mode as the SteadeFi bug: a step that already performed an irreversible state mutation is followed by a second step that can fail, and the failure of the second step does not undo the first step's effects — it instead produces a downstream action (re-borrowing in SteadeFi; a counterparty refund here) that assumes the first step never happened. In Cosmos EVM's `x/erc20` IBC middleware, the underlying ICS-20 transfer callback (`im.Module.OnRecvPacket`) runs first and unescrows/credits the bank coin to the receiver. Only afterward does the erc20 keeper attempt to convert that coin into its ERC-20 representation. If this conversion step fails, `x/erc20/keeper/ibc_callbacks.go`'s `OnRecvPacket` returns an **error acknowledgement**, even though the bank-side credit from the first step was already committed and is not rolled back.

### Finding Description
`x/erc20/ibc_middleware.go` composes the callback as: [1](#0-0) 

`im.Module.OnRecvPacket` (the standard ICS-20 transfer app) runs to completion first and mutates bank state (un-escrows coins to the recipient, or mints vouchers). Only if that succeeds does the code call `im.keeper.OnRecvPacket`, the ERC-20 keeper hook, whose "native ERC20 token" branch performs an additional conversion that can independently fail and return a brand-new error acknowledgement: [2](#0-1) 

Because `MintingEnabled`/`ConvertCoinNativeERC20` can fail for reasons unrelated to the already-completed bank transfer (e.g. `BankKeeper.IsSendEnabledCoin` returning false, a self-destructed/invalid ERC-20 contract, etc.), the resulting acknowledgement written back to the channel is an *error* ack — while the receiving chain has already committed the bank-side credit performed by the transfer app in the first call. IBC core's `RecvPacket` handling does not wrap the whole middleware stack's execution in a cache context that gets discarded on error acks; state mutations performed by an app/middleware during `OnRecvPacket` are committed regardless of the acknowledgement's success/failure (the ack only signals the *counterparty's* subsequent behavior, e.g. whether to refund the sender). Consequently, when a subsequent counterparty refund is triggered by that error ack, the funds effectively exist twice: once as the (unconverted) bank coin credited to the recipient on this chain, and once refunded back to the original sender on the counterparty chain.

This exact behavior is corroborated by an existing test's own comment, which describes precisely this "already unescrowed but ack failed" state: [3](#0-2) 

### Impact Explanation
When the ERC-20 conversion step fails after the underlying ICS-20 transfer has already credited the receiver, the acknowledgement written for the packet is an error ack. Per ICS-20 semantics, an error ack causes the sending chain to refund the original sender (unescrow/re-mint on the source chain) once `OnAcknowledgementPacket`/`OnTimeoutPacket` processes it. Since the destination chain never reverses the bank-side credit it already made (the recipient keeps the plain bank coin, which is fully spendable and can later be manually converted via `ConvertCoinToERC20`), the same unit of value now exists on both chains simultaneously: as a live bank balance on the receiving chain and as a refunded balance on the sending chain. This is an unauthorized duplication of spendable user value across an IBC escrow/token-pair-backed balance, matching the Critical "duplication of spendable user value across native balances ... IBC escrows" impact category.

### Likelihood Explanation
The trigger conditions are attacker-reachable without any privileged role: a user (or the recipient) simply needs the ERC-20-conversion step to fail while a legitimate, otherwise-valid ICS-20 packet is being received — e.g. by having `BankKeeper.SendEnabled` disabled for the denom (a param anyone can be affected by, and which is demonstrated directly in the codebase's own test), by causing the paired ERC-20 contract to revert/self-destruct, or by hitting `MintingEnabled` restrictions. No relayer collusion, validator privilege, or malicious node is required — the condition can arise from ordinary parameter states or a normal token-pair contract failure while packets are in flight.

### Recommendation
Ensure atomicity across the transfer + conversion sequence: wrap the entire `OnRecvPacket` call chain (`im.Module.OnRecvPacket` followed by `im.keeper.OnRecvPacket`) in a single `ctx.CacheContext()`/branch, and only call `writeFn()` (commit) if the final acknowledgement returned by `im.keeper.OnRecvPacket` is a success ack. If the erc20 conversion step fails, the branch should be discarded so that the underlying bank-side transfer never gets committed, matching the semantics implied by the returned error acknowledgement. Alternatively, refactor `x/erc20/keeper/ibc_callbacks.go`'s `OnRecvPacket` so that on conversion failure it returns the original success ack (leaving the bank coin with the recipient, as documented for the acknowledgement/timeout paths) rather than overriding it with an error ack that will trigger a counterparty-side refund of the same value.

### Proof of Concept
The existing integration test already exercises and documents this exact scenario without asserting non-duplication: [4](#0-3) 
1. Set up a native ERC-20 token pair and send it out via IBC so it is escrowed on the source (EVM) chain.
2. Set `BankKeeper.SetSendEnabled(evmCtx, nativeErc20.Denom, false)` so that `MintingEnabled` in `x/erc20/keeper/ibc_callbacks.go` fails.
3. Relay the return packet; `transferStack.OnRecvPacket` returns an error ack (`errAck.Success()` is `false`), while — per the test's own comment — the bank tokens are **not** sent back to escrow, i.e. the underlying transfer credit already occurred and was not reverted.
4. Relaying this error ack back to the counterparty chain (via `OnAcknowledgementPacket`/`OnTimeoutPacket`, exercised elsewhere in `evmd/tests/ibc/ibc_middleware_test.go`) would refund the original sender there, while the destination chain's recipient still holds the credited bank coin — producing two spendable claims to the same escrowed value.

Note: full confirmation that the counterparty-refund step actually completes end-to-end (as opposed to being caught by some other unexamined safeguard) was not traced across the complete round-trip within the available search budget; the destination-side double-credit and the misleading error-ack-after-commit pattern are directly confirmed in code and tests, but the full cross-chain double-spend chain should be validated with a live two-chain IBC integration test (`forge`/Go equivalent) before remediation.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
