### Title
Silent, unconfirmed rewrite of the `origin` remote URL from an attacker-controlled GitHub/GHE API response - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes a repository's GitHub metadata (on repository selection, on adding a repository, or after an account change), it fetches the repository object from the configured API endpoint and, if certain heuristic conditions are met, silently overwrites the local `origin` remote URL with `apiRepo.clone_url` — with no user confirmation dialog.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches `apiRepo` from `api.fetchRepository(owner, name)` and immediately calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [2](#0-1) 

`updateRemoteUrl` performs the write unconditionally, without any confirmation dialog, based only on: (1) protocol equality between old and new URL, (2) the currently-stored remote matching the previously cached `gitHubRepository.cloneURL`, and (3) the new URL differing from the current remote: [3](#0-2) 

The actual mutation happens via `gitStore.setRemoteURL` → `setRemoteURL` in `app/src/lib/git/remote.ts`, which runs `git remote set-url` directly against the API-provided string: [4](#0-3) 

The equality check `urlMatchesRemote` only verifies that hostname/owner/name parsed out of the URL match — it does not validate the literal string written to the remote, and it is evaluated against data returned by whichever API endpoint the account is configured against (GitHub.com or a user-specified GitHub Enterprise host): [5](#0-4) 

This is triggered from `_selectRepository`, `_addRepositories`, and `refreshSelectedRepositoryAfterAccountChange`, i.e. routine background/foreground flows a user cannot opt out of, and none of these paths show any popup/dialog before calling `updateRemoteUrl` — contrast this with `UpstreamAlreadyExists`, which does show a confirmation dialog before changing the *upstream* remote: [6](#0-5) 
No equivalent confirmation exists for the `origin` remote update path.

Because a Desktop Enterprise user configures an arbitrary API endpoint (`api.fromAccount(account)` targets whatever endpoint the Account was created against — including a GitHub Enterprise server the user added), and because `fetchRepository` responses (or a MITM/compromised proxy in front of that endpoint) are trusted as-is, an attacker who controls that API response (a compromised/malicious GHE instance, or a network position able to tamper with the API/TLS traffic to a self-hosted GHE) can set `clone_url` to an attacker-controlled repository URL that still parses to the same owner/name/hostname tuple (or otherwise satisfies `urlMatchesRemote`) but differs in the substring actually written (e.g., embedded userinfo, differing path segments, or a URL matching by regex but pointing to a different backend when git actually resolves it). Desktop will then silently rewrite `origin` for the user without any prompt.

### Impact Explanation
Silent corruption of the user's `origin` remote lets an attacker redirect all future `git fetch`/`git pull`/`git push` operations to attacker-controlled infrastructure without the user's knowledge. Depending on the URL scheme:
- HTTPS remotes with embedded credentials/userinfo could leak the user's Git credential prompts or PATs to the attacker host.
- Subsequent pushes go to (and are silently accepted by) an attacker-controlled remote, and subsequent fetches/pulls can serve attacker-controlled tampered commit history, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires the attacker to control (or MITM) the GitHub Enterprise API endpoint the victim's account is configured against, or otherwise return a manipulated `clone_url` from a `fetchRepository` response. This is realistic for a compromised/malicious GHE deployment, a proxy in the corporate network path, or an SSRF/host-header style redirect on the GHE side, matching the report's allowed threat model ("git remote/proxy response" attacker control). The heuristics (`protocolsMatch`, `remoteUrlUnchanged`) narrow — but don't eliminate — the attack surface; the code comment itself acknowledges uncertainty about when the "early exit conditions" are met, indicating the guard was not designed with an adversarial API response in mind.

### Recommendation
Require explicit user confirmation before silently rewriting the `origin` remote URL based on API data, mirroring the existing `UpstreamAlreadyExists` dialog pattern used for the `upstream` remote. Additionally, validate the full literal URL (not just hostname/owner/name) before writing it via `setRemoteURL`, and consider not auto-updating `origin` at all for GitHub Enterprise accounts without prompting.

### Proof of Concept
1. Victim adds a GitHub Enterprise account pointing to `https://ghe.victim-corp.com` and clones/adds a repository whose `origin` remote is `https://ghe.victim-corp.com/org/repo.git`.
2. Attacker compromises (or MITMs, or controls via SSRF) the GHE server / API path such that a subsequent `GET /repos/org/repo` response returns a `clone_url` that still matches the `owner`/`name` tuple checked by `urlMatchesRemote` (e.g., differing only in scheme-adjacent details not covered by the hostname/owner/name check, or a compromised DNS/host resolving `ghe.victim-corp.com` to attacker infrastructure at the network layer while string comparison still "matches").
3. Victim reopens Desktop or switches repositories, triggering `_selectRepository` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`. [2](#0-1) 
4. `origin` is silently rewritten via `git remote set-url` with no dialog shown to the user. [7](#0-6) 
5. All future fetch/push operations for that repository now target attacker-controlled infrastructure.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
