### Title
Referral reward percentages (`basic` tier + boost) can sum above 100%, causing over-allocation of MGP rewards beyond the harvested amount - ([File: rewards/ReferralStorage.sol])

### Summary
The `trigger()` function in `ReferralStorage.sol` combines a tier-based `basic` reward percentage with a dynamic `boostesd` percentage without ever checking that their sum stays within `DENOMINATOR` (100%). When the combined percentage exceeds 100%, the referer and referee reward allocations minted from a single referee-claim event exceed the `_amount` passed in, over-crediting internal `rewardAmount` balances that are later paid out from the shared MGP pool.

### Finding Description
`trigger()` computes: [1](#0-0) 

`basic` comes from `tiers[tierId].rewardPercentage`, which is validated only against `DENOMINATOR` in isolation via `setTier()`: [2](#0-1) 

`boostesd` is computed independently and additively via `_calBoosted()`: [3](#0-2) 

Nowhere is `basic + boostesd` checked against `DENOMINATOR`. Since `refererPercentage + refereePercentage` always equals `basic + boostesd` (the `sharePercent` split just partitions this combined value), whenever `basic + boostesd > DENOMINATOR`, the sum `refererAmount + refereeAmount` computed from `_amount` exceeds `_amount` itself: [4](#0-3) 

This mirrors the reported bug class: independently-bounded percentage components (here `basic` capped at 100% and `boostesd` capped separately by `BoostPoint`) are summed without an aggregate cap, so their combination can exceed 100% of the base amount, over-allocating funds relative to what was actually contributed.

### Impact Explanation
`trigger()` is invoked by `MasterMagpie` as part of an ordinary referee's reward-claim flow (an unprivileged wallet action), not through any admin call. Once `basic + boostesd` exceeds `DENOMINATOR` for a referrer with sufficiently high tier and vlMGP-derived boost factor, every subsequent referee claim under that referrer over-credits `refererInfo.rewardAmount` and `refereeInfo.rewardAmount` beyond the actual harvested `_amount`. Because these balances are paid out later via `claimReward()` from the shared MGP token balance held by `ReferralStorage`, this creates unbacked claims: referral reward balances can collectively exceed the MGP the contract actually holds for that purpose, resulting in insolvency for the referral pool and later failed/impossible payouts (permanent freezing of legitimately earned unclaimed referral yield for other users) once the shortfall is exhausted by earlier claimants.

### Likelihood Explanation
Reaching `basic + boostesd > DENOMINATOR` requires: (a) a tier with a `rewardPercentage` set reasonably close to 100% by governance (a normal, in-bounds configuration, not malicious), and (b) a referrer with a large boost factor relative to `totalBoostFactor` (achievable simply by locking a large amount of vlMGP, which is available to any unprivileged wallet). No admin misbehavior or out-of-spec parameter is required — normal, valid tier settings combined with normal vlMGP locking by an ordinary user can trigger the overflow condition through the routine referral-claim path.

### Recommendation
Cap the combined percentage before splitting: `uint256 combined = basic + boostesd; if (combined > DENOMINATOR) combined = DENOMINATOR;` and derive `refererPercentage`/`refereePercentage` from `combined`, ensuring `refererAmount + refereeAmount <= _amount` for every `trigger()` call.

### Proof of Concept
1. Governance sets tier 1 `rewardPercentage` to `9000` (90%) via `setTier()` — a normal, in-spec configuration.
2. An unprivileged user (the referrer) registers a code and locks a very large amount of vlMGP relative to `totalBoostFactor`, so `_calBoosted()` returns e.g. `2000` (20%), making `basic + boostesd = 11000` (110%).
3. A referee (any ordinary wallet) using this referrer's code claims rewards through `MasterMagpie`, which calls `trigger(_referee, _amount)`.
4. `refererPercentage + refereePercentage` computed from `basic + boostesd` (110%) causes `refererAmount + refereeAmount > _amount`, crediting more MGP than was actually harvested into `refererInfo.rewardAmount` and `refereeInfo.rewardAmount`.
5. Repeated over multiple claims, the sum of all outstanding `rewardAmount` balances across referrers/referees can exceed the MGP token balance actually held by `ReferralStorage`, causing later `claimReward()` calls from other legitimate referral participants to revert due to insufficient contract balance.
