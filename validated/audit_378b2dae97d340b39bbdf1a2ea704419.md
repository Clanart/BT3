**Reasoning:**

The splitting logic in question is: [1](#0-0) 

Git's `%D` format pretty-prints ref names separated by the literal string `", "` (comma + space), and the code explicitly acknowledges this and switched from a regex approach (which clipped tags containing commas) to a `split(', ')` approach specifically to handle tag names that contain plain commas (e.g. `some-other-tag,with-a-comma`) without breaking them, as documented in the surrounding comment.

The premise of the question — that an attacker can create a tag whose name contains a literal `", "` (comma immediately followed by a space) — is not achievable with standard Git tooling. Git enforces ref-name validity rules (via `git check-ref-format`) that forbid ASCII space characters anywhere in a ref name (along with control characters, `~`, `^`, `:`, `?`, `*`, `[`, `\`, etc.). Since `git tag <name>` internally validates the name against these rules (as does any push/fetch of refs, since the transport also carries fully-qualified ref names subject to the same constraints), an attacker cannot get Git itself to create or advertise a tag containing a space character, and thus cannot embed `", "` inside a tag name. `createTag` in the codebase just passes the name straight to `git tag -a`, so it inherits Git's own name validation rather than doing anything more permissive: [2](#0-1) 

Because the malicious tag name required for the described misparse (containing a literal comma-space substring) cannot exist as a valid Git ref in the first place, the `commit.refs.toString().split(', ')` logic cannot be driven into the described corruption by attacker-controlled repository content. Tags containing plain commas (without a following space) are correctly preserved by this code, which is exactly the case the comment says was fixed. Since the ref-naming constraint is enforced by Git itself before such a tag could ever reach the log output that Desktop parses, this is not an exploitable path.
