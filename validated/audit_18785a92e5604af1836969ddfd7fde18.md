### Title
Prefix-based `startsWith` containment check in `_resolveWithin` allows sibling-directory escape - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` verifies that a resolved path stays inside a root directory by doing `realResolved.startsWith(realRoot)` without ever confirming that `realRoot` is followed by a path separator (or is an exact match) in `realResolved`. Any directory that merely shares `realRoot` as a literal string prefix — such as a sibling directory named `<root>_malicious` — passes the check even though it is not nested under `realRoot` at all.

### Finding Description
The containment logic is: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character-prefix comparison with no boundary check. Given `realRoot = '/tmp/project'` and a caller-supplied relative segment `'../project_malicious/secret'`:

- `resolve('/tmp/project', '../project_malicious/secret')` → `/tmp/project_malicious/secret`
- `'/tmp/project_malicious/secret'.startsWith('/tmp/project')` → `true`, because the string `/tmp/project` is a literal prefix of `/tmp/project_malicious/secret`, even though `/tmp/project_malicious` is a completely different, sibling directory, not a subdirectory of `/tmp/project`.

The function therefore returns the resolved (attacker-influenced) path instead of `null`, incorrectly treating a sibling directory as "within" the root. The existing unit tests for `resolveWithin` in [2](#0-1)  only cover `..`-traversal-then-back-in and symlink escapes; none of them exercise the "shares a name prefix but is a sibling" case, so this gap is not currently caught by tests.

### Impact Explanation
`resolveWithin` is documented and used as a path-traversal / symlink-escape guard, e.g. in `buildConflictContext`, which uses it to sandbox reads of conflicted-file paths (potentially derived from merge/rebase state) to the repository's working directory before reading file content into an LLM prompt: [3](#0-2) . If an attacker can arrange (via crafted repository state, e.g. a submodule/worktree layout, or unusual path segments producing a resolved path adjacent to the working directory) for the resolved path to land in a directory whose name extends the root's name without a separator, this check would fail to reject it, allowing content from outside the intended sandboxed directory to be treated as trusted repository content.

However, I could not confirm a concrete, attacker-reachable code path where `pathSegments` passed into `resolveWithin`/`buildConflictContext` can actually be steered to produce a resolved path landing in such a "prefix sibling" directory that also happens to exist on disk with attacker content, as opposed to a `..`-style traversal (which is already blocked correctly, per the existing tests) or a symlink-based escape (also already blocked). The realistic exploitation requires an existing sibling directory (e.g. `<repoPath>_malicious`) to already exist alongside the repository, which is a precondition outside of purely repository-content control — it depends on the local filesystem layout around the clone destination, not solely on attacker-controlled repo/config content.

### Likelihood Explanation
Low-to-moderate. The bug is real and demonstrable in isolation (`resolveWithin('/tmp/project', '../project_malicious/secret')` returns a non-null path when the target should be rejected), but weaponizing it requires: (1) a caller passing a relative segment that resolves outside the intended root via this specific prefix-collision pattern, and (2) a pre-existing sibling directory matching the crafted name to actually exist on the victim's filesystem. Based on the reachable call sites found (`copilot-conflict-context.ts`), the `file.path` values passed are conflicted-file paths reported by git itself for files within the working tree, which are unlikely to contain `..`-segments that git would report as legitimate conflict paths — reducing practical reachability, though this could not be fully ruled out without deeper tracing of all callers (`dispatcher.ts`, `app-store.ts` also import `resolveWithin` but their exact call sites were not confirmed in this review due to tool/search limitations).

### Recommendation
Change the containment check to require a path-separator boundary or exact equality, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator from the `options` argument, i.e. `join('', '')`-derived separator or `Path.sep`/`Path.posix.sep`/`Path.win32.sep` depending on which `options` variant is active). Add a regression test asserting that `resolveWithin('/tmp/project', '../project_malicious/secret')` (or an equivalent same-parent sibling-name-prefix case) returns `null`.

### Proof of Concept
```ts

it('fails for sibling directories that share a name prefix', async () => {
  const tempDir = await mkdtemp(join(tmpdir(), 'path-test'))
  const root = join(tempDir, 'project')
  const sibling = join(tempDir, 'project_malicious')
  await mkdir(root)
  await mkdir(sibling)
  await writeFile(join(sibling, 'secret'), 'leaked')

  // Should be null: sibling is NOT inside root.
  const result = await resolveWithin(root, join('..', 'project_malicious', 'secret'))
  assert.equal(result, null) // currently fails: returns the sibling's resolved path
})
```
This demonstrates that `realResolved.startsWith(realRoot)` incorrectly returns a truthy containment result for `/tmp/.../project_malicious/secret` against root `/tmp/.../project`, corrupting the boolean containment guarantee documented for `resolveWithin`. [4](#0-3)
