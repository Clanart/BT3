### Title
Webhook Signature Verification Does Not Bind the `X-Shopify-Shop-Domain` Header, Enabling Cross-Shop Webhook Forgery/Replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only that the HMAC of the raw request body matches a value computed with the app's shared client secret [1](#0-0)  using `ShopifyApp::PayloadVerification#hmac_valid?` [2](#0-1) . The `X-Shopify-Shop-Domain` header, which is used downstream to attribute the webhook to a specific merchant, is read separately via `shop_domain` and is **not** included in the HMAC-signed data [3](#0-2) . This is structurally the same class of bug as the reported Beanstalk issue: the signature does not bind a critical contextual value (there: `chainId`; here: the shop/tenant identity), so a signed payload legitimately issued for one context can be replayed and accepted in a different context.

### Finding Description
The webhook signature is computed as `HMAC-SHA256(secret, raw_body)` and compared against the `X-Shopify-Hmac-Sha256` header [4](#0-3) . The app's client secret is shared across **all** merchants who install the app — it is not per-shop. Any merchant who has legitimately installed the app can trigger events (e.g. `orders/create`, `products/update`) on their own store and thereby obtain a body + valid HMAC pair signed with that shared secret.

Because the shop-attribution header (`X-Shopify-Shop-Domain`) is not part of the signed material, an attacker who controls their own shop installation can:
1. Trigger a legitimate webhook on their own store to capture a `(raw_body, valid HMAC)` pair.
2. POST that exact body + HMAC to the app's public webhook endpoint (`ShopifyApp::WebhooksController#receive` [5](#0-4) ), but with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain.
3. `verify_request` passes because it only checks the body HMAC, never the shop header [1](#0-0) .
4. The forged request is then dispatched to `ShopifyAPI::Webhooks::Registry.process` with the attacker-controlled shop domain, and the app's registered job is queued with `shop_domain` taken from that spoofed header, exactly as shown in the generator template and controller (`shop_domain: webhook_request.shop`) [6](#0-5) .

This endpoint is unauthenticated/public by design (it must be reachable by Shopify), so nothing besides the body HMAC prevents an attacker from supplying an arbitrary shop-domain header of their choosing.

### Impact Explanation
Depending on what webhook jobs do with `shop_domain` (e.g. updating billing state, redacting/creating records, toggling install status, syncing inventory), an attacker can inject data attributed to a shop they do not own/operate, corrupting that shop's data or triggering privileged side effects (e.g. `shop/redact`, `app/uninstalled` handling) without ever compromising the victim shop. This is a cross-shop data/action injection analogous to the cross-chain replay in the report: the signature is valid, but the context it was issued for differs from the context it is applied to.

### Likelihood Explanation
Any developer/merchant that can install the app on a shop they control can capture a valid signed webhook body from that shop (attacker-controlled precondition, achievable by any anonymous merchant who installs a public app). No secret leakage or privileged access is required beyond normal app installation, which is the standard "unrelated-merchant" reachable path.

### Recommendation
Bind the tenant context into the verified material, e.g.:
- Include the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Webhook-Id`) header in the HMAC computation, or
- Cross-check that the shop resolved from the header actually has a stored session/install record before processing, and reject webhooks for shops with no active session, or
- Rely on Shopify's per-topic delivery metadata (`webhook_id`) plus idempotency/dedup keyed by shop to prevent cross-shop replay of a captured payload.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger an event (e.g., update a product) to receive a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` valid for `HMAC(secret, B)`.
3. Replay: `POST /webhooks/products_update` with body `B`, header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `verify_request` in `ShopifyApp::WebhookVerification` [1](#0-0)  accepts the request because only `hmac_valid?(request.raw_post)` is checked; the job is queued with the spoofed `victim.myshopify.com` shop domain.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
