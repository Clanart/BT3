In `ArbWomUp.sol` (and identically in `ArbWomUp2.sol`), the unprivileged, externally-callable `incentiveDeposit` function performs an unchecked raw `IERC20.transfer` call (bypassing `SafeERC20`) to pay out the USDT/BUSD incentive reward, while unconditionally updating `claimedReward[msg.sender]` beforehand — mirroring exactly the `rescueERC20` false-positive bug class (unsafe ERC20 call whose failure is not detected, causing state to be updated as if the transfer succeeded).

### Title
Unchecked raw `IERC20.transfer` in `incentiveDeposit` permanently forfeits user incentive rewards on non-reverting ERC20 tokens - (File: wombat/ArbWomUp.sol, wombat/ArbWomUp2.sol)

### Summary
`ArbWomUp.incentiveDeposit()` and `ArbWomUp2.incentiveDeposit()` pay out the deposit incentive using a bare `IERC20(usdt).transfer(...)` / `IERC20(busd).transfer(...)` call whose boolean return value is never checked, instead of the `safeTransfer` wrapper (`SafeERC20`) that is used everywhere else in the same contracts. If the configured reward token is a non-standard ERC20 that returns `false` on failure rather than reverting (a documented behavior class, as cited in the referenced report for tokens like STASIS EURO), the reward transfer can silently fail while the accounting state (`claimedReward[msg.sender]`, `userWOMDeposited`, `totalAccumulated`) is already permanently updated as if the payout succeeded. ### Finding Description
Both contracts import and `use SafeERC20 for IERC20`, and consistently use `safeTransferFrom`/`safeTransfer` for the WOM deposit path [3](#0-2) . However the reward payout in `incentiveDeposit` deliberately (or mistakenly) uses the raw, unchecked `.transfer()`:
- `ArbWomUp.sol`: `IERC20(usdt).transfer(msg.sender, rewardToSend);` [4](#0-3) 
- `ArbWomUp2.sol`: `IERC20(busd).transfer(msg.sender, rewardToSend);` in the non-bull-mode branch [5](#0-4) 

In both functions, `claimedReward[msg.sender] += rewardToSend` is executed unconditionally before/alongside the unsafe transfer [6](#0-5) . Since `getRewardAmount()` computes future entitlement as `rewardAmount/DENOMINATOR - claimedReward[_account]` [7](#0-6) , once `claimedReward` is incremented the user's remaining claimable amount is permanently reduced regardless of whether tokens were actually received. If the reward token (`usdt`/`busd`, set by the admin at deployment/setup time and out of the caller's control) returns `false` on transfer failure instead of reverting — e.g., due to the token being paused/frozen for that recipient, or having insufficient allowance-independent internal restrictions — the call does not revert, `emit USDTRewarded`/`BUSDRewarded` still fires, and the transaction completes successfully with the user's on-chain accounting marked as "paid" while no tokens actually moved.

### Impact Explanation
The affected user permanently loses the incentive reward they were entitled to: `claimedReward` cannot be decremented (no such function exists), so the shortfall is unrecoverable and the user cannot re-claim it on a subsequent `incentiveDeposit` call, since `getRewardAmount` will treat it as already paid. This is a permanent freezing/loss of the user's earned yield, reachable purely from ordinary transaction flow (no privileged role needed to trigger — only requires the pre-configured reward token to exhibit non-reverting failure semantics for some recipients).

### Likelihood Explanation
Likelihood depends on the specific ERC20 token deployed as `usdt`/`busd` at the time `incentiveDeposit` is used; several real-world stablecoins (e.g., the STASIS EURO example cited in the reference report) implement `transfer` to return `false` rather than revert when the sender/recipient is blacklisted or frozen. Since these `WomUp`-family contracts are designed to distribute incentive rewards to arbitrary depositors, a blacklisted or restricted recipient calling `incentiveDeposit` would trigger the false-return path without any special privileges.

### Recommendation
Replace the raw `.transfer()` calls in `ArbWomUp.incentiveDeposit()` and `ArbWomUp2.incentiveDeposit()` with `safeTransfer` from the already-imported `SafeERC20` library (consistent with the rest of the contract), so that a failed transfer reverts the whole transaction instead of silently updating `claimedReward` and emitting a success event.

### Proof of Concept
1. Admin deploys `ArbWomUp` with `usdt` set to a token whose `transfer` returns `false` (rather than reverting) when the recipient is blacklisted/frozen.
2. A user's address becomes blacklisted on that token (a state achievable by the token's own control mechanism, independent of the Magpie protocol).
3. User calls `incentiveDeposit(_amount)`. `_deposit` succeeds (WOM pulled via `safeTransferFrom`), `claimedReward[msg.sender] += rewardToSend` executes, `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` silently, `USDTRewarded` event still emits.
4. Transaction succeeds; user's `claimedReward` is now inflated with no tokens received. Any future call to `getRewardAmount`/`incentiveDeposit` computes a reduced or zero reward because `claimedReward` already reflects the lost amount, permanently freezing that portion of the user's incentive yield.
