Based on my research of GitHub Desktop's Copilot-based merge-conflict resolution feature, I found a concrete analog to the report's core pattern: an invariant ("nothing with unresolved conflict markers should be committed") that is nominally enforced by one signal, but the code path that actually performs the corrupting action does not independently verify that invariant — so a degraded/adverse condition can slip destructive content through.

### Title
Skipped-conflict "resolved" gate trusts absence-from-working-directory instead of verifying conflict markers are gone, allowing unresolved merge conflicts to be committed - (File: app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx)

### Summary
When GitHub Desktop's Copilot conflict-resolution feature encounters a conflict hunk that is too large or "unwieldy" (e.g., a minified/generated file, or one whose combined conflict content exceeds a size threshold), it marks the file as **skipped** rather than resolving it automatically. [1](#0-0) 
The dialog is supposed to block the user from continuing the merge/rebase/cherry-pick until every skipped file has actually been resolved. [2](#0-1) 
However, the "resolved" check for a skipped file short-circuits to `true` whenever the file is simply absent from the current `workingDirectory.files` snapshot or no longer reported as a conflicted status — without independently verifying that the on-disk content is actually free of conflict markers. [3](#0-2) 

### Finding Description
`isSkippedFileResolved` treats a skipped file as resolved in two ways:
1. The user explicitly picked "ours"/"theirs" via the dropdown, or
2. The file is not found in `this.props.workingDirectory.files`, or is found but its `status` no longer satisfies `isConflictedFile` — in which case the comment states "there is nothing left to gate Continue on, so treat it as resolved." [3](#0-2) 

Only in the remaining case (file present *and* still flagged conflicted) does it fall back to checking `conflictMarkerCount === 0` via `isFileResolvedExternally`. [4](#0-3) 

`workingDirectory` is a React prop populated from an asynchronous Git status refresh, not read fresh at the moment `onContinue` fires. `hasUnresolvedSkippedFiles()` — the only gate protecting "Continue" — is computed purely from this potentially stale snapshot at render time, and `onContinue` itself performs no independent re-check before writing resolutions and advancing the operation: [5](#0-4) [6](#0-5) 

This mirrors the Frankencoin bug's structural flaw exactly: the "auction" (here, the skipped-file resolution gate) is designed to prevent a bad outcome, but under an adverse/attacker-influenced condition (a maliciously crafted oversized or minified conflicting file — attacker fully controls this via a branch/PR the user merges, exactly like an attacker-controlled cloned/fetched repository), the mechanism that should block the unsafe path (committing markers) instead falls back to treating an *absence of information* ("file not in the current status snapshot") as equivalent to "safely resolved," rather than treating it as "unverified." Just as a near-zero bid at auction-close is wrongly treated as the collateral's true value, an absent/stale working-directory entry is wrongly treated as proof the conflict was fixed.

### Impact Explanation
An attacker who can get a user to merge/rebase/cherry-pick a branch containing a deliberately oversized or minified conflicting file (a very plausible, unprivileged scenario — pushing to a fork, opening a PR, or publishing a branch the victim pulls) can cause Copilot to skip that file. If the working-directory status listing for that path becomes stale or briefly drops the file's conflicted status between the time the dialog renders and `onContinue` fires (a real possibility since status refreshes are async and event-driven, and the check trusts absence-of-conflicted-status as "resolved"), the file can be committed to the user's repository still containing raw `<<<<<<<`/`=======`/`>>>>>>>` markers. This is exactly the impact category called out as valid: **silent corruption of what the user commits or pushes**, driven entirely by attacker-controlled content in a fetched/merged repository.

### Likelihood Explanation
The likelihood hinges on how easily `workingDirectory.files` can diverge from ground truth at the exact moment `onContinue` is invoked. This is plausible given: (a) status refresh is asynchronous elsewhere in the app, (b) the code's own comment acknowledges the ambiguity ("Gone from the working directory... means the file was resolved/staged externally"), and (c) large/minified conflicting files are exactly the class of file most likely to have expensive/slow git status computations. I was not able to fully trace every code path that updates `workingDirectory` between dialog render and `onContinue` in the time available, so the precise trigger for staleness (race condition specifics) remains unverified and should be confirmed by a background agent with test/reproduction tooling.

### Recommendation
- In `onContinue`, before calling `applyCopilotConflictResolutions`, re-derive `hasUnresolvedSkippedFiles()` from freshly-read on-disk content (or freshly-queried git status) rather than relying on the render-time prop snapshot.
- Change `isSkippedFileResolved` so that "absent from `workingDirectory.files`" is *not* treated as resolved; instead, explicitly stat/read the file (or re-run `getUnmergedFiles`) to confirm zero conflict markers remain before allowing Continue.
- Add a defensive check at the point the merge/rebase/cherry-pick is actually finalized (dispatcher-level, not just dialog-level) that scans for residual conflict markers in any file that was ever flagged as Copilot-skipped, aborting the operation if markers are found.

### Proof of Concept
Conceptual reproduction (not independently executed):
1. Attacker publishes a branch containing a file with a single conflicting line exceeding `MAX_CONFLICT_LINE_LENGTH` (5000 chars) or whose combined conflict content exceeds `MAX_CONFLICT_CONTENT_SIZE` (256KB), e.g., a minified JS bundle. [7](#0-6) 
2. Victim merges/rebases against this branch in Desktop with Copilot conflict resolution enabled; the file is skipped and appears in the "Skipped by Copilot" list. [8](#0-7) 
3. If the working-directory status for that path is stale/absent when `onContinue` runs (e.g., due to a race in status refresh), `isSkippedFileResolved` returns `true` without ever confirming the markers were removed, `hasUnresolvedSkippedFiles()` returns `false`, and Continue proceeds — committing the file with intact `<<<<<<<`/`>>>>>>>` markers into the resulting commit.

/**
 * Determine whether a file's conflict hunks are too large or too unwieldy to
 * send to the model, returning a human-readable skip reason or null when the
 * conflict is resolvable.
 *
 * We gate on the size of the conflict content itself (what we actually send)
 * rather than the whole-file size, so a large file with a small conflict is
 * still resolved. Two conditions trigger a skip:
 *   1. Any single conflict line exceeds `MAX_CONFLICT_LINE_LENGTH` (minified or
 *      generated content where a line-oriented resolution is meaningless).
 *   2. The combined ours/base/theirs content exceeds `MAX_CONFLICT_CONTENT_SIZE`
 *      (protects prompt size and output quality).
 */
export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}

  private isSkippedFileResolved(path: string): boolean {
    if (this.getSkippedFileChoice(path) !== undefined) {
      return true
    }
    const file = this.props.workingDirectory.files.find(f => f.path === path)
    // Gone from the working directory, or no longer reported as conflicted,
    // means the file was resolved/staged externally - there is nothing left to
    // gate Continue on, so treat it as resolved.
    if (file === undefined || !isConflictedFile(file.status)) {
      return true
    }
    // Still conflicted: resolved only once the markers are removed in an editor.
    return this.isFileResolvedExternally(file)
  }

  private isFileResolvedExternally(file: WorkingDirectoryFileChange): boolean {
    if (!isConflictedFile(file.status)) {
      return false
    }
    // A file with no remaining conflict markers has been resolved in an editor.
    // This wins even when a Current/Incoming choice was previously picked from
    // the dropdown — the on-disk edit is the source of truth, so we show the
    // resolved state rather than the stale dropdown selection.
    if (isConflictWithMarkers(file.status)) {
      return file.status.conflictMarkerCount === 0
    }
    return false
  }
