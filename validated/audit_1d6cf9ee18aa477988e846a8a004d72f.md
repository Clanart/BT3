## Analysis

The Badger bug is a class of "derived/partial proxy value stands in for ground truth, and callers trust it for a security-relevant decision." The Desktop analog is in the merge-conflict resolution pipeline: whether a file is considered "resolved" (safe to commit) is derived from `conflictMarkerCount`, which is computed via `git diff --check` rather than by inspecting the actual file content for literal conflict markers.

`getFilesWithConflictMarkers` parses `git diff --check` output for the "leftover conflict marker" warning: [1](#0-0) 

That count is attached to the conflicted file status as `conflictMarkerCount` when building the status result: [2](#0-1) 

`mapStatus` and `hasUnresolvedConflicts` then treat a `conflictMarkerCount` of `0` as "Resolved," which drives the green-checkmark UI and gates whether the Commit/Continue button is enabled: [3](#0-2) [4](#0-3) 

Critically, `git diff --check` reports differences between the **working tree and the index**, not the absolute presence of marker text in the file. If the working-tree content and the index already agree (i.e., the file was staged — by an external tool, a stray `git add`, or any path outside Desktop's own conflict-resolution flow — while conflict markers were still present), `git diff --check` produces no output for that file, so `conflictCountsByPath` never gets an entry and `conflictMarkerCount` defaults to `0`. The app then reports the file as "Resolved," and `_commitIncludedChanges` performs no independent verification before calling `createCommit` — it simply commits whatever files are selected: [5](#0-4) 

Notably, the codebase already has a "ground truth" marker scanner elsewhere (`extractConflictHunks`/`isConflictMarker`, used for Copilot conflict resolution), which reads the actual file bytes and scans line-by-line for marker patterns instead of relying on a diff-based proxy: [6](#0-5) 

This shows the two mechanisms can diverge: one is authoritative (content scan), the other (`git diff --check`) is an index-relative proxy that can silently under-report, exactly mirroring the Badger bug's `badger.balanceOf(sett)` vs. `sett.balance()` distinction.

### Title
Conflict-resolution status relies on `git diff --check` (index-relative proxy) instead of scanning file content, allowing unresolved conflict markers to be silently committed - (File: `app/src/lib/git/diff-check.ts`)

### Summary
`conflictMarkerCount`, which the UI uses to decide whether a conflicted file is "Resolved" and to enable the Commit/Continue button, is computed from `git diff --check` (working tree vs. index) rather than from the actual on-disk file content. When the working tree and index already match (e.g., markers were staged by an external process, tool, or scripted `git add` while resolution was in progress), the diff produces no "leftover conflict marker" warning and the count silently reports `0`, even though the file still contains literal `<<<<<<<`/`=======`/`>>>>>>>` text.

### Finding Description
`getFilesWithConflictMarkers` shells out to `git diff --check` and parses "leftover conflict marker" lines from its stdout: [1](#0-0) 

This is consumed while building the merge/rebase/working-directory conflict details used to construct `IStatusResult`: [7](#0-6) 

The resulting `conflictMarkerCount` is what `hasUnresolvedConflicts` and `mapStatus` use to determine "Resolved" vs. "Conflicted" state: [3](#0-2) 

`git diff --check` (like plain `git diff`) reports differences relative to the **index**, not an absolute scan of file content. This is a "reserve/partial" proxy, structurally analogous to `badger.balanceOf(address(badgerSett))` only reflecting the small liquid reserve rather than the Sett's true total balance (`badgerSett.balance()`). Here, once conflict-marker text is already staged (matching the index), the proxy signal goes silent regardless of what the working file actually contains.

The commit path performs no secondary verification: `_commitIncludedChanges` commits exactly the files passed to it based on UI selection state, with no re-scan of file bytes for marker text: [5](#0-4) 

The codebase's own Copilot conflict-resolution feature implements the correct, ground-truth approach — scanning raw file content for marker regexes — which underscores that the `git diff --check`-based path is a weaker proxy, not an equivalent check: [8](#0-7) 

### Impact Explanation
If the proxy signal under-reports (`conflictMarkerCount = 0`) while the file content still contains literal conflict-marker text, Desktop's UI shows the file as fully "Resolved" (green check) and enables committing/continuing the operation. The user, trusting the app's UI, commits and potentially pushes a file whose content is corrupted with literal `<<<<<<<`/`=======`/`>>>>>>>` markers baked into tracked history — a silent corruption of what the user commits, matching the impact category of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires the index to already match the working tree while markers are still present — a state that is not synthesized purely by ordinary user interaction inside Desktop's own resolution UI, since Desktop's own staging (`stageManualConflictResolution`) operates via `checkout`/`add`/`rm`, not raw `git add` of marker text. However, the underlying scanning mechanism (`git diff --check`) is a proxy relative to the index by design, and I was not able to fully verify, within the exploration budget available, an exact reproducible Desktop-only trigger path (e.g., interaction with autosave/external editors, hooks, or partial-file staging flows) that stages marker text without Desktop detecting it. This should be treated as **moderate-to-low confidence** without further live reproduction — flagged explicitly as an area needing additional verification via a Devin session with terminal/git access, since the analysis here is based on static code review of the index page, not confirmed dynamic exploitation.

### Recommendation
Replace or supplement the `git diff --check`-based conflict-marker detection with a direct content scan of the conflicted file (as already implemented in `extractConflictHunks`/`isConflictMarker` for Copilot) so that "Resolved" status reflects the literal absence of conflict-marker text in the working file, independent of the file's staged/index state. Additionally, perform this content-level marker check as a hard gate immediately before `createCommit` in `_commitIncludedChanges`, rather than relying solely on cached UI state derived from the last status refresh.

### Proof of Concept
Not independently reproduced in this session (read-only Ask mode, no terminal/git execution available). Suggested reproduction steps for a follow-up engineering session:
1. Trigger a merge/rebase conflict in a test repository so a file contains `<<<<<<<`/`=======`/`>>>>>>>` markers.
2. Outside Desktop (e.g., via terminal or another tool), run `git add <file>` on the still-conflicted file so the index matches the working tree exactly (markers included), without removing the markers.
3. In Desktop, trigger a status refresh and observe whether `getFilesWithConflictMarkers`/`conflictMarkerCount` reports `0` for that file (since `git diff --check` will show no difference against the now-matching index) and whether the UI marks it "Resolved," enabling Commit.
4. Complete the commit/continue action and inspect the resulting commit's blob for lingering literal conflict-marker text.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

 * Determine if we have any conflict markers or if its been resolved manually

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

const oursMarker = /^<{7}(?:\s|$)/
const baseMarker = /^\|{7}(?:\s|$)/
const separatorMarker = /^={7}$/
const theirsMarker = /^>{7}(?:\s|$)/

/**
 * Absolute upper bound (in bytes) on a conflicted file we'll read into memory.
 *
 * This is a memory-safety guard only, not a resolvability heuristic — we only
 * ever send the *conflict hunks* to the model, never the whole file, so a large
 * file with a small conflict is still perfectly resolvable. Files above this
 * size are skipped before reading to avoid loading pathological blobs (e.g. a
 * multi-megabyte generated lockfile) into a string.
 */
const MAX_CONFLICT_FILE_READ_SIZE = 10_485_760 // 10MB

/**
 * Maximum length (in characters) of any single line within a conflict hunk.
 *
 * Mirrors the diff renderer's `MaxCharactersPerLine`. Conflicts containing a
 * line longer than this are almost always minified/generated content where a
 * line-oriented resolution is meaningless, so we skip them rather than sending
 * an enormous single line to the model.
 */
const MAX_CONFLICT_LINE_LENGTH = 5000

/**
 * Maximum combined size (in characters) of the actual conflict content in a
 * single file — the sum of the ours/base/theirs text across every hunk.
 *
 * Unlike a whole-file cap, this measures what we actually send to the model, so
 * it protects prompt size and output quality (truncation/malformed JSON)
 * without penalising large files whose conflicts are small.
 */
const MAX_CONFLICT_CONTENT_SIZE = 262_144 // 256KB

function isConflictMarker(line: string): boolean {
  return (
    oursMarker.test(line) ||
    baseMarker.test(line) ||
    separatorMarker.test(line) ||
    theirsMarker.test(line)
  )
}
