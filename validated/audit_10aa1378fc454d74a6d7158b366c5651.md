### Title
Strict `<` Instead of `<=` in Work Comparison Allows Operator with Equal Work to Pass Bridge Circuit — (`circuits-lib/src/bridge_circuit/mod.rs`)

---

### Summary

The bridge circuit enforces that an operator's total proof-of-work must be **strictly greater than** the maximum work submitted by any valid watchtower challenger. The implementation uses a strict `<` comparison, which means the circuit does **not** panic when `total_work == max_total_work`. An operator on a fork whose 128-bit truncated cumulative work exactly equals the watchtower's proven work can pass the circuit and be reimbursed from the bridge vault without having demonstrated canonical-chain superiority.

---

### Finding Description

In `bridge_circuit()`, after computing `max_total_work` from all valid watchtower Groth16 proofs, the operator's own work is extracted from the lower 128 bits of the HCP chain state and compared:

```rust
// circuits-lib/src/bridge_circuit/mod.rs, line 155-160
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
```

The comment says "less than" and the code enforces exactly that — but the protocol specification in `docs/bridge-circuit.md` line 33 states:

> "Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers."

"Greater than" is a strict inequality. The code's `<` guard allows the equal case (`total_work == max_total_work`) to pass silently.

Both sides of the comparison are 128-bit big-endian byte arrays (`TotalWork(pub [u8; 16])`):

- The operator's side is `input.hcp.chain_state.total_work[16..32]` — the lower 128 bits of the 256-bit HCP chain work. [1](#0-0) 
- The watchtower's side is the `work_u128` committed by the work-only circuit via `work_conversion`, which also takes the lower 128 bits of the 256-bit chain work. [2](#0-1) 

`TotalWork` derives `PartialOrd` over `[u8; 16]`, which is lexicographic — correct for big-endian numeric comparison. [3](#0-2)

### Impact Explanation

The bridge circuit is the ZK proof an operator submits (via the BitVM2 assert/disprove flow) to justify reimbursement from the bridge vault after fronting a withdrawal. If the circuit passes, the operator is entitled to reclaim the bridged BTC from the vault.

The canonical-chain determination in Clementine is entirely work-based: the operator must prove they are on a chain with **strictly more** cumulative work than any watchtower's challenged chain. Allowing equal work breaks this invariant — an operator on a fork with the same 128-bit truncated work as the canonical chain (as proven by a watchtower) can produce a valid bridge circuit proof and drain the vault for a withdrawal that was not legitimately settled on the canonical chain.

---

### Likelihood Explanation

The 128-bit truncation (lower half of the 256-bit Bitcoin chainwork) makes an exact collision non-trivial on mainnet today, but:

1. On regtest or testnet4 (both explicitly supported by the codebase), work values are tiny and collisions are trivially engineered.
2. As Bitcoin's cumulative work grows, the upper 128 bits become non-zero and the lower 128 bits cycle — future mainnet collisions become more plausible.
3. A malicious operator who also controls mining can deliberately construct a fork whose 128-bit work matches the canonical chain's 128-bit work at the moment of challenge.

---

### Recommendation

Change the strict `<` to `<=` so that equal work is also rejected:

```rust
// circuits-lib/src/bridge_circuit/mod.rs
// Before:
if total_work < max_total_work {

// After:
if total_work <= max_total_work {
```

This aligns the code with the documented invariant ("greater than") and closes the boundary-case bypass.

---

### Proof of Concept

1. A watchtower submits a valid work-only Groth16 proof for a chain with 128-bit work value `W`.
2. The operator constructs (or finds) a fork whose HCP chain state has lower-128-bit work also equal to `W`.
3. The operator submits a bridge circuit proof using this HCP.
4. At line 156, `total_work < max_total_work` evaluates to `W < W` → `false` → no panic.
5. The circuit completes successfully; the operator's assert transactions are accepted.
6. No valid disprove transaction can be constructed because the circuit output is internally consistent.
7. The operator is reimbursed from the bridge vault for a withdrawal that was not on the canonical chain. [6](#0-5) [3](#0-2) [7](#0-6)
