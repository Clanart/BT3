### Title
Payout OP_RETURN operator key is trusted for reimbursement attribution with no proof the named operator's own funds paid the withdrawal - (File: circuits-lib/src/bridge_circuit/mod.rs, core/src/verifier.rs, core/src/operator.rs)

### Summary
`bridge_circuit`'s `deposit_constant`/`journal_hash` bakes in an `operator_xonlypk` taken solely from `parse_op_return_data` on the payout tx's OP_RETURN, with no check that the named operator's own signature/funds produced that output. Every downstream consumer (`update_finalized_payouts`, `is_kickoff_malicious`, `validate_payer_is_operator`) re-derives and compares against this same untrusted OP_RETURN value instead of an independently authenticated payer identity, so an attacker who fronts a withdrawal payout (already assumed possible via the S+AP signature-reuse precondition) can attribute the payout to any registered operator's `XOnlyPublicKey` of their choosing.

### Finding Description
The broken binding, stated explicitly:

`operator_xonlypk` embedded in `deposit_constant` (and in the DB column `withdrawals.payout_payer_operator_xonly_pk`) **==** the xonly public key of the operator who actually funded/broadcast the payout transaction that pays the withdrawer.

Trace of the code path:
1. `circuits-lib/src/bridge_circuit/mod.rs::bridge_circuit` (lines ~206-229) takes `first_op_return_output` from `input.payout_spv.transaction` and calls `parse_op_return_data` to get `operator_xonlypk: [u8;32]`, which is fed straight into `deposit_constant(...)` with zero validation that this key corresponds to any real signer of the transaction. [1](#0-0) 
2. `parse_op_return_data` (mod.rs:608-617) is a pure script parser — it returns whatever bytes are pushed after `OP_RETURN`, with no cryptographic binding to the transaction's signer/inputs. [2](#0-1) 
3. The host-side mirror, `bridge-circuit-host/src/structs.rs::host_deposit_constant`, does the exact same unauthenticated extraction. [3](#0-2) 
4. On the verifier/attribution side, `core/src/verifier.rs::update_finalized_payouts` scans the confirmed payout tx, calls `get_first_op_return_output` + `parse_op_return_data` + `XOnlyPublicKey::from_slice`, and stores whatever key is found as `payout_payer_operator_xonly_pk` in the DB — again no signature or input-ownership check. [4](#0-3) 
5. `is_kickoff_malicious` (verifier.rs:1857-1915) only compares this DB-stored, attacker-influenced key against `kickoff_data.operator_xonly_pk` — the key of whoever *chooses* to initiate a kickoff. It never checks that the named operator's wallet actually spent BTC to create the payout tx. [5](#0-4) 
6. `core/src/operator.rs::validate_payer_is_operator` similarly only checks `payer_xonly_pk != self.signer.xonly_public_key`, i.e. it trusts the DB-recorded OP_RETURN key completely. [6](#0-5) 

Exploit flow: the attacker, holding the withdrawer's reusable signature (per the stated S+AP precondition), fronts the payout transaction and sets its sole OP_RETURN push to the raw 32-byte x-only public key of operator B — a real, registered operator with valid collateral and kickoff capability who never touched this withdrawal. `update_finalized_payouts` records `payout_payer_operator_xonly_pk = B`. Operator B's own automation (`PayoutCheckerTask` → `get_reimbursement_txs` → `validate_payer_is_operator`) sees a payout attributed to itself and proceeds through the normal kickoff/assert/disprove flow. Since `is_kickoff_malicious` and `validate_payer_is_operator` only compare against the OP_RETURN-derived key — which the attacker chose to equal B's real key — none of these guards fire. `bridge_circuit` then produces a `deposit_constant`/`journal_hash` that cryptographically certifies "operator B funded this payout," even though B's wallet never spent a satoshi toward it; the attacker's own transaction did.

None of `Verifier::is_deposit_valid`, `Operator::is_profitable`, `SECP.verify_schnorr`, `only_aggregator_and_self`, `verify_storage_proofs`, `SPV::verify`, or `lc_proof_verifier` re-derive payer identity from the payout transaction's actual signing key or input provenance — they all operate on outpoints/hashes/proofs unrelated to who paid the OP_RETURN-named operator's bill.

### Impact Explanation
BTC leaves a move-to-vault UTXO via the Reimburse transaction crediting operator B, who never fronted the withdrawal — this is "an operator reimbursed for a payout it never funded," a Critical-category impact. The withdrawer is paid once (by the attacker), but the protocol's reimbursement machinery independently pays out again to operator B based on a `journal_hash` that falsely attests B was the payer. This is repeatable for any deposit/withdrawal and against any registered operator whose x-only public key the attacker chooses to embed, as long as the attacker can front the payout via the assumed signature-reuse precondition. The blast radius scales with the number of open withdrawals and registered operators, since the same unauthenticated-OP_RETURN pattern is used everywhere the payer identity is derived.

### Likelihood Explanation
Preconditions required: a withdrawal registered on Citrea, the withdrawer's reusable signature (obtainable from the public `withdraw` call per the stated precondition), and knowledge of at least one real operator's public `XOnlyPublicKey` (trivially public — operators publish their key via `GetXOnlyPublicKey`/`GetParams`). Attacker cost is the BTC value of the withdrawal itself plus fees (since the attacker must actually fund the payout output to front it) — this is a real cost, but it's a one-time cost per exploited withdrawal and the attacker can plausibly recoup or exceed it if the goal is to redirect protocol funds to an operator they collude with, or simply to grief/mis-attribute payouts and force operators into disputes. No mainnet or live Citrea infrastructure is needed to demonstrate the core defect — it is fully reproducible with unit/integration tests inside `circuits-lib`/`core` using constructed transactions and DB fixtures.

### Recommendation
Do not treat the OP_RETURN push in the payout transaction as an authenticated claim of operator identity. Instead, require an independent, cryptographic binding between the payout transaction and the operator who is credited: e.g., require the payout transaction's OP_RETURN commitment (or a companion signature) to be signed by the named operator's key over the payout transaction's txid/sighash, and have `bridge_circuit`, `update_finalized_payouts`, `is_kickoff_malicious`, and `validate_payer_is_operator` all verify that signature before accepting the OP_RETURN-derived `operator_xonlypk` as authoritative. Alternatively, bind payer identity to a UTXO/input of the payout transaction that is provably controlled by the operator's collateral/reimbursement address, rather than to an arbitrary unauthenticated data push.

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
