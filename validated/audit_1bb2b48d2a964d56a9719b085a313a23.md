### Title
`distribution.rewards()` accepts native value transfers but never records or refunds them, permanently stranding sent SEI/wei - ([File: precompiles/distribution/distribution.go])

### Summary
The `distribution` Cosmos precompile's `rewards` view method is dispatched without the `pcommon.ValidateNonPayable` guard that every other read-only/view method in the same dispatcher enforces. A caller can invoke `rewards(address)` with a non-zero `msg.value`; the EVM will transfer that value to the precompile's address as part of the CALL, but the Go handler `rewards(...)` never touches, records, refunds, or forwards the `value` parameter — it is silently dropped, exactly like the `DepositStableCoinToDealer` analog where an asset/value mismatch causes native ether to be accepted but never accounted for.

### Finding Description
In the distribution precompile's `Execute` dispatcher, every other method that is not supposed to accept a payment either explicitly enforces `pcommon.ValidateNonPayable(value)` (e.g. `WithdrawValidatorCommissionMethod`) or explicitly consumes `value` for a payment flow (e.g. `deposit` in gov). `RewardsMethod`, however, is dispatched directly to `p.rewards(ctx, method, args)` with no `value` parameter at all and no non-payable check: [1](#0-0) 

The `rewards` function signature itself never receives or checks `value`: [2](#0-1) 

This omission is corroborated by the project's own integration-test documentation, which explicitly calls this out as a known "guard quirk": [3](#0-2) 

Because `rewards` is registered as a precompiled contract address, the standard EVM `Call` semantics apply: when a caller issues a CALL with non-zero `value` to the precompile address, the EVM performs the native balance transfer from the caller to the precompile's address *before* invoking the precompile's `Run`/`Execute` logic. Since `rewards()` performs no logic to consume, forward, or reject that value, the transferred wei/usei becomes stranded at the precompile address — unrecoverable by the sender and not represented in any Cosmos-side balance, delegation, or reward accounting.

This is the same bug class as the reported issue: a function that appears to accept value input (payable in EVM terms) fails to validate/process that value, so a user who mistakes it for a payable/deposit-like call loses funds silently, with no possibility for the contract or any other actor to retrieve or credit them.

### Impact Explanation
Any external account or contract can call `rewards(address)` through the distribution precompile with an attached `msg.value`. Because the value is transferred by the EVM's call mechanics but never used, checked, or refunded by the precompile logic, the sent native SEI is permanently and irrecoverably lost/stranded at the precompile address — a concrete, direct loss of user funds. This satisfies the "concrete fund loss or permanent freezing" impact bar. The bug is reachable by any unprivileged EVM caller (JSON-RPC client or contract) making a single transaction — no privileged, governance, or validator access required.

### Likelihood Explanation
`rewards` is a simple, view-like function that developers/integrators would reasonably call without adding an explicit `value: 0` override, and unlike `WithdrawValidatorCommissionMethod`/other guarded methods in the same file, there is no protective revert to catch an accidental non-zero value. Since the wallet/dApp tooling generally allows attaching value to any contract call, and the precompile's ABI does not signal non-payable at the EVM ABI level for this path, an accidental or exploratory value-bearing call is plausible, and any such call results in permanent loss.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used elsewhere in the distribution precompile (and other precompiles) to the `RewardsMethod` case in `Execute`, rejecting any call to `rewards` that carries non-zero `value`, consistent with all other non-payment view/query methods in the file (e.g. `ValidatorOutstandingRewardsMethod`, `DelegationRewardsMethod`, etc., which are pure queries and should equally reject value, and mirroring the explicit check already applied to `WithdrawValidatorCommissionMethod`).

### Proof of Concept
1. Deploy/target the distribution precompile at its fixed address (0x…1007).
2. From any associated EOA, submit a transaction calling `rewards(delegatorAddress)` with `value = 1 ether` (or any non-zero wei amount) and sufficient gas.
3. Observe that:
   - The call succeeds and returns the expected rewards data (no revert), confirming the value was not validated.
   - The sender's native balance decreases by the sent value (the EVM performed the value transfer to the precompile address as part of the CALL).
   - No Cosmos-side bank transfer, delegation, or reward record reflects the sent value — it is not credited to the delegator, not refunded to the sender, and not recorded anywhere.
4. The sent value is now stranded at the distribution precompile's address with no code path in `precompiles/distribution/distribution.go` capable of recovering or crediting it. [4](#0-3)
