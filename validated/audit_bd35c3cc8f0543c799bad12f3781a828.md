## Finding

### Title
Missing per-leg slippage protection in `SmartWomConvert._convertFor()` allows sandwich-attack theft of compounded rewards when triggered via `ManualCompound.compound()` - (File: wombat/SmartWomConvert.sol)

### Summary
`SmartWomConvert._convertFor()` swaps the "buyback" portion of a WOM amount for `mWom` through the Wombat router while passing a hard-coded `0` as the router's minimum-output parameter, relying entirely on a single post-swap aggregate check (`convertAmount + amountRec < _minRec`) to bound loss. When this function is reached via `ManualCompound.compound()`, the amount swapped is derived from the contract's live token balance rather than a value fixed by the caller, allowing any unprivileged wallet to inflate that balance before the victim's transaction executes and defeat the aggregate check while a sandwich attack drains value from the unprotected swap leg — the same bug class as the reported `IdleCDO.harvest()` issue.

### Finding Description
`ManualCompound.compound()` is callable by any wallet and, for each configured reward, computes the amount to convert directly from the contract's current balance: [1](#0-0) 

This `receivedBalance` (not a value chosen/committed by the caller) is passed straight into `IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2)`, where `_convertor` is `SmartWomConvert`.

Inside `SmartWomConvert._convertFor()`, the amount is split into a `buybackAmount` that gets swapped through the Wombat router and a `convertAmount` that is deposited 1:1 into `mWom`. The router call explicitly passes `0` as the minimum amount out, meaning the swap itself has **no** price protection: [2](#0-1) 

Protection is only enforced afterward, on the *sum* of the swapped and directly-deposited portions: [3](#0-2) 

Because `convertAmount` scales with the inflated total `_amount` and is not itself subject to price risk (it's a 1:1 deposit), an attacker can donate extra reward tokens directly to the `ManualCompound` contract before a victim's `compound()` transaction executes. This inflates `receivedBalance`, which inflates both `buybackAmount` and `convertAmount` proportionally. The larger `convertAmount` cushions the aggregate `_minRec` check, letting the transaction pass even if the attacker sandwiches the WOM→mWom router swap (which has zero slippage protection) and extracts nearly all the value from the `buybackAmount` leg. This mirrors exactly the reported `IdleCDO.harvest()` flaw: a minimum-output check computed against a stale/anticipated amount fails to bound loss once the actual amount sold is increased by a third party between transaction submission and execution.

### Impact Explanation
A victim calling `ManualCompound.compound()` to compound their claimed rewards can have the WOM→mWom swap leg sandwiched, resulting in the loss of the price-impact difference on the `buybackAmount` portion, while `_minRec` (set based on the victim's anticipated, smaller `receivedBalance`) still passes because of the inflated `convertAmount` cushion. This is a direct theft of a user's compounded yield/funds by an unrelated third party, extractable without any privileged role.

### Likelihood Explanation
`compound()` and the underlying `convertFor()` path are fully unprivileged and callable by anyone at any time. Front-running a pending `compound()` transaction to donate tokens directly to the `ManualCompound` contract (a simple `IERC20.transfer`) is trivial and requires no special access; the profitability depends on Wombat pool depth and the size of the sandwich, the same caveat noted in the original report for `IdleCDO`.

### Recommendation
Enforce slippage protection at the actual swap call rather than only on the aggregate output. Pass a real minimum-output value (derived from an on-chain quote or caller-supplied minimum for that specific leg) into `IWombatRouter.swapExactTokensForTokens` instead of `0`, and avoid deriving swap amounts from mutable, donation-inflatable contract balances in `ManualCompound.compound()` — instead compute/pass the exact amount actually claimed within the same transaction and validate the per-leg swap output independently of any donated balance.

### Proof of Concept
1. Attacker observes a pending `ManualCompound.compound()` transaction in the mempool for a victim, with a `_minRec` calibrated to the victim's expected `receivedBalance` for reward token WOM.
2. Attacker front-runs by transferring extra WOM tokens directly to the `ManualCompound` contract address, inflating `IERC20(WOM).balanceOf(address(this))`.
3. Victim's `compound()` executes: `receivedBalance` now includes the donated WOM, so both `buybackAmount` and `convertAmount` passed into `SmartWomConvert._convertFor()` are larger than the victim anticipated.
4. Within the same block, the attacker sandwiches the router swap of `buybackAmount` (executed with `0` minimum-out at `wombat/SmartWomConvert.sol:194-196`), pushing the WOM/mWom pool price unfavorably and back-running after the swap.
5. Despite `amountRec` being minimized by the sandwich, `convertAmount + amountRec >= _minRec` still holds because `convertAmount` grew from the donation, so the transaction does not revert at `wombat/SmartWomConvert.sol:204-205`.
6. Attacker recoups the donated tokens' cost (and profits) via the sandwich, at the expense of the value the victim should have received from compounding.
