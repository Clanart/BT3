### Title
Consumed FROST preprocess seed is never marked used — deterministic nonce reuse across repeated `share_internal` calls - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The audit issue is a state variable copied to memory, mutated, and never written back (`latestUpTimestamp` updated on a `memory` struct, so the "last update" is never recorded and the next read accumulates over the same stale interval again). The Serai analog lives in `SigningProtocol::preprocess_internal`: the FROST nonce seed stored under `CachedPreprocesses` is loaded and decrypted on every call, but the fact that it has been *consumed* is never recorded — the entry is only ever `set` when absent and is never deleted or rotated. The result mirrors the original bug exactly: persistent state that protocol logic assumes is updated after each use is left stale, so every subsequent signing operation for the same context silently re-derives the identical nonce pair.

### Finding Description
`SigningProtocol::preprocess_internal` (coordinator/src/tributary/signing_protocol.rs) derives a one-time FROST preprocess from a cached 32-byte seed:

- On first use for a `context`, a random seed is generated via `AlgorithmMachine::new(...).preprocess(&mut OsRng)`, the machine's `cache()` seed is XOR-encrypted with a key derived from `context || self.key`, and stored: `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` (lines 123–135).
- On every subsequent call the same stored seed is decrypted and passed to `AlgorithmSignMachine::from_cache` (lines 137–145), which routes to `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)` → `Commitments::new(rng, ...)` (crypto/frost/src/sign.rs, `seeded_preprocess` lines 121–144). The same seed deterministically reproduces the identical nonce pair `(d, e)` and identical commitments `D, E`.
- Nothing ever deletes, rotates, or marks the entry consumed. `CachedPreprocesses` has no `del`/increment path anywhere in the codebase — the "used" update is made only on the in-memory `AlgorithmSignMachine` (which consumes `self` in `sign`), exactly analogous to mutating the memory copy of `holdTokenRateInfo` while `holdTokenInfo[key]` stays stale.

Callers re-enter `share_internal` multiple times under the same context. `share_internal` (line 156) calls `self.preprocess_internal(participants).0`, rebuilding a machine from the same seed each time. `DkgConfirmer` fixes the context to `(b"DkgConfirmer", self.attempt)` (line 275), and both `share` (line 304) and `complete` (line 312) invoke `share_internal` — `complete` calls it *again* internally (line 321–324) with independently supplied `preprocesses` and `key_pair`. So a single attempt performs at least two `machine.sign(...)` executions over the same nonces, and any retry/reboot within the same attempt performs more, each time publishing a fresh `SignatureShare` to the tributary.

### Impact Explanation
A FROST share is `s = d + e·ρ + λ·x·c`. With the nonce pair `(d, e)` fixed by the reused seed, each additional `sign` call with a different preprocess set yields a different binding factor `ρ` (rho is computed over the participants' commitments and group key) and a different challenge `c` (the adversary controls R via the preprocess bytes it submits through `read_preprocess`). Two distinct shares give `s1 − s2 = e·(ρ1 − ρ2) + k·(c1 − c2)` with `k = λ·x`; a third share (retry, reboot resubmission, or a second `share` call with a different accumulated preprocess map) produces a second independent equation, letting the attacker solve for `e` and `k`, hence the node's MuSig/FROST secret share `x` for the tributary validator key. That is recovery of the validator's signing key share — the exact consequence the `CachedPreprocess` documentation warns about ("Reuse will enable third-party recovery of your private key share", crypto/frost/src/sign.rs lines 83–92, 216–224), reached not through integrator misuse but because the consumption update is never persisted, the same class as the unrecorded `latestUpTimestamp`.

### Likelihood Explanation
`share` and `complete` are separate calls that each internally sign; a participating validator can supply different preprocess bytes in the two rounds (the map passed to `share` comes from accumulated `Preprocess` data and the map passed to `complete` is supplied independently), forcing different `ρ`/`c` under identical nonces. Additionally, the coordinator may re-execute `share` for the same `attempt` after a reboot or accumulation retry, generating further equations. No collusion or privileged access is required — only the ability to submit preprocess data as a signing-set participant and observe shares, which are broadcast publicly.

### Recommendation
Record nonce consumption, completing the write-back the current code omits. After `share_internal` successfully produces a share for a context, delete or mark the `CachedPreprocesses` entry (e.g., store a consumed-flag/`Option` and refuse to sign again under the same context, or key the cache by a hash of the preprocess set plus message so differing inputs derive different seeds). `complete` should reuse the `SignatureMachine` returned by the matching `share` rather than rebuilding one from the same seed via `share_internal`.
