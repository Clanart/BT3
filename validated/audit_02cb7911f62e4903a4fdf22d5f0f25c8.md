### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers a large up-front heap allocation before any bytes are validated - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts a 2-byte `n` field from untrusted input and immediately calls `Vec::with_capacity(usize::from(n))` when the interpolation tag is `Constant`, plus loops reading `n` field elements and `n` group elements. A remote peer feeding ~15 crafted bytes can force a ~2–4 MiB heap allocation that is only released after the read fails at EOF, giving a large allocation-amplification DoS per message.

### Finding Description
In `ThresholdKeys::read`, after reading the curve ID, the code reads `t`, `n`, and `i` as raw `u16`s, then reads a one-byte interpolation tag:

```rust
// crypto/dkg/src/lib.rs ~604-616
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  ...
};
``` [1](#0-0) 

`Vec::with_capacity(n)` commits `n * size_of::<C::F>()` of heap memory *before* a single scalar byte has been read from the stream. With `n = 65535`, the caller's ~15-byte prefix (curve-ID length + ID + 6 bytes of `t/n/i` + 1 tag byte) causes an allocation of roughly 2 MiB for 32-byte fields and more for wider fields — while the backing buffer may hold no scalar data at all. The subsequent `read_F` loop then walks `n` elements; on a short/truncated stream it fails at the first `read_exact`, but the allocation has already been made. A peer can repeat this on every message, and send messages concurrently, multiplying the transient memory footprint.

The same attacker-controlled count then drives a second bounded-but-attacker-sized loop reading `n` group elements into a `HashMap`:

```rust
// crypto/dkg/src/lib.rs ~620-623
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
``` [2](#0-1) 

This is the same bug class as the Discourse report (attacker-injected size parameters causing resource consumption). It is reachable per the threat model: `ThresholdKeys::read` is explicitly in the set of untrusted-byte sinks, and analogous deserializers elsewhere in Serai (`ethereum::machine::Call::read`) explicitly document this pattern — "A valid DoS would be to claim a 4 GB data is present" — and mitigate it with chunked reads. The dkg crate has no such mitigation and no sanity cap on `n` at read time (the `ThresholdParams::new` check that `i <= n` happens only after the loops).

### Impact Explanation
An unprivileged counterparty in a DKG/signing session (or anyone able to deliver bytes to `ThresholdKeys::read`) can force the victim to allocate ~2–4 MiB of heap per ~15-byte message, repeatedly and concurrently. Because the allocation precedes any validation that the data exists, a tiny truncated message yields maximum amplification. Repeated or parallel messages can exhaust memory or trigger OOM termination of the signing/validator process. This is a denial of service with no secret leakage required, matching Medium-severity resource-exhaustion.

### Likelihood Explanation
- Reachability is direct: the bytes are fully attacker-controlled (`t`, `n`, `i`, tag), with no authentication, length cap, or `n`-vs-actual-data check before allocation.
- Cost to attacker is trivial (a handful of bytes; no valid points, scalars, or proofs needed since failure occurs after allocation).
- The only bound is `u16` (65,535 entries), which is precisely why the impact is bounded to MiBs rather than GiBs — but at high message rates/concurrency this is still an effective memory-pressure DoS.
- Exploitation reliability is high; it works against any curve since `with_capacity` is generic over `C::F`.

### Recommendation
- Do not pre-size containers from an untrusted count. Replace `Vec::with_capacity(usize::from(n))` with incremental `push` (or a small fixed initial capacity), so memory grows only as data actually arrives — the same chunked-read approach used in `networks/ethereum/src/machine.rs` `Call::read`.
- Optionally enforce a protocol-level maximum for `n` (e.g., the real validator-set size) before allocating or looping, and reject `n` values exceeding it during deserialization.
- Apply the same audit to other `with_capacity`/count-prefixed read paths in `frost`, `pedpop`, and `musig` to confirm they are likewise bounded by actual stream contents.

### Proof of Concept
Conceptual byte stream fed to `ThresholdKeys::<C>::read` (e.g., `C = Ristretto` or `Secp256k1`, `C::ID` length `L`):

```
[ u32 LE = L ][ C::ID bytes ]
t = 01 00            // u16 LE = 1
n = ff ff            // u16 LE = 65535  <- attacker-controlled count
i = 01 00            // participant 1
tag = 00             // Interpolation::Constant
<EOF or a few bytes of garbage>
```

Upon reading the tag `0`, the implementation executes `Vec::with_capacity(65535)` — committing ~`65535 * size_of::<C::F>()` (~2 MiB for 32-byte fields) — before the first `C::read_F` fails on the truncated stream. Repeating this message N times (sequentially or across parallel sessions/connections) forces N concurrent ~2 MiB+ transient allocations from a ~`L + 11`-byte input each, enabling sustained memory-exhaustion of the host process. The `with_capacity` call is at `crypto/dkg/src/lib.rs` line ~608; the attacker-controlled `n` is read at lines ~591-602; the unbounded-by-actual-data verification-share loop follows at ~620-623.
