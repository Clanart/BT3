### Title
Out-of-bounds pointer arithmetic in `CallerAccount::get_serialized_data`'s virtual-address-adjustment workaround bypasses `MemoryMapping` bounds checks when `syscall_parameter_address_restrictions` is disabled - (File: `program-runtime/src/cpi.rs`)

### Summary
When the feature flag combination `virtual_address_space_adjustments = true`, `account_data_direct_mapping = false`, and `syscall_parameter_address_restrictions = false` is active, `CallerAccount::from_account_info` derives the CPI account-data slice's virtual address (`vm_addr`) and length (`len`) directly from an attacker-forged `AccountInfo.data` fat pointer with no validation, then feeds them into `CallerAccount::get_serialized_data`'s "workaround" branch, which does raw pointer arithmetic on the host pointer for `MM_INPUT_START` instead of calling into `MemoryMapping`'s bounds-checked translation. This can produce a `&mut [u8]` slice that extends arbitrarily outside the actual input-parameter region.

### Finding Description
In `CallerAccount::from_account_info` (`program-runtime/src/cpi.rs:272-395`), `vm_data_addr` is taken from `data.as_ptr()` where `data` is the fat pointer read out of the caller's (attacker's) `AccountInfo.data: Cell<&[u8]>`, and `len` is taken from `data.len()` — both entirely attacker-controlled — *unless* `syscall_parameter_address_restrictions` is enabled, in which case the code calls `check_account_info_pointer` to enforce `data.as_ptr() == account_metadata.vm_data_addr` (the trusted, serializer-computed address) and uses `*ref_to_len_in_vm` for the length instead (`cpi.rs:336-363`).

These two values are passed unchecked into `CallerAccount::get_serialized_data` (`cpi.rs:216-269`). Inside that function, the length-bound check (`len > address_space_reserved_for_account`) is itself gated behind `if syscall_parameter_address_restrictions` (`cpi.rs:228-238`), so when that flag is off, `len` is unconstrained. Then, because `virtual_address_space_adjustments` is on and `account_data_direct_mapping` is off, execution enters the "workaround" branch (`cpi.rs:241-257`):

```rust
let serialization_ptr: &'a mut [u8] = translate_slice_mut_for_cpi::<u8>(
    memory_mapping,
    solana_sbpf::ebpf::MM_INPUT_START,
    1,
    false,
)?;
Ok(std::slice::from_raw_parts_mut(
    serialization_ptr
        .as_mut_ptr()
        .add(vm_addr.saturating_sub(solana_sbpf::ebpf::MM_INPUT_START) as usize),
    len,
))
```

This only asks `MemoryMapping` to validate that byte 0 of the input region is mapped (`len = 1`), then manually computes `serialization_ptr.as_mut_ptr().add(vm_addr - MM_INPUT_START)` and constructs a slice of size `len` via `from_raw_parts_mut` — completely bypassing `MemoryMapping`'s region-bound validation for the actual `[vm_addr, vm_addr+len)` range that `translate_slice_mut_for_cpi` in the `else` branch (used when `virtual_address_space_adjustments` is off, `cpi.rs:258-267`) would have enforced. Because `vm_addr` and `len` are attacker-controlled when `syscall_parameter_address_restrictions` is off, this produces an aliased/out-of-bounds `&'a mut [u8]` that can extend far past the actual serialized-input buffer, into adjacent heap memory backing other `MemoryRegion`s (or past the whole allocation), violating the "guest may only access explicitly mapped, bounds-checked regions" invariant. The resulting mutable slice is subsequently written into via `update_callee_account`/`update_caller_account` (`cpi.rs:1108-1327`), giving out-of-bounds read/write, not just an OOB pointer computation.

The `#[case]`-parametrized tests in `cpi.rs` (e.g. `test_update_callee_account_lamports_owner`, `test_update_callee_account_data_writable`) explicitly exercise `(syscall_parameter_address_restrictions, virtual_address_space_adjustments, account_data_direct_mapping)` as three independently-toggleable booleans, including `(false, false, false)`... but none of the visible parametrized cases test the specific combination `(false, true, false)` with an attacker-forged, mismatched `vm_addr`/`len`, which is exactly the gap identified.

### Impact Explanation
If this exact intermediate feature-activation state (`virtual_address_space_adjustments` on, `syscall_parameter_address_restrictions` off, `account_data_direct_mapping` off) is reachable on a live cluster, an unprivileged attacker deploying and invoking their own sBPF program via CPI could construct an `AccountInfo` with a forged `data` pointer/length to obtain a mutable slice that reads/writes host memory outside the account's mapped input region — a real out-of-bounds memory corruption primitive reachable purely through CPI, matching the "memory corruption / out-of-bounds access via CPI" bounty category.

### Likelihood Explanation
Exploitability is entirely contingent on whether `syscall_parameter_address_restrictions` can actually be disabled while `virtual_address_space_adjustments` is simultaneously enabled on a target cluster. I was not able to confirm, within the available tool budget, the feature-set activation ordering/dependency in `feature-set/src/lib.rs` (i.e., whether these are enforced to activate together or whether `syscall_parameter_address_restrictions` always precedes/implies `virtual_address_space_adjustments`). If the runtime guarantees these features are never in that specific split state on mainnet (e.g., they are bundled or activated in a fixed, safe order), this code path is dead and not exploitable in practice. The independent, per-flag parametrization used throughout the test suite in `cpi.rs` suggests the code was written to defensively support arbitrary combinations (consistent with staged feature rollouts), which increases the concern that this state is a real, transient/production-reachable condition rather than purely theoretical.

### Recommendation
Remove the reliance on the `syscall_parameter_address_restrictions` flag for bounds validation inside the `virtual_address_space_adjustments` workaround branch of `get_serialized_data`. Always validate `len` against `address_space_reserved_for_account` unconditionally (not gated by `syscall_parameter_address_restrictions`), and always validate that `vm_addr` matches the caller's expected/serializer-provided address (or otherwise route the final slice construction through a `MemoryMapping`-checked call covering the full `[vm_addr, vm_addr+len)` range) regardless of which of the three flags happen to be enabled.

#[test]
fn test_get_serialized_data_oob_when_restrictions_off() {
    let transaction_accounts =
        transaction_with_one_writable_instruction_account(b"foo".to_vec());
    let account = transaction_accounts[1].1.clone();
    mock_invoke_context!(
        invoke_context, transaction_context, b"instruction data",
        transaction_accounts, 0, &[1]
    );

    let config = Config { aligned_memory_mapping: false, ..Config::default() };
    let memory_mapping =
        unsafe { MemoryMapping::new(vec![/* small input region */], &config, SBPFVersion::V3).unwrap() };

    // Attacker-controlled vm_addr far beyond the actual input region size,
    // and an attacker-controlled len that is not bounded because
    // syscall_parameter_address_restrictions = false.
    let malicious_vm_addr = MM_INPUT_START + 1_000_000; // arbitrary offset
    let malicious_len = 4096usize;                       // arbitrary length

    let result = unsafe {
        CallerAccount::get_serialized_data(
            &memory_mapping,
            true,                 // check_aligned
            malicious_vm_addr,
            account.data().len(), // original_data_len (trusted)
            malicious_len,
            false, // syscall_parameter_address_restrictions = OFF (no addr/len check)
            true,  // virtual_address_space_adjustments = ON (workaround branch taken)
            false, // account_data_direct_mapping = OFF
        )
    };

    // Expected (fixed) behavior: this must fail because malicious_vm_addr/len
    // fall outside the actual input region granted by memory_mapping.
    // Actual (buggy) behavior: succeeds and returns a &mut [u8] whose backing
    // memory lies outside the region validated by MemoryMapping, which can be
    // demonstrated to alias unrelated heap memory under Miri/ASan.
    assert!(result.is_err(), "expected out-of-bounds rejection, got {:?}", result.map(|s| s.len()));
}

        memory_mapping: &solana_sbpf::memory_region::MemoryMapping,
        check_aligned: bool,
        vm_addr: u64,
        original_data_len: usize,
        len: usize,
        syscall_parameter_address_restrictions: bool,
        virtual_address_space_adjustments: bool,
        account_data_direct_mapping: bool,
    ) -> Result<&'a mut [u8], Error> {
        use crate::memory::translate_slice_mut_for_cpi;

        if syscall_parameter_address_restrictions {
            let is_caller_loader_deprecated = !check_aligned;
            let address_space_reserved_for_account = if is_caller_loader_deprecated {
                original_data_len
            } else {
                original_data_len.saturating_add(MAX_PERMITTED_DATA_INCREASE)
            };
            if len > address_space_reserved_for_account {
                return Err(InstructionError::InvalidRealloc.into());
            }
        }
        if virtual_address_space_adjustments && account_data_direct_mapping {
            Ok(&mut [])
        } else if virtual_address_space_adjustments {
            // Workaround the memory permissions (as these are from the PoV of being inside the VM)
            unsafe {
                // SAFETY: Invariants for constructing a mutable reference delegated to the caller.
                let serialization_ptr: &'a mut [u8] = translate_slice_mut_for_cpi::<u8>(
                    memory_mapping,
                    solana_sbpf::ebpf::MM_INPUT_START,
                    1,
                    false, // Don't care since it is byte aligned
                )?;
                Ok(std::slice::from_raw_parts_mut(
                    serialization_ptr
                        .as_mut_ptr()
                        .add(vm_addr.saturating_sub(solana_sbpf::ebpf::MM_INPUT_START) as usize),
                    len,
                ))
            }
        } else {
            unsafe {
                // SAFETY: Invariants for constructing a mutable reference delegated to the caller.
                translate_slice_mut_for_cpi::<u8>(
                    memory_mapping,
                    vm_addr,
                    len as u64,
                    false, // Don't care since it is byte aligned
                )
            }
        }
    }
