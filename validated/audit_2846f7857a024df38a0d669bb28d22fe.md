### Title
Unauthenticated `InternalSendTx` gRPC call reaches `tx_sender` broadcast pipeline when `client_verification=false` - ([File: core/src/rpc/interceptors.rs], [File: core/src/servers.rs])

### Summary
When the aggregator is started with `config.client_verification = false`, `create_grpc_server` wraps the `ClementineAggregatorServer` in `InterceptedService::new(service, Interceptors::Noop)`, and `Noop::call` returns `Ok(req)` for every request with no identity check whatsoever. This means the `Internal`-prefixed RPC `internal_send_tx`, which is designed to be reachable only via the aggregator's own client certificate (enforced through `is_internal()` inside `only_aggregator_and_self`), is left completely open to any caller who can open a TCP connection to the aggregator's gRPC port.

### Finding Description
The intended binding is: **caller_identity(leaf_cert) == our_cert** for any RPC whose `grpc-method` header starts with `"Internal"`, as implemented in `only_aggregator_and_self` in `core/src/rpc/interceptors.rs` (lines 62-69), which is only invoked when the interceptor variant is `Interceptors::OnlyAggregatorAndSelf`.

`create_grpc_server` in `core/src/servers.rs` (lines 106-139) chooses the interceptor purely based on `config.client_verification`:
```
let service = InterceptedService::new(
    service,
    if config.client_verification { OnlyAggregatorAndSelf { .. } } else { Noop },
);
```
`Interceptors::Noop::call` (interceptors.rs line 30) is `Ok(req)` unconditionally — it performs no certificate or method-prefix check at all. When `client_verification=false`, the `is_internal()` gate is never evaluated, so the binding collapses: any unauthenticated peer that reaches the TCP listener satisfies the (nonexistent) check and its request is passed straight to `AggregatorServer::internal_send_tx`, which deserializes `raw_tx` and calls `self.tx_sender.insert_try_to_send` with no additional caller check inside the handler itself (based on the RPC being reachable purely via the interceptor gate).

Because the server's `ServerTlsConfig` in the `client_verification=false` branch only sets `.identity(server_identity)` and never `.client_ca_root(...)`, the TLS handshake does not require or validate a client certificate — an attacker can connect with a bare TLS client (no client cert) and the handshake still succeeds.

### Impact Explanation
This matches the explicitly enumerated High-severity category: "an unauthenticated state-changing or broadcasting call." An attacker with no key share, no TLS certificate, and no relationship to the protocol can insert an attacker-chosen transaction into the aggregator's `tx_sender` scheduling/database pipeline (`insert_try_to_send`), mutating internal protocol state that is meant to be exclusively driven by the aggregator's own signed workflow. This is repeatable per call and does not require a deposit, withdrawal, or any Bitcoin/Citrea interaction — only network reachability to the aggregator's advertised gRPC port.

### Likelihood Explanation
The precondition is that the aggregator is deployed with `client_verification=false`. This is the value documented in the audit prompt as the aggregator's default/documented state, and the code confirms that in this mode `Noop` provides zero protection for `Internal`-prefixed methods (the entire authorization mechanism is `is_internal()` + `OnlyAggregatorAndSelf`, both of which are bypassed). The attacker cost is trivial: opening a TLS connection without presenting a client certificate and issuing one gRPC call; no fees, deposits, or signatures are required to reach the vulnerable code path itself.

### Recommendation
Do not gate `Internal`-prefixed RPC methods solely on the `client_verification` TLS interceptor toggle. Enforce the `is_internal()` restriction unconditionally (i.e., always reject `Internal`-prefixed methods unless a verified peer certificate matching `our_cert` is present, or gate them exclusively at the transport layer via a loopback/Unix-socket-only listener), so that disabling general client TLS verification cannot silently disable the internal-method authorization boundary.

### Proof of Concept
```
// core/src/test/rpc_auth.rs-style harness
#[tokio::test]
async fn unauthenticated_internal_send_tx_succeeds_when_client_verification_false() {
    let mut config = create_test_config().await; // default config
    assert!(!config.client_verification); // documented default

    let (addr, _shutdown) = create_aggregator_grpc_server(config.clone()).await.unwrap();

    // Connect with a bare TLS channel presenting NO client identity
    let channel = Channel::from_shared(format!("https://{addr}"))
        .unwrap()
        .tls_config(ClientTlsConfig::new().ca_certificate(server_ca_cert()))
        .unwrap()
        .connect()
        .await
        .unwrap();

    let mut client = ClementineAggregatorClient::new(channel);
    let raw_tx = attacker_valid_btc_tx_bytes();

    let resp = client
        .internal_send_tx(SendTxRequest { raw_tx, fee_type: FeeType::Cpfp as i32 })
        .await;

    assert!(resp.is_ok(), "unauthenticated caller was rejected: {:?}", resp);

    // Assert binding equality broken: caller had no cert (None) != our_cert, yet request succeeded
    let row_exists = db_has_tx_sender_row_for(&config, &raw_tx).await;
    assert!(row_exists, "attacker tx was inserted into tx_sender pipeline");
}
```
