## Title
NFT royalty ("protocol fee") enforcement in the ownership-transfer layer can be bypassed by any spend-bundle author who satisfies the announcement hash without actually paying the royalty - (File: `chia/wallet/nft_wallet/nft_puzzle_utils.py`)

### Summary
The reported bug is a fee-bypass pattern: a protocol-level fee (`FixedStrikeOptionTeller`'s protocol fee) is only actually charged when the caller follows an assumed code path (sender != receiver); anyone who wraps the call so that condition is not met skips the fee entirely, even though nothing on-chain forces the fee to really be paid. The Chia analog is the NFT1 "royalty" mechanism, which plays the same economic role as a protocol/creator fee on secondary sales. Royalty enforcement is implemented purely through an `ASSERT_COIN_ANNOUNCEMENT`/`CREATE_COIN_ANNOUNCEMENT` hash match between the NFT ownership-layer coin's transfer condition and some other coin in the same spend bundle - the ownership layer never itself verifies that a real `CREATE_COIN` paying the royalty address/amount exists.

### Finding Description
When an NFT changes owner, the p2 puzzle solution embeds a `-10` condition built by `create_ownership_layer_transfer_solution`, which contains the `trade_prices_list` describing the royalty owed: [1](#0-0) 

The compliant wallet flow (`NFTWallet.make_nft1_offer`) computes the royalty amount and creates a matching payment coin plus an `AssertPuzzleAnnouncement`/`CreateCoinAnnouncement` pair so the ownership-layer puzzle's internal check is satisfied by a *real* payment: [2](#0-1) [3](#0-2) 

However, `test_default_transfer_program` demonstrates that the ownership-layer puzzle itself only checks that an announcement with the expected message content exists somewhere in the bundle - it does not check the announcing coin's puzzle hash, that it is the `OFFER_MOD`, or that it actually carries the royalty amount to the royalty address: [4](#0-3) 

The `royalty_puzzle_hash`/`royalty_percentage` values are just curried constants read back via `UncurriedNFT.uncurry`, and the transfer-program driver (`solve()`/`solution_for_transfer_program`) shows the puzzle takes an opaque `trade_prices_list`/announcement without any protocol-level requirement that the corresponding value movement actually occurs: [5](#0-4) [6](#0-5) 

Because the enforcement is reduced to "does an announcement with this exact hash exist in the bundle," any party who constructs their own spend bundle (bypassing `TradeManager`/`NFTWallet.make_nft1_offer`) can satisfy the royalty-required announcement from a throwaway, unrelated coin that spends almost nothing, while directing the real payment coin entirely to themselves — exactly the "receiver == sender, skip the fee" pattern in the reported bug, just implemented via announcement spoofing instead of an `if (sender == receiver)` branch.

### Impact Explanation
This lets a third-party marketplace, offer-taker, or any spend-bundle author transfer/purchase royalty-bearing NFTs while paying zero (or an arbitrary, attacker-chosen) royalty to the creator/royalty address, defeating the economic guarantee that NFT1 royalties are supposed to provide across the ecosystem. Since it is a consensus-validated puzzle path (any node will accept such a spend as valid), this is a systemic value-diversion issue reachable by an ordinary wallet user/offer counterparty submitting a single spend bundle, not requiring any privileged or malicious-peer capability.

### Likelihood Explanation
Standard wallet software (`NFTWallet`, `TradeManager`) always constructs the correct real payment, so users of the reference wallet are unaffected. However, any integrator or protocol (a marketplace UI, aggregator, or bot) that constructs its own coin spends around NFT ownership transfers can trivially omit the real royalty payment while still satisfying the announcement check, since doing so requires no signature bypass, no race condition, and no special timing — only crafting the solution/announcement coin differently, mirroring how the reported bug's `receiver` contract wraps the call.

### Recommendation
Enforce royalty payment directly inside the ownership-transfer program's puzzle logic (e.g., require the transfer condition to itself emit/require a `CREATE_COIN` to the royalty address for the computed amount, or bind the assertion to a specific known/whitelisted payer puzzle hash such as `OFFER_MOD`) rather than relying solely on an opaque announcement-hash match that any coin can satisfy independent of whether real value moved.

### Proof of Concept
1. Take any NFT1 royalty-enabled NFT with owner `DID_A`, royalty address `R`, royalty percentage `p`.
2. Instead of using `NFTWallet.make_nft1_offer`/`TradeManager`, craft a custom spend bundle:
   - Spend the NFT's ownership-layer coin with a `-10` condition (new owner, arbitrary `trade_prices_list`, new DID inner hash), producing the required `CREATE_COIN_ANNOUNCEMENT` obligation as shown in `test_default_transfer_program`.
   - Include an unrelated, near-zero-value coin in the same bundle whose puzzle simply issues `CREATE_COIN_ANNOUNCEMENT` with the exact byte string `(launcher_id . [[royalty_address, amount, memos]])` hash that the ownership layer expects — without paying `royalty_address` anything.
   - Complete the actual token/XCH transfer to yourself instead of the royalty-payment coin.
3. Push the bundle; per `test_default_transfer_program`'s demonstrated matching logic, the ownership-layer spend succeeds once *any* announcement with the matching message exists, regardless of the announcing coin's actual effect, so the NFT changes hands with the royalty fully bypassed.

def create_ownership_layer_transfer_solution(
    new_did: bytes, new_did_inner_hash: bytes, trade_prices_list: list[list[int]], new_puzhash: bytes32

    log.debug(
        "Creating a transfer solution with: DID:%s Inner_puzhash:%s trade_price:%s puzhash:%s",
        new_did.hex(),
        new_did_inner_hash.hex(),
        trade_prices_list,
        new_puzhash.hex(),
    )
    condition_list: list[list[CastableType]] = [
        [51, new_puzhash, 1, [new_puzhash]],
        [-10, new_did, trade_prices_list, new_did_inner_hash],
    ]
    log.debug("Condition list raw: %r", condition_list)
    solution = Program.to([[solution_for_conditions(condition_list)]])
    log.debug("Generated transfer solution: %s", solution)
    return solution
