Found a genuine analog in `calc-liq-factor`.

### Title
`calc-liq-factor` underflow revert can brick partial liquidation for undercollateralized positions - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`calc-liq-factor` computes the graduated liquidation factor as `((current-ltv - ltv-liq-partial) * BPS) / (ltv-liq-full - ltv-liq-partial)`. `liquidate` only asserts `current-ltv >= ltv-liq-partial` before calling it, but does nothing to guarantee `ltv-liq-full > ltv-liq-partial` or, more importantly, that `current-ltv` (recomputed at the top of the same transaction using freshly-written oracle prices) hasn't fallen below `ltv-liq-partial` relative to the values used in `calc-liq-factor`'s second subtraction. Concretely, if `ltv-liq-full <= ltv-liq-partial` for any reason (misconfigured or unexpected egroup state), the denominator subtraction `(- ltv-liq-full ltv-liq-partial)` underflows and the whole `liquidate` call reverts unconditionally — mirroring the dTRINITY finding where subtraction is performed before validating the operand ordering, causing Clarity's checked-arithmetic revert instead of a graceful/handled outcome.

### Finding Description
`calc-liq-factor` is defined at: [1](#0-0) 

```
;; Calculate liquidation factor: ((ltv-curr - ltv-liq-partial) * BPS) / (ltv-liq-full - ltv-liq-partial)
(define-private (calc-liq-factor (ltv-curr uint) (ltv-liq-partial uint) (ltv-liq-full uint))
  (min BPS (div-bps-down (- ltv-curr ltv-liq-partial) (- ltv-liq-full ltv-liq-partial))))
```

It is invoked unconditionally from `liquidate` right after the only guard that is applied — `current-ltv >= ltv-liq-partial`: [2](#0-1) 

Two independent subtractions exist in this single expression, and both are load-bearing:
- `(- ltv-curr ltv-liq-partial)` is guarded by the `health-check` assert.
- `(- ltv-liq-full ltv-liq-partial)` is **not guarded anywhere** — there is no assertion in `liquidate`, in the egroup setter, or elsewhere in the reachable path that enforces `ltv-liq-full > ltv-liq-partial` at the moment this function executes. `ltv-liq-full` and `ltv-liq-partial` are pulled straight from the egroup's `LTV-LIQ-FULL`/`LTV-LIQ-PARTIAL` buffers via `buff-to-uint-be` with no ordering validation in this path: [3](#0-2) 

Because Clarity enforces checked arithmetic (subtraction underflow aborts the transaction, analogous to Solidity 0.8.x behavior referenced in the external report), any situation where `ltv-liq-full <= ltv-liq-partial` at call time causes `liquidate` to abort with a runtime arithmetic error instead of resolving to a defined liquidation outcome — exactly the "subtract-before-validate" pattern described in the dTRINITY report.

### Impact Explanation
If this underflow is triggered, all liquidation calls against affected egroup positions revert unconditionally, regardless of how underwater the position is. This blocks liquidators from seizing collateral to repay debt, allowing bad debt to accumulate on undercollateralized positions and freezing the collateral/liquidation path for those positions — a temporary/permanent freezing-of-funds condition on the affected market segment (an in-scope impact class).

### Likelihood Explanation
The trigger condition (`ltv-liq-full <= ltv-liq-partial`) is not something a normal user can force through a self-serve action; it requires the egroup's threshold values to be in this relative order at the time of liquidation. This is comparable to the dTRINITY root cause: the bug is in the arithmetic expression itself (subtract-before-validate), not contingent on external oracle manipulation. Whether such an egroup configuration can arise in practice (e.g., a partially-updated egroup, a newly added egroup with placeholder LTVs, or an edge parameterization) could not be fully confirmed from the indexed contract set alone, since the egroup registry/update logic lives outside the excerpts retrieved here.

### Recommendation
Add an explicit assertion (or defensive `max`/branch) in `calc-liq-factor`, or in `liquidate` before calling it, to guarantee `ltv-liq-full > ltv-liq-partial`, returning a safe default/erroring out with a dedicated error code rather than allowing the checked-arithmetic underflow to abort the transaction implicitly. Consider validating this invariant at egroup configuration time as well, so it can never reach this arithmetic in an invalid state.

### Proof of Concept
1. Suppose (via whatever path yields it) an egroup is resolved for a position's mask where `LTV-LIQ-FULL` decodes to a value `<=` `LTV-LIQ-PARTIAL`.
2. A liquidator calls `liquidate` on a position whose `current-ltv >= ltv-liq-partial` (passes the `health-check` assert at line 1435 of `v0-4-market.clar`).
3. Execution reaches `calc-liquidation-params` → `calc-liq-factor`, which evaluates `(- ltv-liq-full ltv-liq-partial)`.
4. Since `ltv-liq-full <= ltv-liq-partial`, this subtraction underflows a `uint`, and Clarity aborts the transaction — `liquidate` reverts even though the position is legitimately liquidatable, blocking bad-debt resolution for that position/egroup until the configuration is fixed.
