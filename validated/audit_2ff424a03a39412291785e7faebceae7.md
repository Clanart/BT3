### Title
Relayer fee withdrawal permanently locks funds if destination-side disbursement reverts, since the source-chain balance is zeroed before delivery succeeds and the message never times out - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
This mirrors the LP wrapper bug class: an action zeroes/advances local state assuming a paired external action (redeposit/disbursement) will succeed, but that paired action can permanently fail, and there is no emergency-withdraw/re-credit path to recover the funds.

### Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads the relayer's `available_amount` from `Fees`, dispatches a zero-timeout ISMP POST to the destination's `HostManager` (EVM) or `HYPERBRIDGE_MODULE_ID` (Substrate) instructing it to disburse the funds, and then unconditionally zeroes `Fees` for that `(dest_chain, address)` once the dispatch call succeeds [2](#0-1) . The dispatch only guarantees the message was *queued*; the payout itself happens later and asynchronously when a relayer delivers it to the destination chain [3](#0-2) .

On the EVM side, `EvmHost.withdraw()` (invoked via `HostManager.onAccept`) executes the disbursement: for the native-token path it does `(bool sent,) = params.beneficiary.call{value: params.amount}("")`, and reverts the entire request delivery with `WithdrawalFailed()` if the call fails [4](#0-3) . Because the withdrawal `DispatchPost` is created with `timeout: 0` [5](#0-4) , the request can never expire and be re-dispatched with different parameters from the source chain — exactly like the LpWrapper case where the withdraw path silently depends on a paired action (deposit back into Core/gauge) that can permanently fail once state has already been mutated.

If that destination-side transfer reverts on every delivery attempt (e.g., the ABI-encoded `beneficiary_address` resolves to a contract/address that cannot accept the native asset, or the `EvmHost` lacks sufficient balance of the disbursed token to complete `IERC20.safeTransfer`/native `call`), the request commitment is simply never satisfied. Since `Fees` was already zeroed on Hyperbridge at withdrawal time, and the pallet exposes no admin/emergency function to re-credit `Fees` or reconstruct the withdrawal with a corrected beneficiary, the relayer's accrued revenue is permanently unrecoverable.

### Impact Explanation
This is a direct loss-of-funds path: a relayer's entire withdrawable balance for a chain can become permanently stranded with no on-chain recovery mechanism, matching the "loss of funds" category explicitly accepted by the impact gate. Unlike a griefing scenario, this can also be triggered unintentionally at scale (e.g. a host running low on the fee token, or a beneficiary contract whose `receive()`/fallback later starts reverting), since the failure mode is silent until delivery is attempted and cannot be reversed once `Fees` is zeroed.

### Likelihood Explanation
Likelihood is moderate: the beneficiary is chosen by the withdrawing relayer themselves via `WithdrawalInputData.beneficiary` [6](#0-5) , so a self-inflicted misconfiguration (wrong/incompatible beneficiary address, or later loss of the destination `EvmHost`'s token balance) is enough to trigger it — no malicious peer, relayer collusion, or governance action is required.

### Recommendation
Do not zero `Fees` until the destination-side disbursement is confirmed, or add an explicit reconciliation/emergency-recredit path (analogous to an "emergency withdraw") that lets a relayer reclaim `Fees` for a commitment whose withdrawal request can be proven undelivered/permanently failed (e.g., via a timeout with a non-zero value, or a governance-gated re-credit keyed by the original commitment, guarded against double-crediting the same commitment).

### Proof of Concept
1. Relayer accrues fees on Hyperbridge for `dest_chain = Evm(X)`.
2. Relayer calls `withdraw_fees` with a `beneficiary` address that is a contract with no payable `receive()`/`fallback()` (or one that reverts), targeting the native-token disbursement path.
3. `Pallet::withdraw` dispatches the zero-timeout `WithdrawalParams` POST and zeroes `Fees::<T>::insert(dest_chain, address, U256::zero())` [7](#0-6) .
4. Any relayer attempts to deliver the request; `EvmHost.withdraw()`'s native `.call{value: amount}("")` fails and reverts with `WithdrawalFailed()` [8](#0-7) .
5. Because `timeout == 0`, the request never becomes eligible for a timeout/refund path, and `pallet-ismp-relayer` has no call to re-credit `Fees` for that commitment — the withdrawn amount is permanently stuck.

**Caveat:** I was unable to fully trace whether pallet-ismp's generic message-retry/DLQ tooling (outside `pallet-ismp-relayer`) offers any way to re-target a stuck zero-timeout request's beneficiary after initial dispatch; if such generic tooling exists elsewhere in `pallet-ismp` it could partially mitigate this, but no such mechanism was found within the relayer pallet itself.

//! Relayer fee withdrawal.
//!
//! Once fees have been accumulated into [`crate::pallet::Fees`] by
//! [`crate::accumulate`], relayers withdraw them via [`Pallet::withdraw`].
//! The flow:
//!
//! 1. The relayer signs a `(nonce, dest_chain, beneficiary?)` payload with their per-chain key (EVM
//!    secp256k1 / sr25519 / ed25519).
//! 2. The pallet verifies the signature, increments the per-relayer nonce, and dispatches an ISMP
//!    POST request to the destination's host manager (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate)
//!    instructing it to disburse `available_amount` of the fee token to the beneficiary.
//! 3. The `Fees` entry is zeroed so the same balance cannot be withdrawn twice.
//!
//! The on-chain effect is just dispatching the message; the destination chain settles the
//! payout when the ISMP request is delivered there.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
