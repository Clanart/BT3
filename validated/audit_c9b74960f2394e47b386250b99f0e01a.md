### Title
Uncontrolled recursion in `PuzzleWithRestrictions.from_memo()` when parsing attacker-controlled coin memos causes wallet sync denial of service - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` recursively parses the `MofN` member tree embedded in a `CREATE_COIN` memo blob, with no bound on nesting depth. Because this parser is invoked automatically during PlotNFT/singleton wallet sync on data taken directly from an on-chain coin's memo (fully attacker-controlled), a malicious singleton spend that creates a coin with a deeply nested `MofN` memo can drive unbounded Python recursion in a victim's wallet process, crashing or hanging the wallet sync loop — the same "uncontrolled recursion causing sustained denial of service" bug class as JLSEC-2026-606.

### Finding Description
`PuzzleWithRestrictions.from_memo()` reconstructs an unknown custody puzzle tree from a CLVM memo `Program`. When the memo indicates "further branching" (an `MofN` node), it recursively calls itself once per member memo: [1](#0-0) 

```
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```

There is no depth limit, no cap on the number of `member_memos`, and no bound enforced by the CLVM cost metering — this is pure Python recursion executed *after* the CLVM run has produced the memo `Program`, so it is not gated by `MAX_BLOCK_COST_CLVM` in the way the mempool's Rust CLVM execution is. Each nesting level only costs a small, cheap CLVM list to construct in the on-chain memo (`(m [member_memo, member_memo, ...])`), so an attacker can cheaply construct a memo blob whose `MofN` nodes nest thousands of levels deep.

This parser is not a debug-only or test-only utility. It is reached in production wallet sync code for `PlotNFT` (pool/plotNFT v2) wallets: [2](#0-1) 

`PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` whenever it cannot recognize the new singleton inner puzzle by re-deriving it from known state — i.e., whenever a singleton spend's inner puzzle change isn't the mundane "rev"/pool-transition case. This is called from `PlotNFT2Wallet.identify()` during coin-state processing: [3](#0-2) 

`identify()` is invoked by `WalletStateManager` while processing incoming coin states for any singleton-shaped coin that looks like it could be a PlotNFT (matched by singleton launcher hash / mod, not by ownership), before ownership is even confirmed via `user_key_is_owned`. Any full node peer serving coin states to a wallet, or any wallet syncing the chain, will therefore invoke `from_memo()` on the attacker-crafted memo of any coin matching the PlotNFT singleton pattern.

Because the memo content is taken verbatim from the coin's `CREATE_COIN` third argument (fully controlled by whoever authored the spending puzzle/solution), an attacker only needs to submit one ordinary spend bundle that creates a singleton-shaped coin with a deeply nested `MofN` memo. No signature over the memo's semantic validity is required for the recursive parse to be attempted — `from_memo()` runs before any further validation that would reject the coin as "not actually a valid PlotNFT."

The custody architecture code comments even acknowledge this is a known recursive design (".cursor/context/testing/clvm.md" notes "`from_memo()` must reconstruct unknown members/restrictions, including recursive `MofN`"), but no recursion-depth guard was added, unlike `sha256_treehash`, which the codebase explicitly redesigned to be iterative specifically "so we don't have to worry about blowing out the python stack": [4](#0-3) 

`from_memo()` has no equivalent iterative rewrite or depth cap.

### Impact Explanation
A successful exploitation causes a Python `RecursionError` (or, on some platforms, a native stack overflow / process crash) inside the wallet's coin-state processing path (`WalletStateManager._add_coin_state` → `PlotNFT2Wallet.identify` → `PlotNFT.get_next_from_coin_spend` → `PuzzleWithRestrictions.from_memo`). Since this runs inside the core wallet sync loop, an unhandled `RecursionError` there can abort processing of the batch of coin updates, repeatedly interrupt sync (if the offending coin keeps being re-delivered), or crash the wallet process — a spend-triggered transaction-processing halt matching the "sustained denial of service" impact called out in the reference CVE. This affects any Chia wallet (including those belonging to unrelated users) that syncs past a block containing such a maliciously memoized coin, since `identify()` inspects all singleton-shaped coins, not just coins already known to belong to the wallet's tracked PlotNFTs.

### Likelihood Explanation
Likelihood is high for any attacker capable of submitting a standard spend bundle: constructing a singleton coin with a curried MofN-shaped puzzle and a matching deeply-nested memo requires no special privileges, keys, or mempool cost beyond what a normal transaction allows (CLVM cost to build nested lists is cheap relative to `MAX_BLOCK_COST_CLVM`). The victim does not need to interact with the attacker's coin in any special way — ordinary chain sync triggers the vulnerable code path via `identify()`'s speculative matching against the PlotNFT singleton mod hash.

### Recommendation
Rewrite `PuzzleWithRestrictions.from_memo()` (and its recursive helper `MofN` construction) to use an explicit iterative work-stack, following the same non-recursive pattern already used in `sha256_treehash()` (`chia/types/blockchain_format/tree_hash.py`). At minimum, enforce and validate a maximum nesting depth and a maximum member count for `MofN` hints before recursing, rejecting memos that exceed sane on-chain custody-architecture limits (e.g., depth/width bounds already implicitly enforced by `MofN.__post_init__`'s `m <= n` check, but with no ceiling on `n` or on nested depth). Also audit other recursive puzzle-tree walkers reachable from untrusted on-chain data (e.g., `fill_in_unknown_puzzles`, `unknown_puzzles` property, `MofNMerkleTree._m_of_n_proof`) for the same unbounded-depth issue.

### Proof of Concept
1. Construct a CLVM memo `Program` matching `PuzzleWithRestrictions`'s spec: `(spec_namespace [nonce restriction_hints 1 (m [member_memo_1, ...])])` where `further_branching_prog` is truthy (non-nil), making `from_memo` recurse.
2. Set each `member_memo_i` to itself be a valid nested `MofNHint`-shaped memo with `further_branching=1`, repeating this nesting to a depth of tens of thousands of levels (e.g., a single-member chain `MofN(m=1, members=[MofN(m=1, members=[...])])`), which is cheap to construct programmatically and cheap to include as CLVM list data in a `CREATE_COIN` memo.
3. Submit a spend bundle whose puzzle reveal curries the standard singleton mod (`SINGLETON_TOP_LAYER_MOD`/`cls.singleton_puzzles.singleton_mod`) with the correct launcher-hash shape so that `singleton.mod == cls.singleton_puzzles.singleton_mod` in `PlotNFT.get_next_from_coin_spend`, and whose inner-puzzle output includes exactly one `CREATE_COIN` condition with `memo_blob` set to the crafted deep memo from step 2.
4. Have this spend bundle accepted into a block (a normal, validly-signed spend is sufficient; the memo payload itself is not consensus-validated beyond being CLVM data).
5. Any wallet syncing past this block will invoke `WalletStateManager._add_coin_state` → `PlotNFT2Wallet.identify()` → `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`, triggering unbounded Python recursion and a `RecursionError`/crash in the wallet sync path.
