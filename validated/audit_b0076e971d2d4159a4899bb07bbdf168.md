### Title
`DeleteTokenPair` on a self-destructed native ERC20 removes the token mapping without checking outstanding minted coin supply, permanently freezing escrowed tokens / leaving unbacked coins in circulation - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertERC20` and `ConvertCoin` both contain a "cleanup" branch that deletes a native-ERC20 `TokenPair` entirely whenever the underlying EVM account has no code hash (i.e. the contract self-destructed). This mirrors the reported `unregisterSingularity()` bug: state that maps a registered asset to the rest of the accounting system is deleted without verifying that no user value is still outstanding against it.

### Finding Description
For a "native ERC20" token pair (`ContractOwner == OWNER_EXTERNAL`), users escrow real ERC20 tokens into the module account and receive newly minted native coins via `convertERC20IntoCoinsForNativeToken`: [1](#0-0) 

Later, any account can trigger `ConvertERC20`/`ConvertCoin` again for that same pair. Both handlers check whether the paired ERC20 contract still has code, and if not, delete the entire token pair mapping (denom map, ERC20 map, allowances) without any check of the escrowed/outstanding balance: [2](#0-1) [3](#0-2) 

`DeleteTokenPair` itself performs an unconditional deletion of the pair, its denom/ERC20 index entries, and its allowances, with no check on the amount of native coin already minted or ERC20 balance still escrowed at `types.ModuleAddress`: [4](#0-3) 

Because the ERC20 contract's balances live entirely in its own contract storage, a self-destruct of that contract (code+storage cleared) destroys the escrowed token balance held for the module account, while any native coins that were already minted against earlier `ConvertERC20` calls remain fully valid and spendable in the bank module. Once the pair is deleted:
- `MintingEnabled` (used by both `ConvertCoin` and `ConvertERC20`) looks up the pair by denom/address via `GetTokenPairID`/`GetTokenPair`, which will now fail with `ErrTokenPairNotFound`: [5](#0-4) 
- This makes it permanently impossible to convert back to ERC20, and there is no invariant check anywhere in `DeleteTokenPair`/`ConvertERC20`/`ConvertCoin` ensuring the total minted coin supply for that denom is zero before deleting the mapping (the analog of the missing `totalDeposited == 0` check in the reported finding).

Net effect: holders of the native coin denom retain fully transferable, spendable value with no backing ERC20 tokens remaining (since the backing contract's storage was wiped by self-destruct), while the escrow mechanism that would normally let the system reconcile is permanently deleted. This is an irreversible accounting break between the native coin representation and its ERC20 backing.

### Impact Explanation
This falls under "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value" — native coins minted 1:1 against an ERC20 escrow remain valid and spendable after the ERC20 side is destroyed and its registration deleted, so the coin supply is no longer backed by any real value, and there is no mechanism to reconcile or unwind this. It simultaneously matches "permanent freezing of escrowed assets" for any real backing that did exist, since deletion removes the only path (`ConvertCoin`) to recover it.

### Likelihood Explanation
`RegisterERC20` is permissionless when `params.PermissionlessRegistration` is enabled, allowing any user to register an arbitrary ERC20 contract as a native-ERC20 pair: [6](#0-5) 
An attacker fully controlling such a contract's bytecode can arrange for the contract to self-destruct (clearing code and storage under EIP-6780 semantics when triggered within the contract-creation transaction, or via any other path that zeroes its code hash), after having escrowed tokens/minted coins through legitimate `ConvertERC20` calls. This requires no privileged access — it is reachable by any ordinary user through the standard `MsgConvertERC20`/`MsgRegisterERC20` message flow.

### Recommendation
Before deleting a token pair in the "self-destructed contract" branches of `ConvertERC20`/`ConvertCoin` (and in `DeleteTokenPair` generally), verify that the outstanding native coin supply for `pair.Denom` (via `bankKeeper.GetSupply`) and/or the escrowed ERC20 balance held at `types.ModuleAddress` are zero. If not, refuse the deletion (or route to a safe/paused state) instead of silently wiping the mapping, analogous to adding a `totalDeposited == 0` guard before `unregisterSingularity()` deletes state in the original report.

### Proof of Concept
1. With `PermissionlessRegistration` enabled, attacker deploys a malicious ERC20 contract and calls `MsgRegisterERC20` to create a native-ERC20 `TokenPair` (`ContractOwner = OWNER_EXTERNAL`).
2. Attacker calls `MsgConvertERC20` to escrow tokens to `types.ModuleAddress` and mint themselves native coins via `convertERC20IntoCoinsForNativeToken`.
3. Attacker triggers the contract to self-destruct, clearing its code and storage (zeroing the escrowed balance recorded in the contract's own storage).
4. Attacker (or anyone) calls `MsgConvertERC20`/`MsgConvertCoin` again for the same pair; since `acc.HasCodeHash()` is now false, `DeleteTokenPair` is invoked, wiping the denom map, ERC20 map, and allowances with no supply check.
5. The native coins minted in step 2 remain fully valid, transferable, and spendable in the bank module, with no backing ERC20 tokens and no way to reconcile, since the token pair no longer exists.

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

		ctx.EventManager().EmitEvent(
			sdk.NewEvent(
				types.EventTypeRegisterERC20,
				sdk.NewAttribute(types.AttributeKeyCosmosCoin, pair.Denom),
				sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
			),
		)
	}

	return &types.MsgRegisterERC20Response{}, nil

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}
