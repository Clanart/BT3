### Title
`ReceivedOutput::read` accepts an offset scalar that is never bound to the output's `script_pubkey`, so deserialized "received" outputs can claim spendability under an unrelated key offset - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to `reviewsByStatus[recipientId][status]` recording votes that are never bound to the recipient content they target, `ReceivedOutput` records an `offset` scalar alongside a `TxOut`/`OutPoint` without any check that the output actually pays to `key + offset * G`. `scan_transaction` only produces pairs where this invariant holds (it looks up `output.script_pubkey` in `scripts`, the map built by `register_offset`), but `ReceivedOutput::read` - an explicitly listed untrusted-bytes sink - decodes `offset`, `TxOut`, and `OutPoint` independently and returns them as an authoritative `ReceivedOutput`. The recorded state (the offset needed to spend) is not bound to the content it describes (the output being spent), exactly like votes not being bound to the recipient version they were cast on.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` where each script was derived as `p2tr(key + offset * G)` with evenness enforced by `register_offset` (`networks/bitcoin/src/wallet/mod.rs:180-196`). `scan_transaction` therefore only yields `ReceivedOutput`s where `offset` genuinely derives the output's script (`mod.rs:199-214`). However, `ReceivedOutput::read` (`mod.rs:122-134`) deserializes the three fields with `Secp256k1::read_F`, `TxOut::consensus_decode`, and `OutPoint::consensus_decode` and performs no consistency check - it has no access to the scanner's key and never recomputes `p2tr_script_buf(key + offset * G) == output.script_pubkey`. The offset is also not bound to the base key at all, so the same serialized blob is "valid" under any key.

### Impact Explanation
An unprivileged party that can feed bytes to `ReceivedOutput::read` (listed as an untrusted-input sink) can fabricate an output that reports itself spendable under an arbitrary offset while its `script_pubkey` pays elsewhere - e.g., an output paying to an attacker-controlled script presented with `offset = 0`. Any consumer treating the deserialized `ReceivedOutput` as a spendable wallet input will construct a `SignableTransaction` whose Schnorr/Taproot signature cannot authorize the spend: the signature commits over `Prevouts::All`, but the prevout's script requires a different key (or the prevout doesn't exist at all). Result: funds reported received that are not spendable - one of the accepted impact classes - and fee value burned into a transaction that can never be validly signed to spend that input.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary (they have `read`/`write`/`serialize` specifically for transport and persistence, and `read` is enumerated as a public untrusted-bytes entry point). The attacker needs only to craft `32 bytes || TxOut || OutPoint`; no key knowledge, collusion, or validator misbehavior is required. Severity is bounded by how consumers use deserialized outputs rather than scanner-produced ones.

### Recommendation
Either restrict `ReceivedOutput::read` to contexts where the scanner's key is available and verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)` (returning an error otherwise), or store the full tweaked key/script alongside the offset and check it on deserialization. At minimum, document that `read` produces an unauthenticated pairing and must be re-validated against `Scanner::scan_transaction` results before being used as a spendable input.

### Proof of Concept
1. Construct `TxOut { value: 50_000, script_pubkey: <attacker's P2TR script> }` and any real `OutPoint` the attacker controls.
2. Serialize `Scalar::ZERO.to_repr() || serialize(txout) || serialize(outpoint)` and pass it to `ReceivedOutput::read` - it succeeds.
3. The resulting `ReceivedOutput` reports `offset() == 0` and `value() == 50_000`, indistinguishable from an output genuinely paying to the base key (`scripts` maps the base script to `Scalar::ZERO` at `mod.rs:164`).
4. Passing it into `SignableTransaction::new` as an input produces a transaction that appears funded; the threshold signature over it cannot satisfy the actual script, so the "received" funds are unspendable - mirroring how `reviewsByStatus` accumulates votes that no longer correspond to the recipient content they were cast on.

Caveat: I was unable to trace every consumer of `ReceivedOutput::read` within the remaining tool iterations, so the in-scope reachability of the fabricated output into signing is asserted from the deserialization API's existence rather than a specific call site; consumers that only ever use scanner-produced outputs are unaffected.
