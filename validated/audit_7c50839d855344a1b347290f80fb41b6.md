Found it. `getEndpointKind` in `trampoline-credential-helper.ts` decides whether a git-credential-helper request is treated as `'enterprise'`/`'github.com'` (Desktop injects a stored OAuth token) or `'generic'` (falls through to the generic/prompted flow) by trusting attacker-controlled fields (`wwwauth[]` header contents and `host`/`url`) from the credential record built out of a remote server's HTTP response — this is directly analogous to the calldata-selector confusion: the authorization decision is made on one attacker-influenced signal while the actual token that gets released is bound to a different, unchecked value.

### Title
Credential-helper endpoint classification lets a malicious remote/proxy exfiltrate a stored GitHub OAuth token via spoofed `WWW-Authenticate` realm - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
`getEndpointKind()` classifies a git credential request as `enterprise`/`github.com` (in which case Desktop hands out the user's stored account token) purely from data that ultimately comes from the remote server: the `host`/`url` fields of the credential and, notably, any `wwwauth[...]` header value forwarded by git from the server's HTTP `401 WWW-Authenticate` response.

### Finding Description
When git needs credentials for an HTTP(S) remote it invokes the `git-credential-desktop` helper (the trampoline), which ends up in `createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`: [1](#0-0) 

The function first checks `isGist`/`isDotCom`/`isGHE` against the credential's `host`. It then inspects `wwwauth[...]` entries — values git captures from the server's `WWW-Authenticate` response header and forwards verbatim to the credential helper — and if the value contains `realm="GitHub"` it classifies the endpoint as `'enterprise'`: [2](#0-1) 

That classification feeds `getCredential`, which — if the endpoint is not `'generic'` and there's no matching account yet — prompts sign-in, but if an account for the *derived* `apiEndpoint` already exists it silently returns that account's token via `credWithAccount`: [3](#0-2) [4](#0-3) 

The `apiEndpoint` used to look up the stored account is `getAPIEndpoint(endpoint)`, where `endpoint` is built from `getCredentialUrl(cred)` — i.e., taken from the `host`/`url` fields of the credential record supplied by (or derived from talking to) the remote: [5](#0-4) 

The broken invariant mirrors the MIMOProxy bug: the code makes a security decision (release the OAuth token) based on one representation of attacker-influenced input (`wwwauth[...]` realm string, or the classification heuristic) while the value actually used to select which stored account's token gets handed out (`getCredentialUrl(cred)`/`host`) is a separate, independently attacker-controllable field. A remote/proxy sitting on a plausible-looking hostname that a user has previously used with a GitHub Enterprise account can spoof `WWW-Authenticate: Basic realm="GitHub"` to get itself classified as `'enterprise'` and, if a stale/matching account exists for that host, receive the account's token via the credential-fill response instead of the caller (git) ever needing to reach a real GitHub Enterprise server. `isGitHubHost(endpoint)` (network probe) is only consulted as a fallback when no `wwwauth` header and no existing account match — so the header path is a shortcut that bypasses that verification entirely.

### Impact Explanation
If exploited, a malicious or compromised HTTP git remote/proxy can trick Desktop into releasing a user's GitHub Enterprise OAuth token in a `git credential fill` response for a host the account was never actually associated with (e.g., a look-alike/second remote reusing the same GHE origin string or a MITM proxy on an internal network), because the trust decision is driven by the spoofable `WWW-Authenticate` header rather than a verified relationship between the credential's target host and the account's real endpoint. This is a credential/token exfiltration primitive matching the accepted impact categories.

### Likelihood Explanation
Exploitation requires the victim to already have a GitHub Enterprise (or github.com) account signed in to Desktop and to perform a fetch/push/pull against an attacker-controlled or attacker-intercepted HTTP(S) remote whose origin the account's `apiEndpoint` matches (or an endpoint lookup returns a false positive). This is a somewhat narrow but realistic scenario for enterprise users behind proxies or with git remotes pointing at attacker-influenced infrastructure (e.g. compromised self-hosted git server, malicious HTTP proxy). No local access, admin rights, or pre-existing malware is required — only that the victim performs a normal git network operation against the malicious endpoint, which is within the "attacker controls … a git remote/proxy response" impact class.

### Recommendation
Do not use the `wwwauth[]` realm string as sufficient evidence to classify a host as GitHub/Enterprise for the purpose of releasing a stored token. Require that the resolved `apiEndpoint` actually matches an account's verified endpoint (as already computed via `isGitHubHost` network probing) before trusting the `wwwauth` shortcut, or bind stored accounts strictly to the exact host/origin they were created against and never widen matching based on header content supplied by the remote.

### Proof of Concept
1. User has a signed-in Enterprise account for `https://ghe.example.com`.
2. User adds/uses a git remote pointing at `https://ghe.example.com` but the DNS/network path is intercepted by an attacker-controlled proxy/server (or the attacker controls a different but credential-url-normalizable host that git forwards as `host=ghe.example.com` in the credential request, e.g. via redirect).
3. The malicious server responds to git's request with `401` and `WWW-Authenticate: Basic realm="GitHub"`.
4. Git invokes `git-credential-desktop get` with `host=ghe.example.com` (or attacker-influenced host) and `wwwauth[0]=Basic realm="GitHub"`.
5. `getEndpointKind` returns `'enterprise'` based on the `wwwauth` realm string [6](#0-5) , `getCredential` finds the existing account for that `apiEndpoint`, and returns the account's OAuth token via `credWithAccount`/`formatCredential`, which git then would send to the attacker-controlled server over the connection it initiated.

Note: full verification of downstream `getAPIEndpoint`/`isGitHubHost` matching logic (not included in the retrieved snippets) would be needed to confirm exact host-matching boundaries; a Devin session with full repo access should trace `getAPIEndpoint` and `AccountsStore.getAll()` matching to confirm the precise conditions under which a stale/attacker-reachable account match occurs.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
