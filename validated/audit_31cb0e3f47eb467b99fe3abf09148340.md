### Title
Hookify `PreToolUse` block rules are trivially bypassed because the security decision is computed from the *literal* `tool_input.command` string, not the command Bash actually executes - ([File: plugins/hookify/core/rule_engine.py])

### Summary
The Hookify plugin lets a project define `block`/`warn` rules (e.g. "block `rm -rf`") that are evaluated by `RuleEngine._rule_matches()` via a regex `search` on the raw `tool_input.command` string supplied by the model/agent turn [1](#0-0) . Exactly like the Timeswap `borrow()` bug — where the state-mutating value (`pool.state.z`) was taken from a user-supplied field (`zIncrease`) instead of the value actually used/enforced (the computed collateral) — Hookify's "blocked" decision is derived from the declared textual command rather than from the command Bash will actually interpret and run. Because shell syntax (`$IFS`, variable indirection, quoting, globbing, `eval`, base64/`$(...)`) lets the literal string diverge arbitrarily from the executed semantics, the enforced value (regex match on literal text) and the real value (what Bash executes) are provably decoupled, so the guard can be defeated while the dangerous action still executes.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` reads the `tool_name`/`tool_input` JSON that Claude Code is about to send to the Bash tool, loads project-defined rules, and calls `RuleEngine.evaluate_rules()` [2](#0-1) . `evaluate_rules()` returns `permissionDecision: "deny"` when a `block` rule's condition matches [3](#0-2) . The match itself is a plain `re.search(pattern, tool_input['command'])` [4](#0-3) [1](#0-0) .

The plugin's own documented example rule is:
```
pattern: rm\s+-rf|dd\s+if=|mkfs|format
action: block
``` [5](#0-4) 

This is the exact same trust-boundary flaw as the Timeswap report: the value that gates the security-critical outcome (deny/allow) is the *declared* command text, while the value that actually determines impact (what the shell interprets and runs) is computed independently by Bash at execution time and can be made arbitrarily different from the declared text — e.g. `r''"m"'' -r''f'' ~`, `a=rm;b='-rf';$a $b ~`, `IFS=x;rm${IFS}-rf${IFS}~`, or `eval "$(echo cm0gLXJmIH4= | base64 -d)"`. None of these literal strings match `rm\s+-rf`, so `_rule_matches` returns `False` and Hookify emits `{}` (i.e., silently allows) [6](#0-5) , yet Bash still deletes the filesystem. The same class of bypass applies to the `Bash(...)` pattern-based deny rules shown throughout the hook-development docs (`^(ls|pwd|echo|date|whoami)$`-style allow-lists and `rm\s+-rf`-style deny lists) [7](#0-6) .

### Impact Explanation
Any user who can influence the Bash command text sent by the agent (directly, or via prompt injection causing the agent to emit an obfuscated command) can cause a destructive/irreversible local action — `rm -rf`, `dd`, `mkfs`, credential exfiltration, etc. — while the project's explicitly configured Hookify safety guardrail reports no block and no warning. This is a concrete unauthorized local/workspace-destructive action enabled by defeating an approval/deny control that the project operator relied on, matching the "hook bypass" / "unauthorized shell action" impact class.

### Likelihood Explanation
High. No privileges are required beyond the normal ability to have the agent run a Bash command (the standard capability any Claude Code user/attacker-influenced session already has). The bypass techniques are standard, well-known shell obfuscation primitives, requiring no exploitation of memory safety, crypto, or race conditions — only that the configured `pattern` regex be written against literal substrings (which is the only mechanism Hookify supports and the one demonstrated in its own README/docs).

### Recommendation
Do not gate security decisions on literal, unparsed command text. Either: (1) parse/normalize the command through a real shell-lexer/AST (e.g., resolve variable expansion, `IFS`, quoting, and command substitution) before pattern matching, or (2) migrate high-risk rules to the `prompt`-based hook type (as the plugin's own migration guide recommends for exactly this reason: "regex... doesn't catch variations" [8](#0-7) ), or (3) treat `block` rules as defense-in-depth only and never document them as sufficient for destructive-command protection without an accompanying LLM/semantic check.

### Proof of Concept
1. Configure the documented example rule verbatim: `.claude/hookify.dangerous-rm.local.md` with `pattern: rm\s+-rf` and `action: block` [5](#0-4) .
2. Have the agent issue a Bash tool call with `tool_input.command` set to an obfuscated equivalent, e.g.:
   `a=rm; b='-rf'; $a $b /tmp/target`
3. `RuleEngine._regex_match("rm\\s+-rf", "a=rm; b='-rf'; $a $b /tmp/target")` returns `False` because the literal substring `rm -rf` (or `rm\s+-rf`) never appears contiguously; `evaluate_rules()` therefore returns `{}` and `pretooluse.py` exits 0 with no `permissionDecision: deny` [6](#0-5) [9](#0-8) .
4. Bash executes the command as written, expanding `$a $b` to `rm -rf`, deleting `/tmp/target`, despite the operator's explicit block rule.

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
