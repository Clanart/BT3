### Title
`InternalSendTx` on the Aggregator allows any unauthenticated caller to make the bridge broadcast and fee-bump arbitrary transactions - (File: `core/src/rpc/aggregator.rs`)

### Summary
The Aggregator's gRPC `InternalSendTx` handler (`internal_send_tx`) takes a raw, already-signed Bitcoin transaction plus a caller-chosen fee type and hands it directly to the tx-sender to be queued for broadcast/fee-bumping, with no check on who is calling or what the transaction is. Unlike the Verifier/Operator servers, the Aggregator does not enforce mTLS client-certificate identity checks, so this "internal" method is in practice reachable by any network caller who can open a TLS connection to the aggregator port.

### Finding Description
The Aggregator's tonic service `internal_send_tx` deserializes `request.raw_tx` and `request.fee_type` straight from the caller and forwards them to `self.tx_sender.insert_try_to_send(...)` with no validation that the transaction belongs to the bridge protocol (no txid/kickoff/round check, no signature-owner check): [1](#0-0) 

This call is meant to be restricted to "internal" callers, and the naming convention (`Internal*`) is used elsewhere by the `is_internal`/`OnlyAggregatorAndSelf` interceptor to gate verifier/operator methods to only the entity itself or the aggregator: [2](#0-1) 

However, that interceptor is only wired up on the generic `create_grpc_server` path used by Verifier/Operator, and the project's own documentation states explicitly that the aggregator does not apply this check:

> "The aggregator does not enforce client certificates but does use TLS for encryption." [3](#0-2) 

The Aggregator server is built through the very same `create_grpc_server` code path, which conditionally installs `OnlyAggregatorAndSelf` only `if config.client_verification`: [4](#0-3) [5](#0-4) 

Per the documented deployment model, the Aggregator's TLS is for encryption only (not client authentication), meaning `InternalSendTx` — despite its name — is exposed to any caller reaching the aggregator's public endpoint. This breaks the intended binding "a caller reaching a signing or state-changing method versus the party it is meant for": the party meant to invoke `InternalSendTx` is the aggregator's own internal automation (e.g. sending round/kickoff/reimburse txs), but per the documented configuration any external caller can invoke it.

### Impact Explanation
`internal_send_tx` is a state-changing/broadcasting call with no authentication boundary as documented. An attacker can submit any transaction and the aggregator's `tx_sender` will attempt to broadcast it and, depending on `fee_type` (CPFP/RBF), will use the aggregator's own fee-payer/anchor UTXOs to bump fees for a transaction of the attacker's choosing: [6](#0-5) 

This lets an unauthenticated party consume the aggregator's fee-bumping funds and force it to broadcast/fee-bump transactions on demand, and — more importantly for bridge custody — lets an attacker replay or race operational Round/Kickoff/Reimburse transactions through the aggregator's own signing/broadcast pipeline ahead of or in place of the legitimate flow, since the endpoint performs no ownership/authorization check on the supplied transaction. This matches the specified High-severity bucket: "an unauthenticated state-changing or broadcasting call."

### Likelihood Explanation
The Aggregator gRPC port is intentionally reachable by the "clementine-backend service" over the network per the proto comments (`// Used by the clementine-backend service`) and, per the documented configuration, without client-certificate verification — TLS is used only for transport encryption. No key, certificate, or privileged role is required to reach it, satisfying the rule against "requiring a verifier, operator, watchtower, aggregator... role or certificate": here the documented deployment explicitly leaves the caller unauthenticated. The likelihood is high for any network-reachable Aggregator deployment following the documented mTLS model.

### Recommendation
Apply the same `OnlyAggregatorAndSelf`/internal-method authentication used for Verifier and Operator servers to the Aggregator's own `Internal*` RPCs (at minimum `InternalSendTx` and `InternalGetEmergencyStopTx`), or otherwise validate that the submitted `raw_tx` in `internal_send_tx` corresponds to a transaction the aggregator itself generated/tracks (e.g., match against a known txid/type recorded in the DB) before queuing it for broadcast/fee-bumping.

### Proof of Concept
1. Stand up an Aggregator per the documented configuration (`client_verification` effectively not enforced for the aggregator, TLS used for encryption only, as stated in `docs/usage.md`).
2. From any client that can establish a TLS connection to the aggregator's gRPC port (no client certificate required for the aggregator per docs), call:
```
ClementineAggregatorClient::internal_send_tx(SendTxRequest {
    raw_tx: Some(RawSignedTx { raw_tx: <attacker-controlled fully-signed tx> }),
    fee_type: FeeType::Cpfp as i32,
})
```
as done in the test harness at: [7](#0-6) 
3. Observe that `insert_try_to_send` accepts the transaction without any check that the caller is the aggregator's own internal automation, and the tx-sender proceeds to broadcast/fee-bump it using the aggregator's operational funds: [8](#0-7)

    async fn internal_send_tx(
        &self,
        request: Request<clementine::SendTxRequest>,
    ) -> Result<Response<Empty>, Status> {
        #[cfg(not(feature = "automation"))]
        {
            Err(Status::unimplemented("Automation is not enabled"))
        }
        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
    }

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}

                our_cert,

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

    pub async fn send_no_funding_tx(
        &self,
        try_to_send_id: u32,
        tx: Transaction,
        tx_metadata: Option<TxMetadata>,
    ) -> Result<()> {
        match self.rpc.send_raw_transaction(&tx).await {
            Ok(sent_txid) => {
                tracing::debug!(
                    try_to_send_id,
                    "Successfully sent no funding tx with txid {}",
                    sent_txid
                );
                let _ = self
                    .db
                    .update_tx_debug_sending_state(try_to_send_id, "no_funding_send_success", true)
                    .await;
            }
            Err(e) => {
                let err_str = e.to_string();
                if rpc_errors::is_rejecting_replacement_error(&err_str) {
                    tracing::debug!(
                        try_to_send_id,
                        "No funding tx rejected (tx already in mempool): {err_str}"
                    );
                    return Ok(());
                } else {
                    tracing::error!(
                        "Failed to send no funding tx with try_to_send_id: {try_to_send_id:?} and metadata: {tx_metadata:?}"
                    );
                    log_error_for_tx!(
                        self.db,
                        try_to_send_id,
                        format!("send_raw_transaction error for no funding tx: {err_str}")
                    );
                }
                let _ = self
                    .db
                    .update_tx_debug_sending_state(try_to_send_id, "no_funding_send_failed", true)
                    .await;
                return Err(SendTxError::Other(eyre::eyre!(e)));
            }
        };

        Ok(())
    }
