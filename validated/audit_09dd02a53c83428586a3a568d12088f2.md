## Finding

The bug-class in the report is: a value cached at one point in time (locked balance) is trusted unconditionally at a later point in time (unlock), even though the underlying state (actual token balance) may have silently diverged, with no revalidation before acting on the stale value. Desktop has a structurally identical pattern in its partial-commit / line-selection pipeline.

### Title
Stale line-selection indices are trusted against a freshly re-fetched diff during commit, causing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines of a file for commit ("partial commit"), Desktop stores the choice as a `DiffSelection` bitmap keyed by *integer line offsets* (`absoluteIndex = hunk.unifiedDiffStart + lineIndex`) that are only meaningful relative to the specific diff/hunk layout that was on screen when the user made the selection [1](#0-0) . At commit time, however, `applyPatchToIndex` does not reuse that diff — it fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and then blindly applies the old `file.selection.isSelected(absoluteIndex)` bitmap against the new diff's hunks [2](#0-1) .

### Finding Description
The commit flow is:
1. User reviews a rendered diff and toggles individual lines/hunks. This diff is loaded once and cached in `IChangesState`/`WorkingDirectoryFileChange.selection` [3](#0-2) .
2. `_commitIncludedChanges` later reads that cached `selection` straight out of `repositoryStateCache` and hands the `WorkingDirectoryFileChange` objects (selection bitmap included) to `createCommit` [4](#0-3) .
3. `createCommit` calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex` [5](#0-4) [6](#0-5) .
4. `applyPatchToIndex` does **not** reuse the diff the user actually looked at — it calls `getWorkingDirectoryDiff(repository, file)` again, right before formatting the patch, and feeds the *old* selection bitmap into `formatPatch` against this brand-new diff's hunks [7](#0-6) , and `formatPatch` walks the new hunks calling `file.selection.isSelected(absoluteIndex)` with no cross-check that `absoluteIndex` still refers to the same logical line [8](#0-7) .

There *is* a guard for this staleness problem, but it only runs in the display path, not the commit path: `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` and drops selections on lines that no longer exist whenever the working-directory diff is refreshed for on-screen rendering [9](#0-8) . This revalidation is never invoked on the diff that `applyPatchToIndex` fetches internally at staging time, so the exact hazard the guard was built to prevent reappears, unguarded, in the commit-time code path.

### Impact Explanation
If the working-tree file content shifts between the last diff render the user based their selection on and the moment `applyPatchToIndex` re-diffs the file (an inherent async gap: user reviews diff → toggles lines → clicks Commit → JS event loop / disk I/O elapses), the hunk boundaries (`unifiedDiffStart`/`unifiedDiffEnd`) in the newly fetched diff can shift relative to the old ones. The stale absolute-index bitmap will then select/deselect the wrong lines in the new hunk layout. `git apply --cached` can succeed on such a patch (rather than fail loudly) whenever the residual context still lines up, producing a commit that **silently differs from what the user visually reviewed and explicitly checked/unchecked** — exactly the "silent corruption of what the user commits" impact category, without any error or warning to the user.

### Likelihood Explanation
Desktop repositories that are cloned/fetched routinely ship tooling (linters/formatters run on save, `husky`/`lint-staged` pre-commit scripts, build watchers, VS Code format-on-save tasks) that rewrite tracked files as a side effect of normal developer workflow concurrently with Desktop being open. Because Desktop's diff refresh is not tightly synchronized with the exact moment `applyPatchToIndex` re-diffs the file for staging, any such concurrent write in that window is sufficient to trigger the mismatch — no privileged access, no local exploit tooling, and no direct user "unnatural" steps are required beyond normal partial-commit usage in a repository whose tooling touches files during editing.

### Recommendation
- Do not re-fetch a fresh diff inside `applyPatchToIndex`; instead, thread through the exact `IDiff` object (with matching hunk offsets) that the `DiffSelection` was computed against, the same way `updateChangesWorkingDirectoryDiff` already does for rendering.
- If a fresh diff must be fetched at staging time (e.g., to defend against races), re-run the same "remap selectable lines" validation used in `updateChangesWorkingDirectoryDiff` (`withSelectableLines`) against the new diff before calling `formatPatch`, and abort/re-prompt the user rather than silently applying a mismatched selection.
- Consider detecting whether the file's mtime/hash changed since the diff was last rendered and, if so, forcing the user to re-review the diff before allowing the partial commit to proceed.

### Proof of Concept
1. Clone a repository that includes an on-save formatter/linter script (e.g., a file watcher or `lint-staged` hook configured to run automatically) that rewrites a tracked file's contents.
2. In Desktop, open the Changes view for that file and toggle a subset of lines/hunks for commit (partial selection) based on the diff currently rendered.
3. Before clicking Commit, let the on-save tool rewrite the file (this happens naturally as part of normal editing/build workflows) so that the file's line offsets shift relative to what was rendered.
4. Click Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-diffs the file fresh and applies the stale `DiffSelection` bitmap against the new hunk layout [7](#0-6) .
5. Inspect the resulting commit: it can contain different lines than the ones visually checked/unchecked by the user in step 2, with no error surfaced by Desktop.
