Confirmed vulnerability analog exists in the service-chain bridge's ERC20 handling.

### Title
Fee-on-transfer (deflationary) ERC20 tokens break bridge accounting and can lock/steal funds - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
`requestERC20Transfer` in `contracts/service_chain/bridge/BridgeTransferERC20.sol` pulls tokens from the caller with `safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then immediately emits/records a value-transfer request using the caller-supplied `_value` and computed `fee`, without ever checking how many tokens the bridge contract actually received.

### Finding Description
`requestERC20Transfer` does:
```
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

`_requestERC20Transfer` then charges the fee, optionally burns `_value` (in mint-burn mode), and emits `RequestValueTransfer` with the nominal `_value`/`fee` that were passed in — not the amount actually credited to the bridge's balance: [2](#0-1) 

If `_tokenAddress` implements a fee-on-transfer / reflection mechanism, the bridge contract's actual token balance increase from the `safeTransferFrom` call will be less than `_value + _feeLimit`. Two exploitable states follow:

1. **Lock-and-mode (non-mint-burn):** the bridge emits `RequestValueTransfer` claiming it holds `_value` tokens for the counterpart chain to release the mirrored amount, and `_payERC20FeeAndRefundChange` (in `BridgeFee.sol`) computes `fee` and any refund from the nominal `_feeLimit` rather than from actually-received tokens. Since the bridge's real balance is smaller than what it promises to have locked, the escrowed liquidity backing outstanding cross-chain claims becomes under-collateralized.
2. **Mint-burn mode:** `ERC20Burnable(_tokenAddress).burn(_value)` burns the full nominal `_value` even though the bridge only actually received `_value - fee` tokens due to the transfer-fee deduction, meaning the bridge burns tokens it never actually custodied (paid for out of tokens meant to cover the fee/refund), silently under-crediting the fee mechanism or draining the contract's residual token balance over repeated calls.

This is the exact bug class from the external report: the protocol assumes `amount transferred in == amount specified`, when fee-on-transfer tokens make `actual received = _value + _feeLimit - transferFee`.

### Impact Explanation
Any unprivileged EOA (the transaction sender calling `requestERC20Transfer`) can register a fee-on-transfer ERC20 token via `BridgeTokens` registration mechanisms and then invoke `requestERC20Transfer` to create a mismatch between the bridge's real token holdings and the value it publicly commits to release on the counterpart chain. Repeated calls compound the discrepancy, and because `HandleValueTransfer`/mint-on-counterpart operations rely on the nominal `_value` emitted here, the bridge can end up promising or minting more value on the destination chain than it actually escrowed/burned on the source chain — a form of unauthorized value creation/drain across the bridge accounting boundary. This matches the "Medium" severity of the original finding (uncommon token type, but concrete loss of accounted value / fund insolvency for the bridge operator or users redeeming on the other side).

### Likelihood Explanation
Likelihood is Medium: it requires (a) a fee-on-transfer ERC20 token to be registered as a bridged token (an operator action, `registerToken`), and (b) any user to call the public `requestERC20Transfer`/`onERC20Received` entrypoints with such a token. Fee-on-transfer tokens are uncommon but not exotic, and once such a token is bridged, exploitation requires no special privilege beyond calling the already-public transfer-request functions.

### Recommendation
In `requestERC20Transfer` (and `onERC20Received`), measure the bridge contract's token balance immediately before and after `safeTransferFrom`, and use the observed delta (rather than the caller-supplied `_value`/`_feeLimit`) as the basis for fee calculation, burn amount, and the `RequestValueTransfer` event/accounting, e.g.:
```solidity
uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
// derive actual value/fee from actualReceived instead of trusting _value/_feeLimit
```
Alternatively, explicitly document and enforce (e.g., via a registration-time check) that fee-on-transfer tokens are disallowed from being registered with `registerToken`.

### Proof of Concept
1. Deploy a deflationary/fee-on-transfer ERC20 (e.g., transferFrom that deducts an X% fee to a fee collector on every transfer, mirroring the report's `MockERC20TransferFee`).
2. Have the bridge operator register this token via the bridge's token-registration flow (`BridgeTokens`).
3. As any user, `approve` the bridge for `value + feeLimit` and call `requestERC20Transfer(tokenAddress, to, value, feeLimit, extraData)`.
4. Observe: `IERC20(tokenAddress).balanceOf(bridgeAddress)` increases by less than `value + feeLimit` (due to the transfer fee), yet:
   - In non-mint-burn mode, `RequestValueTransfer` is emitted with the full nominal `value`, over-stating the tokens now escrowed by the bridge for the counterpart-chain release.
   - In mint-burn mode, `ERC20Burnable(tokenAddress).burn(value)` reverts or drains the bridge's separately-held balance because the bridge only actually received `value + feeLimit - fee_on_transfer` tokens, not `value` alone.
5. Repeating this call demonstrates a growing shortfall between the bridge's real token custody and its emitted/accounted request amounts.
