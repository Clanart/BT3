### Title
Trampoline token is not bound to the git operation/remote it was issued for, allowing credential exfiltration via a malicious repository hook/filter - (File: app/src/lib/trampoline/trampoline-tokens.ts)

### Summary
`DESKTOP_TRAMPOLINE_TOKEN` is a random UUID handed to every spawned git process (including hooks, submodule commands, and clean/smudge filters) as an ambient bearer credential that authorizes calls to Desktop's local credential-helper/askpass socket. Validation of that token is a global set-membership check with no binding to the repository path, remote host, or the specific process that was supposed to receive it — the exact "hash whose params become public and is not bound to `address(this)`" problem described in the report, transplanted to Desktop's trampoline authentication model.

### Finding Description
When Desktop runs a git command it calls `withTrampolineEnv`, which requests a short-lived token via `withTrampolineToken` and injects it (plus the local server port) into the child process environment together with `DESKTOP_PORT`: [1](#0-0) 

The comment at that call site explicitly states this is done via environment variables (rather than one-shot CLI args) *so that commands invoked by filters (e.g. Git LFS) can pick up the configuration* — i.e. the token is intentionally propagated to any subprocess git spawns for the operation, including hooks and smudge/clean filters defined by the repository being cloned/fetched/checked out: [2](#0-1) 

Token issuance/validation is a bare `Set` with no scoping to path, remote, or connection: [3](#0-2) 

The trampoline server's only authorization check before dispatching a command is that the token exists in this set — it does not verify the socket/connection or the caller's expected repository/path: [4](#0-3) 

Once a caller supplies any valid token, the credential-helper `get` handler determines *which account's secret to return* purely from attacker-controllable fields in the request (`host`/`url` in the git credential protocol input), not from the path/remote that was associated with that token: [5](#0-4) [6](#0-5) 

The token-to-path association (`trampolineEnvironmentPath`) is only used to disambiguate external credential-helper delegation, not to constrain which hosts/accounts a request may target: [7](#0-6) 

Put together: a malicious repository can define a git hook or a smudge/clean filter (invoked during `clone`/`fetch`/`checkout`, all of which go through `withTrampolineEnv`/`spawnGit`) that reads its own `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT` environment variables and opens its own raw TCP connection to `127.0.0.1:<port>` (independent of the actual git process), sending a forged `CREDENTIALHELPER get` command whose `host`/`url` fields name an arbitrary GitHub endpoint (e.g. `github.com`) instead of the repository's own remote. Because `processCommand` only checks token liveness, and `getGitHubCredential`/`findGitHubTrampolineAccount` resolve the account purely by matching the attacker-chosen `host` against the user's signed-in accounts, the server will hand back the real GitHub account's OAuth token to the malicious hook/filter process — a token unrelated to the repository that triggered the operation.

### Impact Explanation
This allows an attacker-controlled cloned/fetched repository (via a malicious `.git/hooks/*` script or a `.gitattributes`-declared filter/smudge/clean command) to exfiltrate the user's GitHub OAuth token for any account configured in Desktop, not just credentials relevant to that repository's own remote. This is a credential/token exfiltration primitive stemming from an unprivileged, attacker-controlled repository — matching the "guaranteed win via leveraging a leaked secret in an unintended context" pattern of the original report, mapped onto Desktop's local trampoline IPC channel.

### Likelihood Explanation
Requires the victim to clone/fetch/checkout an attacker-controlled repository containing a hook or filter definition — a standard, low-friction attacker capability already covered by the "valid impact" scope (attacker controls a cloned/fetched repository). The token and port are placed in the environment of every spawned git-related subprocess by design, so no additional local access or social engineering beyond opening the malicious repo is required. Likelihood is Low-to-Medium since it requires the token to still be live (bounded by the duration of the triggering git operation) and requires crafting a raw socket client within a hook/filter, which is feasible but non-trivial.

### Recommendation
Bind the trampoline token cryptographically or structurally to the specific operation context it was issued for (e.g., the repository path and/or the expected remote origin captured at `withTrampolineEnv` invocation time), analogous to encoding `address(this)` in the original report's fix. `processCommand`/`getCredential` should reject requests whose `host`/`url` doesn't match the remote(s) known to be associated with the path stored for that token in `trampolineEnvironmentPath`, rather than trusting attacker-supplied `host`/`url` fields at face value. Consider also scoping the socket accept/validate step to the originating child process (e.g., via a per-connection nonce established at process spawn time) instead of a globally valid bearer token.

### Proof of Concept
1. Victim adds/clones a malicious repository containing a `.gitattributes` filter (e.g. `clean = mal-filter %f`) or a post-checkout hook `mal-filter`.
2. Victim performs a Desktop-initiated `fetch`/`clone`/`checkout` on this repo, which runs through `spawnGit`/`git()` → `withTrampolineEnv`, injecting `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT` into the git process environment: [8](#0-7) 
3. Git invokes the malicious filter/hook as a subprocess, inheriting these two environment variables.
4. The filter/hook process reads `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` and opens its own connection to `127.0.0.1:DESKTOP_PORT`, sending a forged trampoline `CREDENTIALHELPER` `get` command (per the wire format expected by `TrampolineCommandParser`) with `host=github.com` in the credential input, using the stolen token.
5. `trampolineServer.processCommand` accepts it because `isValidTrampolineToken` only checks set membership: [9](#0-8) 
6. `getCredential`/`getGitHubCredential` looks up and returns the real GitHub account's stored OAuth token for `github.com`, which the malicious process now exfiltrates over the network.

```typescript
const trampolineTokens = new Set<string>()

function requestTrampolineToken() {
  const token = crypto.randomUUID()
  trampolineTokens.add(token)
  return token
}

function revokeTrampolineToken(token: string) {
  trampolineTokens.delete(token)
}

/** Checks if a given trampoline token is valid. */
export function isValidTrampolineToken(token: string) {
  return trampolineTokens.has(token)
}

/**
 * Allows invoking a function with a short-lived trampoline token that will be
 * revoked right after the function finishes.
 *
 * @param fn Function to invoke with the trampoline token.
 */
export async function withTrampolineToken<T>(
  fn: (token: string) => Promise<T>
): Promise<T> {
  const token = requestTrampolineToken()
  let result

  try {
    result = await fn(token)
  } finally {
    revokeTrampolineToken(token)
  }

  return result
}
```

```typescript
export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
```
