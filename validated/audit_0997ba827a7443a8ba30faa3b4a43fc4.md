### Title
Copilot conflict-resolution hunks are matched to file content by array order rather than identity, allowing attacker-influenced/malformed model output to silently splice resolved content into the wrong conflict block - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
This is the strongest available Desktop analog to the MobileCoin report's root cause: an invariant ("the model's response corresponds 1:1 and in-order to the physical conflict blocks on disk") is assumed but never actually checked before being relied upon, and the checks that do exist (`validateResolutionPaths`) only validate counts/paths, not ordering or identity. Because the untrusted input that drives the ordering (the LLM's JSON array, itself built from a prompt containing attacker-influenceable repository content) is not cross-validated against the independently re-parsed on-disk conflict-block order, the reassembly step can silently write the wrong resolved content into the wrong hunk before the result is staged and committed.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks a conflicted file and produces an ordered list of hunks, which is then rendered into the prompt as "Conflict 1 of N", "Conflict 2 of N", etc. via `formatConflictContextForPrompt` (`app/src/lib/copilot-conflict-context.ts:560-590`). The prompt also embeds attacker-influenceable content verbatim: PR titles/bodies (`appendPullRequest`, lines 600-610), commit summaries, and the raw ours/theirs hunk content itself — all of which originate from a branch/PR that an attacker can craft and get merged/fetched by the victim. [1](#0-0) 

The model's JSON response is validated only for shape, path membership, duplicate paths, and **hunk count per file**: [2](#0-1) 

Nothing in `validateResolutionPaths` verifies that hunk *order* in the response matches the physical order of conflict blocks in the file. That assumption is only realized later, in `reassembleResolvedFile`, which independently re-walks the raw on-disk content and splices `hunkResolutions[hunkIndex]` into each conflict block strictly by traversal order: [3](#0-2) [4](#0-3) 

This is precisely the pattern in the external report: two independent code paths (prompt-construction/expectation-building vs. final application) share an implicit invariant — "hunk N in the response is hunk N on disk" — but nothing enforces that invariant along the path that actually matters (the untrusted model response), the same way `do_prepare_phase`/`do_commit_phase` assumed a phase invariant that wasn't checked along every code path in `slot.rs`.

The result of `reassembleResolutions` is trusted and written straight to disk and staged with `git add` when the user clicks "Continue Merge": [5](#0-4) [6](#0-5) 

### Impact Explanation
If a hunk's resolved content is spliced into the wrong conflict block (same count, wrong order — which `validateResolutionPaths` cannot detect), the file that is written to disk, staged, and ultimately committed/pushed by the user is silently wrong: code from one logical change is placed where a different, unrelated change should be. This is exactly the "silent corruption of what the user commits or pushes" impact category — the user sees a green "resolved" dialog and a diff that looks plausible, but the actual committed content does not match what either side of the conflict, or the model's stated reasoning, intended. Because the trigger is repository content the attacker controls (a branch/PR merged by the victim, whose commit messages/PR body/file content feed the prompt), this is remotely reachable by an unprivileged attacker without any local access, admin rights, or social engineering step beyond a normal merge.

### Likelihood Explanation
Exploitability depends on the LLM actually reordering hunks relative to their prompt order, which is not something Desktop's code prevents or detects — there is no ordinal/id field per hunk in the response schema, and no check that response order matches file order. LLM outputs are known to be susceptible to prompt injection via embedded untrusted text (PR bodies, commit messages, and the conflicting code itself are all attacker-controlled and placed directly in the prompt with only markdown-fence sanitization, not semantic-instruction stripping). This makes the underlying invariant gap concretely exploitable in principle, though empirically triggering a specific reordering depends on model behavior, which is inherently probabilistic rather than deterministic like the Rust assertion crash in the original report.

### Recommendation
- Add an explicit ordinal or stable identifier to each hunk in the prompt schema (e.g., `"hunkIndex"` per file) and require the model to echo it back per resolution.
- In `validateResolutionPaths`, verify that each file's returned hunk indices are a permutation-free, monotonically increasing sequence matching `expectedFiles[...].hunks` order (or reject/re-request if not) instead of only checking `hunks.length`.
- In `reassembleResolvedFile`/`reassembleResolutions`, splice by the validated hunk identifier rather than positional array index, so a mismatched or attacker-influenced ordering cannot silently relocate content.
- Treat any inability to establish a 1:1 hunk correspondence as a hard validation failure (throwing `CopilotValidationError`) rather than proceeding with a best-effort positional match.

### Proof of Concept
1. Attacker opens a PR / pushes a branch with two independent conflicting hunks in the same file, and a PR body/commit message containing text crafted to bias the model into re-ordering its per-hunk output (prompt-injection payload embedded in `appendPullRequest`/commit summary content that flows into `formatConflictContextForPrompt`).
2. Victim attempts to merge/rebase and clicks "Resolve with Copilot".
3. `buildConflictContext`/`extractConflictHunks` build hunk index 0 and 1 for the file; the prompt shows "Conflict 1 of 2" / "Conflict 2 of 2" with the injected content.
4. The model returns 2 hunks (satisfying `validateResolutionPaths`'s count check) but in reversed order due to the injected instruction.
5. `reassembleResolvedFile` splices `hunkResolutions[0]` into the first on-disk block and `hunkResolutions[1]` into the second — the wrong resolution for each — with no error raised.
6. User clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the corrupted file and stages it via `git add`, and it is committed/pushed as-is. [7](#0-6)

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
