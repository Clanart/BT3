### Title
Out-of-bounds read on attacker-controlled message bytes in Schnorrkel HRAM — reachable panic / invalid index during signing - (File: crypto/schnorrkel/src/lib.rs)

### Summary
The Schnorrkel `Hram::hram` implementation parses the message buffer `m` by indexing it directly (`m[0 .. 4]`, `m[4 .. 4 + ctx_len]`, `m[(4 + ctx_len) ..]`) without checking that `m` is long enough or that the embedded `ctx_len` field fits inside `m`. This is the same bug class as CVE-2022-41649 (IPTC parsing in OpenImageIO reads adjacent heap memory when a length field in untrusted file data is trusted): a length field inside untrusted input is used as a slice bound without validation. In Serai's case, `m` is `len(context) || context || msg` where `msg` is the attacker-influenced message being signed, and `hram` is invoked during both `sign_share` and final `verify` of a FROST signing session.

### Finding Description
In `crypto/schnorrkel/src/lib.rs`, `SchnorrkelHram::hram` does:

```rust
let ctx_len =
  usize::try_from(u32::from_le_bytes(m[0 .. 4].try_into().expect("malformed message")))
    .unwrap();

let mut t = signing_context(&m[4 .. (4 + ctx_len)]).bytes(&m[(4 + ctx_len) ..]);
``` [1](#0-0) 

`m` is constructed in `sign_share` as `u32(context.len()) || context || msg`: [2](#0-1) 

so the length field prepended is honest at sign time — but `hram` is also called by the FROST core on the same buffer during share verification (`verify_share` → `verify_statements` → `hram`), and `hram` is a pure function of its input `m`: any code path that feeds a caller-supplied or deserialized buffer into `hram` (e.g., via `Schnorr<Ristretto, MerlinTranscript, SchnorrkelHram>` used generically, or via `verify` paths that reconstruct the message) trusts the first 4 bytes as a bound. Two concrete out-of-bounds conditions exist even in the honest path:

1. `m.len() < 4` — impossible via `sign_share` (which always prepends 4 bytes), but possible if `hram` is invoked on a raw message through the generic `Hram` interface; `m[0 .. 4]` panics.
2. `ctx_len` inside `m` larger than `m.len() - 4` — `m[4 .. (4 + ctx_len)]` and `m[(4 + ctx_len) ..]` index past the end of the slice, and `4 + ctx_len` can overflow `usize` on 32-bit if `ctx_len = u32::MAX`.

Because `hram` is invoked on every participant's signing path and in `verify`/`verify_share` during `complete` (crypto/frost/src/sign.rs, `AlgorithmSignatureMachine::complete`), a signing session fed a malformed message buffer aborts via panic rather than an error, killing the signer thread mid-session — after nonces have already been committed/consumed for that session.

### Impact Explanation
An unprivileged party who can cause a Schnorrkel signing session to run on a message they control (the `msg` passed to `sign`, and any buffer reaching `hram` through verify paths) can force an out-of-bounds slice index and panic the signer. This is a denial of service against threshold signing: the participant's nonces for that session are consumed and the session aborts without producing a share, stalling the signing set. Unlike a clean `Err` return, a panic in `sign_share`/`verify` can also unwind through `complete` while shares from other participants are in flight, and there is no blame path for a peer that induced the panic (blame is only assigned for invalid shares, not for panics). Severity: Medium — availability loss reachable with public input; no memory contents are disclosed (Rust slice indexing panics rather than reading out of bounds), so it does not escalate to the confidentiality impact of the original CVE.

### Likelihood Explanation
The honest `sign_share` path prepends a valid `u32` context length, so the OOB is not triggerable through that specific entry point with a well-formed context. However, `hram` receives `m` as opaque bytes in the challenge computation during `verify`/`verify_share` as well, and any caller that constructs the `len || ctx || msg` buffer from untrusted components — or any future algorithm reusing `SchnorrkelHram` over raw message bytes — triggers the panic deterministically with `msg` shorter than 4 bytes or a forged `ctx_len`. The missing bounds check is a latent defect: the code assumes the buffer structure but never enforces it, exactly the IPTC-class assumption that a length field in the input describes the actual buffer.

### Recommendation
Validate the buffer before indexing:

```rust
if m.len() < 4 {
  panic!("malformed message"); // or better, return an error up the stack
}
let ctx_len = usize::try_from(u32::from_le_bytes(m[0 .. 4].try_into().unwrap())).unwrap();
if m.len() < 4 + ctx_len {
  panic!("malformed message");
}
```

Prefer returning `Err`/`FrostError` instead of panicking so a malformed message cannot abort the signer. Ideally, `hram` should not re-parse a serialized length prefix at all — the context is already fixed at `Schnorrkel::new(context)` time (crypto/schnorrkel/src/lib.rs, line 68), so the challenge could commit to `context` and `msg` directly (e.g., `signing_context(self.context).bytes(msg)`) rather than decoding them out of a concatenated buffer, eliminating the parsing surface entirely.

### Proof of Concept
```rust
// crypto/schnorrkel scenario: call SchnorrkelHram::hram with a short or
// forged-length buffer, as reachable through verify paths that feed
// caller-controlled bytes into the challenge.

// Case 1: fewer than 4 bytes -> m[0 .. 4] out-of-bounds panic
let m: &[u8] = &[0x01, 0x02]; // < 4 bytes
// SchnorrkelHram::hram(&R, &A, m) -> panics at m[0 .. 4]

// Case 2: ctx_len larger than the buffer -> m[4 .. 4 + ctx_len] OOB panic
let mut m = u32::MAX.to_le_bytes().to_vec(); // ctx_len = 0xffffffff
m.extend(b"ctx");
// SchnorrkelHram::hram(&R, &A, &m) -> panics indexing m[4 .. 4 + 0xffffffff]

// In a FROST session this is triggered when sign/verify run the HRAM over a
// message buffer supplied (directly or via serialization) by an untrusted
// participant, aborting the signer and the signing session.
```

Note: within the shipped `sign_share` path the 4-byte prefix is generated honestly, so triggering this today requires a path where `hram` receives an externally constructed `m` (verify/share-verification calls, or reuse of `SchnorrkelHram`). If such a path is considered unreachable for untrusted bytes in the current API surface, the finding reduces to a latent robustness defect rather than an exploitable vulnerability.
