### Title
Self-referral via two attacker-controlled addresses bypasses `useCode` ownership check, enabling theft of both referer and referee reward shares - (File: rewards/ReferralStorage.sol)

### Summary
`useCode()` only blocks binding a code to the same address that owns it (`codeOwners[_code] == msg.sender`), but does not prevent a second address controlled by the same person from binding to that code. An attacker can `registerCode()` from address A and `useCode()` from address B, creating a fully self-controlled referrer/referee pair. When `trigger()` later distributes rewards, the attacker (as A) collects the referer share and (as B) collects the referee share of their own emissions, with no genuine third-party recruitment involved.

### Finding Description
`useCode` at [1](#0-0)  only checks `codeOwners[_code] == msg.sender` to guard against self-referral, plus that the caller has no existing referrer. There is no proof-of-distinct-identity mechanism (e.g., staking history, KYC, or economic cost), so an attacker trivially:

1. Calls `registerCode(_code)` from address A, setting `codeOwners[_code] = A` [2](#0-1) .
2. Calls `useCode(_code)` from address B (a second address they control). Since `codeOwners[_code] == A != B`, the `Circled()` check does not trigger, and `myReferer[B] = A` is set.
3. Stakes/locks and generates claim activity from B (and/or A) so that `masterMagpie` calls `trigger(B, _amount)` [3](#0-2) , splitting `_amount` into `refererAmount` credited to A and `refereeAmount` credited to B, using `refererPercentage = (basic + boosted) * (DENOMINATOR - sharePercent) / DENOMINATOR` and `refereePercentage = (basic + boosted) * sharePercent / DENOMINATOR`.

Because `refererPercentage + refereePercentage = basic + boosted`, and `basic` (tier `rewardPercentage`) is bounded only by `DENOMINATOR` while `boosted = BoostPoint * factor / totalBoostFactor` is bounded only by `BoostPoint` (which is set once in `__ReferralStorage_init` with no upper-bound validation) [4](#0-3) , the sum `basic + boosted` can exceed `DENOMINATOR` if the deployed configuration has a high `BoostPoint`. In that scenario, `refererAmount + refereeAmount > _amount`, i.e. more MGP is credited across the two `rewardAmount` balances than the reward event `_amount` justifies. Since both addresses belong to the same attacker, they capture 100% of this inflated payout, rather than the intended split between a genuine referrer and a genuine referee.

Even without the `BoostPoint`/`DENOMINATOR` edge case, the `useCode` check fails to prevent the referral system's intended incentive (rewarding recruitment of new, independent users) from being captured entirely by a single actor operating two wallets — violating the stated business invariant that referral rewards should only flow between genuinely distinct parties.

### Impact Explanation
This is a "Theft of unclaimed yield" issue: MGP rewards set aside for the referral program (referer bonus + referee bonus) are diverted entirely to a single attacker instead of being split between a genuine referrer and referee, and — when `basic + boosted > DENOMINATOR` — the attacker can mint/claim more MGP across `rewardAmount[A]` and `rewardAmount[B]` than the underlying `_amount` from `trigger()` justifies, both amounts collectible via `claimReward()` [5](#0-4) .

### Likelihood Explanation
The `registerCode` → `useCode` (from a second address) sequence requires no privileged role, only two attacker-controlled EOAs and normal staking/claim activity to trigger `trigger()`. It is fully repeatable for every claim event. The amplification beyond `DENOMINATOR` additionally requires the protocol's `BoostPoint` configuration (set at initialization, unbounded) combined with a tier `rewardPercentage` to sum above `DENOMINATOR` — a precondition on deployed configuration rather than something the attacker sets, but plausible since `BoostPoint` has no upper-bound check in `__ReferralStorage_init`.

### Recommendation
- In `useCode`, prevent binding to a code whose registered owner shares the same underlying controller where feasible (not fully solvable on-chain, but at minimum cap total referral payout).
- Cap `refererPercentage + refereePercentage` (i.e., `basic + boosted`) to never exceed `DENOMINATOR` inside `trigger()`, e.g. `uint256 totalPct = basic + boosted; if (totalPct > DENOMINATOR) totalPct = DENOMINATOR;` before computing `refererAmount`/`refereeAmount`.
- Add an explicit upper bound on `BoostPoint` in `__ReferralStorage_init` (and any setter) so `basic + boosted` cannot structurally exceed `DENOMINATOR`.
- Consider requiring a minimum stake/lock duration or activity threshold before a referral relationship becomes reward-eligible, raising the cost of Sybil self-referral.

### Proof of Concept
Hardhat test plan:
1. Deploy `ReferralStorage` with a `BoostPoint` and tier `rewardPercentage` configured such that `basic + boosted > DENOMINATOR` (e.g., tier `rewardPercentage = 6000`, `BoostPoint` set so `boosted ≈ 5000` after locking).
2. From address A: call `registerCode(codeA)`.
3. From address B (attacker's second address): call `useCode(codeA)`; assert `myReferer[B] == A` and no revert.
4. Have both A and B lock vlMGP so `totalBoostFactor` and `userInfos[A].factor` are non-zero (via `updateTotalFactor`).
5. As `masterMagpie` (mocked), call `trigger(B, amount)`.
6. Assert `userInfos[A].rewardAmount + userInfos[B].rewardAmount > amount` (confirms `refererPercentage + refereePercentage > DENOMINATOR` in effect), and that both A and B can `claimReward()` to receive MGP exceeding the intended single-recipient amount.
7. Repeat with `basic + boosted <= DENOMINATOR` as a control case to show the split still fully accrues to the same attacker (self-referral) even without amplification, confirming the underlying access-control gap in `useCode`.

        if (_code == bytes32(0)) revert InvalidCode();
        if (codeOwners[_code] == address(0)) revert InvalidCode();

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
