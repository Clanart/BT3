### Title
Missing-participant panic in `GeneratorPromotion::complete` — out-of-range/duplicate participant set causes reachable crash via `unwrap` on absent proof - (File: crypto/dkg/promote/src/lib.rs)

### Summary

`GeneratorPromotion::complete` validates only the *quantity* and the *upper bound* of the attacker-influenced `proofs` map before indexing it with `unwrap()`. A proof map that contains an entry for the local participant (`params.i()`) — or otherwise omits any participant in `1..=n` while still totaling `n - 1` entries — causes an unhandled panic, a remotely triggerable denial of service analogous to the crash-class bug in ALPINE-CVE-2018-2640.

### Finding Description

`crypto/dkg/promote/src/lib.rs` lines 124–156:

```rust
if proofs.len() != (usize::from(params.n()) - 1) { ... }        // count check only
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }                          // upper-bound check only
}
...
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();                          // panics if absent
```

The validation enforces `proofs.len() == n - 1` and `key <= n` for every key, but never enforces that the key set equals `{1..=n} \ {params.i()}`. `HashMap` keys are unique, so the two "obvious" failure modes (duplicates, out-of-range) are covered — but substitution is not. A map of exactly `n - 1` entries containing `params.i()` necessarily omits some other participant `j ∈ 1..=n`, and `proofs.get(&j).unwrap()` then panics.

Since `Participant` is a non-zero `u16` and `> n` is rejected, the only reachable malformed set is exactly this substitution, and it reliably panics.

### Impact Explanation

The `proofs` map is assembled from `GeneratorProof` messages supplied by the other multisig participants — untrusted protocol input fed into a `complete` API (explicitly in-scope per the prompt's reachable-paths list). A single faulty or malicious participant can crash the promotion routine on every honest node that processes the map, aborting the generator-promotion flow and any downstream signing that depends on it. This is a low-privileged, network-reachable availability impact (CVSS-class A:H), matching the Medium severity of the reference advisory.

### Likelihood Explanation

Any party able to cause a `GeneratorProof` to be registered under a chosen `Participant` key (including the victim's own index, which the loop `continue`s over without checking membership) triggers the panic deterministically — no probabilistic conditions, no threshold collusion required. The panic occurs before any proof is verified for the missing participant, so no valid cryptographic material is needed.

### Recommendation

Replace the count/upper-bound checks with an exact key-set validation: for every `i in 1..=n` where `i != params.i()`, require `proofs.contains_key(&i)`, and reject `proofs.contains_key(&params.i())`. Alternatively, replace `proofs.get(&i).unwrap()` with `.ok_or(PromotionError::MissingParticipant(i))?` (adding such a variant), consistent with the `MissingParticipant`/`InvalidParticipant` error handling already used in `dkg` and `pedpop::validate_map` (`crypto/dkg/pedpop/src/lib.rs` lines 57–83).

### Proof of Concept

With `n = 3`, local participant `i = 1`:

```rust
// proofs map assembled from received GeneratorProof messages:
//   { Participant(1): <attacker-submitted proof>,
//     Participant(2): <honest proof> }
// len == 2 == n - 1  → passes line 125 check
// all keys <= 3      → passes line 133 check
// loop:
//   i = 1 → skipped (== params.i())
//   i = 2 → proofs.get(2) → Some
//   i = 3 → proofs.get(3) → None → panic! (line 146)
```

No `GeneratorProof` from participant 3 is ever required; the panic fires on the `unwrap()` at `crypto/dkg/promote/src/lib.rs:146`. The same missing-key panic pattern exists in `pedpop`'s `BlameMachine::blame_internal` (`self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599`) and `Decryption::decrypt_with_proof` (`self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388`), where blame-accusation `sender`/`recipient` indexes are attacker-influenced and never bounds-checked against the participant set — a secondary instance of the same reachable-crash class.
