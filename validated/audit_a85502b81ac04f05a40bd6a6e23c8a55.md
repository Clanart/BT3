## Title
Payout attribution can be front-run: `SIGHASH_SINGLE|ANYONECANPAY` on the payout tx lets any third party swap the OP_RETURN operator credit, stealing reimbursement from the operator who actually fronted the withdrawal - (File: `core/src/rpc/parser/operator.rs`, `core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`)

### Summary
The withdrawal/payout mechanism explicitly enforces `TapSighashType::SinglePlusAnyoneCanPay` on the user's withdrawal signature [1](#0-0) . This sighash flag only commits to input 0 and output 0 of the payout transaction; any other inputs/outputs — including the OP_RETURN output that encodes which operator's x-only pubkey should be credited for fronting the payout — are *not* covered by the signature. The protocol's later accounting of "who paid" is derived purely from parsing this unauthenticated OP_RETURN field from whichever version of the transaction happens to confirm [2](#0-1) .

### Finding Description
`create_payout_txhandler` builds the payout transaction with: (1) the withdrawal UTXO input spent via key-spend with only the user's `SinglePlusAnyoneCanPay` signature, (2) the user payout output, and (3) an OP_RETURN output containing `operator_xonly_pk.serialize()` [3](#0-2) .

Because the signature type is `SinglePlusAnyoneCanPay`, it authorizes spending input 0 to produce output 0 with the fixed amount/script — but it does **not** bind any of the other outputs (the anchor and, critically, the OP_RETURN operator-attribution output) or any additional inputs. This is intentional so operators can add fee-paying inputs, but it also means **anyone observing the mempool can rebuild an alternate transaction** that reuses the exact signed input/output pair (thus fronting the same withdrawal to the same user) while substituting a different OP_RETURN payload naming a different operator's x-only pubkey.

Verifiers determine "who fronted this withdrawal" solely by scanning the confirmed payout transaction for the first OP_RETURN output and parsing an x-only pubkey out of it, with no cryptographic binding between that pubkey and the actual signer/broadcaster of the transaction: [4](#0-3) 

This value is persisted into `withdrawals.payout_payer_operator_xonly_pk` [5](#0-4) [6](#0-5) , and it is this DB column — not any signature — that later grants reimbursement rights: `validate_payer_is_operator` reads `payout_payer_operator_xonly_pk` and, if it equals the requesting operator's key, lets that operator claim the kickoff/reimbursement flow for the deposit [7](#0-6) . `get_first_unhandled_payout_by_operator_xonly_pk` likewise looks up unhandled payouts strictly by this attributed pubkey to drive automatic reimbursement [8](#0-7) [9](#0-8) .

The binding that should hold is:
`operator credited for reimbursement == operator whose funds actually left custody to front the withdrawal`

Because attribution is read from a mutable, unsigned OP_RETURN field rather than from the actual spending key or a signed commitment, an attacker (any unprivileged party who observes the broadcast payout tx in the mempool, before it confirms) can break this equality by replacing the OP_RETURN with an arbitrary x-only pubkey — either their own (to steal the reimbursement that the actual fronting operator earned) or another honest operator's pubkey (to falsely and maliciously credit — or discredit, e.g. to frame or to permanently deny — a party who did nothing).

### Impact Explanation
This directly breaks the "operator credited versus the party that paid" custody binding called out as an analog target:
- **Reimbursement theft**: an operator (or any actor) can hijack another operator's in-flight payout by re-broadcasting a variant transaction with a self-referential OP_RETURN before the honest operator's version confirms, then later claim the `Reimburse`/`Kickoff` flow (`validate_payer_is_operator` will match their pubkey) — resulting in that operator being reimbursed for a payout they never funded, and the honest operator who fronted the withdrawal being unable to claim their rightful reimbursement (their `payout_payer_operator_xonly_pk` no longer matches, and their kickoff for that deposit will subsequently be treated as unmatched / potentially flagged malicious in `is_kickoff_malicious` [10](#0-9) , which can slash their collateral).
- This maps to the report's High/Critical bucket: "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
The attack requires only observing the honest operator's payout transaction in the mempool and constructing a replacement transaction spending the same input with the same signature (which remains valid under `SinglePlusAnyoneCanPay` regardless of the extra outputs), then getting the replacement mined first (e.g. via a higher fee/RBF or simple race). No privileged key, verifier/aggregator role, or majority hashpower is needed — this is exploitable by any unprivileged actor with mempool visibility and basic tx-construction ability, satisfying the "unprivileged attacker" requirement.

### Recommendation
Bind the operator-attribution output to the withdrawal signature itself instead of relying on an unauthenticated OP_RETURN field, e.g.:
- Require the user's withdrawal signature to use `SIGHASH_ALL` (or otherwise cover all outputs including the OP_RETURN operator pubkey) so the operator identity is committed to at signing time, or
- Have the aggregator/verifiers pre-commit to (deposit_id → operator_xonly_pk) off-chain before the payout is signed, and validate on confirmation that the on-chain OP_RETURN matches that pre-committed value, rejecting/ignoring mismatches rather than blindly trusting whatever OP_RETURN happens to confirm, or
- At minimum, treat the first-confirmed spend of a given withdrawal UTXO as authoritative only if it also matches a previously recorded "intent to pay" from a specific operator (recorded before broadcast), and flag/reject payouts whose OP_RETURN does not match that recorded intent.

### Proof of Concept
1. Operator A signs and broadcasts a valid `Payout` tx for withdrawal UTXO `U` → user output `O`, with OP_RETURN = `xonly_pk(A)`, using signature `sig` with `SinglePlusAnyoneCanPay` [3](#0-2) .
2. Attacker (or Operator B) observes this transaction in the mempool. Because `sig` only commits to input 0 and output 0, the attacker constructs `Payout'`: same input `U` + `sig`, same output `O`, but OP_RETURN = `xonly_pk(B)`, and broadcasts it with a higher fee (or via RBF).
3. `Payout'` confirms instead of (or race against) the original. `update_finalized_payouts` scans the confirmed block, parses the OP_RETURN, and writes `payout_payer_operator_xonly_pk = xonly_pk(B)` into the `withdrawals` table [11](#0-10) .
4. Operator B calls `get_reimbursement_txs` / the automated `PayoutCheckerTask` picks up the withdrawal via `get_first_unhandled_payout_by_operator_xonly_pk(xonly_pk(B))` [9](#0-8) , and `validate_payer_is_operator` succeeds for B [7](#0-6) , allowing B to claim the kickoff/reimbursement for a withdrawal it never funded, while A — who actually paid the user — cannot get reimbursed and may later be flagged as malicious for a kickoff that no longer matches recorded payout data.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };
