### Title
Per-call gas multiplier truncation in `multiplierGasMeter.ConsumeGas` allows systematic gas under-charging - ([File: sei-cosmos/store/types/gas.go])

### Summary
Sei's cosmos-SDK gas meter applies a rational multiplier (`numerator`/`denominator`) to every individual `ConsumeGas` call rather than to the cumulative gas total. Because the multiplication is followed by integer division on each call, each call independently truncates its fractional remainder. This is the same bug class as the reported LooksRare issue: computing `price/valuePerEntry` per unit instead of `(price*quantity)/valuePerEntry` in aggregate causes systematic loss versus the mathematically correct single computation.

### Finding Description
`multiplierGasMeter.adjustGas` computes `original * multiplierNumerator / multiplierDenominator` using integer division, and this adjustment is invoked separately for every `ConsumeGas` call: [1](#0-0) 

The gas meter is installed for ordinary (non-EVM) cosmos transaction execution via `GetGasMeterSetter`, using the configured `CosmosGasMultiplierNumerator`/`CosmosGasMultiplierDenominator` params: [2](#0-1) 

Because `ConsumeGas` is called many times over the course of executing a transaction (once per store read/write, per opcode, per CosmWasm gas-metered operation, etc.), and each call independently truncates `amount * numerator / denominator`, the sum of many small truncated charges is always less than or equal to what a single lump-sum computation `(Σamount) * numerator / denominator` would yield. This is mathematically guaranteed: `Σ⌊aᵢ·n/d⌋ ≤ ⌊(Σaᵢ)·n/d⌋`. The gap grows with the number of `ConsumeGas` invocations, i.e., an attacker (any unprivileged tx sender/contract deployer) who structures a transaction or CosmWasm contract call to perform many small gas-consuming operations pays systematically less scaled gas than a single large operation performing the same total amount of underlying (unscaled) work.

### Impact Explanation
When the configured multiplier ratio is non-unity (i.e., `numerator/denominator` is not an integer, e.g. a fractional discount/premium is applied to convert raw gas units into billed gas), an attacker can exploit this truncation to consume more effective execution/storage work per unit of paid (billed) gas by splitting operations into many fine-grained calls. This is a form of fee/gas accounting abuse: it allows executing more computation for a given `GasWanted`/fee than the protocol intends, which can be leveraged to build transactions that execute significantly more real work than their nominal gas limit implies, risking excessive block-processing time (block delay) and unfair fee extraction from validators who are undercompensated for the real resource consumption performed.

### Likelihood Explanation
The multiplier gas meter is used on every cosmos transaction that isn't in simulation/genesis mode, and `ConsumeGas` is called extremely frequently (per store operation, per WASM gas checkpoint, etc.), so the truncation opportunity is present on essentially all standard transaction execution paths. Exploitability depends on whether the configured `CosmosGasMultiplierNumerator`/`Denominator` pair is non-trivial (not `1/1`); if the chain runs with a fractional multiplier (used to convert e.g. wasm gas units to SDK gas), the effect is directly exploitable by any transaction sender or CosmWasm contract author by fragmenting operations to maximize the number of truncation points. I was not able to confirm from the indexed code whether the currently deployed default parameter values for `CosmosGasMultiplierNumerator`/`Denominator` are non-unity in production, so likelihood is conditioned on that configuration.

### Recommendation
Accumulate raw (unscaled) gas consumption first, and apply the multiplier once to the running total (or use a remainder-carrying scheme, e.g., keep a fractional remainder register updated on each `ConsumeGas` call and apply it into the next scaling operation) so that `Σ scaledCharge` converges to `⌊(Σ rawAmount)·n/d⌋` rather than `Σ⌊aᵢ·n/d⌋`.

### Proof of Concept
Given `multiplierNumerator/multiplierDenominator = 3/2` (illustrative fractional multiplier):
- Single lump consumption of `amount = 5`: `adjustGas(5) = 5*3/2 = 7` (floor of 7.5).
- Five separate `ConsumeGas(1, ...)` calls: `adjustGas(1) = 1*3/2 = 1` (floor of 1.5) each, summing to `5`.
The five-call sequence charges `5` scaled gas units versus `7` for the equivalent lump-sum operation — a ~29% reduction in billed gas for identical total raw work, purely by fragmenting the operation into more `ConsumeGas` calls. An attacker can amplify this gap by increasing the number of fine-grained gas-consuming operations in a single transaction. [3](#0-2)

func (g *multiplierGasMeter) adjustGas(original Gas) Gas {
	return original * g.multiplierNumerator / g.multiplierDenominator
}

func (g *multiplierGasMeter) ConsumeGas(amount Gas, descriptor string) {
	g.basicGasMeter.ConsumeGas(g.adjustGas(amount), descriptor)
}

func (g *multiplierGasMeter) RefundGas(amount Gas, descriptor string) {
	g.basicGasMeter.RefundGas(g.adjustGas(amount), descriptor)
}

func GetGasMeterSetter(pk paramskeeper.Keeper) func(bool, sdk.Context, uint64, sdk.Tx) sdk.Context {
	return func(simulate bool, ctx sdk.Context, gasLimit uint64, tx sdk.Tx) sdk.Context {
		cosmosGasParams := pk.GetCosmosGasParams(ctx)

		// In simulation and genesis delivery, still use multiplier but with infinite gas limit.
		if simulate || ctx.IsGenesis() {
			return ctx.WithGasMeter(types.NewInfiniteMultiplierGasMeter(cosmosGasParams.CosmosGasMultiplierNumerator, cosmosGasParams.CosmosGasMultiplierDenominator))
		}

		return ctx.WithGasMeter(types.NewMultiplierGasMeter(gasLimit, cosmosGasParams.CosmosGasMultiplierNumerator, cosmosGasParams.CosmosGasMultiplierDenominator))
	}
