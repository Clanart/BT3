### Title
Uncaught `AssertionError` on crafted offer files with duplicate coin spends causes wallet DoS in `Offer.__post_init__` - (File: `chia/wallet/trading/offer.py`)

### Summary
The reported CVE describes a parser (`ReadData` in libebml2) that crashes with an unhandled assertion fault when fed a crafted, untrusted binary file, causing a denial of service. The same bug class — untrusted, attacker-supplied serialized data reaching a bare `assert` instead of a handled validation error — exists in Chia's offer-file parsing path.

### Finding Description
`Offer.__post_init__` iterates over the coin spends contained in a deserialized offer bundle and enforces the "no coin spent twice in the same bundle" invariant with a bare Python `assert`, not a `ValidationError`/`ValueError`: [1](#0-0) 

Specifically:
```
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
``` [2](#0-1) 

`Offer` objects are constructed from untrusted, wire-format offer files supplied by a counterparty (bech32m-encoded offer strings) via `Offer.from_spend_bundle`/`Offer.from_bytes` paths, which build a `WalletSpendBundle` directly from attacker-controlled `CoinSpend` entries before any signature or full mempool validation occurs: [3](#0-2) 

Because parsing an offer file only requires decoding CLVM/serialized bytes (no valid BLS signature is needed to reach `__post_init__`), an attacker can craft an offer whose `WalletSpendBundle.coin_spends` contains two identical `Coin` entries (same `parent_coin_info`, `puzzle_hash`, `amount`) among the "leftover" (non-settlement) coin spends. When such a file is loaded — e.g. via a wallet RPC call that inspects or takes an offer — the `assert cs.coin not in adds` check fails, raising an unhandled `AssertionError` rather than the `ValidationError`/`ValueError` types the rest of the codebase consistently uses for untrusted-input rejection (contrast with the CLVM/mempool layer, which converts equivalent conditions into `Err.DUPLICATE_OUTPUT`/`Err.DOUBLE_SPEND` `ValidationError`s, e.g. `chia/_tests/core/mempool/test_mempool_manager.py:709-717,730-736`).

### Impact Explanation
An `AssertionError` raised inside offer parsing is not a caught, well-typed error like `ValidationError`; if it is not specifically caught at every call site that parses offer files (e.g. RPC handlers such as `get_offer_summary`/`take_offer` in `chia/wallet/wallet_rpc_api.py`, or CLI/GUI offer-preview flows), it propagates as an unhandled exception. This can crash or fail the request-processing path for any wallet that merely inspects a maliciously crafted offer sent by a counterparty — a spend-triggered halt of offer/trade processing reachable without the victim ever accepting or signing the offer. This matches the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Likelihood is high for reachability (offer files are explicitly designed to be exchanged with untrusted counterparties and inspected before acceptance), but I was not able to fully confirm, within the available investigation budget, whether every call site that constructs an `Offer` from external bytes wraps the construction in a broad `try/except Exception` that would downgrade the crash to a handled error (e.g., `chia/wallet/trade_manager.py:666-668` shows at least one such broad `except Exception` around offer creation, but this is for offer *creation*, not necessarily one for all offer *parsing/inspection* call sites). This uncertainty should be resolved by tracing every caller of `Offer.from_bytes`/`Offer.from_bech32` in `wallet_rpc_api.py` and the CLI/GUI before treating this as high-severity in production.

### Recommendation
Replace the bare `assert cs.coin not in adds` (and any other `assert`s in `Offer.__post_init__`/`Offer` methods reachable from untrusted deserialization) with an explicit `raise ValidationError(Err.DOUBLE_SPEND, ...)` or `ValueError`, consistent with how the mempool layer handles the same invariant. Additionally, audit all RPC/CLI entry points that call `Offer.from_bytes`/`from_bech32` to ensure they catch and translate any exception (including `AssertionError`) into a structured RPC error rather than letting it propagate.

    def __post_init__(self) -> None:
        # Verify that there are no duplicate payments
        for payments in self.requested_payments.values():
            payment_programs: list[bytes32] = [p.name() for p in payments]
            if len(set(payment_programs)) != len(payment_programs):
                raise ValueError("Bundle has duplicate requested payments")

        # Verify we have a type for every kind of asset
        for asset_id in self.requested_payments:
            if asset_id is not None and asset_id not in self.driver_dict:
                raise ValueError("Offer does not have enough driver information about the requested payments")

        # populate the _additions cache
        adds: dict[Coin, list[Coin]] = {}
        hints: dict[bytes32, bytes32] = {}
        max_cost = int(DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM)
        for cs in self._bundle.coin_spends:
            # you can't spend the same coin twice in the same SpendBundle
            assert cs.coin not in adds
            try:
                hinted_coins, cost = compute_spend_hints_and_additions(cs, max_cost=max_cost)
                max_cost -= cost
                adds[cs.coin] = [hc.coin for hc in hinted_coins.values()]
                hints = {**hints, **{id: hc.hint for id, hc in hinted_coins.items() if hc.hint is not None}}
            except ValidationError:
                raise
            except ValueError as e:
                if e.args and e.args[0] == "cost exceeded or below zero":
                    raise ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, "compute_additions for CoinSpend") from e
                continue
            except Exception:
                continue
            if max_cost < 0:
                raise ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, "compute_additions for CoinSpend")
        object.__setattr__(self, "_additions", adds)
