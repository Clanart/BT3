### Title
Partial-commit patch generation re-reads the working-directory diff instead of the one the user reviewed/selected against, allowing a repository-controlled file change to silently corrupt what gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-staging flow (selecting individual lines/hunks to include in a commit) computes the user's selection against one diff (the diff rendered in the Changes view and pruned by `withSelectableLines`), but when the commit is actually executed, `applyPatchToIndex` independently re-fetches the diff from disk via `getWorkingDirectoryDiff` and reuses the *old* selection's line indices against this *new* diff. This is structurally the same bug class as the Oracle `viewPrice`/`getPrice` mismatch: a value shown/used to make a decision (the "view") is not the same value used at write time (the "get"), and nothing forces them to match.

### Finding Description
The Changes view diff shown to the user, and the `DiffSelection` (bitset of selected line indices) the user interacts with, are derived from a diff fetched at some point in time and cached in `IChangesState.selection.diff` [1](#0-0) .

When the working directory status is later refreshed and the diff for the selected file is reloaded, Desktop attempts to keep the selection valid by pruning selectable line indices to match the newly loaded diff's hunk positions: [2](#0-1) 

This defensive pruning only happens inside the "load diff for display" path in `app-store.ts`. It does **not** happen at commit time. When the user commits, `_commitIncludedChanges` takes the files/selections currently held in `repositoryStateCache` (which reflect whatever diff was last loaded for display) and passes them straight to `createCommit`: [3](#0-2) 

`createCommit` → `stageFiles` → `applyPatchToIndex` for files with a partial selection: [4](#0-3) 

Crucially, `applyPatchToIndex` does **not** reuse the diff that produced the selection the user saw/edited. It calls `getWorkingDirectoryDiff` again, fresh, right before building the patch: [5](#0-4) 

`formatPatch` then walks the hunks of this newly fetched diff and asks `file.selection.isSelected(absoluteIndex)` for each line, where `absoluteIndex` is `hunk.unifiedDiffStart + lineIndex` computed from the *new* diff's hunk layout: [6](#0-5) 

If the file's on-disk content changes between (a) the moment the diff was last loaded/pruned for display and the selection was made, and (b) the moment `applyPatchToIndex` re-diffs the file to build the patch, the absolute line indices in the new diff no longer correspond to the same logical lines the user selected. `DiffSelection` is a positional/index-based bitmask with no content hash or line-content binding [7](#0-6) , so `isSelected(absoluteIndex)` will happily report "selected" for whatever line now occupies that index - which may be attacker-injected content that didn't exist when the user reviewed and chose their selection.

This is the same broken invariant as the Oracle bug: a "view" computation (diff shown to the user, driving `DiffSelection`) is decoupled from the "get" computation used to actually produce the effect (the freshly re-fetched diff used to build the git patch), and the code never verifies the two are consistent before using stale positional data against fresh content.

### Impact Explanation
A file in the working directory can be modified by anything running as the user in the context of that repository - a build tool, an npm/yarn postinstall or watch script from a package.json in the cloned repo, an editor auto-format-on-save plugin triggered by repository config, or a git hook (`post-checkout`, `post-merge`) shipped inside the malicious repo - between the time the user visually reviews a diff/selects hunks and the time they click "Commit". Because the patch is rebuilt from a fresh diff using stale index-based selection bits, the commit that Desktop produces can silently:
- include attacker-inserted lines that the user never selected (they land at the same absolute index a previously-selected legitimate line occupied), or
- exclude legitimate lines the user intended to commit while including unrelated ones,

corrupting exactly "what the user commits or pushes" without any error or warning shown to the user. Once pushed, this can inject unreviewed content into the remote history under the user's identity.

### Likelihood Explanation
This requires no local/physical access, no elevated privileges, and no credential leakage - only that the user has cloned/opened a repository containing a script or hook that can touch a tracked file during the (often multi-second-to-minutes) window between diff review and commit, which is well within the "attacker controls a cloned/fetched repository" threat model. Desktop already acknowledges "the diff might have changed dramatically since last we loaded it" as a real, expected condition in its own comments, but only handles it for the display path, not for the actual patch-generation path used to build the commit - so no existing guard stops this.

### Recommendation
Before calling `formatPatch` in `applyPatchToIndex`, verify that the diff used to build the patch is the same diff the user's selection was made against (e.g., compare against a content hash/etag of the file or diff captured at selection time, or re-derive `selectableLines` and abort/re-prompt if they differ from what the current selection assumes) rather than silently applying stale positional selection bits to a freshly fetched diff. At minimum, `applyPatchToIndex` should reuse the exact diff object the UI last validated the selection against (passed in explicitly) instead of independently re-fetching it, and should fail loudly if the working tree changed since that diff was captured.

### Proof of Concept
Conceptual PoC (cannot be executed in this read-only environment, but follows directly from the code paths cited above):
1. Clone a repository containing a file `foo.txt` and a `post-checkout`/npm `postinstall` hook (or any auto-running script) that appends attacker content to `foo.txt` a few seconds after checkout/install.
2. In Desktop, open the Changes view for `foo.txt`, showing a legitimate small diff; select only specific lines to include (partial selection), leaving the rest unselected.
3. Wait for the hook/script to append attacker lines to `foo.txt`, shifting/adding hunks.
4. Click "Commit". `_commitIncludedChanges` uses the previously computed `DiffSelection` bitset; `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff, and `formatPatch` (`app/src/lib/patch-formatter.ts:143-206`) maps the stale selection indices onto the new hunk layout.
5. The resulting commit contains different line content than what was visually selected - potentially including the attacker's injected lines - with no warning to the user.

  All = 'All',

  Partial = 'Partial',
  /** The file should be excluded from committing */
  None = 'None',
}

/**
 * Utility function which determines whether a boolean selection state
 * matches the given DiffSelectionType. A true selection state matches
 * DiffSelectionType.All, a false selection state matches
 * DiffSelectionType.None and if the selection type is partial there's
 * never a match.
 */
function typeMatchesSelection(
  selectionType: DiffSelectionType,
  selected: boolean
): boolean {
  switch (selectionType) {
    case DiffSelectionType.All:
      return selected
    case DiffSelectionType.None:
      return !selected
    case DiffSelectionType.Partial:
      return false
    default:
      return assertNever(
        selectionType,
        `Unknown selection type ${selectionType}`
      )
  }
}
