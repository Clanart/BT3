## Title
Payout-tx OP_RETURN malleability lets anyone front-run a fronted withdrawal and get an honest operator falsely challenged/disproved - ([File: core/src/verifier.rs])

### Summary
The withdrawal input signature is a `SinglePlusAnyoneCanPay` Schnorr signature that only commits to input 0 (the withdrawal UTXO) and output 0 (the user payout), leaving all other inputs/outputs of the payout transaction unconstrained. Anyone who observes an honest operator's broadcast-but-unconfirmed payout tx can reuse that public signature to build a fee-bumped variant spending the same withdrawal UTXO with a stripped/garbled OP_RETURN, get it mined first, and cause `Verifier::is_kickoff_malicious` to treat the honest operator's later kickoff as malicious.

### Finding Description
The claimed binding is: `is_kickoff_malicious(...) == true` **iff** the operator's kickoff diverges from a real, funded payout, i.e. `operator_xonly_pk_opt == Some(kickoff_data.operator_xonly_pk)` should hold whenever the operator genuinely funded the withdrawal output.

`is_kickoff_malicious` derives this equality purely from the DB row populated by `update_finalized_payouts`: [1](#0-0) 

That row is populated from whichever transaction is actually observed spending the specific `withdrawal_utxo_txid`/`withdrawal_utxo_vout` outpoint on-chain — this is a 1:1 mapping keyed on the outpoint, with no notion of "the operator's" tx specifically: [2](#0-1) [3](#0-2) 

`operator_xonly_pk` is parsed purely from the first OP_RETURN output of *whichever* tx spends that outpoint; if OP_RETURN is missing/malformed, it becomes `None`: [4](#0-3) 

The root cause is that the operator's payout input signature only covers input 0 and output 0 (`TapSighashType::SinglePlusAnyoneCanPay`), enforced/normalized in the withdrawal RPC parser and used when the operator constructs/signs the payout: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `ANYONECANPAY` excludes all other inputs and `SIGHASH_SINGLE` only commits output index 0, the anchor output (index 1) and the OP_RETURN output (index 2) containing the operator's xonly pubkey are **not signed**. Any unprivileged attacker who sees the operator's payout transaction (public, once broadcast to the mempool) can:
1. Copy input 0 (`withdrawal_utxo`) and its witness (signature+sighash flag) unchanged.
2. Copy output 0 (payout output) unchanged (mandated by the signature).
3. Add their own fee-paying input(s) and a different (or no) OP_RETURN output.
4. Broadcast this variant with a higher fee (RBF/CPFP or plain fee race) so it confirms instead of the operator's original tx.

Once this attacker tx confirms, `update_finalized_payouts` records `operator_xonly_pk = None` for that withdrawal idx (or, if the attacker fills in a garbage/foreign OP_RETURN, a mismatching pubkey). When the honest operator's already-broadcast kickoff for that same withdrawal is processed, `is_kickoff_malicious` hits the `operator_xonly_pk_opt` `None` branch and returns `Ok(true)`, even though the operator did in fact fund the withdrawal via its own signed payout tx that just lost the confirmation race.

`handle_kickoff` then queues a `Challenge` tx (on non-mainnet/testnet4 networks) for the honest operator's kickoff, feeding into the disprove pipeline that ultimately burns that operator's round-tx collateral: [8](#0-7) 

No existing guard catches this: `is_deposit_valid`, `SPV::verify`, `verify_storage_proofs`, and the presigned tx graph all operate on whichever tx actually spent the withdrawal UTXO — they have no way to distinguish "the tx the operator intended to broadcast" from "the tx that a griefer got mined instead," since the signature itself does not bind the OP_RETURN or fee-paying inputs.

### Impact Explanation
An honest operator that genuinely fronted a withdrawal from its own funds can have its round-tx collateral challenged and ultimately disproved/burned, purely because a third party won a fee race for the withdrawal UTXO with a mutated copy of the same signed spend. This is a Critical-severity outcome ("an honest operator's collateral burned") per the stated impact categories, and it is repeatable across every withdrawal handled by every operator, since the vulnerability is structural (sighash flag choice), not specific to one deposit/operator pair.

### Likelihood Explanation
The attack requires no privileged role, no key compromise, and no majority hashrate — only the ability to observe the public mempool/broadcast a competing Bitcoin transaction with a higher fee, which is explicitly within the allowed attacker capabilities ("anyone who can broadcast Bitcoin transactions and pay fees ... choose ... a Schnorr signature and its sighash flag"). The attacker's cost is only the fee difference needed to win the confirmation race (and dust for an extra input), making this cheap and directly repeatable for every fronted withdrawal an attacker wants to grief.

### Recommendation
Require the payout transaction signature to commit to all outputs that matter for correctness (at minimum, cover the OP_RETURN operator-attribution output, e.g. by using `SIGHASH_ALL` for a transaction template constructed/covenant-enforced by the operator, or by having the protocol authenticate `operator_xonly_pk` some other way that is not malleable independently of the user's signature) so that a third party cannot reuse the user's signature to strip/alter operator attribution while still spending the same withdrawal UTXO. Alternatively, treat a payout tx whose OP_RETURN is missing/invalid as inconclusive rather than automatically "malicious," and instead verify against the specific payout tx the operator itself broadcast (e.g., track the operator's exact intended txid/witness prior to confirmation) before concluding maliciousness.

### Proof of Concept
Extend `core/src/test/manual_reimbursement.rs`:
1. Run a deposit and register a withdrawal as in `deposit_and_get_reimbursement`.
2. Have operator 0 sign/broadcast its real `Payout` tx (with a correct OP_RETURN carrying `op0_xonly_pk`) via `payout_and_start_kickoff`-style helper, but do NOT let it confirm.
3. Before it confirms, craft and broadcast an alternate transaction spending the identical `withdrawal_utxo` outpoint, reusing the identical witness/signature for input 0 and identical output 0, but replacing output 2 with an invalid/garbled OP_RETURN and adding attacker-funded fee input(s)/higher fee, then mine it so it confirms instead of the operator's tx.
4. Allow the state manager to process `update_finalized_payouts` for that block, then trigger `check_if_kickoff_malicious` for the operator's already-in-flight kickoff.
5. Assert `Verifier::is_kickoff_malicious` (or `handle_kickoff`) returns `true` and that a `Challenge` tx is enqueued for operator 0's kickoff, despite operator 0 having genuinely signed/broadcast a correctly-funded payout tx for that withdrawal — demonstrating the binding `operator_xonly_pk_opt == Some(op0_xonly_pk)` fails to hold even though the operator did fund the payout.

    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
