### Title
Zero-Operator Deposit Bypasses All N-of-N and Operator Signature Requirements, Permanently Locking Bridged BTC — (`core/src/builder/sighash.rs`, `core/src/verifier.rs`)

---

### Summary

`get_num_required_nofn_sigs` is a pure product that includes `deposit_data.get_num_operators()` as a multiplicative factor. When the operator count is zero — which occurs at fresh deployment before any operator registers, or when the aggregator is configured with an empty operator endpoint list — the function returns `0`. Every downstream signature-count guard in the deposit pipeline uses `== 0` equality checks that pass vacuously, so the entire MuSig2 signing ceremony for all BitVM pre-signed transactions (kickoff, payout, challenge, disprove) is skipped. The move transaction is still created and broadcast, permanently locking the deposited BTC in the bridge vault with no mechanism for withdrawal.

---

### Finding Description

**Root cause — `get_num_required_nofn_sigs` collapses to zero**

```rust
// core/src/builder/sighash.rs  lines 50-55
pub fn get_num_required_nofn_sigs(&self, deposit_data: &DepositData) -> usize {
    deposit_data.get_num_operators()          // ← zero kills the whole product
        * self.protocol_paramset().num_round_txs
        * self.protocol_paramset().num_signed_kickoffs
        * self.get_num_required_nofn_sigs_per_kickoff(deposit_data)
}
``` [1](#0-0) 

`get_num_required_nofn_sigs_per_kickoff` always returns at least `7 + 4*N_verifiers + 2*assert_txs ≥ 7`, so the only way the product is zero is if `get_num_operators() == 0`, `num_round_txs == 0`, or `num_signed_kickoffs == 0`. The zero-operator case is the most reachable.

**How `num_operators` reaches zero**

In `new_deposit`, the aggregator populates `deposit_data.actors.operators` by calling `fetch_operator_keys()`:

```rust
// core/src/rpc/aggregator.rs  lines 1464-1473
let deposit_data = DepositData {
    actors: Actors {
        verifiers: self.fetch_verifier_keys().await?,
        watchtowers: vec![],
        operators: self.fetch_operator_keys().await?,   // empty Vec if no operators
    },
    ...
};
``` [2](#0-1) 

`fetch_pubkeys_from_entities` initialises `operator_keys` as `vec![None; operator_clients.len()]`. When `operator_clients` is empty, `keys.iter().all(|k| k.is_some())` is vacuously `true`, so the function returns `Ok(vec![])` without error. [3](#0-2) 

**`is_deposit_valid` does not enforce a minimum operator count**

The verifier's deposit validation checks uniqueness, watchtower limits, security council, and that every DB-registered operator with usable collateral appears in the deposit. At fresh deployment the operator DB is empty, so the loop over `operators_in_db` is a no-op and the deposit with zero operators passes all checks:

```rust
// core/src/verifier.rs  lines 603-658
let operators_in_deposit_data = deposit_data.get_operators();   // empty
let operators_in_db = self.db.get_operators(None).await?;       // empty at fresh deploy
for (xonly_pk, ...) in operators_in_db.iter() { ... }          // never executes
for operator_xonly_pk in operators_in_deposit_data { ... }      // never executes
``` [4](#0-3) 

**All pipeline guards pass vacuously when `needed_nofn_sigs == 0`**

`nonce_aggregator` — the sighash stream yields zero items (no operators in `create_nofn_sighash_stream`), so `total_sigs == 0 == needed_nofn_sigs`: [5](#0-4) 

`signature_distributor` — `sig_count == 0 == needed_nofn_sigs`: [6](#0-5) 

`deposit_finalize` RPC — `nonce_idx == 0`, check `nonce_idx < num_required_nofn_sigs` is `0 < 0 = false`: [7](#0-6) 

Operator sig check — `num_required_total_op_sigs = num_required_op_sigs * 0 = 0`, check `total_op_sig_count < 0` is false: [8](#0-7) 

`deposit_sign` verifier — `num_required_sigs + 2 = 2` nonces are requested and generated, nonce count check passes; the agg-nonce receive loop exits immediately because the aggregator sends zero agg-nonces; the remaining-nonce check `session.nonces.len() != 2` passes: [9](#0-8) 

**Move transaction is still created and broadcast**

After the zero-iteration pipeline, the aggregator proceeds to `create_movetx` using the two move-tx/emergency-stop partial signatures that verifiers do produce. The signed move transaction is returned to the caller and broadcast, transferring the user's BTC into the bridge vault. [10](#0-9) 

---

### Impact Explanation

The bridge vault receives the deposited BTC, but **none of the BitVM pre-signed transactions exist**: no kickoff UTXOs are signed, no payout transactions are pre-signed, no watchtower challenge or disprove transactions are pre-signed. Because withdrawals require an operator to broadcast a pre-signed kickoff transaction, and no such transaction was ever created, the deposited BTC is **permanently locked** in the N-of-N vault with no recovery path. This satisfies the "permanent lock of bridged BTC" impact criterion.

---

### Likelihood Explanation

The condition is met in two realistic scenarios:

1. **Fresh deployment** — before any operator calls `setup` and registers in the verifier DB, the DB is empty. A user deposit processed at this moment produces a zero-operator `DepositData` that passes all checks.
2. **Misconfigured aggregator** — if `operator_endpoints` is set to an empty list `[]` in the aggregator config, `fetch_operator_keys()` returns `Ok(vec![])` on every call. Any deposit processed by this aggregator is permanently broken.

Neither scenario requires a malicious actor; both are reachable through normal operational conditions (race at launch, config error).

---

### Recommendation

1. **Enforce a minimum operator count in `is_deposit_valid`** (`core/src/verifier.rs`):

```rust
if deposit_data.get_num_operators() == 0 {
    return Err(BridgeError::InvalidDeposit(
        "Deposit must include at least one operator".to_string()
    ));
}
```

2. **Add a non-zero guard in `get_num_required_nofn_sigs`** (`core/src/builder/sighash.rs`) or assert the result is non-zero before using it as a loop bound.

3. **Validate `num_round_txs >= 1` and `num_signed_kickoffs >= 1`** in `ProtocolParamset::from_env()` alongside the existing `finality_depth >= 1` check (`core/src/config/protocol.rs`). [11](#0-10) 

---

### Proof of Concept

**Trigger path (no malicious actor required):**

1. Deploy Clementine with an aggregator whose `operator_endpoints = []` (or before any operator has called `setup`).
2. A user creates a valid deposit UTXO at the expected taproot address and calls `aggregator.new_deposit(deposit_outpoint)`.
3. `fetch_operator_keys()` returns `Ok(vec![])` → `deposit_data.get_num_operators() == 0`.
4. `get_num_required_nofn_sigs(&deposit_data) == 0 * ... == 0`.
5. `create_nonce_streams` requests `0 + 2 = 2` nonces from each verifier — succeeds.
6. `nonce_aggregator` iterates zero sighashes, `total_sigs == 0 == needed_nofn_sigs` — passes.
7. `signature_distributor` sends zero signatures, `sig_count == 0 == needed_nofn_sigs` — passes.
8. Each verifier's `deposit_sign` receives zero agg-nonces, exits loop, `session.nonces.len() == 2` — passes.
9. Each verifier's `deposit_finalize` iterates zero sighashes, `nonce_idx == 0`, `0 < 0` is false — passes; operator sig check `0 < 0` is false — passes.
10. Verifiers return move-tx and emergency-stop partial signatures.
11. `create_movetx` assembles and returns the signed move transaction.
12. Move transaction is broadcast; user's BTC enters the vault.
13. **No kickoff, payout, challenge, or disprove transactions were ever pre-signed. The BTC is permanently locked.**
