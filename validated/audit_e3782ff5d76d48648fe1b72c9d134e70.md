### Title
Unbalanced/nested conflict-marker text lets Copilot's conflict resolver conflate unrelated code into one hunk, silently corrupting committed content - ([File: app/src/lib/copilot-conflict-context.ts], [File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The reported bug is a *boundary-miscalculation* class of issue: a threshold/parsing routine assumes a monotonic, well-formed input structure, and when that assumption breaks (crossing 500,000 in the TON contract), the output jumps discontinuously in a way an attacker can exploit. GitHub Desktop's AI merge-conflict resolver (`extractConflictHunks` / `reassembleResolvedFile`) has the same class of defect: both functions are naive line-scanners that locate conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) using identical regexes but **never validate that markers are balanced or non-nested**. A single stray/incomplete marker sequence anywhere in a file — trivially placed there by anyone who can influence file content in a repository the user later merges — causes the parser to treat a large, unrelated span of the file as "conflict content," which the AI model rewrites and which is later spliced back into the file and staged for commit.

### Finding Description
`extractConflictHunks` in [1](#0-0)  walks the file line-by-line: on seeing an "ours" marker it collects "ours" lines until the **first** line matching the separator/base marker, then collects "theirs" lines until the **first** line matching the theirs marker. It performs no check that this is the *nearest logically-paired* set of markers — it simply takes whatever separator/closing marker appears next in the file, however far away.

`reassembleResolvedFile` in [2](#0-1)  performs an independent, structurally similar scan when splicing the model's per-hunk output back into the original file. Its look-ahead for `hasSeparator`/`closingIndex` (lines 563-572) likewise scans forward for the first separator, then the first theirs marker, regardless of any other marker-like lines encountered in between.

Because a file that contains a **single unmatched `<<<<<<<`-like line** (e.g. a documentation/example file explaining Git conflict-marker syntax, or a fixture/test file that shows unresolved-merge examples) followed later by a genuine merge conflict marker sequence, both `extractConflictHunks` and `reassembleResolvedFile` will treat the intervening code — including the real conflict's own markers and both sides' real content — as a single opaque "ours"/"theirs" blob. `getHunkSkipReason` ( [3](#0-2)  only gates on total character/line-length size, not marker balance, so this conflated "hunk" sails through unless it happens to exceed `MAX_CONFLICT_CONTENT_SIZE`.

The conflated content — much larger than a real hunk and including code the model never should have touched — is sent to the AI model. The model's contract (`ConflictResolutionSystemPrompt`, [4](#0-3) ) instructs it to make "MINIMAL changes," but the model has no way to know that the huge span it received is not itself a legitimate conflict; it will synthesize new content in place of everything between the stray marker and the real closing marker. `reassembleResolvedFile` then splices this synthetic content in verbatim (lines 584-591), and `validateResolutionPaths` ( [5](#0-4)  only checks hunk *counts* match between extraction and the model's response — it cannot detect that the hunk boundaries themselves were computed incorrectly.

The result is written straight to disk and staged in `_applyCopilotConflictResolutions`: [6](#0-5) . The only remaining guard is the diff shown in the "Changes" tab of `CopilotConflictsDialog` ( [7](#0-6) ) — a large, plausible-looking AI-authored diff that a user reviewing dozens of resolved files during a merge/rebase is unlikely to scrutinize line-by-line, especially since the tool's whole purpose is to reduce manual review burden.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": unrelated, legitimate code between a planted marker-like line and a real conflict's closing marker can be silently deleted/rewritten by the AI and then staged/committed by the user via the normal "Continue merge/rebase" flow, without the user needing to take any unnatural steps — they only need to have a real merge conflict in a file that also happens to contain marker-like example/documentation text, which is common in tooling, documentation, and even source comments about Git.

### Likelihood Explanation
The attacker only needs write access to file *content* that the victim will eventually pull/fetch and merge — e.g. contributing a README/CONTRIBUTING doc containing an unmatched `<<<<<<<` example line, or a test fixture demonstrating conflict markers, in a normal PR. No local access, credentials, or social engineering beyond a routine contribution is required. The likelihood of triggering full corruption is moderated by: (1) the feature is opt-in (user must click "Resolve with Copilot"), and (2) a diff review step exists before commit. However, given large multi-file merges and the tool's purpose of reducing review effort, a user is plausible to overlook a bloated diff on one file among many.

### Recommendation
Add marker-balance validation to `extractConflictHunks` and `reassembleResolvedFile`: reject (or fall back to "skip file, resolve manually") whenever an opening `<<<<<<<` marker is encountered while already inside another candidate conflict block, or when the distance/marker count between an opening marker and its matched separator/closing marker doesn't correspond to a single well-formed 2-way/3-way conflict (e.g., disallow a second `<<<<<<<` appearing between the "ours" marker and its resolved closing `>>>>>>>`). Cross-check that the count and positions of markers detected by `extractConflictHunks` exactly match those consumed by `reassembleResolvedFile` for the same file, and treat any mismatch as a hard validation failure rather than silently proceeding.

### Proof of Concept
1. Attacker submits a PR/commits to a shared branch adding a file, e.g. `docs/merge-help.md`, containing a paragraph such as:
   ```
   When git can't merge, you'll see:
   <<<<<<< HEAD
   explaining what "ours" looks like...
   ```
   with **no** matching `=======`/`>>>>>>>` nearby in that section, but a real merge conflict is later introduced by normal development in the *same file* further down (e.g. two branches both edit a later section of `docs/merge-help.md`), producing genuine `<<<<<<<`/`=======`/`>>>>>>>` markers below the attacker's text.
2. Victim performs a merge/rebase that conflicts on `docs/merge-help.md` and clicks "Resolve with Copilot."
3. `extractConflictHunks` starts at the attacker's stray `<<<<<<<` line, keeps consuming lines as "ours" content until it hits the real `=======` line further down (mistaking it for this bogus hunk's separator), then keeps consuming as "theirs" content until the real `>>>>>>>` — producing one hunk whose `oursContent`/`theirsContent` actually contain the entire real conflict (including its own markers) plus everything in between.
4. The model rewrites this oversized blob per the system prompt's "minimal changes" instruction, but has no ground truth for what should be preserved verbatim.
5. `reassembleResolvedFile` splices the model's output over the same (incorrectly large) span, and `_applyCopilotConflictResolutions` writes and `git add`s the result — corrupting/removing legitimate content that was never actually part of any real conflict, without further validation that would catch the mismatch.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
