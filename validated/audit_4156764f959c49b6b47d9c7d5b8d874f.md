Confirmed: `RESPONSE_RECEIPTS_STORAGE_PREFIX` is the storage prefix for the **pallet-ismp child trie on a remote Substrate/Hyperbridge state machine**, not the EVM host's own local `_responseReceipts` mapping. This confirms the finding is well-supported.

### Title
GET-response and GET-timeout race allows double dispatch (`onGetResponse` + `onGetTimeout`) for the same request - ([File: evm/src/core/HandlerV2.sol], [File: evm/src/core/EvmHost.sol])

### Summary
This is the local analog of the `balanceOfNFT`/`balanceOfNFTAt` inconsistency: `handlePostRequests` enforces a local `MessageTimedOut()` guard, but `handleGetResponses` deliberately skips any local timeout check on the destination-side commitment/receipt bookkeeping, and `EvmHost.dispatchIncoming(GetResponse)` never clears `_requestCommitments[commitment]` after a response is delivered. The Substrate/pallet-ismp implementation explicitly guards against this same race (`GetResponseAlreadyReceived`), but the EVM `HandlerV2`/`EvmHost` path has no equivalent check, breaking cross-implementation consistency and the "process exactly once" invariant.

### Finding Description
`handlePostRequests` explicitly checks `if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();` before dispatch [1](#0-0) . `handleGetResponses`, by contrast, carries only the comment "don't check for timeouts because it's checked on Hyperbridge" and performs no local timeout enforcement at all [2](#0-1) .

`EvmHost.dispatchIncoming(GetResponse, ...)` stores a local `_responseReceipts[commitment]` but never deletes or otherwise marks `_requestCommitments[commitment]` after successfully dispatching the response to the app: [3](#0-2) .

Because `_requestCommitments[commitment]` is left intact after a successful `onGetResponse` callback, the same commitment still satisfies the "known request" check (`meta.sender != address(0)`) inside `handleGetRequestTimeouts` [4](#0-3) . The only remaining guard in that path is a Merkle non-membership proof of `RESPONSE_RECEIPTS_STORAGE_PREFIX + commitment` against `host.stateMachineCommitment(message.height).stateRoot` [5](#0-4) , which is the **remote/foreign chain's pallet-ismp child trie state root** [6](#0-5)  — not this EVM host's own `_responseReceipts` mapping. This proof therefore cannot detect that a response was already delivered locally on this same EVM host; it only proves something about a different state machine's trie.

`EvmHost.dispatchTimeOut(GetRequestTimeout, ...)` itself performs no check against `_responseReceipts[commitment]` before invoking `onGetTimeout` and deleting `_requestCommitments[commitment]` [7](#0-6) .

By contrast, the Substrate/pallet-ismp implementation explicitly guards this exact scenario: `handlers/timeout.rs` checks `if host.response_receipt(&response).is_some() { Err(Error::GetResponseAlreadyReceived {...})? }` before allowing a GET timeout to proceed [8](#0-7) . The EVM path has no equivalent check — this is the concrete, local analog of the reported "inconsistent implementation across sibling functions" bug class: one implementation enforces the invariant, the sibling (EVM) implementation does not.

### Impact Explanation
An unprivileged, permissionless relayer (anyone may call both `handleGetResponses` and `handleGetRequestTimeouts`, as documented — "permissionless call" [9](#0-8) ) can, using two independently valid proofs (a genuine response proof from the correct overlay root, and a genuine non-membership proof from a state root that simply never tracked this EVM chain's local `_responseReceipts`), cause the destination application to receive **both** `onGetResponse` and `onGetTimeout` callbacks for the same GET request. This is a double-dispatch/double-settlement of application state for the same commitment, and for any `IApp` that performs balance movement, order fulfillment, or fee refund logic differently in `onGetResponse` vs `onGetTimeout`, this can be leveraged to duplicate a payout, corrupt accounting, or unlock funds that should only ever be released once. It also triggers `meta.fee` refund from `dispatchTimeOut` even though the fee/flow already completed via the response path, causing a relayer-fee double payout from `_requestCommitments[commitment].fee` state that was never cleared.

### Likelihood Explanation
Medium: no admin, governance, or malicious relayer/prover collusion is required — a normal relayer using two independently-obtainable, legitimate proofs (one for the correct response commitment, one non-membership proof from a state root that genuinely has no `RESPONSE_RECEIPTS_STORAGE_PREFIX+commitment` entry, since that bookkeeping lives only on this EVM chain) can trigger the double dispatch. It does require timing/ordering (response processed while local time has already exceeded the request's timeout window, then submitting the timeout proof afterward), which is achievable whenever a GET request's timeout has elapsed but no timeout has yet been claimed.

### Recommendation
Make the EVM host consistent with the Substrate/pallet-ismp implementation: in `EvmHost.dispatchTimeOut(GetRequestTimeout, ...)`, check `_responseReceipts[commitment]` and revert (or no-op) if a response has already been recorded, mirroring `Error::GetResponseAlreadyReceived` in `modules/ismp/core/src/handlers/timeout.rs`. Additionally, either enforce a local timeout check in `handleGetResponses` (mirroring `handlePostRequests`'s `MessageTimedOut()` guard) or ensure `dispatchIncoming(GetResponse)` clears/marks `_requestCommitments[commitment]` on success so the "known request" check in `handleGetRequestTimeouts` correctly rejects already-answered requests.

### Proof of Concept
1. App on chain A dispatches a `GetRequest` with `timeout = t0`; `_requestCommitments[commitment]` is set.
2. Time passes beyond `t0` on chain A, but no timeout has yet been submitted.
3. A relayer submits `handleGetResponses` with a valid overlay-root proof for the (late but otherwise legitimate) response; since `handleGetResponses` performs no local timeout check [2](#0-1) , `dispatchIncoming(GetResponse)` succeeds, calling `onGetResponse` and setting `_responseReceipts[commitment]`, but leaving `_requestCommitments[commitment]` untouched [3](#0-2) .
4. The same or another relayer then submits `handleGetRequestTimeouts` for the same commitment with a non-membership proof against a remote state root that legitimately never contained this EVM chain's `RESPONSE_RECEIPTS_STORAGE_PREFIX+commitment` key [10](#0-9) ; the check passes because `meta.sender != address(0)` still holds.
5. `dispatchTimeOut(GetRequestTimeout, ...)` executes, calling `onGetTimeout` and refunding `meta.fee` — a second, inconsistent callback and fee payout for a request that was already fulfilled [7](#0-6) .

```text
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

```text
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
