### Title
Reachable assertion failure in `TransactionQueue.pop()` can crash the full node's transaction-processing task, halting all further mempool admission - (File: `chia/full_node/tx_processing_queue.py`)

### Summary
The Node.js CVE described a crash triggered by an attacker sending a small number of crafted protocol frames that violated an internal invariant, causing an assertion to fail on a code path that was reached from unprivileged network input, killing the process. Chia's peer transaction admission queue, `TransactionQueue`, has an analogous internal invariant that its own code does not actually enforce: `put()` accepts a `PeerWithTx` entry with `advertised_cost == 0` for the priority calculation, while `pop()` later asserts that the same value is strictly greater than zero.

### Finding Description
`TransactionQueue.put()` in [1](#0-0)  computes the priority for an entry:

```python
tx_info = tx.peers_with_tx.get(peer_id)
if tx_info is not None and tx_info.advertised_cost > 0:
    ...
    priority = -fpc
else:
    priority = float("inf")
```

Note that when `tx_info.advertised_cost == 0`, the code falls into the `else` branch and *still enqueues the entry* with `priority = float("inf")` — it does not reject or drop the entry. `tx_info` (a `PeerWithTx`, see [2](#0-1) ) with `advertised_cost = 0` is therefore a value that can legitimately sit in the peer's priority queue.

Later, `TransactionQueue.pop()` reads back that same `tx_info` and asserts the opposite invariant:

```python
tx_info = entry.peers_with_tx.get(peer_id)
if tx_info is not None:
    # At this point we have no transactions with zero cost
    assert tx_info.advertised_cost > 0
``` [3](#0-2) 

The comment "we have no transactions with zero cost" is not actually guaranteed by `put()`; `put()` explicitly allows `advertised_cost == 0` to pass through unfiltered. `advertised_cost`/`advertised_fee` originate from the peer-supplied `new_transaction`/transaction-advertisement fields that populate `peers_with_tx`, i.e., they are attacker-controlled values carried on the standard transaction-relay path used by any node/peer relaying a spend bundle (the same path an unprivileged spend-bundle submitter uses to get a transaction into the network via a peer connection), not values that have been validated by CLVM/mempool admission before this point — `TransactionQueue` sits in front of `MempoolManager.add_spend_bundle()`, so cost has not yet been independently verified when the entry reaches `pop()`.

`pop()` is awaited from the full node's background transaction-processing loop (`_transaction_queue_task`, created once in `FullNode.manage()`, see [4](#0-3)  and cancelled only on node shutdown at [5](#0-4) ). There is no evidence in this loop of automatic task respawn on unexpected exception; an uncaught `AssertionError` raised inside `pop()` terminates that task permanently.

### Impact Explanation
If this single background task dies from the assertion failure, the full node stops draining `TransactionQueue` entirely. Because this queue is the intake path for peer-relayed spend bundles feeding `MempoolManager.add_spend_bundle()`, once the task is dead the node will never again admit peer-submitted transactions into its mempool — a persistent, spend/advertisement-triggered transaction-processing halt for that node, closely mirroring the "server crashes instantly after sending a few HTTP/2 frames" impact of the original report (uncontrolled resource consumption / total denial of transaction service triggered by a small amount of attacker-controlled input).

### Likelihood Explanation
Triggering requires only that a peer/attacker cause a `PeerWithTx` entry with `advertised_cost == 0` to be recorded for some spend bundle, and that this same peer's queue subsequently be the "top" (or only) contender polled by `pop()`'s deficit round-robin scan. Since `advertised_cost` is peer-advertised metadata not yet consensus-validated at intake time, and `put()` performs no lower-bound check before accepting the entry, this appears reachable with a single relayed transaction advertisement, making this a low-effort, high-confidence trigger once the invariant mismatch is confirmed live (i.e., confirming that no other upstream code path filters zero-cost `PeerWithTx` records before they reach `put()`).

### Recommendation
- Make `TransactionQueue.put()` and `pop()` enforce the same invariant: either reject/normalize `advertised_cost == 0` entries at `put()` time (treating them the same as "unknown cost," using `float("inf")` priority but also flagging `tx_info` as absent for the `pop()` zero-cost assumption), or remove the `assert tx_info.advertised_cost > 0` in `pop()` and replace it with a graceful fallback (e.g., treat zero cost like "unknown" and use `self._max_tx_clvm_cost`).
- Wrap the body of the full node's transaction-processing loop (`_handle_transactions`, which drives `TransactionQueue.pop()`) so that any unexpected exception is logged and the loop continues/respawns rather than silently dying, preventing a single malformed advertisement from permanently disabling transaction intake.
- Add a regression test that calls `put()` with a `PeerWithTx(advertised_cost=uint64(0), ...)` for a peer whose queue is later polled via `pop()`, and assert the call does not raise.

### Proof of Concept
Not independently executed against a live node in this analysis; root cause is demonstrated directly from source:
1. Call `TransactionQueue.put(entry, peer_id)` with `entry.peers_with_tx[peer_id] = PeerWithTx(peer_host, advertised_fee=uint64(0), advertised_cost=uint64(0))` — this succeeds and enqueues the entry ( [1](#0-0) ).
2. Call `await TransactionQueue.pop()` when this peer's entry is the queue's top candidate — the `assert tx_info.advertised_cost > 0` at line 185 fails, raising `AssertionError` ( [3](#0-2) ).
3. In production, `pop()` is awaited inside the full node's long-running transaction-processing task; an uncaught exception there is not shown to be handled/respawned anywhere in the reviewed `FullNode.manage()` lifecycle code, so the task dies and peer-transaction admission halts for the remaining lifetime of the process.

I was not able to directly inspect the full body of `_handle_transactions()` in `chia/full_node/full_node.py` in this pass to confirm whether it has broader exception suppression around the `pop()` call; this should be verified in a live/full-repository session (e.g., a Devin session with complete file access) before treating the "permanent halt" impact as fully confirmed versus "logged and recovered."
