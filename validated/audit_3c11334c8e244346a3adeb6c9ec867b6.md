### Title
Unbounded buffer read in CLVM canonical-serialization check causes an uncaught `IndexError` on malformed/truncated puzzle or solution bytes - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_clvm_canonical()` and its helper `is_atom_canonical()` walk a raw `bytes` buffer using a length prefix taken from the buffer itself, but never validate that the computed `offset` stays inside the buffer before dereferencing it. This mirrors the CVE-2014-8127 bug class: a length/size field parsed from untrusted input is trusted to index further reads without a bounds check, leading to an out-of-bounds access on malformed input.

### Finding Description
`is_atom_canonical()` reads `clvm_buffer[offset]` and then, for multi-byte length prefixes, increments `offset` up to 5 more times and reads `clvm_buffer[offset]` again in a loop with no check that `offset < len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()` calls this in a loop and also indexes `clvm_buffer[offset]` directly without a bounds check before calling `is_atom_canonical`: [2](#0-1) 

Because Python raises `IndexError` (not silently reading garbage as in C) when `bytes.__getitem__` is called with an out-of-range index, any coin-spend puzzle/solution bytes crafted so a length-prefix byte claims a multi-byte atom length prefix that runs past the end of the actual buffer will raise an unhandled `IndexError` inside this function.

This function is documented as being used to determine DEDUP-eligibility of mempool items — i.e. it inspects the puzzle/solution bytes of individual coin spends inside a submitted `SpendBundle`: [3](#0-2) 

The exception-handling around spend-bundle validation in `MempoolManager.pre_validate_spendbundle()` only catches `ValueError` from the CLVM/signature validation call; it has no protection for an `IndexError` raised elsewhere in the mempool admission pipeline (e.g., during dedup-eligibility classification of a bundle's coin spends): [4](#0-3) 

Since `is_clvm_canonical`/`is_atom_canonical` are pure bytes-walking helpers with no exception guard at their own call sites, an uncaught `IndexError` will propagate up through whatever mempool code path invokes them.

### Impact Explanation
An uncaught `IndexError` triggered by a single attacker-submitted spend bundle can crash or abort the mempool-processing task/thread handling that bundle. Depending on where in the pipeline the exception surfaces (worker pool task vs. main event loop), this can manifest as a spend-triggered transaction-processing halt for that submission path, which is one of the explicitly in-scope impact categories (spend-triggered transaction-processing halt). This is reachable by any unprivileged spend-bundle submitter — no special privileges, peer trust, or node access are required, only crafting a puzzle-reveal or solution byte sequence with a malformed/truncated multi-byte atom length prefix.

### Likelihood Explanation
The precondition is simple to construct: a solution or puzzle-reveal blob ending in a truncated multi-byte length-prefix atom (e.g., an `0xF8`-`0xFE`-class prefix byte placed at or near the very end of the buffer so that `offset` walks past `len(clvm_buffer)`). This requires no cryptographic material and no coordination with other nodes — it is a pure malformed-serialization construction submittable by any wallet/RPC client that can build a `CoinSpend`/`SpendBundle`.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` and `is_clvm_canonical()` before each buffer index/read (`offset < len(clvm_buffer)`), returning "not canonical" (or raising a caught, well-typed error) instead of relying on Python's implicit `IndexError`. Additionally, wrap dedup-eligibility / canonical-serialization checks at their call sites with defensive exception handling so a malformed buffer degrades to "not eligible" rather than propagating an unhandled exception through mempool admission.

### Proof of Concept
Constructing a buffer whose final byte is a multi-byte-length-prefix atom marker with no following length bytes reproduces the crash directly against the exposed function:
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0xF8 signals a 4-byte-prefix atom (see mask 0b11111100 == 0b11111000 branch),
# but the buffer ends immediately after this byte.
buf = b"\xf8"
is_clvm_canonical(buf)  # raises IndexError: index out of range
```
This same style of truncated atom-length-prefix byte can be embedded as a coin spend's `solution`/`puzzle_reveal` bytes in a submitted `SpendBundle`; whichever mempool code path calls `is_clvm_canonical`/`is_atom_canonical` on that data (per the documented DEDUP-eligibility use) will raise this uncaught `IndexError`. def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value


def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)

## Canonical serialization

**Location**: `mempool_manager.py:185`

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.
