### Title
Native-token ERC20 pointer advertises display `decimals()` while `balanceOf`/`totalSupply`/`transfer` operate on unscaled base-denom (usei) integers - ([File: contracts/src/NativeSeiTokensERC20.sol])

### Summary
The pointer precompile's `AddNative` flow creates an `NativeSeiTokensERC20` ERC20 wrapper for a native Sei bank denom (e.g. `usei`) and sets the ERC20 `decimals()` value to the *display* exponent taken from the denom's `DenomUnit` metadata (e.g. `6` for `usei`→`sei`), while every balance-affecting function (`balanceOf`, `totalSupply`, `transfer`/`_update`) forwards the *raw, unscaled* integer amount stored by the bank module in base units. This mirrors the reported Blueberry bug class: a "decimals"/precision value used by external consumers does not match the actual decimal scale of the numeric values returned, causing systematic mis-valuation.

### Finding Description
In `precompiles/pointer/pointer.go` (`AddNative`), the pointer keeper picks the `DenomUnit` with the highest `Exponent` from bank denom metadata and uses that `Exponent` as the ERC20 contract's `Decimals` field: [1](#0-0) 

That `decimals` (e.g. `6` for `usei`, since `1 sei = 10^6 usei`) is passed into `UpsertERCNativePointer`, which deploys `NativeSeiTokensERC20`: [2](#0-1) 

`NativeSeiTokensERC20.sol` stores this value verbatim in `decimals()`, but `balanceOf`, `totalSupply`, and the internal `_update` (used by `transfer`/`transferFrom`) all read/write the **raw bank balance in the base denom** (`usei`) via the bank precompile, with no `10^decimals` scaling applied anywhere: [3](#0-2) 

This is the inverse of the deliberate design used elsewhere in the codebase: the bank precompile itself always reports `decimals() == 0` for native tokens specifically *because* balances/transfers operate on raw integer base-denom units: [4](#0-3) 

So the same underlying value (raw `usei` integer) is exposed through two different EVM-reachable ERC20 surfaces with **contradictory `decimals()` semantics** — `0` via the bank precompile's native ERC20 view vs. the display exponent (e.g. `6`) via the pointer-deployed `NativeSeiTokensERC20`. Any code (a DEX, lending market, price oracle adapter, or generic ERC20-aware contract) that composes `balanceOf()` with `decimals()` following the standard ERC20 convention (`humanAmount = balanceOf() / 10**decimals()`) will compute a value that is off by `10^decimals` (e.g. 10^6 for `usei`) versus the true balance in the underlying bank module.

### Impact Explanation
Because this pointer is a normal ERC20-shaped contract reachable by any EVM contract or transaction (registered permissionlessly via the pointer precompile for denoms with bank metadata, `precompiles/pointer/pointer.go:AddNative`), any third-party contract (AMM, money-market, price feed) built against it and trusting the declared `decimals()` will systematically under- or over-value the wrapped native token by a factor of `10^decimals` (up to `10^6` or more depending on the denom's display exponent). In a liquidity pool, lending, or collateral-valuation context this directly enables fund-loss/mis-pricing exploits (e.g., depositing/borrowing against a token whose value is computed 10^6x too low or too high), matching the "unauthorized transfer via precompile or pointer" / "fee or refund abuse" impact classes.

### Likelihood Explanation
Likelihood is moderate: it requires a downstream contract to naively apply the ERC20 `decimals()` convention to the native pointer's raw balances, which is the default assumption for essentially all ERC20 tooling and DeFi integration code, and pointer creation for any metadata-bearing native/tokenfactory denom is permissionless and directly reachable by any user via `IPointer.addNativePointer`.

### Recommendation
Make `NativeSeiTokensERC20.decimals()` consistent with the actual unscaled base-denom representation used by `balanceOf`/`transfer` (i.e., return `0`, matching the bank precompile's native-token convention), or alternatively scale `balanceOf`/`totalSupply`/`_update` by `10^decimals` so the advertised decimals genuinely reflect the numeric precision of the values returned. The two ERC20 views of the same native denom (bank precompile pointer vs. `AddNative` pointer contract) must not disagree on `decimals()` semantics.

### Proof of Concept
1. Create/observe a native bank denom with a display `DenomUnit` (e.g. standard `usei`/`sei` metadata, exponent 6).
2. Call `IPointer.addNativePointer("usei")` to deploy a `NativeSeiTokensERC20` pointer; the deployed pointer's `decimals()` returns `6`. [5](#0-4) 
3. Query `balanceOf(holder)` on the pointer — it returns the raw bank balance in `usei` (e.g. `1_000_000` for 1 `sei`), not scaled by `10^6`. [6](#0-5) 
4. Any contract computing `balanceOf(holder) / 10**decimals()` (standard ERC20 usage, `1_000_000 / 10^6 = 1`) will believe the holder has `1` unit of value when they truly hold `1_000_000` raw base units (i.e., 1 whole `sei`) — the interpretation is only "correct" by coincidence when the raw amount is at least `10^decimals` in size, and is wrong/misleading for any other magnitude, and is outright inconsistent with the bank precompile's own native-pointer `decimals()==0` semantics for the same denom.

	ctx sdk.Context, evm *vm.EVM, token string, metadata utils.ERCMetadata,

	return k.UpsertERCPointer(

func (p PrecompileExecutor) decimals(ctx sdk.Context, method *abi.Method, _ []interface{}, value *big.Int) ([]byte, uint64, error) {

		return nil, 0, err

	// all native tokens are integer-based, returns decimals for microdenom (usei)
