### Title
Unrestricted recursion in `VCProofs.from_program` when parsing untrusted Verified Credential proof data - (File: `chia/wallet/vc_wallet/vc_store.py`)

### Summary
`VCProofs.from_program` in `chia/wallet/vc_wallet/vc_store.py` recursively walks an arbitrary CLVM `Program` tree supplied as a Verified Credential (VC) proof, calling itself once per internal node with no depth bound. Because the shape of this tree is fully controlled by whoever reveals the VC proof (a spend-bundle submitter / counterparty in a VC/CR-CAT flow), a maliciously skewed (deeply nested, unbalanced) proof tree can drive Python recursion far beyond the interpreter's default limit, producing an unhandled `RecursionError`. This mirrors the HtmlUnit advisory's "unrestricted recursion on untrusted content" bug class (CVE-2023-2798), where attacker-controlled tree depth crashes the parser instead of failing gracefully.

### Finding Description
`VCProofs.from_program` is defined as: [1](#0-0) 

It recurses into `first` and `rest` whenever neither side is an atom, with no check on tree depth. The corresponding constructor path, `VCProofs.as_program`, only ever builds a balanced binary tree via `list_to_binary_tree`: [2](#0-1) 

`list_to_binary_tree` itself is also recursive and unbounded: [3](#0-2) 

However, `from_program` does not require its input to have been produced by `as_program`/`list_to_binary_tree` — it accepts *any* `Program` value. Because VC proofs are revealed as part of a coin's puzzle solution in the VC/CR-CAT spend flow, an attacker who constructs the coin spend (or a VC counterparty in an offer/credential-verification exchange) fully controls the shape of the proof program that gets parsed. A crafted, maximally right- or left-leaning chain of pairs (instead of a balanced binary tree) forces `from_program` to recurse to a depth proportional to the number of pairs in the reveal, rather than `O(log n)`.

This is directly analogous to the CWE-400/CWE-787 pattern in the HtmlUnit advisory: recursive tree-walking logic that trusts the *shape* of externally supplied content to be bounded, when in fact it is attacker-controlled.

By contrast, the codebase elsewhere explicitly hardens the equivalent operation — CLVM tree hashing — specifically to avoid this exact class of bug, noting in `tree_hash.py`: "This implementation goes to great pains to be non-recursive so we don't have to worry about blowing out the python stack" [4](#0-3) , and the Data Layer's merkle-tree file loader was likewise rewritten to be iterative with an explicit `RecursionDepthExceededError` guard for deep untrusted graphs [5](#0-4) . `VCProofs.from_program` has no such protection.

### Impact Explanation
An unhandled `RecursionError` raised while a wallet or Data Layer/VC-processing component is parsing an attacker-supplied VC proof can abort in-flight processing of that spend/offer. If this occurs inside a code path shared by wallet sync, offer verification, or spend-bundle validation logic (rather than being caught and converted into a clean rejection), it can manifest as a crash or hang of that processing loop — a spend-triggered transaction-processing halt / denial of service for the node or wallet handling the malicious VC proof. This is a resource/availability impact only (no coin-value or authorization impact), consistent with the "High" severity but purely availability-focused nature of the referenced CVE-2023-2798.

### Likelihood Explanation
Likelihood is moderate: constructing a skewed CLVM proof program is trivial for any party crafting a VC/CR-CAT spend or offer, and the recursive parser makes no attempt to validate tree balance or depth before recursing. The main uncertainty (not fully confirmed via static reading of the whole call graph) is exactly which top-level RPC/sync entry points feed externally-supplied `Program` data into `VCProofs.from_program` versus only ever feeding it self-generated balanced trees; this affects whether the un-trusted path is reachable without additional wallet-side validation.

### Recommendation
- Convert `VCProofs.from_program` (and `list_to_binary_tree` / `VCProofs.prove_keys`, which has the same recursive pattern) to an explicit-stack, iterative traversal, following the pattern already used in `chia/types/blockchain_format/tree_hash.py`.
- Alternatively, impose and enforce an explicit maximum depth check before recursing, rejecting malformed/oversized VC proof programs with a clean `ValueError` instead of allowing Python's recursion limit to be hit.
- Audit all other recursive `Program`/CLVM-tree walkers that consume externally supplied data (e.g., `MofNMerkleTree._m_of_n_proof`, `PuzzleWithRestrictions.from_memo`'s recursive `MofN` reconstruction in `chia/wallet/puzzles/custody/custody_architecture.py`) for the same unbounded-recursion pattern, since these also parse attacker-influenced memo/proof structures.

### Proof of Concept
Conceptual reproduction (not executed):
1. Construct a `Program` that is a long, unbalanced chain of pairs simulating a VC proof, e.g. in pseudocode: `p = Program.to(("k0","v0")); for i in range(20000): p = Program.to((p, ("k%d"%i, "v%d"%i)))` such that neither side of the outer pair is ever a plain atom until deep in the chain.
2. Call `VCProofs.from_program(p)`.
3. Because `from_program` recurses once per pair without any depth check, this raises a Python `RecursionError` once recursion exceeds the interpreter's stack limit, well before reaching the base case — demonstrating the unrestricted-recursion condition analogous to CVE-2023-2798. [1](#0-0)

```python
def list_to_binary_tree(objects: list[Any]) -> Any:
    size = len(objects)
    if size == 0:
        raise ValueError("Cannot build a tree out of 0 objects")
    if size == 1:
        return objects[0]
    midpoint = (size + 1) >> 1
    first_half = objects[:midpoint]
    last_half = objects[midpoint:]
    return (list_to_binary_tree(first_half), list_to_binary_tree(last_half))
```
