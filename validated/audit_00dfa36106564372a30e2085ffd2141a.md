### Title
Blame proof for ECDH key is emitted before the message's proof-of-possession is verified, leaking the shared decryption key (and thus the sender's secret share) to third parties - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts every incoming `EncryptedMessage` and immediately produces an `EncryptionKeyProof` containing the ECDH shared key, while the Schnorr proof-of-possession (PoP) on that message is only queued into a `BatchVerifier`. If the decrypted bytes fail `from_repr`, the function returns early with `PedPoPError::InvalidShare { blame: Some(proof) }` *before* `batch.verify_with_vartime_blame()` ever runs — so a blame proof is released for a message whose PoP was never verified. This re-enables exactly the attack the PoP was designed to prevent: an attacker Eve copies Alice's per-message key `X` into a malformed message to Bob; Bob emits a blame proof revealing `b·X`; anyone holding that proof plus Alice's real ciphertext can decrypt Alice's secret share to Bob.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` queues the PoP into the batch verifier (lines 479-485) and then unconditionally computes `ecdh(&self.enc_key, msg.key)` and returns an `EncryptionKeyProof { key, dleq }` (lines 487-500). In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` calls `decrypt` and, on a `from_repr` failure, returns `Err(InvalidShare { blame: Some(blame) })` at lines 479-482 — inside the loop, before `batch.verify_with_vartime_blame()` at line 493. The PoP failure (which would map to `BatchId::Decryption(l)` and yield `blame: None`) is never reached on this path.

The in-code comment at `encryption.rs:84-90` describes precisely this attack — Eve claiming Alice's key `X` so that Bob's blame reveals `bX`, leaking Alice's message to Bob — and states the PoP exists to stop it. The ordering bug defeats that mitigation on the malformed-scalar path: Bob's node emits a publicly-transmissible `EncryptionKeyProof` whose `key` field is the raw ECDH shared point, usable with `cipher()` to decrypt Alice's legitimate ciphertext.

The downstream blame verifier (`Decryption::decrypt_with_proof`, lines 366-397) does check the PoP first, so validators will correctly blame Eve — but the ECDH key bytes have already been produced and transmitted as the accuser's blame object (see `processor/src/key_gen.rs:504-556`, where `VerifyBlame` consumes the submitted `blame`).

### Impact Explanation
Disclosure of a PedPoP/Feldman secret share `f_alice(bob)` to any party that observes the published blame proof and Alice's ciphertext. A revealed share is protocol secret data; depending on deployment (e.g., repeated/compound DKG usage, or observers collecting multiple leaked shares of a polynomial), it degrades the confidentiality of the generated threshold key and can contribute toward key-share/key recovery. This is a network-reachable information disclosure caused by a verifier ordering flaw, matching the report's bug class.

### Likelihood Explanation
Eve must be a DKG participant able to send an authenticated share message to Bob — an unprivileged protocol peer with public inputs (the message she causes to be processed). She copies Alice's `key` field (public in Alice's authenticated broadcast/share message) into her own ciphertext; her PoP is invalid but is only batch-checked after the early error return. Trigger requires only that her ciphertext decrypts to non-canonical scalar bytes, which garbage ciphertext does with overwhelming probability.

### Recommendation
Run `batch.verify_with_vartime_blame()` (or at least the PoP for the failing message) before returning an `EncryptionKeyProof` in the error path of `calculate_share`; alternatively, have `Encryption::decrypt` verify the PoP inline and return `blame: None` when it fails, so no `EncryptionKeyProof` is ever emitted for a message with an unverified or invalid proof-of-possession.

### Proof of Concept
1. Participants Alice (i=1), Bob (i=2), Eve (i=3) run PedPoP. Alice's `generate_secret_shares` emits `EncryptedMessage { key: X, pop: σ_A, msg: c_A }` to Bob.
2. Eve crafts `EncryptedMessage { key: X, pop: σ_E, msg: garbage }` to Bob, where `σ_E` is any Schnorr signature Eve makes over a key she controls — it cannot be a valid PoP for `X`, but that is irrelevant.
3. Bob calls `calculate_share`. `decrypt` queues Eve's PoP, computes `key = b·X`, decrypts garbage; `C::F::from_repr` fails → `PedPoPError::InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key: b·X, dleq }) }` returned before the batch (and thus the PoP) is verified.
4. Bob's processor submits the blame to the coordinator (`VerifyBlame`). Any observer combines `b·X` with `cipher(context, b·X)` to decrypt `c_A`, recovering Alice's secret share to Bob in the clear — the exact side-effect `encryption.rs:84-90` says the PoP exists to prevent.
