### Title
`ThresholdKeys::read` accepts semantically inconsistent key material — a deserialized share can encode an arbitrary `group_key` (accepting funds) while holding no valid secret share — (File: crypto/dkg/src/lib.rs)

### Summary

Analogous to the YAML-deserialization bug class (untrusted bytes being instantiated into a security-relevant object without validating the *semantic* invariants of that type), `ThresholdKeys::read` reconstructs a `ThresholdKeys` purely from attacker-influenced bytes and never checks that the serialized `secret_share` is consistent with the serialized `verification_shares`. `ThresholdKeys::new` validates only participant indexes, interpolation applicability (`Constant` requires `t == n`), and then *derives* `group_key` from the supplied verification shares — so the deserializer freely "instantiates" an arbitrary group key backed by an arbitrary, unrelated secret share. The code itself acknowledges this gap: `complete()` in FROST ends with the comment that the only known way to reach `InternalError` "is to deserialize a semantically invalid FrostKeys" [1](#0-0) .

### Finding Description

`ThresholdKeys::read` reads `t`, `n`, `i`, an `Interpolation` method, one `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new` [2](#0-1) . `ThresholdKeys::new` computes `group_key` as the interpolation of `verification_shares[1..=t]` and stores `secret_share` verbatim — it never asserts `C::generator() * secret_share == verification_shares[i]` [3](#0-2) .

Additionally, the deserialization uses `<C as Ciphersuite>::read_G`, which rejects non-canonical/invalid points but explicitly does **not** reject the identity point — only `Curve::read_G` adds that check [4](#0-3) . So a crafted blob can encode identity verification shares, letting the attacker shape `group_key` as the sum of chosen multiples/identity points.

When the deserialized keys are later used for FROST signing, `view()` interpolates the bogus `secret_share` [5](#0-4)  and `complete()` either produces a signature that fails verification or falls into the unreachable-by-design `InternalError` path [6](#0-5) .

### Impact Explanation

The concrete impact is **funds received that are not spendable**: the deserialized `group_key` (e.g., a TapTweak'd Bitcoin output key derived via `Scalar`/`offset` on this `ThresholdKeys`) is whatever the attacker encoded via `verification_shares`, independent of any real DKG. A node that loads this blob exposes a valid-looking threshold public key, receives deposits to it, and then can never produce a valid threshold signature — every signing session either yields an invalid aggregate or hits `FrostError::InternalError`. Alternatively the attacker encodes an *inconsistent* share for an otherwise-real group key, permanently DoS-ing the signer's participation and (via the blame path in `complete()`) causing the honest node to be flagged `InvalidShare`. This is a silent key-material corruption: nothing in `read` detects it, and the failure only manifests after funds are committed to the key.

### Likelihood Explanation

Reachability requires attacker-controlled bytes to reach `ThresholdKeys::read` — i.e., a node restoring/importing serialized threshold key material from a source an unprivileged party can influence (replicated/synced key blobs, backups, or any transport where the serialized `ThresholdKeys` is not integrity-protected). Within the rules' explicit threat model ("untrusted bytes fed to … `ThresholdKeys::read`"), this sink is in scope. The attacker needs no secret knowledge: they pick arbitrary canonical scalars and points. Severity is Medium: high integrity loss (unspendable funds / broken signer) but conditioned on the key-blob channel being attacker-influenceable, which depends on integrator behavior. However, unlike a "documented-MUST misuse," the library exposes `read`/`serialize` as a supported round-trip API and `new`'s docstring gives no warning that consistency is unverified — the invariant failure is latent in library code, not caller error.

### Recommendation

In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), enforce the share-consistency invariant: `C::generator() * secret_share == verification_shares[&params.i()]`, and reject identity verification shares (route reads through `Curve::read_G` semantics or an explicit `is_identity` check). This converts silent corruption into an immediate deserialization error.

### Proof of Concept

```rust
// Deserialize a ThresholdKeys whose secret share is unrelated to its
// verification shares; group_key becomes attacker-shaped.
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());          // t = 1
buf.extend(1u16.to_le_bytes());          // n = 1
buf.extend(Participant::new(1).unwrap().to_bytes()); // i = 1
buf.push(1u8);                           // Interpolation::Lagrange
// attacker-chosen secret share (e.g., 0x01...), canonical
buf.extend(C::F::ONE.to_repr().as_ref());
// attacker-chosen verification share (e.g., identity or any point):
buf.extend(C::G::identity().to_bytes().as_ref()); // accepted: Ciphersuite::read_G allows identity

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap(); // succeeds
// keys.group_key() == identity-derived key; keys.original_secret_share() == 1
// Any address derived from keys receives funds; view()/sign() then produces
// shares inconsistent with verification_shares -> InvalidShare/InternalError.
```

        if params.t() != params.n() {

      scalar: C::F::ONE,

  /// Read a point from a reader, rejecting identity.
  #[allow(non_snake_case)]
  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let res = <Self as Ciphersuite>::read_G(reader)?;

      Err(io::Error::other("identity point"))?;
