### Title
Identity group key / point-at-infinity deserialized from untrusted bytes panics the Bitcoin FROST signing path - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The BIP-340 `Hram` and the `x()`/`x_only()` helpers in `bitcoin-serai` unconditionally panic when handed the point at infinity. `Secp256k1::read_G` (via the k256 `ProjectivePoint` decoding used by the `kp256` ciphersuite) accepts the identity point, and no in-scope deserialization (`GeneratorCommitments::read`, `NonceCommitments::read`, `ThresholdKeys::read`, `SchnorrSignature::read`) rejects identity points. Bytes an attacker supplies to these `read_*` APIs therefore flow, unfiltered, into functions documented as "panics on invalid input".

### Finding Description
`x()` extracts the x-coordinate of a point with `.expect("point at infinity")`, so any identity `ProjectivePoint` causes an unconditional panic:

```rust
// networks/bitcoin/src/crypto.rs:13-16
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

`Hram::hram` calls `x(R)` and `x(A)` directly:

```rust
// networks/bitcoin/src/crypto.rs:59-67
fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
  ...
  data.input(&x(R));
  data.input(&x(A));
```

`A` is `params.group_key()`, passed to `H::hram` inside `Schnorr::sign_share` (`crypto/frost/src/algorithm.rs:208`), which is invoked from `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:398`). The group key is reconstructed from attacker-controlled verification shares inside `ThresholdKeys::read` (threshold interpolation over the first `t` verification-share points), and nothing in the read path checks for a non-identity result. Similarly, `GeneratorCommitments::read` (`crypto/frost/src/nonce.rs:34-36`) and `NonceCommitments::read` (`crypto/frost/src/nonce.rs:74-80`) deserialize nonce commitments via `C::read_G` with no identity rejection, feeding `BindingFactor::nonces` (`nonce.rs:194-211`), whose sums become `R`.

The same panic exists in `x_only` (`crypto.rs:21-23`), used when deriving/verifying Taproot keys, and the `Schnorr` algorithm's own doc comment acknowledges: "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`) and "This may panic if called with nonces/a group key which are the point at infinity" (`crypto.rs:78-80`) — yet the deserialization layer provides no such guarantee.

### Impact Explanation
Analogous to CVE-2020-13577 (crafted input → denial of service), a single maliciously crafted serialized key set or preprocess causes an unconditional panic (`expect`/`assert`-style abort) in the signing or verification path. Because Rust panics in this context abort the signing task/process, an attacker who can get the victim to deserialize a `ThresholdKeys` blob with an identity (or identity-interpolating) group key — or route identity nonce commitments through `read_preprocess` in a protocol arrangement where the aggregate nonce resolves to identity — reliably crashes the signer, halting threshold signing and fund movement. This is an availability-only impact on security-critical signing infrastructure.

### Likelihood Explanation
Reaching the panic requires the attacker to control bytes fed to `ThresholdKeys::read`/`read_preprocess`, which in Serai's deployment means either a malicious key-set distribution or a malicious signing participant. Forging an *aggregate* nonce sum of exactly identity is computationally hard (the binding factor `rho` binds the commitments — `crypto/frost/src/sign.rs:361-379`), so the preprocess route is largely self-defending. However, the group-key route is trivially deterministic: verification shares of all-identity interpolate to an identity group key, and no check in the deserialization or `ThresholdKeys::new`/`view` path rejects it before `Hram::hram`/`x()` panics. The code itself documents the panic as reachable "with malicious participants present," confirming the authors consider the input adversarially reachable.

### Recommendation
Reject the point at infinity at the deserialization boundary: make `Secp256k1::read_G` (or a wrapper used by `GeneratorCommitments::read`, `ThresholdKeys::read`, `SchnorrSignature::read`, and `Commitments::read`) return `io::Error` on identity. Additionally, have `ThresholdKeys::read`/`ThresholdView::new` verify the interpolated `group_key` and all verification shares are non-identity, and make `Hram::hram`/`x`/`x_only` return `Option`/`Result` instead of panicking, propagating a `FrostError` rather than aborting the process.

### Proof of Concept
1. Construct a serialized `ThresholdKeys<Secp256k1>` blob (per the layout exercised in `crypto/frost/src/tests/vectors.rs:118-131`): valid `ThresholdParams`, any secret share, and `n` verification shares all set to the 33-byte identity encoding (`0x00`).
2. Feed it to `ThresholdKeys::<Secp256k1>::read`. `Secp256k1::read_G` accepts each identity point and interpolation yields `group_key = identity`.
3. Build `AlgorithmMachine::new(bitcoin::crypto::Schnorr::new(), keys)`, run `preprocess`, and call `sign` with a valid set of preprocesses.
4. `sign` reaches `Schnorr::sign_share` (`crypto/frost/src/algorithm.rs:208`) → `Hram::hram(&nonce_sums[0][0], &params.group_key(), msg)` → `x(A)` → `expect("point at infinity")` panics, crashing the signing task.

The same panic is reachable via `x_only(group_key)` during Taproot key handling (`networks/bitcoin/src/crypto.rs:21-23`) whenever the identity group key is converted for output/script construction.

Note: I could not fully confirm whether `Secp256k1::read_G` / `ThresholdKeys::read` already reject identity — the ciphersuite `read_G` default implementation was not fully retrievable in this session. If `read_G` already errors on identity for all in-scope curves, this finding reduces to a defense-in-depth gap; the panic sites and the absence of documented identity rejection in the shown read paths are as cited.
