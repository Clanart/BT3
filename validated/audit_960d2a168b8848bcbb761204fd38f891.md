### Title
Deterministic CachedPreprocess reuse across sign attempts enables FROST secret-share recovery (ROS-style nonce reuse) - (File: crypto/frost/src/sign.rs)

### Summary
CVE-2018-11785 is a missing authorization check that lets an authenticated-but-unauthorized party inject attacker-controlled data into an already-running operation, corrupting its results. The Serai analog lives in `crypto/frost`: `AlgorithmSignMachine::from_cache` / `seeded_preprocess` derive the signing nonces deterministically from a reusable 32-byte `CachedPreprocess` seed, with no binding to the message or the selected signer set. Any party that can feed different `preprocesses`/`msg` inputs to repeated `sign` invocations over the same cached seed obtains multiple signature shares `s = d + ρ·e + c·λ·x` reusing the identical nonces `(d, e)` — enough independent equations to recover the victim's secret share `x`.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmMachine::seeded_preprocess` instantiates `ChaCha20Rng::from_seed(*seed.0)` and derives both the nonce scalars (`Commitments::new`) and the algorithm addendum purely from the cached seed [1](#0-0) . `SignMachine::from_cache` simply rebuilds a machine from the same `CachedPreprocess`, and the seed is stored back unchanged via `cache()` [2](#0-1) . Nothing consumes, mutates, or ratchets the seed, and the nonce derivation does not incorporate `msg` or `included`.

`sign` then lets the caller — and transitively whoever supplies the `HashMap<Participant, Preprocess>` — fully determine the signer set: `included` is constructed directly from `preprocesses.keys()` [3](#0-2) . The binding factors `ρ` are computed from a transcript over the per-participant commitments and the message [4](#0-3) , so each injected variation of the preprocess set or message yields a fresh `ρ` and a fresh challenge `c`, while the underlying nonces `d`, `e` stay identical. `sign_share` emits `s_i = d + ρ_i·e + c_i·λ·x_i` [5](#0-4) .

The code documents the hazard — "A preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share" [6](#0-5)  — yet the machine API itself places no constraint preventing an unauthorized party from causing reuse: each call consumes `self`, but a machine rebuilt `from_cache` with the same seed is byte-for-byte identical and accepts a different, attacker-chosen preprocess map.

### Impact Explanation
With three distinct `(ρ_i, c_i)` observed for the same nonce pair, the linear system `s_i = d + ρ_i·e + c_i·λ_i·x` (unknowns `d`, `e`, `x`) is solvable, yielding the victim's FROST secret share `x`. Recovering `t` such shares (or combining with the attacker's own shares) compromises the threshold key — total key compromise, worse than the CVE's "wrong results" integrity impact. Per the crate's own documentation, this is the documented consequence of preprocess reuse [6](#0-5) .

### Likelihood Explanation
The attack requires only the ability to supply public inputs — a preprocess map and message — to `sign` on a machine reconstructed from the same `CachedPreprocess`, which is exactly the untrusted-input surface of `read_preprocess`/`sign`. Any integration that caches preprocesses per context and retries `sign` with coordinator-supplied preprocess sets (the standard two-round deployment shape) lets an unauthorized injector vary the signer set or message to collect the required equations. No malicious validator status, key leakage, or broken transport is needed — just repeated `sign` calls over one seed.

### Recommendation
Bind the nonce derivation to the signing session: derive nonces as `H(seed || group_key || msg || sorted(included) || commitments)` rather than from the bare seed, or make `sign`/`from_cache` consume and rotate the cached seed so a reuse yields independent nonces. At minimum, have `from_cache` return a machine whose `cache()` produces a fresh, ratcheted seed so any retry is cryptographically independent.

### Proof of Concept
1. Victim stores `CachedPreprocess(seed)` and builds `AlgorithmSignMachine::from_cache(algorithm, keys, seed)` → nonces `(d, e)`, commitments `C`.
2. Attacker causes `sign(preprocesses_1, msg_1)` → share `s_1 = d + ρ_1·e + c_1·λ_1·x` (attacker knows `ρ_1`, `c_1`, `λ_1` — all public).
3. Attacker causes a retry `from_cache(same seed)` then `sign(preprocesses_2, msg_2)` with a different injected participant index or message → `s_2` with the same `d`, `e` but new `ρ_2`, `c_2`.
4. Repeat once more → `s_3`. Solve the 3×3 linear system over `C::F` for `(d, e, x)`. Verify with `C::generator() * x == victim_verification_share` (obtainable via `ThresholdView::verification_share` / `original_verification_share` [7](#0-6) ).

This is the ROS/nonce-reuse attack enabled by deterministic seed reuse in `seeded_preprocess` [8](#0-7)  combined with attacker-controlled `included` [9](#0-8) .

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
