### Title
Change outputs and scanned inputs below the economically-spendable threshold are treated as usable funds, permanently stranding value - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` emits a change output whenever the leftover amount is `>= DUST` where `DUST = 546` (the bare Bitcoin relay dust limit), and `Scanner::scan_transaction` registers any output paying to a watched script regardless of value. Both treat outputs as spendable funds even when their value is below the fee required to spend them, so value is reported as received/retained while being economically unspendable — the same class as the external report's "balance remains in the contract but can never be claimed".

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the dust constant is hard-coded to the minimum relay value:

```rust
pub const DUST: u64 = 546;   // send.rs:32
```

Change is added purely on this check:

```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
    ...
  }
}   // send.rs:228-234
```

A Taproot input costs ~57 vbytes to spend (the processor's own analysis in `processor/src/networks/bitcoin.rs:619-630` computes 230 weight units ≈ 57 vbytes and concludes outputs need ≥ ~10,000 sats to be worth spending). At even a modest `fee_per_vbyte`, any change output in the range `[546, 57 * fee_per_vbyte)` costs more in fee to spend than its face value. The wallet nevertheless creates it, `Scanner` will later return it as a `ReceivedOutput` credited at `value()` sats (`wallet/mod.rs:199-214`), and every future attempt to include it as an input is a net loss.

Symmetrically, `Scanner::scan_transaction` has no value floor: an unprivileged third party who sends a dust output (e.g. 546 sats, or any amount below the spendable threshold) to a watched Serai address produces a `ReceivedOutput` indistinguishable from spendable funds — value that is "received" on the books but cannot be redeemed without paying more in fees than it is worth.

The needed-fee check (`send.rs:211`) and `NotEnoughFunds` check (`send.rs:215`) only guard the aggregate, mirroring the original bug's shape: each individual payout was valid, but the accounting allowed a residual that can never be productively claimed.

### Impact Explanation
Value in `[546, ~57*fee_per_vbyte)` sats is permanently stranded: the change output (or attacker-sent dust input) is recorded as received yet spending it is a guaranteed loss. An unprivileged party can unilaterally create this state by dusting a known Serai deposit script — the scanner attributes it as balance, and the only ways to deal with it are overpaying fees or leaving the funds stranded, both equivalent to "tokens stuck in the contract" from the original report. Note the processor layer compensates with its own `DUST = 10_000`, but that is out-of-scope policy; the in-scope wallet/scanner code itself performs no spendability check and actively produces sub-spendable change outputs.

### Likelihood Explanation
Reachable with public inputs: (a) any transaction plan whose leftover lands in `[546, spendable_threshold)` deterministically creates stranded change; (b) any third party can send dust to a publicly known deposit script_pubkey at negligible cost. Both require no privileged access, no key material, and no validator collusion — just an on-chain transaction anyone can broadcast.

### Recommendation
- Raise the change threshold in `SignableTransaction::new` from the relay `DUST` (546) to a spendability floor derived from the input cost: `value >= DUST + (input_vbytes * fee_per_vbyte)` (or a conservative fixed bound such as the processor's 10,000 sats). Leftover below the floor should be folded into the fee, matching the existing "leftover becomes fee when no change address" behavior.
- Add a minimum-value filter in `Scanner::scan_transaction` (or on `ReceivedOutput` consumption in `SignableTransaction::new`) so sub-threshold outputs are not reported/spent as inputs.
