### Title
OP_RETURN `data` output excluded from weight/vbyte estimate causes systematic underpayment of the intended fee rate — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` **before** computing the transaction's weight, yet `calculate_weight_vbytes` is invoked with `payments` only — the `data` output is never included in either the no-change or the with-change size estimate. The resulting `needed_fee` (and the change amount derived from it) is computed for a smaller transaction than the one actually built and signed. The actual fee paid (`sum(inputs) - sum(outputs)`) therefore corresponds to a lower sat/vbyte rate than the caller requested, and can silently fall below the minimum relay fee even though the `TooLowFee` guard passed — producing a signed transaction that the network will not relay. This is the Serai-side analog of the reference bug: fee accounting is performed under a wrong assumption about which branch/shape of transaction the funds cover, and the discrepancy is never corrected or refunded.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at lines 193–202:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}
```

But the fee estimate at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — using `payments` (the pre-data output list), not `tx_outs`. `calculate_weight_vbytes` (lines 62–99) reconstructs a transaction whose `output` vector is built solely from the `payments` slice plus an optional change output; it has no parameter for the data output at all. The same omission occurs in the change branch at lines 225–226. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is computed for a transaction missing an up-to-80-byte OP_RETURN output (~90+ additional bytes, ~90 vbytes since it is entirely non-witness data).
- When `change` is `Some`, the change amount `input_sat - payment_sat - fee_with_change` is correspondingly **too large** — funds that should have covered the fee for the data output are instead diverted into the change output, and the real effective fee rate is `fee_per_vbyte * vbytes_underestimated / vbytes_actual`.
- The `TooLowFee` check (lines 206–213) compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the same underestimated `vbytes`, so a transaction can pass the guard while its true fee rate is below the minimum relay fee.

No downstream code rechecks the achieved fee rate: `fee()` (lines 138–141) simply reports `inputs - outputs`, and `TransactionSignMachine::sign` (lines 355–398) signs whatever fee the constructed outputs imply.

### Impact Explanation
An unprivileged caller who supplies `data` (a public parameter of `SignableTransaction::new`) obtains a threshold-signed transaction whose effective fee rate is strictly lower than the `fee_per_vbyte` they requested and paid for via reduced change. In the worst case — a small transaction near the minimum relay boundary, where ~90 underestimated vbytes are proportionally largest — the signed transaction's real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`. Such a transaction is rejected by Bitcoin Core's mempool acceptance (`minRelayTxFee` check), so the produced, fully-signed transaction cannot be broadcast: the inputs are effectively frozen until an entirely new signing round is run, and the FROST signing session produces an artifact that does not accomplish the intended payment. This is a concrete fee/change-accounting error in in-scope production code, not a rounding issue — the missing output is ~90 vbytes regardless of transaction size.

### Likelihood Explanation
Any caller of the public `new` API who passes `Some(data)` hits this unconditionally — it is deterministic, not probabilistic. Whether it crosses the min-relay threshold depends on transaction size and requested fee rate, but the effective-rate underpayment occurs on every call with `data` set.

### Recommendation
Pass the final output list (including the OP_RETURN output) to `calculate_weight_vbytes` — e.g., restructure it to take `&[TxOut]` or add a `data_len`/`has_op_return` parameter — so both the no-change and with-change estimates reflect the real transaction. As defense-in-depth, after constructing `tx`, assert `weight`/`vbytes` were computed over the actual `tx.output` set, and compare `fee()` against `needed_fee` scaled to the true vbytes before returning `Ok`.

### Proof of Concept
Conceptual trace (values approximate):

1. Call `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` with `fee_per_vbyte = 7` (i.e., ~7 sat/vB, min relay ≈ 1 sat/vB per 1000 sat/kvB).
2. Suppose the payment-only estimate yields `vbytes = 160` → `needed_fee = 1120` sat.
3. The real transaction includes the OP_RETURN output (+~91 vbytes), so actual size ≈ 251 vB. The change output absorbs `input_sat - payment_sat - 1120`, making the real fee rate ≈ `1120 / 251 ≈ 4.5` sat/vB instead of 7.
4. With `fee_per_vbyte` chosen near the minimum (e.g., 2 sat/vB on a ~120 vB base → paid fee 240 sat vs. required ~211→ actually `(240)/(211) ≈ 1.14` but for smaller margins, e.g. base 110 vB, requested 1.0 sat/vB → needed_fee 110 vs actual requirement ~201 sat): the `TooLowFee` check passes (`110 ≥ 1000*110/1000`), yet the broadcast fee of 110 sat is below the ~201 sat needed for relay → the signed transaction is rejected by the network.
