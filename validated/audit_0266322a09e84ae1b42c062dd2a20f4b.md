Based on my research, the OpenQ report's bug class (a snapshot/accounting mechanism whose distribution math can be permanently distorted by an unprivileged actor manipulating the state that the snapshot depends on) has a concrete analog in this codebase's reward-pool `_provisionReward` logic, not in a "close competition" contract (this repo has none), but in the `totalStaked() == 0` branch shared by `BaseRewardPoolV2`, `BaseRewardPool`, `mWOMSVBaseRewarder`, and `vlMGPBaseRewarder`.

### Title
Reward accounting can be permanently skewed by an unprivileged depositor timing a deposit around a zero-`totalStaked()` reward provisioning event - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`_provisionReward`, used by `queueNewRewards` and `donateRewards` across all of Magpie's reward-pool implementations, decides whether incoming reward tokens are immediately distributed pro-rata (`rewardPerTokenStored`) or held in `queuedRewards` based on a single check: whether `totalStaked() == 0` at the moment the reward is provisioned. [1](#0-0) 

### Finding Description
When `totalStaked()` is zero (e.g., all stakers have withdrawn from a pool), any reward pushed in via `queueNewRewards` (called by managers such as `WombatStaking` or `vlMGP`/`mWomSV` on harvest/forfeit events) or via the permissionless `donateRewards` is deferred into `rewardInfo.queuedRewards` rather than being distributed: [2](#0-1) 

The next time `_provisionReward` runs while `totalStaked() > 0`, the *entire* accumulated `queuedRewards` balance is folded into `rewardPerTokenStored`, calculated as `(_amountReward * 10**decimals) / totalStaked()` using whatever `totalStaked()` happens to be **at that exact call**, not the supply that existed while the rewards accrued: [2](#0-1) 

The same pattern is duplicated in `mWOMSVBaseRewarder._provisionReward`/`_queueNewRewardsWithoutTransfer` and `vlMGPBaseRewarder.queueNewRewards`/`_queueNewRewardsWithoutTransfer`: [3](#0-2) [4](#0-3) 

This lets an ordinary wallet exploit the accounting the same way the OpenQ bug exploited `closeCompetition`'s balance snapshot: by controlling the state (`totalStaked()`) that a later accounting/distribution event depends on. Concretely:
1. Wait until (or induce, by withdrawing) `totalStaked() == 0` for a pool (e.g., an mWOMSV/vlMGP/LP reward pool that periodically empties).
2. As soon as a manager pushes a reward while supply is zero, it is queued rather than distributed.
3. Deposit a minimal amount, becoming briefly the sole/near-sole staker (`totalStaked()` now tiny).
4. Trigger (or wait for) the next `queueNewRewards`/`donateRewards` call (a normal, expected periodic protocol operation, e.g. bribe harvesting via `WombatBribeManager.castVotes` calling `wombatStaking.vote` → `IBaseRewardPool(_rewarders[i]).queueNewRewards`) — [5](#0-4)  — which folds all the previously queued rewards into `rewardPerTokenStored` divided by the attacker's near-total supply.
5. Immediately claim the disproportionate reward and withdraw, before other legitimate depositors can re-enter the pool.

The result mirrors the report's root cause pattern: distribution math computed against a value (`totalStaked()`/balance) that an unprivileged actor can manipulate between accrual and settlement, permanently misallocating funds that were rightfully destined for other/future depositors.

### Impact Explanation
This causes theft of unclaimed yield: rewards intended to be shared among all future stakers of the pool are instead captured almost entirely by the attacker who times their deposit around the zero-supply window, permanently depriving other users of yield they would otherwise have earned. This satisfies the "theft or permanent freezing of unclaimed yield" bar.

### Likelihood Explanation
Reward pools naturally pass through zero-`totalStaked()` states (new pools before first deposit, or pools that temporarily empty as users unstake), and reward provisioning (`queueNewRewards`) is a routine, frequent operation driven by harvest/vote/forfeit flows rather than a rare admin action. Any unprivileged wallet can observe pool state on-chain and time a small deposit accordingly, requiring no privileged role, oracle, or governance action.

### Recommendation
Do not let a single `_provisionReward` call retroactively apply previously `queuedRewards` against the `totalStaked()` value observed only at the moment of release. Instead, track the timestamp/supply-weighted accrual of queued rewards (e.g., accrue against a snapshot of eligible depositors, or refuse to release queued rewards into `rewardPerTokenStored` until they can be prorated across the deposits that existed while they accrued), similar to how the OpenQ fix disabled the exploitable path (refunds) rather than allowing state that was valid at accrual time to be gamed at settlement time.

### Proof of Concept
1. Pool P has `totalStaked() == 0`.
2. Manager calls `queueNewRewards(1000, rewardToken)` on `BaseRewardPoolV2` → since `totalStaked() == 0`, `rewardInfo.queuedRewards += 1000` (no distribution yet). [6](#0-5) 
3. Attacker deposits 1 wei of the staking token into pool P, making `totalStaked() == 1`.
4. Manager (in normal operation, e.g. bribe harvest cycle) calls `queueNewRewards` again with any amount, e.g. `1`. `_provisionReward` executes the `else` branch: `_amountReward += queuedRewards (1000)` and `rewardPerTokenStored += (1001 * 10**decimals) / 1` — the entire 1000 previously-queued reward is now owed entirely to the attacker's 1-wei stake. [7](#0-6) 
5. Attacker calls `getReward`/`getRewards` to withdraw the full 1000 reward tokens, then withdraws their 1-wei stake, leaving nothing for subsequent depositors who would have been the legitimate recipients of that reward.

**Uncertainty note:** I could not fully verify the exact `totalStaked()` implementation and the complete withdrawal/deposit flow (whether normal user withdrawals can genuinely drive `totalStaked()` to exactly zero, and whether `getReward` sends the disputed amount without further guard) because the tool budget was exhausted before I could read the full `BaseRewardPoolV2.sol` file. I recommend verifying these mechanics directly in the repository (`rewards/BaseRewardPoolV2.sol`, `rewards/MasterMagpie.sol` deposit/withdraw functions) before treating this as fully confirmed.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
