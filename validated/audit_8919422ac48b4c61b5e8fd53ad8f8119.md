### Title
`fetchRefspec()` accepts exit code 128 as success, silently masking failed fetches from attacker-controlled fork/PR remotes - (File: app/src/lib/git/fetch.ts)

### Summary
The Rolla finding is about a low-level operation (`target.call()`) that reports success even when the underlying action didn't actually happen, and the caller trusting that reported "success" without further verification. The Desktop analog is `fetchRefspec()` in `app/src/lib/git/fetch.ts`, which explicitly treats a `git fetch` exit code of `128` as an acceptable/successful result, causing the wrapping `Promise<void>` to resolve normally even though the fetch did not obtain the requested ref.

### Finding Description
`fetchRefspec()` is used to fetch a specific ref/refspec from an attacker-influenced remote — most notably when GitHub Desktop checks out a pull request from a fork [1](#0-0) . It is invoked from `GitStore.fetchRefspec()`, which loops over all remotes and calls it for each one [2](#0-1) .

The core implementation:
```
export async function fetchRefspec(
  repository: Repository,
  remote: IRemote,
  refspec: string
): Promise<void> {
  await git(['fetch', remote.name, refspec], repository.path, 'fetchRefspec', {
    successExitCodes: new Set([0, 128]),
    env: await envForRemoteOperation(remote.url),
  })
}
``` [3](#0-2) 

In `git()`, any exit code included in `successExitCodes` is treated as fully successful — it returns normally, without throwing a `GitError` and without any signal to the caller that nothing was actually fetched:
```
const acceptableExitCode = opts.successExitCodes
  ? opts.successExitCodes.has(exitCode)
  : false
...
if ((gitError !== null && acceptableError) || acceptableExitCode) {
  return gitResult
}
``` [4](#0-3) 

Exit code `128` from `git fetch` is Git's generic fatal-error code (e.g., "couldn't find remote ref", protocol/host errors, or a repository/ref that doesn't exist on the remote — directly analogous to the "the account being called does not exist" case from the report). Unlike `fastForwardBranches`, which comments that exit code `1` is an *expected partial failure it accounts for* [5](#0-4) , `fetchRefspec` gives no comment or justification for swallowing `128`, and the caller (`GitStore.fetchRefspec`, wrapped in `performFailableOperation`) receives no indication that the fetch silently produced nothing.

This matches the "call() returns true even though nothing happened" invariant break: the low-level operation (`git fetch`) can silently fail (nonexistent ref/host issue controlled by the fork owner or a malicious/compromised remote host) while the wrapping `Promise<void>` resolves as if the fetch succeeded.

### Impact Explanation
Downstream, `_fetchRefspec` calls `_refreshRepository` immediately after `gitStore.fetchRefspec(refspec)` returns, without checking whether the desired ref actually exists locally afterward [6](#0-5) . Similarly `_findPullRequestBranch` performs a full remote fetch (`_fetchRemote`) and then looks up the branch by name; if a stale/similarly named branch exists locally from a previous operation, later logic may proceed against unintended commit content because there was no positive confirmation that the intended ref was freshly retrieved [7](#0-6) . An attacker who controls a fork/PR head repo or an intermediary proxy/remote response (e.g., serving a fatal error for the specific ref while keeping the connection nominally alive) can cause Desktop to silently believe a fetch succeeded, letting the UI proceed with checkout logic based on stale local state without surfacing an error to the user — a "silent corruption of what the user sees/acts upon" per the campaign's impact categories.

### Likelihood Explanation
This code path is reachable without any special local access: it triggers whenever a user views/checks out a pull request from a fork, which is a normal, unprivileged, attacker-influenced action (the fork owner controls the ref content/availability, and a malicious/compromised git host or a MITM-capable proxy could induce a 128 exit deterministically for a targeted ref while still returning 128 for the overall `git fetch` process). No existing guard verifies post-fetch that the intended object/ref was actually retrieved before the caller proceeds.

### Recommendation
Do not include `128` in `successExitCodes` for `fetchRefspec` without explicit downstream verification. Instead:
- After the fetch call returns, verify that the target ref/commit actually exists in the local repository (e.g., via `git rev-parse` on the expected FETCH ref) before treating the operation as successful.
- If exit code `128` must be tolerated for legitimate cases (e.g., ref simply doesn't exist upstream), surface that distinction to the caller (return a boolean/result object) instead of silently resolving `Promise<void>`, so `_fetchRefspec`/`_findPullRequestBranch` can react appropriately and warn the user rather than silently continuing.

### Proof of Concept
1. Attacker creates or controls a fork repository referenced by a pull request (or controls a git server/proxy in the fetch path).
2. Victim opens that PR in GitHub Desktop, triggering `checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch` → `fetchRemote`/`fetchRefspec` against the attacker-controlled remote/refspec [8](#0-7) .
3. Attacker's git server responds such that `git fetch <remote> <refspec>` exits with code `128` (e.g., by advertising the ref then failing to deliver objects for it, or returning a fatal protocol error for that specific request) while the process itself terminates.
4. `git()` in `core.ts` sees `128` is in `successExitCodes` for `fetchRefspec`, treats it as success and returns normally [4](#0-3) .
5. `GitStore.fetchRefspec` / `_fetchRefspec` proceed to `_refreshRepository`/branch lookup with no indication of failure, potentially operating on stale or incomplete branch data without warning the user that the intended fetch never actually completed.

*Note:* I was unable to fully trace every downstream consumer of `_findPullRequestBranch`'s return value to confirm the exact worst-case consequence (e.g., whether a stale local branch could actually be checked out and committed to under the attacker's expectation); this would require deeper tracing of `_checkoutPullRequest` in a live session, which is recommended before treating this as a fully confirmed high-severity issue.

    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
