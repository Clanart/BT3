### Title
Threshold key shares are serialized in plaintext - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::write` emits the holder’s private `secret_share` directly into the serialized key material, without encryption or any confidentiality protection. `ThresholdKeys::serialize` exposes those bytes as a `Vec<u8>`, and `ThresholdKeys::read` interprets the same field as the private share. Consequently, any serialized `ThresholdKeys` blob is equivalent to plaintext key-share material.

### Finding Description
`ThresholdCore` stores the participant’s private key share in `secret_share`. During serialization, `ThresholdKeys::write` converts `self.core.secret_share` with `to_repr` and writes those bytes directly to the caller-provided writer. No encryption, authenticated encryption, wrapping, or other protection is applied.

The plaintext format is then accepted by `ThresholdKeys::read`, which parses the scalar back into `secret_share` and constructs usable `ThresholdKeys`. A party that obtains a serialized `ThresholdKeys` blob therefore obtains the corresponding threshold signing share.

### Impact Explanation
Disclosure of one serialized key blob causes key-share recovery. The recovered share is the secret used by FROST signing and can also be supplied to `recover_key` together with other threshold shares. If an attacker obtains enough serialized shares to satisfy the threshold, they can recover the underlying group secret and forge signatures for the threshold key. Even a single leaked share is a sensitive signing secret and compromises the participant-level confidentiality boundary.

### Likelihood Explanation
The vulnerability does not require malicious cryptography or a malformed protocol message. It occurs whenever `ThresholdKeys::serialize` or `ThresholdKeys::write` is used to persist key material to a file, database, backup, log, message queue, or other storage readable by a lower-privileged party. The serialized format is self-contained and directly parseable by `ThresholdKeys::read`.

### Recommendation
Do not serialize `secret_share` as unprotected bytes. Encrypt serialized `ThresholdKeys` using an authenticated-encryption scheme with a dedicated secret-storage key and explicit domain separation, or require callers to supply a secure key-wrapping interface. At minimum, document `serialize`/`write` as producing raw private key material and ensure production persistence layers encrypt the resulting bytes before storage.

### Proof of Concept
```rust
// Any ThresholdKeys<C> can be exported as raw bytes.
let serialized = threshold_keys.serialize();

// The emitted bytes are sufficient to reconstruct usable ThresholdKeys.
let recovered = ThresholdKeys::<C>::read(&mut serialized.as_slice()).unwrap();

// The recovered object contains the same private signing share.
assert_eq!(
  recovered.original_secret_share(),
  threshold_keys.original_secret_share(),
);
```

The sensitive behavior is the direct plaintext write of `secret_share` in `crypto/dkg/src/lib.rs:553-555` and its direct restoration as `secret_share` in `crypto/dkg/src/lib.rs:618`.
