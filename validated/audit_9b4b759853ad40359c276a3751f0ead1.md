This repo doesn't contain the `GaugeController` referenced in the report — it's a MasterMagpie/Wombat-style protocol. However, there is a genuine analog of the same bug class (premature/sequential division causing reward-calculation precision loss) in the VLMGP/mWomSV forfeit-percentage math, which feeds directly into unprivileged users' reward payouts via `vlMGPBaseRewarder`.

### Title
Sequential division in `getRewardablePercentWAD` systematically underpays users their non-forfeited rewards - (File: `VLMGP.sol` / `wombat/mWomSV.sol`)

### Summary
`VLMGP.getRewardablePercentWAD` and its duplicate in `mWomSV.getRewardablePercentWAD` compute a user's "rewardable" fraction of vlMGP/mWomSV using two sequential integer divisions instead of a single combined division. This is the same "premature division" bug class as the analog report: dividing twice truncates more than dividing once by the product of the denominators, systematically underestimating the rewardable percentage. That percentage is consumed by `vlMGPBaseRewarder._calExpireForfeit`, which is executed on every unprivileged user's `getReward`/`getRewards` claim, directly reducing the amount of reward tokens paid to the user and increasing the amount routed to `_queueNewRewardsWithoutTransfer` as "forfeited."

### Finding Description
In `getRewardablePercentWAD` (identical logic in both files):
```solidity
percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
    / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
``` [1](#0-0) [2](#0-1) 

This performs `x / a / b`, i.e. two sequential floor divisions, rather than `x / (a * b)`. For any non-negative integers, `floor(floor(x/a)/b) <= floor(x/(a*b))`, so the two-step calculation can never overestimate and frequently underestimates `percent` relative to the mathematically correct single-division form — exactly the truncation pattern described in the reference report (`gaugeShare * typeShare` computed via two pre-divided percentages vs. one combined division).

This `percent` value is then consumed unprivileged-reachable by any staker claiming rewards:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
    uint256 forfeitAmount = _amount - rewardableAmount;
``` [3](#0-2) 

which is invoked from `_sendReward`, itself called on `getReward`/`getRewards` during any user's normal, unprivileged claim path: [4](#0-3) 

Because `percent` is undercounted, `rewardableAmount` is undercounted and `forfeitAmount` is overcounted, meaning users in a cooldown/unlocking state receive less than they are actually entitled to on every claim, with the difference instead routed back into the pool as "forfeited" rewards for other stakers.

### Impact Explanation
This directly and systematically reduces the reward payout of any ordinary vlMGP/mWomSV holder who has unlocking slots in progress (a routine, common user state, not an edge case), each time they call `getReward`. Because vesting math combines two truncating divisions instead of one, the loss compounds across every unlocking slot and every claim. This constitutes a direct reduction/misappropriation of a normal, unprivileged user's claimable yield — analogous in nature and severity to the underpayment demonstrated in the reference report, though the magnitude here depends on the specific `amountInCoolDown`, `userTotalVlmgp`, and time deltas involved.

### Likelihood Explanation
High likelihood: this code path executes on every single reward claim (`getReward`/`getRewards`) by any user who has an active or completed unlock slot, which is a normal part of the vlMGP/mWomSV unlocking mechanics — no special conditions, admin actions, or attacker setup are required.

### Recommendation
Combine the two divisions into a single division by the product of the denominators to minimize truncation, mirroring the report's proposed fix:
```diff
- percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
-     / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
+ percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
+     / (userTotalVlmgp * (timeNow - userUnlocking[i].startTime));
```
Apply the same fix in both `VLMGP.sol` and `wombat/mWomSV.sol`.

### Proof of Concept
For integer division, `floor(floor(x/a)/b) <= floor(x/(a*b))` always holds and is frequently strictly less. Concretely, with:
- `amountInCoolDown * 1e18 * (endTime - startTime) = x`
- `userTotalVlmgp = a`
- `timeNow - startTime = b`

pick values where `x mod a != 0` (guaranteed to occur across the wide range of real-world locked amounts, since `userTotalVlmgp` is unbounded and user-specific): the two-step division in `VLMGP.sol:207-208` yields a strictly smaller `percent` than the mathematically correct `x / (a*b)`, which is then propagated into `_calExpireForfeit` in `rewards/vlMGPBaseRewarder.sol:387-388`, causing `rewardableAmount` to be systematically less than entitled and `forfeitAmount` correspondingly higher on every affected user claim — the same underpayment mechanism as the reference report, just manifesting in the vlMGP/mWomSV forfeit-percentage calculation instead of `GaugeController`.
