### Title
`solo` precompile's "must be called by an EOA directly" check relies on EVM call depth, which is bypassable by EIP-7702 delegated accounts - (File: `precompiles/solo/solo.go`)

### Summary
The `solo` precompile's `Execute` function protects `Claim`/`ClaimSpecific` with a check that the precompile call happens at EVM call depth 1, intended to guarantee the caller is an EOA calling the precompile directly rather than through composed contract logic [1](#0-0) . This is functionally the same "onlyEOA" bug class described in the external report: a check meant to guarantee "this is a raw EOA action, not composable contract logic" that account-abstraction features (EIP-3074 there, EIP-7702 here) can invalidate.

### Finding Description
`evm.GetDepth() > 1` returns an error unless the call to the precompile is the first CALL frame after the top-level transaction entry, which the code's comment explicitly equates with "claim must be called by an EOA directly" [1](#0-0) . This same pattern is duplicated verbatim across every legacy version of the precompile (v614, v620, v630, v640, v65, v66, v67) [2](#0-1) .

The chain fully supports EIP-7702 account delegation: `SetCodeTx`/`SetCodeAuthorization` let an EOA delegate its address to arbitrary contract bytecode, and the ante/giga pipeline explicitly recognizes and executes delegated code for the sender [3](#0-2) . When a transaction targets a delegated EOA address (`to: authority.EvmAddress`), the EVM begins executing the delegated contract's bytecode as the top-level call frame (depth 0), so any `CALL` it issues to a precompile is depth 1 — indistinguishable from a genuine, code-less EOA calling the precompile directly. The existing `giga/tests/eip7702_selfbalance_drain_test.go` test demonstrates this exact pattern working end-to-end (self-delegate → run arbitrary logic at the top level → undelegate) and confirms it is a first-class, already-exploited primitive on this chain, not a hypothetical future EIP-3074 concern [4](#0-3) .

Consequently, an attacker can delegate their EOA to a malicious contract, invoke arbitrary pre/post logic (flash loans, price manipulation, multi-step atomic composition, batched actions across other contracts/precompiles) in the same top-level call frame, and still satisfy `depth == 1` when calling into `solo`'s `Claim`/`ClaimSpecific`, defeating the intended "EOA-only, non-composable" guarantee — exactly analogous to the `tx.origin == msg.sender` bypass described in the original report, just achieved via EIP-7702 instead of EIP-3074.

### Impact Explanation
`Claim`/`ClaimSpecific` move the caller's entire bank balance (and CW20/CW721 assets) from the pre-EVM "sender" account to the EVM caller's associated Sei address [5](#0-4) . If the EOA-only restriction exists to prevent this asset-migration operation from being composed with other contract logic in the same atomic transaction (e.g., to block flash-loan-assisted or sandwich-style manipulation of balances/prices around the claim), that protection is nullified for any account using EIP-7702 delegation, since the depth check cannot distinguish "genuine EOA calling directly" from "EOA temporarily running attacker-controlled bytecode at depth 0." This falls under the "unauthorized transfer via precompile" and "fee/refund or fund-loss via bypassed access control" categories.

### Likelihood Explanation
EIP-7702 delegation is a fully supported, user-reachable primitive on this chain (any account holder can submit a `SetCodeTx` to delegate their own EOA), so no privileged access or validator collusion is required — a single attacker-controlled account with normal transaction access can set up the delegation and then call the precompile, exactly as shown by the existing drain test.

### Recommendation
Do not rely on EVM call depth (or `tx.origin`/`msg.sender` equality) as a proxy for "the caller has no code." Explicitly check whether the caller's account currently has code (or an active EIP-7702 delegation) using the EVM keeper's code-lookup (`GetCode`), consistent with how `app.go`'s "sender must be EOA unless delegated" check already inspects code/delegation status, and reject calls from delegated accounts if the "EOA directly" guarantee must be preserved.

### Proof of Concept
1. Attacker's EOA `authority` submits a `SetCodeTx` delegating itself to a malicious contract `M` (per `ethtypes.SetCodeAuthorization`, mirroring `giga/tests/eip7702_selfbalance_drain_test.go` lines 93-109).
2. A subsequent transaction targets `authority` directly; `M`'s bytecode executes as the top-level frame (depth 0) and performs arbitrary composed logic (e.g., manipulate price, take a flash loan) then issues a `CALL` to the `solo` precompile's `claim`/`claimSpecific` method.
3. Inside `Execute`, `evm.GetDepth()` returns 1 (the precompile call is the first CALL from the top-level frame), so the "claim must be called by an EOA directly" check at `precompiles/solo/solo.go:114-116` passes even though `authority` is, for the duration of this transaction, executing arbitrary contract logic.
4. Attacker undelegates afterward (as in the existing test's `undelegateTx`), leaving no persistent code and evading any naive "does this address have code right now" checks performed later.
