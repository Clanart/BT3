### Title
Escrow credited with declared order amount instead of actual token balance received — insolvent/drainable escrow for fee-on-transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` in the Tron `IntentGatewayV2` computes the escrow amount from the *declared* `order.inputs[i].amount` (reduced only by the protocol fee), but for ERC-20 transfers it never measures what the contract *actually* received via `safeTransferFrom`. For fee-on-transfer (or otherwise lossy) tokens, the gateway's real token balance increase is smaller than the amount it credits to `_orders[commitment][token]`. This is the same broken invariant as the Slingshot report: a balance/amount value used for accounting does not correspond to the balance the contract truly custodies, and every later `withdraw()` pays out against the wrong figure.

### Finding Description
In `placeOrder`, the escrow bookkeeping value `reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` and `protocolFeeBps`: [1](#0-0) 

For the "no predispatch" path, the contract pulls tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then immediately credits `_orders[commitment][token] += reducedInputs[i].amount` — with no check of the actual balance delta on `address(this)`: [2](#0-1) 

If `token` deducts a transfer fee (fee-on-transfer token, common on Tron/TRC20 forks and some ERC20s), `address(this)` receives strictly less than `order.inputs[i].amount`, yet the escrow ledger is credited with the full (fee-reduced-only-by-protocol-fee) declared amount. When `protocolFeeBps == 0` (e.g., no destination-specific fee configured), `reducedInputs[i].amount == order.inputs[i].amount`, i.e., the escrow is over-credited by exactly the token's transfer fee.

This is the identical bug class from the external report: `_getTokenBalance`/`initialBalance` used the wrong quantity (native balance instead of the wrapped-token balance actually moved), causing `finalOutputAmount` to diverge from the real balance change. Here, the "declared input amount" plays the role of the wrong `initialBalance`: the contract's internal ledger diverges from its real custodied balance.

The fixed, non-Tron `IntentGatewayV2.sol` explicitly guards against this by snapshotting the balance before and after the transfer and using the delta: [3](#0-2) 

with an explicit comment describing exactly this failure mode: "For fee-on-transfer tokens, the gateway receives less than the requested amount... We mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds" — [4](#0-3) . The Tron deployment lacks this fix.

### Impact Explanation
`_orders[commitment][token]` is a shared per-token escrow ledger across all orders placed in the contract. `withdraw()` pays out of the contract's pooled token balance based solely on this ledger value, decrementing `_orders[body.commitment][token] -= amount` and transferring `amount` to the beneficiary without re-checking the real token balance: [5](#0-4) 

Because the ledger can be inflated above what the contract truly holds (fee-on-transfer discrepancy), the pooled balance becomes systematically insolvent. An unprivileged attacker can repeatedly place and then cancel/fill-and-withdraw orders denominated in a fee-on-transfer token to redeem more tokens than they contributed, draining value that other users' legitimately-escrowed orders depend on — a direct "loss of funds to the rightful beneficiary" and cross-order fund theft, not merely a self-inflicted loss.

### Likelihood Explanation
No privileged role, relayer, prover, or governance action is required — a single unprivileged caller triggers `placeOrder` with a fee-on-transfer ERC20 as `order.inputs[i].token`, no admin cooperation needed. The main (non-Tron) `IntentGatewayV2.sol` already treats this exact scenario as a first-class threat (tests explicitly cover `FeeOnTransferToken` round-trips), confirming this is a realistic, expected token type in production usage of the IntentGateway family, and that the Tron variant simply omitted the corresponding fix.

### Recommendation
In the Tron `IntentGatewayV2.placeOrder`, snapshot `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom`, and use the delta (not `order.inputs[i].amount`) as the basis for `reducedInputs`/escrow crediting and for the `commitment` hash — mirroring the "Phase 1: record actual received amounts" logic already implemented in `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy/select a fee-on-transfer ERC20 (e.g., 5% fee) as an input token; ensure `_destinationProtocolFees`/`_params.protocolFeeBps` is `0` for the destination so `reducedInputs[i].amount == order.inputs[i].amount`.
2. Attacker calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000}`. `safeTransferFrom` moves only `950` into the gateway (5% fee burned/redirected), but `_orders[commitment][FOT]` is credited `1000`.
3. Attacker (or a colluding "solver") drives the order to a state where `withdraw()` is invoked with `body.tokens[0].amount == 1000` for this commitment; `withdraw()` transfers `1000` FOT out of the gateway's pooled balance, even though this order only ever contributed `950`.
4. Repeating this siphons `50` FOT per cycle out of the shared pool backing other users' unrelated escrowed orders, eventually causing legitimate withdrawals to revert (`TransferFailed`) or be shorted once the pool balance is exhausted.
