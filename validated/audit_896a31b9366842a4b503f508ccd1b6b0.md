## Analysis

The Across bug is a **push-pattern batch settlement** issue: a single blacklisted recipient inside a leaf that pays out multiple parties causes the whole leaf's token transfer(s) to revert, and because the leaf is atomic, no other beneficiary in that leaf gets paid either.

Hyperbridge's IntentGatewayV2 has the same atomic-push shape in its escrow settlement path.

### Title
Permanent lock of escrowed multi-token intent orders when a single token payout to the beneficiary reverts - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` iterates over every escrowed token in an order and pushes it to a single `beneficiary` in one atomic loop. If any single token transfer to that beneficiary reverts (e.g. the beneficiary is blacklisted on a USDC-style token, or any other token-level transfer restriction triggers), the entire `withdraw()` call reverts, which reverts `onAccept()`, and since this function is invoked by the host via a low-level `call` that is treated as retriable-but-not-abandoned, the order becomes permanently stuck: every other token escrowed in that same order (which would otherwise be redeemable) is also frozen along with the poisoned one.

### Finding Description
`onAccept` dispatches `RedeemEscrow`/`RefundEscrow` requests to `withdraw()`: [1](#0-0) 

`withdraw()` loops over `body.tokens` and pushes each token to the same `beneficiary` using `token.call(...transfer...)`, reverting the whole function (and therefore the whole redemption/refund) if any single transfer fails: [2](#0-1) 

This call is reached through `EvmHost.dispatchIncoming`, which invokes the app via a low-level `call` and, on failure, only deletes the request receipt so the message can be retried later — it never permanently discards the message nor separates the failing sub-item: [3](#0-2) 

Because the blacklist condition on the token side is permanent (it does not go away on retry), every retry of the same `WithdrawalRequest` fails identically. Since `_orders[body.commitment][token]` accounting is only decremented after a successful transfer inside the same atomic loop (line 701), none of the other, non-blacklisted tokens in that order can ever be redeemed either — the escrowed balance for the whole order is locked forever, with no fallback that splits the payout per-token or defers only the problematic token, unlike what Across ultimately committed to doing off-chain for refund leaves.

### Impact Explanation
This falls under "loss/lock of bridged funds in intent settlement/escrow" as called out in the impact gate. A single blacklisted or reverting-token beneficiary in a multi-token order permanently locks 100% of the escrowed assets for that order — not just the affected token — because `withdraw()` is atomic and irrecoverable via any on-chain fallback. There is no pull-based per-token claim path, no way to skip the poisoned token, and no admin recovery mechanism visible in this function.

### Likelihood Explanation
The trigger condition (a beneficiary being blacklisted on one of several escrowed tokens, or any ERC20 revert-on-transfer restriction) is realistic for common stablecoins like USDC that implement blacklists, and orders bundling multiple tokens to a single beneficiary are a normal, permissionless usage pattern of the intents flow (fillers/solvers set the beneficiary and token set when the order is created/filled) — no privileged actor, relayer misbehavior, or governance action is required to reach this state. The only uncertainty is how commonly multi-token orders to a single beneficiary are used in practice versus single-token orders, which affects the frequency but not the existence of the bug.

### Recommendation
Change `withdraw()` to not let a failure in one token transfer block redemption of the others: iterate defensively (try/catch or low-level call with per-token success bookkeeping) so that a failing token transfer is skipped/deferred (e.g., tracked in a separate "stuck" mapping redeemable by a pull-based claim) while all other tokens in the same order are still delivered and their internal accounting decremented.

### Proof of Concept
1. An order escrows two tokens for the same `beneficiary`: `TOKEN_A` (a standard ERC20) and `TOKEN_B` (a USDC-like token with a blacklist).
2. `beneficiary` gets added to `TOKEN_B`'s blacklist (independently of Hyperbridge, by the token issuer) before the order settles/refunds.
3. Relayer submits the `RedeemEscrow`/`RefundEscrow` message; `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept` → `withdraw(body, ...)`.
4. The loop transfers `TOKEN_A` successfully, then attempts `TOKEN_B.transfer(beneficiary, amount)`, which reverts due to the blacklist; `withdraw()` reverts entirely via `revert TransferFailed()`.
5. `dispatchIncoming` catches the failed low-level call, deletes the request receipt, and returns — the message can be resubmitted indefinitely, but every resubmission fails identically because the blacklist doesn't change.
6. `TOKEN_A`, which had no issue, is never delivered either, and both escrowed tokens remain locked in the `IntentGatewayV2` contract permanently.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
