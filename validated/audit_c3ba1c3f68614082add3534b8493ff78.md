### Title
OP_RETURN `data` output omitted from weight/fee calculation causes signed transactions to underpay fees and risk being unrelayed - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds a zero-value OP_RETURN output to `tx_outs` when `data` is supplied, but computes the transaction weight and `needed_fee` from `payments` alone — which does not include the data output. The resulting `SignableTransaction` therefore commits to (and the threshold signers sign) a transaction whose actual virtual size is larger than the size used for fee estimation, so the effective fee rate is always below `fee_per_vbyte` and can fall below the network minimum relay fee.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` at `networks/bitcoin/src/wallet/send.rs:194-202`:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

However, the weight/vbyte estimate is computed from `payments`, not `tx_outs`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```
(`send.rs:204-206`)

and the change path does the same:

```rust
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```
(`send.rs:225-226`)

`calculate_weight_vbytes` builds its dummy transaction's `output` list exclusively from `payments` (`send.rs:85-94`) plus an optional change output (`send.rs:95-99`). An OP_RETURN output of `data.len()` up to 80 bytes adds roughly `9 + 1 + (1 + 80) + 4 ≈ 95` serialized bytes (≈ 95+ vbytes, all non-witness) that are never counted. The minimum-relay check at `send.rs:211` and the `NotEnoughFunds` check at `send.rs:215` are both evaluated against this underestimated `needed_fee`.

There is a second-order error as well: when change is emitted, the change amount is `input_sat - payment_sat - fee_with_change` (`send.rs:228-230`). Because `fee_with_change` is under-estimated, the change output is *over*-valued, further reducing the real fee `sum(inputs) - sum(outputs)` below the intended `fee_per_vbyte * actual_vbytes`.

### Impact Explanation
Analogous to the source finding (funds moved into a state where the counterparty cannot recover them), an affected transaction is signed and broadcast with a fee rate lower than requested. In the worst case — `fee_per_vbyte` chosen near the relay minimum and a large `data` payload — the true fee rate drops below `DEFAULT_MIN_RELAY_TX_FEE`, the transaction is rejected by Bitcoin Core's mempool, and the inputs are effectively frozen until the processor rebuilds and re-signs the transaction with a corrected fee. Even when relayed, the transaction confirms later than intended, which for a bridge/liquidity protocol translates to stuck or delayed user funds. `fee()` and `needed_fee()` (`send.rs:133-141`) also misreport, so any caller relying on them for accounting is misled.

### Likelihood Explanation
The `data` field is populated with externally influenced instruction data (the OP_RETURN carries the Serai `InInstruction`-style payload for cross-chain operations), so transactions exercising this path exist in normal operation. The underestimation is deterministic whenever `data.is_some()`. Whether it crosses the relay-minimum threshold depends on the chosen `fee_per_vbyte`, so impact ranges from degraded confirmation priority to an unbroadcastable transaction locking the selected `ReceivedOutput` inputs.

### Recommendation
Compute weight over the final `tx_outs` (including the OP_RETURN data output) rather than `payments`. Concretely, change `calculate_weight_vbytes` to accept the full `Vec<TxOut>`/`&[TxOut]` (or a `data: Option<&[u8]>` parameter that appends the OP_RETURN output inside the estimator) and invoke it after `tx_outs` is populated, for both the no-change and with-change estimates. Alternatively, push the data output into the estimator's output list before computing `weight`, `vbytes`, `needed_fee`, and `fee_with_change`.

### Proof of Concept
```rust
// Networks/bitcoin conceptual test (regtest not required):
let inputs = vec![received_output];            // any ReceivedOutput with sufficient value
let payments = [(p2tr_script_buf(key).unwrap(), 10_000u64)];
let data = vec![0xaa; 80];                     // max permitted OP_RETURN payload

let tx = SignableTransaction::new(
    inputs, &payments, None, Some(data), FEE_PER_VBYTE,
).unwrap();

// needed_fee was computed over tx without the OP_RETURN output
let estimated_vbytes = tx.needed_fee() / FEE_PER_VBYTE;
let actual_vbytes = tx.transaction().vsize() as u64; // includes ~95-byte OP_RETURN output

assert!(actual_vbytes > estimated_vbytes);
// Real effective fee rate < FEE_PER_VBYTE:
assert!(tx.fee() < FEE_PER_VBYTE * actual_vbytes);
```
With `FEE_PER_VBYTE` set so `needed_fee` equals the minimum relay fee for the *underestimated* size (passing the check at `send.rs:211`), the actual fee rate `tx.fee() / actual_vbytes` falls below `DEFAULT_MIN_RELAY_TX_FEE`, and `send_raw_transaction` rejects the signed transaction — leaving the consumed outputs unspent and the funds unmovable.
