### Title
Trust granted to a repository path via `safe.directory` is permanent and never re-validated or revoked, allowing a previously-trusted path to be silently treated as safe when repopulated with attacker content - (File: `app/src/lib/git/config.ts`)

### Summary
The reported DCT bug is a broken invariant: a privilege (voting power) is granted based on a resource (staked DCT) but is never revoked when that resource is withdrawn, so the same privilege can be re-derived and reused elsewhere. The GitHub Desktop analog is the "unsafe repository" trust mechanism: `addSafeDirectory()` grants permanent, path-scoped trust by writing the path string to the global `safe.directory` git config, and there is no corresponding "remove/revoke" function anywhere in the codebase (`removeSafeDirectory` does not exist), and no re-validation tied to repository identity/content.

### Finding Description
When Desktop encounters a repository whose directory is owned by a different user, `getRepositoryType()` detects Git's "dubious ownership" error and returns `{ kind: 'unsafe', path }` [1](#0-0) . The UI (`AddExistingRepository.onTrustDirectory` and `MissingRepository.onTrustDirectory`) lets the user click "Trust Repository", which calls `addSafeDirectory(path)` [2](#0-1) [3](#0-2) .

`addSafeDirectory` appends the *path string* (not any repository identity, remote URL, or commit hash) to the global `safe.directory` config, permanently, via `addGlobalConfigValueIfMissing` [4](#0-3) . Once a path is in `safe.directory`, Git will never again flag it as "dubious ownership," and no code path in this codebase ever removes an entry from `safe.directory` - there is no `removeSafeDirectory` function, and `_removeRepository`/repository removal flows do not touch this config value.

This mirrors the DCT bug exactly: trust (voting power / dp2pDToken) is granted once based on a transient state (staked DCT / an ownership check at a point in time) and is never invalidated when the underlying state changes (DCT withdrawn / directory ownership changes again, or the directory is reused for different content). Just as an abuser moves DCT to a new account to re-mint voting power while old power lingers, an attacker can cause a directory path that a user previously trusted to be repopulated with different, attacker-controlled repository content (e.g. via `_relocateRepository`, "Clone Again" (`cloneAgain`) reusing the same on-disk path [5](#0-4) , a removable/shared/network drive, or a path reused after the original repo directory was deleted and recreated by another process/user). Desktop will silently treat that new, potentially malicious repository as trusted with no ownership warning and no re-prompt, because the stale `safe.directory` entry for that path is never re-validated against the actual repository content or removed.

### Impact Explanation
Git treats `safe.directory` as a security boundary specifically to stop automatic execution of repository-controlled config/hooks/filters (e.g. `core.fsmonitor`, `core.hooksPath`, filters) for repos of unknown/different ownership. Because trust is bound only to a filesystem path and persists indefinitely, an attacker who can get attacker-controlled repository content placed at a path the victim previously trusted (a shared directory, an external drive, a path the user relocates a repo to, or a path reused after deletion) causes Desktop/Git to skip the dubious-ownership check entirely, enabling attacker-controlled config/hooks to execute in the victim's environment without any additional prompt.

### Likelihood Explanation
Requires the attacker to control a directory the user will later trust or one the user later reuses/relocates a repository into - consistent with the "attacker controls a cloned/fetched repository" impact class, since the attacker only needs to control content that ends up in a repository path, not the user's machine or credentials. This is a realistic-but-not-trivial precondition (shared/removable media, path reuse via relocate/clone-again, multi-user machines), which is exactly the scenario the `unsafe`/`safe.directory` mechanism was designed to guard against, and it silently defeats that guard once trust has been granted once.

### Recommendation
Do not treat `safe.directory` trust as permanent based on path alone:
- Re-verify repository identity (e.g., remote URL / origin, or a fingerprint of the `.git` directory) before honoring a previously-added `safe.directory` entry, and re-prompt if it has changed.
- Provide a way to revoke/remove `safe.directory` entries (mirroring `removeConfigValue`/`removeGlobalConfigValue` in `app/src/lib/git/config.ts`) when a repository is removed from Desktop, relocated, or found to be missing/replaced.
- Consider scoping trust to session or to a specific detected repository state rather than an indefinite global git config entry.

### Proof of Concept
1. User adds a repository at path `P` owned by another user; Desktop shows the unsafe-repository warning and the user clicks "Trust Repository," calling `addSafeDirectory(P)` [2](#0-1) , permanently adding `P` to the global `safe.directory` list [6](#0-5) .
2. The user later removes/relocates the repository, or the directory at `P` is deleted and repopulated by another process/user/attacker with a different, malicious Git repository (e.g., malicious `core.hooksPath`/filters).
3. When Desktop (or the user via `git`) opens path `P` again, `getRepositoryType(P)` no longer returns `unsafe` because `safe.directory` still contains `P` - Git skips the ownership check entirely and no warning is shown [1](#0-0) .
4. Any Git operation Desktop performs against `P` (fetch, checkout, status) now runs with the attacker's repository-controlled config/hooks trusted, since no code path ever calls a removal equivalent for `safe.directory` for this path.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
