### Title
Out-of-range `Participant` index in a blame accusation panics `Decryption::decrypt_with_proof` / `BlameMachine::blame_internal`, crashing the blame evaluator - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG blame API accepts `sender`/`recipient` as attacker-influenced `Participant` values and then indexes internal `HashMap`s with them (`self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388`, `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599`). `HashMap`'s `Index` impl panics on a missing key, so any accusation naming a participant outside the registered `1 ..= n` set causes an unconditional panic — a reachable-assertion denial of service, the same bug class as CVE-2022-0865 (assert reachable via a crafted file in `tiffcp`).

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` are public APIs taking `sender: Participant`, `recipient: Participant`, an `EncryptedMessage<C, SecretShare<C::F>>`, and an optional `EncryptionKeyProof<C>` — all derivable from an accusation message/bytes supplied by other parties. Both delegate to `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`), which calls `Decryption::decrypt_with_proof`.

Inside `decrypt_with_proof`:

```rust
// crypto/dkg/pedpop/src/encryption.rs
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // line 388: HashMap Index -> panic if absent
  )
```

`self.enc_keys` is populated only for participants `1 ..= n` (see `AdditionalBlameMachine::new`, `crypto/dkg/pedpop/src/lib.rs:656-660`, and `Decryption::register` at `encryption.rs:351-362`). `Participant` indexes are `u16`-based and are parsed from attacker-controlled bytes elsewhere (e.g., `InvalidDkgShare` accuser/faulty fields via `Participant::new(u16::from_le_bytes(..))`), with no bound against `n` at parse time. If `recipient` is `> n` (or simply wasn't registered), the indexing panics.

A second panic on the same path exists at `self.commitments[&sender]` (`lib.rs:599`), reached once decryption succeeds when `sender` is out of range — achievable by an accuser who constructs a well-formed `EncryptedMessage` plus a valid `EncryptionKeyProof` (the proof format is public: `EncryptionKeyProof::read` at `encryption.rs:267-269`) while naming an invalid sender index.

Nothing in `blame`, `blame_internal`, or `decrypt_with_proof` validates `sender`/`recipient` membership before the map lookups; the only participant sanity check anywhere is the `assert!` in `Decryption::register` (`encryption.rs:356-359`), which guards re-registration, not lookup.

### Impact Explanation
A single crafted blame/accusation input deterministically panics the thread evaluating it. In a deployment where blame evaluation runs on the node's main/consensus path, this is an unprivileged remote denial of service: the attacker supplies an accusation referencing `Participant(n+1)` (or any unregistered index) with a self-consistent `EncryptedMessage` + `EncryptionKeyProof` they can generate themselves (the PoP/DLEq challenge functions are public, deterministic, and bind only to attacker-known secrets). Because blame is expected to *always return a `Participant`* rather than crash, the panic also prevents the protocol from attributing fault, aborting DKG error handling entirely. This maps to a Medium-severity availability impact consistent with the CVE (CVSS 5.5, A:H only).

### Likelihood Explanation
Reachability requires only that the application routes externally supplied accusation data (participant indexes + serialized `EncryptedMessage`/`EncryptionKeyProof`) into `BlameMachine::blame`/`AdditionalBlameMachine::blame` — the documented purpose of these APIs. Crafting the inputs needs no private key material: an accusation's `sender`/`recipient` are bare indexes, and reaching the `enc_keys[&decryptor]` panic only requires `msg.pop` to verify, which the attacker satisfies by encrypting to any key they choose and signing the PoP themselves. Likelihood is moderate: it requires the surrounding protocol to expose a blame/accusation message type carrying participant indexes, which Serai's DKG flow does.

### Recommendation
Replace `HashMap` `Index` lookups with fallible access and surface a `PedPoPError`:

- In `Decryption::decrypt_with_proof` (`encryption.rs:388`), use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` (or a dedicated `UnknownParticipant` variant).
- In `BlameMachine::blame_internal` (`lib.rs:599`), use `self.commitments.get(&sender)` and return an error/`sender` when absent.
- Optionally validate `sender`/`recipient ∈ 1..=n` at the top of `blame`/`blame_internal` before any lookup.

### Proof of Concept
```rust
// Setup: run a PedPoP DKG to completion for n = 3, t = 2 over any Curve C,
// obtaining an AdditionalBlameMachine via BlameMachine::blame or
// AdditionalBlameMachine::new(context, n, commitment_msgs).
//
// Attacker crafts an accusation where `recipient` is not a registered participant:
let bogus_recipient = Participant::new(4).unwrap(); // n = 3

// Any EncryptedMessage with a valid PoP suffices. The attacker encrypts a
// share to a key they control, computing pop over
// pop_challenge(context, R, key, sender, msg) themselves.
let msg: EncryptedMessage<C, SecretShare<C::F>> = attacker_crafted_msg_with_valid_pop();

// A valid EncryptionKeyProof: DLEq over [G, msg.key] for a scalar the
// attacker knows, read/produced via EncryptionKeyProof::read / DLEqProof::prove.
let proof: Option<EncryptionKeyProof<C>> = Some(attacker_crafted_dleq());

// PANIC: inside decrypt_with_proof, `self.enc_keys[&bogus_recipient]`
// indexes a HashMap with an absent key -> thread panics instead of
// returning blame. Machine: crypto/dkg/pedpop/src/encryption.rs:388.
machine.blame(sender, bogus_recipient, msg, proof);
```

The simpler variant — calling `blame` with `recipient`/`sender` set to any `Participant` never registered — panics at `encryption.rs:388` as soon as a `Some(proof)` is supplied, with no secret knowledge required beyond generating a valid DLEq over the attacker's own key.
