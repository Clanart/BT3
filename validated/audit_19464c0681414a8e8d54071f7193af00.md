Based on my investigation, this is confirmed to be a real, exploitable analog.

Key evidence: `_refreshRepository()` calls `refreshChangesSection(repository, { includingStatus: false, clearPartialState: false })` after a checkout [1](#0-0) , and `_checkoutBranch`/`_checkoutCommit`/`_mergeBranch` all funnel into `_refreshRepository` after the working tree content changes [2](#0-1) [3](#0-2) . `clearPartialState: false` means `updateChangedFiles()` preserves the exact prior `DiffSelection` object (with its diverging-line index set) onto the new file object as-is [4](#0-3) . The diff is then reloaded and `withSelectableLines()` is applied, which only intersects diverging line *indices* against the new selectable-index set — it does not verify the line *content* is the same, exactly matching the OI bug's flaw of reusing a stale value without validating it against updated ground truth [5](#0-4) [6](#0-5) . The code comment explicitly admits this: "Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist" [7](#0-6) .

### Title
Stale line-index-based partial commit selection silently carries over to unrelated diff content after a merge/checkout - (File: app/src/lib/stores/app-store.ts)

### Summary
When a user has partially selected lines for commit in the Changes view and an attacker-influenced merge, checkout, or pull operation rewrites the working-tree diff for that same file, GitHub Desktop reuses the old `DiffSelection`'s line-index set against the new diff without validating that the selected index still corresponds to the same textual content. If the new diff has a line at the same numeric position that is still "selectable," it stays checked even though it is entirely different content, causing the wrong lines to be silently included in the next commit.

### Finding Description
`updateChangedFiles()` merges new working-directory `IStatusResult` file objects with existing files by re-attaching the previous `DiffSelection` object wholesale whenever `clearPartialState` is `false`: `return file.withSelection(existingFile.selection)` [4](#0-3) . This path is taken after every `_refreshRepository()` following a checkout, merge, pull, or rebase (`clearPartialState: false`) [8](#0-7) .

The reused `DiffSelection` tracks selected/unselected state purely via numeric `divergingLines` indices, not content hashes [9](#0-8) . When the diff for the file is subsequently reloaded, `updateChangesWorkingDirectoryDiff()` computes a fresh `selectableLines` set from the new diff and calls `withSelectableLines()`, which only removes diverging indices that are *no longer selectable at all* — it does not re-verify that an index still selectable in the new diff represents the same line of text [6](#0-5) [5](#0-4) . This is exactly analogous to the reported Solidity bug: a stale value (the checked/unchecked state tied to an index) is carried forward into a new state space (a new diff) without accounting for the fact that the thing it originally represented has "expired" (shifted or replaced), producing an incorrect result (wrong lines flagged for commit) that isn't validated against the new ground truth.

This is a broken invariant that the same numeric diff-line index always represents the same content across successive diff loads for a file — an invariant that does not hold when the file's underlying diff structure changes (lines added/removed elsewhere in the hunk shift all subsequent line indices).

The corrupted value is the `DiffSelection.divergingLines` set attached to a `WorkingDirectoryFileChange`, specifically after: (1) the user partially selects lines in a file's diff, (2) an operation such as `_checkoutBranch`, `_checkoutCommit`, or `_mergeBranch` changes the on-disk content of that same file (e.g., due to a fast-forward merge/checkout pulling in attacker-supplied commits from a fetched branch/PR while the user still has the Changes tab open with a pending partial selection), and (3) `_refreshRepository` reloads status with `clearPartialState: false` and reattaches the stale selection to the new diff.

Existing guards do not stop this: the code only filters out diverging lines that are no longer *selectable at all* (i.e. now a context line or past end of file) [5](#0-4) ; it does not diff the line content itself, so an index that remains "selectable" in the new diff (very likely, since most content is still additions/deletions somewhere) keeps its stale checked/unchecked state.

### Impact Explanation
If a user has staged only some lines of a file (e.g., deliberately excluding a debug print, a secret, or a WIP change) and then performs a checkout/merge/pull that alters that file's diff structure before committing, the app can silently commit or exclude lines that no longer correspond to what the user originally reviewed and selected — without any warning that the selection may now be stale. This is a silent corruption of what the user commits, matching the "Valid Impact" criteria for corruption of commit content driven by attacker-influenced repository content (a fetched/merged branch).

### Likelihood Explanation
Medium-low: it requires the specific sequence of (a) an open partial selection on a file, (b) a checkout/merge/pull that changes that same file's diff while the Changes view retains the old selection object, and (c) the user committing without re-reviewing the diff, trusting the previously-set checkboxes. Desktop's own UI encourages reviewing diffs before commit, which somewhat mitigates likelihood, but nothing in the code invalidates or warns about a stale selection, and the flow through `_refreshRepository → refreshChangesSection(clearPartialState:false) → updateChangedFiles → withSelectableLines` is a normal, frequently-hit path.

### Recommendation
When reloading a file's diff after a background refresh (checkout, merge, pull), invalidate/reset partial selection state instead of blindly reusing index-based `divergingLines`, or make `withSelectableLines`/`updateChangesWorkingDirectoryDiff` compare line content (not just line index) before preserving a line's selected state, clearing to `withSelectNone()`/re-prompting the user whenever the underlying diff hunks for a file have structurally changed.

### Proof of Concept
1. In repo R, modify `file.txt` locally with 10 added lines; in the Changes view, select only lines 3–5 for commit (partial selection), leaving the tab open without committing.
2. Fetch/merge a remote branch (attacker-controlled, e.g., a PR branch) that also modifies `file.txt`, shifting line positions (e.g., inserting 5 lines before the user's local changes) via `_mergeBranch`/`_checkoutBranch`, triggering `_refreshRepository` → `refreshChangesSection({ clearPartialState: false })` [8](#0-7) .
3. `updateChangedFiles` reattaches the old `DiffSelection` (indices 3–5) to the new file entry [10](#0-9) ; `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` from the new diff and calls `withSelectableLines`, which keeps indices 3–5 selected since they are still selectable positions in the new hunk layout, even though the content at those positions is now different (originating from the merged branch) [6](#0-5) .
4. The UI still shows the checkboxes for the "same" lines as checked (no re-review prompt); the user commits, and `_commitIncludedChanges` uses `file.selection.getSelectionType()` to build the patch via `formatPatch`, which invokes `file.selection.isSelected(absoluteIndex)` on the new (post-merge) diff using the stale indices [11](#0-10)  — committing content the user never actually reviewed or intended to include.
