### Title
`verify-package` never compares fetched on-chain bytecode against locally compiled bytecode - ([File: aptos-move/cli/src/stored_package.rs])

### Summary
`aptos move verify-package` is documented as the tool that "checks that on-chain bytecode matches a local source tree" [1](#0-0) . In practice, its implementation only diffs the `PackageMetadata` struct (name, `deps`, `modules` metadata — i.e. gzipped source text/source-map, not bytecode —, `manifest`, `upgrade_policy`, `extension`, `source_digest`) fetched from the `0x1::code::PackageRegistry` resource against a locally rebuilt package's metadata [2](#0-1) . The actual compiled bytecode blobs on chain are never fetched or compared, because `CachedPackageRegistry::create` is invoked with `with_bytecode = false` in the `VerifyPackage` command [3](#0-2) , leaving `CachedPackageRegistry.bytecode` empty and unused by `verify()` [4](#0-3) .

### Finding Description
`PackageMetadata::modules` (the `ModuleMetadata` list) only carries optional gzipped `source` and `source_map` blobs plus a `name` — it never contains the actual bytecode of the module [5](#0-4) . The bytecode that is actually loaded and executed lives in separate module storage created via `code::publish_package_txn` / `request_publish_with_allowed_deps`, entirely outside `PackageMetadata` [6](#0-5) .

`CachedPackageRegistry::create` does support fetching per-module bytecode via `client.get_account_module`, but only when `with_bytecode` is `true` [4](#0-3) . `VerifyPackage::execute` calls `CachedPackageRegistry::create(client, self.account, false)`, i.e. explicitly skips fetching the deployed bytecode, then only calls `package.verify(&compiled_metadata)` [7](#0-6) . `verify()` in turn only compares `name`, `deps`, `modules` (metadata, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest` [2](#0-1) .

`source_digest` itself is derived purely from hashing the source files supplied at publish time — "sha256 of each individual source, than sorting them alphabetically, and sha256 them again" [8](#0-7)  — and is computed locally by the publisher's toolchain when producing `PackageMetadata`, not independently derived from the on-chain bytecode by the VM. Nothing in the publish path (`code::publish_package`, `native_request_publish`, `validate_publish_request`) requires or checks that the submitted `ModuleMetadata.source`/`source_map` or the manifest actually correspond to the bytecode in `code: vector<vector<u8>>` that is stored and executed [9](#0-8) . The VM only checks that the *set of module names* declared in metadata matches the module names in the bytecode bundle (`expected_modules`) [10](#0-9) ; it never validates that the declared `source`/`source_map`/`source_digest` describe the bytecode being published.

Consequently, a publisher (or a code-object owner) can submit `PackageMetadata` whose `source`/`source_map`/`manifest`/`source_digest` describe one program while shipping arbitrary different bytecode in the `code` vector, and `aptos move verify-package` — the officially documented tool for "code review and reproducibility" [1](#0-0)  — will still print `"Successfully verified source of package"` [11](#0-10)  because it only re-derives `source_digest`/`ModuleMetadata` from the locally compiled sources and diffs them against the on-chain metadata fields, never against the actually running bytecode.

### Impact Explanation
This breaks the code-safety invariant that "verified bytes, package metadata, dependency declarations, and committed module bytes" must agree. Downstream consumers, auditors, or integrators who rely on `aptos move verify-package` to confirm that on-chain bytecode matches published/audited source will get a false positive "verified" result even when the deployed bytecode diverges from the claimed source. This is a supply-chain / code-integrity bypass: it does not by itself grant unauthorized publish/upgrade rights (those are separately protected by owner checks in `code::publish_package`/`object_code_deployment`), but it defeats the code-verification/bytecode-provenance guarantee that the ecosystem depends on for trusting deployed contracts, satisfying the "mismatch between verified bytes, package metadata... and committed module bytes" impact category.

### Likelihood Explanation
Any account or object owner who legitimately controls a package (no privilege escalation required) can trivially trigger this by publishing metadata whose `source`/`manifest`/`source_digest` do not match the bytecode blob they submit — the publish natives never cross-check them [12](#0-11) . Anyone later running the standard `aptos move verify-package` CLI flow against that package's address will be misled, since the command is hard-coded to skip bytecode retrieval (`with_bytecode = false`) [13](#0-12) . This requires no special network conditions and reproduces deterministically on every invocation of the command against such a package.

### Recommendation
Update `VerifyPackage::execute` to call `CachedPackageRegistry::create(client, self.account, true)` so on-chain bytecode is fetched, and extend `CachedPackageMetadata::verify` (or add a new check) to compare each module's fetched on-chain bytecode byte-for-byte (or via a canonical hash) against the bytecode produced by locally compiling the same source with the declared build options, in addition to the existing metadata-field comparison in `aptos-move/cli/src/stored_package.rs`.

### Proof of Concept
1. Build and publish a package where `PackageMetadata.modules[i].source`/`source_map` and `manifest`/`source_digest` describe module `M` compiled from source `S1`, but the `code` vector passed to `code::publish_package_txn` actually contains the bytecode compiled from a different, behaviorally distinct source `S2` (same module name, so `expected_modules` check in `validate_publish_request` still passes) — nothing in `native_request_publish`/`validate_publish_request` rejects this mismatch [12](#0-11) .
2. Run `aptos move verify-package --account <addr>` using the source tree for `S1`.
3. Observe the CLI builds `S1` locally, calls `CachedPackageRegistry::create(client, addr, false)` (bytecode not fetched) [13](#0-12) , and `package.verify(&compiled_metadata)` succeeds because it only compares metadata fields that were derived from `S1` on both sides [2](#0-1) , printing `"Successfully verified source of package"` even though the executing bytecode is actually `S2`.

impl CachedPackageRegistry {
    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
