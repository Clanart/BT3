### Title
Payout OP_RETURN operator attribution is unauthenticated and can be swapped via a conflicting transaction, causing wrong-operator reimbursement / permanent reimbursement denial - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` embeds `operator_xonly_pk` in an OP_RETURN output that is never covered by any signature; the only signature present is the user's `SinglePlusAnyoneCanPay` signature over the withdrawal input (input0) and the withdrawal output (output0). Because SIGHASH_SINGLE|ANYONECANPAY leaves every other input and output — including the OP_RETURN and the funding inputs — completely unauthenticated, anyone who observes a broadcast payout transaction can build a conflicting transaction that reuses the same signed input0/output0 but substitutes a different `operator_xonly_pk` in the OP_RETURN and funds the transaction from a different wallet, then win the race to confirmation.

### Finding Description
The claimed binding is:
`operator_xonly_pk bytes embedded in the confirmed payout OP_RETURN == the operator whose wallet actually paid for the withdrawal`

`create_payout_txhandler` builds the OP_RETURN purely from the caller-supplied `operator_xonly_pk` with no cryptographic commitment: [1](#0-0) 

The only signature attached to the transaction is the user's, verified with `SinglePlusAnyoneCanPay`: [2](#0-1) 

`calculate_pubkey_spend_sighash` shows that for `SinglePlusAnyoneCanPay` the sighash only commits `Prevouts::One(txin_index, ...)` (input0) and, per SIGHASH_SINGLE semantics, output0 — every other input/output (funding inputs added later, the anchor output, and the OP_RETURN) is unauthenticated: [3](#0-2) 

The operator's `withdraw` flow itself demonstrates that the large payout output (output0) is not funded by input0 alone — Bitcoin Core's `fund_raw_transaction` with `add_inputs: true` adds whichever wallet inputs are needed to cover it, and those added inputs/witnesses are outside the committed sighash: [4](#0-3) 

Because input0's signature and output0 remain valid regardless of which extra inputs fund the transaction or what OP_RETURN bytes are attached, any party who sees the broadcast (unconfirmed) payout transaction can extract input0's witness and construct a competing transaction: same input0 + output0, but with a different `operator_xonly_pk` in the OP_RETURN and different funding inputs/change (paid by any wallet). If this competing transaction confirms instead of the original, the verifier's block-sync logic parses whatever OP_RETURN ends up on-chain and writes that operator's key into the DB as the payer, with no cross-check against who actually funded it: [5](#0-4) [6](#0-5) 

Downstream, `PayoutCheckerTask` looks up "unhandled" payouts strictly by the operator's own xonly_pk recorded from the OP_RETURN and, if it finds a match, drives `handle_finalized_payout` → kickoff → reimbursement for that operator — with no check that this operator's wallet actually paid the withdrawal: [7](#0-6) 

`is_kickoff_malicious` only checks that the DB-recorded `operator_xonly_pk` (itself derived only from the confirmed OP_RETURN bytes) matches the kickoff's claimed operator — it never checks the funding wallet: [8](#0-7) 

None of the existing guards (`is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr` on the user signature, `is_kickoff_malicious`) validate that the operator named in the OP_RETURN is the one who supplied the funding inputs, because no such signature or commitment exists anywhere in the protocol.

### Impact Explanation
Two mutually reinforcing critical outcomes result from a single attack:
- The operator whose key ends up in the confirmed OP_RETURN (e.g., "Operator B") is credited as the payer in the `withdrawals` table and can later send a kickoff and go through the full reimbursement flow to be paid from the bridge's move-to-vault funds, even though Operator B's wallet never funded the withdrawal — "an operator reimbursed for a payout it never funded."
- The operator who actually intended and attempted to fund the payout (e.g., "Operator A") never finds this withdrawal in `get_first_unhandled_payout_by_operator_xonly_pk` because the confirmed OP_RETURN no longer matches its key, so it can never initiate a kickoff/reimbursement for this deposit — "an honest operator permanently unable to be reimbursed."

Both are listed Critical impact categories. The attack is repeatable per withdrawal/deposit and does not depend on operator collusion; it only requires visibility into the (unconfirmed) payout tx and the ability to pay a competitive fee.

### Likelihood Explanation
The attacker needs no privileged role: any party monitoring the mempool for `withdraw`-initiated payout transactions can extract the public, already-broadcast SinglePlusAnyoneCanPay-signed input0/output0 pair, attach arbitrary funding inputs from their own wallet, substitute any operator's public xonly pubkey (operator pubkeys are protocol-public data) into the OP_RETURN, and broadcast/relay a fee-competitive conflicting transaction. Winning the confirmation race requires only paying real BTC fees comparable to or higher than the original operator's transaction — an ordinary mempool/RBF race, not a cryptographic break. This is feasible on regtest/testnet and would be feasible on mainnet at the cost of covering the withdrawal amount plus fees.

### Recommendation
Bind the OP_RETURN operator pubkey to the transaction's authorization: e.g., require the operator to additionally sign (or have the aggregator/verifiers co-sign) a commitment covering the OP_RETURN output and/or the full set of payout outputs using `SIGHASH_ALL` (or an explicit second signature) so that the OP_RETURN cannot be swapped without invalidating the signature; alternatively, have verifiers cross-check the funding-input wallet/change address against the OP_RETURN-claimed operator before crediting reimbursement eligibility in `update_finalized_payouts`/`is_kickoff_malicious`.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
