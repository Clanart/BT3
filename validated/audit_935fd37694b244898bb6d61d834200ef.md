## Title
Ed25519 shred-signature verification uses non-strict `verify` (malleable), bypassing shred dedup and duplicate-shred budget — (File: `ledger/src/shred.rs`, `ledger/src/shred/merkle.rs`, `ledger/src/sigverify_shreds.rs`)

## Summary
`Shred::verify` in `ledger/src/shred.rs` and `MerkleShred::verify` in `ledger/src/shred/merkle.rs` both call plain `Signature::verify(pubkey, data)` on the shred's `signed_data()` rather than the cofactored/canonical `verify_strict` that the codebase itself already uses in the ed25519 precompile. Because plain `verify` accepts non-canonical `S` encodings, an attacker who observes one legitimately signed shred can derive several byte-distinct signatures that still verify for the same payload, without the leader's private key.

## Finding Description
`ledger/src/shred.rs` lines 558-564 and `ledger/src/shred/merkle.rs` lines 112-118 both perform `self.signature().verify(pubkey.as_ref(), data.as_ref())`, the non-strict ed25519 check that does not reject `S ≥ L` or other non-canonical encodings. [1](#0-0) [2](#0-1)  This is confirmed in contrast to `precompiles/src/ed25519.rs`, which deliberately calls `verify_strict` and has a dedicated `test_ed25519_malleability` regression test proving `verify` accepts a malleable signature that `verify_strict` rejects. [3](#0-2) [4](#0-3) 

The shred sig-verify LRU cache in `ledger/src/sigverify_shreds.rs` keys on raw `(Signature, Pubkey, merkle_root)` and also calls the same non-strict `.verify()`, so each malleated encoding is a distinct cache key and a distinct verification cost. [5](#0-4) [6](#0-5) 

In `turbine/src/retransmit_stage.rs`, `ShredDeduper::dedup` first dedups on `get_common_header_bytes` (which embeds the raw signature bytes) and falls back to a bounded `shred_id_filter` sized by `MAX_DUPLICATE_COUNT`, intended to allow only a small number of genuinely different (equivocated) shreds per `ShredId` through. [7](#0-6)  A malleated shred has different header bytes but the same signed data, so it escapes the fast header-hash dedup and instead consumes one of the `shred_id_filter`'s bounded slots via the `(0..max_duplicate_count).all(|i| self.shred_id_filter.dedup(&(key, i)))` logic, which internally calls the Bloom-filter-style `Deduper::dedup` that inserts as a side effect on every call. [8](#0-7) 

I confirmed all cited code locations exist verbatim in the repository as quoted in the claim, and the underlying dedup mechanics (`Deduper::dedup` inserting into a Bloom-filter bitset with `.all()`-based checking) match the described exhaustion path.

## Impact Explanation
This maps to "non-RPC remote exhaustion/crash" and weakens duplicate-block detection guarantees. An attacker who has observed a single valid shred over turbine can synthesize a bounded number (~8, governed by `2^256 / L`) of additional valid signature encodings for the exact same shred and inject them via the shred-fetch/TVU ingestion path. Each variant forces (a) a fresh, guaranteed-miss entry in the sig-verify LRU cache keyed on raw signature bytes, causing redundant ed25519 CPU cost, and (b) consumption of one of the limited `MAX_DUPLICATE_COUNT` slots in `shred_id_filter` reserved for genuine leader-equivocation evidence in `turbine/src/retransmit_stage.rs`, potentially crowding out real duplicate-shred detection for that `ShredId`.

## Likelihood Explanation
Likelihood is moderate: no leader/validator collusion or private key is required — only observing one valid shred on turbine (trivial) and the ability to send crafted UDP packets to a validator's shred ingestion socket, which is the normal path for turbine/repair shreds. The amplification factor is small (bounded ~8x per captured shred) and requires only cheap byte-level arithmetic on `S`, cheaper than the validator's ed25519 verification cost, and is easily automated across many shreds/slots.

## Recommendation
Switch shred-signature verification in `ledger/src/shred.rs`, `ledger/src/shred/merkle.rs`, and `ledger/src/sigverify_shreds.rs` to `verify_strict` (as already used in `precompiles/src/ed25519.rs`), and dedup/cache shreds on a canonicalized `(pubkey, message)` pair or its hash rather than on raw signature bytes, so malleated encodings of an already-seen valid signature are recognized as duplicates instead of new signatures.

## Proof of Concept
1. Capture one legitimately signed shred `(header || S || payload)` from turbine.
2. Compute `S' = (S_int + k·L) mod 2^256` for small `k` while it remains 32 bytes, producing up to ~7 additional encodings that still satisfy `Signature::verify` (as demonstrated by the codebase's own `test_ed25519_malleability` in `precompiles/src/ed25519.rs`).
3. Replace the signature bytes with each `S'`, keeping slot/index/payload identical, and inject into the target validator's shred ingestion socket.
4. Observe each variant is a fresh miss in the sig-verify LRU cache (`ledger/src/sigverify_shreds.rs`) forcing repeated verification, and produces a distinct `get_common_header_bytes` hash in `ShredDeduper::dedup` (`turbine/src/retransmit_stage.rs`), consuming a slot in the bounded `MAX_DUPLICATE_COUNT` budget instead of being dropped as a duplicate.

    #[must_use]
    fn dedup(&self, key: ShredId, shred: &[u8], max_duplicate_count: usize) -> bool {
        // Shreds in the retransmit stage:
        //   * don't have repair nonce (repaired shreds are not retransmitted).
        //   * are already resigned by this node as the retransmitter.
        //   * have their leader's signature verified.
        // Therefore in order to dedup shreds, it suffices to compare:
        //    (signature, slot, shred-index, shred-type)
        // Because ShredCommonHeader already includes all of the above tuple,
        // the rest of the payload can be skipped.
        // In order to detect duplicate blocks across cluster, we retransmit
        // max_duplicate_count different shreds for each ShredId.
        shred::layout::get_common_header_bytes(shred)
            .map(|header| self.deduper.dedup(header))
            .unwrap_or(true)
            || (0..max_duplicate_count).all(|i| self.shred_id_filter.dedup(&(key, i)))
    }
