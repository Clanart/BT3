## Analog Found

### Title
Unbounded growth of `unacknowledged_asset_tokens` / `unacknowledged_asset_token_states` from unsolicited CAT coins — spend-triggered wallet DoS - (File: `chia/wallet/wallet_interested_store.py`)

### Summary
`CATWallet.identify()` unconditionally persists a database row for every previously-unseen CAT `asset_id` (and every coin state for it) sent to a wallet's puzzle hash, with no cap, whenever `automatically_add_unknown_cats` is `False` (the default). Unlike the analogous auto-creation paths for DID and NFT wallets, which were hardened with explicit `did_auto_add_limit` / `nft_auto_add_limit` caps, the "stray CAT" bookkeeping path has no equivalent bound.

### Finding Description
When a coin whose puzzle reveals a CAT layer is received and hinted to a wallet-owned puzzle hash, but the TAIL/`asset_id` is unrecognized and auto-add is disabled, `CATWallet.identify()` falls into the "unacknowledged" branch instead of creating a wallet: [1](#0-0) 

This calls `WalletInterestedStore.add_unacknowledged_token()` and `add_unacknowledged_coin_state()` unconditionally, once per distinct `asset_id` and once per distinct `coin_state`: [2](#0-1) 

The backing tables use `asset_id` and `coin_state` as primary keys with `INSERT OR IGNORE`, so there is no row-count limit, no eviction policy, and no rate limiting — every distinct fake CAT TAIL sent to the victim's puzzle hash produces a permanent new row.

This is in direct contrast to the DID and NFT auto-add paths in the same module family, which were patched specifically to prevent this class of bug: [3](#0-2) [4](#0-3) [5](#0-4) 

Minting a CAT with a unique TAIL (limitations program) is cheap: TAILs can be arbitrarily parameterized (e.g., curried with an incrementing index) so an attacker can generate unlimited distinct `asset_id`s at negligible on-chain cost, then create a dust CAT coin hinted to a target's puzzle hash for each one. This directly reaches `CATWallet.identify()` for any wallet that has `automatically_add_unknown_cats: False` (the default), which is the overwhelming majority of wallets.

### Impact Explanation
Each crafted CAT causes a durable SQLite row insert in the victim wallet's database with no bound. Sustained spam grows the wallet database unboundedly (disk exhaustion) and degrades wallet sync/coin-processing performance, since these inserts happen synchronously inside the wallet's coin-state processing path (under `WalletStateManager` locks) for every new coin received. This matches the "spend-triggered transaction-processing halt" impact class: a wallet's ability to process further incoming coin states degrades or stalls as the interested-store tables and I/O grow, mirroring the DNN registration-form DoS (unbounded resource consumption triggered by attacker-supplied data via a public-facing intake path — here, the wallet's puzzle-hash subscription/coin-sync intake).

### Likelihood Explanation
High reachability: no privileged access is required. Any party can mint low-value CATs with unique TAILs and send them, hinted, to any known wallet puzzle hash (e.g., harvested from an address, an offer counterparty exchange, or public transaction history). This requires no cooperation from the victim and no wallet RPC access — it is purely an on-chain spend that the victim's wallet will observe via normal SPV sync.

### Recommendation
Apply the same mitigation pattern already used for DID (`did_auto_add_limit`) and NFT (`nft_auto_add_limit`) auto-add paths: introduce a configurable cap (e.g., `unacknowledged_cat_limit`) on the number of distinct unacknowledged `asset_id`s (and/or coin states per asset id) tracked in `WalletInterestedStore`, and drop/ignore new unacknowledged entries once the cap is reached, logging a warning similar to the existing DID/NFT limit-reached messages.

### Proof of Concept
1. Attacker mints N CATs, each with a uniquely parameterized TAIL program (e.g., `(mod (idx) ...)` curried with a distinct `idx`), at minimal fee cost.
2. For each CAT, attacker performs an eve spend that creates a CAT coin hinted to the victim wallet's known puzzle hash.
3. Victim wallet (default config, `automatically_add_unknown_cats: False`) processes each coin via `CATWallet.identify()`, hitting the "Found unacknowledged CAT" branch and calling `add_unacknowledged_token` / `add_unacknowledged_coin_state` for each of the N distinct `asset_id`s — with no limit check, unlike the DID/NFT paths.
4. Repeating with large N causes unbounded growth of `unacknowledged_asset_tokens` and `unacknowledged_asset_token_states` tables in the victim's wallet SQLite database, degrading wallet coin-state processing over time.

    async def add_unacknowledged_token(
        self,
        asset_id: bytes32,
        name: str,
        first_seen_height: uint32 | None,
        sender_puzzle_hash: bytes32,
    ) -> None:
        """
        Add an unacknowledged CAT to the database. It will only be inserted once at the first time.
        :param asset_id: CAT asset ID
        :param name: Name of the CAT, for now it will be unknown until we integrate the CAT name service
        :param first_seen_height: The block height of the wallet received this CAT in the first time
        :param sender_puzzle_hash: The puzzle hash of the sender
        :return: None
        """
        async with self.db_wrapper.writer_maybe_transaction() as conn:
            cursor = await conn.execute(
                "INSERT OR IGNORE INTO unacknowledged_asset_tokens VALUES (?, ?, ?, ?)",
                (
                    asset_id.hex(),
                    name,
                    first_seen_height if first_seen_height is not None else 0,
                    sender_puzzle_hash.hex(),
                ),
            )
            await cursor.close()

    async def get_unacknowledged_tokens(self) -> list[dict[str, Any]]:
        """
        Get a list of all unacknowledged CATs
        :return: A json style list of unacknowledged CATs
        """
        async with self.db_wrapper.reader_no_transaction() as conn:
            cursor = await conn.execute(
                "SELECT asset_id, name, first_seen_height, sender_puzzle_hash FROM unacknowledged_asset_tokens"
            )
            cats = await cursor.fetchall()
        return [
            {"asset_id": cat[0], "name": cat[1], "first_seen_height": cat[2], "sender_puzzle_hash": cat[3]}
            for cat in cats
        ]

    async def add_unacknowledged_coin_state(
        self,
        asset_id: bytes32,
        coin_state: CoinState,
        fork_height: uint32 | None,
    ) -> None:
        """
        Add an unacknowledged coin state of a CAT to the database. It will be inserted into the retry store when the
        user decides to acknowledge the asset ID.
        :param asset_id: CAT asset ID
        :param coin_state: The state being ignored
        :param fork_height: The fork height when the state was sent
        :return: None
        """
        async with self.db_wrapper.writer_maybe_transaction() as conn:
            cursor = await conn.execute(
                "INSERT OR IGNORE INTO unacknowledged_asset_token_states VALUES(?, ?, ?)",
                (bytes(coin_state), asset_id, 0 if fork_height is None else fork_height),
            )
            await cursor.close()
