## Analysis

The GoGoPool bug's core invariant break is: **a value computed from one source of truth (`totalAssets()`) is used to authorize an action that is actually validated/executed against a different, more restrictive source of truth (`totalReleasedAssets`), and nothing keeps them in sync — so the "safe" value the caller was given turns out to be wrong when the real operation runs.**

The Desktop analog is the partial-commit line-selection pipeline, where the UI computes/holds a line-index-based selection against one diff snapshot, but the code that actually builds and applies the patch at commit time independently re-fetches a **fresh** diff and blindly reuses the old selection indices against it, with no reconciliation.

### Title
Stale line-index diff selection is replayed against a freshly re-fetched diff during partial commit, silently corrupting staged content - (File: app/src/lib/git/apply.ts)

### Summary
When a user stages only some lines/hunks of a file ("partial commit"), Desktop stores the selection as a set of line **indices** relative to the diff that was rendered in the UI. At commit time, `applyPatchToIndex` does not reuse that diff — it calls `getWorkingDirectoryDiff` again to get a brand-new diff of the file, and then feeds the *old* index-based selection into `formatPatch` against this *new* diff.

### Finding Description
`WorkingDirectoryFileChange.selection` (`DiffSelection`) only tracks selected line indices (`isSelected(lineIndex)`), it has no awareness of the actual line content it was computed against [1](#0-0) .

The commit flow passes these files, with their existing selection, straight into `createCommit` / `stageFiles` [2](#0-1) . `stageFiles` routes files with a partial selection to `applyPatchToIndex` [3](#0-2) .

Critically, `applyPatchToIndex` re-diffs the file from scratch right before building the patch: [4](#0-3) 

`formatPatch` then walks the hunks of *this newly fetched diff* and asks `file.selection.isSelected(absoluteIndex)` using indices that were only ever validated against the *previous* diff the user reviewed in the UI [5](#0-4) .

There is a partial safeguard elsewhere in the app: when the diff pane refreshes for the *currently displayed* file, `app-store.ts` recomputes `selectableLines` and drops selections that fell outside them [6](#0-5) . But this reconciliation:
- only fires for the single file currently shown in the Changes diff viewer, not for every file that is about to be committed,
- only runs on the render path, not immediately before `applyPatchToIndex`'s independent re-diff,
- does not compare *content* at each index, only whether an index is still "includeable" — so if lines shift but remain includeable, wrong lines can still be matched.

So there is a window between "user reviews a diff and picks lines" and "Desktop re-diffs the file and stages it" during which the working tree file can change (background build tool, formatter, linter, git hook, language server, file watcher, or any other process running in the context of a cloned/opened repository) without Desktop invalidating or reconciling the stale selection.

### Impact Explanation
If the file content shifts between the user's line selection and the commit action, `formatPatch` will apply the old line-index selection to different actual line content in the new diff, causing `git apply --cached` to either:
- silently stage/commit different content than what the user selected (silent corruption of what is committed), or
- fail with a patch-application error that gives the user no indication of *why* (poor diagnosability, since the failure mode is the same class described in the report: a value/selection computed from one state is applied against another with no correctness check).

This falls squarely in the "silent corruption of what the user commits or pushes" impact category — an attacker who controls a repository containing tooling that mutates tracked files as a side effect (build scripts, hooks, watchers) can cause a user's partial-commit selections to be applied against unintended content.

### Likelihood Explanation
Requires a naturally-occurring race: the tracked file must change between the user's UI-driven line selection and the (typically very close in time) commit click. This is plausible in repositories that run file-generation/formatting tooling triggered by editors, save actions, or git hooks bundled in the malicious repository — no local/physical access, admin rights, or social engineering step beyond normal repo cloning and using Desktop's standard partial-commit feature is required. It is a genuine, narrow timing window rather than a routinely-hit bug, similar in spirit to how the GoGoPool issue is "most prevalent" under specific conditions (low liquidity) rather than always triggered.

### Recommendation
- Before calling `applyPatchToIndex`, re-validate (or re-derive) `file.selection` against a diff freshly computed at that exact moment, comparing actual line *content* (not just index existence) to the diff the user last reviewed, similar to the reconciliation already done in `app-store.ts` for the active diff pane.
- If the newly-fetched diff in `apply.ts` differs from the diff the selection was computed against (e.g., compare hunk headers/line hashes), abort the partial commit for that file and surface an explicit "the file changed since your selection was made, please review again" error instead of silently applying a possibly mismatched patch.

### Proof of Concept
1. Attacker publishes a repository containing a git `post-checkout`/editor-integration/build-watch script that, once running, periodically appends/removes lines from a tracked file (e.g. simulating a formatter or code generator).
2. Victim clones the repo in GitHub Desktop, modifies the file, opens the Changes diff, and selects only specific lines/hunks to include in a commit (leaving others unstaged), per the flow tested in [7](#0-6) .
3. Before the victim clicks "Commit", the background script mutates the same file's tracked lines (adds/removes lines, shifting indices).
4. Victim clicks "Commit". `_commitIncludedChanges` passes the file (with the old, now-stale, `DiffSelection`) to `createCommit` → `stageFiles` → `applyPatchToIndex`, which re-diffs the file [8](#0-7)  and applies the old index-selection to the new hunks via `formatPatch` [9](#0-8) .
5. The resulting commit contains content that does not match what the user actually selected in the UI (or `git apply` fails unexpectedly), with no warning shown to the user that the underlying diff changed since their selection.
