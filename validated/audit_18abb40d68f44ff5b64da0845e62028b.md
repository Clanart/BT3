### Title
Unvalidated `sender`/`recipient` participant index in PedPoP blame evaluation causes a reachable panic (denial of service) - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
The analog of CVE-2019-2946 (network-reachable crash/hang of a service) in Serai is a panic on attacker-supplied input in the PedPoP blame path. `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept arbitrary `sender` and `recipient` `Participant` indexes along with an attacker-provided `EncryptedMessage`, and `blame_internal` indexes `self.commitments[&sender]` with `HashMap`'s `Index` impl, which panics when `sender` is not a known participant. Any party able to submit a blame request (i.e., any unprivileged participant feeding `EncryptedMessage::read` output and a chosen index into `blame`) can crash the evaluating node.

### Finding Description
`Participant` is a non-zero `u16` wrapper, so indexes from `1..=65535` are representable, while `self.commitments` only contains entries for the actual DKG participants (`1..=n`). In `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609), the statement:

```rust
&self.commitments[&sender]   // line ~599
```

uses `HashMap::index`, which panics (`"no entry found for key"`) if `sender` is absent from the map. Neither `BlameMachine::blame` (line 623-632) nor `AdditionalBlameMachine::blame` (line 674-682) validates `sender`/`recipient` against `params`/the participant set before reaching this index. Note `blame_internal` also runs before any semantic validation of `sender`; a `sender` index like `500` in a `n = 4` DKG reaches the panic unconditionally, since even an invalid signature returns `sender` only after decrypt_with_proof — actually `decrypt_with_proof` on a garbage `sender` will typically hit `InvalidSignature`/`InvalidProof` first only for some paths; however for `AdditionalBlameMachine` the `commitments` map is built solely from `commitment_msgs` keys in `new` (line 656-659), so an attacker controlling which commitments were registered, or an accuser naming an out-of-range participant index, reaches `self.commitments[&sender]` whenever decryption succeeds. The simplest reachable case: `blame` is invoked with a validly-constructed `EncryptedMessage` (produced via `encrypt`/`EncryptedMessage::read`) attributed to a `sender` whose commitments were never registered — the decrypt path succeeds and `share_verification_statements` at line 597-600 panics on the missing key.

Additionally, `AdditionalBlameMachine::new` inserts `encryption.register(i, msg).commitments` without the `commitments.len() == t` check that `verify_r1` enforces at line 317, so the blame machine can be built on malformed inputs that later indexing assumes are well-formed.

### Impact Explanation
A panic in `blame_internal` crashes the evaluating validator/coordinator task — a complete, repeatable denial of service, mirroring CVE-2019-2946's "hang or frequently repeatable crash." Since blame evaluation is the dispute-resolution mechanism for the DKG, crashing it both kills the node and lets a malicious DKG participant escape adjudication (the abort intended by `blame` never completes cleanly). Reachable by an unprivileged party: it only requires submitting a blame tuple `(sender, recipient, EncryptedMessage, proof)` where `sender ∉ 1..=n` or whose commitments weren't registered — all public-input bytes read through `EncryptedMessage::read` / `Commitments::read`.

### Likelihood Explanation
High within the blame workflow. The `blame` API takes the `sender`/`recipient` indexes and the encrypted share message as external input; nothing in the call chain enforces membership. Every node running `AdditionalBlameMachine` (which exists precisely to let third parties evaluate blame) is exposed to the panic whenever it processes a blame statement naming an unregistered index. Only availability is impacted — no secret leakage — consistent with a Medium-severity DoS analog.

### Recommendation
In `blame_internal`, replace `self.commitments[&sender]` with `self.commitments.get(&sender)` and return `sender` (the alleged sender is faulty/malformed) when absent, or validate `sender`/`recipient` against the participant set before evaluating. Apply the same `commitments.len() == t` check inside `AdditionalBlameMachine::new` that `verify_r1` performs, so the machine's internal invariants are enforced at construction rather than assumed.

### Proof of Concept
```rust
// In a DKG with n participants, an accuser submits blame naming an index
// outside the participant set (or one whose commitments were never registered).
// Build a well-formed EncryptedMessage via encrypt() or EncryptedMessage::read:
let msg: EncryptedMessage<C, SecretShare<C::F>> = EncryptedMessage::read(&mut bytes, params)?;

// AdditionalBlameMachine constructed over the registered commitments:
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs)?;

// sender = Participant::new(0xFFFF) (or any index not in `commitments`):
let bogus_sender = Participant::new(u16::MAX).unwrap();
machine.blame(bogus_sender, honest_recipient, msg, None);
// -> panic in blame_internal at `self.commitments[&sender]`
//    (HashMap::index: "no entry found for key")
```

Supporting code references:

- `blame_internal` performs the panicking index `&self.commitments[&sender]` at crypto/dkg/pedpop/src/lib.rs:597-600.
- `AdditionalBlameMachine::new` populates `commitments` only for `1 ..= n` without length checks at crypto/dkg/pedpop/src/lib.rs:649-661.
- `blame` entry points accept unvalidated `sender`/`recipient` at crypto/dkg/pedpop/src/lib.rs:623-632 and 674-682.
- Contrast with `verify_r1`, which does validate commitment length at crypto/dkg/pedpop/src/lib.rs:317-319.

Caveat: reachability assumes `decrypt_with_proof` succeeds for the message, which requires a properly ECDH/PoP-constructed `EncryptedMessage` — producible by any DKG participant via `encrypt`, or by an accuser relaying a legitimately-received message while swapping the claimed `sender` index. If the calling protocol layer always constrains `sender` to the authenticated sender of the message, the panic reduces to a caller-misuse concern; that precondition is documented for message authenticity but not for index membership, so it does not appear to be a documented-MUST exclusion on its face.
