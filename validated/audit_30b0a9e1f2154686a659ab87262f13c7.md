### Title
Callback controller's phishing check uses a different URL parser than `sanitize_shop_domain`, allowing a parser-differential bypass of the OAuth `host` validation - (File: app/controllers/shopify_app/callback_controller.rb)

### Summary
`RubiconRouter.swapEntireBalance()` passed a *derived* value into a check instead of the value that was actually validated/used downstream, so the enforced check didn't match the real operation and the guard was effectively bypassed. `CallbackController#deduced_phishing_attack?` has the same class of bug: it validates a *re-derived* host (extracted via Ruby's stdlib `URI` parser) while the value actually used for the redirect (`decoded_host`, the raw string returned by `ShopifyAPI::Auth.embedded_app_url(params[:host])`) is different and parsed differently by `Addressable::URI` inside `sanitize_shop_domain`.

### Finding Description
In the OAuth callback flow, after a successful callback the app redirects back into the embedded app: [1](#0-0) 

`decoded_host` is the actual string used to build the redirect target (`"#{decoded_host}#{return_to}"`), while `deduced_phishing_attack?` only validates `URI(decoded_host).host` — parsed with Ruby's stdlib `URI`, not `Addressable::URI`: [2](#0-1) 

`sanitize_shop_domain` internally re-parses whatever host string it receives with `Addressable::URI`: [3](#0-2) 

By contrast, `ShopifyApp::EmbeddedApp#safe_embedded_app_url` — which performs the analogous check for the `redirect_to_embed_app_in_admin` flow — was hardened (per CHANGELOG "Harden embedded app host validation to prevent parser-differential open redirects", PR #2078) to reject control characters, backslashes, and userinfo (`@`) in the *raw* decoded host string before ever handing it to `sanitize_shop_domain`: [4](#0-3) 

`CallbackController#deduced_phishing_attack?` was not updated with this same hardening — it still relies solely on Ruby's `URI(...).host` extraction followed by `sanitize_shop_domain`, with no rejection of backslashes, userinfo, or control characters in the raw `decoded_host` string that is actually used to build the redirect. If Ruby's `URI` and `Addressable::URI` disagree on host-boundary parsing for a crafted string (e.g., containing backslashes, unusual whitespace, or other characters treated differently by the two parsers), an attacker can construct a `host` param whose `URI(decoded_host).host` component looks like a trusted `*.myshopify.com`/`*.shopify.com` domain (passing `sanitize_shop_domain`) while the actual `decoded_host` string used in the subsequent `redirect_to(redirect_to, allow_other_host: true)` points to an attacker-controlled origin.

### Impact Explanation
`redirect_to_app` is called at the end of every successful OAuth callback and uses `allow_other_host: true`, explicitly disabling Rails' own open-redirect protection and relying entirely on `deduced_phishing_attack?` for safety. If the parser differential can be exploited, an unauthenticated or unrelated party inducing a merchant to complete OAuth with a crafted `host` value could redirect the merchant's browser (carrying the freshly-issued session cookie flow) to an attacker-controlled domain immediately after authentication — a classic OAuth-callback open redirect, which can be leveraged for credential/token phishing in the context of a real Shopify authentication event.

### Likelihood Explanation
Exploitation depends on finding a concrete input string on which Ruby's `URI.parse` and `Addressable::URI.parse` disagree about the host component in a security-relevant way (e.g., an input rejected/host-differing between the two on backslashes, unicode, or malformed percent-encoding) — the same underlying weakness that PR #2078 was created to fix in `embedded_app.rb`. Since that hardening was not mirrored in `callback_controller.rb`, there is a reachable, unauthenticated-adjacent path (a merchant completing an OAuth flow with an attacker-supplied `host` query param) where this discrepancy can be probed and, if a differential input exists, weaponized. I could not directly prove a concrete input that both encodes as a Ruby-`URI`-valid `*.myshopify.com` host and as a distinct `Addressable::URI` host without further testing/fuzzing the two parsers — this is the main open uncertainty.

### Recommendation
Apply the same hardening used in `ShopifyApp::EmbeddedApp#safe_embedded_app_url`/`unsafe_embedded_host?` to `CallbackController#deduced_phishing_attack?`: validate the raw decoded host string (rejecting control characters, backslashes, and userinfo) using a single, consistent parser before calling `sanitize_shop_domain`, and ensure the value that is checked is exactly the value used to build the redirect target (`decoded_host`), not a separately re-parsed derivative.

### Proof of Concept
Not fully demonstrated — a concrete crafted `host` parameter causing Ruby `URI` and `Addressable::URI` to disagree on the host component was not verified in this analysis. The logical PoC path is:
1. Attacker crafts a base64 `host` param whose decoded value, when passed through `URI(decoded_host).host`, extracts a string ending in a trusted domain (e.g. `foo.myshopify.com`), causing `sanitize_shop_domain` to return non-nil.
2. The full `decoded_host` string (used verbatim in `redirect_to_app`) actually points `Addressable::URI`/browsers to a different, attacker-controlled host due to parser disagreement (e.g. via backslash-based authority confusion, similar to what `unsafe_embedded_host_characters?` in `embedded_app.rb` was added to block).
3. Merchant completes OAuth via `/callback` with this `host` param; `deduced_phishing_attack?` returns `false`, and the app issues `redirect_to(decoded_host + return_to, allow_other_host: true)` to the attacker's domain.

      def sanitize_shop_domain(shop_domain)
        uri = uri_from_shop_domain(shop_domain)
        return if uri.nil? || uri.host.nil?

        trusted_domains.each do |trusted_domain|
          no_shop_name_in_subdomain = uri.host == trusted_domain
          from_trusted_domain = trusted_domain == uri.domain

          return myshopify_domain_from_unified_admin(uri) if unified_admin?(uri) && from_trusted_domain
          return nil if no_shop_name_in_subdomain || uri.host&.empty?
          return uri.host if from_trusted_domain
        end
        nil
      end

    def safe_embedded_app_url(host)
      decoded_host = Base64.decode64(host.to_s)
      return if deduced_phishing_attack?(decoded_host)

      ShopifyAPI::Auth.embedded_app_url(Base64.strict_encode64(decoded_host))
    end

    def deduced_phishing_attack?(decoded_host)
      sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(decoded_host) unless unsafe_embedded_host?(decoded_host)
      if sanitized_host.nil?
        message = "Host param for redirect to embed app in admin is not from a trusted domain, " \
          "redirecting to root as this is likely a phishing attack."
        ShopifyApp::Logger.info(message)
      end
      sanitized_host.nil?
    end

    def unsafe_embedded_host?(decoded_host)
      return true if decoded_host.empty? || !decoded_host.valid_encoding?
      return true if unsafe_embedded_host_characters?(decoded_host)

      embedded_host_authority(decoded_host).include?("@")
    end

    def unsafe_embedded_host_characters?(decoded_host)
      decoded_host.each_char.any? do |character|
        character_code = character.ord
        character_code <= 0x20 || character_code == 0x7f || character == "\\"
      end
    end

    def embedded_host_authority(decoded_host)
      decoded_host.sub(%r{\Ahttps?://}i, "").split(%r{[/?#]}, 2).first.to_s
    end
