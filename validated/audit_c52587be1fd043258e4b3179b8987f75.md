### Title
Division-by-zero panic in `consolidatedNode.Split` during Prague/Flex staking reward distribution - (File: kaiax/staking/staking_info.go)

### Summary
The external report concerns unguarded division in Cosmos-SDK share-conversion math that panics when the denominator is zero. The structurally closest reachable analog in this Go/Kaia codebase is `consolidatedNode.Split` in [1](#0-0) , which divides by `totalAmount = cnAmountBig + clAmountBig` without checking whether that sum is zero, and is invoked from the consensus-critical block-reward distribution path.

### Finding Description
`Split` computes each consolidated node's CN/CL portion of a staking reward: [1](#0-0) 

It is called from `assignStakingRewardsFlex` and `assignStakingRewards` in the reward module whenever `isPrague && cn.CLStakingInfo != nil`: [2](#0-1) [3](#0-2) 

Both call sites gate entry on `cn.StakingAmount >= config.MinimumStake` (or `> minStake`), which normally guarantees `cnAmountBig > 0`. However, `MinimumStake` is a governance-configurable parameter (`reward.minstake`), and `StakingAmount`/`CLStakingAmount` are truncated `uint64` KAIA amounts derived from on-chain staking balances by integer division by `params.KAIA` (1e18 kei): [4](#0-3) [5](#0-4) 

If `MinimumStake` is configured to `0` (a valid, non-negative integer governance parameter), a validator whose CN staking amount truncates to `0` KAIA can still pass the `>= minStake` filter. If that same validator's consensus-liquidity (CL) pool also currently holds a truncated stake of `0` KAIA (e.g., all CL depositors withdrew, or the pool has sub-1-KAIA balance), then `cnAmountBig == 0` and `clAmountBig == 0`, making `totalAmount == 0`. The subsequent `clAmount.Div(clAmount, totalAmount)` is a `big.Int` division by zero, which panics in Go (unlike Cosmos SDK's `Dec.Quo`, which also panics, but here there is no upstream recovery in block finalization).

### Impact Explanation
This code path executes inside deferred reward distribution during `FinalizeState`, which runs identically on every full/consensus node processing the block. A panic here is not merely a single transaction revert — it is invoked as part of state-transition/block finalization for *every* node, so triggering it would crash block processing network-wide, a denial-of-service on the whole chain rather than a single request. This matches the reachable-surface categories of "staking and reward distribution" and "governance parameters" called out in scope.

### Likelihood Explanation
Likelihood is constrained: it requires `reward.minstake == 0`, a specific but permitted governance configuration, combined with a CN whose staking amount and CL pool amount both round down to zero KAIA under Prague hardfork rules. This is a narrower precondition than the original Cosmos bug (which triggered on the much more common "shares exist, net assets are zero" state), and I could not fully verify from the indexed code whether `MinimumStake == 0` is disallowed elsewhere by parameter validation logic (e.g., in `kaiax/gov/paramset.go`/`param.go`), since those files were not retrievable in enough detail during this session. This uncertainty should be resolved before treating this as confirmed-exploitable; if `MinimumStake` cannot practically be zero, the likelihood drops substantially.

### Recommendation
Add an explicit zero-check in `consolidatedNode.Split` before dividing, mirroring the report's suggested fix pattern (e.g., `GetNetAmountState`'s guarded `MintRate`): if `totalAmount.Sign() == 0`, return `(amount, big.NewInt(0))` or another well-defined default instead of dividing. Additionally, confirm/enforce via governance parameter validation that `MinimumStake` cannot be set to a value that allows zero-stake CNs to be reward-eligible, or explicitly special-case zero-stake nodes before they reach `Split`.

### Proof of Concept
Conceptual (unverified end-to-end due to missing access to governance parameter validation code):
1. Governance sets `reward.minstake = 0` via a valid governance transaction/vote.
2. A validator node registers in the AddressBook with `CNStaking` balance `< 1 KAIA` (truncates to `StakingAmount = 0`), and its associated CL pool (`CLRegistry`) currently holds `< 1 KAIA` (truncates to `CLStakingAmount = 0`), e.g., right after all CL depositors have withdrawn.
3. On a block after Prague activation, `assignStakingRewards`/`assignStakingRewardsFlex` includes this CN (since `0 >= 0`), and because `CLStakingInfo != nil`, calls `cn.Split(reward)`.
4. Inside `Split`, `totalAmount = 0 + 0 = 0`; `clAmount.Div(clAmount, totalAmount)` panics with "division by zero", crashing block finalization on all nodes processing that block.

Note: I was unable to fully confirm whether governance parameter validation (`kaiax/gov/paramset.go`, `param.go`) rejects `MinimumStake = 0`, due to depth-of-search limits in this session — this should be verified directly in the repository (or via a Devin session with full file access) before treating this finding as fully confirmed.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
