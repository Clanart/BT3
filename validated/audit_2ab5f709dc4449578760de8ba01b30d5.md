Unverified-PoP blame path leaks the ECDH key, enabling plaintext recovery of an honest participant's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each incoming `EncryptedMessage` and, when the decrypted bytes fail `C::F::from_repr`, immediately returns `PedPoPError::InvalidShare { blame: Some(blame) }` containing an `EncryptionKeyProof` — which embeds the ECDH shared key `key = enc_key * msg.key` and a DLEq proving its correctness. The message's Schnorr proof-of-possession is only queued into the `BatchVerifier` and never verified on this path, because `batch.verify_with_vartime_blame()` is unreachable after the early `?`. This reintroduces the exact attack the PoP was added to prevent: an attacker who reuses an observed per-message key `X` in a forged message induces the recipient to publish `bX`, which decrypts the honest sender's original ciphertext. This mirrors the bug class of ALPINE-CVE-2018-19608 — an oracle (here the blame proof, there RSA decryption behavior) that lets an unprivileged party recover a plaintext they were never meant to see.

### Finding Description
The `EncryptedMessage` docs explicitly describe the threat: if Eve observes Alice encrypt to Bob with key `X`, Eve can send Bob a message also claiming key `X`; Bob's blame would reveal `bX`, leaking Alice's message. The `pop` field exists solely to stop this [1](#0-0) . However, the PoP is only enforced inside `batch.verify_with_vartime_blame()` in `calculate_share` [2](#0-1) . Before that, `Encryption::decrypt` merely queues `msg.pop.batch_verify(...)` and unconditionally computes `key = ecdh(&self.enc_key, msg.key)`, returns the decrypted bytes plus an `EncryptionKeyProof { key, dleq }` [3](#0-2) . If `C::F::from_repr(share_bytes.0)` fails, the function returns `InvalidShare { participant: l, blame: Some(blame) }` at once [4](#0-3) . The blame proof — containing `key` (the raw ECDH point) and a valid DLEq — is then serialized into `ProcessorMessage::InvalidShare` and broadcast [5](#0-4) . Anyone can then run `cipher(context, key)` and decrypt Alice's original `EncryptedMessage` to Bob [6](#0-5) .

The attacker needs the forged ciphertext to decrypt (under the unknown-to-them `bX`) to a non-canonical scalar. Since the share field is a fixed-length repr and the field modulus is far below `2^256` (e.g. Ristretto/ed25519 `l ≈ 2^252`), a garbage ciphertext yields a non-canonical scalar with overwhelming probability (~15/16), and the attacker can retry across DKG attempts. Because the cipher is unauthenticated ChaCha20 and the PoP covers the ciphertext, the attacker cannot forge the PoP — but the PoP is never checked before the leak.

### Impact Explanation
Plaintext recovery of a threshold secret share addressed to an honest participant. Revealing `bX` decrypts the original honest `EncryptedMessage` carrying `SecretShare` — the share `f_alice(bob)` of Alice's Pedersen polynomial. Combined with other compromised or public information (or repeated across victims), this degrades the DKG's confidentiality guarantees that the encryption layer exists to provide; leaked shares can enable key-share reconstruction attacks depending on how many are harvested. The blame channel is a reliable oracle: one garbage message per session suffices with high probability.

### Likelihood Explanation
Requires the attacker to be a DKG participant able to send a `CoordinatorMessage::Shares`-routed `EncryptedMessage` to a victim and to have observed an honest `EncryptedMessage` ciphertext using ephemeral key `X` (messages are sent over authenticated channels but are visible to routing/coordination infrastructure and to any party that sees the blame/broadcast traffic). No collusion, no leaked keys, no unsafe code — purely public-input manipulation of `msg.key` and `msg.msg`. Medium severity: oracle-based plaintext recovery requiring protocol participation and message observation, matching the CVSS 4.7 local/high-complexity profile of the reference advisory.

### Recommendation
Verify the PoP *before* releasing any `EncryptionKeyProof`. Concretely, in `KeyMachine::calculate_share`, do not emit `blame: Some(blame)` for a scalar-decode failure until the message's PoP has been verified — e.g., perform a standalone `msg.pop.verify(...)` inside `Encryption::decrypt` before computing/returning the ECDH key, or restructure so that decryption-key revelation is deferred until after `batch.verify_with_vartime_blame()` confirms the `BatchId::Decryption(l)` statement. A message failing its PoP must yield `blame: None` (as the `BatchId::Decryption` arm already does) regardless of what its ciphertext decodes to. The same ordering concern applies to `AdditionalBlameMachine`/`blame_internal` callers relying on `decrypt_with_proof`, which correctly verifies `msg.pop` first [7](#0-6)  — `calculate_share` should match that ordering.

### Proof of Concept
1. Observe an honest `EncryptedMessage` from Alice to Bob with ephemeral public key `X` and ciphertext `ct` (e.g., from relayed/broadcast DKG traffic).
2. As DKG participant Eve, send Bob `EncryptedMessage { key: X, pop: <any bytes>, msg: <garbage> }` in place of Eve's real share.
3. Bob's `calculate_share` calls `encryption.decrypt`, computing `key = bX`, applies `cipher(context, bX)` to the garbage, and `C::F::from_repr` fails (~15/16 chance per attempt for Ristretto; retry across attempts otherwise).
4. Bob returns/broadcasts `InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key: bX, dleq }) }`.
5. Eve takes `key = bX`, runs `cipher(context, bX).apply_keystream(ct)` and recovers Alice's secret share to Bob — plaintext obtained without Alice's or Bob's private keys, despite never producing a valid PoP for `X`.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
