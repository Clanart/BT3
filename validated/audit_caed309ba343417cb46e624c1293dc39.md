### Title
`ThresholdKeys::new`/`ThresholdKeys::read` never binds the secret share to the verification shares, deriving `group_key` solely from participants `1..=t` — unauthenticated key substitution on deserialized keys - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
CVE-2017-3167 is the class "a helper is used outside the phase in which the peer was authenticated, so authentication requirements are bypassed." The Serai analog lives in `crypto/dkg`: `ThresholdKeys` is the product of the PedPoP DKG, where every participant's share is verified against their verification share (`share_verification_statements`). The public constructor `ThresholdKeys::new` and the deserializer `ThresholdKeys::read` assume that verification happened, but never check it — exactly like calling `ap_get_basic_auth_pw()` outside the authentication phase. Worse, `group_key` is computed by interpolating only `verification_shares[1..=t]`; the caller's own `secret_share` and the shares for participants `t+1..=n` are never validated against anything.

### Finding Description
In `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`), the only checks are:

- `verification_shares.len() == n` and all keys `<= n` (lines 355-365),
- `Constant` interpolation requires `t == n` (lines 367-374),
- `group_key` is computed as the interpolation of `verification_shares[1]` … `verification_shares[t]` (lines 376-378).

There is no check that `C::generator() * secret_share == verification_shares[params.i()]` — the share↔verification-share binding that PedPoP enforces during DKG is skipped. `ThresholdKeys::read` (lines 574-632) reconstructs `t, n, i`, the interpolation coefficients, the secret share, and all `n` verification shares from raw bytes and funnels them straight into `ThresholdKeys::new`, so this unauthenticated path is directly reachable from untrusted bytes (`ThresholdKeys::read` is an in-scope untrusted-input API).

Because `group_key` only depends on `verification_shares[1..=t]`, an attacker supplying the byte stream can:

1. Choose any polynomial/verification shares — hence a fully attacker-known group key.
2. Claim any `i` and any `secret_share`, consistent or not.

The resulting `ThresholdKeys` passes all invariants: `view()`, `sign()`, `serialize()`, and `group_key()` all operate normally. The codebase itself acknowledges this hole: `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:491-494`) comments that reaching `InternalError` is possible "to deserialize a semantically invalid FrostKeys" — i.e., the deserialization layer produces keys with no semantic binding between the secret share, the verification shares, and the group key.

### Impact Explanation
An attacker who can feed bytes to `ThresholdKeys::read` (a key store, a config file, a network-synced key blob — any path where serialized keys are not additionally authenticated) performs a silent key substitution:

- **Attacker-controlled group key**: since `group_key` is whatever the interpolated `verification_shares[1..=t]` sum to, the attacker can set it to a key whose discrete logarithm they know. Any consumer that derives an identity, address, or scanner target from `keys.group_key()` (e.g., the bitcoin wallet deriving Taproot outputs from the threshold group key) now operates under the attacker's key — funds routed to it are spendable by the attacker, not the honest set.
- **Inconsistent self-share**: a blob with a `secret_share` unrelated to `verification_shares[i]` produces a view whose shares can never aggregate — a persistent integrity failure only detected as the generic `InternalError`, with the wrong participants potentially blamed.

Either way, the security requirement "this ThresholdKeys is the output of an authenticated DKG" is bypassed because the binding check lives only in the DKG verification phase and is never re-established at construction/deserialization time.

### Likelihood Explanation
Reachability is high wherever serialized `ThresholdKeys` cross a trust boundary (backup/restore, key sync between nodes, rehydration from disk). No collusion, no threshold compromise, and no privileged position is needed — only control of the bytes. Exploitation against FROST signing is dampened because `complete` verifies the aggregate signature against `group_key`, so an inconsistent *self-share alone* only yields `InternalError`; the meaningful exploit is the substitution of the entire keyset (group key + shares), which yields fully valid signatures under the attacker's key. Severity: Medium–High depending on whether the deployment authenticates stored key material out-of-band (the crate does not).

### Recommendation
In `ThresholdKeys::new` (and therefore transitively in `read`), enforce the same invariant the DKG phase enforces:

- Verify `C::generator() * secret_share == verification_shares[&params.i()]`, rejecting otherwise.
- Optionally, verify all `n` verification shares lie on a common degree-`t-1` polynomial (check the interpolation of any `t`-subset against the remaining shares) so that shares `t+1..=n` cannot be garbage while `group_key` looks consistent.

This restores the "authentication" at the point of use rather than assuming a prior phase performed it.

### Proof of Concept
The inconsistency is directly demonstrable with the public API — construct keys whose secret share does not match the claimed verification share, and whose group key is fully attacker-chosen:

```rust
// Rust, using the in-scope dkg + ciphersuite crates (e.g. C = a dalek ciphersuite).
use std::collections::HashMap;
use dkg::{ThresholdParams, ThresholdKeys, Interpolation, Participant};
use ciphersuite::Ciphersuite;
use zeroize::Zeroizing;
use rand_core::OsRng;
use ff::Field;
use group::Group;

// Attacker picks an arbitrary secret they fully know, e.g. s, and crafts
// verification shares for a degree-(t-1) polynomial with constant term s.
// t = 2, n = 3, attacker claims to be participant 1.
let t = 2u16; let n = 3u16;
let i = Participant::new(1).unwrap();

// Verification shares for x = 1, 2: v(x) = s + a*x  (a arbitrary, attacker-known)
let s = C::F::random(&mut OsRng);
let a = C::F::random(&mut OsRng);
let mut shares = HashMap::new();
for x in 1u16..=n {
    let v = s + a * C::F::from(u64::from(x));
    shares.insert(Participant::new(x).unwrap(), C::generator() * v);
}

// A secret_share completely unrelated to verification_shares[1]:
let bogus_share = Zeroizing::new(C::F::random(&mut OsRng));
assert!(C::generator() * *bogus_share != shares[&i]); // inconsistent

// ThresholdKeys::new accepts it without any binding check:
let keys = ThresholdKeys::<C>::new(
    ThresholdParams::new(t, n, i).unwrap(),
    Interpolation::Lagrange,
    bogus_share,
    shares,
).expect("inconsistent keys accepted");

// group_key == G*s — a key the attacker knows the discrete log of:
assert_eq!(keys.group_key(), C::generator() * s);
```

Equivalent bytes fed through `ThresholdKeys::read` (curve ID, `t`, `n`, `i`, interpolation tag `1`, the bogus share, then the three attacker-chosen verification-share encodings) produce the identical accepted object, showing the unauthenticated deserialization path reaches the same state.
