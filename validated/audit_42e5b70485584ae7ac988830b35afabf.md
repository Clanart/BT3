## Analog Found

### Title
Value sent to the Distribution precompile's `rewards()` view method is permanently stranded - ([File: precompiles/distribution/distribution.go])

### Summary
The `rewards()` method of the Distribution precompile (deployed at the fixed EVM address `0x0000000000000000000000000000000000001007`) is the only "view" method in the precompile that is not gated by `pcommon.ValidateNonPayable`. Any caller who attaches a nonzero `value` to a `rewards()` call will have that value debited from their EVM balance and credited to the precompile's associated account by the EVM's native value-transfer mechanics, but the Go handler never invokes `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` (which is how every payable precompile method refunds/redirects attached value) to refund or otherwise process it. There is no code path anywhere in the precompile to reclaim that value, mirroring the reported UXDController issue where ETH sent to a `receive()` fallback has no corresponding withdrawal function.

### Finding Description
The dispatch table in `Execute` shows every transaction-like/payable method is validated with either an explicit `readOnly` check plus fund-consuming logic (`setWithdrawAddress`, `withdrawDelegationRewards*`, `withdrawValidatorCommission`, etc.), or with `pcommon.ValidateNonPayable(value)` for pure query methods (e.g. `ParamsMethod`, `ValidatorOutstandingRewardsMethod`, etc. all route through `p.params(...)`/`p.validatorOutstandingRewards(...)` which call `ValidateNonPayable`). `RewardsMethod`, however, dispatches straight to `p.rewards(ctx, method, args)` with no `value` argument passed and no non-payable guard applied before dispatch: [1](#0-0) 

This is called out explicitly in the integration test suite's own documentation comment, which states the tests deliberately skip asserting rejection of value-bearing calls to `rewards()` because such a call would "succeed and strand the funds": [2](#0-1) 

Every other value-consuming precompile method in this codebase funnels the attached `value` through `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei`, which debits the precompile account and credits the payer back (or forwards funds into an actual staking/bank operation): [3](#0-2) 

Since `rewards()` performs neither the non-payable rejection nor the payment-handling refund, any wei attached to a `rewards()` call is simply absorbed by the precompile's underlying account balance with no method exposed anywhere in the ABI to retrieve it — functionally identical to `UXDController`'s `receive()` fallback accepting ETH with no withdraw function.

### Impact Explanation
Any unprivileged EVM caller (EOA or contract) invoking the distribution precompile's `rewards(...)` function with a nonzero `msg.value` permanently loses that value: it is debited from the caller and left unrecoverable in the precompile's account, since there is no withdrawal or refund mechanism for it. This is a concrete, permanent loss of user funds reachable from a single submitted EVM transaction/contract call to a public precompile — no privileged access required.

### Likelihood Explanation
Trivial to trigger: the caller only needs to send any EVM transaction that calls `rewards(...)` on `0x...1007` with `value > 0`. This can happen accidentally (e.g., a wallet/contract that always attaches value optimistically) or be intentionally exploited to grief users, and is explicitly acknowledged as a known gap by the test suite's own comments.

### Recommendation
Add `if err := pcommon.ValidateNonPayable(value); err != nil { return nil, 0, err }` before dispatching to `RewardsMethod` in `Execute`, consistent with the other pure-query methods (`ParamsMethod`, `ValidatorOutstandingRewardsMethod`, etc.), so that value-bearing calls to `rewards()` revert instead of silently stranding funds.

### Proof of Concept
1. From an EOA/contract with EVM balance, call the Distribution precompile at `0x0000000000000000000000000000000000001007` with method selector for `rewards(string,string)` (or whichever signature is used) and attach `value = 1 ether` (in wei) in the call.
2. Because `Execute`'s `RewardsMethod` branch performs no `ValidateNonPayable` check and calls `p.rewards(ctx, method, args)` without processing `value`, the EVM's native call semantics transfer the wei to the precompile's account as part of executing the CALL, while the Go handler only returns query data.
3. The `value` sent is now held by the precompile's account with no exposed method (withdraw/refund) to return it to the caller — permanently lost. [4](#0-3)

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
}
