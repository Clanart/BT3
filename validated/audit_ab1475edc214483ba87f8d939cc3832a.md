## Title
Trampoline authentication token (`DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`) leaks into native Git child processes (hooks/filters) spawned outside the sanitized hooks-proxy path, allowing credential exfiltration - (File: `app/src/lib/git/core.ts`, `app/src/lib/trampoline/trampoline-environment.ts`, `app/src/lib/hooks/with-hooks-env.ts`)

### Summary
The Putty bug is fundamentally about an attacker's code running *mid-operation*, inside a still-trusted execution context, gaining access to assets/state that should only be reachable after all guards have completed. In GitHub Desktop, the analogous trusted context is the trampoline mechanism: every `git` invocation is wrapped with `withTrampolineEnv`, which injects `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` into the process environment so that Git can call back into Desktop (via a local TCP server) for askpass/credential-helper requests [1](#0-0) . Desktop only strips these secrets from the *hook* execution environment when a git command explicitly opts into `interceptHooks` (commit, merge, pull, push) — the hook is then re-spawned by `hooks-proxy.ts` with an allow-listed `GIT_*`/`GITHEAD_*` env (`safeEnv`), explicitly excluding `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` [2](#0-1) [3](#0-2) . Git operations that don't set `interceptHooks` (e.g. checkout) never route hook/filter execution through this sanitizing proxy at all, so any native child process Git spawns (hooks, `clean`/`smudge` filters, diff/merge drivers) inherits the *unfiltered* environment straight from `core.ts`'s `exec()` call, including the live trampoline token and port.

### Finding Description
`core.ts`'s `git()` composes two nested environment layers before calling `exec`: `withHooksEnv` (only active when `interceptHooks` is passed) and `withTrampolineEnv`, which always injects `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, `GIT_ASKPASS=''`, and `GIT_CONFIG_PARAMETERS` pointing `credential.helper` at Desktop [4](#0-3) [5](#0-4) .

The only place these secrets are stripped before reaching a Git-spawned subprocess is `hooks-proxy.ts`'s `safeEnv` filter, which is used exclusively for hooks that are (a) in the caller's `interceptHooks` list and (b) actually detected by `getRepoHooks` [6](#0-5) [7](#0-6) . `interceptHooks` is only wired up for `createCommit`, `merge`, `pull`, and `push` [8](#0-7) . Any other git command executed through `core.ts` (e.g. checkout) does not intercept hooks — `withHooksEnv` short-circuits and returns the untouched trampoline env [9](#0-8) . In that case Git itself spawns the repository's hook/filter binary as a direct child of the process Desktop launched, and that child inherits the full environment — including `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT`.

`DESKTOP_TRAMPOLINE_TOKEN` is the sole authorization credential accepted by the trampoline TCP server (`isValidTrampolineToken`) [10](#0-9) ; any process holding it can connect to `127.0.0.1:DESKTOP_PORT` and issue `ASKPASS`/`CREDENTIALHELPER` trampoline commands, which are handled by `createAskpassTrampolineHandler` and the credential-helper handler and can return stored SSH passphrases, SSH user passwords, or Git credentials for the account associated with the repository [11](#0-10) .

### Impact Explanation
A hook or filter binary that is invoked outside the `interceptHooks` sanitization boundary — because it belongs to a git operation that doesn't intercept hooks, or because it's a `clean`/`smudge`/`diff`/`merge` driver (which is *never* routed through the hooks-proxy allow-list regardless of the operation) — can read `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` from its own environment and impersonate Git to Desktop's local trampoline server, requesting stored SSH passphrases or the credential helper's stored token/password for the currently active operation. This is credential/token exfiltration from an unprivileged local process, achieved purely by having code run as a side effect of a routine repository operation Desktop itself performs.

### Likelihood Explanation
This requires a hook/filter/driver binary to already be configured to run for the repository (e.g. via `core.hooksPath`, `.gitattributes` filters referencing an installed driver, or a hook already present on disk) at the time an unprotected Desktop git operation executes. Because `.git/hooks` and `.git/config` are not populated purely by `git clone`/`fetch`, this generally requires the hook/filter to have been set up beforehand (e.g. by tooling like Husky, or a locally installed filter such as Git LFS), which is a caveat on how "purely attacker-controlled" this path is. I was not able to fully verify from the index whether `checkout.ts` (or other non-`interceptHooks` git operations) actually triggers native hook execution in a scenario reachable purely by cloning/opening an untrusted repository, nor did I confirm the exact contents of `trampoline-credential-helper.ts`'s response payload — the index only returned match counts for that file, not its body, so I could not fully verify what secret material it would hand back. This should be verified in a full checkout of the repository.

### Recommendation
Apply the `safeEnv` allow-list (or an equivalent explicit deny-list of `DESKTOP_*`/`PROCESS_PROXY_*` variables) uniformly to every environment that can reach a Git-spawned child process, not just the intercepted-hooks path — i.e., strip `DESKTOP_TRAMPOLINE_TOKEN`, `DESKTOP_PORT`, `PROCESS_PROXY_TOKEN`, and `PROCESS_PROXY_PORT` from the environment before Git executes any hook, filter, or external driver, regardless of whether `interceptHooks` was requested for that command. Alternatively, scope trampoline tokens so that only the direct Git process (and no descendant processes it spawns) can present them, e.g. by using process-group/parent-PID binding on the trampoline server connection rather than a bearer token alone.

### Proof of Concept
Not independently executed against the running app; this is a static-analysis-derived path based on:
1. `withTrampolineEnv` unconditionally injecting `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` into every `git()` call [5](#0-4) .
2. `withHooksEnv` only sanitizing this environment when `interceptHooks` is explicitly passed, which excludes several git operations [9](#0-8) .
3. The trampoline server accepting any client presenting a valid, currently-live token [10](#0-9) , and the askpass handler returning stored secrets to whoever asks [12](#0-11) .

Given the incomplete confirmation of the exact reachable trigger path (which non-intercepted git command actually spawns a repo-controlled hook/filter as a direct child in a scenario attacker can set up remotely) and the exact payload returned by the credential-helper handler, I recommend a Devin session with full repository access to confirm end-to-end exploitability before treating this as fully validated.

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }

async function handleSSHKeyPassphrase(
  operationGUID: string,
  prompt: string
): Promise<string | undefined> {
  const promptRegex = /^Enter passphrase for key '(.+)': $/

  const matches = promptRegex.exec(prompt)
  if (matches === null || matches.length < 2) {
    return undefined
  }

  let keyPath = matches[1]

  // The ssh bundled with Desktop on Windows, for some reason, provides Unix-like
  // paths for the keys (e.g. /c/Users/.../id_rsa). We need to convert them to
  // Windows-like paths (e.g. C:\Users\...\id_rsa).
  if (__WIN32__ && /^\/\w\//.test(keyPath)) {
    const driveLetter = keyPath[1]
    keyPath = keyPath.slice(2)
    keyPath = `${driveLetter}:${keyPath}`
  }

  const storedPassphrase = await getSSHKeyPassphrase(keyPath)
  if (storedPassphrase !== null) {
    // Keep this stored passphrase around in case it's not valid and we need to
    // delete it if the git operation fails to authenticate.
    await setMostRecentSSHKeyPassphrase(operationGUID, keyPath)
    return storedPassphrase
  }

  if (getIsBackgroundTaskEnvironment(operationGUID)) {
    log.debug(
      'handleSSHKeyPassphrase: background task environment, skipping prompt'
    )
    return undefined
  }

  const { secret: passphrase, storeSecret: storePassphrase } =
    await trampolineUIHelper.promptSSHKeyPassphrase(keyPath)

  // If the user wanted us to remember the passphrase, we'll keep it around to
  // store it later if the git operation succeeds.
  // However, when running a git command, it's possible that the user will need
  // to enter the passphrase multiple times if there are failed attempts.
  // Because of that, we need to remove any pending passphrases to be stored
  // when, in one of those multiple attempts, the user chooses NOT to remember
  // the passphrase.
  if (passphrase !== undefined && storePassphrase) {
    setSSHKeyPassphrase(operationGUID, keyPath, passphrase)
  } else {
    removeMostRecentSSHCredential(operationGUID)
  }

  return passphrase ?? ''
}

  accountsStore: AccountsStore

  (accountsStore: AccountsStore) => async command => {
    if (command.parameters.length !== 1) {
      return undefined
    }

    if (firstParameter.startsWith('The authenticity of host ')) {
      return handleSSHHostAuthenticity(command.trampolineToken, firstParameter)
    }

    if (firstParameter.startsWith('Enter passphrase for key ')) {
      return handleSSHKeyPassphrase(command.trampolineToken, firstParameter)
    }

    if (firstParameter.endsWith("'s password: ")) {
      return handleSSHUserPassword(command.trampolineToken, firstParameter)
    }

    return undefined
  }
