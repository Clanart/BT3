### Title
`clone()` explicitly disables Git's clone hook-injection protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
`app/src/lib/git/clone.ts` builds the environment for every `git clone --recursive` invocation and hard-codes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into that environment. Upstream Git added `GIT_CLONE_PROTECTION_ACTIVE` (defaulting to active) specifically to close the class of vulnerabilities where a malicious repository/submodule ships a crafted `.git/config`, `core.hooksPath`, or symlinked hooks directory that gets executed automatically during a recursive clone before the user has ever inspected the code (the class fixed by upstream CVE-2024-32004/-32020/-32021/-32465). By forcing this protection to `false` on every clone Desktop performs, the app unconditionally re-enables that attack surface for any repository or submodule an attacker controls.

### Finding Description [1](#0-0) 

`clone()` is the function invoked whenever a user clones a repository from the UI (including "Clone repository", "Open in Desktop" deep links, and CLI `--cli-clone`). It always passes `--recursive`, meaning any submodules referenced by the target repository are fetched and checked out automatically, without the user ever reviewing submodule content first: [2](#0-1) 

The `env` object explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. This environment variable is Git's own kill-switch for its clone-time protections against configuration/hook injection via a nested repository (top-level repo or any of its submodules) — protections that were added upstream after multiple CVEs where a `.gitmodules`/`.git/config`/`core.hooksPath` entry in a cloned or fetched tree caused hook scripts to run with the invoking user's privileges as a side effect of `clone --recursive`. Explicitly forcing this to `'false'` means Desktop tells the bundled Git binary to skip these checks unconditionally, on every single clone, for every repository the user chooses to open (including forks, third-party mirrors, or the target of a "Clone repository" / deep-link action).

This is analogous in structure to the reported re-entrancy issue: a broken invariant (Git's own upstream safety check that assumes a specific execution order/gate before untrusted content executes) is deliberately bypassed by the calling application, and the attacker who controls the fetched object (here: a repository or one of its submodules) gets to run code as a side effect of an operation the user believed was "just cloning."

No other guard in the surrounding code compensates for this. `isClonePathSensitive()` only validates the destination directory path, not the content of the repository being cloned; it does nothing to prevent hook execution triggered by the cloned content itself. `envForRemoteOperation()` only adds authentication/proxy environment variables and does not restore or otherwise gate the protection Git provides. The hook-interception feature in `app/src/lib/hooks/with-hooks-env.ts` (which proxies hook execution through a sandboxed process) is not engaged during `clone()` at all — `clone()` does not pass `interceptHooks` in its options — so during clone, any hook that Git decides to run (which is exactly what `GIT_CLONE_PROTECTION_ACTIVE` is meant to prevent from happening implicitly) runs as a normal, unconstrained child process of the real `git` binary.

### Impact Explanation
If a Git clone protection scenario is triggered (e.g., a submodule with a crafted `core.hooksPath`, `.git/config`, or symlinked hooks directory), disabling `GIT_CLONE_PROTECTION_ACTIVE` allows arbitrary hook script execution as a direct, unprompted side effect of the user cloning a repository they do not control (e.g., a fork, a link shared with them, or a repository opened via the `x-github-client://openRepo/...` deep link handled in `app/src/main-process/main.ts` / `parseAppURL`). This maps directly to the "Valid Impact" criteria: an unprivileged attacker who controls a cloned/fetched repository (or a link that causes Desktop to clone one) can obtain code execution on the victim's machine, with no local access, no leaked credentials, and no social engineering beyond "clone/open this repo" — an entirely normal Desktop workflow.

### Likelihood Explanation
Every clone performed by Desktop goes through this exact code path and always sets this variable to `'false'`, so there is no configuration or user action that avoids it — the exposure is unconditional whenever a vulnerable hook/config-injection payload exists in a repository or its submodules. The main mitigating factor is that it depends on the specific Git-level injection primitives that `GIT_CLONE_PROTECTION_ACTIVE` was created to block; how many such primitives remain viable depends on the bundled Git version. That said, the code shows a clear, deliberate override of an upstream security control on every clone, which is the pattern requested by the task (broken invariant + attacker-controlled fetched object + no local/privileged access needed).

### Recommendation
- Remove the hard-coded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` from `clone.ts` and let Git's built-in protection remain active by default.
- If there is a specific compatibility reason this was disabled (e.g., LFS/submodule progress parsing relying on hook execution), scope the override narrowly and only for trusted, already-vetted repositories, and route any hook execution that does need to happen through the existing sandboxed `withHooksEnv`/`hooks-proxy.ts` mechanism (which restricts environment variables and proxies execution) rather than a bare, unconstrained `git` child process.
- Add a regression test asserting that `GIT_CLONE_PROTECTION_ACTIVE` is never explicitly disabled by Desktop's clone path.

### Proof of Concept
1. Attacker publishes/forks a repository (or submodule) that would trigger one of the config/hook-injection primitives Git's clone protection is designed to reject (e.g., a submodule whose `.git/config` sets `core.hooksPath` to a directory containing an executable `post-checkout`/`pre-commit`-named file, laid out so that a plain, protection-enabled `git clone --recursive` refuses/ignores it).
2. Victim opens the repository in GitHub Desktop via "Clone repository", a shared clone URL, or the `x-github-client://openRepo/<url>` deep link (handled by `handleAppURL`/`parseAppURL` in `app/src/main-process/main.ts` and `app/src/lib/parse-app-url.ts`).
3. Desktop calls `clone()` in `app/src/lib/git/clone.ts`, which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` injected into the environment.
4. Because Git's clone-time protection is disabled, the injected hook/config payload from the submodule executes as a normal child process of the user's own Git binary during the recursive clone, with no proxy/sandbox and no user prompt.

I could not execute an actual end-to-end PoC against the bundled Git binary version in this environment to confirm which specific upstream primitive(s) `GIT_CLONE_PROTECTION_ACTIVE` blocks are still reachable in the exact Git release Desktop vendors; that would require running the app/dugite binary, which is outside what static code search can verify.

  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void

  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',

    '-c',
