### Title
Line-selection patch is applied against a freshly re-read diff, not the diff shown to the user, allowing a race-window content swap to silently corrupt partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported `checkpoint.timestamp` bug is a broken invariant: a value meant to bind a piece of state to "the moment it was captured" is never actually populated/checked, so later code that assumes freshness silently operates on stale/mismatched data. The Desktop analog is `applyPatchToIndex` in `app/src/lib/git/apply.ts`, which re-fetches the working directory diff at apply-time instead of using the diff that was captured when the user made their line/hunk selection, and the `WorkingDirectoryFileChange.id` used throughout the app to key that selection is `${status.kind}+${path}` — a value with no content or diff-version binding at all.

### Finding Description
`WorkingDirectoryFileChange` extends `FileChange`, whose `id` is computed purely from status kind and path: [1](#0-0) 

This `id` (and the `DiffSelection` line indices tied to it) is the only handle the UI keeps for "which lines of this file are selected to be committed." It carries no reference to the specific diff/content version the user was looking at when they made line-level selections.

When the commit is actually built, `stageFiles` routes partially-selected files to `applyPatchToIndex`: [2](#0-1) 

`applyPatchToIndex` does not reuse the diff the UI displayed and the user made selections against. It re-reads the working directory diff from disk at commit time and builds the patch from that fresh diff plus the (older) selection object: [3](#0-2) 

`formatPatch` then maps `file.selection.isSelected(absoluteIndex)` — line indices captured against the *old* diff — onto hunks/lines from the *new* diff: [4](#0-3) 

If working-directory file content changes between the moment the user reviews/selects lines in the diff view and the moment the commit is executed, the absolute line indices in `DiffSelection` no longer correspond to the same logical lines in the freshly-fetched diff. `formatPatch` will still happily walk the new hunks and apply the stale index-based selection, producing a patch that includes/excludes different lines than what the user actually reviewed and clicked — and `git apply --cached` will commit exactly that mismatched content. Nothing in the pipeline compares the diff used to build the selection against the diff used to build the patch (no content hash, no diff-version, no `timestamp`-equivalent check), which is exactly the broken-invariant pattern in the report: a value meant to guarantee "this is the state we validated" is never captured or checked.

The window for content to change is real and attacker-influenceable: a repository (cloned or already open) can register a `post-checkout`, `post-merge`, `pre-commit`, or a filter/smudge driver, or an editor/build tool triggered by opening the repo, that rewrites a tracked file's content shortly after the diff is generated for review but before the user hits "Commit". None of that requires local malware pre-existing on the host beyond what's delivered by the untrusted repository itself (hooks/filters are repo-controlled, not host-controlled).

### Impact Explanation
This lets a malicious/compromised repository (attacker-controlled clone content) cause the user to commit and push content they never selected — a silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact class. Depending on what gets silently included, this can smuggle in malicious code additions that the user believed were excluded, or drop safety-relevant lines the user believed were included, without any error or warning from Desktop.

### Likelihood Explanation
Medium: it requires (a) the user to do a partial/line-level stage-and-commit (a common workflow) on a file, and (b) something that mutates that file's on-disk content in the small window between diff generation and commit execution (a hook, filter/smudge driver, or background process triggered by opening/interacting with the untrusted repo). There is no re-validation step that would catch the mismatch, so once the race condition is triggered the corruption is guaranteed and silent, but triggering the precise timing window is non-trivial for an attacker without some additional automation on their side (e.g., a git hook run during checkout/fetch that starts a background rewrite).

### Recommendation
Bind the `DiffSelection`/patch-building process to the exact diff instance the user reviewed rather than re-fetching a new diff at apply time. Concretely:
- Pass the originally displayed `ITextDiff`/`ILargeTextDiff` object (or a content hash of the old/new blob) through to `applyPatchToIndex` instead of calling `getWorkingDirectoryDiff` again inside it.
- Before calling `formatPatch`, verify that the file's current on-disk content (or its diff) still matches what was used to build the selection; if not, abort the partial-stage for that file and force the user to re-review it.
- Alternatively, key `DiffSelection` state by a content hash of the file (not just path+status) so a stale selection can be detected and discarded automatically.

### Proof of Concept
1. Open/clone a repository containing a modified tracked file with multiple hunks.
2. In Desktop, open the file's diff and select only some lines/hunks for the commit (leave others unstaged), but do not commit yet.
3. While the commit dialog/selection is open, have an external process (simulating a hook/filter triggered by repo interaction) modify the same file on disk, shifting or changing line content near the hunks (e.g., inserting/removing lines above the selected hunk).
4. Click "Commit" in Desktop.
5. Observe that `applyPatchToIndex` re-reads the diff (now reflecting the modified file) and `formatPatch` applies the old `DiffSelection` line indices to the new hunks, producing a commit whose staged content does not match the lines the user actually selected in step 2 — verifiable by inspecting `git show --cached` / the resulting commit versus the diff the user visually approved.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
