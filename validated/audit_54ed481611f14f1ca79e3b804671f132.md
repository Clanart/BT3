Based on the investigation, I found a genuine analog: **duplicate relayer-fee payment for a single GET request via two independent settlement paths (response delivery and timeout), because the request's fee-escrow record is never cleared on the response path.**

### Title
GET request fee escrow (`_requestCommitments`) not cleared after response delivery, enabling double payment via timeout - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core defect is: a callback/settlement path can fire more than once because the code fails to consistently invalidate the state that guards it once settlement occurs. Hyperbridge's Substrate ISMP core explicitly defends against this exact class of bug for GET requests — the timeout handler checks `if host.response_receipt(&response).is_some() { Err(Error::GetResponseAlreadyReceived) }` before allowing a timeout to proceed [1](#0-0) . The EVM-side `EvmHost.sol`, however, settles the relayer fee for a GET response without deleting the corresponding fee-escrow entry (`_requestCommitments`), leaving the same commitment eligible to be consumed again by the timeout path.

### Finding Description
When a GET response is delivered, `EvmHost.dispatchIncoming(GetResponse, ...)` pays the relayer fee out of `_requestCommitments[commitment].fee` but never deletes `_requestCommitments[commitment]`: [2](#0-1) 

Compare this to the GET timeout path, `dispatchTimeOut(GetRequestTimeout, ...)`, which explicitly `delete`s `_requestCommitments[commitment]` for replay protection before invoking the app callback and paying the fee to the original payer: [3](#0-2) 

`HandlerV2.handleGetResponses` only guards against redelivering the *same* response twice (via `responseReceipts`), and `HandlerV2.handlePostRequestTimeouts`/the GET-timeout equivalent only checks that `requestCommitments(hash).sender != address(0)` ("known request") before proceeding — it does not check whether a response was already delivered for that request: [4](#0-3) [5](#0-4) 

Because `_requestCommitments[commitment]` is left intact after a successful GET-response delivery, the "known request" check still passes for a subsequent timeout submission on that same commitment, and the timeout path will pay out the fee again (to the payer) — a second payout for a request that has already been paid out once (to the relayer). This mirrors exactly the reentrancy/duplicate-callback class described in the seed report: an external, permissionless caller (anyone can submit `handleGetResponses` and `handlePostRequestTimeouts` — both are documented as "Permissionless (can be called by anyone)") can trigger settlement of the same commitment through two different code paths because the guard that should invalidate it after the first settlement is missing on one path only.

### Impact Explanation
This falls squarely within the bounty's "duplicate settlement / double-claim" and "funds moving more than once" impact categories. The fee token held by the host is disbursed twice for a single dispatched GET request (once to the relayer on response, once to the payer/sender on timeout), directly draining protocol/escrowed fee-token balance beyond what was ever collected for that request.

### Likelihood Explanation
Both `handleGetResponses` and `handlePostRequestTimeouts`/GET-timeout equivalents are permissionless entry points restricted only by valid consensus proofs (membership proof for the response, non-membership proof for the timeout). An attacker/relayer does not need to be malicious infrastructure — they only need to legitimately relay a genuine response and then, once the request's original timeout timestamp elapses, submit a standard (valid) non-membership/timeout proof for the same request. No compromised relayer, prover, or admin is required; only ordinary permissionless usage of both public handler functions is needed. This closely parallels the exact ordering hazard called out by the analogous Substrate-side comment/guard that has no EVM counterpart.

### Recommendation
Delete (or otherwise permanently invalidate) `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse, ...)` immediately after successful response delivery, before or as part of the fee payout, mirroring the pattern already used in `dispatchTimeOut`. Additionally, `HandlerV2`'s GET-timeout handling should check `host.responseReceipts(commitment)` and reject the timeout if a response receipt already exists, matching the Substrate-side `GetResponseAlreadyReceived` guard.

### Proof of Concept
1. App dispatches a GET request via `EvmHost.dispatch(DispatchGet)`, escrowing `fee` in `_requestCommitments[commitment]` [6](#0-5) .
2. Relayer delivers a valid GET response through `HandlerV2.handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse, relayer)`, which pays `fee` to `relayer` but leaves `_requestCommitments[commitment]` intact [7](#0-6) .
3. After the request's original `timeoutTimestamp` elapses, anyone submits a valid non-membership/timeout proof through the GET-timeout handler; because `requestCommitments(commitment).sender != address(0)` still holds, the "known request" check passes, and `dispatchTimeOut(GetRequestTimeout, meta, commitment)` pays `meta.fee` again to `meta.sender` [3](#0-2) .
4. Net result: the same `fee` amount for one GET request is paid out twice from host-held fee-token balance.

**Note on verification limits:** I was not able to fully retrieve the exact GET-timeout function body in `HandlerV2.sol` (only `handlePostRequests`, `handleGetResponses`, and the start of `handlePostRequestTimeouts` were retrieved before the iteration limit) to confirm there is no additional response-receipt check specifically inserted only for the GET-timeout variant. If such a check exists there and was missed, it would mitigate this specific path; I recommend a Devin session verify the full GET-timeout handler function in `evm/src/core/HandlerV2.sol` to close this gap definitively.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
