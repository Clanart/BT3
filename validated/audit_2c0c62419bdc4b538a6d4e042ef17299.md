This confirms the SSRF pattern in Chia's DataLayer mirror flow: any store owner can call `add_mirror` (via `data_layer_rpc_api.add_mirror` → `DataLayer.add_mirror`) to publish arbitrary URLs on-chain in a mirror coin's memo [1](#0-0) , and those URLs are read on-chain by `DataLayerWallet.coin_added()` via `get_mirror_info()` with no validation before being stored as trusted mirror server URLs [2](#0-1) . Any DataLayer client subscribed to that store (`update_subscriptions_from_wallet`) will then have `fetch_and_validate()` pick one of these attacker-controlled URLs and pass it straight into `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an unrestricted `aiohttp` GET with no private-IP/SSRF protection [3](#0-2) [4](#0-3) .

### Title
SSRF via attacker-controlled DataLayer mirror URLs fetched by subscriber nodes without validation - (File: chia/data_layer/download_data.py)

### Summary
Chia's DataLayer lets any wallet owning a DataLayer singleton publish "mirror" URLs on-chain via `add_mirror`. These URLs are propagated to every peer that later subscribes to that store and are fetched directly by the subscriber's local DataLayer service using a plain `aiohttp.ClientSession` with no SSRF protections, no scheme/host allowlist, and no restriction on private/loopback/link-local addresses.

### Finding Description
`DataLayerRpcApi.add_mirror` → `DataLayer.add_mirror` lets the store owner publish an arbitrary list of URL strings on-chain by spending a mirror coin whose memo encodes `[launcher_id, *urls]`, with no URL validation at any point [1](#0-0) [5](#0-4) .

Any other node's wallet that tracks the launcher observes the mirror coin being created and decodes the URLs verbatim from the parent coin's spend solution into a `Mirror` record, again with no validation of the URL content: `Mirror.decode_urls(urls)` in `coin_added()` [2](#0-1) .

The DataLayer service periodically syncs subscribed stores' mirror URLs from the wallet into its local subscription table via `update_subscriptions_from_wallet()` [6](#0-5) , and `fetch_and_validate()` iterates these URLs, calling `insert_from_delta_file()` with the raw `server_info.url` [4](#0-3) .

The actual network request happens in `http_download()`, which builds the request from `server_info.url + "/" + filename` and issues a plain `aiohttp.ClientSession().get(...)` with no destination validation — no blocklist for `127.0.0.1`, `169.254.169.254`, RFC1918 ranges, or any DNS-rebinding protection [3](#0-2) . This is the same missing-SSRF-guard pattern described in the Vikunja advisory (`DownloadFile`/`DownloadFileWithHeaders` making unrestricted GET requests to attacker-influenced URLs), except here the untrusted URL originates from an on-chain mirror coin rather than a third-party migration API response, and the "download" target is any peer node that chooses to subscribe to the store (a normal, expected DataLayer client action).

Unlike Vikunja's migration flow, there is no admin-configured opt-in gate beyond simply subscribing to a store — which is the ordinary, expected DataLayer client workflow (`chia data subscribe`, `data_rpc_api.subscribe`) [7](#0-6) [8](#0-7) .

### Impact Explanation
An attacker who owns (or offers to a victim) a DataLayer store can publish a mirror URL pointing at an internal service on the victim's network (e.g. `http://127.0.0.1:<local-port>/`, a cloud metadata endpoint, or another internal host reachable from the victim's node) via `add_mirror`. Once the victim subscribes to that store — a routine DataLayer action, e.g. to receive updates or evaluate a DataLayer offer — the victim's own DataLayer service will issue outbound HTTP GET requests to that internal URL on the attacker's behalf, and any downloaded bytes are inserted into local files (`target_filename_path`) attempted as delta/full-tree content. Even though `insert_into_data_store_from_file()` will ultimately reject content that doesn't reconstruct the wallet-advertised Merkle root, the SSRF request itself has already been made from the victim's node before that validation occurs, allowing port-scanning of internal services and probing responses via timing/behavior differences (e.g. `aiohttp.client_exceptions.ClientConnectorError` vs. successful connect logged distinctly at `data_layer.py:702-705`), and unbounded response consumption is only bounded by `max_delta_file_size`, not by a network-layer restriction.

### Likelihood Explanation
Reachable by any unprivileged DataLayer participant: no special node privileges are required beyond owning a DataLayer store and running `add_mirror`, and the victim only needs to perform the standard, expected act of subscribing to (or querying an offer against) an attacker's store. This matches an "unprivileged spend-bundle submitter"-equivalent reach for DataLayer clients, as permitted by scope.

### Recommendation
Apply SSRF protections to `http_download()` in `chia/data_layer/download_data.py` (and any URL taken from `get_downloader`/plugin `PluginRemote.url`): validate the resolved URL/IP against a private/loopback/link-local blocklist before connecting (e.g. using a `DialContext`/socket-level control equivalent, similar to `daenney/ssrf` used elsewhere), reject non-HTTP(S) schemes, disallow redirects to disallowed hosts, and continue enforcing (or tighten) the existing `max_delta_file_size` response-size cap. Consider requiring explicit user opt-in/allowlisting before a subscription auto-adopts URLs advertised by mirror coins from `update_subscriptions_from_wallet()`.

### Proof of Concept
1. Attacker creates a DataLayer store and calls `add_mirror` with `urls=["http://169.254.169.254/latest/meta-data/"]` (or an internal victim-only address if attacker has network position), publishing the mirror coin on-chain [1](#0-0) .
2. Victim's DataLayer wallet observes the mirror coin creation and records the URL via `coin_added()` → `Mirror.decode_urls()` [2](#0-1) .
3. Victim subscribes to the attacker's store id (e.g. to evaluate a DataLayer offer or mirror data), causing `update_subscriptions_from_wallet()` to pull the attacker's URL into the local subscription table [6](#0-5) .
4. On the next `periodically_manage_data()` cycle, `fetch_and_validate()` selects the malicious URL and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, causing the victim's node to issue an unrestricted GET request to the internal address [4](#0-3) [3](#0-2) .
5. Response/error behavior differences (connection success/timeout/refused, logged distinctly) let the attacker infer internal network topology; if the response happens to look like valid delta file content it will be stored locally before final root-hash verification fails.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
