### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes large speculative allocations from minimal input, enabling memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
The CL-2020-01 bug class is "an unprivileged network agent can force a victim to consume disproportionate resources (sessions/memory) and crash the service." In Serai, `ThresholdKeys::<C>::read` accepts untrusted bytes and, before validating that any corresponding data exists, performs `Vec::with_capacity(usize::from(n))` where `n` is a raw attacker-controlled `u16` read from the input stream. A ~13-byte input therefore forces an allocation sized for up to 65,535 field elements, and the subsequent per-participant loops (`1 ..= n`) drive further work proportional to the attacker-chosen parameter rather than to input length.

### Finding Description
`ThresholdKeys::read` is explicitly an untrusted-bytes entry point (it is invoked on serialized key material / shares received over the wire). The function reads `t`, `n`, and `i` as bare `u16`s at crypto/dkg/src/lib.rs:591-602, then for `Interpolation::Constant` executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
``` [1](#0-0) 

It then unconditionally iterates `for l in (1 ..= n)` performing `C::read_G` into a `HashMap` at crypto/dkg/src/lib.rs:620-623, and only afterwards calls `ThresholdParams::new(t, n, i)` to validate `t`/`n`/`i` consistency at crypto/dkg/src/lib.rs:625-626. Validation happens *after* the resource consumption: the capacity reservation and the length-driven loops run against whatever `n` the attacker wrote, even if the stream contains no further bytes.

`C::F` for the in-scope ciphersuites (secp256k1, ed25519, Ristretto, ed448) is a 32-byte field element; `Vec::with_capacity(65535)` reserves ≥2 MiB for the interpolation vector alone. `C::read_G` additionally performs a full point decompression per element for as many elements as the attacker actually supplies bytes, so a modest stream of compressed points yields sustained CPU burn plus heap growth well beyond the input size.

This mirrors the Lighthouse discovery crash: a small amount of unauthenticated input forces the victim to allocate disproportionate per-"session" (here, per-message) state. Other in-scope readers bound their work by locally trusted parameters — `Commitments::read` caps its loop at `params.t()` (crypto/dkg/pedpop/src/lib.rs:111-125) — making `ThresholdKeys::read` the outlier that trusts a wire-supplied count.

### Impact Explanation
An attacker who can feed bytes to `ThresholdKeys::read` (any code path loading threshold key material or shares received from a peer) forces a ≥2 MiB heap allocation per call with only ~13 bytes of input — an amplification factor exceeding 100,000x on the allocation alone. Repeated or concurrent calls exhaust memory and crash the process, denying service to the node and aborting any in-progress DKG/signing that depends on it. On memory-constrained validator environments, even a modest request rate suffices. This is a genuine availability impact reachable with purely public input, satisfying Medium severity.

### Likelihood Explanation
Exploitation requires a path where a remote/untrusted party's bytes reach `ThresholdKeys::read`. The function is the canonical deserialization entry point for `ThresholdKeys` and is among the explicitly in-scope untrusted-read surfaces; integrators that accept or exchange serialized key material (e.g., recovery, resharing, or coordinator-supplied payloads) hit it directly. `n` is read before any validation, so no valid header, signature, or proof is required — the attacker just writes `0xFF 0xFF` in the `n` position. The attack is reliable and cheap, though it depends on the deployment exposing this read to untrusted input, which is common for key-exchange flows but not universal.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new` *before* performing any length-driven allocation or iteration — i.e., move the params check to immediately after the three `u16` reads. Additionally, avoid `Vec::with_capacity(n)` on untrusted counts: either grow the vector incrementally so allocation tracks actually-present bytes (as done in `ethereum/src/machine.rs` `Call::read`, which reads `data` in 1 KiB chunks specifically to bound this DoS), or cap `n` at a protocol-meaningful maximum before allocation. Reordering also removes the currently reachable state where the `1 ..= n` `read_G` loop runs against an invalid `n`.

### Proof of Concept
```rust
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;

fn dos<C: Ciphersuite>() {
  let mut bytes = vec![];
  // C::ID length + C::ID to pass the curve check
  bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  bytes.extend(C::ID);
  // t, n, i — n set to the maximum u16
  bytes.extend(1u16.to_le_bytes());      // t
  bytes.extend(u16::MAX.to_le_bytes());  // n = 65535
  bytes.extend(1u16.to_le_bytes());      // i
  bytes.push(0);                         // Interpolation::Constant

  // Only ~13+ID bytes were provided, yet Vec::with_capacity(65535) reserves
  // ~2 MiB of C::F elements before read_F fails on the empty stream.
  // Issued in a loop / concurrently, this exhausts memory.
  let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
}
```

Secondary supporting behavior: `crypto/schnorr/src/aggregate.rs:77-88` `SchnorrAggregate::read` accepts a `u32` element count and performs one `C::read_G` decompression per supplied element with no upper bound on aggregate size, letting `SchnorrAggregate::verify` (crypto/schnorr/src/aggregate.rs:127-146) be driven into an arbitrarily large `multiexp_vartime` plus one `weight()` digest-challenge computation per element — linear-cost amplification on attacker-chosen volume. The primary finding above (speculative `with_capacity` before validation) is the cleaner analog of the session-flood crash.

Uncertain: whether any in-scope call path in this repo itself feeds remote bytes into `ThresholdKeys::read` (the processor's `VerifyBlame` path reads `EncryptedMessage`, not `ThresholdKeys`); the finding holds wherever integrators deserialize received key material, which the read API exists for.
