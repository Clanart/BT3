### Title
`SignableTransaction::new` hardcodes a single dust threshold of 546 sats for all output types, permitting payments/change that are dust (unspendable/non-standard) on-chain - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`DUST` is hardcoded to 546 satoshis and applied uniformly to every payment `ScriptBuf` and to the change output, regardless of the actual dust threshold for that specific `script_pubkey`. Like the referenced oracle hard-pegging stablecoins to 1, this hard-codes a network-derived economic/policy value that varies per output type and over time.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `pub const DUST: u64 = 546` is defined with a comment referencing Bitcoin Core's policy code, and the code explicitly notes it "doesn't bother with delineation" between SegWit and non-SegWit outputs [1](#0-0) . That constant is then used as the acceptance floor for every payment regardless of its script type:

- `for (_, amount) in payments { if *amount < DUST { Err(TransactionError::DustPayment)?; } }` [2](#0-1) 
- change outputs are only created if the leftover `value >= DUST` [3](#0-2) 

Bitcoin Core computes dust per output as `3 * minRelayTxFee * (serialized_output_size + spend_size)`, so the threshold depends on the `script_pubkey` length and the spend type. A P2PKH output spends with a ~148-byte input (dust ≈ 546), while outputs with larger scriptPubKeys or more expensive spends (e.g., bare multisig, uncompressed-key P2PK, large bare scripts, or outputs under a raised min-relay fee) have dust thresholds well above 546. `SignableTransaction::new` accepts `payments` as an arbitrary `(ScriptBuf, u64)` list supplied by callers; any value `546 <= amount < real_dust(script)` passes validation, is embedded into `tx_outs` [4](#0-3) , signed via the FROST flow in the same file, and broadcast.

The comment's justification ("it isn't worth the complexity to implement differentiation") is exactly the bug class of the external report: a hardcoded constant standing in for a value that is not actually constant. The code even acknowledges lower values may be valid for SegWit outputs but never considers the inverse — script types whose dust threshold is *higher* than 546 — nor a future increase in `DEFAULT_MIN_RELAY_TX_FEE`, which is likewise consulted as a hardcoded floor at line 211 [5](#0-4) .

### Impact Explanation
A transaction built by `SignableTransaction::new` containing a payment (or change output, since the change `ScriptBuf` is caller-controlled) with `amount` in `[546, real_dust)` produces an on-chain output that is dust: it is non-standard to relay, and even if mined it cannot be economically spent by the recipient — spending it costs more in fees than it is worth. For Serai, funds the protocol believes it has paid out (a withdrawal/burn fulfillment) are effectively burned, while the scheduler/attacker-facing accounting treats them as delivered. This matches the report's pattern: validating value against a fixed assumption causes the protocol to accept an outcome that is actually invalid/destructive.

### Likelihood Explanation
Reachable by an unprivileged party: `payments` is a public input — any caller (e.g., a withdrawal recipient) supplies a `(ScriptBuf, u64)` pair. They request a payment of, say, 600 sats to a large bare script or legacy output type whose dust threshold exceeds the amount. The check `*amount < DUST` passes, the transaction is signed and published, and the output is provably dust on-chain — funds reported paid that are not spendable. The reverse-direction case (change `ScriptBuf` chosen by the caller with a real dust threshold > 546) is equally reachable.

### Recommendation
Replace the scalar `DUST` constant with a per-output dust calculation: `dust_threshold(script_pubkey) = (spend_size(script) + output_serialized_size) * dust_relay_fee_rate`, mirroring Bitcoin Core's `GetDustThreshold`/`IsDust`. Apply it per payment `ScriptBuf` and per change script, and derive the rate from a configurable min-relay-fee rather than the fixed 546.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, &[(large_bare_script, 546)], None, None, fee)` where `large_bare_script` is a valid output script whose serialized size makes its on-chain dust threshold (at 3 sat/vB) > 546 sats.
2. `new` returns `Ok` — the `DustPayment` check passes because `546 >= DUST`.
3. The produced `tx` contains `TxOut { value: 546, script_pubkey: large_bare_script }`, which is below Bitcoin Core's `IsDust` threshold for that output type: it will not relay and is uneconomical/unspendable for the recipient, while Serai counts it as a completed payment.
