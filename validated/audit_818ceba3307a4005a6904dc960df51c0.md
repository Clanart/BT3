## Analysis

The external report's core broken invariant: **a contract computes "is withdrawal safe?" using only wallet balance, without subtracting funds that are already earmarked/escrowed for a different purpose (commission/reserved amounts)**. That lets a legitimate-looking withdrawal or unstake drain funds that are not actually free.

I looked for the same class of bug in Hyperbridge's fund-custody paths — protocol fee withdrawal, relayer fee escrow, paymaster surplus sweeps, bandwidth withdrawals — and found the closest local analog in `EvmHost.sol`'s revenue withdrawal path.

### Title
EvmHost.withdraw does not exclude escrowed relayer/request fees from withdrawable balance - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` holds a single `feeToken` ERC-20 balance that commingles two economically distinct pools: (1) fees users/apps attach to outgoing requests/responses, tracked per-commitment in `_requestCommitments` as `FeeMetadata` [1](#0-0) , which are owed to whichever relayer delivers the message (or refundable to the payer on timeout), and (2) protocol revenue that governance is entitled to sweep. `withdraw()`, callable only by the `hostManager` after a cross-chain governance instruction, transfers the requested `amount` of `token` straight out of the contract with no check that the remaining balance still covers all outstanding `FeeMetadata` fee commitments: [2](#0-1) 

### Finding Description
`WithdrawParams.amount` is an arbitrary value chosen off-chain (by the `pallet-host-executive` withdraw extrinsic on Hyperbridge, see `modules/pallets/host-executive/src/lib.rs:273-319`) and forwarded through `HostManager.onAccept` → `IHostManager(_params.host).withdraw(withdrawParams)` [3](#0-2) . The `EvmHost.withdraw` function itself performs **no invariant check** between the `feeToken`/native balance being paid out and the sum of unclaimed relayer fees currently escrowed in `_requestCommitments` for requests that have been dispatched but not yet delivered or timed out:

```solidity
function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
    if (params.token == address(0)) {
        (bool sent,) = params.beneficiary.call{value: params.amount}("");
        if (!sent) revert WithdrawalFailed();
    } else {
        IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
    }
    emit HostWithdrawal(...);
}
```

This is structurally identical to the reported `Financial.fc` bug: the balance check (or absence of one) treats the entire contract balance as spendable, ignoring the portion that is reserved for a different beneficiary (there: commission; here: relayer fees / user refunds attached to in-flight `FeeMetadata` entries). Because the only guard on `amount` is `restrict(_hostParams.hostManager)` — i.e., "did this come from Hyperbridge governance" — and not "is this amount actually free," an over-aggressive or miscalculated withdrawal amount computed off-chain (or a race between fee accrual and a withdrawal being dispatched) can pull the token balance below what's owed to relayers/payers for requests still pending delivery or timeout-refund.

### Impact Explanation
If the withdrawable amount is sized without netting out `_requestCommitments` fees still owed (a value that changes continuously as new requests are dispatched with fees, per `RequestFunded`/`PostRequestEvent`), a subsequent relayer fee claim (`pallet-ismp-relayer`'s `withdraw` → `HostManager.onAccept(Withdraw)` → `EvmHost.withdraw`) or a request timeout refund can fail or, in the worst case, race such that the last relayer/payer to claim finds insufficient `feeToken` balance in the host — a loss/lock of user- or relayer-owed funds. This falls squarely in the bounty's "stealing or loss of funds" / "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" category, since the escrowed fee is economically the relayer's/payer's money sitting in the host contract, not ungated protocol revenue.

### Likelihood Explanation
This requires no malicious peer, relayer, or prover — the withdrawal amount is computed and dispatched from `pallet-ismp-host-executive` by governance/root origin (`T::HostExecutiveOrigin`), so exploitation depends on that off-chain/on-chain accounting correctly tracking "free" balance. I could not find, in the code reachable from this repo, any explicit invariant in either `pallet-ismp-host-executive` or `EvmHost.sol` that computes `available = balanceOf(feeToken) - sum(unclaimed FeeMetadata fees)` before allowing a withdrawal — the check is entirely absent on-chain, meaning correctness relies solely on off-chain bookkeeping discipline rather than a contract-enforced invariant. That is a real gap, but since the caller of `withdraw` is a privileged/governance path rather than an arbitrary unprivileged actor, likelihood is lower than a fully public-entrypoint bug; it is best framed as a missing on-chain safety invariant rather than an unprivileged exploit.

### Recommendation
Track total outstanding relayer/request fees owed (sum of live `FeeMetadata.fee` for undelivered, non-timed-out requests) in a running on-chain accumulator, and enforce in `withdraw()`:
```solidity
uint256 balance = token == address(0) ? address(this).balance : IERC20(token).balanceOf(address(this));
require(balance - _outstandingFees[token] >= amount, "InsufficientSpendableBalance");
```
so that governance withdrawals can never dip into funds still escrowed for relayers or refundable to users, mirroring the same fix recommended in the original report (make the commission/reserved-funds accounting part of the spendability condition rather than trusting the caller-supplied amount).

### Proof of Concept
Conceptual reproduction path (no live test harness available in this pass to execute it, so this should be validated with a Foundry test against `evm/tests/rust/src/tests/host_manager.rs`'s existing `test_host_manager_withdraw` scaffold):
1. Mint `feeToken` to `EvmHost`, dispatch several outgoing `PostRequest`s with non-zero relayer fees so `_requestCommitments[commitment].fee` sums to `F`, leaving host `feeToken` balance `B = revenue + F`.
2. Have `pallet-ismp-host-executive::withdraw` (or a directly crafted `WithdrawParams`) request `amount = B` (all of it), routed through `HostManager.onAccept` as in the existing `test_host_manager_withdraw` test [4](#0-3) .
3. `EvmHost.withdraw` succeeds and drains the entire balance to `beneficiary`, without reverting despite `F > 0` in un-relayed `_requestCommitments`.
4. A relayer subsequently delivers one of the still-pending requests and attempts to claim its fee via the relayer-fee withdrawal flow (`modules/pallets/relayer/src/withdrawal.rs`) — the destination `EvmHost.withdraw` call for the relayer payout now reverts or under-pays because the `feeToken` balance was already drained in step 3, demonstrating the missing invariant. #[test]
fn test_host_manager_withdraw() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Mint 1000e18 fee tokens to the host
	let amount_to_mint = U256::from(1000u128) * U256::from(10u128.pow(18));
	env.call(env.fee_token, mintCall { to: env.host, amount: amount_to_mint }.abi_encode());
	assert_eq!(host_balance(&mut env), amount_to_mint);

	// Build a withdraw request (body = [0] + abi.encode(WithdrawParams)).
	// Withdraw the fee token (non-zero `token`) — the zero address would be
	// the native-ETH path which this test isn't exercising.
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	// HostManager.onAccept is `restrict(_params.host)` — must call AS the host
	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	env.call_as(host_addr, manager, calldata);

	let withdraw_amount = U256::from(500u128) * U256::from(10u128.pow(18));
	assert_eq!(host_balance(&mut env), amount_to_mint - withdraw_amount);
}

		/// Issues a call to withdraw the protocol fees from an evm chain
		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(4)]
		pub fn withdraw(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			withdrawal_params: WithdrawalParams,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			ensure!(state_machine.is_evm(), Error::<T>::UnsupportedStateMachine);

			let HostParam::EvmHostParam(params) = HostParams::<T>::get(state_machine)
				.ok_or_else(|| Error::<T>::UnknownStateMachine)?;

			let data = withdrawal_params
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidBeneficiaryAddress)?;

			let post = DispatchPost {
				dest: state_machine,
				from: PALLET_ID.to_bytes(),
				to: params.host_manager.0.to_vec(),
				timeout: 0,
				body: data,
			};

			let dispatcher = <T as Config>::IsmpHost::default();

			// Account is not useful in this case
			dispatcher
				.dispatch_request(
					DispatchRequest::Post(post),
					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)
				.map_err(|_| Error::<T>::DispatchFailed)?;

			Self::deposit_event(Event::<T>::Withdraw {
				address: sp_runtime::BoundedVec::truncate_from(
					withdrawal_params.beneficiary_address,
				),
				state_machine,
				amount: withdrawal_params.amount,
			});

			Ok(())
		}
