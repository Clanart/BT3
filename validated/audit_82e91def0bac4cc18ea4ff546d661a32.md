### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise identity in credential trampoline, enabling GitHub token exfiltration - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The reported BGT bug is fundamentally about code trusting an *external, adversarial signal* (a token's whitelist status is not checked before an action that assumes permissiveness) and taking an unsafe action (transferring value) as a result, causing loss/stuck funds. The Desktop analog is `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, which trusts an attacker-suppliable `WWW-Authenticate` header value forwarded by git as a "happy path" to decide whether a remote host is GitHub/GitHub Enterprise, before falling back to the actually-verified `isGitHubHost` API check. This misclassification can steer a real GitHub sign-in/credential flow toward an attacker-controlled endpoint.

### Finding Description
When Desktop's git credential helper trampoline is asked to `get` a credential for a remote, it calls `getEndpointKind`: [1](#0-0) 

Note lines 153-165: any `wwwauth[...]` credential field — which git populates directly from the `WWW-Authenticate` HTTP header returned by the remote server during the authentication handshake — is pattern-matched for `realm="GitHub"` and, if found, the endpoint is unconditionally classified as `'enterprise'`. This check happens *before* the safer, network-verified fallback at line 178 (`isGitHubHost(endpoint)`, which presumably queries the real API to confirm GitHub identity).

Because the `WWW-Authenticate` header is generated by whatever server the git remote/proxy points to, an attacker who controls the destination of a clone/fetch/push (a malicious remote, a compromised/attacker-run HTTP proxy sitting in the request path, or a spoofed internal git host) can freely set `WWW-Authenticate: Basic realm="GitHub"` on their 401 response. This is a value fully attacker-controlled, delivered as ordinary protocol data, requiring no unusual user action beyond adding/using that remote — matching the "attacker controls ... a git remote/proxy response" primitive in the accepted impact list.

Once `getEndpointKind` returns `'enterprise'`, `getCredential` in the same file takes this path: [2](#0-1) 

If no account is already associated with that specific attacker endpoint (line 109-112), and the operation is not a background task, the user is shown `ui.promptForGitHubSignIn(endpoint)` (line 118) — a real GitHub OAuth sign-in flow, but bound to the attacker's endpoint string. If the user completes it (plausibly, since Desktop is now presenting it as a legitimate "sign in to GitHub Enterprise" prompt for a host they were only trying to fetch/clone from), the resulting account is stored and keyed by that same endpoint via `credWithAccount`.

Subsequently, `findGitHubTrampolineAccount` in `app/src/lib/trampoline/find-account.ts` matches stored accounts purely by origin comparison, not by any cryptographic host-identity check: [3](#0-2) 

Any future `get` request for that same attacker origin will now yield `credWithAccount(cred, account)` — which substitutes the real, valid GitHub username/OAuth token into the credential map returned to git (see `credWithAccount` at line 47-48 of `trampoline-credential-helper.ts`), and git will send this as the `Authorization`/Basic-auth header directly to the attacker's server. The invariant broken is: "only a verified GitHub/GHE endpoint may receive the user's real OAuth token via the credential helper" — an unauthenticated, spoofable header is enough to defeat that verification and redirect where a live token gets sent.

### Impact Explanation
If successful, this results in exfiltration of the user's real GitHub OAuth access token to an attacker-controlled server — enabling account takeover, access to private repositories, and further supply-chain or lateral attacks using that token. This matches the report's core theme (an operation proceeds under an incorrect trust assumption about an external actor's classification/permission, causing loss of a sensitive asset) but the Desktop consequence is credential/token exfiltration rather than stuck token balances.

### Likelihood Explanation
Exploitation requires the victim to add or use a git remote pointing at, or be proxied/MITM'd toward, a server the attacker controls (e.g., internal "enterprise-looking" git host, malicious fork remote, or intercepting proxy), and for the user to accept a GitHub sign-in prompt that Desktop itself initiates for that host — this is a normal-seeming Desktop UX flow, not an unnatural step, satisfying the "attacker controls a git remote/proxy response" condition in the accepted impact list. It does not require local/physical access, admin rights, prior malware, or leaked credentials. The primary source of uncertainty is exactly how `promptForGitHubSignIn`/OAuth binds the resulting `Account.endpoint` field and whether the OAuth flow itself sends the endpoint value anywhere that would let a careful user notice the mismatch — this was not fully verifiable from the available index contents.

### Recommendation
Do not use the client-supplied `wwwauth[...]` value as a trust signal for classifying a host as GitHub/Enterprise before performing (or in place of) the authenticated `isGitHubHost` check. At minimum, `getEndpointKind` should always confirm enterprise/GitHub identity via the verified `isGitHubHost` API call (or an equivalent authenticated check) rather than short-circuiting on an easily-spoofed header string. Any sign-in flow triggered as a result of such classification should clearly and unmistakably display the literal remote host/URL being signed in to, and the resulting `Account` binding should be re-validated against `isGitHubHost` before it is ever handed to `credWithAccount` for a `get` request.

### Proof of Concept
1. Attacker sets up an HTTP git server (or MITM proxy) at `https://evil.example.com/attacker/repo.git`.
2. Victim adds/clones this URL in GitHub Desktop.
3. When git attempts authentication, attacker's server responds with `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as a `wwwauth[0]=Basic realm="GitHub"` field to Desktop's credential trampoline.
5. `getEndpointKind` (lines 157-165 of `trampoline-credential-helper.ts`) matches `realm="GitHub"` and returns `'enterprise'` without any network verification.
6. Because no account exists for `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)` for that endpoint (line 118).
7. Victim, trusting the Desktop-native "Sign in to GitHub" dialog, authenticates with their real GitHub account.
8. The resulting account is bound to `evil.example.com`'s origin; on the next `get` credential request for that origin, `findGitHubTrampolineAccount`/`credWithAccount` return the victim's real GitHub login and OAuth token, which git sends to the attacker's server as Basic auth credentials.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
