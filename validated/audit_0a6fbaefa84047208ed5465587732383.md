### Title
Position-blind splicing of AI-resolved conflict hunks can silently misassign resolved content in committed files - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`reassembleResolvedFile` rebuilds the final file to be written/committed by scanning the raw on-disk content for conflict-marker patterns and splicing in the model's per-hunk resolutions strictly by order of appearance, not by any positional/identity check tying a resolution back to the specific marker block it was generated for.

### Finding Description
`reassembleResolvedFile` walks `rawContent` line by line and, on finding a line matching `reassemblyOursMarker` (`/^<{7}(?:\s|$)/`), looks ahead for a `=======` separator and a `>>>>>>>` closer. [1](#0-0) 
If that lookahead succeeds, it is treated as a real conflict block, the block is skipped, and `hunkResolutions[hunkIndex]` is spliced in, with `hunkIndex` incremented unconditionally — this is explicitly "matched by order, not by line number" per the function's own documentation. [2](#0-1) 

The only safety check upstream, `validateResolutionPaths`, verifies that the *number* of hunks returned by the model equals the *number* of hunks the app extracted from context (`expectedFiles`), but does no positional/content verification that the Nth hunk in the model's response corresponds to the Nth marker block this naive scanner will find. [3](#0-2) 

Because the marker-detection regexes only require the 7-character marker sequences on their own line, any repository-controlled file whose ordinary content happens to contain lines shaped like `<<<<<<< ...`, `=======`, `>>>>>>> ...` (e.g. documentation of git conflict resolution, diff/patch fixtures, ASCII banners, or a file that legitimately teaches merge conflicts) will be interpreted by the scanner as an additional real conflict block if it also has a genuine conflict elsewhere in the same file. This shifts `hunkIndex` for every subsequent legitimate conflict, so the model's resolution for hunk *N* gets spliced into the position of a different, unrelated hunk. The function's own "malformed marker" fallback only protects against unclosed marker sequences — it does nothing to detect a marker-shaped false positive that happens to have a well-formed triplet.

### Impact Explanation
This directly matches the "silent corruption of what the user commits" class from the report: the user asks Copilot to resolve merge conflicts, sees a resolution result, and — if the count validation passes (which it will, since counts aren't affected, only order/position) — the wrong resolved hunk content is written into the file and subsequently staged/committed via the normal write path, with no error surfaced. The attacker's leverage is a crafted file (in a branch/fork merged by the victim) containing marker-shaped lines mixed with a real, unrelated conflict — a scenario fully reachable from a remote/cloned repository the victim merges, matching the "attacker controls a cloned/fetched repository" criterion.

### Likelihood Explanation
Likelihood is constrained by needing: (1) a file with both a genuine conflict and marker-shaped decoy text, and (2) the user invoking the Copilot conflict-resolution feature on that file. This is a real but narrow path — it requires the AI-assisted conflict resolution feature to be used, and I was unable to fully verify (context window exhausted) whether `copilot-conflict-context.ts`'s hunk-extraction logic (which builds `expectedFiles`) uses the exact same naive regex scan or a more precise git-based extraction; if the two use different logic (which the separate, duplicated marker regexes in each file suggest), the divergence described above is real and unguarded. This uncertainty about the exact extraction algorithm in `copilot-conflict-context.ts` is a gap I could not close given tool limits.

### Recommendation
Tie each `IHunkResolution` to a stable identifier (e.g. the line range or a content hash of its `oursContent`/`theirsContent` from the same extraction pass used to build `expectedFiles`) rather than relying on array order, and have `reassembleResolvedFile` match resolutions against that identifier instead of positional index. Additionally, reuse the exact same marker-scanning routine for both extraction (`copilot-conflict-context.ts`) and reassembly (`copilot-conflict-resolution.ts`) so the two can never diverge on what counts as a conflict block.

### Proof of Concept
1. Create a file `README.md` containing an unrelated real merge conflict plus a documentation block that itself contains a literal example of conflict markers, e.g.:
```
<<<<<<< HEAD
actual ours change
=======
actual theirs change
>>>>>>> feature

Example of a conflict marker for documentation purposes:
<<<<<<< HEAD
example ours
=======
example theirs
>>>>>>> example
```
2. Trigger a real merge that produces exactly one genuine conflict elsewhere in the file (so `expectedFiles` hunk count = 1), while the documentation block above is *not* part of an active git conflict but still matches the marker regexes verbatim.
3. `reassembleResolvedFile`'s naive scan will detect two well-formed marker blocks (the real one and the documentation example), assign the model's single resolution to `hunkIndex === 0` (the first block found, potentially the doc example if it appears earlier in the file) and drop/duplicate content for the real conflict, resulting in the committed file having incorrect content that the model never actually intended to produce for that location — with no error shown to the user since `validateResolutionPaths` only checks the hunk *count* (1 == 1), not position.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
