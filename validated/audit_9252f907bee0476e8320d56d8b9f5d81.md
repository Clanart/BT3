Unauthenticated `address` field in `pallet-state-coprocessor::handle_get_requests` lets anyone mint arbitrary Reputation Asset, corrupting collator/validator selection - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`pallet_state_coprocessor::Pallet::handle_get_requests` mints Hyperbridge's `ReputationAsset` to whatever 32-byte `address` is supplied inside the unsigned `GetRequestsWithProof` payload, with no cryptographic binding between that address and any real relayer identity or actual message signer. [1](#0-0)  Unlike the sibling `pallet-messaging-incentives`, which recovers the crediting account from an sr25519 signature over the delivered message, this pallet trusts a raw, unverified byte field. [2](#0-1)  Because `ReputationAsset` is the sole ranking metric `pallet-collator-manager` uses to select the block-producing collator set each session, an attacker can inflate their own reputation balance and get selected as a Hyperbridge collator without ever having relayed anything on anyone's behalf.

### Finding Description
`handle_get_requests` is reachable through the unsigned extrinsic `handle_unsigned` (`ensure_none(origin)`) and equally through `validate_unsigned`, both of which dispatch straight into `Self::handle_get_requests(message)` with no signature check tying the caller to the `address` field. [3](#0-2) 

The function:
1. Verifies the supplied `source` membership proof and `response` state proof for the batch of `GetRequest`s — this proves the *requests* and their *results* are real, but says nothing about who is entitled to the reward. [4](#0-3) 
2. Sums the abi-encoded response size into `total_bytes`. [5](#0-4) 
3. Mints `rate * total_bytes` of `ReputationAsset` directly to `bytes32::from(address)`, where `address` is copied verbatim from the caller-supplied struct. [1](#0-0) 

Nothing in the pipeline recovers `address` from a signature over the request/response payload the way `pallet_messaging_incentives::Pallet::relayer_for` does for POST message delivery. [6](#0-5)  The `validate_unsigned` dedup tag is derived only from the request commitments, not from `address`, so the same legitimate proof data can be resubmitted with a different `address` value by anyone who can reconstruct it (state proofs for already-finalized chain state are public data, requiring no privileged relayer key). [7](#0-6)  The only defenses that exist (timeouts, per-request dedup, duplicate-response check) constrain which *requests* can be re-served, not who gets credited for serving them. [8](#0-7) 

`ReputationAsset` is not a cosmetic counter. `pallet-collator-manager::new_session` ranks all controller accounts strictly by their `ReputationAsset` balance and selects the top N as the new collator set each session. [9](#0-8)  Documentation confirms Reputation Asset "mirrors your $BRIDGE earnings 1:1" and "is the primary factor in Collator selection." [10](#0-9) 

### Impact Explanation
This breaks the "reward claims ... must move exactly once and only to the rightful beneficiary" invariant: the beneficiary of the mint is entirely attacker-chosen and unverified. Because Reputation Asset directly drives collator (block-producer) selection, an unprivileged actor who can construct or reuse a legitimate `GetRequestsWithProof` (state proofs for already-finalized public chain state, requiring no special relaying infrastructure or private key) can repeatedly mint reputation to a controller account they control, artificially outrank honest operators, and get seated as a Hyperbridge collator. This is a path from an unprivileged, unsigned on-chain call to unauthorized block-production privilege — a form of unauthorized execution/logic attack on host-management (collator set) that does not require a malicious relayer, prover, or governance actor; it only requires exploiting the missing authentication in this specific pallet call.

### Likelihood Explanation
Medium-to-high. The call is `ensure_none` (fully unsigned/permissionless), the `address` field is not covered by any signature or proof, and constructing valid `GetRequestsWithProof` data does not require being a genuine registered relayer — only access to public source/destination chain state and the ability to build the membership/state proofs the coprocessor already verifies. The mint amount scales with response byte size and `MintPerByte`, both of which are governance-controlled but nonzero in production configurations that intend to reward relayers, meaning the incentive to abuse this path exists wherever the feature is active.

### Recommendation
Bind the credited account to a verified identity the same way `pallet_messaging_incentives::relayer_for` does: recover the account from an sr25519 (or equivalent) signature over the `GetRequestsWithProof` payload (or over `hash(requests, response)`), and use the recovered signer as the mint target instead of trusting the caller-supplied `address` field. If backward compatibility with the existing wire format is required, at minimum add a `signature` field to `GetRequestsWithProof`, verify it inside `handle_get_requests`/`validate_unsigned`, and reject the call if the derived signer does not match `address`.

### Proof of Concept
1. Observe (via public RPC) a finalized `GetRequest`/response pair for any registered source/dest chain pair supported by Hyperbridge, along with the corresponding membership and state proofs — no relayer key or privileged access is required since this data is public.
2. Construct `GetRequestsWithProof { requests, source, response, address: <attacker_controller_account> }` and submit it as an unsigned transaction via `pallet_state_coprocessor::Pallet::handle_unsigned` (or let it pass `validate_unsigned`).
3. `handle_get_requests` verifies the (real, valid) proofs, computes `total_bytes`, and mints `rate * total_bytes` of `ReputationAsset` directly to `attacker_controller_account`, per `modules/pallets/state-coprocessor/src/impls.rs:157-169`, with no check that the attacker delivered anything or is a registered relayer.
4. Repeat with fresh (or independently-reconstructed) request/response batches, each time crediting the same attacker-controlled controller account.
5. At the next session boundary, `pallet_collator_manager::new_session` reads `T::ReputationAsset::balance(&controller_account)` for all bonded candidates and ranks them highest-first; the attacker's inflated balance can outrank legitimate operators and get the attacker's Stash/Controller pair selected into the collator set, per `modules/pallets/collator-manager/src/lib.rs:514-542`.

	fn relayer_for(message: &Message) -> Option<T::AccountId> {

				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
