### Title
Stale line-selection indices applied to a re-fetched working-directory diff can silently corrupt partial commits - ([File: app/src/lib/git/apply.ts])

### Summary
`WorkingDirectoryFileChange.selection` (a `DiffSelection`) stores *absolute line indices* computed against a specific diff that was rendered in the UI. When the user actually commits, `stageFiles` → `applyPatchToIndex` independently re-fetches a **fresh** diff from the working tree at commit time and blindly re-applies the old, index-based selection to it, with no check that the diff hasn't changed shape since the user made their selection.

### Finding Description
The commit flow works like this:

1. The UI loads a diff (`getWorkingDirectoryDiff`) and lets the user select individual lines/hunks. The selection is stored as a `DiffSelection`, which tracks *diverging line numbers* relative to hunk `unifiedDiffStart` offsets, not the actual line content. [1](#0-0) [2](#0-1) 

2. When the user commits, `_commitIncludedChanges` takes the `WorkingDirectoryFileChange[]` straight from cached state (with their stored `selection`) and calls `createCommit` without re-validating the selection against the current on-disk content. [3](#0-2) 

3. `createCommit` → `stageFiles` → `applyPatchToIndex` then does its own **independent** re-fetch of the diff via `getWorkingDirectoryDiff(repository, file)` (line 60), and immediately runs `formatPatch(file, diff)` which walks the **new** diff's hunks and checks `file.selection.isSelected(absoluteIndex)` using the **old** selection's index space. [4](#0-3) [5](#0-4) 

There is no re-validation step in this path comparable to the one Desktop does elsewhere when it detects a diff has changed mid-flight (e.g. the stash-diff handler explicitly bails out if state changed during the async load, and another code path recomputes `selectableLines` to prune stale selections after a diff reload): [6](#0-5) [7](#0-6) 

Neither of those guards is invoked in the actual staging/commit path (`stageFiles`/`applyPatchToIndex`). If a tracked file's content changes between the moment the user reviewed/selected specific lines in the diff viewer and the moment `applyPatchToIndex` re-diffs the file, the hunk boundaries and `unifiedDiffStart` offsets shift. The stale `divergingLines` set from the old selection is then matched against different line indices in the new diff, so `formatPatch` can select the wrong lines — including lines the user never reviewed or excluding ones they intended to commit — and `git apply --cached` stages that mismatched patch silently (no error, since the patch is syntactically valid against the new working tree).

This is structurally the same class of bug as the Lido report: a value (`unaccountedEth` / the line-selection index space) is computed **before** an operation that can change the underlying state (the `StakingRouter.deposit` call / a working-tree mutation), and is then used **after** that operation without being recomputed or revalidated, leading to silent state corruption instead of the intended, reviewed result.

### Impact Explanation
The corrupted value is exactly "what the user commits" — the staged content in the index no longer matches the diff the user actually reviewed and consciously selected in the Changes/partial-commit UI. This can cause a developer to unknowingly commit and push content they never approved (or omit content they meant to include), which is explicitly called out as valid impact ("silent corruption of what the user commits or pushes"). Because `git apply --cached` succeeds without error as long as the patch is structurally valid against the new tree, there is no user-visible signal that the commit differs from what was reviewed.

### Likelihood Explanation
Exploitation requires that the tracked file's content change between the diff render and the staging step, which is a narrow timing window and depends on some other actor/process modifying files inside the working directory during that window (e.g., a repository-configured hook run by another concurrent Git operation, or an automated tool acting on the repo). This is not attacker-controlled to the same degree as a straightforward remote-content injection, so likelihood is moderate rather than high — it depends on a race condition rather than a fully deterministic trigger.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, re-fetch the diff and re-validate (or recompute) the selection against the freshly fetched hunks — reusing the same "selectable lines" reconciliation logic already implemented in `app-store.ts` — and abort/re-prompt the user if the diff has materially changed (e.g., compare a hash of the diff or hunk count/offsets) rather than silently applying a stale selection to new content.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`, producing a diff with two hunks.
2. In the Changes tab, select only specific lines in hunk #2 (partial selection), but don't click "Commit" yet.
3. While the commit dialog/selection is pending, have some other process/hook running against the same working tree prepend or remove lines earlier in `file.txt`, shifting hunk #2's `unifiedDiffStart` offset in a subsequent `git diff`.
4. Click "Commit". `applyPatchToIndex` re-diffs the file (new hunk layout) and applies the old `DiffSelection`'s absolute indices to it via `formatPatch`, producing a patch that stages different lines than the ones the user selected in step 2.
5. Inspect the resulting commit: it contains lines the user never selected/reviewed, with no warning from Desktop.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
