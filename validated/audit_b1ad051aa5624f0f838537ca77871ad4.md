### Title
Value sent to distribution precompile's `rewards()` view method is permanently stranded, since it is the one query the ABI dispatcher does not reject as non-payable and it performs no fund transfer or refund - ([File: precompiles/distribution/distribution.go])

### Summary
The `rewards()` query on the distribution precompile (`0x0000000000000000000000000000000000001007`) is dispatched without a `pcommon.ValidateNonPayable(value)` guard, unlike other query/transaction methods in the same `Execute` switch. Any caller who sends `msg.value` along with a `rewards()` call causes that value to be accepted by the EVM as a successful transfer to the precompile address, while the executor performs no logic to forward, refund, or otherwise account for the transferred value.

### Finding Description
In `precompiles/distribution/distribution.go`, the `Execute` dispatcher explicitly calls `pcommon.ValidateNonPayable(value)` before running `WithdrawValidatorCommissionMethod`, but there is no equivalent check before `case RewardsMethod: return p.rewards(ctx, method, args)`. [1](#0-0) 

This is a known, explicitly documented quirk in the test suite: the accompanying integration spec states "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds), so this spec deliberately has no 'view rejects value' test." [2](#0-1) 

Because `rewards()` is reachable through a plain EVM `CALL` with nonzero `value` (directly from an EOA or via any intermediary contract, e.g. the test's `PrecompileCaller.callTarget` pattern which forwards `msg.value`), a value-bearing call succeeds at the EVM level (the precompile "address" absorbs the transferred usei/wei balance in the EVM StateDB) while `p.rewards()` itself only queries delegation rewards and returns data — it neither reverts on nonzero value nor moves the received value anywhere. [3](#0-2) 

Unlike an ordinary Solidity contract with a `receive()`/`fallback()`, a Cosmos precompile has no associated contract bytecode or owner-controlled sweep function; there is no equivalent to `InfiltrationPeriphery`'s missing withdraw function that could ever be added at the precompile "address" to later recover value credited there, since precompile addresses are not typical accounts with spendable balances tracked by application logic — the usei that lands there via the EVM value-transfer semantics has no code path defined anywhere in the module to move it back out.

### Impact Explanation
Any native token (usei/wei) sent as `value` in a `rewards()` call is permanently locked — there is no withdrawal, sweep, or refund mechanism for value accidentally or unknowingly delivered to the distribution precompile address through this specific query method. This matches the "permanent freezing of funds" impact class: an unprivileged EVM caller (EOA or contract) can trigger fund loss with a single transaction by mistakenly attaching value to a `rewards()` call (e.g., wallets/dApps that always attach `msg.value` uniformly across precompile calls, or a user manually crafting a call with value).

### Likelihood Explanation
Likelihood is moderate: `rewards()` is a commonly-called read method on a well-known, canonical precompile address, and many other methods on the same precompile (e.g., `withdrawValidatorCommission`) do enforce non-payable, creating an inconsistent surface where a caller might reasonably (but incorrectly) assume `rewards()` also handles or rejects value. The bug is only triggered by an explicit, non-zero `msg.value` on this specific selector, so it depends on caller behavior/tooling rather than being automatically exploitable against unaware users, but requires no special privilege, precompile-internal state, or race condition to trigger.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` (or the equivalent check) to the `RewardsMethod` case in `Execute`, consistent with the other query and transaction methods in `precompiles/distribution/distribution.go`, `precompiles/distribution/legacy/v640/distribution.go`, and other precompile versions with this dispatcher shape, so that a value-bearing call to `rewards()` reverts instead of silently stranding funds. The same audit should be extended to any other precompile "view" methods across the codebase that might have been given the same read-only treatment without the corresponding non-payable guard.

### Proof of Concept
1. From an EOA (or via `PrecompileCaller.callTarget`), submit a transaction calling `rewards(address)` on `0x0000000000000000000000000000000000001007` with `value: ethers.parseEther("1")`. [4](#0-3) 
2. Observe the transaction succeeds (status = 1) and returns the expected reward data, because `Execute` routes straight to `p.rewards(ctx, method, args)` without checking `value`. [3](#0-2) 
3. Confirm the 1 SEI sent as value is deducted from the caller's balance but never credited to any withdrawable account — no `Rewards`/`Withdraw` event moves it, and no subsequent call on the distribution precompile (or any other precompile) can retrieve it, since no code path exists that consumes value delivered to this address via `rewards()`.
