I found a strong analog. GitHub Desktop's clone implementation explicitly **disables** a built-in Git security protection that exists specifically to stop a known repository-triggered RCE, mirroring the "missing validation of an untrusted, attacker-supplied value" pattern in the Sherlock finding.

### Title
Clone operation disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard, re-opening a known clone-time RCE against malicious repositories - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for every `git clone` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [1](#0-0) . `GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to gate the "clone protections" that block a maliciously crafted repository from smuggling files/hooks across the `.git` directory boundary during clone (the class of fix shipped for the CVE-2024-32004-style clone-time arbitrary file write/RCE issue). By forcing this to `'false'` on every clone, Desktop actively opts every user out of that protection.

### Finding Description
Just like the Sherlock finding where `matchOrder` accepted attacker-influenced values (`collateral`, `premium`) without validating them against a trusted invariant, Desktop's `clone()` accepts a completely untrusted, attacker-controlled input — the remote repository content itself — and does not let Git apply its own validation of that content during checkout/recursive-submodule-clone. The `url` and resulting repository tree are fully controlled by whoever hosts the remote (any public git host, or a malicious server behind a "Clone repository" URL). Git's own protection (enabled by default in modern Git via `clone.protectHFS`, `clone.protectNTFS`, and hardened checkout-boundary checks) is toggled by `GIT_CLONE_PROTECTION_ACTIVE`; unconditionally forcing it off in `envForRemoteOperation`'s composed environment removes this defense-in-depth layer for literally every clone Desktop performs, including the `--recursive` submodule fetch that happens on the same call [2](#0-1) .

This is analogous to `checkIsValidOrder` failing to check `collateral`/`premium` — the surrounding code (`isClonePathSensitive`) does add a *destination*-path safety check [3](#0-2) , but there is no equivalent guard for the *content* being cloned; the app instead removes Git's own guard for that content path.

### Impact Explanation
An attacker who controls a repository that a Desktop user opens via "Clone repository" (from GitHub.com, a URL, or an `x-github-client://openRepo/...` deep link routed through `openOrCloneRepository`/`clone` [4](#0-3) ) can craft the repository tree/submodules to exploit whatever clone-time boundary check `GIT_CLONE_PROTECTION_ACTIVE` was meant to enforce. Depending on the underlying Git version, disabling this protection during `clone --recursive` can result in writes outside the intended repository directory (e.g., via crafted submodule paths/hooks), which is a file-write-outside-repo / code-execution primitive — squarely within the accepted impact categories (attacker-controlled cloned repository leading to file write outside the repo or code execution).

### Likelihood Explanation
Likelihood is high for any user who clones an untrusted repository through Desktop, since this environment variable is set on *every* clone unconditionally, with no opt-out, no allowlist, and no compensating check on the cloned content. Unlike the destination-path check, there's no test coverage validating repository *content* safety, only clone *destination* safety (`app/test/unit/git/clone-test.ts`, `app/test/unit/clone-path-safety-test.ts`).

### Recommendation
Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override, or scope it narrowly with a documented, safe justification if it exists. If the override was added to work around a benign Git prompt/behavior, replace it with a targeted mitigation that doesn't blanket-disable the clone-time boundary protection — e.g., only disable it for verified same-origin GitHub.com clones, and keep it enabled for arbitrary/generic URLs and deep-link-initiated clones.

### Proof of Concept
1. Attacker hosts/publishes a git repository crafted to trigger the specific clone-boundary condition that `GIT_CLONE_PROTECTION_ACTIVE` guards against (e.g., a submodule/hook layout designed to escape the intended working directory during recursive clone).
2. Victim clicks a link (or uses "Clone repository" in Desktop UI) pointing at that repository URL; this flows through `openOrCloneRepository` → `CloneRepository` popup → `dispatcher.clone(url, path, ...)` → `clone()` in `app/src/lib/git/clone.ts`.
3. `clone()` spawns `git clone --recursive ... -- url path` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment [5](#0-4) .
4. Because Git's clone-time protection is disabled, the malicious repository content is processed without the safeguard that would otherwise reject/neutralize it, leading to the underlying protection's bypass (file write outside repo root or hook execution, depending on Git version behavior).

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
