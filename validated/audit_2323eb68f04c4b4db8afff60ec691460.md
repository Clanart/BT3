### Title
Permissionless registration of a self-destructible ERC20 contract permanently freezes/destroys wrapped-coin holders' redemption rights - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`RegisterERC20` in the `x/erc20` module allows **any account** (when `PermissionlessRegistration` is `true`) to register an arbitrary external ERC20 contract as a `TokenPair`, creating a bidirectional 1:1 wrapping between a synthetic bank `Coin` and the real ERC20 token, with the ERC20 module acting as custodian of the real ERC20 tokens escrowed at `types.ModuleAddress`. If the registered contract is later self-destructed (a capability entirely controlled by its external deployer/owner), both `ConvertERC20` and `ConvertCoin` silently no-op and delete the `TokenPair` record instead of erroring, permanently orphaning any escrowed ERC20 reserve and rendering any outstanding wrapped `Coin` balance permanently unredeemable — with no admin/governance action required at all.

### Finding Description
`RegisterERC20` [1](#0-0)  permits permissionless registration of external ERC20 contracts:
```
if !params.PermissionlessRegistration {
    if err := k.validateAuthority(req.Signer); err != nil { ... }
}
```
The resulting `TokenPair` is created with `types.OWNER_EXTERNAL` [2](#0-1) , meaning the attacker fully controls the contract's bytecode/logic, including any self-destruct pathway they choose to embed and later trigger unilaterally.

Once registered, users can convert real ERC20 balance into a synthetic bank `Coin` via `ConvertERC20` (escrows ERC20 tokens to the module address, then `MintCoins`) [3](#0-2) , and convert the `Coin` back into ERC20 via `ConvertCoin`/`ConvertCoinNativeERC20` (burns the `Coin`, unescrows real ERC20 tokens back to the user) [4](#0-3) . This makes the module-held ERC20 balance the actual 1:1 backing reserve for all outstanding wrapped `Coin` supply.

Both conversion entry points contain the exact same "self-destruct" bypass, which — instead of reverting — **silently succeeds without performing any conversion and deletes the token-pair mapping**:
```
acc := k.evmKeeper.GetAccountWithoutBalance(ctx, pair.GetERC20Contract())
if acc == nil || !acc.HasCodeHash() {
    k.DeleteTokenPair(ctx, pair)
    ...
    return nil, nil   // <-- treated as success, no error surfaced
}
``` [5](#0-4) [6](#0-5) 

Once the token pair is deleted, `GetTokenPairID`/`GetTokenPair` no longer resolve the denom, so there is **no remaining code path** by which a holder of the wrapped `Coin` denom (`erc20/<contract>`) can ever redeem it for the real ERC20 tokens sitting in the module's escrow — the reserve is orphaned and the outstanding `Coin` supply becomes permanently worthless, non-burnable, non-convertible spendable value.

The attack sequence is fully unprivileged:
1. Attacker deploys a malicious ERC20 contract with an owner-gated self-destruct function.
2. Attacker calls `MsgRegisterERC20` (permissionless) to register it as a `TokenPair`.
3. Victims acquire the ERC20 token (e.g., via a DEX, airdrop, or direct transfer) and call `ConvertERC20` to wrap it into the bank `Coin`, escrowing real tokens into the module reserve.
4. Attacker self-destructs the contract.
5. Any victim who still holds the wrapped `Coin` (or later tries to redeem) finds `ConvertCoin` returns success with `nil, nil` but performs no unescrow/burn — the `TokenPair` is deleted and the funds are unreachable. Existing `Coin` balances remain in victims' wallets but are permanently un-spendable for their intended (redeemable) purpose, and the ERC20 reserve is permanently locked in the module account with no code path to reach it.

This mirrors the seed report's invariant exactly: a state-machine transition ("disable"/tear down a market or, here, a token-pair mapping) is performed without checking for outstanding open exposure (open positions ↔ outstanding wrapped-coin/escrowed-reserve balances), permanently harming holders who have no recourse — except here the trigger requires no privileged/governance actor at all, only the attacker's own contract self-destruct, satisfying the unprivileged-trigger requirement more strongly than the original report.

### Impact Explanation
This is a critical, permanent freezing/loss-of-value bug: legitimate holders of a wrapped `Coin` denomination lose the ability to ever redeem their tokens once the backing ERC20 contract is destroyed, and the ERC20 reserve escrowed at the module address becomes permanently orphaned/unreachable. This falls squarely under "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... token-pair-backed balances," since the 1:1 accounting invariant between the native `Coin` and the ERC20 representation is irrecoverably broken with no admin remedy (the mapping itself is deleted, so even governance cannot re-enable/re-point it back to a working state).

### Likelihood Explanation
Likelihood is high in any deployment with `PermissionlessRegistration = true` (the module explicitly documents and tests this as a supported permissionless mode [7](#0-6) ). An attacker only needs to deploy one malicious contract, register it, wait for organic conversions, then self-destruct — no special privileges, timing races, or governance cooperation required. Even without malicious intent, any external ERC20 contract's owner exercising a legitimate upgrade/kill-switch pattern (common in many token designs) would trigger the same permanent-loss condition for wrapper-`Coin` holders.

### Recommendation
- Do not silently succeed (`return nil, nil`) and delete the `TokenPair` when the underlying contract is missing/self-destructed. Instead, either revert the conversion with an explicit error, or add an explicit, auditable "abandoned pair" recovery/refund mechanism that reconciles outstanding `Coin` supply against the (now-lost) reserve before deletion.
- Before allowing `DeleteTokenPair` on a self-destructed contract, check `bankKeeper.GetSupply(ctx, pair.Denom)`; if nonzero, block deletion (or require a governance-supervised migration/refund process) rather than orphaning the mapping.
- Consider disallowing permissionless registration of contracts capable of self-destruct, or require contracts to pass a bytecode/behavioral check (no `SELFDESTRUCT` opcode) before permissionless registration.

### Proof of Concept
Not executed (no test harness run in this session); however, the exact vulnerable branch is directly reproducible using the repository's own existing test scaffolding, which already demonstrates the "self-destructed contract" scenario for IBC callbacks [8](#0-7) . The equivalent scenario for the direct `MsgConvertCoin`/`MsgConvertERC20` path can be constructed as:
1. `s.setupRegisterERC20Pair` with `PermissionlessRegistration = true` and a non-governance signer.
2. Mint/transfer ERC20 tokens to a victim; victim calls `ConvertERC20` to wrap into `Coin` (escrows tokens at `types.ModuleAddress`).
3. Call `s.network.App.GetEVMKeeper().DeleteAccount(ctx, contractAddr)` to simulate self-destruct (as done in the existing IBC callback tests).
4. Have the victim call `ConvertCoin` to redeem their `Coin` back to ERC20 — observe the call returns `nil, nil` (success) per `x/erc20/keeper/msg_server.go` lines 209-220, no `MsgConvertCoinResponse` side effects occur, `bankKeeper.GetBalance` for the `Coin` denom remains unchanged (not burned), and `GetTokenPair` subsequently returns not-found — proving the wrapped balance is now permanently stranded with no valid redemption path.

		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

// ConvertCoinNativeERC20 handles the coin conversion for a native ERC20 token
// pair:
//   - escrow Coins on module account
//   - unescrow Tokens that have been previously escrowed with ConvertERC20 and send to receiver
//   - burn escrowed Coins
//   - check if token balance increased by amount
//   - check for unexpected `Approval` event in logs
func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}

func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
