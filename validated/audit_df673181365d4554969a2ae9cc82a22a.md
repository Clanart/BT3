### Title
Copilot conflict-resolution reassembly validates hunk **count** but not hunk **identity/order**, allowing silent misapplication of resolved content to the wrong conflict block - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`validateResolutionPaths` only asserts that the number of hunks returned by the LLM equals the number of hunks the app expected for a file. `reassembleResolvedFile` then splices resolutions back into the on-disk file purely by positional order, with no verification that hunk `N` in the model's response corresponds to conflict marker block `N` on disk. If the two independent walks over the file (the one that built the prompt/expected-hunk-count, and the one that reassembles the final file) ever disagree about where conflict blocks start and end for the same count, resolved text is spliced into the wrong location - producing a file that looks fully resolved (no conflict markers, correct hunk count, valid JSON) but contains silently swapped/misplaced content that Desktop then stages and lets the user commit and push.

### Finding Description
`validateResolutionPaths` enforces exact equality between `resolution.hunks.length` and `expectedHunkCounts.get(resolution.path)`: [1](#0-0) 

This is a count-only check - the C4 report's `swap_2` bug is a strict equality assertion on a *value* (`interim_usdc_out == interim_usdc_in`) that can legitimately diverge and cause a revert; here the analog is a strict equality check on a *count* that can pass even when the underlying identities diverge, since count equality does not imply positional correspondence.

`reassembleResolvedFile` is explicit that it matches by **order, not by line number or identity**, and it has a special case: a `<<<<<<<`-looking line that isn't followed by a `=======` and `>>>>>>>` before EOF is treated as ordinary content (not a conflict) and does **not** advance `hunkIndex`: [2](#0-1) 

The expected hunk count consumed by `validateResolutionPaths` comes from `IFileConflictContext.hunks.length`, which is built earlier by the context-gathering code (`copilot-conflict-context.ts`, not fully inspected in this session) when it extracts hunks to build the "Conflict 1 of N" prompt text referenced in the system prompt: [3](#0-2) 

If a repository under conflict resolution contains a file whose content includes marker-like lines that the context-builder's hunk-detection classifies differently than `reassembleResolvedFile`'s marker-detection (e.g. a malformed/partial `<<<<<<<` block embedded in legitimate file content, such as a fixture or documentation file about git conflict markers, alongside a real conflict elsewhere in the file), it is possible for the *total hunk count* to still match while the *positional mapping* between "hunk index in the LLM response" and "conflict block on disk" no longer lines up 1:1. Because `validateResolutionPaths` only ever compares counts, this divergence is never detected, and `reassembleResolvedFile` will happily splice hunk `i`'s resolved text into whatever conflict block it is currently at, which may not be the block the model actually resolved.

### Impact Explanation
This is a silent-corruption bug in exactly the category the assignment calls out as valid: "silent corruption of what the user commits or pushes." The user runs a merge/rebase/cherry-pick against a repository whose content an attacker controls (a malicious branch, fork, or fetched remote), invokes Copilot conflict resolution, and Desktop writes back a file that passes every existing validation (no leftover conflict markers, correct file paths, correct hunk counts, non-empty reasoning) yet contains resolved code spliced into the wrong location relative to the surrounding, unrelated code. The user then stages and commits (and potentially pushes) that corrupted file believing it was correctly merged, since the dialog and validation layer report success.

### Likelihood Explanation
This requires a fairly specific file shape (marker-like content combined with a real conflict in the same file) and depends on the exact hunk-splitting regexes in `copilot-conflict-context.ts` disagreeing with those in `reassembleResolvedFile`, which I could not confirm within this session's tool budget. I flag this as **uncertain/needs verification** rather than a confirmed exploit: the two marker regexes I did see (`reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`) are reasonably strict, so a full proof-of-concept requires inspecting `copilot-conflict-context.ts`'s hunk extraction to show a concrete case where "well-formed count" diverges from "well-formed position." Without that confirmation, this should be treated as a design weakness (missing positional/content-anchored validation) rather than a proven, reproducible corruption bug.

### Recommendation
Replace count-only validation with a positional/content-anchored check: instead of matching hunks purely by array order, anchor each resolution to a stable identifier for its conflict block (e.g., a hash of the original `oursContent`/`theirsContent`/surrounding context, or explicit line-range markers) and verify that identifier at reassembly time, not just the total count. If anchoring is infeasible, at minimum have `reassembleResolvedFile` and the context builder share a single hunk-detection implementation so they can never disagree about what constitutes a conflict block for the same file content.

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
