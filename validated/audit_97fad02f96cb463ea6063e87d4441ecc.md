## Analysis

The underlying bug class in the report is a **TOCTOU / non-atomicity between two independent operations that read-then-write shared state**, with no coordination or revalidation, leading to loss/corruption of data. The closest structural analog in GitHub Desktop is in the partial-commit ("stage selected lines") pipeline, where the diff a user reviews and selects lines against is **not the same diff instance** that is later used to build the actual patch applied to the git index.

### Title
Silent corruption of partial commits via line-index-based selection replayed against a freshly re-fetched diff (TOCTOU) - ([File: app/src/lib/git/apply.ts])

### Summary
`file.selection` (the set of lines a user checked in the Changes view) is stored as a set of **absolute line indices**, not content-addressed positions. When Desktop stages a partial commit, `applyPatchToIndex` independently re-fetches a brand-new diff from disk and blindly reapplies the stale index-based selection to it, with no validation that the new diff's line layout still matches what the user actually reviewed.

### Finding Description
When a user selects a file in the Changes view, `updateChangesWorkingDirectoryDiff` loads a diff and stores line selection state keyed by `absoluteIndex` (`h.unifiedDiffStart + index`) [1](#0-0) . The code comment itself acknowledges this is a known weak point: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines"* [2](#0-1) .

When the user commits, `_commitIncludedChanges` synchronously snapshots `state.changesState.workingDirectory.files` and their `.selection`, then asynchronously calls `createCommit` [3](#0-2) . `createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex` [4](#0-3) [5](#0-4) .

Crucially, `applyPatchToIndex` does **not** reuse the diff the user actually looked at — it independently re-fetches the diff from disk at staging time: `const diff = await getWorkingDirectoryDiff(repository, file)` [6](#0-5) . That freshly-fetched diff is then passed into `formatPatch`, which decides what to include per line purely via `file.selection.isSelected(absoluteIndex)` [7](#0-6)  — i.e., it reapplies the *old* index-based selection to the *new* diff's hunk layout, with zero content/identity validation.

If the tracked file's content changes on disk between the last UI diff refresh and this re-fetch inside `applyPatchToIndex` (shifting hunk line numbers), the line indices selected by the user in the old diff will silently map onto different, unintended lines in the new diff. The result is a patch that is applied to the index and committed without the user ever seeing or approving its actual final contents — no error, no diff re-confirmation, no re-validation step exists between the “selection is stale” comment’s partial mitigation (line 3480) and the raw `applyPatchToIndex` call.

### Impact Explanation
This breaks the invariant that "what the user visually reviewed and checked in the diff view is exactly what gets committed." A file's tracked content can be altered by processes the attacker fully controls through ordinary, unprompted developer workflow — e.g. a malicious repository shipping a `package.json` with a `postinstall`/`prepare` script (executed automatically by `npm install`, a routine step for any cloned JS project) that spawns a background watcher continuously rewriting a tracked file. While the victim reviews a diff and selects specific lines to commit in Desktop, the watcher can shift or replace file content; Desktop's commit path re-fetches the diff independently and reapplies the stale selection indices, silently including attacker-injected content (or excluding user-intended content) in the resulting commit/push — without any warning banner or diff mismatch check at commit time.

### Likelihood Explanation
Medium-Low. It requires a timing window between the last diff render and `applyPatchToIndex`'s independent re-fetch, and a mechanism to modify the file's content within that window originating purely from repository-supplied code (e.g., an npm lifecycle script or a `core.hooksPath` script bundled with the project). No local/physical access or pre-existing malware is required beyond what routine project setup (`npm install`, opening a fetched repo) already executes.

### Recommendation
1. Do not re-fetch a fresh diff purely for patch construction; reuse (or explicitly re-validate) the exact `ITextDiff` object the user's selection was computed against, and pass it end-to-end from the Changes view into `applyPatchToIndex`/`formatPatch`.
2. Fail the partial commit (rather than silently proceeding) if the diff fetched at staging time differs (e.g. via hash of the diff's hunks/line content) from the diff the current selection was validated against, and instead prompt the user to re-review.
3. Prefer content-addressed line identity (e.g., hashing the line text plus a stable anchor) over pure absolute index for `DiffSelection`, so that a shift in unrelated hunks can't silently remap the user's selection to different content.

### Proof of Concept
1. Clone a malicious repository containing a `package.json` with a `postinstall` script that launches a background process which periodically appends/reorders lines in a tracked file, and a benign-looking existing diff.
2. Victim runs `npm install` (standard project setup step), then opens the repo in Desktop, selects the file in Changes, and reviews the diff, choosing to stage only a subset of lines.
3. Before clicking "Commit," the background process (still running) mutates the file, shifting hunk boundaries.
4. Victim clicks "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now shifted) at `app/src/lib/git/apply.ts:60` and applies the stale line-index selection from before the mutation via `formatPatch`'s `file.selection.isSelected(absoluteIndex)` [8](#0-7) .
5. The resulting commit silently contains different line content than what the user selected/reviewed on screen, with no error or confirmation shown.
