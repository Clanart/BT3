### Title
Attacker-controlled Git HTTP response can spoof a "GitHub Enterprise" identity and trick Desktop into sending its OAuth `client_secret` to the attacker's host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Mover bug boils down to: a component shares a trust decision (the whitelist) with another component, and an attacker who can supply the "target" for that shared trust can redirect privileged access (the unlimited allowance) toward themselves. In GitHub Desktop, the credential-helper trampoline makes a similarly consequential trust decision — "is this remote a GitHub host?" — based on data an attacker-controlled git server can freely fabricate, and that decision feeds directly into the OAuth sign-in flow that transmits Desktop's OAuth `client_secret`.

### Finding Description
When Git needs credentials for an HTTP(S) remote, it forwards any `WWW-Authenticate` response headers it received from the server to Desktop's credential helper as `wwwauth[...]` fields. `getEndpointKind` trusts this attacker-suppliable data as a "happy path" signal that the host is a GitHub Enterprise instance: [1](#0-0) 

That classification is not scoped by any prior origin check — it's the exact string a malicious/compromised git HTTP server (or a MITM proxy on the wire, since this happens on Git's own HTTP request, independent of Desktop's `same-origin-filter`) chooses to send back. If `getEndpointKind` returns `'enterprise'` and the user has no matching account, `getCredential` prompts the user to sign in to GitHub for that endpoint: [2](#0-1) 

Accepting that prompt drives the normal enterprise OAuth flow, which opens the browser at an authorize URL built directly from the attacker's `endpoint`: [3](#0-2) [4](#0-3) 

If the flow completes (the attacker's page redirects back into Desktop's `x-github-client://oauth?code=...&state=...` handler with the leaked `state` value), `resolveOAuthRequest` exchanges the code for a token by POSTing to `${endpoint}/login/oauth/access_token` — i.e., the attacker's own host — including Desktop's real OAuth `client_secret`: [5](#0-4) [6](#0-5) 

This mirrors the shared-whitelist pattern in the report: a trust classification meant for one narrow purpose (identifying legitimate GitHub/GHE hosts to safely fill first-party credentials) is reused to gate a much more privileged action (initiating a full OAuth grant, including the app secret), and the classification itself is attacker-controlled input (the git server's response), just as `topupproxy`'s reused whitelist let an attacker redirect an over-broad allowance.

### Impact Explanation
Exfiltration of Desktop's OAuth `client_secret` and CSRF `state`/authorization `code` handling to an attacker-controlled host is a credential/token-exfiltration primitive against the app itself (not a single user's PAT, but the client secret used for every user's OAuth exchanges), and separately the same "enterprise" misclassification can be used to phish the user's real GitHub Enterprise/dotcom credentials, since the classification is based on trivially forgeable data delivered by a git remote/proxy the user merely fetched from or cloned.

### Likelihood Explanation
Requires the victim to add/fetch from an attacker-controlled or MITM'd git HTTP remote (a scenario already covered as valid attacker control — "a git remote/proxy response") and to accept a resulting sign-in prompt that looks like a legitimate first-time GHE authentication, which is a plausible flow for anyone connecting to a new git server for the first time.

### Recommendation
Do not use client-suppliable `WWW-Authenticate` realm strings as sufficient evidence of a GitHub/GHE host; require the stronger `isGitHubHost` network probe (or an explicit prior enterprise account addition) before classifying an unknown endpoint as `'enterprise'`, and never let an unauthenticated hostname string reach `requestOAuthToken`'s `client_secret`-bearing POST without confirming it against `isDotCom`/`isGHE`/a user-added enterprise endpoint.

### Proof of Concept
1. Host a git-over-HTTP server that responds to authentication challenges with `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim add this server as a remote and fetch/clone (e.g. via a malicious `x-github-client://openrepo/...` deep link or a normal clone URL).
3. Git forwards the header to Desktop's credential helper; `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) returns `'enterprise'` for the attacker's host.
4. `getCredential` (`trampoline-credential-helper.ts:107-125`) prompts "Sign in" for that endpoint; if accepted, `authenticateWithBrowser` (`sign-in-store.ts:260-303`) opens the browser at `https://attacker-host/login/oauth/authorize?client_id=...`.
5. Attacker's fake login page redirects to Desktop's OAuth callback with a `code`; `resolveOAuthRequest`/`requestOAuthToken` (`sign-in-store.ts:332-359`, `api.ts:2370-2395`) POST `client_id`, `client_secret`, and `code` to `https://attacker-host/login/oauth/access_token`, leaking the app's OAuth secret to the attacker.

Note: I could not inspect `trampoline-ui-helper.ts`'s exact `promptForGitHubSignIn` dialog copy/behavior within the available index, so the precise wording/friction of the sign-in prompt step is unverified; a full review of that file would be needed to confirm the exact user-facing framing of the prompt.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {

    }

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }

export function getOAuthAuthorizationURL(
  endpoint: string,
  state: string
): string {
  const urlBase = getHTMLURL(endpoint)
  const scope = encodeURIComponent(oauthScopes.join(' '))

  return new window.URL(
    `/login/oauth/authorize?client_id=${ClientID}&scope=${scope}&state=${state}`,
    urlBase
  ).toString()
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
