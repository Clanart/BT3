### Title
Unchecked `kip71.gastarget` governance parameter allows division-by-zero panic in `NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
The KIP-71 dynamic base fee calculation (`NextMagmaBlockBaseFee`) divides by the governance-controlled `GasTarget` parameter without checking it is non-zero. The governance parameter registry (`kaiax/gov/param.go`) validates `Kip71BaseFeeDenominator` to reject zero (`v != 0`), but applies `noopFormatChecker` (no validation at all) to `Kip71GasTarget`, `Kip71LowerBoundBaseFee`, `Kip71UpperBoundBaseFee`, and `Kip71MaxBlockGasUsedForBaseFee`. This asymmetry allows `gas_target=0` to be accepted as a valid governance vote/parameter value.

### Finding Description
`NextMagmaBlockBaseFee` computes the base fee delta using `gasTarget` as a divisor in two branches:
- When `parentGasUsed > gasTarget`: `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` [4](#0-3) 
- When `parentGasUsed < gasTarget`: `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` [5](#0-4) 

Go's `big.Int.Div` panics on division by zero (analogous to the TFLite `BiasAndClamp` bug where `bias_size` was never checked to be non-zero before being used as a divisor/modulus).

If `GasTarget` is set to `0` via governance, then for any block where `parentGasUsed != 0` (i.e., `parentGasUsed > gasTarget`, since `gasTarget == 0`), and `parentBaseFee` has not already saturated at `upperBoundBaseFee`, the code proceeds to `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, causing an unrecovered panic.

This is reachable because:
1. `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, so a governance vote/parameter update setting `gastarget=0` is accepted without rejection [1](#0-0) .
2. `NextMagmaBlockBaseFee` is invoked during header preparation/verification and fee-history/base-fee computations (e.g., `ParamSet.ToKip71Config()` feeding into `kip71Config.NextMagmaBlockBaseFee` in `processBlock`) [6](#0-5) , meaning every node computing the next block's base fee (block assembly and header verification, `VerifyMagmaHeader`) would hit the same panic deterministically [7](#0-6) .
3. `BaseFeeDenominator` has an explicit non-zero check, showing the developers were aware of this specific bug class for one of the two divisors but missed applying the identical fix to `GasTarget`.

### Impact Explanation
Because `NextMagmaBlockBaseFee` is called by all consensus nodes to compute/verify the header's `BaseFee` field for every block after the Magma hardfork, a zero `GasTarget` value would cause an immediate, deterministic panic on all nodes processing the next block — a full chain halt (denial of service impacting the entire network), not merely a single node crash. This satisfies "state divergence between honest nodes" / chain-halt-class impact since honest nodes cannot progress past the block where the malicious parameter takes effect.

### Likelihood Explanation
Setting `GasTarget` requires a governance parameter change, which is gated by governance permissions (voting node / governing node), not a fully permissionless unprivileged transaction. However, per the review rules, "governance parameters" are explicitly listed as an in-scope reachable path. Given the sibling parameter `BaseFeeDenominator` already has this exact protection while `GasTarget` does not, this looks like a genuine oversight rather than an intentional trust boundary, and any account with governance voting rights (which need not be a top validator, depending on `governancemode`) could trigger a network-wide panic.

### Recommendation
Add a non-zero format checker for `Kip71GasTarget` mirroring `Kip71BaseFeeDenominator`'s check (`FormatChecker: func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }`), or add a defensive `if gasTarget == 0 { gasTarget = <safe default> }` guard directly inside `NextMagmaBlockBaseFee` before it is used as a divisor, similar to the existing fallback already implemented for `BaseFeeDenominator == 0` at lines 71-76.

### Proof of Concept
1. Via governance, submit a vote/parameter update setting `kip71.gastarget = 0`. Because `Kip71GasTarget.FormatChecker` is `noopFormatChecker`, this value passes validation in `PartialParamSet.Add` [8](#0-7)  and becomes the active `ParamSet.GasTarget` for a subsequent block.
2. Once active, any block with `header.GasUsed != 0` (virtually guaranteed on a live network) will cause the next node computing `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` to execute `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` (nonzero) versus `gasTarget = 0`, triggering the `parentGasUsed > gasTarget` branch and eventually `x.Div(x, new(big.Int).SetUint64(0))`, panicking the process [9](#0-8) .
3. Since block proposal, header verification, and fee-history computation (used by public RPC `eth_feeHistory` via `node/cn/gasprice/feehistory.go`) all call this same function, the panic occurs across proposer and verifying nodes alike, halting block production network-wide.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]
	if !ok {
		return ErrInvalidParamName
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
}
