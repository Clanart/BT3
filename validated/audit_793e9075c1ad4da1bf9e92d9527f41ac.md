## Finding: Silent mismatch between Desktop's status-code model and Git's actual porcelain v2 status vocabulary

### Title
Unhandled `T` (type-change) status codes are silently reinterpreted as ordinary "Modified" - (File: `app/src/lib/status-parser.ts`)

### Summary
The PoolTogether report's root cause is that the code assumed a fixed, narrower parameter shape (DAI's actual `permit` signature) than what the real object provided, and the mismatch was resolved silently/incorrectly rather than being rejected. The same class of bug — assuming an enumerated, hard-coded set of input shapes that doesn't cover everything the underlying system can legitimately produce — exists in Desktop's `mapStatus` function in `app/src/lib/status-parser.ts`, which enumerates a fixed list of two-character Git status codes and silently falls back to treating any unrecognized code as an ordinary "modified" file.

### Finding Description
`git status --porcelain=2` defines the `XY` status code alphabet as `[MADRCUTX?!.]{2}` — Desktop's own regexes (`changedEntryRe`, `renamedOrCopiedEntryRe`) capture this full alphabet [1](#0-0) , meaning Git can legitimately emit `T` (type-change, e.g. regular-file ↔ symlink ↔ submodule) in either the index or worktree position. However, `mapStatus` only special-cases a fixed, hand-enumerated list of two-character combinations (`.M`, `M.`, `.A`, `A.`, `.D`, `D.`, `R.`, `.R`, `C.`, `.C`, `AD`, `AM`, `RM`, `RD`, and the conflict codes `DD/AU/UD/UA/DU/AA/UU`) [2](#0-1) . Any status code involving `T` (e.g. `.T`, `T.`, `AT`, `TM`, `MT`, `TD`) — all valid per Git's own documentation and reachable via `parseChangedEntry`/`parsedRenamedOrCopiedEntry` — is not matched by any branch and falls through to the final default: [3](#0-2) 

```js
// as a fallback, we assume the file is modified in some way
return {
  kind: 'ordinary',
  type: 'modified',
  submoduleStatus,
}
```

This is analogous to the DAI `permit` bug: the code assumes the input will always match one of the shapes it explicitly checks for, and when Git's real output takes an unhandled but well-formed shape, the code coerces it into the wrong interpretation instead of surfacing an error or a distinct "type changed" status. Nothing downstream (`convertToAppStatus` in `app/src/lib/git/status.ts` [4](#0-3) ) has a path for a `TypeChanged` kind — the model only distinguishes `New`/`Modified`/`Deleted`/`Renamed`/`Copied`/`Untracked`/conflicted, confirming type-changes were never modeled and are unconditionally collapsed into "Modified" throughout the UI.

### Impact Explanation
A repository whose working tree/index a user clones, fetches, checks out, or merges (attacker-controlled content — e.g. a branch where a path is a symlink in one commit and a regular file in another) can produce a `T`-involving status entry. Desktop will display and stage that path as an ordinary "Modified" file with no type-change indicator, rather than warning the user that a file's fundamental type changed. This is a silent misrepresentation of what the user is about to commit/push — e.g. a path silently converting from a symlink to a regular file (or vice versa) is exactly the kind of change users need to notice (symlinks can point outside the working directory and be leveraged for path traversal / arbitrary file read-write once followed by other tools), but Desktop's UI/commit flow gives no indication anything unusual happened. This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker-controlled repository/branch structure that produces a `T` code (e.g., replacing a tracked regular file with a symlink, or a submodule ↔ regular-file conversion) and requires the victim to perform a normal Git operation (checkout/merge/rebase/pull) that surfaces the status entry, then commit via Desktop's UI without noticing (since the UI provides no distinguishing cue). No admin rights, local access, or unnatural steps are needed beyond ordinary use of Desktop against an untrusted remote — this is within scope as an "attacker controls a cloned/fetched repository" scenario.

### Recommendation
Add explicit handling in `mapStatus` (and the corresponding `FileEntry`/`AppFileStatusKind` model) for all `T`-involving status codes, mapping them to a distinct "type changed" status that is surfaced distinctly in the Changes list/diff UI, rather than falling back to a generic "modified" assumption. Additionally, the default branch should log/flag genuinely unrecognized codes instead of silently normalizing them to "modified".

### Proof of Concept
1. Construct a malicious repository with two commits on a branch: commit A has `path/to/file` as a regular file, commit B replaces `path/to/file` with a symlink (or vice versa) at the same path.
2. Victim clones/fetches this repository in Desktop and checks out commit A, then merges/rebases in the tree from commit B (or otherwise ends up with an index/worktree divergence), causing `git status --porcelain=2` to emit a status line beginning with `T` in the `XY` field for `path/to/file`.
3. Trace: `parsePorcelainStatus` → `parseChangedEntry`/`parsedRenamedOrCopiedEntry` (matches via the `[MADRCUTX?!.]{2}` regex, accepting the `T` code) → `mapStatus` (`app/src/lib/status-parser.ts:201-425`) falls through to the default branch, returning `{ kind: 'ordinary', type: 'modified' }` → `convertToAppStatus` reports `AppFileStatusKind.Modified`.
4. Desktop's Changes list shows the file as a normal "Modified" entry with no type-change warning; the user stages and commits, unaware that a file was converted to/from a symlink.

*Note: I was unable to fully verify, within the available search budget, whether any other code path independently detects symlink mode changes before reaching `status-parser.ts` (e.g., via file-mode diffing elsewhere), so I cannot confirm with certainty that no other layer mitigates this. This should be verified directly against the running app / a Devin session with full repo access.*
