### Title
Vault `last-update` timestamp not advanced when the interest index fails to change, causing stale time to be silently accumulated and later applied at the wrong (positive) rate to zToken price/debt calculations - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
In every vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), the `accrue` function only writes `last-update` to the current `stacks-block-time` when the newly computed borrow/liquidity index actually differs from the previously stored one:

```clarity
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [1](#0-0) 

This is structurally identical to the reported bug class: a per-period rate accumulator ("emission_per_second"/here, the vault's interest `rate`) is used to gate whether a timestamp checkpoint (`last_reward_time`/here `last-update`) advances, instead of always advancing the checkpoint and letting the rate itself be zero for that interval.

### Finding Description
`next-index`/`next-liquidity-index` compute the elapsed time since the last checkpoint and apply the *current* interest rate to it:

```clarity
(define-private (next-index)
  ...
  (let (
      (rate (interest-rate))
      (time-delta (- stacks-block-time (var-get last-update)))
      (multiplier (if (is-eq time-delta u0)
                    INDEX-PRECISION
                    (calc-multiplier-delta rate time-delta true))))
    (calc-index-next idx multiplier)))
``` [2](#0-1) 

`calc-multiplier-delta` returns exactly `INDEX-PRECISION` (i.e. "no change") whenever `rate` is `0` (or rounds to 0 for the given `time-delta`), because `mul-div-down/up(rate * time-delta * INDEX-PRECISION, SECONDS_PER_YEAR_BPS)` evaluates to `0`:

```clarity
(define-private (calc-multiplier-delta (rate uint) (time-delta uint) (round-up bool))
  (+ INDEX-PRECISION
    (if round-up
      (mul-div-up rate (* time-delta INDEX-PRECISION) SECONDS-PER-YEAR-BPS)
      (mul-div-down rate (* time-delta INDEX-PRECISION) SECONDS-PER-YEAR-BPS))))
``` [3](#0-2) 

When `next == idx` and `nliq == lindex` (which necessarily happens whenever the interpolated rate for the current utilization is `0`), the `accrue` function skips writing `last-update`:

```clarity
(if (not (is-eq idx next)) (var-set index next) false)
(if (not (is-eq lidx nliq)) (var-set lindex nliq) false)
...
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [4](#0-3) 

Consequently, the elapsed `time-delta` silently keeps growing across the zero-rate period. Once utilization moves and `interest-rate()` becomes positive again, the very next `accrue()` call computes `time-delta = stacks-block-time - last-update`, which now spans the *entire* zero-rate window plus the new window, and applies the *current, positive* rate to that whole stretched interval — exactly the "emission set to zero, then positive" over-accrual bug from the report, but here applied to the borrow/liquidity index instead of a reward accumulator.

This index (`lindex`) is not a cosmetic value — it is consumed directly by the market's oracle price path for zTokens:

```clarity
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
``` [5](#0-4) 

and via `resolve-callcode` for `CALLCODE-ZUSDC`, `CALLCODE-ZUSDH`, `CALLCODE-ZSTX`, `CALLCODE-ZSBTC`, `CALLCODE-ZSTSTX`, `CALLCODE-ZSTSTXBTC`: [6](#0-5) 

as well as by the vault's own `index` for computing borrower debt (`calc-cumulative-debt`, `total-debt`/`debt-preview`), which directly feeds health-factor / liquidation checks in `market.clar`.

### Impact Explanation
Because the stretched `time-delta` is applied to the *current* (positive) rate rather than the true historical (zero) rate for that period, the resulting `index`/`lindex` jump is larger than it should be the moment the rate turns positive:
- `index` inflation → all borrowers' `total-debt` is overstated, which can push otherwise-healthy positions below the liquidation threshold, letting liquidators seize collateral they should not be entitled to (theft of user funds via unwarranted liquidation).
- `lindex` inflation → the zToken price returned by `resolve-ztoken` is overstated, inflating the on-chain valuation of zToken collateral, which can let a borrower use an inflated collateral value to draw more debt than actually backed, later causing bad debt / protocol insolvency once the true value is realized.

Either direction lands in the in-scope **Critical** impact class (protocol insolvency or theft of user funds via incorrect liquidation), since it corrupts the pricing/health-check pipeline that market.clar relies on for both debt valuation and zToken collateral valuation.

### Likelihood Explanation
The zero-rate condition is not a rare edge case: `interest-rate()` is a linear interpolation over admin-configured `(util, rate)` points, and at `utilization = 0` many typical curve configurations start at `rate = 0` (protocols commonly configure a 0% base rate at 0% utilization) [7](#0-6) . Any pool that experiences a period with zero utilization (e.g., all debt repaid) will trigger this path deterministically on every subsequent `accrue()` call until utilization becomes non-zero again, after which the very next accrual mis-prices the elapsed window.

### Recommendation
Update `last-update` to `stacks-block-time` unconditionally inside `accrue`, regardless of whether `index`/`lindex` changed, mirroring the audit's recommendation to always advance `last_reward_time`:

```clarity
(var-set last-update stacks-block-time)
```
placed outside the `is-eq` guards, in all vault contracts (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Drive a vault's utilization to a point where `interest-rate()` returns `0` (e.g., fully repay all debt so `util = 0`, matching a curve point with `rate = 0`).
2. Call `accrue()` repeatedly (or let time pass); `next-index`/`next-liquidity-index` return the same `idx`/`lidx`, so `last-update` is never advanced [8](#0-7) .
3. After a long idle period (e.g., 30 days) with `rate == 0`, have a borrower take on debt to push utilization up so `interest-rate()` becomes positive.
4. Call `accrue()`: `time-delta = stacks-block-time - last-update` now includes the entire idle 30-day zero-rate window, and `calc-multiplier-delta` applies the new positive rate over that whole span, producing an index jump many times larger than the actual few seconds/blocks of true positive-rate elapsed time [9](#0-8) .
5. This inflated `index` increases all borrowers' `total-debt`, and the inflated `lindex` flows into `resolve-ztoken` in `market.clar`, corrupting zToken collateral pricing and debt-based health checks used for liquidation decisions [5](#0-4) .
