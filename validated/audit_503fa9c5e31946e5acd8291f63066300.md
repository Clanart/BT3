### Title
`WombatStaking._sendRewards()` performs unconditional zero-value token transfers/approvals for dust fee amounts, permanently DoS-ing deposit/withdraw/harvest for a pool - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking._sendRewards()` is called from every `deposit()`, `depositLP()`, `withdraw()`, `harvest()`, and `vote()` flow via `_toMasterWomAndSendReward()` to distribute freshly harvested reward tokens to fee recipients and the pool rewarder. Like the referenced `Cooler.roll()` bug where `newCollateral` could round down to `0` and be sent via `transferFrom` unconditionally, this contract computes `feeAmount`/`feeTosend` as a percentage of the harvested amount and then unconditionally calls `safeTransfer`/`safeApprove`/`queueNewRewards` with that value, without checking for zero. [1](#0-0) 

### Finding Description
`_sendRewards()` guards only the top-level `_amount == 0` case: [2](#0-1) 

but inside the per-fee loop, `feeAmount` is computed via integer division against `DENOMINATOR`: [3](#0-2) 

When the harvested `originalRewardAmount` is small (e.g., a bonus reward token accrues a dust amount between calls, or the WOM harvest itself is tiny), `feeAmount`/`feeTosend` can round down to exactly `0` even though `_amount > 0`. That zero value is then passed unconditionally to:
- `IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend)` when the fee recipient is a plain address [4](#0-3) 
- `IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend)` followed by `IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken)` (which itself does `safeTransferFrom(msg.sender, address(this), _amountReward)` with the zero amount) when the fee recipient is a `BaseRewardPool` [5](#0-4) [6](#0-5) 

If any configured reward token (WOM, a bonus reward token, or mWOM after conversion) is a "revert-on-zero-value-transfer" ERC20 — a documented weird-token behavior class — this zero-value call reverts the entire transaction.

### Impact Explanation
Because `_sendRewards()`/`_toMasterWomAndSendReward()` is invoked unconditionally from `deposit()`, `depositLP()`, `withdraw()`, and `harvest()` for the affected pool, a revert here blocks not just reward distribution but the **entire withdraw path** for that pool — an ordinary user cannot withdraw their principal LP/receipt tokens as long as harvested amounts keep rounding a fee to zero. This differs from (and is more severe than) the original Cooler bug, which only blocked loan extension; here it can render user principal and yield inaccessible for an entire pool, satisfying "permanent freezing of funds" / "freezing of unclaimed yield" for an unprivileged user interacting normally with `WombatStaking`/`WombatPoolHelper`.

### Likelihood Explanation
Triggering requires: (1) a configured reward/bonus token that reverts on zero-value transfers, and (2) a harvest/reward amount small enough that a fee percentage rounds to zero. Bonus reward tokens and fee percentages are protocol-configured via normal (non-malicious) admin operations already anticipated by the codebase (`assetToBonusRewards`, `feeInfos`), so this is reachable without any malicious or privileged action — it only requires an unprivileged user's `deposit`/`withdraw`/`harvest` call to land at a moment when accrued bonus rewards are dust. This is a plausible, low-effort scenario for low-liquidity or newly-added bonus-reward pools.

### Recommendation
Guard every downstream transfer/approve/queue call with an explicit `> 0` check, mirroring the top-level guard already present at line 726:
```solidity
if (feeTosend > 0) {
    if (!feeInfo.isAddress) {
        IERC20(rewardToken).safeApprove(feeInfo.to, 0);
        IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend);
        IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken);
    } else {
        IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
        emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
    }
}
```
Apply the same `> 0` guard to the `smartConvert`/`IMWom(mWom).deposit(feeAmount)` calls when `feeAmount == 0`.

### Proof of Concept
1. Admin (in the course of normal, non-malicious protocol configuration) adds a bonus reward token `X` for a pool that reverts on zero-value `transfer`/`transferFrom` (a known ERC20 pattern, e.g. some older/deflationary tokens).
2. A very small amount of `X` accrues to the pool between harvests (e.g., due to low pool activity), such that when `_toMasterWomAndSendReward` computes `bonusBalanceDiff` and calls `_sendRewards(_lpToken, X, poolInfo.rewarder, bonusBalanceDiff)`, `bonusBalanceDiff` is nonzero but small enough that `feeAmount = bonusBalanceDiff * feeInfo.value / DENOMINATOR == 0`.
3. Any ordinary user calling `withdraw()` on `WombatPoolHelper`/`WombatStaking` for that pool triggers `_sendRewards`, which calls `safeTransfer(feeInfo.to, 0)` (or `queueNewRewards(0, X)` → `safeTransferFrom(..., 0)`) on token `X`, which reverts.
4. The user's `withdraw()` transaction reverts, and will continue to revert on every subsequent attempt until the dust condition changes — freezing the user's principal and rewards for that pool.

```text
    function _sendRewards(
        address _lpToken,
        address _rewardToken,
        address _rewarder,
        uint256 _amount
    ) internal {
        if (_amount == 0) return;
        uint256 originalRewardAmount = _amount;

        if (!isPoolFeeFree[_lpToken]) {
            for (uint256 i = 0; i < feeInfos.length; i++) {
                Fees storage feeInfo = feeInfos[i];

                if (feeInfo.isActive) {
                    address rewardToken = _rewardToken;
                    uint256 feeAmount = (originalRewardAmount * feeInfo.value) / DENOMINATOR;
                    _amount -= feeAmount;
                    uint256 feeTosend = feeAmount;

                    if (feeInfo.isMWOM && rewardToken == wom) {
                        if (smartWomConverter != address(0)) {
                            IERC20(wom).safeApprove(smartWomConverter, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IConverter(smartWomConverter).smartConvert(feeAmount, 0);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        } else {
                            IERC20(wom).safeApprove(mWom, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IMWom(mWom).deposit(feeAmount);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        }
                    }

                    if (!feeInfo.isAddress) {
                        IERC20(rewardToken).safeApprove(feeInfo.to, 0);
                        IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend);
                        IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken);
                    } else {
                        IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
                        emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
                    }
                }
            }
        }

        IERC20(_rewardToken).safeApprove(_rewarder, 0);
        IERC20(_rewardToken).safeApprove(_rewarder, _amount);
        IBaseRewardPool(_rewarder).queueNewRewards(_amount, _rewardToken);
    }
```
