Based on my investigation, the relevant repo `Kirstentat/kaia--020` does not implement any auction-house-style entropy callback, but it does have a genuinely analogous "pause"-bypass pattern in the `kaiax/auction` module (KIP-249 auction/bidding subsystem).

### Title
`AuctionAPI.SubmitBid` accepts bids and forwards target transactions while the auction subsystem is not "running" - ([File: kaiax/auction/impl/api.go])

### Summary
The auction module has two independent "off/paused" signals: a static config flag (`AuctionConfig.Disable`, exposed via `IsDisabled()`) and a dynamic runtime flag (`bidPool.running`, an atomic set by `PostInsertBlock` based on downloader sync status and whether a valid `Auctioneer`/`AuctionEntryPoint` is currently configured). The RPC entry point `SubmitBid` only checks the static `IsDisabled()` flag before submitting the target transaction and adding the bid to the pool, never checking `bidPool.running`.

### Finding Description
`AuctionAPI.SubmitBid` gates on `api.a.IsDisabled()` [1](#0-0)  but immediately after, unconditionally sends the decoded target transaction via `api.a.Backend.SendTx` and adds the bid to the pool via `api.a.bidPool.AddBid(bid)` [2](#0-1) , without consulting `a.bidPool.running`.

The `running` flag is the actual signal of whether the auction subsystem is currently active for this chain height; it is toggled asynchronously in `PostInsertBlock`, which runs on block execution (a different code path than the RPC handler):
- It is cleared while the downloader is synchronizing or the Randao fork isn't active [3](#0-2) .
- It is cleared if `updateAuctionInfo` cannot resolve a valid `Auctioneer`/`AuctionEntryPoint` from the on-chain `Registry` [4](#0-3) .
- It is only set back to `1` once the auctioneer/entry point are confirmed valid for the current block [5](#0-4) .

This mirrors the reported bug class exactly: one asynchronous code path (`entropyCallback` in the external report; here, `PostInsertBlock`/block execution) is responsible for toggling the "paused" state, while a different, request-triggered code path (`settleCurrentAndCreateNewAuction` in the report; here, the `SubmitBid` RPC handler) can still perform the state-changing action (submit a transaction, register a bid) without consulting that pause flag.

### Impact Explanation
While the node is desynchronized/reorging, or between blocks where the `AuctionEntryPoint`/`Auctioneer` registry entries are being changed (a legitimate governance/registry update flow), `bidPool.running` will be `0`. Despite this, `SubmitBid` still: (1) forwards the caller-supplied target transaction into the transaction pool, and (2) inserts the bid into the bid pool's internal bookkeeping. Because bid pool state is used later to build MEV/auction bundles in the block-builder logic (`ExtractTxBundles` in `kaiax/auction/impl/builder.go`), bids admitted during a "not running" window can persist and later be picked up and included once `running` flips back to `1`, even though they were accepted during a period the module considered auction processing inactive. This can result in transactions/bids being processed against a stale or transitioning `Auctioneer`/`AuctionEntryPoint` configuration.

### Likelihood Explanation
Any unprivileged RPC caller (auction bidder) can trigger `SubmitBid` at any time; no special privilege is required. The window where `running == 0` while `IsDisabled() == false` is a normal, recurring condition (node syncing, or registry-driven `AuctionEntryPoint`/`Auctioneer` transitions), not a rare edge case, so the mismatch between the two checked/unchecked flags is readily reachable.

### Recommendation
Have `AuctionAPI.SubmitBid` check `atomic.LoadUint32(&a.bidPool.running) == 1` (in addition to `IsDisabled()`) before sending the target transaction and adding the bid, so bid admission is consistently gated on the same "is the auction subsystem currently active" signal used elsewhere in the module.

### Proof of Concept
1. Node begins block download/sync (`Downloader.Synchronising()` returns `true`), or the on-chain `Registry`/`AuctionEntryPoint` is mid-update such that `updateAuctionInfo` returns `false`; `PostInsertBlock` clears `bidPool.running` to `0` [6](#0-5) .
2. `AuctionConfig.Disable` remains `false` (the module was never operator-disabled), so `IsDisabled()` returns `false`.
3. A bidder calls `auction_submitBid` with a valid `BidInput`; `SubmitBid` passes the `IsDisabled()` check, sends the target transaction, and calls `bidPool.AddBid(bid)`, all without checking `running` [7](#0-6) .
4. Once sync completes or the registry stabilizes and `running` is set back to `1`, the previously-admitted bid remains in the pool and can be picked up by `ExtractTxBundles` for block building, having bypassed the intended "auction inactive" gate.

Note: I was unable to fully inspect `kaiax/auction/impl/bid_pool.go`'s `AddBid` implementation within the available tool budget, so I cannot confirm whether `AddBid` performs any internal `running` check that would mitigate this at a deeper layer; if such a check exists there, it would reduce (but not fully eliminate, since `SendTx` still executes unconditionally) the severity of this finding.

```go
func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
```

```go
func (a *AuctionModule) PostInsertBlock(block *types.Block) error {
	if a.Downloader.Synchronising() || !a.ChainConfig.IsRandaoForkEnabled(block.Number()) {
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}

	if !a.updateAuctionInfo(block.Number()) {
		logger.Debug("stop auction since auctioneer or auction entry point is not set")
		atomic.CompareAndSwapUint32(&a.bidPool.running, 1, 0)
		return nil
	}
```
