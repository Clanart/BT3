Confirmed: `purchase()` is fully permissionless — anyone can call `BandwidthManager.purchase(app, tier, months, chain)` for **any** `app`/`chain` pair, with no relationship to the app owner required. This matches the pattern I need to check against the FIFO cap eviction logic.## Analysis

The Basket report's broken invariant is: **a threshold/quota parameter, controllable by a party other than the victim, can be pushed to a value that causes a shared pool's legitimate participants to lose already-committed value with no recourse**, and the exploitation path requires no special privilege on the attacker's part — just an ordinary interaction with a public entrypoint.

The closest verifiable analog in Hyperbridge is `pallet-bandwidth`'s FIFO subscription cap. `BandwidthManager.purchase()` on any EVM source chain is **fully permissionless**: any caller can name an arbitrary `app` and arbitrary `chain` and buy the cheapest configured tier for it — there is no check that the caller owns, controls, or is related to the app being credited. [1](#0-0) 

Each `(app_chain, app)` bucket keeps subscriptions in a FIFO list capped at 1024 entries. `push_subscription` evicts index `0` (the oldest by insertion order) whenever a new purchase arrives at capacity — this eviction is **purely FIFO by arrival order, not by value or remaining bytes**: [2](#0-1) 

Because `purchase()` is open to anyone and the minimum unit cost is whatever governance set for the cheapest tier, an attacker can cheaply spam 1024 minimum-tier, 1-month purchases against a victim app's `(app_chain, app)` bucket. Each cheap purchase enters at the tail; once the list is full, every subsequent cheap purchase evicts the current head — which, in FIFO order, will eventually be the victim's much larger, already-paid-for, mostly-unconsumed subscription, well before its `expires_at`. The eviction emits `SubscriptionEvicted` with `lost_bytes` but the pallet performs **no refund** of the fee token the victim paid — the paid-for allowance is simply destroyed.

This mirrors the Basket bug's shape precisely:
- A shared resource pool (`Allowance<T>` FIFO for a given app) can be manipulated by any external actor.
- The manipulation forces the legitimate participant (the app that funded bandwidth) to lose committed value (already-paid bytes) with no recourse or refund.
- No malicious relayer, prover, admin, or governance actor is required — `purchase()` is a public entrypoint on the EVM manager contract that any address can call, and the credit flows through the ordinary purchase→relay→`on_accept` path.
- The attack is cheap relative to the damage: an attacker pays only for minimum-tier purchases (which need not even be consumed) while destroying a potentially much larger prepaid allowance belonging to a legitimate app, effectively a denial/fund-loss attack on the app's bandwidth budget rather than the attacker's own.

This directly hits the "bandwidth accounting" and "fund loss" impact categories named in the bounty gate, and does not rely on any excluded assumption (malicious peer/relayer/prover/admin, front-running, or generic DoS) — it is a straightforward abuse of an intentionally-open purchase entrypoint interacting with a value-blind eviction policy.

### Title
Permissionless third-party bandwidth purchases can FIFO-evict a victim app's paid-for, unexpired allowance with no refund — (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `Allowance` FIFO list is capped at 1024 entries per `(app_chain, app)` and evicts strictly by insertion order regardless of remaining value. Because `BandwidthManager.purchase()` lets *anyone* credit *any* app on *any* chain for the price of the cheapest configured tier, an attacker can flood a victim's bucket with 1024 minimum-cost, 1-month purchases to evict the victim's much larger, unexpired, already-paid subscription — permanently destroying prepaid bandwidth the victim funded, with no refund path.

### Finding Description
`purchase()` takes an arbitrary `app`/`chain` pair from the caller with no ownership check: [3](#0-2) 

The pallet's `on_accept` credits whatever `(app_chain, app)` the purchase message names, via `push_subscription`, which enforces only a size cap and evicts the list head (oldest) unconditionally on overflow: [2](#0-1) 

There is no minimum-value floor, no "don't evict an entry with more remaining bytes/longer expiry than the incoming one" rule, and no refund mechanism tied to `SubscriptionEvicted`. The eviction is auditable (`lost_bytes` is emitted) but irreversible. [4](#0-3) 

### Impact Explanation
A victim app that has paid for a large, long-duration bandwidth allowance can have that allowance destroyed by an unrelated, unprivileged attacker who never needs to interact with the victim, its keys, or any bridge operator role. This is a direct loss of the fee-token value the victim already paid, converted into wasted bandwidth for the attacker's throwaway low-tier purchases. The app is then forced to re-purchase to regain the throughput it already paid for — analogous to the Basket bug where the honest user is forced to sacrifice value to restore a shared resource for everyone.

### Likelihood Explanation
The attack requires only calling `purchase()` 1024 times against the cheapest configured tier — a purely permissionless, unprivileged, mechanical operation with no relayer collusion, no governance action, and no reliance on any trust assumption excluded by the bounty scope. The cost is bounded by `1024 × cheapest_tier_price`, which can be made arbitrarily cheap by governance's own tier pricing (the pallet places no floor on tier price relative to potential victim allowance size).

### Recommendation
Do not evict purely by FIFO order. Either (a) evict the entry with the least remaining value (smallest `remaining_bytes × time-to-expiry`) rather than strictly the oldest, (b) refund a pro-rated amount of the evicted subscription's unused value back to whoever paid for it, or (c) increase `MAX_SUBSCRIPTIONS` dynamically / charge an anti-spam fee scaled to prevent cheap flooding of a specific bucket, and consider gating third-party purchases behind an allowlist or a minimum purchase-size floor relative to existing allowance.

### Proof of Concept
1. Governance configures `TierOne` with a small `bytes`/`duration_secs` and low price, and `TierFour` with large `bytes` for legitimate high-volume apps (both tiers already exist per the documented tier model).
2. Victim app buys 1 month of `TierFour` for `(EVM-8453, victimApp)`, receiving a subscription with large `remaining_bytes` and a long `expires_at`.
3. Attacker (any unrelated EOA) repeatedly calls `BandwidthManager.purchase(victimApp, TierOne, 1, "EVM-8453")` 1024 times, paying only the cheap `TierOne` price each time, each dispatched and credited via the normal relay path — see `push_subscription`'s cap-and-evict logic: [5](#0-4) 
4. Once the list of 1024 hits capacity, the 1025th attacker purchase evicts index 0. Because insertion order does not track value, once the victim's `TierFour` entry ages to the front of the FIFO (attacker keeps buying), it is evicted and `SubscriptionEvicted { lost_bytes: <victim's large remaining_bytes> }` fires — the victim's paid bandwidth is gone with no compensation, confirmed by the pallet's own eviction test showing unconditional oldest-first eviction: [6](#0-5) 

**Uncertainty note:** I was unable to directly inspect `modules/pallets/bandwidth/src/types.rs` (tool errors on the final iteration prevented reading it), so the exact `Subscription`/`SubscriptionList` struct bounds and any possibly-unindexed additional constraints (e.g., a per-caller rate limit or minimum-tier-value gate that might mitigate this) could not be fully verified. Based on all documentation and pallet code inspected, no such mitigation appears to exist, but this should be confirmed against `types.rs` directly before treating this as fully conclusive.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
