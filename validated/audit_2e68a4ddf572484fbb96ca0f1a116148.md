## Finding

### Title
Missing protocol allowlist on the `open-external` IPC handler allows arbitrary URI schemes to reach `shell.openExternal()` - ([File: app/src/main-process/main.ts])

### Summary
GitHub Desktop's main process exposes an `open-external` IPC handler that forwards any string supplied by the renderer directly to Electron's `shell.openExternal()`. The handler only *logs* when the URL starts with `http://`/`https://`; it never rejects other schemes. This is the same class of bug as the Rocket.Chat report: insufficient filtering on `shell.openExternal()` at the trust boundary, letting a non-`http(s)` URI (e.g. `file://`, `smb://`, or any OS-registered custom handler) reach the OS shell resolver, which on Linux/Windows can execute attacker-supplied `.desktop`/`.url`/protocol-handler payloads.

### Finding Description
The IPC handler in the main process is the last line of defense before Electron/OS-level URL handling, since it runs with full main-process privileges (unlike the sandboxed renderer): [1](#0-0) 

It does no allowlisting — it merely checks the protocol to decide whether to log, then unconditionally calls `shell.openExternal(path)` regardless of the result of that check.

On the renderer side, the primary consumer, `LinkButton`, forwards its `uri` prop straight to `shell.openExternal()` with **no protocol validation at all**: [2](#0-1) 

`LinkButton` is used across dozens of UI surfaces that render data influenced by remote/GitHub-API content (PR comments, check-run links, notifications, commit-message warnings, etc.) via `dispatcher.openInBrowser` / `shell.openExternal` chains such as: [3](#0-2) 

Only one call site — the sandboxed markdown renderer — enforces an `https?:` protocol check before invoking its `onMarkdownLinkClicked` callback: [4](#0-3) 

That check is local to the markdown iframe's click interceptor. It is not enforced by the IPC boundary itself, and it does not protect the many other `LinkButton`/`shell.openExternal` call sites that don't go through `SandboxedMarkdown`. Because the ultimate authority (`main.ts`'s `open-external` handler) trusts whatever string it receives, any renderer-side path that fails to apply (or bypasses) protocol validation is a viable route to an arbitrary-scheme `shell.openExternal()` call — mirroring the Rocket.Chat root cause where the filter existed only as an incomplete blocklist in one layer rather than as an enforced allowlist at the trust boundary.

### Impact Explanation
`shell.openExternal()` with an uncontrolled protocol can, depending on OS and installed handlers, resolve to execution of attacker-supplied code (e.g., SMB-hosted `.desktop` launchers on Linux, `search-ms:`/other registered protocol handlers on Windows) exactly as demonstrated in the source report. Because the primitive is a link/URL sourced from remote, attacker-influenced content (PR bodies, comments, check-run metadata, notifications) that a user clicks inside GitHub Desktop, this satisfies the "link the user clicks" / "GitHub API object" attacker-control criteria and can lead to code execution outside the sandboxed renderer.

### Likelihood Explanation
Exploitability depends on finding a concrete `LinkButton`/`openInBrowser` call site that renders an attacker-controlled URL without going through the `SandboxedMarkdown` protocol check. Several `LinkButton` usages render text/links derived from PR/notification data (`pull-request-comment-like.tsx`, `ci-check-run-popover.tsx`, etc.), but I was not able to fully trace, within the remaining investigation budget, which of these pass a raw attacker-controlled URI (vs. an internally-constructed `https://github.com/...` URL) into the `uri` prop. This is the main open question and should be verified with full repository access.

### Recommendation
Enforce an allowlist (`http:`, `https:`, `mailto:`) inside the `open-external` IPC handler in `app/src/main-process/main.ts` itself, rejecting any other scheme before calling `shell.openExternal()`, rather than relying on renderer-side checks that are inconsistently applied. This centralizes the fix at the trust boundary, matching the disclosed mitigation ("only an allowlist can successfully prevent attacks here").

### Proof of Concept
Conceptual (not fully verified against a live attacker-controlled call site):
1. Attacker crafts a PR comment/notification whose body/metadata surfaces a link with a non-`http(s)` scheme (e.g., `smb://attacker.tld/public/pwn.desktop`) in a UI element that ultimately calls `shell.openExternal`/`dispatcher.openInBrowser` via a `LinkButton` that is not wrapped by `SandboxedMarkdown`'s protocol check.
2. Victim clicks the link inside GitHub Desktop.
3. `LinkButton.onClick` (`app/src/ui/lib/link-button.tsx:76-92`) calls `shell.openExternal(uri)` unconditionally.
4. The renderer proxy invokes IPC `open-external`, which is handled in `app/src/main-process/main.ts:581-597` with no scheme validation, and forwards the URI to Electron's `shell.openExternal`.
5. On a vulnerable OS/desktop-environment configuration, this triggers execution of the remote payload, as demonstrated in the original Rocket.Chat report.

**Uncertainty:** I could not confirm within the available investigation which exact `LinkButton` instance renders a truly attacker-controlled (non-sanitized, non-internally-generated) URL outside the `SandboxedMarkdown` path — that link needs to be established with full codebase access (e.g., via a Devin session) to convert this from a plausible architectural weakness into a fully proven exploit chain.

    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
