## Analysis

The reachable analog to CVE‑2023‑28867 (unbounded recursion causing stack consumption from untrusted input) exists in Chia's offer/outer-puzzle-driver matching code, which is exercised whenever a wallet processes an offer file supplied by an untrusted counterparty.

### Title
Unbounded Python recursion in outer-puzzle driver matching (`match_puzzle`) allows an offer counterparty to crash the wallet via stack exhaustion - ([File: chia/wallet/outer_puzzles.py])

### Summary
`match_puzzle()` and each outer-puzzle driver's `match()` method (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`, etc.) recursively call `self._match(...)` on the puzzle's inner layer with no depth limit, directly mirroring the graphql-java bug class (attacker-controlled input drives unbounded Python-stack recursion).

### Finding Description
`match_puzzle` iterates registered drivers and calls `driver.match(puzzle)`: [1](#0-0) 

Each driver's `match()` recurses into its inner puzzle via the shared `_match` callback whenever the puzzle_reveal has another matching layer, e.g. in `CATOuterPuzzle.match()`: [2](#0-1) 

and identically in `SingletonOuterPuzzle.match()`, `OwnershipOuterPuzzle.match()`, `MetadataOuterPuzzle.match()`, and `CROuterPuzzle.match()`: [3](#0-2) [4](#0-3) 

None of these driver `match()` implementations enforce a recursion-depth cap; the depth is entirely a function of how many curried outer layers are present in the attacker-supplied `puzzle_reveal` (CAT-wraps-CAT-wraps-CAT..., or any chain of matched layer types). This is reachable directly from offer processing: `Offer.from_spend_bundle()` calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every coin spend in an incoming spend bundle: [5](#0-4) 

and `Offer._get_offered_coins()` (computed eagerly as an `init=False` dataclass field populated in `__post_init__`, i.e. automatically whenever an `Offer` object is constructed/deserialized from an offer file) also calls `match_puzzle` on every parent spend's puzzle reveal: [6](#0-5) [7](#0-6) 

Because `Offer` objects are constructed the moment a wallet parses an offer file (e.g. via bech32/RPC `check_offer_validity`/`get_offer_summary` paths in `TradeManager`), an attacker (the offer maker / counterparty) can hand a victim wallet an offer whose puzzle reveal contains many nested layers that each satisfy one of the driver `match()` shapes (trivial to construct by repeatedly currying `CAT_MOD` around itself, as shown in the existing test `test_cat_outer_puzzle` which nests CAT twice deliberately): [8](#0-7) 

Unlike CLVM tree-hashing, which the codebase deliberately made iterative specifically to avoid Python recursion-limit issues (documented and implemented in `sha256_treehash`): [9](#0-8) 

the outer-puzzle driver matching code was never given the same treatment — it is genuine unbounded Python-level recursion driven by attacker-controlled nesting depth.

### Impact Explanation
A sufficiently deep chain of nested matched puzzle layers in an offer's `puzzle_reveal` will exceed Python's recursion limit and raise `RecursionError`, potentially with enough depth to exhaust the C stack before Python's own guard triggers (each layer of recursion here spans multiple mutually-recursive Python function calls: `match_puzzle` → driver `.match()` → `self._match()` → next driver `.match()` …). This crashes or hangs wallet-side processing of an untrusted offer, a wallet-user/offer-counterparty reachable denial-of-service against the wallet client processing the offer (matches the "spend-triggered transaction-processing halt" acceptance criterion).

### Likelihood Explanation
High likelihood: constructing a deeply nested, driver-matchable puzzle is straightforward chialisp/`curry()` composition (no signatures or special privileges are required to *construct* an offer's puzzle reveal — only to eventually spend it), and offer files are explicitly designed to be shared with and parsed by arbitrary counterparties before any spend is broadcast or accepted.

### Recommendation
Add an explicit recursion-depth limit (or convert to an iterative work-list algorithm, matching the pattern already used in `sha256_treehash`) in `match_puzzle`/`construct_puzzle`/`get_inner_puzzle`/`get_inner_solution` and each outer-puzzle driver's recursive `also`/`_match` chains, rejecting or safely erroring out puzzle reveals whose nesting exceeds a sane bound before recursing.

### Proof of Concept
1. Build `puzzle = CAT_MOD` curried with the CAT tail hash and an inner puzzle `P0` (arbitrary ACS).
2. Repeat N times: `puzzle = construct_cat_puzzle(CAT_MOD, tail, puzzle)`, nesting CAT layers arbitrarily deep (as the test `test_cat_outer_puzzle` demonstrates for depth 2 already).
3. Package `puzzle` as the `puzzle_reveal` of a dummy `CoinSpend` inside a `WalletSpendBundle`, and serialize it as an offer (bech32-encoded `Offer`).
4. Send the offer to a victim wallet; when it parses the offer (`Offer.from_bech32`/deserialization triggers `Offer.__post_init__` → `_get_offered_coins()` → `match_puzzle()`), the recursive `_match` chain recurses N times purely in Python, exhausting the stack once N is large enough (a few thousand layers suffices well below any CLVM program-size ceiling).
