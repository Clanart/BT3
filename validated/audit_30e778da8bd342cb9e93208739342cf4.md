This confirms the analog. In CR-CAT (Credential-Restricted CAT) transfers, when a payment goes to a recipient without a recognized puzzle hash (e.g., during an offer settlement, or any `generate_signed_transaction` to an address the sender's wallet doesn't recognize as its own), the coin is force-wrapped into a "pending approval" state via `construct_pending_approval_state(puzhash, amount)` at [1](#0-0) , using the puzzle defined in [2](#0-1) .

The only way out of this pending state is `claim_pending_approval_balance`, which unconditionally requires a `VerifiedCredential` issued by one of the CAT's fixed `authorized_providers`: [3](#0-2) 

`authorized_providers` is immutable — it's curried into the CR layer at CAT launch time (`CRCAT.launch`) and is part of the asset's identity [4](#0-3) . A VC is only usable if the recipient's DID (proof provider) is still one of those authorized providers and hasn't revoked the credential. A provider (DID owner) can unilaterally revoke a VC at any time via `activate_backdoor`/`revoke_vc`, which is described as making the VC unusable going forward: [5](#0-4)  and [6](#0-5) .

If a recipient's only usable VC (or the only VC from an authorized provider) is revoked, or never exists, before they claim, the CR-CAT sitting in "pending approval" state has no other escape path in the codebase — `claim_pending_approval_balance` is the sole mechanism to move a `CoinType.CRCAT_PENDING` coin out of that puzzle hash, and it hard-fails with `RuntimeError` when no valid VC is found [7](#0-6) . This exactly mirrors the reported bug class: a fixed, unchangeable "authorization" gate (`authorized_providers`, analogous to the option's fixed `receiver`) that a single trusted party can revoke, permanently trapping the recipient's already-received CAT tokens with no reassignment or reclaim path available to the token holder.

### Title
CR-CAT recipients can be permanently locked out of pending-approval funds via VC revocation, with no reclaim/reassignment path - (File: chia/wallet/vc_wallet/cr_cat_wallet.py)

### Summary
CR-CAT payments to addresses not already recognized by the sending wallet are force-routed into a "pending approval" puzzle state (`construct_pending_approval_state`). The only exit from this state, `claim_pending_approval_balance`, requires a `VerifiedCredential` from one of the CAT's fixed `authorized_providers`. If the recipient's VC is revoked (or was never issued) by the provider before the claim is made, the coin becomes permanently unspendable by that recipient, with no mechanism to redirect or reclaim it to another puzzle hash — directly analogous to the reported "blacklisted receiver can't reclaim option token" bug class.

### Finding Description
When a `CRCATWallet.generate_signed_transaction` sends to a puzzle hash the sender doesn't recognize, it wraps the output in `construct_pending_approval_state(puzhash, amount)` [1](#0-0) . This puzzle hash is derived only from the intended recipient's inner puzzle hash and amount, and is curried under the same fixed CR layer (`authorized_providers`, `proofs_checker`) as the parent CAT [2](#0-1) .

The sole documented/implemented path to move funds out of this pending state is `CRCATWallet.claim_pending_approval_balance`, which mandatorily looks up a VC "with provider in `self.info.authorized_providers`" and aborts if none is found [3](#0-2) . `authorized_providers` is baked into the asset at `CRCAT.launch` time and cannot be changed per-recipient or reassigned [4](#0-3) .

A DID that is an authorized provider can revoke any VC it issued at any time using `VCWallet.revoke_vc` / `VerifiedCredential.activate_backdoor`, which spends the VC through a "backdoor" and is explicitly documented to make it "perfectly useful as a singleton" going forward — i.e., it can no longer authorize CR-CAT claims [8](#0-7) . There is no code path that lets the CR-CAT pending-approval coin be redirected to a different recipient/puzzle hash or unwrapped without a qualifying VC.

### Impact Explanation
Any recipient of a CR-CAT payment (e.g., received via an offer settlement or direct transfer to an as-yet-unknown puzzle hash) is exposed to permanent loss of those specific funds if their VC issuer revokes their credential (or never issues one) before they call `crcat_approve_pending`/`claim_pending_approval_balance`. Since `authorized_providers` is fixed at CAT-mint time and cannot be updated, and the pending-approval puzzle hash has no alternate spend path, the affected coin's value is permanently stuck and unspendable by anyone — a direct fund-loss condition reachable by a normal, unprivileged wallet user simply receiving a CR-CAT payment.

### Likelihood Explanation
This requires the CAT to be a Credential-Restricted CAT (CR-CAT) with a VC-issuing authority the recipient does not fully control, and that authority choosing (or being compelled) to revoke the recipient's credential before the pending payment is claimed. This is a realistic occurrence for CR-CATs used in regulated/KYC-gated asset scenarios, where the whole point of `authorized_providers`/VC is that a third-party issuer controls eligibility, and issuers regularly revoke credentials for compliance reasons.

### Recommendation
Add a fallback/expiry or re-issuance path for CR-CAT coins stuck in the pending-approval state, e.g., allow the original sender to reclaim after a timeout (similar to the clawback puzzle's sender-can-always-reclaim design in `chia/wallet/puzzles/clawback/drivers.py`), or allow the pending-approval puzzle to accept authorization from any currently-authorized-provider VC rather than requiring one specifically usable by the intended recipient, so a revoked/missing individual VC does not permanently strand funds.
