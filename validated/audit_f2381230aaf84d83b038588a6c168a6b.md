### Title
Cached FROST nonce reused across repeated `share`/`complete` signing passes without a consumed-nonce guard - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The bug class of the external report — functions performing security-critical external interaction without a re-entrancy/consumed-state guard — maps onto `DkgConfirmer`'s signing flow. `preprocess_internal` deterministically rebuilds the `AlgorithmSignMachine` (and hence the FROST nonces) from a DB-cached `CachedPreprocesses` seed keyed only by `("DkgConfirmer", attempt)`. The cached entry is never deleted or marked consumed, so `share_internal` can execute `AlgorithmSignMachine::sign` multiple times with the *same* nonces — the documented precondition (`CachedPreprocess` "MUST only be used once. Reuse will enable third-party recovery of your private key share", `crypto/frost/src/sign.rs:83-92`) is violated.

### Finding Description
`SigningProtocol::preprocess_internal` loads (or creates once) a 32-byte seed from `CachedPreprocesses::get(self.txn, &self.context)` and calls `AlgorithmSignMachine::from_cache`, which seeds a `ChaCha20Rng` and regenerates identical nonces/commitments (`crypto/frost/src/sign.rs:121-144`, `seeded_preprocess`). Nothing removes or invalidates the cached seed after `sign` runs, so every call reuses the same nonce pair.

`DkgConfirmer::share` calls `share_internal` once, and `DkgConfirmer::complete` calls `share_internal` *again* (line 321-324) to reconstruct the machine before completing. Each `share_internal` invocation feeds attacker-influenced inputs — the `preprocesses` map (other validators' preprocess messages, read via `read_preprocess`) and `key_pair` (which feeds `set_keys_message`, i.e., the signed `msg`) — into `machine.sign(preprocesses, msg)`. If the preprocess set or message differs between any two invocations (share vs. complete, or repeated share calls after state changes/reboot re-execution), the signer produces two signature shares `s = d + b*rho*lambda + c*share` with the same nonces `d, e` but different binding factors/challenges. Standard nonce-reuse algebra then recovers the validator's MuSig private key share — the root-of-trust key used to confirm DKG results on-chain.

The file's own header acknowledges this class of issue: the re-execution design is only safe because nonces are "context-bound under a BFT protocol", and there is an explicit TODO noting the need to "review how we're handling ... preprocesses" and implement an "on-chain-preprocess-matches-presumed-preprocess check before publishing shares" (lines 25-54). That check is the missing nonReentrant-equivalent guard: there is no assertion that the second `sign` is byte-identical in inputs to the first, and no flag marking the cached nonce consumed.

### Impact Explanation
Reuse of a FROST/MuSig nonce across two signing passes with differing `preprocesses` (different participant set → different binding factors `rho` and Lagrange coefficients) or differing `msg` (different `key_pair`) yields two linear equations exposing the secret key share. Since these are validator keys underpinning MuSig confirmation of validator-set keys on Substrate, recovery of a threshold coalition of shares compromises the consensus root of trust — an attacker could forge `set_keys` confirmations and install attacker-controlled group keys, enabling theft of all network funds.

### Likelihood Explanation
Requires two `share_internal` executions for the same `("DkgConfirmer", attempt)` context with non-identical preprocess/message inputs. The inputs are sourced from tributary (BFT-ordered) data, so divergence requires the preprocess map or `key_pair` observed at `share` time to differ from that at `complete` time — plausible across reboot/re-execution or when the validator set/removed list changes between calls. Re-execution is an explicit design feature here (line 16: "a combination of the DB and re-execution are used"), which makes the second `sign` invocation routine rather than exceptional. Uncertainty: I could not verify `handle.rs` call sites within the iteration limit; if the coordinator guarantees bit-identical inputs on every invocation, the shares would be identical and no leak occurs — but the code performs no such verification, relying on an unstated invariant.

### Recommendation
Add a consumed-nonce guard (the `nonReentrant` analog): after `share_internal` successfully calls `machine.sign`, store a commitment to the exact `(participants, serialized_preprocesses, msg)` tuple in `SigningProtocolDb`, and on any subsequent `share_internal`/`complete` for the same context, require the inputs hash-match the stored value before re-signing — abort otherwise. Alternatively, delete `CachedPreprocesses` for the context after the first share is produced and persist the produced share/signature-machine state for `complete`, so the nonce can never be re-rolled.

### Proof of Concept
1. As a validator, `DkgConfirmer::share(preprocesses_A, key_pair)` produces share `s1` using nonces `(d, e)` derived from seed `CachedPreprocesses[("DkgConfirmer", attempt)]`.
2. Trigger `DkgConfirmer::complete(preprocesses_B, key_pair', shares)` where `preprocesses_B` differs (e.g., a different signer subset or different binding commitments — these are `read_preprocess`-parsed public inputs). `share_internal` re-derives the identical `(d, e)` from the still-present cached seed and emits share `s2`.
3. From `s1 = d + e·b1·λ + c1·share` and `s2 = d + e·b2·λ + c2·share` with known `b1, b2, c1, c2` (all computable from public preprocesses/messages per `sign.rs:283+`), solve for `share` — the validator's MuSig secret key share. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  Additionally, to ensure a rebuilt service isn't flagged as malicious, we have to check the
  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
