### Title
Untrusted preprocess/share vector length causes index-out-of-bounds panic in Bitcoin transaction signing - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` index into per-participant `Vec<Preprocess>`/`Vec<SignatureShare>` values that are deserialized verbatim from untrusted bytes via `read_preprocess`/`read_share`. A malicious co-signer who supplies a vector shorter than the transaction's input count causes a panic, crashing the signer — the same availability-impact class as the reference DoS advisory.

### Finding Description
`TransactionSignMachine::read_preprocess` delegates to `AlgorithmSignMachine::read_preprocess`, which parses a `Preprocess` message per internal sign machine (`self.sigs`), one per transaction input (send.rs:351-353). The resulting `HashMap<Participant, Vec<Preprocess>>` carries no length validation tying each participant's vector to `self.sigs.len()`.

In `sign`, each sub-machine's commitments are extracted by direct indexing:

```rust
commitments.iter().map(|(l, commitments)| (*l, commitments[c].clone()))
```
(send.rs:364-371)

`c` ranges over `0 .. self.sigs.len()`. If any participant's preprocess vector has fewer than `self.sigs.len()` elements — trivially produced by truncating the serialized preprocess stream — `commitments[c]` panics.

The same pattern exists in `complete`: `shares.remove(0)` (send.rs:419) is called once per input on each participant's `Vec<SignatureShare>` returned by `read_share`; a short or empty vector panics on `remove(0)` when the input count exceeds the shares supplied.

### Impact Explanation
A single malicious signing participant can crash the victim's signing process mid-protocol by sending malformed (short) preprocess or share vectors. FROST's `validate_map` in `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:313) only checks the `HashMap` key set, not vector length, so the panic is reached before any share verification. A panic kills the signing session and, depending on embedding, the whole processor — a repeatable remote DoS from public protocol bytes, matching the advisory's "hang or frequently repeatable crash" class.

### Likelihood Explanation
Any counterparty in a multisig session can trigger it with crafted preprocess/share bytes; no privileged position needed. Exploitation is deterministic (empty vector always panics for a ≥1-input transaction). Impact is limited to availability of the signing session/process — no key or fund compromise — consistent with a Medium rating.

### Recommendation
In `TransactionSignMachine::sign`, validate that each participant's preprocess vector length equals `self.sigs.len()` before indexing (return `FrostError` on mismatch); likewise verify share vector lengths in `complete` before `remove(0)`, or use `get(c)`/`pop_front`-style fallible access returning an `InvalidShare`/`InvalidParticipant` error.

### Proof of Concept
A malicious participant P sends, as their preprocess bytes for a transaction with N inputs, a serialized `Vec<Preprocess>` containing N-1 valid preprocess encodings. `read_preprocess` on the victim reads exactly `self.sigs.len()` items per... — correction: `TransactionSignMachine::read_preprocess` iterates `self.sigs` reading one `Preprocess` each, so a peer's `Vec<Preprocess>` is whatever length the bytes parse to, e.g., truncated so fewer entries exist relative to `self.sigs.len()` — then `sign` panics at `commitments[c]` for `c` beyond the vector's end. Equivalently, a peer's `Vec<SignatureShare>` shorter than the input count panics at `shares.remove(0)` during `complete` (send.rs:419). [1](#0-0) [2](#0-1) [3](#0-2) 

Note: the panic vector for `read_preprocess` requires the peer's byte stream to still parse successfully for the entries it does contain; the crash occurs in `sign`/`complete` when the per-input fan-out indexes past the attacker-controlled vector length.
