## Finding: Native ETH sent to `placeOrder` gets permanently stuck when inputs are ERC20-only and `order.fees == 0`

### Title
Stuck/locked native ETH in `IntentGatewayV2.placeOrder` when no native input or protocol fee consumes `msg.value` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
This is a direct local analog of the reported Trading.sol bug: `msg.value` is consumed only inside specific conditional branches, and any leftover value is neither used nor refunded, leaving native ETH permanently locked in the contract.

### Finding Description
`placeOrder` caches `msg.value` into a local `msgValue` and only decrements/consumes it in two conditional paths:
1. Inside the predispatch-assets loop, only for assets where `token == address(0)` (native token inputs). [1](#0-0) 
2. Inside the non-predispatch escrow loop, again only for `token == address(0)` inputs. [2](#0-1) 
3. Finally, only if `order.fees > 0`, the remaining `msgValue` is swapped to fee tokens via Uniswap. [3](#0-2) 

If a caller places an order whose `order.inputs` are entirely ERC20 (no `token == address(0)` entries) and `order.fees == 0`, none of these three branches ever touch `msgValue`. The function then proceeds straight to emitting `OrderPlaced` and returns, with no refund of unused `msg.value` back to `msg.sender` anywhere in the function. [4](#0-3) 

This exactly mirrors the reported pattern: a fee/value parameter (`msg.value`) is used only in one specific branch of the logic, and the contract has no compensating withdrawal mechanism for the case where that branch is not taken — the value is simply absorbed into the contract's balance with no accounting entry (`_orders[commitment][...]` mapping) pointing to it, so it cannot be recovered by the placer, a solver, or any admin path visible in this contract.

### Impact Explanation
Native ETH sent alongside an all-ERC20, zero-protocol-fee order becomes permanently locked in the `IntentGatewayV2` contract. Unlike the escrowed input/fee amounts (which are tracked in `_orders[commitment][token]` and can be released via `withdraw`/redeem/refund flows), this stray `msg.value` has no corresponding storage entry, so no existing withdrawal, cancel, or sweep-dust code path can recover it. This is a direct, unconditional loss-of-funds bug for any user (or front-end/SDK bug) that attaches native value to a call that doesn't need it.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin — it is reachable by any ordinary unprivileged caller of the public `placeOrder` entrypoint who (accidentally, or due to a wallet/SDK miscalculation of `msg.value`) attaches ETH to an order composed purely of ERC20 inputs with `fees == 0`. Given that `placeOrder` is payable and takes `msg.value` implicitly rather than as an explicit parameter, this is a plausible operational mistake, especially from integrators computing native dispatch/predispatch fees incorrectly.

### Recommendation
After the escrow and fee-handling logic, refund any remaining `msgValue` back to `msg.sender`, mirroring the pattern already implemented correctly in `_fillCrossChain` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`: [5](#0-4) 
Add an equivalent `if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); if (!sent) revert InsufficientNativeToken(); }` at the end of `placeOrder` (and audit the sibling `evm/src/apps/IntentGatewayV2.sol` / `sdk/packages/core/contracts/apps/IntentGatewayV2.sol` variants for the same gap).

### Proof of Concept
1. Construct an `Order` where all `order.inputs[i].token != address(0)` (pure ERC20 inputs) and `order.fees == 0`.
2. Call `placeOrder(order, options)` with `msg.value = 1 ether` (e.g. due to a client miscalculation).
3. Trace execution: the predispatch loop (or plain escrow loop) only decrements `msgValue` for `token == address(0)` entries — none exist, so `msgValue` stays `1 ether`; the `order.fees > 0` block at line 465 is skipped since fees are zero. [3](#0-2) 
4. `placeOrder` returns successfully, emitting `OrderPlaced`, with 1 ETH now sitting in the contract's balance, unaccounted for in `_orders[commitment]` and unrecoverable by any subsequent `withdraw`/`cancelOrder`/dust-sweep call, since those only operate on tracked escrow amounts.
