Based on the evidence gathered, I can now provide a complete analysis.

The `getBalance` helper reads directly from `pool.currentState` (the chain's last-known state), and each fee-delegated transaction's admission check (`validateTx` in `blockchain/tx_pool.go`) and pending-filter check (`txList.Filter` in `blockchain/tx_list.go`) independently compares `tx.Fee()` (or the ratio-adjusted portion) against that single, un-reserved `feePayerBalance` snapshot. Neither function tracks or decrements a running "committed" total for a given fee-payer address across the *other* pending/queued transactions that name the same fee payer — decrements to `pool.currentState` only happen when a block is actually mined via `StateTransition.buyGas` (`blockchain/state_transition.go:341,368`). This mirrors the ZenHive mpp bug class: bounding is done per-transaction, not in aggregate. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Fee-delegated transaction pool admission checks only a single transaction's fee against the sponsor's on-chain balance, allowing concurrent distinct senders to drain a shared fee-payer wallet - ([File: blockchain/tx_pool.go])

### Summary
Kaia's fee-delegation feature lets an unrelated `feePayer` account sponsor gas for a transaction signed by a different `sender`. When a fee-delegated transaction enters the pool, `TxPool.validateTx` checks that `feePayerBalance := pool.getBalance(feePayer)` covers `tx.Fee()` (or its ratio-adjusted share) at that moment, and the same balance-vs-fee comparison is repeated per-transaction in `txList.Filter` during promotion/demotion. Nothing in the pool subtracts or reserves the fee amount for the sponsor across the *other* pending/queued fee-delegated transactions naming the same `feePayer`. Because `pool.currentState` (the source of `getBalance`) is only mutated when a block actually executes (`StateTransition.buyGas`), many distinct sender-signed transactions that all designate the same sponsor can each pass the individual balance check simultaneously, even though their combined fee obligation vastly exceeds the sponsor's actual balance.

### Finding Description
`TxPool.validateTx` performs the fee-payer solvency check using only the current, unreserved on-chain balance:
```go
feePayer            = tx.ValidatedFeePayer()
feePayerBalance     = pool.getBalance(feePayer)
...
if feePayerBalance.Cmp(tx.Fee()) < 0 {
    return ErrInsufficientFundsFeePayer
}
``` [4](#0-3) 

This check is keyed on the transaction's own value, not on any aggregate exposure tracked for the `feePayer` address. The pool's per-account (`pool.pending`/`pool.queue`) organization is keyed by `sender`, not by `feePayer`, so there is no data structure that sums up outstanding fee commitments for a sponsor across transactions coming from many different senders. The same unreserved-balance pattern recurs in `txList.Filter`, used both for queue admission and for pending-list re-validation on state changes:
```go
feePayerBalance := pool.getBalance(feePayer)
...
return senderBalance.Cmp(tx.Value()) < 0 || feePayerBalance.Cmp(tx.Fee()) < 0
``` [2](#0-1) 

The actual balance deduction for a fee payer only happens deep in block execution, inside `StateTransition.buyGas`, via `st.state.SubBalance(validatedFeePayer, feePayerFee)` — i.e., only one transaction at a time, only once it is included in a block: [5](#0-4) 

Between pool admission and block inclusion, an arbitrary number of *distinct* senders can each craft a fee-delegated transaction (with the sponsor's valid fee-payer signature, e.g. obtained via an open sponsorship/relay service) targeting the same `feePayer`. Each transaction independently passes `validateTx`/`Filter` because each is checked against the sponsor's full, undiminished on-chain balance. All of them can be pending simultaneously and be included across one or more blocks until the sponsor's real balance is exhausted, at which point legitimate sponsored transactions begin failing (`errInsufficientBalanceForGasFeePayer` / `vm.ErrInsufficientBalance` in `state_transition.go`) or reverting after being selected, wasting sponsor funds and denying the fee-delegation service to legitimate users — the direct analog of the reported mpp finding.

### Impact Explanation
Any public relay/dApp that offers fee-delegation sponsorship (a very common Kaia pattern where a dApp signs as `feePayer` for user-submitted transactions) is exposed to unauthenticated drain: an attacker who can obtain (or replay/request) sponsor fee-payer signatures for many distinct sender-signed transactions can commit far more aggregate fee exposure than the sponsor's balance actually supports. Legitimate sponsored users are denied service once the sponsor wallet is exhausted, and depending on how the sponsorship service issues signatures, this can also cause block-inclusion churn (transactions failing in `buyGas` after passing pool admission), wasting proposer resources. This matches the "High" classification of the original report: unauthenticated remote resource-exhaustion/DoS against a fee-payer wallet with no aggregate throttling.

### Likelihood Explanation
Exploitability depends on how a sponsor issues fee-payer signatures (e.g., an open relay that co-signs many independent sender transactions per some policy). Given Kaia's fee-delegation design intentionally supports "sender != feePayer" scenarios and there is no pool-level, cross-transaction sponsor-exposure accounting anywhere in `tx_pool.go`/`tx_list.go`, any sponsor service that signs multiple concurrent fee-delegated transactions is structurally exposed the moment more sponsored transactions are in-flight than the sponsor's balance can cover.

### Recommendation
Track outstanding committed fee exposure per `feePayer` address across all pending/queued fee-delegated transactions in the pool (e.g., a running total keyed by fee-payer, decremented on removal/inclusion and consulted in `validateTx` and `txList.Filter` instead of, or in addition to, the raw `pool.getBalance(feePayer)` snapshot), so that the sum of fees committed against one sponsor cannot exceed that sponsor's real balance.

### Proof of Concept
1. Sponsor `F` maintains balance `B` and operates (or is tricked into operating) an open fee-payer signing endpoint for `TxTypeFeeDelegated*` transactions.
2. Attacker generates `N` distinct sender keys `S1...SN`, each crafting a valid fee-delegated transaction with `tx.Fee() ≈ B` (or any value making `N * fee > B`), all naming `F` as `feePayer`, and obtains `F`'s fee-payer signature for each (via the sponsor's normal signing flow).
3. Attacker submits all `N` transactions to the pool via `AddRemote`/RPC. Each independently passes `validateTx`'s check `feePayerBalance.Cmp(tx.Fee()) < 0` because `pool.getBalance(F)` still reports the full, undiminished balance `B` for every check — none of the other N-1 in-flight transactions are accounted for.
4. As blocks are mined, `buyGas` deducts `F`'s balance transaction-by-transaction; once `F`'s real balance is exhausted, subsequent legitimate sponsored transactions from other genuine users fail with `errInsufficientBalanceForGasFeePayer`, demonstrating sponsor-wallet drain and denial of service caused purely by concurrent submission exceeding the aggregate, un-tracked sponsor exposure.
