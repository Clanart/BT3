### Title
Hardcoded, non-upgradable Pyth/DIA oracle contract addresses in market.clar will desync from Pyth's live governance execution plan, freezing price updates and eventually all oracle-gated operations - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` resolves and writes Pyth prices by calling literal, version-pinned principal addresses (`'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-oracle-v4`, `.pyth-storage-v4`, `.pyth-pnau-decoder-v3`, `.wormhole-core-v4`) and a hardcoded DIA oracle address, instead of reading them dynamically or exposing a DAO-updatable setter for these addresses. Because Clarity contracts are immutable post-deployment, if Pyth's on-chain governance migrates its "current execution plan" to newer contract versions (which the repo's own Pyth governance code shows already happened multiple times, v1→v4), `market.clar`'s calls become permanently pinned to a deprecated, frozen oracle instance.

### Finding Description
`write-feed` submits price-feed VAAs to a hardcoded Pyth oracle/storage/decoder/wormhole quad: [1](#0-0) 

`call-pyth` reads prices directly from a hardcoded storage contract address: [2](#0-1) 

`call-dia` similarly hardcodes the DIA oracle address: [3](#0-2) 

Pyth's own governance contract enforces that only calls matching its `current-execution-plan` (oracle/decoder/storage/wormhole quad) succeed, rejecting stale combinations with `ERR_UNAUTHORIZED_ACCESS`: [4](#0-3) 

This execution-plan model is dynamic and has already been exercised through several real migrations (v1→v2→v3→v4) via `update-pyth-oracle-contract`, `update-pyth-storage-contract`, etc., with tests explicitly confirming that calls from an "outdated" contract combination are rejected: [5](#0-4) 

Since `market.clar` hardcodes one fixed combination rather than the live execution plan, once Pyth migrates again, `write-feed` will start failing (`ERR_UNAUTHORIZED_ACCESS` → surfaced as `ERR-PRICE-FEED-UPDATE-FAILED`), and no new prices will ever be written into the now-deprecated `pyth-storage-v4`. Meanwhile `call-pyth`/`resolve-pyth` keeps reading only from that same frozen storage contract. Price freshness is enforced later in `price-resolve` via `oracle-timestamp-fresh`, which compares the last feed timestamp against `max-staleness`: [6](#0-5) 

Once the frozen timestamp's age exceeds `max-staleness`, this staleness gate begins rejecting all price resolutions for every asset using the Pyth type oracle with `ERR-ORACLE-INVARIANT`, and there is no DAO/admin function in `market.clar` to repoint the hardcoded addresses (`assets.clar`'s `update` only touches `type`/`ident`/`callcode`/`max-staleness`, not the underlying oracle contract addresses used inside `market.clar`'s private functions).

### Impact Explanation
Once Pyth's live infrastructure moves past the hardcoded `v4`/`v3` instance, `market.clar` cannot receive fresh price updates for any Pyth-priced asset (STX, BTC, USDC, etc.). After `max-staleness` elapses, borrowing, withdrawing, liquidating, and health checks for every position holding those assets will permanently revert via `ERR-ORACLE-INVARIANT`, since there is no code path to point the contract's oracle calls elsewhere without deploying and DAO-migrating an entirely new market contract (and all dependent vault contracts). This is a freezing-of-funds impact: user collateral and debt positions become unmanageable (cannot be withdrawn, repaid, or liquidated) for as long as the migration takes, and could effectively become permanent for any position that isn't or can't be migrated before deprecation.

### Likelihood Explanation
Likelihood is driven entirely by Pyth's/DIA's own upgrade cadence, which the repository's own history shows is not hypothetical — the local Pyth governance contracts and deployment plans record multiple already-completed migrations (v1→v2→v3→v4 for oracle/storage/decoder, and equivalent wormhole-core upgrades) each requiring on-chain `update-pyth-*-contract` calls. Any future such migration on the live Pyth infra will silently desynchronize `market.clar`'s hardcoded addresses without any transaction or error until the staleness threshold is crossed.

### Recommendation
Store the Pyth oracle/storage/decoder/wormhole-core addresses (and the DIA oracle address) as DAO-updatable data-vars (or read them dynamically via Pyth's `get-current-execution-plan`) instead of literal `contract-call?` targets, and add a DAO-gated setter analogous to `assets.clar`'s `update` function so the addresses can be kept in sync with upstream governance migrations without requiring a full market contract redeployment.

### Proof of Concept
1. Pyth governance executes `update-pyth-storage-contract`/`update-pyth-oracle-contract` (as demonstrated in `ptgm.test.ts`) to move the live execution plan to `pyth-storage-v5`/`pyth-oracle-v5`.
2. `write-feed` in `market.clar` continues submitting VAAs against the hardcoded `pyth-oracle-v4`/`pyth-storage-v4`/`pyth-pnau-decoder-v3`/`wormhole-core-v4` combination; Pyth's `check-execution-flow` rejects it with `ERR_UNAUTHORIZED_ACCESS`, surfaced by `market.clar` as `ERR-PRICE-FEED-UPDATE-FAILED`.
3. No further updates ever land in `pyth-storage-v4`; `call-pyth` keeps returning the last pre-migration price/timestamp.
4. Once `stacks-block-time - timestamp > max-staleness` for an asset, every `price-resolve` call for that asset's oracle data reverts with `ERR-ORACLE-INVARIANT`, blocking deposits requiring health checks, borrows, repayments needing price, and liquidations for all positions holding that asset, with no on-chain remedy available in `market.clar`.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
