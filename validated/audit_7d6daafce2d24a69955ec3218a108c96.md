This confirms the bug. The analog contract `vlMGPBaseRewarder._calExpireForfeit` correctly computes `rewardableAmount = _amount * vlMGP.getRewardablePercentWAD(_account) / 1e18` [1](#0-0) , while `mWOMSVBaseRewarder._calExpireForfeit` was copy-pasted but the call to `mWOMSV.getRewardablePercentWAD(_account)` was dropped, leaving `rewardableAmount = _amount` so `forfeitAmount` is always `0` [2](#0-1) . `mWomSV.getRewardablePercentWAD` exists and correctly computes a reduced percentage for partially-unlocked/cooling-down balances [3](#0-2) , but it is never called from the rewarder.

### Title
Broken `_calExpireForfeit` in `mWOMSVBaseRewarder` lets any staker keep earning full mWomSV bonus rewards after starting unlock, with zero forfeiture - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` fails to call `mWomSV.getRewardablePercentWAD`, unlike the near-identical `vlMGPBaseRewarder` implementation, so `forfeitAmount` is hardcoded to always be `0` regardless of how much of a user's balance is in cooldown or fully unlocked. Consequently, `startUnlock`-ing 100% of a locked position immediately after locking (e.g. via `SmartWomConvert.convertFor(..., mode=2)` → `mWomSV.lockFor`, but equally reachable via direct `mWomSV.lock`) does not reduce a staker's bonus reward rate at all, since `mWOMSVBaseRewarder.balanceOf` reads the full staked amount from `MasterMagpie.stakingInfo` which is unaffected by `startUnlock` (only `unlock()` after cooldown calls `withdrawMWomSVFor`) [4](#0-3) [5](#0-4) [6](#0-5) .

### Finding Description
`_sendReward` computes the amount to forfeit via `_calExpireForfeit(_account, userRewards[...])` and only re-queues `forfeitAmount` back into the pool if it is nonzero [7](#0-6) . The forfeiture is supposed to penalize users who are not fully locked (partially or fully in cooldown), based on `mWomSV.getRewardablePercentWAD`, which returns a percentage under 100% for any account with cooldown balances [3](#0-2) .

However, in `mWOMSVBaseRewarder._calExpireForfeit`, `rewardableAmount` is simply set to `_amount` (the full accrued reward) instead of `_amount * getRewardablePercentWAD(_account) / 1e18`, so the subsequent check `rewardableAmount > _amount` can never be true and `forfeitAmount = _amount - rewardableAmount` is always `0` [2](#0-1) . Comparing to the sibling `vlMGPBaseRewarder`, which correctly wires in `vlMGP.getRewardablePercentWAD(_account)`, confirms this is a missing call / dead-code bug rather than intended behavior [8](#0-7) .

Because `balanceOf` in the rewarder is sourced from `MasterMagpie.stakingInfo(stakingToken, _account)` and that stake is only reduced when `unlock()` (post-cooldown) calls `IMasterMagpie.withdrawMWomSVFor` [5](#0-4) , a user who calls `startUnlock(fullAmount)` immediately after locking keeps their full reward-accrual weight in the rewarder throughout the entire cooldown, and — due to the broken forfeit — the `getReward`/`getRewards` calls will pay out 100% of that accrued bonus with no penalty [9](#0-8) .

`SmartWomConvert._convertFor` mode==2 is one path to mint mWOM and lock it via `mWomSV.lockFor(obtainedmWomAmount, _for)` [10](#0-9) , but it is not the root cause — any unprivileged account calling `mWomSV.lock`/`lockFor` directly and then `startUnlock` triggers the identical broken-forfeiture behavior. No modifier, `nonReentrant` guard, or accounting check in `startUnlock`, `getReward`, or `_sendReward` prevents this, because the bug is a missing computation, not a bypassable check.

### Impact Explanation
This is a real, permanent loss of the forfeiture mechanism (theft of unclaimed yield): stakers who never intend to keep their principal fully locked receive the same bonus reward rate as stakers who keep 100% locked, diluting the yield that the reward-forfeiture mechanism (`_queueNewRewardsWithoutTransfer`) was designed to redirect back to genuinely-locked stakers. Matches Immunefi's "theft of unclaimed yield" impact class. It is a protocol-wide reward-accounting defect, not a fund-drain of principal, and does not affect withdrawal of locked principal itself (that remains gated by the cooldown in `mWomSV.unlock`).

### Likelihood Explanation
Trivially and repeatably exploitable by any unprivileged account with no special capital requirement beyond the amount they wish to lock: lock (via `mWomSV.lock`, `lockFor`, or `SmartWomConvert.convertFor(mode=2)`) → `startUnlock(full amount)` immediately → call `getReward`/`getRewards` each epoch after `queueNewRewards`. No admin/governance role, flash loan, or reentrancy required. The bug is unconditional (always triggers `forfeitAmount == 0`), so it affects every user who does this, not just a targeted attacker.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder`'s implementation by computing `rewardableAmount = _amount * mWOMSV.getRewardablePercentWAD(_account) / 1e18` before comparing/forfeiting, i.e. wire in the existing `mWomSV.getRewardablePercentWAD` function that is already implemented but currently unused.

### Proof of Concept
Foundry fork test plan:
1. Deploy/fork with `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie`, and a reward token registered via `queueNewRewards`.
2. Account A: `mWomSV.lock(amount)` and keep fully locked for N epochs.
3. Account B (attacker): `mWomSV.lock(amount)` (same amount as A) then immediately `mWomSV.startUnlock(amount)` (100% into cooldown).
4. Each epoch: `rewarder.queueNewRewards(rewardAmount, token)` (as manager) to simulate emissions; advance time within cooldown boundaries (renewing/canceling+restarting `startUnlock` to remain perpetually in cooldown, or repeatedly calling `startUnlock` before `unlock()` to avoid ever completing withdrawal).
5. Call `getReward(A, A)` and `getReward(B, B)` each epoch.
6. Assert: `B`'s realized reward per epoch equals `A`'s (both receive full `rewardPerTokenStored * balance`), i.e. `calExpireForfeit(B, token) == 0` even though `mWomSV.getRewardablePercentWAD(B) < 1e18`, proving the forfeiture is dead and B suffers no penalty relative to A despite never maintaining a fully-locked position.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
