Found it: `AccountKeyRoleBased.DecodeRLP` recursively invokes RLP decoding of nested `AccountKeySerializer` values with no depth limit, and this is reachable via a public RPC call before any composite-type check occurs.

### Title
Unbounded recursion in `AccountKeySerializer`/`AccountKeyRoleBased` RLP decoding causes stack exhaustion - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`ALPINE-CVE-2026-40612` describes `jq`'s `jv_contains` recursing into nested JSON without a depth limit, exhausting the C stack when given deeply-nested but otherwise valid input. Kaia has an analogous unbounded-recursion pattern in the RLP decoding path for `AccountKey` values: `AccountKeySerializer.DecodeRLP` decodes a key-type byte and dispatches to `key.DecodeRLP`; when the type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` decodes a list of byte-strings and, for each element, calls `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, which can again be an `AccountKeyRoleBased`. There is no depth check during decoding itself — the "nested composite type is not allowed" rule is only enforced afterward, in `CheckInstallable`/`CheckUpdatable`, which run after the full recursive decode has already completed.

### Finding Description
- `AccountKeySerializer.DecodeRLP` [1](#0-0)  decodes a key type then recursively calls `s.Decode(serializer.key)`.
- When `serializer.key` is an `*AccountKeyRoleBased`, `AccountKeyRoleBased.DecodeRLP` [2](#0-1)  iterates over an attacker-supplied list of RLP-encoded sub-keys and calls `rlp.DecodeBytes(b, &serializer)` (a fresh `AccountKeySerializer`) for each element — which can itself decode to another `AccountKeyRoleBased`, recursing arbitrarily deep as long as the input contains nested `RoleBased`-typed byte strings.
- The safeguard against nested composite keys, `IsCompositeType()`/`ErrNestedCompositeType`, is only checked in `CheckInstallable` [3](#0-2)  and in the `checkAccountKeyZeroValues` RPC helper [4](#0-3) , both of which run only **after** the recursive `DecodeRLP` has fully unwound. If decoding itself overflows the goroutine stack, these downstream checks never execute.
- `KaiaAPI.DecodeAccountKey`, a public JSON-RPC method, takes arbitrary attacker-controlled bytes and feeds them directly into this recursive decode: `rlp.DecodeBytes(encodedAccKey, &dec)` [5](#0-4) . This is reachable by any unauthenticated public RPC caller with no transaction, fee, or gas required.
- The same decode path (`AccountKeySerializer`/`AccountKeyRoleBased.DecodeRLP`) is also used when decoding an `AccountUpdate` transaction's account key field from raw transaction bytes submitted via `eth_sendRawTransaction`/`kaia_sendRawTransaction`, meaning an unprivileged transaction sender can trigger the same unbounded recursion during tx-pool ingestion/RLP decoding, prior to any semantic validation such as `CheckInstallable`.

Unlike Go's `reflect`-based RLP struct decoders (whose recursion depth is bounded by the compile-time Go type graph), this path is a hand-written recursive `DecodeRLP` whose recursion depth is driven entirely by the *encoded byte content*, i.e., attacker-controlled input — directly analogous to `jv_contains` recursing based on JSON input structure rather than a fixed schema.

### Impact Explanation
A crafted RLP payload with many nested `AccountKeyRoleBased`-typed sub-keys can drive Go-level recursion deep enough to exhaust the goroutine stack, causing a fatal, unrecoverable runtime crash (Go stack-overflow panics cannot be caught by `recover()`). If reachable through:
- the public RPC method `DecodeAccountKey`, an unauthenticated caller can crash the node's RPC-serving process.
- the transaction RLP-decoding path for `AccountUpdate` transactions, an unprivileged sender can crash a node while it decodes/validates a submitted (possibly even unsigned/invalid) transaction in the mempool or during block processing, potentially crashing multiple nodes simultaneously if they all attempt to decode/gossip the same malicious payload — a availability-impacting, cross-node crash vector.

### Likelihood Explanation
Likelihood is limited by the following factors: (1) I was unable to confirm within the RLP stream decoding limits (`rlp.Stream` size/lists are bounded by the resource limits enforced in `willRead`/`listLimit`, see `rlp/decode.go`) how large an encoded nested-list payload of this shape can practically be before hitting the input-size limit — go-ethereum-style RLP has global size ceilings that may cap effective nesting depth well below what's needed to overflow a typical several-MB goroutine stack. (2) Whether the p2p/tx-pool ingestion path actually calls this recursive decoder before any other bound-checking (e.g., transaction size caps) was not fully traced. These are open questions that would need dynamic testing (constructing an actual deeply-nested payload and measuring stack growth) to establish real-world exploitability, which is outside what static code review can confirm.

### Recommendation
Add an explicit recursion-depth counter/limit to `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if depth > 1, consistent with the "no nested composite type" invariant that is already enforced post-hoc in `CheckInstallable`). Enforce this check *during* decoding, not only after full decode completion, so a malicious deeply-nested payload is rejected before recursion depth grows unbounded.

### Proof of Concept
Construct RLP bytes representing an `AccountKeySerializer` of type `AccountKeyTypeRoleBased` whose single "role key" element is itself an RLP-encoded `AccountKeySerializer` of type `AccountKeyTypeRoleBased`, repeated N times (e.g., N = 100,000, each nesting level encoded as `[keyTypeByte, innerBytes]`). Submitting this via:
```
curl -X POST --data '{"jsonrpc":"2.0","method":"kaia_decodeAccountKey","params":["0x<deeply-nested-RLP-hex>"],"id":1}' <RPC endpoint>
```
would drive `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` recursively N times before any `IsCompositeType`/`CheckInstallable` check is reached, exhausting the goroutine stack. I was not able to fully verify the exact N required to trigger a crash, or whether RLP's global size limits prevent constructing a payload of sufficient nesting depth — this would require dynamic testing with an actual Devin/engineering session against a running node.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
