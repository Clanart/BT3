### Title
`massUpdatePools()`/`updatePool()` lpSupply inflation via direct token donation dilutes `accMGPPerShare` for non-vlMGP/mWomSV pools - ([File: rewards/MasterMagpie.sol])

### Summary
`_calLpSupply()` computes the reward denominator for any pool other than the vlMGP/mWomSV pools as the raw `balanceOf(address(this))` of the staking/receipt token, rather than the sum of `UserInfo.amount` actually credited to stakers. `updatePool()`/`massUpdatePools()` are `public`/callable by anyone (only gated by `whenNotPaused`), so an attacker can transfer staking-token receipts directly to `MasterMagpie` and immediately call `massUpdatePools()` to inflate the denominator used to accrue `accMGPPerShare`, permanently diluting the MGP rewards distributable to legitimately staked balances.

### Finding Description
`_calLpSupply()` returns `IERC20(_stakingToken).balanceOf(address(this))` for any staking token that is not `vlmgp` or `mWomSV`: [1](#0-0) 

`updatePool()` uses this value directly as the divisor when accruing `pool.accMGPPerShare`: [2](#0-1) 

`massUpdatePools()` is a `public` function with no role restriction (only `whenNotPaused`), iterating over every registered pool and calling `updatePool()`: [3](#0-2) 

Because `balanceOf(address(this))` counts any tokens sitting in the contract — including tokens sent by a raw `transfer()` call that never goes through `_deposit`/`_stake` and never increments any `UserInfo.amount` — an attacker can inflate `lpSupply` without crediting themselves (or anyone) additional stake. This increases the divisor in `pool.accMGPPerShare = pool.accMGPPerShare + (mgpReward * 1e12) / lpSupply`, permanently reducing the per-share reward rate for the interval, since `accMGPPerShare` is monotonically accumulated and never re-based. Reward calculations for individual users (`_calNewMGP`, `_calMGPReward`) are keyed off `user.amount`, not the actual pool balance, so the diluted `accMGPPerShare` is applied uniformly to legitimately staked balances: [4](#0-3) [5](#0-4) 

The donated tokens themselves are not withdrawable by any staker (withdrawals are bounded by `UserInfo.amount`), so they remain stuck in the contract, permanently inflating the divisor for that pool going forward unless a compensating equal-or-greater amount is later staked.

### Impact Explanation
Any interval processed while the donated balance is inflated distributes MGP at a diluted rate to genuine stakers, and that diluted `accMGPPerShare` increment is permanent (it accumulates and is never corrected). This causes legitimate stakers to receive strictly less MGP than they are entitled to for that interval, i.e., a permanent reduction/freezing of yield that would otherwise have accrued to `UserInfo.amount` holders. This matches "Permanent freezing of unclaimed yield" in scope, since no owner/governance action is required and it is not reversible without an equal offsetting stake increase.

### Likelihood Explanation
The attack path is fully permissionless: `massUpdatePools()`/`updatePool()` have no caller restriction (`whenNotPaused` only), and `_calLpSupply()` is directly keyed off the raw ERC20 balance for any pool other than vlMGP/mWomSV. Any unprivileged EOA holding the staking token (or receipt token, e.g. an LP/receipt token pool) can execute the donation + `massUpdatePools()` call in a single transaction, at the cost of permanently losing the donated tokens (a pure griefing cost, no direct profit for the attacker, but real loss for stakers). It is repeatable on every pool of this type, and requires no special capital beyond acquiring the target staking token.

I could not fully verify from the retrieved code how `UserInfo.available` is set/used elsewhere (it appears declared in the struct but I did not locate assignment logic distinguishing it from `amount` in the excerpts reviewed), so I cannot confirm the specific claim that `available` diverges from `amount` as a result of this issue; the confirmed, concrete impact is dilution of `accMGPPerShare`/reward yield via `_calLpSupply`'s use of raw balance.

### Recommendation
Track staked supply internally (e.g., a `pool.totalStaked` counter incremented/decremented only in `_deposit`/`_withdraw`) instead of relying on `IERC20(_stakingToken).balanceOf(address(this))` in `_calLpSupply()`, so direct token donations cannot affect the reward-accrual denominator.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, register a pool with a mock ERC20 staking token and a V1 `BaseRewardPool` rewarder.
2. Have user A `deposit` a known amount into the pool (credits `UserInfo.amount`).
3. Advance time; from an unprivileged EOA, `transfer()` (not deposit) additional staking tokens directly to `MasterMagpie`.
4. Call `massUpdatePools()` from the same unprivileged EOA.
5. Assert: `pool.accMGPPerShare` increment for that interval is smaller than it would have been absent the donation (compute expected `mgpReward * 1e12 / userA.amount` vs actual using inflated `lpSupply`).
6. Assert user A's claimable MGP (`_calMGPReward`) is less than the undiluted expectation, demonstrating permanent yield loss for the interval.

    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }

    function _calMGPReward(address _stakingToken, address _user) internal view returns(uint256 pendingMGP) {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_user];
        uint256 accMGPPerShare = pool.accMGPPerShare;
        uint256 lpSupply = _calLpSupply(_stakingToken);

        if (block.timestamp > pool.lastRewardTimestamp && lpSupply != 0) {
            uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
            uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) /
            totalAllocPoint;
            accMGPPerShare = accMGPPerShare + (mgpReward * 1e12) / lpSupply;
        }

        pendingMGP = (user.amount * accMGPPerShare) / 1e12 - user.rewardDebt;
        pendingMGP += unClaimedMgp[_stakingToken][_user];
