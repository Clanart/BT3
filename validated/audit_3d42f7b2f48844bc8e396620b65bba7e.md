### Title
Type confusion in shared `tx.from` sigCache field causes runtime panic across chain nodes - ([File: blockchain/types/transaction_signing.go])

### Summary
`SenderFrom` and `SenderPubkey` in `blockchain/types/transaction_signing.go` both read/write the *same* `tx.from` `atomic.Value` field, but they store and type-assert two different, mutually-incompatible concrete types (`sigCache` vs `sigCachePubkey`). Whichever function is called first on a given `*Transaction` "wins" and poisons the cache slot for the other function, and the second caller's unchecked type assertion panics.

### Finding Description
`Transaction.from` is a single `atomic.Value` cache slot shared by two unrelated caching helpers:

- `SenderFrom` stores/reads `sigCache{signer, from}` in `tx.from` [1](#0-0) 
- `SenderPubkey` stores/reads `sigCachePubkey{signer, pubkey}` in the **same** `tx.from` slot [2](#0-1) 

Both accessors perform an unchecked (single-value) type assertion immediately after `Load()`:
```go
sigCache := sc.(sigCache)         // SenderFrom, line 193
...
sigCache := sc.(sigCachePubkey)   // SenderPubkey, line 216
``` [3](#0-2) [4](#0-3) 

If `SenderFrom(signer, tx)` is invoked first (populating `tx.from` with a `sigCache` value) and later `SenderPubkey(signer, tx)` is invoked on the *same transaction object* (or vice versa), the second call's type assertion `sc.(sigCachePubkey)` (or `sc.(sigCache)`) does not match the stored concrete type and panics with "interface conversion" — an unrecovered runtime panic. This is the same root-cause bug class as the PostgreSQL `refint` advisory: a cache/slot that is reused across two logically distinct "plans"/types without a discriminator check, so a value produced under one type is later interpreted as the other type.

The analogous parallel cache pair `SenderFeePayerPubkey`/(fee-payer address caching) uses a separate `tx.feePayer` field consistently for `sigCachePubkey` only, so that pair is not affected the same way; the collision is specifically between `SenderFrom` and `SenderPubkey` both keying off `tx.from`. [5](#0-4) 

Both `SenderFrom` and `SenderPubkey` are reachable on transactions submitted by ordinary users: `Sender()` (called throughout tx-pool admission, block assembly, and signature validation) calls `SenderFrom` for Ethereum-typed transactions [6](#0-5) , while `SenderPubkey` is used wherever the sender's public key must be recovered (e.g. AccountKey signature validation paths for `AccountKeyPublic`/`AccountKeyWeightedMultiSig`/`AccountKeyRoleBased`). Any code path that calls both accessors on the same `*Transaction` instance — e.g., first computing `Sender()` during pool admission/gas estimation and later computing `SenderPubkey()` during full signature validation of an AccountKey-based sender, or the reverse ordering across different subsystems (RPC `eth_sendRawTransaction` handling vs. txpool validation vs. block execution) touching the identical in-memory transaction object — triggers the panic.

### Impact Explanation
An unrecovered panic in transaction sender/pubkey derivation, triggered by a single crafted (but otherwise valid) transaction whose processing path exercises both `SenderFrom` and `SenderPubkey` on the same object, can crash the node goroutine handling that transaction. Because this code sits in the hot path of tx-pool admission, gasless/AccountKey signature validation, and block execution, a reachable panic here is a public, unprivileged-transaction-triggerable denial-of-service against full nodes, and if it fires inconsistently between nodes (e.g., depending on goroutine scheduling / cache warm state) it also risks state divergence between honest nodes processing the same transaction in different call orders.

### Likelihood Explanation
The likelihood depends on whether any real call path exercises `SenderFrom` and `SenderPubkey` on the same `*Transaction` pointer. Given `Sender()` is the general entry point used for `from` address resolution and `SenderPubkey` is used for full multi-sig/AccountKey signature-recovery validation, and given transaction objects are commonly reused (not re-parsed) between pool admission and validation/execution stages, this ordering is plausible in normal AccountKey-based transaction processing rather than requiring an unusual attacker setup. I was not able to fully confirm every concrete call site pairing within the available index (some call sites in `blockchain/tx_pool.go`, `api/api_kaia_transaction.go`, and AccountKey validation code were only partially visible), so the exact triggering path should be confirmed against the full source before treating this as fully proven.

### Recommendation
- Use distinct cache fields for `SenderFrom`/`Sender` results (`sigCache`) versus `SenderPubkey` results (`sigCachePubkey`), mirroring how `tx.feePayer` is kept separate from `tx.from`.
- Replace all single-value type assertions on cache loads (`sc.(sigCache)`, `sc.(sigCachePubkey)`) with the two-value form (`sc, ok := sc.(sigCache)`) and fall through to recomputation on a type mismatch instead of panicking.
- Add a regression test that calls `SenderPubkey` then `SenderFrom` (and the reverse) on the same `*Transaction` to ensure no panic occurs.

### Proof of Concept
Conceptual reproduction (matches code at [7](#0-6) ):
```go
tx := <any validly signed Ethereum-typed transaction>
signer := types.LatestSignerForChainID(chainID)

// Step 1: populate tx.from with sigCache{...}
_, _ = types.SenderFrom(signer, tx)

// Step 2: SenderPubkey loads tx.from, which currently holds a sigCache value,
// and does sc.(sigCachePubkey) unconditionally -> panic: interface conversion
_, _ = types.SenderPubkey(signer, tx)
```
Any subsystem that resolves a transaction's `from` address first (pool admission, `Sender()`) and later needs the sender's public key for AccountKey validation (`SenderPubkey()`) on the identical transaction object reproduces the panic without recovery, crashing the goroutine/node processing the transaction.

func SenderFrom(signer Signer, tx *Transaction) (common.Address, error) {
	if sc := tx.from.Load(); sc != nil {
		sigCache := sc.(sigCache)
		if signer.IsCompatibleWith(sigCache.signer, tx) {
			return sigCache.from, nil
		}
	}

	addr, err := signer.Sender(tx)
	if err != nil {
		return common.Address{}, err
	}
	tx.from.Store(sigCache{signer: signer, from: addr})
	return addr, nil
}

// SenderPubkey returns the public key derived from the signature (V, R, S) using secp256k1
// elliptic curve and an error if it failed deriving or upon an incorrect
// signature.
//
// SenderPubkey may cache the public key, allowing it to be used regardless of
// signing method. The cache is invalidated if the cached signer does
// not match the signer used in the current call.
func SenderPubkey(signer Signer, tx *Transaction) ([]*ecdsa.PublicKey, error) {
	if sc := tx.from.Load(); sc != nil {
		sigCache := sc.(sigCachePubkey)
		if signer.IsCompatibleWith(sigCache.signer, tx) {
			return sigCache.pubkey, nil
		}
	}

	pubkey, err := signer.SenderPubkey(tx)
	if err != nil {
		return nil, err
	}
	tx.from.Store(sigCachePubkey{signer: signer, pubkey: pubkey})
	return pubkey, nil
}
