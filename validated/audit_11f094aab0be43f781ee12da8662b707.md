### Title
Hookify `RuleEngine.evaluate_rules` silently drops the "block" enforcement for `UserPromptSubmit` (and any non-PreToolUse/PostToolUse/Stop) rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The Malt `Bonding.sol` bug is a case where a downstream edge case (the DEX handler returning zero tokens) is silently handled by returning value to the wrong place, but the calling contract has no logic to recognize or forward it, so the user's protection/value is lost. The analogous pattern in this codebase is in the Hookify plugin's rule engine: when a `block` rule matches for an event type outside `PreToolUse`/`PostToolUse`/`Stop` — which includes `UserPromptSubmit`, the plugin's own documented event type — the enforcement action is never emitted, so a rule the user configured to *block* is silently downgraded to a no-op message.

### Finding Description
`RuleEngine.evaluate_rules` branches on `hook_event` to decide how to render a blocking decision: [1](#0-0) 

For `Stop` it emits `{"decision": "block", ...}`; for `PreToolUse`/`PostToolUse` it emits `{"hookSpecificOutput": {"permissionDecision": "deny"}, ...}`. For every other `hook_event_name` — the `else` branch — it only returns `{"systemMessage": combined_message}` with no `decision`, no `permissionDecision`, nothing that Claude Code's hook runner recognizes as a block.

`userpromptsubmit.py` is exactly one of these "other" callers: it loads `event='prompt'` rules and calls `evaluate_rules` the same way as the Pre/PostToolUse and Stop hooks, but its `hook_event_name` will be `UserPromptSubmit`, which falls into the unhandled `else` branch: [2](#0-1) 

The `Rule` dataclass explicitly supports `action: "block"` for any rule regardless of `event` value (`"bash"`, `"file"`, `"stop"`, `"prompt"`, `"all"`): [3](#0-2) 

So a user can legitimately author a `.claude/hookify.*.local.md` rule with `event: prompt` and `action: block` intending to block a dangerous user prompt (e.g., one containing a secret or an instruction to exfiltrate data) before it reaches Claude — but the engine's edge-case handling for that event type never translates the match into an actual block; it degrades to a cosmetic `systemMessage`. Compounding this, every hookify hook entrypoint (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) unconditionally `sys.exit(0)` in a `finally` block, so there is no secondary defense (e.g., non-zero exit) that would cause Claude Code's hook runner to treat the event as blocked: [4](#0-3) 

### Impact Explanation
This is a fail-open security-control bypass in the unprivileged-user "hook bypass" trust boundary listed as in-scope. A user (or org) who configures Hookify blocking rules on `UserPromptSubmit` to prevent sensitive prompts/content from proceeding will have those rules silently ignored — the prompt proceeds to Claude unblocked even though the intended control was to stop it, exactly mirroring the original bug's core defect: an edge case in a downstream component isn't accounted for by the orchestrating layer, so the protective/return path that should occur never does, and the caller has no way to notice or recover.

### Likelihood Explanation
Likelihood is moderate-to-high for any Hookify user who defines `event: prompt` + `action: block` rules, since this is a directly supported and documented configuration surface of the plugin, not a contrived corner case — the `Rule.from_dict` and `load_rules(event=...)` machinery treats `prompt` as a first-class event type equal to `bash`/`file`/`stop`. Any user relying on Hookify to block risky prompts will trigger this silently, without any error or warning, since the hook still exits 0 and prints a "message" that looks like normal output.

### Recommendation
In `RuleEngine.evaluate_rules`, extend the blocking branch to cover `UserPromptSubmit` (and ideally any event) by emitting the appropriate hook-specific block payload — e.g., `{"decision": "block", "reason": ...}` for `UserPromptSubmit` per Claude Code's hook output contract — rather than falling through to a message-only response. More robustly, the `else` branch should fail closed (or at minimum log a clear warning) when a `block`-action rule matches but the engine doesn't know how to enforce it for that event, instead of silently converting a block into a warning.

### Proof of Concept
1. Create `.claude/hookify.prompt-block.local.md`:
```
---
name: block-secret-prompt
enabled: true
event: prompt
action: block
pattern: "AWS_SECRET_ACCESS_KEY"
---
Blocking prompts containing AWS secrets.
```
2. Submit a user prompt containing `AWS_SECRET_ACCESS_KEY=...`.
3. `userpromptsubmit.py` calls `load_rules(event='prompt')` → the rule matches → `RuleEngine.evaluate_rules` puts it in `blocking_rules` since `action == 'block'`.
4. Because `hook_event_name == "UserPromptSubmit"`, the function falls into the `else` branch at [5](#0-4)  and returns only `{"systemMessage": ...}`.
5. `userpromptsubmit.py` prints this JSON and exits 0 — Claude Code sees no block signal and processes the prompt normally, despite the user's explicit `action: block` rule.
