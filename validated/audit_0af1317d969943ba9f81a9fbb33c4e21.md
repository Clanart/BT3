### Title
Attacker-controlled output spam forces `SignableTransaction::new`/`TransactionSignMachine::sign` to always fail once the multisig accumulates too many received outputs - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

The external report describes a function that iterates over an array whose size grows with public activity (`positions[]` grown by `nextPositionId`), so that once the set is large enough the call always reverts and becomes unusable for integrators.

The analogous shape in Serai is the Bitcoin wallet path. `Scanner::scan_transaction`/`scan_block` collect *every* output paying to a registered script into `Vec<ReceivedOutput>` (`networks/bitcoin/src/wallet/mod.rs:199-227`), and `SignableTransaction::new` then consumes the entire `inputs: Vec<ReceivedOutput>` set, iterating it repeatedly (`input_sat` sum at line 175, `offsets`/`tx_ins`/`prevouts` maps at lines 176-185, 253) and constructing one FROST `AlgorithmMachine` per input in `multisig()` (line 275). Anyone can grow the received-output set without limit by sending dust outputs to the wallet's P2TR script. Once `weight > MAX_STANDARD_TX_WEIGHT` (line 241), `SignableTransaction::new` deterministically returns `TransactionError::TooLargeTransaction`, so any spend/consolidation attempt over that output set always fails — the same "always reverts when the set is too big" behavior as `getPositionIdsByOwner()`.

### Finding Description

- `Scanner::register_offset` inserts attacker-payable scripts into `self.scripts`, and `scan_transaction` pushes a `ReceivedOutput` for every matching output with no bound on `res` (`networks/bitcoin/src/wallet/mod.rs:180-214`).
- `SignableTransaction::new` performs multiple full passes over `inputs` (`send.rs:175-191`) and unconditionally errors with `TooLargeTransaction` when the transaction weight exceeds `MAX_STANDARD_TX_WEIGHT` (`send.rs:241-243`). A P2TR input is ~58 vbytes, so roughly ~4-7k inputs guarantee failure.
- `SignableTransaction::multisig` creates an `AlgorithmMachine` and performs an `offset`/`p2tr_script_buf` check per input (`send.rs:275-282`), and `TransactionSignMachine::sign` iterates `commitments.iter()` once per input (`send.rs:364-371`), making signing work O(inputs × participants) before it even reaches the sighash loop (`send.rs:377-395`).

There is no pagination, selection bound, or chunking — the entire received-output vector must be processed in a single call.

### Impact Explanation

An unprivileged party can send a large number of minimum-value (>= `DUST = 546` sats, `send.rs:32`) outputs to the multisig's registered Taproot script. Any signing flow that consumes the accumulated `Vec<ReceivedOutput>` will then deterministically fail at `send.rs:241` with `TooLargeTransaction`, and `multisig`/`sign` waste CPU proportional to inputs × participants before that. This permanently degrades the spend path for integrators until they implement manual input subset selection, mirroring the third-party-integration breakage in the original report.

### Likelihood Explanation

The attacker only needs to broadcast ordinary Bitcoin transactions to a publicly known script — a fully public-input attack requiring no validator status, collusion, or leaked material. The cost to the attacker is dust-value outputs they cannot recover, but per-output cost is small (~546 sats minimum) while each forced input permanently inflates every subsequent spend attempt's weight and signing work.

### Recommendation

Bound the number of inputs accepted by `SignableTransaction::new` (e.g., reject `inputs.len()` above a conservative limit derived from `MAX_STANDARD_TX_WEIGHT` before doing any work, rather than after building `tx_ins`/`tx_outs`), and provide/prescribe coin selection so callers pass a bounded subset of `ReceivedOutput`s instead of the full scanned set. In `Scanner`, consider capping or batching outputs returned per `scan_transaction`/`scan_block` call.

### Proof of Concept

1. Obtain the multisig's P2TR `ScriptBuf` (public; derivable from the group key via `p2tr_script_buf`).
2. Broadcast transactions creating N outputs of 546+ sats to that script, where N × ~58 vbytes exceeds `MAX_STANDARD_TX_WEIGHT` (~400,000 WU → ~6,900 inputs).
3. `Scanner::scan_block`/`scan_transaction` returns all N as `ReceivedOutput`s.
4. `SignableTransaction::new(all_outputs, payments, change, None, fee)` reaches `send.rs:241` and returns `Err(TransactionError::TooLargeTransaction)` on every attempt; `multisig()`/`sign()` additionally scale O(N × participants) before producing shares.

Caveat: a caller that itself selects a bounded subset of inputs avoids the failure, so the concrete impact depends on the consuming code passing the full scanned set; the wallet library provides no bound or selection helper to make that safe by default.
