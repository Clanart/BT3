## Analysis Summary

The Sherlock bug (H-24) is a "shared bookkeeping helper is invoked from multiple execution paths, and the helper's window/scope tracking is corrupted across those paths, causing balance deltas to be applied to the wrong account or not at all." The reachable Cosmos EVM analog is the `BalanceHandler` mechanism that bridges bank-module coin-spent/received events into `StateDB.AddBalance`/`SubBalance` calls for stateful precompiles. [1](#0-0) [2](#0-1) 

The repository itself already contains a regression test whose docstring names this exact bug class: [3](#0-2) 

### Title
Nested/recursive precompile calls cause `BalanceHandler` event-window overlap, leading to double-application of balance deltas to `StateDB` — (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
`BalanceHandler.BeforeBalanceChange` records a cursor (`prevEventsLen`) into the shared `ctx.EventManager().Events()` slice, and `AfterBalanceChange` replays every bank event emitted since that cursor into `StateDB.AddBalance`/`SubBalance`. When a stateful precompile call is nested — i.e., a precompile's native action itself triggers another EVM call that re-enters `runNativeAction` (recursive/callback precompile invocation, contract-to-contract reentrancy through the debug/erc20/staking/distribution/ics20 precompiles) — both the inner and the outer `BalanceHandler` instances read from the *same* underlying `EventManager` event log. The inner call's `AfterBalanceChange` consumes and applies its own event slice to `StateDB`. When control returns to the outer call, the outer's `AfterBalanceChange` replays events from `events[outerPrevEventsLen:]`, a window that still includes the events already consumed and applied by the inner call. This causes the same `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events to be applied to `StateDB` a second time. [4](#0-3) 

### Finding Description
`runNativeAction` snapshots gas/state, executes the native precompile action, and then calls `AfterBalanceChange` to sync `x/bank`/`x/precisebank` state changes into the EVM `StateDB`: [2](#0-1) 

`AfterBalanceChange` walks the full `ctx.EventManager().Events()` slice starting at `bh.prevEventsLen` (captured once, before the action ran) up to the *current* length at call time, and unconditionally applies `AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` event in that window: [5](#0-4) 

Because `ctx` is derived from `stateDB.GetCacheContext()` and its `EventManager` is not scoped/reset per nested precompile invocation, any events emitted by an inner (nested) precompile call remain visible in the outer call's post-action event window. The inner call already applied those deltas to `StateDB` during its own `AfterBalanceChange`. The outer call, having captured its `prevEventsLen` before the inner call ran, will re-process the same events and apply the deltas to `StateDB` again — this is a classic "shared cursor state not isolated across nested invocations" bug, structurally identical to `repayBorrowInternal` being invoked from both the same-chain and cross-chain repayment flows without properly scoping which borrow ledger to touch.

The project's own test suite documents this exact failure mode and reproduces it with a caller contract that recursively invokes a debug precompile, showing an event/log-count mismatch (`15` total events vs. `10` expected `debug_precompile` events) consistent with double-counted/duplicated balance-changing events during recursive precompile calls: [6](#0-5) 

### Impact Explanation
If a bank-mediated balance delta (a `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` event) is replayed into `StateDB.AddBalance`/`SubBalance` more than once, the EVM-visible balance for an account diverges from its true `x/bank`/`x/precisebank` balance without any corresponding real transfer. This breaks the strict 1:1 invariant between native coin balances and EVM balances that `x/vm`, `x/precisebank`, and the precompile balance-sync layer are specifically designed to preserve (see `x/vm/keeper/statedb.go SetBalance`, which mints/burns aatom purely based on comparing `StateDB` balance deltas against `x/bank` spendable coin). An attacker who can trigger a nested/recursive call into a stateful precompile that moves coins (e.g., ERC20 precompile `transfer`/`transferFrom`, staking/distribution/ICS20 precompiles) from within the same precompile call (contract calls back into the same precompile, or one precompile call is invoked as part of the action of another) can cause `StateDB` to record more (or less) balance than what is actually backed by `x/bank`, resulting in irreversible accounting corruption / unauthorized inflation of spendable EVM-visible value — matching the Critical "unauthorized minting/duplication ... accounting corruption of spendable user value across EVM balances" impact class.

### Likelihood Explanation
This does not require any privileged role — it requires only an unprivileged EVM caller to construct a contract that triggers a nested precompile invocation (calling a stateful precompile from within the execution triggered by another stateful precompile call, or recursively re-entering the same one), which is standard, permissionless smart-contract composition. The repository's own dedicated test (`TestRecursivePrecompileCallsWithDebugPrecompile`) exists specifically to exercise and document this scenario, indicating the code path is both reachable and already known to produce anomalous event counts.

### Recommendation
Scope the event window strictly to the current invocation: either (a) snapshot/truncate `ctx.EventManager()` to a fresh event manager per `runNativeAction` call (so nested calls cannot observe or double-consume the outer call's or an inner call's already-applied events), or (b) have `AfterBalanceChange` mark each event as consumed (e.g., track a running “last processed index” shared via the cache context or `StateDB`, incremented after each consumption) instead of relying purely on a call-local start offset compared against a shared, ever-growing event log. Add an invariant check comparing total `StateDB` balance for touched addresses against `x/bank`/`x/precisebank` spendable coin at the end of nested precompile execution and fail/revert on mismatch.

### Proof of Concept
The repository already contains a reproducing test: `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile` deploys a `DebugPrecompileCaller` contract that recursively calls a `debug` precompile registered with a `BalanceHandler`, and asserts the resulting event counts (`15` total events, `10` `debug_precompile` events), demonstrating that recursive precompile invocation produces divergent/duplicated event processing under the shared `BalanceHandler` cursor model. [7](#0-6) 

**Note on confidence**: I confirmed that `runNativeAction` allocates a *new* `BalanceHandler` per call via `BalanceHandlerFactory.NewBalanceHandler()` [8](#0-7) , so the "sharing" is at the level of the underlying `ctx.EventManager()` event log/cursor overlap between nested calls rather than a literal shared Go struct pointer. I was not able to fully trace, within the available iterations, the exact call chain in a production (non-debug) precompile — e.g., ERC20/staking/distribution/ICS20 — that produces genuine reentrant/nested `runNativeAction` invocations with real fund-moving events (as opposed to the debug precompile used in the existing test), so the concrete attacker-reachable precompile combination that turns this into fund duplication should be verified with a full Devin session that can build and run a PoC against one of the real value-moving precompiles (e.g., `erc20` or `distribution`) to confirm double `AddBalance` application with actual `aatom`/coin transfers.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())

	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()
