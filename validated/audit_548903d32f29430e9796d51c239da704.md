### Title
Cross-chain `tierPrice` desynchronization lets any buyer under-pay for bandwidth (stale governance-pushed rate, no on-chain freshness check) - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.purchase()` charges buyers using a locally-cached `tierPrice[tier]` that is pushed asynchronously, per chain, by governance via `pallet-bandwidth::dispatch_set_tiers`. Unlike `SimplexPaymaster`, which enforces `maxOracleAge`/staleness checks on every price read, `BandwidthManager` has no notion of price freshness or cross-chain consistency — the docs themselves flag that "the same SKU costs different amounts depending on which chain a buyer is on" until every deployment is manually re-pushed. This is structurally identical to the Boba report's core flaw: a value-denominating rate that is updated out-of-band/periodically by an operator, consumed unconditionally by a public, unprivileged entrypoint that moves real value, with no on-chain mechanism to reject a stale rate.

### Finding Description
`purchase()` reads `tierPrice[tier]` (an 18-decimal USD-denominated price set solely by the last `SetTiers` governance message delivered to *this* chain's manager) and transfers exactly that amount of the local fee token from the caller: [1](#0-0) 

There is no staleness bound, no timestamp recorded with the price, and no cross-chain oracle check — contrast this with `SimplexPaymaster._getOraclePrice`, which explicitly reverts if `block.timestamp - updatedAt > maxOracleAge`: [2](#0-1) 

`tierPrice` is instead set purely by whichever `SetTiers` message last landed on this chain's manager, dispatched one chain at a time by governance: [3](#0-2) 

The pallet's byte/duration side of a tier (`TierConfig`) is *global* across all chains, while the price side is deployed and updated *independently per chain* via `dispatch_set_tiers(target, [(tier, price)])`. The documentation explicitly acknowledges the resulting arbitrage window and places the entire burden of avoiding it on governance diligence rather than on-chain enforcement:

> "If you change a tier's price, dispatch the update to every chain where a manager is deployed — otherwise the same SKU costs different amounts depending on which chain a buyer is on." [4](#0-3) 

This is exactly the Boba pattern: an off-chain/asynchronous updater (there: the 5-minute gas-price-oracle service; here: governance's manual per-chain `dispatch_set_tiers` calls) maintains a rate that a public function consumes without validating recency or cross-chain agreement, and the amount of "value" (bandwidth bytes, globally fixed per tier) delivered per unit paid is fixed to whichever stale number happens to sit in that chain's `tierPrice` mapping.

### Impact Explanation
Any unprivileged caller can monitor `tierPrice(tier)` across every chain where a `BandwidthManager` is deployed. Whenever governance updates the USD-anchored price on one chain (e.g., raising a tier's price to track fee-token depreciation, or correcting an initial misconfiguration) but has not yet completed the multi-transaction rollout to every other chain, an attacker buys the maximum affordable quantity of the *same globally-defined* byte/duration allotment on the chain(s) still running the stale (lower) price. Because `TierConfig.bytes`/`duration_secs` are pallet-global and not chain-specific, the attacker receives identical bandwidth value for less fee-token payment than the protocol intended, at the expense of the treasury's expected revenue for that finite, protocol-metered resource. This is a direct, repeatable, real-fund-denominated loss to the protocol (systemic underpricing/arbitrage of a custodial storefront contract), triggerable by any address with no privileged role, relayer, or prover assumption — matching the bounty's "logic attacks" / "loss of funds" category.

### Likelihood Explanation
Likelihood is high in practice: tier price changes are a normal, expected governance operation (fee-token repricing, SKU adjustments), and the multi-chain rollout is inherently non-atomic (separate ISMP dispatches per chain, each requiring independent relayer delivery and confirmation). The window between the first and last chain's price update is attacker-observable on-chain (`tierPrice` is a public mapping) and requires zero privileged access — only calling `purchase()` before the propagation completes.

### Recommendation
- Record a `lastUpdated` timestamp alongside each `tierPrice` entry and optionally reject purchases if the local price is older than a governance-configured max age, mirroring `SimplexPaymaster.maxOracleAge`.
- Alternatively, redesign the sync flow so a chain's manager cannot process purchases against a tier price known to be stale relative to the last dispatched update sequence number (e.g., include a monotonically increasing epoch/nonce in `SetTiers` and reject/flag divergence at the pallet level when reconciling revenue).
- Consider bounding per-transaction purchase size or adding a cooldown immediately after a `SetTiers` dispatch to shrink the arbitrage window while propagation is in flight.

### Proof of Concept
1. Governance decides tier 2's price should rise from `50e18` to `80e18` (18-decimal USD) to reflect an increase in the underlying resource cost, and calls `dispatch_set_tiers(StateMachine::Evm(1), [(TierTwo, 80e18)])` for Ethereum first.
2. The ISMP message to Ethereum's `BandwidthManager` is delivered and `tierPrice[2]` becomes `80e18` there, but the equivalent dispatch to `StateMachine::Evm(8453)` (Base) has not yet been relayed/confirmed — Base's manager still holds `tierPrice[2] == 50e18`: [3](#0-2) 
3. An attacker monitoring both chains' `tierPrice(2)` views calls `purchase(app, 2, months, "EVM-8453")` on Base repeatedly, paying the stale `50e18`-per-month price: [1](#0-0) 
4. Because `TierConfig.bytes`/`duration_secs` for tier 2 are global on the pallet (not per-chain), the attacker's purchase credits the exact same byte/duration allotment as an Ethereum purchase would at the higher, intended price — extracting the price differential as pure arbitrage against the protocol's revenue expectations, with no privileged role, relayer collusion, or malformed proof required.

    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
