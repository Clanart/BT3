### Title
Scanner::scan_block reports immature coinbase outputs as spendable ReceivedOutputs, yielding consensus-invalid spends - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including `block.txdata[0]` (the coinbase), and returns any output paying to a registered script_pubkey as a `ReceivedOutput` indistinguishable from a normal output. An unprivileged miner can create a coinbase output paying the multisig's P2TR script; it will be reported as received funds, yet it is consensus-unspendable for 100 blocks. Any `SignableTransaction` built over it produces a transaction that will never be accepted by the network.

### Finding Description
`Scanner::new` registers the tweaked-key P2TR script, and `register_offset` registers offset scripts in `self.scripts`. `scan_transaction` matches purely on `output.script_pubkey` and constructs a `ReceivedOutput` for each match. `scan_block` then calls `scan_transaction` on **all** transactions, including the coinbase: [1](#0-0) 

There is no maturity marker, no filtering, and no way for a caller holding a `ReceivedOutput` to distinguish an immature coinbase output from a normal output: [2](#0-1) 

The doc comment acknowledges the caveat ("This will also scan the coinbase transaction which is bound by maturity"), but the function still performs the scan and returns the immature output through the same `Vec<ReceivedOutput>` channel as spendable outputs.

### Impact Explanation
Bitcoin consensus rules forbid spending a coinbase output until it has 100 confirmations. A `ReceivedOutput` obtained from `scan_block` flows into `SignableTransaction::new` as a normal input: [3](#0-2) 

The resulting transaction is signed successfully by `TransactionSignMachine` (the sighash, Schnorr shares, and completion all succeed — nothing checks maturity) but is invalid at the consensus layer and will be rejected by every node. This mirrors the oracle bug: a rule meant to constrain behavior (coinbase maturity / spot-vs-TWAP deviation) is enforced downstream rather than at the reporting/valuation point, so the pipeline produces a result that fails exactly when it is consumed. Funds are reported as received and usable when they are not, and any spend plan containing them produces a permanently-invalid transaction, stalling the payout that was attempted.

### Likelihood Explanation
Any miner on the Bitcoin network — an unprivileged party — can include a P2TR output paying the multisig's (or an offset) script_pubkey in their coinbase transaction at zero marginal cost. `scan_block` will then emit it. The path requires no privileges, no collusion, and no control over Serai validators; it only requires broadcasting a valid block, which miners do routinely. Whether a downstream consumer post-filters is outside the audited surface; within `bitcoin-serai` itself the bug is fully present and reachable.

### Recommendation
Do not scan `txdata[0]` in `scan_block`, or mark `ReceivedOutput`s derived from coinbase transactions (e.g., via `Transaction::is_coinbase()`) and exclude them from results until maturity. Concretely, change the loop to `for tx in &block.txdata[1 ..]` or check `tx.is_coinbase()` inside `scan_transaction` callers that require immediately spendable outputs, rather than relying on every consumer to reimplement the post-processing pass noted in the comment.

### Proof of Concept
1. An external miner constructs a coinbase transaction containing `TxOut { value: v, script_pubkey: <multisig's tweaked P2TR script> }` (obtainable via `p2tr_script_buf` on the group key, or simply observed on-chain) and mines a block containing it.
2. `Scanner::scan_block(&block)` returns a `ReceivedOutput` with `offset = Scalar::ZERO` and that outpoint, reported identically to any spendable output.
3. A spend attempt `SignableTransaction::new(vec![received], payments, change, data, fee)` succeeds, `multisig(keys)` succeeds since `p2tr_script_buf` matches, and `complete` produces a fully-signed transaction.
4. Broadcasting fails: Bitcoin consensus rejects any transaction spending a coinbase with fewer than 100 confirmations (`bad-txns-premature-spend-of-coinbase`). The reported-received funds are not spendable, and the constructed spend is invalid regardless of how many signatures are collected.

Note: I could not inspect `processor/src/networks/bitcoin.rs` (outside the allowed scope) to confirm whether the consumer performs the documented post-processing filter; the finding stands on the in-scope code, where `scan_block` itself emits immature outputs as spendable.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
