## Title
Unbounded per-block staking unbonding-queue drain lets a funded attacker halt/delay `EndBlock` (`DequeueAllMatureUBDQueue` / `BlockValidatorUpdates`) - (File: `sei-cosmos/x/staking/keeper/delegation.go`, `sei-cosmos/x/staking/keeper/val_state_change.go`)

### Summary
`x/staking`'s `EndBlocker` unconditionally drains and fully processes every unbonding-delegation entry that matures in a given block, with no per-block cap on the number of entries processed. Because any account can create an unbonding-delegation entry cheaply (small delegate + undelegate), and Undelegate completion time is deterministic (`ctx.BlockHeader().Time + UnbondingTime`), an attacker can pre-stage an arbitrarily large number of entries that all mature in the same future block, forcing a single `EndBlock` call to synchronously process all of them. This mirrors the OpenQ `getLockedFunds` bug class: cheap, repeatable user-controlled state growth (many deposits/entries) that a later unrelated/critical code path must fully iterate with no bound, causing gas/latency blow-up.

### Finding Description
`BlockValidatorUpdates`, invoked every block from `EndBlocker` (`sei-cosmos/x/staking/abci.go`), calls: [1](#0-0) 

which fetches **all** mature unbonding-delegation pairs via `DequeueAllMatureUBDQueue`: [2](#0-1) 

and then, for each pair, calls `CompleteUnbonding`, which itself loops over every mature entry in the `UnbondingDelegation` and performs a bank transfer per entry: [3](#0-2) 

The only per-delegation cap is `MaxEntries` (default 7), which bounds entries **within a single delegator→validator pair**: [4](#0-3) 

There is no cap on the **number of distinct delegator→validator pairs** whose unbonding completions land in the same queue timeslice, nor any per-block work budget for this loop (unlike the governance module, which the codebase's own spec notes was explicitly hardened with a "record-work budget" for its analogous slash-update backlog processing): [5](#0-4) 

An attacker can therefore:
1. Fund and create a large number of accounts, each with the minimum stake needed to delegate to any validator.
2. Delegate a small amount from each account.
3. Call `MsgUndelegate` from each account within transactions whose block has the same `ctx.BlockHeader().Time`, so completion time = `blockTime + UnbondingTime` is identical for all of them. This inserts one `DVPair` into the same `UBDQueueTimeSlice` per account (`InsertUBDQueue`): [6](#0-5) 

When the maturity block arrives, `EndBlock` must synchronously dequeue and fully process every one of these entries — each requiring a store read/write and a `bankKeeper.UndelegateCoinsFromModuleToAccount` call — with no early exit, no pagination, and no gas metering (this work happens outside the per-tx gas meter, in the deferred `EndBlock` phase).

### Impact Explanation
A sufficiently large backlog of same-maturity unbonding entries makes a single `EndBlock` call take substantially longer than normal, since the work is proportional to the attacker-controlled backlog size rather than the current block's transaction volume. This can push block production time beyond the target interval (risking the "block delay beyond 2.5 seconds" threshold) and, in the extreme, cause validators to fall behind or stall on that height, since `EndBlock` is not gas-metered/interruptible per this loop. This is a chain-liveness (validator halt / consensus delay) risk rather than a fund-loss risk, matching the High-severity griefing/DOS bug class in the source report (loop over an attacker-inflatable list with no bound, reached by an unprivileged unbounded number of ordinary transactions).

### Likelihood Explanation
Reaching this requires only ordinary, permissionless transactions (`MsgDelegate`/`MsgUndelegate`) from many funded accounts — no privileged role, no validator collusion, no p2p/consensus-message manipulation. The attacker pays normal tx fees and minimal stake amounts per account; the amplification comes from the fact that the expensive dequeue/complete work is deferred to a single future `EndBlock` and is not bounded or spread across blocks. This makes the likelihood non-trivial for a well-funded but otherwise ordinary attacker, though the practical cost (funding N accounts + N transactions) is a mitigating factor compared to the trivial OpenQ single-contract case.

### Recommendation
Bound per-block work for unbonding/redelegation queue processing, e.g.:
- Cap the number of `DVPair`/`DVVTriplet` entries drained and completed per `EndBlock` call, carrying over the remainder to subsequent blocks (similar to the record-work-budget approach already used for governance's delegation-tracking backlog).
- Alternatively, spread queue insertion across multiple time buckets or require a minimum unbonding amount/fee proportional to entries created, to make backlog inflation costly per unit of `EndBlock` work.

### Proof of Concept
1. Fund N accounts (N large, e.g. 50k–200k) with minimal stake each.
2. From each account, submit `MsgDelegate` (small amount, any validator) followed by `MsgUndelegate` for the full amount, all within transactions committed under the same block time `T`.
3. Each `Undelegate` call inserts a `DVPair` into `UBDQueueTimeSlice(T + UnbondingTime)` via `InsertUBDQueue`.
4. When block time reaches `T + UnbondingTime`, `EndBlocker` → `BlockValidatorUpdates` → `DequeueAllMatureUBDQueue` returns all N pairs at once, and the subsequent loop calls `CompleteUnbonding` (with an internal bank transfer) N times synchronously in that single `EndBlock`, with no cap or pagination — verifiable by measuring `EndBlock` duration/`stakingMetrics.endBlockerDuration` at that height versus baseline.

// InsertUBDQueue inserts an unbonding delegation to the appropriate timeslice
// in the unbonding queue.
func (k Keeper) InsertUBDQueue(ctx sdk.Context, ubd types.UnbondingDelegation,
	completionTime time.Time,
) {
	dvPair := types.DVPair{DelegatorAddress: ubd.DelegatorAddress, ValidatorAddress: ubd.ValidatorAddress}

	timeSlice := k.GetUBDQueueTimeSlice(ctx, completionTime)
	if len(timeSlice) == 0 {
		k.SetUBDQueueTimeSlice(ctx, completionTime, []types.DVPair{dvPair})
	} else {
		timeSlice = append(timeSlice, dvPair)
		k.SetUBDQueueTimeSlice(ctx, completionTime, timeSlice)
	}
}

// DequeueAllMatureUBDQueue returns a concatenated list of all the timeslices inclusively previous to
// currTime, and deletes the timeslices from the queue.
func (k Keeper) DequeueAllMatureUBDQueue(ctx sdk.Context, currTime time.Time) (matureUnbonds []types.DVPair) {
	store := ctx.KVStore(k.storeKey)

	// gets an iterator for all timeslices from time 0 until the current Blockheader time
	unbondingTimesliceIterator := k.UBDQueueIterator(ctx, ctx.BlockHeader().Time)
	defer func() { _ = unbondingTimesliceIterator.Close() }()

	for ; unbondingTimesliceIterator.Valid(); unbondingTimesliceIterator.Next() {
		timeslice := types.DVPairs{}
		value := unbondingTimesliceIterator.Value()
		k.cdc.MustUnmarshal(value, &timeslice)

		matureUnbonds = append(matureUnbonds, timeslice.Pairs...)

		store.Delete(unbondingTimesliceIterator.Key())
	}

	return matureUnbonds
}

// CompleteUnbonding completes the unbonding of all mature entries in the
// retrieved unbonding delegation object and returns the total unbonding balance
// or an error upon failure.
func (k Keeper) CompleteUnbonding(ctx sdk.Context, delAddr sdk.AccAddress, valAddr sdk.ValAddress) (sdk.Coins, error) {
	ubd, found := k.GetUnbondingDelegation(ctx, delAddr, valAddr)
	if !found {
		return nil, types.ErrNoUnbondingDelegation
	}

	bondDenom := k.GetParams(ctx).BondDenom
	balances := sdk.NewCoins()
	ctxTime := ctx.BlockHeader().Time

	delegatorAddress, err := sdk.AccAddressFromBech32(ubd.DelegatorAddress)
	if err != nil {
		return nil, err
	}

	// loop through all the entries and complete unbonding mature entries
	for i := 0; i < len(ubd.Entries); i++ {
		entry := ubd.Entries[i]
		if entry.IsMature(ctxTime) {
			ubd.RemoveEntry(int64(i))
			i--

			// track undelegation only when remaining or truncated shares are non-zero
			if !entry.Balance.IsZero() {
				amt := sdk.NewCoin(bondDenom, entry.Balance)
				if err := k.bankKeeper.UndelegateCoinsFromModuleToAccount(
					ctx, types.NotBondedPoolName, delegatorAddress, sdk.NewCoins(amt),
				); err != nil {
					return nil, err
				}

				balances = balances.Add(amt)
			}
		}
	}

	// set the unbonding delegation or remove it if there are no more entries
	if len(ubd.Entries) == 0 {
		k.RemoveUnbondingDelegation(ctx, ubd)
	} else {
		k.SetUnbondingDelegation(ctx, ubd)
	}

	return balances, nil
}

Delegation changes caused by validator slashing are queued as constant-size updates
instead of rewriting every affected vote snapshot in `BeginBlock`. Before advancing
a tally, `EndBlock` drains the globally ordered update queue through that proposal's
frozen boundary sequence under the same record-work budget. Updates at or before the
boundary can consume that budget even when their voters did not vote on the proposal,
so a slash-update backlog can postpone its vote processing and later expired proposals
in the queue. Updates after the boundary neither delay nor alter the frozen proposal.
