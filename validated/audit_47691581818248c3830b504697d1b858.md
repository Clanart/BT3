## Title
Auto-update of the `origin` remote URL from an untrusted GitHub API `clone_url` value with no validation of the new value — silent remote hijack (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop automatically rewrites a repository's `origin` remote URL to match the `clone_url` reported by the GitHub API whenever it detects the local remote has drifted from the previously known clone URL. The function that performs this rewrite, `updateRemoteUrl`, never validates that the new `clone_url` value is a legitimate, safe, or user-approved destination before calling `gitStore.setRemoteURL`, mirroring the audited Solidity finding where an ownership-critical value is swapped without validating the new value.

### Finding Description
`updateRemoteUrl` compares the current remote URL to `apiRepo.clone_url` and, if the git protocol matches and the existing remote hasn't been "manually" altered from the last known-good API value, silently calls `gitStore.setRemoteURL(...)` with the new API-supplied URL: [1](#0-0) 

The only checks performed are:
- protocol equality between old and new URL,
- whether the *current* remote still equals the previously cached `gitHubRepository.cloneURL`.

There is no check that the new `clone_url` value:
- points to the same GitHub host/owner/repo lineage the user actually intended to track (the whole point of the update is to allow owner/name changes, so `urlMatchesRemote` divergence is expected and accepted),
- is even a well-formed GitHub URL beyond a generic parse,
- was produced by a trusted, unmodified API response tied to the repository the user is actually working in.

`setRemoteURL` itself performs no validation either — it forwards the string straight to `git remote set-url`: [2](#0-1) [3](#0-2) 

This callback is invoked from `app-store.ts` as part of normal repository refresh/API-repository update flow (three call sites reference `updateRemoteUrl`), so any code path that supplies an `IAPIRepository` object for the tracked `GitHubRepository` — including a repository object obtained through GitHub API responses for repos the user has merely associated with the local clone (e.g., after following a link/PR from a fork, or an Enterprise server response) — can end up driving this rewrite. The matching helper `urlMatchesRemote`/`repositoryMatchesRemote` only checks hostname/owner/name structurally and is explicitly bypassed by design in the "repo was renamed/transferred" case: [4](#0-3) 

Because the invariant "the API-reported `clone_url` for this GitHub repository is trustworthy and intended by the user" is never re-validated (no user confirmation dialog, no allow-list, no comparison against the endpoint the user actually authenticated to), a crafted or attacker-influenced API repository object can cause Desktop to silently re-point `origin` to an attacker-controlled remote.

### Impact Explanation
Once `origin` is silently repointed:
- subsequent `git push` operations from the user (and any credentials/tokens negotiated through Desktop's credential helper for that host) are sent to the attacker's server, and
- subsequent `git fetch`/`pull` operations pull attacker-supplied history/objects into the user's working repository without any warning,

satisfying the in-scope impact category "silent corruption of what the user commits or pushes" driven by an attacker-controlled "GitHub API object." This is analogous to the Solidity bug: a security-critical reference (contract owner / git remote-of-record) is swapped for a new value supplied by an external actor with no sanity check on that new value.

### Likelihood Explanation
The rewrite only triggers under a specific combination of conditions (protocol match, and the current remote must still equal the last cached API `cloneURL`), which limits it to a narrow window, and the exact code path by which a fully attacker-controlled `IAPIRepository` reaches `updateRemoteUrl` for a victim's tracked repository was not fully traced in this pass (I was only able to confirm the sink and its three call sites in `app-store.ts`, not each producer of the `apiRepo` argument). This should be treated as **medium-to-low confirmed likelihood** pending a full trace of all producers of `IAPIRepository` objects feeding this function — I was not able to enumerate and verify every source with the tools available in this session.

### Recommendation
Before calling `gitStore.setRemoteURL` in `updateRemoteUrl`, explicitly validate the new `clone_url` against the account/endpoint the repository is authenticated against (host allow-list tied to the signed-in `Account.endpoint`), and/or prompt the user for confirmation when the remote's owner/name actually diverges from what's on disk, rather than silently trusting API-supplied data for an already-cloned repository.

### Proof of Concept
Conceptual trace (not independently executed against a live attacker payload in this session):
1. Attacker gets Desktop to hold a `GitHubRepository`/`IAPIRepository` object whose `clone_url` points to an attacker-controlled git server (exact injection vector — e.g., malicious Enterprise API response, forked-repo metadata, or a crafted API object reached via a deep link — needs confirmation with full repo access; see caveat above).
2. `updateRemoteUrl` is invoked with this `apiRepo`; protocol matches and the previous remote still equals the last cached clone URL, so the "unchanged"/"protocol match" gates pass. [5](#0-4) 
3. `gitStore.setRemoteURL` executes `git remote set-url origin <attacker-url>` with no further validation. [2](#0-1) 
4. The next `git push`/`git fetch` in Desktop silently targets the attacker's remote.

Given the index size limits and the need to fully confirm every caller/producer of the `IAPIRepository` passed into this path, a Devin session with full repo access is recommended to verify the exact triggering call chain end-to-end before treating this as a fully confirmed exploit chain.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
