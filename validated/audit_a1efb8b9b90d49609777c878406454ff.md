## Analysis

The external report's core pattern is a **security check that computes a value but the enforcement of that value has a logic gap that lets the intended constraint be silently bypassed**. In GitHub Desktop, the closest structural analog is the path-containment guard `_resolveWithin()` in `app/src/lib/path.ts`, which is the guard used to make sure attacker/URL-controlled relative paths (e.g. from a deep link) stay inside a repository root before the app touches the filesystem.

The final containment check is: [1](#0-0) 

`realResolved.startsWith(realRoot)` is a **string-prefix check, not a path-boundary check**. It never verifies that `realResolved` equals `realRoot` or starts with `realRoot + path.sep`. This is exploitable whenever a sibling directory exists whose name has the repository directory's name as a literal string prefix (e.g. repo at `.../GitHub/desktop` and a sibling `.../GitHub/desktop-secrets` or `.../GitHub/desktop-old`).

This guard is used directly on attacker-influenced, deep-link-supplied input in `Dispatcher.openRepositoryFromUrl`, which handles the `x-github-client://openRepo/...&filepath=...` protocol action: [2](#0-1) 

The only other check applied to `filepath` is `isAbsolute(filepath)`, which does nothing to stop relative traversal segments like `../sibling-dir/secret.txt`.

The existing unit tests for `resolveWithin` only cover "goes outside and comes back to root" and symlink-escape cases — they never test the sibling-prefix scenario, confirming the boundary gap was not considered: [3](#0-2) 

The same flawed primitive (`resolveWithin`) is reused elsewhere as a "path traversal and symlink escape" guard, e.g. in the Copilot conflict-context builder that reads file contents to send to an AI model: [4](#0-3) 

### Title
Path-containment guard `resolveWithin()` uses a prefix-only `startsWith` check, allowing sibling-directory escape from a malicious deep link - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` in `app/src/lib/path.ts` is GitHub Desktop's central helper for verifying that a user/attacker-supplied relative path stays inside a trusted root directory (e.g. a repository's working directory) before the app reveals, reads, or otherwise touches the resolved file. Its final decision is `realResolved.startsWith(realRoot)`, which is a raw string-prefix comparison rather than a path-segment boundary comparison. Any directory that is a sibling of the root and whose name is prefixed by the root's basename (e.g. root `desktop`, sibling `desktop-secrets`) will incorrectly pass the containment check.

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` computes `resolved = resolve(normalizedRoot, normalizedRelative)`, then `realpath`s both the root and the resolved candidate, and finally does:

```
return realResolved.startsWith(realRoot) ? resolved : null
```

Because JavaScript string `startsWith` has no notion of path separators, `"/Users/victim/Documents/GitHub/desktop-secrets/token.txt".startsWith("/Users/victim/Documents/GitHub/desktop")` evaluates to `true`, even though `desktop-secrets` is a completely different directory from `desktop`. The correct invariant ("resolved path is at or under root") is silently broken for any pair of directories that share a literal name prefix.

This guard is reached with attacker-controlled input via GitHub Desktop's registered custom protocol handlers (`x-github-client://`, `github-mac://`, `github-windows://`), which a user can be lured into clicking as a normal link:

- `parseAppURL` extracts an untrusted `filepath` query parameter from the deep link URL.
- `Dispatcher.openRepositoryFromUrl` passes that `filepath` straight into `resolveWithin(repository.path, filepath)`, gated only by an `isAbsolute()` check that does nothing against relative traversal (`../desktop-secrets/id_rsa`).
- If the sibling-prefix collision exists on disk, `resolveWithin` returns a non-null path even though it lies outside `repository.path`, and Desktop calls `shell.showItemInFolder(resolved)` on it.

The same primitive is reused as the sole traversal/symlink-escape guard in `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts`), which reads file contents from disk to build context sent to an AI conflict-resolution feature — an unrelated but structurally identical mis-trust of `resolveWithin`'s guarantee.

### Impact Explanation
An attacker who can get a user to click a crafted `x-github-client://openRepo/...&filepath=...` (or `github-mac://`/`github-windows://`) link can cause Desktop to resolve and act on a path outside the intended repository, as long as a similarly-prefixed sibling directory happens to exist next to the target repository on the victim's machine (a common occurrence for users who keep multiple related checkouts, e.g. `project`, `project-old`, `project-backup`, `desktop`, `desktop-internal`, monorepo forks, etc.). Depending on which of Desktop's internal callers use `resolveWithin`, this can result in revealing/opening a file outside the repo (current `openRepositoryFromUrl` path via `shell.showItemInFolder`) or, for other callers of the same primitive such as the Copilot conflict-context builder, reading file content from outside the repository and forwarding it to an external context-building pipeline.

### Likelihood Explanation
Reaching this bug requires only that the victim click a link (the protocol handlers are registered by default at app startup) and that a sibling directory with a matching name prefix exists — a plausible but not universal precondition, since Desktop users frequently keep sibling project checkouts. There is no requirement for local/physical access, admin rights, or pre-existing malware; the "device access" is entirely a normal browser click on an attacker-supplied link, matching the deep-link attack surface explicitly called out in-scope.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to enforce an actual path-segment boundary instead of a raw string prefix, e.g.:

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```

Add regression tests for the sibling-directory-with-shared-prefix case (e.g. root `foo`, candidate `foo-evil`) to `app/test/unit/path-test.ts`, since the current suite only tests traversal-then-return-to-root and symlink-escape scenarios and does not cover this boundary condition.

### Proof of Concept
1. On disk, have two sibling directories: `/Users/victim/Documents/GitHub/desktop` (the tracked repository, open in Desktop) and `/Users/victim/Documents/GitHub/desktop-secrets/token.txt` (any file the attacker wants revealed, which the victim happens to have alongside).
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/desktop/desktop?filepath=..%2Fdesktop-secrets%2Ftoken.txt`
3. Victim clicks the link. Desktop's protocol handler invokes `handleAppURL` → `parseAppURL` → `dispatcher.openRepositoryFromUrl`.
4. `isAbsolute('../desktop-secrets/token.txt')` is `false`, so the check passes.
5. `resolveWithin('/Users/victim/Documents/GitHub/desktop', '../desktop-secrets/token.txt')` resolves to `/Users/victim/Documents/GitHub/desktop-secrets/token.txt`; `realResolved.startsWith(realRoot)` is `true` (string-prefix match) even though the file is outside the `desktop` repository.
6. Desktop calls `shell.showItemInFolder(resolved)`, revealing/opening the out-of-repo file instead of refusing as intended (`log.error('Prevented attempt to open path outside of the repository root...')` is never reached).
