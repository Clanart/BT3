Checking whether the registered encryption key is validated (identity/small-order keys would leak shares to observers).### Title
Unvalidated DKG encryption key accepts the identity point, leaking secret shares to any observer of the channel - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
PedPoP's `EncryptionKeyMessage.enc_key` is registered and used as an ECDH peer key without ever being checked for the identity (or, for `EdwardsPoint`, small-order-but-torsion-free is impossible, but identity is explicitly permitted). `C::read_G` only rejects non-canonical encodings and non-torsion-free points — the identity point passes [1](#0-0) . A participant who registers `enc_key = identity` causes every sender's ECDH shared key for messages addressed to them to be the publicly-known identity point, so all `EncryptedMessage<C, SecretShare<C::F>>` payloads sent to that participant decrypt with a publicly computable ChaCha20 key. This is the direct analog of the AutoQueryable leak: an unrestricted input field causes confidential data (threshold secret shares) to be readable by unprivileged observers.

### Finding Description
`Decryption::register` inserts `msg.enc_key` with no validation [2](#0-1) . `SecretShareMachine::verify_r1` batch-verifies the PoK `sig` against `commitments[0]` and a challenge over `msg.cached_msg`, but `cached_msg` covers only the commitment points — `enc_key` is neither PoK-bound nor sanity-checked [3](#0-2) . The PoK challenge binds context, participant index, nonce, and commitments only [4](#0-3) .

When any honest participant encrypts a share to the attacker, `encrypt` computes `ecdh(key, to)` = `to * key` [5](#0-4) . With `to = C::G::identity()`, the shared key is `identity * key = identity` regardless of the ephemeral key. `cipher` then derives the ChaCha20 key solely from `context` (public session context) and `shared_key.to_bytes()` — the identity point's canonical encoding [6](#0-5) . The per-message `key`/`pop` in `EncryptedMessage` remain valid, so decryption, batch PoP verification, and share verification all succeed normally for the attacker; no blame is ever triggered.

Any third party who observes the (authenticated but not confidential) channel — including the coordinator, which retains `share` ciphertexts for `VerifyBlame` [7](#0-6)  — can recompute `cipher(context, identity_bytes)` and decrypt all `n-1` shares addressed to the attacker. Summing them recovers the attacker's `ThresholdKeys` secret share `secret = Σ s_j(l)` exactly as `calculate_share` does [8](#0-7) .

### Impact Explanation
Confidentiality breach of a threshold secret share: a full FROST/PedPoP signing share for one participant index is recoverable by any observer with access to the DKG transcript. Combined with any `t-1` compromised/colluding shares it yields full group private key recovery; even alone it enables share-targeted attacks (e.g., share forgery against that participant's verification share, which is publicly computable from the stripes). Severity: Medium — analogous to CVE-2024-57716's unauthorized disclosure of sensitive data through an unvalidated input field.

### Likelihood Explanation
Any DKG participant can mount this by serializing `EncryptionKeyMessage { enc_key: identity, msg: valid_commitments }`. Nothing in `read`, `register`, `verify_r1`, or `AdditionalBlameMachine::new` rejects identity [9](#0-8) . The malicious participant still completes the protocol correctly (they decrypt via their own `enc_key = 0`... — note `enc_key` scalar is random but the *public* key they publish is what matters; publishing `enc_pub_key = identity` while knowing the shared key is `identity` is self-consistent), so no error or blame surfaces. Requires only participation in one key-generation session and an observer of the channel traffic.

### Recommendation
- In `Decryption::register` / `Encryption::register` (or `EncryptionKeyMessage::read`), reject `enc_key` equal to `C::G::identity()` (and, defensively, enforce a non-identity check in `read_G` consumers for encryption keys specifically — `random` already bans identity [10](#0-9) , but `from_bytes` does not [11](#0-10) ).
- Optionally bind `enc_key` into the `challenge()` transcript (`append_message(b"enc_key", ...)`) so it is PoK-authenticated alongside the commitments.

### Proof of Concept
```rust
// Attacker l registers with the identity point as its encryption public key.
let mut msg = honest_commitments_msg.clone(); // EncryptionKeyMessage<Ristretto, Commitments<_>>
msg.enc_key = <Ristretto as Ciphersuite>::G::identity();

// Honest senders call:
//   encryption.encrypt(rng, l, share_bytes)
// which internally does:
//   ecdh = msg.enc_key * ephemeral_key = identity
//   cipher(context, identity.to_bytes()) applied to the SecretShare bytes.

// Observer, given context and any wire copy of EncryptedMessage to l:
let shared = <Ristretto as Ciphersuite>::G::identity(); // public knowledge
let mut plaintext = ciphertext.msg.clone();
cipher::<Ristretto>(context, &Zeroizing::new(shared))
    .apply_keystream(plaintext.as_mut().as_mut());
// plaintext now holds s_j(l); summing over all senders j yields l's threshold secret share.
```

Root cause: `enc_key` in `EncryptionKeyMessage` is consumed raw by `ecdh`/`cipher` with no identity rejection, and `read_G` deliberately admits identity since it only enforces canonical, torsion-free encodings.

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
