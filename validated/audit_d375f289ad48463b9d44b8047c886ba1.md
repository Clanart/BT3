### Title
Unrefunded native-token overpayment stranded in `EvmHost` on `dispatch()`/`fundRequest()` - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment via `msg.value` and swap it for the exact required `feeToken` amount using `swapETHForExactTokens`. Any native token sent above the amount the swap actually consumes is refunded by the Uniswap router back to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction caller. Unlike `IntentGatewayV2.placeOrder`/`fillOrder`, which explicitly track leftover `msgValue` and forward it back to the user, `EvmHost` has no such forwarding logic, so any overpaid ETH permanently accumulates in the host contract instead of being returned to the caller.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

Each of these functions calls `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(exactAmount, path, address(this), block.timestamp)`. The router's `swapETHForExactTokens` implementation refunds any ETH beyond what was actually required for the exact-output swap directly to its own `msg.sender`. Since `EvmHost` is the one invoking the router, that refund lands in `EvmHost`'s balance, not the wallet that originally called `dispatch`/`fundRequest`. None of these three `EvmHost` functions capture a "leftover" value and forward it back to `_msgSender()`.

Contrast this with the sibling app-level contract `IntentGatewayV2.placeOrder`, which explicitly does this bookkeeping and refund: [4](#0-3) 

The pattern is proven by the project's own test comment: `swapETHForExactTokens{value: budget}` with `budget = 100 ether` against an `amountOut` of ~1 token unit, and the test explicitly states "the wrapper refunds the excess" (to whichever address invoked the swap): [5](#0-4) 

This is the same broken invariant as the reported `Trading.openTrade` bug: a payable function accepts native coin, but any amount beyond what is functionally required is neither reverted nor refunded to the sender — it is simply absorbed by the contract.

### Impact Explanation
Any unprivileged user (or any `HyperApp`/integrator contract calling `dispatch{value: msg.value}` or `fundRequest{value: msg.value}` with more native token than the exact swap requires — which is the normal/expected case since fee estimation via Uniswap `getAmountsIn` is only approximate and subject to slippage, as the docs themselves warn) will have the excess ETH permanently stuck in `EvmHost`, unrecoverable by that user. This is a direct, repeatable loss of funds for ordinary callers using the documented "Native Token Payment" pattern shown in the SDK/documentation examples (`dispatch{value: msg.value}(post)`), which do not perform slippage-exact estimation before sending.

### Likelihood Explanation
High. This isn't a contrived edge case — it is the default flow described in the project's own documentation and SDK (`developers/evm/messaging/post-requests.mdx`, `get-requests.mdx`), which explicitly instruct integrators to send native tokens and let the swap consume "enough," and separately warn that `quote()`/`quoteNative()` estimates are "approximate (subject to slippage)". Every dispatch or fundRequest call paid in native token that doesn't hit the exact swap price will lose the difference. The existing app contract `IntentGatewayV2` had to independently implement excess-refund logic for exactly this reason, confirming the developers were aware of the risk in that surface but did not carry the same protection into `EvmHost` itself.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, track the actual amount spent returned by `swapETHForExactTokens` (`amounts[0]`) and refund `msg.value - amounts[0]` back to `_msgSender()` via a low-level call, mirroring the pattern already used in `IntentGatewayV2.placeOrder`/`fillOrder`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 5 ether}(post)` with `post.fee` requiring only ~0.01 ETH worth of `feeToken` at current pool price (an entirely normal scenario since the frontend `quoteNative()`/`quote()` estimate is only approximate, per the docs' own slippage warning).
2. Inside `dispatch`, `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` executes; the router consumes only ~0.01 ETH and refunds the remaining ~4.99 ETH to its caller, `EvmHost`.
3. `EvmHost.dispatch` never checks or forwards this refund; the ~4.99 ETH remains locked in `EvmHost`'s balance.
4. The original caller has no function to reclaim this ETH — it is permanently lost to them, identical in effect to the `Trading.openTrade` "coin wasted, not returned" bug class.
This matches the behavior already validated in `evm/tests/foundry/ConfiguredWrapperForkTest.t.sol` (lines 45-59), which asserts the router refunds unused ETH to the calling contract rather than the original transaction sender.
