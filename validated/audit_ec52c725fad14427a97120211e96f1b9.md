Confirmed: the `filepath` query parameter of the `x-github-client://openRepo` deep link is fully attacker-controlled, unvalidated free text (only checked for `isAbsolute`), and is passed straight into `resolveWithin()`, whose containment check has the same "boundary-less prefix comparison" defect described in the external report.

### Title
Prefix-only path containment check in `resolveWithin` allows deep-link `filepath` to escape the intended repository directory into a sibling directory - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is the sole guard that Desktop uses to make sure a user/attacker supplied relative path cannot escape a given root directory before being handed to filesystem or shell APIs. Its containment test is a plain string `startsWith()` check with no boundary/separator verification, so it accepts any resolved path whose string form merely begins with the root path's characters — including a sibling directory that happens to share the root directory name as a prefix. This is the exact same bug class as the reported `opCALLDATALOAD` issue: a boundary comparison (`offset == txCalldataLen`, here `realResolved == realRoot` boundary) that is missing the strict "must be followed by a path separator / equal length" condition, letting an off-by-a-component read slip through.

### Finding Description
`_resolveWithin` computes the real, symlink-resolved paths of both the root and the candidate, then does: [1](#0-0) 

`String.prototype.startsWith` has no concept of path-segment boundaries. If `realRoot` is `/Users/victim/Documents/GitHub/project` and the resolved candidate is `/Users/victim/Documents/GitHub/project-secrets/token.txt`, then `realResolved.startsWith(realRoot)` evaluates to `true` even though `project-secrets` is a completely different, sibling directory — not a subdirectory of `project`. The function returns the escaped path as "safe," and the same defect exists in the null-byte and empty-root checks around it, all missing an explicit separator check: [2](#0-1) 

The unit tests only cover traversal-then-return-into-root and symlink cases, never the "sibling directory with shared name prefix" case, so this specific escape is untested: [3](#0-2) 

### Attacker-controlled entry point
The `openRepo` custom-protocol deep link exposes a `filepath` query parameter that is parsed with zero sanitization beyond an absolute-path check: [4](#0-3) 

That value flows directly into the vulnerable guard in the dispatcher when handling the deep link: [5](#0-4) 

The only check performed before calling `resolveWithin` is `isAbsolute(filepath)` — a relative path containing `../` segments is fully permitted, and that is precisely what `resolveWithin`'s prefix check fails to catch when the resulting sibling directory name happens to start with the repository's own directory name.

### Impact Explanation
If successful, `shell.showItemInFolder(resolved)` is invoked on a path outside the intended repository, and Explorer/Finder will open/reveal that path, which can be used to disclose the existence and location of files outside the repo (or, combined with directory naming that GitHub Desktop itself creates for repositories cloned side-by-side under the same parent folder such as `~/Documents/GitHub/<repo>`), point the user at an attacker-influenced sibling folder. This matches the "file read outside the repo" and "link/deep link the user clicks" categories called out as valid impact. The severity is bounded by `shell.showItemInFolder` (reveal, not arbitrary read/execute), but the underlying `resolveWithin` primitive is also relied on elsewhere in the codebase (e.g. `app/src/lib/copilot-conflict-context.ts:393`) where a similar escape would let file *contents* be exfiltrated to the Copilot conflict-resolution context.

### Likelihood Explanation
Requires: (1) the user clicks an `x-github-client://openRepo?...&filepath=...` link (a normal, expected Desktop feature — no unnatural steps), and (2) a directory happens to exist next to the target repository whose name has the repository's directory name as a string prefix (e.g. `project` vs `project-old`, `repo` vs `repository`, or an attacker who also convinces the victim to clone a second, attacker-named repository next to the first). The second condition is a real-world constraint that lowers likelihood somewhat, but it is not "local/physical access" or "prior malware" — it is a naming coincidence/attacker-influenced directory layout reachable purely through normal Desktop usage (cloning repos side by side, which Desktop does by default into a shared parent folder).

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to require an exact match or a path-separator boundary after the root, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the report's recommendation to replace the loose boundary comparison (`<`) with the strict one (`<`, exact) — here replacing bare `startsWith` with a separator-aware containment check.

### Proof of Concept
1. Attacker (or naming coincidence) causes a directory `~/Documents/GitHub/project-exfil/secret.txt` to exist alongside the victim's real repository `~/Documents/GitHub/project`.
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/project?filepath=../project-exfil/secret.txt`.
3. Victim clicks the link; Desktop routes it through `parseAppURL` → `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`.
4. `filepath` is not absolute, so it passes the only check, then `resolveWithin(repository.path, filepath)` is called.
5. `realResolved` (`.../project-exfil/secret.txt`) `.startsWith(realRoot)` (`.../project`) evaluates `true` because the string `project-exfil` starts with `project`.
6. `shell.showItemInFolder(resolved)` reveals `secret.txt`, a file outside the cloned repository, confirming the containment check is bypassed. [6](#0-5) [7](#0-6)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
