### Title
Immature coinbase outputs reported as spendable received funds — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including `block.txdata[0]` (the coinbase), and returns any matching outputs as `ReceivedOutput`s indistinguishable from ordinary, immediately-spendable UTXOs. Coinbase outputs are consensus-bound by a 100-block maturity rule: they exist on-chain but cannot be spent until maturity. This mirrors the reported bug class — resources are accounted/committed (here, returned as spendable inputs) before they are actually deliverable, and the failure is silent: nothing in the returned `ReceivedOutput` marks it as immature.

### Finding Description
`scan_transaction` matches outputs purely on `script_pubkey` and constructs a `ReceivedOutput { offset, output, outpoint }` with no notion of coinbase status or confirmation depth [1](#0-0) . `scan_block` applies this to `block.txdata` wholesale, so `block.txdata[0]` — the coinbase — is included [2](#0-1) .

A `ReceivedOutput` flows directly into `SignableTransaction::new`, which sums `input.output.value` as available funds and uses `input.outpoint` as a transaction input [3](#0-2) . If an immature coinbase output is included, the transaction is invalid under consensus rules (`bad-txns-premature-spend-of-coinbase`): it will be rejected by relay/mining, yet the wallet has already "spent" accounting-wise on inputs it never actually controls yet. Analogous to the Olas finding where `effectiveBond` accounts tokens that cannot yet be minted, the scanner commits value that cannot yet be moved — silently, since the struct carries no maturity flag and `SignableTransaction` performs no maturity check.

### Impact Explanation
Funds are reported as received and spendable that are not. Any consumer of `Scanner::scan_block` (the documented API for scanning blocks) can select an immature coinbase as an input, producing a transaction that fails on broadcast — burning fee budget / stalling payouts — or, in a threshold-wallet setting, causing signers to produce a signature over a transaction that can never confirm. Downstream accounting crediting the scanned value as available balance overstates spendable funds by the coinbase amount (currently 3.125 BTC per block).

### Likelihood Explanation
Reachability requires a coinbase output paying a scanned `script_pubkey`. Any miner can include such an output — mining a block paying a chosen Taproot script is normal behavior (e.g., pool payouts), and an adversary with even modest hash power, or an innocuous pool, can produce it. Given Serai's keys are public, anyone can direct a coinbase to them. The trigger probability is bounded by mining economics but the code path is deterministic once triggered.

### Recommendation
Either exclude `txdata[0]` in `scan_block`, or extend `ReceivedOutput`/`scan_transaction` to carry a coinbase/maturity marker so consumers can filter outputs younger than 100 blocks. As the inline comment notes [4](#0-3) , a post-processing pass is needed — that requirement should be enforced in the type/API rather than left as an implicit caller obligation.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

    let mut res = Vec::new();
