### Title
Durable-nonce transactions lack cluster/genesis-hash domain separation, enabling cross-cluster replay after hard-fork/snapshot-based cluster creation - ([File: programs/system/src/system_instruction.rs], [File: svm/src/transaction_processor.rs], [File: runtime/src/bank/check_transactions.rs])

### Summary
Solana's durable-nonce mechanism authorizes an offline-signed transaction by binding `recent_blockhash` to a `DurableNonce` value stored in a nonce account, as seen in `advance_nonce_account`/`initialize_nonce_account` in `programs/system/src/system_instruction.rs` (lines 25-78, 163-211), which call `DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash)`. This nonce value is a pure hash with no chain/genesis/cluster identifier folded in. Verification of the nonce, in `validate_transaction_nonce` (`svm/src/transaction_processor.rs:833-892`) and `check_nonce_transaction_validity`/`load_message_nonce_data` (`runtime/src/bank/check_transactions.rs:258-300`), only checks that `message.recent_blockhash()` equals the account's stored `durable_nonce` and that the authority signed — nothing about which cluster/genesis the account belongs to is part of that check. This is structurally the same broken invariant as the Harpie `changeRecipientAddress()` bug: the signed payload/state has no domain separator (no `chain.id` equivalent), so a validly signed message remains valid verbatim on any chain that happens to share that state.

### Finding Description
Agave clusters can be created from an existing chain's ledger/snapshot state via the documented hard-fork/cluster-restart procedure (`agave-ledger-tool create-snapshot`, exercised in `local-cluster/tests/local_cluster.rs:2199-2258` `create_snapshot_to_hard_fork`, and driven from `core/src/validator.rs` `maybe_warp_slot`/`post_process_restored_tower`). When this happens, all account state — including any live nonce accounts and their stored `durable_nonce` hash — is carried over unchanged into the new cluster's genesis/snapshot. Separately, the new cluster gets a distinguishing `shred_version` computed from `compute_shred_version(&genesis_config.hash(), Some(&hard_forks))` (`core/src/validator.rs:952`), but this value is used **only** to filter gossip CRDS traffic (`gossip/src/cluster_info.rs:1951-2130`, `discard_different_shred_version`, `check_pull_request_shred_version`) — it is never consulted by transaction signature verification, nonce validation, or the SVM transaction processor. The `blockhash_queue` is reseeded per-cluster via `genesis_hash()` (`runtime/src/bank.rs:3225-3228`), which does protect ordinary recent-blockhash transactions once the two clusters' block histories diverge, but nonce accounts are exempt from that expiry mechanism by design (that's the entire point of durable nonces) and their state is copied as-is. Therefore, a durable-nonce transaction signed by a user before/at the fork point remains fully valid and replayable on the newly created cluster, because the on-chain check never asks "is this the cluster I signed for?" — only "does the nonce value match?"

### Impact Explanation
An attacker who obtains (via public broadcast, mempool sniffing, or simply because the user never got it confirmed on the original chain) a signed durable-nonce transaction can replay it on any hard-forked/cloned cluster that inherited the same nonce-account state, executing the exact instructions (transfers, authority changes, program calls) the signer authorized only for the original chain. This mirrors the Harpie impact: funds/actions intended for one chain get executed on another, and because nonce transactions are specifically designed to remain valid indefinitely (no blockhash-age expiry), the replay window is unbounded until someone advances the nonce on the new cluster.

### Likelihood Explanation
Hard-fork/cluster-restart-from-snapshot is a supported, documented Agave operational procedure (present in `local-cluster` tests and `net/remote/remote-node.sh`), not a hypothetical. Any deployment that clones/forks a live network for testing, migration, or incident recovery inherits this exposure automatically for every existing nonce account, with no additional attacker privilege required — the attacker only needs a previously valid signed nonce transaction and access to submit it to the new cluster's RPC/TPU.

### Recommendation
Bind a cluster-identifying value (e.g., `genesis_hash`, or the `hard_forks`-derived identifier already used for `shred_version`) into the `DurableNonce` derivation or into `nonce::state::Data`, and check it during `validate_transaction_nonce`/`check_nonce_transaction_validity`, analogous to including `chain.id` in the Harpie fix.

### Proof of Concept
1. On cluster A, initialize/advance a nonce account, producing `durable_nonce = DurableNonce::from_blockhash(blockhash_A)` (`programs/system/src/system_instruction.rs:50-51`).
2. Sign (but do not necessarily land) a transaction with `recent_blockhash = durable_nonce` authorizing some action (e.g., transfer, `authorize_nonce_account`).
3. Operator hard-forks/clones the cluster into cluster B using `agave-ledger-tool create-snapshot` (as in `local-cluster/tests/local_cluster.rs:2199-2258`), preserving the nonce account's state.
4. Submit the same signed transaction to cluster B. `validate_transaction_nonce` (`svm/src/transaction_processor.rs:833-892`) finds `message.recent_blockhash() == nonce_data.durable_nonce`, the authority signature checks out, and the transaction executes on cluster B exactly as it would have on cluster A — even though `shred_version` (the only cluster-distinguishing value computed) differs and would have prevented the two clusters' validators from gossiping with each other. pub fn advance_nonce_account(
    account: &mut BorrowedInstructionAccount,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Advance nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    let state: Versions = account.get_state()?;
    match state.state() {
        State::Initialized(data) => {
            if !signers.contains(&data.authority) {
                ic_msg!(
                    invoke_context,
                    "Advance nonce account: Account {} must be a signer",
                    data.authority
                );
                return Err(InstructionError::MissingRequiredSignature);
            }
            let next_durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            if data.durable_nonce == next_durable_nonce {
                ic_msg!(
                    invoke_context,
                    "Advance nonce account: nonce can only advance once per slot"
                );
                return Err(SystemError::NonceBlockhashNotExpired.into());
            }

            let new_data = nonce::state::Data::new(
                data.authority,
                next_durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            account.set_state(&Versions::new(State::Initialized(new_data)))
        }
        State::Uninitialized => {
            ic_msg!(
                invoke_context,
                "Advance nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

    fn validate_transaction_nonce<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        message: &impl SVMMessage,
        nonce_address: &Pubkey,
        next_durable_nonce: &DurableNonce,
        next_lamports_per_signature: u64,
        strict_nonce_size_check: bool,
        error_counters: &mut TransactionErrorMetrics,
    ) -> TransactionResult<NonceInfo> {
        // When SIMD83 is enabled, if the nonce has been used in this batch already, we must drop
        // the transaction. This is the same as if it was used in different batches in the same slot.
        // It is possible that the nonce account was used, closed, closed and reopened, closed and
        // spoofed by a non-system program, or had its authority changed. Such a transaction cannot
        // be processed, even as fee-only.

        let Some(mut nonce_account) = account_loader
            .load_transaction_account(nonce_address, true)
            .map(|loaded| loaded.account)
        else {
            error_counters.account_not_found += 1;
            return Err(TransactionError::AccountNotFound);
        };

        if strict_nonce_size_check && nonce_account.data().len() != NonceState::size() {
            error_counters.blockhash_not_found += 1;
            return Err(TransactionError::BlockhashNotFound);
        }

        // This function verifies:
        // * Nonce account owner is SystemProgram
        // * Nonce account parses as State::Initialized
        // * Stored durable nonce matches the message blockhash
        let Some(nonce_data) = verify_nonce_account(&nonce_account, message.recent_blockhash())
        else {
            error_counters.blockhash_not_found += 1;
            return Err(TransactionError::BlockhashNotFound);
        };

        // We must still check that the nonce account is usable and that its authority has signed.
        let nonce_can_be_advanced = &nonce_data.durable_nonce != next_durable_nonce;
        let nonce_authority_is_valid = message
            .get_ix_signers(NONCED_TX_MARKER_IX_INDEX as usize)
            .any(|signer| signer == &nonce_data.authority);

        if nonce_can_be_advanced && nonce_authority_is_valid {
            let next_nonce_state = NonceState::new_initialized(
                &nonce_data.authority,
                *next_durable_nonce,
                next_lamports_per_signature,
            );
            nonce_account
                .set_state(&NonceVersions::new(next_nonce_state))
                .expect("Serializing into a validated nonce account cannot fail");

            Ok(NonceInfo::new(*nonce_address, nonce_account))
        } else {
            error_counters.blockhash_not_found += 1;
            Err(TransactionError::BlockhashNotFound)
        }
    }

#[must_use]
fn check_pull_request_shred_version(self_shred_version: u16, caller: &CrdsValue) -> bool {
    let shred_version = match caller.data() {
        CrdsData::ContactInfo(node) => node.shred_version(),
        _ => return false,
    };
    shred_version == self_shred_version
}

// Discards CrdsValues in PushMessages and PullResponses from nodes with
// different shred-version.
fn discard_different_shred_version(
    msg: &mut Protocol,
    self_shred_version: u16,
    crds: &Crds,
    stats: &GossipStats,
) {
    let (values, skip_shred_version_counter) = match msg {
        Protocol::PullResponse(_, values) => (values, &stats.skip_pull_response_shred_version),
        Protocol::PushMessage(_, values) => (values, &stats.skip_push_message_shred_version),
        // Shred-version on pull-request callers can be checked without a lock
        // on CRDS table and is so verified separately (by
        // check_pull_request_shred_version).
        Protocol::PullRequest(..) => return,
        // No CRDS values in Prune, Ping and Pong messages.
        Protocol::PruneMessage(_, _) | Protocol::PingMessage(_) | Protocol::PongMessage(_) => {
            return;
        }
    };
    let num_values = values.len();
    values.retain(|value| match value.data() {
        CrdsData::ContactInfo(ci) => ci.shred_version() == self_shred_version,
        // for any other CRDS types we check if we store anything already
        // for this pubkey, if we do we allow more values in
        _ => crds.get_records(&value.pubkey()).next().is_some(),
    });
    let num_skipped = num_values - values.len();
    if num_skipped != 0 {
        skip_shred_version_counter.add_relaxed(num_skipped as u64);
    }
}
