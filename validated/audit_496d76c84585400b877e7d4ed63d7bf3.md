### Title
Naive `content.split('---', 2)` in `extract_frontmatter` silently truncates YAML frontmatter and drops `action: block`, downgrading enforcement to `warn` - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` delimits YAML frontmatter by naive substring splitting (`content.split('---', 2)`) instead of requiring `---` to appear on its own line. If a rule's `pattern` (or any frontmatter value) contains a literal `---` before the real closing delimiter, the split treats that embedded substring as the closing marker, truncating the frontmatter text before fields like `action: block` are parsed. `Rule.from_dict` then falls back to the default `action = "warn"`, so `RuleEngine.evaluate_rules` treats the rule as a warning-only rule instead of a blocking one.

### Finding Description
`load_rules()` globs `.claude/hookify.*.local.md` and calls `load_rule_file()` → `extract_frontmatter(content)` [1](#0-0) [2](#0-1) .

`extract_frontmatter` does:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
``` [3](#0-2) 

`str.split('---', 2)` splits on the first two literal occurrences of `---` anywhere in the text, not just on lines consisting solely of `---`. Given a file:
```
---
name: block-dangerous
event: bash
pattern: foo---bar
action: block
---
message
```
the second occurrence of `---` is the one embedded inside `pattern: foo---bar`, not the real closing fence. Consequently `frontmatter_text` becomes `\nname: block-dangerous\nevent: bash\npattern: foo`, silently dropping `action: block` (and the true closing `---` plus message end up folded into `message`). `Rule.from_dict` then computes `action=frontmatter.get('action', 'warn')` [4](#0-3) , yielding `action == "warn"` even though the source file visibly states `action: block`.

Downstream, `RuleEngine.evaluate_rules` branches purely on `rule.action == 'block'` to decide whether to return a `permissionDecision: deny` (blocking) response or just a `systemMessage` (non-blocking) response [5](#0-4) . A rule silently downgraded to `warn` will allow the dangerous Bash/Write operation to proceed instead of being denied, even though the on-disk rule declares `action: block`.

No validation anywhere requires the frontmatter delimiter to be on its own line, and no schema/consistency check re-verifies that the parsed `action` field matches what a human reviewing the raw markdown would expect.

### Impact Explanation
This is a trust-boundary/confused-deputy issue in a user-facing security control: a repository can contain a `.claude/hookify.*.local.md` file that visually reads `action: block` (and would be approved/trusted as such by a reviewer or the user who wrote it), but due to the naive delimiter parsing, Claude Code actually enforces it as `action: warn`. Any Bash command or file edit matching the rule's pattern is only warned about, not blocked, silently defeating the intended "deny means deny" guarantee and letting a dangerous operation execute when the user/plugin expects it to be stopped.

### Likelihood Explanation
Preconditions are simply: (1) the repository contains a `.claude/hookify.*.local.md` file (created by a user, a plugin generator, or merged via PR) whose `pattern` (or another frontmatter value before `action`) contains a literal `---` substring, and (2) `load_rules()` auto-loads it, which happens automatically on every PreToolUse/PostToolUse/Stop/UserPromptSubmit hook invocation with no extra privilege required [6](#0-5) . Triple-dash sequences are plausible in real regex patterns (e.g. ranges like `\d{3}---\d{3}`, comment markers, ASCII art, or an intentionally crafted pattern), making this both accidentally and deliberately triggerable, and the resulting weakening is completely silent (no error, warning about frontmatter parsing failure is only emitted when frontmatter is entirely empty, not when it's truncated).

### Recommendation
Replace the substring-based split with a line-anchored frontmatter parser, e.g. use `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or split on lines and only treat a line that is exactly `---` (after stripping trailing whitespace) as a delimiter. Additionally, add a sanity check after parsing that logs/rejects rule files where fields appear truncated (e.g., an unterminated `pattern:` value or a missing/incomplete `action` when the raw text clearly contains `action: block` after the point where parsing stopped), and prefer a real YAML parser (`yaml.safe_load`) over the hand-rolled state machine to avoid ambiguity.

### Proof of Concept
Differential unit test on `extract_frontmatter`:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

clean = """---
name: block-dangerous
event: bash
pattern: foobar
action: block
---
Blocked!
"""

malicious = """---
name: block-dangerous
event: bash
pattern: foo---bar
action: block
---
Blocked!
"""

fm_clean, _ = extract_frontmatter(clean)
fm_mal, _ = extract_frontmatter(malicious)

assert fm_clean.get('action') == 'block'
# BUG: this fails today because 'action' is dropped from fm_mal
assert fm_mal.get('action') == 'block', f"expected block, got {fm_mal.get('action')}"

rule_mal = Rule.from_dict(fm_mal, "Blocked!")
assert rule_mal.action == 'block', f"rule silently downgraded to {rule_mal.action}"
```
Expected (fixed) result: both `fm_clean['action']` and `fm_mal['action']` equal `'block'`, and `rule_mal.action == 'block'`, preserving the "deny means deny" invariant. Currently, `fm_mal` is missing the `action` key entirely, `rule_mal.action` evaluates to `'warn'`, and `RuleEngine.evaluate_rules` would return a non-blocking (`systemMessage`-only) response instead of `permissionDecision: deny` for a matching dangerous command.
