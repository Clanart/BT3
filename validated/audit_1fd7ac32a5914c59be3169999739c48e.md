### Title
Partial-commit line selection is positional, not content-bound, allowing a background-modified file to silently commit unintended content - (File: `app/src/models/diff/diff-selection.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
`DiffSelection` records which lines a user has (de)selected for a partial commit purely as a set of numeric line indices (`divergingLines`), with no binding to the actual line content or diff hunk identity. [1](#0-0)  When the user later commits, `applyPatchToIndex` re-fetches a *fresh* diff of the file's current on-disk state and blindly re-applies the old, positionally-indexed selection to it via `formatPatch`/`file.selection.isSelected(absoluteIndex)`. [2](#0-1) [3](#0-2)  If the file's diff has changed shape (lines shifted, hunks reflowed) between when the user made their selection and when the patch is generated, the old line indices will map to different, unrelated lines in the new diff, producing a patch that does not correspond to what the user actually reviewed and selected.

### Finding Description
This mirrors the external report's broken invariant: a value (the fee/selection) is computed against one state (`lent`/the original diff), but the real effect is realized against a different, later state (the balance delta/the refreshed diff), and the mismatch is never reconciled or re-validated against content.

In Desktop:
1. The user opens a file's diff in the Changes view; `updateChangesWorkingDirectoryDiff` loads a diff and lets the user toggle line selections via `withLineSelection`/`withRangeSelection`, which store raw absolute line indices in `divergingLines`. [4](#0-3) 
2. The code is aware that the diff can change "dramatically" between loads and only reconciles by intersecting with the new set of *selectable* (indexable) positions — not by matching actual line content: `withSelectableLines` merely filters `divergingLines` to indices still present in `selectableLines`, it does not check whether the content at that index is the same line the user selected. [5](#0-4) [6](#0-5) 
3. At commit time, `applyPatchToIndex` fetches yet another independent, current diff (`getWorkingDirectoryDiff`) and feeds it straight into `formatPatch(file, diff)`, which walks the new diff's hunks and asks `file.selection.isSelected(absoluteIndex)` for each line — using indices computed from a diff that may already be stale relative to this newest one. [7](#0-6) 

Because nothing in this path compares old-line-content vs new-line-content (only position), if the working file is modified by any external process between the user's selection and the commit action (e.g., a build tool, a lint/format-on-save hook, a `post-checkout`/`post-merge` git hook shipped in a cloned/fetched repository, or any background watcher the repository's tooling spawns), the positional indices silently point at different content. Existing guards (`resolveWithin`, `sanitizeCloneName`, `isClonePathSensitive`) address path-traversal on clone/checkout but do nothing to protect line-selection integrity during the commit/patch-generation stage, so they do not stop this path. [8](#0-7) 

### Impact Explanation
The corrupted value is the generated patch/commit content itself: the user believes they are committing exactly the lines they visually selected, but the actual staged/committed diff can differ from what was reviewed, silently including unreviewed additions or excluding intended ones, without any error or warning to the user. This falls squarely under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires only that the working tree file change (in a way that reshapes the diff, e.g., inserting/removing lines above the previously-selected hunk) between the time the user makes a partial selection and the time they click Commit — a normal race window in any workflow that involves file watchers, auto-formatters, or repository-provided git hooks, none of which require local/admin access or social engineering by the attacker beyond the user opening/using a crafted repository. It is a background/UI-timing condition rather than a forced exploit, so exploitability depends on timing, but the code path itself has no content-based reconciliation to prevent it once the race is hit.

### Recommendation
Bind diff-selection state to actual line content (e.g., hash or exact text of the line) rather than pure positional index, or re-diff and re-validate that the selected hunks' content is unchanged immediately before formatting/applying the patch, aborting or prompting the user if a mismatch is detected — analogous to recomputing the fee after the real balance-changing operation in the original report rather than trusting the pre-operation quantity.

### Proof of Concept
1. Open GitHub Desktop on a repository containing `file.txt` with several lines.
2. Modify `file.txt` and, in the Changes view, select only a subset of the added lines for a partial commit (`DiffSelectionType.Partial`, storing absolute indices in `divergingLines`).
3. Before clicking "Commit", have an external process (e.g., a `post-checkout`/`post-merge` hook bundled in the cloned repo, or an editor auto-format-on-save/build watcher configured by the repo) rewrite `file.txt`, adding/removing lines above the selected hunk so the diff reflows.
4. Click "Commit". `applyPatchToIndex` re-fetches the diff (now shifted) and calls `formatPatch(file, diff)`, which uses the stale `divergingLines` indices against the new hunk layout. [7](#0-6) [3](#0-2) 
5. Inspect the resulting commit: the staged/committed lines do not match what was visually selected in step 2 — content the user never reviewed or explicitly selected is committed (or vice versa, intended content is dropped) without any warning.

  public withRangeSelection(
    from: number,
    length: number,
    selected: boolean
  ): DiffSelection {
    const computedSelectionType = this.getSelectionType()
    const to = from + length

    // Nothing for us to do here. This state is when all lines are already
    // selected and we're being asked to select more or when no lines are
    // selected and we're being asked to unselect something.
    if (typeMatchesSelection(computedSelectionType, selected)) {
      return this
    }

    if (computedSelectionType === DiffSelectionType.Partial) {
      const newDivergingLines = new Set<number>(this.divergingLines!)

      if (typeMatchesSelection(this.defaultSelectionType, selected)) {
        for (let i = from; i < to; i++) {
          newDivergingLines.delete(i)
        }
      } else {
        for (let i = from; i < to; i++) {
          // Ensure it's selectable
          if (this.isSelectable(i)) {
            newDivergingLines.add(i)
          }
        }
      }

      return new DiffSelection(
        this.defaultSelectionType,
        newDivergingLines.size === 0 ? null : newDivergingLines,
        this.selectableLines
      )
    } else {
      const newDivergingLines = new Set<number>()
      for (let i = from; i < to; i++) {
        if (this.isSelectable(i)) {
          newDivergingLines.add(i)
        }
      }

      return new DiffSelection(
        computedSelectionType,
        newDivergingLines,
        this.selectableLines
      )
    }
  }
