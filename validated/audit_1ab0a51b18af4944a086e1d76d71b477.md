Audit Report

## Title
Unbounded per-request work in `getVoteAccounts` RPC over an attacker-growable vote-account set - (File: `rpc/src/rpc.rs`)

## Summary
`get_vote_accounts` at `rpc/src/rpc.rs:1155-1246` iterates the entirety of `bank.vote_accounts()` and, for every entry, unconditionally deserializes the vote state, computes `last_vote`, and builds an `epoch_credits` vector before any stake-based filtering is applied. Because `bank.vote_accounts()` admits any correctly-sized, initialized vote-program account regardless of stake, an unprivileged attacker can inflate this map with cheap, zero-stake vote accounts and force disproportionate per-request CPU/memory cost on any node serving this public RPC method.

## Finding Description
The vulnerable code path does the expensive per-account work unconditionally inside the iterator, before the delinquency/stake partition and filter: [1](#0-0) 

This is confirmed to have no per-account-count guard: the only relevant limit in this file, `MAX_RPC_VOTE_ACCOUNT_INFO_EPOCH_CREDITS_HISTORY`, only bounds the length of the `epoch_credits` array *within* a single account's history, not the number of accounts iterated: [2](#0-1) 

Stake-based filtering (`activated_stake > 0`) is applied only after the expensive work, and only to the delinquent bucket, and only when the caller doesn't set `keep_unstaked_delinquents`: [3](#0-2) 

`bank.vote_accounts()` is populated unconditionally by `StakesCache::check_and_store` for any account owned by the vote program that passes the size/initialization check — with no relationship to stake: [4](#0-3) 

A dedicated unit test explicitly confirms a zero-stake vote account is inserted into `VoteAccounts` (only `staked_nodes` excludes it, not the main map that `get_vote_accounts` reads): [5](#0-4) 

Creating such an account is fully permissionless via `VoteInstruction::InitializeAccount`, requiring only a rent-exempt, correctly-sized account and a self-controlled signer — no stake, no validator identity, no special permission: [6](#0-5) 

The only existing cap that reduces the size of a vote-account collection in this codebase, `clone_and_filter_for_vat` in `vote/src/vote_account.rs`, applies to the separate VAT (Vote Account Table) construction path used for Alpenglow/SIMD-357, not to `bank.vote_accounts()` itself or to the `get_vote_accounts` RPC handler: [7](#0-6) 

Thus the general-purpose `Stakes::vote_accounts` map that backs `get_vote_accounts` is unbounded, and the RPC handler processes it in full on every call with no cap, no pagination, and no pre-filtering by stake before the expensive per-account work.

## Impact Explanation
This falls under the allowed "single-client low-rate RPC crash/degradation" impact category: a single unauthenticated caller issuing one `getVoteAccounts` request can force a target RPC node to perform vote-state deserialization and epoch-credit extraction for every attacker-created zero-stake vote account, with cost scaling linearly and unboundedly with the attacker-controlled account count, degrading or crashing the node for legitimate users.

## Likelihood Explanation
High. `VoteInstruction::InitializeAccount` is a stable, permissionless instruction requiring only rent-exemption lamports (recoverable later via withdrawal) and a normal transaction fee — as reflected in vote-account creation tooling that computes the rent-exempt minimum for `VoteStateV4::size_of()`: [8](#0-7) 
`getVoteAccounts` is a standard, commonly enabled public RPC method (`rpc_minimal`), and the vulnerable iteration is unconditional with no feature gate: [9](#0-8) 

## Recommendation
- Apply stake filtering (or another cap) before the expensive per-account work (vote-state deserialization, epoch-credit extraction, string formatting) rather than after.
- Impose an explicit cap or pagination on the number of vote accounts processed per `getVoteAccounts` call.
- Consider bounding how many zero-stake vote accounts `StakesCache`/`Stakes::vote_accounts` retains, since other bank/RPC code paths reference this same unbounded map.

## Proof of Concept
1. Generate N keypairs; for each, submit a `VoteInstruction::create_account_with_config` + `InitializeAccount` transaction funding only the rent-exempt minimum for a `VoteStateV4`-sized account, with attacker-controlled `authorized_voter`/`authorized_withdrawer` and no delegated stake.
2. Repeat for a large N, spread across multiple transactions/slots to stay within normal per-transaction fee/compute limits.
3. Once these accounts populate `bank.vote_accounts()` via `StakesCache::check_and_store`, issue a single `getVoteAccounts` RPC call (no `vote_pubkey` filter) against the target node.
4. Observe RPC-node CPU/latency degradation proportional to N, since `get_vote_accounts` deserializes vote state and builds `epoch_credits` for every one of the N accounts before any stake-based filtering is applied.
