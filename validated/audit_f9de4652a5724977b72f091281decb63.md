### Title
`ExecuteTransactions` validator-path speculative execution omits bundle-atomicity / receipt-status checks enforced on the block-building path, allowing acceptance of an invalid gasless-bundle block - ([File: work/execution.go])

### Summary
Kaia's `kaiax/gasless` module funds gas for users via a `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` bundle, and the block-building path (`work/worker.go`) enforces that this bundle is atomic: if any transaction in the bundle fails or reverts, the whole bundle — including the `LendTx` that transfers value from the proposer to the sender — is rolled back via `restoreEnv()` in `commitBundleTransaction`. However, the validator-side "read"/verification path, `DefaultExecutor.ExecuteTransactions` in `work/execution.go`, which is explicitly documented as "the validator-path primitive used during speculative execution of a received pre-prepare block", replays the bundle's transactions one by one via plain `ApplyTransaction` calls and only aborts on a hard Go `err != nil`. It never checks `receipt.Status != types.ReceiptStatusSuccessful`, unlike the analogous atomicity check in `commitBundleTransaction`.

### Finding Description
Two code paths exist for executing a block's transaction list in Kaia:

1. **Block building (proposer) path** — `work/worker.go`'s `ApplyTransactions` → `commitBundleTransaction`, which explicitly enforces bundle atomicity: [1](#0-0) 
This checks both `err != nil` **and** `receipt.Status != types.ReceiptStatusSuccessful`, and calls `restoreEnv()` to fully roll back every transaction in the bundle — including the `LendTx` — if the trailing `SwapTx` (repayment) reverts.

2. **Validator speculative-execution path** — `work/execution.go`'s `ExecuteTransactions`, used by other validators to replay a received pre-prepare block before voting: [2](#0-1) 
This loop calls `e.chain.ApplyTransaction` per transaction and only treats the transaction as invalid if it returns a Go-level `err`. It has **no knowledge of gasless bundles** and never inspects `receipt.Status`. A reverted EVM call (e.g. the `GaslessSwapTx` failing its repayment due to slippage, insufficient balance, or a deliberately-crafted revert condition) does **not** produce a Go `err` from `bc.ApplyTransaction` — `ApplyTransaction` only returns an error for out-of-gas/consensus-level failures, not for `VmExecutionStatus` reverts: [3](#0-2) 

Consequently, this validator path will accept — and compute a "matching" state root for — a block in which a `LendTx` (moving value out of the proposer's balance to the swap sender) succeeds while the corresponding `GaslessApproveTx`/`GaslessSwapTx` (the on-chain repayment mechanism) reverts, something the honest block-building path is specifically designed to prevent via full-bundle rollback.

The `Executor` interface documents this asymmetry explicitly: [4](#0-3) 

### Impact Explanation
This is a state-transition/acceptance-of-invalid-block bug rather than a simple crash: a malicious block proposer can hand-craft a pre-prepare block containing a `[LendTx, GaslessApproveTx, GaslessSwapTx]` sequence where the `SwapTx` is engineered to revert (e.g., mismatched `minAmountOut`/slippage, or targeting a DEX pool state that will cause revert) while the `LendTx` still executes successfully. When honest validators run `ExecuteTransactions` to speculatively validate this pre-prepare block, they will not detect that the bundle's atomicity invariant was violated (since only `err != nil` is checked, not receipt status), and may therefore vote to accept a block whose state transition diverges from what the canonical block-building logic in `work/worker.go`/`commitBundleTransaction` would ever produce (that code path would have discarded the whole bundle instead). This breaks the core safety guarantee of the gasless mechanism (KIP-247) — that a proposer's gas loan is only released atomically alongside its DEX-based repayment — enabling fee/value-movement abuse: the "lender" value transfer proceeds without the paired on-chain repayment being enforced consistently across validators, and risks state divergence between honest nodes that build blocks (always enforcing atomicity) and honest nodes that only validate via `ExecuteTransactions` (not enforcing it).

### Likelihood Explanation
Any block proposer participating in BFT consensus can submit a pre-prepare block; the trigger only requires embedding a bundle whose trailing transaction reverts via `VmExecutionStatus` rather than a hard Go error, which is a well-known/easy EVM primitive (e.g. through a Solidity `require`/`revert` in a DEX contract call). The vulnerable code (`ExecuteTransactions`) is explicitly the designated path other validators use to verify a proposer's exact transaction ordering, so the divergent-check behavior is reliably reachable by any adversarial validator/proposer — no special network position or malicious-node capability beyond being a normal (even rotating) validator is required.

### Recommendation
Add the same atomicity/receipt-status enforcement used in `commitBundleTransaction` to `ExecuteTransactions`: identify gasless (and any other bundling-module) transaction groups within the replayed list, and treat `receipt.Status != types.ReceiptStatusSuccessful` for any transaction inside a bundle as equivalent to a hard failure requiring rejection of the entire bundle/block, mirroring the `err != nil || receipt.Status != types.ReceiptStatusSuccessful` check in `work/worker.go`. Alternatively, refactor `ExecuteTransactions` to reuse `builder.ExtractBundlesAndIncorporate` plus `commitBundleTransaction`/`shouldDiscardBundle` logic so both the block-building and block-validating code paths share one authoritative bundle-atomicity implementation.

### Proof of Concept
Conceptual PoC (cannot be executed without the live chain/tooling):
1. As a malicious proposer, construct a pre-prepare block containing (in order): `LendTx` (signed with the proposer's node key, sending gas-loan value to `senderAddr`), `GaslessApproveTx` (from `senderAddr`), and `GaslessSwapTx` (from `senderAddr`) where the swap parameters are chosen so the underlying router call reverts (e.g. set `minAmountOut`/`amountRepay` inconsistent with actual pool state, or target a pool state known to revert at execution time).
2. Broadcast this block as a pre-prepare to the validator set.
3. Each validator calls `Executor.ExecuteTransactions` (`work/execution.go:147-180`) to replay the block prior to voting. Because `bc.ApplyTransaction` returns `err == nil` for a transaction that reverts inside the EVM (only the receipt's `VmExecutionStatus`/`Status` reflects the revert), the loop does not detect the failure and proceeds to compute a resulting state/root that includes the `LendTx`'s balance transfer without the corresponding repayment enforced.
4. Validators, seeing a "successfully executed" replay matching the proposer's claimed transactions, vote to accept the block — despite this exact bundle being one the local proposer's own `commitBundleTransaction` logic (`work/worker.go:916-936`) would have fully reverted (including undoing the `LendTx`) had it built the block itself.

func (e *DefaultExecutor) ExecuteTransactions(txs []*types.Transaction) (*consensus.ExecutionResult, error) {
	e.mu.Lock()
	defer e.mu.Unlock()

	if !e.initialized {
		return nil, ErrExecutorNotInitialized
	}

	// Pre-tx hooks (EIP-2935, kaiax module pre-hooks, etc.)
	e.chain.Processor().InitializeState(e.header, e.state)

	// Extract the block proposer from the header seal — must match
	// StateProcessor.Process so COINBASE and reward distribution are identical.
	// Using e.nodeAddr here would be wrong: the local validator is not
	// necessarily the proposer of this block.
	author, _ := e.chain.Sealer().Author(e.header)

	var (
		receipts types.Receipts
		allLogs  []*types.Log
		usedGas  = new(uint64)
	)

	for i, tx := range txs {
		e.state.SetTxContext(tx.Hash(), common.Hash{}, i)
		receipt, _, err := e.chain.ApplyTransaction(
			e.config, &author, e.state, e.header, tx, usedGas, &vm.Config{},
		)
		if err != nil {
			return nil, fmt.Errorf("tx %d (%s): %w", i, tx.Hash().Hex(), err)
		}
		receipts = append(receipts, receipt)
		allLogs = append(allLogs, receipt.Logs...)
	}
