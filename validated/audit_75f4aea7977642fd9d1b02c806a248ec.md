### Title
Missing module/app identity binding in `HostManager.onAccept` allows any Hyperbridge-chain app to trigger host governance actions - (File: evm/src/core/HostManager.sol)

### Summary
`HostManager.onAccept` only checks that an incoming ISMP POST request's `source` chain equals the configured `hyperbridge` state-machine id. It never checks the `from` field of the `PostRequest` (the specific pallet/module identity on the Hyperbridge chain that is expected to originate governance actions). As a result, any contract/pallet capable of dispatching a POST request from the Hyperbridge parachain to this destination module can trigger `Withdraw` (drain host revenue to an attacker-chosen beneficiary) or `SetHostParam` (rewrite the `EvmHost`'s `admin`, `hostManager`, `handler`, `consensusClient`, fee token, or challenge period) actions.

### Finding Description
`HostManager.onAccept` is restricted only by `restrict(_params.host)` (caller must be the local `EvmHost`, which is enforced by ISMP delivery) and by a chain-id check: [2](#0-1) 

It decodes `request.body[0]` as an `OnAcceptActions` enum and executes `withdraw` or `updateHostParams` directly on the host with attacker/proposer-controlled parameters: [3](#0-2) 

`PostRequest` carries both a `source` (chain identifier) and a `from` (source application address) field: [4](#0-3) 

Only `source` is checked here — `from` is read into the local `request` variable but is never compared against any expected governance-module address. This breaks the Hyperbridge pivot requirement that "request... paths must bind chain id, module/app identity... on both Substrate and EVM." Binding only the chain id is insufficient: on the Hyperbridge parachain, chain-id-level source identity is shared by every pallet/contract capable of dispatching ISMP requests from that chain, so nothing here restricts the caller to specifically the intended governance/host-executive module (e.g., `pallet_ismp_host_executive`, referenced in the test env). The Rust test suite corroborates that only `source` (`StateMachine::Kusama(2000)` vs `StateMachine::Polkadot(1000)`) is exercised as the authorization boundary; `from` is set to an arbitrary `env.sender` in every test and is never asserted against an allow-listed governance module address: [5](#0-4) [6](#0-5) 

`EvmHost.updateHostParams`/`withdraw` themselves only check `restrict(_hostParams.hostManager)`, i.e. they trust `HostManager` as the sole gatekeeper for governance-origin requests: [7](#0-6) [8](#0-7) 

Because `HostManager` is the single point that is supposed to authenticate that a governance request truly originated from the intended Hyperbridge governance module, and it omits the `from` check, the entire authorization chain collapses to "any dispatcher on the Hyperbridge parachain."

### Impact Explanation
This is a false-authorization / unauthorized-execution primitive matching the bounty's "unauthorized transaction or execution" and "stealing or loss of funds" categories: an attacker-controlled module on the Hyperbridge chain could dispatch a `Withdraw` action draining all fee-token/native revenue held by `EvmHost` to an arbitrary beneficiary, or a `SetHostParam` action replacing `admin`, `hostManager`, `handler`, or `consensusClient` with attacker-controlled addresses — which would let the attacker subsequently accept forged consensus/state proofs or seize full administrative control of the host, cascading into false state acceptance and fund loss across the whole bridge.

### Likelihood Explanation
This does not require a malicious relayer, prover, or leaked key — it only requires the ability to dispatch an ISMP POST request from an address on the Hyperbridge parachain with `dest` set to the target `EvmHost`'s `HostManager`. Since `from`-binding is absent, any contract/pallet on the Hyperbridge chain (not just the intended governance pallet) that can invoke the ISMP dispatch mechanism qualifies as a valid caller, once its request is relayed and delivered through the (already correctly verified) proof/consensus pipeline. This is a normal, permissionless-looking dispatch, not a privileged or off-chain compromise.

### Recommendation
In `HostManager.onAccept`, in addition to verifying `request.source.equals(hyperbridge)`, verify `request.from` equals a configured, immutable (or governance-settable-only-through-a-safe-path) governance-module identity on the Hyperbridge chain, e.g. store an expected `bytes governanceModule` in `HostManagerParams` and require `request.from.equals(_params.governanceModule)` before dispatching `Withdraw`/`SetHostParam`.

### Proof of Concept
Based on the existing Rust integration test harness, replace the governance `from` sender with an arbitrary, non-governance signer while keeping `source = StateMachine::Kusama(2000)` (the correct chain id) — the request still succeeds because `from` is never checked: [9](#0-8) 
Modify `test_host_manager_withdraw`/`test_host_manager_set_host_params` to set `from: <attacker_address>.as_slice().to_vec()` instead of `env.sender` tied to any governance role — the assertions (`host_balance` decreases by the withdrawn amount, or `challengePeriod` updates to attacker-chosen value) still pass, demonstrating that `onAccept` authorizes based on chain id alone, not module identity.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");

        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
