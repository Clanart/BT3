## Finding: Missing zero-value validation for `GasTarget` governance parameter causes divide-by-zero panic in KIP-71 base fee calculation

### Title
Unvalidated `Kip71GasTarget=0` governance parameter causes divide-by-zero panic in `NextMagmaBlockBaseFee` - ([File: params/kip71_config.go])

### Summary
The CVE describes a Python function that fails to validate a value used later as a divisor (`nchannels`), causing an unhandled divide-by-zero exception when malicious/malformed input reaches that code path. The same bug class exists in Kaia's KIP-71 dynamic base-fee logic: `GasTarget` is used as a divisor in `NextMagmaBlockBaseFee` but, unlike its sibling parameter `BaseFeeDenominator`, it has no zero-value validation anywhere in the governance parameter pipeline.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` explicitly guards against `BaseFeeDenominator == 0` by substituting a safe default of 64: [1](#0-0) 

However, `GasTarget` receives no equivalent protection and is used directly as a `big.Int` divisor when the parent block's gas usage differs from the target: [2](#0-1) [3](#0-2) 

`big.Int.Div`/`.Quo` panics on division by zero in Go, so if `GasTarget == 0` and `parentGasUsed != 0`, `parentGasUsed > gasTarget` is true and `x.Div(x, new(big.Int).SetUint64(gasTarget))` panics.

Critically, the governance parameter registry validates `Kip71BaseFeeDenominator` with an explicit non-zero `FormatChecker`, but `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all: [4](#0-3) 

This means a governance vote/parameter update setting `GasTarget` to `0` is accepted by the governance format checker with no rejection, and will later be applied by every node computing the next block's base fee via `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` — including in `feehistory.go`'s `processBlock` (used by the public `eth_feeHistory` RPC) and in `gasprice.go`'s `SuggestPrice`.

### Impact Explanation
Once `GasTarget=0` is active, any block whose gas usage is nonzero (i.e., virtually every real block) will cause `NextMagmaBlockBaseFee` to panic on every node that evaluates it — during block header verification, fee suggestion (`SuggestPrice`), and public RPC fee history queries (`eth_feeHistory`). This is a network-wide denial of service: full nodes crash or reject valid blocks as soon as this governance value takes effect, since header verification for the next Magma block calls this same divide path.

### Likelihood Explanation
`Kip71GasTarget`'s `FormatChecker` is a no-op, so nothing in the governance parameter validation pipeline prevents this value from being set to zero via a governance parameter change. This contrasts with `Kip71BaseFeeDenominator`, which the developers clearly intended to protect from being zero via an explicit check, but the same protection was not extended to `GasTarget` despite it being used identically as a divisor.

### Recommendation
Add a non-zero `FormatChecker` for `Kip71GasTarget`, matching `Kip71BaseFeeDenominator`, and/or add a defensive zero-check for `GasTarget` inside `NextMagmaBlockBaseFee` (as already done for `BaseFeeDenominator`) so a zero value cannot reach the `big.Int` division.

### Proof of Concept
1. Submit/approve a governance parameter update setting `governance.kip71.gastarget` (`Kip71GasTarget`) to `0`. The format checker at [5](#0-4)  accepts this value unconditionally (`noopFormatChecker`).
2. Once this parameter set becomes active, any block with `GasUsed > 0` (i.e., `parentGasUsed > gasTarget`, since `gasTarget == 0`) triggers `NextMagmaBlockBaseFee` in [6](#0-5)  to execute `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, which panics with "division by zero" in Go's `math/big`.
3. This function is invoked from block header verification (`VerifyMagmaHeader`) on every node, and from the public `eth_feeHistory` RPC path in `node/cn/gasprice/feehistory.go`'s `processBlock`, causing crashes/DoS network-wide.
