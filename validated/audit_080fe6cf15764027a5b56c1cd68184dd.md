Based on my investigation, I found a genuine analog to the reported bug class: a proof-verification threshold that accepts exactly the boundary quorum instead of the documented supermajority-plus-one, mirroring the "few validators / weak quorum" primitive from the LightClient report.

### Title
BSC consensus client accepts exactly 2/3 validator participation instead of the required supermajority-plus-one - (File: modules/consensus/bsc/verifier/src/lib.rs)

### Summary
The on-chain BSC (Parlia) consensus client's participation check in `verify_bsc_header` uses a strict `<` comparison against `(2 * current_validators.len()) / 3`, so a vote-attestation with participation *exactly equal to* the truncated 2/3 boundary is accepted. This contradicts the protocol's own documented safety threshold — `(2/3 * N) + 1` — described in `docs/content/protocol/consensus/parlia.mdx:33`, and mirrors the exact bug class in the external report: a fallback/edge condition where less-than-true-supermajority signatures are treated as sufficient to finalize a header and roll forward validator-set state used to accept state commitments for the ISMP bridge.

### Finding Description
`verify_bsc_header` computes the participant threshold as:
```rust
if participant_count < ((2 * current_validators.len()) / 3) {
    Err(Error::NotEnoughParticipants)?
}
``` [1](#0-0) 

For an odd or non-multiple-of-3 validator count this integer-division truncates, so the effective quorum required can be strictly less than 2/3 of the validator set — e.g., for `N=21`, `2*21/3 = 14`, so `participant_count == 14` passes even though the documented safety margin (`(2/3 * N) + 1 = 15`) is not met. The project's own spec states the target explicitly: "requires votes from more than two-thirds of the validators... at least one more unique validator needs to participate to reach the required threshold of (2/3 * N) + 1 votes" [2](#0-1) . The same weaker (non-`+1`) boundary is echoed throughout the relayer pre-filter logic in `tesseract/consensus/bsc/src/host.rs` (`count_ones() < (2 * validators.len() / 3)`) [3](#0-2) , confirming the boundary is systemic rather than a one-off typo, and is exactly the accepted quorum baked into consensus verification, not merely a relayer heuristic.

This is the local analog of the reported LightClient issue: instead of a dedicated `force()` fallback for delayed finality, Hyperbridge's BSC client's *primary* verification path itself accepts the minimal boundary case of "exactly 2/3", one honest-validator short of genuine BFT supermajority safety. Just as the report's `force()` allowed as few as `MIN_SYNC_COMMITTEE_PARTICIPANTS` (10) signers to finalize a sync-committee rotation, here the accepted quorum is silently weaker than the intended and documented BFT threshold, so a validator subset at exactly the 2/3 boundary — which under standard BFT assumptions does *not* guarantee overlap with any other honest quorum — can finalize a header and roll the validator set state (`consensus_state.next_validators` / `current_validators`) that gates all subsequent ISMP state commitments accepted from BSC into Hyperbridge (`modules/ismp/clients/bsc/src/lib.rs:74-172`) [4](#0-3) .

### Impact Explanation
If a header is finalized on this exact-2/3 boundary using a validator subset that does not constitute a genuine 2/3+1 majority, the resulting `StateCommitment` (state root) is accepted as canonical BSC state for the ISMP bridge [4](#0-3) . Downstream, this state root gates request/response and timeout verification (state-trie membership/non-membership checks) for all cross-chain messages routed through the BSC consensus client, meaning false state acceptance could enable unauthorized message delivery or malformed timeouts to be processed as valid, directly matching the "false proof/state acceptance" impact category.

### Likelihood Explanation
Exploiting this requires control (or collusion) of validators whose signed weight lands exactly on the truncated 2/3 boundary rather than a genuine supermajority — this is a validator-set/consensus-participant condition, which is closer to a "compromised validator/consensus" scenario than a pure unprivileged-attacker path. It is not directly reachable by an unprivileged actor without validator key control, so likelihood under the stated Impact Gate (which excludes "compromised relayer/prover/operator assumptions") is borderline; however, unlike the DoS-forced-`force()` scenario in the original report, no DoS or privileged relayer/admin action is needed — the weaker boundary is baked into the client's always-active primary verification path, so it fires on every consensus update, not just during an induced liveness failure.

### Recommendation
Change the check in `verify_bsc_header` to enforce the documented `(2/3 * N) + 1` threshold:
```rust
if participant_count < ((2 * current_validators.len()) / 3) + 1 {
    Err(Error::NotEnoughParticipants)?
}
```
Apply the same correction to the relayer-side pre-filters in `tesseract/consensus/bsc/src/host.rs` and `modules/consensus/bsc/prover/src/test.rs` for consistency (though these are advisory only, not security-critical). Add a regression test asserting that participation exactly equal to the truncated `2N/3` boundary is rejected, matching the existing `rejects_too_few_in_range_participants` test pattern already present in `modules/consensus/bsc/verifier/src/lib.rs:372-382`.

### Proof of Concept
For `N=21` validators (BSC testnet shape used in existing tests), the threshold in code is `2*21/3 = 14`. A vote-attestation bit-set with exactly 14 of 21 validators set will pass `verify_bsc_header`'s participation check (`participant_count < 14` is false when `participant_count == 14`), whereas the protocol's documented supermajority requirement is 15 (`(2*21/3)+1`). This can be reproduced by adapting the existing test `accepts_fully_populated_in_range_bits` in `modules/consensus/bsc/verifier/src/lib.rs:330-346` to set exactly 14 bits instead of all 21, and observing that the error returned is *not* `NotEnoughParticipants` — confirming the boundary case is accepted contrary to the documented spec.
