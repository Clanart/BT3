### Title
Unauthenticated `purchase()` sponsorship lets an attacker evict a victim app's paid bandwidth via FIFO cap-eviction, causing loss of funds - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth`'s `on_accept` credits a `(app_chain, app)` bandwidth allowance based solely on the `chain`/`app` fields chosen by the caller of `BandwidthManager.purchase()` — there is no check that the purchaser is the app itself or an authorized sponsor. Combined with the hard 1024-entry FIFO cap that unconditionally evicts the oldest subscription on overflow, any unprivileged attacker can grief a victim app by repeatedly buying the cheapest tier targeted at the victim's `(chain, app)` key until the victim's legitimately paid-for, non-expired, high-value subscription is evicted and its `remaining_bytes` permanently lost.

### Finding Description
The "Sponsorship" feature intentionally allows anyone to pay for bandwidth on behalf of any `(chain, app)` pair — the pallet keys allowance storage on the message body's `chain`/`app`, not on `request.source`/the payer [1](#0-0) . `on_accept` only validates that `request.from` equals the registered `BandwidthManager` contract address for the source chain; it performs no authorization on the `app` field decoded from the purchase body [2](#0-1) .

Each `(app_chain, app)` row is a `BoundedVec<Subscription, ConstU32<1024>>` (`SubscriptionList`) [5](#0-4) . `push_subscription` appends every new purchase; when the list is already at `MAX_SUBSCRIPTIONS` (1024), it unconditionally `remove(0)`s the oldest entry — the head of the FIFO — with no check on that entry's remaining bytes or time-to-expiry [3](#0-2) .

This is the direct structural analog of the external report's core broken invariant: an unprivileged actor can flood a FIFO queue with cheap, low-value entries to force the eviction/displacement of a legitimate, high-value entry that a victim is entitled to. In the EigenLayer report, the queue holds withdrawal requests processed FIFO; here, the queue holds paid bandwidth subscriptions drained FIFO. In both cases, the queue has a bound (implicit gas/processing limit there, explicit `1024` cap here) and no cost-scaling or per-purchaser rate limiting ties queue slots to the value being displaced.

Concretely: the cheapest configured tier (e.g. `TierOne`, 100 KB, priced from as little as $50 per the docs' example pricing table [6](#0-5) ) can be purchased 1024 times targeting a victim's `(chain, app)` key. Since same-tier repurchases "queue" rather than "stack" [7](#0-6) , each attacker purchase appends a new entry; the 1025th purchase evicts the oldest entry in the list — which, if the attack is timed after (or interleaved with) a victim's own legitimate large purchase (e.g., the $1000/8MB tier), evicts the victim's subscription outright, emitting `SubscriptionEvicted { lost_bytes }` for funds the victim already paid for and had not yet consumed [8](#0-7) .

### Impact Explanation
This is a direct loss-of-funds condition matching the bounty's "stealing or loss of funds" impact category: a victim app's already-paid bandwidth allowance (fee-token value locked in the `BandwidthManager` contract, held until governance withdraws it per the docs [9](#0-8) ) is permanently destroyed by an unrelated, unprivileged third party, with the attacker paying only for cheap-tier eviction filler while the victim's costly allowance is discarded. No relayer/prover/admin collusion is required — the path is a fully public `purchase()` call plus normal message delivery.

### Likelihood Explanation
The attack requires no privileged role, no compromised infrastructure, and no malformed proofs — only repeated calls to the public `purchase()` entrypoint targeting a known victim `app` address, which is discoverable on-chain from the victim's own purchase events (`BandwidthPurchased`/`BandwidthCredited`). The only cost is 1024 cheapest-tier purchase transactions (a bounded, calculable cost) versus the value of whatever the victim previously locked in; for high-value/long-duration subscriptions (e.g., annual $1000 tiers) the economics can clearly favor the attacker, especially against smaller or infrequent apps that don't top up often enough to keep the queue full of their own legitimate entries.

### Recommendation
- Scale eviction to value: reject/evict based on remaining value or require the incoming purchase's value to exceed the evicted entry's remaining value, or refuse to evict entries with significant unused `remaining_bytes`/long `expires_at` in favor of a purchase-fee refund/queue mechanism.
- Consider tying `Allowance` mutation authorization to `request.source` + `app` combination the app itself controls (e.g., an opt-in "sponsor allowlist" per app) so unsolicited third-party purchases can't independently manipulate a victim's queue.
- Alternatively, replace hard FIFO eviction with a priority scheme that only evicts fully-expired or fully-drained entries, returning an error (and refusing to credit further) once the list is genuinely full of live, valuable subscriptions — mirroring the "no mutation on insufficient" safety property already used in the gate's `try_consume`.

### Proof of Concept
1. Governance configures `TierOne` cheaply (e.g., `bytes: 1, duration_secs: large`) and `TierFour` richly (per the docs' example tiers) [10](#0-9) .
2. Victim app buys a `TierFour` multi-month subscription for its own `(chain, app)` key via `BandwidthManager.purchase()`, landing as one `Subscription` entry with large `remaining_bytes` and a distant `expires_at`.
3. Attacker, with no relationship to the victim, calls `purchase()` 1024 times from any account, each time setting `app = victim_app_bytes` and `chain = victim_chain` in the `BandwidthPurchaseMsg`, buying the cheapest tier each time.
4. Each purchase is delivered to `pallet-bandwidth::on_accept`, which calls `push_subscription` [11](#0-10) ; once the victim's `(chain, app)` list reaches 1024 entries, the next attacker purchase evicts the oldest entry in the list via `list.remove(0)` [12](#0-11) .
5. If the victim's `TierFour` entry is (or becomes, through repeated attacker purchases) the oldest live entry, it is evicted and `SubscriptionEvicted { lost_bytes }` fires — the victim's paid-for bandwidth is gone, verifiable via `Pallet::remaining(app_chain, app)` dropping to reflect only attacker-purchased dregs.

		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

## Cost of a Purchase

A purchase is an ordinary ISMP dispatch under the hood. The pallet-side credit pays no relayer fee (`fee: 0` in the dispatch) because the pallet itself is the recipient — there's no relayer network involvement in landing the credit. The only on-chain cost on the source side is:
