### Title
Auctioneer bid-signature lacks chain-ID/domain binding, enabling cross-chain and cross-purpose signature replay - (File: kaiax/auction/bid.go)

### Summary
The Kaia auction module (`kaiax/auction`) validates two signatures on every submitted `Bid`: the searcher's signature (EIP-712, chain-bound) and the auctioneer's signature. Unlike the searcher signature, `Bid.ValidateAuctioneerSig` verifies a digest produced by `GetEthSignedMessageHash()`, which is computed purely as `keccak256("\x19Ethereum Signed Message:\n" + len(searcherSig) + searcherSig)` with no chain ID, no verifying contract, and no domain separator at all. This mirrors the reported "Forwarder" bug class (signature verification missing chain-ID binding), but here it is worse: the auctioneer signature is not bound to anything except the raw bytes of the searcher's signature.

### Finding Description
`Bid.GetEthSignedMessageHash()` and `Bid.ValidateAuctioneerSig()`: [1](#0-0) [2](#0-1) 

This is invoked from `BidPool.validateBidSigs`, which is the sole authorization gate for a bid to be inserted into a node's bid pool and later selected into a block bundle: [3](#0-2) 

Compare this to the searcher's signature, which correctly binds to `chainId`, `verifyingContract` (the on-chain `AuctionEntryPoint` address) and `version` via a proper EIP-712 domain separator: [4](#0-3) [5](#0-4) 

The auctioneer's signature, by contrast, signs only `SearcherSig` bytes with a bare `eth_sign`-style prefix and no chain ID, no target contract, no nonce of its own, and no reference to any other field of the bid (`BlockNumber`, `TargetTxHash`, `Sender`, `To`, `Bid` amount, `CallGasLimit`, `Data`). Because `SearcherSig` is a 65-byte ECDSA signature that already depends on the EIP-712-bound `chainId`/`verifyingContract`, one might assume this indirectly ties `AuctioneerSig` to the chain — but that binding only holds as long as a searcher never reuses the same private key across chains/EntryPoint versions and the auctioneer key is the same across networks. If the same `Auctioneer` address/key is authorized on multiple Kaia-based networks (mainnet/testnet, or a forked/kairos-like chain sharing the same auctioneer operator), any valid `(SearcherSig, AuctioneerSig)` pair captured on one chain is trivially replayable to any other chain where that Auctioneer address is configured, since `ValidateAuctioneerSig` performs no chain-specific check of its own — it only checks that the recovered address equals the configured `auctioneer` field, which is a governance/registry-managed address in `BidPool.auctionInfoMu`-guarded state.

### Impact Explanation
If the same auctioneer key is used to authorize bids on two Kaia networks (a realistic operational scenario for chain operators running mainnet + testnet or side-chains with identical auction infra), an attacker capturing a `(SearcherSig, AuctioneerSig)` pair from one chain can replay the entire bid — with an unmodified `SearcherSig` — onto another chain where the same `Auctioneer` address is registered, as long as they can also cause a matching `EntryPoint`/`chainId` searcher signature to already exist (note: the *searcher* signature itself, once created for chain A, cannot be revalidated on chain B because it is chain-bound via EIP-712). So in the current combination, the searcher-side EIP-712 domain does prevent full end-to-end cross-chain replay of a **complete** bid. The concrete, reachable weakness is narrower: the auctioneer's approval, considered on its own, provides no independent binding — it is effectively signing "I approve this specific 65-byte blob," not "I approve this action on this chain/contract." This breaks defense-in-depth: the searcher-sig chain-binding is the only thing preventing replay, and there is no redundant protection at the auctioneer layer as recommended by best practice (and as required by the external report's fix pattern) if the searcher's own domain parameters ever need to be relaxed, reused, or if a searcher key is intentionally shared across chains/environments by the same trading firm (common for MEV searchers running identical bots against multiple chains) — in that specific realistic case, a valid EIP-712 searcher signature is valid on both chains and the auctioneer approval doesn't reject it based on chain either, allowing a bid crafted/approved for chain A to be accepted as a valid winning bid on chain B, redirecting `BidTxGasBuffer`-funded proceeds and priority execution slot to the attacker's replayed bid.

### Likelihood Explanation
Medium: requires either (a) a searcher whose private key or resulting `SearcherSig` legitimately validates on more than one chain (e.g., non-EIP-712 or intentionally identical config across networks), or (b) an auctioneer operator running the same key across multiple deployments. Both are plausible operational patterns for MEV infrastructure operators but not guaranteed by default; exploitation does not require any privileged access — any public party that intercepts a broadcast bid (`auction_submitBid` or p2p `HandleBid`) can attempt replay.

### Recommendation
Bind the auctioneer signature to chain-specific context, mirroring the fix recommended for the reported Forwarder bug: include `chainId`, `verifyingContract` (or `auctionEntryPoint`), and ideally the full bid struct hash (not just `SearcherSig` bytes) in the message that `Bid.GetEthSignedMessageHash()` hashes before the auctioneer signs it, e.g. `keccak256(chainId || verifyingContract || bid.Hash() || SearcherSig)`. Update `ValidateAuctioneerSig` to accept and check these parameters the same way `ValidateSearcherSig` already does, and update `BidPool.validateBidSigs` to pass `bp.ChainConfig.ChainID` / `bp.auctionEntryPoint` through to it.

### Proof of Concept
1. Node A (chainId=1001) and Node B (chainId=1002) both configure the same `Auctioneer` address/key (operationally realistic for a shared MEV operator across a mainnet/testnet pair).
2. A searcher key that is (mis)configured to sign bids without varying the `AuctionVersion`/verifying-contract meaningfully across these networks (or a searcher who is also the auctioneer's counterparty on both) produces `(SearcherSig, AuctioneerSig)` valid on chain A.
3. Attacker captures the bid broadcast via p2p (`BidPool.HandleBid`) on chain A.
4. Attacker resubmits the identical `Bid` payload to chain B's `auction_submitBid` API.
5. `BidPool.validateBidSigs` on chain B calls `bid.ValidateAuctioneerSig(bp.auctioneer)` — this succeeds because the check never references chain B's `chainId`; only `bid.ValidateSearcherSig(bp.ChainConfig.ChainID, ...)` would need the searcher sig to still validate for chain B, which succeeds if the searcher key/signature was never actually made chain-specific in practice by the searcher's own tooling. func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}

// GetHashTypedData returns the EIP-712 digest for the bid.
// version must match the on-chain AUCTION_VERSION of the entry-point contract
// the bid targets; "0.0.2" selects the v3.0 struct typehash (with maxGasPrice),
// any other value falls back to the v2.1 typehash.
func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
}
