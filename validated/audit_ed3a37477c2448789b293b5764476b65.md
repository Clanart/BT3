### Cached FROST preprocess seed is reused across signatures, leaking validator private key shares - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`SigningProtocol::preprocess_internal` stores one deterministic FROST preprocess seed per context, then reloads that same seed every time it signs. Reusing the seed reconstructs the same nonce commitments and secret nonce scalars. If the same validator signs two different messages, or signs once with different peer preprocess sets, an observer can solve the resulting Schnorr shares for the validator’s private key share.

### Finding Description
`preprocess_internal` creates a `CachedPreprocess` only when `CachedPreprocesses::get` returns `None`. It encrypts and stores the seed, but never deletes or rotates it after use. On every later call it loads the same stored seed and calls `AlgorithmSignMachine::from_cache`, deterministically reconstructing the same preprocess and signing machine state. [1](#0-0) 

`AlgorithmMachine::seeded_preprocess` seeds a `ChaCha20Rng` directly with the cached value and derives all nonce scalars and commitments from it. [2](#0-1)  During `sign`, the local nonce is combined as `base + actual * rho`, and the Schnorr share is generated from that reused secret nonce. [3](#0-2)  The Schnorr implementation then returns `s = nonce + challenge * secret_share`. [4](#0-3) 

The library explicitly warns that a cached preprocess “MUST only be used once” and that reuse enables recovery of the private key share. [5](#0-4)  The coordinator wrapper nevertheless intentionally reloads the same value each call instead of consuming it.

### Impact Explanation
If two executed sessions reuse the same seed, the validator emits shares of the form:

```text
s1 = r + c1 * x
s2 = r + c2 * x
```

where `r` is the reused local effective nonce and `x` is the validator’s interpolated private key share. If the effective nonce is exactly unchanged, `x = (s1 - s2) / (c1 - c2)` when `c1 != c2`. More generally, if the same `(base, actual)` pair is reused but `rho` differs because attacker-controlled peer preprocesses differ, the two public shares provide two linear equations in `base`, `actual`, and `x`; the public commitments constrain `base` and `actual`, exposing the private share through nonce reuse.

This is key-share recovery, not merely a signing failure. A recovered validator key share can be combined with other exposed shares or used in attacks against the MuSig-based validator signing path.

### Likelihood Explanation
The reused path is the normal code path: after the first signature for a context, `CachedPreprocesses::get` succeeds and `from_cache` reconstructs identical nonce material. [1](#0-0)  `share_internal` always calls `preprocess_internal` again and therefore always reloads the same seed for that context. [6](#0-5) 

An unprivileged participant can vary public preprocess bytes sent to the signer, which changes binding factors and challenge inputs while the local seed remains fixed. A second signing attempt for a different message has the same effect when it causes a different Schnorr challenge.

### Recommendation
Treat a cached preprocess as single-use state:

- Atomically load-and-delete `CachedPreprocesses` before constructing the signing machine.
- Do not call `preprocess_internal` again for a different message or preprocess set under the same cached seed.
- Persist a consumed marker before publishing any signature share, while preserving crash-safety.
- Prefer generating a fresh seed for each signing attempt unless the entire finalized signing transcript, peer set, and message are cryptographically bound to the cache key.
- Add a regression test proving two `share_internal` calls with the same context do not produce identical nonce commitments.

### Proof of Concept
Conceptual derivation:

1. First call stores seed `k` and returns machine/nonces derived from `ChaCha20Rng::from_seed(k)`.
2. Second call reloads `k`, so it derives the same `(base, actual)` nonce pair.
3. For the same effective nonce and two distinct challenges:

```text
x = (s1 - s2) * inverse(c1 - c2)
```

4. The public signature shares `s1`, `s2`, commitments, and challenges are sufficient to recover the signer’s private share `x`.
