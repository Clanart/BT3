Based on my research, I found a concrete division-by-zero analog in the Kaia reward/staking code, structurally similar to the reported `getSupplyRate()` bug (an unguarded `Div` whose denominator can become zero under adversarial-but-reachable input).

### Title
Division by zero in `consolidatedNode.Split()` when consensus-liquidity and CN staking amounts round down to zero - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split()`, used during block reward finalization to split a validator's reward between its CN (staking-only) reward address and its Consensus Liquidity (CL) pool address, divides by `totalAmount = StakingAmount + CLStakingAmount` without checking that this sum is nonzero.

### Finding Description
`consolidatedNode.Split()` performs an unguarded division: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount) // panics if totalAmount == 0
	...
}
```

Both `StakingAmount` and `CLStakingAmount` are derived from on-chain wei amounts, rounded down to whole KAIA units, at ingestion time: [2](#0-1) 

If a validator's CN stake and its associated consensus-liquidity pool stake are both less than 1 KAIA (rounding to `0` after `Div(amounts[i], KAIA)`), then `StakingAmount == 0` and `CLStakingAmount == 0`, yet the node still has a non-nil `CLStakingInfo` entry (any CL pool registered for the `CLNodeId` in the CLRegistry produces an entry, regardless of amount). This is called from the reward finalization path for both the proposer split and staker-reward split: [3](#0-2) [4](#0-3) 

### Impact Explanation
A `big.Int.Div` by zero in Go causes an immediate runtime panic. Since `Split()` is invoked unconditionally from `FinalizeState()`/deferred-reward computation for every Prague-hardfork block whose proposer or eligible stakers have a `CLStakingInfo` entry, triggering this condition would crash block processing for every honest node executing the block — a chain-halting denial of service, not merely a "no impact" revert. This matches the required "state divergence between honest nodes / acceptance of an invalid transaction or block" impact class, since it can prevent any node from producing or importing a valid block.

### Likelihood Explanation
Reaching this requires a validator/staker (an unprivileged, permissionless actor who can register with the AddressBook/CLRegistry and deposit stake) to arrange that both:
1. The CN's own bonded stake (in the AddressBook/CNStakingV2 contract) rounds down to 0 KAIA (i.e., less than 1×10^18 wei bonded), and
2. Its associated consensus-liquidity pool's staked amount also rounds down to 0 KAIA,

while the node remains reward-eligible (`valset.NodeState.IsRewardEligible()`) and is included as the block proposer or an eligible staker. I was not able to fully verify, within the available tool budget, whether the eligibility/minimum-stake gating logic (`reward.minstake`, `IsRewardEligible`) unconditionally prevents a node with 0 rounded CN stake from being selected as proposer or from being included in `ConsolidatedNodes()` with a non-nil `CLStakingInfo`. This is the key uncertainty: if eligibility strictly requires `StakingAmount >= 1 KAIA` (rounded) before a CN can become proposer or an eligible staker, then this exact panic path may not be reachable for the *proposer* case, though the general unguarded-division pattern in `Split()` remains a latent defect that should be hardened regardless.

### Recommendation
In `consolidatedNode.Split()` (kaiax/staking/staking_info.go), guard against `totalAmount.Sign() == 0` before dividing — e.g., return `(amount, big.NewInt(0))` (attribute entirely to the CN) or `(big.NewInt(0), amount)` when `totalAmount` is zero, consistent with the existing `CLStakingInfo == nil` fallback. This removes the panic regardless of whether the precondition is otherwise guaranteed by staking eligibility logic elsewhere.

### Proof of Concept
1. Register a node in the AddressBook as a CN with staking-only bonded amount `< 1 KAIA` (e.g. 0.5 KAIA), sufficient to pass whatever `IsRewardEligible` check exists at deployment (this step could not be fully confirmed against current eligibility code within the available investigation).
2. Register the same `CLNodeId` in the CLRegistry with a CL pool holding `< 1 KAIA` staked (e.g. 0.5 KAIA), producing a `CLStakingInfo` entry with `CLStakingAmount == 0` after rounding.
3. Have this node become the block proposer (or an eligible staker) for a Prague-hardfork block.
4. During `FinalizeState()`, `specWithProposerAndFundsFlex`/`assignStakingRewardsFlex` calls `cn.Split(proposer)` (or equivalent for stakers with CL), where `cn.StakingAmount == 0` and `cn.CLStakingInfo.CLStakingAmount == 0`, causing `totalAmount == 0` and a `big.Int` division-by-zero panic, crashing block finalization on all honest nodes processing that block.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
