Based on my investigation, I was not able to fully confirm the exact hook-execution/environment-sandboxing behavior of `app/src/lib/hooks/get-repo-hooks.ts` and `app/src/lib/hooks/with-hooks-env.ts` (I found these files exist and are named for exactly this purpose, but ran out of iterations before reading their full contents to verify whether they restrict or scope the trampoline environment variables passed to hook subprocesses). That said, the strongest re-entrancy-class analog with concrete file/function support is a credential-helper token replay through the trampoline mechanism.

### Title
Trampoline credential-helper token can be replayed by a repository-controlled subprocess to exfiltrate the signed-in GitHub OAuth token - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop authenticates Git operations via a short-lived `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` pair passed as environment variables to the spawned `git` process [1](#0-0) . That token stays valid (`isValidTrampolineToken`) for the entire duration of the outer git operation and is only revoked when the operation finishes [2](#0-1) . The credential `get` handler resolves credentials purely from the URL/host embedded in the credential request payload it receives over the socket, not from the repository or remote that originated the outer operation [3](#0-2) .

### Finding Description
Any child process spawned during a Desktop-initiated git operation (clone/fetch/pull/push/checkout) inherits the parent process environment, including `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT`, because these are set as plain environment variables on the `git` invocation rather than being scoped to the specific git subprocess that needs them [4](#0-3) . Desktop explicitly supports running repository-local git hooks as part of its operations (`app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/with-hooks-env.ts`), and `_commitIncludedChanges` in `app-store.ts` wires up `onHookProgress`/`onHookFailure` callbacks around `createCommit`, confirming hooks fire during Desktop's own git flows [5](#0-4) .

If such a hook (or any other subprocess spawned transitively by git, e.g. a filter/clean driver) re-invokes the git credential protocol (`git credential fill`) or speaks the trampoline TCP protocol directly with a credential payload whose `url`/`host` is `github.com`, the still-valid inherited token is accepted by `isValidTrampolineToken`, and `getGitHubCredential`/`getCredential` will look up the signed-in account purely by that attacker-chosen endpoint string and hand back `account.token` (the user's GitHub OAuth token) via `credWithAccount` [6](#0-5) [7](#0-6) . Nothing in `getCredential`, `getEndpointKind`, or the trampoline server ties the credential request back to the specific repository/remote/operation for which the outer token was minted — the only check is `isValidTrampolineToken(token)` [8](#0-7) .

### Impact Explanation
A successful replay hands the attacker-controlled process the user's live GitHub token, which can be used for full account API access (impersonation, private repo read/write, further token/credential exfiltration) — a direct violation of the "credential/token exfiltration" impact category, without any prompt to the user because `getIsBackgroundTaskEnvironment` legitimately suppresses UI prompts for background/automated git operations that this replay would appear to be part of.

### Likelihood Explanation
Exploitation requires only that the attacker's repository content cause a subprocess to run during a Desktop git operation and that subprocess talk to the trampoline TCP server on `127.0.0.1` using the inherited token — no additional local/admin access, no leaked credentials, and no unnatural user steps are needed beyond the user cloning/fetching/pulling the malicious repository, which is the exact "attacker controls a cloned/fetched repository" scenario in scope. I could not fully verify from the index whether `get-repo-hooks.ts`/`with-hooks-env.ts` scrub the trampoline environment variables before running hooks, which is the key remaining unknown that would determine whether this path is currently exploitable or already mitigated — this should be verified directly against those two files in a full checkout.

### Recommendation
Bind each `DESKTOP_TRAMPOLINE_TOKEN` to the specific endpoint/remote it was issued for (store the expected host alongside the token in `trampoline-tokens.ts`) and reject `get`/`store`/`erase` requests whose credential URL host doesn't match the operation's expected remote. Additionally, scrub `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` from the environment passed to hook subprocesses in `with-hooks-env.ts` unless the hook explicitly needs them.

### Proof of Concept
1. Attacker publishes a repository containing a `post-checkout` (or similar) hook — or relies on any filter/clean driver invoked during checkout — that runs while a legitimate Desktop clone/checkout of that repo is in progress.
2. The hook process inherits `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` from the parent `git` process spawned by `withTrampolineEnv` [4](#0-3) .
3. The hook runs `git credential fill` (or speaks the raw trampoline protocol) with `url=https://github.com`.
4. `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential` matches the signed-in account by that URL and returns `account.token` in cleartext to the hook process [9](#0-8) .
5. The hook exfiltrates the token to an attacker-controlled server.

const trampolineTokens = new Set<string>()

function requestTrampolineToken() {
  const token = crypto.randomUUID()
  trampolineTokens.add(token)
  return token
}

function revokeTrampolineToken(token: string) {
  trampolineTokens.delete(token)
}

/** Checks if a given trampoline token is valid. */
export function isValidTrampolineToken(token: string) {
  return trampolineTokens.has(token)
}

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
