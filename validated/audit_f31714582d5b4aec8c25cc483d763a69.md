### Title
Conflict-hunk index misalignment in Copilot conflict resolution can silently splice mismatched merged content into a committed file - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The reported PoolTogether bug is a "double counting"/state-mismatch class issue: an action's effect is recorded against the wrong ledger entry because two independent code paths track the same event with different, unsynchronized bookkeeping (open draw vs. committed draw), producing a mismatch between the true balance and what gets minted/emitted. The closest analog in GitHub Desktop is the positional (index-based, not content-based) matching between conflict-marker blocks found in a file on disk and the model-returned `hunks` array in `reassembleResolvedFile`, used by the AI conflict-resolution feature.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file content and replaces each `<<<<<<<` ... `=======` ... `>>>>>>>` block it finds, in the order encountered, with `hunkResolutions[hunkIndex]`, incrementing `hunkIndex` per marker block regardless of whether that block's content actually corresponds to the hunk the model was shown/reasoned about: [1](#0-0) 

The system prompt tells the model hunks are "matching the 'Conflict 1 of N', 'Conflict 2 of N' order from the input" — i.e., correspondence between the model's resolution and the file's actual conflict blocks relies entirely on ordinal position, not on any content fingerprint (e.g. a hash of `oursContent`/`theirsContent` per hunk): [2](#0-1) 

The reassembled content is then written directly to disk and staged without further verification that the replaced regions match what was actually shown to the model: [3](#0-2) 

Because the count/order of conflict-marker blocks is derived purely from scanning the working-tree file for `<<<<<<<`/`=======`/`>>>>>>>` sequences, this is the exact kind of "two independent counters that should stay in lockstep but can drift" invariant broken in the PoolTogether report. If the number or order of conflict blocks the extraction step sees when building context (sent to the LLM) differs even slightly from what `reassembleResolvedFile` sees when splicing the response back in (e.g., due to a race where the working directory changes between context-gathering and reassembly, or due to attacker-crafted file content containing literal `<<<<<<<`/`=======`/`>>>>>>>`-looking text that is valid content in one side of the merge), `hunkIndex` will misalign, and resolution content intended for one hunk gets spliced into an unrelated location in the file.

I was unable to fully verify (due to running out of tool iterations) whether the context-extraction code in `copilot-conflict-context.ts` performs any content-based validation to guarantee the hunk count/order it captures for the prompt exactly matches what `reassembleResolvedFile` will later re-derive from the file on disk at write time. This is the key uncertainty in this finding.

### Impact Explanation
If the attacker can craft repository content (e.g. a fork/PR/branch a victim merges, or upstream content the victim fetches and merges) containing conflict-marker-shaped text as literal file content, or can otherwise cause a mismatch between the context sent to Copilot and the file re-scanned at apply-time, the tool can silently splice the wrong resolved content into the wrong location of a file the user then commits and pushes — satisfying "silent corruption of what the user commits or pushes." Since `_applyCopilotConflictResolutions` writes and `git add`s the result without diffing against the intended per-hunk source, the corruption would not be surfaced to the user before staging.

### Likelihood Explanation
Likelihood is uncertain/low-to-moderate: it depends on the presence of a genuine race between context capture and reassembly, or on git actually producing a merge conflict where the surrounding content coincidentally reproduces marker syntax — this needs live-repro verification I could not complete. The `resolveWithin` check does defend against path traversal but not against content misalignment.

### Recommendation
Have Devin verify whether `copilot-conflict-context.ts` ties each `IHunkResolution` to a stable identifier (e.g. content hash or byte offset of the original conflict block) rather than relying solely on ordinal position, and whether `reassembleResolvedFile` validates that the block it's about to replace matches the `oursContent`/`theirsContent` recorded in the context that was sent to the model before splicing in `resolvedContent`. If no such validation exists, add a content-hash check (or refuse to apply resolutions when the file's conflict-block count/order has changed since context was gathered) before the write path in `_applyCopilotConflictResolutions`.
