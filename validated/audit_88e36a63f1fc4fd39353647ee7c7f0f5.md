### Title
Unchecked u64 multiplication in fee calculation allows attacker-supplied fee rate to wrap around, bypassing `TooLowFee` and redirecting nearly all input funds to a chosen change script - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes` and `fee_with_change = fee_per_vbyte * vbytes_with_change` using unchecked `u64` multiplication. In release builds these wrap on overflow. `fee_per_vbyte`, `payments`, and `change` are all caller-supplied parameters (the analog of the LiFi report's unverified API-supplied values: fees, limits, addresses). A maliciously chosen `fee_per_vbyte` wraps `needed_fee` to a small value that passes the `TooLowFee` and `NotEnoughFunds` checks, while `checked_sub(payment_sat + fee_with_change)` then treats nearly the entire input balance as "change," sending it to whatever `change` script was supplied.

### Finding Description
At `send.rs:206` and `send.rs:227` the fee is `fee_per_vbyte * vbytes` with no `checked_mul` or bound on `fee_per_vbyte` (a `u64`). `vbytes` is on the order of hundreds, so any `fee_per_vbyte` above roughly `u64::MAX / vbytes` (~1e17) causes wraparound in release builds. The wrapped product can be made to land just above `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, so the `TooLowFee` guard at `send.rs:211` passes. The `NotEnoughFunds` check at `send.rs:215` compares `input_sat` against `payment_sat + needed_fee`, both now attacker-shaped values.

Then, at `send.rs:228`, `input_sat.checked_sub(payment_sat + fee_with_change)` succeeds (since `fee_with_change` also wrapped small), and the `value >= DUST` check passes, pushing a change output whose value is approximately `input_sat - payment_sat` — i.e., effectively the full wallet balance — to the supplied `change` `ScriptBuf`. The resulting `SignableTransaction` is signed by `TransactionSignMachine::sign` (`send.rs:355-398`), which commits to `Prevouts::All` and produces valid BIP-340 signatures for this transaction, so it is consensus-valid and broadcastable.

This is exactly the bug class of the external report: values (fee rate, change address) taken from an untrusted upstream (an API, frontend, or RPC fee estimator) are used verbatim to construct a signed transaction without verification, letting the upstream redirect funds.

### Impact Explanation
An unprivileged party who can influence `fee_per_vbyte` or the `change` script passed into `SignableTransaction::new` (e.g., a compromised fee-estimation API or a malicious site building transaction parameters for a signer, the precise scenario in the source report) can cause the threshold group to sign a transaction paying nearly the entire input balance to an attacker-chosen change script while the recorded `needed_fee()` reports only the wrapped, plausible-looking fee. This is concrete signing of an unintended, fund-draining transaction. Severity: Medium/High (requires influence over parameters, not the signing keys themselves).

### Likelihood Explanation
The trigger requires `fee_per_vbyte ≈ 2^64 / vbytes`, far above any honest fee rate — no honest caller hits it accidentally. Exploitation requires an attacker to control the parameters fed to `SignableTransaction::new` (the upstream-API trust assumption the report criticizes). Within the in-scope library, no sanity bound on `fee_per_vbyte` exists anywhere between the parameter and the signed transaction, so any integrator that forwards an external fee estimate is exposed.

### Recommendation
- Use `checked_mul` for `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change`, returning a `TransactionError` on overflow.
- Enforce a sane upper bound on `fee_per_vbyte` (and reject `fee_per_vbyte` values whose implied fee exceeds `input_sat - payment_sat`).
- Recompute the final fee as `input_sat - payment_sat - change_value` and verify it equals the intended `needed_fee` before returning the `SignableTransaction`.

### Proof of Concept
Conceptual (release-mode arithmetic):

```rust
// vbytes for a 1-in/1-out P2TR tx ~ 110-150; pick fee_per_vbyte so the
// product wraps to a small value just above the minimum relay fee.
let vbytes_approx: u64 = 118; // for a single input + one payment
let fee_per_vbyte: u64 = (u64::MAX / vbytes_approx) + (MIN_WRAP_TARGET / vbytes_approx);

// inputs: a real ReceivedOutput owned by the group key, value = 1_000_000 sats
// payments: [(attacker_payment_script, 10_000)]
// change:   attacker_script
let tx = SignableTransaction::new(
    vec![received_output],
    &[(attacker_payment_script, 10_000)],
    Some(attacker_script.clone()),
    None,
    fee_per_vbyte,
).unwrap();

// needed_fee() reports only the wrapped (small) fee.
// tx.output[1] is `attacker_script` with value ≈ 1_000_000 - 10_000 - wrapped_fee.
// multisig() + sign() produce a valid signed TX sending ~99% of funds to attacker_script.
```

Root cause lines: unchecked multiplication at `send.rs:206` and `send.rs:227`, change derivation at `send.rs:228-230`.
