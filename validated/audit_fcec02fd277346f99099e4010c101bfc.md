## Analysis

I could not find a literal analog to `staked` desyncing (that's Substrate/pool-specific), but there is a real, concrete Desktop analog to the underlying bug class: **a code path that changes trusted state is missing the same safety mechanism that all sibling paths already apply**, letting attacker-controlled input reach an unguarded operation.

In Kintsu, `unbond`/`staked` accounting is protected on the "normal" path (`start_unbond` restricted to `vault`), but a permissionless side-path (pool destroying + non-depositor member) bypasses the guard and desyncs `staked`. In Desktop, git-hook execution is treated as untrusted, attacker-influenceable content, so Desktop routes `commit`, `merge`, `pull`, and `push` through a hook-interception sandbox (`interceptHooks`) — but `checkout` (`checkoutBranch`/`checkoutCommit`) does **not** apply that same guard, even though `post-checkout` is exactly the hook Git fires right after a checkout. [1](#0-0) [2](#0-1) 

### Title
Post-checkout Git hooks run unsandboxed because `checkoutBranch`/`checkoutCommit` omit `interceptHooks` used everywhere else - ([File: app/src/lib/git/checkout.ts])

### Summary
Desktop's git-hook interception sandbox (`withHooksEnv`) redirects `core.hooksPath` to a temporary, process-proxy-guarded directory whenever a git command runs with `interceptHooks` set, so any repository-supplied hook script executes through a controlled proxy rather than the user's real shell environment. `commit.ts`, `merge.ts`, `pull.ts`, and `push.ts` all pass `interceptHooks` in their execution options, but `checkout.ts`'s `getCheckoutOpts` builds its `IGitStringExecutionOptions` without setting `interceptHooks`, so `post-checkout` hooks fire with the real, unproxied environment and shell. [2](#0-1) [3](#0-2) 

### Finding Description
`withHooksEnv` only redirects hook execution into the sandbox when `opts?.interceptHooks` is truthy; otherwise it just forwards `opts?.env` unchanged and Git uses whatever hooks are configured for the repository (`core.hooksPath` or `.git/hooks`) with the caller's real environment: [1](#0-0) 

`getRepoHooks` explicitly enumerates `post-checkout` as one of the "known hooks" it looks for and proxies when interception is enabled: [4](#0-3) 

Every other command path that can trigger repository-supplied hooks passes `interceptHooks` to opt into the sandbox (`commit.ts`, `merge.ts`, `pull.ts`, `push.ts` all reference `interceptHooks`), establishing the invariant that "hook-triggering git operations must run through the interception sandbox." `checkoutBranch`/`checkoutCommit`, however, build their options via `getCheckoutOpts`, which only sets `env` (via `envForRemoteOperation`) and `expectedErrors` — no `interceptHooks` field is ever included: [5](#0-4) [6](#0-5) 

This is the same class of defect as the Kintsu report: a guard/update that is enforced on the "expected" call path is silently skipped on an alternate path that is still reachable with attacker-controlled input (here, a repository containing a crafted `post-checkout` hook, reached whenever Desktop checks out a branch or commit in that repository — e.g. after opening/cloning it or after a submodule update establishes such a hook via known Git name-confusion / case-collision issues on the local filesystem).

### Impact Explanation
If a `post-checkout` hook is present for a repository Desktop checks out (whether committed via a Git hook-smuggling technique, via `core.hooksPath` pointed at attacker-controlled content, or produced by a submodule checkout), it runs with the user's real shell/environment instead of the sandboxed process-proxy that Desktop otherwise applies. That means arbitrary command execution with the privileges of the Desktop process/user — i.e., remote code execution triggered purely by checking out a branch/commit in an untrusted repository, which Desktop performs routinely (opening a repo, switching branches, checking out a PR branch). This satisfies the "attacker controls a cloned/fetched repository ... and the result is code execution" impact category.

### Likelihood Explanation
`checkoutBranch` and `checkoutCommit` are invoked on very common, low-friction user actions (switching branches, checking out a PR, restoring a commit) that do not require any unusual steps beyond opening/using a repository the attacker controls or influences (e.g., a malicious fork/PR branch). Because the interception guard is applied consistently elsewhere in the codebase, this is a genuine gap rather than an intentional exemption, and the exact hook name (`post-checkout`) is already recognized by Desktop's own hook enumeration list, showing Desktop is aware this hook exists and is meant to be intercepted.

### Recommendation
Pass `interceptHooks: ['post-checkout']` (or the equivalent filter) into the execution options built by `getCheckoutOpts` in `app/src/lib/git/checkout.ts`, mirroring how `commit.ts`, `merge.ts`, `pull.ts`, and `push.ts` opt into `withHooksEnv`, so `post-checkout` hooks are always routed through the sandboxed process-proxy regardless of which git command path triggers them.

### Proof of Concept
1. Prepare/obtain a repository whose checkout will result in a `post-checkout` hook being present and executable (e.g., via a submodule/`core.hooksPath` configuration reachable through normal repository setup) with the hook script containing an arbitrary command (e.g., writing a file outside the repo or exfiltrating environment variables).
2. Open/clone this repository in GitHub Desktop and check out a branch or commit belonging to it.
3. Observe that `checkoutBranch`/`checkoutCommit` in `app/src/lib/git/checkout.ts` execute `git checkout ...` without `interceptHooks`, so the `post-checkout` hook runs directly against the real environment instead of being routed to the sandbox in `app/src/lib/hooks/with-hooks-env.ts`, and the attacker's command executes with the user's real privileges.

Note: I was not able to fully verify, from the indexed portion of the codebase alone, the exact upstream mechanism by which a `post-checkout` hook file/`core.hooksPath` value would be smuggled in via a normal clone/fetch (hooks are ordinarily local-only content); a Devin session with full repo/history access would be needed to confirm the precise delivery vector (e.g., submodule-based hook installation) end-to-end.

```typescript
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```

```typescript
async function getCheckoutOpts(
  repository: Repository,
  title: string,
  target: string,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  initialDescription?: string
): Promise<IGitStringExecutionOptions> {
  const opts: IGitStringExecutionOptions = {
    env: await envForRemoteOperation(
      getFallbackUrlForProxyResolve(repository, currentRemote)
    ),
    expectedErrors: AuthenticationErrors,
  }

  if (!progressCallback) {
    return opts
  }

  const kind = 'checkout'

  // Initial progress
  progressCallback({
    kind,
    title,
    description: initialDescription ?? title,
    value: 0,
    target,
  })

  return await executionOptionsWithProgress(
    { ...opts, trackLFSProgress: true },
    new CheckoutProgressParser(),
    progress => {
      if (progress.kind === 'progress') {
        const description = progress.details.text
        const value = progress.percent

        progressCallback({
          kind,
          title,
          description,
          value,
          target,
        })
      }
    }
  )
}
```

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
```
