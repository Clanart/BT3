## Analysis

The seed report's core broken invariant is: **a contract accepts ETH via `receive()` but has no controlled path to move that ETH back out**, so value gets trapped. Searching for a Hyperbridge analog, I found something structurally similar but with a materially different — and more severe — consequence in `CallDispatcher.sol`, which is the shared execution proxy used by `IntentGatewayV2` to run solver-supplied `predispatch`/`output` calldata during intent settlement. [1](#0-0) 

`CallDispatcher` has a payable `receive()` (identical pattern to `HibernationDen`) but, unlike the seed report's scenario, it also exposes `dispatch(bytes memory encoded)` as a fully public function with **no `msg.sender` check whatsoever** — not `onlyIntentGateway`, not `onlyOwner`, nothing: [2](#0-1) 

`dispatch()` decodes an arbitrary `Call[]` (each with `to`, `value`, `data`) and executes `to.call{value: call.value}(data)` for each entry. Since `IntentGatewayV2` routes escrowed order funds through this shared contract during `_execute` (output-call fulfillment) and the Tron variant's predispatch flow, transient ETH balances legitimately pass through `CallDispatcher`: [3](#0-2) [4](#0-3) 

Within a single `fillOrder`/`placeOrder` transaction the fund/sweep sequence is atomic, so there's no reentrant window for an outside caller to interleave a `dispatch()` call mid-transaction. However, because `dispatch()` has zero access control, **any ETH balance that ever sits in `CallDispatcher` between transactions — whether from an accidental direct send (same failure mode as the seed report), a partially-swept residue, or any other integration mistake — can be drained by any arbitrary address**, not just recovered by governance/owner. This is strictly worse than the seed finding: instead of "no way to withdraw," it is "anyone can withdraw to anywhere," turning a stuck-funds bug into an active loss-of-funds primitive the moment any value lands in the contract outside the exact orchestrated call sequence.

### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain any ETH/token balance held by the shared intent-execution proxy - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` accepts ETH via an unrestricted `receive()` and exposes a fully public `dispatch(bytes)` function with no caller authorization. This contract is used by `IntentGatewayV2` as a shared execution proxy to run solver/order-supplied calldata during order fulfillment, meaning it transiently or residually holds user escrow value. Because `dispatch()` performs `to.call{value: call.value}(data)` for attacker-chosen `to`/`value`/`data` with no `msg.sender` restriction, any address can redirect the contract's balance to itself.

### Finding Description
`CallDispatcher.dispatch()` is declared `external` with no modifier restricting the caller to `IntentGatewayV2` or any privileged role: [5](#0-4) 

`IntentGatewayV2`/`IntentsBase._execute` funds this contract with the order's output value and then calls `dispatch()` to run the order's attached calldata, later sweeping the resulting balance back: [6](#0-5) 

The Tron variant of `IntentGatewayV2` similarly transfers escrowed native/ERC20 input value into the dispatcher before invoking `predispatch.call`, then sweeps the dispatcher's balance back: [4](#0-3) 

Because `dispatch()` is callable by anyone, and the contract also unconditionally accepts ETH via `receive()`, any value that ends up sitting in `CallDispatcher` outside the exact IntentGatewayV2-orchestrated fund → dispatch → sweep sequence in the *same* transaction (e.g., a stray/misdirected transfer, or any future/alternate integration that funds this shared singleton before invoking `dispatch()` in a separate transaction) can be redirected to an arbitrary address by an unprivileged caller. This differs from the seed report's `HibernationDen` bug (stuck ETH, no drain path at all) — here, the same class of unrestricted `receive()` is compounded by an unrestricted execution primitive that acts as a public backdoor withdrawal function for whoever notices funds sitting in the contract.

### Impact Explanation
Any ETH (or, via `data`, any token approval/allowance-based action) transiently or accidentally held by `CallDispatcher` is not merely locked — it is actively stealable by any unprivileged address, since `dispatch()` lets the caller specify destination and value with no ownership check. This matches the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" impact classes for a shared contract that intermediates real escrowed order value in `IntentGatewayV2`.

### Likelihood Explanation
Exploitation requires the `CallDispatcher` to hold a balance at a point where `dispatch()` can be called independently of the atomic fund/sweep sequence performed by `IntentGatewayV2` in a single transaction (e.g., direct/accidental sends, or any other caller/integration funding the shared dispatcher before invoking it). Given the contract has an unconditional `receive()` inviting exactly that kind of stray ETH, and `dispatch()` is public, this is a real, low-complexity path once any balance exists, requiring no privileged position, malicious relayer, or governance compromise.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized caller(s) that are meant to use it (e.g., an `onlyAuthorizedCaller` modifier keyed to `IntentGatewayV2`/registered gateways), or make the contract per-order/ephemeral so it never persists a spendable balance between calls. Additionally, since the seed bug class applies directly, add an owner/governance-gated ETH (and token) withdrawal function for any balance that should never accumulate in the first place, rather than relying solely on the open `dispatch()` execution path.

### Proof of Concept
1. `CallDispatcher` is deployed once and referenced by `IntentGatewayV2._params.dispatcher` (a shared singleton, not a fresh contract per order): [7](#0-6) .
2. Suppose native ETH ends up in `CallDispatcher` outside of the atomic fund→dispatch→sweep sequence performed by `IntentGatewayV2` — e.g., an accidental direct transfer to the contract (accepted unconditionally by `receive()`), or a partial/failed sweep from a prior order.
3. Any external address calls `CallDispatcher.dispatch(abi.encode(Call[]))` with `Call({to: attacker, value: address(CallDispatcher).balance, data: ""})`.
4. Because `dispatch()` performs no `msg.sender` check, the low-level call executes and the entire balance is sent to `attacker`: [8](#0-7) .

**Note:** I was not able to fully trace every code path where `CallDispatcher` might independently accumulate a persistent balance across transactions (e.g., whether the Solidity `_execute`/predispatch flows always fully atomically sweep to zero in every code path and every deployment variant), so I cannot state with certainty how frequently a non-zero balance would actually be observable in production. This should be verified against the full deployed set of `IntentGatewayV2` variants and any other contracts that may reference the same `CallDispatcher` instance.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}
