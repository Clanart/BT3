## Title
Stale line-index diff selection is applied against a freshly re-fetched diff during partial commit, allowing silent inclusion of unintended/attacker-influenced lines - (File: `app/src/lib/git/apply.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
The Reaper Vault bug is a class of "check performed on rebased/recomputed value instead of the originally validated value" bug: `_withdraw()` computes `value`, then silently clamps it to `token.balanceOf(address(this))`, and the loss guard is evaluated against the clamped value rather than what the user actually requested, so the real invariant is never enforced. GitHub Desktop's partial-commit ("stage selected lines") pipeline has the same structural flaw: the user's line selection (`DiffSelection`) is a bare set of numeric line indices with no binding to diff *content*, and it is captured against one diff object shown in the UI, but applied against a **second, independently re-fetched diff** at commit time, with no re-validation that the indices still refer to the same lines.

### Finding Description
When a user stages a subset of lines for a partial commit, the UI builds a `DiffSelection` of numeric line indices (`divergingLines`) against the `ITextDiff` that was rendered (`app/src/lib/stores/app-store.ts:3444-3497`, `updateChangesWorkingDirectoryDiff`). `DiffSelection.isSelected(lineIndex)` (`app/src/models/diff/diff-selection.ts:122-136`) is purely index-based — it has no knowledge of the text/content of the line it is supposed to represent.

When the commit is actually staged, `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`) does **not** reuse the diff object the selection was derived from. It re-fetches a brand-new diff directly from disk/git: [1](#0-0) 
and then calls `formatPatch(file, diff)` which walks the *new* diff's hunks and asks `file.selection.isSelected(absoluteIndex)` for each line by index: [2](#0-1) 

If the working tree content changes between the moment the user visually reviews/selects lines and the moment `applyPatchToIndex` executes (e.g. because the attacker-controlled repository contains a hook, a build/watch script, a symlinked file, or any process that mutates tracked files after checkout/fetch, or simply because Desktop's own background refresh races with the commit action), the newly fetched diff can have a different hunk/line layout than the one the selection indices were computed against. Because the guard (`file.selection.isSelected(absoluteIndex)`) is evaluated against the *new* diff's line indices rather than being re-validated against the diff that produced the selection, lines the user never looked at (potentially attacker-planted content) can be silently included in — or lines the user did select can be silently excluded from — the generated patch that is applied via `git apply --cached` and ultimately committed.

This mirrors the Vault bug precisely: the guard (`isSelected`) is checked against a rebased/recomputed context (fresh diff indices) instead of the context the value (line selection) was originally validated against (the diff shown to the user), and there is no re-derivation of the selection based on the "real" content actually being applied.

### Impact Explanation
This is a silent corruption of what the user commits: content the user did not review or intend to include can end up staged and committed (and subsequently pushed), including content sourced from a modified/attacker-influenced working tree. Because `git apply --unidiff-zero --whitespace=nowarn` is used, the patch can be applied without complaint even when hunk content doesn't perfectly correspond to what the user visually approved, so there is no error surfaced to the user — the commit simply contains different content than what was shown and selected in the diff viewer.

### Likelihood Explanation
Exploitation requires a window between diff rendering/selection and commit staging in which the working tree content backing that diff changes — a scenario an attacker who controls the cloned/fetched repository (e.g. via a `post-checkout`/`post-merge` hook, a build tool triggered by repository configuration, or a file that legitimately gets rewritten by tooling shipped in the repo) can realistically create, especially for repositories with automated tooling that rewrites files on checkout. It does not require local/physical access, admin rights, or pre-existing malware — only that the user commits from a repository whose content is partially attacker-controlled.

### Recommendation
Do not treat `DiffSelection`'s numeric indices as durable identifiers across independently-fetched diffs. `applyPatchToIndex` should either (a) reuse the exact `ITextDiff` object the selection was derived/validated against instead of re-fetching a new diff at staging time, or (b) re-derive/re-validate the selection against the freshly fetched diff's actual line content (not just index) before generating the patch, failing/re-prompting the user if the underlying diff has changed since selection, analogous to how `updateChangesWorkingDirectoryDiff` already invalidates `selectableLines` for the UI — that same invalidation/consistency check must be enforced immediately before `formatPatch`/`git apply` runs, not only for UI freshness.

### Proof of Concept
1. Attacker publishes/controls a repository (or a branch/PR the victim fetches) containing a script or hook that, shortly after checkout, rewrites a tracked file, inserting attacker content into what was previously a benign line at the same or nearby line index.
2. Victim opens Desktop, views the diff for that file, and selects only specific benign lines to include in a partial commit (`DiffSelection.withLineSelection`, `app/src/models/diff/diff-selection.ts:205-210`).
3. Before the victim clicks "Commit", the attacker-triggered process rewrites the file so the underlying diff/hunk layout shifts.
4. Victim commits. `applyPatchToIndex` calls `getWorkingDirectoryDiff` again (`app/src/lib/git/apply.ts:60`), obtaining the new diff, and `formatPatch` walks its lines checking `file.selection.isSelected(absoluteIndex)` (`app/src/lib/patch-formatter.ts:157`) against the stale index set.
5. Because the index set was computed for the old diff layout, the wrong (potentially attacker-authored) lines are matched as "selected" and staged/committed, without any error or warning to the user.
