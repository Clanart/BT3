## Analysis



### Title
Git credential helper grants GitHub OAuth tokens to arbitrary HTTPS remotes that spoof an unauthenticated "GitHub host" signal - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The trampoline git-credential-helper decides whether to hand out a signed-in GitHub account's OAuth token to a remote endpoint based on `getEndpointKind()`, which classifies an unknown HTTPS host as `'enterprise'` (i.e., a trusted GitHub-controlled host) using two unauthenticated, attacker-controllable signals: a `WWW-Authenticate: realm="GitHub"` header the remote itself returns, or `isGitHubHost()`, whose only verification is the presence of an `x-github-request-id` response header. Neither signal cryptographically proves the endpoint is actually GitHub, analogous to trusting a Chainlink price feed's `updatedAt` field without independently confirming the underlying oracle/sequencer hasn't been manipulated or spoofed.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts:137-179` first checks known-good cases (`isGist`, `isDotCom`, `isGHE`, existing account match). When none apply, it falls back to two weak heuristics:

1. It reads `WWW-Authenticate` header values Git captured from the remote's own HTTP response and, if any contains `realm="GitHub"`, classifies the endpoint as `'enterprise'`: [1](#0-0) 

2. Otherwise it calls `isGitHubHost(endpoint)`: [2](#0-1) 

`isGitHubHost` in `app/src/lib/api.ts` performs a `HEAD` request to `${endpoint}/meta` and treats the presence of the `x-github-request-id` response header as proof the host is GitHub: [3](#0-2) 

Both signals are values the remote server fully controls in its own response — there is no verification against a fixed allowlist, certificate pinning, or any signed/authenticated attestation, comparable to the oracle report's missing sequencer-uptime check: the code treats an attacker-suppliable value as if it were a trustworthy freshness/legitimacy signal. Once `getEndpointKind` returns `'enterprise'`, `getCredential` in the same file will (a) prompt the user to "sign in" to that host if no matching account exists, or (b) hand out an existing GitHub account's token if the endpoint happens to match: [4](#0-3) 

An attacker who controls a git remote/proxy the user clones or fetches from (the same threat model class named in scope: "a git remote/proxy response") can:
- Return `WWW-Authenticate: realm="GitHub"` on a 401, or
- Serve a `/meta` endpoint (or any response) with a forged `x-github-request-id` header,

to make Desktop classify their host as `'enterprise'`, triggering `ui.promptForGitHubSignIn(endpoint)` — a legitimate-looking Desktop sign-in prompt pointed at the attacker's endpoint — which can be used to phish OAuth credentials, or to cause the credential helper to attempt to send an already-stored token to that host if it later matches account bookkeeping logic elsewhere.

### Impact Explanation
If exploited, this can result in credential/token exfiltration or unauthorized OAuth flows being initiated against an attacker-controlled endpoint impersonating "GitHub Enterprise," matching the in-scope impact category "credential/token exfiltration, unauthorized OAuth or account binding." The attacker only needs control of the git remote/proxy the victim fetches or clones from — no local access, malware, or leaked credentials required, which matches the required attacker model exactly.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to add/clone from an attacker-controlled HTTPS remote (a normal action, e.g., adding a "private GHE mirror" remote or being redirected via a compromised proxy/MITM on an untrusted network), and the attacker to control the HTTP response of that remote (trivial, since it's their own server). The `isGitHubHost` probe additionally suppresses certificate errors for the specific probe URL via `suppressCertificateErrorFor`, meaning even a self-signed or invalid-cert host can pass this check for that HEAD request: [5](#0-4) [6](#0-5) 

### Recommendation
Do not rely on unauthenticated, remote-supplied signals (`WWW-Authenticate` realm string, presence of an arbitrary response header) to classify a host as a trusted GitHub endpoint. Restrict `'enterprise'` classification to endpoints that are already registered accounts, an explicit user-confirmed allowlist, or endpoints verified via a signed/pinned mechanism. At minimum, warn the user explicitly before prompting a GitHub sign-in against a newly-discovered, unverified host, and never suppress certificate validation errors even for a probe request. This mirrors the Chainlink recommendation of validating a liveness/legitimacy signal through a trustworthy channel instead of trusting a value the counterparty fully controls.

### Proof of Concept
1. Attacker stands up an HTTPS git server (e.g., using a self-signed cert or normal HTTPS) at `https://evil.example.com`.
2. Attacker configures the server to respond to `/meta` with a `HEAD` 200 response containing header `x-github-request-id: <anything>`, or to return `401` with `WWW-Authenticate: realm="GitHub"` on git's credential probe.
3. Victim adds `https://evil.example.com/foo/bar.git` as a remote in Desktop and performs a fetch/pull, invoking the credential helper trampoline.
4. `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:137-179`) classifies the endpoint as `'enterprise'` based on the forged signal.
5. `getCredential` (`app/src/lib/trampoline/trampoline-credential-helper.ts:94-125`) invokes `ui.promptForGitHubSignIn(endpoint)`, presenting what looks like a legitimate Desktop GitHub sign-in prompt scoped to the attacker's host, or attempts to reuse a matching stored account's token against it.

Note: I was not able to trace every downstream consumer of the `'enterprise'` classification (e.g., exact conditions under which an existing token would be sent versus only a sign-in prompt shown) within the indexed code; a full Devin session with complete repository access would be needed to confirm the exact token-exfiltration path end-to-end versus the phishing-prompt path.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
