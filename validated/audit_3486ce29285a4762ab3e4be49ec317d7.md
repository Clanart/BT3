### Title
Missing `request.from` (module-identity) binding on `HostManager.onAccept` allows unauthenticated administrative message forgery - (File: `evm/src/core/HostManager.sol`)

### Summary
The external report's core broken invariant is: a contract exposes privileged administrative state transitions (change trusted admin, change adapter) that are gated only on the *transport* being "cross-chain governance," while the intermediary that carries these messages never lets the legitimate caller reach them, and — more importantly for this codebase — the receiving contract's authorization check binds only to the **source chain**, not to the **specific module/account on that chain** that is supposed to be the sole legitimate sender of these privileged instructions. That second half of the pattern reproduces almost verbatim in Hyperbridge's `HostManager` contract.

### Finding Description
`HostManager.onAccept` is the sole entry point through which the `EvmHost`'s privileged `IHostManager` functions (`withdraw` and `updateHostParams`) can be invoked: [1](#0-0) 

The only authentication performed is:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
```
This checks that the ISMP `PostRequest.source` equals the configured Hyperbridge state-machine identifier — i.e., that the message originated from *the Hyperbridge chain*. It never checks `request.from`, the field that identifies *which module/pallet on that chain* dispatched the message. Contrast this with `HyperFungibleToken.onAccept`, which — for the exact same class of decision (should this incoming message be trusted to mint tokens/withdraw funds) — checks both source *and* `request.from` against a registered per-chain sender: [2](#0-1) 

`HostManager` skips the `request.from` check entirely, so any module capable of dispatching a raw `PostRequest` from the Hyperbridge chain to the `HostManager` address is treated as fully authorized to invoke `withdraw` (drains the host's fee-token/native balance to an attacker-chosen `beneficiary`) or `updateHostParams` (which can rewrite `admin`, `hostManager`, `handler`, `consensusClient`, and `feeToken` — i.e., seize full control of the host).

The root cause on the dispatch side is that the low-level `IsmpDispatcher` implementation used by every pallet in the runtime passes the caller-supplied `from` field straight into the outgoing `PostRequest` with no binding to the calling pallet's own module identity: [3](#0-2) 

`source` is always correctly set to `self.host_state_machine()` (line 130), so the destination-side "must come from Hyperbridge" check will always pass for any message dispatched from this chain — but `from` (line 133) is taken verbatim from the caller's `DispatchRequest::Post` struct. Nothing in this shared, generic dispatcher function enforces that `from` matches the module id of the pallet that is actually calling it. Governance-side confirmation of this exact gap for the sibling `BandwidthManager` app is documented explicitly: "The `to` field is the manager's address — no module-id lookup," meaning authorization there similarly rests entirely on `request.source`, not `request.from`. [4](#0-3) 

### Impact Explanation
If any pallet in the Hyperbridge runtime that is reachable by a normal signed account exposes (directly or transitively) a call path into `IsmpDispatcher::dispatch_request` where the `to` and `body` (and effectively `from`) of the outgoing `PostRequest` are attacker-influenced, an attacker can craft a message whose `source` is legitimately `Hyperbridge` (satisfying `HostManager`'s only check) and whose `body` encodes `OnAcceptActions.Withdraw` with an arbitrary beneficiary/amount, or `OnAcceptActions.SetHostParam` with attacker-chosen `HostParams` (including a new `admin`/`hostManager`/`handler`/`consensusClient`). This would result in direct theft of the host's accrued protocol/relayer revenue and/or complete unauthorized takeover of the EVM host's trust parameters — squarely within "stealing or loss of funds" and "unauthorized transaction or execution" per the bounty scope.

### Likelihood Explanation
The vulnerability's precondition — a signed-extrinsic path that lets an ordinary account control the `to`/`body`/`from` of a `PostRequest` dispatched through `Pallet::<T>::dispatch_request` — was not fully confirmed within the available investigation budget. I inspected `dispatcher.rs` and confirmed the missing `from`-binding at the dispatch layer and the missing `request.from` check at `HostManager.onAccept`, but I was not able to trace, with certainty, a concrete unprivileged pallet extrinsic (e.g., in `intents-coprocessor`, `hyper-fungible-token`, or `demo`) that exposes fully attacker-controlled `to`/`body`/`from` parameters for a `DispatchPost` targeting an arbitrary EVM address. This is the key remaining uncertainty: if no such permissionless entrypoint exists in the runtime (i.e., all callers of this dispatcher trait hardcode their own `from` and constrain `to`/`body` to their own protocol semantics), then this specific path is not directly exploitable by an unprivileged actor today, even though the authorization gap in `HostManager.onAccept` itself is real and structurally unsound (defense-in-depth failure — it relies entirely on every possible caller in the runtime self-restricting `from`, rather than the receiving contract enforcing it).

### Recommendation
Add a `request.from` check in `HostManager.onAccept` (and any structurally identical app, e.g. `BandwidthManager`) that requires `from` to equal a specifically registered/whitelisted governance module id (e.g., the `pallet-ismp-host-executive` module id), mirroring the pattern already used in `HyperFungibleToken.onAccept`. Do not rely solely on `request.source` for privileged administrative actions. Additionally, audit `IsmpDispatcher::dispatch_request` callers to ensure `from` is always derived from the calling pallet's own registered module id rather than accepted as free-form caller input.

### Proof of Concept
Not executable — this report identifies a structural authorization gap (missing `request.from` binding in `HostManager.onAccept`, and a `from`-field pass-through in `dispatcher.rs`) confirmed by direct code reading, but a full end-to-end exploit requires identifying a concrete permissionless Hyperbridge-chain extrinsic that lets a normal account fully control the dispatched `PostRequest`'s `to`/`body`/`from`, which I was unable to conclusively verify or refute given the remaining iteration budget.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
