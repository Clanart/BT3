### Title
Immature coinbase outputs are reported as spendable wallet inputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`Scanner::scan_block` scans every transaction in `block.txdata`, including the coinbase transaction at index `0`, and returns matching outputs as `ReceivedOutput` values without retaining maturity state. `ReceivedOutput` is defined and consumed as a spendable output, while `SignableTransaction::new` converts each supplied `ReceivedOutput` directly into a transaction input without checking whether its prevout is an immature coinbase output. An unprivileged miner can therefore send a coinbase output to a watched Serai P2TR script and cause the wallet API to report funds as spendable before Bitcoin permits them to be spent. ### Finding Description

`scan_transaction` treats any transaction output whose `script_pubkey` exists in `scripts` as a `ReceivedOutput`, storing only its offset, `TxOut`, and outpoint. [2](#0-1) 

`scan_block` then calls `scan_transaction` over the complete `block.txdata` slice rather than excluding the coinbase transaction. Its documentation explicitly notes that coinbase outputs are bound by maturity and require post-processing if returned outputs must be immediately spendable, but the returned `ReceivedOutput` contains no flag that would let downstream transaction construction identify that condition. [3](#0-2) [1](#0-0) 

When such an output is passed to `SignableTransaction::new`, its outpoint is inserted directly into `TxIn` and its value is counted toward `input_sat`; no coinbase-maturity check or transaction-type check is performed. [4](#0-3) [5](#0-4) 

This is analogous to the external issue’s mutable accounting state causing an invalid distribution assumption: the scanner incorporates a newly arriving balance that is not actually usable at the time it is counted. Here, the newly arriving output is not merely late, but consensus-immature.

### Impact Explanation

A miner can place a payment to the watched P2TR script in a coinbase transaction. After `scan_block` returns it, callers treating `ReceivedOutput` as spendable may select it for payments or aggregation and ask the threshold key holders to sign a transaction spending it. The resulting transaction is invalid until the coinbase reaches maturity, so Bitcoin rejects publication even though the wallet reported the funds as available. [6](#0-5) [7](#0-6) 

The primary impact is funds being reported received and available when they are not currently spendable. Depending on caller retry behavior, repeatedly selecting the immature output can stall payments or aggregation until maturity despite other spendable outputs being available.

### Likelihood Explanation

Any miner capable of producing a block can trigger this path with public transaction data by directing one coinbase output to a watched script. No validator key, privileged Serai API, malformed encoding, or invalid transaction is required: the coinbase transaction is consensus-valid, and `scan_block` itself supplies the unqualified `ReceivedOutput`. The issue requires a caller to rely on `scan_block`’s documented “spendable output” result without implementing the separate maturity filter described in the comment. [1](#0-0) [3](#0-2) 

### Recommendation

Do not return coinbase outputs from `scan_block` as ordinary `ReceivedOutput` values. Either:

- iterate only over `block.txdata[1 ..]`; or
- return a structured result that distinguishes immature coinbase outputs from immediately spendable outputs and prevents `SignableTransaction::new` from accepting them.

A defense-in-depth check in `SignableTransaction::new` should also reject coinbase prevouts or require maturity metadata, since an arbitrary deserialized `ReceivedOutput` can otherwise reintroduce the same invalid-input condition. [8](#0-7) [4](#0-3) 

### Proof of Concept

Conceptually:

1. Create a `Scanner` for an even group key.
2. Produce a valid block whose `txdata[0]` coinbase contains an output paying `p2tr_script_buf(key)`.
3. Call `scanner.scan_block(&block)`.
4. Observe that the coinbase output is returned as a normal `ReceivedOutput`.
5. Pass it to `SignableTransaction::new`.
6. Observe that construction succeeds and creates an input referencing the coinbase outpoint, even though Bitcoin consensus forbids spending it until maturity.

The decisive code path is:

```rust
// networks/bitcoin/src/wallet/mod.rs
for tx in &block.txdata {
  res.extend(self.scan_transaction(tx));
}
```

followed by:

```rust
// networks/bitcoin/src/wallet/send.rs
previous_output: input.outpoint,
```

with no maturity or coinbase classification preserved between those operations. [9](#0-8) [7](#0-6)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
