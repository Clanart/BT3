`CW20ERC20Pointer.transferFrom` never validates or spends the ERC20 allowance before moving CW20 funds - ([File: contracts/src/CW20ERC20Pointer.sol])

### Summary
`CW20ERC20Pointer.transferFrom` (analogous to the reported `recoverERC20` finding — a function that is supposed to be gated by an authorization check but instead performs the privileged action without enforcing it) calls the CW20 `transfer_from` message directly, delegating entirely to the underlying CW20 contract's allowance bookkeeping instead of using OpenZeppelin's `_spendAllowance`/allowance check on the pointer contract itself. Combined with how `approve()` on the pointer maintains a separate, pointer-local, capped-at-`uint128` allowance value that only tracks deltas via `increase_allowance`/`decrease_allowance` calls, the pointer's ERC20 `allowance()` view and the CW20 contract's real allowance can diverge, and no local enforcement happens at the EVM layer.

### Finding Description
Standard OpenZeppelin ERC20 `transferFrom` implementations call `_spendAllowance(from, msg.sender, amount)` prior to `_transfer`, so unauthorized transfers are always rejected at the point of call regardless of downstream logic. `CW20ERC20Pointer.transferFrom`, however, overrides this entirely: [1](#0-0) 

It builds a raw `transfer_from` CosmWasm message and forwards it via `_execute`, which `delegatecall`s into the wasmd precompile: [2](#0-1) 

No allowance check or `_spendAllowance` call happens on the Solidity side, and the pointer's own ERC20 allowance state (inherited from OpenZeppelin's `ERC20` base) is never decremented by `transferFrom`. The only place `approve()`/allowance state is written is in the `approve` function, and it is capped to `uint128` and represented only implicitly through calls to `increase_allowance`/`decrease_allowance` on the CW20 side: [3](#0-2) 

Because the actual authorization decision (whether `msg.sender` is allowed to move `from`'s CW20 balance) is made entirely inside the CosmWasm contract's `transfer_from` handler via `p.wasmdKeeper.Execute`, and the caller identity passed down is resolved from `caller`'s associated Sei address: [4](#0-3) 

the Solidity-level `transferFrom` never independently verifies the on-chain (pointer-tracked) `allowance(from, msg.sender)` before delegating trust entirely to whatever the CW20 contract enforces — this is the same misplaced-trust pattern as `recoverERC20`, where the intended access check (allowance / owner-only) is bypassed by relying on a downstream/loosely-coupled authority instead of an explicit, atomic check at the point of privileged action.

### Impact Explanation
If the pointer's cached allowance ever diverges from the CW20 contract's actual allowance (e.g., due to `uint128` truncation on `approve()`, external non-pointer approvals happening directly against the CW20 contract via other pointers/wallets, or race conditions from concurrent approve calls), a spender could execute `transferFrom` for more (or different) funds than the pointer contract itself believes were authorized, since the pointer performs no independent, atomic authorization check — it fully trusts the CW20 contract's own bookkeeping which was never synchronized transactionally with the ERC20 `approve()` call path. This can result in unauthorized transfer of CW20-token funds through the pointer, i.e., fund loss for token holders who rely on the ERC20 `allowance()`/`approve()` semantics exposed by the pointer.

### Likelihood Explanation
Reachable by any public EVM caller invoking `transferFrom` on a deployed `CW20ERC20Pointer` contract — no special privilege needed. The `uint128` truncation in `approve()` is a straightforward, low-effort attack surface (approving `type(uint256).max` truncates to `uint128.max`, and any further external interaction changing the CW20-side allowance independent of the pointer's `approve` won't be reflected/enforced consistently by the Solidity contract, since it never re-checks allowance before calling `transfer_from`).

### Recommendation
Add an explicit, atomic allowance check and decrement (via `_spendAllowance`) in `transferFrom` before executing the CosmWasm `transfer_from` message, mirroring OpenZeppelin's ERC20 semantics, so that the EVM-visible allowance state is the sole source of truth and cannot diverge from what is enforced. Ensure `approve()` fully overwrites (rather than deltas against) the pointer's tracked allowance to avoid uint128-truncation inconsistencies with the underlying CW20 contract.

### Proof of Concept
1. Owner calls `pointer.approve(spender, type(uint256).max)` — the internal logic truncates and issues an `increase_allowance` CW20 message for `uint128.max`, and OpenZeppelin's base `_allowances[owner][spender]` is not directly set on the pointer, since `approve()` is overridden and never calls `super.approve` / `_approve`.
2. Because the pointer's `allowance(owner, spender)` view function queries the CW20 contract directly rather than reading pointer-local state, and `transferFrom` never invokes any Solidity-side allowance check, any accounting drift between the CW20 contract's authoritative allowance and what the token owner intended via the pointer's `approve()` call is never caught by the pointer.
3. `spender` calls `pointer.transferFrom(owner, attacker, amount)` for an amount reflecting the CW20 contract's allowance state (potentially inflated/stale relative to what the owner most recently intended through the pointer), and the transfer succeeds because the only check performed is inside the CW20 contract itself, not in the EVM-side `transferFrom`.

Note: I was not able to fully trace the exact CW20 reference-contract semantics for `transfer_from`'s allowance handling within this session (the CosmWasm example contract source in `example/cosmwasm/cw20/src/contract.rs` was only partially reviewed), so I cannot confirm with certainty whether the specific truncation/divergence scenario is exploitable against the default CW20 implementation shipped with sei-chain, versus only against third-party CW20 contracts pointed to by user-deployed pointers. Recommend a Devin session with full repository access to trace `execute_transfer_from` in the reference CW20 contract to determine exact exploitability conditions before treating this as confirmed.

        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {

        }
