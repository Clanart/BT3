## Analysis

The external report's core broken invariant: an **unprivileged caller can invoke a legitimate, permissionless function with a small amount of value that mutates a shared accounting structure used by other users, causing them aloss** (diluting the reward-per-second for other beneficiaries of the same pool).

The closest local analog in this Hyperbridge repo is not the reward pallets (`pallet-consensus-incentives` computes rewards directly from block-height deltas and transfers immediately — no shared duration state to dilute) nor `StreamingYieldVault.addYield` (correctly restricted `onlyOwner`). The analog exists in **`pallet-bandwidth`**'s prepaid subscription ledger, reachable via the fully permissionless `BandwidthManager.purchase()` entrypoint on any registered EVM source chain.

### Why this qualifies
`purchase()` lets **any caller** target an arbitrary `(app, chain)` pair — the credit chain/app is attacker-supplied and is *not* validated to be the caller's own app, by design, to support "sponsorship": [1](#0-0) 

That credit lands in a FIFO `BoundedVec` capped at `MAX_SUBSCRIPTIONS` (1024). When the cap is hit, `push_subscription` unconditionally evicts index `0` — the oldest entry — regardless of how many bytes it still has remaining or how much was paid for it: [2](#0-1) 

Because `purchase()` is open to anyone and the target `(app_chain, app)` is attacker-chosen, an attacker can drive 1,024 minimal, cheap Tier-1 purchases against a victim app's bucket. Each cheap purchase appends a new row (subscriptions never stack/renew, they always queue — confirmed by the pallet's own doc comment), pushing the queue length to the cap and evicting the victim's legitimately-paid, unexpired, high-value subscriptions one by one: [3](#0-2) 

This is the same broken-invariant shape as the external report: a **permissionless, cheap call into a function that legitimately exists for a different purpose (adding rewards / adding bandwidth) is repurposed to damage a shared resource pool that other honest participants depend on** — in the TRST-M-4 case diluting reward-rate; here, evicting a victim's already-purchased and unconsumed bandwidth allowance, i.e. an unrecoverable loss of prepaid funds for the victim app, auditable only after the fact via `SubscriptionEvicted`.

### Title
Unprivileged FIFO-eviction griefing of prepaid bandwidth via `BandwidthManager.purchase()` sponsorship — (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `Allowance` ledger is a per-`(app_chain, app)` FIFO list capped at 1024 entries (`MAX_SUBSCRIPTIONS`). `push_subscription` evicts the oldest entry unconditionally whenever the cap is reached, with no regard for `remaining_bytes` or `expires_at` of the evicted row. Because the on-chain credit path (`purchase()` on `BandwidthManager.sol`) lets any caller specify an arbitrary target `app` and `chain` ("sponsorship" is by design), and each purchase always appends a new row rather than topping up an existing one, an attacker can flood a victim's bucket with cheap, minimal Tier-1 purchases to force-evict the victim's legitimately purchased, unexpired, high-value subscriptions.

### Finding Description
- `BandwidthManager.purchase(app, tier, months, chain)` is a public function; `app`/`chain` are caller-supplied and intentionally not restricted to the caller's own identity (sponsorship model): [1](#0-0) 
- Every accepted purchase always **appends** a new `Subscription` row via `push_subscription`, never stacking/renewing existing entries: [4](#0-3) 
- When the FIFO list is at the 1024 cap, the *oldest* entry is evicted unconditionally — there is no check on how many bytes remain unused or how far from expiry the evicted subscription is: [5](#0-4) 
- The pallet-side `on_accept` handler that credits purchases only checks `request.from` matches the registered `BandwidthManager` for the source chain — it performs no check that the purchaser is authorized to credit the specific `app` being targeted: [6](#0-5) 

An attacker with a modest amount of the fee token can:
1. Identify a victim app with a large, long-duration Tier-4 subscription (e.g., 8 MB / large window) that still has significant `remaining_bytes` and a distant `expires_at`.
2. Call `purchase()` 1,024 times with the cheapest configured tier, targeting the victim's exact `(chain, app)` pair.
3. Each call appends a new row; once the queue reaches 1024, each subsequent purchase evicts the oldest entry — eventually evicting the victim's high-value subscription while it still had unconsumed bytes and time remaining.

The victim's paid-for, unexpired bandwidth allowance is permanently destroyed (only auditable after the fact via `SubscriptionEvicted`), and their app subsequently fails to dispatch messages through the `BandwidthGate` once the real allowance is gone, even though they never consented to the drain and the ledger shows they still had a live balance moments before.

### Impact Explanation
This is a fund-loss/logic-attack primitive against a **production bridge economic subsystem** (`pallet-bandwidth` gates all non-purchase ISMP dispatches from managed source chains). A victim's fully-paid subscription — real money paid to a `BandwidthManager` contract and credited on Hyperbridge — can be destroyed by an unrelated, unprivileged third party without needing any relayer/prover/admin compromise, malicious peer behavior, or front-running: it is a direct consequence of the permissionless targeting model combined with an unconditional oldest-first eviction policy that ignores value/urgency of the evicted entry. The victim loses the prepaid bandwidth they are entitled to and their app becomes unable to dispatch messages once genuinely drained, which is exactly the kind of "loss of funds" / "logic attack" impact in scope.

### Likelihood Explanation
High feasibility for a determined attacker: `purchase()` requires no special permission, targets are fully attacker-chosen, and the eviction path is deterministic and cheap relative to the value of a large Tier-3/Tier-4 subscription being destroyed (cost asymmetry favors the attacker when the victim's subscription value exceeds 1,024× the cheapest tier price). No relayer collusion, no proof forgery, and no governance/admin action is required — only the ordinary, documented purchase flow used as intended by the protocol, repeated against someone else's bucket.

### Recommendation
- Restrict `push_subscription`'s eviction so it cannot silently destroy a subscription with nonzero `remaining_bytes` unless the queue-owner (the app itself, via some authorization) consents, or
- Require that only the `app`'s own authorized manager/relationship (not an arbitrary sponsor) can credit — or evict from — its bucket, or
- Track subscriptions per-purchaser/per-tier separately so that a flood of tiny purchases cannot evict a large one, or
- Emit `SubscriptionEvicted` pre-emptively as a governance-visible alarm and add a minimum bytes/expiry-weighted eviction policy (evict smallest-value-first, not strictly oldest-first) so cheap spam cannot displace high-value entries.

### Proof of Concept
1. Governance configures Tier1 (cheap, e.g. 100 KB / 30 days) and Tier4 (8 MB / 30 days) per `docs/content/developers/evm/bandwidth/configuration.mdx`.
2. Victim buys Tier4 for `app = VictimApp` on `chain = EVM-8453`, crediting a `Subscription { remaining_bytes: 8_000_000, expires_at: now+30d }` as row `#0` (or wherever it lands) in `Allowance[EVM-8453][VictimApp]`.
3. Attacker calls `BandwidthManager.purchase(app=VictimApp, tier=Tier1, months=1, chain="EVM-8453")` 1,024 times in rapid succession (any source chain with a registered manager works; attacker does not need to be near the victim).
4. Once the FIFO list length hits `MAX_SUBSCRIPTIONS` (1024) and one more purchase lands, `push_subscription` (`modules/pallets/bandwidth/src/lib.rs:416-425`) evicts index 0 — eventually reaching and evicting the victim's Tier4 row while `remaining_bytes` is still large and `expires_at` is still far in the future.
5. `Event::SubscriptionEvicted { app_chain, app, tier: Tier4, lost_bytes: <large> }` fires, confirming the loss; `Pallet::remaining(EVM-8453, VictimApp)` now reflects only the attacker's residual cheap subscriptions, and the victim's app begins failing at the `BandwidthGate` on its next dispatch despite having paid for a much larger, still-valid allowance.

```rust
//! # pallet-bandwidth
//!
//! Prepaid `(chain, app)` byte balances credited by tier purchases
//! from `BandwidthManager.sol`. Each purchase carries its own
//! `app_chain`, so any deployment can sponsor any app on any chain.
//!
//! Each `(chain, app)` row holds a FIFO list of [`Subscription`]s
//! (`BoundedVec`, capped at 1024). Every purchase appends a new
//! subscription with a fixed `expires_at`; expiry never extends and
//! same-tier repurchases don't stack — they queue. The gate drains
//! the oldest live subscription first; once empty it moves to the
//! next. Subscriptions that aren't reached before their expiry are
//! swept silently — what you paid for is yours only until it expires.
//! Pushes onto a full list evict the oldest entry and emit
//! [`Event::SubscriptionEvicted`].
```

```rust
		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
```
