## Title
Consensus-Incentives reward misattribution — entire batch's state-machine-advance rewards paid only to `messages[0]`'s signer, regardless of which message produced each update - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` computes the highest `latest_height` per `StateMachineId` across **every** `StateMachineUpdated` event in the whole processed batch, but only recovers a single relayer's signature — from `messages[0]` — to attribute payment for **all** of those updates. An unprivileged actor can submit a batch containing a trivial, self-signed `ConsensusMessage` as the first entry alongside one or more independently-valid (and independently obtainable) consensus proofs for other state machines, and collect the treasury reward for every state-machine advance in the batch even though those other proofs were not "theirs" in the sense the reward design intends.

### Finding Description
`on_executed` only inspects the first message in the batch to recover a relayer account: [1](#0-0) 

It then iterates over *all* events in the batch, collapsing multiple `StateMachineUpdated` events per `state_machine_id` down to the single highest height, and pays that one relayer for every one of them: [2](#0-1) 

The reward calculation itself (`calculate_reward`) is per-state-machine and correctly watermarked (`LastRewardedHeight`) to avoid double-paying the *same* span twice: [3](#0-2) 

But the watermark only prevents re-paying the same height span again; it does nothing to ensure the party being paid is the one who actually produced the advance. The `signer` field on a `ConsensusMessage` is a self-declared attribution signature over `keccak256(consensus_proof)` — it is *not* cryptographically bound to the `state_machine_id`/height it advances, and it is not checked against which specific message in the batch produced which `StateMachineUpdated` event: [4](#0-3) 

Consensus proofs are explicitly public, unauthenticated data by design — "these proofs can be generated by anyone, as they are freely provided by its connected chains": [5](#0-4) 

Consequently, anyone can assemble a `Vec<Message>` for `pallet_ismp::handle_unsigned` where:
- `messages[0]` is a cheap, throwaway `Message::Consensus` self-signed with the attacker's own sr25519 key (any bytes, any state machine the attacker controls a valid client transition for, even a 1-block advance), and
- `messages[1..N]` are separately-valid, publicly reconstructible consensus proofs that advance one or more *other* state machines by large spans (each independently verified for correctness by pallet-ismp's own consensus-client logic, unrelated to the fee handler).

Because `on_executed` only ever looks at `messages[0]`'s embedded signature, the attacker's account is credited with `(LatestHeight - LastRewardedHeight) * CostPerBlock` for *every* state machine whose height advanced anywhere in that batch, not just the one corresponding to their own message.

### Impact Explanation
This is a direct, wrong-beneficiary fund transfer out of the protocol treasury: `T::Currency::transfer(&TreasuryAccount, &relayer_account, reward, ...)` moves treasury `$BRIDGE` (and mints an equal amount of `ReputationAsset`) to an account that did not do the proportional work the reward is meant to compensate, simply because it happened to occupy `messages[0]` in a batch it assembled. This directly violates the stated invariant that "relayer rewards... must move exactly once and only to the rightful beneficiary and amount." No admin, prover, or relayer compromise is required — any account holding a small amount of funds to submit an unsigned extrinsic (or even none, since `handle_unsigned` requires no fee) can perform this.

### Likelihood Explanation
The precondition — multiple `StateMachineUpdated` events landing in a single processed batch — is a normal, expected occurrence in day-to-day operation (multiple pending consensus updates for different chains are commonly batched for efficiency), and the "signer" attribution field is explicitly documented as self-declared rather than tied to the actual proof content or its position in the batch. No malicious peer, prover, relayer, or governance actor is needed; the attacker only needs to (a) hold a keypair and (b) observe publicly available consensus proof data for chains other than their own, which is exactly how the protocol says relaying is supposed to work.

### Recommendation
Attribute each state-machine's reward to the signer of the specific `ConsensusMessage` that produced its `StateMachineUpdated` event, rather than defaulting to `messages[0]`. Concretely, iterate `messages` and `events` together (or tag each `StateMachineUpdated` event with an index/reference back to the `Message` that generated it) and recover/verify a signer per message, only crediting the state machines that message's proof actually advanced.

### Proof of Concept
1. Attacker holds sr25519 keypair `K`.
2. Attacker crafts `message_0 = Message::Consensus(ConsensusMessage { consensus_proof: <trivial 1-byte valid proof for chain A>, signer: Signature::Sr25519 { public_key: K.public(), signature: K.sign(keccak256(consensus_proof)) } })`.
3. Attacker independently fetches (public, unauthenticated) valid consensus proof data that advances chain B by N blocks (obtainable exactly as documented — "freely provided by its connected chains") and builds `message_1 = Message::Consensus(...)` for chain B, need not even embed a matching signer since it's never inspected.
4. Attacker submits `pallet_ismp::handle_unsigned(RuntimeOrigin::none(), vec![message_0, message_1])`.
5. `on_executed` extracts the relayer from `message_0` only (`messages.get(0)`), then loops over `StateMachineUpdated` events for **both** chain A and chain B, and pays `K`'s account `(latest_height_A - baseline_A)*cost_A + (latest_height_B - baseline_B)*cost_B` — the reward legitimately earned for chain B's advance (which could be arbitrarily large) is misdirected entirely to the attacker instead of being split/attributed to the actual proof source.

This is directly demonstrated by the existing test harness pattern that constructs `(Message, AccountId32)` pairs and feeds them through `FeeHandler::on_executed`: [6](#0-5) 
— extending that test with a second, independently-sourced `StateMachineUpdated` event for a different `state_machine_id` in the same `on_executed` call, while keeping `messages` at length 1 (or with `messages[1]` signed by a different key), reproduces the misattributed payout.

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

#[test]
fn reward_covers_only_unpaid_heights_after_rollback() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		const BLOCK_COST: u128 = 100;
		let host = Ismp::default();
		let state_machine_id = setup_state_machine();
		let treasury_account: AccountId32 = PalletId(*b"treasury").into_account_truncating();

		pallet_consensus_incentives::Pallet::<Test>::update_cost_per_block(
			RuntimeOrigin::root(),
			state_machine_id,
			BLOCK_COST,
		)
		.unwrap();

		let (consensus_message, relayer_account) = setup_host_and_message(&host);
		let message = MessageWithWeight { message: consensus_message, weight: Weight::zero() };
		let updated = |height: u64| {
			vec![IsmpEvent::StateMachineUpdated(StateMachineUpdated {
				state_machine_id,
				latest_height: height,
			})]
		};

		// The chain has already advanced to 1025 and every block up to it has been rewarded once.
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1024 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1024,
		})
		.unwrap();
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1025 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1025,
		})
		.unwrap();

		let treasury_before_first = Balances::balance(&treasury_account);
		<pallet_consensus_incentives::Pallet<Test> as FeeHandler>::on_executed(
			vec![message.clone()],
			updated(1025),
		)
		.unwrap();

		assert_eq!(Balances::balance(&treasury_account), treasury_before_first - BLOCK_COST);
		assert_eq!(
			pallet_consensus_incentives::LastRewardedHeight::<Test>::get(state_machine_id),
			Some(1025)
		);

		// The previous-height pointer references an older height whose commitment is no longer
		// retained in the bounded map.
		pallet_ismp::PreviousStateMachineHeight::<Test>::insert(state_machine_id, 1);

		// Deleting the latest commitment rolls the latest height back to that previous pointer.
		host.delete_state_commitment(StateMachineHeight { id: state_machine_id, height: 1025 })
			.unwrap();
		assert_eq!(host.latest_commitment_height(state_machine_id).unwrap(), 1);

		// The next honest consensus update advances to 1030, carrying the stale pointer forward as
		// the new previous height.
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1030 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1030,
		})
		.unwrap();
		assert_eq!(host.previous_commitment_height(state_machine_id), Some(1));

		let treasury_before_second = Balances::balance(&treasury_account);
		<pallet_consensus_incentives::Pallet<Test> as FeeHandler>::on_executed(
			vec![message],
			updated(1030),
		)
		.unwrap();

		// The real advance is 1025 -> 1030, so only the 5 new blocks are paid rather than the full
		// span back to the previous pointer.
		assert_eq!(Balances::balance(&treasury_account), treasury_before_second - 5 * BLOCK_COST);
		assert_eq!(
			pallet_consensus_incentives::LastRewardedHeight::<Test>::get(state_machine_id),
			Some(1030)
		);
	})
}

# Pallet Relayer

The Hyperbridge protocol is uniquely enabled by cryptographic proofs which certify the integrity of cross-chain transactions. These proofs can be generated by anyone, as they are freely provided by its connected chains. However, the Hyperbridge protocol provides a mechanism to incentivize the generation and submission of these proofs. This is where relayers come in.

Relayers are responsible for collecting and transmitting proofs of cross-chain messages across connected chains. In return, relayers are rewarded with the associated transaction fees that were provided by users and applications. The `pallet-ismp-relayer` module is responsible for tracking the accrued fees and distributing them to the relayers. The module permits relays to withdraw their fees at any time, the module works in conjunction with the [`pallet-host-executive`](/developers/explore/nexus/host-executive) to perform fee withdrawals on the destination chain.
