### Title
Unchecked arithmetic overflow in `SignableTransaction::new` allows bypassing the insufficient-funds check and producing an unspendable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The PCRE bug class is an integer overflow reached by attacker-controlled numeric input during parsing/validation. The analog in `bitcoin-serai` is the unchecked `u64` arithmetic in `SignableTransaction::new`: `payment_sat` is computed with a wrapping `sum::<u64>()` over caller-supplied payment amounts, `needed_fee` is an unchecked `fee_per_vbyte * vbytes` product, and the solvency test `input_sat < (payment_sat + needed_fee)` uses unchecked addition. Overflowing any of these wraps the values and defeats the `NotEnoughFunds`/`TooLowFee` checks, so the machine proceeds to FROST-sign a transaction Bitcoin consensus will reject.

### Finding Description
`SignableTransaction::new` computes its economics entirely in `u64`:

```rust

...

...

  Err(TransactionError::TooLowFee)?;
}
if input_sat < (payment_sat + needed_fee) {               // unchecked add
  Err(TransactionError::NotEnoughFunds { ... })?;
}
...
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) { // unchecked add inside
```

- `payments.iter().map(|payment| payment.1).sum::<u64>()` wraps on overflow (release) or panics (debug). Two payments each `> u64::MAX/2` (both `>= DUST`, so they pass the dust check at line 165-169) wrap `payment_sat` to a small value.
- `input_sat < (payment_sat + needed_fee)` then passes even though the real `tx_outs` contain `Amount::from_sat(payment.1)` for each giant payment — the constructed `Transaction` spends more than its inputs provide.
- `payment_sat + fee_with_change` inside `checked_sub` can itself overflow before the subtraction runs, causing the change logic to be skipped or panic.
- `fee_per_vbyte * vbytes` can overflow to a tiny `needed_fee`, bypassing `TooLowFee` so a transaction is signed that can never relay.

None of these expressions use `checked_*`/`saturating_*`, and no per-payment upper bound (e.g. `MAX_MONEY` = 21e6 BTC) is enforced anywhere in `new`.

### Impact Explanation
The resulting `SignableTransaction` is handed to `TransactionSignMachine::sign`/`complete`, which produces FROST signature shares and a fully signed Bitcoin `Transaction` that consensus-invalidly pays more than its inputs (or pays a sub-relay fee). The threshold group signs an output set that can never confirm: honest processors burn a signing attempt and, critically, the plan's inputs are treated as consumed by a payment that is unspendable — funds are accounted as moved while the transaction can never enter a block. In debug builds the same inputs panic the process (DoS of the signing pipeline). Either way it is reachable corruption of the signing result from numeric input, matching the integer-overflow bug class.

### Likelihood Explanation
The payments and `fee_per_vbyte` are data-driven inputs to `SignableTransaction::new` — they flow from plan/scheduler data, not constants. An attacker able to influence a payment amount (or a plan containing adversarial payment values) can set two `u64` amounts summing past `2^64`, or a `fee_per_vbyte` whose product with `vbytes` overflows. No cryptographic assumption, collusion, or privileged position is required — only large numeric values in fields that are never range-checked against Bitcoin's `MAX_MONEY` or `u64` headroom.

### Recommendation
- Validate each payment amount against `bitcoin::Amount::MAX_MONEY` (or `is_some()`/`to_sat()` bounds) and reject oversized amounts before summing.
- Replace `sum::<u64>()` with a checked fold (`try_fold`/`checked_add`) for `input_sat` and `payment_sat`.
- Use `checked_mul` for `fee_per_vbyte * vbytes` and `checked_add` for `payment_sat + needed_fee` / `payment_sat + fee_with_change`, mapping overflow to a `TransactionError`.
