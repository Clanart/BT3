### Title
Cached FROST preprocess is never consumed, causing nonce reuse across share attempts - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug (CVE-2024-41046) is a counter that is never incremented, so the same resource is released multiple times. The Serai analog is a cached nonce seed that is never deleted or rotated: `SigningProtocol::preprocess_internal` stores the FROST preprocess seed under `CachedPreprocesses: (context) -> [u8; 32]` and `share_internal` rebuilds an `AlgorithmSignMachine` from that identical seed on every call, regenerating the same nonces `(d, e)` each time. Because a `share` attempt that errors (e.g., `FrostError::InvalidPreprocess(p)` blamed on a peer-supplied preprocess) is not terminal, each subsequent attempt with a distinct set of peer preprocesses reuses the same nonce material — a ROS-style nonce-reuse that enables recovery of the validator's MuSig secret share. [1](#0-0) 

### Finding Description
`create_db!` defines `CachedPreprocesses` keyed only by `context` (for `DkgConfirmer`, `(b"DkgConfirmer", attempt)`). In `preprocess_internal`, if no cache exists it generates a fresh preprocess and stores `cache.0` XORed with an encryption key; otherwise it loads the existing seed and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`. There is no `del`, no incrementing index, and no rotation — the same seed deterministically regenerates identical nonces via `ChaCha20Rng::from_seed(*seed.0)` in `seeded_preprocess`. [2](#0-1) [3](#0-2) 

`share_internal` calls `self.preprocess_internal(participants).0` — i.e., every `share()` and every `complete()` re-derives the same `(d, e)` under the same context. `complete()` calls `share_internal` again (`expect("trying to complete a machine which failed to preprocess")`), and any failed `share` (returning `Err(participant)` on a malicious `InvalidPreprocess`/`InvalidShare`) leaves the cache untouched, so a later retry under the same `attempt` reuses the nonce pair with different peer preprocesses, hence different binding factors `rho` and/or different challenge `c`. [4](#0-3) [5](#0-4) 

The module's own header concedes the invariant: "it is explicitly unsafe to reuse nonces across signing sessions... In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — and marks as TODO the check that published commitments match the presumed preprocess before publishing shares. [6](#0-5) 

### Impact Explanation
With the nonce pair `(d, e)` fixed, each signature share is `z_j = d + e·rho_j + λ·s·c_j`. Each distinct attempt (distinct peer preprocess set → distinct `rho_j`, `c_j`) yields one linear equation; after three attempts the peer can solve the 3×3 system for `d`, `e`, and the secret share `s` — full recovery of the validator's MuSig secret share, i.e., compromise of the on-chain validator key used for DKG confirmations (`set_keys_message`). This is the exact consequence the FROST docs warn about: "Reusing preprocesses would enable a third-party to recover your private key share." [7](#0-6) 

### Likelihood Explanation
A participant in the DKG-confirmation MuSig set (or anyone whose bytes reach `read_preprocess` in `share_internal`) can force repeated `share()` invocations under the same `attempt` context by submitting invalid or varying preprocesses across finalized tributary blocks — each failed call blames them but leaves `CachedPreprocesses` intact, and each retry with a modified preprocess set reuses the victim's nonces. This is reachable purely with untrusted preprocess bytes; no malicious-node or colluding-threshold assumption is needed beyond being a signing participant. The residual uncertainty: the header argues BFT ordering prevents distinct finalized message sets, but retries after `FrostError::InvalidPreprocess`/`InvalidShare` (which return `Err` rather than abort the attempt) are not shown to be impossible — handle.rs invocation sites were not fully verified. [8](#0-7) 

### Recommendation
Consume the cache: after `from_cache` in `preprocess_internal` (or after a successful `share`), `del` the `CachedPreprocesses` entry — or store a per-attempt counter that is incremented on each `share` and mixed into the seed — so a seed is usable exactly once. If `share` fails with `InvalidPreprocess`/`InvalidShare`, rotate the seed rather than reusing it. Additionally implement the noted TODO: verify the commitments derived from the cached seed match the preprocess already published on-chain before emitting any share.

### Proof of Concept
1. As a `DkgConfirmer` participant for `attempt = A`, the victim coordinator generates and caches seed `S` under context `(b"DkgConfirmer", A)` on the first `preprocess()`/`share()` call; nonces `d = d(S)`, `e = e(S)` are fixed.
2. Submit a preprocess set `P1`; victim signs `share z1 = d + e·rho1 + λ·s·c1`. Submit a malformed preprocess for another participant so the victim's next attempt still occurs under context `A` (cache still present — no deletion path exists in `preprocess_internal`).
3. Submit a distinct preprocess set `P2` (e.g., drop one peer's preprocess); victim re-derives the same `(d, e)` via `from_cache` and emits `z2 = d + e·rho2 + λ·s·c2`. Repeat for `z3`.
4. Solve the linear system over `{d, e, s}` from `z1, z2, z3` with known `rho_j`, `c_j`, `λ` — recovering the validator's secret share `s`.

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  Additionally, to ensure a rebuilt service isn't flagged as malicious, we have to check the
  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
