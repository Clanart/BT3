### Title
Unrestricted arbitrary file deletion via harvester `delete_plot` RPC (path traversal / missing ownership check) - (File: `chia/plotting/util.py`)

### Summary
The harvester's `delete_plot` RPC endpoint takes a caller-supplied `filename` string and passes it straight through to `os.unlink()` with no check that the path actually refers to a plot file tracked by the harvester's `PlotManager`, nor that it lies inside a configured plot directory. This mirrors the Applio `restart.py` bug class: user-controlled input is used to build a filesystem path for a destructive/administrative operation with no ownership or scope validation, so a caller of the endpoint can act on files/resources that were never legitimately exposed by that endpoint.

### Finding Description
The RPC route `/delete_plot` reads `filename` directly out of the request body: `filename = request["filename"]` and forwards it unmodified to `self.service.delete_plot(filename)` [1](#0-0) .

`Harvester.delete_plot()` wraps the string in a `Path` and calls `remove_plot()`, then triggers a refresh: [2](#0-1) .

`remove_plot()` performs no validation that the path is one of the plots known to `PlotManager`, that it resides under any of the configured `plot_directories`, or that it even has a `.plot`/`.plot2` extension — it simply checks existence and unlinks:

```python
def remove_plot(path: Path):
    log.debug(f"remove_plot {path!s}")
    # Remove absolute and relative paths
    if path.exists():
        path.unlink()
``` [3](#0-2) 

The project's own module documentation confirms this is an accepted gap rather than an oversight in review: "`delete_plot()` unlinks the supplied path, triggers refresh, and emits a `"plots"` state change. There is no extra ownership model in this module; RPC authorization and local file permissions are the relevant gates." [4](#0-3) 

This is the same root-cause shape as the Applio CVE: a caller-supplied string flows unsanitized into a path used for a destructive filesystem operation (`unlink` here vs. `kill` in Applio), and the only real protection is the outer authorization layer (RPC/TLS cert) rather than any check that the target is actually one the endpoint is meant to manage. Any relative path segment (`../../...`) or absolute path supplied as `filename` is accepted as-is, so the RPC caller is not restricted to files inside `harvester.plot_directories` or even to `.plot` files.

### Impact Explanation
A party with access to the harvester's local RPC (a "local RPC caller" — the harvester RPC is TLS/cert-gated but not scoped to plot ownership) can delete arbitrary files reachable by the harvester process's OS permissions by supplying a traversal path in `filename`. Depending on target, this can:
- Delete the node's/harvester's config files, keyring/cache files, or other Chia data-directory contents, producing a denial of service to the harvester/farmer service.
- If the harvester process runs with broader filesystem permissions (common in shared-service deployments), delete files outside the Chia root entirely.

This matches the "spend-triggered transaction-processing halt" / DoS class called out in scope, adapted to the harvester/RPC-authorization surface: a normally-limited RPC action (delete a *known plot*) is turned into an unrestricted file-deletion primitive.

### Likelihood Explanation
Exploitation requires the ability to call the harvester RPC at all (the same prerequisite as calling any other harvester RPC endpoint such as `add_plot_directory`/`remove_plot_directory`). Given that access, the exploit itself is a single RPC call with a crafted `filename` value — no additional race conditions or timing are needed, making likelihood high once RPC access is available (the reachable low-privilege scenario is a locally-authorized RPC client, consistent with the "local RPC caller" role in scope).

### Recommendation
Before unlinking, `remove_plot()` (or `Harvester.delete_plot()`) should:
1. Resolve the requested path and verify it is a plot currently tracked by `self.plot_manager.plots` (i.e., known and previously reported via `get_plots()`), rejecting anything not in that set.
2. Additionally verify the resolved path is contained within one of the configured `harvester.plot_directories` (`get_plot_directories(root_path)`), rejecting traversal outside those roots.
3. Reject non-`.plot`/`.plot2` targets defensively even if the above checks are bypassed by a bug.

### Proof of Concept
Given local RPC access to the harvester service:
```python
await harvester_rpc_client.fetch("delete_plot", {"filename": "../../../../etc/some_target_file"})
```
This reaches `HarvesterRpcApi.delete_plot()` → `Harvester.delete_plot()` → `remove_plot()`, which unlinks the resolved path with no ownership/scope check, since `remove_plot()` only checks `path.exists()` before calling `path.unlink()` [3](#0-2) .
