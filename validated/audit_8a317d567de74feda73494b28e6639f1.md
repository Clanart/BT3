## Title
Cross-Function Beneficiary/Withdrawal Signature Replay via Identical Message Hashing Between `accumulate_fees` and `withdraw_fees` — ([File: modules/pallets/relayer/src/accumulate.rs] / [File: modules/pallets/relayer/src/withdrawal.rs])

## Summary
The specific target named in the question, `pallet_ismp_relayer::claim_outbound_request_delivery_reward` → `process_outbound_request_delivery_claim`, is **not** vulnerable to the described replay: its signed payload `outbound_request_delivery_message(commitment, dest_chain, payee)` [1](#0-0)  hashes an `H256` commitment first, which cannot collide with any other signed message format in the pallet, and reuse is additionally blocked by the one-time `OutboundRequestsClaimed[commitment]` tag checked before payout [2](#0-1) .

However, the exact exploit pattern described in the question ("reuse a relayer signature or beneficiary signature under a different nonce, destination, or payee context… two public flows that share one byte string") **is present elsewhere in the same pallet**, between `accumulate_fees`'s beneficiary redirect and `withdraw_fees`.

## Finding Description
Two independent signed-message constructors in `pallet-ismp-relayer` produce byte-identical SCALE encodings for the same `(nonce, state_machine, beneficiary_bytes)` input:

- `withdrawal.rs::message(nonce, dest_chain, Some(beneficiary))` → `keccak_256((nonce: u64, dest_chain: StateMachine, beneficiary: Vec<u8>).encode())` [3](#0-2) 
- `accumulate.rs::beneficiary_message(nonce, state_machine, beneficiary)` → `keccak_256((nonce: u64, state_machine: StateMachine, beneficiary: &[u8]).encode())` [4](#0-3) 

`Vec<u8>` and `&[u8]` encode identically in SCALE (compact length prefix + raw bytes), so for equal `(nonce, chain, beneficiary)` these two functions return the **same 32-byte hash**, meaning a signature produced for one context verifies successfully in the other.

Both call sites also share the exact same `Nonce<T>` storage, keyed by `(address, state_machine)`:
- `accumulate.rs`: `Nonce::<T>::get(&delivery_address, state_machine)` [5](#0-4) 
- `withdrawal.rs`: `Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain)` [6](#0-5) 

Critically, in `withdraw_fees` the "address" used to look up the nonce, debit `Fees`, and select the message is taken **directly from the caller-supplied `Signature::Sr25519`/`Ed25519` variant's `public_key` field**, not independently anchored to any proof: [7](#0-6)  — any unprivileged caller can submit any `(public_key, signature)` pair they have observed, as long as it verifies over the message.

In `accumulate_fees`, by contrast, the analogous signer check binds the signature to the state-proof-derived `delivery_address` (`signature.verify(&msg, Some(delivery_address.clone()))`) [8](#0-7) , but `withdraw_fees`'s Sr25519/Ed25519 branches call `.verify(&msg, None)` with no external anchor [9](#0-8) .

**Attack path:** A relayer signs `beneficiary_message(n, C, B)` intending only to redirect the fee accrued from one specific delivery batch to beneficiary `B` via `accumulate_fees`. This `(public_key, signature)` pair is broadcast publicly as part of the (unsigned) extrinsic. An unprivileged attacker observes it and, before the original `accumulate_fees` call lands, submits `withdraw_fees(WithdrawalInputData { signature: Signature::Sr25519{ public_key: relayer_key, signature }, dest_chain: C, beneficiary: Some(B) })`. Because the message hash is identical and `Nonce(relayer_key, C)` is still `n`, verification succeeds and the pallet withdraws the **entire currently-accumulated `Fees[C][relayer_key]` balance** (not just the intended single-delivery amount) to `B`, and advances `Nonce(relayer_key, C)` to `n+1`. This both breaks the amount-scoping the relayer intended and desynchronizes the shared nonce, causing the legitimate `accumulate_fees`/`withdraw_fees` transaction (still signed against nonce `n`) to fail once it lands.

This directly matches the invariant violation named in the question: *"each withdrawal or payee redirection signature must be single-use and bound to the exact destination chain and beneficiary"* — here a beneficiary-redirect signature scoped to accumulation of one delivery's fee is reinterpreted, via identical message bytes, as authorization for a full-balance withdrawal through a different, unprivileged, publicly reachable entrypoint.

## Impact Explanation
An unprivileged attacker can force early, out-of-scope withdrawal of a relayer's full accumulated fee balance on a chain, using a signature the relayer only intended for a narrower purpose (redirecting one delivery's accrued fee), and can grief legitimate relayer transactions by desynchronizing the shared nonce. Because `withdraw_fees`'s signer binding for Sr25519/Ed25519 is not independently anchored (relies solely on caller-supplied `public_key`), any publicly observed signature over this specific message shape is replayable cross-function. This falls under "broken timeout/refund/reward accounting" and "wrong beneficiary or amount" in the Decision Standard, since the withdrawn amount and timing no longer match what the signer approved.

## Likelihood Explanation
Requires: (1) a relayer to use the `beneficiary_details` redirect path in `accumulate_fees` at least once (a supported, documented flow, not malicious behavior) [10](#0-9) ; (2) the attacker observing the signature in a public extrinsic/mempool before it lands; (3) racing/front-running the actual `accumulate_fees` submission with a `withdraw_fees` call using the identical bytes. No relayer collusion or compromise is needed — this is exploitable purely from unprivileged, publicly reachable calls.

## Recommendation
Domain-separate the two signed message constructors (e.g., prepend a distinct context tag/discriminant byte or function selector to `message()` and `beneficiary_message()` before hashing) so identical `(nonce, chain, beneficiary)` tuples never produce the same hash across functions. Additionally, anchor `withdraw_fees`'s Sr25519/Ed25519 signer to something the caller cannot freely supply (e.g., require the recovered/verified public key to match a stored relayer identity, mirroring the `Some(delivery_address)` anchoring already used in `accumulate_fees`), rather than trusting the caller-provided `public_key` field directly.

## Proof of Concept
1. Relayer submits `accumulate_fees` with `withdrawal_proof.beneficiary_details = Some((B, sig))` where `sig` verifies over `beneficiary_message(n, C, B)`, `n = Nonce(relayer_key, C)`.
2. Attacker extracts `(relayer_key, sig)` from the pending/broadcast extrinsic.
3. Attacker submits `withdraw_fees(WithdrawalInputData{ signature: Signature::Sr25519{public_key: relayer_key, signature: sig}, dest_chain: C, beneficiary: Some(B) })` before step 1 finalizes.
4. `message(n, C, Some(B))` == `beneficiary_message(n, C, B)` (byte-identical), so `.verify(&msg, None)` succeeds; `Fees::<T>::get(C, relayer_key)` (full balance) is dispatched to `B`, and `Nonce(relayer_key, C)` becomes `n+1`.
5. The original `accumulate_fees` call, when it lands, now signs/verifies against stale nonce `n` and fails against the mutated nonce state (or, if it lands first, the reverse ordering still causes the following legitimate `withdraw_fees`/`accumulate_fees` call by the relayer to fail due to nonce desync).

Note: I could not fully trace whether any additional runtime-level transaction-priority or `validate_unsigned` ordering guarantees prevent the attacker's `withdraw_fees` from being included ahead of the relayer's `accumulate_fees` in practice; this would need to be confirmed with a running node/testnet, which is outside what static code review can determine with certainty.
