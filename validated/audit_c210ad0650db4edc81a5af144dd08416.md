### Title
OP_RETURN data is excluded from transaction weight and fee accounting - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

`SignableTransaction::new` adds a caller-controlled OP_RETURN output before calculating the transaction’s weight and required fee, but `calculate_weight_vbytes` receives only `payments` and the optional change output, not the OP_RETURN output. [1](#0-0)  Consequently, the returned transaction can contain an output that was never included in `needed_fee`, the minimum-relay check, or the transaction-weight check. [2](#0-1) 

### Finding Description

`calculate_weight_vbytes` constructs a mock transaction using only payment outputs and, optionally, one change output. [3](#0-2)  In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs`, after which weight and vbytes are calculated from `payments` rather than from `tx_outs`. [4](#0-3)  The change calculation repeats the same omission by passing only `payments` and `change`, even though the final transaction already contains the OP_RETURN output. [5](#0-4) 

An 80-byte OP_RETURN produces an additional serialized output of approximately 91 non-witness bytes, corresponding to roughly 91 additional vbytes, while `data` of up to 80 bytes is accepted. [6](#0-5)  When change is present, `input_sat - payment_sat - underestimated_fee` is assigned to the change output, so the actual transaction fee remains the underestimated `needed_fee` while the transaction’s actual vsize is larger. [7](#0-6) 

### Impact Explanation

A transaction constructed at the default minimum relay feerate can be signed successfully but carry less than the required fee for its real size. [8](#0-7)  If the resulting transaction is queued for broadcast, standard mempool relay policy can reject it, causing outbound-processing failure until the transaction is rebuilt with a higher fee. [9](#0-8) 

This is the same accounting-desynchronization class as the reference issue: an output/state component is added to the final operation, while the accounting used to validate and price that operation omits it. [1](#0-0) 

### Likelihood Explanation

The issue is directly reachable through the public `SignableTransaction::new` `data` parameter and requires no malformed encoding, leaked key, malicious validator, or consensus failure. [10](#0-9)  Supplying an OP_RETURN payload and a change output while requesting a minimum or tight feerate is sufficient to make the calculated fee lower than the fee required for the actual transaction. [11](#0-10) 

### Recommendation

Calculate weight and vbytes from the complete output set, including the OP_RETURN output, for both the no-change and change cases. [12](#0-11)  A straightforward fix is to make `calculate_weight_vbytes` accept the final `tx_outs` shape—or an explicit OP_RETURN/data parameter—and to apply the maximum-standard-weight and minimum-relay checks against the resulting vsize. [13](#0-12) 

Add a regression test that creates a transaction with an 80-byte OP_RETURN and change at `fee_per_vbyte = 1`, then verifies that its calculated fee is at least the minimum relay fee for the witness-inclusive transaction size. [14](#0-13) 

### Proof of Concept

```rust
// Conceptual reproduction against networks/bitcoin/src/wallet/send.rs.

let inputs = vec![received_output_with_10_000_sats];
let payments = [(payment_script, DUST)];
let change = Some(change_script);
let data = Some(vec![0x42; 80]);
let fee_per_vbyte = 1;

let tx = SignableTransaction::new(
    inputs,
    &payments,
    change,
    data,
    fee_per_vbyte,
).unwrap();

// `needed_fee` is calculated as 1 * vbytes_without_op_return.
assert_eq!(tx.needed_fee(), fee_per_vbyte * underestimated_vbytes);

// The actual transaction has one additional serialized OP_RETURN output.
assert_eq!(
    tx.transaction().output.len(),
    payments.len() + 1 /* OP_RETURN */ + 1 /* change */
);

// Because change consumes the remainder, the actual fee equals the
// underestimated `needed_fee`, while the real transaction is about 91
// vbytes larger. Its effective feerate is therefore below 1 sat/vbyte,
// despite the minimum-relay check having passed.
```

The root cause is visible without executing the code: the OP_RETURN is appended to `tx_outs`, but the subsequent weight calculation still uses `payments` and omits `tx_outs` entirely. [1](#0-0)

impl SignableTransaction {
  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }

    let weight = tx.weight();

    // Now calculate the size in vbytes

    /*
      "Virtual transaction size" is weight ceildiv 4 per
      https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki

      https://github.com/bitcoin/bitcoin/blob/306ccd4927a2efe325c8d84be1bdb79edeb29b04
        /src/policy/policy.cpp#L295-L298
      implements this almost as expected, with an additional consideration to signature operations

      Signature operations (the second argument of the following call) do not count Taproot
      signatures per https://github.com/bitcoin/bips/blob/master/bip-0342.mediawiki#cite_ref-11-0

      We don't risk running afoul of the Taproot signature limit as it allows at least one per
      input, which is all we use
    */
    (
      weight.to_wu(),
      u64::try_from(bitcoin::policy::get_virtual_tx_size(
        i64::try_from(weight.to_wu()).unwrap(),
        0i64,
      ))
      .unwrap(),
    )
  }

    // bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE is in sats/kilo-vbyte

    }

    if input_sat < (payment_sat + needed_fee) {
      Err(TransactionError::NotEnoughFunds {
        inputs: input_sat,
        payments: payment_sat,
        fee: needed_fee,

    }

    // If there's a change address, check if there's change to give it
    if let Some(change) = change {
